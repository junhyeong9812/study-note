# css/syntax/34 — 뷰포트 단위와 컨테이너 단위 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 **모든 수치는 Google Chrome 151.0.7922.173 headless 에서 실제로 렌더해 잰 값**이다. 단위는 px 다.\
> **뷰포트가 주제이므로 `--window-size` 를 바꿔 가며 세 판을 쟀다**(800×600 · 375×667 · 1200×400).\
> ★ **`svh`/`lvh`/`dvh` 가 갈리는 것은 이 환경에서 재지 못했다** — headless 에 접히는 주소창이 없다. 해당 답에 그렇게 적었다.\
> **손으로 계산해 유도한 수치는 없다.** 규칙은 [CSS Values and Units 4](https://drafts.csswg.org/css-values-4/) 와 [CSS Containment 3](https://drafts.csswg.org/css-contain-3/) 으로 접지했다.

## 정답

### 1. `100vw` 와 `100%` 가 갈린다

**실행 결과** (Chrome 151 headless, `--window-size=800,600`)

```text
  window.innerWidth            = 800
  documentElement.clientWidth  = 785
  스크롤바 폭                   = 15

  width: 100vw 상자 = 800px
  width: 100%  상자 = 785px

  documentElement.scrollWidth = 800 > clientWidth 785
    => 가로로 15px 스크롤된다
```

```text
  세로 스크롤바가 있을 때              없을 때 (.tall 을 지우면)
  +--------------------------+-+      +----------------------------+
  | 100vw 상자      800px    | |      | 100vw 상자        780px    |
  +--------------------------+S|      +----------------------------+
  | 100%  상자  785px      |  |c|      | 100%  상자        780px    |
  +------------------------+  |r|      +----------------------------+
   => 15px 이 삐져나가 가로          => 둘이 같아지고 가로 스크롤도
      스크롤바가 하나 더 생긴다          없어진다 (demo 로 확인)
```

**왜 그런가**

- **`vw` 의 「창」에는 세로 스크롤바 자리가 포함된다.** 명세가 뷰포트로 정의했기 때문이다.
- `%` 는 **부모의 content 폭**을 본다. 스크롤바가 빠진 785 다.
- 그래서 `100vw` 상자가 15px 넘치고, **그 넘침이 가로 스크롤을 만든다.**
- `.tall` 을 지우면 **세로 스크롤바가 사라져 둘이 같아진다.** 스크롤바가 없으면 차이도 없다 — 그래서 「어떤 페이지에서만」 생기는 버그가 된다.
- 15 는 **이 환경의 스크롤바 폭**이다. 오버레이 스크롤바 환경에서는 0 일 수 있다 — **보장이 아니라 관찰이다.**

### 2. 창 크기를 세 번 바꿔 잰다

**실행 결과**

```text
  창 (innerWidth x innerHeight)   10vw   10vh         10vmin       10vmax
  ------------------------------  -----  -----------  -----------  -------
  800 x 513                       80     51.296875    51.296875    80
  500 x 580   (★ 375 를 줬으나     50     58           50           58
               Chrome 하한 500)
  1200 x 313                      120    31.296875    31.296875    120

  같은 판의 논리 축
  1200 x 313                      10vi = 120      10vb = 31.296875
```

**왜 그런가**

- `1200 × 313` 판에서 **가장 큰 것은 `10vmax` = 120**(= `10vw`), **가장 작은 것은 `10vmin` = 31.296875**(= `10vh`)다.
- **`vmin`/`vmax` 는 물리적으로 짧은 쪽 / 긴 쪽**을 고른다. 이 판은 가로가 길어 `vmax`=가로, `vmin`=세로가 됐다.\
  `500 × 580` 판에서는 세로가 길어 **`vmax` 가 세로(58)** 로 뒤집혔다 — 축이 고정이 아니라는 증거다.
- **`vi`/`vb` 는 논리 축**(글이 흐르는 축 / 줄이 쌓이는 축)이다. 가로쓰기에서는 `vi`=`vw`, `vb`=`vh` 로 **같았다**.\
  세로쓰기(`writing-mode: vertical-rl`)에서 둘이 뒤집히는데, **이 문서는 세로쓰기를 재지 않았다**(정본은 [목록의 **32번 주제**](../32-logical-properties-and-writing-mode/)).

### 3. `svh`·`lvh`·`dvh` 셋

**실행 결과** — ★ **세 값이 전부 같게 나왔다**

```text
  창 (innerWidth x innerHeight)   10vh         10svh        10lvh        10dvh
  ------------------------------  -----------  -----------  -----------  -----------
  800 x 513                       51.296875    51.296875    51.296875    51.296875
  500 x 580                       58           58           58           58
  1200 x 313                      31.296875    31.296875    31.296875    31.296875

  가로도 같았다 (800x600 판): 100vw = 100svw = 100lvw = 100dvw = 800
```

**왜 그런가**

- **headless 에는 접히는 주소창이 없다.** 작은·큰·동적 뷰포트가 물리적으로 같은 영역이라 셋이 갈릴 수 없다.
- 그러므로 **이 문서는 셋이 갈리는 것을 재지 못했다.** 아래 서술은 전부 명세(css-values-4)에 기댄 것이다.
  - **`svh`(small)** — 브라우저 UI 가 **전부 보일 때**의 높이. 가장 작다.
  - **`lvh`(large)** — UI 가 **전부 접혔을 때**의 높이. 가장 크다.
  - **`dvh`(dynamic)** — **지금 이 순간** 보이는 높이. 스크롤 중에 값이 변한다.
  - `svh` ≤ `dvh` ≤ `lvh`.
- **`100vh` 는 `100lvh` 와 같게 정의돼 있다.** 그래서 주소창이 펼쳐진 모바일에서 **아래가 잘린다.**
- **대가** — `svh` 는 **안 잘리는 대신 빈 자리가 남고**, `lvh` 는 **꽉 차는 대신 잘리고**, `dvh` 는 **항상 맞는 대신 스크롤 중에 레이아웃이 움직인다.**
- 값이 갈리는 환경은 **모바일 브라우저**다. 재려면 실제 단말이나 UI 가 접히는 브라우저가 필요하다.

### 4. 컨테이너 단위를 등록 없이 쓴다

**실행 결과** (카드 300×150, 창 800×513, `container-type` 선언 없음)

```text
  50cqw   -> 400        <- 뷰포트 폭 800 의 50%
  50cqi   -> 400
  50cqb   -> 256.5      <- 뷰포트 높이 513 의 50%
  50cqmin -> 256.5
  50cqmax -> 400
```

**왜 그런가**

- **`.t` 의 폭은 400px 다** — 카드(300)가 아니라 **뷰포트**를 봤다.
- 명세가 그렇게 정했다 — **적격한 컨테이너를 못 찾으면 작은 뷰포트(small viewport)로 떨어진다.**
- **에러도 경고도 나오지 않는다.** CSS 는 에러가 없는 언어라 이런 자리가 조용히 지나간다.
- **진단 3창** 중 세 번째, **`getComputedStyle` 창**으로만 잡힌다 —
  - `cssRules` 에는 `width: 50cqw` 가 **멀쩡히 담겨 있고**,
  - `querySelectorAll` 은 **잡히고**,
  - **계산값만 엉뚱하다.**
  - 「담겼는데 졌나」가 아니라 「**담겼고 이겼는데 기준이 다르다**」는 제5의 상태다([07번](../07-syntax-and-error-recovery/2-summary.md)의 분류에 없던 자리다).

### 5. `container-type: inline-size` 의 경계

**실행 결과** (카드 300×150, 창 800×513)

```text
  container-type: inline-size
     50cqw   -> 150       <- 카드 폭 300 의 50%
     50cqi   -> 150
     50cqb   -> 256.5     <- ★ 뷰포트 높이 513 의 50%  (카드가 아니다)
     50cqh   -> 256.5

  container-type: size 로 올리면
     50cqw   -> 150
     50cqb   -> 75        <- 카드 높이 150 의 50%
```

**왜 그런가**

- **`.w` = 150px, `.b` = 256.5px** 다.
- `inline-size` 는 이름 그대로 **인라인 축만 컨테인먼트한다.** 블록 축은 컨테인먼트되지 않았으므로 **컨테이너로 인정되지 않고**, 기준이 뷰포트로 새어 올라간다.
- 근거는 대조 실측이다 — 같은 카드를 `container-type: size` 로 바꾸자 `50cqb` 가 **256.5 에서 75 로** 떨어졌다.
- **두 축을 다 쓰려면 `container-type: size`** 로 올려야 한다. 그것은 **높이까지 컨테인먼트**한다는 뜻이고, 그 대가(내용이 높이를 정하지 못하게 된다)는 [목록의 **40번 주제**](../40-container-and-style-queries/)가 정본이다.

### 6. `cqmin` 이 축을 섞는다

**실행 결과**

```text
  container-type: inline-size (카드 300x150, 뷰포트 800x513)
     50cqmin -> 150       <- 카드 인라인 300 쪽
     50cqmax -> 256.5     <- 뷰포트 높이 513 쪽

  container-type: size
     50cqmin -> 75        <- 카드 높이 150 쪽
     50cqmax -> 150       <- 카드 폭 300 쪽
```

**왜 그런가**

- `inline-size` 판에서는 **한 축은 카드(300), 한 축은 뷰포트(513)** 라 둘을 비교한 결과가 섞인다.\
  300 < 513 이므로 `cqmin` 은 카드를, `cqmax` 는 뷰포트를 골랐다.
- `size` 로 올리면 **두 축이 모두 카드 안에서 정해져** 직관대로 돈다 — 짧은 쪽 150, 긴 쪽 300.
- 교훈은 「**`cqmin`/`cqmax` 의 값을 보고 컨테이너 크기를 역산하지 말라**」는 것이다. 한 축이 밖을 보고 있을 수 있다.

### 7. 기준을 찾아 올라가는 경로

**왜 그런가**

```text
    %                        cqi                      vw
    자기                     자기                     자기
     ↓ 한 칸                  ↓ 조상을 훑어 올라가며    (아무 데도 안 간다)
    부모  <- 멈춘다           container-type 이         창 하나
                              선언된 첫 상자
                              못 찾으면 -> 작은 뷰포트
```

- **`%` 는 한 칸**(부모)만 본다. 부모가 크기를 안 정했으면 거기서 안 풀린다(`height: 50%` + 부모 `auto` — [33번](../33-length-units/2-summary.md)).
- **`cqi` 는 조상을 훑는다.** 중간에 어떤 상자가 끼어도 같은 컨테이너 아래면 값이 같다.
- **`vw` 는 아무것도 안 훑는다.** 문서가 몇 겹 안에 있든 창 하나다.
- 그래서 **사이드바에서 글자가 안 줄어드는 쪽은 `vw` 로 짠 것**이다. 창은 그대로이므로 값도 그대로다.\
  `cqi` 로 짜면 카드 폭을 따라가므로 사이드바에서 저절로 작아진다 — 본문 (5) 의 demo 가 그 실측이다(`10cqi` 가 40px 대 15px).

### 8. 모바일에서 화면이 잘린다

**왜 그런가**

```text
  세 높이가 한 화면에서 어디까지인가 (명세 기준 — 이 환경에서는 재지 못했다)

  +----------------------+  <- lvh 의 위          100vh == 100lvh
  | [주소창]             |
  +----------------------+  <- svh 의 위
  |                      |
  |   dvh = 지금 이 순간  |   svh <= dvh <= lvh
  |   (스크롤하면 변한다) |
  +----------------------+  <- svh 의 아래
  | [하단 툴바]          |
  +----------------------+  <- lvh 의 아래
```

- `height: 100vh` 는 명세상 **`100lvh`** 와 같다 — **UI 가 전부 접혔을 때의 높이**다.
- 주소창이 펼쳐져 있으면 실제 보이는 영역이 그보다 작으므로, **아래쪽이 UI 에 가려 잘린다.**
- **`dvh` 로 바꾸면** — 얻는 것: 어느 순간에도 정확히 화면에 맞는다. 잃는 것: **스크롤하는 동안 높이가 계속 변해 레이아웃이 움직인다.**
- **`svh` 로 바꾸면** — 얻는 것: 어느 상태에서도 **절대 안 잘린다.** 잃는 것: UI 가 접히면 아래에 **빈 자리가 남는다.**
- ★ **이 문서는 그 차이를 재지 못했다**(질문 3). 명세로만 접지했다.

### 9. 이 환경에서 못 잰 것

**왜 그런가**

- **재지 못한 것 ①** — `svh`/`lvh`/`dvh` 가 **갈리는 것**. headless 창에는 접히는 주소창이 없어 세 값이 같게 나왔다.\
  값을 셋 다 받아 놓고 **같았다고 적는 것**이 정직한 기록이다. 「갈린다」를 실측인 양 적으면 거짓이 된다.
- **재지 못한 것 ②** — **세로쓰기에서 `vi`/`vb` 가 뒤집히는 것**. 이 문서에서 `writing-mode` 를 건드리지 않았다.
- **재지 못한 것 ③** — **오버레이 스크롤바에서 `100vw`** 가 어떻게 되는지. 이 환경에서 만들 수 없는 조건이다.
- **스크롤바 폭 15px 은 관찰이다.** 명세가 정한 수치가 아니고 환경·설정에 따라 다르다.\
  **보장인 것은 「`vw` 가 스크롤바를 포함한다」는 성질**이지 15 라는 숫자가 아니다.
- **`--window-size=375,667` 판을 「375px 판」이라 부를 수 없는 이유** — `innerWidth` 를 읽으니 **500** 이었다. Chrome 에 창 폭 하한이 있어 375 로 줄지 않았다.\
  그 판의 수치는 전부 **폭 500 기준**이다. 요청한 값이 아니라 **실제로 읽힌 값**을 기준으로 적어야 한다.

### 10. 다른 주제로 잇기

- **`@container` 질의와 `container-type` 의 대가** — [목록의 **40번 주제**](../40-container-and-style-queries/)(컨테이너 쿼리와 스타일 쿼리)가 정본이다. 이 편은 **단위까지**다.
- **창 크기로 규칙을 갈라 쓰는 문법** — [목록의 **38번 주제**](../38-media-queries/)(미디어 쿼리). 이 편은 **창 크기를 길이로 쓰는 것**까지다.
- **유동 타이포의 상하한** — [35번](../35-calc-clamp-min-max/2-summary.md)의 `clamp(16px, 4vw, 24px)`.
- **`vi`/`vb` 의 축 규칙** — [목록의 **32번 주제**](../32-logical-properties-and-writing-mode/)(논리 속성과 글쓰기 방향).
- **단위 일반**(`%`·`em`·`rem`·`ch`) — [33번](../33-length-units/2-summary.md).

## 용어 풀이

- **뷰포트(viewport)** — 문서가 그려지는 창 안쪽 영역. 예: 실측에서 창 800px 중 785px 이 문서 자리, 15px 이 세로 스크롤바였다.
- **`vw` / `vh`** — 뷰포트 폭 / 높이의 1%. **스크롤바 자리를 포함한다.** 예: 실측 `100vw` 800 대 `100%` 785.
- **`vmin` / `vmax`** — 뷰포트의 짧은 쪽 / 긴 쪽의 1%. 예: 1200×313 판에서 `10vmin` 31.296875, `10vmax` 120.
- **`vi` / `vb`** — 인라인 축 / 블록 축의 1%. 가로쓰기에서는 각각 `vw`/`vh` 와 같았다.
- **작은 / 큰 / 동적 뷰포트** — UI 가 전부 보일 때 / 전부 접혔을 때 / 지금 이 순간의 영역. `sv*`/`lv*`/`dv*` 가 각각을 잰다. ★ 이 문서에서 **갈리는 것을 재지 못했다**.
- **`container-type`** — 그 요소를 컨테이너로 등록하는 속성. `inline-size` 는 인라인 축만, `size` 는 두 축을 컨테인먼트한다.
- **`cqw`/`cqh`/`cqi`/`cqb`** — 컨테이너의 폭/높이/인라인/블록 크기의 1%. 가로쓰기에서 `cqi`=`cqw`, `cqb`=`cqh` 였다.
- **`cqmin`/`cqmax`** — 컨테이너의 두 축 중 짧은/긴 쪽의 1%. 예: `inline-size` 판에서 한 축이 뷰포트라 값이 섞였다(150 대 256.5).
- **컨테인먼트(containment)** — 상자 안의 레이아웃 계산을 밖과 끊는 것. 끊겨 있어야 「컨테이너 → 안쪽」이 순환 없이 풀린다.
- **진단 3창** — `cssRules`(담겼나) · `querySelectorAll`(잡혔나) · `getComputedStyle`(이겼나). 정본은 [07번](../07-syntax-and-error-recovery/2-summary.md).

**재지 못한 것** — ① `svh`/`lvh`/`dvh` 가 **갈리는 것**(headless 에 접히는 주소창이 없다) ② **세로쓰기**에서 `vi`/`vb` 가 뒤집히는 것 ③ **오버레이 스크롤바** 환경의 `100vw` ④ `--window-size=375` 판(Chrome 하한 500 에 걸렸다).\
**구현 의존 항목** — 스크롤바 폭 15px · `innerHeight` 가 창 높이보다 작은 것(600 → 513) · 창 폭 하한 500 은 전부 **이 환경의 Chrome 151 관찰**이다.\
**엔진은 Chrome 하나다.** Firefox 155.0.1 은 이 환경에서 headless 산출이 조용히 실패하고 WebKit 은 이 머신에 없다 — **「두 엔진에서 확인했다」고 적지 않았다.**
