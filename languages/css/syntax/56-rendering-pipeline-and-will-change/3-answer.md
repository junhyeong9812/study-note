# css/syntax/56 — 렌더링 파이프라인과 `will-change`: 무엇이 합성만으로 도는가 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 **모든 수치는 Google Chrome 151.0.7922.173 headless 에서 실제로 측정한 것**이다.\
> 도구는 **CDP `Performance.getMetrics`**(`RecalcStyleCount`·`LayoutCount`·`LayoutDuration`)와 **CDP `Tracing` 도메인**(`devtools.timeline` 의 `UpdateLayoutTree`·`Layout`·`PrePaint`·`Paint`·`Commit`·`RasterTask`)이다.\
> ★★ **못 잰 것이 있다** — **합성 레이어의 수와 메모리**는 이 환경에서 못 쟀다(문항 9). 그 대목은 「못 쟀다」로 적혀 있고, 관련 주장은 **명세의 서술**로만 인용한다.\
> 규칙은 [CSS Containment Level 2](https://drafts.csswg.org/css-contain-2/) 와 [CSS Will Change Level 1](https://drafts.csswg.org/css-will-change-1/) 로 접지했다.

### 1. 네 공정과 그 순서

**순서**

```text
  스타일 재계산 ──> 레이아웃 ──> 페인트 ──> 합성 ──> 화면
```

**뒤 공정도 도나**

- **돈다.** 레이아웃이 다시 돌면 그 아래가 전부 따라 돈다.\
  실측이 그것을 보인다 — `width` 를 애니메이션하면 `Layout` 120·`Paint` 240 이 같이 올라갔고, `color` 는 `Layout` 0 인데 `Paint` 240 이었다.

**명세 용어인가**

- ★ **아니다. 구현 용어다.** 「레이아웃·페인트·합성」은 명세가 정의한 단계가 아니라 엔진이 쓰는 이름이다.\
  그래서 이 문서는 **Chrome 151 의 카운터 이름으로** 접지한다.

**판단 규칙 한 줄**

- **「이 속성이 어느 공정에 처음 닿는가」로 고른다.** 앞 공정에 닿을수록 비싸다.

### 2. 무엇으로 재는가

**스크린샷으로 되나**

- **안 된다.** 두 움직임의 화면 좌표가 **매 시각 같기 때문**이다(문항 4 실측).\
  `--disable-gpu` 의 픽셀은 보장도 아니므로 **합성 여부를 픽셀로 판정하지 않는다.**

**`Performance.getMetrics` 의 카운터 셋**

```text
  RecalcStyleCount    스타일 재계산 횟수
  LayoutCount         레이아웃 횟수
  LayoutDuration      레이아웃에 쓴 시간(초)
```

- 쓰는 법: **애니메이션 전후로 두 번 읽어 증가분**을 본다.

**페인트 횟수**

- ★ **`Performance.getMetrics` 에는 페인트 카운터가 없다.**
- 그래서 **`Tracing` 도메인**(`devtools.timeline`)을 켜고 이벤트를 셌다 — `PrePaint`·`Paint`·`Commit`·`RasterTask`.

**신호 대 잡음**

- **정지 대조군**(값이 바뀌지 않는 애니메이션)을 같이 돌렸고, 그 대조군이 **여섯 칸 전부 0** 이었다.\
  그러므로 120 이라는 값은 **측정 자체가 만들어 낸 잡음이 아니다.**
- 그리고 **각 속성을 3판씩** 돌려 판마다의 흔들림(120 대 121)을 그대로 적었다.

### 3. 이 열세 속성은 각각 어디부터 도는가

**출력** (Chrome 151 headless — 2초 × 3판. 판마다 다르면 `/` 로 나눠 적었다)

| 애니메이션한 속성 | Style | Layout | PrePaint | Paint | Commit | Raster |
|---|---|---|---|---|---|---|
| `width` | 121/120/120 | 121/120/120 | 121/120/120 | 242/240/240 | 121/120/120 | 176/174/175 |
| `height` | 121 | 121 | 121/120/121 | 242/240/242 | 121/120/121 | 121/120/121 |
| `left` | 120/120/121 | 120/120/121 | 120 | 240 | 120 | 175/175/174 |
| `margin-left` | 120/120/121 | 120/120/121 | 120/121/121 | 240/242/242 | 120/121/121 | 175/176/176 |
| `font-size` | 120/121/120 | 120/121/120 | 120/121/120 | 240/242/240 | 120/121/120 | 120/121/120 |
| `color` | 121/121/120 | **0** | 121/121/120 | 242/242/240 | 121/121/120 | 121/121/120 |
| `box-shadow` | 120/120/121 | **0** | 120/121/120 | 240/242/240 | 120/121/120 | 120/121/120 |
| `border-radius` | 121/120/120 | **0** | 121/120/120 | 242/240/240 | 121/120/120 | 121/120/120 |
| `filter` | 121/121/120 | **0** | 120/121/120 | **0** | 120/121/120 | **0** |
| `visibility` | 120/120/121 | **0** | 120 | **0** | 120 | **0** |
| `background-color` | **0** | **0** | **0** | **0** | **0** | 121/121/120 |
| **`transform`** | **0** | **0** | **0** | **0** | **0** | **0** |
| **`opacity`** | **0** | **0** | **0** | **0** | **0** | **0** |
| (정지 대조군) | 0 | 0 | 0 | 0 | 0 | 0 |

**둘 다 0 인 것**

- **`transform`·`opacity`·`background-color`** 셋이다. 앞의 둘은 여섯 칸 전부 0 이고, `background-color` 는 `RasterTask` 만 돈다.

**`Layout` 0 인데 `Paint` 는 도는 것**

- **`color`·`box-shadow`·`border-radius`.** 자리는 그대로인데 그림이 바뀌는 속성들이다.

**`Style` 은 도는데 `Paint`·`Raster` 가 0 인 것**

- **`filter` 와 `visibility`.**
- `filter` 는 이미 구워 둔 레이어에 효과만 다시 거는 것으로 보이고, `visibility` 는 **값이 실제로 바뀌는 순간이 한 번뿐**이라 그릴 것이 없다.

**여섯 칸 0 인데 `RasterTask` 만 도는 것**

- **`background-color`** 다.

```text
  널리 알려진 서술          이 브라우저에서 잰 것
  "색은 페인트부터 돈다"     Style 0 · Layout 0 · Paint 0 · Raster 120
```

- ★★ **뜻밖인 이유**: 「색 = 페인트」라는 통설과 어긋난다. Chrome 151 이 배경색 애니메이션을 **주 스레드 밖으로** 넘긴다는 뜻이다.\
  같은 색 계열이어도 **`color`(글자색)는 안 그랬다**(Style 121 · Paint 242) — **속성마다 다르다.**

**`visibility` 가 120번 도는 이유**

- **애니메이션이 살아 있는 동안 매 프레임 그 요소의 스타일을 다시 판정하기 때문**이다.\
  값이 바뀌었는지는 그 판정을 **끝내야** 알 수 있다. 그래서 「값이 안 바뀌어도 앞 공정은 돈다」가 성립한다.
- 그 뒤 공정은 바뀐 것이 없으니 안 돌았다(`Paint` 0 · `Raster` 0).

### 4. 같은 움직임의 비용

**출력** (Chrome 151 headless — 마우스를 올린 뒤 시각별 화면 x 좌표)

```text
  시각      .lft (left)    .tfm (translate)
  0.10s     22.8           22.8
  0.50s     80.4           80.4
  1.00s     152.4          152.4
  1.50s     222.0          222.0
  2.00s     291.6          291.6
```

**출력** (같은 두 애니메이션을 **하나씩만** 돌리고 2초 동안의 지표)

```text
  .lft 만 (left)        RecalcStyleCount = 122   LayoutCount = 122
  .tfm 만 (translate)   RecalcStyleCount = 0     LayoutCount = 0
```

**좌표**

- **매 시각 같다.** 소수 첫째 자리까지 같았다.

**`LayoutCount`**

- **122 대 0.**

**눈으로 구분할 수 있나**

- **없다.** 이것이 이 주제가 계측으로만 접지되는 이유다.

**정지 대조군을 둔 이유**

- 「**카운터가 도는 것이 애니메이션 때문인가, 아니면 그냥 페이지가 살아 있어서인가**」를 가르기 위해서다.\
  대조군이 전 항목 0 이었으므로 120 은 애니메이션이 만든 값이다.

### 5. `will-change` 는 무엇을 하는가

**출력** (Chrome 151 — 2초 × 2판)

```text
  경우                                          Style      Layout     TaskDuration(초)
  transform 애니메이션, will-change 없음         0/0        0/0        0.002/0.003
  transform 애니메이션, will-change: transform   0/0        0/0        0.003/0.003
  left 애니메이션, will-change 없음              120/120    120/120    0.054/0.053
  left 애니메이션, will-change: left             120/120    120/120    0.052/0.053
  left 애니메이션, will-change: transform        120/120    120/120    0.052/0.049
```

**넷의 지표**

- `transform` 쪽은 **둘 다 0/0**, `left` 쪽은 **둘 다 120/120**.

**바꾼 자리가 있나**

- ★ **없다.** 다섯 줄 어디에서도 `will-change` 가 카운터를 바꾸지 않았다.
- `TaskDuration` 도 판별할 만한 차이가 아니다(0.052\~0.054 대 0.049\~0.053 — 구간이 겹친다).

**끊김의 처방**

- **아니다. 처방은 속성을 바꾸는 것**이다 — `left`/`top`/`width` 를 `transform` 으로, 페이드를 `opacity` 로.
- `will-change` 가 도움이 되는 자리는 「**바뀌기 전에 미리 준비시킬 것이 있는**」 경우이고, 이미 합성 경로인 애니메이션에는 준비할 것이 없다.

**명세의 경고**

- **많은 요소에 미리 선언하지 말라**, **바뀌기 직전에 켜고 끝나면 끄라**는 것이다.\
  힌트는 자원을 미리 잡아 두라는 뜻이므로 **뿌리면 대가만 치른다.**

### 6. `will-change` 의 대가

**생기는 것 둘**

- ① **쌓임 맥락** — 정본은 [22번](../22-stacking-context-and-z-index/2-summary.md)(픽셀 실측 있음).
- ② **`fixed`·`absolute` 자손의 포함 블록** — 정본은 [21번](../21-position-and-containing-block/2-summary.md).\
  ★ 21번이 **`will-change: transform` 하나로 `fixed` 자식이 래퍼 안에 갇히는 것**을 좌표로 재 놨다.

**3D 를 깨뜨리는 쪽**

- **`will-change: opacity`** 다. `will-change: transform` 은 안 깨뜨린다([55번](../55-3d-transforms/2-summary.md) 실측).

**한 문장의 규칙**

- ★ 「**그 속성이 부작용을 갖는 속성이면, 힌트만 줘도 그 부작용이 미리 적용된다.**」\
  `opacity` 는 1 미만이면 평탄화를 일으키는 속성이고, `transform` 은 아니다.

**언제 켜고 끄나**

```js
el.style.willChange = 'transform';
requestAnimationFrame(() => { /* 여기서 애니메이션 시작 */ });
el.addEventListener('transitionend', () => { el.style.willChange = 'auto'; });
```

- **켠 다음 한 프레임을 주고** 시작해야 준비할 틈이 생긴다. 끝나면 **반드시 끈다.**

### 7. `contain` 은 얼마나 줄이는가

**출력** (Chrome 151 — 뒤에 3000줄이 있는 문서, 상자 높이 애니메이션, 2초 × 3판)

```text
  wrap 에 준 선언       Style           Layout          LayoutDuration(초)
  (없음)                120/120/120     120/120/120     0.195/0.190/0.202
  contain: layout       120/120/120     120/120/120     0.182/0.205/0.193
  contain: size         120/120/120     120/120/120     0.148/0.147/0.143
  contain: strict       120/120/121     120/120/121     0.022/0.025/0.025
  (transform 으로 같은 움직임)  0/0/0     0/0/0          0.000/0.000/0.000
```

**네 경우**

- 대조군 **약 0.19초** · `layout` **약 0.19초** · `size` **약 0.15초** · `strict` **약 0.024초**.

**`layout` 혼자서 효과가 있었나**

- ★ **이 실험에서는 없었다.** 세 판의 폭(0.182\~0.205)이 대조군(0.190\~0.202)과 **겹친다** — 잡음 안이다.
- **이유**: 상자가 높아지면 **뒤에 오는 3000줄이 밀려야** 한다. 그 크기 변화가 바깥으로 새는 것은 `layout` 가둠으로는 못 막는다.

**어느 값이 붙어야 하나**

- **`size`** 다. `strict`(= `layout + paint + style + size`)에서 **약 8배** 줄었다.

**`transform` 으로 하면**

- **0.000초.** 레이아웃 자체가 안 돈다.

**`contain` 의 자리**

- ★ **`contain` 은 「레이아웃을 싸게 만드는」 도구이지 `transform` 의 대체재가 아니다.**\
  움직임을 만들 때는 **애초에 레이아웃을 안 돌리는 쪽**이 훨씬 세다. `contain` 은 **레이아웃이 꼭 돌아야 하는** 자리(내용이 실제로 바뀌는 패널 등)를 위한 것이다.

### 8. `contain: strict` 의 대가

**출력** (Chrome 151 headless — `getBoundingClientRect()`)

```text
  .card           236.0 x 56.0
  .card.strict    236.0 x 16.0
```

**두 상자의 높이**

- **56px 과 16px.**

**글자**

- **아래 상자에서는 안 보인다.** 높이가 16px 로 줄고, 넘친 글자는 `paint` 가둠에 **잘린다.**

**계산**

```text
  .card         글 두 줄 (20px x 2 = 40) + 안쪽 여백 (6 x 2 = 12) + 테두리 (2 x 2 = 4) = 56
  .card.strict  안쪽 내용 0            + 안쪽 여백 12            + 테두리 4          = 16
                ↑ size 가둠이 "안쪽을 안 본다"
```

**높이를 모르면**

- **`contain: content`**(= `layout + paint + style`)를 쓴다. `size` 가 빠지므로 내용이 높이를 정한다.
- 또는 `strict` 를 쓰되 `height` 나 `contain-intrinsic-size` 로 크기를 직접 알려 준다.

### 9. 못 잰 것

**측정했나**

- ★★ **못 했다.**

**출력** (시도와 결과)

```text
  시도한 것                                       결과
  CDP LayerTree.enable + layerTreeDidChange 수집  layers 가 빈 목록 (4벌 전부 0)
  --disable-gpu 를 뺀 Chrome 으로 재시도          마찬가지로 빈 목록
  Performance.getMetrics 의 JSHeapUsedSize        GC 때문에 흔들린다. 레이어는 JS 힙에 없다
  LayoutObjects 카운터                             누적값이라 페이지 간 비교가 안 된다
                                                   (8059 -> 10063 -> 12067 로 계속 더해졌다)
```

**`--disable-gpu` 를 빼면**

- **달라지지 않았다.** 두 경우 모두 `LayerTree` 가 빈 목록이었다.

**어떻게 적어야 하나**

- ★ **「못 쟀다」고 적는다.** 그리고 관련 주장은 **명세·문서의 서술로만** 인용한다.
- 「못 잰 것」은 **「안 돌려 본 것」과 다르다** — 측정 방법 자체가 이 환경에서 성립하지 않았다.\
  그러므로 이 문서는 **「레이어가 N장 생겼다」·「메모리가 M MB 늘었다」를 한 줄도 적지 않는다.**
- 명세(css-will-change-1)가 남용을 직접 경고하는 것은 사실이고, 그것은 **명세의 말**로 인용한다.

### 10. 다른 주제와 잇기

**[52번](../52-transition/2-summary.md)이 가리키는 표**

- 「어디서 틀리나 6 — 비싼 속성을 전환한다」가 이 문서의 **(3) 속성별 실측 표**를 정본으로 가리킨다.

**좌표로 보인 주제**

- [54번](../54-transform-2d-and-origin/2-summary.md)이다. 변환한 요소의 **형제가 안 움직이고**(rect left 160 그대로) **`offsetWidth` 는 변환 전 값**(80)을 준다는 실측이 거기 있다.

**`contain: paint` 와 `overflow: hidden`**

- [55번](../55-3d-transforms/2-summary.md) 실측에서 **`overflow: hidden` 은 `preserve-3d` 를 깨뜨렸고 `contain: paint` 는 안 깨뜨렸다.**
- 같은 「자르기」인데 결과가 다른 이유는 **목적이 다른 선언**이기 때문이다 — `overflow` 는 스크롤 상자를 만드는 일이고, `contain: paint` 는 「밖으로 안 그린다」는 약속이다.

**표를 외우나 재는 법을 외우나**

- ★ **재는 법이다.**
- 근거: 이 문서의 **`background-color` 결과**가 통설과 어긋났다. 어떤 속성이 합성 경로로 갈 수 있는지는 **구현이 계속 늘려 왔고**, 표는 **Chrome 151 의 것**이다.
- 외울 것은 「**전후로 `Performance.getMetrics` 를 읽고 정지 대조군과 비교한다**」는 절차다.

| `left` 대 `transform` | 같은 거리·같은 시간, 좌표 5시각 + 각각 단독 2초 지표 | 서머리 (4) / 문항 4 |
| `will-change` | 5경우 × 2초 × 2판 | 서머리 (5) / 문항 5 |
| `contain` 네 값 | 3000줄 문서, 4경우 × 2초 × 3판 + `transform` 대조 | 서머리 (6) / 문항 7 |
| `contain: strict` 의 크기 | rect 2벌 | 서머리 (6) / 문항 8 |
| 레이어 수·메모리 | ★ **4벌 시도 → 전부 실패.** `LayerTree` 가 빈 목록 | 서머리 (8) / 문항 9 |

**구현 의존 항목** — 다시 찍어야 하는 것

- ★★ **`background-color` 가 주 스레드를 안 쓰는 것** — **다시 찍을 1순위**다. 통설과 어긋나고, 구현이 바뀌면 가장 먼저 움직일 칸이다.
- **`filter`·`visibility` 가 스타일만 돌리는 것** — 같은 성격이다.
- **`contain` 의 감소폭(약 8배)** — 이 실험 설계(3000줄)의 값이다. 문서 구조가 달라지면 배수가 달라진다.
- **120 과 121 사이의 흔들림** — 프레임 경계다. 결론은 「**0 이냐 120 이냐**」에만 세웠다.

**못 잰 것**

- **합성 레이어의 수·메모리·GPU 시간** — 위 문항 9.
- **`content-visibility: auto` 의 효과 크기** — 1500줄 문서에서 `LayoutDuration` 이 0.010 → 0.004 로 줄었지만 **반복이 부족해 신호를 확정하지 못했다.** 그래서 서머리에 수치를 결론으로 싣지 않았다.
- **`PerformanceObserver` 의 `long-animation-frame`** — 쓰지 않았다.
- **크로스 브라우저** — 엔진이 Chrome 하나뿐이다.

## 용어 풀이

- **스타일 재계산** — 계산값을 다시 만드는 공정. 카운터 `RecalcStyleCount`.
- **레이아웃** — 상자의 크기·자리를 정하는 공정. `LayoutCount`·`LayoutDuration`.
- **페인트** — 그리기 명령 목록을 만드는 공정. Tracing 이벤트 `Paint`·`PrePaint`.
- **래스터(raster)** — 그리기 명령을 픽셀로 굽는 일. `RasterTask`.
- **합성** — 구운 조각을 옮기고 겹쳐 한 장으로 만드는 일.
- **합성 레이어** — 따로 구워 두고 옮기기만 하는 조각. **수와 메모리는 이 문서가 못 쟀다.**
- **`will-change`** — 「곧 바뀐다」는 힌트. 브라우저가 무시해도 된다. **부작용은 즉시 생긴다.**
- **가둠(containment)** — 「안쪽 일이 밖에 영향을 안 준다」는 약속. `layout`·`paint`·`size`·`style`.
- **`contain: strict`** — 네 축 전부. **내용 크기를 0 으로 본다.**
- **`contain: content`** — `size` 를 뺀 것. 높이를 모르는 상자에 쓴다.
- **`content-visibility: auto`** — 화면 밖인 동안 안쪽 렌더링을 건너뛴다. Baseline **newly**(2025-09-15).
- **정지 대조군** — 값이 바뀌지 않는 애니메이션. **「120 이 잡음이 아니다」를 보이는 기준선.**
- **`Performance.getMetrics` / `Tracing`** — CDP 의 누적 카운터 / 이벤트 수집. 페인트 층은 뒤엣것에서만 보인다.
