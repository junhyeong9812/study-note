# css/syntax/42 — 색 표기와 색 공간 — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [CSS Color Module Level 4](https://drafts.csswg.org/css-color-4/) (`rgb()`·`hsl()`·`hwb()`·`lab()`·`lch()`·`oklab()`·`oklch()`·`color()`·`currentColor`·`transparent` 의 정본) · [CSS Color Level 5](https://drafts.csswg.org/css-color-5/) (`none` 성분·누락 성분 규칙). 열어서 확인한 것만 적었다.
> **실행 검증** — **Google Chrome 151.0.7922.173** headless 하나. 표기 **28개**를 한 문서에 던져 `cssRules`·`getComputedStyle` 을 받았고, 색 견본 **14장**을 스크린샷으로 찍어 **PNG 픽셀의 `(r,g,b)` 를 파이썬으로 읽었다.** 본문의 RGB 는 전부 그 픽셀값이다.
> ★ **휘도(Y) 수치만은 그 픽셀값에서 WCAG 상대 휘도 식으로 계산한 파생값**이며, 그 사실을 해당 자리에 다시 적었다.
> **엔진은 Chrome 하나다** — Firefox 155 는 이 환경에서 headless 스크린샷이 산출되지 않는다. 크로스 브라우저는 **Baseline 데이터로만** 접지했고 「두 엔진에서 확인했다」고 적지 않았다.
> **버전** — CSS 에는 언어 버전이 없으므로 Baseline 으로 읽는다. `rgb`/`hsl` = widely(2020-01-15) · `Oklab and OkLCh` = widely(2023-05-09) · `Lab and LCH` = widely(2023-05-09) · `color()` = widely(2023-05-09) · `HWB` = widely(2022-04-28) · `color-gamut` 미디어 질의 = widely(2023-02-14). `webstatus.dev` API 로 조회한 값이다(2026-09-23).
> **여기서 다루지 않는 것** — 색 **둘을 섞는 것**과 **한 색에서 다른 색을 뽑는 것**은 [43번](../43-color-mix-and-relative-color/2-summary.md), 색이 **면을 따라 변하는 것**은 [45번](../45-gradients-and-interpolation/2-summary.md)이 정본이다. `getComputedStyle` 이 **어느 단계의 값을 주느냐**는 [04번](../04-value-processing-stages/2-summary.md)이 정본이고, 여기서는 **색이라는 한 갈래에서 그 규칙이 어떻게 갈라지나**만 잰다. `currentColor` 가 **상속을 타고 내려가는 규칙**은 [03번](../03-inheritance-and-global-keywords/2-summary.md)이 정본이다. 색을 **나중에 가공하는 것**(`filter`)은 [목록의 **47번 주제**](../47-filter-and-backdrop-filter/), **아래 것과 섞는 것**(`mix-blend-mode`)은 [목록의 **48번 주제**](../48-blend-modes-and-isolation/)다.
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 수치는 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

**색 표기는 주소 체계다. 같은 집 한 채를 지번으로도, 도로명으로도, 위경도로도 부를 수 있다.**

비유 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 집 한 채 | **화면에 실제로 칠해지는 한 색** |
| 지번 주소 `산 12-3` | **`#ff8800`** — 기계가 쓰기 편한 표기 |
| 도로명 주소 `햇빛로 88` | **`rgb(255 136 0)`** — 사람이 읽기 조금 나은 표기 |
| 「시청에서 북동쪽 2km」 | **`hsl(32 100% 50%)`** — 방향과 거리로 부르는 표기 |
| 위경도 `37.5665, 126.9780` | **`oklch(0.75 0.17 60)`** — 좌표계가 다른 표기 |
| 「우리 동네 안」이라는 범위 | **색 영역(gamut)** — 그 좌표로 부른 집이 이 동네에 있기는 한가 |

- 앞의 넷은 **같은 동네(sRGB) 안의 같은 집**이다. 부르는 방식만 다르다.\
  *(Chrome 151 실측: `#ff8800`·`rgb(255, 136, 0)`·`rgb(255 136 0)`·`hsl(32 100% 50%)`·`hwb(32 0% 0%)` 다섯이 전부 계산값 `rgb(255, 136, 0)` 으로 같았다.)*
- 위경도만 **동네 밖도 가리킬 수 있다.** `oklch`·`lab`·`color(display-p3 …)` 가 그쪽이다.
- 그래서 「무슨 색이냐」는 질문의 답이 **표기마다 같고**, 「그 색을 어떻게 옮기면 자연스러우냐」는 질문의 답은 **표기마다 다르다.**

```text
  같은 한 색을 부르는 다섯 가지 이름 (전부 계산값 rgb(255, 136, 0))

  #f80                 ┐
  #ff8800              │
  rgb(255, 136, 0)     ├─→  [ ■ 주황 한 칸 ]  ← 화면에 칠해지는 픽셀은 하나
  rgb(255 136 0)       │
  hsl(32 100% 50%)     │
  hwb(32 0% 0%)        ┘
```

실무에서 이게 터지는 자리는 **「같은 밝기로 색만 바꿔 달라」** 는 주문이다.\
`hsl` 의 `l` 을 고정해 놓고 `h` 만 돌리면 **눈에 보이는 밝기가 열두 배까지 벌어진다**(아래 실측).

> **색 공간(color space)** — 색 하나를 몇 개의 숫자로 적기로 한 약속. 축이 무엇이고 단위가 무엇인지가 공간마다 다르다.\
> 예: `rgb` 는 「빨강·초록·파랑을 얼마씩 켜나」, `hsl` 은 「색상·선명함·밝기」, `oklch` 는 「지각 밝기·선명함·색상」이다.

> **색 영역(gamut)** — 어떤 장치가 실제로 낼 수 있는 색의 범위.\
> 예: 값싼 모니터는 sRGB 까지만 내고, 최근 휴대폰 화면은 그보다 넓은 Display-P3 를 낸다.

> **휘도(luminance)** — 그 색이 실제로 내뿜는 빛의 양. 눈이 느끼는 「밝다/어둡다」의 물리적 뿌리다.\
> 예: 순수한 노랑은 순수한 파랑보다 훨씬 밝게 보이는데, 그 차이가 휘도 차이다.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 셋을 둔다.

1. **표기가 이렇게 많은데 무엇이 다른가** — 화면에 칠해지는 색이 달라지나, 아니면 적는 법만 다른가.
2. `hsl` 의 `l` 을 고정하면 **밝기가 고정되나.** 안 된다면 무엇으로 해야 하나.
3. 내가 `oklch(...)` 라고 적었을 때 **`getComputedStyle` 은 무엇을 돌려주고, 픽셀에는 무엇이 칠해지나.**

## 동작 방식

### (1) 색 하나가 지나가는 네 칸

**언제 쓰나** — 이 주제 전부의 좌표계다. 「왜 계산값과 픽셀이 다르냐」는 질문이 여기서 갈린다.

```text
  ① 적은 것          ② 파서가 받아들였나       ③ 계산값               ④ 픽셀
  (선언 텍스트)       (cssRules)               (getComputedStyle)     (스크린샷)

  oklch(0.75 0.17 60)  → 담김                 → oklch(0.75 0.17 60)  → rgb(250, 143, 25)
  hsl(32 100% 50%)     → 담김                 → rgb(255, 136, 0)     → rgb(255, 136, 0)
  notacolor(1 2 3)     → [[선언째 버려짐]]     → rgb(0, 0, 0)         → 검정 (초기값)
```

그림 해설 (한 단계씩):

- **②에서 버려지면 아무 에러도 안 난다.** CSS 는 에러가 없는 언어라 모르는 표기는 조용히 사라진다.
- **③은 표기에 따라 「그대로」거나 「sRGB 로 접힌다」.** 어느 쪽인지는 (4)에서 잰다.
- **④는 ③과 다를 수 있다.** 화면이 못 내는 색이면 화면이 낼 수 있는 색으로 옮겨진다((7)).
- 그래서 **「계산값이 `oklch(...)` 다」와 「화면이 그 색이다」는 다른 문장**이다.

비용 — 이 네 칸을 안 가르면 진단이 전부 헛돈다. 「색이 안 나와요」의 원인이 ②일 수도 ④일 수도 있다.

### (2) 진단 3창 — 색이 안 나올 때 어디가 무너졌나

**언제 쓰나** — 적은 대로 안 보일 때. **화면 증상은 세 경우가 전부 같다.**

```text
  창 1  document.styleSheets[0].cssRules[i].style.cssText
        → 빈 문자열이면  ① 파서가 표기를 몰라 선언째 버렸다

  창 2  document.querySelectorAll(선택자).length
        → 0 이면        ② 선택자가 아무것도 안 잡았다  (08~12번 주제)

  창 3  getComputedStyle(el).color
        → 남의 값이면   ③ 담겼고 잡았는데 캐스케이드에서 졌다  (01번 주제)
```

실측 — 모르는 색 함수를 던지면 **창 1 에서만 잡힌다.**

```text
  선언                        cssText                          계산값
  color: notacolor(1 2 3)     "" (빈 문자열)                    rgb(0, 0, 0)
  color: rgb(300 -20 0)       "color: rgb(255, 0, 0);"          rgb(255, 0, 0)   ← 버린 게 아니라 잘랐다
  color: hsl(32 100 50)       "color: rgb(255, 136, 0);"        rgb(255, 136, 0) ← % 없이도 받는다
```

- **`notacolor(...)` 는 선언 하나만 죽는다** — 같은 규칙의 다른 선언은 산다(07번 주제의 오류 복구).
- **범위를 넘긴 수는 버려지지 않고 잘린다.** `rgb(300 -20 0)` 이 `rgb(255, 0, 0)` 이 됐다. **조용한 데이터 손실**이라 창 1 만 보면 못 잡는다.
- `hsl` 의 `s`·`l` 은 **`%` 없는 수도 받는다**(실측). 「`%` 를 빠뜨려 무효가 됐겠지」라는 진단이 틀린다.

비용 — 세 창을 안 가르면 같은 증상에 세 가지 잘못된 처방을 돌려 보게 된다.

### (3) sRGB 계열 — 네 표기가 같은 한 색이다

**언제 쓰나** — 평범한 색을 적는 거의 모든 자리.

```text
  #f80        3자리 줄임. 각 자리를 두 번 쓴 것과 같다  →  #ff8800
  #ff8800     6자리
  #ff880080   8자리. 뒤 두 자리가 알파(0x80 = 128/255 = 0.5)
  #f808       4자리 줄임 = #ff880088
```

```text
  hex 한 자리가 두 자리로 펴지는 법

     #f80
      │││
      ││└──  0  →  00
      │└───  8  →  88      ("반복"이지 "0 채우기"가 아니다. #f80 ≠ #f00800)
      └────  f  →  ff
```

실측 — 여섯 표기의 계산값이 **한 글자도 다르지 않았다.**

```text
  선언                          getComputedStyle(el).color
  --------------------------    --------------------------
  color: #f80                   rgb(255, 136, 0)
  color: #ff8800                rgb(255, 136, 0)
  color: #FF8800                rgb(255, 136, 0)   ← 대소문자 무관
  color: rgb(255, 136, 0)       rgb(255, 136, 0)   ← 옛 쉼표 문법
  color: rgb(255 136 0)         rgb(255, 136, 0)   ← 새 공백 문법
  color: rgb(100% 53.3% 0%)     rgb(255, 136, 0)   ← % 로도 된다
  color: hsl(32, 100%, 50%)     rgb(255, 136, 0)
  color: hsl(32deg 100% 50%)    rgb(255, 136, 0)   ← deg 를 붙여도 된다
  color: hwb(32 0% 0%)          rgb(255, 136, 0)
```

- **계산값 직렬화는 옛 쉼표 형태로 고정된다.** 새 공백 문법으로 적어도 `rgb(255, 136, 0)` 으로 돌아온다.
- 그래서 **문자열 비교로 색을 대조하면 내가 적은 형태와 안 맞는다.**

비용 — 없다. 어느 표기를 쓰든 픽셀은 같다. 고르는 기준은 **읽기 쉬움**뿐이다.

### (4) 옛 쉼표 문법 대 새 공백 문법 — 둘 다 된다

**언제 쓰나** — 알파를 섞어 적을 때 특히.

```text
  옛 문법 (CSS Color 3 계열)         새 문법 (CSS Color 4)
  ---------------------------        ---------------------------
  rgb(255, 136, 0)                   rgb(255 136 0)
  rgba(255, 136, 0, 0.5)             rgb(255 136 0 / 50%)
  hsl(32, 100%, 50%)                 hsl(32 100% 50%)
  hsla(32, 100%, 50%, 0.5)           hsl(32 100% 50% / 0.5)

  두 문법을 한 함수 안에서 섞는 것은 안 된다 —
  rgb(255 136, 0) 같은 형태는 파서가 받지 않는다.
```

실측 — 던져 확인한 것들.

```text
  선언                              cssText                        계산값
  rgba(255, 136, 0, 0.5)            color: rgba(255, 136, 0, 0.5)  rgba(255, 136, 0, 0.5)
  rgb(255 136 0 / 50%)              color: rgba(255, 136, 0, 0.5)  rgba(255, 136, 0, 0.5)
  rgb(255, 136, 0, 0.5)             color: rgba(255, 136, 0, 0.5)  rgba(255, 136, 0, 0.5)  ★
  rgb(255 136 0 / 1)                color: rgb(255, 136, 0)        rgb(255, 136, 0)        ★
```

- ★ **쉼표 문법에 네 번째 인자(알파)를 넣어도 받는다.** `rgba()` 라고 이름을 바꿀 필요가 없다 — `rgb()` 와 `rgba()` 는 CSS Color 4 에서 **같은 함수의 별칭**이 됐다.
- ★ **알파가 1 이면 `rgb(…)` 로, 1 미만이면 `rgba(…)` 로 직렬화된다.** 알파를 명시해도 1 이면 흔적이 사라진다.

비용 — 없다. 새 문법이 `/` 로 알파를 떼어 놓아 읽기 낫고, `color-mix()`·상대 색 구문(43번)과 형태가 맞는다.

### (5) ★ `hsl` 의 `l` 은 밝기가 아니다 — 픽셀로 잰 것

**언제 쓰나** — 「밝기는 그대로 두고 색만 바꿔 달라」는 요구가 올 때. **이것이 이 주제의 과녁이다.**

`hsl(h 100% 50%)` 에서 `h` 만 돌린 네 색을 화면에 칠하고 **PNG 픽셀을 읽었다.**

```text
  선언                     읽은 픽셀            거기서 계산한 상대 휘도 Y
  ---------------------    -----------------    ------------------------
  hsl( 60 100% 50%) 노랑   rgb(255, 255, 0)     0.9278
  hsl(120 100% 50%) 초록   rgb(  0, 255, 0)     0.7152
  hsl(  0 100% 50%) 빨강   rgb(255,   0, 0)     0.2126
  hsl(240 100% 50%) 파랑   rgb(  0,   0, 255)   0.0722
                                                 ↑ 최대 ÷ 최소 = 12.9 배
```

> **재서술자 주 — 이 표의 Y 는 측정값이 아니라 파생값이다.** 픽셀 `(r,g,b)` 는 스크린샷에서 읽은 실측이고,
> `Y` 는 그 세 수에 WCAG 상대 휘도 식(각 채널을 선형화한 뒤 `0.2126R + 0.7152G + 0.0722B`)을 적용해 **계산한 값**이다.
> 픽셀은 실측, 휘도는 계산 — 갈라서 읽는다.

같은 실험을 `oklch` 의 `l` 을 고정해 되풀이했다.

```text
  선언                     읽은 픽셀              계산한 Y
  ---------------------    -------------------    --------
  oklch(0.7 0.15  25)      rgb(237, 117, 110)     0.3185
  oklch(0.7 0.15 100)      rgb(181, 159,   0)     0.3462
  oklch(0.7 0.15 145)      rgb( 91, 182,  97)     0.3654
  oklch(0.7 0.15 260)      rgb(101, 157, 251)     0.3385
                                                   ↑ 최대 ÷ 최소 = 1.15 배
```

두 실험을 나란히 놓으면 결론이 한 줄이다.

```text
  hsl  l=50%  로 고정            oklch  l=0.7  로 고정
  +--------------------------+   +--------------------------+
  | 휘도 0.0722 \~ 0.9278     |   | 휘도 0.3185 \~ 0.3654     |
  | 12.9 배 차이              |   | 1.15 배 차이              |
  | 파랑은 거의 검정처럼 보인다 |   | 넷이 같은 밝기로 보인다    |
  +--------------------------+   +--------------------------+
    → l 은 「밝기」가 아니다          → l 은 「지각 밝기」다
```

- **`hsl` 의 `l` 은 색공간 좌표의 중간값일 뿐**이다. 「`l: 50%` 면 중간 밝기」라는 읽기가 틀렸다.
- `l: 50%` 는 **「그 색상에서 가장 선명한 지점」** 에 가깝다. 노랑의 가장 선명한 지점은 눈부시고, 파랑의 가장 선명한 지점은 어둡다.
- `oklch` 의 `l` 은 **사람 눈이 느끼는 밝기를 축으로 삼는다.** 그래서 고정하면 실제로 고정된다.

비용 — `oklch` 는 **적어 놓은 숫자로 결과 색을 떠올리기 어렵다.** `hsl(120 …)` 이 초록인 건 외우기 쉽지만 `oklch(0.7 0.15 145)` 는 그렇지 않다. 그래서 (6)의 「세 축이 무엇을 바꾸나」를 알아야 쓸 수 있다.

### (6) `oklch` 의 세 축 — 하나씩 돌려 본 것

**언제 쓰나** — 기준색 하나에서 팔레트를 만들 때(43번의 준비).

```text
  oklch( L        C        H   )
          │        │        └── Hue 색상. 0\~360 의 각도. 빨강 \~29, 초록 \~145, 파랑 \~260
          │        └─────────── Chroma 선명함. 0 이면 회색, 커질수록 쨍하다. 상한은 색상마다 다르다
          └──────────────────── Lightness 지각 밝기. 0 = 검정, 1 = 흰색
```

```text
  축 하나씩 돌린 실측 (기준 #3b82f6 = oklch(0.623066 0.187997 259.821))

  선언                                    읽은 픽셀
  ------------------------------------    -----------------
  (기준)                                  rgb( 59, 130, 246)
  oklch(from #3b82f6 calc(l + 0.2) c h)   rgb(121, 195, 255)   ← 밝아지기만 했다
  oklch(from #3b82f6 l calc(c * 2) h)     rgb(  0,  85, 255)   ← 쨍해지기만 했다
  oklch(from #3b82f6 l c calc(h + 180))   rgb(193, 116,   0)   ← 색상만 반대편으로
  oklch(from red l 0 h)                   (계산값 oklch(0.627966 0 29.2346)) ← C=0 = 회색
```

*(위 네 줄은 43번의 상대 색 구문을 미리 쓴 것이다. 문법 자체는 [43번](../43-color-mix-and-relative-color/2-summary.md)이 정본이고, 여기서는 **축이 따로 논다는 것**만 보인다.)*

- `L` 을 올리면 **색상과 선명함은 그대로** 밝아진다. `hsl` 에서 `l` 을 올리면 흰색 쪽으로 빨려 들어가면서 선명함도 같이 죽는 것과 다르다.
- `C` 를 0 으로 하면 **그 밝기의 회색**이 된다. 회색 팔레트를 「무채색」이 아니라 「그 색의 회색」으로 만들 수 있다.
- `H` 는 각도라 **360 을 넘어도 돈다.**

비용 — `C` 의 상한이 색상마다 달라서 **같은 `C` 를 줘도 어떤 색상은 화면 밖으로 나간다**((7)).

### (7) 색 영역 — 화면이 못 내는 색을 적으면

**언제 쓰나** — `color(display-p3 …)` 나 큰 `C` 를 쓸 때.

```text
        색 좌표의 세계 (oklch·lab 이 가리킬 수 있는 범위)
   +-------------------------------------------------------+
   |                                                       |
   |     +---------------------------------+               |
   |     |        Display-P3 영역           |              |
   |     |    +---------------------+       |               |
   |     |    |    sRGB 영역         |      |               |
   |     |    |   ■ #ff8800         |       |               |
   |     |    +---------------------+       |               |
   |     |        ● color(display-p3 1 0 0) |               |
   |     +---------------------------------+               |
   |            ◆ oklch(0.7 0.4 150)  ← 어느 화면도 못 내는 자리 |
   +-------------------------------------------------------+
```

이 환경의 화면이 어디까지인지부터 물었다.

```text
  matchMedia('(color-gamut: srgb)').matches     →  true
  matchMedia('(color-gamut: p3)').matches       →  false
  matchMedia('(color-gamut: rec2020)').matches  →  false
  screen.colorDepth                              →  24
```

**그래서 이 headless 환경은 sRGB 화면이다.** 그 위에서 넓은 색 영역 색을 던진 결과다.

```text
  선언                          계산값                        읽은 픽셀
  ---------------------------   --------------------------    -----------------
  color(display-p3 1 0 0)       color(display-p3 1 0 0)       rgb(255,   0,   0)
  rgb(255 0 0)                  rgb(255, 0, 0)                rgb(255,   0,   0)   ← 같다
  color(display-p3 0 1 0)       color(display-p3 0 1 0)       rgb(  0, 255,   0)
  rgb(0 255 0)                  rgb(0, 255, 0)                rgb(  0, 255,   0)   ← 같다
  color(rec2020 0 1 0)          color(rec2020 0 1 0)          rgb(  0, 255,   0)   ← 역시 같다
  color(display-p3 0.5 0.9 0.2) color(display-p3 0.5 0.9 0.2) rgb( 82, 233,   0)   ← 영역 안이라 제 색
  oklch(0.7 0.4 150)            oklch(0.7 0.4 150)            rgb(  0, 214,   0)
  oklch(0.7 0.2 150)            oklch(0.7 0.2 150)            rgb(  0, 191,  84)
```

- **P3 의 가장 빨간 색과 sRGB 의 가장 빨간 색이 픽셀에서 한 글자도 안 다르다.** 이 화면이 sRGB 라서 **잘려 나온 것**이다.
- ★ **「넓은 색 영역이 보인다」고 적을 수 없다.** 이 환경에서는 **못 본다.** 못 본 것은 못 봤다고 적는다.
- **계산값은 `color(display-p3 1 0 0)` 그대로 남는다.** 잘린 것은 ④(픽셀)에서 일어난 일이지 ③(계산값)이 아니다.
- `oklch(0.7 0.4 150)` 처럼 **어느 영역에도 없는 좌표**도 조용히 화면이 낼 수 있는 색으로 옮겨진다.

비용 — **개발 머신에서는 P3 색의 효과를 확인할 수 없다.** 넓은 색 영역을 쓸 거면 `@media (color-gamut: p3)` 로 갈라 놓고, 좁은 화면에서 어떻게 잘리는지를 기준으로 설계해야 한다.

### (8) `currentColor` — 색 하나를 끌어다 쓰는 자리

**언제 쓰나** — 테두리·아이콘·그림자를 글자색에 맞출 때. **03번과 이어지는 자리다.**

```text
  .j { color: #e11d48 }          ← 여기서 color 를 정하고
     └─ <span> 에 상속된다
        border-color 초기값 = currentColor
                            └─ 「이 요소의 color 계산값」

  실측: .j 의 자식 <span> 의 borderTopColor = rgb(225, 29, 72)
        ( = .j 의 color 와 같은 값. border-color 를 한 번도 안 적었다 )
```

- **`currentColor` 자체가 상속되는 게 아니다.** 상속되는 것은 `color` 이고, `border-color` 는 **초기값이 `currentColor`** 라서 따라 보이는 것이다.\
  이 구분은 [03번](../03-inheritance-and-global-keywords/2-summary.md)이 정본이다.
- 실측: `background: currentColor` 를 준 요소의 계산값 `backgroundColor` 가 `rgb(225, 29, 72)` 로 나왔다 — **cssText 에는 `currentcolor` 로 소문자 정규화돼 남고, 계산값에서 실제 색으로 풀린다.**

비용 — 없다. 오히려 **다크 모드 대응 비용을 줄인다** — `color` 하나만 바꾸면 따라오는 것들이 같이 바뀐다.

### (9) `transparent` 는 검정의 알파 0 이다

**언제 쓰나** — 「투명」을 적는 모든 자리. **45번의 고전 사고가 여기서 나온다.**

```text
  선언                     계산값                     뜻
  -------------------      --------------------      ---------------------------
  color: transparent       rgba(0, 0, 0, 0)          검정인데 알파가 0
  background: transparent  rgba(0, 0, 0, 0)          〃
```

- **`transparent` 는 「색 없음」이 아니라 「검정 + 알파 0」이다.** 색 성분이 검정으로 정해져 있다.
- 알파가 0 이니 **화면에서는 아무 차이가 없다.** 문제는 **그 색을 다른 색과 섞을 때** 생긴다 — [45번](../45-gradients-and-interpolation/2-summary.md)에서 픽셀로 잰다.

비용 — 없다. 다만 「투명」이라는 낱말 때문에 **성분이 없다고 오해**하면 45번에서 막힌다.

### (10) `none` 성분 — 「이 축은 안 정한다」

**언제 쓰나** — 43번의 상대 색 구문에서 축 하나를 비울 때. 드물지만 결과가 놀랍다.

```text
  선언                     계산값                     읽은 픽셀
  ---------------------    ----------------------    -----------------
  oklch(none 0.2 150)      oklch(none 0.2 150)       rgb(  0,   2,   0)   ← L 이 0 처럼 칠해졌다
  oklch(0.7 none 150)      oklch(0.7 none 150)       rgb(158, 158, 158)   ← C 가 0 = 회색
  rgb(none 128 0)          rgb(0, 128, 0)            rgb(  0, 128,   0)   ← ★ cssText 에서 이미 0 이 됐다
```

- **`none` 은 계산값에 살아남는 공간과 그렇지 않은 공간이 있다**(실측). `oklch()` 는 `none` 을 유지했고, 레거시 `rgb()` 는 **파싱 단계에서 이미 `0` 으로 굳었다.**
- **혼자 칠할 때 `none` 은 `0` 과 같게 보인다.** `none` 이 다르게 동작하는 것은 **보간할 때**다 — 그때는 상대편 색의 같은 축 값을 물려받는다.

비용 — 드물게 쓰는 문법인데 **혼자 칠했을 때는 `0` 과 구분이 안 돼서** 잘못 배우기 쉽다.

## 문법 — 형태와 규칙

CSS 는 문법 표면이 단순하므로 이 절은 「**형태 — 어디서 헷갈리나**」로 읽는다.

### 형태

```css
/* sRGB 계열 — 계산값이 rgb(...) 로 접힌다 */
#f80                       /* 3자리 hex */
#ff8800                    /* 6자리 */
#ff880080                  /* 8자리 — 뒤 둘이 알파 */
rgb(255 136 0)             rgb(255 136 0 / 50%)
rgb(255, 136, 0)           rgba(255, 136, 0, 0.5)
hsl(32 100% 50%)           hsl(32deg 100% 50% / 0.5)
hwb(32 0% 0%)

/* 넓은 색 영역·지각 균등 계열 — 계산값이 그대로 남는다 */
lab(70 40 70)              lch(70 80 60)
oklab(0.75 0.09 0.14)      oklch(0.75 0.17 60 / 40%)
color(srgb 1 0.533 0)      color(display-p3 1 0.5 0)      color(rec2020 0 1 0)

/* 키워드 */
transparent                currentColor                    rebeccapurple
```

### 금지 사례 — 조용히 버려지거나 조용히 잘리는 형태

```css
color: notacolor(1 2 3);   /* 선언째 버려진다. cssText 가 빈 문자열 */
color: rgb(300 -20 0);     /* 안 버려진다. rgb(255, 0, 0) 으로 잘린다 ← 더 위험 */
color: #ff88;              /* 4자리는 유효(=#ff8888) — 「자리 수가 이상하다」가 아니다 */
```

### 어디서 헷갈리나 — 이름 다섯

| 이름 | 무엇인가 | 헷갈리는 짝 |
|---|---|---|
| `l` in `hsl()` | 색공간 좌표의 중간값 | `l` in `oklch()` — 이쪽만 지각 밝기다 |
| `s` in `hsl()` | 채도(그 좌표계 기준) | `c` in `oklch()` — 상한이 색상마다 다르다 |
| `transparent` | **검정** + 알파 0 | 「색 없음」이 아니다 |
| `currentColor` | 이 요소의 `color` **계산값** | 상속되는 것은 `color` 쪽이다 |
| `color(srgb …)` | 0\~1 스케일 | `rgb(…)` 는 0\~255 스케일 |

## 어디서 틀리나

### 1. `l` 을 고정하면 밝기가 고정될 거라고 믿는다

가장 크게 틀리는 자리다. `hsl` 의 `l: 50%` 네 색의 휘도가 **12.9배** 벌어졌다((5) 실측).\
접근성 대비를 `hsl` 의 `l` 로 맞추면 **어떤 색상에서는 통과하고 어떤 색상에서는 떨어진다.**

### 2. 계산값이 `oklch(...)` 로 나왔으니 화면도 그 색이라고 믿는다

계산값은 **③**이고 화면은 **④**다((1)). `oklch(0.7 0.4 150)` 은 계산값이 그대로 남지만 픽셀은 `rgb(0, 214, 0)` 이었다.

### 3. `rgb(300 -20 0)` 이 무효라 무시될 거라 기대한다

**안 버려진다.** `rgb(255, 0, 0)` 으로 잘린다. `calc()` 로 계산한 값이 범위를 넘으면 **조용히 다른 색이 칠해진다.**

### 4. 문자열로 색을 대조한다

`el.style.color === 'rgb(255 136 0)'` 은 절대 참이 안 된다 — 계산값이 **옛 쉼표 형태**로 직렬화되기 때문이다((3)).

### 5. `transparent` 를 「색이 없다」로 읽는다

`rgba(0, 0, 0, 0)` 이다. 이 검정 성분이 [45번](../45-gradients-and-interpolation/2-summary.md)에서 드러난다.

### 6. `hsl(32 100 50)` 을 「`%` 를 빠뜨려 무효」라고 진단한다

**받는다**(실측 — 계산값 `rgb(255, 136, 0)`). 안 나오는 이유가 여기 있는 줄 알고 엉뚱한 데를 고치게 된다.

### 7. 개발 머신에서 P3 가 보이지 않으니 「지원 안 한다」고 결론짓는다

지원은 한다 — **파싱되고 계산값에 남는다.** 못 보이는 것은 **화면의 색 영역** 문제다((7)).

## 구현 세부사항 대 언어 보장

| 항목 | 누가 보장하나 | 근거 |
|---|---|---|
| `#f80` 과 `rgb(255 136 0)` 이 같은 색인 것 | **언어 보장** | CSS Color 4 의 표기 정의. 변환식이 명세에 있다 |
| `oklch` 의 `l` 이 지각 밝기 축인 것 | **언어 보장** | Oklab 의 정의 자체. 픽셀 실측이 그것과 어긋나지 않았다 |
| 계산값이 `rgb(r, g, b)` **쉼표 형태**로 직렬화되는 것 | **CSSOM 이 정한 직렬화 형식** | 실측. 표기를 바꿔도 형태가 하나로 고정됐다 |
| `oklch`·`lab`·`color()` 의 계산값이 **그 공간 그대로 남는** 것 | **언어 보장(Color 4)** — 다만 형태의 세부는 구현 | 레거시 색만 sRGB 로 접힌다는 것이 명세의 규칙이고, 소수 자릿수는 실측 형태다 |
| `color(display-p3 1 0 0)` 이 **`rgb(255, 0, 0)` 으로 칠해진** 것 | **구현 + 하드웨어** | 이 환경이 sRGB 화면이기 때문이다. `(color-gamut: p3)` 가 `false` 였다. **다른 화면에서는 다른 픽셀이 나온다** |
| 영역 밖 색을 **어떻게** 옮기나(`oklch(0.7 0.4 150)` → `rgb(0, 214, 0)`) | **구현** | 명세는 「영역 안으로 매핑한다」까지를 정하고, 알고리즘 세부는 엔진이 고른다. **다른 엔진·다른 버전에서 다른 값이 나올 수 있다** |
| `rgb(none 128 0)` 이 cssText 에서 이미 `0` 이 된 것 | **구현 세부** | 레거시 `rgb()` 의 처리. `oklch(none …)` 은 `none` 이 남았다 |
| `rgb()`/`rgba()` 가 같은 함수인 것 | **언어 보장(Color 4)** | 실측이 일치 — 네 인자 쉼표 형태도 받았다 |

★ **이 환경에서 보지 못한 것을 적지 않았다.** 넓은 색 영역 화면에서 P3 가 어떻게 보이는지는 **확인하지 못했고**, 본문 어디에도 「더 쨍하게 보인다」를 관찰로 적지 않았다.

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 안 쓸 것 |
|---|---|---|
| 디자인 시안의 색을 그대로 옮긴다 | `#rrggbb` | — (변환하면 반올림 오차만 는다) |
| 반투명을 준다 | `rgb(R G B / 50%)` · `#rrggbbaa` | `opacity` (요소 전체가 투명해진다) |
| 한 색에서 밝기 단계를 만든다 | `oklch` 의 `l` 을 옮긴다 | `hsl` 의 `l` — 색상마다 다르게 밝아진다 |
| 접근성 대비를 맞춘다 | 휘도를 계산하거나 대비 검사 도구 | 「`l` 이 같으니 대비도 같겠지」 |
| 테두리·아이콘을 글자색에 맞춘다 | `currentColor` | `color: inherit` 을 자식마다 반복 |
| 넓은 색 영역을 쓴다 | `@media (color-gamut: p3)` 로 갈라서 | 무조건 `color(display-p3 …)` — 좁은 화면에서 잘린다 |
| 회색 계열을 만든다 | `oklch(l 0 h)` — 그 색의 회색 | `#888` — 색조가 안 맞는다 |

## 핵심 문장

- **표기는 주소이고 색은 집이다.** `#f80`·`rgb(255 136 0)`·`hsl(32 100% 50%)`·`hwb(32 0% 0%)` 는 전부 같은 한 색이다.
- **`hsl` 의 `l` 은 밝기가 아니다.** `l: 50%` 를 고정한 네 색의 휘도가 12.9배 벌어졌다. `oklch` 의 `l` 은 1.15배였다.
- **계산값과 픽셀은 다른 칸이다.** `oklch`·`lab`·`color()` 는 계산값이 그 공간 그대로 남고, sRGB 계열만 `rgb(r, g, b)` 로 접힌다.
- **못 내는 색은 조용히 옮겨진다.** 이 환경에서 P3 빨강과 sRGB 빨강의 픽셀이 한 글자도 안 달랐다.
- **`transparent` 는 「검정 + 알파 0」이다.** 「색 없음」이 아니다.

## 용어 풀이

- **색 공간(color space)** — 색 하나를 몇 개의 숫자로 적기로 한 약속. 예: `rgb` 는 빨강·초록·파랑 세 개, `oklch` 는 밝기·선명함·색상 세 개.
- **색 영역(gamut)** — 어떤 장치가 실제로 낼 수 있는 색의 범위. 예: 이 headless 환경은 `(color-gamut: srgb)` 만 `true` 였다.
- **sRGB** — 1996년부터 웹의 기본으로 쓰여 온 색 영역. 예: `#ff8800` 이라고 적으면 그 숫자는 sRGB 좌표다.
- **Display-P3** — sRGB 보다 넓은 색 영역. 예: 최근 애플 기기 화면이 이 범위를 낸다.
- **지각 균등(perceptually uniform)** — 숫자를 같은 만큼 바꾸면 눈에도 같은 만큼 달라 보이는 성질. 예: `oklch` 의 `l` 을 0.1 올리면 색상이 무엇이든 비슷하게 밝아진다.
- **휘도(luminance)** — 그 색이 내는 빛의 양. 예: 순수 노랑의 상대 휘도는 0.9278, 순수 파랑은 0.0722였다(측정한 픽셀에서 계산).
- **상대 휘도(relative luminance)** — 검정 0, 흰색 1 로 잡은 휘도. 예: 접근성 대비비 계산의 재료가 이 값이다.
- **알파(alpha)** — 그 색이 얼마나 불투명한가. 예: `rgb(255 0 0 / 50%)` 는 반투명 빨강이다.
- **색상(hue)** — 「빨강이냐 파랑이냐」에 해당하는 각도. 예: `oklch` 에서 빨강은 약 29도, 파랑은 약 260도였다(실측 계산값).
- **채도·크로마(chroma)** — 색이 얼마나 쨍한가. 예: `oklch(0.7 0 150)` 처럼 0 이면 회색이 된다.
- **계산값(computed value)** — 캐스케이드와 상속이 끝난 뒤 그 요소가 갖는 값. 예: `getComputedStyle(el).color` 가 돌려주는 것.
- **직렬화(serialization)** — 내부 값을 문자열로 다시 적는 것. 예: `rgb(255 136 0)` 이 `rgb(255, 136, 0)` 으로 돌아오는 것.
- **Baseline** — 주요 브라우저에 그 기능이 언제부터 다 들어갔는지를 나타내는 지표. 예: `Oklab and OkLCh` 는 2023-05-09 부터 `widely` 다.

## 더 들어가면

- **`color-gamut` 미디어 질의**로 화면에 따라 색을 갈라 줄 수 있다. 이 환경에서는 `srgb` 만 `true` 였다((7) 실측).
- **`lab`/`lch` 와 `oklab`/`oklch` 는 형제 관계**다. 앞엣것은 CIELAB(1976), 뒤엣것은 Oklab(2020) 기반이다. Baseline 은 둘 다 2023-05-09 `widely` 로 같다.
- **`color(srgb 1 0.533 0)` 은 `rgb(255 136 0)` 과 같은 색인데 계산값이 안 접힌다**(실측). 같은 공간을 가리켜도 **함수가 다르면 직렬화가 다르다.**
- **`rebeccapurple` 은 cssText 에 이름 그대로 남고 계산값에서 `rgb(102, 51, 153)` 이 된다**(실측). 이름 있는 색은 **지정값 단계까지 이름으로 산다.**
