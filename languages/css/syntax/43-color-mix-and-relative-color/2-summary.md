# css/syntax/43 — `color-mix()` 와 상대 색 구문 — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [CSS Color Module Level 5](https://drafts.csswg.org/css-color-5/) (`color-mix()`·상대 색 구문·색상 보간법의 정본) · [CSS Color Module Level 4](https://drafts.csswg.org/css-color-4/) (색 공간과 보간 규칙). 열어서 확인한 것만 적었다.
> **실행 검증** — **Google Chrome 151.0.7922.173** headless 하나. `color-mix()`·상대 색 구문 **48개 선언**을 던져 `cssRules`·`getComputedStyle` 을 받았고, 색 견본 **33장**을 스크린샷으로 찍어 **PNG 픽셀의 `(r,g,b)` 를 파이썬으로 읽었다.** 본문의 RGB 는 전부 그 픽셀값이다.
> **엔진은 Chrome 하나다** — Firefox 155 는 이 환경에서 headless 스크린샷이 산출되지 않는다. 크로스 브라우저는 **Baseline 데이터로만** 접지했고 「두 엔진에서 확인했다」고 적지 않았다.
> **버전** — `color-mix()` = **widely**(low 2023-05-09 · high 2025-11-09, Chrome 111 / Firefox 113 / Safari 16.2). 상대 색 구문(`Relative colors`) = **newly**(low 2024-09-16, Chrome 125 / Firefox 128 / Safari 18). `webstatus.dev` API 로 조회한 값이다(2026-09-23).
> **여기서 다루지 않는 것** — 색 **하나를 적는 표기와 색 공간 자체**는 [42번](../42-color-notation-and-spaces/2-summary.md)이 정본이다. 색이 **면을 따라 변하는 것**(그라디언트의 보간)은 [45번](../45-gradients-and-interpolation/2-summary.md)이 정본이고, 여기는 **두 색의 한 점 결과**까지만 잰다. 색을 **다 칠한 뒤 가공하는 것**(`filter`)은 [목록의 **47번 주제**](../47-filter-and-backdrop-filter/), **아래 레이어와 섞는 것**(`mix-blend-mode`)은 [목록의 **48번 주제**](../48-blend-modes-and-isolation/)다 — 이름이 「섞는다」로 같지만 **섞는 시점이 완전히 다르다**((9) 참고).
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 수치는 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

**`color-mix()` 는 물감 두 통을 섞는 것이고, 상대 색 구문은 한 통에서 물감을 떠다가 농도만 바꾸는 것이다.**

비유 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 물감 두 통을 섞는다 | **`color-mix(in <공간>, A, B)`** |
| 어느 팔레트 위에서 섞나 | **`in <공간>`** — 섞는 좌표계. **결과가 달라진다** |
| 통 하나에서 떠 온 물감 | **`oklch(from <색> …)`** — 상대 색 구문 |
| 떠 온 물감의 농도·밝기만 조절한다 | **`l`·`c`·`h` 축을 따로 건드린다** |
| 비율 조절 | **`A 25%`** 처럼 붙이는 백분율 |

- **같은 두 색을 섞어도 어느 팔레트 위에서 섞느냐에 따라 결과가 다르다.**\
  *(Chrome 151 실측: 빨강과 청록을 반씩 — `in srgb` 는 `rgb(128, 128, 128)` 회색, `in oklab` 은 `rgb(210, 169, 147)` 베이지, `in hsl` 은 `rgb(128, 255, 0)` 연두.)*
- 상대 색 구문은 **섞는 게 아니라 뜯어서 고치는 것**이다. 색을 축 세 개로 분해해 원하는 축만 바꿔 다시 조립한다.
- 그래서 실무 쓰임이 갈린다 — **`color-mix()` 는 「이 색과 흰색을 20%」**, 상대 색 구문은 **「이 색과 같은 색상에서 밝기만 다른 다섯 단계」** 다.

```text
  color-mix — 두 색을 하나로                    상대 색 구문 — 한 색을 뜯어 고친다

   A ■──┐                                        #3b82f6
        ├──[ in <공간> 에서 보간 ]── ■ 결과         │
   B ■──┘                                         ├─ l → 0.95 로 바꾼다  ┐
                                                  ├─ c → 그대로          ├─→ ■ 연한 파랑
   섞는 공간이 결과를 바꾼다                        └─ h → 그대로          ┘
```

실무에서 이게 터지는 자리는 **「브랜드 색 하나만 주면 나머지 색을 다 만들어 줘」** 라는 요구다.\
sRGB 에서 흰색과 섞으면 **연해지면서 색이 탁해지고**, `oklch` 로 `l` 만 올리면 **선명함이 유지된 채 밝아진다.**

> **보간(interpolation)** — 두 값 사이의 중간값을 만드는 것.\
> 예: 빨강과 파랑의 50% 지점을 구하는 것이 보간이고, 어느 좌표계에서 계산하느냐에 따라 답이 다르다.

> **보간 색 공간(interpolation color space)** — 그 중간값을 어느 좌표계에서 계산하느냐.\
> 예: `in srgb` 는 R·G·B 세 수를 각각 평균 내고, `in oklch` 는 밝기·선명함·색상 각도를 각각 평균 낸다.

> **상대 색 구문(relative color syntax)** — 기존 색을 `from` 으로 받아 그 성분을 이름(`r`·`g`·`b`·`l`·`c`·`h` 등)으로 참조해 새 색을 만드는 문법.\
> 예: `oklch(from red l c calc(h + 180))` 은 「빨강과 밝기·선명함은 같고 색상만 반대편」인 색이다.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 셋을 둔다.

1. **같은 두 색을 섞었는데 결과가 왜 여럿인가** — 어느 공간을 고르면 무엇이 달라지나.
2. **보색을 섞으면 회색이 되나** — 되는 공간과 안 되는 공간을 가른다.
3. 기준색 하나에서 **팔레트를 만드는 형태는 무엇인가** — 그리고 그게 어디까지 쓸 수 있나.

## 동작 방식

### (1) `color-mix()` 의 다섯 조각

**언제 쓰나** — 두 색을 하나로 합칠 때. 이 그림이 이 절의 좌표계다.

```text
  color-mix( in oklch longer hue ,  red 30% ,  blue )
             ─┬─ ──┬── ────┬────    ─┬─ ─┬─    ──┬─
              │    │       │         │   │       └── 색 B. 비율 생략 = 나머지
              │    │       │         │   └────────── 색 A 의 비율 (선택)
              │    │       │         └────────────── 색 A
              │    │       └──────────────────────── 색상 보간법 (극좌표 공간에서만)
              │    └──────────────────────────────── 보간 색 공간
              └───────────────────────────────────── 이 낱말은 필수다
```

실측 — **`in` 을 빼면 선언째 버려진다.**

```text
  선언                                 cssText
  -----------------------------------  ---------------------
  color-mix(srgb, red, blue)           ""  [[버려짐]]
  color-mix(in srgb, red, blue)        "background: color-mix(in srgb, red, blue);"
```

- 진단 3창의 **창 1** 로만 잡힌다. 화면은 배경 없는 상자로 보이고 콘솔은 조용하다.

비용 — 없다. 다만 **`in <공간>` 이 결과를 정하는 가장 큰 손잡이**인데 문법상 눈에 안 띄는 자리에 있다.

### (2) ★ 같은 두 색, 다른 공간 — 픽셀로 잰 것

**언제 쓰나** — 「보간 공간이 정말 결과를 바꾸나」를 확인할 때. **이것이 이 주제의 첫 과녁이다.**

빨강 `#ff0000` 과 청록 `#00ffff` 를 **반씩** 섞었다. 두 색은 **sRGB 의 보색**이다.

```text
  선언                                        계산값                              읽은 픽셀
  ------------------------------------------  ---------------------------------  -----------------
  color-mix(in srgb,        #ff0000, #00ffff)  color(srgb 0.5 0.5 0.5)            rgb(128, 128, 128)
  color-mix(in srgb-linear, #ff0000, #00ffff)  color(srgb-linear 0.5 0.5 0.5)     rgb(188, 188, 188)
  color-mix(in oklab,       #ff0000, #00ffff)  oklab(0.766676 0.0377 0.0432)      rgb(210, 169, 147)
  color-mix(in oklch,       #ff0000, #00ffff)  oklch(0.766676 0.206105 112.001)   rgb(184, 190,   0)
  color-mix(in hsl,         #ff0000, #00ffff)  color(srgb 0.5 1 0)                rgb(128, 255,   0)
  color-mix(in lab,         #ff0000, #00ffff)  lab(72.4774 15.0888 27.4682)       rgb(216, 167, 128)
```

```text
  보색을 섞으면 회색이 되나 — 공간마다 답이 다르다

  in srgb         ■ rgb(128, 128, 128)   완전한 회색.  R·G·B 세 수를 각각 평균했다
  in srgb-linear  ■ rgb(188, 188, 188)   밝은 회색.    빛의 양으로 평균했더니 더 밝아졌다
  in lab          ■ rgb(216, 167, 128)   살구색.       회색이 아니다
  in oklab        ■ rgb(210, 169, 147)   베이지.       회색이 아니다
  in oklch        ■ rgb(184, 190,   0)   올리브.       각도를 돌아가다 노랑을 지났다
  in hsl          ■ rgb(128, 255,   0)   연두.         전혀 다른 색이 됐다
```

그림 해설 (한 단계씩):

- **`in srgb` 만 깨끗한 회색이 된다.** 두 색의 R·G·B 가 정확히 서로의 보수라 세 수가 전부 128 이 된다.
- **`in srgb-linear` 는 더 밝은 회색**이다. 감마를 푼 「빛의 양」으로 평균 내면 어두운 쪽이 덜 끌어내린다. **회색이지만 같은 회색이 아니다.**
- **`in lab`·`in oklab` 은 회색이 안 된다.** 이 좌표계에서 빨강과 청록은 원점 기준 정반대가 **아니라서**, 중간점이 원점(무채색)에 떨어지지 않는다.
- **극좌표 공간(`oklch`·`hsl`)은 색상 각도를 돌아간다.** 회색을 지나가는 게 아니라 **다른 색상들을 거쳐서** 간다. 그래서 전혀 다른 색이 나온다.

```text
  직교 공간(srgb·oklab·lab)          극좌표 공간(oklch·hsl)
  두 점을 직선으로 잇는다             각도를 따라 호를 그린다

     빨강 ●                              빨강 ●─┐
           \                                     │ 각도가 돌아간다
            \  ← 중간점은 이 선 위          노랑 ●─┤
             \                             연두 ●─┤
              ● 청록                       청록 ●─┘
     (무채색 근처를 지날 수 있다)        (무채색을 전혀 안 지난다)
```

비용 — **기본값이 `in oklab`** 이므로(아래 (3)), 아무 생각 없이 쓰면 회색이 아니라 베이지가 나온다. **탁한 중간색이 싫으면 공간을 고르는 것이 손잡이다.**

### (3) 기본값은 `in oklab` — 그리고 직렬화에서 사라진다

**언제 쓰나** — cssText 를 읽어 진단할 때. 안 알면 「내가 적은 게 지워졌나」로 오해한다.

```text
  적은 것                                  cssText 에 남은 것
  ---------------------------------------  --------------------------------------
  color-mix(in oklab, red, blue)           color-mix(red, blue)            ★ in oklab 이 사라졌다
  color-mix(in srgb, red, blue)            color-mix(in srgb, red, blue)
  color-mix(in hsl shorter hue, red, cyan) color-mix(in hsl, red, cyan)    ★ shorter 가 사라졌다
  color-mix(in hsl longer hue, red, cyan)  color-mix(in hsl longer hue, red, cyan)
```

- **기본값은 직렬화에서 생략된다.** `in oklab` 이 보간의 기본이고 `shorter hue` 가 색상 보간법의 기본이다.
- 그래서 **`cssText` 에 `in oklab` 이 없다고 해서 안 먹은 게 아니다.** 오히려 먹었다는 증거다.
- **이것은 CSSOM 의 직렬화 규칙이지 값이 바뀐 게 아니다** — 계산값은 그대로 `oklab(...)` 으로 나온다.

비용 — 없다. 다만 **진단할 때 창 1 의 출력을 오독하기 쉽다.**

### (4) 비율 — 두 수의 합이 100% 가 아니면

**언제 쓰나** — 한쪽만 비율을 적거나 둘 다 적을 때. **알파가 조용히 바뀌는 자리**가 여기다.

```text
  적은 것                                  결과
  ---------------------------------------  ----------------------------------------
  color-mix(in oklab, red 25%, blue)       red 25% + blue 75%       (나머지가 채워진다)
  color-mix(in srgb, red 20%, blue 20%)    비율은 50:50 으로 정규화 + ★ 알파가 0.4 가 된다
  color-mix(in srgb, red 150%, blue)       [[선언째 버려짐]]        (0\~100% 밖)
  color-mix(in srgb, red 0%, blue 0%)      [[선언째 버려짐]]        (합이 0)
```

실측으로 확인한 ★ 자리.

```text
  color-mix(in srgb, red 20%, blue 20%)
    계산값  color(srgb 0.5 0 0.5 / 0.4)     ← 알파 0.4 가 붙었다
    흰 배경 위 픽셀  rgb(204, 153, 204)      ← 그래서 연보라로 보인다

  color-mix(in srgb, red, blue)
    계산값  color(srgb 0.5 0 0.5)           ← 알파 없음
    픽셀    rgb(128,   0, 128)              ← 진한 보라
```

- **두 비율의 합이 100% 미만이면 그 합이 결과의 알파가 된다.** 비율 자체는 **합이 100% 가 되도록 정규화**된다.
- 「20% 씩 섞었더니 왜 연하지?」의 답이 이것이다. **비율을 하나만 적으면 이 함정이 없다.**
- 합이 100% 를 넘는 것도, 어느 한쪽이 범위를 벗어난 것도 **선언째 버려진다** — 창 1 에서 잡힌다.

비용 — **비율은 하나만 적는 습관**으로 이 함정 전체를 피할 수 있다.

### (5) 색상 보간법 — `shorter` 와 `longer`

**언제 쓰나** — 극좌표 공간(`hsl`·`hwb`·`lch`·`oklch`)을 쓸 때만. 직교 공간에서는 무시된다.

```text
  빨강(h=0) 에서 파랑(h=240) 으로 가는 두 길

        0°(빨강)
          ●
       ／    ＼
  300°        60°
    ｜          ｜      shorter : 짧은 쪽 = 0° → 300° → 240°  (120° 만 돈다)
  240°        120°      longer  : 긴 쪽   = 0° →  60° → 240°  (240° 를 돈다)
   (파랑)      ＼／
          180°
```

```text
  실측 — color-mix(in hsl <법> hue, red, blue) 의 50% 픽셀
  ----------------------------------------------------------
  shorter hue (기본)   →  계산값 color(srgb 1 0 1)   픽셀 rgb(255,   0, 255)  자홍
  longer hue           →  계산값 color(srgb 0 1 0)   픽셀 rgb(  0, 255,   0)  초록 ★

  in oklch 로 같은 실험
  ----------------------------------------------------------
  shorter hue (기본)   →  oklch(0.539974 0.285457 326.643)
  longer hue           →  oklch(0.539974 0.285457 146.643)   ★ 각도가 180 도 반대편
```

- **★ 같은 두 색인데 결과가 자홍과 초록이다.** 색상환의 어느 쪽으로 도느냐만 바꿨다.
- **보색(각도 차가 정확히 180도)에서는 둘이 같아진다** — 실측: 빨강과 청록은 `shorter`·`longer` 둘 다 `color(srgb 0.5 1 0)` 로 같았다. 어느 쪽으로 돌든 180도라 길이가 같기 때문이다.
- 나머지 두 법(`increasing hue`·`decreasing hue`)은 「각도가 늘어나는 방향으로만/줄어드는 방향으로만」이다.

비용 — **`longer hue` 는 거의 언제나 사고다.** 일부러 무지개를 만들 때만 쓴다.

### (6) 상대 색 구문 — 색을 뜯어 고친다

**언제 쓰나** — 기준색 하나에서 변형을 뽑을 때.

```text
  oklch( from  #3b82f6   l    c    calc(h + 180) )
         ─┬─   ───┬───   ┬    ┬    ──────┬──────
          │       │      │    │          └── 이 축만 바꾼다
          │       │      └────┴───────────── 그대로 쓰는 축 (이름이 곧 값이다)
          │       └──────────────────────── 원본 색 (var() 도 된다)
          └──────────────────────────────── 이 낱말이 상대 색 구문의 표지다
```

```text
  from 이 하는 일 — 색 하나를 그 함수의 축으로 분해한다

  #3b82f6  ──[ oklch 로 분해 ]──→  l = 0.623066
                                    c = 0.187997
                                    h = 259.821
                                    ↓ 세 이름을 그 자리에서 쓸 수 있다
                                  oklch(  l  ·  c  ·  h  )
```

실측 — 축 하나씩 바꾼 결과다.

```text
  선언                                      계산값                                    픽셀
  ----------------------------------------  ---------------------------------------  -----------------
  (기준) #3b82f6                            rgb(59, 130, 246)                         rgb( 59, 130, 246)
  oklch(from #3b82f6 l c h)                 oklch(0.623066 0.187997 259.821)          (기준과 같은 색)
  oklch(from #3b82f6 calc(l + 0.2) c h)     oklch(0.823066 0.187997 259.821)          rgb(121, 195, 255)
  oklch(from #3b82f6 l calc(c * 2) h)       oklch(0.623066 0.375994 259.821)          rgb(  0,  85, 255)
  oklch(from #3b82f6 l c calc(h + 180))     oklch(0.623066 0.187997 79.8207)          rgb(193, 116,   0)
  oklch(from #3b82f6 l c h / 50%)           oklch(0.623066 0.187997 259.821 / 0.5)    (반투명)
  oklch(from var(--c) l c h)                oklch(0.623066 0.187997 259.821)          ★ var() 도 받는다
  rgb(from red calc(255 - r) g b)           color(srgb 0 0 0)                         검정
```

- **축 이름은 함수마다 다르다** — `rgb()` 는 `r`·`g`·`b`, `hsl()` 은 `h`·`s`·`l`, `oklch()` 는 `l`·`c`·`h`.
- **`from` 뒤의 색과 바깥 함수가 달라도 된다.** `oklch(from #3b82f6 …)` 처럼 hex 를 받아 oklch 축으로 분해한다.
- **`rgb(from …)` 의 계산값은 `color(srgb …)` 로 나온다**(실측). 레거시 `rgb()` 로 안 접힌다.
- `rgb(from red calc(255 - r) g b)` 가 검정인 이유: 빨강은 `r=255, g=0, b=0` 이므로 `255-255=0` → `rgb(0 0 0)`.
- **각도는 360 을 넘기면 계산값 단계에서 한 바퀴 접힌다**(실측). `259.821 + 180 = 439.821` 을 적었는데 계산값은 `79.8207` 이었다.

비용 — **Baseline 이 `newly`(2024-09-16)** 다. 오래된 브라우저를 받아야 하면 `@supports` 로 갈라야 한다([목록의 **41번 주제**](../41-supports-feature-queries/)).

### (7) ★ 축 이름은 「수」로 풀린다 — 여기서 선언이 죽는다

**언제 쓰나** — 상대 색 구문 안에서 `calc()` 를 쓸 때. **실측에서 유일하게 버려진 선언이 여기였다.**

```text
  선언                                        cssText
  ------------------------------------------  ------------------------------------------
  hsl(from #3b82f6 h s calc(l + 20%))         ""  [[버려짐]]   ★
  hsl(from #3b82f6 h s calc(l + 20))          "background: hsl(from rgb(59, 130, 246) h s calc(20 + l));"
  oklch(from #3b82f6 calc(l + 0.2) c h)       "background: oklch(from rgb(59, 130, 246) calc(0.2 + l) c h);"
```

- ★ **`s`·`l` 같은 백분율 축의 이름도 `<number>` 로 풀린다.** `hsl` 의 `l` 은 `0\~100` 범위의 **수**이지 `50%` 라는 백분율이 아니다.
- 그래서 `calc(l + 20%)` 는 **수 + 백분율**이 되어 타입이 안 맞고, 선언째 버려진다.
- 고치는 법은 `%` 를 떼는 것이다 — `calc(l + 20)`.
- `oklch` 의 `l` 은 `0\~1` 스케일이라 **`calc(l + 0.2)`** 다. 같은 글자 `l` 인데 **함수마다 스케일이 다르다.**

```text
  같은 이름 l, 다른 스케일

  hsl(from … h s l)      l ∈ 0 \~ 100      → calc(l + 20)
  oklch(from … l c h)    l ∈ 0 \~ 1        → calc(l + 0.2)
                              ↑ 20% 를 더하려면 여기서는 0.2 다
```

비용 — **에러가 없는 언어라 조용히 사라진다.** 「상대 색 구문이 이 브라우저에서 안 되나」로 오진하기 딱 좋다.

### (8) 실무 — 기준색 하나에서 다섯 단계

**언제 쓰나** — 디자인 토큰을 만들 때. 여기가 이 주제의 값이 몰리는 자리다.

```text
  --b (기준) 하나에서 다섯 칸을 만드는 형태

  oklch(from var(--b) 0.95 calc(c * 0.3) h)   밝게 + 흐리게   → 배경용
  oklch(from var(--b) 0.8  calc(c * 0.6) h)   조금 밝게       → 테두리용
  var(--b)                                    기준            → 주 색
  oklch(from var(--b) calc(l * 0.8) c h)      조금 어둡게     → 호버용
  oklch(from var(--b) calc(l * 0.6) c h)      더 어둡게       → 눌림용
```

실측 — **같은 다섯 줄을 서로 다른 두 기준색에 적용한 픽셀이다.**

```text
  --b: #3b82f6 (파랑)                    --b: #16a34a (초록)
  ------------------------------------   ------------------------------------
  rgb(217, 240, 255)                     rgb(216, 249, 220)
  rgb(147, 191, 255)                     rgb(142, 208, 154)
  rgb( 59, 130, 246)  ← 기준             rgb( 22, 163,  74)  ← 기준
  rgb( 16,  90, 203)                     rgb(  0, 124,  35)
  rgb(  0,  50, 161)                     rgb(  0,  87,   0)
```

- **선언 다섯 줄은 한 글자도 안 바꿨고 `--b` 만 갈았다.** 색상이 달라도 단계의 「느낌」이 같은 것이 `oklch` 의 `l` 덕이다([42번](../42-color-notation-and-spaces/2-summary.md)의 실측).
- `color-mix` 로 같은 일을 할 수도 있다 — `color-mix(in oklab, var(--b) 20%, white)`. **차이는 「흰색으로 간다」와 「밝기 축을 올린다」** 다. 앞엣것은 선명함도 같이 떨어진다.

비용 — **상대 색 구문의 Baseline 이 `newly` 이고 `color-mix()` 는 `widely`** 다. 지원 폭이 중요하면 후자로 쓴다.

### (9) 이름이 비슷한 셋 — 섞는 시점이 다르다

**언제 쓰나** — 47·48번과 헷갈릴 때.

```text
  ① color-mix()        값 단계에서 두 색을 섞어 한 색을 만든다
                       → 결과는 색 하나. 계산값에 보인다
                       ↓
  ② 요소를 그 색으로 칠한다
                       ↓
  ③ filter (47번)      칠해진 결과를 가공한다 (밝기·대비·흐림)
                       ↓
  ④ mix-blend-mode     칠해진 결과를 아래 레이어와 합성한다
     (48번)            → 아래에 무엇이 있느냐에 따라 결과가 달라진다
```

- **`color-mix()` 의 피연산자는 「값」이고, 혼합 모드의 피연산자는 「화면에 그려진 픽셀」이다.**
- 그래서 `color-mix()` 는 `getComputedStyle` 로 결과를 읽을 수 있고, 혼합 모드는 **픽셀을 읽어야** 안다.

비용 — 없다. 경계를 알면 중복 학습이 사라진다.

## 문법 — 형태와 규칙

CSS 는 문법 표면이 단순하므로 이 절은 「**형태 — 어디서 헷갈리나**」로 읽는다.

### 형태

```css
/* color-mix — in 은 필수 */
color-mix(in srgb, red, blue)
color-mix(in oklab, red 25%, blue)              /* 나머지 75% 는 자동 */
color-mix(in oklch longer hue, red, blue)       /* 극좌표 공간에서만 의미 있다 */
color-mix(in srgb, currentColor 12%, white)     /* currentColor 도 받는다 */
color-mix(in oklab, var(--brand), black 20%)

/* 상대 색 구문 — from 이 표지 */
oklch(from #3b82f6 l c h)                       /* 그대로 다시 만든다 */
oklch(from var(--brand) calc(l + 0.2) c h)      /* 축 하나만 바꾼다 */
oklch(from red l c calc(h + 180))               /* 각도는 360 을 넘어도 된다 */
rgb(from red calc(255 - r) g b)                 /* rgb 축은 r·g·b */
hsl(from #3b82f6 h s calc(l + 20))              /* hsl 의 l 은 0~100 스케일의 수 */
oklch(from var(--brand) l c h / 50%)            /* 알파는 / 뒤에 */
```

### 금지 사례 — 조용히 버려지는 형태

```css
background: color-mix(srgb, red, blue);            /* in 이 없다 */
background: color-mix(in srgb, red 150%, blue);    /* 비율이 0~100% 밖 */
background: color-mix(in srgb, red 0%, blue 0%);   /* 합이 0 */
background: hsl(from #3b82f6 h s calc(l + 20%));   /* ★ l 은 수다. % 를 더할 수 없다 */
```

### 어디서 헷갈리나 — 이름 다섯

| 이름 | 무엇인가 | 헷갈리는 짝 |
|---|---|---|
| `in <공간>` | **보간**을 어디서 하나 | 결과 색이 그 공간으로 나온다는 뜻이기도 하다 |
| `shorter`/`longer hue` | 색상환의 **어느 쪽으로 도나** | 직교 공간(`srgb`·`oklab`·`lab`)에서는 아무 의미가 없다 |
| `l` in `hsl(from …)` | **0\~100 의 수** | `l` in `oklch(from …)` — 이쪽은 0\~1 |
| `color-mix()` | **값**을 섞는다 | `mix-blend-mode`(48번) — **픽셀**을 섞는다 |
| 비율 두 개 | 정규화 + **알파에 반영** | 비율 하나 — 나머지가 자동으로 채워지고 알파는 안 건드린다 |

## 어디서 틀리나

### 1. 「보색을 섞으면 회색」이라고 외운다

**공간에 달렸다.** `in srgb` 만 `rgb(128, 128, 128)` 회색이었고, 기본값인 `in oklab` 은 `rgb(210, 169, 147)` 베이지, `in hsl` 은 `rgb(128, 255, 0)` 연두였다((2) 실측).

### 2. `cssText` 에 `in oklab` 이 없어서 안 먹었다고 본다

**기본값이라 직렬화에서 생략된 것**이다((3)). 오히려 먹었다는 증거다.

### 3. `20%` 씩 둘 다 적는다

비율의 합이 100% 미만이면 **그 합이 알파가 된다.** `red 20%, blue 20%` 의 계산값은 `color(srgb 0.5 0 0.5 / 0.4)` 였고 흰 배경 위에서 `rgb(204, 153, 204)` 로 보였다((4) 실측). **비율은 하나만 적는다.**

### 4. `calc(l + 20%)` 를 쓴다

상대 색 구문의 축 이름은 **수**로 풀린다. 선언째 버려지고 아무 말도 안 나온다((7) 실측). `calc(l + 20)` 이다.

### 5. `oklch` 의 `l` 에 `0.2` 대신 `20` 을 더한다

`oklch` 의 `l` 은 `0\~1` 스케일이다. `calc(l + 20)` 은 무효는 아니지만 **1 을 한참 넘겨 흰색이 된다.** 같은 글자가 함수마다 다른 스케일이라는 것이 이 문법의 가장 큰 함정이다.

### 6. `longer hue` 를 「부드럽게」로 읽는다

**색상환을 먼 쪽으로 돈다**는 뜻이다. 빨강↔파랑 보간에서 중간이 **초록**이 됐다((5) 실측).

### 7. `color-mix()` 와 `mix-blend-mode` 를 같은 것으로 본다

전자는 **값**을, 후자는 **그려진 픽셀**을 섞는다((9)). 전자의 결과는 `getComputedStyle` 로 읽히고 후자는 안 읽힌다.

### 8. 상대 색 구문의 지원을 전제한다

Baseline **`newly`**(2024-09-16)다. `color-mix()` 는 **`widely`**(2023-05-09, high 2025-11-09)라 지원 폭이 다르다.

## 구현 세부사항 대 언어 보장

| 항목 | 누가 보장하나 | 근거 |
|---|---|---|
| `in <공간>` 이 결과를 바꾸는 것 | **언어 보장** | Color 5 가 공간별 보간을 정의한다. 실측 여섯 공간이 전부 다른 픽셀을 냈다 |
| `in srgb` 로 보색을 섞으면 회색이 되는 것 | **언어 보장** | 채널별 평균의 산술적 귀결. `#ff0000`·`#00ffff` 가 정확히 서로의 보수라서 |
| 보간 기본값이 `oklab`, 색상 보간 기본값이 `shorter` 인 것 | **언어 보장(Color 5)** | 실측 직렬화가 그 값을 생략한 것과 일치 |
| **기본값이 직렬화에서 생략되는 것** | **CSSOM 직렬화 형식 = 구현 표면** | 값이 바뀐 게 아니다. 계산값은 `oklab(...)` 으로 나온다 |
| 비율 합이 100% 미만일 때 **알파가 된다**는 것 | **언어 보장(Color 5)** | 실측 `color(srgb 0.5 0 0.5 / 0.4)` 와 일치 |
| `calc(l + 20%)` 가 버려지는 것 | **언어 보장** — 축 이름이 `<number>` 로 치환되므로 타입 불일치 | 실측에서 cssText 가 빈 문자열 |
| `rgb(from …)` 의 계산값이 `color(srgb …)` 로 나오는 것 | **구현 표면** | 실측. 레거시 `rgb()` 형태로 안 접혔다 |
| 계산값의 **소수 자릿수**(`0.766676`) | **구현 세부** | 직렬화 정밀도. 버전이 오르면 바뀔 수 있다 |
| 픽셀 RGB 의 **마지막 1 단위** | **구현 + 반올림** | 같은 색이 `rgb(128, …)` 과 `rgb(127, …)` 사이에서 흔들릴 수 있다 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 안 쓸 것 |
|---|---|---|
| 「이 색을 20% 연하게」 | `color-mix(in oklab, var(--c) 80%, white)` | `opacity` (요소 전체가 투명해진다) |
| 브랜드 색 하나에서 팔레트 | `oklch(from var(--b) … )` 로 `l` 만 옮긴다 | 흰색과 섞기 — 선명함이 같이 죽는다 |
| 호버 상태 색 | `color-mix(in oklab, currentColor 85%, black)` | 손으로 고른 hex 를 하나 더 둔다 |
| 중간색이 탁해지면 곤란하다 | `in oklch` 나 `in hsl` 로 각도를 따라간다 | `in srgb` — 무채색을 지난다 |
| 무지개를 만든다 | `longer hue` | (그 밖에는 쓰지 않는다) |
| 오래된 브라우저도 받아야 한다 | `color-mix()`(widely) + `@supports` | 상대 색 구문 단독(newly) |
| 아래 레이어와 섞고 싶다 | `mix-blend-mode`([목록의 **48번 주제**](../48-blend-modes-and-isolation/)) | `color-mix()` — 아래 레이어를 못 본다 |

## 핵심 문장

- **`in <공간>` 이 이 함수의 가장 큰 손잡이다.** 같은 두 색이 회색·베이지·연두로 갈렸다.
- **기본값은 `in oklab` 이고 직렬화에서 생략된다.** cssText 에 없다고 안 먹은 게 아니다.
- **비율을 둘 다 적으면 합이 알파가 된다.** 하나만 적는 습관이 함정 전체를 없앤다.
- **상대 색 구문의 축 이름은 수다.** `calc(l + 20%)` 는 조용히 버려진다.
- **`color-mix()` 는 값을, 혼합 모드는 픽셀을 섞는다.** 이름이 비슷할 뿐 층이 다르다.

## 용어 풀이

- **보간(interpolation)** — 두 값 사이의 중간값을 만드는 것. 예: 빨강과 청록의 50% 지점을 구하는 것.
- **보간 색 공간(interpolation color space)** — 그 중간값을 계산하는 좌표계. 예: `in srgb` 와 `in oklab` 이 같은 두 색에서 다른 결과를 냈다.
- **직교 공간(rectangular color space)** — 축이 서로 수직인 좌표계. 예: `srgb`·`oklab`·`lab` — 두 색을 직선으로 잇는다.
- **극좌표 공간(polar color space)** — 축 하나가 각도인 좌표계. 예: `hsl`·`oklch` — 색상 각도를 따라 호를 그린다.
- **색상 보간법(hue interpolation method)** — 각도를 어느 쪽으로 도느냐의 규칙. 예: `shorter hue`(기본)는 짧은 쪽, `longer hue` 는 먼 쪽으로 돈다.
- **보색(complementary color)** — 색상환에서 정반대에 있는 색. 예: 빨강 `#ff0000` 과 청록 `#00ffff`.
- **상대 색 구문(relative color syntax)** — `from` 으로 받은 색의 성분을 이름으로 참조해 새 색을 만드는 문법. 예: `oklch(from red l c calc(h + 180))`.
- **축 이름(channel keyword)** — 상대 색 구문 안에서 원본 색의 성분을 가리키는 이름. 예: `oklch()` 안에서는 `l`·`c`·`h`, `rgb()` 안에서는 `r`·`g`·`b`.
- **정규화(normalization)** — 비율의 합을 100% 로 맞추는 것. 예: `red 20%, blue 20%` 가 50:50 으로 정규화되고 합 40% 는 알파가 됐다.
- **디자인 토큰(design token)** — 색·간격 같은 디자인 값을 이름 붙여 모아 둔 것. 예: `--b` 하나에서 다섯 단계를 파생시킨 (8)의 형태.
- **Baseline** — 주요 브라우저에 그 기능이 언제부터 다 들어갔는지를 나타내는 지표. 예: `color-mix()` 는 `widely`, 상대 색 구문은 `newly` 다.

## 더 들어가면

- **`color-mix()` 는 중첩된다.** `color-mix(in oklab, color-mix(in oklab, a, b), c)` 가 유효하다 — 셋을 섞는 문법이 따로 없어서 이렇게 쓴다.
- **`light-dark()`** 는 같은 Color 5 의 함수로 Baseline `newly`(2024-05-13)다. 다크 모드 대응은 [목록의 **39번 주제**](../39-color-scheme-and-preferences/)가 정본이다.
- **`contrast-color()`** 는 「이 배경 위에서 읽히는 글자색」을 골라 주는 함수로 Baseline `newly`(2026-04-10)다 — 42번에서 본 「`l` 로는 대비를 못 맞춘다」 문제의 언어 차원 해법이다.
- **`color-mix()` 의 결과는 계산값 단계에서 이미 확정된다**(실측 — `getComputedStyle` 에 섞인 결과가 나온다). 그래서 애니메이션의 중간 프레임에서도 다시 섞지 않는다.
