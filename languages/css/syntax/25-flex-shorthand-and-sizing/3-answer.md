# css/syntax/25 — `flex` 단축의 세 값(`grow`/`shrink`/`basis`)과 크기 해결 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 **모든 치수는 Google Chrome 151.0.7922.173 headless 에서 실제로 렌더해 `getBoundingClientRect()` 로 잰 값**이고,
> **계산값은 `getComputedStyle` 로 따로 읽어 구분해 적었다**(8번이 그 이유다). 단위는 px 다.\
> 규칙은 [CSS Flexible Box Layout Level 1](https://drafts.csswg.org/css-flexbox-1/) §7·§9.7·§4.5 와
> [CSS Box Sizing Level 3](https://drafts.csswg.org/css-sizing-3/) 으로 접지했다.

## 정답

### 1. `flex: 1` 과 `flex: auto` 는 몇 픽셀로 갈리는가

**실행 결과** (Chrome 151 headless — 컨테이너 600px, 항목 내용 `A`·`BBBB`·`CCCCCCCCCCCC`)

```text
각 항목의 내용 크기(max-content)   A=8.02   BBBB=32.02   CCCCCCCCCCCC=96.02   합 136.06

flex: 1      ->  200.00 / 200.00 / 200.00   합 600.00
flex: auto   ->  162.66 / 186.67 / 250.67   합 600.00
flex: none   ->    8.02 /  32.02 /  96.02   합 136.06
```

**`.one`(`flex: 1`)의 세 칸**

- **200.00 / 200.00 / 200.00.** `flex: 1` = `1 1 0%` 이므로 basis 가 전부 0 이다.
- basis 합 0 → 자유 공간 = 600 − 0 = **600** → `grow` 1:1:1 로 **200 씩**.

**`.two`(`flex: auto`)의 세 칸 — 계산 과정**

```text
① basis = auto = 내용 크기          8.02  32.02  96.02      합 136.06
② 자유 공간 = 600 − 136.06 = 463.94
③ grow 1:1:1  ->  463.94 ÷ 3 = 154.6467 씩 더한다
④  8.02+154.65 = 162.66
   32.02+154.65 = 186.67
   96.02+154.65 = 250.67
```

- 실측이 162.66 / 186.67 / 250.67 로 이 계산과 맞는다.

**갈리는 원인이 되는 값**

- **`flex-basis` 하나뿐이다.** 두 판 모두 `grow`·`shrink` 는 `1 1` 로 같다.
- `0%` 냐 `auto` 냐 — 「총예산 전부를 나눈다」와 「내용을 먼저 주고 남은 것만 나눈다」의 차이다.

**탭 넷을 폭이 똑같게**

- **`flex: 1`** 이다. `flex: auto` 는 글자가 긴 탭이 그만큼 넓어진다.

### 2. 단축의 한 값 축약

**실행 결과** (Chrome 151 headless — `getComputedStyle` 로 각 롱핸드를 직접 읽었다)

```text
쓴 것                grow   shrink   basis        계산된 flex
(선언 없음)            0      1        auto         0 1 auto
flex: initial         0      1        auto         0 1 auto
flex: 1               1      1        0%           1 1 0%
flex: 2               2      1        0%           2 1 0%
flex: auto            1      1        auto         1 1 auto
flex: none            0      0        auto         0 0 auto
flex: 10em            1      1        160px        1 1 160px
flex: 0%              1      1        0%           1 1 0%
flex: 1 2             1      2        0%           1 2 0%
flex: 1 30px          1      1        30px         1 1 30px
flex: 0 0 50%         0      0        50%          0 0 50%
flex-basis: 50% 만     0      1        50%          0 1 50%
flex-basis: content 만 0      1        content      0 1 content
```

**세 단축의 롱핸드**

- `flex: 1` = **`1 1 0%`** · `flex: auto` = **`1 1 auto`** · `flex: none` = **`0 0 auto`**.

**초기값**

- **`0 1 auto`.** 「제 크기로 있다가 모자랄 때만 양보한다」.

**`flex: 30px` 과 자리가 다른 이유**

- `flex: 30px` = **`1 1 30px`**. 값이 **숫자면 `grow` 자리**, **길이·`%` 면 `basis` 자리**로 읽힌다.
- 생략된 나머지가 자리마다 다르다 — `grow` 자리를 채웠으면 `1 0%` 가, `basis` 자리를 채웠으면 `1 1` 이 붙는다.

**`flex: 0%` 의 `flex-grow`**

- **1 이다.** `0%` 는 숫자가 아니라 **길이**라서 `basis` 자리로 읽히고, 생략된 `grow` 에 1 이 채워진다.
- 「안 늘어나게」를 원했다면 `flex: 0 1 0%` 또는 `flex: none` 이다.

**`flex: 1` 과 `flex-grow: 1`**

- **다르다.** 단축은 생략된 `basis` 를 **`0%` 로 채우고**, 롱핸드 한 줄은 `basis` 를 초기값 `auto` 로 둔다.
- 그래서 `flex-grow: 1` 한 줄은 사실상 **`flex: auto` 와 같다.** 1번의 두 결과가 갈리는 자리가 바로 여기다.

### 3. 남는 공간은 어떻게 나뉘는가

**실행 결과** (Chrome 151 headless — 컨테이너 900px)

```text
basis 100/200/300, grow 전부 1    ->  200.00 / 300.00 / 400.00
basis 100/200/300, grow 1/2/3     ->  150.00 / 300.00 / 450.00
basis 0/0/0,       grow 1/2/3     ->  150.00 / 300.00 / 450.00
basis 0/0/0,       grow 0.2/0.3/0 ->  180.00 / 270.00 /   0.00   (합 450.00)
```

**자유 공간**

- basis 합 = 100 + 200 + 300 = 600 → 자유 공간 = 900 − 600 = **300**.

**세 칸의 최종 폭**

```text
grow 지분 합 = 3
300 × 1/3 = 100 씩 더한다
  100+100 = 200     200+100 = 300     300+100 = 400
```

**`grow` 를 1/2/3 으로 바꾸면**

- 300 을 1:2:3 으로 → **50 / 100 / 150** 을 더해 **150 / 300 / 450**.

**`grow` 는 basis 에 비례해 가중되는가**

- **아니다. 지분(`grow` 값)만으로 나눈다.**
- 근거: 같은 `grow 1/2/3` 을 **basis 0** 판과 **basis 100/200/300** 판에 걸었더니 둘 다 150 / 300 / 450 이 나왔다.\
  앞엣것은 900 을 1:2:3 으로, 뒤엣것은 300 을 1:2:3 으로 나눠 더한 것이다 — **가중했다면 두 결과가 달랐어야 한다.**
- 이것이 4번의 `shrink` 와 정반대다.

### 4. 모자라는 공간은 어떻게 깎이는가

**실행 결과** (Chrome 151 headless — 컨테이너 300px, 항목에 `min-width: 0`)

```text
① basis 100/200/300, shrink 전부 1  ->   50.00 / 100.00 / 150.00
② basis 전부 200,    shrink 1/2/3   ->  150.00 / 100.00 /  50.00
③ basis 전부 200,    shrink 0/1/1   ->  200.00 /  50.00 /  50.00
```

**세 칸의 최종 폭**

- **50 / 100 / 150.**

```text
넘침 = 600 − 300 = 300
가중치 = shrink × basis = 1×100, 1×200, 1×300 = 100, 200, 300   합 600
깎이는 양 = 300 × (가중치 / 600) = 50, 100, 150
  100−50  = 50     200−100 = 100     300−150 = 150
```

**`shrink` 가 같은데 깎이는 양이 다른 이유**

- **`shrink` 는 basis 로 가중하기 때문**이다. 지분만으로 나눴다면 100 씩 깎여 첫 칸이 **0 이 됐을 것**이다.
- 큰 항목이 더 많이 양보하는 쪽이 자연스럽다는 설계다.

**basis 를 같게 두고 shrink 만 1/2/3 이면**

- **150 / 100 / 50.** basis 가 같으니 가중이 지분 그대로가 되고, **많이 깎일수록 작아진다**(3번과 방향이 반대다).

**`flex-shrink: 0` 이 섞이면**

- **그 칸은 한 톨도 안 깎인다**(③에서 200.00 그대로). 나머지 둘이 넘침 전부를 나눠 진다.

### 5. ★ 본문이 컨테이너를 뚫는다

**실행 결과** (Chrome 151 headless — 컨테이너 300px, 왼쪽 위를 원점으로)

```text
min-width 기본(auto)   side 100.00   main 280.02   main 오른끝 x=380.02   계산값 min-width=auto
min-width: 0           side 100.00   main 200.00   main 오른끝 x=300.00   계산값 min-width=0px
두 판 모두 pre.scrollWidth = 280        (내용은 같고 상자만 달라졌다)
그 <pre> 의 min-content = 280.02, max-content = 280.02   (둘이 같다)
```

**`.main` 의 폭**

- **200px 가 아니라 280.02px 다.**

**오른쪽 끝**

- **밖이다.** x=380.02 로 300px 컨테이너를 **80.02px 뚫고 나간다.** 가로 스크롤이 여기서 생긴다.

**`flex-shrink` 는 일하고 있는가**

- **하고 있다.** basis(= 내용 크기 280.02)에서 줄이려고 했지만 **바닥이 280.02 라 한 픽셀도 못 줄였다.**
- 그래서 `flex-shrink` 를 999 로 키워도 아무 변화가 없다. **고칠 곳이 아니다.**

**고치는 한 줄과 그것이 바꾸는 것**

- **`.main { min-width: 0 }`.**
- 바꾸는 것은 **바닥의 높이**다. `flex-shrink` 를 켜는 것이 아니라, 이미 켜져 있던 `shrink` 가 **내려갈 수 있는 한계**를 0 으로 내린다.
- 다만 고쳐지는 것은 **상자의 크기**뿐이다 — 실측에서 글자 오른끝은 두 판 다 380.02 로 같았다. 넘친 내용은 `overflow` 로 따로 처리해야 한다.

**`<pre>` 대신 평범한 문단이었다면**

**실행 결과** (Chrome 151 headless — 같은 문서에서 `<pre>` 만 `<p>` 로 바꿨다. 바닥은 기본값 그대로)

```text
<pre> 판   main 280.02   오른끝 380.02
<p>  판   main 248.00   오른끝 348.00     <- 덜 뚫지만 여전히 뚫는다
```

- ★ **달라지긴 했는데 고쳐지지는 않았다.** 280.02 → 248.00 으로 줄었을 뿐 오른끝이 348 로 여전히 컨테이너(300) 밖이다.
- `<pre>` 의 `white-space: pre` 가 사라져 공백에서 쪼갤 수 있게 됐지만, **`/api/v1/users/12345/preferences` 라는 쪼갤 수 없는 조각 하나**가 248px 로 남았기 때문이다.
- 「문단으로 바꾸면 해결된다」는 직관이 **이 데이터에서는 틀렸다.** `min-content` 를 정하는 것은 태그가 아니라 **줄바꿈 기회**다. 정본은 [31번](../31-intrinsic-sizing-and-aspect-ratio/).
- *(같은 실측 — `min-width: 0` 에 `overflow-x: auto` 를 더한 판은 `main` 200.00 · 오른끝 300.00 · `scrollWidth` 280 으로, 넘친 내용이 **칸 안의 가로 스크롤**로 들어갔다.)*

**`column` 에서 같은 사고가 나면**

- 고칠 속성은 **`min-height`** 다. 주축이 세로면 자동 최소 크기도 세로에 걸린다.

### 6. `min-width` 의 기본값은 무엇인가

**두 기본값**

- 일반 블록 상자 — **`0`**.
- flex 항목 — **`auto`**. *(실측: 같은 `<div>` 가 flex 항목일 때 계산값이 `auto`, 아닐 때 `0px` 였다.)*

**무엇으로 풀리는가**

- **자동 최소 크기** — 대개 **`min-content`** 다. 「내용을 부러뜨리지 않고 가질 수 있는 가장 작은 크기」.

**「가장 긴 낱말」과 「한 줄 전체」를 가르는 것**

- **줄바꿈 기회가 있느냐**다. 낱말 사이 공백·하이픈이 있으면 거기서 쪼갤 수 있고, `white-space: pre` 면 쪼갤 곳이 없다.
- 실측 근거: 그 `<pre>` 는 `min-content` 와 `max-content` 가 **둘 다 280.02 로 같았다.** 쪼갤 수 없다는 것이 이 등식으로 드러난다.

**`getComputedStyle` 로 진단할 수 있는가**

- **부분적으로만.** 계산값이 `auto` 라는 것까지는 보이지만, **그 `auto` 가 몇 px 로 풀렸는지는 안 보인다.**
- 게다가 `overflow: hidden` 을 준 항목은 **계산값이 `auto` 인 채로 바닥이 사라진다**(10번). 계산값만 보면 사고가 나는 판과 안 나는 판이 구분되지 않는다.
- 판정은 **`getBoundingClientRect()` 로 재서** 한다 — 「컨테이너 폭보다 큰 항목이 있나」.

### 7. `width` 를 줬는데 안 먹는다

**실행 결과** (Chrome 151 headless — 셋 다 `width: 100px` 를 준 항목)

```text
flex: 0 0 auto    ->  100.00   계산값 flex-basis = auto
flex: 0 0 50px    ->   50.00   계산값 flex-basis = 50px
flex 선언 없음     ->  100.00   계산값 flex-basis = auto

flex: 0 0 100px + padding: 0 20px
  box-sizing: content-box  ->  바깥 폭 140.00
  box-sizing: border-box   ->  바깥 폭 100.00
```

**`flex: 0 0 50px; width: 100px`**

- **50px.** `flex-basis` 가 길이면 `width` 는 **무시된다.**

**`flex: 0 0 auto; width: 100px`**

- **100px.** `flex-basis: auto` 는 「`width` 를 봐라」라는 뜻이다.

**`column` 일 때 겨루는 상대**

- **`height`** 다. `flex-basis` 는 **주축 크기**이고 주축이 세로면 높이가 된다.
- *(실측: 높이 300px 인 `column` 컨테이너에서 `flex: 1 1 0` 과 `flex: 2 1 0` 항목의 높이가 100.00 / 200.00.)*

**`padding: 0 20px` 를 더하면**

- `content-box` — **140.00px**(basis 100 이 내용 칸이고 패딩이 밖에 붙는다).
- `border-box` — **100.00px**(basis 100 안에 패딩이 들어간다).
- `flex-basis` 가 재는 칸은 **`width` 와 같은 규칙**이다. 정본은 [15번](../15-box-model-and-box-sizing/).

### 8. `getComputedStyle` 은 무엇을 돌려주는가

**실행 결과** (Chrome 151 headless — 컨테이너 400px, 항목 넷을 한 화면에서 세 창으로 읽었다)

```text
항목  선언                                flex-basis(계산값)   width(계산값)   rect().width
1     flex: 0 1 50%                      50%                 163.031px       163.03
2     flex: 0 1 10em                     160px               130.438px       130.44
3     width: 25%; flex: 0 0 auto         auto                100px           100.00
4     flex: 1 1 min-content; min-width:0 min-content         6.53125px         6.53
```

**`flexBasis` 가 `50%` 인가 픽셀인가**

- **`50%` 그대로다.** 백분율은 계산값 단계에서 풀리지 않는다.

**`10em` 은 왜 다른가**

- **`160px` 로 풀린다.** 상대 길이 단위(`em`)는 **계산값 단계에서 절대 길이가 되고**, 백분율은 **사용값 단계까지 남는다.**
- 속성마다 `getComputedStyle` 이 어느 단계를 돌려주는지가 정본으로 다뤄지는 곳은 [04번](../04-value-processing-stages/)이다.

**그 값이 실제 폭인가**

- **아니다.** 항목2 는 계산값이 `160px` 인데 실제 폭은 **130.44px** 다(자유 공간이 음수라 깎였다).
- 항목1 은 계산값이 `50%`(= 200px)인데 실제 폭은 163.03px 다.

**실제 폭을 알려면**

- **`getBoundingClientRect().width`** 를 따로 잰다. 또는 `getComputedStyle().width`(사용값)를 읽는다.
- **한 표에 섞어 적지 말고 어느 창인지 밝힌다.** 위 표를 세 열로 나눠 놓은 이유가 그것이다.

### 9. 상한에 걸린 항목이 섞이면

**실행 결과** (Chrome 151 headless — 컨테이너 600px)

```text
i { flex: 1 1 0 }, 첫 항목에 max-width: 50px
  ->  50.00 / 275.00 / 275.00   합 600.00

i { flex: 0.2 / 0.3 / 0 1 0 } (grow 합 0.5), 컨테이너 900px
  ->  180.00 / 270.00 / 0.00   합 450.00   (450px 가 빈 채로 남는다)
```

**세 칸의 폭**

- **50 / 275 / 275.**

```text
① 일단 200 / 200 / 200 로 나눈다
② 첫 항목이 max-width 50 에 걸려 얼어붙는다
③ 남은 550 을 얼지 않은 둘이 1:1 로 다시 나눈다  ->  275 / 275
```

**「`flex: 1` 을 똑같이 줬는데 폭이 다르다」의 원인 둘**

1. **`max-*` 상한에 걸려 얼어붙은 항목**이 있다(위 ②).
2. **`min-width: auto` 바닥에 걸린 항목**이 있다(5번).

- 둘 다 **계산값에는 안 나타나고** `getBoundingClientRect()` 로만 보인다.

**`grow` 합이 1 보다 작으면**

- **자유 공간이 비율만큼만 쓰이고 나머지는 빈 채로 남는다.**
- 실측: 900px 컨테이너에서 `0.2 / 0.3 / 0` → 180 / 270 / 0, 합 450 — **450px 가 아무에게도 안 갔다.**

### 10. 유효하지 않은 값

**실행 결과** (Chrome 151 headless — 진단 3창의 첫째 창)

```text
document.styleSheets 의 cssRules 로 읽은 결과
  #n1 { }                      <- flex-grow: -1
  #n2 { flex-grow: 1; }        <- 정상 (대조군)
  #n3 { }                      <- flex: 1 1 -10px
  #n4 { }                      <- flex-shrink: -1

overflow 만 바꾼 판 (5번과 같은 문서, 컨테이너 300 / side 100)
  overflow: visible  ->  main 280.02   오른끝 380.02   계산값 min-width = auto
  overflow: hidden   ->  main 200.00   오른끝 300.00   계산값 min-width = auto
  overflow: auto     ->  main 200.00   오른끝 300.00   계산값 min-width = auto
```

**이 선언들은 어떻게 되는가**

- **에러 없이 통째로 버려진다.** 콘솔 경고도 없고 화면도 아무 말을 안 한다.
- `flex-grow`·`flex-shrink` 는 음수를 받지 않으므로 유효하지 않은 값이고, 오류 복구 규칙상 **선언 하나가 버려진다**([07번](../07-syntax-and-error-recovery/)).

**어떻게 확인하는가**

- **첫째 창 `cssRules`** 다. 규칙 상자가 `{ }` 로 비어 있으면 파싱 단계에서 버려진 것이다.
- `getComputedStyle` 로 보면 초기값(`0`/`1`)이 돌아와서 **「내가 안 썼나」와 「썼는데 버려졌나」가 구분되지 않는다.**

**`overflow: hidden` 을 준 flex 항목은 사고가 나는가**

- **안 난다.** 실측에서 폭이 200.00 으로 딱 맞고 오른끝이 300.00 이다.
- 스크롤 컨테이너는 내용을 잘라도 되므로 자동 최소 크기가 적용되지 않는다.

**그때 `minWidth` 는**

- ★ **세 판 모두 `auto` 다.** 계산값이 똑같은데 결과가 다르다.
- 「담겼나(`cssRules`)·잡혔나(`querySelectorAll`)·이겼나(`getComputedStyle`)」 **세 창 어디에도 안 잡히는 자리**이고, `getBoundingClientRect()` 로만 드러난다.
- 실무적 함의 — `min-width: 0` 없이 잘 돌던 코드가 **누군가 `overflow` 를 지우는 순간 터진다.**

### 11. 다른 주제와 잇기

**크기가 정해진 뒤의 배치**

- [24번](../24-flexbox-axes/)(주축·교차축과 정렬). `justify-*`·`align-*` 는 **이 문서가 정한 크기 위에서** 남는 공간을 배치한다.

**`min-content` 의 정본**

- [31번](../31-intrinsic-sizing-and-aspect-ratio/)(내재적 크기). 5·6번의 바닥과 `flex-basis: auto` 가 푸는 「내용 크기」가 거기서 정의된다.

**`gap` 이 들어가는 자리**

- **자유 공간 계산의 ②** 다 — basis 합에 `gap` 총량이 더해져 **자유 공간을 미리 줄인다.**
- 그래서 `flex: 1` 항목 셋에 `gap: 20px` 를 주면 각 칸이 `(폭 − 40) ÷ 3` 이 된다. 정본은 [26번](../26-flex-wrap-gap-order/).

**flex 항목끼리 마진 상쇄**

- **일어나지 않는다.** [18번](../18-margin-collapsing/) §(6)의 실측이 그것이다.
- 그래서 `margin: 0 10px` 를 준 항목 셋의 간격은 **20px 로 온전히 더해지고**, 그만큼 자유 공간이 줄어든다.

## 이 주제가 답하려는 질문

1. `flex: 1` 과 `flex: auto` 는 무엇이 달라서 결과가 달라지는가 — **`basis` 가 `0%` 냐 `auto` 냐 하나뿐이다**(1·2번).
2. 남는 공간과 모자라는 공간은 각각 무슨 비율로 나뉘는가 — **`grow` 는 지분만, `shrink` 는 지분 × basis**(3·4번).
3. 항목이 더 이상 안 줄어드는 바닥은 무엇이 정하는가 — **`min-width: auto` 가 `min-content` 로 풀린 값**(5·6번).

## 구현 세부사항 대 언어 보장

- **명세가 보장하는 것** — 단축의 생략값(`flex: 1` = `1 1 0%` 등) · 자유 공간 부호에 따른 `grow`/`shrink` 배타성 · `shrink` 의 basis 가중 · flex 항목의 `min-width: auto` 와 자동 최소 크기 · `overflow` 가 `visible` 이 아니면 자동 최소 크기가 적용되지 않는 것.
- **이 Chrome 의 관찰인 것** — 모든 구체 픽셀값 · 소수 자릿수 · 재분배 반복의 순서와 반올림 잔차 · `getComputedStyle` 이 `flex-basis` 에 `%`·키워드를 남기는 표현 형식.
- **관찰을 보장으로 적지 않았다** — 「여러 번 돌려 같았다」는 것은 보장이 아니다. 위 표의 값은 전부 **한 머신 한 엔진의 출력**이다.

## 용어 풀이

- **flex 항목(flex item)** — flex 컨테이너의 직계 자식 상자. `flex` 는 항목에 주는 속성이다.
- **`flex-grow`** — 자유 공간이 남을 때 더 받을 지분. 초기값 0. **basis 로 가중하지 않는다.**
- **`flex-shrink`** — 자유 공간이 모자랄 때 깎일 지분. 초기값 1. **basis 로 가중한다.**
- **`flex-basis`** — 나누기 전 항목이 먼저 받는 주축 크기. 초기값 `auto`(= `width`/`height` 를 본다).
- **자유 공간(free space)** — 컨테이너 주축 크기 − (basis 합 + `gap` + 마진). 부호가 `grow`/`shrink` 중 무엇이 일할지 정한다.
- **자동 최소 크기(automatic minimum size)** — flex 항목의 `min-width`/`min-height` 가 `auto` 일 때의 바닥. 대개 `min-content` 이고, `overflow` 가 `visible` 이 아니면 적용되지 않는다.
- **`min-content`** — 내용을 부러뜨리지 않고 가질 수 있는 가장 작은 크기. `white-space: pre` 면 한 줄 전체다.
- **얼어붙음(freeze)** — 해결 중 `min-*`/`max-*` 에 걸린 항목을 고정하고 나머지끼리 다시 나누는 것.
- **단축(shorthand)** — 여러 롱핸드를 한 줄로 쓰는 속성. 생략 자리에 채워지는 값이 롱핸드 초기값과 다를 수 있다.
- **계산값(computed value) / 사용값(used value)** — 상속에 쓰이는 값 / 레이아웃이 끝난 뒤 확정된 값. `flex-basis` 는 앞엣것만 읽히고 크기는 뒤엣것이다.
- **진단 3창** — `cssRules`(담겼나) → `querySelectorAll`(잡혔나) → `getComputedStyle`(이겼나). 10번은 **셋 다 통과하고도 결과가 갈리는** 제4의 자리다.
