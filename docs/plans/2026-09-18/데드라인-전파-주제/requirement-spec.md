# 요구사항 명세 — cs/ops-patterns 에 「데드라인 전파」 주제 신설

작성 2026-09-18 · 대상: `~/project/study-note/cs/ops-patterns/deadline-propagation/`

## ① 목표·대상

클라이언트 타임아웃과 서버 데드라인의 설계 패턴을 `cs/ops-patterns/` 에 한 주제로 신설한다.
산출물은 3파일 — `1-question.md` · `2-summary.md` · `3-answer.md` (사용자 확정).

폴더 이름은 번호 없는 `deadline-propagation/` — 기존 `failure-modes/`·`failure-at-scale/` 와 같은 선례를 따른다.
(번호 01~19는 `myway/ops-patterns` 원본 챕터에 대응하므로 원본이 없는 이 주제는 번호를 받지 않는다.)

**하나의 주제로 묶는다.** 사용자가 든 두 덩어리 — (가) 클라이언트만 타임아웃을 갖고 서버는 계속 도는 문제, (나) 중복 요청이 쌓일 때 서버를 지키는 법 — 은 같은 질문의 두 면이다:
**이 작업의 수명(lifetime)을 누가 소유하는가.** 쪼개면 (나)가 (가)의 결과라는 연결이 끊긴다.

다룰 뼈대:

1. **수명의 소유권** — 타임아웃(클라이언트의 인내심, 상대 시간, 각자 따로) ≠ 데드라인(작업의 만료 시각, 절대 시각, 호출을 타고 전파).
2. **고아 작업(orphaned work)** — 클라이언트가 끊어도 서버·DB는 모른다. 자원은 계속 잡힌다.
3. **전파 경로** — 서버 진입점 → 작업 스레드 → **DB 연결**(statement/lock/idle-in-transaction 수준의 제한) → **외부 연결**(남은 예산을 빼서 넘김) → 큐(만료분 폐기). *사용자 요구: DB 연결·외부 연결 프로세스를 어떻게 고려하는지 반드시 포함.*
4. **취소가 닿지 않는 곳** — 이미 커밋된 쓰기·보낸 메일·외부 결제. 취소는 "중단"이 아니라 "보상"이다.
5. **취소해도 남겨야 하는 것** — 감사 로그. 「취소됐다」는 사실도 기록 대상이고, 수행 기록과 성공 기록은 다르다.
6. **중복 요청과 재시도 증폭** — 클라이언트가 서버 상태를 모를 때 같은 일이 여러 벌 쌓인다.
7. **입구에서 서버를 지키는 층** — 멱등키·요청 병합·승인 제어·부하 차단. **만료된 요청은 처리하지 않고 버린다.**
8. **패턴이 서로를 배신하는 자리** — 재시도 × 타임아웃 = 증폭 등.

## ② 경계·불변식

- **성격은 설계·신뢰 패턴의 개념 정리**다(사용자 표현). 특정 언어·프레임워크 튜토리얼이 아니다.
- **기존 챕터를 다시 가르치지 않는다.** `01-retry-backoff`·`02-circuit-breaker`·`03-bulkhead`·`04-rate-limiter`·`05-backpressure`·`06-idempotency-store`·`09-stampede`·`19-graceful-shutdown` 과 겹치는 내용은 **링크로 보내고**, 이 문서는 *그 패턴들이 데드라인과 만나면 어떻게 어긋나는지*만 다룬다.
- 작성 원칙은 `reference/study-note-guide.md` — §3 도식화, §4 가독성(한 문장 한 줄), §6 수치 날조 금지.
- history 이관에서 얻은 규칙 중 **원본이 없는 문서에도 적용되는 것**을 지킨다:
  - 「대가는 무엇인가」 아래엔 실제 손실·비용만(연혁·설계 원칙·안전장치는 표제를 달리한다).
  - 도식의 화살표·칸 라벨·캡션·해설의 관계어는 근거 없이 쓰지 않는다. 부정 주장도 주장이다.
  - 용어 블록 「예:」는 같은 문서의 다른 정의와 모순되면 안 되고, 수치를 지어내지 않는다.
- 3파일 포맷·작성 순서는 `cs/ops-patterns/README.md` 와 `cs/templates/` 를 따른다.

## ④ 금지영역

- 기존 `cs/` 챕터 수정, 원본 repo(`~/project/myway` 등) 수정.
- **수치 날조** — 벤치마크 값·지연 시간·기본값을 지어내지 않는다. 확인 못 한 값은 적지 않거나 `(확인 필요)`.
- 특정 제품 고유 동작을 일반 원리처럼 쓰는 것(예: 한 DB의 기본값을 "DB는 원래 이렇다"로).
- 사용자의 실제 프로젝트(jun-bank·myway) 내부 결정을 사례로 끌어오는 것 — 이번 기준소스에서 제외됐다.

## ⑤ 검증 방법

1. **Fable 초안 → 별도 검증 패스 → 수정** (사용자 확정). 검증은 작성자와 컨텍스트가 분리된 워커가 맡는다.
2. **사실 검증** — 설정 이름·기본값·API 동작은 공식 문서로 확인. 확인 못 한 것은 본문에서 빼거나 `(확인 필요)` 표기. 날조 0건이 통과 기준.
3. **중복 검증** — ② 에 나열한 기존 8개 챕터와 내용이 겹치지 않는지 대조. 겹치면 링크로 대체됐는지 확인.
4. **형식 린트** — 코드펜스 짝, 펜스 안 하드브레이크 0, 용어 블록 「정의 + 예」, ASCII 박스 한글 2폭 정렬.
5. **3파일 정합** — `1-question.md` 의 질문이 `2-summary.md` 범위 안에 있고, `3-answer.md` 가 그 질문에 답하는지.
