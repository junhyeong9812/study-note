  - ASCII 그림을 먼저 두고, 글은 그 해설로 쓴다.

- **관련 주제·근거**

## 3. 쓰는 방식 (사용자와 합의된 기준)

1. **그림 먼저, 글은 그림 해설.** 단순 ASCII를 쓴다. 복잡한 그림 하나보다 단순한 그림 여러 개가 낫다.
2. **용어는 처음 나오는 자리 바로 아래에서 푼다.** 형식은 `  - *용어*: 설명`이다.
3. 한 문장에 한 개념만 담는다. 용어가 셋 넘게 든 문장은 쪼갠다.
4. **코드 스니펫**: OS는 저수준이 많으니 C를 주로 쓴다(시스템 콜·메모리·시그널). 앱 쪽 영향은 Java·JS·TS로 보여 준다(예: JVM 스레드와 OS 스레드, Node의 epoll/libuv).
5. **사실 규칙**
   - 수치·기본값·버전은 출처를 확인했을 때만 쓴다.
   - 확인하지 못하면 `[?]`를 붙인다.
   - **지어내지 않는다.** 예시 수치에는 "(예시)"를 붙인다.

## 3-1. 네트워크에서 나온 주의 (시범 + 2차 리뷰 약 130건의 유형)

- **`[?]` 기준**: 1차 출처로 **확인하지 못한 것에만** 붙인다. 확인했으면 근거(절·URL·소스 경로)를 쓴다.
- **규범 수준을 정확히**: POSIX·man의 "shall/must/may"와 "unspecified·implementation-defined"를 바꾸지 않는다.
- **"항상·모든·반드시·절대" 금지**: 예외가 있으면 조건을 붙인다. 네트워크에서 가장 많이 나온 지적이다.
  - 예) "close()는 FIN" → 읽지 않은 데이터가 있으면 RST
  - 예) "스위치는 프레임을 안 바꾼다" → VLAN 태그를 붙이고 뗄 때는 바뀐다
- **노트 안 모순 금지**: 그림과 식, 요약과 정답, 정답 N과 정답 M이 같은 말을 해야 한다.
  - 네트워크 예: CUBIC 그림이 식과 반대 방향이었다. NAT 그림이 본문의 MUST를 어겼다.
  - 다 쓰고 나서 스스로 대조한다.
- **man 페이지는 최신 커널보다 뒤처질 수 있다**: 기본값·동작은 kernel.org 문서나 소스와 대조하고, "리눅스 X.Y부터" 같은 버전 조건을 붙인다.
  - 네트워크 예: tcp(7)은 127초라 했지만 6.5+는 131초였다. udp(7)의 EMSGSIZE, ss(8)의 rto도 같은 경우였다.
- **방향·경우를 섞지 않는다**: RX에 대한 설명을 TX에, 한 모드(예: 레벨 트리거)에 대한 설명을 다른 모드에 그대로 쓰지 않는다.
- **계층을 섞지 않는다**: 커널 상태와 프로세스·fd 상태를 구분한다. libc 래퍼와 시스템 콜을 구분한다(예: glibc `fork()`는 `clone` 계열을 호출).
- **에러가 드러나는 방식은 구현 의존이다**: errno → Java 예외·Node 에러 매핑은 소스(OpenJDK, libuv/Node)로 확인하고 "JDK 구현에서는"처럼 한정한다.
- **진단 명령의 옵션은 실제 문서와 대조한다**. 로컬 `man`과 `--help`로 확인한다.

## 4. 원고·기존 초안 이어받기 (04·07·08·09·10·11·15·18 담당자)

- 원고는 부트캠프 책을 따라 친 노트이며, **수정하지 않는다**.
  - `cs/foundations/process-thread/README.md`: 04·07·08·15

- 새 leaf는 원고가 이미 설명한 개념을 길게 되풀이하지 않는다. 「해결하는 문제」나 「동작·원리」 첫머리에 "기초는 원고 §N"으로 링크하고 한두 줄로 요약한다.
- 빈 곳을 채운다: 리눅스 구현(시스템 콜·커널 구조·`/proc`), 커리큘럼 ⚠ 장애, 자료구조, 적용, 질문·정답.

  - root, `sudo`, sysctl 쓰기, cgroup 쓰기
