절마다 쓸 내용:
- **해결하는 문제**: 이것이 없으면 무엇이 안 되나. 쉬운 예 → "똑같은 구조다" → 실무 예.
- **동작·원리**: 본문의 중심이다. ASCII 그림을 먼저 두고 글은 그 해설로 쓴다(예: 패킷 교환도, 상태 전이도, 헤더 배치도). 하위 절(`###`)은 자유롭게 둔다.
- **쓰이는 자료구조·알고리즘**: 이 주제 안에 들어 있는 자료구조·알고리즘을 적는다. 예: 슬라이딩 윈도, 상태 기계, 해시 테이블(conntrack), 트라이(LPM), EWMA(RTO). 가능하면 cs 노트로 링크한다.
- **적용 — 풀어나가는 법**: 실무에서 이 지식을 쓰는 순서를 적는다. 설정, 코드, 진단 명령(`ss`, `tcpdump`, `curl -v`, `openssl s_client`, `dig` 등)을 포함한다.
- **장애 시나리오와 대처**: 3~5개. 각각 **현상 → 보이는 형태(에러코드·로그·지표·패킷 모양) → 원인 → 대처**로 쓴다. 커리큘럼 ⚠ 칸의 항목을 반드시 포함한다.
- **핵심 문장**: 3~6문장.
- **관련 주제·근거**
  - 선행·후속 노트 링크: 새 노트는 `../NN-slug/2-summary.md`, 아직 없는 주제는 영역 표 `../README.md` 링크와 함께 "미작성"이라고 적는다.
  - RFC 절 번호(예: RFC 9293 §3.5.2), 문서 URL, 교재 장을 적는다.

## 3. 쓰는 방식 (사용자와 합의된 기준)

1. **그림 먼저, 글은 그림 해설.** 단순 ASCII(`+--+`, `->`)를 쓴다. 복잡한 그림 1개보다 단순한 그림 여러 개가 낫다.
2. **용어는 처음 나오는 자리 바로 아래에서 푼다.** 형식은 `  - *용어*: 설명`이다.
3. 한 문장에 한 개념. 용어가 셋 넘게 든 문장은 쪼갠다.
4. **코드 스니펫**은 Java·JS·TS로 쓴다. 소켓·시스템콜·커널 경로처럼 저수준이면 C로 쓴다.
5. 줄 끝 `\`로 줄바꿈하는 등 저장소 관례를 따른다.
6. **사실 규칙**
   - 수치·기본값·버전(예: tcp_retries2, TIME_WAIT 60초, TLS 1.3 1-RTT)은 출처를 확인했을 때만 쓴다.
   - 확인하지 못하면 `[?]`를 붙인다.
   - **지어내지 않는다.** 예시 수치에는 "(예시)"를 붙인다.

## 3-1. A/B 시범에서 나온 주의 (2026-09-30)

- **`[?]` 기준**: 1차 출처(RFC·man·공식 문서·소스)로 **확인하지 못한 것에만** 붙인다. 확인했으면 근거(절·URL)를 쓰고 `[?]`는 붙이지 않는다(시범에서 맞는 주장에 `[?]` 과잉 8건).
- **규범 수준 정확히**: RFC의 MUST/SHOULD/MAY를 바꾸지 않는다(SHOULD를 "반드시"로 쓰지 않는다).
- **"항상·모든·반드시·절대" 금지 규칙**: 예외가 있으면 조건을 붙인다(예: TLS 1.3 "모든 키 교환이 전방 비밀성" → PSK 단독 모드 예외).
- **계층을 섞지 않는다**: TCP 사건(FIN = 상대 송신 종료)과 응용 사건(응답 완결 — 길이·프레이밍 필요)을 구분한다. 커널 TCP 상태와 앱 fd 상태를 구분한다(close 후 fd로는 못 읽음).
- **에러가 드러나는 순서는 구현 의존**: 예) 리눅스는 RST 수신 뒤 첫 쓰기가 ECONNRESET, 그다음부터 EPIPE+SIGPIPE — 단정 대신 "리눅스에서는(근거)"으로.
- **진단 명령은 옵션을 실제 문서와 대조**(예: TLS 1.3 암호군은 `-ciphersuites`, `-cipher`는 1.2 이하).
