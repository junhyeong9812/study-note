# issue/shell/closed-pipe-sigpipe — 정답

태그: —

## 정답
<!-- 질문 1:1 대응 -->

1. **`printf` 는 실패를 돌려주지 못하고, 스크립트가 141 로 죽는다.**\
   읽는 쪽이 모두 닫힌 파이프에 `write(2)` 를 하면 커널은 쓰던 프로세스에 SIGPIPE 를 보낸다.\
   SIGPIPE 의 기본 동작은 종료다 — `printf` 가 비0 을 돌려주기 전에 프로세스가 끝나므로 `|| handle_failure` 는 돌지 않는다.\
   셸이 보고하는 종료 코드는 128 + 신호 번호(13) = 141 이다.\
   직접 확인(bash 5.2.21): 읽는 쪽 없는 파이프로 `printf` 뒤에 한 줄을 더 둔 스크립트를 돌리면 exit 141 이고 뒷줄은 실행되지 않았다.
   > **SIGPIPE** — 읽는 쪽이 없는 파이프·소켓에 쓸 때 커널이 쓰는 프로세스에 보내는 신호(13번). `yes | head -1` 에서 `yes` 가 조용히 끝나는 것이 이 신호 덕분이다.

2. **신호가 쓰기 실패로 바뀐다.**\
   `trap '' PIPE` 는 SIGPIPE 를 무시(SIG_IGN)로 둔다. 그러면 같은 `write(2)` 가 -1 과 EPIPE 를 돌려준다.\
   bash 의 `printf` 는 "쓰기 오류: 파이프가 깨어짐"을 stderr 에 쓰고 rc 1 을 돌려준다 — 이제 `|| 처리` 가 돈다(직접 확인: 같은 스크립트가 exit 0, 뒷줄 실행, 그 줄이 본 rc 는 1).
   > **EPIPE** — 읽는 쪽 없는 파이프에 쓸 때 `write(2)` 가 돌려주는 오류 번호. 신호를 무시하거나 처리할 때만 프로그램에 보인다.

3. **되돌리기는 실행되지 않고, 경고는 원인을 잘못 말한다.**\
   출력 줄에서 서브셸이 SIGPIPE 로 죽으므로 그 뒤의 되돌리기 줄에 도달하지 못한다.\
   바깥은 서브셸 rc 로 경고 문구를 고르는데, 141 은 "출력 실패"(20)도 "되돌리기 실패"(21)도 아니어서 "그 밖" 분기의 "기록 실패(잠금·쓰기)" 경고가 나갔다.\
   기록은 남은 채라 그 대상의 "한 번만 알림"이 소비되고, 경고는 다른 원인을 가리킨다.\
   교정: 출력과 되돌리기를 하는 그 서브셸 안에만 `trap '' PIPE` 를 걸어 출력 실패를 rc 로 받는다(뒤에 이 순서 자체를 바꿨다 — [idempotent-retry-design](../../cross-cutting/reliability/idempotent-retry-design/) 의 "한 번만 알린다" 방안 비교).

4. **경고가 스크립트를 죽인다 — exit 141.**\
   stdout 이 끊겨 출력이 실패하면 스크립트는 약속대로 stderr 에 경고 한 줄을 쓴다.\
   stderr 도 읽는 쪽 없는 파이프면 그 `echo` 가 다시 SIGPIPE 를 받는다. 출력 서브셸에 건 `trap` 은 그 서브셸 안에서만 유효하므로 바깥의 경고에는 걸려 있지 않다.\
   "실패해도 통과"가 계약인데, 실패를 **알리는** 줄이 비정상 종료를 만들었다 — 리뷰어가 실험으로 재현했다(exit 141).

5. **서브셸과 `|| true` 가 막는다. `trap` 은 보조다.**\
   `( … )` 는 별도 프로세스다. 그 안의 `echo` 가 SIGPIPE 로 죽어도 죽는 것은 서브셸이고, 바깥 스크립트는 rc 141 을 받을 뿐이며 `|| true` 가 그것을 삼킨다.\
   그래서 `trap` 한 줄을 빼도 바깥은 exit 0 이고 테스트는 초록이었다.\
   `trap` 이 남아 있으면 서브셸도 죽지 않고 `echo` 가 rc 1 로 끝난다 — 관측되는 결과(바깥 exit 0, 경고는 읽는 쪽이 없어 어차피 못 본다)가 같아서 테스트로 구별되지 않는다.\
   감싸기 전체를 풀면 그 사례가 빨강(exit 141)이 되므로 방어선은 서브셸 + `|| true` 쪽이다.
   > **변형 실험(뮤테이션)** — 지키려는 줄을 일부러 지우거나 바꾼 구현으로 테스트를 돌려, 테스트가 빨강이 되는지 보는 확인. 초록이면 그 줄은 테스트가 지키지 않는다.

6. **버리면 정상 실패 경로의 경고까지 사라지고, 무시는 자식에게 이어진다.**\
   stderr 가 살아 있는 실패(잠금 실패·stdout 만 끊긴 출력 실패)에서는 경고 한 줄이 남아야 실패가 드러난다.\
   경고를 버리는 변형에서는 경고 한 줄을 단언하는 사례가 빨강이 됐다 — 구현 쪽 실험(`2>/dev/null`)에서 18개, 테스트 작성 쪽 실험(경고를 통째로 버림)에서 4개다. 두 실험의 변형이 정확히 어떻게 달랐는지는 기록 없음.\
   신호 무시(SIG_IGN)는 `exec` 를 넘어 자식 프로세스에 그대로 이어진다(POSIX).\
   직접 확인: `( trap '' PIPE; yes | head -1 )` 에서 `yes` 는 조용히 끝나지 않고 "표준 출력: 파이프가 깨어짐"을 쓴 뒤 rc 1 로 끝났다.\
   스크립트 전체에 걸면 파이프라인 앞쪽 명령들이 모두 이렇게 바뀐다 — 그래서 필요한 서브셸 안에만 건다.

7. **FIFO 를 읽기·쓰기로 한 번 열고, 쓰기 끝을 하나 더 연 뒤 첫 fd 를 닫는다.**\
   읽기·쓰기 겸용 열기는 막히지 않으므로 상대를 기다릴 필요가 없다. 첫 fd 를 닫으면 남은 쓰기 끝에는 읽는 쪽이 하나도 없다 — 쓰는 순간 반드시 SIGPIPE 다.\
   "읽는 쪽 프로세스를 띄웠다가 먼저 끝나게" 하는 방식은 끝나는 시점이 시간에 따라 달라진다.\
   `>&-` 는 fd 자체가 없어 `write` 가 EBADF 로 실패하고, `/dev/full` 은 ENOSPC 로 실패한다 — 둘 다 신호가 아니라 rc 로 돌아오므로 SIGPIPE 경로를 시험하지 못한다. 세 방식을 따로 사례로 둔다.

## 문제 구조 (추상화 코드)

### 변형 A — 출력 실패를 rc 로 처리하는 코드가 신호로 죽는다
① 문제 코드
```bash
(
  flock -x -w 2 9 || exit 1
  # ... 확인 · 기록(temp → mv) ...
  printf '%s\n' "$notice" && exit 0          # 닫힌 파이프면 여기서 SIGPIPE — 서브셸이 죽는다
  rollback=$(mktemp "$dir/.record.XXXXXX") || exit 21
  sed '$d' "$record" > "$rollback" && mv -fT -- "$rollback" "$record" || { rm -f -- "$rollback"; exit 21; }
  exit 20                                    # 도달하지 못한다
) 2>/dev/null || record_rc=$?
case "$record_rc" in
  0|10) ;;
  20) echo "경고: 출력 실패 — 기록을 되돌리고 알림 생략(통과)." >&2 ;;
  21) echo "경고: 출력 실패·되돌리기도 실패 — 이 대상의 알림은 다시 뜨지 않음(통과)." >&2 ;;
  *)  echo "경고: 기록 실패(잠금·쓰기) — 알림 생략(통과)." >&2 ;;   # 141 이 여기로 온다
esac
```
② 고친 코드
```bash
(
  trap '' PIPE                               # 이 서브셸 안에만 — 닫힌 파이프는 printf 의 rc 1 로 돌아온다
  # ... 잠금 · 확인 · 준비 ...
  printf '%s\n' "$notice" || { rm -f -- "$temporary"; exit 3; }   # 출력 실패가 rc 로 잡힌다
  mv -fT -- "$temporary" "$record" || { rm -f -- "$temporary"; exit 4; }
) 2>/dev/null || record_rc=$?
```
깨진 것: 실패 처리를 종료 코드로 짰는데, 실패가 종료 코드가 아니라 신호로 왔다.

### 변형 B — 실패를 알리는 경고가 새 실패를 만든다
① 문제 코드
```bash
case "$record_rc" in
  0|10) ;;
  3) echo "경고: 알림 생략 — 출력 실패(stdout). 다음 쓰기에서 다시 뜬다(통과)." >&2 ;;   # stderr 도 끊겼으면 SIGPIPE
  # ...
esac
return 0                                     # 도달하지 못한다 — 스크립트 exit 141
```
② 고친 코드
```bash
# 경고 출력만 SIGPIPE 에 죽지 않게 — 서브셸 안에만 trap(함수·스크립트 전체로 번지지 않게).
# 경고를 2>/dev/null 로 버리지는 않는다 — stderr 가 살아 있는 실패 경로의 경고 한 줄은 그대로 나가야 한다.
(
  trap '' PIPE
  case "$record_rc" in
    0|10) ;;
    1) echo "경고: 알림 생략 — 잠금 실패. 다음 쓰기에서 다시 시도(통과)." >&2 ;;
    3) echo "경고: 알림 생략 — 출력 실패(stdout). 다음 쓰기에서 다시 뜬다(통과)." >&2 ;;
    # ...
  esac
) || true
return 0
```
깨진 것: 실패 경로의 출력은 실패하지 않는다고 가정했다 — stdout 과 stderr 가 함께 끊기는 경우를 따로 생각하지 않았다.

### 변형 C — 방어선을 테스트로 판별한다
```bash
# 읽는 쪽 없는 파이프 — 시간에 기대지 않는 재현
mkfifo "$fifo"
exec 7<>"$fifo"; exec 8>"$fifo"; exec 7<&-     # fd 8 = 읽는 쪽 없는 쓰기 끝
# stderr 용도 같은 방법으로 fd 6
run_script >&8 2>&6; script_exit=$?
[ "$script_exit" = 0 ] || fail both-pipes-broken-exit    # 141 이 아니라 0
run_script; assert_notice                                # 실패한 호출은 "한 번"을 소비하지 않았다
```
```
변형                          결과
감싸기 전체 제거               이 사례 빨강 (exit 141)
경고를 2>/dev/null 로 버림      사례 18개 빨강 (경고 한 줄 단언 — 구현 쪽 실험)
trap 한 줄만 제거              초록 — 서브셸 + || true 가 죽음을 삼킨다
출력 서브셸의 trap 제거         읽는 쪽 없는 파이프를 쓰는 사례 2개 빨강
```
깨진 것: 고친 코드 두 줄 중 어느 줄이 실제로 막는지 몰랐다 — 테스트가 구별하지 못하는 줄은 지켜지지 않는 줄이다.
