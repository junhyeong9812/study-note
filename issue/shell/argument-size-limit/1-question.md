# issue/shell/argument-size-limit — 명령행 인수는 데이터 채널이 아니다: 인수 하나에 크기 상한이 있어 데이터가 자라는 순간 명령이 실행되지 못한다 — 질문

## 질문
1. (왜) 측정 회차마다 산출물 JSON 몇 개를 `jq --argjson name "$(cat file.json)"`로 묶어 메타 파일 하나를 만들었다. 몇 주 동안 멀쩡하던 이 줄이 산출물이 약 190KB로 커진 회차부터 `인수 명단이 너무 김`(Argument list too long)으로 실패했다. 실패한 것은 jq의 파싱인가, 그 앞 단계인가 — 커널이 명령행 인수에 두는 상한 두 가지(인수 하나·전체)는 무엇인가.
2. (예측) 같은 줄이 `... > meta.json`으로 출력을 리다이렉트하고 있었고, 회차 상태 파일(`status`)은 그 줄보다 **먼저** `ok`로 써졌다. 명령이 실행되지 못하면 디스크에는 무엇이 남는가. 그 결과를 집계 단계가 어떻게 읽게 되는가.
3. (경계) 같은 상한이 페이지 단위로 DB 기록을 이어 붙이는 루프(`jq --argjson p "$page" '. + $p'`)에도 있었다. 이 루프는 몇 행까지는 정상이고 언제부터 무엇을 하는가 — 실패가 `&&` 사슬 안에 있으면 왜 "페이지를 조용히 버림"이 되는가.
4. (교정) 인수 대신 파일로 넘기는 방법(`--slurpfile`)은 무엇을 바꾸나. 받는 쪽 식에서 `$x` 대신 `$x[0]`을 써야 하는 이유는 무엇인가. 파일이 없거나 깨졌을 때 이전과 같은 `null`을 유지하려면 무엇을 넘기나.
5. (교정) 출력 파일 쓰기를 "임시 파일 → 내용 검증 → 이름 바꾸기"로 바꾸고, 실패면 상태를 `meta-write-failed`로, 상태 파일 쓰기는 메타 **뒤**로 옮겼다. 각각이 막는 실패는 무엇인가 — 특히 상태를 뒤로 옮긴 것은 중간에 끊긴 회차를 어떻게 다루게 하나.
6. (연결) 이 결함은 한 곳을 고친 뒤 "인수로 데이터를 넘기는 곳"을 전수 감사해 두 번째 잠재 결함을 찾았다. 셸 스크립트에서 이런 자리를 찾는 기준은 무엇인가(무엇이 입력 크기에 비례해 자라는가).
