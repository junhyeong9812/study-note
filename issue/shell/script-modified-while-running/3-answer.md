# issue/shell/script-modified-while-running — 정답

태그: `race-condition`

## 정답
<!-- 질문 1:1 대응 -->

1. **실행하면서 읽는다.** bash는 스크립트 파일을 연 채로 명령 하나(복합 명령이면 그 덩어리 전체)를 읽어 파싱·실행하고, 끝나면 **파일의 현재 바이트 위치부터** 다음 명령을 읽는다.\
그래서 실행 도중 파일을 제자리에서 고치면, bash는 "원래 파일에서 다음 명령이 시작하던 오프셋"을 **새 내용**에 그대로 적용한다 — 앞쪽 줄 길이가 바뀌었다면 그 오프셋은 새 파일에서 줄 중간이 되어 문법 오류가 나거나, 우연히 다른 명령의 시작에 걸려 엉뚱한 명령이 실행된다.\
이 사례에서는 수 시간짜리 측정 실행기를 스모크 실행 중에 고쳤고, 같은 실수가 두 측정 준비에 걸쳐 반복돼 실행이 세 번 깨졌다(문법 오류로 중단 2회, 실행 코드-커밋 불일치 안전장치의 거부 1회).
   > **스크립트 오프셋** — 셸이 스크립트 파일에서 다음에 읽을 바이트 위치. 파일 내용이 바뀌어도 위치는 그대로다.

2. **루프는 이미 메모리에 있고, 루프 뒤는 아직 파일에 있다.** `for … done` 같은 복합 명령은 `done`까지 통째로 읽어 파싱한 뒤 실행하므로, 실행 중인 루프 본문은 파일을 고쳐도 바뀌지 않는다.\
루프가 끝나면 bash는 그제야 루프 뒤 오프셋에서 다음 명령을 읽는다 — 이 사례에서 스모크 9회는 모두 정상 기록됐지만 루프 뒤 줄이 수정된 파일에서 읽혀 **문법 오류(exit 2)**로 멈췄고, 마지막 정리(원격 서버의 측정 컨테이너 내리기)가 실행되지 않아 컨테이너를 손으로 정리했다.\
"본 작업은 다 끝났는데 정리만 빠졌다"는 모양이라 결과 파일만 보면 정상처럼 보인다는 점이 위험하다.

3. **제자리 덮어쓰기 vs rename 교체.** bash가 쥔 것은 파일 이름이 아니라 **열린 파일 디스크립터(=그 inode)**다(일반 원리).\
같은 inode를 제자리에서 덮어쓰면 열린 디스크립터가 새 내용을 보므로 위 사고가 난다. 새 파일을 쓴 뒤 rename으로 바꾸면 이름만 새 inode를 가리키고 열린 디스크립터는 **옛 inode를 계속** 읽으므로 실행은 옛 내용대로 끝난다.\
편집기·복사 도구마다 저장 방식이 다르고(설정으로도 바뀐다), 어느 방식이었는지는 실행 중에 드러나지 않는다 — "예전에 고쳐도 괜찮았다"는 그때의 저장 방식과 편집 위치가 우연히 맞았다는 뜻일 뿐이다. 그래서 대처는 저장 방식에 기대지 않는 **동결**이다.
   > **inode** — 파일 내용의 실체. 이름(디렉터리 항목)은 inode를 가리키는 링크일 뿐이고, 열린 파일은 이름이 아니라 inode에 묶인다.

4. **동결 사본을 exec한다.** 시작하자마자 스크립트 디렉터리를 `mktemp -d`로 만든 임시 위치에 통째로 복사하고, 그 사본을 `exec bash`로 다시 실행한다 — 이후 원본을 어떻게 고쳐도 실행 중인 프로세스는 사본만 읽는다.\
① **재복사 방지**: 동결 여부를 환경변수(`FROZEN=1`)로 넘겨, 사본으로 다시 들어온 실행은 복사를 건너뛴다.\
② **결과 위치**: 사본의 위치(`$0` 기준 경로)는 임시 폴더이므로, 결과·로그를 쓸 원래 경로를 동결 전에 계산해 환경변수로 넘긴다 — 안 그러면 결과가 임시 폴더에 쓰이고 지워진다.\
③ **정리 가드**: 끝나고 사본을 지울 때 그 경로가 **mktemp 경로 패턴**(`$TMPDIR/tmp.*`)이고 사본 구조(`scripts/`)가 있을 때만 `rm -rf`한다 — 변수가 비거나 원래 경로를 가리키면 작업 트리를 지우게 되기 때문이다.\
운영 규칙도 함께 둔다: 실행 중에는 그 디렉터리를 편집하지 않는다(동결은 사고를 무해하게 만들 뿐, 고친 내용이 실행에 반영되지는 않는다).

5. **모든 진입점과 입력을 동결한다.** 두 번째 측정 준비에서 상위 실행기와 하위 실행기는 동결했지만, 쿼리 벤치마크 도구를 **직접 실행하는 경로**는 동결하지 않아 실행 중 편집에 다시 문법 오류로 멈췄다 → 그 도구에도 같은 동결 머리말을 넣었다(상위가 이미 동결한 사본에서 부르면 환경변수로 재동결을 건너뜀).\
스크립트가 읽는 **입력 파일**도 같은 문제다 — 부하 시나리오를 작업 트리에서 읽으면 "기록한 커밋"과 다른 시나리오가 실행될 수 있으므로, 실행 시작 때 기록된 커밋에서 꺼낸다(`git archive <SHA> <경로> | tar -x -C <임시>`).

6. **이중 검사 + 실패 무시.** 동결과 짝으로 "작업 트리(추적·미추적 파일)가 기록할 SHA와 다르면 시작 거부" 검사를 두었는데, 이 검사가 **하위 실행기에도** 있어서, 실행 중 작업 트리를 고치면 상위가 다음 조건을 부를 때마다 하위가 즉시 거부하는 구조였다 — 그리고 상위는 하위의 실패를 보지 않고 다음으로 넘어가 **"done"**으로 끝나게 되어 있었다(측정 전 코드 리뷰에서 발견·수정).\
교정: ① 검사는 **최상위가 시작할 때 한 번** — 상위가 동결·확인한 상태로 부른 하위는 검사를 건너뛴다. ② 상위는 하위가 비정상 종료하면 **중단(ABORT)을 기록하고 멈춘다**.\
곁가지: 1차 수정은 괄호가 없어 "건너뛰어야 할" 미추적 파일 검사가 그대로 돌았다(`A && ! B || C`는 `(A && ! B) || C`로 묶인다) — 재점검에서 잡아 `A && { ! B || C; }`로 괄호를 쳐 고쳤다 — 연산자 결합은 [exit-status-semantics](../exit-status-semantics/)와 같은 계열의 함정이다.

## 문제 구조 (추상화 코드)

### 변형 A — 실행 중 원본 편집: 루프 뒤 줄을 어긋난 오프셋에서 읽음
① 문제 코드
```bash
#!/usr/bin/env bash
for cell in $CELLS; do        # 수 시간 — done까지 이미 파싱되어 메모리에서 실행
  run_one "$cell"
done
cleanup_remote                # 루프가 끝난 뒤에야 파일에서 읽음
# (실행 도중 이 파일을 제자리에서 수정) → 루프 뒤 오프셋이 새 내용의 줄 중간 → syntax error, exit 2
# → cleanup_remote 미실행 → 원격 컨테이너 잔존
```
② 고친 코드
```bash
#!/usr/bin/env bash
if [[ "${FROZEN:-0}" != 1 ]]; then                       # 시작 즉시 동결
  src="$(cd "$(dirname "$0")" && pwd)"
  frozen="$(mktemp -d)"
  cp -r "$src" "$frozen/scripts"
  export FROZEN=1 FROZEN_DIR="$frozen" OUT_DIR="${OUT_DIR:-$(cd "$src/.." && pwd)}"   # 결과는 원래 위치로
  exec bash "$frozen/scripts/runner.sh" "$@"              # 이후 원본 편집은 이 프로세스에 무관
fi
cleanup_tmp() {                                           # 지우는 것은 이 실행이 만든 mktemp 사본만
  [[ -n "${FROZEN_DIR:-}" && "$FROZEN_DIR" == "${TMPDIR:-/tmp}"/tmp.* && -d "$FROZEN_DIR/scripts" ]] \
    && rm -rf "$FROZEN_DIR"
}
trap cleanup_tmp EXIT
# ... 본 실행 ...
```
무엇이 깨졌나: 실행 중인 해석기가 읽고 있는 파일을 바꿔, 아직 읽지 않은 뒷부분이 다른 내용이 됐다.

### 변형 B — 동결 범위 누락: 하위 도구 직접 실행·작업 트리 입력
① 문제 코드
```bash
bash tools/bench.sh --out "$OUT"          # 상위 경유가 아닌 직접 실행 → 동결 없음 → 편집 시 문법 오류
k6 run scenarios/load.js                  # 시나리오를 작업 트리에서 읽음 → 기록한 커밋과 다를 수 있음
```
② 고친 코드
```bash
# tools/bench.sh 맨 앞에도 같은 동결 머리말 (상위 사본에서 불리면 FROZEN=1이라 건너뜀)
SCEN="$(mktemp -d)"
git -C "$REPO" archive "$SHA" scenarios | tar -x -C "$SCEN" \
  || { echo "cannot extract scenarios from $SHA" >&2; exit 2; }
k6 run "$SCEN/scenarios/load.js"          # 실행 입력 = 기록된 커밋
```
무엇이 깨졌나: 동결이 "진입점 하나"에만 걸려, 다른 진입 경로와 입력 파일은 여전히 원본을 읽었다.

### 변형 C — 상·하위 이중 검사 + 하위 실패 무시 → "done" 위장
① 문제 코드
```bash
# 상위: 조건들을 순서대로
for cond in "${CONDS[@]}"; do
  bash runner.sh --sha "$SHA" $cond        # 반환값 무시
done
echo "$(date -Is) done" >> "$LOG"
# 하위 runner.sh: 매번 "작업 트리 == SHA" 검사 → 실행 중 편집 시 남은 조건 전부 즉시 exit 2
```
② 고친 코드
```bash
# 하위: 상위가 시작 때 확인·동결했으면 검사 생략 (괄호로 결합 명시)
if [[ "${PARENT_FROZEN:-0}" != 1 ]] && { ! git -C "$REPO" diff --quiet "$SHA" -- harness \
     || [[ -n "$(git -C "$REPO" ls-files --others --exclude-standard -- harness)" ]]; }; then
  echo "harness differs from $SHA — commit first" >&2; exit 2
fi
# 상위: 하위 비정상 종료 = 중단
for cond in "${CONDS[@]}"; do
  bash runner.sh --sha "$SHA" $cond; rc=$?
  if (( rc != 0 )); then echo "$(date -Is) ABORT $cond exit=$rc" >> "$LOG"; exit "$rc"; fi
done
```
무엇이 깨졌나: 같은 검사를 두 층에 두어 정상 운영(실행 중 원본 편집)이 대량 실패가 됐고, 상위가 그 실패를 성공으로 접었다.

## 방안 비교

### 방안 1 — 동결 사본 실행 (이 사례의 선택)
위 변형 A·B의 ② — 시작 시 디렉터리를 복사해 사본을 exec, 입력은 기록된 커밋에서 추출.

### 방안 2 — 파일 전체를 먼저 파싱시키는 구조 (일반 원리 — 이 사례에서는 쓰지 않음)
```bash
#!/usr/bin/env bash
main() {
  # ... 스크립트 전체 ...
}
main "$@"; exit      # 함수 정의(복합 명령)는 끝까지 파싱된 뒤 호출된다 + exit로 뒤를 읽지 않음
```

### 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 동결 사본 exec | 임시 디렉터리 쓰기 가능, 결과 경로를 별도로 전달 | 머리말 몇 줄 + 경로 전달 규약, 정리 가드 | 진입점·입력 하나라도 빠지면 재발, 결과 경로 전달 누락 시 결과가 임시 폴더로 감 | 여러 스크립트·입력 파일이 묶인 장시간 하네스 |
| `main "$@"; exit` | 스크립트가 파일 하나 | 구조 변경만 | 그 파일만 보호 — `source`하는 다른 파일·하위 스크립트·입력 데이터는 보호 못 함 | 단일 파일 스크립트 |

**결론**: 단일 파일이면 `main "$@"; exit` 구조로 충분하지만, 하위 스크립트·라이브러리·시나리오 파일을 함께 읽는 장시간 실행이면 그 묶음 전체를 동결하는 쪽이 맞다.\
어느 쪽이든 "실행한 코드 = 기록한 커밋"을 남기려면 시작 시 작업 트리-커밋 일치 확인이 따로 필요하다(동결은 실행 중 변경만 막고, 시작 시점의 미커밋 변경은 막지 않는다).
