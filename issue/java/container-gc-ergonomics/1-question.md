# issue/java/container-gc-ergonomics — JVM은 실행 환경을 보고 수집기를 고른다: 작은 컨테이너에선 Serial GC가 꼬리 지연을 만든다 — 질문

## 질문
1. (왜) 수집기를 지정하지 않은 JVM이 CPU 4개·메모리 한도 1GiB 컨테이너에서 G1이 아니라 Serial을 골랐다. JVM은 무엇을 보고 기본 수집기를 정하는가. 같은 이미지가 개발 PC에서는 G1이었다면 무엇이 달라진 것인가.
2. (예측) 최대 힙은 768MB까지 허락돼 있는데 실제로 잡은 힙은 약 200MB에 머물렀고, Full GC가 약 47초마다 72~108ms씩 났다. 힙 상한이 큰데 왜 old 영역이 금방 차는가.
3. (예측) 고정 도착률 1초 4,200건 부하에서 앱이 100ms 멈추면 무슨 일이 생기는가. 처리량(초당 성공 수)과 평균 지연은 왜 거의 그대로이고 무엇만 나빠지는가.
4. (경계) 메모리를 2GB로 늘려도 G1이 자동으로 골라지고 Full GC가 사라졌다. 그런데도 "메모리를 늘린다"가 아니라 "수집기를 명시한다"를 기준으로 삼은 이유는 무엇인가. 명시 옵션이 실제로 먹었는지는 어떻게 확인하는가.
5. (대가) Serial → G1로 바꾸자 Full GC는 0이 됐지만 앱 CPU가 약 25% 늘었다. 이 비용은 어디서 오는가(추정까지). 어떤 부하에서 이 비용이 문제가 되는가.
6. (연결) G1으로 바꾼 뒤에도 50~150ms 튐이 약 26초 간격으로 남았다. "GC가 꼬리 지연의 원인"이라는 결론을 어디까지만 말할 수 있는가 — 튐의 크기만으로 GC 여부를 가를 수 있는가.
