# issue/java/container-gc-ergonomics — 정답

태그: `environment-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **JVM 에르고노믹스가 보이는 자원으로 고른다.** 수집기를 지정하지 않으면 JVM은 기동 시 CPU 수와 메모리 크기를 보고 "서버급 기계"인지 판정해, 서버급이면 G1, 아니면 Serial을 쓴다.\
판정 기준은 CPU 2개 이상이면서 메모리 약 1792MB(2GB − 256MB) 이상이다(OpenJDK HotSpot 소스의 판정 — 이 사례에서 확인한 것은 1792MB에서 G1이 골라진다는 것까지이고, 그 바로 아래는 재지 않았다).\
컨테이너 안의 JVM은 호스트가 아니라 **컨테이너 한도**를 자원으로 본다 — CPU는 4개였지만 메모리 한도 1GiB가 기준 아래라 Serial이 골라졌다.\
같은 이미지가 다른 곳에서 G1이었다면 바뀐 것은 코드가 아니라 실행 환경(한도)이다.
   > **에르고노믹스(ergonomics)** — JVM이 기동 시 하드웨어·한도를 보고 수집기·힙 크기 같은 기본값을 스스로 정하는 동작.
   > **stop-the-world** — GC가 일하는 동안 앱의 모든 스레드를 세우는 정지. Serial은 이 정지 안에서 스레드 하나로 치운다.

2. **힙 상한이 아니라 "잡은 힙"이 old 여유를 정한다.** `MaxRAMPercentage=75`라 상한은 768MB였지만, Serial은 Full GC 뒤 살아남은 양(약 80MB)에 맞춰 실제로 잡는 힙을 작게(약 190~200MB) 유지했다.\
그래서 old 칸에 여유가 거의 없고, Young GC가 오래 산 객체를 old로 옮기다 old가 가득 차면 같은 정지 안에서 Full GC로 이어진다(GC 로그에서 old 영역이 한도 직전까지 찬 시점에 Full GC가 붙었다).\
결과는 약 47초(25~60초)마다 72~108ms의 Full GC였다 — 방은 큰데 작은 쓰레기통만 두고, 찰 때마다 모두를 세워 대청소하는 상태다.

3. **정지는 처리량이 아니라 꼬리로 간다.** 고정 도착률이면 앱이 멈춰도 요청은 계속 들어온다 — 100ms 정지면 약 420건이 쌓이고, 풀리는 순간 몰려 처리되며 뒤 요청까지 줄을 선다.\
그 1초의 최대 응답이 150~300ms로 튀었고(평소 p99 약 4ms), 처리량(4,200건/s)과 p50은 거의 그대로였다.\
평균·처리량만 보면 문제가 보이지 않는다 — 꼬리 지표를 정지 길이와 비슷한 해상도(1초)로 봐야 드러난다.

4. **자동 경계에 기대면 경계가 바뀔 때 조건이 바뀐다.** 메모리를 늘려 G1이 골라지게 하는 방법은 JVM 버전마다 다를 수 있는 숨은 규칙에 기대고, 자원도 두 배를 쓴다.\
그래서 기준을 "메모리 1g + `-XX:+UseG1GC` 명시"로 정했다 — 측정 전에 고정한 판정 규칙(Full GC 0 · 정지 최대 < 50ms · 1초 p99 최대가 Serial보다 낮음)을 1g에서 통과했기 때문이다.\
명시 옵션이 실제로 먹었는지는 회차마다 **실제 컨테이너 메모리 한도·실제 JVM 옵션·GC 로그의 수집기**를 기록해 계획과 대조하고, 다르면 그 회차를 하네스 실패로 처리해 다시 잰다.\
같은 이유로 공유 이미지의 기본값은 바꾸지 않고 새 측정의 실행 옵션에만 넣었다 — 이미지를 바꾸면 지난 측정을 다시 돌릴 때 수집기가 달라진다.

5. **G1의 대가는 CPU다.** G1은 힙을 구역으로 나눠 여러 스레드로 치우고 old 영역 표시를 앱과 동시에 돌린다 — 정지가 짧아지는 대신 그 일을 앱 실행 중에 CPU로 한다.\
앱 CPU 평균이 140% → 166~175%(1코어 = 100%)로 늘었다.\
원인은 잡은 힙이 150~170MB로 작게 유지된 상태에서 동시 표시가 자주 돈 탓으로 **추정**한다(CPU를 나눠 재지는 않았다).\
앱 CPU가 병목인 부하에서는 이 비용이 처리량을 깎을 수 있으므로 그때 다시 잰다.
   > **동시 표시(concurrent marking)** — 앱 스레드를 세우지 않고 old 영역의 살아 있는 객체를 표시하는 G1 단계. 시작·끝(Remark)만 짧게 멈춘다.

6. **GC 시각과 일치한 튐까지만 GC 탓이다.** Serial 회차의 느린 초(최대 응답 > 50ms) 12개 중 8개가 Full GC 시각(±1초)과 일치했고(99~314ms), 나머지 4개(57~82ms)는 일치하지 않았다.\
G1 회차들은 Full GC가 없고 정상 구간 정지 최대 2.6~4.8ms인데도 51~149ms 튐이 회차마다 8~13초 남았고, 약 26.5초 간격(또는 그 배수)에 맞았다 — 관측된 GC 정지만으로는 설명되지 않는다(원인 미확인).\
두 종류의 튐은 크기 범위가 겹치므로 크기만으로 가를 수 없다 — 원인 귀속은 **사건 시각 대조**로 한다.\
그리고 한 번씩만 잰 비교라, 수집기 사이의 작은 차이(G1 1g의 p99가 Serial보다 +12% 등)는 흔들림과 구분하지 못한다.
   > **safepoint** — JVM이 모든 스레드를 멈춰 세울 수 있는 지점. GC 정지 시간은 safepoint 기록으로 재면 앱이 실제로 멈춘 길이에 가깝다.

## 문제 구조 (추상화 코드)

### 변형 A — 수집기 미지정 + 작은 메모리 한도
① 문제 코드
```yaml
services:
  app:
    image: app:latest
    mem_limit: 1g                                     # 서버급 판정 기준(약 1792MB) 아래
    environment:
      JAVA_TOOL_OPTIONS: "-XX:MaxRAMPercentage=75"    # 수집기 미지정 → JVM이 Serial을 고름
```
② 고친 코드
```yaml
services:
  app:
    image: app:latest                                 # 이미지 기본값은 그대로(지난 측정 재현용)
    mem_limit: ${APP_MEM:-1g}
    environment:
      JAVA_TOOL_OPTIONS: "${APP_JVM_OPTS:+${APP_JVM_OPTS} }-XX:MaxRAMPercentage=75 -Xlog:gc*,safepoint:file=..."   # G1 조건: APP_JVM_OPTS=-XX:+UseG1GC
```
```sh
# 자동 조건도 빈 값을 명시해 넘긴다 — 실행 환경에 남은 값이 섞이지 않게
APP_JVM_OPTS=$([ "$APP_GC" = g1 ] && echo "-XX:+UseG1GC") compose up -d app
```
```sh
# 회차마다 실제 적용값을 기록하고 계획과 대조 — 다르면 하네스 실패(다시 잼)
mem=$(container_memory_limit "$APP")                  # 바이트
opts=$(container_env "$APP" JAVA_TOOL_OPTIONS)
[ "$mem" = "$WANT_MEM_BYTES" ] && [[ "$opts" == "$WANT_OPTS_PREFIX"* ]] || reasons+=(jvm-mismatch)
[ "$WANT_GC" = g1 ] && [ "$(collector_from_gc_log)" != G1 ] && reasons+=(gc-collector-mismatch)
```
무엇이 깨졌나: 런타임이 실행 환경을 보고 고른 기본값(수집기)이 실행 조건의 일부가 됐는데, 기록·고정되지 않았다.

### 변형 B — 튐의 원인 귀속: 크기 대신 시각 대조
① 문제 코드
```text
1초 최대 응답 > 200ms 인 초가 있다 → "Full GC 탓" (GC 로그 없이, 크기로 추정)
```
② 고친 코드
```python
slow = [s for s, mx in max_latency_per_sec.items() if s >= ramp_end and mx > 50]   # 느린 초
full = [t - clock_offset for t in full_gc_times(gc_log)]                          # 서버 시계 → 부하 생성기 시계
match = {s: any(abs(s - g) <= 1 for g in full) for s in slow}                     # ±1초 일치
# 일치한 초만 "GC 튐", 나머지는 주기·다른 주기 작업 시각과 따로 대조
```
무엇이 깨졌나: 증상의 크기로 원인을 정해, GC가 없는 같은 크기의 튐을 같은 원인으로 묶었다.\
(G1 회차의 남은 튐은 이 대조로 "GC와 일치하지 않음"까지만 확인했다 — 원인은 미확인.)

## 방안 비교

같은 문제(작은 메모리 한도에서 Serial Full GC가 꼬리 지연을 만든다)를 푸는 네 조건을, 고정 도착률 4,200건/s · 디스크 영향을 뺀 같은 셀 · 각 1회로 쟀다.

```text
① 1g  미지정   → Serial(자동)
② 1g  -XX:+UseG1GC
③ 1792m 미지정 → G1(자동 — 경계 위)
④ 2g  미지정   → G1(자동)
```

| 방안 | 정상 구간 Full GC | 정지 최대 | 1초 p99 최대 | p99 | 앱 CPU | 전제 | 실패 모드 | 맞는 조건 |
|------|------|------|------|------|------|------|------|------|
| ① 그대로 | 8 | 100.5ms | 301ms | 4.58ms | 140% | 꼬리 지연을 보지 않는다 | 약 47초마다 0.1초 정지가 모든 측정의 꼬리에 섞인다 | 처리량·평균만 보는 짧은 측정 |
| ② G1 명시 | 0 | 3.4ms | 97ms | 5.13ms | 175% | CPU 여유가 있다 | CPU 병목 부하에서 처리량 비용, 메모리가 더 작으면 G1도 Full GC로 떨어질 수 있다 | 자원은 그대로 두고 꼬리를 없애야 할 때 |
| ③ 경계까지 메모리 | 0 | 4.8ms | 90ms | 4.18ms | 167% | 자동 선택 경계가 고정돼 있다 | JVM 버전·판정 규칙이 바뀌면 조용히 Serial로 돌아간다 | 옵션을 못 넣는 환경 |
| ④ 넉넉한 메모리 | 0 | 2.6ms | 96ms | 3.81ms | 166% | 메모리를 두 배 써도 된다 | 자원 비용, 경계 의존은 ③과 같다 | 메모리가 싸고 p99 자체를 더 낮추고 싶을 때(1회 측정 — 미확정) |

**결론**: 꼬리 지연을 없애는 데는 메모리를 늘리는 것보다 **수집기를 명시하는 것**이 충분했다 — ②는 자원 그대로 Full GC 0·1초 p99 최대 약 1/3이다.\
③·④는 같은 효과를 자동 선택에 기대어 얻으므로, 경계가 바뀌면 조건이 조용히 바뀐다.\
다만 1회 측정이라 ②~④ 사이의 p99·30초 구간 p99 차이(④가 ②보다 p99 −26%)는 흔들림과 구분하지 못한다 — 메모리를 늘리는 이득은 반복 측정으로 다시 본다.\
②의 대가(앱 CPU +19~25%)는 CPU가 병목인 부하에서 다시 잰다.
