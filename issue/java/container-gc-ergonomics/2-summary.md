# issue/java/container-gc-ergonomics — 정리 (힌트)

## 전체 흐름

```text
[JVM 기동 — 수집기 미지정]
  컨테이너 한도 읽기 (CPU 4 · 메모리 1GiB)
        │
        ▼
  "서버급 기계인가?"  CPU ≥ 2  그리고  메모리 ≥ 약 1792MB(2GB − 256MB)
        │ 아니오 (메모리 미달)                       │ 예
        ▼                                            ▼
  Serial (단일 스레드 · stop-the-world)            G1 (구역 단위 · 동시 표시)

[Serial로 돈 결과 — 실패 지점]
  힙 상한 768MB(MaxRAMPercentage=75) 인데 잡은 힙 ≈ 200MB
        │  Full GC 뒤 살아남은 양(≈80MB)에 맞춰 힙을 작게 유지
        ▼
  old 여유 없음 → Young GC가 old로 옮기다 old 가득 → 같은 정지 안에서 Full GC
        │  약 47초마다 72~108ms 앱 전체 정지
        ▼
  고정 도착률 4,200건/s → 정지 동안 약 420건 적체 → 풀리며 몰림
        ▼
  처리량·p50 그대로, 그 1초의 최대 응답 150~300ms (평소 p99 약 4ms)

[교정]
  -XX:+UseG1GC 명시 (메모리 1g 그대로)  → Full GC 0 · 정지 최대 3.4ms · 1초 p99 최대 301 → 97ms
  회차마다 실제 수집기·메모리 한도·JVM 옵션을 기록하고 계획과 다르면 실패 처리
  대가: 앱 CPU +19~25%
  남은 것: GC와 시각이 맞지 않는 50~150ms 주기 튐 (원인 미확인)
```

## 핵심 문장

- 수집기를 지정하지 않으면 JVM이 **보이는 자원**(컨테이너 한도)으로 고른다 — 같은 이미지라도 한도가 바뀌면 수집기가 바뀐다.
- Serial은 앱 전체를 세우고 스레드 하나로 치운다 — 힙을 살아남은 양에 맞춰 작게 유지하면 Full GC가 주기적으로 반복된다.
- 고정 도착률 부하에서 0.1초 정지는 처리량이 아니라 **꼬리 지연**(그 1초의 최대·p99)으로 나타난다.
- 자동 선택의 경계에 기대지 말고 **수집기를 명시**하고, 회차마다 실제로 적용된 수집기를 기록·대조한다.
- G1의 대가는 CPU다 — CPU가 병목인 부하에서는 다시 재야 한다.
- "GC가 원인"은 GC 시각과 일치한 튐에 대해서만 말한다 — 크기만으로는 GC 튐과 다른 튐을 가를 수 없다.
