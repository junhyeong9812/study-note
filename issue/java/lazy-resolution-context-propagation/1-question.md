# issue/java/lazy-resolution-context-propagation — 지연 해석되는 값은 해석 문맥과 함께 다닌다: 파생 객체가 ClassLoader를 떨어뜨리면 기본 로더가 조용히 다른 답을 낸다 — 질문

## 질문
1. (왜) 클래스 파일을 로드하지 않고 어노테이션 메타데이터를 읽는 경로는 `Class` 타입 속성값을 `Class` 객체가 아니라 **클래스 이름 문자열**로 저장하고, 나중에 해석할 ClassLoader를 함께 보관한다. 왜 이름과 로더를 한 쌍으로 들고 있어야 하는가 — 이름만으로는 무엇이 정해지지 않는가.
2. (예측) 루트 뷰(로더 + 이름 맵)에서 상위 단계 뷰를 파생하는 팩토리가 원천·속성 맵·값 추출기는 복사했지만 로더 자리에 `null`을 넘겼다. 파생 뷰에서 그 속성을 `Class`로 꺼내면, 클래스가 **커스텀 로더에만** 보일 때와 **기본 로더에도** 보일 때 각각 무슨 일이 일어나는가.
3. (경계) 같은 메타데이터에서 루트 뷰로 꺼내면 정상이고 파생 뷰로 꺼낼 때만 틀렸다. 왜 루트는 멀쩡했는가. 그리고 리플렉션으로 읽은 경로는 같은 팩토리에서 `null` 로더를 넘겨도 왜 문제가 없는가.
4. (식별성) JVM에서 "같은 클래스"는 무엇으로 정해지는가. 이름이 같은 두 `Class` 객체가 `==`·`isAssignableFrom`·캐스트에서 어떻게 행동하는지, 그리고 이 결함이 예외 없이 지나갈 때 어디서 드러나는지 설명하라.
5. (검증) 이 결함을 재현하는 테스트를 설계하라. 클래스가 기본 로더에도 보이는 상황에서 "다른 로더의 Class"를 어떻게 만들고, 무엇을 단언해야 고치기 전 실패·고친 뒤 통과가 갈리는가. "예외가 안 난다"를 단언하면 왜 부족한가.
6. (연결) 이 원리를 ClassLoader 밖으로 일반화하라 — charset·타임존·로케일·보안 문맥처럼 "값을 나중에 해석하는 데 필요한 문맥"이 파생·복사 단계에서 빠지고 `null = 기본값` 대체가 일어나면 공통적으로 무엇이 깨지는가. 이미 로더를 넘기던 형제 팩토리가 있었다는 사실은 어떤 점검 방법을 시사하는가.
