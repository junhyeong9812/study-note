## 정답

<!-- 질문 1:1 대응 -->

1. Spring Data JPA의 기본 구현은 엔티티가 **새 것인지(isNew)** 를 판단한다. 기본 판단은 id가 null(원시 타입이면 0)인지, 버전 필드가 있으면 버전이 null인지다. 새 것이면 `EntityManager.persist`, 아니면 `EntityManager.merge`를 부른다. 이름은 "저장" 하나지만 의미가 전혀 다른 두 연산이다.
   > **isNew 판단** — 엔티티가 아직 DB에 없는지 가르는 규칙. 식별자를 앱이 직접 채우는 엔티티는 이 판단이 틀리기 쉬워 `Persistable`로 재정의하기도 한다.

2. 루트의 id가 있으므로 isNew = 거짓 → **merge**가 실행된다. 루트는 이미 관리 중이라 그대로지만, cascade MERGE가 새 자식에 닿으면 JPA는 그 자식이 비영속이므로 **새 관리 인스턴스를 만들어 상태를 복사**하고 그 복사본을 영속화한다. flush에서 INSERT되고 id를 받는 것은 복사본이다. 코드가 들고 있던 원본 자식은 관리 밖이라 id가 null로 남고, `id!!`에서 NPE가 났다.

3. `persist(x)`: **x 자신**이 관리 대상이 된다 — 이후 x의 변경이 추적되고, id가 x에 채워진다. `merge(x)`: x의 상태를 **관리 중인 다른 인스턴스**(없으면 새로 만든 것)에 복사하고 그 인스턴스를 반환한다 — x는 여전히 관리 밖이다. 즉 persist는 정체성을 보존하고, merge는 정체성을 바꿔 치운다. "인자로 넘긴 객체 = 영속 객체"는 persist에서만 참이다.
   > **영속성 컨텍스트(persistence context)** — 트랜잭션 동안 엔티티 인스턴스를 id별로 하나씩 관리하는 1차 캐시. 관리 중인 인스턴스의 변경은 flush 때 자동으로 SQL이 된다.

4. 필요 없다. 트랜잭션 안에서 조회한 엔티티는 이미 관리 중이므로, flush(커밋 직전 자동, 또는 명시 호출) 때 **변경 감지**가 필드 변경을 UPDATE로 만들고, **cascade PERSIST**가 관리 중인 부모에 새로 붙은 자식을 찾아 persist한다 — 이때 영속화되는 것은 원본 자식이다. id를 DB가 발급하는 방식(IDENTITY)이면 INSERT가 실행돼야 id가 생기므로, 응답에 id가 필요하면 커밋 전에 flush를 명시한다.

5. 비교:
   - **flush만 호출**(이번 선택): 애그리거트 경계를 지킨다 — 루트를 통해 자식이 생기고 루트를 통해 저장된다. 코드도 가장 짧다. 대가는 "save를 안 부르는 게 맞다"는 JPA 지식을 요구한다는 것(그래서 주석을 남겼다).
   - **save 반환값에서 자식 찾기**: 동작은 맞지만 반환된 루트에서 방금 추가한 자식을 다시 찾아야 해서(동일성으로 못 찾음) 어색하다.
   - **자식을 자기 리포지토리로 직접 저장**: id는 확실히 얻지만 **애그리거트 내부 엔티티를 밖에서 저장**하게 되어 경계가 깨진다(루트를 거치지 않는 변경 경로가 생긴다).

6. 원본과 복사본이 **둘 다 존재**하게 된다. 이후 코드가 원본을 계속 수정하면 그 변경은 DB에 가지 않는다(관리 밖이므로). 반대로 원본을 다시 컬렉션에 넣거나 같은 자식을 또 저장하면 **중복 INSERT**가 생길 수 있다. id를 읽지 않으면 이 어긋남은 에러 없이 데이터만 틀어진다 — 이번엔 id를 곧바로 읽는 코드였기에 NPE로 즉시 드러났다.

## 발생한 문제 / 해결 (추상 원리)

**문제:** "저장"이라는 하나의 이름 아래 persist/merge가 분기하는 추상. 이미 영속 상태인 애그리거트에 습관적으로 save를 부르자 merge의 복사 의미론이 새 자식에 적용됐고, 코드가 들고 있던 원본은 영속화되지 않았다.

**해결:** ① 트랜잭션 안에서 불러온 애그리거트는 save 없이 flush(또는 커밋)로 저장한다 — 변경 감지 + cascade PERSIST가 원본을 영속화한다. ② save를 써야 한다면 반환값을 영속 인스턴스로 쓴다. ③ 이 선택은 코드만 봐서는 이유가 안 보이므로 주석으로 남긴다.

## 이번 프로젝트 사례

- Kotlin·Spring Boot 3.5 실험 프로젝트에서 트랜잭션 스크립트를 DDD 애그리거트(좌석 루트가 홀드 자식을 소유)로 리팩토링하던 중 발생. 선점 유스케이스가 좌석을 불러와 홀드를 추가한 뒤 `saveAndFlush(좌석)`를 부르고 홀드 id를 응답에 담았는데, 홀드 id가 null이라 통합 테스트 10개가 NPE로 실패했다. `flush()`로 바꿔 전건 green으로 복구했다.
