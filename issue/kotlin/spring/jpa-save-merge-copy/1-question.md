# issue/kotlin/spring/jpa-save-merge-copy — 영속 애그리거트에 save()를 부르면 merge가 복사본을 영속화한다 — 질문

태그: `leaky-abstraction` · `identity-vs-copy`

## 질문

1. (왜) Spring Data의 `save(entity)`는 "이 객체를 저장해라"가 아니다. 실제로는 무엇을 판단해서 어떤 두 연산 중 하나를 고르는가?

2. (예측) 트랜잭션 안에서 불러온(이미 영속 상태인) 애그리거트 루트에 새 자식을 추가하고 `saveAndFlush(root)`를 불렀다. 루트의 id가 있으므로 어떤 연산이 실행되고, 방금 추가한 자식 객체의 id는 왜 여전히 null인가?

3. (경계) `persist`와 `merge`는 **객체의 정체성(identity)** 측면에서 어떻게 다른가? "내가 들고 있는 그 객체가 영속화되는가, 다른 객체가 영속화되는가"로 설명해 보라.

4. (연결) 이미 영속 상태인 엔티티는 애초에 `save()`가 필요한가? 변경 감지(dirty checking)와 cascade PERSIST가 flush 시점에 무엇을 해 주는가?

5. (경계) 새 자식의 id를 곧바로 응답에 써야 한다. 선택지 세 가지(flush만 호출 / save의 반환값에서 자식 찾기 / 자식을 자기 리포지토리로 직접 저장)를 애그리거트 설계 관점에서 비교하라.

6. (연결) 이 버그가 테스트에서 "id null → NPE"로 즉시 드러난 것은 운이 좋았던 경우다. 반환값을 쓰지 않고 id도 안 읽는 코드였다면 무엇이 조용히 어긋날 수 있나?
