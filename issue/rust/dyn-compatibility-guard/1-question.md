# issue/rust/dyn-compatibility-guard — dyn 호환성은 trait의 암묵적 계약이다: 깨지는 순간을 정의 옆에서 컴파일 에러로 만든다 — 질문

## 질문
1. (예측) 구현을 `Box<dyn Store>`로 바꿔 끼우려고 만든 trait `Store`에 `fn visit<F: Fn(u64)>(&self, f: F)` 같은 제네릭 메서드를 하나 추가했다. trait 정의 파일은 컴파일되는가? 에러는 언제·어디서 나는가.
2. (왜) 제네릭 메서드가 있으면 왜 `dyn Store`를 만들 수 없는가. vtable과 단형화(monomorphization)로 설명하라. 제네릭 메서드 말고 dyn 호환성을 깨는 다른 모양은 무엇이 있는가.
3. (경계) 프로젝트 안에 `dyn Store`를 쓰는 곳이 아직 없거나(다음 단계에서 만들 예정), 다른 모듈·다른 크레이트에만 있다면 이 깨짐은 언제 발견되는가. 제네릭 사용처(`fn run<T: Store>(t: &T)`)만 있으면 무엇이 일어나는가.
4. (설계) trait 정의 옆에 `const _: Option<&dyn Store> = None;` 한 줄을 둔다. 이 줄은 왜 런타임 비용이 0이고 구현체도 필요 없는가. 왜 이 줄이 dyn 호환성을 "단언"하는 효과를 내는가.
5. (검증) 이 가드가 실제로 동작하는지는 어떻게 확인하는가. 컴파일이 통과한다는 사실만으로 충분하지 않은 이유는?
6. (경계) 제네릭 메서드가 꼭 필요하면 dyn 호환성을 유지하면서 추가할 수 있는가 — `where Self: Sized`와 별도 확장 trait는 각각 무엇을 포기하는가.
