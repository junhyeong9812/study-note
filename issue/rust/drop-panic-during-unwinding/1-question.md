# issue/rust/drop-panic-during-unwinding — Drop 안의 패닉은 되감기 중이면 abort가 된다: 테스트 하나의 실패가 실행 전체를 지운다 — 질문

## 질문
1. (예측) 테스트 A는 `assert_eq!(1, 2)`로 패닉한다. 테스트 B는 `Drop`에서 패닉하는 값을 지역 변수로 든 채 `panic!`한다. `cargo test`로 둘을 같이 돌리면 각각 어떻게 끝나고, 나머지 테스트는 계속 도는가?
2. (왜) 패닉의 기본 동작인 되감기(unwinding)는 무엇을 하는가. `catch_unwind`는 무엇을 잡고 무엇을 못 잡는가. abort는 되감기와 무엇이 다른가?
3. (왜) 되감는 도중 `Drop` 안에서 두 번째 패닉이 나면 Rust는 왜 되감기를 계속하지 않고 프로세스를 abort하는가?
4. (경계) RAII 가드의 `Drop`이 장부(카운터)를 내리면서 `debug_assert!(count > 0)`로 불변식을 검사한다. 평소엔 좋은 검사인데, 어떤 상황에서 이 검사가 프로세스 전체를 죽이는 원인이 되는가?
5. (설계) 검사를 지우지 않고 `debug_assert!(count > 0 || std::thread::panicking())`로 바꿨다. 평소와 되감는 중에 각각 무엇이 달라지는가. 카운터 감소를 `-=` 대신 `saturating_sub`로 바꾼 이유는 debug·release 빌드에서 각각 무엇인가?
6. (검증) 이 결함은 어떻게 드러났나. "핀된 자원을 무시" 같은 변이를 넣었을 때 테스트가 assert 실패가 아니라 프로세스 abort로 끝난다면, 그것은 무엇의 신호인가?
