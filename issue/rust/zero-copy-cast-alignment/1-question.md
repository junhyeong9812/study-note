# issue/rust/zero-copy-cast-alignment — 바이트 버퍼를 구조체로 재해석하면 주소 정렬이 계약이 된다: 정렬 1인 버퍼는 주소 운에 따라 가끔만 실패한다 — 질문

## 질문
1. (예측) 16KB 바이트 배열 하나를 감싼 페이지 타입(정렬 1)을 `u64` 필드로 된 같은 크기 구조체로 제로 카피 캐스트한다. 버퍼 시작 주소가 0·1·8바이트 오프셋일 때 각각 어떻게 되는가. `try_` 계열과 그냥 캐스트 함수는 실패를 어떻게 다르게 드러내는가?
2. (왜) 캐스트 라이브러리는 크기는 물론 **주소 정렬**까지 런타임에 검사한다. 정렬이 안 맞는 `&u64`를 만들면 왜 안 되는가. 그리고 이 실패는 왜 "항상"이 아니라 "가끔" 일어나는가?
3. (설계) 정렬 문제를 없애는 두 방법 — 버퍼 타입 자체에 `#[repr(C, align(8))]`을 주기 vs 매번 정렬 무관 읽기(`pod_read_unaligned`)로 사본을 만들기 — 는 각각 무엇을 얻고 무엇을 잃는가?
4. (경계) `#[derive(Pod)]`는 무엇을 컴파일 타임에 막아 주는가(헤더 필드 하나를 `u64 → u32`로 바꾸면?). 반대로 derive가 막지 못해 따로 단언해야 하는 것은 무엇인가(구조체가 정확히 한 페이지 크기인지)?
5. (예측) `[u8; 16384]`를 감싼 타입에 `#[derive(Pod, Zeroable)]`을 붙였더니 E0277(`[u8; 16384]: Zeroable` 미구현)로 빌드가 깨졌다. `[u8; 4096]`이었다면 통과했다. 무엇이 다른가?
6. (검증) 정렬 의존 결함은 왜 보통의 테스트로 잡기 어려운가. 어떻게 하면 결정적으로 재현할 수 있는가?
