# issue/cross-cutting/reliability/silent-failure-vs-artifact — 정답

태그: `silent-failure`

## 정답

<!-- 질문 1:1 대응 -->

1. **성공 신호는 "됐다는 주장", 산출물은 "됐다면 남았을 흔적"이다.** 로그의 success·exit 0·HTTP 202는 전부 어떤 단계가 스스로 보고한 값이다 — 그 단계가 실패를 삼켰거나 성공/실패를 잘못 판정했으면 그 값은 거짓이 된다. 산출물은 작업 주체의 자기보고와 독립적으로 관찰되는 증거(저장된 레코드 수, 컨테이너의 실제 이미지, 응답하는 헬스 URL)라서, 신호를 믿는 대신 산출물을 되물으면 삼켜진 실패가 드러난다. 단 산출물의 **존재만으로는 완료가 증명되지 않는다** — 이전 실행이 남긴 옛 산출물, 개수는 같지만 내용이 틀린 레코드, 옛 버전이 내는 헬스 200도 통과하므로 "이번 작업·이 버전·이 내용"인지까지 확인해야 한다(4번).
   > **산출물(artifact)** — 작업이 실제로 완료됐다면 관찰 가능하게 남았어야 하는 결과물. 신호와 달리 작업 주체의 자기보고에 의존하지 않는다.

2. silent failure는 **실패가 발생했지만 그 실패가 호출자·상위 단계로 전파되지 못한** 상태다. "실패가 났다"는 정상(시끄럽게 알리면 됨)이고, 문제는 "실패가 신호에 반영되지 않는 것"이다. 흔한 원인 셋: (a) 예외를 의도적으로 삼키는 경로("실패해도 무해" 설계), (b) 성공과 실패를 구분 못 하는 호출(4xx/5xx를 성공으로 받는 `curl`), (c) 실패를 실패로 안 보는 관대한 도구(없는 산출물을 오류로 안 보는 빌드, 상태코드만 보는 healthcheck).
   > **silent failure(조용한 실패)** — 실패했는데도 성공 신호가 나가, 아무도 실패를 알아채지 못하는 사고 유형.

3. B가 실패를 삼키고 성공을 반환하면, C는 "B가 됐다"를 전제로 자기 일을 하거나 건너뛰고, 최종 success는 "A·B·C가 다 됐다"가 아니라 **"아무도 실패를 보고하지 않았다"** 만 의미하게 된다. 신뢰의 사슬은 가장 약한 고리(실패를 삼키는 단계)에서 끊기고, 그 뒤로 전달되는 성공 신호는 "전부 됐다"는 **보장을 잃는다**(우연히 결과가 맞을 수는 있지만 신호가 그걸 증명하지 못한다). 후속 단계가 앞 단계의 산출물을 스스로 재검증하거나 복구한다면 사슬은 거기서 다시 이어진다. 그래서 파이프라인의 "성공"은 각 단계가 **실패를 전파하거나, 뒤 단계가 재검증해야만** 의미가 있다.

4. 네 가지의 공통 구조는 **"주장을 무시하고 독립된 산출물을 되묻는다"** 이다. (a) 넣으려던 청크 수와 저장소가 실제로 가진 수를 비교, (b) 배포 로그 대신 `docker inspect`로 이미지·생성 시각, (c) 빌드 성공 메시지 대신 라우트 표를 grep, (d) exit 코드 대신 헬스 URL로 실제 요청. 넷 다 "그 일이 됐다면 X가 참이어야 한다"는 **사후 조건(postcondition)** 을 세우고 X를 직접 측정한다. 다만 각각 여전히 속을 수 있다 — (a) 개수는 맞지만 내용이 틀린 레코드, (b) 이미지 태그는 같지만 digest가 다른 경우, (c) 이전 빌드가 남긴 산출물 목록, (d) 옛 버전·다른 인스턴스가 내는 200. 그래서 사후 조건에는 **작업 ID·버전(digest)·내용(표본·체크섬)·완전성·관측 시점(작업 시작 이후인가)** 을 함께 넣는다.
   > **사후 조건(postcondition)** — 연산이 성공적으로 끝났다면 반드시 참이어야 하는 상태. 검증은 이것을 신호가 아니라 실측으로 확인한다.

5. 일반화: **"접수/기동/시작"을 알리는 신호를 "완료/정상/반영"으로 오해하지 마라.** 202는 서버가 요청을 처리 대상으로 **접수**했다는 뜻일 뿐이다 — 큐 적재나 영속 저장을 보장하지도 않고(HTTP 의미상 처리가 나중에 거부되거나 유실될 수 있다), 실제 처리는 뒤에서 일어나며 실패할 수 있다. `compose up -d`(분리 모드) 종료 0은 컨테이너를 생성·시작했다는 뜻이고, 그 안의 프로세스가 곧바로 크래시 루프에 빠져도 명령은 이미 성공으로 끝난다(헬스 대기가 필요하면 healthcheck + `--wait` 같은 별도 장치가 있어야 한다). 둘 다 **"명령을 접수한 시점의 신호"를 "결과가 확정된 시점의 신호"로 착각**하는 함정이다.

6. 검증 코드가 틀리면(예: 에러 상세를 넣으려던 문자열 템플릿을 잘못 써 진짜 에러가 리터럴로 가려짐) 실패는 나는데 원인이 안 보여 디버깅 비용이 배가 된다. 검증 도구가 관대하면(없는 라우트를 오류로 안 봄, 상태코드만 보는 healthcheck) **실패 자체가 초록불로 바뀐다.** "테스트 초록불인데 제품이 틀렸다"는, 검증 장치가 계약이 아니라 엉뚱한 것을 재고 있어 *검증이라는 산출물마저 거짓 성공 신호가 된* 특수한 silent failure다. 그래서 "테스트 통과 ≠ 검증 완료"이고, 검증기 자신도 실측으로 한 번 의심해야 한다(그린 위장 점검).

7. 데이터 작업은 "예외가 안 났다"가 "다 들어갔다"를 보장하지 않는다 — bulk 저장이 부분 실패해도 예외 없이 끝날 수 있고, 필터가 조용히 레코드를 스킵하거나 인코딩이 값을 절단해도 프로세스는 성공으로 끝난다. 그래서 record-level 검증이 필요하다: **count**(넣으려던 수 == 저장된 수), **sample**(표본을 되읽어 내용 확인), **orphan 검출·정리**(더 이상 소스에 없는데 저장소에 남은 것). 이것들은 부분 실패·조용한 스킵·조용한 절단을 명시적으로 반증하는 강력한 수단이지만 한계도 있다 — count는 개수만 보므로 같은 수의 틀린·중복 레코드를 놓치고, sample은 표본 밖 결함을 놓친다. 필요하면 키 단위 존재 대조·체크섬·필드별 존재 건수 전수 조사로 보강한다.
   > **record-level 검증** — 집계 성공 여부가 아니라 개별 레코드 수·내용·정합성을 실제로 세어 확인하는 것. 데이터 작업에서 흔한 사고 유형인 silent failure를 잡는 핵심 방어선.

8. 산출물 대조는 **"산출물이 생겼는지 되물을 수 있다"** 를 전제로 한다. 그 전제가 무너지는 곳에서는 대조에 더해 **관측 경로 자체를 만드는 것**이 방어다. 요청이 응답을 요구하지 않으면(fire-and-forget) 거절은 원리적으로 도착하지 않으므로 응답을 요구하게 바꾼다. 사후 관측으로 성공을 확인한다면 베이스라인을 부작용 **전에** 잡고, 관측된 사건을 요청 하나에만 귀속(claim)시켜야 남의 사건을 내 성공으로 오인하지 않는다. 종료 순간에 늦게 도착하는 신호는 수신 자격을 바로 폐기하면 무음 거절되므로 폐기를 유예하고 거절을 기록한다. 산출물을 만들지 말지 정하는 게이트가 산출기보다 좁으면 "파일이 아예 없음"이 생기는데, 이는 "있어야 할 산출물이 있는가"를 묻는 부재 검사 — 산출물 검증의 한 종류 — 로 잡고, 근본적으로는 게이트와 산출기를 동기화해 막는다(자세한 것은 아래 방안 비교).
   > **관측 가능성(observability) 경로** — 실패가 일어났을 때 그 사실이 누군가에게 도달하는 통로. 이 통로가 없으면 산출물 대조 이전에 실패가 존재하지 않는 것처럼 보인다.

## 문제 구조 (추상화 코드)

> 이 카드의 사건들은 모두 **"성공 신호가 산출물과 떨어진 지점"** 이 어디냐로 나뉜다.\
> 변형마다 대표 사건만 코드로 보이고, 같은 구조의 나머지는 한 줄씩 적는다.

```text
  요청 ──▶ [실행] ──▶ [결과 보고] ──▶ [완료 판정] ──▶ [상태 신호] ──▶ [검증기]
            │            │               │               │               │
            A 예외 삼킴  B 실패=빈 값    F 중간 흔적으로  G "떴음"만 봄   H 검증기 사각
            C 데이터 무음 탈락           완료 판정
            D 설정 누락→빈 정상 대체
                         E 전송 성공=업무 성공
```

### 변형 A — 삼켜진 예외·버려진 결과 채널

① 문제 코드 (병렬 워커의 예외가 어디에도 닿지 않음 — 원문은 증상만 기록, 코드는 흔한 원인의 재구성)
```java
for (Batch b : batches) {
    executor.submit(() -> bulkWrite(b));   // 반환된 Future를 버린다
}
// ... failed 카운트는 0 그대로 → 실패한 잡이 RUNNING으로 보인다
```
② 고친 방향 (원문은 "예외 보고·실패 카운트 필요"로만 기록 — 적용 여부 미확인)
```java
List<Future<?>> fs = new ArrayList<>();
for (Batch b : batches) fs.add(executor.submit(() -> bulkWrite(b)));
for (Future<?> f : fs) {
    try { f.get(); }
    catch (ExecutionException e) { failed++; log.warn("batch failed", e.getCause()); }
    catch (InterruptedException e) { Thread.currentThread().interrupt(); throw new IllegalStateException(e); }
}
```
무엇이 깨졌나: 스레드풀에 제출한 작업의 예외는 Future를 조회하지 않으면 전파되지 않는다.

① 문제 코드 (실패를 보고하는 유일한 채널의 수신단을 버림)
```rust
let (exec_rx, status_rx) = open_channels(target);
let _ = status_rx;              // 연결·인증 단계 실패는 이쪽으로만 온다
relay(exec_rx);                 // exec 이전 실패 = 이벤트 0개 → 빈 검은 화면
```
② 고친 코드
```rust
relay_status(status_rx);        // Failed/Closed를 기존 종료 경로로 전달
relay(exec_rx);
// 두 릴레이가 같은 끝을 볼 수 있으므로 표시는 먼저 도착한 사유 하나로 한다 — 이는 표시 정책일 뿐,
// 동시 채널에서 먼저 도착한 것이 근본 원인이라는 보장은 없으므로 나머지 사유도 로그에 보존한다
```
무엇이 깨졌나: "이벤트 0개"가 정상과 파국을 동시에 뜻하게 됐다.

같은 구조:
- 상태 파일 쓰기를 `|| true`로 삼키고 성공 메시지를 출력 → 그 상태에 기대는 보호가 조용히 꺼짐. 교정: 쓰기 실패 = 차단(fail-closed), 원자 교체.
- 비동기 `create_task`의 반환값을 버림 → 예외 유실·참조 미보존으로 GC·발행 실패 시 메시지 drop. 교정 계획: done 콜백으로 예외 로깅, 참조 집합 보관, 종료 시 대기.
- bare `except: return 기본값`·부분 실패 `continue` → 결과 수가 줄어든 이유를 호출자가 모름. 교정 계획: 구체 예외만, 실패 수를 응답에 반영.
- (상태, 에러)를 돌려주는 API에서 에러를 먼저 검사 → "에러와 함께 온 UNKNOWN 상태"가 소실되고 락이 풀림, 이력 기록 오류는 `_ =`로 버림. 교정: 상태 분기 우선, 기록 오류 전파.
- UNKNOWN 분기가 이른 return으로 오류 객체를 버리고, 영속 이력에 상세 칸 자체가 없음 → 원인이 어디에도 남지 않음. 교정: 상세 필드 추가·응답에 노출.
- "못 찾음"을 계약(예외) 대신 null로 반환 → 호출자 NPE → 넓은 catch가 삼켜 폴백, 로그엔 엉뚱한 원인. 교정: 원래 예외 재전파.
- 방어 파서의 malformed 줄 skip·목록 상한 절단·UI 드롭 거절·catch 삼킴 → "성공처럼 보이는 불완전 결과". 교정: skip 수를 산출물에 기록, 절단·거절을 화면에 노출.
- 출력 전용 원격 실행에 입력 EOF를 보내지 않음 → 원격이 입력을 영원히 대기, 종료 이벤트 미도착. 교정: 수락 즉시 EOF, 모든 종료 경로에서 dead 표시(Drop 가드).

### 변형 B — 실패와 "정상적으로 비어 있음"이 같은 값

① 문제 코드
```python
def collect():
    try:
        return container_stats()
    except Exception:
        return []            # 수집 실패 = "컨테이너 0개(정상)"와 구분 불가
```
② 고친 코드
```python
def collect():
    out = {"items": [], "errors": []}
    try:
        out["items"] = container_stats()
    except Exception as e:
        out["errors"].append(f"stats: {e}")
    return out
# 소비자: errors가 비어 있지 않으면 경보 / 폴링 연속 실패 카운터 → "agent unreachable" 경보
```
무엇이 깨졌나: "우아한 폴백"이 오류와 정상 빈 결과를 같은 값으로 표현했다.

같은 구조:
- 서비스 관리자에 존재하지 않는 유닛을 물어도 rc=0·기본 속성(`inactive`) 반환 → 오타 유닛이 "감시 중·정상". 교정: 로드 상태가 `loaded`가 아니면 오류.
- 공통 액션 래퍼가 실패에도 resolve → 커밋 실패인데 입력창이 지워짐, status 실패가 "변경 없음"으로 보임. 교정: 래퍼가 성공 여부를 반환, 성공일 때만 후속 처리.
- 조회 예외를 잡아 빈 리스트 반환 → 일부 배치에서 필드가 조용히 누락.
- 읽을 수 없는 루트·파일인 루트를 빈 목록으로 처리. 교정: 오류로 노출.
- 스크립트에 `set -e`가 없어 중간 실패에도 마지막 명령의 rc(0)로 종료 → 일일 배치가 수일간 성공으로 기록.

### 변형 C — 데이터가 오류 없이 빠지는 경로 (필터·키 조회·투영·파서·배선)

① 문제 코드 (형식 필터가 새 형식을 조용한 탈락)
```sql
SELECT ... FROM rows
WHERE term REGEXP '^[0-9]{6}([0-9]{2})?$'   -- 새로 들어온 ISO 타임스탬프 행은 전량 탈락
```
② 고친 코드
```java
String year = normalizer.normalize(row.term());   // 정규화를 코드 한 곳(단일 출처)으로
if (year == null) { droppedByYear++; continue; }
// ...
if (droppedByYear > 0) log.warn("집계 제외 행 {}", droppedByYear);   // 탈락을 보이게
// SQL 쪽 NULL 필터는 제거 — 두 곳에 나누면 카운터가 일부 경로를 못 본다
```
무엇이 깨졌나: 통제되지 않는 입력 형식에 필터를 걸어, 새 형식 데이터가 집계에서 오류 없이 사라졌다.

① 문제 코드 (생산자가 필드를 분리했는데 소비자는 옛 키 조회)
```java
List<String> desc = (List<String>) row.get("desc_text");   // 더 이상 방출되지 않음 → 항상 null
```
② 고친 코드
```java
List<String> desc = firstNonEmpty(row.get("desc_" + nativeLang),   // 원어 우선
                                  row.get("desc_en"),               // 영어 폴백
                                  List.of());
```
무엇이 깨졌나: 스키마 없는 Map 조회는 키가 사라져도 컴파일·런타임 오류 없이 null을 준다.

같은 구조:
- projection 허용목록에 새 필드를 넣지 않음 → 응답에서 필드가 조용히 빠짐(폴백이 누락을 더 가림).
- 같은 테이블의 단건/배치 SELECT 컬럼 목록이 불일치 → 배치 경로 문서만 해당 필드 영구 null. 명시 스키마가 모르는 키를 변환 때 버림.
- 파싱 실패를 null로 돌려주는 변환 → 파티션 키가 null이 되어 기본 파티션으로 무음 적재. 교정: 생산자가 실제 보내는 형식(Unix 시각)에 맞춤.
- 언어 코드 정확 일치 필터 → 원천이 비표준 코드로 분류한 언어가 전량 탈락해 헤더만 있는 산출물. 교정: 코드 정규화 매핑을 두 입력 칸 모두에 적용.
- 계산한 값을 와이어에 싣지 않음 + 수신 측 타입에 칸 없음 → "기능 없음"과 "배선 안 됨"이 화면에서 동일.
- 요청 파라미터의 존재만 검증하고 작업 함수에 전달하지 않음 → 증분 대신 전량 재처리 시작. 모듈을 만들었지만 호출 경로에 연결 안 함.
- 비어 있지 않음 검사를 원시 출력에 하고, 이후 분리 변환 결과가 비게 됨 → 빈 산출물 저장. 교정: 최종 산출물 기준 재검사·폴백.
- 구조화 출력 스키마는 통과했지만 내용이 엉뚱함(식별자 자리에 다른 값) → 식별자·필드 수·완비 여부를 결정론적으로 따로 검사. 퍼지 보정은 원값→보정값을 영속 기록.
- 인덱싱 시점에 마스터 조인이 빠져 파생 검색 필드가 비었는데 적재는 에러 없이 끝남 → 필드별 존재 건수 전수 조사로만 발견.

### 변형 D — 설정 누락·오타가 "비어 있는 정상"으로 대체

① 문제 코드
```yaml
services:
  app:
    volumes:
      - ${DATA_DIR}:/data        # 값에 오타 → 호스트에 빈 디렉토리가 자동 생성되어 마운트(rootful 데몬이면 root 소유)
# 로그: "Initialization complete ... ready=[]"  (에러 없음)
```
② 고친 코드
```sh
DATA_DIR=/srv/data/embeddings_x      # 실제 존재하는 경로로 정정
# 판별 단서: 빈 디렉토리의 생성 시각 == 컨테이너 기동 시각 → 자동 생성된 빈 마운트
```
무엇이 깨졌나: Docker의 단축 bind 문법(`host:container`)은 없는 호스트 경로를 오류 대신 빈 디렉토리로 만든다(`--mount type=bind`처럼 없으면 오류를 내는 문법도 있다 — 엔진·문법별로 다름).

① 문제 코드
```yaml
volumes:
  data: { ... }                        # 최상위 정의만 있고
services:
  db:
    volumes: ["${DB_DIR}:/var/lib/db"]  # 정의된 볼륨을 참조하지 않음 → 빈 경로로 신규 초기화
```
② 고친 코드
```text
DB_DIR = 기존 named volume의 실경로로 정정 → 재생성 → 행 수 표본 대조(record-level)
빈 초기화본은 삭제하지 않고 보존
```
무엇이 깨졌나: 최상위 선언은 서비스가 참조해야만 마운트되고, "기존 상태"를 재배포 **후** 컨테이너 기준으로 측정해 비교 기준 자체가 오염됐다.

같은 구조:
- 배포 매니페스트에 DB 접속 환경변수 누락 → 앱이 DB 없이 조용히 기동(DB 초기화 로그 부재·미저장으로만 드러남). 교정: 파드의 실제 env 확인 후 추가.
- 운영 서버의 소스 갱신(pull)이 untracked 파일 충돌로 거부된 채 방치 → 옛 빌드 정의로 이미지 생성, 플러그인 미설치. 교정: 갱신 정상화 → 재빌드 단계 실행 여부·이미지 해시 → 플러그인 목록 확인.

### 변형 E — 전송·호출 성공을 업무 성공으로 기록

① 문제 코드
```python
resp = http.post(callback_url, body)      # 401/500도 예외가 아니다
history.add(status="success", duration=resp.elapsed)   # 왕복 시간만 재고 성공 기록
```
② 고친 코드
```python
resp = post_with_backoff(callback_url, body, retries=3)   # 재시도는 수신 측이 멱등(요청 ID 중복 제거)일 때만 안전
if not (200 <= resp.status < 300):
    raise DeliveryFailed(resp.status)
if not resp.json().get("requestId"):       # 2xx여도 필수 응답 필드가 없으면 실패
    raise DeliveryFailed("no requestId")
```
무엇이 깨졌나: 전송 계층 성공(예외 없음·2xx)은 업무 성공의 필요조건일 뿐이다.

① 문제 코드 (fire-and-forget 트리거를 성공으로 기록)
```python
prepare(country); sleep(5); start(country)          # start는 필수 파라미터 누락으로 매일 422
add_history(country, "success", duration=roundtrip)  # relay가 4xx를 success 봉투로 감쌈
```
② 고친 코드
```python
entry = add_history(country, "in_progress")
# 완료 이벤트 수신 시 실제 processed/success/failed로 같은 엔트리를 확정
# watchdog 3시간 / 대상 0건은 "no_data" / HTTP>=400은 failed 명시
```
무엇이 깨졌나: 트리거의 왕복을 작업 완료로 간주해, 오류가 봉투 안에서 사라졌다.

같은 구조:
- 배포 호출에 `curl`의 `-f`가 없어 401 거절이 성공으로 위장 → 운영 실값·배포 이력·http 코드로 원인을 좁힘. (`-f`도 인증이 얽힌 401/407에서는 빠져나갈 수 있다고 curl 문서가 밝히므로, 상태 코드를 `-w '%{http_code}'`로 직접 확인하는 편이 확실하다.)
- 202(처리 접수일 뿐 완료·적재 보장 아님)를 배포 완료로 오해해 조용한 유실 → 접수 시점에 진행 중인 대상은 409로 거절.
- 원격 명령 캡처가 "빈 stdout"만 실패로 봄 → `{"response":"error"}` 같은 비어 있지 않은 에러 본문이 Ok로 도착. 교정: 응답을 파싱해 에러를 실패로.
- 원격이 "없음"을 오류 대신 짧은 텍스트 본문으로 돌려줌 → 다운로드는 성공, 확장자만 맞는 쓰레기 파일이 남음.
- 죽은 세션·미연결 핸들에 대한 호출·쓰기·close가 Ok 반환 → 대상 생존·모드 검사를 먼저, 하위 실패 전파, 종료 시 레지스트리에서 제거.
- 결과 보고가 실제 결과가 아니라 요청값을 메아리(요청 신호를 실제 전달 신호처럼 보고), 여러 결과를 한 값으로 뭉뚱그림 → (생존 × 기록 존재) 조합별로 분리 보고.
- 리팩터링이 "등록 완료" 안내를 결과 판정 분기 밖으로 끌어올림 → 실패 경로에서도 성공 안내.

### 변형 F — 완료 판정을 중간 흔적으로 (폴더·마커·처리 로그·워터마크)

① 문제 코드
```rust
for s in sessions {
    if archive_dir_exists(&s) { skip(s); continue; }   // 폴더 = 중간 산출물
    match extract(&s) { _ => ok += 1 }                  // 추출 실패도 ok로 집계
}
```
② 고친 코드
```rust
for s in listing.sessions {
    if s.summary_path.is_some() { complete.insert(s.id); }   // 최종 산출물 존재 = 완료
    else { partial.insert(s.id); }                           // 재추출 후보 → 재실행이 자동 복구
}
// 결과 4분류 집계(ok / 부분 / skip / fail), 추출 1회 재시도
```
무엇이 깨졌나: 멱등 재실행의 skip 조건이 중간 산출물이라, 부분 실패가 영구히 "완료"로 고착됐다.

① 문제 코드 (재시도 대상 = 워커가 append한 실패 로그)
```python
retry_ids = read_lines("failed.txt")      # 4건 — 실제 누락은 수백만 건
process(retry_ids, skip_already_processed=True)   # "처리됨" 필터가 진짜 누락도 가린다
```
② 고친 코드
```python
missing, unknown = [], []
for batch in chunks(source_ids, 10_000):
    try:
        docs = store.mget(ids=batch, source=False)          # 본문 없이 존재 여부만
        missing += [d.id for d in docs if not d.found]
    except Exception:
        unknown += batch                                    # 조회 실패 ≠ 부재 — 확인 불능으로 따로 모음
# unknown은 조회를 재시도해 missing/존재로 확정한 뒤 합친다.
# (재적재로 몰아넣는다면 문서 id 기반 멱등 쓰기·버전 조건부 쓰기가 전제 — 아니면 최신 값 덮어쓰기·중복 부작용)
reindex(missing, rebuild_all=True)                            # 처리됨 필터 무시
```
무엇이 깨졌나: 처리 흔적 파일은 저장소의 실제 상태와 동기화되지 않는다(bulk 200 ≠ 색인 보장) — 성공의 진실 원천은 최종 저장소다.

같은 구조:
- 완료를 "산출물 일부 존재"로 판정 → 모든 단계 성공 뒤에만 쓰는 명시 완료 마커로. 의도적 생략도 별도 명시 마커(오류 반환으로 흉내 내면 영구 "부분 실패"로 오분류).
- 진행 마커 파일을 DB 밖에 둠 → DB만 초기화하자 마커가 남아 전 테이블 SKIP, 로그는 "import all done". 교정: 마커 삭제 후 재적재, DB 카운트 ↔ 원천 행수 이중 대조.
- bulk API는 문서 단위로 성공/실패 → 배치 단위 성공 판정은 누락을 숨기고, 예외 시 배치 전체를 failed로 적으면 과대 계상. 교정: 실패 목록 대신 저장소 존재 대조로 missing 생성.
- 저장소 디스크가 가득 차 쓰기 거부(읽기 전용 전환·마스터 상실) → 적재 잡은 DONE, 문서는 대량 누락(원문은 원인 관측만 — 잡이 항목별 실패를 반영하지 못한 것으로 추정).
- 워터마크·커서가 실패 포함 배치에서도 전진 → 미처리 행 영구 스킵. 결정적 실패 한 행은 "실패 0일 때만 전진"하는 워터마크를 영구히 붙잡음. 멱등 키에 식별 축이 빠져 다른 출처의 같은 id를 중복으로 오인.
- 재개 로직이 "파일 존재"를 완료로 봄 → 깨진 부분 파일이 성공으로 간주되어 재실행에서 스킵. 교정: 깨진 파일 정리 후 재다운로드.
- 재빌드 뒤 "현재 객체의 출처 경로"를 갱신하지 않음 → 다음 교체 실패 시 옛 원본이 무음 복원, 개수는 같아 품질만 저하. 교정: 쓰기 성공 시 경로 갱신, 실패 시 None.
- 대상 목록을 먼저 파일로 떨군 뒤 그 목록으로 적재 → 그 사이 원천에 추가된 행이 제외, 원본 distinct 수와 인덱스 문서 수 대조로 발견.
- bulk 색인 뒤 (검색 엔진이 near-real-time이면 refresh 후) `count == 넣으려던 청크 수`를 되물어 "돌았다"가 아니라 "들어갔다"를 검증.

### 변형 G — 상태 신호가 "떴음"만 보고 "무엇이 떴나·일하나"를 안 봄

① 문제 코드
```yaml
healthcheck:
  test: ["CMD", "python", "-c", "d = get('/health'); exit(0 if d['loaded'] else 1)"]   # 객체가 메모리에 있음만
```
② 고친 코드
```yaml
healthcheck:
  test: ["CMD-SHELL", "python -c \"r = get('/health/deep', timeout=20); r.raise_for_status(); exit(0 if r.json().get('ok') else 1)\" || exit 1"]    # 실제 추론 1건 — HTTP 오류·실패 본문도 비정상 종료
  interval: 60s
# 배치와 경합 시 거짓 unhealthy 방지: 처리 중 카운터가 있으면 busy:true 반환
# 단 busy를 무조건 healthy로 보면 교착·무한 처리도 healthy로 숨는다 →
# 마지막 진행 시각·최대 처리 시간을 넘긴 busy는 unhealthy로, readiness는 별도 기준으로 판정
```
무엇이 깨졌나: 프로세스는 살아 있고 기능은 죽은 상태를 구분하지 못해, 장애가 수일간 healthy로 보였다.

① 문제 코드
```text
pull → up → health.Check → COMPLETED        # 헬스는 "무엇이 떴나"(이미지 정체)를 안 본다
```
② 고친 코드
```text
pull → up → 이미지 digest 검증(대상 서비스만, 전부 일치, 매치 0 = 오류) → 헬스 검사 → COMPLETED
각 실패 → cleanup(down 성공 = UNEXECUTED / down 실패 = UNKNOWN)
```
무엇이 깨졌나: 생존형 헬스는 산출물의 정체·완전성을 보지 않고, 방어선의 전제 설정이 없을 때 "생략"으로 떨어지면 조용히 통과한다.

같은 구조:
- 컨테이너 기동 명령 종료 0 ≠ 서비스 정상 → 배포 후 헬스 URL을 최대 90초 폴링해 200을 받아야 ok.
- pull 래퍼가 수백 ms 만에 "deploy ok"를 찍었지만 `image:`+`build:` 병존으로 실제로는 Skipped → 컨테이너의 실제 이미지·생성 시각으로 확인.
- 모델이 없는데 `/health`가 200(본문만 missing) → 부재를 503으로 바꿔 "정상인 척" 차단. 헬스 스크립트가 `HTTP/` 문자열만 grep해 500도 healthy → 기대 상태 줄을 정확 일치로.
- 의존성 장애를 503으로 분류하지 않고 `/health`는 늘 200 → liveness와 readiness(의존성 ping)를 분리.
- 구버전 정지 명령 rc=0 ≠ 컨테이너 사라짐, "배포완료"를 정지 확인 전에 보고 → 실제 부재 관측 후 보고, 잔존 시 경고+실패 이벤트(위장 금지).
- 프록시 설정 파일은 "의도"일 뿐 → 쓰기→문법 검사→reload→worker 세대교체 확인→연속 3회 새 upstream 응답까지 관측, 중간 실패는 이전 설정으로 원복.
- 검증 대상을 배포 서비스로 한정하지 않고 "≥1 컨테이너 일치면 통과" → 무관한 컨테이너가 판정을 대신하고 혼합 replica가 완료로 위장. 교정: 서비스 라벨 필터 + 전부 일치.

산출물이 "아예 없음"으로 실패하는 경로는 존재만 확인하는 느슨한 검사로는 놓치기 쉬우므로, "있어야 할 산출물이 있는가"를 묻는 부재 검사(산출물 검증의 한 형태)를 두고 게이트와 산출기를 함께 바꿔 막는다(4).

## 방안 비교 — 기동 실패를 넘긴 측정이 이전 실행의 대상을 잰다

같은 원리(변형 G — "떴음"이 "무엇이 떴나"를 보장하지 않는다)가 **회차마다 컨테이너를 새로 띄우는 측정 배치**에서 나타난 사례.\
회차는 `down → up → 헬스 대기 → 측정` 순서였고, 앱 2대 조건은 기본 compose 파일 위에 오버레이 파일을 겹쳐 띄웠다.\
오버레이의 `extends`에 `file:`이 없어 compose가 **오버레이 파일 안에서** 원본 서비스를 찾았고(그 안의 서비스 정의는 포트 재설정뿐), `service "app2" has neither an image nor a build context specified: invalid compose project`로 **프로젝트 전체가 무효**가 됐다 — `up`만이 아니라 `down`도 매 회차 실패했다.\
하네스는 `up`의 실패를 넘겼고, 헬스 검사는 **이전 회차(다른 조건)의 컨테이너**에서 UP을 받아 그 앱을 측정했다. `down` 실패로 볼륨도 지워지지 않아 다음 조건의 결과까지 무효가 됐다.\
드러난 것은 우연이었다 — 실행 중 설정을 수집하는 단계가 오버레이에만 있는 컨테이너를 찾지 못해 실패했다(`no such object`).

```text
회차 n  (조건 X):  down ✓  up ✓  health UP  측정 → X의 앱
회차 n+1(조건 Y):  down ✗  up ✗(무시)  health UP ← X의 컨테이너가 그대로  측정 → "Y의 결과"로 기록된 X의 앱
```

### 방안 1 — 기동 명령의 실패를 회차 실패로 (이 사례에서 적용)
```bash
compose_down "$SHA" >> "$dir/compose.log" 2>&1
if ! compose_up "$SHA" $cfg_env >> "$dir/compose.log" 2>&1; then
  finish_rep "$dir" ... "compose-up-failed"; return 1      # 넘기면 이전 회차의 컨테이너를 잰다
fi
wait_health 180 || { finish_rep "$dir" ... "unhealthy"; return 1; }
```
```yaml
app2:
  extends:
    file: base.yml          # 명시 — 없으면 이 오버레이 파일 안에서 찾는다
    service: app
```

### 방안 2 — 떠 있는 것의 정체를 기대값과 대조 (이 사례에 이미 있던 층)
```bash
app_config "$dir"           # 실행 중인 앱에서 적용된 설정·풀 크기·DB 인덱스·컨테이너 목록 수집
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 기동 rc를 치명으로 | 기동 명령이 실패를 종료 코드로 알린다 | 한 줄 | rc 0인데 일부 서비스만 뜬 경우·rc를 삼키는 래퍼는 못 잡는다 | 모든 "띄우고 쓰는" 단계 — 가장 먼저 둘 층 |
| 2. 정체 대조(설정·버전·컨테이너) | 실행 중인 대상에서 정체를 조회할 수 있다, 조건마다 기대값이 다르다 | 수집·대조 코드, 조건별 기대값 관리 | 이전 대상이 **같은 기대값**을 가지면(같은 조건의 재시도 등) 통과한다 — 이 사례도 수집 단계가 다른 이유로 실패해서 걸렸다(추론: 같은 설정이었다면 통과) | 조건이 회차마다 바뀌는 측정·배포 검증 |

**결론**: 기동 실패는 **실패 그 자리에서** 끊는 것이 가장 싸고 확실하다(1) — 넘기는 순간 헬스 검사는 "무언가 살아 있음"만 확인하므로 이전 실행의 대상이 그 자리를 채운다.\
정체 대조(2)는 1을 대신하지 못하고, rc가 거짓말하는 경우를 잡는 **두 번째 층**이다 — 회차 고유값(실행 ID·생성 시각)을 정체에 넣어야 "같은 조건의 옛 대상"까지 가른다.\
정리 명령(`down`)도 같은 프로젝트 로드를 거치므로, 파일 오류는 기동과 정리를 **함께** 망가뜨린다는 점을 같이 기억한다(→ [compose-variable-resolution-timing](../../infra/compose-variable-resolution-timing/)).\

## 방안 비교 — 정리 실패를 넘긴 생성 단계가 이전 실행의 산출물 위에 쌓인다

같은 원리(1번 — 산출물의 **존재만으로는** 이번 작업의 완료가 증명되지 않는다)가 **리뷰 입력 묶음을 만드는 셸 체인**에서 나타난 사례.\
리뷰마다 정해진 이름 규칙의 작업 디렉토리에 저장소 사본과 입력 묶음(검토할 diff·명세)을 만들고, 리뷰어가 고치지 못하게 사본 전체를 읽기 전용(`chmod -R a-w`)으로 바꾼 뒤 리뷰어 둘에게 넘겼다.\
이번에 고른 디렉토리 이름은 이전 세션이 이미 쓴 것이었고, 그 디렉토리는 읽기 전용 사본과 다른 작업의 입력 묶음(명세·패치)을 그대로 갖고 있었다.\
생성 명령은 `rm -rf` → `mkdir -p` → 복사 → `git diff > 묶음/diff` …를 `;`와 줄바꿈으로 이은 체인(errexit 없음)이었고, 백그라운드로 돌리면서 리뷰어를 곧바로 띄웠다.\
`rm -rf`는 "허가 거부"로 실패했다 — 디렉토리 안의 항목을 지우려면 그 **디렉토리**에 쓰기 권한이 있어야 한다(일반론).\
`mkdir -p`는 이미 있어서 성공했고, 뒤의 복사·리다이렉트도 읽기 전용 디렉토리에 쓰지 못해 실패했지만 체인은 끝까지 갔다.\
한 리뷰어에게 준 준비 완료 조건은 "묶음에 명세 파일이 있으면 시작"이었는데, **이전 작업의 명세 파일**이 이미 있어 조건이 바로 참이 됐다.\
다른 리뷰어가 "기대한 diff 파일이 묶음에 없다"며 판정을 보류해 드러났고, 그 회차 결과는 버리고 새 디렉토리에서 다시 만들었다.

```text
rm -rf OUT        ✗ 허가 거부 (읽기 전용 트리)   ─┐
mkdir -p OUT/pkt  ✓ (이미 있음)                    │ ; 로 이어져 계속 진행
복사 → OUT        ✗ 쓰기 불가                       │
diff > OUT/pkt/x  ✗ 쓰기 불가                      ─┘
리뷰어 A: "pkt/spec 있음 → 준비 완료"  ← 이전 작업의 spec
리뷰어 B: "pkt/x 없음 → 판정 보류"    ← 여기서 드러남
```

### 방안 1 — 새 경로 + 단계별 실패 표시 (이 사례에서 적용)
```sh
OUT=$WORK/review-$NEW_ID
[ -e "$OUT" ] && echo EXISTS                      # 사례: 표시만 — 일반형은 여기서 중단(exit 1)
mkdir -p "$OUT/pkt"
copy_tree "$OUT" || echo COPYFAIL
make_diff > "$OUT/pkt/x" && cp spec "$OUT/pkt/spec" && ... || echo PKTFAIL
chmod -R a-w "$OUT"; ls -la "$OUT/pkt"            # 만든 것을 눈으로 대조한 뒤 리뷰어를 띄운다
```

### 방안 2 — 읽기 전용으로 만든 트리는 쓰기 권한을 되돌린 뒤 지운다 (같은 흐름의 다른 정리에서 쓰던 형태)
```sh
chmod -R u+w "$OLD" && rm -rf "$OLD"              # && — 권한 복구가 실패하면 지우지 않고 멈춘다
```

### 방안 3 — 소비자 쪽에서 기대 산출물을 대조 (이 사례에서 실제로 잡은 층)
```sh
# 리뷰어: 받기로 한 파일 목록이 전부 있는지 먼저 확인, 없으면 판정하지 않는다
for f in x spec contract; do [ -s "pkt/$f" ] || { echo "missing pkt/$f — 판정 보류"; exit 1; }; done
# 준비 완료 표지는 이번 생성에서만 생기는 것이어야 한다(일반 원리)
[ "$(cat pkt/RUN_ID 2>/dev/null)" = "$NEW_ID" ] || exit 1
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 새 경로 + 단계별 표시 | 경로 이름을 매번 새로 고를 수 있다 | 줄마다 `\|\| echo FAIL` | 표시를 출력만 하고 멈추지 않으면, 출력을 읽기 전에 소비자가 출발한 경우 여전히 샌다 | 사본·묶음을 반복해서 만드는 작업 |
| 2. 권한 복구 후 삭제 | 정리하는 쪽이 그 트리의 소유자다 | 한 줄 | `rm` 단독은 rc만 남기고 체인이 계속된다 | 일부러 읽기 전용으로 만든 산출물을 다시 쓰는 경로 |
| 3. 소비자 대조 | 소비자가 기대 목록을 안다 | 확인 코드 | 표지가 "파일 있음"뿐이면 옛 산출물이 통과한다(이 사례의 리뷰어 A) | 생성과 소비가 다른 주체·비동기일 때 |

**결론**: 생성 쪽은 실패 그 자리에서 멈추는 것(1을 표시가 아니라 중단으로)이 가장 싸다 — 넘기면 이전 실행이 남긴 파일이 빈자리를 채운다.\
소비 쪽 대조(3)는 생성 쪽이 놓친 것을 잡는 두 번째 층이고, "있음"이 아니라 **이번 생성의 표지**(실행 ID)를 봐야 옛 산출물을 가른다.\
같은 체인의 rc 문제는 [exit-status-semantics](../../../shell/exit-status-semantics/) 변형 B(순차 명령의 rc = 마지막 명령)와 같다 — 그 카드의 단계별 rc 처방이 그대로 적용된다.

검증 기록: 2026-10-15 사건 기록·실행 기록 대조·추상화(Claude 초안) — 방안 3의 실행 ID 표지와 방안 1의 중단형은 일반 원리(사례는 표시 출력 + 새 경로로 재생성).

## 방안 비교 — 실패를 스스로 재시도하는 실행기를 종료 코드로만 감시하면, 확정 실패의 반복이 "진행 중"으로 보인다

같은 원리(1번 — 종료 코드는 산출물이 아니다)가 **장시간 측정을 기다리는 감시 스크립트**에서 나타난 사례.\
측정 실행기는 회차가 끝 검사에서 실패하면 그 회차를 **자동으로 다시 측정**하고, 모든 회차가 끝나야 종료한다.\
감시 스크립트는 실행기가 0이 아닌 코드로 끝나는지만 봤다.\
30분 회차가 매번 같은 사유(끝 정합성 검사 쿼리의 임시 파일이 저장 공간을 넘침 — [temp-spill-on-bounded-storage](../../database/temp-spill-on-bounded-storage/))로 실패했고, 실행기는 재측정을 4번 연달아 시작했다.\
실행기는 실패로 끝난 것이 아니라 "아직 끝나지 않은" 상태였으므로 감시는 약 4시간 동안 침묵했다 — 사람이 실행 기록을 열어서야 드러났고, 확정적 실패라 다섯 번째 회차 도중 멈췄다.

```text
실행기:  회차 ─✗(사유 S)─▶ 재측정 ─✗(S)─▶ 재측정 ─✗(S)─▶ 재측정 ─✗(S)─▶ 재측정 …   (프로세스 생존, 종료 코드 없음)
감시:    while alive: sleep        on exit: rc != 0 → 알림
         └──────────── 끝나지 않으니 계속 "정상 진행 중" ────────────┘
```

### 방안 1 — 종료 코드만 본다 (문제 코드)
```sh
wait_for_exit "$RUNNER_PID"; rc=$?
[ "$rc" -ne 0 ] && notify "실행 실패 rc=$rc"      # 재시도를 품은 실행기는 "결국 끝났나"만 말한다
```

### 방안 2 — 시도 단위의 실패 신호도 감시한다 (이 사례에서 적용)
```sh
tail -n0 -F "$RUN_LOG" | while IFS= read -r line; do
  case "$line" in
    *re-measure*|*FAIL*) notify "회차 실패 → 재시도: $line" ;;   # 재시도 시작 = 실패 1건
  esac
done &
wait_for_exit "$RUNNER_PID"; rc=$?
[ "$rc" -ne 0 ] && notify "실행 실패 rc=$rc"
```

### 방안 3 — 같은 사유가 반복되면 실행기가 스스로 멈춘다 (일반 원리 — 이 사례에서 적용하지 않음)
```sh
# 회차 실패 처리 안
if [ "$reason" = "$last_reason" ]; then streak=$((streak + 1)); else streak=1; fi
last_reason=$reason
[ "$streak" -ge 2 ] && { mark_campaign_failed "same-reason:$reason"; exit 1; }   # 확정 실패는 재시도로 안 풀린다
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 종료 코드만 | 실행기가 실패하면 곧 끝난다 | 없음 | 내부 재시도·무한 대기 중에는 아무것도 알리지 않는다 — 실패가 "오래 걸림"으로 둔갑 | 재시도 없는 한 번짜리 명령 |
| 2. 시도 단위 신호 감시 | 실행기가 시도마다 실패 사유를 기록한다, 감시가 그 형식을 안다 | 로그 추적 한 갈래 | 사유 줄의 형식이 바뀌면 조용히 놓친다 — 형식을 실행기와 함께 고정·시험해야 함 | 사람이 기다리는 장시간 작업 |
| 3. 같은 사유 반복 시 중단 | 실패 사유를 비교 가능한 값으로 남긴다 | 사유 비교 몇 줄 | 일시적 실패가 우연히 두 번 겹치면 멈춘다 — 사유별로 재시도 가능 여부를 나눠야 함 | 재시도로 풀리지 않는 실패(공간·설정·데이터)가 섞일 수 있을 때 |

**결론**: 재시도를 품은 실행기의 종료 코드는 "결국 성공했나"만 말한다 — 기다리는 쪽은 **시도 단위의 실패 신호**(재시도 시작·실패 사유)를 함께 봐야 한다(2).\
근본 처방은 실행기 쪽이다 — 같은 사유가 되풀이되면 확정 실패로 끊는다(3, → [retry-policy-design](../retry-policy-design/)의 "영구 실패를 재시도하면 무한 루프").\
2는 사람의 시간을, 3은 실행기의 시간을 지킨다 — 둘 다 없으면 확정 실패가 회차 길이 × 재시도 수만큼 조용히 시간을 먹는다.\
검증 기록: 2026-10-17 사건 기록 대조·추상화(Claude 초안) — "약 4시간"은 기록된 시각(앞 캠페인 끝 → 수동 정지)으로 계산한 값, 방안 3은 일반 원리(사례는 감시 쪽 2만 적용).

## 방안 비교 — 비동기 접수(202) 뒤의 완료: 호출자는 무엇을 기다려야 하나

변형 E의 "202를 배포 완료로 오해"가 **호출자 쪽**에서 다시 나타난 사례.\
CI 워크플로는 배포 관리 서버에 "이 커밋을 배포하라"를 한 번 보내고 끝났다.\
호출은 `curl -sS ... -w "http:%{http_code}"`로 상태 코드를 **출력만** 했다 — `-f`가 없는 curl은 4xx/5xx에도 종료 코드 0이다.\
엣지 프록시가 집 쪽 서버 연결에 실패해 504를 돌려줬는데 워크플로는 초록불로 끝났다(같은 모양의 기록이 이전에도 한 번 있었다).\
진단 순서: 워크플로 로그의 `http:504` → 배포 관리 서버 이력에 그 요청 없음 → 운영 서버의 소스 커밋·컨테이너 이미지가 이전 것 그대로 → 엣지 오류 로그 같은 시각에 upstream connect 시간 초과.\
게다가 504를 잡아도 절반이다 — 이 서버는 202(접수)를 즉시 돌려주고 테스트·빌드·교체를 뒤에서 하므로, 202만 보는 호출자는 그 뒤의 실패를 모른다.

```
[전]  CI ── POST 배포 ──▶ 엣지 ──✕ connect 시간 초과
      CI ◀── 504 ─────── 엣지
      curl 종료 0 ─▶ 초록불            ← 배포는 일어나지 않았다

[전'] CI ── POST 배포 ─────────────────▶ 관리 서버: 기록 → 202 accepted
      202 ─▶ 초록불                      └─ 뒤에서: 테스트·빌드 ─✕ 실패   ← 호출자는 모른다

[후]  CI ── POST(요청 번호) ─▶ 504·연결 실패면 상한 있는 재시도, 409면 대기
         ── GET /deploys/<요청 번호> 반복 ─▶ accepted → integrating → delivering → succeeded | failed(단계)
         succeeded + 배포된 커밋 == 요청 커밋 일 때만 초록불
```

### 방안 1 — 상태 코드를 출력만 한다 (문제 코드)
```sh
curl -sS -X POST "$DEPLOY_URL" -d "$body" -w "\nhttp:%{http_code}\n"
# 504·401 이어도 curl 종료 코드 0 → 단계 성공 → 초록불
```

### 방안 2 — 접수 응답 코드를 판정한다
```sh
code=$(curl -sS -o resp.json -w '%{http_code}' -X POST "$DEPLOY_URL" -d "$body") || true
[ "${code:0:1}" = "2" ] || exit 1     # 504 는 빨간불이 된다 — 202 뒤의 실패는 여전히 못 본다
```

### 방안 3 — 요청 번호로 멱등 접수 + 종단 상태까지 조회 (이 사례에서 적용)
```sh
REQUEST_ID="run-$RUN_ID-$RUN_ATTEMPT"     # 같은 실행의 재전송 = 같은 번호, 수동 재실행 = 새 번호
# 접수: 2xx 수락 · 409(같은 대상 배포 중) 대기 · 그 외(504·연결 실패 등) 5회까지 20초 간격 재시도
while true; do
  code=$(curl -sS --max-time 30 -o resp.json -w '%{http_code}' -X POST "$DEPLOY_URL" -d "$body") || true
  case "$code" in
    2??) break ;;
    409) busy=$((busy + 1)); [ "$busy" -ge 40 ] && exit 1; sleep 30 ;;
    *)   transient=$((transient + 1)); [ "$transient" -ge 5 ] && exit 1; sleep 20 ;;
  esac
done
# 대기: 전체 기한(20분) 안에서 10초 간격 조회, 종단 상태에서만 끝낸다
while [ "$SECONDS" -lt "$deadline" ]; do
  code=$(curl -sS --max-time 20 -o status.json -w '%{http_code}' "$DEPLOY_URL/$REQUEST_ID") || true
  if [ "$code" = "200" ]; then
    state=$(jq -r '.data.state // "unknown"' status.json) || state=unreadable   # 깨진 본문은 다음 조회로
    if [ "$state" = "succeeded" ]; then
      [ "$(jq -r '.data.commit_sha' status.json)" = "$COMMIT" ] || exit 1      # 이 커밋이 배포됐나
      exit 0
    elif [ "$state" = "failed" ]; then
      echo "실패 단계: $(jq -r '.data.failed_stage' status.json)"; jq -r '.data.detail' status.json
      exit 1
    fi
  elif [ "$code" = "404" ]; then
    missing=$((missing + 1)); [ "$missing" -ge 3 ] && exit 1    # 접수했는데 모른다 = 일시 오류가 아니다
  fi                                                            # 그 외(조회 중 504 등)는 다음 조회로
  sleep 10
done
exit 1                                                          # 기한 초과도 빨간불
```
```go
// 서버: 같은 요청 번호의 재전송은 새 작업을 만들지 않는다 (응답 유실 뒤 재시도 = 이중 배포 방지)
if rec, found := store.Find(id); found {
    if rec.Target != req.Target || rec.Commit != req.Commit {
        return fail(409, "request_id_conflict")         // 같은 번호, 다른 내용
    }
    return accepted(rec.State, duplicate=true)
}
if inFlight[req.Target] { return fail(409, "in_progress") }
if err := store.Insert(id, StateAccepted); err != nil { return fail(500) }   // 기록 못 하는 작업은 받지 않는다
go advance(id)      // accepted → integrating → delivering → succeeded | failed(단계 + 출력 끝부분)
return accepted(StateAccepted)
```
적용 뒤 관측:\
실제 장애 중 접수가 504를 4번 연속 받고 5번째(약 2분 뒤)에 202 → 배포 성공·초록불.\
일부러 실패하는 테스트를 넣은 커밋 → 빨간불, 로그에 실패 단계(테스트)와 실패한 테스트 이름, 운영 컨테이너 생성 시각 불변.\
가짜 서버로 경우별 종료 코드: 504 2회 뒤 성공 0 · 접수 5회 실패 1 · 401 1 · 409 대기 뒤 테스트 실패 1 · 조회 404 유실 1 · 시간 초과 1 · 커밋 불일치 1.

### 방안 4 — 동기 호출: 요청 하나가 완료까지 응답을 붙잡는다 (선택하지 않은 방법)
```sh
curl -f --max-time 1200 -X POST "$DEPLOY_URL/sync" -d "$body"   # 완료 후에야 응답
```
선택하지 않은 이유: 이 경로의 엣지 프록시는 응답 대기 제한이 60초인데, 이전 방식의 배포 한 건은 400초를 넘긴 적이 있다.\
연결이 중간에 끊기면 결과도 함께 잃고(배포가 계속되는지 호출자는 모른다 → [three-state-rpc-outcome](../../distributed/three-state-rpc-outcome/)), 명세가 "진행 주체 = 서버, 호출자와 엣지 사이가 끊겨도 배포는 끝까지 간다"로 정했다.

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 출력만 | 사람이 매번 로그를 읽는다 | 없음 | 실패가 초록불로 위장 | 없음 |
| 2. 접수 코드 판정 | 작업이 요청 안에서 끝난다 | 한 줄 | 202 뒤 비동기 실패를 놓침, 일시 장애(504) 한 번에 바로 빨간불 | 동기 API |
| 3. 멱등 접수 + 상태 조회 | 서버가 요청 번호로 상태를 내주고 접수가 멱등 | 상태 API·이력 저장·러너가 기다리는 시간 | 재시도 상한(약 2분)보다 긴 장애·조회 경로 단절은 빨간불(수동 재실행) | 수 분짜리 비동기 작업, 중간에 프록시가 있는 경로 |
| 4. 동기 호출 | 경로의 모든 타임아웃 > 작업 시간 | 연결 하나 | 중간 프록시 제한에 잘리면 결과 모름 | 짧은 작업, 직접 연결 |

**결론**: 호출자가 응답으로 아는 것은 "접수됐다"까지다 — 완료를 초록불의 조건으로 삼으려면 서버가 완료를 물어볼 수단(요청 번호 + 상태 조회)을 내주고, 호출자는 종단 상태와 "이 커밋"까지 확인해야 한다(3).\
재시도를 붙이는 순간 "응답만 유실된 요청의 재전송"이 생기므로 접수는 요청 번호로 멱등이어야 한다 — 같은 실행의 재전송과 사람의 재실행은 번호를 달리해 구분한다([idempotent-retry-design](../idempotent-retry-design/) 변형 E와 같은 원리).\
작업이 짧고 경로의 모든 타임아웃이 작업 시간보다 길면 동기 호출(4)이 가장 단순하다.

검증 기록: 2026-11-20 사건 기록·실험 기록·코드(수정 전후) 대조·추상화(Claude 초안) — 방안 4는 실행하지 않은 방법이며, 근거 수치(응답 대기 제한·이전 배포 시간)는 경로 설정과 배포 기록에서 가져왔다.

## 방안 비교 — 헬스가 "정상"이라 말하는 근거: 작업 바퀴에서 추론하기 vs 물을 때 직접 확인하기

같은 원리(상태 신호는 "떴음"이 아니라 "일하나"를 말해야 한다 — 변형 G)의 다른 입구다.\
대상은 주기적으로 큐를 읽어 DB 에 저장하는 수집기이고, 헬스는 배포 게이트(첫 200 에서 통과)와 밖의 감시자가 함께 본다.\
처음 헬스는 같은 자리에서 세 가지로 틀렸다.

```
                 헬스가 본 것                     실제                        결과
(a) 오류 뭉갬    "DB 조회 실패" = 닿지 못함        닿았고, 표가 아직 없다       진짜 원인(스키마 생성 실패)이 "DB 불통"으로 가려짐
(b) 시작 중      첫 바퀴 전 = "starting" 200       한 번도 일하지 못했다        배포 게이트가 첫 200 에서 통과 → 일 못 하는 인스턴스로 전환
(c) 조용한 큐    마지막 바퀴 성공 = 정상           할 일이 없어 DB 에 안 닿음   DB 가 죽었는데 200
```

(c)는 처음 초안의 결함이라 원문이 남아 있지 않다 — 아래 문제 코드는 기록된 증상("조용한 큐에서 DB 가 죽어도 200")에서 구조를 재구성했다.

### 방안 1 — 작업 바퀴의 결과로 판정하고, 실패는 한 종류로 본다 (처음 형태)
```kotlin
fun report(now: Instant): Report {
    val failure = collector.lastFailure                   // 바퀴가 남긴 결과
    val database = runCatching { store.latestStoredAt() } // 실패 = 무엇이든 "닿지 못함"
    val status = when {
        database.isFailure -> "unreachable"
        failure != null -> "failing"
        collector.lastLoopAt?.let { between(it, now) < stallAfter } == true -> "ok"   // (c) 할 일이 없던 바퀴도 성공
        collector.lastLoopAt == null && between(startedAt, now) < stallAfter -> "starting"
        else -> "stalled"
    }
    return Report(healthy = status == "ok" || status == "starting", body(status))   // (b) 시작 중도 200
}
```

### 방안 2 — 물을 때 의존 서비스에 직접 묻고, 오류 종류를 가르고, 첫 성공 전에는 503 (이 사례의 선택)
```kotlin
fun report(now: Instant): Report {
    val failure = collector.lastFailure
    val pending = runCatching { queue.unacknowledgedCount() }         // (c) 헬스가 물을 때마다 큐에 직접
    val stored = runCatching { store.latestStoredAt() }               // (c) DB 에도 직접 — 결과를 담아 두지 않는다
        .recoverCatching { if (isTableMissing(it)) null else throw it }   // (a) 표 없음 = 닿았다. 판정은 바퀴 결과에 맡긴다
    val problems = listOfNotNull(pending.exceptionOrNull()?.let { "queue" to it },
                                 stored.exceptionOrNull()?.let { "database" to it })
    val status = when {
        problems.isNotEmpty() -> "unreachable"
        failure != null -> "failing"                                  // 스키마 생성 실패는 여기로: "schema <예외 종류>"
        collector.lastLoopAt?.let { between(it, now) < stallAfter } == true -> "ok"
        collector.lastLoopAt == null && between(startedAt, now) < stallAfter -> "starting"
        else -> "stalled"
    }
    return Report(healthy = status == "ok", body(status, problems.map { (where, e) -> "$where ${e.javaClass.simpleName}" }))
}

fun isTableMissing(error: Throwable) =                                // 원인 사슬에서 "relation does not exist" 를 찾는다
    generateSequence(error) { it.cause }.any { it is SQLException && it.sqlState == "42P01" }
```
```kotlin
// 헬스 전용 연결 풀 — 인증 없는 헬스가 몰려도 헬스끼리만 기다린다. 수집 풀은 비어 있다
val healthPool = pool("health", size = 1, statementTimeoutMs = 2_000, connectionTimeoutMs = 2_000)
```
세 고침이 각각 막는 것:\
(a) 오류 종류를 가르면 "닿지 못함"은 정말 닿지 못한 경우만 남고, 스키마 생성 실패는 `failing` 으로 제 이름을 단다.\
(b) 200 을 `ok` 하나로 좁히면 배포 게이트는 첫 바퀴가 성공한 인스턴스만 통과시킨다.\
(c) 바퀴 결과는 "그 바퀴가 닿은 것"만 말한다 — 할 일이 없던 바퀴는 DB 에 닿지 않으므로, 헬스가 물을 때 직접 묻는다.\
직접 확인한 결과를 몇 초 담아 두는 안도 나왔지만 선택하지 않았다 — 담아 두면 끊긴 직후에도 200 이 나간다.\
헬스 본문의 실패 사유는 예외 **종류 이름**만 낸다 — 헬스는 인증이 없어, 예외 문구는 서버 로그에만 남긴다.

(b)와 반대처럼 보이는 경우: 무중단 교체에서 **대기** 인스턴스는 200 이어야 한다 — 배포 게이트가 전환 **전에** 그 인스턴스가 떴는지 봐야 하기 때문이다([active-instance-from-routing-truth](../../distributed/active-instance-from-routing-truth/) 7번).\
둘을 가르는 것은 "게이트가 이 200 을 보고 무엇을 하나"다 — 이 사례의 게이트는 200 을 보면 곧바로 트래픽을 넘기므로, 일한 적 없는 인스턴스가 200 을 내면 안 된다.

실측(같은 기록): 기동부터 첫 200 까지 약 11초(게이트의 대기 한도 90초 안).\
DB 를 멈추자 다음 헬스 요청에서 503 `unreachable`, DB 가 돌아오고 6.9초 뒤 회복.\
(a)는 실제 PostgreSQL 에서 표를 만들 권한이 없는 계정으로 스키마 생성 실패를 만들어 확인했다 — 처음 테스트는 가짜 저장소가 늘 성공해 이 경우를 놓쳤고, 수정 뒤 재점검에서 드러났다.

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 바퀴 결과로 추론 · 실패 한 종류 · 시작 중 200 | 바퀴가 매번 모든 의존 서비스에 닿는다 | 없음(헬스가 아무것도 묻지 않는다) | 할 일이 없으면 의존 장애가 숨는다 · 원인이 "불통"으로 뭉개진다 · 게이트가 일 못 하는 인스턴스를 통과시킨다 | 바퀴가 늘 같은 일을 하는 작업(할 일 없음이 없을 때) |
| 2. 물을 때 직접 · 오류 종류 구별 · 200 은 `ok` 만 | 의존 서비스에 싸게 물을 수 있다(건수·최신 행 하나) | 헬스 요청마다 의존 서비스 왕복 몇 번, 전용 연결 하나 | 헬스가 몰리면 헬스끼리 기다리다 503 — 거짓 장애 쪽으로 실패한다 | 할 일이 들쭉날쭉한 수집·소비 작업 · 첫 200 에서 통과하는 게이트 |

**결론**: 헬스의 200 은 "이 인스턴스가 지금 제 일을 할 수 있다"의 **양성 증거**여야 한다 — 바퀴 결과는 그 바퀴가 닿은 범위만 증명하므로, 닿지 않았을 수 있는 의존 서비스는 헬스가 직접 묻는다(2).\
"아직 모름"(시작 중)은 정상이 아니라 정상이 아닌 쪽에 둔다 — 그 200 을 누가 무엇에 쓰는지(배포 게이트)를 보고 정한다.\
실패의 이름은 종류를 갈라 붙인다 — "닿지 못함" 하나로 뭉개면 헬스가 진짜 원인을 가리는 쪽으로 일한다.

검증 기록: 2026-11-21 사건 기록·수정 전후 코드 대조·추상화(Claude 초안).
