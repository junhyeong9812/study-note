# issue/reliability/abandoned-request-late-processing — 정리 (힌트)

## 전체 흐름

```
client (timeout 30s)
   │ ── 요청 ──▶ [ 서버 앞단 대기열: 상한 없음 ] ──▶ [ 처리 스레드 200 ] ──▶ [ DB 커넥션 10 ] ──▶ DB
   │                 ▲ 과부하: 거절하지 않고 쌓임
   │  30s 경과 ✂ 포기 (응답 코드 0 = "실패")
   │                 │
   │                 └──▶ ... 한참 뒤 차례가 와서 처리 → COMMIT (상태 변경)
   │                                    └─ 응답을 보낼 상대가 없음
   ▼
 클라이언트 집계: 확정 200 수                     DB 집계: CONFIRMED 수 (더 많음)
        └── 확정 200 − DB 확정 = −345 / −265 (과부하 두 단계, 회차 중앙값) = "유령 확정" ──┘
            (과부하가 없던 단계: 0)

실패를 원인별로 가르면 (과부하 단계 확정 요청의 응답 코드 0 내역 — 5xx는 0건)
  연결 수립 실패(dial timeout)   요청이 나가지 않음 → 처리 불가     (약 12%)
  보낸 뒤 연결 끊김(reset·EOF)   서버가 처리했을 수 있음 → 유령 후보 (약 6%)
  요청 타임아웃(30s)             대기열에서 기다리다 포기 → 유령 후보 (약 44%)

판정의 사각
  DB 최종 상태만 보면  → 위반 0 (뒤늦은 확정도 최종 상태로는 정상)
  응답만 보면          → 실패 61~66% (실제로는 일부가 성공)
  응답 ↔ DB 대조       → 불일치가 처음 보임

방향 (원 기록이 지목 / 일반 원리 — 이 사례에서 적용·검증 안 함)
  진입 속도 제어(대기열)·앞단 대기열 상한(즉시 거절)  → 발생 자체를 줄임
  요청 기한 전파(기한 지난 요청은 상태 변경 전 버림)    → 창을 좁힘
  멱등 키 + 결과 조회                                → 남은 모호함을 클라이언트가 해소
```

## 핵심 문장

- 클라이언트 타임아웃은 **클라이언트가 기다림을 그만두는 것**이지 서버 작업을 취소하는 것이 아니다 — 대기열에 남은 요청은 나중에 처리된다.
- 그래서 "응답 실패"는 "상태 변경 없음"이 아니다 — 서버 상태와 클라이언트 인식이 갈라진다(유령 확정).
- 최종 상태 불변식 검사와 응답 집계는 각각 이 불일치를 못 본다 — **응답과 DB를 대조**해야 보인다.
- 응답 없음의 원인을 **오류 코드로 가른다** — 요청이 나가기 전 실패만 "처리 안 됨"이 확실하다.
- 쿼리를 빠르게 해도 안 줄었다면 원인은 쿼리가 아니라 **과부하 앞단의 적체**다. 타임아웃을 늘리는 것은 처리량을 늘리지 않고 지연만 늘린다.
