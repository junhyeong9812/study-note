# issue/reliability/abandoned-request-late-processing — 정답

태그: `resource-bounding`

## 정답
<!-- 질문 1:1 대응 -->

1. **대기열이 요청을 붙잡아 두었다가 나중에 처리한다.** 설정은 처리 스레드 200·서버 앞단 대기열 상한 없음·DB 커넥션 10·클라이언트 타임아웃 30초였다.\
과부하(앱 CPU 포화)에서 들어온 요청은 거절되지 않고 앞단 대기열에 쌓이고, 클라이언트는 30초가 지나면 기다림을 그만두고 "응답 없음(코드 0)"으로 기록한다.\
그러나 클라이언트가 떠나도 서버 안의 요청은 사라지지 않는다 — 차례가 오면 정상적으로 처리·커밋되고, 응답만 보낼 상대가 없다.\
결과: 과부하 두 단계에서 **확정 200 응답 수가 DB의 확정 수보다 회차 중앙값 345·265건 적었다**(과부하가 없던 단계는 0). 한 회차의 확정 응답은 200이 6,625·코드 0이 10,472·409가 10건이었다.
   > **유령 확정(ghost commit)** — 클라이언트는 실패로 알고 있는데 서버에는 반영된 상태 변경. 응답 수와 저장소 행 수의 차이로만 드러난다.

2. **최종 상태 검사는 "어떻게 거기 도달했나"를 보지 못한다.** 뒤늦게 처리된 확정도 그 자체로는 정상 확정이라, 부하 후 DB 불변식(중복 확정·오래된 점유·매수 초과)은 과부하 단계에서도 **위반 0**이었다.\
응답만 보면 확정 실패율 61~66%로 보이지만 그중 일부는 실제로 성공했다 — 응답만으로도, DB만으로도 보이지 않는 불일치다.\
그래서 판정기는 **응답 기록과 DB 사실을 대조**한다: 클라이언트가 받은 성공 수(201·200)와 DB에 실제로 생긴 행(점유 행·확정 수)의 차이를 별도 지표로 둔다. 같은 대조가 "성공 응답마다 DB 행이 정확히 하나 있다(차이 0)"도 증명해 준다 — 그래야 동시 중복 성공이 응답 오류가 아니라 실제 중복 소유임을 확정할 수 있었다.

3. **요청 바이트가 나갔는가로 가른다.** 응답 코드 0을 부하 도구의 오류 코드로 나누면(과부하 단계 확정 요청, 5xx는 전 캠페인 0건): 요청 타임아웃 약 44%, **연결 수립 실패** 약 12%, **맺어진 연결이 도중에 끊김**(reset·EOF) 약 6%.\
연결 수립 실패는 요청이 서버에 닿지 않았으므로 처리될 수 없다. 반면 보낸 뒤 끊긴 요청과 대기열에서 기다리다 타임아웃된 요청은 **서버가 처리했을 수 있다** — 유령 확정의 후보다.\
주의: 연결 수립 실패가 서버의 연결 대기열 포화에서 났는지 네트워크 경로(무선·NAT)에서 났는지는 이 데이터로 가르지 못했다(같은 오류 코드가 난다).\
이 3분류는 [three-state-rpc-outcome](../../distributed/three-state-rpc-outcome/)의 "미실행 보증 · 결과 모름 · 성공"과 같은 구조다.

4. **반증: 5xx 0건 + 커넥션 풀 대기 예외 0건.** 쿼리가 30초를 넘겼다면 서버 쪽 타임아웃·오류가, 풀 대기라면 풀 대기 예외가 있어야 하는데 둘 다 없었다 — 원인은 **앞단 대기열 적체**였다(측정 중 정정한 판단).\
이어진 측정에서 인덱스를 추가해 요청 경로 쿼리가 수십 배 빨라졌는데도, 같은 과부하 단계의 확정 실패율은 0.61 → 0.62, 확정 불일치는 −266 → −243으로 **거의 그대로**였다 — 요청당 쿼리 비용이 원인이 아니라는 뜻이다.\
그 단계에서 실패가 난 회차들은 앱 CPU가 한도(약 200%)에 붙어 있었고, 같은 설정인데 실패 0%로 끝난 회차가 드물게 있어(앱 CPU 124~132%) "무너짐/안 무너짐" 두 갈래라는 가설만 세우고 원인은 후속으로 넘겼다.

5. **처리량은 그대로, 지연만 무한히 는다.** 타임아웃은 기다림의 상한일 뿐 처리 용량을 바꾸지 않는다 — 도착률이 용량을 넘는 동안 대기열은 계속 길어지고, 타임아웃을 없애면 그 길이가 그대로 응답 지연이 된다(측정 중 논의에서 "개선이 아님"으로 정리).\
타임아웃 값이 바꾸는 것은 **실패로 집계되는 비율과 유령의 크기**다 — 그래서 원 기록은 유령 확정의 "존재"는 판별되지만 "크기(−345 등)"는 클라이언트 타임아웃과 과부하 정도에 좌우되므로 운영에 옮기지 말라고 적었다.

6. **도구 중단도 진행 중 요청을 버린다.** 계단식 부하는 단계 오류율이 기준을 넘으면 실행을 중단(abort)하는데, 그 순간 진행 중이던 요청도 서버는 계속 처리한다.\
그래서 처리량 시나리오의 "DB 점유 행 − 성공 응답"은 회차당 약 8.7천~1만이었지만, 그중 실제 클라이언트 타임아웃은 670~3,185건뿐이었고 **나머지는 하네스 중단이 만든 산물**이었다.\
차이의 존재는 "포기 후 처리"를 증명하지만, 차이의 크기에는 측정 도구의 종료 방식이 섞인다 — 원인별로 나누기 전에는 크기를 해석하지 않는다.

7. **층마다 막는 지점이 다르다** (원 기록은 이 문제를 과부하·응답 경계 문제로 분류하고 진입 대기열·확정 원자성·결제 후 확정 실패 보상 실험으로 넘겼다 — 아래 해법은 그 방향과 일반 원리이며 **이 사례에서 적용·측정하지 않았다**).\
① 진입 속도 제어(대기열)·앞단 대기열 상한(넘치면 즉시 거절) — 적체 자체를 줄여 **발생 빈도**를 낮춘다.\
② 요청 기한 전파 — 서버가 상태를 바꾸기 직전에 기한을 확인해 이미 포기된 요청을 버린다. **창을 좁히지만 닫지는 못한다**(기한 확인 직후의 커밋, 커밋 후 응답 유실).\
③ 멱등 키 + 결과 조회 — 클라이언트가 "결과 모름"을 받으면 같은 키로 결과를 조회·재시도해 서버 상태와 맞춘다.\
보낸 뒤 연결이 끊기는 경우(이 측정에서도 약 6%)는 ①②로 없앨 수 없으므로, 결과가 모호할 수 있는 상태 변경 API에는 ③이 끝까지 필요하다. 서버 쪽 상한의 일반 원리는 [resource-bounding-last-defense](../resource-bounding-last-defense/) 참고.

## 문제 구조 (추상화 코드)

### 변형 A — 무제한 앞단 대기열 + 클라이언트 포기 → 유령 확정
① 문제 코드
```yaml
server:
  worker_threads: 200
  accept_queue: unbounded        # 과부하를 거절하지 않고 적재
db:
  pool_size: 10
client:
  timeout: 30s                   # 30초 뒤 포기 → "실패" 집계, 서버의 요청은 계속 대기
```
```python
# 판정: 최종 상태만 검사
assert db.count_violations() == 0          # 통과 — 뒤늦은 확정도 정상 확정
```
② 고친 코드 (판정 쪽 — 이 사례에서 적용)
```python
ok_confirms = count(r for r in responses if r.op == "confirm" and r.status == 200)
ghost = ok_confirms - db.count(status="CONFIRMED")   # 음수 = 클라이언트가 모르는 확정
report(ghost=ghost)                                  # 위반 항목과 별도 지표로
ok_holds = count(r for r in responses if r.op == "hold" and r.status == 201)
assert ok_holds - db.count_rows("holds") == 0        # 성공 응답마다 행이 정확히 하나
```
무엇이 깨졌나: "응답 실패 = 상태 변경 없음"을 가정했고, 판정이 최종 상태만 봐서 갈라진 인식을 못 봤다.

### 변형 B — 실패 원인 오진: 지연 기반 추정 → 오류 코드 분류
① 문제 코드
```text
가설: 30s 실패 = 느린 쿼리(30s+) 또는 커넥션 풀 대기
조치: 인덱스로 쿼리 가속 → 실패율 0.61 → 0.62 (변화 없음)
```
② 고친 코드
```python
# 반증 먼저: 5xx 0건, 풀 대기 예외 0건 → 쿼리·풀 아님 → 앞단 대기열 적체
def classify(r):                       # 응답 코드 0을 도구의 오류 코드로 분류
    if r.error == "request_timeout":   return "timeout"        # 처리됐을 수 있음
    if r.error == "dial_timeout":      return "not_sent"       # 처리 불가
    if r.error in ("conn_reset", "eof"): return "cut_after_send"  # 처리됐을 수 있음
    return "other"
```
무엇이 깨졌나: 실패를 한 종류로 보고 가장 그럴듯한 원인(쿼리)에 처방했다.

### 변형 C — 부하 도구 중단이 만든 같은 구조
① 문제 코드
```text
DB 점유 행 − 성공 응답 = +8.7천 ~ +1만 / 회차   → "전부 유령 점유"로 해석
```
② 고친 코드
```text
차이 = (클라이언트 타임아웃 후 처리: 670 ~ 3,185) + (도구 abort 시점 진행 중 요청: 나머지)
→ 존재만 판정, 크기는 원인별로 분리하기 전에는 해석하지 않음
```
무엇이 깨졌나: 측정 도구의 종료가 "포기한 요청"을 대량으로 만들어 현상의 크기에 섞였다.

## 방안 비교

일반 원리 — 이 사례는 판정(응답-DB 대조)까지 적용했고, 아래 서버·클라이언트 쪽 방안은 적용·측정하지 않았다. 표의 실패 모드는 구조에서 추론한 것이다.

### 방안 1 — 앞단 대기열 상한 + 즉시 거절 (또는 진입 속도 제어)
```text
accept_queue: bounded(N)  → 넘치면 즉시 503 (요청이 서버 안에 머물지 않음 = 나중 처리 없음)
```

### 방안 2 — 요청 기한 전파
```kotlin
fun confirm(req: Req): Resp {
    if (clock.now() > req.deadline) return Resp.expired()   // 이미 포기된 요청은 상태를 바꾸지 않는다
    return tx { doConfirm(req) }                            // 확인 ~ 커밋 사이의 창은 남는다
}
```

### 방안 3 — 멱등 키 + 결과 조회
```kotlin
// 클라이언트: 결과 모름(타임아웃·끊김) → 같은 키로 조회/재시도
val r = runCatching { api.confirm(key, item) }
if (r.isAmbiguous()) api.statusOf(key)          // 서버가 처리했으면 그 결과, 아니면 미처리
// 서버: 같은 키는 한 번만 반영하고 같은 결과를 돌려준다
```

### 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 대기열 상한·즉시 거절 / 진입 속도 제어 | 거절된 요청을 호출자가 재시도·대기로 다룰 수 있음 | 과부하 때 거절 증가, 상한·속도 튜닝 | 상한이 너무 크면 적체가 남고, 너무 작으면 정상 폭주도 거절 | 도착률이 용량을 넘을 수 있는 모든 공개 경로 |
| 요청 기한 전파 | 클라이언트 기한을 서버가 알 수 있음(헤더 등), 시계 차이 허용 | 모든 단계에 기한 전달·확인 | 확인 직후 커밋·커밋 후 응답 유실은 못 막음 | 오래 대기할 수 있는 상태 변경 요청 |
| 멱등 키 + 결과 조회 | 요청마다 클라이언트가 키 생성, 서버가 키별 결과 저장 | 키 저장소·조회 API·보존 기간 | 키 재사용·보존 만료 후 재시도는 중복이 될 수 있음 | 결과가 모호할 수 있는 모든 상태 변경 API |

**결론**: 대기열 상한·진입 속도 제어는 이 현상을 **덜 일어나게** 하고, 기한 전파는 **창을 좁히지만**, 둘 다 "보낸 뒤 연결이 끊긴" 요청의 모호함은 없애지 못한다.\
따라서 상태를 바꾸는 요청에는 멱등 키와 결과 조회로 **모호함을 해소하는 경로**가 기본으로 있어야 하고, 앞의 두 방안은 그 위에서 발생 빈도와 대기 비용을 줄이는 층으로 얹는다.\
어느 쪽을 택하든 검증은 이 사례의 판정 방식(응답 ↔ 저장소 대조, 실패를 오류 코드로 분류)으로 한다.
