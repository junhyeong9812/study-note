# issue/reliability/abandoned-request-late-processing — 클라이언트가 포기한 요청을 서버가 뒤늦게 처리한다: 응답은 실패, 상태는 변경 — 질문

## 질문
1. (왜) 클라이언트는 30초 뒤 "확정 실패(응답 없음)"를 받았는데, DB에는 그 확정이 반영돼 있었다. 서버 앞단 대기열이 무제한이고 처리 스레드·DB 커넥션이 유한할 때, 클라이언트가 떠난 요청은 서버 안에서 어떤 경로를 거쳐 결국 처리되는가.
2. (예측) 부하가 끝난 뒤 DB 최종 상태만으로 불변식(중복 확정 0·오래된 점유 0 등)을 검사하면 위반 0이 나온다. 이것으로 "정합하다"고 결론 내리면 무엇을 놓치는가. 응답 기록과 DB를 어떻게 대조해야 이 불일치가 보이는가.
3. (경계) 응답을 못 받은 실패에도 종류가 있다 — 연결 수립 실패, 보낸 뒤 연결 끊김, 요청 타임아웃. 이 중 "서버가 처리했을 수 있는" 것은 무엇이고, 확실히 처리되지 않은 것은 무엇인가.
4. (오진) 30초 실패를 처음에는 "쿼리가 30초 넘게 걸렸거나 커넥션 풀 대기"로 의심했다. 어떤 관측 두 가지가 그 가설을 반증했는가. 그리고 인덱스로 쿼리를 수십 배 빠르게 했는데도 이 실패율·불일치가 거의 줄지 않은 것은 원인에 대해 무엇을 말해 주는가.
5. (예측) "그럼 클라이언트 타임아웃을 없애거나 늘리면 실패가 사라지니 개선 아닌가?" — 처리량과 지연은 각각 어떻게 되는가.
6. (경계) 부하 도구가 한계 도달로 실행을 중단(abort)해도 같은 구조가 생긴다. 이것이 "응답 성공 수 vs DB 행 수" 차이의 **크기**를 해석할 때 어떤 함정을 만드는가.
7. (연결) 대기열 상한·요청 기한 전파·멱등 키와 결과 조회·진입 속도 제어는 각각 이 문제의 어느 지점을 막는가. 네트워크가 요청을 보낸 뒤 끊기는 경우까지 생각하면, 어느 것이 끝까지 필요한가.
