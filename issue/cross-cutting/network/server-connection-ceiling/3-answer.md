# issue/cross-cutting/network/server-connection-ceiling — 정답

태그: `resource-bounding`

## 정답
<!-- 질문 1:1 대응 -->

1. **"못 받는다" 쪽이다 — 연결 수가 서버의 연결 상한에 닿았다.**\
   느린 서버라면 지연이 늘고 시한 초과가 섞이지만, 이 회차는 새 연결 8,153개 직후부터 끝까지 **일정한 비율(초당 약 60건)로** 코드 0이 났다.\
   결정적인 것은 서버 안에서 앱을 직접 두드린 저율 측정기도 같은 시간대에 코드 0(11,714건)을 받은 것이다 — 클라이언트와 네트워크 경로를 빼도 실패하므로, 경로가 아니라 받는 쪽(앱 프로세스)이 연결을 받지 않은 것이다.\
   앱 설정·배포 설정 어디에도 연결 상한이 없었으므로 내장 서블릿 서버의 기본값 8,192가 그대로 쓰였다.\
   상한을 올린 뒤 같은 칸을 다시 재자 코드 0이 0건이 됐다 — 원인 추정이 개입으로 확인됐다.

2. **동시 연결 ≈ 도착률 × 연결을 쥐는 시간 — 쉬는 세션도 연결을 쥐고 있으면 들어간다.**\
   부하 도구의 가상 사용자(VU)는 세션 동안 keep-alive 연결 하나를 쥔다 — 요청 사이 생각 시간에도 연결은 열려 있다.\
   그래서 같은 도착률이라도 세션이 30초인 칸은 동시 VU가 약 4,700으로 상한 아래였고, 세션이 5분인 칸은 최대 9,254로 상한 8,192를 넘었다.\
   VU 수는 연결 수의 하한 어림일 뿐이다 — 상한을 올린 뒤 실측한 열린 연결(ESTABLISHED)은 최대 14,727이었다(원인은 따로 보지 않음). 여유는 어림이 아니라 실측 연결 수로 판단한다.
   > **리틀의 법칙** — 안정 상태에서 계 안의 평균 개수 = 도착률 × 평균 체류 시간. 연결·스레드·풀 크기를 어림하는 기본 식이다.

3. **상한에 닿으면 서버는 연결을 더 꺼내 처리하지 않고, 새 연결은 커널 대기열에서 기다리다 넘치면 거절·시한 초과로 끝난다(일반 동작).**\
   내장 서블릿 서버(Tomcat NIO)는 열린 연결 수가 `maxConnections`에 닿으면 accept를 멈춘다 — 이미 TCP 연결이 맺어진 것들은 운영체제의 accept 대기열(`acceptCount` · 커널 `somaxconn`이 상한)에 쌓이고, 그것도 차면 새 연결 시도가 거절되거나 응답 없이 시한을 넘긴다(서버 문서의 일반 동작 — 이 사례는 어느 갈래였는지 따로 가르지 않았다).\
   클라이언트에는 HTTP 상태가 아니라 연결 단계 오류(코드 0)로 보인다 — 서버 로그에는 요청이 없으므로 앱 오류로 남지 않는다.

4. **연결 상한 ≤ 서버 프로세스의 파일 기술자 한도 · 커널 대기열 · 클라이언트 포트·메모리 — 그리고 적용값 대조.**\
   연결 하나는 서버 프로세스의 기술자 하나다 — 상한을 20,000으로 올리면서 앱 컨테이너의 `nofile`을 65,536으로 함께 올렸다(기술자 한도가 낮으면 올린 상한은 닿을 수 없는 숫자다 — [load-balancer-defaults-in-backend-switch](../../infra/load-balancer-defaults-in-backend-switch/) 변형 A).\
   서버 호스트의 커널 값도 읽었다 — `somaxconn` 4,096(서버 accept 대기열의 상한)과 임시 포트 범위 32768–60999.\
   임시 포트 범위는 그 호스트가 **밖으로 여는** 연결의 상한이다 — 들어오는 연결 수와는 무관하고, 같은 범위가 클라이언트 호스트에 있으면 한 대상(주소·포트)에 열 수 있는 연결이 약 28,000개로 묶인다(일반론).\
   설정 파일을 바꾼 것만으로는 적용을 보장하지 않으므로, 회차 시작 때 서버의 실제 적용값(연결 상한·기술자 한도)을 읽어 계획과 다르면 그 회차를 무효로 하는 규칙을 넣었다.\
   큰 동시 연결은 클라이언트도 무겁게 한다 — 같은 칸에서 부하 도구의 상주 메모리가 10.6GB였고, 이후 측정에는 클라이언트 PC의 가용 메모리 하한 규칙을 함께 뒀다.

5. **측정 결과는 "상한이 충분할 때의 비교"이고, 운영 기본 설정이 그 부하를 견딘다는 근거가 아니다.**\
   상한은 측정용 배포 설정에서만, 비교한 모든 방식에 같게 올렸다 — 방식 비교의 공정성은 지켜진다.\
   대신 앱의 기본 설정은 8,192 그대로이므로, 세션이 길고 동시 접속이 수천~1만이면 운영에서 같은 상한을 다시 봐야 한다는 것을 결과 문서의 해석 주의로 남겼다.

6. **시나리오 크기를 정할 때 "동시 연결 어림 vs 알려진 상한" 표를 먼저 만든다.**\
   같은 상한(8,192)은 앞선 실험의 기록에 이미 있었지만, 세션 길이를 늘린 새 시나리오의 동시 연결을 그 상한과 대조하지 않았다 — 깨진 것은 확인 스모크에서였다.\
   칸마다 도착률 × 세션 길이로 동시 연결을 어림하고, 서버 연결 상한·기술자 한도·커널 대기열·클라이언트 포트·클라이언트 메모리와 나란히 놓으면 측정 전에 걸러진다.\
   어림이 상한의 일정 비율(예: 절반)을 넘는 칸은 스모크에서 실측 연결 수를 먼저 본다.

## 문제 구조 (추상화 코드)

### 변형 A — 긴 세션이 연결을 쥔 채 쉬어 기본 상한을 넘음
① 문제 코드
```yaml
# 서버 배포 설정 — 연결 상한 지정 없음 → 내장 서버 기본 8,192
app:
  image: app:<sha>
  # server.tomcat.max-connections: (없음)
  # ulimits.nofile: (런타임 기본)
```
```js
// 부하: 도착률 고정, 세션 = 요청 → 생각 시간(최대 수 분) → 요청 — VU마다 keep-alive 연결 1개
scenarios.main = { executor: 'constant-arrival-rate', rate: R, duration: D, preAllocatedVUs: P };
```
② 고친 코드
```yaml
app:
  environment:
    SERVER_TOMCAT_MAX_CONNECTIONS: "20000"   # 측정 배포에서만 · 모든 비교 대상에 같게
  ulimits:
    nofile: { soft: 65536, hard: 65536 }      # 연결 1개 = 기술자 1개
```
```sh
# 회차 시작 조건 — 적용값 대조(설정 파일이 아니라 실행 중인 값)
applied=$(read_applied_config "$APP")         # 연결 상한 · 프로세스 nofile
[ "$applied" = "$PLANNED" ] || invalidate "cond-config-mismatch"
```
무엇이 깨졌나: 연결 수 = 도착률 × 보유 시간인데, 보유 시간을 늘린 시나리오를 서버 기본 연결 상한과 대조하지 않았다.

## 검증 기록
- 2026-11-04: 사건 기록 대조·추상화(Claude 초안) — 원인은 회차 자료(새 연결 수·실패 비율·서버 안 측정기 코드 0)로 추정한 뒤 상한을 올린 재측정에서 코드 0이 0건이 되는 것으로 확인, 상한 도달 시 서버의 accept 동작은 서버 문서의 일반 동작(이 사례에서 갈래를 가르지 않음).

## 방안 비교

같은 원리(열린 연결 수가 받는 쪽 상한을 넘는다)에 대한 세 방안.

### 방안 1 — 측정 배포에서만 상한·기술자 한도를 올리고 적용값을 대조 (이 사례의 선택)
```yaml
SERVER_TOMCAT_MAX_CONNECTIONS: "20000"; ulimits.nofile: 65536   # + 회차 시작 적용값 대조
```

### 방안 2 — 연결을 쥐는 시간을 줄인다 (일반 원리 — 이 사례에서 상한 대책으로 적용하지 않음)
```js
// 긴 생각 시간 앞에서 연결을 닫아 쉬는 동안 자리를 비운다
if (thinkMs >= LONG_THINK_MS) req.params.headers.Connection = 'close';
// 또는 서버 keep-alive 유휴 한도를 짧게 → 쉬는 연결을 서버가 먼저 회수
```

### 방안 3 — 앱 기본 설정의 상한을 올린다 (선택하지 않은 방법 — 범위 밖)
```properties
server.tomcat.max-connections=20000   # 운영 기본값 변경 = 측정 대상 밖의 결정
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 측정에서만 올림 | 비교 대상 모두에 같은 조건, 기술자 한도도 함께 | 설정 2곳 + 적용값 검사 | 결과가 운영 기본값의 한계를 가린다 — 해석 주의로 적어야 한다 | 상한이 비교 변수가 아닌 측정 |
| 2. 보유 시간 줄임 | 연결 수립 비용이 작다(같은 LAN) | 세션마다 연결 수립 · 서버 유휴 한도를 줄이면 [keep-alive-idle-close-race](../keep-alive-idle-close-race/)의 경합 창이 앞당겨진다 | 쉬는 시간이 고르지 않으면 효과가 칸마다 다르다 | 세션 대부분이 쉬는 부하(사람의 생각 시간) |
| 3. 앱 기본값 올림 | 서버 메모리·스레드가 그 연결 수를 감당한다 | 운영 결정 · 다른 환경에 퍼짐 | 기술자 한도·프록시 상한이 그대로면 닿을 수 없는 숫자 | 운영 동시 접속 어림이 상한에 가까울 때 |

**결론**: 측정에서는 방안 1이 맞다 — 비교 대상 모두에 같게 올리고, 설정 파일이 아니라 실행 중인 적용값으로 회차마다 확인한다.\
운영 경로라면 먼저 방안 2(연결 보유 시간)를 보고, 그래도 동시 연결 어림이 상한에 가까우면 방안 3을 기술자 한도·앞단 프록시 상한과 한 묶음으로 바꾼다.\
검증 기록: 2026-11-04 사건 기록 대조(Claude 초안) — 방안 1은 적용·재측정 확인, 방안 2는 이 사례에서 keep-alive 경합 대책으로만 쓰였고 상한 대책으로는 재지 않음, 방안 3은 범위 밖.
