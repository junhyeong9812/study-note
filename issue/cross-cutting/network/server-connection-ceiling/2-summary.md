# issue/cross-cutting/network/server-connection-ceiling — 정리 (힌트)

## 전체 흐름

```text
동시 연결 ≈ 도착률 × 연결을 쥐는 시간            (리틀의 법칙 — 세션마다 keep-alive 연결 1개)
  세션 30초 칸: 동시 세션 약 4,700  → 상한 아래
  세션 5분  칸: 동시 세션 최대 9,254 → 상한 8,192 위

부하 도구 ──새 연결──▶ [커널 accept 대기열] ──accept──▶ [서버: 연결 수 < max-connections?]
                                                         ├─ 예 → 처리
                                                         └─ 아니오 → 더 받지 않음(일반 동작)
   첫 30초 새 연결 8,153 ──▶ 상한 근처 ──▶ 이후 초당 약 60건 코드 0 (회차 끝까지)
   서버 안 측정기(앱 직접)도 코드 0 11,714   → "느림"이 아니라 "못 받음"

올릴 때 함께 맞출 상한
  서버 연결 상한(max-connections)  ≤  서버 프로세스 nofile  (연결 1개 = 기술자 1개)
  커널 accept 대기열(somaxconn) · 클라이언트 쪽 임시 포트 범위(밖으로 여는 연결의 상한) · 클라이언트 메모리
  적용값 대조: 회차 시작 때 실제 설정을 읽어 계획과 다르면 무효
```

## 핵심 문장

- 연결 상한은 "동시 요청"이 아니라 "열려 있는 연결" 수를 센다 — 쉬고 있는 keep-alive 연결도 자리를 쥔다.
- 동시 연결 수는 도착률 × 연결 보유 시간이다 — 생각 시간이 길어지는 시나리오는 같은 도착률에서도 상한에 닿는다.
- 상한에 닿은 서버는 느려지는 대신 연결을 받지 않는다 — 클라이언트에는 응답 코드 없는 연결 오류로 보인다.
- 서버 안에서 앱을 직접 두드린 측정기까지 실패하면 경로가 아니라 받는 쪽이다.
- 연결 상한을 올리면 기술자 한도도 함께 올리고, 바뀐 값이 실제로 적용됐는지 회차마다 읽어 대조한다.
- 측정에서만 올린 상한은 운영 기본값의 결함을 지운 것이 아니라 가린 것이다 — 결과에 그 조건을 적는다.
