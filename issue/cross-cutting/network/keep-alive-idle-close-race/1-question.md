# issue/cross-cutting/network/keep-alive-idle-close-race — keep-alive 유휴 종료 경합: 서버가 쉬는 연결을 닫는 순간 클라이언트가 그 연결로 비멱등 요청을 보내면, 재시도되지 않는 연결 오류가 된다 — 질문

## 질문
1. (왜) 클라이언트가 요청 하나를 보낸 뒤 60초 남짓 쉬고, 같은 keep-alive 연결로 POST를 보냈더니 응답 코드 없이 `EOF`로 끝났다. 서버의 유휴 한도가 60초이고 클라이언트에는 유휴 한도가 없으면 두 쪽의 무엇이 겹치나. 왜 61초 넘게 쉰 요청은 실패하지 않았나.
2. (예측) 같은 경합에서 그 요청이 GET이었다면 결과가 달랐을까. Go `net/http`는 재사용 연결이 끊긴 요청을 어떤 조건에서 새 연결로 다시 보내나 — POST에 `Idempotency-Key` 헤더를 붙이면 무엇이 달라지고, 그 대가는 무엇인가.
3. (경계) 실패한 POST는 서버 처리 코드에 닿았나. 서버 처리 수와 클라이언트 성공 수를 대조하면 무엇을 말할 수 있나 — 이 오류를 언제나 "서버가 처리하지 않았다"로 읽어도 되나.
4. (설계) 고치는 길 세 가지 — 긴 휴지 앞 요청에 `Connection: close` · 서버 유휴 한도를 클라이언트 휴지보다 길게 · 클라이언트 유휴 한도를 서버보다 짧게 — 를 비교하라. "클라이언트·중간 장치의 유휴 한도 < 서버 keep-alive 한도"라는 일반 규칙은 왜 이 방향인가.
5. (측정) 실측에서 0.2% 남짓으로 드문 경합을 어떻게 재현하나. 휴지 분포를 어디에 두고, 무엇을 대조군으로 두나 — 서버 한도를 2초로 줄인 축소판은 왜 쓰나.
6. (연결) 부하 실험에서 이 경합 두 건이 비교 대상 방식의 "실패"로 집계됐다. 측정 도구(하네스)의 인공물과 측정 대상의 결함을 가르는 서명은 무엇인가 — 그리고 같은 경합이 측정 전에 다른 경로에서 먼저 보였는데 왜 남아 있었나.
