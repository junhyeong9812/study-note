# issue/cross-cutting/network/keep-alive-idle-close-race — 정리 (힌트)

## 전체 흐름

```text
클라이언트(유휴 한도 없음)                         서버(유휴 한도 60초 · 시간 초과 검사 약 1초 간격)
  요청 A ───────────────────────────────────────▶ 응답 A   ── 연결은 풀로 돌아가 쉰다
  │ 생각 시간 (60초 언저리)                        │
  │                                                ├─ 60~61초 사이 어느 검사에서 "유휴 초과" → FIN
  POST B ── 풀에서 "살아 있는" 연결을 꺼내 씀 ───▶ │  (FIN이 클라이언트에 닿기 전·닿은 직후 송신)
          ◀──────────────── EOF / RST ──────────────┘  POST B는 서버 처리 코드에 닿지 않음
  재시도?  재사용 연결 + 이미 씀 + 비멱등(POST, 키 없음) → 하지 않음 → 코드 0 · EOF

  61초 넘게 쉼  → 서버가 이미 닫았고 클라이언트도 그 사실을 알아챈 뒤 → 새 연결 → 성공
  60초 미만     → 서버가 아직 안 닫음 → 재사용 성공
  경합 창       = [서버 한도, 서버 한도 + 검사 간격) 근처의 좁은 띠

고치는 길
  ① 긴 휴지 앞 요청에 Connection: close      → 다음 요청은 늘 새 연결 (대가: 연결 수립 1회)
  ② 서버 유휴 한도 > 클라이언트 최대 휴지     → 서버가 먼저 닫지 않음 (대가: 쉬는 연결 보유)
  ③ 클라이언트 유휴 한도 < 서버 유휴 한도     → 클라이언트가 먼저 버림 (일반 규칙)
  ④ 멱등 키(Idempotency-Key)                 → Go가 새 연결로 다시 보냄 (대가: 서버가 중복을 견뎌야 함)
```

## 핵심 문장

- keep-alive 연결의 종료는 서버가 혼자 정한다 — 클라이언트는 FIN을 받기 전까지 그 연결이 살아 있다고 믿는다.
- 경합은 휴지가 서버 한도 바로 위 좁은 띠에 들 때만 생긴다 — 그래서 드물고, 휴지가 긴 흐름에서만 보인다.
- 재사용 연결의 실패를 다시 보내는 것은 멱등 요청뿐이다 — POST는 키가 없으면 그대로 오류로 남는다.
- 유휴 한도의 순서 규칙: 연결을 재사용하는 쪽(클라이언트·중간 장치)의 한도가 더 짧아야 먼저 닫는 쪽이 재사용하지 않는 쪽이 된다.
- 드문 경합은 휴지를 경계 띠 안에 몰아 넣어 재현하고, 한도를 줄인 축소판으로 표본을 늘린다 — 대조군(한도 > 휴지)은 0이어야 한다.
- 같은 경합이 한 경로에서 먼저 보였으면, 같은 조건(긴 휴지 뒤 재사용)을 가진 다른 경로도 함께 고친다.
