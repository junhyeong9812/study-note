# issue/cross-cutting/network/keep-alive-idle-close-race — 정답

태그: `race-condition`

## 정답
<!-- 질문 1:1 대응 -->

1. **서버가 유휴 연결을 닫는 순간과 클라이언트가 그 연결을 다시 쓰는 순간이 겹쳤다.**\
   서버(내장 Tomcat 10.1.x)는 keep-alive 유휴 한도를 따로 주지 않으면 연결 시한(`connectionTimeout`, 기본 60,000ms)을 그대로 쓴다 — 프레임워크(Spring Boot)도 이 값을 설정하지 않으면 넣지 않는다.\
   NIO poller는 시간 초과를 약 1초 간격(`selectorTimeout` 1,000ms)으로 검사하므로, 실제 종료는 유휴 60~61초 사이의 어느 순간이다.\
   클라이언트(부하 도구 k6 — Go `net/http`)의 Transport에는 `IdleConnTimeout`이 없다(0 = 한도 없음) — 풀의 연결을 언제까지나 "살아 있다"고 보고 꺼내 쓴다.\
   그래서 휴지가 그 1초 띠에 들면, 서버가 FIN을 보내는 순간과 클라이언트가 POST를 쓰는 순간이 겹쳐 응답 대신 `EOF`가 온다.\
   61초 넘게 쉰 요청은 서버가 이미 닫았고 클라이언트도 그 연결을 버린 뒤라 새 연결로 갔다 — 실측에서 61초 넘게 쉰 요청의 실패는 0이었다.
   > **keep-alive(지속 연결)** — HTTP/1.1에서 응답 뒤에도 TCP 연결을 닫지 않고 다음 요청에 다시 쓰는 것. 언제 닫을지는 양쪽이 각자 정한다.

2. **GET이었다면 새 연결로 다시 보내 성공했을 것이다 — Go는 재사용 연결의 실패를 멱등 요청에만 재시도한다.**\
   Go `net/http`의 재시도 판단(`shouldRetryRequest`)은 대략 이렇다: 새 연결이었으면 재시도하지 않는다 · 아무것도 쓰지 못했으면 본문을 되감을 수 있을 때 재시도한다 · 이미 썼으면 **요청이 재생 가능(`isReplayable`)할 때만** 재시도한다.\
   재생 가능 = 본문이 없거나 되감을 수 있고, 메서드가 GET·HEAD·OPTIONS·TRACE이거나 **`Idempotency-Key`·`X-Idempotency-Key` 헤더가 있는** 요청이다.\
   그래서 키 없는 POST는 서버가 닫은 연결에 이미 쓴 뒤라 그대로 `EOF`(k6 오류 코드 1000)로 남는다.\
   키를 붙이면 클라이언트가 같은 요청을 한 번 더 보낼 수 있으므로, 서버는 같은 키의 두 번째 요청을 한 번만 처리해야 한다 — 그 보장이 없으면 키는 경합을 이중 처리로 바꾼다.
   > **멱등(idempotent)** — 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질. 전송 계층이 자동 재시도해도 되는지를 가르는 기준이다.

3. **이 경우 닿지 않았다 — 하지만 일반적으로는 "모름"이다.**\
   재현에서 서버 서블릿이 센 POST 수는 클라이언트 성공 수와 정확히 같았다(36,057회 중 실패 57 → 서버 처리 36,000).\
   서버가 연결을 닫기로 한 뒤 도착한 바이트는 요청으로 해석되지 않은 것이다.\
   다만 연결 오류 자체는 "요청이 서버에서 실행됐는지"를 말해 주지 않는다 — 응답을 쓰는 도중 끊긴 경우와 겉으로는 같은 코드 0이다.\
   이 사례는 서버 처리 수를 따로 세어 갈랐고, 그런 대조 없이는 비멱등 요청의 결과를 모르는 것으로 다뤄야 한다(같은 원리: [three-state-rpc-outcome](../../distributed/three-state-rpc-outcome/)).

4. **연결을 재사용하는 쪽이 먼저 닫게 만드는 것이 원칙이고, 그렇게 못 하면 긴 휴지 앞에서 연결을 끊는다.**\
   경합이 생기는 이유는 "닫는 쪽(서버)"과 "다시 쓰는 쪽(클라이언트)"이 다르기 때문이다.\
   클라이언트·로드밸런서의 유휴 한도를 서버 keep-alive 한도보다 짧게 두면 늘 재사용하는 쪽이 먼저 연결을 버리므로, 서버가 닫는 연결에 요청이 실릴 일이 없다(일반 규칙 — 로드밸런서 문서들이 백엔드 keep-alive를 LB 유휴 한도보다 길게 두라고 권하는 것과 같은 방향).\
   이 사례의 클라이언트(부하 도구)는 유휴 한도를 바꿀 손잡이가 없었고, 서버 한도는 측정 대상 설정이라 바꾸지 않았다 — 그래서 **생각 시간이 50초 이상인 흐름은 그 앞 요청을 `Connection: close`로 보내** 다음 요청이 늘 새 연결로 가게 했다(문턱 50초 = 서버 60초보다 검사 간격·송신 지연 여유 10초 짧게).\
   대가는 그런 세션마다 연결 수립 1회(같은 LAN에서 약 0.5ms)이고, 연결 조건이 실제로 바뀐 것은 휴지 [50, 61)초 구간(약 5%)뿐이었다 — 61초 넘게 쉬는 요청은 원래도 새 연결이었다.

5. **휴지를 경계 띠 안에 몰아 넣고, 한도를 줄인 축소판으로 표본을 늘리고, 대조군은 0이어야 한다.**\
   본 측정에서 휴지가 60~61초였던 요청은 약 970건이었고 그중 2건이 실패했다(약 0.21%) — 이대로는 재현에 수만 건이 든다.\
   재현은 같은 PC의 루프백에서 같은 버전 내장 서버 + 같은 부하 도구로 했다: 휴지 U[60,61)초 2,000회 → `EOF` 8건(0.40% · 휴지 60.03~60.24초 · 모두 재사용 연결 `connecting` 0).\
   축소판: 서버 한도 2초 · 휴지 U[2,3)초 · 36,057회 → `EOF` 57건. 같은 축소판에서 대조군 셋은 모두 0건이었다 — 서버 한도 10초(> 휴지) · 쉬기 전 요청에 `Connection: close` · POST에 `Idempotency-Key`.\
   한도를 줄여도 경합의 모양(1초 검사 띠 · 재사용 연결 · 비멱등)은 같고 시간만 줄어든다 — 그래서 원인 판정에는 축소판, 빈도 대조에는 실제 한도판을 쓴다.

6. **서명: 재사용 연결(`connecting` 0) · 유휴가 서버 한도 바로 위 · 1ms 미만에 끝난 `EOF` · 서버 쪽 오류 기록 없음.**\
   실측 두 건은 각각 60.27초·60.15초 쉰 재사용 연결 위에서 0.585ms·0.758ms 만에 `EOF`로 끝났고, 서버에는 ERROR 줄이 없었다.\
   휴지 60~61초 요청은 비교한 네 방식에 각각 약 240건씩 같은 만큼 있었다 — 노출이 같으므로 실패 0건인 방식이 이 경합에 "강하다"는 근거가 되지 않는다(그 빈도에서 0건일 확률이 약 0.6).\
   같은 경합은 측정 전 스모크의 탐침 요청에서 먼저 나왔다 — 그때는 탐침만 `Connection: close`로 고쳤고, 주 흐름의 "생각 시간 뒤 확정" 경로는 남았다.\
   서버 기본 유휴 한도(60초)가 생각 시간(최대 수 분)보다 짧다는 위험도 측정 전에 기록돼 있었다 — 같은 조건(긴 휴지 뒤 재사용)을 가진 형제 경로를 함께 고치지 않은 것이 본 측정까지 남은 이유다([sibling-path-invariant-drift](../../reliability/sibling-path-invariant-drift/)).

## 문제 구조 (추상화 코드)

### 변형 A — 긴 생각 시간 뒤 같은 연결로 비멱등 요청
① 문제 코드
```js
// 서버: keep-alive 유휴 한도 미설정 → 연결 시한 60s를 그대로 씀(검사 약 1s 간격 → 실제 60~61s)
// 클라이언트: Transport에 유휴 한도 없음
const r1 = http.post(`${BASE}/step1`, body1);          // 연결 C를 풀에 반납
sleep(think);                                            // think ∈ [30s, 240s] — 일부가 60~61s에 든다
const r2 = http.post(`${BASE}/step2`, body2);           // 풀에서 C를 꺼냄 → 서버가 막 닫음 → EOF, 재시도 없음
if (r2.status === 0) countAsFailure();                   // 측정 대상의 실패로 집계됨
```
② 고친 코드
```js
const KEEPALIVE_SAFE_MS = 50000;                         // 서버 유휴 한도(60s)보다 여유 있게 짧게
function closeBeforeLongThink(req, thinkMs) {
  if (thinkMs >= KEEPALIVE_SAFE_MS) req.params.headers.Connection = 'close';   // 응답 뒤 연결을 닫는다
  return req;
}
const r1 = send(closeBeforeLongThink(step1Req, think));  // 긴 휴지 앞이면 C를 닫는다
sleep(think);
const r2 = send(step2Req);                               // 늘 새 연결 → 경합 창 없음
```
무엇이 깨졌나: 연결을 닫는 쪽(서버)의 한도보다 다시 쓰는 쪽(클라이언트)의 휴지가 길 수 있었고, 그 요청은 전송 계층이 다시 보내지 않는 비멱등 요청이었다.

### 변형 B — 같은 경합을 한 경로에서만 고침
```js
// 측정 전: 탐침 흐름에서 같은 EOF → 탐침만 고침
probeReq = closeConn(probeReq);                          // 탐침은 연결 재사용 안 함
// 주 흐름의 "생각 시간 뒤 확정"은 그대로 → 본 측정에서 같은 서명의 EOF 2건
```
무엇이 깨졌나: 원인(긴 휴지 > 서버 유휴 한도 · 클라이언트 한도 없음)이 아니라 증상이 난 경로를 고쳤다.

## 검증 기록
- 2026-11-04: 사건 기록·재현 로그·서버/클라이언트 소스 대조·추상화(Claude 초안) — 서버 기본값(연결 시한 60,000ms를 keep-alive에 씀 · poller 검사 1,000ms)과 Go 재시도 규칙(`shouldRetryRequest`·`isReplayable`)은 해당 버전 소스에서 확인, 수치는 재현 로그(같은 버전 내장 서버 + 같은 부하 도구, 루프백)와 측정 기록에서 옮김. "LB 유휴 한도 < 백엔드 keep-alive" 규칙은 일반 지식.
- 2026-11-04(재측정): 방안 1을 주 흐름(생각 시간 ≥ 50초인 확정 앞 선점)에 적용한 뒤 같은 칸 12회(긴 생각 시간 두 칸 × 두 방식 × 3) 코드 0 · 5xx **0건**(앞 캠페인 같은 자리 12회에서 1건) — 요청 기록 전수 대조. 수치는 회차 기록에서 옮김.

## 방안 비교

같은 원리(닫는 쪽과 다시 쓰는 쪽의 유휴 한도 순서)에 대한 네 방안.

### 방안 1 — 긴 휴지 앞 요청에 `Connection: close` (이 사례의 선택)
```js
if (thinkMs >= SERVER_IDLE_MS - MARGIN_MS) req.params.headers.Connection = 'close';
```

### 방안 2 — 서버 유휴 한도를 클라이언트 최대 휴지보다 길게 (선택하지 않은 방법)
```properties
server.keep-alive-timeout=300s       # 측정 대상 설정을 바꾼다 — 쉬는 연결을 더 오래 쥔다
```

### 방안 3 — 클라이언트 유휴 한도를 서버보다 짧게 (일반 규칙 — 이 사례의 도구에는 손잡이 없음)
```go
tr := &http.Transport{ IdleConnTimeout: 50 * time.Second }   // 서버 60s보다 짧게 → 클라이언트가 먼저 버림
```

### 방안 4 — 비멱등 요청에 멱등 키 (재현에서 0건 확인 — 측정 하네스에는 적용하지 않음)
```js
headers['Idempotency-Key'] = `${session}-${step}`;   // Go가 재사용 연결 실패를 새 연결로 다시 보낸다
// 서버: 같은 키의 두 번째 요청을 한 번만 처리해야 한다(저장·만료·충돌 응답)
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 긴 휴지 앞 close | 휴지 길이를 요청 전에 안다 | 그런 세션마다 연결 수립 1회 | 휴지를 모르는 흐름(사용자 입력 대기)에는 못 쓴다, 문턱이 서버 한도보다 길면 그대로 남는다 | 휴지가 계획된 부하 시나리오 |
| 2. 서버 한도 늘림 | 서버 설정을 바꿀 수 있고, 쉬는 연결 보유가 자원 상한 안이다 | 쉬는 연결 수 × 보유 시간만큼 연결 슬롯·메모리 | 연결 상한에 먼저 닿는다([server-connection-ceiling](../server-connection-ceiling/)), 클라이언트 휴지가 그보다 길면 다시 생긴다 | 클라이언트가 고정이고 연결 수가 적을 때 |
| 3. 클라이언트 한도 짧게 | 클라이언트·중간 장치 한도를 정할 수 있다 | 쉬는 연결의 재사용 이득이 줄어듦 | 중간 장치(프록시·LB)마다 따로 맞춰야 한다 — 한 홉이라도 순서가 뒤집히면 그 홉에서 생긴다 | 운영 경로의 기본값 |
| 4. 멱등 키 | 서버가 키 기반 중복 제거를 한다 | 키 저장·만료·충돌 처리 | 서버가 키를 무시하면 경합이 **이중 처리**로 바뀐다 | 원래 재시도가 필요한 비멱등 API |

**결론**: 운영 경로의 기본은 방안 3이다 — 연결을 다시 쓰는 쪽이 먼저 닫게 홉마다 한도 순서를 맞춘다.\
클라이언트 한도를 못 바꾸는 측정 하네스에서는 측정 대상 설정을 건드리지 않는 방안 1이 맞고, 문턱은 서버 한도 + 검사 간격보다 여유 있게 짧게 둔다.\
방안 4는 경합을 감추는 것이 아니라 재시도를 허용하는 것이므로, 서버의 중복 제거가 먼저 있어야 한다 — 없으면 방안 1·3보다 위험하다.\
검증 기록: 2026-11-04 재현 로그 대조(Claude 초안) — 방안 1·4는 축소판 재현에서 0건 확인, 방안 1은 하네스에 적용, 방안 2·3은 일반 원리(이 사례에서 적용하지 않음).
