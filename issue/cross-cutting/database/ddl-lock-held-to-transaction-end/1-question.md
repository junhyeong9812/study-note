# issue/cross-cutting/database/ddl-lock-held-to-transaction-end — DDL 락은 트랜잭션 끝까지 간다: 마이그레이션 파일 하나가 트랜잭션 하나면 가장 센 락이 가장 긴 문장 동안 유지된다 — 질문

## 질문
1. (왜) 마이그레이션 파일 하나에 `ALTER TABLE … ADD COLUMN …`, 트리거 생성, `CREATE INDEX`가 차례로 있다. 마이그레이션 도구가 파일마다 트랜잭션 하나로 실행하면(PostgreSQL에서 흔한 기본값) 그 테이블의 읽기·쓰기는 언제부터 언제까지 막히나. 문장별 락만 보고 "인덱스 생성은 쓰기만 막는다"고 판단하면 무엇을 놓치나.
2. (예측) `ACCESS EXCLUSIVE`를 아주 잠깐만 쥐는 문장도 운영 중에는 위험하다 — 그 락이 앞의 긴 트랜잭션을 기다리는 동안 뒤에 오는 평범한 읽기는 어떻게 되나. 이를 묶는 설정과 재시도 방법은 무엇인가.
3. (지식) 일반 `CREATE INDEX`와 `CREATE INDEX CONCURRENTLY`의 락 모드는 각각 무엇이고, CONCURRENTLY는 어떤 제약(트랜잭션 블록·소요·실패 시 남는 것)을 갖나.
4. (경계) 짧은 단계(열 추가·트리거)에 쓰려고 세션에 `SET lock_timeout = '2s'`를 걸어 둔 채 같은 세션에서 CONCURRENTLY를 실행하면 무엇이 일어나나. `SET LOCAL`과 `RESET`은 각각 무엇을 막나.
5. (설계) 무거운 단계를 도구 밖에서 따로 실행했다면, 원래 마이그레이션 파일과 도구의 적용 이력은 어떻게 맞추나 — 파일을 비트랜잭션 판으로 바꾸는 방법은 왜 선택하지 않았나. 이력을 기록하기 전에 무엇을 확인해야 하나.
6. (경계) CONCURRENTLY가 끊겨 INVALID 인덱스가 남았다. 어떻게 알아내고 어떻게 처리하나 — 이름만 확인하는 기동 검사는 이 인덱스를 어떻게 판정하나.
7. (측정) 이 사례 규모에서 트랜잭션 안 적용의 막힘은 1초 안팎이었고 결국 그 경로를 골랐다. 이 결과로 말할 수 있는 것과 말할 수 없는 것은 무엇인가.
