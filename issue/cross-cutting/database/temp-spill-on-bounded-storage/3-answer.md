# issue/cross-cutting/database/temp-spill-on-bounded-storage — 정답

태그: `resource-bounding`

## 정답
<!-- 질문 1:1 대응 -->

1. **쿼리의 임시 파일이 데이터와 같은 공간을 썼다.**\
   정합성 검사는 부하가 쌓은 행까지 대상으로 하는 큰 쿼리였고, 그 중간 결과가 작업 메모리를 넘쳐 임시 파일 디렉터리(데이터 디렉터리 아래)에 파일을 썼다.\
   그 순간 "데이터 + 로그 + 임시 파일"이 상한 6GB를 넘었고, 쿼리는 `could not write to file ".../pgsql_tmp/...": No space left on device`로 실패했다.\
   부하 구간에는 그런 쿼리가 없어서 무사했다 — 실패는 데이터가 아니라 **가장 큰 쿼리**가 정한다.
   > **ENOSPC** — 파일 쓰기가 남은 공간 부족으로 실패할 때의 오류(`No space left on device`). 크기 상한이 있는 메모리 파일시스템에서는 디스크 여유와 무관하게 상한에서 난다.

2. **임시 파일로 흘려 쓴다(spill).**\
   정렬·해시 집계·해시 조인이 쓰는 메모리가 세션 작업 메모리 한도(PostgreSQL `work_mem`)를 넘으면, 실행기는 실패하는 대신 넘친 부분을 임시 파일에 쓰고 나눠 처리한다(예: `Sort Method: external merge  Disk: ...kB`).\
   PostgreSQL은 임시 공간을 따로 지정하지 않으면(`temp_tablespaces` 비어 있음) 기본 테이블스페이스 아래 `base/pgsql_tmp`에 이 파일을 만든다 — 즉 데이터 디렉터리 안이다(일반 동작).\
   그래서 데이터 디렉터리의 상한은 데이터 크기가 아니라 **데이터 + 로그 + 동시에 도는 가장 큰 쿼리들의 임시 파일**을 담아야 한다.
   > **spill** — 메모리 작업 공간을 넘친 중간 결과를 디스크(임시 파일)로 내려 처리를 계속하는 것. 오류가 아니라 정상 경로라 평소에는 보이지 않는다.

3. **아니다 — 메모리 한도도 함께 키워야 한다.**\
   메모리 파일시스템의 내용은 메모리에 있다 — 컨테이너 안에 둔 메모리 파일시스템은 그 컨테이너의 메모리 한도 안에서 DB 프로세스 메모리(공유 버퍼·작업 메모리)와 나눠 쓴다(일반 동작).\
   상한만 키우면 공간 부족 대신 메모리 한도 초과(강제 종료)로 실패 지점이 옮겨 갈 수 있다.\
   이 사례는 상한을 12GB로 올리면서 DB 컨테이너 메모리 한도를 8GB → 14GB로 같이 올렸다(기본값은 6GB/8GB 그대로 — 손잡이를 쓰지 않은 기존 조건은 문자열까지 같게 유지).

4. **임시 파일은 쿼리가 도는 동안에만 있기 때문이다.**\
   부하 전·후에 잰 남은 공간은 "데이터가 얼마나 차 있나"만 말한다 — 가장 큰 쿼리가 만든 임시 파일은 그 쿼리가 끝나면 지워지므로, 쿼리 앞의 기록으로는 넘칠지 알 수 없다.\
   "충분했다"를 말하려면 **가장 큰 쿼리가 끝난 뒤**의 남은 공간(그리고 가능하면 쿼리 중 최대 사용량)을 남긴다 — 이 사례는 처음에 정합성 검사 앞에서만 공간을 기록했다가, 검사 뒤 기록을 더했다(12GB에서 끝 검사 뒤 8.8GB 남음).

5. **요청이 적용됐다는 증거가 따로 필요해서다.**\
   크기 손잡이가 어떤 경로에서 무시되거나 다른 값으로 바뀌면, 회차는 여전히 6GB로 돌면서 "12GB로 쟀다"고 기록된다 — 오류가 나지 않는 조건 오염이다.\
   그래서 회차마다 실제로 붙은 크기(마운트 크기·컨테이너 메모리 한도)를 읽어 요청과 대조하고, 다르면 회차를 실패로 표시한다.\
   대조가 실제로 실패할 수 있는지도 먼저 본다 — 6GB로 돈 회차의 실측 값을 12GB 요청과 대조해 불일치가 나는 것을 확인했다(→ [green-masking](../../testing/green-masking/)의 "실패할 수 있었을 때만 증거").

6. **임시 파일 전용 공간 · 임시 파일 크기 상한 — 이 사례에서 쓰지 않은 일반 방법이다.**\
   (a) 임시 공간을 다른 파일시스템(디스크 볼륨)에 두면(`temp_tablespaces`) 데이터 디렉터리 상한은 데이터만 담으면 되지만, 그 쿼리는 디스크 속도로 흘려 쓰게 되고 임시 공간 쪽에도 별도 상한·여유 감시가 필요하다.\
   (b) 프로세스당 임시 파일 크기 상한(`temp_file_limit`)을 두면 공간 전체가 차기 전에 **그 쿼리만** 명확한 오류로 끊는다 — 같은 공간을 쓰는 다른 쓰기(로그·다른 세션)를 지키지만, 큰 쿼리 자체는 여전히 실패한다.\
   어느 쪽이든 먼저 "가장 큰 쿼리가 임시 파일을 얼마나 쓰는가"를 재야 한다(`log_temp_files`·실행 계획의 디스크 사용량).

## 문제 구조 (추상화 코드)

### 변형 A — 데이터 크기로만 잡은 고정 상한 저장 공간
① 문제 구조
```sh
# 실행 프리셋: 데이터 디렉터리를 메모리 파일시스템에 — 크기는 "데이터가 들어가는가"로 정함
docker run --tmpfs /var/lib/db/data:size=6g --memory=8g db-image
seed --rows 8_000_000          # 데이터는 상한 안에 들어감
load --duration 30m            # 부하 구간: 무사
check_consistency              # 누적 행 대상의 큰 쿼리 → 중간 결과 spill → data/.../pgsql_tmp/... ENOSPC → 회차 실패
```
② 고친 구조
```sh
# 크기 손잡이 — 지정하지 않으면 기존 값 그대로(기존 조건의 재현성 유지), 상한 검사 후 산술
SIZE_GB=${PG_STORAGE_GB:-0}                       # 0 = 기존 6g/8g
[ "$SIZE_GB" -ge 0 ] && [ "$SIZE_GB" -le 20 ] || die "size 0..20"
if [ "$SIZE_GB" -gt 0 ]; then TMPFS="${SIZE_GB}g"; MEM="$((SIZE_GB + 2))g"; else TMPFS=6g; MEM=8g; fi
docker run --tmpfs /var/lib/db/data:size=$TMPFS --memory=$MEM db-image
```
무엇이 깨졌나: 고정 상한을 "평소에 차 있는 양"으로 잡아, 일시적으로 가장 많이 쓰는 순간(큰 쿼리의 임시 파일)을 담지 못했다.

### 변형 B — 공간 기록이 큰 작업 앞에만 있고, 적용 값을 대조하지 않음
① 문제 구조
```sh
record_storage > storage-before-check.json      # 끝 검사 "앞" — 임시 파일이 생기기 전
check_consistency
# 요청한 크기가 실제로 붙었는지는 보지 않음 → 손잡이가 무시돼도 "12g로 쟀다"로 기록
```
② 고친 구조
```sh
check_consistency
record_storage > storage-end.json                # 가장 큰 쿼리 "뒤"의 남은 공간 (기록만)
applied=$(container_tmpfs_bytes db)               # 실제 마운트 크기·메모리 한도를 읽음
[ "$applied" = "$((SIZE_GB * 1024**3))" ] || reasons+=("storage-size-mismatch")
# 대조 검증: 6g 회차의 실측 값을 12g 요청과 대조 → mismatch가 나는지 먼저 확인
```
무엇이 깨졌나: "충분했다"와 "요청대로 돌았다"를 둘 다 관측하지 않고 가정했다 — 실패 시점은 기록 시점 뒤에 있었고, 적용 여부는 기록에 없었다.

## 검증 기록
- 2026-10-17: 사건 기록 대조·추상화(Claude 초안) — 질문 2·3·6의 엔진·파일시스템 동작(`temp_tablespaces`·`temp_file_limit`·`log_temp_files`, 메모리 파일시스템의 메모리 한도 계상)은 일반 동작 설명이고 이 사례에서 따로 실험하지 않았다. 변형 A ②·B ②의 코드는 원 구성을 일반화한 형태.

## 방안 비교

같은 원리(고정 상한 저장 공간은 일시적 최대 사용량을 담아야 한다)에 대한 세 가지 처방. 이 사례는 1을 적용했고 2·3은 일반 방법이다.

### 방안 1 — 상한을 키우고 메모리 한도를 함께 올린다 (이 사례에서 적용)
```sh
docker run --tmpfs /var/lib/db/data:size=12g --memory=14g db-image   # 끝 검사 뒤 남은 공간 8.8GB
```

### 방안 2 — 임시 파일을 다른 공간에 둔다 (일반 방법 — 미적용)
```sql
-- 디스크 볼륨에 테이블스페이스를 만들고 임시 파일만 그쪽으로
CREATE TABLESPACE temp_disk LOCATION '/mnt/disk/db-temp';
ALTER SYSTEM SET temp_tablespaces = 'temp_disk';
```

### 방안 3 — 임시 파일 크기에 상한을 둔다 (일반 방법 — 미적용)
```sql
ALTER SYSTEM SET temp_file_limit = '4GB';   -- 넘으면 그 쿼리만 오류, 공간 전체가 차는 것은 막음
ALTER SYSTEM SET log_temp_files = 0;        -- 임시 파일을 쓸 때마다 크기를 기록 (최대 사용량을 잰다)
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 상한 + 메모리 한도 증가 | 호스트 메모리에 여유가 있다, 가장 큰 쿼리의 사용량을 안다 | 메모리 6GB 추가 | 데이터·쿼리가 더 커지면 같은 벽에 다시 닿는다 — 끝 뒤 남은 공간 기록으로 여유를 계속 봐야 함 | 측정 조건(메모리 파일시스템 자체가 처리 변수)을 바꾸지 않아야 할 때 |
| 2. 임시 공간 분리 | 별도 볼륨이 있다 | 볼륨·테이블스페이스 관리 | 큰 쿼리가 디스크 속도로 느려진다, 분리한 공간에도 상한·감시가 필요 | 운영 DB에서 데이터 영역을 임시 파일 폭주로부터 지킬 때 |
| 3. 임시 파일 상한 | 정상 쿼리의 임시 사용량 상한을 안다 | 설정 한 줄 + 사용량 측정 | 상한이 낮으면 정상 큰 쿼리가 실패한다, 여러 세션의 합은 막지 못한다(프로세스 단위) | 공유 공간에서 한 쿼리가 전체를 채우는 것을 막아야 할 때 |

**결론**: 측정 환경처럼 저장 위치 자체가 조건이면 1(상한을 최대 사용량 + 여유로)이 조건을 덜 바꾼다 — 대신 가장 큰 작업 뒤의 남은 공간을 매번 남겨 여유를 관측한다.\
운영 환경이면 2·3이 실패를 국소화한다 — 3은 "한 쿼리가 모두를 망치는 것"을, 2는 "임시 파일이 데이터 영역을 채우는 것"을 막고, 둘 다 먼저 임시 파일 사용량을 재야 상한을 정할 수 있다.\
검증 기록: 2026-10-17 사건 기록 대조·추상화(Claude 초안) — 방안 2·3은 일반 방법(이 사례에서 미적용·미측정).
