# issue/cross-cutting/database/temp-spill-on-bounded-storage — 데이터 디렉터리 용량은 데이터 크기가 아니다: 큰 쿼리의 임시 파일이 같은 공간을 쓴다 — 질문

## 질문
1. (왜) DB 데이터 디렉터리를 크기 상한 6GB인 메모리 파일시스템에 두고 800만 행을 시드한 뒤 30분 부하를 걸었다. 부하 구간은 무사했는데, 부하가 끝난 약 25초 뒤 도는 큰 정합성 검사 쿼리가 `No space left on device`로 실패했다. 데이터는 상한 안에 들어갔는데 무엇이 공간을 넘쳤나.
2. (예측) 정렬·해시 집계가 세션의 작업 메모리 한도를 넘으면 실행기는 무엇을 하는가. 그 파일은 따로 지정하지 않으면 어디에 생기는가 — 그래서 데이터 디렉터리의 크기 상한은 무엇까지 담아야 하는가.
3. (경계) 메모리 파일시스템의 상한만 키우면 끝인가. 그 공간의 내용은 어디에 잡히며, 컨테이너 메모리 한도와는 어떤 관계인가.
4. (연결) 남은 공간을 정합성 검사 쿼리 **전에만** 기록하면 왜 이 실패를 예측하지 못하는가. 공간을 언제 재야 "충분했다"를 말할 수 있는가.
5. (경계) 실행 옵션으로 저장 공간 크기를 바꿀 수 있게 했다. 요청한 크기와 실제로 붙은 크기를 왜 따로 대조해야 하며, 그 대조 자체가 동작하는지는 어떻게 확인하는가.
6. (방안) 상한을 키우는 것 말고 임시 파일을 다루는 방법 두 가지(임시 파일을 다른 공간에 두기 · 임시 파일 크기에 상한 두기)는 각각 무엇을 바꾸고, 어떤 실패 모드를 남기는가.
