# issue/cross-cutting/database/temp-spill-on-bounded-storage — 정리 (힌트)

## 전체 흐름

```
메모리 파일시스템 (상한 6GB) = DB 데이터 디렉터리
 ├─ 테이블·인덱스 ── 시드 800만 행 + 30분 부하가 쌓은 행
 ├─ 로그(WAL)
 └─ 임시 파일 디렉터리 ── 작업 메모리를 넘친 정렬·해시 (쿼리가 도는 동안만 존재)

시간 ──────────────────────────────────────────────────────────────▶
 [시드] [부하 30분 ............................] [끝 검사: 전체 집계 쿼리]
   남은 공간 기록 ✓ (여기서만 잼)                      │ 약 25초 뒤
                                                       ▼
                                   임시 파일 + 데이터 > 상한 → ENOSPC → 쿼리 실패 → 회차 실패
 부하 구간 지표는 오류 전에 끝나 있음 (꼬리 지표는 쓸 수 있음, 정합성 판정은 없음)

[고친 것]
  상한 6GB → 12GB, 컨테이너 메모리 한도도 함께 (8GB → 14GB — 메모리 파일시스템 내용은 메모리다)
  가장 큰 쿼리 "뒤"의 남은 공간 기록 (12GB에서 끝 검사 뒤 8.8GB 남음)
  요청 크기 ↔ 실제 붙은 크기 대조 (다르면 회차 실패) — 일부러 다른 값을 넣어 대조가 실패하는지 확인
```

## 핵심 문장

- DB 데이터 디렉터리가 담는 것은 데이터만이 아니다 — 작업 메모리를 넘친 **정렬·해시 임시 파일**도 (따로 지정하지 않으면) 그 아래에 생긴다.
- 임시 파일은 쿼리가 도는 동안만 있다 — 부하 전·후의 "남은 공간"으로는 보이지 않고, **가장 큰 쿼리가 도는 순간**에 상한을 넘는다.
- 크기 상한이 고정인 저장 공간(메모리 파일시스템·작은 볼륨)은 "데이터 크기 + 가장 큰 쿼리의 임시 파일 + 로그"로 잡는다.
- 메모리 파일시스템의 내용은 메모리다 — 상한을 키우면 그 프로세스가 속한 메모리 한도도 함께 키워야 한다.
- 공간 기록은 가장 큰 작업 **뒤**에 둔다 — 그래야 "충분했다"가 관측이 된다.
- 설정 손잡이를 더했으면 요청 값과 적용 값을 대조하고, 그 대조가 실패할 수 있는지(다른 값으로) 먼저 확인한다.
