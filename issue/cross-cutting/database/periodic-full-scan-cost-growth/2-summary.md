# issue/cross-cutting/database/periodic-full-scan-cost-growth — 정리 (힌트)

## 전체 흐름

```
부하가 행을 쌓는다: 누적 쌍 N ↑
                     │
[앱 안 스케줄러] fixed delay 60초
  바퀴 = 전체 훑기(청크 단위) — 일 ∝ N
  T(N): 395만 쌍 14.0초 → 526만 20.6초 → 766만 25.4초
  주기 = 60 + T(N) (실측 시작 간격 74~80초)
  대조 중 비율 = T / (60 + T) : 14초 → 약 19% · 25초 → 약 29%
                     │ 같은 앱 풀 · 같은 DB
                     ▼
  바퀴 동안 DB 컨테이너 CPU 338~384% / 한도 400%
  요청: '서버 응답 대기'만 늘어난 느린 초 (최대 135~206ms)  ← 꼬리 튐
                     │
  7분 측정  : N 작음 → T 작음 → p99 +2.2% (보이지 않음)
  30분 측정 : 약 17~20분 뒤부터 몰림 — 후반 76개 중 72개가 바퀴 안 (×3.1)
  약 460만 쌍: 청크당 12 → 15.3ms 단절 + 병렬 쿼리 대기 첫 등장 (계획 전환 정황, 이유 미확인)

[원인 확정 — 켜고 끄기]
  켬(앞선 6회) 느린 초 12~15 → 끔 1 → 켬 12 (그중 9가 바퀴 안, 기대 2.7의 3.4배)
  1초 p99 최대 50.6ms(끔) ↔ 97.6ms(켬)   한계: 조건마다 1회 · 끔→켬 순서 고정

[대처 후보 — 작은 것부터, 미적용]
  ① 별도 대조 앱(자기 풀)   → 풀 대기 제거, DB CPU 비용은 그대로 → 병목이 풀인지 CPU인지 가른다
  ② 증분 대조 + 드문 전체 훑기 → 일 ∝ 변경 수, 바뀌지 않은 쌍의 어긋남은 안전망만 본다
  ③ 복제본에서 탐지, 원본에서 복구 → 원본 CPU를 비움, 복제 지연·VACUUM 충돌·서버 2대
  ④ CDC/메시지로 바뀐 쌍 전달 → 앱 밖 변경까지, 이중 쓰기 문제·인프라 비용
```

## 핵심 문장

- 매 바퀴 **전체를 훑는** 주기 작업의 비용은 누적 행 수에 비례해 자란다 — 오늘 싸 보이는 작업이 데이터가 쌓이면 꼬리를 만든다.
- fixed delay 스케줄은 바퀴가 길어질수록 **쉬는 비율이 줄어** DB를 대조에 쓰는 시간 비율이 커진다 — 주기 자체가 행 수의 함수다.
- 짧은 측정은 이 성장을 보지 못한다 — 배경 작업의 영향은 **목표 규모의 행 수·실행 시간**에서 잰다.
- 같은 풀·같은 DB를 쓰는 배경 작업은 요청 경로와 자원을 나눈다 — 병목이 DB CPU인지 풀 대기인지는 풀을 떼어 보는 실험으로 가른다.
- 시각 일치(겹침 배수)는 후보까지다 — 켜고 끄기(있음 → 없앰 → 되돌림)로 원인을 확정한다.
- 비용은 선형으로만 자라지 않는다 — 규모 문턱에서 실행 계획이 바뀌면 끊기듯 오른다.
- 증분 대조는 바뀐 것만 보므로, 바뀌지 않은 곳의 어긋남(직접 수정·정리 작업)을 위한 드문 전체 훑기를 안전망으로 남긴다.
