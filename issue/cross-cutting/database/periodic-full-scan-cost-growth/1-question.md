# issue/cross-cutting/database/periodic-full-scan-cost-growth — 매 바퀴 전체를 훑는 주기 작업의 비용은 누적 행 수에 비례한다: 짧은 측정은 그것을 숨긴다 — 질문

## 질문
1. (왜) 원본 행에서 다시 센 값과 사본(카운터)을 대조하는 작업이 앱 안 스케줄러로 "끝나고 60초 뒤 다음 바퀴"로 돈다. 7분 측정에서는 요청 p99 영향이 +2.2%였는데, 30분 측정에서는 약 17~20분 뒤부터 서버 쪽 꼬리 튐이 몰려 나왔다. 무엇이 시간에 따라 달라졌나.
2. (예측) 바퀴 시간 T가 누적 행 수에 비례해 자란다. 끝난 뒤 60초를 쉬는 스케줄(fixed delay)에서 주기와 "DB가 대조 중인 시간 비율"은 T = 14초일 때와 25초일 때 각각 얼마인가. 시작 기준 스케줄(fixed rate)이었다면 무엇이 달라지는가.
3. (경계) 후반 느린 초 76개 중 72개가 대조 바퀴 진행 중이었다(우연 기대 23.2개의 3.1배, 6회 모두). 이것만으로 "대조가 원인"이라고 말할 수 있는가. 무엇을 더 해야 하며, 이 사례는 무엇을 했나.
4. (연결) 대조 바퀴가 요청 처리와 같은 앱의 커넥션 풀·같은 DB를 쓴다. 꼬리가 튀는 경로는 무엇이 될 수 있나 — DB CPU 포화와 풀 대기를 어떻게 가르는가.
5. (경계) 약 460만 쌍 부근에서 청크당 시간이 약 12 → 15.3ms로 끊기듯 오르고, 병렬 쿼리 대기가 처음 나타났다. "비용 ∝ 행 수"라는 선형 모형만으로 규모 한계를 예측하면 무엇을 놓치는가.
6. (방안) 별도 대조 앱(자기 풀) · 증분 대조 · 읽기 복제본 탐지 · 변경 이벤트(CDC/메시지) 전달은 각각 무엇을 줄이고 무엇을 새로 떠안는가. 증분 대조만 두면 놓치는 어긋남은 무엇인가.
