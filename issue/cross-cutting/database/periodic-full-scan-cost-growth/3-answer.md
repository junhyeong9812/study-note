# issue/cross-cutting/database/periodic-full-scan-cost-growth — 정답

태그: `resource-bounding`

## 정답
<!-- 질문 1:1 대응 -->

1. **누적 행 수가 달라졌다 — 대조 바퀴의 일이 그 수에 비례한다.**\
   대조는 매 바퀴 모든 쌍을 청크 단위로 훑어 원본에서 다시 센 값과 사본을 비교한다 — 일의 양이 "바뀐 것"이 아니라 "쌓인 것"에 비례한다.\
   7분 회차는 쌓인 행이 적어 바퀴가 짧았고, 30분 회차는 부하가 행을 계속 쌓아 바퀴가 14초 → 26초 안팎으로 길어졌다(395만 쌍 14.0초 → 526만 20.6초, 마지막 766만 25.4초).\
   바퀴 동안 DB 컨테이너 CPU가 한도 400% 중 338~384%였고, 그 시간에 요청의 '서버 응답 대기'가 늘어난 느린 초(최대 135~206ms)가 몰렸다 — 약 400~460만 쌍을 넘는 시점이 대략 17~20분 뒤였다.\
   기각한 후보: 체크포인트(겹침 배수 0.92)·autovacuum(0.73)·DB 메모리·JVM 정지(최대 0.05ms)·호스트 CPU 포화.
   > **비정규화 카운터 대조** — 원본 행에서 다시 센 값과 따로 저장한 카운터를 비교해 어긋남을 찾고 고치는 작업. 왜 필요한지는 [denormalized-counter-drift](../../data/denormalized-counter-drift/).

2. **주기 = 60 + T, 대조 중 비율 = T / (60 + T).**\
   T = 14초면 주기 74초·약 19%, T = 25초면 주기 85초·약 29%다(실측 시작 간격 74~80초) — 바퀴가 길어질수록 쉬는 비율이 줄어, DB가 대조에 쓰는 시간 몫이 행 수와 함께 커진다.\
   fixed delay는 바퀴가 겹치지 않는 대신 주기가 늘어나고, 시작 시각 기준(fixed rate, 예: 60초)이었다면 T가 주기에 다가갈수록 다음 바퀴가 곧바로 이어 붙어 쉬는 시간이 0에 가까워진다(Java `ScheduledExecutorService`는 같은 작업을 동시에 돌리지 않고 늦게 시작한다 — 일반 동작).\
   어느 쪽이든 "바퀴 시간이 행 수에 비례"하는 한 배경 작업의 점유율은 데이터와 함께 자란다.
   > **fixed delay / fixed rate** — 앞 실행이 **끝난** 시각부터 지연을 재는 스케줄 / 앞 실행이 **시작한** 시각부터 주기를 재는 스케줄.

3. **아니다 — 시각 일치는 후보까지다. 켜고 끄기로 확정했다.**\
   겹침 배수는 "바퀴 동안 자주 튄다"를 말할 뿐, 같은 시각에 함께 도는 다른 무언가(바퀴와 같이 오는 다른 작업)를 배제하지 못한다.\
   이 사례는 대조만 끈 조건을 1회 더 돌렸다 — 끔: 느린 초 1(체크포인트 끝과 겹친 1개) · 켬: 12(서버형 10, 그중 9가 바퀴 안 — 우연 기대 2.7의 3.4배) · 1초 p99 최대 50.6 대 97.6ms.\
   앞선 켬 6회(느린 초 12~15)가 기준선이 되어 "있음 → 없앰 → 되돌림"이 성립했다.\
   한계: 조건마다 1회, 끔 → 켬 순서 고정이라 순서 효과는 가르지 않았다(기준선 6회는 저장 공간 크기가 달라 모양 비교로만 썼다).

4. **DB CPU를 나눠 쓰는 경로와 풀 연결을 기다리는 경로 둘 다다.**\
   대조 쿼리가 DB CPU를 채우면 요청 쿼리가 느려지고, 대조가 앱 풀의 연결을 오래 쥐면 요청이 연결을 기다린다 — 둘 다 클라이언트에는 '서버 응답 대기'로 보인다.\
   이 사례에서 풀 대기 표본은 느린 초 근처에서만 늘었다(원인이 아니라 결과일 수 있다) — 둘을 가르는 실험은 대조를 **자기 풀을 가진 별도 앱**으로 옮겨 같은 규모로 재는 것이다.\
   이전 디스크 측정에서 별도 앱은 바퀴 최대 약 4초, 앱 안 대조는 풀 대기를 포함해 94초였다 — 이번 30분 측정에서는 아직 가르지 않았다.

5. **규모 문턱에서의 계획 전환을 놓친다.**\
   약 460만 쌍에서 행 없음 갈래의 청크당 시간이 약 12 → 15.3ms로 끊기듯 올랐고 병렬 쿼리 대기 표본이 처음 나타났다(6회 모두 같은 바퀴) — 실행 계획이 규모에 따라 바뀐 정황이다(계획 내용·전환 이유는 확인하지 않았다).\
   선형 외삽("7분에 +2.2%면 30분에도 작다")은 이런 문턱을 담지 못한다 — 목표 규모의 행 수에서 직접 재고, 바퀴마다 시간·대상 수를 기록해 꺾이는 지점을 본다.

6. **각 방안은 줄이는 자원과 새 실패 모드가 다르다 — 아래 방안 비교.**\
   증분 대조만 두면 "바뀐 쌍"으로 알려지지 않은 어긋남 — DB 직접 수정, 정리 작업처럼 앱 밖에서 생긴 어긋남 — 을 보지 못한다. 그래서 드문 전체 훑기를 안전망으로 남긴다.

## 문제 구조 (추상화 코드)

### 변형 A — 매 바퀴 전체 훑기 + 요청과 같은 풀
① 문제 구조
```kotlin
scheduler.scheduleWithFixedDelay({ reconcileAll() }, 0, 60, SECONDS)   // 끝난 뒤 60초 — 주기 = 60 + 바퀴 시간
fun reconcileAll() {                                     // 앱 풀(요청과 공유)·같은 DB
    for (chunk in allPairKeys().chunked(CHUNK)) {         // 전체 훑기 — 일 ∝ 누적 쌍 수
        val drift = db.query(DRIFT_SQL, chunk)             // 원본에서 다시 센 값 vs 카운터
        drift.forEach { repair(it) }                       // 원본에서 잠근 뒤 다시 세어 고침
    }
}
// 7분: 쌍 수 작음 → 바퀴 짧음 → 안 보임 / 30분: 바퀴 14 → 26초 안팎, DB CPU 338~384%/400% → 요청 꼬리 튐
```
② 이 사례의 처리 (측정 쪽 — 대조 자체는 고치지 않음)
```text
기록: 바퀴마다 시작·끝 시각·대상 쌍 수 → 느린 초와의 겹침 배수(우연 기대 대비)
확정: 켬(6회) → 끔(1회) → 켬(1회) — 느린 초 12~15 → 1 → 12
해석 규칙: 15분이 넘거나 행이 수백만인 측정은 대조 바퀴가 꼬리에 섞인다는 전제로 읽고,
           주제가 대조가 아니면 바퀴 시각을 함께 기록·대조한다
```
무엇이 깨졌나: 규모가 작은 짧은 측정으로 "비용이 작다"를 판정해, 일이 누적 행 수에 비례하는 배경 작업이 목표 규모에서 요청과 자원을 다툰다는 것을 보지 못했다.

## 방안 비교

같은 원리(배경 대조의 일이 쌓인 양에 비례하고 요청과 자원을 나눈다)에 대한 대처 후보 — 작은 것부터. **모두 이 사례에서 구현하지 않았다.**

### 방안 1 — 별도 대조 앱(자기 풀)으로 옮긴다
```text
reconciler-app: own pool(size small) → same DB
효과: 요청 풀 대기 제거 / DB CPU 비용은 그대로 → 30분 측정으로 병목이 풀인지 CPU인지 가른다
```

### 방안 2 — 증분 대조 + 드문 전체 훑기
```kotlin
every(1.seconds) { reconcile(changedPairsSince(cursor)) }   // 일 ∝ 변경 수
every(rarely)    { reconcileAll() }                          // 안전망: 바뀌지 않은 쌍의 어긋남(직접 수정·정리 작업)
// 설계 때 정할 것: 바뀐 쌍을 아는 방법(앱 메모리 집합 · 증가 id 기준점 · updated_at), 커밋 순서·창 겹침
```

### 방안 3 — 읽기 복제본에서 탐지, 원본에서 복구
```text
detect on replica  → candidate pairs
repair on primary  → lock + recount (복제 지연으로 생긴 오탐은 다시 세기가 거른다)
주의: 복제본의 긴 쿼리 vs 원본 VACUUM 충돌 — hot_standby_feedback을 켜면 원본이 부푼다
      복제본은 원본과 다른 CPU에 있어야 부하가 나뉜다(서버 2대)
```

### 방안 4 — CDC/메시지로 바뀐 쌍을 전달
```text
DB change log ─CDC─▶ topic ─▶ reconciler   (또는 앱이 outbox 행을 같은 트랜잭션에 쓰고 중계)
담는 것: 앱 재시작·여러 앱·앱 밖 DB 변경
대가: 이중 쓰기 문제(직접 발행은 커밋과 어긋남 → outbox 또는 CDC), 브로커·커넥터 운영
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 별도 앱 | 병목의 큰 몫이 풀 대기다 | 앱 하나·배포 단위 추가 | 병목이 DB CPU면 꼬리는 그대로 — 풀만 옮긴 셈 | 먼저 병목을 가를 때(가장 작은 실험) |
| 2. 증분 + 안전망 | 바뀐 쌍을 빠짐없이 알 수 있다, 변경률 ≪ 누적 수 | 변경 추적·커서·창 겹침 설계 | 추적 경로 밖 어긋남은 안전망 주기까지 남는다, 커밋 순서를 잘못 잡으면 바뀐 쌍을 건너뛴다 | 누적은 크고 변경은 작은 일반적 경우 |
| 3. 복제본 탐지 | 복제본이 다른 하드웨어에 있다 | 서버 추가·복제 운영 | 복제 지연 오탐(다시 세기로 흡수), 긴 쿼리 취소 또는 원본 팽창 | 전체 훑기를 유지해야 하고 하드웨어가 있을 때 |
| 4. CDC/메시지 | 브로커·커넥터를 운영할 수 있다 | 인프라·이중 쓰기 대책 | 파이프라인 지연·유실 시 대조 누락 — 그 자체를 감시해야 함 | 여러 쓰기 주체·앱 밖 변경까지 잡아야 할 때 |

**결론**: 먼저 1로 병목(풀 대기 대 DB CPU)을 가른다 — 그 답에 따라 풀 분리로 끝날지, 일 자체를 줄여야(2) 할지가 갈린다.\
일을 줄이는 기본은 2이고, 전체 훑기를 버릴 수 없거나 앱 밖 변경이 많으면 3·4가 맞다 — 3은 하드웨어를, 4는 운영 복잡도를 비용으로 낸다.\
어느 방안이든 "목표 규모의 행 수·실행 시간에서 다시 잰다"가 판정 조건이다 — 이 사례의 교훈 자체가 짧은 측정이 이 비용을 숨겼다는 것이다.\
검증 기록: 2026-10-17 사건 기록 대조·추상화(Claude 초안) — 방안 1~4는 원 기록이 다음 결정으로 넘긴 후보(미구현·미측정).
