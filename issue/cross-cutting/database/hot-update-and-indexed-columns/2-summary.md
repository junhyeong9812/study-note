# issue/cross-cutting/database/hot-update-and-indexed-columns — 정리 (힌트)

## 전체 흐름

```text
[HOT 갱신이 되는 조건]
  UPDATE row
    ├─ 인덱스가 걸린 열이 하나도 안 바뀜   (PG16+: 요약 인덱스(BRIN)만 바뀌면 예외적으로 허용)
    └─ 새 버전이 같은 페이지에 들어갈 자리가 있음
         ▼ 둘 다 참
    HOT: 새 버전을 같은 페이지에 체인으로 붙임 → 인덱스는 손대지 않음

[이 설계]
  cnt 갱신 ── BEFORE UPDATE 트리거 ── updated_at := now()   ← 인덱스 열이 "매번" 바뀜
                                         ▼
  HOT 불가 → 새 버전 + PK 인덱스 새 항목 + updated_at 인덱스 새 항목 (갱신마다)

[대안 — 선택하지 않은 방법]
  BRIN(updated_at) : HOT은 살지만, 제자리 갱신된 행이 페이지에 남아
                     페이지마다 범위가 [오래된 값, 지금]으로 넓어짐 → "최근 창" 조회가 거의 모든 페이지를 읽음
  인덱스 없음      : 틱마다 수백만 행 순차 읽기

[측정]
  pg_stat_user_tables.n_tup_upd · n_tup_hot_upd  (부하 직전 · 회차 끝 차분)
  + 인덱스 크기
  결과: 트리거 셀 쿼터 UPDATE 약 2,400건 중 HOT 0건 · 경합 셀 100건 중 0~1건
        선점 p99: 대조군(열·인덱스 없음) 대비 나빠지지 않음 (범위 겹침)
  못 한 것: 인덱스 없는 HOT 비율 직접 비교 · 같은 행에 초당 수천 건 UPDATE가 몰리는 부하
```

## 핵심 문장

- HOT 갱신은 **인덱스 열이 안 바뀌고** 같은 페이지에 자리가 있을 때만 일어난다 — 그때는 인덱스를 고치지 않는다.
- "갱신 시각" 같은 변경 추적 열은 정의상 **갱신마다 바뀐다** — 거기에 B-tree 인덱스를 걸면 그 테이블의 HOT은 사실상 0이 된다.
- HOT이 사라지면 갱신마다 **모든 인덱스**(변경 추적 열과 무관한 PK까지)에 새 항목이 생긴다.
- BRIN은 HOT을 살리지만(PG16+) 제자리 갱신되는 테이블에서는 페이지별 범위가 넓어져 "최근 창" 조회를 거르지 못한다.
- 측정에서 HOT 0%와 지연 무영향이 함께 나와도, 그 결론은 **잰 부하**까지다 — 같은 행에 갱신이 몰리는 부하는 따로 재야 한다.
- 변경 추적 열·인덱스를 기본으로 켜면 HOT 손실은 **운영 위험으로 기록**한다 — 큰 테이블의 인덱스 생성이 쓰기를 막는 것도 함께.
