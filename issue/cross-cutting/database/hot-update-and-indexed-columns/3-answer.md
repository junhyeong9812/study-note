## 정답
<!-- 질문 1:1 대응 -->

1. **HOT은 "인덱스 열이 안 바뀐 갱신"에만 일어나는데, 이 열은 매번 바뀐다.**\
   PostgreSQL은 UPDATE마다 행의 새 버전을 만든다 — 이때 인덱스가 걸린 열이 하나도 바뀌지 않고 같은 페이지에 새 버전이 들어갈 자리가 있으면, 새 버전을 같은 페이지 안에 체인으로 붙이고 인덱스는 고치지 않는다(HOT).\
   이 설계는 모든 UPDATE에서 트리거가 `updated_at := now()`를 쓰고, 그 열에 B-tree 인덱스가 있다 — 카운터 값만 바꾸는 갱신도 인덱스 열을 바꾸므로 HOT 조건이 거의 늘 깨진다.\
   설계 단계에서 이것을 비용으로 추론해 두고(쓰기 경로의 선점 지연에 대한 가설), 측정으로 확인하는 항목에 넣었다.
   > **HOT(Heap-Only Tuple)** — 인덱스 열이 바뀌지 않은 UPDATE에서 새 행 버전을 같은 힙 페이지에 두고 인덱스 항목을 만들지 않는 PostgreSQL의 갱신 방식. 페이지 안 정리(pruning)로 죽은 버전도 빨리 회수된다.

2. **갱신마다 모든 인덱스에 새 항목이 생긴다.**\
   HOT이 아니면 새 행 버전을 가리키는 항목을 **테이블의 모든 인덱스**에 넣는다 — 바뀐 열과 무관한 PK 인덱스에도 넣는다.\
   PK 하나뿐이던 테이블에 `updated_at` 인덱스를 더하면, 갱신 한 번이 힙 새 버전 + 인덱스 항목 2개를 만든다(이전에는 HOT이면 0개).\
   죽은 인덱스 항목은 vacuum이 치울 때까지 남아 인덱스 크기도 함께 자란다 — 그래서 측정에서 인덱스 크기를 함께 기록했다.

3. **BRIN은 범위가 넓어져 거르지 못하고, 인덱스 없음은 매번 전체를 읽는다.**\
   PostgreSQL 16부터는 갱신이 바꾼 인덱스 열이 요약 인덱스(BRIN)에만 걸려 있으면 HOT을 허용한다 — HOT은 살릴 수 있다.\
   그러나 BRIN은 페이지 묶음마다 값의 최소·최대만 기억한다 — 카운터 행은 제자리(같은 페이지)에서 계속 갱신되므로 한 페이지에 오래된 시각의 행과 방금 갱신된 행이 섞이고, 페이지마다 범위가 [오래된 값, 지금]으로 넓어진다.\
   "최근 몇 초 안에 바뀐 행" 조회가 거의 모든 페이지를 후보로 읽게 되어 인덱스의 목적(최근 창만 읽기)을 잃는다 — 그래서 선택하지 않았다.\
   인덱스를 아예 두지 않으면 대조 틱마다 수백만 행을 순차로 읽어야 해서 역시 선택하지 않았다.
   > **BRIN(Block Range INdex)** — 연속된 페이지 묶음마다 열 값의 요약(최소·최대)만 저장하는 작은 인덱스. 값이 물리 순서와 함께 늘어나는(추가 위주) 테이블에서만 잘 거른다.

4. **`pg_stat_user_tables`의 갱신·HOT 누적 카운터를 구간 양끝에서 읽는다.**\
   `n_tup_upd`(갱신 수)와 `n_tup_hot_upd`(그중 HOT)는 통계가 초기화되기 전까지 누적값이라, 부하 직전과 회차 끝에 읽어 차분을 내야 **그 구간의** 비율이 된다(시드·기동 중 갱신이 섞이지 않게).\
   결과: 쿼터 UPDATE가 생기는 부하에서 트리거 셀의 갱신 약 2,400건 중 HOT 0건(0%), 같은 행에 갱신이 몰리는 경합 셀은 100건 중 0~1건이었다(이전 캠페인에서도 2.7~3.4%로 낮았다).\
   다만 대조군 셀에는 그 열·인덱스가 없어 HOT 표본을 남기지 않았다 — "인덱스 때문에 HOT이 사라진다"는 추론과 **일치**하는 관측이지, 인덱스 없는 HOT 비율과 직접 비교한 값은 없다.
   > **n_tup_hot_upd** — 테이블별 통계 뷰의 HOT 갱신 누적 수. `n_tup_upd` 대비 비율이 그 테이블의 HOT 비율이다.

5. **잰 부하가 갱신 경로 비용을 크게 드러내지 않는 부하였기 때문이다.**\
   판정 규칙은 측정 전에 고정했다: 같은 캠페인의 대조군(변경 추적 없음) 대비 선점 p99 중앙값 +10% 이내.\
   결과는 두 부하 모두 대조군보다 낮았다(−1.9% · −26.8%) — 그러나 앞 부하의 갱신은 초당 약 2.4건이라 갱신 비용이 p99에 드러나기 어렵고, 뒤 부하는 짧은 경합이라 회차 사이 범위가 겹친다 — "나빠지지 않았다"로만 읽는다.\
   같은 행에 초당 수천 건 UPDATE가 몰리는 부하(한 사용자의 반복 선점·취소 등)는 재지 않았다 — HOT 손실의 비용(인덱스 항목·vacuum 부담)은 그런 부하에서 다시 재야 한다.

6. **큰 테이블의 인덱스 생성은 쓰기를 막는다.**\
   기본값으로 이 열·인덱스를 켜면 기존 DB에 처음 올릴 때 `CREATE INDEX`가 돈다 — 일반 `CREATE INDEX`는 생성 동안 그 테이블의 쓰기를 막는다(`CONCURRENTLY`는 쓰기를 막지 않지만 트랜잭션 안에서 못 돌고 더 느리다 — 별도 작업으로 넘겼다).\
   그래서 운영 위험 목록에 "이후 갱신의 HOT이 사라진다(측정 부하에서 지연 영향 없음)"와 "처음 적용 시 인덱스 생성이 쓰기를 막는다"를 함께 적었다.

## 문제 구조 (추상화 코드)

### 변형 A — 변경 추적 열 + B-tree 인덱스
① 문제 코드 (설계 그대로 — 비용이 생기는 구조)
```sql
ALTER TABLE counter ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now();
CREATE INDEX idx_counter_updated_at ON counter (updated_at);      -- B-tree

CREATE FUNCTION touch() RETURNS trigger AS $$
BEGIN NEW.updated_at := now(); RETURN NEW; END $$ LANGUAGE plpgsql;
CREATE TRIGGER counter_touch BEFORE UPDATE ON counter FOR EACH ROW EXECUTE FUNCTION touch();

UPDATE counter SET cnt = cnt + 1 WHERE id = $1;   -- 인덱스 열(updated_at)이 바뀜 → HOT 불가 → PK·updated_at 인덱스 모두 새 항목
SELECT id FROM counter WHERE updated_at >= now() - interval '2 seconds';   -- 이 조회를 위해 인덱스가 필요
```
② 대처 (설계는 유지 — 비용을 재고 기록)
```sql
-- 구간 양끝에서 읽어 차분
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'counter';
SELECT pg_relation_size('idx_counter_updated_at');
-- 판정(측정 전 고정): 대조군 대비 선점 p99 중앙값 +10% 이내 → 성립
-- 기록: HOT 손실(측정 부하에서 지연 영향 없음) · 큰 테이블 첫 적용 시 인덱스 생성이 쓰기를 막음
```
무엇이 깨졌나: 변경 추적 열은 정의상 갱신마다 바뀌므로, 그 열의 인덱스가 HOT의 전제(인덱스 열 불변)를 매번 깬다.

## 방안 비교

"최근 몇 초 안에 바뀐 행"을 싸게 찾는다는 같은 목표에 대한 세 방안. 이 사례는 1을 적용했고 2·3은 설계 단계에서 선택하지 않은 방법이다(측정하지 않음).

### 방안 1 — B-tree 인덱스 (이 사례에서 적용)
```sql
CREATE INDEX ON counter (updated_at);              -- 최근 창만 읽음 · 갱신마다 HOT 손실
```

### 방안 2 — BRIN 인덱스 (선택하지 않은 방법)
```sql
CREATE INDEX ON counter USING brin (updated_at);   -- PG16+: HOT 유지 · 제자리 갱신이면 페이지 범위가 넓어짐
```

### 방안 3 — 인덱스 없음 (선택하지 않은 방법)
```sql
SELECT id FROM counter WHERE updated_at >= $1;     -- HOT 유지 · 틱마다 전체 순차 읽기
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. B-tree | 갱신 경로의 추가 인덱스 쓰기를 감당할 여유가 있다 | 갱신마다 모든 인덱스에 새 항목 · 인덱스 팽창 · vacuum 부담 | 같은 행에 갱신이 몰리는 부하에서 쓰기 지연이 커질 수 있다(이 사례는 미측정) | 최근 창 조회가 자주(초 단위) 돌고, 측정한 부하에서 갱신 비용이 허용선 안일 때 |
| 2. BRIN | 값이 물리 순서와 함께 늘어난다(추가 위주) · PG16+ | 작은 인덱스 · HOT 유지 | 제자리 갱신되는 행이 많으면 페이지 범위가 넓어져 조회가 거의 전체를 읽는다 | 새 행 추가 위주(로그·이벤트)로 최근 행이 뒤쪽 페이지에 모이는 테이블 |
| 3. 인덱스 없음 | 테이블이 작거나 조회가 드물다 | 갱신 비용 없음 | 행 수에 비례하는 순차 읽기가 조회마다 반복된다 | 수만 행 이하이거나 조회 주기가 길 때 |

**결론**: 행이 제자리에서 갱신되는 테이블에서는 BRIN이 "최근 창"을 거르지 못하므로, 초 단위로 최근 창을 읽어야 하면 B-tree의 HOT 손실을 비용으로 받아들이고 **재서** 판정하는 쪽이 맞았다.\
그 판정은 잰 부하(초당 수 건 갱신 · 짧은 경합)까지다 — 같은 행에 갱신이 몰리는 부하로 넓히려면 그 부하에서 HOT 손실의 비용을 다시 잰다.\
