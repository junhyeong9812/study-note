# issue/cross-cutting/database/write-back-out-of-order-eviction — 정리 (힌트)

## 전체 흐름

```text
[할당 순서 ≠ 쓰기 순서]
  allocate() → 5   (번호만, 디스크 I/O 없음 · 프레임에 dirty로 상주)
  allocate() → 6   (〃)
        │
        ▼  프레임 부족 → 교체 정책(LRU)이 희생자를 고름
  evict(6) → write(6)      ← 6이 먼저 나감
        │
        ▼
  저장소: page_count = 5   ("끝에만 붙이기": 허용 = 0..=5)
        └─ write(6) = 구멍 → 거부 ❌  (5는 아직 디스크에 없음)

[고친 계약 — 역할을 둘로 나눔]
  저장소: write(id ≥ page_count) → id + 1장으로 성장, 사이 페이지 = 0
          page_count = max(page_count, id + 1)
  할당기: write(id ≥ next) → "not allocated" 거부   ← 잘못된 번호는 여기서 막음
        │
        ▼
  evict(6) → write(6) ✅ (5 자리는 0으로 채워짐)
  evict(5) → write(5) ✅ (0 페이지를 덮어씀)

[선택하지 않은 방법]
  allocate() 때 0 페이지를 즉시 write
     → 구멍은 안 생기지만 새 페이지마다 쓰기 +1
     → 분할마다 I/O가 늘어 측정이 왜곡됨
```

## 핵심 문장

- write-back 캐시가 디스크에 쓰는 순서는 할당 순서가 아니라 **교체 정책**이 정한다.
- "끝에만 붙이기"는 순차 쓰기를 전제한 계약이다 — 캐시를 얹는 순간 그 전제가 사라진다.
- 고친 방법: 저장소는 끝 뒤 쓰기를 **0으로 채워 성장**시키고, "할당된 번호인가"는 **할당기가 따로** 지킨다 — 한 계층이 두 불변식을 다 지키려 하지 않는다.
- 구멍을 미리 메우는 쓰기(할당 즉시 0 페이지)는 동작은 맞지만 I/O를 늘린다 — I/O를 재는 시스템이라면 측정 대상을 바꾼다.
- 아래 계층 계약은 위 계층의 **호출 순서**까지 놓고 설계한다.
