# issue/cross-cutting/database/write-back-out-of-order-eviction — write-back 캐시는 쓰기 순서를 바꾼다: 할당 순서를 전제한 "끝에만 붙이기" 저장소 계약이 깨진다 — 질문

## 질문
1. (예측) 페이지 저장소는 "기존 페이지를 덮어쓰거나 맨 끝에 한 장 붙이기만 허용(구멍 금지)"이다. 그 위에 write-back 버퍼 풀을 얹고, 새 페이지 5와 6을 차례로 할당했다(할당은 번호만 주고 디스크에 닿지 않는다). 프레임이 모자라 6이 5보다 먼저 내보내지면 무슨 일이 일어나는가?
2. (왜) 저장소를 단독으로 테스트할 때는 이 계약이 왜 멀쩡해 보였는가. 버퍼 풀이 디스크에 쓰는 순서는 무엇이 정하는가 — 할당 순서인가, 교체 정책인가?
3. (설계) 고친 계약은 "끝 뒤에 쓰면 저장소가 `id + 1`장으로 자라고, 사이 페이지는 0으로 채운다"이다. 그러면 "할당되지 않은 번호에 쓰는 버그"는 이제 누가 막는가?
4. (설계) 선택하지 않은 방법 — "할당하는 순간 0 페이지를 디스크에 바로 써서 구멍을 없앤다" — 는 무엇을 대가로 치르는가. I/O 수를 재는 실험이라면 왜 특히 나쁜가?
5. (경계) 파일 저장소에서 끝 뒤 위치에 `pwrite`하면 파일 크기와 사이 바이트는 어떻게 되는가. 메모리 저장소는 같은 의미를 어떻게 흉내 내는가. 저장소가 기억하는 페이지 수는 어떻게 갱신해야 하는가?
6. (연결) 이 결함은 구현 중이 아니라 **다음 계층을 설계하다가** 드러났다. 아래 계층의 계약을 정할 때 "위에서 누가 어떤 순서로 부를 것인가"를 왜 함께 봐야 하는가?
