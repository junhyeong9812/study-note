# issue/cross-cutting/database/write-back-out-of-order-eviction — 정답

태그: `contract-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **6을 쓰는 순간 저장소에는 아직 페이지 5가 없으므로 "구멍"으로 판정되어 쓰기가 실패한다 — 내보내기 자체가 오류가 된다.**\
   할당은 번호만 주고, 새 페이지 내용은 프레임에 dirty로 머문다. 디스크에 처음 닿는 시점은 그 프레임이 내보내질 때다.\
   두 새 페이지 중 어느 쪽이 먼저 내보내질지는 교체 정책이 정하므로, 6이 먼저 나가는 일은 정상 동작이다.
   > **write-back** — 고친 페이지를 바로 디스크에 쓰지 않고 캐시에 dirty로 두었다가, 내보내거나 flush할 때 쓰는 방식.
   > **구멍(hole)** — 저장소 끝보다 뒤에 쓰려고 해서 그 사이에 아무도 쓰지 않은 페이지가 생기는 상황.

2. **저장소만 단독으로 테스트할 때는 호출자가 늘 번호 순서대로 썼기 때문이다 — 그 테스트에는 "할당 순서와 다른 순서로 쓰는 호출자"가 없었다.**\
   버퍼 풀이 디스크에 쓰는 순서는 희생자 선택(LRU 등)과 flush 순서가 정한다. 할당 순서와는 무관하다.\
   계약 자체는 저장소 안에서는 일관됐지만, 위 계층의 실제 호출 순서와 맞지 않았다.

3. **할당기가 막는다 — 할당기는 다음에 줄 번호(`next`)를 기억하고, `id ≥ next`인 쓰기를 "할당되지 않은 페이지"로 거부한다.**\
   저장소는 "어디까지 자랄 수 있는가"를 묻지 않고 받은 위치에 쓰기만 한다. "이 번호가 정당한가"는 번호를 발급한 쪽이 판정한다.\
   불변식 하나를 그것을 아는 계층 하나에 두는 분담이다 — 저장소는 할당 상태를 모른다.

4. **새 페이지마다 쓰기가 한 번 더 생긴다 — 나중에 내보낼 때 진짜 내용을 또 쓰므로 같은 페이지를 두 번 쓰는 셈이다.**\
   인덱스 분할처럼 새 페이지를 자주 만드는 연산에서는 분할마다 쓰기가 +1 된다.\
   버퍼 풀의 읽기·쓰기 횟수를 측정하는 것이 목적인 시스템에서는 이 추가 쓰기가 측정 대상 자체를 왜곡하므로 선택하지 않았다.

5. **파일 끝 뒤 위치에 쓰면 파일이 그 끝까지 늘어나고, 사이 바이트는 0으로 읽힌다. 메모리 저장소는 페이지 배열을 `id + 1`장까지 0 페이지로 늘려 같은 의미를 낸다. 페이지 수는 `max(기존, id + 1)`로 갱신한다.**\
   `max`가 필요한 이유: 끝 안쪽 페이지(앞에서 0으로 채워진 5)를 나중에 쓸 때 페이지 수가 줄면 안 된다.\
   다시 열 때는 파일 길이 ÷ 페이지 크기로 페이지 수를 복원하고, 할당기는 그 뒤 번호부터 발급한다.
   > **pwrite** — 파일의 지정 위치에 쓰는 시스템 호출. 끝 뒤 위치를 주면 파일이 늘어나고 그 사이는 0으로 읽힌다(파일시스템에 따라 실제 블록 없이 희소 파일이 될 수 있다).

6. **아래 계층의 계약은 위 계층이 실제로 부르는 순서에서만 의미가 있기 때문이다 — 단독 테스트는 호출 순서까지 검증하지 않는다.**\
   이 결함은 저장소를 만들 때가 아니라, 그 위에 버퍼 풀을 설계하며 "새 페이지 두 장이 역순으로 내보내지면?"을 따라갈 때 드러났다.\
   계약을 고친 뒤 저장소 테스트 2개의 의미를 "구멍 거부"에서 "끝 뒤 쓰기는 0으로 채워 성장"으로 바꿨다 — 계약 변경은 테스트 기대값 변경을 동반한다.

## 문제 구조 (추상화 코드)

### 변형 A — 순차 쓰기를 전제한 저장소 위에 write-back 캐시
① 문제 코드
```rust
impl Storage for Store {
    fn write_page(&mut self, id: u64, page: &Page) -> io::Result<()> {
        if id > self.pages {                       // 끝에 붙이기(id == pages)만 허용
            return Err(invalid("hole"));           // 캐시가 6을 5보다 먼저 쓰면 여기서 실패
        }
        self.file.write_all_at(page.bytes(), id * PAGE)?;
        if id == self.pages { self.pages += 1; }
        Ok(())
    }
}

// 위 계층
let a = pool.new_page()?;   // id 5 — 번호만, 디스크 I/O 없음
let b = pool.new_page()?;   // id 6
// ... 프레임 부족 → LRU가 6을 먼저 내보냄 → write_page(6) → "hole"
```
② 고친 코드
```rust
impl Storage for Store {
    fn write_page(&mut self, id: u64, page: &Page) -> io::Result<()> {
        // 끝 뒤에 쓰면 파일이 id + 1장으로 늘고, 사이 바이트는 0으로 읽힌다.
        self.file.write_all_at(page.bytes(), id * PAGE)?;
        self.pages = self.pages.max(id + 1);
        Ok(())
    }
}

impl Allocator {
    fn write(&mut self, id: u64, page: &Page) -> io::Result<()> {
        if id >= self.next { return Err(invalid("not allocated")); }   // 번호의 정당성은 여기서
        self.storage.write_page(id, page)
    }
}
```
무엇이 깨졌나: 저장소 계약이 "쓰기는 할당 순서대로 온다"를 암묵적으로 가정했고, write-back 캐시가 그 순서를 교체 정책 순서로 바꿨다.

## 검증 기록
- 2026-11-17: 사건 기록 대조·추상화(Claude 초안) — 버퍼 풀 설계 중 "새 페이지 5·6 할당 후 6이 먼저 내보내지면 쓰기 실패" 발견, 저장소 계약을 "끝 뒤 쓰기 = `id + 1`장으로 성장, 사이 0"으로 변경(메모리·파일 두 구현), 할당 여부는 할당기의 `id < next` 검사가 막음, 할당 즉시 0 페이지 쓰기는 분할마다 쓰기 +1로 측정 왜곡이라 선택하지 않음 — 작업 기록과 코드 대조.
