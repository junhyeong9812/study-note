# issue/cross-cutting/database/hidden-lock-wait-edges — 정답

태그: `race-condition`

## 정답
<!-- 질문 1:1 대응 -->

1. **외래 키 검사가 부모 행에 공유 잠금을 요구하고, 그것이 정리의 배타 잠금과 충돌한다 — 코드에 없는 대기 간선이다.**\
   PostgreSQL은 자식 쪽 `INSERT`의 외래 키 검사에서 참조된 부모 행에 `FOR KEY SHARE` 잠금을 잡는다 — 부모 행을 `FOR UPDATE`로 쥔 트랜잭션이 있으면 그 끝을 기다린다.\
   그래서 X(자식 행 h를 쥠 → 결과 행 INSERT의 FK 검사로 부모 행 대기)와 C(부모 행을 쥠 → `DELETE`가 h에서 X 대기)가 서로를 기다린다 → PostgreSQL이 한쪽을 40P01로 롤백한다.\
   X의 코드에는 부모 행을 잠그는 줄이 없다 — 이 간선은 스키마(FK)가 만든다.\
   이 고리는 설계 검토(정리 작업 설계를 확정 경로의 잠금 순서와 나란히 놓고 본 단계)에서 찾았고, 구현 뒤 고치기 전 형태를 흉내 낸 대조 테스트에서 실제로 40P01이 났다.
   > **FOR KEY SHARE** — 외래 키 검사가 참조 행에 거는 가장 약한 행 잠금. 키를 바꾸지 않는 UPDATE와는 공존하지만 `FOR UPDATE`·키 변경·삭제와는 충돌한다.

2. **정리가 기다리지 않으면 정리에서 나가는 간선이 없어 고리가 닫히지 않는다 — 대신 "남은 것이 있는지"를 다시 보고 뒷단계를 미룬다.**\
   `DELETE … WHERE id IN (SELECT id … FOR UPDATE SKIP LOCKED)`는 다른 트랜잭션이 쥔 행을 건너뛴다 — X가 쥔 h는 지우지 않고, C는 X를 기다리지 않는다.\
   그러면 "그룹에 자식 행이 하나도 없을 때만 집계 행을 지운다"는 불변식이 위험해진다 — 그래서 삭제 뒤 **새 문장으로** 남은 자식 행이 있는지 다시 보고, 남았으면 집계 행 삭제를 다음 실행으로 미룬다.\
   다음 실행이 그 그룹을 다시 고르려면 대상 조건이 "닫힘 ∧ 집계 행이 남아 있음"이어야 한다 — 미룬 그룹은 자연스럽게 다시 대상이 된다.\
   건너뛴 행은 X가 끝나면 사라지거나(성공 — X가 지움) 다음 실행이 지운다(거부·롤백).\
   테스트로 확인했다: X가 h를 쥔 동안 정리는 기다리지 않고 0행 삭제·건너뜀 1을 기록했고, 집계 행은 남았으며, X가 롤백한 뒤 다음 실행이 h를 지웠다(40P01 0).

3. **같은 앞쪽 k개를 다시 고른다 — 진행이 0이 된다. 진행형 커서는 "이미 본 후보 뒤부터"로 바꿔 앞쪽 잠금이 뒤를 막지 않게 한다.**\
   `SKIP LOCKED`는 잠긴 후보를 지우지 않고 건너뛰므로, 후보 질의가 늘 `ORDER BY key LIMIT k`면 다음 청크도 같은 잠긴 후보를 다시 집는다.\
   그래서 후보 질의에 `key > :after`(앞 청크 후보의 최대 키 · 틱 시작 때 0)를 넣었다 — 잠그지 못했거나 실패한 후보가 있어도 커서는 그 뒤로 간다.\
   여러 열 키면 행 비교 `(a, b) > (:a, :b)`로 같은 일을 한다.\
   이 막힘은 설계 검토에서 찾아 구현 전에 막았다(실측 사건은 없음).
   > **SKIP LOCKED** — 잠긴 행을 기다리지도 오류를 내지도 않고 결과에서 빼는 행 잠금 옵션. 작업 큐·배치처럼 "다른 쪽이 처리 중이면 나중에"인 소비자에 맞다.

4. **앞쪽에서 계속 건너뛰거나 실패하는 후보가 상한을 다 써서, 뒤쪽 후보는 차례가 오지 않는다.**\
   틱당 청크 상한(이 사례 기본 100 · 장애 뒤 밀림처럼 큰 경우에 틱 길이를 묶으려는 것)은 필요하지만, 다음 틱을 늘 처음부터 시작하면 매 틱 같은 앞쪽 구간만 훑는다.\
   그래서 상한에 닿으면 틱을 끝내고 **커서를 다음 틱에 넘겼다** — 다음 틱은 그 뒤부터 이어 가고, 후보 끝에 닿으면 커서를 버려 그다음 틱은 처음부터 다시 훑는다.\
   상한에 닿은 틱 수는 지표로 남겨, 상한이 실제로 일을 자르고 있는지 보이게 했다.\
   커서는 인스턴스 메모리에만 산다 — 인스턴스가 여럿이면 각자 따로 돈다(잠금이 겹침을 나눈다).

5. **한쪽 자원(대상 행)에서 두 경로 모두 기다리지 않으면, 그 자원에서 시작하는 대기 간선이 없어 순서가 반대여도 고리가 닫히지 않는다.**\
   교착은 대기 간선의 고리다 — 간선은 "기다리는 잠금"에서만 생긴다.\
   선점은 대상 행을 `NOWAIT`(못 잡으면 즉시 실패), 배치는 `SKIP LOCKED`(못 잡으면 건너뜀)로 잡으므로, 대상 행을 쥔 쪽을 누구도 기다리지 않는다.\
   기다리는 잠금은 집계 행뿐이고, 여러 집계 행을 잡는 쪽은 키 순으로 정렬해 잡는다 — 같은 자원 종류 안의 고리도 막는다.\
   대상 행을 **기다리는** 제3의 경로가 있으면 그것까지 같은 그래프에 넣는다 — 이 사례의 확정 경로는 대상 행을 기다리지만, 그 뒤에 기다리는 자식 행을 쥔 쪽(회수·배치)은 대상 행을 기다리지 않으므로 고리가 닫히지 않는다는 것을 따로 짚었다.\
   이 판단은 설계에서 "추정"으로 두고 동시성 테스트로 확인했다(고리 후보 간선 7개 시나리오에서 40P01 0).

6. **고친 형태의 0건은 "그 시나리오가 고리를 만들 수 있는가"를 말해 주지 않는다 — 고치기 전 형태로 40P01이 나는 대조가 있어야 시나리오가 이빨을 가진다.**\
   타이밍이 맞지 않으면 고치기 전 형태로도 교착이 안 날 수 있다 — 그러면 고친 형태의 0건은 아무것도 증명하지 않는다.\
   대조 테스트는 정리의 두 문장(부모 행 `FOR UPDATE` → 자식 행 `DELETE`)을 `SKIP LOCKED` 없이 따로 실행하고, X가 쥔 상태에서 정리가 **대기 중인 것을 확인한 뒤** X의 INSERT를 실행해 40P01을 기대한다.\
   "대기 중인 것을 확인한 뒤"가 핵심이다 — 잠(sleep)으로 순서를 맞추면 느린 환경에서 순서가 뒤집혀, 대조는 흔들리고 고친 형태의 테스트는 고리를 만들 기회 없이 통과할 수 있다([test-isolation-and-determinism](../../testing/test-isolation-and-determinism/)).

## 문제 구조 (추상화 코드)

### 변형 A — 정리의 DELETE가 확정이 쥔 행을 기다림 (FK 검사와 고리)
① 문제 코드
```sql
-- 정리 C (닫힌 그룹 :g 하나 = 트랜잭션 하나)
SELECT closes_at FROM grp WHERE id = :g FOR UPDATE;          -- 부모 행 배타 — FK 검사도 막는다
DELETE FROM child WHERE group_id = :g AND expires_at <= now();   -- X가 쥔 행에서 기다림
DELETE FROM agg   WHERE group_id = :g;
-- 확정 X
SELECT … FROM child WHERE id = :h FOR UPDATE;
INSERT INTO result (group_id, …) VALUES (:g, …);             -- FK 검사 → grp 행 FOR KEY SHARE → C 대기 → 40P01
```
② 고친 코드
```sql
SELECT closes_at FROM grp WHERE id = :g FOR UPDATE;
DELETE FROM child WHERE id IN (
  SELECT id FROM child WHERE group_id = :g AND expires_at <= now() FOR UPDATE SKIP LOCKED)
RETURNING id;                                                  -- 지운 수 · 건너뛴 수는 기록
SELECT EXISTS (SELECT 1 FROM child WHERE group_id = :g);       -- 잠근 뒤 새 문장으로 다시 본다
DELETE FROM agg WHERE group_id = :g;                           -- 위가 false일 때만 — 아니면 다음 실행으로
-- 대상 선정: 닫힘 AND agg 행이 남아 있음 → 미룬 그룹은 다음 실행에 다시 든다
```
무엇이 깨졌나: 늦어도 되는 정리 작업이 사용자 트랜잭션이 쥔 행을 기다렸고, 그 사용자 트랜잭션은 FK 검사로 정리가 쥔 부모 행을 기다렸다.

### 변형 B — SKIP LOCKED + 고정 LIMIT + 틱 상한
① 문제 코드
```sql
-- 청크마다
SELECT DISTINCT key FROM child WHERE expires_at <= now() ORDER BY key LIMIT :k;   -- 늘 같은 앞쪽
SELECT id FROM target WHERE id = ANY(:candidates) FOR UPDATE SKIP LOCKED;          -- 잠긴 앞쪽은 매번 건너뜀
-- 틱: 청크 상한 N에 닿으면 끝, 다음 틱은 처음부터
```
② 고친 코드
```kotlin
var after = carriedCursor ?: 0L                       // 앞 틱에서 넘긴 커서(없으면 처음)
repeat(maxChunksPerTick) {
    val cand = query("… WHERE expires_at <= now() AND key > ? ORDER BY key LIMIT ?", after, k)
    if (cand.isEmpty()) { carriedCursor = null; return }        // 후보 끝 → 다음 틱은 처음부터
    runChunk(cand)                                     // SKIP LOCKED · 청크 실패도 커서는 넘긴다
    after = cand.max()
}
carriedCursor = after; metrics.chunkCapReached()      // 상한에 닿음 → 다음 틱은 이 뒤부터
```
무엇이 깨졌나: 건너뛴 후보가 그대로 남는 선택(SKIP LOCKED)과 "늘 앞에서부터"인 후보 질의가 만나, 잠긴 앞쪽이 진행을 막았다.

## 검증 기록
- 2026-11-04: 설계 검토 기록·동시성 테스트·사건 기록 대조·추상화(Claude 초안) — 변형 A는 설계 검토에서 찾고 구현 뒤 대조 테스트에서 40P01 재현 · 고친 형태 테스트에서 건너뜀·미룸·다음 실행 삭제 확인, 변형 B는 설계 검토에서 찾아 구현 전에 막음(실측 사건 없음), 질문 5의 "고리 없음"은 동시성 테스트(간선 7개 시나리오 40P01 0)로 확인. FK 검사의 잠금 모드는 PostgreSQL 일반 동작.

## 방안 비교

같은 원리(정리 작업이 사용자 트랜잭션을 기다리면 숨은 간선과 고리를 만든다)에 대한 세 방안.

### 방안 1 — 정리는 SKIP LOCKED로 기다리지 않고 남은 것은 다음 실행으로 (이 사례의 선택)
```sql
DELETE FROM child WHERE id IN (SELECT id … FOR UPDATE SKIP LOCKED) RETURNING id;
-- 새 문장으로 남은 것 확인 → 남았으면 뒷단계 미룸
```

### 방안 2 — 사용자 경로가 먼저 부모 행을 같은 순서로 잠근다 (선택하지 않은 방법)
```sql
-- 확정 X 맨 앞에: 정리와 같은 순서(부모 → 자식)를 강제
SELECT … FROM grp WHERE id = :g FOR SHARE;
SELECT … FROM child WHERE id = :h FOR UPDATE;
```

### 방안 3 — 교착을 허용하고 재시도 (선택하지 않은 방법)
```kotlin
retryOn("40P01", times = 3) { cleanup.runOnce(g) }
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 정리는 기다리지 않음 | 정리가 늦어도 된다, 대상 조건이 미룬 것을 다시 고른다 | 건너뜀·미룸 기록, 재확인 문장 1개 | 한 행이 오래 잡혀 있으면 정리가 계속 미뤄진다 — 미룬 횟수를 지표로 봐야 한다 | 배치·정리·청소처럼 다음 실행이 있는 작업 |
| 2. 같은 잠금 순서 강제 | 모든 사용자 경로를 고칠 수 있다 | 사용자 경로마다 잠금 1문장, 부모 행 경합 | 경로 하나라도 빠지면 고리가 돌아온다, FK 검사처럼 순서를 못 바꾸는 간선은 남는다 | 경로 수가 적고 모두 같은 코드베이스일 때 |
| 3. 교착 후 재시도 | 롤백이 싸고 재시도가 멱등이다 | 롤백·재시도 비용 | 교착 피해자가 사용자 요청이면 사용자가 실패를 본다 — 어느 쪽이 롤백될지 고를 수 없다 | 드문 고리를 감수할 수 있을 때 |

**결론**: 정리·배치처럼 "다음 실행"이 있는 쪽이 기다리지 않게 하는 방안 1이 가장 국소적이다 — 사용자 경로를 건드리지 않고, 스키마가 만든 간선(FK)도 그대로 둔다.\
방안 2는 FK 검사처럼 코드가 순서를 정할 수 없는 간선 앞에서는 완결되지 않는다.\
어느 방안이든 "고리 없음"은 고치기 전 형태의 40P01 대조 테스트와 함께 확인한다.\
검증 기록: 2026-11-04 설계 검토·테스트 대조(Claude 초안) — 방안 1은 적용·테스트, 방안 2·3은 설계 단계에서 고르지 않은 일반 형태(미측정).
