# issue/cross-cutting/database/rolled-back-write-cost — 정답

태그: `resource-bounding`

## 정답
<!-- 질문 1:1 대응 -->

1. **로그는 먼저 쓰이고, 롤백은 새 버전을 "무효"로 표시할 뿐이다.**\
   로그 선행 기록 엔진은 데이터 페이지를 바꾸기 전에 변경을 로그에 쓴다 — 트랜잭션이 나중에 롤백돼도 이미 쓴 로그 레코드는 그대로 디스크로 간다.\
   MVCC 엔진(이 사례: PostgreSQL)에서 INSERT·UPDATE는 새 행 버전과 인덱스 항목을 만들고, 롤백은 그 버전을 "중단된 트랜잭션의 것"으로 볼 뿐 즉시 지우지 않는다 — vacuum이 치울 때까지 죽은 행으로 남는다.
   > **WAL(write-ahead log)** — 데이터 변경을 데이터 파일보다 먼저 순차 로그에 기록해 장애 뒤 복구를 보장하는 방식. 커밋 여부와 무관하게 변경 시점에 쓰인다.
   > **dead tuple** — MVCC에서 더 이상 어떤 트랜잭션에도 보이지 않지만 아직 물리적으로 남아 있는 행 버전. vacuum이 회수한다.

2. **지는 시도마다 쓰기 비용이 붙어 로그가 2.8배가 됐다.**\
   실제 흐름(입장 → 선점 → 확정·이탈 → 만료)에서 선점 시도 228만 건 중 98.4%가 매진 뒤 거절이었다.\
   카운터를 좌석보다 앞에서 올리면, 좌석에서 지는 시도도 upsert(+1, 행이 없으면 INSERT)를 쓰고 롤백한다.\
   카운터 없는 방식은 좌석 잠금(NOWAIT)에서 먼저 지고 끝난다 — 로그 86.5MB 대 243MB(2.8배), 디스크 쓰기 515MB 대 796MB(1.55배).\
   (원인은 처음엔 추정이었다 — 아래 3의 순서 변경으로 로그가 크게 준 것이 이 추정과 맞는다.)

3. **지는 시도가 아무것도 쓰지 않고 끝나기 때문이다.**\
   잠금 없는 `SELECT status`로 팔린 좌석을 먼저 거르자 로그가 24.6MB — 카운터 없는 방식(86.5MB)의 0.28배, 시도당 32B가 됐다. 디스크 쓰기도 438MB로 카운터 없는 방식(519MB)보다 적었다.\
   카운터 없는 방식은 팔린 좌석에서도 **행 잠금을 시도**한다 — MVCC 엔진은 행 잠금을 행 헤더에 기록하므로 그것이 로그를 쓴 것으로 본다(추정 — 대기 이벤트·로그 레코드 종류로 확인하지는 않았다).\
   교훈: "기능을 하나 더한 방식"이 "기능 없는 방식"보다 쓰기가 적을 수 있다 — 비교 기준은 기능 수가 아니라 **지는 시도가 어디서 끝나는가**다.

4. **커밋 전 변경이다.**\
   잠금 없는 읽기는 커밋된 상태만 본다 — 다른 트랜잭션이 잠그고 아직 커밋하지 않은 좌석은 "비어 있음"으로 보인다.\
   그래서 한도가 찬 사용자가 그런 좌석을 누르면 선조회를 통과하고, upsert가 0행(한도)이 되고, 재조회도 여전히 "비어 있음"이라 **"한도 초과"**를 받는다 — 명세 순서("좌석이 먼저")라면 "좌석 없음"이었을 응답이다.\
   한도 찬 사용자와 일반 사용자가 같은 좌석에 동시에 보내는 시험에서는 이 틈이 **매 회차 100/100** 났다 — 드물지 않다. 정합성(초과 보유 0)과 다른 사용자 피해(억울한 좌석 0)에는 영향이 없어 받아들인 한계로 남겼다.\
   커밋된(이미 팔린) 좌석에는 이 오류가 0/100이었다 — 순서 변경의 목적(팔린 좌석에 "한도 초과"를 주지 않음)은 지켰다.

5. **선조회는 필터일 뿐, 판정은 트랜잭션 안의 원자 연산이 한다.**\
   선조회가 틀려도(그 사이 팔림, 커밋 전 잠김) 결과가 잘못 확정되지 않는다 — 한도는 조건부 upsert(`WHERE cnt + 1 <= limit`, 0행이면 거절)가, 좌석은 뒤의 행 잠금(NOWAIT)이 최종 판정한다.\
   check-then-act가 결함이 되는 것은 **확인이 유일한 판정**일 때다. 여기서 확인이 틀리면 생기는 일은 "쓰기 한 번 더"(선조회 뒤 팔린 경우)나 "오류 코드 순서"(4)뿐이다.
   > **check-then-act** — 상태를 확인한 뒤 그 결과에 기대어 행동하는 패턴. 확인과 행동 사이에 상태가 바뀌면 깨진다. 확인을 최적화용 필터로만 쓰고 최종 판정을 원자 연산에 두면 안전하다.

6. **카운터 테이블의 행 수(와 그 인덱스)가 고유 사용자 수만큼 늘어난다.**\
   만료는 `UPDATE … SET cnt = cnt - ?`만 하고 DELETE가 없어서, `cnt`가 0으로 돌아와도 행은 남는다 — 살아 있는 행은 "한 번이라도 선점에 성공해 커밋한 고유 사용자 수"다.\
   롤백된 INSERT는 살아 있는 행이 아니지만 vacuum 전까지 죽은 행·인덱스 항목으로 남는다.\
   만료가 돌아도 이 비용은 줄지 않으므로, 정리(삭제·파티션 교체)와 vacuum 비용은 만료 설계에서 따로 다뤄야 한다 — 이 사례는 그 설계를 다음 작업으로 넘겼다.

## 문제 구조 (추상화 코드)

### 변형 A — 지는 시도가 쓰고 롤백한다 (쓰기 먼저)
① 문제 코드
```kotlin
@Transactional
fun hold(cmd: HoldCommand) {
    val ok = jdbc.update("""
        INSERT INTO user_quota (scope_id, user_id, cnt) VALUES (?, ?, 1)
        ON CONFLICT (scope_id, user_id) DO UPDATE SET cnt = user_quota.cnt + 1
        WHERE user_quota.cnt + 1 <= ?""", cmd.scopeId, cmd.userId, limit) == 1
    if (!ok) throw LimitExceeded()
    val item = repo.lockNoWait(cmd.itemId)        // 이미 팔림 → 예외 → 롤백
    item.assertAvailable()                        //   upsert의 WAL·행 버전은 이미 쓰였다
    // ...
}
```
② 고친 코드
```kotlin
@Transactional
fun hold(cmd: HoldCommand) {
    assertItemAvailable(cmd)                      // 잠금 없는 SELECT status — 팔렸으면 쓰기 없이 거절
    if (!upsertQuota(cmd, limit)) {
        assertItemAvailable(cmd)                  // 선조회 뒤 팔렸으면 "좌석 없음"이 먼저
        throw LimitExceeded()
    }
    val item = repo.lockNoWait(cmd.itemId)        // 최종 판정은 그대로 — 선조회는 필터일 뿐
    item.assertAvailable()
    // ...
}
```
무엇이 깨졌나: 시도의 98%가 지는 흐름에서 지는 시도마다 쓰기·롤백이 일어나 로그가 2.8배가 됐다(순서 변경 뒤 0.28배).\
남은 틈: 커밋 전 잠긴 좌석은 선조회에 "비어 있음"으로 보여, 동시 경합에서 한도 찬 사용자가 "좌석 없음" 대신 "한도 초과"를 받는다.

### 변형 B — 감소만 하고 지우지 않는 카운터 행
① 문제 코드
```sql
-- 만료 배치: 개수만 내린다
UPDATE user_quota SET cnt = cnt - ? WHERE scope_id = ? AND user_id = ?;   -- 만료된 보유 수만큼
-- cnt = 0 인 행도 남는다 → 행 수 = 누적 고유 사용자 수
```
② 정리 방향 (일반 형태 — 이 사례에서는 후속 설계로 넘김)
```sql
DELETE FROM user_quota WHERE cnt = 0 AND <대상 기간 종료>;   -- 또는 기간 단위 파티션을 통째로 교체
-- 롤백 잔해(죽은 행)는 vacuum 주기·비용과 함께 본다
```
무엇이 깨졌나(잠재): 만료가 정상 동작해도 카운터 테이블은 줄지 않는다 — 사용자가 매번 새로 오는 부하에서는 선점마다 행이 하나씩 쌓였다.
