# issue/cross-cutting/database/rolled-back-write-cost — 정리 (힌트)

## 전체 흐름

```
[쓰기 먼저] 한 트랜잭션                                   지는 시도(98%)가 남기는 것
  BEGIN
   ├─ upsert quota  (cnt+1, 없으면 INSERT) ─────────▶  WAL 레코드 · 새 행 버전/인덱스 항목
   ├─ lock seat NOWAIT ── 이미 팔림 ──▶ 예외
  ROLLBACK ──────────────────────────────────────────▶  죽은 행(dead tuple) — vacuum 전까지 남음
                                                         WAL은 이미 기록됨(되돌리지 않음)

[싼 거절 먼저] 한 트랜잭션
  BEGIN
   ├─ SELECT seat.status (잠금 없음) ── 팔림 ──▶ 거절   ──▶  쓰기 0
   ├─ upsert quota ── 0행(한도) ──▶ 좌석 재조회 → 팔렸으면 "좌석 없음", 아니면 "한도 초과"
   ├─ lock seat NOWAIT  (최종 판정은 그대로 여기)
  COMMIT

실측 (실제 흐름 — 시도 228만 건, 98.4%가 매진 뒤 거절)
  카운터 없음      WAL  86.5MB   디스크 쓰기 515~519MB
  쓰기 먼저        WAL 243MB(×2.8) 디스크 쓰기 796MB(×1.55)
  싼 거절 먼저     WAL  24.6MB(×0.28) 디스크 쓰기 438MB

남는 것
  잠금 없는 읽기는 "커밋 전 쥔 좌석"을 비어 있다고 본다 → 한도 찬 사용자는 "좌석 없음" 대신 "한도 초과"
  카운터 행은 만료로 지워지지 않는다(cnt만 감소) → 고유 사용자 수만큼 계속 늘어남 → 별도 정리 필요
```

## 핵심 문장

- 롤백은 결과를 되돌릴 뿐 **비용을 되돌리지 않는다** — 로그는 이미 쓰였고, 롤백된 행은 vacuum 전까지 죽은 행·인덱스 항목으로 남는다.
- 시도 대부분이 지는 흐름에서는 **쓰기 비용 × 지는 시도 수**가 운영 비용이 된다 — 지는 시도가 쓰기 전에 끝나게 순서를 둔다.
- 앞의 싼 거절은 **필터**일 뿐이다 — 최종 판정(조건부 갱신·행 잠금)은 트랜잭션 안에 그대로 남겨야 check-then-act 결함이 되지 않는다.
- 잠금 없는 읽기는 커밋되지 않은 변경을 못 본다 — 정합성은 지켜도 **오류 코드의 순서**가 동시 경합에서 흔들릴 수 있다.
- 감소만 하고 지우지 않는 행은 입력 다양성에 비례해 자란다 — 정리 주체를 설계에 넣는다.
