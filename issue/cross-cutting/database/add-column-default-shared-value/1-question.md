# issue/cross-cutting/database/add-column-default-shared-value — 빠른 기본값으로 더한 열은 기존 행 전부에 같은 값을 준다: 그 열로 "바뀐 행"을 찾는 증분은 첫 창에서 기존 행 전부를 읽는다 — 질문

## 질문
1. (왜) 수백만 행 테이블에 `ALTER TABLE … ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now()`를 실행했다. PostgreSQL 11 이후 이 문장은 테이블을 다시 쓰지 않는다 — 기존 행의 `updated_at`은 어떤 값이며 그 값은 어디에 있나.
2. (예측) 이 열과 "갱신마다 `updated_at := now()`" 트리거로 "하한 뒤에 바뀐 행"만 대조하는 증분 작업이 있다. 첫 하한이 "기동 시각 − 60초"이고, 열을 더한 직후 60초 안에 이 작업이 기동하면 첫 틱은 무엇을 읽나. 왜 오류 없이 비용(틱 시간·메모리·DB 부하)만 기존 데이터 크기에 비례해 커지나.
3. (설계) 기존 행을 첫 창에서 빼는 규칙으로 "하한 = max(기동 − 60초, 열 추가 시각)"(엄격한 하한)과 "값이 열 추가 값 m인 행만 뺀다" 두 가지가 있다. 열 추가 문장의 락을 기다렸다가 행을 고친 트랜잭션을 떠올리면, 엄격한 하한은 무엇을 잃나.
4. (경계) "값이 m인 행만 뺀다"를 `WHERE updated_at >= $L AND updated_at <> $m` 한 조건으로 쓰면 인덱스는 무엇을 하나. 왜 `[L, m)`와 `(m, ∞)` 두 범위로 나눠야 하나.
5. (경계) 카탈로그의 그 값은 언제 사라지나(테이블 재작성). 사라졌을 때 증분은 어떻게 동작해야 하나 — 그리고 m을 매 틱 읽지 않고 기동 때 한 번 읽어 기억하는 이유는 무엇인가.
6. (한계) 후보 조회에 키셋 페이지 상한(틱마다 최대 N행)을 두었다. 인덱스가 `(updated_at)` 단일 열이고 같은 `updated_at` 값을 가진 행이 수백만이면, `(updated_at, k1, k2) > (…)` 키셋 비교의 비용이 왜 N으로 묶이지 않나.
