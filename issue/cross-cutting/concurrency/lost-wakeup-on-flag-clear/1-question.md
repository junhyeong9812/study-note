# issue/cross-cutting/concurrency/lost-wakeup-on-flag-clear — 깨움 플래그를 "확인 → (멈춤) → clear → 대기" 순서로 쓰면 확인과 clear 사이에 온 신호가 지워진다: clear 뒤에 조건을 다시 보고 기다린다 — 질문

## 질문
1. (왜) 대기자는 루프를 돈다: ① 조건(교체 중인가)을 확인 → ② 상태 이벤트를 내보낸다(`yield`) → ③ 깨움 플래그를 `clear()` → ④ 플래그 또는 자리 획득을 기다린다(상한 = 하트비트). 정리 신호를 보내는 쪽은 "조건을 참으로 바꾸고 모든 플래그를 `set()`"한다. 신호가 ②에서 멈춰 있는 동안 오면 무슨 일이 일어나나.
2. (지식) 단일 스레드 이벤트 루프(asyncio)에는 선점이 없다. 그런데도 1의 끼어들기가 생기는 이유는 무엇인가 — 비동기 제너레이터의 `yield`는 언제 다시 이어지나.
3. (예측) 1의 결함이 있어도 대기자는 결국 신호를 알아챘다. 무엇 덕분이고, 그 대가는 얼마인가. 이 결함을 "유실"이 아니라 "지연"으로만 보면 무엇을 놓치나.
4. (교정) 고친 코드는 ③ `clear()` 직후에 조건을 다시 본다. 왜 "clear → 조건 확인 → 대기" 순서여야 하고, "조건 확인 → clear → 대기"는 안 되나. 조건 변수(condition variable)의 술어 루프와 무엇이 같은가.
5. (테스트) 원래 테스트는 이 결함이 있는데도 초록이었다. 하트비트가 테스트를 어떻게 구했나. 테스트를 결함에 이빨이 있게 바꾸려면 하트비트와 시간 상한을 어떻게 놓아야 하나 — 그리고 그 테스트가 정말 이 결함을 잡는지 어떻게 확인하나.
6. (경계) 대기자를 "② 이벤트를 내보낸 직후, 아직 ④에 들어가기 전"에 세워 두는 시나리오를 테스트에서 어떻게 만드나. 대기 지점 **안**에 들어간 대기자만 쓰는 테스트는 왜 이 결함을 못 보나.
7. (연결) 이 결함은 "늦게 확인하면 사건이 사라진다"는 점에서 edge 판정·이벤트 구독 카드와 닮았다. 플래그 기반 깨움이 "보관 없는 신호"라는 관점에서 공통점을 말하라.
