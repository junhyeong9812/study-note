# issue/cross-cutting/concurrency/lost-wakeup-on-flag-clear — 정리 (힌트)

## 전체 흐름

```
대기자 루프 (한 대기자)                        신호 보내는 쪽 (정리 시작)
──────────────────────────────                 ──────────────────────────
① if handing_off and 맨 앞: retry 내고 끝
② yield queued  ─────┐  ← 소비자가 다음 이벤트를
                     │    달라고 할 때까지 멈춤    handing_off = True
                     │  ◀──────────── 이 틈 ───── for t in tickets: t.set()   (플래그 = 1)
③ ticket.clear()  ◀──┘                                    │
     플래그 = 0  ← 방금 온 깨움을 지움 ───────────────────┘
④ wait(플래그 | 자리 획득, timeout = 하트비트)
     → 아무도 다시 깨우지 않음 → 하트비트(운영 10초)까지 잠 → 그제야 ①에서 알아챔

[결과]  교체 중인 서버의 대기자가 최대 하트비트만큼 늦게 넘겨진다 (유실처럼 보이지 않는 이유 = 시간 제한 재확인)

[교정]  ③ clear 뒤에 조건을 다시 본다
        ② yield → ③ clear → if handing_off: (맨 앞이면) ①로 → ④ wait
        = "깨움을 지운 뒤에 조건을 확인하고, 그 다음에 기다린다" (조건 변수의 술어 루프와 같은 순서)

[테스트가 초록이던 이유]
   하트비트 10초 → 깨움을 잃어도 10초 뒤 ①에서 알아챔 → 단언(retry 받음)은 통과, 시간만 김(전체 24초)
   교정: 하트비트 60초 + 시나리오마다 시간 상한 3초 + "yield 직후 멈춘 대기자" 시나리오
        → 고친 줄을 빼면 실패함을 확인(변이)  → 전체 5초
```

## 핵심 문장

- 플래그(Event) 깨움은 **보관되지 않는 신호**다 — 대기자가 `clear()`하는 순간 그 전에 온 신호는 사라진다.
- 안전한 순서는 **clear → 조건 확인 → 대기**다 — 확인과 clear 사이에 멈출 수 있는 지점(`yield`·`await`)이 있으면 "확인 → clear"는 그 사이의 신호를 지운다.
- 단일 스레드 이벤트 루프에도 끼어들기는 있다 — **모든 `await`와 비동기 제너레이터의 `yield`가 양보 지점**이다.
- 시간 제한 재확인(하트비트·타임아웃)은 잃어버린 깨움을 **지연으로 바꿔 숨긴다** — 결과 단언만 하는 테스트는 초록이 된다.
- 깨움 테스트는 시간 상한을 **재확인 주기보다 짧게** 두어야 이빨이 생긴다 — 그리고 고친 줄을 빼서 실패하는지 본다.
