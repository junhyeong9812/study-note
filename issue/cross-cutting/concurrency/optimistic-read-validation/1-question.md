# issue/cross-cutting/concurrency/optimistic-read-validation — 잠금 없이 여러 번 읽어 한 답을 만들 때: 앞뒤 버전 값 비교 — 질문

## 질문
1. (왜) 한 응답을 만들려고 저장소에 명령을 여러 번 보낸다. 그 사이 다른 프로세스가 저장소를 바꿀 수 있다. 명령마다 "지금 상태가 이상하지 않은지" 따로 검사하는 방어는 왜 모자라는가?
2. (경계) 쓰는 쪽과 같은 잠금을 잡으면 문제는 사라진다. 그런데도 잠금을 쓰지 않은 까닭은 무엇이고, 잠금 대신 무엇을 기준으로 "일관된 읽기였다"를 판정하는가?
3. (왜) "읽기 앞뒤로 버전 값을 읽어 같을 때만 결과를 쓴다"는 방식이 성립하려면 버전 값은 어떤 성질을 가져야 하는가? 버전 값이 데이터보다 늦게 바뀌는 틈이 있으면 무엇이 보이는가?
4. (예측) 앞뒤 버전 값이 다를 때 계속 다시 시도하면 어떻게 되는가? 재시도 횟수와 기한을 어떻게 묶어야 하는가?
5. (경계) 읽기 도중 기한 초과가 나면, 앞뒤 버전 값을 비교하지 않고 바로 시간 초과로 답한다. 왜 그래도 되는가?
6. (연결) 같은 결함을 두 번째 고치게 됐을 때 "방어를 하나 더 붙이기" 대신 "경쟁을 한 곳에서 닫기"로 방식을 바꾼 판단은 무엇에 근거했는가?
7. (방법) "읽는 도중 상태가 바뀐다"를 시간에 기대지 않고 테스트로 재현하려면 어떻게 하는가?
