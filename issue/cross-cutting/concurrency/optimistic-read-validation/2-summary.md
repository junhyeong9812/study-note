# issue/cross-cutting/concurrency/optimistic-read-validation — 정리 (힌트)

## 전체 흐름

```
조회 하나 = 명령 여러 번 (객체 확인 → 목록 → 파일별 diff → 관계 판정 …)
쓰는 쪽   = 배포의 fetch (잠금을 공유하지 않음 — 조회가 배포를 막으면 안 된다)

[실패] 명령마다 따로 본 상태
   경계 판정 ── 옛 경계 목록
   git 명령  ──────────── fetch ── 새 이력
   → 경계 커밋 검사는 통과했는데, 실제 diff 는 부모 없는 커밋 → 전부 "추가" → 200

[교정] 버전 값으로 앞뒤를 묶는다 (seqlock 꼴)
   for 시도 in 1..2:
       before = 경계 목록 읽기
       data   = 명령들 (경계 판정도 before 로만)
       if 기한 초과: return 시간 초과           ← 비교하지 않는다 (data 를 쓰지 않으므로)
       after  = 경계 목록 읽기
       if before == after: return data          ← 오류 결과도 그대로
   return 503 "바뀌는 중 — 잠시 뒤 다시"

   기한 = 재시도를 포함한 조회 하나 전체 (같은 컨텍스트)
```

## 핵심 문장
- 잠금 없이 여러 번 읽어 한 답을 만들면 그 사이의 쓰기가 섞인다 — 명령마다 방어하면 "명령 사이"가 계속 남는다.
- 읽기 앞뒤로 버전 값을 비교해 같을 때만 답한다. 다르면 버리고 다시, 계속 다르면 "바뀌는 중"을 따로 답한다.
- 버전 값은 데이터가 바뀔 때마다 함께 바뀌어야 한다 — 버전 값이 늦게 바뀌는 틈은 이 방식이 잡지 못한다(이 사례의 남은 한계: 일시 오류).
- 재시도는 횟수 상한과 전체 기한 안에서만 — 쓰는 쪽이 오래 바쁘면 읽는 쪽은 포기하고 그 사실을 알린다.
- 같은 결함을 두 번째 고치게 되면 방어를 덧붙이지 말고 경쟁을 닫는 지점을 하나로 옮긴다.
