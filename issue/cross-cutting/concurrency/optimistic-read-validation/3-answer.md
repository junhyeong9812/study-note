# issue/cross-cutting/concurrency/optimistic-read-validation — 정답

태그: `race-condition`

## 정답
<!-- 질문 1:1 대응 -->

1. **검사와 사용 사이, 그리고 명령과 명령 사이가 계속 남기 때문이다.**\
   한 응답을 만드는 명령들(커밋 확인 → 파일 목록 → patch → 관계 판정)이 각각 다른 순간의 저장소를 본다.\
   이 사례에서는 얕은 경계 목록으로 "부모 없는 커밋인가"를 검사한 뒤 diff 명령을 돌렸는데, 그 사이 배포의 fetch 가 경계를 옮기면 검사는 옛 이력으로, diff 는 새 이력으로 한 셈이 됐다.\
   결과는 부모 없는 diff(파일 전체가 "추가")와 틀린 관계가 200 으로 나간 것이다 — 테스트 워커가 리뷰한 커밋에서 이 재현을 빨강으로 확인했다.\
   명령마다 방어를 붙여도 방어와 다음 명령 사이에 같은 틈이 생긴다 — 처음 잡은 수정 방향이 이것이었고, 감사에서 모자라다는 지적을 받았다.
   > **TOCTOU(time-of-check to time-of-use)** — 확인한 시점과 사용하는 시점 사이에 상태가 바뀌어 확인이 무효가 되는 경합.

2. **조회가 배포를 막으면 안 된다는 요구가 있었다. 그래서 잠금 대신 "읽은 동안 바뀌지 않았다"를 사후에 확인한다.**\
   배포의 fetch 와 같은 잠금을 잡으면 조회가 길어질 때 배포가 기다린다 — 명세는 "조회는 배포 잠금을 잡지 않고 배포 중에도 답한다"였다.\
   대신 경계 목록(`.git/shallow` 의 내용)을 git 명령들 앞뒤로 읽어 비교한다. 같으면 그 사이 이력이 바뀌지 않았다고 보고 결과를 낸다.
   > **낙관적 읽기(optimistic read)** — 잠금 없이 읽고, 읽은 뒤 버전이 그대로인지 확인해 맞으면 채택, 아니면 다시 읽는 방식. 쓰는 쪽을 막지 않는 대신 읽는 쪽이 재시도 비용을 진다.

3. **데이터가 바뀌는 쓰기마다 버전 값도 바뀌어야 하고, 버전 값은 데이터보다 늦게 바뀌면 안 된다.**\
   seqlock 은 이것을 쓰기 시작·끝에 올리는 카운터로 보장한다. 이 사례의 버전 값은 쓰는 쪽(git fetch)이 스스로 갱신하는 경계 목록이라, 그 갱신 순서를 읽는 쪽이 고를 수 없었다.\
   실제로 fetch 가 새 객체는 받았는데 경계 목록을 아직 확정하지 않은 짧은 틈에는 조회가 일시적으로 500 이 될 수 있다 — 명세에 알려진 한계로 적었다(틀린 내용이 아니라 오류로 나오고, 새로 고치면 풀린다).\
   일반론으로, 내용 비교로 버전 값을 쓰면 값이 바뀌었다가 되돌아온 경우(ABA)를 구분하지 못한다. 이 사례 기록에는 그 경우의 분석이 없다.
   > **seqlock** — 쓰는 쪽이 쓰기 앞뒤로 순번을 올리고, 읽는 쪽은 읽기 앞뒤 순번이 같고 짝수일 때만 결과를 믿는 동기화 방식.

4. **쓰는 쪽이 계속 바쁘면 읽는 쪽이 끝없이 돈다. 그래서 다시 하기는 한 번, 기한은 조회 하나 전체에 건다.**\
   두 번 모두 버전 값이 다르면 503 과 "배포가 이력을 바꾸는 중 — 잠시 뒤 새로 고침"으로 답한다.\
   기한(3초)은 재시도를 포함한 조회 전체에 하나만 걸었다 — 시도마다 기한을 새로 주면 최악의 응답 시간이 기한 × 시도 수가 된다. 시도마다 기한을 새로 주는 변형을 넣으면 깨지는 테스트를 따로 두었다.

5. **기한 초과는 결과를 쓰지 않으므로, 결과의 일관성을 따질 필요가 없다.**\
   비교는 "이 결과를 내보내도 되나"를 가르는 절차다. 내보낼 결과가 없으면 비교도 필요 없고, 기한이 지난 뒤 경계 목록을 또 읽는 것은 시간만 더 쓴다.

6. **같은 결함을 두 번째 고친다는 사실 자체가 근거였다.**\
   앞 리뷰에서 경계 판정을 붙였고, 다음 리뷰에서 그 판정과 git 명령 사이의 경쟁이 나왔다. 여기에 명령마다 방어를 또 붙이면 다음 리뷰에서 또 다른 사이가 나온다.\
   그래서 경계 판정(부모 없음 · 관계 · 범위 온전함)을 모두 "앞에서 읽은 한 번의 목록"으로만 하게 바꾸고, 그 목록이 끝까지 유효했는지를 한 곳에서 확인했다.

7. **저장소 명령을 감싸는 가짜 실행 파일이 명령 도중 경계 파일을 바꾸게 한다.**\
   감싸개가 한 번만 바꾸면 두 번째 시도에서 옳은 답이 나와야 하고, 매번 바꾸면 503 이 나와야 한다 — 두 사례를 시간 경쟁 없이 결정적으로 만든다.\
   이와 별도로 실제 경쟁도 돌렸다: 배포를 흉내 낸 fetch 300바퀴와 동시 조회에서 틀린 diff 0건(구현 쪽 스모크).

## 문제 구조 (추상화 코드)

### 변형 A — 명령마다 다른 순간의 상태를 본다
① 문제 코드
```go
func detail(repo Repo, sha string) (Detail, error) {
    boundary := repo.readBoundaryList()          // t0
    if boundary[sha] { return Detail{}, errParentMissing }
    files := repo.listFiles(sha)                 // t1  ← 이 사이 fetch 가 경계를 옮길 수 있다
    patch := repo.patch(sha)                     // t2  ← 부모 없는 커밋이 되어 "전부 추가"
    return Detail{files, patch}, nil
}
```
② 고친 코드
```go
const attempts = 2

func readUnchanged(ctx context.Context, repo Repo, read func(boundary Set) (any, error)) (any, error) {
    for i := 0; i < attempts; i++ {
        before, err := repo.readBoundaryList()
        if err != nil { return nil, err }
        data, readErr := read(before)            // 경계 판정은 before 하나로만
        if errors.Is(readErr, errTimeout) {
            return nil, readErr                  // 결과를 쓰지 않으니 비교하지 않는다
        }
        after, err := repo.readBoundaryList()
        if err != nil { return nil, err }
        if after.Equal(before) {
            return data, readErr                 // 오류 결과도 같은 이력 위의 답이다
        }
    }
    return nil, errChanging                      // 503 — 쓰는 쪽이 바꾸는 중
}
// ctx 의 기한은 이 함수 전체(재시도 포함)에 하나
```
깨진 것: 여러 번의 읽기가 같은 시점을 본다고 가정했다 — 쓰는 쪽과 잠금을 공유하지 않으면 그 가정은 성립하지 않는다.

### 변형 B — 결정적 재현
```go
// 저장소 명령을 감싸는 스크립트: 실제 명령을 실행하고, 그 뒤 경계 파일을 다음 값으로 바꾼다
installWrappedRepoCommand(t, changeBoundaryOnce(repo))   // 한 번 → 두 번째 시도가 옳은 답

```
깨진 것 없음 — 경쟁 창을 시간이 아니라 순서로 만들어, 앞뒤 비교가 실제로 결과를 가르는지 확인한다.
