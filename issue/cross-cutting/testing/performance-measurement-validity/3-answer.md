## 정답
<!-- 질문 1:1 대응 -->

1. **생존자 편향.** 성공 요청만 집계하는 지표라면 실패한 요청은 지연 분포에 들어가지 않는다(도구·집계 설정마다 다르다 — 실패까지 포함해 집계하면 이번엔 빠른 거절이 분포를 왜곡한다. 어느 쪽이든 오류율이 크게 다른 조건의 지연은 같은 모집단이 아니다).\
오류율 71%인 조건의 p95는 전체 요청이 아니라 **실패하지 않고 살아남은 요청**의 지연이므로, 오류율이 낮은 조건(5.4%)의 p95와 같은 모집단이 아니다.\
공정한 비교는 **성공 처리량**(초당 성공 요청 수)을 함께 보는 것이다 — 실측에서 결론은 "지연 8.6배 단축"이 아니라 "처리량 129 → 427 req/s, 3.3배"로 재서술됐다.\
같은 기록에서 세그먼트 수 같은 교란 변수를 정규화하고, 대리 실험 결과를 본 실측으로 쓰지 않으며, "무실패 + 낮은 p95"는 포화 미도달이라는 점도 함께 바로잡았다.
   > **survivorship bias** — 걸러지고 남은 표본만 보고 전체를 판단하는 편향. 실패가 표본에서 빠지면 성과가 과대평가된다.

2. **JIT·분기 예측.** 내림차순 데이터에서 안쪽 비교가 **항상 거짓**이면 분기 예측이 완벽하게 맞고, JIT가 그 루프를 강하게 최적화한다.\
그래서 이론상 O(n·k)인 변종이 3×10⁹회 규모에서도 1초대에 끝났고, O(n²)가 20만 건에서 1.54초로 통과했다.\
교정은 두 가지다: 입력 규모를 상향(100만×k=5만)하고 루프 제거를 막는 체크섬을 넣는 것, 그리고 **타이밍 대신 결정적 계수기**(이동 횟수·트리 높이·회전 수·방문 수)로 한계를 재는 것.\
계수기는 하드웨어·JIT 상태와 무관하게 알고리즘의 일의 양을 직접 센다.
   > **JIT warm-up** — 런타임이 실행 중 뜨거운 코드를 기계어로 최적화하기까지의 구간. 이 전후의 측정값은 같은 코드라도 다르다.

3. **쿠폰 수집가.** 무작위로 키를 뽑을 때 "아직 안 본 키"를 만날 확률은 캐시가 찰수록 줄어서, 전 키를 한 번씩 보는 데는 키 개수보다 훨씬 많은 요청이 필요하다.\
축출 없는 캐시의 히트율은 이 속도로 수렴하므로, 80초 워밍업 뒤 캐시가 6,638/10,000만 차 있었다 — 히트율이 **과소평가**됐다(가설에 불리한 방향의 편향).\
결정적 프리웜은 무작위 요청 대신 **전 키를 정확히 한 번씩** 요청해 채운다(부하 도구의 공유 반복 실행기로 반복 번호를 키 인덱스로 사용).
   > **coupon collector** — n종을 무작위로 모을 때 전부 모으는 데 기대 약 n·ln n 번이 필요한 문제.

4. **생성기도 측정 대상.** 도착률(arrival-rate) 실행기의 사전 할당 VU는 **시나리오마다 곱해지고**, VU마다 런타임 메모리가 있다.\
계단형 부하를 한 런의 여러 시나리오로 잡아 합계 15,000 VU가 되자 초기화가 1,730 근처에서 멈추고 SSH가 끊긴 뒤 호스트 전원 재시작까지 갔다.\
교정은 계단마다 **런을 분리**(런이 끝나면 VU 해제)하고 사전 할당을 상한(≤ 2,000) 아래로 두며, 생성기를 **메모리 캡을 건 컨테이너**로 돌려 최악에도 컨테이너만 죽게 하는 것이다.\
무선 경로의 생성기가 목표 8,000에 4,623(드롭 42%)만 낸 것은 **생성기·네트워크 경로의 한계**가 측정에 섞였다는 뜻이다 — 그 결과는 대상 시스템의 한계가 아니므로 생성기를 실격시키고 유선 생성기를 쓴다.

5. **무작위 기저선.** 두 집합이 같은 모집단에서 서로 무관하게 뽑혀도 모집단 대비 집합 크기에 따라 **우연히 겹치는 기대값**이 있다.\
실측에서 교집합 0.49는 무작위 기저선 0.5와 거의 같아 "중복"이 아니라 "무관"의 신호였다.\
지표는 기저선을 뺀 **초과분**으로 정의해야 신호가 된다.

6. **데이터 부재.** 입력 배열이 비어 있어도 부하 스크립트는 에러 없이 돌고, 캐시 실험은 ~100% 히트율 같은 "좋은 숫자"를 낼 수 있다.\
측정 파이프라인은 실패를 내지 않으므로, 입력 데이터가 실제로 있는지를 측정 전에 **따로 확인**해야 한다(이 사례의 교정 방법은 원 기록에 남아 있지 않다 — 여기서는 원리만 적는다).\
테스트가 대상이 0개여도 초록을 내는 그린 위장과 같은 구조다: 측정 장치가 **실패할 수 있는 조건**을 갖추지 않으면 출력은 증거가 아니다.

## 방안 비교

같은 원리("측정 장치·집계 규칙이 결과에 섞인다")가 계단식 부하 측정의 **해석 단계**에서 나타난 세 가지. 조건: 도착률 50건/s에서 1.5배씩 13계단(마지막 6,487건/s), 단계 오류율이 기준을 넘으면 중단, 조건 10개를 며칠에 걸쳐 순서대로 측정.

### 비교 1 — 계단식 부하의 한계값: 점값으로 읽기 vs 구간·절단으로 읽기
```text
# 점값으로 읽기 (과장되는 방식)
한계 A = 378, 한계 B = 2,867  →  "7.6배"(점값끼리 나눈 값)
한계 C = 6,294 (마지막 계단까지 통과)  →  "C의 한계는 6,294"
# 구간·절단으로 읽기 (고친 서술)
한계 = "기준을 지킨 마지막 계단" → 진짜 한계는 [그 계단, 다음 계단) 사이
A ∈ [378, 567)   B ∈ [2,867, 4,325)   → 배수는 구간으로: 약 5~11배
C = 마지막 계단까지 통과 → "≥6,294"(상한 절단 — 진짜 한계 미관측), 배수도 "≥"
```

| 읽는 법 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 점값 | 계단이 충분히 촘촘함, 마지막 계단 전에 한계가 옴 | 없음 | 1.5배 간격이 배수·백분율을 과장(차이 한 칸을 "32%"로), 상한 절단을 실측 한계로 오인 | 계단 간격이 요구 정밀도보다 훨씬 작을 때 |
| 구간 + `≥` 표기 | 계단 설계(간격·상한)를 결과와 함께 기록 | 표기·계산 규칙 추가 | 구간이 넓어 작은 효과는 "판별 불가"로 남음 | 기하급수 계단, 상한까지 통과한 조건이 있을 때 |

**결론**: 계단식 부하의 한계는 항상 **계단 해상도 안의 구간**으로 읽고, 마지막 계단까지 통과한 결과는 `≥`로 절단을 표시한다 — 차이가 계단 한 칸이면 "방향만 일관"까지만 말한다.\
같은 계열의 함정: "처음 기준을 넘은 단계의 직전"이라는 엄격 한계 규칙은 시작 직후 한 번의 지연 튐(첫 단계 p99 26.8초)에도 한계를 0으로 만든다 — 중앙값으로 판정하고 그런 회차를 표시했다.

### 비교 2 — 실패 분류: 지연 시간 기준 vs 오류 코드 기준
```python
# 지연 기준 (첫 산출 — 틀림)
kind = "timeout" if r.latency >= 29.9 else "conn_fail"     # 부하 도구는 타임아웃 요청의 지연을 0 근처로 기록
                                                            # → 타임아웃이 연결 실패로 오분류
# 오류 코드 기준 (고친 산출)
kind = {"request_timeout": "timeout", "dial_timeout": "conn_setup_fail",
        "conn_reset": "cut", "eof": "cut"}.get(r.error_code, "other")
# 검증: 한 회차에서 도구의 경고 로그 메시지 수와 정확히 일치 (타임아웃 7,710 · 연결 수립 2,077 · reset 737 · EOF 326)
```

| 분류 기준 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 지연 시간 | 실패 요청의 지연이 실제 대기 시간으로 기록됨 | 원시 지연만 있으면 됨 | 도구가 실패 요청의 지연을 다르게 기록하면 조용히 오분류(오류 없이 그럴듯한 표가 나옴) | 도구의 실패 지연 기록 방식을 확인한 뒤에만 |
| 오류 코드 | 도구가 실패 종류별 코드를 요청 단위로 남김 | 코드 체계 확인, 독립 출처(경고 로그)와 대조 | 코드 체계가 바뀌거나 미지 코드가 생기면 "other"로 모임 — 그 양을 감시해야 함 | 실패 원인이 결론에 들어가는 모든 분석 |

**결론**: 실패는 **도구가 붙인 오류 코드**로 분류하고, 분류 결과를 한 회차라도 독립 출처(도구 로그)와 수치 대조한다 — 지연 시간은 "성공한 요청의 성질"로만 쓴다.\
이 분류로 "타임아웃"이라 부르던 실패에 연결 단계 실패가 섞여 있었음이 드러났다(과부하 단계 확정 실패 약 62% = 타임아웃 약 44% + 연결 수립 실패 약 12% + 연결 끊김 약 6%).

### 비교 3 — 조건 순차 측정의 드리프트: 조건 내 반복 vs 같은 시기 대조
```text
# 순차 측정 (이 사례)
day1: 조건 X × 5회 연속 → 범위 좁음
day2: 조건 Y × 5회 연속 → 범위 좁음
결론 "Y < X" ← 조건 내 범위가 좁다고 조건 사이 차이가 조건 효과라는 보장은 없음
               (같은 조건이 측정 시기 사이에 2배 움직인 전례가 있음)
# 같은 시기 대조 (일반 원리 — 이 사례에서는 하지 않음)
X, Y, X, Y ... 교차 배치  또는  기준 조건 X를 Y 직전·직후에 다시 측정
```

| 설계 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 조건 순차 + 조건 내 반복 | 측정 기간 동안 환경이 안정 | 배포·초기화가 조건당 1회라 가장 쌈 | 조건 사이 드리프트가 조건 효과로 둔갑 — 조건 내 반복 범위는 이를 제한하지 못함 | 기대 효과가 드리프트보다 훨씬 클 때(이 사례: 인덱스 효과 5배+, 대규모 데이터에서의 붕괴) |
| 교차 배치·기준 조건 재측정 | 조건 전환 비용을 감당할 수 있음 | 전환(재배포·재기동) 반복, 측정 시간 증가 | 전환 자체의 간섭(예열 상태 차이)이 생길 수 있음 | 효과가 작을 때(이 사례: 풀 크기 효과 = 계단 한 칸) |

**결론**: 같은 조건의 연속 반복은 **조건 안의 잡음**만 재고 조건 사이의 드리프트는 재지 않는다 — 큰 효과는 순차 측정으로도 말할 수 있지만, 계단 한 칸 수준의 차이는 교차 배치나 같은 시기 기준 재측정 없이는 "드리프트와 구분되지 않음"으로 적는다.\
이 사례는 이전 측정과의 환경 동일성 확인이 실패해(같은 조건이 2배 차이) 기준 조건을 같은 측정 묶음 안에서 다시 재는 데까지는 했지만, 작은 효과의 조건 쌍을 같은 시기에 다시 재지는 않았다.\
검증 기록: 2026-10-02 사건 기록 대조·추상화(Claude 초안) — 비교 3의 교차 배치는 일반 원리(사건에서 미적용).

## 방안 비교 — 포화 뒤의 더 낮은 단계가 "한계"로 집힌다

같은 원리("측정 장치·집계 규칙이 결과에 섞인다")가 계단식 부하의 **한계 산출 규칙**에서 나타난 또 하나의 형태(비교 1의 "엄격 한계 규칙" 함정과 같은 계열).\
조건: 도착률 계단(1.5배씩, 마지막 6,487건/s), 단계마다 성공 처리량·p99·오류율·목표 도달 여부(실제 도착률이 목표의 90% 미만이면 "목표 미달")를 기록.\
한계 규칙은 "기준(p99 < 500ms·오류율 < 1%)을 처음 어긴 단계의 직전 단계 성공 처리량"이었다.\
한 조건이 4,325건/s 단계에서 성공 약 1,994건/s로 포화했다(목표 미달). 그 단계는 기준을 지켜 통과했고, 다음 6,487건/s 단계는 성공이 약 670건/s 수준으로 떨어졌는데도 p99 기준을 만족해 또 통과했다.\
규칙은 마지막 통과 단계의 값을 한계로 집어 엄격 한계 708건/s 등을 보고했다 — 실제 성공 상한(포화점 약 1,994건/s)의 1/3 수준이다.\
결과 문서 리뷰에서 엄격 한계와 포화점의 어긋남으로 드러났고, 문서는 포화점을 그 조건의 상한으로 고쳐 적었다(산출 규칙 수정은 후속 항목).

```
단계 목표(건/s)   …   4,325                      6,487
성공(건/s)        …   ~1,994 (목표 미달 = 포화)   ~670
기준(p99·오류)    …   통과                        통과   ← 붕괴 뒤 단계도 지연 기준은 지켰다
원 규칙            last = 1,994 → 뒤 단계 값으로 덮어씀 ⇒ 보고 한계 708 등   (단조성·목표 도달을 보지 않는다)
고친 해석          포화 단계에서 멈춤                  ⇒ 상한 ≈ 1,994 (포화점)
```

### 방안 1 — 기준 위반만 보는 규칙 (원 규칙)
```python
def strict_limit(stages):
    last = 0
    for s in stages:                                   # 단계 순서대로
        if s.p99 is None or s.p99 >= 500 or s.err >= 0.01:
            return last
        last = s.ok_rps                                # 통과 = 값 갱신 — 앞 단계보다 낮아도 덮어쓴다
    return last
```

### 방안 2 — 목표 미달(포화) 단계에서 멈추고 포화점을 함께 보고 (고친 해석 — 산출 코드 반영은 후속, 아래는 일반 형태)
```python
def strict_limit(stages):
    last = 0
    for s in stages:
        if s.p99 is None or s.p99 >= 500 or s.err >= 0.01:
            return last
        last = max(last, s.ok_rps)
        if s.achieved_rps < 0.9 * s.target_rps:      # 목표 미달 = 포화 — 이후 단계는 붕괴 뒤 상태
            return last
    return last

saturation = max(s.ok_rps for s in stages)            # 함께 보고: 한계 ≪ 포화점이면 규칙 산물을 의심
```

| 규칙 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 기준 위반만 | 부하가 오르면 지연·오류가 단조롭게 나빠진다 | 없음 | 포화 뒤 처리량이 무너져도 지연·오류 기준을 지키면(빠른 거절 등) 더 낮은 값으로 덮어쓴다 — 오류 없이 그럴듯한 숫자 | 포화가 곧 지연 폭증으로 드러나는 시스템 |
| 2. 포화에서 멈춤 + 포화점 병기 | 단계마다 목표 대비 실제 도착률·성공 처리량을 기록한다 | 판정 칸 1개, 해석 규칙 추가 | 측정 경로(부하 생성기) 쪽 한계로 목표 미달이 나면 시스템 포화로 오인 — 생성기 자원을 따로 확인해야 함(변형 D) | 거절이 빠르게 끝나 지연만으로 포화가 안 보이는 조건이 섞인 비교 |

**결론**: 계단식 부하의 한계는 "기준을 지켰는가"만이 아니라 **"부하가 실제로 들어갔는가(목표 도달)"와 "처리량이 계속 올랐는가"**를 함께 봐야 한다 — 포화 뒤 단계는 시스템의 한계가 아니라 붕괴 뒤 상태를 잰다.\
보고에는 엄격 한계와 포화점을 나란히 두고, 둘이 크게 어긋나면(한계 ≪ 포화점) 숫자를 쓰기 전에 단계별 원자료를 연다 — 이 사례도 그 어긋남으로 발견했다.\
검증 기록: 2026-10-09 사건 기록 대조·추상화(Claude 초안) — 방안 2의 코드는 일반 형태(원 기록의 후속 항목, 산출 코드에 아직 반영하지 않음).

## 방안 비교 — 계단 부하에서는 붕괴가 단계 경계 어디에 오느냐가 결과가 된다

같은 원리("측정 장치·집계 규칙이 결과에 섞인다")가 **계단식 도착률 부하의 설계 자체**에서 나타난 사례(비교 1의 "계단 해상도"와 같은 계열 — 여기서는 해상도가 아니라 **위치**와 **교락**이 문제다).\
조건: 도착률 계단 1.5배씩, 한 단계 약 30초, 한계 = "기준을 지킨 마지막 단계".\
한 방식이 4,325건/s 단계를 p99 5~17ms로 26~27초 버티다가 **단계 끝 약 4초를 남기고** 무너졌다(10회 모두 같은 초).\
그 단계 전체가 실패로 판정돼 엄격 한계가 한 칸 아래(4,300 → 2,866, −33%)로 떨어졌다 — 같은 조건의 다른 회차는 붕괴가 단계 경계 뒤에 와서 4,150~4,262였다.\
다음 단계는 모든 방식이 과부하인 구간이라, 붕괴가 얼마나 지속되는지도 이 설계로는 관측할 수 없었다(처음 문서는 "마지막 4초에만"이라고 썼다가 리뷰에서 "지속 기간 관측 불가"로 고쳤다).\
또 도착 계획이 고정이라 붕괴 시점의 **누적 처리량(약 37만 건)**과 **경과 시간**이 늘 함께 움직였다 — "누적 행 수 때문"과 "시간(주기 작업) 때문"을 가를 수 없었다.

```
단계(건/s)   ... 2,866 │ 4,325 ───────────────────────────│ 6,487 (모든 방식 과부하)
회차 a                 │ 정상 ...................... 붕괴 │      → 단계 실패 → 한계 2,866
회차 b                 │ 정상 ............................│ 붕괴 → 단계 통과 → 한계 ~4,2xx
                                                 ↑ 같은 지점(같은 누적 쓰기량)이 경계 앞/뒤
누적 처리량 ∝ 경과 시간 (도착 계획 고정)  →  "무엇이 쌓여서"인지 "시간이 지나서"인지 구분 불가
```

### 방안 1 — 계단 부하 하나로 한계와 원인을 함께 읽는다 (처음 설계)

```text
cause = "누적 약 37만 건에서 무너짐"                      # 누적과 시간이 교락 — 판정 불가
```

### 방안 2 — 고정 도착률 두 수준으로 누적과 시간을 떼어 놓는다 (후속 설계)
```text
for rate in [4200, 2000]:                                # 계단 대신 일정 도착률 6분
    run(rate, duration=360s)
# 붕괴 시점의 누적 처리량: 2,000/s ≈ 30~32만 · 계단 ≈ 37만 · 4,200/s ≈ 47~56만  → 누적 행 수가 아니다
# 체크포인트 끔·버퍼 4배 조건에서도 같은 지점        → 주기 작업(시간)도 아니다

# 2,000/s: 처리량은 6분 내내 유지, 지연 스파이크만 / 4,200/s: 모든 방식이 지속 못 함
```

| 설계 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 계단 하나 | 붕괴가 부하 수준의 함수다(시간·누적과 무관) | 회차 하나로 여러 수준을 훑는다 | 누적·시간에 의존하는 붕괴는 **경계에 대한 위치**로 한 칸씩 갈린다 — 같은 조건이 −33%와 정상으로 나뉜다, 지속 기간·원인(누적 vs 시간)은 관측 불가 | 포화가 부하 수준에서 바로 오는 시스템의 대략적 상한 탐색 |
| 2. 고정 도착률 여러 수준 | 수준 수만큼 회차를 더 돌릴 수 있다 | 회차 증가(이 사례: 수준 2개 × 6분) | 고른 수준 사이의 한계는 여전히 모른다 | "무엇이 쌓이면 무너지나"를 가려야 할 때, 지속 처리량이 결론일 때 |

**결론**: 시간·누적에 따라 상태가 변하는 시스템을 계단으로 재면, 한계 값은 시스템의 성질이 아니라 **붕괴 지점과 단계 경계의 상대 위치**를 반영한다 — 계단 결과에서 회차 간 한 칸 차이가 보이면 먼저 초 단위 시계열을 연다.\
원인 판정(누적 행·시간·쓰기량)은 도착률을 달리한 고정 부하처럼 **교락을 깨는 설계**로 한다 — 이 사례는 그렇게 해서 두 후보(누적 행 수·주기 작업)를 모두 기각하고 세 번째(누적 쓰기량)로 좁혔다.\

## 방안 비교 — 원인 판독을 오도하는 두 가지: 전체 구간 평균과 정의상 참인 지표

같은 원리(측정 파이프라인이 오류 없이 "그럴듯한 증거"를 낸다 — 질문 6의 데이터 부재와 같은 구조)가 **원인 진단의 근거 고르기**에서 두 번 나타났다.

**사례 ① 전체 평균이 상태 전환을 가렸다.** 저장 장치만 따로 재는 합성 쓰기 시험(쓰기마다 동기화)에서 동기화 지연 평균이 2.44ms(p50 1.09·p90 4.11ms)로 나왔다.\
DB 실측의 장치 flush 지연(약 0.41ms)보다 훨씬 커서, "이 시험은 쓰기 패턴이 달라 동기화가 원래 느리다 — DB와 다른 부하다"로 해석하고 패턴을 바꾼 시험을 새로 설계했다.\
나중에 10초 칸으로 다시 보니 전환 전 flush 평균은 0.421~0.427ms로 DB와 같았고, 약 110~120초(누적 약 7.8GB)에서 1.9~2.2ms로 **꺾여 있었다** — 2.44ms는 꺾인 뒤 구간이 대부분을 차지한 평균이었다.\
즉 옛 시험도 DB와 같은 서명을 이미 재현하고 있었는데, 평균 하나가 그것을 "다른 부하"로 보이게 했다(새 시험의 결론은 바뀌지 않았고 오히려 강화됐다).

**사례 ② 정의상 0일 수밖에 없는 지표를 증거로 썼다.** "저장소를 메모리 파일시스템으로 옮기면 쓰기 반감이 사라진다"의 근거로 "그 조건 12회 중 쓰기 반감 0회"를 적었다.\
그런데 반감 탐지는 컨테이너의 **블록 장치 쓰기 카운터**로 했고, 메모리 파일시스템 쓰기는 블록 장치를 지나지 않는다 — 그 카운터는 회차 내내 수십 kB에 머물렀다.\
반감이 "사라진" 것이 아니라 **잴 대상이 없었다** — 어떤 결과여도 0이므로 증거가 아니다. 실제 근거는 처리량 유지·붕괴 시점 이동·대기 이벤트의 변화였다(문서 검토 중 정정).

```
사례 ①  flush 지연 ─────────────┐ 0.42ms
                                 └────────────────────── ~2ms
        전체 평균 = 2.44ms  →  "원래 느린 부하"로 오독      (전환 전/후로 나누면 0.42 → ~2)

사례 ②  지표 = 블록 장치 쓰기 카운터
        디스크 조건   : 9GB까지 증가 → 반감 탐지 가능
        메모리 조건   : 항상 ~0     → 반감 "0회"는 관측 결과가 아니라 정의의 결과
```

### 방안 1 — 실행 전체 요약값·쉽게 나오는 카운터로 판독 (처음)

### 방안 2 — 전환점 전후 창으로 나누고, 지표가 실패할 수 있었는지부터 확인 (고친 판독)
```python

evidence["memory_fs"] = [throughput_held, wall_moved, wait_events_changed]
```

| 판독 방법 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 전체 평균·편한 카운터 | 측정 구간이 한 상태(정상 상태)다, 지표가 그 조건에서 변할 수 있다 | 요약 하나 | 상태 전환이 있으면 평균은 **어느 상태도 아닌 값**이 된다, 정의상 고정인 지표는 어떤 가설도 "지지"한다 | 전환 없음이 확인된 구간, 같은 경로를 지나는 조건끼리의 비교 |
| 2. 전환점 탐지 + 전후 창 + 반증 가능성 확인 | 시간 칸 시계열이 남아 있다, 지표가 어느 층을 세는지 안다 | 시계열 보관·탐지 규칙·조건별 지표 점검 | 전환점 탐지 규칙(임계·창 크기)이 또 하나의 측정 장치가 된다 | 원인 판독·조건 간 서명 비교 |

**결론**: 원인을 읽기 전에 두 가지를 묻는다 — 이 구간에 **상태 전환이 있었나**(있으면 평균이 아니라 전후로 나눈다), 이 지표가 **이 조건에서 다른 값을 낼 수 있었나**(없으면 근거에서 뺀다).\
실행 전체 평균은 "전환이 없다"가 확인된 뒤에만 비교에 쓴다 — 이 사례는 그 평균 때문에 이미 성립한 재현을 놓치고 시험을 한 번 더 설계했다.\
검증 기록: 2026-10-11 사건 기록 대조·추상화(Claude 초안).

## 방안 비교 — 집계 창이 멈춤을 가리고, 조건마다 다른 준비 절차가 효과로 둔갑한다

같은 원리("측정 장치·집계 규칙이 결과에 섞인다")가 고정 도착률(1초 4,200건) 부하로 조건 몇 개를 비교한 측정에서 두 번 나타났다.\
하나는 꼬리 지표의 **집계 창 길이**, 하나는 조건마다 달랐던 **측정 전 준비 절차**다.\
앞의 두 방안 비교(「원인 판독을 오도하는 두 가지」의 사례 ① 전체 평균, 「계단 부하에서는 붕괴가…」의 누적·시간 교락)와 같은 계열이지만 처방이 다르다 — 거기서는 전환점 전후로 창을 나누고 고정 도착률로 교락을 깼고, 여기서는 창 길이를 찾으려는 사건 길이에 맞추고(비교 4) 준비 절차를 조건마다 같게 맞춘다(비교 5).

### 비교 4 — 꼬리 지표의 집계 창: 30초 구간 p99 vs 1초 단위 꼬리
```text
# 30초 구간 p99 (처음 지표 — "가장 나쁜 구간 p99")
창 하나 = 30초 × 4,200건 ≈ 126,000건
앱이 0.1초 멈춘 1초: 묶인 요청 약 500건이 200~300ms   → 창 안 비중 약 0.4% (< 1%)
→ p99는 그 꼬리를 보지 못한다: 가장 나쁜 30초 구간 p99 = 4.2ms
# 1초 단위 꼬리 (고친 지표 — 측정 전에 판정 지표를 바꿈)
초마다 p99·최대 응답 → 1초 p99 최대 = 283ms, 최대 응답 > 50ms인 초 = 8개 (= 그 회차의 Full GC 8회)
```
```python
per_sec = group_by_second(requests, after=ramp_end)            # 램프 밖, 부하 생성기 타임스탬프의 정수 초
thin = {s for s, rs in per_sec.items() if len(rs) < planned_rate / 2}   # 얇은 초(표본 부족)는 p99에서 제외
p99_max  = max(p99(rs) for s, rs in per_sec.items() if s not in thin)
slow_sec = sum(1 for rs in per_sec.values() if max(rs) > 50)
report(p99_max, slow_sec, secs_used=len(per_sec) - len(thin), secs_planned=duration)  # 집계 초/계획 초도 같이
```

| 지표 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 긴 창(30초) 구간 p99 | 나쁜 사건이 창 안 요청의 1%를 넘게 이어진다 | 표본이 많아 안정적 | 창보다 훨씬 짧은 멈춤(0.1초)이 창 안 비중 1% 미만이라 **0으로 보인다** — 오류 없이 "꼬리 깨끗함" | 몇 초 이상 이어지는 저하(디스크 포화 같은 벽) |
| 1초 단위 꼬리(p99 최대·느린 초 수·최대 응답) | 1초 표본이 p99를 낼 만큼 크다 | 초마다 집계, 얇은 초 처리 규칙 | 표본이 적은 초는 p99가 흔들린다 — 얇은 초를 빼고 그 수를 보고해야 한다, 타임스탬프 해상도(정수 초)보다 짧은 구조는 여전히 못 본다 | 찾으려는 사건 길이가 창 길이에 가까울 때 |

**결론**: 집계 창은 **찾으려는 사건의 길이**에 맞춘다 — 창 안 비중이 백분위 꼬리(1%)보다 작은 사건은 그 백분위로 보이지 않는다.\
긴 창 지표는 버리지 않고 참고로 둔다(오래 가는 저하에는 그쪽이 안정적이다).\
이 사례에서는 판정 지표를 **측정 전에** 1초 단위로 바꿨고, 1초 지표의 느린 초가 GC 로그의 Full GC 시각과 일치하는 것을 확인했다.

### 비교 5 — 조건마다 다른 준비 절차: 조건별 준비 대기 vs 공통 기준점에서 같은 시간
```text
# 조건별 준비 대기 (처음 하네스)
시드 끝 ─▶ [대조 작업이 있는 조건만] 첫 대조 바퀴 대기 30초 ─▶ 부하 시작
  → 부하 시작이 DB 준비 뒤 80~88초(대조 조건) vs 53~55초(그 밖)
  → DB 자동 정리(autovacuum)가 도는 시점과 부하 램프가 조건마다 다르게 겹침
  → 대조 없는 조건 9회 전부 램프 붕괴(시작 26~36초, p99 최대 약 4.2초), 대조 조건 6회는 없음
  → "대조를 켜면 p99 −42%"·"선점당 WAL −33%" = 조건 효과가 아니라 교란
# 공통 기준점에서 같은 시간 (고친 하네스)
시드 끝 ─▶ 대기점(70초)까지 각 조건의 준비 ─▶ 목표 87초(±5초)에 첫 요청 ─▶ 부하
  + 대기 중 DB 상태 기록 · 실제 시드 끝→첫 요청 시간을 기록하고 허용 밖이면 회차 실패
  → 재측정 48회: 85.81~88.48초(퍼짐 2.68초), 램프 붕괴 전 조건에서 없음, 같은 비교 p99 +2.2%(차이 없음)
```

| 설계 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 조건별 준비 대기(각 조건이 필요한 것만 기다림) | 대기 시간 차이가 시스템 상태를 바꾸지 않는다 | 가장 짧다 | 백그라운드 작업(자동 정리·캐시·JIT)의 위상이 조건마다 달라져 **시작 상태 차이가 조건 효과로 보인다** — 회차 반복으로는 줄지 않는다(같은 조건은 매번 같은 위상) | 시작 상태에 민감한 백그라운드 작업이 없음을 확인한 경우 |
| 공통 기준점 + 같은 시간 + 실측 대조 | 모든 조건의 준비가 그 시간 안에 끝난다 | 회차마다 대기가 길어진다(가장 긴 조건에 맞춤), 넘침 검사 필요 | 기준점 밖의 차이(별도 컨테이너 기동 등)는 남는다 — 이 사례에서도 한 조건만 DB 기동→부하 시작이 약 7초 길었고 그 조건의 작은 잔여 차이는 원인 미확인으로 남겼다 | 조건이 다른 준비 단계를 가질 때의 기본값 |

**결론**: 조건 비교에서 **측정 전 절차는 처리 변수가 아닌 한 모든 조건에 같아야 한다** — 다르면 그 차이가 결과에 섞이고, 같은 조건을 여러 번 반복해도 드러나지 않는다.\
준비 시간이 조건마다 다를 수밖에 없으면 가장 긴 쪽에 맞춘 **고정 시각**을 두고, 실제 시각을 기록해 허용 밖이면 회차를 버린다.\
이 교란은 "효과가 특정 조건 묶음에만 몰려 있다"는 리뷰 지적에서 원시 데이터 대조로 찾았다 — 효과가 처리 변수와 무관한 절차 차이와 같은 경계로 갈리면 교란부터 의심한다.
   > **교란 변수(confounder)** — 처리 변수와 함께 움직여 결과에 영향을 주는 다른 변수. 처리 효과와 구분되지 않는다.

검증 기록: 2026-10-15 사건 기록 대조·추상화(Claude 초안) — 비교 4의 "창 안 비중 약 0.4%"는 기록된 수(30초 × 4,200건, 묶인 요청 약 500건)로 계산한 값.

## 방안 비교 — 생성기 호스트의 이웃이 꼬리를 만들고, 진단 기록이 생성기를 흔들고, 귀무가설이 자기상관을 지운다

같은 원리("측정 장치·조건이 결과에 섞인다")가 고정 도착률 부하(1초 4,200건)의 **꼬리 지연 원인 찾기**에서 세 번 나타났다.\
하나는 부하 생성기가 도는 호스트의 다른 프로세스(비교 6), 하나는 생성기에 켠 런타임 진단 기록(비교 7), 하나는 주기 검정의 귀무 모형(비교 8)이다.\
변형 D(생성기 자원 한계)와 질문 5(무작위 기저선)의 연장이다 — 생성기는 자기 부하가 아니어도 **같은 호스트의 남의 부하**에 흔들리고, 기저선은 "무작위"라는 이름만으로 맞지 않는다.

### 비교 6 — 주기 튐의 위치 찾기: 바뀐 것을 되돌리기 vs 층마다 측정기를 두기

```
관측: 약 26초마다 1초 최대 응답 50~150ms (서버 GC 수집기 종류와 무관)
지연 분해: 서버가 실제로 멈춘 초 → 늦어짐이 전부 '서버 응답 대기'
           주기 튐 초             → 생성기 안 구간(연결 대기·보내기·받기) 중앙 30~57ms = 생성기가 잠깐 멈춘 모양

[생성기 호스트] ─ 주 생성기 ───────────────▶ [서버] ─ 앱
   ├ 측정기 P (별도 프로세스, 상태를 안 바꾸는 GET 50건/s)     ├ 측정기 S (서버 안, 앱 직접)
   └ 이웃: 재시작 정책 컨테이너 — 약 24초마다 기동 실패 ↻
           기동마다 힙 약 9GB를 미리 건드림 · CPU 400%+ · 재시작 4,635회
판정:  주 생성기만 튐 → 생성기 프로세스 안
       P도 같이 튐    → 생성기 호스트 전체   ← 이 사례 (겹침 = 우연 기대의 약 9~12배)
       S까지 튐       → 서버 쪽도 의심 (이 사례: S도 일부 동반 — 멈춘 뒤 밀린 요청이 한꺼번에 나간 것으로 해석, 추정)
```

#### 방안 1 — 튐이 시작된 시점에 바뀐 것을 하나 골라 되돌린다 (처음 가설)
```text
튐 시작 = 생성기 호스트 재부팅 — 같은 재부팅에 생성기 버전·커널·패키지 약 120개가 함께 바뀜(같은 날 앱 조건도)
실험: 생성기 옛 버전 × 3 vs 새 버전 × 3
결과: 옛 버전도 3/3 주기 성분 유의 → "버전" 기각 — 남은 후보는 여전히 "그 재부팅 뒤의 무언가"
```

#### 방안 2 — 경로의 층마다 저율 측정기를 두고 함께 튀는지 본다 (이 사례에서 적용 — 이후 꼬리 측정에 상시 유지)
```text
spike(probe)  = 응답 > max(그 측정기 평소 p99 × 3, 20ms) 또는 코드 ≠ 200, 구간 = [끝 − 응답 시간, 끝]
overlap       = 주 생성기 느린 초 ±1초 창과 spike 구간의 겹침 / 우연 기대
                (최대 배수가 2 미만인 회차는 판정 불가, spike 0건 회차는 '겹침 없음')
→ 측정기 P가 같이 튐 → "호스트 전체"로 좁힘 → 호스트를 읽기 전용 점검 → 재시작을 반복하는 이웃 컨테이너 발견
→ 이웃을 없앰: 느린 초 회차당 7~14 → 0(꺼짐 20회 중 1회만 3개 — 따로 보지 않음), 주기 성분 유의 16/16 → 0/20
```
```sh
# 측정 조건으로 둔 측정 전 생성기 호스트 점검 (캠페인 시작 전, 기록 1행)
docker ps --format '{{.Names}} {{.Status}}'                  # Restarting·재시작 횟수가 느는 컨테이너가 없는지
docker inspect -f '{{.Name}} {{.RestartCount}}' $(docker ps -aq)
uptime                                                         # 부하 평균, 다른 실험 프로세스 확인
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 바뀐 것 되돌리기 | 원인이 "바뀐 것" 목록 안에 있고 하나씩 되돌릴 수 있다 | 회차 몇 개 | 여러 변화가 한 시점에 묶이면(교락) 하나를 기각해도 후보가 좁혀지지 않는다, 측정 대상 밖 프로세스는 목록에 아예 없다 | 바뀐 것이 하나뿐일 때 |
| 2. 층별 측정기 | 측정기가 주 부하보다 훨씬 작다(이 사례 2.4%) | 측정기 2개 상시, 겹침 계산 | 층까지만 좁힌다 — 그 층 안의 원인은 따로 찾는다, 측정기가 같은 호스트 CPU를 나눠 써 측정을 바꿀 수 있다(기존 신호가 남는지로 확인) | 원인 위치가 불명일 때 기본 |

**결론**: 생성기 쪽이 의심되면 "바뀐 것"을 되돌리기 전에 **층마다 측정기를 두어 위치부터 좁힌다** — 위치가 좁혀지면 후보가 "바뀐 것"에서 "그 층에서 도는 모든 것"으로 넓어지고, 이 사례처럼 측정과 무관한 이웃이 나온다.\
생성기 호스트도 측정 장비다 — 재시작 중인 컨테이너·부하 평균 점검을 측정 조건에 넣는다.\
원인을 없애자 사라졌지만 다시 넣는 실험(되돌리기)은 하지 않았다 — 켜짐·꺼짐 측정이 시간 순서로 갈려 그사이 다른 변화는 배제되지 않으므로 결론은 "강하게 지지"까지다(보강: 없앤 시점 앞뒤 회차의 갈림, 실측 기동 간격 23.4~27.9초와 주기의 일치).\
이웃 컨테이너가 기동에 실패한 이유는, compose 파일이 사라진 뒤 남아 있던 컨테이너를 재시작 정책이 재부팅 때 다시 띄우면서 없는 바인드 경로가 root 소유 빈 디렉토리로 새로 만들어져 데이터 경로 잠금을 못 얻은 것이다 — 기전은 [effective-uid-file-access](../../infra/effective-uid-file-access/) 변형 A·[silent-failure-vs-artifact](../../reliability/silent-failure-vs-artifact/) 변형 D와 같다.

### 비교 7 — 생성기 안의 진단 기록: 모든 회차에 켜기 vs 조건을 따로 두고 모양이 같을 때만 판정

```text
스모크(진단 기록 켬): 느린 초 72 (같은 조건 기록 없이 9~11) · 주기 성분 사라짐 · 느린 초 70/72가 긴 런타임 GC와 겹침
                       기록 353줄 / 430초
→ "기록을 켠 생성기"는 다른 생성기다 — 이 상태의 버전 비교는 기록의 효과를 잰다
```

#### 방안 1 — 진단 기록을 모든 회차에 켠다 (처음 계획)
```text
for version in [old, new]: run(loadgen=version, env={GC_TRACE: on})
```

#### 방안 2 — 기록 조건을 따로 두고, 기록 없는 같은 조건과 모양이 같을 때만 그 기록으로 판정한다 (측정 전 정정)
```text
conditions = [old, new, new + GC_TRACE]          # 버전 비교는 앞 둘, GC 대조는 셋째만
if shape(new + GC_TRACE) != shape(new):            # 느린 초 수 · 주기 성분
    verdict_gc = "판정 불가 — 기록이 측정을 바꿈"
gc_event = stw >= 5ms or wall >= 100ms             # 모든 GC를 세면 약 1.2초마다 → 우연 비율 1.0 — 가설이 참이어도 기각만 나온다
# 본 측정: 셋째 조건도 같은 모양(주기 성분 3/3, 느린 초 7~9) → 판정 가능 · 겹침 21/23 (우연 기대 1.9의 11.2배)
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 모든 회차에 기록 | 기록이 측정 대상의 동작을 바꾸지 않는다 | 회차 추가 없음 | 기록이 지연을 바꾸면 모든 비교가 "기록 켠 상태"의 비교가 되고, 기준 조건이 없어 바뀐 것조차 모른다 | 기록 비용이 무시할 만하다고 따로 확인된 경우 |
| 2. 기록 조건 분리 + 모양 대조 | 한 조건만큼 회차를 더 돌릴 수 있다 | 회차 1.5배 | 영향이 회차마다 다를 수 있다(이 사례: 스모크 72개 ↔ 본 측정 같은 모양) — 회차 단위로 대조해야 함 | 측정 장치 자체에 진단을 붙일 때 기본 |

**결론**: 측정 장치 안에 켜는 진단(런타임 추적·프로파일러)은 **그 장치의 측정을 바꿀 수 있다** — 진단은 별도 조건에 두고, 진단 없는 같은 조건과 결과 모양이 같을 때만 그 진단으로 판정한다.\
겹침이 강해도 방향은 따로다 — 긴 GC는 주기 튐과 21/23 겹쳤고 GC 자체도 약 26초 간격이었지만, 비교 6의 이웃을 없애자 함께 사라져 원인이 아니라 **호스트 정지의 동반 현상**으로 읽었다(정지 동안 GC 구간이 길게 잡혔다는 해석).\
겹침 검정에 쓰는 사건은 우연히 겹칠 비율이 충분히 작아야 한다 — 사건이 잦으면 어떤 가설이든 겹친다(「원인 판독을 오도하는 두 가지」의 정의상 참인 지표와 같은 구조).

### 비교 8 — 주기 검정의 귀무: 무작위 재배열 vs 자기상관을 보존한 대리 계열

```
검정: x = log1p(10ms 넘는 요청 수)의 1초 계열 → 주기도에서 24~31초 대역 최대 = 통계량
1초 계열은 이웃 값끼리 닮는다(자기상관)
  ├ 재배열 귀무: 순서를 섞어 주기뿐 아니라 자기상관까지 지움 → 귀무 주기도 = 평평
  │              관측 주기도는 자기상관 때문에 저주파(긴 주기) 쪽이 원래 높음 → 주기가 없어도 "귀무보다 크다"
  └ AR 대리 귀무: 자기상관(매끈한 스펙트럼)은 남기고 특정 주기만 없는 계열 → 그 위로 솟은 봉우리만 유의
```

#### 방안 1 — 무작위 재배열 귀무 (처음)
```python
stat = band_max(periodogram(x), 24, 31)
null = [band_max(periodogram(shuffle(x)), 24, 31) for _ in range(N)]
p = mean([n >= stat for n in null])
# 주기 없는 AR(1) φ=0.5 합성 계열에서 거짓 양성 13/40
```

#### 방안 2 — AR 모형 스펙트럼 대리 계열 귀무 (측정 전 정정)
```python
model = fit_ar(x, order=4)
def surrogate(rng):
    S = model.spectrum(freqs)                                 # 주기 없는 자기상관 스펙트럼
    amp = sqrt(S) * rng.amplitude(len(freqs))                 # 진폭도 무작위 — 위상만 섞으면 귀무 분포가 너무 좁다
    return inverse_fft(amp * exp(1j * rng.phase(len(freqs))))
rng = seeded(FIXED)
null = [band_max(periodogram(surrogate(rng)), 24, 31) for _ in range(1000)]
# 확인: 합성 AR(1) 거짓 양성 4.5~4.8% · 주기 없던 기존 20회 0/20 · 주기 있던 기존 24회 23/24
```

| 귀무 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 1. 재배열 | 관측값이 서로 독립이다 | 가장 쌈 | 자기상관 계열에서 저주파 대역이 원래 높아 거짓 양성이 크다(φ=0.5에서 약 33%) | 시간 순서가 의미 없는 독립 표본 |
| 2. AR 대리 계열 | 배경이 저차 AR로 근사된다 | 모형 적합 + 대리 계열 1000개 | 배경 모형이 틀리면(차수 부족·비정상 계열) 다시 거짓 양성·음성 — 거짓 양성률을 따로 재야 함 | 시계열에서 특정 주기를 검정할 때 |

**결론**: 귀무는 "무작위"가 아니라 **"가설이 말하는 것만 빠진 세계"**여야 한다 — 재배열은 주기와 함께 자기상관까지 지워, 자기상관만 있는 계열도 주기가 있는 것처럼 보이게 한다.\
귀무를 바꾼 뒤에는 거짓 양성률을 **주기 없는 합성 계열과 답을 아는 기존 회차**로 먼저 잰다 — 이 사례는 측정 전에 그렇게 확인하고 판정 규칙을 고정했다.\
질문 5의 무작위 기저선과 같은 원리다 — 기저선이 데이터의 구조(여기서는 시간 상관)를 보존하지 않으면 초과분은 신호가 아니다.
   > **대리 계열(surrogate)** — 귀무가설이 허용하는 성질(여기서는 자기상관 스펙트럼)만 보존해 만든 가짜 계열. 그 통계량 분포가 귀무 분포가 된다.
   > **AR(p) 모형** — 현재 값을 직전 p개 값의 선형 결합 + 잡음으로 보는 자기회귀 모형. AR(1)의 φ는 직전 값의 계수(클수록 이웃 값이 닮는다).
