# issue/cross-cutting/testing/property-test-cost-budget — 정리 (힌트)

## 전체 흐름

```text
무작위 테스트 비용 ≈ 케이스 수 × 케이스당 단계 수 × 단계당 검사 비용 × 빌드 계수
                     4 용량 × 30 시드   300          O(칸 × 버킷)        debug ≫ release
                     (속성 테스트면 256 케이스)
                                                     │
                                  매개변수 범위가 구조 크기를 정한다
                                  용량 1  → 칸 최대 2^15 = 32768  💥 debug 에서 120s 초과
                                  용량 2..=4 → 칸이 훨씬 얕음

  + 실패했을 때만: 축소(shrink)
      실패 입력 발견 ─▶ 더 작은 후보 생성 ─▶ 테스트 본문 전체 재실행 ─▶ 여전히 실패? ─┐
                         ▲                                                          │
                         └──────────── 최대 4 × 케이스 수(=1024)번, 시간 한도 없음 ◀──┘
      변이 점검에서 실패는 금방, 축소에 ~110s

  대처
  ├ 무거운 스모크는 release 빌드로
  ├ 속성 테스트의 용량 범위 2..=4          ── 극단값 1 은 결정적 단위 테스트로 이동(검사는 끝에서 1회)
  ├ 매 단계 검사하는 속성은 단계 수를 더 작게 (≤120 vs 비교 속성 ≤300)
  └ 결과: 38 tests ≈ 1.8s (debug)
```

## 핵심 문장

- 매 단계 불변식 검사는 비용을 O(단계 × 구조 크기)로 만든다 — 구조 크기는 매개변수(용량)가 정한다.
- 매개변수 범위는 커버리지와 비용을 동시에 정한다 — 비싼 극단값은 무작위 범위에서 빼서 결정적 단위 테스트로 고정한다.
- 축소는 실패 뒤에만 지불하는 비용이고, 한 번마다 테스트 본문 전체를 다시 돈다 — 입력이 크고 본문이 비쌀수록 길다.
- proptest 기본값: 256케이스, 축소 반복 한도 = 4 × 케이스 수, 축소 시간 한도 없음.
- 빠른 테스트 묶음은 그 자체가 요구사항이다 — 느리면 덜 돌리게 되고, 시한에 걸리면 결과가 없다.
