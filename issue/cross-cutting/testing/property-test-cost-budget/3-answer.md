# issue/cross-cutting/testing/property-test-cost-budget — 정답

태그: `resource-bounding`

## 정답
<!-- 질문 1:1 대응 -->

1. **용량 1이면 두 키가 해시 하위 비트를 많이 공유하는 순간 그 비트 수만큼 깊어져, 칸 수가 2^깊이로 커진다.**\
   확장 해싱은 버킷이 넘치면 해시 하위 비트를 하나 더 보며 나누고, 필요하면 디렉터리(칸 배열)를 두 배로 늘린다.\
   용량 1은 "버킷 하나에 키 하나"라서, 서로 다른 두 키가 하위 d비트까지 같으면 둘을 가르려고 깊이가 d+1까지 간다. 키 300개 사이에서는 그런 쌍이 생기기 쉽다(생일 문제와 같은 구조).\
   release 스모크(용량 1..4 × 시드 30 × 삽입 300)에서 최대 깊이는 15 — 칸 32768개였다(용량 1).\
   삽입마다 도는 검사가 칸 수 × 버킷 수에 비례하므로, 같은 테스트라도 용량 1은 단계당 비용이 크게 뛴다. 여기에 debug 빌드가 곱해져 첫 스모크(debug)가 120초 시한을 넘겼고, 중단한 뒤 다시 짰다.
   > **확장 해싱(extendible hashing)** — 해시의 하위 `depth`비트로 디렉터리 칸을 고르고, 칸이 버킷을 가리키는 2단 구조. 넘친 버킷만 나누고 필요할 때만 디렉터리를 두 배로 늘린다.

2. **분할 직후의 중간 상태가 불변식을 지키는지 보려는 것이다.**\
   끝에서 한 번만 검사하면, 중간에 깨졌다가 이후 분할이 우연히 덮어 쓴 상태나, 끝 상태에는 흔적이 없는 잘못된 전이를 놓친다.\
   또 매 단계 검사는 실패를 **처음 깨진 단계**에서 멈추게 해 원인 위치를 바로 알려 준다.\
   대가는 비용이다 — 단계당 O(구조 크기) 검사를 단계 수만큼 하므로 전체는 O(단계 × 구조 크기)이고, 구조 크기는 입력과 매개변수에 따라 커진다.

3. **손잡이마다 잃는 것이 다르다.**
   - **매개변수 범위 좁히기(용량 2..=4)** — 용량 1의 무작위 탐색을 잃는다. 이 사례는 속성 테스트의 용량을 2..=4로 정하고, 용량 1은 결정적 단위 테스트(용량 [1, 2] 각각에 키 0..300을 넣고 **끝에서 한 번** 전체 검사 + 모든 키 조회·전체 순서 대조)로 옮겼다 — 극단값에서는 검사 횟수를 줄여 비용을 묶었다.
   - **단계 수 줄이기** — 깊은 상태(많이 분할된 구조)에 도달할 확률이 줄어든다. 이 사례는 매 단계 검사하는 속성은 연산열 ≤120, 정답 모델(정렬 맵)과 결과만 대조하는 속성은 ≤300으로 나눴다 — 비싼 검사는 짧게, 싼 대조는 길게.
   - **release 빌드** — 기본 설정에서 `debug_assertions`·오버플로 검사가 빠진 상태로 돈다(이 검사들에 기대는 단언은 사라진다). "넓게 많이 돌려 보는" 스모크에 맞다 — 이 사례는 다시 짠 스모크(용량 1..4 × 시드 30 × 삽입 300, 삽입마다 검사)를 release로 돌려 통과했다.
   - **극단값을 단위 테스트로** — 무작위 조합에서만 나오는 상호작용은 잃지만, 극단값 자체는 매번 결정적으로 검사된다.
   비싼 극단값은 범위에서 빼되 **커버리지 구멍을 이름 있는 단위 테스트로 메운다**는 것이 핵심이다 — 범위만 좁히고 끝내면 조용히 검사 범위가 줄어든다.

4. **축소(shrinking)에 쓰였다.**\
   proptest는 실패 입력을 찾으면 더 작은 후보를 만들어 테스트 본문을 **다시 통째로** 돌리고, 여전히 실패하면 그쪽으로 좁혀 간다.\
   proptest 1.12 기본값은 `max_shrink_iters = u32::MAX`인데 이는 "케이스 수의 4배"를 뜻한다 — 256케이스면 최대 1024번 재실행이다. `max_shrink_time`의 기본값 0은 시간 한도 없음이다.\
   축소 한 번의 비용은 그 후보 입력에 대한 테스트 한 번의 비용이다 — 연산열 300개를 적용하고 범위 질의를 대조하는 본문이면, 1024번 가까이 도는 축소는 원래 케이스 탐색보다 길어질 수 있다.\
   이 사례는 칸 재지정을 생략하는 변이에서 정답 모델 대조 속성의 축소에 약 110초가 걸렸다(실패 자체는 빨리 찾음).
   > **축소(shrinking)** — 속성 테스트가 실패한 무작위 입력을 실패가 유지되는 한 더 작은 입력으로 줄여, 사람이 읽을 수 있는 최소 반례를 내놓는 단계.

5. **정상이다 — 축소는 실패한 뒤에만 지불하는 비용이고, 그 대가로 최소 반례를 얻는다.**\
   통과하는 평소 실행에는 축소가 없으므로 CI 시간에 영향이 없다. 변이 점검처럼 실패를 일부러 만드는 작업에서 길게 드러난다.\
   `max_shrink_iters`·`max_shrink_time`(또는 `PROPTEST_MAX_SHRINK_ITERS`·`PROPTEST_MAX_SHRINK_TIME` 환경 변수)으로 묶으면 끝나는 시간이 보장되는 대신 반례가 덜 작아진다 — 디버깅할 때 읽어야 할 입력이 커진다.\
   이 사례는 커밋된 설정을 바꾸지 않았다 — 축소 비용은 변이 점검에서만 겪는 비용이었고, 평소 실행은 1.8초였다.

6. **느린 테스트 묶음은 덜 돌게 되고, 시한에 걸리면 아무 결과도 남기지 않는다.**\
   매 변경마다 도는 묶음이 수 분이면 개발자는 일부만 돌리거나 건너뛰게 된다 — 커버리지가 있어도 실행되지 않으면 증거가 아니다.\
   시한 초과는 "통과도 실패도 아님"이다 — 120초에 잘린 실행은 결함 유무를 말해 주지 않는다.\
   그래서 매개변수 범위·단계 수·검사 강도는 **커버리지와 비용을 함께** 보고 정하고, 그 결과(38 tests ≈ 1.8s debug)를 지켜야 할 예산으로 둔다.

## 문제 구조 (추상화 코드)

### 변형 A — 매 단계 전체 검사 × 구조를 폭발시키는 매개변수
① 문제 코드
```rust
// 첫 무작위 스모크 — debug 빌드
for cap in 1..=4 {
    for seed in 0..30 {
        let mut rng = Rng::seeded(seed);
        let mut t = Table::new(cap);
        for _ in 0..300 {
            t.insert(rng.next(), rng.next());
            t.check();          // O(칸 × 버킷) — cap 1 이면 칸이 2^15 까지
        }
    }
}
// 결과: 120s 시한 초과 → 중단
```
② 고친 코드
```rust
// 같은 스모크는 release 빌드로 (통과 — 최대 깊이 15, cap 1)

proptest! {
    #![proptest_config(ProptestConfig::with_cases(256))]

    #[test]
    fn matches_model(cap in 2usize..=4, ops in ops(300), /* 질의 */) {
        // 정답 모델(정렬 맵)과 결과만 대조 — 단계당 검사가 싸다 → 길게
    }

    #[test]
    fn invariants_hold_each_step(cap in 2usize..=4, ops in ops(120)) {
        // 매 삽입 t.check() — 비싼 검사 → 짧게
    }
}

#[test]
fn many_inserts_small_caps() {
    for cap in [1, 2] {                 // 극단값 cap 1 은 결정적 단위 테스트로
        let mut t = Table::new(cap);
        for k in 0..300u64 { assert_eq!(t.insert(k, !k), None); }
        t.check();                      // 끝에서 1회
        // 모든 키 조회 + 전체 순서 대조
    }
}
// 결과: 38 tests ≈ 1.8s (debug)
```
무엇이 깨졌나: 매 단계 검사 비용이 매개변수가 정하는 구조 크기에 비례한다는 것을 범위를 정할 때 계산하지 않았다.

### 변형 B — 실패 뒤 축소가 실패 발견보다 오래 걸림
```text
변이(칸 재지정 생략) 투입
  → 정답 모델 대조 속성: 실패 입력 발견(빠름)
  → 축소: 후보마다 연산열 적용 + 질의 대조 전체 재실행
          기본 한도 4 × 256 = 1024 회, 시간 한도 없음
  → 약 110s 뒤 최소 반례 출력
설정은 바꾸지 않음 — 실패할 때만 지불하는 비용(평소 실행 영향 없음)
필요하면: ProptestConfig { max_shrink_time: <ms>, max_shrink_iters: <n>, .. } 또는 환경 변수
```
무엇이 깨졌나: 깨진 것은 없다 — "실패를 찾는 비용"과 "실패를 줄이는 비용"이 따로라는 것을 몰라 멈춘 것으로 오해하기 쉽다.

## 검증 기록
- 2026-11-12: 사건 기록 대조·추상화(Claude 초안) — 120s 초과(첫 스모크, debug)·최대 깊이 15(release 스모크, cap 1)·축소 ~110s(변이 점검)·38 tests 1.8s는 작업 기록 수치, 속성 테스트 매개변수(cap 2..=4, 연산열 ≤300/≤120, 256 cases)와 cap 1 단위 테스트는 테스트 코드 대조. proptest 기본값(`cases` 256, `max_shrink_iters` u32::MAX = 4 × cases, `max_shrink_time` 0 = 무제한)은 proptest 1.12.0 소스의 설정 문서 주석에서 확인.
