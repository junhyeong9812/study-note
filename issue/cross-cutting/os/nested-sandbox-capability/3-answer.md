# issue/os/nested-sandbox-capability — 정답

태그: `environment-drift` · `silent-failure`

## 정답

1. 도구는 자기 격리를 위해 네임스페이스(user·network 등)를 새로 만들고, 새 네트워크 네임스페이스의 루프백 인터페이스에 주소를 설정하려 한다.\
관측된 오류(`loopback: Failed RTM_NEWADDR: Operation not permitted`)는 **그 루프백 주소 설정이 거부됐다**는 뜻이다. 바깥 실행 환경이 그 조작을 허용하지 않은 것으로 보이며, 정확히 어느 정책이 막았는지는 바깥 환경을 따로 확인해야 한다.\
바깥에서 되던 이유는 그 제한이 없는 문맥이었기 때문이다 — 코드가 아니라 **실행 문맥**이 달라졌다.
> **user namespace** — UID/GID와 capability를 격리해, 비특권 프로세스가 그 안에서 다른 네임스페이스(마운트·네트워크 등 — 각각 별도 네임스페이스)를 만들 수 있게 하는 커널 기능.
> **RTM_NEWADDR** — 커널에 인터페이스 주소를 추가하라는 netlink 요청.

2. 이 사례에서 도구는 셸 명령 실패를 내부에서 처리하고 "검증하지 못했다"는 **정상 형식의 결과물**을 내며 종료 코드 0을 반환했다(내부 처리가 늘 0으로 이어지는 것은 아니다).\
호출 쪽이 종료 코드만 보면 "리뷰 완료·지적 0"으로 기록하게 된다 — **검증을 안 한 것이 검증 통과로 둔갑**한다(silent failure).\
완료 판정은 종료 코드·필수 산출물 존재·결과 본문의 검토 범위("읽지 못함·검증 불가·미열람" 같은 표식)를 **함께** 본다. 표식이 없다고 완료인 것도 아니다.

3. - **입력 인라인(표준입력)**: 포기하는 것 = 도구가 스스로 파일을 더 찾아보는 탐색력. 필요한 내용을 호출 쪽이 골라 넣어야 하므로, 넣지 않은 범위는 "미열람"으로 명시해야 한다. 격리는 그대로 유지된다.
   - **내부 샌드박스 끄기**: 포기하는 것 = 도구 자체의 격리(바깥 샌드박스 정책은 남는다). 명시 승인이 있을 때만 쓰고, 도구가 명령을 실제 실행하는 용도에는 쓰지 않는다.
   - **바깥 샌드박스 밖에서 실행**: 포기하는 것 = 바깥 격리(호출자 쪽 보호). 운영 경로를 바꾸는 결정이다.
   - 입력이 텍스트로 충분한 작업(리뷰·요약)이면 인라인이 가장 덜 포기한다.

4. **쓰기 제한**이다. 읽기는 막지 않는다.\
읽기 범위를 **강제**하려면 파일시스템 노출 자체를 줄이는 접근 정책이 필요하다. 필요한 파일만 담은 복사본(미러)을 작업 디렉토리로 두고 "밖은 읽지 말라"고 지시하는 것은 **작업 범위 안내**이지 접근 통제가 아니다.\
인라인 방식은 도구가 파일을 읽을 **필요**를 없앨 뿐, 읽기 권한을 제거하지는 않는다.

5. 내부 격리 초기화가 **보조 자식 프로세스**(예: 설정·목록 갱신)에서 실패하고 그 자식이 제때 끝나지 않을 때, 도구가 그 종료를 타임아웃까지 기다렸다 진행하는 구조다(실패가 늘 정지로 이어지는 것은 아니다).\
결과는 정상이고 매 호출에 고정 지연만 붙는다 — 에러 로그 한 줄 외에는 증상이 "느리다"뿐이라 원인 추적이 늦다.\
지연을 비용으로 받아들이되, 호출 타임아웃을 그 지연보다 넉넉히 잡아야 한다(너무 짧으면 정상 작업까지 죽인다).

## 문제 구조 (추상화 코드)

### 변형 A — 내부 격리 실패 → 파일 읽기 전면 실패 → exit 0

① 문제 코드
```bash
# 바깥: 이미 샌드박스 안의 셸
cd "$mirror"
cat prompt.md | tool exec --sandbox read-only -o "$OUT/review.md" -
echo "exit=$?"            # exit=0
# review.md: "파일 목록만 확인했고 이후 모든 읽기가 권한 오류로 실패 — 문제없음이 아니라 검증 불가"
```
② 고친 코드
```bash
{ cat prompt.md
  for f in spec.md diff.md; do echo "===== $f ====="; cat "$OUT/packet/$f"; done
} | tool exec --sandbox read-only -o "$OUT/review.md" -     # 필요한 입력을 인라인으로
rc=$?                                                        # 도구 종료 상태 보존
[ "$rc" -eq 0 ] && [ -s "$OUT/review.md" ] || { echo "tool failed rc=$rc"; exit 1; }
if grep -qE '검증 불가|읽지 못|미열람' "$OUT/review.md"; then echo "INCOMPLETE"; exit 2; fi
```
무엇이 깨졌나: 내부 격리를 만들 권한이 상속 문맥에 없어 도구의 파일 접근이 전부 실패했고, 실패가 도구 안에서 "정상 결과물"로 포장돼 종료 코드로는 보이지 않았다.

### 변형 B — 보조 자식만 실패 → 호출마다 고정 지연

① 문제 구조
```text
tool exec ... ─┬─ 본 작업 ─────────────────────────▶ 정상 결과
               └─ 보조 갱신 자식: 내부 격리 생성 시도 → 멈춤
                   → "timeout waiting for child process to exit" (약 30초 후 진행)
```
② 대응
```bash
timeout 900 tool exec ...        # 고정 지연 + 본 작업 시간보다 넉넉한 상한
# 입력 인라인은 이 지연을 없애지 못한다(보조 자식은 파일 읽기와 무관) — 상한을 넉넉히 잡는 것이 대응
```
무엇이 깨졌나: 실패가 결과가 아니라 **시간**으로만 드러나, 짧은 타임아웃과 결합하면 정상 작업이 중단된다.

## 방안 비교

| | 입력 인라인 | 내부 샌드박스 끄기 | 바깥 밖에서 실행 |
|---|---|---|---|
| 전제 | 입력이 텍스트로 충분(리뷰·요약) | 명시 승인 | 운영 경로 변경 권한 |
| 비용 | 입력 선별·크기 관리 | 도구 자체 격리 상실(바깥 정책 유지) | 호출자 보호 상실 |
| 실패 모드 | 넣지 않은 범위를 못 봄("미열람" 명시 필요) · 보조 자식 지연은 그대로 | 도구가 명령을 실행하면 바깥 샌드박스가 허용하는 범위까지 영향 | 바깥 정책 우회 |
| 맞는 조건 | 읽기 전용 분석 작업 | 격리 없이도 안전한 조회 전용 | 격리가 이중으로 필요 없는 전용 러너 |

**결론:** 읽기 전용 분석이면 입력 인라인이 가장 덜 포기한다.\
어떤 방안이든 완료는 종료 코드·필수 산출물·결과 본문의 검토 범위를 함께 보고 판정한다.
