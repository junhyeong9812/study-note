# issue/os/job-lifetime-bound-to-user-session — 정답

태그: `silent-failure` · `environment-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **oomd의 단위는 프로세스가 아니라 cgroup이다.** systemd-oomd는 메모리 압박(PSI)·스왑 사용량을 보고 있다가 한도를 넘으면 후보 cgroup 하나를 골라 **그 안의 모든 프로세스에 SIGKILL**을 보낸다(systemd 문서).\
`setsid`는 세션·프로세스 그룹을, `nohup`은 SIGHUP 처리를 바꿀 뿐 **cgroup 소속은 바꾸지 않는다** — 자식은 부모가 있던 cgroup에서 태어나 거기 머문다.\
이 사례에서 측정 실행기를 터미널 앱 안에서 `setsid nohup`으로 띄웠더니 그 앱의 scope(당시 14.7G) 안에 측정이 들어 있었고, 메모리 압박 때 oomd가 그 scope를 통째로 종료해 앱과 측정이 함께 죽었다.\
직전 상황은 부하 도구 RSS 6.0GB·load 109에 IDE 9.3G가 동시에 떠 있었다 — 부하 도구 RSS는 그 시나리오에서 원래 약 5.8GB로 일정했으므로 측정 자체의 이상 증가는 아니었다 — 같은 머신에 큰 프로세스들이 **함께** 떠 있던 상황이다(사용자는 이후 큰 앱을 끄고 재개했다).
   > **cgroup** — 리눅스가 프로세스 묶음 단위로 자원(메모리·CPU)을 회계·제한하는 계층. systemd는 유닛(service·scope·slice)마다 cgroup을 하나씩 만든다.

2. **자기 cgroup을 가진 별도 유닛.** 측정을 별도 유닛(서비스)으로 띄우면 측정만의 cgroup이 생겨, oomd가 앱의 cgroup을 골라도 측정은 그 안에 없다 — 이 사례는 중단 후 이어서 잴 때부터 별도 사용자 유닛 + `ManagedOOMPreference=avoid`로 실행했다.\
`avoid`는 "다른 후보가 없을 때만 이 cgroup을 고른다"는 **우선순위 낮춤**이지 면제가 아니다(면제는 `omit`, systemd는 둘 다 아껴 쓰라고 권한다).\
또 systemd 문서상 이 설정은 cgroup 확장 속성으로 전달되는데, oomd는 **스왑 기준 판단에서는 root 소유 cgroup의 속성만**, 압박 기준 판단에서는 root 소유이거나 감시 대상 조상과 소유자가 같을 때만 존중한다 — 사용자 매니저 아래 유닛(사용자 소유)은 시스템 전체(root 소유) 기준 판단에서 무시될 수 있다.\
이 사례에서 별도 유닛으로 옮긴 뒤 oomd 개입이 다시 일어난 기록은 없다 — 즉 `avoid`가 실제로 측정을 지켰는지는 **검증되지 않았다**(분리된 cgroup 덕에 앱과 "함께" 죽는 경로가 사라진 것이 확실한 효과다).

3. **사용자 매니저의 수명 = 로그인 세션(linger 꺼짐).** 사용자 유닛은 그 사용자의 서비스 매니저(`user@<uid>.service`) 아래에서 돈다.\
linger가 꺼져 있으면 사용자 매니저는 로그인 세션이 있을 때만 살아 있고, **마지막 세션이 끝나면 매니저가 종료되며 그 아래 유닛도 모두 정지**한다.\
이 사례에서 노트북의 데스크톱 세션이 (이미 세션 관리자가 실패 상태이던 중) 종료되자 사용자 매니저가 종료 단계로 들어가 측정 유닛이 정지했고, 진행 중이던 회차는 상태 기록 없이 끊겼으며 **캠페인 로그에는 중단(ABORT) 기록조차 없었다** — 실행기가 스스로 실패를 쓰기 전에 바깥에서 멈췄기 때문이다.\
`loginctl enable-linger <user>`는 부팅 때 그 사용자의 매니저를 띄우고 로그아웃 후에도 유지시킨다(systemd 문서). 또는 시스템 유닛(`User=`로 실행 계정 지정)으로 띄우면 로그인 세션과 무관해진다.\
이 사례는 세션 종료 3분 뒤 같은 id로 재개했고, linger 활성화는 사용자 확인 대기로 남았다 — 대처는 **원인 확인까지이고 적용·검증은 아직**이다.
   > **linger** — 로그인하지 않은 사용자에게도 사용자 서비스 매니저를 유지시키는 logind 설정.

4. **바깥에서 죽은 작업은 자기 죽음을 기록하지 못한다.** SIGKILL(oomd)이나 매니저 정지는 실행기의 실패 처리 경로를 거치지 않으므로, 결과 폴더에는 "마지막으로 성공한 회차"까지만 있고 실패 표시가 없다.\
oomd 사건은 세션을 다시 열어 진행을 확인한 시점에야 드러났다 — 180회 중 108회, 마지막 완료 후 **약 2시간 46분 무진행**, 그동안 원격 서버의 측정 컨테이너가 3시간 방치돼 손으로 정리했다.\
게다가 진행 확인 명령의 `pgrep -f`가 **자기 자신의 명령줄**에 걸려 죽은 작업을 "RUNNING"으로 오탐했다 — [process-group-and-tree-termination](../process-group-and-tree-termination/)의 self-match와 같은 함정이다.\
생존 판단은 프로세스 검색이 아니라 진행 로그의 **마지막 갱신 시각**(여기서는 매트릭스 로그의 마지막 완료 시각)으로 하는 편이 정확하다.

5. **Restart=on-failure + 시작 횟수 상한.** 실행기가 0이 아닌 코드로 끝나면 유닛이 다시 띄우도록 `Restart=on-failure`, 즉시 재시도가 같은 단절에 다시 부딪히지 않게 `RestartSec=`(이 사례 180초), 영구 고장에서 무한 반복하지 않게 시작 횟수 상한(`StartLimitBurst=5`, 기간 6시간)을 건다.\
이 사례는 일시 네트워크 단절로 실행기가 두 번 비정상 종료해 각각 수 시간 유휴가 생긴 뒤 이 설정을 걸었다(코드 무변경 — 측정 커밋 유지). 그 뒤 측정 종료까지 정지·자동 재시작은 **0회** — 재시작 경로가 실제로 돌아 본 적은 없다.\
재시작이 복구가 되려면 실행기가 **같은 명령으로 다시 불렸을 때 이어서 하도록**(멱등 재개) 만들어져 있어야 한다 — 그렇지 않으면 재시작이 처음부터 다시 재거나 이미 쓴 결과를 덮어쓴다.
   > **StartLimitIntervalSec / StartLimitBurst** — 그 기간 안에 이 횟수를 넘겨 시작되면 유닛을 더 이상 시작하지 않는 제한. `[Unit]` 절에 둔다.

6. **멱등 재개 = 끝난 것은 건너뛰고, 다른 조건은 거부하고, 끊긴 것은 보존 후 다시.**\
① 조건이 끝나면 완료 표식(`DONE`)을 남기고, 재개 때 표식이 있는 조건은 건너뛴다. 계획 파일이 있는데 표식이 없으면 그 조건 안에서 이어서(`--resume`) 잰다.\
② 이어서 잴 때는 계획 파일의 조건(인덱스·풀·배경 등)을 **복원**하고, 명령줄 값이 계획과 다르면 거부한다 — 초기 구현은 재개 때 조건이 기본값으로 돌아가 서로 다른 조건이 한 결과에 섞일 수 있었다(리뷰 발견).\
③ 측정 대상(앱·시나리오·실행 환경 정의)이 계획의 커밋과 다르면 재개를 거부한다.\
④ 도중에 끊긴 회차는 지우지 않고 `<회차>.killed-oomd`·`<회차>.incomplete-<시각>`처럼 **이름을 바꿔 보존**한 뒤 다시 잰다 — 지우면 "왜 끊겼나"의 증거(부분 로그·자원 시계열)가 사라지고, 그대로 두면 집계가 미완성 회차를 정상으로 읽는다.

## 문제 구조 (추상화 코드)

### 변형 A — 앱 cgroup 안에서 떼어 띄운 장기 작업이 oomd에 함께 종료
① 문제 코드
```bash
# 터미널 앱 안의 셸에서
setsid nohup ./runner.sh --sha "$SHA" --id "$ID" > runner.log 2>&1 < /dev/null &
# 세션·그룹은 분리됐지만 cgroup = 앱의 scope 그대로
# 메모리 압박 → oomd가 앱 scope(측정 포함)에 SIGKILL → 실패 기록 없이 정지
```
② 고친 코드
```ini
# 별도 유닛 — 측정만의 cgroup
[Service]
ExecStart=/path/runner.sh --sha <SHA> --id <ID>
ManagedOOMPreference=avoid
# 주의: avoid는 우선순위 낮춤(면제 아님)이고, 사용자 유닛이면 oomd가 소유자 조건에 따라 무시할 수 있다
```
무엇이 깨졌나: 프로세스 트리를 떼어 냈다고 자원 회계·종료 단위(cgroup)까지 떼어 냈다고 착각했다.

### 변형 B — 사용자 유닛이 로그아웃과 함께 정지 (linger 꺼짐)
① 문제 코드
```text
사용자 유닛 job.service  (부모 = user@<uid>.service, Linger=no)
마지막 로그인 세션 종료 → 사용자 매니저 종료 → job.service stop
→ 진행 중 회차는 상태 없이 끊김, 캠페인 로그에 ABORT 없음
```
② 고친 코드
```bash
loginctl enable-linger "$USER"     # 매니저를 부팅 때 띄우고 로그아웃 후에도 유지
# 또는 시스템 유닛으로: [Service] User=<user>  — 로그인 세션과 무관
# (이 사례: 원인 확인 후 적용 대기 — 미검증)
```
무엇이 깨졌나: 사용자 유닛의 수명이 사용자 매니저, 그 매니저의 수명이 로그인 세션에 묶여 있다는 사슬을 놓쳤다.

### 변형 C — 일시 장애 후 수 시간 유휴: 재시작 + 멱등 재개
① 문제 코드
```ini
[Service]
ExecStart=/path/runner.sh --sha <SHA> --id <ID>
# Restart 없음 → 단절 1회에 비정상 종료 → 사람이 발견할 때까지 유휴
```
② 고친 코드
```ini
[Unit]
StartLimitIntervalSec=6h
StartLimitBurst=5
[Service]
ExecStart=/path/runner.sh --sha <SHA> --id <ID>      # 같은 id = 이어서
Restart=on-failure
RestartSec=180
```
```bash
# runner.sh — 멱등 재개
for cond in "${CONDS[@]}"; do
  name="${cond%% *}"
  [[ -f "$ROOT/$name/DONE" ]] && continue                     # 끝난 조건 건너뜀
  resume=""; [[ -f "$ROOT/$name/plan.json" ]] && resume="--resume"   # 시작한 조건은 이어서
  run_condition "$cond" $resume || { echo "ABORT $name" >> "$LOG"; exit 1; }
  touch "$ROOT/$name/DONE"
done
# --resume: plan.json의 조건 복원, 명령줄·측정 대상 커밋이 다르면 거부
#           끊긴 회차 dir → dir.incomplete-<시각> 로 보존 후 다시 잼
```
무엇이 깨졌나: 실패 후 재진입을 사람의 발견에 맡겼다 — 재진입 경로(멱등 재개)는 있었지만 그것을 부르는 주체가 없었다.
