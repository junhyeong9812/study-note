# issue/data/lookup-cost-and-indexing — 정답

태그: `resource-bounding`

## 정답
<!-- 질문 1:1 대응 -->

1. **역검색은 O(n), 역인덱스는 O(1).** 해시맵은 key 를 해시해 버킷을 바로 찾으므로 key→value 가 (평균) O(1)이다.\
   value 쪽에는 아무 색인이 없으니 value→key 를 찾으려면 모든 항목을 순회해야 한다(O(n)).\
   이 역검색을 레코드마다 부르면 전체는 **호출 수 × n** 이 된다 — 실측으로 180만 항목 사전을 호출마다 훑어 건당 206ms, 535만 건 기준 약 12.8일이 걸렸다.\
   초기화 때 `value → [key...]` 역인덱스를 **한 번** 만들어 두면 조회가 `.get()` O(1)이 되어 건당 0.58ms(약 355배)로 줄었다.\
   대가는 메모리(+50~100MB)와 초기화 시간(+약 1초)이다 — 사전이 불변이고 조회가 빈번할 때 맞는 교환이다.
   > **역인덱스(inverted index)** — 원래 매핑의 값을 키로 뒤집어, 값으로 원래 키를 O(1)에 찾게 만든 보조 색인.

2. **upsert = 조회 + 쓰기.** upsert 는 "이 키가 이미 있나"를 매 건 먼저 조회한다.\
   조회 키에 인덱스가 없으면 그 조회가 컬렉션 풀스캔이고, 컬렉션은 적재할수록 커지므로 전체가 1+2+…+n = **O(n²)** 가 된다 — 실측에서 적재가 80% 지점에서 18시간 정체했다.\
   빈 컬렉션을 비우고 **순수 insert** 로 넣으면 존재 확인이 없어 건당 비용이 상수가 되고(63만 건 7초), 인덱스는 적재가 끝난 뒤 한 번에 만든다.\
   전제: 대상이 비어 있어 중복 판정이 필요 없어야 한다.

3. **평탄한 페이지 비용 = 고정비, 순차 진행 = 굶는 워커.** 페이지 비용이 OFFSET 과 무관하게 일정하다면 비용이 "몇 행을 건너뛰나"가 아니라 **매 페이지 반복되는 고정 작업**에 지배된다는 뜻이다 — 조인/IN 조건 컬럼에 인덱스가 없어 매 페이지가 수억 행 자식 테이블을 풀스캔하고 있었다.\
   워커 12개가 있어도 일감을 공급하는 **동기 리더 1개**가 페이지당 18분씩 걸리면 워커는 할 일이 없어 기다리고, 결과적으로 직렬처럼 보인다(64코어로 옮겨도 0.4 docs/s).\
   확정은 `EXPLAIN` 으로 한다 — 대형 테이블에 `type=ALL`(풀스캔)이 찍히고 `key` 가 비어 있으면 조인/조건 컬럼 인덱스 부재가 원인이다(`Using filesort`·`Using temporary` 는 정렬·임시 테이블 사용 표시일 뿐 그 자체로 인덱스 부재를 뜻하지는 않는다 — 함께 보이면 비용을 키우는 신호).\
   조인 키에 인덱스를 건 뒤 페이지 읽기가 6.8분 이상에서 0.06초로 떨어졌다.

4. **OFFSET 은 건너뛸 행을 매번 읽는다.** `LIMIT 500 OFFSET 800000` 은 앞의 80만 행을 실제로 읽고 버린 뒤 500행을 준다 — 페이지가 깊어질수록 비용이 선형으로 는다.\
   keyset 은 `WHERE key > :lastKey ORDER BY key LIMIT n` 으로 **직전 페이지의 마지막 키에서 인덱스를 바로 타고 들어가** 버리는 행이 없다.\
   결과적으로 페이지 비용이 깊이와 무관하게 첫 페이지 수준으로 유지된다(정렬 키가 유일하고 인덱스가 그 순서를 제공할 때)(인덱스 + keyset 후 약 2400 docs/s, 1400만 건 완주).
   > **keyset(seek) 페이징** — 오프셋 대신 "마지막으로 본 정렬 키" 이후를 조회하는 커서 방식.

5. **인덱스가 있어도 못 타는 쿼리.** B-tree 는 키가 정렬돼 있어 **접두**가 정해질 때만 범위를 좁힐 수 있다.\
   `LIKE 'kw%'` 는 접두가 고정이라 인덱스 범위 탐색이 가능하지만(엔진·collation 에 따라 조건이 있다 — 예: PostgreSQL 은 C 가 아닌 locale 에서 `text_pattern_ops` 류 인덱스가 필요), `LIKE '%kw%'` 는 첫 글자가 무엇이든 될 수 있어 정렬 순서로 범위를 좁힐 수 없고 결국 전체(테이블 또는 인덱스 전체)를 훑는다. `lower(col)` 처럼 컬럼에 함수를 씌우면 일반 컬럼 인덱스는 못 쓴다(같은 식의 함수 기반 인덱스가 있으면 예외).\
   또 utf8mb4 긴 VARCHAR 는 InnoDB 인덱스 키 길이 한도(행 포맷에 따라 767 또는 3072 바이트 — utf8mb4 는 문자당 최대 4바이트)를 넘을 수 있어, 넘으면 `col(191)` 같은 **접두 길이 인덱스**로 만든다(191 은 767바이트 한도 기준 값).\
   부분일치 성능이 목적이면 B-tree 가 아니라 전문 검색(FULLTEXT) 인덱스를 검토해야 한다 — 이 사례는 원리만 기록되고 실측은 후속 과제로 남았다.

6. **1차 군집화 — 자료구조의 성질.** 정수의 기본 해시가 값 그대로(항등)면 연속 키 0..199999 가 슬롯 0..199999 를 **빈틈없이** 채운다.\
   선형 탐사는 충돌 시 다음 칸을 보므로, 이 덩어리 안으로 떨어진 "없는 키" 조회는 **덩어리 끝까지** 탐사해야 미스를 확정한다.\
   같은 용량에서 체이닝 120ms vs 선형 탐사 약 75초(약 625배)였다 — 알고리즘(O(n) twoSum)은 맞고, 느려진 것은 해시 × 키 분포 × 충돌 해결 방식의 조합이다.\
   대응은 성능 입력을 흩뿌려(`i * 4001`) 알고리즘을 공정하게 재고, 군집화 자체는 별도 테스트로 한계를 문서화하는 것이었다.
   > **1차 군집화(primary clustering)** — 선형 탐사에서 점유 슬롯이 연속 덩어리를 이뤄 탐사 길이가 급증하는 현상.

7. **입력 크기 × 호출 수를 함께 본다.** "O(n) 루프"는 루프 본문이 O(1)이라는 가정 위에서만 참이다.\
   본문 안의 조회가 컬렉션 크기에 비례하면 전체는 곱이 된다 — 그런데 코드는 짧고 정상 동작하므로 눈으로는 안 보인다.\
   그래서 프로파일링(한 함수가 전체 시간의 99.9%)이나 EXPLAIN(type=ALL)으로 **측정해 특정**한 뒤 고친다 — 다른 함수는 모두 0.1ms 미만이었다는 기록처럼, 병목은 대개 한 곳에 몰려 있다.

## 문제 구조 (추상화 코드)

### 변형 A — 값→키 역검색을 매 호출 전체 순회
```python
# ① 문제
def lookup_keys(self, value):
    result = []
    for k, v in self.table.items():      # 180만 항목 / 호출
        if v == value:
            result.append(k)
    return result

# ② 고친 코드
def __init__(self, table):
    self.table = table
    self.reverse = defaultdict(list)     # 초기화 때 1회 구축
    for k, v in table.items():
        self.reverse[v].append(k)

def lookup_keys(self, value):
    return list(self.reverse.get(value, []))
```
무엇이 깨졌나: 호출마다 O(n) 순회 → 전체 O(호출 수 × n), 배치가 수일로 늘어남.\
같은 구조: 군집 생성 단계에서 id 매핑을 매번 전체 순회하던 것도 역인덱스로 O(1) 전환.

### 변형 B — 인덱스 없는 upsert 로 대량 적재
```text
# ① 문제
for doc in docs:                                  # n건
    collection.update_one({"key": doc.key},       # key 인덱스 없음 → 건당 풀스캔
                          {"$set": doc}, upsert=True)

# ② 고친 코드
collection.drop()
bulk_insert(collection, docs, workers=4)          # 존재 확인 없는 순수 insert
collection.create_index("key")                    # 인덱스는 적재 후 1회
```
무엇이 깨졌나: 적재가 커질수록 건당 조회가 느려져 O(n²) — 80%에서 장시간 정체.

### 변형 C — 조인 키 인덱스 부재 + OFFSET 페이징
```sql
-- ① 문제: 페이지마다 자식 테이블 풀스캔(인덱스 없음) + 깊은 OFFSET
SELECT DISTINCT p.key FROM parent p JOIN child c ON c.key = p.key
ORDER BY p.key LIMIT 500 OFFSET :n;

-- ② 고친 코드
ALTER TABLE child ADD INDEX idx_key (key), ALGORITHM=INPLACE, LOCK=NONE;  -- 작은 테이블부터
SELECT DISTINCT p.key FROM parent p JOIN child c ON c.key = p.key
WHERE p.key > :lastKey ORDER BY p.key LIMIT 500;                          -- keyset
```
```text
reader(동기, 페이지당 18분) ──▶ queue ──▶ worker × 12   # 워커는 대부분 대기 = 사실상 직렬
```
무엇이 깨졌나: 페이지 비용이 고정 풀스캔에 지배되고, 느린 동기 리더가 병렬 워커를 굶겼다; 인덱스 후엔 OFFSET 이 선형 병목으로 드러남.\
부수: 대형 테이블 온라인 인덱스 생성 중 저장 공간 부족(`table is full`)이 나 공간 확보 후 재시도 — DDL 전 디스크 여유 확인이 필요하다.

### 변형 D — 인덱스를 추가했지만 쿼리가 못 탐
```sql
-- ① 문제
CREATE INDEX idx_name ON t (name);                       -- 긴 VARCHAR: 키 길이 한도
SELECT * FROM t WHERE lower(name) LIKE CONCAT('%', :kw, '%');   -- 선행 와일드카드

-- ② 고친 코드(생성) + 후속 과제
CREATE INDEX idx_name ON t (name(191));                  -- 접두 길이 인덱스
-- 부분일치 성능은 FULLTEXT 인덱스를 데이터량 확인 후 검토
```
무엇이 깨졌나: "인덱스 추가 = 검색 빨라짐" 가정 — B-tree 는 접두 없는 패턴에 쓰이지 않는다.

### 변형 E — 항등 해시 + 연속 키 + 선형 탐사
```text
# ① 문제
hash(i) = i,  keys = 0..199999,  capacity = 524288
slots:  [0][1][2] ... [199999][ ][ ] ...        # 빈틈없는 한 덩어리
miss lookup(k in 0..199999 범위로 떨어짐) → 덩어리 끝까지 탐사

# ② 고친 코드(측정 입력)
keys = [i * 4001 for i in range(200000)]        # 흩뿌린 키로 알고리즘 측정
test sequential_keys_cluster()                  # 군집화 한계는 별도 테스트로 문서화
```
무엇이 깨졌나: 같은 O(n) 알고리즘이 충돌 해결 방식에 따라 약 625배 차이 — 복잡도 표기 뒤에 숨은 상수가 자료구조 성질이었다.

## 방안 비교

같은 원리("인덱스가 있어도 쿼리가 못 탄다" — 변형 D)의 다른 얼굴: 인덱스를 **쿼리의 이름(의도)**으로 설계해, 복합 인덱스의 앞 열이 실제 WHERE에 없었던 사례.\
조인 쿼리라 조건 하나가 **다른 테이블**에 걸려 있었고, 실데이터 규모의 실행 계획으로 확인하기 전까지 아무 오류도 나지 않았다.

### 방안 1 — 쿼리 이름·의도 기준 설계 (처음 설계)
```sql
-- ORM 메서드 이름: "그룹별·사용자별 점유 수"  →  "holds에 (group_id, user_id)"
CREATE INDEX ON holds (group_id, user_id);

-- 실제로 생성되는 SQL: 그룹 조건은 조인한 items 쪽에 걸린다
SELECT count(i.id) FROM items i JOIN holds h ON i.id = h.item_id
WHERE i.group_id = ? AND h.user_id = ?;
-- holds.group_id(앞 열)가 WHERE에 없음 → 이 인덱스를 못 씀 → holds Seq Scan
```
무엇이 깨졌나: 인덱스 앞 열이 조건에 없으면 B-tree는 범위를 좁힐 수 없다(PostgreSQL 16 기준 앞 열을 건너뛰는 스캔 없음 — 엔진·버전마다 다르다).\
실측(점유 10만 행): 다른 세 쿼리는 인덱스로 60~90배 빨라졌는데 이 쿼리만 3.9ms → 4.1ms로 그대로였다.

### 방안 2 — 실제 SQL 조건 열 기준 설계 + 실데이터 규모에서 실행 계획 확인 (바꾼 설계)
```sql
-- 1) ORM이 만드는 실제 SQL을 확인 → 테이블별 조건 열: holds.user_id / items.group_id
-- 2) holds 쪽 조건 열로 인덱스 (사용자당 점유는 몇 개뿐이라 선택적) — 그룹은 items PK 조인으로 확인
CREATE INDEX ON holds (user_id);
-- 3) 측정 전에 실데이터 규모로 실행 계획 확인
EXPLAIN ANALYZE SELECT count(i.id) FROM items i JOIN holds h ON i.id = h.item_id
WHERE i.group_id = ? AND h.user_id = ?;
-- → Index Scan on holds(user_id) → items PK
```
실측(같은 10만 행): 3.433ms → 0.102ms. 단 행이 거의 없을 때(배경 0)는 인덱스 유무 차이가 없었고(0.04~0.08ms) 오히려 인덱스 쪽이 약간 느렸다 — **규모가 없는 스모크로는 이 결함이 보이지 않는다.**

### 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 이름·의도 기준 | 쿼리 이름이 실제 조건 열·테이블과 일치 | 설계가 빠름(SQL을 안 봄) | 조인·ORM 파생 쿼리에서 조건이 다른 테이블에 걸리면 인덱스가 조용히 안 쓰임 — 오류 없음 | 단일 테이블·조건 열이 이름과 1:1인 단순 쿼리(그래도 확인은 필요) |
| 실제 SQL 조건 열 + 규모별 실행 계획 | 실제 SQL을 얻을 수 있음, 실데이터 규모 재현 가능 | 실제 SQL 확인 + 규모 데이터 준비 + EXPLAIN | 실행 계획을 작은 데이터로만 보면 플래너가 인덱스를 고르지 않아 판단이 흐려짐 | 조인·ORM 파생 쿼리, 인덱스 효과가 결론이 되는 측정·운영 변경 |

**결론**: 인덱스는 이름이 아니라 **실제 SQL의 조건 열과 그 열이 걸린 테이블**로 설계하고, 설계한 뒤에는 **실데이터 규모에서 실행 계획**으로 쓰이는지 확인한다.\
이 사례에서 그 확인이 없었다면 "인덱스를 넣어도 이 쿼리는 그대로"라는 틀린 결론이 이어진 수십 시간 측정에 실렸을 것이다 — 인덱스가 안 쓰이는 것은 오류가 아니라 조용한 성능 결함이라, 확인하지 않으면 아무도 알려 주지 않는다.\

## 방안 비교 — 변형 E의 다른 얼굴: 확장 해싱의 디렉터리 폭증

같은 원리("해시 성능은 해시 함수 × 키 분포 × 자료구조의 주소 방식의 성질이다 — 항등 해시는 키의 규칙성을 그대로 슬롯 배치로 옮긴다" — 변형 E)가 **확장 해싱**에서는 탐사 길이가 아니라 **디렉터리 크기**로 드러난다.\
확장 해싱은 해시의 하위 `depth`비트로 디렉터리 칸을 고르고, 버킷이 넘치면 비트를 하나 더 보며 나누며, 그 버킷이 이미 모든 비트를 쓰고 있으면 디렉터리를 두 배로 늘린다.\
키가 전부 2^k의 배수처럼 하위 비트를 공유하면, 그 비트들로는 아무리 나눠도 키가 갈라지지 않아 분할·두 배가 헛돌다가 공유하지 않는 비트에 닿아야 멈춘다 — 디렉터리는 2^(그 비트 위치 + 1)칸이 된다.\
변형 E는 "알고리즘 측정"이 목적이라 입력을 흩뿌리는 것으로 끝낼 수 있었지만, 저장 구조의 키는 사용자 데이터라 입력을 고를 수 없다 — 그래서 해결이 다르다.

### 방안 1 — 항등 해시 (문제)
```rust
fn slot(&self, key: u64) -> usize {
    (key & ((1 << self.depth) - 1)) as usize     // hash(key) = key
}
// 용량 2 에 8, 16, 24 삽입 (하위 비트 8=1000, 16=0000, 24=1000)
//   비트 0·1·2: 셋 다 0 → 분할해도 한쪽으로 몰림 → 두 배 반복
//   비트 3: 16 / 8·24 로 갈림 → 깊이 4 = 디렉터리 16칸 (키 3개, 쓰는 버킷 2개)
// 키가 2^40 의 배수들이면 깊이 41 이 필요 → 디렉터리 2^41 칸 (계산: 칸당 8바이트면 16 TiB)
```
무엇이 깨졌나: 디렉터리 깊이가 키 개수가 아니라 **키의 비트 구조**로 정해진다.

### 방안 2 — 전단사 비트 믹서 (splitmix64 마무리 단계) — 선택한 방법
```rust
fn mix(key: u64) -> u64 {                         // 전단사: 서로 다른 키 → 서로 다른 해시
    let mut z = key;
    z = (z ^ (z >> 30)).wrapping_mul(0xbf58_476d_1ce4_e5b9);
    z = (z ^ (z >> 27)).wrapping_mul(0x94d0_49bb_1331_11eb);
    z ^ (z >> 31)
}
fn slot(&self, key: u64) -> usize {
    (mix(key) & ((1 << self.depth) - 1)) as usize
}
// 같은 8, 16, 24 → 깊이 1 = 디렉터리 2칸
// 운이 나빠 하위 비트가 겹칠 수는 있다(32·40 은 mix 하위 3비트가 같아 4비트째에서 갈림)
```
xorshift(`z ^ (z >> n)`)와 홀수 곱셈은 각각 되돌릴 수 있는 연산이라 합성도 전단사다.\
**전단사**가 주는 것은 "서로 다른 키는 64비트 안 어딘가에서 반드시 다르다 → 분할 루프는 반드시 끝난다"이다 — 전단사가 아닌 해시(예: 32비트로 자르기)는 해시가 완전히 같은 서로 다른 키를 만들 수 있고, 그런 키가 용량보다 많으면 어떤 깊이로도 갈라지지 않아 분할이 끝나지 않는다.\
단, 항등 해시도 전단사라 "끝난다"는 같다 — 믹서가 더 주는 것은 **비트를 섞어** 규칙 있는 키(배수·연속 수)의 하위 비트를 고르게 퍼뜨리는 것이고, 그래서 깊이가 키의 구조가 아니라 키의 개수를 따라간다.\
한계: `mix(0) = 0`처럼 고정점이 있고(키 하나라 무해), 키가 없는 공개 함수라 되돌려 계산할 수 있다 — 하위 비트가 같은 키를 **일부러** 고르는 입력에는 방안 1과 같은 폭증이 다시 가능하다.

### 방안 3 — 최대 깊이 가드 (설계 시 선택지로 기록, 구현하지 않음)
```rust
fn split(&mut self, id: usize) -> Result<(), Full> {
    if self.items[id].local_depth == self.depth {
        if self.depth == MAX_DEPTH {
            return Err(Full);                   // 또는 넘침 체인 등 — 닿았을 때의 동작을 따로 정해야 한다
        }
        self.slots.extend_from_within(..);
        self.depth += 1;
    }
    // ...
}
```
해시 함수와 무관하게 디렉터리 크기에 상한을 건다 — 대신 상한에 닿은 삽입을 어떻게 처리할지(오류·넘침 버킷)가 새 계약이 된다.

### 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 항등 해시 | 키 하위 비트가 이미 고르게 분포 | 없음 | 배수·정렬된 키에서 디렉터리가 키 구조만큼 깊어짐 — 오류 없이 메모리 폭증 | 키가 이미 무작위(다른 해시의 출력 등)라고 보장될 때 |
| 전단사 비트 믹서 | 입력이 적대적이지 않음 | 키당 시프트·곱셈 몇 번 | 비밀 키 없는 공개 함수라 의도적으로 고른 키에는 폭증 재발 가능 | 일반 데이터의 저장·인덱스 구조(이 사례) |
| 최대 깊이 가드 | 상한 도달 시 동작(오류·넘침)을 정의할 수 있음 | 분기 1개 + 넘침 처리 설계 | 상한에서 삽입 실패 또는 넘침 버킷의 선형 탐색으로 성능 저하 | 적대적 입력 가능성이 있거나 메모리 상한이 계약일 때 — 믹서와 함께 |

**결론**: 해시 기반 구조의 비용은 해시 함수가 키의 규칙성을 얼마나 지우느냐에 달려 있다 — 입력을 고를 수 있는 측정(변형 E)은 입력을 흩뿌리면 되지만, 입력을 고를 수 없는 저장 구조는 **해시 함수 자체를 섞는 전단사 함수로** 바꿔야 한다.\
전단사는 분할의 종료를, 섞기는 깊이가 키 개수를 따르는 것을 보장한다 — 둘 중 하나만으로는 부족하다.\
적대적 입력까지 막아야 하면 믹서만으로는 안 되고 최대 깊이 가드(또는 비밀 키를 쓰는 해시)가 함께 필요하다.\
검증 기록: 2026-11-12 사건 기록 대조·추상화(Claude 초안) — 8·16·24 용량 2의 깊이(항등 4 / 믹서 1)와 32·40의 하위 3비트 겹침은 기록의 손계산·스모크 출력, 2^40 배수·16 TiB는 같은 규칙으로 한 계산.
