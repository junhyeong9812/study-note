# issue/cross-cutting/data/denormalized-counter-drift — 정답

태그: `silent-failure` · `single-source-of-truth`

## 정답
<!-- 질문 1:1 대응 -->

1. **같은 사실이 두 곳에 생기고, 모든 쓰기 경로가 둘 다 갱신해야 한다.**\
   카운터를 두면 한도 판정이 "보유 행 수를 세는 조회" 대신 **카운터 행 하나에 대한 조건부 upsert**(`cnt + 1 <= 한도`일 때만 올림, 0행이면 거절)가 된다 — 같은 사용자의 동시 요청이 그 행에서 줄을 서므로 한도를 원자적으로 지킬 수 있다.\
   대가는 사본이다: 보유 수라는 사실이 원본(보유 행 + 확정 행)과 카운터 두 곳에 있다.\
   선점·확정·만료·마이그레이션 등 원본을 바꾸는 **모든** 경로가 카운터도 바꿔야 하고, 하나라도 빠지면(카운터를 유지하지 않는 옛 버전이 쓰거나, 백필 정의가 틀리거나) 둘이 어긋난다.
   > **비정규화(denormalization)** — 다른 행에서 계산할 수 있는 값을 읽기·판정 비용을 줄이려고 따로 저장하는 것. 계산 원본과의 일치는 스키마가 아니라 쓰기 경로들이 지켜야 한다.

2. **세 갈래로 갈린다.**\
   ① 카운터 행이 없으면 `UPDATE` 의 영향 행이 0이다 — 이 사례는 이를 "이미 어긋난 것"으로 보고 조용히 넘기지 않도록 명시적 검사(`check(updated == 1)`)로 예외를 던진다.\
   ② `cnt` 가 지운 수보다 작으면 결과가 음수가 되어 `CHECK (cnt >= 0)` 제약 위반으로 문장이 실패한다.\
   ③ 행이 있고 `cnt` 가 실제와 다르지만 지운 수 이상이면 감소는 **성공한다** — 어긋남은 그대로 남고 아무 오류도 나지 않는다.

3. **실패한 쌍이 다음 틱에 그대로 다시 잡히기 때문이다.**\
   만료 배치는 트랜잭션 하나에서 "만료 시각이 지난 보유 전체"를 조회·삭제하고 쌍마다 카운터를 내린다 — ①·② 중 하나라도 예외가 나면 그 틱의 삭제와 감소가 **전부** 롤백된다.\
   롤백됐으니 어긋난 쌍의 보유도 지워지지 않았고, 다음 틱의 조회가 그것을 다시 가져와 같은 자리에서 또 실패한다.\
   그래서 손실은 한 틱이 아니라 **사람이 고칠 때까지 매 틱**이고, 그 배치가 처리하던 다른 사용자·다른 범위의 만료까지 함께 멈춘다 — 만료된 보유가 풀리지 않고 남는다.\
   (같은 구조의 일반론: 넓은 경계에서 한 건의 실패가 전부를 되돌리는 것은 [transaction-boundary-scope](../../database/transaction-boundary-scope/), 재처리마다 같은 입력에서 실패하는 것은 [retry-policy-design](../../reliability/retry-policy-design/)의 poison 입력과 같다.)
   > **poison 입력** — 처리할 때마다 같은 방식으로 실패하는 입력. 재시도·재조회로는 풀리지 않고, 격리하지 않으면 뒤의 정상 입력까지 막는다.

4. **과소면 한도를 넘게 받고, 과대면 정당한 요청이 거절된다 — 둘 다 오류가 없다.**\
   한도 판정은 카운터만 본다. 카운터가 실제보다 작으면 판정이 여유가 있다고 보아 사용자가 한도를 넘게 보유하고, 크면 이미 찼다고 보아 정당한 요청을 "한도 초과"로 거절한다.\
   배치 실패로 보이는 것은 ①·②뿐이다 — ③은 배치가 정상으로 돌면서도 계속 틀린다.\
   그러니 정합은 "배치가 실패하지 않는다"가 아니라 **원본에서 다시 센 값과 카운터의 대조**(불일치 쌍 수 = 0)로만 말할 수 있다 — 이 사례는 그 대조를 측정 판정기에만 두었고, 운영 중 탐지·복구는 아직 없다.

5. **넣어야 한다 — 정의는 감소 시점이 정한다.**\
   카운터는 "만료 배치가 실제로 행을 지울 때" 내려간다. 만료 시각이 지났어도 아직 배치가 지우지 않은 보유는 카운터에 **남아 있는** 상태가 정상이다.\
   그러므로 재계산 기준은 "보유 행 전체 수(만료 전·후 구분 없음) + 확정 수"여야 하고, 정합 대조도 같은 정의를 써야 한다.\
   "유효한(만료 전) 보유만"으로 백필하면 만료됐지만 안 지운 보유만큼 카운터가 작아진다 → 배치가 그 보유를 지우며 내리는 순간 실제보다 더 내려가 ②(음수) 또는 ③(과소)을 **백필이 직접 만든다**.\
   (이 사례의 설계 문서에도 처음엔 "유효 보유"로 적혀 있었고, 백필 작업에서 정정했다.)

6. **잠금은 실행 중의 쓰기만 막는다.**\
   백필은 원본·카운터 테이블을 함께 잠근 뒤(진행 중인 쓰기는 끝날 때까지 기다리고 새 쓰기는 커밋까지 막는다) 원본에서 다시 센 값으로 카운터를 덮어쓴다 — 두 문장이 같은 사실을 보게 하려는 것이다.\
   하지만 백필은 한 번만 돈다. 백필이 커밋된 **뒤에** 카운터를 유지하지 않는 옛 버전이 보유를 쓰면 그 쓰기는 카운터에 반영되지 않는다.\
   그래서 전환 조건을 따로 둔다: 백필 **전에** 옛 쓰기 주체를 모두 멈추고, 적용 직후 불일치 0을 확인한다.\
   이 조건을 어기고 옛 쓰기 주체가 돌고 있으면, 그쪽과 백필의 잠금 순서가 엇갈려 교착이 날 수도 있다(설계 기록 — 조건을 지키면 생기지 않는다).
   > **cutover(전환)** — 옛 버전에서 새 버전으로 쓰기 주체를 넘기는 시점. 데이터 의미가 바뀌는 전환은 "옛 쓰기 정지 → 변환 → 검증 → 새 쓰기 시작" 순서를 지켜야 한다.

7. **조회와 삭제 사이에 상태가 바뀔 수 있기 때문이다.**\
   "만료 대상"을 따로 조회해 그 수만큼 내리면, 조회와 삭제 사이에 확정으로 넘어간 보유(삭제되지 않음)까지 내릴 수 있다 — 감소 자체가 어긋남을 만든다.\
   실제로 지운 행 목록에서 쌍별로 세면 "지운 만큼만 내린다"가 정의상 성립한다.

## 문제 구조 (추상화 코드)

### 변형 A — 감소 경로가 어긋남을 일부만 드러낸다 (만료 배치)
① 문제 구조
```kotlin
@Transactional                                      // 틱 하나 = 트랜잭션 하나
fun expire(): Int {
    val expired = repo.findExpired(now).flatMap { it.removeExpired(now) }   // 실제로 지운 행
    expired.groupingBy { it.scopeId to it.userId }.eachCount().forEach { (key, n) ->
        val updated = jdbc.update(
            "UPDATE user_quota SET cnt = cnt - ? WHERE scope_id = ? AND user_id = ?", n, key.first, key.second)
        check(updated == 1) { "카운터 행 없음: $key" }   // ① 행 없음 → 예외
    }                                                // ② 음수 → CHECK (cnt >= 0) 위반 → 예외
    return expired.size                              // ③ cnt ≠ 실제지만 ≥ n → 성공, 조용히 틀림
}
// ①·② → 틱 전체 롤백 → 다음 틱에 같은 행을 다시 조회 → 매 틱 실패 = 모든 범위의 만료 정지
```
② 필요한 것 (원문은 후속 과제로 남긴 미해결 위험 — 아래는 후속 설계가 다룰 축이며 이 사례에서 구현하지 않았다)
```text
탐지: 원본 재계산과 카운터의 대조(불일치 쌍)를 운영 중에도 본다 — 배치 실패에 기대지 않는다
격리: 어긋난 쌍 하나가 배치 전체를 멈추지 않게 한다
복구: 어긋난 쌍을 원본에서 다시 센 값으로 되돌린다
```
무엇이 깨졌나(잠재): 정상 경로는 어긋남을 만들지 않지만, 한 번 어긋나면 탐지·복구가 없다 — 시끄러운 갈래는 전역 정지로, 조용한 갈래는 한도 판정 오류로 나타난다.\
같은 구조: 감소량을 별도 조회로 세면 조회~삭제 사이 확정된 행까지 내린다 → 실제로 지운 행에서 센다(질문 7).

### 변형 B — 카운터를 유지하지 않던 데이터에서 전환하기 (백필 + cutover)
① 문제 구조
```text
옛 버전: 원본 행만 쓴다(카운터 없음 또는 낡음)
새 버전: 카운터로 한도를 판정 → 전환 직후 카운터 = 0 또는 낡은 값 → 판정이 틀리고, 만료 감소가 음수·행 없음으로 실패
```
② 고친 코드
```sql
-- 전제: 이 파일 실행 전에 옛 쓰기 주체를 모두 멈춘다(cutover). 직후 불일치 0을 확인한다.
LOCK TABLE holds, confirmed, user_quota IN SHARE ROW EXCLUSIVE MODE;   -- 실행 중의 쓰기 차단

-- 실제 값 >= 1 인 쌍: 없으면 만들고, 다르면 덮어쓰고, 같으면 쓰지 않는다(멱등)
INSERT INTO user_quota (scope_id, user_id, cnt)
SELECT scope_id, user_id, sum(n)::int                 -- 범위를 넘으면 조용히 자르지 않고 오류
FROM ( SELECT scope_id, user_id, count(*) n FROM holds GROUP BY 1, 2          -- 만료 전·후 구분 없음
       UNION ALL
       SELECT scope_id, user_id, count(*) n FROM confirmed GROUP BY 1, 2 ) actual
GROUP BY scope_id, user_id
ON CONFLICT (scope_id, user_id) DO UPDATE SET cnt = EXCLUDED.cnt
WHERE user_quota.cnt <> EXCLUDED.cnt;

-- 실제 값 0 인데 cnt <> 0 인 기존 행: 0으로 둔다(행은 지우지 않는다 — 다른 경로가 만든 행을 보존)
UPDATE user_quota q SET cnt = 0
WHERE q.cnt <> 0
  AND NOT EXISTS (SELECT 1 FROM holds h     WHERE (h.scope_id, h.user_id) = (q.scope_id, q.user_id))
  AND NOT EXISTS (SELECT 1 FROM confirmed c WHERE (c.scope_id, c.user_id) = (q.scope_id, q.user_id));
```
무엇이 깨졌나(예방한 것): 카운터 정의를 감소 시점에 맞춰(만료됐지만 안 지운 행 포함) 원본에서 다시 세고 덮어써, 전환 직후의 어긋남을 0으로 만들었다 — 섞인 데이터에서 불일치 4 → 0, 두 번째 실행은 아무 행도 쓰지 않음, 빈 DB는 무동작.\
남은 것: 잠금은 실행 중의 쓰기만 막는다 — 백필 뒤의 옛 쓰기는 cutover 조건으로만 막히고, 그 뒤 생기는 어긋남의 탐지·복구는 변형 A ②로 넘어간다.
