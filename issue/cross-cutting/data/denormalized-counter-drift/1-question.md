# issue/cross-cutting/data/denormalized-counter-drift — 비정규화 카운터가 원본과 어긋나면 일부만 오류로 드러나고 나머지는 조용히 틀린다 — 질문

## 질문
1. (왜) 한 사람이 가진 보유 수를 매번 원본 행에서 세지 않고 `(범위, 사용자)`당 카운터 행(`cnt`, `CHECK (cnt >= 0)`)으로 따로 둔다. 무엇을 얻고, 그 순간 어떤 의무가 생기는가 — "같은 사실이 두 곳에 있다"로 설명하라.
2. (예측) 만료 배치가 지운 보유 수만큼 `UPDATE … SET cnt = cnt - n` 으로 카운터를 내리고, 영향 행이 1이 아니면 예외를 던진다. 카운터가 ① 행 자체가 없을 때 ② 지운 수보다 작을 때 ③ 실제와 다르지만 지운 수 이상일 때, 각각 무슨 일이 일어나는가.
3. (경계) 만료 배치는 트랜잭션 하나로 "만료된 보유 전체"를 다시 조회해 처리한다. ①·②의 쌍이 하나만 있어도 왜 한 틱의 손실로 끝나지 않는가 — 다른 사용자·다른 범위의 만료는 어떻게 되는가.
4. (연결) ③에서 카운터가 실제보다 작으면, 크면 사용자는 각각 무엇을 겪는가. 왜 "배치가 실패하지 않는다"는 감시만으로는 정합을 말할 수 없는가.
5. (정의) 카운터 감소가 "만료 시각"이 아니라 "실제로 행을 지운 시점"에 일어난다면, 카운터 정의(=재계산 기준)에 만료 시각이 지났지만 아직 안 지운 행을 넣어야 하는가. 정의를 틀리게 잡은 백필은 무엇을 만드는가.
6. (전환) 카운터를 유지하지 않던 버전에서 유지하는 버전으로 바꿀 때 백필을 한다. 백필 안의 테이블 잠금은 무엇을 막고 무엇을 못 막는가 — 전환 조건(cutover)으로 무엇을 따로 지켜야 하는가.
7. (감소의 출처) 감소량을 "만료 대상 조회"로 따로 세지 않고 실제로 지운 행에서 세는 이유는 무엇인가.
