# issue/cross-cutting/infra/client-api-version-floor — 정답

## 정답

<!-- 질문 1:1 대응 -->

1. 바뀐 것은 **로컬 Docker 데몬**이다. 데몬이 새 메이저(29)로 올라가며 받아 주는 최소 API 버전을 1.44로 올렸고, 테스트 라이브러리는 여전히 1.32로 요청했다. "재현 가능한 빌드"는 **빌드에 들어오는 산출물**(라이브러리 버전)을 고정한다는 뜻이지, 테스트가 실행 중에 말을 거는 **외부 상대**까지 고정하지는 않는다. 데몬은 빌드 밖에 있어 OS 업데이트로 스스로 바뀌므로, 그쪽이 바뀌면 같은 커밋이 다른 결과를 낸다.
   > **환경 드리프트(environment drift)** — 코드·설정은 그대로인데 실행 환경(데몬·OS·런타임)이 바뀌어 결과가 달라지는 것.

2. **고정**은 클라이언트가 "나는 v1.32로 말한다"를 일방적으로 정하는 방식이다. 서버가 그 버전을 더 이상 받지 않으면 즉시 실패한다. **협상**은 먼저 서버에 지원 범위를 묻고(버전 조회) 양쪽이 아는 가장 높은 버전으로 맞추는 방식이라, 서버가 최소 버전을 올려도 클라이언트가 그 범위 안에 있는 한 계속 동작한다. 서버의 최소 버전 상향에 고정 방식은 깨지고, 협상 방식은 견딘다.
   > **API 버전 협상** — 클라이언트와 서버가 통신 전에 공통으로 지원하는 버전을 정하는 절차. HTTP 콘텐츠 협상, TLS 버전 협상이 같은 부류다.

3. 폴백 구조에서 최종 메시지는 **마지막 판단**("쓸 수 있는 전략이 없다")만 전한다. 각 전략의 실패 사유는 중간 로그로만 남고, 뒤쪽 전략의 실패(이번엔 소켓 경로가 없어 NPE)는 원인과 무관한 잡음이다. 먼저 볼 곳은 **첫 번째로 시도된 전략**의 사유다. 설정 파일이 "이 전략부터 시도"라고 지정해 둔 전략이 대개 실제 환경이고, 거기서 나온 `400 client version 1.32 is too old`가 진짜 원인이었다.

4. BOM 구조에서는 라이브러리 버전이 **프레임워크 버전에 딸려** 정해진다. 한 라이브러리만 올리려면 BOM이 노출하는 **버전 프로퍼티**를 빌드 설정에서 덮어쓴다(개별 의존성에 버전을 직접 박으면 같은 계열의 다른 아티팩트가 옛 버전에 남아 섞일 수 있다). 확인할 것: ① 같은 계열 아티팩트(코어·DB 모듈·JUnit 연동)가 모두 새 버전으로 해석되는가 ② 그 버전이 실제로 문제를 고친 판인가(릴리스 노트·이슈) ③ 프레임워크의 연동 모듈과 호환되는가 — 여기서는 패치 버전(1.21.3 → 1.21.4)이라 호환 위험이 작았다.
   > **BOM(Bill of Materials)** — 서로 호환되는 의존성 버전 묶음. 가져다 쓰면 개별 버전을 적지 않아도 되지만, 그 대신 버전을 내가 고르지 않게 된다.

5. 증거는 **실제로 나간 요청**이다. 설정 파일에 1.44가 있었지만 서버 응답 메시지는 "client version **1.32**"라고 말했다 — 클라이언트가 그 키를 읽지 않았다는 뜻이다(설정 키 이름이 다르거나, 그 전략이 해당 설정을 쓰지 않는 경우). 규칙: 설정의 효과는 설정 파일로 증명하지 않는다. **관측 가능한 행동**(보낸 버전, 로그의 적용값, 요청 헤더)으로 증명한다.

6. 선택지와 대가:
   - **협상하는 클라이언트로 올린다** — 가장 근본적이다. 대가는 메이저 업그레이드일 경우 API 변경 대응.
   - **수정된 패치 버전으로 고정한다**(이번 선택) — 변경이 작다. 대가는 다음 데몬 업데이트 때 또 올 수 있다는 것.
   - **데몬 버전을 고정한다**(자동 업데이트 끄기, CI 러너 이미지 고정) — 재현성이 가장 높다. 대가는 보안 패치가 늦어지고 로컬·CI 환경을 따로 관리해야 한다.
   - **실패를 빨리 알리게 한다** — 테스트 시작 시 환경 점검(데몬 버전 출력)을 둬서 "환경을 찾을 수 없다" 대신 원인을 바로 보인다.

## 발생한 문제 / 해결 (추상 원리)

**문제:** 버전을 협상하지 않는 클라이언트 × 빌드 밖에서 자동 업데이트되는 서버. 서버가 최소 지원 버전을 올리자 코드 변경 없이 연결이 거부됐고, 폴백 구조의 요약 메시지가 원인을 가렸다. 사용자 설정에 새 버전을 적어 둔 것도 적용되지 않았다.

**해결:** ① 시도 로그의 첫 전략 실패 사유에서 원인(버전 하한)을 찾는다. ② BOM의 버전 프로퍼티를 덮어써 수정판(패치 버전)으로 올린다 — 코드 한 줄, 같은 계열 아티팩트 일괄 적용. ③ 설정이 먹었는지는 실제 요청의 버전으로 확인한다. ④ 근본적으로는 협상하는 메이저 버전으로의 이전을 후속 과제로 둔다.
