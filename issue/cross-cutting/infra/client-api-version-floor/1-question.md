# issue/cross-cutting/infra/client-api-version-floor — 클라이언트가 고정한 API 버전이 서버의 최소 버전 아래로 떨어지면 코드 변경 없이 깨진다 — 질문

태그: `version-negotiation` · `environment-drift`

## 질문

1. (왜) 코드도 의존성도 한 줄 안 바꿨는데 어제 되던 통합 테스트가 오늘 "Docker 환경을 찾을 수 없다"로 실패했다. 무엇이 바뀌었고, 왜 빌드가 "재현 가능"하다는 믿음이 여기서 깨지는가?

2. (경계) 클라이언트가 API 버전을 **고정해서 보내는 것**과 **서버와 협상하는 것**은 무엇이 다른가? 서버가 최소 지원 버전을 올렸을 때 두 방식은 각각 어떻게 반응하는가?

3. (예측) 실패 메시지는 "유효한 Docker 환경 없음"이었고 진짜 원인(400 "client version 1.32 is too old")은 그 아래 시도 로그에 있었다. 라이브러리가 여러 연결 전략을 순서대로 시도하고 모두 실패하면 최종 메시지가 왜 원인을 가리게 되는가? 로그의 어디를 먼저 봐야 하나?

4. (연결) 그 버전은 내가 선택한 적이 없다 — 프레임워크 BOM이 정했다. BOM(의존성 관리 목록)이 버전을 정해 주는 구조에서, 한 라이브러리만 올리려면 어디를 바꿔야 하고 무엇을 확인해야 하나?

5. (경계) 사용자 설정 파일에 "API 버전 1.44"를 적어 뒀는데도 클라이언트는 1.32를 보냈다. 설정이 있어도 적용되지 않는 경우를 어떻게 확인하나 — "설정했다"와 "적용됐다"를 가르는 증거는 무엇인가?

6. (연결) 로컬 Docker 데몬처럼 **빌드 밖에서 자동 업데이트되는 의존**을 가진 테스트는 어떻게 재현성을 지킬 수 있나? 선택지와 그 대가를 말해 보라.
