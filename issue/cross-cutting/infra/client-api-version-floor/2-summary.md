# issue/cross-cutting/infra/client-api-version-floor — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 클라이언트 라이브러리가 API 버전을 협상하지 않고 **고정값으로 보내면**, 서버(외부에서 자동 업데이트되는 데몬)가 최소 지원 버전을 올리는 순간 내 코드와 무관하게 연결이 끊긴다 — 해결은 협상하는(또는 새 버전을 고정한) 클라이언트로 올리는 것이다.

```
[어제]                                  [오늘 — 데몬만 자동 업데이트]
테스트 ─▶ 컨테이너 라이브러리              테스트 ─▶ 컨테이너 라이브러리 (그대로)
            │ API v1.32 고정                          │ API v1.32 고정
            ▼                                        ▼
         Docker 데몬 (최소 v1.2x)                  Docker 데몬 (최소 v1.44로 상향)
            │ 200 OK                                  │ 400 "client version 1.32 is too old"
            ▼                                        ▼
         컨테이너 기동                            전략 A 실패 → 전략 B 실패(엉뚱한 NPE)
                                                     ▼
                                   최종 메시지: "Could not find a valid Docker environment"
                                   (진짜 원인은 전략 A의 400 — 시도 로그에만 있다)

해결: BOM이 고른 라이브러리 버전을 수정판으로 덮어쓴다
     (빌드 설정의 버전 프로퍼티 1개) → 데몬이 받는 버전으로 요청 → 기동
```

핵심은 **"빌드 밖의 의존"** 이다. 의존성 잠금은 내 빌드에 들어오는 라이브러리 버전을 고정할 뿐, 테스트가 말을 거는 로컬 데몬의 버전은 고정하지 못한다. 데몬이 OS 패키지로 자동 업데이트되면 **양쪽 버전 범위가 어긋나는 날**이 조용히 온다.

두 번째 함정은 **요약 메시지가 원인을 가린다**는 것이다. 여러 연결 전략을 순서대로 시도하는 라이브러리는 마지막에 "다 실패했다"만 말한다. 원인은 **첫 번째(가장 유력한) 전략의 실패 사유**에 있다.

세 번째는 **"설정했다" ≠ "적용됐다"** 다. 사용자 설정 파일에 버전을 적어 뒀어도 클라이언트가 그 키를 읽지 않으면 효과가 없다. 증거는 설정 파일이 아니라 **실제로 보낸 요청(에러 메시지 속 버전 숫자)** 이다.

## 핵심 문장

- 의존성 잠금은 빌드 안만 고정한다 — 데몬·브라우저·클라우드 API 같은 빌드 밖 상대는 스스로 바뀐다.
- 고정 버전 클라이언트 × 서버 최소 버전 상향 = 코드 변경 없는 파손. 협상하는 클라이언트는 이 부류에 강하다.
- 폴백 전략이 여럿이면 최종 메시지는 "다 실패"뿐 — 첫 전략의 실패 사유를 읽어라.
- 설정이 적용됐는지는 설정 파일이 아니라 실제 요청(메시지 속 버전)으로 확인한다.
- BOM이 고른 버전은 내가 고른 게 아니다 — 올릴 땐 BOM 프로퍼티를 덮어쓰고, 같은 계열 아티팩트가 함께 따라오는지 확인한다.
