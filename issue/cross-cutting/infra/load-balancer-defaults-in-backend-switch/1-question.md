# issue/cross-cutting/infra/load-balancer-defaults-in-backend-switch — 로드밸런서는 전환 경로의 일부다: 파일 기술자 한도·수동 장애 판정·reload의 기본 동작이 백엔드 교체 순간 자기 몫의 오류를 만든다 — 질문

## 질문
1. (왜) 컨테이너로 띄운 nginx에 `worker_connections 8192`를 주었다. 컨테이너의 기본 파일 기술자 soft 한도가 1024면, 백엔드 하나가 느려져 연결이 쌓이는 순간 무엇이 일어나나. 프록시하는 요청 하나가 기술자를 몇 개 쓰는지로 설명하라 — 이때 클라이언트가 받는 오류는 백엔드 탓처럼 보이나.
2. (예측) upstream `server` 줄에 아무 옵션도 주지 않으면 nginx는 시한 초과·연결 실패를 보고 그 서버를 잠시 뺀다(기본 `max_fails=1` · `fail_timeout=10s`). upstream에 서버가 하나뿐인 구간에서 요청 하나가 시한을 넘기면 다음 10초 동안 무엇이 나가나.
3. (설계) 2의 동작을 끄면(`max_fails=0`) 죽은 백엔드로 계속 보내게 되지 않나 — 그 책임은 누가 맡아야 하나. 롤링 전환에서 "구성원 넣기"는 어떤 조건 뒤에 해야 하나.
4. (지식) 구성원을 바꾸려고 `nginx -s reload`를 하면 새 작업자가 뜨고 옛 작업자는 진행 중 요청을 끝내고 내려간다. 그런데도 reload 직후 일부 요청이 응답 코드 없이(연결 오류로) 끝났다. 클라이언트가 재사용하던 keepalive 연결에 무슨 일이 일어났나.
5. (측정) 4의 연결 오류는 백엔드 교체 절차의 비용인가, 측정용 로드밸런서의 비용인가. 절차 비교에서 그것을 따로 세려면 어떤 창을 어떤 시각 기준으로 잡아야 하나(완료 시각 vs 보낸 시각).
6. (연결) 세 결함은 모두 "앱이 아닌 곳에서 생긴 5xx·연결 오류"였다. 전환을 재는 실험에서 로드밸런서를 측정 대상 밖으로 두려면 무엇을 고정하고 무엇을 따로 세야 하나.
