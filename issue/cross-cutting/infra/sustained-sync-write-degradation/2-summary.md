# issue/cross-cutting/infra/sustained-sync-write-degradation — 정리 (힌트)

## 전체 흐름

```
요청 ─▶ 앱 ─▶ 커넥션 풀(10) ─▶ DB ─▶ 커밋마다 로그 동기화(fsync/fdatasync)
                                              │
                                              ▼
                       파일시스템 ─▶ 볼륨 매니저 ─▶ 파티션 ─▶ SSD   (= 저장 경로)
                                              │
              누적 쓰기 수 GB 뒤 ─────────────┘
                flush/s  ~2,000 → ~400~800 (약 1/3)
                flush 평균 ~0.4ms → ~1.2~2.2ms (약 3배)
                       ▼
              DB: 로그 쓰기 대기(WALWrite) 0.3 → 4.5 세션, 커밋 경로 시간 약 5배(추정)
              앱: 풀 10개가 차고 요청이 앱 안에서 줄 섬
                       ▼
              처리량 반감 — 세 방식 모두 같은 지점(방식 차이 = 도달 시점뿐)

원인 확정 (세 갈래)
  (a) 꺾이는 순간 호스트 장치 지연이 함께 뜀              → 앱·DB 내부 원인만으로는 설명 불가
  (b) DB 없이 합성 쓰기(미리 채운 파일 덮어쓰기 + 매 쓰기 동기화)로 같은 서명 재현 → DB 동작이 아님
  (c) 데이터 디렉터리를 메모리로 → 고정 4,200건/s 6/6 유지(디스크 6/6 붕괴) → 저장 경로를 빼면 사라짐
  (d) 30분 쉬어도 같은 지점 → 디스크 이력에 거의 매이지 않음 (선택 신호, 불성립)

남는 한계
  · 확인된 것은 "이 서버의 저장 경로"(장치 + 호스트 쓰기 층) — SSD 하나가 아니다
  · 메모리 조건은 DB 메모리 한도도 함께 바꿨다(교란)
  · "DRAM 없는 SSD의 캐시·매핑 동작"은 해석 — 장치 안은 못 봤다
  · 꺾이는 누적량이 DB(3.3~3.7GB)와 합성(5.2GB)에서 다르다 — 미설명
```

## 핵심 문장

- 저장 경로의 쓰기 성능은 **정상 상태가 아니다** — 지속 동기화 쓰기는 일정량 뒤 flush 지연이 커지고 flush 수가 줄어드는 형태로 꺾일 수 있다.
- 모든 비교 대상이 같은 환경 벽에 닿으면 처리량 차이는 방식의 차이가 아니라 **벽에 닿는 시점의 차이**다 — 같은 서버에서는 정합·쓰기량·순서 같은 상대 비교만 유효하다.
- 원인을 환경 층에 돌리려면 **함께 움직임(상관) + 그 층만으로 재현 + 그 층을 빼면 소멸**을 갖춘다.
- 합성 재현은 대상의 쓰기 **패턴**(덮어쓰기·동기화 빈도)을 흉내 내고, 판정은 총 MB/s가 아니라 **flush 수·flush 지연**으로 한다.
- 장치 안을 보지 못했으면 장치 내부 설명은 **해석**으로 적는다 — 확인 범위는 커널이 보는 요청 시간까지다.
