# issue/cross-cutting/infra/sustained-sync-write-degradation — 저장 경로는 지속 동기화 쓰기에서 느려진다: 모든 방식이 같은 벽에 닿으면 비교가 가려진다 — 질문

## 질문
1. (왜) 저장 장치의 쓰기 성능은 처음 몇 분과 수 GB를 쓴 뒤가 같다고 가정해도 되는가. 쓰기마다 동기화(fdatasync)가 붙는 부하에서 그 변화는 MB/s보다 어떤 지표에 먼저·크게 나타나는가.
2. (예측) DB 쓰기 방식 세 가지를 같은 서버에서 비교했더니, 세 방식 모두 DB의 누적 블록 쓰기가 비슷한 양(약 8~9GB)에 닿는 순간 처리량이 반으로 꺾였다. 이 상황에서 "방식 A의 한계가 낮다"는 결론은 무엇을 재고 있는가. 같은 서버에서 여전히 유효한 비교는 무엇인가.
3. (교정) 벽을 저장 경로 탓으로 확정하려고 세 가지를 했다 — 꺾이는 순간 호스트 장치 지연이 함께 뛰는지, DB 없이 합성 쓰기 도구로 재현되는지, 데이터 디렉터리를 메모리로 옮기면 사라지는지. 각각은 어떤 대안 설명을 배제하는가.
4. (경계) 합성 쓰기 재현은 왜 대상 부하의 **패턴**(미리 채운 파일 덮어쓰기 + 쓰기마다 동기화)을 흉내 내야 하는가. 파일 끝에 덧붙이는 패턴으로 잰 결과는 무엇을 말해 주었고, 무엇을 말해 주지 못했는가.
5. (경계) 메모리 파일시스템 조건에서 벽이 사라졌다. 이것이 "SSD가 원인"의 증거가 되지 못하는 이유는 무엇인가 — 그 조건이 함께 바꾼 것을 말하라.
6. (왜) "캐시용 DRAM이 없는 소비자용 SSD의 내부 동작 때문"이라는 설명은 측정으로 확인된 사실인가, 해석인가. 커널 쪽에서 볼 수 있는 것은 어디까지인가.
7. (연결) DB 설정(체크포인트 끄기·공유 버퍼 4배)으로 벽이 옮겨지지 않았다. 처리량 벽을 만나면 설정 손잡이부터 돌리는 접근이 왜 위험한가 — 병목 식별 원칙과 연결하라.
