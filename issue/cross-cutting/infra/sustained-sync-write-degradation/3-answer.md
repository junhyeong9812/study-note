# issue/cross-cutting/infra/sustained-sync-write-degradation — 정답

태그: `environment-drift`

## 정답
<!-- 질문 1:1 대응 -->

1. **가정할 수 없다 — 지속 쓰기에서는 일정량 뒤 꺾일 수 있다. 신호는 flush 수와 flush 지연이다.**\
   이 사례의 저장 경로는 매 쓰기 동기화가 섞인 부하에서 몇 GB를 쓴 뒤 flush/s가 약 1/3로 줄고(약 2,000 → 약 700회/s) flush 평균 지연이 약 3배(0.40 → 1.24~1.30ms)가 됐다.\
   총 쓰기 MB/s는 버퍼 쓰기가 받쳐 0.67배 정도로만 줄어, 총량 기준 탐지(0.6배 미만)에는 잡히지 않았다 — 동기화 쓰기의 성능은 **요청 단위 지연·횟수**로 본다.
   > **flush(동기화) 요청** — `fsync`·`fdatasync`가 장치에 보내는 "휘발성 캐시를 영구 저장소로 내려라" 요청. 커널 디스크 통계에 횟수·누적 시간 열이 따로 있다(신형 커널).
   > **w_await** — 쓰기 요청 하나가 대기열에서 기다린 시간까지 포함한 평균 체류 시간. 장치 속도 자체가 아니라 대기열이 섞인 값이라 flush 평균과 함께 본다.

2. **방식이 아니라 "벽에 언제 닿는가"를 재고 있다.**\
   세 방식 모두 DB 컨테이너의 누적 블록 쓰기 8.29~9.51GB 지점에서 쓰기가 반감했고, 무너진 뒤 처리량은 세 방식이 같았다(약 2,450건/s).\
   방식 차이는 요청당 쓰기량(예: 891B 대 1.09KB의 로그)에 따른 **도달 시점**뿐이었다 — 계단 부하에서는 그 시점이 단계 경계 앞이냐 뒤냐로 한계가 한 칸씩 갈렸다.\
   같은 서버에서 여전히 유효한 것은 상대 비교다 — 정합성, 오류 순서, 요청당 쓰기량, 도달 순서. 오염된 것은 **처리량의 절대 한계**다(처리량 자체를 볼 때는 메모리 저장소나 다른 디스크에서 잰다).

3. **세 갈래가 서로 다른 대안을 지운다.**\
   (a) 상관: 디스크 회차 12/12에서 반감 순간 호스트 장치 w_await 0.24~0.30 → 0.76~2.16ms, flush 평균 0.41~0.49 → 1.15~2.22ms가 함께 뛰었다 → "DB·앱 내부만의 원인"(체크포인트·버퍼 교체·락)이 장치 지연을 같이 만들 이유가 없다. DB 대기 이벤트도 로그 쓰기 계열만 커졌고 버퍼·확장 락 계열은 없었다.\
   (b) 단독 재현: DB를 띄우지 않고 합성 쓰기 도구로 같은 서명(flush/s 약 1/3·flush 평균 약 3배)이 2/2 재현됐다 → DB 소프트웨어의 동작이 아니다.\
   (c) 층 제거: 데이터 디렉터리(로그 포함)를 메모리 파일시스템으로 옮기자 고정 4,200건/s가 6/6 유지됐다(디스크 6/6 붕괴), 로그 쓰기 대기도 0.01 이하로 사라졌다 → 저장 층을 빼면 벽이 없다.\
   계단 부하의 벽은 메모리 조건에서도 사라지지 않고 1~2단계 뒤로 밀렸는데, 그때 대기 상위는 CPU·클라이언트 읽기였다 — **다른 벽**(서명이 바뀜)이다.

4. **패턴이 다르면 "재현 안 됨"도 "재현됨"도 증거가 약하다.**\
   DB 로그는 미리 만들어 둔 세그먼트 파일을 **덮어쓰며** 커밋마다 동기화한다. 그래서 합성 시험도 1GiB 파일을 0으로 미리 채우고 그 안을 8KiB씩 순차 덮어쓰며 매 쓰기 `fdatasync`(16MiB/s 제한), 옆에 버퍼 쓰기 작업을 함께 돌렸다 → 기준선(flush 약 2,020회/s · 0.40ms)이 DB 회차의 반감 전 값과 같은 자릿수였다.\
   처음의 덧붙이기 패턴(파일이 자람)은 실행 전체 평균 동기화 지연이 2.44ms라 "패턴이 달라 원래 느리다"로 읽혔지만, 시간 칸으로 다시 보니 꺾이기 전은 0.42~0.44ms였고 약 7.8GB에서 같은 모양으로 꺾여 있었다(총량 기준 탐지가 놓쳤다).\
   덧붙이기 패턴이 알려 준 것: 초당 flush가 약 900회로 절반 이하여도 꺾였다 — "초당 2,000회" 자체가 조건은 아니다. 못 알려 준 것: DB와 같은 기준선에서 같은 서명이 나는지(그래서 패턴을 맞춰 다시 쟀다).

5. **메모리 조건은 저장 층 전체를 빼고, DB 메모리 한도도 함께 바꿨다.**\
   메모리 파일시스템은 파일시스템·볼륨 매니저·파티션·장치를 **모두** 우회한다 — 그래서 확인된 범위는 "이 서버의 저장 경로(장치 + 호스트 쓰기 층)"이지 SSD 하나가 아니다(합성 재현도 같은 층을 모두 지났다).\
   또 그 조건은 DB 메모리 한도를 2g → 8g로 올렸다 — 교란 변수다. "저장 경로를 빼면 사라진다"까지만 말할 수 있다.

6. **해석이다.**\
   볼 수 있었던 것은 커널 디스크 통계(요청 수·누적 시간·대기열)까지다. 권한이 없어 장치 자체 진단(SMART 등)도 읽지 못했다.\
   "DRAM 없는 SSD의 캐시·매핑 동작"은 관측과 맞는 설명일 뿐 측정이 아니므로, 문서에는 해석으로 표시했다.\
   설명되지 않은 것도 그대로 남겼다 — 꺾이는 누적량이 DB 회차(호스트 기준 3.26~3.74GB)와 합성 시험(5.2GB, 미리 채우기 포함 6.3GB)에서 다르고, 고정 속도라 합성 시험에서는 시간(+179초)과 누적량이 겹친다. 계단 회차 하나는 반감보다 약 100초 앞에서 다른 서명으로 무너졌다(미설명).

7. **손잡이가 병목에 닿지 않으면 결과는 우연이다.**\
   체크포인트를 끄거나 공유 버퍼를 4배로 해도 같은 지점에서 반감·붕괴했다 — 병목이 DB 안이 아니라 그 아래 저장 경로였기 때문이다.\
   설정을 바꿔 벽이 "밀렸다"면 오히려 위험하다 — 설정은 캐시·쓰기 시점을 함께 바꾸므로, 원인을 모른 채 증상만 옮긴 것일 수 있다(그래서 이 사례는 설정 축을 대기 이벤트와 함께 판정했다).\
   먼저 어느 층이 포화·지연되는지를 층별 지표로 찾고, 손잡이는 그 층에서 고른다(→ [bottleneck-identification](../bottleneck-identification/)).

## 문제 구조 (추상화 코드)

### 변형 A — 모든 방식이 같은 환경 벽에 닿아 비교가 가려짐
① 문제 해석
```text
방식 X  계단 한계 2,866   방식 Y  4,300   방식 Z  4,165
결론: "X는 처리량이 낮다"            ← 세 방식 모두 같은 누적 쓰기 지점에서 반감, 붕괴 뒤 처리량 동일
```
② 고친 해석
```text
벽 = DB 누적 블록 쓰기 ~9GB 지점의 쓰기 반감 (방식·DB 설정 무관)
방식 차이 = 요청당 쓰기량 → 벽 도달 시점          (상대 비교: 유효)
처리량 절대값 = 이 서버 저장 경로에 묶임          (오염 — 다른 저장소에서 다시 잼)
```
무엇이 깨졌나: 환경의 성능 상한이 방식의 성능 차이처럼 보였다.

### 변형 B — 저장 경로 원인 확정: 상관 + 단독 재현 + 층 제거
```bash
# (a) 상관 — DB 회차 중 호스트 디스크 통계를 1초마다 표본
while sleep 1; do read_diskstats "$DEV"; done        # writes, write_ms, flushes, flush_ms
# 반감 시각 ±30초: flush/s · flush 평균 · w_await 전후 비교

# (b) 단독 재현 — DB 없이 같은 쓰기 패턴
fio --name=log  --filename=log.dat --size=1g --rw=write --bs=8k --fdatasync=1 \
    --rate=16m --time_based --runtime=300          # log.dat 는 미리 0으로 채워 둠(덮어쓰기)
    --name=data --filename=data.dat --rw=write --bs=8k --rate=12m --fsync=4096
# 판정: 총 MB/s 가 아니라 flush/s · flush 평균의 반감·지속 상승

# (c) 층 제거 — 데이터 디렉터리를 메모리 파일시스템에(메모리 한도 변경은 교란으로 기록)
docker run --tmpfs /var/lib/db/data:size=... db-image
```
무엇이 깨졌나(처음 판정): 덧붙이기 패턴 + 총량 기준 탐지로 (b)를 "재현 안 됨"으로 읽었다 — 패턴을 맞추고 flush 기준으로 보자 성립했다.
