# 템플릿 — 프로젝트 이슈 정리

> 프로젝트에서 이슈 하나(이슈 → 구현 → PR)가 끝나면, 그 전체 맥락을 이 골격으로
> `project/study-note-deploy-system/<서버>/issueN/README.md` 한 파일에 정리한다.

## 작성 규칙

1. **일상적인 용어로 쓴다.** 전문용어를 썼다면 첫 등장에서 괄호나 한 줄로 풀어준다.
   용어 설명이 세 줄을 넘어가면 별도 용어 노트로 빼고 여기선 링크만 건다.
2. **그림은 ASCII로 코드블럭 안에.** 요청이 어디로 흘러 어떤 객체를 거치는지,
   화살표로 따라갈 수 있게 그린다.
2-1. **배경·검토한 방식들에도 스니펫·예시를 반드시 보여준다** — "A방식은 이래서 탈락"
   같은 말만 있으면 판단을 재구성할 수 없다. 각 방식의 모양(코드·설정·요청/응답 예시)을
   코드블럭으로 보여주고 그 위에서 비교한다. 수식·계산이 있으면 구체 숫자로 예를 든다
   (issue4의 RRF 계산표처럼).
3. **코드 수정 이슈라면 "기존 흐름 → 바뀐 흐름"을 둘 다 그린다.** 대안들도
   각각의 워크플로우를 그려서 왜 탈락했는지 흐름으로 보이게 한다.
4. **diff는 핵심 hunk만.** 전체 파일이 아니라 "이 몇 줄이 이 결정이다"를 보여준다.
5. 구현 중 문제는 **절대 요약하지 않는다.** 문제마다 이 흐름을 원맥락 그대로 적는다
   (읽는 사람이 맥락을 이해하고 → 개념을 모듈화·단순화하고 → 연결해서 장기기억으로
   가져갈 수 있어야 한다):
   - **상황**: 무엇을 하던 중이었나 — **실행 주체와 위치까지**(예: "에이전트 컨테이너 안의
     git이, 마운트된 호스트 디렉토리를 대상으로"). 주체가 애매하면 문제 전체가 애매해진다.
   - **문제(증상)**: 실제 에러 메시지·로그·명령 출력을 코드블럭으로 그대로 (기억 재현 금지).
   - **접근(진단)**: 무엇을 어떤 순서로 확인했고 각 단계에서 실제로 뭘 봤나. 검토한
     대안이 있으면 왜 버렸는지까지.
   - **결론(수정)**: 실제 diff + **그 수정이 왜 문제를 없애는지 메커니즘으로 설명**
     ("이렇게 하니 됐다"가 아니라 "이래서 된다").
   - **배경/원칙**: 여기서 꺼낼 일반 원칙 한 줄. 낯선 개념이 등장하면 본문에서 한 줄로
     풀고, 세 줄 넘으면 **별도 cs 문서로 모듈화**해 링크(예: RESP·세마포어·백오프).
6. 특정 사내·개인 프로젝트명은 이슈 문서에 쓰지 않는다 — "다른 프로젝트와 동형" 수준으로.

## 골격 (이 순서 그대로)

```markdown
# issueN — 제목 한 줄

- 리포 / 이슈 / PR 링크

## 1. 배경 (요구사항)
무엇이 필요했고 왜 필요했나. 이 이슈가 없으면 무슨 일이 생기나.

## 2. 검토한 방식들
### 선택 — <방식> (이유)
### 대안 — <방식> (선택하지 않은 이유)     ← 대안마다 반복. 코드 수정이면 대안별 워크플로우도.

## 3. 구현 워크플로우
요청/데이터가 객체들을 어떻게 타고 흐르는지 ASCII로. 처리 프로세스 단계별 설명.
(코드 수정 이슈면: 기존 흐름 → 바뀐 흐름 두 그림)

## 4. 코드 변경 (diff와 맥락)
핵심 hunk + "왜 이 줄인가" 한 문단씩.

## 5. 구현 중 마주친 문제
### 문제 → 원인(워크플로우) → 수정 → 이유/배경     ← 문제마다 반복

## 6. 결론
한 문단 요약 + PR 링크 + 남긴 것([구현 검증] 이연, 후속 이슈).
```

## ★ 최우선 원칙 — "처음 읽는 사람"이 맥락째 읽히게 (2026-09-02 강화)

이 문서들은 결정 로그가 아니라 **읽는 글**이다. 다음을 어기면 다시 쓴다:

1. **결정만 축약 금지.** "기각 2/이연 1", "채택 F4~F9" 같은 압축은 배경을 지운다.
   각 결정은 반드시 **왜 이 문제가 생겼나 → 무엇을 고민했나 → 그래서 이렇게 했다**의
   서사로 풀어 쓴다. 처음 읽는 사람이 그 결정에 도달하는 사고를 따라올 수 있어야 한다.
2. **모든 절차·워크플로우는 그림으로.** 흐름이 있으면 ASCII 플로우차트를 그린다.
   코드 수정 이슈면 **[기존 흐름] 과 [바뀐 흐름]을 나란히** 그려 무엇이 어디서
   달라졌는지 화살표로 보이게 한다. 글로만 "A를 B로 바꿨다"는 금지.
3. **낯선 용어는 그 자리에서 한 줄로 푼다** (in-flight, chunked, collapse 등). 세 줄
   넘으면 cs 문서로 빼고 링크. 약어·전문어를 설명 없이 던지지 않는다.
4. 분량이 늘어도 좋다 — "짧게"가 목표가 아니라 "혼자 읽어도 이해됨"이 목표다.

## 표현 규칙 — 은어 순화 (2026-09-02)

"박아뒀다/박았다" 같은 은어 대신 중립적 서술을 쓴다. 영어 원표현 매핑:

| 쓰지 않음 | 대신 | (영어 맥락) |
|---|---|---|
| 명세에 박아뒀다 | 명세에 기록해놨다 / 명시했다 | pinned/hardcoded in the spec → recorded/specified |
| 코드에 박았다 | 코드에 명시했다 / 못박았다(계약 한정) | hardcoded → specified; (계약이면) fixed |
| 규칙으로 박아뒀다 | 규칙으로 정해뒀다 | established as a rule |

의미가 "고정·불변 계약"일 때만 "못박다"를 남기고, 단순히 "적어뒀다"는 "기록/명시"로.
