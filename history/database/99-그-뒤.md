## 원본이 멈춘 자리

원본 6편은 **연표가 아니라 계보**로 쓰여 있다 — 관계형 → 오픈소스 → NoSQL → NewSQL → 특화 DB → 개념사.\
그래서 "어느 버전까지 다뤘다"로 자르기 어렵다.\
대신 **원문이 서술의 현재로 삼은 시점**을 기준으로 잡으면 이렇다.

| 원문의 마지막 언급 | 어디 |
|---|---|
| 2025년 5월 — Databricks 가 Neon 을 인수해 Lakebase 의 기반으로 삼음 | 05편 서버리스 |
| 2025년 9월 — PlanetScale 이 Neki 기반 Postgres 제품 추가 | 05편 서버리스 |
| "2026년 현재" — 벡터 DB 가 전용 엔진 / 기존 DB 확장 두 진영으로 갈림 | 05편 벡터 |
| 인용한 가장 늦은 출처: 2026-05-10 | 05편 출처 절 |
| 원본 repo 의 마지막 커밋: 2026-06-28 | git log |

**정리하면 원본은 「2026년 상반기의 풍경」에서 멈춰 있다.**\
제품별 릴리스 번호(PostgreSQL 18, MySQL 9.x 같은)는 원문이 거의 다루지 않는다 — 원본의 관심은 버전이 아니라 계보였기 때문이다.\
그래서 이 문서는 **"그 계보의 각 갈래가 2026-05-10 ~ 09-20 에 어디까지 갔나"**를 적는다.

### PostgreSQL 19 — 베타 진행 중, 정식은 아직 (2026-05 ~ 08)

원본 05편은 그래프 DB 를 다루며 **GQL 이 2024년 ISO 표준이 됐다**고 적었다.\
그 표준의 사촌뻘인 **SQL/PGQ** 가 PostgreSQL 본체에 들어오는 중이다.

> **SQL/PGQ (SQL Property Graph Queries)** — 관계형 테이블을 속성 그래프처럼 보이게 정의해 두고, SQL 표준 문법으로 그래프 질의를 던지는 기능.\
> 예 — PostgreSQL 19 릴리스 안내문의 표현 그대로: "letting users execute property graph queries using SQL standard syntax".

**PostgreSQL 19 는 2026-09-20 현재 정식 출시가 아니다.**\
베타다.\
아래는 **공식 뉴스 색인을 열어 창 안(05-10 ~ 09-20) 항목을 전수로 옮긴 것**이다 — 이 넷이 전부다.

| 날짜 | 사건 |
|---|---|
| 2026-05-14 | 18.4 · 17.10 · 16.14 · 15.18 · 14.23 정기 패치 |
| 2026-06-04 | PostgreSQL 19 **Beta 1** |
| 2026-07-16 | PostgreSQL 19 **Beta 2** |
| 2026-08-13 | **Beta 3** — 같은 날 18.6 · 17.11 · 16.15 · 15.19 · 14.24 정기 패치 동시 배포 |

Beta 1 안내문이 밝힌 주요 변화는 이렇다(모두 안내문의 서술 범위 안에서만 적는다).

- **SQL/PGQ** — 위 설명.
- **`REPACK` 명령** 신설. `CONCURRENTLY` 옵션을 붙이면 "less operational overhead" 로 테이블을 재구축한다.
- **데이터 체크섬을 온라인으로 켜고 끄기** — 클러스터 재시작이나 재초기화 없이.
- **JIT 컴파일이 기본 비활성화**로 바뀜.
- **`default_toast_compression` 기본값이 lz4** 로 — 안내문 표현으로 "better default compression and decompression performance".
- **비동기 I/O** — 18에서 들어온 비동기 I/O 위에서, `io_method=worker` 가 `io_min_workers`·`io_max_workers` 설정에 따라 워커 수를 자동 조절한다.

⚠️ 안내문은 정식 출시를 "September/October 2026" 무렵으로 **예상**한다고만 적었다 — 확정 날짜가 아니다.\
Beta 3 안내문은 정식 일정을 아예 언급하지 않았다.

같은 8월 패치에서 밝혀진 운영상의 기한 하나:\
**PostgreSQL 14 는 2026-11-12 에 수정 제공이 끝난다**(안내문이 직접 권고한 사항이다).

### MySQL — 버전 번호 체계가 바뀌었다 (2026-07-28), 그리고 26.10 EA 까지 (09-18)

원본 02편은 MySQL 을 "2000년 GPL 전환으로 LAMP 의 M 이 된" 자리까지 다루고, 버전으로는 8.0 매뉴얼만 인용한다.\
그 사이 MySQL 의 **번호 매기는 방식 자체**가 바뀌었다.

| 이전 | 이후 |
|---|---|
| 8.0 → 8.4 → 9.0 … 9.7 (순차 번호) | **26.7 …** (연·월 기반) |

공식 매뉴얼의 표현 그대로다.

> **캘린더 버저닝 (calendar versioning, YY.M.P)** — 버전 번호에 출시 **연도와 달**을 그대로 쓰는 방식.\
> 예 — MySQL 매뉴얼: "MySQL 26.7 represents the July 2026 release, and MySQL 27.7 represents the July 2027 release."

- **MySQL 9.7 이 순차 번호를 쓰는 마지막 라인**이다 — 매뉴얼 표현으로 "the final release line using the previous sequential versioning model".
- **MySQL 26.7.0 이 첫 캘린더 버전 릴리스**이고, 릴리스 노트가 직접 그렇게 적었다: "MySQL 26.7.0 is the first such calendar-version release."
- 출시일은 **2026-07-28**.

⚠️ 번호 체계가 바뀐 것이지 **트랙이 늘어난 게 아니다.**\
매뉴얼은 여전히 두 트랙만 둔다 — **LTS**(Oracle Lifetime Support Policy 에 따라 premier 5년 + extended 3년, "There are no removals within an LTS release")와 **Innovation**("supported until the next Innovation release").\
그럼 `26.7` 은 어느 쪽인가 — **릴리스 노트는 26.7.0 을 Innovation 이라고 직접 부르지 않는다.**\
노트가 적은 것은 이것뿐이다: "9.7.0" is the previous LTS version for MySQL 26.7.0.\
**확실한 것은 「26.7.0 은 LTS 가 아니고, 그 직전 LTS 가 9.7.0 이다」까지다.**\
⚠️ 트랙이 둘뿐이니 남는 쪽은 Innovation 이라는 **소거 추론은 가능하지만, 그건 출처의 문장이 아니라 이 문서의 추론이다.**

26.7.0 의 눈에 띄는 기능 하나는 복제 쪽이다.

> **CSA (Change Stream Applier)** — 다중 스레드 복제에서 복제본(replica) 쪽 SQL 적용기(applier)를 새로 구현한 것.\
> 예 — 릴리스 노트 표현: "an opt-in, per-channel alternative to the Multi-Threaded Applier (MTA)" — 기존 MTA 를 **대체한 게 아니라 채널별로 켜는 선택지**다.

릴리스 노트가 밝힌 CSA 의 성격은 이렇다 — 채널마다 applier 를 따로 설정하고, 채널당 워커 스레드를 1~1,024 개로 두며, **트랜잭션 적용과 커밋 순서 결정을 분리**한다("When a worker cannot yet commit, it can apply another dependency-ready transaction instead of waiting idle").

**릴리스 노트 색인을 열어 창 안(05-10 ~ 09-20) 항목을 전수로 세면 여섯이다.**

| 날짜 | 릴리스 | 성격(노트 표기) |
|---|---|---|
| 2026-06-16 | 9.7.1 | 순차 번호 라인(LTS)의 패치 |
| 2026-07-28 | **26.7.0** | **첫 캘린더 버전 릴리스** |
| 2026-07-28 | 9.7.2 | 같은 날 나온 9.7 라인 패치 |
| 2026-08-18 | 26.7.1 | "This release is a Critical Security Patch Update for the MySQL Server docker image, only." |
| 2026-08-18 | 9.7.3 | 같은 날 나온 9.7 라인 패치 |
| **2026-09-18** | **26.10.0** | 노트 제목의 표기 그대로 **"(Early Access Release)"** |

⚠️ **26.10.0 은 이 문서 기준일의 이틀 전**이다.\
번호가 캘린더 규칙("26.10" = 2026년 10월분)을 그대로 따른다는 것은 확인되지만, **노트가 스스로 Early Access 라고 적었으므로 「정식 출시」로 읽으면 안 된다.**\
정식 GA 날짜는 이 조사에서 **확인하지 못했다.**

### DuckDB — v2.0 가 예고되고 알파까지 왔다 (2026-08-17 · 09-02), 아직 출시 전

원본 05편은 DuckDB 를 "SQLite 가 OLTP 에서 한 일을 OLAP 에서 하는 in-process 엔진"으로 소개한다.\
그 정체성 자체가 흔들릴 수 있는 예고가 **2026-08-17** 에 나왔다 — 공식 블로그의 **v2.0 미리보기** 글이다.

⚠️ **v2.0 은 2026-09-20 현재 출시되지 않았다.**\
8월 미리보기의 표현은 "DuckDB v2.0 is coming this fall" — **가을 예정**이다.\
그 뒤 **2026-09-02 에 알파가 공개**되면서 일정이 한 칸 좁혀졌다 — "getting DuckDB v2.0 ready for release in **October**" 이고, `v2.0-cyanoptera` 브랜치를 떼어 **기능 동결(feature freeze)** 에 들어갔다고 적었다.\
**여전히 「예정」이다** — 10월도 블로그가 말한 목표이지 확정 날짜가 아니다.

미리보기가 꼽은 머리기사 기능 중 원본의 서술과 직접 부딪히는 것은 첫 번째다.

> **DuckDB as a Server** — DuckDB 프로세스가 자기 데이터베이스를 **네트워크 너머로 제공**하고, 다른 DuckDB 가 거기에 붙는(attach) 방식.\
> 예 — 블로그 표현: "Any DuckDB process can serve its databases over the network, and any other DuckDB can attach to it" — Quack 프로토콜과 새 `CONNECT` 문을 쓴다.

⚠️ **오해 주의** — "DuckDB 가 서버 DB 가 된다"로 읽으면 과하다.\
블로그가 말한 것은 *어떤 DuckDB 프로세스든 서버 역할을 **할 수 있다***는 것이지, in-process 모델을 버린다는 서술은 없다.\
원본이 적은 "프로세스 안에 임베드되는 분석 엔진"이라는 정체성이 폐기됐다는 근거는 이 글에 없다.

나머지 머리기사(블로그가 나열한 순서대로):

| 기능 | 블로그가 적은 내용 |
|---|---|
| **VARIANT 타입** | "A VARIANT column can store differently-shaped data in every row" — 구조 자동 감지·압축 |
| **트리거** | BEFORE/AFTER, FOR EACH ROW/STATEMENT 지원 |
| **SQL 방언 추가** | 유사도 검색용 NEAREST 조인, CTE 안의 DML, 중첩 스키마 등 |
| **비동기 I/O** | "The I/O layer now scales independently from the query processing layer" |
| **질의 속도** | 재귀 CTE 약 40배 빨라짐, row-group 가지치기 확대 |
| **스토리지 포맷 v2.0** | 컬럼 메타데이터 지연 로딩, 기본 압축 DICT_FSST, 손상 검증 강화 |

그 앞의 실제 출시분은 전부 패치 계열이다.\
공식 뉴스 색인에서 **창 안(05-10 ~ 09-20) 의 릴리스 발표를 전수로 세면 셋**이다.

| 날짜 | 릴리스 | 블로그가 적은 성격 |
|---|---|---|
| 2026-05-20 | **1.5.3** | "updates in DuckDB itself are limited bugfixes" — 대신 동봉 확장이 늘었다(Quack 클라이언트-서버 프로토콜이 core 확장으로) |
| 2026-06-17 | **1.5.4 (Variegata)** · **1.4.5 LTS (Andium)** | 같은 날 함께 배포 |
| 2026-07-22 | **1.5.5** | "bugfixes and performance improvements" — 1.5 라인의 여섯 번째 패치 |

**메이저는 하나도 없었다** — 창 안의 v2.0 관련 발표는 미리보기(08-17)와 알파(09-02) 둘 다 **출시가 아니다.**

그리고 프로젝트 바깥 소식 하나가 같은 창에 있다.\

⚠️ 블로그는 **라이선스·거버넌스·로드맵은 그대로**라고 못박았다 — "DuckDB, DuckLake, Quack, and all the other extensions will remain free and open source software under the MIT license under the stewardship of the non-profit DuckDB Foundation".\
원본 05편이 Neon·Databricks 인수를 적어 둔 것과 같은 종류의 사건이므로 적어 둔다 — **다만 이 발표만으로 무엇이 바뀐다고 쓸 근거는 없다.**

### 분산 SQL — CockroachDB v26.3 (2026-08-19) · YugabyteDB v2026.1 (2026-06-29)

원본 04편은 CockroachDB·TiDB·YugabyteDB **셋**을 "Spanner 를 특수 하드웨어 없이 오픈소스로" 라는 계보로 묶는다.\
셋을 각각 릴리스 색인으로 확인했다 — **창 안의 새 메이저는 둘**(CockroachDB v26.3 · YugabyteDB v2026.1)이고, **TiDB 만 패치뿐**이다.

| 제품 | 창 안(2026-05-10 ~ 09-20)에서 확인한 것 | 연 곳 |
|---|---|---|
| **CockroachDB** | **v26.3** — Innovation, GA **2026-08-19** | 릴리스 색인의 "Supported releases" 표(직전 메이저 v26.2 는 2026-04-27 로 창 밖) |
| **YugabyteDB** | **v2026.1 STS** — 최초 빌드 **2026-06-29**, 이후 패치 2026.1.0.1(07-22)·2026.1.1.0(08-13)·2026.1.1.1(08-18)·2026.1.1.2(09-10) | 릴리스 색인 표 + v2026.1 시리즈 릴리스 노트 |
| **TiDB** | **새 메이저 없음** — 창 안은 패치 두 건(**v8.5.7** 2026-07-09 · **v8.5.8** 2026-08-27)뿐 | GitHub releases 목록 |

CockroachDB 는 분기마다 메이저를 내되 두 종류를 번갈아 낸다 — 문서 표현으로 **Regular**("extended support windows for long-term stability")와 **Innovation**("shorter support windows but include all of the latest features").

> **Innovation 릴리스** — 지원 기간이 짧은 대신 최신 기능을 먼저 담는 계열. CockroachDB 문서는 이것을 **건너뛸 수 있는(optional)** 릴리스라고 적는다.\
> 예 — v26.3 문서: "can be skipped for CockroachDB Advanced and self-hosted clusters".

v26.3 에서 원본의 서술과 이어지는 항목은 두 가지다.

- **슈퍼 리전별 생존 목표(Survival Goal)가 정식(GA)이 됨** — 슈퍼 리전마다 "its own survival goal and zone configuration, independent of the database default". 04편이 다룬 "지리 분산에서 몇 개까지 죽어도 사는가"를 리전 단위로 따로 정하는 것이다.
- **PostgreSQL 18 호환** — 클라이언트에 PostgreSQL 18 로 보고하고 `pg_catalog` 스키마를 맞춘다. PostgreSQL 18 의 `pg_dump` 로 CockroachDB 스키마를 뽑을 수 있게 됐다.

그 밖에 DOMAIN 타입 지원(GA), 저장 프로시저 안의 DDL·DCL(GA), 그리고 AI 도구가 붙는 **CockroachDB MCP Server**(GA)가 들어갔다.\
⚠️ 같은 절의 「저장 프로시저 안의 **임시 테이블**」은 GA 가 아니라 **Preview** 다 — 문서의 Availability 칸 표기를 그대로 따른다.

**YugabyteDB v2026.1 (STS)** 은 2026-06-29 빌드가 최초다.\
릴리스 노트가 Highlights 로 꼽은 것 중 04편의 서술(PostgreSQL 호환 분산 SQL)과 곧장 이어지는 둘만 옮긴다.

- **즉시 복제(Instant database cloning) — GA** — "Clones are point-in-time copies created in seconds regardless of database size" — 생성 시점엔 원본과 스토리지를 공유하고 쓰기가 들어올 때만 갈라진다.
- **YSQL 테이블 상속 — GA** — `CREATE TABLE` 의 PostgreSQL `INHERITS` 절 지원. 04편이 말한 "PostgreSQL 호환"을 한 칸 더 넓힌 항목이다.

⚠️ **STS(표준 기간 지원) 계열이다** — 릴리스 색인이 적은 유지보수 종료는 2027-06-29, EOL 은 2027-12-29 다.\
LTS 는 여전히 v2025.2(2025-12-11)다.

**TiDB 는 v8.5 계열 이후의 새 메이저가 창 안에 없다.**\
GitHub releases 목록을 열어 센 결과, 창 안의 TiDB 릴리스는 **v8.5.7(2026-07-09)·v8.5.8(2026-08-27) 패치 두 건**뿐이다(v7.5.8 도 2026-09-17 에 나왔지만 이는 구 계열 패치다).\
목록에서 가장 늦은 메이저는 **v8.5.0(2024-12-19)**, `v9.0.0-beta.1` 은 **2025-03-31** 로 창 밖이다.\
PingCAP 문서도 v8.5 이후 버전명·시기를 "공개 로드맵에 확정되는 대로 게시한다"고만 적고 있다.

### 키값 — Valkey 9.1 (2026-05-19)

원본 05편은 **Redis 를 두 군데에서** 언급한다 — 기존 강자들이 벡터 검색을 흡수한 사례로 한 번(검색 절), 벡터 「확장(bolt-on)」 진영 표에서 한 번.\
그 갈래에서 창이 열리자마자 나온 것이 **Valkey 9.1.0** 이다(2026-05-19 — 창 시작 05-10 의 아흐레 뒤, **창 안이다**).

발표문이 머리기사로 꼽은 것 중 셋만 옮긴다.

- **데이터베이스 단위 ACL** — 전에는 ACL 규칙이 명령과 키만 가렸고 **어느 데이터베이스든 똑같이** 적용됐다. 9.1 부터 `ACL SETUSER ... db=0,1` 처럼 권한을 특정 DB 로 좁힐 수 있다.
- **Lua 를 모듈로 분리** — 스크립팅 엔진을 코어에서 떼어 냈다. 발표문의 이유는 보안 표면 축소와 "gives operators the option to disable Lua entirely if it is not required".
- **TLS 인증서 만료일을 `INFO` 로 노출** — 만료된 인증서로 인한 장애를 미리 잡으라는 것.

수치 하나는 **잰 조건과 함께** 옮긴다 — 발표문은 단일 서버 처리량을 **초당 210만 요청**이라 적으면서 조건을 같이 밝혔다: "using 512-byte payloads, 9 IO threads, and a pipeline depth of 10 commands".\
⚠️ 이것은 **프로젝트가 자기 대시보드에서 잰 값**이다 — 다른 조건의 비교치로 쓰면 안 된다.

## 원문이 「예정」이라 한 것은 어떻게 됐나

### ① "2030년 140억 달러" — 확인하지 못했다

원본 05편은 벡터 DB 시장을 두고 **"2025년 약 43억 달러로 추정되며 2030년 140억 달러로의 성장이 전망된다"**고 적었다.

이건 **전망이지 사실이 아니다.**\
그래서 그 뒤 실측치가 나왔는지 확인해 봤다.

**확인하지 못했다.**\
**1차 출처(프로젝트·벤더의 발표)에 해당하는 실측치를 찾지 못했다.**\
이 문서의 규칙(수치는 1차 출처의 값만, 잰 조건과 함께)에 걸리므로 **숫자를 옮기지 않는다.**

⚠️ 원본의 그 문장을 "2030년에 140억 달러가 된다"로 읽으면 안 된다.\
원본도 "전망된다"고 썼다.

### ② "벡터 검색은 독립 카테고리로 남을까, 모든 DB 의 기능으로 흡수될까"

원본 05편이 **열어놓은 논쟁**이다.\
넉 달 반으로는 결판나지 않는다 — 결론을 적지 않는다.

다만 이 창 안에서 **흡수 쪽 데이터포인트 하나**는 확인됐다.\
DuckDB v2.0 미리보기가 **유사도 검색용 `NEAREST` 조인**을 SQL 방언 추가 항목으로 올렸다(2026-08-17, 아직 미출시).\
"전용 엔진이 밀렸다"는 근거는 아니다 — 범용 엔진이 기능을 하나 더 얹었다는 사실이 전부다.

### ③ HTAP → zero-ETL·레이크하우스

원본이 "2025년 무렵 무게추가 옮겨갔다"고 적은 대목이다.\
이 창(05-10 ~ 09-20)에서 이 판단을 뒤집거나 굳히는 **1차 발표를 확인하지 못했다** — 위 「무엇을 조사했고 무엇을 조사하지 않았나」에 적은 아홉 제품의 릴리스·뉴스 색인 범위에서 그렇다.
