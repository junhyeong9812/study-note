# 오픈소스·웹 DB 시대 (1995~2010)

> 원본: `~/project/database-history/02-오픈소스-웹-시대.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-18).\
> 연도·인명·논문명·표준번호·코드는 원문 그대로다. 더 압축된 원문이 필요하면 원본 문서를 보면 된다.\
> 용어 블록의 「예:」, 「대가는 무엇인가」, 트레이드오프 표는 원문에 없는 보충 설명이다.

## 한눈에 — 쉽게 말하면

**오픈소스 DB = 회원비 수만 달러짜리 회원제 도서관만 있던 동네에, 무료 공공도서관이 생긴 것.**

- 1990년대 중반까지 "데이터베이스를 쓴다"는 말은 곧 "라이선스를 산다"는 뜻이었다.\
  회원비가 비싸서 동네 사람 대부분은 도서관 자체를 못 썼다.
- 그때 무료 도서관 셋이 차례로 문을 열었다.\
  빠르고 단순한 곳(MySQL), 규칙이 엄격하고 기능이 많은 곳(PostgreSQL), 아예 책 한 권을 집에 두는 방식(SQLite)이다.
- 그런데 사람이 너무 많이 몰렸다.\
  창구 하나로는 감당이 안 되니 **같은 책의 사본을 여러 분관에 두고**(복제), **자주 빌리는 책은 입구 진열대에 미리 꺼내 두고**(캐시), **창구 줄을 미리 만들어 두었다**(커넥션 풀).
- 이 15년의 이야기가 그것이다 — 값이 0이 되었고, 규모가 문제가 되었다.

```text
Linux      운영체제        공짜
   +
Apache     웹 서버         공짜
   +
MySQL      데이터베이스    공짜
   +
PHP/Perl   언어            공짜
   =
LAMP       동적 웹사이트 한 벌을 0원에 띄운다
```

이 도서관이 **똑같은 구조로** 2000년대 웹 인프라다.\
무료 회원증 = 오픈소스 라이선스(GPL), 분관 = 복제본(slave), 입구 진열대 = memcached 캐시, 창구 줄 = 커넥션 풀이다.\
지금도 MySQL/MariaDB·PostgreSQL·SQLite와 앞단 캐시·커넥션 풀은 전부 이 시기에 자리를 잡았다.

> **오픈소스(open source)** — 소스 코드를 공개하고, 누구나 쓰고 고치고 재배포할 수 있게 한 소프트웨어.\
> 예: MySQL은 2000년에 GPL로 바뀌면서 돈을 내지 않고도 상용 서비스에 쓸 수 있게 됐다.

> **GPL(GNU General Public License)** — 대표적인 오픈소스 라이선스. 쓰는 것은 자유지만, 고쳐서 배포할 때는 소스도 함께 공개해야 한다.\
> 예: MySQL 3.23 베타가 GPL로 바뀌자 라이선스 비용이라는 진입 장벽이 사라졌다.

## 시대 배경 — 그전에는 어땠나

1990년대 중반까지 데이터베이스 시장은 Oracle·IBM DB2·Microsoft SQL Server·Informix·Sybase 같은 고가의 상용 제품이 지배했다.\
라이선스 비용이 수만 달러에 달했기 때문에, 막 태동하던 웹 스타트업이나 개인 개발자에게 "데이터베이스를 쓴다"는 것은 곧 큰 비용을 의미했다.\
동시에 웹은 정적 HTML에서 동적 페이지로 빠르게 이동하고 있었다.\
게시판·방명록·쇼핑몰처럼 데이터를 저장하고 조회하는 애플리케이션 수요가 폭발했다.

> **정적 HTML / 동적 페이지** — 정적은 미리 만들어 둔 파일을 그대로 내려주는 것, 동적은 요청이 올 때마다 DB를 읽어 페이지를 만들어 내는 것.\
> 예: 방명록은 글이 올라올 때마다 내용이 달라지므로 동적이고, 그래서 DB가 필요하다.

이 공백을 메운 것이 오픈소스 데이터베이스였다. 핵심 동력은 두 가지다.

- 첫째, **비용 제로**다.\
  Linux·Apache·PHP와 함께 묶인 MySQL은 한 푼도 들이지 않고 동적 웹 사이트를 띄울 수 있게 했다.\
  이것이 1998년 명명된 **LAMP 스택**이며, 2000년대 웹 개발의 사실상 표준 조합이 되었다.
- 둘째, **설치와 운영의 단순함**이다.\
  MySQL은 빠르고 가볍고 배우기 쉬웠으며, SQLite는 아예 서버 프로세스조차 없앴다.

> **LAMP 스택** — Linux + Apache + MySQL + PHP/Perl 네 개를 묶어 부르는 이름. 1998년 12월 독일 잡지에서 처음 명명됐다.\
> 예: 이 넷을 깔면 서버 한 대로 동적 웹사이트를 띄울 수 있었고, 전부 무료였다.

2000년대 중반에 들어서면 또 다른 압력이 등장한다. **웹 스케일**이다.\
LiveJournal·Flickr·YouTube·Facebook 같은 서비스가 수백만 사용자를 받기 시작하면서, 단일 데이터베이스 서버 한 대로는 트래픽을 감당할 수 없게 됐다.\
데이터베이스의 관심사가 "어떻게 SQL을 실행하는가"에서 "어떻게 수십 대로 부하를 분산하는가"로 옮겨갔다.\
복제(replication)·캐싱(caching)·커넥션 풀(connection pool) 같은 운영 기술이 애플리케이션 아키텍처의 1급 구성요소가 되었다.

> **웹 스케일(web-scale)** — 사용자 수백만 명분의 트래픽을 24시간 받아 내야 하는 규모.\
> 예: 서버 한 대가 초당 수천 건을 받으면 CPU가 아니라 DB 연결 수부터 먼저 바닥난다.

연표를 세로로 내려 읽으면 이 시대의 뼈대가 보인다 — 연도는 전부 원문 그대로다.


## 무엇이 바뀌었나

### MySQL — "웹의 데이터베이스" (1995)

**무엇** — MySQL은 스웨덴의 Monty Widenius 등이 1995년에 만든 관계형 데이터베이스다.\
처음부터 **속도와 단순함**을 최우선 가치로 삼았다.\
복잡한 트랜잭션이나 학술적 완결성보다 "읽기가 많은 웹 워크로드에서 빠르게 동작할 것"을 지향했다.

**언제·왜 떴나** — 2000년 라이선스를 GPL로 바꾸면서 진입 장벽이 사라졌고, LAMP 스택의 'M'으로 자리 잡으며 사용량이 폭증했다.\
Facebook·YouTube·Twitter·Flickr 등 2000년대를 대표하는 웹 서비스 다수가 MySQL 위에 세워졌다.

**플러그형 스토리지 엔진** — MySQL의 독특한 설계는 SQL 처리 계층과 실제 저장 계층을 분리해, 테이블마다 다른 스토리지 엔진을 선택하게 한 것이다.\
이 구조가 뒤이은 MyISAM ↔ InnoDB 선택의 무대가 되었다.

> **스토리지 엔진(storage engine)** — 데이터를 실제로 디스크에 어떻게 넣고 꺼낼지를 담당하는 부품. SQL을 해석하는 부분과 분리돼 있다.\
> 예: 같은 `SELECT` 문이라도 테이블이 MyISAM이냐 InnoDB냐에 따라 잠금 방식과 복구 능력이 달라진다.

```sql
-- 같은 데이터베이스 안에서 테이블마다 엔진을 고를 수 있었다
CREATE TABLE article  (id INT, body TEXT)   ENGINE = MyISAM;  -- 읽기 위주
CREATE TABLE payment  (id INT, amount INT)   ENGINE = InnoDB;  -- 트랜잭션 필요
```

**왜 이게 나은가** — 워크로드마다 저장 방식을 갈아끼울 수 있으니, 게시글 테이블과 결제 테이블이 서로 다른 성질을 가질 수 있었다.

**대가는 무엇인가** — 한 DB 안에 성격이 다른 엔진이 섞이면, "이 테이블은 트랜잭션이 되나?"를 테이블마다 따져야 한다.\
실제로 MyISAM 테이블에 건 변경은 `ROLLBACK` 을 해도 되돌아오지 않는다 — 트랜잭션이 없는 엔진이기 때문이다. *(Claude 보강)*

### PostgreSQL — 학계의 정통을 잇다 (POSTGRES → 1996)

**무엇** — PostgreSQL의 뿌리는 1986년 Berkeley에서 Michael Stonebraker가 이끈 **POSTGRES** 연구 프로젝트다.\
1994년 대학원생 Andrew Yu와 Jolly Chen이 기존의 POSTQUEL 질의 언어를 **SQL**로 교체해 Postgres95를 만들었다.\
1996년 이름을 **PostgreSQL**로 바꾸면서 자원봉사 개발 그룹(PGDG)이 코드를 이어받았다.

**왜 중요한가** — MySQL이 속도를 택했다면, PostgreSQL은 **정합성과 확장성(extensibility)** 을 택했다.\
사용자 정의 타입·함수·연산자·인덱스 방식을 추가할 수 있는 확장형 아키텍처는 POSTGRES 시절부터 내려온 DNA였다.

> **확장성(extensibility)** — DB 자체를 고치지 않고도 새 타입·함수·인덱스 방식을 사용자가 덧붙일 수 있는 성질.\
> 예: 위치 데이터를 다루는 PostGIS는 PostgreSQL을 포크한 게 아니라 확장으로 얹은 것이다.

**MVCC (1998)** — PostgreSQL을 결정적으로 차별화한 기능이다.\
**다중 버전 동시성 제어**는 같은 행의 여러 버전을 유지함으로써, 읽기가 쓰기를 막지 않고 쓰기가 읽기를 막지 않게 한다("readers don't block writers").\
읽기에 락을 걸지 않고도 높은 동시성을 달성한다.

> **MVCC(다중 버전 동시성 제어)** — 같은 행의 옛 버전과 새 버전을 함께 보관해, 읽는 쪽은 옛 버전을, 쓰는 쪽은 새 버전을 보게 하는 방식.\
> 예: 누군가 잔액을 고치는 중에도 다른 트랜잭션은 "고치기 전 잔액"을 기다림 없이 읽는다.

```text
락 방식 (읽기가 쓰기를 기다린다)
  쓰기 트랜잭션 --잠금--> 행 100번
  읽기 트랜잭션 ......... 대기 ......... 대기 ......... 겨우 읽음

MVCC (읽기가 안 기다린다)
  쓰기 트랜잭션 --> 행 100번 [새 버전: 잔액 900]  (아직 커밋 전)
  읽기 트랜잭션 --> 행 100번 [옛 버전: 잔액 1000] 즉시 읽음
                    커밋되면 그 다음 읽기부터 새 버전이 보인다
```

```sql
-- PostgreSQL은 표준 SQL 트랜잭션을 일관되게 지원했다 (MVCC 기반)
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;  -- 이 사이 다른 트랜잭션은 '커밋 이전 버전'을 락 없이 읽는다
```

**대가는 무엇인가** — 옛 버전이 쌓이므로 주기적으로 청소해야 한다.\
PostgreSQL에서 `VACUUM` 이 필요한 이유가 이것이다. *(Claude 보강)*

### SQLite — 서버 없는 임베디드 DB (2000)

**무엇** — SQLite는 D. Richard Hipp이 2000년 미 해군 함정용 소프트웨어 프로젝트(General Dynamics 컨설팅 계약)를 위해 만든 데이터베이스다.\
함정의 밸브·배관 데이터를 다루는 임베디드 환경에서는 별도의 데이터베이스 서버를 띄우는 클라이언트-서버 방식이 부적합했다.\
이 제약이 SQLite의 설계 철학을 규정했다.

> **임베디드(embedded)** — 독립 제품이 아니라 다른 기계·프로그램 안에 박혀서 도는 형태.\
> 예: 안드로이드 폰 안의 앱이 연락처를 저장하는 데 쓰는 DB가 SQLite다.

**서버리스(serverless)** — 별도 서버 프로세스가 없다.\
데이터베이스 전체가 **단일 파일**이고, 애플리케이션이 라이브러리로 직접 링크해 그 파일을 읽고 쓴다.\
네트워크 프로토콜도, 설치도, 관리자도 필요 없다.

```text
서버형 DB (MySQL/PostgreSQL)                 SQLite (서버 없음)
+---------------------------------------+    +------------------------+
| 앱  --(TCP 연결)-->  DB 서버 프로세스 |    | 앱 (라이브러리로 링크) |
| DB 서버  -->  데이터 파일들           |    |     |  그냥 함수 호출  |
| 설치 / 포트 / 계정 / 관리자 필요      |    |     v                  |
+---------------------------------------+    | 데이터베이스 파일 1개  |
                                             +------------------------+
  여러 앱이 한 DB에 붙을 수 있다               설치도 포트도 관리자도 없다
```

왼쪽은 "DB라는 별도의 서비스에 접속"하고, 오른쪽은 "내 프로그램이 파일을 직접 연다".

**언제·왜 퍼졌나** — 설정 없이 동작하고 이식성이 뛰어나며 퍼블릭 도메인이라는 점 덕분에, 이후 안드로이드·iOS·브라우저·항공기 등 무수한 기기에 내장되었다.\
세계에서 가장 많이 배포된 데이터베이스 엔진이 되었다.\
서버 DB의 대체재가 아니라 `fopen()`의 대체재를 지향한 것이 핵심이었다.

> **퍼블릭 도메인(public domain)** — 저작권을 주장하지 않아 누구나 아무 조건 없이 쓸 수 있는 상태.\
> 예: SQLite는 GPL 같은 조건조차 없어서, 상용 기기에 넣을 때 법무 검토가 거의 필요 없다.

### 웹 스케일의 압박 — 복제·캐싱·커넥션 풀

단일 서버의 한계에 부딪힌 대형 웹 서비스들은 데이터베이스 **바깥에서** 확장 기법을 발전시켰다.

**읽기 복제 / master-slave 복제** — 웹 워크로드는 대개 쓰기보다 읽기가 압도적으로 많다.\
그래서 모든 쓰기는 한 대의 **master**가 전담하고, 데이터를 여러 **slave(복제본)** 로 복사한 뒤 읽기 요청을 복제본들에 분산했다(read scale-out).\
MySQL은 내장 복제 기능으로 이 패턴을 대중화했다.\
부수 효과로 복제본은 장애 대비(고가용성)와 백업 용도로도 쓰였다.

```text
                  +---------------+
      앱 서버 --> |   master DB   | <-- 쓰기(INSERT/UPDATE)
                  +-------+-------+
                          |  복제(replication) - 바이너리 로그 전송
          +---------------+---------------+
          |               |               |
          v               v               v
   +-----------+   +-----------+   +-----------+
   |  slave 1  |   |  slave 2  |   |  slave 3  |   <-- 읽기(SELECT) 분산
   +-----------+   +-----------+   +-----------+
```

그림 해설 (한 단계씩):

- 쓰기는 master 한 곳에만 간다 — 그래야 "정답"이 한 군데로 모인다.
- master는 무엇을 바꿨는지를 바이너리 로그에 적고, 그 로그를 slave들에게 흘려보낸다.
- 읽기는 slave 셋에 나눠 보낸다 — 읽기 처리량이 대략 대수만큼 늘어난다.
- 대가 — slave는 로그를 받아 적용하는 데 시간이 걸리므로, 방금 쓴 값을 바로 읽으면 옛 값이 보일 수 있다(복제 지연).

> **복제 지연(replication lag)** — master의 변경이 slave에 반영되기까지 걸리는 시간.\
> 예: 글을 쓰자마자 목록을 새로고침했는데 내 글이 안 보이는 현상이 이것이다.

> **고가용성(high availability)** — 장애가 나도 서비스가 계속 돌아가게 만드는 성질.\
> 예: master가 죽으면 slave 하나를 master로 승격시켜 서비스를 이어간다.

**memcached (2003)** — Brad Fitzpatrick이 LiveJournal의 부하를 줄이려 만든 **분산 메모리 객체 캐시**다.\
자주 조회되는 결과를 여러 서버의 RAM에 key-value로 올려두어, 같은 쿼리가 데이터베이스까지 내려가지 않게 막는다.\
"DB 앞단의 캐시 계층"이라는 패턴을 표준화했고, 이후 대규모 웹 아키텍처의 기본 구성요소가 되었다.

```text
캐시 없음                         memcached 앞단
+----------------------------+    +----------------------------+
| 요청 1000건                |    | 요청 1000건                |
|    |  전부 DB까지 내려간다 |    |    |                       |
|    v                       |    |    v                       |
| DB: 같은 SELECT 1000번     |    | memcached (RAM, key-value) |
+----------------------------+    |    |  없을 때 1번만        |
                                  |    v                       |
                                  | DB: 같은 SELECT 1번        |
                                  +----------------------------+
  인기 글 하나가 DB를 태운다        같은 질의가 DB까지 안 내려간다
```

캐시의 대가는 "언제 지우나"다 — 원본이 바뀌었는데 캐시가 옛 값을 들고 있으면 사용자가 옛 화면을 본다.

> **캐시(cache)** — 느린 곳에서 가져온 결과를 빠른 곳에 잠시 보관해 두고 재사용하는 것.\
> 예: 메인 화면의 인기 글 목록을 60초 동안 RAM에 두면, 그 60초 동안 DB는 그 질의를 한 번만 받는다.

**커넥션 풀(connection pool)** — 웹 요청마다 DB 연결을 새로 맺고 끊는 비용은 컸다.\
미리 일정 수의 연결을 만들어 두고 재사용하는 커넥션 풀이 표준이 되었다.\
연결 수립 오버헤드를 없애고 동시 연결 수를 제어했다.

> **커넥션 풀(connection pool)** — 미리 만들어 둔 DB 연결 몇 개를 돌려 쓰는 장치.\
> 예: 풀 크기를 20으로 두면, 요청이 500개 몰려도 DB가 동시에 받는 연결은 20개로 묶인다.

### 스토리지 엔진 전쟁 — InnoDB vs MyISAM

MySQL의 플러그형 구조에서 가장 중요한 선택은 **MyISAM**(1999)과 **InnoDB**(2002, Innobase) 사이였다.\
이 둘의 대비는 2000년대 MySQL 운영의 핵심 의사결정이었다.

| | **MyISAM** | **InnoDB** |
|---|---|---|
| 트랜잭션 | 없음 | **ACID 트랜잭션** 지원 |
| 락 단위 | 테이블 락 | **행(row) 락** |
| 외래키 | 미지원 | 지원 |
| 동시성 모델 | 단순 | **MVCC** |
| 크래시 복구 | 약함 | 리두 로그 기반 복구 |
| 강점 | 읽기 위주·단순 조회에서 빠름 | 동시 쓰기·정합성 |

표에서 가장 몸으로 와닿는 줄은 "락 단위"다. 그림으로 보면 이렇다.

```text
MyISAM — 테이블 락                     InnoDB — 행 락
+---------------------------------+    +---------------------------+
| 쓰기 1건이 테이블 전체를 잠근다 |    | 쓰기 1건이 그 행만 잠근다 |
| +------------------------+      |    | +------+------+------+    |
| | article 테이블 (잠김)  |      |    | | 행1  | 행2  | 행3  |    |
| +------------------------+      |    | | 잠김 | 진행 | 진행 |    |
| 다른 쓰기 3건은 줄을 선다       |    | +------+------+------+    |
+---------------------------------+    +---------------------------+
  읽기 위주라면 문제 없다                동시 쓰기가 늘어도 버틴다
```

왼쪽은 한 명이 쓸 때 나머지가 전부 멈추고, 오른쪽은 서로 다른 행이면 동시에 쓴다.

> **테이블 락 / 행 락** — 잠그는 범위의 크기 차이. 테이블 락은 표 전체를, 행 락은 건드리는 행만 잠근다.\
> 예: 게시글 10만 건이 든 표에서 1건을 수정할 때, 테이블 락이면 나머지 9만9999건에 대한 쓰기도 함께 막힌다.

> **리두 로그(redo log)** — 변경 내용을 데이터 파일보다 먼저 순차 기록해 두는 로그. 장애 후 그 로그를 다시 적용해 복구한다.\
> 예: 커밋 직후 전원이 나가도, 재시작할 때 리두 로그를 읽어 커밋된 변경을 되살린다.

> **외래키(foreign key)** — 다른 표의 행을 가리키는 열에 "가리키는 대상이 실제로 있어야 한다"는 규칙을 건 것.\
> 예: 존재하지 않는 회원 번호로 주문 행을 넣으려 하면 DB가 거절한다.

**왜 처음엔 MyISAM이 기본이었나** — 초기 웹은 읽기 중심이었고, 트랜잭션 없는 단순 구조가 더 빨랐다.\
테이블 락도 부하가 낮을 때는 문제가 되지 않았다.

**왜 InnoDB로 넘어갔나** — 서비스가 커지며 동시 쓰기가 늘자, 테이블 락은 병목이 됐고 트랜잭션·외래키 부재는 데이터 정합성 위험이 됐다.\
행 단위 락과 MVCC를 갖춘 InnoDB가 동시성 환경에서 압도했다.\
2005년 Oracle이 Innobase를 인수해 한때 긴장이 있었지만, 결국 2010년 MySQL 5.5에서 InnoDB가 **기본 엔진**으로 승격되며 전환이 완성됐다.

## 왜 그렇게 갔나 — 남은 선택지와 트레이드오프

| 선택 | 얻은 것 | 내준 것 |
|---|---|---|
| 상용 라이선스 → 오픈소스(GPL) | 비용 0, 누구나 창업 가능 | 벤더 보증·지원이 없다, 문제는 스스로 푼다 |
| 기능 완결성 → 속도·단순함(MySQL) | 빠른 채택, 배우기 쉬움 | 초기 기본 엔진(MyISAM)에는 트랜잭션·외래키가 없었다 |
| 속도 → 정합성·확장성(PostgreSQL) | 표준 준수, 확장으로 기능 증식 | 초기엔 느리고 무겁다는 평을 오래 들었다 |
| 서버형 → 서버리스 단일 파일(SQLite) | 설치·관리 0, 어디에나 내장 | 여러 앱이 동시에 쓰기에는 부적합하다 |
| 단일 서버 → master-slave 복제 | 읽기 처리량이 대수만큼 증가 | 복제 지연 — 방금 쓴 값이 안 보일 수 있다 |
| DB 직접 조회 → 앞단 캐시 | DB 부하 급감, 응답 빨라짐 | 캐시 무효화 — 옛 값이 보이는 구간이 생긴다 |
| 매 요청 연결 → 커넥션 풀 | 연결 비용 제거, 동시 연결 통제 | 풀이 마르면 요청이 줄을 서서 대기한다 |
| 테이블 락(MyISAM) → 행 락(InnoDB) | 동시 쓰기 확장 | 락 관리·MVCC 버전 유지라는 추가 비용 |

- 쓰기까지 여러 대로 나누는 선택지(샤딩)는 이 시대에도 쓰였지만, 데이터베이스가 아니라 애플리케이션이 떠맡아야 했다.\
  그 부담이 다음 시대(NoSQL)의 출발점이 된다.
- PostgreSQL이 아니라 MySQL이 웹의 기본값이 된 것은 속도·가벼움과 GPL 전환, 그리고 LAMP라는 묶음이 함께 작용한 결과였다.

## 남긴 것 — 오늘 우리가 쓰는 것

이 15년은 데이터베이스의 무게중심을 **상용에서 오픈소스로, 단일 서버에서 분산 운영으로** 옮긴 시기다.

- **데이터베이스의 민주화** — 무료 오픈소스 DB와 LAMP 스택은 누구나 자본 없이 동적 웹 서비스를 만들 수 있게 했다.\
  2000년대 웹 창업 붐의 인프라적 토대였으며, 오늘날 MySQL/MariaDB와 PostgreSQL이 누리는 광범위한 채택은 이 시기에 뿌리내렸다.
- **두 갈래의 철학** — "빠르고 단순한" MySQL과 "정합적이고 확장 가능한" PostgreSQL이라는 대비는 지금까지 이어지는 선택지를 정립했다.\
  MVCC·트랜잭션·확장성 같은 PostgreSQL의 정통적 가치들은 이후 MySQL(InnoDB)에도 흡수되며 업계 표준이 되었다.
- **운영 기술의 부상** — 복제·캐싱·커넥션 풀·스토리지 엔진 선택은 "DB를 쓴다"는 행위를 단순 설치에서 **아키텍처 설계**로 끌어올렸다.\
  이 시기 굳어진 master-slave 복제와 캐시 계층 패턴은 2010년 이후 NoSQL·분산 데이터베이스 시대(샤딩·최종 일관성)로 가는 직접적인 디딤돌이 되었다.
- **임베디드라는 제3의 길** — SQLite는 "데이터베이스 = 서버"라는 등식을 깨고, 단일 파일 라이브러리라는 형태를 보편화했다.\
  서버 DB와 경쟁하지 않으면서도 전 세계에서 가장 많이 배포된 DB 엔진이 되었다.

오늘 우리가 실제로 만지는 것들로 옮기면 이렇다 — 아래 네 줄은 원문에 없는 보충이다. *(Claude 보강)*

- 애플리케이션 설정의 `maxPoolSize` 는 커넥션 풀, `readOnly` 데이터소스 분리는 master-slave 복제의 후손이다.
- Redis를 DB 앞에 두는 관행은 memcached가 세운 "앞단 캐시 계층" 패턴 그대로다.
- `ENGINE=InnoDB` 가 오늘 기본값인 것은 2010년 MySQL 5.5의 결정이다.
- 안드로이드 앱의 로컬 저장소, 브라우저 내장 DB가 SQLite인 것도 이 시기 설계의 결과다.

## 용어 풀이

- **오픈소스(open source)** — 소스를 공개하고 누구나 쓰고 고치고 재배포할 수 있게 한 소프트웨어.
- **GPL** — 대표적 오픈소스 라이선스. 고쳐서 배포하면 소스도 공개해야 한다.
- **퍼블릭 도메인(public domain)** — 저작권을 주장하지 않아 조건 없이 쓸 수 있는 상태. SQLite가 이쪽이다.
- **LAMP 스택** — Linux + Apache + MySQL + PHP/Perl. 1998년 12월 명명.
- **정적 HTML / 동적 페이지** — 미리 만든 파일을 주는 것 / 요청마다 DB를 읽어 만드는 것.
- **웹 스케일(web-scale)** — 수백만 사용자의 트래픽을 24시간 감당해야 하는 규모.
- **스토리지 엔진(storage engine)** — 데이터를 디스크에 넣고 꺼내는 일을 담당하는 교체 가능한 부품.
- **MyISAM** — MySQL 초기 기본 엔진(1999). 트랜잭션 없음, 테이블 락, 읽기에 빠름.
- **InnoDB** — 2002년 통합된 엔진. ACID 트랜잭션·행 락·MVCC·리두 로그 복구. 2010년부터 기본.
- **테이블 락 / 행 락** — 잠그는 범위가 표 전체냐, 건드리는 행 하나냐의 차이.
- **MVCC(다중 버전 동시성 제어)** — 같은 행의 여러 버전을 두어 읽기와 쓰기가 서로를 막지 않게 하는 방식.
- **리두 로그(redo log)** — 변경을 먼저 순차 기록해 두고 장애 후 재적용해 복구하는 로그.
- **외래키(foreign key)** — 가리키는 대상 행이 실제로 존재해야 한다는 제약.
- **확장성(extensibility)** — DB 본체를 고치지 않고 타입·함수·인덱스를 덧붙일 수 있는 성질.
- **복제(replication)** — master의 변경을 slave로 흘려보내 같은 데이터를 여러 대에 두는 것.
- **master / slave** — 쓰기를 전담하는 원본 / 읽기를 나눠 받는 복제본.
- **복제 지연(replication lag)** — 변경이 복제본에 도달하기까지의 시간차.
- **read scale-out** — 읽기 요청을 복제본 여러 대로 분산해 처리량을 늘리는 것.
- **고가용성(high availability)** — 장애가 나도 서비스가 이어지게 만드는 성질.
- **캐시(cache)** — 느린 곳의 결과를 빠른 곳에 잠시 두고 재사용하는 것.
- **memcached** — 2003년 공개된 분산 메모리 key-value 캐시. DB 앞단 캐시 계층의 표준을 세웠다.
- **커넥션 풀(connection pool)** — 미리 만든 DB 연결을 돌려 써서 연결 비용을 없애는 장치.
- **서버리스 / 임베디드** — 별도 DB 서버 프로세스 없이, 앱에 라이브러리로 박혀 파일을 직접 읽고 쓰는 형태.
- **PGDG** — PostgreSQL Global Development Group. 1996년부터 코드를 이어받은 자원봉사 개발 그룹.
- **POSTQUEL** — POSTGRES가 SQL 이전에 쓰던 자체 질의 언어.
