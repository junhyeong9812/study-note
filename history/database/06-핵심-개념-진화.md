# DB 핵심 개념의 진화 (개념사)

> 원본: `~/project/database-history/06-핵심-개념-진화.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-18).\
> 연도·인명·논문명·표준번호·코드는 원문 그대로다.\
> 용어 블록의 「예:」, 「대가는 무엇인가」, 트레이드오프 표는 원문에 없는 보충 설명이다.

## 한눈에 — 쉽게 말하면

**개념사 = 제품이 아니라 "부품의 역사".**

- 앞의 01~05편이 자동차 회사들의 역사라면, 이 편은 **엔진·브레이크·서스펜션의 역사**다.\
  Oracle이나 MongoDB가 아니라, 그 안에 공통으로 들어 있는 장치들이 언제 왜 만들어졌나를 본다.
- 예를 들어 "커밋했으면 정전이 나도 안 날아간다"는 약속.\
  이것은 제품 기능이 아니라 WAL이라는 부품이 하는 일이고, 1992년에 표준이 정해졌다.
- 부품의 역사는 딱 두 토막으로 갈린다.\
  **한 대 안에서 옳게 하기**(1972~1992) → **여러 대로 흩뿌렸을 때 무엇을 포기할지 정하기**(1996~2014).
- 그리고 오늘의 분산 DB는 이 두 토막의 부품을 다시 조립한 것이다.

```text
     [ 1972 ~ 1992 ]                    [ 1996 ~ 2014 ]
   한 대에서의 정확성                  여러 대에서의 타협
+------------------------+          +------------------------+
| B-tree   (1972)        |          | LSM-tree (1996)        |
| MVCC     (1978·1983)   |   -->    | Paxos    (1998)        |
| ACID     (1981·1983)   |          | CAP      (2000·2002)   |
| WAL/ARIES(1992)        |          | BASE     (2008)        |
| 격리수준 (1992·1995)   |          | PACELC   (2012)        |
+------------------------+          | Raft     (2014)        |
 질문: "고장과 동시성에도            +------------------------+
  어떻게 옳은가"                     질문: "흩뿌렸을 때 무엇을 포기하나"
```

이 두 칸이 **똑같은 구조로** 오늘날 모든 DB의 부품 목록이다.\
CockroachDB 한 대 안에도 왼쪽 칸(MVCC·WAL)과 오른쪽 칸(Raft)이 같이 들어 있다.

> **개념사** — 제품이 아니라 그 제품들이 공유하는 이론과 추상의 계보.\
> 예: "MySQL의 역사"가 아니라 "MVCC라는 아이디어가 어디서 나와 어디까지 갔나"를 따라가는 것.

> **트랜잭션(transaction)** — 여러 개의 읽기·쓰기를 "전부 되거나 전부 안 되거나" 한 덩어리로 묶은 것.\
> 예: 계좌 A에서 빼고 B에 넣는 두 작업을 한 덩어리로 묶어, 중간에 죽어도 돈이 사라지지 않게 한다.

## 시대 배경 — 그전에는 어땠나

데이터베이스 개념사는 하나의 큰 압력으로 추동되었다 — **규모(scale)**.

1970~80년대의 핵심 질문은 이랬다.\
"한 대의 기계 안에서, 동시에 들어오는 트랜잭션과 갑작스러운 고장에도 데이터를 어떻게 올바르게 지킬 것인가."\
이 시기에 트랜잭션(ACID)·격리수준·MVCC·WAL 같은 **단일 노드 정확성**의 개념들이 정립됐다.

2000년대 들어 웹 서비스가 단일 서버의 용량을 넘어서자 질문이 바뀌었다.\
"수백 대로 데이터를 흩뿌리고 복제했을 때, 일관성과 가용성을 *동시에* 가질 수 있는가."\
답은 "없다"였고(CAP), 그 한계를 다루는 개념들 — BASE·복제·파티셔닝·합의 — 이 뒤따랐다.

즉 개념사는 **"한 대에서의 정확성" → "여러 대에서의 타협"**으로 흐른다.\
아래 표가 그 골격이다.

| 연도 | 개념 | 정립 문헌 | 해결한 문제 |
|------|------|-----------|-------------|
| 1972 | B-tree | Bayer & McCreight | 디스크 블록 단위의 정렬 인덱스 |
| 1978 | MVCC(착상) | Reed (MIT 박사논문) | 읽기-쓰기 충돌 제거 |
| 1981 | 트랜잭션 개념 | Gray (VLDB) | 원자성·일관성·내구성의 정식화 |
| 1983 | **ACID**(명명) | Härder & Reuter | 트랜잭션 4속성에 이름 부여 |
| 1983 | MVCC(이론) | Bernstein & Goodman | 다중버전 직렬성의 형식 이론 |
| 1992 | ARIES/WAL | Mohan 외 | 로그 기반 충돌 복구의 표준화 |
| 1995 | 격리수준 비판 / SI | Berenson 외 | ANSI 정의의 모호성·스냅샷 격리 |
| 1996 | LSM-tree | O'Neil 외 | 쓰기 집약 워크로드의 인덱싱 |
| 1998 | **Paxos** | Lamport | 비신뢰 네트워크에서의 합의 |
| 2000 | **CAP**(추측) | Brewer (PODC) | 분산 시스템의 본질적 타협 |
| 2002 | CAP(증명) | Gilbert & Lynch | CAP을 정리로 격상 |
| 2007 | Dynamo | DeCandia 외 | 샤딩·복제·결과적 일관성의 종합 |
| 2008 | **BASE** | Pritchett | ACID의 대안적 설계 철학 |
| 2012 | **PACELC** | Abadi | CAP이 빠뜨린 지연-일관성 축 |
| 2014 | **Raft** | Ongaro & Ousterhout | 이해 가능한 합의 알고리즘 |

이 문서는 corpus의 **데이터 정합성**·**일관성 모델** 문서와 이어지는 이론 축이다.\
정합성·일관성 문서가 "어떤 보장을 사용자에게 약속하는가"를 다룬다면, 이 문서는 "그 보장을 가능하게(또는 불가능하게) 한 개념 장치들"의 역사를 따라간다.

## 무엇이 바뀌었나

### 1. 트랜잭션과 ACID — 그리고 BASE

#### ACID: 트랜잭션 정확성의 4속성 (1981 정식화 → 1983 명명)

**언제 나오나** — 여러 사용자가 동시에 쓰는데 서버가 언제든 죽을 수 있을 때.

트랜잭션이라는 추상은 짐 그레이(Jim Gray)가 1981년 VLDB 초청 논문 *The Transaction Concept: Virtues and Limitations*에서 정식화했다.\
그는 트랜잭션을 "상태의 변환(transformation of state)"으로 정의하고 세 속성을 들었다 — **원자성(Atomicity, 전부 아니면 전무)**·**내구성(Durability, 고장 후에도 효과 보존)**·**일관성(Consistency, 올바른 변환)**.\
흥미롭게도 그는 이를 *계약법*에 비유했다 — 두 당사자가 구속력 있는 합의에 이르는 과정.

여기에 **격리성(Isolation)**을 더하고 네 속성의 머리글자로 **ACID**라는 이름을 붙인 것은 테오 헤르더(Theo Härder)와 안드레아스 로이터(Andreas Reuter)의 1983년 논문 *Principles of Transaction-Oriented Database Recovery* (ACM Computing Surveys 15(4))이다.\
이 논문은 복구 기법을 *구현이 아니라 개념* 차원에서 기술할 용어 틀을 제공했고, 그 핵심 산물이 ACID라는 약어였다.

```text
A  원자성  — 커밋 or 롤백, 중간 상태 없음
C  일관성  — 제약조건을 만족하는 상태→상태 변환
I  격리성  — 동시 트랜잭션이 서로를 간섭하지 않음 (강도는 §3 격리수준)
D  내구성  — 커밋되면 고장에도 살아남음 (실현은 §9 WAL)
```

- **언제·왜**: 다중 사용자 RDBMS(System R, INGRES)가 등장하면서 "동시 접근 + 고장"이라는 두 위협을 한 묶음으로 다룰 어휘가 필요했다.
- **무엇을 해결**: 개발자가 복잡한 동시성·복구 메커니즘을 몰라도, "이 작업 묶음은 ACID하다"는 한마디로 정확성을 보장받게 했다.\
  ACID는 이후 모든 RDBMS의 기본 계약(default contract)이 된다.

> **원자성(atomicity)** — 한 덩어리가 전부 반영되거나 전부 취소되지, 절반만 남지 않는다는 성질.\
> 예: 이체 중 정전이 나도 "출금만 되고 입금은 안 된" 상태는 남지 않는다.

> **내구성(durability)** — 커밋했다고 답한 순간부터는 고장이 나도 그 결과가 살아남는다는 보장.\
> 예: 주문 완료 화면을 본 뒤 서버가 죽어도 그 주문은 남아 있다.

#### BASE: 규모를 위해 일관성을 양보한다 (2008)

**언제 나오나** — 수백 대에 흩뿌린 상태에서 매 요청마다 전원 동의를 기다리기엔 너무 느릴 때.

2000년대 대규모 웹 서비스는 ACID의 강한 일관성이 수평 확장의 병목임을 깨달았다.\
댄 프리쳇(Dan Pritchett)은 2008년 ACM Queue 논문 *BASE: An Acid Alternative*에서 ACID의 대척점에 있는 설계 철학을 제시했다.\
**BA**sically Available(기본적 가용), **S**oft state(연성 상태), **E**ventually consistent(결과적 일관)이다.

```text
 [ ACID — 비관적 ]                     [ BASE — 낙관적 ]
+-------------------------------+      +------------------------------+
| 쓰기 → 제약·격리 검사 → 응답  |      | 쓰기 → 즉시 응답 → 나중 전파 |
| 통과 못 하면 통째로 되돌림    |      | 빠르고 잘 죽지 않음          |
| 느리지만 언제나 정확          |      | 잠깐 옛 값을 볼 수 있음      |
+-------------------------------+      +------------------------------+
 매 연산 끝에 일관성을 확인한다         일관성이 잠시 "흔들리는" 것을 허용
```

이 대비의 결론 — 두 철학의 차이는 "언제 일관성을 확인하느냐"의 시점 차이다.

- **ACID는 비관적**: 매 연산 끝에서 일관성을 강제한다.
- **BASE는 낙관적**: 일관성이 잠시 "흔들리는(in flux)" 상태를 받아들이는 대신, 가용성과 확장성을 얻는다.
- **무엇을 해결**: 부하를 다수 컴포넌트로 분산할 때 분산 트랜잭션(2PC)이 가용성을 떨어뜨리는 문제.\
  연산을 분리(decouple)해 순차 처리함으로써 가용성과 규모를 확보하고, 그 대가로 일관성을 양보한다.

ACID↔BASE는 양자택일이 아니라 **스펙트럼**이며, 이 스펙트럼이 왜 존재하는지를 이론적으로 설명한 것이 다음의 CAP이다.

> **가용성(availability)** — 요청을 보내면 (옛 값이라도) 답이 돌아온다는 성질.\
> 예: 네트워크가 끊긴 지점에서도 잔액 조회가 에러 없이 답을 준다.

### 2. CAP과 PACELC — 분산의 본질적 타협

#### CAP 정리 (2000 추측 → 2002 증명)

**언제 나오나** — 노드 사이의 네트워크가 끊겼을 때 무엇을 할지 정해야 할 때.

에릭 브루어(Eric Brewer)는 2000년 PODC 기조연설에서 *추측*을 제시했다.\
분산 시스템은 **일관성(Consistency)**·**가용성(Availability)**·**분단 내성(Partition tolerance)** 셋 중 둘만 동시에 보장할 수 있다는 것이다.\
2002년 세스 길버트(Seth Gilbert)와 낸시 린치(Nancy Lynch)가 *Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services* (ACM SIGACT News)에서 이를 형식적으로 증명해 **정리(theorem)**로 격상시켰다.

```text
네트워크 분단 발생?
   │
   ├─ 아니오(평시) ──▶ 양쪽 노드 모두
   │                    정상 응답
   │
   └─ 예 ──▶ 분단 시 무엇을 포기?
              │
              ├─ 가용성 포기 → CP ──▶ 응답 거부/대기
              │                        일관성 유지
              │                        (예: HBase, etcd)
              │
              └─ 일관성 포기 → AP ──▶ 오래된 값이라도 응답
                                       가용성 유지
                                       (예: Dynamo, Cassandra)
```

그림 해설 — 한 단계씩.

- 평시에는 셋 다 문제가 없다.\
  CAP이 말하는 선택은 오직 분단이 일어난 순간에만 강요된다.
- 분단이 나면 둘 중 하나다.\
  "확실하지 않으니 답하지 않는다"(CP)이거나 "옛 값이라도 답한다"(AP)이거나.

핵심 통찰: 네트워크 분단(partition)은 분산 시스템에서 *선택이 아니라 필연*이다.\
따라서 실질적 선택지는 "분단이 일어났을 때 **일관성(CP)**을 지킬 것인가, **가용성(AP)**을 지킬 것인가"로 좁혀진다.

- **무엇을 해결**: NoSQL 운동(2000년대 후반)에 이론적 정당성을 부여했다.\
  "왜 Cassandra는 강한 일관성을 안 주는가"에 대한 답이 CAP이었다.\
  BASE는 곧 "AP 진영의 설계 철학"으로 읽을 수 있다.

> **네트워크 분단(partition)** — 노드들 사이의 통신이 끊겨 서로 연락이 안 되는 상태.\
> 예: 서울 데이터센터와 도쿄 데이터센터를 잇는 회선이 끊겨, 양쪽이 상대가 죽었는지 알 수 없게 된 것.

#### PACELC — CAP이 빠뜨린 절반 (2012)

**언제 나오나** — 분단이 없는 평상시에도 "얼마나 기다릴 것인가"를 정해야 할 때.

다니엘 아바디(Daniel Abadi)는 2012년 IEEE Computer 논문 *Consistency Tradeoffs in Modern Distributed Database System Design: CAP is Only Part of the Story*에서 CAP의 맹점을 지적했다.\
CAP은 **분단이 있을 때**만 말한다.\
그러나 분단이 없는 평시에도 시스템은 매 요청마다 **지연(Latency) vs 일관성(Consistency)** 사이에서 선택한다.\
강한 일관성을 위해 여러 복제본의 동기 응답을 기다릴수록 지연이 커지기 때문이다.

> **PACELC**: **if P**artition → **A** or **C**, **E**lse → **L**atency or **C**onsistency

```text
 CAP 이 말하는 구간  PACELC 이 더한 구간
 분단 발생           평시 (분단이 없을 때)
+-------------+      +---------------------+
| A 를 택하나 |      | L(저지연) 을 택하나 |
| C 를 택하나 |      | C(일관성) 를 택하나 |
+-------------+      +---------------------+
 Dynamo 계열 = PA    Dynamo 계열 = EL
 전통 RDBMS  = PC    전통 RDBMS  = EC
```

이 대비의 결론 — 일관성 타협은 장애 상황만의 문제가 아니라, **평상시 매 요청의 문제**다.

- **무엇을 해결**: "분단도 없는데 왜 어떤 DB는 느리고 어떤 DB는 stale을 반환하나"를 설명한다.\
  예컨대 Dynamo 계열은 **PA/EL**(분단 시 가용성, 평시 저지연), 전통 RDBMS는 **PC/EC**로 분류된다.\
  CAP의 단일 축을 *2축*으로 확장해, 일관성 타협이 장애 상황만의 문제가 아님을 드러냈다.

> **stale(오래된) 읽기** — 최신 값이 아니라 조금 전의 값을 읽는 것.\
> 예: 방금 올린 프로필 사진이 새로고침하면 옛 사진으로 보이는 현상.

### 3. 격리수준 — ANSI의 모호함에서 스냅샷 격리까지

#### ANSI SQL 격리수준과 그 비판 (1992 표준 → 1995 비판)

**언제 나오나** — 완전 격리는 너무 느려서, 얼마만큼 양보할지 눈금을 정해야 할 때.

ACID의 I(격리성)는 "완전 격리(직렬성)"가 비싸기 때문에 **수준(level)**으로 약화될 수 있다.\
ANSI SQL-92(ISO/IEC 9075:1992)는 세 가지 **현상(phenomena)**의 허용 여부로 네 격리수준을 정의했다.\
현상은 Dirty Read, Non-repeatable Read, Phantom이고, 수준은 Read Uncommitted / Read Committed / Repeatable Read / Serializable이다.

1995년 베렌슨·번스타인·그레이·멜튼·오닐·오닐의 SIGMOD 논문 *A Critique of ANSI SQL Isolation Levels*는 이 정의가 **모호하다**는 점을 폭로했다.\
현상을 좁게 해석하면(strict) 락 구현이 배제되고, 넓게 해석하면(broad) 의도와 달라진다.\
논문은 정의를 엄밀히 다듬고 새 현상들을 추가했으며(총 8개 현상·6개 수준), 무엇보다 다중버전에 기반한 중요한 격리 타입 — **스냅샷 격리(Snapshot Isolation, SI)** — 를 정의했다.

> **Dirty Read(더티 리드)** — 아직 커밋되지 않은 남의 변경을 읽어 버리는 것.\
> 예: 상대가 입금했다가 취소할 이체를 중간에 읽어 잔액을 잘못 판단한다.

> **Phantom(팬텀)** — 같은 조건으로 두 번 조회했는데 두 번째에 없던 행이 나타나는 것.\
> 예: "재고 0인 상품"을 두 번 세는 사이 새 상품이 끼어들어 개수가 달라진다.

#### 스냅샷 격리와 write skew

**언제 나오나** — 읽기를 빠르게 하려고 "시작 시점의 사진"을 보게 할 때.

스냅샷 격리에서 트랜잭션은 *시작 시점의 일관된 스냅샷*을 읽고, 커밋 시 **First-Committer-Wins** 규칙으로 쓰기-쓰기 충돌만 막는다.\
읽기는 쓰기를 막지 않고(읽기-쓰기 충돌 없음), 그래서 매우 빠르다 — 이것이 MVCC와 결합해 현대 DB의 사실상 표준이 됐다.

그러나 SI는 직렬성(serializable)이 *아니다*.\
같은 1995 논문이 지적한 대표 이상현상이 **write skew(쓰기 편향)**다.\
두 트랜잭션이 *겹치지 않는 행*을 쓰지만 *서로의 읽기 집합에 의존*할 때, 각자는 일관된 스냅샷을 보고 커밋하지만 결과는 불변식을 깬다.

```text
불변식: 의사 중 최소 1명은 당직(on-call)이어야 한다. (현재 Alice·Bob 2명 당직)

T1: "Bob이 당직이니 나(Alice)는 빠진다" → Alice off
T2: "Alice가 당직이니 나(Bob)는 빠진다" → Bob off
  └ 둘 다 시작 스냅샷에선 상대가 당직. 쓰는 행도 다름(각자 자기 행).
     SI는 충돌을 못 보고 둘 다 커밋 → 당직 0명. 불변식 붕괴.
```

그림 해설 — 두 트랜잭션은 각자 자기 행만 고쳤으므로 "쓰기끼리의 충돌"은 없다.\
문제는 둘 다 **상대가 아직 당직이라는 옛 사진**을 보고 판단했다는 데 있다.\
쓰기 충돌만 검사하는 SI는 이 상황을 볼 수 없다.

> **불변식(invariant)** — 어떤 일이 벌어져도 항상 참이어야 하는 규칙.\
> 예: "당직 의사는 최소 1명", "계좌 잔액은 음수가 아니다".

> **write skew(쓰기 편향)** — 각자 다른 행을 고쳤는데도, 서로의 옛 읽기에 기대어 판단한 탓에 전체 규칙이 깨지는 이상현상.\
> 예: 위의 당직 예에서 둘 다 빠져 당직이 0명이 되는 것.

- **무엇을 해결/남긴 문제**: SI는 격리 비용을 극적으로 낮췄지만 write skew를 남겼다.\
  이를 다시 막기 위해 PostgreSQL의 **Serializable Snapshot Isolation(SSI, 2008 Cahill 외)** 같은 후속 연구가 이어진다.\
  격리수준의 역사는 "정확성을 얼마나 양보하면 얼마나 빨라지는가"의 눈금을 정교화해 온 역사다.

### 4. MVCC — 읽기와 쓰기를 떼어놓다

**언제 나오나** — 읽는 사람과 쓰는 사람이 서로를 기다리느라 멈추는 것을 없애고 싶을 때.

다중버전 동시성 제어(Multiversion Concurrency Control)는 데이터의 **여러 버전**을 보관해, 쓰기가 이전 버전을 덮어쓰는 대신 *새 버전을 추가*하게 한다.\
그러면 읽는 트랜잭션은 자신에게 보이는 과거 버전을 읽고, 쓰는 트랜잭션은 새 버전을 만든다.\
**읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않는다.**

- **착상(1978)**: 데이비드 리드(David P. Reed)의 MIT 박사논문 *Naming and Synchronization in a Decentralized Computer System*이 다중버전 아이디어를 처음 명확히 기술했다.
- **이론화(1983)**: 필립 번스타인(Philip Bernstein)과 네이선 굿맨(Nathan Goodman)의 *Multiversion Concurrency Control — Theory and Algorithms* (ACM TODS 8(4))가 직렬화 그래프·버전 순서로 다중버전 스케줄의 **정확성(직렬성)을 형식적으로 분석**하는 이론을 세웠다.

```text
행 X의 버전 체인

   +---------------------+        +---------------------+
   | X=10                | -----> | X=20                |
   | xmin=T1  xmax=T5    |        | xmin=T5  xmax=∞     |
   +---------------------+        +---------------------+
              ^                              ^
              | 보임                          | 생성
   +---------------------+        +---------------------+
   | 읽기 Tr             |        | 쓰기 Tr             |
   | 스냅샷=T4           |        | =T5 커밋            |
   +---------------------+        +---------------------+
```

그림 해설 — 한 단계씩.

- T5가 X를 20으로 고칠 때 옛 값 10을 지우지 않고 새 버전을 뒤에 붙인다.
- 스냅샷이 T4인 읽기 트랜잭션은 자기 시점에 유효한 옛 버전(X=10)을 본다.\
  기다리지 않고, 잠그지도 않는다.
- `xmin`은 "이 버전을 만든 트랜잭션", `xmax`는 "이 버전을 밀어낸 트랜잭션"이다.\
  두 값이 그 버전이 보이는 구간을 정한다.

- **무엇을 해결**: 락 기반 동시성에서 "읽기 vs 쓰기" 충돌로 인한 대기·교착을 제거했다.\
  **MVCC + 스냅샷 격리**의 결합이 오늘날 PostgreSQL·Oracle·MySQL(InnoDB)·SQL Server의 기본 동시성 모델이다.
- **대가는 무엇인가**: 옛 버전을 청소(vacuum/purge)해야 하는 **공간·GC 비용**을 새로 들여왔다.\
  §3의 스냅샷 격리는 사실상 MVCC의 격리수준 면이다.

> **교착(deadlock)** — 서로가 상대가 쥔 잠금을 기다리며 둘 다 영원히 못 나아가는 상태.\
> 예: T1은 A를 쥐고 B를 기다리고, T2는 B를 쥐고 A를 기다린다.

> **GC(garbage collection) / vacuum** — 더 이상 아무도 볼 수 없는 옛 버전을 치워 공간을 되찾는 작업.\
> 예: PostgreSQL의 VACUUM이 아무 스냅샷에도 안 보이는 죽은 행을 회수한다.

### 5. 저장 구조 — B-tree vs LSM-tree

**언제 나오나** — "읽기와 쓰기 중 무엇을 최적화할 것인가"를 정해야 할 때.

데이터가 디스크에 어떻게 배치되는가는 그 선택 자체다.\
두 거대 패러다임이 있다.

#### B-tree (1972) — 읽기 최적, 제자리 갱신

루돌프 바이어(Rudolf Bayer)와 에드워드 맥크레이트(Edward McCreight)의 1972년 논문 *Organization and Maintenance of Large Ordered Indexes* (Acta Informatica 1(3))가 B-tree를 도입했다.\
노드 하나를 **디스크 블록 크기**에 맞춰 여러 키를 담게 하여 트리 높이를 낮추고, 조회·삽입·삭제를 인덱스 크기의 로그 시간에 수행한다.

- **특성**: 데이터를 **제자리(in-place)로 갱신**한다.\
  정렬 순서를 유지하므로 점 조회·범위 조회 모두 강하다(읽기 친화).\
  그러나 갱신마다 무작위 디스크 쓰기가 발생하고, 페이지가 일부만 차도 통째로 쓰게 되어 **쓰기 증폭(write amplification)**이 생긴다.

#### LSM-tree (1996) — 쓰기 최적, 추가 후 병합

패트릭 오닐 외의 1996년 논문 *The Log-Structured Merge-Tree* (Acta Informatica 33(4))는 정반대 전략을 택했다.\
쓰기를 **메모리 버퍼(memtable)에 모아두었다가**, 정렬된 불변 파일(SSTable)로 디스크에 *순차* 기록하고, 백그라운드에서 **병합(compaction)**으로 정리한다 — 마치 머지 정렬처럼.

- **특성**: 무작위 쓰기를 순차 쓰기로 바꿔 쓰기 처리량이 매우 높다(쓰기 친화).\
  대신 한 키가 여러 레벨에 흩어져 있을 수 있어 조회 시 여러 파일을 봐야 하고(블룸 필터로 완화), 병합이 같은 데이터를 반복해 다시 쓴다.

```text
[ B-tree — 제자리 갱신 ]            [ LSM-tree — 붙이고 나중에 병합 ]
키 42 를 고친다                      키 42 를 고친다
   그 키가 사는 페이지를 찾아          memtable 에 그냥 적는다 (메모리)
   디스크에서 읽고                          ↓ 가득 차면
   고쳐서                              SSTable 로 순차 기록 (디스크)
   그 자리에 다시 쓴다                       ↓ 나중에
   → 무작위 쓰기 1회 이상              compaction 으로 병합 정리

읽기: 트리 한 경로만 (빠름)          읽기: 여러 레벨·파일을 봐야 함 (느림)
쓰기: 무작위 (느림)                  쓰기: 순차 (빠름)
```

이 대비의 결론 — 같은 "고친다"는 일을 **지금 제자리에서 끝낼지, 나중에 몰아서 정리할지**의 차이다.

> **순차 쓰기 / 무작위 쓰기** — 디스크의 이어진 자리에 죽 쓰는 것과, 여기저기 흩어진 자리에 쓰는 것.\
> 예: 공책 뒤에 이어 적는 것과, 300쪽 중 한 줄씩 찾아가 고치는 것의 차이.

> **블룸 필터(Bloom filter)** — "이 파일에 이 키가 확실히 없다"를 아주 싸게 판정해 주는 자료구조.\
> 예: 파일 10개를 다 열어보는 대신, 없는 게 확실한 8개를 먼저 건너뛴다.

#### 증폭(amplification)이라는 공통 언어

두 구조의 차이는 **세 가지 증폭**으로 요약된다 — 이 어휘 자체가 저장구조 비교의 핵심 개념이다.

| 증폭 | 의미 | B-tree | LSM-tree |
|------|------|--------|----------|
| **읽기 증폭** | 1회 조회에 실제 읽는 양 | 낮음(트리 1경로) | 높음(여러 레벨·파일) |
| **쓰기 증폭** | 1회 쓰기에 실제 쓰는 양 | 페이지 단위·제자리 | 병합 재기록 |
| **공간 증폭** | 논리 데이터 대비 실제 점유 | 페이지 단편화 | 미병합 중복·tombstone |

> **tombstone(묘비)** — 삭제를 "지움"이 아니라 "삭제됨 표시"로 적어 두는 기록.\
> 예: LSM에서 지운 키는 바로 사라지지 않고, 병합될 때 비로소 실제로 제거된다.

- **무엇을 해결**: LSM은 SSD·로그형 워크로드(시계열·KV)의 폭발적 쓰기를 감당하기 위해 등장했다.\
  LevelDB·RocksDB·Cassandra·HBase가 LSM, 전통 RDBMS는 대개 B-tree(또는 B+tree)다.\
  "어느 증폭을 감수할 것인가"가 저장 엔진 선택의 본질이다.

### 6. 복제 — 같은 데이터를 여러 곳에

**언제 나오나** — 한 대가 죽어도 서비스가 계속돼야 하고, 읽기 부하를 나눠야 할 때.

복제(replication)는 같은 데이터를 여러 노드에 둬서 세 가지를 얻는다.\
**가용성**(한 노드가 죽어도 서비스), **읽기 확장**(읽기 부하 분산), **지역성**(사용자 근처에서 응답)이다.\
핵심 설계 변수는 **언제 쓰기를 "성공"으로 볼 것인가**이다.

```text
                    ┌────────────┐
     쓰기 ────────▶ │  리더(주)  │
                    └─────┬──────┘
        동기(sync)  ┌─────┴─────┐ 비동기(async)
   팔로워 ACK 기다림  ▼           ▼ ACK 안 기다림(곧 전파)
              ┌──────────┐  ┌──────────┐
              │ 팔로워 A │  │ 팔로워 B │   ← 복제 지연(lag) 발생 지점
              └──────────┘  └──────────┘
```

그림 해설 — 왼쪽 팔로워는 리더가 답하기 전에 확인을 보내고, 오른쪽 팔로워는 나중에 따라온다.\
그 "나중에"가 벌어지는 틈이 복제 지연이다.

- **동기 복제(synchronous)**: 리더가 *팔로워의 확인을 받은 뒤* 클라이언트에 성공을 알린다.\
  팔로워가 항상 최신이지만, 팔로워가 느리면 쓰기 전체가 막힌다(가용성↓).
- **비동기 복제(asynchronous)**: 리더가 *먼저 성공을 알리고* 나중에 전파한다.\
  빠르고 가용하지만, 리더 장애 시 아직 전파 안 된 쓰기가 **유실**될 수 있다.
- **복제 지연(replication lag)**: 비동기에서 팔로워가 리더보다 뒤처지는 시간차.\
  이 지연이 corpus의 일관성 모델 문서가 다루는 이상현상들의 물리적 원인이다 — *read-your-writes 위반*(내가 쓴 걸 못 읽음), *monotonic reads 위반*(시간이 거꾸로 가는 읽기).

> **리더 / 팔로워** — 쓰기를 받아 순서를 정하는 노드와, 그 순서를 받아 그대로 따라 적는 노드.\
> 예: 리더에 입금을 적으면 팔로워 두 대가 같은 내용을 뒤따라 적는다.

> **ACK(확인 응답)** — 상대가 "받았다"고 알려 주는 신호.\
> 예: 팔로워가 로그를 저장하고 리더에게 보내는 한 줄짜리 답장.

- **무엇을 해결/남긴 문제**: 복제는 단일 노드의 가용성·확장 한계를 깼지만, "어느 복제본을 읽느냐에 따라 다른 값을 본다"는 일관성 문제를 만들었다.\
  이 긴장이 §2 CAP/PACELC의 무대다.

### 7. 파티셔닝 / 샤딩 — 데이터를 쪼개 흩뿌리다

**언제 나오나** — 한 대에 다 안 들어가거나, 쓰기 처리량이 한 대를 넘을 때.

복제가 *같은 데이터를 여러 곳에* 두는 것이라면, 파티셔닝(샤딩)은 *서로 다른 데이터를 여러 곳에* 나눠 둬서 **쓰기와 저장 용량까지** 수평 확장한다.\
둘은 보통 함께 쓰인다(각 샤드를 다시 복제).

핵심 질문은 "어떤 키를 어느 노드로 보낼 것인가"다.

```text
[ 범위 파티셔닝 ]                   [ 해시 파티셔닝 ]
A–F → 노드1                          hash(key) % 3
G–M → 노드2                          key1 → 노드2
N–Z → 노드3                          key2 → 노드1
                                     key3 → 노드3
범위 조회에 강함                     고르게 퍼짐
("H~K 를 다 주세요" = 노드2 하나)     ("H~K" 가 세 노드에 흩어짐)
핫스팟에 취약                        범위 조회가 흩어짐
(이름이 A로 몰리면 노드1만 바쁨)
```

이 대비의 결론 — 고르게 퍼뜨리는 것과 이웃끼리 붙여 두는 것은 동시에 가질 수 없다.

- **범위 파티셔닝(range)**: 키 구간으로 분할(A–F는 노드1…).\
  범위 조회에 강하지만 핫스팟(특정 구간 집중)에 취약.
- **해시 파티셔닝(hash)**: 키 해시로 분산.\
  고르게 퍼지지만 범위 조회가 흩어진다.
- **일관된 해싱(consistent hashing)**: 카거(Karger) 외의 1997년 연구가 도입한 기법으로, 노드 추가/삭제 시 *재배치되는 키를 최소화*한다(전체 재해싱 회피).\
  아마존 **Dynamo**(DeCandia 외, SOSP 2007)가 이를 가상 노드와 결합해 실전화했다.

> **핫스팟(hotspot)** — 부하가 특정 노드 하나에 몰려 그 노드만 터지는 현상.\
> 예: 최신 타임스탬프를 키로 쓰면 지금 이 순간의 쓰기가 전부 마지막 노드로 간다.

> **일관된 해싱(consistent hashing)** — 노드가 늘거나 줄 때 옮겨야 하는 키를 최소로 만드는 해시 배치 방식.\
> 예: 노드 10대에서 1대를 빼도 전체가 아니라 그 1대 몫만 이웃으로 옮겨간다.

Dynamo 논문은 사실상 이 문서의 여러 개념을 **하나의 시스템으로 종합한 분수령**이다.\
일관된 해싱 파티셔닝 + N개 복제 + 정족수(quorum) + 벡터 클록 + 결과적 일관성(=AP, BASE)이 그 조합이다.\
이후 Cassandra·Riak 등 "Dynamo 계열"의 청사진이 됐다.

- **무엇을 해결**: 단일 노드의 *저장·쓰기 용량* 한계.\
  단, 샤드 경계를 넘는 트랜잭션·조인·재균형(rebalancing)이라는 새 난제를 들여왔다.

### 8. 합의 — 여러 노드가 하나의 진실에 동의하기

**언제 나오나** — "누가 리더인가", "이 쓰기가 몇 번째인가"를 모두가 똑같이 알아야 할 때.

복제와 파티셔닝은 그 질문을 남긴다.\
비신뢰 네트워크(메시지 유실·지연·노드 고장)에서 여러 노드가 **단일 값에 합의**하는 문제가 **합의(consensus)**이며, 강한 일관성(CP)의 토대다.

#### Paxos (1998) — 정확하지만 난해한

레슬리 램포트(Leslie Lamport)는 *The Part-Time Parliament* (ACM TOCS 16(2), 1998 — 1990년 작성)에서 Paxos를 제시했다.\
고대 그리스 의회의 우화로 서술된 이 논문은 **악명 높게 난해**해, "읽은 이를 당황시키고 이해를 가로막아 왔다"는 평을 받았다.\
램포트는 이후 *Paxos Made Simple*(2001)로 재설명해야 했다.\
Paxos는 노드·메시지·시계가 모두 불완전해도 **안전성(잘못된 합의는 절대 안 함)**을 보장한다.

#### Raft (2014) — 이해 가능함을 설계 목표로

디에고 온가로(Diego Ongaro)와 존 오스터하우트(John Ousterhout)는 2014년 USENIX ATC 논문 *In Search of an Understandable Consensus Algorithm*에서 Raft를 발표했다.\
**Paxos와 동등한 결과**를 내면서도, 제일의 설계 목표를 *이해 가능성(understandability)*으로 삼았다.\
문제를 세 부분으로 분해했다 — **리더 선출 / 로그 복제 / 안전성**.

```text
   Follower ──선거 타임아웃──▶ Candidate ──과반 득표──▶ Leader
      ▲                            │                      │
      │                            │                      │
      └────────다른 리더 발견───────┘                      │
      │                                                   │
      └────────더 높은 term 발견──────────────────────────┘

   Leader ┈┈ 로그 복제(AppendEntries) ┈┈▶ Follower
```

그림 해설 — 한 단계씩.

- 팔로워가 리더 소식을 일정 시간 못 들으면 후보가 되어 선거를 연다.
- 과반의 표를 받으면 리더가 되고, 그때부터 로그 복제를 주도한다.
- 자기보다 높은 term(임기 번호)을 보면 리더도 즉시 팔로워로 내려온다.\
  "임기가 더 최신인 쪽이 이긴다"는 한 줄 규칙이 분열을 정리한다.

> **term(임기)** — 선거가 한 번 열릴 때마다 1씩 오르는 번호.\
> 예: term 7의 리더가 term 8 메시지를 보면 자기가 구식임을 알고 물러난다.

> **안전성(safety) / 라이브니스(liveness)** — "나쁜 일은 절대 안 일어난다"와 "좋은 일은 언젠가 일어난다".\
> 예: 서로 다른 두 값이 동시에 확정되는 일은 없다(안전성), 네트워크가 회복되면 결국 리더가 뽑힌다(라이브니스).

- **무엇을 해결**: 분산 시스템에서 "단일 리더·단일 로그 순서"를 신뢰성 있게 정하는 문제.\
  etcd·Consul·CockroachDB·TiDB 등이 Raft를 채택하면서, Raft는 *합의 = 강한 일관성 분산 시스템의 심장*이라는 위치를 굳혔다.\
  Paxos가 "옳음"을 증명했다면 Raft는 그것을 "구현 가능·교육 가능"하게 만들었다.

### 9. WAL과 체크포인트 — 고장에서 살아 돌아오기

**언제 나오나** — "커밋했다"는 답을 정전·크래시가 나도 지켜야 할 때.

ACID의 **D(내구성)**와 **A(원자성)**를 고장 상황에서 실제로 실현하는 메커니즘이 **선행 기록 로그(Write-Ahead Logging, WAL)**다.\
원칙은 단순하다 — **데이터 페이지를 디스크에 바꾸기 *전에*, 그 변경을 기술한 로그 레코드를 먼저 디스크에 기록한다.**\
그러면 변경 도중 죽어도 로그로부터 복구할 수 있다.

```text
[ 로그 없이 ]                       [ WAL ]
페이지를 바로 고친다                 ① 로그에 "X를 10→20" 먼저 기록
   ↓ 도중에 정전                     ② 그다음 페이지를 고친다
페이지가 반만 고쳐진 채 남는다          ↓ 도중에 정전
   ↓                                로그를 읽어 다시 적용하거나 되돌린다
무엇이 맞는 값인지 알 길이 없다         ↓
                                    항상 옳은 상태로 돌아온다
```

이 대비의 결론 — 로그가 먼저 있으면, 고장 시점이 언제든 **어느 쪽으로 정리할지 알 수 있다**.

이 WAL 계열의 표준을 세운 것이 모한(C. Mohan) 외의 1992년 논문 *ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging* (ACM TODS 17(1))이다.\
ARIES는 복구를 세 단계로 정식화했다.

```text
충돌 후 재시작 복구 (ARIES 3단계)

  ① Analysis  — 로그를 훑어 충돌 시점의 더티 페이지·활성 트랜잭션 파악
  ② Redo      — 마지막 체크포인트 이후의 모든 변경을 *다시 적용*(디스크 반영 보장)
  ③ Undo      — 커밋 안 된 트랜잭션의 변경을 *되돌림*(원자성 보장)
```

그림 해설 — 먼저 무엇이 어디까지 됐는지 파악하고, 일단 전부 다시 적용해 상태를 맞춘 뒤, 커밋 안 된 것만 골라 되돌린다.\
"다시 적용부터 하고 되돌리기는 나중에"라는 순서가 ARIES의 요점이다.

> **더티 페이지(dirty page)** — 메모리에서는 고쳐졌지만 아직 디스크에 반영되지 않은 페이지.\
> 예: 방금 수정한 행이 든 페이지는 디스크에 쓰이기 전까지 더티 상태다.

- **체크포인트(checkpoint)**: 로그가 무한정 길어지면 복구 시 처음부터 다시 읽어야 한다.\
  주기적으로 **현재 메모리 상태를 디스크에 반영하고 그 지점을 로그에 표시**해, Redo의 시작점을 앞당긴다 — 복구 시간과 로그 보관량의 균형추다.

- **무엇을 해결**: "에러 없이 커밋했다 = 디스크에 안전하다"를 보장하는 *물리적 토대*.\
  WAL은 내구성을 주는 동시에, 그 로그를 **복제 스트림으로 재사용**하는 이중 역할을 한다(§6 복제는 흔히 WAL을 팔로워에 흘려보낸다).\
  즉 단일 노드 복구 개념(WAL)이 분산 복제의 운반체로 확장된 셈이다.

## 왜 그렇게 갔나 — 남은 선택지와 트레이드오프

이 개념들은 대부분 "무엇을 포기할지"의 눈금이다.\
각 눈금을 한 줄로 세우면 이렇게 된다.

```text
정확성 ◀────────────────────────────────▶ 속도
  SERIALIZABLE   Repeatable Read   Read Committed   Read Uncommitted
  (완전 격리)                                        (더티 리드 허용)
  비쌈                                               쌈·이상현상 허용

읽기 ◀──────────────────────────────────▶ 쓰기
  B-tree (제자리 갱신)                     LSM-tree (붙이고 병합)
  읽기 증폭 낮음 / 쓰기 증폭 높음           쓰기 빠름 / 읽기·공간 증폭 높음

일관성 ◀────────────────────────────────▶ 가용성·지연
  동기 복제 · CP · PC/EC                   비동기 복제 · AP · PA/EL
  최신값 보장 / 느리고 잘 막힘              빠르고 잘 죽지 않음 / stale 읽기
```

읽는 법 — 어느 눈금에서도 한쪽 끝이 정답인 적은 없다.\
개념의 값어치는 "어디가 좋은가"를 정해 준 데 있지 않고, **선택지를 셀 수 있게 만든 데** 있다.

포기하지 않으려는 시도도 물론 있었다.\
SI가 남긴 write skew를 다시 막으려는 SSI(2008 Cahill 외)가 그렇고, 분산 위에서 ACID를 되찾으려는 NewSQL이 그렇다.\
다만 그런 시도도 다른 비용(예컨대 합의 대기)을 대신 낸다.

## 남긴 것 — 오늘 우리가 쓰는 것

데이터베이스 개념사는 **두 개의 큰 호(arc)**로 읽힌다.

1. **단일 노드 정확성의 호 (1972~1992)** — 트랜잭션·ACID·격리수준·MVCC·B-tree·WAL.\
   질문은 "한 대 안에서 동시성과 고장에도 어떻게 옳은가".\
   이 시기의 산물은 오늘날까지 거의 모든 DB의 *불변의 토대*로 남아 있다.\
   ACID는 여전히 RDBMS의 기본 계약이고, MVCC+SI는 사실상의 표준 동시성 모델이며, WAL은 내구성의 보편적 구현이다.

2. **분산 타협의 호 (1996~2014)** — LSM·CAP·BASE·복제·샤딩·합의·PACELC.\
   질문은 "여러 대에 흩뿌렸을 때 무엇을 양보할 것인가".\
   이 시기는 *불가능성*을 받아들이는 법(CAP)과, 그 안에서 선택지를 정교화하는 법(PACELC·합의·결과적 일관성)을 가르쳤다.

이 두 호를 관통하는 메타-주제는 **"정확성과 성능의 교환 비율을 어떻게 *이름 붙이고 측정할 것인가*"**이다.

```text
막연한 타협             →      명시적 눈금
"좀 느슨하게 하면 빨라짐"  →   격리수준 (정확성 ↔ 속도)
"저장 방식에 따라 다름"    →   증폭    (읽기 ↔ 쓰기 ↔ 공간)
"분산하면 뭔가 포기함"     →   CAP/PACELC (일관성 ↔ 가용성 ↔ 지연)
```

개념의 진보란 곧 **막연한 타협을 명시적 눈금으로 바꾼 사건들**의 연속이었다.

오늘날의 "NewSQL"(Spanner·CockroachDB·TiDB)은 이 두 호를 다시 합치려는 시도다.\
분산 위에서 ACID·직렬성·강한 일관성을 *합의(Raft/Paxos) + MVCC + WAL*로 복원하려 한다.\
즉 현대 분산 DB는 이 문서가 따라온 모든 개념의 **재조합**이다.\
그래서 이 개념사는 과거가 아니라, 지금 설계되는 시스템의 *부품 목록*이기도 하다.

> **corpus 연결**: 정합성·일관성 모델 문서가 다루는 "선형성(linearizability)·인과 일관성·결과적 일관성" 같은 *보장의 위계*는, 이 문서의 합의(§8)·복제(§6)·CAP(§2)가 *어떻게 실현되거나 포기되는가*의 결과다. 보장(약속)을 그 문서가, 그 약속을 가능케 하는 장치(개념)를 이 문서가 맡는다.

## 용어 풀이

- **트랜잭션** — 여러 읽기·쓰기를 "전부 되거나 전부 안 되거나"로 묶은 단위.
- **ACID** — 원자성·일관성·격리성·내구성. 트랜잭션이 주는 4가지 약속.
- **원자성 / 내구성** — 절반만 남지 않는다 / 커밋하면 고장에도 살아남는다.
- **BASE** — Basically Available · Soft state · Eventually consistent. 가용성과 규모를 위해 일관성을 양보하는 설계 철학.
- **가용성(availability)** — 요청하면 (옛 값이라도) 답이 온다는 성질.
- **네트워크 분단(partition)** — 노드 사이 통신이 끊긴 상태.
- **CAP** — 분단 시 일관성(CP)과 가용성(AP) 중 하나를 골라야 한다는 정리.
- **PACELC** — 분단 시 A/C, 평시에는 지연(L)/일관성(C)을 고른다는 확장된 틀.
- **stale 읽기** — 최신이 아닌 조금 전 값을 읽는 것.
- **격리수준** — 완전 격리를 얼마나 양보할지의 눈금(Read Uncommitted ~ Serializable).
- **Dirty Read / Non-repeatable Read / Phantom** — ANSI SQL-92가 정의한 세 가지 이상현상.
- **스냅샷 격리(SI)** — 시작 시점의 일관된 사진을 읽고, 커밋 시 쓰기-쓰기 충돌만 막는 격리.
- **First-Committer-Wins** — 같은 행을 쓴 트랜잭션 중 먼저 커밋한 쪽만 살리는 규칙.
- **write skew** — 각자 다른 행을 고쳤는데 서로의 옛 읽기 탓에 불변식이 깨지는 이상현상.
- **불변식(invariant)** — 항상 참이어야 하는 규칙.
- **MVCC** — 값을 덮어쓰지 않고 버전을 쌓아 읽기와 쓰기를 떼어놓는 기법.
- **교착(deadlock)** — 서로 상대의 잠금을 기다리며 둘 다 멈춘 상태.
- **vacuum / GC** — 아무도 볼 수 없는 옛 버전을 치우는 작업.
- **B-tree** — 디스크 블록 크기에 맞춘 노드로 트리 높이를 낮춘 정렬 인덱스. 제자리 갱신, 읽기 친화.
- **LSM-tree** — 메모리에 모았다가 순차 기록하고 나중에 병합하는 구조. 쓰기 친화.
- **memtable / SSTable / compaction** — LSM의 메모리 버퍼, 정렬된 불변 파일, 병합 정리 작업.
- **블룸 필터** — "이 파일에 그 키는 확실히 없다"를 싸게 판정하는 자료구조.
- **tombstone** — 삭제를 표시로 남겨 두는 기록.
- **증폭(amplification)** — 읽기·쓰기·공간 각각에서 논리적 요구보다 실제로 더 드는 양.
- **복제(replication) / 리더 / 팔로워** — 같은 데이터를 여러 노드에 두는 것과 그 역할들.
- **동기 / 비동기 복제** — 팔로워 확인을 기다리고 응답 / 먼저 응답하고 나중에 전파.
- **복제 지연(replication lag)** — 팔로워가 리더보다 뒤처진 시간차.
- **파티셔닝 / 샤딩** — 서로 다른 데이터를 여러 노드로 나눠 담는 것.
- **범위 / 해시 파티셔닝** — 키 구간으로 나누기 / 키 해시로 흩뿌리기.
- **일관된 해싱** — 노드 증감 시 옮길 키를 최소화하는 배치 방식.
- **핫스팟** — 부하가 한 노드로 몰리는 현상.
- **정족수(quorum)** — 과반 등 정해진 수의 노드만 동의하면 성립으로 치는 규칙.
- **합의(consensus) / Paxos / Raft** — 불신뢰 네트워크에서 하나의 값·순서에 동의하는 문제와 두 알고리즘.
- **term(임기)** — Raft에서 선거마다 1씩 오르는 번호.
- **안전성 / 라이브니스** — 나쁜 일은 절대 안 일어난다 / 좋은 일은 언젠가 일어난다.
- **WAL(선행 기록 로그)** — 페이지를 고치기 전에 변경 내용을 로그에 먼저 적는 규칙.
- **ARIES 3단계** — Analysis · Redo · Undo 순서의 충돌 복구 절차.
- **더티 페이지** — 메모리에서만 고쳐지고 아직 디스크에 안 내려간 페이지.
- **체크포인트** — 메모리 상태를 디스크에 반영하고 로그에 표시해 Redo 시작점을 앞당기는 것.
