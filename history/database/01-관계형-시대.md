# 관계형 DB 시대 (1970s ~ 1990s)

> 원본: `~/project/database-history/01-관계형-시대.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-18).\
> 연도·인명·논문명·표준번호·코드는 원문 그대로다. 더 압축된 원문이 필요하면 원본 문서를 보면 된다.\
> 용어 블록의 「예:」, 「대가는 무엇인가」, 트레이드오프 표는 원문에 없는 보충 설명이다.

## 한눈에 — 쉽게 말하면

**관계형 DB = 창고에서 물건을 직접 찾아오는 대신, 주문서만 써서 넘기는 것.**

- 옛날 창고는 이랬다.\
  "3번 선반 왼쪽에서 상자를 꺼내고, 그 상자 안 쪽지에 적힌 5번 선반으로 가고, 거기서 또 쪽지를 따라가라."\
  가는 길을 사람이 전부 외워서 직접 걸어야 했다.
- 창고 주인이 선반 배치를 바꾸면?\
  그 길을 외운 사람 전부가 길을 다시 외워야 한다.
- 관계형 DB는 대신 **주문서**를 받는다.\
  "영업부 사람들 이름이랑 급여를 줘."\
  선반이 어디 있고 어떤 순서로 가야 하는지는 창고 직원(DB 엔진)이 알아서 정한다.
- 그래서 창고 안쪽이 바뀌어도 주문서는 그대로다.\
  이것이 이 시대의 핵심 단어인 **데이터 독립성**이다.

```text
옛날 방식 (길을 내가 안다)     관계형 (원하는 것만 적는다)
+-------------------------+    +-------------------+
| 3번 선반 -> 쪽지 5번    |    | 주문서:           |
| -> 5번 선반 -> 쪽지 9번 |    |   영업부 사람들의 |
| -> 9번 선반에서 꺼내기  |    |   이름과 급여     |
+-------------------------+    +-------------------+
  배치가 바뀌면 전부 수정        배치가 바뀌어도 그대로
```

이 창고가 **똑같은 구조로** 1970년대의 데이터베이스 전환이다.\
쪽지를 따라가던 방식이 계층형·네트워크 모델이고, 주문서를 넘기는 방식이 관계 모델과 SQL이다.\
오늘 우리가 쓰는 Oracle·MySQL·PostgreSQL이 전부 "주문서" 쪽의 후손이다.

> **관계(relation) / 테이블** — 행과 열로 된 표 하나. 수학의 집합론에서 말하는 관계를 데이터에 옮긴 것이다.\
> 예: 사번·이름·부서 세 열을 가진 「사원」 표 하나가 관계 하나다.

> **데이터 독립성(data independence)** — 데이터가 디스크에 어떻게 저장되는지 몰라도 질의가 돌아가는 성질.\
> 예: 인덱스를 새로 만들거나 파일 구조를 바꿔도 `SELECT` 문장은 고칠 필요가 없다.

## 시대 배경 — 그전에는 어땠나

1970년 이전의 데이터베이스는 데이터의 **물리적 저장 구조**에 프로그램이 직접 묶여 있었다.\
당시 주류는 **계층형(hierarchical) 모델**(IBM IMS, 1968)과 **네트워크 모델**(CODASYL DBTG, 1969)이었다.\
둘 다 레코드들을 포인터로 엮어 트리나 그래프로 표현했다.

> **계층형 모델 / 네트워크 모델** — 레코드를 포인터로 이어 붙여 트리(계층형) 또는 그물(네트워크) 모양으로 저장하는 방식.\
> 예: 「부서」 레코드가 「사원」 레코드를 가리키고, 그 사원이 다시 「급여」 레코드를 가리킨다.

> **포인터(pointer)** — 다른 데이터가 있는 위치를 적어 둔 값. 쪽지에 적힌 "다음은 5번 선반".\
> 예: 사원 레코드 안에 "다음 사원은 여기" 하는 주소가 들어 있다.

데이터를 꺼내려면 프로그래머가 "어느 포인터를 따라 어떤 순서로 순회할지"를 손으로 코딩해야 했다(이른바 *navigational* 접근).\
저장 구조가 바뀌면 응용 프로그램을 전부 고쳐야 했다.\
데이터의 논리적 의미와 물리적 표현이 분리되지 않은 것이 근본 문제였다.

전과 후를 같은 일(영업부 사원의 급여 뽑기)로 나란히 놓으면 이렇다.

```text
관계 모델 이전 — 길을 코딩한다(how)   관계 모델 이후 — 원하는 것만 쓴다(what)
+--------------------------------+    +-------------------------------+
| 부서 레코드를 찾는다           |    | SELECT 사원.이름, 급여.금액   |
|   -> 부서.첫사원 포인터로 이동 |    |   FROM 부서, 사원, 급여       |
|   -> 사원.다음사원 포인터 순회 |    |  WHERE 부서.이름 = '영업'     |
|   -> 사원.급여 포인터로 이동   |    |    AND 사원.부서 = 부서.이름  |
|   -> 금액을 읽는다             |    |    AND 급여.사번 = 사원.사번  |
+--------------------------------+    +-------------------------------+
  저장 구조가 바뀌면 전부 고친다        저장 구조가 바뀌어도 그대로다
```

왼쪽은 **어떻게(how)** 를 쓰고, 오른쪽은 **무엇(what)** 만 쓴다 — 그 차이가 데이터 독립성이다.

IBM 산호세 연구소의 수학자 **Edgar F. Codd**는 여기에 정면으로 반기를 들었다.\
그는 데이터를 집합론과 술어 논리(predicate logic)에 기반한 **수학적 관계(relation)**, 즉 행과 열로 이루어진 테이블의 모음으로 표현하자고 제안했다.\
그리고 포인터 순회가 아니라 "무엇을 원하는가"만 기술하는 **선언적(declarative)** 질의로 접근하자고 했다.\
데이터가 어떻게 저장되든 사용자는 테이블과 그 위의 연산만 알면 된다는 **데이터 독립성**이 핵심이었다.

> **선언적(declarative) / 절차적(procedural)** — 결과를 말하는 것이 선언적, 과정을 말하는 것이 절차적이다.\
> 예: "영업부 급여를 줘"는 선언적, "3번 선반부터 순서대로 훑어라"는 절차적이다.

이 발상이 이론에 머물지 않고 SQL이라는 언어, Oracle·DB2 같은 제품, ACID 트랜잭션이라는 신뢰성 모델로 구체화되면서 관계형 DB는 1980년대 엔터프라이즈 컴퓨팅의 사실상 표준이 되었다.

시대 정보를 한 줄씩 정리하면 이렇다.

- 시기: 1970년 ~ 1990년대 중반 (이론 정립 → 상용 제품 → 국제 표준화의 한 사이클)
- 출발점: 1970년 E. F. Codd, "A Relational Model of Data for Large Shared Data Banks" (Communications of the ACM, Vol. 13, No. 6)
- 핵심 무대: IBM San Jose 연구소(System R), UC Berkeley(Ingres), 그리고 Relational Software/Oracle·Sybase 등 초기 상용 벤더
- 표준화: ANSI/ISO SQL — SQL-86(최초) → SQL-89 → SQL-92(대규모 개정)
- 이 시대가 남긴 것: 관계 모델 + 선언적 질의어(SQL) + 트랜잭션(ACID) + 클라이언트-서버 아키텍처

## 무엇이 바뀌었나

### 관계 모델 — Codd의 1970년 논문 (1970)

**무엇** — 데이터를 *n*-항 관계(테이블)의 집합으로 보는 제안이다.\
1970년 6월 Communications of the ACM에 발표했다.\
그 전신인 1969년 IBM 내부 기술 보고서가 먼저 있었다.\
논문은 중복과 불일치를 줄이기 위한 **정규형(normal form)** 과, 모든 응용이 공유하는 **범용 데이터 서브언어(universal data sublanguage)** 개념을 제시했다.

> **정규형(normal form)** — 같은 사실이 여러 곳에 중복 저장되지 않도록 표를 쪼개는 규칙.\
> 예: 사원 표마다 부서 주소를 적어 두지 않고 「부서」 표로 떼어 내면, 주소가 바뀔 때 한 곳만 고치면 된다.

**왜 이게 나은가** — 포인터를 따라 "어떻게(how)" 찾을지 코딩하던 절차적 세계를, 원하는 결과를 "무엇(what)"으로 기술하는 선언적 세계로 옮겼다.\
저장 구조와 응용 로직을 분리(데이터 독립성)해, 스키마가 바뀌어도 질의가 깨지지 않게 했다.\
이 한 편이 이후 모든 관계형 시스템의 이론적 토대가 되었다.

> **스키마(schema)** — 어떤 표가 있고 각 표에 어떤 열이 있는지를 적어 둔 설계도.\
> 예: 「사원(사번 정수, 이름 문자열, 부서 문자열)」이 스키마 한 줄이다.

**대가는 무엇인가** — 사람이 직접 경로를 지정하지 않으므로, "왜 이 질의가 느린가"를 사람이 눈으로 바로 알 수 없게 된다.\
그 대신 그 판단을 기계(질의 옵티마이저)가 맡아야 했다.\
이 판단의 수학적 근거가 다음 절의 관계 대수다 — Codd는 관계 대수를 모델의 일부로 함께 정의했고, 그것이 훗날 옵티마이저의 근거가 되었다.

### 관계 대수와 관계 해석 (1970년대 초)

**무엇** — Codd는 관계를 조작하는 두 가지 동등한 형식 체계를 정의했다.

- **관계 대수(relational algebra)** 는 선택(σ, selection)·투영(π, projection)·합집합·차집합·곱집합·조인(join) 같은 **연산자**로 결과를 절차적으로 조립하는 방식이다.
- **관계 해석(relational calculus)** 은 "어떤 조건을 만족하는 튜플"을 논리식으로 선언하는 방식이다.

> **관계 대수(relational algebra)** — 표를 넣으면 표가 나오는 연산자들의 모음. 표를 재료로 표를 만든다.\
> 예: 「사원」 표에서 영업부만 고르고(σ), 거기서 이름 열만 남기면(π) 결과도 또 하나의 표다.

> **튜플(tuple)** — 표의 행 하나.\
> 예: `(1, Alice, 영업)` 이 튜플 하나다.

이름이 어려워 보이지만, σ와 π는 표를 가위로 자르는 두 방향일 뿐이다.\
σ는 가로로(행을 고르고), π는 세로로(열을 고른다) 자른다.

```text
[1] 원래 표 (사원)
+------+--------+--------+
| 사번 | 이름   | 부서   |
+------+--------+--------+
| 1    | Alice  | 영업   |
| 2    | Bob    | 개발   |
| 3    | Carol  | 영업   |
+------+--------+--------+
        |
        |  선택 sigma(부서 = '영업')  -- 조건에 맞는 "행"을 고른다
        v
[2] 행이 줄어든 표
+------+--------+--------+
| 1    | Alice  | 영업   |
| 3    | Carol  | 영업   |
+------+--------+--------+
        |
        |  투영 pi(이름)  -- 필요한 "열"만 남긴다
        v
[3] 열까지 줄어든 표
+--------+
| 이름   |
+--------+
| Alice  |
| Carol  |
+--------+
```

그림 해설 (한 단계씩):

- [1] → [2] 선택(σ)은 조건에 맞지 않는 행을 통째로 버린다.\
  열 구성은 그대로다.
- [2] → [3] 투영(π)은 필요 없는 열을 버린다.\
  열만 줄고, 중복 행은 하나로 합쳐진다.
- 결과가 다시 표이므로 연산을 계속 이어 붙일 수 있다 — 이것이 "대수"라고 부르는 이유다.

**왜 이게 나은가** — 관계 대수는 질의를 **최적화 가능한 대수식**으로 표현할 수 있게 했다.\
`σ` 를 먼저 하고 `join` 을 나중에 하면 중간 결과가 훨씬 작아지는 식으로, 같은 답을 더 싸게 얻는 순서가 수식 변형으로 계산된다.\
이것이 훗날 질의 옵티마이저가 "같은 결과를 더 싸게 계산하는 실행 계획"을 자동으로 찾는 근거가 되었다.

> **질의 옵티마이저(query optimizer)** — 같은 결과를 내는 여러 실행 방법 중 가장 싼 것을 골라 주는 DB 내부 부품.\
> 예: 두 표를 합칠 때 어느 쪽을 먼저 걸러낼지, 인덱스를 쓸지 전체를 훑을지를 자동으로 정한다.

또한 Codd는 어떤 질의 언어가 "충분히 표현력 있는가"를 재는 기준으로 **관계 완전성(relational completeness)** — 관계 해석으로 쓸 수 있는 질의를 모두 표현할 수 있는가 — 을 제시했고, 이것이 SQL 같은 언어의 설계 목표가 되었다.

### System R과 SEQUEL/SQL의 탄생 (1973~1979)

**언제·어디서** — 1973년경 IBM 산호세 연구소에서 관계 모델을 실제로 구현해 검증하는 실험 프로젝트 **System R**이 시작되었다.

**SEQUEL → SQL** — **Donald D. Chamberlin**과 **Raymond F. Boyce**는 처음에 SQUARE를 만들었다(첨자·위첨자 표기라 쓰기 어려웠다).\
그 뒤 일상 영어에 가까운 질의어 **SEQUEL(Structured English Query Language)** 로 다시 설계했다.\
"SEQUEL"이 영국 회사의 상표와 충돌해 모음을 떼고 **SQL**로 줄였다.\
Boyce는 1974년 뇌동맥류로 27세에 요절했지만, SQL은 이름에 그의 유산을 남겼다 — BCNF의 'B'.

**무엇이 바뀌었나** — System R은 관계 모델이 **실용적인 성능으로 동작함**을 증명했다.\
특히 **비용 기반 질의 옵티마이저(cost-based optimizer)**, **트랜잭션·락·로그를 통한 회복** 같은, 이후 모든 RDBMS가 채택한 핵심 기법을 이 프로젝트에서 확립했다.\
무엇보다 SQL이라는, 비전공자도 읽을 수 있는 선언적 언어를 세상에 내놓았다.

> **비용 기반 옵티마이저(cost-based optimizer)** — 각 실행 방법의 예상 비용(읽을 페이지 수 등)을 숫자로 추정해 가장 싼 것을 고르는 방식.\
> 예: 조건에 맞는 행이 3건뿐이면 인덱스로, 절반이면 전체 훑기로 자동 전환한다.

> **락(lock) / 로그(log)** — 락은 같은 데이터를 동시에 못 건드리게 잠그는 것, 로그는 무엇을 바꿨는지 미리 적어 두는 기록이다.\
> 예: 정전으로 꺼져도 로그를 다시 읽어 중간에 끊긴 작업을 되돌리거나 마저 반영한다.

### 상용 RDBMS의 등장 — Oracle, IBM, Ingres, Sybase (1979~1989)

관계 모델은 학계·연구소를 벗어나 빠르게 제품이 되었다.\
"누가 먼저 파느냐"의 경쟁이 곧 산업을 만들었다.

그림 해설 (한 단계씩):

- 1970년 Codd의 논문 한 편에서 두 갈래가 **각각 따로** 출발한다 — IBM 산호세의 System R과 버클리의 Ingres다.\
  Ingres는 System R에서 갈라져 나온 것이 아니다.
- Ingres에서 뻗는 두 화살표는 종류가 다르다.\
  Postgres는 **코드가 파생**된 것이고, Sybase는 Ingres 출신 사람이 나가서 세운 **인적 계보**다.
- 맨 아래 칸은 화살표가 아니라 **연대순 구분선**이다.\
  Oracle Version 2 → SQL/DS → DB2 는 서로에게서 파생된 제품이 아니라, 서로 다른 회사가 몇 년 간격으로 낸 제품이다.\
  IBM은 자기 연구 성과인 System R을 제품화했고, Oracle은 Codd의 논문과 System R 프로토타입을 참고해 따로 만들었다.

제품별로 풀어 쓰면 이렇다.

- **Oracle (1979)** — Larry Ellison·Bob Miner·Ed Oates가 1977년 세운 Software Development Laboratories(→ Relational Software, Inc. → Oracle)가 **1979년 Oracle Version 2를 출시**했다.\
  Codd의 1970년 논문과 1974년 SQL 논문에 영감을 받아, IBM의 System R 프로토타입과 최대한 호환되도록 미니컴퓨터 위에 구현한 것이다.\
  이것이 **상업적으로 판매된 최초의 SQL 기반 RDBMS**다.\
  IBM의 제품 출시보다 앞섰다는 점을 마케팅 포인트로 삼았다 — 그래서 "Version 1"은 건너뛰고 Version 2부터 팔았다.
- **IBM SQL/DS (1981) · DB2 (1983)** — IBM은 System R의 연구 성과를 제품화했다.\
  먼저 1981년 VM/VSE 계열용 **SQL/DS**를 냈다.\
  1983년 6월 7일 메인프레임 MVS용 **DB2(Database 2)** 를 발표했다(GA는 1985년).\
  DB2는 IBM 메인프레임의 미션 크리티컬 워크로드를 떠받치며 관계형 모델의 엔터프라이즈 신뢰성을 입증했다.
- **Ingres (1970년대 중반~) — UC Berkeley** — **Michael Stonebraker**와 Eugene Wong이 버클리에서 만든 학술 RDBMS다.\
  SQL이 아니라 자체 질의어 **QUEL**을 썼다(기본 발상은 유사).\
  상용화를 위해 Relational Technology, Inc.(→ Ingres Corp.)가 설립되었다.\
  이 프로젝트는 오픈소스 데이터베이스 계보(PostgreSQL의 직접 조상인 Postgres가 여기서 파생)와 수많은 인재의 산실이 되었다.
- **Sybase → Microsoft SQL Server (1980년대 말~1990년대)** — Ingres 프로젝트 출신 **Robert Epstein**이 세운 Sybase는 클라이언트-서버 아키텍처를 정면에 내세운 RDBMS를 만들었다.\
  **1992년 Sybase가 코드를 Microsoft에 라이선스**하면서 그 코드베이스가 **Microsoft SQL Server**의 출발점이 되었다.

### 표준화 — SQL-86 / SQL-89 / SQL-92

**무엇** — 벤더마다 SQL 방언이 갈라지자, "어디서든 통하는 SQL"을 위한 국제 표준이 필요해졌다.

- **SQL-86 (ANSI X3.135-1986 / ISO 9075:1987)** — 최초의 공식 SQL 표준.\
  DDL(정의)·DML(조작)·질의의 기본 문법을 못박았다.
- **SQL-89** — 소규모 개정이지만 의미가 컸다.\
  **무결성 제약(integrity constraints)** 을 도입해 `PRIMARY KEY`·`FOREIGN KEY`·`DEFAULT`·`CHECK`로 데이터의 일관성을 스키마 수준에서 강제할 수 있게 했다(기존엔 `UNIQUE`·`NOT NULL` 수준).
- **SQL-92 (ANSI X3.135-1992 / ISO 9075:1992)** — 대규모 개정.\
  명시적 **JOIN 문법**, **서브쿼리**, **집합 연산(UNION/INTERSECT/EXCEPT)** 등을 표준화하고 DDL/DML을 크게 확장했다.\
  서로 다른 DBMS 간 **이식성(portability)** 을 비약적으로 끌어올렸다.\
  오늘날 "표준 SQL"이라 할 때 기준이 되는 판본이다.

> **DDL / DML** — DDL은 표와 열을 정의하는 문장(`CREATE TABLE`), DML은 데이터를 넣고 빼고 고치는 문장(`INSERT`·`SELECT`)이다.\
> 예: 책장을 짜는 것이 DDL, 책을 꽂고 꺼내는 것이 DML이다.

> **무결성 제약(integrity constraint)** — 애초에 말이 안 되는 데이터가 저장되지 못하게 스키마에 박아 둔 규칙.\
> 예: `FOREIGN KEY` 를 걸어 두면 존재하지 않는 부서 번호를 가진 사원 행은 아예 들어가지 않는다.

> **이식성(portability)** — 같은 코드가 다른 제품에서도 그대로 도는 성질.\
> 예: 표준 SQL만 쓴 질의는 Oracle에서 짜서 DB2로 옮겨도 대체로 돈다.

**왜 이게 나은가** — 표준 SQL은 응용을 특정 벤더에 묶이지 않게 했고(이론상 DB를 갈아끼울 수 있게), SQL을 한 번 배우면 어느 제품에서나 통하는 **공용어**로 만들었다.\
관계형이 산업 표준으로 굳는 마지막 못이었다.

**대가는 무엇인가** — 표준은 최소 공통분모라서, 실제로는 제품마다 표준 밖 확장을 얹었다.\
"이론상 갈아끼울 수 있다"와 "실제로 갈아끼운다"의 간격은 이 시대에도 좁지 않았다.

### 트랜잭션과 ACID, 그리고 2PC (1978~1983)

관계 모델이 "데이터를 어떻게 표현하나"였다면, 트랜잭션은 "동시 접근·장애 속에서 데이터를 어떻게 **믿을 수 있게** 바꾸나"의 답이었다.

> **트랜잭션(transaction)** — 여러 개의 변경을 하나의 덩어리로 묶어, 전부 되거나 전부 안 되게 만드는 단위.\
> 예: A 계좌에서 빼고 B 계좌에 넣는 두 동작은 한 트랜잭션이어야 돈이 공중에 뜨지 않는다.

**트랜잭션 개념과 ACID** — Tandem/IBM의 **Jim Gray**가 1970년대 후반~1981년에 트랜잭션의 핵심 성질로 **원자성(Atomicity)·일관성(Consistency)·지속성(Durability)** 을 정식화했다.\
1983년 **Theo Härder와 Andreas Reuter**가 논문 *"Principles of Transaction-Oriented Database Recovery"*(ACM Computing Surveys)에서 여기에 **격리성(Isolation)** 을 더해 **ACID**라는 머리글자를 처음 만들었다.

- **A**tomicity: 트랜잭션은 전부 반영되거나 전혀 반영되지 않는다("all or nothing").
- **C**onsistency: 트랜잭션 전후로 무결성 제약이 유지된다.
- **I**solation: 동시에 도는 트랜잭션들이 서로의 중간 상태를 보지 않는다(직렬화 가능성).
- **D**urability: 한 번 커밋되면 장애가 나도 살아남는다(로그·회복).

> **직렬화 가능성(serializability)** — 동시에 돌린 결과가, 하나씩 차례로 돌린 어떤 순서의 결과와 같다는 성질.\
> 예: 두 이체를 동시에 처리해도 "먼저 하나, 다음 하나"로 한 것과 잔액이 똑같다.

> **커밋(commit)** — "여기까지를 확정한다"고 선언하는 것. 그 반대가 취소(abort/rollback)다.\
> 예: 커밋 전에 정전이 나면 그 트랜잭션의 변경은 전부 없던 일이 된다.

**2단계 커밋(Two-Phase Commit, 2PC)** — Jim Gray가 1978년에 정리한, **여러 노드/자원에 걸친 분산 트랜잭션**을 원자적으로 커밋하기 위한 프로토콜이다.\
코디네이터가 모든 참가자에게 "준비됐나(prepare)"를 묻고(1단계), 전원이 yes면 "커밋(commit)", 하나라도 no면 "취소(abort)"를 전파한다(2단계).\
**부분 커밋(partial commit)** 으로 인한 불일치를 막아, 여러 데이터베이스에 걸친 갱신도 한 덩어리처럼 안전하게 묶을 수 있게 했다.

```text
1단계 — 코디네이터가 묻는다: "준비됐나(prepare)?"
        |
        +--> 참가자 A (계좌 DB)  : yes
        +--> 참가자 B (카드 DB)  : yes
        |
        v
      전원이 yes 였나?
        |
        +-- 예 --------------> 2단계: 전원에게 "커밋(commit)" 전파
        |                             A, B 둘 다 확정
        |
        +-- 아니오(하나라도 no) -> 2단계: 전원에게 "취소(abort)" 전파
                                      A, B 둘 다 없던 일로
```

그림 해설 (한 단계씩):

- 1단계는 실제로 확정하지 않고 "확정할 수 있는 상태"까지만 만들어 둔 뒤 답을 모은다.
- 2단계는 그 답을 보고 전원에게 같은 결론(커밋 또는 취소)을 내려보낸다.
- 그래서 "A만 커밋되고 B는 안 된" 상태(부분 커밋)가 생기지 않는다.
- 대가 — 코디네이터가 1단계와 2단계 사이에 죽으면 참가자들이 답을 못 듣고 묶인 채 기다린다.\
  이 비용이 뒤의 NoSQL 시대에 "분산 트랜잭션은 비싸다"의 근거가 된다.

**왜 중요했나** — 은행 이체·재고 차감처럼 "중간에 끊기면 큰일 나는" 작업을 RDBMS가 책임지고 보장하면서, 관계형 DB는 단순한 조회 도구가 아니라 **기업의 기간계 시스템을 맡을 신뢰성**을 갖추게 되었다.\
Jim Gray는 이 공로로 1998년 튜링상을 받았다.

### 클라이언트-서버 아키텍처 (1980년대)

**무엇** — 데이터베이스 엔진(서버)이 한쪽에서 데이터·트랜잭션·동시성을 책임지고, 응용 프로그램(클라이언트)은 네트워크 너머에서 SQL을 보내 결과만 받는 구조다.\
Sybase·Oracle 등이 1980년대에 이 모델을 전면화했다.

```text
메인프레임 한 덩어리            클라이언트-서버
+--------------------------+    +----------------------------+
| 응용 + 데이터 + 화면     |    | 응용 (PC/워크스테이션)     |
| 전부 한 기계 안에서 돈다 |    +-------------+--------------+
+--------------------------+                  |
                                              |  SQL 문장만 보낸다
                                              v
                                +----------------------------+
                                | DB 엔진 (중앙 서버)        |
                                | 데이터 / 트랜잭션 / 동시성 |
                                +----------------------------+
  기계 한 대가 전부를 감당한다    싼 PC 여럿 + 중앙 서버 한 대
```

**왜 이게 나은가** — 메인프레임에 모든 것을 올려두던 시대에서, 값싼 PC·워크스테이션을 클라이언트로 쓰고 데이터는 중앙 서버가 일관되게 관리하는 분산 구조로 옮겨갔다.\
SQL이 "클라이언트와 서버가 주고받는 표준 프로토콜" 역할을 하면서, 다양한 응용이 같은 DB에 동시에 붙을 수 있게 되었다.\
이 구조는 1990년대 3-tier 웹 아키텍처의 직접적인 토대가 된다.

**대가는 무엇인가** — 네트워크가 새 실패 지점이 된다.\
연결 수립 비용과 동시 연결 수 관리라는 문제가 생기는데, 그 답(커넥션 풀)은 다음 시대에 나온다.

## 왜 그렇게 갔나 — 남은 선택지와 트레이드오프

이 시대의 선택은 "전부 얻는 길"이 아니라 무언가를 내주고 무언가를 산 거래였다.

| 선택 | 얻은 것 | 내준 것 |
|---|---|---|
| 포인터 순회 → 선언적 질의 | 데이터 독립성, 저장 구조 변경에 응용이 안 깨짐 | 실행 경로를 사람이 직접 통제하지 못한다 |
| 사람이 최적화 → 옵티마이저가 최적화 | 사람보다 나은 실행 계획, 스키마 진화 가능 | 옵티마이저가 잘못 고르면 원인 파악이 어렵다 |
| 벤더 방언 → ANSI/ISO 표준 SQL | 공용어, 이론상 제품 교체 가능 | 표준은 최소 공통분모 — 실제 이식은 여전히 비싸다 |
| 느슨한 갱신 → ACID 트랜잭션 | 중간에 끊겨도 데이터를 믿을 수 있음 | 락·로그의 비용, 동시성 저하 |
| 단일 자원 → 2PC 분산 트랜잭션 | 여러 DB에 걸친 갱신도 한 덩어리로 | 코디네이터 장애 시 참가자가 묶인다 |

- 계층형·네트워크 모델을 계속 쓰는 선택지도 있었다.\
  실제로 성능만 보면 손으로 짠 포인터 순회가 초기에는 더 빨랐다.\
  System R이 증명해야 했던 것이 바로 "선언적으로 써도 쓸 만한 성능이 난다"였다.
- 질의어로 SQL이 아니라 QUEL을 쓰는 선택지도 있었다(Ingres).\
  결과적으로 표준이 된 것은 SQL이었다 — 원문은 어느 쪽이 왜 이겼는지는 말하지 않는다.

## 남긴 것 — 오늘 우리가 쓰는 것

관계형 시대가 정립한 세 기둥 — **관계 모델(테이블+선언적 질의)**, **표준 SQL**, **ACID 트랜잭션** — 은 이후 30년이 넘도록 데이터 관리의 기본 문법으로 남았다.\
1970년 Codd의 추상적인 수학 논문이 10년 만에 Oracle·DB2라는 제품이 되고, 다시 10년 만에 ISO 표준이 되어 산업 전체의 공용어로 굳었다.\
이론이 곧바로 거대한 산업을 만든 드문 사례다.

특히 "데이터가 **어떻게** 저장되는지 몰라도 **무엇을** 원하는지만 쓰면 된다"는 선언적 패러다임은 단순히 편의가 아니었다.\
질의 옵티마이저가 사람보다 나은 실행 계획을 자동으로 찾고, 스키마와 응용을 분리해 시스템을 오래 진화시킬 수 있게 한 구조적 혁신이었다.\
ACID와 2PC는 데이터베이스를 "조회 도구"에서 "기업의 신뢰를 떠받치는 기간 인프라"로 승격시켰다.

오늘 우리가 실제로 만지는 것들로 옮기면 이렇다.

- `SELECT ... FROM ... WHERE` 라는 문장 모양 자체가 SEQUEL/SQL의 유산이다.
- `PRIMARY KEY`·`FOREIGN KEY`·`CHECK` 는 SQL-89, 명시적 `JOIN` 문법과 서브쿼리는 SQL-92에서 왔다.
- `BEGIN` / `COMMIT` / `ROLLBACK` 과 격리 수준 이야기는 전부 ACID의 후손이다.
- 애플리케이션 서버가 DB에 커넥션을 맺고 SQL을 보내는 오늘의 구조는 1980년대 클라이언트-서버 그대로다.

이 시대가 남긴 자산은 현재진행형이다.\
Oracle·DB2·SQL Server·PostgreSQL(Ingres/Postgres 계보)·MySQL은 모두 이 시기의 직계 후손이다.\
2000년대 NoSQL과 2010년대 NewSQL/분산 SQL의 논쟁조차 "관계형이 세운 ACID·SQL을 어디까지 포기하거나 되살릴 것인가"라는, 이 시대가 정의한 좌표 위에서 벌어진다.\
관계형 DB 시대는 데이터베이스 역사의 출발점이자, 이후 모든 흐름이 끊임없이 되돌아보는 기준점이다.

## 용어 풀이

- **관계(relation) / 테이블** — 행과 열로 된 표 하나. 관계 모델의 기본 단위.
- **튜플(tuple)** — 표의 행 하나. `(1, Alice, 영업)` 같은 값의 묶음.
- **계층형 모델(hierarchical)** — 레코드를 포인터로 이어 트리 모양으로 저장하는 방식(IBM IMS, 1968).
- **네트워크 모델(CODASYL DBTG, 1969)** — 같은 포인터 방식이되 트리가 아닌 그물 모양을 허용한 것.
- **포인터(pointer)** — 다른 데이터가 있는 위치를 적어 둔 값.
- **navigational 접근** — 포인터를 순서대로 따라가며 원하는 레코드에 도달하는 방식.
- **선언적(declarative)** — 원하는 결과만 기술하는 방식. 반대는 과정을 기술하는 절차적(procedural).
- **데이터 독립성(data independence)** — 저장 구조가 바뀌어도 질의가 깨지지 않는 성질.
- **스키마(schema)** — 어떤 표에 어떤 열이 있는지를 적어 둔 설계도.
- **정규형(normal form)** — 중복과 불일치를 줄이기 위해 표를 쪼개는 규칙.
- **관계 대수(relational algebra)** — 선택(σ)·투영(π)·조인 등 연산자로 표에서 표를 만드는 체계.
- **관계 해석(relational calculus)** — 원하는 튜플의 조건을 논리식으로 선언하는 체계.
- **선택(σ, selection)** — 조건에 맞는 행을 고르는 연산.
- **투영(π, projection)** — 필요한 열만 남기는 연산.
- **조인(join)** — 두 표를 공통 값 기준으로 이어 붙이는 연산.
- **관계 완전성(relational completeness)** — 관계 해석으로 쓸 수 있는 질의를 모두 표현할 수 있는가의 기준.
- **질의 옵티마이저(query optimizer)** — 같은 결과를 내는 실행 방법 중 가장 싼 것을 고르는 부품.
- **비용 기반 옵티마이저(cost-based optimizer)** — 예상 비용을 숫자로 추정해 실행 계획을 고르는 방식.
- **락(lock)** — 동시 접근을 막기 위해 데이터를 잠그는 장치.
- **로그(log)** — 무엇을 바꿨는지 미리 적어 두어 장애 후 회복에 쓰는 기록.
- **트랜잭션(transaction)** — 여러 변경을 전부 되거나 전부 안 되게 묶는 단위.
- **ACID** — 원자성·일관성·격리성·지속성. 트랜잭션이 보장하는 네 성질.
- **직렬화 가능성(serializability)** — 동시 실행 결과가 차례로 실행한 어떤 순서의 결과와 같은 성질.
- **커밋(commit)** — 트랜잭션의 변경을 확정하는 선언. 반대는 취소(abort/rollback).
- **2단계 커밋(2PC)** — 준비 질의 → 전원 응답 → 커밋/취소 전파로 분산 트랜잭션을 원자적으로 끝내는 프로토콜.
- **부분 커밋(partial commit)** — 일부 노드만 커밋되어 데이터가 어긋난 상태. 2PC가 막으려는 것.
- **DDL / DML** — 표를 정의하는 문장 / 데이터를 다루는 문장.
- **무결성 제약(integrity constraint)** — 잘못된 데이터가 애초에 저장되지 못하게 하는 스키마 규칙.
- **이식성(portability)** — 같은 SQL이 다른 제품에서도 도는 성질.
- **클라이언트-서버** — 응용은 SQL만 보내고, 데이터·트랜잭션은 중앙 서버가 책임지는 구조.
- **QUEL** — Ingres가 SQL 대신 쓴 자체 질의어.
- **BCNF** — Boyce-Codd 정규형. 이름의 'B'가 Raymond F. Boyce다.
