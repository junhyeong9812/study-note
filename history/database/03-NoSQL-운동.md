# NoSQL 운동 (2004~2015)

> 원본: `~/project/database-history/03-NoSQL-운동.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-18).\
> 연도·인명·논문명·표준번호·코드는 원문 그대로다. 더 압축된 원문이 필요하면 원본 문서를 보면 된다.\
> 용어 블록의 「예:」, 「대가는 무엇인가」, 트레이드오프 표는 원문에 없는 보충 설명이다.

## 한눈에 — 쉽게 말하면

**NoSQL = 모든 일을 다 하는 만능 공구 하나 대신, 일마다 전용 공구를 골라 쓰기 시작한 것.**

- 30년 동안은 공구가 하나였다.\
  관계형 DB는 나사도 조이고 못도 박고 자르기도 하는 만능 공구였고, 실제로 웬만한 일은 그것으로 됐다.
- 그런데 일감이 너무 커졌다.\
  하루에 못을 1억 개 박아야 하는 현장에서는, 만능 공구의 "정확히 한 번에 딱 맞게"라는 미덕이 오히려 발목을 잡았다.
- 그래서 몇몇 현장이 **일부러 기능을 뺀 전용 공구**를 만들었다.\
  조인도 빼고, 트랜잭션도 빼고, 스키마도 뺐다 — 대신 수천 대로 늘려도 안 무너지게 했다.
- 중요한 건 "관계형이 틀렸다"가 아니다.\
  "한 가지 모델이 모든 워크로드를 감당할 수는 없다"는 **다중 저장소(polyglot persistence)** 사고로의 전환이었다.

```text
2004년 이전                        2004년 이후
데이터 = 관계형 테이블             워크로드를 먼저 보고 저장소를 고른다
        |                                  |
        v                          +-------+-------+-------+-------+
   RDBMS 한 종류                   |       |       |       |       |
   (전부 여기에 넣는다)            키-값   문서   컬럼    그래프   RDBMS
                                   캐시   프로필  시계열  소셜    결제
```

이 공구함이 **똑같은 구조로** 오늘의 백엔드 아키텍처다.\
세션과 랭킹은 Redis, 상품 카탈로그는 MongoDB, 로그·시계열은 Cassandra, 결제는 여전히 PostgreSQL에 둔다.\
"저장소를 하나만 고른다"가 아니라 "워크로드마다 고른다"가 이 시대의 결론이다.

> **폴리글랏 퍼시스턴스(polyglot persistence, 다중 저장소)** — 한 서비스 안에서 용도마다 다른 종류의 데이터 저장소를 함께 쓰는 설계.\
> 예: 로그인 세션은 Redis에, 주문 내역은 관계형 DB에 두면 각각의 강점만 쓴다.

> **워크로드(workload)** — 그 데이터에 실제로 어떤 요청이 얼마나 오는가의 성질. 읽기·쓰기 비율, 질의 모양, 규모, 요구하는 일관성.\
> 예: "키 하나로 단건 조회만 초당 10만 건"과 "임의 조건으로 집계"는 완전히 다른 워크로드다.

시대 정보를 한 줄씩 정리하면 이렇다.

- 기간: 대략 2004년(Google의 사내 인프라 구축) ~ 2015년(NewSQL·관리형 클라우드 DB로 흡수되며 "운동"으로서는 일단락)
- 분수령이 된 논문: Bigtable(OSDI 2006), Dynamo(SOSP 2007), CAP 정리 형식 증명(2002)
- 용어 "NoSQL"의 현대적 등장: 2009년 6월 11일 샌프란시스코 밋업 (Johan Oskarsson 주최, Eric Evans 명명 제안). 의미는 "No SQL"이 아니라 "**Not Only SQL**"로 곧 재해석됨
- 주도 주체: 웹스케일 기업의 자체 인프라 팀(Google·Amazon·Facebook·LinkedIn)과, 그들의 논문을 오픈소스로 구현한 커뮤니티·스타트업(10gen·Basho·DataStax 등)
- 결과물 유형: 키-값(Key-Value) / 문서(Document) / 컬럼 패밀리(Wide-Column) / 그래프(Graph)의 4대 계열

## 시대 배경 — 그전에는 어땠나

2000년대 중반, 웹 서비스의 규모가 단일 관계형 데이터베이스(RDBMS)가 다룰 수 있는 한계를 넘어서기 시작했다.\
세 가지 압력이 동시에 작용했다.

**① 웹스케일(web-scale) 트래픽.**\
아마존·구글·페이스북 같은 서비스는 수천만~수억 사용자의 요청을 24시간 처리해야 했다.\
전통적 RDBMS의 확장 전략은 **수직 확장(scale-up)** — 더 비싼 단일 서버로 갈아타는 것 — 이었는데, 이는 비용이 기하급수적으로 늘고 결국 물리적 상한에 부딪힌다.\
필요한 것은 평범한 상용 하드웨어(commodity hardware) 수백~수천 대로 부하를 나누는 **수평 확장(scale-out)** 이었다.

```text
수직 확장 (scale-up)                    수평 확장 (scale-out)
+----------------------------------+    +------------------------------------+
| 서버 1대를 더 비싼 것으로 교체   |    | 평범한 서버(commodity)를 여러 대로 |
| [ 소형 ] -> [ 중형 ] -> [ 대형 ] |    | [서버][서버][서버][서버][서버]     |
| 값은 기하급수적으로 오른다       |    | 같은 값싼 기계를 계속 더한다       |
+----------------------------------+    +------------------------------------+
  비용이 폭증하고 결국 물리 상한          대수를 늘리면 처리량도 늘어난다
```

왼쪽은 한 대의 성능에 한계가 걸리고, 오른쪽은 대수를 늘리는 만큼 늘어난다 — 대신 "여러 대가 서로 다른 값을 볼 수 있다"는 새 문제가 생긴다.

> **수직 확장(scale-up) / 수평 확장(scale-out)** — 한 대를 더 좋게 만드는 것 / 여러 대로 나누는 것.\
> 예: CPU를 64코어로 바꾸는 게 수직 확장, 8코어 서버 8대에 데이터를 쪼개 넣는 게 수평 확장이다.

**② 빅데이터(big data)의 부피·속도·다양성.**\
웹 로그·클릭스트림·센서·소셜 그래프처럼 정형화되지 않고, 끊임없이 쏟아지며, 페타바이트 규모로 누적되는 데이터가 등장했다.\
미리 정한 테이블 스키마에 맞춰 정규화하는 모델은 이런 반정형(semi-structured) 데이터와 빠른 스키마 변경 요구에 잘 맞지 않았다.

> **반정형(semi-structured) 데이터** — 표처럼 열이 고정되어 있지는 않지만, 나름의 구조(중첩된 키-값)는 있는 데이터.\
> 예: 사용자마다 들어 있는 필드가 제각각인 JSON 로그.

**③ 관계형 모델의 분산 한계.**\
RDBMS의 강점인 **조인·트랜잭션·강한 일관성**은 단일 노드 안에서는 우아하다.\
그러나 여러 노드에 데이터를 쪼개 놓으면(sharding) 분산 조인과 분산 트랜잭션(2PC)의 비용이 폭발한다.\
한 노드가 죽거나 네트워크가 끊겼을 때 전체 시스템을 멈추지 않으려면, 역설적으로 "모든 노드가 항상 같은 값을 본다"는 보장을 약화시켜야 했다.

> **샤딩(sharding)** — 데이터를 기준값으로 쪼개서 서로 다른 서버에 나눠 담는 것.\
> 예: 사용자 ID를 10으로 나눈 나머지에 따라 10대의 서버에 흩뿌린다.

> **2PC(2단계 커밋)** — 여러 노드/자원에 걸친 변경을 "전부 되거나 전부 안 되게" 묶는 프로토콜. 준비를 묻고, 전원이 yes일 때만 커밋을 전파한다.\
> 예: 노드 100대에 걸친 트랜잭션이면 100대 전부의 답을 기다려야 하고, 한 대만 느려도 전체가 느려진다.

이 압력에 가장 먼저 답한 것은 학계가 아니라 **인터넷 기업의 인프라 팀**이었다.\
구글은 GFS(2003)·Bigtable(2006)·MapReduce(2004)로 자체 스택을 쌓았다.\
아마존은 장바구니가 절대 멈추면 안 된다는 요구에서 Dynamo(2007)를 만들었다.\
이들이 자신의 설계를 **논문**으로 공개하자, 오픈소스 커뮤니티가 그 청사진을 구현하면서 NoSQL 운동이 점화되었다.

## 이론적 토대 — 무엇을 근거로 포기했나

NoSQL은 단순한 엔지니어링 유행이 아니라, 분산 시스템 이론의 결론을 데이터 저장소 설계에 적용한 것이다.\
네 개의 기둥이 있다.

### CAP 정리 (Brewer, 2000 / Gilbert·Lynch 형식 증명, 2002)

**무엇** — 에릭 브루어(Eric Brewer)는 2000년 PODC(분산 컴퓨팅 원리 심포지엄) 기조연설에서, 분산 데이터 시스템은 다음 세 보장을 **동시에 모두** 만족할 수 없다는 추측(conjecture)을 제시했다.

- **C**onsistency(일관성): 모든 노드가 같은 시점에 같은 데이터를 본다(선형화 가능성).
- **A**vailability(가용성): 살아 있는 모든 노드가 모든 요청에 (실패가 아닌) 응답을 돌려준다.
- **P**artition tolerance(분할 내성): 노드 간 네트워크 메시지가 임의로 유실돼도 시스템이 계속 동작한다.

2002년 세스 길버트(Seth Gilbert)와 낸시 린치(Nancy Lynch)가 이를 형식적으로 증명해 **정리(theorem)** 로 굳혔다.

> **네트워크 분할(partition)** — 네트워크 문제로 노드들이 서로 연락이 끊겨, 두 무리로 갈라진 상태.\
> 예: 데이터센터 A와 B를 잇는 회선이 끊기면, 양쪽 다 살아는 있는데 서로의 변경을 모른다.

> **선형화 가능성(linearizability)** — 쓰기가 끝난 그 순간부터 모두가 새 값을 본다는, 가장 강한 형태의 일관성.\
> 예: 서울에서 잔액을 바꾸자마자 부산에서 읽어도 바뀐 값이 나온다.

**왜 이게 중요한가** — 핵심은 흔히 "셋 중 둘만 고를 수 있다"로 요약되지만, 더 정확한 해석은 이렇다.\
**분산 시스템에서 네트워크 분할(P)은 선택지가 아니라 언젠가 반드시 일어나는 현실**이다.\
그러므로 분할이 일어난 *그 순간* 설계자는 **C와 A 사이에서** 양자택일해야 한다.\
강한 일관성을 지키려면 분할 동안 일부 요청을 거절(가용성 포기)해야 한다.\
항상 응답하려면 노드마다 값이 잠시 갈라지는 것(일관성 포기)을 허용해야 한다.

```text
네트워크 분할 발생
(P는 피할 수 없음)
        |
        +-- 일관성 우선 (CP) --> 응답을 보류/거절해서라도
        |                        모든 노드가 같은 값 유지
        |                        예: HBase, MongoDB(기본)
        |
        +-- 가용성 우선 (AP) --> 일단 응답하고
                                 나중에 값을 수렴시킴
                                 예: Dynamo, Cassandra, Riak
```

그림 해설 (한 단계씩):

- 분기점은 "분할이 일어났을 때"다 — 분할이 없을 때의 동작은 CAP가 말하지 않는다.
- 위쪽(CP)은 답이 확실하지 않으면 아예 답하지 않는 쪽을 택한다.
- 아래쪽(AP)은 일단 답하고, 갈라진 값은 나중에 맞추는 쪽을 택한다.

전통 RDBMS는 단일 노드(또는 동기 복제)를 전제로 **CA**에 가깝게 동작했다.\
NoSQL의 다수, 특히 Dynamo 계열은 분할 앞에서 **AP** 를 선택했다.\
이 선택을 정당화하는 일관성 모델이 BASE다.

### BASE — ACID의 대안 (Dan Pritchett, eBay, ACM Queue 2008)

**무엇** — 전통 RDBMS의 트랜잭션 보장은 **ACID**(Atomicity·Consistency·Isolation·Durability)다.\
Dan Pritchett는 그 정반대 극을 의도적으로 화학 은유로 묶어 **BASE** 라 명명했다.\
(산(acid)과 염기(base)를 빗댄 말장난이다.)

- **B**asically **A**vailable: 부분 실패가 있어도 시스템 전체는 (성능이 떨어질지언정) 항상 응답한다.
- **S**oft state: 외부 입력이 없어도 상태가 (복제 수렴·만료 등으로) 시간에 따라 변할 수 있다 — 즉 어느 한 순간의 상태가 "확정"이 아니다.
- **E**ventual consistency(최종 일관성): 새 쓰기가 멈추면, 시간이 지나면서 모든 복제본이 결국 같은 값으로 수렴한다.

> **최종 일관성(eventual consistency)** — 지금 당장은 노드마다 값이 다를 수 있지만, 쓰기가 멎으면 결국 모두 같은 값이 된다는 보장.\
> 예: 좋아요 수가 새로고침할 때마다 잠깐 다르게 보이다가, 몇 초 뒤 전부 같은 숫자로 맞춰진다.

```text
ACID — 쓰는 순간 맞춘다                 BASE — 나중에 맞춘다
+----------------------------------+    +----------------------------------+
| 쓰기 -> 모든 복제본 확정 -> 응답 |    | 쓰기 -> 일단 응답 -> 뒤에서 수렴 |
| 분할이 나면 응답을 미룬다        |    | 분할이 나도 계속 받는다          |
| 항상 같은 값이 보인다            |    | 잠깐 값이 갈라질 수 있다         |
+----------------------------------+    +----------------------------------+
  틀린 값은 안 보이지만 멈출 수 있다      멈추지 않지만 잠깐 옛 값이 보인다
```

**왜 이게 나은가 / 대가는 무엇인가** — ACID가 "쓰기 순간 모든 것이 일관됨"을 보장한다면, BASE는 "지금은 갈라져 있어도 결국 맞춰진다"를 약속한다.\
장바구니에 담은 물건이 잠깐 옆 복제본에 안 보이는 것은 비즈니스적으로 감당 가능하다.\
그러나 그 때문에 "추가" 버튼이 멈추는 것은 매출 손실이다.\
이 트레이드오프가 AP/BASE 선택의 실제 논리였다.

### Bigtable 논문 (Google, OSDI 2006)

**무엇** — Fay Chang 등이 발표한 **"Bigtable: A Distributed Storage System for Structured Data"** 는 GFS 위에서 페타바이트 데이터를 상용 서버 수천 대로 다루는 분산 저장소를 기술했다.\
핵심 데이터 모델은 관계형 테이블이 아니라 **희소(sparse)·다차원·정렬된 맵**이다.

```
(row key, column family:column qualifier, timestamp) → value
```

- 행 키로 정렬·범위 분할(태블릿)되고, 컬럼은 **컬럼 패밀리** 로 묶인다. 같은 셀의 여러 버전을 타임스탬프로 보관한다.
- 행마다 다른 컬럼 집합을 가질 수 있어 **스키마가 유연**하고, 빈 셀은 저장 공간을 차지하지 않는다(희소성).
- 저장 엔진은 **LSM 트리**(메모리의 memtable → 디스크의 SSTable, 순차 쓰기 후 컴팩션) 구조로, 대량 쓰기에 최적화됐다.

> **희소(sparse)** — 대부분의 칸이 비어 있는 상태. 비어 있는 칸은 아예 저장하지 않는다.\
> 예: 열이 100만 개인 표라도 어떤 행은 실제로 3개 열만 채워져 있고, 그 3개만 디스크를 쓴다.

LSM 트리가 "왜 대량 쓰기에 강한가"는 그림이 빠르다.

```text
쓰기 --> memtable (메모리 안의 정렬된 맵)
             |  가득 차면 통째로 디스크에 "순차" 기록
             v
        SSTable 1   SSTable 2   SSTable 3  ...  (한 번 쓰면 안 고친다)
             |           |           |
             +---- 컴팩션(백그라운드로 병합) ----+
                              |
                              v
                 합쳐진 SSTable (중복과 삭제 표시가 정리됨)
```

그림 해설 (한 단계씩):

- 쓰기는 디스크의 임의 위치를 고치지 않고, 메모리에만 쌓는다 — 그래서 쓰기가 빠르다.
- 메모리가 차면 통째로 한 번에 순차 기록한다 — 디스크가 가장 잘하는 방식이다.
- 대가 — 같은 키의 값이 여러 SSTable에 흩어지므로, 읽기는 여러 곳을 뒤져야 하고 컴팩션이라는 뒷정리 비용이 계속 든다.

> **LSM 트리(Log-Structured Merge tree)** — 변경을 메모리에 모았다가 디스크에 순차로 쏟아붓고, 나중에 병합해 정리하는 저장 구조.\
> 예: 메모에 계속 덧붙여 쓰다가 나중에 한 번에 정서하는 방식 — 쓸 때 빠르고, 읽을 때는 여러 장을 봐야 한다.

이 논문은 **컬럼 패밀리** 계열(HBase·Cassandra의 저장 모델)의 직접적 청사진이 되었다.

### Dynamo 논문 (Amazon, SOSP 2007)

**무엇** — Giuseppe DeCandia 등의 **"Dynamo: Amazon's Highly Available Key-value Store"** 는 "항상 켜져 있는(always-on)" 키-값 저장소를 목표로, **가용성을 위해 일관성을 희생**하는 일군의 분산 기법을 한데 엮었다.\
이 기법 세트가 이후 AP 계열 NoSQL의 표준 도구상자가 되었다.

- **일관 해싱(consistent hashing)**: 키를 해시 링에 배치해, 노드 추가·제거 시 재배치되는 데이터를 최소화 — 무중단 수평 확장의 토대.
- **복제 + 정족수(quorum)**: 각 키를 N개 노드에 복제하고, 읽기 R개·쓰기 W개의 정족수로 일관성/가용성을 **튜닝 가능한 다이얼**로 노출(`W+R>N`이면 강한 읽기에 근접).
- **벡터 클록(vector clock)**: 동시 쓰기로 갈라진 버전을 탐지하고, 충돌은 애플리케이션이 해소(예: 장바구니는 합집합으로 병합).
- **힌티드 핸드오프·머클 트리·가십(gossip)**: 일시적 노드 장애를 우회하고, 복제본 간 차이를 백그라운드로 수복하며, 멤버십을 분산적으로 전파.

일관 해싱이 무엇을 아끼는지가 이 목록의 핵심이다.

```text
해시 링을 일자로 펼쳐 놓으면 (0에서 최대값까지, 끝은 다시 0으로 이어진다)

  0 ------------------------------------------------ 최대값 -> 다시 0
      key1     [노드 A]     key2     [노드 B]     key3     [노드 C]
        |__ 맡김 __^          |__ 맡김 __^          |__ 맡김 __^

규칙 : 키는 오른쪽(시계 방향)으로 가다 처음 만나는 노드가 맡는다

노드 D를 [노드 A]와 [노드 B] 사이에 끼워 넣으면?
  key2 만 D로 옮겨간다. key1, key3 은 그대로 자리를 지킨다.
  반대로 "키를 노드 수로 나눈 나머지"로 배치했다면,
  노드 수가 3에서 4로 바뀌는 순간 거의 모든 키의 담당이 바뀐다.
```

> **일관 해싱(consistent hashing)** — 키와 노드를 같은 원형 공간에 올려두고, 키를 시계 방향 첫 노드에 맡기는 배치법.\
> 예: 서버를 3대에서 4대로 늘려도 옮겨야 하는 데이터가 전체의 일부뿐이라, 서비스를 멈추지 않고 증설할 수 있다.

> **정족수(quorum)** — 몇 개 노드가 답해야 그 읽기/쓰기를 성공으로 칠지 정한 수. N=복제본 수, W=쓰기 정족수, R=읽기 정족수.\
> 예: N=3, W=2, R=2로 두면 `W+R>N` 이라 읽기와 쓰기가 최소 한 노드에서 겹쳐, 최신 값을 볼 가능성이 높아진다.

> **벡터 클록(vector clock)** — 어느 노드가 몇 번째로 고쳤는지를 함께 적어 두어, 두 버전이 "순서 관계인지 동시 충돌인지"를 구분하는 장치.\
> 예: 두 기기에서 같은 장바구니를 동시에 고치면 충돌로 표시되고, 앱이 두 목록을 합쳐서 해소한다.

> **가십(gossip) 프로토콜** — 노드들이 무작위로 서로에게 상태를 조금씩 퍼뜨려, 중앙 관리자 없이 전체가 소식을 알게 하는 방식.\
> 예: 새 노드가 들어오면 몇 다리 건너 몇 초 안에 모든 노드가 그 사실을 알게 된다.

Bigtable이 "구조와 저장"의 청사진이었다면, Dynamo는 "**분산·가용성·최종 일관성**"의 청사진이었다.\
Cassandra는 이 둘을 합쳐 — Dynamo의 분산 구조 + Bigtable의 컬럼 패밀리 모델 — 만들어졌다.

## 무엇이 바뀌었나 — 4대 계열

NoSQL은 단일 제품이 아니라 **데이터 모델에 따른 4개 계열**의 묶음이다.\
각 계열은 "어떤 질문에 빠르게 답하도록 데이터를 배치하는가"가 다르다.

### ① 키-값 저장소 (Key-Value)

**무엇** — 가장 단순한 모델이다.\
데이터를 불투명한 값으로 보고 **키로만** 넣고 뺀다.\
조회 패턴이 "기본 키 단건 조회"로 고정될 때 극단적으로 빠르고 확장이 쉽다.

> **불투명한 값(opaque value)** — DB가 그 안을 들여다보지 않는 값. 그냥 바이트 덩어리로 넣고 꺼낸다.\
> 예: 세션 정보를 통째로 넣어 두면, "로그인한 지 1시간 넘은 세션만 찾기" 같은 질의는 DB가 못 해 준다.

**Dynamo (Amazon, 2007 — 사내)**: 위 논문의 원조 구현.\
외부 공개 제품은 아니었지만(후일 관리형 DynamoDB로 부활), 설계가 곧 표준이 되었다.

**Redis (Salvatore Sanfilippo "antirez", 2009)**: 단순 KV를 넘어선 **자료구조 서버**다.\
값이 문자열뿐 아니라 리스트·해시·셋·정렬 셋·비트맵·HyperLogLog일 수 있다.\
모든 데이터를 **메모리**에 두어 마이크로초 단위 지연을 낸다.\
캐시·세션·실시간 랭킹·큐로 폭넓게 쓰이며, NoSQL 운동의 가장 대중적인 산물 중 하나다.

```
# Redis: 값이 단순 문자열이 아니라 자료구조
SET user:1000:name "Alice"          # 문자열
INCR page:home:views                # 원자적 카운터
LPUSH queue:jobs "job-42"           # 리스트(큐)
ZADD leaderboard 1500 "Alice"       # 정렬 셋(실시간 랭킹)
ZREVRANGE leaderboard 0 9 WITHSCORES # 상위 10명 즉시 조회
EXPIRE user:1000:name 3600          # TTL — soft state의 예
```

> **TTL(Time To Live)** — 데이터가 자동으로 사라지기까지의 시간.\
> 예: 세션에 TTL 3600을 걸면 한 시간 뒤 아무도 지우지 않아도 없어진다 — BASE의 soft state가 이런 모습이다.

**Riak (Basho, 2009)**: Dynamo 논문을 거의 그대로 오픈소스로 구현한 분산 KV다.\
일관 해싱·정족수·벡터 클록을 충실히 따른 대표적 **AP/고가용** 저장소로, "한 노드가 죽어도 전체는 계속 쓰기를 받는다"는 Dynamo의 약속을 실현했다.

**대가는 무엇인가** — 값 안을 못 본다.\
"금액이 1만원 넘는 주문"을 찾으려면 모든 키를 꺼내 앱이 직접 훑어야 한다.

### ② 문서 저장소 (Document)

**무엇** — 값이 불투명하지 않고 **JSON/BSON 문서**(중첩 가능한 키-값 트리)다.\
문서 내부 필드로 질의·인덱싱할 수 있어, 키-값의 단순함과 관계형의 질의력 사이 절충점에 있다.\
객체를 테이블 여러 개로 쪼개지 않고 한 문서에 통째로 저장해 **객체-관계 임피던스 불일치**를 줄인다.

> **객체-관계 임피던스 불일치(impedance mismatch)** — 프로그램의 객체(중첩 구조)와 관계형 표(평평한 행)가 모양이 달라서, 오갈 때마다 쪼개고 다시 조립해야 하는 마찰.\
> 예: 주문 객체 하나를 저장하려고 주문·주문항목·주소 세 표에 나눠 넣고, 읽을 때 다시 조인해 합친다.

**MongoDB (10gen, 2009)**: NoSQL 운동에서 가장 널리 채택된 문서 DB다.\
스키마가 유연하고(같은 컬렉션의 문서마다 필드가 다를 수 있음), 풍부한 질의·보조 인덱스·집계 파이프라인, 그리고 샤딩 기반 수평 확장을 제공한다.\
"개발자 친화성"(JSON 그대로 저장·질의)이 채택의 큰 동력이었다.

> **보조 인덱스(secondary index)** — 기본 키가 아닌 다른 필드로도 빨리 찾게 해 주는 색인.\
> 예: `address.city` 에 인덱스를 걸면 "서울 사는 사용자"를 전체 훑기 없이 찾는다.

```javascript
// MongoDB: 객체를 쪼개지 않고 중첩 문서로 통째 저장
db.users.insertOne({
  _id: 1000,
  name: "Alice",
  emails: ["alice@example.com"],          // 배열
  address: { city: "Seoul", zip: "04524" }, // 중첩 문서
  orders: [ { id: 42, total: 19000 } ]       // 1:N을 한 문서에 임베드
});
// 문서 내부 필드로 질의 — 키-값과 달리 값 안을 본다
db.users.find({ "address.city": "Seoul", "orders.total": { $gt: 10000 } });
```

**CouchDB (Damien Katz, 2005 / Apache 2008)**: Erlang으로 작성된 문서 DB다.\
HTTP/REST API와 JSON을 1급으로 채택했다.\
**다중 마스터 복제와 충돌 해소**가 강점이라 오프라인-우선·모바일 동기화에 적합했다.\
MVCC로 읽기 동안 잠금이 없다.

> **다중 마스터 복제(multi-master replication)** — 아무 복제본에나 쓸 수 있고, 나중에 서로 맞추는 방식.\
> 예: 비행기 안에서 오프라인으로 메모를 고쳐도, 착륙 후 연결되면 서버와 양방향으로 합쳐진다.

**대가는 무엇인가** — 문서 경계를 넘는 조인과 여러 문서에 걸친 트랜잭션이 약하다(초기엔 아예 없었다).\
그래서 "어디까지 한 문서에 묻을 것인가"가 설계의 핵심 결정이 된다.

### ③ 컬럼 패밀리 / 와이드 컬럼 (Wide-Column)

**무엇** — Bigtable 모델의 계열이다.\
행마다 컬럼이 수만~수백만 개일 수 있고, 컬럼 패밀리 단위로 디스크에 모여 저장된다.\
**쓰기 처리량과 시계열·대규모 테이블**에 강하다.

> **컬럼 패밀리(column family)** — 함께 읽힐 컬럼들을 한 묶음으로 정해 디스크에도 붙여 저장하는 단위.\
> 예: 「프로필」 패밀리와 「접속 로그」 패밀리를 나눠 두면, 프로필만 읽을 때 로그는 디스크에서 건드리지도 않는다.

**Cassandra (Facebook, 2008 오픈소스 / Apache)**: Dynamo의 co-author인 Avinash Lakshman가 페이스북 인박스 검색을 위해 Prashant Malik과 만들었다.\
**Dynamo의 분산·AP 구조 + Bigtable의 컬럼 패밀리 데이터 모델**을 결합한 것이 핵심이다.\
마스터가 없는(masterless) 대칭 구조로 단일 장애점이 없고, 쓰기 가용성과 선형적 수평 확장이 뛰어나다.\
튜닝 가능한 일관성(`ONE`/`QUORUM`/`ALL`)을 노출한다.

> **단일 장애점(SPOF, single point of failure)** — 그것 하나가 죽으면 전체가 멈추는 부품.\
> 예: master 한 대가 쓰기를 전담하는 구조에서는 그 master가 SPOF다. Cassandra는 모든 노드가 같은 역할이라 SPOF가 없다.

```sql
-- Cassandra(CQL): 조인이 없으므로 "질의 패턴에 맞춰" 테이블을 설계한다
CREATE TABLE sensor_data (
  sensor_id  text,
  ts         timestamp,
  value      double,
  PRIMARY KEY (sensor_id, ts)   -- 파티션 키 + 클러스터링 키
) WITH CLUSTERING ORDER BY (ts DESC);  -- 최신 데이터부터 순차 저장
-- 한 센서의 최근 측정값을 디스크 순차 읽기로 빠르게
SELECT value FROM sensor_data WHERE sensor_id = 'A12' LIMIT 100;
```

> **파티션 키 / 클러스터링 키** — 데이터를 어느 노드에 둘지 정하는 키 / 그 안에서 어떤 순서로 줄 세울지 정하는 키.\
> 예: `sensor_id` 로 노드를 정하고 `ts DESC` 로 줄 세우면, 한 센서의 최근 100건이 디스크에 이미 붙어 있어 순차로 읽힌다.

**HBase (2008)**: Bigtable 논문을 거의 그대로 따른 오픈소스 구현으로, **Hadoop 생태계(HDFS 위)** 에서 동작한다.\
마스터(HMaster)·리전 서버 구조의 **CP** 지향이라 강한 일관성을 제공한다.\
MapReduce·Spark와 결합한 대규모 배치·분석 파이프라인의 저장 계층으로 자리 잡았다.

**대가는 무엇인가** — 조인이 없으므로 질의 패턴을 **먼저** 정하고 그에 맞춰 테이블을 설계해야 한다.\
나중에 새로운 각도의 질문이 생기면 테이블을 새로 만들어 데이터를 다시 채워야 한다.

### ④ 그래프 데이터베이스 (Graph)

**무엇** — 데이터를 **노드(정점)와 관계(엣지)** 로 모델링하고, 관계 자체를 1급 시민으로 저장한다.\
소셜 그래프·추천·사기 탐지·경로 탐색처럼 "연결을 따라가는" 질의가 본질인 도메인에 특화됐다.

> **노드 / 엣지** — 점과 선. 노드는 사람·상품 같은 개체, 엣지는 "친구다"·"샀다" 같은 관계다.\
> 예: Alice(노드) -[:FRIEND]-> Bob(노드)에서 화살표가 엣지다.

**Neo4j (2007)**: 가장 대표적인 **네이티브 그래프** DB다.\
저장 계층까지 그래프 구조로 구현해, 관계 순회가 인접 포인터를 따라가는 상수 시간 연산("index-free adjacency")이다.\
RDBMS에서 다단계 조인으로 표현해야 할 "친구의 친구의 친구" 같은 질의를, 선언적 패턴 언어 **Cypher** 로 간결하게 표현한다.

```text
관계형 — 친구의 친구의 친구           그래프 — 인접 포인터 순회
+--------------------------------+    +-------------------------------+
| 친구 표를 자기 자신과 3번 조인 |    | Alice -> Bob -> Carol -> Dave |
| JOIN 1  -> 중간 결과 한 겹     |    | 각 노드에서 이웃 포인터를     |
| JOIN 2  -> 그 결과에 또 한 겹  |    | 그대로 따라간다               |
| JOIN 3  -> 또 한 겹            |    | 방문한 노드 수에만 비례한다   |
| 깊이마다 중간 결과가 곱해진다  |    +-------------------------------+
+--------------------------------+
  깊이가 늘수록 비용이 폭발한다         깊이가 늘어도 비용이 평탄하다
```

> **index-free adjacency** — 이웃을 찾을 때 인덱스를 뒤지지 않고, 노드가 들고 있는 포인터를 바로 따라가는 저장 방식.\
> 예: "Alice의 친구"를 찾을 때 친구 표 전체를 검색하는 게 아니라, Alice 레코드에 붙은 링크를 바로 읽는다.

```cypher
// Neo4j(Cypher): 관계를 따라가는 다단계 순회가 조인 폭증 없이 표현된다
MATCH (me:User {name: 'Alice'})-[:FRIEND]->()-[:FRIEND]->(fof:User)
WHERE NOT (me)-[:FRIEND]->(fof) AND me <> fof
RETURN fof.name AS 추천친구, count(*) AS 공통친구수
ORDER BY 공통친구수 DESC;
```

관계형에서 이런 질의는 자기 조인을 깊이만큼 반복해야 하고, 깊이가 커질수록 비용이 폭발한다.\
그래프 DB는 그 비용을 관계 순회로 평탄화한다.

**대가는 무엇인가** — 그래프는 본질적으로 서로 얽혀 있어서, 여러 서버로 쪼개기(샤딩)가 대단히 어렵다.\
"어디서 잘라도 선이 잘린다"는 것이 이 계열의 근본 한계다.

### 4대 계열 트레이드오프

```text
키-값                        --> 단순, 초고속, 확장 용이
Redis·Riak·Dynamo                <-> 값 내부 질의 불가

문서                         --> 유연한 스키마, 필드 질의
MongoDB·CouchDB                  <-> 다중 문서 조인 약함

컬럼 패밀리                  --> 쓰기 처리량, 수평 확장
Cassandra·HBase                  <-> 질의 패턴에 종속된 설계

그래프                       --> 관계 순회 강력
Neo4j                            <-> 대규모 분산 샤딩 난해
```

| 계열 | 데이터 모델 | 강점 | 약점·비용 | 전형적 용도 |
|------|------------|------|-----------|-------------|
| 키-값 | 키 → 불투명 값(또는 자료구조) | 단순함, 마이크로초 지연, 손쉬운 수평 확장 | 값 **내부**로 질의 불가, 관계 표현 없음 | 캐시·세션·카운터·큐 |
| 문서 | 키 → JSON/BSON 문서 | 유연한 스키마, 필드 질의·보조 인덱스, 객체 매핑 자연스러움 | 문서 간 조인·다문서 트랜잭션이 약함(초기엔 부재) | 카탈로그·콘텐츠·사용자 프로필 |
| 컬럼 패밀리 | (행키, 컬럼패밀리:컬럼, ts) → 값 | 막대한 쓰기 처리량, 선형 수평 확장, 시계열 | 질의 패턴을 미리 정해 테이블을 설계해야 함(ad-hoc 질의 약함) | 시계열·로그·IoT·대규모 이벤트 |
| 그래프 | 노드·엣지(속성 포함) | 깊은 관계 순회, 패턴 매칭이 직관적 | 대규모 분산 샤딩이 본질적으로 어려움 | 소셜·추천·사기탐지·지식그래프 |

**공통의 거래(trade)** — 네 계열 모두, 관계형이 주던 **범용 ad-hoc 질의(임의 조인·집계)** 와 **강한 트랜잭션 일관성**을 일정 부분 내주었다.\
그 대가로 **특정 접근 패턴에서의 확장성·성능·유연성**을 얻었다.\
NoSQL DB는 "무엇이든 질의할 수 있는" 범용 도구가 아니라, **알려진 접근 패턴에 데이터 배치를 맞춘** 특화 도구다.

> **ad-hoc 질의** — 미리 계획하지 않은, 그때그때 떠오른 조건으로 던지는 질의.\
> 예: "지난달 가입자 중 주문이 3건 이상이고 서울에 사는 사람"을 즉석에서 물어보는 것.

## 왜 그렇게 갔나 — 남은 선택지와 트레이드오프

### 관계형을 버린 이유

1. **수평 확장의 필요**: 관계형의 조인·트랜잭션은 단일 노드를 전제로 설계됐다.\
   데이터를 수천 노드에 흩뿌리면 분산 조인·2PC의 조율 비용이 가용성과 처리량을 갉아먹는다.\
   조인·강한 일관성을 **포기**하는 것이 곧 수평 확장의 자유를 사는 값이었다.
2. **CAP의 현실 직시**: 분할(P)은 대규모 분산에서 반드시 일어난다.\
   "장바구니가 멈추면 안 된다"는 비즈니스 요구는, 분할 동안 C 대신 A를 택하라(AP/BASE)는 결론으로 이어졌다.
3. **스키마 경직성**: 빠르게 변하는 웹 제품에서, 마이그레이션 없이 필드를 더하고 빼는 유연성이 개발 속도를 높였다.
4. **임피던스 불일치 완화**: 객체를 테이블 여러 개로 정규화·재조립하는 ORM의 마찰을, 문서·KV 모델이 줄였다.

### 그러나 — 운동이 드러낸 한계

NoSQL은 만능이 아니었고, 2010년대 중반에 그 비용이 분명해졌다.

- **최종 일관성은 공짜가 아니다**: 충돌 해소·읽기 시점 불일치 처리를 **애플리케이션이 떠안아야** 했다.\
  ACID가 DB 안에서 처리하던 복잡성이 앱 코드로 새어 나왔다.
- **조인·트랜잭션의 부재가 아팠다**: 많은 워크로드가 실제로는 다중 엔티티 일관성을 필요로 했다.\
  "질의 패턴에 맞춰 데이터를 미리 복제(denormalize)"하는 설계는 쓰기 증폭과 데이터 정합성 부담을 낳았다.
- **"NoSQL이라서 빠르다"는 오해**: 많은 경우 빠름의 원천은 모델이 아니라 *포기한 보장*이었다.\
  같은 보장을 요구하면 비슷한 비용이 돌아왔다.
- **성숙도 격차**: 도구·운영·인재 생태계가 RDBMS의 수십 년 축적을 따라잡지 못했다.

> **비정규화(denormalize)** — 조인을 피하려고 같은 값을 여러 곳에 일부러 중복해 두는 것.\
> 예: 주문 행에 사용자 이름을 복사해 두면 읽을 때 조인이 없지만, 이름이 바뀌면 복사본 전부를 고쳐야 한다.

> **쓰기 증폭(write amplification)** — 한 번의 논리적 변경이 실제로는 여러 번의 쓰기로 불어나는 현상.\
> 예: 질의 패턴 3가지를 위해 같은 데이터를 표 3개에 복제해 두면, 쓰기 1건이 물리적으로 3건이 된다.

이 반성은 두 방향의 수렴으로 이어졌다.

- ① RDBMS가 JSON 컬럼·논리적 복제·읽기 복제본을 흡수하며 NoSQL의 유연성 일부를 받아들였다.
- ② **NewSQL**(Google Spanner·CockroachDB 등)이 "수평 확장 + ACID/강한 일관성"을 동시에 노린다고 선언했다.

NoSQL이 던진 진짜 메시지는 "관계형을 버려라"가 아니라, **워크로드마다 다른 저장소를 골라 쓰라(polyglot persistence)** 였다.

## 남긴 것 — 오늘 우리가 쓰는 것

NoSQL 운동은 데이터 저장에 대한 업계의 기본 가정을 영구히 바꿨다.

- **"하나의 DB가 모든 것을 한다"의 종말** — 2004년 이전엔 "데이터 = 관계형 테이블"이 거의 자동이었다.\
  이후엔 워크로드(접근 패턴·일관성 요구·규모)를 먼저 보고 저장소를 고르는 것이 상식이 되었다.
- **분산 시스템 개념의 대중화** — CAP·정족수·일관 해싱·벡터 클록·최종 일관성·LSM 트리 같은, 한때 논문 속 용어이던 개념들이 평범한 백엔드 엔지니어의 어휘가 되었다.
- **클라우드 관리형 DB로의 흡수** — 운동의 산물 다수가 관리형 서비스로 재탄생했다(DynamoDB·Bigtable·Cosmos DB·관리형 MongoDB/Redis/Cassandra).\
  운영 부담이 큰 분산 저장소를, 클라우드가 버튼 하나로 제공하게 되었다.
- **데이터 모델의 영구한 다양화** — 문서·그래프·시계열·검색 등 특화 모델이 1급 선택지로 정착했다.\
  관계형은 사라지지 않았지만, 더 이상 유일한 정답도 아니게 되었다.

오늘 우리가 실제로 만지는 것들로 옮기면 이렇다.

- 세션·랭킹·큐를 Redis에 두는 관행, `EXPIRE` 로 TTL을 거는 습관이 이 시대의 것이다.
- Cassandra·DynamoDB에서 "질의를 먼저 정하고 테이블을 나중에 만든다"는 순서가 그대로 남아 있다.
- RocksDB·LevelDB를 비롯해 오늘날 수많은 저장 엔진이 Bigtable이 대중화한 LSM 트리 위에 서 있다.
- "이 API는 읽은 직후 쓴 값이 보이나요?"라는 질문 자체가 최종 일관성이 남긴 어휘다.

NoSQL은 결국 관계형을 대체하지 못했고, 그럴 의도도 점차 옅어졌다.\
대신 그것이 남긴 것은 **트레이드오프를 의식적으로 선택하는 문화**다.\
CAP가 강제하는 선택을 외면하지 않고, "이 워크로드에서 우리는 무엇을 포기하고 무엇을 얻는가"를 설계 시점에 묻는 태도였다.\
그것이 이 운동의 가장 오래 남은 유산이다.

## 용어 풀이

- **NoSQL** — "No SQL"이 아니라 "Not Only SQL". 2009년 6월 11일 샌프란시스코 밋업에서 현대적 의미로 명명됐다.
- **폴리글랏 퍼시스턴스(polyglot persistence)** — 용도마다 다른 저장소를 함께 쓰는 설계.
- **워크로드(workload)** — 그 데이터에 실제로 오는 요청의 성질(읽기/쓰기 비율, 질의 모양, 규모, 일관성 요구).
- **수직 확장(scale-up)** — 서버 한 대를 더 좋은 것으로 교체해 성능을 올리는 것.
- **수평 확장(scale-out)** — 평범한 서버를 여러 대로 늘려 부하를 나누는 것.
- **commodity hardware** — 특별할 것 없는 값싼 범용 서버.
- **반정형(semi-structured) 데이터** — 열이 고정돼 있지 않지만 나름의 구조가 있는 데이터(JSON 등).
- **샤딩(sharding)** — 데이터를 기준값으로 쪼개 서로 다른 서버에 나눠 담는 것.
- **2PC(2단계 커밋)** — 여러 노드/자원에 걸친 변경을 전부/전무로 묶는 프로토콜.
- **CAP 정리** — 분할이 일어난 순간 일관성(C)과 가용성(A) 중 하나를 골라야 한다는 정리.
- **네트워크 분할(partition)** — 네트워크가 끊겨 노드들이 서로 연락이 안 되는 상태.
- **선형화 가능성(linearizability)** — 쓰기가 끝난 순간부터 모두가 새 값을 보는 가장 강한 일관성.
- **CP / AP** — 분할 시 일관성을 지키는 설계 / 가용성을 지키는 설계.
- **ACID** — 원자성·일관성·격리성·지속성. 관계형 트랜잭션의 보장.
- **BASE** — Basically Available · Soft state · Eventual consistency. ACID의 반대 극.
- **최종 일관성(eventual consistency)** — 쓰기가 멎으면 결국 모든 복제본이 같은 값으로 수렴한다는 보장.
- **soft state** — 외부 입력 없이도 시간에 따라 상태가 변할 수 있음(복제 수렴·TTL 만료 등).
- **Bigtable** — Google이 2006년 OSDI에 발표한 분산 저장소. 컬럼 패밀리 계열의 청사진.
- **희소(sparse)** — 빈 칸이 대부분이고, 빈 칸은 저장하지 않는 성질.
- **LSM 트리** — 메모리에 모았다가 디스크에 순차로 쏟아붓고 나중에 병합(컴팩션)하는 저장 구조.
- **memtable / SSTable** — LSM 트리에서 메모리의 정렬된 맵 / 한 번 쓰면 고치지 않는 디스크 파일.
- **컴팩션(compaction)** — 흩어진 SSTable들을 백그라운드로 병합해 중복·삭제를 정리하는 작업.
- **Dynamo** — Amazon이 2007년 SOSP에 발표한 고가용 키-값 저장소. AP 계열의 청사진.
- **일관 해싱(consistent hashing)** — 키와 노드를 원형 공간에 올려 시계 방향 첫 노드가 키를 맡는 배치법.
- **정족수(quorum)** — 읽기/쓰기를 성공으로 칠 최소 응답 노드 수(N·W·R).
- **벡터 클록(vector clock)** — 버전이 순서 관계인지 동시 충돌인지 구분하는 장치.
- **힌티드 핸드오프(hinted handoff)** — 담당 노드가 잠시 죽었을 때 다른 노드가 대신 받아 뒀다가 나중에 넘겨주는 기법.
- **머클 트리(Merkle tree)** — 복제본 간 차이를 적은 통신으로 찾아내는 해시 트리.
- **가십(gossip)** — 노드들이 무작위로 서로에게 상태를 퍼뜨려 중앙 관리자 없이 소식을 공유하는 방식.
- **불투명한 값(opaque value)** — DB가 안을 들여다보지 않는 값. 키-값 모델의 기본 전제.
- **TTL(Time To Live)** — 데이터가 자동으로 사라지기까지의 시간.
- **객체-관계 임피던스 불일치** — 객체의 중첩 구조와 관계형 표의 평평한 구조가 달라 생기는 변환 마찰.
- **보조 인덱스(secondary index)** — 기본 키가 아닌 필드로도 빠르게 찾게 해 주는 색인.
- **다중 마스터 복제(multi-master)** — 아무 복제본에나 쓸 수 있고 나중에 맞추는 복제 방식.
- **컬럼 패밀리(column family)** — 함께 읽힐 컬럼들을 묶어 디스크에도 붙여 저장하는 단위.
- **파티션 키 / 클러스터링 키** — 데이터를 어느 노드에 둘지 정하는 키 / 그 안의 정렬 순서를 정하는 키.
- **masterless** — 모든 노드가 같은 역할이라 쓰기를 전담하는 특별한 노드가 없는 구조.
- **단일 장애점(SPOF)** — 그것 하나가 죽으면 전체가 멈추는 부품.
- **노드 / 엣지** — 그래프의 점(개체)과 선(관계).
- **index-free adjacency** — 이웃을 인덱스 검색 없이 포인터로 바로 따라가는 그래프 저장 방식.
- **Cypher** — Neo4j의 선언적 그래프 패턴 질의 언어.
- **ad-hoc 질의** — 미리 계획하지 않고 그때그때 던지는 임의 조건의 질의.
- **비정규화(denormalize)** — 조인을 피하려고 같은 값을 여러 곳에 일부러 중복해 두는 것.
- **쓰기 증폭(write amplification)** — 한 번의 논리적 변경이 여러 번의 물리적 쓰기로 불어나는 현상.
- **NewSQL** — 수평 확장과 ACID/강한 일관성을 동시에 노린 흐름(Google Spanner·CockroachDB 등).
