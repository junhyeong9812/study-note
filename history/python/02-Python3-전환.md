## 한눈에 — 쉽게 말하면

원문이 제목 아래에 적은 한 줄 요약은 이것이다.

> Python이 의도적으로 하위 호환을 깨고 언어의 근본 설계 결함을 바로잡은 사건. 2008년 12월 Python 3.0 출시로 시작해, 2 vs 3 양분 시대의 길고 고통스러운 마이그레이션을 거쳐, 2020년 1월 1일 Python 2.7의 수명 종료(EOL)로 마침내 끝난 11년짜리 대전환이다.

이 11년을 하나의 비유로 읽으면 **강 건너편으로 마을을 통째로 옮기는 일**이다.\
강 저쪽에 더 나은 터가 생겼는데, 이쪽 집들을 그대로 들어 옮길 수는 없다.\
그래서 다리를 놓고, 짐을 옮겨 주는 수레를 만들고, 양쪽에서 다 쓸 수 있는 짐을 따로 싸고 — 그러고도 마을 전체가 다 건너는 데 11년이 걸린다.\
**Python 2에서 3으로 가는 길도 똑같은 구조다** — 원문 자신이 2.6/2.7을 "다리(bridge) 릴리스"·"3로 가는 다리"라 부르고, 이 시기를 "이를 건너기 위한 도구들이 등장했다"고 적는다.

본문 흐름에 쓰는 비유는 이 강 건너기 하나뿐이다.

| 비유 | 실체 |
|------|------|
| 강 이쪽 마을 / 저쪽 터 | Python 2 / Python 3 |
| 두 마을을 잇는 다리 | Python 2.6 · 2.7 — 원문 표현으로 "3로 가는 다리" |
| 짐을 기계로 옮겨 주는 수레 | `2to3` — "Python 2 소스를 받아 3 문법으로 **기계적으로 변환**" |
| 양쪽 마을에서 다 쓸 수 있게 싼 짐 | `__future__`·`six` — "하나의 코드베이스가 2와 3 양쪽에서 동작"(single-source) |
| 마을 전체가 다 건너가는 데 걸린 시간 | 11년 — 2008년 12월 3.0 출시부터 2020년 1월 1일 2.7 EOL까지 |

초보자가 가장 자주 하는 오해부터 짚어 두면 이렇다.\
"2와 3은 호환되지 않으니 모두 코드를 처음부터 새로 썼다"가 아니다.\
원문은 "이를 건너기 위한 도구들이 등장했다"고 적고, 이어지는 네 절에서 그 도구들을 든다.

- **2.6 / 2.7** — "`python -3` 플래그를 주면 3에서 깨질 코드에 경고를 띄워 주었고, 3의 새 기능 일부를 미리 백포트했다".
- **`__future__` 임포트** — "한 파일 단위로 '미래의 동작'을 미리 켜는 장치"라서, "Python 2.7에서도 Python 3의 의미로 동작하는 코드를 짤 수 있었다".
- **`six` 라이브러리** — "2와 3의 차이를 런타임에 흡수해 주는 호환 계층 라이브러리".
- **`2to3` 자동 변환기** — "정형적 변환을 자동으로 처리했다".

그리고 이 네 가지로도 안 되는 자리가 어디였는지를 원문이 따로 못 박는데, 그것이 아래 「`2to3` 자동 변환기」 절의 **함정**이다.

## 시대 정보

*(아래 여섯 줄은 원문의 불릿 그대로다.)*

- 시작: Python 3.0 (코드네임 "Python 3000" / "Py3k") 출시 — 2008년 12월 3일
- 다리(bridge) 릴리스: Python 2.6 (2008년 10월) — 3.0과 같은 시기에 출시되어 마이그레이션 경로 제공
- 마지막 2.x: Python 2.7 — 2010년 7월 3일 출시, 2.x 계열의 최종 버전 (Python 2.8은 만들어지지 않음)
- 종결: Python 2.7 EOL — 2020년 1월 1일 (최종 릴리스 2.7.18은 2020년 4월)
- 개발 주체: Python Software Foundation, BDFL Guido van Rossum 주도
- 성격: Python 역사상 **최초의 의도적 하위 비호환 릴리스**

> **하위 호환(backward compatibility)** — 새 판을 내놓아도 예전에 쓰던 코드가 그대로 돌아가는 성질.\
> 예: 원문이 3.0을 "최초의 의도적 하위 비호환 릴리스"라 부르는 것은, Python 2용으로 짜 둔 코드가 3에서 그대로 돌지 않는 일이 의도적으로 일어났다는 뜻이다.

> **EOL(End Of Life, 수명 종료)** — 만든 쪽이 더 이상 손대지 않겠다고 선언한 시점.\
> 예: 원문이 적은 2.7의 EOL은 2020년 1월 1일이고, 그 뒤로 "보안 패치도, 버그 수정도, CVE 대응도 더 이상 제공되지 않는다".

## 시대적 배경

Python 2는 오랜 시간에 걸쳐 기능이 겹겹이 쌓이면서, "같은 일을 하는 방법이 여러 개"인 영역이 늘어나고 초기 설계 단계의 실수가 굳어져 있었다.\
가장 뼈아픈 것은 **문자열 모델**이었다.\
Python 2의 `str`은 사실상 바이트 열(byte string)이면서 동시에 텍스트로도 취급되었고, 별도의 `unicode` 타입이 따로 있었다.\
둘 사이의 암묵적 변환은 ASCII를 가정했기 때문에, 비ASCII 데이터를 만나는 순간 그 악명 높은 `UnicodeDecodeError`가 엉뚱한 곳에서 터졌다.\
전 세계가 UTF-8로 옮겨가던 시대에 이 모델은 더 이상 버틸 수 없었다.

> **바이트 열(byte string) / 텍스트** — 0~255 사이 숫자가 줄지어 있는 날것의 데이터 / 사람이 읽는 글자.\
> 예: 원문이 문제 삼는 것이 바로 Python 2의 `str`이 이 둘을 겸했다는 점이다 — "사실상 바이트 열이면서 동시에 텍스트로도 취급되었고".

> **암묵적 변환(implicit conversion)** — 적어 놓지 않았는데 언어가 알아서 바꿔 주는 것.\
> 예: 원문이 든 것이 Python 2에서 `str`과 `unicode`를 섞어 쓸 때 일어나던 변환이고, 그 변환이 "ASCII를 가정했기 때문에" 비ASCII 데이터에서 터졌다.

Guido van Rossum은 이 문제들을 "호환성을 유지한 채로는 고칠 수 없는, 언어의 근본 설계 버그"로 규정했다.\
그래서 그는 완전히 새 언어를 만드는 대신, **딱 한 번 하위 호환을 깨는 것을 허용**하고 그 기회에 묵은 설계 실수를 정리하기로 했다.\
이 방침과 변경 목록은 PEP 3000(Python 3.0 Plans)과 PEP 3100(Miscellaneous Python 3.0 Plans)에 정리되었고, 비호환 변경을 다루는 절차 자체는 PEP 3002로 규정되었다.\
핵심 원칙은 Python의 선(禪)에 나오는 한 줄, **"There should be one obvious way to do it"** — 중복된 옛 방식을 걷어내자는 것이었다.

## 3.0이 깬 것들 (의도적 비호환)

### print 문 → print() 함수 (PEP 3105)

Python 2에서 `print`는 특별한 **문(statement)** 이었다. Python 3에서는 평범한 **함수**가 되었다.

> **문(statement) / 함수(function)** — 언어 문법에 박혀 있어 그 모양으로만 쓸 수 있는 것 / 이름 뒤에 괄호를 붙여 값을 넘겨 부르는 것.\
> 예: 아래 「도입 전」의 `print "Hello", name`에 원문이 "print는 문법 키워드"라는 주석을 달았고, 「도입 후」의 `print("Hello", name)`에는 "평범한 함수 호출"이라 적었다.

도입 전 (Python 2):
```python
print "Hello", name        # print는 문법 키워드
print >> sys.stderr, "err"  # 특수한 리다이렉트 문법
```

도입 후 (Python 3):
```python
print("Hello", name)                 # 평범한 함수 호출
print("err", file=sys.stderr)        # 인자로 제어
print("a", "b", sep="-", end="")     # sep/end 같은 키워드 인자 활용
```
함수가 되면서 구분자(`sep`), 끝 문자(`end`), 출력 대상(`file`)을 인자로 깔끔하게 제어할 수 있게 되었다.\
동시에 Python 2 코드의 `print "..."`는 Python 3에서 즉시 `SyntaxError`를 내며, 이 변경이 두 버전 비호환의 가장 눈에 띄는 상징이 되었다.

> **`SyntaxError`** — 실행을 시작하기도 전에, 문장의 모양 자체가 문법에 맞지 않아 나는 오류.\
> 예: 원문이 적은 대로 Python 2 코드의 `print "..."`를 Python 3에 주면 "즉시 `SyntaxError`"가 난다 — 값이 이상해지는 게 아니라 아예 시작하지 못한다.

### str / bytes 분리 — 전환의 진짜 핵심

Python 3는 **텍스트와 이진 데이터를 타입 수준에서 완전히 분리**했다.\
모든 텍스트는 유니코드 `str`이고, 바이트 데이터는 `bytes`다.\
둘 사이에는 암묵적 변환이 없으며, 반드시 인코딩을 명시해야 한다.

두 버전의 문자열 모델을 나란히 놓으면 이렇다.

```text
Python 2 의 문자열 모델                 Python 3 의 문자열 모델
+---------------------------------+     +---------------------------------+
| str     = 사실상 바이트 열이면서|     | str   = 모든 텍스트(유니코드)   |
|           동시에 텍스트로도 취급|     | bytes = 바이트 데이터           |
| unicode = 별도의 타입           |     |                                 |
|                                 |     | 둘 사이에는 암묵적 변환이 없고, |
| 둘 사이의 암묵적 변환은         |     | 반드시 인코딩을 명시해야 한다   |
| ASCII 를 가정                   |     |                                 |
+---------------------------------+     +---------------------------------+
 비ASCII 데이터를 만나는 순간           인코딩 오류가 데이터가 들어오고
 UnicodeDecodeError 가                  나가는 "경계에서" 명시적으로
 엉뚱한 곳에서 터졌다                   드러나게 되었다
```

- 두 칸의 대립축은 원문의 대립축 그대로다 — **암묵적 변환이 있느냐, 없느냐**.
- 왼쪽 칸과 그 아래 문장은 원문 「시대적 배경」 절의 문장들이고, 오른쪽 칸과 그 아래 문장은 이 절의 문장들이다.
- 왼쪽 칸은 타입이 `str`·`unicode` 둘, 오른쪽 칸도 `str`·`bytes` 둘이다.\
  달라진 것은 개수가 아니라 **무엇과 무엇으로 갈렸는지와, 그 사이를 언어가 알아서 건너느냐**다.

도입 전 (Python 2):
```python
s = "café"          # str = 바이트 열 (인코딩에 의존)
u = u"café"         # 별도의 unicode 타입
s + u               # 필요하면 암묵적으로 ASCII 디코드 시도 → 종종 UnicodeError
```

도입 후 (Python 3):
```python
s = "café"                  # 항상 유니코드 텍스트 (str)
b = b"caf\xc3\xa9"          # 바이트는 별도 타입 (bytes)
s.encode("utf-8")           # str -> bytes (인코딩 명시)
b.decode("utf-8")           # bytes -> str (디코딩 명시)
s + b                       # TypeError — 암묵적 변환 없음
```
이 분리는 "ASCII가 기본"이라는 가정을 언어에서 추방했다.

> **인코딩(encoding) / 디코딩(decoding)** — 글자를 바이트로 바꾸는 일 / 바이트를 글자로 되돌리는 일.\
> 예: 위 코드에 원문이 달아 둔 주석 그대로다 — `s.encode("utf-8")`이 "str -> bytes (인코딩 명시)", `b.decode("utf-8")`이 "bytes -> str (디코딩 명시)".

> **`TypeError`** — 값의 타입이 그 연산에 맞지 않아 나는 오류.\
> 예: 위 코드의 `s + b`가 그것이고, 원문 주석대로 "암묵적 변환 없음"이라서 언어가 알아서 맞춰 주지 않고 오류를 낸다.

**대가는 무엇인가** — 원문이 비용으로 적은 문장은 이것이다.

> 덕분에 인코딩 오류가 데이터가 들어오고 나가는 **경계에서** 명시적으로 드러나게 되었지만, 동시에 마이그레이션이 가장 어려운 지점이기도 했다. `str`이 바이트라는 가정에 기대 짠 코드는 기계적 변환 도구로는 고칠 수 없고 사람이 직접 의미를 따져야 했기 때문이다.

### 정수 나눗셈 (PEP 238)

`/` 연산자가 항상 실수 나눗셈(true division)을 하도록 바뀌었다. 정수 몫이 필요하면 `//`(floor division)를 쓴다.

도입 전 (Python 2):
```python
5 / 2     # 2   (정수끼리는 정수 나눗셈)
5.0 / 2   # 2.5
```

도입 후 (Python 3):
```python
5 / 2     # 2.5  (항상 실수 나눗셈)
5 // 2    # 2    (몫이 필요하면 명시적으로 //)
```

> **실수 나눗셈(true division) / floor division** — 소수점 아래까지 살려 나누는 것 / 나눈 뒤 아래로 버려 몫만 남기는 것.\
> 예: 위 두 코드에서 같은 `5 / 2`가 Python 2에서는 `2`, Python 3에서는 `2.5`이고, Python 3에서 `2`를 얻으려면 `5 // 2`라고 적어야 한다.

**함정** — 원문이 위험으로 적은 문장은 이것이다.

> 이 변경은 문법 오류를 내지 않고 **조용히 결과 값만 바꾸기 때문에** 특히 위험했다. 같은 코드가 두 버전에서 다른 숫자를 내놓아도 예외가 없으니, 통계·금융 계산 등에서 발견하기 어려운 버그의 단골 원인이 되었다.

`print` 문은 Python 3에서 "즉시 `SyntaxError`"를 내지만, `/`는 아무 말 없이 다른 숫자를 돌려준다 — 원문이 이 절을 "특히 위험했다"고 적은 이유가 그 차이다.

### int / long 통합

Python 2의 `int`(고정 크기)와 `long`(임의 정밀도, `100L` 같은 리터럴)이 하나의 `int`로 합쳐졌다.\
Python 3의 정수는 메모리가 허락하는 한 무한히 커질 수 있으며, 오버플로를 신경 쓸 필요가 없어졌다.

```python
# Python 3: 별도 long 타입도, 100L 리터럴도 없음
2 ** 100   # 1267650600228229401496703205376 — 자동으로 큰 정수
```

> **임의 정밀도(arbitrary precision) / 오버플로(overflow)** — 자릿수 제한 없이 수를 담는 것 / 담을 수 있는 크기를 넘어서는 것.\
> 예: 위 코드의 `2 ** 100`이 원문 주석대로 "자동으로 큰 정수"가 되고, 원문 표현으로 "메모리가 허락하는 한 무한히 커질 수 있"다.

### 그 밖의 정리

- `xrange()` 제거 — `range()`가 게으른 이터레이터(Python 2의 xrange)처럼 동작.
- `dict.keys()`/`values()`/`items()`가 리스트가 아닌 **뷰(view)** 반환.
- 비교 연산이 엄격해짐 — `1 < "a"` 같은 서로 다른 타입 간 비교는 `TypeError`.
- 예외 문법 통일 — `except Exception, e:` → `except Exception as e:`.
- `<>` 연산자 폐기 (`!=`만 사용).

> **게으른 이터레이터(lazy iterator)** — 값을 미리 다 만들어 두지 않고, 달라고 할 때마다 하나씩 내놓는 것.\
> 예: 원문이 든 것이 `range()`다 — Python 3의 `range()`가 "Python 2의 xrange처럼" 그렇게 동작한다.

## 왜 굳이 깨는 변경을 했나

"호환성을 깨면 사용자가 떠나지 않을까"라는 우려에도 불구하고 Python 진영이 이 길을 택한 이유는 분명했다.

1. **유니코드는 점진적으로 고칠 수 없었다.** `str`이 바이트이면서 텍스트인 이중성은 언어의 가장 깊은 곳에 박혀 있었다. 이를 바로잡으려면 문자열의 의미 자체를 바꿔야 했고, 그것은 정의상 하위 호환을 깰 수밖에 없었다.
2. **중복 제거 — "한 가지 분명한 방법".** `print` 문 vs `print` 함수, `range` vs `xrange`, 정수 vs 실수 나눗셈처럼 같은 일을 하는 옛길과 새길이 공존하면 학습자의 인지 부하가 커진다. Guido는 초심자가 처음 배울 때의 부담을 줄이는 것을 명시적 목표로 삼았다.
3. **초기 설계 실수의 청산.** 예외 문법, 타입 간 비교 규칙 등 오래전 결정이 굳어진 부분을, "딱 한 번 깨는" 이 기회에 한꺼번에 정리했다.

*(위 세 항목은 원문이 나란히 든 이유 셋 그대로다 — 원문은 이 중 어느 것이 더 큰 이유인지 순위를 매기지 않는다.)*

대신 Python 진영은 무책임하게 깨지 않았다.\
PEP 3002는 **모든 비호환 변경은 PEP로 문서화하고, Python 2 코드의 문제 지점을 식별할 수 있는 도구를 동반해야 한다**고 규정했다.\
그 도구가 바로 다음의 마이그레이션 생태계다.

## 2 vs 3 대분열과 마이그레이션의 고통

3.0이 나왔다고 세상이 곧장 옮겨간 것은 아니다.\
수많은 라이브러리가 아직 Python 2 전용이었기 때문에, 의존성 하나라도 3을 지원하지 않으면 전체 프로젝트가 옮겨갈 수 없었다.\
결과적으로 **두 버전이 10년 넘게 공존하는 대분열**이 벌어졌고, 이를 건너기 위한 도구들이 등장했다.

> **의존성(dependency)** — 내 프로그램이 돌아가려고 끌어다 쓰는 남의 코드.\
> 예: 원문이 적은 상황이 이것이다 — "의존성 하나라도 3을 지원하지 않으면 전체 프로젝트가 옮겨갈 수 없었다".

### Python 2.6 / 2.7 — 다리 역할

2.6과 2.7은 3.0과 같은 시기·이후에 나오면서 **3로 가는 다리** 역할을 하도록 설계되었다.\
`python -3` 플래그를 주면 3에서 깨질 코드에 경고를 띄워 주었고, 3의 새 기능 일부를 미리 백포트했다.

> **백포트(backport)** — 새 버전에 들어간 것을 옛 버전에도 가져다 넣는 것.\
> 예: 원문이 적은 대로 2.6·2.7이 "3의 새 기능 일부를 미리 백포트했다".

### `__future__` 임포트

한 파일 단위로 "미래의 동작"을 미리 켜는 장치다. 이것을 쓰면 Python 2.7에서도 Python 3의 의미로 동작하는 코드를 짤 수 있었다.

```python
# 파일 맨 위에서 Python 3 동작을 미리 활성화
from __future__ import print_function   # print를 함수로
from __future__ import division         # / 를 실수 나눗셈으로
from __future__ import unicode_literals # "..." 를 유니코드로
from __future__ import absolute_import  # 절대 임포트 우선
```
이 덕분에 **하나의 코드베이스가 2와 3 양쪽에서 동작**(single-source)하게 만드는 전략이 가능해졌다.

- 위 네 줄은 앞에서 본 3.0의 변경들과 하나씩 짝이 맞는다 — `print_function`은 「print 문 → print() 함수」, `division`은 「정수 나눗셈」, `unicode_literals`는 「str / bytes 분리」가 다룬 그 문제다.
- 짝이 맞는 것은 이 셋까지다. `absolute_import`가 다루는 임포트 규칙은 원문이 3.0 변경 절에서 따로 설명하지 않는다.

> **single-source(하나의 소스)** — 버전별로 파일을 따로 두지 않고, 같은 소스 하나가 양쪽에서 돌게 하는 방식.\
> 예: 원문이 적은 대로 `__future__`를 쓰면 "하나의 코드베이스가 2와 3 양쪽에서 동작"한다 — 2용 파일과 3용 파일을 따로 관리하지 않아도 된다.

### `six` 라이브러리

2와 3의 차이를 런타임에 흡수해 주는 호환 계층 라이브러리다.\
이름은 "2 × 3 = 6".\
버전별로 갈라지는 모듈 경로·함수 이름을 통일된 인터페이스로 감쌌다.

```python
import six

if six.PY2:
    ...
text = six.text_type      # 2에서는 unicode, 3에서는 str
six.print_("hello")       # 양쪽에서 동작하는 print
from six.moves import range, zip   # 이동된 표준 라이브러리 경로 흡수
```
(비슷한 목적의 `future` 라이브러리도 널리 쓰였다.)

> **호환 계층(compatibility layer)** — 서로 다른 두 환경 사이에 끼워 넣어, 위에서는 한 가지 방법으로만 쓰게 해 주는 코드.\
> 예: 위 코드의 `six.text_type`이 그것이다 — 원문 주석대로 "2에서는 unicode, 3에서는 str"인데, 쓰는 쪽은 `six.text_type` 하나만 적으면 된다.

### `2to3` 자동 변환기

Python 2 소스를 받아 3 문법으로 **기계적으로 변환**해 주는 표준 도구다.\
`print` 문 → 함수, `except ..., e` → `except ... as e` 같은 정형적 변환을 자동으로 처리했다.

```bash
$ 2to3 -w myscript.py    # 변환 결과를 파일에 직접 기록(-w)
```

**함정** — 원문이 한계로 적은 문장은 이것이다.

> 다만 `2to3`는 만능이 아니었다. **`str`이 바이트라는 가정에 의존하거나 암묵적 ASCII 인코딩에 기댄 로직은 기계가 판별할 수 없어 반드시 사람이 손봐야 했다.** 마이그레이션 고통의 대부분이 바로 이 "도구로 안 되는" 부분, 즉 텍스트/바이트 경계의 재설계에서 나왔다.

이 함정이 가르는 두 쪽을 나란히 놓으면 이렇다.

```text
2to3 가 자동으로 처리한 것              기계가 판별할 수 없던 것
+-------------------------------+      +----------------------------------+
| print 문 → 함수               |      | str 이 바이트라는 가정에         |
|                               |      | 의존하는 로직                    |
| except ..., e                 |      |                                  |
|   → except ... as e           |      | 암묵적 ASCII 인코딩에 기댄 로직  |
+-------------------------------+      +----------------------------------+
 "정형적 변환을 자동으로 처리했다"       "반드시 사람이 손봐야 했다"
                                        — 마이그레이션 고통의 대부분이
                                          여기서 나왔다
```

- 두 칸의 대립축은 원문의 대립축 그대로다 — **기계가 판별할 수 있느냐 없느냐**.
- 네 칸 안의 항목은 원문이 각 쪽에 든 것 그대로다. 왼쪽은 "정형적 변환"의 예 둘, 오른쪽은 "기계가 판별할 수 없"는 것 둘이다.
- 두 칸 아래 따옴표도 원문 문장이다. 오른쪽에 화살표를 그리지 않은 이유는, 원문이 이 둘을 대비로 적었을 뿐 한쪽이 다른 쪽으로 이어진다고 적지는 않았기 때문이다.

### 생태계의 더딘 이동

NumPy, Django, Twisted 같은 핵심 라이브러리가 3를 지원하기까지 수년이 걸렸고, 커뮤니티는 주요 패키지의 Python 3 지원 현황을 추적표("Python 3 Wall of Superpowers")로 공개하며 이동을 독려했다.\
리눅스 배포판들도 오랫동안 `python` = `python2`를 유지했기 때문에, 시스템 차원의 전환은 더욱 더뎠다.

## 종결 — 2.7 EOL (2020년 1월 1일)

Python 2.7은 2.x 계열의 마지막 버전으로 못 박혔다(PEP 404, "Python 2.8은 없다").\
원래 2.7의 수명 종료는 2015년으로 예정되어 있었지만, 아직 3로 옮기지 못한 사용자들의 부담을 덜어 주기 위해 **EOL이 5년 뒤인 2020년으로 연장**되었다(PEP 373).

그리고 마침내 **2020년 1월 1일, Python 2.7은 공식 수명을 다했다.**\
이후로는 보안 패치도, 버그 수정도, CVE 대응도 더 이상 제공되지 않는다.\
코드 동결은 그날 이루어졌고, 마지막 정리 릴리스 2.7.18이 2020년 4월에 나오며 2 계열의 역사는 완전히 닫혔다.\
11년에 걸친 대전환이 끝나는 순간이었다.

> **CVE(Common Vulnerabilities and Exposures)** — 공개적으로 알려진 보안 취약점에 붙는 번호와 그 목록.\
> 예: 원문이 적은 대로 2020년 1월 1일 이후로는 2.7에 대해 "CVE 대응도 더 이상 제공되지 않는다" — 새 취약점이 알려져도 고쳐 주지 않는다는 뜻이다.

## 영향과 의의

*(이 편의 「남긴 것」에 해당한다 — 아래 두 불릿과 마지막 문단은 전부 원문 「영향과 의의」의 것이다.)*

Python 3 대전환은 소프트웨어 역사에서 손꼽히는 **장기 호환성 단절 사례**로 남았다. 교훈은 양면적이다.

- **얻은 것**: 일관된 유니코드 텍스트 모델, 중복이 정리된 문법, 임의 정밀도 정수, 그리고 이후 폭발적으로 성장할 `asyncio`·타입 힌트·f-string 같은 현대적 기능을 받아들일 깨끗한 토대를 얻었다. 오늘날 데이터 과학과 AI 시대의 Python은 이 전환 없이는 불가능했다.
- **치른 값**: 분열은 예상보다 훨씬 길었다. "두어 해면 옮겨가겠지"라던 전망과 달리 11년이 걸렸고, 그 사이 양쪽을 모두 지원하느라 들인 커뮤니티의 노력은 막대했다. 이 경험은 이후 다른 언어·프레임워크가 "절대 print 함수 같은 식으로 호환을 깨지 말라"는 반면교사로 두고두고 인용된다.

결국 이 전환의 본질은 단순한 버전 업그레이드가 아니라, **언어가 자신의 근본 설계를 다시 쓰기 위해 치른 대가**였다.\
무엇이 언제·왜 갈렸는지를 한 줄로 요약하면 이렇다 — 2008년, 유니코드를 제대로 다루기 위해 Python은 자신의 과거와의 호환을 의도적으로 끊었고, 그 비용을 2020년까지 나눠 치렀다.

## 용어 풀이

- **하위 호환(backward compatibility)** — 새 판을 내도 예전 코드가 그대로 도는 성질. 3.0은 이것을 의도적으로 깬 최초의 릴리스다.
- **바이트 열(byte string) / 텍스트** — 날것의 바이트 데이터 / 사람이 읽는 글자. Python 2의 `str`이 이 둘을 겸한 것이 전환의 발단이다.
- **암묵적 변환(implicit conversion)** — 적지 않았는데 언어가 알아서 바꿔 주는 것. Python 2에서는 ASCII를 가정했고, Python 3에는 없다.
- **인코딩(encoding) / 디코딩(decoding)** — 글자를 바이트로 / 바이트를 글자로 바꾸는 일. Python 3는 이것을 반드시 명시하게 한다.
- **`UnicodeDecodeError`** — 비ASCII 데이터를 만났을 때 Python 2의 암묵적 변환이 터뜨리던 오류.
- **`SyntaxError`** — 문장의 모양이 문법에 맞지 않아 실행 전에 나는 오류. Python 2의 `print "..."`가 3에서 이것을 낸다.
- **`TypeError`** — 값의 타입이 연산에 맞지 않아 나는 오류. Python 3의 `s + b`, `1 < "a"`가 이것이다.
- **문(statement) / 함수(function)** — 문법에 박힌 형태 / 괄호를 붙여 부르는 것. `print`가 전자에서 후자가 됐다.
- **실수 나눗셈(true division) / floor division** — 소수점까지 살려 나누기 / 아래로 버려 몫만 남기기. Python 3에서 `/`와 `//`다.
- **임의 정밀도(arbitrary precision) / 오버플로(overflow)** — 자릿수 제한 없이 수를 담는 것 / 담을 크기를 넘는 것. Python 3의 `int`는 오버플로를 신경 쓸 필요가 없다.
- **뷰(view)** — Python 3에서 `dict.keys()`/`values()`/`items()`가 리스트 대신 돌려주는 것.
- **게으른 이터레이터(lazy iterator)** — 달라고 할 때마다 값을 하나씩 내놓는 것. Python 3의 `range()`가 그렇다.
- **PEP 3000 / 3100 / 3002** — 3.0의 방침·변경 목록·비호환 변경 절차를 각각 정리한 문서.
- **의존성(dependency)** — 내 프로그램이 끌어다 쓰는 남의 코드. 이것 하나가 3을 지원하지 않으면 프로젝트 전체가 묶였다.
- **백포트(backport)** — 새 버전의 것을 옛 버전에 가져다 넣는 것. 2.6·2.7이 3의 기능 일부에 대해 그렇게 했다.
- **`__future__` 임포트** — 한 파일 단위로 "미래의 동작"을 미리 켜는 장치.
- **single-source(하나의 소스)** — 같은 소스 하나가 2와 3 양쪽에서 돌게 하는 전략.
- **호환 계층(compatibility layer)** — 두 환경의 차이를 흡수해 한 가지 방법으로만 쓰게 해 주는 코드. `six`가 그것이다.
- **`2to3`** — Python 2 소스를 3 문법으로 기계적으로 변환해 주는 표준 도구. 정형적 변환까지만 할 수 있다.
- **EOL(End Of Life, 수명 종료)** — 더 이상 손대지 않겠다고 선언한 시점. 2.7은 2020년 1월 1일이다.
- **CVE** — 공개적으로 알려진 보안 취약점의 번호와 목록. EOL 이후로는 이 대응도 제공되지 않는다.
