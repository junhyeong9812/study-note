원문이 「들어가며」 첫 문단에서 든 대비를 그대로 옮기면 이렇다.

```text
[ 다른 언어 생태계 ]

```

그림 해설 — 위 칸과 아래 칸의 문구는 원문 「들어가며」 첫 문단을 위아래로 나눠 놓은 것이다.\
아래 칸의 세 줄(설치 도구·빌드 설정·의존성 잠금)은 원문이 "…가 공존하고, 빌드 설정은 …이 뒤섞이며, 의존성은 …로 제각각 잠긴다"로 적은 세 마디를 그대로 나눈 것이다.\
원문은 유명한 XKCD #1987("Python environment")이 이 혼돈을 풍자할 정도라고 적는다.

> **패키지 매니저** — 남이 만든 코드 묶음을 내려받아 설치하고, 그 묶음이 필요로 하는 다른 묶음까지 챙겨 주는 도구.\
> 예: 원문이 든 Cargo(Rust)·npm(Node)·gem/Bundler(Ruby)가 각 언어의 패키지 매니저다.

> **표준 라이브러리** — 언어를 설치하면 따라오는, 언어 본체에 포함된 모듈 모음.\
> 예: distutils는 여기에 들어갔기 때문에 Python 릴리스 주기에 묶였다(1세대 절).

## 들어가며: 왜 이 역사가 유독 복잡한가

다른 언어 생태계는 보통 패키지 매니저가 하나다 — Rust는 Cargo, Node는 npm(과 그 변종), Ruby는 gem/Bundler.\
그런데 Python은 `pip`, `pipenv`, `poetry`, `conda`, `uv`가 공존하고, 빌드 설정은 `setup.py`·`setup.cfg`·`pyproject.toml`이 뒤섞이며, 의존성은 `requirements.txt`·`Pipfile.lock`·`poetry.lock`·`uv.lock`·`environment.yml`로 제각각 잠긴다.\
유명한 XKCD #1987("Python environment")이 이 혼돈을 풍자할 정도다.

이 파편화에는 역사적 이유가 있다.\
Python(1991)은 패키지 매니저라는 개념 자체가 보편화되기 한참 전에 태어났고, 패키징은 언제나 **언어 본체보다 늦게, 사후에 덧붙여진 레이어**였다.\
표준 라이브러리에 들어간 도구는 Python 릴리스 주기에 묶여 빠르게 진화할 수 없었고, 그 공백을 서드파티 도구들이 메우면서 "표준 vs 도구"의 긴장이 30년간 이어졌다.\
이 문서는 그 변천을 시간순으로 따라가며 "언제·왜"를 정리한다.

## 1세대: distutils — 표준 라이브러리에 갇힌 시작 (2000)

**무엇인가** — `distutils`는 2000년경 Python 1.6/2.0과 함께 표준 라이브러리에 들어온 최초의 공식 패키징 도구다.\
핵심 아이디어는 단순했다: 패키지 루트에 `setup.py`라는 **Python 스크립트**를 두고, 그것을 실행하면 빌드·설치·소스 배포본(sdist) 생성이 이뤄진다.

```python
# setup.py (distutils 시절)
from distutils.core import setup

setup(
    name='mypackage',
    version='1.0',
    py_modules=['mypackage'],
    author='Someone',
)
```

```bash
python setup.py build          # 빌드
python setup.py install        # 설치
python setup.py sdist          # 소스 배포본(.tar.gz) 생성
```

```text
distutils 방식 — 알아내려면 실행해야 한다

  setup.py   (빌드 설정이 곧 실행 가능한 Python 코드)
      |
      |  python setup.py build / install / sdist
      v
  빌드 · 설치 · 소스 배포본(.tar.gz) 생성

  설치 도구가 패키지 정보를 알려면 그 코드를 *실행* 해야 한다 — 정적 분석 불가
```

그림 해설 — 세로 화살표 하나는 위 코드블록의 세 명령(`build`·`install`·`sdist`)에 대응한다.\
맨 아랫줄은 원문이 "첫째"로 든 유산이자 원죄를 그대로 옮긴 것이다.

**왜 서드파티 도구가 태어났나** — distutils가 남긴 결정적 유산이자 원죄는 두 가지다.

- 첫째, **빌드 설정이 곧 실행 가능한 Python 코드**라는 점 — `setup.py`는 임의 로직을 담을 수 있어 유연하지만, 설치 도구가 패키지 정보를 알려면 그 코드를 *실행*해야 한다(정적 분석 불가).
- 둘째, **표준 라이브러리에 박혀 있어** Python 릴리스 주기에 묶였다 — 버그 하나 고치는 데도 다음 Python 마이너 버전을 기다려야 했다.

distutils에는 의존성 자동 설치, 업그레이드, 제거 기능조차 없었다.\
이 경직성이 이후 모든 서드파티 도구가 태어난 근본 동기다.\
distutils는 결국 PEP 632에 따라 deprecated되어 **Python 3.12(2023-10)에서 완전히 제거**됐다.

> **sdist(소스 배포본)** — 소스 코드를 그대로 묶어 놓은 배포 파일.\
> 예: 위 코드의 `python setup.py sdist`가 만드는 `.tar.gz` — 받는 쪽은 설치할 때마다 빌드를 돌려야 한다(wheel 절).

> **정적 분석** — 코드를 실행하지 않고 글자 그대로 읽어 정보를 알아내는 것.\
> 예: 원문이 PEP 518에서 든 대로, `pyproject.toml`의 `[build-system]`을 **정적 TOML로** 읽어 빌드 의존성을 아는 것.

## 2세대: setuptools / easy_install / egg — 확장과 자동화 (2004)

**무엇을 더했나** — distutils의 한계를 메우기 위해 Phillip J. Eby가 2004년경 **setuptools**를 내놨다.\
setuptools는 distutils를 상속·monkeypatch하는 방식으로 기능을 얹었고("복잡한 서브클래스와 몽키패칭 더미"라고 공식 문서도 인정한다), 함께 제공한 `easy_install` 명령으로 **PyPI에서 의존성을 자동으로 내려받아 설치**하는 길을 열었다.

setuptools는 **egg**라는 바이너리 배포 포맷도 도입했다 — 설치된 패키지를 `.egg` 디렉터리/zip으로 두고 `sys.path`에 끼워 넣는 방식.

**무엇이 문제였나** — 하지만 easy_install/egg에는 문제가 많았다.

- 설치를 되돌릴 수 없고(uninstall 미지원),
- 의존성을 `sys.path` 조작으로 욱여넣어 충돌이 잦았으며,
- egg는 표준이 아니라 setuptools 전용 관습이었다.

```bash
easy_install requests        # PyPI에서 받아 .egg로 설치
```

> setuptools는 비판을 받으면서도 **사라지지 않았다.** 오늘날에도 가장 널리 쓰이는 빌드 백엔드 중 하나이며, distutils가 제거된 뒤 그 기능을 흡수해 하위 호환을 제공한다. "easy_install은 죽었지만 setuptools는 산다"가 정확한 요약이다.

> **몽키패치(monkeypatch)** — 남의 코드를 고쳐 쓰지 않고, 실행 중에 그 동작을 바깥에서 갈아 끼우는 것.\
> 예: setuptools가 distutils를 상속·monkeypatch해 기능을 얹은 것 — 원문 말대로 공식 문서도 "복잡한 서브클래스와 몽키패칭 더미"라고 인정한다.

> **`sys.path`** — Python이 모듈을 찾을 때 차례로 뒤지는 디렉터리 목록.\
> 예: egg 방식은 설치한 패키지를 이 목록에 끼워 넣었고, 원문 표현대로 그렇게 "욱여넣어" 충돌이 잦았다.

## pip — 사실상의 표준 설치 도구 (2008)

**무엇이 달라졌나** — 2008년 Ian Bicking이 `easy_install`의 대안으로 **pip**를 만들었다(최초 이름은 `pyinstall`, 곧 pip으로 개명 — "Pip Installs Packages"의 재귀 약어).\
pip은 setuptools 위에서 동작하지만 easy_install의 고질병을 정조준했다:

- **egg로 설치하지 않고** 패키지를 평범하게 풀어 설치 → 제거(`pip uninstall`)와 추적이 가능
- **`requirements.txt`** 관습 도입 → 의존성 목록을 파일로 고정해 환경 복제
- 설치 전 전체 다운로드·검증 → 중간 실패 시 깨진 상태를 남기지 않음

```text
[ easy_install / egg (2004) ]                [ pip (2008) ]

.egg 디렉터리/zip 으로 두고                  패키지를 평범하게 풀어 설치
sys.path 에 끼워 넣는다

설치를 되돌릴 수 없다(uninstall 미지원)      제거(pip uninstall)와 추적이 가능

의존성을 sys.path 조작으로 욱여넣어
충돌이 잦았다

egg 는 표준이 아니라
setuptools 전용 관습이었다
```

그림 해설 — 오른쪽 두 줄은 pip 절의 첫 불릿("**egg로 설치하지 않고** 패키지를 평범하게 풀어 설치 → 제거(`pip uninstall`)와 추적이 가능")을 좌우가 아니라 위아래로 나눈 것이고, 왼쪽 두 줄은 2세대 절이 egg를 설명한 문장(".egg 디렉터리/zip으로 두고 `sys.path`에 끼워 넣는 방식")과 그 뒤 문제 목록("설치를 되돌릴 수 없고(uninstall 미지원)")에서 짝이 되는 것을 골라 놓은 것이다.\
왼쪽에만 있는 아래 두 줄은 원문이 easy_install/egg의 문제로만 적은 것이라, 짝을 지어 줄 오른쪽 문구가 원문에 없다.

```bash
pip install requests
pip install -r requirements.txt
pip freeze > requirements.txt   # 현재 환경을 그대로 박제
```

```text
# requirements.txt
requests==2.31.0
urllib3==2.0.7
```

pip은 빠르게 표준이 됐고, 2011년에는 pip과 virtualenv의 유지보수를 개인(Bicking)에서 넘겨받기 위해 **PyPA(Python Packaging Authority)**가 결성됐다.\
패키징이 "한 사람의 프로젝트"에서 "커뮤니티 거버넌스"로 넘어간 분기점이다.

> **PyPA(Python Packaging Authority)** — 2011년에 결성된, pip·virtualenv의 유지보수를 맡은 조직.\
> 예: 원문 표현대로 패키징이 "한 사람의 프로젝트"에서 "커뮤니티 거버넌스"로 넘어간 분기점이다.

## virtualenv / venv — 환경 격리 (2007 / 2012)

**무엇이 문제였나** — 설치 도구만큼 중요한 축이 **격리**다.\
시스템 Python 하나에 모든 패키지를 깔면 프로젝트 A가 요구하는 `Django 2`와 프로젝트 B의 `Django 4`가 충돌한다.\
Ian Bicking이 2007년 **virtualenv**를 발표해(2007-10-10, "Workingenv is dead, long live Virtualenv!") 프로젝트마다 독립된 `site-packages`를 갖는 가상 환경을 만들 수 있게 했다.

```text
[ 시스템 Python 하나에 모두 ]            [ 프로젝트마다 독립된 site-packages ]

+---------------------------+            +----------------+  +----------------+
| Django 2  <- 프로젝트 A   |            | 프로젝트 A     |  | 프로젝트 B     |
| Django 4  <- 프로젝트 B   |            |   Django 2     |  |   Django 4     |
+---------------------------+            +----------------+  +----------------+

충돌한다                                 설치는 "이 환경에만" 적용된다
```

그림 해설 — 왼쪽 칸의 `Django 2`/`Django 4`와 프로젝트 A/B는 원문이 충돌 예로 든 그 조합이다.\
오른쪽 아랫줄은 원문 코드블록의 주석 "이 환경에만 설치됨"을 옮긴 것이다.

이 아이디어는 충분히 핵심적이어서, Carl Meyer의 **PEP 405**를 통해 **venv**라는 이름으로 표준 라이브러리에 흡수됐다(**Python 3.3**, 2012).\
오늘날 `python -m venv`는 추가 설치 없이 쓸 수 있다.

```bash
python -m venv .venv           # 표준 라이브러리 venv
source .venv/bin/activate      # (Windows: .venv\Scripts\activate)
pip install requests           # 이 환경에만 설치됨
```

> **가상 환경(virtual environment)** — 프로젝트마다 독립된 `site-packages`를 갖는 환경.\
> 예: 위 코드의 `python -m venv .venv` 뒤에 깐 `requests`는 원문 주석 그대로 "이 환경에만 설치됨"이다.

> **`site-packages`** — 설치한 서드파티 패키지가 놓이는 디렉터리.\
> 예: 격리란 이 디렉터리를 프로젝트마다 따로 두는 것이다.

설치(pip) + 격리(venv) + 잠금(requirements.txt) — 이 3종 조합이 2010년대 내내 Python 패키징의 "기본기"였다.\
문제는 이 셋이 **서로 다른 도구**라 매번 손으로 엮어야 했다는 점이다.

## wheel — 바이너리 배포의 표준 (PEP 427, 2013)

**무엇이 문제였나** — 소스 배포본(sdist)은 설치할 때마다 빌드를 돌려야 한다 — C 확장이 있으면 컴파일러가 필요하고 느리다.\
egg가 이를 풀려 했지만 표준이 아니었다.\
**PEP 427**(Alyssa Coghlan이 2013-02-16에 1.0으로 승인)이 **wheel**(`.whl`) 포맷을 표준으로 정립했다.

wheel은 본질적으로 **메타데이터가 규격화된 ZIP**이다.\
파일명에 호환성 태그(Python 버전·ABI·플랫폼)를 박아 두어, 설치 도구가 **빌드 시스템을 전혀 몰라도** 맞는 wheel을 골라 풀어 넣기만 하면 된다.

```text
requests-2.31.0-py3-none-any.whl
        │       │   │    └ 플랫폼 (any = 순수 파이썬)
        │       │   └ ABI 태그
        │       └ Python 태그 (py3)
        └ 버전
numpy-1.26.0-cp312-cp312-manylinux_2_17_x86_64.whl   # C 확장 포함, 플랫폼별
```

```text
[ sdist (소스 배포본) ]                     [ wheel (.whl) = 메타데이터가 규격화된 ZIP ]

설치할 때마다 빌드를 돌려야 한다            파일명의 호환성 태그로 맞는 것을 골라
C 확장이 있으면 컴파일러가 필요하고 느리다  풀어 넣기만 하면 된다

컴파일을 설치자가 매번                      컴파일을 배포자가 한 번 해서 올려 둔다
```

그림 해설 — 첫 행이 원문의 직접 대비다: 왼쪽은 "소스 배포본(sdist)은 **설치할 때마다 빌드를 돌려야 한다** — C 확장이 있으면 컴파일러가 필요하고 느리다", 오른쪽은 "맞는 wheel을 골라 **풀어 넣기만 하면 된다**".\
오른쪽 칸 머리의 "메타데이터가 규격화된 ZIP"은 대비의 한쪽이 아니라 wheel이 무엇인지를 적은 원문 문장이라 행 밖 머리로 올렸다.\
마지막 행은 원문이 "효과는 컸다"로 적은 대비다 — 오른쪽은 "컴파일을 **배포자가 한 번** 해서 올려 두면 설치자는 빌드 없이 받기만 한다"의 앞쪽이고, 왼쪽은 그 문장이 전제하는 반대쪽을 한 마디로 줄인 것이다.

효과는 컸다: 컴파일을 **배포자가 한 번** 해서 올려 두면 설치자는 빌드 없이 받기만 한다.\
오늘날 PyPI에서 wheel은 sdist와 함께 표준 배포 형식이며, `numpy`·`pandas` 같은 무거운 패키지를 `pip install` 한 줄로 즉시 설치할 수 있는 것이 바로 wheel 덕분이다.

> **wheel(`.whl`)** — 메타데이터가 규격화된 ZIP으로 된 표준 바이너리 배포 포맷.\
> 예: 원문이 든 대로 `numpy`·`pandas` 같은 무거운 패키지를 `pip install` 한 줄로 즉시 설치할 수 있는 것이 이 덕분이다.

## requirements.txt의 한계 — 왜 그것으로 충분하지 않았나

2010년대 표준이던 `requirements.txt`는 단순함이 장점이자 한계였다.\
핵심 결함은 **그것이 진짜 락파일이 아니라는 점**이다.

- **직접 의존성과 전이 의존성의 구분이 없다.**\
  `requests`만 적어도 그것이 끌어오는 `urllib3`·`certifi`의 버전은 고정되지 않는다.\
  재현성을 얻으려면 `pip freeze`로 *모든* 전이 의존성을 수동으로 박제해야 하는데, 그러면 이번엔 "내가 진짜 원한 패키지가 무엇이었는지"가 사라진다.
- **잠금과 선언이 한 파일에 섞인다.**\
  다른 생태계(npm의 `package.json`+`package-lock.json`, Cargo의 `Cargo.toml`+`Cargo.lock`)는 "원하는 것"과 "확정된 것"을 두 파일로 나누지만, requirements.txt에는 그런 관습이 없다.
- **해시 검증·환경 분리(dev/prod)·플랫폼 분기**가 기본 제공되지 않는다.
- **리졸버가 약했다.**\
  초기 pip은 충돌하는 버전 제약을 만나도 일관된 해를 보장하지 못했다(2020년 pip 20.3에서야 backtracking 리졸버가 기본이 됐다).

```text
[ 다른 생태계 — 두 파일로 나눈다 ]
  npm     package.json ("원하는 것")  +  package-lock.json ("확정된 것")
  Cargo   Cargo.toml   ("원하는 것")  +  Cargo.lock        ("확정된 것")

[ requirements.txt — 한 파일이다 ]
  "원하는 것"과 "확정된 것"이 한 파일에 섞인다 — requirements.txt 에는 그런 관습이 없다
  requests 만 적으면 그것이 끌어오는 urllib3·certifi 의 버전은 고정되지 않는다
  pip freeze 로 모두 박제하면, 이번엔 "내가 진짜 원한 패키지가 무엇이었는지"가 사라진다
```

그림 해설 — 위 칸의 두 줄은 원문이 든 두 생태계이고, 괄호 안의 "원하는 것"·"확정된 것"도 원문의 말이다.\
아래 칸의 세 줄은 원문의 첫째·둘째 불릿을 그대로 옮긴 것이다.

> **전이 의존성(transitive dependency)** — 내가 직접 적지는 않았지만, 내가 적은 패키지가 끌어오는 패키지.\
> 예: 원문이 든 대로 `requests`를 적으면 따라오는 `urllib3`·`certifi`.

> **락파일(lock file)** — 무엇을 원하는지가 아니라 **어느 버전으로 확정됐는지**를 적어 두되, **전이 의존성까지 고정하고 선언 파일과는 분리된** 파일. 원문은 여기에 해시 검증까지 든다.\
> 예: pipenv의 `Pipfile.lock` — 원문 표현대로 "해시까지 박힌 결정적 잠금"이고, 원하는 것을 적는 `Pipfile`과 파일이 나뉜다.\
> 주의: `pip freeze > requirements.txt`로 버전을 전부 박아도 락파일이 되지는 않는다 — 전이 의존성은 고정되지만, 원문이 든 결함 가운데 "잠금과 선언이 한 파일에 섞인다"와 "해시 검증이 기본 제공되지 않는다"가 그대로 남는다.

> **리졸버(resolver)** — 여러 패키지가 내건 버전 제약을 한꺼번에 만족시키는 조합을 찾아내는 부분.\
> 예: 원문이 적은 대로 초기 pip은 충돌하는 제약을 만나도 일관된 해를 보장하지 못했고, 2020년 pip 20.3에서야 backtracking 리졸버가 기본이 됐다.

이 공백을 임시로 메운 것이 `pip-tools`의 `pip-compile`(직접 의존성 → 고정된 requirements.txt 생성)이었지만, 근본 해법은 **"선언 + 잠금 + 환경 관리"를 한 도구로 통합**하는 방향으로 갔다.\
그게 pipenv와 poetry다.

## pipenv — "사람을 위한" 통합 시도 (2017)

**무엇을 노렸나** — Kenneth Reitz(`requests` 저자)가 2017년 1월 **pipenv**를 발표했다.\
목표는 pip + virtualenv + 락파일을 **하나의 일관된 경험**으로 묶는 것.\
`Pipfile`(사람이 쓰는 선언)과 `Pipfile.lock`(해시까지 박힌 결정적 잠금)을 분리해 다른 생태계의 모범을 따랐고, 2017년 11월 python.org가 공식 권장 도구로 올리며 정점을 찍었다.

```toml
# Pipfile
[packages]
requests = "*"

[dev-packages]
pytest = "*"

[requires]
python_version = "3.11"
```

```bash
pipenv install requests        # 가상환경 생성 + 설치 + Pipfile/lock 갱신
pipenv install --dev pytest
pipenv run pytest
```

**무엇이 문제였나** — 그러나 pipenv는 **리졸버가 치명적으로 느렸다** — 사용자가 설치를 걸어 두고 다른 일을 하다 돌아와도 여전히 의존성을 풀고 있는 경우가 흔했다.\
릴리스도 한동안 정체됐다.\
"올바르지만 느린" 통합은 결국 더 빠른 대안에 자리를 내준다.

## poetry — pyproject.toml 기반 워크플로 (2018)

**무엇이 달랐나** — Sébastien Eustace가 2018년 **poetry**를 내놨다.\
pipenv와 문제의식은 같았지만(통합), 두 가지가 달랐다: **빌드·메타데이터·의존성을 모두 `pyproject.toml` 하나에** 담았고, **PubGrub 알고리즘**(Dart의 pub과 동일)으로 빠르고 설명 가능한 의존성 해결을 제공했다.

```toml
# pyproject.toml (poetry 방식)
[tool.poetry]
name = "myapp"
version = "0.1.0"

[tool.poetry.dependencies]
python = "^3.11"
requests = "^2.31"

[tool.poetry.group.dev.dependencies]
pytest = "^8.0"

[build-system]
requires = ["poetry-core"]
build-backend = "poetry.core.masonry.api"
```

```bash
poetry add requests          # 의존성 추가 + poetry.lock 갱신
poetry install               # lock 기준 재현 설치
poetry build                 # wheel + sdist 빌드
poetry publish               # PyPI 업로드
```

poetry는 설치·격리·빌드·배포를 한 명령 체계로 묶어 큰 인기를 얻었다.

**어떤 비판을 받았나** — 다만 역설이 있다 — poetry는 **자체 lock 포맷과 (당시) 비표준 메타데이터 테이블(`[tool.poetry]`)**을 도입해, "파편화를 해결한다며 선택지를 하나 더 늘렸다"는 비판을 받았다.\
이 긴장이 다음 단계, 즉 PEP를 통한 **표준화** 흐름을 불렀다.

## pyproject.toml과 PEP들 — 도구에서 표준으로 (2016~2020)

**무엇을 끊으려 했나** — poetry·pipenv 같은 도구 경쟁의 밑바닥에서, PyPA는 `setup.py`의 근본 문제(빌드하려면 코드를 실행해야 하고, 그러려면 setuptools가 먼저 깔려 있어야 하는 **순환 의존**)를 표준으로 끊고 있었다.

- **PEP 518 (2016)** — `pyproject.toml`을 도입하고 `[build-system]` 테이블을 규정.\
  빌드에 필요한 의존성을 **정적 TOML로 미리 선언**해, 설치 도구가 프로젝트 코드를 실행하지 않고도 격리된 빌드 환경을 꾸릴 수 있게 했다.
- **PEP 517 (2017)** — **빌드 프론트엔드 ↔ 백엔드** 사이의 훅 API를 정의.\
  이로써 setuptools뿐 아니라 `flit`, `hatchling`, `poetry-core`, `maturin`(Rust), `uv_build` 등 **어떤 백엔드든** 같은 `pip install`로 빌드된다.
- **PEP 621 (2020)** — `[project]` 테이블로 이름·버전·의존성 등 **프로젝트 메타데이터를 도구 중립적으로 표준화**.\
  poetry의 `[tool.poetry]` 같은 도구 전용 표 없이도 메타데이터를 공유할 수 있게 됐다.

```toml
# pyproject.toml (PEP 621 표준 메타데이터 — 특정 도구에 묶이지 않음)
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["requests>=2.31"]

[project.optional-dependencies]
dev = ["pytest>=8.0"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

빌드 프론트엔드(pip·build·uv)와 백엔드(setuptools·hatchling·flit·poetry-core)가 PEP 517/518 계약으로 분리되는 구조를 그림으로 보면 다음과 같다.

```text
사용자
pip install / build / uv
      |
      v
빌드 프론트엔드
(PEP 517 호출자)
      |
      |  pyproject.toml
      |  [build-system] 읽기 (PEP 518)
      v
격리된 빌드 환경
(build deps 설치)
      |
      v
빌드 백엔드
setuptools / hatchling /
flit / poetry-core / maturin
      |
      |  build_wheel() / build_sdist()
      |  (PEP 517 훅)
      v
wheel + sdist
```

그림 해설 — 원문 mermaid 그림을 글자로 옮긴 것이다.\
마디 다섯과 화살표 넷의 문구·방향은 원문 그대로이고, 가로로 놓인 것을 세로로 폈을 뿐이다.\
화살표 옆에 붙은 두 줄은 원문 그림이 그 화살표에 달아 둔 라벨이다.

프론트엔드는 `[build-system]`만 정적으로 읽어 어떤 백엔드를 쓸지 알아내고, 실제 빌드는 표준 훅(`build_wheel`/`build_sdist`)으로 백엔드에 위임한다.\
**누가 빌드하든 결과물(wheel·sdist)과 호출 방식이 같다** — 이것이 표준화의 핵심이다.

> **빌드 프론트엔드 / 백엔드** — 빌드를 *시키는* 쪽 / 실제로 *하는* 쪽.\
> 예: 원문 본문이 든 대로 `pip`·`build`·`uv`가 프론트엔드, `setuptools`·`hatchling`·`flit`·`poetry-core`가 백엔드다. 둘 사이의 약속이 PEP 517의 훅이다.

> **순환 의존** — A를 하려면 B가 있어야 하는데, B를 얻으려면 다시 A가 필요한 상태.\
> 예: 원문이 든 대로 빌드하려면 `setup.py`를 실행해야 하고, 그러려면 setuptools가 먼저 깔려 있어야 했던 것.

## conda — 다른 길을 간 과학 생태계 (2012)

**왜 갈라졌나** — 지금까지의 계보(distutils→pip→poetry)와 **평행하게 갈라져 나간** 생태계가 conda다.\
Continuum Analytics(Peter Wang, Travis Oliphant — NumPy 창시자)가 2012년 Anaconda 배포판과 함께 내놨고, conda 1.0은 Anaconda 1.1(2012-10)에 포함됐다.

왜 별도 도구가 필요했나?\
**과학·데이터 스택은 순수 Python이 아니기 때문**이다.\
NumPy·SciPy는 BLAS/LAPACK 같은 Fortran/C 라이브러리에 의존하고, 딥러닝은 CUDA·MKL 같은 비-Python 네이티브 의존성을 끌어온다.\
pip+wheel은 *Python 패키지*는 잘 다루지만, **컴파일러·시스템 라이브러리·비-Python 런타임**까지 통합 관리하지는 못했다(특히 wheel 표준화 이전엔 더 심각했다).

conda는 이를 정면으로 해결했다: **언어 불문(language-agnostic)·플랫폼 불문 바이너리 패키지 매니저**로, Python 자체도 conda가 설치하는 하나의 패키지로 취급한다.\
패키지는 PyPI가 아니라 별도 채널(defaults, `conda-forge`)에서 받는다.

```text
[ PyPI 세계 ]                         [ conda 세계 ]

pip + wheel                           conda

Python 패키지는 잘 다룬다             Python 자체도 conda가 설치하는 하나의 패키지

컴파일러·시스템 라이브러리·비-Python  (이를 정면으로 해결했다)
런타임까지 통합 관리하지는 못했다     언어 불문·플랫폼 불문 바이너리 패키지 매니저

  conda 쪽 패키지는 PyPI가 아니라 별도 채널(defaults, conda-forge)에서 받는다
  두 세계는 패키지 출처·메타데이터·해결 알고리즘이 달라, 섞으면 환경이 깨지기 쉽다
```

그림 해설 — 셋째 행을 같은 행에 둔 근거는 원문 문장 "conda는 **이를** 정면으로 해결했다: 언어 불문(language-agnostic)·플랫폼 불문 바이너리 패키지 매니저로"의 「이를」이 바로 왼쪽 칸(pip+wheel이 통합 관리하지는 못했다)을 가리킨다는 점이다 — 원문이 든 인과는 채널이 아니라 **언어 불문**이다.\
둘째 행의 두 문구도 각각 "pip+wheel은 *Python 패키지*는 잘 다루지만"과 "Python 자체도 conda가 설치하는 하나의 패키지로 취급한다"로, 원문이 같은 축(무엇까지를 패키지로 보나)에 놓은 대비다.\
아래 두 줄은 어느 한쪽 칸에 짝지을 원문 문구가 없어 행 밖으로 뺐다 — 첫 줄은 conda 쪽만의 사실이고, 둘째 줄은 두 칸에 걸친 원문의 결론이다(원문 "대가는 이원화다" 문단).

```yaml
# environment.yml
name: ml-env
channels:
  - conda-forge
dependencies:
  - python=3.11
  - numpy
  - pytorch
  - pip:
      - some-pypi-only-package    # conda 채널에 없는 건 pip로 보충
```

```bash
conda create -n ml-env python=3.11 numpy
conda activate ml-env
conda env create -f environment.yml
```

**대가는 무엇인가** — 대가는 **이원화**다.\
conda 세계와 PyPI 세계는 패키지 출처·메타데이터·해결 알고리즘이 달라, 둘을 섞으면 환경이 깨지기 쉽다.\
과학 커뮤니티에 깊이 뿌리내렸지만, 동시에 "Python 패키징은 왜 둘로 갈렸나"를 가장 극적으로 보여주는 사례다.

> **네이티브 의존성** — Python이 아닌 언어로 컴파일돼 있어서, pip+wheel이 **통합 관리하지는 못한** 라이브러리.\
> 예: 원문이 든 BLAS/LAPACK(Fortran/C)과 CUDA·MKL.

## uv — Rust로 다시 쓴 통합 도구 (2024)

**무엇인가** — 2024년 2월 15일, **Astral**(린터 `Ruff`로 유명한 Charlie Marsh의 회사)이 **uv**를 공개했다.\
**Rust로 작성**된 uv는 처음엔 "초고속 pip 대체재"로 출발했다 — Astral 벤치마크 기준 콜드 캐시에서 pip의 8~10배, 웜 캐시에서 80~115배, 설치는 10~100배 빠르다.\
동시성·최적화된 시스템 콜·전역 캐시(하드링크)가 그 비결이다.

uv는 곧 **단일 도구로의 통합**으로 야심을 넓혔다 — pip·pip-tools·virtualenv·pipenv·poetry·pyenv가 하던 일(설치·잠금·가상환경·프로젝트 관리·Python 버전 설치)을 하나로 묶는 **"Python의 Cargo"**를 지향한다.\
이 과정에서 Armin Ronacher의 실험적 도구 `rye`의 운영권도 인수했다.

```bash
uv venv                        # 가상환경 생성 (즉시)
uv pip install requests        # pip 호환 인터페이스
uv add requests                # 프로젝트에 의존성 추가 + uv.lock 갱신
uv sync                        # uv.lock 기준 환경 재현
uv run pytest                  # 환경 자동 보장 후 실행
uv python install 3.12         # Python 인터프리터 자체도 설치
```

uv는 PEP 621 표준 메타데이터를 그대로 쓰고(`[tool.poetry]` 같은 전용 표가 필요 없다), 자체 크로스플랫폼 `uv.lock`을 주 포맷으로 두되 PEP 751 표준 락파일도 내보낼 수 있다.\
빠른 속도와 PEP 표준 위에 선 설계로 빠르게 채택되며, 현재 패키징 "전쟁"의 가장 유력한 통합 후보로 거론된다.

## 표준 락파일을 향하여 — PEP 751 (2025)

**무엇이 남아 있었나** — 도구마다 락파일이 달랐던 것(`Pipfile.lock`·`poetry.lock`·`uv.lock`)이 마지막 파편화 지점이었다.\
Brett Cannon의 **PEP 751**이 2025년 3월 승인되며 **`pylock.toml`이라는 표준 락파일 포맷**을 정의했다 — 도구가 생성하고 사람이 읽을 수 있는 TOML.\
pip은 25.1(2025-04)에 실험적 `pip lock`을 추가했고, uv는 `uv export --format pylock.toml`로 상호운용한다.\
메타데이터(PEP 621)에 이어 잠금까지 표준화되면, 도구는 달라도 **결과물은 호환되는** 그림이 완성된다.

## 패키징 "전쟁"사 — 왜 이렇게 파편화됐나

도구 목록을 나열하는 것만으로는 본질이 안 보인다.\
파편화의 구조적 원인을 정리하면 이렇다.

```text
A  Python(1991): 패키지 매니저 개념 이전에 탄생
   → 패키징은 항상 사후에 덧붙인 레이어
B  distutils가 표준 라이브러리에 박힘
   → 릴리스 주기에 묶여 진화 불가
C  서드파티가 공백을 메움
   setuptools→pip→pipenv→poetry→uv
D  setup.py = 실행 가능한 코드
   → 빌드가 튜링 완전, 정적 분석 불가
E  PEP 517/518/621
   선언적 pyproject.toml로 전환
F  초기엔 중앙 설계 권위 부재
   (PyPA는 2011에야 결성)
G  C 확장·비-Python 의존성
   (BLAS, CUDA)
H  egg→wheel,
   그리고 conda가 생태계째 분기
I  각 도구가 자체 UX·자체 락파일 도입
   → 표준이 아니라 선택지가 늘어남
J  표준화로 수렴 시도
   PEP 621(메타데이터)·751(락파일)·uv(통합)

   A ──> B ──> C ──> I ──┐
   A ──> D ──> E ────────┼──> J
   A ──> F ──> C         │
   G ──> H ──────────────┘
```

그림 해설 — 원문 mermaid 그림을 글자로 옮긴 것이다.\
마디 열(A~J)의 문구는 원문 그대로이고, 아래 네 줄이 원문 그림의 화살표 열하나를 전부 적은 것이다 — A→B, B→C, C→I, I→J, A→D, D→E, E→J, A→F, F→C, G→H, H→J.\
마디 안에 있는 `→`와 `setuptools→pip→…`의 화살표는 원문 마디 글자에 들어 있던 것이라 마디의 일부로 두었다.

핵심 원인을 풀어 쓰면:

1. **늦게, 사후에 덧붙은 레이어.**\
   Python은 npm·Cargo 같은 매니저가 상식이 되기 전에 태어났다.\
   패키징은 언제나 언어 본체를 뒤따라가며 *덧칠*됐고, 그래서 일관된 설계 대신 누적된 호환 레이어가 됐다.

2. **표준 라이브러리의 함정.**\
   distutils를 표준에 넣은 것은 보급에는 좋았지만, **Python 릴리스 주기에 결박**되어 빠른 개선이 불가능했다.\
   도구는 본체보다 빨리 진화해야 하는데 본체에 묶인 것이다 — 이 교훈 때문에 이후 pip·venv는 표준화하되 핵심 도구는 별도로 빠르게 굴린다.

3. **setup.py의 원죄 — 실행 가능한 빌드.**\
   빌드 설정이 임의 Python 코드라, 설치 도구가 패키지를 이해하려면 신뢰할 수 없는 코드를 실행해야 했다(순환 의존·재현성·보안 문제).\
   PEP 517/518의 선언적 `pyproject.toml`은 바로 이 원죄를 끊으려는 시도다.

4. **거버넌스의 부재 → 뒤늦은 형성.**\
   2011년 PyPA가 생기기 전까지 패키징은 개인 자원봉사자들의 산물이었다.\
   중앙 설계 권위가 없으니 "한 가지 명백한 방법"(Zen of Python)이 패키징에는 적용되지 못했고, 좋은 아이디어마다 새 도구가 생겼다.

5. **바이너리·비-Python 의존성.**\
   순수 Python이면 wheel로 충분하지만, 과학 스택의 네이티브 의존성은 그 경계를 넘었다.\
   conda는 이를 풀었지만 **생태계를 통째로 분기**시켰다 — pip 세계와 conda 세계의 이원화는 지금도 가장 큰 균열이다.

6. **"통합 도구"의 역설.**\
   pipenv·poetry·uv는 모두 "파편화를 끝내겠다"며 등장했지만, 각자 **자체 워크플로와 자체 락파일**을 들고 와 단기적으로는 선택지를 하나 더 늘렸다.\
   진짜 수렴은 도구 경쟁이 아니라 **PEP 표준화**(517/518/621/751)에서 왔다.

종합하면, Python 패키징의 역사는 **"표준 라이브러리에 묶인 경직된 도구 → 서드파티의 폭발적 실험 → PEP를 통한 표준 인터페이스로의 재수렴"**이라는 한 사이클로 읽을 수 있다.\
uv가 속도와 통합으로, PEP 621/751이 메타데이터·락파일 표준으로 양쪽에서 수렴을 밀어붙이는 지금이, 30년 파편화 이후 처음으로 "하나의 명백한 방법"에 가까워진 시점이다 — 적어도 PyPI 세계에서는.

## 용어 풀이

- **패키지 매니저** — 남이 만든 코드 묶음을 내려받아 설치하고, 그 묶음이 필요로 하는 다른 묶음까지 챙겨 주는 도구.
- **표준 라이브러리** — 언어를 설치하면 따라오는, 언어 본체에 포함된 모듈 모음.
- **sdist(소스 배포본)** — 소스 코드를 그대로 묶어 놓은 배포 파일. 설치할 때마다 빌드를 돌려야 한다.
- **정적 분석** — 코드를 실행하지 않고 글자 그대로 읽어 정보를 알아내는 것.
- **몽키패치(monkeypatch)** — 남의 코드를 고쳐 쓰지 않고, 실행 중에 그 동작을 바깥에서 갈아 끼우는 것.
- **egg** — setuptools가 도입한 바이너리 배포 포맷. 표준이 아니라 setuptools 전용 관습이었다.
- **`sys.path`** — Python이 모듈을 찾을 때 차례로 뒤지는 디렉터리 목록.
- **PyPI(Python Package Index)** — 2003년 가동된 중앙 패키지 저장소. 옛 이름은 "Cheese Shop".
- **PyPA(Python Packaging Authority)** — 2011년에 결성된, pip·virtualenv의 유지보수를 맡은 조직.
- **가상 환경(virtual environment)** — 프로젝트마다 독립된 `site-packages`를 갖는 환경.
- **`site-packages`** — 설치한 서드파티 패키지가 놓이는 디렉터리.
- **wheel(`.whl`)** — 메타데이터가 규격화된 ZIP으로 된 표준 바이너리 배포 포맷(PEP 427, 2013).
- **전이 의존성(transitive dependency)** — 내가 직접 적지는 않았지만, 내가 적은 패키지가 끌어오는 패키지.
- **락파일(lock file)** — 어느 버전으로 확정됐는지를, 전이 의존성까지 고정하고 선언 파일과는 분리해 적어 두는 파일(원문은 해시 검증까지 든다).
- **리졸버(resolver)** — 여러 패키지가 내건 버전 제약을 한꺼번에 만족시키는 조합을 찾아내는 부분.
- **빌드 프론트엔드 / 백엔드** — 빌드를 시키는 쪽(pip·build·uv) / 실제로 하는 쪽(setuptools·hatchling·flit·poetry-core).
- **순환 의존** — A를 하려면 B가 있어야 하는데, B를 얻으려면 다시 A가 필요한 상태.
- **네이티브 의존성** — Python이 아닌 언어로 컴파일돼 있어서 pip+wheel이 통합 관리하지는 못한 라이브러리(BLAS/LAPACK·CUDA·MKL).
