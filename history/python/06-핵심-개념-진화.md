# Python 핵심 개념·구현의 진화 (개념사)

> 원본: `~/project/python-history/06-핵심-개념-진화.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-20).\
> 연도·인명·버전·PEP 번호·수치·코드블록·표는 원문 그대로다.\
> ASCII 도식 10개(그중 4개는 원문 mermaid 그림을 글자로 옮긴 것)와 「한눈에」의 빚 비유, 용어 블록의 「예:」, 「용어 풀이」는 원문에 없는 보충이다.

## 한눈에 — 쉽게 말하면

원문이 제목 아래에 적은 한 줄 요약은 이것이다.

> 버전별 신규 문법이 아니라, Python을 떠받치는 **핵심 개념과 그 구현**이 30여 년에 걸쳐 어떻게 바뀌어 왔는가 — GIL·인터프리터·타입·동시성·메모리를 각각 "언제, 왜, 무엇을 해결하려고" 바꿨는지의 관점에서 추적한다.

**개념사 = 제품이 아니라 "부품의 역사".**\
어느 버전에 무엇이 추가됐나가 아니라, 그 아래의 구현이 왜 그 모양이 되었나를 따라간다.

이 문서의 비유는 **초기에 진 빚을 나중에 갚는다** 하나뿐이다 — 원문이 마지막 문장에서 「되갚아 온 과정」이라 쓴 것을 그대로 늘린 것이다.\
이 비유는 「한눈에」에서만 쓴다 — 본문 맨 끝의 「되갚아 온 과정」은 비유가 아니라 원문 문장 그대로다.\
나머지는 용어 블록 안의 국소 비유다.

| 비유 | 실체 |
|------|------|
| 당시로서는 합리적인, 가장 단순한 선택을 한다 | 멀티코어·멀티스레드가 일반적이지 않던 때, **가장 단순하고 확실한 해법**으로 GIL을 채택했다 |
| 그 선택이 나중에 청구서로 돌아온다 | **CPU 바운드 작업에서 멀티스레드가 멀티코어를 활용하지 못한다** |
| 수십 년에 걸쳐 나눠 갚는다 | 원문의 마지막 문장 — **초기 설계 결정이 낳은 제약을 수십 년에 걸쳐 되갚아 온 과정** |

똑같은 구조다 — 그때는 합리적이던 선택이 나중에 비싼 항목이 된다.

원문이 「정리」 절 마지막 문단에서 "이 표를 관통한다"고 적은 세 가닥의 인과는 이렇다.

```text
  레퍼런스 카운팅  →  GIL  →  async 모델        (메모리 모델이 동시성 방향을 결정)

  동적 타이핑  →  점진적 타이핑                  (자유의 대가를 선택적 타입으로 보완)

  대안 구현의 JIT/특수화  →  CPython 자신의 JIT화  (외부 실험의 본체 흡수)
```

그림 해설 — 세 줄과 괄호 안의 문구는 원문 「정리」 절 마지막 문단을 그대로 옮긴 것이다.\
화살표 넷도 그 문장에 이미 있던 것이고, 세 줄 사이에는 원문이 관계를 적지 않아 아무것도 잇지 않았다.

> **개념사** — 제품이 아니라 그 제품들이 공유하는 장치와 아이디어의 계보.\
> 예: "Python 3.13에 무엇이 추가됐나"가 아니라 "왜 GIL이 지금 모양이어야 했나"를 따라가는 것.

Python은 1991년 Guido van Rossum이 발표한 이래 "단순함과 가독성"이라는 철학을 유지하면서도, 그 아래의 구현은 끊임없이 재설계되어 왔다.\
이 문서가 다루는 일곱 갈래는 서로 깊게 얽혀 있다 — **레퍼런스 카운팅**이라는 메모리 모델이 **GIL**을 낳았고, GIL이 **동시성 모델**(스레드 대신 async)의 방향을 결정했으며, **동적 타이핑**의 자유가 **점진적 타이핑**이라는 보완을 불렀고, "느린 인터프리터"라는 평판이 **대안 구현**(PyPy·Cython)과 **CPython 자체의 JIT화**를 촉발했다.\
각 절은 독립적으로 읽을 수 있지만, 이 인과의 사슬을 염두에 두면 진화의 논리가 선명해진다.

*(위 문단은 원문이 제목 아래에 이어 적은 들어가는 글이다 — 원문에 절 제목이 없어 여기서도 제목을 붙이지 않았다.)*

## 1. GIL — 왜 생겼고, 어떻게 사라지고 있나

### 1.1 언제·왜 생겼나

**언제·왜** — GIL(Global Interpreter Lock, 전역 인터프리터 락)은 Python 탄생 초기인 1990년대 초 Guido van Rossum이 **인터프리터 구현을 단순화하기 위해** 도입했다.\
그 뿌리는 CPython의 메모리 관리 방식인 **레퍼런스 카운팅**(§6)에 있다.

CPython의 모든 객체(정수·문자열·리스트 등)는 자신을 가리키는 참조의 개수를 담은 카운터를 들고 다닌다.\
객체가 새로 참조되면 `+1`, 참조가 사라지면 `-1`, 0이 되면 즉시 메모리를 해제한다.\
문제는 이 `+1`/`-1` 연산이 **원자적(atomic)이지 않다**는 점이다.\
두 스레드가 같은 객체의 카운터를 동시에 건드리면 갱신이 유실되어 — 아직 살아있는 객체가 해제되거나, 죽은 객체가 영원히 남는 — 메모리 손상과 크래시가 발생한다.

```text
+1 / -1 이 원자적이지 않다는 것

  어떤 객체의 카운터: 2

  스레드 A                    스레드 B
  카운터를 읽는다 → 2
                              카운터를 읽는다 → 2
  +1 한 값 3 을 쓴다
                              +1 한 값 3 을 쓴다

  두 번 늘렸는데 카운터는 3 — 갱신이 유실됐다
  → 아직 살아있는 객체가 해제되거나, 죽은 객체가 영원히 남는다
```

그림 해설 — 마지막 두 줄은 원문 문장("갱신이 유실되어 — 아직 살아있는 객체가 해제되거나, 죽은 객체가 영원히 남는")을 그대로 옮긴 것이다.\
다만 이 그림이 실제로 만드는 결과는 둘 가운데 **앞의 것뿐**이다 — `+1`이 유실돼 카운터가 실제보다 작아지니 아직 살아있는 객체가 먼저 0에 닿아 해제된다. 뒤의 "죽은 객체가 영원히 남는" 쪽은 `-1`이 유실돼 카운터가 0에 닿지 못하는 경우라, 이 그림에는 없다.\
가운데 네 줄은 원문이 「원자적(atomic)이지 않다」고만 적은 것을 단계로 풀어 그린 것이다 — 원문은 단계를 이렇게 쪼개 적지 않는다.\
카운터 값 2와 3은 이 그림 안에서 고른 구체적인 값이다.

Python이 처음 만들어졌을 때 멀티코어·멀티스레드는 일반적이지 않았으므로, 가장 단순하고 확실한 해법이 채택되었다: **인터프리터 전체에 락을 하나만 두고, 한 시점에 하나의 스레드만 Python 바이트코드를 실행하게 한다.**\
이것이 GIL이다.\
GIL 덕분에 레퍼런스 카운팅을 비롯한 인터프리터 내부 자료구조가 락 없이도 스레드 안전해졌고, C 확장 모듈 역시 GIL을 전제로 단순하게 작성할 수 있었다.\
당시로서는 합리적인 엔지니어링 트레이드오프였다.

> **레퍼런스 카운팅(reference counting)** — 모든 객체가 자신을 가리키는 참조의 개수를 들고 다니다가, 0이 되는 즉시 메모리를 해제하는 방식.\
> 예: 원문이 적은 대로 참조가 생기면 `+1`, 사라지면 `-1`이다 — 이 `+1`/`-1`이 GIL의 뿌리다.

> **원자적(atomic)** — 중간에 다른 것이 끼어들 수 없이 한 덩어리로 끝나는 연산.\
> 예: 위 그림처럼 "읽고 → 더하고 → 쓰는" 사이에 다른 스레드가 끼어들 수 있으면 원자적이지 않은 것이다.

> **GIL(Global Interpreter Lock, 전역 인터프리터 락)** — 인터프리터 전체에 락을 하나만 두고, 한 시점에 하나의 스레드만 Python 바이트코드를 실행하게 하는 장치.\
> 예: 원문이 적은 대로 CPU 바운드 연산은 이 때문에 직렬화되지만, I/O 바운드 작업은 **대기 중 GIL을 놓아주므로** 멀티스레드가 여전히 유효하다(1.2절).

### 1.2 동시성의 한계

**대가는 무엇인가** — GIL의 대가는 명확하다.\
**CPU 바운드 작업에서 멀티스레드가 멀티코어를 활용하지 못한다.**\
스레드를 여러 개 띄워도 GIL을 쥔 하나만 실제로 실행되므로, 순수 Python 연산은 코어가 8개든 64개든 한 코어 속도에 묶인다.

```python
# CPU 바운드: 스레드를 늘려도 GIL 때문에 빨라지지 않는다
import threading
def crunch(n):
    while n > 0: n -= 1
threads = [threading.Thread(target=crunch, args=(10**8,)) for _ in range(4)]
# 4개를 동시에 돌려도 GIL이 직렬화 → 1개 돌릴 때와 비슷한 시간
```

```text
[ CPU 바운드 ]                             [ I/O 바운드 (파일·네트워크 대기) ]

스레드를 여러 개 띄워도                    대기 중 GIL을 놓아준다
GIL을 쥔 하나만 실제로 실행된다

코어가 8개든 64개든                        멀티스레드가 여전히 유효하다
한 코어 속도에 묶인다

  그리고 NumPy 같은 C 확장은 무거운 연산 동안 GIL을 해제해 병렬성을 얻는다
```

그림 해설 — 왼쪽 칸은 원문이 "GIL의 대가"로 적은 문장들이고, 오른쪽 칸은 바로 뒤의 "단, …" 문장이다.\
같은 행에 놓인 것은 원문이 "…하지 못한다 / 단, …에서는 여전히 유효하다"로 마주 놓은 짝이다.\
맨 아랫줄은 두 칸 어느 쪽에도 속하지 않는, 원문이 따로 덧붙인 한 문장이다.

> **CPU 바운드 / I/O 바운드** — 계산 자체에 시간이 드는 일 / 파일·네트워크 응답을 기다리는 데 시간이 드는 일.\
> 예: 위 코드의 `while n > 0: n -= 1`이 앞의 것이고, 원문이 "파일·네트워크 대기"라 적은 것이 뒤의 것이다.

단, I/O 바운드 작업(파일·네트워크 대기)에서는 대기 중 GIL을 놓아주므로 멀티스레드가 여전히 유효하다.\
또한 NumPy 같은 C 확장은 무거운 연산 동안 GIL을 해제해 병렬성을 얻는다.\
그럼에도 "순수 Python으로 멀티코어를 쓰려면 스레드가 아니라 `multiprocessing`(별도 프로세스)을 써야 한다"는 우회는 메모리 비용과 직렬화 오버헤드를 강요했고, 이것이 수십 년간 Python의 가장 유명한 약점으로 남았다.

### 1.3 제거 시도의 역사

| 시기 | 시도 | 결과 |
|------|------|------|
| 1999 | Greg Stein의 "free threading" 패치 | 단일 스레드 성능이 ~2배 느려져 거부 |
| 2007~ | Guido의 입장 정리 — "GIL을 없애되 단일 스레드를 느리게 하지 않는 패치라면 환영" | 사실상의 수용 기준 제시 |
| 2015~ | Larry Hastings의 "Gilectomy" 프로젝트 | 세밀한 락으로 단일 스레드가 크게 느려져 미완 |
| 2021~ | Sam Gross의 `nogil` 포크 (PEP 703의 전신) | 바이어스드 레퍼런스 카운팅 등으로 단일 스레드 부담을 최소화 |

표는 원문 그대로다(4행).

핵심 난제는 일관됐다: **GIL을 빼면 레퍼런스 카운팅을 스레드 안전하게 만들어야 하는데, 모든 `+1`/`-1`을 원자적 연산으로 바꾸면 단일 스레드 성능이 급락한다.**\
Gilectomy는 이 벽에 부딪혀 멈췄다.

### 1.4 PEP 684 — 인터프리터별 GIL (Python 3.12, 2023)

**무엇을 쪼갰나** — 본격적 제거에 앞서, **PEP 684**가 GIL을 "전역" 하나에서 **서브인터프리터(subinterpreter)별 하나**로 쪼갰다.\
그전까지는 한 프로세스 안에 서브인터프리터를 여러 개 만들어도 GIL이 단 하나라 동시에 하나만 실행됐다.\
PEP 684는 CPython 내부의 전역 상태를 인터프리터별 상태로 리팩터링해, **각 서브인터프리터가 자기 GIL을 갖고 병렬 실행**할 수 있게 했다(데이터 공유는 PEP 554 API가 담당).\
프로세스보다 가벼우면서 멀티코어를 쓰는 새 동시성 단위가 열린 것이다.

> **서브인터프리터(subinterpreter)** — 한 프로세스 안에 여러 개 만들 수 있는 인터프리터.\
> 예: 원문이 적은 대로 PEP 684 전에는 여럿을 만들어도 GIL이 단 하나라 동시에 하나만 실행됐다.

### 1.5 PEP 703 — GIL을 선택적으로 (free-threading, Python 3.13~)

**무엇을 열었나** — **PEP 703**은 Sam Gross의 `nogil` 작업을 표준화해, `--disable-gil` 빌드 플래그로 **GIL 없는 CPython("free-threaded build")**을 컴파일할 수 있게 했다.\
Steering Council이 2023년 10월 24일 단계적 도입을 전제로 승인했다:

- **Python 3.13 (2024)**: 실험적(experimental) free-threaded 빌드 제공
- **Python 3.14**: PEP 779에 따라 "지원되는(supported)" 상태로 승격
- **기본값 전환**: 향후 수년간 보류 — 기존 빌드는 여전히 GIL이 기본

free-threaded 빌드는 1.3절의 난제를 두 가지 핵심 기법으로 푼다:

- **바이어스드 레퍼런스 카운팅(biased reference counting)**: 객체를 주로 다루는 "소유자 스레드"는 빠른 비원자 카운터를, 다른 스레드는 별도의 공유 카운터를 쓴다.\
  흔한 단일 스레드 경로의 비용을 낮춘다.
- **pymalloc → mimalloc 교체**: 스레드 안전하면서 작은 할당에 강한 범용 할당자로 교체.

```bash
# free-threaded 빌드는 런타임에 GIL을 켜고 끌 수 있다
python3.13t -X gil=0 script.py        # GIL 비활성
PYTHON_GIL=0 python3.13t script.py    # 환경변수로도 제어
```

**대가는 무엇인가** — 대가도 명시됐다: free-threaded 빌드는 **단일 스레드 워크로드에서 GIL 빌드보다 약 10~15% 느리다**(스레드 안전 변형 연산 때문).\
즉 "공짜 점심"이 아니라, 멀티코어 병렬성과 단일 스레드 속도를 맞바꾸는 옵션으로 제공된다.\
30여 년 만에 GIL은 "제거"가 아니라 **"선택 가능"**이라는 형태로 풀려나고 있다.

## 2. CPython vs 대안 구현 — "Python"은 하나가 아니다

"Python"은 **언어 명세**이고, 그 명세를 실행하는 **구현체**는 여럿이다.\
우리가 흔히 쓰는 것은 C로 작성된 참조 구현 **CPython**이지만, 서로 다른 목표를 가진 대안들이 Python의 약점을 각자의 방식으로 공략해 왔다.

### 2.1 CPython — 참조 구현

- **무엇**: Guido가 처음 만든 C 기반 구현.\
  Python 소스를 바이트코드로 컴파일해 **스택 기반 인터프리터**가 실행한다.
- **왜 기준인가**: 모든 PEP가 먼저 적용되는 곳이며, C 확장 생태계(NumPy·pandas 등)가 CPython의 C-API를 전제로 만들어져 있다.
- **한계**: 인터프리터 방식이라 순수 Python 연산이 느리고, GIL에 묶여 있다.\
  이 두 약점이 아래 대안들을 낳았다.

> **바이트코드** — 소스를 인터프리터가 실행하기 좋은 중간 형태로 번역해 둔 것.\
> 예: 원문이 적은 대로 CPython은 소스를 바이트코드로 컴파일해 스택 기반 인터프리터가 실행한다. §7이 최적화하는 대상이 바로 이것이다.

### 2.2 PyPy — JIT로 빠른 Python

- **언제·왜**: 2007년경부터 본격화.\
  "CPython은 왜 느린가 — 인터프리터이기 때문"이라는 문제에 **JIT(Just-In-Time) 컴파일**로 답한다.
- **무엇**: 실행 중 "뜨거운(hot)" 코드 경로를 감지해 기계어로 컴파일한다.\
  순수 Python 연산이 많은 장기 실행 프로그램에서 CPython보다 수 배 빠를 수 있다.
- **독특한 점 — 메타트레이싱(meta-tracing)**: PyPy는 JIT을 직접 손으로 짜지 않는다.\
  **RPython**(Python의 제약된 부분집합)으로 인터프리터를 작성하면, RPython 툴체인이 그 인터프리터로부터 **추적 기반 JIT을 자동 생성**한다.\
  "JIT 컴파일러를 만드는 프레임워크"인 셈이라, 다른 언어에도 재사용할 수 있다.
- **한계**: C 확장 호환성(C-API 에뮬레이션 비용)과 JIT 워밍업 비용·메모리 사용량 때문에 CPython을 완전히 대체하지는 못했다.\
  하지만 PyPy의 성공은 "Python도 JIT으로 빨라질 수 있다"를 증명했고, 이는 §7의 CPython 자체 JIT화에 영감을 줬다.

> **JIT(Just-In-Time) 컴파일** — 미리 전부 번역해 두는 대신, 실행 중에 자주 쓰이는 부분만 골라 기계어로 번역하는 것.\
> 예: 원문 그대로 실행 중 "뜨거운(hot)" 코드 경로를 감지해 기계어로 컴파일하는 것.

### 2.3 Cython — Python을 C로 컴파일

- **언제·왜**: Pyrex(2002년경)에서 갈라져 나온 프로젝트.\
  "느린 부분만 골라 C 속도로"가 목표다.
- **무엇**: Python의 **상위집합(superset)** 언어.\
  변수에 C 타입(`cdef int i`)을 선언하면 Cython 컴파일러가 그 코드를 C로 번역해 컴파일된 확장 모듈로 만든다.\
  무거운 루프를 Cython으로 다시 쓰면 인터프리터 오버헤드 없이 네이티브 속도를 얻는다.
- **위치**: 대안 인터프리터가 아니라 **CPython과 함께 쓰는 가속 도구**.\
  NumPy·SciPy·scikit-learn 등 과학 계산 생태계가 핵심 커널을 Cython으로 작성해 왔다.

> **상위집합(superset)** — 원래 언어를 전부 포함하면서 표기를 더 얹은 언어.\
> 예: 원문이 든 `cdef int i` — Python 문법에 C 타입 선언이 더해진 자리다.

### 2.4 Jython · IronPython — 다른 VM 위의 Python

- **Jython**: C 대신 **Java**로 작성되어, Python 소스를 **JVM 바이트코드**로 컴파일한다.\
  JVM 위에서 돌기 때문에 Java 라이브러리를 그대로 호출할 수 있다.\
  흥미롭게도 **Jython에는 GIL이 없다** — JVM의 스레드/GC 위에 얹혀 있어 CPython의 레퍼런스 카운팅 제약을 물려받지 않기 때문이다.
- **IronPython**: 마찬가지로 **.NET CLR** 위에서 도는 구현.\
  .NET 생태계와의 상호운용이 목표.
- **한계**: 둘 다 CPython C-API 기반 확장(NumPy 등)을 쓸 수 없고, 최신 Python 버전 추격이 더디다.\
  그래서 특정 VM 통합이 필요한 틈새에서 주로 쓰인다.

```text
Python 소스 (언어 명세)
      |
      +--> CPython        C 인터프리터 + GIL
      +--> PyPy           메타트레이싱 JIT (RPython)
      +--> Cython         → C 컴파일 (가속 도구)
      +--> Jython         → JVM 바이트코드 (GIL 없음)
      +--> IronPython     → .NET CLR
```

그림 해설 — 원문 mermaid 그림을 글자로 옮긴 것이다. 마디 여섯과 화살표 다섯의 문구·방향은 원문 그대로다.\
마디 안의 `→`는 원문 마디 글자에 들어 있던 것이라 마디의 일부로 두었다.

요점: 각 구현은 CPython의 특정 약점(속도·VM 통합)을 공략하지만, **C 확장 생태계**라는 중력 때문에 CPython이 사실상의 표준 자리를 지켜 왔다.\
그리고 그 약점들은 이제 CPython **자신**이 free-threading(§1)과 JIT(§7)으로 흡수하는 중이다.

## 3. 동적 타이핑 — 자유와 그 대가

### 3.1 무엇이고 왜 그랬나

Python은 처음부터 **동적 타이핑(dynamic typing)** 언어다.\
변수에는 타입이 없고 **객체에 타입이 있다.**\
변수는 그저 객체를 가리키는 이름표이며, 같은 이름이 차례로 정수·문자열·리스트를 가리켜도 문제없다.\
타입 검사는 컴파일 시점이 아니라 **실행 시점**에, 연산을 실제로 시도할 때 이뤄진다.

```python
x = 42          # x는 지금 int 객체를 가리킨다
x = "hello"     # 이제 str 객체를 가리킨다 — 합법
x = [1, 2, 3]   # 이제 list — 역시 합법
```

> **동적 타이핑(dynamic typing)** — 변수에는 타입이 없고 **객체에 타입이 있는** 방식. 타입 검사는 컴파일 시점이 아니라 실행 시점에, 연산을 실제로 시도할 때 이뤄진다.\
> 예: 위 코드에서 `x`가 차례로 `int`·`str`·`list`를 가리켜도 합법이다 — 타입이 없어진 것이 아니라, 변수가 아니라 객체가 타입을 갖고 있기 때문이다.

여기에 **덕 타이핑(duck typing)**이 더해진다: "오리처럼 걷고 운다면 오리로 취급한다" — 객체의 **선언된 타입**이 아니라 **실제로 가진 메서드/속성**만 보고 동작한다.\
함수는 인자가 무슨 타입인지 묻지 않고, 필요한 메서드(`.read()`, `__len__()` 등)가 있으면 그냥 쓴다.

```python
def total_length(items):
    return sum(len(x) for x in items)   # x가 len()을 지원하기만 하면 된다
total_length(["ab", "cde"])             # 5  — 문자열
total_length([[1,2], [3,4,5]])          # 5  — 리스트도 OK
```

> **덕 타이핑(duck typing)** — 객체의 **선언된 타입**이 아니라 **실제로 가진 메서드/속성**만 보고 동작하는 것.\
> 예: 위 코드의 `total_length`는 인자가 무슨 타입인지 묻지 않고, `len()`을 지원하는지만 본다 — 그래서 문자열도 리스트도 통과한다.

이 설계의 **이유**는 Python의 철학과 직결된다 — 빠른 프로토타이핑, 적은 보일러플레이트, 유연한 추상화.\
인터페이스를 미리 선언하지 않아도 협력하는 코드를 짤 수 있어 생산성이 높다.

### 3.2 대가

자유에는 비용이 따른다.\
타입 오류가 **런타임에야** 드러나므로, 실행되지 않은 분기에 숨은 `AttributeError`·`TypeError`가 프로덕션에서 터질 수 있다.\
IDE는 변수 타입을 확신하지 못해 자동완성·리팩터링 지원이 약하고, 대규모 코드베이스에서는 "이 함수가 대체 뭘 받고 뭘 돌려주나"를 코드만 보고 알기 어렵다.\
이 대가가 커질수록 — 특히 Python이 소규모 스크립트를 넘어 대형 시스템에 쓰이면서 — 다음 절의 **점진적 타이핑** 수요가 자라났다.

## 4. 점진적 타이핑 — 동적 언어에 타입을 "선택적으로"

### 4.1 언제·왜 도입했나

**언제·왜** — 대형 코드베이스(특히 Dropbox 등)에서 동적 타이핑의 유지보수 비용이 커지자, **타입을 강제하지 않되 원하는 곳에 선택적으로 붙일 수 있는** 방식 — **점진적 타이핑(gradual typing)** — 이 필요해졌다.\
그 출발점이 Jukka Lehtosalo의 독립 정적 타입 검사기 **mypy**였다.

| 시기 | 사건 |
|------|------|
| ~2012 | Jukka Lehtosalo가 독립 도구 **mypy** 개발 (별도 문법 기반) |
| 2014-09 | **PEP 484 (Type Hints)** 작성 — Guido van Rossum·Jukka Lehtosalo·Łukasz Langa 공저 |
| 2015-01 | Guido가 PEP 484 첫 초안 공개 |
| 2015-09 | **Python 3.5** — `typing` 모듈과 함께 타입 힌트 정식 도입 |
| 2016 | **Python 3.6** — PEP 526 변수 어노테이션(`x: int = 0`) 추가 |

표는 원문 그대로다(5행).

mypy가 쓰던 별도 문법을 **언어 표준 문법으로 흡수한 것이 PEP 484**다.\
Python 3.0이 이미 도입해 둔 **함수 어노테이션 문법**(PEP 3107)이 그릇 역할을 했다.

### 4.2 무엇을 해결하나 (그리고 무엇을 하지 않나)

```python
from typing import Optional

def greet(name: str, times: int = 1) -> str:
    return ("Hi " + name + "! ") * times

def find_user(uid: int) -> Optional[str]:   # str 또는 None
    ...
```

핵심 설계 결정은 **"런타임에는 타입 검사를 하지 않는다"**이다.\
어노테이션은 `__annotations__` 속성으로 런타임에 접근할 수 있을 뿐, 인터프리터는 이를 강제하지 않는다.\
실제 검사는 **별도의 오프라인 도구**(mypy, pyright 등)가 소스를 훑어 수행한다 — 사용자가 자발적으로 돌리는 검사다.

```text
[ 런타임 — 인터프리터 ]                  [ 오프라인 도구 — mypy, pyright 등 ]

어노테이션을 __annotations__ 속성으로     소스를 훑어 실제 검사를 수행한다
접근할 수 있을 뿐,
인터프리터는 이를 강제하지 않는다         사용자가 자발적으로 돌리는 검사다

  핵심 설계 결정: "런타임에는 타입 검사를 하지 않는다"
```

그림 해설 — 두 칸의 문구는 원문 한 문단을 좌우로 나눠 놓은 것이다.\
같은 행에 놓인 것은 원문이 "…강제하지 않는다. 실제 검사는 …별도의 오프라인 도구가 …수행한다"로 마주 놓은 짝이다.\
맨 아랫줄은 그 문단이 먼저 못 박은 핵심 설계 결정이다.

> **타입 힌트 / 어노테이션(annotation)** — 함수·변수에 기대하는 타입을 적어 두는 표기.\
> 예: 위 코드의 `name: str`·`-> str` — 인터프리터는 이 표기를 **강제하지 않는다**. 원문의 핵심 설계 결정 그대로 "런타임에는 타입 검사를 하지 않는다"이고, 검사는 mypy·pyright 같은 별도 도구가 소스를 훑어 한다.\
> (3.1의 "타입 검사는 … 실행 시점에" 와 말이 겹치지만 가리키는 것이 다르다 — 그쪽은 **연산을 시도할 때 객체의 타입을 확인**하는 것이고, 여기서 하지 않는다는 것은 **어노테이션과 실제 값을 대조**하는 것이다. 앞의 검사는 지금도 실행 시점에 일어난다.)

> **점진적 타이핑(gradual typing)** — 타입을 강제하지 않되 원하는 곳에 선택적으로 붙일 수 있는 방식.\
> 예: 원문이 적은 대로 타입을 안 붙인 코드는 그대로 동작한다 — 레거시에 한꺼번에 달 필요 없이 중요한 곳부터 하나씩 붙이면 된다.

- **해결하는 것**: 정적 분석으로 버그를 실행 전에 잡고, IDE의 자동완성·리팩터링·문서화를 강화하며, 대형 코드베이스의 인터페이스 계약을 명문화한다.\
  PEP의 표현대로 **가장 중요한 목표는 정적 분석**이다.
- **유지하는 것**: 타입을 안 붙인 코드는 그대로 동작한다(동적 타이핑과 100% 공존).\
  이것이 "점진적(gradual)" — 레거시에 한꺼번에 타입을 달 필요 없이, 중요한 곳부터 하나씩 붙이면 된다.

### 4.3 이후 진화

PEP 484는 시작일 뿐이었다.\
제네릭(`List[int]`), 프로토콜(PEP 544, 구조적 서브타이핑으로 덕 타이핑을 정적으로 표현), 데이터클래스, `TypedDict`, 그리고 Python 3.9+의 내장 제네릭(`list[int]`)·`X | Y` 유니언 문법(PEP 604)으로 타입 시스템은 계속 풍부해졌다.\
동적 언어 위에 정적 타입 레이어를 "선택적으로" 얹는 실험은 현대 Python의 가장 큰 흐름 중 하나가 되었다.

## 5. async 모델 — 제너레이터에서 async/await까지

Python의 비동기 동시성은 **하나의 혈통**을 따라 진화했다: 제너레이터의 "실행을 멈췄다 재개하는" 능력이 코루틴이 되고, 코루틴이 이벤트 루프를 만나 asyncio가 되고, 마지막으로 전용 문법 `async`/`await`로 독립했다.\
GIL(§1) 때문에 CPU 병렬화가 막힌 Python이 **I/O 동시성**을 푸는 주된 길이었다.

### 5.1 제너레이터 (PEP 255, Python 2.2 / 2001)

**무엇인가** — 모든 것의 씨앗.\
`yield`를 쓴 함수는 호출 시 즉시 실행되지 않고 **제너레이터 객체**를 돌려주며, `yield`에서 **실행을 멈추고 값을 내보낸 뒤, 다음 요청에 그 자리에서 재개**한다.\
"함수의 실행 상태를 보존했다 재개한다"는 이 능력이 이후 모든 코루틴의 토대다.

```python
def count_up(n):
    i = 0
    while i < n:
        yield i      # 여기서 멈췄다가, next() 호출 때 재개
        i += 1
```

```text
count_up(n) 을 부르면

  호출
    |
    v
  제너레이터 객체를 돌려준다            ← 즉시 실행되지 않는다
    |
    |  next()
    v
  i = 0 까지 가서 yield i 에서 멈춘다   → 0 을 내보낸다
    |
    |  next()
    v
  멈췄던 그 자리에서 재개해 i += 1      → 다음 yield i 에서 다시 멈추고 1 을 내보낸다
```

그림 해설 — 오른쪽 세 마디는 원문 문장("호출 시 즉시 실행되지 않고 제너레이터 객체를 돌려주며, `yield`에서 실행을 멈추고 값을 내보낸 뒤, 다음 요청에 그 자리에서 재개")과 코드 주석("여기서 멈췄다가, next() 호출 때 재개")에서 그대로 왔다.\
0과 1은 위 코드의 `i = 0`과 `i += 1`에서 나온 값이다.

> **제너레이터(generator)** — `yield`를 쓴 함수. 호출하면 즉시 실행되지 않고 제너레이터 객체를 돌려주며, `yield`에서 멈추고 값을 내보낸 뒤 다음 요청에 그 자리에서 재개한다.\
> 예: 위 코드의 `count_up` — `next()`를 부를 때마다 값 하나가 나오고, 함수는 그 자리에 멈춰 선 채로 남는다.

### 5.2 향상된 제너레이터 = 코루틴 (PEP 342, Python 2.5 / 2006)

**무엇이 더해졌나** — `yield`를 **표현식**으로 만들어, 제너레이터가 값을 내보낼 뿐 아니라 `.send()`로 **값을 받을** 수도 있게 했다.\
단방향 이터레이터였던 제너레이터가 **양방향 통신 채널** — 즉 코루틴 — 이 되었다.\
"협력적으로 멈추고 재개하며 데이터를 주고받는" 동시성의 원형이 여기서 생겼다.

> **코루틴(coroutine)** — 협력적으로 멈추고 재개하며 데이터를 주고받는 실행 단위.\
> 예: 원문이 적은 대로 `.send()`로 값을 받을 수도 있게 된 제너레이터가 곧 코루틴이다.

### 5.3 yield from (PEP 380, Python 3.3 / 2012)

**무엇을 가능하게 했나** — 코루틴을 **위임(delegate)**하는 문법.\
`yield from sub()`는 하위 제너레이터에 실행과 값 전달을 통째로 위임해, 여러 코루틴을 깔끔하게 **연쇄**할 수 있게 했다.\
이는 코루틴으로 복잡한 비동기 스케줄러를 짤 수 있는 길을 닦았다 — 바로 다음 단계인 asyncio의 전제 조건이었다.

### 5.4 asyncio (PEP 3156, Python 3.4 / 2014)

**무엇을 모았나** — 흩어져 있던 비동기 패턴(Twisted·Tornado 등 서드파티가 각자 이벤트 루프를 만들던 시대)을 표준 라이브러리로 통합.\
**이벤트 루프 + `yield from` 기반 코루틴 스케줄러 + 퓨처/태스크**를 제공한다.

**무엇이 한계였나** — 이로써 "표준 비동기 I/O 프레임워크"가 생겼지만, 코루틴을 여전히 **제너레이터 문법(`yield from`)으로** 표현해야 하는 한계가 있었다.

> **이벤트 루프(event loop)** — 코루틴이 기다리는 동안 양보한 제어권을 받아 두었다가, 다음으로 이어 갈 곳에 넘겨 주는 쪽.\
> 예: 5.5절 코드 주석 그대로 `await asyncio.sleep(1)`이 "I/O 대기 동안 이벤트 루프에 제어권 양보"할 때, 그 제어권을 받는 쪽이 이것이다.

### 5.5 async / await (PEP 492, Python 3.5 / 2015)

**무엇이 독립했나** — 마지막 도약.\
**코루틴을 언어의 일급 기능으로 승격**하고 제너레이터와 명확히 분리했다.\
전용 키워드 `async def`로 코루틴을 정의하고 `await`로 다른 코루틴을 기다린다.

```python
import asyncio

async def fetch(url):
    await asyncio.sleep(1)        # I/O 대기 동안 이벤트 루프에 제어권 양보
    return f"data from {url}"

async def main():
    results = await asyncio.gather(fetch("a"), fetch("b"))  # 동시 실행
    print(results)

asyncio.run(main())
```

> **`await`** — 다른 코루틴을 기다리는 키워드.\
> 예: 위 코드 주석 그대로 `await asyncio.sleep(1)`은 "I/O 대기 동안 이벤트 루프에 **제어권 양보**"다 — 원문은 모든 `await`가 결국 어딘가의 `yield`로 **일시정지**된다고 적는다.

**왜 필요했나** — PEP 492가 명시한 동기는 이렇다: 기존 방식은 코루틴과 일반 제너레이터가 **같은 `yield` 문법을 공유**해 혼동되기 쉬웠고, 함수가 코루틴인지 아닌지가 본문에 `yield`가 있느냐로 암묵 결정됐으며, `await`를 쓸 수 있는 위치도 `yield`가 허용되는 곳으로 제한됐다.\
`async`/`await`는 이 모호함을 없애 **특정 라이브러리(asyncio)에 의존하지 않고도 코루틴을 신뢰성 있게 정의**할 수 있게 했다.\
내부적으로 코루틴은 여전히 특수한 제너레이터이며, 모든 `await`는 결국 어딘가의 `yield`로 일시정지된다 — 5.1의 씨앗이 그대로 살아 있다.

```text
제너레이터        PEP 255 (2.2)    yield로 멈춤/재개
     |
     v
코루틴            PEP 342 (2.5)    send()로 양방향
     |
     v
yield from        PEP 380 (3.3)    위임/연쇄
     |
     v
asyncio           PEP 3156 (3.4)   이벤트 루프
     |
     v
async/await       PEP 492 (3.5)    일급 코루틴 문법
```

그림 해설 — 원문 mermaid 그림을 글자로 옮긴 것이다. 마디 다섯과 화살표 넷의 문구·방향은 원문 그대로이고, 가로로 놓인 것을 세로로 폈을 뿐이다.

이후 Python 3.6은 비동기 제너레이터(PEP 525)와 비동기 컴프리헨션(PEP 530)을 더해 async 생태계를 완성했다.

## 6. 메모리·GC — 레퍼런스 카운팅 + 순환 수집기

### 6.1 1차 메커니즘 — 레퍼런스 카운팅

**무엇인가** — CPython의 메모리 관리 **주 엔진**은 처음부터 **레퍼런스 카운팅**이다(§1.1에서 GIL의 원인이기도 했던 바로 그 메커니즘).\
모든 객체는 참조 카운트를 들고 있고, 참조가 생기면 증가·사라지면 감소하며, **0이 되는 즉시** 메모리를 해제한다.

- **장점**: 메모리가 **결정론적·즉시** 회수된다.\
  객체가 마지막으로 쓰인 직후 해제되므로 메모리 사용이 예측 가능하고, 별도의 "멈춤(stop-the-world)" 없이 점진적으로 정리된다.
- **치명적 약점**: **순환 참조(reference cycle)를 회수하지 못한다.**\
  두 객체가 서로를 가리키면, 외부에서 아무도 둘을 참조하지 않게 되어도 카운트가 1 밑으로 내려가지 않아 영원히 살아남는다 — 메모리 누수.

```python
a = {}
b = {}
a['b'] = b      # a → b
b['a'] = a      # b → a  (순환!)
del a, b        # 외부 참조는 사라졌지만, 서로의 카운트가 1로 남아 해제 안 됨
```

```text
del a, b  전
  이름 a ──> {첫째 dict}
  이름 b ──> {둘째 dict}
  {첫째 dict} ──> {둘째 dict}      (a['b'] = b)
  {첫째 dict} <── {둘째 dict}      (b['a'] = a)

del a, b  후
  이름 a·b 가 사라진다
  {첫째 dict} ──> {둘째 dict}
  {첫째 dict} <── {둘째 dict}      서로의 카운트가 1로 남아 해제 안 됨
```

그림 해설 — 위 칸은 다섯 줄짜리 위 코드에서 앞 네 줄이 만든 상태이고, 아래 칸은 마지막 줄 `del a, b` 뒤의 상태다.\
아래 칸 마지막 줄은 그 코드 줄의 주석("외부 참조는 사라졌지만, 서로의 카운트가 1로 남아 해제 안 됨")을 그대로 옮긴 것이다.\
두 dict 를 「첫째·둘째」로 부른 것은 그림 안에서 구분하려고 붙인 이름이다 — 원문은 `a`·`b`라는 이름만 쓴다.

> **순환 참조(reference cycle)** — 두 객체가 서로를 가리켜, 외부에서 아무도 참조하지 않게 되어도 카운트가 1 밑으로 내려가지 않는 상태.\
> 예: 위 코드의 `a['b'] = b`와 `b['a'] = a` — `del a, b` 뒤에도 둘은 해제되지 않는다.

> **멈춤(stop-the-world)** — 정리를 하려고 프로그램 전체를 잠시 세우는 것.\
> 예: 원문이 레퍼런스 카운팅의 장점으로 든 것이 바로 이것 **없이** 점진적으로 정리된다는 점이다.

### 6.2 2차 메커니즘 — 순환 GC (gc 모듈, Python 2.0 / 2000)

**무엇을 메웠나** — 6.1의 누수를 메우려고 **Python 2.0**에서 **순환 가비지 컬렉터**가 추가됐다(`gc` 모듈).\
이것이 레퍼런스 카운팅을 **보완**한다 — 컨테이너 객체(리스트·딕트·인스턴스 등 다른 객체를 담을 수 있는 것)들을 추적하다가, **외부에서 도달 불가능하지만 자기들끼리만 참조하는** 순환을 탐지해 끊고 회수한다.

흔히 그냥 "GC"라 부르지만, 엄밀히는 **레퍼런스 카운팅도 일종의 가비지 컬렉션**이며 순환 수집기는 그 위에 얹힌 두 번째 층이다.\
순환을 절대 만들지 않는다고 확신하면 `gc.disable()`로 끌 수도 있다.

### 6.3 세대별 수집 (generational)

**왜 나눴나** — 순환 수집은 모든 컨테이너 객체를 훑어야 해 비싸다.\
비용을 줄이려 **세대 가설**을 도입했다: "대부분의 객체는 수명이 매우 짧다."\
객체를 **3개 세대(0·1·2)**로 나눠, 새 객체는 0세대에서 시작한다.\
수집을 견뎌낸(오래 산) 객체는 윗세대로 승격되고, **젊은 세대를 더 자주, 늙은 세대를 드물게** 수집한다.\
단명 객체는 0세대 수집에서 대부분 회수되므로, 전체 힙을 매번 훑는 비용을 피한다.

```text
새 컨테이너 객체
      |
      v
세대 0 (가장 자주 수집)
      |  수집 생존
      v
세대 1 (가끔 수집)
      |  수집 생존
      v
세대 2 (드물게 수집)

레퍼런스 카운트 == 0
→ 즉시 해제 (세대 무관)
```

그림 해설 — 원문 mermaid 그림을 글자로 옮긴 것이다. 마디 다섯과 화살표 셋의 문구·방향은 원문 그대로다.\
맨 아래 마디는 원문 그림에서도 화살표 없이 따로 놓여 있다 — 세대와 무관한 경로라는 뜻이다.

요약하면 CPython의 메모리 모델은 **두 축의 협업**이다: 레퍼런스 카운팅이 비순환 객체의 99%를 즉시·결정론적으로 치우고, 세대별 순환 수집기가 남은 순환 쓰레기를 주기적으로 청소한다.\
이 모델의 결정론성은 큰 장점이지만, 모든 객체가 카운터를 들고 다녀야 한다는 점이 바로 free-threading(§1.5)을 어렵게 만든 근본 원인이었다 — 개념들이 어떻게 얽혀 있는지를 다시 보여준다.

## 7. 인터프리터 최적화 — Faster CPython과 JIT화

**무엇이 바뀌었나** — 오랫동안 "느린 인터프리터"는 CPython의 숙명처럼 여겨졌고, 속도는 PyPy(§2.2) 같은 대안의 몫이었다.\
2020년경 Mark Shannon이 제안한 **다개년 성능 로드맵(Faster CPython / "Shannon Plan")**과 Microsoft의 지원으로 흐름이 바뀌었다 — **CPython 자신이** 단계적으로 빨라지기 시작했다.

### 7.1 특수화 적응형 인터프리터 (PEP 659, Python 3.11 / 2022)

**무엇인가** — Python 3.11의 핵심.\
**특수화 적응형 인터프리터(Specializing Adaptive Interpreter)**는 실행 중인 바이트코드 명령을 관찰하다가, **그 자리에서(in-place)** 타입에 특화된 버전으로 **바이트코드를 다시 쓴다.**

작동 원리: 예컨대 `a + b`를 실행하는 범용 `BINARY_OP` 명령은, 실제로 흐르는 값이 매번 정수임을 관찰하면 자신을 정수 전용 고속 명령(`BINARY_OP_ADD_INT` 같은)으로 교체한다.\
타입 검사·디스패치 오버헤드를 건너뛰어 빨라진다.\
가정이 깨지면(다른 타입이 들어오면) **빠르게 범용 버전으로 되돌린다(de-optimize)** — "공격적으로 특수화하되, 아주 좁은 영역에서, 실수 시 저비용으로 즉시 복구"가 설계 모토다.\
Python 3.11이 3.10 대비 평균 ~25% 빨라진 주된 동력이었다.

```text
  범용 바이트코드     ──── 실행 관찰: 계속 int ────>     특수화 명령
  BINARY_OP                                             BINARY_OP_ADD_INT (고속)
       ^                                                      |
       └──────────── 가정 위반: str 등장 ─────────────────────┘
```

그림 해설 — 원문 mermaid 그림을 글자로 옮긴 것이다. 마디 둘과 화살표 둘의 문구·방향은 원문 그대로다.\
되돌아가는 아래 화살표가 원문이 "빠르게 범용 버전으로 되돌린다(de-optimize)"고 적은 경로다.

> **특수화(specialization)** — 실제로 흐르는 값을 보고, 그 경우에만 맞는 빠른 버전으로 갈아 끼우는 것.\
> 예: 원문이 든 대로 범용 `BINARY_OP`가 값이 매번 정수임을 관찰하면 `BINARY_OP_ADD_INT` 같은 정수 전용 명령으로 자신을 교체한다.

> **역최적화(de-optimize)** — 특수화의 가정이 깨졌을 때 범용 버전으로 되돌리는 것.\
> 예: 위 그림의 아래 화살표 — 정수만 오던 자리에 `str`이 등장하면 되돌아간다.

### 7.2 JIT 컴파일 (PEP 744, Python 3.13 / 2024)

**무엇을 얹었나** — Python 3.13은 **실험적 JIT 컴파일러**를 도입했다.\
7.1의 특수화 인터프리터가 **수집해 둔 런타임 프로파일 정보**를 활용해 "뜨거운" 경로를 탐지하고, 그 부분을 기계어로 컴파일한다 — 즉 PEP 659가 닦아 둔 프로파일링 기반 위에 JIT을 얹은 구조다.

기법은 **copy-and-patch 컴파일**: 미리 컴파일해 둔 작은 기계어 "스텐실(stencil)" 조각들을 런타임에 복사하고 구멍(피연산자 주소 등)을 메워 붙이는, **매우 빠른** 코드 생성 방식이다.\
전통적 JIT(LLVM 등)이 무거운 컴파일 백엔드와 긴 빌드를 요구하는 데 비해, copy-and-patch는 빌드·실행 비용이 가볍다.\
Python 3.13 시점에서는 아직 실험적이라 기본 비활성이며, 성능 이득은 점진적으로 키워가는 중이다.

> **copy-and-patch 컴파일 / 스텐실(stencil)** — 미리 컴파일해 둔 작은 기계어 조각을 복사하고, 비워 둔 구멍만 메워 붙이는 코드 생성 방식 / 그 조각.\
> 예: 원문이 든 구멍이 "피연산자 주소 등"이다. 원문은 이 방식이 전통적 JIT보다 빌드·실행 비용이 가볍다고 적는다.

요점: CPython은 §2의 대안들이 보여준 길(JIT·특수화)을 **자기 본체로 흡수**하고 있다.\
"Python을 빠르게 하려면 다른 구현으로 갈아타라"는 오랜 통념이, 참조 구현 스스로의 진화로 흐려지는 국면이다 — GIL(§1)과 더불어, 2020년대 CPython의 두 거대한 자기 갱신 축이다.

## 정리: 얽혀 있는 진화

*(이 편의 「남긴 것」에 해당한다 — 원문에는 별도의 「영향과 의의」 절이 없고, 이 절이 문서의 결론이다.)*

| 개념 | 언제 | 핵심 동기 | 무엇을 해결했나 |
|------|------|-----------|-----------------|
| GIL | ~1992 | 레퍼런스 카운팅을 스레드 안전하게 (단순화) | 인터프리터·C확장 동시성 안전 / 멀티코어를 막은 대가 |
| 인터프리터별 GIL (PEP 684) | 3.12 (2023) | 서브인터프리터 병렬화 | GIL을 인터프리터 단위로 분할 |
| free-threading (PEP 703) | 3.13 (2024)~ | GIL 자체를 선택적으로 | 멀티코어 병렬 ↔ 단일 스레드 ~10–15% 비용 트레이드오프 |
| 대안 구현 (PyPy·Cython·Jython) | 2000년대~ | CPython의 속도·VM 한계 공략 | JIT·C가속·JVM통합 (C확장 생태계 중력은 못 넘음) |
| 점진적 타이핑 (PEP 484) | 3.5 (2015) | 동적 타이핑의 유지보수 비용 | 선택적 정적 분석 — 런타임 강제 없음, mypy 흡수 |
| async/await (PEP 255→492) | 2.2→3.5 | GIL 우회한 I/O 동시성 | 제너레이터 혈통을 일급 코루틴 문법으로 |
| 순환 GC (gc, 세대별) | 2.0 (2000) | 레퍼런스 카운팅이 순환 누수 | 결정론적 회수 + 순환 청소의 2층 구조 |
| 특수화 인터프리터 (PEP 659) | 3.11 (2022) | "느린 인터프리터" 탈피 | 바이트코드 in-place 타입 특수화 |
| JIT (PEP 744) | 3.13 (2024) | 핫 경로 기계어화 | copy-and-patch JIT (PEP 659 프로파일 활용) |

표는 원문 그대로다(9행).

세 가닥의 인과가 이 표를 관통한다: **레퍼런스 카운팅 → GIL → async 모델**(메모리 모델이 동시성 방향을 결정), **동적 타이핑 → 점진적 타이핑**(자유의 대가를 선택적 타입으로 보완), **대안 구현의 JIT/특수화 → CPython 자신의 JIT화**(외부 실험의 본체 흡수).\
Python의 개념사는 단발적 기능 추가의 나열이 아니라, **초기 설계 결정이 낳은 제약을 수십 년에 걸쳐 되갚아 온 과정**이다.

## 용어 풀이

- **개념사** — 제품이 아니라 그 제품들이 공유하는 장치와 아이디어의 계보.
- **레퍼런스 카운팅** — 객체가 자신을 가리키는 참조 개수를 들고 다니다가 0이 되는 즉시 해제하는 방식.
- **원자적(atomic)** — 중간에 다른 것이 끼어들 수 없이 한 덩어리로 끝나는 연산.
- **GIL(전역 인터프리터 락)** — 한 시점에 하나의 스레드만 Python 바이트코드를 실행하게 하는 장치.
- **CPU 바운드 / I/O 바운드** — 계산 자체에 시간이 드는 일 / 파일·네트워크 응답을 기다리는 데 시간이 드는 일.
- **서브인터프리터** — 한 프로세스 안에 여러 개 만들 수 있는 인터프리터(PEP 684가 각자에게 GIL을 줬다).
- **바이어스드 레퍼런스 카운팅** — 소유자 스레드는 빠른 비원자 카운터를, 다른 스레드는 별도의 공유 카운터를 쓰는 기법.
- **언어 명세 / 구현체** — "이 언어는 이렇게 동작한다"는 규정 / 그 규정대로 실제로 돌려 주는 프로그램.
- **바이트코드** — 소스를 인터프리터가 실행하기 좋은 중간 형태로 번역해 둔 것.
- **JIT(Just-In-Time) 컴파일** — 실행 중에 자주 쓰이는 부분만 골라 기계어로 번역하는 것.
- **메타트레이싱** — JIT을 손으로 짜는 대신, 인터프리터로부터 추적 기반 JIT을 자동 생성하는 PyPy의 방식.
- **상위집합(superset)** — 원래 언어를 전부 포함하면서 표기를 더 얹은 언어(Cython).
- **동적 타이핑** — 변수에는 타입이 없고 객체에 타입이 있으며, 검사가 실행 시점에 이뤄지는 방식.
- **덕 타이핑** — 선언된 타입이 아니라 실제로 가진 메서드/속성만 보고 동작하는 것.
- **점진적 타이핑** — 타입을 강제하지 않되 원하는 곳에 선택적으로 붙일 수 있는 방식.
- **타입 힌트 / 어노테이션** — 기대하는 타입을 적어 두는 표기. 인터프리터가 이를 강제하지 않는다.
- **제너레이터** — `yield`를 쓴 함수. 호출하면 즉시 실행되지 않고, 멈췄다 그 자리에서 재개한다.
- **코루틴** — 협력적으로 멈추고 재개하며 데이터를 주고받는 실행 단위.
- **이벤트 루프** — 코루틴이 기다리는 동안 양보한 제어권을 받아 두었다가 다음으로 이어 갈 곳에 넘겨 주는 쪽.
- **`await`** — 다른 코루틴을 기다리는 키워드. 기다리는 동안 이벤트 루프에 제어권을 양보한다.
- **순환 참조** — 두 객체가 서로를 가리켜 카운트가 1 밑으로 내려가지 않는 상태.
- **멈춤(stop-the-world)** — 정리를 하려고 프로그램 전체를 잠시 세우는 것.
- **컨테이너 객체** — 다른 객체를 담을 수 있는 객체(리스트·딕트·인스턴스 등).
- **세대 가설** — "대부분의 객체는 수명이 매우 짧다"는 전제.
- **특수화 / 역최적화(de-optimize)** — 흐르는 값에 맞춘 빠른 버전으로 갈아 끼움 / 가정이 깨지면 되돌림.
- **copy-and-patch 컴파일 / 스텐실** — 미리 컴파일해 둔 기계어 조각을 복사하고 구멍만 메워 붙이는 코드 생성 / 그 조각.
