## 한눈에 — 쉽게 말하면

원문이 제목 아래에 적은 한 줄 요약은 이것이다.

> 한 사람이 크리스마스 휴가에 취미로 시작한 언어가, 가독성이라는 단일한 신념을 끝까지 밀어붙여 세계에서 가장 널리 쓰이는 언어 중 하나가 되기까지의 첫 17년. ABC의 교훈을 물려받은 0.9.0에서 출발해, 모든 것이 객체가 되는 2.x로 성숙하기까지의 기록이다.

이 17년을 하나의 비유로 읽으면 **잘 지었는데 문이 없던 집**의 이야기다.\
방 배치는 훌륭한데 밖으로 드나들 문이 없어서 아무도 살지 않게 된 집이 있고,\
그 방 배치는 그대로 베끼되 문을 하나 낸 집이 그 옆에 세워진다.\
**ABC와 Python도 똑같은 구조다** — 원문 표현으로 ABC는 "연결할 통로가 없었"고, Python은 "모듈 시스템으로 외부 확장 통로를 열어 둔 것이 결정적 차이였다".

본문 흐름에 쓰는 비유는 이 집 하나뿐이고, 용어 블록에서 「값을 담는 그릇」이라는 국소 비유를 한 번 더 쓴다.

| 비유 | 실체 |
|------|------|
| 방 배치는 훌륭한데 드나들 문이 없는 집 | ABC — "닫힌 설계 탓에 사용자가 확장할 수 없었고", "운영체제나 외부 라이브러리와 연결할 통로가 없었"다 |
| 그 집의 좋은 방 배치는 그대로 베낀다 | "가독성·들여쓰기·고수준 자료형"을 ABC에서 물려받은 것 |
| 대신 밖으로 나가는 문을 낸다 | "C 모듈로 언제든 확장할 수 있는 개방형 구조" |

## 시대 개요

*(아래 다섯 줄은 원문의 불릿 그대로다.)*

- 착수: 1989년 12월, 네덜란드 CWI(Centrum Wiskunde & Informatica)
- 창시자: 귀도 반 로섬(Guido van Rossum) — 훗날 "BDFL(Benevolent Dictator For Life, 자비로운 종신 독재자)"로 불린다
- 첫 공개: 1991년 2월, Python 0.9.0 (alt.sources 뉴스그룹에 게시)
- 이름의 유래: 영국 코미디 그룹 *몬티 파이썬의 비행 서커스(Monty Python's Flying Circus)* — 뱀이 아니다
- 이 문서의 범위: 0.9.0 → 1.x → 2.0(2000) → 2.2(2001) → 2.6(2008). Python 3.0 직전까지.

> **BDFL(Benevolent Dictator For Life)** — 원문이 괄호 안에 적어 둔 대로 "자비로운 종신 독재자"다. 공동체가 합의하지 못할 때 최종 결정을 내리는 한 사람을 가리키는 별칭인데, **이 뜻풀이는 원문에 없는 보충이다** — 원문은 괄호 안의 우리말 이름까지만 적는다.\
> 예: 원문은 이 말을 귀도 반 로섬 한 사람에게 붙이고, 마지막 절에서 "PEP 프로세스와 BDFL 모델"을 한 묶음의 제도로 든다.

## 시대적 배경

### ABC라는 실패한 스승

1980년대 후반, 귀도 반 로섬은 CWI에서 **ABC**라는 교육용 언어 프로젝트에 참여하고 있었다.\
ABC는 초보자도 쉽게 배울 수 있도록 설계된 언어로, 들여쓰기로 블록을 표현하고, 고수준 자료형(리스트·딕셔너리에 해당하는 구조)을 내장하며, 컴파일 없이 바로 실행되는 등 당시로서는 앞선 아이디어를 담고 있었다.\
그러나 ABC는 실패했다.\
닫힌 설계 탓에 사용자가 확장할 수 없었고(파일 I/O조차 빈약했다), 운영체제나 외부 라이브러리와 연결할 통로가 없었기 때문이다.

> **블록(block)** — 여러 줄의 코드를 "여기서부터 여기까지가 한 덩어리"라고 묶은 것.\
> 예: 뒤에 나오는 0.9.0 코드에서 `def speak(self):` 아래로 한 단계 들여쓴 `raise NotImplementedError` 한 줄이 그 함수의 블록이다.

> **고수준 자료형** — 값을 여러 개 담아 두는 그릇을 언어가 처음부터 갖춰 둔 것. 원문은 ABC의 그것을 "리스트·딕셔너리에 해당하는 구조"라고 적는다.\
> 예: 뒤에 나오는 0.9.0 코드의 `['Eric', 'John', 'Graham']`이 `list`이고 `{'Eric': 40, 'John': 38}`이 `dict`다.

귀도는 ABC의 **좋은 아이디어(가독성·들여쓰기·고수준 자료형)는 살리되, 그 치명적 약점(확장 불가·고립)은 버리는** 언어를 원했다.\
이 한 문장의 괄호 두 개를 따로 떼어 적으면 이렇다.

- **살린 것(좋은 아이디어)** — 가독성 · 들여쓰기 · 고수준 자료형
- **버린 것(치명적 약점)** — 확장 불가 · 고립

마침 그는 Amoeba라는 분산 운영체제 프로젝트에서 시스템 관리 도구를 만들 언어가 필요했는데, C는 너무 저수준이었고 셸 스크립트는 너무 빈약했다.

**왜 Python이 나왔나** — 원문이 출발 동기로 적은 문장은 이것이다.

> 그 사이의 빈자리를 메우는 것이 Python의 출발 동기였다.

### "취미 프로젝트"

1989년 12월 크리스마스 연휴, 귀도는 시간을 보낼 "취미 프로그래밍 프로젝트"로 인터프리터를 만들기 시작했다.\
ABC에서 물려받은 들여쓰기 기반 문법, 예외 처리, 그리고 C 모듈로 언제든 확장할 수 있는 개방형 구조 — 이 세 가지가 처음부터 설계의 뼈대였다.\
**확장성**은 ABC가 죽은 이유에 대한 직접적인 응답이었다.

> **인터프리터(interpreter)** — 소스 코드를 받아 실행해 주는 프로그램. 원문은 귀도가 1989년 크리스마스 연휴에 만들기 시작한 것을 이 말로 부른다.\
> 예: 원문이 뒤에서 `>>> import this`를 쳐 보는 그 대화창이 인터프리터다.

> **모듈(module)** — 기능을 담아 두고 필요할 때 끌어다 쓰는 코드 묶음. 원문이 말하는 **C 모듈**은 그 묶음을 C 언어로 만들어 Python에 붙이는 것이다.\
> 예: 원문이 뒤에서 드는 `gc`(2.0)·`sets`(2.3)·`decimal`(2.4)이 전부 모듈이다.

## 주요 추가 기능 (언제·왜)

### Python 0.9.0 — 첫 공개 (1991년 2월)

첫 공개 버전에서 이미 오늘날 Python을 알아볼 수 있는 핵심이 갖춰져 있었다.\
**상속을 지원하는 클래스, 예외 처리, 함수, 그리고 핵심 자료형 `list`·`dict`·`str`**이 들어 있었다.

```python
# 0.9.0 시점에 이미 가능했던 코드의 모습
class Animal:
    def __init__(self, name):
        self.name = name
    def speak(self):
        raise NotImplementedError   # 예외도 처음부터 있었다

names = ['Eric', 'John', 'Graham']   # list
ages = {'Eric': 40, 'John': 38}      # dict
```

> **예외(exception)** — 실행 중에 문제가 생겼을 때 그 자리에서 조용히 멈추는 대신, "이런 문제가 났다"는 신호를 던져 올리는 것.\
> 예: 위 코드의 `raise NotImplementedError`가 그 신호를 던지는 줄이고, 원문은 바로 그 줄에 "예외도 처음부터 있었다"는 주석을 달아 두었다.

**왜 중요한가**: 대부분의 언어가 절차적 기능부터 시작해 객체지향을 나중에 덧붙인 것과 달리, Python은 첫날부터 클래스·예외·고수준 자료형을 내장했다.\
ABC의 "고수준 자료형을 언어에 박아 넣는다"는 철학을 계승하되, 모듈 시스템으로 외부 확장 통로를 열어 둔 것이 결정적 차이였다.

### Python 1.0 — 함수형 도구의 합류 (1994년 1월)

1.0에서 **`lambda`·`map`·`filter`·`reduce`**라는 함수형 프로그래밍 도구가 추가되었다.\
귀도의 회고에 따르면 이 기능들은 "이것들을 그리워하던 한 Lisp 해커가 동작하는 패치를 제출해 준 덕분에" 들어왔다.

```python
nums = [1, 2, 3, 4, 5]
squares = map(lambda x: x * x, nums)        # 함수형 변환
evens   = filter(lambda x: x % 2 == 0, nums)
total   = reduce(lambda a, b: a + b, nums)  # 1.0에서는 내장 함수
```

> **`lambda`** — 이름을 붙이지 않고 그 자리에서 만들어 쓰는 짧은 함수.\
> 예: 위 코드의 `lambda x: x * x`가 "받은 값을 제곱해 돌려주는 함수"이고, 이름 없이 `map`의 인자 자리에 바로 들어가 있다.

**왜 중요한가**: 외부 기여자의 패치가 언어 핵심에 반영된 이 사건은, Python이 한 사람의 폐쇄적 산물이 아니라 **커뮤니티 기여로 자라는 언어**임을 보여 준 초기 신호였다.\
(다만 귀도 자신은 함수형 스타일을 그리 좋아하지 않았고, 훗날 Python 3에서 `reduce`는 `functools`로 밀려난다.)

### 거주지의 변천 — CWI → CNRI → BeOpen

초기 Python은 만든 사람이 어디에 소속돼 있느냐에 따라 라이선스와 배포 주체가 바뀌는, 다소 불안정한 시기를 거쳤다.

- **CWI 시기 (~1995)**: 네덜란드 CWI에서 1.2까지 릴리스.
- **CNRI 시기 (1995~2000)**: 귀도가 미국 버지니아주 레스턴의 CNRI(Corporation for National Research Initiatives)로 옮겨 1.3~1.6을 릴리스. 이 무렵 `comp.lang.python` 뉴스그룹과 첫 워크숍이 생기며 커뮤니티가 형성된다.
- **BeOpen 시기 (2000)**: 핵심 개발팀이 BeOpen.com으로 옮겨 PythonLabs 팀을 꾸리고 **Python 2.0**을 릴리스. 이후 곧 Digital Creations(훗날 Zope Corporation)로 이동.

**왜 중요한가**: 1.6의 CNRI 라이선스에는 "버지니아주 법을 따른다"는 조항이 있었는데, 자유소프트웨어재단(FSF)은 이것이 GPL과 호환되지 않는다고 보았다.\
BeOpen·CNRI·FSF의 협상 끝에 GPL 호환 라이선스로 정리되었고, 이 과정이 오늘날 **Python Software Foundation 라이선스**의 토대가 되었다.\
언어의 기능사만큼이나 "누가 소유하고 어떤 라이선스로 푸는가"가 초기 Python의 운명을 좌우했다.

> **라이선스 호환** — 두 라이선스로 된 코드를 한데 묶어 배포해도 되는지의 문제.\
> 예: 원문이 든 것이 1.6의 "버지니아주 법을 따른다"는 조항이고, FSF는 그 조항 때문에 GPL과 호환되지 않는다고 보았다.

### Python 2.0 — 현대 Python의 시작 (2000년 10월 16일)

BeOpen에서 나온 단 하나의 릴리스이자, 오늘날 Python 코드의 관용구가 본격적으로 자리 잡은 분수령이다.

**1) 리스트 컴프리헨션 (List Comprehension)** — Haskell·SETL의 영향을 받아 도입. `map`/`filter`/`lambda`의 조합을 한 줄의 읽기 쉬운 식으로 대체한다.

```python
# 도입 전: 함수형 도구의 조합 또는 명시적 루프
squares = map(lambda x: x * x, range(10))

# 도입 후: 의도가 그대로 드러나는 표현식
squares = [x * x for x in range(10)]
evens   = [x for x in range(10) if x % 2 == 0]
```

- 위가 도입 전, 아래가 도입 후다 — 두 주석(`# 도입 전: …`, `# 도입 후: …`)도 원문이 붙여 둔 것이다.
- 같은 `squares`를 만드는 데 `map`과 `lambda`가 빠지고 `[x * x for x in range(10)]` 한 줄이 그 자리에 들어갔다.

> **리스트 컴프리헨션(list comprehension)** — 대괄호 안에 "무엇을, 어디서, 어떤 조건으로"를 한 줄에 적어 리스트를 만드는 식.\
> 예: 위 코드의 `[x for x in range(10) if x % 2 == 0]`에서 `x`가 무엇을, `for x in range(10)`이 어디서, `if x % 2 == 0`이 어떤 조건으로다.

**왜**: "읽기 좋은 코드"라는 Python의 핵심 가치를 문법 차원에서 구현한 대표 사례다.\
이후 딕셔너리·집합·제너레이터 컴프리헨션으로 확장되며 Python다움(Pythonic)의 상징이 된다.

**2) 순환 참조 탐지 가비지 컬렉터 (Cycle-detecting GC)** — Python은 원래 **참조 카운팅**으로 메모리를 관리했는데, 이 방식은 객체가 서로를 가리키는 **순환 참조**를 회수하지 못해 메모리 누수를 일으켰다.\
2.0은 참조 카운팅 위에 순환을 탐지해 끊어 주는 **세대별 보조 수집기**(`gc` 모듈)를 얹었다.

```python
a = {}
b = {}
a['b'] = b
b['a'] = a        # 서로를 가리키는 순환 — 참조 카운트는 0이 되지 않는다
del a, b          # 2.0 이전엔 누수, 2.0부터는 순환 수집기가 회수
```

위 코드의 `a`와 `b`가 어떤 모양이 되는지를 그림으로 보면 이렇다.

```text
del a, b 를 한 뒤의 모습

  이름 a  -X             이름 b  -X           (이름 쪽 연결은 끊겼다)

  +------------+   a['b']   +------------+
  |  딕셔너리  | ---------> |  딕셔너리  |
  |   (전 a)   | <--------- |   (전 b)   |
  +------------+   b['a']   +------------+

  두 객체는 서로를 가리키고 있어 "참조 카운트는 0이 되지 않는다"
```

- 화살표는 둘이고, 각각 원문 코드의 `a['b'] = b`와 `b['a'] = a` 한 줄씩이다.
- 맨 아래 따옴표 안은 원문 코드에 달린 주석을 그대로 옮긴 것이다.
- 2.0 이전에는 이 상태가 원문 표현대로 "누수"이고, 2.0부터는 "순환 수집기가 회수"한다.

> **참조 카운팅(reference counting)** — 어떤 객체를 가리키는 곳이 몇 개인지 세어 두었다가, 그 수가 0이 되면 메모리를 돌려주는 방식. 원문은 이것을 Python이 "원래" 쓰던 방식으로 적는다.\
> 예: 위 그림에서 이름 `a`·`b`를 지워도 두 딕셔너리가 서로를 가리키고 있어 세어 둔 수가 0이 되지 않는다.

> **메모리 누수(memory leak)** — 더 쓰지 않는 값이 메모리에서 회수되지 않고 계속 남아 있는 것.\
> 예: 위 코드의 `del a, b` 뒤에도 두 딕셔너리가 그대로 남아 있던 것이 원문이 말하는 "2.0 이전엔 누수"다.

> **세대별 보조 수집기** — 원문이 2.0이 얹은 것을 부르는 이름이자 `gc` 모듈의 정체다. 원문은 이 수집기가 하는 일을 "순환을 탐지해 끊어 주는" 것까지만 적고, "세대별"이 무슨 뜻인지는 적지 않는다.

**왜**: 장기 실행 서버나 GUI처럼 객체 그래프가 복잡해지는 프로그램에서 메모리 누수는 치명적이었다.\
이 변경으로 Python은 "오래 켜 두는" 응용에서도 신뢰할 수 있는 언어가 되었다.

**3) 유니코드 문자열 (Unicode)** — 2.0의 가장 큰 신규 기능. ASCII의 8비트를 넘어 다국어 문자를 표현하는 새 기본 자료형 `unicode`가 추가되었다.

```python
u = u"안녕하세요"      # u 접두사로 유니코드 리터럴
print len(u)           # 바이트가 아니라 문자 수로 센다
```

> **유니코드(Unicode)** — 세상의 문자마다 번호를 매겨 둔 약속. 원문은 이것을 "ASCII의 8비트를 넘어 다국어 문자를 표현하는" 것으로 적는다.\
> 예: 위 코드의 `print len(u)`가 세는 것이 무엇인지 원문 주석이 말해 준다 — "바이트가 아니라 문자 수로 센다".

**왜**: 인터넷이 영어권을 넘어 전 세계로 퍼지던 시기, 다국어 텍스트 처리는 필수가 되어 가고 있었다.

**대가는 무엇인가** — 원문이 바로 이어서 적은 문장은 이것이다.

> 다만 2.x는 `str`(바이트)과 `unicode`(문자)를 **별개의 두 타입으로 공존**시켰고, 이 어정쩡한 이원 구조가 끝없는 인코딩 혼란을 낳아 — 훗날 Python 3가 둘을 통합하며 하위 호환을 깨는 가장 큰 이유가 된다.

**그 외**: 증분 대입 연산자(`x += 1`), 본격적인 `string` 메서드 정착, 그리고 **개방형 의사결정 절차인 PEP(Python Enhancement Proposal) 프로세스의 시작**도 이 시기다.

> **PEP(Python Enhancement Proposal)** — 원문이 적은 대로 Python의 "개방형 의사결정 절차". 무엇을 왜 바꾸자는 제안을 번호 붙은 문서로 남겨 공개 논의한다.\
> 예: 이 편에 나오는 PEP 20(Zen of Python)·234(반복자)·252/253(new-style class)·255(제너레이터)·318(데코레이터)·343(`with` 문)이 전부 그렇게 남은 문서다.

### Python 2.2 — 타입과 클래스의 통합 (2001년 12월)

"정리(cleanup) 릴리스"로 불린다.\
Python 내부의 오래된 비일관성을 도려내고, 언어의 객체 모델을 근본적으로 다시 세웠다.

**1) 새로운 형식의 클래스 (New-style classes, PEP 252/253)** — 그전까지 `list`·`dict` 같은 **내장 타입**과 사용자가 `class`로 정의한 **클래스**는 서로 다른 종족이었고, 내장 타입을 상속할 수 없었다.\
2.2는 둘의 구분을 없애 **모든 것을 `object`에서 출발하는 하나의 타입 계층으로 통합**했다.

```text
2.2 이전 — 서로 다른 두 종족            2.2 이후 — 하나의 타입 계층
+-----------------------------+        +-----------------------------+
| [내장 타입]                 |        |            object           |
|     list    dict            |        |              |              |
|                             |        |             list            |
| [사용자가 class로 정의한    |        |              |              |
|  클래스]                    |        |            MyList           |
+-----------------------------+        +-----------------------------+
 "내장 타입을 상속할 수 없었다"          "class MyList(list):" 가 성립한다
```

- 두 칸의 대립축은 원문의 대립축 그대로다 — **내장 타입과 사용자 클래스가 서로 다른 종족이냐, 하나의 타입 계층이냐**.
- 왼쪽 칸 아래 따옴표는 원문 문장 그대로이고, 오른쪽 칸 꼭대기의 `object`는 원문의 "모든 것을 `object`에서 출발하는 하나의 타입 계층으로 통합"에서 온 것이다.
- 오른쪽 칸의 위쪽 세로줄(`object` 아래)이 그 "출발하는"에 해당하고, 아래쪽 세로줄은 바로 아래 코드의 `class MyList(list):` 한 줄이 만드는 상속 관계다 — 원문이 "2.2 이전엔 불가능했다"고 주석을 단 그 줄이다.

```python
# new-style: object를 상속하면 내장 타입도 부모로 삼을 수 있다
class MyList(list):          # 2.2 이전엔 불가능했다
    def second(self):
        return self[1]

# property, __slots__, 일관된 super() 등 new-style에서만 가능한 기능들
class Temperature(object):
    def __init__(self, c):
        self._c = c
    @property
    def fahrenheit(self):
        return self._c * 9 / 5 + 32
```

> **상속(inheritance)** — 이미 있는 타입의 기능을 그대로 물려받아 새 타입을 만드는 것.\
> 예: 위 코드의 `class MyList(list):`가 `list`의 기능을 물려받으면서 `second`만 새로 얹은 것이고, 원문 주석대로 이것이 "2.2 이전엔 불가능했다".

> **`property`** — 메서드로 정의해 두고 값처럼 읽게 만드는 장치. 원문은 이것을 new-style에서만 가능한 기능의 하나로 든다.\
> 예: 위 코드의 `fahrenheit`가 그것이다 — `@property`가 붙어 있어 `self._c * 9 / 5 + 32`라는 계산을 속성처럼 꺼내 쓴다.

**왜**: 내장 타입과 사용자 클래스를 차별하던 "어두운 구석"을 없애, 메타클래스·디스크립터·`property` 같은 강력한 객체 모델 기능의 토대를 깔았다.\
이 통합은 Python 3에서 완성되어 모든 클래스가 자동으로 new-style이 된다.

**2) 반복자 (Iterators, PEP 234)** — `for` 루프가 동작하는 방식을 `__iter__()`/`next()`라는 명시적 프로토콜로 표준화했다. 이로써 어떤 객체든 반복 가능하게 만들 수 있게 되었다.

> **프로토콜(protocol)** — "이 이름의 메서드를 갖추고 있으면 이 자리에 쓸 수 있다"는 약속.\
> 예: 원문이 든 것이 `__iter__()`/`next()`이고, 이 둘을 갖춘 객체라면 무엇이든 `for` 루프에 넣을 수 있다.

**3) 제너레이터 (Generators, PEP 255)** — `yield` 키워드로 값을 하나씩 "지연 생산"하는 함수. 큰 데이터를 한꺼번에 메모리에 올리지 않고 필요할 때마다 흘려보낼 수 있다.

```python
def countdown(n):
    while n > 0:
        yield n          # 값을 내보내고 그 자리에서 멈춘다
        n -= 1

for x in countdown(3):   # 3, 2, 1 을 차례로
    print x
```

위 코드의 `countdown(3)`이 원문 주석대로 "3, 2, 1 을 차례로" 내놓는 동안 무슨 일이 일어나는지를 세로로 펴면 이렇다.

```text
for 문이 하는 일                  그때 countdown(3) 안에서 일어나는 일
------------------                ------------------------------------
값을 하나 달라 한다               yield n 이 3 을 내보내고 그 자리에서 멈춘다
        ↓
또 하나 달라 한다                 멈춘 자리에서 이어져 n -= 1, yield 가 2 를 내보내고 멈춘다
        ↓
또 하나 달라 한다                 같은 식으로 1 을 내보내고 멈춘다
        ↓
또 하나 달라 한다                 while n > 0 이 참이 아니어서 함수가 끝나고, for 문도 끝난다
```

- 오른쪽 칸 첫 줄의 "값을 내보내고 그 자리에서 멈춘다"는 원문이 `yield n` 줄에 달아 둔 주석이다.
- 왼쪽 네 칸은 원문 주석 "3, 2, 1 을 차례로"가 말하는 세 번에, 루프가 끝나는 한 번을 더한 것이다.\
  마지막 칸의 `while n > 0`은 위 코드에서 읽은 것이다.
- 원문이 이 코드에 **주석으로** 직접 적은 것은 「값을 내보내고 그 자리에서 멈춘다」와 「3, 2, 1 을 차례로」 둘이다 — **멈춘 자리에서 다시 이어진다**는 것은 그 둘을 이어 놓으면 나오는 그림이다.\
  (산문 쪽에는 "지연 생산"·"필요할 때마다 흘려보낼"이 따로 있다.)
- 원문의 "큰 데이터를 한꺼번에 메모리에 올리지 않고"는 이 그림에서 한 번에 숫자 하나씩만 오른쪽에서 왼쪽으로 건너간다는 뜻이다.

> **제너레이터(generator)** — 값을 한꺼번에 다 만들어 돌려주는 대신, 부를 때마다 하나씩 내놓고 그 자리에서 멈추는 함수(원문은 이것을 "지연 생산"이라 적는다).\
> 예: 위 코드의 `countdown`이 그것이고, 멈추는 자리가 `yield n`이다.

**언제 쓸 수 있게 됐나** — 원문이 적은 시점은 이렇다.

> 2.2에서는 모듈 맨 위에 `from __future__ import generators`를 적어야 활성화됐고, 2.3에서 정식 문법으로 승격된다.

> **`from __future__ import ...`** — 다음 버전에서 정식이 될 동작을, 그 파일 하나에서 미리 켜는 장치.\
> 예: 원문이 든 `from __future__ import generators`를 2.2에서 적으면 그 모듈에서 제너레이터를 쓸 수 있었다.

**왜**: 반복자와 제너레이터는 메모리 효율적이고 게으른(lazy) 데이터 처리의 문을 열었다.\
이 둘은 훗날 컴프리헨션·`itertools`·코루틴·`async`로 이어지는 Python 데이터 흐름 사고방식의 출발점이 된다.

### Python 2.3 ~ 2.6 — 성숙과 다리 놓기 (2003 ~ 2008)

2.x는 이 시기에 실무 언어로 무르익는다. 매 릴리스가 큼직한 기능을 하나씩 안정시켰다.

- **2.3 (2003)**: 제너레이터 정식화, `sets` 모듈, 더 빠른 import.
- **2.4 (2004)**: **데코레이터(`@`) 문법(PEP 318)** — 함수를 감싸 기능을 덧입히는 선언적 문법. 제너레이터 식, 내장 `set` 타입, `decimal` 모듈.
  ```python
  @staticmethod
  def helper():            # @ 한 줄로 함수를 변형 — 2.4의 대표 문법
      ...
  ```
- **2.5 (2006)**: **`with` 문(PEP 343)** — 파일·락 등 자원을 안전하게 열고 닫는 컨텍스트 매니저. `yield`가 식으로 승격되어 코루틴의 씨앗이 된다.
  ```python
  with open('data.txt') as f:   # 블록을 벗어나면 자동으로 close
      data = f.read()
  ```
- **2.6 (2008년 10월 1일)**: **Python 3로 가는 다리**. `from __future__ import` 기능과 `-3` 경고 플래그로 3.0의 변화를 미리 맛보게 했다. 2.6은 그 자체로 새 기능을 더하기보다, 거대한 비호환 도약을 앞두고 마이그레이션 통로를 닦는 역할이었다.

> **데코레이터(decorator)** — 원문 정의 그대로 "함수를 감싸 기능을 덧입히는 선언적 문법".\
> 예: 위 2.4 코드의 `@staticmethod` 한 줄이 그것이고, 원문 주석대로 "`@` 한 줄로 함수를 변형"한다.

> **컨텍스트 매니저(context manager)** — 원문 정의 그대로 "파일·락 등 자원을 안전하게 열고 닫는" 장치. `with` 문이 그것을 쓰는 문법이다.\
> 예: 위 2.5 코드의 `with open('data.txt') as f:`가 그것이고, 원문 주석대로 "블록을 벗어나면 자동으로 close"된다.

**왜**: 데코레이터·`with`·제너레이터 식은 오늘날 우리가 매일 쓰는 관용구다.\
이 시기에 Python은 스크립트 언어를 넘어 웹(Django·Zope)·과학 계산(NumPy의 전신)·시스템 도구의 주력으로 자리 잡는다.

## 철학 — 가독성이라는 헌법

### "코드는 쓰는 것보다 읽히는 일이 더 많다"

Python의 모든 설계 결정을 관통하는 원칙이다.\
중괄호 대신 **들여쓰기로 블록을 강제**한 것이 그 상징이다 — 다른 언어에서는 스타일 권장에 불과한 것을 Python은 문법으로 못 박아, 누가 짜든 비슷한 모양의 코드가 나오게 했다.

### Zen of Python (PEP 20)

팀 피터스(Tim Peters)가 1999년 메일링 리스트에 올린 19개의 격언으로, 2004년 **PEP 20**으로 정식화되었다.\
인터프리터에서 `import this`를 치면 부활절 달걀처럼 출력된다.

```python
>>> import this
The Zen of Python, by Tim Peters

Beautiful is better than ugly.          # 아름다운 것이 추한 것보다 낫다
Explicit is better than implicit.       # 명시적인 것이 암시적인 것보다 낫다
Simple is better than complex.          # 단순한 것이 복잡한 것보다 낫다
...
Readability counts.                     # 가독성은 중요하다
There should be one-- and preferably only one --obvious way to do it.
```

> **부활절 달걀(easter egg)** — 프로그램 안에 재미로 숨겨 둔 장치.\
> 예: 원문이 든 것이 `import this`다 — 모듈을 불러오는 평범한 문법인데 격언이 출력된다.

**왜 중요한가**: Perl의 "방법은 여러 가지(TMTOWTDI)"와 정반대로, Python은 **"한 가지 명백한 방법이 있어야 한다"**를 지향한다.\
격언 20개 중 19개만 적혀 있고 마지막 하나는 "귀도가 채우도록" 비워 둔 농담까지 — 이 문서 자체가 Python 문화의 자기 정체성 선언이다.

## 영향과 의의

*(이 편의 「남긴 것」에 해당한다 — 아래 네 항목과 마지막 인용구는 전부 원문 「영향과 의의」의 것이다.)*

1. **"읽기 쉬운 코드"를 산업 표준으로** — 들여쓰기 강제와 Zen of Python은 가독성을 미덕이 아닌 규범으로 만들었다. 이후 많은 언어가 간결한 문법을 지향하게 된 데에 Python의 영향이 크다.

2. **2.x가 깐 토대 위에 생태계가 자랐다** — new-style class(객체 모델), 제너레이터/반복자(데이터 흐름), 데코레이터·`with`(선언적 자원 관리)는 Django·NumPy·SQLAlchemy 같은 후대 프레임워크의 문법적 기반이 되었다.

3. **`str`/`unicode` 이원 구조라는 빚** — 2.0이 유니코드를 "기존 `str` 옆에 새 타입으로" 붙인 타협은 두고두고 인코딩 혼란을 낳았고, 이를 근본부터 고치려는 시도가 곧 Python 3.0(2008년 12월, 비호환 도약)이다. 즉 2.x의 가장 큰 미해결 과제가 다음 시대의 가장 큰 사건을 불렀다.

4. **개방형 거버넌스의 정착** — PEP 프로세스와 BDFL 모델은 한 사람의 취미를 수만 명이 함께 키우는 언어로 전환시킨 제도적 장치였다. 라이선스 분쟁(CNRI)과 그 해결은 오늘날 Python Software Foundation의 전사다.

> 2.x 계열은 이후 2010년 **2.7**을 마지막으로 동결되며, 2020년 1월 1일 공식 지원이 종료된다. 그러나 1991년의 0.9.0에서 굳어진 "가독성이 먼저다"라는 신념은 한 줄도 바뀌지 않은 채 Python 3로 이어진다.

## 용어 풀이

- **ABC** — 귀도가 CWI에서 참여했던 교육용 언어. 가독성·들여쓰기·고수준 자료형은 Python이 물려받았고, 확장 불가·고립은 버렸다.
- **BDFL(Benevolent Dictator For Life)** — "자비로운 종신 독재자". 원문이 귀도 반 로섬에게 붙이는 별칭이다.
- **인터프리터(interpreter)** — 소스 코드를 받아 실행해 주는 프로그램. 귀도가 1989년 크리스마스 연휴에 만들기 시작한 것이 이것이다.
- **블록(block)** — 여러 줄의 코드를 한 덩어리로 묶은 것. Python은 이것을 들여쓰기로 표현하고, 문법으로 강제한다.
- **고수준 자료형** — 값을 **여러 개** 담아 두는 그릇을 언어가 내장한 것. 원문은 ABC의 그것을 "리스트·딕셔너리에 해당하는 구조"라 적고, 0.9.0의 핵심 자료형으로는 `list`·`dict`에 `str`을 함께 든다.
- **예외(exception)** — 실행 중 문제가 났음을 신호로 던져 올리는 것. 0.9.0부터 있었다.
- **모듈(module) / C 모듈** — 기능을 담아 끌어다 쓰는 코드 묶음, 그리고 그것을 C로 만들어 붙인 것. ABC에 없던 확장 통로가 이것이다.
- **`lambda`·`map`·`filter`·`reduce`** — 1.0에서 합류한 함수형 도구. `reduce`는 Python 3에서 `functools`로 밀려난다.
- **리스트 컴프리헨션** — 2.0에서 도입. `map`/`filter`/`lambda`의 조합을 한 줄의 식으로 대체한다.
- **참조 카운팅(reference counting)** — 가리키는 곳의 수를 세어 0이 되면 메모리를 돌려주는 방식. Python이 원래 쓰던 관리법이다.
- **순환 참조(reference cycle)** — 객체가 서로를 가리켜 참조 카운트가 0이 되지 않는 상태. 2.0 이전에는 누수로 남았다.
- **세대별 보조 수집기(`gc` 모듈)** — 2.0이 참조 카운팅 위에 얹은, 순환을 탐지해 끊어 주는 수집기.
- **메모리 누수(memory leak)** — 더 쓰지 않는 값이 회수되지 않고 남아 있는 것.
- **유니코드(Unicode)** — ASCII의 8비트를 넘어 다국어 문자를 표현하는 것. 2.0이 `unicode`를 새 기본 자료형으로 추가했다.
- **`str` / `unicode` 이원 구조** — 2.x가 바이트와 문자를 별개의 두 타입으로 공존시킨 것. 끝없는 인코딩 혼란을 낳은 2.x의 빚이다.
- **PEP(Python Enhancement Proposal)** — 2.0 시기에 시작된 개방형 의사결정 절차.
- **new-style class** — 2.2가 도입한, 모든 것이 `object`에서 출발하는 하나의 타입 계층. Python 3에서 모든 클래스가 자동으로 이것이 된다.
- **상속(inheritance)** — 이미 있는 타입의 기능을 물려받아 새 타입을 만드는 것. 2.2 이전에는 내장 타입을 상속할 수 없었다.
- **`property`** — 메서드로 정의해 두고 값처럼 읽게 만드는 장치. new-style에서만 가능한 기능의 하나다.
- **메타클래스 · 디스크립터** — 원문이 new-style이 토대를 깔아 준 객체 모델 기능으로 `property`와 함께 이름만 드는 것들이다.
- **반복자(iterator)** — `__iter__()`/`next()`라는 명시적 프로토콜. 2.2가 `for` 루프의 동작을 이것으로 표준화했다.
- **제너레이터(generator)** — `yield`로 값을 하나씩 지연 생산하는 함수. 2.2에 들어와 2.3에서 정식 문법이 됐다.
- **`from __future__ import ...`** — 다음 버전의 동작을 그 파일에서 미리 켜는 장치. 2.2의 제너레이터, 2.6의 3.0 대비가 이것을 썼다.
- **데코레이터(decorator)** — 함수를 감싸 기능을 덧입히는 선언적 `@` 문법. 2.4에서 들어왔다.
- **컨텍스트 매니저(context manager) / `with`** — 파일·락 등 자원을 안전하게 열고 닫는 장치. 2.5에서 들어왔다.
- **Pythonic(Python다움)** — 리스트 컴프리헨션으로 상징되는, 읽기 좋은 Python다운 표현 방식.
- **Zen of Python (PEP 20)** — 팀 피터스가 1999년에 올리고 2004년 PEP 20으로 정식화된 격언 모음. `import this`로 볼 수 있다.
