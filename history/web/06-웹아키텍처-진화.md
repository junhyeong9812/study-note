## 한눈에 — 쉽게 말하면

원문이 이 편을 한 줄로 요약한 문장은 이렇다.

> "HTML을 **어디서·언제** 만드는가"를 둘러싼 30여 년의 이동사. 렌더링의 무게중심은 서버 → 클라이언트 → 다시 서버로 진자처럼 오갔고, 매번 그 이동에는 "직전 시대가 비싸게 만든 것을 싸게 돌려받으려는" 분명한 동기와 트레이드오프가 있었다.

**이 30년의 질문은 하나다 — "요리를 어디서 완성해서 내놓을 것인가."**

- **주방에서 다 만들어 내보내기** = 서버가 완성된 HTML을 보낸다.\
  받는 즉시 먹을 수 있다. 대신 반찬 하나 바꾸려 해도 접시를 통째로 다시 받아야 한다.
- **밀키트로 보내기** = 서버는 재료(데이터)와 조리법(JS)만 보내고 브라우저가 화면을 만든다.\
  내 입맛대로 바꾸기 쉽다. 대신 받자마자 먹을 수는 없고, 조리하는 동안 빈 접시를 보고 있어야 한다.
- 웹은 이 두 방식 사이를 **진자처럼 왕복**했다.\
  한쪽으로 가면 그쪽 비용이 쌓이고, 그러면 반대쪽으로 민다.
- 그리고 지금은 **"국은 주방에서, 샐러드만 식탁에서"**처럼 접시마다 나눠 만드는 쪽으로 왔다.

이 요리 이야기가 **똑같은 구조로** 웹 아키텍처의 역사다.\
원문의 표현으로는 "HTML을 **어디서·언제** 만드는가"를 둘러싼 30여 년의 이동사다.

> **렌더링(rendering)** — 데이터를 사람이 보는 화면(HTML·픽셀)으로 만들어 내는 일.\
> 예: 상품 목록 데이터를 `<li>상품A</li>` 같은 HTML로 바꾸는 것이 렌더링이다.

> **서버 렌더 / 클라이언트 렌더** — 그 일을 서버에서 하느냐, 브라우저의 JavaScript가 하느냐.\
> 예: 페이지 소스 보기를 눌렀을 때 내용이 다 들어 있으면 서버 렌더, 빈 `<div>`만 있으면 클라이언트 렌더에 가깝다.

## 큰 그림: 렌더링이 오간 진자

웹 아키텍처의 역사는 새 기술의 단순 누적이 아니라 **하나의 축 위를 왕복한 진자 운동**으로 읽는 편이 정확하다.\
그 축은 corpus의 「렌더링 전략」 문서가 정리한 두 직교 차원과 같다 — **생성 위치**(서버에서 HTML ↔ 브라우저에서 JS로 DOM)와 **생성 시점**(빌드 타임 ↔ 요청 타임).\
(원본 repo 기준 경로: `../local-llm/corpus/frontend/렌더링-전략.md`)

아래 연표의 각 단계는 이 평면 위의 한 점이며, 다음 점으로의 이동은 언제나 "직전 점이 지불하던 비용"을 줄이려는 시도였다.

원문의 진자 도식을 그대로 옮기면 이렇다.

```text
서버 렌더 ◄───────────────────────────────────► 클라이언트 렌더
  │                                                      │
정적 HTML(1991)                                          │
  └─ CGI(1993) ─ 서버사이드 동적(PHP/ASP/JSP/Rails)       │
       페이지마다 풀 리로드 ──────────────────► AJAX·SPA(2005~)
                                                  클라가 렌더·앱화
       SSR/SSG 회귀(Next·Jamstack 2016) ◄──────── API 분리(REST/GraphQL)
       │                                          SEO·초기로딩 손실 반성
       └─ 엣지·RSC·아일랜드(2020~)
            "서버에서 만들되, 상호작용 섬만 클라로"
```

핵심 통찰: **진자는 같은 자리로 돌아오지 않는다.**\
2016년 이후의 "서버 회귀"는 1999년의 서버 렌더와 모양은 비슷해도, CDN·엣지·부분 hydration·컴포넌트 모델을 갖춘 더 높은 나선이다.

> **CDN(콘텐츠 전송 네트워크)** — 세계 곳곳에 복사본을 미리 깔아 두고 가장 가까운 곳에서 응답하는 서버망.\
> 예: 서울 사용자는 서울 노드에서, 상파울루 사용자는 상파울루 노드에서 같은 파일을 받는다.

## 1. 정적 HTML 시대 (1991~)

*(이 편의 「시대 배경」에 해당한다)*

### 시대적 배경

1991년 8월 팀 버너스리가 최초의 웹사이트를 공개했을 때, 웹은 **하이퍼링크로 연결된 정적 문서의 집합**이었다.\
서버는 디스크의 `.html` 파일을 그대로 읽어 HTTP로 돌려주는 파일 서버에 가까웠다.\
모든 사용자는 같은 URL에서 똑같은 바이트를 받았다.

```text
사용자 A  --- GET /index.html --->  서버
사용자 B  --- GET /index.html --->  서버
사용자 C  --- GET /index.html --->  서버
                                      |
                                      v
                            디스크의 index.html 을
                            그대로 읽어 돌려준다
                                      |
                  누가 요청하든 완전히 같은 바이트
```

**얻은 것** — 극단적 단순함·빠른 응답·완벽한 캐시 가능성.\
서버는 상태가 없고 무한히 복제된다.

**잃은 것** — 사용자·시점·입력에 따라 달라지는 화면이 불가능.\
폼을 받아 처리하거나, 방문자 수를 세거나, 검색 결과를 만드는 — 즉 **"애플리케이션"이라 부를 만한 것**이 원리적으로 없었다.

> **무상태(stateless)** — 서버가 이전 요청을 기억하지 않는 성질.\
> 예: 기억할 게 없으니 서버를 몇 대로 늘려도 아무 대나 응답하면 된다.

> 이 한계가 다음 모든 진화의 출발점이다.\
> "같은 URL, 다른 응답"을 만들려는 욕구가 렌더링을 서버 쪽으로 처음 밀어 넣는다.

## 무엇이 바뀌었나

### 2. CGI — 최초의 동적 웹 (1993)

**왜 이동했나** — 정적 파일만으로는 폼 처리·DB 조회·방문자 카운터조차 못 만든다.\
1993년 NCSA의 **Rob McCool**이 NCSA HTTPd 서버를 위해 **CGI(Common Gateway Interface)** 규격을 제안했다 (이후 RFC 3875로 CGI/1.1 공식화).\
CGI는 "웹 서버가 외부 실행 프로그램을 호출하고, 그 표준출력을 HTTP 응답으로 흘려보내는" 표준 약속이다.\
CERN httpd·Plexus 등 경쟁 서버들이 곧 채택해 **사실상 첫 산업 표준**이 됐다.

> **표준출력(stdout)** — 프로그램이 결과를 내보내는 기본 통로.\
> 예: 터미널에서 `print`를 하면 화면에 찍히는 그 통로인데, CGI에서는 그 내용이 곧 HTTP 응답이 된다.

#### 어떻게 동작했나

서버는 요청이 오면 프로그램(보통 Perl·C·셸 스크립트)을 **프로세스로 새로 띄우고**, 환경변수(`QUERY_STRING`, `REQUEST_METHOD` 등)로 입력을 넘긴다.\
프로그램은 HTML을 stdout으로 찍고 종료한다.

```text
요청 도착
   |
   v
서버가 프로그램을 새 프로세스로 fork
   |
   v
환경변수로 입력 전달 (QUERY_STRING, REQUEST_METHOD ...)
   |
   v
프로그램이 HTML 을 stdout 으로 찍는다
   |
   v
서버가 그 출력을 HTTP 응답으로 흘려보낸다
   |
   v
프로세스 종료   <- 요청 1건마다 여기까지가 통째로 반복된다
```

```perl
#!/usr/bin/perl
# 1990년대 전형적 CGI — 요청마다 이 프로세스가 새로 뜬다
print "Content-type: text/html\n\n";
print "<html><body>";
print "<h1>안녕, 동적 웹</h1>";
print "<p>당신의 호스트: $ENV{'REMOTE_ADDR'}</p>";
print "</body></html>";
```

코드에서 보이듯 HTML이 전부 `print` 문 안에 문자열로 들어 있다 — 이 모양이 다음 시대를 부른다.

**얻은 것** — 드디어 "같은 URL, 다른 응답".\
언어 무관(stdout만 맞추면 됨)·서버 무관.

**잃은 것** — **요청 1건 = 프로세스 1개 fork**.\
트래픽이 늘면 프로세스 생성·소멸 비용이 서버를 무너뜨린다.\
DB 연결도 매번 새로 맺는다.\
이 성능 벽이 곧 FastCGI·mod_perl, 그리고 **언어 내장형 서버사이드**로의 이동을 부른다.

> **fork(프로세스 생성)** — 운영체제가 새 프로그램 실행 단위를 통째로 하나 더 띄우는 것.\
> 예: 요청 1000건이 동시에 오면 프로세스 1000개를 만들었다 없애야 한다.

### 3. 서버사이드 동적 — HTML 안에 코드를 넣다 (1995~2004)

**왜 이동했나** — CGI는 "HTML을 코드 문자열로 print"해야 해서 페이지가 조금만 복잡해도 코드가 지옥이 된다.\
발상을 뒤집어 — **HTML을 본문으로 두고 그 안에 코드 조각을 끼워 넣자**(template-first).\
그리고 프로세스를 매번 띄우지 말고 서버에 **상주하는 인터프리터/런타임**이 처리하자.\
이 두 아이디어가 한 세대의 서버사이드 기술을 낳았다.

뒤집기 전후를 나란히 놓으면 이렇다.

```text
CGI (코드가 본문)                  템플릿 (HTML 이 본문)
+---------------------------+      +---------------------------+
| print "<html><body>";     |      | <html><body>              |
| print "<h1>목록</h1>";    |      |   <h1>목록</h1>           |
| print "<li>" . $n . "</li>|      |   <li><?= $n ?></li>      |
| print "</body></html>";   |      | </body></html>            |
+---------------------------+      +---------------------------+
 HTML 이 문자열 안에 숨는다          HTML 이 눈에 보인다
```

> **템플릿(template)** — 빈칸이 뚫린 HTML 틀. 실행할 때 그 빈칸에 값을 채워 완성한다.\
> 예: `<li><?= $row['name'] ?></li>` 에서 `<?= ?>` 자리가 매 요청마다 다른 상품 이름으로 채워진다.

> **상주 런타임(persistent runtime)** — 요청마다 새로 뜨지 않고 서버에 계속 떠 있는 실행 환경.\
> 예: 인터프리터가 이미 떠 있으면 요청이 와도 프로세스를 새로 만들 필요가 없다.

이 시대의 기술을 원문 표 그대로 옮기면 이렇다.

| 기술 | 등장 | 주체 | 특징 |
|------|------|------|------|
| **PHP** | 1995 (PHP Tools) / 1996 (PHP/FI) | Rasmus Lerdorf | HTML에 `<?php ?>` 직접 임베드. 배우기 쉬워 폭발적 확산 |
| **ASP** | 1996 (IIS 3.0) | Microsoft | VBScript/JScript, Windows·IIS 생태계 |
| **JSP** | 1999 | Sun | 서블릿 위의 템플릿, Java 엔터프라이즈 |
| **Ruby on Rails** | 2004 | DHH (Basecamp) | **MVC·"설정보다 관습"·ORM(ActiveRecord)** 풀스택 프레임워크 |

```php
<!-- PHP: HTML이 본문, 코드는 끼워넣기 (CGI의 print 지옥에서 탈출) -->
<html><body>
  <h1>상품 목록</h1>
  <ul>
  <?php foreach ($db->query("SELECT name FROM products") as $row): ?>
    <li><?= htmlspecialchars($row['name']) ?></li>
  <?php endforeach; ?>
  </ul>
</body></html>
```

#### Rails의 의미

2004년 Rails는 단순한 템플릿 엔진을 넘어 **라우팅·ORM·마이그레이션·MVC 관습**을 묶은 풀스택 패러다임을 대중화했다.\
"요청 → 컨트롤러 → 모델(DB) → 뷰(HTML 렌더) → 응답"이라는 **요청-응답 사이클 안에서 완결되는 서버 렌더**가 이 시대의 정점이다.\
Django(2005)·Spring MVC도 같은 모델이다.

사이클을 세로로 그리면 이렇다.

```text
요청
  |
  v
컨트롤러       어떤 처리를 할지 고른다
  |
  v
모델(DB)       데이터를 읽고 쓴다
  |
  v
뷰(HTML 렌더)  완성된 HTML 을 만든다
  |
  v
응답           이 한 바퀴 안에서 전부 끝난다
```

> **MVC(Model-View-Controller)** — 데이터·화면·흐름 제어를 세 역할로 나눠 두는 구조.\
> 예: DB를 다루는 코드(모델)와 HTML을 만드는 코드(뷰)를 섞지 않는 것.

> **ORM(객체-관계 매핑)** — DB의 표를 프로그래밍 언어의 객체처럼 다루게 해 주는 층.\
> 예: `Product.all` 한 줄이 `SELECT * FROM products` 로 번역된다.

> **라우팅(routing)** — 들어온 URL을 어느 처리 코드로 보낼지 정하는 규칙.\
> 예: `/products` 는 상품 목록 컨트롤러로, `/users/1` 은 사용자 상세 컨트롤러로.

**얻은 것** — 생산성·SEO 친화(서버가 완성된 HTML을 줌)·단일 배포 단위.\
로직과 데이터가 서버 한곳에.

> **SEO(검색엔진 최적화)** — 검색엔진이 페이지 내용을 잘 읽어 가게 만드는 일.\
> 예: 서버가 완성된 HTML을 주면 검색 로봇이 JS를 돌리지 않고도 본문을 읽을 수 있다.

**잃은 것** — **모든 상호작용이 풀 페이지 리로드**.\
버튼 하나 눌러도 전체 HTML을 다시 받아 화면이 깜빡인다.\
데스크톱 앱 같은 매끈한 UX는 불가능 — 이 답답함이 렌더링을 **클라이언트로** 밀어내는 다음 진자의 동력이다.

### 4. AJAX·SPA — 렌더링이 클라이언트로 (2005~)

**왜 이동했나** — 풀 리로드의 깜빡임을 없애려면 **페이지를 다시 받지 않고 데이터 일부만 비동기로 갱신**해야 한다.\
그 기술적 토대는 이미 있었다 — Microsoft가 IE5(1999)에 넣은 `XMLHttpRequest`(원래 Outlook Web Access용 ActiveX).\
2005년 2월 18일 **Jesse James Garrett**이 이 비동기 패턴에 **AJAX**(Asynchronous JavaScript + XML)라는 이름을 붙인 짧은 에세이를 발표하면서 한 시대가 열렸다.\
Google Maps·Gmail(2004~2005)이 "웹도 데스크톱 앱처럼 될 수 있다"를 증명한 결정적 사례였다.

```javascript
// AJAX의 핵심: 페이지를 리로드하지 않고 데이터만 가져와 DOM 일부만 갱신
const xhr = new XMLHttpRequest();
xhr.open("GET", "/api/products");
xhr.onload = () => {
  const products = JSON.parse(xhr.responseText);
  document.querySelector("#list").innerHTML =
    products.map(p => `<li>${p.name}</li>`).join("");
};
xhr.send();
```

마지막 두 줄이 요점이다 — 페이지 전체가 아니라 `#list` 안쪽만 새 내용으로 바뀐다.

#### SPA로의 급진화

"일부만 갱신"이 "전부를 클라이언트에서 그린다"로 급진화하면 **SPA(Single Page Application)**가 된다.\
서버는 빈 껍데기 HTML + JS 번들만 주고, 라우팅·렌더링·상태를 전부 브라우저가 맡는다.\
Backbone(2010)·AngularJS(2010)·**React(2013)**·Vue(2014)가 이 모델을 주류로 만들었다.\
서버는 점점 **데이터(JSON)만 내는 존재**로 후퇴한다 → 다음 단계(API 분리)의 복선.

> **SPA(Single Page Application)** — 페이지를 한 번만 받고, 이후 화면 전환까지 브라우저가 처리하는 방식.\
> 예: 메뉴를 눌러도 주소만 바뀌고 페이지는 새로 받지 않는 서비스가 SPA다.

> **번들(bundle)** — 여러 JS 파일을 하나로 묶어 만든 배포용 파일.\
> 예: 앱이 커질수록 이 파일이 수 MB까지 불어난다.

서버가 주는 첫 응답을 나란히 놓으면 차이가 분명하다.

```text
서버사이드 렌더                    SPA
+---------------------------+      +---------------------------+
| <ul>                      |      | <div id="root"></div>     |
|   <li>상품 A</li>         |      | <script src="app.js">     |
|   <li>상품 B</li>         |      |                           |
| </ul>                     |      |                           |
+---------------------------+      +---------------------------+
 첫 응답에 내용이 다 있다            첫 응답은 비어 있다
                                     JS 를 받아 돌려야 내용이 생긴다
```

**얻은 것** — 데스크톱급 상호작용·부분 갱신·프론트/백 역할 분리.\
클라가 풍부한 상태를 가진 진짜 "앱".

**잃은 것** — corpus 「렌더링 전략」이 짚는 **CSR의 대가** — 빈 HTML→JS 의존이라 **첫 화면이 비고(FCP 느림), TTI가 늦고, SEO·소셜 미리보기가 약하다.**\
거대 JS 번들·느린 기기에서 첫 페인트 전 폭포수.\
**이 손실의 반성이 2016년 서버 회귀를 부른다.**

> **FCP(First Contentful Paint)** — 화면에 내용이 처음 그려지는 시점.\
> 예: 빈 흰 화면이 사라지고 글자 한 줄이라도 보이는 순간이 FCP다.

> **TTI(Time To Interactive)** — 눌렀을 때 실제로 반응하기 시작하는 시점.\
> 예: 버튼이 보이는데 눌러도 아무 일이 없다면 FCP는 지났지만 TTI는 아직이다.

> **CSR(Client-Side Rendering)** — 브라우저의 JS가 화면을 만드는 방식.\
> 예: 서버는 빈 `<div>` 하나만 주고, 나머지는 JS가 그린다.

### 5. API 분리 — 백엔드는 데이터, 프론트는 화면 (2000년 이론 / 2015 GraphQL)

**왜 이동했나** — SPA·모바일 앱이 늘면서 백엔드는 "HTML 렌더링 기계"가 아니라 **여러 클라이언트(웹·iOS·안드로이드)가 공유하는 데이터 공급원**이 되어야 했다.\
렌더링과 데이터의 관심사가 분리되자, 그 경계를 잇는 **API 계약**이 1급 설계 대상이 된다.

```text
                 +--- 웹 브라우저
                 |
데이터 API ------+--- iOS 앱
(JSON)           |
                 +--- 안드로이드 앱

 서버는 화면을 만들지 않고 데이터만 낸다
 화면 만들기는 각 클라이언트가 맡는다
```

두 접근을 원문 서술대로 옮기면 이렇다.

- **REST**: Roy Fielding이 2000년 박사논문에서 정의한 아키텍처 스타일.\
  **리소스(URL) + HTTP 동사(GET/POST/PUT/DELETE) + 무상태**.\
  웹의 기존 메커니즘(URI·HTTP·캐시)을 그대로 활용해 표준화 — 2000년대 후반~2010년대 API의 기본형이 됐다.
- **GraphQL**: Facebook이 2012년 모바일 앱의 과다/과소 페칭 문제를 풀려고 내부 개발, **2015년 오픈소스화**.\
  클라이언트가 **필요한 필드만 질의**하는 단일 엔드포인트 — over-fetching/under-fetching과 다중 왕복을 한 번에 해결.

> **over-fetching / under-fetching(과다·과소 페칭)** — 필요 없는 필드까지 받거나, 필요한 것이 모자라 또 요청해야 하는 상황.\
> 예: 이름만 필요한데 주소·결제이력까지 딸려 오면 과다, 글 목록을 받고 작성자 이름을 얻으려 또 요청하면 과소다.

> **엔드포인트(endpoint)** — 클라이언트가 요청을 보내는 주소 하나.\
> 예: REST는 `/users`·`/posts`처럼 여럿이고, GraphQL은 `/graphql` 하나로 모은다.

```graphql
# GraphQL: 클라가 필요한 모양 그대로 요청 (REST의 고정 응답·N+1 왕복 대비)
query {
  user(id: "1") {
    name
    posts(last: 3) { title }   # 필요한 필드만, 한 번의 왕복으로
  }
}
```

질의문의 모양이 곧 응답의 모양이다 — `name`과 `posts.title`만 적었으니 그것만 온다.

원문의 트레이드오프 표를 그대로 옮기면 이렇다.

| | REST | GraphQL |
|---|------|---------|
| 강점 | HTTP 캐시·단순·생태계 성숙 | 정확한 페칭·단일 왕복·강타입 스키마 |
| 약점 | over/under-fetching·엔드포인트 폭증 | HTTP 캐시 어려움·서버 복잡도·쿼리 비용 통제 |

**공통 함의** — 프론트와 백이 **독립 배포·독립 스케일** 가능해졌다.\
동시에 **네트워크 경계가 명시화**되면서 인증·버저닝·계약 호환성이 새 stakes로 떠올랐다.\
그리고 이 분리 덕에 — 같은 데이터 API 위에서 **렌더링 위치를 자유롭게 고를** 토대가 마련된다(다음 단계의 전제).

> **버저닝(versioning)** — API를 고칠 때 옛 클라이언트가 깨지지 않게 버전을 나눠 관리하는 일.\
> 예: 앱 구버전을 쓰는 사용자가 남아 있으면 `/v1`을 그대로 두고 `/v2`를 따로 연다.

### 6. SSR/SSG 회귀 — 서버로 돌아온 진자 (2016~)

**왜 이동했나** — 순수 SPA가 지불하던 청구서(느린 FCP·약한 SEO·거대 번들)가 너무 컸다.\
답은 "클라 렌더를 버리자"가 아니라 **"HTML은 다시 서버/빌드에서 미리 만들되, 그 위에 SPA의 상호작용을 얹자"** — 즉 **하이드레이션(hydration)** 모델이었다.

> **하이드레이션(hydration)** — 서버가 보낸 마른 HTML에 JS로 "물을 주어" 움직이게 만드는 과정.\
> 예: 버튼이 이미 화면에 그려져 있지만, JS가 이벤트를 붙여 줘야 비로소 눌린다.

> **SSR / SSG** — 요청이 올 때 서버에서 HTML을 만드는 것(SSR)과, 미리 빌드할 때 만들어 두는 것(SSG).\
> 예: 요청이 올 때마다 그 자리에서 만들면 SSR, 빌드할 때 한 번 만들어 두고 계속 쓰면 SSG다.

- **Next.js (2016, Vercel)**: React 컴포넌트를 **서버에서 미리 렌더(SSR)** 하거나 **빌드 타임에 정적 생성(SSG)** 한 뒤, 브라우저에서 같은 트리를 hydrate해 상호작용을 붙인다.\
  "첫 화면은 서버가, 이후는 SPA가." Gatsby(2017)·Nuxt(Vue)도 같은 흐름.
- **Jamstack (2016, Mathias Biilmann/Netlify)**: SmashingConf SF에서 제시.\
  **J**avaScript + **A**PIs + **M**arkup — 빌드 타임에 정적 HTML을 굽고 **CDN에 올린 뒤**, 동적 부분만 클라이언트 JS가 API를 호출해 채운다.\
  서버를 끄고 **CDN + 서버리스 함수**로 대체.

> **서버리스 함수(serverless function)** — 늘 켜 둔 서버 없이, 요청이 올 때만 잠깐 실행되는 함수 단위 배포.\
> 예: 문의 폼 전송 같은 동적 처리만 함수 하나로 올려 두고, 나머지는 전부 정적 파일로 둔다.

시간 축으로 그리면 SSR과 SSG가 갈리는 지점이 보인다.

```text
SSG (빌드 타임에 만든다)
  빌드할 때 ----> HTML 완성 ----> CDN 에 올림 ----> 요청 오면 그대로 준다

SSR (요청 타임에 만든다)
  요청이 올 때 ----> 서버가 그 자리에서 HTML 생성 ----> 응답

두 경우 모두, 브라우저에 도착한 뒤 hydrate 로 상호작용이 붙는다
```

**얻은 것** — corpus 「렌더링 전략」의 SSR/SSG 칸 그대로 — **빠른 FCP·강한 SEO**(서버/빌드가 완성 HTML 제공) + SPA급 상호작용.\
정적은 CDN에 올려 가장 싸고 빠르게.

**잃은 것** — **하이드레이션 세금.**\
서버가 HTML을 줘도 클라가 같은 컴포넌트 트리를 다시 그려 이벤트를 붙이는 비용(JS 다운로드+파싱+실행).\
"보이지만 안 눌리는" **uncanny valley**(FCP는 빠른데 TTI는 느림).\
빌드 타임 SSG는 **개인화·실시간 불가** → ISR(증분 정적 재생성)이 그 다리.\
진자는 서버로 돌아왔지만, hydration이라는 **새 비용**을 만들었다 — 이걸 깎는 게 다음 단계다.

```text
0ms                FCP                     TTI
 |------------------|-----------------------|
 흰 화면            화면은 다 보인다         이제 눌린다
                    (서버가 준 HTML)
                    그러나 눌러도 반응 없음
                    <-- 이 구간이 uncanny valley -->
```

> **ISR(증분 정적 재생성)** — 정적으로 구운 페이지를 나중에 다시 구워 갱신하는 방식.\
> 예: 원문은 "빌드 타임 SSG는 개인화·실시간 불가"라는 한계의 다리로 이것을 든다.

### 7. 엣지·서버 컴포넌트·아일랜드 — 진자의 현재 위치 (2020~)

**왜 이동했나** — "서버 회귀"의 남은 문제는 둘 — **(a) 전부 hydrate하는 JS 세금**, **(b) 서버가 한 리전에 있어 먼 사용자에게 느림.**\
2020년대의 해법은 진자를 한쪽 끝으로 더 밀지 않고, **렌더링을 잘게 쪼개 각 조각을 가장 싼 곳에 배치**하는 것이다.

- **엣지 렌더링**: 중앙 서버 대신 **사용자와 가까운 CDN 엣지 노드**(Cloudflare Workers 2017·Vercel Edge Functions 2021)에서 렌더·미들웨어 실행 → TTFB 단축.\
  단 엣지 런타임은 제약(노드 API 제한·콜드스타트)이 있어 무엇을 엣지로 보낼지가 설계 판단.
- **React Server Components(RSC)**: React 팀이 2020년 12월 공개, **Next.js 13 App Router(2022)** 가 주류화.\
  서버 컴포넌트는 **서버에서만 렌더되고 클라 번들을 만들지 않으며 hydrate할 것이 없다(hydration 비용 0).**\
  상호작용은 `"use client"` 경계 안으로만 격리.
- **아일랜드 아키텍처**: Jason Miller가 2020년 정식화, **Astro**가 구현.\
  페이지는 정적 HTML이 기본이고, **상호작용이 필요한 영역만 독립 "섬"으로 hydrate**.\
  JS를 페이지 단위가 아니라 위젯 단위로 절약.\
  React가 이 발상을 RSC로 흡수했다("서버 컴포넌트 = hydration 없는 HTML 섬").

> **TTFB(Time To First Byte)** — 요청을 보내고 첫 바이트가 돌아오기까지 걸린 시간.\
> 예: 서버가 지구 반대편에 있으면 아무리 빨리 만들어도 오가는 시간만으로 느려진다.

> **콜드스타트(cold start)** — 꺼져 있던 실행 환경을 처음 깨울 때 드는 추가 지연.\
> 예: 한동안 요청이 없던 함수가 첫 호출에서만 유난히 느린 현상.

> **엣지 노드(edge node)** — 사용자와 지리적으로 가까운 CDN 서버.\
> 예: 서울 사용자의 요청을 서울 노드가 받아 그 자리에서 렌더해 돌려준다.

페이지 하나에서 hydrate되는 범위를 나란히 놓으면 차이가 보인다.

```text
전부 hydrate (기존 SSR)            섬만 hydrate (islands · RSC)
+---------------------------+      +---------------------------+
| ##### 헤더 #####          |      |       헤더                |
| ##### 본문 #####          |      |       본문                |
| ##### 목록 #####          |      |       목록                |
| ##### 담기 버튼 #####     |      | ##### 담기 버튼 #####     |
+---------------------------+      +---------------------------+
 ##### = JS 가 다시 그리는 영역      버튼 하나만 JS 가 맡는다
```

```jsx
// RSC (Next.js App Router): 서버 컴포넌트는 클라 번들 0·hydration 0
// 기본이 서버 컴포넌트 — DB를 직접 await, JS는 클라로 안 감
async function ProductList() {
  const products = await db.products.findAll();   // 서버에서 실행
  return <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

// 상호작용이 필요한 "섬"만 클라이언트로 격리
"use client";
function AddToCart({ id }) {
  return <button onClick={() => addToCart(id)}>담기</button>;
}
```

주석이 말하듯 위쪽 함수는 DB를 직접 `await`하고 그 JS가 브라우저로 가지 않는다.\
아래쪽 `"use client"` 아래만 브라우저로 내려가는 "섬"이다.

**얻은 것** — hydration 세금을 **상호작용 섬만큼으로 최소화**(RSC·islands) + **지리적 지연 최소화**(엣지).\
corpus 「렌더링 전략」의 "HTML은 서버, hydration은 부분적으로" 원칙의 구현체.\
한 앱 안에서 페이지·컴포넌트마다 SSG/SSR/스트리밍/CSR을 **혼합**(하이브리드).

**잃은 것** — **정신적·구조적 복잡도.**\
서버/클라이언트 경계(`"use client"`)·엣지 런타임 제약·스트리밍 Suspense 경계·캐시 계층을 개발자가 의식적으로 설계해야 한다.\
"어디서 도느냐"가 컴포넌트 단위 의사결정이 되면서, 잘못 그으면 디버깅·정신모델 비용이 커진다.

## 8. 종합: 왜 진자는 멈추지 않는가

*(이 편의 「왜 그렇게 갔나」에 해당한다)*

각 이동을 한 줄로 압축하면, 매번 **"직전 시대가 비싸게 만든 것을 싸게 돌려받으려는" 교환**이었다.\
원문의 종합 표를 그대로 옮기면 이렇다.

| 이동 | 버린 비용 | 새로 진 비용 |
|------|----------|-------------|
| 정적 → CGI | 동적 불가 | 요청마다 프로세스 fork |
| CGI → 서버사이드 | print 지옥·프로세스 비용 | 풀 페이지 리로드(깜빡임) |
| 서버사이드 → AJAX/SPA | 풀 리로드·답답한 UX | 느린 FCP·약한 SEO·거대 JS |
| SPA → API 분리 | 렌더·데이터 결합 | 네트워크 경계·계약 관리 |
| SPA → SSR/SSG 회귀 | 느린 FCP·SEO 손실 | 하이드레이션 세금·인프라 |
| 회귀 → 엣지/RSC/아일랜드 | hydration·지리 지연 | 서버/클라 경계 설계 복잡도 |

표를 읽는 법 — 오른쪽 칸(새로 진 비용)이 대체로 다음 줄 왼쪽 칸(버린 비용)으로 넘어간다.\
한 시대의 해법이 다음 시대의 문제가 되는 사슬이다.\
다만 「SPA → API 분리」 행은 그 사슬의 한 칸이 아니라 SPA에서 갈라져 나온 **병렬 가지**다 — 바로 아래 「SPA → SSR/SSG 회귀」 행도 같은 SPA에서 출발한다.

**근본 동인은 변하지 않는다.**\
콘텐츠 성격(공개·정적 ↔ 개인화·실시간)과 두 트레이드오프 축 — **초기로딩·SEO ↔ 인프라·복잡도**, **즉시성 ↔ 정합성** — 사이의 긴장은 어떤 기술로도 소거되지 않고, 다만 **어디서 지불할지**가 바뀔 뿐이다.\
그래서 진자는 멈추지 않는다.

## 남긴 것 — 오늘 우리가 쓰는 것

다만 **돌아온 자리는 더 높은 나선**이다.\
2024년의 "서버 렌더"는 1999년의 그것과 달리 CDN·엣지·부분 hydration·컴포넌트 모델·하이브리드 라우팅을 갖췄다.

```text
1999 의 서버 렌더                  2024 의 서버 렌더
+---------------------------+      +---------------------------+
| 서버가 HTML 을 만든다     |      | 서버가 HTML 을 만든다     |
|                           |      | + CDN · 엣지              |
|                           |      | + 부분 hydration          |
|                           |      | + 컴포넌트 모델           |
|                           |      | + 하이브리드 라우팅       |
+---------------------------+      +---------------------------+
 모양은 같아 보이지만 같은 자리가 아니다
```

오늘의 정답은 한 점이 아니라 **"페이지·조각마다 렌더링 모드를 고르는 능력"** 그 자체다 — 이것이 corpus 「렌더링 전략」이 "콘텐츠 성격으로 되돌아가 재판정하라"고 말하는 이유이고, 30년 진자사가 도달한 결론이다.

남아 있는 것들을 한 줄씩 정리하면 이렇다.

- **CGI/1.1(RFC 3875)** — "서버가 외부 프로그램을 불러 그 출력을 응답으로 쓴다"는 약속. 사실상 첫 산업 표준이었다.
- **템플릿 + 상주 런타임** — 한 세대의 서버사이드 기술(PHP·ASP·JSP·Rails)을 낳은 두 아이디어.
- **MVC와 요청-응답 사이클** — Rails(2004)가 대중화하고 Django(2005)·Spring MVC가 공유하는 구조.
- **XMLHttpRequest에서 시작한 부분 갱신** — 페이지를 리로드하지 않고 DOM 일부만 바꾸는 방식의 원형.
- **REST와 GraphQL** — 프론트와 백을 잇는 두 가지 계약 형태.
- **hydration과 그 최소화 기법** — Next.js·Jamstack·RSC·아일랜드로 이어지는 계보.
- **엣지 실행** — Cloudflare Workers(2017)·Vercel Edge Functions(2021)로 상용화된 배치 선택지.

> **corpus 연결**: 이 역사 문서는 *왜 이 전략들이 생겨났나*(통시적)를, corpus 「렌더링 전략」은 *지금 무엇을 고를까*(공시적·의사결정)를 다룬다.\
> 둘을 함께 읽으면 CSR/SSR/SSG/ISR/스트리밍·RSC·islands가 **역사적 반작용의 산물**임이 보인다.\
> 관련: 「데이터-페칭-캐싱」(즉시성↔정합성) · 「상태-관리」(서버상태 vs 클라이언트상태) · 「성능-최적화」(번들·CWV).

## 용어 풀이

- **렌더링(rendering)** — 데이터를 사람이 보는 화면(HTML)으로 만드는 일.
- **정적 HTML** — 디스크의 파일을 그대로 돌려주는 방식. 누가 요청하든 같은 바이트.
- **무상태(stateless)** — 서버가 이전 요청을 기억하지 않는 성질. 복제가 쉬워진다.
- **CGI(Common Gateway Interface)** — 서버가 외부 프로그램을 호출해 그 표준출력을 응답으로 쓰는 규격. 1993년 Rob McCool 제안, RFC 3875로 CGI/1.1 공식화.
- **fork** — 요청마다 새 프로세스를 띄우는 것. CGI 성능 한계의 원인.
- **FastCGI / mod_perl** — CGI의 프로세스 비용을 줄이려 나온 후속 방식들.
- **템플릿(template)** — 빈칸이 뚫린 HTML 틀. 실행 시 값으로 채운다.
- **상주 런타임** — 요청마다 새로 뜨지 않고 계속 떠 있는 인터프리터·실행 환경.
- **PHP / ASP / JSP** — HTML에 코드를 끼워 넣는 1995~1999년의 서버사이드 기술들.
- **Ruby on Rails** — 2004년 DHH가 만든 풀스택 프레임워크. MVC·"설정보다 관습"·ORM(ActiveRecord).
- **MVC** — 모델·뷰·컨트롤러로 역할을 나눈 구조.
- **ORM** — DB의 표를 객체처럼 다루게 해 주는 층.
- **라우팅(routing)** — URL을 어느 처리 코드로 보낼지 정하는 규칙.
- **SEO** — 검색엔진이 페이지 내용을 잘 읽어 가게 만드는 일.
- **풀 페이지 리로드** — 상호작용 때마다 HTML 전체를 다시 받는 것. 서버사이드 시대의 대가.
- **AJAX** — 페이지를 리로드하지 않고 데이터만 비동기로 받아 일부만 갱신하는 기법. 2005-02-18 Jesse James Garrett 명명.
- **XMLHttpRequest** — 그 비동기 요청을 보내는 객체. IE5(1999)의 ActiveX가 기원.
- **SPA(Single Page Application)** — 라우팅·렌더링·상태를 전부 브라우저가 맡는 방식.
- **번들(bundle)** — 여러 JS 파일을 하나로 묶은 배포 파일.
- **CSR(Client-Side Rendering)** — 브라우저의 JS가 화면을 만드는 방식.
- **FCP(First Contentful Paint)** — 화면에 내용이 처음 그려지는 시점.
- **TTI(Time To Interactive)** — 눌렀을 때 실제로 반응하기 시작하는 시점.
- **REST** — Roy Fielding이 2000년 박사논문에서 정의한 아키텍처 스타일. 리소스(URL) + HTTP 동사 + 무상태.
- **GraphQL** — Facebook이 2012년 내부 개발, 2015년 오픈소스화. 필요한 필드만 질의하는 단일 엔드포인트.
- **over-fetching / under-fetching** — 필요 없는 것까지 받거나, 모자라 또 요청해야 하는 상황.
- **엔드포인트(endpoint)** — 요청을 보내는 주소 하나.
- **버저닝(versioning)** — API를 고칠 때 옛 클라이언트가 깨지지 않게 버전을 나누는 일.
- **SSR(Server-Side Rendering)** — 요청이 올 때 서버에서 HTML을 만드는 방식.
- **SSG(Static Site Generation)** — 빌드 타임에 미리 HTML을 만들어 두는 방식.
- **하이드레이션(hydration)** — 서버가 보낸 HTML에 JS로 이벤트를 붙여 움직이게 만드는 과정.
- **uncanny valley** — 화면은 보이는데 아직 눌리지 않는 구간(FCP는 빠른데 TTI는 느림).
- **ISR(증분 정적 재생성)** — 정적으로 구운 페이지를 조건에 따라 다시 구워 갱신하는 방식.
- **Next.js / Gatsby / Nuxt** — SSR·SSG + hydration 모델을 대중화한 프레임워크들(2016·2017).
- **Jamstack** — JavaScript + APIs + Markup. 2016년 Mathias Biilmann이 SmashingConf SF에서 제시.
- **서버리스 함수** — 요청이 올 때만 잠깐 실행되는 함수 단위 배포.
- **CDN** — 세계 곳곳의 복사본에서 가장 가까운 곳이 응답하는 서버망.
- **엣지 렌더링 / 엣지 노드** — 사용자와 가까운 CDN 노드에서 렌더·미들웨어를 실행하는 것.
- **TTFB(Time To First Byte)** — 요청 후 첫 바이트가 돌아오기까지의 시간.
- **콜드스타트(cold start)** — 꺼져 있던 실행 환경을 깨울 때 드는 추가 지연.
- **RSC(React Server Components)** — 서버에서만 렌더되고 클라 번들도 hydration도 만들지 않는 컴포넌트. 2020년 12월 공개.
- **`"use client"`** — RSC에서 클라이언트로 내려보낼 경계를 표시하는 지시자.
- **아일랜드 아키텍처(islands)** — 정적 HTML을 기본으로 두고 상호작용 영역만 독립적으로 hydrate하는 구조. Jason Miller가 2020년 정식화, Astro가 구현.
