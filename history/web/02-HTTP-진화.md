# HTTP 프로토콜의 진화 — HTTP/0.9부터 HTTP/3·TLS 1.3까지

> 원본: `~/project/web-history/02-HTTP-진화.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-18).\
> 연도·인명·논문명·표준번호·코드·표는 원문 그대로다.\
> ASCII 도식 21개와 「한눈에」의 택배 비유, 용어 블록의 「예:」, 「용어 풀이」는 원문에 없는 보충이다.\
> 원문이 절마다 반복해 쓴 소제목(「시대적 배경」)은 이 문서의 골격으로 대체했다.

## 한눈에 — 쉽게 말하면

**HTTP의 30년은 "택배 절차를 계속 고쳐 온 역사"다 — 1.0 이후로는 무엇을 보내는지를 그대로 두고, 보내는 방법만 바꿨다.**

- 처음에는 **쪽지 한 장**이었다.\
  "그 문서 주세요"라고 적힌 한 줄을 보내면, 답으로 문서 내용만 왔다. 송장도 영수증도 없었다.
- 그래서 **송장(헤더)**을 붙였다.\
  "이건 이미지입니다", "찾는 물건이 없습니다" 같은 말을 할 수 있게 됐다.
- 그런데 **물건 하나마다 배달원이 새로 오는** 것이 낭비였다.\
  그래서 배달원을 문 앞에 대기시켰다(연결 재사용).
- 다음 병목은 **줄 서기**였다.\
  먼저 온 주문이 느리면 뒤의 주문이 다 막혔다. 그래서 한 트럭에 여러 상자를 섞어 싣게 했다.
- 마지막 병목은 **트럭 자체**였다.\
  상자 하나가 떨어지면 트럭이 뒤의 모든 상자를 붙들고 기다렸다. 그래서 트럭을 새로 짰다.

핵심 패턴은 단순하다.

> **각 버전은 직전 버전이 만든 병목을 푼다.**

```text
HTTP/0.9  응답이 무엇인지 설명할 수 없다
   |
   | 헤더·상태 코드를 붙인다
   v
HTTP/1.0  요청 하나마다 TCP를 새로 열어야 한다
   |
   | 연결을 재사용한다 (keep-alive)
   v
HTTP/1.1  응답이 요청 순서대로 와야 한다 (애플리케이션 계층 HOL 블로킹)
   |
   | 한 연결 안에서 요청을 독립적으로 다룬다 (멀티플렉싱)
   v
HTTP/2    한 패킷이 유실되면 무관한 스트림까지 멈춘다 (TCP 계층 HOL 블로킹)
   |
   | 전송 계층을 TCP에서 QUIC(UDP)로 갈아끼운다
   v
HTTP/3    (현재)
```

그림 해설 (한 단계씩):

- 세로줄 옆의 한 줄이 **그 버전이 한 일**이고, 박스 안의 문장이 **그 다음 버전이 마주한 병목**이다.
- 마지막 단계에서는 원문 표현대로 **전송을 아예 UDP 기반 QUIC로 바꿔** 그 병목까지 풀었다.

> **프로토콜(protocol)** — 두 프로그램이 서로 말이 통하게 하려고 미리 정해 둔 절차와 형식.\
> 예: 전화를 걸면 "여보세요" → 용건 → "끊습니다" 순서를 서로 지키는 것과 같다.

> **TCP / UDP** — 인터넷에서 데이터를 실어 나르는 두 가지 방식. TCP는 순서와 도착을 보장하고, UDP는 보장하지 않는 대신 단순하다.\
> 예: TCP는 등기우편(순서·수령 확인), UDP는 그냥 던지는 전단지에 가깝다.

## 한눈에 보는 타임라인

원문의 표를 그대로 옮긴 것이다 — 연도·표준 번호는 여기서 확인하면 된다.

| 버전 | 연도 | 표준 문서 | 전송 | 한 줄 요약 | 풀어낸 병목 |
|------|------|-----------|------|------------|-------------|
| HTTP/0.9 | 1991 | (RFC 없음) | TCP | `GET /path` 한 줄, 응답은 HTML 본문뿐 | — (출발점) |
| HTTP/1.0 | 1996 | RFC 1945 (정보성) | TCP | 헤더·상태코드·`Content-Type`·POST/HEAD | "HTML 말고 다른 것"을 못 보내던 한계 |
| HTTP/1.1 | 1997 | RFC 2068 → 2616 → 7230~7235 | TCP | keep-alive·파이프라이닝·`Host` 헤더·청크 인코딩 | 요청마다 새 TCP 핸드셰이크 / 가상호스팅 불가 |
| HTTP/2 | 2015 | RFC 7540 (+ HPACK 7541) | TCP | 바이너리 프레이밍·멀티플렉싱·헤더압축·서버푸시 | 애플리케이션 계층 HOL 블로킹 / 헤더 중복 |
| HTTP/3 | 2022 | RFC 9114 (+ QUIC 9000) | **UDP/QUIC** | QUIC 기반·스트림별 독립 전달·0-RTT·QPACK | **TCP 계층** HOL 블로킹 / 핸드셰이크 지연 |

> RFC 9113(2022)이 HTTP/2를, RFC 9110~9112(2022)가 HTTP "시맨틱"과 1.1 메시징을 재정리해 현재의 공식 기준이 되었다. 즉 HTTP/1.1·2의 최신 정본은 각각 RFC 9112·9113이며, RFC 9110(HTTP Semantics)이 버전 공통 의미론을 한곳에 모았다.

### 진화의 큰 줄기

원문의 타임라인 그림을 글자 도식으로 옮기면 이렇다(노드 문구는 그대로다).

```text
HTTP 주요 버전 타임라인

1991 : HTTP/0.9 - 한 줄 GET, 응답은 HTML뿐
1996 : HTTP/1.0 - 헤더·상태코드·Content-Type (RFC 1945)
1997 : HTTP/1.1 - keep-alive·Host 헤더·파이프라이닝 (RFC 2068)
2015 : HTTP/2 - 멀티플렉싱·HPACK·서버푸시 (SPDY 기반)
2018 : TLS 1.3 - 핸드셰이크 1-RTT, 0-RTT 재개 (RFC 8446)
2021 : QUIC - UDP 위 신뢰성 전송 표준화 (RFC 9000)
2022 : HTTP/3 - QUIC 위 HTTP, TCP HOL 블로킹 해소 (RFC 9114)
```

> **시맨틱(semantics, 의미론)** — "무엇을 말하는가"에 해당하는 부분. HTTP에서는 메서드·상태코드·헤더의 뜻이다.\
> 예: "GET은 가져오기다"라는 약속은 버전이 바뀌어도 그대로다 — 그게 시맨틱이다.

## HTTP/0.9 (1991) — 한 줄 프로토콜

### 시대 배경

팀 버너스리(Tim Berners-Lee)가 1989~1991년 CERN에서 월드와이드웹을 만들면서 함께 설계한 최초의 전송 규약이다.

1991년 8월 6일 버너스리가 `alt.hypertext` 뉴스그룹에 웹을 공개하면서 사실상 공개 프로젝트로서의 웹이 시작됐다.

이 최초 버전은 나중에 후속 버전과 구분하기 위해 "HTTP/0.9"로 불리게 됐고, **정식 RFC로 발행된 적이 없다.**

### 무엇이었나

프로토콜 전체가 한 줄이었다.\
요청은 유일한 메서드인 `GET`과 경로뿐이고, 응답은 요청한 문서(HTML)의 본문 그 자체뿐이었다.

```text
요청:  GET /index.html⏎          (CRLF로 끝나는 단 한 줄)

응답:  <html>안녕하세요 …</html>   (HTML 본문만, 헤더 없음)
```

- 메서드는 `GET` 하나뿐. 상태 코드도, 헤더도, 버전 표기도 없다.
- 응답에 메타데이터가 전혀 없으므로 **HTML만** 주고받을 수 있었다. 이미지·텍스트·JSON 같은 다른 형식을 "이건 무슨 타입이다"라고 알릴 방법이 없었다.
- 응답이 끝나면 서버가 곧바로 TCP 연결을 닫았다.

> **메서드(method)** — 요청이 무엇을 하려는지 나타내는 동사. `GET`은 "가져와라"다.\
> 예: 주문서 맨 위에 "구매"인지 "반품"인지 적어 두는 칸에 해당한다.

> **메타데이터(metadata)** — 내용물 자체가 아니라 그 내용물을 설명하는 정보.\
> 예: 소포 안의 물건이 내용물이고, 겉면의 "깨지기 쉬움 / 3kg / 식품"이 메타데이터다.

### 왜 이대로는 안 됐나

웹이 문서 공유를 넘어 이미지·폼·다양한 콘텐츠로 확장되자, **"응답이 무엇인지 설명하는 메타데이터"의 부재**가 결정적 한계가 됐다.

서버는 성공/실패를 알릴 수도, 콘텐츠 종류를 밝힐 수도 없었다.\
이 공백을 메우는 것이 다음 버전의 과제였다.

## HTTP/1.0 (1996, RFC 1945) — 헤더와 상태 코드의 등장

### 시대 배경

1991~1995년 사이 브라우저(Mosaic, Netscape)와 서버가 폭증하면서 제각각 확장 기능을 붙였다.

이 난립한 "실전 관행"을 정리해, HTTP 워킹그룹(HTTP-WG)이 1996년 5월 **RFC 1945**로 문서화한 것이 HTTP/1.0이다.

다만 이 문서는 표준이 아니라 **정보성(informational) RFC**다 — 즉 "현장에서 통용되던 구현들의 공통 사용법"을 기록한 것이지 강제 규격이 아니었다.

> **정보성(informational) RFC** — 지켜야 할 규격이 아니라, 참고용으로 기록해 둔 문서.\
> 예: "다들 이렇게 쓰고 있더라"를 정리한 회의록에 가깝고, "이렇게 해야 한다"는 명령문은 아니다.

### 무엇을 풀었나 — 응답을 "설명"할 수 있게 됐다

0.9의 핵심 결핍이었던 메타데이터를 **헤더(header)** 로 도입했다.

```text
요청:
GET /index.html HTTP/1.0
User-Agent: Mozilla/2.0
Accept: text/html

응답:
HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 137
Date: Tue, 14 May 1996 08:12:31 GMT

<html>…</html>
```

- **버전 표기**: 요청 줄 끝에 `HTTP/1.0`이 붙어, 이후 버전 협상이 가능해졌다.
- **상태 코드**: `200 OK`, `404 Not Found` 같은 코드가 응답 첫 줄(status line)에 등장했다. 성공·실패가 HTML 관습이 아니라 **프로토콜 수준의 사실**이 됐다.
- **`Content-Type`**: 서버가 이미지를 보내며 "이건 image/gif다"라고 말할 수 있게 됐다. 웹이 HTML 너머로 확장되는 토대.
- **메서드 추가**: `GET`에 더해 `HEAD`, `POST`가 들어와 폼 전송·메타데이터 조회가 가능해졌다.
- 그 외 기본적인 캐싱·인증(`Authorization`) 메커니즘이 도입됐다.

0.9와 1.0의 응답을 나란히 놓으면 무엇이 늘었는지가 한눈에 보인다.

```text
HTTP/0.9 의 응답                      HTTP/1.0 의 응답
+---------------------------+        +---------------------------+
|                           |        | HTTP/1.0 200 OK           |
|                           |        | Content-Type: text/html   |
|  (설명하는 줄이 없다)     |        | Content-Length: 137       |
|                           |        | Date: ...                 |
|                           |        |                           |
| <html>...</html>          |        | <html>...</html>          |
+---------------------------+        +---------------------------+
  받은 쪽은 이게 무엇인지               무엇인지, 성공인지, 길이가
  추측할 수밖에 없다                    얼마인지 적혀서 온다
```

> **헤더(header)** — 본문 앞에 붙는 "이름: 값" 형식의 설명 줄들.\
> 예: `Content-Type: text/html` 은 "이 본문은 HTML이다"라는 안내다.

> **상태 코드(status code)** — 요청이 어떻게 됐는지를 숫자로 알리는 값.\
> 예: `200 OK`는 잘 됐다, `404 Not Found`는 그런 문서가 없다는 뜻이다.

### 남은 문제

HTTP/1.0은 기본적으로 **요청 하나당 TCP 연결 하나**를 쓰고 응답 후 닫았다.

이미지 20개가 박힌 페이지를 받으려면 TCP 핸드셰이크를 20번 반복해야 했다 — 매번 3-way handshake의 왕복 지연(RTT)이 누적됐다.

또한 한 서버 IP에서 여러 도메인을 호스팅할 방법이 없었다(요청에 호스트명이 없으므로).

이 두 문제가 1.1의 출발점이 된다.

> **3-way handshake · RTT** — TCP 연결을 열 때 주고받는 3번의 인사와, 한 번 왕복하는 데 걸리는 시간.\
> 예: 통화를 시작할 때마다 "여보세요 / 네 / 들리세요"를 반복해야 한다면, 통화 자체보다 인사가 더 오래 걸릴 수 있다.

## HTTP/1.1 (1997, RFC 2068) — 오늘날까지 쓰이는 표준

### 시대 배경

HTTP/1.0이 나온 지 불과 1년 만인 1997년 1월, **RFC 2068**로 HTTP/1.1이 발행됐다.\
1.0의 비효율(연결 재사용 불가)과 운영상 한계(가상호스팅 불가)가 그만큼 시급했다는 뜻이다.

이후 1999년 **RFC 2616**으로 개정되어 15년간 사실상의 웹 표준 노릇을 했다.\
2014년 **RFC 7230~7235**로 분할·정밀화됐다(현재 정본은 2022년 RFC 9110·9112).

HTTP/1.1은 지금도 가장 널리 호환되는 버전이다.

### 무엇을 풀었나 ① — keep-alive(지속 연결)

**연결을 응답 후 닫지 않고 재사용**한다.

페이지에 자산 20개가 있어도 핸드셰이크 20번이 아니라 한두 개의 TCP 연결로 처리할 수 있게 됐다.\
HTTP/1.1에서는 지속 연결이 **기본값**이며, 끊고 싶을 때만 `Connection: close`를 보낸다.

```text
GET /a.png HTTP/1.1
Host: example.com
Connection: keep-alive     ← 연결 유지(1.1 기본)

(같은 TCP 연결로 이어서 b.png, c.png … 요청)
```

전후를 그림으로 대비하면 이렇다.

```text
HTTP/1.0 — 자산 20개                 HTTP/1.1 keep-alive
+-------------------------------+   +-------------------------------+
| [연결] a.png [끊음]           |   | [연결]                        |
| [연결] b.png [끊음]           |   |    a.png                      |
| [연결] c.png [끊음]           |   |    b.png                      |
|   ... 20번 반복 ...           |   |    c.png  ... 20개 ...        |
+-------------------------------+   | [끊음]                        |
  핸드셰이크 20번, RTT 20번 누적    +-------------------------------+
                                      핸드셰이크는 한두 번으로 끝난다
```

**왜 이게 나은가** — 요청 하나하나가 "인사부터 다시 하는" 비용을 내지 않아도 된다.\
자산이 많은 페이지일수록 이득이 커진다.

> **keep-alive(지속 연결)** — 응답을 받은 뒤에도 TCP 연결을 닫지 않고 다음 요청에 다시 쓰는 것.\
> 예: 배달원이 물건 하나 주고 돌아가는 대신, 문 앞에서 기다렸다가 다음 물건도 바로 건네주는 셈이다.

### 무엇을 풀었나 ② — `Host` 헤더(가상호스팅)

HTTP/1.1은 `Host` 헤더를 **필수**로 만들었다.

요청에 목적지 도메인이 담기므로, **하나의 IP 주소에서 여러 도메인**(가상호스트)을 구분해 서빙할 수 있게 됐다.\
IPv4 주소가 희소해지던 시기에 웹 호스팅 경제성을 바꾼 변화다.

```text
GET /index.html HTTP/1.1
Host: blog.example.com     ← 같은 서버 IP라도 이 헤더로 사이트를 구분
```

```text
Host 헤더가 없을 때                    Host 헤더가 있을 때
+-----------------------------+       +-----------------------------+
| 서버 IP 하나                |       | 서버 IP 하나                |
|   -> 사이트도 하나          |       |   Host: blog.example.com    |
|                             |       |   Host: shop.example.com    |
| 사이트를 늘리려면 IP를      |       |   Host: docs.example.com    |
| 새로 사야 한다              |       | 요청마다 목적지가 적혀 온다 |
+-----------------------------+       +-----------------------------+
  IP 주소가 곧 비용이 된다              IP 하나로 여러 사이트를 돌린다
```

> **가상호스팅(virtual hosting)** — 서버 한 대(IP 하나)에서 여러 도메인의 사이트를 함께 서비스하는 것.\
> 예: 한 건물 주소에 여러 회사가 층별로 입주해 있고, 우편물은 "○층 ○○회사"라는 표시로 갈린다.

### 무엇을 풀었나 ③ — 그 외

- **청크 전송 인코딩(`Transfer-Encoding: chunked`)**: 전체 크기를 미리 모를 때도 본문을 조각내어 스트리밍할 수 있다(동적 생성 응답에 필수).
- **파이프라이닝(pipelining)**: 응답을 기다리지 않고 여러 요청을 연속해서 보내는 기능. 이론상 지연을 줄인다 — 그러나 아래의 치명적 한계로 사실상 실패했다.
- 더 정교한 캐싱 모델(`Cache-Control`, `ETag`/조건부 요청), `OPTIONS`·`PUT`·`DELETE` 등 메서드 정비.

> **청크 전송 인코딩(chunked)** — 본문 전체 길이를 모른 채로, 만들어지는 대로 조각내어 먼저 보내는 방식.\
> 예: 요리가 다 끝나길 기다리지 않고 완성된 접시부터 순서대로 내가는 것과 같다.

### 남은 문제 — 줄 맨 앞이 막히는 현상(Head-of-Line Blocking)

파이프라이닝은 **응답이 요청 순서대로 와야 한다**는 제약이 있었다.

첫 응답이 느리면 그 뒤의 모든 응답이 줄줄이 막힌다 — 이것이 **HOL(Head-of-Line) 블로킹**이다.

```text
파이프라이닝으로 세 요청을 연달아 보냈다

  보낸 순서 :  [1] a.html   [2] b.png   [3] c.png
                  |            |           |
  서버 처리 :  a.html 이 느리다 (예: 서버가 오래 계산한다)
                  |            |           |
  응답 순서 :  a.html 이 끝날 때까지 b.png, c.png 는
               이미 준비됐어도 내보낼 수 없다

  결과 : 줄의 맨 앞(head of line)이 막히면 뒤가 전부 대기
```

그림 해설 (한 단계씩):

- 문제는 서버가 느린 게 아니라 **순서를 지켜야 한다는 규칙**이다.
- b.png가 먼저 준비돼도, 순서가 뒤이므로 내보낼 수 없다.
- 그래서 어떤 주요 브라우저도 파이프라이닝을 기본 활성화하지 않았다.

**현실의 우회책**은 **도메인당 여러 TCP 연결을 동시에 여는 것**(브라우저당 보통 6개)이었다.\
그러나 이는 연결 수 제한·혼잡 제어 비효율이라는 새 비용을 낳았다.

진짜 해법은 한 연결 안에서 요청들을 **독립적으로** 다루는 것이었고, 그것이 HTTP/2의 멀티플렉싱이다.

> **HOL(Head-of-Line) 블로킹** — 줄의 맨 앞이 막히면 뒤에 있는 것들이 준비돼 있어도 못 나가는 현상.\
> 예: 계산대 한 줄에서 앞 손님이 카드 오류로 오래 걸리면, 뒤의 모두가 기다려야 한다.

## HTTP/2 (2015, RFC 7540) — 멀티플렉싱으로 다시 쓴 전송

### 시대 배경

HTTP/2의 뿌리는 구글이 2009년 발표한 실험 프로토콜 **SPDY("speedy")** 다.

SPDY는 단일 TLS 연결 위에서 바이너리 프레이밍·멀티플렉싱·헤더 압축·서버 푸시를 도입해 페이지 로딩 지연을 줄였다.\
이 아이디어들이 IETF 표준화 과정을 거쳐 2015년 5월 **RFC 7540**으로 HTTP/2가 됐다.

**중요한 점**: HTTP/2는 HTTP의 의미론(메서드·상태코드·헤더)은 그대로 두고, **전송 방식만** 바꿨다.\
기존 웹 애플리케이션을 고치지 않아도 적용되도록 한 설계다.

### 무엇을 풀었나 ① — 바이너리 프레이밍과 멀티플렉싱

HTTP/2는 텍스트 메시지를 **바이너리 프레임(frame)** 으로 쪼갠다.\
그리고 각 요청/응답을 **스트림(stream)** 이라는 논리적 채널에 실어 하나의 TCP 연결 위에 **동시에 인터리빙**한다.

응답이 순서대로 올 필요가 없으므로, 1.1 파이프라이닝의 애플리케이션 계층 HOL 블로킹이 사라진다.

```text
하나의 TCP 연결:
 stream 1 ──[HEADERS][DATA]──┐
 stream 3 ──[HEADERS][DATA]──┤  프레임이 뒤섞여(interleave) 동시에 흐른다
 stream 5 ──[HEADERS]────────┘  → 도메인당 연결 1개로 충분
```

이 덕분에 1.1 시대의 "도메인당 6개 연결" 같은 우회책(및 도메인 샤딩)이 불필요해졌다.

우회책이 사라진다는 것이 무슨 뜻인지 전후로 대비하면 이렇다.

```text
HTTP/1.1 의 우회책                    HTTP/2
+-----------------------------+      +-----------------------------+
| 연결 1 : 요청 -> 응답       |      | 연결 1 개                   |
| 연결 2 : 요청 -> 응답       |      |   stream 1 - 프레임         |
| 연결 3 : 요청 -> 응답       |      |   stream 3 - 프레임         |
|   ... 도메인당 보통 6개 ... |      |   stream 5 - 프레임         |
+-----------------------------+      +-----------------------------+
  연결 수 제한과 혼잡 제어             한 연결 안에서 요청들이
  비효율이라는 새 비용이 든다          서로를 기다리지 않는다
```

> **멀티플렉싱(multiplexing)** — 통로 하나에 여러 흐름을 섞어 동시에 실어 나르는 것.\
> 예: 차선 하나에 여러 목적지의 차가 섞여 달리되, 각자 목적지 표시를 달고 있어 헷갈리지 않는 상태다.

> **프레임(frame) / 스트림(stream)** — 메시지를 쪼갠 조각 / 그 조각들이 속한 논리적 채널.\
> 예: 프레임은 낱장, 스트림은 "3번 문서"라는 묶음 이름이다. 낱장이 섞여 도착해도 묶음 번호로 다시 모은다.

> **바이너리 프레이밍(binary framing)** — 텍스트 메시지를 이진 형식의 프레임으로 쪼개어 보내는 것.\
> **[보충]** 예: 글로 쓴 주소 대신 바코드를 붙이는 것에 가깝다 — 원문은 "쪼갠다"는 사실만 적고 그 이유는 말하지 않는다.

### 무엇을 풀었나 ② — HPACK 헤더 압축

HTTP 요청은 매번 비슷한 헤더(쿠키·User-Agent 등)를 반복 전송한다.

**HPACK(RFC 7541)** 은 이를 세 방식으로 압축한다.

아래 도식의 괄호 줄은 **[보충]** 이다 — 원문은 정적 테이블·동적 테이블·허프만 인코딩의 이름만 적는다.

```text
같은 헤더를 반복해서 보낼 때 HPACK이 하는 일

  ① 정적 테이블   자주 쓰는 헤더는 번호로 미리 약속돼 있다
                  (그 번호만 보내면 된다)
  ② 동적 테이블   최근에 보낸 헤더를 양쪽이 기억해 둔다
                  (두 번째부터는 "아까 그거"로 가리킨다)
  ③ 허프만 인코딩 그래도 보내야 하는 글자는 짧은 비트로 바꿔 보낸다

  결과 : 반복 헤더의 중복 전송이 크게 줄었다
```

> **HPACK** — HTTP/2가 쓰는 헤더 압축 방식. 정적 테이블·동적 테이블·허프만 인코딩을 조합한다.\
> 예: 같은 주소를 매번 다 적는 대신 "지난번 그 주소"라고만 적는 것과 같다.

> **허프만 인코딩(Huffman encoding)** — 자주 나오는 글자에 짧은 부호를, 드문 글자에 긴 부호를 주어 전체 길이를 줄이는 방법.\
> 예: 자주 쓰는 단어를 약어로 줄여 쓰면 문서 전체가 짧아지는 것과 같다.

### 무엇을 풀었나 ③ — 서버 푸시·스트림 우선순위

- **서버 푸시**: 클라이언트가 요청하기 전에, 서버가 곧 필요할 자원(예: HTML과 함께 쓰일 CSS)을 미리 보낸다.\
  다만 캐시된 자원까지 중복 전송하는 비효율이 드러나 실전 활용은 제한적이었고, 이후 브라우저들이 지원을 거두었다.
- **스트림 우선순위(priority)**: 어떤 스트림을 먼저 처리할지 가중치로 표현.

### 남은 문제 — TCP 계층의 HOL 블로킹

HTTP/2는 애플리케이션 계층의 HOL 블로킹은 풀었지만, **여전히 TCP 위에서 동작**한다.

TCP는 바이트 순서 보장을 위해, 패킷 하나가 유실되면 그 뒤에 도착한 모든 패킷을 커널 버퍼에 묶어두고 재전송을 기다린다.

그런데 HTTP/2는 모든 스트림을 **하나의** TCP 연결에 담으므로, 한 스트림의 패킷 유실이 **무관한 다른 스트림들까지** 멈춰 세운다.

멀티플렉싱이 한 단계 아래(전송 계층)에서 다시 막히는 것이다.

```text
HTTP/2 — 애플리케이션 계층은 뚫렸지만 전송 계층에서 다시 막힌다

  [HTTP/2 계층]   stream A · stream B · stream C  (서로 독립이라고 본다)
        |
        v
  [TCP 계층]      하나의 순서 있는 바이트 스트림으로 취급한다
                  A의 패킷 하나가 유실되면
                  뒤에 도착한 B·C의 패킷도 커널 버퍼에 묶인다
        |
        v
  결과 : 무관한 스트림까지 재전송을 기다린다
```

이 "TCP HOL 블로킹"을 풀려면 **전송 계층 자체를 바꿔야** 했다.

## HTTP/3 (2022, RFC 9114) — TCP를 버리고 QUIC 위로

### 시대 배경

TCP HOL 블로킹은 TCP가 "연결 전체를 하나의 순서 있는 바이트 스트림"으로 다루는 한 근본적으로 풀 수 없다.

그래서 구글은 **QUIC** 라는 새 전송 프로토콜을 UDP 위에 만들었다.

UDP는 순서·신뢰성을 보장하지 않는 단순 전송이라, 그 위에 **스트림 인식·신뢰성·혼잡 제어·암호화**를 직접 구현해 TCP의 역할을 대체하되 더 유연하게 만든 것이다.

IETF가 이를 2021년 5월 **RFC 9000**(QUIC)으로 표준화했고, 그 위에 HTTP를 얹은 **HTTP/3**가 2022년 6월 **RFC 9114**로 나왔다.

> **QUIC** — UDP 위에 스트림 인식·신뢰성·혼잡 제어·암호화를 직접 구현한 새 전송 프로토콜.\
> 예: 규격이 고정된 남의 트럭(TCP)을 쓰는 대신, 빈 섀시(UDP) 위에 필요한 기능만 골라 얹어 트럭을 새로 짠 셈이다.

> **혼잡 제어(congestion control)** — 네트워크가 막히지 않도록 보내는 속도를 스스로 조절하는 장치.\
> 예: 도로가 밀리는 기미가 보이면 출발 대수를 줄이는 것과 같다.

### 무엇을 풀었나 ① — 스트림별 독립 전달 (TCP HOL 해소)

QUIC는 **전송 계층에서 스트림을 인식**한다.

각 스트림은 독립된 순서 있는 바이트열이며, 패킷이 유실되면 **그 패킷에 들어 있던 스트림만** 영향을 받고 나머지 스트림은 지연 없이 계속 처리된다.

HTTP/2가 풀지 못한 TCP 계층 HOL 블로킹이 여기서 사라진다.

```text
HTTP/2 (TCP):   stream A의 패킷 유실 → A·B·C 전부 대기 (TCP가 순서 보장)
HTTP/3 (QUIC):  stream A의 패킷 유실 → A만 대기, B·C는 계속 진행
```

**왜 이게 나은가** — 차이는 "누가 순서를 보장하는가"에 있다.\
TCP는 연결 전체를 하나의 순서 있는 흐름으로 보고, QUIC는 스트림마다 따로 본다.\
그래서 QUIC에서는 한 스트림의 사고가 다른 스트림으로 번지지 않는다.

### 무엇을 풀었나 ② — 더 빠른 연결 수립 (0-RTT)

TCP+TLS는 연결을 열 때 TCP 핸드셰이크와 TLS 핸드셰이크를 **따로** 한다(왕복 여러 번).

QUIC는 **전송 핸드셰이크와 TLS 1.3 암호 핸드셰이크를 하나로 합쳐** 1-RTT에 끝낸다.

게다가 한 번 연결했던 서버에는 **0-RTT**로 첫 패킷에 데이터를 함께 실어 보낼 수 있어, 재방문 시 지연이 거의 없다.

```text
TCP + TLS                              QUIC
+-----------------------------+        +-----------------------------+
| TCP 핸드셰이크              |        | 전송 핸드셰이크와 TLS 1.3   |
|        그다음               |        | 암호 핸드셰이크를 하나로    |
| TLS 핸드셰이크              |        | 합쳐 1-RTT 에 끝낸다        |
|                             |        |                             |
| 왕복이 여러 번 필요하다     |        | 재방문이면 0-RTT            |
+-----------------------------+        +-----------------------------+
  연결을 여는 데 시간이 든다             첫 패킷에 데이터를 같이 싣는다
```

QUIC는 또 **연결 ID** 로 연결을 식별한다.\
그래서 Wi-Fi↔LTE처럼 네트워크(IP)가 바뀌어도 연결이 끊기지 않는 **연결 마이그레이션**을 지원한다.

> **0-RTT / 1-RTT** — 데이터를 보내기 전에 필요한 왕복 횟수. 0-RTT는 첫 패킷에 데이터를 같이 싣는다는 뜻이다.\
> 예: 단골 가게에 들어서자마자 "늘 먹던 걸로"라고 말할 수 있으면 0-RTT, 매번 메뉴부터 물어야 하면 그만큼 왕복이 는다.

> **연결 마이그레이션(connection migration)** — IP 주소가 바뀌어도 같은 연결을 이어 가는 기능. QUIC는 연결 ID로 연결을 식별해 이를 가능하게 한다.\
> 예: 집을 나서며 Wi-Fi가 LTE로 바뀌어도 보던 영상이 끊기지 않는다.

### 무엇을 풀었나 ③ — QPACK 헤더 압축

HTTP/2의 HPACK은 헤더가 **순서대로** 도착한다고 가정한다.\
그런데 QUIC는 스트림 독립성 때문에 그 순서를 보장하지 않는다.

그래서 HTTP/3는 HPACK 대신, 순서 비의존성을 견디도록 설계된 **QPACK(RFC 9204)** 으로 헤더를 압축한다.

> **QPACK** — HTTP/3의 헤더 압축 방식. 헤더가 순서대로 도착하지 않아도 동작하도록 설계됐다.\
> 예: HPACK이 "아까 그거"라고 말하려면 '아까'가 먼저 도착했어야 하는데, QPACK은 그 전제를 깐 채로도 버틴다.

### 의의

HTTP/3는 의미론(메서드·상태코드)은 HTTP/1.1 이래 그대로 유지하면서, 그것을 실어 나르는 **바닥(전송 계층)을 TCP에서 QUIC로 교체**한 변화다.

"HTTP가 무엇을 말하는가"는 그대로 두고 "어떻게 실어 나르는가"만 30년에 걸쳐 세 번(1.1 연결 재사용 → 2 멀티플렉싱 → 3 QUIC) 다시 쓴 셈이다.

## 보안 계층의 진화 — SSL에서 TLS 1.3까지

HTTP 자체는 평문 프로토콜이다.

기밀성·무결성·서버 인증은 그 아래 **TLS(Transport Layer Security)** 계층이 담당하며, "HTTP over TLS"가 곧 **HTTPS**다.

HTTP의 진화와 보안 계층의 진화는 맞물려 왔다.

> **TLS(Transport Layer Security)** — HTTP 아래에서 내용을 암호화하고 상대가 진짜 그 서버인지 확인해 주는 계층.\
> 예: 엽서(평문 HTTP)를 봉인된 봉투(TLS)에 넣어 보내는 것에 해당한다.

> **HTTPS** — HTTP를 TLS 위에서 주고받는 것. "HTTP over TLS"의 이름이다.\
> 예: 주소창의 자물쇠 표시가 이 상태를 가리킨다.

### SSL → TLS — 이름과 주인의 변천

```text
[연대순 구분선 — 아래는 같은 계보의 버전 변천이다]

1994  SSL 1.0   넷스케이프의 Taher Elgamal 설계
                치명적 결함으로 공개되지 못했다
------
1995  SSL 2.0   역시 취약했다
1996  SSL 3.0   Paul Kocher 등이 전면 재작성
                데이터 전송 계층과 메시지 계층을 분리
                Diffie-Hellman 키 교환을 더했다
------
1999  TLS 1.0   RFC 2246 (1월)
                사실상 "SSL 3.1"이지만 넷스케이프가 SSL을 IETF에 넘기며
                이름을 TLS로 바꿨다. SSL과 호환은 끊겼다
------
2006  TLS 1.1
2008  TLS 1.2   SHA-256·AEAD 암호 모드 도입, 오랫동안 주력 버전
------
2018  TLS 1.3   RFC 8446 (8월). 프로토콜 최초의 대대적 개편
------
2021  RFC 8996 (3월) 으로 TLS 1.0·1.1 공식 폐기
```

그림 해설 (한 단계씩):

- 이 세로 목록은 **하나의 계보가 버전을 갈아 온 순서**다 — 서로 다른 갈래가 아니다.
- 이름이 SSL에서 TLS로 바뀐 지점은 1999년이고, 그 이유는 기술이 아니라 **주인이 바뀐 것**이다(넷스케이프 → IETF).
- SSL 1.0은 아예 공개되지 못했으므로, 실제로 쓰인 SSL은 2.0부터다.

### TLS 1.3 (2018, RFC 8446) — 첫 전면 개편

28번의 드래프트 끝에 2018년 8월 발행된 TLS 1.3은 프로토콜 최초의 대대적 개편이다.

**① 핸드셰이크 단축.**\
기존 TLS는 핸드셰이크에 2-RTT가 걸렸으나, **TLS 1.3은 1-RTT**로 줄였다.\
재방문 시에는 **0-RTT**로 첫 메시지에 데이터를 실어 보낼 수 있다(QUIC의 0-RTT가 이 위에 선다).

```text
기존 TLS                  TLS 1.3                  TLS 1.3 재방문
+-------------------+     +-------------------+    +-------------------+
| 핸드셰이크 2-RTT  |     | 핸드셰이크 1-RTT  |    | 0-RTT             |
|                   |     |                   |    | 첫 메시지에       |
| 그다음 데이터     |     | 그다음 데이터     |    | 데이터를 같이     |
+-------------------+     +-------------------+    +-------------------+
```

**② 취약 암호 제거.**\
RSA 키 교환·정적 DH·RC4·SHA-1·CBC 모드 등 약점이 알려진 옛 알고리즘을 통째로 들어냈다.\
키 교환은 **순방향 비밀성(forward secrecy)** 을 보장하는 ephemeral Diffie-Hellman만 남겼다.

**③ HTTP/3와의 관계.**\
HTTP/3가 의무적으로 쓰는 보안 계층이 바로 이 TLS 1.3이다(QUIC에 내장).

> **[보충] 순방향 비밀성(forward secrecy)** — 나중에 서버의 장기 키가 털려도, 과거에 오간 통신은 여전히 풀 수 없다는 성질. 원문은 이 용어를 쓰되 정의하지는 않는다.\
> 예: 매번 다른 일회용 열쇠로 잠그면, 금고 주인의 마스터키가 털려도 지난 상자들은 열리지 않는다.

> **[보충] AEAD** — 암호화와 위변조 검증을 한 번에 처리하는 암호 모드. TLS 1.2가 도입했다. 원문은 이 용어를 쓰되 정의하지는 않는다.\
> 예: 봉인과 내용물 숨기기를 따로 하지 않고 한 동작으로 끝내는 포장 방식이다.

### TLS 1.0/1.1 폐기와 HSTS

**폐기(deprecation).**\
2021년 3월 IETF는 **RFC 8996**으로 TLS 1.0·1.1을 공식 폐기했다.\
오늘날 권장 하한은 TLS 1.2이며, 1.2도 강력한 AEAD 암호군에 한해 fallback으로만 허용한다.

**HSTS(HTTP Strict Transport Security).**\
서버가 `Strict-Transport-Security` 응답 헤더로 "이 사이트는 앞으로 무조건 HTTPS로만 접속하라"고 브라우저에 지시한다.

이후 방문부터 브라우저는 평문 HTTP 요청을 **아예 보내지 않고** HTTPS로 직행한다.\
최초 접속을 가로채 평문으로 강등시키는 **SSL 스트리핑** 공격을 막는 장치다.

```text
응답 헤더:
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
  └ 2년간 이 도메인(및 서브도메인)은 HTTPS로만 접속하라는 지시
```

```text
HSTS 없이                              HSTS 지시를 받은 뒤
+-----------------------------+       +-----------------------------+
| 브라우저 -> 평문 HTTP 요청  |       | 브라우저는 평문 HTTP 요청을 |
|                             |       | 아예 보내지 않고 HTTPS 로   |
|                             |       | 직행한다                    |
| 그 사이를 가로채면          |       | 가로챌 평문 요청 자체가     |
| 평문으로 강등시킬 수 있다   |       | 존재하지 않는다             |
+-----------------------------+       +-----------------------------+
  SSL 스트리핑 공격이 성립한다          그 공격 경로가 닫힌다
```

> **HSTS(HTTP Strict Transport Security)** — 서버가 브라우저에게 "앞으로 이 사이트는 HTTPS로만 접속하라"고 지시하는 응답 헤더.\
> 예: 한 번 안내를 받아 두면, 다음부터는 주소창에 `http://`를 쳐도 브라우저가 알아서 HTTPS로 간다.

> **SSL 스트리핑(SSL stripping)** — 최초의 평문 접속을 가로채 HTTPS로 못 올라가게 막고 평문으로 붙잡아 두는 공격.\
> 예: 봉투에 넣으려던 편지를 중간에서 가로채 엽서인 채로 계속 주고받게 만드는 셈이다.

## 정리 — 진화를 관통하는 한 가지 원리

*(이 편의 「왜 그렇게 갔나」에 해당한다)*

HTTP의 30여 년은 **"의미론은 보존하고 전송을 개선한다"** 는 한 줄로 요약된다.

**무엇을 말하는가**(메서드·상태코드·헤더의 의미)는 1.0에서 잡힌 뒤 거의 그대로다.\
RFC 9110이 이 버전 공통 의미론을 한곳에 모은 것은 그래서다.

**어떻게 실어 나르는가**는 병목이 드러날 때마다 다시 쓰였다.

- 1.0 → 1.1: 요청마다 TCP를 새로 여는 비용을 keep-alive로 제거, `Host`로 가상호스팅 개방.
- 1.1 → 2: 순서 강제(애플리케이션 HOL)를 멀티플렉싱으로 제거.
- 2 → 3: 멀티플렉싱이 다시 막히던 TCP 계층 HOL을, 전송을 QUIC(UDP)로 갈아끼워 제거.

그 아래에서 **보안 계층(TLS)** 도 SSL의 결함을 걷어내며 1.3에서 "더 빠르고 더 안전하게"로 수렴했고, HTTP/3는 그 TLS 1.3을 전송 안에 녹여 넣었다.

```text
바뀌지 않은 층과 바뀐 층
+-----------------------------------------------------------+
| 의미론 (메서드, 상태코드, 헤더의 뜻)                      |
|   1.0 에서 잡힌 뒤 거의 그대로. RFC 9110 이 모았다        |
+-----------------------------------------------------------+
| 전송 (어떻게 실어 나르는가)                               |
|   1.1 연결 재사용 -> 2 멀티플렉싱 -> 3 QUIC               |
+-----------------------------------------------------------+
| 보안 (TLS)                                                |
|   SSL 3.0 -> TLS 1.0 ... 1.2 -> 1.3 (QUIC 안에 내장)      |
+-----------------------------------------------------------+
```

각 버전을 **"이전 것의 무엇이 아팠나"**로 읽으면, HTTP의 진화는 끊김 없는 하나의 이야기로 이어진다.

### 대가는 무엇인가

원문이 대가·실패를 직접 적은 대목은 세 곳이다.

- **파이프라이닝** — 이론상 지연을 줄이지만 응답 순서 강제라는 한계로 **사실상 실패**했고, 어떤 주요 브라우저도 기본 활성화하지 않았다.
- **도메인당 여러 연결(보통 6개)** — HOL 블로킹의 현실적 우회책이었지만, **연결 수 제한·혼잡 제어 비효율**이라는 새 비용을 낳았다.
- **서버 푸시** — 캐시된 자원까지 중복 전송하는 비효율이 드러나 실전 활용이 제한적이었고, **이후 브라우저들이 지원을 거두었다.**

## 남긴 것 — 오늘 우리가 쓰는 것

- **HTTP/1.1은 지금도 가장 널리 호환되는 버전**이다.
- **HTTP/1.1·2의 최신 정본은 각각 RFC 9112·9113**이고, 버전 공통 의미론은 **RFC 9110**에 모여 있다.
- 오늘날 **권장 하한은 TLS 1.2**이고, HTTP/3가 의무로 쓰는 것은 **TLS 1.3**이다.
- 멀티플렉싱 덕분에 1.1 시대의 우회책(도메인 샤딩, 도메인당 다중 연결)은 필요가 없어졌다.

## 용어 풀이

- **프로토콜(protocol)** — 두 프로그램이 통신하려고 미리 정해 둔 절차와 형식.
- **TCP** — 순서와 도착을 보장하는 전송 프로토콜. HTTP/0.9~2가 그 위에서 동작한다.
- **UDP** — 순서·신뢰성을 보장하지 않는 단순 전송. QUIC가 그 위에 얹혔다.
- **3-way handshake** — TCP 연결을 열 때 주고받는 세 번의 인사.
- **RTT(Round-Trip Time)** — 한 번 왕복하는 데 걸리는 시간.
- **메서드(method)** — 요청이 무엇을 하려는지 나타내는 동사(`GET`·`HEAD`·`POST`·`OPTIONS`·`PUT`·`DELETE`).
- **헤더(header)** — 본문 앞에 붙는 "이름: 값" 형식의 설명 줄.
- **상태 코드(status code)** — 요청 결과를 숫자로 알리는 값(`200 OK`, `404 Not Found`).
- **`Content-Type`** — 본문이 무슨 형식인지 알리는 헤더.
- **메타데이터(metadata)** — 내용물 자체가 아니라 그 내용물을 설명하는 정보.
- **정보성(informational) RFC** — 강제 규격이 아니라 통용되던 관행을 기록한 문서. RFC 1945가 그렇다.
- **keep-alive(지속 연결)** — 응답 후에도 TCP 연결을 닫지 않고 재사용하는 것. HTTP/1.1의 기본값.
- **`Host` 헤더** — 요청의 목적지 도메인을 담는 헤더. HTTP/1.1에서 필수가 됐다.
- **가상호스팅(virtual hosting)** — IP 하나로 여러 도메인의 사이트를 서비스하는 것.
- **청크 전송 인코딩(`Transfer-Encoding: chunked`)** — 전체 크기를 모를 때 본문을 조각내어 스트리밍하는 방식.
- **파이프라이닝(pipelining)** — 응답을 기다리지 않고 여러 요청을 연속으로 보내는 기능. 사실상 실패했다.
- **HOL(Head-of-Line) 블로킹** — 줄의 맨 앞이 막히면 뒤가 전부 대기하는 현상.
- **SPDY** — 구글이 2009년 발표한 실험 프로토콜. HTTP/2의 뿌리다.
- **바이너리 프레이밍(binary framing)** — 메시지를 기계가 읽기 쉬운 이진 프레임으로 쪼개는 것.
- **프레임(frame) / 스트림(stream)** — 메시지를 쪼갠 조각 / 그 조각들이 속한 논리적 채널.
- **멀티플렉싱(multiplexing)** — 한 연결에 여러 요청·응답을 섞어 동시에 흘리는 것.
- **HPACK(RFC 7541)** — HTTP/2의 헤더 압축. 정적 테이블·동적 테이블·허프만 인코딩.
- **허프만 인코딩(Huffman encoding)** — 자주 나오는 글자에 짧은 부호를 주어 전체 길이를 줄이는 방법.
- **서버 푸시** — 요청 전에 서버가 필요할 자원을 미리 보내는 기능. 이후 브라우저들이 지원을 거두었다.
- **QUIC(RFC 9000)** — UDP 위에 스트림 인식·신뢰성·혼잡 제어·암호화를 구현한 전송 프로토콜.
- **혼잡 제어(congestion control)** — 네트워크가 막히지 않도록 전송 속도를 조절하는 장치.
- **0-RTT / 1-RTT** — 데이터를 보내기까지 필요한 왕복 횟수.
- **연결 ID / 연결 마이그레이션** — QUIC가 연결을 식별하는 값 / IP가 바뀌어도 연결을 이어 가는 기능.
- **QPACK(RFC 9204)** — HTTP/3의 헤더 압축. 헤더 도착 순서에 의존하지 않는다.
- **시맨틱(semantics, 의미론)** — 메서드·상태코드·헤더의 뜻. RFC 9110이 한곳에 모았다.
- **TLS(Transport Layer Security)** — 기밀성·무결성·서버 인증을 담당하는 계층.
- **HTTPS** — HTTP over TLS.
- **순방향 비밀성(forward secrecy)** — 장기 키가 유출돼도 과거 통신은 풀리지 않는 성질.
- **ephemeral Diffie-Hellman** — 매번 새 값을 쓰는 키 교환 방식. TLS 1.3이 유일하게 남긴 키 교환이다.
- **AEAD** — 암호화와 위변조 검증을 한 번에 처리하는 암호 모드.
- **HSTS** — "앞으로 HTTPS로만 접속하라"를 브라우저에 지시하는 응답 헤더.
- **SSL 스트리핑** — 최초 평문 접속을 가로채 HTTPS로 못 가게 막는 공격.
