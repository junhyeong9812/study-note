# HTML·CSS의 진화

> 원본: `~/project/web-history/03-HTML-CSS-진화.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-18).\
> 연도·인명·논문명·표준번호·코드·표는 원문 그대로다.\
> ASCII 도식 18개와 「한눈에」의 비유, 용어 블록의 「예:」, 「용어 풀이」는 원문에 없는 보충이다.

## 한눈에 — 쉽게 말하면

> 문서를 기술하던 마크업 언어가 어떻게 애플리케이션 플랫폼의 구조 언어가 되었는가 — 그리고 표현(presentation)이 어떻게 HTML에서 떨어져 나와 CSS라는 독립된 레이어로 성숙했는가. 각 변화가 **언제·왜** 일어났는지를 따라간다.

**HTML·CSS의 역사는 한 문장이다 — "구조(structure)와 표현(presentation)의 분리".**

- 책 원고를 떠올려 보자.\
  원고에는 "여기는 제목, 여기는 인용"이라고만 적고, 글씨 크기·색·여백은 조판하는 사람에게 맡긴다.
- 초기 HTML은 그 원칙을 지켰다.\
  무엇이 제목이고 무엇이 문단인지만 적고, 어떻게 보일지는 브라우저에 맡겼다.
- 그런데 디자이너가 화면을 통제하고 싶어지자, **원고지에 조판 지시를 직접 적기 시작했다.**\
  `<font>`, `<center>`, `<table>` 같은 태그가 그것이다.
- 그 결과 마크업은 의미를 잃고 **시각 효과를 흉내 내는 도구로 전락했다.**
- 이 혼탁함을 걷어내는 **30년의 싸움**이 이 문서의 줄거리다.

```text
표현이 섞인 마크업                     구조와 표현이 갈라진 뒤
+-----------------------------+       +-----------------------------+
| HTML                        |       | HTML                        |
|   <font color=...>          |       |   <h1>제목</h1>             |
|   <center>                  |       |   (무엇인가만 적는다)       |
|   <table> 로 화면 쪼개기    |       +-----------------------------+
|   제목인지 장식인지 모른다  |       | CSS                         |
+-----------------------------+       |   h1 { color: navy; }       |
  디자인을 바꾸려면 마크업을            |   (어떻게 보일지만 적는다)  |
  전부 다시 손대야 한다                 +-----------------------------+
                                         한쪽만 바꿔도 다른 쪽은 그대로
```

왼쪽에서는 디자인 변경이 곧 원고 수정이고, 오른쪽에서는 조판 지시서만 갈아 끼우면 된다.\
이 차이를 **눈으로 증명한 사건**이 뒤에 나오는 CSS Zen Garden(2003)이다.

> **마크업(markup)** — 글의 어느 부분이 무슨 역할인지를 표시해 두는 것.\
> 예: 원고에 빨간 펜으로 "여기는 제목", "여기는 각주"라고 표시하는 것이 마크업이다.

> **구조(structure) / 표현(presentation)** — "이것이 무엇인가" / "이것이 어떻게 보이는가".\
> 예: "제목이다"는 구조, "24pt 남색 굵게"는 표현이다.

## 큰 그림: 두 개의 레이어가 갈라서는 역사

*(이 편의 「시대 배경」에 해당한다)*

원문의 시대 구분표를 그대로 옮긴 것이다.

| 시기 | HTML 축 | CSS 축 | 시대정신 |
|------|---------|--------|----------|
| 1991~1994 | HTML 태그 셋 (비공식) | (없음) | 문서 공유 |
| 1995~1999 | HTML 2.0 → 3.2 → 4.01 | CSS1(1996) → CSS2(1998) | 표현 분리의 *선언* |
| 2000~2008 | XHTML 1.0/1.1 (엄격함의 실험) | CSS2.1 정비 | XML 정통주의 vs 현실 |
| 2004~2014 | WHATWG 반란 → HTML5 | CSS3 모듈화 시작 | 웹 애플리케이션 |
| 2010~2017 | HTML Living Standard | 반응형·Flexbox·Grid | 멀티 디바이스 |
| 2017~현재 | WHATWG 단일 표준(2019 합의) | 커스텀 속성·컨테이너 쿼리 | 컴포넌트·디자인 시스템 |

## 1부. HTML의 진화

먼저 HTML 쪽 30년을 한 장에 놓는다.

```text
[연대순 구분선 — 아래 항목들은 일어난 순서다]

1991~1994   HTML 에는 버전이 없었다 (약 18개 태그, SGML 의 한 응용)
----------
1995.11     HTML 2.0  (IETF, RFC 1866) — 첫 공식 표준
----------
1997.01     HTML 3.2  (W3C 권고안) — 표현용 태그를 대거 공식화
1997.12     HTML 4.0  / 1999.12  HTML 4.01 — "구조와 표현을 분리하라"
----------
2000.01     XHTML 1.0 (W3C 권고안) / 2001  XHTML 1.1
----------
2004.06     WHATWG 결성, "Web Applications 1.0" 명세 작업 시작
----------
2007        W3C 가 WHATWG 의 작업을 다시 받아들인다 (이후 양측이 함께 다듬는다)
----------
2009        W3C, XHTML 2.0 워킹그룹 종료 (발표 7월 2일)
----------
2014.10.28  HTML5  (W3C 권고안)
----------
2019.05     W3C · WHATWG 양해각서(MOU) — HTML Living Standard 단일 표준

[원문이 인과를 밝힌 연결만 화살표로 잇는다]

XHTML 2.0 워킹그룹 종료 --(원문: "역량은 HTML5로 옮겨갔다")--> HTML5
XHTML 좌초의 교훈 "웹은 관용적이어야 한다" --(원문: "HTML5 설계 철학의 뿌리")--> HTML5
WHATWG "Web Applications 1.0" --(원문: "곧 HTML5의 모태")--> HTML5
```

그림 해설 (한 단계씩):

- 세로 목록은 **화살표가 아니라 연대순 구분선**이다 — HTML 3.2에서 4.0이 "갈라져 나온" 식의 관계가 아니라 같은 표준이 판을 갈아 온 순서다.
- 아래 세 화살표는 **원문이 인과를 직접 적은 것만** 옮겼다. 화살표 위의 괄호가 그 근거 문구다.
- 세 화살표가 모두 HTML5로 모이는 것이 이 그림의 요점이다 — HTML5는 **XHTML의 실패와 WHATWG의 작업이 함께 흘러든 지점**이다.

### 1.1 태초: HTML에는 버전이 없었다 (1991~1994)

팀 버너스리(Tim Berners-Lee)가 1991년경 CERN에서 만든 최초의 HTML은 **공식 명세 없이 약 18개의 태그**로 시작했다.

SGML(Standard Generalized Markup Language)의 한 응용으로 설계됐고, 목적은 단 하나 — **연구 문서를 하이퍼링크로 연결**하는 것이었다.

표현은 전적으로 브라우저(당시엔 주로 텍스트 단말)에게 맡겨졌다.

이 **"구조만 적고 표현은 위임한다"는 원형(原型)**이 훗날 CSS가 복원하려는 이상이 된다.

> **SGML(Standard Generalized Markup Language)** — 문서에 표시를 다는 방법 자체를 규정한 상위 규격. HTML은 그 한 응용으로 설계됐다.\
> 예: SGML이 "표시를 다는 문법의 문법"이라면, HTML은 그 문법으로 만든 구체적인 표시 목록이다.

### 1.2 HTML 2.0 — 첫 표준화 (RFC 1866, 1995년 11월)

웹이 폭발적으로 퍼지면서 브라우저마다 제멋대로 태그를 추가하던 혼란을 잠재울 *합의된 기준*이 필요해졌다.

IETF(Internet Engineering Task Force)가 그때까지 실제로 쓰이던 관행을 모아 **RFC 1866 "HTML 2.0"**으로 표준화했다.

폼(`<form>`, `<input>`), 이미지(`<img>`) 등 오늘날에도 쓰는 기본기가 여기서 공식화됐다.

> **왜 2.0인가?** "1.0"은 정식 명세 없이 통용되던 초기 HTML을 사후적으로 가리키는 이름이었기 때문에, 첫 *공식* 표준이 2.0으로 출발했다.

### 1.3 HTML 3.2 → 4.01 — 표현 태그의 전성기, 그리고 후회 (1997~1999)

웹 표준 주도권이 IETF에서 **W3C(World Wide Web Consortium)**로 넘어갔다.

넷스케이프와 인터넷 익스플로러의 "브라우저 전쟁"이 한창이던 시기라, 두 진영이 경쟁적으로 도입한 비표준 태그를 **표준이 뒤따라가며 흡수하는 형국**이었다.

**HTML 3.2 (1997년 1월, W3C 권고안)** — `<font>`, `<center>`, `align` 속성 등 **표현용 태그를 대거 공식화**했다.

왜 그랬나. 원문의 답은 두 가지다.

- 디자이너가 시각 통제권을 원했다.
- CSS는 아직 브라우저 지원이 빈약했다.

역설적으로 **이때가 HTML이 "의미"에서 가장 멀어진 시점**이다.

**HTML 4.0 (1997년 12월) / 4.01 (1999년 12월)** — 방향을 180도 틀었다.

- **"구조와 표현을 분리하라"**는 철학을 명문으로 내세웠다.
- 표현용 태그·속성을 **deprecated(권장 폐기)**로 강등했다.
- 스타일링은 CSS로 넘기라고 권고했다.
- 동시에 접근성·국제화·테이블·프레임·스크립트를 정비했다.

```text
HTML 3.2 (1997.01)                    HTML 4.0 (1997.12)
+-----------------------------+       +-----------------------------+
| 표현용 태그를 표준에 넣는다 |       | 같은 태그를 deprecated 로   |
|   <font>                    |       | 강등한다                    |
|   <center>                  |       |                             |
|   align 속성                |       | 스타일링은 CSS 로 넘기라고  |
|                             |       | 권고한다                    |
+-----------------------------+       +-----------------------------+
  1997년 1월에 표준에 넣은 태그를 같은 해 12월에 권장 폐기로 강등했다
```

> **deprecated(권장 폐기)** — "아직 동작은 하지만 앞으로는 쓰지 말라"고 표시된 상태.\
> 예: 당장 지우면 기존 페이지가 깨지므로, 금지 대신 "쓰지 말 것" 딱지를 붙여 둔다.

> **권고안(Recommendation)** — W3C가 논의를 마치고 "이것을 표준으로 쓰라"고 확정해 내놓는 문서 등급.\
> 예: 권고안이 되면 사실상 확정된 규격이다. **[보충]** — 그 앞 단계(초안·후보)까지의 W3C 절차는 원문 밖의 세부다.

HTML 4.01은 세 가지 **DTD(문서 형식 정의)**를 제공해 전환기의 현실을 절충했다.

```html
<!-- Strict: 표현 태그 금지, 순수 구조 + CSS만 (이상향) -->
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN"
    "http://www.w3.org/TR/html4/strict.dtd">

<!-- Transitional: 레거시 표현 태그 허용 (현실적 과도기) -->
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01 Transitional//EN"
    "http://www.w3.org/TR/html4/loose.dtd">

<!-- Frameset: <frameset> 기반 레이아웃용 -->
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01 Frameset//EN"
    "http://www.w3.org/TR/html4/frameset.dtd">
```

세 줄짜리 선언이 뜻하는 것은 하나다 — **"당신은 이 셋 중 어느 세계에서 쓸 것인가"**를 문서 첫 줄에 밝히라는 것이다.

> **DTD(문서 형식 정의)** — 이 문서가 어떤 태그를 어떤 규칙으로 쓸 수 있는지를 적어 둔 정의.\
> 예: 문서 맨 위의 `<!DOCTYPE ...>` 한 줄이 "나는 이 규칙집을 따른다"는 선언이다.

> **언제·왜:** HTML 4.0의 "표현 분리" 선언(1997)이 CSS가 살아남을 명분을 제도적으로 확보해 준 결정적 분기점이다. 다만 *선언*은 했어도 브라우저 CSS 구현이 부실해, 실제 분리는 2000년대 중반 웹 표준 운동(3부)을 기다려야 했다.

### 1.4 XHTML — 엄격함이라는 이상, 그리고 좌초 (2000~2009)

2000년대 초(XHTML 1.0은 2000년 1월), W3C는 웹의 미래가 **XML**에 있다고 봤다.

XML의 장점은 명확했다.

- 엄격한 문법 규칙(태그를 반드시 닫고, 소문자로 쓰고, 속성값에 따옴표를 강제)을 가져 **기계가 파싱하기 쉽다.**
- 다른 XML 도구 생태계(XSLT, XPath 등)와 통합된다.

HTML을 XML 문법으로 재정의한 것이 **XHTML**이다.

- **XHTML 1.0 (2000년 1월, W3C 권고안)**: HTML 4.01을 XML 문법으로 다시 쓴 것. 내용은 같되 규칙이 엄격해졌다.
- **XHTML 1.1 (2001)**: 모듈화하며 더 순수한 XML로.

```html
<!-- XHTML 1.0 Strict: XML 규칙 강제 -->
<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Strict//EN"
    "http://www.w3.org/TR/xhtml1/DTD/xhtml1-strict.dtd">
<html xmlns="http://www.w3.org/1999/xhtml" xml:lang="ko">
  <head><title>예시</title></head>
  <body>
    <p>모든 태그는 닫혀야 한다.<br />빈 요소도 <img src="a.png" alt="a" /> 처럼 self-close.</p>
  </body>
</html>
```

> **XML(eXtensible Markup Language)** — 태그로 데이터를 적되 문법을 엄격히 강제하는 범용 형식.\
> 예: HTML이 "대충 써도 봐준다"면, XML은 쉼표 하나만 틀려도 안 받아 주는 서식이다.

#### 좌초의 핵심: "엄격함의 실패"

XHTML이 진짜 XML로 제공되려면(`application/xhtml+xml` MIME 타입) **draconian error handling(가차 없는 오류 처리)** 규칙을 따라야 했다.

XML 파서는 문법 오류가 **단 하나라도** 있으면 페이지 렌더링을 *전면 중단*하고 오류 화면을 띄운다 — 이른바 **"노란 죽음의 화면(Yellow Screen of Death)"**.

HTML이 깨진 마크업도 너그럽게 복구해 보여주던 것(tag soup 관용)과 정반대다.

```text
같은 문서에 태그 하나가 안 닫혀 있을 때

  HTML 파서 (관용)                     XML 파서 (draconian)
  +---------------------------+        +---------------------------+
  | 깨진 부분을 복구해서      |        | 렌더링을 전면 중단한다    |
  | 어떻게든 화면에 그린다    |        | 오류 화면을 띄운다        |
  |                           |        | ("노란 죽음의 화면")      |
  +---------------------------+        +---------------------------+
    독자는 문제를 눈치채지 못한다        독자는 아무것도 볼 수 없다
```

**현실은 어느 쪽이었나.**\
현실의 웹은 사람이 손으로 짜고, 광고·CMS·댓글이 동적으로 끼어드는 곳이라 *완벽한 문법*은 환상에 가까웠다.

그래서 거의 모든 사이트가 XHTML 문법으로 작성해 놓고도 실제로는 관대한 `text/html`로 서빙했다.

```text
XHTML 을 쓴 사이트가 실제로 한 일

  마크업        XHTML 문법으로 정성껏 작성한다
                  |
                  v
  서빙          MIME 타입은 관대한 text/html 로 보낸다
                  |
                  v
  브라우저      HTML 파서로 읽는다 (관용적으로 복구)
                  |
                  v
  결과          이름만 XHTML, 동작은 HTML
                엄격함의 이득은 못 누리고 형식의 번거로움만 떠안았다
```

> **MIME 타입** — 이 내용물이 무슨 형식인지 알리는 표시. `text/html` 과 `application/xhtml+xml` 은 브라우저가 쓰는 파서를 바꾼다.\
> 예: 같은 파일이라도 겉면에 붙은 딱지에 따라 읽는 방식이 달라진다.

> **tag soup(태그 수프)** — 문법이 엉망인 마크업. HTML 파서는 이것도 어떻게든 복구해 보여 준다.\
> 예: 닫는 태그가 빠져 있어도 브라우저가 알아서 메워 화면을 그려 준다.

**여기에 더해, W3C는 한 발 더 나아갔다.**\
**XHTML 2.0**을 추진했는데, 이는 **하위 호환을 포기**하는 급진적 설계였다(`<img>` 대신 임의 요소에 `src`, 새로운 폼 모델 등 기존 웹과 단절).

개발자·브라우저 벤더의 반발이 컸다.

> **하위 호환(backward compatibility)** — 새 규격을 따르더라도 예전에 만들어진 것이 계속 동작하는 성질.\
> 예: 20년 전 만든 페이지가 오늘 브라우저에서도 열리는 것이 하위 호환이다.

> **결말:** W3C는 **2009년**(발표 7월 2일) XHTML 2.0 워킹그룹의 헌장을 갱신하지 않고 연말에 종료시켰다 — 사실상의 사망 선고였고, 역량은 HTML5로 옮겨갔다. "엄격하고 순수한 XML 웹"이라는 이상은, 깨진 문서도 어떻게든 보여줘야 하는 웹의 본성 앞에서 좌초했다. 이 실패의 교훈 — **"웹은 관용적이어야 한다"** — 이 HTML5 설계 철학의 뿌리가 된다.

### 1.5 WHATWG의 반란 (2004)

W3C가 XHTML 2.0에 몰두하던 2004년, 브라우저를 만드는 쪽에서 반대 방향의 제안이 나왔다.

```text
2004년에 일어난 일 (원문이 밝힌 순서 그대로)

  2004년 6월   모질라와 오페라가 W3C 워크숍에 포지션 페이퍼를 낸다
               내용 : "하위 호환을 지키며 실용적 HTML을 계속 발전시키자"
                  |
                  v
               표결에서 부결됐다
                  |
                  v
  사흘 뒤      애플까지 합류해 독립 단체 WHATWG 를 결성한다
               (Web Hypertext Application Technology Working Group)
                  |
                  v
               "Web Applications 1.0" 명세 작업을 시작한다
                  |
                  v
               이것이 곧 HTML5 의 모태다
```

> **왜 반란인가:** W3C가 "문서로서의 웹(XHTML 2.0)"을 좇는 동안, 브라우저 벤더들은 이미 웹이 **애플리케이션 플랫폼**으로 가고 있음을 봤다. 폼·드래그앤드롭·오프라인·멀티미디어 같은 *앱에 필요한* 기능을, 하위 호환을 지키며, 깨진 마크업도 일관되게 파싱하도록 — 현실에서 출발하는 표준이 필요했다.

두 진영이 무엇을 다르게 봤는지 나란히 놓으면 이렇다.

```text
W3C 의 XHTML 2.0 이 보던 웹            브라우저 벤더가 보던 웹
+-----------------------------+       +-----------------------------+
| 문서로서의 웹               |       | 애플리케이션 플랫폼         |
| XHTML 2.0                   |       | 폼, 드래그앤드롭            |
| 엄격한 XML 문법             |       | 오프라인, 멀티미디어        |
| 하위 호환을 포기한다        |       | 하위 호환을 지킨다          |
+-----------------------------+       +-----------------------------+
  이상에서 출발한다                     현실에서 출발한다
```

### 1.6 HTML5 — 웹이 애플리케이션 플랫폼이 되다 (2014년 10월 28일)

WHATWG의 작업을 W3C가 2007년 다시 받아들여 양측이 (불편한 동거 속에) 함께 다듬은 결과가 **HTML5**다.

**2014년 10월 28일 W3C 권고안(Recommendation)**으로 확정됐다.

HTML5는 세 갈래로 웹을 바꿨다.

#### (1) 시맨틱(semantic) 요소 — 의미를 가진 구조

`<div class="header">`처럼 의미 없는 박스에 클래스로 역할을 붙이던 관행을, **역할 자체를 가진 태그**로 대체했다.

검색엔진·스크린리더·개발자 모두가 문서 구조를 이해할 수 있게 됐다.

```html
<!-- Before (HTML4): div 수프 — 의미는 class 이름에만 있음 -->
<div id="header">...</div>
<div id="nav">...</div>
<div class="article">
  <div class="section">...</div>
</div>
<div id="footer">...</div>

<!-- After (HTML5): 태그 자체가 의미를 가짐 -->
<header>...</header>
<nav>...</nav>
<article>
  <section>...</section>
</article>
<aside>...</aside>
<footer>...</footer>
```

차이가 어디에 있는지를 그림으로 보면 이렇다.

```text
div 수프                               시맨틱 요소
+-----------------------------+       +-----------------------------+
| 태그  : 전부 div            |       | 태그  : header, nav,        |
| 의미  : class 이름에만 있다 |       |         article, footer     |
|                             |       | 의미  : 태그 자체에 있다    |
| class 이름은 약속이 아니다  |       | 기계도 구조를 그대로        |
| 기계가 의지할 수 없다       |       | 읽을 수 있다                |
+-----------------------------+       +-----------------------------+
  사람만 읽을 수 있는 의미              기계도 읽을 수 있는 의미
```

> **시맨틱(semantic) 요소** — 태그 이름 자체가 역할을 뜻하는 HTML 요소.\
> 예: `<nav>` 는 "이 안은 내비게이션이다"를 태그 이름만으로 알린다 — `<div class="nav">` 는 그렇지 않다.

> **스크린리더(screen reader)** — 화면의 내용을 소리로 읽어 주는 보조 기술.\
> 예: 눈으로 볼 수 없는 사용자가 웹을 쓰는 통로이며, 태그의 의미를 근거로 구조를 읽어 준다.

#### (2) 멀티미디어 — 플러그인 없는 네이티브 미디어

그전까지 동영상·인터랙티브 그래픽은 **Adobe Flash** 같은 플러그인에 의존했다(보안·성능·모바일 비호환 문제의 온상).

HTML5는 이를 브라우저 기본 기능으로 끌어들였다.

```html
<!-- 네이티브 비디오/오디오: <object>+Flash 대체 -->
<video controls width="640" poster="thumb.jpg">
  <source src="movie.webm" type="video/webm">
  <source src="movie.mp4" type="video/mp4">
  자막: <track src="subs.vtt" kind="subtitles" srclang="ko">
</video>

<!-- canvas: 스크립트로 그리는 2D/3D 그래픽 -->
<canvas id="c" width="300" height="150"></canvas>
<script>
  const ctx = document.getElementById('c').getContext('2d');
  ctx.fillStyle = '#36c'; ctx.fillRect(10, 10, 120, 80);
</script>
```

> **플러그인(plugin)** — 브라우저에 따로 설치해서 기능을 덧붙이는 외부 프로그램.\
> 예: Flash Player가 깔려 있어야만 동영상이 보이던 시절이 그 상태다.

#### (3) 폼 강화와 자바스크립트 API — 앱의 토대

```html
<!-- 새로운 input 타입: 브라우저 기본 검증·UI 제공 -->
<input type="email"    required placeholder="you@example.com">
<input type="date">
<input type="range" min="0" max="100">
<input type="color">
<input type="search" list="suggestions">
```

여기에 명세 군(群)으로 따라온 자바스크립트 API들이 웹을 데스크톱 앱에 견줄 플랫폼으로 만들었다.

- **localStorage/sessionStorage** — 클라이언트 저장
- **Geolocation** — 위치
- **Web Workers** — 백그라운드 스레드
- **WebSocket**
- **History API** — SPA 라우팅
- **드래그앤드롭**

> **localStorage / sessionStorage** — 브라우저 안에 값을 저장해 두는 자리. 서버에 보내지 않고도 상태를 기억한다.\
> 예: 로그인 상태나 장바구니를 새로고침해도 유지하는 데 쓴다.

> **Web Workers** — 화면을 멈추지 않고 뒤에서 따로 계산을 돌리는 백그라운드 스레드.\
> 예: 무거운 계산을 워커에 맡기면 그동안에도 화면이 버벅이지 않는다.

> **History API · SPA** — 페이지를 새로 받지 않고 주소만 바꿔 화면을 갈아 끼우는 방식과, 그렇게 만든 단일 페이지 앱.\
> 예: 앱처럼 화면이 부드럽게 바뀌지만 주소창과 뒤로가기는 그대로 동작한다.

#### WHATWG vs W3C, 그리고 화해 (Living Standard, 2019 합의)

HTML5를 함께 만들면서도 두 단체의 철학은 끝내 달랐다.

```text
W3C 방식                               WHATWG 방식
+-----------------------------+       +-----------------------------+
| 특정 시점에 명세를 동결한다 |       | 버전 번호를 버린다          |
| "HTML5", "HTML 5.1" 처럼    |       | HTML Living Standard        |
| 버전 스냅샷(Recommendation) |       | 끊임없이 갱신되는 단일 문서 |
|                             |       |                             |
| 안정성, 인용 가능성 중시    |       | 브라우저가 실제 구현하는    |
|                             |       | 것이 곧 표준                |
+-----------------------------+       +-----------------------------+
  같은 HTML 을 두고 서로 다른 두 문서가 나오는 분열이 수년간 이어졌다
```

두 단체가 같은 HTML을 두고 *서로 다른 두 문서*를 내는 분열이 수년간 이어지다, **2019년 5월 양측이 양해각서(MOU)를 체결**해 종지부를 찍었다.

합의 내용은 명확하다 — **HTML과 DOM은 WHATWG의 Living Standard 하나를 단일 표준으로 삼고**, W3C는 별도 버전을 내지 않고 이를 검토·승인한다.

오늘날 "HTML 명세"는 사실상 [html.spec.whatwg.org](https://html.spec.whatwg.org) 한 곳이며, **버전 번호 없는 HTML**의 시대가 됐다.

> **Living Standard(살아있는 표준)** — 버전을 끊어 동결하지 않고 계속 갱신되는 단일 명세 문서.\
> 예: 판을 찍어 내는 책이 아니라, 늘 최신으로 고쳐지는 위키 문서에 가깝다.

> **양해각서(MOU)** — 두 조직이 앞으로 이렇게 하겠다고 서면으로 합의한 문서.\
> 예: 2019년 5월의 MOU가 "HTML 명세는 한 곳"이라는 오늘의 상태를 확정했다.

> **언제·왜:** HTML5의 본질은 "버전 5"가 아니라 **"웹을 문서에서 애플리케이션 플랫폼으로 재정의했다"**는 데 있다. 그리고 2019년 합의로 HTML은 *버저닝을 끝내고* 영구히 진화하는 living standard가 됐다 — XHTML의 "동결된 순수성"과 정반대의 결말이다.

## 2부. CSS의 진화

### 2.1 CSS의 탄생 — 표현을 마크업에서 떼어내다 (CSS1, 1996년 12월)

HTML에 `<font>` 같은 표현 태그가 범람하던 1994년, 오페라의 **호콘 비움 리(Håkon Wium Lie)**가 "Cascading Style Sheets"를 제안했다.

*cascading(종속)*이라는 이름은 여러 출처(작성자·사용자·브라우저 기본값)의 스타일이 **우선순위 규칙에 따라 폭포처럼 흘러 합쳐진다**는 핵심 아이디어를 담는다.

```text
"cascading" 이 뜻하는 것 — 여러 출처가 폭포처럼 흘러 합쳐진다

   스타일은 세 곳에서 온다 (원문이 든 세 출처를 나란히 둔다)

      [ 작성자 ]     [ 사용자 ]     [ 브라우저 기본값 ]
           |              |                  |
           +--------------+------------------+
                          |
                          v
        우선순위 규칙에 따라 폭포처럼 흘러 합쳐진다
                          |
                          v
        그 요소에 최종적으로 적용될 값 하나가 정해진다
```

그림 해설 (한 단계씩):

- 스타일은 **한 곳에서만 오지 않는다** — 브라우저·사용자·작성자 셋이 각자 말을 얹는다.
- 그래서 "누구 말이 이기는가"를 정하는 **우선순위 규칙**이 필요했고, 그 규칙이 곧 cascade다.
- 이름 자체가 이 구조를 가리킨다 — 폭포(cascade)처럼 위에서 아래로 흘러 합쳐진다.

**CSS1 (1996년 12월, W3C 권고안)**은 글꼴·색·여백·정렬 같은 기본 스타일링을 마크업 *바깥*에서 선언하는 길을 열었다.

비로소 HTML은 "무엇인가(구조)"를, CSS는 "어떻게 보이는가(표현)"를 맡는 분업이 가능해졌다.

```css
/* CSS1: 표현을 HTML 밖에서 선언 — <font> 태그의 종말 시작 */
h1 { color: navy; font-family: Georgia, serif; }
p  { line-height: 1.5; margin: 1em 0; }
```

> **캐스케이드(cascade, 종속)** — 여러 출처의 스타일이 우선순위 규칙에 따라 하나로 합쳐지는 방식.\
> 예: 같은 요소에 세 군데서 색을 지정해도, 규칙에 따라 최종 색 하나가 정해진다.

### 2.2 CSS2 / CSS2.1 — 레이아웃과 미디어의 등장 (1998, 2011)

**CSS2 (1998년 5월, 권고안)**는 단순 스타일링을 넘어 *레이아웃 도구*로 진화하기 시작했다.

- **포지셔닝**(`position: absolute/relative/fixed`)
- **z-index**
- **미디어 타입**(`print`/`screen` 구분)
- 생성 콘텐츠(`::before`/`::after`)

다만 브라우저 구현이 제각각이고 버그가 많아, W3C는 실제 구현에 맞춰 명세를 정리·수정한 **CSS2.1을 2011년 권고안**으로 확정했다(오류 수정·현실 반영 버전).

> **포지셔닝(positioning)** — 요소를 문서 흐름에서 떼어 원하는 위치에 놓는 기능.\
> 예: 화면 오른쪽 아래에 고정된 "위로" 버튼이 그 결과다.

> **z-index** — 겹친 요소 중 어느 것이 위에 보일지 정하는 값.\
> 예: 팝업이 본문 위에 뜨는 것은 z-index가 더 크기 때문이다.

> **시대적 한계:** CSS2 시대에도 *진짜 2차원 레이아웃* 도구는 없었다. 그래서 개발자들은 `<table>`로 화면을 격자처럼 쪼개 배치하는 **테이블 레이아웃**에 의존했다(3부). float·position을 레이아웃에 *전용(轉用)*하는 편법도 이때 굳어졌다 — Flexbox/Grid(2.5~2.6)가 나오기까지 10여 년을 기다려야 했다.

### 2.3 CSS3 — "버전"을 버리고 모듈로 쪼개다 (2000년대~)

CSS2.1 이후 **"CSS3"라는 단일 거대 명세는 존재하지 않는다**.

W3C CSS 워킹그룹은 전체를 한 번에 동결하던 방식을 버렸다.\
대신 **기능별 모듈(module)**로 쪼개 **각각 독립적으로 버전을 매기고 진화**시키는 방식으로 전환했다.

```text
CSS2 방식 — 하나의 문서                모듈 방식
+-----------------------------+       +-----------------------------+
| 셀렉터 (안정적)             |       | Selectors     Level 4       |
| 색                          |       | Color         Level 5       |
| 애니메이션 (실험적)         |       | 애니메이션    별도 진행     |
|                             |       |                             |
| 전체가 한 배를 탄다         |       | 각자 자기 속도로 성숙한다   |
+-----------------------------+       +-----------------------------+
  표준화가 가장 느린 기능에              안정된 기능이 실험적 기능을
  전체가 발목 잡힌다                     기다리지 않는다
```

> **왜 모듈화인가:** CSS2를 하나의 문서로 묶었더니, 셀렉터 같은 안정된 부분과 애니메이션 같은 실험적 부분이 *한 배를 타* 전체 표준화가 가장 느린 기능에 발목 잡혔다. 모듈로 쪼개면 **Selectors Level 4**, **Color Level 5**처럼 각 기능이 자기 속도로 성숙·출시될 수 있다. 그래서 "CSS3"는 엄밀히는 *모듈들의 Level 3 묶음을 부르는 마케팅 별칭*이고, 실제로는 모듈마다 레벨이 제각각이다(Selectors는 4, Color는 5…).

이 모듈화 덕분에 아래의 굵직한 기능들이 *연쇄적으로* 쏟아질 수 있었다.

> **모듈(module) · 레벨(level)** — 기능 단위로 쪼갠 명세와, 그 명세가 몇 번째 판인지 나타내는 번호.\
> 예: "Selectors Level 4"는 셀렉터 기능만 다루는 명세의 4번째 판이라는 뜻이다.

### 2.4 반응형 웹 — 미디어 쿼리 (2010~2012)

스마트폰(2007년 아이폰)이 등장하자 **"하나의 HTML이 데스크톱·태블릿·폰 모든 화면에 적응해야 한다"**는 요구가 생겼다.

2010년 **이선 마콧(Ethan Marcotte)**이 *A List Apart*에 글을 실어 **"Responsive Web Design(반응형 웹 디자인)"**이라는 용어와 방법론을 제시했다.

그 방법론은 세 가지의 결합이다 — 유동 그리드 + 유연한 이미지 + **미디어 쿼리**.

기술적 토대인 **CSS3 Media Queries는 2012년 6월 W3C 권고안**으로 *정식 표준화*됐다.

브라우저는 이미 그 몇 해 전부터 지원했기에 마콧이 2010년에 활용할 수 있었다 — 즉 **"2012년 도입"이 아니라 "2012년 표준 확정"**이다.

뷰포트 너비 등 *기기 특성*에 따라 다른 스타일을 적용한다.

```css
/* 모바일 우선(mobile-first): 기본은 좁은 화면 */
.container { display: block; padding: 1rem; }

/* 화면이 768px 이상이면 다단 레이아웃 */
@media (min-width: 768px) {
  .container { display: grid; grid-template-columns: 1fr 2fr; }
}
/* 인쇄 시 */
@media print { nav, .ads { display: none; } }
```

```text
같은 HTML 한 벌, 화면에 따라 다른 배치

  뷰포트 너비 < 768px                뷰포트 너비 >= 768px
  +-------------------+              +-----------------------------+
  | .container        |              | .container                  |
  |   display: block  |              |   display: grid             |
  |                   |              |   1fr        2fr            |
  |  [ 내용 ]         |              |  [ 좁은 칸 ][ 넓은 칸 ]     |
  |  [ 내용 ]         |              |                             |
  +-------------------+              +-----------------------------+
    세로로 쌓인다                      가로로 두 칸이 된다
```

> **뷰포트(viewport)** — 브라우저에서 페이지가 실제로 보이는 영역.\
> 예: 같은 페이지라도 폰에서는 뷰포트가 좁고, 데스크톱에서는 넓다.

> **미디어 쿼리(media query)** — 화면 너비 같은 기기 특성을 조건으로 걸어 다른 스타일을 적용하는 CSS 문법.\
> 예: `@media (min-width: 768px)` 는 "가로가 768px 이상일 때만 이 규칙을 써라"는 뜻이다.

> **모바일 우선(mobile-first)** — 좁은 화면을 기본으로 두고, 넓어질 때 규칙을 덧붙이는 작성 순서.\
> 예: 기본 스타일은 폰 기준으로 쓰고, 데스크톱용은 미디어 쿼리 안에만 적는다.

### 2.5 Flexbox — 1차원 레이아웃의 해방 (~2012~2017 표준화)

float·position으로 가로 배치·세로 중앙정렬을 *흉내* 내던 고통을 끝낸 것이 **Flexbox(Flexible Box Layout)**다.

한 축(가로 *또는* 세로)을 따라 자식들을 정렬·분배·신축한다.

수년의 Working Draft/Candidate Recommendation을 거쳐 2010년대 중반 모든 주요 브라우저에 안착했다.

```css
/* 악명 높던 "세로 중앙 정렬"이 세 줄로 끝난다 */
.toolbar {
  display: flex;
  align-items: center;       /* 교차축(세로) 중앙 */
  justify-content: space-between; /* 주축(가로) 분배 */
  gap: 1rem;
}
.toolbar .spacer { flex: 1; } /* 남는 공간을 채워 밀어낸다 */
```

> **주축 / 교차축(main axis / cross axis)** — Flexbox가 자식을 늘어놓는 방향과, 그에 직각인 방향.\
> 예: 가로로 늘어놓으면 주축이 가로, 교차축이 세로다. 세로 중앙 정렬은 교차축 정렬이다.

### 2.6 Grid — 2차원 레이아웃, 테이블의 진짜 후계자 (2017년 3월)

Flexbox가 *한 축*이라면, **CSS Grid Layout**은 행과 열을 *동시에* 다루는 진짜 **2차원 레이아웃** 시스템이다.

**2017년 3월** 주요 브라우저들이 거의 동시에 지원을 출시하며 — 표준이 합의되고 벤더들이 함께 배포한 보기 드문 사건 — 웹 레이아웃의 새 시대를 열었다.

1996년 표현 분리를 선언한 지 20여 년 만에, 마침내 `<table>` 없이 격자 레이아웃을 *구조와 분리해* 짤 수 있게 됐다.

```css
/* 영역 이름으로 페이지 레이아웃을 '그림처럼' 선언 */
.page {
  display: grid;
  grid-template-columns: 200px 1fr;
  grid-template-rows: auto 1fr auto;
  grid-template-areas:
    "header  header"
    "sidebar main"
    "footer  footer";
  min-height: 100vh;
}
header  { grid-area: header; }
.side   { grid-area: sidebar; }
main    { grid-area: main; }
footer  { grid-area: footer; }
```

Flexbox와 Grid가 다루는 축을 나란히 놓으면 이렇다.

```text
Flexbox — 한 축                        Grid — 행과 열을 동시에
+-----------------------------+       +-----------------------------+
| [A][B][C]                   |       | header    header            |
|                             |       | sidebar   main              |
| 가로 또는 세로 한 방향으로  |       | footer    footer            |
| 정렬, 분배, 신축한다        |       |                             |
+-----------------------------+       | 행과 열을 함께 정한다       |
  줄 세우기에 맞는 도구                +-----------------------------+
                                        판을 짜는 데 맞는 도구
```

> **2차원 레이아웃** — 행과 열을 동시에 정해 화면을 판처럼 짜는 방식.\
> 예: 머리말·사이드바·본문·바닥글의 자리를 한 번에 지정하는 것이 2차원 배치다.

### 2.7 커스텀 속성 — CSS에 변수가 생기다 (CSS Variables, ~2015~2017)

그전까지 색·간격 같은 값을 재사용하려면 Sass/Less 같은 **전처리기(preprocessor)**로 *빌드 타임에* 변수를 펼쳐야 했다.

**Custom Properties for Cascading Variables(CSS 커스텀 속성)**은 이를 *런타임*으로 가져왔다.

- cascade·상속을 따른다.
- 자바스크립트로 바꿀 수 있다.
- 테마 전환에 강하다.

```css
:root {
  --brand: #3366cc;
  --gap: 16px;
}
.card {
  color: var(--brand);
  padding: var(--gap);
}
/* 런타임에 테마 교체 — 전처리기 변수는 불가능 */
[data-theme="dark"] { --brand: #88aaff; }
```

```js
// JS로 동적 변경 — 빌드 타임 변수와 결정적 차이
document.documentElement.style.setProperty('--brand', '#e91e63');
```

```text
전처리기 변수                          CSS 커스텀 속성
+-----------------------------+       +-----------------------------+
| 빌드할 때 값이 펼쳐진다     |       | 브라우저에서 살아 있다      |
| 결과물에는 변수가 없다      |       | cascade 와 상속을 따른다    |
|                             |       | 자바스크립트로 바꿀 수 있다 |
| 테마를 바꾸려면 다시        |       | 테마를 그 자리에서          |
| 빌드해야 한다               |       | 교체할 수 있다              |
+-----------------------------+       +-----------------------------+
```

> **전처리기(preprocessor)** — CSS를 만들어 내는 상위 언어. Sass·Less가 대표적이다.\
> 예: 변수를 쓴 파일을 빌드하면 평범한 CSS로 펼쳐져 나온다 — 브라우저는 변수를 보지 못한다.

> **빌드 타임 / 런타임** — 배포 전에 미리 처리하는 시점 / 브라우저에서 실제로 도는 시점.\
> 예: 빌드 타임 변수는 배포 후 못 바꾸고, 런타임 변수는 사용자가 버튼을 누르는 순간 바꿀 수 있다.

### 2.8 컨테이너 쿼리 — 반응형의 다음 단계 (2022~2023)

미디어 쿼리는 *뷰포트(화면 전체)* 크기에만 반응한다.

하지만 컴포넌트 기반 개발(같은 카드가 사이드바에도, 본문에도 들어감)에서는 **"내가 놓인 컨테이너가 얼마나 넓은가"**에 반응해야 한다.

이 오랜 숙원을 푼 것이 **컨테이너 쿼리(Container Queries)**다 — 부모 컨테이너의 크기에 따라 자식 스타일을 바꾼다.

```text
같은 카드가 두 자리에 놓였을 때

  사이드바 안 (좁다)                 본문 안 (넓다)
  +-------------------+             +-----------------------------+
  | [카드]            |             | [       카드       ]        |
  |  세로형으로       |             |  가로형으로 배치한다        |
  |  배치한다         |             |                             |
  +-------------------+             +-----------------------------+

  미디어 쿼리       : 뷰포트가 같으므로 두 카드가 같게 보인다
  컨테이너 쿼리     : 놓인 컨테이너 너비가 다르므로 각자 다르게 보인다
```

크롬 105(**2022년 8월**)가 처음 출시했고, **2023년**(`container-type` 기준 약 2월)에 주요 브라우저 전반으로 퍼져 실무 사용이 가능해졌다.

```css
/* 부모를 '쿼리 가능한 컨테이너'로 지정 */
.card-wrapper { container-type: inline-size; container-name: card; }

/* 뷰포트가 아니라 '컨테이너'가 400px 이상일 때 가로형으로 */
@container card (min-width: 400px) {
  .card { display: grid; grid-template-columns: 120px 1fr; }
}
```

> **컨테이너 쿼리(container query)** — 뷰포트가 아니라 부모 컨테이너의 크기를 조건으로 거는 CSS 문법.\
> 예: 같은 카드 컴포넌트가 좁은 사이드바에서는 세로형, 넓은 본문에서는 가로형으로 스스로 바뀐다.

> **언제·왜:** 컨테이너 쿼리는 반응형의 단위를 *페이지*에서 *컴포넌트*로 내렸다. 디자인 시스템·웹 컴포넌트 시대에 "위치를 모르고도 스스로 적응하는 부품"을 가능하게 한 마지막 퍼즐 조각이다.

## 3부. 웹 표준 운동과 접근성 — 정신(精神)의 진화

기술(HTML5·CSS3)만으로 분리가 이뤄진 건 아니다.\
*개발 문화*를 바꾼 운동이 있었다.

### 3.1 테이블 레이아웃 탈피와 웹 표준 운동

1990년대 후반~2000년대 초, 레이아웃 도구가 없던 시절 개발자들은 **`<table>`로 화면을 격자처럼 쪼개** 디자인을 구현했다.

투명 1px GIF로 간격을 맞추는 **"스페이서 GIF"** 같은 악명 높은 해킹도 여기에 포함된다.

문제는 심각했다.

- 표가 아닌 것을 표로 표현하니 **의미가 깨진다.**
- 스크린리더는 "표 셀"을 읽어 **접근성이 무너진다.**
- 마크업이 비대해진다.
- 수정이 지옥이었다.

```text
테이블 레이아웃                        CSS 레이아웃
+-----------------------------+       +-----------------------------+
| <table> 로 화면을 쪼갠다    |       | HTML 은 구조만 적는다       |
| 투명 1px GIF 로 간격을      |       | 배치는 CSS 가 맡는다        |
| 맞춘다 (스페이서 GIF)       |       |                             |
|                             |       |                             |
| 스크린리더는 "표 셀"이라고  |       | 스크린리더는 본문 구조를    |
| 읽는다                      |       | 그대로 읽는다               |
+-----------------------------+       +-----------------------------+
  의미가 깨지고 마크업이 비대해진다     의미가 남고 수정이 한 곳에서 끝난다
```

이 전환을 밀어붙인 두 사건이 있다.

- **WaSP(Web Standards Project, 1998 결성)**: "브라우저는 표준을 지키고, 개발자는 표준 기반으로 만들자"는 운동을 주도해 벤더들을 압박했다.
- **CSS Zen Garden (데이브 셰이, 2003)**: **똑같은 HTML 문서**에 CSS만 바꿔 끼워 완전히 다른 디자인 수십 개를 보여준 전설적 시연.

CSS Zen Garden이 무엇을 보여 줬는지는 그림이 빠르다.

```text
CSS Zen Garden (2003)

   똑같은 HTML 문서 한 벌
        |
        +---- 디자인 A 의 CSS ----> 완전히 다른 화면
        |
        +---- 디자인 B 의 CSS ----> 완전히 다른 화면
        |
        +---- 디자인 C 의 CSS ----> 완전히 다른 화면
        |
        ( 수십 개 )

   HTML 은 한 글자도 바꾸지 않았다
```

"구조(HTML)와 표현(CSS)을 분리하면 이런 힘이 생긴다"를 *눈으로* 증명해, 테이블 레이아웃에서 CSS 레이아웃으로의 전환을 결정적으로 가속했다.

> **언제·왜:** HTML 4.0(1997)이 *선언*한 "구조·표현 분리"를, 6년 뒤 CSS Zen Garden(2003)이 *문화적으로 완성*했다. 명세가 길을 열고, 운동이 사람들을 그 길로 옮겼다.

> **스페이서 GIF(spacer GIF)** — 투명한 1px 이미지를 늘려 여백을 만들던 해킹.\
> 예: 여백을 지정할 방법이 없으니, 보이지 않는 그림을 원하는 만큼 늘려 끼워 넣었다.

### 3.2 접근성(Accessibility) — 시맨틱이 곧 접근성

구조·표현 분리는 미적 문제가 아니라 **접근성** 문제이기도 하다.

의미를 가진 마크업(시맨틱 HTML)은 스크린리더·키보드 내비게이션·검색엔진이 콘텐츠를 *이해*하게 한다.

`<div onclick>` 대신 `<button>`을 쓰는 것이 접근성의 출발점이다.

**WCAG(Web Content Accessibility Guidelines)** — W3C의 WAI(Web Accessibility Initiative)가 만든 표준이다.

```text
[연대순 구분선 — WCAG 의 판이 갈린 순서다]

1999   WCAG 1.0
------
2008   WCAG 2.0   4대 원칙 POUR 제시
                  Perceivable 인식 · Operable 운용
                  Understandable 이해 · Robust 견고
------
2018   WCAG 2.1
------
2023   WCAG 2.2
```

2.0이 제시한 4대 원칙 **POUR**가 오늘날 법적·실무적 기준이 됐다.

**WAI-ARIA** — 시맨틱 HTML만으로 표현 못 하는 동적 위젯(탭, 모달, 자동완성)에 역할·상태를 부여하는 보조 속성이다.

**단, 첫 번째 규칙은 "ARIA를 쓰지 않는 것"** — 가능하면 네이티브 시맨틱 요소를 먼저 쓰라는 의미다.

```html
<!-- 나쁜 예: 의미 없는 div + JS — 키보드/스크린리더 불가 -->
<div class="btn" onclick="submit()">전송</div>

<!-- 좋은 예: 네이티브 시맨틱 — 포커스·엔터·낭독 모두 공짜 -->
<button type="submit">전송</button>

<!-- 네이티브로 안 될 때만 ARIA로 보강 -->
<div role="tablist">
  <button role="tab" aria-selected="true" aria-controls="p1">개요</button>
</div>
```

> **접근성(accessibility)** — 장애·환경에 관계없이 누구나 콘텐츠를 쓸 수 있게 하는 성질.\
> 예: 마우스를 못 쓰는 사용자도 키보드만으로 버튼을 누를 수 있어야 한다.

> **WCAG · POUR** — W3C WAI가 만든 접근성 표준과, 2.0이 제시한 4대 원칙(Perceivable·Operable·Understandable·Robust).\
> **[보충]** 예: "이미지에 대체 텍스트를 넣어라"는 Perceivable(인식) 원칙에 해당한다 — 원문이 든 예는 아니다.

> **WAI-ARIA** — 네이티브 태그만으로 표현할 수 없는 위젯에 역할·상태를 붙이는 보조 속성.\
> 예: `role="tab"`, `aria-selected="true"` 처럼 "이건 탭이고 지금 선택돼 있다"를 기계에 알린다.

> **언제·왜:** HTML5 시맨틱 요소(`<nav>`, `<main>`, `<article>`)와 WCAG의 진화는 같은 목표의 두 축이다 — **마크업이 의미를 되찾을수록, 더 많은 사람이 웹에 접근한다.** 30년 전 "구조만 적고 표현은 위임하라"던 HTML 원형의 이상이, 접근성이라는 이름으로 되돌아온 셈이다.

## 왜 그렇게 갔나 — 남은 선택지와 트레이드오프

원문이 "왜"를 직접 밝힌 갈림길은 세 곳이다.

**① 왜 HTML 3.2는 표현 태그를 표준에 넣었나.**\
원문은 두 가지를 나란히 든다 — 디자이너가 시각 통제권을 원했고, CSS는 아직 브라우저 지원이 빈약했다.\
그래서 표준이 현장을 뒤따라가며 흡수했고, 그 결과 **HTML이 "의미"에서 가장 멀어진 시점**이 됐다.

**② 왜 XHTML은 좌초했나.**\
엄격한 XML 파싱이 관용적 웹 현실과 충돌했기 때문이다.

- XML 파서는 오류 하나에 렌더링을 전면 중단한다(draconian error handling).
- 현실의 웹은 사람이 손으로 짜고 광고·CMS·댓글이 동적으로 끼어드는 곳이다.
- 그래서 거의 모든 사이트가 XHTML 문법으로 쓰고도 `text/html`로 서빙했다 — **이름만 XHTML, 동작은 HTML.**
- XHTML 2.0은 하위 호환까지 포기해 개발자·브라우저 벤더의 반발을 샀다.

**③ 왜 CSS3는 단일 명세를 버렸나.**\
CSS2를 하나의 문서로 묶었더니 안정된 부분과 실험적 부분이 한 배를 타, **전체 표준화가 가장 느린 기능에 발목 잡혔기** 때문이다.

### 대가는 무엇인가

원문이 대가를 직접 적은 대목은 다음과 같다.

- **XHTML을 문법대로 쓴 사이트들** — 엄격함의 이득은 못 누리고 **형식의 번거로움만 떠안았다.**
- **테이블 레이아웃** — 표가 아닌 것을 표로 표현해 의미가 깨지고, 스크린리더 접근성이 무너지고, 마크업이 비대해지고, 수정이 지옥이었다.
- **CSS2 시대의 편법** — 진짜 2차원 레이아웃 도구가 없어 float·position을 레이아웃에 전용하는 편법이 굳어졌고, Flexbox/Grid까지 **10여 년을 기다려야 했다.**

## 남긴 것 — 오늘 우리가 쓰는 것

웹의 30년은 **"표현을 마크업에서 떼어내, 각자 독립된 레이어로 성숙시킨"** 역사다.

- **HTML은 의미(시맨틱)를 되찾았다.**
- **CSS는** 변변한 변수 하나 없던 스타일 언어에서 **Grid·커스텀 속성·컨테이너 쿼리를 갖춘 본격 레이아웃 시스템**으로 자랐다.
- **HTML 명세는 한 곳**이 됐다 — 2019년 5월 MOU 이후 WHATWG의 Living Standard 하나다.
- 그리고 그 방향키를 쥔 철학은, 역설적으로 1991년 최초의 HTML이 품었던 이상 — **"구조는 적고, 표현은 위임하라"** — 으로의 회귀였다.

## 용어 풀이

- **마크업(markup)** — 글의 어느 부분이 무슨 역할인지 표시해 두는 것.
- **구조(structure) / 표현(presentation)** — "이것이 무엇인가" / "이것이 어떻게 보이는가".
- **SGML** — 문서에 표시를 다는 방법 자체를 규정한 상위 규격. HTML은 그 한 응용이다.
- **RFC 1866** — IETF가 1995년 11월 발행한 HTML 2.0 표준 문서.
- **W3C** — 웹 표준을 합의하는 기구. HTML 3.2(1997.01, W3C 권고안)부터 주도권을 가져갔다.
- **권고안(Recommendation)** — W3C가 "표준으로 쓰라"고 확정해 내놓는 문서 등급.
- **deprecated(권장 폐기)** — 동작은 하지만 앞으로 쓰지 말라고 표시된 상태.
- **DTD(문서 형식 정의)** — 이 문서가 어떤 태그를 어떤 규칙으로 쓸 수 있는지 적은 정의.
- **XML** — 태그로 데이터를 적되 문법을 엄격히 강제하는 범용 형식.
- **XHTML** — HTML을 XML 문법으로 재정의한 표준. 1.0(2000년 1월), 1.1(2001).
- **draconian error handling** — 문법 오류가 하나라도 있으면 렌더링을 전면 중단하는 XML의 오류 처리 규칙.
- **노란 죽음의 화면(Yellow Screen of Death)** — 그 중단 시 뜨는 오류 화면의 별칭.
- **tag soup(태그 수프)** — 문법이 엉망인 마크업. HTML 파서는 이것도 복구해 보여 준다.
- **MIME 타입** — 내용물이 무슨 형식인지 알리는 표시(`text/html`, `application/xhtml+xml`).
- **하위 호환(backward compatibility)** — 새 규격에서도 예전 것이 계속 동작하는 성질.
- **WHATWG** — 2004년 6월 모질라·오페라·애플이 결성한 독립 단체. "Web Applications 1.0"을 시작했다.
- **HTML5** — 2014년 10월 28일 W3C 권고안. 시맨틱·멀티미디어·API로 웹을 앱 플랫폼으로 바꿨다.
- **시맨틱(semantic) 요소** — 태그 이름 자체가 역할을 뜻하는 요소(`<header>`, `<nav>`, `<article>`).
- **플러그인(plugin)** — 브라우저에 따로 설치해 기능을 덧붙이는 외부 프로그램(예: Adobe Flash).
- **canvas** — 스크립트로 그리는 2D/3D 그래픽 영역.
- **localStorage / sessionStorage** — 브라우저 안에 값을 저장하는 클라이언트 저장소.
- **Web Workers** — 화면을 멈추지 않고 뒤에서 도는 백그라운드 스레드.
- **History API / SPA** — 페이지를 새로 받지 않고 주소만 바꾸는 방식과 그렇게 만든 단일 페이지 앱.
- **Living Standard** — 버전을 동결하지 않고 계속 갱신되는 단일 명세.
- **양해각서(MOU)** — 2019년 5월 W3C와 WHATWG가 체결해 HTML 단일 표준을 확정한 합의 문서.
- **캐스케이드(cascade, 종속)** — 작성자·사용자·브라우저 기본값의 스타일이 우선순위 규칙에 따라 합쳐지는 방식.
- **CSS1 / CSS2 / CSS2.1** — 1996년 12월 / 1998년 5월 / 2011년 권고안.
- **포지셔닝(positioning)** — 요소를 문서 흐름에서 떼어 원하는 위치에 놓는 기능.
- **z-index** — 겹친 요소 중 어느 것이 위에 보일지 정하는 값.
- **미디어 타입** — `print`/`screen` 처럼 출력 매체를 구분하는 CSS2의 기능.
- **모듈(module) / 레벨(level)** — 기능 단위로 쪼갠 명세와 그 판 번호(Selectors Level 4, Color Level 5).
- **반응형 웹 디자인(Responsive Web Design)** — 2010년 이선 마콧이 제시한 용어와 방법론. 유동 그리드 + 유연한 이미지 + 미디어 쿼리.
- **뷰포트(viewport)** — 브라우저에서 페이지가 실제로 보이는 영역.
- **미디어 쿼리(media query)** — 기기 특성을 조건으로 다른 스타일을 적용하는 문법. 2012년 6월 W3C 권고안.
- **모바일 우선(mobile-first)** — 좁은 화면을 기본으로 두고 넓어질 때 규칙을 덧붙이는 작성 순서.
- **Flexbox** — 한 축을 따라 자식을 정렬·분배·신축하는 1차원 레이아웃.
- **주축 / 교차축** — Flexbox가 자식을 늘어놓는 방향과 그에 직각인 방향.
- **CSS Grid Layout** — 행과 열을 동시에 다루는 2차원 레이아웃. 2017년 3월 주요 브라우저가 거의 동시에 출시했다.
- **전처리기(preprocessor)** — CSS를 만들어 내는 상위 언어(Sass·Less). 변수를 빌드 타임에 펼친다.
- **빌드 타임 / 런타임** — 배포 전에 처리하는 시점 / 브라우저에서 실제로 도는 시점.
- **커스텀 속성(Custom Properties)** — 런타임에 살아 있는 CSS 변수. cascade·상속을 따르고 JS로 바꿀 수 있다.
- **컨테이너 쿼리(container query)** — 뷰포트가 아니라 부모 컨테이너 크기를 조건으로 거는 문법.
- **테이블 레이아웃** — `<table>`로 화면을 격자처럼 쪼개 배치하던 옛 방식.
- **스페이서 GIF** — 투명 1px 이미지를 늘려 여백을 만들던 해킹.
- **WaSP(Web Standards Project)** — 1998년 결성된 웹 표준 운동 단체.
- **CSS Zen Garden** — 데이브 셰이가 2003년 만든 시연. 같은 HTML에 CSS만 바꿔 끼워 전혀 다른 디자인들을 보여 줬다.
- **접근성(accessibility)** — 장애·환경에 관계없이 누구나 콘텐츠를 쓸 수 있게 하는 성질.
- **스크린리더(screen reader)** — 화면 내용을 소리로 읽어 주는 보조 기술.
- **WCAG** — W3C WAI의 접근성 표준. 1.0(1999) → 2.0(2008) → 2.1(2018) → 2.2(2023).
- **POUR** — WCAG 2.0의 4대 원칙(Perceivable·Operable·Understandable·Robust).
- **WAI-ARIA** — 동적 위젯에 역할·상태를 부여하는 보조 속성. 첫 번째 규칙은 "ARIA를 쓰지 않는 것"이다.
