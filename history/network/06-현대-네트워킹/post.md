# 현대 네트워킹 (CDN · 클라우드 · SDN)

> 연도·인명·RFC 번호·표준명·제품명·수치·코드블록은 원문 그대로다.\

## 한눈에 — 쉽게 말하면

> 네트워크가 "선을 깔고 패킷을 옮기는 일"에서 **소프트웨어로 정의되고, 전 지구에 분산되며, 애플리케이션 가까이로 끌려오는 일**로 바뀐 시대의 기록. 콘텐츠를 사용자 곁(엣지)으로 미는 CDN에서 시작해, 제어 평면을 데이터 평면에서 떼어낸 SDN/NFV, 데이터센터를 통째로 소프트웨어 오버레이로 추상화한 클라우드 네트워킹, TCP를 갈아엎은 QUIC, 그리고 컨테이너·서비스 메시·eBPF가 네트워크를 커널과 사이드카로 끌어내린 흐름까지를 "언제·왜"로 추적한다.

**이 문서의 30년은 "네트워크가 손으로 만지는 장비에서 코드로 다루는 자원이 된" 이야기다.**

이 문서 전체에서 비유는 하나로 고정한다 — **물류 창고**다.

- 처음에는 **창고가 한 곳**이었다.\
  멀리 사는 사람은 대륙을 건너 물건을 받아야 했다. 그래서 창고를 사람 곁에 복제했다(CDN).
- 창고가 여럿이 되자 **어디로 보낼지 정하는 일**이 생겼다.\
  겉의 주소만 보고 나눌지, 안을 열어 보고 나눌지가 갈렸다(L4/L7 로드 밸런싱).
- 그런데 **창고 설비를 바꾸려면 사람이 직접 가야 했다.**\
  설비의 두뇌를 떼어내 중앙 소프트웨어로 올렸다(SDN).
- 다음에는 **한 창고를 여러 고객이 나눠 쓰게** 해야 했다.\
  물리 구조 위에 소프트웨어로 가상의 칸막이를 덧씌웠다(VPC·오버레이).
- 마지막으로 **처리 자체를 물건 옆으로** 옮겼다.\
  사이드카로, 커널로, 그리고 다시 엣지로 내려왔다.

핵심 패턴은 원문의 한 문장이다.

> **네트워크가 하드웨어의 정적 자산에서 소프트웨어로 정의되는 동적 자원으로 바뀌었다.**

```text
세 가지 압력과 그 답

1990년대 말까지의 세계관
   콘텐츠는 한 곳(오리진)에 있다
   라우터·스위치는 벤더 펌웨어대로 패킷을 전달한다
   네트워크 구성은 사람이 장비마다 CLI로 만든다
   |
   | 거리의 압력 (1998~) : 물리적 왕복 지연이 병목이 됐다
   v
CDN — 콘텐츠를 사용자 곁으로 복제한다
   |
   | 유연성의 압력 (2008~) : 서버는 분 단위로 뜨는데 네트워크는 수동 구성이다
   v
SDN / NFV — 네트워크를 프로그래밍 가능한 소프트웨어로 만든다
   |
   | 밀도의 압력 (2014~) : 짧은 수명 워크로드가 수백 개, 서비스 간 호출이 폭증
   v
사이드카 · eBPF — 정책·암호화·관측을 애플리케이션 옆이나 커널로 내린다
```

그림 해설 — 세로줄 옆 한 줄이 **원문이 번호를 매겨 적은 세 가지 압력**이고, 박스 없는 각 줄이 **그 압력에 대한 답**이다.\
첫 블록("1990년대 말까지의 세계관" 3줄)만은 답이 아니라 출발 상태다.

> **오리진(origin) 서버** — 콘텐츠의 원본이 놓인 서버.\
> 예: CDN이 캐시를 못 찾았을 때만 여기까지 올라간다.

> **엣지(edge)** — 사용자와 물리적으로 가까운 쪽의 서버·노드.\
> 예: 원문 표현대로 CDN은 콘텐츠를 "전 세계 수천 대의 엣지 서버(edge server)에 복제해" 둔다.

> **제어 평면 / 데이터 평면(control plane / data plane)** — 경로를 어떻게 정할지 결정하는 쪽과, 실제 패킷을 전달하는 쪽.\
> 예: 원문 표현 그대로 "제어 평면(control plane: 경로를 어떻게 정할지 결정)"과 "데이터 평면(data plane: 실제 패킷 전달)"이다.

## 시대적 배경

1990년대 말까지 네트워크의 세계관은 단순했다.

콘텐츠는 한 곳(오리진 서버)에 있고, 라우터와 스위치는 벤더가 박아넣은 펌웨어대로 패킷을 전달하며, 네트워크 구성은 사람이 장비 하나하나에 CLI로 명령을 쳐서 만드는 것이었다.

이 세계관은 세 가지 압력에 차례로 무너진다.

1. **거리의 압력 (1998~)**: 웹이 전 지구로 퍼지면서 "서울 사용자가 버지니아 서버에서 이미지를 받는" 물리적 왕복 지연(빛의 속도 한계)이 병목이 됐다.\
   콘텐츠를 사용자 곁으로 복제하는 **CDN**이 답이었다.
2. **유연성의 압력 (2008~)**: 클라우드·가상화로 서버는 분 단위로 생성·소멸하는데, 네트워크는 여전히 사람이 수동으로 구성해야 했다.\
   네트워크를 **프로그래밍 가능한 소프트웨어**로 만들려는 SDN/NFV가 등장했다.
3. **밀도의 압력 (2014~)**: 컨테이너·마이크로서비스로 한 호스트에 수백 개의 짧은 수명 워크로드가 뜨고, 서비스 간 호출이 폭증했다.\
   네트워크 정책·암호화·관측을 **애플리케이션 바로 옆(사이드카)이나 커널**(eBPF)으로 끌어내려야 했다.

이 세 압력을 관통하는 한 문장: **네트워크가 하드웨어의 정적 자산에서 소프트웨어로 정의되는 동적 자원으로 바뀌었다.**\
이 문서는 그 변환의 각 단계를 다룬다.

> **CLI(명령줄 인터페이스)** — 장비에 글자로 명령을 쳐서 설정하는 방식.\
> 예: 원문 표현대로 네트워크 구성은 "사람이 장비 하나하나에 CLI로 명령을 쳐서" 만드는 것이었다.

> **워크로드(workload)** — 실제로 일을 하는 프로그램 하나의 단위(VM·컨테이너·Pod 등).\
> 예: 원문 표현대로 컨테이너 시대에는 "한 호스트에 수백 개의 짧은 수명 워크로드"가 뜬다.

## 1. CDN — 콘텐츠를 사용자 곁으로 (Akamai, 1998)

- **언제**: 1998년 8월 MIT에서 Tom Leighton 교수와 대학원생 Daniel Lewin이 동료들과 함께 Akamai Technologies를 창업.\
  상용 서비스 FreeFlow를 1999년 출시.
- **왜**: 당시 MIT의 Tim Berners-Lee가 "웹이 폭발적 트래픽 급증(**flash crowd**)에 무너지는 문제를 근본적으로 풀라"고 던진 도전이 출발점이었다.\
  인기 페이지에 트래픽이 몰리면 중앙 서버가 압사하고, 멀리 있는 사용자는 대륙을 건너는 왕복 지연을 고스란히 떠안았다.
- **무엇을 풀었나**: 콘텐츠(이미지·동영상·정적 파일)를 전 세계 수천 대의 **엣지 서버**(edge server)에 복제해 두고, 사용자의 요청을 **물리적으로 가장 가까운 엣지**로 보낸다.\
  오리진은 부하에서 해방되고, 사용자는 짧은 거리만 왕복한다.

> **flash crowd** — 인기 페이지에 트래픽이 갑자기 몰리는 현상.\
> 예: 원문 표현대로 이때 중앙 서버가 압사한다 — Tim Berners-Lee가 이 문제를 풀라고 던진 도전이 Akamai의 출발점이었다.

CDN의 두 핵심 기술:

- **일관된 해싱(consistent hashing)**: 어떤 콘텐츠를 어느 엣지 서버가 캐싱할지 결정하는 매핑.\
  서버가 추가·제거돼도 재배치되는 키가 최소화되어, 캐시 적중률이 유지된다.\
  (이 자료구조는 분산 시스템 전반의 기초 — corpus `database-history/03-NoSQL-운동`의 Dynamo 링도 같은 일관된 해싱 위에 선다.)
- **실시간 매핑(real-time mapping)**: DNS 단계에서 사용자의 위치·네트워크 상태·서버 부하를 종합해 최적 엣지를 골라준다.\
  사용자는 같은 도메인을 묻지만, 위치마다 다른 IP를 돌려받는다.

```text
일관된 해싱이 지키는 것 — 서버가 바뀌어도 대부분의 매핑은 그대로다

  콘텐츠 하나하나 ──[일관된 해싱]──▶ 어느 엣지 서버가 캐싱할지 정해진다

  서버를 추가하거나 제거하면
     재배치되는 키가 최소화된다
        ⇒ 캐시 적중률이 유지된다
```

```text
실시간 매핑 — 같은 도메인을 물어도 위치마다 다른 IP가 온다

  서울 사용자      ──"이 도메인이 어디죠?"──▶ [DNS]
  다른 대륙 사용자 ──"이 도메인이 어디죠?"──▶ [DNS]
                                              |
              사용자의 위치 · 네트워크 상태 · 서버 부하를 종합
                                              |
  서울 사용자      ◀── 서울에서 가까운 엣지의 IP ──┘
  다른 대륙 사용자 ◀── 그쪽에서 가까운 엣지의 IP ──┘
```

> **일관된 해싱(consistent hashing)** — 서버가 늘거나 줄어도 다시 옮겨야 하는 항목이 최소가 되도록 설계한 매핑 방식.\
> 예: 원문 표현대로 "서버가 추가·제거돼도 재배치되는 키가 최소화되어, 캐시 적중률이 유지된다".

> **캐시 적중(cache hit) / 캐시 미스** — 찾는 것이 캐시에 있어 바로 주는 경우 / 없어서 원본까지 가야 하는 경우.\
> 예: 아래 블록처럼 캐시 미스일 때만 엣지가 오리진까지 올라간다.

```
CDN 없이:  서울 사용자 ───────────대륙 횡단──────────▶ 버지니아 오리진
            (매 요청 ~200ms RTT, 오리진에 부하 집중)

CDN:       서울 사용자 ─짧은 왕복─▶ [서울 엣지]  ──(캐시 미스 시만)──▶ 오리진
            (캐시 적중 시 ~5ms, 오리진은 origin pull 때만 깨어남)
                          ▲
              일관된 해싱 + DNS 실시간 매핑으로
              "가장 가까운, 부하 적은" 엣지 선택
```

> CDN의 본질은 "**계산보다 복제가 싸다**"는 통찰이다. 같은 콘텐츠를 1000번 전송할 바엔 1000곳에 한 번씩 복제해 두는 편이 빠르고 싸다. 이 발상은 이후 엣지 컴퓨팅(7절)으로 확장되어, 캐싱뿐 아니라 **연산 자체를 엣지로** 미는 데까지 이어진다.

## 2. 로드 밸런싱 — L4와 L7 (트래픽을 나누는 두 층위)

엣지든 오리진이든, 한 대로는 트래픽을 감당할 수 없다.

**로드 밸런서**(load balancer)는 들어오는 요청을 여러 백엔드로 분산한다.\
분산을 어느 OSI 계층에서 판단하느냐로 두 갈래가 갈린다.

> **로드 밸런서(load balancer)** — 들어오는 요청을 여러 백엔드 서버로 나눠 주는 장치.\
> 예: 원문 표현대로 "한 대로는 트래픽을 감당할 수 없"을 때 쓴다.

### L4 로드 밸런싱 (전송 계층)
- **무엇을**: TCP/UDP 패킷의 **IP·포트만** 보고 백엔드를 고른다. 패킷 내용을 들여다보지 않는다.
- **왜 빠른가**: 페이로드를 파싱하지 않으므로 연결당 CPU가 거의 들지 않고, 처리량이 회선 속도(line rate)에 가깝게 확장된다.\
  한 TCP 연결이 클라이언트–백엔드 간에 그대로 유지된다(패스스루에 가까움).

#### 대가는 무엇인가 — L4의 한계

HTTP 경로·헤더·쿠키를 모르므로 "이 URL은 A 서버로" 같은 콘텐츠 기반 라우팅이 불가능하다.

### L7 로드 밸런싱 (애플리케이션 계층)
- **무엇을**: HTTP 요청을 **종료**(terminate)하고 그 안의 경로·헤더·쿠키·메서드를 읽어 백엔드를 고른다.\
  본질적으로 **리버스 프록시**(reverse proxy)다.
- **무엇이 되는가**: 두 개의 TCP 연결(클라이언트↔LB, LB↔백엔드)을 유지하므로 **TLS 종료, 경로 기반 라우팅, 캐싱, 압축, 요청 재시도**가 가능하다.

#### 대가는 무엇인가 — L7의 비용

매 요청을 파싱·재조립하므로 L4보다 무겁다.

```
L4:  Client ══TCP══▶ [L4 LB] ══같은 TCP 흐름══▶ Backend     (IP:port만 판단, 1 연결)

L7:  Client ──TCP1──▶ [L7 LB] ──TCP2──▶ Backend             (HTTP 내용 판단, 2 연결)
                         │ TLS 종료 / "/api→A, /img→B" / 캐싱 / 재시도
```

> **리버스 프록시(reverse proxy)** — 클라이언트 요청을 대신 받아 뒤쪽 서버에 전달하는 중개 서버.\
> 예: 원문 표현대로 L7 로드 밸런서는 "본질적으로 리버스 프록시"다.

> **TLS 종료(TLS termination)** — 암호화된 연결을 중간 지점에서 풀어, 그 안의 내용을 보고 처리하는 것.\
> 예: 위 블록처럼 L7 LB가 두 연결을 유지하기 때문에 가능한 일이다.

```text
실무에서는 둘을 계층적으로 쓴다

  거대한 트래픽
      |
      v
  [ 바깥 : L4  또는 DNS·Anycast 기반 GSLB ]   데이터센터·존 단위로 쪼갠다
      |
      v
  [ 안 : L7 ]                                 마이크로서비스 단위로 라우팅한다
```

> 실무에서는 둘을 **계층적으로** 쓴다. 바깥에 L4(또는 DNS·Anycast 기반 GSLB)로 거대한 트래픽을 데이터센터·존 단위로 쪼개고, 안에서 L7로 마이크로서비스 단위 라우팅을 한다. 이 L7 프록시가 6절의 **서비스 메시 사이드카**(Envoy)로 진화한다 — 즉 로드 밸런서가 애플리케이션마다 한 개씩 따라붙는 형태로.

## 3. SDN / NFV — 제어 평면과 데이터 평면의 분리 (2008~2012)

### SDN (Software-Defined Networking)
- **언제**: 2008년 Stanford의 Nick McKeown 팀이 **OpenFlow** 프로토콜을 발표("OpenFlow: Enabling Innovation in Campus Networks").\
  선행 연구는 2007년 Ethane 프로젝트. 2011년부터 ONF(Open Networking Foundation)가 표준을 관리.
- **왜**: 전통 라우터·스위치는 **제어 평면**(control plane: 경로를 어떻게 정할지 결정)과 **데이터 평면**(data plane: 실제 패킷 전달)이 한 박스 안에 벤더 펌웨어로 묶여 있었다.\
  네트워크 동작을 바꾸려면 장비마다 벤더가 정한 CLI를 쳐야 했고, 새 라우팅 정책을 실험할 자유가 없었다.
- **무엇을 풀었나**: **제어 평면을 장비에서 떼어내** 중앙 컨트롤러(소프트웨어)로 올린다.\
  스위치는 "흐름 테이블(flow table)"만 가진 단순 데이터 평면으로 남고, OpenFlow로 컨트롤러가 "이 흐름은 이 포트로" 같은 규칙을 내려보낸다.\
  네트워크 전체가 **하나의 프로그래밍 가능한 시스템**이 된다.

```
전통 네트워크: 각 박스가 제어+데이터를 모두 내장 (분산된, 벤더 종속 두뇌)

   [스위치]   [스위치]   [스위치]      ← 각자 알아서 경로 계산
      ▲          ▲          ▲

SDN:  ┌──────── SDN 컨트롤러 (중앙 제어 평면, 소프트웨어) ────────┐
      │           ▼ OpenFlow로 흐름 규칙 주입 ▼                   │
   [스위치]   [스위치]   [스위치]      ← 데이터 평면만, "시키는 대로 전달"
```

> **OpenFlow** — 중앙 컨트롤러가 스위치에 흐름 규칙을 내려보내는 프로토콜.\
> 예: 위 블록 그대로 "이 흐름은 이 포트로" 같은 규칙을 컨트롤러가 주입한다.

> **흐름 테이블(flow table)** — 스위치가 들고 있는, "이런 흐름은 이렇게 처리하라"는 규칙 목록.\
> 예: SDN에서 스위치는 이것만 가진 단순 데이터 평면으로 남는다.

### NFV (Network Functions Virtualization)
- **언제**: 2012년 10월 세계 주요 통신사들이 독일 다름슈타트에서 백서를 발표, 11월 ETSI 산하에 NFV 표준화 그룹(ISG NFV) 발족.
- **왜**: 방화벽·로드 밸런서·라우터·DPI 같은 네트워크 기능이 모두 **전용 하드웨어 박스**(appliance)였다.\
  통신사는 새 기능마다 박스를 사서 랙에 꽂고 배선해야 했고, 확장은 곧 하드웨어 구매였다.
- **무엇을 풀었나**: 이 네트워크 기능들을 **범용 서버 위의 소프트웨어**(VNF, Virtual Network Function)로 가상화한다.\
  방화벽이 어플라이언스가 아니라 VM/컨테이너가 되면, 클라우드 자원처럼 분 단위로 띄우고 끄고 확장할 수 있다.

```text
같은 기능, 다른 형태 — 대립축은 "전용 하드웨어 박스" vs "범용 서버 위 소프트웨어"

어플라이언스
   방화벽 · 로드 밸런서 · 라우터 · DPI  →  각각 전용 박스
      새 기능마다 박스를 사서 랙에 꽂고 배선한다
      확장은 곧 하드웨어 구매다

VNF (Virtual Network Function)
   방화벽 · 로드 밸런서 · 라우터 · DPI  →  범용 서버 위 VM / 컨테이너
      클라우드 자원처럼 분 단위로 띄우고 끄고 확장할 수 있다
```

> **어플라이언스(appliance)** — 한 가지 기능을 위해 만들어진 전용 하드웨어 장비.\
> 예: 원문 표현대로 방화벽·로드 밸런서·라우터·DPI가 모두 전용 박스였다.

> SDN과 NFV는 종종 함께 묶이지만 직교한다. **SDN = 네트워크 제어를 소프트웨어로(어떻게 흐르게 할지)**, **NFV = 네트워크 기능을 소프트웨어로(무슨 일을 할지)**. 둘이 합쳐져 "네트워크 전체가 코드로 정의·운영되는" 4절 클라우드 네트워킹의 토대가 됐다.

## 4. 클라우드 네트워킹 — VPC와 오버레이 (VXLAN, RFC 7348 / 2014)

- **언제**: VPC(Virtual Private Cloud)는 AWS가 2009년 도입.\
  그 기반 기술인 **VXLAN**은 2014년 8월 정보 RFC 7348로 표준화(VMware·Cisco·Arista·Broadcom 등 공동 저술).
- **왜**: 클라우드는 한 물리 데이터센터에서 **수많은 테넌트**(고객)가 서로를 보지 못하게 격리된 가상 네트워크를 써야 한다.\
  그런데 전통 VLAN은 식별자가 12비트(**최대 4094개**)뿐이라 대규모 멀티테넌트에 턱없이 부족했다.\
  또 서버 가상화(VM 마이그레이션)는 평평한 L2 네트워크를 원하는데, 물리 데이터센터는 L3로 분할돼 있었다.
- **무엇을 풀었나**: **오버레이 네트워크(overlay network)** — 물리 L3 망(언더레이) *위에* 가상 L2 망을 소프트웨어로 덧씌운다.\
  VXLAN은 L2 프레임을 **UDP 패킷 안에 캡슐화**(MAC-in-UDP)해 L3 망을 가로질러 옮긴다.\
  식별자(VNI)는 **24비트 = 약 1600만 개**라 테넌트 격리 한계가 사실상 사라진다.

```text
왜 VXLAN이 나왔나 — 식별자가 몇 개까지 되는가

VLAN   식별자 12비트  =  최대 4094개
          ⇒ 대규모 멀티테넌트에 턱없이 부족했다

VXLAN  식별자(VNI) 24비트  =  약 1600만 개
          ⇒ 테넌트 격리 한계가 사실상 사라진다
```

> **테넌트(tenant)** — 한 인프라를 함께 쓰는 고객 하나하나.\
> 예: 원문 표현대로 클라우드는 "수많은 테넌트(고객)가 서로를 보지 못하게 격리된 가상 네트워크"를 써야 한다.

> **오버레이 / 언더레이(overlay / underlay)** — 물리 망 위에 소프트웨어로 덧씌운 가상 망 / 그 아래의 실제 물리 망.\
> 예: 아래 블록 그대로 오버레이에서는 같은 가상 L2 세그먼트처럼 보이지만, 언더레이는 실제 L3 IP 라우팅 망이다.

```
오버레이 (가상): VM-A ─── 같은 가상 L2 세그먼트처럼 보임 ─── VM-B
                   │                                          ▲
            VXLAN 캡슐화                              VXLAN 역캡슐화
            (L2 프레임을 UDP에 감쌈, VNI=테넌트 식별)
                   ▼                                          │
언더레이 (물리): [호스트1] ════ 실제 L3 IP 라우팅 망 ════ [호스트2]

   ⇒ 물리 토폴로지와 무관하게, 소프트웨어로 가상 네트워크를 그린다.
```

VPC는 이 오버레이 위에 **사용자가 정의하는 가상 네트워크**다.\
자신만의 IP 대역, 서브넷, 라우팅 테이블, 보안 그룹을 API로 선언하면, 클라우드가 SDN(3절)으로 물리 망에 실현한다.

**네트워크가 클릭/코드로 만들어지는 자원**이 된 것이 핵심이다.

> VXLAN의 "L2-in-L3 캡슐화" 발상은 6절 컨테이너 네트워킹에서 그대로 재등장한다(Flannel의 VXLAN 백엔드 등). 오버레이는 현대 분산 인프라가 물리 토폴로지에서 해방되는 공통 문법이다.

## 5. QUIC / HTTP3 — TCP를 갈아엎고 네트워크에 남긴 흔적 (RFC 9000, 2021)

> 프로토콜 자체의 진화는 corpus `web-history/02-HTTP-진화`가 다룬다. 여기서는 **QUIC이 네트워크 계층·운영에 무엇을 강제했는가**에 초점을 둔다.

- **언제**: Google이 2013년 실험 프로토콜로 시작, IETF가 2015년 워킹그룹 발족, 2021년 5월 QUIC 전송(RFC 9000), 2022년 6월 HTTP/3(RFC 9114)·QPACK 표준화.
- **왜**: HTTP/2는 한 TCP 연결에 여러 스트림을 다중화했는데, TCP는 바이트 순서를 보장하므로 **패킷 하나가 유실되면 그 뒤 모든 스트림이 커널 버퍼에서 함께 멈춘다**(전송 계층 head-of-line blocking).\
  또 TCP+TLS 핸드셰이크는 왕복이 여러 번 필요해 연결 설정이 느렸다.
- **무엇을 풀었나**: QUIC은 TCP를 버리고 **UDP 위에 전송 계층을 새로 구현**한다.\
  TLS 1.3을 내장하고, 스트림을 **독립적으로** 전달한다 — 5번 스트림이 패킷을 잃어도 1~4·6번 스트림은 그대로 흐른다.\
  0-RTT/1-RTT로 연결 설정도 빨라진다.

```
HTTP/2 (TCP):  스트림들 ─┐
                          ├─ 한 TCP 바이트스트림 ─▶ 패킷 1개 유실 시 전부 정지 (HoL)
                          ┘

HTTP/3 (QUIC):  스트림5 ──X─▶ (5번만 대기)
                스트림1,2,3,4,6 ──────▶ 계속 흐름   (스트림 독립 전달)
                   └ UDP 위, TLS1.3 내장, 헤더 암호화 → 미들박스 불투명
```

> **head-of-line blocking(HoL)** — 줄의 맨 앞이 막히면 뒤가 전부 대기하는 현상.\
> 예: 위 블록 그대로 HTTP/2에서는 패킷 하나가 유실되면 그 뒤 모든 스트림이 함께 멈춘다.

> **스트림(stream)** — 한 연결 안에서 독립적으로 흐르는 논리적 통로.\
> 예: QUIC에서는 5번 스트림이 패킷을 잃어도 1~4·6번 스트림은 그대로 흐른다.

**QUIC이 네트워크에 강제한 변화 (이 절의 핵심):**

- **혼잡 제어가 커널에서 유저스페이스로**: TCP의 혼잡 제어는 OS 커널이 했다.\
  QUIC은 UDP 위 애플리케이션이라 **혼잡 제어·재전송·흐름 제어가 전부 유저스페이스 라이브러리**로 옮겨졌다.\
  새 알고리즘을 **OS 업데이트 없이 앱 배포만으로** 굴릴 수 있게 됐지만, CPU 부담도 앱으로 넘어왔다.
- **미들박스의 실명(失明)**: 방화벽·로드 밸런서·DPI 장비는 수십 년간 TCP 헤더(포트·플래그·시퀀스)를 읽어 트래픽을 분류·제어했다.\
  QUIC은 전송 헤더 대부분을 **암호화**해 미들박스에 노출하지 않는다.
- **UDP를 1급 시민으로**: 많은 방화벽·NAT가 UDP를 홀대(차단·짧은 타임아웃)했다.\
  QUIC 보급은 망 장비들이 UDP 443을 진지하게 다루도록 강제했고, QUIC이 막히면 TCP로 떨어지는 **폴백** 설계를 표준 운영 관행으로 만들었다.
- **연결 ID로 IP 이동 견디기**: QUIC 연결은 4-튜플(IP:port 쌍)이 아니라 **Connection ID**로 식별된다.\
  Wi-Fi↔셀룰러로 IP가 바뀌어도 연결이 끊기지 않는다(connection migration) — 모바일 네트워크 운영에 직접적 영향.

```text
혼잡 제어가 어디서 도는가 — 대립축은 "OS 커널" vs "유저스페이스 라이브러리"

TCP
   [ 애플리케이션 ]
   [ OS 커널 : 혼잡 제어 · 재전송 · 흐름 제어 ]
       ⇒ 새 알고리즘을 쓰려면 OS 업데이트가 필요하다

QUIC
   [ 애플리케이션 + 유저스페이스 라이브러리 : 혼잡 제어 · 재전송 · 흐름 제어 ]
   [ OS 커널 : UDP 만 ]
       ⇒ 새 알고리즘을 OS 업데이트 없이 앱 배포만으로 굴릴 수 있다
```

```text
연결을 무엇으로 식별하는가 — 대립축은 "4-튜플" vs "Connection ID"

4-튜플 (IP:port 쌍)
   Wi-Fi 에서 셀룰러로 IP 가 바뀐다 ──▶ 연결을 다시 세워야 한다

Connection ID
   Wi-Fi 에서 셀룰러로 IP 가 바뀐다 ──▶ 연결이 끊기지 않는다
                                        (connection migration)
```

> **미들박스(middlebox)** — 출발지와 목적지 사이에 놓여 트래픽을 보고 처리하는 장비(방화벽·로드 밸런서·DPI 등).\
> 예: 원문 표현대로 이들은 "수십 년간 TCP 헤더(포트·플래그·시퀀스)를 읽어 트래픽을 분류·제어했다".

> **유저스페이스(userspace)** — OS 커널 바깥, 보통의 프로그램이 도는 영역.\
> 예: QUIC은 혼잡 제어·재전송·흐름 제어를 전부 이쪽 라이브러리로 옮겼다.

> **폴백(fallback)** — 원하는 방식이 막혔을 때 예비 방식으로 떨어지는 설계.\
> 예: 원문 표현대로 "QUIC이 막히면 TCP로 떨어지는" 것이 표준 운영 관행이 됐다.

### 대가는 무엇인가

- 혼잡 제어가 유저스페이스로 옮겨가면서 **CPU 부담도 앱으로 넘어왔다.**
- 전송 헤더가 암호화되면서 **네트워크 운영자의 가시성·제어력이 줄고, "L4에서 무엇을 보던" 장비들이 무력해졌다.**

## 6. 컨테이너 네트워킹과 서비스 메시 (CNI · Istio, 2017)

### CNI (Container Network Interface)
- **언제·왜**: 2015년 전후 컨테이너(Docker)·Kubernetes가 퍼지면서, **수명이 짧고 호스트마다 수백 개씩 뜨는 컨테이너에 IP를 붙이고 서로 통신시키는** 표준이 필요해졌다.\
  CNI는 컨테이너 런타임과 네트워크 플러그인 사이의 **얇은 표준 인터페이스**다 — "컨테이너가 뜰 때 네트워크에 붙이고, 죽을 때 떼라"만 정의하고, 구현은 플러그인(Flannel·Calico·Cilium 등)에 맡긴다.
- **무엇을**: 각 Pod에 고유 IP를 주고(평평한 IP 공간), 오버레이(VXLAN — 4절 재등장)나 BGP 라우팅으로 노드를 가로질러 통신시킨다.\
  네트워크 정책(어떤 Pod가 어떤 Pod와 통신 가능한가)도 여기서 집행된다.

> **Pod** — Kubernetes가 컨테이너를 묶어 다루는 가장 작은 단위.\
> 예: 원문 표현대로 CNI는 "각 Pod에 고유 IP를 주고(평평한 IP 공간)" 노드를 가로질러 통신시킨다.

> **플러그인(plugin)** — 표준 인터페이스만 맞추면 갈아 끼울 수 있는 구현체.\
> 예: 원문이 든 CNI 플러그인이 Flannel·Calico·Cilium이다.

### 서비스 메시 (Istio, 2017)
- **언제**: Google·IBM·Lyft가 2017년 Istio를 발표. 데이터 평면은 Lyft가 만든 **Envoy** 프록시.
- **왜**: 마이크로서비스가 수십~수백 개로 쪼개지자, **서비스 간 통신**(재시도·타임아웃·서킷 브레이킹·로드 밸런싱·암호화·추적)을 각 서비스 코드에 일일이 구현하는 것이 지옥이 됐다.\
  언어마다 라이브러리도 제각각이었다.
- **무엇을 풀었나**: 이 통신 관심사를 애플리케이션에서 **사이드카**(sidecar)로 빼낸다.\
  모든 Pod에 Envoy 프록시를 주입해, **그 Pod의 모든 인·아웃 트래픽이 Envoy를 통과**하게 한다.\
  애플리케이션은 비즈니스 로직만 짜고, 네트워크 정책은 사이드카 메시(데이터 평면) + 중앙 컨트롤(istiod, 제어 평면)이 처리한다.\
  **SDN의 제어/데이터 평면 분리(3절)가 애플리케이션 계층에서 재현**된 것이다.

핵심 기능 **mTLS(상호 TLS)**: istiod가 인증 기관(CA) 역할을 해 각 워크로드에 인증서를 발급하고, 사이드카끼리 **자동으로 양방향 TLS**를 맺는다.\
애플리케이션 코드를 한 줄도 안 고치고 서비스 간 통신이 전부 암호화·상호 인증된다 — **제로 트러스트** 네트워킹의 실현.

```
        ┌─────────── istiod (제어 평면: 정책 배포 + CA로 인증서 발급) ───────────┐
        ▼                                                                      ▼
  ┌── Pod A ──┐                  mTLS (자동 암호화+상호인증)            ┌── Pod B ──┐
  │ App  │Envoy│ ══════════════════════════════════════════════════▶ │Envoy│ App │
  └──────┴─────┘   재시도·타임아웃·서킷브레이커·추적·로드밸런싱        └─────┴──────┘
      ▲ 사이드카가 모든 트래픽을 가로챔 — App은 평문 localhost만 인지
```

> **사이드카(sidecar)** — 애플리케이션 옆에 함께 떠서 통신을 대신 처리하는 보조 프로세스.\
> 예: 위 블록 그대로 Envoy가 Pod의 모든 인·아웃 트래픽을 가로채고, App은 평문 localhost만 인지한다.

> **mTLS(상호 TLS)** — 양쪽이 서로 인증서를 내밀어 상호 인증하는 TLS.\
> 예: 원문 표현대로 istiod가 CA 역할을 해 인증서를 발급하고, 사이드카끼리 자동으로 양방향 TLS를 맺는다.

> **서킷 브레이킹(circuit breaking)** — 뒤쪽 서비스가 계속 실패하면 잠시 호출을 끊어 연쇄 장애를 막는 장치.\
> 예: 원문이 서비스 간 통신 관심사로 든 것들 — 재시도·타임아웃·서킷 브레이킹·로드 밸런싱·암호화·추적 — 중 하나다.

### 대가는 무엇인가

> 서비스 메시는 강력하지만, **Pod마다 프록시 하나**라는 비용(메모리·지연 홉)이 따른다. 이 오버헤드가 7절 eBPF·사이드카리스(ambient) 메시로의 다음 진화를 낳는다.

## 7. eBPF (Cilium)와 엣지 컴퓨팅 — 커널로, 그리고 다시 엣지로

### eBPF / Cilium — 네트워킹을 커널 안으로
- **언제**: eBPF(extended Berkeley Packet Filter)는 2014년 Linux 커널 3.18에 병합(1992년 BPF의 확장판).\
  2016년 XDP로 드라이버 수준 고속 처리 추가. Cilium은 이 eBPF를 기반으로 한 CNI/네트워킹·보안·관측 플랫폼.
- **왜**: 6절 사이드카 모델은 모든 패킷이 **유저스페이스 프록시를 거치며** 컨텍스트 스위칭·복사·지연을 유발했다.\
  iptables 기반 기존 CNI도 규칙이 수만 개로 늘면 선형 탐색으로 느려졌다.
- **무엇을 풀었나**: eBPF는 **검증된 작은 프로그램을 커널 안에 안전하게 주입**해 실행하는 기술이다(커널을 새로 컴파일하거나 모듈을 올리지 않고).\
  Cilium은 라우팅·로드 밸런싱·네트워크 정책·암호화·관측을 **커널 데이터 경로에서 직접** 처리한다 — 유저스페이스 왕복 없이.\
  네트워크 정책을 IP가 아니라 **서비스 신원(identity)** 기준으로 집행하고, 사이드카 없이도 메시 기능 일부를 커널에서 제공한다.

```
사이드카 경로:  App ─▶ [Envoy(유저스페이스)] ─▶ 커널 ─▶ NIC   (홉·복사·컨텍스트 스위치)

eBPF 경로:      App ─▶ 커널[eBPF 프로그램이 직접 라우팅/정책/LB] ─▶ NIC
                          ▲ 유저스페이스 프록시 없이 커널에서 처리
```

> **eBPF** — 검증된 작은 프로그램을 커널 안에 안전하게 주입해 실행하는 기술.\
> 예: 원문 표현대로 "커널을 새로 컴파일하거나 모듈을 올리지 않고" 커널 데이터 경로에서 직접 처리한다.

> **컨텍스트 스위칭(context switching)** — 처리 주체가 바뀔 때 상태를 저장하고 복원하느라 드는 비용.\
> 예: 원문이 사이드카 모델의 비용으로 든 것이 "컨텍스트 스위칭·복사·지연"이다.

### 엣지 컴퓨팅 — CDN의 발상을 연산으로 확장
- **언제**: ETSI가 2014년 말 **MEC**(처음엔 Mobile Edge Computing, 2017년 Multi-access Edge Computing으로 개명) 표준화 그룹 발족.\
  같은 2017년 Cloudflare가 **Workers**(CDN 엣지에서 코드를 실행하는 서버리스)를 출시.
- **왜**: CDN(1절)이 *콘텐츠*를 엣지로 밀어 거리 지연을 없앴다면, 동적 처리·개인화·IoT·실시간 추론은 *연산 자체*가 사용자(또는 단말) 곁에 있어야 했다.\
  클라우드 리전까지 왕복하기엔 지연·대역폭·프라이버시 비용이 컸다.
- **무엇을 풀었나**: 연산을 **사용자 가까운 엣지 노드**(통신사 기지국 근처 = MEC, 또는 CDN PoP = Workers)에서 실행한다.\
  5G의 초저지연 요구, 자율주행·AR/VR·실시간 추론이 주 동인.\
  CDN이 만든 "사용자 곁의 분산 인프라"가 캐시에서 **실행 환경**으로 격상된 것이다.

```text
7절의 두 방향 — 원문이 "두 방향의 동일한 운동"이라 적은 것

eBPF        네트워킹을 아래로 (커널)
                유저스페이스 프록시 ──▶ 커널 데이터 경로

엣지 컴퓨팅  연산을 밖으로 (사용자 곁)
                클라우드 리전 ──▶ 사용자 가까운 엣지 노드

   둘 다 "병목 지점에 처리를 더 가까이 붙인다"는 본능을 보여준다
```

> **서버리스(serverless)** — 서버를 직접 띄우지 않고 코드만 올리면 실행되는 방식.\
> 예: 원문이 Cloudflare Workers를 "CDN 엣지에서 코드를 실행하는 서버리스"라고 적는다.

> **PoP(Point of Presence)** — 네트워크 사업자가 사용자와 가까운 곳에 둔 접속 거점.\
> 예: 원문 표현대로 Workers는 "CDN PoP"에서 코드를 실행한다.

> 7절은 두 방향의 동일한 운동이다 — eBPF는 네트워킹을 **아래로(커널)**, 엣지 컴퓨팅은 연산을 **밖으로(사용자 곁)** 끌어내린다. 둘 다 "병목 지점에 처리를 더 가까이 붙인다"는 현대 네트워킹의 통일된 본능을 보여준다.

## 영향과 의의

*(이 편의 「왜 그렇게 갔나」에 해당한다)*

현대 네트워킹의 30년을 한 줄로 요약하면 "**네트워크의 소프트웨어화(softwarization)**"다.\
세 축에서 동시에 일어났다.

- **위치의 분산**: 오리진 한 곳 → CDN 엣지 → MEC/Workers.\
  콘텐츠도 연산도 사용자 곁으로 복제·이동했다.\
  일관된 해싱이라는 한 자료구조가 이 분산의 토대를 깔았다.
- **제어의 분리와 중앙화**: SDN이 제어 평면을 장비에서 떼어 소프트웨어 컨트롤러로 올렸고(3절), 같은 패턴이 서비스 메시에서 애플리케이션 계층으로(istiod, 6절), 클라우드 VPC에서 사용자 API로(4절) 재현됐다.\
  "**단순한 데이터 평면 + 똑똑한 중앙 제어 평면**"이 시대의 공통 아키텍처가 됐다.
- **추상화의 하강**: 네트워크 기능이 전용 하드웨어 → 가상 소프트웨어(NFV) → 사이드카 프록시 → 커널 eBPF로 점점 더 **워크로드 가까이, 더 낮은 층으로** 내려왔다.

```text
같은 패턴이 세 자리에서 재현됐다 — "단순한 데이터 평면 + 똑똑한 중앙 제어 평면"

3절 SDN           중앙 컨트롤러          ──▶  스위치 (흐름 테이블만)
6절 서비스 메시   istiod                 ──▶  Envoy 사이드카
4절 클라우드 VPC  사용자 API 선언        ──▶  물리 망(언더레이)
```

```text
추상화의 하강 — 워크로드 가까이, 더 낮은 층으로

   전용 하드웨어 (어플라이언스)
        |
        v
   가상 소프트웨어 (NFV)
        |
        v
   사이드카 프록시 (Envoy)
        |
        v
   커널 (eBPF)
```

## 남긴 것 — 오늘 우리가 쓰는 것

원문의 「영향과 의의」가 적은, 그 결과 오늘 남은 것들이다.

- 오늘날 엔지니어는 IP 대역·서브넷·라우팅·방화벽·로드 밸런서·암호화를 **물리 장비가 아니라 코드(IaC)·API·선언적 정책**으로 다룬다.
- "**단순한 데이터 평면 + 똑똑한 중앙 제어 평면**"이 시대의 공통 아키텍처가 됐다.
- 콘텐츠도 연산도 사용자 곁으로 복제·이동했다 — 오리진 한 곳에서 CDN 엣지로, 다시 MEC/Workers로.
- 네트워크 기능은 전용 하드웨어에서 가상 소프트웨어(NFV)로, 사이드카 프록시로, 커널 eBPF로 내려왔다.

## 대가는 무엇인가 — 소프트웨어화가 치른 값

동시에 새로운 긴장도 남겼다.

QUIC의 헤더 암호화가 네트워크 가시성을 줄였듯(5절), 소프트웨어화는 유연성을 주는 대신 **운영자의 직접 통제와 투명성을 일부 앗아갔다.**

## 다음 세대 — 원문이 내다본 것

다음 세대(eBPF 기반 사이드카리스 메시, AI 트래픽을 위한 엣지 추론)는 이 유연성과 가시성·효율의 균형을 다시 맞추는 작업이 될 것이다.

## 용어 풀이

- **오리진(origin) 서버** — 콘텐츠의 원본이 놓인 서버.
- **엣지(edge) 서버** — 사용자와 물리적으로 가까운 쪽의 서버.
- **flash crowd** — 인기 페이지에 트래픽이 갑자기 몰리는 현상.
- **일관된 해싱(consistent hashing)** — 서버가 추가·제거돼도 재배치되는 키가 최소화되는 매핑 방식.
- **실시간 매핑(real-time mapping)** — DNS 단계에서 위치·네트워크 상태·서버 부하를 종합해 최적 엣지를 고르는 것.
- **캐시 적중 / 캐시 미스** — 캐시에 있어 바로 주는 경우 / 없어서 오리진까지 가야 하는 경우.
- **CDN** — 콘텐츠를 전 세계 엣지 서버에 복제해 가까운 곳에서 응답하는 망. Akamai(1998) 창업, FreeFlow(1999).
- **로드 밸런서(load balancer)** — 들어오는 요청을 여러 백엔드로 분산하는 장치.
- **L4 로드 밸런싱** — TCP/UDP의 IP·포트만 보고 백엔드를 고르는 방식. 연결 하나가 그대로 유지된다.
- **L7 로드 밸런싱** — HTTP를 종료하고 경로·헤더·쿠키·메서드를 읽어 고르는 방식. 두 개의 TCP 연결을 유지한다.
- **리버스 프록시(reverse proxy)** — 클라이언트 요청을 대신 받아 뒤쪽 서버로 전달하는 중개 서버.
- **TLS 종료(TLS termination)** — 암호화된 연결을 중간에서 풀어 내용을 보고 처리하는 것.
- **GSLB** — DNS·Anycast 기반으로 트래픽을 데이터센터·존 단위로 쪼개는 바깥쪽 분산.
- **제어 평면 / 데이터 평면** — 경로를 어떻게 정할지 결정하는 쪽 / 실제 패킷을 전달하는 쪽.
- **SDN(2008, OpenFlow)** — 제어 평면을 장비에서 떼어 중앙 컨트롤러로 올린 네트워킹. Nick McKeown 팀, ONF(2011~).
- **OpenFlow** — 컨트롤러가 스위치에 흐름 규칙을 내려보내는 프로토콜.
- **흐름 테이블(flow table)** — 스위치가 들고 있는 흐름별 처리 규칙 목록.
- **NFV(2012, ETSI ISG NFV)** — 네트워크 기능을 범용 서버 위 소프트웨어(VNF)로 가상화하는 것.
- **어플라이언스(appliance)** — 한 기능 전용 하드웨어 박스.
- **VNF(Virtual Network Function)** — 범용 서버 위 VM/컨테이너가 된 네트워크 기능.
- **VPC(Virtual Private Cloud)** — 사용자가 API로 선언하는 가상 네트워크. AWS가 2009년 도입.
- **VXLAN(RFC 7348, 2014)** — L2 프레임을 UDP에 캡슐화(MAC-in-UDP)해 L3 망을 가로지르는 오버레이 기술.
- **VNI** — VXLAN의 테넌트 식별자. 24비트 = 약 1600만 개(VLAN은 12비트 = 최대 4094개).
- **오버레이 / 언더레이** — 물리 망 위에 덧씌운 가상 망 / 그 아래의 실제 물리 망.
- **테넌트(tenant)** — 한 인프라를 함께 쓰는 고객 하나하나.
- **QUIC(RFC 9000, 2021)** — UDP 위에 새로 구현한 전송 계층. TLS 1.3 내장, 스트림 독립 전달.
- **HTTP/3(RFC 9114, 2022)** — QUIC 위의 HTTP. QPACK과 함께 표준화.
- **head-of-line blocking(HoL)** — 줄의 맨 앞이 막히면 뒤가 전부 대기하는 현상.
- **스트림(stream)** — 한 연결 안에서 독립적으로 흐르는 논리적 통로.
- **혼잡 제어(congestion control)** — 네트워크가 막히지 않도록 전송 속도를 조절하는 장치.
- **유저스페이스(userspace)** — OS 커널 바깥, 보통의 프로그램이 도는 영역.
- **미들박스(middlebox)** — 출발지와 목적지 사이에서 트래픽을 보고 처리하는 장비.
- **폴백(fallback)** — 원하는 방식이 막혔을 때 예비 방식으로 떨어지는 설계.
- **Connection ID / connection migration** — QUIC이 연결을 식별하는 값 / IP가 바뀌어도 연결이 끊기지 않는 성질.
- **CNI(Container Network Interface)** — 컨테이너 런타임과 네트워크 플러그인 사이의 얇은 표준 인터페이스.
- **Pod** — Kubernetes가 컨테이너를 묶어 다루는 가장 작은 단위.
- **서비스 메시 / Istio(2017) / Envoy** — 서비스 간 통신을 사이드카로 빼낸 계층 / Google·IBM·Lyft의 구현 / Lyft가 만든 데이터 평면 프록시.
- **사이드카(sidecar)** — 애플리케이션 옆에 함께 떠서 통신을 대신 처리하는 보조 프로세스.
- **istiod** — Istio의 제어 평면. 정책을 배포하고 CA로 인증서를 발급한다.
- **mTLS(상호 TLS)** — 양쪽이 서로 인증서를 내밀어 상호 인증하는 TLS.
- **서킷 브레이킹** — 뒤쪽 서비스가 계속 실패하면 잠시 호출을 끊는 장치.
- **eBPF(2014, 커널 3.18)** — 검증된 작은 프로그램을 커널 안에 안전하게 주입해 실행하는 기술. 1992년 BPF의 확장판.
- **XDP(2016)** — 드라이버 수준의 고속 처리를 더한 eBPF 기능.
- **Cilium** — eBPF 기반 CNI/네트워킹·보안·관측 플랫폼. 정책을 IP가 아니라 서비스 신원으로 집행한다.
- **컨텍스트 스위칭** — 처리 주체가 바뀔 때 상태를 저장·복원하느라 드는 비용.
- **MEC(2014, ETSI)** — 처음엔 Mobile Edge Computing, 2017년 Multi-access Edge Computing으로 개명.
- **Cloudflare Workers(2017)** — CDN 엣지에서 코드를 실행하는 서버리스.
- **PoP(Point of Presence)** — 사용자와 가까운 곳에 둔 접속 거점.
- **IaC(Infrastructure as Code)** — 인프라를 코드로 선언해 다루는 방식.
