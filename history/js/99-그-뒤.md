## 그 뒤 무슨 일이 있었나

### 1. 언어 — ES2024·ES2025·ES2026 세 판이 나왔다

원문이 적은 규칙은 그대로다 — **"Stage 4에 도달한 제안만 그해 에디션에 실린다"**, 그리고 매년 6~7월 Ecma 총회 비준.
그 규칙대로 세 판이 차례로 비준됐다.

| 판 | ECMA-262 | 비준 |
|----|----------|------|
| ECMAScript 2024 | 15th edition | 2024년 6월 |
| ECMAScript 2025 | 16th edition | 2025년 6월 |
| ECMAScript 2026 | 17th edition | 2026년 6월 30일, 제131차 총회(제네바) |

- 15·16·17판의 발행 시점이 각각 2024년 6월·2025년 6월·2026년 6월이라는 것은 Ecma의 ECMA-262 표준 페이지가 판별로 적어 두고 있다. (출처: [ECMA-262 — Ecma International](https://ecma-international.org/publications-and-standards/standards/ecma-262/), 1차)
- ES2026이 17판이고 2026년 6월 30일 제131차 Ecma 총회에서 승인됐다는 것은 Ecma International의 승인 공지에 적혀 있다.\
  같은 총회에서 ECMA-402(국제화 API)는 **13판 = ECMAScript 2025 판**이 승인됐다 — 본체와 국제화 API는 판 번호가 따로 간다. (출처: [Ecma International approves new standards](https://ecma-international.org/news/ecma-international-approves-new-standards-14/), 1차)
- ES2026 명세 본문 표지에도 "ECMA-262, 17th edition, June 2026"과 "seventeenth edition"이 적혀 있다. (출처: [ECMAScript 2026 Language Specification](https://262.ecma-international.org/17.0/index.html), 1차)

#### ES2024 (15판)에 들어간 것

명세 서문이 직접 열거하는 항목은 이렇다 — ArrayBuffer·SharedArrayBuffer의 **크기 변경과 소유권 이전**, 문자열 집합을 다루는 **정규식 `/v` 플래그**, `Promise.withResolvers`, 데이터를 묶는 `Object.groupBy`·`Map.groupBy`, 공유 메모리 변화를 비동기로 기다리는 `Atomics.waitAsync`, 그리고 문자열이 올바른 유니코드인지 보고 고치는 `String.prototype.isWellFormed`·`toWellFormed`. (출처: [ECMA-262 17판 Introduction](https://262.ecma-international.org/17.0/index.html), 1차)

#### ES2025 (16판)에 들어간 것

명세 서문이 열거하는 항목 — **`Iterator` 전역**과 그에 딸린 정적/프로토타입 메서드, `Set.prototype`의 집합 연산 메서드들, **JSON 모듈 import**와 **import attributes 문법**, `RegExp.escape`, 정규식 안에서 플래그를 켜고 끄는 **modifiers 문법**, `Promise.try`, 그리고 `Float16Array`와 `DataView.prototype.getFloat16`·`setFloat16`·`Math.f16round`. (출처: [ECMA-262 17판 Introduction](https://262.ecma-international.org/17.0/index.html), 1차)

여기서 **import attributes**는 원문 05편이 다룬 ESM 이야기의 뒷이야기다 — 모듈을 들여올 때 그것이 무엇인지(예: JSON) 문법으로 밝히는 장치이고, JSON 모듈이 그 첫 소비자다.

> **import attributes** — `import` 문에 그 모듈의 종류 같은 속성을 덧붙이는 문법.\
> 예: `import data from "./d.json" with { type: "json" };`

#### ES2026 (17판)에 들어간 것

ES2026 명세의 서문에는 아직 "ECMAScript 2026이 무엇을 들여왔다"는 문단이 없다(서문의 판별 설명은 ES2025에서 끝난다).
대신 TC39의 완료 제안 목록이 ES2026 소속으로 적는 7건은 다음과 같고, 7건 모두 17판 본문에 실제로 들어 있는 것을 확인했다.

| 제안 | 본문에 생긴 것 |
|------|---------------|
| Upsert | `Map.prototype.getOrInsert`·`getOrInsertComputed` |
| JSON.parse source text access | `JSON.rawJSON`·`JSON.isRawJSON` |
| Iterator Sequencing | `Iterator.concat` |
| Uint8Array to/from Base64 | `Uint8Array.prototype.toBase64`·`fromBase64` 계열 |
| Math.sumPrecise | `Math.sumPrecise` |
| Error.isError | `Error.isError` |
| Array.fromAsync | `Array.fromAsync` |

(출처: [tc39/proposals — finished-proposals.md](https://github.com/tc39/proposals/blob/main/finished-proposals.md), 1차 / 본문 확인: [ECMA-262 17판](https://262.ecma-international.org/17.0/index.html), 1차)

#### ★ Stage 4인데 아직 안 나온 것 — Temporal·Explicit Resource Management

여기가 이 절에서 가장 헷갈리기 쉬운 자리다.

원문 02편이 적은 대로 **Stage 4는 "완료(Finished)"이지, "이미 릴리스됐다"가 아니다.**
Stage 4에 닿은 제안은 *다음* 연간 스냅샷에 실린다. 그래서 "Stage 4다"와 "ES2026에 있다"는 다른 말이다.

2026-09 시점에 Stage 4이면서 **발행 예정 연도가 2027**로 적힌 제안이 넷 있다.\
괄호 안은 완료 제안 목록의 「Meeting Notes」 열이 "for stage 4"라고 적는 회의다.

- **Temporal** — 날짜·시각 API (**2026-03** 회의)
- **Explicit Resource Management** — `using` / `await using` (2025-05 회의에 "for stage 4" 항목이 있고, 2026-03·2026-05에 후속 보고가 이어진다)
- **Atomics.pause** (**2026-05** 회의)
- **Joint Iteration** (**2026-05** 회의)

**가르는 것은 "몇 년도에 Stage 4가 됐나"가 아니다.**\
같은 목록에서 **Upsert는 2026-01 회의에서 Stage 4가 됐는데 ES2026(17판)에 실렸다** — 위 Temporal(2026-03)보다 두 달 앞선다.\
즉 기준은 **그해 판의 내용이 굳는 시점보다 앞이냐 뒤냐**이지 연도가 아니다.\
"2026년에 Stage 4 = ES2027"로 읽으면 Upsert가 설명되지 않는다.

(출처: [tc39/proposals — finished-proposals.md](https://github.com/tc39/proposals/blob/main/finished-proposals.md), 1차)

ES2026 명세 본문을 실제로 뒤져 확인했다 — `DisposableStack`·`AsyncDisposableStack`·`Atomics.pause`·`Iterator.zip`은 **17판에 없다**.
`Temporal`이라는 글자는 17판에 나오지만, 그것은 날짜 문자열 문법의 기호 이름(`TemporalDecimalFraction` 등)이고 **Temporal API가 아니다**. (출처: [ECMA-262 17판 전문 검색](https://262.ecma-international.org/17.0/index.html), 1차)

> 흔한 오해와 대조 — "Temporal은 Stage 4니까 ES2026에 들어갔겠지"는 성립하지 않는다.\
> 위의 1차 확인이 말하는 것은 이렇다: 둘은 Stage 4이지만 **발행 예정은 ES2027**이고, 17판 본문에 없다.\
> 즉 "표준으로 확정됐다"와 "ES2026 판에 실렸다"는 지금 서로 다른 문장이다.

#### Stage 3 — 아직 표준이 아닌 것들

원문이 "Stage 3부터 Babel로 먼저 쓴다"고 적은 그 칸에는 2026-09 현재 이런 제안들이 있다: Source Phase Imports, Deferring Module Evaluation, Import Text, Iterator Chunking, Iterator Includes, Iterator Join, Error Stack Accessor, RegExp Buffer Boundaries, Await Dictionary, Dynamic Code Brand Checks, Non-extensible Applies to Private, Legacy RegExp features. (출처: [tc39/proposals — README](https://github.com/tc39/proposals), 1차)

**이 목록은 "곧 표준이 된다"는 뜻이 아니다.** 원문이 적은 대로 Stage 3는 구현·피드백 단계이고, 여기서 철회되거나 되돌아가는 일도 있다.

### 2. 런타임 — Node·Deno·Bun

**언어와 런타임은 다르다.** 위 1절은 Ecma TC39가 매년 비준하는 *언어 표준*이고, 이 절은 그 언어를 돌리는 *프로그램*들이다.
결정 주체도(위원회 vs 각 프로젝트) 주기도(연 1회 vs 프로젝트마다) 다르므로 섞어 읽으면 안 된다.

#### Node.js — 26이 Current, 24가 Active LTS

원문 03편은 Node의 버전 번호를 따라가지 않았다. 2026-09-20 현재 공식 릴리스 일정표의 상태는 이렇다.

| 계열 | 상태 | 최초 릴리스 | EOL |
|------|------|-------------|-----|
| 26.x | Current | 2026-05-05 | 2029-04-30 |
| 24.x (Krypton) | Active LTS (2025-10-28~) | 2025-05-06 | 2028-04-30 |
| 22.x (Jod) | Maintenance LTS (2025-10-21~) | 2024-04-24 | 2027-04-30 |
| 20.x (Iron) | End-of-life | 2023-04-18 | 2026-04-30 |

(출처: [nodejs/Release — README](https://github.com/nodejs/Release/blob/main/README.md), 1차. 일정표에는 "Dates are subject to change"가 함께 적혀 있다.)

여기서 언어 절과 **엇갈리는 지점**이 하나 있고, 그게 이 문서에서 가장 조심해야 할 자리다.

- **Node.js 26(2026-05-05)은 Temporal API를 기본 켜짐으로 들여왔다.** 릴리스 노트의 표현 그대로 "The Temporal API is now enabled by default in Node.js 26"이다. (출처: [Node.js 26.0.0 릴리스 노트](https://nodejs.org/en/blog/release/v26.0.0), 1차)
- 그런데 위 1절에서 확인했듯 **Temporal은 ES2026(17판)에 없다** — 발행 예정은 ES2027이다.

즉 **런타임이 언어 표준보다 먼저 켠다.** 원문 02편이 "브라우저·Node·Babel이 Stage 3부터 선제 구현하므로 표준 비준 전에 이미 그 기능을 쓰는 경우가 많다"고 적은 그 구조가, Temporal에서 그대로 재현된 것이다.
"내 Node에서 `Temporal`이 돌아간다"는 "Temporal이 ES2026에 실렸다"를 뜻하지 않는다.

Node 26이 얹은 V8 14.6(Chromium 146)에는 위 ES2026 항목 중 Upsert(`getOrInsert`·`getOrInsertComputed`)와 Iterator sequencing(`Iterator.concat`)이 들어 있다. (출처: [Node.js 26.0.0 릴리스 노트](https://nodejs.org/en/blog/release/v26.0.0), 1차)

한 계열 앞의 Node.js 24(2025-05-06)는 V8 13.6과 함께 `Float16Array`·`using`(Explicit Resource Management)·`RegExp.escape`·`Error.isError`를 들여왔고, npm 11을 묶었으며, 실험 플래그였던 `--experimental-permission`을 `--permission`으로 줄였다. (출처: [Node.js 24.0.0 릴리스 노트](https://nodejs.org/en/blog/release/v24.0.0), 1차)

Node의 TypeScript 지원에는 **되돌림**이 하나 있다 — Node 26은 `--experimental-transform-types` 플래그를 **제거**했다(SEMVER-MAJOR). (출처: [Node.js 26.0.0 릴리스 노트](https://nodejs.org/en/blog/release/v26.0.0), 1차)

#### Deno — 2.0에서 노선을 틀었고, 2.9까지 왔다

원문이 적은 Deno의 초기 노선은 "Node와 비호환"이었다(원문 03편 184행이 Bun의 Node 호환성과 대비해 적는다).
**그 노선이 뒤집혔다.**

- **Deno 2.0**(2024년 10월 9일) — Node.js·npm 하위 호환을 전면에 내세웠다.\
  `package.json`·`node_modules` 네이티브 지원, `deno install`·`deno add`·`deno remove` 명령, 워크스페이스/모노레포 지원이 함께 왔다.\
  공지는 그러면서도 "Deno's goal is not to become a Node clone"이라고 못 박는다. (출처: [Announcing Deno 2](https://deno.com/blog/v2.0), 1차)
- **Deno 2.9**(2026년 6월 25일) — Node.js 26 호환(보고 버전 v26.3.0), npm·pnpm·yarn·Bun 락파일을 그대로 읽는 `deno install`, import attributes를 쓴 CSS 모듈 import, 웹 암호 API의 post-quantum 알고리즘(ML-KEM·ML-DSA·SLH-DSA). (출처: [Deno 2.9](https://deno.com/blog/v2.9), 1차)

> **락파일(lockfile)** — 의존성의 정확한 버전을 고정해 적어 두는 파일.\
> 예: `package-lock.json`·`pnpm-lock.yaml`처럼 도구마다 형식이 달라, 도구를 갈아타면 보통 다시 해석해야 한다.

#### Bun — 0.1에서 1.4까지, 그리고 Zig에서 Rust로

원문은 Bun을 0.1(2022.07)에서 멈춰 세우고, 마지막에 "2026년 들어 Zig에서 Rust로의 재작성을 진행 중"이라고만 덧붙였다.
**그 "진행 중"이 끝났다.**

| 시점 | 사건 |
|------|------|
| 2023-09-08 | Bun 1.0 — "production-ready" 선언 |
| 2025-10-10 | Bun 1.3 — 무설정 프론트엔드 개발, 통합 SQL API, 내장 Redis 클라이언트 |
| 2025-12-02 | Bun이 Anthropic에 인수됨 |
| 2026-05-03 ~ 05-14 | Zig → Rust 이식 작업 |
| 2026-07-08 | Jarred Sumner이 재작성기를 공개 |
| 2026-08-20 | **Bun 1.4 — Rust로 쓰인 첫 릴리스** |

- Bun 1.0은 2023년 9월 8일 공개됐다. (출처: [Bun 1.0](https://bun.com/blog/bun-v1.0), 1차)
- Bun 1.3은 2025년 10월 10일. (출처: [Bun 블로그 목록](https://bun.com/blog), 1차)
- Anthropic 인수는 2025년 12월 2일 Bun 블로그의 "Bun is joining Anthropic"에 적혀 있다. (출처: [Bun 블로그 목록](https://bun.com/blog), 1차)
- 재작성기 본문의 숫자는 이렇다 — 주석을 뺀 Zig 코드 **535,496줄**, 기간 **11일**(5월 3일 시작 → 5월 14일 머지), **머지 포함 6,778 커밋**(머지를 뺀 수는 6,502로 따로 적혀 있다).\
  동기로 적힌 것은 **메모리 안전**이다 — 글은 버그 목록의 상당수가 use-after-free·double-free·에러 경로에서의 해제 누락이고 "In safe Rust, these are compiler errors"라고 적는다.\
  **속도는 동기가 아니라 이식 결과로 따로 보고된다** — 전반적으로 2~5%, `Bun.serve`는 169.6k → 177.7k req/s(+4.8%)다.\
  글은 "Bun v1.3.14 was the last version of Bun written in Zig. Bun v1.4.0 will be the first version of Bun written in Rust"라고 적는다. (출처: [Rewriting Bun in Rust](https://bun.com/blog/bun-in-rust), 1차)
- Bun 1.4는 2026년 8월 20일 릴리스됐다.\
  공지는 "Bun 1.4 adds +1,517 tests from the Node.js test suite"라고 적는다 — **새로 통과한 수가 아니라 매 커밋마다 돌리도록 더한 테스트 수**다. (출처: [Bun 1.4](https://bun.com/blog/bun-v1.4), 1차)

Bun 1.4가 적은 성능 수치는 **그 수치가 실린 표에 물리적으로 붙어 있는 조건과 함께**만 옮긴다.\
Fastify 서버의 최대 메모리 **233MB → 120MB**가 실린 표에 붙은 조건 줄은 하나뿐이다 — "Peak memory under load (1,000,000 requests with 64 connections; 100,000 for Next.js and Vite)".\
즉 **100만 요청·64연결 부하에서 잰 최대 메모리**이고, 하드웨어나 측정 도구를 적은 줄은 그 표에 없다. (출처: [Bun 1.4](https://bun.com/blog/bun-v1.4), 1차)

> 주의 — 233MB는 **Bun 1.3**, 120MB가 **Bun 1.4**다.\
> 즉 이 쌍은 Zig판과 Rust판의 비교다.\
> 다만 **같은 표에는 Node.js 26 열도 있다**(fastify 156MB). 그러니 "Node와 나란히 놓지 않은 표"는 아니다 — 표는 비교하고, 위의 233→120 **쌍만** Bun 내부 비교다.\
> 원문 03편이 적은 "벤치마크 조건에 따라 Node·Deno 대비 수 배"와는 다른 비교다.

> **한 공지 안에서도 절마다 조건 줄이 다르다.** 같은 Bun 1.4 공지의 패키지 설치 벤치마크에는 "Linux x64, EPYC 9R14 … medians of 3, peak memory is the largest of the 3 runs"가, 스트림·바디 벤치마크에는 "AMD EPYC 9R14, Linux x64 … Median of 3 runs, one process per run, peak RSS from `/usr/bin/time -v`"가 따로 붙어 있다.\
> **다른 절의 조건 줄을 이 표의 수치에 옮겨 붙이면 안 된다.** (출처: 같은 글, 1차)

#### "JavaScript" 상표 다툼 — 아직 안 끝났다

원문에는 없는 갈래다.\
Deno가 Oracle의 "JavaScript" 상표 취소를 미국 특허상표청(USPTO)에 청구한 날은 **2024년 11월 22일**이다 — 청구 사실을 알린 글이 "On November 22, 2024, Deno formally filed a petition with the USPTO to cancel Oracle's"라고 적는다. ### 3. 빌드·도구 — Rolldown이 실제로 들어왔고, TypeScript는 Go로 갔다

#### Vite 8 — Rolldown이 기본 번들러가 됐다

원문 05편은 Rolldown을 "Vite의 미래 번들 코어"라고만 적었다. **그 미래가 도착했다.**

- **Vite 8**(2026년 3월 12일)이 Rolldown을 기본 번들러로 싣고 나왔다.\
  공지의 표현은 "Vite 8 ships with Rolldown as its single, unified, Rust-based bundler"다.\
  공지는 Vite의 자리를 "빌드 도구(Vite) · 번들러(Rolldown) · 컴파일러(Oxc)"가 맞물린 **엔드투엔드 툴체인의 입구**로 설명한다. (출처: [Announcing Vite 8](https://vite.dev/blog/announcing-vite8), 1차)
- 그 사이의 릴리스는 Vite 6(2024-11-26) → Vite 7(2025-06-24) → Vite 8(2026-03-12) → Vite 8.1(2026-06-23)이다. (출처: [Vite 블로그 목록](https://vite.dev/blog), 1차)

**여기서 원문의 구도가 하나 완성된다.** 원문은 1세대 파편화(도구마다 별개 + 전부 JS라 느림)가 "네이티브 언어 + 통합" 두 축으로 흡수되는 중이라고 적었는데, Vite 8은 그 두 축을 한 릴리스에 같이 담았다 — 번들러 코어가 Rust로 쓰였고(네이티브), 공지가 감사를 표한 두 전임자(개발 서버의 esbuild, 프로덕션의 Rollup)가 맡던 자리를 하나로 합쳤다(통합).

빌드 시간 수치에 대해서는 조심해야 한다.\
Vite 8 공지가 드는 숫자(Linear 46초 → 6초 등)는 **베타·프리뷰 단계에서 각 회사가 자기 프로젝트를 재 본 값**이고, 공지에 측정 환경·설정이 적혀 있지 않다.\
그래서 이 문서는 그 수치를 "일반적으로 몇 배 빨라진다"로 옮기지 않는다. (출처: [Announcing Vite 8](https://vite.dev/blog/announcing-vite8), 1차)

#### TypeScript 7 — Rust가 아니라 **Go**다

원문 05편은 "Rust 물결"이라는 제목으로 swc·oxc·Turbopack·Rspack·Rolldown·Biome을 묶었다.
**TypeScript 컴파일러는 그 물결에 합류하지 않았다 — Go로 갔다.** 여기서 "빠른 도구 = Rust"라는 오해가 깨진다.

| 판 | 날짜 | 무엇 |
|----|------|------|
| TypeScript 6.0 | 2026-03-23 | JavaScript 코드베이스에 기반한 **마지막** 릴리스 |
| TypeScript 7.0 RC | 2026-06-18 | Go 기반 컴파일러 |
| **TypeScript 7.0** | 2026-07-08 | Go로 만든 네이티브 판 정식 |

- TypeScript 7은 **재작성(rewrite)이 아니라 이식(port)**이다 — 공지는 "the structure and logic of the original codebase"를 유지해 두 컴파일러의 결과가 일치하도록 했다고 적는다. (출처: [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), 2026-07-08, 1차)
- 공지가 드는 전체 빌드 속도 향상은 **7.7배~11.9배**이고, 그 값은 **특정 코드베이스의 전체 빌드**를 잰 것이다 — VS Code 125.7초 → 10.6초(11.9배), Sentry 139.8초 → 15.7초(8.9배), Playwright 12.8초 → 1.47초(8.7배). 메모리는 프로젝트에 따라 6~26% 감소. (출처: 같은 글, 1차)
- **아직 안 끝난 부분이 있다.** TypeScript 7.0에는 **안정된 프로그래매틱 API가 없다.**\
  그래서 TypeScript를 자기 컴파일러 안에 끼워 쓰는 도구들(공지는 Volar를 예로 든다)은 당분간 6.0에 머물러야 한다.\
  API는 7.1에 예정돼 있다. (출처: 같은 글, 1차)

> **프로그래매틱 API(programmatic API)** — 명령줄로 실행하는 대신, 다른 프로그램이 코드로 불러 쓰는 진입점.\
> 예: 에디터의 언어 서버가 `tsc`를 프로세스로 띄우는 대신 컴파일러를 라이브러리처럼 불러 쓰는 경우.

#### Next.js — 16에서 Turbopack이 기본이 됐고, 16.3까지 왔다

원문은 "Next.js 16(2025)부터 기본 번들러"라고만 적었다. 그 릴리스의 실제 날짜와 내용은 이렇다.

- **Next.js 16**(2025년 10월 21일) — Turbopack이 **stable**이 되어 모든 앱의 기본 번들러가 됐고, `use cache`와 PPR을 쓰는 Cache Components 모델, React Compiler 지원(stable), React 19.2 지원이 함께 왔다. Build Adapters API는 **alpha**, Turbopack 파일시스템 캐싱은 **beta**로 표시돼 있다.
- 그 뒤 **16.2**(2026-03-18), **16.3**(2026-08-03)이 나왔다. (출처: [Next.js 블로그 목록](https://nextjs.org/blog), 1차)

### 4. 프레임워크 — React가 Meta를 떠났고, Angular는 Zone.js를 뺐다

#### React 19와 그 뒤

- **React 19**(2024년 12월 5일)에서 Actions·`use`·**Server Components**·`ref`를 그냥 prop으로 받기·문서 메타데이터 지원이 **stable**로 들어갔다.\
  단, 공지는 **Server Components의 구현용 내부 API는 semver를 따르지 않으며 19.x 마이너 사이에서도 깨질 수 있다**고 명시한다 — 프레임워크는 React 버전을 고정하라고 적는다. (출처: [React v19](https://react.dev/blog/2024/12/05/react-19), 1차)
- 이후 **19.2**(2025-10-01), **19.3**(2026-09-09)이 나왔다.\
  2026-09-20 현재 React 20은 없다. (출처: [React 블로그 목록](https://react.dev/blog), 1차)

원문 06편이 "RSC는 서버/클라이언트 경계라는 새 멘탈 모델이 진입 장벽을 높였다"고 적은 반작용에는 **보안 쪽 후속담**도 붙었다.

2025년 12월부터 React Server Components에서 취약점이 잇달아 공지됐다.\
**시작은 CVSS 10.0짜리 무인증 원격 코드 실행이다** — 이 첫 항목을 빼고 뒤의 것들만 세면 사건의 크기를 통째로 잘못 읽는다.

| 2025-12-11 | CVE-2025-55183 | 소스 코드 노출 | 5.3 | 19.0.4 · 19.1.5 · 19.2.4 |

#### React Compiler — "응수하는 중"이 1.0이 됐다

원문은 React Compiler를 "응수하는 중"이라고 적었다. **2025년 10월 7일 v1.0이 나왔다.**

- 빌드 타임에 **자동 메모이제이션**을 하는 컴파일러이고, 조기 반환 뒤에도 조건부로 메모할 수 있다 — 손으로 쓰는 메모이제이션이 못 하는 일이다. React 17 이상과 호환된다.
- 컴파일러 기반 린트 규칙이 `eslint-plugin-react-hooks`의 권장 프리셋에 들어갔다.
- 공지가 적는 수치는 **Meta Quest Store 같은 앱에 적용한 결과로 적힌 값**이다 — 문장은 "The compiler has already shipped in apps like Meta Quest Store. We've seen initial loads and cross-page navigations improve by up to 12%, while certain interactions are more than 2.5× faster"다.\
  즉 **초기 로드·페이지 간 이동이 최대 12%, 일부 상호작용이 2.5배 이상**이고, 공지는 그 값을 어떤 환경에서 어떻게 쟀는지까지는 적지 않는다. (출처: [React Compiler v1.0](https://react.dev/blog/2025/10/07/react-compiler-1), 1차)

#### React Foundation — 소유권이 Meta에서 재단으로 넘어갔다

원문에 없는, 그리고 프레임워크 역사에서는 드문 종류의 사건이다.

**2026년 2월 24일, React·React Native·JSX의 소유권이 Meta에서 React Foundation으로 넘어갔다.** 재단은 Linux Foundation이 호스팅하고, 플래티넘 창립 멤버는 여덟 곳(Amazon·Callstack·Expo·Huawei·Meta·Microsoft·Software Mansion·Vercel), 초대 상임이사는 Seth Webster다. (출처: [The React Foundation](https://react.dev/blog/2026/02/24/the-react-foundation), 1차)

#### Angular — 옵셔널 zoneless가 기본값이 됐다

원문은 Angular signals를 두고 "세분 반응성·옵셔널 zoneless로 이동 중"이라고 적었다.\
**Angular v21부터 zoneless가 기본값이다.**\
공식 가이드의 문장은 "Zoneless is the default in Angular v21+ so you do not need to do anything to enable it"이고, v20에서는 `provideZonelessChangeDetection()`으로 직접 켜야 한다고 적는다. (출처: [Zoneless — Angular](https://angular.dev/guide/zoneless), 1차)

- **v21.0.0은 2025년 11월 19일**에 나왔고, 그 뒤 **v22.0.0이 2026년 6월 3일**에 나왔다 — 2026-09 현재 zoneless 기본값은 두 메이저째 이어지고 있다. (출처: [Angular — Releases](https://angular.dev/reference/releases), 1차)
- **"v21로 올리면 Zone.js가 저절로 빠진다"로 읽으면 안 된다.** 변경 로그의 표현이 갈라져 있다.\
  `angular/angular-cli` 21.0.0에는 "**Applications are zoneless by default**"가 적혀 있다 — **새로 만드는 애플리케이션**이 zoneless로 생성된다는 쪽이다. (출처: [angular/angular-cli — CHANGELOG.md, 21.0.0 (2025-11-19)](https://github.com/angular/angular-cli/blob/main/CHANGELOG.md), 1차)\
  `angular/angular` 21.0.0에는 "**Add migration for zoneless by default**"가 적혀 있다 — **이미 있는 앱**에는 마이그레이션이 따로 준비돼 있다는 쪽이다. (출처: [angular/angular — CHANGELOG.md, 21.0.0 (2025-11-19)](https://github.com/angular/angular/blob/main/CHANGELOG.md), 1차)

> **Zone.js** — 비동기 작업이 끝나는 순간을 가로채서 "이제 화면을 다시 그릴 때"라고 Angular에 알려 주던 라이브러리.\
> 예: `setTimeout`이 끝나면 Zone.js가 그것을 알아채고 변경 감지를 돌렸다 — zoneless는 그 알림을 시그널이 대신한다.

## 아직 안 끝난 것

「정식이 됐다」로 읽히면 안 되는 것들이다.

- **Temporal · Explicit Resource Management(`using`) · Atomics.pause · Joint Iteration** — Stage 4(완료)이지만 **발행 예정 연도는 2027**이다.\
  ES2026(17판) 본문에는 없다.\
  다만 **런타임에는 이미 있다** — Node.js 26은 Temporal을 기본으로 켜고, Node.js 24는 `using`을 들여왔다.\
  "런타임에서 쓸 수 있다"와 "현재 판 표준에 실려 있다"가 지금 갈라져 있다.
- **Stage 3 제안 12건** — Source Phase Imports, Deferring Module Evaluation, Import Text, Iterator Chunking/Includes/Join, Error Stack Accessor, RegExp Buffer Boundaries, Await Dictionary 등. 구현·피드백 단계이고, 표준 편입이 보장된 단계가 아니다.
- **TypeScript 7.0의 프로그래매틱 API** — 아직 없다. 7.1에 **예정**돼 있고, 그때까지 TypeScript를 라이브러리로 끼워 쓰는 도구들은 6.0에 머문다.
- **"JavaScript" 상표 취소 청구** — 사기 주장은 2025-06-18 각하, 일반명칭화·포기 주장은 계속. **2026-09-20 현재 결론은 확인하지 못했다.**
- **Next.js 16의 일부 기능** — Build Adapters API는 **alpha**, Turbopack 파일시스템 캐싱은 **beta**로 표시돼 있다.
- **ES2026 명세의 서문** — 17판 서문에는 아직 "ECMAScript 2026이 무엇을 들여왔다"는 문단이 없다. 이 문서의 ES2026 목록은 TC39 완료 제안 목록과 본문 확인에 근거한 것이다.

## 용어 풀이

본문에서 처음 쓴 말 중, 그 자리에서 풀지 않은 것만 모았다.

> **Stage 4 (Finished)** — TC39 제안 절차의 마지막 단계. "이 제안은 완료됐다"는 뜻이지 "이번 판에 실렸다"는 뜻이 아니다.\
> 예: Temporal은 2026-09 현재 Stage 4이지만 ES2026이 아니라 ES2027 발행 예정이다.

> **연간 스냅샷(yearly snapshot)** — 매년 한 번 그 시점까지 완료된 것을 모아 찍어 내는 판.\
> 예: ES2026(17판)이 2026년의 스냅샷이고, 그 뒤 Stage 4에 닿은 것은 다음 스냅샷으로 간다.

> **LTS (Long-Term Support)** — 오래 고쳐 주기로 약속한 버전 계열.\
> 예: Node.js는 짝수 계열만 LTS로 들어가고, 24.x는 2025-10-28부터 Active LTS다.

> **이식(port) vs 재작성(rewrite)** — 이식은 원래 코드의 구조·논리를 유지한 채 다른 언어로 옮기는 것, 재작성은 설계부터 새로 하는 것.\
> 예: TypeScript 7은 스스로를 Go로의 **이식**이라 부르고, 원본과 결과가 일치하도록 구조를 유지했다고 적는다.

> **일반명칭화(genericness)** — 상표가 그 물건의 일반 이름이 되어 버려 상표로서의 힘을 잃는 것.\
> 예: Deno가 "JavaScript"는 브랜드가 아니라 언어 이름이라며 취소를 청구한 근거 중 하나다.
