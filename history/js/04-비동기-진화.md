> ASCII 도식 7개(그중 2개는 원문 그림을 글자로 옮긴 것)와 「한눈에」의 카페 비유(대응표 포함), 용어 블록의 「예:」, 「용어 풀이」는 원문에 없는 보충이다.

## 한눈에 — 쉽게 말하면

원문이 제목 아래에 적은 한 줄 요약은 이것이다.

> 단 하나의 스레드로 수많은 I/O를 동시에 다뤄야 했던 언어가, 콜백 → Promise → async/await로 *표현*을 진화시키고 이벤트 루프로 *실행*을 정교화하며, 끝내 Web Worker로 진짜 병렬까지 손에 넣은 역사. "무엇이 언제·왜 바뀌었나"를 코드 before/after로 따라간다.

이 문서의 주 비유는 **직원이 한 명뿐인 카페**이고, 본문 흐름에서는 끝까지 같은 대응으로 쓴다.\
다만 용어 블록에서만 잠깐 쓰는 국소 비유(번호표·진동벨·책갈피 등)가 몇 개 더 있다.

| 비유 | 실체 |
|------|------|
| 카운터 직원이 딱 한 명 | JavaScript는 단일 스레드 — 한 번에 하나만 실행한다 |
| 주문을 받아 적고 다음 손님을 받는다 | 완료되면 부를 함수(콜백)를 등록하고 즉시 다음 코드로 간다 |
| 음료를 실제로 만드는 기계 | 호스트(브라우저·Node.js)가 대신 맡는 I/O |
| 다 된 음료가 픽업대에 놓인다 | 완료된 콜백이 큐에 들어간다 |
| 손이 비면 픽업대에서 하나 집어 처리한다 | 스택이 비면 이벤트 루프가 큐에서 하나 꺼낸다 |

- 직원이 한 명인데 음료 한 잔을 **서서 기다리면** 뒤의 손님이 전부 멈춘다.\
  브라우저에서 이건 화면이 얼어붙는다는 뜻이다.
- 그래서 JavaScript는 **기다리지 않기**로 했다.\
  오래 걸리는 일은 기계(호스트)에 맡기고, 끝나면 부를 함수만 등록한 뒤 바로 다음 일로 간다.
- 이 편은 그 "등록하고 떠난다"를 **어떻게 쓰느냐**가 콜백 → Promise → async/await로 바뀐 이야기다.\
  밑에서 돌아가는 기계(이벤트 루프)는 내내 같다.
- 마지막에 딱 하나 진짜로 바뀌는 것이 있다.\
  **Web Worker** — 직원을 한 명 더 고용하는 것, 즉 진짜 병렬이다.

> **비동기(asynchronous)** — 결과를 기다리며 멈춰 서지 않고, 완료됐을 때 할 일을 미리 등록한 뒤 바로 다음 일로 넘어가는 방식.\
> 예: 음료가 나올 때까지 카운터에 서 있지 않고, 바로 다음 손님의 주문을 받는 것.

> **콜백(callback)** — "이 일이 끝나면 이걸 불러 줘"라고 미리 넘겨 두는 함수.\
> 예: 번호표에 적어 둔 "다 되면 이 번호를 부르세요"가 콜백이다.

> **이벤트 루프(event loop)** — 실행할 것이 없어지면 큐에서 다음 할 일을 꺼내 오는, 비동기 실행을 조율하는 심장.\
> 예: 직원이 손이 비는 순간마다 픽업대를 확인하는 습관과 같다.

## 한눈에 보기 (타임라인)

원문의 타임라인 표를 그대로 옮긴다.

| 시기 | 모델 | 핵심 문제 | 무엇이 바뀌었나 |
|------|------|-----------|-----------------|
| ~2009 | **콜백** | 결과를 함수로 넘겨받음 | 비동기를 표현하는 유일한 수단 |
| 2009~ | **콜백 지옥** | 콜백의 콜백의 콜백 | 중첩·에러 전파 불가·역제어가 한계로 노출 |
| ES2015 (2015) | **Promise** | 미래값을 *객체*로 | `.then` 체이닝·`.catch` 단일 에러 경로·평탄화 |
| ES2015 | **제너레이터/이터레이터** | 함수 실행을 *일시정지* | `yield`로 협력형 중단 — async/await의 뿌리 |
| ES2017 (2017) | **async/await** | 비동기를 *동기처럼* | `await`로 콜백·`.then` 제거, `try/catch` 복귀 |
| ES2018 | **async iterator** | 스트림을 `for-await-of`로 | 비동기 시퀀스의 순회 |
| 2012~ | **Web Worker** | 단일 스레드의 CPU 한계 | 별도 스레드 + 메시지 패싱 |
| ES2017 | **SharedArrayBuffer / Atomics** | 스레드 간 공유 메모리 | 진짜 공유 + 원자적 동기화 |

- 원문이 **"실행 모델은 그대로 두고 표현만 바꾼"** 사례라고 부른 것은 **콜백·Promise·async/await** 세 줄이다 — 밑에서 도는 기계(이벤트 루프)는 같다.
- 아래 두 줄(Web Worker · SharedArrayBuffer)은 별도 스레드를 들여오는 자리다 — 원문 요약이 "끝내 Web Worker로 진짜 병렬까지 손에 넣은 역사"라 적은 대목이다.
- 나머지 두 줄(제너레이터/이터레이터 · async iterator)은 원문이 이 분류로 나누어 말하지 않는다. 제너레이터에 대해서는 "async/await의 뿌리"라고만 적는다.

## 시대적 배경 — 왜 단일 스레드인가

*(이 편의 「시대 배경 — 그전에는 어땠나」에 해당한다)*

JavaScript는 브라우저 안에서 태어났다.\
한 페이지의 DOM은 단일 스레드가 소유하는 가변 상태이며, 만약 두 스레드가 동시에 같은 DOM 노드를 수정할 수 있었다면 락·경합·교착이라는 멀티스레드의 모든 고통이 UI 코드에 들어왔을 것이다.\
그래서 언어는 처음부터 **"한 번에 하나의 작업만 실행한다(run-to-completion)"** 는 단일 스레드 모델을 택했다.\
원문의 표현대로, 어떤 함수도 실행 중에 다른 코드에 의해 중간에 끼어들지 않는다는 보장은 공유 상태 동기화를 통째로 없애 준다.

> **run-to-completion** — 한 번 시작한 코드는 끝날 때까지 다른 코드가 끼어들지 못한다는 실행 규칙.\
> 예: 계산 중인 직원의 손을 아무도 중간에 붙잡을 수 없는 것 — 그래서 "지금 중간 상태를 누가 건드렸나"를 걱정할 필요가 없다.

문제는 네트워크 요청·타이머·파일 읽기 같은 I/O다.\
단일 스레드가 응답을 *기다리며 멈추면(blocking)* 그동안 UI는 통째로 얼어붙는다.

```text
같은 작업, 두 가지 방식 (I/O 세 건을 처리한다)

멈추고 기다리면 (blocking)
  요청1 ─ 기다림 ─ 요청2 ─ 기다림 ─ 요청3 ─ 기다림 ─ 화면 갱신
        (이 구간 내내 JS 스레드가 멈춰 있다 = UI가 얼어붙는다)

기다리지 않으면 (비동기)
  요청1 등록 → 요청2 등록 → 요청3 등록 → 다음 코드 계속 실행
        기다리는 일은 호스트(브라우저/Node)가 맡는다
        끝난 것부터 콜백이 큐에 들어오고, 스택이 비면 실행된다
```

- 두 줄의 차이는 **누가 기다리느냐**다. 위는 JS 스레드가, 아래는 호스트가 기다린다.
- 원문이 적은 해법이 아래 줄이다 — "I/O를 운영체제/호스트(브라우저·Node.js)에 맡겨 두고, 완료되면 그때 호출할 함수(콜백)를 등록한 뒤 즉시 다음 일로 넘어간다."
- 요청 세 건은 그림을 위해 늘어놓은 것이고, 원문에 있는 개수는 아니다.

> **블로킹(blocking)** — 결과가 나올 때까지 그 자리에서 멈춰 서 있는 것.\
> 예: 음료가 나올 때까지 카운터 직원이 기계 앞에 서 있는 것 — 그동안 줄은 한 명도 줄지 않는다.

원문의 이벤트 루프 그림을 글자 도식으로 옮기면 이렇다(노드 문구와 방향은 그대로다).

```text
   호출 스택(한 줄)          호스트(브라우저/Node) — 별도 스레드들이 I/O 처리
   +-----------+          +------------------------------------------
   | main()    |          | 타이머 · fetch · fs · DOM 이벤트 ...
   |  fetch()--+--------->| (여기서 실제 대기 — JS 스레드는 안 멈춤)
   +-----------+          +--------------------+---------------------
        ^   스택이 비면                        | 완료된 콜백을 큐에 넣음
        |   큐에서 하나 꺼내 실행              v
        +---------------------------  [ 태스크 큐 / 마이크로태스크 큐 ]
                       이벤트 루프
```

- 왼쪽 박스가 **JS가 실제로 코드를 실행하는 유일한 자리**다 — 한 줄뿐이다.
- 오른쪽 칸이 호스트다. 실제 기다림은 여기서 일어나고, JS 스레드는 멈추지 않는다.
- 아래 큐를 거쳐 왼쪽으로 돌아오는 화살표가 이벤트 루프다.

핵심 계약은 원문이 이렇게 적었다.

> **JavaScript 코드는 절대 멈추지 않는다(스스로 양보하기 전까지). 멈춤은 호스트가 대신하고, JS는 "완료 통보"만 큐로 받는다.**

비동기 문법의 모든 진화는 이 큐에 올라탈 콜백을 *어떻게 쓰느냐*의 진화였다.

## 1단계 — 콜백: 최초의 비동기

*(여기 1단계부터 5단계까지가 이 편의 「무엇이 바뀌었나」다)*

비동기를 표현할 언어 기능이 따로 없던 시절, 답은 단순했다.\
**결과를 받을 함수를 인자로 넘긴다.**\
Node.js는 여기에 관례를 더했다 — 콜백의 첫 인자는 항상 에러(error-first callback)다.

```js
// 콜백 스타일 — 완료되면 호출될 함수를 등록하고 즉시 반환
fs.readFile('/config.json', 'utf8', function (err, data) {
  if (err) {
    // 에러는 throw가 아니라 첫 인자로 "전달"된다 — 비동기 경계를 try/catch가 못 넘는다
    console.error('읽기 실패', err);
    return;
  }
  console.log('내용:', data);
});
console.log('이 줄이 콜백보다 먼저 찍힌다'); // run-to-completion: 동기 코드 먼저
```

> **error-first callback** — 콜백의 첫 인자를 항상 에러 자리로 약속한 Node.js의 관례.\
> 예: 위 코드에서 `err`가 그 자리다 — 그래서 `if (err)`로 에러가 있었는지부터 확인한다.

**왜 try/catch가 안 통하나**를 원문은 이렇게 설명한다.\
`readFile`는 *즉시 반환*하고, 실제 읽기는 한참 뒤 다른 이벤트 루프 틱에서 끝난다.\
그 시점엔 바깥 `try` 블록의 스택은 이미 사라진 지 오래다.\
그래서 비동기 에러는 "던지는" 게 아니라 "인자로 건네주는" 수밖에 없었다 — corpus [[에러-부재-표현]]이 말하는 *예외 vs 값으로서의 에러*의 가장 원시적 형태다.

## 2단계 — 콜백 지옥 (callback hell)

콜백 하나는 멀쩡하다.\
문제는 **여러 비동기 작업을 순서대로** 엮을 때 터진다.\
다음 작업이 이전 결과에 의존하면, 콜백 안에 콜백을 넣는 수밖에 없다.

```js
// before — 콜백 지옥(pyramid of doom): 오른쪽으로 무한히 밀려나는 들여쓰기
getUser(userId, function (err, user) {
  if (err) return handle(err);
  getOrders(user.id, function (err, orders) {
    if (err) return handle(err);              // ← 같은 에러 처리 반복
    getPayment(orders[0].id, function (err, payment) {
      if (err) return handle(err);            // ← 또 반복
      sendReceipt(payment, user.email, function (err, ok) {
        if (err) return handle(err);          // ← 또또 반복
        console.log('완료');
      });
    });
  });
});
```

콜백 지옥의 진짜 병폐는 들여쓰기가 아니라 **세 가지 구조적 결함**이라고 원문은 적는다.

1. **에러 전파 부재** — `if (err) return handle(err)`를 *모든 레벨마다 손으로* 반복해야 한다. 하나라도 빠뜨리면 에러가 조용히 삼켜진다(corpus [[에러-처리-로딩]]의 "에러 삼킴" 안티패턴의 뿌리).
2. **역제어(Inversion of Control)** — 내 콜백을 남의 함수에게 *넘겨주는* 순간, 그 함수가 콜백을 0번 부를지·2번 부를지·동기로 부를지 내가 통제할 수 없다.
3. **합성 불가** — 병렬 실행("셋 다 끝나면")이나 경쟁("먼저 끝난 것")을 표현할 1급 수단이 없어, 카운터 변수를 손으로 굴려야 했다.

> **역제어(Inversion of Control)** — 내가 부를 함수를 남에게 넘겨, 언제·몇 번 불릴지의 결정권이 상대에게 넘어가는 상태.\
> 예: 내 번호표를 남의 가게에 맡겼더니 그쪽이 두 번 부를지 한 번도 안 부를지 내가 못 정하는 것.

이 셋이 "표현의 위기"였고, ES2015의 Promise는 정확히 이 셋을 겨냥했다.

## 3단계 — Promise (ES2015): 미래의 값을 객체로

Promise는 **"아직 없는 값"을 1급 객체로 승격**한다.\
비동기 작업은 이제 콜백을 받는 대신 *Promise를 반환*하고, 그 Promise는 `pending → fulfilled | rejected` 세 상태를 가진 불변의 미래값이다.

> **Promise** — "아직 없는 값"을 지금 손에 쥘 수 있게 만든 객체. `pending → fulfilled | rejected` 세 상태를 갖는다.\
> 예: 음료 대신 먼저 받는 진동벨 — 아직 음료는 없지만, 나중에 음료로 바뀌거나 "품절"로 끝난다.

```js
// after — Promise 체이닝: 중첩이 "평탄한 파이프라인"으로 펴진다
getUser(userId)
  .then(user => getOrders(user.id))        // then이 Promise를 반환하면 평탄화(flatten)
  .then(orders => getPayment(orders[0].id))
  .then(payment => sendReceipt(payment))
  .then(() => console.log('완료'))
  .catch(handle);                          // ← 단 하나의 에러 경로가 위 전부를 받는다
```

같은 네 단계를 두 방식으로 그려 보면 모양이 이렇게 달라진다.

```text
콜백 (before)                       Promise 체이닝 (after)

getUser(                            getUser(userId)
  getOrders(                          .then(getOrders)
    getPayment(                       .then(getPayment)
      sendReceipt(                    .then(sendReceipt)
        완료                          .then(완료)
      )                               .catch(handle)
    )
  )
)

  에러 처리: 네 단계마다 한 줄씩    에러 처리: 맨 아래 .catch 한 줄
```

- 왼쪽의 들여쓰기가 오른쪽에서 **평탄한 파이프라인**으로 펴진다 — 원문이 "pyramid of doom" / "평탄화(flatten)"라 부른 그 차이다.
- 맨 아랫줄이 에러 처리다. 원문의 두 코드블록에서 `if (err) return handle(err)`가 네 번, `.catch(handle)`이 한 번 나온 그대로다.

Promise가 콜백 지옥의 세 결함을 어떻게 푸는가.

- **에러 전파**: 체인 어디서든 reject되면(또는 `.then` 콜백이 throw하면) 가장 가까운 `.catch`로 *건너뛰며* 흐른다 — 동기 코드의 예외 버블링이 비동기에 돌아왔다. `if (err)` 반복이 `.catch` 한 줄로 압축된다.
- **역제어 회복**: Promise는 **한 번만, 단 하나의 상태로 정착(settle)** 한다 — 두 번 resolve해도 무시된다. "콜백을 2번 부르는" 류의 배신이 구조적으로 불가능해진다.
- **합성**: 병렬·경쟁을 정적 메서드로 1급 표현한다.

> **정착(settle)** — Promise가 성공(fulfilled)이든 실패(rejected)든 하나의 상태로 확정되는 것. 한 번 정착하면 다시 바뀌지 않는다.\
> 예: 진동벨이 "음료 나옴" 또는 "품절"로 한 번 울리고 나면, 그 뒤에 또 신호를 보내도 무시되는 것.

```js
// 합성 연산자 — 손으로 굴리던 카운터가 사라진다
const [a, b, c] = await Promise.all([fa(), fb(), fc()]); // 셋 다 성공해야 — 하나라도 실패면 즉시 reject
const first   = await Promise.race([slow(), timeout(3000)]); // 먼저 정착한 것 (타임아웃 패턴)
const results = await Promise.allSettled([fa(), fb()]);   // ES2020: 실패해도 끝까지 — 부분 실패 수집
```

**미묘한 함정 — 평탄화 규칙**을 원문은 이렇게 짚는다.\
`.then`의 콜백이 *값*을 반환하면 다음 `.then`에 그 값이 그대로 오지만, *Promise*를 반환하면 그것이 정착할 때까지 기다렸다가 *내용물*을 넘긴다.\
이 자동 평탄화가 없었다면 `Promise<Promise<Promise<...>>>`라는 새로운 중첩 지옥이 생겼을 것이다.

> **평탄화(flatten)** — `.then`이 Promise를 돌려받으면 그것이 정착하기를 기다렸다가 껍데기를 벗겨 내용물만 다음 단계로 넘기는 규칙.\
> 예: 진동벨을 또 진동벨로 바꿔 받지 않고, 그 벨이 가리키던 음료로 바꿔 받는 것.

## 4단계 — 제너레이터/이터레이터 (ES2015): 함수를 일시정지하다

같은 ES2015가 조용히 들여온 또 하나의 기능이 다음 도약의 *뿌리*가 된다.\
이터레이터는 `{ value, done }`을 내놓는 `next()` 프로토콜이고, **제너레이터(`function*`)는 그 이터레이터를 만드는 함수인데, 결정적으로 `yield`에서 실행을 멈췄다가 재개할 수 있다.**

> **제너레이터(generator, `function*`)** — `yield`에서 실행을 멈췄다가 `next()`가 부르면 그 자리부터 다시 이어 가는 함수.\
> 예: 읽다 만 책에 끼워 둔 책갈피 — 덮었다 펴도 그 줄부터 이어 읽는다.

```js
function* counter() {
  console.log('시작');
  const x = yield 1;   // 여기서 멈춘다 — next()가 다시 부를 때까지
  console.log('받음:', x);
  yield 2;
}
const it = counter();
it.next();      // '시작' 출력, { value: 1, done: false } — yield에서 정지
it.next('hi');  // '받음: hi' 출력, { value: 2, done: false } — yield의 결과로 'hi' 주입
it.next();      // { value: undefined, done: true }
```

핵심은 **양방향 통신**이다.\
`yield`는 값을 *내보내고*, `next(v)`의 인자는 그 `yield` 자리로 값을 *주입*한다.

```text
양방향 통신 — 위 코드가 그대로다

제너레이터 안쪽             바깥쪽 호출자
  console.log('시작')  <--- it.next()로 시작
  yield 1              ---> { value: 1, done: false }   (값을 내보낸다)
       (여기서 정지)
       ^
       |  'hi'         <--- it.next('hi')                (값을 주입한다)
  const x = 'hi'
  console.log('받음:', x)
  yield 2              ---> { value: 2, done: false }
```

- 오른쪽으로 나가는 화살표가 `yield`가 **내보내는** 값이고, 왼쪽으로 들어오는 화살표가 `next(v)`가 **주입하는** 값이다.
- 값 `1`·`'hi'`·`2`는 전부 위 원문 코드에 있는 값 그대로다.

여기서 결정적인 통찰이 나온다 — **`yield`가 "Promise를 내보내고", 그 Promise가 정착하면 결과를 `next()`로 다시 주입하는 러너를 만들면, 비동기 코드를 동기처럼 쓸 수 있다.**\
ES2015~2016 시절 `co` 같은 라이브러리가 정확히 이걸 했다.

```js
// async/await가 나오기 전, 제너레이터 + Promise로 흉내 낸 "동기 같은 비동기"
co(function* () {
  const user    = yield getUser(userId);     // yield가 곧 await의 원형
  const orders  = yield getOrders(user.id);
  return orders;
});
```

ES2017의 async/await는 이 패턴을 **언어 차원으로 흡수**한 것이다 — "async 함수는 본질적으로 제너레이터 + Promise 자동 러너"라는 게 그 정체다.\
그래서 둘의 관계를 이해하면 await가 마법이 아님이 보인다.

## 5단계 — async/await (ES2017): 비동기를 동기처럼

`async` 함수는 항상 Promise를 반환하고, 그 안에서 `await`는 Promise가 정착할 때까지 **함수의 실행을 일시정지**했다가(스레드는 안 멈춘다 — 함수만 멈춘다) 결과를 *반환값처럼* 꺼내 준다.

> **`await`** — Promise가 정착할 때까지 **그 async 함수 안에서만** 다음 줄을 미뤄 두고, 결과를 반환값처럼 받아 이어 가는 연산자.\
> 예: 그 손님에게 번호표를 주고 그 손님 응대만 잠시 접어 두는 것 — 카운터 직원(스레드)은 그동안 다른 손님을 받는다.

```js
// after — async/await: .then 체인이 평범한 위에서 아래로 읽는 코드가 된다
async function checkout(userId) {
  try {
    const user    = await getUser(userId);       // await = "정착할 때까지 이 함수를 멈춰라"
    const orders  = await getOrders(user.id);
    const payment = await getPayment(orders[0].id);
    await sendReceipt(payment, user.email);
    console.log('완료');
  } catch (err) {
    handle(err);   // ← try/catch가 비동기에 완전히 복귀했다
  }
}
```

무엇이 결정적으로 바뀌었나.

- **`try/catch` 복귀** — 콜백 시대에 못 넘던 비동기 경계를, await가 reject를 *throw로 변환*해 줘서 동기 예외 처리가 그대로 통한다. corpus [[에러-처리-로딩]]의 상태 enum(`idle/loading/success/error`)과 만나, `try`에서 error 상태를, 본문에서 success를 세팅하는 표준 패턴이 여기서 나온다.
- **변수 스코프 자연화** — `.then` 체인에서 이전 단계 값을 다음 단계에서 쓰려면 클로저를 중첩해야 했지만, await는 그냥 평범한 `const`라 모두 같은 스코프에 산다.
- **루프·조건문과의 결합** — `for`·`if` 안에서 await를 자연스럽게 쓸 수 있다. `.then`으로는 동적 길이의 순차 실행이 매우 어색했다.

**가장 흔한 함정 — 순차 vs 병렬**: await는 "여기서 멈춘다"이므로, 독립적인 작업을 무심코 await로 줄세우면 *직렬화*되어 느려진다.

```js
// ❌ 느림 — b는 a가 끝난 뒤에야 시작 (불필요한 직렬화, 합산 대기)
const a = await fa();
const b = await fb();

// ✅ 빠름 — 동시에 띄우고 함께 기다림 (Promise.all로 합성)
const [a, b] = await Promise.all([fa(), fb()]);
```

```text
위 두 코드의 시간축 (fa와 fb는 서로 의존하지 않는 작업이다)

줄세우기 (느림)
  fa() 시작 ─────────── fa() 끝
                       fb() 시작 ─────────── fb() 끝
  |<--------------- 합산 대기 --------------->|

Promise.all (빠름)
  fa() 시작 ─────────── fa() 끝
  fb() 시작 ─────────── fb() 끝
  |<----- 함께 기다림 ----->|
```

- 위 칸이 원문의 ❌ 코드, 아래 칸이 ✅ 코드다.
- 차이를 만드는 것은 **시작 시점**이다 — 아래 칸은 둘을 먼저 띄워 놓고 함께 기다린다.
- 가로 길이는 그림을 위한 것이고, 원문에 있는 수치는 아니다.

await는 *표현*을 동기처럼 바꿀 뿐, 비동기의 *의미*까지 지우진 않는다.\
"이 둘이 서로 의존하는가"는 여전히 개발자가 판단해야 한다.

### ES2018 — 비동기 이터레이션

제너레이터와 async가 합쳐져 `async function*`(비동기 제너레이터)와 `for-await-of`가 나왔다.\
페이지네이션·스트림처럼 **"다음 조각을 가져오는 것 자체가 비동기"인 시퀀스**를 동기 루프처럼 순회한다.

```js
async function* pages(url) {
  let next = url;
  while (next) {
    const res = await fetch(next);       // 각 페이지 가져오기가 비동기
    const page = await res.json();
    yield page.items;                    // 한 페이지씩 내보냄
    next = page.nextUrl;
  }
}
for await (const items of pages('/api/orders')) {  // 비동기 시퀀스를 동기 루프처럼
  render(items);
}
```

## 이벤트 루프 상세 — 매크로태스크 vs 마이크로태스크

문법이 아무리 동기처럼 보여도, 실행 순서는 이벤트 루프가 정한다.\
그리고 그 루프에는 **두 종류의 큐**가 있다 — 이것을 모르면 `setTimeout`과 `Promise.then`의 순서를 영영 헷갈린다.

- **태스크(매크로태스크) 큐**: `setTimeout`/`setInterval` 콜백, I/O 완료, DOM 이벤트, `MessageChannel` 등. **루프 한 바퀴에 큐에서 단 하나만** 꺼내 실행한다.
- **마이크로태스크 큐**: `Promise.then/catch/finally` 콜백, `queueMicrotask()`, `await` 이후 재개, `MutationObserver`. **우선순위가 높고, 한 번 비우기 시작하면 완전히 빌 때까지** 모두 실행한다 — 도중에 새로 추가된 마이크로태스크까지 *이번 턴 안에서* 다 처리한다.

> **매크로태스크(태스크)** — 이벤트 루프가 한 바퀴에 **단 하나만** 꺼내 실행하는 일감.\
> 예: `setTimeout` 콜백이 여기 들어간다.

> **마이크로태스크** — 매크로태스크 하나가 끝난 직후, 큐가 **완전히 빌 때까지** 연달아 실행되는 우선순위 높은 일감.\
> 예: `Promise.then` 콜백과 `await` 다음 줄이 여기 들어간다.

원문이 적은 루프의 한 사이클(브라우저 기준)을 글자 도식으로 옮기면 이렇다(문구와 순서는 그대로다).

```text
반복:
  1. 태스크 큐에서 매크로태스크 하나 꺼내 실행 (run-to-completion, 끝까지)
  2. 마이크로태스크 큐를 "완전히" 비운다 (도중 추가분 포함, 빌 때까지)
  3. 필요하면 렌더링/페인트 (스타일·레이아웃·paint)
  4. (다시 1로)
```

- 1번은 **하나만**, 2번은 **전부**다. 그리고 2번이 **다음 1번보다 먼저** 온다 — 이 순서가 아래 출력 순서를 만든다.
- 3번이 화면이 실제로 갱신되는 자리다. 2번이 끝나야 3번이 온다.

이 규칙이 만드는 유명한 출력 순서.

```js
console.log('1 동기');
setTimeout(() => console.log('4 매크로태스크(setTimeout)'), 0);
Promise.resolve().then(() => console.log('3 마이크로태스크(then)'));
console.log('2 동기');

// 출력: 1 동기 → 2 동기 → 3 마이크로태스크 → 4 매크로태스크
// 이유: ① 현재 스크립트(매크로태스크 1개)가 끝까지(1,2) → ② 마이크로태스크 전부(3)
//       → ③ 비로소 다음 매크로태스크(4). setTimeout(…,0)도 then보다 "항상 늦다"
```

**왜 이 구분이 중요한가**를 원문은 두 가지로 든다.

1. `await` 다음 줄은 마이크로태스크라 *항상 같은 사이클의 렌더링보다 먼저* 실행된다 — UI 갱신 타이밍에 직결된다.
2. 마이크로태스크가 끝없이 자신을 재등록하면(`then` 안에서 또 `then`) **렌더링이 영영 안 일어나는 기아(starvation)** 가 생긴다.

**함정 — 기아** — 위 2번이 그것이다.\
마이크로태스크는 "빌 때까지 전부" 실행되므로, 스스로 계속 채워 넣으면 위 사이클의 3번(렌더링)에 영영 도달하지 못한다.\
원문의 처방은 이것이다 — 무거운 반복 작업을 잘게 쪼개 UI에 양보하려면 마이크로태스크가 아니라 매크로태스크(`setTimeout`·`MessageChannel`)나 `scheduler`/`requestIdleCallback`에 실어야 한다.

> **기아(starvation)** — 우선순위 높은 일이 끊이지 않아, 뒤에 있는 일이 영영 차례를 못 받는 상태.\
> 예: 위 사이클에서 2번이 끝나지 않아 3번 렌더링이 오지 않는 것.

원문이 덧붙인 Node.js 주석은 이렇다.

> Node.js는 큐 구조가 조금 다르다(`process.nextTick`이 마이크로태스크보다도 먼저, `setImmediate`·libuv의 phase들). 그러나 "매크로 한 개 → 마이크로 전부"라는 큰 골격은 동일하다.

## 동시성 — 진짜 병렬이 필요할 때

이벤트 루프는 **I/O 동시성**(여러 요청을 동시에 *대기*)을 공짜로 주지만, **CPU 병렬성**은 못 준다.\
단일 스레드에서 무거운 계산(이미지 처리·암호화·대용량 파싱)을 돌리면 그동안 이벤트 루프가 막혀 UI가 얼어붙는다.\
해법은 **별도 스레드 = Web Worker**다.

> **I/O 동시성 / CPU 병렬성** — 여러 건을 동시에 *기다리는* 것 / 여러 계산을 동시에 *실행하는* 것.\
> 예: 음료 여러 잔이 기계에서 동시에 만들어지는 것은 전자, 직원이 두 명이 되어 계산을 나눠 하는 것은 후자다.

```js
// main.js — 무거운 계산을 다른 스레드로 떠넘긴다
const worker = new Worker('crunch.js');
worker.postMessage({ numbers: bigArray });   // 데이터는 "구조화 복제"로 복사되어 전달
worker.onmessage = (e) => console.log('결과:', e.data); // 끝나면 메시지로 회신

// crunch.js (워커 — 독립된 전역·독립된 이벤트 루프, DOM 접근 불가)
onmessage = (e) => {
  const sum = e.data.numbers.reduce((a, b) => a + b, 0); // 메인 스레드를 안 막고 계산
  postMessage(sum);
};
```

Worker는 **메모리를 공유하지 않는다.**\
`postMessage`로 주고받는 데이터는 *구조화 복제(structured clone)*로 **값 복사**되므로, 동시 접근으로 인한 경합 자체가 원천적으로 없다 — 단일 스레드 철학(공유 가변 상태 회피)을 멀티스레드로 확장한 셈이다.

**대가는 무엇인가** — 원문이 적은 복사 비용이다.\
큰 데이터의 복사 비용이 부담이면 `ArrayBuffer`를 **전송(transfer)** 해 소유권만 넘길 수 있다(넘긴 쪽에선 사용 불가가 됨).

> **구조화 복제(structured clone)** — `postMessage`로 건넨 데이터를 **값으로 복사**해 상대 스레드에 주는 방식.\
> 예: 같은 종이를 넘기는 게 아니라 복사본을 떠서 주는 것 — 그래서 둘이 동시에 고쳐도 서로를 망가뜨리지 않는다.

> **전송(transfer)** — 복사하지 않고 `ArrayBuffer`의 소유권만 넘기는 방식. 넘긴 쪽에서는 그 버퍼를 더 못 쓴다.\
> 예: 복사본을 뜨지 않고 원본을 통째로 건네주는 것 — 빠른 대신 내 손에는 남지 않는다.

진짜 공유 메모리가 필요할 때만 **SharedArrayBuffer**를 쓴다 — 같은 메모리 블록을 두 에이전트가 동시에 본다.\
이때부터는 다른 언어의 멀티스레드와 똑같이 **데이터 경합**이 생기므로, 읽기·쓰기를 원자화하는 **Atomics**로 동기화한다.

```text
두 방식의 차이 — 원문이 대비한 축은 "메모리를 공유하나"이다

메시지 패싱 (Web Worker의 기본)
  메인 [ 데이터 ] --복사--> 워커 [ 데이터 사본 ]
  서로 다른 메모리라서 경합 자체가 원천적으로 없다

공유 메모리 (SharedArrayBuffer)
  메인 --+
         +--- [ 같은 메모리 블록 ] ---  두 에이전트가 동시에 본다
  워커 --+
  여기서부터 데이터 경합이 생긴다 → Atomics로 원자화한다
```

- 위 칸이 원문의 "값 복사", 아래 칸이 "같은 메모리 블록을 두 에이전트가 동시에 본다"다.
- 아래 칸에서만 경합이 생긴다는 것이 이 그림의 요점이다.

```js
const sab = new SharedArrayBuffer(4);
const view = new Int32Array(sab);
// main과 worker가 같은 view를 공유 — postMessage(sab)로 버퍼 자체를 보냄

// 비원자적: view[0]++ 은 read-modify-write 3단계라 경합 발생 — corpus [[동시성-제어]]의 그 문제
Atomics.add(view, 0, 1);          // 원자적 증가 — "끼어듦 없이" 완료 보장
Atomics.wait(view, 0, 0);         // 값이 0인 동안 이 스레드를 블록(워커에서만 가능)
Atomics.notify(view, 0, 1);       // 기다리는 스레드를 깨움
```

> **데이터 경합(data race)** — 두 스레드가 같은 값을 동시에 읽고 고쳐 쓰다가 한쪽의 결과가 사라지는 현상.\
> 예: 원문이 든 `view[0]++` — 읽기·더하기·쓰기 3단계 사이에 상대가 끼어들 수 있다.

> **Atomics** — 읽기·수정·쓰기를 "끼어듦 없이" 한 번에 끝내도록 보장하는 연산 모음.\
> 예: 위 코드의 `Atomics.add(view, 0, 1)`이 그 원자적 증가다.

**대가는 무엇인가** — 원문이 적은 대로, 여기서 단일 스레드 세계엔 없던 락·펜싱·경합이 다시 등장한다.\
corpus [[동시성-제어]]가 다루는 "read-modify-write 원자화"가 그대로 JavaScript에 온 것이다.\
그래서 SharedArrayBuffer는 *최후의 수단*이고, 대부분의 동시성은 여전히 **메시지 패싱(복사)** 으로 푸는 것이 권장된다.\
(보안상 Spectre 대응으로 SharedArrayBuffer는 `cross-origin isolation` 헤더가 있어야 활성화된다.)

## corpus와의 연결 — 언제·왜 쓰나

*(이 편에서 「왜 그렇게 갔나 — 남은 선택지」에 가장 가까운 자리다 — 원문의 실무 가이드가 여기 있다)*

이 진화사는 코퍼스의 설계 문서들과 한 축으로 이어진다.

| 이 문서의 도구 | 연결 코퍼스 | 무엇을 보강하나 |
|----------------|-------------|-----------------|
| 콜백/Promise의 에러 전달·`.catch`·`try/catch` | [[에러-처리-로딩]] (frontend) | 비동기는 본질적으로 다상태 — async 본문은 success, `catch`는 error 상태로. "에러 삼킴"의 기원이 콜백 |
| 값으로서의 에러 vs throw | [[에러-부재-표현]] (backend tactical) | error-first 콜백 = 에러를 값으로 넘긴 원시 형태. Promise reject는 그 throw 판본 |
| Promise.all/race·async 합성 | [[동시성-제어]] (backend) | I/O 동시성과 CPU 병렬성의 구분. SharedArrayBuffer는 read-modify-write 경합을 JS로 들여옴 |
| 비동기 제너레이터·스트림 | [[메시징-이벤트-드리븐]] (backend) | "송수신을 시간으로 분리" — `for-await-of`는 그 소비측 순회 |

**언제 무엇을 쓰나(실무 가이드)**:

- **순차 의존 흐름** → `async/await` + `try/catch`. 가장 읽기 쉽다. 기본값.
- **독립 작업 동시 실행** → `Promise.all`(전부 필요) / `allSettled`(부분 실패 허용) / `race`(타임아웃·먼저 끝난 것).
- **저수준 라이브러리·세밀한 제어** → Promise 직접(`new Promise`, 체이닝). 일반 앱 코드에선 지양.
- **CPU 바운드(계산)** → Web Worker(메시지 패싱). UI 블로킹 회피.
- **공유 메모리 고성능** → SharedArrayBuffer + Atomics. 경합 설계를 감당할 수 있을 때만, 최후의 수단.
- **콜백 API(레거시·Node)** → `util.promisify`나 `new Promise`로 감싸 await 세계로 끌어온다.

## 영향과 의의

*(이 편의 「남긴 것 — 오늘 우리가 쓰는 것」에 해당한다)*

아래 네 줄은 원문의 「영향과 의의」 절에 적힌 것이다.

- JavaScript 비동기의 진화는 **"실행 모델은 그대로 두고 표현만 바꾼" 보기 드문 사례**다.\
  콜백·Promise·async/await는 *같은 이벤트 루프 위에서 같은 큐에 콜백을 올리는* 동일한 기계를, 점점 더 사람이 읽기 좋은 문법으로 감싼 것이다 — async/await가 제너레이터+Promise의 문법적 포장이라는 사실이 이를 증명한다.
- 덕분에 개발자는 단일 스레드라는 제약을 *거의 의식하지 않고도* 동기처럼 코드를 쓰면서, 그 밑에서 수천 개의 I/O가 한 스레드로 흐르는 효율을 누린다.
- 동시에 이 모델은 다른 언어 생태계에 깊은 영향을 줬다.\
  Python의 `async/await`, C#의 `async/await`(시기적으론 JS보다 앞섰지만 대중화는 함께), Rust의 `Future`/`.await`, Kotlin 코루틴 모두 "미래값 + 일시정지 문법"이라는 같은 어휘를 공유한다.
- JavaScript는 그중에서도 **단일 스레드 + 이벤트 루프 + 마이크로태스크**라는 가장 순수한 형태로, "동시성은 병렬성이 아니다"라는 명제를 언어 전체로 증명해 낸 사례로 남는다.

## 용어 풀이

- **비동기(asynchronous)** — 기다리며 멈추지 않고, 완료됐을 때 할 일을 등록한 뒤 다음 일로 가는 방식.
- **블로킹(blocking)** — 결과가 나올 때까지 그 자리에서 멈춰 서 있는 것. 단일 스레드에서는 UI가 얼어붙는다.
- **run-to-completion** — 한 번 시작한 코드는 끝날 때까지 다른 코드가 끼어들지 못한다는 실행 규칙.
- **이벤트 루프(event loop)** — 스택이 비면 큐에서 다음 할 일을 꺼내 오는 비동기 실행의 심장.
- **호스트(브라우저·Node.js)** — 실제 I/O 대기를 대신 맡고, 끝나면 콜백을 큐에 넣어 주는 실행 환경.
- **콜백(callback)** — "끝나면 이걸 불러 줘"라고 넘겨 두는 함수.
- **error-first callback** — 콜백의 첫 인자를 항상 에러 자리로 약속한 Node.js 관례.
- **콜백 지옥(callback hell) / pyramid of doom** — 콜백 안에 콜백을 넣어 오른쪽으로 밀려나는 코드 모양.
- **역제어(Inversion of Control)** — 내 콜백이 언제·몇 번 불릴지의 결정권이 상대 함수에 넘어간 상태.
- **Promise** — "아직 없는 값"을 담은 객체. `pending → fulfilled | rejected`.
- **정착(settle)** — 성공이든 실패든 하나의 상태로 한 번만 확정되는 것.
- **평탄화(flatten)** — `.then`이 Promise를 받으면 정착을 기다렸다가 내용물만 다음 단계로 넘기는 규칙.
- **`Promise.all` / `race` / `allSettled`** — 전부 성공해야 하는 합성 / 먼저 정착한 것 / 실패해도 끝까지(ES2020).
- **이터레이터 / 제너레이터(`function*`)** — `{ value, done }`을 내놓는 `next()` 프로토콜 / `yield`에서 멈췄다 재개하는 함수.
- **`yield` / `next(v)`** — 값을 밖으로 내보내는 자리 / 그 자리로 값을 주입하며 재개하는 호출.
- **async 함수 / `await`** — 항상 Promise를 반환하는 함수 / 정착할 때까지 **그 함수 안에서만** 다음 줄을 미루는 연산자.
- **비동기 제너레이터(`async function*`) / `for-await-of`** — 다음 조각을 가져오는 것 자체가 비동기인 시퀀스와 그 순회 문법(ES2018).
- **매크로태스크(태스크) / 마이크로태스크** — 한 바퀴에 하나만 꺼내는 일감 / 큐가 빌 때까지 전부 실행하는 우선순위 높은 일감.
- **기아(starvation)** — 마이크로태스크가 끊이지 않아 렌더링 차례가 영영 오지 않는 상태.
- **Web Worker** — 독립된 전역·독립된 이벤트 루프를 가진 별도 스레드. DOM 접근은 불가.
- **구조화 복제(structured clone) / 전송(transfer)** — `postMessage` 데이터를 값 복사하는 방식 / `ArrayBuffer` 소유권만 넘기는 방식.
- **SharedArrayBuffer** — 두 에이전트가 같은 메모리 블록을 동시에 보는 공유 메모리. `cross-origin isolation` 헤더가 필요하다.
- **데이터 경합(data race) / Atomics** — 동시 read-modify-write로 결과가 어긋나는 현상 / 그것을 끼어듦 없이 끝내는 연산 모음.
- **I/O 동시성 / CPU 병렬성** — 여러 건을 동시에 기다리는 것 / 여러 계산을 동시에 실행하는 것.
