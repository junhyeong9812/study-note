## 한눈에 — 쉽게 말하면

원문이 제목 아래에 적은 한 줄 요약은 이것이다.

> 컴파일러가 데이터 레이스를 막아주는 "두렵지 않은 동시성", 그리고 `Future`·`async/await`가 언제·왜 그런 모양으로 자리 잡았는가

이 문서의 주 비유는 **식당 홀**이고, 끝까지 같은 대응으로 쓴다.\
다만 용어 블록에서만 잠깐 쓰는 국소 비유(열쇠·규격 상자·전화번호 등)가 몇 개 더 있다.

| 비유 | 실체 |
|------|------|
| 종업원 | OS 스레드 |
| 테이블(손님 한 팀) | 동시에 진행되는 작업 하나 = task |
| 주방에 주문을 넣고 기다리는 시간 | I/O 대기 |
| 한 종업원이 한 테이블에 붙어 서 있기 | 스레드-당-연결 모델 |
| 기다리는 동안 다른 테이블로 가기 | `.await` 지점에서 양보(yield) |
| "요리 나왔습니다" 벨 | `Waker` — 준비되면 다시 깨우는 장치 |
| 홀 매니저가 "다음은 이 테이블" 하고 지시 | 실행자(executor) |
| 픽업 창구를 지켜보는 사람 | 리액터(reactor) |
| 여러 종업원이 같이 쓰는 공용 장부 | 여러 스레드가 공유하는 데이터 |
| 장부에 달린 자물쇠 | `Mutex` |
| 가구에 붙은 "넘겨도 됨"·"같이 봐도 됨" 스티커 | `Send`·`Sync` 마커 트레이트 |
| 바닥에 고정해 못 옮기게 하는 것 | `Pin` |

원문은 이 편의 이야기가 **두 갈래로 나뉜다**고 적는다.

```text
[ 갈래 1 — fearless concurrency ]        [ 갈래 2 — async/await ]
+-------------------------------+        +-------------------------------+
| 스레드 사이의 데이터 레이스를 |        | OS 스레드 없이 수십만 개의    |
| 런타임이 아니라 컴파일타임에  |        | 동시 작업을 굴리기 위한       |
| 차단하는 타입 시스템          |        | 무비용(zero-cost) 비동기 모델 |
| (소유권 + Send/Sync)          |        |                               |
+-------------------------------+        +-------------------------------+
        1부에서 다룬다                            2~5부에서 다룬다
```

두 칸은 원문 문장을 그대로 나눠 놓은 것이다.\
원문은 "둘은 별개로 출발했지만, async 코드가 스레드 위에서 안전하게 돌아가려면 결국 `Send`/`Sync`로 묶이며 한 그림이 된다"고 적는다.

> **데이터 레이스(data race)** — 여러 스레드가 같은 데이터에 동시에 접근하는데 그중 최소 하나가 쓰기인 상황.\
> 예: 두 종업원이 같은 장부 칸에 동시에 숫자를 고쳐 적어, 한쪽의 기록이 통째로 사라진다.

> **동시성(concurrency)** — 여러 작업을 번갈아·또는 나란히 진행시키는 것.\
> 예: 종업원 한 명이 세 테이블을 왔다 갔다 하며 동시에 맡는 것도 동시성이다.

## 1부. Fearless Concurrency — 컴파일타임 데이터 레이스 차단

### 왜 "두렵지 않은가"

**무엇이 문제였나** — 원문은 데이터 레이스를 "**런타임에, 그것도 가끔만** 터지는 가장 디버깅하기 어려운 버그"라고 적는다.

가끔만 터진다는 게 왜 최악인지부터 보자.

```text
[ 런타임에 가끔만 터진다 ]              [ 컴파일 단계에서 잡는다 ]
+------------------------------+        +------------------------------+
| 런타임에 터진다              |        | 잘못 쓰면 빌드가 실패한다    |
| 그것도 가끔만 터진다         |        | 통과하면 그 버그는 구조적으로|
| 디버깅이 가장 어렵다         |        | 불가능하다 (unsafe 없이)     |
+------------------------------+        +------------------------------+
 전통적인 멀티스레드 코드                Rust — 소유권/빌림 검사기 + 마커 트레이트 둘
```

이 대비의 결론 — 원문의 표현대로 "컴파일이 되면 데이터 레이스(`unsafe` 없이)는 구조적으로 불가능하다."\
그래서 "두려움 없이" 리팩터링하고 병렬화할 수 있다는 의미에서 *fearless concurrency*라 부른다.

원문이 인용 블록으로 따로 뽑은 핵심은 이것이다.

> 핵심은 별도의 동시성 전용 검사기가 있는 게 아니라, **단일 스레드 안전성을 위해 만든 소유권 규칙이 멀티스레드에도 그대로 확장된다**는 점이다. "공유하려면 불변, 변경하려면 단독 소유"라는 빌림 규칙이 곧 데이터 레이스의 정의("동시 접근 + 최소 하나의 쓰기")를 막는다.

빌림 규칙과 데이터 레이스의 정의를 나란히 놓으면 왜 막히는지가 보인다.

```text
  빌림 규칙                        데이터 레이스의 정의
  "공유하려면 불변,                "동시 접근
   변경하려면 단독 소유"            + 최소 하나의 쓰기"

            이 규칙이  -->  이 정의를 막는다
```

왼쪽은 원문이 따옴표로 묶은 빌림 규칙, 오른쪽은 원문이 따옴표로 묶은 데이터 레이스의 정의다.\
원문은 이 둘을 "빌림 규칙이 곧 데이터 레이스의 정의를 막는다"로 이었다 — 항목끼리 하나씩 짝지은 것은 아니므로, 같은 줄에 놓인 것을 대응 쌍으로 읽지 말 것.

> **빌림(borrow)** — 소유권을 넘기지 않고 값을 잠시 참조로 빌려 쓰는 것.\
> 예: 장부를 가져가지 않고 그 자리에서 들여다보기만 하는 것.

> **컴파일타임 / 런타임** — 프로그램을 빌드하는 시점 / 빌드된 프로그램이 실제로 도는 시점.\
> 예: 컴파일타임에 잡히면 빌드가 실패하고, 런타임에 터지면 사용자가 먼저 본다.

### 두 개의 마커 트레이트: `Send`와 `Sync`

**무엇인가** — 원문은 둘을 이렇게 정의한다.

- **`Send`**: 값의 **소유권을 다른 스레드로 옮겨도** 안전한 타입. (대부분의 타입)
- **`Sync`**: 값의 **참조(`&T`)를 여러 스레드가 공유해도** 안전한 타입. 정의상 `T: Sync` ⟺ `&T: Send`.

둘 다 메서드가 없는 **마커 트레이트**이고, 컴파일러가 **자동 도출**한다(모든 필드가 `Send`면 그 구조체도 `Send`). 즉 개발자가 직접 구현할 일은 거의 없고, 대신 **타입에 이 트레이트가 붙어 있느냐를 컴파일러가 검사**한다. `thread::spawn`에 넘기는 클로저는 `Send`여야 하고, 캡처하는 값도 전부 `Send`여야 한다 — 아니면 컴파일 에러다.

> **마커 트레이트(marker trait)** — 메서드가 하나도 없고, "이 타입은 이런 성질이다"라는 표시 역할만 하는 트레이트.\
> 예: 가구에 붙은 "2인이 들 수 있음" 스티커 — 스티커가 가구를 가볍게 만드는 게 아니라, 이미 그런 가구에 붙는다. `Send`/`Sync`도 컴파일러가 **자동 도출**하는 표시이고, 검사는 그 표시가 붙어 있느냐를 본다.

```rust
use std::thread;
use std::sync::{Arc, Mutex};

fn main() {
    // Arc<Mutex<T>>: 여러 스레드가 공유(Arc) + 안전한 변경(Mutex)
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);     // 참조 카운트 증가 (원자적)
        let handle = thread::spawn(move || {    // move: 소유권을 스레드로 이동
            let mut num = counter.lock().unwrap(); // 락을 잡아야만 내부 접근 가능
            *num += 1;
        });
        handles.push(handle);
    }
    for handle in handles { handle.join().unwrap(); }
    println!("결과: {}", *counter.lock().unwrap()); // 항상 10 (레이스 없음)
}
```

> **`Mutex`(뮤텍스)** — 한 번에 한 스레드만 안을 들여다보게 하는 자물쇠.\
> 예: 공용 장부에 자물쇠를 달아, 열쇠를 쥔 한 사람만 그 순간 적을 수 있게 하는 것.

> **클로저(closure)** — 주변의 값을 붙잡아(capture) 들고 다니는 함수 덩어리.\
> 예: 위 코드의 `move || { ... }`가 `counter`를 붙잡아 새 스레드로 들고 간다.

### `Rc` vs `Arc` — 트레이트가 막아주는 실제 사례

**언제 드러나나** — 같은 "참조 카운트 스마트 포인터"인데도 둘의 운명이 갈리는 곳이 `Send`/`Sync`다.

```rust
use std::rc::Rc;
use std::thread;

let data = Rc::new(5);
let d = Rc::clone(&data);
thread::spawn(move || {       // ❌ 컴파일 에러:
    println!("{}", d);        //    `Rc<i32>` cannot be sent between threads safely
});
```

`Rc<T>`는 참조 카운트를 **비원자적**으로 증감한다 — 두 스레드가 동시에 `clone`/`drop`하면 카운트가 깨져 메모리 안전성이 무너진다. 그래서 `Rc`는 일부러 `Send`도 `Sync`도 아니다(`!Send + !Sync`). 멀티스레드가 필요하면 **원자적 카운트**를 쓰는 `Arc<T>`로 바꿔야 하고, 컴파일러가 그 전환을 강제한다.

```text
[ Rc<T> — 비원자적 카운트 ]            [ Arc<T> — 원자적 카운트 ]
+------------------------------+       +------------------------------+
| 두 스레드가 동시에           |       | 증감이 쪼개지지 않는다       |
| clone/drop 하면              |       |                              |
| 카운트가 깨진다              |       | 그래서 스레드 경계를 넘어도  |
| → 메모리 안전성이 무너진다   |       |   안전하다                   |
|                              |       |                              |
| 그래서 일부러 !Send + !Sync  |       | 대신 원자 연산 비용을 낸다   |
+------------------------------+       +------------------------------+
 단일 스레드에서는 비용을 안 낸다       멀티스레드가 필요하면 이쪽으로
```

이 대비의 결론 — 원문의 표현대로 **"안전한 기본값"이 아니라 "비용을 선택"하게 하는** Rust다운 설계다.\
컴파일러는 잘못된 쪽을 고르지 못하게 막을 뿐, 어느 쪽을 쓸지는 개발자가 고른다.

> **참조 카운트(reference count)** — 이 값을 지금 몇 곳에서 들고 있는지 세어 두었다가, 0이 되면 메모리를 치우는 방식.\
> 예: 열쇠를 몇 개 복사해 줬는지 세어 두고, 전부 반납되면 방을 비우는 것.

> **원자적(atomic)** — 중간에 다른 스레드가 끼어들 수 없게, 쪼개지지 않는 한 덩어리로 수행되는 연산.\
> 예: "숫자를 읽고 1을 더해 다시 쓰는" 세 동작을 한 동작처럼 처리해, 두 사람이 동시에 해도 하나가 묻히지 않는다.

원문의 비교표다.

| 타입 | 카운트 증감 | `Send`/`Sync` | 용도 |
|------|------------|---------------|------|
| `Rc<T>` | 비원자적 | ❌ / ❌ | 단일 스레드 (빠름) |
| `Arc<T>` | 원자적 | ✅ / ✅(T가 Send+Sync면) | 멀티 스레드 공유 |
| `RefCell<T>` | — | ✅ / ❌ | 단일 스레드 내부 가변성 |
| `Mutex<T>` | — | ✅ / ✅(T: Send) | 멀티 스레드 내부 가변성 |

표를 읽는 법 — 네 행을 하나씩 짚어 본다.

- `Rc<T>`는 둘 다 ❌라서 스레드 경계를 아예 못 넘는다.
- `Arc<T>`는 둘 다 ✅인데, 원문이 조건을 달아 둔 쪽은 `Sync`다 — 안에 담긴 `T`가 `Send`+`Sync`일 때다.
- `RefCell<T>`는 `Send`는 ✅인데 `Sync`는 ❌다 — 넘기는 건 되고 여럿이 동시에 공유하는 건 안 된다.
- `Mutex<T>`도 둘 다 ✅인데, 조건이 붙어 있는 쪽은 `Sync`다 — 안에 담긴 `T`가 `Send`일 때다.

## 2부. async의 역사 — `futures` 크레이트에서 `async/await`까지

### 왜 스레드만으로는 부족했나

**무엇이 문제였나** — 원문은 "OS 스레드는 강력하지만 **무겁다**"고 적는다.\
스레드 하나당 수 MB의 스택과 커널 컨텍스트 스위칭 비용이 들어, 동시 연결 수만~수십만 개를 다루는 네트워크 서버에서는 스레드-당-연결 모델이 무너진다(C10k 문제).

```text
[ 스레드-당-연결 ]                      [ 협력적으로 번갈아 진행 ]
+-------------------------------+       +-------------------------------+
| 연결 1 → 종업원 1             |       | 연결 1 ┐                      |
| 연결 2 → 종업원 2             |       | 연결 2 ├→ 종업원 1 이 번갈아  |
|  ...                          |       | 연결 3 ┘  맡는다              |
| 연결 100,000 → 종업원 100,000 |       |                               |
|                               |       | 주방을 기다리는 동안          |
| 종업원 한 명당 수 MB 스택     |       | 다른 테이블로 넘어간다        |
| + 커널 컨텍스트 스위칭 비용   |       |                               |
+-------------------------------+       +-------------------------------+
 동시 연결 수만~수십만 개에서 무너진다   원문의 해법 — 비동기 모델
```

이 대비의 결론 — 원문이 든 해법은 **하나의 스레드가 수많은 작업을 협력적으로(cooperatively) 번갈아 진행**하는 것, 즉 I/O를 기다리는 동안 다른 작업으로 넘어가는 비동기 모델이다.\
왼쪽 칸이 무너지는 조건은 원문이 적은 대로 **동시 연결이 수만~수십만 개일 때**다 — 원문은 연결 수가 적을 때를 다루지 않는다.

남은 문제는 원문의 표현대로 **GC도 런타임 오버헤드도 없이** 이걸 어떻게 표현하느냐였다.

> **비동기(asynchronous)** — 결과가 나올 때까지 그 자리에 붙잡혀 있지 않고, 기다리는 동안 다른 일을 진행하는 방식.\
> 예: 주문을 주방에 넣은 종업원이 요리가 나올 때까지 창구 앞에 서 있지 않고 다른 테이블을 받는 것.

> **C10k 문제** — 한 서버가 동시에 1만 개의 연결을 감당할 수 있는가라는 오래된 과제.\
> 예: 연결 하나마다 종업원을 한 명씩 붙이는 식당이 손님 1만 팀을 받으려 할 때 생기는 문제다.

> **GC(가비지 컬렉터)** — 쓰지 않는 메모리를 런타임이 알아서 찾아 치워 주는 장치.\
> 예: 식당이 문을 연 채로 청소부가 수시로 돌아다니며 빈 그릇을 걷어 가는 것 — 편하지만 그 사람 몫의 비용이 든다.

### `futures` 0.1 (2016) — zero-cost의 씨앗

**언제 나왔나** — 2016년 8월, Aaron Turon과 Alex Crichton이 `futures` 0.1 크레이트를 공개하며 **task/polling 모델**을 제시했다.

핵심은 future를 "콜백을 등록하는 객체"(힙 할당 다발)가 아니라, **실행자가 필요할 때 `poll`로 떠밀어 진행시키는 상태 기계**로 본 것이다.

```text
[ 콜백을 등록하는 객체 ]                [ poll 로 떠미는 상태 기계 ]
+------------------------------+        +------------------------------+
| 콜백 체인                    |        | future 하나가                |
| → 힙 할당이 다발로 생긴다    |        | 단일 상태 기계로 컴파일된다  |
| → 가상 호출을 거친다         |        | → 힙 할당·가상 호출을 없앤다 |
+------------------------------+        +------------------------------+
 원문이 "~가 아니라"로 부정한 쪽         원문이 택한 쪽
```

두 칸은 원문이 "~가 아니라 ~로 본 것이다"로 적은 한 문장을 좌우로 나눠 놓은 것이다.\
원문은 이 모델이 "콜백 체인의 힙 할당과 가상 호출을 없앤다"고 적는다.

이 시기의 코드는 콤비네이터로 future를 조립했다.

```rust
// futures 0.1 시절 — 콤비네이터로 future를 손으로 조립 (콜백 지옥의 타입 버전)
fn load_user(id: u64) -> impl Future<Item = User, Error = Error> {
    fetch_row(id)
        .and_then(|row| parse_user(row))
        .map(|user| user.normalize())
}
```

**왜 async/await가 필요했나** — 콤비네이터 방식은 동작했지만, 분기·루프·에러 전파(`?`)가 들어가면 타입이 폭발하고 가독성이 무너졌다.\
그래서 "명령형 코드처럼 읽히는 비동기"가 필요했다.

> **콤비네이터(combinator)** — 작은 조각을 이어 붙여 더 큰 것을 만드는 함수. 위 코드의 `and_then`·`map`이 그것이다.\
> 예: `A 한 다음 B`를 한 줄로 이어 붙이는 연결 고리.

> **상태 기계(state machine)** — "지금 몇 번째 단계인가"를 상태로 들고 있다가, 떠밀릴 때마다 그 지점부터 이어서 진행하는 구조.\
> 예: 종업원이 테이블마다 "주문 받음 / 주방 대기 중 / 서빙 완료" 중 어디인지 적어 두고, 다시 그 테이블에 갈 때 그 단계부터 이어 하는 것.

### `async/await` 안정화 (2019-11-07, Rust 1.39)

**언제 쓸 수 있게 됐나** — RFC 2592(2018-04)를 거쳐 `std::future::Future`와 `Pin`이 표준 라이브러리에 들어가고, `futures`는 0.3로 개편됐다.\
그리고 **2019년 11월 7일 Rust 1.39.0**에서 `async`/`await` 문법이 안정화됐다.

위의 콤비네이터 코드는 이렇게 바뀐다.

```rust
// Rust 1.39+ — 동기 코드와 거의 같은 모양, 하지만 .await 지점에서 양보(yield)한다
async fn load_user(id: u64) -> Result<User, Error> {
    let row = fetch_row(id).await?;      // I/O 대기 중 다른 작업에 스레드를 양보
    let user = parse_user(row)?;
    Ok(user.normalize())
}
```

세 가지 형태가 함께 안정화됐다:
- **`async fn`** — 호출하면 즉시 실행되지 않고 **`Future`를 반환**한다(게으름, lazy).
- **`async { ... }` / `async move { ... }`** — 클로저처럼 future 리터럴을 만든다.
- **`.await`** — future를 현재 task 안에서 완료까지 떠민다. **`async` 문맥 안에서만** 쓸 수 있다.

> **`.await`** — 그 future가 끝날 때까지 이 task를 이어 나가되, 아직이면 **스레드를 다른 작업에 양보**하는 지점.\
> 예: 주방에 주문을 넣은 종업원이 창구 앞에 멈춰 서 있는 게 아니라, 다른 테이블을 보러 갔다가 요리가 준비되면 그 테이블로 돌아와 이어 하는 것. 위 코드 주석이 적은 "I/O 대기 중 다른 작업에 스레드를 양보"가 바로 이것이다.

> **`Future`** — "나중에 값이 나올 예정인 작업"을 담은 값. 원문 표현으로는 실행자가 `poll`로 떠밀어 진행시키는 상태 기계다.\
> 예: **아직 주방에 넣지 않은** 주문표 — 주문표 자체는 요리가 아니고, 매니저가 떠밀어 넣어야 비로소 진행된다.

원문이 인용 블록으로 따로 뽑은 대목은 이것이다.

> 당시 핵심 팀은 이를 의도적으로 **"MVP(최소 기능 제품)"**라 불렀다. 즉 문법은 안정화하되, 트레이트의 async·스트림·더 나은 진단 등은 이후 과제로 남긴 것이다 — 이 "미완"의 흔적이 5부의 주제다. Niko Matsakis가 강조했듯, 다른 언어와 달리 Rust의 async/await는 **zero-cost 추상화**다(future 하나 = 스택에 박히는 상태 기계, 별도 힙 할당·GC 없음).

> **zero-cost 추상화(무비용 추상화)** — 고수준으로 편하게 쓴 대가를 실행 시간에 따로 치르지 않는 추상화.\
> 예: 위 인용이 든 대로 future 하나가 스택에 박히는 상태 기계로 컴파일되어, 별도 힙 할당도 GC도 붙지 않는 것.

### `async fn`의 게으름 — 흔한 함정

**함정** — `async fn`을 호출하는 것만으로는 **아무 일도 일어나지 않는다.**\
반환된 future를 실행자가 `poll`해야 비로소 코드가 돈다.\
원문은 이것이 다른 언어(즉시 실행되는 Promise/goroutine)와 가장 다른 점이라고 적는다.

```rust
async fn say_hi() { println!("hi"); }

fn main() {
    let fut = say_hi();   // 아무것도 출력 안 됨 — future를 만들기만 함
    // fut를 실행자에 넘겨 .await 하거나 block_on 해야 "hi"가 찍힌다
}
```

초보자가 자주 틀리는 지점이 여기다 — **future는 만들어졌다고 시작되는 물건이 아니다.**

## 3부. `Future`·`Poll`·실행자(executor)의 동작 모델

### `Future` 트레이트의 실제 모양

**무엇인가** — 모든 `async fn`/`async {}`는 컴파일러에 의해 이 트레이트를 구현하는 **익명 상태 기계**로 바뀐다.

```rust
pub trait Future {
    type Output;
    // 실행자가 "진행시켜 봐"라고 떠미는 단 하나의 메서드
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),   // 완료 — 결과 T를 들고 끝남
    Pending,    // 아직 — 준비되면 깨워달라고 Waker를 등록해 둠
}
```

위 코드에서 눈여겨볼 것은 메서드가 `poll` **하나뿐**이라는 점이다(원문 주석이 "단 하나의 메서드"라고 적는다).\
그 하나가 돌려주는 답도 `Ready`와 `Pending` 둘뿐이다.

> **`poll`(폴링)** — 실행자가 future에게 "지금 진행할 수 있나"라고 떠밀어 보는 것.\
> 예: 홀 매니저가 **벨이 울려 대기 줄에 올라온 테이블만** 찾아가 "나갈 준비 됐어요?"라고 물어보는 것과 같다(아래 도식의 "준비된 task를 큐에서 꺼냄"이 그 대기 줄이다). 묻지 않으면 그 테이블은 그대로 멈춰 있다.

### poll–wake 루프 — 협력적 스케줄링의 심장

**무엇이 일어나나** — 실행자(executor)는 task를 `poll`한다.\
future가 **`Poll::Ready`**를 내면 완료, **`Poll::Pending`**을 내면 "아직 준비 안 됐다"는 뜻이다.

이때 중요한 규칙을 원문은 이렇게 적는다 — **`Pending`을 반환하기 전에, future는 자기를 다시 깨워줄 `Waker`를 어딘가(I/O 리액터·타이머)에 등록해 둔다.**\
그래야 실행자가 그 task를 헛되이 반복 poll하지 않고 **잠재워 둘 수 있다.**\
준비가 되면(소켓에 데이터 도착 등) 리액터가 `wake()`를 호출하고, 실행자는 그 task를 다시 큐에 넣어 poll한다.

원문의 mermaid 그림을 글자 도식으로 옮기면 이렇다(노드 문구와 방향은 그대로다).

```text
   실행자(Executor)
   준비된 task를 큐에서 꺼냄   <---------------------+
        |                                           |
        v                                           |
   future.poll(cx)                                  |
        |                                           |
        v                                           |
      결과?                                         |
        |                                           |
        +-- 준비됨 --> Poll::Ready(v)               |
        |              → task 완료                  |
        |                                           |
        +-- 미준비 --> Poll::Pending                |
                       → cx의 Waker를 리액터에 등록 |
                            |                       |
                            v                       |
                       task를 재움                  |
                       (busy-loop 안 함)            |
                                                    |
   리액터(Reactor)                                  |
   OS I/O 이벤트 감시 (epoll/kqueue)                |
        |                                           |
        | "I/O 준비 완료"                           |
        v                                           |
   Waker.wake()                                     |
   → task를 다시 ready 큐로  ----------------------+
```

그림 해설 — 한 단계에 한 문장.

- 실행자가 큐에서 task를 꺼내 `poll`한다.
- 결과가 `Poll::Ready(v)`면 그 task는 완료되고 루프에서 빠진다.
- 결과가 `Poll::Pending`이면 `cx`의 `Waker`를 리액터에 등록하고 task를 재운다 — 원문 노드 문구 그대로 **busy-loop을 하지 않는다**.
- 리액터가 OS I/O 이벤트를 보고 있다가 준비되면 `Waker.wake()`로 task를 다시 ready 큐에 넣는다.
- 오른쪽으로 돌아가는 선이 그 되돌림이다 — 이 그림은 한 번 내려가고 끝나는 절차가 아니라 **루프**다.

원문이 불릿으로 덧붙인 두 가지다.

- **`Context`/`Waker`**: `poll`의 인자 `cx`는 `Waker`를 들고 있다. 이 `Waker`가 "이 task를 다시 깨우는 콜백" — 협력적 스케줄러가 빈 폴링(busy-wait)을 피하는 장치다.
- **상태 기계 변환**: `.await`가 여러 개 있는 `async fn`은 각 `.await` 지점이 상태 기계의 "멈출 수 있는 지점"이 된다. `poll`이 다시 불릴 때마다 **마지막으로 멈춘 지점부터 이어서** 실행된다 — 이것이 스레드 스택 없이 작업을 중단/재개하는 방법이다.

두 번째 불릿의 "멈출 수 있는 지점"을 `async fn` 한 개에 대고 세로로 그리면 이렇다.

```text
async fn 안의 코드            poll 이 불릴 때마다
--------------------          ---------------------
  첫 줄들 실행                 1회차: 여기서 시작
      |
      v
  첫 번째 .await               → 아직이면 Pending, 여기서 멈춘다
      |
      v
  중간 줄들 실행               2회차: 멈췄던 지점부터 이어서
      |
      v
  두 번째 .await               → 아직이면 Pending, 여기서 멈춘다
      |
      v
  마지막 줄들 실행             3회차: 다시 이어서 → Ready
```

그림 해설 — 왼쪽은 코드가 적힌 순서, 오른쪽은 `poll`이 불린 회차다.\
`.await` 지점이 둘이면 멈출 수 있는 지점도 둘이다 — 개수는 그림 안에서 만들어졌다.\
회차 숫자도 그림 안의 예시다 — 한 `.await`에서 준비가 안 돼 `Pending`이 여러 번 날 수도 있으므로, `.await` 하나당 `poll` 한 번이라는 뜻은 아니다.\
스레드 스택을 붙들고 기다리는 게 아니라 "어디서 멈췄는지"만 들고 있기 때문에, 종업원 한 명이 테이블을 여러 개 맡을 수 있다.

> **실행자(executor)** — 준비된 task를 꺼내 `poll`로 떠미는 쪽.\
> 예: "다음은 이 테이블" 하고 지시하는 홀 매니저.

> **리액터(reactor)** — OS의 I/O 이벤트(epoll/kqueue)를 지켜보다가 준비된 것을 알려 주는 쪽.\
> 예: 픽업 창구를 지켜보다가 요리가 나오면 벨을 누르는 사람.

> **`Waker`** — `Pending`을 낸 task를 나중에 다시 깨우기 위해 등록해 두는 콜백.\
> 예: 그 벨 자체 — 누르면 해당 테이블이 다시 매니저의 대기 줄로 들어간다.

## 4부. 왜 런타임을 표준 라이브러리 밖으로 분리했나

### std가 제공하는 것 / 제공하지 않는 것

**무엇이 어디에 있나** — Rust 표준 라이브러리는 비동기의 **언어적 뼈대만** 담는다:

- ✅ **있는 것**: `async`/`await` 문법, `Future`·`Poll` 트레이트, `Pin`, `Context`/`Waker`.
- ❌ **없는 것**: **실행자(executor), 리액터(reactor), task 스폰, 타이머, 비동기 I/O.**

즉 `Future`를 정의할 수는 있어도, 그것을 **실제로 돌릴 엔진은 표준 라이브러리에 없다.** 그래서 async Rust를 쓰려면 거의 항상 외부 **런타임 크레이트**가 필요하다 — 가장 대표적인 것이 **Tokio**, 그리고 (한때 인기였던) **async-std**다.

> **런타임(runtime) 크레이트** — `Future`를 실제로 돌려 주는 엔진을 담은 외부 라이브러리.\
> 예: 주문표(`Future`)를 만드는 방법은 표준에 들어 있지만, 그 주문표를 실제로 돌릴 **홀 매니저와 창구 감시원**은 Tokio 같은 크레이트에서 데려온다.

여기가 초보자가 자주 걸리는 지점이다 — **Rust는 async 런타임을 표준에 두지 않는다.**\
`async fn`을 썼는데 아무 일도 일어나지 않는 까닭 자체는 2부 「`async fn`의 게으름」이 적은 대로 — **반환된 future를 실행자가 `poll` 해야 비로소 코드가 돈다.**

### 왜 일부러 비웠나 — zero-cost와 선택의 자유

**왜 그렇게 갔나** — 원문은 "이건 미완성이 아니라 **설계 결정**이다"라고 못 박는다.\
그 아래 세 가지 이유를 병렬로 든다.

1. **응용마다 최적 실행자가 다르다.** 고성능 네트워크 서버(work-stealing 멀티스레드 실행자)와 임베디드/`no_std` 환경(단일 스레드, 할당 없는 실행자)은 요구가 정반대다. 표준이 하나를 못 박으면 한쪽은 항상 손해다.
2. **zero-cost 철학.** "안 쓰는 것엔 비용을 안 낸다." async를 안 쓰는 프로그램이 스케줄러·리액터를 끌고 다닐 이유가 없다. future는 std에 두되(타입 통일), 무거운 엔진은 선택하게 한다.
3. **빠른 진화.** 런타임을 std 밖에 두면, 안정성 보장에 묶이지 않고 생태계가 빠르게 실험·개선할 수 있다.

원문의 mermaid 그림을 글자 도식으로 옮기면 이렇다(노드 문구와 방향은 그대로다).

```text
   내 async 코드
   (async fn …)
        |
        v
+--------------------------------------+
| 표준 라이브러리 (언어 뼈대 — 통일)   |
|   Future / Poll / Pin                |
|   async · await · Waker              |
+--------------------------------------+
        |            |            |
        v            v            v
+--------------------------------------------------------------+
| 런타임 크레이트 (선택 — 경쟁)                                |
|                                                              |
|  Tokio                  async-std        embassy / smol ...  |
|  work-stealing 실행자   std 닮은 API     임베디드 · 경량     |
|  + I/O 리액터                                                |
|  타이머 · task::spawn                                        |
+--------------------------------------------------------------+
        ^
        |
   "엔진 선택"

   내 async 코드  ····(엔진 선택)····>  런타임 크레이트
   (위 점선 관계를 한 줄로 다시 적은 것이다)
```

그림 해설 — 위 칸과 아래 칸의 부제가 대비의 축이다.\
위는 **통일**(모두가 같은 `Future` 타입을 쓴다), 아래는 **경쟁**(엔진은 골라 쓴다)이다.\
원문 그림에서 내 코드는 `Future`로 실선, 런타임 묶음으로는 점선("엔진 선택")으로 이어진다.

### Tokio vs async-std — 무엇을 골랐나

**무엇이 다른가** — 원문이 든 두 후보다.

- **Tokio**: 사실상의 표준. work-stealing 멀티스레드 실행자, 검증된 비동기 I/O, 방대한 생태계(`hyper`, `tonic`, `axum`). **런타임을 명시적으로 노출**한다(`#[tokio::main]`, `Runtime::new`) — 제어가 세밀한 대신 설정이 보인다.
- **async-std**: 표준 라이브러리와 **거의 같은 API**로 친숙함을 노렸다(런타임을 암묵적으로 숨김). 한때 양대 산맥이었으나, 생태계가 Tokio로 수렴하며 현재는 유지보수 모드에 가깝다.

**대가는 무엇인가** — 원문이 인용 블록으로 뽑은 단점이다.

> 단점도 분명하다. 런타임이 갈리면서 **생태계 파편화**가 생긴다 — Tokio용 라이브러리를 async-std 위에서 그냥 쓰지 못하는 일이 잦다(특히 I/O·타이머처럼 리액터에 묶인 것). "런타임을 고른다"는 자유의 이면이다.

> **생태계 파편화(fragmentation)** — 같은 언어 안에서 서로 호환되지 않는 갈래가 갈라져, 한쪽 라이브러리를 다른 쪽에서 그대로 못 쓰게 되는 현상.\
> 예: 위 인용이 든 대로 Tokio용 라이브러리를 async-std 위에서 그냥 쓰지 못하는 일이 잦은 것.

## 5부. 아직 미완인 영역 — `Pin` 복잡도와 async 트레이트

2019년 안정화가 "MVP"였던 만큼, 거친 모서리가 남아 있다. async Rust를 어렵게 만드는 주범 둘이다.

### `Pin` — 자기참조 상태 기계를 위한 필요악

**무엇이 문제였나** — `async fn`이 상태 기계로 컴파일될 때, 함수 안의 지역 변수가 **같은 함수 안의 다른 값을 참조**하는 경우가 생긴다(자기참조 구조체, self-referential).\
그런데 future는 실행자가 여기저기 옮길(move) 수 있는 값이다 — 만약 옮기면서 메모리 주소가 바뀌면, 그 내부 자기참조 포인터는 **무효한 주소를 가리키게 된다(dangling).**

`Pin<&mut T>`은 "이 값을 메모리에서 **더 이상 옮기지 못하게 고정한다**"는 타입 수준 약속으로 이 문제를 막는다. 그래서 `Future::poll`의 `self`가 `Pin<&mut Self>`인 것이다.

```rust
// 왜 Pin이 필요한가 — async 블록이 만드는 자기참조의 모습(개념)
async fn f() {
    let s = String::from("hi");
    let r = &s;            // r은 같은 future 안의 s를 가리킨다 (자기참조)
    some_io().await;       // 이 지점에서 future가 통째로 move되면 r이 무효해진다
    println!("{r}");       // → Pin이 move를 금지해 이 참조를 지켜준다
}
```

위 코드의 `s`와 `r`을 그림으로 놓으면 이렇다.

```text
[ 고정하지 않으면 ]                     [ Pin 으로 고정하면 ]
+------------------------------+        +------------------------------+
| future 안:                   |        | future 안:                   |
|   s = "hi"                   |        |   s = "hi"                   |
|   r ──> s                    |        |   r ──> s                    |
|                              |        |                              |
| future가 통째로 move 되면    |        | Pin 이 move 를 금지한다      |
|   r 은 옛 주소를 가리킨다    |        |   r 은 계속 s 를 가리킨다    |
|   = 무효(dangling)           |        |                              |
+------------------------------+        +------------------------------+
 위 코드 주석의 "r이 무효해진다"         위 코드 주석의 "이 참조를 지켜준다"
```

두 칸에 등장하는 `s`·`r`·move는 전부 위 코드와 그 주석에 실재하는 것들이다.

**대가는 무엇인가** — 원문은 "문제는 **`Pin`의 사용성**이다"라고 적는다.\
직접 future를 손으로 구현하거나(`Stream`, 수동 `poll`) `Pin`을 다뤄야 할 때, `Pin`/`Unpin`/`pin!`/`Box::pin`의 규칙은 Rust에서 가장 가파른 학습 곡선 중 하나로 꼽힌다.\
평범한 `async/await`만 쓰면 컴파일러가 숨겨주지만, 추상화의 틈이 보이는 순간 복잡도가 새어 나온다.

> **`Pin`** — 그 값을 메모리에서 더 이상 옮기지 못하게 고정한다는 **타입 수준의 약속**.\
> 예: 안쪽 부품끼리 선으로 이어진 장치를 바닥에 볼트로 고정해, 옮기다 선이 끊기는 일을 막는 것.

> **자기참조(self-referential)** — 한 값의 내부가 같은 값의 다른 부분을 가리키고 있는 구조.\
> 예: 위 코드의 `r`이 같은 future 안의 `s`를 가리키는 것.

> **dangling(무효한 참조)** — 가리키던 대상이 옮겨지거나 사라져, 더 이상 유효하지 않은 주소를 가리키는 상태.\
> 예: 이사 간 집 주소로 계속 편지를 보내는 것.

### 트레이트 안의 `async fn` (AFIT) — 2023년에야 절반 해결

**무엇이 문제였나** — 오랫동안 **트레이트 메서드에 `async fn`을 직접 쓸 수 없었다.**\
이유는 `async fn`의 반환 타입이 컴파일러가 만든 **익명 future 타입**이라, 트레이트에 그 타입을 적을 방법이 없었기 때문이다(반환 위치 `impl Trait`가 트레이트에서 안 됐다).

우회책이 `async-trait` 크레이트였다 — 매크로로 반환 타입을 **`Pin<Box<dyn Future + Send>>`로 박싱**해 우회한다.\
**대가는 무엇인가** — 동작하지만 **힙 할당 + 동적 디스패치 비용**을 매 호출마다 낸다(zero-cost가 깨진다).

```rust
// 과거 (async-trait 크레이트) — 매크로가 Pin<Box<dyn Future>>로 박싱
#[async_trait]
trait Repository {
    async fn find(&self, id: u64) -> User;   // 실제론 박싱된 future 반환
}

// 현재 (Rust 1.75+, 2023-12) — 네이티브 async fn in trait, 박싱 없음
trait Repository {
    async fn find(&self, id: u64) -> User;   // RPITIT로 컴파일, 정적 디스패치
}
```

**언제 쓸 수 있게 됐나** — **Rust 1.75(2023-12-21)**에서 트레이트의 `async fn`(AFIT)과 RPITIT(`-> impl Trait` in trait)가 안정화되며 정적 디스패치 경로가 열렸다.

다만 **여전히 남은 제약**이 있어 `async-trait`는 아직 쓰인다:

- **`dyn` 호환 불가**: `async fn`을 가진 트레이트는 아직 `dyn Trait`로 (객체 안전하게) 쓸 수 없다 — 동적 디스패치가 필요하면 여전히 박싱(`async-trait`)이 필요하다.
- **`Send` 경계 전파의 어려움**: 반환 future가 `Send`인지를 트레이트 수준에서 조건부로 표현하기 까다롭다(멀티스레드 실행자는 future가 `Send`여야 한다). auto trait이 async 트레이트 경계를 매끄럽게 흐르지 못한다.

> **박싱(boxing)** — 값을 힙에 담아 두고 포인터로 다루는 것.\
> 예: 크기와 모양이 제각각인 물건을 똑같은 규격 상자에 넣어 창고에 두고, 상자 번호만 들고 다니는 것. 위 코드의 `Pin<Box<dyn Future + Send>>`가 그 상자다.

> **정적 디스패치 / 동적 디스패치** — 어느 함수 본체를 부를지 컴파일 시에 정해 두는 것 / 실행 중에 찾아 가는 것.\
> 예: 전화를 걸기 전에 번호를 종이에 적어 두는 것 / 걸 때마다 안내에 물어 번호를 받는 것.

원문이 이 절 끝에 인용 블록으로 뽑은 정리는 이것이다.

> 이 두 가지(`Pin`의 노출과 async 트레이트의 미완)가 "async Rust는 어렵다"는 평판의 실체다. 문법은 동기 코드처럼 단순해 보이지만, 추상화 아래의 상태 기계·`Pin`·런타임 경계가 특정 상황에서 표면으로 올라온다.

## 영향과 의의

*(이 편의 「남긴 것」에 해당한다)*

Rust 동시성의 유산은 **"안전을 런타임 비용 없이 타입으로 산다"**는 한 문장으로 요약된다.

- **Fearless concurrency**는 GC도 락의 규율(convention)도 아닌 **타입 시스템**으로 데이터 레이스를 컴파일타임에 없앴다. `Send`/`Sync`는 별도 기능이 아니라 소유권 규칙의 자연스러운 확장이며, 그래서 단일 스레드 안전성과 멀티 스레드 안전성이 **같은 검사기**로 보장된다.
- **async/await**는 GC 언어들이 런타임에 얹은 비동기를, Rust는 **컴파일타임 상태 기계 변환**으로 무비용화했다. `Future`를 std에 통일하되 실행자는 밖에 둔 분리 설계는, 고성능 서버부터 `no_std` 임베디드까지 같은 문법을 쓰게 했다 — Tokio 생태계(`axum`, `tonic`, `hyper`)가 그 위에서 번성했다.
- 대가도 분명하다. **런타임 파편화**(Tokio/async-std 비호환), **`Pin`/함수 색깔(async ↔ sync) 문제**, **트레이트 async의 미완**은 여전히 진행형 과제다. 그럼에도 이 모델은 "안전성과 성능은 양자택일"이라는 통념을 깨뜨린 가장 성공적인 사례로 남았다.

## 용어 풀이

- **데이터 레이스** — 여러 스레드가 같은 데이터에 동시 접근하는데 그중 최소 하나가 쓰기인 상황.
- **동시성(concurrency)** — 여러 작업을 번갈아·또는 나란히 진행시키는 것.
- **컴파일타임 / 런타임** — 빌드하는 시점 / 빌드된 프로그램이 도는 시점.
- **빌림(borrow)** — 소유권을 넘기지 않고 참조로 잠시 빌려 쓰는 것.
- **마커 트레이트** — 메서드 없이 "이 타입은 이런 성질이다"를 표시만 하는 트레이트. 컴파일러가 자동 도출한다.
- **`Send` / `Sync`** — 소유권을 다른 스레드로 옮겨도 안전 / 참조를 여러 스레드가 공유해도 안전.
- **`Mutex`** — 한 번에 한 스레드만 안을 만지게 하는 자물쇠.
- **클로저** — 주변 값을 붙잡아 들고 다니는 함수 덩어리.
- **참조 카운트** — 몇 곳에서 들고 있는지 세어 두었다가 0이면 치우는 방식.
- **원자적(atomic)** — 중간에 끼어들 수 없게 쪼개지지 않는 한 덩어리로 수행되는 연산.
- **`Rc` / `Arc`** — 비원자적 카운트(단일 스레드) / 원자적 카운트(멀티 스레드 공유).
- **비동기(asynchronous)** — 기다리는 동안 그 자리에 묶이지 않고 다른 일을 진행하는 방식.
- **C10k 문제** — 한 서버가 동시에 1만 개의 연결을 감당할 수 있는가라는 과제.
- **GC(가비지 컬렉터)** — 쓰지 않는 메모리를 런타임이 알아서 치워 주는 장치.
- **콤비네이터** — `and_then`·`map`처럼 조각을 이어 붙이는 함수.
- **상태 기계** — "지금 몇 번째 단계인가"를 들고 있다가 떠밀릴 때마다 그 지점부터 이어 진행하는 구조.
- **`Future`** — 나중에 값이 나올 예정인 작업. 실행자가 `poll`로 떠밀어야 진행된다.
- **`.await`** — future가 끝날 때까지 이어 가되, 아직이면 스레드를 다른 작업에 양보하는 지점.
- **zero-cost 추상화** — 고수준으로 쓴 대가를 실행 시간에 따로 치르지 않는 추상화.
- **`poll`** — 실행자가 future에게 "지금 진행할 수 있나" 떠밀어 보는 것.
- **`Poll::Ready` / `Poll::Pending`** — 완료(결과를 들고 끝남) / 아직(깨워달라고 `Waker`를 등록해 둠).
- **실행자(executor)** — 준비된 task를 꺼내 `poll`로 떠미는 쪽.
- **리액터(reactor)** — OS I/O 이벤트(epoll/kqueue)를 지켜보다 준비된 것을 알리는 쪽.
- **`Waker`** — `Pending`을 낸 task를 나중에 다시 깨우기 위해 등록해 두는 콜백.
- **busy-wait(빈 폴링)** — 준비됐는지 계속 물어보며 CPU를 헛되이 태우는 대기.
- **런타임 크레이트** — `Future`를 실제로 돌릴 엔진을 담은 외부 라이브러리(Tokio·async-std 등).
- **생태계 파편화** — 호환되지 않는 갈래가 갈라져 한쪽 라이브러리를 다른 쪽에서 못 쓰게 되는 현상.
- **`Pin`** — 그 값을 메모리에서 더 이상 옮기지 못하게 고정한다는 타입 수준 약속.
- **자기참조(self-referential)** — 한 값의 내부가 같은 값의 다른 부분을 가리키는 구조.
- **dangling** — 가리키던 대상이 옮겨지거나 사라져 무효해진 참조.
- **박싱(boxing)** — 값을 힙에 담아 두고 포인터로 다루는 것.
- **정적 / 동적 디스패치** — 어느 본체를 부를지 컴파일 시에 정함 / 실행 중에 찾아감.
- **함수 색깔(async ↔ sync)** — `.await`는 `async` 문맥 안에서만 쓸 수 있어서, 한쪽을 쓰기 시작하면 그것을 부르는 사슬까지 같은 쪽으로 물드는 문제. **원문이 「영향과 의의」에서 설명 없이 부른 용어**이고, 이 한 줄은 재서술자가 붙인 풀이다.
- **AFIT / RPITIT** — 트레이트 안의 `async fn` / 트레이트 반환 위치의 `impl Trait`. Rust 1.75에서 안정화됐다.
