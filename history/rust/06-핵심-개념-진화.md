> 원본: `~/project/rust-history/06-핵심-개념-진화.md` — 이 문서는 그 내용을 초보자용으로 다시 쓴 것이다(2026-09-19).\
> 연도·인명·버전·RFC 번호·논문명·코드·표는 원문 그대로다.\
> ASCII 도식 13개와 「한눈에」의 「싸고·빠르고·좋게」 비유, 용어 블록의 「예:」, 「용어 풀이」는 원문에 없는 보충이다.\

## 한눈에 — 쉽게 말하면

원문이 제목 아래에 적은 한 줄 요약은 이것이다.

> 트레이트·제네릭·매크로·에러 처리·패턴 매칭·unsafe — Rust의 핵심 개념들은 따로 발명된 것이 아니라, **"고수준 표현력을 런타임 비용 0으로, 메모리 안전을 포기하지 않고 어떻게 얻을 것인가"** 라는 단 하나의 질문에 대한 서로 다른 답이다. 이 문서는 그 답들이 어떻게·왜 지금의 모습이 되었는지를 추적한다.

**개념사 = "무엇이 추가됐나"가 아니라 "왜 그 모양이어야 했나".**

- 원문이 「들어가며」에서 세운 대비축은 이것이다 — **버전별 변경 이력(릴리스 노트)이 "무엇이 추가됐나"를 본다면, 개념사는 "왜 그 모양이어야 했나"를 본다.**
- 흔히 하는 말로 **"싸고·빠르고·좋게 — 셋 중 둘만 고르시오"**가 있다.\
  원문이 세운 축도 같은 모양의 삼각형이고, 대부분의 언어는 실제로 하나를 희생한다.\
  (이 비유는 여기서 한 번만 쓴다 — 나머지 비유는 용어 블록 안의 국소 비유다.)
- Rust의 모든 핵심 개념은 원문의 표현대로 **"이 셋을 동시에 쥐겠다"는 고집의 산물**이다.

원문이 든 축과, 다른 언어들이 무엇을 희생했는지를 나란히 놓으면 이렇다.

```text
        표현력 ↔ 비용 ↔ 안전의 삼각형
        대부분의 언어는 이 셋 중 하나를 희생한다

  C            안전을 포기한다
  Java/Go      GC와 런타임 비용을 받아들인다
  Haskell      추상화를 위해 런타임 표현(박싱·지연 평가)을 감수한다
  ------------------------------------------------------
  Rust         "이 셋을 동시에 쥐겠다"
               → 그 고집의 이름이 zero-cost abstraction (§7)
```

세 줄은 원문 「들어가며」가 병렬로 든 세 예를 그대로 옮긴 것이고, 순위를 매긴 것이 아니다.\
마지막 줄의 화살표 하나는 원문의 "그 고집의 이름이 마지막 절에서 다룰 zero-cost abstraction이다"라는 한 문장에 대응한다.

> **개념사** — 제품이 아니라 그 제품들이 공유하는 장치와 아이디어의 계보.\
> 예: "Rust 1.x에 무엇이 추가됐나"가 아니라 "왜 트레이트가 지금 모양이어야 했나"를 따라가는 것.

> **런타임 비용** — 프로그램이 실제로 도는 동안 추가로 드는 시간·메모리.\
> 예: 값을 힙에 담아 두고 포인터를 한 번 더 따라가는 것, 실행 중에 어느 함수를 부를지 표를 뒤지는 것.

## 들어가며 — 왜 "개념사"인가

버전별 변경 이력(릴리스 노트)이 "무엇이 추가됐나"를 본다면, 개념사는 "왜 그 모양이어야 했나"를 본다. Rust는 2015년 1.0 이전에 문법과 의미를 수없이 갈아엎으며 자신의 정체성을 찾아갔다. 가비지 컬렉터 기반 `@T`(managed pointer) 문법을 버렸고, Erlang식 경량 태스크와 `fail!`을 버렸으며, 트레이트 객체 문법을 두 번 바꿨다. 이 폐기와 재설계의 궤적을 따라가면, 개별 기능 뒤에 일관된 설계 축이 보인다.

그 축은 **표현력 ↔ 비용 ↔ 안전의 삼각형**이다. 대부분의 언어는 이 셋 중 하나를 희생한다. C는 안전을 포기하고, Java/Go는 GC와 런타임 비용을 받아들이며, Haskell은 추상화를 위해 런타임 표현(박싱·지연 평가)을 감수한다. Rust의 모든 핵심 개념은 "이 셋을 동시에 쥐겠다"는 고집의 산물이다. 그 고집의 이름이 마지막 절에서 다룰 **zero-cost abstraction**이다.

아래 7개 개념을 각각 "언제(역사적 분기점)·왜(해결하려던 문제)"로 읽는다.

*이 문단이 든 폐기 목록은 뒤 절에서 다시 나온다 — `@T`/`@Trait` 계열의 sigil 문법은 §1(트레이트 객체 문법의 진화), `fail!`과 경량 태스크는 §4(에러 처리)에서 이어 읽는다.*

## 1. 트레이트 — 인터페이스와 제네릭 제약의 통합

### 언제·왜

Rust의 트레이트는 Java의 인터페이스가 아니라 **Haskell의 타입클래스(typeclass)** 에서 왔다. 이 계보가 중요하다. 인터페이스는 "이 클래스는 이 메서드들을 가진다"는 *명목적(nominal) 상속*의 도구지만, 타입클래스는 "이 타입은 이 동작을 만족한다"는 *제약(constraint)* 의 도구다. 트레이트는 이 두 역할 — **동적 디스패치용 인터페이스**와 **제네릭 경계(bound)** — 를 하나의 개념으로 통합했다.

```text
[ 인터페이스 — 명목적 상속의 도구 ]     [ 타입클래스 — 제약의 도구 ]
+-------------------------------+       +-------------------------------+
| "이 클래스는 이 메서드들을    |       | "이 타입은 이 동작을          |
|  가진다"                      |       |  만족한다"                    |
+-------------------------------+       +-------------------------------+
 원문이 "~가 아니라"로 부정한 쪽         원문이 트레이트의 계보로 든 쪽
```

두 칸의 문구는 원문의 한 문장을 좌우로 나눠 놓은 것이다.\
원문은 트레이트가 **동적 디스패치용 인터페이스**와 **제네릭 경계(bound)** 라는 두 역할을 하나의 개념으로 통합했다고 적는다.

**핵심 결정** — "트레이트 구현을 타입 정의와 분리"한 것이다. 내가 만들지 않은 타입(`i32`)에 내가 만들지 않은 동작을 붙일 수 있고(coherence 규칙 안에서), 이는 상속 기반 인터페이스로는 불가능하다.

```rust
// 트레이트 = 공유 동작의 명세
trait Summary {
    fn summarize(&self) -> String;

    // 기본 구현 (default method) — Java 8 default와 같은 동기
    fn preview(&self) -> String {
        format!("{}...", &self.summarize()[..10.min(self.summarize().len())])
    }
}

struct Article { title: String, body: String }

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("{}: {}", self.title, self.body)
    }
}
```

위 코드에서 `struct Article { … }`(타입 정의)과 `impl Summary for Article`(트레이트 구현)이 **따로 적혀 있다**는 점이 그 분리다.

> **트레이트(trait)** — "이 타입은 이런 동작을 할 수 있다"를 적어 둔 명세.\
> 예: 위 코드의 `Summary` — `impl Summary for …`를 적어 준 타입은 무엇이든 이 명세를 만족한다.

> **제네릭 경계(bound)** — 제네릭 타입에 "이 트레이트를 만족하는 타입만 받는다"고 거는 조건.\
> 예: 아래 코드의 `fn notify<T: Summary>(...)`에서 `T: Summary` 부분.

### 두 얼굴 — 제네릭 경계(정적) vs 트레이트 객체(동적)

**무엇이 갈리나** — 같은 트레이트가 두 방식으로 쓰인다. 이 분기가 Rust 디스패치 모델의 핵심이다.

```rust
// (A) 제네릭 경계 — 정적 디스패치. 타입마다 코드가 특수화(모노모피제이션)된다.
fn notify<T: Summary>(item: &T) {
    println!("속보! {}", item.summarize());
}
// 동의어: fn notify(item: &impl Summary)   (impl Trait, 1.26 안정화)

// (B) 트레이트 객체 — 동적 디스패치. vtable을 통해 런타임에 메서드를 찾는다.
fn notify_all(items: &[Box<dyn Summary>]) {
    for item in items {
        println!("속보! {}", item.summarize());
    }
}
```

위 코드의 (A)와 (B)는 같은 `summarize`를 부르지만, **어느 본체를 부를지 정하는 시점**이 다르다 — (B)는 위 주석 그대로 "vtable을 통해 런타임에 메서드를 찾는다"이고, (A)의 시점은 §2의 표가 "컴파일 시 (모노모피제이션)"으로 적는다.

> **vtable(가상 함수 표)** — "이 값의 실제 타입에서 이 메서드는 어디 있나"를 적어 둔 표.\
> 예: 실행 중에 그 표를 한 번 뒤져 주소를 찾아 부른다 — 그래서 호출이 한 단계 더 든다.

### 트레이트 객체 문법의 진화 — `~Trait` → `Box<Trait>` → `Box<dyn Trait>`

**무엇이 바뀌었나** — 이 문법은 Rust 역사상 가장 많이 바뀐 표면 중 하나다.

- **1.0 이전**: `~Trait`(소유 박스), `@Trait`(GC 관리 포인터) 같은 sigil 문법. 포인터 종류가 문법에 박혀 있었다.
- **1.0**: sigil이 사라지고 `Box<Trait>`, `&Trait`로 정리됐다. 그런데 여기서 문제가 생겼다. `Box<Foo>`에서 `Foo`가 트레이트인지 타입인지가 **문맥에만 의존**해 베테랑조차 헷갈렸고, "트레이트 객체가 기본값"이라는 잘못된 인상을 줬다.
- **1.27 (RFC 2113)**: `dyn` 키워드 도입. `Box<dyn Summary>`, `&dyn Summary`. `dyn`은 "이 값의 실제 타입은 런타임에야 알 수 있다(dynamically)"를 명시한다. 정적 디스패치의 `impl Trait`와 동적 디스패치의 `dyn Trait`가 키워드 차원에서 대칭을 이루게 되었다 — 둘 다 중요한 선택이며 어느 쪽도 "그냥 기본값"이 아니라는 신호다.

세 단계를 세로로 놓으면 이렇다.

```text
1.0 이전    ~Trait (소유 박스) · @Trait (GC 관리 포인터)
            포인터 종류가 문법에 박혀 있었다
   →
1.0         Box<Trait> · &Trait
            Foo 가 트레이트인지 타입인지 문맥에만 의존해 헷갈렸다
   →
1.27        Box<dyn Summary> · &dyn Summary   (RFC 2113)
            "실제 타입은 런타임에야 알 수 있다"를 명시한다
```

그림 해설 — 위 불릿 셋을 그대로 세로로 옮긴 것이고, 화살표 둘은 원문 절 제목의 화살표 둘에 대응한다.\
각 칸 아래 줄은 그 단계에 대해 원문이 적은 문제 또는 의미다.

```rust
// 옛 문법 (1.0~): 경고 후 폐지 수순
let x: Box<Summary> = Box::new(article);
// 현대 문법 (1.27+): dyn으로 동적 디스패치를 명시
let x: Box<dyn Summary> = Box::new(article);
```

원문이 인용 블록으로 뽑은 교훈은 이것이다.

> 교훈: Rust는 "문법이 의미의 비용을 숨기면 바꾼다." `dyn`은 단 세 글자지만, "동적 디스패치는 공짜가 아니다(vtable 간접 호출)"를 코드에 새긴 설계 결정이다.

## 2. 제네릭과 모노모피제이션 — 추상화의 런타임 비용 0

### 언제·왜

**무엇이 새로운가** — 제네릭 자체는 새롭지 않다. 새로운 것은 **구현 전략**이다. 같은 "제네릭"이라도:

- **Java/C# (타입 소거 또는 박싱)**: `List<Integer>`는 런타임에 `List<Object>`로 소거되고, 원시 타입은 박싱된다 → 간접 비용.
- **C++ 템플릿**: 타입마다 코드를 복제(특수화)한다 → 비용 0이지만 제약이 약해 에러 메시지가 난해(SFINAE 지옥).
- **Rust 모노모피제이션**: C++처럼 타입마다 코드를 특수화하되, **트레이트 경계로 제약을 미리 검사**한다. 비용 0 + 명확한 에러.

"모노모피제이션(monomorphization)"은 컴파일 시 제네릭 함수를 *실제로 사용된 구체 타입마다* 별도의 기계어 함수로 펼치는 것이다.

```rust
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest { largest = item; }
    }
    largest
}

let _ = largest(&[1, 5, 3]);          // i32 버전 생성
let _ = largest(&['y', 'm', 'a']);    // char 버전 생성
```

컴파일러는 위 호출을 보고 내부적으로 `largest_i32`, `largest_char` 두 개의 구체 함수를 생성한다. 호출부는 일반 함수 호출과 동일 — 가상 디스패치도, 박싱도 없다. 인라이닝까지 더해지면 "추상화를 썼다는 사실"이 기계어에서 완전히 사라진다.

```text
  내가 쓴 코드                       컴파일러가 만든 것
  ------------------------           --------------------------
  fn largest<T: PartialOrd>          largest_i32   ← largest(&[1, 5, 3])
                                     largest_char  ← largest(&['y', 'm', 'a'])
  (제네릭 함수 하나)                 (구체 함수 둘)

  호출부는 일반 함수 호출과 동일 — 가상 디스패치도, 박싱도 없다
```

그림 해설 — 왼쪽은 원문 코드의 제네릭 함수 하나, 오른쪽은 원문 문장이 든 두 개의 구체 함수다.\
오른쪽 두 줄의 근거는 원문 코드 주석의 "i32 버전 생성"·"char 버전 생성" 두 줄이다 — 개수는 그림 안에서 만들어졌다.

> **모노모피제이션(monomorphization)** — 제네릭 함수를 실제로 쓰인 구체 타입마다 별도 기계어 함수로 펼치는 것.\
> 예: 위 그림처럼 `largest` 하나가 `largest_i32`와 `largest_char` 둘로 펼쳐지는 것.

> **인라이닝(inlining)** — 함수를 부르는 대신 그 본문을 호출 자리에 그대로 펴 넣는 최적화.\
> 예: 호출이라는 절차 자체가 사라져, 원문 표현대로 "추상화를 썼다는 사실"이 기계어에서 안 보이게 된다.

### 트레이드오프 — 그래서 `dyn`이 존재한다

**대가는 무엇인가** — 모노모피제이션은 공짜가 아니다. 타입이 N개면 코드도 N벌 → **바이너리 비대(code bloat)** 와 컴파일 시간 증가.\
그래서 동적 디스패치(`dyn Trait`)가 보완재로 존재한다.

| 축 | 정적 디스패치 (`impl`/제네릭) | 동적 디스패치 (`dyn`) |
|----|------------------------------|------------------------|
| 디스패치 시점 | 컴파일 시 (모노모피제이션) | 런타임 (vtable 간접 호출) |
| 런타임 비용 | 0 (인라이닝 가능) | vtable 조회 1회 + 인라이닝 불가 |
| 코드 크기 | 타입마다 복제 (bloat) | 1벌 공유 |
| 이종(heterogeneous) 컬렉션 | 불가 | 가능 (`Vec<Box<dyn T>>`) |
| 적합 신호 | 핫 패스·소수 타입 | 다수/미지 타입·플러그인·바이너리 절약 |

표를 읽는 법 — 다섯 행을 하나씩 짚어 본다.

- 디스패치 시점: 컴파일 시에 정해지느냐, 실행 중에 표를 뒤지느냐.
- 런타임 비용: 왼쪽은 0이고 인라이닝까지 되지만, 오른쪽은 vtable 조회가 1회 들고 인라이닝이 안 된다.
- 코드 크기: 왼쪽은 타입마다 복제되고(bloat), 오른쪽은 1벌을 공유한다 — 위 두 행과 방향이 반대인 행이 여기다.
- 이종 컬렉션: 서로 다른 타입을 한 컬렉션에 담는 것은 왼쪽은 불가, 오른쪽은 가능하다.
- 적합 신호: 어느 쪽을 고를지 판단하는 힌트다.

> **이종(heterogeneous) 컬렉션** — 서로 다른 타입의 값을 한 목록에 섞어 담은 것.\
> 예: 위 표의 `Vec<Box<dyn T>>` — 같은 트레이트만 만족하면 실제 타입이 달라도 한 줄에 담긴다.

원문이 인용 블록으로 뽑은 정리는 이것이다.

> Rust는 "둘 중 하나를 강제"하지 않고 **선택을 문법에 노출**한다. 이것이 zero-cost 철학의 실제 모습이다: 비용이 없는 길을 기본으로 두되, 비용을 지불할 자유도 명시적으로 남긴다.

## 3. 매크로 — 선언적 `macro_rules!`와 절차적 매크로

### 언제·왜

**무엇이 문제였나** — 제네릭과 트레이트로도 못 지우는 보일러플레이트가 있다 — 가변 인자(`println!`의 임의 개수 인자), 구조체마다 반복되는 `impl`(직렬화·디버그 출력), 도메인 특화 문법(DSL). 함수는 타입과 개수가 고정이라 이걸 못 한다.

Rust의 답은 **컴파일 시 코드 생성**, 즉 매크로다. 런타임 비용 0(코드는 컴파일 시 펼쳐진다)이라는 점에서 이 역시 zero-cost 계보다.

매크로는 두 종류로 진화했다.

> **보일러플레이트(boilerplate)** — 내용은 거의 같은데 손으로 반복해 적어야 하는 코드.\
> 예: 구조체마다 똑같은 모양으로 직렬화·디버그 출력 `impl`을 다시 쓰는 것.

### (A) 선언적 매크로 `macro_rules!`

**무엇인가** — 토큰 트리(token tree)에 대한 **패턴 매칭**으로 코드를 생성한다. "이런 모양으로 호출되면 이런 코드로 펼쳐라"의 규칙 집합이다. C의 텍스트 치환 매크로와 달리 **위생적(hygienic)** — 매크로가 만든 변수가 호출부 변수와 충돌하지 않는다.

```rust
// 직접 만든 vec! 의 단순화 버전
macro_rules! my_vec {
    // $( ... ),*  : 콤마로 구분된 0개 이상의 표현식 반복
    ( $( $x:expr ),* ) => {
        {
            let mut v = Vec::new();
            $( v.push($x); )*   // 매칭된 각 $x 마다 push 한 줄을 펼침
            v
        }
    };
}

let nums = my_vec![1, 2, 3];   // → { let mut v = Vec::new(); v.push(1); ... v }
```

위 코드의 마지막 줄이 펼침의 결과다. 호출과 결과를 나란히 놓으면 이렇다.

```text
[ 내가 쓴 호출 ]                        [ 컴파일 시 펼쳐진 코드 ]
+------------------------------+        +------------------------------+
| my_vec![1, 2, 3]             |        | { let mut v = Vec::new();    |
|                              |        |   v.push(1); ... v }         |
+------------------------------+        +------------------------------+
 콤마로 구분된 0개 이상의 표현식 반복    매칭된 각 $x 마다 push 한 줄을 펼침
```

두 칸의 문구는 위 코드의 주석 세 줄을 좌우로 나눠 놓은 것이다 — 오른쪽 칸은 원문 마지막 줄의 주석을 그대로 옮겼다.

`$x:expr`(표현식), `$t:ty`(타입), `$i:ident`(식별자) 같은 **프래그먼트 지정자**가 토큰의 종류를 제약한다. `std`의 `vec!`, `println!`, `assert_eq!`가 모두 이 방식이다.

> **위생적(hygienic) 매크로** — 매크로가 안에서 만든 이름이 호출한 쪽의 같은 이름과 섞이지 않는 성질.\
> 예: 위 매크로가 안에서 쓰는 `v`가, 호출부에 이미 있는 `v`를 덮어쓰지 않는다.

> **토큰(token)** — 코드를 잘게 쪼갠 최소 조각(이름·기호·숫자 하나하나).\
> 예: `my_vec![1, 2, 3]`은 `my_vec`·`!`·`[`·`1`·`,` … 같은 토큰들로 읽힌다.

### (B) 절차적 매크로 (procedural macro)

**언제 쓰나** — `macro_rules!`의 패턴 매칭으로는 표현이 어려운, **임의의 코드 변환**이 필요할 때 쓴다. 입력 토큰 스트림(`TokenStream`)을 받아 임의의 Rust 코드로 변환하는 **함수**다. 세 형태로 단계적으로 안정화됐다.

| 형태 | 예 | 안정화 |
|------|-----|--------|
| 커스텀 derive | `#[derive(Serialize)]` | **1.15** (2017-02) |
| 함수형(function-like) | `sql!("SELECT ...")` | **1.30** (2018-10) |
| 속성(attribute) | `#[route(GET, "/")]` | **1.30** (2018-10) |

표를 읽는 법 — 세 형태가 두 시점에 나뉘어 안정화됐다.\
커스텀 derive가 1.15(2017-02)로 먼저였고, 함수형과 속성 둘이 1.30(2018-10)에 함께 들어왔다.

```rust
// 사용자: derive 한 줄로 직렬화 코드 전체를 자동 생성
#[derive(Debug, Clone, serde::Serialize)]
struct Point { x: i32, y: i32 }

// 매크로 구현 측(별도 proc-macro 크레이트): TokenStream → TokenStream
// #[proc_macro_derive(HelloMacro)]
// pub fn hello_derive(input: TokenStream) -> TokenStream { ... }
```

위 코드 주석이 적은 대로, 쓰는 쪽은 `#[derive(...)]` 한 줄이고 구현 쪽은 `TokenStream`을 받아 `TokenStream`을 돌려주는 함수다.

**무엇이 분기점이었나** — 1.30은 절차적 매크로를 모듈 시스템에 통합해 `#[macro_use]` 같은 군더더기 없이 일반 아이템처럼 임포트할 수 있게 만든 분기점이었다. `serde`, `tokio`, `clap` 등 생태계의 사실상 모든 핵심 크레이트가 절차적 매크로 위에 서 있다 — 보일러플레이트를 컴파일 시로 밀어내는 Rust 생태계의 동력이다.

> **`TokenStream`** — 코드를 토큰의 흐름으로 담은 값. 절차적 매크로의 입력이자 출력이다.\
> 예: 위 코드 주석의 `fn hello_derive(input: TokenStream) -> TokenStream` — 코드를 받아 코드를 돌려준다.

## 4. 에러 처리 — `Result`, `?` 연산자, panic vs Result

### 언제·왜 — Erlang식 실패에서 타입화된 에러로

**무엇이 있었나** — 초기 Rust는 Erlang을 닮아 있었다. **경량 태스크(lightweight task)** 가 있었고, 태스크가 회복 불가능한 상태에 빠지면 `fail!`로 스스로를 죽이는 모델이었다. 그러나 "추상화를 줄이고 OS 스레드로 간다"는 1.0 직전의 방향 전환 속에서 경량 태스크는 제거됐고, 용어도 정리됐다.

- **RFC 221 (1.0 직전)**: `fail!` → `panic!`로 개명. 이유는 **용어 충돌**이었다. "어떤 연산이 *실패(fail)* 한다"(즉 `Err`/`None` 반환)와 "태스크가 죽는다"가 같은 단어를 써 혼란스러웠다. 개명 후 의미가 3층으로 갈렸다:
  - **failure** = `Err`/`None`을 내는 회복 가능한 실패 (값으로 표현)
  - **panic** = 태스크/스레드 수준의 스택 언와인딩 (회복 불가 기본값)
  - **abort** = 프로세스 전체 종료

개명 전후를 나란히 놓으면 왜 바꿨는지가 보인다.

```text
[ 개명 전 — 한 단어가 둘을 가리켰다 ]   [ 개명 후 — 의미가 3층으로 갈렸다 ]
+-------------------------------+       +-------------------------------+
| fail                          |       | failure = Err/None 을 내는    |
|   "어떤 연산이 실패한다"      |       |   회복 가능한 실패 (값)       |
|   (Err/None 반환)             |       |                               |
|                               |       | panic = 태스크/스레드 수준의  |
| fail!                         |       |   스택 언와인딩 (회복 불가)   |
|   "태스크가 죽는다"           |       |                               |
|                               |       | abort = 프로세스 전체 종료    |
+-------------------------------+       +-------------------------------+
 같은 단어를 써 혼란스러웠다             RFC 221 (1.0 직전)
```

왼쪽 칸의 두 항목은 원문이 "용어 충돌"로 든 두 뜻이고, 오른쪽 칸의 세 항목은 원문의 3층 불릿을 그대로 옮긴 것이다.

이 개명이 곧 Rust 에러 철학의 선언이다: **회복 가능한 실패는 값(`Result`)이고, 회복 불가능한 버그는 `panic!`이다.**

```rust
// panic! — 회복 불가능한 프로그래밍 오류. 스택을 언와인딩하며 종료.
let v = vec![1, 2, 3];
// v[99];                       // panic: index out of bounds (계약 위반 = 버그)

// Result — 회복 가능한, 예상된 실패를 타입에 박는다.
use std::num::ParseIntError;
fn parse(s: &str) -> Result<i32, ParseIntError> {
    s.parse::<i32>()            // Ok(n) | Err(e)
}
```

`panic!`의 기본 동작은 **언와인딩**(스택을 거슬러 올라가며 `Drop` 정리)이지만, `Cargo.toml`에 `panic = "abort"`를 주면 정리 없이 즉시 종료해 바이너리를 줄일 수 있다 — 임베디드에서 흔한 선택이다.

> **언와인딩(unwinding)** — 죽는 길에 스택을 거슬러 올라가며 정리(`Drop`)를 실행하는 것.\
> 예: 나가면서 열어 둔 파일과 잠금을 하나씩 닫고 나가는 것. `panic = "abort"`는 그 정리 없이 즉시 종료한다.

> **`Result` / `Option`** — "할 수 없었음 + 왜"를 담는 타입 / "찾았는데 없음"을 담는 타입.\
> 예: 위 코드의 `Result<i32, ParseIntError>`는 숫자로 못 바꿨을 때 그 이유까지 값으로 돌려준다.

### `?` 연산자 — `try!` 매크로의 후계자

**무엇이 문제였나** — `Result`의 약점은 **전파의 장황함**이었다. 1.0 시절엔 `try!` 매크로로 "에러면 조기 반환, 성공이면 언랩"을 했다.

```rust
// 1.0 시절: try! 매크로 — 중첩되면 LISP처럼 괄호가 깊어진다
fn read_username() -> Result<String, io::Error> {
    let mut f = try!(File::open("user.txt"));
    let mut s = String::new();
    try!(f.read_to_string(&mut s));
    Ok(s)
}
```

- **1.13 (RFC 243)**: `?` 연산자 안정화. `try!(expr)`은 거의 모든 경우 `expr?`로 기계적 치환이 가능했다(rustfix 지원). `?`는 "`Ok`면 언랩, `Err`면 `From`으로 변환 후 조기 반환"을 한 글자로 표현한다.

```rust
// 1.13+: ? 연산자 — 선형적이고 읽기 쉽다
fn read_username() -> Result<String, io::Error> {
    let mut s = String::new();
    File::open("user.txt")?.read_to_string(&mut s)?;
    Ok(s)
}
```

위 두 코드블록을 나란히 읽으면 바뀐 것이 보인다.

```text
[ try! 매크로 (1.0 시절) ]              [ ? 연산자 (1.13+) ]
+------------------------------+        +------------------------------+
| try!(File::open(...))        |        | File::open(...)?             |
| try!(f.read_to_string(...))  |        |   .read_to_string(...)?      |
|                              |        |                              |
| 중첩되면 LISP처럼            |        | 선형적이고 읽기 쉽다         |
| 괄호가 깊어진다              |        |                              |
+------------------------------+        +------------------------------+
 위 두 코드블록의 주석 그대로다
```

두 칸의 아래 문구는 위 두 코드블록 첫 줄의 주석을 그대로 옮긴 것이고, 위쪽 코드 줄은 그 블록에서 요점만 줄여 옮긴 것이다.

`?`의 진짜 힘은 **`From` 트레이트를 통한 자동 에러 변환**이다. 함수 반환 타입의 에러로 변환 가능하면(`From<하위에러> for 상위에러`), 서로 다른 라이브러리 에러를 한 함수에서 자연스럽게 합성할 수 있다. 이 한 글자가 Rust 에러 처리를 "장황해서 못 쓰겠다"에서 "행복 경로가 깨끗하다"로 바꾼 전환점이었다. (이후 `?`는 `Option`, 그리고 `Try` 트레이트(RFC 3058)를 통해 사용자 타입으로까지 일반화된다.)

> **`?` 연산자** — `Ok`면 값을 꺼내 이어 가고, `Err`면 `From`으로 변환해 그 자리에서 함수를 빠져나가는 한 글자.\
> 예: 위 코드의 `File::open("user.txt")?` — 열리면 파일을 들고 다음 줄로, 안 열리면 그 에러를 반환 타입에 맞게 바꿔 곧장 돌려준다.

> **행복 경로(happy path)** — 아무 문제 없이 성공만 이어지는 실행 경로.\
> 예: `?` 덕분에 에러 처리 코드가 줄 사이에 끼지 않아, 성공했을 때의 흐름만 한눈에 읽힌다.

### corpus 연결 — "에러/부재의 타입 수준 표현"의 정전(正典)

*(corpus 경로: `~/project/local-llm/corpus/backend/tactical/에러-부재-표현.md`)*

이 절은 corpus 「에러-부재-표현」 문서가 말하는 원칙의 **언어 차원 구현 사례**다. 그 문서의 핵심 명제 — *"부재와 실패를 값/타입으로 만들어 시그니처에 드러내고, 컴파일러가 처리(또는 명시적 무시)를 강제하게 한다"* — 를 Rust는 다음과 같이 제도화했다:

- **부재 ≠ 실패의 타입 분리**: corpus 표 그대로, Rust는 "찾았는데 없음(정상)"을 `Option<T>`로, "할 수 없었음 + 왜(비정상)"를 `Result<T, E>`로 갈라 둔다. 둘 다 enum이라 섞이지 않는다(§5).
- **무시 불가 강제**: `Result`에는 `#[must_use]`가 붙어, 쓰지 않고 버리면 컴파일러가 경고한다. corpus의 안티패턴 "Result/error 무시 → null 시대로 회귀"를 타입 시스템이 직접 막는다.
- **에러를 String이 아닌 ADT로**: corpus가 경고하는 "에러를 단일 String으로" 대신, Rust 관용은 에러를 enum(sum type)으로 정의해 호출자가 분기할 수 있게 한다.
- **expected vs unexpected의 언어적 경계**: corpus가 인용하는 Wlaschin의 ROP 경고("모든 걸 `Result`로 끌면 안 된다")가 Rust에선 `Result`(예상된 도메인 에러) vs `panic!`(회복 불가 버그)의 구분으로 그대로 나타난다. corpus의 "언어 관용" 행이 `Rust=Result/Option`으로 적은 바로 그 정전이 이 절이다.

> **`#[must_use]`** — 돌려받은 값을 쓰지 않고 버리면 컴파일러가 경고하게 하는 표시.\
> 예: `Result`를 받아 놓고 성공·실패를 확인하지 않은 채 버리면 경고가 뜬다.

원문이 이 절 끝에 인용 블록으로 뽑은 정리는 이것이다.

> 요컨대 corpus 문서가 *원칙*(언어 중립)이라면, 이 절은 Rust가 그 원칙을 **문법·트레이트·린트로 강제**한 *구현*이다.

## 5. 패턴 매칭과 대수적 자료형 (enum)

### 언제·왜

**무엇인가** — Rust의 `enum`은 C의 enum(정수 상수 목록)이 아니라 ML/Haskell의 **합 타입(sum type), 즉 대수적 자료형(ADT)** 이다. "이 값은 A이거나 B이거나 C인데, 각 변형은 서로 다른 데이터를 담는다"를 타입으로 표현한다. 이 선택이 §4의 에러 처리를 가능케 한 토대다 — `Option`과 `Result`는 특별한 문법이 아니라 표준 라이브러리의 평범한 enum이다.

```rust
// Option/Result는 마법이 아니라 그냥 enum이다
enum Option<T> { Some(T), None }
enum Result<T, E> { Ok(T), Err(E) }

// 도메인 상태를 합 타입으로 — "불가능한 상태를 표현 불가능하게"
enum WebEvent {
    PageLoad,                       // 데이터 없음
    KeyPress(char),                 // 튜플형 변형
    Click { x: i64, y: i64 },       // 구조체형 변형
}
```

위 코드의 `WebEvent`가 세 변형을 갖고, 각 변형이 담는 데이터가 서로 다르다는 점을 그림으로 놓으면 이렇다.

```text
  enum WebEvent — "이 값은 셋 중 하나다"

  PageLoad                  데이터 없음
  KeyPress(char)            튜플형 변형
  Click { x: i64, y: i64 }  구조체형 변형
```

오른쪽 열은 위 코드 주석 세 줄을 그대로 옮긴 것이다 — 변형이 셋이므로 줄도 셋이다.

> **합 타입(sum type) / 대수적 자료형(ADT)** — "이 값은 A이거나 B이거나 C"를 타입으로 적은 것.\
> 예: 위 `WebEvent` — 한 값이 세 모양 중 정확히 하나이고, 모양마다 담는 데이터가 다르다.

> **변형(variant)** — enum이 가질 수 있는 각각의 모양.\
> 예: `PageLoad`·`KeyPress`·`Click` 셋이 `WebEvent`의 변형이다.

### 패턴 매칭 — 망라성(exhaustiveness) 검사

**무엇을 강제하나** — `match`는 단순 분기가 아니라 **구조 분해 + 망라성 강제**다. 컴파일러가 "모든 변형을 처리했는가"를 검사해, 새 변형을 추가하면 그것을 처리하지 않은 모든 `match`가 컴파일 에러가 된다. 리팩토링 안전망이다.

```rust
fn describe(e: WebEvent) -> String {
    match e {
        WebEvent::PageLoad => "로드".into(),
        WebEvent::KeyPress(c) => format!("키: {}", c),        // c를 추출(바인딩)
        WebEvent::Click { x, y } => format!("클릭 {},{}", x, y), // 필드 분해
        // 한 갈래라도 빠지면: error[E0004] non-exhaustive patterns
    }
}

// if let — 한 변형만 관심 있을 때의 축약형
if let Some(name) = maybe_name {
    println!("이름: {}", name);
}
```

```text
[ 갈래를 빠뜨리면 ]                     [ 새 변형을 추가하면 ]
+------------------------------+        +------------------------------+
| error[E0004]                 |        | 그것을 처리하지 않은         |
| non-exhaustive patterns      |        | 모든 match 가 컴파일 에러    |
+------------------------------+        +------------------------------+
 위 코드 주석 그대로다                   원문이 "리팩토링 안전망"이라 부른 것
```

두 칸은 같은 검사가 두 상황에서 하는 일이다 — 왼쪽은 위 코드 주석의 에러 이름, 오른쪽은 원문 문장 그대로다.

ADT + 망라적 패턴 매칭의 조합은 "불가능한 상태를 표현 불가능하게 만든다(make illegal states unrepresentable)"는 타입 주도 설계의 Rust식 구현이다. corpus 「상태-머신」(corpus 경로: `~/project/local-llm/corpus/backend/dimensions/상태-머신.md`) 문서가 말하는 "상태를 enum으로, 전이를 타입으로"가 여기서 출발한다.

> **망라성(exhaustiveness) 검사** — 가능한 모든 경우를 빠짐없이 처리했는지 컴파일러가 확인하는 것.\
> 예: 위 `match`에서 세 변형 중 하나라도 빠지면 `error[E0004]`로 빌드가 멈춘다.

> **구조 분해(destructuring)** — 값 안의 데이터를 그 자리에서 꺼내 이름을 붙이는 것.\
> 예: 위 코드의 `WebEvent::Click { x, y }`가 안의 두 필드를 `x`·`y`로 꺼내 쓴다.

## 6. unsafe와 안전 추상화 경계

### 언제·왜 — 시스템 언어의 딜레마

**무엇이 문제였나** — Rust는 시스템 언어를 자처한다. 그러려면 생포인터, FFI(C 호출), 메모리 맵 하드웨어 접근이 필요하다 — 본질적으로 컴파일러가 안전을 증명할 수 없는 영역이다. 그러나 "안전"이 Rust의 브랜드다. 이 모순의 해법이 `unsafe`다: **위험을 언어에서 추방하는 대신, 작은 블록 안에 격리하고 그 경계에 안전한 API를 두른다.**

**핵심 오해부터 정정한다** — 원문의 표현 그대로다. **`unsafe`는 빌림 검사기(borrow checker)를 끄지 않는다.** 그것이 푸는 것은 딱 다섯 가지 "초능력(superpower)"뿐이고, 나머지 모든 안전 검사는 그대로다.

```rust
unsafe {
    // unsafe가 허용하는 다섯 가지 (그 외엔 전부 평소대로 검사됨):
    // 1) 생포인터 역참조
    let x = 5;
    let raw = &x as *const i32;
    println!("{}", *raw);
    // 2) unsafe 함수/메서드 호출
    // 3) 가변 static 변수 접근/수정
    // 4) unsafe 트레이트 구현
    // 5) union 필드 접근
}
```

```text
[ unsafe 가 푸는 것 — 딱 다섯 가지 ]    [ unsafe 가 끄지 않는 것 ]
+-------------------------------+       +-------------------------------+
| 1) 생포인터 역참조            |       | 빌림 검사기                   |
| 2) unsafe 함수/메서드 호출    |       |                               |
| 3) 가변 static 변수 접근/수정 |       | 나머지 모든 안전 검사         |
| 4) unsafe 트레이트 구현       |       |   — 전부 평소대로 검사됨      |
| 5) union 필드 접근            |       |                               |
+-------------------------------+       +-------------------------------+
 위 코드 주석의 다섯 줄 그대로다         원문 문장 그대로다
```

왼쪽 다섯 줄은 위 코드 주석에 번호까지 그대로 적혀 있는 것이고, 오른쪽은 원문의 "`unsafe`는 빌림 검사기를 끄지 않는다 / 나머지 모든 안전 검사는 그대로다"를 옮긴 것이다.\
초보자가 자주 틀리는 지점이 여기다 — **`unsafe`는 안전 검사를 전부 끄는 스위치가 아니다.**

> **`unsafe`** — 컴파일러가 스스로 증명할 수 없는 다섯 가지 연산을 개발자의 책임 아래 허용하는 블록.\
> 예: 위 코드의 `*raw`(생포인터 역참조) — 그 다섯 가지 말고는 블록 안에서도 평소와 똑같이 검사된다.

> **생포인터(raw pointer)** — 유효성을 언어가 보장해 주지 않는 날 주소값.\
> 예: 위 코드의 `&x as *const i32` — 가리키는 곳이 살아 있는지는 쓰는 사람이 책임진다.

> **빌림 검사기(borrow checker)** — 빌림이 규칙을 지키는지 검사하는, 컴파일러의 정적 분석 패스. 규칙 자체는 03편이 다룬다.\
> 예: 위 문장이 적은 대로 `unsafe` 블록 안에서도 이 검사는 계속 돈다 — `unsafe`가 푸는 다섯 가지에 이 검사는 들어 있지 않다.

### 안전 추상화 경계 — Rust 안전성의 진짜 메커니즘

**무엇이 진가인가** — `unsafe`의 진가는 **격리와 캡슐화**에 있다. `Vec`, `RefCell`, `Mutex`는 내부적으로 생포인터와 unsafe 연산으로 구현되지만, **공개 API는 100% 안전**하다. unsafe 블록 안에서 개발자가 손으로 증명한 불변식(invariant)을 안전한 타입 경계가 봉인한다. 사용자는 unsafe를 한 줄도 쓰지 않고 그 성능을 누린다.

```rust
// 개념 예시: 안전한 껍데기가 unsafe 내부를 봉인한다
pub struct MyBox<T> { ptr: *mut T }   // 내부는 생포인터(위험)

impl<T> MyBox<T> {
    pub fn get(&self) -> &T {
        // 생성자에서 ptr이 항상 유효함을 보장했다는 불변식에 기댄다.
        unsafe { &*self.ptr }          // unsafe는 여기 한 줄에 격리
    }
}
// 호출자는 unsafe를 모른 채 안전하게 쓴다: my_box.get()
```

```text
  호출자:  my_box.get()          ← unsafe를 모른 채 안전하게 쓴다
              |
              v
  +--------------------------------------------+
  |  안전한 껍데기  pub fn get(&self) -> &T    |
  |                                            |
  |   +------------------------------------+   |
  |   |  unsafe { &*self.ptr }             |   |
  |   |  unsafe는 여기 한 줄에 격리        |   |
  |   +------------------------------------+   |
  |                                            |
  |  내부는 생포인터(위험)  ptr: *mut T        |
  +--------------------------------------------+
```

그림 해설 — 바깥 상자가 공개 API, 안쪽 상자가 격리된 `unsafe` 한 줄이다.\
문구는 전부 위 코드와 그 주석에서 가져왔고, 그림 안의 `get`·`ptr`·`unsafe` 한 줄은 그 코드에 실재한다.

이 "안전 위에 unsafe를 숨긴다"는 원리는 학술적으로도 검증됐다 — **RustBelt**(POPL'18)는 표준 라이브러리의 unsafe 추상화들이 실제로 안전 계약을 지킴을 형식 증명했다.

**함정** — 반대로, unsafe가 모듈 경계 밖으로 새어 나가 `unsafe fn`이 전염되면, 타입 시스템의 이득은 사라진다.\
그래서 관용은 **"unsafe는 최소 표면적으로 가두고, 안전 API로 봉인하라"** 이다.

> **불변식(invariant)** — 그 코드가 도는 내내 항상 참이어야 하는 규칙.\
> 예: 위 코드 주석의 "생성자에서 `ptr`이 항상 유효함을 보장했다"가 그 규칙이고, `get`은 그것에 기댄다.

> **캡슐화(encapsulation)** — 안쪽 사정을 감추고 바깥에는 정해진 통로만 열어 두는 것.\
> 예: `Vec`을 쓰는 사람은 그 안의 생포인터를 볼 일이 없고 `push`·`len` 같은 안전한 통로만 쓴다.

원문이 이 절 끝에 인용 블록으로 뽑은 정리는 이것이다.

> unsafe는 "Rust가 안전을 포기하는 곳"이 아니라 **"안전의 책임이 컴파일러에서 개발자로 명시적으로 이양되는 표식"** 이다. `unsafe` 키워드는 코드 리뷰어에게 "여기를 보라"고 외치는 좌표이기도 하다.

## 7. zero-cost abstraction 철학 — 모든 것을 꿰는 실

### 기원과 정의

**어디서 왔나** — 위 여섯 개념을 관통하는 단 하나의 원리가 **zero-cost abstraction(영비용 추상화)** 이다. 출처는 C++의 창시자 Bjarne Stroustrup의 정식화다:

> **"What you don't use, you don't pay for. And further: what you do use, you couldn't hand-code any better."**
> (쓰지 않는 것엔 비용을 내지 않는다. 그리고 쓰는 것은, 손으로 짜도 그보다 나을 수 없다.)

C++이 이 원리를 *지향*했다면, Rust는 이를 **설계 공리(design axiom)** 로 격상시켰다 — 언어의 모든 층에 구워 넣은 약속이다. 앞의 개념들은 모두 이 공리의 사례다:

| 개념 | "쓰지 않으면 비용 0" | "쓰면 손코딩만큼 빠름" |
|------|----------------------|------------------------|
| 제네릭/트레이트 (§1–2) | 안 쓰면 코드 생성 없음 | 모노모피제이션 + 인라이닝 → 가상 호출·박싱 없음 |
| 매크로 (§3) | 컴파일 시 펼침 | 런타임 흔적 0, 손으로 쓴 코드와 동일 |
| `Result`/`Option` (§4–5) | enum 태그 1바이트 수준 | `?`·`match`는 분기로 컴파일, 예외 테이블·언와인딩 비용 없음 |
| `Iterator` 체인 | — | `.filter().map().sum()`이 손으로 쓴 `for` 루프와 동일한 기계어로 |
| `unsafe` 추상화 (§6) | 안전 껍데기는 런타임 비용 0 | 내부는 생포인터 = C 수준 |

표를 읽는 법 — 두 열이 위 인용문의 두 문장에 각각 대응한다.\
왼쪽 열이 "쓰지 않는 것엔 비용을 내지 않는다", 오른쪽 열이 "쓰는 것은 손으로 짜도 그보다 나을 수 없다"다.\
`Iterator` 체인 행의 왼쪽이 `—`인 것은 원문이 그 칸을 비워 둔 것이다.

```rust
// 고수준 선언적 코드가...
let total: u32 = (1..=100)
    .filter(|n| n % 2 == 0)
    .map(|n| n * n)
    .sum();

// ...손으로 쓴 명령형 루프와 (거의) 동일한 기계어로 컴파일된다.
// 클로저도, 이터레이터 어댑터도 인라이닝되어 흔적 없이 사라진다.
```

```text
[ 고수준 선언적 코드 ]                  [ 기계어 ]
+------------------------------+        +------------------------------+
| (1..=100)                    |        |                              |
|   .filter(...)               |   →    |   (거의) 동일한 기계어       |
|   .map(...)                  |        |                              |
|   .sum()                     |        |                              |
+------------------------------+        +------------------------------+
 클로저도, 이터레이터 어댑터도 인라이닝되어 흔적 없이 사라진다
```

두 칸과 캡션의 문구는 위 코드의 주석 두 줄에서 따온 것이고, 화살표 하나는 그 주석의 "동일한 기계어로 컴파일된다"에 대응한다.\
오른쪽 칸이 가리키는 것은 손으로 쓴 루프 자체가 아니라, 양쪽이 **함께 도달하는 기계어**다.\
원문이 괄호로 달아 둔 "(거의)"도 그대로 두었다.

### 정직한 단서 — "zero-cost"의 진짜 의미

**대가는 무엇인가** — 이름이 과장처럼 들리지만, 정확한 의미는 **"이 추상화에는 추상화이기 때문에 추가로 드는 *런타임* 비용이 없다"** 이다. 비용이 *아예* 없다는 뜻은 아니다:

- **동적 디스패치(`dyn`)** 는 vtable 간접 호출 비용을 낸다 — 그래서 `dyn`은 선택이지 기본이 아니다(§2).
- **경계 검사(bounds check)**, **`Rc`의 참조 카운트 증감**은 안전을 위한 의도적 런타임 비용이다.
- 비용은 사라지는 게 아니라 **런타임에서 컴파일 시간(긴 빌드)과 바이너리 크기(code bloat)로 이동**한다.

```text
  비용이 사라지는 게 아니라 자리를 옮긴다

  런타임          →   컴파일 시간 (긴 빌드)
                  →   바이너리 크기 (code bloat)
```

화살표 둘은 원문 마지막 불릿이 든 두 이동처("컴파일 시간"·"바이너리 크기")에 대응한다.

즉 Rust의 약속은 "마법처럼 공짜"가 아니라, **"고수준으로 쓴 대가를 *실행 속도로* 치르게 하지는 않겠다 — 그 비용은 명시적이고, 보통은 컴파일러가 흡수한다"** 이다. 그리고 추상화를 쓰지 않을 자유, 비용을 지불할 곳을 직접 고를 자유(`impl` vs `dyn`, `panic=abort` 등)를 늘 문법에 노출한다.

> **경계 검사(bounds check)** — 배열·슬라이스의 범위를 벗어나 읽거나 쓰지 않는지 실행 중에 확인하는 것.\
> 예: 위 불릿이 적은 대로 이것은 안전을 위한 **의도적** 런타임 비용이지, 추상화가 붙인 비용이 아니다.

## 마치며 — 진화의 방향

*(이 편의 「남긴 것」에 해당한다)*

Rust의 핵심 개념들은 서로 독립적으로 보이지만, 하나의 설계 의지가 관통한다: **표현력 ↔ 비용 ↔ 안전의 삼각형에서 어느 꼭짓점도 양보하지 않는다.**

- 트레이트와 모노모피제이션은 **추상화의 비용**을 0으로 만들었고,
- 매크로는 **보일러플레이트의 비용**을 컴파일 시로 밀어냈으며,
- `Result`·`?`·ADT·패턴 매칭은 **에러를 타입으로** 끌어와 안전을 표현력으로 바꿨고,
- `unsafe`와 안전 추상화 경계는 **저수준 제어**를 안전의 봉투 안에 격리했다.

이 모든 결정의 공통 분모가 zero-cost abstraction이다. 그래서 Rust의 개념사는 곧 "고수준 언어의 편의와 저수준 언어의 통제를 *동시에* 가지려는 시도의 역사"다. `~Trait`을 `dyn Trait`으로, `fail!`을 `panic!`과 `Result`로, `try!`를 `?`로 바꿔 온 궤적은 모두 그 시도를 더 정직하고 명시적으로 만들려는 조정이었다. 개별 문법이 또 바뀌더라도, 이 축은 바뀌지 않을 것이다.

## 용어 풀이

- **개념사** — 제품이 아니라 그 제품들이 공유하는 장치와 아이디어의 계보.
- **런타임 비용** — 프로그램이 실제로 도는 동안 추가로 드는 시간·메모리.
- **트레이트(trait)** — "이 타입은 이런 동작을 할 수 있다"를 적어 둔 명세.
- **타입클래스(typeclass)** — "이 타입은 이 동작을 만족한다"는 제약의 도구. 트레이트의 계보다.
- **제네릭 경계(bound)** — 제네릭 타입에 "이 트레이트를 만족하는 타입만"이라고 거는 조건.
- **트레이트 객체 / `dyn`** — 실제 타입을 런타임에야 아는 값과, 그것을 명시하는 키워드(1.27, RFC 2113).
- **vtable** — "이 값의 실제 타입에서 이 메서드는 어디 있나"를 적어 둔 표.
- **정적 / 동적 디스패치** — 어느 본체를 부를지 컴파일 시에 정함 / 실행 중에 vtable로 찾아감.
- **모노모피제이션** — 제네릭 함수를 실제로 쓰인 구체 타입마다 별도 기계어 함수로 펼치는 것.
- **인라이닝** — 함수를 부르는 대신 본문을 호출 자리에 펴 넣는 최적화.
- **code bloat(바이너리 비대)** — 타입마다 코드가 복제되어 바이너리가 커지는 현상.
- **이종 컬렉션** — 서로 다른 타입의 값을 한 목록에 섞어 담은 것(`Vec<Box<dyn T>>`).
- **보일러플레이트** — 내용은 거의 같은데 손으로 반복해 적어야 하는 코드.
- **`macro_rules!`(선언적 매크로)** — 토큰 트리에 대한 패턴 매칭으로 코드를 생성하는 매크로.
- **위생적(hygienic) 매크로** — 매크로가 만든 이름이 호출부의 같은 이름과 충돌하지 않는 성질.
- **토큰 / `TokenStream`** — 코드를 이룬 최소 조각 / 그 조각들의 흐름을 담은 값.
- **절차적 매크로** — `TokenStream`을 받아 임의의 Rust 코드로 바꾸는 함수. derive·함수형·속성 세 형태.
- **프래그먼트 지정자** — `$x:expr`·`$t:ty`·`$i:ident`처럼 매칭할 토큰의 종류를 제약하는 표기.
- **`panic!` / abort** — 태스크·스레드 수준의 스택 언와인딩(회복 불가 기본값) / 프로세스 전체 종료.
- **언와인딩(unwinding)** — 죽는 길에 스택을 거슬러 올라가며 `Drop` 정리를 실행하는 것.
- **`Result` / `Option`** — "할 수 없었음 + 왜"를 담는 타입 / "찾았는데 없음"을 담는 타입. 둘 다 평범한 enum이다.
- **`?` 연산자** — `Ok`면 값을 꺼내 이어 가고, `Err`면 `From`으로 변환해 조기 반환하는 한 글자(1.13, RFC 243).
- **`From` 트레이트** — 한 타입을 다른 타입으로 바꾸는 변환 명세. `?`의 자동 에러 변환이 이것에 기댄다.
- **행복 경로(happy path)** — 아무 문제 없이 성공만 이어지는 실행 경로.
- **`#[must_use]`** — 돌려받은 값을 쓰지 않고 버리면 경고하게 하는 표시.
- **합 타입(sum type) / ADT** — "이 값은 A이거나 B이거나 C"를 타입으로 적은 것.
- **변형(variant)** — enum이 가질 수 있는 각각의 모양.
- **망라성(exhaustiveness) 검사** — 가능한 모든 경우를 빠짐없이 처리했는지 컴파일러가 확인하는 것.
- **구조 분해(destructuring)** — 값 안의 데이터를 그 자리에서 꺼내 이름을 붙이는 것.
- **`unsafe`** — 컴파일러가 증명할 수 없는 다섯 가지 연산을 개발자 책임 아래 허용하는 블록. 빌림 검사기를 끄지 않는다.
- **생포인터(raw pointer)** — 유효성을 언어가 보장해 주지 않는 날 주소값.
- **빌림 검사기(borrow checker)** — 빌림이 규칙을 지키는지 검사하는 컴파일러의 정적 분석 패스. `unsafe`는 이것을 끄지 않는다.
- **불변식(invariant)** — 그 코드가 도는 내내 항상 참이어야 하는 규칙.
- **캡슐화** — 안쪽 사정을 감추고 바깥에는 정해진 통로만 열어 두는 것.
- **RustBelt** — 표준 라이브러리의 unsafe 추상화가 안전 계약을 지킴을 형식 증명한 연구(POPL'18).
- **zero-cost abstraction** — 추상화이기 때문에 추가로 드는 *런타임* 비용이 없다는 원리. 비용이 아예 없다는 뜻은 아니다.
- **경계 검사(bounds check)** — 범위를 벗어난 접근이 아닌지 실행 중에 확인하는, 안전을 위한 의도적 비용.
