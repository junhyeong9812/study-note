## 한눈에 — 쉽게 말하면

**`LinkedList` 는 「손을 맞잡고 선 사람들의 줄」이다.**
사람마다 앞사람과 뒷사람의 손을 잡고 있을 뿐, 다들 운동장 여기저기에 흩어져 서 있다.
줄 맨 앞이나 맨 뒤에 한 사람을 붙이는 일은 손 한 번만 잡으면 끝난다.
하지만 「앞에서 세 번째 사람」을 찾으려면 맨 앞에서부터 손을 따라 한 명씩 건너가야 한다.
반면 `Vec` 은 「극장의 한 줄 좌석」이다.
모두 붙어 앉아 있어서 3번 좌석은 바로 찾고, 한 줄을 훑어보는 일도 빠르다.
Rust 의 `LinkedList` 도 똑같은 구조다.

| 비유 | 실체 |
|---|---|
| 줄 선 사람 한 명 | 노드(값 + 앞 · 뒤 포인터) |
| 앞사람 · 뒷사람과 잡은 손 | `prev` · `next` 포인터 |
| 운동장에 흩어져 섬 | 노드마다 힙의 다른 곳에 따로 할당됨 |
| 극장의 붙은 좌석 | `Vec` 의 연속된 메모리 |
| 두 줄의 끝사람끼리 손잡기 | `append` |

```text
LinkedList (이중 연결)              Vec (연속 메모리)

 head                tail
  │                   │             ┌───┬───┬───┬───┐
  ▼                   ▼             │ 0 │ 1 │ 2 │ 3 │
 [0] ⇄ [1] ⇄ [2] ⇄ [3]              └───┴───┴───┴───┘
  힙 여기저기에 흩어져 있다           한 덩어리로 붙어 있다
```

> **노드** — 연결 리스트에서 값 하나와 이웃을 가리키는 포인터를 함께 담은 칸.\
> 예: `[1]` 노드는 값 1, `[0]` 을 가리키는 `prev`, `[2]` 를 가리키는 `next` 를 담는다.

> **이중 연결 리스트** — 노드마다 앞 노드와 뒤 노드를 둘 다 가리키는 연결 리스트.\
> 예: Rust 의 `std::collections::LinkedList` 가 이것이다.

## 이 주제가 답하려는 질문

1. `LinkedList` 로 양쪽 끝에 넣고 빼고, 앞뒤로 훑고, 두 리스트를 합치는 일은 어떻게 하나?
2. 이론상 중간 삽입이 O(1) 인데 왜 실제로는 이점이 적은가?
3. 왜 거의 항상 `Vec` 이나 `VecDeque` 가 더 나은가, 그리고 `LinkedList` 가 맞는 드문 경우는 언제인가?

## 동작 방식

### (1) 양쪽 끝에 넣고 보고 빼기

**언제 쓰나** — 리스트의 맨 앞이나 맨 뒤에서만 값을 다룰 때.

```text
push_back(1), push_back(2), push_back(3)   →  [1, 2, 3]
push_front(0)                              →  [0, 1, 2, 3]
front() → Some(&0)   back() → Some(&3)   len() → 4
pop_front() → Some(0)                      →  [1, 2, 3]
pop_back()  → Some(3)                      →  [1, 2]
```

- `push_back` 은 뒤 끝 노드에 새 노드를 이어 붙인다 — O(1) 이다.
- `push_front` 는 앞 끝에 붙인다 — 역시 O(1) 이고, 이것이 `LinkedList` 의 강점이다.
- `front` · `back` 은 양 끝 값을 꺼내지 않고 들여다본다(peek) — 비어 있을 수 있으니 `Option` 으로 돌려준다.
- `pop_front` · `pop_back` 은 양 끝 노드를 떼어 내고 그 값을 `Some(값)` 으로 돌려준다 — O(1) 이다.

> **peek** — 값을 빼지 않고 보기만 하는 일.\
> 예: `list.front()` 는 맨 앞 값을 보여 주지만 리스트는 그대로다.

### (2) 정방향 · 역방향 순회

**언제 쓰나** — 모든 원소를 앞에서부터, 또는 뒤에서부터 훑을 때.

```text
let list: LinkedList<i32> = (1..=5).collect();

for val in &list            →  1 → 2 → 3 → 4 → 5   (head 에서 next 를 따라감)
for val in list.iter().rev() →  5 → 4 → 3 → 2 → 1   (tail 에서 prev 를 따라감)
```

- `collect` 로 범위나 다른 반복자에서 `LinkedList` 를 바로 만들 수 있다.
- `&list` 를 `for` 에 넣으면 빌려 쓰는 순회가 되어 리스트는 그대로 남는다.
- 노드가 `prev` 도 갖고 있으므로 뒤에서 앞으로도 갈 수 있다 — 그래서 `iter()` 가 `DoubleEndedIterator` 이고 `.rev()` 를 붙일 수 있다.

> **`DoubleEndedIterator`** — 앞쪽과 뒤쪽 양 끝에서 값을 꺼낼 수 있는 반복자.\
> 예: `list.iter().rev()` 는 뒤에서부터 값을 낸다.

### (3) `append` — 두 리스트를 O(1) 로 합치기

**언제 쓰나** — 한 리스트의 모든 원소를 다른 리스트 뒤에 통째로 옮길 때.

```text
list1: [1] ⇄ [2] ⇄ [3]          list2: [4] ⇄ [5] ⇄ [6]

list1.append(&mut list2);

list1: [1] ⇄ [2] ⇄ [3] ⇄ [4] ⇄ [5] ⇄ [6]
list2: []   (비어 있다 — 노드를 모두 넘겨줬다)
```

- `list1` 의 꼬리 노드와 `list2` 의 머리 노드를 서로 가리키게만 바꾼다.
- 원소 개수와 상관없이 포인터 몇 개만 고치므로 O(1) 이다.
- `list2` 는 `&mut` 로 빌려 주었기 때문에 사라지지 않고, 비어 있는 채로 남는다.
- `Vec` 은 원소를 실제로 옮겨 담아야 하므로 원본 비교표에서 O(n) 으로 적혀 있다.

### (4) `contains` · `clear` · `is_empty`

**언제 쓰나** — 값이 있는지 확인하거나 리스트를 비울 때.

```text
[1, 2, 3, 4, 5, 6].contains(&3)  → 머리부터 하나씩 비교 → true
[1, 2, 3, 4, 5, 6].contains(&9)  → 끝까지 비교 → false
clear()                          → []      is_empty() → true
```

- `contains` 는 머리부터 차례로 비교하는 선형 탐색이라 O(n) 이다.
- 값을 넘길 때는 참조(`&3`)로 넘긴다.
- `clear` 는 모든 노드를 없애고, 그 뒤 `is_empty()` 는 `true` 다.

> **선형 탐색** — 처음부터 하나씩 차례로 비교해 찾는 방법.\
> 예: `contains(&9)` 는 원소 6개를 모두 본 뒤 `false` 를 낸다.

### (5) 왜 거의 항상 `Vec` 이 나은가

**언제 쓰나** — 어떤 컬렉션을 고를지 정할 때.

```text
"중간에 넣기"를 할 때

LinkedList: 위치 찾기 ── head 부터 한 칸씩 ── O(n)  →  끼워 넣기 O(1)
                                                        (합계: 결국 O(n))
Vec:        위치 찾기 O(1)  →  뒤 원소를 한 칸씩 밀기 O(n)
            (밀기는 붙은 메모리를 한 번에 옮기는 일이라 CPU 가 빠르게 처리)
```

- 끼워 넣는 동작 자체는 O(1) 이지만, 그 자리까지 가는 데 O(n) 이 든다 — 그래서 실질적 이점이 적다.
- 노드가 힙에 흩어져 있어 다음 노드를 읽을 때마다 캐시 미스가 나기 쉽고, CPU 가 미리 읽어 오기(prefetch) 어렵다.
- 노드마다 `prev` · `next` 포인터를 따로 들고 있어 메모리를 더 쓴다.
- `list[2]` 같은 인덱스 접근이 없다 — 원하는 자리까지 순회해야 한다.
- 그래서 `Vec` 의 맨 앞 삽입이 O(n) 이어도 실제로는 `Vec` 이 더 빠른 경우가 많다.
- Rust 표준 라이브러리 문서도 「대부분 `Vec` 이나 `VecDeque` 를 쓰라」고 안내한다.

> **캐시 지역성** — 가까이 붙은 메모리를 이어서 읽을 때 CPU 캐시가 잘 맞는 성질.\
> 예: `Vec` 을 처음부터 훑으면 다음 원소가 이미 캐시에 올라와 있는 경우가 많다.

> **캐시 미스** — 읽으려는 데이터가 CPU 캐시에 없어 더 느린 메인 메모리까지 가야 하는 일.\
> 예: 흩어진 노드를 `next` 로 따라갈 때 자주 일어난다.

### (6) 대안 — 큐는 `VecDeque`

**언제 쓰나** — 뒤에 넣고 앞에서 빼는 큐가 필요할 때.

```text
queue.push_back("작업1"), queue.push_back("작업2")   →  ["작업1", "작업2"]
while let Some(task) = queue.pop_front() { … }       →  작업1 처리 → 작업2 처리 → None 이면 멈춤
```

- `VecDeque` 는 양쪽 끝 넣기 · 빼기가 O(1) 이라 `LinkedList` 대신 권장된다.
- `while let Some(task) = queue.pop_front()` 는 큐가 빌 때(`None`)까지 앞에서 하나씩 꺼내는 관용구다.

> **`VecDeque`** — 양쪽 끝에서 O(1) 로 넣고 뺄 수 있는, 배열 기반의 양방향 큐.\
> 예: 작업 대기열을 만들 때 쓴다.

## 문법 — 형태와 규칙

```rust
use std::collections::LinkedList;

fn main() {
    let mut a: LinkedList<&str> = LinkedList::new();
    a.push_back("b");
    a.push_front("a");                  // [a, b]
    let mut b: LinkedList<&str> = ["c", "d"].into_iter().collect();
    a.append(&mut b);                   // a = [a, b, c, d], b = []
    if let Some(x) = a.pop_front() {
        println!("{x}");
    }
    for s in a.iter().rev() {
        print!("{s} ");
    }
}
```

- `use std::collections::LinkedList;` 로 가져온다 — 프렐류드에 없다.
- 만들기: `LinkedList::new()` 또는 반복자에 `.collect()`(타입을 `LinkedList<T>` 로 밝힌다).
- 넣기: `push_back(x)` · `push_front(x)` — 둘 다 O(1), `&mut self` 가 필요하다.
- 보기: `front()` · `back()` → `Option<&T>`, `len()` · `is_empty()`.
- 빼기: `pop_front()` · `pop_back()` → `Option<T>`.
- 합치기: `a.append(&mut b)` — O(1), 뒤에 `b` 는 빈 리스트로 남는다.
- 찾기 · 비우기: `contains(&x)`(O(n)) · `clear()`.
- 순회: `for v in &list` · `list.iter()` · `list.iter().rev()`.
- `list[i]` 인덱싱 문법은 없다.

원본 비교표:

| 연산 | `Vec` | `LinkedList` |
|---|---|---|
| `push_back` | O(1)\* | O(1) |
| 맨 앞에 넣기 | O(n) | O(1) |
| 인덱스 접근 | O(1) | O(n) |
| 중간 삽입 | O(n) | O(1)\*\* |
| 캐시 친화성 | 매우 좋음 | 나쁨 |
| 메모리 오버헤드 | 낮음 | 높음 |
| `append` | O(n) | O(1) |
| `split` | O(n) | O(n) |

\* amortized — 평균은 O(1) 이지만 가끔 재할당이 일어난다.
\*\* 커서가 이미 그 위치에 있을 때.

> **amortized(분할 상환)** — 여러 번 했을 때 한 번당 평균 비용으로 따지는 복잡도.\
> 예: `Vec::push` 는 가끔 재할당하지만 평균 O(1) 이다.

> **커서** — 리스트 안의 한 위치를 가리키고 앞뒤로 움직이며 그 자리에서 넣고 빼는 도구.\
> 예: 커서가 3번째 노드에 있으면 그 옆에 바로 끼워 넣을 수 있다.

## 어디서 틀리나

### 1. 「중간 삽입 O(1)」만 보고 고른다
O(1) 은 커서가 이미 그 자리에 있을 때 이야기다.
위치를 찾는 데 O(n) 이 들기 때문에 실질적 이점이 적다.

### 2. 복잡도가 같으면 속도도 같다고 생각한다
`LinkedList` 는 노드가 흩어져 있어 캐시 미스가 잦다.
CPU 캐시 지역성 때문에 `Vec` 이 거의 항상 더 빠르다.

### 3. `pop_front` · `front` 가 값을 바로 준다고 생각한다
둘 다 `Option` 으로 감싸서 준다 — 비었을 때를 다뤄야 한다.
`front` 는 참조를 담은 `Option<&T>`, `pop_front` 는 값 자체를 담은 `Option<T>` 다.

### 4. `append` 뒤의 두 번째 리스트를 잊는다
`list2` 는 사라지지 않고 빈 리스트로 남는다.
노드가 옮겨 갔을 뿐 변수는 여전히 쓸 수 있다.

### 5. 메모리 오버헤드를 숫자 하나로 외운다
원본 출력은 「노드마다 `prev`/`next` 포인터 (16바이트)」, 원본 주석은 「16~24바이트」라 적는다.
포인터 크기는 플랫폼에 따라 다르므로 정확한 숫자는 환경마다 다르다(확인 필요).

### 6. 「`Vec` 의 `push_front`」라는 메서드가 있다고 생각한다
원본 결론은 「`Vec` 의 `push_front` 가 O(n) 이어도」라고 적는다.
그런데 `Vec` 에는 `push_front` 라는 메서드가 없다 — 맨 앞에 넣으려면 `insert(0, x)` 를 쓴다(원본에 근거 없음 — 추론).
원본의 뜻은 「`Vec` 의 맨 앞에 넣는 일」로 읽어야 한다.

### 7. 큐를 `LinkedList` 로 만든다
양쪽 끝 작업만 필요하면 `VecDeque` 가 맞다.
원본도 큐에는 `VecDeque` 를 권장한다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| `LinkedList` 는 이중 연결 리스트다 | 표준 라이브러리 API 문서가 밝히는 자료구조 |
| `push_*` · `pop_*` · `append` 가 O(1) | 표준 라이브러리 문서가 밝히는 복잡도(확인 필요) |
| `{:?}` 가 `[0, 1, 2, 3]` 꼴로 찍힌다 | 현재 표준 라이브러리 `Debug` 구현 — `Debug` 출력 형식은 안정된 약속이 아니다(확인 필요) |
| 노드당 포인터 오버헤드 16바이트 | 64비트 플랫폼의 포인터 크기에 따른 값 — 플랫폼 · 할당기에 따라 다르다(확인 필요) |
| `Vec` 이 거의 항상 더 빠르다 | 언어 보장이 아니라 CPU 캐시 구조에 따른 경험칙 |
| 중간 삽입 O(1) 은 커서가 있을 때 | 커서 API 가 안정판에 있는지는 버전에 따라 다르다(확인 필요) |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 대부분의 순서 있는 목록 | `Vec` | `LinkedList` |
| 뒤에 넣고 앞에서 빼는 큐 | `VecDeque` | `LinkedList` |
| 인덱스로 자주 접근 | `Vec` | `LinkedList`(O(n) 순회) |
| 두 리스트를 O(1) 로 합쳐야 함 | `LinkedList::append` | `Vec::append`(원소를 옮김) |
| 리스트 중간에서 대량 삽입 · 삭제, 랜덤 접근 불필요 | `LinkedList` 를 고려 | 복잡도만 보고 `Vec` 을 무조건 배제하지도 말 것 — 측정해 본다 |

## 핵심 문장

1. **`LinkedList` 는 이중 연결 리스트다** — 양 끝 넣기 · 빼기와 `append` 가 O(1), 인덱싱은 O(n).
2. **중간 삽입 O(1) 은 위치를 찾은 뒤의 이야기다** — 찾는 데 O(n) 이 들어 이점이 적다.
3. **흩어진 노드는 캐시 미스와 포인터 오버헤드를 부른다** — 그래서 `Vec` 이 거의 항상 빠르다.
4. **양쪽 끝 작업은 `VecDeque`, 그 밖은 `Vec`** — 표준 라이브러리 문서의 안내도 같다.

## 용어 풀이

- **노드** — 값과 이웃 포인터를 함께 담은 연결 리스트의 칸.
- **이중 연결 리스트** — 노드가 앞 · 뒤 노드를 모두 가리키는 리스트.
- **peek** — 값을 빼지 않고 보기만 하는 일.
- **`DoubleEndedIterator`** — 양 끝에서 값을 꺼낼 수 있는 반복자, `.rev()` 를 쓸 수 있다.
- **선형 탐색** — 처음부터 하나씩 비교해 찾는 방법.
- **캐시 지역성** — 붙은 메모리를 이어 읽을 때 캐시가 잘 맞는 성질.
- **캐시 미스** — 데이터가 캐시에 없어 메인 메모리까지 가야 하는 일.
- **prefetch** — CPU 가 곧 쓸 메모리를 미리 캐시로 읽어 오는 일.
- **amortized** — 여러 번의 평균으로 따진 비용.
- **커서** — 리스트 안 한 위치를 가리키며 그 자리에서 넣고 빼는 도구.
- **`VecDeque`** — 양 끝 O(1) 인 배열 기반 양방향 큐.
