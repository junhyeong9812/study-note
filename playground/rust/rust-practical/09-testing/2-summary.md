## 한눈에 — 쉽게 말하면

**테스트는 「매장 직원 교육용 연습 단말기」로 결제 절차를 미리 돌려 보는 일이다.**
교육 때는 진짜 카드사에 연결하지 않는다.
대신 「승인」이나 「거절」처럼 미리 정해 둔 답만 내놓고, 카드를 몇 번 긁었는지 적어 두는 연습용 단말기를 꽂는다.
검사관은 체크리스트를 들고 「0원 결제는 막았나」「거절이 나면 직원이 그대로 알렸나」를 하나씩 확인한다.
Rust 의 테스트도 똑같은 구조다.

| 비유 | 실체 |
|---|---|
| 결제를 처리하는 직원 | `PaymentService` |
| 단말기를 꽂는 규격 | `PaymentGateway` 트레이트 |
| 진짜 카드 단말기 | `StripeGateway` |
| 연습용 단말기 (정해진 답 + 긁은 횟수 기록) | `MockGateway` |
| 검사관의 체크 항목 하나 | `assert!` · `assert_eq!` · `assert_ne!` |
| 체크리스트 한 장 | `#[test]` 함수 하나 (예제에서는 `test!` 블록 하나) |
| 교육장에서만 쓰는 장비 | `#[cfg(test)] mod tests` |

```text
   운영                         테스트
 ┌──────────────┐           ┌──────────────┐
 │PaymentService│           │PaymentService│
 └──────┬───────┘           └──────┬───────┘
        │ PaymentGateway 규격       │ PaymentGateway 규격
 ┌──────▼───────┐           ┌──────▼───────┐
 │StripeGateway │           │ MockGateway  │ ← 정해진 답 + 호출 기록
 └──────────────┘           └──────────────┘
                                   ▲
                            assert 로 결과와 기록을 확인
```

## 이 주제가 답하려는 질문

1. Rust 에서 「테스트 하나가 통과했다 / 실패했다」는 무엇으로 갈리나?
2. 단위 테스트와 통합 테스트는 어디에 두고, 어떤 속성 · 매크로 · 명령으로 다루나?
3. 바깥 시스템(결제 API)에 기대는 코드를 바깥 시스템 없이 어떻게 시험하나?
4. 테스트하기 쉬운 대상 코드는 어떤 꼴로 짜나?

## 동작 방식

### (1) assert 매크로 — 조건이 어긋나면 패닉한다

**언제 쓰나** — 「이 값은 이래야 한다」를 코드로 못 박을 때 쓴다.
테스트의 판정은 전부 이 매크로가 내린다.

```text
assert_eq!(sum.amount, 3000);
        │
        ├─ 두 값이 같다 ──→ 아무 일 없이 다음 줄로
        │
        └─ 두 값이 다르다 ─→ 패닉 (왼쪽 값 · 오른쪽 값을 메시지에 담는다)
```

- `assert!(식)` 은 식이 `true` 인지 본다.
- `assert_eq!(a, b)` 는 `a == b` 인지 보고, `assert_ne!(a, b)` 는 `a != b` 인지 본다.
- 어긋나면 셋 다 패닉한다.
- `assert_eq!` 와 `assert_ne!` 는 실패할 때 두 값을 메시지에 찍어야 하므로, 비교하는 타입에 `PartialEq`(비교)와 `Debug`(찍기)가 둘 다 있어야 한다.

> **패닉** — 프로그램이 더 진행할 수 없다고 보고 현재 흐름을 멈추는 일.\
> 예: `assert!(false)` 를 만나면 그 자리에서 패닉한다.

### (2) 테스트 하나 = 패닉 없이 끝나면 통과

**언제 쓰나** — 여러 검사를 한 번에 돌리면서, 하나가 실패해도 나머지를 계속 돌려 성적을 모을 때.

```text
테스트 본문 실행
   │
   ├─ 끝까지 패닉 없음 ──→ 통과 (✓, passed += 1)
   │
   └─ 중간에 패닉 ──────→ 실패 (✗, failed += 1)
                           └─ 그래도 다음 테스트로 넘어간다
```

- `cargo test` 는 `#[test]` 가 붙은 함수를 하나씩 돌리고, 패닉한 함수를 실패로 센다.
- 예제의 `run_tests` 는 이 동작을 `main` 안에서 흉내 낸다(원본 주석: 「cargo test의 동작 모방」).
- 흉내의 핵심은 `test!` 매크로다.
- 매크로는 본문을 클로저로 감싸 `std::panic::catch_unwind` 에 넘긴다.
- `catch_unwind` 는 본문이 정상 종료하면 `Ok`, 패닉하면 `Err` 를 돌려준다.
- 그래서 패닉이 `main` 까지 번지지 않고 `✓` 또는 `✗` 한 줄을 찍은 뒤 다음 테스트로 간다.
- `catch_unwind` 가 없으면 첫 실패에서 프로그램 전체가 멈추고, 뒤의 테스트는 돌지 못한다.
- 마지막에 `총 결과: {passed} 성공, {failed} 실패` 를 찍는다.

> **catch_unwind** — 클로저를 실행하다 난 패닉을 잡아 `Err` 로 바꿔 주는 표준 함수.\
> 예: `catch_unwind(|| panic!("x"))` 는 `Err(..)` 를 돌려준다.

### (3) 테스트 대상 — 검증하는 생성자를 가진 `Money`

**언제 쓰나** — 잘못된 값이 아예 만들어지지 않게 하고, 그 규칙을 테스트로 고정할 때.

```text
Money::new(1000, "usd")
   │
   ├─ currency.len() != 3 ? ──예──→ Err("통화 코드는 3자리여야 합니다")
   │
   └─아니오─→ Ok(Money { amount: 1000, currency: "USD" })   ← 대문자로 정규화
```

- `amount` 는 `i64` 이고 센트 단위다.
- `1050` 은 10달러 50센트를 뜻한다.
- 부동소수점(`f64`)은 십진 소수를 정확히 담지 못해 더하고 곱할 때 오차가 쌓인다.
- 정수 센트로 두면 덧셈 · 곱셈이 정확하다.
- `new` 는 통화 코드가 3자리(원본 주석: ISO 4217)인지 검사하고 대문자로 바꾼다.
- 그래서 `"usd"` 와 `"USD"` 는 같은 통화로 취급된다.
- `add` 는 통화가 다르면 `Err("통화 불일치: USD != EUR")` 꼴의 에러를, 같으면 합을 돌려준다.
- `multiply(factor)` 는 금액에 정수를 곱한다.
- `display` 는 `amount / 100` 을 정수부로, `(amount % 100).abs()` 를 두 자리 소수부(`{:02}`)로 찍는다.
- `1050` 은 `"10.50 USD"` 가 된다.

> **스마트 생성자** — 값을 검사한 뒤에만 구조체를 만들어 `Result` 로 돌려주는 생성 함수.\
> 예: `Money::new(1000, "K")` 는 `Err` 를 돌려준다.

예제가 `Money` 에 거는 테스트 일곱 개는 이렇다.

| 테스트 이름 | 확인하는 것 |
|---|---|
| 유효한 Money 생성 | `(1000, "KRW")` → 금액 1000, 통화 `"KRW"` |
| 잘못된 통화 코드 | `(1000, "K")` → `Err`, 메시지에 「3자리」 |
| 소문자 통화 코드 대문자 변환 | `"usd"` → `"USD"` |
| 같은 통화 덧셈 | 1000 + 2000 → 3000, 통화 `"USD"` |
| 다른 통화 덧셈 실패 | USD + EUR → `Err` |
| 곱셈 | 999 × 3 → 2997 |
| 표시 형식 | 1050 → `"10.50 USD"` |

### (4) 트레이트로 의존성을 갈라 Mock 을 꽂는다

**언제 쓰나** — 테스트하려는 코드가 네트워크 · 결제 · 데이터베이스처럼 테스트에서 진짜로 부르면 안 되는 것에 기댈 때.

```text
struct PaymentService<G: PaymentGateway> { gateway: G }

PaymentService::new(StripeGateway)            → 운영: 진짜 결제
PaymentService::new(MockGateway::succeeding()) → 테스트: 항상 "tx_mock_123"
PaymentService::new(MockGateway::failing("카드 거절")) → 테스트: 항상 Err("카드 거절")
```

- `PaymentGateway` 트레이트는 `charge` 와 `refund` 두 메서드의 꼴만 정한다.
- `PaymentService` 는 구체 타입이 아니라 「`PaymentGateway` 를 구현한 아무 `G`」를 받는다.
- 바깥에서 게이트웨이를 만들어 `new` 로 넣어 주므로, 서비스 코드를 한 줄도 고치지 않고 진짜와 가짜를 바꿔 꽂을 수 있다.
- 서비스가 구체 구현이 아니라 추상(트레이트)에 기대게 하는 이 짜임을 원본 주석은 「의존성 역전」이라 부른다.
- `process_payment` 는 금액이 0 이하이면 `Err("금액은 양수여야 합니다")`, 카드가 빈 문자열이면 `Err("카드 정보 필요")` 를 돌려주고, 둘 다 통과해야 `gateway.charge` 를 부른다.
- 검증에서 걸리면 `charge` 는 불리지 않는다.
- `charge` 가 `Err` 를 돌려주면 서비스는 그 값을 그대로 돌려준다(에러 전파).

> **Mock** — 테스트에서 진짜 의존 대상 대신 꽂는 가짜 구현. 정해 둔 답을 내놓고 호출을 기록한다.\
> 예: `MockGateway::failing("카드 거절")` 은 `charge` 마다 `Err("카드 거절")` 을 돌려준다.

> **의존성 주입** — 객체가 쓸 협력자를 안에서 만들지 않고 바깥에서 넣어 받는 방식.\
> 예: `PaymentService::new(gateway)` 가 게이트웨이를 넣어 받는다.

### (5) Mock 은 답을 내놓고 호출을 기록한다 — `RefCell`

**언제 쓰나** — 「결과가 맞나」뿐 아니라 「몇 번, 무엇으로 불렸나」까지 확인할 때.

```text
service.process_payment(&5000 USD, "card1")
   └→ MockGateway::charge(&self, ..)
        ├─ charge_calls.borrow_mut().push((5000, "card1"))   ← &self 인데도 기록
        └─ charge_result.clone() 을 돌려줌                   ← 미리 정한 답

service.gateway.charge_call_count()  →  charge_calls.borrow().len()  →  1
```

- `charge` 는 트레이트가 `&self`(공유 참조)로 정해 두었다.
- 공유 참조로는 보통 필드를 바꿀 수 없다.
- `RefCell` 은 빌림 규칙을 컴파일 때가 아니라 실행 중에 검사하므로, `&self` 에서도 `borrow_mut()` 으로 안쪽 `Vec` 을 바꿀 수 있다.
- 기록은 `(금액, 카드)` 짝으로 쌓인다.
- `charge_call_count` 는 쌓인 짝의 개수를 센다.
- `charge_result` 를 `clone()` 해서 돌려주므로, 여러 번 불려도 매번 같은 답이 나온다.

> **내부 가변성** — 공유 참조(`&`)만 가진 상태에서 안쪽 값을 바꿀 수 있게 하는 짜임.\
> 예: `RefCell<Vec<_>>` 에 `&self` 로 `push` 한다.

예제가 `PaymentService` 에 거는 테스트 다섯 개는 이렇다.

| 테스트 이름 | 꽂는 Mock | 확인하는 것 |
|---|---|---|
| 결제 성공 | `succeeding()` | 5000 USD → `Ok("tx_mock_123")` |
| 결제 금액 0 이하 거부 | `succeeding()` | 0 USD → `Err`, 메시지에 「양수」 |
| 카드 정보 없으면 거부 | `succeeding()` | 카드 `""` → `Err` |
| 게이트웨이 실패 전파 | `failing("카드 거절")` | `Err`, 메시지에 「카드 거절」 |
| Mock 호출 횟수 검증 | `succeeding()` | 결제 한 번 → 호출 기록 1개 |

### (6) 실제 배치 — 단위 테스트 · 통합 테스트 · 속성

**언제 쓰나** — `run_tests` 같은 흉내 대신 `cargo test` 로 돌리는 진짜 테스트를 쓸 때.

```text
src/money.rs
 ├─ struct Money … (대상 코드)
 └─ #[cfg(test)]           ← cargo test 로 빌드할 때만 컴파일
    mod tests {
        #[test] fn add_same_currency() { … }   ← 단위 테스트
    }

tests/payment.rs           ← 통합 테스트 (crate 를 바깥에서 쓰듯이)
```

- 단위 테스트는 대상 코드와 같은 파일의 `#[cfg(test)] mod tests` 안에 쓴다.
- `#[cfg(test)]` 덕분에 테스트 코드는 일반 빌드에 들어가지 않는다.
- 통합 테스트는 프로젝트의 `tests/` 디렉토리에 둔다.
- `#[should_panic]` 을 붙인 테스트는 패닉해야 통과한다.
- `#[ignore]` 를 붙인 테스트는 기본으로 빠지고, `cargo test -- --ignored` 로 돌린다.
- `cargo test` 는 테스트 안의 `println!` 출력을 기본으로 가린다.
- 보려면 `cargo test -- --nocapture` 로 돌린다.
- 예제의 `test!` 한 블록은 `#[test]` 함수 하나에 해당한다.

## 문법 — 형태와 규칙

```rust
pub fn double(x: i64) -> i64 { x * 2 }

#[cfg(test)]
mod tests {
    use super::*;                 // 바깥 모듈의 항목을 가져온다

    #[test]
    fn doubles() { assert_eq!(double(21), 42); }

    #[test]
    #[should_panic]
    fn fails_on_purpose() { assert!(double(1) == 3); }

    #[test]
    #[ignore]
    fn slow_case() { assert_ne!(double(0), 1); }
}
```

- `#[test]` 는 인자 없는 함수 위에 붙인다.
- 테스트 함수는 패닉 없이 끝나면 통과다.
- `#[cfg(test)]` 는 붙은 항목을 테스트 빌드에서만 컴파일하게 한다.
- `use super::*;` 로 테스트 모듈 바깥(대상 코드)의 항목을 이름만으로 부른다.
- `assert!(식)` · `assert_eq!(왼, 오)` · `assert_ne!(왼, 오)` 는 어긋나면 패닉한다.
- `assert_eq!` · `assert_ne!` 로 비교할 타입에는 `PartialEq` 와 `Debug` 가 있어야 한다 — 직접 만든 구조체면 `#[derive(Debug, PartialEq)]` 를 붙인다.
- `assert_eq!(money.currency, "KRW")` 처럼 `String` 과 `&str` 도 비교된다 — 표준 라이브러리가 두 타입 사이의 `PartialEq` 를 마련해 둔다.
- `Result` 를 돌려주는 함수는 `.is_ok()` · `.is_err()` 로 갈래를 보고, `.unwrap()` · `.unwrap_err()` 로 안쪽 값을 꺼내 다시 확인한다.

| 명령 | 하는 일 |
|---|---|
| `cargo test` | 단위 테스트와 `tests/` 의 통합 테스트를 돌린다 |
| `cargo test -- --nocapture` | 테스트 안 `println!` 출력을 보여 준다 |
| `cargo test -- --ignored` | `#[ignore]` 가 붙은 테스트를 돌린다 |

| 속성 · 매크로 | 뜻 |
|---|---|
| `#[cfg(test)]` | 테스트 코드 조건부 컴파일 |
| `#[test]` | 테스트 함수 표시 |
| `#[should_panic]` | 패닉을 예상하는 테스트 |
| `#[ignore]` | 기본 제외, `--ignored` 로 실행 |
| `assert!` / `assert_eq!` / `assert_ne!` | 참 / 동등 / 부등 검증 |

## 어디서 틀리나

### 1. 단위 테스트를 `#[cfg(test)]` 밖에 둔다

테스트 함수와 테스트용 헬퍼가 일반 빌드에 섞여 들어간다.
단위 테스트는 같은 파일의 `#[cfg(test)] mod tests` 안에 쓴다.

### 2. 통합 테스트를 `src/` 안에 둔다

통합 테스트는 `tests/` 디렉토리에 둔다.
그곳의 파일은 crate 를 바깥 사용자처럼 쓰는 시험이다.

### 3. `Debug` 없는 타입을 `assert_eq!` 에 넣는다

`assert_eq!` 는 `PartialEq` 와 `Debug` 가 둘 다 필요하다.
`Money` 에서 `Debug` 를 빼면 `assert_eq!(money_a, money_b)` 는 컴파일되지 않는다.
필드 하나(`i64` · `String`)만 비교하는 줄은 그 필드 타입이 이미 둘 다 갖고 있어 상관없다.

### 4. 테스트 안 `println!` 이 안 보인다고 당황한다

`cargo test` 는 출력을 가린다.
`cargo test -- --nocapture` 로 돌린다.

### 5. 의존 대상을 구체 타입으로 박아 버린다

`struct PaymentService { gateway: StripeGateway }` 로 쓰면 테스트에서 가짜를 꽂을 자리가 없다.
트레이트로 의존성을 추상화해야 Mock 을 주입할 수 있다.

### 6. `&self` 메서드 안에서 기록하려다 막힌다

트레이트가 `&self` 를 정해 두었으면 Mock 의 필드를 그냥 바꿀 수 없다.
기록용 필드를 `RefCell` 로 감싼다.

### 7. 음수 금액을 `display` 하면 부호가 사라질 수 있다

Rust 의 정수 나눗셈 `/` 는 0 쪽으로 버리고, `%` 는 왼쪽 피연산자의 부호를 따른다.
`-150` 은 `-150 / 100 = -1`, `-150 % 100 = -50` → `.abs()` 로 `50` → `"-1.50"` 이 되어 괜찮다.
`-50` 은 `-50 / 100 = 0`, `-50 % 100 = -50` → `50` → `"0.50"` 이 되어 음수 부호가 사라진다.
정수부가 0 인 음수에서 깨지므로, 이런 경계값이 바로 테스트로 박아 둘 자리다.

### 8. `currency.len()` 은 글자 수가 아니라 바이트 수다

`str::len()` 은 UTF-8 바이트 수를 센다.
한글 한 음절은 UTF-8 로 3바이트이므로 `Money::new(100, "원")` 은 3자리 검사를 통과해 `Ok` 가 된다.
「3자리」라는 의도는 영문 대문자 세 글자인데, 검사는 그것을 보장하지 못한다.

### 9. `multiply` 의 곱셈이 넘칠 수 있다

`i64` 범위를 넘는 곱은 debug 빌드에서 패닉하고, release 빌드에서는 기본으로 값이 감싸진다.
아주 큰 금액이나 배수를 다루면 `checked_mul` 같은 넘침 검사가 필요하다.

### 10. `run_tests` 의 `test!` 를 진짜 테스트로 착각한다

`test!` 매크로는 `cargo test` 의 동작을 `main` 에서 흉내 낸 것이다.
원본 주석대로 실제로는 `#[cfg(test)] mod tests { ... }` 안의 `#[test]` 함수로 쓴다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| 정수 `/` 는 0 쪽으로 버리고 `%` 는 왼쪽 피연산자 부호를 따른다 | 언어(Rust 의 정수 연산 규칙) |
| `str::len()` 은 UTF-8 바이트 수다 | 표준 라이브러리 문서 |
| `String` 과 `&str` 을 `==` · `assert_eq!` 로 비교할 수 있다 | 표준 라이브러리의 `PartialEq` 구현 |
| `catch_unwind` 는 패닉을 잡아 `Err` 로 돌려준다 | 표준 라이브러리 — 단 패닉 전략이 `abort` 로 설정된 빌드에서는 잡지 못한다 |
| `i64` 곱셈이 넘치면 debug 는 패닉, release 는 감싸기 | 컴파일러의 빌드 설정(overflow 검사 켜짐/꺼짐), 언어가 하나로 정하지 않는다 |
| `cargo test` 가 `println!` 을 가리고 `--nocapture` 로 보인다 | cargo 와 테스트 실행기 — 언어가 아니라 도구의 동작 |
| `#[cfg(test)]` 코드는 테스트 빌드에서만 컴파일된다 | 컴파일러가 테스트 빌드에서 `test` 설정을 켜는 규칙 |
| `charge_call_count` 가 「mockall 의 `.times()` 와 유사」 | 원본 주석의 비교 — 바깥 크레이트의 API 다 (확인 필요) |
| 통화 코드 3자리가 ISO 4217 이다 | 원본 주석의 주장 — 언어와 무관한 바깥 표준 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 함수 하나의 규칙(검증 · 계산)을 고정 | 같은 파일의 `#[cfg(test)] mod tests` + `#[test]` | `main` 에서 손으로 `println!` 비교 |
| crate 를 바깥에서 쓰는 흐름을 시험 | `tests/` 디렉토리의 통합 테스트 | `src/` 안에 섞어 둔 테스트 |
| 결제 · 네트워크에 기대는 코드 | 트레이트 + Mock 구조체 주입 | 테스트에서 진짜 API 호출 |
| 「몇 번 불렸나」 확인 | Mock 안 `RefCell<Vec<..>>` 호출 기록 | 기록 없는 Mock 으로 결과만 확인 |
| 패닉해야 맞는 경우 | `#[should_panic]` | 패닉을 잡지 않고 테스트 실패로 두기 |
| 오래 걸려 평소엔 빼고 싶은 테스트 | `#[ignore]` + `--ignored` | 주석 처리해 지워 두기 |
| 돈 계산 | 정수 센트(`i64`) | `f64` |

## 핵심 문장

1. **Rust 테스트는 패닉 없이 끝나면 통과다** — `assert!` · `assert_eq!` · `assert_ne!` 가 어긋나면 패닉해 실패로 갈린다.
2. **단위 테스트는 같은 파일의 `#[cfg(test)] mod tests`, 통합 테스트는 `tests/`** 에 둔다.
3. **의존성을 트레이트로 추상화하면 Mock 을 꽂을 수 있다** — 서비스는 그대로, 게이트웨이만 바꾼다.
4. **Mock 은 정해 둔 답을 내놓고 호출을 기록한다** — `&self` 에서 기록하려면 `RefCell` 이 필요하다.
5. **경계값이 테스트의 과녁이다** — 0원, 빈 카드, 다른 통화, 음수 표시, 바이트 길이처럼 규칙이 갈리는 자리를 박아 둔다.

## 용어 풀이

- **테스트** — 코드가 기대대로 동작하는지 코드로 확인하는 일.
- **단위 테스트** — 함수 · 타입 하나를 따로 떼어 확인하는 테스트. 같은 파일의 `mod tests` 에 둔다.
- **통합 테스트** — 여러 부분을 엮은 흐름을 crate 바깥에서 확인하는 테스트. `tests/` 에 둔다.
- **`#[test]`** — 함수를 테스트 함수로 표시하는 속성.
- **`#[cfg(test)]`** — 테스트 빌드에서만 컴파일하게 하는 조건부 컴파일 속성.
- **`#[should_panic]`** — 패닉해야 통과하는 테스트로 표시하는 속성.
- **`#[ignore]`** — 기본 실행에서 빼는 속성. `--ignored` 로 돌린다.
- **`assert!` · `assert_eq!` · `assert_ne!`** — 참 · 동등 · 부등을 확인하고 어긋나면 패닉하는 매크로.
- **`PartialEq`** — `==` 비교를 가능하게 하는 트레이트.
- **`Debug`** — `{:?}` 로 값을 찍을 수 있게 하는 트레이트.
- **패닉** — 진행할 수 없어 현재 흐름을 멈추는 일.
- **`catch_unwind`** — 패닉을 잡아 `Err` 로 바꾸는 표준 함수.
- **`AssertUnwindSafe`** — 클로저를 `catch_unwind` 에 넘길 수 있다고 단언하는 감싸개.
- **스마트 생성자** — 검사를 통과한 값만 만들어 `Result` 로 돌려주는 생성 함수.
- **트레이트** — 타입이 갖춰야 할 메서드의 꼴을 정한 것.
- **제네릭 경계** — `G: PaymentGateway` 처럼 타입 매개변수가 구현해야 할 트레이트를 정한 것.
- **의존성 주입** — 협력 객체를 바깥에서 넣어 받는 방식.
- **의존성 역전** — 구체 구현이 아니라 추상(트레이트)에 기대게 짜는 원칙.
- **Mock** — 테스트에서 진짜 대신 꽂는, 답을 정해 두고 호출을 기록하는 가짜 구현.
- **`RefCell`** — 빌림 검사를 실행 중에 하여 `&` 로도 안쪽 값을 바꾸게 해 주는 타입.
- **내부 가변성** — 공유 참조만으로 안쪽 값을 바꿀 수 있게 하는 짜임.
- **TDD(테스트 주도 개발)** — 실패하는 테스트를 먼저 쓰고, 통과하도록 코드를 짜는 개발 방식.
- **`--nocapture`** — `cargo test` 가 가리는 테스트 출력을 보이게 하는 옵션.

## 더 들어가면

- 단위 테스트는 같은 모듈 트리 안에 있으므로 `pub` 이 아닌 비공개 함수도 시험할 수 있고, 통합 테스트는 `pub` 항목만 쓸 수 있다 (확인 필요).
- `#[should_panic(expected = "3자리")]` 처럼 패닉 메시지 일부를 함께 확인하는 꼴이 있다 (확인 필요).
- 테스트 함수가 `Result<(), E>` 를 돌려주게 짜면 `?` 를 쓸 수 있고, `Err` 를 돌려주면 실패로 센다 (확인 필요).
- `cargo test` 는 기본으로 테스트를 여러 스레드에서 나란히 돌리며, `-- --test-threads=1` 로 하나씩 돌릴 수 있다 (확인 필요).
- `catch_unwind` 로 패닉을 잡아도 기본 패닉 훅은 패닉 메시지를 표준 에러로 찍는다 — 그래서 `test!` 의 `✗` 줄 근처에 패닉 메시지가 함께 나올 수 있다 (확인 필요).
- `test!` 의 클로저는 본문 안에서 지역 변수를 새로 만들 뿐 바깥 값을 거의 잡지 않아, `AssertUnwindSafe` 없이도 컴파일될 수 있다 — 본문이 `RefCell` 같은 값을 바깥에서 잡을 때를 대비한 감싸개로 보인다 (확인 필요).
- `StripeGateway` 는 예제에서 만들어지지 않고 `amount` · `transaction_id` 매개변수도 쓰이지 않아, 컴파일러가 쓰이지 않는 코드 경고를 낼 수 있다 (확인 필요).
- Mock 을 손으로 짜지 않고 트레이트에서 자동 생성해 주는 `mockall` 같은 크레이트가 있다 (확인 필요).
