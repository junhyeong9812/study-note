## 한눈에 — 쉽게 말하면

**메모리 매핑(mmap)은 「서고의 책을 복사해 오지 않고, 서고 선반을 내 책상 서랍처럼 열어 보는 것」이다.**
일반 파일 읽기는 사서(커널)에게 「몇 쪽부터 몇 쪽까지 복사해 주세요」라고 부탁해 내 공책(버퍼)에 받아 적는 일이다.
mmap 은 사서가 원본 책을 내 책상 서랍 번호(주소)에 이어 붙여 두고, 나는 서랍을 열 듯 원하는 쪽을 바로 펼쳐 보는 일이다.
파일과 프로그램 메모리도 똑같은 구조다.

| 비유 | 실체 |
|---|---|
| 서고의 원본 책 | 디스크의 파일(과 OS 의 페이지 캐시) |
| 사서 | 커널 |
| 복사해 받는 공책 | `read` 가 채우는 버퍼(`[0u8; 8192]`, `Vec<u8>`) |
| 「몇 쪽부터」라고 말하기 | `seek(SeekFrom::Start(offset))` |
| 서랍 번호에 이어 붙인 책 | 가상 메모리에 매핑된 파일(`Mmap`) |
| 서랍을 열어 바로 보기 | `mmap[0..100]` 같은 슬라이스 접근 |

```text
일반 I/O                                mmap
┌──────────┐  read (복사)  ┌────────┐     ┌──────────┐   매핑    ┌───────────────┐
│ 파일/커널 │ ───────────▶ │ 내 버퍼 │     │ 파일/커널 │ ═══════▶ │ 내 주소 공간   │
└──────────┘              └────────┘     └──────────┘ (복사 없음)│ mmap[i] 로 접근│
                                                               └───────────────┘
```

## 이 주제가 답하려는 질문

1. 파일 내용을 프로그램 메모리처럼(슬라이스처럼) 다루면 일반 `read` · `seek` 와 무엇이 달라지나?
2. 왜 mmap 은 대용량 파일, 특히 랜덤 액세스에 유리하다고 하나?
3. 왜 `memmap2` 의 `Mmap::map()` 은 `unsafe` 블록 안에서만 부를 수 있나?
4. 언제 mmap 을 쓰고, 언제 buffered I/O 로 충분한가?

## 동작 방식

이 항목의 예제는 실제 mmap 을 쓰지 않는다.
표준 라이브러리만으로 「일반 I/O 로는 이렇게 한다」를 보이고, mmap 이라면 그 자리가 어떻게 바뀌는지를 주석과 문자열로 대비한다.
`memmap2` 사용법은 실행되는 코드가 아니라 `println!` 으로 찍는 문자열로만 들어 있다.

### (1) 일반 I/O — 청크 단위로 복사해 온다

**언제 쓰나** — 파일을 처음부터 끝까지 한 번 훑으며 무언가를 셀 때.
예제의 `count_bytes_regular` 는 파일의 바이트마다 값(0~255)별 빈도를 센다.

```text
file.read(&mut buffer)       // buffer: [0u8; 8192] (스택의 8KB)
   │
   ▼ 커널이 파일 내용을 버퍼로 복사, 읽은 길이 n 을 돌려줌
n == 0 ? ── 예 ──▶ break (EOF)
   │ 아니오
   ▼
for &byte in &buffer[..n]  →  freq[byte as usize] += 1
   │
   └── 다시 read 로
```

- `read` 는 버퍼를 「채울 수 있는 만큼」 채우고, 실제로 채운 길이 `n` 을 돌려준다.
- `n` 이 0 이면 파일 끝(EOF)이므로 반복을 끝낸다.
- 버퍼 전체가 아니라 `&buffer[..n]` 만 센다 — 마지막 청크는 8192 보다 짧을 수 있고, 그 뒤쪽 칸에는 이전 청크의 찌꺼기가 남아 있기 때문이다.
- 빈도 배열 `[0u64; 256]` 은 바이트 값을 그대로 인덱스로 쓴다(`byte as usize`).
- 버퍼는 고정 크기 배열이라 힙 할당이 없다(원본 주석: 「스택 버퍼 - 힙 할당 없음」).

> **청크** — 큰 데이터를 일정 크기로 잘라 한 번에 다루는 덩어리.\
> 예: 44KB 파일을 8KB 버퍼로 읽으면 청크가 여러 개 생긴다.

> **EOF** — End Of File, 더 읽을 내용이 없는 파일 끝.\
> 예: `read` 가 0 을 돌려주면 EOF 다.

### (2) 랜덤 액세스 — 위치를 옮긴 뒤 읽는다

**언제 쓰나** — 파일의 중간 어느 지점(오프셋)만 콕 집어 읽을 때.
예제의 `read_at_offset(path, offset, len)` 이다.

```text
file.seek(SeekFrom::Start(offset))   // 파일 시작에서 offset 바이트 지점으로 커서 이동
   ▼
let mut buf = vec![0u8; len];        // len 바이트짜리 버퍼
let n = file.read(&mut buf)?;        // 최대 len 바이트를 복사해 옴
   ▼
buf.truncate(n);                     // 실제로 읽은 n 바이트만 남김
```

- `SeekFrom::Start(n)` 은 「파일 시작에서 n 바이트」 위치다.
- `read` 가 `len` 보다 적게 읽을 수 있으므로 `truncate(n)` 으로 남는 0 들을 잘라 낸다.
- mmap 이라면 이 세 단계가 `&mmap[offset..offset + len]` 슬라이스 하나로 바뀐다(원본 주석: 「mmap이라면 직접 슬라이스 인덱싱」).
- 잘라 낸 바이트를 문자열로 보일 때는 `String::from_utf8_lossy` 를 쓴다 — 올바르지 않은 UTF-8 바이트는 `�` 로 바꾼다.

> **오프셋** — 파일(또는 메모리) 시작에서 센 바이트 위치.\
> 예: 오프셋 0 은 첫 바이트, 오프셋 100 은 101번째 바이트.

> **랜덤 액세스** — 앞에서부터 차례로가 아니라 임의의 위치로 바로 가서 읽는 접근.\
> 예: 오프셋 0 을 읽고 곧바로 오프셋 100 을 읽기.

### (3) 통째로 읽어 검색한다

**언제 쓰나** — 파일 전체에서 바이트 패턴이 나오는 모든 위치를 찾을 때.
예제의 `search_in_file` 이다.

```text
let data = fs::read(path)?;               // 파일 전체를 Vec<u8> 로 복사
for i in 0..data.len().saturating_sub(pattern.len()) {
    if &data[i..i + pattern.len()] == pattern { positions.push(i as u64); }
}
```

- `fs::read` 는 파일 전체를 한 번에 `Vec<u8>` 으로 읽는다 — 파일 크기만큼 메모리를 쓴다.
- 위치 `i` 마다 `pattern.len()` 길이의 슬라이스를 떼어 패턴과 바이트 단위로 비교한다.
- `saturating_sub` 는 뺄셈 결과가 0 아래로 내려가면 0 에서 멈춘다 — 파일이 패턴보다 짧을 때 `usize` 언더플로를 막는다.
- mmap 이라면 `data` 가 복사본이 아니라 매핑된 파일 그 자체가 된다(원본 주석: 「mmap이면 zero-copy」).

> **언더플로** — 부호 없는 정수에서 0 보다 작은 값을 만들려는 일.\
> 예: `usize` 인 `3 - 6` 은 디버그 빌드에서 패닉, `3usize.saturating_sub(6)` 은 0.

### (4) mmap — 파일을 주소 공간에 붙인다

**언제 쓰나** — 큰 파일을 여기저기 건너뛰며 읽을 때, 또는 여러 프로세스가 같은 파일 내용을 나눠 볼 때.
예제가 문자열로 보여 주는 `memmap2` 패턴은 다음과 같다(Cargo.toml 에 `memmap2 = "0.9"` 라고 적혀 있다).

```text
File::open("data.bin")
   ▼
unsafe { Mmap::map(&file)? }          // 파일을 가상 메모리에 매핑(읽기 전용)
   ▼
mmap[0..100]                          // 슬라이스처럼 접근 — 복사 없음

OpenOptions::new().read(true).write(true).open("data.bin")
   ▼
unsafe { MmapMut::map_mut(&file)? }   // 쓰기 가능한 매핑
   ▼
mmap[0] = 42;                         // 메모리에 쓰듯 파일에 쓰기
mmap.flush()?;                        // 디스크에 반영
```

- 매핑은 파일을 가상 메모리에 붙여, 프로그램이 파일을 바이트 슬라이스처럼 다루게 한다.
- 커널 공간에서 유저 공간 버퍼로 내용을 복사하는 단계가 없다(zero-copy).
- OS 의 페이지 캐시를 그대로 쓴다.
- 랜덤 액세스가 슬라이스 인덱싱이 되므로 매우 효율적이다.
- 여러 프로세스가 같은 매핑을 공유할 수 있다.
- 쓰기 매핑에 쓴 내용은 `flush()` 로 디스크에 반영한다.

> **가상 메모리** — 프로세스가 보는 주소 공간으로, OS 가 실제 메모리나 파일에 연결해 준다.\
> 예: 매핑된 파일의 1000번째 바이트가 어떤 주소 하나로 보인다.

> **zero-copy** — 데이터를 중간 버퍼로 옮겨 적지 않고 원래 자리에서 바로 쓰는 방식.\
> 예: `read` 로 버퍼에 받지 않고 `mmap[i]` 로 바로 읽기.

> **페이지 캐시** — OS 가 디스크의 파일 내용을 메모리에 들고 있는 캐시.\
> 예: 방금 읽은 파일을 다시 읽으면 디스크 대신 페이지 캐시에서 온다.

### (5) 왜 `unsafe` 인가 · 오류는 어디로 오나

**언제 쓰나** — mmap 을 쓸지 말지 판단할 때 반드시 따져 볼 대가다.

```text
내 프로세스: let s: &[u8] = &mmap[..];   // 「이 바이트들은 안 바뀐다」고 믿는 참조
                     │
다른 프로세스: 같은 파일을 수정하거나 잘라 냄
                     ▼
내 슬라이스 밑의 바이트가 바뀌거나 사라짐 → UB, 또는 접근 시 SIGBUS/SIGSEGV
```

- Rust 의 공유 참조(`&[u8]`)는 「참조가 살아 있는 동안 값이 바뀌지 않는다」를 전제로 한다.
- 매핑된 파일은 내 프로그램 바깥(다른 프로세스)에서 바뀔 수 있고, 컴파일러는 그것을 막을 수 없다.
- 그래서 `Mmap::map()` 은 `unsafe` 다 — 「다른 누구도 이 파일을 건드리지 않는다」는 약속을 호출하는 쪽이 진다.
- 그 약속이 깨지면 정의되지 않은 동작(UB)이 일어날 수 있다.
- 일반 I/O 의 오류는 `read` 가 돌려주는 `Result` 로 오지만, mmap 의 접근 오류는 슬라이스를 읽는 순간 SIGBUS/SIGSEGV 신호로 올 수 있다 — `?` 로 잡을 자리가 없다.

> **UB (정의되지 않은 동작)** — 언어가 결과를 아무것도 약속하지 않는 상태.\
> 예: 바뀌지 않는다고 믿은 `&[u8]` 의 바이트가 실행 중에 바뀌는 것.

> **SIGBUS / SIGSEGV** — 잘못된 메모리 접근 때 OS 가 프로세스에 보내는 신호.\
> 예: 매핑 범위의 파일이 잘려 나간 뒤 그 바이트를 읽으면 신호를 받을 수 있다.

### (6) 예제의 테스트 파일 모양

**언제 쓰나** — 예제가 찍는 값을 코드에서 추론할 때.
`main` 은 `/tmp/rust_mmap_test.txt` 에 `writeln!(f, "Line {}: Hello, memory-mapped world! ABCDEF", i)` 를 `i = 0..1000` 동안 쓴다.

```text
한 줄 = "Line " (5) + 숫자 (d) + ": " (2) + "Hello, memory-mapped world! ABCDEF" (34) + "\n" (1)
      = 42 + d 바이트

i = 0~9     : d=1 → 43바이트 × 10   =   430
i = 10~99   : d=2 → 44바이트 × 90   =  3960
i = 100~999 : d=3 → 45바이트 × 900  = 40500
                                  합 44890 바이트

줄 안에서 "ABCDEF" 는 "Line 0: " 꼴(8) + "Hello, memory-mapped world! "(28) 뒤 → 줄 시작에서 36 (한 자리 줄 기준)
줄 시작 오프셋(0~9 번 줄) = 43 × i  →  0, 43, 86, 129, …
```

- 각 줄에는 `H` 가 하나(`Hello`), `A` 가 하나(`ABCDEF`), 줄바꿈이 하나 있다.
- 파일을 만드는 `File` 은 블록 `{ … }` 이 끝날 때 버려져 닫힌다 — 그 뒤에야 다시 열어 읽는다.
- 끝에서 `fs::remove_file` 로 테스트 파일을 지운다.
- 이 표의 수는 코드를 읽어 센 값이다.

## 문법 — 형태와 규칙

표준 라이브러리로 오프셋을 읽는 최소 꼴과, `memmap2` 로 같은 일을 하는 꼴을 나란히 둔다.

```rust
use std::fs::File;
use std::io::{Read, Seek, SeekFrom};

// 일반 I/O: 오프셋 10 에서 4바이트
let mut f = File::open("data.bin")?;
f.seek(SeekFrom::Start(10))?;
let mut buf = vec![0u8; 4];
let n = f.read(&mut buf)?;
buf.truncate(n);

// memmap2 (외부 크레이트): 같은 4바이트
let f = File::open("data.bin")?;
let map = unsafe { memmap2::Mmap::map(&f)? };
let part: &[u8] = &map[10..14];
```

- `Read::read(&mut buf)` 는 `io::Result<usize>` 를 돌려준다 — 읽은 바이트 수이고, 0 이면 EOF 다.
- `Seek::seek(SeekFrom::Start(n))` 는 파일 시작에서 `n` 바이트로 커서를 옮긴다.
- `Vec::truncate(n)` 는 길이를 `n` 으로 줄인다.
- `fs::read(path)` 는 파일 전체를 `Vec<u8>` 로 읽고, `fs::metadata(path)?.len()` 은 파일 크기(바이트)다.
- `memmap2::Mmap::map(&file)` 은 읽기 전용 매핑, `MmapMut::map_mut(&file)` 은 쓰기 매핑이며 둘 다 `unsafe` 안에서 부른다.
- 쓰기 매핑은 읽기·쓰기로 연 파일(`OpenOptions::new().read(true).write(true)`)이 필요하다.
- `MmapMut` 에 쓴 내용은 `flush()` 로 디스크에 반영한다.
- `println!` 의 형식 문자열 안에서 글자 `{` · `}` 를 그대로 찍으려면 `{{` · `}}` 로 쓴다 — 원시 문자열 `r#"…"#` 이어도 형식 문자열이면 같다.
- `b'H'` 는 `u8` 바이트 리터럴, `b"ABCDEF"` 는 `&[u8; 6]` 바이트 문자열 리터럴이다.

## 어디서 틀리나

### 1. `read` 한 번이 버퍼를 다 채운다고 믿기

`read` 는 「최대」 버퍼 길이만큼 읽을 뿐, 다 채운다고 약속하지 않는다.
그래서 `count_bytes_regular` 는 `&buffer[..n]` 만 세고, `read_at_offset` 는 `truncate(n)` 을 한다.
버퍼 전체를 세면 마지막 청크 뒤쪽의 이전 데이터가 두 번 세어진다.

원본의 주장 → 왜 의심스러운가: 원본 주석은 `truncate` 를 「EOF 근접 시」 필요하다고 적는다.
그런데 `Read` 트레이트는 EOF 가 아니어도 짧게 읽을 수 있다고 둔다.
정확히 `len` 바이트가 필요하면 반복해서 읽거나 `read_exact` 같은 메서드를 써야 한다 (확인 필요).

### 2. `search_in_file` 의 범위가 마지막 위치를 빼먹는다

원본의 주장 → 왜 의심스러운가: 반복 범위는 `0..data.len().saturating_sub(pattern.len())` 다.
패턴이 들어갈 수 있는 마지막 시작 위치는 `len - plen` 인데, `..` 범위는 끝을 포함하지 않으므로 그 위치는 검사하지 않는다.
파일이 패턴으로 딱 끝나면 그 마지막 등장은 놓친다.
같은 까닭으로 파일 길이와 패턴 길이가 같으면 범위가 `0..0` 이 되어 아무것도 찾지 못한다.
예제의 파일은 각 줄이 `ABCDEF` 뒤에 줄바꿈을 두므로 이 빈틈에 걸리지 않는다.

### 3. `unsafe` 를 형식으로 여기기

`Mmap::map()` 이 `unsafe` 인 까닭은 다른 프로세스가 파일을 수정하면 UB 가 생길 수 있어서다.
`unsafe { … }` 로 감싸는 순간 「아무도 이 파일을 바꾸지 않는다」를 내가 보증한 셈이다.
여러 프로세스가 쓰는 파일, 로그처럼 계속 자라는 파일에 무심코 매핑을 거는 것은 이 보증을 어긴다.

### 4. 오류를 `Result` 로만 기다리기

mmap 단점 목록에 있듯 에러 처리가 SIGBUS/SIGSEGV 로 올 수 있다.
매핑 뒤 파일이 잘리면, 그 영역을 읽는 평범한 인덱싱에서 프로세스가 신호를 받는다.
`Mmap::map(&file)?` 의 `?` 는 매핑을 만드는 순간의 오류만 잡는다.

### 5. 작은 파일에도 mmap 을 쓰기

mmap 은 매핑을 세우는 비용이 있어 작은 파일에는 오버헤드다.
몇 KB 짜리 설정 파일이라면 `fs::read` 로 통째로 읽는 편이 단순하다.

### 6. 「mmap 이 언제나 더 빠르다」고 믿기

순차 읽기에서는 buffered I/O 도 충분히 빠르다.
mmap 이 특히 유리한 것은 랜덤 액세스가 많을 때다.
처음부터 끝까지 한 번 훑는 `count_bytes_regular` 같은 일은 일반 I/O 로도 충분하다.

### 7. `fs::read` 를 거대한 파일에 쓰기

`fs::read` 는 파일 전체를 메모리로 복사한다.
파일이 메모리보다 크면 쓸 수 없고, 커지는 만큼 메모리를 그대로 차지한다.
원본이 「mmap이면 zero-copy」라고 대비한 자리가 바로 여기다.

### 8. 형식 문자열 안의 중괄호

원본의 `memmap2` 안내는 `println!(r#"…"#)` 로 찍는데, 안의 `{` 를 `{{` 로 적었다.
원시 문자열이어도 `println!` 의 첫 인자는 형식 문자열이라 `{` 하나는 자리표시로 읽힌다.
그래서 화면에는 `{Mmap, MmapMut}` 처럼 중괄호가 하나씩 찍힌다.

### 9. `/tmp` 경로

예제는 `/tmp/rust_mmap_test.txt` 를 쓴다.
유닉스 꼴 경로라 그런 디렉터리가 없는 환경에서는 `File::create` 가 실패할 수 있다 (확인 필요).

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| mmap 은 커널 ↔ 유저 복사가 없다(zero-copy), 페이지 캐시를 쓴다 | OS(커널)의 메모리 매핑 동작 — Rust 가 보장하는 것이 아니다 |
| 여러 프로세스가 같은 매핑을 공유할 수 있다 | OS 와 매핑 방식(공유 매핑) — 크레이트 설정에 따라 다를 수 있다 (확인 필요) |
| 접근 오류가 SIGBUS/SIGSEGV 로 온다 | 유닉스 계열 OS 의 신호 — 다른 OS 에서는 다른 꼴로 온다 (확인 필요) |
| `Mmap::map()` 은 `unsafe` 다 | `memmap2` 크레이트의 API 설계 — 그 까닭(공유 참조의 불변 전제)은 Rust 언어 규칙 |
| `memmap2 = "0.9"` | 원본이 적은 크레이트 버전 — 언어와 무관 |
| `read` 는 읽은 길이를 돌려주고 0 은 EOF 다 | 표준 라이브러리 `Read` 트레이트의 계약 |
| 일반 파일에서 `read` 가 EOF 전이면 버퍼를 다 채운다 | 보장 없음 — 흔히 그렇게 되는 것은 OS · 파일 종류에 기댄 동작 |
| `[0u8; 8192]` 는 힙 할당이 없다 | 언어 의미론(배열은 값) — 정확히 어느 메모리에 놓이나는 컴파일러 몫 |
| `fs::read` 는 파일 전체를 `Vec<u8>` 로 읽는다 | 표준 라이브러리 |
| `saturating_sub` 는 0 에서 멈춘다 | 표준 라이브러리 정수 메서드 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 큰 파일을 여기저기 건너뛰며 읽기 | mmap 슬라이스 인덱싱 | 매번 `seek` + `read` |
| 파일을 처음부터 끝까지 한 번 훑기 | buffered I/O, 청크 `read` | 굳이 mmap (이득이 작다) |
| 작은 파일 | `fs::read` | mmap (오버헤드) |
| 다른 프로세스가 수정할 수 있는 파일 | 일반 I/O | `Mmap::map` (UB 위험) |
| 오류를 `Result` 로 다뤄야 하는 코드 | 일반 I/O | mmap (신호로 올 수 있다) |
| 메모리보다 큰 파일 전체 검색 | mmap 또는 청크 읽기 | `fs::read` |
| 여러 프로세스가 같은 내용을 나눠 보기 | mmap 공유 매핑 | 프로세스마다 따로 복사 |

## 핵심 문장

1. **mmap 은 파일을 가상 메모리에 붙여 슬라이스처럼 다루게 한다** — `seek` + `read` + `truncate` 가 `&mmap[a..b]` 하나가 된다.
2. **일반 I/O 는 커널에서 유저 버퍼로 복사하고, mmap 은 그 복사를 없앤다(zero-copy).**
3. **`read` 는 「최대」 버퍼만큼 읽는다** — 돌려받은 `n` 만큼만 써야 한다.
4. **`Mmap::map()` 이 `unsafe` 인 것은 바깥에서 파일이 바뀌면 UB 가 될 수 있어서다** — 오류도 `Result` 가 아니라 신호로 올 수 있다.
5. **mmap 은 대용량 · 랜덤 액세스에서 빛나고, 순차 읽기 · 작은 파일에는 일반 I/O 로 충분하다.**

## 관련 자료

- `zero-copy` — 같은 사이트의 관련 항목(이 폴더에 없어 링크를 걸지 않았다)
- `unsafe-raw-pointers` — 같은 사이트의 관련 항목(이 폴더에 없어 링크를 걸지 않았다)
- `benchmarking` — 같은 사이트의 관련 항목(이 폴더에 없어 링크를 걸지 않았다)
- 원본: study-site 항목 데이터 `data/rust/systems.json` 의 `mmap`

## 용어 풀이

- **mmap(메모리 매핑)** — 파일을 프로세스의 가상 메모리에 연결해 메모리처럼 읽고 쓰게 하는 기법.
- **memmap2** — Rust 에서 mmap 을 감싼 외부 크레이트, `Mmap` · `MmapMut` 을 준다.
- **`Mmap` / `MmapMut`** — 읽기 전용 매핑 / 쓰기 가능한 매핑.
- **가상 메모리** — 프로세스가 보는 주소 공간, OS 가 실제 메모리나 파일에 연결한다.
- **페이지 캐시** — OS 가 디스크 파일 내용을 메모리에 들고 있는 캐시.
- **zero-copy** — 데이터를 중간 버퍼로 옮겨 적지 않고 제자리에서 쓰는 방식.
- **buffered I/O** — 버퍼에 일정량씩 받아 오며 읽고 쓰는 일반 I/O.
- **청크** — 일정 크기로 자른 데이터 덩어리.
- **EOF** — 파일 끝, `read` 가 0 을 돌려주는 지점.
- **오프셋** — 시작에서 센 바이트 위치.
- **랜덤 액세스** — 임의 위치로 바로 가서 읽는 접근.
- **`seek` / `SeekFrom::Start`** — 파일 커서를 옮기는 메서드 / 시작 기준 위치.
- **`truncate`** — `Vec` 의 길이를 줄이는 메서드.
- **`from_utf8_lossy`** — 바이트를 문자열로 바꾸며 잘못된 UTF-8 은 `�` 로 바꾸는 함수.
- **`saturating_sub`** — 0 아래로 내려가면 0 에서 멈추는 뺄셈.
- **언더플로** — 부호 없는 정수에서 0 보다 작은 값을 만들려는 일.
- **UB(정의되지 않은 동작)** — 언어가 결과를 약속하지 않는 상태.
- **SIGBUS / SIGSEGV** — 잘못된 메모리 접근 때 OS 가 보내는 신호.
- **`unsafe`** — 컴파일러가 확인하지 못하는 약속을 프로그래머가 지는 블록.
- **`flush`** — 쓰기 매핑의 변경을 디스크에 반영하는 호출.

## 더 들어가면

- 매핑은 파일 전체를 한 번에 메모리로 올리지 않는다고 알려져 있다 — 접근한 페이지만 페이지 폴트로 그때그때 채운다 (확인 필요).
- 유닉스의 `mmap` 시스템 호출에는 변경을 파일에 반영하는 공유 매핑과, 내 프로세스에만 보이는 사적 매핑(copy-on-write)이 있다 (확인 필요).
- `memmap2` 의 `Mmap` 은 `Deref<Target = [u8]>` 를 구현해 `&[u8]` 처럼 쓰인다고 알려져 있다 (확인 필요).
- 접근 패턴을 OS 에 알려 미리 읽기를 조절하는 `madvise` 같은 힌트가 있다 (확인 필요).
- Windows 에서는 `CreateFileMapping` 계열 API 로 같은 일을 하며, 오류 꼴도 유닉스 신호와 다르다 (확인 필요).
- 파일 잠금(advisory lock)을 걸어도 다른 프로세스가 지키지 않으면 `unsafe` 의 전제를 완전히 지킬 수 없다 (확인 필요).
