## 한눈에 — 쉽게 말하면

**FFI 는 「통역사를 끼고 외국 회사와 거래하는 일」이다.**
우리 회사(Rust)는 자기 규칙(소유권 · 빌림 검사)으로 일한다.
외국 회사(C 라이브러리)는 다른 규칙으로 일하고, 우리 회사의 검사관은 그 회사 안을 들여다볼 수 없다.
그래서 거래할 때는 「상대가 약속대로 움직인다고 믿겠다」는 서명(`unsafe`)을 한다.
서류 양식도 다르다.
우리 회사의 문서(`String`)는 길이를 따로 적는다.
외국 회사의 문서(C 문자열)는 끝에 마침표(`\0`)를 찍어 끝을 알린다.
그래서 서류를 보낼 때는 마침표를 붙인 양식(`CString`)으로 바꾸고, 받을 때는 마침표까지 읽어 우리 양식(`&str`)으로 옮긴다(`CStr`).
Rust 의 FFI 도 똑같은 구조다.

> **FFI** — Foreign Function Interface. 한 언어에서 다른 언어로 만든 함수를 부르는 통로다.\
> 예: Rust 코드에서 C 표준 라이브러리의 `strlen` 을 부르는 것.

| 비유 | 실체 |
|---|---|
| 외국 회사 | C 라이브러리(libc 등) |
| 거래 약속 양식 | `extern "C"` (C 호출 규약) |
| 「믿겠다」 서명 | `unsafe` 블록 |
| 마침표로 끝나는 서류 | null 종료 문자열 |
| 보낼 서류(우리가 만든 것) | `CString` — 소유 |
| 받은 서류(빌려 보는 것) | `CStr` — 빌림 |
| 통역 창구 | 안전한 래퍼 함수 |

```text
   Rust 세계                         C 세계
 ┌──────────────┐   CString    ┌──────────────┐
 │ String / &str│ ───────────▶ │ char* + '\0' │
 │              │ ◀─────────── │              │
 └──────────────┘    CStr      └──────────────┘
         │ 호출: unsafe { abs(n) }       ▲
         └───────────────────────────────┘
```

## 이 주제가 답하려는 질문

1. Rust 코드에서 C 함수를 어떻게 선언하고 부르나, 왜 `unsafe` 가 필요한가?
2. 길이를 아는 Rust 문자열과 `\0` 으로 끝나는 C 문자열을 어떻게 서로 바꾸나?
3. 거꾸로, Rust 함수를 C 에서 부를 수 있게 하려면 무엇을 붙이나?
4. `unsafe` 를 코드 곳곳에 흩뿌리지 않으려면 어떻게 감싸나?

## 동작 방식

### (1) C 함수 선언과 호출

**언제 쓰나** — libc 같은 C 라이브러리에 이미 있는 함수를 Rust 에서 쓰고 싶을 때.

```text
extern "C" {                       컴파일러: "이런 이름 · 모양의 함수가
    fn abs(input: c_int) -> c_int;  어딘가 있다"고 기록만 한다
}                                          │
                                           ▼
unsafe { abs(-42) }                링커: libc 에서 abs 심볼을 찾아 연결
                                           │
                                           ▼
                                   실행: C 의 abs 가 돌고 42 를 돌려준다
```

- `extern "C" { … }` 블록은 함수의 **본문 없이 모양(시그니처)만** 적는다.
- `"C"` 는 C 호출 규약을 쓰겠다는 뜻이다 — 인자를 어느 레지스터 · 스택에 놓고 결과를 어디서 받는지의 약속이다.
- 본문은 링커가 링크할 때 libc 에서 찾아 붙인다.
- 컴파일러는 그 함수 안을 볼 수 없으므로, 선언한 모양이 맞는지 · 함수가 메모리를 망가뜨리지 않는지 검증하지 못한다.
- 그래서 이렇게 선언한 바깥 함수를 부르는 일은 `unsafe` 블록 안에서만 할 수 있다.

> **호출 규약(ABI)** — 함수를 부를 때 인자와 반환값을 기계 수준에서 주고받는 약속이다.\
> 예: 원본 주석은 x86-64 의 System V AMD64 ABI 를 예로 든다.

> **링커** — 컴파일된 조각들과 라이브러리를 이어 붙여, 선언만 된 이름을 실제 함수 주소로 채우는 도구다.\
> 예: `strlen` 이라는 이름을 libc 안의 `strlen` 본문에 연결한다.

인자 타입은 `std::os::raw` 의 `c_int` · `c_double` · `c_char` 를 쓴다.
이것들은 플랫폼마다 C 쪽 타입과 크기가 맞도록 정해 둔 **타입 별칭**이다.

### (2) 안전한 래퍼 — `unsafe` 를 한곳에 가두기

**언제 쓰나** — FFI 호출을 여러 곳에서 쓸 때, 호출하는 쪽은 평범한 safe 함수만 보게 하고 싶을 때.

```text
fn safe_abs(n: i32) -> i32 {      호출하는 쪽:  safe_abs(-42)   ← unsafe 없음
    unsafe { abs(n) }                                 │
}                                                     ▼
                                  래퍼 안:      unsafe { abs(n) } ← 여기만 unsafe
```

- 래퍼는 `unsafe` 를 함수 안으로 흡수해 바깥에 safe API 를 내놓는다.
- 대신 래퍼를 쓴 사람이 「어떤 입력이 와도 안전하다」를 책임진다 — 이 책임은 「어디서 틀리나 6」에서 다시 본다.

> **래퍼** — 다른 함수를 감싸 더 쓰기 쉽거나 안전한 겉모양을 주는 함수다.\
> 예: `safe_strlen(&str)` 은 `strlen(*const c_char)` 을 감싼다.

### (3) Rust → C: `CString`

**언제 쓰나** — Rust 문자열을 C 함수에 넘길 때.

```text
"hello" (&str, 길이 5 를 따로 앎)
      │  CString::new
      ▼
[h][e][l][l][o][\0]   ← 힙에 새로 만든, 끝에 \0 이 붙은 소유 버퍼
      │  .as_ptr()
      ▼
*const c_char ──▶ strlen 이 \0 을 만날 때까지 센다 → 5
```

- `CString::new(s)` 는 문자열을 힙에 복사하고 끝에 `\0` 을 붙인 **소유** 값을 만든다.
- 내부에 `\0` 이 이미 있으면 `Err(NulError)` 를 돌려준다 — C 쪽은 첫 `\0` 을 문자열의 끝으로 읽으므로 뒷부분이 잘려 나가기 때문이다.
- 원본의 `safe_strlen` 은 이 `Result` 를 `.expect(…)` 로 풀므로, 내부 `\0` 이 든 입력이 오면 패닉한다.
- `.as_ptr()` 는 C 에 넘길 `*const c_char` 를 준다. 이 포인터는 **`CString` 이 살아 있는 동안만** 유효하다.
- `.as_bytes()` 는 끝의 `\0` 을 **뺀** 바이트 슬라이스다.
- 예: `"Hello from Rust!"` 의 `as_bytes()` 앞 5 바이트는 `H e l l o` 의 바이트 값 `[72, 101, 108, 108, 111]` 이다.
- `{:?}` 로 찍으면 따옴표로 감싼 문자열 꼴로 보인다(원본 주석).

> **null 종료 문자열** — 길이를 따로 적지 않고 끝에 값 0 인 바이트(`\0`)를 두어 끝을 표시하는 C 의 문자열 꼴이다.\
> 예: `"hi"` 는 메모리에 `h`, `i`, `\0` 세 바이트로 놓인다.

> **원시 포인터** — `*const T` · `*mut T`. 빌림 검사를 받지 않는 맨 주소다.\
> 예: `c_string.as_ptr()` 의 결과 `*const c_char`.

### (4) C → Rust: `CStr`

**언제 쓰나** — C 함수가 돌려준 `*const c_char` 를 Rust 문자열로 읽을 때.

```text
*const c_char (C 에서 받음)
      │  unsafe { CStr::from_ptr(p) }   ← \0 까지 훑어 길이를 잰다
      ▼
&CStr (빌림 — 메모리는 여전히 C 쪽 · 원래 주인 것)
      │
      ├─ .to_str()            → Result<&str, _>  UTF-8 검증, 실패 가능
      └─ .to_string_lossy()   → Cow<str>         잘못된 바이트를 U+FFFD 로 바꿈
```

- `CStr::from_ptr` 은 `unsafe` 다. 포인터가 유효하고 `\0` 으로 끝나는 문자열을 가리킨다는 조건을 컴파일러가 확인할 수 없기 때문이다.
- `CStr` 은 **빌린** 값이다 — 메모리를 소유하지 않는다.
- `.to_str()` 은 바이트가 올바른 UTF-8 인지 검사하고, 맞으면 `&str` 를, 아니면 에러를 돌려준다.
- `.to_string_lossy()` 는 실패하지 않는다. 잘못된 바이트를 대체 문자 U+FFFD 로 바꾸며 결과는 `Cow<str>` 다.
- 바이트 리터럴에서 곧바로 만들 수도 있다: `CStr::from_bytes_with_nul(b"hello\0")` 는 마지막이 `\0` 인지 검증한 뒤 `CStr` 을 만들고, 검증에 실패하면 에러를 돌려준다. 이 함수는 `unsafe` 가 아니다.

> **`Cow`** — Clone-on-write. 빌린 값이거나 새로 만든 소유 값이거나 둘 중 하나를 담는 타입이다.\
> 예: 바꿀 바이트가 없으면 원래를 빌리고, 바꿔야 하면 새 `String` 을 만든다.

> **UTF-8 검증** — 바이트 열이 올바른 UTF-8 인코딩인지 확인하는 일이다. Rust 의 `&str` 는 늘 올바른 UTF-8 이어야 한다.\
> 예: 바이트 `0xFF` 는 UTF-8 에서 나올 수 없어 검증에 실패한다.

### (5) Rust → C 로 내보내기: `#[no_mangle]`

**언제 쓰나** — C 코드(또는 다른 언어)가 Rust 함수를 부르게 하고 싶을 때.

```text
#[no_mangle]                        컴파일러: 심볼 이름을 "rust_add" 그대로 둔다
pub extern "C" fn rust_add(..)      컴파일러: C 호출 규약으로 컴파일한다
            │
            ▼
C 쪽:  int rust_add(int, int);  선언 후 rust_add(3, 4) 로 호출 가능
```

- 보통 Rust 는 함수 이름에 경로 · 해시 같은 정보를 덧붙여 심볼 이름을 바꾼다(맹글링).
- `#[no_mangle]` 은 이 바꾸기를 꺼서 C 가 `rust_add` 라는 이름으로 찾을 수 있게 한다.
- `pub extern "C"` 는 함수를 바깥에 드러내고 호출 규약을 C 로 맞춘다.
- 본문은 Rust 로 쓴 것이므로, Rust 안에서는 `unsafe` 없이 `rust_add(3, 4)` 처럼 부를 수 있다(원본 `main` 이 그렇게 부른다).

> **이름 맹글링** — 컴파일러가 함수 이름에 추가 정보를 섞어 겹치지 않는 심볼 이름을 만드는 일이다.\
> 예: `rust_add` 가 사람이 짐작하기 어려운 긴 이름으로 바뀐다.

## 문법 — 형태와 규칙

```rust
use std::ffi::{CStr, CString};
use std::os::raw::{c_char, c_int};

extern "C" {
    fn strlen(s: *const c_char) -> usize;   // 본문 없이 모양만
}

#[no_mangle]
pub extern "C" fn twice(x: c_int) -> c_int { x * 2 }

fn len_of(s: &str) -> usize {
    let owned = CString::new(s).expect("내부 \\0");   // Rust → C
    unsafe { strlen(owned.as_ptr()) }                   // owned 가 살아 있는 동안 호출
}

fn read_back(p: *const c_char) -> String {
    unsafe { CStr::from_ptr(p) }.to_string_lossy().into_owned()  // C → Rust
}
```

- `extern "C" { fn 이름(인자: 타입) -> 반환; }` — 바깥 함수 선언. 부를 때는 `unsafe { … }`.
- `#[no_mangle] pub extern "C" fn …` — Rust 함수를 C 이름 · C 규약으로 내보내기.
- 인자 · 반환 타입은 `c_int` · `c_double` · `c_char` 같은 C 호환 별칭을 쓴다.

| 타입 · 메서드 | 방향 | 소유 | 실패 가능 | 하는 일 |
|---|---|---|---|---|
| `CString::new(s)` | Rust → C | 소유(힙) | 예 — 내부 `\0` 이면 `NulError` | 복사 후 끝에 `\0` 추가 |
| `CString::as_ptr()` | Rust → C | — | 아니오 | C 에 넘길 `*const c_char` |
| `CString::as_bytes()` | — | 빌림 | 아니오 | 끝 `\0` 을 뺀 바이트 |
| `CStr::from_ptr(p)` | C → Rust | 빌림 | `unsafe` — 조건은 호출자 책임 | 포인터에서 `\0` 까지 읽기 |
| `CStr::from_bytes_with_nul(b)` | 바이트 → CStr | 빌림 | 예 — 끝 `\0` 검증 | 바이트 리터럴에서 만들기 |
| `CStr::to_str()` | CStr → `&str` | 빌림 | 예 — UTF-8 검증 | 검증된 `&str` |
| `CStr::to_string_lossy()` | CStr → `Cow<str>` | 빌림 또는 소유 | 아니오 | 잘못된 바이트를 U+FFFD 로 |

## 어디서 틀리나

### 1. 「`extern "C"` 호출은 항상 unsafe」의 범위
원본 팁은 「`extern "C"` 함수 호출은 항상 unsafe」라고 적는다.
이것은 `extern "C" { … }` 블록에 **선언만 한 바깥 함수**를 부를 때의 이야기다.
`pub extern "C" fn rust_add` 처럼 본문을 Rust 로 쓴 함수는 Rust 안에서 `unsafe` 없이 부른다 — 원본 `main` 도 그렇게 한다.
`unsafe` 를 요구하는 까닭은 「C 규약이라서」가 아니라 「컴파일러가 본문을 볼 수 없어서」다.

### 2. 내부 `\0` 이 든 문자열
`CString::new("hello\0world")` 는 `Err(NulError)` 다.
C 쪽은 첫 `\0` 에서 문자열이 끝났다고 보므로 `world` 가 조용히 사라지기 때문이다.
`safe_strlen` 처럼 `.expect()` 로 풀면 이런 입력에서 패닉한다 — 래퍼가 「안전」하다는 것은 메모리 안전이지 실패하지 않는다는 뜻이 아니다.

### 3. `as_ptr` 포인터의 수명
`as_ptr()` 가 준 포인터는 `CString` 이 살아 있는 동안만 유효하다.
`CString::new(s).unwrap().as_ptr()` 를 한 줄로 쓰면, 임시 `CString` 은 그 문장이 끝날 때 해제되고 포인터만 남는다.
그 포인터를 나중에 C 에 넘기면 해제된 메모리를 가리킨다(댕글링 포인터).
원본처럼 `let c_string = …;` 로 변수에 묶어 두고 그 변수가 살아 있는 동안 호출해야 한다.

> **댕글링 포인터** — 이미 해제된 메모리를 가리키는 포인터다.\
> 예: 임시 `CString` 이 사라진 뒤에도 남은 `as_ptr()` 결과.

### 4. `CStr::from_ptr` 의 안전 조건
포인터가 null 이 아니고, 유효한 메모리를 가리키고, `\0` 으로 끝나야 한다.
`\0` 이 없으면 `\0` 을 찾을 때까지 남의 메모리를 계속 읽는다.
이 조건은 컴파일러가 확인할 수 없어 `unsafe` 블록을 쓴 사람이 책임진다.

### 5. `to_str` 은 실패할 수 있다
C 문자열은 UTF-8 이라는 보장이 없다.
`to_str().unwrap()` 은 잘못된 UTF-8 이 오면 패닉한다.
실패 없이 읽어야 하면 `to_string_lossy()` 를 쓰되, 바이트가 U+FFFD 로 바뀌어 원래 값이 사라진다는 점을 감수한다.

### 6. 「안전한 래퍼」가 정말 모든 입력에 안전한가
원본은 `safe_abs` 를 「안전한 래퍼」로 소개한다.
그런데 C 표준에서 `abs` 에 `int` 의 최솟값(`i32::MIN`)을 넘기면 결과를 표현할 수 없어 정의되지 않은 동작이다 (원본에 근거 없음 — 추론).
그러면 safe 함수 `safe_abs(i32::MIN)` 이 정의되지 않은 동작을 일으킬 수 있어, 래퍼가 약속을 다 지키지 못한다.
래퍼를 safe 로 내놓으려면 그런 입력을 미리 걸러야 한다 — 예를 들어 Rust 의 `i32::checked_abs` 같은 것을 쓴다 (확인 필요).

### 7. 바이트에서 `CStr` 을 만들 때
`CStr::from_bytes_with_nul` 은 마지막 바이트가 `\0` 인지 검증한다.
`b"hello"` 처럼 `\0` 을 빠뜨리면 에러를 돌려주므로 `.unwrap()` 하면 패닉한다.

### 8. 선언한 모양은 검사받지 않는다
`extern "C"` 블록의 시그니처를 틀리게 적어도(인자 타입 · 개수) 컴파일러는 C 쪽 정의와 대조하지 못한다.
틀린 선언으로 부르면 엉뚱한 값이 나오거나 정의되지 않은 동작이 된다.
원본은 `strlen` 의 반환을 `usize` 로 적었는데, C 의 `size_t` 와 같은 크기라는 것은 흔한 플랫폼의 사정이다 (확인 필요).

### 9. 원본 주석의 `12.0`
원본 주석은 `println!("sqrt(144) = {}", safe_sqrt(144.0))` 옆에 `12.0` 이라고 적었다.
`{}`(Display)로 찍은 `f64` 값 12 는 `12` 로 찍히고, `12.0` 꼴은 `{:?}`(Debug)에서 나오는 것으로 알려져 있다 (원본에 근거 없음 — 추론, 확인 필요).
값 자체는 12 가 맞고, 찍히는 꼴만 다를 수 있다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| `extern` 블록에 선언한 함수 호출은 `unsafe` 가 필요하다 | Rust 언어 |
| `#[no_mangle]` 이 심볼 이름을 그대로 둔다 | Rust 언어(속성의 정의) |
| `CString::new` 가 내부 `\0` 에 `NulError` 를 돌려준다 · `to_string_lossy` 가 U+FFFD 로 바꾼다 | 표준 라이브러리 API |
| `c_int` 가 `i32` 다 · `c_char` 가 부호 있는 타입이다 | 플랫폼(타겟) — `c_char` 는 플랫폼에 따라 `i8` 또는 `u8` 이다 (확인 필요) |
| `strlen` 의 `size_t` 가 `usize` 와 같다 | 흔한 플랫폼의 사정 (확인 필요) |
| `extern "C"` 가 System V AMD64 ABI 로 컴파일된다 | 타겟 플랫폼 — 원본 주석의 「등」이 그 뜻이다 |
| `abs` · `sqrt` · `strlen` 을 libc 에서 찾는다 | 플랫폼의 링크 설정 — `sqrt` 가 libm 에 따로 있는 시스템도 있다 (확인 필요) |
| `abs(INT_MIN)` 이 정의되지 않은 동작이다 | C 표준 (원본에 근거 없음 — 추론) |
| `as_ptr` 를 `{:?}` 로 찍은 주소 값 | 실행 때마다 · 할당기마다 다르다 — 아무도 보장하지 않는다 |
| `NulError` 를 `{:?}` 로 찍은 꼴 | 표준 라이브러리의 Debug 구현 세부 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| Rust 문자열을 C 에 넘긴다 | `CString::new` → 변수에 묶고 `.as_ptr()` | `&str` 의 `as_ptr()` 를 그대로 넘기기(끝 `\0` 이 없다) |
| C 가 준 `char*` 를 읽는다 | `unsafe { CStr::from_ptr(p) }` | 길이를 짐작해 슬라이스 만들기 |
| C 문자열의 인코딩을 믿을 수 없다 | `to_string_lossy()` | `to_str().unwrap()` |
| 정확한 바이트가 중요하다 | `to_str()` 로 에러를 다루기 · `to_bytes()` | `to_string_lossy()` (바이트가 바뀐다) |
| C 함수를 여러 곳에서 쓴다 | 안전한 래퍼 한 곳에 `unsafe` 를 모으기 | 호출하는 곳마다 `unsafe` 블록 |
| C 에서 Rust 함수를 부른다 | `#[no_mangle] pub extern "C" fn` | 맹글링된 일반 `fn` |

## 핵심 문장

1. **`extern "C"` 블록은 바깥 함수의 모양만 적고, 본문은 링커가 붙이며, 컴파일러가 안을 볼 수 없어 호출은 `unsafe` 다.**
2. **`CString` 은 Rust → C 로 보내는 소유 · `\0` 종료 문자열이고, `CStr` 은 C → Rust 로 받는 빌린 · `\0` 종료 문자열이다.**
3. **내부 `\0` 은 C 에서 끝 표시가 되므로 `CString::new` 가 거부한다.**
4. **`as_ptr()` 포인터는 `CString` 이 살아 있는 동안만 쓸 수 있다.**
5. **안전한 래퍼는 `unsafe` 를 한곳에 가두지만, 모든 입력에 대한 안전을 래퍼 작성자가 책임진다.**

## 용어 풀이

- **FFI** — 다른 언어로 만든 함수를 부르는 통로.
- **호출 규약(ABI)** — 함수 호출 때 인자 · 반환값을 기계 수준에서 주고받는 약속.
- **`extern "C"`** — C 호출 규약을 쓰겠다는 표시. 블록이면 바깥 함수 선언, `fn` 앞이면 C 규약으로 내보내기.
- **링커** — 선언만 된 이름을 라이브러리 속 실제 함수에 연결하는 도구.
- **libc** — C 표준 라이브러리. `abs` · `strlen` 등이 들어 있다.
- **null 종료 문자열** — 끝에 `\0` 을 두어 끝을 표시하는 C 문자열.
- **`CString`** — 힙에 소유한, `\0` 으로 끝남이 보장된 문자열. Rust → C.
- **`CStr`** — `\0` 으로 끝나는 C 문자열을 빌린 슬라이스. C → Rust.
- **`NulError`** — `CString::new` 에 내부 `\0` 이 있을 때의 에러.
- **`c_char` · `c_int` · `c_double`** — C 타입과 크기를 맞춘 플랫폼별 타입 별칭.
- **원시 포인터** — 빌림 검사를 받지 않는 맨 주소(`*const T`).
- **댕글링 포인터** — 해제된 메모리를 가리키는 포인터.
- **래퍼** — 다른 함수를 감싸 안전하거나 쓰기 쉬운 겉모양을 주는 함수.
- **이름 맹글링** — 심볼 이름에 추가 정보를 섞는 일. `#[no_mangle]` 이 끈다.
- **UTF-8 검증** — 바이트가 올바른 UTF-8 인지 확인하는 일.
- **U+FFFD** — 해석할 수 없는 바이트 자리에 넣는 대체 문자.
- **`Cow`** — 빌린 값 또는 소유 값을 담는 타입(Clone-on-write).

## 더 들어가면

- Rust 2024 에디션부터는 바깥 함수 블록을 `unsafe extern "C" { … }` 로 써야 하고, `#[no_mangle]` 도 `#[unsafe(no_mangle)]` 로 써야 한다 (확인 필요). 원본 코드는 그 이전 에디션의 꼴이다.
- 2024 에디션의 `unsafe extern` 블록 안에서는 항목에 `safe fn` 을 붙여 호출을 `unsafe` 없이 할 수 있다고 선언할 수 있다 (확인 필요).
- 요즘 표준 라이브러리는 `std::ffi::c_char` · `c_int` 처럼 `std::ffi` 에서도 C 타입 별칭을 제공한다 (확인 필요).
- `c"hello"` 꼴의 C 문자열 리터럴이 있어 `&CStr` 을 바로 만들 수 있다 (확인 필요).
- C 가 `malloc` 으로 만든 문자열은 Rust 가 해제하면 안 되고 C 의 `free` 로 돌려줘야 한다. 반대로 `CString::into_raw` 로 넘긴 것은 `CString::from_raw` 로 되찾아 해제한다 (확인 필요).
- 큰 C 라이브러리의 선언은 손으로 쓰지 않고 `bindgen` 같은 도구로 헤더에서 뽑는 일이 많다. 실제 프로젝트는 손 선언 대신 `libc` 크레이트를 쓰기도 한다 (확인 필요).
- 패닉이 `extern "C" fn` 경계를 넘어 C 로 풀려 나가는 것은 문제가 되므로, 내보내는 함수 안에서 패닉을 막거나 잡는 습관이 필요하다 (확인 필요).
