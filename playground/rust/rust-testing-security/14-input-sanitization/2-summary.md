## 한눈에 — 쉽게 말하면

**입력 검증과 살균은 「건물 출입 관리」다.**
출입 명단에 있는 사람만 들여보내는 것이 검증이다.
들어온 사람이 위험한 물건을 들고 있으면, 무해한 꼴로 포장해 들여보내는 것이 살균이다.
명단에 없는 사람은 묻지도 않고 돌려보낸다.
「수상한 사람 목록」에 있는 사람만 막는 경비보다 이쪽이 안전하다.
수상한 목록에 아직 오르지 않은 새 침입자는 그대로 통과하기 때문이다.
프로그램의 사용자 입력 처리도 똑같은 구조다.

| 비유 | 실체 |
|---|---|
| 출입 명단 | 허용 문자 · 허용 형식 (화이트리스트) |
| 수상한 사람 목록 | 금지 문자 · 금지 패턴 (블랙리스트) |
| 위험한 물건을 포장하기 | 이스케이프 (`<` → `&lt;`) |
| 출입 기록을 따로 받는 창구 | 파라미터화된 쿼리 (`$1` 자리에 값만 따로 넘기기) |
| 건물 안 허가 구역 | base 디렉토리 |
| 「통과함」 도장이 찍힌 출입증 | newtype 으로 감싼 검증된 값 |

```text
사용자 입력 ──▶ [검증: 명단에 있나?] ──아니오──▶ Err(이유)
                      │ 예
                      ▼
               [쓰는 곳에 맞게 살균]
             ┌────────┼─────────┐
             ▼        ▼         ▼
           SQL      HTML       경로
       (파라미터화) (이스케이프) (base 안으로 제한)
```

> **검증(validation)** — 입력이 허용된 형식 · 범위 안에 있는지 확인하고, 아니면 거부하는 일.\
> 예: 사용자명에 영숫자 · `_` · `-` 말고 다른 문자가 있으면 `Err` 를 돌려준다.

> **살균(sanitization)** — 입력을 쓰는 곳에서 특별한 뜻을 갖지 못하도록 바꾸거나 걸러 내는 일.\
> 예: HTML 에 넣기 전에 `<` 를 `&lt;` 로 바꾼다.

## 이 주제가 답하려는 질문

1. 받아도 되는 입력과 거부할 입력을 어떤 기준으로 가르나 — 허용 목록인가, 금지 목록인가?
2. 사용자가 보낸 문자열이 SQL · HTML · 파일 경로 안으로 들어갈 때, 어떻게 하면 「데이터」가 「명령」으로 바뀌지 않나?
3. 길이 제한처럼 단순해 보이는 처리는 UTF-8 문자열에서 어디가 까다롭나?
4. Rust 의 타입 시스템은 「검증됨」과 「검증 안 됨」을 어떻게 가를 수 있나?

## 동작 방식

### (1) 형식 검증 — 화이트리스트로 하나씩 걸러 내기

**언제 쓰나** — 이메일 · 사용자명처럼 꼴이 정해진 문자열을 받을 때 쓴다.
검사를 차례로 통과해야만 `Ok` 가 나온다.

```text
validate_username("  alice_bob ")
  │
  ├─ trim()                        → "alice_bob"
  ├─ len() < 3 ?                   → 아니오 (9바이트)
  ├─ len() > 30 ?                  → 아니오
  ├─ 모든 문자가 영숫자/_/- ?        → 예
  ├─ '-' 또는 '_' 로 시작 ?         → 아니오
  ▼
반환값: Ok("alice_bob")

validate_email("user@domain")
  ├─ trim · 빈 문자열 · 254 초과 검사 → 통과
  ├─ split('@') → ["user", "domain"] → 두 조각 (통과)
  ├─ 두 조각 다 비어 있지 않음        → 통과
  ├─ 도메인에 '.' 이 있나?            → 없음
  ▼
반환값: Err("도메인에 . 이 없습니다")
```

그림 해설:
- 먼저 `trim()` 으로 양옆 공백을 걷어 낸다. 사용자의 실수를 보정하는 단계다.
- 검사는 위에서 아래로 진행하고, 하나라도 걸리면 바로 `Err` 를 돌려준다(이른 반환).
- 사용자명의 문자 검사는 `chars().all(...)` 로 「모든 문자가 허용 목록에 있는가」를 묻는다. 이것이 화이트리스트다.
- 이메일은 `split('@')` 결과가 정확히 두 조각인지로 「`@` 가 정확히 하나」를 확인한다. `"invalid"` 는 한 조각, `"a@b@c.com"` 은 세 조각이 되어 걸린다.
- `"@example.com"` 은 `["", "example.com"]`, `"user@"` 는 `["user", ""]` 로 갈라져 「앞뒤가 비어있다」에 걸린다.
- 길이 검사의 `len()` 은 **바이트 수**다. 메시지는 「3자」라고 말하지만, 실제로는 3바이트를 센다.
- `is_alphanumeric()` 은 ASCII 만이 아니라 유니코드의 글자 · 숫자를 모두 참으로 본다. 그래서 한글 사용자명도 문자 검사를 통과한다.

> **화이트리스트(허용 목록)** — 허용할 것만 적어 두고 나머지를 모두 거부하는 방식.\
> 예: 「영숫자 · `_` · `-` 만 허용」.

> **블랙리스트(금지 목록)** — 금지할 것만 적어 두고 나머지를 모두 허용하는 방식.\
> 예: 「`<` · `'` 를 금지」. 목록에 빠진 위험 문자는 그대로 통과한다.

### (2) 타입 파싱으로 범위 검증 — 포트 번호

**언제 쓰나** — 숫자 입력을 받을 때 쓴다.
알맞은 정수 타입으로 파싱하면, 그 타입의 범위 밖 값은 파싱 단계에서 이미 거부된다.

```text
validate_port(" 8080 ") → trim → "8080" → parse::<u16>() → Ok(8080) → 0 인가? 아니오 → Ok(8080)
validate_port("70000")  → parse::<u16>() 실패 (u16 은 0..=65535)  → Err("유효한 숫자가 아닙니다")
validate_port("-1")     → parse::<u16>() 실패 (부호 없는 정수)      → Err("유효한 숫자가 아닙니다")
validate_port("0")      → parse 성공 → 0 이므로                     → Err("포트 0은 사용할 수 없습니다")
```

그림 해설:
- `u16` 은 0 부터 65535 까지만 담는 타입이라, 파싱이 범위 검사를 겸한다.
- 파싱 실패 이유(범위 초과 · 음수 · 숫자 아님)는 `map_err` 로 한 가지 메시지로 바꾼 뒤 `?` 로 바로 돌려준다.
- 타입이 막지 못하는 남은 조건(0 은 안 된다)만 따로 검사한다.

### (3) SQL 인젝션 방지 — 파라미터화가 먼저, 이스케이프는 최후

**언제 쓰나** — 사용자 입력이 SQL 문 안으로 들어갈 때마다 쓴다.

```text
입력 name = '; DROP TABLE users; --

[위험] format! 로 끼워 넣기
  "SELECT * FROM users WHERE name = '" + name + "'"
  = SELECT * FROM users WHERE name = ''; DROP TABLE users; --'
                                      ▲▲ 따옴표가 닫히고 새 문장이 시작된다

[안전] 파라미터화
  쿼리:     SELECT * FROM users WHERE name = $1
  파라미터: ["'; DROP TABLE users; --"]   ← 쿼리와 따로 전달, 통째로 「값」

[최후의 수단] 이스케이프
  ' → ''   로 바꾸면   ''; DROP TABLE users; --
```

그림 해설:
- `unsafe_query` 는 입력을 SQL 문자열 안에 그대로 이어 붙인다. 입력의 `'` 가 문자열 리터럴을 닫아 버리고, 그 뒤가 SQL 명령으로 읽힌다. 이것이 SQL 인젝션이다.
- `parameterized_query` 는 쿼리 틀(`$1` 자리표시)과 값 목록을 따로 돌려준다. 실제 DB 드라이버가 값을 자리에 바인딩하므로, 값은 어떤 글자를 담든 SQL 구조를 바꾸지 못한다. 예제 함수 자체는 튜플을 돌려줄 뿐이고 실제 바인딩은 드라이버의 일이다.
- `escape_sql_string` 은 특별한 뜻을 가진 문자를 바꾼다. 백슬래시를 **가장 먼저** 두 배로 만든다. 뒤 단계에서 새로 넣는 `\` 를 다시 두 배로 만들지 않기 위해서다. 이어서 `'` 는 `''`, `"` 는 `\"`, 널 바이트는 제거, 줄바꿈 `\n` · `\r` 은 글자 `\n` · `\r` 로 바꾼다.
- 이스케이프는 DB 마다 규칙이 달라 빠뜨리기 쉽다. 그래서 원본은 이것을 「최후의 수단」이라 부르고 파라미터화를 앞세운다.

> **SQL 인젝션** — 입력에 섞인 SQL 문법이 쿼리 구조를 바꿔 의도하지 않은 명령이 실행되는 공격.\
> 예: 이름 칸에 `'; DROP TABLE users; --` 를 넣는다.

> **파라미터화된 쿼리** — 쿼리 틀과 값을 따로 DB 에 넘겨, 값이 언제나 데이터로만 취급되게 하는 방식.\
> 예: `WHERE name = $1` + 파라미터 `["alice"]`.

### (4) 경로 순회 방지 — base 디렉토리 밖으로 못 나가게

**언제 쓰나** — 사용자가 준 파일 이름을 서버의 디렉토리 경로에 붙일 때 쓴다.

```text
base = /var/www/uploads

"image.png"             → 금지 패턴 없음 → join → /var/www/uploads/image.png → 접두사 OK → Ok
"sub/file.txt"          → 금지 패턴 없음 → join → /var/www/uploads/sub/file.txt          → Ok
"../../etc/passwd"      → ".." 포함      → Err("경로에 '..'를 사용할 수 없습니다")
"..\windows\system32"   → ".." 포함      → Err("경로에 '..'를 사용할 수 없습니다")
"/etc/shadow"           → '/' 로 시작    → Err("절대 경로는 허용되지 않습니다")
"a\0.png"               → 널 바이트      → Err("널 바이트 포함")
```

그림 해설:
- 1단계는 금지 패턴 검사다. `..`(상위 디렉토리로 올라가기), `/` · `\` 로 시작하는 절대 경로, 널 바이트를 거부한다.
- `..` 검사는 `contains("..")` 라서 구분자가 `/` 든 `\` 든 상관없이 걸린다. 대신 `"report..txt"` 같은 정상 파일 이름도 거부한다.
- 널 바이트는 C 문자열의 끝 표시로 해석될 수 있어, 그 뒤를 잘라 먹는 우회에 쓰일 수 있다(원본 주석의 설명).
- 2단계는 `base.join(user_input)` 으로 경로를 잇는다. `Path::join` 은 붙이는 쪽이 절대 경로면 base 를 버리고 그 절대 경로로 바꿔 버린다. 그래서 1단계의 절대 경로 검사가 필요하다.
- 3단계는 이은 결과를 문자열로 바꿔 base 문자열로 시작하는지 본다. 절대 경로 검사가 빠졌더라도 `"/etc/shadow"` 는 이 단계에서 「기본 경로를 벗어났습니다」로 걸린다.
- 주석은 「정규화 후」라고 말하지만 코드는 정규화를 하지 않는다. `canonicalize` 는 파일이 실제로 있어야 동작하므로 문자열 비교로 대신했다고 원본이 밝힌다.

> **경로 순회(path traversal)** — `..` 등을 써서 허용된 디렉토리 밖의 파일에 접근하는 공격.\
> 예: `../../etc/passwd`.

### (5) XSS 방지 — HTML 이스케이프

**언제 쓰나** — 사용자 입력을 HTML 페이지에 출력할 때 쓴다.

```text
<script>alert('XSS')</script>
  1) & → &amp;   (해당 없음)
  2) < → &lt;    &lt;script>alert('XSS')&lt;/script>
  3) > → &gt;    &lt;script&gt;alert('XSS')&lt;/script&gt;
  4) " → &quot;  (해당 없음)
  5) ' → &#x27;  &lt;script&gt;alert(&#x27;XSS&#x27;)&lt;/script&gt;
반환값: 브라우저는 이것을 태그가 아니라 글자로 보여 준다
```

그림 해설:
- 다섯 문자 `&` `<` `>` `"` `'` 를 HTML 엔티티로 바꾼다.
- `&` 를 **맨 먼저** 바꾼다. 나중에 바꾸면 앞 단계가 만든 `&lt;` 의 `&` 까지 다시 `&amp;` 로 바뀌어 `&amp;lt;` 가 된다(이중 이스케이프).
- 바뀐 문자열은 태그로 해석되지 않으므로 스크립트가 실행되지 않는다.
- `<img src=x onerror=alert(1)>` 는 `<` · `>` 만 바뀌어 `&lt;img src=x onerror=alert(1)&gt;` 가 된다. `=` · `(` 는 그대로다.

> **XSS(교차 사이트 스크립팅)** — 입력에 섞인 HTML · 스크립트가 다른 사용자의 브라우저에서 실행되는 공격.\
> 예: 게시글 본문에 `<script>…</script>` 를 넣는다.

> **HTML 엔티티** — HTML 에서 특별한 문자를 글자 그대로 보이게 쓰는 표기.\
> 예: `<` 는 `&lt;`, `&` 는 `&amp;`.

### (6) 입력 크기 제한 — UTF-8 경계를 지키며 자르기

**언제 쓰나** — 너무 긴 입력을 정해진 바이트 수 안으로 줄일 때 쓴다.

```text
"가나다라마바사…" — 한글 한 글자 = UTF-8 3바이트
 바이트: 0  3  6  9  12 15 18 …   ← 글자 경계

limit_input(s, 15): end=15 → 경계인가? 예 → &s[..15] = "가나다라마" (15바이트)
limit_input(s, 14): end=14 → 아니오 → 13 → 아니오 → 12 → 예 → &s[..12] = "가나다라"
```

그림 해설:
- 입력이 이미 `max_bytes` 이하면 그대로 돌려준다.
- 넘으면 `end = max_bytes` 에서 시작해, `is_char_boundary(end)` 가 참이 될 때까지 한 바이트씩 줄인다.
- 글자 중간에서 자르면 `&input[..end]` 가 패닉을 일으키므로 이 되돌림이 필요하다.
- 결과는 원본의 일부를 빌린 `&str` 이라 새 메모리를 만들지 않는다.
- `end > 0` 조건이 있어 `max_bytes` 가 0 이거나 첫 글자보다 작아도 빈 문자열로 안전하게 끝난다.

> **UTF-8 문자 경계** — 한 글자를 이루는 바이트들이 시작하는 자리.\
> 예: 한글 문자열에서는 0, 3, 6, … 번째 바이트가 경계다.

### (7) newtype 패턴 — 검증 여부를 타입으로 나누기

**언제 쓰나** — 검증된 값만 받아야 하는 함수가 많을 때 쓴다.
원본의 팁이 권하는 방법이며, 예제 코드에는 들어 있지 않다.

```text
&str (검증 안 됨) ──▶ Username::parse() ──Ok──▶ Username (검증됨)
                                       └─Err─▶ 거부

fn create_account(name: Username)   ← &str 를 넘기면 컴파일 오류
```

그림 해설:
- 문자열을 감싼 새 타입 `Username` 을 만들고, 만드는 길을 검증 함수 하나로만 열어 둔다.
- 다른 함수는 `&str` 대신 `Username` 을 받는다. 그러면 검증을 빼먹은 호출은 컴파일 단계에서 막힌다.
- `validate_username` 이 `Result<&str, String>` 을 돌려주는 것과 비교하면, 그쪽은 검증 뒤에도 그냥 `&str` 이라 「검증됨」이라는 사실이 타입에 남지 않는다.

> **newtype 패턴** — 기존 타입을 필드 하나짜리 구조체로 감싸 다른 타입으로 만드는 방법.\
> 예: `struct Username(String);`

## 문법 — 형태와 규칙

```rust
use std::path::Path;

struct Username(String); // newtype: 검증된 사용자명

impl Username {
    fn parse(raw: &str) -> Result<Self, String> {
        let s = raw.trim();
        if s.len() < 3 || !s.chars().all(|c| c.is_alphanumeric() || c == '_') {
            return Err("허용되지 않는 사용자명".to_string());
        }
        Ok(Username(s.to_string()))
    }
}

fn greet(name: &Username) -> String {
    format!("<p>{}</p>", name.0.replace('&', "&amp;").replace('<', "&lt;"))
}

fn main() {
    let _p = Path::new("/srv/data").join("a.txt");
    if let Ok(u) = Username::parse(" bob_1 ") { let _ = greet(&u); }
}
```

- 검증 함수는 `Result<성공값, String>` 을 돌려주고, 실패 시 사람이 읽을 이유를 `Err` 에 담는다.
- 검사는 `if 조건 { return Err(...) }` 를 차례로 늘어놓는 이른 반환 꼴로 쓴다.
- `chars().all(|c| ...)` 는 「모든 문자가 허용 목록에 있나」를 묻는 화이트리스트 검사다.
- `parse::<u16>()` 처럼 좁은 정수 타입으로 파싱하면 범위 검사를 겸한다. 실패는 `map_err(...)?` 로 메시지를 바꿔 전한다.
- `str::replace` 를 이어 쓰는 이스케이프는 **순서가 뜻을 가진다** — HTML 은 `&` 먼저, SQL 문자열은 `\` 먼저.
- `str::len()` 은 바이트 수, `chars().count()` 는 글자 수다.
- 바이트 인덱스로 자를 때는 `is_char_boundary(i)` 로 경계를 확인한 뒤 `&s[..i]` 를 쓴다.
- `Path::join` 은 인자가 절대 경로면 base 를 대체한다. `to_string_lossy()` 는 경로를 문자열로 바꾸되, UTF-8 이 아닌 부분은 대체 문자로 바꾼다.

## 어디서 틀리나

### 1. 블랙리스트로 막으려 한다
원본의 팁은 화이트리스트가 블랙리스트보다 안전하다고 말한다.
금지 목록은 목록에 아직 없는 위험 문자 · 새 인코딩을 통과시킨다.
허용 목록은 모르는 것을 모두 거부하므로 빠뜨림이 안전한 쪽으로 기운다.
예제에서는 `validate_username` 의 문자 검사가 화이트리스트, `safe_path_join` 의 `..` · 절대 경로 · 널 바이트 검사는 블랙리스트에 가깝다.

### 2. SQL 을 `format!` 으로 조립한다
원본의 팁: SQL 은 반드시 파라미터화된 쿼리를 쓴다.
`format!` 으로 끼우면 입력의 `'` 가 리터럴을 닫아 쿼리 구조가 바뀐다.
이스케이프는 최후의 수단일 뿐이다.
**원본의 주장 → 왜 의심스러운가**: `escape_sql_string` 은 `'` 를 `''` 로 바꾸는 SQL 표준 방식과, `"` 를 `\"` 로 · `\` 를 `\\` 로 바꾸는 백슬래시 방식을 함께 쓴다. 백슬래시를 특별히 다루지 않는 DB 설정에서는 `\\` 가 글자 그대로 두 개의 백슬래시로 저장될 수 있어, 「모두 이스케이프」라는 주석과 달리 DB 마다 결과가 달라질 수 있다(확인 필요). 이것이 이스케이프를 최후의 수단으로 두는 까닭이기도 하다.

### 3. HTML 에 입력을 그대로 내보낸다
원본의 팁: HTML 출력은 이스케이프한다.
이스케이프할 때 `&` 를 먼저 바꾸지 않으면 엔티티가 이중으로 망가진다.

### 4. 경로 검사가 너무 넓거나 너무 좁다
원본의 팁: 경로 입력은 `..` 를 막고 base 밖을 접근할 수 없게 한다.
- `contains("..")` 는 `"report..txt"` 같은 정상 이름까지 거부한다(오탐).
- 접두사 검사는 **문자열** 비교다. 예제의 흐름에서는 `join` 결과가 언제나 base 로 시작하므로, 이 검사가 실제로 걸러 내는 것은 사실상 절대 경로 입력뿐이다.
- **원본의 주장 → 왜 의심스러운가**: 주석은 「정규화 후 base 내에 있는지 확인」이라 하지만 코드에는 정규화 단계가 없다. 원본 스스로 `canonicalize` 대신 문자열 비교를 썼다고 밝힌다. 그래서 `..` 차단이 빠지면 3단계만으로는 순회를 막지 못한다(`/var/www/uploads/../x` 도 base 문자열로 시작한다).

### 5. 길이를 「글자 수」로 착각한다
`len()` 은 바이트 수다.
`validate_username` 의 메시지는 「최소 3자」지만 한글 한 글자(3바이트)도 통과한다.
반대로 한글 11자(33바이트)는 「최대 30자」에 걸린다.
`limit_input` 도 바이트 기준이라, 글자 중간을 자르지 않으려고 `is_char_boundary` 로 물러난다.

### 6. 메시지와 검사가 어긋난다
`validate_username` 은 `-` · `_` 로 시작하는 것만 막는다.
「문자로 시작해야 합니다」라는 메시지와 달리, `"123abc"` 처럼 숫자로 시작하는 이름은 통과한다.
`is_alphanumeric` 이 유니코드 전체를 받아들이므로 한글 · 다른 문자 체계도 허용된다 — ASCII 만 받으려면 `is_ascii_alphanumeric` 을 써야 한다.

### 7. 검증한 사실이 타입에 남지 않는다
원본의 팁: 검증된 입력과 미검증 입력을 newtype 으로 구분하라.
`Result<&str, String>` 의 `Ok` 값은 다시 평범한 `&str` 이라, 나중에 검증 안 된 `&str` 과 섞여도 컴파일러가 알지 못한다.

### 8. 이메일 검증을 완전하다고 믿는다
예제의 `validate_email` 은 「기본 검증」이다.
`@` 하나 · 앞뒤 비어 있지 않음 · 도메인에 `.` 이 있음만 본다.
`"a b@x.y"` 처럼 공백이 섞인 주소도 통과한다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| `u16` 파싱은 0..=65535 밖의 값과 음수를 `Err` 로 돌려준다 | Rust 표준 라이브러리(`u16` 의 범위와 `FromStr`) |
| `str::len()` 은 바이트 수다 | Rust 표준 라이브러리 |
| `is_alphanumeric()` 은 유니코드 글자 · 숫자를 참으로 본다 | Rust 표준 라이브러리(유니코드 속성 기준) |
| 글자 경계가 아닌 곳에서 `&s[..i]` 로 자르면 패닉 | Rust 표준 라이브러리 |
| `Path::join` 에 절대 경로를 넘기면 base 가 대체된다 | Rust 표준 라이브러리(플랫폼별 경로 규칙을 따름) |
| `$1` 자리표시자 | DB · 드라이버의 관례(PostgreSQL 식). 다른 DB 는 `?` 등을 쓴다(확인 필요) |
| `'` → `''` 로 따옴표를 이스케이프 | SQL 표준 관례. `\` 처리 방식은 DB 와 설정마다 다르다(확인 필요) |
| 이메일 최대 254자 | 원본 주석은 「RFC 길이 제한」이라 한다. 어느 RFC 인지 원본에 없다(확인 필요) |
| 널 바이트가 C 문자열 끝으로 해석된다 | C 언어 · OS API 의 관례. Rust 언어 자체의 규칙이 아니다 |
| 다섯 문자를 엔티티로 바꾸면 태그로 해석되지 않는다 | HTML 규격(본문 텍스트 · 따옴표로 감싼 속성 맥락에서) |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 사용자명 · 식별자처럼 허용 문자가 정해짐 | 화이트리스트 `chars().all(...)` | 금지 문자만 찾는 검사 |
| 숫자 · 포트 번호 입력 | 알맞은 정수 타입으로 `parse` + 남은 범위 검사 | 문자열 그대로 비교 |
| 입력을 SQL 에 넣음 | 파라미터화된 쿼리 | `format!` 끼워 넣기, 손으로 쓴 이스케이프(최후의 수단) |
| 입력을 HTML 로 출력 | HTML 이스케이프(`&` 먼저) | 그대로 출력 |
| 입력을 파일 경로에 씀 | `..` · 절대 경로 · 널 바이트 차단 + base 안인지 확인 | `base.join(input)` 만 하고 끝내기 |
| 긴 입력을 바이트 단위로 자름 | `is_char_boundary` 로 경계 찾기 | 임의 바이트 인덱스로 바로 자르기 |
| 검증된 값만 받아야 하는 함수가 많음 | newtype 패턴 | 검증 결과를 그냥 `&str` 로 돌리기 |

## 핵심 문장

1. **허용할 것만 적는다** — 화이트리스트는 모르는 입력을 거부하므로 블랙리스트보다 안전하다.
2. **데이터가 명령이 되지 않게 한다** — SQL 은 파라미터화로 값과 구조를 떼어 놓고, HTML 은 이스케이프로 메타문자를 글자로 바꾼다.
3. **경로는 base 안에 가둔다** — `..` · 절대 경로 · 널 바이트를 막고, 이은 결과가 base 안인지 확인한다.
4. **Rust 문자열 길이는 바이트다** — 자를 때는 UTF-8 경계를, 길이를 셀 때는 바이트와 글자의 차이를 의식한다.
5. **검증을 타입으로 남긴다** — 좁은 정수 타입 파싱과 newtype 은 「검증됨」을 컴파일러가 지키게 한다.

## 용어 풀이

- **검증(validation)** — 입력이 허용된 형식 · 범위 안인지 확인하고, 아니면 거부하는 일.
- **살균(sanitization)** — 입력이 쓰이는 곳에서 특별한 뜻을 못 갖도록 바꾸거나 걸러 내는 일.
- **화이트리스트(허용 목록)** — 허용할 것만 적고 나머지를 모두 거부하는 방식.
- **블랙리스트(금지 목록)** — 금지할 것만 적고 나머지를 모두 허용하는 방식.
- **SQL 인젝션** — 입력의 SQL 문법이 쿼리 구조를 바꾸는 공격.
- **파라미터화된 쿼리** — 쿼리 틀과 값을 따로 넘겨 값을 데이터로만 다루게 하는 방식.
- **이스케이프** — 특별한 뜻을 가진 문자를 글자 그대로의 표기로 바꾸는 일.
- **XSS** — 입력에 섞인 스크립트가 다른 사용자의 브라우저에서 실행되는 공격.
- **HTML 엔티티** — `&lt;` 처럼 특별한 문자를 글자로 보이게 하는 HTML 표기.
- **경로 순회** — `..` 등으로 허용 디렉토리 밖에 접근하는 공격.
- **base 디렉토리** — 사용자 입력 경로가 벗어나면 안 되는 기준 디렉토리.
- **널 바이트** — 값이 0 인 바이트(`\0`). C 문자열에서 끝 표시로 쓰인다.
- **UTF-8 문자 경계** — 한 글자의 바이트 묶음이 시작하는 자리.
- **newtype 패턴** — 기존 타입을 필드 하나짜리 구조체로 감싸 새 타입을 만드는 방법.
- **이른 반환** — 조건에 걸리면 함수 중간에서 바로 `return` 하는 꼴.

## 더 들어가면

- `Path::starts_with` 는 문자열이 아니라 **경로 구성요소** 단위로 비교한다. 문자열 접두사 비교는 `/var/www/uploads_evil` 도 `/var/www/uploads` 로 시작한다고 보지만, 구성요소 비교는 그렇지 않다(확인 필요).
- 파일이 이미 있는 경우라면 `canonicalize` 로 `..` 와 심볼릭 링크를 풀어 실제 위치를 얻은 뒤 base 안인지 확인하는 방법이 있다. 예제의 문자열 검사는 base 안의 심볼릭 링크가 밖을 가리키는 경우를 막지 못한다(확인 필요).
- Windows 에서는 `C:` 같은 드라이브 접두사가 붙은 입력이 `/` · `\` 로 시작하지 않으면서도 base 를 바꿀 수 있다. 예제의 절대 경로 검사는 이것을 따로 다루지 않는다(확인 필요).
- Rust 의 파일 API 는 경로 안에 널 바이트가 있으면 OS 에 넘기기 전에 오류를 내는 것으로 알려져 있다. 그래도 C 라이브러리로 경로를 넘기는 코드에서는 직접 막는 편이 안전하다(확인 필요).
- HTML 이스케이프는 맥락에 따라 부족할 수 있다. 따옴표 없는 속성 값, `href="javascript:…"` 같은 URL 맥락, `<script>` 안의 문자열은 각자 다른 처리가 필요하다(확인 필요).
- Rust 의 DB 라이브러리들은 대체로 쿼리 틀과 값 바인딩을 나눠 받는 API 를 제공한다. 쿼리 문자열을 컴파일 시점에 검사하는 것도 있다(확인 필요).
- newtype 에서 내부 필드를 비공개로 두고 생성자를 검증 함수 하나로만 열어 두면, 모듈 밖에서는 검증을 우회해 값을 만들 수 없다(확인 필요).
