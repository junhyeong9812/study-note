## 한눈에 — 쉽게 말하면

**비밀번호 해싱은 「반죽에 비밀 재료를 넣고 오래 굽는 빵」이다.**
비밀번호(밀가루)에 집집마다 다른 양념(솔트)을 섞는다.
그다음 일부러 오래 굽는다(반복 라운드).
다 구운 빵에서 원래 반죽을 되살릴 수는 없다.
확인할 때는 같은 양념, 같은 굽는 시간으로 새 빵을 구워 저장된 빵과 견준다.
비밀번호 저장도 똑같은 구조다.

| 비유 | 실체 |
|---|---|
| 밀가루 | 사용자가 입력한 비밀번호 |
| 집집마다 다른 양념 | 솔트(사용자마다, 해싱마다 새로 만든 바이트) |
| 오래 굽기 | `iterations` 만큼 도는 반복 라운드(key stretching) |
| 구운 빵 | 해시 바이트 |
| 빵 옆에 붙인 레시피 쪽지 | 저장 문자열 `$반복횟수$솔트$해시` |
| 새로 구워 견주기 | `verify_password` 의 재계산 + 상수 시간 비교 |

```text
비밀번호 ──┐
           ├─► 섞기(XOR) ─► 라운드 × N ─► 해시 32바이트
솔트 16B ──┘                                  │
                                              ▼
                  저장: $N$솔트hex$해시hex  (비밀번호 자체는 저장하지 않는다)
```

## 이 주제가 답하려는 질문

1. 비밀번호를 평문으로 두지 않고 어떻게 저장하나?
2. 같은 비밀번호를 쓴 두 사람의 저장값이 왜 달라야 하나?
3. 저장값만 가지고 나중에 입력한 비밀번호가 맞는지 어떻게 확인하나?
4. 왜 SHA · MD5 처럼 빠른 해시는 안 되고, 왜 비교도 특별하게 해야 하나?

## 동작 방식

이 절의 코드는 원본이 밝히듯 **교육용 시뮬레이션**이다.
실제 서비스에서는 쓰면 안 된다 — 실제로는 `argon2` 나 `bcrypt` 크레이트를 쓴다.
시뮬레이션은 「솔트 · 반복 · 저장 형식 · 검증 · 상수 시간 비교」라는 뼈대를 손으로 보여 주려고 만든 것이다.

### (1) 솔트 만들기 — `generate_salt`

**언제 쓰나** — 비밀번호를 새로 해싱할 때마다 한 번 부른다.
같은 비밀번호라도 결과를 다르게 만드는 재료다.

```text
SystemTime::now() - UNIX_EPOCH ─► as_nanos() : u128 하나
        │
        ▼  i = 0..15 마다  (now >> (i*8)) & 0xFF  를 u8 로
salt = [바이트0, 바이트1, …, 바이트15]   (16바이트)
```

1. 현재 시각을 유닉스 기원(1970년) 이후의 나노초 수로 얻는다.
2. 시각이 기원보다 앞서면 `unwrap_or_default()` 가 0 을 준다.
3. 그 큰 정수를 8비트씩 오른쪽으로 밀어 가며 아래 8비트를 잘라 16칸에 채운다.
4. 원본 주석대로 실제로는 **CSPRNG**(예: `OsRng`)를 써야 한다 — 시각은 무작위가 아니다.

> **솔트** — 해싱 전에 비밀번호에 덧붙이는, 해싱마다 새로 만든 바이트 묶음.\
> 예: 두 사용자가 모두 `1234` 를 써도 솔트가 달라 해시가 다르다.

> **CSPRNG** — 암호용으로 예측할 수 없게 만든 난수 생성기.\
> 예: 운영체제가 주는 난수를 쓰는 `OsRng`.

### (2) 섞고 오래 굽기 — `hash_with_salt`

**언제 쓰나** — 해싱할 때와 검증할 때 **둘 다** 부른다.
같은 비밀번호 · 같은 솔트 · 같은 반복 횟수면 언제나 같은 32바이트가 나와야 한다.

```text
combined = 비밀번호 바이트 ++ 솔트 16바이트
hash[i % 32] ^= combined[i]          ← 초기 상태 (XOR 로 32칸에 접어 넣기)

round = 0 .. iterations-1 마다:
  new[i] = ((hash[i] + hash[i+1]) * (hash[i+7] | 1)) + (round as u8)
           (모든 덧셈·곱셈은 wrapping, 인덱스는 % 32)
  hash = new
```

1. 비밀번호 바이트 뒤에 솔트를 이어 붙인다.
2. 붙인 바이트를 차례로 32칸 배열에 XOR 로 접어 넣는다 — 32바이트를 넘으면 앞칸으로 돌아와 겹친다.
3. 라운드마다 각 칸이 바로 다음 칸과 7칸 뒤 칸에 기대도록 섞는다.
4. 곱할 값에 `| 1` 을 붙여 맨 아래 비트를 1 로 만든다 — 원본 주석대로 「0 곱셈 방지」다(0 을 곱하면 그 칸 정보가 통째로 사라진다).
5. `wrapping_add` · `wrapping_mul` 은 넘치면 256 으로 나눈 나머지로 감싸 돈다.
6. `round as u8` 은 라운드 번호의 아래 8비트만 쓴다 — 256 라운드마다 같은 값이 돌아온다.
7. 이 반복이 **key stretching** 이다 — 한 번 계산하는 데 일부러 시간이 들게 해 공격자의 대입 비용을 키운다.

> **key stretching** — 해시 계산을 여러 번 되풀이해 한 번 시도하는 비용을 늘리는 기법.\
> 예: 1000 라운드면 공격자도 후보 하나마다 1000 라운드를 돌려야 한다.

> **브루트포스** — 가능한 비밀번호를 하나씩 모두 대입해 보는 공격.\
> 예: `aaaa`, `aaab`, … 순서로 해시를 계산해 저장값과 견준다.

### (3) 저장 문자열 만들기 — `hash_password`

**언제 쓰나** — 가입하거나 비밀번호를 바꿀 때 한 번 부르고, 돌려받은 문자열을 DB 에 저장한다.

```text
salt = generate_salt()                 → 16바이트 → hex 32글자
hash = hash_with_salt(pw, &salt)       → 32바이트 → hex 64글자
format!("${}${}${}", iterations, salt_hex, hash_hex)

예) $1000$<32글자>$<64글자>
```

1. 매번 새 솔트를 만들고 그 솔트로 해시를 계산한다.
2. 바이트마다 `format!("{:02x}", b)` 로 두 글자 소문자 hex 를 만들어 이어 붙인다.
3. 반복 횟수 · 솔트 · 해시를 `$` 로 이어 한 문자열에 담는다 — 원본은 이를 PHC 스타일 형식이라 부른다.
4. 길이는 `$` 세 개 + 반복 횟수의 자릿수 + 32 + 64 다.
5. 솔트는 비밀이 아니다 — 검증할 때 다시 써야 하므로 해시 옆에 그대로 저장한다.
솔트의 일은 숨는 것이 아니라 「해시마다 다르게 만드는 것」이다.

> **hex** — 바이트 하나를 16진수 두 글자로 적는 표기.\
> 예: 바이트 10 → `0a`, 255 → `ff`.

### (4) 검증 — `verify_password`

**언제 쓰나** — 로그인할 때 입력된 비밀번호와 저장 문자열을 받아 맞는지 판단한다.

```text
stored = "$1000$ab12…$9f3e…"
split('$') → ["", "1000", "ab12…", "9f3e…"]   (4조각이 아니면 false)
            parts[1] 파싱 실패 → false
            parts[2] → 2글자씩 잘라 16바이트 솔트
PasswordHasher::new(파싱한 반복 횟수).hash_with_salt(입력, &솔트) → hex
constant_time_compare(계산한 hex, parts[3])
```

1. 문자열이 `$` 로 시작하므로 `split('$')` 의 첫 조각은 빈 문자열이다 — 그래서 조각이 정확히 4개여야 한다.
2. 반복 횟수는 `self.iterations` 가 아니라 **저장 문자열의 값**을 쓴다 — 저장할 때와 같은 조건으로 다시 굽기 위해서다.
3. 솔트 hex 를 `&salt_hex[i*2..i*2+2]` 로 두 글자씩 잘라 `u8::from_str_radix(…, 16)` 으로 바이트로 되돌린다.
4. hex 가 아닌 글자면 `unwrap_or(0)` 이 조용히 0 을 넣는다.
5. 같은 솔트 · 같은 반복으로 입력 비밀번호를 다시 해싱하고, 그 hex 를 저장된 해시 hex 와 견준다.
6. 해시는 되돌릴 수 없으므로 「풀어서 견주기」가 아니라 「다시 계산해 견주기」다.

### (5) 상수 시간 비교 — `constant_time_compare`

**언제 쓰나** — 비밀과 관련된 두 값이 같은지 볼 때 `==` 대신 쓴다.

```text
a = "9f3e…", b = "9f3d…"
길이 다르면 → false (곧장)
길이 같으면 → acc = 0
              각 자리: acc |= (x ^ y)     ← 같으면 0, 다르면 0 아닌 비트
              끝까지 다 돈 뒤 acc == 0 ?
```

1. 길이가 다르면 바로 `false` 다 — 해시 hex 길이(64)는 형식상 알려진 값이라 숨길 것이 아니다.
2. 길이가 같으면 모든 바이트 쌍을 XOR 하고 그 결과를 OR 로 누적한다.
3. 한 바이트라도 다르면 누적값에 비트가 남는다.
4. 중간에 멈추지 않으므로, 첫 글자가 틀렸든 마지막 글자가 틀렸든 같은 횟수만큼 돈다.
5. 보통의 `==` 는 처음 다른 자리에서 멈출 수 있다 — 그러면 걸린 시간으로 「몇 글자까지 맞았나」가 새어 나간다.

> **타이밍 공격** — 연산에 걸린 시간 차이를 재서 비밀 정보를 알아내는 공격.\
> 예: 비교가 늦게 끝날수록 앞부분이 더 많이 맞았다고 짐작한다.

### (6) 실제로는 — `argon2` 크레이트

**언제 쓰나** — 실제 서비스에서는 (1)~(5)를 직접 만들지 않고 이 크레이트에 맡긴다.
원본의 `main` 은 이 코드를 실행하지 않고 문자열로 찍어 보여 줄 뿐이다.

```text
시뮬레이션                      argon2 = "0.5"
generate_salt()           ↔    SaltString::generate(&mut OsRng)
PasswordHasher::new(1000) ↔    Argon2::default()
hash_password(pw)         ↔    argon2.hash_password(pw.as_bytes(), &salt)?.to_string()  (PHC 형식)
문자열 split 해 솔트 복원  ↔    PasswordHash::new(&hash_string)?
verify_password(pw, s)    ↔    Argon2::default().verify_password(pw.as_bytes(), &parsed)?
```

1. 솔트 생성은 `OsRng`(운영체제 난수)로 한다.
2. 결과는 알고리즘 · 파라미터 · 솔트 · 해시를 함께 담은 PHC 형식 문자열이다.
3. 검증은 그 문자열을 파싱한 뒤 `verify_password` 가 맡는다 — 성공 · 실패가 `Result` 로 돌아온다.

## 문법 — 형태와 규칙

```rust
let a: u8 = 200;
let b = a.wrapping_add(100);          // 300 을 256 으로 감싼 44
let c = a.wrapping_mul(3);            // 600 을 256 으로 감싼 88
let r = 300u32 as u8;                 // 상위 비트를 버려 44
let hex = format!("{:02x}", 10u8);    // "0a"
let back = u8::from_str_radix("0a", 16).unwrap_or(0); // 10
let parts: Vec<&str> = "$1000$ab$cd".split('$').collect(); // ["", "1000", "ab", "cd"]
let diff = b"ab".iter().zip(b"ac".iter())
    .fold(0u8, |acc, (x, y)| acc | (x ^ y));
let same = diff == 0;                 // false
```

- `wrapping_add` · `wrapping_mul` — 넘침을 오류로 보지 않고 감싸 돈다. 해시처럼 「넘쳐도 되는 섞기」에 쓴다.
- `x as u8` — 더 큰 정수를 `u8` 로 바꾸면 아래 8비트만 남는다.
- `{:02x}` — 두 자리, 빈 자리는 0, 소문자 16진수.
- `u8::from_str_radix(s, 16)` — 16진수 문자열을 바이트로. 실패하면 `Err` 라 `unwrap_or` 로 기본값을 준다.
- `&s[a..b]` — 문자열 바이트 범위 슬라이스. 범위가 길이를 넘거나 글자 경계가 아니면 패닉이다.
- `split('$')` — 구분자 앞의 빈 조각도 결과에 든다.
- `iter().zip().fold()` — 두 열을 짝지어 한 값으로 누적한다. 상수 시간 비교의 몸통이다.
- 저장 형식 — `$반복횟수$솔트hex(32)$해시hex(64)`.
- 원본이 적은 실제 의존성 — `argon2 = "0.5"` 또는 `bcrypt = "0.15"`.

## 어디서 틀리나

### 1. 비밀번호에 SHA · MD5 를 쓴다

원본의 팁: SHA/MD5 는 비밀번호에 절대 쓰지 않는다 — 너무 빨라서 브루트포스에 취약하다.
원본은 「GPU로 초당 수십억 개 해시 가능」이라 적는다 (원본의 주장 — 정확한 수치는 확인 필요).
빠른 해시는 파일 무결성 같은 데 쓰는 것이고, 비밀번호 해싱 전용 알고리즘은 **의도적으로 느리다**.
원본 체크리스트의 [금지] 「MD5, SHA 단독 사용」도 같은 말이다.

### 2. 솔트를 안 쓰거나 고정한다

원본: 솔트가 없으면 레인보우 테이블 공격이 가능하다.
미리 계산해 둔 「비밀번호 → 해시」 표가 그대로 통하기 때문이다.
솔트를 코드에 박아 두면(하드코딩) 모든 사용자가 같은 솔트를 쓰는 셈이라 효과가 거의 없다 — 체크리스트의 [금지] 「하드코딩된 솔트」.
솔트는 사용자마다, 해싱할 때마다 새로 만든다.

> **레인보우 테이블** — 흔한 비밀번호들의 해시를 미리 계산해 둔 거대한 표.\
> 예: 저장값을 표에서 찾기만 하면 원래 비밀번호가 나온다.

### 3. 솔트를 시각으로 만든다

시뮬레이션의 `generate_salt` 는 시각에서 바이트를 뽑는다.
시각은 짐작할 수 있고, 상위 바이트들은 거의 바뀌지 않으며, `u128` 의 상당 부분은 늘 0 이다.
두 번 연달아 불러도 보통은 시각이 달라 솔트가 다르겠지만, OS 시계 해상도에 따라 같은 값이 나올 가능성도 있다 (확인 필요).
시스템 시각이 기원보다 앞서면 솔트가 전부 0 이 된다.
그래서 원본 주석이 「실제로는 CSPRNG 사용」이라고 못 박는다.

### 4. 비교를 `==` 로 한다

원본의 팁: 비교는 상수 시간으로 해야 타이밍 공격을 막는다.
체크리스트의 [필수] 「상수 시간 비교」.

### 5. 깨진 저장 문자열에서 패닉이 난다

`verify_password` 는 조각 개수와 반복 횟수 파싱은 검사하지만 솔트 길이는 검사하지 않는다.
솔트 hex 가 32글자보다 짧으면 `&salt_hex[i*2..i*2+2]` 가 범위를 넘어 **패닉**한다 — `false` 가 아니다.
한글처럼 여러 바이트 글자가 섞이면 글자 경계에서 잘려 패닉할 수도 있다.
반대로 hex 가 아닌 영문자는 `unwrap_or(0)` 으로 0 이 되어 조용히 넘어간다.

### 6. 대문자 hex 저장값

계산한 해시는 늘 소문자 hex 다.
저장된 해시 hex 를 누가 대문자로 바꿔 두었다면 같은 바이트라도 글자가 달라 `false` 가 된다.

### 7. 시뮬레이션을 실제로 쓴다

원본: 「교육용 시뮬레이션입니다. 실제 사용하면 안 됩니다!」
XOR 접기와 손으로 만든 라운드 식은 암호학적으로 검증된 해시가 아니다.
반복이 있어도 메모리를 많이 요구하지 않는다(원본이 Argon2id · scrypt 의 장점으로 꼽는 「메모리 하드」가 없다).

### 8. 평문 저장 · 정책 부재

체크리스트의 [금지] 「평문 저장」, [권장] 「비밀번호 정책(최소 길이, 복잡성)」.
아무리 해싱을 잘해도 `1234` 는 대입 몇 번에 뚫린다.

| 이 문서의 서술 | 누가 보장하나 |
|---|---|

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 사용자 비밀번호 저장 | Argon2id(권장) · bcrypt · scrypt · PBKDF2 | SHA · MD5 단독, 평문 |
| 솔트 만들기 | CSPRNG(`OsRng`, `SaltString::generate`) | 시각, 고정 문자열 |
| 저장값 검증 | 같은 솔트 · 파라미터로 다시 계산 + 상수 시간 비교 | `==` 비교, 해시를 「풀려는」 시도 |
| 해싱 원리 공부 | 이 항목의 시뮬레이션 | 시뮬레이션을 실제 서비스에 넣기 |

## 핵심 문장

1. **비밀번호는 전용 해싱 알고리즘으로 저장한다** — 원본은 Argon2id 를 권장하고, 빠른 SHA · MD5 는 금지한다.
2. **솔트는 해싱마다 새로, 예측할 수 없게** 만들고 해시 옆에 함께 저장한다 — 같은 비밀번호도 저장값이 달라진다.
3. **검증은 「다시 굽기」다** — 저장된 솔트와 반복 횟수로 입력을 다시 해싱해 견준다.
4. **비교는 상수 시간으로** — 처음 다른 자리에서 멈추지 않아야 시간으로 정보가 새지 않는다.
5. **반복 라운드는 공격 비용을 키우려고 일부러 느리게 만든 것**이다.

## 용어 풀이

- **해싱** — 입력을 되돌릴 수 없는 고정 길이 값으로 바꾸는 일.
- **솔트** — 해싱 전에 덧붙이는, 해싱마다 새로 만든 바이트.
- **CSPRNG** — 암호용으로 예측할 수 없게 만든 난수 생성기.
- **`OsRng`** — 운영체제 난수를 쓰는 CSPRNG.
- **key stretching** — 해시를 여러 번 되풀이해 한 번 시도하는 비용을 키우는 기법.
- **브루트포스** — 가능한 값을 모두 대입해 보는 공격.
- **레인보우 테이블** — 흔한 비밀번호의 해시를 미리 계산해 둔 표.
- **타이밍 공격** — 연산 시간 차이로 비밀을 알아내는 공격.
- **상수 시간 비교** — 입력 내용과 상관없이 같은 횟수만큼 도는 비교.
- **메모리 하드** — 계산에 많은 메모리를 요구해 병렬 대량 공격을 어렵게 하는 성질.
- **PHC 형식** — 알고리즘 · 파라미터 · 솔트 · 해시를 `$` 로 이어 한 문자열에 담는 저장 형식.
- **hex** — 바이트를 16진수 두 글자로 적는 표기.
- **wrapping 연산** — 넘치면 감싸 도는 정수 연산.
