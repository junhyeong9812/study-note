## 한눈에 — 쉽게 말하면

**프로퍼티 기반 테스트는 「제품 하나하나를 재는 검사」가 아니라 「규칙을 정해 두고 아무 제품이나 마구 집어 재는 품질 검사」다.**
보통 단위 테스트는 「이 입력에는 이 답」을 사람이 골라 적는다.
품질 검사원은 다르게 일한다.
「어떤 병이든 뚜껑을 닫았다 열면 처음 상태로 돌아와야 한다」 같은 규칙을 먼저 정한다.
그다음 창고에서 병을 아무거나 백 개 집어 규칙이 깨지는지 본다.
깨진 병이 나오면 「어느 병에서 깨졌나」를 적고, 같은 문제를 일으키는 더 단순한 병을 찾아 보고한다.
프로퍼티 기반 테스트도 똑같은 구조다.

| 비유 | 실체 |
|---|---|
| 품질 규칙 | 프로퍼티 — 모든 입력에서 성립해야 하는 속성 |
| 창고에서 병을 아무거나 집기 | 전략(생성기)이 무작위 입력을 만든다 |
| 백 개 집어 재기 | 실행기가 프로퍼티를 정해진 횟수만큼 반복한다 |
| 깨진 병 기록 | 실패한 반복 번호와 반례 메시지 |
| 더 단순한 병 찾아 보고 | shrinking — 반례를 줄여 작은 반례를 찾는다 |

```text
  전략(생성기) ──무작위 입력──▶ 프로퍼티 검사 ──▶ Ok  → 다음 입력
                                     │
                                     └──▶ Err → 반례 기록 → (proptest 라면) 반례 줄이기
```

> **프로퍼티** — 모든 입력에 대해 성립해야 하는 속성.\
> 예: 어떤 문자열 `s` 든 `reverse(reverse(s)) == s` 다.

## 이 주제가 답하려는 질문

1. 입력을 사람이 고르지 않고 무작위로 만들 때, 무엇을 검사해야 하나(어떤 프로퍼티를 세우나)?
2. 무작위 입력을 어떻게 만들고, 같은 입력을 어떻게 다시 재현하나?
3. 프로퍼티가 깨지면 실행기는 무엇을 알려 주고, 반례를 어떻게 다루나?
4. 이 예제의 순수 Rust 흉내와 진짜 `proptest` 크레이트는 무엇이 같고 무엇이 다른가?

## 동작 방식

이 예제는 `proptest` 크레이트를 쓰지 않는다.
개념과 패턴을 순수 Rust 로 흉내 낸 작은 실행기(`TestRunner`)를 만들어 일곱 개 프로퍼티를 검사한다.
마지막에 진짜 `proptest` 코드의 모양과 shrinking 개념을 글로 찍는다.

### (1) 의사 난수 생성기 — 고정 시드의 LCG

**언제 쓰나** — 무작위 입력의 재료가 되는 수를 뽑을 때 쓴다.
시드를 고정하면 몇 번을 돌려도 같은 수열이 나와 실패를 재현할 수 있다.

```text
TestRunner::new(100)          seed = 12345 (고정)
        │
next_u64() 한 번 부를 때마다
        │   seed = seed × 6364136223846793005 + 1442695040888963407   (2^64 에서 감아 돎)
        ▼
새 seed 를 돌려준다 → 다음 호출은 이 값에서 이어진다
```

- 실행기는 `seed` 를 12345 로 고정해 만든다.
- `next_u64` 는 seed 에 큰 상수를 곱하고 더해 새 seed 로 바꾸고, 그 값을 돌려준다.
- 곱셈과 덧셈은 `wrapping_mul` · `wrapping_add` 라서 `u64` 범위를 넘으면 감아 돌고 패닉하지 않는다.
- 같은 시드에서 시작하면 같은 순서로 같은 수가 나오므로, 프로그램을 다시 돌려도 모든 프로퍼티는 같은 입력을 받는다.
- 일곱 프로퍼티가 **실행기 하나를 함께 쓴다**.
- 그래서 프로퍼티 2 의 입력은 프로퍼티 1 이 수를 몇 개 꺼내 썼는지에 달려 있다.
- 앞에 프로퍼티를 하나 끼워 넣거나 앞 프로퍼티가 일찍 실패해 수를 덜 꺼내면, 뒤 프로퍼티들이 받는 입력이 통째로 바뀐다.

> **LCG(선형 합동 생성기)** — `다음 = 현재 × a + c` 를 되풀이해 수열을 만드는 의사 난수 생성기.\
> 예: `next_u64` 의 `seed.wrapping_mul(…).wrapping_add(…)`.

> **시드** — 의사 난수 수열의 시작값.\
> 예: `seed: 12345`.

### (2) 입력 만들기 — 전략 흉내

**언제 쓰나** — 프로퍼티에 넣을 값(정수 · 문자열 · 벡터)을 원하는 범위와 모양으로 만들 때 쓴다.
진짜 `proptest` 에서 「전략」이 하는 일이다.

```text
next_i32(min, max)
   range = (max - min) as u64 + 1
   next_u64() % range  → 0 ..= range-1
   + min               → min ..= max          (양 끝 포함)

next_string(max_len)
   len = next_u64() % max_len  → 0 ..= max_len-1
   글자마다 next_u64() % 26 + b'a' → 'a' ..= 'z'
```

- `next_i32(min, max)` 는 범위 크기 `range` 로 나눈 나머지에 `min` 을 더해 `[min, max]` 의 정수를 만든다(양 끝 포함).
- `next_string(max_len)` 는 먼저 길이를 `max_len` 으로 나눈 나머지로 정하므로 길이는 0 부터 `max_len - 1` 까지다.
- 글자는 26 으로 나눈 나머지에 `b'a'` 를 더해 영문 소문자만 나온다.
- 벡터는 프로퍼티 안에서 직접 만든다.
- 길이를 `next_u64() % N` 으로 정하고 `(0..len).map(|_| rng.next_i32(lo, hi)).collect()` 로 채운다.
- 길이가 0 인 빈 입력도 나올 수 있다 — 빈 문자열 · 빈 벡터도 검사된다.

> **전략(strategy)** — 어떤 모양과 범위의 값을 어떻게 무작위로 만들지 정한 것.\
> 예: `proptest` 의 `"[a-z]{0,100}"`, 이 예제의 `next_string(20)`.

### (3) 실행기 `run` — 반복하고 첫 실패에서 멈춘다

**언제 쓰나** — 프로퍼티 하나를 정해진 횟수만큼 무작위 입력으로 돌릴 때 쓴다.

```text
run("이름", prop)
   "  이름 ... " 를 줄바꿈 없이 찍는다
   i = 0 .. iterations-1 동안
       prop(self) ──Ok(())──▶ 다음 i
                  └─Err(msg)─▶ "FAILED (iteration i)" 찍고
                                "    msg" 찍고  → return (남은 반복 안 함)
   반복을 다 통과하면 "OK (iterations iterations)" 를 찍는다
```

- `run` 은 먼저 `print!` 로 이름을 찍고 줄을 바꾸지 않는다.
- 그래서 결과(`OK …` 또는 `FAILED …`)가 같은 줄 뒤에 붙는다.
- 프로퍼티는 클로저 `prop` 이다.
- 클로저는 실행기(`&mut TestRunner`)를 받아 그 안에서 입력을 만들고, 성립하면 `Ok(())`, 깨지면 반례를 담은 `Err(String)` 을 돌려준다.
- `Err` 가 나오면 몇 번째 반복(`iteration i`, 0 부터 셈)에서 깨졌는지와 메시지를 찍고 그 프로퍼티를 끝낸다.
- 다음 `runner.run(…)` 호출은 그대로 이어진다 — 한 프로퍼티의 실패가 다른 프로퍼티를 막지 않는다.
- 다만 `run` 은 `Result` 만 본다.
- 클로저 안에서 **패닉**(나머지 0 · 정수 넘침 등)이 나면 `run` 이 잡지 못해 프로그램 전체가 멈추고, 남은 프로퍼티는 돌지 않는다.
- 이 흉내 실행기에는 **shrinking 이 없다**.
- 실패하면 처음 만난 반례를 그대로 보여 줄 뿐, 더 작은 반례를 찾지 않는다.

> **반례** — 프로퍼티를 깨뜨리는 입력.\
> 예: `sort` 가 중복을 지우는 버그라면 `[3, 3]`.

> **클로저** — 주변 값을 붙잡을 수 있는 이름 없는 함수.\
> 예: `|rng| { let s = rng.next_string(20); … }`.

### (4) 프로퍼티의 갈래 — 항등성 · 불변량 · 라운드트립 · 법칙

**언제 쓰나** — 「정답을 미리 알 수 없는 무작위 입력」에서도 확인할 수 있는 성질을 찾을 때 쓴다.
원본의 팁은 대표 프로퍼티로 라운드트립(encode/decode), 항등성(`f(f(x)) == x`), 불변량(정렬 후 길이 보존)을 든다.

```text
프로퍼티                 갈래        무엇을 검사하나
1 reverse 항등성         항등성      reverse(reverse(s)) == s       (s: 길이 0..19 소문자)
2 reverse 길이 보존      불변량      s.len() == reverse(s).len()    (s: 길이 0..49)
3 sort 정렬 보장         불변량      모든 이웃 쌍 w[0] <= w[1]       (v: 길이 0..19, -100..=100)
4 sort 길이 보존         불변량      v.len() == sort(v).len()       (v: 길이 0..29, -50..=50)
5 sort 원소 보존         불변량      정렬한 두 벡터가 같다(같은 다중집합) (v: 길이 0..19, -10..=10)
6 RLE 라운드트립         라운드트립  decode(encode(data)) == data    (data: 길이 0..29, 값 0..=3)
7 덧셈 교환법칙          수학 법칙   a + b == b + a                 (a, b: -1000..=1000)
```

- 항등성: 같은 함수를 두 번 적용하면 원래로 돌아온다.
- 문자열 뒤집기는 대표적인 예다.
- 불변량: 함수가 무엇을 하든 바뀌면 안 되는 성질이다.
- 정렬은 길이와 원소 구성을 바꾸지 않고, 결과의 모든 이웃 쌍이 `<=` 이다.
- 프로퍼티 3 은 `windows(2)` 로 이웃한 두 원소씩 훑는다.
- 프로퍼티 5 는 원본 `v` 와 `sort(v)` 결과를 **둘 다 다시 정렬해** 비교한다.
- 원소의 순서는 무시하고 「무엇이 몇 개 있나」만 같은지 보는 것이다.
- 라운드트립: 인코딩한 것을 디코딩하면 원본과 같아야 한다.
- 수학 법칙: 덧셈 교환법칙처럼 늘 성립해야 하는 식도 프로퍼티가 된다.
- 프로퍼티 6 의 데이터는 `% 4` 로 값을 0~3 네 가지로만 만든다.
- 값의 가짓수가 적으면 같은 값이 연달아 나올 일이 많아, RLE 가 압축할 「반복 구간」이 자주 생긴다.
- 0~255 를 고르게 뽑으면 이웃한 값이 같을 일이 드물어 RLE 의 핵심 경로를 거의 검사하지 못한다.

> **불변량** — 연산 전후로 바뀌면 안 되는 성질.\
> 예: 정렬 전후의 길이.

> **라운드트립** — 변환한 것을 되돌렸을 때 원본으로 돌아오는 성질.\
> 예: `rle_decode(&rle_encode(data)) == data`.

> **다중집합(multiset)** — 순서는 보지 않고 원소와 그 개수만 보는 모음.\
> 예: `[2, 1, 2]` 와 `[1, 2, 2]` 는 같은 다중집합이다.

### (5) 검사 대상 RLE — `[개수, 바이트]` 쌍

**언제 쓰나** — 라운드트립 프로퍼티의 검사 대상이다.
같은 바이트가 이어지면 `[개수, 바이트]` 두 바이트로 줄인다.

```text
data      = [0, 0, 0, 2, 2, 1]
rle_encode: 0 이 3번 → [3, 0]   2 가 2번 → [2, 2]   1 이 1번 → [1, 1]
encoded   = [3, 0, 2, 2, 1, 1]
rle_decode: chunks(2) → [3,0] [2,2] [1,1] → 0,0,0, 2,2, 1
결과      = [0, 0, 0, 2, 2, 1]  == data
```

- 빈 입력이면 인코더는 곧바로 빈 벡터를 돌려준다.
- 인코더는 첫 바이트를 `current`, `count = 1` 로 잡고 둘째 바이트부터 훑는다.
- 같은 바이트이고 `count < 255` 면 개수를 하나 늘린다.
- 다르거나 개수가 255 에 이르면 지금까지의 `[count, current]` 를 넣고 새 그룹을 시작한다.
- 개수가 `u8` 이라 255 를 넘을 수 없으므로 255 에서 끊는 것이다.
- 루프가 끝나면 마지막 그룹을 넣는다.
- 디코더는 `chunks(2)` 로 두 바이트씩 끊어 `chunk[0]` 번만큼 `chunk[1]` 을 넣는다.
- `chunk.len() == 2` 검사는 바이트 수가 홀수인 입력이 들어와 마지막 조각이 한 바이트일 때 `chunk[1]` 에 접근하다 패닉하지 않게 막는다.
- 이 예제의 생성기는 길이가 최대 29 라서, 한 값이 255 번 넘게 이어지는 입력은 **만들어지지 않는다**.
- 따라서 `count < 255` 에서 끊는 경로는 100 번을 돌려도 검사되지 않는다.

> **RLE(Run-Length Encoding)** — 같은 값이 이어지는 구간을 「개수와 값」으로 줄이는 압축.\
> 예: `[7, 7, 7]` → `[3, 7]`.

### (6) 진짜 `proptest` 와 shrinking

**언제 쓰나** — 실제 프로젝트에서 프로퍼티 테스트를 쓸 때 쓴다.
예제는 `Cargo.toml` 에 `proptest = "1.0"` 을 넣는다고 적는다.

```text
proptest! {
    #[test]
    fn test_reverse(s in "[a-z]{0,100}") { … }        ← 이름 in 전략
    #[test]
    fn test_sort(v in prop::collection::vec(-100..100i32, 0..50)) { … }
}
        │
        ▼  proptest 가 전략으로 입력을 여러 번 만들어 본문을 돌린다
        ▼  assert 가 깨지면 → shrinking: 반례를 더 단순하게 줄여 가며 여전히 깨지는지 본다
        ▼
   줄어든 반례를 보고한다   (원본 예: vec![99, -50, 77, 3] → vec![1, 0])
```

- `use proptest::prelude::*;` 로 필요한 것을 가져온다.
- `proptest! { … }` 매크로 안에 `#[test]` 함수를 쓰고, 인자를 `이름 in 전략` 꼴로 적는다.
- `"[a-z]{0,100}"` 는 정규식 모양의 문자열 전략이다 — 흉내의 `next_string` 에 해당한다.
- `prop::collection::vec(-100..100i32, 0..50)` 는 `-100..100` 범위 `i32` 로 길이 `0..50` 의 벡터를 만드는 전략이다 — 흉내에서 `len` 을 정하고 `next_i32` 로 채우는 부분에 해당한다.
- 본문은 `Result` 를 돌려주는 대신 `assert_eq!` · `assert!` 로 검사한다.
- shrinking 은 실패한 입력을 줄여 가며 여전히 실패하는 더 작은 입력을 찾는다.
- 원본은 「`vec![99, -50, 77, 3]` 에서 실패 → `vec![1, 0]` 으로 축소」를 예로 들고, 이를 통해 디버깅이 훨씬 쉬워진다고 한다.
- 이 예제의 흉내 실행기는 이 줄이는 단계가 없다 — (3) 참고.
- 예제는 이 `proptest` 코드를 실제로 돌리지 않고 `println!` 으로 글자만 찍는다.
- `println!` 의 형식 문자열에서 `{` · `}` 는 자리표시자라서, 글자 그대로 찍으려면 `{{` · `}}` 로 두 번 쓴다.
- `\"` 는 문자열 안의 큰따옴표 하나다.

> **shrinking** — 실패한 입력을 더 작고 단순한 입력으로 줄여 가며 여전히 실패하는 것을 찾는 과정.\
> 예: 원본 예시의 `vec![99, -50, 77, 3]` → `vec![1, 0]`.

## 문법 — 형태와 규칙

흉내 실행기에 프로퍼티 하나를 더하는 최소 예제다.
아래 `sort` 는 일부러 버그(중복 제거)를 심은 것이다.

```rust
// 일부러 버그를 심은 정렬 — dedup 은 이웃한 같은 값을 하나만 남긴다
fn buggy_sort(mut v: Vec<i32>) -> Vec<i32> {
    v.sort();
    v.dedup();
    v
}

runner.run("buggy_sort 길이 보존", |rng| {
    let len = (rng.next_u64() % 10) as usize;            // 길이 0..=9
    let v: Vec<i32> = (0..len).map(|_| rng.next_i32(0, 3)).collect();
    let sorted = buggy_sort(v.clone());
    if v.len() != sorted.len() {
        Err(format!("길이 변경: {:?} -> {:?}", v, sorted)) // 반례를 메시지에 담는다
    } else {
        Ok(())
    }
});
```

- 프로퍼티 클로저의 꼴은 `FnMut(&mut TestRunner) -> Result<(), String>` 이다.
- 입력은 클로저가 받은 `rng` 로 클로저 **안에서** 만든다.
- 원본 `v` 를 나중에 다시 써야 하면 `v.clone()` 을 넘긴다 — `sort` 가 `Vec` 의 소유권을 가져가기 때문이다.
- 깨졌을 때 `Err` 메시지에 **입력을 담는다** — 그래야 어떤 입력이 반례였는지 알 수 있다.
- 정렬 결과를 검사할 때는 `sorted.windows(2)` 로 이웃 쌍을 훑고, 하나라도 `w[0] > w[1]` 이면 곧바로 `return Err(…)` 한다.
- `v.dedup()` 은 **이웃한** 같은 값만 하나로 줄인다 — 정렬 뒤라면 모든 중복이 사라진다.
- `println!` · `format!` 에서 중괄호를 글자로 쓰려면 `{{` · `}}` 다.
- 진짜 `proptest` 라면 `proptest! { #[test] fn 이름(x in 전략) { assert!(…); } }` 꼴로 쓴다.

| 흉내 실행기 | 진짜 `proptest` |
|---|---|
| `TestRunner::new(100)` 의 반복 횟수 | 크레이트가 정한 반복 횟수 |
| `rng.next_string(20)` | `"[a-z]{0,100}"` 같은 문자열 전략 |
| `len` 을 정하고 `next_i32` 로 채운 `Vec` | `prop::collection::vec(범위, 길이범위)` |
| `Err(String)` 돌려주기 | `assert!` · `assert_eq!` |
| 첫 반례를 그대로 보고 | shrinking 으로 줄인 반례 보고 |

## 어디서 틀리나

### 1. 원본 팁의 「최소 반례」라는 말

원본의 주장 → 「proptest 의 shrinking 은 실패 시 최소 반례를 자동으로 찾아 준다」.
왜 의심스러운가 → shrinking 은 반례를 **줄여 가는** 과정이라 더 작은 반례를 내놓는 것은 맞다.
그러나 가능한 모든 반례 가운데 가장 작은 것을 찾는다고 보장하는지는 확인 필요다 — 「더 이상 이 방식으로는 줄일 수 없는 반례」일 수 있다.
원본의 `vec![99, -50, 77, 3]` → `vec![1, 0]` 도 어떤 프로퍼티인지 밝히지 않은 그림 예시다.

### 2. 흉내 실행기에는 shrinking 이 없다

이 예제의 `run` 은 처음 깨진 입력을 그대로 보여 주고 멈춘다.
길이 29 짜리 벡터에서 깨지면 29 개짜리 반례를 사람이 들여다봐야 한다.
「shrinking 개념」 줄은 진짜 `proptest` 의 동작을 글로 설명한 것일 뿐이다.

### 3. 생성기의 범위가 경계를 덮지 못한다

RLE 인코더의 `count < 255` 분기는 같은 값이 255 번 넘게 이어져야 실행된다.
생성기는 길이 0~29 만 만들므로 이 분기는 절대 실행되지 않는다.
프로퍼티가 100 번 통과해도 「생성기가 만든 범위 안에서 깨지지 않았다」는 뜻일 뿐이다.
경계가 있는 코드라면 생성기가 그 경계를 넘는 입력도 만들게 해야 한다.

### 4. 검사 기준이 검사 대상과 같은 코드다

프로퍼티 5(원소 보존)는 결과와 원본을 둘 다 표준 `sort` 로 다시 정렬해 비교한다.
검사 대상 `sort` 도 속은 표준 `v.sort()` 다.
검사 대상이 쓰는 코드에 버그가 있으면 검사 쪽도 같은 버그를 가져 서로 맞아 버릴 수 있다.
다만 이 프로퍼티는 `sort` 가 원소를 **빼거나 더하는** 버그(예: `dedup`)는 잡아낸다 — 다시 정렬해도 개수가 달라지기 때문이다.

### 5. `next_string(0)` 은 패닉한다

길이를 `next_u64() % max_len` 으로 정하므로 `max_len` 이 0 이면 0 으로 나눈 나머지가 된다.
Rust 에서 정수를 0 으로 나누거나 나머지를 구하면 패닉한다.
`run` 은 패닉을 잡지 못하므로 프로그램 전체가 멈춘다.
또 `next_string(20)` 의 최대 길이는 20 이 아니라 19 다.

### 6. 범위를 넓히면 정수 넘침이 난다

교환법칙의 범위를 `-1000..=1000` 에서 `i32` 전체로 넓히면 `a + b` 가 `i32` 를 넘을 수 있다.
그보다 먼저 `next_i32(i32::MIN, i32::MAX)` 의 `max - min` 계산 자체가 `i32` 를 넘는다.
디버그 빌드에서 정수 넘침은 패닉이고, 이것도 `run` 이 잡지 못한다.
「수학적으로 늘 참인 법칙」도 고정 폭 정수에서는 범위에 따라 깨지는 곳이 생긴다.

### 7. 앞 프로퍼티가 뒤 프로퍼티의 입력을 바꾼다

일곱 프로퍼티가 실행기 하나의 난수 수열을 이어 쓴다.
프로퍼티를 하나 더 끼우거나, 앞 프로퍼티가 일찍 실패해 수를 덜 꺼내면 뒤 프로퍼티의 입력이 모두 달라진다.
「어제 실패한 입력」을 재현하려면 시드뿐 아니라 프로퍼티의 차례도 같아야 한다.

### 8. `use std::fmt;` 는 쓰이지 않는다

정답 코드의 주석은 「현재 사용되지 않지만 디스플레이 확장 가능성을 위해 유지」라고 한다.
쓰지 않는 `use` 는 컴파일러가 경고로 알린다 — 오류는 아니라 프로그램은 만들어진다(원본에 근거 없음 — 추론).

### 9. `s.len()` 은 글자 수가 아니라 바이트 수다

프로퍼티 2 는 `String::len` 을 비교하는데, 이것은 UTF-8 바이트 수다.
생성기가 ASCII 소문자만 만들어 여기서는 글자 수와 같다.
`reverse` 는 `chars()` 를 뒤집으므로 한글 같은 여러 바이트 글자가 섞여도 바이트 수는 그대로다.

### 10. 「항등성」이라는 이름

원본 팁은 `f(f(x)) == x` 를 항등성이라 부른다.
정확히는 「두 번 적용하면 항등」인 성질이라 정답 코드 주석은 involution 이라고 덧붙인다.
`f(x) == x` (함수 자체가 아무것도 안 함)와 헷갈리지 않아야 한다.

## 핵심 문장

1. **프로퍼티 테스트는 「이 입력엔 이 답」이 아니라 「모든 입력에서 이것이 참」을 검사한다** — 라운드트립 · 항등성 · 불변량 · 수학 법칙이 대표 꼴이다.
2. **무작위 입력은 전략(생성기)이 만들고, 시드를 고정하면 같은 입력을 재현한다** — 대신 난수 수열을 함께 쓰는 프로퍼티끼리 입력이 얽힌다.
3. **통과는 「생성기가 만든 범위 안에서는 깨지지 않았다」는 뜻이다** — 범위가 경계를 덮지 않으면 그 경로는 검사되지 않는다.
4. **실패하면 반례가 남는다** — 흉내 실행기는 첫 반례를 그대로 보여 주고, `proptest` 는 shrinking 으로 줄여서 보여 준다.

## 용어 풀이

- **프로퍼티(속성)** — 모든 입력에 대해 성립해야 하는 성질.
- **프로퍼티 기반 테스트(속성 기반 테스트)** — 무작위 입력을 많이 만들어 프로퍼티가 깨지는지 보는 테스트.
- **전략(strategy)** — 값을 어떤 모양 · 범위로 무작위 생성할지 정한 것.
- **생성기** — 이 예제에서 전략 노릇을 하는 `next_i32` · `next_string` 같은 함수.
- **의사 난수** — 계산으로 만든, 무작위처럼 보이는 수열.
- **LCG(선형 합동 생성기)** — `다음 = 현재 × a + c` 를 되풀이하는 의사 난수 생성기.
- **시드** — 의사 난수 수열의 시작값.
- **반례** — 프로퍼티를 깨뜨리는 입력.
- **shrinking** — 실패한 입력을 줄여 가며 여전히 실패하는 더 단순한 입력을 찾는 과정.
- **라운드트립** — 변환 후 되돌리면 원본이 되는 성질.
- **항등성(involution)** — 두 번 적용하면 원래로 돌아오는 성질, `f(f(x)) == x`.
- **불변량** — 연산 전후로 바뀌면 안 되는 성질.
- **다중집합** — 순서는 무시하고 원소와 개수만 보는 모음.
- **RLE** — 같은 값이 이어지는 구간을 `[개수, 값]` 으로 줄이는 압축.
- **클로저** — 주변 값을 붙잡을 수 있는 이름 없는 함수.
- **`windows(2)`** — 슬라이스를 이웃한 두 원소씩 겹쳐 훑는 메서드.
- **`chunks(2)`** — 슬라이스를 겹치지 않게 두 원소씩 끊는 메서드, 마지막 조각은 짧을 수 있다.
- **`dedup`** — 벡터에서 이웃한 같은 값을 하나만 남기는 메서드.
- **정수 넘침** — 계산 결과가 정수 타입의 범위를 벗어나는 일.

## 더 들어가면

- 정답 코드의 LCG 상수 `6364136223846793005` 는 Knuth 가 MMIX 에서 쓴 곱셈 상수로 알려져 있다(확인 필요).
- LCG 의 낮은 비트는 주기가 짧아, `% 4` · `% 26` 처럼 작은 수로 나눈 나머지만 쓰면 무작위성이 떨어질 수 있다 — 높은 비트를 쓰는 편이 낫다고들 한다(확인 필요).
- `proptest` 는 기본으로 한 테스트에 256 개 입력을 시도한다고 알려져 있다(확인 필요).
- `proptest` 는 실패한 입력의 시드를 `proptest-regressions` 디렉터리에 저장해 다음 실행에서 먼저 다시 돌린다(확인 필요).
- `prop_assert!` · `prop_assert_eq!` 는 패닉 대신 실패를 돌려주어 shrinking 과 더 잘 맞는다고 한다(확인 필요).
- `prop_map` · `prop_filter` · `prop_oneof!` 로 전략을 조합할 수 있다(확인 필요).
- Haskell 의 QuickCheck 가 이 방식의 원조로 꼽히고, Rust 에는 `quickcheck` 크레이트도 있다(확인 필요).
- 같은 계열의 기법으로, 입력을 바이트 단위로 바꿔 가며 크래시를 찾는 퍼징(`cargo fuzz`)이 있다(확인 필요).
