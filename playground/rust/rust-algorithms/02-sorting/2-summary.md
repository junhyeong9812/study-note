## 한눈에 — 쉽게 말하면

**정렬은 「카드 한 줄을 작은 수부터 늘어놓기」다.**
손에 든 카드를 정리하는 방법은 사람마다 다르다.
옆 카드끼리 비교해 바꾸는 사람(버블), 가장 작은 카드를 찾아 맨 앞으로 빼는 사람(선택), 한 장씩 집어 이미 정리된 쪽 알맞은 자리에 끼우는 사람(삽입)이 있다.
기준 카드 하나를 골라 작은 것과 큰 것으로 나누는 사람(퀵), 반으로 나눠 따로 정리한 뒤 두 묶음을 맞물리는 사람(머지)도 있다.
Rust 의 정렬 함수들도 똑같은 구조다.
결과는 모두 같은 「작은 수부터의 줄」이지만, 걸리는 시간 · 드는 메모리 · 같은 값끼리의 순서를 지키는지가 다르다.

| 비유 | 실체 |
|---|---|
| 카드 한 줄 | `&mut [i32]` 슬라이스 |
| 옆 카드와 자리 바꾸기 | `arr.swap(j, j + 1)` |
| 기준 카드 | 퀵 정렬의 피벗(`pivot`) |
| 두 묶음 맞물리기 | 머지 정렬의 병합 단계 |
| 숫자가 같은 카드의 원래 앞뒤 | 안정성(stability) |
| 사서 쓰는 정리 기계 | `sort` · `sort_unstable` |

```text
정렬 전   [64, 34, 25, 12, 22, 11, 90]
             │  (버블 · 선택 · 삽입 · 퀵 · 머지 · sort · sort_unstable)
             ▼
정렬 후   [11, 12, 22, 25, 34, 64, 90]   ← 어느 방법이든 같은 줄
```

## 이 주제가 답하려는 질문

1. 다섯 가지 정렬은 각각 한 단계에서 무엇을 하며, 왜 시간 복잡도가 O(n²) 와 O(n log n) 으로 갈리나?
2. 「안정 정렬」이란 무엇이고, 어느 알고리즘이 안정이며 어느 코드 줄이 그것을 결정하나?
3. Rust 의 빌림 규칙 아래에서 슬라이스를 둘로 나눠 재귀하거나, 원본 배열을 여러 번 복사해 쓰려면 어떻게 하나?
4. 표준 라이브러리의 `sort` · `sort_unstable` · `sort_by_key` · `sort_by` 계열은 언제 무엇을 고르나?

## 동작 방식

> **슬라이스** — 배열이나 `Vec` 의 연속된 일부를 가리키는 참조. `&mut [i32]` 는 고칠 수 있는 슬라이스다.\
> 예: `fn bubble_sort(arr: &mut [i32])` 는 배열이든 `Vec` 이든 받아 제자리에서 고친다.

### (1) 버블 정렬 — 옆끼리 비교해 큰 값을 끝으로 밀기

**언제 쓰나** — 원리를 배울 때.
데이터가 이미 거의 정렬돼 있으면 조기 종료 덕에 빨리 끝난다.

```text
입력 [3, 1, 2]          (n = 3)
패스 i=0 : j=0  3>1 → swap → [1, 3, 2]   swapped = true
           j=1  3>2 → swap → [1, 2, 3]   ← 가장 큰 3 이 끝에 자리잡음
패스 i=1 : j=0  1>2? 아니오               swapped = false → break
결과 [1, 2, 3]
```

- 안쪽 루프는 `arr[j] > arr[j + 1]` 이면 두 칸을 바꾼다.
- 한 패스가 끝날 때마다 남은 것 중 가장 큰 값이 맨 끝으로 간다.
- 그래서 안쪽 루프 범위는 `0..n - 1 - i` 로, 이미 자리잡은 마지막 `i` 칸을 건너뛴다.
- 한 패스 동안 한 번도 바꾸지 않았으면(`swapped == false`) 이미 정렬된 것이라 `break` 한다.
- 이 조기 종료 덕에 이미 정렬된 입력은 패스 한 번(비교 n−1 번)으로 끝난다 — 최선 O(n).
- 같은 값은 `>` 가 거짓이라 서로 바꾸지 않는다 — 안정이다.

> **패스** — 배열을 처음부터 한 번 훑는 일.\
> 예: 버블 정렬의 바깥 루프 한 바퀴가 패스 하나다.

### (2) 선택 정렬 — 남은 것 중 최솟값을 앞으로

**언제 쓰나** — 교환(`swap`) 횟수를 적게 하고 싶을 때(바깥 루프 한 바퀴에 한 번).
비교 횟수는 입력과 상관없이 늘 많다.

```text
입력 [2a, 2b, 1]        (a, b 는 같은 값 2 를 구별하는 표시)
i=0 : (0..3) 중 arr[j] 최소 → j=2 (값 1) → swap(0, 2) → [1, 2b, 2a]
i=1 : (1..3) 중 최소 → j=1 (2b)          → swap(1, 1) → [1, 2b, 2a]
결과 [1, 2b, 2a]        ← 2a 와 2b 의 앞뒤가 뒤집혔다
```

- `(i..n).min_by_key(|&j| arr[j])` 는 인덱스 `j` 들 가운데 `arr[j]` 가 가장 작은 `j` 를 고른다.
- 범위 `i..n` 은 `i < n` 이라 비어 있지 않으므로 `.unwrap()` 이 안전하다.
- 고른 인덱스와 `i` 를 `swap` 한다.
- 이 「멀리 떨어진 칸과의 교환」이 같은 값을 건너뛰어 순서를 뒤집을 수 있다 — 그래서 불안정이다.

> **`min_by_key`** — 반복자의 원소마다 클로저를 적용해 그 결과가 가장 작은 원소를 `Option` 으로 돌려준다.\
> 예: `(0..3).min_by_key(|&j| arr[j])` 는 값이 가장 작은 칸의 인덱스를 준다.

### (3) 삽입 정렬 — 한 장씩 집어 끼워 넣기

**언제 쓰나** — 거의 정렬된 데이터, 작은 데이터.
원본 주석대로 최선은 O(n) 이다.

```text
입력 [1, 3, 2]
i=1 : key=3, arr[0]=1 > 3? 아니오 → 그대로        [1, 3, 2]
i=2 : key=2, arr[1]=3 > 2 → 3 을 오른쪽으로 밀기   [1, 3, 3]   j=1
             arr[0]=1 > 2? 아니오 → 멈춤
      arr[1] = key                                  [1, 2, 3]
```

- `key = arr[i]` 를 따로 쥐어 둔다(칸은 곧 덮어쓰인다).
- 왼쪽으로 가며 `key` 보다 큰 값을 한 칸씩 오른쪽으로 민다(`arr[j] = arr[j - 1]`).
- 더 밀 것이 없으면 빈 자리 `arr[j]` 에 `key` 를 넣는다.
- 미는 조건이 `>` 라서 `key` 와 같은 값은 밀지 않는다 — 안정이다.
- 이미 정렬된 입력이면 `while` 이 한 번도 돌지 않아 전체가 n 번에 가깝게 끝난다.

### (4) 퀵 정렬 — 피벗으로 나누고 양쪽을 재귀

**언제 쓰나** — 평균 O(n log n) 이 필요하고 안정성은 필요 없을 때.

```text
partition([5, 2, 8, 1, 4])       pivot = 4 (마지막 원소, Lomuto)
 i=0
 j=0 : 5 <= 4? 아니오
 j=1 : 2 <= 4 → swap(0,1) → [2, 5, 8, 1, 4]  i=1
 j=2 : 8 <= 4? 아니오
 j=3 : 1 <= 4 → swap(1,3) → [2, 1, 8, 5, 4]  i=2
 끝  : swap(2, 4)          → [2, 1, 4, 5, 8]  return 2
                              └┬─┘  ▲  └┬─┘
                           피벗 이하 피벗 피벗 초과

quick_sort:  split_at_mut(2) → left = [2, 1]   right = [4, 5, 8]
             quick_sort(left)   quick_sort(&mut right[1..]) → [5, 8]
```

- `partition` 은 마지막 원소를 피벗으로 삼는다(Lomuto 방식).
- `i` 는 「피벗 이하 영역」의 다음 칸이다.
- `arr[j] <= pivot` 인 원소를 만날 때마다 `i` 자리로 보내고 `i` 를 늘린다.
- 끝에 피벗을 `i` 자리로 옮기면, 피벗 왼쪽은 모두 피벗 이하, 오른쪽은 모두 피벗 초과가 된다.
- 피벗은 제자리를 찾았으므로 재귀에서 뺀다(`right[1..]`).
- 이미 정렬된 입력이면 피벗이 늘 최댓값이라 한쪽이 n−1 개, 다른 쪽이 0 개로 갈린다 — 이것이 최악 O(n²) 이다.
- 멀리 떨어진 칸끼리 `swap` 하므로 불안정이다.

`split_at_mut(mid)` 은 하나의 `&mut` 슬라이스를 `[..mid]` 와 `[mid..]` 두 개의 `&mut` 슬라이스로 나눈다.
Rust 는 같은 데이터에 대한 `&mut` 참조를 동시에 둘 만들지 못하게 한다.
`split_at_mut` 은 두 조각이 겹치지 않음을 표준 라이브러리가 보증하고 둘을 한꺼번에 내준다.

> **피벗** — 퀵 정렬에서 나누는 기준으로 고른 원소.\
> 예: Lomuto 방식은 마지막 원소 `arr[arr.len() - 1]` 을 피벗으로 쓴다.

> **`split_at_mut`** — 가변 슬라이스를 겹치지 않는 두 가변 슬라이스로 쪼개는 메서드.\
> 예: `let (left, right) = arr.split_at_mut(2);` 는 `arr[..2]` 와 `arr[2..]` 를 동시에 고칠 수 있게 한다.

### (5) 머지 정렬 — 반으로 나눠 정렬하고 맞물리기

**언제 쓰나** — 최악에도 O(n log n) 이 필요하고 안정성이 필요할 때.
대가는 O(n) 추가 메모리다.

```text
[38, 27, 43, 3]
   분할 ─► left = [38, 27] → 재귀 → [27, 38]
          right = [43, 3]  → 재귀 → [3, 43]
   병합:  left[i] <= right[j] ?
          27 vs 3  → 3   ┐
          27 vs 43 → 27  │ arr 에 차례로 씀
          38 vs 43 → 38  │
          남은 43   → 43  ┘
   결과 [3, 27, 38, 43]
```

- `arr[..mid].to_vec()` · `arr[mid..].to_vec()` 로 두 절반을 새 `Vec` 에 복사한다.
- 복사본을 재귀로 정렬한 뒤, 두 앞머리를 비교해 작은 쪽을 원본 `arr[k]` 에 쓴다.
- 비교가 `<=` 라서 값이 같으면 왼쪽(원래 앞에 있던 것)을 먼저 쓴다 — 이 한 글자가 안정성을 만든다.
- 한쪽이 바닥나면 남은 쪽을 그대로 이어 쓴다.
- 복사본이 필요하므로 공간은 O(n) 이다.

> **안정 정렬** — 비교 기준이 같은 원소들의 원래 앞뒤 순서를 정렬 뒤에도 지키는 정렬.\
> 예: `[(1,'b'), (1,'a')]` 를 첫 값으로 안정 정렬하면 `'b'` 가 여전히 앞에 있다.

### (6) 표준 라이브러리 — `sort` 계열과 `sort_unstable` 계열

**언제 쓰나** — 실제 코드에서는 직접 짠 정렬 대신 이것을 쓴다.

```text
v1 = [(1,'b'), (1,'a'), (2,'c')]
v1.sort_by_key(|&(k, _)| k)       키 = 튜플의 첫 값
   키:  1      1      2
   안정 → 키가 같은 (1,'b') 와 (1,'a') 는 원래 앞뒤 그대로

v4.sort_unstable_by(|a, b| b.cmp(a))
   보통은 a.cmp(b) → 오름차순
   b.cmp(a)        → 비교 방향을 뒤집어 큰 값이 먼저 = 내림차순
```

- `sort()` 는 안정 정렬이다 — 원본 팁은 TimSort 기반이라고 한다.
- `sort_unstable()` 은 안정성이 없다 — 원본 팁은 pdqsort 기반이며 더 빠르고 추가 메모리를 쓰지 않는다고 한다.
- 원본 팁은 대부분의 경우 `sort_unstable()` 이 성능이 좋다고 한다.
- `sort_by_key(|x| 키)` 는 키 함수의 결과로 비교한다 — 특정 필드 기준 정렬.
- `sort_by(|a, b| Ordering)` 은 비교 함수를 직접 준다 — 커스텀 비교.
- `_unstable` 이 붙은 판(`sort_unstable_by` 등)도 같은 꼴이다.
- `sort_unstable` 로 `v1` 을 정렬하면 `(1,'b')` 와 `(1,'a')` 의 앞뒤는 약속되지 않는다.

> **`Ordering`** — 두 값의 비교 결과 `Less` · `Equal` · `Greater` 중 하나.\
> 예: `3.cmp(&5)` 는 `Less` 다.

### (7) 원본을 지키며 여러 번 정렬하기 — 배열 복사

**언제 쓰나** — 같은 입력으로 여러 알고리즘을 비교할 때.

```text
let original = [64, 34, 25, 12, 22, 11, 90];   // [i32; 7]
let mut a1 = original;   ── 원소 7개가 통째로 복사됨
bubble_sort(&mut a1);    ── a1 만 바뀜, original 은 그대로
let mut a2 = original;   ── 다시 정렬 전 값으로 새 복사
```

- `[i32; 7]` 같은 고정 길이 배열은 원소가 `Copy` 면 배열 자체도 `Copy` 다.
- 그래서 `let mut a1 = original;` 은 이동(move)이 아니라 복사이고, `original` 을 계속 쓸 수 있다.
- `&mut a1` 은 `&mut [i32; 7]` 이지만 `&mut [i32]` 를 받는 함수에 그대로 넘어간다(배열 참조가 슬라이스로 바뀐다).

> **`Copy`** — 대입할 때 이동 대신 비트 복사가 일어나는 타입의 성질.\
> 예: `i32` · `char` · `[i32; 7]` 은 `Copy` 다. `Vec<i32>` 는 아니다.

## 문법 — 형태와 규칙

```rust
use std::cmp::Ordering;

fn main() {
    let mut nums = [5, 3, 9, 1];
    nums.sort();                                // 오름차순, 안정
    nums.sort_unstable();                       // 오름차순, 불안정
    nums.sort_unstable_by(|a, b| b.cmp(a));     // 내림차순

    let mut people = vec![("kim", 30), ("lee", 25)];
    people.sort_by_key(|&(_, age)| age);        // 나이 기준
    people.sort_by(|a, b| a.0.cmp(b.0));        // 이름 기준 (커스텀 비교)

    let (left, right) = nums.split_at_mut(2);   // 겹치지 않는 두 &mut
    left.swap(0, 1);
    let _ = (right, Ordering::Less);
}
```

- 정렬 메서드는 모두 슬라이스 메서드이고 제자리(in-place)에서 고친다 — 새 컬렉션을 돌려주지 않는다.
- 그래서 받는 쪽이 `let mut` 이어야 한다.
- `sort` · `sort_unstable` 은 원소 타입이 `Ord` 여야 한다.
- `sort_by_key` 의 클로저는 원소의 참조를 받는다 — `|&(k, _)| k` 는 참조를 패턴으로 풀어 첫 값을 꺼낸다.
- `sort_by` 의 클로저는 `(&T, &T) -> Ordering` 이다.
- 직접 짠 정렬 함수는 `&mut [i32]` 를 받게 하면 배열과 `Vec` 모두에 쓸 수 있다.
- `arr.swap(i, j)` 는 두 칸을 바꾼다 — 범위를 벗어나면 패닉이다.

원본의 비교 표:

| 알고리즘 | 평균 | 최악 | 공간 | 안정 |
|---|---|---|---|---|
| 버블 정렬 | O(n²) | O(n²) | O(1) | O |
| 선택 정렬 | O(n²) | O(n²) | O(1) | X |
| 삽입 정렬 | O(n²) | O(n²) | O(1) | O |
| 퀵 정렬 | O(n log n) | O(n²) | O(log n) | X |
| 머지 정렬 | O(n log n) | O(n log n) | O(n) | O |

원본 주석이 덧붙이는 최선의 경우: 버블(조기 종료)과 삽입 정렬은 이미 정렬된 입력에서 O(n) 이다.

## 어디서 틀리나

### 1. `sort` 와 `sort_unstable` 의 차이를 「속도」로만 기억한다

원본 팁: `sort()` 는 같은 값의 상대 순서를 보존하고, `sort_unstable()` 은 그렇지 않다.
정수만 정렬할 때는 같은 값을 구별할 방법이 없으니 둘의 결과가 똑같다.
차이는 `sort_by_key` 처럼 「키는 같지만 원소는 다른」 경우에 드러난다.
여러 기준으로 차례로 정렬하는 경우(먼저 이름, 다음 나이)처럼 앞선 순서를 지켜야 하면 안정 판을 써야 한다.

### 2. 안정성은 비교 연산자 한 글자에 걸려 있다

머지 정렬 병합에서 `left[i] <= right[j]` 를 `<` 로 바꾸면, 같은 값일 때 오른쪽 것이 먼저 들어가 안정성이 깨진다.
삽입 정렬의 `arr[j - 1] > key`, 버블 정렬의 `arr[j] > arr[j + 1]` 을 `>=` 로 바꿔도 같은 값을 건너뛰게 되어 안정성이 깨진다.

### 3. 선택 정렬은 「차례대로 앞에 놓으니까」 안정이라고 착각한다

`swap(i, min_idx)` 가 `i` 자리에 있던 원소를 멀리 보낸다.
`[2a, 2b, 1]` 에서 첫 교환이 `2a` 를 맨 뒤로 보내 `[1, 2b, 2a]` 가 된다.

### 4. Lomuto 퀵 정렬은 이미 정렬된 입력에 약하다

피벗이 늘 마지막 원소라 정렬된 입력에서는 피벗이 최댓값이 되고, 나뉜 한쪽이 비어 버린다.
이때 시간은 O(n²) 이고, 재귀 깊이도 n 에 가까워진다.
`<= pivot` 비교라 모든 값이 같은 입력도 전부 한쪽으로 몰린다.

**원본의 주장 → 왜 의심스러운가** — 원본 표는 퀵 정렬의 공간을 O(log n) 으로 적는다.
이것은 평균 재귀 깊이다.
이 구현은 작은 쪽을 먼저 재귀하는 식의 처리를 하지 않으므로, 최악에는 재귀 스택이 O(n) 까지 깊어진다 (원본에 근거 없음 — 추론).

### 5. `split_at_mut` 이 「유일한 방법」이라고 여긴다

원본 주석은 `split_at_mut` 이 「대여 검사 통과」를 위한 것이라고 한다.
두 `&mut` 조각을 **동시에** 쥐려면 맞는 말이다.
**원본의 주장 → 왜 의심스러운가** — 이 코드처럼 왼쪽 재귀가 끝난 뒤 오른쪽을 재귀하는 경우라면 `quick_sort(&mut arr[..p]); quick_sort(&mut arr[p + 1..]);` 처럼 차례로 빌려도 두 빌림의 기간이 겹치지 않아 컴파일될 것으로 보인다 (원본에 근거 없음 — 추론, 확인 필요).

### 6. 머지 정렬의 `to_vec()` 이 공짜라고 여긴다

재귀 호출마다 두 절반을 새 `Vec` 으로 복사한다.
그래서 공간이 O(n) 이고, 할당 비용도 든다.

### 7. 내림차순을 위해 정렬 후 뒤집기만 떠올린다

원본은 비교 클로저의 인자 순서를 뒤집는다 — `|a, b| b.cmp(a)`.
`a.cmp(b)` 가 오름차순이고, `b.cmp(a)` 는 모든 비교 결과를 반대로 만들어 내림차순이 된다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| `sort` 계열은 안정 정렬이다 | 표준 라이브러리 API 의 약속(문서에 적힌 동작) |
| `sort_unstable` 계열은 같은 값의 순서를 보존하지 않을 수 있다 | API 의 약속 — 「보존을 약속하지 않음」이지 「반드시 뒤집음」이 아니다 |
| `sort` 가 TimSort 기반이다 | 원본 팁의 서술 · 표준 라이브러리 구현 세부사항 — Rust 버전에 따라 바뀔 수 있다 (확인 필요) |
| `sort_unstable` 이 pdqsort 기반이다 | 원본 팁의 서술 · 구현 세부사항 (확인 필요) |
| `sort_unstable` 은 추가 메모리를 쓰지 않는다 | 원본 팁의 서술 — 문서에 제자리 정렬로 적힌 것으로 보인다 (확인 필요) |
| `sort_unstable` 이 대부분 더 빠르다 | 원본 팁의 경험적 서술 — 보장이 아니고 데이터에 따라 다르다 |
| 표의 O(…) 복잡도 | 알고리즘의 성질 — 이 문서의 직접 구현에 대한 분석이다 |
| `[i32; 7]` 이 `Copy` 다 | 언어 규칙(원소가 `Copy` 인 배열은 `Copy`) |
| `split_at_mut` 의 두 조각은 겹치지 않는다 | 표준 라이브러리의 약속 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 일반 코드에서 숫자 정렬 | `sort_unstable()` | 직접 짠 버블 · 선택 정렬 |
| 같은 키의 기존 순서를 지켜야 함 | `sort` · `sort_by_key` · `sort_by` | `sort_unstable` 계열 |
| 구조체의 특정 필드 기준 | `sort_by_key(\|x\| x.필드)` | 필드를 따로 뽑아 정렬 후 맞추기 |
| 내림차순 · 복합 비교 | `sort_by` / `sort_unstable_by` + `b.cmp(a)` | 정렬 후 수동 재배열 |
| 거의 정렬된 작은 데이터를 직접 구현 | 삽입 정렬 | 피벗이 마지막인 Lomuto 퀵 정렬 |
| 최악에도 O(n log n) + 안정 | 머지 정렬 | 퀵 정렬 |
| 메모리를 더 쓰기 어려움 | 제자리 정렬(퀵 · 삽입 · `sort_unstable`) | `to_vec` 을 쓰는 머지 정렬 |

## 핵심 문장

1. **버블 · 선택 · 삽입은 O(n²), 퀵 · 머지는 평균 O(n log n)** — 퀵은 최악 O(n²), 머지는 최악에도 O(n log n) 이지만 O(n) 메모리를 쓴다.
2. **안정성은 「같은 값을 건너뛰느냐」로 갈린다** — 이웃끼리 `>` 로만 움직이거나 병합에서 `<=` 로 왼쪽을 먼저 쓰면 안정, 멀리 `swap` 하면 불안정.
3. **Lomuto 퀵 정렬은 피벗을 제자리에 놓고 양쪽을 재귀한다** — `split_at_mut` 으로 겹치지 않는 두 `&mut` 를 얻는다.
4. **실제로는 표준 정렬을 쓴다** — 순서 보존이 필요하면 `sort` 계열, 아니면 `sort_unstable` 계열, 기준은 `_by_key` · `_by` 로 바꾼다.
5. **`Copy` 배열은 대입하면 복사된다** — 원본 하나로 여러 정렬을 따로 시험할 수 있다.

## 용어 풀이

- **정렬** — 원소들을 비교 기준에 따라 차례대로 늘어놓는 일.
- **버블 정렬** — 인접한 두 원소를 비교해 바꾸기를 반복하는 정렬.
- **선택 정렬** — 남은 범위의 최솟값을 찾아 앞자리와 바꾸는 정렬.
- **삽입 정렬** — 원소를 하나씩 집어 정렬된 앞부분의 알맞은 자리에 끼우는 정렬.
- **퀵 정렬** — 피벗으로 나눈 뒤 양쪽을 재귀 정렬하는 정렬.
- **머지 정렬** — 반으로 나눠 각각 정렬한 뒤 병합하는 정렬.
- **Lomuto 파티션** — 마지막 원소를 피벗으로 삼아 한 번 훑으며 나누는 분할 방식.
- **피벗** — 퀵 정렬에서 나누는 기준 원소.
- **패스** — 배열을 한 번 훑는 일.
- **안정 정렬** — 같은 키를 가진 원소들의 원래 순서를 지키는 정렬.
- **제자리(in-place) 정렬** — 입력 공간 안에서 원소를 옮겨 정렬하는 방식.
- **슬라이스** — 연속된 원소 구간에 대한 참조(`&[T]` · `&mut [T]`).
- **`split_at_mut`** — 가변 슬라이스를 겹치지 않는 두 가변 슬라이스로 나누는 메서드.
- **`min_by_key`** — 키 함수 결과가 가장 작은 원소를 돌려주는 반복자 메서드.
- **`Ordering`** — 비교 결과(`Less` · `Equal` · `Greater`).
- **`Copy`** — 대입 시 복사되는 타입의 성질.
- **`sort` / `sort_unstable`** — 표준 라이브러리의 안정 / 불안정 정렬.
- **`sort_by_key` / `sort_by`** — 키 함수 / 비교 함수로 기준을 바꾸는 정렬.
- **TimSort · pdqsort** — 원본 팁이 `sort` · `sort_unstable` 의 기반으로 든 정렬 알고리즘 이름.

## 더 들어가면

- 최근 Rust 표준 라이브러리는 `sort` 와 `sort_unstable` 의 내부 알고리즘을 TimSort · pdqsort 에서 다른 것(driftsort · ipnsort 라는 이름)으로 바꾼 것으로 알려져 있다 — 바뀌어도 안정성 약속은 그대로다 (확인 필요).
- `f64` 는 `NaN` 때문에 `Ord` 가 아니어서 `sort()` 를 바로 쓸 수 없다 — `sort_by(|a, b| a.total_cmp(b))` 같은 방법을 쓴다 (확인 필요).
- 내림차순은 `sort_by_key(|&x| std::cmp::Reverse(x))` 로도 쓸 수 있다 (확인 필요).
- 키를 계산하는 비용이 크면 `sort_by_cached_key` 가 키를 한 번만 계산한다 (확인 필요).
- `Iterator::min_by_key` 는 최솟값이 여럿이면 첫 원소를 돌려준다고 문서에 적혀 있다 (확인 필요).
- 퀵 정렬 피벗을 무작위나 「세 값의 중앙값」으로 고르면 정렬된 입력에서의 최악을 피하기 쉽다 (확인 필요).
- 퀵 정렬 재귀를 작은 쪽만 하고 큰 쪽은 반복문으로 돌리면 스택 깊이를 O(log n) 으로 묶을 수 있다 (확인 필요).
