## 한눈에 — 쉽게 말하면

**Strategy 패턴은 「계산대에 꽂는 할인 쿠폰」이다.**
계산대는 그대로 두고, 쿠폰만 바꿔 꽂으면 계산 결과가 달라진다.
계산대는 쿠폰이 「정가 그대로」인지 「10% 할인」인지 몰라도 된다.
쿠폰의 규격(가격을 받아 가격을 돌려준다)만 맞으면 어떤 쿠폰이든 꽂힌다.
Rust 의 전략 패턴도 똑같은 구조다.

> **전략(strategy)** — 바꿔 끼울 수 있는 알고리즘 한 조각.\
> 예: `member_discount(0.1)` 이 만든 「10% 할인」 클로저.

> **컨텍스트(context)** — 전략을 들고 있다가 그것에 일을 맡기는 쪽.\
> 예: `PricingEngine`, `Sorter`.

| 비유 | 실체 |
|---|---|
| 계산대 | 컨텍스트 — `PricingEngine` · `Sorter` |
| 쿠폰 | 전략 — 클로저 · `BubbleSort` 같은 구조체 |
| 쿠폰 규격 | `Fn(f64) -> f64` · `trait SortStrategy` · `trait Validator` |
| 쿠폰 꽂는 슬롯 | `strategy: Box<dyn …>` 필드 |
| 쿠폰 갈아 끼우기 | `set_strategy(...)` |

```text
  컨텍스트 (PricingEngine)
  ┌──────────────────────┐
  │ strategy: [ 슬롯 ] ──┼──▶ 지금 꽂힌 전략 (클로저)
  └──────────────────────┘
  calculate(100000) ──▶ 전략(100000) ──▶ 90000
  set_strategy(새 전략) ──▶ 슬롯의 내용만 바뀐다
```

## 이 주제가 답하려는 질문

1. 알고리즘을 바꿀 때 그 알고리즘을 쓰는 쪽 코드를 고치지 않으려면 어떻게 하나?
2. Rust 에서 「바꿔 끼울 수 있는 알고리즘」을 무엇으로 표현하나 — 클로저인가, 트레이트 객체인가, 제네릭인가?
3. 실행 중에 전략을 바꾸는 자유와 성능 사이에서 무엇을 고르나?

## 동작 방식

### (1) 클로저 전략 — `Box<dyn Fn(f64) -> f64>` 를 필드로

**언제 쓰나** — 전략이 「값 하나를 받아 값 하나를 돌려주는」 단순한 계산일 때.
원본 팁의 말로는 「단순한 전략은 클로저로」.

> **클로저** — 이름 없이 그 자리에서 만드는 함수. 주변 변수를 붙잡아 둘 수 있다.\
> 예: `|price| price * 0.9`.

```text
PricingEngine::new(regular_price())
   │  regular_price() 가 |price| price 클로저를 돌려준다
   ▼
Box::new(strategy)  ──▶  strategy 필드에 저장 (Box<dyn Fn(f64) -> f64>)
   │
engine.calculate(100_000.0)
   ▼
(self.strategy)(price)  ──▶  클로저 실행 ──▶ 100000.0
   │
engine.set_strategy(member_discount(0.1))
   ▼
self.strategy = Box::new(새 클로저)  ──▶  옛 Box 는 버려진다(drop)
```

- `new` 는 `impl Fn(f64) -> f64 + 'static` 을 받는다 — 규격에 맞는 클로저라면 어떤 타입이든 받는다는 뜻이다.
- 클로저마다 타입이 제각각이라 필드에 그대로 담을 수 없다. 그래서 `Box::new` 로 힙에 올리고 `dyn Fn` 으로 타입을 지운다.
- `calculate` 는 `(self.strategy)(price)` 로 필드 안의 클로저를 부른다. 괄호가 「필드를 꺼낸 다음 호출」이라는 뜻을 만든다.
- `set_strategy` 는 필드를 바꾸므로 `&mut self` 를 받는다. 대입하면 이전 Box 는 버려진다.

> **트레이트 객체** — `dyn 트레이트` 꼴로, 구체 타입은 지우고 「이 트레이트를 구현한 무언가」로만 다루는 값. 보통 `Box` 나 참조 뒤에 둔다.\
> 예: `Box<dyn Fn(f64) -> f64>`, `Box<dyn SortStrategy>`.

### (2) 클로저 팩토리 — 전략을 만들어 주는 함수

**언제 쓰나** — 같은 모양의 전략을 숫자(할인율 · 할인액)만 바꿔 여러 개 만들고 싶을 때.

```text
member_discount(0.1)
   │  rate = 0.1 을 클로저 안으로 옮겨 담는다 (move)
   ▼
클로저 { rate: 0.1 }  ──  호출되면 price * (1.0 - rate)
   │  함수가 끝나 rate 매개변수는 사라져도
   ▼
클로저 안의 rate 사본은 남아 있다
```

- `regular_price()` 는 아무것도 붙잡지 않는 `|price| price` 를 돌려준다.
- `member_discount(rate)` 는 `move |price| price * (1.0 - rate)` 를 돌려준다 — `rate` 를 붙잡는다.
- `fixed_discount(amount)` 는 `move |price| (price - amount).max(0.0)` 를 돌려준다 — 결과가 0 아래로 내려가지 않는다.
- 셋 다 반환 타입이 `impl Fn(f64) -> f64` 다. 「`Fn` 규격에 맞는 어떤 한 타입」을 돌려준다는 뜻이다.
- `move` 가 없으면 클로저는 `rate` 를 빌려 쓰려 한다. 그런데 `rate` 는 함수가 끝나면 사라지므로 컴파일러가 막는다.

> **캡처** — 클로저가 바깥 변수를 붙잡아 두는 일. `move` 를 붙이면 빌리지 않고 값을 옮겨(복사해) 담는다.\
> 예: `move |price| price * (1.0 - rate)` 가 `rate` 를 담는다.

### (3) 트레이트 전략 — `Box<dyn SortStrategy>`

**언제 쓰나** — 전략이 메서드를 여럿 가지거나(`sort` 와 `name`), 알고리즘이 길고 복잡할 때.
원본 팁의 말로는 「복잡한 전략은 트레이트로」.

```text
trait SortStrategy { sort(&self, &mut Vec<i32>); name(&self) -> &str }
        ▲               ▲                ▲
   BubbleSort      InsertionSort      QuickSort      (필드 없는 구조체)

Sorter { strategy: Box<dyn SortStrategy> }
   │
sorter.sort(&mut data)
   ├─▶ self.strategy.name()  ──▶ "  [BubbleSort] 정렬 시작" 을 찍는다
   └─▶ self.strategy.sort(data) ──▶ 꽂힌 구조체의 sort 가 data 를 제자리에서 바꾼다
   │
sorter.set_strategy(Box::new(InsertionSort))  ──▶ 이후 호출은 삽입 정렬로
```

- `SortStrategy` 가 쿠폰 규격이다. 정렬하는 법(`sort`)과 이름(`name`)을 약속한다.
- `BubbleSort` · `InsertionSort` · `QuickSort` 는 필드가 없는 구조체다. 원본 주석은 이것을 zero-sized type 이라 부른다.
- `Sorter` 는 어느 구조체가 꽂혔는지 모른다. `name()` 을 찍고 `sort()` 에 일을 넘길 뿐이다.
- 세 알고리즘의 요지:
  - 버블 정렬 — 이웃한 두 칸을 비교해 큰 쪽을 뒤로 보낸다. 바깥 반복 `i` 마다 끝의 `i` 칸은 이미 정렬된 상태라 안쪽 반복은 `0..n - 1 - i` 까지만 돈다.
  - 삽입 정렬 — `i` 번째 값(`key`)을 앞쪽 정렬된 구간에서 제자리를 찾을 때까지 큰 값들을 한 칸씩 뒤로 민다.
  - 퀵 정렬(단순 구현) — 가운데 원소를 피벗으로 삼아 「작은 것 · 같은 것 · 큰 것」 세 `Vec` 으로 나누고, 작은 쪽과 큰 쪽을 재귀로 정렬한 뒤 `data` 를 비우고 차례로 이어 붙인다.
- `main` 은 원본 데이터를 매번 `clone()` 해서 정렬한다. 그래서 세 전략이 모두 같은 입력 `[64, 34, 25, 12, 22, 11, 90]` 을 받는다.

> **동적 디스패치** — 어떤 메서드를 부를지 실행 중에 정하는 방식. `dyn 트레이트` 를 통한 호출이 이렇다.\
> 예: `self.strategy.sort(data)` 는 꽂힌 구조체가 무엇인지에 따라 실행 중에 갈 곳이 정해진다.

### (4) 제네릭 전략 — `fn validate_input<V: Validator>`

**언제 쓰나** — 실행 중에 전략을 바꿀 필요는 없고 성능이 중요할 때.
원본 팁의 말로는 「성능이 중요하면 제네릭(정적 디스패치)」.

```text
validate_input(&length_check, "hi")
   │  V = LengthValidator 로 정해진다 (컴파일 때)
   ▼
validator.validate("hi")  ──▶  Err("길이 3~20 필요, 현재: 2")
   ▼
match → Err(e) 갈래 ──▶ "  'hi' -> 실패: …" 를 찍는다

validate_input(&pattern_check, "user@mail.com")
   │  V = PatternValidator 로 정해진다 (컴파일 때)
   ▼
"user@mail.com".contains("@") ──▶ Ok(()) ──▶ "  '…' -> 유효"
```

- `Validator` 는 `validate(&self, input: &str) -> Result<(), String>` 하나를 약속한다.
- `LengthValidator { min, max }` 는 `input.len()` 이 `min` 이상 `max` 이하면 `Ok(())`, 아니면 「길이 min~max 필요, 현재: len」 메시지로 `Err` 다.
- `PatternValidator { pattern }` 은 `input.contains(&self.pattern)` 이 참이면 `Ok(())`, 아니면 「'pattern' 패턴이 포함되어야 합니다」로 `Err` 다.
- `validate_input` 은 `Box` 도 `dyn` 도 쓰지 않는다. 호출하는 자리마다 `V` 가 구체 타입으로 정해진다.
- 원본 주석: 「호출마다 타입에 특화된 코드가 사용됨 (인라인 가능)」.
- 대신 「한 변수에 담긴 전략을 실행 중에 갈아 끼우기」는 이 모양으로 할 수 없다. `V` 는 컴파일 때 하나로 굳는다.

> **정적 디스패치** — 어떤 메서드를 부를지 컴파일 때 정하는 방식. 제네릭 매개변수를 통한 호출이 이렇다.\
> 예: `validate_input::<LengthValidator>` 안의 `validator.validate(...)`.

> **인라이닝** — 컴파일러가 함수 호출을 그 함수의 본문으로 바꿔 끼우는 최적화.\
> 예: `validator.validate(input)` 호출 자리에 `LengthValidator::validate` 본문이 들어갈 수 있다.

### (5) 세 방식 나란히

```text
             전략을 담는 꼴              어느 코드를 부를지 정하는 때   실행 중 교체
클로저      Box<dyn Fn(f64) -> f64>      실행 중 (동적)                  된다 (set_strategy)
트레이트    Box<dyn SortStrategy>        실행 중 (동적)                  된다 (set_strategy)
제네릭      V: Validator (타입 매개변수) 컴파일 때 (정적)                한 변수 안에서는 안 된다
```

원본 `main` 의 끝 세 줄이 이것을 요약한다.
「클로저 전략: 간단한 변환/계산에 적합. 가장 가벼움」.
「트레이트 객체: 복잡한 알고리즘, 상태 보유. 동적 디스패치」.
「제네릭: 정적 디스패치, 인라이닝 가능. 최고 성능」.
이 요약의 첫 줄과 셋째 줄에는 단서가 붙는다 — 「어디서 틀리나」 8 · 9 를 본다.

## 문법 — 형태와 규칙

```rust
trait Shape { fn area(&self) -> f64; }          // 전략 규격
struct Square(f64);
impl Shape for Square { fn area(&self) -> f64 { self.0 * self.0 } }

struct Holder { f: Box<dyn Fn(f64) -> f64> }    // 클로저 전략 보관
impl Holder {
    fn run(&self, x: f64) -> f64 { (self.f)(x) } // 필드 호출은 괄호로
}

fn scale(k: f64) -> impl Fn(f64) -> f64 { move |x| x * k } // 클로저 팩토리

fn total<S: Shape>(s: &S) -> f64 { s.area() }    // 제네릭 = 정적
fn total_dyn(s: &Box<dyn Shape>) -> f64 { s.area() } // dyn = 동적

enum Op { Double, Neg }                          // enum 디스패치
fn apply(op: &Op, x: f64) -> f64 { match op { Op::Double => x * 2.0, Op::Neg => -x } }
```

- 클로저를 필드에 담을 때는 `Box<dyn Fn(입력) -> 출력>` 꼴로 쓴다.
- 클로저를 받는 매개변수는 `impl Fn(f64) -> f64 + 'static` 처럼 쓸 수 있다. `'static` 은 「짧게 사는 지역 변수를 빌리고 있지 않다」는 조건이다 — `Box<dyn Fn …>` 필드가 기본으로 `'static` 을 요구하기 때문에 붙인다.
- 필드에 담긴 클로저는 `(self.필드)(인자)` 로 부른다. `self.필드(인자)` 는 「`필드` 라는 이름의 메서드」를 찾는다.
- 붙잡은 값을 클로저와 함께 함수 밖으로 내보내려면 `move` 를 붙인다.
- 반환 타입 `impl Fn(…)` 은 「한 가지 구체 타입」을 숨길 뿐이다. 분기마다 다른 클로저를 돌려주려면 `Box<dyn Fn(…)>` 를 반환해야 한다.
- 전략을 바꾸는 메서드는 `&mut self` 를 받는다.
- `Box<dyn 트레이트>` 는 실행 중 교체가 되고 여러 종류를 한 `Vec` 에 담을 수 있다. `<T: 트레이트>` 는 컴파일 때 타입이 정해진다.
- 전략 종류가 정해져 있고 더 늘지 않는다면 `enum` 과 `match` 로도 표현할 수 있다(enum 디스패치). 원본 팁은 이쪽이 트레이트 객체보다 빠른 경우가 많다고 한다.

> **enum 디스패치** — 전략 종류를 `enum` 의 변형으로 나열하고 `match` 로 갈라 부르는 방식.\
> 예: 위의 `apply(&Op::Double, 3.0)`.

## 어디서 틀리나

### 1. 필드의 클로저를 `self.strategy(price)` 로 부른다
Rust 는 이것을 `strategy` 라는 메서드 호출로 읽는다.
그런 메서드가 없으니 컴파일 오류다.
`(self.strategy)(price)` 처럼 필드를 괄호로 묶어야 「필드 값을 꺼내 호출」이 된다.

### 2. 클로저 팩토리에서 `move` 를 뺀다
`member_discount` 의 매개변수 `rate` 는 함수가 끝나면 사라진다.
`move` 없이는 클로저가 `rate` 를 빌리려 하고, 사라질 값을 빌린 클로저를 돌려줄 수 없어 컴파일러가 막는다.

### 3. `impl Fn` 반환 함수에서 분기마다 다른 클로저를 돌려준다
클로저는 하나하나가 서로 다른 이름 없는 타입이다.
`impl Fn` 은 그중 **한 타입**만 숨긴다.
`if` 의 두 갈래가 서로 다른 클로저를 돌려주면 타입이 맞지 않는다.
이럴 때는 `Box<dyn Fn(f64) -> f64>` 를 반환한다.

### 4. 지역 변수를 빌린 클로저를 `PricingEngine` 에 넣는다
`new` 와 `set_strategy` 는 `'static` 클로저만 받는다.
`main` 안 지역 변수를 빌려 쓰는 클로저는 이 조건을 못 채운다.
`move` 로 값을 옮겨 담으면 된다.

### 5. `LengthValidator` 는 글자 수가 아니라 바이트 수를 잰다
`input.len()` 은 UTF-8 바이트 수다.
한글 한 글자는 UTF-8 로 3바이트다.
그래서 「가나」(2글자)는 6바이트로 재어져 `min: 3` 을 통과한다.
글자 수로 재려면 `input.chars().count()` 를 쓴다.

### 6. 버블 정렬의 `n - 1 - i` 가 빈 `Vec` 에서 터질 것 같다
`usize` 는 0 아래로 빼면 오류(디버그 빌드에서 패닉)다.
하지만 `n == 0` 이면 바깥 반복 `0..0` 이 한 번도 돌지 않아 `n - 1 - i` 가 계산되지 않는다.
`n >= 1` 이면 `i` 는 최대 `n - 1` 이라 `n - 1 - i` 는 0 이상이다.

### 7. `QuickSort` 는 제자리 정렬이 아니다
원본 주석은 「퀵 정렬 (단순 구현)」이라 적는다.
나눌 때마다 `left` · `mid` · `right` 새 `Vec` 을 만들고 마지막에 `data` 에 다시 붓는다.
결과는 정렬되지만 메모리를 더 쓴다.

### 8. 원본의 「클로저 전략: 가장 가벼움」
**원본의 주장** — 클로저 전략이 셋 중 가장 가볍다.
**왜 의심스러운가** — 이 예제의 클로저 전략은 `Box<dyn Fn(f64) -> f64>` 에 담긴다.
즉 트레이트 객체와 같은 동적 디스패치이고, 값을 붙잡은 클로저(`member_discount`)는 `Box` 로 힙에 올라간다.
「작성하기 가볍다」는 맞을 수 있어도, 실행 비용이 트레이트 객체보다 가볍다고 볼 근거는 코드에 없다.

### 9. 원본의 「제네릭: 최고 성능」 · 「enum 디스패치가 빠른 경우가 많다」
**원본의 주장** — 제네릭이 최고 성능이고, enum 디스패치가 트레이트 객체보다 빠른 경우가 많다.
**왜 의심스러운가** — 인라이닝은 「가능」할 뿐 컴파일러가 반드시 하는 일이 아니다.
속도 차이는 코드와 상황마다 달라 측정 없이 단정할 수 없다.
「흔히 그렇다」 정도로 받아들인다.

### 10. 원본의 팁 전부 — 고르는 기준
원본 팁은 네 가지 기준을 준다.
단순한 전략은 클로저, 복잡한 전략은 트레이트.
성능이 중요하면 제네릭(정적 디스패치), 런타임 교체가 필요하면 `Box<dyn Trait>`(동적 디스패치).
그리고 enum 디스패치가 트레이트 객체보다 빠른 경우가 많다.
아래 「언제 쓰고 언제 안 쓰나」 표가 이것을 상황별로 펼친다.

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 값 하나 → 값 하나인 단순 계산을 바꿔 끼우기 | 클로저 + `Box<dyn Fn>` | 메서드 하나뿐인 트레이트와 구조체 여러 개 |
| 이름 · 설정 등 메서드가 여럿인 복잡한 알고리즘 | 트레이트 + 구조체 | 클로저 하나에 모든 것을 우겨 넣기 |
| 실행 중에 전략을 갈아 끼워야 한다 | `Box<dyn 트레이트>` 필드 + `set_strategy` | 제네릭 매개변수(한 변수 안에서 못 바꾼다) |
| 전략이 컴파일 때 정해지고 성능이 중요하다 | 제네릭 `<V: 트레이트>` | 굳이 `Box<dyn …>` |
| 전략 종류가 정해져 있고 더 늘지 않는다 | `enum` + `match` | 바깥 사용자가 전략을 새로 추가해야 하는 경우의 enum |
| 서로 다른 전략 여러 개를 한 목록에 담는다 | `Vec<Box<dyn 트레이트>>` | `Vec<V>`(한 타입만 담긴다) |

## 핵심 문장

1. **전략 패턴은 「쓰는 쪽(컨텍스트)」과 「바꿔 끼우는 알고리즘(전략)」을 떼어 놓는다** — 컨텍스트는 규격만 알고 전략은 갈아 끼운다.
2. **Rust 에서는 전략을 클로저, 트레이트 객체, 제네릭 세 가지로 담는다** — 단순하면 클로저, 복잡하면 트레이트.
3. **`Box<dyn …>` 는 실행 중 교체를 주고, 제네릭은 컴파일 때 타입을 굳힌다** — 교체가 필요하면 동적, 성능이 먼저면 정적.
4. **필드 클로저는 `(self.f)(x)` 로 부르고, 함수 밖으로 내보내는 클로저는 `move` 로 값을 담는다.**
5. **성능 주장(「가장 가벼움」 · 「최고 성능」 · 「enum 이 빠르다」)은 경향이지 보장이 아니다.**

## 용어 풀이

- **Strategy(전략) 패턴** — 알고리즘을 따로 떼어 내 바꿔 끼울 수 있게 하는 행위 패턴.
- **행위 패턴** — 객체들이 일을 나누고 주고받는 방식을 다루는 설계 패턴 묶음.
- **전략** — 바꿔 끼울 수 있는 알고리즘 한 조각.
- **컨텍스트** — 전략을 들고 있다가 일을 맡기는 쪽.
- **다형성** — 같은 호출이 대상의 실제 타입에 따라 다르게 동작하는 성질.
- **클로저** — 그 자리에서 만드는 이름 없는 함수로, 주변 변수를 붙잡을 수 있다.
- **캡처** — 클로저가 바깥 변수를 붙잡아 두는 일.
- **`move`** — 클로저가 바깥 값을 빌리지 않고 옮겨(복사해) 담게 하는 키워드.
- **클로저 팩토리** — 클로저를 만들어 돌려주는 함수.
- **`Fn(f64) -> f64`** — 「`f64` 를 받아 `f64` 를 돌려주고 여러 번 부를 수 있는 것」이라는 트레이트.
- **`impl 트레이트`** — 「이 트레이트를 구현한 어떤 한 타입」을 이름 없이 쓰는 표기.
- **`'static`** — 짧게 사는 값을 빌리고 있지 않아 프로그램 끝까지 살아도 되는 성질.
- **트레이트** — 타입이 구현해야 할 메서드 묶음(규격).
- **트레이트 객체** — `dyn 트레이트` 꼴로 구체 타입을 지운 값.
- **`Box`** — 값을 힙에 올리고 그 소유권을 쥐는 포인터.
- **동적 디스패치** — 부를 메서드를 실행 중에 정하는 방식.
- **정적 디스패치** — 부를 메서드를 컴파일 때 정하는 방식.
- **인라이닝** — 함수 호출을 함수 본문으로 바꿔 끼우는 최적화.
- **zero-sized type** — 크기가 0 인 타입. 필드 없는 구조체가 그 예다.
- **enum 디스패치** — 전략 종류를 `enum` 변형으로 나열하고 `match` 로 갈라 부르는 방식.
- **`Result<(), String>`** — 성공이면 `Ok(())`, 실패면 `Err(메시지)` 인 값.
- **피벗** — 퀵 정렬에서 「이보다 작은 것 / 큰 것」을 가르는 기준 값.

## 더 들어가면

- 아무것도 붙잡지 않는 전략만 쓴다면 `Box<dyn Fn>` 대신 함수 포인터 `fn(f64) -> f64` 를 필드로 둘 수 있다 — 힙 할당이 필요 없다 (확인 필요).
- 크기 0 인 값을 `Box::new` 로 감싸면 실제 힙 할당이 일어나지 않는다고 알려져 있다 (확인 필요).
- 소유할 필요가 없으면 `Box<dyn 트레이트>` 대신 `&dyn 트레이트` 로 빌려 써도 동적 디스패치가 된다.
- 전략을 다른 스레드로 넘기려면 `Box<dyn Fn(f64) -> f64 + Send>` 처럼 `Send` 를 더 요구해야 한다 (확인 필요).
- 실제 정렬에는 표준 라이브러리의 `sort` · `sort_unstable` 을 쓰는 편이 낫다 — 예제의 세 정렬은 패턴을 보이기 위한 것이다.
- enum 디스패치를 매크로로 자동 생성해 주는 외부 크레이트가 있다고 알려져 있다 (확인 필요).
