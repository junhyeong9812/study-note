## 한눈에 — 쉽게 말하면

**CPython 의 메모리 관리는 「도서관 대출 카드」다.**
책마다 지금 그 책을 빌려 간 사람 수를 적는 카드가 붙어 있다.
누가 빌려 가면 숫자가 오르고, 반납하면 내려간다.
숫자가 0 이 되는 순간 사서가 그 책을 바로 치운다.
그런데 두 책이 서로의 책갈피에 끼워진 채 아무도 들고 있지 않으면, 두 카드는 각각 1 에 머물러 영영 0 이 되지 않는다.
그래서 순찰원이 가끔 돌며 「바깥 누구와도 이어지지 않은 책 무리」를 찾아 치운다.
열람석에서 슬쩍 보기만 하는 사람은 카드에 적히지 않는다.
Python 객체도 똑같은 구조다.

| 비유 | 실체 |
|---|---|
| 책 | 객체 |
| 대출 카드의 숫자 | 참조 카운트 |
| 빌려 간 사람 | 강한 참조(이름 · 리스트 칸 · 속성) |
| 숫자 0 → 바로 치움 | 참조 카운팅에 의한 즉시 해제 |
| 서로의 책갈피에 끼워진 두 책 | 순환 참조 |
| 순찰원 | 순환 수집기(`gc`) |
| 보기만 하는 사람 | 약한 참조(`weakref`) |

```text
 이름 · 칸 · 속성 ──(강한 참조)──▶ 객체 [refcount n]
                                     n == 0 → 그 자리에서 해제

 A ⇄ B (서로만 가리킴)  → n 이 0 에 닿지 않음 → gc 가 찾아서 해제

 약한 참조 ┄┄┄┄┄┄┄┄┄┄┄▶ 객체        (n 에 세지 않음)
```

## 이 주제가 답하려는 질문

1. 객체는 언제 메모리에서 사라지나?
2. 참조 카운팅이 놓치는 경우는 무엇이고, 누가 그 빈틈을 메우나?
3. 객체를 가리키되 살려 두지는 않으려면 어떻게 하나?
4. 파일 닫기 같은 정리 작업은 어디에 맡겨야 안전한가?

## 동작 방식

### (1) 참조 카운팅 — 카운트가 오르내린다

**언제 쓰나** — 따로 켜는 기능이 아니라 CPython 에서 늘 일어난다.
객체가 왜 아직 살아 있는지 셀 때 이 계산을 떠올린다.

```text
코드                     실제 참조 수     sys.getrefcount(a) 로 보면
a = [1, 2, 3]            1 (a)            2
b = a                    2 (a, b)         3
c = [a, a, a]            5 (a, b, 칸×3)   6
del b                    4                5
del c                    1                2   ← 리스트 c 가 사라지며 칸 3개도 사라짐
```

- `b = a` 는 리스트를 복사하지 않고, 같은 리스트를 가리키는 이름을 하나 더 만든다.
- `c = [a, a, a]` 는 리스트 c 의 칸 셋이 각각 같은 리스트를 가리키므로 카운트가 3 오른다.
- `del b` 는 리스트를 지우지 않고 이름 `b` 만 지운다 — 그래서 카운트가 1 내려간다.
- `del c` 로 리스트 c 자체의 카운트가 0 이 되어 해제되고, 그 칸들이 들고 있던 참조 3개도 함께 사라진다.
- `sys.getrefcount(a)` 는 `a` 를 인자로 받는 순간 함수 쪽에 참조가 하나 더 생기므로 늘 실제보다 1 크게 보인다.
- 그래서 원본 코드는 곳곳에서 `sys.getrefcount(x) - 1` 로 그 인자분을 뺀다.

> **참조 카운트** — 한 객체를 가리키는 강한 참조의 개수.\
> 예: `b = a` 를 하면 리스트의 참조 카운트가 1 오른다.

### (2) 카운트 0 → 즉시 해제와 `__del__`

**언제 쓰나** — 객체가 언제 정리되는지 눈으로 보고 싶을 때 `__del__` 에 출력을 넣어 추적한다.

```text
t = Tracked("obj1")   → __init__ → "생성: obj1"
del t                 → 마지막 강한 참조가 사라짐 → refcount 0
                      → 그 자리에서 __del__ → "해제: obj1"
print("해제 완료")     → 해제 줄 다음에 찍힌다
```

- `t` 가 유일한 참조였으므로 `del t` 로 카운트가 0 이 된다.
- CPython 은 카운트가 0 이 되는 순간 객체를 해제하고, 해제 직전에 `__del__` 을 부른다.
- 이 경로는 순환 수집기(`gc`)를 거치지 않는다.
- 그래서 「해제: obj1」 이 「해제 완료」 보다 먼저 찍힌다.

> **finalizer(`__del__`)** — 객체가 해제되기 직전에 불리는 메서드.\
> 예: `def __del__(self): print("해제")`.

### (3) 순환 참조 — 카운트가 0 에 닿지 않는다

**언제 쓰나** — 두 객체가 서로를 속성으로 들고 있는 구조(양방향 링크, 부모↔자식)를 만들 때 이 문제가 생긴다.

```text
a ──▶ Node A ──ref──▶ Node B ◀── b
        ▲                 │
        └──────ref────────┘
A 의 참조: a, B.ref → 2        B 의 참조: b, A.ref → 2

del a, b
        Node A ⇄ Node B        각자 1 — 0 이 아니다
        (바깥 어떤 이름에서도 닿을 수 없다)
```

- `a.ref = b`, `b.ref = a` 로 서로를 가리키게 하면 두 객체의 카운트는 각각 2 다(이름 하나 + 상대의 속성 하나).
- `del a, b` 는 이름 둘을 지워 카운트를 1씩 내릴 뿐이다.
- 남은 1 은 상대 객체의 `ref` 속성이 들고 있으므로 0 에 닿지 않는다.
- 이 객체들은 프로그램 어디에서도 닿을 수 없지만 참조 카운팅만으로는 해제되지 않는다.
- 이 때문에 `del a, b` 직후에는 `__del__` 이 불리지 않는다.

> **순환 참조** — 객체들이 서로를 가리켜 고리를 이룬 상태.\
> 예: `a.ref = b; b.ref = a`.

> **도달 불가능** — 프로그램의 어떤 이름 · 변수에서 출발해도 따라갈 수 없는 상태.\
> 예: `del a, b` 뒤의 A ⇄ B 고리.

### (4) 순환 수집기 `gc` — 고리를 찾아 해제한다

**언제 쓰나** — 순환 참조가 쌓이는지 확인하거나, 짧은 구간에서 자동 수집을 멈추고 싶을 때 `gc` 모듈을 쓴다.

```text
gc.collect()
  → 도달 불가능한 순환 무리를 찾는다 (A ⇄ B)
  → 각 객체의 __del__ 을 부르고 해제한다 → "[GC] Node(A) 해제됨", "[GC] Node(B) 해제됨"
  → 수집한 객체 수를 돌려준다 → 2

gc.disable()   → 자동 순환 수집이 멈춘다 (gc.isenabled() → False)
  X ⇄ Y 를 만들고 del x, y → 아무도 치우지 않는다
gc.enable(); gc.collect()  → 그때 X, Y 가 해제된다 → 2
```

- CPython 은 참조 카운팅과 세대별 GC 를 함께 쓴다.
- 참조 카운팅이 대부분의 객체를 즉시 치우고, `gc` 는 참조 카운팅이 놓친 순환 참조를 주기적으로 수집한다.
- `gc.collect()` 는 수동으로 수집을 한 번 돌리고, 수집한 객체 수를 정수로 돌려준다.
- `gc.isenabled()` 는 자동 수집이 켜져 있는지 `True`/`False` 로 알려 준다.
- `gc.get_threshold()` 는 세대별(0세대, 1세대, 2세대) 수집 임계값을 튜플로 돌려준다 — 원본 예제의 출력에는 `(700, 10, 10)` 이 찍혀 있다.
- `gc.get_count()` 는 세대별로 지금 쌓인 카운트를 튜플로 돌려준다.
- `gc.disable()` 은 성능이 중요한 구간에서 자동 순환 수집을 잠시 멈출 때 쓴다.
- `gc.disable()` 이 멈추는 것은 순환 수집기뿐이다 — 참조 카운팅은 별개의 장치라 꺼지지 않고, 순환이 없는 객체는 여전히 카운트 0 순간에 해제된다.
- 끈 동안 만든 순환 쓰레기는 남아 있다가, 다시 켜서 수집이 돌 때 치워진다.

> **가비지 컬렉터(GC)** — 더 쓰이지 않는 객체를 찾아 메모리를 돌려주는 장치. CPython 의 `gc` 모듈은 순환 참조를 맡는다.\
> 예: `gc.collect()`.

> **세대별 GC** — 객체를 나이(살아남은 수집 횟수)별 묶음으로 나눠, 젊은 묶음을 더 자주 검사하는 방식.\
> 예: `gc.get_threshold()` 가 세 세대의 임계값을 돌려준다.

### (5) `weakref` — 세지 않는 참조

**언제 쓰나** — 객체를 가리키고는 싶지만, 그 참조 때문에 객체가 살아남지는 않게 하고 싶을 때 쓴다.

```text
obj = Cache("data")          refcount 1
strong_ref = obj             refcount 2
weak_ref = weakref.ref(obj)  refcount 2   ← 오르지 않는다
weak_ref()                   → Cache(data)

del obj                      refcount 1  → strong_ref 가 붙잡고 있다
weak_ref()                   → Cache(data)

del strong_ref               refcount 0  → 즉시 해제 → "Cache(data) 해제"
weak_ref()                   → None
```

- `weakref.ref(obj)` 는 약한 참조 객체를 만든다.
- 약한 참조는 참조 카운트에 세지 않으므로 객체의 생존을 막지 않는다.
- 약한 참조를 함수처럼 호출하면, 대상이 살아 있으면 그 객체를, 해제됐으면 `None` 을 돌려준다.
- `del obj` 뒤에도 `strong_ref` 라는 강한 참조가 남아 있어 객체는 살아 있다.
- `del strong_ref` 로 마지막 강한 참조가 사라지는 순간 객체가 해제되고(`__del__` 이 그 자리에서 불린다), 이후 `weak_ref()` 는 `None` 이다.
- 부모↔자식처럼 서로 가리켜야 하는 구조에서는 한쪽(보통 자식→부모)을 약한 참조로 두면 고리가 강한 참조만으로 닫히지 않는다.
- 그러면 바깥 이름이 루트를 놓는 순간 루트의 카운트가 0 이 되고, 루트가 해제되며 자식들의 카운트도 차례로 0 이 된다 — `gc` 없이 참조 카운팅만으로 치워진다.

> **강한 참조** — 참조 카운트를 올리는 보통의 참조.\
> 예: `strong_ref = obj`.

> **약한 참조** — 참조 카운트를 올리지 않는 참조. 대상이 해제되면 `None` 을 돌려준다.\
> 예: `weak_ref = weakref.ref(obj)`.

### (6) `WeakValueDictionary` — 쓰는 동안만 들고 있는 캐시

**언제 쓰나** — 「누군가 이 객체를 쓰는 동안에는 같은 객체를 돌려주고, 아무도 안 쓰면 캐시에서도 빼고 싶을」 때 쓴다.

```text
cache = WeakValueDictionary()
d1 = get_data("user:1") → 없음 → "캐시 미스" → Cache("user:1") 생성, cache 에 넣음
d2 = get_data("user:1") → 있음 → "캐시 히트" → 같은 객체를 돌려줌
len(cache) → 1

del d1, d2  → 강한 참조 0 → "Cache(user:1) 해제" → 캐시 항목도 저절로 사라짐
len(cache) → 0
```

- `WeakValueDictionary` 는 dict 처럼 쓰지만 값을 약한 참조로 들고 있다.
- 그래서 캐시 자신은 값 객체를 살려 두지 않는다.
- 바깥의 강한 참조(`d1`, `d2`)가 모두 사라지면 객체가 해제되고, 그 키의 항목도 캐시에서 자동으로 빠진다.
- 원본의 팁은 이것을 「weakref 로 캐시를 구현하면 메모리 누수를 방지할 수 있다」로 적는다 — 보통 dict 캐시는 한 번 넣은 객체를 영원히 붙잡지만, 이 캐시는 그러지 않는다.

> **`WeakValueDictionary`** — 값을 약한 참조로 담는 dict. 값이 해제되면 그 항목이 저절로 사라진다.\
> 예: `cache = weakref.WeakValueDictionary()`.

## 문법 — 형태와 규칙

```python
import sys, gc, weakref

class Box:
    pass

x = Box()
print(sys.getrefcount(x) - 1)  # 인자분 1 을 빼고 실제 참조 수를 본다
w = weakref.ref(x)             # 세지 않는 참조
x.me = x                       # 자기 자신을 가리키는 순환
del x                          # 이름만 지운다 — 고리는 남는다
print(w() is None)             # 아직 수집 전이면 False
print(gc.collect())            # 순환 수집 — 수집한 객체 수
print(w() is None)             # 수집됐으면 True
```

- `sys.getrefcount(obj)` — 참조 카운트를 돌려준다. 인자로 넘긴 몫 때문에 실제보다 1 크다.
- `del 이름` — 이름(또는 리스트 칸 · 속성)을 지워 참조를 하나 끊는다. 객체를 직접 지우는 명령이 아니다.
- `gc.collect()` — 순환 수집을 한 번 돌리고 수집한 객체 수를 정수로 돌려준다.
- `gc.disable()` / `gc.enable()` / `gc.isenabled()` — 자동 순환 수집을 끄고 · 켜고 · 상태를 본다.
- `gc.get_threshold()` / `gc.get_count()` — 세대별 임계값과 지금의 세대별 카운트를 세 칸짜리 튜플로 돌려준다.
- `weakref.ref(obj)` — 약한 참조를 만든다. 호출하면(`r()`) 객체 또는 `None`.
- `weakref.WeakValueDictionary()` — 값을 약하게 쥐는 dict. `in` · `[]` · `len()` 을 dict 처럼 쓴다.
- `__del__(self)` — 해제 직전에 불리는 메서드. 언제 불리는지는 참조가 끊기는 방식(즉시 · 순환 수집 때)에 달려 있다.

## 어디서 틀리나

### 1. `getrefcount` 의 숫자를 그대로 읽는다
`sys.getrefcount(a)` 는 인자로 받는 순간 참조가 하나 더 생겨 늘 1 크다.
생성 직후 2 가 나오는 것은 이름 `a` 하나 + 인자 하나다.
실제 참조 수가 궁금하면 원본처럼 `- 1` 로 보정한다.

### 2. `del` 을 「객체 삭제」로 읽는다
`del b` 는 이름 `b` 를 지운다.
같은 객체를 다른 이름 · 칸 · 속성이 들고 있으면 객체는 그대로 산다.
객체가 사라지는 것은 마지막 강한 참조가 끊길 때다.

### 3. 순환 참조도 `del` 로 풀린다고 믿는다
서로를 가리키는 객체는 이름을 다 지워도 카운트가 1 에 머문다.
이런 고리는 `gc` 가 수집할 때까지 메모리에 남는다.
`gc.disable()` 로 자동 수집을 꺼 두면 그 사이 생긴 고리는 계속 쌓인다.

### 4. 리소스 해제를 `__del__` 에 맡긴다
원본의 팁: 리소스 해제는 `__del__` 보다 컨텍스트 매니저(`with` 문)가 안전하다.
`__del__` 이 불리는 때는 객체가 어떻게 버려지느냐에 따라 달라진다 — 마지막 참조가 끊길 때 즉시일 수도, 순환에 걸려 `gc` 가 돌 때까지 미뤄질 수도 있다.
파일 · 연결 · 락처럼 「지금 반드시」 닫혀야 하는 것은 블록을 벗어나는 순간 정리가 일어나는 `with` 에 맡긴다.
**원본의 주장 → 왜 의심스러운가** — 원본의 핵심 정리는 「`__del__` 은 GC 타이밍에 따라 호출」이라고 적는다.
그러나 같은 원본의 2절에서는 `del t` 순간 `gc` 를 거치지 않고 `__del__` 이 불린다.
「GC 타이밍」은 순환에 걸린 객체에만 맞는 말이고, 정확한 결론은 「불리는 시점을 코드가 통제하기 어렵다」다.

### 5. 약한 참조에서 꺼낸 객체를 이름에 붙잡아 둔다
`o = weak_ref()` 처럼 꺼낸 결과를 이름에 담으면 그 이름은 강한 참조다.
그 이름이 살아 있는 동안 객체도 산다.
원본의 `print(f"... {weak_ref()}")` 는 꺼낸 값을 출력에만 쓰고 이름에 담지 않는다. (원본에 근거 없음 — 추론)

### 6. `WeakValueDictionary` 캐시를 「무엇이든 오래 기억하는 캐시」로 쓴다
이 캐시는 바깥에서 아무도 값을 들고 있지 않으면 곧 비워진다.
`d1`, `d2` 를 지우자 캐시 크기가 1 에서 0 이 된 것이 그 모습이다.
**원본의 주장 → 왜 의심스러운가** — 팁의 「메모리 누수를 방지할 수 있다」는 「캐시가 값을 붙잡지 않는다」는 뜻까지만 맞다.
캐시가 아닌 다른 곳의 누수까지 막아 주지는 않고, 자주 쓰지만 잠깐씩 놓이는 값은 매번 다시 만들어질 수 있다.

### 7. 6절의 `gc.collect()` 가 있어야 캐시가 빈다고 읽는다
`Cache` 객체는 순환에 걸려 있지 않다.
그래서 `del d1, d2` 로 마지막 강한 참조가 끊기는 순간 참조 카운팅이 해제한다.
원본 6절의 `gc.collect()` 는 CPython 에서는 결과를 바꾸지 않는 안전장치로 읽는 것이 맞다. (원본에 근거 없음 — 추론)

### 8. 세대 수와 임계값을 언어 사실로 외운다
원본은 「gc: 3세대 가비지 컬렉터」라고 적고, 예제 출력에는 `(700, 10, 10)` 이 찍힌다.
이것은 CPython 구현의 설정이다.
CPython 의 버전에 따라 세대 구조나 기본 임계값이 달라질 수 있다. (확인 필요)

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| 참조 카운트가 0 이 되는 순간 즉시 해제된다 | CPython 구현 — 언어 명세는 해제 시점을 약속하지 않는다 (확인 필요) |
| `sys.getrefcount` 가 돌려주는 숫자(2, 3, 6 …) | CPython 구현 — 참조 카운트라는 개념 자체가 CPython 의 방식이다 |
| 세대가 셋이고 임계값이 `(700, 10, 10)` | CPython 구현 · 버전 의존 (확인 필요) |
| `gc.collect()` 가 이 예제에서 2 를 돌려준다 | CPython 구현 — 무엇을 몇 개로 세는지는 버전에 따라 다를 수 있다 (확인 필요) |
| `__del__` 이 불리는 시점 | 언어는 시점을 보장하지 않는다 — CPython 에서는 즉시 또는 순환 수집 때 |
| `weakref.ref` 가 대상을 살려 두지 않고, 대상이 해제되면 `None` 을 돌려준다 | 표준 라이브러리 `weakref` 의 동작 |
| `with` 블록을 벗어나면 정리가 일어난다 | 언어 보장(`with` 문의 의미) |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 파일 · 연결 · 락을 확실히 닫기 | `with` 문(컨텍스트 매니저) | `__del__` 에 정리 맡기기 |
| 부모↔자식이 서로 가리켜야 하는 구조 | 한쪽(자식→부모)을 `weakref` 로 | 양쪽 다 강한 참조로 두고 `del` 에 기대기 |
| 쓰는 사람이 있는 동안만 같은 객체를 돌려주는 캐시 | `WeakValueDictionary` | 값을 영원히 붙잡는 보통 dict |
| 짧은 성능 민감 구간에서 수집 멈추기 | `gc.disable()` 후 끝에서 `gc.enable()` | 끈 채로 두기 |
| 객체가 왜 안 사라지는지 조사 | `sys.getrefcount(x) - 1`, `gc.collect()` 의 반환값 | 숫자를 언어 보장처럼 믿기 |

## 핵심 문장

1. **CPython 의 기본은 참조 카운팅이다** — 마지막 강한 참조가 끊기는 순간 객체가 해제된다.
2. **순환 참조는 카운트가 0 에 닿지 않는다** — 이 빈틈을 세대별 순환 수집기 `gc` 가 메운다.
3. **`del` 은 이름을 지울 뿐이다** — 객체의 생사는 남은 강한 참조 수가 정한다.
4. **약한 참조는 세지 않는다** — 그래서 캐시 · 역방향 링크에 쓰면 객체를 붙잡지 않는다.
5. **정리는 `with` 에** — `__del__` 이 불리는 시점은 통제하기 어렵다.

## 용어 풀이

- **참조** — 객체를 가리키는 이름 · 컨테이너의 칸 · 속성.
- **강한 참조** — 참조 카운트를 올리는 보통의 참조.
- **참조 카운트** — 한 객체를 가리키는 강한 참조의 개수.
- **참조 카운팅** — 참조 카운트를 오르내리며 0 이 되는 순간 해제하는 방식.
- **순환 참조** — 객체들이 서로를 가리켜 고리를 이룬 상태.
- **도달 불가능** — 프로그램의 어떤 이름에서 출발해도 닿을 수 없는 상태.
- **가비지 컬렉터(GC)** — 쓰이지 않는 객체를 찾아 메모리를 돌려주는 장치. CPython 의 `gc` 는 순환 참조를 맡는다.
- **세대별 GC** — 객체를 살아남은 횟수별 묶음으로 나눠 젊은 묶음을 자주 검사하는 방식.
- **임계값(threshold)** — 세대별 수집을 언제 돌릴지 정하는 기준 숫자.
- **finalizer(`__del__`)** — 객체가 해제되기 직전에 불리는 메서드.
- **약한 참조(`weakref`)** — 참조 카운트를 올리지 않고, 대상이 해제되면 `None` 을 돌려주는 참조.
- **`WeakValueDictionary`** — 값을 약한 참조로 담아, 값이 해제되면 항목이 저절로 사라지는 dict.
- **컨텍스트 매니저** — `with` 문에 쓰여 블록에 들어갈 때와 나갈 때 할 일을 정하는 객체.

## 더 들어가면

- `__del__` 이 정의된 객체가 순환에 걸리면 예전 CPython 에서는 수집되지 못하고 `gc.garbage` 에 남았지만, PEP 442 이후로는 수집된다고 알려져 있다. (확인 필요)
- `int` · `list` · `tuple` 같은 일부 내장 타입의 인스턴스는 `weakref.ref` 의 대상이 될 수 없고, `__slots__` 를 쓰는 클래스는 `__weakref__` 칸을 따로 넣어야 약한 참조를 받을 수 있다. (확인 필요)
- `__del__` 대신 `weakref.finalize` 로 해제 시 호출될 함수를 등록하는 방법이 있다. (확인 필요)
- 인터프리터가 끝날 때 아직 살아 있는 객체의 `__del__` 이 불린다는 보장은 없다. (확인 필요)
- `gc.collect()` 는 `gc.disable()` 상태에서도 수동으로 부를 수 있다 — `disable` 이 막는 것은 자동 수집뿐이다. (확인 필요)
- PyPy 같은 다른 Python 구현은 참조 카운팅을 쓰지 않아, `del` 순간 `__del__` 이 불리지 않을 수 있다. (확인 필요)
- 최근 CPython 은 `None` 같은 일부 객체를 「불멸(immortal)」로 다뤄 참조 카운트가 고정된 큰 값으로 보이고, 버전에 따라 `getrefcount` 가 예전보다 작게 나올 수 있다. (확인 필요)
- 최근 CPython 버전에서 순환 수집기의 세대 구조를 바꾸는 작업(점진적 GC)이 진행됐다. (확인 필요)
