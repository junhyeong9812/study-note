## 한눈에 — 쉽게 말하면

**`@pytest.mark.parametrize` 는 「채점 기준 하나로 답안 여러 장을 따로따로 채점하는 자동 채점기」다.**
채점 기준(테스트 함수 본문)은 한 번만 쓴다.
답안(입력과 기대값)은 표처럼 여러 줄로 넣는다.
채점기는 줄마다 따로 채점하고, 줄마다 합격 · 불합격을 따로 적는다.
pytest 의 파라미터화도 똑같은 구조다.

> **파라미터화** — 테스트 함수 하나에 여러 입력 묶음을 넣고, 묶음마다 별도의 테스트로 돌리는 것.\
> 예: `test_square` 하나에 `(1, 1)` · `(2, 4)` 등 여섯 줄을 넣으면 테스트가 여섯 개 생긴다.

| 비유 | 실체 |
|---|---|
| 채점 기준 | 테스트 함수 본문의 `assert …` |
| 답안 한 장 | 튜플 하나, 예: `(input_val, expected)` |
| 답안 칸의 이름 | 첫 인자 문자열 `"input_val, expected"` |
| 답안에 붙인 이름표 | `ids=[…]` 또는 `pytest.param(…, id="…")` |
| 답안을 채점 전에 손질해 주는 조교 | `indirect=True` 로 거치는 fixture |

```text
  데이터 표                       테스트 함수 하나
  (1, 1)   ──┐
  (2, 4)   ──┤   pytest 가 줄마다     test_square[케이스1] → 통과/실패
  (3, 9)   ──┼── 함수를 따로 부른다 → test_square[케이스2] → 통과/실패
  ...      ──┘                       ...
```

## 이 주제가 답하려는 질문

1. 입력만 다른 테스트를 함수 하나로 어떻게 여러 개 만드나?
2. 매개변수 여럿의 모든 조합을 손으로 나열하지 않고 어떻게 만드나?
3. 실패했을 때 어느 케이스가 실패했는지 어떻게 바로 알 수 있게 하나?
4. 파라미터 값을 테스트에 넣기 전에 필요한 복잡한 준비를 어디로 떼어 내나?

## 동작 방식

### (1) 기본 — 튜플 하나가 테스트 하나

**언제 쓰나** — 검사하는 논리는 같고 입력과 기대값만 바뀔 때 쓴다.

```text
@pytest.mark.parametrize("input_val, expected", [(1, 1), (2, 4), (-1, 1)])
def test_square(input_val, expected): ...
        │
        ▼  pytest 가 이름 문자열을 쉼표로 나눠 매개변수 이름 두 개를 얻는다
        ▼  목록의 튜플마다 test_square(input_val=…, expected=…) 를 따로 부른다
        │
결과:  테스트 세 개 — 각자 통과 · 실패가 따로 기록된다
```

- 첫 인자 `"input_val, expected"` 는 매개변수 이름을 쉼표로 이은 문자열이다.
- 둘째 인자는 케이스 목록이고, 튜플의 값이 차례대로 그 이름에 묶인다.
- 튜플마다 함수가 따로 불리므로, 한 케이스가 실패해도 나머지 케이스는 그대로 돌아간다.
- `pytest 파일.py -v` 로 돌리면 각 파라미터 조합이 별도 테스트 한 줄로 표시된다.

원본의 `test_square` 는 양수 1~4, 음수 `-1`, 0 의 여섯 케이스로 제곱을 검사한다.
음수와 0 을 넣은 것은 「부호가 바뀌는 지점」과 「0」이라는 특별한 값을 일부러 끼운 것이다.

### (2) 데코레이터를 겹치기 — 곱집합

**언제 쓰나** — 두 매개변수를 서로 독립적으로 바꿔 가며 모든 조합을 돌려 보고 싶을 때 쓴다.

```text
@pytest.mark.parametrize("base", [2, 10])
@pytest.mark.parametrize("exp", [0, 1, 2, 3])
def test_power(base, exp): ...
        │
        ▼  base 의 값 2개 × exp 의 값 4개를 짝지어
        ▼  (2,0) (2,1) (2,2) (2,3) (10,0) (10,1) (10,2) (10,3)
        │
결과:  테스트 8개
```

- `@pytest.mark.parametrize` 를 여러 개 겹치면 모든 조합의 곱집합이 생성된다.
- 케이스 수는 각 목록 길이의 곱이다 — 2 × 4 = 8.
- 한 데코레이터 안에 튜플로 나열하는 것(1)은 「적어 둔 조합만」 돌리고, 겹치기(2)는 「모든 조합」을 돌린다.

> **곱집합** — 여러 집합에서 원소를 하나씩 골라 만든 모든 짝의 집합.\
> 예: `{2, 10}` 과 `{0, 1, 2, 3}` 의 곱집합은 짝 8개다.

### (3) 케이스에 이름 붙이기 — `ids` 와 `pytest.param`

**언제 쓰나** — 케이스가 많거나 값만 봐서는 무슨 케이스인지 알기 어려울 때 쓴다.

```text
parametrize("email, is_valid", [("", False), ...], ids=["빈_문자열", ...])
        │
        ▼  케이스 목록과 ids 목록을 순서대로 짝짓는다
        │
결과:  테스트 이름에 "빈_문자열" 이 붙는다 → 실패 보고에서 바로 보인다

pytest.param({"name": "Bob", "age": 17, ...}, False, id="underage_user")
        │
        ▼  값과 이름표를 한 덩어리로 묶는다
        │
결과:  이 케이스의 테스트 이름에 "underage_user" 가 붙는다
```

- `ids=[…]` 는 케이스 목록과 같은 순서로 이름을 하나씩 준다.
- `ids` 를 지정하면 테스트가 실패했을 때 어떤 케이스인지 즉시 파악할 수 있다.
- `pytest.param(값…, id="…")` 은 케이스 하나에 값과 id 를 함께 묶는다 — 이름표가 데이터 바로 옆에 있어 목록이 길어도 짝이 어긋날 일이 적다.
- `pytest.param` 에는 id 말고 마커도 붙일 수 있다.
- 원본은 사용자 케이스 목록을 `test_users` 라는 바깥 변수로 떼어 내고, 데코레이터에는 변수 이름만 넘긴다 — 테스트 데이터와 검사 논리가 갈라져 읽기 쉬워진다.

원본 `test_user_validation` 의 판정은 「이름이 빈 문자열이 아니고(`bool(user.get("name"))`) 나이가 18 이상」이다.
그래서 Alice(30) 는 참, Bob(17) 은 나이 때문에 거짓, 이름이 `""` 인 사용자는 이름 때문에 거짓이다.

원본 `test_email_validation` 의 패턴 `^[^@]+@[^@]+\.[^@]+$` 은 「`@` 아닌 글자 하나 이상 → `@` → `@` 아닌 글자 하나 이상 → 점 → `@` 아닌 글자 하나 이상」이다.
`"user@.com"` 은 `@` 바로 뒤가 점이라, 점 앞에 와야 할 「글자 하나 이상」을 채울 다른 점이 없어 맞지 않는다.

### (4) `indirect=True` — 값을 fixture 에 먼저 보낸다

**언제 쓰나** — 파라미터 값(예: `"user"`)을 그대로 쓰지 않고, 그 값을 바탕으로 복잡한 준비를 거친 결과를 테스트에 넣고 싶을 때 쓴다.

```text
@pytest.mark.parametrize("db_record", ["user", "product"], indirect=True)
def test_db_record(db_record): ...
        │
        ▼  "user" 를 테스트에 바로 넣지 않고, 같은 이름의 fixture db_record 로 보낸다
        ▼  fixture 안에서 request.param == "user"
        ▼  fixture 가 {"type": "user", "table": "users", "fields": [...]} 를 돌려준다
        │
결과:  test_db_record 는 문자열이 아니라 그 딕셔너리를 받는다 (케이스 2개)
```

- `indirect=True` 는 파라미터 값을 fixture 에 전달한다.
- fixture 는 `request.param` 으로 그 값을 꺼낸다.
- 테스트 함수는 fixture 가 돌려준 「변환된 값」을 받는다.
- `indirect` 를 빼면 값이 fixture 를 거치지 않고 그대로 테스트 인자로 들어간다 — 위 예라면 테스트가 딕셔너리 대신 문자열 `"user"` 를 받는다.
- 원본 fixture 는 모르는 종류가 오면 `ValueError` 를 일으켜, 잘못된 파라미터를 조용히 넘기지 않는다.
- 이렇게 하면 복잡한 설정은 fixture 로, 검사는 테스트 함수로 나뉜다.

> **fixture** — 테스트에 필요한 준비물을 만들어 매개변수 이름으로 넘겨주는 pytest 함수(`@pytest.fixture` 를 붙인다).\
> 예: `db_record` fixture 는 레코드 종류에 맞는 딕셔너리를 만들어 준다.

> **`request.param`** — 간접 파라미터화로 fixture 에 넘어온 현재 케이스의 값.\
> 예: 첫 케이스에서 `request.param` 은 `"user"` 다.

### (5) 예외도 데이터로 — `pytest.raises` 와 함께

**언제 쓰나** — 입력마다 다른 예외가 나야 하는지를 한 함수로 검사할 때 쓴다.

```text
parametrize("a, b, expected_error", [(1, 0, ZeroDivisionError), ("a", 1, TypeError)])
        │
        ▼  예외 클래스 자체를 파라미터 값으로 넘긴다
        ▼  with pytest.raises(expected_error): a / b
        │
결과:  1 / 0       → ZeroDivisionError 가 나야 통과
       "a" / 1     → TypeError 가 나야 통과
```

- 예외 클래스도 값이라 튜플에 넣어 넘길 수 있다.
- `pytest.raises(X)` 블록은 안에서 `X` 가 나면 통과한다.
- 블록 안에서 아무 예외도 나지 않으면 테스트는 실패한다.
- `X` 가 아닌 다른 예외가 나면 그 예외는 잡히지 않고 밖으로 퍼져 테스트가 실패한다.

### (6) 경계값 분석 — 표에 어떤 값을 넣나

**언제 쓰나** — 범위를 나눠 분기하는 코드(`<`, `<=`)를 검사할 때 쓴다.

```text
categorize 의 구간
   invalid | infant | child  | teen   | adult  | senior
   ... -1  | 0 ~ 2  | 3 ~ 12 | 13~17  | 18~64  | 65 ...
           ↑        ↑        ↑        ↑        ↑
         전환점    전환점    전환점    전환점    전환점
경계값 분석: 전환점마다 양쪽 값을 하나씩 → (-1, 0) (2, 3) (12, 13) (17, 18) (64, 65)
```

- 경계값 분석은 버그가 가장 많이 생기는 경계 지점을 체계적으로 테스트한다.
- 원본이 정리한 규칙은 「하한값, 하한-1, 하한+1」 · 「상한값, 상한-1, 상한+1」 · 「경계 전환점 양쪽 값」이다.
- `<` 와 `<=` 를 헷갈리는 실수는 전환점 바로 위 · 바로 아래 값에서만 드러난다.
- 경계값들을 parametrize 목록에 한 줄씩 넣으면, 각 경계가 별도 테스트가 되어 어느 경계가 깨졌는지 따로 보인다.

> **경계값 분석** — 입력 범위가 바뀌는 지점과 그 바로 옆 값을 골라 테스트하는 방법.\
> 예: `age <= 17` 이면 17 과 18 을 둘 다 넣는다.

## 문법 — 형태와 규칙

```python
import pytest

@pytest.mark.parametrize("a, b, total", [
    (1, 2, 3),
    (-1, 1, 0),
    pytest.param(0, 0, 0, id="둘_다_0"),
])
def test_add(a, b, total):
    assert a + b == total

@pytest.fixture
def mode(request):
    return request.param.upper()

@pytest.mark.parametrize("mode", ["dev", "prod"], indirect=True)
def test_mode(mode):
    assert mode in ("DEV", "PROD")
```

- 첫 인자는 매개변수 이름을 쉼표로 이은 문자열이고, 테스트 함수의 매개변수 이름과 같아야 한다.
- 둘째 인자는 케이스 목록이다.
- 이름이 둘 이상이면 각 케이스는 이름 수와 같은 길이의 튜플이다.
- 이름이 하나면 값을 그대로 나열한다 — `["user", "product"]`.
- `ids=[…]` 는 케이스 순서대로 이름을 하나씩 준다.
- `pytest.param(값…, id="…")` 은 케이스 하나에 이름(또는 마커)을 붙인다.
- 데코레이터를 여러 개 겹치면 모든 조합의 곱집합이 생긴다.
- `indirect=True` 면 값은 같은 이름의 fixture 로 가고, fixture 가 `request.param` 으로 받는다.
- 실행은 `pytest 파일.py -v` 다.

| 도구 | 하는 일 | 원본의 예 |
|---|---|---|
| `parametrize("x, y", [...])` | 튜플 하나 = 테스트 하나 | `test_square` (6개) |
| 데코레이터 겹치기 | 곱집합 | `test_power` (2 × 4 = 8개) |
| `ids=[...]` | 케이스 이름 목록 | `test_email_validation` (5개) |
| 예외 클래스를 값으로 | 케이스마다 다른 예외 검사 | `test_division_errors` (2개) |
| `pytest.param(..., id=...)` | 케이스 하나에 이름 · 마커 | `test_user_validation` (3개) |
| `indirect=True` | 값 → fixture → 테스트 | `test_db_record` (2개) |
| 경계값 목록 | 전환점 양쪽 검사 | `test_age_category` (10개) |

## 어디서 틀리나

### 1. 케이스에 이름이 없으면 실패한 케이스를 찾기 어렵다

케이스가 수십 개면 실패 보고만 보고 어느 입력이 문제인지 알기 어렵다.
`ids` 나 `pytest.param(…, id=…)` 로 이름을 붙이면 실패한 케이스를 즉시 알 수 있다.
`ids` 목록은 케이스 목록과 순서로 짝지어지므로, 케이스를 추가 · 삭제할 때 `ids` 도 함께 고쳐야 한다.
이름표가 값 바로 옆에 붙는 `pytest.param` 은 이 어긋남이 생기기 어렵다.

### 2. 데코레이터를 겹치면 케이스 수가 곱으로 불어난다

여러 `@parametrize` 를 겹치면 모든 조합의 곱집합이 생성된다.
목록 셋이 각각 10개면 1000개가 된다.
모든 조합이 의미 있을 때만 겹치고, 특정 조합만 필요하면 한 데코레이터에 튜플로 적는다.

### 3. `indirect` 를 빼먹으면 fixture 를 거치지 않는다

파라미터 이름이 fixture 이름과 같아도 `indirect=True` 가 없으면 값이 그대로 테스트에 들어간다.
그러면 테스트는 준비된 객체 대신 원재료 값(예: 문자열)을 받아 엉뚱하게 실패한다.

### 4. 경계값 목록에 빠진 경계가 있다

원본 `test_age_category` 는 「경계값 분석」이라 적었지만, `infant` 와 `child` 사이의 전환점(2 와 3)을 넣지 않았다.
그래서 `if age <= 2` 를 `if age < 2` 로 잘못 써도 목록의 열 케이스는 그대로 모두 통과한다.
또 `150` 에 「상한」 주석이 붙어 있지만 `categorize` 에는 위쪽 경계가 없다 — 150 은 코드가 나누는 경계가 아니라 「큰 값 하나」다.
경계는 주석이 아니라 코드의 조건문에서 찾아야 한다.

### 5. 같은 계산끼리 비교하는 단언은 아무것도 검증하지 못한다

원본 `test_power` 는 `base ** exp` 와 `pow(base, exp)` 를 비교한다.
둘은 같은 거듭제곱 계산이라 이 단언은 사실상 언제나 참이다.
이 테스트는 「곱집합으로 8개가 생긴다」를 보이는 예일 뿐, 내가 쓴 코드의 버그를 잡는 테스트가 아니다.
실제 테스트에서는 기대값을 계산 코드와 따로 적는다(예: `(2, 3, 8)`).

### 6. `pytest.raises` 는 지정한 예외만 잡는다

블록 안에서 예외가 안 나면 실패한다.
다른 종류의 예외가 나면 잡히지 않고 퍼져서 역시 실패한다.
그래서 예외 케이스의 기대 예외 클래스를 잘못 적으면 테스트가 실패로 드러난다 — 조용히 넘어가지 않는다.

### 7. 파일을 `python` 으로 돌리면 테스트가 돌지 않는다

원본 파일을 `python 파일.py` 로 실행하면 `if __name__ == '__main__':` 아래의 요약 문장만 찍힌다.
테스트 함수는 정의만 될 뿐 호출되지 않는다 — 테스트를 모으고 부르는 일은 pytest 가 한다.
원본 주석의 실행 명령은 `pytest test_parametrize.py -v` 다.
원본은 `import math` 를 하지만 쓰지 않는다.

### 8. `ids` 에 한국어를 쓰면

원본의 주장 → 「ids 는 한국어 가능」.
왜 의심스러운가 → 이름표로 쓸 수는 있지만, pytest 는 기본 설정에서 ASCII 아닌 글자를 이스케이프해 `-v` 보고에 `\uXXXX` 꼴로 보여 줄 수 있다 (확인 필요).
읽기 쉬운 이름이 목적이면 이 점을 염두에 둔다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| 튜플 하나마다 별도 테스트가 생긴다 | pytest 라이브러리의 동작 (Python 언어가 아니다) |
| 데코레이터를 겹치면 곱집합 | pytest 라이브러리의 동작 |
| `indirect=True` 면 값이 fixture 의 `request.param` 으로 간다 | pytest 라이브러리의 동작 |
| `ids` 의 ASCII 아닌 글자를 이스케이프한다 | pytest 의 기본 설정 · 버전에 따라 다를 수 있음 (확인 필요) |
| `1 / 0` 은 `ZeroDivisionError`, `"a" / 1` 은 `TypeError` | Python 언어 |
| `bool("")` 은 `False` | Python 언어 |
| `re.match` 는 문자열 처음부터 맞춰 본다 | Python 표준 라이브러리 `re` |
| `python 파일.py` 로 돌리면 `__main__` 블록만 실행된다 | Python 언어 (`__name__` 규칙) |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 같은 검사, 입력 · 기대값만 다름 | `parametrize` 에 튜플 목록 | 복사한 테스트 함수 여러 개 |
| 두 매개변수의 모든 조합이 의미 있음 | 데코레이터 겹치기 | 조합을 손으로 나열 |
| 특정 조합 몇 개만 필요 | 한 데코레이터에 튜플로 | 데코레이터 겹치기(불필요한 조합이 생김) |
| 케이스가 많고 값만으로 의미가 안 보임 | `ids` 또는 `pytest.param(id=…)` | 이름 없는 긴 목록 |
| 값마다 복잡한 준비가 필요 | fixture + `indirect=True` | 테스트 본문 안의 긴 `if` 분기 |
| 범위로 나누는 분기 검사 | 전환점 양쪽 값을 고른 목록 | 범위 한가운데 값 몇 개 |
| 케이스마다 검사 논리 자체가 다름 | 테스트 함수를 따로 | `parametrize` 안에 `if` 로 분기 |

## 핵심 문장

1. **튜플 하나가 테스트 하나다** — 한 케이스가 실패해도 나머지는 따로 돌고 따로 보고된다.
2. **데코레이터를 겹치면 곱집합이다** — 케이스 수는 목록 길이의 곱이다.
3. **이름표(`ids` · `pytest.param(id=…)`)가 실패한 케이스를 바로 알려 준다.**
4. **`indirect=True` 는 값을 fixture 에 먼저 보낸다** — 준비는 fixture, 검사는 테스트.
5. **좋은 케이스 목록은 코드의 전환점 양쪽을 덮는다** — 경계 하나가 빠지면 그 경계의 버그는 숨는다.

## 용어 풀이

- **파라미터화** — 테스트 함수 하나에 여러 입력 묶음을 넣어 묶음마다 별도 테스트로 돌리는 것.
- **`@pytest.mark.parametrize`** — 파라미터화를 지시하는 pytest 마커(데코레이터).
- **마커** — `@pytest.mark.…` 꼴로 테스트에 붙이는 표지.
- **테스트 케이스** — 파라미터화로 생긴 개별 테스트 하나.
- **`ids`** — 케이스 목록과 순서대로 짝지어지는 이름 목록.
- **`pytest.param`** — 케이스 하나의 값에 id 나 마커를 함께 묶는 함수.
- **곱집합** — 여러 집합에서 하나씩 골라 만든 모든 짝의 집합.
- **fixture** — 테스트에 필요한 준비물을 만들어 매개변수 이름으로 넘겨주는 pytest 함수.
- **`request.param`** — 간접 파라미터화로 fixture 에 넘어온 현재 케이스의 값.
- **간접 파라미터화(`indirect`)** — 파라미터 값을 테스트 대신 같은 이름의 fixture 로 보내는 방식.
- **`pytest.raises`** — 블록 안에서 지정한 예외가 나는지 검사하는 컨텍스트 매니저.
- **경계값 분석** — 범위가 바뀌는 지점과 그 바로 옆 값을 골라 테스트하는 방법.
- **데이터 주도 테스트** — 검사 논리는 고정하고 테스트 데이터를 표로 바꿔 끼우는 방식.

## 더 들어가면

- `ids` 를 주지 않으면 pytest 가 값으로 이름을 자동으로 만든다 — 숫자 · 문자열은 값을 `-` 로 이어 붙이고, 딕셔너리 같은 객체는 「매개변수 이름 + 번호」 꼴을 쓴다 (확인 필요).
- `ids` 에는 목록 대신 함수를 넘겨, 값에서 이름을 계산하게 할 수 있다 (확인 필요).
- `indirect` 에 `True` 대신 이름 목록을 주면, 일부 매개변수만 fixture 로 보내고 나머지는 직접 넣을 수 있다 (확인 필요).
- 파라미터화되지 않은 상태에서 fixture 가 `request.param` 을 읽으면 속성이 없다는 오류가 난다 (확인 필요).
- `pytest.param(…, marks=pytest.mark.xfail)` 처럼 케이스 하나에만 「실패 예상」 같은 마커를 붙일 수 있다 (확인 필요).
- fixture 자체에 `@pytest.fixture(params=[…])` 를 주면, 그 fixture 를 쓰는 모든 테스트가 자동으로 파라미터화된다 (확인 필요).
