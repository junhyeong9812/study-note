## 한눈에 — 쉽게 말하면

**커버리지는 「청소한 방에 발자국 스티커를 붙여 보는 일」이다.**
청소기를 돌린 뒤 바닥을 보면, 바퀴가 지나간 자리와 한 번도 닿지 않은 구석이 갈린다.
스티커가 없는 구석은 「여기는 청소기가 안 갔다」는 뜻이다.
하지만 스티커가 있다고 그 자리가 깨끗하다는 뜻은 아니다 — 지나가기만 하고 흡입을 껐을 수도 있다.
코드 커버리지도 똑같은 구조다.
테스트를 돌리는 동안 실행된 줄에 표시를 남기고, 표시가 없는 줄을 「테스트되지 않은 코드」로 알려 준다.
표시가 있다고 그 줄이 제대로 검증됐다는 보장은 없다.

| 비유 | 실체 |
|---|---|
| 방의 바닥 | 측정 대상 소스 코드 (`--cov=src`) |
| 청소기를 돌리는 일 | `pytest` 로 테스트를 실행하는 일 |
| 발자국 스티커 | 실행된 줄 · 지나간 분기의 기록 |
| 스티커 없는 구석 | 리포트의 미커버 줄 (`Missing`) |
| 흡입을 끈 채 지나가기 | 실행은 했지만 의미 있는 `assert` 가 없는 테스트 |
| 「여기는 청소 안 해도 됨」 표지 | `# pragma: no cover` · `exclude_lines` |

```text
  소스 코드              테스트 실행              리포트
 ┌──────────┐         ┌──────────┐         ┌───────────────────┐
 │ 줄 1  ●  │         │ test_a() │         │ 실행된 줄: 8 / 10   │
 │ 줄 2  ●  │ ◀────── │ test_b() │ ──────▶ │ 커버리지: 80%       │
 │ 줄 3  ○  │  기록    └──────────┘         │ Missing: 3, 7      │
 │ ...      │                              └───────────────────┘
 └──────────┘
  ● 실행됨   ○ 실행 안 됨
```

## 이 주제가 답하려는 질문

1. 내 테스트가 코드의 어느 줄 · 어느 갈래를 한 번도 지나가지 않았나?
2. 「줄을 지나갔다」와 「갈래를 모두 지나갔다」는 무엇이 다르고, 왜 뒤쪽이 더 엄격한가?
3. 굳이 테스트할 필요가 없는 코드는 어떻게 측정에서 빼나?
4. 커버리지가 떨어지는 것을 CI 에서 어떻게 막고, 목표는 몇 % 쯤으로 잡나?

## 동작 방식

### (1) 측정 — 테스트를 돌리며 실행된 곳을 기록한다

**언제 쓰나** — 테스트를 다 짰다고 생각할 때, 실제로 어디가 비었는지 확인하고 싶을 때 쓴다.
`pytest-cov` 는 `pytest` 에 커버리지 측정을 붙이는 플러그인이고, `pip install pytest-cov` 로 설치한다.

> **커버리지(coverage)** — 테스트를 돌리는 동안 실행된 코드가 전체 코드의 얼마인지를 나타낸 비율.\
> 예: 실행 가능한 줄 10줄 중 8줄이 실행됐으면 라인 커버리지 80% 다.

> **pytest-cov** — `pytest` 실행에 커버리지 측정과 리포트를 붙여 주는 플러그인.\
> 예: `pytest --cov=src tests/` 는 `tests/` 를 돌리며 `src` 의 커버리지를 잰다.

```text
pytest --cov=src tests/
        │         │
        │         └─ 이 폴더의 테스트를 돌린다
        └─ 이 패키지(폴더)의 실행 기록을 남긴다
            │
            ▼
  테스트가 src 의 함수를 부를 때마다 → 그 줄에 「실행됨」 표시
            │
            ▼
  테스트가 끝나면 → 줄마다 표시 여부를 모아 % 로 계산 → 리포트
```

- `--cov=` 뒤에는 측정할 대상(패키지 이름이나 폴더)을 적는다.
- 측정 대상이 아닌 코드(테스트 파일 자체, 설치된 라이브러리)는 비율 계산에 넣지 않으려고 대상을 좁힌다.
- 측정은 「테스트가 실제로 부른 코드」만 표시하므로, 아무 테스트도 부르지 않는 함수는 통째로 미커버로 나온다.

### (2) 라인 커버리지 — 줄을 한 번이라도 지나갔나

**언제 쓰나** — 가장 기본이 되는 지표이고, 「한 번도 실행되지 않은 줄」을 찾을 때 쓴다.

> **라인 커버리지(line coverage)** — 실행 가능한 줄 중 테스트 동안 한 번 이상 실행된 줄의 비율.\
> 예: `divide` 의 정상 경로만 테스트하면 `raise` 줄이 실행되지 않아 미커버로 남는다.

```text
def divide(self, a, b):
    if b == 0:                         ● test_divide(10, 2) 가 지나감
        raise ZeroDivisionError(...)   ○ b == 0 인 테스트가 없으면 미실행
    return a / b                       ● 지나감

test_divide 만 있으면  → raise 줄이 Missing
test_divide_by_zero 추가 → raise 줄도 ● → 이 함수의 라인 100%
```

- `test_divide` 는 `b` 가 0이 아니라서 `if` 를 건너뛰고 `return` 으로 간다.
- 그래서 `raise` 줄에는 표시가 생기지 않는다.
- `test_divide_by_zero` 가 `pytest.raises(ZeroDivisionError)` 로 예외 경로를 지나가면 비로소 모든 줄이 표시된다.

### (3) 브랜치 커버리지 — 분기의 모든 갈래를 지나갔나

**언제 쓰나** — `if` · `elif` · `else` · 반복문처럼 길이 갈리는 코드에서, 「줄은 다 지나갔는데 한쪽 갈래는 안 갔다」를 잡아낼 때 쓴다.
`--cov-branch` 옵션이나 설정의 `branch = true` 로 켠다.

> **브랜치 커버리지(branch coverage)** — 분기마다 갈 수 있는 갈래(참 쪽 · 거짓 쪽) 중 테스트가 실제로 지나간 갈래의 비율.\
> 예: `if` 에 `else` 가 없어도 「조건이 거짓이라 `if` 블록을 건너뛴 갈래」가 따로 있다.

라인 커버리지와 갈리는 가장 짧은 예는 이렇다.

```python
def clamp(x):
    if x < 0:
        x = 0
    return x

# 테스트: clamp(-5) 하나만
```

```text
clamp(-5):
  if x < 0:  ── 참 ──▶  x = 0  ──▶  return x      ● 세 줄 모두 실행
             └─ 거짓 ─▶ (바로) return x            ○ 이 갈래는 한 번도 안 감

라인 커버리지   : 3 / 3 줄 → 100%
브랜치 커버리지 : 「if 가 거짓인 갈래」가 미커버로 남는다
```

- `clamp(-5)` 는 조건이 참이라 세 줄을 전부 지나간다.
- 그래서 라인 커버리지만 보면 빈틈이 없어 보인다.
- 하지만 「음수가 아닌 값이 들어오면 그대로 돌려준다」는 갈래는 한 번도 검사되지 않았다.
- 브랜치 커버리지는 이 빠진 갈래를 드러낸다 — 이것이 팁의 「브랜치 커버리지가 라인 커버리지보다 더 의미 있다」 · 「브랜치 > 라인: 더 엄격하고 더 유용」의 뜻이다.

원본의 `grade` 는 결과가 `'A'` ~ `'F'` 다섯 갈래로 나뉜다(원본 주석: 「브랜치 5개」).
원본의 `divide` 는 「0이다 / 0이 아니다」 두 갈래다(원본 주석: 「브랜치 2개」).
다섯 갈래를 모두 지나가려면 점수 다섯 개가 필요하고, 원본은 `@pytest.mark.parametrize` 로 `(95,'A')` ~ `(55,'F')` 다섯 쌍을 한 테스트 함수에 넣었다.

> **parametrize** — 하나의 테스트 함수를 여러 입력 · 기대값 쌍으로 되풀이해 돌리게 하는 `pytest` 데코레이터.\
> 예: `@pytest.mark.parametrize("score, expected", [(95, 'A'), (85, 'B')])` 는 테스트를 두 번 돈다.

`process` 는 분기가 겹쳐 있다.

```text
process(data)
  if not data ── 참 ─▶ return None           (빈 입력 · None)
             └─ 거짓 ─▶ for item in data:
                          ├ 숫자   ─▶ item * 2
                          ├ 문자열 ─▶ item.upper()
                          └ 그 밖  ─▶ continue   ← 「이 라인이 커버되는지?」
                        return results
```

- `test_process_mixed` 의 입력 `[1, "hello", 2.5, None, "world"]` 에는 `None` 이 들어 있다.
- `None` 은 숫자도 문자열도 아니라 `else` 로 가서 `continue` 를 실행한다.
- 그래서 원본 주석이 묻는 `continue` 줄은 이 테스트가 커버한다.
- 입력에 `None` 같은 「그 밖」의 값이 없었다면 `continue` 줄과 그 갈래는 미커버로 남는다.

### (4) 리포트 — 결과를 어떤 꼴로 보나

**언제 쓰나** — 터미널에서 바로 빈 줄을 보고 싶을 때, 브라우저로 줄마다 색을 보고 싶을 때, CI 도구에 넘길 때 각각 다른 꼴을 쓴다.

```text
--cov-report=term-missing  → 터미널 표 + 「Missing」 칸에 미실행 줄 번호
--cov-report=html          → htmlcov/ 폴더에 줄마다 색칠한 HTML
--cov-report=xml           → 기계가 읽는 XML (CI 용)
```

- `term-missing` 은 「몇 %」뿐 아니라 「몇 번째 줄이 비었나」를 알려 준다.
- `html` 리포트가 생기는 폴더는 설정의 `[tool.coverage.html]` 아래 `directory = "htmlcov"` 로 정한다.
- `xml` 은 사람이 읽기보다 CI 서비스나 다른 도구가 읽어 들이는 용도다.
- 설정의 `show_missing = true` 는 터미널 리포트에 미커버 줄 번호를 늘 보여 주라는 뜻이다.

### (5) 제외 — 측정할 필요 없는 코드를 빼기

**언제 쓰나** — `__repr__` · 로깅 · 메인 가드처럼 테스트하는 의미가 적은 코드가 비율을 깎아 먹을 때 쓴다.

> **제외 패턴(exclude pattern)** — 리포트 계산에서 뺄 줄을 고르는 문자열 패턴 목록(`exclude_lines`).\
> 예: `"def __repr__"` 을 넣으면 `__repr__` 정의가 측정에서 빠진다.

> **pragma: no cover** — 줄 끝에 `# pragma: no cover` 주석을 달아 그 줄(블록을 여는 줄이면 그 블록)을 측정에서 빼는 표시.\
> 예: `def debug_dump(self):  # pragma: no cover`

```text
exclude_lines 의 패턴 하나하나를 소스의 각 줄과 대조
        │
        ├─ 맞는 줄이 블록을 여는 줄(def · if …)이면 → 그 블록 전체를 뺀다
        └─ 그렇지 않으면                         → 그 줄만 뺀다
        │
        ▼
뺀 줄은 분모(실행 가능한 줄)에서도 빠진다 → 비율이 다시 계산된다
```

- 원본 설정의 제외 목록은 `"pragma: no cover"` · `"def __repr__"` · `"if __name__"` · `"raise NotImplementedError"` · `"pass"` · `"\.\.\."`(타입 스텁의 `...`) 여섯 개다.
- `"if __name__"` 을 넣는 까닭은 `if __name__ == '__main__':` 아래 코드가 테스트가 아니라 직접 실행할 때만 돌기 때문이다.
- 원본 정답 코드도 메인 가드 안에 안내문 출력만 두어 「테스트와 분리」했다.
- 패턴은 줄의 **일부만 맞아도** 걸리는 문자열 패턴(정규식)으로 대조된다 — 그래서 짧은 패턴일수록 뜻하지 않은 줄까지 빠질 수 있다(「어디서 틀리나」 3번).

### (6) 목표와 강제 — 기준 아래로 떨어지면 실패시키기

**언제 쓰나** — 팀 프로젝트에서 새 코드가 테스트 없이 들어와 비율이 슬금슬금 떨어지는 것을 막을 때 쓴다.

```text
pytest --cov=. --cov-fail-under=80
        │
        ▼
테스트는 모두 통과 ──▶ 커버리지 계산 ──▶ 80% 미만?
                                        ├ 예   → pytest 가 실패로 끝남 → CI 빨간불
                                        └ 아니오 → 성공
```

- 명령줄의 `--cov-fail-under=80` 과 설정의 `fail_under = 80` 은 같은 역할이다.
- 테스트가 전부 통과해도 비율이 기준 아래면 실패로 끝나므로, CI 가 병합을 막아 커버리지 저하를 방지한다.
- 원본이 든 일반적인 기준은 아래와 같다.

| 기준 | 원본의 설명 |
|---|---|
| 60~70% | 최소 (레거시 프로젝트) |
| 80% | 권장 (대부분의 프로젝트) |
| 90%+ | 높은 신뢰성 필요 (금융, 의료) |
| 100% | 비현실적, 커버리지≠품질 |

이 수치는 원본이 소개하는 관례이지, 도구가 정한 규칙이 아니다.

## 문법 — 형태와 규칙

최소 예제 — 측정 설정과 제외 표시를 한 번에 보인다.

```python
# shapes.py — 측정 대상
class Square:
    def __init__(self, side):
        self.side = side

    def area(self):
        if self.side < 0:
            raise ValueError("음수 변")
        return self.side * self.side

    def __repr__(self):              # 설정의 "def __repr__" 패턴으로 제외
        return f"Square({self.side})"

    def debug(self):  # pragma: no cover
        print(vars(self))
```

```bash
pip install pytest-cov
pytest --cov=shapes --cov-branch --cov-report=term-missing tests/
pytest --cov=shapes --cov-fail-under=80 tests/
```

명령줄 옵션 정리:

| 옵션 | 하는 일 |
|---|---|
| `--cov=대상` | 측정할 패키지 · 폴더를 정한다 (`.` 은 현재 폴더 전체) |
| `--cov-report=term-missing` | 터미널 표에 미커버 줄 번호를 함께 보인다 |
| `--cov-report=html` | HTML 리포트를 만든다 |
| `--cov-report=xml` | CI 용 XML 리포트를 만든다 |
| `--cov-branch` | 브랜치 커버리지를 켠다 |
| `--cov-fail-under=N` | 비율이 N% 미만이면 실패로 끝낸다 |

설정 파일(원본의 `pyproject.toml` 꼴):

| 절 | 키 | 뜻 |
|---|---|---|
| `[tool.coverage.run]` | `source = ["src"]` | 측정 대상 |
| `[tool.coverage.run]` | `branch = true` | 브랜치 커버리지를 늘 켠다 |
| `[tool.coverage.report]` | `fail_under = 80` | 최소 기준 |
| `[tool.coverage.report]` | `show_missing = true` | 미커버 줄 번호 표시 |
| `[tool.coverage.report]` | `exclude_lines = [...]` | 제외 패턴 목록 |
| `[tool.coverage.html]` | `directory = "htmlcov"` | HTML 리포트 폴더 |

원본이 나눈 커버리지 종류:

| 종류 | 원본의 정의 |
|---|---|
| 라인 커버리지 | 실행된 라인 비율 |
| 브랜치 커버리지 | if/else 모든 분기 실행 비율 |
| 함수 커버리지 | 호출된 함수 비율 |

규칙:

- 설정 파일에 적은 값은 명령줄에 매번 옵션을 쓰지 않아도 적용된다.
- `# pragma: no cover` 는 파이썬 문법이 아니라 그냥 주석이다 — 측정 도구가 그 글자를 찾아 뺄 뿐이다.
- 제외한 줄은 분자와 분모 모두에서 빠진다.
- 브랜치 커버리지를 켜면 리포트에 분기 관련 칸이 더해지고, 갈래를 빠뜨린 분기도 비율을 깎는다.

## 어디서 틀리나

### 1. 커버리지를 품질 점수로 읽는다

원본 팁의 첫 문장대로, 커버리지는 테스트되지 않은 코드를 찾는 도구이지 품질의 척도가 아니다.
`assert` 없이 함수를 부르기만 해도 줄은 「실행됨」이 된다.
원본도 「커버리지가 높아도 의미 없는 assert가 많으면 무의미」라고 적었다.
낮은 커버리지는 「확실히 빈 곳이 있다」는 신호지만, 높은 커버리지는 「잘 검증했다」는 증거가 아니다.

### 2. 라인 커버리지 100% 에 안심한다

`clamp(-5)` 예처럼 `else` 가 없는 `if` 는 참 쪽만 지나가도 모든 줄이 실행된다.
거짓 갈래의 동작은 검사되지 않았는데 라인 커버리지는 100% 로 나온다.
분기가 많은 코드일수록 `--cov-branch` 를 켜야 이런 빈틈이 보인다.

### 3. 제외 패턴을 너무 넓게 쓴다

`pragma: no cover` 와 `exclude_lines` 는 `repr` · 로깅처럼 「테스트가 불필요한」 코드에만 쓴다(원본 팁).
테스트하기 귀찮은 실제 로직을 빼면 비율만 오르고 빈틈은 그대로 숨는다.
원본 설정의 `"pass"` 패턴은 의심스럽다 — 패턴이 줄의 일부만 맞아도 걸린다면 `password = ...` · `bypass(...)` 처럼 `pass` 가 들어간 다른 줄까지 빠질 수 있다(확인 필요).
줄 전체가 `pass` 인 경우만 노리려면 줄 시작과 끝을 고정한 패턴이 더 안전하다(확인 필요).

### 4. 원본 테스트 `test_process_empty` 의 기대값

원본의 주장 → `calc.process([])` 가 `[]` 를 돌려준다고 보고 `assert calc.process([]) == []` 를 적었다(주석: 「빈 리스트 분기」).
왜 의심스러운가 → `process` 의 첫 줄은 `if not data: return None` 이다.
빈 리스트는 거짓으로 취급되므로 `not []` 은 참이고, `process([])` 는 `None` 을 돌려준다.
그러면 `None == []` 은 거짓이라 이 테스트는 실패해야 한다.
커버리지 측면에서는 이 테스트도 `return None` 줄을 지나가므로 「커버됨」에 보태진다 — 줄을 지나갔다는 것과 기대값이 맞다는 것은 별개라는 예다.

### 5. 원본 설정 예의 형식

원본의 주장 → 「`.coveragerc` 또는 `pyproject.toml`」이라고 쓰고 `[tool.coverage.run]` 꼴의 절을 보였다.
왜 의심스러운가 → `[tool.coverage.…]` 라는 절 이름과 `["src"]` 같은 배열 표기는 `pyproject.toml`(TOML) 꼴이다.
`.coveragerc` 는 INI 꼴이라 절 이름이 `[run]` · `[report]` 처럼 다르다(확인 필요).
또 원본이 찍는 `"\.\.\."` 는 TOML 의 큰따옴표 문자열 안에서 허용되지 않는 이스케이프라, 작은따옴표 문자열 `'\.\.\.'` 로 써야 할 수 있다(확인 필요).

### 6. 100% 를 목표로 잡는다

원본은 100% 를 「비현실적, 커버리지≠품질」로 적었다.
마지막 몇 %를 채우려고 의미 없는 테스트를 덧붙이면 유지 부담만 는다.
프로젝트 성격에 맞는 기준(원본 권장: 대부분 80%)을 `--cov-fail-under` 로 강제하는 편이 현실적이다.

### 7. 기준을 정해 놓고 강제하지 않는다

목표를 문서에만 적어 두면 비율은 조금씩 떨어진다.
팁대로 CI 에서 `--cov-fail-under` 로 최소 기준을 강제하면 기준 아래의 변경이 실패로 드러난다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| `not []` 은 참이라 `process([])` 가 `None` 을 돌려준다 | 파이썬 언어 (빈 시퀀스는 거짓으로 취급) |
| `5.0 == 5` 는 참이라 `test_divide` 가 통과한다 | 파이썬 언어 (수치 비교) |
| 실행된 줄 · 갈래를 기록해 % 로 계산한다 | 측정 도구(`pytest-cov` 와 그것이 쓰는 측정 라이브러리) — 언어 기능이 아니다 |
| `# pragma: no cover` 가 줄을 측정에서 뺀다 | 측정 도구의 관례 — 파이썬에게는 그냥 주석이다 |
| 블록을 여는 줄이 제외되면 블록 전체가 빠진다 | 측정 도구의 동작 (확인 필요) |
| `@pytest.fixture` 가 테스트마다 새 인스턴스를 준다 | `pytest` (기본 범위가 함수 단위일 때) |
| 60~70 · 80 · 90%+ 기준 | 원본이 든 관례 — 도구 · 언어 어느 쪽의 규칙도 아니다 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 테스트가 빠진 곳을 찾고 싶다 | `--cov-report=term-missing` | 비율 숫자만 보고 끝내기 |
| 분기가 많은 로직을 검증 | `--cov-branch` · `branch = true` | 라인 커버리지만으로 판단 |
| `__repr__` · 디버그 출력 · 메인 가드 | `pragma: no cover` · `exclude_lines` | 실제 로직까지 제외 |
| 커버리지 저하를 막고 싶다 | CI 의 `--cov-fail-under` | 문서에만 목표 적어 두기 |
| 여러 입력으로 같은 분기 검증 | `@pytest.mark.parametrize` | 같은 테스트 함수 복붙 |
| CI 도구와 연동 | `--cov-report=xml` | 사람이 볼 HTML 만 만들기 |
| 테스트 품질을 평가 | 기대값을 따져 보는 리뷰 | 높은 커버리지 = 좋은 테스트로 간주 |

## 핵심 문장

1. **커버리지는 테스트되지 않은 코드를 찾는 도구다** — 품질의 척도가 아니다.
2. **브랜치 커버리지는 분기의 모든 갈래를 따진다** — 그래서 라인 커버리지보다 엄격하고 더 쓸모 있다.
3. **테스트할 필요 없는 코드는 `pragma: no cover` · `exclude_lines` 로 뺀다** — 실제 로직을 빼면 빈틈을 숨기는 것이다.
4. **CI 의 `--cov-fail-under` 가 최소 기준을 지킨다** — 테스트가 통과해도 기준 아래면 실패한다.
5. **줄을 지나간 것과 결과가 맞는 것은 다르다** — 의미 있는 `assert` 가 있어야 커버리지가 뜻을 갖는다.

## 용어 풀이

- **커버리지(coverage)** — 테스트 동안 실행된 코드의 비율.
- **pytest-cov** — `pytest` 에 커버리지 측정을 붙이는 플러그인.
- **라인 커버리지** — 실행 가능한 줄 중 실행된 줄의 비율.
- **브랜치 커버리지** — 분기의 갈래 중 지나간 갈래의 비율.
- **함수 커버리지** — 함수 중 한 번 이상 호출된 함수의 비율.
- **커버리지 리포트** — 측정 결과를 표 · HTML · XML 로 보인 것.
- **Missing** — 리포트에서 실행되지 않은 줄 번호를 보이는 칸.
- **제외 패턴(`exclude_lines`)** — 측정에서 뺄 줄을 고르는 패턴 목록.
- **pragma: no cover** — 줄 끝 주석으로 그 줄 · 블록을 측정에서 빼는 표시.
- **`--cov-fail-under`** — 비율이 기준 미만이면 실패로 끝내는 옵션.
- **메인 가드** — `if __name__ == '__main__':` 블록, 직접 실행할 때만 도는 코드.
- **fixture** — 테스트에 필요한 객체를 만들어 넘겨 주는 `pytest` 함수.
- **parametrize** — 한 테스트를 여러 입력 쌍으로 되풀이하는 `pytest` 데코레이터.
- **CI(지속적 통합)** — 코드를 올릴 때마다 테스트 · 검사를 자동으로 돌리는 체계.
- **타입 스텁** — 본문 없이 `...` 로 시그니처만 적은 정의.

## 더 들어가면

- `pytest-cov` 는 측정 자체를 `coverage.py` 라이브러리에 맡긴다 — `pyproject.toml` 의 `[tool.coverage.*]` 절이 그 라이브러리의 설정이다(확인 필요).
- `coverage.py` 의 브랜치 측정은 「한 줄에서 다른 줄로 넘어가는 이동(arc)」 단위로 센다고 알려져 있다 — 그래서 `if`/`elif` 사슬의 갈래 수는 원본 주석의 「5개」와 다르게 셀 수 있다(확인 필요).
- `coverage.py` 의 기본 리포트는 줄 · 갈래 중심이고, 함수 단위 표는 최근 버전의 HTML 리포트에 추가됐다는 이야기가 있다(확인 필요).
- 여러 프로세스나 병렬 실행(`pytest-xdist`)에서는 측정 결과를 합치는 단계가 따로 필요할 수 있다(확인 필요).
- 커버리지가 「테스트가 정말 잡아내나」를 보여 주지 못하는 한계를 보완하려고, 코드를 일부러 바꿔 테스트가 실패하는지 보는 변이 테스트(mutation testing, 예: `mutmut`)를 쓰기도 한다(확인 필요).
- `exclude_also` 처럼 기본 제외 목록을 지우지 않고 덧붙이는 설정 키가 최근 버전에 있다(확인 필요).
