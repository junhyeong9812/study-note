## 한눈에 — 쉽게 말하면

**입력 검증은 「신청서의 빈칸과 직원 지시문을 섞지 않는 일」이다.**
은행 신청서에는 직원이 읽는 지시문(인쇄된 글)과 고객이 채우는 빈칸이 있다.
고객이 이름 칸에 「그리고 금고를 열어 주시오」라고 적었을 때 직원이 그것을 지시로 읽으면 사고가 난다.
프로그램도 똑같은 구조다.
SQL 문 · HTML · 셸 명령 · 파일 경로는 「지시문」이고, 사용자 입력은 「빈칸」이다.
입력이 지시문의 문법으로 읽히는 순간 공격이 된다.

> **인젝션(injection)** — 데이터로 넣은 입력이 코드(명령)의 일부로 해석되는 취약점.\
> 예: 사용자명 칸에 `' OR '1'='1' --` 를 넣어 SQL 조건을 바꾼다.

| 비유 | 실체 |
|---|---|
| 인쇄된 지시문 | SQL 문 · HTML 태그 · 셸 명령 · 기준 디렉터리 |
| 고객이 채운 빈칸 | 사용자 입력 문자열 |
| 빈칸 글씨를 지시로 읽는 직원 | 입력을 문자열로 이어 붙여 해석하는 코드 |
| 「빈칸은 빈칸일 뿐」이라고 정해진 양식 | 파라미터 바인딩 · `html.escape()` · 리스트 인자 |
| 칸에 적을 수 있는 글자를 미리 정해 둔 양식 | 화이트리스트 검증 |

```text
  지시문(코드)                    빈칸(데이터)
  "SELECT ... WHERE name = ?"  +  "' OR '1'='1' --"
        │                               │
        └──── 따로 전달 ────────────────┘
                     │
                     ▼
       DB 는 빈칸을 "글자 덩어리"로만 비교한다 → 공격 실패
```

## 이 주제가 답하려는 질문

1. 사용자 입력이 SQL · HTML · 셸 · 파일 경로 안에서 「코드」로 바뀌는 것을 어떻게 막나?
2. 입력을 미리 거를 때 「허용할 것만 적기」와 「막을 것을 적기」 중 무엇이 왜 더 안전한가?
3. 경로처럼 문자열만 보고는 판단이 어려운 입력은 어떤 순서로 확인하나?

## 동작 방식

### (1) SQL Injection — 문자열 포맷팅 대 파라미터 바인딩

**언제 쓰나** — 사용자 입력을 조건으로 DB 를 조회 · 수정할 때 언제나.

> **SQL Injection** — 사용자 입력이 SQL 문의 문법 일부로 해석되어 쿼리의 뜻이 바뀌는 공격.\
> 예: 로그인 조건이 항상 참이 되어 모든 행이 나온다.

```text
[위험] f"SELECT * FROM users WHERE username = '{username}'"
   username = "' OR '1'='1' --"
        │  문자열을 그대로 끼워 넣는다
        ▼
   SELECT * FROM users WHERE username = '' OR '1'='1' --'
                                       ──  ──────────  ───
                                     빈 값   항상 참   뒤는 주석
        ▼
   모든 행이 조건을 만족 → 전체 사용자 노출

[안전] cursor.execute('SELECT * FROM users WHERE username = ?', (username,))
        │  SQL 틀과 값을 따로 넘긴다
        ▼
   DB: username 열이 글자 그대로 "' OR '1'='1' --" 인 행을 찾는다
        ▼
   그런 행 없음 → fetchall() 은 [] (빈 리스트)
```

- 위험한 쪽에서는 입력 속 작은따옴표(`'`)가 문자열 칸을 닫아 버린다.
- 그 뒤의 `OR '1'='1'` 은 조건식이 되고, `'1'='1'` 은 어느 행에서나 참이다.
- `--` 는 SQL 주석 시작이라 쿼리 끝에 남은 `'` 를 무력화한다.
- 안전한 쪽에서는 `?` 자리에 값이 「값」으로만 들어간다.
- 그래서 공격 문자열은 그냥 긴 사용자명 하나로 비교되고, 일치하는 행이 없다.
- 정상 입력 `"alice"` 는 같은 방식으로 `(1, 'alice', 'alice@test.com')` 행을 찾는다.

> **파라미터 바인딩(parameter binding)** — SQL 문에 자리표시자(`?` · `%s`)를 두고 값은 따로 넘겨 DB 가 값으로만 다루게 하는 방식.\
> 예: `cursor.execute('... WHERE username = ?', (name,))`.

자리표시자 모양은 DB 드라이버마다 다르다.
원본은 SQLite 의 `?` 와, 다른 드라이버에서 쓰는 `%s` 를 함께 든다.
값은 튜플로 넘긴다 — 값이 하나여도 `(name,)` 처럼 쉼표가 필요하다.

### (2) XSS — HTML 이스케이프

**언제 쓰나** — 사용자 입력을 웹 페이지(HTML)에 다시 보여 줄 때.

> **XSS(Cross-Site Scripting)** — 사용자 입력에 섞인 스크립트가 다른 사람의 브라우저에서 실행되는 공격.\
> 예: 게시글에 `<script>` 를 넣어 읽는 사람의 쿠키를 빼 간다.

```text
입력:  <script>alert("XSS")</script>
          │ html.escape()
          ▼
       &lt;script&gt;alert(&quot;XSS&quot;)&lt;/script&gt;
          │ 브라우저가 받으면
          ▼
       태그가 아니라 "<script>..." 라는 글자로 화면에 보인다
```

- `html.escape()` 는 HTML 에서 뜻이 있는 문자를 엔티티로 바꾼다.
- 바뀌는 문자는 `<` → `&lt;`, `>` → `&gt;`, `&` → `&amp;`, `"` → `&quot;`, `'` → `&#x27;` 다.
- 브라우저는 엔티티를 「그 글자 모양」으로 그릴 뿐 태그로 해석하지 않는다.
- `quote=True` 는 따옴표(`"` · `'`)까지 바꾸라는 뜻이다.
- 따옴표를 바꾸지 않으면 `" onmouseover="alert(1)"` 같은 입력이 HTML 속성값을 닫고 새 이벤트 핸들러 속성을 만들 수 있다(속성 탈출).
- 원본 주석의 예상 결과에서 `quote` 를 주지 않은 호출도 `"` 를 `&quot;` 로 바꾼다 — 즉 기본값이 이미 따옴표를 바꾸는 쪽이다.
- 이스케이프는 위 다섯 문자만 바꾼다.
- 그래서 `javascript:alert(1)` 처럼 그 문자가 없는 부분은 그대로 남는다(→ 「어디서 틀리나」 4).

> **이스케이프(escape)** — 특별한 뜻을 가진 문자를 뜻 없는 표기로 바꿔 「글자 그대로」 다루게 하는 것.\
> 예: `<` 를 `&lt;` 로 쓴다.

### (3) 화이트리스트 입력 검증 — 정규식과 범위

**언제 쓰나** — 입력이 들어오는 입구에서 「모양이 맞는지」를 먼저 확인할 때(사용자명 · 이메일 · 페이지 번호 · 수량).

> **화이트리스트(whitelist)** — 허용할 패턴만 적고 나머지는 모두 거부하는 방식. 반대로 블랙리스트는 막을 패턴만 적는다.\
> 예: 사용자명은 영문 · 숫자 · `_` 만, 3~20자.

```text
validate_username("admin'; DROP TABLE--")
   패턴 ^[a-zA-Z0-9_]{3,20}$
        │ 처음부터 끝까지 허용 문자만 3~20개인가?
        ▼
   '  ;  공백  -  는 허용 문자가 아님 → False

validate_integer("101", 1, 100)
   int("101") = 101 → 101 > 100 → False
validate_integer("abc", 1, 100)
   int("abc") → ValueError → except → False
```

- `^` 는 문자열 시작, `$` 는 끝을 뜻해 「일부만 맞는」 입력을 거른다.
- `{3,20}` 은 앞 문자 집합이 3개 이상 20개 이하라는 뜻이다 — `"ab"` 는 2자라 떨어진다.
- 이메일 패턴은 `이름@도메인.영문2자이상` 꼴만 받는다 — `"a@b"` 는 점과 끝부분이 없어 떨어지고, `"user@test.co.kr"` 은 통과한다.
- 원본은 이 이메일 패턴을 「RFC 단순화 패턴」이라 부른다 — 실제 이메일 규칙 전부를 담지는 않는다.
- `validate_integer` 는 `int()` 변환이 실패하면(`ValueError` · `TypeError`) 거부하고, 성공하면 하한(`min_val`) · 상한(`max_val`)을 따로 검사한다.
- 하한 · 상한이 `None` 이면 그쪽 검사는 건너뛴다.
- 블랙리스트는 「생각해 낸 공격」만 막는다 — 생각하지 못한 문자 · 인코딩 · 조합이 빠져나간다.
- 화이트리스트는 「생각해 낸 정상 입력」만 받으므로 모르는 것은 기본으로 거부된다.
- 원본 주석은 이를 「예외적 우회 케이스가 적다」로 말한다.

### (4) 명령어 인젝션 — `shell=False` + 리스트

**언제 쓰나** — 파이썬에서 `subprocess` 로 외부 프로그램을 실행하고, 인자에 사용자 입력이 들어갈 때.

> **명령어 인젝션(command injection)** — 셸 명령 문자열에 끼운 입력 속 `;` · `&&` · `|` 같은 셸 문법이 새 명령으로 실행되는 공격.\
> 예: 파일명 `test.txt; rm -rf /` 가 두 번째 명령을 만든다.

```text
[위험] subprocess.run(f"cat {user_file}", shell=True)
   셸이 받는 줄: cat test.txt; rm -rf /
        │ 셸이 ; 를 "명령 구분"으로 읽는다
        ▼
   cat test.txt  그리고  rm -rf /   ← 두 명령 실행

[안전] subprocess.run(["cat", user_file], shell=False)
        │ 셸을 거치지 않고 프로그램에 인자 목록을 바로 넘긴다
        ▼
   cat 이 받는 인자 1개: "test.txt; rm -rf /"  ← 그냥 이상한 파일명

[셸이 꼭 필요할 때] shlex.quote(user_file)
   → 'test.txt; rm -rf /'   (작은따옴표로 감싼 한 덩어리)
```

- 리스트로 넘기면 각 원소가 그대로 하나의 인자가 된다.
- 셸이 끼지 않으니 `;` 를 해석할 주체가 없다.
- `shlex.quote()` 는 셸 문자열을 써야만 하는 경우에 입력 하나를 셸이 한 인자로 읽도록 감싼다.
- 원본 예제는 위험한 명령을 실제로 실행하지 않고, 무엇이 일어나는지를 `print` 로 설명만 한다.

### (5) 경로 탐색(Path Traversal) — 정규화 후 접두어 비교

**언제 쓰나** — 사용자가 고른 파일 이름으로 서버의 파일을 열 때(업로드 폴더 등).

> **경로 탐색(path traversal)** — `../` 로 상위 디렉터리로 올라가 허용 범위 밖 파일에 닿는 공격.\
> 예: `../../../etc/passwd`.

```text
base_dir = "/app/uploads",  user_path = "../../../etc/passwd"
   os.path.realpath(base_dir)               → /app/uploads
   os.path.join(base, user_path)            → /app/uploads/../../../etc/passwd
   os.path.realpath(...)                    → /etc/passwd   (.. 를 실제로 계산)
        │
   "/etc/passwd".startswith("/app/uploads/") ? 아니다
   "/etc/passwd" == "/app/uploads" ?          아니다
        ▼
   ValueError("경로 탐색 공격 감지: ../../../etc/passwd")
```

- `os.path.realpath()` 는 `..` 와 심볼릭 링크를 풀어 「실제로 가리키는 절대 경로」를 만든다.
- 문자열에 `..` 가 있는지 찾는 대신, 계산이 끝난 결과가 어디인지를 본다.
- 비교는 `base + os.sep`(예: `/app/uploads/`)으로 한다.
- 그냥 `base` 로 비교하면 `/app/uploads_evil/x` 도 `/app/uploads` 로 시작하므로 통과해 버린다.
- 원본 주석은 이를 「같은 prefix 디렉토리 우회 방지」라 부른다.
- `full != base` 조건은 기준 디렉터리 그 자체를 가리키는 경우를 따로 허용한다.

> **정규화(normalization)** — 같은 대상을 가리키는 여러 표기를 하나의 표준 표기로 바꾸는 것.\
> 예: `/a/b/../c` → `/a/c`.

## 문법 — 형태와 규칙

```python
import html, re, sqlite3, shlex, subprocess, os

conn = sqlite3.connect(':memory:')
cur = conn.cursor()
cur.execute('SELECT ? AS v', ("' OR 1=1 --",))          # 값은 튜플로 따로
safe = html.escape('<b>"hi"</b>', quote=True)          # HTML 에 넣기 전
ok = bool(re.match(r'^[a-zA-Z0-9_]{3,20}$', 'alice'))  # 허용 패턴만
subprocess.run(['echo', 'a; b'], shell=False)          # 리스트 + 셸 없음
arg = shlex.quote('a; b')                              # 셸이 꼭 필요할 때
base = os.path.realpath('/srv/files')
full = os.path.realpath(os.path.join(base, 'x/../y.txt'))
inside = full.startswith(base + os.sep) or full == base
```

- SQL 은 자리표시자(`?` 또는 드라이버에 따라 `%s`)를 쓰고, 값은 `execute` 의 두 번째 인자(튜플)로 넘긴다.
- 문자열 포맷팅(f-string · `%` · `+` 연결)으로 쿼리를 만들지 않는다.
- HTML 에 들어갈 사용자 입력은 `html.escape(text, quote=True)` 로 바꾼 뒤 넣는다.
- 정규식 검증은 `^ … $` 로 전체를 묶고, 허용 문자 집합과 길이(`{최소,최대}`)를 적는다.
- 숫자 검증은 `int()` 를 `try` 로 감싸 변환 실패를 거부로 처리하고, 범위를 따로 확인한다.
- `subprocess` 는 `shell=False` + 리스트 인자를 기본으로 쓴다.
- 경로는 `realpath` 로 정규화한 뒤 `base + os.sep` 접두어로 비교한다.

## 어디서 틀리나

### 1. 쿼리를 문자열 포맷팅으로 만든다

원본 팁 그대로, SQL 쿼리는 반드시 파라미터 바인딩(`?` 나 `%s`)으로 쓴다.
f-string 으로 만든 쿼리는 따옴표 하나로 뜻이 바뀐다.
「따옴표만 지우면 되지 않나」 같은 손질은 블랙리스트라 다른 우회 길이 남는다.

### 2. HTML 출력에 이스케이프를 빼먹는다

원본 팁 그대로, HTML 출력에는 `html.escape()` 로 사용자 입력을 이스케이프한다.
태그 사이뿐 아니라 속성값 안에 들어갈 때는 따옴표까지 바꿔야 한다(`quote=True`).

### 3. 블랙리스트로 막으려 한다

원본 팁 그대로, 화이트리스트(허용 패턴) 방식이 블랙리스트(차단 패턴)보다 안전하다.
막을 목록은 언제나 불완전하다.

### 4. 「이스케이프했으니 모든 페이로드가 무해하다」

원본 주석의 주장 → 세 XSS 페이로드가 「모두 무해한 텍스트로 변환됨」.
왜 의심스러운가 → 이 말은 입력이 **태그 사이 본문이나 따옴표로 감싼 속성값**에 글자로 들어갈 때 맞다.
`javascript:alert(1)` 에는 바꿀 문자가 없어서, 사용자 입력을 `href` 값 자체로 쓰면 이스케이프 뒤에도 그대로 `javascript:` 링크가 된다.
이런 자리에는 URL 의 시작(스킴)을 따로 화이트리스트로 검사해야 한다(원본에 근거 없음 — 추론).

### 5. 「DB 드라이버가 값을 이스케이프한다」

원본 주석의 주장 → 파라미터 바인딩에서 「DB 드라이버가 값을 안전하게 이스케이프」한다.
왜 의심스러운가 → 바인딩의 요점은 SQL 틀과 값을 **따로** 넘겨 값이 SQL 문법으로 해석될 기회 자체를 없애는 것이다.
드라이버가 내부에서 이스케이프로 흉내 내는지, 값을 따로 전달하는지는 드라이버마다 다를 수 있다(확인 필요).
어느 쪽이든 쓰는 사람이 할 일(자리표시자 + 값 튜플)은 같다.

### 6. `shell=True` 에 입력을 끼운다

원본 팁 그대로, `subprocess` 는 `shell=False` + 리스트 형태가 안전하다.
셸 문자열이 꼭 필요하면 입력마다 `shlex.quote()` 를 씌운다.

### 7. 경로를 문자열로만 검사한다

`'..' in user_path` 같은 검사는 표기를 바꾼 입력(링크 · 다른 구분자)에 뚫릴 수 있다.
정규화한 최종 경로를 기준 디렉터리 + 구분자로 비교한다.
`base` 만으로 접두어를 비교하면 이름이 같은 접두어로 시작하는 이웃 디렉터리가 통과한다.

### 8. 예제의 `..\windows\system32` 는 운영체제마다 다르게 풀린다

원본은 이 입력을 공격 예로 넣었지만 결과를 적지 않았다.
`\` 를 경로 구분자로 보지 않는 운영체제에서는 이 문자열 전체가 파일 이름 하나가 되어 기준 디렉터리 안으로 해석될 수 있다(원본에 근거 없음 — 추론).
Windows 에서는 `\` 가 구분자라 상위로 올라가는 경로가 된다(확인 필요).

### 9. 출력용 자르기가 엔티티를 끊는다

원본 루프는 이스케이프 결과를 `[:40]` 으로 잘라 보여 준다.
`<a href='javascript:alert(1)'>` 의 이스케이프 결과는 40자보다 길어 끝의 엔티티가 중간에 잘린다(원본에 근거 없음 — 추론).
이것은 화면 표시만의 문제지만, 잘린 문자열을 실제 HTML 에 쓰면 안 된다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| `?` 가 자리표시자다 | SQLite 용 `sqlite3` 모듈 — 다른 드라이버는 `%s` 등 다른 꼴을 쓴다 |
| 바인딩된 값은 SQL 문법으로 해석되지 않는다 | DB 드라이버 · DB 엔진 (내부 방식은 드라이버마다 다를 수 있음 — 확인 필요) |
| `html.escape` 가 다섯 문자를 엔티티로 바꾼다 | 파이썬 표준 라이브러리 `html` 모듈 |
| `shlex.quote` 결과가 한 인자로 읽힌다 | 유닉스 계열 셸 문법 기준 — Windows 명령 해석기에는 맞지 않을 수 있다(확인 필요) |
| `realpath` 가 `..` · 링크를 푼다 | 표준 라이브러리 + 운영체제 파일시스템 (구분자 `os.sep` 은 OS 마다 다르다) |
| `INSERT ... VALUES (1, "alice", ...)` 가 문자열로 들어간다 | SQLite 의 너그러운 처리 — SQL 표준에서 큰따옴표는 식별자다(확인 필요) |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 입력으로 DB 조회 | `execute(sql, (값,))` 파라미터 바인딩 | f-string · `%` · `+` 로 만든 쿼리 |
| 입력을 HTML 에 표시 | `html.escape(text, quote=True)` | 그대로 삽입 · 태그 몇 개만 지우기 |
| 입력을 URL 속성으로 사용 | 스킴 화이트리스트(`http` · `https` 등) + 이스케이프 | 이스케이프만 믿기 |
| 입력 모양 확인 | `^…$` 허용 패턴 · `int()` + 범위 | 금지 단어 목록 |
| 외부 명령 실행 | 리스트 + `shell=False` | `shell=True` + 입력 끼우기 |
| 셸이 꼭 필요 | 입력마다 `shlex.quote()` | 직접 따옴표 붙이기 |
| 입력으로 파일 열기 | `realpath` 후 `base + os.sep` 비교 | `'..' in path` 검사 |

## 핵심 문장

1. **인젝션은 데이터가 코드로 읽혀서 생긴다** — 방어는 둘을 섞지 않고 따로 넘기는 것이다(바인딩 · 리스트 인자).
2. **섞을 수밖에 없는 출력에서는 이스케이프한다** — HTML 은 `html.escape`, 셸은 `shlex.quote`.
3. **입구의 검증은 화이트리스트로 한다** — 모르는 것은 기본으로 거부된다.
4. **경로는 계산을 끝낸 뒤에 비교한다** — `realpath` 로 정규화하고 `base + os.sep` 로 확인한다.
5. **이스케이프는 문맥 하나에만 맞는다** — 같은 입력이 URL · 속성 · 본문에 들어갈 때 필요한 처리가 다르다.

## 용어 풀이

- **인젝션** — 데이터로 넣은 입력이 명령의 일부로 해석되는 취약점.
- **SQL Injection** — SQL 문에 끼운 입력이 쿼리의 뜻을 바꾸는 공격.
- **XSS** — 사용자 입력에 든 스크립트가 다른 사람 브라우저에서 실행되는 공격.
- **명령어 인젝션** — 셸 명령 문자열에 끼운 입력이 새 명령을 만드는 공격.
- **경로 탐색** — `../` 등으로 허용 디렉터리 밖 파일에 닿는 공격.
- **파라미터 바인딩** — 자리표시자를 둔 SQL 에 값을 따로 넘기는 방식.
- **자리표시자(placeholder)** — 값이 들어갈 자리를 표시하는 기호(`?` · `%s`).
- **이스케이프** — 특별한 뜻을 가진 문자를 글자 그대로의 표기로 바꾸는 것.
- **엔티티(entity)** — `&lt;` 처럼 HTML 에서 문자를 대신 나타내는 표기.
- **속성 탈출** — 속성값 안의 입력이 따옴표를 닫고 새 속성을 만드는 공격.
- **화이트리스트** — 허용할 것만 적고 나머지를 거부하는 방식.
- **블랙리스트** — 막을 것만 적고 나머지를 허용하는 방식.
- **정규화** — 여러 표기를 하나의 표준 표기로 바꾸는 것.
- **페이로드(payload)** — 공격에 쓰는 입력 문자열 그 자체.

## 더 들어가면

- 파이썬 `re` 의 `$` 는 문자열 끝에 붙은 줄바꿈 하나 앞에서도 맞는다고 알려져 있다 — `"alice\n"` 이 `^…$` 를 통과할 수 있어, 엄격하게 하려면 `re.fullmatch` 나 `\Z` 를 쓴다(확인 필요).
- `int()` 는 앞뒤 공백이나 숫자 사이의 `_` 를 받아들이는 것으로 알려져 있다 — 「정수 모양 문자열」을 엄격히 원하면 정규식을 함께 쓴다(확인 필요).
- 웹 템플릿 엔진 다수는 출력 시 자동 이스케이프를 켜 둔다 — 그래도 「안전함」 표시로 이스케이프를 끄는 기능을 사용자 입력에 쓰면 같은 문제가 생긴다(확인 필요).
- 브라우저 쪽 방어로 Content-Security-Policy 헤더가 인라인 스크립트 실행을 막는 데 쓰인다(확인 필요).
- 파이썬 3.9 이후 `pathlib.Path.is_relative_to` 로 경로 포함 여부를 검사할 수 있다(확인 필요).
- 검사한 뒤 파일을 여는 사이에 링크가 바뀌는 경쟁 조건은 이 방식만으로 막지 못한다(확인 필요).
