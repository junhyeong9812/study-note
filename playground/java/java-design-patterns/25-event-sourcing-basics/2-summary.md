## 한눈에 — 쉽게 말하면

**이벤트 소싱은 「바둑판 사진 대신 기보를 남기는 것」이다.**
바둑에서 지금 판의 모양을 사진으로 남기면 「어떻게 여기까지 왔나」는 사라진다.
대신 기보(한 수 한 수의 기록)를 남기면, 첫 수부터 다시 놓아 지금 판을 만들 수 있다.
30수째 판이 궁금하면 30수까지만 놓으면 된다.
이벤트 소싱도 똑같은 구조다.
잔액 같은 「지금 상태」를 저장하지 않고, 「입금했다 · 출금했다」 같은 변경 사실을 순서대로 저장한다.
지금 상태는 그 사실들을 처음부터 다시 적용해서 얻는다.

> **이벤트 소싱** — 상태 대신 상태를 바꾼 사건(이벤트)을 순서대로 저장하고, 재생해 상태를 복원하는 패턴.\
> 예: 잔액 720,000 을 저장하지 않고 「생성 100,000 · 입금 500,000 · …」 다섯 줄을 저장한다.

| 비유 | 실체 |
|---|---|
| 기보 전체 | `EventStore` 에 쌓인 이벤트 목록 |
| 한 수 | `DomainEvent` 하나 (`MoneyDeposited` 등) |
| 수를 두기 전 규칙 확인 | 명령 메서드(`deposit` · `withdraw` …)의 검증 |
| 지금 판의 돌 배치 | `BankAccount` 의 필드(`balance` · `isClosed` …) |
| 처음부터 다시 놓기(복기) | `BankAccount.fromHistory(…)` |
| 30수까지만 놓기 | `getEventsUntil(id, 30)` 뒤 `fromHistory` |
| 100수째 판 사진을 따로 남겨 두기 | 스냅샷 |

```text
  저장하는 것                         얻는 것
 ┌──────────────────────────┐
 │ 1. 계좌 생성  100,000    │
 │ 2. 입금     +500,000    │   재생(처음부터 적용)
 │ 3. 출금      -50,000    │ ───────────────────▶  잔액 720,000
 │ 4. 입금     +200,000    │
 │ 5. 출금      -30,000    │   3번까지만 적용
 └──────────────────────────┘ ───────────────────▶  잔액 550,000
   (추가만 한다 — 고치거나 지우지 않는다)
```

## 이 주제가 답하려는 질문

1. 상태를 저장하지 않으면 지금 상태는 어떻게 알아내나?
2. 새로 일어난 이벤트와 저장소에서 다시 읽은 이벤트는 어떻게 다르게 다루나?
3. 과거의 어느 시점 상태는 어떻게 되살리나?
4. 이벤트가 쌓여 재생이 느려지거나, 읽기 요구가 복잡해지면 어떻게 하나?

## 동작 방식

### (1) 이벤트 — 일어난 사실을 담는 불변 객체

**언제 쓰나** — 도메인에서 무언가가 바뀔 때마다, 「무엇이 바뀌었나」를 한 객체로 남긴다.

```text
new MoneyDeposited("ACC-001", 500_000, "월급")
        │
        ▼  DomainEvent 생성자가 자동으로 채움
 ┌─────────────────────────────────────────────┐
 │ eventId     = UUID 앞 8자 (예: "3f9a1c2e")   │
 │ aggregateId = "ACC-001"                      │
 │ occurredAt  = 지금 시각                      │
 │ amount = 500000.0, description = "월급"       │  ← 모두 final
 └─────────────────────────────────────────────┘
```

- 구체 이벤트는 `super(accountId)` 로 공통 정보를 부모에게 맡긴다.
- 부모 `DomainEvent` 가 이벤트 ID · 집합체 ID · 발생 시각을 생성 순간에 정한다.
- 모든 필드가 `final` 이라 만든 뒤에는 바꿀 수 없다 — 이벤트는 「이미 일어난 사실」이기 때문이다.
- 이름이 과거형(`AccountCreated` · `MoneyDeposited` · `MoneyWithdrawn` · `AccountClosed`)인 것도 같은 뜻이다.
- `getEventType()` 은 종류를 문자열로 돌려준다(역직렬화 · 라우팅에 쓰는 식별자라고 원본 주석이 설명한다).

> **집합체(aggregate)** — 이벤트가 속하는 도메인 객체 단위. 이벤트는 집합체 ID 로 묶인다.\
> 예: 계좌 `ACC-001` 하나가 집합체 하나다.

### (2) 명령 → 검증 → 이벤트 발생 → 적용

**언제 쓰나** — 바깥에서 「입금해라」 같은 요청(명령)이 들어올 때.

```text
account.deposit(500_000, "월급")
   │
   ├─ 검증: isClosed? → IllegalStateException
   │        amount <= 0? → IllegalArgumentException
   ▼
apply(new MoneyDeposited(...))
   ├─ handleEvent(event)       → balance += 500,000   (상태 변경)
   └─ uncommittedEvents.add()  → 아직 저장 안 된 이벤트 목록에 추가
```

- 명령 메서드는 먼저 규칙(도메인 불변식)을 검사한다.
- 통과해야만 이벤트를 만들어 `apply` 에 넘긴다.
- `apply` 는 두 가지를 한다 — 상태를 바꾸고(`handleEvent`), 「저장 대기」 목록에 넣는다.
- 상태를 실제로 바꾸는 코드는 `handleEvent` 한 곳뿐이다.
- 계좌 생성도 명령이다 — 정적 팩토리 `create` 가 빈 `BankAccount` 에 `AccountCreated` 를 `apply` 한다.

각 명령의 검증은 이렇다.

| 명령 | 검사 | 실패 시 |
|---|---|---|
| `create` | 없음 | — |
| `deposit` | 해지됨? · 금액 0 이하? | `IllegalStateException` · `IllegalArgumentException` |
| `withdraw` | 해지됨? · 금액 > 잔액? | 둘 다 `IllegalStateException` |
| `close` | 이미 해지됨? | `IllegalStateException` |

- `withdraw` 는 금액이 0 이하인지는 검사하지 않는다(「어디서 틀리나 3」).
- 잔액과 똑같은 금액은 `amount > balance` 가 거짓이라 출금된다.

`handleEvent` 는 Java 의 패턴 매칭 `switch` 로 이벤트 종류를 가른다(원본 주석: Java 21+).

```text
switch (event)
  case AccountCreated e  → accountId · ownerName · balance · isClosed=false 를 모두 설정
  case MoneyDeposited e  → balance += 금액
  case MoneyWithdrawn e  → balance -= 금액
  case AccountClosed e   → isClosed = true
  default                → IllegalArgumentException("알 수 없는 이벤트")
```

- `handleEvent` 에는 검증이 없다 — 이미 일어난 사실은 되묻지 않고 반영만 한다.

> **명령(command)** — 상태를 바꿔 달라는 요청. 거절될 수 있다.\
> 예: `deposit(-5, …)` 은 거절된다.

### (3) 저장 — 대기 중인 이벤트를 저장소에 덧붙이기

**언제 쓰나** — 명령을 처리한 뒤, 새 이벤트를 영구 기록으로 옮길 때.

```text
account.getUncommittedEvents()
   ├─ 대기 목록의 복사본을 만든다
   ├─ 대기 목록을 비운다
   └─ 복사본을 돌려준다
        │
        ▼ 하나씩
eventStore.append(event)
   └─ store.computeIfAbsent("ACC-001", 새 ArrayList).add(event)
```

- `getUncommittedEvents` 는 「꺼내 가기」다 — 한 번 부르면 대기 목록이 빈다.
- 그래서 같은 이벤트가 저장소에 두 번 들어가지 않는다.
- `EventStore` 는 `Map<집합체 ID, 이벤트 리스트>` 다.
- `computeIfAbsent` 는 그 ID 가 처음이면 새 리스트를 만들어 넣고, 있으면 기존 리스트를 준다.
- 저장소에는 `append` 만 있고 수정 · 삭제 메서드가 없다 — append-only 다.

> **이벤트 스토어** — 이벤트를 집합체별로 순서대로 쌓아 두는 저장소.\
> 예: `EventStore.store` 의 `"ACC-001"` 칸에 이벤트 다섯 개가 순서대로 있다.

> **append-only** — 끝에 덧붙이기만 하고 고치거나 지우지 않는 저장 방식.\
> 예: 잘못된 입금은 지우지 않고, 바로잡는 새 이벤트를 덧붙인다.

### (4) 재생 — 저장된 이벤트로 상태를 다시 만들기

**언제 쓰나** — 메모리에 객체가 없을 때(다시 시작했을 때 등) 저장소의 기록으로 현재 상태를 얻는다.

```text
history = eventStore.getEvents("ACC-001")      (없는 ID 면 빈 목록)
        │
        ▼
BankAccount.fromHistory(history)
   ├─ new BankAccount()               (모든 필드가 기본값)
   └─ for 이벤트 : history
          account.handleEvent(이벤트)  ← apply 가 아니다
        │
        ▼
상태가 원본과 같은 BankAccount  (uncommittedEvents 는 비어 있음)
```

- 재생은 `apply` 가 아니라 `handleEvent` 만 부른다.
- 이미 저장된 이벤트를 다시 「저장 대기」에 넣으면, 다음 저장 때 중복으로 쌓이기 때문이다.
- 재생은 명령의 검증도 거치지 않는다 — 사실을 그대로 다시 놓을 뿐이다.
- 새 이벤트 처리와 재생이 같은 `handleEvent` 를 쓰므로, 두 길의 결과가 어긋나지 않는다.
- 원본 데모는 복원한 계좌와 원래 계좌의 잔액을 `==` 로 비교해 같은지 확인한다.

> **재생(replay)** — 저장된 이벤트를 처음부터 순서대로 상태에 적용하는 일.\
> 예: 다섯 이벤트를 차례로 적용하면 잔액이 다시 720,000 이 된다.

### (5) 시간 여행 — 앞에서 N 개만 재생하기

**언제 쓰나** — 「세 번째 거래 직후 잔액은 얼마였나?」처럼 과거 시점을 볼 때.

```text
getEventsUntil("ACC-001", 3)
   └─ events.subList(0, Math.min(3, events.size()))   → 앞 3개
        │
        ▼
fromHistory(앞 3개)  →  생성 100,000 + 500,000 - 50,000 = 550,000
```

- 앞에서 N 개를 잘라 재생하면 N 번째 이벤트 직후의 상태가 나온다.
- `Math.min` 덕분에 N 이 이벤트 수보다 커도 예외 없이 전부를 돌려준다.
- N 이 0 이면 빈 목록이고, 재생하면 필드가 모두 기본값인 계좌가 된다(`balance` 0, `accountId` `null`).
- 원본 데모는 N 을 1 부터 이벤트 수까지 늘리며 잔액을 찍는다.

> **시간 여행** — 이벤트를 특정 지점까지만 재생해 그 시점의 상태를 되살리는 일.\
> 예: 이벤트 2개 재생 → 잔액 600,000.

### (6) 감사 추적 · 스냅샷 · CQRS

**언제 쓰나** — 이력을 보여 줘야 할 때, 이벤트가 너무 많아질 때, 읽기와 쓰기 요구가 달라질 때.

```text
감사 추적:  history 를 그대로 훑으면 [시각] 이벤트 (id=…) 가 순서대로 나온다

스냅샷:     이벤트 1 … 1000 │ 이벤트 1001 … 1050
            └ 1000 시점 상태를 따로 저장 ┘   └ 이것만 재생 ┘

CQRS:       명령 ──▶ 집합체 ──▶ 이벤트 저장소   (쓰기 모델)
                                   │ 이벤트
                                   ▼
            조회 ◀── 읽기용 모델(잔액표 등)        (읽기 모델)
```

- 이벤트 목록 자체가 「언제 · 무엇이 · 어떤 ID 로」 일어났는지의 완전한 기록이다 — 감사 로그를 따로 만들 필요가 없다.
- 원본 데모의 마지막 단계가 시각(`HH:mm:ss.SSS`) · 이벤트 · 이벤트 ID 를 순서대로 찍는 감사 로그다.
- 이벤트가 많아지면 매번 처음부터 재생하는 시간이 길어진다.
- 그래서 어느 시점의 상태를 스냅샷으로 저장해 두고, 그 뒤의 이벤트만 재생한다(원본 팁).
- 원본 데모에서 시간 여행 루프의 변수 이름이 `snapshot` 이지만, 저장해 두는 스냅샷이 아니라 그때그때 재생한 결과다.
- CQRS 와 함께 쓰면 쓰기(이벤트를 만드는 쪽)와 읽기(보여 주는 쪽)의 모델을 나눌 수 있다(원본 팁).
- 이벤트 저장소가 쓰기 쪽이 되고, 읽기 쪽은 이벤트를 받아 조회하기 좋은 꼴로 따로 만들어 둔다.

> **감사 추적(audit trail)** — 누가 언제 무엇을 바꿨는지 되짚을 수 있는 기록.\
> 예: 「[12:00:01.234] 출금 -50,000 (점심 식사)」 한 줄.

> **스냅샷** — 어느 시점까지 재생한 상태를 따로 저장해 둔 것. 재생을 그 지점부터 시작하게 해 준다.\
> 예: 이벤트 1,000 개째의 잔액을 저장하고 1,001 번째부터 재생.

> **CQRS** — 명령(쓰기)과 조회(읽기)를 다른 모델로 나누는 설계.\
> 예: 쓰기는 이벤트 저장소, 읽기는 「계좌별 현재 잔액」 표.

## 문법 — 형태와 규칙

```java
// 최소 예제 — 이벤트 하나, 집합체 하나
record Added(int n) {}                         // 이벤트: 불변 · 과거형
class Counter {
    private int total;
    private final List<Added> pending = new ArrayList<>();
    void add(int n) {                          // 명령: 검증 → 이벤트
        if (n <= 0) throw new IllegalArgumentException();
        apply(new Added(n));
    }
    private void apply(Added e) { handle(e); pending.add(e); }
    private void handle(Added e) { total += e.n(); }   // 상태 변경은 여기서만
    static Counter replay(List<Added> history) {
        Counter c = new Counter();
        history.forEach(c::handle);            // 재생: 검증 · 대기 목록 없이 적용만
        return c;
    }
}
```

- 이벤트는 불변으로 만든다 — 필드를 `final` 로 두거나 `record` 를 쓴다.
- 이벤트 이름은 「이미 일어난 일」이 드러나게 과거형으로 짓는다.
- 상태를 바꾸는 코드는 이벤트 핸들러(`handleEvent` · `handle`) 한 곳에만 둔다.
- 명령은 「검증 → 이벤트 생성 → `apply`」 순서를 지킨다.
- `apply` = 핸들러 호출 + 저장 대기 목록에 추가.
- 재생 = 빈 객체에 핸들러만 차례로 호출.
- 패턴 매칭 `switch` 의 꼴은 `case 타입 변수 -> 문장;` 또는 `case 타입 변수 -> { … }` 다.
- `DomainEvent` 는 하위 타입이 정해져 있지 않은 추상 클래스라, 모든 경우를 덮으려면 `default` 가지가 필요하다.
- 원본은 이 `default` 에서 알 수 없는 이벤트를 `IllegalArgumentException` 으로 거절한다.

> **패턴 매칭 switch** — `case` 에 타입과 변수 이름을 써서, 타입이 맞으면 그 변수로 꺼내 쓰는 `switch`.\
> 예: `case MoneyDeposited e -> balance += e.getAmount();`

## 어디서 틀리나

### 1. 재생에서 `apply` 를 부른다

- `fromHistory` 가 `handleEvent` 대신 `apply` 를 부르면, 저장된 이벤트가 다시 저장 대기 목록에 들어간다.
- 다음에 `getUncommittedEvents` 로 저장하면 같은 이벤트가 저장소에 두 번 쌓인다.
- 재생한 뒤 잔액이 두 배로 늘어나는 식의 오류가 그다음 재생에서 드러난다.

### 2. 핸들러에 검증을 넣는다

- 검증은 명령에서 한다 — 핸들러는 사실을 반영만 한다.
- 핸들러가 「잔액 부족」 같은 검사를 하면, 규칙이 바뀐 뒤 옛 이벤트를 재생할 때 예외가 나서 복원이 깨질 수 있다.

### 3. `withdraw` 는 음수 금액을 막지 않는다

- `deposit` 은 `amount <= 0` 을 거절하지만, `withdraw` 는 해지 여부와 잔액 초과만 본다.
- `withdraw(-3_000, …)` 은 `-3,000 > 잔액` 이 거짓이라 통과한다.
- 핸들러가 `balance -= -3000` 을 하므로 잔액이 오히려 3,000 늘어난다.
- 그리고 그 이벤트는 저장되면 지울 수 없는 사실이 된다 — 명령 검증이 빠지면 잘못된 사실이 영구히 남는다.

### 4. 「추가만 가능」은 이 코드에서 약속일 뿐이다

- 원본 팁: 이벤트는 불변이며 추가만 가능하다(수정 · 삭제 불가).
- 이벤트 객체 자체는 `final` 필드라 불변이다.
- 하지만 `getEvents` 는 저장소 안의 리스트를 그대로 돌려준다 — 받은 쪽이 `remove` · `clear` 를 부르면 저장소가 바뀐다.
- `getEventsUntil` 이 돌려주는 `subList` 도 원래 리스트의 뷰라, 고치면 원본에 반영된다.
- 저장소가 진짜로 append-only 이려면 바꿀 수 없는 목록(복사본 등)을 돌려줘야 한다(원본에 근거 없음 — 추론).
- 원래 없는 ID 에 대해 돌려주는 `List.of()` 는 바꿀 수 없는 목록이다.

### 5. `getUncommittedEvents` 는 두 번 부르면 두 번째가 비어 있다

- 이 메서드는 조회가 아니라 「꺼내고 비우기」다.
- 로그를 찍으려고 한 번, 저장하려고 또 한 번 부르면 저장할 이벤트가 없다.

### 6. `AccountCreated` 없이 재생한다

- `fromHistory` 는 첫 이벤트가 생성 이벤트인지 검사하지 않는다.
- 입금 이벤트만 재생하면 `accountId` · `ownerName` 은 `null` 이고 잔액만 더해진 계좌가 나온다.
- 빈 목록을 재생해도 예외 없이 기본값 계좌가 나온다.

### 7. 이벤트 수가 늘면 재생이 느려진다 — 스냅샷

- 재생 시간은 이벤트 수에 비례해 늘어난다.
- 원본 팁대로 스냅샷을 저장해 그 뒤만 재생한다.
- 원본 데모의 변수 `snapshot` 은 이름만 그렇고 실제 스냅샷 저장은 하지 않는다.

### 8. 패턴 자체의 단점

- 원본 주석: 복잡도가 늘고, 이벤트 스키마 진화가 어렵다.
- 이벤트는 고칠 수 없으므로, 이벤트 클래스의 필드를 바꾸면 옛 꼴로 저장된 이벤트도 계속 읽을 수 있어야 한다.

### 9. 돈을 `double` 로 다룬다

- 데모 값은 모두 정수라 `double` 덧셈 · 뺄셈이 정확하고, `==` 비교도 성립한다.
- 소수 금액이 섞이면 부동소수점 오차가 생길 수 있고, `==` 비교가 깨질 수 있다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| `switch` 에 `case 타입 변수 ->` 를 쓸 수 있다 | Java 언어 — 원본 주석은 Java 21+ 라고 적는다 |
| `DomainEvent` 를 덮는 패턴 `switch` 에 `default` 가 필요하다 | Java 언어 규칙(봉인되지 않은 타입이라 모든 경우를 덮어야 함) |
| `eventId` 는 이벤트마다 다르다 | 보장 아님 — 무작위 UUID 의 앞 8자만 써서 겹칠 가능성이 0 은 아니다(이 코드의 선택) |
| 같은 집합체 안 이벤트 순서가 유지된다 | `ArrayList` 의 명세(덧붙인 순서 유지) |
| `occurredAt` 이 이벤트마다 다르다 | 보장 아님 — `LocalDateTime.now()` 의 정밀도는 시스템 시계에 달려 있어 연달아 만든 이벤트가 같은 시각을 가질 수 있다(확인 필요) |
| 이벤트는 수정 · 삭제되지 않는다 | 패턴의 약속 — 이 코드는 수정 메서드를 두지 않는 관례로만 지키고, `getEvents` 가 내부 리스트를 내준다 |
| 복원 잔액과 원래 잔액이 `==` 로 같다 | 이 데모의 값(정수 금액)에서 성립 — `double` 일반에 대한 보장은 아니다 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 모든 변경 이력 · 감사 추적이 필수다(금융 거래 등) | 이벤트 소싱 | 상태만 덮어쓰는 저장 |
| 「그때 상태는 어땠나」를 자주 묻는다 | 이벤트 + `getEventsUntil` 식 부분 재생 | 현재 값만 남는 테이블 |
| 이벤트가 매우 많아 재생이 느리다 | 스냅샷 + 그 뒤 이벤트만 재생 | 매번 처음부터 전부 재생 |
| 읽기 화면이 쓰기 모델과 모양이 많이 다르다 | CQRS 로 읽기 모델 분리 | 이벤트 목록을 매 조회마다 직접 훑기 |
| 이력이 필요 없는 단순 CRUD | 상태 저장 | 이벤트 소싱(복잡도만 는다) |
| 데이터 구조가 자주 바뀐다 | 스키마 진화 계획부터 | 아무 대비 없이 이벤트 소싱 |

## 핵심 문장

1. **상태는 저장하지 않고 이벤트에서 파생한다** — 지금 상태 = 이벤트를 처음부터 순서대로 적용한 결과다.
2. **명령은 검증하고 이벤트를 만들며, 핸들러는 검증 없이 반영만 한다** — 상태 변경 코드는 핸들러 한 곳이다.
3. **새 이벤트는 `apply`(반영 + 저장 대기), 재생은 `handleEvent`(반영만)** — 이 구분이 중복 저장을 막는다.
4. **이벤트는 불변 · 추가만** — 그래서 이벤트 목록이 그대로 감사 추적이 되고, 앞 N 개 재생이 시간 여행이 된다.
5. **이벤트가 많으면 스냅샷, 읽기가 복잡하면 CQRS** 를 곁들인다.

## 관련 자료

- `command` — 같은 사이트의 관련 항목(이 폴더에 없어 링크를 걸지 않았다)
- `observer` — 같은 사이트의 관련 항목(이 폴더에 없어 링크를 걸지 않았다)
- `state` — 같은 사이트의 관련 항목(이 폴더에 없어 링크를 걸지 않았다)

## 용어 풀이

- **이벤트 소싱** — 상태 대신 상태 변경 이벤트를 순서대로 저장하고 재생해 상태를 복원하는 패턴.
- **이벤트(도메인 이벤트)** — 도메인에서 이미 일어난 사실 하나를 담은 불변 객체.
- **집합체(aggregate)** — 이벤트가 속하는 도메인 객체 단위. 여기서는 계좌 하나.
- **명령(command)** — 상태 변경 요청. 검증에 걸리면 거절된다.
- **이벤트 핸들러** — 이벤트 하나를 받아 상태를 바꾸는 코드. 여기서는 `handleEvent`.
- **uncommitted 이벤트** — 발생했지만 아직 저장소에 넣지 않은 이벤트.
- **이벤트 스토어** — 집합체별로 이벤트를 순서대로 쌓는 저장소.
- **append-only** — 덧붙이기만 하고 수정 · 삭제하지 않는 방식.
- **재생(replay)** — 저장된 이벤트를 순서대로 상태에 적용하는 일.
- **시간 여행** — 앞에서 N 개만 재생해 과거 시점 상태를 되살리는 일.
- **감사 추적** — 언제 무엇이 바뀌었는지 되짚을 수 있는 기록.
- **스냅샷** — 어느 시점까지의 상태를 따로 저장해 재생 출발점으로 쓰는 것.
- **CQRS** — 쓰기 모델과 읽기 모델을 나누는 설계.
- **도메인 불변식** — 도메인이 언제나 지켜야 하는 규칙. 예: 잔액보다 많이 출금할 수 없다.
- **정적 팩토리** — 생성자 대신 객체를 만들어 돌려주는 `static` 메서드. 여기서는 `create`.
- **패턴 매칭 switch** — `case 타입 변수 ->` 로 타입을 확인하고 변수로 꺼내는 `switch`.

## 더 들어가면

- 여러 요청이 같은 집합체에 동시에 이벤트를 덧붙이면 충돌한다. 흔히 집합체마다 버전 번호를 두고 「기대한 버전일 때만 덧붙이기」로 막는다(낙관적 동시성). (확인 필요)
- `DomainEvent` 를 `sealed` 로 선언하고 허용 하위 타입을 나열하면, 패턴 `switch` 에서 `default` 없이도 모든 경우를 덮었는지 컴파일러가 확인해 준다. (확인 필요)
- 이벤트 스키마가 바뀔 때, 옛 꼴 이벤트를 읽는 순간 새 꼴로 바꿔 주는 「업캐스팅」 기법을 쓰기도 한다. (확인 필요)
- CQRS 의 읽기 모델은 흔히 「프로젝션」이라 부르며, 이벤트를 구독해 갱신한다. 그래서 쓰기 직후 읽기에 바로 반영되지 않을 수 있다(최종 일관성). (확인 필요)
- 금액은 `double` 보다 `BigDecimal` 이나 정수(원 단위 `long`)로 다루는 것이 일반적이다. (확인 필요)
- 상태를 바꾼 뒤 저장에 실패하면 메모리 상태와 저장소가 어긋난다. 저장에 성공한 뒤에만 객체를 계속 쓰거나, 실패 시 저장소에서 다시 재생하는 식으로 다룬다. (확인 필요)
