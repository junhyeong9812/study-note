## 한눈에 — 쉽게 말하면

**스텝 빌더는 「한 칸씩만 열리는 문 복도」다.**
첫 문을 지나야 둘째 문의 손잡이가 손에 들어오고, 둘째 문을 지나야 셋째 문의 손잡이가 들어온다.
필수 문을 다 지나면 마지막 방에 닿는다.
그 방에는 서랍(선택 값)이 몇 개 있어 아무 순서로 열어도 되고, 하나도 안 열어도 된다.
방에서 출구로 나가면 완성품이 나온다.
스텝 빌더도 똑같은 구조다.
메서드를 하나 부를 때마다 「다음에 부를 수 있는 메서드만 가진 타입」이 돌아온다.

| 비유 | 실체 |
|---|---|
| 문 하나 | 단계 인터페이스 하나 (`FromStep` · `ToStep` · `SubjectStep`) |
| 손에 쥔 손잡이 | 그 인터페이스에 선언된 메서드 |
| 문을 지나기 | 메서드 호출 → 다음 단계 인터페이스를 반환 |
| 마지막 방 | `OptionalStep` |
| 서랍 | 선택 값 메서드 `body()` · `html()` · `cc()` |
| 출구 | `build()` |
| 복도 전체(사실은 한 건물) | 모든 인터페이스를 구현한 `Builder` 인스턴스 하나 |

```text
builder() ──► [FromStep] ──from()──► [ToStep] ──to()──► [SubjectStep] ──subject()──► [OptionalStep] ──build()──► Email
                                                                                       │      ▲
                                                                                       └──────┘
                                                                              body() / html() / cc()
```

## 이 주제가 답하려는 질문

1. 필수 값을 빠뜨리거나 순서를 어긴 빌더 호출을, 실행하기 전에 컴파일러가 막게 하려면 어떻게 하나?
2. 실제 객체는 하나인데 호출자가 단계마다 다른 메서드만 보게 되는 까닭은 무엇인가?
3. 선택 값은 어떻게 아무 순서로, 생략도 가능하게 받나?
4. 이 안전성은 어디까지 믿을 수 있고, 어디서 새나?

## 동작 방식

### (1) 반환 타입이 다음 단계를 고른다

**언제 쓰나** — 필수 값이 여럿이고 「이것을 정해야 다음 것을 정할 수 있다」는 차례가 있을 때 쓴다.
원본의 예는 이메일이고, 반드시 `from` → `to` → `subject` 차례로 정해야 한다.

```text
식                               식의 정적 타입        이 시점에 부를 수 있는 메서드
──────────────────────────────── ─────────────────── ──────────────────────────────
Email.builder()                  FromStep            from
  .from("sender@example.com")    ToStep              to
  .to("receiver@example.com")    SubjectStep         subject
  .subject("안녕하세요")            OptionalStep        body, html, cc, build
  .build()                       Email               (완성품)
```

- `Email.builder()` 는 `FromStep` 으로 선언되어 있어서, 호출자가 처음 받는 것은 `from()` 하나뿐이다.
- `from()` 의 반환 타입이 `ToStep` 이라서, 그 다음 점(`.`) 뒤에는 `to()` 만 쓸 수 있다.
- `to()` 는 `SubjectStep` 을, `subject()` 는 `OptionalStep` 을 돌려준다.
- `build()` 는 `OptionalStep` 에만 있으므로, 필수 세 단계를 다 지나야 비로소 부를 수 있다.

> **정적 타입** — 컴파일러가 코드만 보고 아는 변수 · 식의 타입이다. 호출할 수 있는 메서드는 이 타입이 정한다.\
> 예: `Email.builder()` 의 정적 타입은 `FromStep` 이다.

> **스텝 빌더(Step Builder)** — 단계마다 다른 인터페이스를 반환해 필수 값의 설정과 차례를 컴파일 타임에 강제하는 빌더다.\
> 예: `from()` 이 `ToStep` 을 반환하므로 `from()` 다음에는 `to()` 만 부를 수 있다.

### (2) 한 인스턴스, 네 얼굴 — `return this`

**언제 쓰나** — 단계마다 객체를 새로 만들지 않고, 하나의 빌더가 값을 모아 가게 할 때 쓴다.

```text
              new Builder()  ← 실제 객체는 이것 하나
             ┌─────────────────────────────────────────┐
             │ implements FromStep, ToStep,            │
             │            SubjectStep, OptionalStep    │
             │ 필드: from, to, subject,                 │
             │       body="", html=false, cc=null      │
             └─────────────────────────────────────────┘
 from(x) : this.from = x; return this;   → 같은 객체를 ToStep 으로 내보냄
 to(x)   : this.to = x;   return this;   → 같은 객체를 SubjectStep 으로 내보냄
 subject : ...            return this;   → 같은 객체를 OptionalStep 으로 내보냄
```

- `Builder` 하나가 네 인터페이스를 모두 구현한다.
- 각 메서드는 필드에 값을 적고 `this` 를 돌려준다.
- 돌려주는 객체는 늘 같지만, 메서드의 **선언된 반환 타입**이 단계마다 달라서 호출자 쪽 정적 타입이 바뀐다.
- `Builder` 는 `private static class` 라서 바깥에서는 이 클래스 이름을 쓸 수도, `new` 로 만들 수도 없다.
- 그래서 바깥이 손에 쥘 수 있는 것은 `Email.builder()` 가 돌려주는 `FromStep` 뿐이다.

> **`return this` 체이닝** — 메서드가 자기 자신을 돌려주어 호출을 점으로 이어 붙이게 하는 기법이다.\
> 예: `.body(...).html(true).cc(...)`.

### (3) 선택 단계는 자기 자신을 반환한다

**언제 쓰나** — 있어도 되고 없어도 되는 값, 순서가 상관없는 값을 받을 때 쓴다.

```text
[OptionalStep] ──body()──► [OptionalStep] ──html()──► [OptionalStep] ──build()──► Email
       └──────────────────────────build()────────────────────────────────────────► Email
```

- `body()` · `html()` · `cc()` 는 모두 `OptionalStep` 을 반환하므로 몇 번이든, 어떤 순서로든 부를 수 있다.
- `build()` 도 같은 인터페이스에 있어 언제든 끝낼 수 있다.
- 하나도 안 부르면 필드 기본값이 그대로 들어간다: `body = ""`, `html = false`, `cc = null`.
- `toString()` 은 `String.format` 의 `%s` 로 값을 넣는데, `%s` 에 `null` 을 주면 글자 `null` 이 들어간다.
- 그래서 선택 값을 다 생략한 이메일은 문자열로 `body=''`, `html=false`, `cc='null'` 꼴이 된다.

### (4) 불변 객체로 마무리한다

**언제 쓰나** — 다 만든 뒤에는 값이 바뀌지 않는 객체를 원할 때 쓴다.

```text
Builder(가변, 값을 모으는 중) ──build()──► new Email(this) ──► Email(불변, final 필드 6개)
                                              │
                                              └ 생성자 안에서 builder 의 필드를 하나씩 복사
```

- `Email` 의 필드 여섯 개는 모두 `private final` 이다.
- 생성자 `Email(Builder builder)` 는 `private` 이라 바깥에서 `new Email(...)` 을 쓸 수 없다.
- 생성자는 빌더의 필드 값을 `Email` 의 필드로 복사한다.
- `build()` 에는 필수 값 검사가 없다 — 필수 단계를 다 지나야만 `build()` 를 부를 수 있으니, 호출 차례는 이미 인터페이스 체인이 보장한다는 설계다.

> **불변 객체** — 만든 뒤 상태가 바뀌지 않는 객체다.\
> 예: `final` 필드만 있고 setter 가 없는 `Email`.

### (5) 잘못된 차례는 컴파일 에러가 된다

**언제 쓰나** — 사용자 실수를 실행 전에 잡고 싶을 때, 이 단계가 패턴의 핵심 가치다.

```text
Email.builder().to("x")                      FromStep 에 to() 없음     → 컴파일 에러
Email.builder().from("x").subject("y")       ToStep 에 subject() 없음  → 컴파일 에러
Email.builder().from("x").to("y").build()    SubjectStep 에 build() 없음 → 컴파일 에러
```

- 세 줄 모두 「그 정적 타입에 그런 메서드가 없다」는 이유로 컴파일되지 않는다.
- 일반 빌더라면 같은 실수가 실행 중 `build()` 의 검사(예외)로 드러나거나, 검사가 없으면 그냥 빈 값으로 통과한다.
- 원본 팁은 이렇게 컴파일 타임에 잡는 편이 런타임 예외보다 훨씬 안전하다고 말한다.
- IDE 자동완성도 정적 타입을 따르므로, 점을 찍으면 그 단계에서 부를 수 있는 메서드만 뜬다(원본 주석의 설명).

> **컴파일 타임 검증** — 프로그램을 돌리기 전, 컴파일러가 코드만 보고 오류를 찾아내는 것이다.\
> 예: `SubjectStep` 에 없는 `build()` 를 부르면 컴파일이 실패한다.

## 문법 — 형태와 규칙

필수 값 둘(`start` → `end`)과 선택 값 하나(`label`)를 가진 최소 예제다.

```java
class Range {
    private final int start, end; private final String label;
    private Range(B b) { start = b.start; end = b.end; label = b.label; }

    public interface StartStep { EndStep start(int s); }
    public interface EndStep   { Optional end(int e); }
    public interface Optional  { Optional label(String l); Range build(); }

    public static StartStep builder() { return new B(); }

    private static class B implements StartStep, EndStep, Optional {
        int start, end; String label = "";
        public EndStep  start(int s)    { start = s; return this; }
        public Optional end(int e)      { end = e;   return this; }
        public Optional label(String l) { label = l; return this; }
        public Range build()            { return new Range(this); }
    }
}
```

- 필수 단계마다 인터페이스를 하나씩 만들고, 메서드 하나를 둔다. 그 메서드의 반환 타입은 **다음 단계의 인터페이스**다.
- 마지막 필수 단계는 선택 단계 인터페이스를 반환한다.
- 선택 단계 인터페이스의 메서드는 **자기 인터페이스**를 반환하고, 여기에 `build()` 를 함께 둔다.
- 진입점 `builder()` 는 **첫 단계 인터페이스 타입**으로 선언하고 빌더 객체를 돌려준다.
- 빌더 클래스 하나가 모든 단계 인터페이스를 `implements` 하고, 각 메서드는 값을 적은 뒤 `this` 를 돌려준다.
- 빌더 클래스는 `private` 으로 숨겨, 바깥이 단계 인터페이스로만 다루게 한다.
- 만들 객체의 생성자는 `private` 으로 두고 빌더만 부르게 한다.
- 선택 필드의 기본값은 빌더 필드의 초기값으로 정한다.

## 어디서 틀리나

### 1. 인터페이스가 많아져 코드가 길어진다

원본 팁이 꼽는 단점이다.
필수 값이 n 개면 필수 단계 인터페이스 n 개에 선택 단계 하나가 더해진다 — 원본은 필수 3개라 인터페이스가 4개다.
필수 값이 늘수록 인터페이스와 메서드 선언이 함께 는다(보일러플레이트).

### 2. 필수 값이 적거나 차례가 의미 없으면 과하다

원본 팁은 「필수 파라미터가 3개 이상이고 설정 순서가 중요할 때」 유용하다고 한다.
필수 값이 하나둘이면 생성자 인자로 받는 편이 짧다.

### 3. Lombok `@Builder` 로는 만들 수 없다

원본 팁에 따르면 Lombok 의 `@Builder` 는 스텝 빌더를 지원하지 않으므로 직접 구현해야 한다.

### 4. 호출은 강제하지만 값은 검사하지 않는다

`from(null)` 이나 `to("")` 도 컴파일된다 — 인터페이스 체인이 강제하는 것은 「메서드를 불렀다」는 사실뿐이다.
`build()` 에 검증이 없으므로 `null` 이 그대로 `Email` 에 들어간다.
값의 형식(예: 이메일 주소 꼴)까지 지키려면 단계 메서드나 생성자에서 따로 검사해야 한다. (원본에 근거 없음 — 추론)

### 5. 중간 단계를 변수에 담아 다시 쓰면 같은 빌더를 공유한다

`Email.OptionalStep base = Email.builder().from(..).to(..).subject(..);` 처럼 담아 두고 `base` 에서 두 번 `build()` 하면, 두 호출은 **같은 `Builder` 객체**를 건드린다.
앞에서 `body("first")` 를 정한 뒤 다음 호출에서 `html(true)` 만 바꾸면, 두 번째 `Email` 에도 `body` 가 `"first"` 로 남아 있다.
다만 첫 번째 `Email` 은 `build()` 때 값을 복사해 갔고 `final` 이라, 그 뒤 빌더가 바뀌어도 영향받지 않는다. (원본에 근거 없음 — 추론)

### 6. 강제 캐스팅으로 차례를 건너뛸 수 있다

실제 객체는 네 인터페이스를 모두 구현하므로, `((Email.SubjectStep) Email.builder()).subject("y")` 처럼 인터페이스로 캐스팅하면 컴파일도 되고 실행도 된다.
그러면 `from` · `to` 가 `null` 인 채로 `build()` 까지 갈 수 있다.
정적 타입 검사로 얻은 안전이라, 정적 타입을 일부러 바꾸는 캐스팅 앞에서는 막지 못한다. (원본에 근거 없음 — 추론)

### 7. 원본 주석의 예상 줄은 빈 줄 하나를 빠뜨린 것으로 보인다

원본의 주장: 마지막 줄 주석에 `타입 안전: 잘못된 순서는 컴파일 타임에 차단됨` 이 바로 이어져 찍힌다고 적혀 있다.
왜 의심스러운가: 코드는 `"\n타입 안전: ..."` 처럼 줄바꿈 문자로 시작하는 문자열을 `println` 하므로, 그 앞에 빈 줄이 하나 생길 것이다. (원본에 근거 없음 — 추론)

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| 정적 타입에 없는 메서드를 부르면 컴파일 에러 | Java 언어(컴파일러의 타입 검사) |
| `private` 클래스 · 생성자는 바깥에서 쓸 수 없다 | Java 언어(접근 제어) |
| 필수 세 단계를 거쳐야 `build()` 에 닿는다 | 이 코드의 설계 — 캐스팅을 쓰지 않는다는 전제에서만 |
| `%s` 에 `null` 을 주면 글자 `null` 이 들어간다 | Java 표준 라이브러리(`String.format` 의 명세) |
| Lombok `@Builder` 는 스텝 빌더를 지원하지 않는다 | Lombok 라이브러리 — 버전에 따라 다를 수 있다 (확인 필요) |
| 자동완성이 단계별로 다음 메서드만 보여 준다 | IDE 의 구현 — 언어가 정한 것이 아니다 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 필수 값 3개 이상, 정하는 차례가 중요 | 스텝 빌더 | 모든 메서드가 같은 빌더를 반환하는 일반 빌더(빠뜨림을 못 막음) |
| 필수 값 1~2개 | 생성자 인자 또는 일반 빌더 | 스텝 빌더(인터페이스만 늘어남) |
| 선택 값이 많고 필수 값은 거의 없음 | 일반 빌더 | 스텝 빌더 |
| Lombok 으로 빌더를 자동 생성하고 싶음 | `@Builder`(일반 빌더) | 스텝 빌더를 기대하는 것 — 직접 구현해야 함 |
| 값의 내용(형식 · `null` 아님)까지 지켜야 함 | 스텝 빌더 + 메서드 · 생성자 안의 검사 | 스텝 빌더만 믿는 것 |

## 핵심 문장

1. **단계마다 반환 타입을 바꿔 다음에 부를 메서드를 좁힌다** — 그래서 차례를 어긴 호출은 컴파일되지 않는다.
2. **실제 객체는 모든 단계를 구현한 빌더 하나이고, `return this` 로 같은 객체를 다른 얼굴로 내보낸다.**
3. **선택 단계는 자기 자신을 반환하고 `build()` 를 함께 가진다** — 아무 순서로, 생략도 하며 끝낼 수 있다.
4. **강제하는 것은 「불렀다」는 사실까지다** — `null` · 형식 · 캐스팅 우회는 막지 못한다.
5. **대가는 인터페이스 수** — 필수 값이 3개 이상이고 차례가 중요할 때 값어치를 한다.

## 용어 풀이

- **빌더 패턴** — 객체를 만드는 과정을 별도 객체(빌더)에 맡겨 값을 하나씩 정한 뒤 `build()` 로 완성하는 패턴이다.
- **스텝 빌더** — 단계마다 다른 인터페이스를 반환해 필수 값과 차례를 컴파일 타임에 강제하는 빌더다.
- **단계 인터페이스** — 한 단계에서 부를 수 있는 메서드만 선언한 인터페이스다(`FromStep` 등).
- **정적 타입** — 컴파일러가 코드만 보고 아는 식의 타입으로, 부를 수 있는 메서드를 정한다.
- **`return this` 체이닝** — 메서드가 자기 객체를 돌려주어 호출을 점으로 잇게 하는 기법이다.
- **컴파일 타임 검증** — 실행 전에 컴파일러가 오류를 잡는 것이다.
- **런타임 예외** — 프로그램이 도는 중에 던져지는 예외다.
- **불변 객체** — 만든 뒤 상태가 바뀌지 않는 객체다.
- **보일러플레이트** — 기능보다 형식 때문에 되풀이해 써야 하는 코드다.
- **캐스팅** — 식의 정적 타입을 다른 타입으로 바꿔 보도록 컴파일러에 지시하는 것이다.

## 더 들어가면

- 키워드의 「제네릭 빌더」는 단계를 인터페이스 대신 타입 매개변수(예: 필드마다 「설정됨/안 됨」을 나타내는 타입)로 표시해, 차례 없이 필수 값만 강제하는 변형을 가리키기도 한다 (확인 필요).
- 필수 값 사이에 차례가 꼭 필요 없다면, 단계 인터페이스 대신 필수 값을 `builder(from, to, subject)` 인자로 받고 선택 값만 체이닝하는 절충도 쓰인다 (확인 필요).
- Kotlin 처럼 이름 붙은 인자와 기본값이 있는 언어에서는 빌더 자체가 덜 필요하다는 견해가 있다 (확인 필요).
- 레코드(`record`)로 불변 데이터 클래스를 짧게 쓰고, 빌더는 그 앞단에만 두는 조합도 가능하다 (확인 필요).
