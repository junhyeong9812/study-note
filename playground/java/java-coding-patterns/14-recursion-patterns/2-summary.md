## 한눈에 — 쉽게 말하면

**재귀는 「마트료시카 인형 열기」다.**
큰 인형을 열면 조금 작은 인형이 나오고, 그것을 열면 더 작은 인형이 나온다.
더 열 수 없는 가장 작은 인형에 닿으면 멈추고, 그때부터 거꾸로 하나씩 닫으며 올라온다.
재귀 함수도 똑같은 구조다.
함수는 자기보다 조금 작은 문제로 자신을 부르고, 더 쪼갤 수 없는 문제에서 멈춘 뒤, 돌아오면서 결과를 합친다.

| 비유 | 실체 |
|---|---|
| 인형 하나를 연다 | 자기 자신을 더 작은 인자로 부른다(재귀 호출) |
| 가장 작은 인형 | 기저 조건(`if (n <= 1) return 1;`) |
| 열어 둔 인형들이 책상에 쌓인다 | 호출마다 스택 프레임이 쌓인다 |
| 거꾸로 닫으며 올라온다 | 반환값을 받아 `n * …` 처럼 결과를 합친다 |
| 책상이 꽉 찬다 | 스택이 넘친다(`StackOverflowError`) |

```text
factorial(3)
  └─ 3 * factorial(2)
          └─ 2 * factorial(1)
                  └─ 1        ← 기저 조건, 여기서 멈춘다
          ← 2 * 1 = 2
  ← 3 * 2 = 6
```

## 이 주제가 답하려는 질문

1. 재귀 함수는 어떤 뼈대로 쓰나 — 어디서 멈추고, 어떻게 작은 답을 모아 큰 답을 만드나?
2. 같은 문제를 더 빨리 푸는 재귀의 모양(분할 정복 · 메모이제이션)은 무엇이고, 왜 빨라지나?
3. 재귀가 깊어지면 Java 에서 무엇이 깨지고, 어떻게 피하나(꼬리 재귀 · 반복문 변환 · `-Xss`)?

## 동작 방식

### (1) 기본 재귀 — 팩토리얼

**언제 쓰나** — 문제의 정의가 이미 「자기보다 작은 같은 문제」로 쓰여 있을 때 쓴다.
`n! = n × (n−1)!` 이 그 예다.

> **재귀** — 함수가 자기 자신을 다시 부르는 것.\
> 예: `factorial(n)` 안에서 `factorial(n - 1)` 을 부른다.

> **기저 조건** — 더 부르지 않고 바로 답을 돌려주는, 재귀를 멈추는 조건.\
> 예: `if (n <= 1) return 1;`

```text
입력 코드                         무엇이 일어나나                     결과
static long factorial(int n) {
  if (n <= 1) return 1;          n 이 1 이하면 멈춘다                1
  return n * factorial(n - 1);   n 을 쥔 채 n-1 로 다시 부른다        n * (돌아온 값)
}

factorial(4) → 4 * f(3) → 3 * f(2) → 2 * f(1) → 1
                                     ← 2      ← 6      ← 24
```

- 기저 조건을 맨 위에 둔다 — 원본 주석은 이것을 「Guard Clause」라 부른다.
- `n * factorial(n - 1)` 은 곱셈을 하기 전에 재귀 호출의 답을 기다려야 한다.
- 그래서 호출마다 `n` 을 기억한 프레임이 쌓이고, 깊이는 `n` 이다.
- 맨 아래에서 1 이 돌아오면 쌓인 프레임이 차례로 곱하며 풀린다.
- 원본 주석의 정리: 수학 정의를 그대로 옮겨 읽기 쉽지만, 스택 깊이에 주의해야 한다.

### (2) 꼬리 재귀 — 누산기를 들고 내려간다

**언제 쓰나** — 재귀를 나중에 반복문으로 바꿀 생각일 때, 중간 결과를 인자로 넘기는 꼴로 쓴다.

> **꼬리 재귀** — 재귀 호출이 함수의 마지막 연산이라, 돌아온 값에 아무것도 더 하지 않는 재귀.\
> 예: `return factorialTail(n - 1, n * acc);`

> **누산기(accumulator)** — 지금까지의 중간 결과를 담아 다음 호출로 넘기는 인자.\
> 예: `factorialTail` 의 `acc`.

```text
입력 코드                                   무엇이 일어나나
static long factorialTail(int n, long acc) {
  if (n <= 1) return acc;                   누적값을 그대로 돌려준다
  return factorialTail(n - 1, n * acc);     곱셈을 먼저 하고, 그 값을 들고 내려간다
}

factorialTail(3, 1) → (2, 3) → (1, 6) → 6 을 그대로 위로 넘긴다
```

- 곱셈은 내려가는 길에 이미 끝난다.
- 맨 아래 호출이 답 전체를 쥐고 있고, 위의 호출들은 그 값을 받아 그대로 넘기기만 한다.
- 이 꼴은 「`n` 과 `acc` 를 바꾸며 도는 반복문」으로 거의 기계적으로 옮겨진다.
- 그러나 원본의 팁대로 Java 는 꼬리 재귀를 최적화하지 않는다.
- 호출은 여전히 프레임을 하나씩 쌓으므로, 깊이 문제는 그대로 남는다 — 반복문으로 직접 바꿔야 한다.

### (3) 분할 정복 — 거듭제곱

**언제 쓰나** — 문제를 절반 크기로 줄여 한 번만 풀고, 그 답을 재사용할 수 있을 때 쓴다.

> **분할 정복** — 문제를 작은 부분 문제로 나눠 풀고(분할), 그 답들을 합쳐(정복) 원래 답을 만드는 방법.\
> 예: `base^10 = (base^5)²`.

```text
입력 코드                                   무엇이 일어나나
if (exp == 0) return 1;                     0제곱은 1
if (exp % 2 == 0) {
  long half = power(base, exp / 2);         절반을 한 번만 계산해
  return half * half;                       제곱해서 재사용한다
}
return base * power(base, exp - 1);         홀수면 하나 떼어 짝수로 만든다

power(2, 10) → exp: 10 → 5 → 4 → 2 → 1 → 0
```

- 짝수면 지수가 절반이 되고, 홀수면 1 을 빼서 다음 단계가 반드시 짝수가 된다.
- 그래서 많아야 두 단계마다 지수가 절반이 되고, 호출 수는 `log₂ exp` 의 몇 배 수준이다.
- 원본의 팁: 지수를 하나씩 줄이는 O(n) 이 O(log n) 으로 줄어든다.
- 핵심은 `half` 변수다 — 같은 부분 문제를 두 번 부르지 않고 한 번 계산해 둔 값을 쓴다.

### (4) 분할 정복 — 최대 부분 배열 합

**언제 쓰나** — 배열을 반으로 나눴을 때, 답이 「왼쪽 안 · 오른쪽 안 · 가운데에 걸침」 셋 중 하나일 때 쓴다.

> **부분 배열** — 배열에서 이어 붙은 구간 하나.\
> 예: `[-2, 1, -3, 4, -1, 2, 1, -5, 4]` 에서 `[4, -1, 2, 1]`.

```text
입력 코드                                         무엇이 일어나나
if (left == right) return nums[left];             원소 하나면 그 값이 답
int mid = (left + right) / 2;                     가운데를 정한다
int leftMax  = maxSubarrayDC(nums, left, mid);    왼쪽 절반 안의 최대
int rightMax = maxSubarrayDC(nums, mid+1, right); 오른쪽 절반 안의 최대
int crossMax = maxCrossing(nums, left, mid, right); mid 를 가로지르는 최대
return max(leftMax, rightMax, crossMax);          셋 중 최대

[ left ......... mid | mid+1 ......... right ]
          ←──── 누적         누적 ────→
          leftSum 최대   +   rightSum 최대  = crossMax
```

- `maxCrossing` 은 `mid` 에서 왼쪽으로 한 칸씩 더하며 가장 큰 누적합을 기록한다.
- 이어서 `mid + 1` 에서 오른쪽으로 같은 일을 하고, 두 최대를 더한다.
- 두 최대는 `Integer.MIN_VALUE` 에서 시작하고 반복문은 적어도 한 번 돌므로, 걸치는 구간은 양쪽에서 원소를 하나 이상 포함한다.
- 기저 조건이 `nums[left]` 를 그대로 돌려주므로, 빈 구간(합 0)은 답이 될 수 없다.
- 예제 배열에서 답은 `[4, -1, 2, 1]` 의 합 6 이다(손으로 셈한 값).
- 원본 주석: 완전 탐색 O(n²) 를 O(n log n) 으로 줄이지만, Kadane 알고리즘 O(n) 이 더 빠르다.

### (5) 메모이제이션 — 피보나치

**언제 쓰나** — 재귀 나무 안에서 같은 부분 문제가 여러 번 나올 때 쓴다.

> **메모이제이션** — 한 번 계산한 부분 문제의 답을 저장해 두고, 다시 나오면 저장한 값을 꺼내 쓰는 것.\
> 예: `memo.put(n, result)` 후 `memo.get(n)`.

```text
메모 없이 fib(5)                       메모가 있으면
fib(5)                                fib(5) → fib(4) → fib(3) → fib(2) → …
├─ fib(4)                             fib(3), fib(2) 를 두 번째로 만날 때
│  ├─ fib(3) ─ …                      memo 에서 바로 꺼낸다
│  └─ fib(2) ─ …
└─ fib(3) ─ …   ← 같은 계산을 또 한다
```

```text
입력 코드                                        무엇이 일어나나
if (n <= 1) return n;                            fib(0)=0, fib(1)=1
if (memo.containsKey(n)) return memo.get(n);     계산해 둔 값이면 즉시 반환
long result = fibMemo(n - 1) + fibMemo(n - 2);   처음이면 재귀로 계산
memo.put(n, result);                             저장한 뒤 반환
```

- 메모가 없으면 호출 하나가 둘로 갈라지며 같은 값을 거듭 계산해 O(2^n) 이 된다.
- 메모가 있으면 각 `n` 은 한 번만 계산되므로 O(n) 이다.
- 원본 주석은 이것을 「대표적 DP 패턴」이라 부른다 — 위에서 아래로 내려가며 채우는 동적 계획법이다.
- `memo` 는 `static` 필드라 여러 번 불러도 같은 저장소를 쓴다.

> **동적 계획법(DP)** — 겹치는 부분 문제의 답을 저장해 다시 쓰며 큰 문제를 푸는 방법.\
> 예: `fibMemo` 의 `memo`.

### (6) 하노이 탑 — 본질적으로 지수인 재귀

**언제 쓰나** — 「n−1 개를 치우고, 가장 큰 것을 옮기고, n−1 개를 다시 올린다」처럼 정의 자체가 재귀일 때 쓴다.

```text
hanoi(n, from, to, aux)
  1. hanoi(n-1, from, aux, to)   위의 n-1 개를 보조 기둥으로
  2. print from -> to            가장 큰 원판을 목표 기둥으로
  3. hanoi(n-1, aux, to, from)   n-1 개를 보조 기둥에서 목표 기둥으로

n == 1 이면 한 줄 찍고 return (기저 조건)
```

- 이동 횟수를 `T(n)` 이라 하면 `T(n) = 2·T(n−1) + 1`, `T(1) = 1` 이라 `T(n) = 2^n − 1` 이다.
- `main` 은 이 값을 `(int) Math.pow(2, 3) - 1`, 곧 7 로 찍는다.
- 원본의 팁: O(2^n) 이며, 원본 주석대로 출력해야 할 이동 자체가 그만큼 많아 최적화할 수 없다.
- 각 줄은 앞에 공백 두 칸을 붙여 `"  " + from + " -> " + to` 꼴로 찍힌다.

### (7) 깊이 카운터 — 재귀 없이 재귀적으로 생각하기

**언제 쓰나** — 괄호처럼 안으로 들어갔다 나오는 구조를, 호출 대신 정수 하나로 추적할 수 있을 때 쓴다.

```text
입력 코드                              무엇이 일어나나
int depth = 0;
for (char c : s.toCharArray()) {
  if (c == '(') depth++;               한 겹 들어간다
  else if (c == ')') depth--;          한 겹 나온다
  else if (depth == 0) sb.append(c);   괄호 밖 글자만 남긴다
}

"a(b(c)d)e"   depth: 0 1 1 2 2 1 1 0 0  → "ae"
```

- `depth` 는 「지금 호출 스택이 몇 층인가」를 숫자 하나로 흉내 낸 것이다.
- 재귀 호출이 없으니 스택이 쌓이지 않고, 문자열을 한 번 훑어 O(n) 에 끝난다.
- 원본 코드에서 `removeParentheses` 는 정의만 있고 `main` 이 부르지 않는다.

### (8) 호출 스택과 깊이 한계

```text
호출할 때마다          돌아올 때마다
┌──────────────┐
│ factorial(1) │  ← 맨 위에서 먼저 끝난다
│ factorial(2) │
│ factorial(3) │
│ main         │
└──────────────┘  스택이 정해진 크기를 넘으면 StackOverflowError
```

> **호출 스택** — 아직 끝나지 않은 호출마다 지역 변수와 돌아갈 자리를 쌓아 두는 메모리.\
> 예: `factorial(3)` 이 진행 중이면 `factorial(3)`, `(2)`, `(1)` 의 프레임이 쌓인다.

- 원본의 팁: Java 의 기본 스택 크기는 약 512KB~1MB 이고, 재귀 깊이 약 5000~10000 정도에서 넘친다(이 수치는 「어디서 틀리나 2」를 보라).
- 깊이가 깊으면 두 길이 있다 — `-Xss` 옵션으로 스택을 키우거나, 반복문으로 바꾼다.
- 분할 정복(거듭제곱 · 최대 부분 배열)은 깊이가 `log n` 수준이라 이 한계에 잘 닿지 않는다.
- 팩토리얼 · 꼬리 재귀 · 메모 피보나치는 깊이가 `n` 에 비례해 큰 입력에서 닿는다.

## 문법 — 형태와 규칙

```java
public class SumDemo {
    // 배열 a 의 i 번째부터 끝까지의 합
    static int sum(int[] a, int i) {
        if (i == a.length) return 0;        // 1. 기저 조건을 먼저
        return a[i] + sum(a, i + 1);        // 2. 더 작은 문제 + 3. 결과 조합
    }

    // 같은 일을 누산기로(꼬리 재귀 꼴)
    static int sumTail(int[] a, int i, int acc) {
        if (i == a.length) return acc;
        return sumTail(a, i + 1, acc + a[i]);
    }

    public static void main(String[] args) {
        int[] a = {1, 2, 3};
        System.out.println(sum(a, 0) + " " + sumTail(a, 0, 0));
    }
}
```

- **기저 조건을 먼저 쓴다** — 원본의 설계 원칙 1번.
- **매 호출마다 문제가 기저 쪽으로 줄어야 한다** — `i + 1`, `n - 1`, `exp / 2` 처럼.
- **부분 문제의 결과를 조합한다** — `n * …`, `half * half`, `max(…)`, `a + b`.
- **중복 계산이 있으면 메모이제이션** — 저장소를 확인하고, 없으면 계산해 넣는다.
- **깊이가 깊으면 반복문으로 바꿀 것을 고려한다** — 꼬리 재귀 꼴이면 바꾸기 쉽다.
- 위 다섯 줄은 원본 `main` 이 찍는 「재귀 설계 원칙」 다섯 줄과 같은 내용이다.
- 분할 정복은 구간을 `left`, `right` 인자로 넘기고, `mid = (left + right) / 2` 로 나눈다.

## 어디서 틀리나

### 1. 기저 조건이 없거나 닿지 않는다
기저 조건이 없으면 호출이 끝없이 쌓여 스택이 넘친다.
기저 조건이 있어도 인자가 그쪽으로 줄지 않으면 같다 — 예를 들어 `power` 에서 홀수 분기를 `exp - 1` 대신 `exp` 로 넘기면 영원히 내려간다.

### 2. 깊이 한계 수치를 그대로 믿는다
원본의 주장: 기본 스택은 약 512KB~1MB, 재귀 깊이는 약 5000~10000.
왜 의심스러운가: 스택 크기는 JVM 구현 · 운영체제 · 설정에 따라 다르고, 넘치는 깊이는 프레임 하나의 크기(지역 변수 · 인자 수 · JIT 컴파일 여부)에 따라 크게 달라진다.
지역 변수가 적은 함수라면 이보다 훨씬 깊이 들어갈 수도 있다(확인 필요).
「대략 수천~수만 단계에서 넘칠 수 있다」 정도로 기억하고, 입력 크기가 그보다 크면 반복문을 먼저 생각한다.

### 3. 꼬리 재귀니까 안전하다고 생각한다
원본의 팁대로 Java 는 꼬리 재귀를 최적화하지 않는다.
`factorialTail` 도 `factorial` 과 똑같이 깊이 `n` 만큼 프레임을 쌓는다.
꼬리 재귀의 가치는 「반복문으로 옮기기 쉬운 꼴」이라는 데 있다 — 옮기는 일은 직접 해야 한다.

### 4. 분할 정복에서 절반을 두 번 부른다
`return power(base, exp / 2) * power(base, exp / 2);` 로 쓰면 결과는 같지만 한 호출이 둘로 갈라진다.
갈라진 호출이 단계마다 두 배가 되어, 지수를 절반으로 줄인 이득이 사라지고 O(n) 이 된다.
`half` 에 한 번 담아 두는 것이 O(log n) 의 핵심이다.

### 5. 메모 저장소의 범위와 자료형
`memo` 는 `static` 이라 프로그램 전체에서 공유된다 — 다른 문제(다른 점화식)에 같은 맵을 쓰면 엉뚱한 값을 꺼낸다.
`Map<Integer, Long>` 은 값을 객체로 감싸므로, 크기가 정해진 문제라면 `long[]` 배열이 더 가볍다.
메모가 있어도 처음 `fibMemo(n)` 을 부르면 깊이는 `n` 까지 내려간다 — 메모는 시간을 줄이지 깊이를 줄이지 않는다.

### 6. `long` 도 넘친다
`factorial` 과 `power` 는 `long` 을 돌려주지만 `long` 의 최댓값은 약 9.22 × 10^18 이다.
`20!` 은 이 안에 들지만 `21!` 은 넘쳐서, 예외 없이 엉뚱한 값이 된다(원본에 근거 없음 — 추론).
스택보다 오버플로가 먼저 문제가 되는 경우도 많다.

### 7. 원본 주석의 「재귀 -> 반복 변환 (하노이 탑)」
원본의 주장: 6번 절의 제목이 「재귀 -> 반복 변환」이다.
왜 의심스러운가: `hanoi` 본문은 반복문이 아니라 재귀 그대로다.
반복으로 바꾼 꼴은 원본에 없다 — 제목은 「이것도 원리상 반복으로 바꿀 수 있다」는 뜻으로 읽어야 한다.

### 8. 짝이 맞지 않는 괄호
`removeParentheses` 는 괄호가 짝을 이룬다고 가정한다.
`")ab"` 처럼 닫는 괄호가 먼저 오면 `depth` 가 −1 이 되어, 그 뒤 글자가 하나도 남지 않는다.

### 9. 원본 끝의 `// 출력:` 주석
`main` 은 `"\n=== …"` 처럼 줄바꿈으로 시작하는 문자열을 찍어 절 사이에 빈 줄을 만들고, 마지막에 「재귀 설계 원칙」 다섯 줄도 찍는다.
원본 끝의 출력 주석에는 그 빈 줄과 다섯 줄이 빠져 있다 — 코드를 읽으면 그 줄들도 찍힌다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| 기본 스택 크기 약 512KB~1MB | JVM 구현 · 운영체제 · 설정에 따라 다르다 — 언어 보장 아님(확인 필요) |
| 재귀 깊이 약 5000~10000 에서 넘친다 | 프레임 크기 · JVM 에 따라 다른 경험치 — 언어 보장 아님(확인 필요) |
| `-Xss` 로 스택 크기를 키운다 | JVM 구현의 실행 옵션(표준 `java` 명령 계열의 비표준 `-X` 옵션) — 언어 문법 아님(확인 필요) |
| Java 는 꼬리 재귀를 최적화하지 않는다 | 언어 명세가 최적화를 요구하지 않고, 널리 쓰는 JVM 이 하지 않는다 — 「앞으로도 절대 안 한다」는 보장은 아님(확인 필요) |
| 스택이 넘치면 `StackOverflowError` | Java 플랫폼(JVM 명세)이 정한 오류 종류(확인 필요) |
| `long` 은 64비트라 `21!` 에서 넘친다 | 언어 명세가 `long` 을 64비트로 정한다 — 언어 보장 |
| 거듭제곱 O(log n) · 하노이 O(2^n) · 메모 피보나치 O(n) | 알고리즘의 성질 — 언어 · 구현과 무관 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 정의가 자기 자신으로 쓰여 있고 깊이가 작다 | 기본 재귀 | 억지로 만든 반복문 |
| 깊이가 입력 크기 `n` 에 비례하고 `n` 이 크다 | 반복문 변환(꼬리 재귀 꼴에서 출발) | 「꼬리 재귀라 괜찮다」는 믿음 |
| 문제를 절반으로 나눠 한 번만 풀면 된다 | 분할 정복(`half` 재사용) | 같은 절반을 두 번 부르는 꼴 |
| 같은 부분 문제가 거듭 나온다 | 메모이제이션 | 메모 없는 순수 재귀(O(2^n)) |
| 최대 부분 배열 합을 빨리 구해야 한다 | Kadane O(n) | 분할 정복 O(n log n)(학습용으로만) |
| 괄호 깊이처럼 층수만 알면 된다 | 깊이 카운터 반복문 | 재귀 호출 |
| 답이 본질적으로 지수적이다(하노이) | 재귀 그대로 · 작은 `n` 만 | 「최적화하면 빨라진다」는 기대 |

## 핵심 문장

1. **재귀는 「기저 조건 → 작은 문제로 호출 → 결과 조합」의 세 칸으로 쓴다.**
2. **분할 정복은 절반을 한 번만 풀어 재사용할 때 빨라진다** — 거듭제곱이 O(n) 에서 O(log n) 이 된다.
3. **메모이제이션은 겹치는 부분 문제를 한 번만 계산하게 한다** — 피보나치가 O(2^n) 에서 O(n) 이 된다.
4. **Java 는 꼬리 재귀를 최적화하지 않는다** — 깊은 재귀는 직접 반복문으로 바꾸거나 `-Xss` 로 스택을 키운다.
5. **재귀적 사고는 재귀 호출 없이도 쓸 수 있다** — 괄호 깊이 카운터가 호출 스택을 숫자 하나로 대신한다.

## 용어 풀이

- **재귀** — 함수가 자기 자신을 다시 부르는 것.
- **기저 조건** — 재귀를 멈추고 바로 답을 돌려주는 조건.
- **꼬리 재귀** — 재귀 호출이 마지막 연산이라 돌아온 값에 더 할 일이 없는 재귀.
- **누산기** — 중간 결과를 담아 다음 호출로 넘기는 인자.
- **분할 정복** — 나눠 풀고 합쳐 답을 만드는 방법.
- **부분 배열** — 배열에서 이어 붙은 한 구간.
- **메모이제이션** — 계산한 부분 문제의 답을 저장해 다시 쓰는 것.
- **동적 계획법(DP)** — 겹치는 부분 문제의 답을 저장해 큰 문제를 푸는 방법.
- **호출 스택** — 끝나지 않은 호출들의 프레임을 쌓아 두는 메모리.
- **스택 프레임** — 호출 하나가 쓰는 지역 변수 · 인자 · 돌아갈 자리의 묶음.
- **`StackOverflowError`** — 호출 스택이 정해진 크기를 넘을 때 나는 오류.
- **`-Xss`** — JVM 의 스레드 스택 크기를 정하는 실행 옵션.
- **반복문 변환** — 재귀를 `while` · `for` 와 변수 갱신으로 바꾸는 것.
- **Kadane 알고리즘** — 최대 부분 배열 합을 한 번 훑어 O(n) 에 구하는 방법.

## 더 들어가면

- **분할 정복의 복잡도 식** — 최대 부분 배열은 `T(n) = 2T(n/2) + O(n)` 꼴이라 O(n log n) 이 된다(마스터 정리의 대표 경우).
- **Kadane 의 모양** — `cur = max(x, cur + x)`, `best = max(best, cur)` 를 한 번 돌면 된다 — 「지금 위치에서 끝나는 최대 합」을 이어 가는 DP 다.
- **스레드 단위 스택 크기** — `-Xss` 대신 `new Thread(null, runnable, "name", stackSize)` 로 특정 스레드만 큰 스택을 주는 방법이 코딩 테스트에서 쓰인다(확인 필요).
- **`computeIfAbsent` 로 메모를 쓸 때** — 재귀 안에서 같은 `HashMap` 을 `computeIfAbsent` 로 고치면 최근 JDK 에서 `ConcurrentModificationException` 이 날 수 있다(확인 필요).
- **하노이 탑의 반복 풀이** — 원판 수의 홀짝에 따라 기둥을 도는 순서가 정해지는 반복 풀이가 알려져 있다(확인 필요).
- **아래에서 위로 채우는 DP** — `fib` 를 배열이나 변수 두 개로 0 부터 올라가며 채우면 깊이 문제도 사라진다.
