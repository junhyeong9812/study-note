## 퀴즈 정답

### 1. 보호를 위해서이며, 모드 전환 자체가 비싸다

악의적이거나 버그가 있는 프로그램이 하드웨어를 직접 건드리면 다른 프로그램이나 OS 자체를 망가뜨릴 수 있다.
그래서 유저 프로그램은 하드웨어에 직접 접근하지 못하고, 시스템 콜이라는 관문을 지나야만 커널 모드의 OS 가 권한을 확인한 뒤 대신 일을 해 준다.
그런데 유저 → 커널 모드 전환에는 수백~수천 사이클의 오버헤드가 든다.
그래서 시스템 콜을 적게 부를수록 빨라진다.

근거 — 장 본문 §1.2 「커널 모드와 유저 모드」.

### 2. Running → Waiting → Ready → Running

디스크 읽기를 요청하면 프로세스는 I/O 를 기다려야 하므로 Running 에서 Waiting(Blocked) 으로 간다.
I/O 가 끝나 데이터가 도착하면 Waiting 에서 Ready 로 간다(바로 Running 이 아니다).
스케줄러가 이 프로세스를 고르면 Ready 에서 Running 으로 간다.

그 사이 CPU 는 놀지 않고 다른 Ready 프로세스를 실행한다.
Waiting 상태를 따로 두는 까닭이 바로 이것, 곧 CPU 이용률을 높이기 위해서다.

근거 — 장 본문 §2.2 「프로세스 상태」의 상태 전이 목록.
(직접 계산한 값 — 실행하지 않음)

### 3. 저장 · 복원과 캐시 손실 때문이고, 균형이 필요하다

문맥 교환은 A 의 레지스터 · PC · 스택 포인터를 PCB 에 저장하고 B 의 상태를 PCB 에서 복원하는 일이다.
이 동안 CPU 는 사용자 프로그램의 일을 하지 않으며, TLB 플러시와 캐시 미스 증가까지 뒤따른다.
본문은 한 번에 보통 1~10 마이크로초라고 적는다.

- 너무 잦으면 오버헤드가 쌓여 성능이 떨어진다.
- 너무 드물면 반응 시간(응답성)이 나빠진다.

이 균형을 잡는 것이 스케줄링 알고리즘의 설계 목표다.

근거 — 장 본문 §2.3 「문맥 교환」.

### 4. 코드 · 데이터 · 힙은 공유하고, 스택만 따로다

같은 프로세스의 스레드는 코드 · 데이터 · 힙을 함께 쓰고, 스택만 스레드마다 따로 가진다.
그래서 생성 · 통신 · 문맥 교환이 프로세스보다 가볍다.

대가는 두 가지다.
1. 한 스레드가 죽으면 프로세스 전체가 영향받을 수 있다.
2. 메모리를 공유하므로 동기화 문제(경쟁 상태)가 생긴다.

근거 — 장 본문 §2.4 「스레드」.

### 5. FCFS 평균 대기 17, SJF 평균 대기 3 — 호위 효과

대기 시간은 Ready 큐에서 기다린 시간이다.
모두 시각 0 에 왔으므로 각자의 시작 시각이 곧 대기 시간이다.

FCFS (A → B → C):

```text
A: 0~24   대기 0
B: 24~27  대기 24
C: 27~30  대기 27
평균 = (0 + 24 + 27) / 3 = 51 / 3 = 17
```

SJF (B → C → A, 짧은 것부터):

```text
B: 0~3    대기 0
C: 3~6    대기 3
A: 6~30   대기 6
평균 = (0 + 3 + 6) / 3 = 9 / 3 = 3
```

긴 작업 A 가 앞에 서면 뒤의 짧은 작업 둘이 모두 24 를 기다려야 한다.
이것이 FCFS 의 호위 효과(Convoy Effect)다.
SJF 는 짧은 작업을 먼저 끝내 기다리는 작업 수를 빨리 줄이므로 대기 시간의 합이 최소가 된다.

근거 — 장 본문 §3.1 성능 지표, §3.2 FCFS · SJF.
(직접 계산한 값 — 실행하지 않음)

### 6. 크면 FCFS, 작으면 문맥 교환 폭증 — 최대 대기 80ms

- q 가 너무 크면 한 프로세스가 끝날 때까지 놓지 않으므로 FCFS 와 같아지고 응답 시간이 나빠진다.
- q 가 너무 작으면 문맥 교환이 너무 잦아져 오버헤드가 폭증한다.

RR 에서 모든 프로세스는 최대 (n − 1) × q 안에 CPU 를 받는다.
n = 5, q = 20ms 이면 (5 − 1) × 20 = 80ms 다.
자기 차례가 지난 뒤 나머지 4개가 한 번씩 q 를 다 쓰는 경우가 가장 오래 기다리는 경우다.

근거 — 장 본문 §3.2 Round Robin.

### 7. 실행해 보면서 짧은 작업을 가려내기 때문이다

SJF 는 실행 시간을 미리 알아야 하지만, 그것은 알 수 없다.
MLFQ 는 모든 새 프로세스를 최고 우선순위 큐에 넣고 실제로 돌려 본다.
할당량을 다 쓰면 CPU-bound 로 보고 한 단계 내리고, I/O 로 일찍 반납하면 I/O-bound 로 보고 높은 큐에 둔다.
그 결과 짧은 대화형 작업은 높은 우선순위에서 빨리 처리되어, 예측 없이도 SJF 와 비슷한 효과를 낸다.

주기적으로 모두를 최고 큐로 올리는 것은 기아(Starvation) 방지다.
낮은 큐로 밀려난 긴 작업이 영원히 CPU 를 못 받는 일을 막는다.
SJF 에서 에이징으로 기아를 푸는 것과 같은 목적이다.

근거 — 장 본문 §3.2 SJF(기아 · 에이징), MLFQ.

### 8. 최종 잔고 1500 — B 의 출금 200 이 사라진다

```text
B: 잔고 읽기   → B 가 본 값 1000
A: 잔고 읽기   → A 가 본 값 1000
B: 잔고 쓰기   → 1000 − 200 = 800
A: 잔고 쓰기   → 1000 + 500 = 1500  (B 의 800 을 덮어씀)
```

기대한 값은 1000 + 500 − 200 = 1300 이다.
실제로는 1500 이 되어 출금 200 이 증발했다(은행 입장에서는 200 이 생긴 셈이다).
본문의 예는 반대 순서로 덮어써 800 이 되었는데, 어느 쪽이 나중에 쓰느냐에 따라 결과가 달라지는 것이 경쟁 상태다.

원인은 「읽기-수정-쓰기」가 원자적이지 않은 데 있다.
이 구간을 한 번에 하나의 스레드만 들어가는 임계 구역으로 만들면(뮤텍스 등) 막을 수 있다.

근거 — 장 본문 §4.1 「경쟁 상태」, §4.2 「임계 구역」.
(직접 계산한 값 — 실행하지 않음)

### 9. 뮤텍스는 소유권이 있고 세마포어는 없다

뮤텍스는 잠근 스레드만 풀 수 있다.
그래서 「내가 들어가 있는 동안 아무도 못 들어온다」는 임계 구역 보호에 맞다.
세마포어에는 소유권이 없어 한 스레드가 wait 하고 다른 스레드가 signal 할 수 있다.
그래서 생산자가 「채웠다」고 알리고 소비자가 그 신호를 기다리는 생산자-소비자 같은 신호 패턴에 맞는다.
또 카운팅 세마포어는 n 개의 자원을 동시에 허용할 수 있다.

주차장(S = 3)에 차 세 대가 들어가면 wait 를 세 번 해서 S = 0 이 된다.
네 번째 차의 wait 는 S == 0 이므로 기다린다.
차 한 대가 나가며 signal 하면 S 가 1 늘고 기다리던 차가 깨어나 들어간다.

근거 — 장 본문 §4.3 뮤텍스 · 세마포어.

### 10. 순환 대기가 깨진다 — 넷이 모두 있어야 데드락이다

번호 순서대로만 요청하면 「높은 번호를 쥔 채 낮은 번호를 기다리는」 일이 없다.
그래서 P₁ → P₂ → … → P₁ 처럼 고리를 이루는 순환 대기가 생길 수 없다.

데드락은 상호 배제 · 점유와 대기 · 비선점 · 순환 대기가 동시에 성립해야 일어난다.
그래서 하나만 깨져도 데드락은 일어나지 않는다.
이것이 예방 · 회피 · 탐지 전략의 기반이다.

범용 OS 가 무시(오스트리치) 전략을 고르는 것은, 데드락은 드물고 예방 · 회피의 오버헤드가 가끔 생기는 데드락의 비용보다 크다고 보는 실용적 판단 때문이다.
생기면 사용자가 프로세스를 직접 종료한다.

근거 — 장 본문 §5.2 「네 가지 필요 조건」, §5.3 「처리 전략」.

### 11. 고정 크기라서 외부 단편화가 없고, 내부 단편화는 한 페이지 미만이다

연속 할당은 빈 공간의 합이 충분해도 조각나 있으면 큰 연속 블록을 줄 수 없다(외부 단편화).
페이징은 모든 블록이 같은 크기라 어떤 빈 프레임이든 어떤 페이지에 쓸 수 있다.
그래서 「연속된 큰 빈자리」가 필요 없다.

대신 프로세스의 마지막 페이지가 꽉 차지 않으면 그 나머지가 낭비된다(내부 단편화).
4KB 페이지에서 그 낭비는 최대 4KB − 1 바이트, 곧 한 페이지 미만이다.

근거 — 장 본문 §6.2 「페이징」.

### 12. TLB 없이는 두 번 — 지역성 덕분에 작은 TLB 로 충분하다

페이지 테이블도 메모리에 있으므로, 주소 변환에 한 번, 실제 데이터 접근에 한 번, 모두 두 번 메모리에 간다.
속도가 절반이 된다.

TLB 는 최근 쓴 변환 결과를 담는 작은 고속 캐시다.
프로그램은 소수의 페이지를 반복 접근하는 지역성(Ch.11)을 가지므로, 64~1024 엔트리 정도의 작은 TLB 로도 대부분의 접근이 TLB 히트가 된다.

근거 — 장 본문 §6.3 「페이지 테이블과 TLB」.

### 13. FIFO 6번, LRU 5번

FIFO (가장 먼저 올라온 것을 버린다):

```text
참조 1 → [1]        폴트
참조 2 → [1,2]      폴트
참조 3 → [1,2,3]    폴트
참조 1 → [1,2,3]    히트
참조 4 → [2,3,4]    폴트 (가장 먼저 온 1 을 버림)
참조 1 → [3,4,1]    폴트 (2 를 버림)
참조 2 → [4,1,2]    폴트 (3 을 버림)
폴트 6번
```

LRU (가장 오래 안 쓴 것을 버린다):

```text
참조 1 → {1}        폴트
참조 2 → {1,2}      폴트
참조 3 → {1,2,3}    폴트
참조 1 → {1,2,3}    히트 (1 이 가장 최근으로)
참조 4 → {1,3,4}    폴트 (가장 오래 안 쓴 2 를 버림)
참조 1 → {1,3,4}    히트
참조 2 → {1,4,2}    폴트 (가장 오래 안 쓴 3 을 버림)
폴트 5번
```

FIFO 는 1 이 방금 쓰였어도 「먼저 왔다」는 이유로 버려 곧바로 다시 폴트를 낸다.
LRU 는 최근에 쓴 1 을 지켜 한 번 덜 폴트한다.
시간적 지역성을 반영하느냐의 차이다.

근거 — 장 본문 §7.3 「페이지 교체 알고리즘」.
(직접 계산한 값 — 실행하지 않음)

### 14. 적게라도 제대로 돌리는 편이 낫다 / WAL 과 같은 「먼저 기록」 원리

스래싱은 실행 중인 프로세스들의 워킹 셋 합계가 물리 메모리보다 커서, 서로의 페이지를 계속 밀어내는 상태다.
그러면 디스크 I/O 만 반복하고 CPU 이용률이 급락한다.
일부 프로세스를 중단하면 남은 프로세스의 워킹 셋이 메모리에 들어가 제대로 진행된다.
모두가 스래싱하는 것보다 적은 수라도 실제로 일하는 편이 낫다.

저널링은 데이터베이스의 WAL(Write-Ahead Log)과 같은 원리다.
변경 사항을 먼저 로그(저널)에 적고 나서 실제로 적용한다.
쓰는 도중 전원이 꺼져도 로그를 보고 메타데이터와 데이터의 불일치를 복구할 수 있다.

근거 — 장 본문 §7.4 「스래싱」, §8.3 「저널링」.

## 실습 정답

### 실습 1. 네 작업을 FCFS · SJF · RR 로 스케줄링하기

모두 시각 0 에 도착하므로 반환 시간 = 완료 시각이다.
대기 시간 = 반환 시간 − 실행 시간이다.
응답 시간 = 처음 CPU 를 받은 시각이다.

**1단계 — FCFS (P1 → P2 → P3 → P4)**

```text
| P1 | P2      | P3     | P4 |
0    6         14       21   24
```

| 프로세스 | 실행 | 완료(반환) | 대기 | 응답 |
|---|---|---|---|---|
| P1 | 6 | 6 | 0 | 0 |
| P2 | 8 | 14 | 6 | 6 |
| P3 | 7 | 21 | 14 | 14 |
| P4 | 3 | 24 | 21 | 21 |

- 평균 대기 = (0 + 6 + 14 + 21) / 4 = 41 / 4 = 10.25
- 평균 응답 = 10.25 (비선점이라 대기와 같다)
- 평균 반환 = (6 + 14 + 21 + 24) / 4 = 65 / 4 = 16.25

**2단계 — SJF (짧은 순: P4 3 → P1 6 → P3 7 → P2 8)**

```text
| P4 | P1    | P3     | P2      |
0    3       9        16        24
```

| 프로세스 | 실행 | 완료(반환) | 대기 | 응답 |
|---|---|---|---|---|
| P1 | 6 | 9 | 3 | 3 |
| P2 | 8 | 24 | 16 | 16 |
| P3 | 7 | 16 | 9 | 9 |
| P4 | 3 | 3 | 0 | 0 |

- 평균 대기 = (3 + 16 + 9 + 0) / 4 = 28 / 4 = 7
- 평균 응답 = 7
- 평균 반환 = (9 + 24 + 16 + 3) / 4 = 52 / 4 = 13

**3단계 — RR (q = 4)**

큐의 흐름을 한 칸씩 따라간다.

```text
0~4   P1 실행 (남은 2)  → 큐: P2 P3 P4 P1
4~8   P2 실행 (남은 4)  → 큐: P3 P4 P1 P2
8~12  P3 실행 (남은 3)  → 큐: P4 P1 P2 P3
12~15 P4 실행 3 → 완료 → 큐: P1 P2 P3
15~17 P1 실행 2 → 완료 → 큐: P2 P3
17~21 P2 실행 4 → 완료 → 큐: P3
21~24 P3 실행 3 → 완료

| P1 | P2 | P3 | P4 |P1| P2 | P3 |
0    4    8    12   15 17   21   24
```

| 프로세스 | 실행 | 완료(반환) | 대기 | 응답 |
|---|---|---|---|---|
| P1 | 6 | 17 | 11 | 0 |
| P2 | 8 | 21 | 13 | 4 |
| P3 | 7 | 24 | 17 | 8 |
| P4 | 3 | 15 | 12 | 12 |

- 평균 대기 = (11 + 13 + 17 + 12) / 4 = 53 / 4 = 13.25
- 평균 응답 = (0 + 4 + 8 + 12) / 4 = 24 / 4 = 6
- 평균 반환 = (17 + 21 + 24 + 15) / 4 = 77 / 4 = 19.25

**비교**

| 알고리즘 | 평균 대기 | 평균 응답 | 평균 반환 |
|---|---|---|---|
| FCFS | 10.25 | 10.25 | 16.25 |
| SJF | 7 | 7 | 13 |
| RR (q=4) | 13.25 | 6 | 19.25 |

- 평균 대기 시간은 SJF 가 가장 작다.
  장 본문 §3.2 의 「SJF 는 평균 대기 시간이 최소」와 맞는다.
- 평균 응답 시간은 RR 이 가장 작다.
  모든 프로세스가 (n − 1) × q = 3 × 4 = 12 안에 처음 CPU 를 받았고(P4 가 딱 12), 장 본문의 「RR 은 응답 시간을 보장한다」와 맞는다.
- 대신 RR 은 일을 잘게 나눠 평균 대기 · 반환이 가장 나쁘다.
  장 본문 §3.1 의 「지표들은 서로 충돌한다」는 트레이드오프의 한 예다.

근거 — 장 본문 §3.1 성능 지표, §3.2 FCFS · SJF · RR.
(직접 계산한 값 — 실행하지 않음)

참조열: `7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2`

| 0 | 0 2 3 | 히트 | |

| 참조 | 프레임 (먼저 온 순) | 결과 | 버린 페이지 |

| 3 | 2 3 0 | 히트 | |
| 2 | 2 3 0 | 히트 | |

폴트 **10번** (히트 3번, 합 13).

**3단계 — LRU (가장 오래 안 쓴 페이지를 버린다)**

프레임은 「오래 안 쓴 것 → 최근 쓴 것」 순으로 적는다.

| 참조 | 프레임 (오래된 순) | 결과 | 버린 페이지 |
|---|---|---|---|
| 7 | 7 | 폴트 | |

**비교**

```text
OPT 7  ≤  LRU 9  ≤  FIFO 10
```

- OPT 는 미래를 알아야 해서 실제로는 못 쓰지만, 다른 알고리즘을 재는 기준선이 된다.
- LRU 는 FIFO 보다 OPT 에 가깝다.
  시간적 지역성, 곧 「최근에 안 쓴 것은 앞으로도 안 쓸 가능성이 높다」를 이용하기 때문이다.
- FIFO 는 5번째 참조에서 0 을 다시 썼는데도 「먼저 왔다」는 이유로 6번째 참조에서 0 을 버려, 7번째 참조에서 곧장 폴트를 냈다.

### 실습 3. 4KB 페이지에서 가상 주소를 물리 주소로 바꾸기

가상 주소 = [페이지 번호 | 오프셋] 이고, 페이지 크기가 4096 이므로 다음과 같다.

```text
페이지 번호 = 가상 주소 ÷ 4096 의 몫
오프셋     = 가상 주소 ÷ 4096 의 나머지
물리 주소  = 프레임 번호 × 4096 + 오프셋   (오프셋은 그대로)
```

**1단계 — 주소 변환**

가상 주소 10000:

```text
10000 ÷ 4096 = 몫 2, 나머지 10000 − 8192 = 1808
페이지 2 → 프레임 5
물리 주소 = 5 × 4096 + 1808 = 20480 + 1808 = 22288
```

가상 주소 4100:

```text
4100 ÷ 4096 = 몫 1, 나머지 4
페이지 1 → 프레임 3
물리 주소 = 3 × 4096 + 4 = 12288 + 4 = 12292
```

**2단계 — 가상 주소 13000**

```text
13000 ÷ 4096 = 몫 3, 나머지 13000 − 12288 = 712
페이지 3 → invalid (메모리에 없음)
```

페이지 폴트가 난다.
장 본문 §7.2 의 처리 단계를 따른다.
1. OS 가 트랩을 받는다.
2. 디스크에서 페이지 3 을 찾는다.
3. 빈 프레임에 싣는다(빈 프레임이 없으면 교체 알고리즘으로 한 페이지를 버린다).
4. 페이지 테이블의 페이지 3 항목을 새 프레임 번호와 valid 로 고친다.
5. 멈췄던 명령어를 다시 실행하면, 이번에는 그 프레임의 오프셋 712 에 접근한다.

**3단계 — 내부 단편화**

```text
10000 ÷ 4096 = 2 페이지를 꽉 채우고 1808 바이트가 남는다
→ 필요한 페이지 수 = 3
마지막 페이지에서 쓰는 양 = 1808 바이트
낭비 = 4096 − 1808 = 2288 바이트
```

낭비 2288 바이트는 「최대 4KB − 1」(4095 바이트) 안에 든다.
장 본문 §6.2 의 「내부 단편화는 한 페이지 미만」과 맞는다.
