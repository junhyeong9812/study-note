## 퀴즈 정답

### 1. 중복은 불일치를 낳고, 3단계 스키마는 데이터 독립성을 위해 나눈다

같은 정보가 여러 파일에 있으면 하나를 고칠 때 나머지도 다 고쳐야 하고, 하나라도 빠뜨리면 불일치가 생긴다.
3단계 스키마는 「무엇이 저장되나(개념)」와 「어떻게 저장되나(내부)」와 「누가 무엇을 보나(외부)」를 갈라 데이터 독립성을 얻으려는 구조다.
인덱스 추가는 내부 스키마의 변화라서 논리 구조가 그대로이고, 이것이 물리적 독립성이다.

근거 — 장 본문 §1.1 「파일로 데이터를 관리하면」 · §1.2 「3단계 스키마 구조」.

### 2. 집합에는 순서와 중복이 없기 때문이다

릴레이션은 튜플들의 집합으로 정의된다.
집합에는 원소의 순서가 없고 같은 원소가 두 번 들어가지 않으므로, 릴레이션도 튜플 순서가 없고 중복 튜플이 없다.
속성값이 원자적이어야 한다는 성질은 1NF 의 근거다.

근거 — 장 본문 §2.1 「관계형 모델의 핵심 아이디어」 · §4.3 1NF.

### 3. `{id, name}` 은 슈퍼키지만 후보키는 아니고, 학과 99 는 거부된다

`id` 하나로 튜플이 유일하게 정해지므로 `{id}` 가 슈퍼키다.
슈퍼키에 속성을 더해도 슈퍼키이므로 `{id, name}` 도 슈퍼키다.
그러나 `name` 을 빼도 유일성이 유지되므로 최소가 아니고, 따라서 후보키가 아니다.
외래키 값은 참조된 테이블에 반드시 있어야 하므로(참조 무결성), 없는 학과 99 를 넣으려는 시도는 거부된다.
(직접 계산한 값 — 실행하지 않음)

근거 — 장 본문 §2.2 「키의 종류」.

### 4. LEFT JOIN 은 4행, 이영희의 `course_id` 가 NULL 이고 INNER JOIN 은 3행이다

students 의 각 행을 enrollments 와 맞춰 본다.

```text
김철수(id 1) → CS101, CS201  → 2행
이영희(id 2) → 짝 없음        → LEFT JOIN 에서는 (이영희, NULL) 1행, INNER JOIN 에서는 0행
박민수(id 3) → CS101          → 1행

LEFT JOIN  : 2 + 1 + 1 = 4행
INNER JOIN : 2 + 0 + 1 = 3행
```

LEFT JOIN 은 왼쪽 테이블의 모든 행을 남기고 짝이 없으면 오른쪽 열을 NULL 로 채운다.
INNER JOIN 은 양쪽에 짝이 있는 행만 남기므로 이영희가 빠진다.
결과 행의 차례는 릴레이션에 순서가 없으므로 정해져 있지 않다.
(직접 계산한 값 — 실행하지 않음)

근거 — 장 본문 §3.3 「JOIN」 · §2.1 릴레이션의 성질.

### 5. FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY 차례로, CS 3.85 만 남는다

처리 차례대로 따라간다.

```text
FROM students       : 김철수 CS 3.8 · 이영희 EE 3.5 · 박민수 CS 3.9
WHERE gpa > 3.0     : 세 행 모두 통과
GROUP BY dept       : CS {3.8, 3.9} · EE {3.5}
HAVING AVG(gpa)>3.5 : CS 평균 = (3.8 + 3.9) / 2 = 3.85 → 통과
                      EE 평균 = 3.5 → 3.5 > 3.5 가 거짓 → 탈락
SELECT dept, AVG    : (CS, 3.85)
ORDER BY dept       : (CS, 3.85)
```

`WHERE` 는 `GROUP BY` 전에 개별 행을 거른다.
`AVG(gpa)` 는 그룹이 만들어진 뒤에야 계산되므로 `WHERE` 단계에는 아직 없는 값이다.
그래서 그룹 조건은 `HAVING` 에만 쓸 수 있다.
(직접 계산한 값 — 실행하지 않음)

근거 — 장 본문 §3.2 「실행 순서」 · §3.4 「왜 WHERE가 아니라 HAVING인가」.

### 6. 학과장 변경은 2행을 고쳐야 하고, 이영희를 지우면 EE 학과 정보가 사라진다

CS 학과 정보는 김철수 행과 박민수 행 두 곳에 들어 있다.
그래서 학과장이 바뀌면 2행을 고쳐야 하고, 하나만 고치면 불일치가 남는다(갱신 이상).
EE 학과의 정보(EE · 박교수 · 5678)는 이영희 행에만 있다.
그래서 이영희 행을 지우면 EE 학과의 학과장과 전화번호도 함께 사라진다(삭제 이상).
원인은 학생과 학과라는 서로 다른 개념이 한 테이블에 섞여 있다는 데 있다.
(직접 계산한 값 — 실행하지 않음)

근거 — 장 본문 §4.1 「이상 현상」.

### 7. 부분 종속은 2NF 를, 이행 종속은 3NF 를 어기고, BCNF 는 모든 결정자가 후보키이길 요구한다

`student_name` 은 복합키의 일부인 `student_id` 만으로 정해지므로 부분 함수 종속이고, 이는 2NF 위반이다.
`id → dept → dept_head` 에서 `dept_head` 는 `dept` 를 거쳐 간접적으로 정해지므로 이행 함수 종속이고, 이는 3NF 위반이다.
BCNF 는 모든 함수 종속 X → Y 에서 X 가 슈퍼키여야 한다는 조건, 곧 모든 결정자가 후보키여야 한다는 조건을 더 요구한다.

근거 — 장 본문 §4.3 「정규형」.

### 8. 조인이 비쌀 때 성능을 얻으려고 중복을 둔다

반정규화는 정규화의 역과정으로, 의도적으로 중복을 허용한다.
조인이 비싸서 성능이 문제가 될 때 테이블을 합치거나 값을 겹쳐 두어 조인을 줄인다.
정규화는 설계의 정확성을, 반정규화는 성능을 얻는 쪽이라 둘은 트레이드오프다.

근거 — 장 본문 §4.3 「반정규화」.

### 9. 원자성은 Undo, 일관성은 제약 조건, 격리성은 잠금 · MVCC, 지속성은 WAL 이 받친다

| 성질 | 구현 |
|---|---|
| 원자성 | Undo 로그 — 실패하면 변경을 역순으로 되돌린다 |
| 일관성 | 제약 조건 검사 + 트리거 |
| 격리성 | 잠금(Lock) 또는 MVCC |
| 지속성 | WAL — 로그를 먼저 디스크에 쓴다 |

복구에서 Redo 는 커밋된 변경을 다시 적용하므로 지속성을 지킨다.
Undo 는 커밋되지 않은 변경을 되돌리므로 원자성을 지킨다.
WAL 은 운영체제 파일 시스템의 저널링과 같은 원리다.

근거 — 장 본문 §5.2 「ACID」 · §5.5 「회복」 · §9 「분야 간 연결」.

### 10. Non-Repeatable Read 와 Phantom Read 는 여전히 일어난다

Read Committed 는 커밋되지 않은 데이터를 읽는 Dirty Read 만 막는다.
같은 행을 다시 읽을 때 값이 바뀌는 Non-Repeatable Read 와, 같은 조건으로 다시 조회할 때 행 수가 바뀌는 Phantom Read 는 막지 못한다.
격리 수준을 낮추면 성능은 오르고 데이터 정확성은 떨어진다.

근거 — 장 본문 §5.3 「격리 수준」의 표.

### 11. 중간에 풀면 남이 끼어들 수 있고, MVCC 는 읽기가 스냅샷을 보기 때문이다

2PL 에서 잠금을 중간에 풀었다가 다시 잡으면 그 틈에 다른 트랜잭션이 끼어들어 직렬 가능성이 깨진다.
Growing 단계에서 필요한 잠금을 다 잡고 Shrinking 단계에서만 풀면 끼어들 여지가 없다.
MVCC 는 데이터의 여러 버전을 두고, 읽기는 자기가 시작한 때의 스냅샷을 보며, 쓰기는 새 버전을 만든다.
그래서 읽기와 쓰기가 서로를 기다리게 하지 않는다.
대가로 오래된 버전을 정리(vacuum · garbage collection)해야 한다.

근거 — 장 본문 §5.4 「동시성 제어」.

### 12. (가) 만 인덱스로 좁힐 수 있고, 인덱스가 많을수록 쓰기는 느려진다

인덱스는 `dept → gpa → name` 차례로 정렬되어 있다.

```text
(가) dept + gpa       → 맨 왼쪽부터 이어진 접두사(A+B) → 사용 가능
(나) gpa 만           → A 없이 B 만                   → 사용 불가
(다) gpa + name       → A 없이 B+C                    → 사용 불가
```

맨 앞 열 `dept` 를 모르면 `gpa` 가 정렬된 구간을 찾을 수 없어 전체를 훑어야 한다.
인덱스는 삽입 · 삭제 때 함께 갱신해야 하므로 쓰기 성능이 떨어지고 공간도 더 든다.
(직접 계산한 값 — 실행하지 않음)

근거 — 장 본문 §6.2 「복합 인덱스 · 최좌선 접두사 원칙」 · 「인덱스의 비용」.

### 13. 사용자는 「무엇을」, DBMS 는 「어떻게」를 맡고, 조인 순서만 3! = 6 가지다

SQL 은 원하는 결과만 적고, 그 결과를 어떻게 찾을지는 DBMS 가 정한다.
그 「어떻게」를 정하는 모듈이 옵티마이저이며, 비용을 추정해 실행 계획을 고른다.
세 테이블의 조인 순서는 n! 가지이므로 3! = 3 × 2 × 1 = 6 가지다.
여기에 각 조인 방식(중첩 루프 · 해시 조인 · 소트-머지 조인)과 인덱스 사용 여부가 곱해져 경우는 더 늘어난다.
실행 계획은 `EXPLAIN` 명령으로 확인한다.

근거 — 장 본문 §3.1 「왜 선언적인가」 · §7 「쿼리 처리와 최적화」.

### 14. 네트워크는 반드시 실패하므로 P 는 필수이고, 항상 응답하는 쪽은 AP 다

네트워크 분할은 현실에서 피할 수 없으므로 P 를 포기할 수 없고, 실제 선택은 C 와 A 사이에서 이루어진다.
분할 중에 응답을 거부하더라도 잘못된 데이터를 주지 않는 쪽이 CP 다.
오래된 데이터일 수 있어도 항상 응답하는 쪽이 AP 이며, 시간이 지나면 일관성을 회복한다(결과적 일관성).
캐시 · 세션 · 설정처럼 단순 조회가 대부분인 데이터에는 키-값 유형(Redis · DynamoDB)이 맞는다.

근거 — 장 본문 §8.2 「CAP 정리」 · §8.3 「NoSQL 유형별 적합한 사용 사례」.

## 실습 정답

### 실습 1. 수강 테이블을 3NF 까지 쪼개기

**(1) 후보키 구하기**

`student_id` 로 `student_name` · `dept` 가 정해지고(FD1 · FD2), `dept` 로 `dept_head` 가 정해진다(FD3).
그러나 `grade` 는 `{student_id, course_id}` 가 있어야 정해진다(FD4).
`course_id` 는 어떤 FD 의 오른쪽에도 없으므로 키에 반드시 들어가야 한다.
따라서 `{student_id, course_id}` 가 모든 속성을 정하고, 둘 중 하나를 빼면 유일성을 잃으므로 후보키다.

**(2) 부분 종속과 이행 종속**

```text
부분 함수 종속 (키의 일부 student_id 만으로 정해짐)
  {student_id, course_id} → student_name
  {student_id, course_id} → dept
  {student_id, course_id} → dept_head   (student_id → dept → dept_head 를 거쳐)

이행 함수 종속
  student_id → dept → dept_head
```

**(3) 분해**

2NF — 부분 종속을 떼어 낸다.

```text
R1(student_id, course_id, grade)                  키: {student_id, course_id}
R2(student_id, student_name, dept, dept_head)     키: student_id
```

3NF — R2 에 남은 이행 종속 `student_id → dept → dept_head` 를 떼어 낸다.

```text
R1(student_id, course_id, grade)       키: {student_id, course_id}
R2(student_id, student_name, dept)     키: student_id
R3(dept, dept_head)                    키: dept
```

**(4) BCNF 판정**

각 테이블에 남은 FD 의 결정자는 R1 에서 `{student_id, course_id}`, R2 에서 `student_id`, R3 에서 `dept` 다.
모두 자기 테이블의 후보키이므로 세 테이블은 BCNF 다.
(직접 계산한 값 — 실행하지 않음)

장 본문 §4.2 「함수 종속」 · §4.3 「정규형」에 기댄다.

### 실습 2. 순차 스캔과 인덱스 검색의 비교 횟수

**(1) n = 1,000,000**

순차 스캔의 최악은 모든 행을 보는 것이므로 1,000,000 번이다.
2¹⁹ = 524,288 < 1,000,000 ≤ 1,048,576 = 2²⁰ 이므로 ⌈log₂ 1,000,000⌉ = 20 이다.
장 본문의 「~20번」과 맞는다.

**(2) n = 100,000,000**

순차 스캔의 최악은 100,000,000 번이다.
2²⁶ = 67,108,864 < 100,000,000 ≤ 134,217,728 = 2²⁷ 이므로 ⌈log₂ 100,000,000⌉ = 27 이다.

**(3) 100배 늘었을 때**

```text
순차 스캔 : 1,000,000 → 100,000,000   100배
인덱스    : 20 → 27                    7번 증가
```

행 수가 100배가 되면 순차 스캔은 비교 횟수도 100배가 되지만, log₂ 기준으로는 log₂ 100 ≈ 6.6 만큼만 늘어 정수로 올리면 7번 늘었다.
(직접 계산한 값 — 실행하지 않음)

장 본문 §6.1 「왜 인덱스가 필요한가」에 기댄다.

### 실습 3. 시간표를 보고 이상 현상과 필요한 격리 수준 고르기

| 시간표 | T1 이 읽는 값 | 이상 현상 | 막는 가장 낮은 수준 |
|---|---|---|---|
| (가) | 50 — 커밋되지 않은 값이며, T2 가 롤백하면 없던 일이 된다 | Dirty Read | Read Committed |
| (나) | 처음 100, 다시 읽으면 50 | Non-Repeatable Read | Repeatable Read |
| (다) | 처음 2, 다시 세면 3 | Phantom Read | Serializable |

풀이는 장 본문 §5.3 의 정의에 시간표를 하나씩 맞춰 본 것이다.
(가) 는 다른 트랜잭션이 아직 커밋하지 않은 데이터를 읽었다.
표에서 Dirty Read 를 처음 「방지」하는 수준은 Read Committed 다.
(나) 는 같은 행을 두 번 읽었는데 그 사이 수정 + 커밋이 끼어 값이 달라졌다.
표에서 Non-Repeatable Read 를 처음 「방지」하는 수준은 Repeatable Read 다.
(다) 는 같은 조건의 조회에서 그 사이 삽입 + 커밋이 끼어 행 수가 달라졌다.
표에서 Phantom Read 를 「방지」하는 수준은 Serializable 하나뿐이다.
(직접 계산한 값 — 실행하지 않음)

장 본문 §5.3 「격리 수준」의 표와 세 이상 현상의 정의에 기댄다.
