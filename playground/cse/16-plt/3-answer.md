## 퀴즈 정답

### 1. 공유 상태가 없으면 경쟁할 대상이 없다

불변성은 데이터를 바꾸지 않고 새 데이터를 돌려준다.
여러 실행 흐름이 같은 값을 읽기만 하니, 동시에 쓰다 꼬이는 공유 상태가 생기지 않는다.
그래서 경쟁 상태가 원천적으로 일어날 수 없다.
OOP 는 객체의 상태를 변이(mutation)하는 방식이라 여러 흐름이 같은 객체를 바꿀 때 경쟁 상태가 생긴다.

근거: 장 본문 「2.2 명령형」의 OOP 한계 · 「2.3 함수형」의 「왜 함수형이 다시 주목받는가 (1)」.

### 2. 뿌리는 `+`, 곱셈이 먼저다

`2 * 3` 은 `<term> "*" <factor>` 로 묶여 하나의 `<term>` 이 된다.
그 `<term>` 과 `4` 가 `<expr> "+" <term>` 규칙으로 묶인다.
그래서 AST 는 다음과 같다.

```text
      [+]
     ╱   ╲
   [*]   [4]
  ╱   ╲
[2]   [3]
```

뿌리는 `+` 이고, 트리 아래쪽에 있는 `*` 가 먼저 계산된다.
값은 6 + 4 = 10 이다.
(직접 계산한 값 — 실행하지 않음)

근거: 장 본문 「3.1 BNF와 문맥 자유 문법」의 「연산자 우선순위가 문법에 인코딩되는 방식」 · 「3.2」의 AST 예.

### 3. 토큰은 정규 언어, 구문은 CFG 와 푸시다운 오토마타

토큰의 구조는 단순하다(식별자 = `[a-z][a-z0-9]*`, 숫자 = `[0-9]+`).
정규 언어로 표현되니 정규식으로 적고 DFA 로 인식할 수 있다.
구문 분석은 문맥 자유 문법(CFG)과 푸시다운 오토마타에 대응한다(Ch.04).
하향식(LL · 재귀 하강)은 직관적이고 손으로 구현하기 쉬워 많은 컴파일러가 쓴다.
상향식(LR · LALR)은 더 넓은 문법을 인식해 복잡한 문법에 맞고, yacc/bison 같은 도구가 이 방식이다.

근거: 장 본문 「3.2 어휘 분석과 구문 분석」 · 「3.1」의 「왜 BNF/CFG를 쓰는가 (3)」 · 「10.1」 파이프라인.

### 4. 첫 인수 7 이 남는다

`λx.λy.x` 는 첫 인수를 돌려주고 두 번째 인수를 무시하는 상수 함수다.
1단계: `(λx.λy.x) 7` → `x` 자리에 7 을 넣어 `λy.7`.
2단계: `(λy.7) 8` → `y` 는 본문에 없으므로 결과는 `7`.
(직접 계산한 값 — 실행하지 않음)
세 구성 요소는 변수(`x`) · 추상화(`λx.M`) · 적용(`M N`)이다.

근거: 장 본문 「11. 람다 대수」의 구성 요소와 예시.

### 5. 공리적 의미론(호어 논리)이다

`{P} S {Q}` 꼴은 사전 조건 · 문장 · 사후 조건의 관계로 의미를 정하는 공리적 의미론이다.
조작적 의미론으로 적으면 `<x = x + 1, {x: 3}> → {x: 4}` 꼴이 된다.
공리적 의미론은 프로그램이 명세를 만족한다는 정당성을 형식적으로 증명할 수 있게 해 준다.
그래서 안전 필수 시스템의 형식 검증 기반이 된다.

근거: 장 본문 「4.2 조작적 의미론」 · 「4.4 공리적 의미론」.

### 6. 빠른 바인딩은 안전 · 효율, 늦은 바인딩은 유연

컴파일 시 바인딩(정적 타입)은 실행 전에 타입 오류를 잡고 최적화할 수 있지만 유연성이 낮고 선언이 장황할 수 있다.
실행 시 바인딩(동적 타입)은 짧고 유연하지만 오류가 실행해 봐야 드러나고 최적화가 어렵다.
타입 추론은 선언을 쓰지 않아도 컴파일러가 사용 맥락에서 타입을 정한다.
그래서 정적 타입의 안전성과 동적 타입의 간결함을 함께 얻는다.

근거: 장 본문 「5.1 바인딩」 · 「6.2 정적 vs 동적 타입」 · 「6.3 타입 추론」.

### 7. 정적이면 1, 동적이면 2

정적 스코프는 코드의 텍스트 위치로 이름을 찾는다.
`f` 는 바깥에서 정의됐으니 `f` 안의 `x` 는 바깥의 `x = 1` 이다 → 1.
동적 스코프는 호출 순서로 찾는다.
`g` 가 `f` 를 불렀으니 `f` 는 `g` 의 `x = 2` 를 본다 → 2.
(직접 계산한 값 — 실행하지 않음)

근거: 장 본문 「5.2 스코프」의 예(같은 구조, 10 과 20 대신 1 과 2).

### 8. 15, 20, 25 — 클로저가 `count` 를 붙잡고 있다

첫 호출: 10 + 5 = 15.
둘째 호출: 15 + 5 = 20.
셋째 호출: 20 + 5 = 25.
(직접 계산한 값 — 실행하지 않음)
`increment` 는 자신이 정의된 환경의 자유 변수 `count` 를 함께 캡처한 클로저다.
그래서 `make_counter()` 가 리턴한 뒤에도 `count` 는 클로저 안에 살아 있고 호출마다 이어서 바뀐다.

근거: 장 본문 「5.3 클로저」의 `make_counter` 예.

### 9. 임시 · 매개변수 · 서브타입 다형성

Java 의 `+` 는 같은 이름이 타입에 따라 다르게 구현되는 임시(ad-hoc) 다형성 · 오버로딩이다.
`List<T>` 는 타입을 매개변수로 받는 매개변수 다형성(제네릭)이다.
`Animal a = new Dog()` 는 서브타입 다형성이고, 동적 디스패치로 `Dog` 의 `speak()` 가 불린다.

근거: 장 본문 「6.4 다형성」.

### 10. 순환 참조는 참조 카운팅이 놓친다

A → B → A 처럼 서로 가리키면 바깥에서 아무도 안 써도 둘 다 참조 수가 1 로 남아 영원히 해제되지 않는다.
Mark-and-Sweep 은 루트(전역 변수 · 스택)에서 도달 가능한 객체만 마킹하고 나머지를 해제하므로, 루트에서 닿지 않는 순환도 쓰레기로 처리한다.
대신 전체 힙을 순회해야 해 느릴 수 있다.
Python 은 이 때문에 참조 카운팅에 순환 탐지기를 함께 쓴다.

근거: 장 본문 「7.1 세 가지 전략」의 「주요 GC 알고리즘」.

### 11. `&T` 는 여럿, `&mut T` 는 하나뿐이다

불변 참조 `&T` 는 여러 개 둘 수 있다.
가변 참조 `&mut T` 는 하나만 둘 수 있다.
가변 참조는 불변 참조와 동시에 공존할 수 없다.
이 규칙으로 데이터 레이스를 컴파일 시점에 막지만, 학습 곡선이 가파르고 컴파일러와 「싸워야」 한다.

근거: 장 본문 「7.1 (3) 소유권 시스템」.

### 12. 마지막 연산이 재귀 호출이어야 한다

`n * factorial(n-1)` 은 재귀 호출이 돌아온 뒤 곱셈을 해야 하므로 마지막 연산이 곱셈이다.
그래서 스택 프레임을 재사용할 수 없고 스택이 O(n) 으로 쌓인다.
`factorial(n-1, n*acc)` 처럼 재귀 호출이 마지막이면 TCO 대상이 된다.
그러나 Python 과 Java 는 TCO 를 지원하지 않아 꼬리 재귀여도 깊어지면 스택 오버플로가 난다.

근거: 장 본문 「8.1 재귀 vs 반복」의 꼬리 재귀 최적화.

### 13. 바깥 객체의 `x` 는 5 다

`p.setX(5)` 시점의 `p` 는 바깥 변수와 같은 객체를 가리키므로 바깥 객체의 `x` 가 5 로 바뀐다.
`p = new Point()` 는 메서드 안의 `p` 가 새 객체를 가리키게 할 뿐 바깥 변수는 그대로다.
그 뒤의 `p.setX(9)` 는 새 객체에만 적용된다.
따라서 바깥 객체의 `x` 는 5 다.
(직접 계산한 값 — 실행하지 않음)
Java 는 참조(주소값)를 값으로 복사해 넘기는 공유에 의한 호출이라, 객체 내부는 바꿀 수 있어도 바깥 참조 자체는 바꿀 수 없다.

근거: 장 본문 「9. 매개변수 전달」.

### 14. m×n 을 m+n 으로, 핫 코드 10% 만 컴파일

IR 이 없으면 3 × 4 = 12 개의 컴파일러가 필요하다.
IR 이 있으면 프론트엔드 3 개 + 백엔드 4 개 = 7 개면 된다.
JIT 는 프로그램 시간의 90% 가 코드의 10% 에서 소비된다는 지역성에 기댄다.
그 10% 의 핫 코드만 컴파일하면 전체의 90% 가 빨라지고, 나머지는 인터프리트해 컴파일 비용을 아낀다.

근거: 장 본문 「10.1 컴파일러 전체 구조」의 「왜 중간 표현(IR)을 쓰는가」 · 「10.3 인터프리터와 JIT」.

## 실습 정답

### 실습 1. 괄호가 들어간 식의 AST 와 값

**1단계 — `2 * (3 + 4)`**
`(3 + 4)` 는 `<factor> ::= "(" <expr> ")"` 규칙으로 하나의 `<factor>` 가 된다.
그 `<factor>` 가 `2` 와 `<term> "*" <factor>` 로 묶이므로 뿌리는 `*` 다.

```text
    [*]
   ╱   ╲
 [2]   [+]
      ╱   ╲
    [3]   [4]
```

계산: 3 + 4 = 7 → 2 × 7 = 14.

**2단계 — `2 * 3 + 4`**
`2 * 3` 이 먼저 `<term>` 으로 묶이고 `+` 가 맨 위 `<expr>` 규칙에서 쓰이므로 뿌리는 `+` 다.

```text
      [+]
     ╱   ╲
   [*]   [4]
  ╱   ╲
[2]   [3]
```

계산: 2 × 3 = 6 → 6 + 4 = 10.

**3단계 — 뿌리가 다른 까닭**
`*` 는 `<term>` 규칙, `+` 는 `<expr>` 규칙에 있어 `*` 가 보통 트리 아래쪽에 놓인다.
괄호는 `<factor>` 단계에서 `<expr>` 를 통째로 다시 열어 주므로, 괄호 안의 `+` 가 `*` 아래로 내려간다.

(직접 계산한 값 — 실행하지 않음)
기대는 절: 장 본문 「3.1 BNF와 문맥 자유 문법」 · 「3.2」의 「파스 트리 vs AST」.

### 실습 2. 순환 참조가 있는 힙에서 쓰레기 찾기

**1단계 — 지우기 전 참조 수**
- A: 루트 → A 하나 → 1.
- B: A → B, C → B 둘 → 2.
- C: B → C 하나 → 1.

**2단계 — 참조 카운팅만 쓸 때**
1. 루트 → A 를 지운다 → A 의 참조 수 1 → 0.
2. A 가 0 이므로 해제된다 → A 가 가진 A → B 참조도 사라져 B 의 참조 수 2 → 1.
3. 남은 참조는 B → C, C → B 뿐이다 → B = 1, C = 1.
4. 어느 것도 0 이 되지 않으므로 B 와 C 는 영원히 해제되지 않는다(순환 참조).

**3단계 — Mark-and-Sweep**
루트에서 출발하는데 루트가 가리키는 객체가 없다.
마킹되는 객체는 없다.
따라서 A · B · C 모두 「마킹 안 된 것」이라 쓰레기로 해제된다.

(직접 계산한 값 — 실행하지 않음)
기대는 절: 장 본문 「7.1 세 가지 전략」의 참조 카운팅 · Mark-and-Sweep.

### 실습 3. 상태를 따라가며 사후 조건 확인하기

**1단계 — 조작적 의미론으로 추적**

```text
<x = 2,     {}>             → {x: 2}
<y = x * 3, {x: 2}>         → {x: 2, y: 6}
<x = x + y, {x: 2, y: 6}>   → {x: 8, y: 6}
```

**2단계 — 호어 삼중쌍 판정**
사전 조건 `x = 2` 인 상태에서 `y = x * 3` 을 실행하면 `y = 6` 이다.
이어서 `x = x + y` 를 실행하면 `x = 2 + 6 = 8` 이다.
사후 조건 `x = 8` 이 성립하므로 삼중쌍 `{x = 2} y = x * 3; x = x + y {x = 8}` 은 참이다.

**3단계 — 상수 폴딩**
`x` 가 2 로 알려져 있으면 `y = x * 3` 은 `y = 2 * 3` 이 되고, 컴파일 시 계산해 `y = 6` 으로 바뀐다.

(직접 계산한 값 — 실행하지 않음)
