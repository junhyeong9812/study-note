# cse/13-networks — Ch.13 — 네트워크 (Networks) — 정답

## 퀴즈 정답

### 1. 복잡도 폭발을 막고 계층마다 독립적으로 바꾸기 위해서다
하나의 프로토콜이 모든 일을 맡으면 복잡도가 폭발하고, 하나를 바꾸면 전체가 영향을 받는다.
계층화는 각 계층이 하나의 관심사만 맡고, 아래 계층이 위 계층에 서비스를 주는 구조다.
「편지 내용을 바꿔도 배달 방식은 그대로」는 각 계층을 **독립적으로 변경할 수 있다**는 성질을 가리킨다.
근거: 장 본문 「1.1 네트워크의 근본 문제」.

### 2. 응용 계층으로 묶인다 — OSI 는 설명용 참조 모델이다
OSI 의 5(세션) · 6(표현) · 7(응용) 계층은 TCP/IP 의 응용 계층 하나로 합쳐진다.
OSI 는 이론적으로 깔끔한 분류라 교육 · 참조에 쓰이고, TCP/IP 는 인터넷이 실제로 작동하는 구현 중심 모델이다.
그래서 현실의 표준은 TCP/IP 이지만 설명할 때는 OSI 7계층을 참조한다.
근거: 장 본문 「1.2 OSI 7계층 vs TCP/IP 4계층」.

### 3. 이더넷 헤더 · IP 헤더 · TCP 헤더 · HTTP 데이터 · 이더넷 트레일러 순이다
계층을 내려갈 때마다 그 계층의 헤더가 앞에 붙는다.
- 전송 계층: `[TCP 헤더][HTTP 데이터]`
- 네트워크 계층: `[IP 헤더][TCP 헤더][HTTP 데이터]`
- 링크 계층: `[Eth 헤더][IP 헤더][TCP 헤더][HTTP 데이터][Eth Trailer]`

헤더 셋이 앞에 붙고, 링크 계층에서만 뒤에 트레일러가 하나 더 붙는다.
받는 쪽의 IP 계층은 자기 헤더만 읽고 벗긴 뒤 위로 넘긴다.
각 계층은 안의 내용을 신경 쓰지 않으므로, IP 는 안에 든 것이 TCP 인지 UDP 인지 상관없이 전달한다.
(직접 계산한 값 — 실행하지 않음)
근거: 장 본문 「1.3 캡슐화」.

### 4. MAC 은 같은 네트워크 안에서만 · 스위치는 필요한 포트로만 · ARP 는 IP 로 MAC 을 찾는다
MAC 주소는 NIC 에 붙은 48비트 물리 주소로, 원칙적으로 바뀌지 않고 같은 네트워크 안에서만 의미가 있다.
IP 주소는 논리 주소로, 바꿀 수 있고 전 세계에서 유일한 주소다.
스위치는 MAC 주소를 학습해 목적지 MAC 이 있는 포트로만 프레임을 보낸다.
허브는 모든 포트에 뿌리므로, 필요한 곳에만 보내는 스위치가 더 효율적이다.
ARP 는 IP 주소를 알고 그 장치의 MAC 주소를 알아내려는 프로토콜이다.
브로드캐스트로 묻고, 그 IP 를 가진 장치가 자기 MAC 으로 답한다.
근거: 장 본문 「2. 데이터링크 계층」.

### 5. 호스트 62개 · 브로드캐스트 `10.0.0.63`
1. 호스트 부분은 32 − 26 = 6비트다.
2. 주소 총수는 2⁶ = 64개다.
3. 호스트 부분이 모두 0인 주소(네트워크 주소)와 모두 1인 주소(브로드캐스트)를 빼면 64 − 2 = 62개다.
4. 마지막 옥텟의 호스트 6비트가 모두 1이면 `00111111` = 63 이므로 브로드캐스트 주소는 `10.0.0.63` 이다.

장 본문의 `/24` 예(2⁸ − 2 = 254)와 같은 계산을 6비트에 적용한 것이다.
(직접 계산한 값 — 실행하지 않음)
근거: 장 본문 「3.1 IP 주소와 서브넷팅」.

### 6. RIP 는 벨만-포드 · OSPF 는 다익스트라 · BGP 는 경로로 루프를 막는다
RIP 는 거리 벡터 방식으로, 이웃끼리 라우팅 테이블을 공유하며 벨만-포드 알고리즘에 기댄다.
OSPF 는 링크 상태 방식으로, 모든 라우터가 전체 토폴로지를 알고 다익스트라로 최단 경로를 계산한다.
BGP 는 어떤 AS 를 거치는지 경로 정보를 공유해 **루프를 막는다**.
규모로 보면 RIP 는 소규모 네트워크, OSPF 는 한 조직 내부의 대규모 네트워크, BGP 는 조직 간 · 인터넷 전체에 맞는다.
근거: 장 본문 「3.2 라우팅」, 「7. 분야 간 연결」의 라우팅(다익스트라) ↔ Ch.10.

### 7. IPv4 주소가 모자라서다
IPv4 주소는 부족하다.
내부에서는 사설 주소(192.168.x.x 등)를 쓰고, 바깥과 통신할 때만 공인 IP 로 바꾸면 적은 공인 IP 로 많은 장치를 연결할 수 있다.
근거: 장 본문 「3.2」의 NAT.

### 8. 양쪽 합의를 확인하기 위해서 · 서버가 여럿일 수 있어서다
2번만 주고받으면 서버는 클라이언트가 자기 응답을 받았는지 모른다.
오래된 SYN 이 늦게 도착하면 서버는 SYN+ACK 로 답하고 연결 상태로 들어간다.
클라이언트는 이미 연결을 포기한 상태라, 서버만 혼자 연결 상태로 기다리게 된다.
세 번째 ACK 가 있으면, 클라이언트가 답하지 않을 때 서버가 연결을 해제할 수 있다.
그래서 양쪽 모두의 합의를 보장하려면 최소 3번이 필요하다.
DHCP 서버는 여러 개일 수 있다.
클라이언트는 Offer 들을 받고 Request 로 그중 하나를 고르며, 서버가 ACK 로 그 선택을 확정한다.
근거: 장 본문 「4.1 TCP」의 3-way Handshake, 「5.3 DHCP」.

### 9. 초당 50 패킷 — 윈도우는 ACK 를 기다리지 않고 여러 개를 보낸다
패킷 하나마다 RTT 한 번을 기다리므로 1초 동안 보낼 수 있는 패킷 수는 다음과 같다.
1초 ÷ 20ms = 1,000ms ÷ 20ms = 50 패킷.
장 본문의 예(RTT 100ms → 초당 10 패킷)와 같은 계산이다.
슬라이딩 윈도우는 수신자가 알려 준 W바이트 이내에서 ACK 없이 패킷을 연속으로 보낸다.
파이프라인처럼 네트워크를 채워 처리량을 높인다.
(직접 계산한 값 — 실행하지 않음)
근거: 장 본문 「4.1」의 TCP 흐름 제어.

### 10. A: cwnd 1 · ssthresh 8 / B: cwnd 8
경우 A(타임아웃)의 규칙은 「cwnd = 1, ssthresh = cwnd/2」이다.
ssthresh 는 손실이 일어난 시점의 cwnd 16 을 반으로 나눈 값이므로 16 ÷ 2 = 8 이다.
cwnd 는 1 로 떨어지고 Slow Start 부터 다시 시작한다.
경우 B(3중복 ACK)의 규칙은 「cwnd = cwnd/2」이다.
16 ÷ 2 = 8 로 줄이고, 처음으로 돌아가지 않고 계속 보낸다(Fast Recovery).
(직접 계산한 값 — 실행하지 않음)
근거: 장 본문 「4.1」의 TCP 혼잡 제어 (3) 손실 감지 시.

### 11. 실시간에서는 지연이 재전송보다 나쁘다 · TCP 는 커널에 있어 고치기 느리다
영상 통화에서 1초 전 프레임을 재전송받아 봤자 쓸모가 없다.
재전송을 기다리느라 생기는 끊김보다 약간의 화질 저하가 낫다.
그래서 핸드셰이크 · 재전송 · 흐름/혼잡 제어가 없는 UDP 가 이 자리에 맞는다.
TCP 는 OS 커널에 있어서 업그레이드가 느리다.
QUIC 은 UDP 위의 사용자 공간에서 TCP 의 장점(신뢰성, 혼잡 제어)을 구현하므로, 앱 업데이트만으로 프로토콜을 개선할 수 있다.
근거: 장 본문 「4.2 UDP」.

### 12. PUT 은 전체 · PATCH 는 일부 / 404 는 클라이언트 · 503 은 서버 / 1.1 은 연결을 유지한다
`PUT` 은 자원 전체를 교체하고, `PATCH` 는 자원을 부분 수정한다.
4xx 는 클라이언트 오류이므로 404(없음)는 클라이언트 쪽 문제를 알린다.
5xx 는 서버 오류이므로 503(서비스 불가)은 서버 쪽 문제를 알린다.
HTTP/1.0 은 요청마다 TCP 연결을 만들고 닫아 비효율적이었다.
HTTP/1.1 은 지속 연결(keep-alive)로 한 연결을 여러 요청에 이어 쓴다.
근거: 장 본문 「5.1 HTTP」.

### 13. 루트 → TLD → Authoritative 순서로 묻고, 결과를 TTL 동안 캐싱한다
로컬 DNS 서버는 다음 순서로 묻는다.
1. 루트 DNS 에 `.com` 을 관리하는 곳을 물어 TLD DNS 주소를 받는다.
2. TLD DNS 에 `google.com` 을 물어 Authoritative DNS 주소를 받는다.
3. Authoritative DNS 에 `www.google.com` 을 물어 IP 를 받는다.
4. 받은 결과를 TTL 동안 캐싱한다.

중앙 서버 하나만 두면 단일 장애점이 생기고 전 세계 트래픽이 한곳에 몰린다.
분산하면 부하가 나뉘고, 장애가 격리되며, 로컬 캐시로 속도가 빨라진다.
대부분의 질의는 이 캐시에서 끝나므로 매우 빠르다.
이것이 트리 구조와 캐싱을 실제로 적용한 예다(Ch.09 자료구조와의 연결).
근거: 장 본문 「5.2 DNS」, 「7. 분야 간 연결」.

### 14. 서버만 `bind` · `listen` · `accept` / 소켓은 (IP, 포트) / HTTPS 443 · DNS 53
서버는 `socket()` 다음에 `bind(주소, 포트)` · `listen()` · `accept()` 를 부르고, 클라이언트는 이 셋 대신 `connect()` 를 부른다.
`accept()` 는 연결을 기다리고, `connect()` 가 그 연결을 요청하는 쪽이다.
소켓은 (IP 주소, 포트 번호)의 쌍이다.
포트 번호는 같은 IP 안에서 어떤 프로세스와 통신하는지 구분한다.
well-known 포트는 HTTPS 가 443, DNS 가 53 이다.
근거: 장 본문 「6. 소켓 프로그래밍」.

## 실습 정답

### 실습 1. `/27` 서브넷 하나를 손으로 풀기

**1단계 — 호스트 비트**
32 − 27 = **5비트**다.

**2단계 — 주소 수**
- 주소 총수: 2⁵ = **32개**
- 호스트에게 줄 수 있는 주소: 32 − 2 = **30개** (네트워크 주소와 브로드캐스트 주소를 뺀다)

**3단계 — 주소 범위**
마지막 옥텟만 호스트 비트 5개를 품는다(앞 3비트는 네트워크 부분).

```text
마지막 옥텟  =  000 | 00000   → 네트워크 주소     (호스트 비트 모두 0)  = 0
마지막 옥텟  =  000 | 11111   → 브로드캐스트 주소 (호스트 비트 모두 1)  = 31
```

- 네트워크 주소: **192.168.10.0**
- 브로드캐스트 주소: **192.168.10.31**
- 첫 호스트 주소: **192.168.10.1**
- 마지막 호스트 주소: **192.168.10.30**

**4단계 — 서브넷 마스크**
네트워크 부분 27비트를 1로, 호스트 부분 5비트를 0으로 채운다.
앞 세 옥텟은 모두 1이므로 각각 255 이다.
마지막 옥텟은 `11100000` 이고, 128 + 64 + 32 = 224 다.
- 2진(마지막 옥텟): **`11100000`**
- 점 표기: **255.255.255.224**

(직접 계산한 값 — 실행하지 않음)
근거: 장 본문 「3.1 IP 주소와 서브넷팅」의 CIDR 표기와 `/24` → 2⁸ − 2 = 254 계산.

### 실습 2. cwnd 를 라운드마다 따라가기

**과정**
- 라운드 1~5: 1 에서 시작해 2배씩 늘어 1 → 2 → 4 → 8 → 16 이 된다. 라운드 5 에서 ssthresh 16 에 닿는다.
- 라운드 6~9: 선형 증가로 17 → 18 → 19 → 20 이 된다.
- 라운드 9 의 cwnd 20 에서 3중복 ACK 가 온다. 라운드 10 의 cwnd 는 20 ÷ 2 = 10 이고, 여기서 선형 증가를 잇는다.
- 라운드 11~12: 11 → 12 가 된다.
- 라운드 12 의 cwnd 12 에서 타임아웃이 난다. ssthresh 는 12 ÷ 2 = **6**, cwnd 는 1 이 된다.
- 라운드 13~15: Slow Start 로 1 → 2 → 4 가 된다. 아직 ssthresh 6 아래다.

| 라운드 | cwnd | 단계 |
|---|---|---|
| 1 | 1 | Slow Start |
| 2 | 2 | Slow Start |
| 3 | 4 | Slow Start |
| 4 | 8 | Slow Start |
| 5 | 16 | Slow Start (ssthresh 도달) |
| 6 | 17 | Congestion Avoidance |
| 7 | 18 | Congestion Avoidance |
| 8 | 19 | Congestion Avoidance |
| 9 | 20 | Congestion Avoidance (3중복 ACK) |
| 10 | 10 | Congestion Avoidance (절반에서 이어 감) |
| 11 | 11 | Congestion Avoidance |
| 12 | 12 | Congestion Avoidance (타임아웃) |
| 13 | 1 | Slow Start |
| 14 | 2 | Slow Start |
| 15 | 4 | Slow Start |

타임아웃 직후 ssthresh = **6**.
(직접 계산한 값 — 실행하지 않음)
근거: 장 본문 「4.1」의 TCP 혼잡 제어 (1) Slow Start · (2) Congestion Avoidance · (3) 손실 감지 시.
장 본문의 시각화 그림(지수 증가 → 선형 증가 → 손실 시 감소)과 같은 모양이 숫자로 나온다.

### 실습 3. 윈도우가 처리량을 얼마나 늘리나

**1단계 — 하나씩 보내기**
- 초당 패킷: 1,000ms ÷ 100ms = **10 패킷**
- 초당 바이트: 10 × 1,000 = **10,000바이트**

**2단계 — 윈도우 8세그먼트**
- RTT 한 번(100ms)마다 8개를 보내므로 초당 라운드는 10번이다.
- 초당 패킷: 10 × 8 = **80 패킷**
- 초당 바이트: 80 × 1,000 = **80,000바이트**

**3단계 — 비교**
80,000 ÷ 10,000 = **8배**다.
전송 시간을 0 으로 쳤으므로 처리량은 윈도우 크기에 비례한다.

(직접 계산한 값 — 실행하지 않음)
근거: 장 본문 「4.1」의 TCP 흐름 제어 — RTT 100ms 에서 하나씩 보내면 초당 10 패킷이고, 윈도우는 ACK 를 기다리지 않고 연속으로 보내 파이프라인처럼 네트워크를 채운다.
