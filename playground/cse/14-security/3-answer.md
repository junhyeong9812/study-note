## 퀴즈 정답

### 1. 셋 중 하나라도 빠지면 다른 쪽 구멍으로 무너진다
기밀성만 있으면 제3자가 읽지는 못해도, 메시지가 중간에 바뀌었을 때 받는 쪽이 알아차리지 못한다.
무결성만 있으면 변조는 드러나지만 누구나 내용을 읽을 수 있다.
가용성만 있으면 서비스는 돌아가도 비밀도 지켜지지 않고 변조도 막지 못한다.
세 성질이 서로 다른 위협을 막기 때문에 셋이 함께 있어야 「안전하다」고 말할 수 있다.
근거: 장 §1.1 「CIA 삼각형」.

### 2. ECB 는 같은 블록을 같은 암호문으로, CBC 는 다른 암호문으로 만든다
ECB 는 각 블록을 독립적으로 같은 키로 암호화한다.
첫째와 셋째 평문 블록이 같으니 암호문의 첫째와 셋째 블록도 똑같다.
그래서 암호문만 보고도 「같은 내용이 되풀이됐다」는 패턴이 드러난다(ECB 이미지에서 윤곽이 보이는 까닭).
CBC 는 이전 암호문 블록을 다음 평문 블록에 XOR 한 뒤 암호화한다.
셋째 블록은 둘째 암호문 블록과 섞인 뒤 암호화되므로 첫째 블록과 다른 암호문이 나온다.
근거: 장 §2.2 「운용 모드」.
(직접 계산한 값 — 실행하지 않음)

### 3. 병렬은 CTR, 암호화 + 무결성은 GCM
CBC 는 앞 블록의 암호문이 있어야 다음 블록을 처리하므로 순차적이라 병렬화할 수 없다.
CTR 은 카운터 값을 암호화해 키 스트림을 만들고 평문과 XOR 하므로 블록마다 따로 계산할 수 있어 병렬화가 된다.
GCM 은 CTR 에 인증(MAC)을 더한 모드로, 암호화와 무결성을 함께 준다.
이것을 「인증된 암호화」라 하고, 현대 TLS 의 표준이다.
ECB 는 어느 경우에도 쓰지 않는다.
근거: 장 §2.2.

### 4. 대칭키는 키를 건네는 길이 없고, 비대칭키는 느리다
대칭키는 잠그는 키와 여는 키가 같아서, 상대에게 그 키를 먼저 안전하게 전해야 한다.
인터넷에서 만나서 건넬 수는 없고, 네트워크로 보내면 도청되는 순간 끝난다(키 분배 문제).
비대칭키는 공개키를 누구에게 보여 줘도 안전하므로 이 문제를 풀지만, 모듈러 거듭제곱 때문에 100~1000배 느리다.
그래서 실전에서는 비대칭키로 대칭키를 교환하고, 실제 데이터는 대칭키(AES)로 암호화한다.
근거: 장 §2.1 · §3.1 · §3.2 · §11 「원리 4」.

### 5. 충돌은 반드시 있고, 충돌 저항은 「찾기 어렵다」는 약속이다
입력은 무한히 많고 출력 길이는 고정이라, 비둘기집 원리에 따라 같은 해시를 가진 서로 다른 입력이 반드시 존재한다.
따라서 충돌을 없애는 것은 불가능하다.
충돌 저항은 H(x) = H(y) 인 x ≠ y 를 **찾아내기가** 현실적으로 어렵다는 뜻이다.
MD5 · SHA-1 은 이 성질이 깨져서 보안 용도로 쓰지 않는다.
근거: 장 §4.1.

### 6. 솔트가 없으면 같고, 솔트가 있으면 다르다
저장 방식 (가)에서는 같은 입력에 같은 해시 함수를 쓰므로 두 사용자의 DB 값이 똑같다.
그래서 흔한 비밀번호의 해시를 미리 계산한 레인보우 테이블에서 바로 찾아낼 수 있다.
저장 방식 (나)에서는 사용자마다 salt 가 다르므로 해시 입력이 달라지고, 저장값도 서로 다르다.
같은 비밀번호라도 다른 해시가 되므로 미리 계산한 표가 쓸모없어진다.
근거: 장 §4.2.
(직접 계산한 값 — 실행하지 않음)

### 7. RSA 가 느리기 때문이다
메시지 전체를 RSA 로 서명하면 매우 느리다.
해시(예: 256비트)만 서명하면 빠르다.
해시는 메시지를 대표하므로, 메시지가 바뀌면 해시가 바뀌고 서명 검증이 실패해 무결성도 그대로 지켜진다.
서명은 비대칭키를 거꾸로 쓰는 것이다 — 개인키로 서명하고 공개키로 검증한다.
근거: 장 §5.

### 8. 비대칭키는 인증과 키 교환에만, 데이터는 대칭키로
비대칭키 쪽 기술은 서버 인증(인증서 검증)과 키 교환(ECDHE)에만 쓰인다.
느리기 때문이다.
핸드셰이크에서 합의한 대칭키로 이후의 모든 데이터를 AES-GCM 으로 암호화한다.
빠르기 때문이다.
이것은 4번의 「비대칭으로 키 교환 → 대칭으로 데이터 암호화」 구조가 실제 프로토콜에 들어간 모습이다.
근거: 장 §6.1 · §3.3.

### 9. 루트 CA 의 개인키를 숨겨 피해 범위를 줄이려고
CA 가 없다면 공격자가 자기 공개키를 상대의 공개키인 것처럼 속이는 중간자 공격(MITM)을 막을 수 없다.
CA 는 「이 공개키가 진짜 그 도메인의 것」이라고 서명으로 보증한다.
루트 CA 의 개인키는 극도로 중요해서 오프라인으로 보관한다.
일상적인 서명은 중간 CA 가 맡는다.
중간 CA 가 뚫려도 루트 CA 는 안전하므로 피해가 그 아래로 제한된다.
근거: 장 §6.2.

### 10. 조건이 항상 참이 되어 모든 사용자가 나온다
입력을 그대로 이어 붙이면 쿼리가 이렇게 된다.

```text
SELECT * FROM users WHERE name = '' OR '1'='1'
```

입력의 첫 `'` 가 원래 따옴표를 닫고, 뒤의 `OR '1'='1` 이 SQL 코드로 해석된다.
`'1'='1'` 은 어느 행에서나 참이므로 `WHERE` 조건이 모든 행에서 참이 된다.
따라서 테이블의 모든 사용자 데이터가 돌아온다.
근거: 장 §7.1.
(직접 계산한 값 — 실행하지 않음)

### 11. 데이터가 코드로 해석되는 것이 공통 원인이다
SQL Injection 은 사용자 입력이 SQL 코드로, XSS 는 사용자 입력이 HTML/JS 코드로 해석되어 생긴다.
둘 다 데이터와 코드의 경계가 무너진 것이다.
Prepared Statement 는 입력을 무엇이든 「데이터」로만 넘겨 SQL 코드로 해석될 길을 막는다.
출력 이스케이핑은 `<` 를 `&lt;` 로 바꿔 브라우저가 태그로 읽지 못하게 한다.
공통 교훈은 「사용자 입력을 절대 신뢰하지 마라」다.
근거: 장 §7.1 · §7.2 · §7.4.

### 12. HttpOnly 는 쿠키 자동 첨부를 막지 못한다
HttpOnly 는 자바스크립트가 쿠키를 읽지 못하게 하는 것으로, XSS 로 쿠키를 훔치는 경로를 막는다.
CSRF 는 스크립트가 쿠키를 읽어서가 아니라, 브라우저가 은행 요청에 쿠키를 **자동으로** 붙여 보내서 생긴다.
그래서 HttpOnly 가 있어도 위조 요청에는 쿠키가 그대로 실린다(장의 서술에서 추론 — 장에 직접 쓰인 문장은 아니다).
CSRF 토큰은 악성 사이트가 모르는 랜덤 값을 요구해, 서버가 사용자의 의도인지 가려낼 수 있게 한다.
SameSite 쿠키는 다른 사이트에서 온 요청에 쿠키를 붙이지 않아 자동 첨부 자체를 끊는다.
근거: 장 §7.2 · §7.3.

### 13. 둘 다 「지식」 요소라 MFA 가 아니다
MFA 는 지식 · 소유 · 생체 중 **서로 다른** 요소 2개 이상을 결합하는 것이다.
비밀번호와 PIN 은 둘 다 「알고 있는 것」이라 요소가 하나뿐이다.
하나가 뚫리면 나머지로 보호한다는 MFA 의 취지도 같은 종류의 정보라 약해진다.
JWT 는 토큰 안에 정보를 담고 서명으로 위조 여부를 검증하므로 서버가 세션을 저장할 필요가 없다.
서버가 무상태라 아무 서버나 요청을 처리할 수 있어 수평 확장이 쉽다.
근거: 장 §8.1 · §8.2.

### 14. 덮어쓰기 감지 · 주소 숨기기 · 실행 금지로 각각 끊는다
버퍼 오버플로는 버퍼를 넘친 데이터가 반환 주소를 덮어써, 함수가 리턴할 때 공격자 코드로 점프하는 공격이다.
Stack Canary 는 반환 주소 앞에 랜덤 값을 두고 리턴 전에 확인해 「덮어썼다」는 사실을 잡아내 프로그램을 끝낸다.
ASLR 은 메모리 주소를 랜덤화해 공격자가 「어디로 점프할지」를 예측하지 못하게 한다.
DEP/NX 는 스택 · 힙의 데이터를 실행 불가로 표시해 삽입한 코드가 「실행되는 것」을 막는다.
C/C++ 은 배열 경계를 검사하지 않지만, Rust · Go · Java 는 메모리 안전성을 언어 차원에서 보장해 넘침 자체가 일어나기 어렵다.
근거: 장 §9.1.

## 실습 정답

### 실습 1. 작은 수로 RSA 한 바퀴 돌리기
근거: 장 §3.2 「RSA — 구조 요약」.

**1단계 — n 과 φ(n)**
n = p·q = 3 × 11 = 33
φ(n) = (p−1)(q−1) = 2 × 10 = 20

**2단계 — d 구하기**
3·d ≡ 1 (mod 20) 인 d 를 찾는다.
3 × 7 = 21 = 20 + 1 이므로 d = 7 이다.

**3단계 — 키**
공개키 `(33, 3)`, 개인키 `(33, 7)`.

**4단계 — 암호화**
c = 4³ mod 33 = 64 mod 33 = 64 − 33 = 31

**5단계 — 복호화 (31⁷ mod 33)**
31² = 961, 961 − 33 × 29 = 961 − 957 = 4
31⁴ = 4² = 16
31⁶ = 31⁴ × 31² = 16 × 4 = 64 → 64 mod 33 = 31
31⁷ = 31⁶ × 31 = 31 × 31 = 961 → 961 mod 33 = 4
m = 4 가 돌아온다.

(직접 계산한 값 — 실행하지 않음)

### 실습 2. 작은 수로 Diffie-Hellman 공유 비밀 만들기
근거: 장 §3.3 「Diffie-Hellman」.

**1단계 — A = 5⁶ mod 23**
5² = 25 → 25 mod 23 = 2
5⁴ = 2² = 4
5⁶ = 5⁴ × 5² = 4 × 2 = 8
A = 8

**2단계 — B = 5¹⁵ mod 23**
5⁸ = 4² = 16
5¹⁵ = 5⁸ × 5⁴ × 5² × 5 이다.
16 × 4 = 64 → 64 mod 23 = 18
18 × 2 = 36 → 36 mod 23 = 13
13 × 5 = 65 → 65 mod 23 = 19
B = 19

**3단계 — 공유 비밀**
앨리스: 19⁶ mod 23
19² = 361 → 361 − 23 × 15 = 361 − 345 = 16
19⁴ = 16² = 256 → 256 − 23 × 11 = 256 − 253 = 3
19⁶ = 19⁴ × 19² = 3 × 16 = 48 → 48 mod 23 = 2

밥: 8¹⁵ mod 23
8² = 64 → 64 mod 23 = 18
8⁴ = 18² = 324 → 324 − 23 × 14 = 324 − 322 = 2
8⁸ = 2² = 4
8¹⁵ = 8⁸ × 8⁴ × 8² × 8 이다.
4 × 2 = 8, 8 × 18 = 144 → 144 − 138 = 6, 6 × 8 = 48 → 48 mod 23 = 2

둘 다 K = 2 로 같다.
둘 다 결국 g^(ab) mod p 를 계산한 것이기 때문이다.

**4단계 — 도청자의 시야**
아는 값: g = 5, p = 23, A = 8, B = 19
모르는 값: a = 6, b = 15, K = 2
도청자가 K 를 얻으려면 A 나 B 에서 a 나 b 를 되찾는 이산 로그를 풀어야 한다.
이 작은 수에서는 금방 풀리지만, 실제로는 수가 매우 커서 어렵다.

(직접 계산한 값 — 실행하지 않음)

### 실습 3. 느린 해시가 무차별 대입을 얼마나 늦추나
근거: 장 §4.2 「느린 해시」.

**1단계 — 총 시간(초)**
(가) 10⁹ × 0.000001초 = 10⁹ × 10⁻⁶ = 10³ = 1,000초
(나) 10⁹ × 0.1초 = 10⁸ = 100,000,000초

**2단계 — 단위 바꾸기**
(가) 1,000 ÷ 60 ≈ 16.7분
(나) 하루 = 86,400초이므로 10⁸ ÷ 86,400 ≈ 1,157일
1년 = 365 × 86,400 = 31,536,000초이므로 10⁸ ÷ 31,536,000 ≈ 3.17년

**3단계 — 배수**
10⁸ ÷ 10³ = 10⁵, 즉 10만 배 느려진다.

**4단계 — 정상 사용자**
정상 사용자는 로그인할 때 해시를 한 번만 계산하므로 0.1초 늦어지는 것을 거의 느끼지 못한다.
반면 공격자는 수십억 번을 시도해야 하므로 같은 0.1초가 몇 년으로 불어난다.

(직접 계산한 값 — 실행하지 않음)
