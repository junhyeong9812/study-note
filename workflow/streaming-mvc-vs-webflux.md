# 스트리밍 채팅에 WebFlux가 필요한가 — MVC vs WebFlux 방법론 비교

> 결론 먼저: **이 시스템 규모에선 MVC로 충분하고, 그쪽이 낫다.** 아래는 그 판단의 추상화.

## 1. "스트리밍"이 실제로 요구하는 것

토큰이 생기는 대로 브라우저에 흘려보내려면 필요한 건 딱 두 가지다:

```
① 응답을 조각(chunk)으로 나눠 즉시 flush할 수 있을 것
② 응답이 끝날 때까지 연결을 오래(수십 초) 유지할 수 있을 것
```

이 둘은 **리액티브의 기능이 아니라 HTTP/서블릿의 기능**이다. HTTP는 원래
chunked 전송을 지원하고, Servlet 3.1+의 비동기 처리로 연결 유지도 된다.
Spring MVC는 이를 `ResponseBodyEmitter`/`SseEmitter`로 노출한다:

```kotlin
@GetMapping("/api/chat", produces = [MediaType.TEXT_EVENT_STREAM_VALUE])
fun chat(...): SseEmitter {
    val emitter = SseEmitter(120_000)
    executor.execute {                     // 서블릿 스레드는 즉시 반납(비동기 모드)
        llmStream.forEach { token -> emitter.send(token) }   // 토큰마다 flush
        emitter.complete()
    }
    return emitter                          // 연결은 열린 채 유지
}
```

즉 "MVC = 응답을 한 번에 다 만들어 반환"이라는 통념이 틀린 것이지, MVC가
스트리밍을 못 하는 게 아니다.

## 2. 그럼 WebFlux는 언제 필요한가

두 모델의 진짜 차이는 **스트리밍 가능 여부가 아니라 스레드가 무엇을 기다리며 몇 개나
잡혀 있는가**다.

```
MVC(+async)    연결 유지 자체는 스레드를 안 잡지만, "LLM 응답을 기다리며 forEach 도는"
               작업 스레드가 스트림당 1개 필요. 동시 스트림 100개 = 스레드 100개.
WebFlux        이벤트 루프 몇 개가 수천 연결을 나눠 든다. 스트림당 스레드 0개.
               단, 전 구간(HTTP 클라이언트·저장소 접근)이 논블로킹이어야 이득이 성립.
```

| 기준 | MVC + SseEmitter | WebFlux |
|---|---|---|
| 동시 스트림 수십까지 | 문제 없음 | 문제 없음 |
| 동시 스트림 수백~수천 | 스레드 고갈 위험 | 설계 목적 그 자체 |
| 프로그래밍 모델 | 명령형 — 읽히는 대로 동작 | Mono/Flux 체인 — 에러 삼킴·컨텍스트 유실 함정 |
| 블로킹 라이브러리(JDBC 등) 혼용 | 자연스러움 | 오염 지점 — 별도 스케줄러 격리 필요 |
| 디버깅·스택트레이스 | 평범하게 읽힘 | 리액티브 체인 추적 필요 |
| 기존 코드베이스(backend) | 그대로 | 전면 전환 비용 |

## 3. 이 시스템의 수치를 대입하면

- 동시 사용자: 사실상 1~2명. 동시 채팅 스트림: llm 세마포어가 **2로 상한**.
- 스트림당 스레드 1개 × 최대 2~3 = 걱정할 스레드 수가 아니다.
- backend는 이미 MVC(명령형)로 8개 API가 안정 동작 — 전환은 전면 재작성.

→ WebFlux가 주는 것(수천 연결 확장성)은 여기 없고, 가져가는 것(모델 전환 비용·
에러 삼킴 함정·블로킹 혼용 제약)은 실재한다. **MVC 유지.**

## 4. MVC 스트리밍에서 실제로 조심할 것 (전환보다 이게 중요)

1. **프록시 버퍼링** — nginx가 응답을 모아서 보내면 스트림이 죽는다.
   오라클 mcp conf에서 이미 쓴 패턴 그대로: `proxy_buffering off` (+ 필요시 `X-Accel-Buffering: no`).
2. **타임아웃 3층**: SseEmitter 타임아웃 · 서블릿 async 타임아웃 · 프록시 read 타임아웃 —
   가장 짧은 놈이 스트림을 끊는다. 채팅 예산에 맞춰 정렬할 것.
3. **완료·에러 처리**: `complete()`/`completeWithError()` 누락 시 연결·스레드 누수.
4. **작업 스레드 상한**: 스트림 실행기를 고정 풀로 — llm 세마포어(2)와 정렬.

## 5. 전환 트리거 (미리 정해두는 되돌림 조건)

동시 스트림이 **상시 수백**을 넘거나, 스트림 대기 스레드가 풀을 압박하는 게 관측되면
그때 채팅 경로만 WebFlux(또는 별도 경량 서버)로 분리한다 — 계약이 SSE/HTTP라
소비자(front)는 무변경.
