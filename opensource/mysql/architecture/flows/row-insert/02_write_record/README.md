# write_record

상위: [행 쓰기 (handler -> row0ins)](../README.md)

**서버 계층에서 한 행을 엔진에 쓰는 마지막 함수다.** 보통의 INSERT 에게는 `ha_write_row` 한 번과 AFTER INSERT 트리거가 전부다. REPLACE 와 ON DUPLICATE KEY UPDATE 에게는 엔진이 돌려준 **중복 키 오류가 제어 흐름의 일부**가 된다. 오류를 받아 충돌한 행을 읽고, 갱신하거나 지운 뒤 `ha_write_row` 를 다시 부르는 `while` 루프가 이 함수의 볼거리다.

```cpp
// sql_insert.cc L1801-L1838
bool write_record(THD *thd, TABLE *table, COPY_INFO *info, COPY_INFO *update) {
  int error, trg_error = 0;
  char *key = nullptr;
  MY_BITMAP *save_read_set, *save_write_set;
  ulonglong prev_insert_id = table->file->next_insert_id;
  ulonglong insert_id_for_cur_row = 0;
  DBUG_TRACE;

  /* Here we are using separate MEM_ROOT as this memory should be freed once we
     exit write_record() function. This is marked as not instumented as it is
     allocated for very short time in a very specific case.
  */
  MEM_ROOT mem_root(PSI_NOT_INSTRUMENTED, 256);
  info->stats.records++;
  save_read_set = table->read_set;
  save_write_set = table->write_set;

  const enum_duplicates duplicate_handling = info->get_duplicate_handling();

  if (duplicate_handling == DUP_REPLACE || duplicate_handling == DUP_UPDATE) {
    assert(duplicate_handling != DUP_UPDATE || update != nullptr);
    while ((error = table->file->ha_write_row(table->record[0]))) {
      uint key_nr;
      /*
        If we do more than one iteration of this loop, from the second one the
        row will have an explicit value in the autoinc field, which was set at
        the first call of handler::update_auto_increment(). So we must save
        the autogenerated value to avoid thd->insert_id_for_cur_row to become
        0.
      */
      if (table->file->insert_id_for_cur_row > 0)
        insert_id_for_cur_row = table->file->insert_id_for_cur_row;
      else
        table->file->insert_id_for_cur_row = insert_id_for_cur_row;
      bool is_duplicate_key_error;
      if (!table->file->is_ignorable_error(error)) goto err;
      is_duplicate_key_error =
          (error == HA_ERR_FOUND_DUPP_KEY || error == HA_ERR_FOUND_DUPP_UNIQUE);
```

REPLACE 가 충돌한 행을 처리하는 두 방식이다. 조건이 맞으면 UPDATE 로 바꾸고, 아니면 지운 뒤 루프를 한 바퀴 더 돈다.

REPLACE 는 부딪친 유니크 키가 여러 개면 루프를 여러 번 돈다. 한 바퀴마다 충돌 행 하나를 지우고 다시 써 보는 구조라, 지운 행 수만큼 `stats.deleted` 가 오른다. UPDATE 로 덮어쓴 마지막 충돌도 값이 실제로 바뀌었으면(`HA_ERR_RECORD_IS_THE_SAME` 가 아니면) `stats.deleted` 에 하나로 센다(L2131-L2132).

## 다루지 않는 것

뷰의 `replace_filter` 검사, BLOB 값 보존(`mysql_prepare_blob_values`), 생성 열 재계산, ON DUPLICATE KEY UPDATE 에서 AUTO_INCREMENT 값 충돌 판정(`ER_AUTO_INCREMENT_CONFLICT`), 트리거 실행 내부는 곁가지라 줄만 적었다. `ha_update_row` 와 `ha_delete_row` 가 InnoDB 에서 타는 경로(`row_update_for_mysql`)는 이 흐름이 아니다.
