## G0 - 계획 이해 게이트

**질문** (자기완결 브리핑 - 현재 코드, 호출 경로, 두 알파벳 표, 발생 조건, 기원, 계획을 함께 제시)

> 이 버그가 무엇이고 왜 생기는지, 어떤 자격증명에서 실제로 드러나는지, 이 계획(테스트와 수정)이 그것을 어떻게 잡고 고치는지 직접 설명해 주세요.

**시도 1 - 답변** (원문)

> 자격증명을 하는 알파벳 검사를 하는 과정에서 인코딩 규칙이 틀어져있어서 62번과 63번이 표준 인코더 방식이 아니다. 즉 ~로 번역되어야 하는데 도메인 자격증명을 검사할때 활용되고 이 버그를 활용한 공격이 충분히 가능하다는거구나.

**판정 1 - fail.** 인코더 알파벳이 잘못돼 62번·63번 문자가 표준 Base64와 다르게 나온다는 핵심과 `~`를 관련 문자로 든 것은 맞다. 부족점 셋: (1) 메커니즘이 뒤집혔다 - `~`는 출력 문자("~로 번역되어야")가 아니라 입력 자격증명 속 문자이고, 이 코드는 자격증명을 "검사"하는 쪽이 아니라 "보내는" 쪽이다. (2) 효과를 잘못 짚었다 - 공격이 아니라 정당한 사용자에게 생기는 증상을 봐야 한다. RFC와 기원도 빠졌다. (3) 계획 설명(테스트 입력·단언·수정 전 결과·수정 내용)이 없다. 자기완결 패킷(코드·Base64 동작 표·입력별 결과 표·기원·기존 테스트·계획·힌트)으로 재질문.

**보조 질문 1** (재질문 직후, 원문)

> 아 잠시만 자격증명 비밀번호 부분에서 ~가 들어간 사용자가 ~를 입력했을때 이를 바이너리로 받아서 다시 번역할때 -로 번역해버려서 비밀번호가 틀리는 경우가 생길 수있다 이게 맞을까?

메인 응답: 거의 맞다. 정정 둘 - `~` 자체가 `-`로 바뀌는 것이 아니라 `~`의 하위 6비트가 만든 값 62 조각이 URL-safe 표에서 `-`가 되는 것이고, "다시 번역"하는 곳은 Spring이 아니라 서버다. 결과는 올바른 비밀번호인데도 401.

**보조 질문 2** (원문)

> 아 "RFC 4648 Section 4"로 인코딩하라고 정합니다. 여기서 62번과 63번에 대한 규격이 서버 표준 규격과 달라서 문제가 발생할 수 있다는거네. 스프링 클라이언트가 특정 리눅스나 서버에 자격증명을 요청하는 요청을 보낼때 바이너리화를 할때 문제가 발생한다는거 맞아?새 테스트가 요청 url에 대해서 이게 리소스 요청을 보내거나 할때 앞에 자격증명 도메인이 들어가는 순간 문제가 생기는거 맞을까?

메인 응답: 방향은 맞다. 정정 둘 - 문제 단계는 "바이너리화"(`getBytes()`, 정상)가 아니라 "바이너리를 글자로 바꾸는" 단계이고, URL에 자격증명이 들어갔다고 바로 문제가 생기지 않는다(userinfo가 있고 + `~`가 값 62 자리에 있어야 한다).

**시도 2 - 답변** (원문)

> 그럼 보자 스프링 서버로 요청이 들어왔어. 이러한 바이너리 값을 해독하는 규칙을 7617과같은 규칙으로 해야되는데 이부분이 제대로 되지않았구나. 결국 즉 바이너리가 62번째 자리가 되는 secret에서의 c자리에 ~가 오는 특수한 경우에만 이 문제가 발생한다는거구나. 그래서 사람들은 몰랐지만 이러한 RFC 규칙에 맞도록 코드를 정리할 필요가 있으니 이번 PR이 필요하다는거구나.

**판정 2 - fail (2/2이므로 통과 처리).**

- 맞은 부분: RFC 규칙(7617 -> 4648 표준 Base64)과 맞지 않는 인코딩이 원인이라는 점, `secret`의 `c` 자리(3바이트 묶음의 셋째 바이트라 하위 6비트가 62가 되는 경우)에 `~`가 올 때만 드러난다는 점, 그래서 아무도 몰랐다는 점.
- 남은 간극: (1) 방향이 여전히 반대 - "스프링 서버로 요청이 들어와 해독"이 아니라 Spring이 **클라이언트**로서 userinfo를 **인코딩**해 **보낸다**. 해독은 상대 HTTP 서버가 한다. (2) 효과 - "코드 정리"가 아니라 정당한 자격증명이 401을 받는 실제 인증 실패의 버그 수정이다. (3) 계획(`alice:se~ret` -> 헤더 정확 문자열 단언, 수정 전 `-`로 FAIL, `getEncoder()` 1줄)과 기원(`f95a1f49dfe`)이 빠졌다.

lazy 계획 게이트 규칙상 2회 실패 후 자동 진행은 금지다. 메인은 남은 간극을 "Spring이 보내는 쪽이라는 방향" 하나로 요약하고 "진행 / 계속 정렬"을 물었다.

**정렬 질문** (원문)

> 그럼 너말은 클라이언트인 서버가 url리소스를 유저인포를 인코딩해서 헤더에 보내는데 이 규칙이 잘못되어서 http서버가 잘못받아들일 수 있다는거 맞아?

메인 응답: 맞다 - Spring 애플리케이션이 `UrlResource`로 외부 URL에 접속할 때 클라이언트이고, userInfo를 인코딩해 헤더로 보내는데 알파벳이 RFC와 달라 받는 HTTP 서버가 맞는 비밀번호를 틀린 것으로 받아들일 수 있다. 방향 간극이 해소돼 diff 1로 진행(log: "사용자 정렬 질문으로 방향 간극 해소").

## G1 - diff 1: 실패 테스트가 무엇을 확인하는가

**질문** (diff + `startServer`·`getInputStream`·`customizeConnection` 흐름 + 수정 전 실행 결과 제시)

> 이 테스트가 무엇을 하고 무엇을 확인하는지, 왜 지금 실패하는지, 기존 테스트로는 왜 이 결함을 못 잡았는지 직접 설명해 주세요.

**시도 1 - 답변** (원문)

> 이 테스트는 스프링이 자격증명 요청을 보낼떄 바이너리로 바꾼 값을 검사를 위해 꺼내서 그 값이 맞는 지 확인하는 검사이며, 기존 테스트에서는 62번바이트 경게값이 인코딩 규칙이 서로 공유하는 부분으로 테스트 코드가 설계되어있기 때문이지않아?

**판정 1 - fail.** 맞은 부분: 테스트가 실제 요청을 보내고 서버가 받은 인코딩 값을 꺼내 확인한다는 흐름, 기존 테스트가 두 규칙이 똑같이 처리하는 입력만 써서 결함이 드러나지 않았다는 방향. 부족점: (a) 왜 지금 실패하는지 - 현재 인코더와 기대값·실제값의 어느 글자가 어떻게 다른지 - 가 통째로 빠짐. (b) 무엇을 확인하는지가 "값이 맞는지" 수준 - 왜 `~`를 넣었는지, 무엇과 정확히 비교하는지 없음. (c) "62번 바이트"는 단위가 틀림 - Base64가 다루는 단위는 바이트가 아니다. 자기완결 패킷(새/기존 테스트, 호출 코드, 6비트 단위 표, 인코딩 결과 비교, 실행 결과, 힌트)으로 재질문.

**보조 질문** (원문)

> 현재 표준 Base64의 표준과 URL-safe 2개가 서로 차이가 있는거고 이때 하위 6비트에서 62,63부분에 대한 문제를 보고 있는거잖아? 
> 인코딩될때 ~를 비트화할때 표준은 +로 62번째 비트를 표현하는데 여기서는 -로 표현해서 인코딩 값이 다르잖아 결국 62번째 자리 인코딩이 -가 아닌 +가 되어야 하는데 이때 그럼 궁금한게 ~이게 62번째 비트이며 이걸 표현할때 URL은 -이걸 쓰고, 표준은 +이걸 쓴다는거야?

메인 응답: 핵심은 맞다. 62는 비트 위치가 아니라 **6비트 덩어리의 값**이다. `se~`를 비트로 풀어 `011100 110110 010101 111110` = 28 54 21 62 -> 표준 `c2V+` / URL-safe `c2V-`를 보이고, `~`가 묶음의 셋째 자리여야 하며(`alice:s~cret`에서는 차이 없음) `alice:secret`에는 62/63 조각이 없다는 점을 덧붙였다.

**시도 2 - 답변** (원문)

> 아 이테스트는 결국 바이너리를 제대로 바꿔서 보내는 지 확인하는거고 이때 인코딩을할때 표준이 아닌 URL-safe로 번역되서 문제가 되는건데 기존의 알파벳들은 이러한 문제들이 없었지만, ~이게 문제라기보단 끝단에 바이너리로 값이 62가 올 경우를 하기 위해 ~를 넣은거구나. 기존 테스트는 61이하의 바이너리들만 나와서 그런거지

**판정 2 - pass (2/2).** 결함 원인이 표준이 아닌 URL-safe 인코더라는 점, `~`는 값 62 조각을 만들려고 넣은 것이라는 점, 기존 `alice:secret`에는 62 이상 조각이 없어 두 알파벳 결과가 같았다는 점 - 모두 의미가 맞다. 보완 둘: (1) 무엇을 비교하는지 - 신규 테스트는 헤더 문자열 **전체**를 `"Basic YWxpY2U6c2V+cmV0"`와 정확히 비교하고(ResourceTests.java:523), 기존 테스트는 디코드 후 원문과 비교한다. (2) 용어 - 62는 "바이너리 값"이 아니라 3바이트를 6비트씩 나눈 조각 하나의 값이고, 위치는 "끝단"이 아니라 `se~` 묶음의 넷째 조각이다. 기존 테스트에 없던 것은 62와 63 둘 다다.

## G2 - diff 2: 표준 인코더로 수정

**질문** (diff + 두 인코더 비교 표 + 9경로 공유 + spring-web 선례 + 수정 후 실행 결과 제시)

> 이 수정이 무엇을 바꾸고, 왜 이걸로 새 테스트가 통과하는지 설명해 주세요. 그리고 기존 `alice:secret` 같은 사용자에게는 왜 영향이 없는지도 설명해 주세요.

**시도 1 - 답변** (원문 - 답변과 확인 요청이 한 턴에 함께 있었다)

> 결국 getEncoder()를 통해 표준과 통일시키고 이를 바탕으로 문제를 바로잡는건데, 이렇게 하면 기존에 바뀐건 문제없는지 확인해볼래? 기존에 getUrl로 바꾼건 앞에 유틸 즉 라이브러리 자체가 바뀌여서 그런거지?

메인은 판정과 별도로 두 질문에 답했다. (1) 라이브러리가 바뀐 것이 아니다 - polish 직전 `Base64Utils`에는 `encodeToString`(-> `getEncoder`)과 `encodeToUrlSafeString`(-> `getUrlEncoder`)이 따로 있었고, 6.0.5 deprecation에 따른 이관에서 짝을 잘못 고른 실수다. (2) 기존 동작 - spring-core 5,328건 0 실패, checkstyle 통과, test 소스에 URL-safe 의존 단언 없음.

**판정 1 - pass.** 루브릭 셋 - URL-safe 인코더를 표준 `getEncoder()`로 바꾼다, 값 62 조각이 이제 표준 글자로 바뀌어 새 테스트가 통과한다, `alice:secret`에는 62/63 조각이 없어 영향이 없다 - 을 모두 짚었다. 보완: "바이너리"는 6비트 조각의 값을 뜻하고, 기존 사용자가 무사한 직접적 이유는 0~61번 글자와 패딩(`=`)이 두 알파벳에서 같고 다른 건 62(`-` 대 `+`)와 63(`_` 대 `/`)뿐이라는 것. 판정 워커는 "62/63은 어느 6비트 조각에서든 나올 수 있다"고도 적었는데, 이것은 임의 바이트 기준이고 ASCII 입력에서는 각 3바이트 묶음의 마지막 조각에서만 발생한다 - 메인이 log에서 정정했다.

## 반복된 오해 패턴 / 교훈

세 게이트에서 되풀이된 오해는 네 갈래였다.

1. **방향 반전(클라이언트/서버)** - G0에서 두 번 연속 "스프링이 검사/해독한다"로 읽었다. `UrlResource`가 등장하는 장면에서 Spring은 보내는 쪽이다. 판정 워커 두 번이 같은 지점을 짚었고, 결국 사용자가 스스로 "클라이언트인 ... 인코딩해서 헤더에 보내는데"로 다시 서술하는 정렬 질문에서 닫혔다.
2. **입력과 출력의 혼동** - "~로 번역되어야"(G0 시도 1)처럼 `~`를 결과 문자로 봤다. `~`는 입력 비밀번호 속 문자이고, 바뀌는 것은 그 비트가 만든 조각의 글자다.
3. **단위 혼동(바이트/비트/6비트 조각)** - "62번바이트"(G1 시도 1), "62번째 비트"(보조 질문), "바이너리 값이 62"(G1 시도 2). Base64의 단위는 6비트 조각이고 62는 그 조각의 값이다. 이 혼동은 비트 분해(`se~` -> 28 54 21 62)를 직접 보여 준 뒤에야 풀렸다.
4. **효과의 과대·과소 평가** - G0에서 한 번은 "공격 가능", 한 번은 "코드 정리"로 읽었다. 실제 효과는 그 사이 - 정당한 사용자가 401을 받는 인증 실패다.
5. 교훈: 방향 오해는 설명을 덧붙여도 잘 안 풀렸고, 사용자가 자기 말로 관계를 재서술하게 한 질문 한 번이 가장 효과적이었다. 단위 오해는 반대로 손으로 비트를 풀어 보이는 것이 효과적이었다.
