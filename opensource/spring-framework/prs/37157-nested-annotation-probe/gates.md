## G1 — 계획 게이트 (nested 재귀 probe 설계)

**질문** (원문)

> 1. 오늘 아침의 fix(#37153)처럼 **플래그만 추가하는 것으로는 왜 이 문제가 안
>    잡히고**, probe 반환값에 대한 **재귀 호출**이 왜 필요한가요? (스모크 Case
>    B에서 `outer.value()`가 어떻게 동작했는지 떠올리시면 됩니다)
> 2. annotation 안에 annotation이 들어가는 구조를 재귀로 따라가는데, 이 재귀가
>    **무한히 돌 수 없는 이유**는 무엇인가요?

**시도 1 — 답변** (사용자 원문)

> 아 어노테이션 자체에 대해서는 플래그로 구별이 되지만, probe를 거친 내부 객체
> 안에 어노테이션이 있으면 그건 검사를 안하기에 이것도 검사하도록 probe에 대한
> 재기호출이 필요하다는거고,
> 결국 안에 어노테이션이 없으면 이 재귀가 끝나기 때문에 왜냐면 결국 내부 객체에
> 대해서 Annotation[]이거면 probe재귀가 끝나니깐.

**판정 1** — pass (보완점 1건)

> {pass, 보완점: ②는 실용적 종료 조건(내부에 어노테이션 속성이 더 없으면 재귀
> 종료)만 짚었다 — "순환 참조면 무한 아니냐"는 반례를 막는 구조적 보장, 즉 JLS가
> annotation 멤버 타입의 순환(자기/상호 참조)을 금지해 중첩 깊이가 컴파일 시점에
> 유한함이 보장된다는 근거를 함께 알아두면 완결된다.}

**정답 정리**

1. probe는 "속성을 실호출해 예외를 관측"하는 장치인데, nested annotation 속성은
   **invoke 자체가 성공**한다. JDK가 nested annotation 프록시를 정상 반환하기
   때문이다(스모크 실측: `outer.value()` 성공 -> 그 다음 `inner.color()`에서
   `EnumConstantNotPresentException`). 폭탄이 반환된 프록시 **안**에 있으므로,
   플래그만 켜서 한 겹 호출해서는 아무 예외도 관측되지 않는다. 그래서 fix는
   "플래그 확장 + probe 반환값이 `Annotation`/`Annotation[]`이면 그 인스턴스에
   대해 `forAnnotationType(...).canLoad/validate`를 재귀 호출"이 된다.
2. 재귀 종료 근거는 두 겹이다. (1) 실용적 종료 조건 — 더 이상 annotation 타입
   속성이 없으면 재귀가 내려가지 않는다(사용자가 짚은 부분). (2) 구조적 보장 —
   **JLS가 annotation 멤버 타입의 순환(자기 참조·상호 참조)을 컴파일 시점에
   금지**하므로 중첩 깊이가 문법적으로 유한하다. (2)가 있어야 "순환이면 무한 아니냐"는
   반례 자체가 불가능함이 보장된다.

메인이 게이트 직후 덧붙인 구분(이후 G2에서 재등장): **메타-annotation 그래프는
순환이 가능**하다(`@Retention` 선언에 `@Documented`, `@Documented` 선언에
`@Retention`). 그래서 `AnnotationTypeMappings`는 visited 집합으로 방어한다. F1의
재귀는 그 타입 그래프가 아니라 **멤버 값 트리**를 내려가므로 방어가 필요 없다 —
같은 "annotation 재귀"라도 축이 다르다. 이 내용은
`docs/study/concepts/jls-annotation-rules.md`로 문서화됐다.

> "구동하는 단일 스레드"도 정확히는 스레드별 ThreadLocal 슬롯이라는 뜻. 실질 이해에는
> 영향 없음.)

**정답 정리**

(1) **2겹 mock이 필요한 이유**: 1겹(outer의 `value()`가 바로 예외)으로 만들면 "직접
속성 probe에서 예외 관측"을 검증하는 테스트가 되는데, 그것은 기존 Class/enum
테스트가 이미 검증하는 동작이다. 이번 fix의 새 동작은 "invoke가 **성공해** nested
인스턴스를 받은 뒤 그 안으로 재귀해 들어가 예외를 관측"이므로, 그 재귀 층을
검증하려면 성공적으로 반환되는 inner mock(2겹)이 반드시 필요하다.

(2) **Mockito `UnfinishedStubbingException`**: `given(mock.value())`는 특별한 문법이
아니라 그냥 Java 코드다. JLS가 정한 런타임 인자 평가 순서에 따라 `given(...)` 호출
전에 괄호 안 `mock.value()`가 **실제로 호출**된다. Mockito는 그 호출을 스레드별
ThreadLocal의 "진행 중 stubbing" 1칸 슬롯에 기록(열림)하고 더미 값을 반환하며,
`willReturn`/`willThrow`가 그 슬롯을 읽어 stubbing을 완결(닫힘)한다. 열림-닫힘 쌍
사이에 다른 mock의 stubbing이 새로 열리면 예외다.

```java
// before — UnfinishedStubbingException이 났던 코드
NestedValue annotation = mockAnnotation(NestedValue.class);
given(annotation.value()).willReturn(mockBrokenEnumValueInner());
//   ^ stubbing #1 열림          ^ 인자 평가 중 헬퍼 안에서
//                                 given(inner.value()).willThrow(...)가
//                                 stubbing #2를 열려고 함 → #1 미완결 상태라 예외

// after — 현재 실파일 (AttributeMethodsTests.java:156-163)
EnumValueInner inner = mockBrokenEnumValueInner();   // #2를 여기서 열고-닫아 완결
NestedValue annotation = mockAnnotation(NestedValue.class);
given(annotation.value()).willReturn(inner);         // #1 열림 → 인자는 완성된 변수 → 즉시 닫힘
```

일반 규칙: **헬퍼는 다른 stubbing의 인자 자리에서 호출하지 않는다.** 사용자가 정확히
짚은 표현 그대로 "완결시켜놓고 객체 그 자체로 넣는 것". 이 내용은
`docs/study/concepts/mockito-stubbing-mechanics.md`로 문서화됐다.

부수 정정(서두 문장): "메타-annotation 그래프는 순환이 안 된다"는 반대다. **메타-
annotation 그래프는 순환이 된다**(`@Retention` <-> `@Documented` 실례). 순환이 금지된
쪽은 **멤버 값 타입**이고, F1 재귀가 안전한 근거는 후자다.

**판정 2** — pass (보정 1건)

> {pass — (a) 빈 배열은 둘 다 통과(true/무예외)가 올바른 귀결임을 정정했고, (b)
> false 귀결로 annotation이 소실되는 회귀를 막는다는 가드의 실질을 짚음. 다만 "객체
> 생성이 안 되는 것"은 정확히는 스캔 단계에서 필터링되어 isPresent=false가 되는
> 것(annotation 객체 생성 실패가 아니라 스캔 결과 소실)이라는 점만 보정 필요.}

**정답 정리**

(1) **빈 배열의 올바른 귀결은 "통과"** — 예외도 false도 아니다. `@NestedArrayValue({})`는
문법상 완전히 합법이고, 오염 여부를 물을 **원소 자체가 없다**. 검사할 대상이 없으면
"깨진 게 발견되지 않았다" = 통과다(공허한 참, vacuous truth). "비어 있음"은 결함이
아니므로 예외를 던지면 멀쩡한 annotation을 벌주는 것이 된다.

이 테스트가 잡는 것은 **현재 구현이 아니라 미래의 잘못된 재구성**이다. 현재 배열
분기는 "깨진 원소를 발견하면 false" 구조라 루프 0회면 자연히 말미의 `return true`로
떨어진다.

```java
if (value instanceof Annotation[] nestedArray) {
	for (Annotation nested : nestedArray) {
		if (!...canLoad(nested, source)) {
			return false;      // 깨진 원소를 "발견하면" false
		}
	}
}
return true;                   // 루프 0회 포함, 발견 못 하면 true
```

미래에 누군가 이걸 "적재 가능함이 **증명**될 때만 true"(예: `boolean ok = false;
for(...) ok = ...; return ok;` 식 누적) 구조로 리팩토링하면, 원소가 있는 경우는 동작이
같아 다른 테스트가 전부 green인 채 **루프 0회 경로만 false로 뒤집힌다** — 빈 배열
annotation이 조용히 스캔에서 사라지는(`isPresent=false`) 회귀다. 빈 배열 테스트 한
건이 정확히 그 경로를 고정한다. (판정의 보정: 결과는 "annotation 객체 생성 실패"가
아니라 "스캔 단계 필터링으로 결과에서 소실".)

(2) **`withMessageContaining("EnumValueInner")`가 고정한 계약**: 예외 메시지가 실제로
깨진 **안쪽 프레임**(EnumValueInner의 속성)을 지목한다는 것 — 즉 안쪽 validate가 만든
ISE가 바깥 프레임들에서 재래핑되지 않고 그대로 전파된다는 계약이다. 이 어서션이
없으면, 미래에 각 프레임이 ISE를 자기 컨텍스트로 다시 감싸는 수정(메시지가 바깥
annotation을 지목하게 되는 변화)이 들어와도 "ISE가 던져진다"는 타입 검사만으로는
테스트가 통과해버린다. G3 (1)의 "그대로 재던지기 vs 재래핑" 논의를 어서션으로 못박은
것이다.

## 반복된 오해 패턴

일곱 번의 시도에서 되풀이된 오해는 다섯 갈래이고, 대체로 메커니즘 대신 이름이나 인상으로 답한 형태였다.

1. **이름·표기의 의미로 메커니즘을 대체한다.** G3 (2)에서 로그에 `@Inner`가 찍히는
   이유를 "fixture 이름이 inner라서"로 설명했다. 정답은 "어느 호출 프레임의 catch가
   실행되고 그 프레임의 파라미터가 무엇인가"다. 재질문에서 이름을 지우고 **호출
   스택 그림만** 준 뒤에야 정확한 답이 나왔다.
2. **추측형 메커니즘을 사실처럼 말한다.** G2 (2)의 "단일 프록시라서 다중 주입이
   안 된다"는 방향이 반대였다(프록시는 몇 개든 만들 수 있고, 제약은 stubbing 슬롯
   쪽). 본인이 곧바로 "설명이 필요하다"고 밝힌 것이 회복을 빠르게 했다.
3. **맞는 결론과 상충하는 되물음을 같은 답변에 붙인다.** G4 (1)에서 "빈 배열도 통과가
   맞다"고 쓴 직후 "비었으니 예외가 맞지 않냐"고 되물어 스스로 상충 — 판정이
   fail이 된 직접 원인이다.
4. **가드 테스트의 존재 이유를 "현재 동작 확인"으로 읽는다.** G4 (1)의 빈 배열 테스트,
   그리고 #37153 게이트에서 반복됐던 양성 가드 오해가 같은 뿌리다. 가드는 현재
   구현이 아니라 **미래의 잘못된 재구성**을 겨냥한다.
5. **반대로 이해한 대칭 개념.** "annotation 순환은 금지된다"를 메타-annotation
   그래프에 적용했는데, 순환이 금지된 것은 **멤버 값 타입**이고 메타-annotation
   그래프는 오히려 순환한다.

## 교훈

이 기록이 남긴 것은 힌트를 주는 방식, 사고를 학습 재료로 바꾸는 법, 게이트를 쪼갠 설계의 효과다.

- **fail은 정답 비노출, 부족점만 1~2줄**이라는 1회차 규칙이 실제로 작동했다. G3에서
  정답 대신 호출 스택 그림만 준 재질문이 2회차 pass로 이어졌다 — 정답을 주지 않고
  **오해의 축(이름 -> 프레임)을 바꿔주는 힌트**가 가장 효과적이었다.
- 게이트가 **테스트 코드 버그를 학습 재료로 승격**시켰다. Mockito
  `UnfinishedStubbingException`은 작업 중 실제로 겪은 사고였는데, 게이트 질문이 되면서
  개념 문서 한 편이 남았다.
- 4게이트 중 3건이 1회차 fail이었지만, **전부 두 질문 중 한쪽만 미달**이었다. 게이트를
  두 질문으로 쪼갠 설계 덕에 재질문 범위가 좁아져 2회차가 짧게 끝났다.
- G1(계획)이 유일한 1회 pass였고, 나머지 셋은 구현 세부(mock 구조 · 예외 전파 프레임 ·
  가드 대상)에서 걸렸다. **설계 의도는 잡히지만 실행 층의 "누가 어디서"는 코드 흐름을
  직접 따라가야 잡힌다**는 패턴이다.
