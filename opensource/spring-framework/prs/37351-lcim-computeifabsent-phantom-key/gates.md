## G0 - 계획: 팬텀 키는 왜 생기고 B안은 어떻게 막나

**질문** (두 맵의 필드 선언, `size()`·`containsKey()` 본문, 현재 코드와 B안 스니펫과 함께)

지금 코드에서 "팬텀 키"가 왜 생기는지(두 맵 중 어느 쪽이 어떻게 어긋나는지), 그리고 B안이 그걸 어떻게 막는지.\
새 키일 때 `oldKey == null && value != null` 조건이 각각 무엇을 거르는지.

**되묻기 턴** (원문, 시도로 세지 않음)

> 우선 보면 현재 코드에서 색인에 바로 등록할 때 충돌이 날 수 있어서 그런거야?

-> 충돌이 아니라 두 맵에 **쓰는 시점**이 다르다는 힌트와, `computeIfAbsent("Key", k -> null)`의 빈 추적표(호출 전/줄 1 후/줄 2 후)를 제시.

> 1불에서 케이스키를 호출하면 1줄에서는 convertKey(key)라면 Key가 convertKey이 메서드가 어떤 처리를 하는지 알아야 ?를 기록할 수 있지않아?

-> 지적이 맞다. 패킷에서 `convertKey` 본문이 빠져 있었다. `key.toLowerCase(getLocale())` 스니펫을 추가.

> 1줄에서는 key,{}\
> 2줄에서는 key,Key\
> 이렇게 등록이 되는게 맞아?

-> 반은 맞다. 줄 1 후 색인 `{"key" -> "Key"}`·저장소 `{}`는 맞고, 줄 2 후 저장소 칸이 다르다(함수가 null이면 기록 안 함).

> 1줄은 key,{}\
> 2줄은 key,null 이겠네 key랑 비교했을때 Key니깐?

-> 추론 대신 실행으로 차이를 보였다.

```text
computeIfAbsent(k -> null) 후: {}          size=0  containsKey("Key")=false
put("Key", null) 후:          {Key=null}  size=1  containsKey("Key")=true
```

그리고 판정 대상 질문 셋을 다시 냈다 - (1) 호출 후 `size()`와 `containsKey("key")`의 반환값과 왜 팬텀인가, (2) B안이 등록을 계산 뒤로 옮기면 어떻게 막나, (3) 두 조건이 각각 거르는 경우.

**시도 1 - 답변** (원문)

> 1번에서 size는 각각 1과 0을 반환하고,\
> 2번에서는 이때 팬텀 키 용어를 한번 정리하고 이게 먼지 모르겠어. 이런 유령키를 막으려면 똑같이 비교할때 같은 데이터로 비교해야되니 비교해서 각각 확인 후 등록하겠다는거고,\
> 3번에서 올드키가 null인건 진짜 없는경우이고 벨류가 null이 아닌경우는 해당 키 값이 실제 있을 경우 아니야?

**판정 1 - fail.**
- Q1 오답: `size()`는 1이 아니고, `containsKey`는 boolean이라 0일 수 없다. 두 메서드가 서로 다른 맵을 본다는 점을 짚지 못했다.
- Q2 표면적: 등록(:225 `putIfAbsent`)과 계산(:235)의 순서, 계산 실패 시 무엇이 남는지, 순서를 바꾸면 왜 남지 않는지가 없다.
- Q3: `oldKey == null`이 "어떤 대소문자로도 원래 없던 새 키"라는 이해는 맞다. `value != null`을 targetMap에 기록되는 것과 연결하지 못했고, `oldKey != null`일 때 건너뛰는 이유가 없다.

자기완결 패킷으로 재질문했다. 용어 힌트 - "팬텀(유령)은 있다고 나오는데 실제로는 없는 것".

**시도 2 - 답변** (원문)

> 1번 컨테인키는 false이며\
> 아 타겟은 0인데 실제 값은 1개가 들어있어서 수치가 안맞는구나\
> 2번에서는 애초에 계산 먼저하니깐 순수 등록값을 확인하는구나 그러면 애초에 서로 동일하게 정규화하고 비교한다는 선택지는 없던거야?\
> 3번 타겟에 키값이 등록되었는지 아닌지 보는 거 아니야?  올드키에 있으면 중복이라 이전 값이 깨져서 그럼거 아니야?

**판정 2 - fail + 정답 확정**
- Q1: `containsKey("key")`는 **true**다. 1개 있는 쪽은 색인이고 저장소(값)는 0개다. 불일치 감각은 맞았지만 방향이 거꾸로였다.
- Q2: 남는 것은 색인 항목 `"key" -> "Key"` 하나다. B안은 등록 줄이 계산 뒤에 있으므로 null이면 조건에서 건너뛰고, 예외면 등록 줄에 도달하지 못한다.
- Q3: `value != null` = 매핑이 실제로 기록됨. null인데 등록하면 지금 버그와 같은 팬텀이 생긴다.
  - 판정 워커는 `oldKey`가 있을 때 등록하면 "인덱스가 새 대소문자 키로 덮어써진다"고 설명했다.
  - 메인이 정정했다 - B안은 그 분기에서 `key = oldKey`로 재대입하므로 다시 등록해도 같은 값이 들어갈 뿐(no-op)이고, 건너뛰는 진짜 이유는 "색인이 이미 저장된 키를 올바르게 가리키고 있어 재등록이 불필요"이기 때문이다.
- 설계 질문(정규화 선택지)의 답: 이 클래스는 원래 표기 보존이 계약이다(`keySet()`이 넣은 표기 그대로). 저장소 키까지 소문자로 바꾸면 그 계약이 깨지고, 맵을 하나로 합치는 것은 클래스 재설계라 범위 밖이다.

**정렬** - 플레이북상 계획 게이트 2회 fail은 자동 진행 금지라 사용자에게 진행 방식을 물었고, 사용자가 선택지 "계속 정렬"을 골랐다.\
정답을 보지 않고 자기 말로 다시 설명해 달라는 요청에 대한 재설명 원문:

> 1번에서 색인 맵에서는 값이 색인 되지만 저장소에서는 해당 데이터가 없기에 key에 대해서 true가 나오지만 정직 타겟은 비여있어서 0이 나온다\
> 2번은 값을 계산 먼저하고 등록을 하면 이러한 팬텀키가 생길 이유가 없어지니깐\
> 이렇게하면 각각 key와 Key가 들어있겠지\
> 해당 자료구조는 규약상 실제 저장되는 타겟의 대소문자를 구별하니깐 \
> 그럼 key.Key 2개가 타겟으로 저장되면 키는 key이걸로 2개를 호출시키는거야? 아니면 \
> Key가 있을 때 key를 등록하려고 하면 어떻게 되는거야?

1번(팬텀이 생기는 이유)과 3번(정규화하지 않는 이유)은 정확했다.\
2번의 "각각 key와 Key가 들어있다"는 색인의 소문자 키와 저장소의 원래 키가 **한 쌍**이라는 뜻이지 항목이 둘이라는 뜻이 아니며, null 반환이면 B안에서 둘 다 비어 있다고 교정했다.\
대소문자 변형 질문은 실측(`CaseDemo`)으로 답했다.

```text
put(Key,v1)              -> {Key=v1}  size=1
computeIfAbsent(key,..)  -> returns v1, map={Key=v1}
get(KEY)                 -> v1
put(key,v3) returns      -> v1, map={key=v3}  size=1
```

> 아니 내말은 람다 널은 애초에 키가 없을 때고 실제 벨류가 람다로 들어가는 케이스가 존재하냐고 묻는거라고

(정정: `StompHeaders`는 `LinkedMultiValueMap`을 쓰므로 이 클래스의 예가 아니다. PR 게시 후 확인됐다 - [README](README.md) 3절.)

> 아니 테스트가 value가 아닌 실제 저장되는 값 KEY문자열로 넣는게 맞지않냐는거야

-> 질문을 잘못 이해했다고 인정한 뒤 답했다. 값은 임의의 표식이라 아무 문자열이어도 되고, 대소문자 처리는 키에만 적용된다.\
대안으로 `key -> key`(받은 키를 값으로 반환 - 수정 전에는 `"Key"`가 값으로도 드러남)를 제안했고, 사용자는 선택지 "그대로 유지"를 골랐다.

> 2번은 암먼추지않아?

**판정 2 - fail -> 교정 후 통과 처리**

## G2 - diff 2: B안(계산 후 등록)

**질문** - 수정 후 코드로 한 줄씩 따라가서 각 줄의 실행 여부와 끝난 뒤 두 맵의 상태를 설명.
1. 빈 맵에서 `computeIfAbsent("KEY", k -> "value")` - `oldKey`는 무엇이고, 어느 조건을 거쳐 색인에 무엇이 등록되나.

## 반복된 오해 패턴 / 교훈

일곱 게이트에서 되풀이된 오해는 다섯 갈래였고, 그중 넷이 "두 맵을 한 덩어리로 보는 습관"을 함께 가리킨다.

1. **두 맵을 한 덩어리로 본다** - `size()`와 `containsKey()`가 서로 다른 맵을 읽는다는 점을 놓쳐 G0에서 "1과 0", "containsKey false"(방향 반전) 같은 오답이 반복됐다. 추적표를 색인/저장소 두 칸으로 나눠 채우게 하자 풀렸다.
2. **변수 이름과 값의 종류를 혼동한다** - G2에서 `caseInsensitiveKey`(변환한 키)와 `oldKey`(색인 조회 결과)를 같은 것으로 봤다. 이 혼동은 리뷰 3회차의 네이밍 지적(F5)과 같은 뿌리다 - 같은 클래스 안에서 같은 이름이 반대 의미로 쓰이고 있었다.
3. **null의 두 의미** - "`put`으로 명시한 null 값 항목"과 "함수가 만들지 못해 기록되지 않음"을 구분하지 못해 G4에서 (D)의 size 1을 오답으로 봤다. G0의 `put("Key", null)` 대 `computeIfAbsent(k -> null)` 실측이 이미 같은 차이를 보였는데도 다시 걸렸다.
4. **"실행되지 않음"과 "그 줄에 도달하지 않음"** - G1·G3에서 예외 경로를 "안 멈춘다", "람다가 스킵된다"로 봤다. 실제로는 람다는 실행되고, 그 안의 한 줄에서 예외가 나 아래 줄에 도달하지 않는다.
5. **패킷의 자기완결성** - G0의 `convertKey` 누락, G5의 `put`·`get`·`remove` 본문과 테스트 전문 누락을 사용자가 지적했다. 둘 다 답에 필요한 코드가 질문에 없어 조립을 사용자에게 떠넘긴 경우였고, G5의 해당 턴은 시도로 세지 않았다.
6. 교훈: 두 저장소를 다루는 결함은 **상태표를 저장소별 열로 나눠** 손으로 채워야 잡힌다. 그리고 메인의 설명도 틀릴 수 있다 - G1의 `StompHeaders` 예시와 G5의 변이 설명은 둘 다 PR 게시 후에 정정됐다.
