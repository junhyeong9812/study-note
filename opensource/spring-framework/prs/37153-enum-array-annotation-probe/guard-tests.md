# 개념: 가드 테스트 — red를 만드는 테스트와 green을 지키는 테스트

> PR #37153 학습 중 놓쳤던 개념. 질문의 형태: "왜 3건은 fix 전에 실패하고 2건은
> fix 전에도 통과해? 통과하는 테스트는 왜 넣어?"

## 한 줄 요약

버그 수정 PR의 테스트는 두 종류가 한 세트다: **red 테스트**(수정 전 실패 — "버그가
있다"의 증명이자 "고쳐졌다"의 증명)와 **가드 테스트**(수정 전에도 통과 — "고치면서
아무것도 안 깨뜨렸다"의 증명). 가드는 다시 양성 가드와 음성 가드로 나뉜다.

## PR #37153의 실제 배치

이 PR의 테스트 6건은 검사 축(플래그·canLoad·validate)과 입력 종류(오염된 annotation ·
멀쩡한 annotation)의 격자에 놓인다.

| | 오염된 annotation (willThrow) | 멀쩡한 annotation (willReturn) |
|---|---|---|
| 플래그 | red: probe 대상으로 표시되나 | — |
| canLoad | red: false로 걸러지나 | **양성 가드**: true로 통과하나 |
| validate | red: ISE 던지나 | **양성 가드**: 무예외인가 |
| 플래그(비-enum 배열) | — | **음성 가드**: String[]은 여전히 false인가 |

- **red 3건**: 수정 전 실패해야 정상. test-first에서 "이 테스트가 지금 깨진다"를
  실측하는 것이 버그 재현의 최소 형태다. 수정 후 green으로 넘어가면 그 diff가
  정확히 이 결함을 고쳤다는 인과가 성립한다.
- **양성 가드 2건**: 수정 전에도 green이다(probe를 안 하면 무조건 통과하므로).
  존재 이유는 수정 **후**에 있다 — 새로 추가된 probe가 정상 값을 반환하는
  annotation까지 걸러버리는 **과잉 필터링**을 하지 않음을 고정한다. "fix 전에도
  통과하니 무의미한 테스트"가 아니라, fix가 지켜야 할 보존 동작의 명세다.
- **음성 가드 1건** (리뷰에서 추가): 새 조건 `isArray() && componentType().isEnum()`이
  **비-enum 배열로 과확장되지 않음**을 고정한다. 이게 없으면 미래에 누군가 조건을
  실수로 넓혀도(예: componentType 검사 누락으로 모든 배열 probe) 테스트가 침묵한다
  — 불필요한 리플렉션 비용 증가가 무음으로 통과하는 회귀.

## 일반화

이 배치에서 다른 PR로 옮겨 갈 만한 원칙은 둘이다.

- 무회귀 보증은 두 축이다: (a) 이 diff에 밀착한 가드 테스트, (b) 영향권 전체를
  덮는 기존 회귀 스위트(이번 건은 annotation 패키지 733건). "테스트가 있으니까"가
  아니라 **어느 테스트가 무엇을 보증하는지** 지목할 수 있어야 한다.
- 가드 테스트의 이름은 검증하는 계약을 드러내야 한다 — 이번 PR에서는 파일 기존
  관용구(예외 축 `WhenHas...`/`WhenDoesNotHave...`)에 맞춰 개명했다.
