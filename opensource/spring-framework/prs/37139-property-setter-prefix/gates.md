# PR #37139 — 이해 게이트 기록

> 출처: 세션 07fec95c (2026-08-14~17), 작업 폴더 `docs/plans/2026-08-14/property-setter-startswith/`.
> 답변은 원문 그대로(오타 포함), 판정·정답은 대화에 기록된 것만 옮긴다.

게이트는 계획 1건과 diff 2건으로 모두 세 번 있었고, 그중 둘을 1회차에 통과했다.

| 번호 | 대상 | 시도 | 최종 판정 |
|------|------|------|-----------|
| G1 | 계획 게이트 (`offsetX`의 변경 전후 처리) | 2 | 2회차 fail, 규칙에 따라 통과 처리 |
| G2 | diff A — write 분기 `indexOf` -> `startsWith` | 1 | pass |
| G3 | diff B — 테스트 4건 | 1 | pass |

## G1 — 계획 게이트 (`offsetX`의 변경 전후 처리)

계획 요약: upstream/main 기준 새 브랜치에서 write 분기를 `indexOf("set")`에서 `startsWith("set")`로 전환하고, 비-setter write 메서드는 엉뚱한 이름 대신 `IllegalArgumentException`을 내게 한다. #36911에서 리뷰어 요청으로 떼어낸 스코프다.

**질문** (원문)

> `offsetX(String value)`라는 write 메서드를 `Property` 생성자에 넘기면, **변경 전(indexOf 기반 main)** 과 **변경 후(startsWith)** 각각 어떻게 처리될까요? (o-f-f-s-e-t-X 글자에서 무엇이 매칭되는지로 설명해 주세요)

**시도 1 — 답변**

> 이것도 똑같은 케이스인건데, upset일때 indexOf면 set 뒤에 아무것도 없는데 거기를 가리키면서 거기서부터 프롬퍼티가 ""필드를 찾게 되지만 startsWith라면 이런 문제가 안생기지않아?

**판정 1** — fail (1/2). 부족점:

- `upset`의 indexOf 계산(중간 "set"에 매칭되어 그 뒤가 없으므로 빈 이름)은 정확하다. 다만 질문 대상인 `offsetX`는 빈 이름이 아니라 다른 결과가 나오는데, 그 값이 무엇인지 글자 단위로 짚어야 한다.
- "startsWith면 문제가 안 생긴다"가 구체적으로 어떤 처리인지가 빠졌다. 이런 메서드가 통과되어 다른 이름을 갖게 되는지, 아니면 그 앞에서 무슨 일이 벌어지는지 명시해야 한다.

**시도 2 — 답변**

> X로 반환될꺼고, 프로퍼티 이름이 X겠지, startsWith는 offsetX라는 이름을 가지겟지?

**판정 2** — fail (2/2), 규칙에 따라 통과 처리.

**정답 정리**

전반부는 맞다. `"offsetX".indexOf("set")` -> o(0) f(1) f(2) s(3) e(4) t(5) -> 3, +3 = 6, `substring(6)` = "X". 한 단계가 더 있는데, 마지막에 `StringUtils.uncapitalize`를 거치므로 최종 프로퍼티 이름은 대문자 "X"가 아니라 소문자 `x`다. 어느 쪽이든 `offsetX`와 무관한 엉뚱한 이름이 예외 없이 조용히 만들어진다는 것이 버그의 요지다.

후반부는 틀렸다. write 분기에는 read 분기 같은 폴백이 없다. read 쪽은 `isPlainAccessor`가 false여도 else로 흘러 index=0 -> 이름 전체를 쓰는 경로가 있지만 write 쪽은 구조가 다르다.

```java
int index = name.indexOf("set");   // 변경 후: name.startsWith("set")
if (index == -1) {                 // 변경 후: 시작하지 않으면
    throw new IllegalArgumentException("Not a setter method");
}
```

"set"으로 시작하지 않으면 이름을 만들지 않고 `IllegalArgumentException("Not a setter method")`을 던진다. `offsetX`는 변경 후 "offsetX"라는 프로퍼티 이름을 갖는 게 아니라 생성자 호출 자체가 예외로 실패한다.

이것이 이 변경을 별도 PR로 분리하는 이유이기도 하다. 지금까지 조용히 통과하며 잘못된 이름을 받던 비-setter write 메서드가 이제 명시적으로 거부되므로, 기존 사용자 코드에서 예외가 새로 발생할 수 있는 behavior change다. read 경로의 이름 해석 수정과는 성격이 달라 리뷰어(sbrannen)가 스코프 분리를 요청했다.

## G2 — diff A: write 분기 `indexOf` -> `startsWith`

변경: `indexOf("set")` 및 -1 검사를 `startsWith("set")` 검사로 교체. "set"으로 시작하는 정상 setter만 3글자를 잘라 이름을 만들고 나머지는 전부 `IllegalArgumentException`.

**질문** (원문)

> `updateName(String)`이라는 write 메서드는 **변경 전(indexOf)에도, 변경 후(startsWith)에도 똑같이 예외**가 납니다. `offsetX`는 동작이 바뀌는데 `updateName`은 왜 안 바뀔까요?

**시도 1 — 답변**

> 아 기존에는 애초에 생성이 되는게 문제인데 이제는 생성이 안되고 예외가 발생해서 여기서 동작에 대한 변경이 생긴다는거네.결국 setter가 있으면 오류가 안생기고 중간에 set이있는 문자열이면 그냥 set 뒤의 프롬퍼티를 그대로 필드로 만드는게  문제였고 이게 조용히 성공하니깐 문제라는거네. 그리고 질문에 대한 답변이야 어차피 set자체가 없으면 예외가 발생했던건 똑같으니깐, 그런데 index는 부분일치로라도 set을 찾고 그에 따른 프롬퍼티 필드를 만들었지만,
> 이제는 부분일치가 아닌 실제 앞에 있는 경우만 파악해서?

**판정 1** — pass.

**정답 정리** (판정 워커 서술)

대비를 정확히 짚었다. `updateName`은 "set"이라는 글자열 자체가 없어 indexOf도 -1이라 예외였으므로 변경 전후가 같고(동작 불변), `offsetX`는 중간 "set" 부분일치로 조용히 통과해 엉뚱한 이름을 만들던 것이 이제 시작 위치가 아니라서 거부된다(동작 변경). 정리하면 동작이 바뀌는 집합은 "set을 포함하되 set으로 시작하지 않는 이름"뿐이고, 정상 setter(`setName`)와 set이 아예 없는 이름은 양쪽 다 그대로다.

## G3 — diff B: 테스트 4건

테스트 구성: (1) `setName` -> `"name"` 정상 setter 동작 보존, (2) `updateName` -> 예외("set"이 아예 없는 케이스, 변경 전에도 예외), (3) `offsetX` -> 예외(중간 "set", 변경 전엔 조용히 `"x"`), (4) `upset` -> 예외(끝의 "set", 변경 전엔 `""`).

**질문** (원문)

> 테스트 1(`setName` → `"name"`)은 변경 전에도 통과하던 테스트인데, 이 PR에 왜 필요할까요? 이 테스트가 **막아주는 실수**는 무엇일까요?

**시도 1 — 답변** (되묻기가 함께 있었고, 뒤 문장이 게이트 답변으로 제출됐다)

> 그런데 질문이 있는데 저게 실제 어떤 동작이라 set을 제외하고 필드를 만들 때 이걸 비교하기 위해 메타정보로 만드는 상황인거야? 우선 1번 기본 동작은 보존된다는 논리가 필요하다.

되묻기에 대한 Claude의 답: 메타정보(이름) 생성이 맞다. write 분기가 하는 일은 필드를 만드는 게 아니라 `setName` 같은 메서드에서 "이 setter가 다루는 논리적 프로퍼티의 이름은 `name`이다"라는 문자열을 유도하는 것뿐이다. 그 이름은 `Property` 카드에 저장되고, 이후 `getField()`가 그 이름으로 backing field를 찾거나(애노테이션 수집) `getName()` 소비자들이 비교에 쓴다. 예를 들어 SpEL이 쓰기 전용 프로퍼티를 다룰 때 `new Property(type, null, setterMethod)`로 만드는데, 이때 이름이 없으면 이 분기가 호출된다.

**판정 1** — pass.

**정답 정리** (판정 워커 보강)

핵심 방향(정상 setter의 기본 동작이 보존됨을 고정한다)이 맞아 최소 통과선을 충족한다. 보강: 이 PR은 판별을 엄격하게 만드는 변경이라 "거부해야 할 것을 거부한다"는 축만 테스트하면 반대 방향 실수를 놓친다. 테스트 1은 과도한 엄격화(정상 setter까지 예외로 거부), substring 오프셋 실수(+3이 아닌 값), 프리픽스 검사 자체의 오작성 같은 실수를 잡는 회귀 가드 역할이다.

## 반복된 오해 패턴

fail로 판정된 답변에서 되풀이된 오해는 두 갈래였고, 둘 다 G1에 몰려 있다.

1. **폴백 구조를 read 분기에서 write 분기로 전이.** G1 2회차에서 `offsetX`가 변경 후 "offsetX"라는 이름을 갖는다고 봤다. read 분기에는 else(index=0, 이름 전체) 폴백이 있지만 write 분기에는 없고 곧바로 예외다. 같은 파일 안의 두 분기라도 구조가 다르다는 점을 확인해야 한다.
2. **마지막 변환 단계 누락.** G1에서 `substring(6)` = "X"까지는 맞았지만 `StringUtils.uncapitalize`를 거쳐 `x`가 된다는 마지막 단계가 빠졌다. 이름 유도 경로는 substring 다음에 uncapitalize가 항상 붙는다.

## 교훈

이 기록에서 남는 것은 통과한 답변과 실패한 답변을 가른 서술 방식이다.

- 이 작업은 3개 게이트 중 2개를 1회차 pass로 통과했다. 통과한 답변들의 공통점은 "동작이 바뀌는 집합"과 "안 바뀌는 집합"을 나눠 대조한 서술이었다. G1의 fail도 대조가 아니라 한쪽만 설명한 데서 나왔다.
- 직전 작업(#36911)의 G2에서 다룬 setter 원복 논의가 이 PR의 계획 게이트와 같은 소재였는데, 그때 지적받은 "startsWith가 더 엄격한 쪽"이라는 방향은 유지됐고 남은 오해는 폴백 유무 하나였다. 지적을 받은 축은 다음 게이트에서 교정되는 패턴이 보인다.
