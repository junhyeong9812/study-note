# PR #37186 — 리뷰 과정 기록 (높음 등급 풀코스가 무엇을 바꿨나)

> 이 시리즈 최초의 높음 등급 작업 — 설계 선검증 → blind 테스트 워커 → 듀얼 리뷰
> 루프 3회의 전 과정 기록이다. 中 등급(듀얼 1패스)과 무엇이 달랐는지가 관전 포인트.

## 구성

이 작업의 검증 사슬은 조사에서 리뷰 종료까지 여섯 단계로 이어졌다.

```
조사(연구 워커: 19개 생성 경로 매트릭스·설계 후보 3종 실증)
  → 설계 선검증 (codex high — 구현 전에 설계 자체를 리뷰)
  → blind 테스트 설계 (구현 미열람 워커)
  → 구현 → 리뷰 루프 1 (codex ∥ Opus) → 반영 → 루프 2 → 반영 → 루프 3 (종료)
```

## 설계 선검증 — 구현 전에 잡힌 것 5가지

codex(high effort)가 설계안을 "조건부 미승인"으로 돌려보내며 조건 5개를 달았고,
전부 구현 전에 반영됐다:

1. **분기 순서**: Serializable 검사보다 **마커(identity) 검사 우선** — 비-HotSpot
   JVM에서 TypeVariable이 Serializable일 경우 복사본이 복원돼 정본성이 깨지는
   미래 호환성 결함을 설계 단계에서 차단.
2. 훅 시그니처 고정(`private Object writeReplace()/readResolve()` — 반환형을
   프록시 타입으로 좁히면 JDK가 훅으로 인식하지 않음).
3. 0-파라미터는 원본 직렬화.
4. `readResolve` 입력 검증 -> `InvalidObjectException`.
5. rawType은 Class 검사 후 캐스트.

교훈: **설계 리뷰는 구현 리뷰보다 싸다.** 같은 지적이 구현 후 나왔다면 코드·테스트
재작업이었을 것이 문서 수정으로 끝났다.

## blind 테스트 설계 — 구현을 모르는 눈이 잡은 것

별도 워커가 spec만 보고 15건을 설계했다(구현 diff 미열람 계약). 핵심 기여 두 가지:

- **I2 함정**: "복원 인스턴스가 원본과 identical"이라는 불변식을 순진하게
  `read.getType() isSameAs type.getType()`으로 쓰면 **어떤 올바른 구현도 실패**한다
  — Synthetic 래퍼는 Spring 객체라 새 인스턴스가 정상이니까. identity 단언은 내부
  JDK Type 원소에만 걸어야 fix-agnostic하다. 실측으로 검증해 설계에 박았다.
- red 10건 예측이 구현 후 실측과 **개수·항목 정확 일치** — 테스트가 spec에서
  나왔고 구현에 끌려가지 않았다는 증거.

## 리뷰 루프 1 — 수렴이 만든 확신, 비대칭이 만든 지적

codex 2건 + Opus 5건, 그중 **2건이 독립 수렴**(서로 다른 모델이 같은 결함 지적):

- **RF3 (수렴·최중요)**: 마커가 하나도 없는 인스턴스(0-파라미터, 전 인자 직렬화
  가능)까지 프록시로 바꾸고 있었다 — **원래 직렬화되던 스트림의 형식이 바뀌어**,
  롤링 업그레이드 중 구버전 서버가 신버전 스트림을 `ClassNotFoundException`으로
  못 읽는 순수 회귀. `encodedVariable` 플래그로 "마커를 실제로 쓴 경우에만 프록시"
  — "프록시는 원래 실패하던 그래프에만 등장한다"는 무악화 원칙의 정확한 구현으로
  교정.
- **RF1**: Synthetic 프록시의 readResolve가 인덱스 **범위**는 검증하면서 배열
  **길이**는 검증하지 않았다 — 마커가 0건인 조작 스트림에서는 범위 검증이 아예
  실행되지 않으므로, 인자 수와 타입 파라미터 수가 어긋난 기형 객체가 조용히
  복원될 수 있었다(형제 클래스에는 있던 검증 — 비대칭이 단서였다).
- RF2(null 필드가 NPE로 새는 문제), RF4(파생 후 직렬화 테스트 부재), RF5(load-
  bearing한 매칭 관용구 2종에 의도 주석) — 모두 반영.
- 기각·해소도 근거와 함께: serialVersionUID(파일 관례 없음 + "버전 간 보증 없음"
  방침), hash의 cross-JVM identity 의존(이 diff 이전부터 모든 직렬화 가능
  ResolvableType의 선재 성질), 순환 참조(생성 순서상 역참조 불가) 등.

## 루프 2 — 리뷰어가 리뷰(주석)를 리뷰하다

Opus가 딱 하나를 채택 지적했다: RF2 때 넣은 주석 "defensive measures against
**tampered streams**"가 **과장**이라는 것. 스트림을 조작할 수 있는 상대는 프록시를
거치지 않고 본체 클래스의 기본 역직렬화 경로로 우회할 수 있으므로, 이 검증은 보안
방어선이 아니다. 실제 효용 — "자기 일관성 없는 스트림에 NPE 대신
`InvalidObjectException`으로 명확히 실패" — 로 문구를 교체했다. 코드가 아니라
**주석의 주장까지 검증 대상**이라는 좋은 사례. (+파일 관례에 맞춰
`@SuppressWarnings("serial")` 2건 추가, write측 arity는 상위 팩토리의 Assert로
도달 불가임을 실코드로 해소.)

## 루프 3 — 종료

양측 모두 "신규 채택 대상 없음" + 6렌즈 전부 applicable-verified(근거 포함).
높음 종료식(open 0 + 신규 채택 0 + 대칭 부담) 충족으로 루프 종료. Opus는 루프 2
수정의 주석이 두 곳에서 **바이트 동일**한 것까지 확인했고, 기각 후보 4건을 사유와
함께 명시했다(리뷰가 "왜 지적하지 않았는가"까지 기록하는 형태).

## 이 과정에서 배운 것

높음 등급 풀코스를 완주하고 남은 것은 관점의 독립, 비대칭이라는 단서, 무악화의 범위 셋이다.

1. **높음 등급의 값은 "단계가 많음"이 아니라 "관점의 독립"이다** — 설계자·blind
   테스트 설계자·리뷰어 2명·감사가 서로의 산출물을 모르거나 의심하는 구조가 각
   단계에서 실제 결함/함정을 하나씩 잡았다.
2. **형제 클래스 간 비대칭은 결함의 냄새다** — 루프 1 채택 5건 중 3건(RF1·RF2·RF3)
   이 "한쪽에는 있는데 다른 쪽에는 없다"에서 나왔다.
3. **무악화는 폴백 조건이 아니라 발동 조건까지 포함한다** — "실패하던 것만 고치고,
   되던 것은 형식조차 바꾸지 않는다".
