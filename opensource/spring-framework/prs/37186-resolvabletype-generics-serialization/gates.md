## 게이트 목록

게이트는 계획 1건과 diff 2건으로 모두 세 번 있었고, 마지막 하나는 사용자가 직접 요구해 열렸다.

| 번호 | 대상 | 시도 | 최종 판정 |
|------|------|------|-----------|
| G1 | 계획 게이트 — 후보 Z/X 분기 기준(질문1) + 동일 인스턴스 복원 원리(질문2) | 2 | pass (판정 워커 2회차 verdict=pass) |
| G2 | diff 게이트 — 인코딩 분기 순서(질문1) + `readResolve` 검증의 방어 대상(질문2) | 2 | fail-통과처리 (2회차 규칙) |
| G3 | 리뷰 반영 diff 게이트(RF) — RF3 `this` 반환(질문1) + RF1 길이 검증(질문2) | 1 | pass (판정 워커 1회차 verdict=pass) |

- 판정 워커가 실제로 돈 것은 4회: 계획 1회차(fail) / 계획 2회차(pass) / diff 2회차(fail-통과처리) / RF 1회차(pass).
- G2의 1회차 답변은 판정 워커에 넘기지 않았다 — 답변 말미가 "1번과 2번에 대해서 너가 한번
  설명해줄 수 있을까?"라는 설명 요청이어서, 메인이 먼저 설명하고 2회차로 재질문했다.
- G3은 사용자가 직접 요구해서 생긴 게이트다. 리뷰 루프 1의 반영 diff가 게이트 없이 넘어가려던 것을
  "멀 수정했는지 ... 제대로 이해했는지 확인해야지"로 사용자가 지적했고, 메인이 "리뷰 반영 diff도
  게이트 대상인데 기계적으로 넘어갔네요"라고 인정하며 열었다.

**정답 정리**

- 질문1(분기 순서) — 한 객체가 두 분기에 **동시에** 해당할 수 있는 환경이 문제다. HotSpot의
  `TypeVariableImpl`은 `Serializable`이 아니라 순서가 무의미해 보이지만, Java 명세는 TypeVariable
  구현이 Serializable인 것을 금지하지 않는다(다른 JVM 구현에서는 가능).
  - Serializable 검사 먼저: raw TypeVariable이 "그대로 직렬화" 분기를 타 -> 역직렬화 시 **새 복사본**이
    생겨 `==`(canonical identity)가 깨지고, `resolveVariable`의 변수 매칭·hash 정합 같은 하류 보장이 무너진다.
  - 마커 검사 먼저: "이 인자는 rawType의 i번째 타입 파라미터"라는 **의미**를 인코딩 -> 어느 JVM에서든
    복원 시 `getTypeParameters()[i]`라는 정본으로 되돌아온다.
  - 일반화: "직렬화 가능한가"는 우연한 구현 속성이고 "무엇인가"는 의미다. 의미 기반 인코딩이 가능한
    값은 항상 의미를 우선해야 이식성 있게 결정론적이다.
  - 근거 코드(`3bb5ed1ae4f`, `ResolvableType.java` L1754-1765): `indexOf(variables, argument)`가 먼저,
    `else if (argument instanceof Serializable)`가 다음, `else return this;`가 마지막.
    `indexOf`는 L1774-1783에서 `variables[i] == argument` identity 비교다.
- 질문2(readResolve 검증의 방어 대상) — 인코딩 실패가 아니라 **신뢰할 수 없는 스트림**이다.
  1. 손상·조작된 스트림(파일·네트워크 경유, 자바 역직렬화는 전통적 공격 표면). 조작이 `index=999`를 넣는 경우.
  2. 양쪽 클래스 정의 불일치 — 직렬화한 쪽은 타입 파라미터 2개, 역직렬화하는 쪽 클래스는 1개.
  - 검증이 없으면 raw `ArrayIndexOutOfBoundsException`으로 엉뚱한 시점에 터지거나, 최악엔 잘못된 변수에
    **조용히** 매칭되어 틀린 타입 해석이 하류로 흐른다. 검증이 있으면 역직렬화 시점에 직렬화 계약의
    표준 신호인 `InvalidObjectException`으로 즉시 실패한다.
  - 근거 코드(`3bb5ed1ae4f`, `ResolvableType.java` L1802-1829): null 가드 -> 길이 검증 ->
    인덱스 범위 검증 -> 인코딩 타입 검증, 전부 `InvalidObjectException`.

**되물음 2에 대한 답** — "다른 버전 클래스가 1개? 이게 가능해?"

가능하고 흔하다. 성립 조건은 "바이트 스트림이 만들어진 시점/장소와 읽히는 시점/장소 사이에
클래스 정의가 바뀌는 것"이며 실제 경로 셋:
1. 서로 다른 서버 간 전송 — HTTP 세션 복제(톰캣 클러스터), Redis 등 캐시에 직렬화 객체 저장 후
   다른 노드가 읽기, RMI, 메시지 큐. 롤링 배포 중이면 두 노드의 배포 버전이 반드시 다르다.
2. 같은 서버의 시간축 — 직렬화해 디스크/캐시에 저장 -> 앱 업그레이드 -> 새 버전이 옛 스트림을 읽음.
3. 대상이 사용자 정의 클래스일 때 — `java.util.List`의 타입 파라미터는 안 바뀌지만
   `forClassWithGenerics`는 앱/라이브러리의 아무 제네릭 클래스에나 쓰인다. `MyContainer<T>`가
   리팩토링으로 `MyContainer<T, U>`가 되는 것은 흔하다.

메인의 덧붙임: Juergen이 gh-36346에서 "버전 간 직렬화는 보증 안 한다"고 했지만,
**보증을 안 하는 것과 보증 밖 입력에 미정의 동작을 해도 되는 것은 다르다.**

## G2 이후 학습 요청 — "정본 인스턴스의 identity"

게이트 판정과 별개로, 사용자가 3연속으로 개념을 다시 세웠다. 이 문답이 이후
`docs/study/concepts/serialization-proxy-and-version-skew.md`의 뼈대가 됐다.

**요청 1** (00:07, 원문)

> 위 직렬화에 대한 서로 다름에 대해서도 이 동작방식과 개념에 대해 별도 문서화가 필요하고, 아 이해했어 이전 서버가 직렬화로 내보낸 작업 데이터가 업데이트 된서버에서는 제대로 직렬화가 안될 수 있다 재로드시. 그리고
> 1번에 대해서 정본 인스턴스의 아이덴티티가 정확히 어떻게 존재하는지 알아야될 꺼같아.
> 너말대로 직렬화 전에 아이덴티티를 인코딩 앞단에 추가해놓고 역직렬화시 해당 인코딩을 역직렬화해서 해당정보를 기반으로 뒷단 인코딩 정보를 매핑해서 문제가 안생기게 한다는 취지가 맞아?

메인 답: 반쯤 맞는데 가장 중요한 지점이 반대다. **identity는 스트림에 실리지 않는다. 실을 수가 없다.**
정본이란 "JVM이 클래스 로드 시 한 번 만들어 캐시한, 그 JVM 안에 하나뿐인 그 객체"이고
identity는 저장된 값이 아니라 **각 JVM 내부에서 성립하는 성질**이다. 스트림에 넣는 것은 identity가
아니라 **정본을 다시 찾아갈 좌표**이며, 동작은 매핑이 아니라 **재조회**(re-lookup)다.
따름정리: 테스트의 "원본과 `isSameAs`"가 성립하는 것은 같은 JVM 안에서 라운드트립했기 때문이고,
다른 JVM으로 건너가면 "받는 쪽 JVM의 정본과 identical"이 된다 — 그리고 그것이 원하는 바다.

**요청 2** (00:10, 원문)

> 이 내용도 방금 말한 개념 문서에 포함해줘 위 내용을 내가 한번 정리해보면, 객체를 직렬화할때 보내는게 아닌 JVM 내에 클래스 객체 주소를 보냄으로 써 역직렬화 사 JVM내 해당 객체 주소를 찾아서 가져옫록 한다는건데,
> 그럼 서로 다른 JVM서버일 경우에도 이 위치가 같을 수 있나?

메인 답: "주소"가 아니라 **이름 기반 좌표**다. 메모리 주소는 절대 보내지 않는다(JVM마다, 재시작마다
달라 무의미). 스트림에 실리는 것은 클래스 **이름**(자바 직렬화가 Class를 이름으로 내보냄)과
정수 마커(0번째 타입 파라미터)다. "위치가 같을 수 있나"의 답은 **위치는 다르지만 같을 필요가 없다** —
받는 쪽이 이름으로 클래스를 로드하고 `getTypeParameters()[i]`로 그 세계의 정본을 얻으면 충분하다.
이 구도가 실패하는 유일한 경우가 버전 스큐이고, 그때 범위 검증이 `InvalidObjectException`으로 끊는다.

**요청 3** (00:12, 원문)

> 아 그럼 jvm내에 heap에 등록되는 객체명을 보내고 이때 마커를 통해 해당 객체 내에 어떤 파라미터 타입인지 이 마커를 이용해서 해당 객체에 대한 클래스타입파라미터를 요청하면 이전에 캐시해놓은 파라미터를 재조회한다는건데,
> 그럼 이게 서로 다른 서버에서도 통한다는거야?

메인 답: 통한다. 한 군데만 다듬으면 "heap에 등록되는 객체명"이 아니라 **클래스의 정식 이름**(FQCN)이다.
조건표: 같은 버전이면 정상 동작 / 클래스가 아예 없으면 `ClassNotFoundException`(자바 직렬화 전반의
기본 동작) / 클래스는 있는데 타입 파라미터 수가 다르면 `InvalidObjectException`.
핵심 통찰: **자바 직렬화는 원래부터 "양쪽에 같은 클래스가 있다"를 전제로 동작하고, 좌표 방식은 그
표준 전제에 아무것도 추가로 요구하지 않는다.** 달라지는 것은 실패의 품질뿐이다.

**요청 4** (00:14, 원문)

> 그럼 사실 같은 클래스 패스를 바라본다면 마커가 왜 필요한거지? 같은 클래스인데 내부 타입 파라미터가 다른 케이스가 존재해?

메인 답: 마커는 "파라미터가 다를까 봐"가 아니라 **"그 객체를 스트림에 실을 수 없어서"** 필요하다.
역할 셋을 분리하면 (1) 문제 = `TypeVariable`은 비직렬화라 바이트로 변환 자체가 안 됨(이것이 고치는
버그 그 자체), (2) 마커 = 못 싣는 객체 대신 실을 수 있는 좌표를 넣는 **운반(transport) 수단**이지
구별(disambiguation) 수단이 아님, (3) 검증 = 같은 버전 안에서는 좌표가 어긋날 일이 없고 버전 스큐나
조작 스트림에서만 생기는 비정상 케이스를 위한 **부가 안전망**.

## 반복된 오해 패턴

이 작업에서 되풀이된 오해는 다섯 갈래이고, 대체로 답의 축을 한 칸씩 옆으로 옮긴 형태였다.

1. **"기법"으로 "기준"을 대체한다** (G1 시도1). "어떻게 고치나"(프록시 패턴)를 "왜 다르게
   취급하나"(계약 상태)의 답으로 내놓았다. 판정 워커가 정확히 이 축을 지적했고, 재질문에서
   축을 명시하자 곧바로 pass했다. 판단 기준을 묻는 질문에는 구현 설명이 답이 되지 않는다.
2. **보존 대상을 순환 표현한다** (G2 시도2). "순서가 보장되기 때문에 순서를 보장한다"는 형태로,
   실제 보존 대상인 **정본 인스턴스 identity**에 도달하지 못했다. 메커니즘의 이름은 붙였으나
   그 메커니즘이 지키는 불변식을 지목하지 못한 경우다.
3. **저장된 값과 성립하는 성질을 혼동한다** (G2 이후 요청1~3). identity를 "인코딩해서 실어 보내는
   값"으로 상상했고("아이덴티티를 인코딩 앞단에 추가"), 다음에는 "클래스 객체 주소"로 상상했다.
   실제는 정반대 — 스트림에는 identity도 주소도 없고 **이름 기반 좌표**만 있으며, identity는
   양쪽 JVM 각각의 캐시가 공짜로 제공하는 성질이다. 3회의 되묻기를 거쳐 도달했다.
4. **되묻기를 답변 자리에 놓는다** (G2 시도1·시도2). 두 시도 모두 답변 대신 "설명해줄 수 있을까?",
   "이게 가능해?"로 끝나 질문2가 미답 처리됐다. 이해를 위한 질문 자체는 좋았지만(요청4의
   "마커가 왜 필요하지?"는 메인이 세션 결산에서 방향을 바꾼 질문으로 꼽았다), 게이트 시도 횟수를
   소모하는 자리에 놓이면 판정에서는 미답이 된다.
5. **방어 코드의 대상을 실패 경로와 혼동한다** (G2 시도1 질문2). "인코딩 불가 재료에 예외가 나면
   안 되니까"로 답했으나, 그 처리는 `writeReplace`의 `this` 반환 폴백 소관이고
   `readResolve` 검증은 **신뢰할 수 없는 입력** 전용이다. 쓰기 측 폴백과 읽기 측 가드는 서로 다른 문제를 푼다.

## 교훈

이 기록이 남긴 것은 버그와 제안을 가르는 기준, 인코딩 설계의 원칙, 그리고 게이트 범위에 대한 반성이다.

- **javadoc의 상태가 버그와 제안을 가른다.** 같은 "직렬화 깨짐"이라도 계약이 살아있으면 PR,
  계약이 문서로 축소돼 있으면 제안이다. 그리고 축소가 적용된 범위(여기서는 파생 3경로)를
  실제로 확인해야 경계가 그어진다 — 사용자의 "일부 포함이라 그런 거 아니야?"가 그 확인이었다.
- **의미 우선 인코딩.** "직렬화 가능한가"는 우연한 구현 속성이고 "무엇인가"는 의미다.
  분기 순서를 의미 쪽으로 고정해야 JVM 구현이 달라져도 결정론적이다.
- **객체를 보내지 말고, 받는 쪽에서 다시 찾을 수 있는 이름/좌표를 보내라.** enum 직렬화가
  이름을 저장하고 읽는 순간 로드된 enum에서 조회하는 것과 같은 패턴이다.
- **정상 경로에서 절대 안 걸리는 검사는 낭비가 아니라 비정상 입력 전용 관문이다.**
  실패는 원인 가까이에서, 계약된 형태(`InvalidObjectException`)로.
- **리뷰 반영 diff도 게이트 대상이다.** 이 원칙은 절차가 아니라 사용자의 지적으로 복구됐다.
  그리고 그 게이트(G3)는 세 게이트 중 유일하게 1회차 pass였다 — 리뷰 findings의 서사가
  "무엇이 문제였고 어떻게 바꿨나" 형태로 먼저 제시된 것이 이해를 도왔다고 볼 수 있다.
- **무악화 원칙.** 프록시는 원래 실패하던 그래프에만 등장해야 한다. 되던 것의 wire form을
  바꾸면 롤링 업그레이드 중 구버전 소비자가 조용히 깨진다.
