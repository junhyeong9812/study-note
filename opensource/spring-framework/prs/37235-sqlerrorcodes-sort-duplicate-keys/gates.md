**판정 2** - verdict: pass (시도 2/2 통과 처리, Sonnet 대체 워커)

Q1 맞은 점: "미스난 코드 이후 각 그룹 배열은 빈 배열이라 전부 무매치"는 정확.
"null 반환 = SQL 예외가 발생하지 않는다"는 구분도 정확 - `translate()`는 `throw`가
아니라 `return null`로 끝난다.

Q1 정정 - **"fallback 자체도 null"은 틀렸다.** 폴백은 **설치되어 있고 실행까지
되지만** 각자의 사유로 null을 반환한다. 정답 경로 네 단계는 이렇다.

1. `SQLErrorCodeSQLExceptionTranslator` 생성자(L95-97)가
   `setFallbackTranslator(new SQLExceptionSubclassTranslator())`로 폴백을 설치한다.
   `errorCode=90002`가 미정렬 배열에서 `Arrays.binarySearch` 미스(L250) -> 다른 그룹도
   전부 미스 -> `doTranslate`가 L297에서 `null` 반환.
2. `AbstractFallbackSQLExceptionTranslator.translate()`(L90-115, 특히 L108-112)가 그
   null을 보고 `fallback.translate(...)`를 호출 - 즉 `SQLExceptionSubclassTranslator`가
   **실제로 실행된다**.
3. `SQLExceptionSubclassTranslator`는 자기 생성자(L70-72)에서
   `SQLStateSQLExceptionTranslator`를 2차 폴백으로 설치해 두었다. 그 `doTranslate`는
   `SQLTransientException` / `SQLNonTransientException` / `SQLRecoverableException`
   세 분기를 검사하는데, 테스트가 만든 것은 `new SQLException("", "", 90002)`라는
   **순수 SQLException**이라 전부 불일치 -> null.
4. 다시 상위 골격이 `SQLStateSQLExceptionTranslator.translate()`를 호출한다.
   `sqlState`가 `""`라 L128 가드 `sqlState.length() >= 2`가 실패해 SQLState 분기를
   통째로 건너뛰고, L161의 `Timeout` 이름 체크도 false -> L166에서 null. 이 클래스는
   자기 폴백을 설정한 적이 없어 상위 L109에서 `fallback == null` -> 그대로 null 반환.

그래서 실패 메시지가 "wrong type"이 아니라 "Expecting actual not to be null"이다 -
애초에 반환값이 예외 객체가 아니라 Java `null`이기 때문. 프로덕션 경로에서는 이
null을 받은 `JdbcTemplate`이 `UncategorizedSQLException`으로 감싸지만, 테스트는
`translator.translate()`를 직접 호출하므로 그 감싸기 단계가 없어 null이 그대로
드러난다.

Q2 - 시도 2 답변이 대체로 정답에 도달했다(오타 정정: "1568" -> 1586, "900002" ->
90002). 정리하면 이렇다.

| 코드 | 배열 index | fix 전 결과 | 이유 |
|---|---|---|---|
| `"1586"` | 1 | **hit (우연)** | 3원소 배열에서 첫 `mid`가 항상 index 1이라 정렬 여부와 무관하게 첫 비교에서 맞는다. 고쳐도 안 고쳐도 통과하는 대조군 |
| `"1062"` | 2 | miss | `"1062" < "1586"`이라 비교가 "왼쪽으로"를 가리키는데 실제 값은 오른쪽에 있다. 왼쪽(index 0 = `"90002"`)으로 갔다가 못 찾음 |
| `"90002"` | 0 | miss | `"90002" > "1586"`이라 비교가 "오른쪽으로"를 가리키는데 실제 값은 왼쪽 끝에 있다. 오른쪽(index 2 = `"1062"`)으로 갔다가 못 찾음 |

정렬 저장 시 셋 다 hit인 이유: 배열이 `["1062","1586","90002"]`가 되어 각 원소가
이진 탐색이 기대하는 상대 위치(작은 값 = 왼쪽 / 큰 값 = 오른쪽)에 오므로, 첫 `mid`
비교 이후의 분기가 항상 그 값이 실제로 있는 방향과 일치한다.

**시도 2 - 답변** (사용자 원문)

> string... 자체가 동적 배열을 받는다는뜻이고, 해당 객체를 생성할때 생성자 내부에서 컴파일러가 배열을 생성해주는 거 아니야? 제네릭타입으로?
> 이때 그냥 순수 배열을 넘기면, String...을 처리할 때 파라미터를 배열인지 그냥 value인지 확인해서 처리하기에 문제 없다는 거 아니야?

**판정 2** - verdict: pass (시도 2/2 통과 처리)

맞은 점: "`String...`은 컴파일러가 배열을 만들어 준다"는 방향은 정확하다. 이것이
첫 번째 층의 핵심이고, 여기서 "정렬되는 배열은 누가 만든 것인가"의 답(호출자가
아니라 컴파일러)에 도달했다.

정정 1 - **생성 위치**. 배열이 만들어지는 곳은 "생성자/메서드 내부"가 아니라
**호출 지점**(call site)이다. `errorCodes.setDuplicateKeyCodes("90002", "1586", "1062")`는
컴파일 시점에 `setDuplicateKeyCodes(new String[] {"90002", "1586", "1062"})`로 바뀐다.
메서드 안에서 보이는 `String[] duplicateKeyCodes` 파라미터는 **그 호출만을 위해 갓
생성된, 호출자 쪽 어느 변수도 참조하지 않는 배열**이다. 그래서 `Arrays.sort`로
제자리 정렬을 해도 훼손될 "호출자의 배열"이 존재하지 않는다.

정정 2 - **제네릭 무관**. varargs는 제네릭과 무관하다. `String...`은 `String[]`
파라미터에 대한 문법 설탕일 뿐이고 타입 소거나 타입 파라미터가 개입하지 않는다.
시그니처는 `String[]`이며 비제네릭 `StringUtils.sortStringArray(String[])`로 그대로
넘어간다.

정정 3 - **뒤 문장은 틀렸다(두 번째 층)**. "배열을 직접 넘기면 배열인지 value인지
확인해서 처리하기에 문제 없다"는 오답이다. `setDuplicateKeyCodes(myArray)`처럼 이미
`String[]`인 값을 넘기면 컴파일러는 **새 배열을 만들지 않고 그 참조를 그대로 전달한다**
(varargs는 "이미 맞는 배열 타입이면 감싸지 않는다"가 규칙이다). 즉 파라미터가
`myArray` 그 자체이고, `Arrays.sort`가 **호출자의 `myArray`를 실제로 제자리에서
변이시킨다**. 검사 후 복사해 주는 안전장치는 없다.

**그럼에도 이 PR의 새 문제가 아닌 이유**: 그 변이는 이 클래스의 기존 관례 그 자체다.
형제 setter 아홉 개(L106, 114, 130, 138, 146, 154, 162, 170, 178)가 전부 동일하게
인자 배열을 제자리 정렬하고 `CustomSQLErrorCodesTranslation.setErrorCodes`(L44)도
같다. 이 한 줄은 새 변이 계약을 도입하는 것이 아니라 **오래된 계약에 합류**하는
것이고, 오히려 `setDuplicateKeyCodes`만 정렬하지 않던 것이 비대칭이자 버그였다.
방어적 복사가 필요하다는 판단이 선다면 그것은 setter 하나가 아니라 열 곳 전체에
대한 별개의 API 변경 논의다.

## 게이트 중 보조 질문

게이트 답변과 별개로 사용자가 던진 질문들이다. 판정 대상은 아니었고, 두 건은
그 자리에서 문서로 반영됐다.

### 1. 실제로 발생할 수 있는 결함이냐 (G1 질문 직후)

> 우선 실제 이러한 문제가 발생할 가능성이 있어? 아니면 그냥 이런일이 발생할 일이 없지만 그냥  기능상 문제라 해당 부분으로 고친다는거야?

답: 둘 다다 - 실제 도달 경로가 있는 결함이면서 발생 빈도는 낮은 "조용한 함정"
부류다. 실발생 경로 셋: (a) 커스텀 `sql-error-codes.xml`은 공식 지원 기능이다,
(b) 숫자 순서와 사전식 순서가 다르므로 사람이 자연스럽게 적은 목록이 미정렬이 될
수 있다(`548, 2601, 2627` 같은 예), (c) 증상이 조용한 예외 강등이라 발견이 늦다.
빈도를 낮추는 요인 셋: 배포 XML이 이미 정렬 상태, well-known 코드는 SQLState 23000
폴백이 가림, 커스텀 구성 자체가 틈새. 결론적으로 PR의 정당성은 발생 빈도가 아니라
**열 개 setter 중 하나만 다르다는 비대칭**에 있다.

부수 발견 하나가 여기서 나왔다. 배포 XML의 Informix `-239,-268,-6017`은 숫자로는
내림차순인데 사전식으로는 오름차순이다 - 누군가 사전식 기준으로 맞춰 놓았다는
흔적이고, "정렬이 계약"이라는 판단의 방증이 됐다.

### 2. 이진 탐색은 앞부터 읽는 것 아니냐 (G1 시도 1 직전)

> 바이너리면 앞부터 읽으니 90002는 찾아지지만 그 뒤에 값이 안찾아지는거 아니야? 바이너리 서치가 뒤부터 탐색하는게 아니지않아?

답: 이 게이트에서 가장 중요한 오해였다. `binarySearch`는 앞에서부터 읽지 않는다.
항상 가운데에서 시작해 비교 결과로 한쪽 절반을 통째로 버린다. 미정렬 배열
`["90002","1586","1062"]`에 대해 손으로 세 번 트레이스해 답했다.

```
"90002" : low=0 high=2 mid=1 "1586" < "90002" -> 오른쪽
          low=2 high=2 mid=2 "1062" < "90002" -> 또 오른쪽
          low=3 > high -> miss        (index 0 에 답이 있지만 그 자리를 한 번도 안 본다)
"1586"  : mid=1 에서 첫 비교 즉시 hit  (우연)
"1062"  : mid=1 "1586" > "1062" -> 왼쪽
          mid=0 "90002" > "1062" -> 또 왼쪽
          high=-1 -> miss
```

정리: "앞에 있으면 찾아진다"가 아니라 **값들의 상대 배치에 따라 복불복**이다.
정렬하면 `["1062","1586","90002"]`가 되어 셋 다 hit이고, 테스트의 red는 90002에서
났다(1586은 우연 hit이라 그 회차는 통과했다).

### 3. SQLState가 `""`인 것은 SQL 문장 때문이냐 (G2 시도 1 앞부분)

> 그럼  failback에서 내부에 호출 되는 객체의 형태가 SQLException객체라서 분기에 전부 불일치해서 null이고 SQLState가 ""이라 length >=2라는게 그럼 ""이렇게 나온다는게, 내부에 sql 자체에 대해 그 sql이 아니라 그런거야?

답: SQLState `""`는 SQL 문장에서 나온 것이 아니다. 테스트가 예외를 그렇게 만들었기
때문이다.

```java
new SQLException("", "", errorCode)
//               ^메시지  ^SQLState  ^벤더 에러코드
```

두 번째 인자가 곧 SQLState다. 프로덕션에서는 이 값을 **JDBC 드라이버가** 실어 주는
표준 5자리 상태 코드(예: `"23000"`)이고, `translate("task", "SQL", ex)`의 `"SQL"`
문자열(실행하던 SQL문)과는 무관하다. 기존 형제 테스트들이 전부 `("", "", code)` 꼴로
예외를 만들어 **에러코드 경로만 고립시키는** 관례라 새 테스트도 그것을 따랐고,
그 덕에 SQLState 폴백이 개입하지 못해 red가 깨끗하게 드러났다.

### 4. varargs 처리 방식을 개념 문서로 (G2 시도 2 직후)

> 이 컴파일이 String...을 어떻게 처리하는지 별도 study문서에 /home/jun/project/spring-framework-fork/docs/study/concepts 여기 안에 동작 방식을 정리해주면 좋을 꺼 가탕.

`docs/study/concepts/java-varargs-mechanics.md`가 이 요청에서 태어났다. `javac`와
`javap`로 실제 바이트코드를 뽑아 쓴 문서이고, 확인된 것은 이렇다.

- 메서드 쪽에는 varargs가 없다: `descriptor: ([Ljava/lang/String;)V` +
  `flags: (0x0088) ACC_STATIC, ACC_VARARGS`. `String[]`을 받는 메서드와 디스크립터가
  글자 하나 다르지 않다.
- 배열은 호출 지점에서 만들어진다: 값 나열 호출은
  `iconst_3 / anewarray / dup+ldc+aastore x3 / invokestatic #30`, 배열 전달 호출은
  `aload_0 / invokestatic #30`. **같은** `#30`이므로 오버로드가 둘인 것이 아니라
  컴파일러가 한쪽에만 배열 생성 코드를 끼워 넣은 것이다.
- 호출자 배열 변이 실증: `caller array after call = [1062, 1586, 90002]`,
  `same reference as stored = true`.

문서에는 이 PR 범위 밖의 함정 둘(`f(null)`이 "인자 없음"이 아니라는 것, 오버로드
모호로 컴파일이 막히는 사례)도 함께 담겼다. 오버로드 모호 사례는 처음에 #37186
문서의 서술에 기대고 있어 확신이 낮다고 보고됐고, `ResolvableType.java` L1162
(`Class<?>...`)와 L1178(`ResolvableType...`)을 실코드로 확인해 확정했다.

## 반복된 오해 패턴

두 게이트에서 같은 종류의 착오가 반복됐다.

1. **"동작하지 않았다"와 "설치되지 않았다"를 섞음** - G1 시도 2의 "fallback 자체도
   null"이 그것이다. 실제로는 폴백 두 단이 모두 설치돼 있고 실행까지 되지만 각자
   다른 사유(순수 `SQLException`이라 서브클래스 분기 무매치 / SQLState가 두 글자
   미만이라 가드에 막힘)로 null을 돌려준다. 이 구분이 없으면 "왜 예외 타입이
   틀린 게 아니라 null이냐"에 답할 수 없다.
2. **"그대로 넘어간다"와 "새로 만들어진다"를 구분하지 않음** - G2의 핵심이다.
   varargs는 호출 형태에 따라 둘 다 일어나고, 그 차이가 곧 "호출자 배열이 변이되나"의
   답이다. 시도 2에서 "컴파일러가 배열을 만든다"까지 도달했지만 **어디서** 만드는지
   (메서드 안이 아니라 호출 지점)를 한 칸 옮겨 짚었다.
3. **관측 결과를 규칙으로 일반화** - G1 시도 1의 "정렬되면 다 찾아진다"는 결과
   서술로는 맞지만, 세 코드가 각각 무엇의 반례인지를 지우면 테스트가 왜 코드를
   셋 쓰는지 설명할 수 없다. 특히 `1586`의 우연 hit은 "코드가 목록에 있으면
   찾아진다"는 직관이 왜 틀렸는지를 보여 주는 장치인데, 뭉뚱그리면 사라진다.
4. **두 사안을 섞음** - G2 시도 1의 "순서를 보장하지 않아서 생기는 문제를 이번에
   고쳤다"는 diff 01의 결함(정렬 누락) 이야기이고, 질문이 물은 in-place 변이의
   책임 소재와는 별개 사안이다.
5. **자료구조 동작을 자기 직관으로 대체** - 보조 질문 2의 "바이너리면 앞부터 읽으니"가
   그것이다. 이 결함 전체가 "정렬 전제가 깨진 이진 탐색"이므로, 이 오해가 남으면
   결함 자체가 보이지 않는다.

## 교훈

이 기록이 남긴 것은 결함의 한 문장 요약, 정답을 주지 않는 재질문의 효과, 게이트가 산출물을 늘린 사례, 그리고 판정 주체의 기록이다.

- 이 결함의 학습 핵심은 한 문장으로 압축된다: **저장측이 지키기로 한 순서 약속을
  조회측이 전제하고 있고, 그 약속을 강제하는 것은 setter의 `sortStringArray` 호출
  하나뿐이다.** 두 게이트의 질문이 전부 이 문장의 다른 각도였다 - G1은 약속이
  깨졌을 때 조회가 어떻게 되는가, G2는 약속을 지키는 그 한 줄이 무엇을 하는가.
- 판정 워커가 "정답을 주지 말고 다시 볼 파일:줄만 지목하라"는 형식으로 동작한 것이
  두 번 다 효과가 있었다. G2 시도 1의 재질문은 테스트 L113에 `String[]` 변수가
  하나도 없다는 사실 하나만 가리켰고, 시도 2에서 사용자가 "컴파일러가 만든다"에
  스스로 도달했다.
- 게이트에서 나온 질문이 산출물을 늘렸다. varargs 질문은 개념 문서 한 편으로
  이어졌고, "실제 발생 가능성이 있냐"는 질문은 배포 XML의 Informix 목록이 사전식
  기준으로 맞춰져 있다는 방증을 찾게 했다.
- 판정 워커가 API 529로 두 번 중단돼 모델을 대체한 것도 기록해 둘 일이다. 판정
  자체는 대체 모델로 정상 수행됐지만, "누가 판정했는가"는 게이트 기록의 일부이므로
  log와 이 문서에 남겼다.
