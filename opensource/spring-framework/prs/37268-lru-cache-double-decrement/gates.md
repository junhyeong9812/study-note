## G1 — diff 01: red 테스트가 무엇을 재는가

**질문** (자기완결 브리핑과 함께)

1. 이 테스트의 마지막 단언이 `currentSize`(내부 카운터)가 아니라 `cache.size()`(map 실크기)를 검사하는 이유는? — 결함의 "피해"가 최종적으로 어디에 나타나는지와 연결해서.
2. remover 스레드가 `remove(0)`만 반복하지 않고 `get(0)`을 먼저 하는 이유는?

**시도 1 — 답변** (되묻기 턴과 재서술 턴, 원문)

> 이때 makeAsRemoved가 2번 발생하면 해당 노드 아 리무버가 시작해서 하나씩 제거하는데 이때 캐시때 가져오면 문제가 발생한다는거야? / 2번에서 리무버쓰래드가 처리하면 결국 하나의 스레드가 전체 처리하니깐 그런거 아니야? 2번에 대해서는 커런트가 아닌 캐시 자체 맵에 추가적으로 키가 쌓인다는거야?

> 아 커런트는 2번 감소되서 작아지는데 map은 1번 커런트는 2번 발생해서 문제가 발생한다는거구나. / 아 get(0)이 있어야 노드 자체가 node == null이 아니게 되니깐 그런거구나. 결국 get읠통해 캐시 위에 해당 객체를 올리고 다시 지우는 방향으로 간다는거 아니야? 이때 절차대로 커런트와 맵에서 지워져야된느데 이때 커런트만 2번 지워지면 이때 카운트가 더 작아지는게 문제고 그걸 보기 위함 아니야?

**판정 1 — pass (자력)**

- Q1: "커런트는 2번 감소, map은 1번 제거 -> 어긋난다"로 메커니즘과 피해 지점 도달. 교정 1건 — 단언 대상은 map이다: `currentSize`는 private(볼 수 없음)일 뿐 아니라 결함으로 **거짓말하는 쪽**이고, 사용자 관점의 계약 위반("capacity 제한인데 map이 넘는다")이 드러나는 유일한 공개 표면이 `size()`다.
- Q2: `remove(K)`는 `cache.remove(key)`가 null이면 조기 반환해 RemovalTask를 만들지 않으므로, `get(0)`이 매 사이클 노드를 되살려야 경합 재료(RemovalTask + PENDING_REMOVAL 노드)가 생긴다 — 도달.

## G2 — diff 02: 가드와 수렴 quiesce의 수지 계산

**질문**

1. 수렴 quiesce가 pre-fix에서 영원히 수렴하지 못하는 이유 — `cache.get(새키)` 한 번이 map 크기에 주는 +와 -의 수지 계산으로.
2. 가드 3줄이 동시 진입에서도 감산을 정확히 1회로 만드는 메커니즘 — CAS 실패자가 재시도에서 무엇을 보는지로.

**시도 1 — 답변** (원문)

> get(i)형태는 제대로된 쓰기를 보장하지 않아서, 더하고 i++이 아니라 key++로 바뀐게 key의 값이 for문 i++이 각 순차적으로 완결하고 절차 처리르 보장하지 않아서 생긴 문제라는거야? (중략) 2번 답변은 이미 상태가 리무브가 되어있다면 감산하지말고 나감으로 써 감산 후 리턴하는 게 아닌 그 전에 가드로 막는다. 이거잖아? 캐시가 비여있으면 삭제된건데 맵을 제대로 안보고 한거라 맵을 제대로 보도록 수정한거고, 1번에 대해서는 for문 내의 ++이 제대로 동작하지 않아서 (중략) 1번이 좀 애매하네

**판정 1 — fail.** Q1의 축(i++/key++ 순차 보장)은 결함과 무관 — 변수명은 "이미 쓴 키와 겹치지 않는 새 키"를 위한 코드 조직일 뿐. Q2는 방향은 맞으나 "맵을 본다"가 오해(가드는 map이 아니라 노드의 상태 필드를 읽는다), CAS 패자 메커니즘 누락. 자기완결 패킷으로 재질문(빈 칸 채우기 힌트 포함).

**시도 2 — 답변** (원문)

> map에 +1이 되고 카운트가 1이 오른다. 이때 카운트는 딱1만큼 초과되럮고, 루프는 1번돌고 종료되고 map은 -1이 된다. map 순변화는 size는 map은 -1이 될꺼고, 초과분 k가 있으면 k-1을 돌아 수렴한다는건가?

**판정 2 — pass (통과 처리) + 정답 확정**

- 전반부(map +1, 카운터 +1, 딱 1 초과, 루프 1번, map -1)는 정확. 정정 2개: (1) 순변화 = (+1) + (-1) = **0**(-1이 아님) — 그래서 map이 capacity+k에서 얼어붙고 예산이 소진된다(pre-fix 영구 초과의 본체). (2) fix 후는 카운터 == map이므로 첫 get 후 카운터 = capacity+k+1 -> evictEntries가 **k+1번** 돌아 즉시 수렴(k-1이 아님).
- Q2 정답 확정(이 턴 무응답): 승자만 REMOVED 전이 + 감산, 패자는 CAS 실패 -> 재시도에서 REMOVED 스냅샷을 읽고 새 가드에서 무감산 return. 감산 합계 = 노드당 정확히 1회. 판단 근거는 map이 아니라 노드의 `CacheEntry.state`(단일 진리원).

## G3 — diff 03: 리뷰 반영 테스트 단언 2개

**질문** — `assertThat(removals.get()).isGreaterThan(0)`과 `assertThat(remover.isAlive()).isFalse()`가 각각 어떤 실패 모드를 막는가.

**시도 1 — 답변** (원문)

> isgreatethen의 경우 스레드의 스레드가 죽어서 경합이 0회인게 아니라 실제 동작 자체가 0인걸 확인하기 우ㅟ함 / isAlive는 타임아웃이 되어도, 만약 동작중이면 문제 없는거니 이에 대해서 확인하는 단언이지 실제로 잘 죽었는지 완전히 종료되서,

**판정 1 — (a) 도달 / (b) fail.** (a) "실제 동작이 0인지 확인" = 워커가 죽어 경합 0회여도 자명하게 통과하는 위장 green 차단 — 도달. (b) "동작 중이면 문제 없는"은 방향 반전 — join 후에도 동작 중이면 그게 곧 문제다. `join(millis)`가 타임아웃 시 무예외로 조용히 반환한다는 결정적 고리 누락.

**시도 2 — 답변** (원문)

> 아하 이떄 5000초가 지나서 실제 리무버 객체가 살아있는게 아니라 죽었따고 확실히 단언이 되어야되는구나. 돌아가고 있으면 안되낚ㄴ.

**판정 2 — pass (통과 처리) + 정답 확정.** `join(5000)`은 타임아웃돼도 예외 없이 반환하므로 join만으로는 종료 미보증 -> 단언이 없으면 행 걸린 스핀 스레드를 둔 채 통과(위장 green + 스레드 누수 + 살아있는 워커가 캐시를 건드리는 중에 최종 단언을 읽는 오염) -> `isAlive()==false`가 "join이 실제 종료로 반환했음"을 보증. F2의 join(무제한 -> 5초)과 N1의 isAlive 단언은 한 쌍이다. (사소 정정: 5000은 초가 아니라 밀리초.)

## 반복된 오해 패턴 / 교훈

1. **피해 표면과 내부 상태의 혼동** — "카운터가 작아지는 게 문제"까지는 왔지만, 단언은 사용자가 관측하는 표면(map)에 걸어야 한다는 연결이 늦었다.
2. **무관한 축으로의 귀인** — G2에서 i++/key++라는 표기 차이를 원인으로 짚었다. 변수명·루프 형태는 코드 조직이고, 물어본 것은 수지 계산이었다.
3. **"본다"의 대상 오인** — 가드가 map을 조회한다고 이해했으나 실제로는 노드의 상태 필드가 단일 진리원이다. H3(신호 vs 타입)와 같은 계열의 오해.
4. **방향 반전** — G3 (b)에서 "동작 중이면 문제 없다"로 뒤집었다. 단언은 문제 상태를 배제하는 것이다.
5. 교훈: 수지 계산(+1/-1 상쇄 -> 동결)은 손으로 표를 채워야 잡힌다 — 빈 칸 채우기 힌트가 이번에 실제로 작동했다.
