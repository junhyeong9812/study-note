**판정 2** — fail 후 통과 처리 (`fail_but_proceed`)

> 1번 메커니즘의 '같은 키로 정규화'는 맞지만, 핵심 오해를 바로잡아야 합니다: 수정의 효과는 '제대로 덮어쓰기'가 아니라 **예외로 거부(reject)**입니다. 같은 키가 되면 put이 기존 값(non-null)을 반환하고, 기존 L255 `if (put(...) != null) throw`가 이를 감지해 중복 예외를 던집니다. 오히려 조용히 마지막 값으로 덮어쓰던 것이 '버그 동작'이고, 수정은 그 덮어쓰기를 막습니다. 2번은 방향은 맞으나(대소문자 무시로 조회) 진짜 이유는 최종 MimeType 생성자가 임시 맵을 다시 LinkedCaseInsensitiveMap으로 재복사하므로 저장/조회 구조가 그대로 유지된다는 점입니다.

**정답 정리** (대화에 제시된 것)

- 수정의 효과는 "제대로 덮어쓰기"가 아니라 **예외 거부**다. 현재의 조용한 마지막 값 채택이야말로 버그 동작이고, 수정은 그 덮어쓰기를 막는다.
- 메커니즘: 같은 키가 되면 `put`이 기존 값(non-null)을 반환하고, 이미 존재하던 `if (put(...) != null) throw`(당시 `MimeTypeUtils.java` L255)가 중복 예외를 던진다.
- `MimeType` 동작이 안 깨지는 진짜 이유는 "대소문자 무시로 조회해서"가 아니라, 최종 `MimeType` 생성자가 임시 맵을 다시 `LinkedCaseInsensitiveMap`으로 재복사하기 때문이다.

**시도 2 — 답변** (사용자 원문)

**판정 2** — fail 후 통과 처리 (`fail_but_proceed`)

> 1번(Locale.ROOT=로케일 무관 안정적 소문자화, 터키어 I 문제 회피 -> 'ASCII 기준 고정' 이해로 충분)과 2번 전반부('중복 없으면 put이 null 반환->L255 throw 안 됨->파싱 정상')는 맞습니다. 다만 마지막 의문을 바로잡아야 합니다: LinkedCaseInsensitiveMap은 대소문자를 무시해 '비교'할 뿐, 소문자 키는 내부 조회용으로만 쓰고 **원본 케이스를 그대로 보존**해 저장·반환합니다(예: 'Charset'은 'Charset'으로 유지, 값 UTF-8도 불변). 따라서 '키가 소문자로 전달/저장된다'는 오해입니다. 게다가 이 임시 맵은 최종적으로 MimeType 생성자가 다시 LinkedCaseInsensitiveMap으로 재복사하므로 정상 입력의 getParameters() 결과는 수정 전과 완전히 동일합니다.

워커는 별도 note로 "사용자가 Locale.ROOT/ASCII 규약과 대소문자 무시 동작에 대한 설명을 코드 주석/문서로 추가해 달라고 요청함 — 기록 단계에서 반영 필요"를 남겼고, 이는 코드의 설명 주석과 해설 문서에 반영됐다.

**정답 정리**

- `Locale.ROOT`: 로케일 무관 안정적 소문자화. 터키어 로케일의 `I` -> `ı`(U+0131) 문제를 피한다. `MimeType` 자신이 파라미터 맵을 만들 때 쓰는 값과 동일하게 맞춘 것이다.
- 정상 입력이 안 깨지는 이유(전반): 중복이 아니면 `put`이 null을 반환하므로 기존 throw 문(L255)이 발동하지 않는다.
- 교정된 오해: `LinkedCaseInsensitiveMap`은 소문자 키를 내부 조회용으로만 쓰고 저장·반환은 원본 케이스를 보존한다. `Charset`은 `Charset`으로 유지되고 값도 불변이다.
- 추가로, 이 임시 맵은 `MimeType` 생성자에서 다시 `LinkedCaseInsensitiveMap`으로 재복사되므로 정상 입력의 `getParameters()` 결과는 수정 전과 완전히 동일하다.

   수정의 효과를 "제대로 덮어쓰기"로 이해했으나, 조용한 덮어쓰기야말로 버그 동작이고 수정은 그것을 예외로 막는 것이다.

3. **목표 재진술로 메커니즘을 대신함 (1부 G1, 2부 G1, 2부 G2)**
   "대소문자를 같게 비교해야 한다", "가드를 해야 한다" 같은 목표 재진술까지는 나오지만, "그래서 어떤 호출이 무엇을 반환하고 어떤 기존 코드가 발동하는가"라는 인과 사슬이 빠지는 패턴이 세 번 반복됐다. 판정 워커의 fail 사유 대부분이 이 항목이다.

4. **질문의 뒷부분 누락 (1부 G1, 2부 G2)**
   질문이 두세 부분으로 나뉘어 있을 때 앞부분만 답하고 나머지를 통째로 빠뜨린 경우가 두 번 있었다. 1부 G1은 (2)(3)을, 2부 G2는 (b) 전체를 빠뜨렸다.

5. **인접 개념으로의 치환 (2부 G3)**
   `Locale`을 문자 인코딩(UTF-8, OS 기본 charset)과 연결했다. 둘 다 "환경에 따라 달라지는 것"이라는 공통점이 있어 붙기 쉽지만, `Locale`이 결정하는 것은 `toLowerCase`의 언어 규칙이지 바이트를 문자로 읽는 방식이 아니다.

# 교훈

- **인과 사슬 한 줄이 이해의 기준이다.** 두 세션 모두 게이트를 최종 통과시킨 것은 "맵 교체 -> put 반환값이 null에서 이전 값으로 바뀜 -> 기존 if문이 참이 됨 -> throw"라는 한 줄이었다. 목표를 아는 것과 메커니즘을 아는 것은 다르고, 워커는 후자만 pass로 인정했다.
- **같은 오해는 두 번 온다.** "소문자 저장" 오해가 1부에서 교정됐는데 2부에서 재발했다. 한 번 교정된 개념도 기록으로 남겨두지 않으면 다음 세션에서 같은 자리에서 다시 걸린다. 이 문서 자체가 그 재발을 막기 위한 산출물이다.
- **되묻기는 fail이 아니다.** 1부 G3에서 사용자가 `Locale.ROOT`를 모르겠다고 되물었을 때 메인은 판정 워커에 넘기지 않고 개념을 설명한 뒤 남은 항목만 재질문했다. 2부 G1에서도 자료구조 선택이 최선인지 되물어 대안 세 가지 비교를 끌어냈다. 모르는 것을 되묻는 쪽이 추측 답변보다 학습 효율이 높았다.
- **red의 의미는 실패 자체가 아니라 실패의 범위다.** 53개 중 신규 1개만 red라는 사실이 "이 실패는 이 케이스 고유"를 보증하고, red->green 전환이 fix의 증명이 된다. 이 논리가 2부 G2에서 두 번 지적된 누락 항목이었다.
- **2회 cap은 무한 차단을 막되 정렬을 포기하지 않는다.** 계획 게이트는 2회 실패 시 자동 진행 금지 규칙이 있어, 2부 G1에서 통과 처리 후에도 사용자가 스스로 인과를 정리할 때까지 대화가 이어졌다. diff 게이트의 통과 처리와 계획 게이트의 정렬 요구가 다르게 설계돼 있다는 점이 실제로 작동했다.
