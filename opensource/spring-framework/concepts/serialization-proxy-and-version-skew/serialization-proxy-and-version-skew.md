# 개념: 직렬화 프록시 패턴과 버전 스큐 — "객체가 아니라 좌표를 보내라"

> PR #37186 작업의 개념 묶음. 학습 중 실제로 나온 질문 순서대로 구성했다:
> "identity를 인코딩해서 보내는 건가?", "주소를 보내는 건가?", "다른 서버에서도
> 통하나?", "같은 classpath면 마커가 왜 필요하지?"

## 1. 직렬화 프록시 패턴이란

객체를 그대로 스트림에 싣는 대신, 직렬화 순간에 **"재구성 설명서"(프록시)로
바꿔치기**하고 역직렬화 때 설명서대로 실물을 다시 만드는 관용구다(Effective Java
Item 90, JDK의 `SerializedLambda`가 대표 사례).

```
[직렬화]   원본 객체 ──writeReplace()──> 프록시(재구성에 필요한 최소 정보)  → 스트림
[역직렬화] 스트림 → 프록시 복원 ──readResolve()──> 설명서대로 실물 재구성
```

- 훅 시그니처는 정확해야 한다: `private Object writeReplace()` /
  `private Object readResolve()` — 인스턴스 메서드, 무인자, 반환형 정확히 `Object`.
- 프록시가 발동하지 않아야 할 때는 `writeReplace()`가 `this`를 반환하면 기본
  직렬화로 진행된다 — "원래 되던 것은 형식도 그대로"를 지키는 장치.

## 2. 스트림에 실리는 것: identity도, 주소도 아니고 — 이름 기반 좌표

#37186의 프록시가 보내는 것을 정확히 하면:

| 오해 | 실제 |
|---|---|
| "identity(같은 객체임)를 인코딩해 보낸다" | identity는 스트림에 실을 수 없다 — 각 JVM 내부에서만 성립하는 성질이다 |
| "메모리 주소를 보낸다" | 주소는 JVM마다·재시작마다 달라 무의미하다 |
| **좌표를 보낸다** | `Class`는 **정식 이름**(FQCN)으로, 타입 변수는 **"그 클래스의 i번째 파라미터"라는 인덱스**로 — 둘 다 JVM 밖에서도 유효한 기호적 지정 |

역직렬화 쪽은 좌표를 읽고 **재조회**(re-lookup)한다: 이름으로 클래스를 로드하고,
`getTypeParameters()[i]`를 호출해 **받는 쪽 JVM의 정본**을 얻는다
([instance-stability](../jdk-generic-info-instance-stability/jdk-generic-info-instance-stability.md)가 이 재조회의 근거).
"보낸 쪽 객체와 같은 객체"가 되는 게 아니라(불가능), **받는 쪽 세계에서 유일한 그
객체**가 되는 것이고, 받는 쪽의 모든 비교는 받는 쪽 정본과 이루어지므로 충분하다.

이 구도는 annotation의 enum 값 처리(이름 저장 -> 읽는 순간 로드된 enum에서 조회 —
`../../prs/37153-enum-array-annotation-probe/enum-annotation-name-resolution.md`)와 동형이다. "**객체를 보내지 말고,
받는 쪽에서 다시 찾을 수 있는 이름/좌표를 보내라**"는 직렬화 설계의 반복 원칙.

## 3. "같은 classpath면 마커가 왜 필요하지?" — 역할 셋의 분리

이 질문은 문제·운반·검증이라는 서로 다른 세 역할을 하나로 뭉쳐 놓은 데서 나온다.

- **문제**: raw `TypeVariable`은 비직렬화 — 스트림에 싣는 순간 실패. classpath가
  같든 다르든 바이트 변환 자체가 안 된다.
- **마커(좌표) = 운반 수단**: 못 싣는 객체 대신 실을 수 있는 좌표를 넣는 것.
  구별용이 아니라 **운반용**이다.
- **검증 = 안전망**: 같은 버전 안에서 좌표는 결정적이라 어긋날 일이 없다. 어긋남은
  비정상 입력(버전 스큐·조작 스트림)에서만 생기고, 그걸 위한 것이 `readResolve`의
  null·개수·범위 검증 -> `InvalidObjectException`.

비유: 편지에 생화를 넣을 수 없어 "정원 3번째 화분의 꽃"이라 적어 보낸다(마커).
받는 쪽 정원이 같다면 그대로 찾으면 되고, 정원이 리모델링됐을 수 있으니 "3번
화분이 실제 있는지" 확인하는 것이 검증이다.

## 4. 직렬화 버전 스큐 — 다른 서버/시점에서 무슨 일이 생기나

"직렬화한 쪽과 역직렬화하는 쪽의 클래스 정의가 다른" 상황은 실제로 흔하다:

1. **서버 간 전송**: 세션 복제, Redis류 캐시를 다른 노드가 읽기, 메시지 큐 — 롤링
   배포 중이면 두 서버의 버전이 반드시 다른 순간이 있다.
2. **같은 서버의 시간축**: 직렬화해 저장해 둔 뒤 앱을 업그레이드하면 새 버전이 옛
   스트림을 읽게 된다.
3. 대상이 사용자 정의 제네릭 클래스면 타입 파라미터 수가 리팩토링으로 바뀌는 것도
   흔하다.

이때의 동작 조건표:

| 받는 쪽 상태 | 결과 |
|---|---|
| 같은 이름·같은 구조의 클래스 존재 | 정상 — 재조회가 그쪽 정본으로 복원 |
| 클래스 자체가 없음 | `ClassNotFoundException` — **일반 자바 직렬화도 동일**(양쪽에 같은 클래스가 있다는 전제는 직렬화 전반의 기본 계약) |
| 클래스는 있으나 구조가 다름(파라미터 수 등) | 검증이 `InvalidObjectException`으로 명확히 실패 — 검증이 없다면 raw AIOOBE나 조용한 오매칭 |

핵심: 좌표 방식은 표준 직렬화의 전제에 **아무것도 추가로 요구하지 않는다** —
일반 직렬화가 통하는 만큼 정확히 똑같이 통하고, 실패할 때 더 깔끔하게 실패한다.
그리고 "보증하지 않는 것"(Spring은 버전 간 직렬화 호환을 계약하지 않음 —
gh-36346의 Juergen 발언)과 "보증 밖 입력에 미정의 동작을 해도 되는 것"은 다르다 —
검증은 후자를 막는 장치다.

## 5. 설계 세부에서 배운 것 (#37186 리뷰 루프의 산물)

리뷰 루프에서 확정된 설계 규칙은 셋이다.

- **분기 순서가 결과를 가른다**: 한 인자가 "마커 대상이면서 Serializable"일 수
  있는 환경(비-HotSpot JVM)에서는 먼저 잡히는 분기가 이긴다 — Serializable 우선이면
  역직렬화가 **복사본**을 만들어 정본 identity가 깨지므로, **의미 기반
  인코딩(마커)이 언제나 우선**이어야 한다.
- **프록시는 "원래 실패하던 그래프"에만 등장해야 한다**: 마커가 하나도 필요 없는
  인스턴스까지 프록시로 바꾸면 멀쩡히 직렬화되던 스트림의 형식이 바뀌어, 롤링
  업그레이드에서 구버전이 신버전 스트림을 못 읽는 순수 회귀가 생긴다(무악화 원칙).
- **검증 실패는 계약된 예외로**: `InvalidObjectException`은 "역직렬화 입력이
  잘못됐다"의 표준 신호 — NPE·AIOOBE가 새는 것보다 원인 가까이에서, 계약된 형태로.
