# study-note 작성법 — 도식화와 문서 골격

이 문서는 **study-note에 기록을 남기는 모든 사람(과 에이전트)이 따르는 작성 규칙**이다.\
다른 프로젝트를 진행하다가 그 내용을 study-note로 이관할 때, 이 문서 하나만 읽으면 어떤 폴더에 어떤 골격으로 써야 하는지 알 수 있게 하는 것이 목적이다.

역할 분담은 이렇다.

- 루트 [README](../README.md) — 무엇을 하라(공부 루프·복습 규칙). 규칙의 정본.
- [reference/writing/](writing/README.md) — 왜 그렇게 쓰나(문서 작성 방법론 리서치).
- [reference/learning/](learning/README.md) — 왜 그렇게 공부하나(인출·대칭화·순서화).
- **이 문서** — 그래서 study-note에 실제로 어떻게 쓰나(골격·도식화·가독성의 실행 규칙).

---

## 1. 먼저 정할 것 — 어느 갈래에 쓰는가

study-note의 폴더는 성격이 둘로 갈린다.\
갈래를 잘못 고르면 골격이 통째로 어긋나므로 이것부터 정한다.

| 갈래 | 폴더 | 목적 | 파일 구조 | 골격 |
|---|---|---|---|---|
| **훈련** | `cs/` | 기억에서 꺼내는 연습(인출) | 3파일: `1-question` / `2-summary` / `3-answer` | §2 |
| **기록 — 실험** | `lab/` | 무엇을 알고 싶었고 무엇이 나왔나 | 프로젝트=폴더, README 하나 | §2-A |
| **기록 — 구현** | `project/` | 이 문제를 왜 이렇게 풀었나 | 이슈=폴더, README 하나 | §2-B |
| **기록 — 기여** | `opensource/` | 남의 코드를 왜 이렇게 고쳤나 | PR=폴더, 파일 5개 | §2-B2 |
| **기록 — 보고** | `세미나/` · `독후감/` | 듣고 읽고 생각한 것 | 행사·책=폴더 | §2-C |

> **인출(retrieval)** — 읽어서 익히는 게 아니라, 기억에서 억지로 꺼내 보는 연습.\
> 예: 정답을 덮고 "동적 배열은 왜 2배씩 늘리지?"에 먼저 답해 보는 것.

훈련 갈래는 **정답이 눈에 먼저 들어오면 안 되므로** 파일을 셋으로 물리적으로 나눈다.\
기록 갈래는 그 제약이 없으니 README 하나로 충분하다.

- 판단이 서지 않으면 이렇게 묻는다: "나중에 이걸 **문제로 풀** 것인가, **읽을** 것인가."
- 풀 것이면 `cs/`, 읽을 것이면 기록 폴더.
- 실험·프로젝트에서 나온 **지식**은 기록 폴더에 남기고, 그 지식을 훈련 대상으로 승격할 때 `cs/`에 주제를 만든다(링크로 잇는다).

**갈래가 달라도 §3(도식화)·§4(가독성)·§6(수치)은 똑같이 적용된다.** 다른 것은 절 골격뿐이다.

## 2. 훈련 문서(cs/)의 3파일 골격 — CS 주제

**작성 순서는 2 → 1 → 3이다.**\
서머리가 완성돼야 "무엇이 핵심인가"를 판별할 수 있고, 그 판별 위에서 질문이 나온다.\
사용 순서는 반대로 1 → 2 → 3이다(질문에서 시작해 막힐 때만 다음 파일).

### 2-summary.md — 정리

절 순서를 고정한다. 순서가 같으면 두 번째 주제부터는 읽는 비용이 0에 가까워진다.

```text
# <폴더>/<주제> — 정리 (힌트)
> 안내 2줄 + 원고 출처·날짜 + 어느 절이 원고/압축/Claude 작성인지

## 한눈에 — 쉽게 말하면     ← 일상 비유 → "똑같은 구조다" → 실무 예 → 쉬운 설명 → 단순 그림 1개
## 문제 — 이 챕터가 시키는 것 ← 원본 요구사항 인용 + 과제(TODO) 목록 + "아래 서머리는 이 문제를 분석·정리한 것이다"
## 전체 흐름                 ← 워크플로우 압축(text 블록)
## 동작/규칙 절들            ← 절마다 같은 골격(아래 §3)
## 핵심 문장                 ← 지도 수준 3~5문장
## 관련 자료                 ← 실존 확인한 경로만
## 용어 풀이                 ← 등장 용어 전부 1~2줄
---
## [Claude 추가] 더 알면 좋은 것  ← 원고에 없던 지식은 전부 여기에만
```

- 「문제」 절이 먼저 오는 이유: 서머리는 **그 문제를 분석한 결과**이지 독립된 지식 카드가 아니다.
- 원본에 문제가 없는 개념 주제는 「문제」 대신 "이 개념이 답하려는 질문"을 쓴다.

### 1-question.md — 질문

```text
### A. 과제  ← 원문 javadoc/TODO/요구사항을 코드블록으로 먼저, 그 아래 질문
### B. 개념  ← 원본의 "생각해볼 것" 전부 이관 + 서머리 기반 파생 질문
## 복습 기록  ← 날짜·결과·틀린 질문·다음 복습 표
```

- **질문 하나 = "?" 하나 = 한 줄.** 옆으로 묶지 않고 아래로 늘어놓는다.
- 세부 암기("TAG_INSERT 값은?")가 아니라 지도 수준으로: **왜 / 예측 / 경계 / 연결** 네 유형.
- 도메인·설계 주제는 한 유형을 더 쓴다 — **"이 한 줄 요구사항에 안 들어 있는 결정은 무엇인가"**(경계값·기준점·반올림·순서).

### 3-answer.md — 정답

- 1-question의 절·번호에 **1:1로 대응**시킨다. 질문 수 = 답 수.
- 근거는 문서가 아니라 **코드**다. 구현 핵심부를 인용하고 손계산·그림을 곁들인다.
- 근거가 없는 답은 반드시 표시한다 — `(원본에 근거 없음 — 내 추론)`.

## 2-A. 기록 — 실험(lab/)의 골격

실험은 **질문에서 시작해 수치로 끝난다.** 그 순서를 절로 고정한다.

```text
# <프로젝트명> — <한 줄 요약>
- 원본 repo · 기간 · 스택 · 상태(완료 / 부분 / 설계만 미실행)

## 무엇을 알고 싶었나 — 질문·가설   ← 측정 전에 무엇을 예상했는지까지
## 실험 환경과 방법                 ← 구성도(ASCII), 측정 도구, 부하 조건
## 결과 — 페이즈/시나리오별          ← 표 위주. 표마다 아래에 `출처: <원본 파일 경로>`
## 종합 결론                        ← 핵심 발견 3~5개. "그래서 무엇을 다르게 하나"
## 한계·남은 질문                   ← 측정이 오염된 곳, 답 못 한 것
## 원본 문서 지도                   ← 어느 문서에 무엇이 있는지 표
```

지켜야 할 것.

- **수치는 원본에서 복사만 한다.** 재측정·추정 금지. 원본에 없으면 "문서에 없음".
- **원본 문서의 자체 경고를 그대로 옮긴다.** "이 지연 수치는 부하 오염 상태에서 측정됨" 같은 문장은 결론보다 중요하다.
- **실패와 미완도 쓴다.** "설계만 하고 실행 안 함", "10억 건 적재하다 클러스터가 죽음"이 기록의 절반이다.\
  실패를 지우면 나중에 같은 실패를 반복한다.
- 원본 문서끼리 어긋나면(README와 측정 로그가 다르면) 어느 쪽을 정본으로 삼았는지 밝힌다.

## 2-B. 기록 — 내 프로젝트 구현(project/)의 골격

구현 기록은 **결정의 이유를 남기는 글**이다. 코드는 repo에 있으니 여기서 반복하지 않는다.\
이슈 하나 = 폴더 하나.

```text
# <이슈 제목>

## 1. 무엇이 문제였나        ← 상황과 증상. 왜 그냥 두면 안 되는가
## 2. 무엇을 고민했나        ← 후보 안들을 나란히, 각각의 대가
## 3. 그래서 이렇게          ← 고른 안과 그 이유 + 구조도(ASCII)
## 4. 코드 — 실제 커밋에서   ← 커밋 해시와 before/after 스니펫(실파일에서 복사)
## 5. 구현 중 마주친 문제    ← 예상 못 한 것, 되돌린 것
## 6. 결론                  ← 지금 상태와 남은 빚
```

지켜야 할 것.

- **후보를 지우지 않는다.** 안 고른 안과 그 이유가 이 문서의 값어치다.\
  "A를 골랐다"만 남으면 나중에 같은 고민을 처음부터 다시 한다.
- **코드 스니펫은 실파일에서 복사한다.** 기억으로 재현하거나 `...` placeholder를 쓰지 않는다.
- 커밋 해시를 적어 원본과 대조할 수 있게 한다.
- 검증 도구(리뷰 에이전트 등)의 이름은 여기에 쓰되 **커밋 메시지·PR 본문에는 쓰지 않는다**.

## 2-B2. 기록 — 오픈소스 기여(opensource/)의 골격

이 골격은 지어낸 것이 아니라 **이미 쓰인 36편의 PR 문서에서 뽑은 것**이다.\
남의 코드베이스를 다루므로 내 프로젝트(§2-B)와 달라진다 — 무대를 먼저 세우고, 리뷰 대응과 머지 여부까지 남긴다.

PR 하나 = 폴더 하나(`<PR번호>-<슬러그>/`), 그 안에 **역할이 다른 파일 다섯**을 둔다.

| 파일 | 역할 | 필수 |
|---|---|---|
| `README.md` | **서사** — 처음 보는 사람이 재구성할 수 있게 | 필수 |
| `structure.md` | **무대 구조** — 수정 전 실구조와 워크플로우 | 권장 |
| `analysis.md` | **분석** — 기준 커밋·실파일 정독 근거 | 권장 |
| `tests.md` | **테스트 해설** — 테스트 하나하나가 무엇을 고정하나 | 필수 |
| `gates.md` | **이해 게이트** — 스스로 답해 본 문답 기록 | 선택 |

`README.md`의 절 순서(실제 문서에서 확립된 것):

```text
# PR #<번호> — <영문 제목>

## 0. 정향            ← 이 문서가 무엇이고, 다 읽으면 무엇을 설명할 수 있어야 하는가 + 관련 개념 문서 링크
## 1. 배경            ← 문제의 무대. 이 객체·기능이 원래 무엇을 하는 물건인가
## 2. 수정 전 동작 방식 ← 고치기 전 코드가 실제로 어떻게 돌았나 (코드 인용)
## 3. 무엇이 문제였나   ← 증상과 그것이 조용히 지나가는 이유
## 4. 수정 해설        ← 어떻게 고쳤나 (diff 기준, 여러 단계면 단계별로)
## 5. 리뷰 대응        ← 메인테이너 지적과 그에 따른 변경 (있을 때만)
## 6. 검증            ← 테스트가 각각 무엇을 고정하나
## 7. 상태와 교훈      ← 머지/리뷰 대기 여부, 다음에 쓸 판단
```

지켜야 할 것.

- **기준 커밋을 문서 머리에 박는다.** 머지 후 코드를 인용하면 "머지 후 코드이며 수정 전은 diff의 `-` 쪽"이라고 밝힌다.\
  좌표(파일·줄 번호)는 어느 시점 기준인지 없으면 나중에 못 찾는다.
- **"조용히 지나가는 이유"를 반드시 쓴다.** 에러를 던지는 버그는 금방 잡힌다.\
  기록할 값어치가 있는 것은 무음 실패이고, 그것이 §3의 핵심 서사다.
- **머지 안 된 것도 남긴다.** "리뷰 대기", "거절됨 — 의도된 동작이었다"가 교훈의 절반이다.
- 상태는 마지막 절에 **머지 커밋 해시와 마일스톤**까지 적는다.

## 2-C. 기록 — 보고(세미나/ · 독후감/)의 골격

```text
세미나/<행사>/<회차>.md   — 날짜·주제 → 세션별 느낀 점 → 내 방향에 미친 영향
독후감/<책>/README.md     — 책 정보·읽은 동기 → 챕터 색인 표 → cs/ 추출 목록 → 총평
독후감/<책>/NN-챕터.md     — 핵심 내용 2~3줄 → 내 생각 → 동의 안 되는 점 → cs/ 추출 후보
```

- 여기는 **생각**을 쓰는 곳이다. 내용 요약을 길게 쓰기 시작하면 `cs/` 서머리와 역할이 겹친다.
- 책·발표에서 건진 지식은 `cs/`로 추출하고 여기엔 링크만 남긴다.

## 3. 도식화 규칙 — 그림이 먼저, 글은 그림을 읽어준다

이 저장소에서 그림은 장식이 아니라 **본문**이다.\
글로 설명하고 그림을 곁들이는 게 아니라, 그림을 두고 그 그림에서 무슨 일이 일어났는지 문장으로 읽어준다.

### 3.1 동작 절의 고정 골격

모든 동작·규칙 절을 같은 순서로 쓴다.

```text
**언제 쓰나** — 어떤 상황에서 이 동작이 나오는가 (1~2줄)
(그림) 전 상태
   ↓ 조작
(그림) 후 상태
그림 해설 — 한 단계에 한 문장
비용 — 빅오 또는 트레이드오프 + 그 이유 한 줄
```

> **대칭화** — 형태가 제각각인 것을 하나의 정해진 모양으로 바꾸는 것.\
> 예: 모든 동작 절을 "언제→전→단계→후→비용" 순서로 고정하면, 두 번째 절부터는 어디에 뭐가 있는지 찾지 않아도 된다.

### 3.2 그림 자체의 규칙

- **그리기 쉬운 문자를 기본으로**: `+--+`, `|`, `->`, `v`, `^`.\
  더 잘 보이면 박스 그리기 문자(`┌ ─ ┐ │ └ ┘ ├ ┤ ▼ ↓`)를 써도 된다 — 중첩 구조나 표 형태의 상자는 이쪽이 읽기 낫다.\
  한 그림 안에서는 한 종류로 통일한다(섞으면 선이 안 맞는다). 코드 펜스는 ` ```text `(언어 이름을 붙이면 색칠이 그림을 망친다).
- **그림 하나가 말하는 것은 하나.** 상태 하나 또는 변화 한 단계.\
  복잡한 그림 1개보다 단순한 그림 3개가 낫다.
- **구체적인 값으로 그린다.** `[5, 2, 8, 1]`처럼 5~8개짜리 실제 숫자를 쓴다. `[a1, a2, ..., an]`은 그림이 아니라 수식이다.
- **같은 주제 안에서는 같은 예시 데이터를 쓴다.** 정렬 5편을 같은 배열로 그리면 알고리즘 간 비교가 공짜로 된다.
- 비교가 필요하면 **나란히 놓는다**(왼쪽 나쁜 경우 / 오른쪽 좋은 경우).

### 3.3 갈래별로 그리는 것이 다르다

| 갈래 | 그림의 중심 |
|---|---|
| 자료구조 | 메모리 배치와 포인터 — 전 상태 → 조작 → 후 상태 |
| 알고리즘 | 같은 입력 배열의 단계별 변화 추적 |
| 운영 패턴 | **무엇이 실패하는가 → 패턴이 어떻게 막는가**(전/후 대비). 실패 없는 패턴 설명은 반쪽이다 |
| API 설계 | **나쁜 계약 → 좋은 계약**의 요청/응답 대비 |
| 도메인 모델링 | 요구사항 문장 → 코드의 어느 타입·필드가 됐는지 짝짓기 표 + 경계값 수직선 |
| 법령·기준 | 조문 원문 인용 → 개발자 함의 |
| 실험(lab) | 구성도(무엇이 무엇을 부르나) + 축별 결과 표 |
| 오픈소스(PR) | **수정 전 호출 경로 → 어디서 갈라지나** + 수정 전/후 동작 대비 |
| 구현(project) | 요청 하나가 지나가는 경로 + 바뀌기 전/후 구조 대비 |

### 3.4 워크플로우는 세로로, 한 칸에 한 단계

흐름을 그릴 때는 가로로 늘어놓지 말고 **세로로 내려쓴다.**\
가로 화살표는 줄이 길어지면 읽는 눈이 되돌아와야 하고, 화면 폭에서 잘린다.

```text
minutesParked(입차, 출차)      몇 분 주차했나 (초는 올림, 뒤집힌 시각은 거부)
        ↓
feeForMinutes(분, 정책)        그 분의 요금 (무료 → 기본 → 단위 순서, 상한 없음)
        ↓
charge(입차, 출차, 정책)        자정으로 조각내고, 조각마다 요금+상한, 합산
        ↓
chargeFor(..., 정기권 여부)     정기권이면 계산 자체를 안 하고 0원
```

- 왼쪽은 **무엇을 하는 단계**, 오른쪽은 **그 단계가 정하는 것**. 두 칸을 넘기지 않는다.
- 갈래가 나뉘면 들여쓰기로 표현하고, 각 갈래 끝에 결과를 적는다.
- 상태가 바뀌는 흐름(주문 상태·회로 차단기 등)은 상태 전이도로:

```text
    CLOSED ──(실패율 임계 초과)──> OPEN
      ^                             │
      │                     (대기 시간 경과)
      │                             v
      └──(시험 호출 성공)──── HALF_OPEN
```

### 3.5 전/후 대비는 나란히 놓는다

"이렇게 하면 안 되고 이렇게 해야 한다"는 두 그림을 **같은 눈높이에** 둔다.

```text
무한 큐 (지표는 전부 초록)            정원이 있는 큐 (밀어내기)
+---------------------+             +---------------------+
| 대기 1,000,000건    |             | 대기 100건 (상한)   |
| CPU 30% · 에러 0%   |             | 초과 요청은 즉시 거절 |
+---------------------+             +---------------------+
  → 어느 순간 OOM 으로 죽는다          → 느려지는 게 보인다
```

- 나란히 못 놓을 만큼 넓으면 위아래로 놓되, 두 그림의 **칸 폭을 맞춘다.**
- 대비의 결론은 그림 아래 한 문장으로 적는다("지표가 초록인 채로 죽는다").

## 4. 가독성 표준 — 인지 부하를 낮추는 세 가지

목표는 "짧게"가 아니라 **읽는 사람이 한 번에 붙들 것을 줄이는 것**이다.

> **인지 부하(cognitive load)** — 무언가를 이해하려고 머리에 한꺼번에 올려둬야 하는 양.\
> 예: 한 문장에 처음 보는 용어가 셋 있으면, 뜻 셋을 붙들고 문장 구조까지 따라가야 해서 이해가 멈춘다.

### 4.1 한 문장 = 한 줄

여러 문장이 한 불릿·한 문단에 붙어 있으면 문장 끝에 `\`(마크다운 하드 브레이크)를 넣어 줄을 나눈다.

```markdown
- 확장은 두 배씩 한다.\
  한 칸씩 늘리면 복사 총량이 O(n²)이 되기 때문이다.\
  두 배면 총 복사량이 2n을 넘지 않는다.
```

한 문단은 한 생각만 담고, 3~7줄에서 끊는다.

### 4.2 용어는 등장한 자리에서 바로 푼다

전문용어를 처음 쓴 **문단 바로 아래**에 인용 블록을 단다.

```markdown
> **상환 분석(amortized analysis)** — 가끔 드는 큰 비용을 평소의 싼 연산들에 나눠 평균 낸 것.\
> 예: 이사 비용을 매달 적금 든 셈 치면, 한 번에 나가는 목돈이 월 얼마로 환산된다.
```

- **정의 한 줄 + "예:" 한 줄**이 최소 단위다. 추상 정의만 쓰면 안 푼 것과 같다.
- 문서 끝 「용어 풀이」는 **모음집**으로 따로 둔다. 독자를 글로서리까지 왕복시키지 않는 것이 요점이다.
- 주제당 8개 이상이 보통이다(정답 파일 기준).

### 4.3 순서화 — 사전 지식은 필요해지는 자리에

개념 A를 모르면 B가 안 읽히는 구조라면, B 바로 앞에 A를 3줄로 심는다.\
문서 맨 앞에 몰아두지 않는다 — 읽을 때쯤이면 잊는다.

쉬운 예를 먼저 들고, **"똑같은 구조다"라는 문장으로 명시적으로 이어** 실무 예로 넘어간다.

## 5. 원고와 보강의 경계

원고(내가 쓴 글)와 보강(Claude가 보탠 지식)을 섞지 않는다.\
복습할 때 "내가 이해한 순서"와 "외부 지식"이 섞이면 인출 훈련이 흐려진다.

- 본문에는 원고 문장을 그대로 둔다 — 오탈자·끊긴 문장만 고친다.
- 본문에 보강이 불가피하면 그 문장 끝에 ` *(Claude 보강)*`.
- 원고에 없던 독립 지식은 문서 끝 `## [Claude 추가] 더 알면 좋은 것` 절로만 넣는다.
- 원고가 아예 없는 기준 문서 주제(표준·법령 등)는 본문 전체가 Claude 작성일 수 있다 — 그때는 **문서 상단에 "이 본문은 Claude 작성, 원고 아님"을 명시**한다.

## 6. 사실과 수치 — 날조 금지

- 수치는 **원본 README·테스트 assert·측정 로그에 있는 값만** 쓴다. 기억으로 재구성하지 않는다.
- 원본에 없으면 "문서에 없음"이라고 쓴다. 그럴듯한 값을 지어내지 않는다.
- 손계산으로 유도한 값은 계산 과정을 보이고 "직접 계산한 값"임을 밝힌다.
- 법령·표준은 **조문 원문을 인용**하고 출처와 시행일을 적는다. 조문 번호만 적으면 독자가 다시 찾아야 한다.
- 원본 문서끼리 어긋나면(README와 테스트 값이 다르면) **양쪽을 병기하고 어느 쪽을 기준으로 삼았는지** 밝힌다.
- 컷오프 이후 사실·최신 버전은 웹으로 확인하고 출처를 남긴다. 확인 못 하면 `(확인 필요)`.

## 7. 다른 프로젝트에서 이관할 때

프로젝트를 진행하다 study-note에 남길 거리가 생겼을 때의 순서다.

1. **갈래를 정한다**(§1). 실험 기록이면 `lab/<프로젝트>/README.md`, 개념 지식이면 `cs/<주제>/`.
2. **원본 경로를 기록한다.** 이관본에는 항상 `출처: <원본 repo 경로>`를 절마다 남긴다.\
   나중에 원본이 바뀌었는지 대조할 수 있어야 한다.
3. **수치는 복사한다**(§6). 원본 문서에서 그대로 옮기고 표마다 출처를 단다.
4. **프로젝트 고유 이름을 일반화한다.** 특정 클래스·사내 용어에 기대면 저장소 밖에서 안 읽힌다.\
   지우는 게 아니라 "누구나 겪는 형태"로 다시 쓴다.
5. **인덱스를 갱신한다.** 해당 폴더의 `index.md`와 루트 README 색인에 행을 추가한다.
6. 실험 기록이면 그 안에서 뽑을 개념을 **"cs/ 추출 후보"** 목록으로 남긴다.
