# arch-map — 아키텍처 지도 작성·검증 도구

`opensource/<도구>/architecture/` 의 소스 기준 지도를 여러 워커로 나눠 쓸 때 쓰는 도구 셋이다. MySQL 지도(흐름 13편·함수 문서 129편·구조 6편, 코드 블록 598개)를 이 절차로 썼고, PostgreSQL 지도에 그대로 다시 쓴다.

## 구성

| 파일 | 쓰임 |
|---|---|
| [check-code-blocks.py](check-code-blocks.py) | 코드 블록이 고정 태그의 소스와 같은지 기계 대조 (`blocks=N bad=M`) |
| [writer-brief.md](writer-brief.md) | 작성 워커 공통 브리핑 — 형식·규칙·자체 점검·packet |
| [verifier-brief.md](verifier-brief.md) | 검증 워커 브리핑 — 작성자와 다른 워커가 소스로 반증 |

## 절차

```text
 1. 소스 레포를 기준 태그로 체크아웃해 둔다 (로컬 클론의 HEAD 를 읽는다)
 2. 지도 README 에 흐름 목록과 흐름별 함수 목록을 소스로 확정한다 (목록 단계)
 3. 파일럿 흐름 하나를 작성 -> 검증 -> 형식 확정
 4. 나머지를 흐름 2개씩 작성 워커에 맡긴다 (동시 워커 상한 안에서)
 5. 작성이 끝난 묶음마다 다른 워커가 검증한다
      코드 블록 기계 대조 + 줄 번호 전수 + 서술 반증
      고친 줄 번호는 sed 한 줄 출력으로 다시 확인
 6. 메인이 표본을 다시 대조하고 묶음별로 커밋한다
 7. 지도 README 와 api-index 를 완성 상태로 갱신한다
```

브리핑의 `<도구>`·`<소스>`·`<태그>`·`<커밋>`·`<워크트리>` 자리는 작업마다 채운다. 형식의 본보기는 [MySQL 지도](../../../opensource/mysql/architecture/README.md)다.

## 실측에서 배운 것

- 검증 워커도 틀린다. `sed -n A,Bp` 로 여러 줄을 보다가 맞는 줄 번호를 하나 어긋나게 고친 사례가 있어, 고친 값은 한 줄 출력으로 다시 확인하게 했다.
- 렌더 스크립트로 코드를 채우는 워커가 중단되면 `@@` 자리표시자가 남은 채 커밋될 수 있다. 병합 전에 `grep -rn '@@'` 로 0 을 확인한다.
- 예시 그림의 숫자(분할 지점, 가중치, 트랜잭션 번호)는 소스 규칙으로 손계산해 맞는지 검증 항목에 넣는다. 불가능한 시나리오가 실제로 하나 나왔다.
