# 데이터 모니터링/무중단 배포 시스템 구축 (중앙 관제, blue/green)

> 소속 경력: MarkView 서비스 개발 및 고도화 - 변리사 대상 글로벌 다국어 유사 상표 검색 서비스 (한국, 중국, 일본, 미국, 유럽) - 검색 알고리즘 설계, 검색 성능 개선, 데이터 모니터링/무중단 배포 시스템 구축

## 문제 상황

```text
## 구축 전 - 서버 2대, 관측 없음, 단일 인스턴스 배포

       +-- Data Hub 서버 (A) -----------------------------------------+                                +-- Control 서버 (B) ----------------------------------+
       |                                                              |                                |                                                      |
       |   +------------------------------------------------------+   |  ES 쿼리 질의/반환 (내부망)    |   +----------------------------------------------+   |
       |   | 5개국 x [ ES / FastAPI(인덱싱) / Kibana ]            |   <--------------------------------|   | 검색 서버 (단일 인스턴스)                    |   |
       |   +------------------------------------------------------+   |                                |   +----------------------------------------------+   |
       |   +-----------------------------+                            |                                |                                                      |
       |   | MariaDB (원천 파일)         |                            |                                |   x 무중단 배포 없음 (배포 = 중단)                   |
       |   +-----------------------------+                            |                                |   x 장애 시 수동 재구동                              |
       |   x 상태, 트래픽 부하 메트릭 수집 없음                       |                                |                                                      |
       |   x 확인하려면 SSH 접속 후 컨테이너 개별 조회                |                                |                                                      |
       |                                                              |                                |                                                      |
       |                                                              |                                |                                                      |
       +--------------------------------------------------------------+                                +------------------------------------------------------+
```

도식 32. 구축 전 - Data Hub 서버(5개국 ES, 인덱싱, Kibana, MariaDB)와 Control 서버(검색 서버). 메트릭 수집 없음, 단일 인스턴스

프로토타입을 빠르게 만드는 데 집중하느라 데이터 최신화가 자동화되어 있지 않았고, **각 서버의 현재 상황을 한눈에 볼 수 있는 구조가 없었습니다**. 서버 상태를 확인하려면 **매번 SSH로 접속해 도커 컨테이너 상태를 일일이 들여다봐야** 했습니다.

## 해결 과정

흩어진 시스템을 **한 곳에서 모니터링하고 자원까지 제어하는 중앙 관제 구조**로 바꾸고, 서버별 자원 임계점을 정해 두고 **임계점을 넘으면 알림 또는 자동 대응**하게 하자는 생각에서 출발했습니다.

### 관측과 자동 대응

- 수집: 에이전트가 일정 주기로 **도커 컨테이너 메트릭, 호스트 자원, ES 클러스터와 JVM heap 상태, 마이그레이션 진행 정보를 수집해 중앙으로** 올리고, **로그는 WebSocket으로 스트리밍**하며 에러와 인시던트 기록은 저장해 두고 알림으로 연결해 **대시보드 한 곳에서 확인**하게 했습니다.

```text
## 수집 워크플로우 - 에이전트 주기 수집 + 로그 스트리밍

     +----------------------------------+    +-----------------------------------+  +----------------------------------+   +----------------------------------+
     | Data Hub 에이전트                |    | 수집 항목                         |  | 별도 엔드포인트로                |   | 오케스트레이션 서버              |
     | 일정 주기 실행                   |----> 도커 컨테이너 메트릭             -|--> 중앙에 전송                      |---> 대시보드 한 곳에서 확인          |
     |                                  |    | 호스트 자원 (CPU, 메모리, 디스크) |  |                                  |   |                                  |
     |                                  |    | ES 클러스터, JVM heap             |  |                                  |   |                                  |
     |                                  |    | 마이그레이션 진행 정보            |  |                                  |   |                                  |
     +----------------------------------+    +-----------------------------------+  +----------------------------------+   +----------------------------------+

     로그와 에러
     +------------------------------------------+     +------------------------------------------+     +------------------------------------------+
     | 컨테이너 로그                            |     | 대시보드 실시간 표시                     |     | 에러, 인시던트                           |
     | WebSocket 스트리밍                       |----->                                          |-----> 별도 DB 저장 (분석 가능한 형태)          |
     | (누적 방지: 컨텍스트 윈도우)             |     |                                          |     | 알림 연결                                |
     +------------------------------------------+     +------------------------------------------+     +------------------------------------------+
```

도식 33. 수집 워크플로우 - 에이전트 주기 수집, 로그 스트리밍(컨텍스트 윈도우), 에러 별도 DB

- 임계점 기반 자동 대응: ES는 **힙이 고갈되면 컨테이너는 떠 있는데 응답을 못 하는 상태**가 빈번했고 **도커의 restart나 healthcheck로는 잡히지 않아**, 호스트 자원까지 함께 수집했습니다. **부하 테스트로 정한 임계점**을 넘으면 알림을 보내는 한편, **실행 중인 마이그레이션의 동시성(워커 수, 배치 크기)을 자동으로 낮춰 부하를 흡수**했습니다.

```text
## 임계점 기반 자동 대응 워크플로우

                                                                                               +----------------------+
     +------------------------------------+      +------------------------------------+        |                      |
     | 메트릭 수신                        |------> 임계점 비교                        |-------->        초과?         |
     |                                    |      | (부하 테스트로 정한 값)            |        |                      |
     +------------------------------------+      +------------------------------------+        |                      |
                                                                                     ----------+----------------------+-------------yes
                                                                                     |no                                           |
                                                                                     |                                             |
                                                                                     v                                             v
                                                                   +-----------------------------------+      +------------------------------------------+
                                                                   | 계속 관측                         |      | 자동 대응                                |
                                                                   |                                   |      | 알림 발송                                |
                                                                   |                                   |      | 실행 중 마이그레이션 동시성 하향         |
                                                                   +-----------------------------------+      | (워커 수, 배치 크기)                     |
                                                                                                              | 부하 흡수, 회복 후 복원                  |
                                                                                                              +------------------------------------------+
```

도식 34. 임계점 기반 자동 대응 - 초과 시 알림 + 마이그레이션 동시성 하향

- 장애 자동 복구: 컨테이너 사망은 **메트릭으로 감지해 원인(OOM 여부)과 마지막 로그를 수집한 뒤 자동 재구동**하고, 힙 고갈로 떠 있기만 한 상태는 **서비스 코드 차원에서 별도 감지**해 다시 띄웠습니다. 무한 재시작으로 번지지 않도록 **서킷브레이커**를 두어, 재시작이 반복되면 **쿨다운 후 재시도하고 회복되지 않으면 복구를 멈추고 사람이 개입**하도록 알림을 보냈습니다.

```text
## 장애 자동 복구 워크플로우 - 서킷브레이커로 무한 재시작 차단

     +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+
     | 감지                       |  | 원인 수집                  |  | 자동 재구동                |  | 재시작 반복?               |  | 복구 판정                  |
     | 컨테이너 사망 (메트릭)     |  | OOM 여부, 마지막 로그      |  |                            |  | (서킷브레이커)             |  | yes: 쿨다운 후 재시도      |
     | 힙 고갈로 응답 없음        |-->                            |-->                            |-->                            |--> 회복 안 되면 중단          |
     | (서비스 코드 차원 감지)    |  |                            |  |                            |  |                            |  | -> 사람 개입 알림          |
     |                            |  |                            |  |                            |  |                            |  | no: 정상 복귀              |
     +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+
```

도식 35. 장애 자동 복구 - 감지, 원인 수집, 재구동, 서킷브레이커

- 데이터 최신화 스케줄링: **국가별 정해진 시각에 증분 마이그레이션을 자동 트리거**하고(시각은 대시보드에서 런타임 변경 가능), **변경분 기준 + ES upsert(있으면 갱신, 없으면 추가)로 재시도해도 중복이 생기지 않게(멱등)** 처리해, ES에 **실제 누락된 건만 다시 처리해 데이터 손실을 최소화**했습니다.

```text
## 데이터 최신화 스케줄링 워크플로우 - 증분 + upsert 멱등

     +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+
     | 국가별 정해진 시각         |  | 증분 마이그레이션          |  | 변경분 기준 조회           |  | ES upsert                  |  | 누락 건만 재처리           |
     | (대시보드에서 런타임 변경) |--> 자동 트리거                |-->                            |--> 있으면 갱신, 없으면 추가   |--> 데이터 손실 최소화         |
     |                            |  |                            |  |                            |  | = 재시도해도 중복 없음     |  |                            |
     |                            |  |                            |  |                            |  |                            |  |                            |
     +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+  +----------------------------+
```

도식 36. 데이터 최신화 스케줄링 - 증분 트리거, upsert 멱등, 누락 건만 재처리

### 무중단 배포

```text
## 무중단 배포 워크플로우 - 검증 단계 전부 통과 + 사람 확인 -> nginx 전환 (blue/green)

     검증
     +--------------------------------+    +--------------------------------+   +--------------------------------+   +--------------------------------+
     | merge                          |    | 빌드                           |   | 헬스체크                       |   | 단위 테스트                    |
     |                                |    | 새 색상 컨테이너               |   |                                |   |                                |
     |                                |----> (현재 blue면 green)           -|--->                                |--->                                |
     +--------------------------------+    +--------------------------------+   +--------------------------------+   +--------------------------------+
                                                                                                                                      |
                           -----------------------------------------------------------------------------------------------------------|
     +---------------------v--------------------+     +------------------------------------------+
     | API 테스트                               |     | [사람 확인]                              |
     | 실제 요청으로 검색 결과 대조             |-----> 테스트 결과 검토 후 승인 (안전장치)      |
     |                                          |     |                                          |
     +------------------------------------------+     +------------------------------------------+

     승인 후 전환

     +-----------------------------------+  +-----------------------------------+ +-----------------------------------+ +-----------------------------------+
     | nginx upstream 전환               |--> 트래픽이 새 컨테이너로            |-> 구 컨테이너 대기                  |-> 안정 확인 후 정리                 |
     | blue -> green                     |  | 사용자 단절 없음                  | | 문제 시 upstream 되돌려 즉시 롤백 | | 다음 배포의 대기 슬롯             |
     |                                   |  |                                   | |                                   | |                                   |
     +-----------------------------------+  +-----------------------------------+ +-----------------------------------+ +-----------------------------------+
     * 한 단계라도 실패 -> 배포 중단, 기존 컨테이너 그대로 서비스 (검증되지 않은 빌드는 실제 검색에 노출되지 않음)
```

도식 37. 무중단 배포 워크플로우 - 검증 통과와 사람 확인 뒤 nginx upstream 전환, 구 컨테이너로 즉시 롤백 가능

GitLab 서버의 IP가 동적이라 러너를 고정해 등록해 둘 수 없어, 별도 GitLab CI 대신 **오케스트레이션 서버의 배포 파이프라인으로 처리**했습니다. merge 이후 git pull -> 빌드 -> 헬스체크 -> 단위 테스트 -> API 테스트(실제 API에 요청을 보내 검색 결과가 기대값과 맞는지 검증) 순으로 진행하고, **모든 단계를 통과한 경우에만 blue/green 방식으로 트래픽을 전환**하며 **한 단계라도 실패하면 배포를 중단**합니다. **검증되지 않은 빌드가 실제 검색에 노출되는 일을 막았습니다**. 검색 서버는 메인 비즈니스와 직결된 서비스라, 자동 API 테스트로 정합성까지 검사하더라도 실제 장애 시 서비스 신뢰성 문제가 남아 **마지막 단계에서 사람이 테스트 결과를 확인한 뒤 배포하는 안전장치**를 두었습니다.

### 구축 후 구조 - 중앙 관제 아키텍처 (k3s 구조의 응용)

```text
## 구축 후 구조 - 중앙 관제 + blue/green (Python, k3s 구조 응용)

       +-- Data Hub 서버 (A) ---------------------------------------------+            +-- Control 서버 (B) -------------------------------------------+
       |                                                                  |            |                                                               |
       |   +----------------------------------------------------------+   |            |   +---------------------------------------------------------+ |
       |   | 5개국 ES + 인덱싱 FastAPI + Kibana + MariaDB             |   메트릭, 로그 |   | 오케스트레이션 서버 (중앙 제어 + 대시보드)              | |
       |   +----------------------------------------------------------+  -|------------>   | 임계 판단 -> 스로틀링 / 알림                            | |
       |   +----------------------------------------------------------+   |            |   | 장애 감지 -> 자동 재구동, 서킷브레이커                  | |
       |   | 수집 에이전트 (es-collector)                             |   |            |   | 로그 스트리밍(컨텍스트 윈도우), 에러 DB, .env 중앙 제어 | |
       |   | 컨테이너, 호스트, ES/JVM heap, 마이그레이션 진행         |   |            |   +---------------------------------------------------------+ |
       |   +----------------------------------------------------------+   |            |                                                               |
       |                                                                  |            |   +-------------------------------------------------------+   |
       |   +----------------------------------------------------------+  명령, 스로틀링|   | nginx -> 검색 서버 [blue] [green]                     |   |
       |   | 재구동/제어 스크립트 (중앙 명령 수행)                    |  <|------------|   |                                                       |   |
       |   +----------------------------------------------------------+   |            |   +-------------------------------------------------------+   |
       |   | 증분 마이그레이션 (스케줄, upsert 멱등)                  |   |            |   | 배포 파이프라인 (검증 + 사람 확인 후 전환)            |   |
       |   +----------------------------------------------------------+   |            |   +-------------------------------------------------------+   |
       +------------------------------------------------------------------+            +---------------------------------------------------------------+
```

도식 38. 구축 후 구조 - Data Hub 서버의 에이전트와 Control 서버의 오케스트레이션, nginx 뒤 blue/green 검색 서버

중앙에서 오케스트레이션하고 각 노드의 에이전트가 해당 서버를 관리하는 **k3s의 구성 방식을, 우리 환경(검색 서비스용 2대 서버 체제)에 맞게 Python으로 응용**했습니다. Control 서버에는 오케스트레이션과 검색 서비스를, Data Hub 서버에는 국가별 ES, 마이그레이션 스택과 수집 에이전트(es-collector)를 두고, **중앙이 각 서버에 명령을 내리고 상태를 받아오는 형태**입니다.

## 결과

구축 이후 **운영 문제로 서버에 SSH로 접속할 필요가 사실상 없어졌습니다**. 부하로 인한 다운을 근본적으로 없애려면 IDC 서버 증설이 필요해 시간이 걸렸지만, 그동안에도 **자동 감지, 복구 구조가 다운타임을 짧게 억제**해 안정성을 유지했습니다. **서버 자원 관리, 로그와 에러 모니터링, 데이터 최신화 스케줄링, 무중단 배포까지를 대시보드 한 곳에서 처리하는 인프라**를 갖추게 되었습니다.
