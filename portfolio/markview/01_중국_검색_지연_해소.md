# 중국 검색 지연 해소 (세그먼트 최적화, 정렬 병목 제거)

> 소속 경력: MarkView 서비스 개발 및 고도화 - 변리사 대상 글로벌 다국어 유사 상표 검색 서비스 (한국, 중국, 일본, 미국, 유럽) - 검색 알고리즘 설계, 검색 성능 개선, 데이터 모니터링/무중단 배포 시스템 구축

## 핵심 요약

- 여러 조건을 조합한 검색은 9초 이상, 기본 검색도 5~6초가 걸리던 지연을 구간별 측정으로 ES 연산 단계까지 좁힘(중국 실 상표 데이터 약 8,600만 건, 분석 인덱스 포함 약 12억 건)
- 원인이 데이터의 절대 크기가 아니라 인덱스 구조임을 확인 - 세그먼트가 153개까지 늘어나고 크기도 28MB에서 2.7GB까지 불균형
- 성능을 노리고 force merge로 단일 세그먼트(약 120GB)까지 병합했다가 오히려 느려지는 역효과를 실측(되돌릴 수 없는 작업이라 운영 인덱스가 아닌 별도 테스트 ES 복제본에서 수행). 세그먼트는 분할 API가 없어 되돌릴 수 없다는 제약까지 확인하고 재색인 전제로 방향 전환
- 남은 병목이 정렬임을 실측(정렬 있음 5~6초, 제거 시 1.5초)해 키워드 없는 기본 검색에서 정렬을 제거, 기본 검색 응답을 약 70% 단축

## 문제 상황

중국 데이터를 Elasticsearch에 색인한 뒤 검색이 크게 느려졌습니다. 여러 조건을 조합한 검색은 9초 이상, 키워드 없이 조건만으로 조회하는 기본 검색도 5~6초가 걸렸습니다. 중국의 실 상표 데이터는 약 8,600만 건, 형태, 발음, 도치 분석용 인덱스를 모두 포함하면 약 12억 건 규모였습니다. 원본 MySQL에는 상표와 관련 테이블 전체가 들어 있었고, 그중 검색에 필요한 필드만 정규화해 ES에는 약 350GB로 적재한 상태였습니다. 유사 상표 검색은 변리사 업무 특성상 응답 속도가 곧 사용성이라, 이 지연은 그대로 둘 수 없는 문제였습니다.

## 해결 과정

```text
## 지연 구간 분리 - API 레이어와 ES 쿼리 작업, 2구간으로 나눠 측정

                   +-----------------------------+     +---------------------------+     +---------------------------+             
 +-----------+     | 구간 1: API 레이어          |     | 같은 IDC 내부 통신        |     | 구간 2: ES 쿼리 작업      |     +------+
 | 검색 요청 | --> | 쿼리 빌더 (조건 -> ES 쿼리) | --> | 네트워크 지연 = 측정 제외 | --> | 세그먼트 순회, 정렬, 집계 | --> | 응답 |
 +-----------+     | 측정: 작음                  |     +---------------------------+     | 측정: 지연의 대부분       |     +------+
                   +-----------------------------+                                       +---------------------------+             

   -> 병목은 검색 엔진(ES) 쪽. 이후 조사는 인덱스 구조(세그먼트)와 쿼리 단계(정렬)에 집중
```

*도식 15. 지연 구간 분리 - API 레이어(쿼리 빌더)와 ES 쿼리 작업 2구간, 같은 IDC 내부 통신이라 네트워크 지연은 제외*

가장 먼저 지연 구간을 나눠 측정했습니다. API 레이어와 ES 중 어디서 시간이 걸리는지 확인한 결과 ES 연산 과정이 지연의 대부분을 차지하고 있어, 병목이 검색 엔진 쪽임이 분명해졌습니다.

처음에는 "데이터 규모가 커서 느린 것 아닌가"라고 가정했지만, 인덱스 상태를 들여다보니 원인은 절대 크기가 아니라 구조였습니다. 세그먼트가 153개까지 늘어나 있었고 크기도 28MB에서 2.7GB까지 크게 불균형했습니다.

```text
## 세그먼트 파편화 과정 - refresh마다 생기는 소형 세그먼트를 병합이 따라가지 못함

 +----------------------+     +--------------------------------+     +---------------------------+     +-----------------------+
 | 대량 적재            |     | refresh (주기적)               |     | 백그라운드 병합           |     | 적재 속도 > 병합 속도 |
 | (중국 약 8,600만 건) | --> | 메모리 버퍼 -> 새 세그먼트 1개 | --> | 비슷한 크기끼리 계층 병합 | --> | 소형 세그먼트 누적    |
 +----------------------+     | 세그먼트는 불변, 작음          |     | CPU, 디스크 IO 사용       |     +-----------------------+
                              +--------------------------------+     +---------------------------+                              

 결과 = 153개, 28MB ~ 2.7GB 불균형
 +- 큰 것 ---------------------+     +- 작은 것 -------------------+
 | 2.7GB                       |     | 28MB  28MB  28MB  28MB  ... |
 | 이미 커진 세그먼트          |     | 소형 세그먼트 수십 개       |
 | = 병합 대상에서 사실상 제외 |     | 계속 생기고 계속 남음       |
 +-----------------------------+     +-----------------------------+
```

*도식 16. 세그먼트 파편화 - refresh마다 생기는 소형 세그먼트를 병합이 따라가지 못해 153개, 28MB ~ 2.7GB 불균형*

크기 불균형 자체도 원인의 일부였습니다. Elasticsearch의 병합 정책은 비슷한 크기의 세그먼트를 계층으로 묶어 단계적으로 합치는 방식이라, 크기가 극단적으로 벌어지면 이미 커진 세그먼트는 병합 대상에서 사실상 빠지고 작은 세그먼트만 계속 쌓입니다. 대량 적재 중에는 refresh 때마다 작은 세그먼트가 생기는 속도를 백그라운드 병합이 따라가지 못해 이 상태가 누적됩니다.

```text
## 검색이 느려지는 두 경로 - 세그먼트별 고정 순회 비용 + 끝나지 않는 병합 부하

                       +- 세그먼트마다 고정 비용 ----------------+                   
                       | seg 1 (2.7GB)  순회                     |                   
 +---------------+     | seg 2 (1.1GB)  순회                     |     +------------+
 | 검색 쿼리 1건 | --> | seg 3 (28MB)   순회  <- 데이터는 적은데 | --> | 결과 병합  |
 +---------------+     | seg 4 (28MB)   순회  <- 비용은 그대로   |     | 응답 5~6초 |
                       |   ...  x 153                            |     +------------+
                       | seg 153 (28MB) 순회                     |                   
                       +-----------------------------------------+                   

 +- 동시에: 백그라운드 병합 ------------------------+
 | 소형 세그먼트 계속 생성 -> 병합 스레드 상시 가동 |
 | CPU, 디스크 대역폭을 검색과 나눠 씀              |
 +--------------------------------------------------+

   검색 = 세그먼트 수만큼 붙는 순회 오버헤드  +  서버 = 끝나지 않는 병합 IO  ->  동시에 느려짐
```

*도식 17. 느려지는 두 경로 - 세그먼트별 고정 순회 비용, 동시에 도는 백그라운드 병합의 CPU, 디스크 IO 경합*

검색은 세그먼트마다 순회 비용이 고정으로 붙기 때문에, 28MB짜리 세그먼트 수십 개는 담고 있는 데이터량에 비해 오버헤드만 키우는 셈이었습니다. 여기에 더해, 작은 세그먼트가 계속 생기는 동안에는 백그라운드 병합 작업이 쉬지 않고 돌면서 CPU와 디스크 대역폭을 검색과 나눠 쓰게 됩니다. 즉 검색은 세그먼트마다 붙는 순회 비용으로, 서버는 끝나지 않는 병합 부하로 동시에 느려지는 상태였습니다.

### force merge - 방향 확인과 과도 병합의 역효과

```text
## force merge 역효과 - 단일 세그먼트(약 120GB)는 전체 순회 비용이 더 컸다 (별도 테스트 ES 복제본에서 실측)

 +- 병합 전 ----------------+     +- 단일 세그먼트로 병합 --------+     +- 확인한 사실 ------------------+
 | seg x 153 (28MB ~ 2.7GB) |     | seg x 1 (약 120GB)            |     | 세그먼트 수 적정 구간          |
 | 세그먼트마다 순회 비용   |     | 조건 안 맞는 세그먼트를       |     | 너무 많아도, 하나뿐이어도 느림 |
 | + 병합 부하 상시         | --> | 통째로 건너뛰는 최적화 상실   | --> | -> '적을수록 빠르다'는 가정은  |
 | -> 5~6초                 |     | 캐시, 메모리 매핑 단위 거대화 |     |    어느 지점부터 성립하지 않음 |
 +--------------------------+     | -> 오히려 더 느림 (반복 측정) |     +--------------------------------+
                                  +-------------------------------+
```

*도식 18. force merge 역효과 - 단일 세그먼트는 건너뛰기 최적화를 잃고 전체 순회 비용이 커져 오히려 느림, 적정 구간의 존재를 확인*

세그먼트 수를 줄이는 방향이 맞다고 보고 force merge를 진행했습니다. 병합은 되돌릴 수 없는 작업이라 운영 인덱스가 아니라 별도 테스트용 ES에 데이터를 복제해 실험했고, 성능을 더 끌어올리려 단일 세그먼트까지 병합해 봤습니다. 그러나 약 120GB짜리 단일 세그먼트가 되자 오히려 느려졌습니다. 세그먼트가 하나뿐이면 조건에 맞지 않는 세그먼트를 통째로 건너뛰는 최적화를 잃고 캐시와 메모리 매핑 단위도 거대해진다는 것을 유력한 가설로 봤습니다. 원인을 항목별로 분리해 측정하지는 못했지만, "세그먼트는 적을수록 빠르다"는 처음 가정이 어느 지점부터는 성립하지 않는다는 사실 자체는 반복 측정으로 확인했습니다.

### 되돌릴 수 없다는 제약 확인

```text
## 해결 - 세그먼트 최대 크기 상한 고정 + 재색인 (병합은 단방향, 분할 API 없음)

 +-----------------------+     +-----------------------------------+                                       +-------------------------+
 | 분할 API 없음 확인    |     | 세그먼트 최대 크기 상한을         |     +---------------------------+     | 세그먼트 수, 크기가     |
 | 병합 = 되돌릴 수 없음 | --> | 데이터 규모에 맞춰 지정           | --> | 파편화 누적된 운영 인덱스 | --> | 적정 구간 유지          |
 | 되돌리려면 재색인     |     | -> 병합이 한 덩어리로 쏠리지 않음 |     | 재색인으로 정리           |     | 이후 인덱스 구조 변경은 |
 +-----------------------+     +-----------------------------------+     +---------------------------+     | 재색인 전제로 설계      |
                                                                                                           +-------------------------+
```

*도식 19. 해결 - 세그먼트 최대 크기 상한 고정 + 재색인, 이후 인덱스 구조 변경은 재색인 전제*

병합한 세그먼트를 다시 여러 개로 나누려 했지만, Elasticsearch에는 세그먼트를 분할하는 API가 없다는 것을 확인했습니다. 병합은 단방향이라 구조를 되돌리려면 재색인이 필요합니다. 이후 세그먼트 최대 크기 상한을 데이터 규모에 맞춰 지정해 병합이 한 덩어리로 쏠리지 않고 적정 구간을 유지하도록 했고, 이미 파편화가 누적된 운영 인덱스는 재색인으로 정리했습니다.

### 정렬 병목 제거

```text
## 정렬 분기 워크플로우 - 정렬이 의미 있는 경우에만 수행

 +-----------+     +------------------------+
 | 검색 요청 | --> | 키워드 있음?           |
 +-----------+     | 또는 사용자 정렬 지정? |
                   +------------------------+
                               |
               +---------------+----------------+
               |                                |
               v                                v
  +- no --------------------+    +- yes ----------------------+
  | 기본 검색 (조건만 조회) |    | 키워드 검색: score 순 정렬 |
  | 정렬 생략               |    | 정렬 지정: 지정 기준 정렬  |
  | -> 약 1.5초             |    | -> 정렬 수행               |
  +-------------------------+    +----------------------------+

   결과: 정렬 있음 5~6초 -> 기본 검색 1.5초 (약 70% 단축). 대량 결과에 붙던 정렬 비용을 필요한 경우로 한정
```

*도식 20. 정렬 분기 - 조건만 조회하는 기본 검색은 정렬 생략, 키워드 검색이나 정렬 지정 시에만 수행*

남은 병목은 정렬이었습니다. 대량 결과에 정렬을 적용하면 5~6초, 정렬을 빼면 1.5초로 측정돼 정렬 단계가 지배적임을 확인했습니다. 그래서 정렬을 조건부로 나눴습니다. 키워드 없이 조건만으로 조회하는 기본 검색에서는 정렬을 제거하고, 사용자가 정렬 기준을 명시했거나 키워드 검색이라 score가 의미를 갖는 경우에만 정렬을 수행하도록 했습니다.

## 결과

정렬 정책 분리로 기본 검색 응답을 5~6초에서 1.5초 수준으로, 약 70% 단축했습니다.

## 회고

수치보다 남은 것은 판단 기준이었습니다. 세그먼트는 많아도 적어도 안 되며 그 사이에 최적 구간이 있다는 것을 역효과까지 겪으며 실측으로 확인했고, 병합이 되돌릴 수 없는 작업이라는 점 때문에 이후로는 인덱스 구조 변경을 재색인 전제로 설계하게 됐습니다. 이 경험이 다음 프로젝트에서 샤드 수를 확정하기 전에 통제된 부하 실험을 먼저 설계한 배경입니다(경력 1 - 05).
