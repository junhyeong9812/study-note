# 중국 검색 지연 해소 (세그먼트 최적화, 정렬 병목 제거)

> 소속 경력: MarkView 서비스 개발 및 고도화 - 변리사 대상 글로벌 다국어 유사 상표 검색 서비스 (한국, 중국, 일본, 미국, 유럽) - 검색 알고리즘 설계, 검색 성능 개선, 데이터 모니터링/무중단 배포 시스템 구축

## 한 줄 요약

중국 상표 약 8,600만 건을 색인한 뒤 기본 검색이 5~6초가 됐고, 원인을 데이터 크기가 아니라 **세그먼트 구조와 정렬 단계**로 특정해 세그먼트 상한 재지정과 정렬 분기로 **1.5초**까지 줄였습니다.

## 문제 상황

중국 상표 약 8,600만 건을 색인한 뒤 **기본 검색이 5~6초**, 조건을 조합한 검색은 9초 이상이 됐습니다.\
분석용 인덱스까지 약 12억 건, ES 적재 약 350GB 규모였습니다.\
변리사 업무는 응답 속도가 곧 사용성이라 그대로 둘 수 없었습니다.

1. [중국 데이터 색인 뒤 기본 검색 5~6초, 조건 조합 검색 9초 이상](문제상황/01_색인_후_검색_지연/post.md)
2. [실 상표 약 8,600만 건, 분석 인덱스 포함 약 12억 건, ES 약 350GB](문제상황/02_데이터_규모와_적재_상태/post.md)
3. [변리사 업무 특성상 응답 속도가 사용성이라 지연을 둘 수 없음](문제상황/03_응답_속도가_곧_사용성/post.md)

## 해결 과정

세 번의 판단으로 진행했습니다. 가정을 실측으로 검증하고, 되돌릴 수 없는 작업은 복제본에서 먼저 실험하고, 남은 병목은 정책으로 분리했습니다.

**판단 1. 병목은 데이터 크기가 아니라 구조다**\
"데이터가 커서 느리다"는 첫 가정을 측정으로 접었습니다.

1. [API 레이어와 ES 쿼리 두 구간을 따로 재니 지연의 대부분이 ES 연산이었다](해결과정/01_지연_구간_측정/post.md)
2. [인덱스를 열어 보니 세그먼트가 153개, 크기가 28MB에서 2.7GB로 불균형했다 - 절대 크기가 아니라 구조 문제](해결과정/02_원인_세그먼트_구조_특정/post.md)
3. [왜 이렇게 됐나: 크기가 벌어지면 병합 정책이 큰 세그먼트를 제외하고 작은 세그먼트만 쌓는다](해결과정/03_세그먼트_파편화_원리/post.md)
4. [왜 느린가: 세그먼트마다 붙는 고정 순회 비용과 끝나지 않는 백그라운드 병합의 CPU/IO 경합, 두 경로가 동시에 작용](해결과정/04_느려지는_두_경로/post.md)

**판단 2. 세그먼트는 적을수록 좋은 것이 아니다**\
두 번째 가정도 실험으로 접었습니다. 병합은 되돌릴 수 없으므로 운영 인덱스가 아니라 복제본에서 했습니다.

5. [테스트 ES 복제본에서 단일 세그먼트(약 120GB)까지 force merge - 오히려 느려지는 역효과를 실측, 적정 구간이 있다](해결과정/05_force_merge_실험/post.md)
6. [되돌릴 수 없음을 확인 - 병합은 단방향이고 세그먼트 분할 API가 없어 구조를 되돌리려면 재색인뿐](해결과정/06_되돌릴_수_없는_제약/post.md)

**판단 3. 상한을 정해 두고, 남은 병목은 정책으로 가른다**\
전부를 한 번에 고치지 않고 세그먼트와 정렬을 따로 다뤘습니다.

7. [세그먼트 최대 크기 상한을 5GB로 재지정(IO 시간과 연산 시간을 따로 재서 고른 값)하고, 파편화된 운영 인덱스는 재색인으로 정리](해결과정/07_상한_재지정_재색인/post.md)
8. [정렬을 빼면 5~6초가 1.5초 - 정렬이 지배적 병목. 중국 한정으로 정렬 지정 시 수행, 미지정 시 500만 건(정렬의 CPU와 IO가 서버 용량을 넘기 시작한 경계) 기준 생략 또는 기본 정렬로 2차 분기](해결과정/08_정렬_병목_분기/post.md)

덧붙임: [병합 정책의 하한(floor_segment)이 동작하는 방식 - 처음부터 두었다면 파편화를 막았을 설정](해결과정/09_최소_세그먼트_설정_동작_방식/post.md)

선택하지 않은 방법: 단일 세그먼트까지 병합(역효과 실측), 정렬을 무조건 제거(사용자가 지정한 정렬은 그대로 수행해야 하고 결과가 작으면 기본 정렬 비용을 감수할 수 있어 조건 분기로 대체).

## 결과

- 기본 검색 응답 **5~6초 -> 1.5초 (약 70% 단축)** - 정렬 정책 분리의 효과
- 세그먼트 상한 재지정과 재색인으로 소형 세그먼트 누적과 끝나지 않는 병합 부하를 제거
- 이후 인덱스 구조 변경은 재색인을 전제로 설계

## 회고

수치보다 남은 것은 판단 기준이었습니다.\
**세그먼트는 많아도 적어도 안 되며 그 사이에 최적 구간이 있다**는 것을 **역효과까지 겪으며 실측으로 확인**했고,\
병합이 되돌릴 수 없는 작업이라는 점 때문에 이후로는 **인덱스 구조 변경을 재색인 전제로 설계**하게 됐습니다.\
이 경험이 다음 프로젝트에서 **샤드 수를 확정하기 전에 통제된 부하 실험을 먼저 설계한 배경**입니다(경력 1 - 05).\
아쉬운 점은 **병합 정책의 하한을 처음부터 5GB로 두지 않은 것**입니다. 그랬다면 소형 세그먼트가 쌓이지 않아 파편화도 force merge도 없었을 것이고, 이 설정이 어떻게 동작하는지는 해결 과정의 덧붙임에 정리했습니다.
