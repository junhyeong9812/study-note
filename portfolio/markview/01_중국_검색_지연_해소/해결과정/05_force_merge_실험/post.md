# 5. 테스트 ES 복제본에서 force merge 실험: 단일 세그먼트(약 120GB)는 오히려 느려지는 역효과를 실측

> 중국 검색 지연 해소 - 해결 과정 5/8. [사례로 돌아가기](../../) | [이전 4단계](../04_느려지는_두_경로/post.md) | [다음 6단계](../06_되돌릴_수_없는_제약/post.md)

### force merge 역효과 - 단일 세그먼트(약 120GB)는 오히려 느렸다 (별도 테스트 ES 복제본에서 실측)

```text
     +-------------------------------------------------+  +----------------------------------------------------+-+-----------------------------------------------+
     | 병합 전                                         |  | 단일 세그먼트로 병합                               | 확인한 사실                                     |
     | seg x 153 (28MB ~ 2.7GB)                        |--> seg x 1 (약 120GB)                              ---> 세그먼트 수 적정 구간 존재                      |
     | 세그먼트마다 순회 비용 + 병합 부하              |  | 조건 안 맞는 세그먼트 건너뛰기 최적화 상실         | '적을수록 빠르다'는 어느 지점부터 성립 안 함    |
     | -> 5~6초                                        |  | 캐시, 메모리 매핑 단위 거대화 -> 더 느림 (반복 측정) |                                               |
     |                                                 |  |                                                    | |                                               |
     +-------------------------------------------------+  +----------------------------------------------------+-+-----------------------------------------------+
```

도식 31. force merge 역효과 - 단일 세그먼트는 건너뛰기 최적화를 잃고 전체 순회 비용이 커져 오히려 느림, 적정 구간의 존재를 확인

세그먼트 수를 줄이는 방향이 맞다고 보고 force merge를 진행했습니다.\
병합은 되돌릴 수 없는 작업이라 **운영 인덱스가 아니라 별도 테스트용 ES에 데이터를 복제해 실험**했고, 성능을 더 끌어올리려 단일 세그먼트까지 병합해 봤습니다.\
그러나 **약 120GB짜리 단일 세그먼트가 되자 오히려 느려졌습니다**. 세그먼트가 하나뿐이면 **조건에 맞지 않는 세그먼트를 통째로 건너뛰는 최적화를 잃고** 캐시와 메모리 매핑 단위도 거대해진다는 것을 유력한 가설로 봤습니다.\
원인을 항목별로 분리해 측정하지는 못했지만, "세그먼트는 적을수록 빠르다"는 처음 가정이 어느 지점부터는 성립하지 않는다는 사실 자체는 **반복 측정으로 확인**했습니다.

### 지금의 설명 - 단일 세그먼트가 느려진 세 가지 이유

당시에는 원인을 항목별로 분리해 재지 못했지만, 지금은 세 가지로 설명합니다.

1. **병렬성 손실** - 사용하던 ES 8.15는 한 샤드의 세그먼트들을 여러 슬라이스로 나눠 동시에 검색합니다. 세그먼트가 하나면 나눌 단위가 없어 검색과 IO가 한 줄로 직렬화됩니다. 이 이득은 코어에 여유가 있고 디스크가 병렬 읽기를 감당(SSD)할 때의 이야기이고, 포화 상태의 처리량은 코어 수가 정합니다. 반대로 세그먼트가 너무 많으면 세그먼트마다 역색인과 doc values를 여는 고정 비용이 병렬 이득을 넘어서므로, 두 힘이 만나는 적정 구간이 생깁니다.
2. **건너뛰기 손실** - 세그먼트마다 갖는 범위 정보와 삭제 문서 정보로 조건에 맞지 않는 세그먼트를 통째로 제외하는데, 하나뿐이면 이 최적화가 사라지고 정렬과 집계에서 doc values를 읽는 범위도 120GB 전체가 됩니다.
3. **캐시 손실** - 120GB 파일은 페이지 캐시에 머물지 못해 매 요청의 상당 부분이 디스크 IO로 떨어집니다.

역색인 자체는 그대로라 term 조회가 풀스캔이 되는 것은 아닙니다. 느려진 것은 스캔 방식이 아니라 병렬성, 건너뛰기, 캐시 세 이점을 동시에 잃었기 때문이며, 그래서 세그먼트에는 적정 구간이 있고 그 값이 7단계의 5GB였습니다.
