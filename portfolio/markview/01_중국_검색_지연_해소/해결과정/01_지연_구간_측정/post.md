# 1. 지연 구간을 API 레이어와 ES 쿼리 두 구간으로 나눠 측정해 병목이 ES 연산임을 확인

### 지연 구간 분리 - API 레이어와 ES 쿼리 작업, 2구간으로 나눠 측정

```text
     +---------------------------+   +-----------------------------+ +---------------------------+  +---------------------------+   +---------------------------+
     | 검색 요청                 |   | 구간 1: API 레이어          | | 같은 IDC 내부 통신        |  | 구간 2: ES 쿼리 작업      |   | 응답                      |
     |                           |---> 쿼리 빌더 (조건 -> ES 쿼리)-|-> 네트워크 지연 = 측정 제외 |--> 세그먼트 순회, 정렬, 집계 |--->                           |
     |                           |   | 측정: 작음                  | |                           |  | 측정: 지연의 대부분       |   |                           |
     |                           |   |                             | |                           |  |                           |   |                           |
     +---------------------------+   +-----------------------------+ +---------------------------+  +---------------------------+   +---------------------------+
     * -> 병목은 검색 엔진(ES) 쪽. 이후 조사는 인덱스 구조(세그먼트)와 쿼리 단계(정렬)에 집중
```

도식 26. 지연 구간 분리 - API 레이어(쿼리 빌더)와 ES 쿼리 작업 2구간, 같은 IDC 내부 통신이라 네트워크 지연은 제외

가장 먼저 **지연 구간을 나눠 측정**했습니다.\
측정은 API 레이어의 구간별 타이밍 로그로 했습니다. 요청 수신, 쿼리 조립, ES 호출과 응답, 결과 가공의 경계마다 시각을 남겨 구간 소요를 뽑았습니다.\
API 레이어와 ES 중 어디서 시간이 걸리는지 확인한 결과 **ES 연산 과정이 지연의 대부분**을 차지하고 있어, **병목이 검색 엔진 쪽**임이 분명해졌습니다.
