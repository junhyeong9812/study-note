# 약 50억 행 저장소 계층 설계와 레거시 통합 (아키텍처, 인증/인가, 11개국 단일 검색 인덱스)

> 소속 경력: 한국지식재산보호원 K-브랜드 지킴이 - 해외 상표 무단선점 경보 서비스 개발
> 한국지식재산보호원 발주 "해외 상표 무단선점 시스템" (나라장터 공개 공공 발주 사업). 2026-07-27 K-브랜드 지킴이(www.ip-navi.or.kr/kbrands/guard)로 대국민 배포를 완료했습니다.

## 핵심 요약

- 물리 서버 2대에 부하 성격이 다른 서비스(WAS, 프론트 / 검색, ETL)를 나눠 배치하는 아키텍처를 Docker Compose로 설계하고, 레거시(Java 8, Spring 2.x) 통합과 인증/인가(JWT, DB 기반 동적 권한) 설계 담당. 별도 사이트로 가던 초기 설계에 로그인 상호 유지 요구가 중간에 들어와 레거시 인증/인가 구조를 분석해 재설계
- 로그인 세션: 리프레시 토큰을 두지 않는 sliding 모델(유효한 액세스 토큰을 제시하면 재발급, 액세스 만료 1시간, 최초 로그인 시각 고정 클레임 기준 절대 만료 8시간) + 사용자별 활성 토큰 1개만 인정하는 화이트리스트로 단일 활성 세션
- 약 50억 행(11개국, 상표 관련 전체 테이블 합산) 원본 데이터를 사용 목적에 따라 저장소를 나눠 설계. 검색용은 선별한 데이터를 ES에, 관리자 조회용 원본 전체는 저빈도 조회 전용 lake로 MySQL에 두어 자원을 검색 경로에 집중. 인프라가 기관 할당이라 증설이 어려워, 색인 데이터 최소화와 국가별 상세 데이터 제한으로 MySQL 원본과 ES 인덱스를 모두 기존 SSD 용량 안에 들여놓음
- 1개월 시점에 추가된 11개국 동시 검색 요구를, 국가별로 격리돼 있던 검색 인덱스를 단일 검색 인덱스 + 상세 인덱스 구조로 전환하고 국가별 데이터 정규화와 검색 알고리즘을 통일해 흡수

## 문제 상황

백지에서 시작하는 신규 개발이 아니라, 이미 운영 중인 기존 서비스에 우리 서비스를 추가로 결합하는 형태였습니다.

처음 설계는 기존 서비스와 신규 사이트를 서로 다른 사이트로 두는 구조였습니다. 그런데 프로젝트 1개월이 지난 시점에 로그인은 양쪽이 상호 유지되었으면 한다는 요구사항이 들어왔고, 이미 설계를 마친 인증/인가를 레거시(Java 8, Spring 2.x 기반 WAR)의 인증/인가 구조를 분석해 다시 설계해야 했습니다. 진입 서버에서 사용자를 기존 서비스 또는 신규 사이트로 분기하되, 로그인, 인증과 일부 백오피스 기능은 양쪽이 공유하고 화면 스타일도 통일해야 하는 구조가 된 것입니다.

데이터 측면의 제약은 더 컸습니다. 원본 데이터는 JSON 파일 형태로 보존하면서, 그 JSON을 원본 형태 그대로 MySQL에 적재한 뒤 ES로 가공해야 했습니다. 11개국 JSON과 이미지 데이터는 약 9TB였고, 상표 관련 전체 테이블을 합산하면 약 50억 행(중국을 제외한 나머지 국가 기준으로도 인덱스 포함 약 1.35TB)입니다. 상표 데이터는 출원번호가 서로 랜덤한 위치에 흩어져 있어 조회가 본질적으로 랜덤 액세스인데, HDD는 순차 읽기와 지역성에 기대는 구조라 이 워크로드에서는 지연이 너무 컸습니다(랜덤 액세스 기준 SSD 대비 약 100배 수준으로 느림). 그런데 인프라 서버 자원은 정부 기관에서 할당받는 구조라, 더 큰 SSD나 HDD를 비용 문제로 추가 지원받기 어려웠습니다.

여기에 4개국 검색을 기준으로 시작했던 검색 범위가, 역시 1개월이 지난 시점에 "11개국 데이터가 있으니 전부 한 번에 검색되게 해 달라"는 요구로 바뀌었습니다. 인증과 검색 두 축에서 요구사항이 중간에 바뀐 상태에서, 늘릴 수 없는 자원 안에 들어가는 설계를 다시 찾아야 했습니다.

## 해결 과정

### 아키텍처와 역할 분담

```text
## 물리 서버 2대 - 부하 성격이 다른 서비스의 분리 (Docker Compose)

 +- A 서버 - 사용자 요청 -----------+                  +- B 서버 - 검색, 데이터 ---------------------------------------+
 | Next.js 프론트엔드               |                  | text-server (텍스트 검색)   image-server (이미지 검색)        |
 | WAS (사용자 요청 처리)           |  <-- 내부망 -->  |   bulkhead: 커넥션 풀 최대 동시 100 / fail-fast: 타임아웃 5초 |
 |                                  |                  |   (과부하가 ES로 번지지 않게 차단)                            |
 | 레거시 연동, 인증/인가, 백오피스 |                  | ES (검색 인덱스, SSD)      MySQL (원본 lake)                  |
 +----------------------------------+                  | 원천 데이터 (HDD, 국가별)  이미지 (NAS)                       |
                                                       | 데이터 ETL 전처리 API                                         |
                                                       +---------------------------------------------------------------+

   애플리케이션 아키텍처, API 설계, 프론트/백엔드 담당 (물리 인프라와 자원 할당은 별도 담당)
```

*도식 1. 물리 서버 2대 - 사용자 요청(A)과 검색, 데이터(B)의 분리, text-server의 bulkhead와 fail-fast*

물리 서버 2대에 인스턴스를 나눠 배치했습니다. 사용자 요청을 처리하는 WAS(웹 애플리케이션 서버)와 Next.js 프론트엔드를 한 서버에, 텍스트, 이미지 검색 인스턴스와 데이터 ETL(추출, 변환, 적재) 전처리 API를 다른 서버에 두어 부하 성격이 다른 서비스를 분리하고, 이 구성을 Docker Compose로 설계했습니다. 검색 서버(text-server)는 커넥션 풀 상한(최대 동시 100)과 요청 타임아웃(5초)으로, 과부하가 Elasticsearch로 번지지 않게 막고 문제 시 빠르게 실패시키는 방어 구조(bulkhead, fail-fast)를 갖췄습니다. 애플리케이션 아키텍처와 API 설계, 프론트엔드, 백엔드 개발을 담당했고, 물리 인프라와 자원 할당은 별도 담당이었습니다.

### 레거시 통합과 인증/인가 재설계

```text
## 레거시 통합 - 공유 영역은 JDBC 조회, 신규 영역은 자체 DB(JPA), 권한은 변환 정책으로 래핑

 +- 레거시 (연계 기업 운영) --------+                +- 우리 WAS ---------------------------------------------+
 | 레거시 서버 (Java 8, Spring 2.x) |                | 공유 영역: 레거시 DB를 JDBC로 직접 조회                |
 | 레거시 DB                        |  <-- JDBC -->  |   (로그인, 백오피스 공유 - 스키마 무변경)              |
 |   회원, 로그인, 권한 원본        |                | 신규 영역: 자체 DB만 JPA로 사용                        |
 +----------------------------------+                |                                                        |
                                                     | 레거시 권한 조회 -> 변환 정책 -> 자체 인증/인가 테이블 |
                                                     |   (레거시 권한을 우리 정책으로 래핑, 접근 권한 분리)   |
                                                     | Spring Security 6 JWT + DB 기반 동적 권한(RBAC)        |
                                                     +--------------------------------------------------------+

   기존 시스템과 충돌 없이 맞물리고, 신규 영역은 우리 구조로 - 결정은 구현 가이드로 정리해 팀 공통 기준화
```

*도식 2. 레거시 통합 - 공유 영역은 JDBC 조회, 신규 영역은 자체 DB(JPA), 레거시 권한을 변환 정책으로 래핑해 접근 권한 분리*

기존 팀이 구축한 DB 스키마와 서버 코드, 데이터 처리 절차를 직접 분석해, 공유 영역은 기존 시스템과 충돌 없이 맞물리게 하고 신규 영역은 우리 구조로 구현하는 방식으로 통합을 설계했습니다. 신규 영역은 전자정부 프레임워크의 레거시, MSA 예제 코드를 직접 분석해, 보안성 평가를 통과해야 하는 인증, 인가와 통신 구조는 MSA 예제를 커스터마이징하고, 게시판 등 도메인 모듈은 레거시 예제 기반에 데이터 접근 계층만 JPA로 전환하는 식으로 영역별로 적합한 구조를 선택했습니다. 이 결정들은 구현 가이드로 정리해 팀이 동일한 기준으로 개발하게 했습니다. 이미 설계해 둔 인증/인가는 이 분석 결과에 맞춰 다시 설계해, Spring Security 6 기반 JWT 인증과 DB 기반 동적 권한(RBAC)으로 로그인과 백오피스를 양쪽이 공유하게 했습니다.

### 로그인 세션 모델 - 리프레시 토큰이 없는 것이 설계

```text
## 로그인 세션 갱신 워크플로우 - 리프레시 토큰 없는 sliding, 절대 만료 8시간, 단일 활성 세션

 +-------------------------+     +------------------------------------+     +---------------------------------+     +-----------------------------------+
 | 유효한 액세스 토큰 제시 |     | 최초 로그인 시각 클레임 확인       |     | DB에서 사용자 재조회            |     | 새 액세스 토큰 발급               |
 | (만료 1시간)            | --> | 8시간 경과? -> 갱신 거부, 재로그인 | --> | 권한, 계정 상태 재파생          | --> | 화이트리스트 식별자 교체          |
 +-------------------------+     | (무한 연장 차단)                   |     | 정지 전이 시에만 즉시 폐기 가드 |     | -> 이전 토큰 자동 폐기(단일 세션) |
                                 +------------------------------------+     +---------------------------------+     +-----------------------------------+

   화이트리스트 선택 근거: 재시작으로 목록이 비면 전부 무효 = 안전한 방향의 실패 (블랙리스트는 폐기 토큰이 되살아남)
   절대 만료로 연장 거부 시: 강제 로그아웃 대신 안내 후 현재 토큰의 자연 만료로 전환 (서버 상태와 일치하도록 정책 정정)
```

*도식 3. 세션 갱신 - 절대 만료 확인, DB 재파생, 화이트리스트 교체로 단일 활성 세션*

레거시와 로그인을 공유하는 회원, 관리자 경로의 세션 모델은 다음 원칙으로 설계했습니다(비회원 이메일 OTP 인증은 경력 1 - 03).

- 리프레시 토큰을 발급하지 않습니다. 유효한 액세스 토큰을 제시하면 새 액세스 토큰을 내주는 sliding 방식이고, 액세스 만료는 1시간입니다. 무한 연장을 막기 위해 최초 로그인 시각을 별도 클레임으로 고정해 실어, 그 시점부터 8시간이 지나면 갱신을 거부하고 재로그인을 요구합니다.

- 단일 활성 세션은 블랙리스트(쓰인 토큰을 등록해 재사용을 거절)가 아니라 화이트리스트(사용자별 활성 토큰 식별자 1개만 유지)로 택했습니다. 새로 발급하면 이전 토큰이 자동으로 폐기되고, 인스턴스가 재시작해 목록이 비면 전부 무효가 되어 안전한 방향으로 실패합니다. 블랙리스트는 반대로 재시작하면 비어서 폐기된 토큰이 되살아납니다. 이 정리 과정에서 토큰에 식별자가 아예 발급되지 않아 정책이 사실상 무력했던 결함을 발견해 함께 고쳤습니다.

- 갱신 시 사용자를 DB에서 다시 조회해 권한과 계정 상태를 재파생하도록 했습니다. 권한 변경과 비활성 전환이 갱신 시점에 반영됩니다. 계정 상태나 자격증명이 바뀌는 흐름에는 즉시 폐기를 추가했는데, 무조건 폐기하면 남의 계정을 강제 로그아웃시키는 수단이 되므로 실제로 정지 상태로 전이된 경우만 폐기하도록 가드를 걸었습니다.

- 헤더에 남은 시간과 연장을 붙일 때는 코드 리뷰를 하는 과정에서 정책이 서버 상태와 어긋나는 문제를 발견해 정책을 정정했습니다. 절대 만료로 연장이 거부되면 즉시 로그아웃시키려 했지만, 서버는 현재 토큰이 만료될 때까지는 인증을 허용합니다. 그래서 강제 로그아웃 대신 안내를 띄우고 로그인을 유지한 뒤 실제 만료 시점에 자연 전환하게 바꿨습니다.

### 접근 패턴별 계층 분리

```text
## 접근 패턴별 계층 분리 - 저장 3계층과 적재 파이프라인, 11개국 단일 통합 인덱스

 [B 서버 저장 계층]
 +- HDD - 원천 -----------------+   +- SSD -------------------------------+   +- NAS - 이미지 -----------------------+
 | 국가별 원본 zip              |   | MySQL: 선별 적재한 원본 lake        |   | 이미지 서빙용 정적 파일              |
 |   상표 데이터: json 또는 xml |   |   관리자 경로 - 완전성 우선(저빈도) |   | 파일명 = 출원번호 -> 해싱키 파티셔닝 |
 |   이미지: jpeg, png          |   | ES: 검색 인덱스만                   |   |   국가 규모 따라 3자리 / 4자리 키    |
 +------------------------------+   |   사용자 경로 - 속도 우선           |   |   정적 파일 탐색 고속화              |
                                    +-------------------------------------+   +--------------------------------------+

 [적재 파이프라인]
                                                  +-----------------------------------+     +-----------------------------+
 +----------------------+     +-------------+     | 검색 필요 필드만 ES 색인          |     | 11개국 단일 통합 인덱스     |
 | zip 배치 해제        | --> | MySQL 적재  | --> | 상표명 변환 필드 생성             | --> | 국가별 정규화 어댑터로 흡수 |
 | json/xml 메모리 로드 |     | (원본 lake) |     |   원본 / 영어 / 한국어 발음 3계열 |     | (국가 추가 = 어댑터 추가)   |
 +----------------------+     +-------------+     |   변환 저장 -> 검색 시 O(1) 탐색  |     +-----------------------------+
                                                  +-----------------------------------+                                    

   상세 조회: ES가 돌려준 출원번호로 MySQL join (상세까지 ES에 정제해 두기에는 용량 부족 - 의도적 분리)
```

*도식 4. 저장 3계층(HDD 원천, SSD의 MySQL lake와 ES, NAS 이미지 해싱 파티셔닝)과 적재 파이프라인, 11개국 단일 통합 인덱스*

50억 행을 전부 SSD에 둘 수 없다는 제약 아래, 같은 데이터를 두 경로에 나눠 각각 저장하는 설계로 타협했습니다.

- 사용자 경로(속도 우선): 검색에 실제 필요한 데이터만 선별해 ES(SSD)에 적재하고, 필요 필드를 용도별 인덱스로 분리

- 관리자 경로(완전성 우선): MySQL 원본을 저빈도 조회 전용 lake로 HDD에 두고, 느리더라도 원본 전체를 조회 가능하게 유지. 파티셔닝 같은 추가 투자 대신 자원은 검색 경로(ES)에 집중

이 선별, 계층 설계의 직접 계기는 마이그레이션 중 디스크 포화 사건(약 1.8TB 한계, 소스가 약 1.278TB까지 차오름)으로, 상세를 ES에 통째로 적재하던 인덱스 11개를 삭제(약 110GB 회수)하고 선별 적재로 방향을 잡았습니다.

HDD lake는 실 테스트에서 한계가 명확했습니다. 출원번호 기준 조회가 본질적으로 랜덤 액세스라 읽기 지연이 컸고, 적재 시 출원번호 순 연속 배치로 지역성을 만드는 방향도 검토했지만 적재 파이프라인 복잡도가 커 현실적이지 않았습니다. 스토리지를 늘릴 수 없었으므로 방향은 스케일업이 아니라 데이터 쪽이었습니다. ES 검색용 인덱스와 국가별 상세 데이터를 분석해 색인되는 데이터를 최소화하고 상세 데이터를 제한해, 검색 품질은 유지하면서 용량을 최대한 줄였습니다. 그 결과 MySQL 원본과 ES 인덱스를 모두 기존 SSD 용량 안에 들여놓을 수 있었습니다.

### 11개국 단일 검색 인덱스 전환

검색 인덱스는 원래 국가별로 격리돼 있었습니다. 11개국 동시 검색 요구에 맞춰 이를 단일 검색 인덱스와 상세 인덱스 구조로 전환했고, 하나의 인덱스에서 제대로 검색되도록 국가별로 달랐던 데이터 정규화와 검색 알고리즘을 어느 정도 통일해 나갔습니다(샤드 수는 사례 6의 통제 실험으로 확정).

## 결과

상세조회 경로(미국, MySQL)는 SSD 이전 후 k6 부하테스트로 검증했습니다. 실서비스에서도 사용자마다 조회 상표가 달라 데이터 캐시 적중을 기대하기 어려운 워크로드라 무작위 출원번호로 동일 키 반복 조회(핫키 편중)를 배제한 조건을 썼고, 저부하 구간부터 단계적으로 요청률을 올리는 램프업 프로파일로 포화 지점을 탐색했습니다. 총 23,899 요청을 실패 없이 처리했고(평균 약 341 req/s), p95는 12.7ms였습니다.

11개국 데이터를 단일 검색 인덱스에서 한 번에 검색할 수 있게 됐고, 이후 국가 추가도 인덱스를 새로 만드는 대신 같은 구조에 흡수하는 방식으로 대응할 수 있습니다.

이 밖에 상표 무단선점 위험도 산출 기준(상표명 유사도와 상품류 관련성의 심각도 매트릭스, z-score 표준화, 4단계 경보)을 데이터분석 팀원과 공동 설계했습니다. 이 중 저는 데이터 분석과 기준 도출, 피드백을 담당했습니다. 무단선점 의심 발생 시 이메일 경보를 보내는 알림 서비스도 개발했습니다.

로그인 세션 상태는 인메모리 단일 인스턴스 전제라 재기동 시 재인증이 필요하고 수평 확장이 불가합니다. 서비스 부하가 크지 않다는 피드백 위에서 복잡도를 줄이려고 택한 트레이드오프이며, 저장소를 인터페이스로 분리해 다중 인스턴스가 필요해지면 구현체 교체로 전환할 경로를 남겨 뒀습니다. 로그인 세션 쪽은 액세스 토큰이 갱신 자격을 겸하는 모델이라, 토큰이 탈취되면 절대 만료까지 연장될 수 있는 여지가 있습니다. 다만 절대 만료 8시간이 그 상한이고, 단일 활성 세션이라 탈취자가 갱신하는 순간 정상 사용자의 세션이 끊겨 이상 신호가 드러나기 때문에 현 단계에서는 이 수준으로 수용했고, 이 부분은 별도 이슈로 남겨 뒀습니다.
