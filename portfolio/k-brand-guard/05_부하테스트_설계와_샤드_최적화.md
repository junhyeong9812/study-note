# 검색 서버 부하테스트 설계와 샤드 구조 최적화 (k6 기반 통제 실험)

> 소속 경력: 한국지식재산보호원 K-브랜드 지킴이 - 해외 상표 무단선점 경보 서비스 개발 (검색 서버 text-server)

## 문제 상황

발주처 요구로 기존 4개국(미국, 태국, 베트남, 인도네시아)에서 11개국으로 확장하면서 국가별 개별 인덱스가 아닌 단일 통합 인덱스로 흡수하는 설계를 택했습니다. 이때 샤드 수는 되돌리기 어려운 결정입니다. shrink는 소스 샤드 수의 약수로만, split은 배수로만 가능하고 둘 다 인덱스 쓰기를 멈추고 새 인덱스로 전환해야 해서, 제약을 못 맞추면 재색인이 됩니다. 잘못 잡으면 운영 내내 성능 상한이 고정됩니다. 앞선 프로젝트에서 세그먼트와 샤드를 사후에 조정하며 치른 비용이 있어, 이번에는 구조를 확정하기 전에 실측으로 근거를 만들기로 했습니다. 통합 인덱스를 만들기 전이었으므로, 먼저 기존 국가 인덱스 중 규모가 다른 둘(태국, 인도네시아)로 기준을 세우기로 했습니다.

## 해결 과정

```text
## 검색 한 건의 처리 - 샤드마다 스레드 하나, 병렬도는 코어 수(12)에 묶인다

                                            +- 샤드 병렬 처리 ----+                  
                   +------------------+     | shard 1 -> 스레드 1 |     +-----------+
 +-----------+     | 코디네이터       |     | shard 2 -> 스레드 2 |     | 결과 병합 |
 | 검색 요청 | --> | 샤드 수만큼 분배 | --> | shard 3 -> 스레드 3 | --> | 응답      |
 +-----------+     +------------------+     | shard 4 -> 스레드 4 |     +-----------+
                                            | (샤드당 스레드 1개) |                  
                                            +---------------------+                  

 +- 한 검색의 병렬도 = 샤드 수 --------------+  +- 포화 처리량의 상한 = 코어 --------------+  +- 그래서 --------------------------------------+
 | 샤드 1 = 코어 1개만 일함                  |  | 동시 검색이 쌓이면 총 처리량은           |  | 샤드 수 실험 범위 = 1, 2, 4, 8 (12코어 안)    |
 | 샤드 4 = 코어 4개                         |  | 데이터량이 아니라 코어 수(12)가 상한     |  | 수확 체감 지점은 서버가 정하므로              |
 | 샤드 8 = 코어 8개 (fan-out 오버헤드 증가) |  | -> 4샤드에서 CPU 포화, 8샤드는 이득 없음 |  | 규모가 다른 두 나라 결과를 통합 인덱스에 적용 |
 +-------------------------------------------+  +------------------------------------------+  +-----------------------------------------------+
```

*도식 14. 검색 한 건의 처리 - 샤드마다 스레드 하나, 포화 처리량의 상한은 데이터량이 아니라 코어 수(12)가 정한다*

"샤드를 늘리면 병렬성이 올라 빨라지지만 무한정은 아니고 어딘가에 수확 체감 구간이 있다"가 가설이었습니다. 문제는 이를 일반론이 아니라 우리 데이터와 우리 서버에서 확인해야 한다는 점이었습니다.

또 하나의 과제는 교란변수였습니다. 샤드 수를 바꾸면 세그먼트 분포도 함께 달라지기 때문에, 그대로 비교하면 성능 차이를 무엇에 귀속해야 할지 알 수 없습니다.

### 비교 인덱스 구성과 세그먼트 조건 통제

```text
## 비교 인덱스 구성 - 샤드 1/2/4/8, 두 나라 두 조건으로 세그먼트 교란 통제

 +- 태국 - 세그먼트 통일 ---------------+     +- 인도네시아 - 자연 세그먼트 ---------+
 | 샤드 1 / 2 / 4 / 8 (각각 색인)       |     | 샤드 1 / 2 / 4 / 8 (각각 색인)       |
 | 비교 직전 샤드당 세그먼트 1개로 통일 |     | 잔여물만 정리, 자연 세그먼트 유지    |
 | (총 세그먼트가 샤드 수에 종속        |     | (같은 비교를 조건을 바꿔 한 번 더)   |
 |  = 완전한 통제는 아님)               |     |                                      |
 +--------------------------------------+     +--------------------------------------+
                  |                                          |
                  +--------------------+---------------------+
                                       v
              +- 교차 확인 ----------------------------------------+
              | 두 조건에서 같은 경향(수확 체감 지점)이 재현되는가 |
              +----------------------------------------------------+
```

같은 국가 데이터를 샤드 1, 2, 4, 8로 각각 색인한 인덱스를 만들었습니다. 세그먼트 조정만으로는 한계가 있어, 먼저 샤드 수와 세그먼트의 연관을 끊어야 했습니다. 그래서 태국에서는 비교 직전 모든 인덱스를 샤드당 세그먼트 1개로 통일했습니다.

다만 이 처치는 총 세그먼트 수를 샤드 수에 종속시키므로 그 자체가 완전한 통제는 아닙니다. 그래서 같은 비교를 인도네시아에서는 자연 세그먼트 상태(분할 과정에서 생긴 잔여물만 정리)로 한 번 더 돌려, 두 조건에서 같은 경향이 나오는지 교차 확인했습니다.

### 부하 프로파일 보정

```text
## 부하 프로파일 보정 - 모드별 상한 분리, 램프업, 동시 수집

 +- 키워드 검색 ----+
 | 쿼리 비용 큼     | --+     +- 램프업 -------------------+     +- 동시 수집 -------------+
 | 상한 900 req/s   |   +---> | 저부하에서 단계적으로 증가 | --> | ES 메트릭 1초 간격      |
 +------------------+   |     | 포화 지점 탐색             |     | 응답 지표와 같은 시간축 |
 +- 이름 검색 ------+   |     +----------------------------+     +-------------------------+
 | 쿼리 비용 작음   | --+
 | 상한 3000 req/s  |
 +------------------+
  * 같은 램프를 쓰면 비용이 큰 쪽이 먼저 포화 -> 모드별로 상한을 나눈다
```

검색 모드에 따라 쿼리 비용이 크게 달라서 같은 램프를 쓰면 한쪽이 먼저 포화됩니다. 키워드 검색은 최대 900 req/s, 이름 검색은 최대 3000 req/s로 상한을 나누고, 저부하에서 단계적으로 요청률을 올리는 램프업으로 포화 지점을 탐색했습니다. 부하가 걸리는 동안 ES 메트릭을 1초 간격으로 함께 수집해, 응답 지표와 서버 상태를 같은 시간축에서 확인했습니다.

### 애플리케이션 경유가 아닌 ES 직접 측정

```text
## 측정 경로 - 애플리케이션 경유 배제, ES 직접 측정

 +----+     +- 애플리케이션 서버 -----------+     +---------------+
 | k6 | --> | 직렬화, 커넥션 풀 효과가 섞임 | --> | Elasticsearch |   x 경유 측정 배제
 +----+     +-------------------------------+     +---------------+

 +----+  직접 요청  +- Elasticsearch 직접 요청 --------------------------+
 | k6 | ----------> | 엔진 자체 처리시간(took) / 전체 응답시간 분리 기록 |
 +----+             | 비교 인덱스, 시나리오, 램프, 지표 수집 직접 설계   |
                    +----------------------------------------------------+
```

서버 코드를 경유하면 직렬화와 커넥션 풀 효과가 섞이므로, 이 실험은 ES에 직접 요청해 엔진 자체 처리시간과 전체 응답시간을 분리해 기록했습니다. 비교 인덱스 구성부터 k6 시나리오와 램프 프로파일 설계, 지표 수집까지 제가 직접 설계하고 실행했습니다.

## 결과

태국 데이터, 키워드 검색, 동일 램프(약 11만 요청) 기준입니다.

| 샤드 수 | ES 처리시간 p95 | 오류율 | 성공 처리량 |
|---|---|---|---|
| 1 | 7.29초 | 71.2% | 129 req/s |
| 2 | 2.31초 | 28.9% | 320 req/s |
| 4 | 846ms | 5.4% | 427 req/s |
| 8 | 813ms | 7.6% | 417 req/s |

이 실험은 목표 부하를 넘어 과포화 구간까지 밀어 올려 한계를 찾는 설계라 오류율이 높게 나옵니다. 그래서 지연만 비교하면 오해가 생깁니다. 1샤드는 같은 램프에서 제시 부하의 약 29%만 처리하고 포화했고 4샤드는 약 95%를 처리했으므로, 이 표가 실제로 보여주는 것은 지연 단축이 아니라 같은 부하를 견디는 처리량이 129 req/s에서 427 req/s로 약 3.3배 올라갔다는 것입니다.

4샤드에서 8샤드로는 지연과 처리량이 모두 평평했습니다. 단일 실행이라 8샤드의 오류율 상승(5.4%에서 7.6%)까지 유의미하다고 보지는 않았고, 추가 이득이 없다는 선에서 4샤드를 채택했습니다. 샤드 범위를 1, 2, 4, 8로 잡은 것은 검색 서버의 코어가 12개라 한 검색이 쓸 수 있는 병렬도가 그 안에 묶이기 때문입니다. 포화 처리량의 상한은 데이터량이 아니라 코어 수가 정하므로, 규모가 다른 두 나라에서 수확 체감 지점이 같은 곳(4샤드)에서 재현되는지를 기준으로 삼았습니다. 통합 인덱스는 이 기준으로 4샤드로 구성했고, 세그먼트는 Elasticsearch 병합 정책의 기본 상한인 5GB에서 나뉘도록 두어 병합이 한 덩어리로 쏠리지 않게 했습니다. 이후 중국을 제외한 10개국이 색인된 통합 인덱스에서 같은 비교를 해 4샤드가 최선임을 재확인했고, 중국까지 포함한 전체 인덱스의 최종 측정은 중국 색인이 끝나기 전에 퇴사해 하지 못했습니다.

자연 세그먼트 상태로 돌린 인도네시아에서도 1샤드 4.72초, 2샤드 2.14초, 4샤드 1.38초로 같은 방향이 재현됐습니다. 여기에 더해 인도네시아 2샤드 인덱스를 샤드당 1세그먼트(18GB)로 강제 병합하자 p95가 2.14초에서 3.85초로 나빠졌는데, 이는 세그먼트를 통일한 태국 표의 절대 수치가 운영 성능이 아니라 하한에 가깝다는 뜻입니다. 샤드 간 비교에는 그 조건이 필요했지만, 세그먼트가 분리된 실제 운영 구성에서는 더 빠릅니다. 정규화는 샤드가 적을수록 더 큰 단일 세그먼트를 강제해 저샤드 구성을 불리하게 만들기 때문에, 태국 표의 지연 배수는 그대로 운영 성능으로 읽지 않고 이 실험 조건 안에서의 비교로만 썼습니다.

```text
## 최종 구성 - 11개국 통합 인덱스 4샤드, 세그먼트는 5GB 상한 자연 분할

 +- 11개국 통합 인덱스 (검색 서버 12코어) --------------------------------+
 | +- 샤드 1 ---+   +- 샤드 2 ---+   +- 샤드 3 ---+   +- 샤드 4 ---+     |
 | | 세그먼트   |   | 세그먼트   |   | 세그먼트   |   | 세그먼트   |     |
 | | 여러 개    |   | 여러 개    |   | 여러 개    |   | 여러 개    |     |
 | | (5GB 상한) |   | (5GB 상한) |   | (5GB 상한) |   | (5GB 상한) |     |
 | +------------+   +------------+   +------------+   +------------+     |
 +------------------------------------------------------------------------+
  * 검색 1건 = 샤드당 스레드 1개 -> 4샤드 병렬, 코어 12개 안에서 여유
  * 강제 병합 없음 - 병합이 한 덩어리로 쏠리지 않게 5GB 기본 상한 유지
  * 근거: 두 나라 통제 실험 + 중국 제외 10개국 통합 인덱스 재확인 (4샤드 = 수확 체감 지점)
```
