# 5. 열람 토큰을 URL fragment로 옮겨 접근로그와 Referer 유출을 차단하고 저장소에는 SHA-256 해시만, 발송마다 새 토큰, 인메모리에서 DB 영속으로 전환하며 재기동 시뮬레이션까지 검증

> 이메일 OTP 인증과 토큰 상태 관리 설계 - 해결 과정 5/5. [사례로 돌아가기](../../) | [이전 4단계](../04_실버그_만료_오발화/post.md)

### 결과 열람 토큰 흐름 - fragment로 유출 경로 차단, 저장은 해시만

```text
     발급 - 경보 메일 발송 시
     +-------------------------------------------+     +-------------------------------------------+     +-------------------------------------------+
     | 난수 32바이트 생성                        |     | 메일 링크의 URL fragment에 탑재           |     | 저장소에는 SHA-256 해시만                 |
     | 30일 유효, 발송마다 새 토큰               |     | (#... 은 서버로 전송되지 않음)            |     | 유출돼도 링크로 못 씀                     |
     | (재사용 발급 폐기)                        |----->                                           |-----> 만료 행 정리 스케줄러 1시간 주기          |
     |                                           |     |                                           |     |                                           |
     +-------------------------------------------+     +-------------------------------------------+     +-------------------------------------------+

     열람 - 링크 클릭 시

     +--------------------------------+    +--------------------------------+    +--------------------------------+    +--------------------------------+
     | 사용자 링크 클릭               |    | fragment는 흔적이 없음         |    | 페이지가 fragment를 읽어       |    | 서버: 해시 대조                |
     |                                |----> 접근로그, Referer에 안 남음    |----> API 요청에 실어 전송           |----> 특정 상표 1건 결과만 열람      |
     |                                |    | (no-referrer 정책)             |    |                                |    |                                |
     +--------------------------------+    +--------------------------------+    +--------------------------------+    +--------------------------------+
```

도식 19. 결과 열람 토큰 - 발송마다 새 토큰을 fragment에 실어 유출 경로를 차단하고, 저장소에는 SHA-256 해시만

1. 경보 메일의 상세결과 링크는 로그인 없이 열려야 해서, **이메일에 결속된 열람 토큰**(암호학적 난수 32바이트, 30일 유효)을 링크에 실었습니다. 코드 리뷰를 하는 과정에서 **토큰이 URL 쿼리에 있으면 서버 접근로그와 Referer 헤더로 새어나간다**는 문제를 발견해, **토큰을 URL fragment로 옮기고 페이지 referrer 정책을 no-referrer로 지정**했습니다. fragment는 서버로 전송되지 않고, 검증은 페이지가 fragment를 읽어 API 요청에 실어 보내는 경로로만 이뤄집니다.
2. 1차는 인메모리 저장이었고, 재기동하면 이미 발송한 링크가 죽는다는 **트레이드오프를 빚으로 명시한 뒤 이어서 DB 영속으로 해소**했습니다. 토큰 저장소에는 원본이 아니라 **SHA-256 해시만 남깁니다**. 저장소가 유출돼도 그 값으로는 링크를 직접 쓸 수 없습니다.
3. 해시는 일방향이라 이메일로 활성 토큰을 찾아 재사용하는 것이 불가능합니다. 그래서 **재사용 발급을 폐기하고 발송할 때마다 새 토큰을 만드는 쪽으로 계약을 바꾸고**, 실제 동작과 어긋나게 된 메서드 이름도 정직하게 고쳤습니다. 만료된 행만 지우는 **정리 스케줄러를 1시간 주기**로 함께 넣었습니다.
4. 검증은 저장 컨텍스트를 비운 뒤 새 인스턴스가 기존 토큰을 검증하는 **재기동 시뮬레이션, 만료 토큰 거부, 원본이 저장되지 않았음을 반증하는 조회**, 정리 스케줄러가 유효한 행을 지우지 않는지까지 **실 DB 컨테이너로 확인**했습니다.
5. 발송 이력의 메일 본문에는 **링크 토큰이 평문으로 남아**, 토큰 저장을 해시로 바꾼 목적을 일부 우회합니다. 코드 리뷰 과정에서 확인한 사안이고, 발송 시점에 토큰을 주입해 본문에 남기지 않는 재설계는 추가 작업으로 이슈에 작성해 두고 현 단계에서는 수용했습니다. 수용의 근거는 피해 범위입니다. 이 토큰으로 열 수 있는 것은 **특정 상표 1건의 무단선점 비교 결과 조회에 한정**돼, 유출돼도 피해가 좁다고 판단했습니다.
