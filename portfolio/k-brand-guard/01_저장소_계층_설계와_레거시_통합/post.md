# 약 50억 행 저장소 계층 설계와 레거시 통합 (아키텍처, 인증/인가, 11개국 단일 검색 인덱스)

> 소속 경력: 한국지식재산보호원 K-브랜드 지킴이 - 해외 상표 무단선점 경보 서비스 개발
> 한국지식재산보호원 발주 "해외 상표 무단선점 시스템" (나라장터 공개 공공 발주 사업). 2026-07-27 K-브랜드 지킴이(www.ip-navi.or.kr/kbrands/guard)로 대국민 배포를 완료했습니다.

## 한 줄 요약

4개국이 11개국으로, 별도 사이트가 로그인 공유로 요구가 중간에 바뀐 상황에서, 서버 2대 분리와 레거시 공유 인증, 검색용 ES와 원본 MySQL lake 분리, 11개국 단일 통합 인덱스로 스토리지 증설 없이 수용했습니다.

## 문제 상황

백지에서 시작하는 신규 개발이 아니라, 이미 운영 중인 기존 서비스에 우리 서비스를 추가로 결합하는 형태였습니다.

처음 설계는 기존 서비스와 신규 사이트를 서로 다른 사이트로 두는 구조였습니다.\
그런데 아래와 같이 프로젝트 1개월이 지난 시점에 로그인은 양쪽이 상호 유지되었으면 한다는 요구사항이 들어왔습니다.

### 요구사항 변경 - 별도 사이트 구조에서, 1개월 뒤 인증/인가를 공유하는 구조로

도식 1. 요구사항 변경 - 별도 사이트 구조가 1개월 뒤 공통 인증/인가 레이어를 공유하는 구조로

이미 설계를 마친 인증/인가를 레거시(Java 8, Spring 2.x 기반 WAR)의 인증/인가 구조를 분석해 다시 설계해야 했습니다.\
진입 서버에서 사용자를 기존 서비스 또는 신규 사이트로 분기하되, 로그인, 인증과 일부 백오피스 기능은 양쪽이 공유하고 화면 스타일도 통일해야 하는 구조가 된 것입니다.

여기에 **4개국 검색**을 기준으로 시작했던 검색 범위가, 역시 **1개월이 지난 시점**에 "**11개국 데이터**가 있으니 전부 한 번에 검색되게 해 달라"는 요구로 아래와 같이 바뀌었습니다.

### 검색 요구 변경 - 국가별 검색뿐이던 4개국이, 11개국 통합 검색 + 국가별 검색으로

```text
     +-- 처음 요구사항 - 4개국, 국가별 검색만 --------------------+                         +-- 변경된 요구사항 - 11개국, 통합 + 국가별 ----------------+
```

도식 2. 검색 요구 변경 - 4개국 국가별 검색만 -> 11개국 통합 검색 + 국가별 검색 (데이터 확장 + 검색 방식 변경)

기존의 **4개국** 데이터만 처리하면 됐던 상황에서 **11개국**으로 확장되면서 데이터 측면의 제약은 더 컸습니다.\
원본 데이터는 JSON 파일 형태로 보존하면서, 그 JSON을 원본 형태 그대로 MySQL에 적재한 뒤 ES로 가공해야 했습니다.\
**11개국 JSON과 이미지 데이터는 약 9TB**였고, 상표 관련 전체 테이블을 합산하면 **약 50억 행**(중국을 제외한 나머지 국가 기준으로도 인덱스 포함 **약 1.35TB**)입니다.\
상표 데이터는 출원번호가 서로 랜덤한 위치에 흩어져 있어 조회가 본질적으로 랜덤 액세스인데, HDD는 순차 읽기와 지역성에 기대는 구조라 이 워크로드에서는 지연이 너무 컸습니다(랜덤 액세스 기준 SSD 대비 **약 100배 수준으로 느림**). 그런데 인프라 서버 자원은 정부 기관에서 할당받는 구조라, 더 큰 SSD나 HDD를 비용 문제로 추가 지원받기 어려웠습니다.

### 랜덤 액세스 워크로드와 저장 매체 - HDD는 탐색으로 느려지고, SSD는 위치와 무관

```text
     +-- 상표 데이터 조회 패턴 ------------------+       +-- HDD - 기계식 탐색 -------------------------+       +-- SSD - 전자적 접근 ------------------+
     |                                           |       |                                              |       |                                       |
     |   출원번호가 서로 랜덤한 위치에 흩어짐    |       |   순차 읽기, 지역성에 최적화                 |       |   위치와 무관하게 바로 읽음           |
     |   +---++---+---++---+---++---++---+---+   |       |                                              |       |                                       |
     |   +---++---+---++---+---++---++---+---+   |       |                                              |       |                                       |
     |   +---++---+---++---+---++---++---+---+   |       |       |--------------------------------      |       |       -        -        -      -      |
     |   +---++---+---++---+---++---++---+---+   |       |   +------------------------------------+     |       |   +---v--------v--------v------v--+   |
     |   +---++---+---++---+---++---++---+---+   |       |   +------------------------------------+     |       |   +-------------------------------+   |
     |   +---++---+---++---+---++---++---+---+   |       |                                              |       |                                       |
     |   +---++---+---++---+---++---++---+---+   |       |   읽을 때마다 헤드 이동 + 회전 대기          |       |   탐색 비용 없음 - 랜덤 접근에도 일정 |
     |   +---++---+---++---+---++---++---+---+   |       |   랜덤 액세스에서 지연이 큼                  |       |                                       |
     |   +---++---+---++---+---++---++---+---+   |       |                                              |       |                                       |
     |   +---++---+---++---+---++---++---+---+   |       |   랜덤 액세스 기준 SSD 대비                  |       |                                       |
     |   조회마다 서로 다른 위치 = 랜덤 액세스   |       |   약 100배 수준으로 느림                     |       |                                       |
     |                                           |       |                                              |       |                                       |
     +-------------------------------------------+       +----------------------------------------------+       +---------------------------------------+


     * 인프라 서버 자원은 정부 기관 할당 - 더 큰 SSD/HDD를 비용 문제로 추가 지원받기 어려움
     * -> 방향은 스케일업(저장 장치 증설)이 아니라 데이터 쪽: 색인 최소화와 접근 패턴별 계층 분리
```

도식 3. 랜덤 액세스 워크로드 - 흩어진 출원번호 조회, HDD의 기계식 탐색(SSD 대비 약 100배 느림)과 SSD의 위치 무관 접근

## 해결 과정

두 축을 세 번의 판단으로 풀었습니다. 경계를 먼저 긋고, 늘릴 수 없는 자원은 데이터 쪽에서 풀고, 국가가 늘어도 구조가 늘지 않게 했습니다.

**판단 1. 경계를 먼저 긋는다**\
서버, 레거시와 신규 영역, 세션의 경계를 정한 뒤에 구현했습니다.

1. [부하 성격이 다른 서비스를 물리 서버 2대로 나누고, 검색 서버에 커넥션 풀 상한과 타임아웃(bulkhead, fail-fast)을 둬 과부하가 ES로 번지지 않게 설계](해결과정/01_서버_2대_분리_배치/post.md)
2. [기존 팀의 스키마와 코드를 분석해 공유 영역은 JDBC로 맞물리고 신규 영역은 JPA로 두며, 로그인과 백오피스를 양쪽이 공유하는 JWT + DB 기반 RBAC로 인증을 재설계](해결과정/02_레거시_통합_인증_재설계/post.md)
3. [리프레시 토큰 없이 sliding 갱신, 절대 만료 8시간, 화이트리스트 단일 활성 세션으로 재시작 시 안전한 방향으로 실패하는 세션 모델 확정](해결과정/03_로그인_세션_모델/post.md)

**판단 2. 늘릴 수 없는 자원은 데이터 쪽에서 푼다**\
스토리지 증설이 불가능했으므로 저장 경로와 색인 범위를 갈랐습니다.

4. [50억 행을 SSD에 다 둘 수 없어 검색용 ES(선별 적재)와 원본 MySQL lake(완전성)로 갈라 저장, 직접 계기는 마이그레이션 중 디스크 포화 사건](해결과정/04_접근_패턴별_계층_분리/post.md)
5. [국가별 격리 인덱스를 단일 검색 인덱스 + 상세 인덱스로 전환하고 국가별로 달랐던 정규화와 검색 알고리즘을 통일](해결과정/05_11개국_단일_검색_인덱스/post.md)

선택하지 않은 방법: 스토리지 증설(정부 기관 할당 구조라 불가), HDD lake의 출원번호 순 연속 배치(적재 파이프라인 복잡도), 블랙리스트 세션(재시작 시 폐기 토큰이 부활).

## 결과

상세조회 경로(미국, MySQL)는 **SSD 이전 후 k6 부하테스트로 검증**했습니다.\
실서비스에서도 사용자마다 조회 상표가 달라 데이터 캐시 적중을 기대하기 어려운 워크로드라 **무작위 출원번호로 동일 키 반복 조회(핫키 편중)를 배제**한 조건을 썼고, 저부하 구간부터 단계적으로 요청률을 올리는 **램프업 프로파일로 포화 지점을 탐색**했습니다.\
**총 23,899 요청을 실패 없이 처리했고(평균 약 341 req/s), p95는 12.7ms**였습니다.

**11개국 데이터를 단일 검색 인덱스에서 한 번에 검색**할 수 있게 됐고, 이후 국가 추가도 인덱스를 새로 만드는 대신 **같은 구조에 흡수하는 방식으로 대응**할 수 있습니다.

이 밖에 상표 무단선점 위험도 산출 기준(**상표명 유사도와 상품류 관련성의 심각도 매트릭스, z-score 표준화, 4단계 경보**)을 데이터분석 팀원과 **공동 설계**했습니다.\
이 중 저는 데이터 분석과 기준 도출, 피드백을 담당했습니다.\
무단선점 의심 발생 시 이메일 경보를 보내는 알림 서비스도 개발했습니다.

로그인 세션 상태는 **인메모리 단일 인스턴스 전제라 재기동 시 재인증이 필요하고 수평 확장이 불가**합니다.\
서비스 부하가 크지 않다는 피드백 위에서 복잡도를 줄이려고 택한 트레이드오프이며, **저장소를 인터페이스로 분리해 다중 인스턴스가 필요해지면 구현체 교체로 전환할 경로**를 남겨 뒀습니다.\
로그인 세션 쪽은 액세스 토큰이 갱신 자격을 겸하는 모델이라, 토큰이 탈취되면 절대 만료까지 연장될 수 있는 여지가 있습니다.\
다만 **절대 만료 8시간이 그 상한**이고, **단일 활성 세션이라 탈취자가 갱신하는 순간 정상 사용자의 세션이 끊겨 이상 신호가 드러나기** 때문에 현 단계에서는 이 수준으로 수용했고, 이 부분은 별도 이슈로 남겨 뒀습니다.
