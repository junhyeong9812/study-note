### 물리 서버 2대 - 부하 성격이 다른 서비스의 분리 (Docker Compose)

```text
     +-- A 서버 - 사용자 요청 ---------------------------+                +-- B 서버 - 검색, 데이터 -----------------------------------------------------+
     |   +-------------------------------------------+   |                |   +----------------------------------+  +--------------------------------+   |
     |   | Next.js 프론트엔드                        |   |                |   | text-server (텍스트 검색)        |  | image-server (이미지 검색)     |   |
     |   +-------------------------------------------+   |       +--------|---> bulkhead: 커넥션 풀 최대 100     |  |                                |   |
     |   +---------------------v---------------------+   내부망 검색 요청 |   | fail-fast: 타임아웃 5초          |  |                                |   |
     |   | WAS (Spring Boot)                         |   |       |        |   +----------------------------------+  +--------------------------------+   |
     |   | 사용자 요청 처리                          |---|-------+        |                     |                                                        |
     |   | 레거시 연동, 인증/인가, 백오피스          |   |                |   +-----------------v----------------+  +--------------------------------+   |
     |   |                                           |   |                |   | Elasticsearch (SSD)              |  | MySQL (SSD)                    |   |
     |   +-------------------------------------------+   |                |   | 검색 인덱스만 선별 적재          |  | 원본 lake (관리자 조회)        |   |
     +---------------------------------------------------+                |   +----------------------------------+  +--------------------------------+   |
                                                                          |   +----------------------------------+  +--------------------------------+   |
                                                                          |   | 원천 데이터 (HDD)                |  | 이미지 (NAS)                   |   |
                                                                          |   | 국가별 json/xml, 이미지 zip      |  | 출원번호 해싱키 파티셔닝       |   |
                                                                          |   +----------------------------------+  +--------------------------------+   |
                                                                          |   +----------------------------------------------------------------------+   |
                                                                          |   | 데이터 ETL 전처리 API                                                |   |
                                                                          |   +----------------------------------------------------------------------+   |
                                                                          +------------------------------------------------------------------------------+
     * 과부하가 ES로 번지지 않게 차단(bulkhead, fail-fast). 애플리케이션/API/프론트/백엔드 담당 - 물리 인프라와 자원 할당은 별도 담당
```

도식 4. 물리 서버 2대 - 사용자 요청(A)과 검색, 데이터(B)의 분리, text-server의 bulkhead와 fail-fast

**물리 서버 2대**에 인스턴스를 나눠 배치했습니다.\
사용자 요청을 처리하는 **WAS(웹 애플리케이션 서버)**와 **Next.js 프론트엔드**를 한 서버에, 텍스트, 이미지 검색 인스턴스와 **데이터 ETL(추출, 변환, 적재) 전처리 API**를 다른 서버에 두어 **부하 성격이 다른 서비스를 분리**하고, 이 구성을 **Docker Compose**로 설계했습니다.\
검색 서버(text-server)는 커넥션 풀 상한(최대 동시 100)과 요청 타임아웃(5초)으로, 과부하가 Elasticsearch로 번지지 않게 막고 문제 시 빠르게 실패시키는 **방어 구조(bulkhead, fail-fast)**를 갖췄습니다.\
애플리케이션 아키텍처와 API 설계, 프론트엔드, 백엔드 개발을 담당했고, 물리 인프라와 자원 할당은 별도 담당이었습니다.

### 근거 - 방어 구조 값

- bulkhead: ES 클라이언트 튜닝 설정에서 커넥션 풀 총량과 경로당 상한 100.
- fail-fast: 커넥션 요청 타임아웃 5초.
- 검색 서킷브레이커는 두지 않았습니다. 버스트 방어의 주 도구가 아니고, ES가 단일이라 fallback이 없어 open 시 검색이 전면 중단될 위험이 있어 보류했습니다(부하테스트 기록).
