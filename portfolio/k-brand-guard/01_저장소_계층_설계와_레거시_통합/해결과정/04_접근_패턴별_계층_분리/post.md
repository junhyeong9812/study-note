# 4. 50억 행을 SSD에 다 둘 수 없어 검색용 ES(선별 적재)와 원본 MySQL lake(완전성)로 갈라 저장, 직접 계기는 마이그레이션 중 디스크 포화 사건

> 약 50억 행 저장소 계층 설계와 레거시 통합 - 해결 과정 4/5. [사례로 돌아가기](../../post.md) | [이전 3단계](../03_로그인_세션_모델/post.md) | [다음 5단계](../05_11개국_단일_검색_인덱스/post.md)

### 접근 패턴별 계층 분리 - 저장 3계층과 적재 파이프라인, 11개국 단일 통합 인덱스

```text
     B 서버 저장 계층
     +----------------------------------------------+   +------------------------------------------------+ +--------------------------------------------+
     | HDD - 원천                                   |   | SSD                                            | | NAS - 이미지 서빙                          |
     | 국가별 원본 zip                              |   | MySQL: 선별 적재한 원본 lake (관리자 - 완전성) | | 파일명 = 출원번호 -> 해싱키 파티셔닝       |
     | 상표 데이터: json 또는 xml                   |   | ES: 검색 인덱스만 (사용자 - 속도)              | | 국가 규모 따라 3자리 / 4자리 키            |
     | 이미지: jpeg, png                            |   |                                                | | 정적 파일 탐색 고속화                      |
     |                                              |   |                                                | |                                            |
     +----------------------------------------------+   +------------------------------------------------+ +--------------------------------------------+


     적재 파이프라인
     +----------------------------------+   +----------------------------------+   +----------------------------------+  +----------------------------------+
     | zip 배치 해제                    |   | MySQL 적재                       |   | 검색 필요 필드만 ES 색인         |  | 11개국 단일 통합 인덱스          |
     | json/xml 메모리 로드             |   | (원본 lake)                      |   | 상표명 변환 필드 생성            |  | 국가별 정규화 어댑터로 흡수      |
     |                                  |--->                                  |---> 원본 / 영어 / 한국어 발음 3계열 -|--> (국가 추가 = 어댑터 추가)        |
     |                                  |   |                                  |   | 변환 저장 -> 검색 시 O(1) 탐색   |  |                                  |
     +----------------------------------+   +----------------------------------+   +----------------------------------+  +----------------------------------+


     * 상세 조회: ES가 돌려준 출원번호로 MySQL join (상세까지 ES에 정제해 두기에는 용량 부족 - 의도적 분리)
```

도식 7. 저장 3계층(HDD 원천, SSD의 MySQL lake와 ES, NAS 이미지 해싱 파티셔닝)과 적재 파이프라인, 11개국 단일 통합 인덱스

**50억 행을 전부 SSD에 둘 수 없다는 제약** 아래, **같은 데이터를 두 경로에 나눠 각각 저장**하는 설계로 타협했습니다.

- **사용자 경로(속도 우선)**: **검색에 실제 필요한 데이터만 선별해 ES(SSD)에 적재**하고, 필요 필드를 용도별 인덱스로 분리
- **관리자 경로(완전성 우선)**: MySQL 원본을 저빈도 조회 전용 lake로 HDD에 두고, 느리더라도 **원본 전체를 조회 가능하게 유지**. 파티셔닝 같은 추가 투자 대신 **자원은 검색 경로(ES)에 집중**

이 선별, 계층 설계의 직접 계기는 마이그레이션 중 **디스크 포화 사건(약 1.8TB 한계, 소스가 약 1.278TB까지 차오름)**으로, 상세를 ES에 통째로 적재하던 **인덱스 11개를 삭제(약 110GB 회수)**하고 **선별 적재**로 방향을 잡았습니다.

HDD lake는 실 테스트에서 한계가 명확했습니다.\
출원번호 기준 조회가 본질적으로 **랜덤 액세스라 읽기 지연**이 컸고, 적재 시 출원번호 순 연속 배치로 지역성을 만드는 방향도 검토했지만 적재 파이프라인 복잡도가 커 현실적이지 않았습니다.\
스토리지를 늘릴 수 없었으므로 **방향은 스케일업이 아니라 데이터 쪽**이었습니다.\
ES 검색용 인덱스와 국가별 상세 데이터를 분석해 **색인되는 데이터를 최소화**하고 상세 데이터를 제한해, **검색 품질은 유지하면서 용량을 최대한** 줄였습니다.\
그 결과 **MySQL 원본과 ES 인덱스를 모두 기존 SSD 용량 안에** 들여놓을 수 있었습니다.
