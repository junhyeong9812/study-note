# text-server 리팩토링 (LLM 프로토타입의 유지보수성 개선)

> 소속 경력: 한국지식재산보호원 K-브랜드 지킴이 - 해외 상표 무단선점 경보 서비스 개발 (검색 서버 text-server)
> 회사 내부 식별자(클래스명, 파일 경로, 커밋 해시)는 노출하지 않고 맥락만 서술합니다.

## 핵심 요약

- 동작 검증과 부하테스트를 통과했지만 유지보수가 어려웠던 LLM 프로토타입 코드베이스를 동작 보존을 전제로 구조 개선 - 죽은 코드 제거, 폴더 구조와 이름 통일, 관심사 단위 메서드 분리, 공통 유틸 승격, 조건분기를 이름 있는 타입으로 정리하는 순서로 수행
- 매 구조 변경마다 전체 테스트 0실패 유지, 테스트 수 577개 -> 668개. 문서화되지 않은 채 암묵적으로 쓰이던 필드 규칙을 타입과 테스트로 고정하는 과정에서 규칙을 벗어난 필드 21건을 찾아냄(19건은 숨어 있던 결함으로 판정. 동작 보존 원칙에 따라 수정은 별도 동작 변경 작업으로 분리했고, 이후 전건 수정 완료)
- 요구사항 변경 대응 시간이 기존 1~2시간에서 약 30분 수준으로 단축

## 문제 상황

제가 도메인 요구사항을 정리해 Claude Code로 빠르게 만든 프로토타입으로, 동작 검증과 부하테스트까지 통과한 코드베이스였습니다. 기능은 입증됐지만 문제는 유지보수였습니다. 인수인계 시 이해에 오래 걸렸고, 구현 당시 맥락을 아는 제가 다시 봐도 어려운 코드였습니다.

가드레일 테스트는 존재했지만, 메서드와 클래스 구조가 깊고 흐름과 알고리즘이 혼재해 있었으며, 여러 번의 요구사항 변경을 거치며 네이밍도 일관성을 잃었습니다. 코드가 여기저기 흩어져 있어 응집도가 떨어졌고, 캡슐화와 추상화가 부족해 읽는 사람이 길을 잃기 쉬운 구조였습니다.

## 해결 과정

과제를 이렇게 정의했습니다. 죽은 코드를 덜어내고, 폴더 구조와 클래스 위치부터 바로잡아 응집도를 높인 뒤, 검증/정규화/중복검사/저장과 도메인 알고리즘을 각각 이름 붙인 메서드로 분리해 캡슐화하고, 공통 유틸과 정책을 추상화합니다. 단, 이미 검증을 통과한 코드베이스이므로 모든 작업의 전제는 동작 보존입니다 - 매 단계에서 테스트로 동작이 변하지 않았음을 확인하며 구조만 바꿉니다.

```text
## 리팩토링 워크플로우 - 가드레일을 먼저 세우고, 매 단계 전체 테스트 0실패를 확인하며 구조만 바꾼다

 +- 0. 가드레일 ---------------------+                                                   +- 2. 재배치 (응집도) ------------------+
 | 현재 입출력을 실 데이터로 실측    |     +- 1. 죽은 코드 제거 -------------------+     | 폴더 구조, 클래스 위치, 이름을        |
 | characterization 테스트로 고정    | --> | 참조 없는 구세대 클래스 8개(약 750줄) | --> | 사내 표준으로 통일                    |
 | 버그 의심 출력도 일단 그대로 고정 |     | 호출부 없는 레거시 메서드 삭제        |     | 국가별 라우팅 복제 -> 제네릭 디스패치 |
 | 바이트 보존 경로는 골든 픽스처    |     +---------------------------------------+     +---------------------------------------+
 +-----------------------------------+                                                                                            
                                                                                                         |
                                                                                                         v
 +- 3. 모듈화 (캡슐화) ----------------+     +- 4. 정책 추상화 (타입화) ---------------+     +- 5. 모듈 단위 테스트 추가 ------+
 | 검증 / 정규화 / 중복검사 / 저장을   |     | 트랜잭션 골격 -> 함수형 인자 메서드 1개 |     | 모듈별 비즈니스 규칙을          |
 | 관심사 단위 이름 있는 메서드로 분리 | --> | 분기 -> 결과 enum, 복구 판정 enum       | --> | 실 데이터 기반 테스트로 추가    |
 | 공통 유틸 승격 (통합은 개별 검토)   |     | 국가 리터럴 -> 국가 enum                |     | 577 -> 668개                    |
 | 컨벤션 규칙 13개로 축적             |     | (적용 범위는 정책 판정 지점까지)        |     | 암묵적 필드 규칙 위반 21건 발견 |
 +-------------------------------------+     +-----------------------------------------+     +---------------------------------+

   각 단계 끝 = 전체 테스트 실행 -> 0실패 확인 -> 다음 단계.  실패하면 구조 변경을 되돌린다 (현재 동작이 곧 스펙, 수정은 별도 작업)
```

*도식 13. 리팩토링 워크플로우 - 가드레일(0) -> 죽은 코드 제거(1) -> 재배치(2) -> 모듈화(3) -> 정책 추상화(4) -> 모듈 단위 테스트 추가(5), 매 단계 전체 테스트 0실패*

### 0. 가드레일 - 현재 동작을 실 데이터로 고정

구조를 바꾸기 전에 현재 입출력을 실측해 기존 동작을 그대로 보존하는 테스트(characterization)로 고정했고, 버그로 의심되는 출력도 일단 그대로 고정했습니다(리팩토링 단계에서는 현재 동작이 곧 스펙, 수정은 별도 동작 변경 작업으로 분리).

바이트 수준 보존이 필요한 데이터 파이프라인 전환은 전환 후 사라질 구코드로 기준 출력(골든 픽스처)을 먼저 만들어 새 경로의 출력과 같은지 비교했고, 매 구조 변경마다 전체 테스트를 돌려 0실패를 유지했습니다.

### 1. 죽은 코드 제거

각 영역 착수 시 죽은 코드를 먼저 덜어냈습니다. 아무도 참조하지 않는 구세대 아키텍처 잔재 클래스 8개(약 750줄)와 호출부 없는 레거시 메서드를 삭제한 뒤에야 재배치를 진행했습니다.

### 2. 재배치 - 폴더 구조, 클래스 위치, 이름 통일로 응집도 확보

헥사고날 표기와 사내 표준 레이어 구조가 섞여 있던 폴더 구조, 클래스 위치, 이름을 사내 표준으로 통일했고, 조회 메서드마다 통째로 복제돼 있던 국가별 라우팅은 제네릭 디스패치 메서드 하나로 모았습니다.

### 3. 모듈화 - 관심사 단위 메서드 분리와 공통 유틸 승격

검증, 정규화, 중복검사, 저장처럼 한 메서드에 섞여 있던 절차를 의도가 드러나는 이름의 메서드로 분리해 진입점이 도메인 문장처럼 읽히게 했습니다. 분리 기준은 "if문 단위가 아니라 관심사 단위"로 확정하고, 세션에서 확정된 판단들을 리팩토링 컨벤션 규칙 13개로 축적해 다음 세션이 같은 기준으로 이어가게 했습니다.

여러 클래스가 공유하는 순수 유틸(음절 처리, 인코딩 스켈레톤)은 공용 패키지로 승격하되 통합 여부를 개별 검토했습니다. 예를 들어 정규화 로직 세 벌은 모양만 같고 공백 처리의 의미가 서로 달라, 통합하면 API 응답이 바뀌므로 의도적으로 그대로 두었습니다.

### 4. 정책 추상화 - 조건분기를 이름 있는 타입으로

상태 전이 메서드 9개가 반복하던 트랜잭션 골격을 함수형 인자를 받는 메서드 하나로 통합하고, 백그라운드 루프의 다중 catch에 흩어져 있던 분기는 결과 enum으로, 다섯 갈래 복구 판정은 분류 enum으로 올렸습니다.

다섯 개 파일에 흩어져 있던 국가별 분기 리터럴과 정책은 국가 enum 하나로 모으되, enum의 적용 범위를 정책 판정 지점까지로 제한하고 저장 계층은 문자열을 유지해 마이그레이션 없이는 되돌릴 수 없는 변경을 만들지 않았습니다.

### 5. 모듈 단위 테스트 추가 - 데이터 기반

모듈이 나뉜 뒤에는 각 모듈의 비즈니스 규칙을 실제 데이터 기반으로 테스트에 추가해 테스트 수를 577개에서 668개로 늘렸습니다. 이 과정에서 문서화되지 않은 채 암묵적으로 쓰이던 필드 규칙을 타입과 테스트로 고정하며 규칙을 벗어난 필드 21건을 찾아냈고, 그중 19건은 숨어 있던 결함으로 판정했습니다. 동작 보존 원칙에 따라 수정은 별도 동작 변경 작업으로 분리했습니다.

## 결과

분리해 둔 결함 19건은 후속 동작 변경 작업에서 모두 수정했습니다. 리팩토링 이후 코드 리뷰와 인수인계, 신입 온보딩에서 이전보다 빨리 적응할 수 있게 됐고, 기존 1~2시간 걸리던 요구사항 변경 대응을 약 30분 안에 처리할 수 있게 되었습니다. 이 과정 전체에서 동작 보존을 지켰습니다.
