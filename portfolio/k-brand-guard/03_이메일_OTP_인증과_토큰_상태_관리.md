# 이메일 OTP 인증과 토큰 상태 관리 설계 (로그인 없는 대국민 서비스)

> 소속 경력: 한국지식재산보호원 K-브랜드 지킴이 - 해외 상표 무단선점 경보 서비스 개발
> 회사 내부 식별자(클래스명, 파일 경로, 커밋 해시)는 노출하지 않고 맥락만 서술합니다.

## 핵심 요약

- 회원가입, 로그인 없이 이메일 소유 확인만으로 경보 구독과 결과 열람이 되도록 인증 경계를 설계. 요구가 두 번 뒤집히는(인증 도입, 인증 제거, 인증 재도입) 변경을 거치며 최종안으로 수렴
- OTP: 예측 불가 6자리, 3분 유효, 시도 5회 상한에 더해 검증을 키 단위 원자 구간으로 묶어 병렬 시도의 상한 우회와 정답 동시 요청의 이중 발급을 차단. 상수시간 비교, 발송 성공 후 코드 활성화(리뷰 지적 채택), 이메일별 재발송 제한(60초 1회, 시간당 5회)
- 결과 열람 토큰: 메일 링크의 토큰을 URL 쿼리에서 fragment로 옮겨 서버 접근로그와 Referer 유출 경로를 제거하고, 토큰 저장소에는 SHA-256 해시만 저장(발송 이력 본문의 평문 잔존은 위험도를 평가해 수용, 빚으로 기록). 2026-07-27 대국민 배포 완료

## 문제 상황

대국민 공개 서비스라 경보 구독과 결과 열람에 회원가입을 요구할 수 없었습니다. 기존 알림 화면은 마이페이지처럼 로그인을 전제로 만들어져 있었고, 요구는 "로그인 없이 이메일만으로 신청하고 조회한다"였습니다. 인증과 인가는 제가 담당한 영역이라 이 전환의 설계와 구현을 맡았습니다.

요구는 하루 사이 두 번 뒤집혔습니다. 이메일 인증(OTP)으로 구현한 뒤 "인증 없이 이메일만 입력"으로 내려갔고, 다시 "이메일 인증 방식으로" 돌아왔습니다. 두 번째 단계에서 지웠던 인증 도메인은 형상관리 이력에서 리뷰 완료본을 되살려 복원했고, 그 사이 새로 생긴 발송내역, 해지 엔드포인트까지 같은 토큰 인증으로 통일해 최종 상태를 하나로 맞췄습니다.

## 해결 과정

비회원 이메일 인증은 "그 메일함을 열 수 있는 사람이 본인"이라는 얇은 근거 하나에 기대는 구조입니다. 그래서 보안 경계를 세 갈래로 나눠 정의했습니다. 코드 무차별 대입, 동시 요청으로 생기는 상태 경합, 그리고 발급된 토큰의 유출 경로입니다.

제3자 이메일로 인증을 완료하는 위협은 제외했습니다. 코드는 그 주소의 소유자만 받기 때문입니다. 남의 주소로 반복 발송을 유발하는 소모성 위협은 이메일별 재발송 제한이 맡고, 인증한 이메일과 알림을 받을 이메일을 하나로 고정해 남의 주소로 알림이 발송되는 경로 자체를 없앴습니다.

제약이 하나 더 있었습니다. 별도 저장소를 새로 도입해 운영 복잡도를 늘리지 않는 선에서 해결해야 했습니다.

### OTP 발급과 검증 - 원자 구간, 그리고 발송 순서

```text
## OTP 발급과 검증 워크플로우 - 발송 성공 후 활성화, 검증은 키 단위 원자 구간

 [발급]
                                     +------------------------+                                                           +----------------------+
 +-----------------------------+     | 재발송 제한 검사       |     +-----------------------------+     +-----------+     | 성공: 코드 활성화    |
 | 이메일 입력                 | --> | 이메일별 슬라이딩 윈도 | --> | 암호학적 난수 6자리 생성    | --> | 메일 발송 | --> | 3분 유효, 시도 5회   |
 | (인증 이메일 = 알림 이메일) |     | 60초 1회, 시간당 5회   |     | (순번형 채번 서비스 미사용) |     +-----------+     | 실패: 이전 코드 유지 |
 +-----------------------------+     +------------------------+     +-----------------------------+                       | (3중 잠김 방지)      |
                                                                                                                          +----------------------+

 [검증]
                   +- 키 단위 원자 구간 ----------------+                                            
                   | 1 만료 검사                        |     +-------------------------------------+
 +-----------+     | 2 상수시간 코드 비교               |     | 성공: 인증 토큰 발급                |
 | 코드 입력 | --> | 3 시도 횟수 +1                     | --> | 등록 겸 조회 토큰 > 조회 전용 토큰  |
 +-----------+     | 4 정답이면 소비(1회용)             |     | (엔드포인트마다 요구 용도 명시)     |
                   | -> 병렬 시도의 상한 우회 차단      |     | 실패: 5회 초과 시 잠금, 3분 후 만료 |
                   | -> 정답 동시 요청의 이중 발급 차단 |     +-------------------------------------+
                   +------------------------------------+                                            

   보안 경계 세 갈래: 코드 무차별 대입(5회, 3분, 상수시간)  /  동시 요청의 상태 경합(원자 구간)  /  발급 토큰의 유출 경로(별도 절)
```

*도식 11. OTP 발급과 검증 - 발송 성공 뒤 코드 활성화, 검증 4단계를 키 단위 원자 구간으로 묶어 병렬 시도와 이중 발급 차단*

- 코드는 암호학적 난수 6자리로 발급했습니다. 사내 표준 채번 서비스는 순번 성격이라 예측 불가 요건을 충족하지 못해 쓰지 않았습니다. 유효시간 3분, 시도 5회 상한입니다.

- 만료 검사, 코드 비교, 시도 횟수 증가, 소비를 키 단위 단일 원자 구간으로 묶었습니다. 이렇게 하지 않으면 병렬 검증 요청이 시도 상한을 우회하거나, 정답이 동시에 두 번 들어와 토큰이 두 개 발급됩니다. 코드 비교는 상수시간 비교로 타이밍 차이를 줄였습니다.

- 코드를 리뷰하는 과정에서 발급 순서의 문제를 발견해 순서를 바꿨습니다. 코드를 먼저 저장하고 메일을 보내면, 발송이 실패한 순간 사용자는 새 코드도 못 받고 직전 코드는 무효가 되고 재발송 쿨다운에까지 걸려 3중으로 잠깁니다. 발송이 성공한 뒤에 코드를 활성화하도록 순서를 뒤집어, 실패 시 이전 메일의 코드가 계속 유효하게 했습니다.

- 인증 토큰은 용도를 둘로 나눠 등록 겸 조회 토큰이 조회 전용 토큰의 권한을 포함하게 계층화하고, 엔드포인트마다 요구 용도를 명시했습니다. 재발송은 이메일별 슬라이딩 윈도로 60초 1회, 시간당 5회로 제한했습니다.

### 재전송 제한 관련 프론트, 백엔드 설계 문제

기능 테스트 중 "요청이 많습니다"가 반복되던 문제가 있었습니다. 로그를 실측하니 거절된 요청은 전부 발송 성공 후 23초에서 54초 사이의 재클릭이었고(쿨다운 60초 이내), 밀리초 간격의 중복 발사는 없었습니다. 프론트의 중복 요청이 아니라, 사용자가 쿨다운이 걸려 있다는 사실을 알 수 없는 상태에서 재전송 버튼이 그대로 눌리는 프론트와 백엔드 설계의 문제였습니다. 제한 자체는 이메일별이라 대국민 트래픽 총량과 무관하고, "1초에 1건"으로 풀면 한 주소에 시간당 3,600통을 허용하게 되므로 제한은 유지했습니다. 대신 재전송 버튼에 남은 초 카운트다운과 도착 소요 안내를 붙여 설계를 고쳤습니다.

### 결과 열람 토큰 - 유출 경로와 저장 형태

```text
## 결과 열람 토큰 흐름 - fragment로 유출 경로 차단, 저장은 해시만

 [발급 - 경보 메일 발송 시]
 +-----------------------------+     +---------------------------------+     +----------------------------------+
 | 암호학적 난수 32바이트      |     | 메일 링크의 URL fragment에 탑재 |     | 저장소에는 SHA-256 해시만        |
 | 30일 유효, 발송마다 새 토큰 | --> | (#... 는 서버로 전송되지 않음)  | --> | 유출돼도 링크로 못 씀            |
 | (재사용 발급 폐기)          |     +---------------------------------+     | 만료 행 정리 스케줄러 1시간 주기 |
 +-----------------------------+                                             +----------------------------------+

 [열람 - 링크 클릭 시]
 +------------------+     +--------------------------------+     +--------------------------+     +---------------------------+
 | 사용자 링크 클릭 | --> | fragment는 접근로그, Referer에 | --> | 페이지가 fragment를 읽어 | --> | 서버: 해시 대조 후        |
 +------------------+     | 남지 않음 (no-referrer 정책)   |     | API 요청에 실어 전송     |     | 특정 상표 1건 결과만 열람 |
                          +--------------------------------+     +--------------------------+     +---------------------------+
```

*도식 12. 결과 열람 토큰 - 발송마다 새 토큰을 fragment에 실어 유출 경로를 차단하고, 저장소에는 SHA-256 해시만*

- 경보 메일의 상세결과 링크는 로그인 없이 열려야 해서, 이메일에 결속된 열람 토큰(암호학적 난수 32바이트, 30일 유효)을 링크에 실었습니다. 코드 리뷰를 하는 과정에서 토큰이 URL 쿼리에 있으면 서버 접근로그와 Referer 헤더로 새어나간다는 문제를 발견해, 토큰을 URL fragment로 옮기고 페이지 referrer 정책을 no-referrer로 지정했습니다. fragment는 서버로 전송되지 않고, 검증은 페이지가 fragment를 읽어 API 요청에 실어 보내는 경로로만 이뤄집니다.

- 1차는 인메모리 저장이었고, 재기동하면 이미 발송한 링크가 죽는다는 트레이드오프를 빚으로 명시한 뒤 이어서 DB 영속으로 해소했습니다. 토큰 저장소에는 원본이 아니라 SHA-256 해시만 남깁니다. 저장소가 유출돼도 그 값으로는 링크를 직접 쓸 수 없습니다.

- 해시는 일방향이라 이메일로 활성 토큰을 찾아 재사용하는 것이 불가능합니다. 그래서 재사용 발급을 폐기하고 발송할 때마다 새 토큰을 만드는 쪽으로 계약을 바꾸고, 실제 동작과 어긋나게 된 메서드 이름도 정직하게 고쳤습니다. 만료된 행만 지우는 정리 스케줄러를 1시간 주기로 함께 넣었습니다.

- 검증은 저장 컨텍스트를 비운 뒤 새 인스턴스가 기존 토큰을 검증하는 재기동 시뮬레이션, 만료 토큰 거부, 원본이 저장되지 않았음을 반증하는 조회, 정리 스케줄러가 유효한 행을 지우지 않는지까지 실 DB 컨테이너로 확인했습니다.

- 발송 이력의 메일 본문에는 링크 토큰이 평문으로 남아, 토큰 저장을 해시로 바꾼 목적을 일부 우회합니다. 코드 리뷰 과정에서 확인한 사안이고, 발송 시점에 토큰을 주입해 본문에 남기지 않는 재설계는 추가 작업으로 이슈에 작성해 두고 현 단계에서는 수용했습니다. 수용의 근거는 피해 범위입니다. 이 토큰으로 열 수 있는 것은 특정 상표 1건의 무단선점 비교 결과 조회에 한정돼, 유출돼도 피해가 좁다고 판단했습니다.

### 실버그 진단 - 인증 직후 "만료" 오발화

기능 테스트 중 인증에 성공한 직후 "인증 시간이 만료되었습니다"가 뜨고 첫 화면으로 되돌아가는 문제를 발견했습니다. 서버 로그를 실측하니 토큰과 OTP 오류가 0건이고 검증, 조회 응답이 전부 정상이어서 원인을 서버가 아니라 프론트로 귀속했습니다. 원인은 카운트다운 훅의 렌더 타이밍이었습니다. 남은시간이 미확정에서 확정값으로 바뀌는 렌더에 남은시간 0인 낡은 프레임이 한 번 끼어 만료 감시가 오발화한 것입니다. 남은시간을 상태로 들지 않고 매 렌더마다 만료 시각에서 도출하도록 바꿔 그 틈을 없앴고, 검토했던 다른 가설(토큰 보관 키 문제)은 검증 결과 부작용만 확인돼 기각했습니다. 회귀 테스트는 구버전에 먼저 걸어 2건이 실제로 실패하는 것을 확인한 뒤 신버전에서 전부 통과시켜, 테스트가 실패 모드를 실제로 재현하는지 확인했습니다.

## 결과

2026-07-27 대국민 서비스로 배포를 완료했습니다.

검증은 인증과 구독 영역 108개 테스트(구독 영역은 실 DB 컨테이너, 인증 저장소는 단위 테스트)를 통과시키고, OTP 발송 수락, 오답 거절, 재발송 제한, 무토큰 거절이 계약대로 응답하는지 E2E 스모크로 확인했습니다. 결과 열람 토큰은 만료, 위조, 권한 격리를 다룬 보안 테스트 30건과, 영속화 이후 재기동 시뮬레이션 및 정리 스케줄러 통합 테스트를 통과했습니다.

한계와 트레이드오프는 분명합니다. OTP 코드와 이메일 인증 토큰 상태가 인메모리 단일 인스턴스 전제입니다. 재기동하면 재인증이 필요하고 수평 확장도 불가합니다. 서비스 자체 부하가 크지 않다는 피드백 위에서 복잡도를 줄이려고 의도적으로 택한 트레이드오프이며, 저장소를 인터페이스로 분리해 다중 인스턴스가 필요해지면 구현체 교체로 전환할 경로를 남겨 뒀습니다. 그중 유출 시 피해가 가장 큰 결과 열람 토큰만 먼저 DB로 옮겼습니다.
