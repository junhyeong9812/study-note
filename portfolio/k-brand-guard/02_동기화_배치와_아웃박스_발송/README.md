# 레거시 동기화와 경보 메일 발송 파이프라인 (일일 배치, 트랜잭셔널 아웃박스)

> 소속 경력: 한국지식재산보호원 K-브랜드 지킴이 - 해외 상표 무단선점 경보 서비스 개발
> 회사 내부 식별자(클래스명, 파일 경로, 커밋 해시)는 노출하지 않고 맥락만 서술합니다.
> 역할 구분: 알림 서비스의 초기 구조와 계약을 제가 명세로 설계해 기본 도메인 구현을 팀원에게 위임했고, 이후 작업 - 아웃박스 분리 구조, 동기화 배치 설계와 구현, 고도화(상태 전이 버그 수정, 발송 채널 전환, 전량 미러 개선) - 는 제가 담당했습니다.

## 한 줄 요약

push 연동이 없는 타사 레거시와 로그만 남기던 발송을, 매일 멱등 전량 대조 동기화와 트랜잭셔널 아웃박스로 바꿔 최신본 73,747건 대조 차이 0건으로 2026-07-27 대국민 배포했습니다.

## 문제 상황

레거시에 있는 무단선점 의심 사례를 받아 구독자에게 이메일 경보를 보내야 했습니다.\
레거시는 변경을 알려주는 **push 연동이 없었고**, 타사에 연동 기능을 새로 만들게 하기엔 일정과 협의 비용이 컸습니다.\
발송 쪽은 메일을 보내지 않고 정상 종료되는 구현과, 일부 실패를 남길 수 없는 결과 표현이 문제였습니다.

1. [원천 레거시가 변경을 알려주는 push 연동을 제공하지 않음](문제상황/01_push_연동이_없는_레거시/post.md)
2. [유일한 발송 구현이 로그만 남기고 정상 종료되고, 결과가 전체 성공 또는 전체 실패로만 표현됨](문제상황/02_발송_구현의_결함/post.md)

## 해결 과정

세 번의 판단으로 진행했습니다. 판단과 전송을 분리하고, 실패는 멱등과 격리로 갚고, 불변식을 고정한 채 실측으로 고쳤습니다.

**판단 1. 판단과 전송을 분리한다**\
한 트랜잭션에 두면 전송 지연이 DB 지연이 되고 전송 실패를 롤백으로 갚게 됩니다.

1. [문제를 세 가지(레거시 무요구 최신화, 발송 실패가 동기화를 막지 않음, 실패 건만 재시도)로 정의하고, 판단과 전송을 한 트랜잭션에 두면 둘째와 셋째를 동시에 만족할 수 없어 분리를 설계 축으로 확정](해결과정/01_문제_정의_분리_축/post.md)
2. [구독 두 테이블 정규화와 동기화 직후 발송 구조를 명세로 먼저 고정해 팀원에게 위임하고, 아웃박스와 발송 배치 분리는 직접 발전시켜 Claude와 Codex 리뷰로 점검](해결과정/02_명세_고정_위임/post.md)

**판단 2. 실패는 멱등과 격리로 갚는다**\
재호출이 곧 재처리가 되게 하고, 한 건의 실패가 다른 건을 막지 않게 했습니다.

3. [매일 새벽 pull, 타임존 명시, 출원인 마스터 먼저 적재하는 순서, 레거시 식별자 기준 멱등 전량 대조, 실패는 시각 앵커 재시도 2회 후 다음날 멱등 커버](해결과정/03_동기화_배치/post.md)
4. [발송 의도를 사례와 같은 트랜잭션에 원자 커밋하고 1시간 뒤 별도 배치가 행별 독립 발송, 상태로 필터한 첫 페이지 반복 조회로 건너뜀 없음](해결과정/04_아웃박스/post.md)

**판단 3. 불변식을 고정하고 실측으로 고친다**\
아웃박스와 상태머신은 바꾸지 않는다는 조건 아래 버그와 채널 교체, 미전파를 처리했습니다.

5. [전이 조건 반전 버그와 재시도 성공 경로 누락을 고쳐 테스트로 고정하고, 발송 채널 교체는 어댑터만 갈아끼우며 무음 성공 차단과 런타임 예외의 실패 계약 변환 2건을 흡수](해결과정/05_고도화_전이_버그_채널_교체/post.md)
6. [insert-only 동기화가 최신본을 반영하지 못함을 실측(신규 305건 삽입 0, 활성 전환 235건 미전파)하고 보존형 전량 미러로 전환, 통지 기준은 활성 전환 시점](해결과정/06_전량_미러_전환/post.md)

선택하지 않은 방법: 레거시에 push 연동 요구(일정과 협의 비용), 발송을 동기화 트랜잭션 안에서 수행, 외부 큐나 잠금 저장소 도입(부하 대비 복잡도).

## 결과

파이프라인은 **새벽 동기화, 한 시간 뒤 대기 건 발송, 30분 주기 실패 재시도의 3단**으로 자리잡았고, 실발송 경로는 두 갈래로 검증했습니다.\
메일 API를 직접 호출해 접수 식별자를 받는 경로와, 대기 건을 스케줄러가 집어 발송한 뒤 상태가 발송 완료로 전이되고 발송 시각이 기록되는 경로를 각각 **실제 수신까지 확인**했습니다.

최신본 반영은 레코드 단위로 검증했습니다.\
보정 후 **총 73,747건(기존 보유분에 신규 305건 추가)**이고, 원천에 현존하는 행 기준 **8개 필드 전량 대조에서 차이는 0건**이었습니다(원천에서 사라진 행은 이력 보존 원칙대로 남긴 채). **활성 전환 235건이 반영**됐고, 구독 중인 출원번호와 교집합이 없음을 사전 확인한 대로 의도치 않은 대기 메일이 생기지 않았음을 **대기 건 증가 0으로 확인**했습니다.\
이 서비스는 **2026-07-27 대국민 서비스로 배포를 완료**했습니다.

### 한계와 트레이드오프

재처리 큐는 **인메모리이고 단일 인스턴스를 전제**합니다.\
재기동하면 큐가 사라집니다.\
이 유실을 수용한 근거는 세 가지입니다.\
동기화가 멱등이라 다음날 정기 실행이 미적재분을 다시 채운다는 것, 서비스 자체의 부하가 크지 않다는 피드백 위에서 외부 큐나 잠금 저장소를 들이는 복잡도를 줄이는 편이 낫다고 판단한 것, 그리고 일정 여유가 크지 않은 상황에서 실패가 예측 가능한 범위의 문제였다는 것입니다.\
**복잡도를 높이기보다 예외를 빠르게 파악할 수 있는 단순한 구조로 낮추는 선택**을 했습니다.\
발송 역시 메일 API 접수 후 완료 상태를 커밋하기 전에 프로세스가 중단되면 같은 메일이 한 번 더 나갈 수 있는 **at-least-once 구조**라는 한계가 있습니다.\
정확히 한 번에 가깝게 만들려면 발송 건별 멱등 키를 메일 제공자와 공유해 중복 접수를 차단하거나, 접수 결과를 사후 대조하는 복구 절차가 더 필요합니다.\
이 항목들과, 다중 인스턴스 전환 시 필수가 되는 재시도 실패 기록 시점의 상태 검증, 전이 검증 예외와 전송 실패 예외를 분리해 잡는 처리는 이슈로 만들어 구현을 위임해 두었습니다.

## 회고

상태 전이, 배치 처리, 메일 발송처럼 구간마다 예외가 생길 수 있는 지점을 미리 잡아 두고, 각 가능성을 조금 더 자세히 들여다볼 필요가 있다는 것을 느꼈습니다.\
그리고 이런 설계는 한 번에 다 만들기보다 **기본 파이프라인을 먼저 설계하고 가드레일을 잡아 둔 상태에서 점진적으로 확장**해 나가는 편이 더 좋은 방향이라는 것을 배웠습니다.
