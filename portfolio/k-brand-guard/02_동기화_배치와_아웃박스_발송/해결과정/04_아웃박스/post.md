# 4. 발송 의도를 사례와 같은 트랜잭션에 원자 커밋하고 1시간 뒤 별도 배치가 행별 독립 발송, 상태로 필터한 첫 페이지 반복 조회로 건너뜀 없음

> 레거시 동기화와 경보 메일 발송 파이프라인 - 해결 과정 4/6. [사례로 돌아가기](../../) | [이전 3단계](../03_동기화_배치/post.md) | [다음 5단계](../05_고도화_전이_버그_채널_교체/post.md)

### 아웃박스 - 발송 의도를 데이터와 함께 원자 커밋, 행별 독립 발송

```text
     +--------------------------------------------------+        +----------------------------------------+         +-----------------------------------+
     | 동기화 트랜잭션 (원자 커밋)                      |        | 발송 배치 (1시간 뒤)                   |         | 행 1건씩 별도 트랜잭션            |
     | 1 사례 적재                                      |커밋 후 | 상태 필터 첫 페이지 반복 조회          |         | 성공: 완료 전이                   |
     | 2 출원번호 감시 구독자 매칭                      |--------> 처리된 행은 상태가 바뀌어 빠짐         |---------> 실패: 30분 재시도 -> 한계 시 종결 |
     | 3 발송 의도를 대기 상태로 기록                   |        | (건너뜀 없는 페이징)                   |         |                                   |
     |                                                  |        |                                        |         |                                   |
     |                                                  |        |                                        |         |                                   |
     +--------------------------------------------------+        +----------------------------------------+         +-----------------------------------+

     * 얻은 것: 롤백 시 발송 의도도 소멸(데이터 없이 메일만 나가는 상태 불가) / 한 건의 실패가 다른 건의 상태 갱신을 되돌리지 않음
```

도식 13. 아웃박스 - 발송 의도의 원자 커밋과 1시간 뒤 행별 독립 발송, 건너뜀 없는 상태 페이징

동기화가 사례를 적재하면서, 그 사례의 출원번호를 감시하는 구독자를 찾아 **같은 트랜잭션 안에 대기 상태의 발송 의도를 함께 기록**합니다.\
실제 발송은 **한 시간 뒤 별도 배치**가 대기 건을 집어 보내고, 실패한 건은 **30분 주기 재시도 배치**가 다시 시도한 뒤 한계를 넘으면 종결 상태로 내립니다.

이 구조에서 얻은 것이 두 가지입니다.\
첫째, 동기화가 롤백되면 발송 의도도 함께 사라지므로 **데이터 없이 메일만 나가는 상태가 원천적으로 불가능**합니다.\
둘째, **상태 갱신을 행 1건씩 별도 트랜잭션으로 커밋**해서 **한 건의 발송 실패가 다른 건의 상태 갱신까지 되돌리지 않습니다**. 조회는 상태로 필터한 첫 페이지를 반복해서 다시 읽는 방식입니다.\
처리된 행은 상태가 바뀌어 다음 조회에서 자연히 빠지므로, 위치 기반 페이징에서 흔한, **처리 도중 일부 행을 건너뛰는 문제가 발생하지 않습니다**.

### 근거 - 상태, 전이, 스케줄

- 상태는 대기, 발송 완료, 실패, 종결 네 가지이고 허용 전이를 상태 정의 안에 둡니다. 대기 -> 발송 완료 또는 실패, 실패 -> 발송 완료(재시도 성공) 또는 실패 또는 종결, 발송 완료와 종결은 끝.
- 전이 검증 메서드가 허용 목록에 없는 전이를 예외로 막습니다. 5단계에서 고친 버그가 바로 이 검증의 조건이 반대로 쓰인 것이었습니다.
- 발송 배치는 매일 새벽 정해진 시각(한국시간)에 대기 건을, 재시도 배치는 30분마다 실패 건을 처리합니다(cron 스케줄, 타임존 명시).
- 재시도 상한은 2회, 초과 시 종결. 배치 조회 크기는 100행으로 전량 메모리 적재를 막습니다.
- 행별 상태 갱신은 별도 빈의 REQUIRES_NEW 트랜잭션으로 커밋해, 한 행의 실패가 다른 행의 갱신을 되돌리지 않습니다. 조회는 항상 0페이지를 다시 읽어 처리된 행이 상태 변경으로 빠지게 합니다.
