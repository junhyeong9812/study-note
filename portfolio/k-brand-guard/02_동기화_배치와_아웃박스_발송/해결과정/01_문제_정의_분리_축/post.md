# 1. 문제를 세 가지(레거시 무요구 최신화, 발송 실패가 동기화를 막지 않음, 실패 건만 재시도)로 정의하고, 판단과 전송을 한 트랜잭션에 두면 둘째와 셋째를 동시에 만족할 수 없어 분리를 설계 축으로 확정

> 레거시 동기화와 경보 메일 발송 파이프라인 - 해결 과정 1/6. [사례로 돌아가기](../../post.md) | [다음 2단계](../02_명세_고정_위임/post.md)

문제 상황을 세 가지로 정의했습니다.

- **레거시에 추가 요구를 하지 않고 매일 최신 데이터를 확보한다.**
- **발송의 실패가 데이터 동기화를 되돌리거나 막지 않는다.**
- **한 건의 발송 실패가 나머지 발송을 막지 않고, 실패한 건만 다시 시도할 수 있다.**

### 왜 판단과 전송을 분리하는가 - 트랜잭션 시간축으로 보면

```text
     한 트랜잭션에 판단 + 전송을 두면

     +--------------------------------------------------------------------------------------------------------------------------------------------------+
     | DB 트랜잭션 - 커밋까지 열린 채 유지                                                                                                              |
     |   +------------------------+    +------------------------+   +--------------------------------------------------+   +----------------------+     |
     |   | 사례 적재              |----> 구독자 매칭            |---> 메일 게이트웨이 호출 (외부 I/O)                  |---> 커밋                 |     |
     |   +------------------------+    +------------------------+   | 전송 지연 = 그대로 트랜잭션 지연                 |   +----------------------+     |
     +---------------v----------------------------------------------+--------------------------------------------------+--------------------------------+
                     |                                                                       |
                     ------------------------------------------------------------------------|
                                           전송 실패 -> 전체 롤백: 적재한 데이터까지 되돌림 (요구 2, 3 위반)

     분리 - 아웃박스
       DB 트랜잭션 - 외부 호출 없음, 짧고 확실
     +----------------------------------------------------------------------------+                     +-----------------------------------------------+
     |   +-------------------+  +-------------------+  +------------------------+ |  커밋 이후 별도로   | 발송 배치 (1시간 뒤, 행별 독립 트랜잭션)      |
     |   | 사례 적재         |--> 구독자 매칭       |--> 발송 의도 기록 + 커밋  | |---------------------> 실패해도 그 행만 재시도 - 데이터는 무관       |
     |   +-------------------+  +-------------------+  +------------------------+ |                     |                                               |
     +----------------------------------------------------------------------------+                     +-----------------------------------------------+

     * 전송 지연이 DB를 붙잡지 않고(요구 2), 한 건의 실패가 나머지를 막지 않는다(요구 3). 롤백되면 발송 의도도 함께 사라져 죽은 링크가 생기지 않는다
```

도식 9. 왜 판단과 전송을 분리하는가 - 한 트랜잭션에 두면 전송 지연이 DB 지연이 되고 전송 실패를 데이터 롤백으로 갚게 된다

두 번째와 세 번째는 "판단"과 "전송"을 같은 트랜잭션에 두면 동시에 만족할 수 없습니다.\
외부 메일 게이트웨이 호출이 트랜잭션 안에 들어가면 **전송 지연이 곧 DB 트랜잭션 지연**이 되고, **전송 실패를 데이터 롤백으로 갚게** 됩니다.\
그래서 **"보낼지 결정해 기록하는 단계"와 "실제로 보내는 단계"를 분리**하는 것이 설계의 축이 됐습니다.

### 동기화 배치와 아웃박스 발송 개요 - 판단(원자 커밋)과 전송(별도 배치)의 분리

```text
     1단 - 동기화: 매일 새벽, pull
     +----------------------------------+    +----------------------------------+   +----------------------------------+        +----------------------+
     | 레거시 (연계 기업)               |    | pull - 전량 대조 멱등 배치       |   | 전량 미러                        |        |                      |
     | push 연동 없음                   |---->                                 -|---> 삽입 + 현재 값 갱신              |-------->        성공?         |
     |                                  |    |                                  |   |                                  |        |                      |
     +----------------------------------+    +----------------------------------+   +----------------------------------+        |                      |
                                                                                           -------------------------------------+----------------------+
                                                                                           |실패                                     |성공
                                                                                           |                                         |
                                                                                           v                                         v
                                                                        +------------------------------------+     +----------------------------------------+
                                                                        | 실패                               |     | 성공 - 아웃박스                        |
                                                                        | 실패 시각 앵커 재시도 (최대 2회)   |     | 같은 트랜잭션에서 구독자 매칭          |
                                                                        | 그래도 실패: 로그 남기고 제거      |     | 발송 의도를 대기 상태로 원자 커밋      |
                                                                        | -> 다음날 정기 실행이 멱등 커버    |     | (롤백 시 의도도 소멸 = 죽은 링크 불가) |
                                                                        +------------------------------------+     +----------------------------------------+

     2단 - 발송: 1시간 뒤 별도 배치, 행별 독립 트랜잭션
     +------------------------------+    +------------------------------+      +----------------------+
     | 대기 건 조회                 |    | 메일 API 발송                |      |                      |
     |                              |---->                             -|------>        성공?         |
     +------------------------------+    +------------------------------+      |                      |
                                                                               |          |           |
                                                                     ----------+----------------------+-----------성공
                                                                     |실패                                       |
                                                   +-----------------v-----------------------+ +-----------------v------------------+
                                                   | 실패                                    | | 성공                               |
                                                   | 30분 주기 재시도 배치                   | | 발송 완료로 전이                   |
                                                   | 한계 초과 시 종결 상태 (다른 건은 계속) | | 발송 시각 기록                     |
                                                   +-----------------------------------------+ +------------------------------------+
```

도식 10. 동기화 배치와 아웃박스 발송 - 판단은 동기화 트랜잭션에 원자 커밋, 전송은 별도 배치. 실패는 두 층으로 격리
