# 3. 키워드 검색 900 req/s, 이름 검색 3000 req/s로 모드별 상한을 나누고 램프업으로 포화 지점을 탐색하며 ES 메트릭을 1초 간격으로 동시 수집

> 검색 서버 부하테스트 설계와 샤드 구조 최적화 - 해결 과정 3/4. [사례로 돌아가기](../../post.md) | [이전 2단계](../02_비교_인덱스_구성/post.md) | [다음 4단계](../04_ES_직접_측정/post.md)

### 부하 프로파일 보정 - 모드별 상한 분리, 램프업, 동시 수집

```text
     +-----------------------------------+
     | 키워드 검색                       |
     | 쿼리 비용 큼                      |-------+       +------------------------------------------+               +-----------------------------------+
     | 상한 900 req/s                    |  모드별 램프  | 램프업                                   |               | 동시 수집                         |
     |                                   |       |       | 저부하에서 단계적으로 증가               |               | ES 메트릭 1초 간격                |
     +-----------------------------------+       +-------> 포화 지점 탐색                           |---------------> 응답 지표와 같은 시간축           |
     | 이름 검색                         |       |       |                                          |               |                                   |
     | 쿼리 비용 작음                    |       |       +------------------------------------------+               +-----------------------------------+
     | 상한 3000 req/s                   |-------+
     |                                   |
     +-----------------------------------+
     * 같은 램프를 쓰면 비용이 큰 쪽이 먼저 포화 -> 모드별로 상한을 나눈다
```

도식 23. 부하 프로파일 - 모드별 상한 분리(900/3000 req/s), 램프업 포화 탐색, ES 메트릭 동시 수집

검색 모드에 따라 쿼리 비용이 크게 달라서 같은 램프를 쓰면 한쪽이 먼저 포화됩니다.\
**키워드 검색은 최대 900 req/s, 이름 검색은 최대 3000 req/s로 상한을 나누고**, 저부하에서 단계적으로 요청률을 올리는 **램프업으로 포화 지점을 탐색**했습니다.\
부하가 걸리는 동안 **ES 메트릭을 1초 간격으로 함께 수집**해, 응답 지표와 서버 상태를 **같은 시간축에서 확인**했습니다.

### 근거 - k6 설정값

부하테스트 스크립트는 공통 설정, 시나리오, 실행 스크립트, 결과로 나뉘어 있습니다.\
실행기는 ramping-arrival-rate(초당 도착률 램프)이고, 기본값은 시작 50 req/s, 단계 50 req/s, 상한 600 req/s, 단계당 30초, 사전 할당 VU 200, 최대 VU 3000입니다.\
샤드 비교 스윕은 태국 인덱스와 그것을 2, 4, 8샤드로 다시 색인한 인덱스 네 개에 대해 키워드 검색은 상한 900 req/s(단계 75, 20초), 이름 검색은 상한 3000 req/s(단계 300, 15초)로 램프했고, 이때 VU는 사전 400, 최대 6000으로 올렸습니다.\
포화 지점까지 밀어 올리는 것이 목적이라 thresholds는 실행을 중단하지 않고 관측만 합니다(오류율 100%가 아니면 통과). 지표는 avg, med, p90, p95, p99, max를 남겼습니다.\
원본 결과는 회차별 JSON으로 남아 있습니다. 예를 들어 태국 ES 직접 측정 한 회차(2026-06-22)는 요청 200,017건, 처리량 1,243/s, p95 3,631ms, ES took p95 4,192ms, 오류율 82.6%로 과포화 구간까지 밀어 올린 기록입니다.
