# 2. 현재 입출력을 실측한 특성화 테스트로 기존 동작을 고정하고, 바이트 보존이 필요한 파이프라인은 구코드로 골든 픽스처를 먼저 만들어 비교

> text-server 리팩토링 - 해결 과정 2/7. [사례로 돌아가기](../../post.md) | [이전 1단계](../01_과제_정의_동작_보존/post.md) | [다음 3단계](../03_죽은_코드_제거/post.md)

구조를 바꾸기 전에 현재 입출력을 실측해 **기존 동작을 그대로 보존하는 테스트(characterization)로 고정**했고, 버그로 의심되는 출력도 일단 그대로 고정했습니다(리팩토링 단계에서는 **현재 동작이 곧 스펙**, 수정은 별도 동작 변경 작업으로 분리).

바이트 수준 보존이 필요한 데이터 파이프라인 전환은 전환 후 사라질 구코드로 **기준 출력(골든 픽스처)을 먼저 만들어 새 경로의 출력과 같은지 비교**했고, **매 구조 변경마다 전체 테스트를 돌려 0실패를 유지**했습니다.

### 근거 (코드) - 특성화 테스트와 골든 픽스처

- 특성화 테스트는 국가별 G2P와 전사(toEng) 클래스에 신설했습니다. 예를 들어 toEng 리팩토링 전에 28케이스를 리팩토링 전 코드의 실측 출력으로 고정해 25에서 53케이스가 됐고, 발음 규칙 리팩토링 전에는 7케이스를 보강해 16에서 23케이스가 됐습니다. 각 테스트 파일 머리에 "리팩토링 전 실측 출력 고정" 주석이 있습니다.
- 골든 픽스처는 `src/test/resources/golden/` 아래 199개 파일입니다. ES 질의 골든(search-query 30 + 원본 스냅샷 30), API 응답 골든 16, US 프로젝션 9, CN 합성 13과 라이브 10, ASEAN 합성 11과 9개국 라이브.
- 질의 골든(`QueryGolden`)은 SearchRequest를 결정론적 canonical JSON으로 박제합니다(객체 키 정렬, 스칼라 배열 정렬, bool 절 순서는 의미가 있어 보존). API 골든(`ApiGolden`)은 `-Dgolden.regenerate=true`일 때만 다시 생성하고, 골든 파일이 없으면 실패합니다(fail-closed. 유실이나 오타 이름을 조용히 통과시키지 않음).
