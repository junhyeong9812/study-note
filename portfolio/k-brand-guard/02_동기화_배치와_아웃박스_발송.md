# 레거시 동기화와 경보 메일 발송 파이프라인 (일일 배치, 트랜잭셔널 아웃박스)

> 소속 경력: 한국지식재산보호원 K-브랜드 지킴이 - 해외 상표 무단선점 경보 서비스 개발
> 회사 내부 식별자(클래스명, 파일 경로, 커밋 해시)는 노출하지 않고 맥락만 서술합니다.
> 역할 구분: 알림 서비스의 초기 구조와 계약을 제가 명세로 설계해 기본 도메인 구현을 팀원에게 위임했고, 이후 작업 - 아웃박스 분리 구조, 동기화 배치 설계와 구현, 고도화(상태 전이 버그 수정, 발송 채널 전환, 전량 미러 개선) - 는 제가 담당했습니다.

## 핵심 요약

- 구독자가 등록한 상표에 무단선점 의심 사례가 잡히면 이메일로 알리는 서비스. 원천 레거시는 연계 기업이 운영하고 push 연동이 없어, 매일 정해진 시각에 pull 해 전량 대조하는 멱등 배치로 설계했습니다. 타사에 추가 개발을 요구하지 않고 성립하는 구조라는 점이 선택 이유입니다
- 발송은 트랜잭셔널 아웃박스(outbox)로 분리(기본 도메인 구현은 팀원에게 맡기고, 아웃박스 분리부터는 제가 직접 진행): 동기화 트랜잭션 안에서 발송 의도만 대기 상태로 원자 커밋하고, 실제 발송은 다음 시각의 별도 배치가 수행합니다. 동기화가 롤백되면 메일도 존재하지 않으므로 "메일은 갔는데 열 데이터가 없는" 죽은 링크가 생기지 않습니다. 메일 본문과 결과 열람 토큰도 같은 트랜잭션에서 커밋된 뒤에야 발송됩니다
- 실패 격리를 두 층으로 분리: 동기화 실패는 실패 시각에 앵커된 재시도로 최대 2회 재처리하고 그래도 실패하면 다음날 정기 실행이 멱등하게 커버합니다. 발송은 행별 독립 트랜잭션이라 한 건의 실패가 배치 전체를 멈추지 않습니다
- 초기 insert-only 동기화의 갱신 미전파 한계를 데이터 실측으로 발견해 전량 미러로 개선. 신규 305건이 전부 비활성 상태로 들어와 삽입 대상이 0건이던 사실과 활성 전환 235건이 반영되지 않던 사실을 확인하고, 활성으로 전환되는 시점에만 통지하는 불변식을 세웠습니다

## 문제 상황

무단선점 의심 사례의 원천 데이터는 연계 기업이 운영하는 레거시에 있고, 우리 쪽에서 그 데이터를 받아 구독자에게 이메일 경보를 보내야 했습니다. 문제는 레거시가 변경을 알려주는 push 연동을 제공하지 않는다는 점이었습니다. 우리 요구로 타사 시스템에 연동 기능을 새로 만들게 하는 것은 일정과 협의 비용이 모두 큰 선택이었습니다.

발송 쪽도 온전하지 않았습니다. 코드 리뷰 중 전체 코드를 점검하다가, 당시 유일한 발송 구현이 실제로 메일을 보내지 않고 로그만 남기며 정상 종료된다는 점(발송 성공으로 오인될 수 있는 상태)과, 발송 결과가 전체 성공 또는 전체 실패로만 표현돼 여러 수신자 중 일부만 실패한 경우의 이력과 재시도 근거를 남길 수 없다는 점을 확인했습니다.

## 해결 과정

문제 상황을 세 가지로 정의했습니다.

- 레거시에 추가 요구를 하지 않고 매일 최신 데이터를 확보한다.

- 발송의 실패가 데이터 동기화를 되돌리거나 막지 않는다.

- 한 건의 발송 실패가 나머지 발송을 막지 않고, 실패한 건만 다시 시도할 수 있다.

```text
## 왜 판단과 전송을 분리하는가 - 한 트랜잭션에 두면 요구 2, 3을 동시에 만족할 수 없다

 +- 한 트랜잭션: 판단 + 전송 ------------------------------+       +- 분리: 아웃박스 -----------------------------------+
 | [ 적재 -> 구독자 매칭 -> 메일 게이트웨이 호출 -> 커밋 ] |       | 판단: [ 적재 -> 매칭 -> 발송 의도 기록 ] 원자 커밋 |
 |                                                         |  ==>  |         (외부 호출 없음 - 트랜잭션 짧고 확실)      |
 | x 외부 호출이 트랜잭션을 붙잡음                         |       | 전송: 1시간 뒤 별도 배치, 행별 독립 트랜잭션       |
 |   전송 지연 = DB 트랜잭션 지연                          |       |                                                    |
 | x 전송 실패 -> 데이터 롤백 (요구 2 위반)                |       | o 발송 실패가 동기화를 못 건드림 (요구 2)          |
 | x 한 건 실패 -> 전체 되돌림 (요구 3 위반)               |       | o 실패한 건만 다시 시도 (요구 3)                   |
 +---------------------------------------------------------+       +----------------------------------------------------+
```

*도식 5. 왜 판단과 전송을 분리하는가 - 한 트랜잭션에 두면 전송 지연이 DB 지연이 되고 전송 실패를 데이터 롤백으로 갚게 된다*

두 번째와 세 번째는 "판단"과 "전송"을 같은 트랜잭션에 두면 동시에 만족할 수 없습니다. 외부 메일 게이트웨이 호출이 트랜잭션 안에 들어가면 전송 지연이 곧 DB 트랜잭션 지연이 되고, 전송 실패를 데이터 롤백으로 갚게 됩니다. 그래서 "보낼지 결정해 기록하는 단계"와 "실제로 보내는 단계"를 분리하는 것이 설계의 축이 됐습니다.

```text
## 동기화 배치와 아웃박스 발송 개요 - 판단(원자 커밋)과 전송(별도 배치)의 분리, 성공/실패 경로

 [1단 - 동기화: 매일 새벽, pull]
 +--------------------+     +----------------------------+     +---------------------+     +--------------+
 | 레거시 (연계 기업) | --> | pull - 전량 대조 멱등 배치 | --> | 전량 미러           | --> | 동기화 성공? |
 | push 연동 없음     |     +----------------------------+     | 삽입 + 현재 값 갱신 |     +--------------+
 +--------------------+                                        +---------------------+                     
                                                                                                  |
                                                                            +---------------------+----------------------+
                                                         실패                 |                                            | 성공
                                                                            v                                            v
                                                         +- 실패 ------------------------------+    +- 성공 - 아웃박스 ----------------------+
                                                         | 실패 시각 앵커 재시도 (최대 2회)    |    | 같은 트랜잭션에서 구독자 매칭          |
                                                         | 그래도 실패: 로그 남기고 제거       |    | 발송 의도를 대기 상태로 원자 커밋      |
                                                         | -> 다음날 정기 실행이 멱등하게 커버 |    | (롤백 시 의도도 소멸 = 죽은 링크 불가) |
                                                         +-------------------------------------+    +----------------------------------------+

 [2단 - 발송: 1시간 뒤 별도 배치, 행별 독립 트랜잭션]
 +--------------+     +---------------+     +------------+
 | 대기 건 조회 | --> | 메일 API 발송 | --> | 발송 성공? |
 +--------------+     +---------------+     +------------+
                                                  |
                                   +--------------+-----------+
                      실패           |                          | 성공
                                   v                          v
                      +- 실패 -----------------+    +- 성공 -----------+
                      | 30분 주기 재시도 배치  |    | 발송 완료로 전이 |
                      | 한계 초과 시 종결 상태 |    | 발송 시각 기록   |
                      | (다른 건 발송은 계속)  |    +------------------+
                      +------------------------+
```

*도식 6. 동기화 배치와 아웃박스 발송 - 판단은 동기화 트랜잭션에 원자 커밋, 전송은 별도 배치. 실패는 두 층으로 격리*

### 구조와 계약을 명세로 먼저 고정하고 위임

구독 정보를 사용자당 1행의 구독자와 구독자당 N행의 출원번호 두 테이블로 정규화하고, 발송을 별도 스케줄 없이 동기화 완료 직후에 잇는 구조를 명세로 작성했습니다. 동기화가 끝난 데이터라야 최신 사례로 매칭할 수 있기 때문입니다. 이 명세를 기준으로 팀원이 구독 도메인의 기본 구조를 구현했고, 일정이 촉박해 이후 작업은 위임하지 않고 제가 직접 맡아 발송을 대기 이력(아웃박스)과 별도 발송 배치로 분리하는 구조로 발전시켰습니다. 직접 구현하면서 놓친 부분이 있는지는 Claude와 Codex 리뷰로 점검했습니다.

### 동기화 배치 - pull, 멱등, 순서, 재시도 앵커

```text
## 동기화 배치 - pull, 순서, 멱등, 실패 시각 앵커 재시도

 +-------------------------------+     +----------------------------------+     +------------------------------+              
 | 매일 새벽 정해진 시각         |     | 1 출원인 마스터 적재             |     | 레거시 식별자 기준 전량 대조 |     +-------+
 | (타임존 명시 - 한국시간 고정) | --> | 2 피해사례 적재                  | --> | 멱등: 재호출 = 재처리        | --> | 성공? |
 +-------------------------------+     | (순서 보장 - 본인확인 기준 선행) |     | (실패 행 별도 보관 불필요)   |     +-------+
                                       +----------------------------------+     +------------------------------+              
                                                                                               |
                                                                         +---------------------+------------+
                                                      실패                 |                                  | 성공
                                                                         v                                  v
                                                      +- 실패 ------------------------------+    +- 성공 -------------+
                                                      | 인메모리 재처리 큐에 등록           |    | 적재 완료          |
                                                      | 항목에 다음 재시도 시각을 직접 담음 |    | -> 아웃박스 단계로 |
                                                      | (실패 시각 기준 앵커)               |    +--------------------+
                                                      +-------------------------------------+                          

   폴러: 짧은 주기로 돌되 시각이 도래하지 않은 항목은 큐에 되돌림 -> 최대 2회 재시도 -> 초과 시 에러 로그 + 제거 -> 다음날 정기 실행이 멱등하게 커버
   (처음의 고정 간격 폴러는 실패 직후 tick이 오면 재시도가 몰림 - 리뷰 지적을 관측 테스트로 재현해 확인하고 시각 앵커로 교체)
```

*도식 7. 동기화 배치 - 순서 보장과 멱등 전량 대조, 실패는 시각 앵커 재시도 후 다음날 멱등 커버*

레거시를 매일 새벽 정해진 시각에 우리가 조회해 적재하는 pull 방식으로 정했습니다. 배치 시각은 타임존을 명시해 배포 환경의 기본 타임존이 바뀌어도 한국시간 기준이 유지되게 했습니다. 동기화는 레거시 식별자를 기준으로 전량 대조하는 멱등 연산이라 몇 번 호출해도 중복이 생기지 않고, 그래서 실패한 행 데이터를 따로 보관할 필요 없이 재호출이 곧 재처리가 됩니다.

동기화 단위에는 순서를 뒀습니다. 출원인 마스터를 피해사례보다 먼저 적재합니다. 출원인 이메일이 상세 결과 열람의 본인확인 기준이라, 피해사례만 먼저 들어오고 출원인이 따라오지 않으면 그 건은 아무도 열 수 없기 때문입니다.

실패는 인메모리 재처리 큐로 다룹니다. 처음 설계에서는 재처리 폴러를 고정 간격으로 돌렸는데, Claude와 Codex로 놓친 부분을 점검하는 과정에서 "실패 직후에 폴러 tick이 오면 재시도가 몰려 의도한 간격 분산이 깨진다"는 지적을 받았고, 이를 관측 테스트로 만들어 돌려 실제로 재현되는 것을 확인했습니다. 그래서 큐 항목에 다음 재시도 시각을 직접 담아 실패 시각 기준으로 앵커하고, 폴러는 짧은 주기로 돌되 시각이 도래하지 않은 항목은 큐에 되돌려 놓는 방식으로 고쳤습니다. 최대 2회까지만 재시도하고 그 이후는 에러 로그를 남기고 큐에서 제거합니다. 데이터 유실이 없는 근거는 멱등성입니다. 다음날 정기 실행이 미적재분을 다시 채웁니다.

### 아웃박스 - 발송 의도를 데이터와 함께 원자 커밋

```text
## 아웃박스 - 발송 의도를 데이터와 함께 원자 커밋, 행별 독립 발송

 +- 동기화 트랜잭션 --------------+                        +--------------------------------+     +-----------------------------------+
 | 1 사례 적재                    |     +------------+     | 상태 필터 첫 페이지 반복 조회  |     | 행 1건씩 별도 트랜잭션 발송       |
 | 2 출원번호 감시 구독자 매칭    | --> | (1시간 뒤) | --> | 처리된 행은 상태가 바뀌어 빠짐 | --> | 성공: 완료 전이                   |
 | 3 발송 의도를 대기 상태로 기록 |     | 발송 배치  |     | (건너뜀 없는 페이징)           |     | 실패: 30분 재시도 -> 한계 시 종결 |
 | => 하나의 원자 커밋            |     +------------+     +--------------------------------+     +-----------------------------------+
 +--------------------------------+                                                                                                    

   얻은 것: 롤백 시 발송 의도도 소멸(데이터 없이 메일만 나가는 상태 불가)  /  한 건의 실패가 다른 건의 상태 갱신을 되돌리지 않음
```

*도식 8. 아웃박스 - 발송 의도의 원자 커밋과 1시간 뒤 행별 독립 발송, 건너뜀 없는 상태 페이징*

동기화가 사례를 적재하면서, 그 사례의 출원번호를 감시하는 구독자를 찾아 같은 트랜잭션 안에 대기 상태의 발송 의도를 함께 기록합니다. 실제 발송은 한 시간 뒤 별도 배치가 대기 건을 집어 보내고, 실패한 건은 30분 주기 재시도 배치가 다시 시도한 뒤 한계를 넘으면 종결 상태로 내립니다.

이 구조에서 얻은 것이 두 가지입니다. 첫째, 동기화가 롤백되면 발송 의도도 함께 사라지므로 데이터 없이 메일만 나가는 상태가 원천적으로 불가능합니다. 둘째, 상태 갱신을 행 1건씩 별도 트랜잭션으로 커밋해서 한 건의 발송 실패가 다른 건의 상태 갱신까지 되돌리지 않습니다. 조회는 상태로 필터한 첫 페이지를 반복해서 다시 읽는 방식입니다. 처리된 행은 상태가 바뀌어 다음 조회에서 자연히 빠지므로, 위치 기반 페이징에서 흔한, 처리 도중 일부 행을 건너뛰는 문제가 발생하지 않습니다.

### 고도화 - 상태 전이 버그 수정, 발송 채널 교체

```text
## 고도화 - 상태 전이 버그 수정, 발송 어댑터 교체 (아웃박스, 상태머신은 불변)

 +- 발견한 버그 -------------------------+     +- 수정 ------------------------------+
 | 허용된 전이에서 예외 발생 (조건 반전) |     | 조건 정정                           |
 | -> 정상 전이 전부 실패                | ==> | 실패 -> 성공(재시도 성공) 경로 추가 |
 | 실패 -> 성공 전이가 허용 목록에 없음  |     | 전이 케이스를 테스트로 고정         |
 | -> 재시도 성공을 반영 불가            |     +-------------------------------------+
 +---------------------------------------+                                            

 +- 채널 교체 -----------------------------------+   +- 리뷰에서 계약으로 흡수한 2건 -------------------------+
 | 불변식 선고정: 아웃박스, 상태머신 무변경      |   | 2xx인데 접수 식별자 없음 -> 실패 판정 (무음 성공 차단) |
 | 발송 어댑터만 교체: SMTP -> 클라우드 메일 API | + | 서명, 본문 구성 런타임 예외 -> 발송 실패 계약으로 변환 |
 +-----------------------------------------------+   | (배치 전체가 중단되지 않음)                            |
                                                     +--------------------------------------------------------+
```

*도식 9. 고도화 - 전이 조건 반전 버그 수정과 재시도 성공 경로 추가, 어댑터만 교체하며 계약 2건 흡수*

브랜치 병합 검증 중에 상태 전이 검증의 조건이 반대로 쓰여 있는 것을 발견했습니다. 허용된 전이일 때 예외를 던지고 있어서 정상 전이가 전부 실패하는 상태였고, 실패에서 성공으로 가는 전이가 허용 목록에 아예 없어 재시도가 성공해도 반영할 수 없었습니다. 조건을 바로잡고 재시도 성공 경로를 허용 목록에 추가한 뒤 전이 케이스를 테스트로 고정했습니다.

발송 채널을 SMTP에서 클라우드 메일 API로 교체할 때는, 아웃박스와 상태머신을 변경하지 않는다를 불변식으로 먼저 고정하고 발송 어댑터만 갈아끼웠습니다. 이때 코드 리뷰 과정에서 찾은 두 가지를 계약으로 흡수하도록 설계했습니다. 응답이 2xx인데 접수 식별자가 비어 있으면 성공으로 확정하지 않고 실패로 판정하는 불변식(무음 성공 차단), 그리고 서명이나 본문 구성에서 나는 런타임 예외까지 발송 실패 계약으로 변환해 배치 전체가 중단되지 않게 하는 처리입니다.

### 전량 미러 - 데이터 실측으로 드러난 미전파 한계

```text
## 전량 미러 - insert-only의 미전파를 실측으로 확인하고 교체, 통지는 활성 전환 시점만

 +- 전: insert-only (실측) ---------------------------+     +- 후: 전량 미러 -----------------------------------+
 | 신규 305건 전부 비활성(공개 전) -> 삽입 대상 0건   |     | 없는 건은 삽입, 있는 건은 레거시 현재 값으로 갱신 |
 | 비활성 -> 활성 전환 235건 -> 갱신 경로 없어 미전파 | ==> | 삭제는 반영하지 않음 (보존형 - 이력 유지)         |
 +----------------------------------------------------+     +---------------------------------------------------+

   통지 기준 = 활성으로 전환되는 시점:  비활성 -> 활성 = 통지  /  활성 유지 갱신 = 재통지 없음  /  비활성 갔다가 재공개 = 활성 전환으로 다시 잡혀 재통지
```

*도식 10. 전량 미러 전환 - insert-only 미전파 실측(305건, 235건)과 활성 전환 시점 통지 기준*

배포를 앞두고 원천 데이터를 최신본으로 교체하면서 실측해 보니, 초기의 insert-only 동기화로는 최신본을 반영할 수 없다는 사실이 드러났습니다. 신규 305건이 전부 비활성(공개 전) 상태로 들어와 삽입 대상이 0건이었고, 기존 건 중 비활성에서 활성으로 바뀐 235건은 갱신 경로가 없어 전파되지 않았습니다. 없는 건은 삽입하고 있는 건은 레거시 현재 값으로 갱신하는 전량 미러(삭제는 반영하지 않는 보존형)로 바꾸고, 통지 기준은 "활성으로 전환되는 시점"으로 못 박았습니다. 비활성 사례는 통지하지 않고, 활성 상태가 유지되는 갱신은 재통지하지 않으며, 비활성으로 내려갔다가 다시 활성으로 돌아오는 재공개는 활성 전환으로 다시 잡혀 재통지합니다. 레거시에서 사라진 행은 지우지 않아 이력을 보존했습니다.

## 결과

파이프라인은 새벽 동기화, 한 시간 뒤 대기 건 발송, 30분 주기 실패 재시도의 3단으로 자리잡았고, 실발송 경로는 두 갈래로 검증했습니다. 메일 API를 직접 호출해 접수 식별자를 받는 경로와, 대기 건을 스케줄러가 집어 발송한 뒤 상태가 발송 완료로 전이되고 발송 시각이 기록되는 경로를 각각 실제 수신까지 확인했습니다.

최신본 반영은 레코드 단위로 검증했습니다. 보정 후 총 73,747건(기존 보유분에 신규 305건 추가)이고, 원천에 현존하는 행 기준 8개 필드 전량 대조에서 차이는 0건이었습니다(원천에서 사라진 행은 이력 보존 원칙대로 남긴 채). 활성 전환 235건이 반영됐고, 구독 중인 출원번호와 교집합이 없음을 사전 확인한 대로 의도치 않은 대기 메일이 생기지 않았음을 대기 건 증가 0으로 확인했습니다. 이 서비스는 2026-07-27 대국민 서비스로 배포를 완료했습니다.

### 한계와 트레이드오프

재처리 큐는 인메모리이고 단일 인스턴스를 전제합니다. 재기동하면 큐가 사라집니다. 이 유실을 수용한 근거는 두 가지입니다. 동기화가 멱등이라 다음날 정기 실행이 미적재분을 다시 채운다는 것, 그리고 서비스 자체의 부하가 크지 않다는 피드백 위에서 외부 큐나 잠금 저장소를 들이는 복잡도를 줄이는 편이 낫다고 판단한 것입니다. 즉 몰라서 생긴 구멍이 아니라 범위를 알고 고른 선택입니다. 발송 역시 메일 API 접수 후 완료 상태를 커밋하기 전에 프로세스가 중단되면 같은 메일이 한 번 더 나갈 수 있는 at-least-once 구조라는 한계가 있습니다. 정확히 한 번에 가깝게 만들려면 발송 건별 멱등 키를 메일 제공자와 공유해 중복 접수를 차단하거나, 접수 결과를 사후 대조하는 복구 절차가 더 필요합니다. 이 항목들과, 다중 인스턴스 전환 시 필수가 되는 재시도 실패 기록 시점의 상태 검증, 전이 검증 예외와 전송 실패 예외를 분리해 잡는 처리는 이슈로 만들어 구현을 위임해 두었습니다.

## 회고

상태 전이, 배치 처리, 메일 발송처럼 구간마다 예외가 생길 수 있는 지점을 미리 잡아 두고, 각 가능성을 조금 더 자세히 들여다볼 필요가 있다는 것을 느꼈습니다. 그리고 이런 설계는 한 번에 다 만들기보다 기본 파이프라인을 먼저 설계하고 가드레일을 잡아 둔 상태에서 점진적으로 확장해 나가는 편이 더 좋은 방향이라는 것을 배웠습니다.
