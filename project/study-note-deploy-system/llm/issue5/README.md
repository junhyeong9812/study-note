# issue5 — /digest 예약 계약 제거 (안 쓰면 지운다)

- 리포: https://github.com/junhyeong9812/study-note-deploy-system-llm
- 이슈 #10 · PR: https://github.com/junhyeong9812/study-note-deploy-system-llm/pull/11

## 1. 배경 (요구사항)

issue1에서 /digest(검색 결과를 모델이 한국어로 요약해주는 API)를 "계약만 예약"
상태(호출하면 501)로 남겨뒀다. 다시 따져보니:

- **사람용 검색**: 이 시스템의 목적이 인출 학습(기억에서 꺼내는 훈련)이라
  기본 동작은 링크 목록 — 요약 자동 노출은 목적과 충돌한다.
- **MCP 확장(코딩 중 Claude가 질의)**: 소비자가 강한 모델이라 문서 조각
  원문을 직접 읽는 쪽이 항상 낫다. 8B가 미리 요약하면 오히려 정보를 깎아서
  전달하는 꼴.

즉 현재 수요 0, 미래 수요도 불분명. **쓰지 않는 것은 지운다.**

## 2. 검토한 방식들

### 선택 — 완전 제거

- 예약석의 유지 비용이 "0에 가깝다"고 해도 0은 아니다: 설계 문서·README·테스트가
  계속 이 계약을 설명해야 하고, 읽는 사람(미래의 나)이 "이건 뭐지"를 반복한다.
- 필요해지면 **그때의 요구로 다시 설계**하는 게 낫다 — 지금 기록해둔 입출력 모양이
  그때도 맞으리란 보장이 없고, 틀린 예약석은 없느니만 못하다.

### 대안 — 예약석 유지 (탈락)

- "나중에 backend 수정 없이 켠다"가 명분이었지만, 그 '나중'의 소비자(MCP)가
  이 기능을 원하지 않는다는 결론이 나면서 명분 소멸. → 탈락.

> 용어 — **YAGNI**(You Aren't Gonna Need It): "어차피 안 쓸걸?" — 미래를 위해
> 미리 만들어두는 걸 경계하는 원칙. 예측으로 만든 것은 대개 틀린 모양으로 만들어진다.

## 3. 워크플로우 (기존 → 변경)

```
[기존]  POST /digest ──▶ 501 {"success":false,"error":{"code":"not_implemented"}}
        (설계 D2에 입출력 계약, domain에 모델 3형, 테스트 2건)

[변경]  POST /digest ──▶ 404 (그런 경로 없음 — FastAPI 기본)
        설계 D5에 "왜 지웠나"만 남김 (결정의 흔적은 지우지 않는다)
```

## 4. 코드 변경

- domain: `DigestChunk`·`DigestIn`·`DigestResult` 삭제
- api: `/digest` 핸들러 삭제, error code 목록에서 `not_implemented` 삭제
- 설계 D2/D9·README에서 계약 삭제, **D5에 제거 사유를 기록으로 남김**
- 테스트 27건 green

## 5. 구현 중 마주친 문제

없음 — 예약석이 로직 없는 계약뿐이라 제거가 곧 끝. (역설적으로 "지우기 쉬웠다"는
사실이 예약석의 비용이 정말 낮았다는 증거이기도 하다. 그래도 지운 이유는 2절.)
