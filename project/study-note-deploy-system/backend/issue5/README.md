## 1. 배경

이슈 1~4를 머지한 뒤 누적 diff를 두 독립 리뷰어(다른 모델 2종)에게 같은 packet(명세+설계+
diff)으로 보냈다. 같은 모델 둘은 편향을 공유하므로 **서로 다른 모델**이어야 독립 신호다.
결과: 11건 + 14건, 겹치는 핵심 5건. 이후 종합 감사 1회 → 수정 → 타깃 재점검 1회.

## 2. 채택·기각의 기준

- **채택**: 명세·설계와 어긋남 + 실패 시나리오가 구체적 + 코드 위치가 있음.
- **기각(근거 기록)**: 설계 의도로 설명되는 것. 기각도 이유를 남긴다 — 나중에 같은 지적이
  또 오면 "그때 왜 안 했지"를 다시 고민하지 않게.
- **감사·재점검**: 리뷰어의 지적도 틀릴 수 있다 — 실행해보고 판정(이슈3의 conftest 건처럼).

## 3. 주요 finding과 조치 (25건 중 핵심)

| 구멍 | 무엇이 문제였나 | 조치 |
|---|---|---|
| RRF 병합 키 | `path#heading`으로 합쳤는데, 큰 절을 문단으로 쪼갠 청크들은 heading이 전부 같다 → 서로 다른 청크가 하나로 접혀 순위 왜곡 | 키를 `path#chunk_no`(설계의 청크 정체성)로 |
| ES 타임아웃 없음 | ES가 멈추면 검색 스레드가 무한 대기, sync는 영원히 "처리 중"(409 폭탄) | ES 접근을 한 클래스로 모으고 query 5s / bulk 60s |
| kNN이 검색을 인질로 | llm 폴백은 있는데 임베딩 장애는 503 전량 실패 | try/catch → BM25 단독 + `dense_used` |
| 전역 봉투 구멍 | 파라미터 누락·타입 오류·예상 못 한 예외가 Spring 기본 JSON으로 새어 나감 | `@RestControllerAdvice`로 전부 봉투 |
| full 재색인 경로 없음 | 처리 SHA가 shallow clone 경계를 벗어나면 diff 실패 → 영구 스톨. 복구 API도 없음 | `full:true` 플래그 + diff 실패 시 자동 전체 색인 강등 + 이번 SHA 아닌 문서 삭제(고아 정리) |
| git 프로세스 행 | 출력을 다 읽은 뒤 타임아웃을 거는 순서라, 프로세스가 멈추면 readText에서 영원히 대기 | 출력 읽기를 별도 스레드로, `waitFor(120s)` 먼저 |
| diff 파싱 무테스트 | 여기가 틀리면 문서가 조용히 인덱스에서 사라진다 | 순수 함수로 분리 + rename/한글/탭 테스트 |
| 단일 거대 문단 | 문단 하나가 8KB를 넘으면(무개행 코드블록) 상한이 안 지켜짐 | 줄/코드포인트 경계로 강제 분할 (surrogate 안전) |
| LAN 바인딩 | `0.0.0.0` 기본값 — 인터페이스가 늘면 외부 노출 | `${BIND_ADDR:?}` — 지정 안 하면 기동 실패(fail-closed) |
| **기각** SHA 고정 색인 | "요청 SHA를 checkout해 색인하라" | 설계 확정: SHA는 **중복 판별 힌트**, 색인 대상은 항상 원격 HEAD(수렴). 뒤처진 재요청은 no-op |
| **기각** 트리 API | "평면 목록은 계약 위반" | front가 트리를 구성하는 게 계약 — 문서에 명문화 |

## 4. 워크플로우 변화 (예: full 재색인·고아 정리)

```
[기존] prev 있음 → diff → 실패하면 끝 (prev 안 움직임 → 다음도 실패 → 영구 스톨)

[변경] prev 있음 → diff ──실패(shallow 경계 밖)──▶ 전체 목록으로 강등(warning 로그)
       전체 색인 후 → commit_sha != 이번 SHA 인 문서 삭제  ← 저장소에서 사라진 문서 청소
       + POST /internal/sync {"full": true} 수동 경로
```

## 5. 구현 중 마주친 문제

### 감사가 "채택 조치가 결함을 해소하지 못한다"고 반려한 3건

리뷰 채택/기각표를 다시 다른 모델에게 감사시켰더니, 조치의 **강도**를 지적했다. 예를 들어
임베딩 절단 건 — 내 조치는 "절단 시 warning 로그"였는데 감사 왈:

> "warning만 추가해도 청크 뒷부분이 dense 검색에서 제외되는 문제는 그대로다.
> 모델 토큰 한도에 맞춘 추가 청킹 또는 전체 청크 임베딩이 필요하다."

맞는 말이다 — 로그는 문제를 **알려줄** 뿐 **없애지** 못한다. 재조치: 절단 상한을 6000자
→ 9000자로 올렸다. 청크 자체가 8KB(≈ASCII 8192자·한글 ~2700자) 이하로 잘리므로 9000자
상한이면 **절단이 구조적으로 발생하지 않는다**(warning은 안전벨트로 유지). 같은 방식으로
BIND 기본값 `0.0.0.0`은 "설정 안 하면 그대로 노출"이라는 지적 → `${BIND_ADDR:?}`
(미설정 시 기동 자체가 실패하는 fail-closed)로.

### 재점검이 잡은 "수정이 만든 새 구멍" 3건

수정 diff만 다시 보게 했더니(전체 재리뷰 아님) 셋 다 **내 수정이 방금 만든** 결함이었다:

```
- GlobalErrorHandler.kt:19 · 포괄 Exception 처리로 size=abc 같은 클라이언트 입력 예외까지
  500으로 변환된다. 기존 Spring 4xx 응답을 서버 장애로 회귀시킨다.
- ContentController.kt:42 · readFile()의 모든 예외를 404로 처리해 I/O·권한 장애도
  "문서 없음"으로 오인한다.
- Chunker.kt:86 · String.chunked()는 UTF-16 단위로 자르므로 surrogate pair(이모지 등
  4바이트 문자)를 찢을 수 있다.
```

각각의 수정:
- 타입 불일치(`MethodArgumentTypeMismatchException`)·본문 파싱 실패를 422 봉투로 분리
  → 이후 실기동에서 `size=abc` → `422 {"code":"invalid_request"}` 확인.
- 404는 `FileNotFoundException`류만, 그 외 I/O는 전역 500 봉투로.
- 코드포인트 경계 분할 함수 직접 구현(끝 글자가 high surrogate면 경계를 한 칸 당김).

**배경**: 리뷰→수정 루프의 마지막 재점검이 왜 "수정 diff 한정"인지가 여기서 드러난다 —
수정은 급하게 이뤄지는 코드라 새 결함 밀도가 높고, 좁게 보니 깊게 본다.
