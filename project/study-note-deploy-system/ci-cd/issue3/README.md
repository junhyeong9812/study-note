## 1. 배경 — 왜 이 시점에 리뷰를 했나

ci-cd(배포 서버)는 다른 이슈들과 성격이 다르다. 위키·검색이 잘못되면 화면이 이상할
뿐이지만, **배포 서버가 잘못되면 남의 서버에서 임의 명령이 돈다.** 그래서 명세를 쓸 때부터
"이 서버는 stakes 중간~높음, 코드 리뷰 1회를 반드시 거친다"를 조건으로 박아뒀다.

리뷰 방식은 계속 쓰던 것 — **전체 소스를 다른 모델(codex)에게 주고, 내가 그 지적을
하나씩 판정**한다. 같은 모델은 같은 맹점을 공유하니, 다른 모델이어야 내가 못 본 걸 본다.
결과 9건. 아래는 그중 **왜 그게 문제인지**를 하나씩 풀어 쓴 것이다.

## 2. 채택한 지적

### F4 — master 컨테이너가 너무 많은 걸 쥐고 있었다 (가장 아픈 지적)

당시 구조:

```
              docker-compose.yml  (서비스 정의 1개: ci-cd, MODE만 바꿔 재사용)
                       |  볼륨 마운트가 공통이라...
        +--------------+---------------+
        v                              v
  [master 컨테이너]                [agent 컨테이너]
   외부 배포요청 받음                실제 배포 실행
   * docker.sock 마운트  <-문제       docker.sock 마운트  <-필요
   * 저장소 3개 마운트   <-문제       저장소 3개 마운트   <-필요
```

`docker.sock`은 "호스트의 도커를 조종하는 리모컨"이다. 이게 마운트된 컨테이너는 호스트에서
아무 컨테이너나 띄우고 지울 수 있다. agent는 그게 **일**이니 필요하다. 그런데 master가
하는 일은 "요청 받아 어느 agent로 보낼지 정하기"뿐인데 같은 리모컨을 쥐고 있었다.

**왜 위험한가(침해 반경):** master는 외부(GitHub Actions) 요청을 받는 입구다. 입구가
뚫리면(취약점 하나) 즉시 호스트 도커 전체 + 저장소 3개 접근으로 번진다. 하는 일에 비해
쥔 권한이 너무 컸다 — "최소 권한(least privilege)" 위반.

**어떻게 고쳤나:** compose를 **하나의 서비스 재사용**에서 **두 개의 분리된 서비스**로 나눴다.
`profiles`(서비스마다 꼬리표를 달아 켤 때 원하는 것만 켜는 도커 컴포즈 기능)를 사용:

```
[기존]  services: { ci-cd: { MODE로 전환, 볼륨 공통 } }
        -> 어느 역할이든 sock/저장소가 딸려온다

[변경]  services:
          master: { profiles:[master], 볼륨 없음        }   <- 접수/라우팅만
          agent:  { profiles:[agent],  볼륨=sock+저장소 }   <- 실행 권한은 여기만
        .9 기동:  docker compose --profile master --profile agent up
        그 외:    docker compose --profile agent up
```

배포 후 `docker inspect ci-cd-master`로 마운트 **0개** 확인.
> 원칙: 편의(서비스 정의 하나 재사용)가 최소 권한을 침식하면 편의를 버린다.

### F6 — 빠르게 두 번 push하면 두 번째 배포가 소리 없이 사라졌다

> 용어 — in-flight: "처리 중인·아직 안 끝난" 요청. 비행기가 이륙~착륙 전까지 "떠 있는
> (in flight)" 상태에 빗댄 말. 여기선 "지금 배포가 진행 중"을 가리킨다.

push A 직후 push B가 오면:

```
push A --> master: 202 "접수완료" --> (백그라운드) agent에게 배포 시킴
push B --> master: 202 "접수완료" --> (백그라운드) agent에게 배포 시킴
                                            |
                                  agent는 배포 중이면 409로 거절
                                            v
                        B의 배포 = 409로 버려짐. 그런데 push B는
                        이미 202(성공)를 받았다 -> 아무도 실패를 모른다
```

**무엇이 문제인가:** master가 요청 받자마자 202("접수했어요")를 주고 실제 배포는 뒤에서
한다. A·B가 거의 동시에 오면 둘 다 202를 받지만, agent는 하나씩만 배포하므로 B는 거절.
B를 보낸 Actions는 이미 202로 "성공" 처리 → **B 배포가 실제로 안 됐다는 걸 아무도 모른다.**
202가 "접수됨"인데 "배포됨"으로 오해되는 함정.

**어떻게 고쳤나:** master가 "이 서비스 배포 중이야?"를 스스로 추적(서비스별 in-flight).
진행 중이면 **접수 시점에 바로 409** — 뒤늦게 조용히 버리는 게 아니라 부르는 쪽이 즉시 알도록:

```
[변경]  push B --> master: "front 배포 중" 확인 --> 즉시 409 "in progress"
                          (Actions 로그에 빨간불로 바로 보임)
```

**부수 효과:** 요청마다 무한정 백그라운드 작업(goroutine — Go의 경량 실행 단위)을 띄우던
것이 서비스별 최대 1개로 유계(bounded)가 됐다 — 무한정 쌓여 메모리·연결이 고갈되는 위험 제거.
> 원칙: 실패는 시끄러워야 한다. "202=접수"와 "배포됨"은 다르다.

### F5 — 잘못된 커밋 해시가 로그를 오염시키고 엉터리 202를 받았다

```
[기존]  요청 --> master: sha 비었나만 확인 --> 로그에 sha 기록 --> 202 --> agent 전달
                                                                  |
                                        agent가 뒤늦게 정규식 검증 --> 여기서야 거절
```

두 문제: ①**로그 오염** — master가 sha를 검증 없이 로그에 그대로 쓴다. sha에 개행(`\n`)을
섞으면 우리 로그 형식(`requestId:server:message` 한 줄)에 **가짜 줄**을 꽂을 수 있다(로그 주입).
②**엉터리 202** — 틀린 sha도 202를 주고 한참 뒤 agent가 거절(F6과 같은 계열).

**고침:** sha 형식 검증(hex 7~64자)을 **agent가 아니라 master 접수 시점으로 앞당김**.
틀리면 로그·202 전에 422로 거절.

```
[변경]  요청 --> master: sha가 hex 형식인가? --(아니오)--> 즉시 422 (로그도 202도 없음)
                         --(예)--> 로그/202/전달
```

### F7 — "배포 성공"과 "서비스 정상"은 다른 말이었다

당시 agent는 `docker compose up`이 **종료 코드 0**이면 "ok"로 기록했다. 그런데 컨테이너가
떴다는 것과 그 안 서비스가 정상 응답한다는 건 다르다 — 뜨자마자 크래시 루프여도 compose는
"띄웠음(0)"이라 한다.

**고침:** 배포 후 **서비스 헬스 URL을 실제로 찔러본다**(최대 90초 폴링). 200이 와야 진짜 ok.

```
[변경]  compose up (종료 0) --> 서비스 health URL 폴링(90s)
                                 +- 200 -> deploy ok
                                 +- 계속 실패 -> deploy_unhealthy
```

이 기능이 바로 다음 배포에서 실제로 뭔가를 잡아냈다 — 3장.

### F8·F9 (짧게)

- **F8(healthcheck 포트):** master 기본 포트 15000인데 컨테이너 헬스체크가 15001(agent 포트)을
  보고 있어 master가 정상인데도 unhealthy로 찍힘 → MODE별 올바른 포트로 정합.
- **F9(서버 타임아웃):** HTTP 서버에 읽기·유휴 타임아웃이 없어, 느린 연결을 여러 개 열면
  인증 검사에 닿기도 전에 자원을 오래 문다 → read/idle 타임아웃·헤더 크기 상한 명시.

## 3. 헬스체크(F7)의 첫 실전 — backend 배포가 "성공인데 실패"로 잡히다

**상황:** agent(.158, 호스트 네트워크)가 backend 배포 후 `http://127.0.0.1:8090/actuator/health`
(자기 루프백)를 폴링.

**증상:**
```
agent deploy unhealthy backend: health 미도달:
  dial tcp 127.0.0.1:8090: connect: connection refused
```
그런데 backend는 멀쩡했다 — `http://192.168.55.158:8090`(LAN IP)으로는 200.

**진단:**
```
"떠 있는데 127.0.0.1만 거부"
  -> 프로세스는 살아있고 특정 주소로만 안 열림 = 바인딩(binding) 문제
  -> backend compose 확인
  -> 발견: 보안 리뷰 때 넣은 fail-closed 바인딩  ${BIND_ADDR:?}:8090:8090
     = 앱을 LAN IP에만 열고 루프백(127.0.0.1)엔 아예 안 연다
```
> 용어 — 바인딩: 서버가 "어느 주소로 귀를 열지" 정하는 것. `0.0.0.0`=모든 주소,
> `192.168.55.158`=그 IP로만, `127.0.0.1`=자기 자신만. LAN IP에만 바인딩하면 루프백 연결은 거부.

**해결:** agent의 헬스 URL을 127.0.0.1이 아니라 LAN 주소로 교정.

**"두 검증 장치가 서로를 검증했다"의 뜻:**
- backend의 fail-closed 바인딩(보안): "허가된 LAN 주소로만 연다"
- ci-cd의 배포 후 헬스체크(검증): "정말 응답하나 확인한다"

충돌처럼 보이지만, 헬스체크가 **바인딩이 의도대로 걸려 있음을 증명**해줬고(루프백이 정말
막혀 있더라), 동시에 헬스체크가 "compose 성공"을 곧이곧대로 안 믿는다는 것도 실증됐다.
F7이 없었다면 "deploy ok" 로그를 믿고 넘어갔을 것.

## 4. 기각한 지적 — 왜 안 받아들였나 (이것도 기록으로)

### 기각 (1) "ghcr 이미지 방식으로 되돌려라" (리뷰어는 Critical)

리뷰어가 본 명세는 **전환 이전 버전**(리뷰 packet에 옛 명세가 들어감). 실제로는 사용자
결정으로 "git pull + 호스트 재빌드"로 이미 전환 — 코드가 아니라 **명세 문서가 낡았다.**
코드 되돌리는 대신 명세를 최신으로 갱신.

단 리뷰어의 부수 지적은 유효 → **수용 리스크로 명문화**: git-pull 방식은 "저장소 커밋이
compose를 바꿀 수 있다" = 배포 때 실행되는 정의가 커밋 따라 변한다. 감수 근거는
main의 PR 게이트 + 자기 소유 저장소가 신뢰 경계라는 것 — 문서에 "왜 괜찮은지" 남김.

### 기각 (2) "go.mod가 없어 빌드 불가"

`go.mod`(Go 의존성 정의 파일)는 실제로 존재한다 — 내가 **리뷰 packet 만들 때 빠뜨림.**
코드 문제가 아니라 입력 실수. **두 번째** 같은 사고라(front 리뷰 때도 첫 커밋 누락),
"리뷰 자료 자동 검증"이 후속 과제로 확정.

### 이연 (1) HMAC + 타임스탬프 (재전송 방지)

> 용어 — HMAC / 재전송: 지금은 "공유 비밀번호"를 헤더로 붙여 검증한다. HMAC은 "비밀키
> +요청 내용+시각"을 함께 서명해 ①변조 시 깨지고 ②과거 요청 재전송도 시각으로 막는 방식.

현재는 엣지 HTTPS + LAN 전용이라 위험이 낮아 후속으로 이연. 명세 표현도 "HMAC"->
"공유 시크릿"으로 정정(안 한 걸 한 척하지 않기).

## 5. 결론

세 서비스 전부 push->자동 배포가 되는 상태가 됐고, 그 과정에서 배포 서버의 위험한 구멍
6개를 메웠다. 특히 F4(권한 분리)·F7(헬스 확인)은 "배포 서버가 남의 호스트를 만진다"는
본질적 위험에 직접 닿는 수정이었다.
남긴 것: HMAC(후속) · 롤백(sha 이력이 /status에 축적 중) · 리뷰 packet 자기검증. PR #10
