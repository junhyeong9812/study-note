# 애그리게이트 명세 — 양식과 작성법

---

## 1. 목적

**무엇이 함께 변해야 하고, 무엇이 항상 참이어야 하는지를 고정한다.**

애그리게이트(Aggregate)는 **정합성과 트랜잭션의 단위**다. 이 경계가 곧 "한 번에 원자적으로 바뀌는 범위"이고, 그래서 Phase 3의 트랜잭션 설계가 여기서 직접 파생된다.

> **애그리게이트는 저장 단위가 아니다.**
> 테이블과 1:1로 만들면 저장 구조가 도메인을 지배하게 된다. 판단 기준은 오직 **"이 규칙을 지키려면 무엇이 함께 바뀌어야 하는가"** 다.

## 3-B. 묶음 산출물 — `aggregates/README.md` ★★

> 애그리게이트 **파일마다 하나**와 별개로, 묶음 전체에 **하나만** 있는 산출물이 있다.
> 개별 파일에서는 보이지 않는 결함 — **여러 애그리게이트에 걸친 누락** — 은 여기서만 잡힌다.

```markdown
## 트랜잭션 경계

**원칙**: 하나의 트랜잭션은 하나의 애그리게이트만 변경한다.

**의식적 예외 <n>건**

| # | 무엇을 한 트랜잭션으로 | 왜 |
|---|---|---|
| E1 | <조작군> — **<참여자 전체를 빠짐없이>** | <갈리면 무슨 사고가 나나> |

## 변경 매트릭스 ★★

| 조작 | <애그A> | <애그B> | … | **경계** |
|---|:-:|:-:|---|---|
| <조작> `code` | ● | | | **E1** / — (단일) |
```

### 왜 매트릭스가 필요한가

트랜잭션 경계 목록만 있으면 **거기 없는 것을 알아채지 못한다.** 실측:

```
R5  E4가 예외 목록에 아예 없다        → 예외를 신설했다
R6  E4 목록에 회수 대상이 빠졌다       → 참여자를 추가했다
R7  E4 목록에 매입 배치가 빠졌다       → ???
```

**같은 자리, 형태만 바뀌며 네 번.** 리뷰어를 바꿔도 둘로 늘려도 같았다 —
목록은 **빠진 것을 보여주지 않기 때문**이다. 표는 **빈 칸**으로 보여준다.

### 매트릭스는 손으로 쓰지 않는다 ★

| 무엇 | 어디서 생성하나 | 안 지키면 |
|---|---|---|
| **열** | `aggregates/*.md` 파일 목록 | 열이 없는 애그리게이트는 **영원히 검사 대상이 아니다** |
| **행** | 각 파일 §5 조작 표의 코드명 전집 | 빠진 조작은 **영원히 검사 대상이 아니다** |
| **경계 칸** | 예외 목록의 참여자 집합과 `==` 비교 | 참여자를 빠뜨려도 통과한다 |
| **집계 문장** | 표에서 세어 생성 | *"● 2개 이상인 행은 7개"* ← **실제 10개였다** |

> ★ **표를 만드는 것만으로는 부족하다.** 형태만 구조 기반이고 검사가 형식적이면
> **통과 신호가 나오는 만큼 사람 리뷰보다 위험하다.**
> 성립 조건 4가지는 [`verification-by-construction.md`](../verification-by-construction.md).

### 검산 규칙

```
① 열 집합 == aggregates/*.md 목록                    (차집합 0건)
② 행 집합 == Σ 각 문서 §5 조작 코드명                 (차집합 0건)
③ ● 2개 이상인 행 → 경계가 정확히 하나 (0개도 2개도 실패)
④ 각 경계의 참여자 집합 == 그 경계가 붙은 행들의 ● 집합
⑤ 이동·폐기된 심볼(옛 INV 번호, 폐기 필드)이 0건
```

## 4. 작성법

### 불변식 찾는 법

**"이 두 값이 동시에 바뀌지 않으면 무엇이 깨지는가?"** 를 물으면 나온다.

| 유형 | 예 |
|---|---|
| **합계 제약** | 누적 취소액 ≤ 원거래 금액 |
| **균형 제약** | 차변 합계 = 대변 합계 |
| **상태 정합** | 상태가 완료면 완료일시가 반드시 있다 |
| **범위 제약** | 잔액은 음수가 될 수 없다 |
| **참조 무결** | 취소는 반드시 원거래를 가리킨다 |

**불변식은 애그리게이트 안에서만 검증 가능해야 한다.** 검증하려고 다른 애그리게이트를 조회해야 한다면:
- 경계가 잘못됐거나
- 그건 불변식이 아니라 **프로세스 규칙**(정책)이다

> ⚠️ **둘 중 어느 쪽인지 반드시 판정한다.** 판정 없이 "프로세스 규칙"으로 넘기는 것이 기본값이 되면 아래 §합계 필드 문제가 그대로 통과한다.

### 교차 애그리게이트 술어 분류 ★★

**애그리게이트 밖을 읽어야 참·거짓을 알 수 있는 명제**는 INV로 두면 안 된다. 넷 중 하나로 분류한다.

| 분류 | 언제 | 어디에 적나 | 언제 검증되나 |
|---|---|---|---|
| **불변식 (INV)** | 이 애그리게이트 안에서만 검증 가능 | §3 불변식 | **모든 조작 후** |
| **사전조건 (PRE)** | 특정 조작 진입 시 밖을 조회해 확인 | §3 사전조건 | 그 조작 진입 시 |
| **사후조건** | 조작이 끝난 뒤 참이어야 하나 밖과 함께 성립 | §5 조작 표 | 그 조작 종료 시 |
| **대사 불변식** | 여러 애그리게이트에 걸쳐 있고 **실시간 검증 불가** | §3에 **별도 표**로 | **대사·정합성 배치** |

#### 왜 나눠야 하는가

`INV`는 정의상 **모든 조작 후 참**이다. 밖을 읽어야 아는 명제를 INV로 적으면:

| 문제 | 결과 |
|---|---|
| 매 조작마다 밖을 조회해야 한다 | 실시간 경로가 다른 애그리게이트에 종속된다 |
| **검증이 사실상 안 일어난다** | 문서에만 있는 규칙 — 구조가 막아주지 않는다 |
| 어긋나는 구간을 **인정하지 못한다** | "어긋날 수 없다"고 단언하고 탐지를 안 만든다 |

> ⚠️ **가장 흔한 실수는 "대사 불변식"을 INV로 적는 것이다.** 그러면 *"이건 항상 참"* 이라고 선언하면서 정작 **아무도 검사하지 않는** 상태가 된다. 실시간 검증이 불가능하면 그 사실을 표에 드러내야 한다.

#### 자기 점검

```
이 명제를 "모든 조작 후" 검증하려면 무엇이 필요한가?
  → 이 애그리게이트 필드만으로 된다      → INV
  → 특정 조작 전에 한 번만 조회하면 된다  → PRE
  → 그 조작이 끝날 때 함께 성립한다       → 사후조건
  → 매번은 불가능하고 배치로만 가능하다   → 대사 불변식 (탐지 장치를 반드시 명시)
```

### 합계 필드 판정 ★★

**한 애그리게이트가 다른 애그리게이트들의 합을 필드로 드는 경우** — 이것을 그냥 두면 안 된다.

```
계좌.holdTotal    = Σ(승인별 홀딩)
계좌.receivable   = Σ(승인별 잔여미수)
배치.processedCnt = |처리된 레코드|
```

이런 필드는 **저장된 값과 실제 합이 어긋날 수 있고, 그것을 막는 것이 애그리게이트 안에 없다.** "다른 쪽이 막아준다"는 설명은 **구조가 아니라 약속**이다.

#### 왜 반드시 깨지는가

| 깨지는 경로 | 예 |
|---|---|
| **이미 반영된 것을 또 반영** | 만료로 이미 푼 홀딩을 지연 매입이 또 해제 → 남의 점유가 깎인다 |
| **한쪽만 반영** | 개별 값은 0이 됐는데 합계를 줄이는 경로가 없다 → 유령 잔량 |
| **부분 집합에만 적용되는 규칙** | 일부를 제외해야 하는데(보류 등) 합계는 그것을 구분 못 한다 |

> **셋 다 에러가 나지 않는다.** 숫자만 조용히 틀린다.

#### 판정 — 셋 중 하나를 반드시 고른다

| # | 선택 | 언제 | 대가 |
|---|---|---|---|
| **①** | **파생값으로 바꾼다** (저장하지 않는다) | 읽기 빈도가 낮거나 구성 요소가 적을 때 | 읽을 때마다 조회 |
| **②** | **별도 애그리게이트로 분리** | 그 값 자체가 생명주기·상태를 가질 때 | 애그리게이트 수 증가 |
| **③** | **의식적 예외로 등재** | 실시간 경로라 조회 비용을 못 감당할 때 | **아래 세 가지를 전부 적어야 한다** |

**③을 고르면 반드시 함께 적는다:**

1. **등식을 불변식으로 명시** — `합계 필드 = Σ(구성 요소)` 를 어느 문서 어느 INV에 두는가
2. **그 등식이 성립하는 트랜잭션 경계** — 합계와 구성 요소가 **같은 커밋**에서 바뀌는가, 아니면 어긋나는 구간이 있는가
3. **어긋남을 잡는 장치** — 대사·정합성 배치 등. **없으면 ③을 고를 수 없다**
4. ★ **우변의 부분집합을 고를 키** — *"그 영업일의"*, *"그 기준일의"* 처럼 **범위가 붙은 등식**은
   그 범위를 표현하는 **필드가 실재해야** 계산할 수 있다

> ★ **4번은 두 번 걸려서 추가됐다.** 정산 합계는 *"C3 영업일 버킷"* 을 정본으로 지목했는데
> 그런 버킷이 없었고(DC-002), 한도 복원은 *"해당 기준일"* 을 되돌린다면서 그 날짜를 든 필드가
> 없었다(DC-003). **둘 다 우변의 소유자는 처음부터 있었고, 부분집합을 고를 키가 없었다.**

### 상한을 쓸 때 묻는 네 가지 ★★

*"상한을 적었는데 좌변이 어디에도 없다"* 가 이 프로젝트에서 **다섯 번** 나왔다
(미수 · 환불 · 입금 정정 · 정산 합계 · `SETTLED` 환불).

```
① 좌변(누계·합계)을 **누가** 드는가      — 이름을 못 대면 상한은 없는 것이다
② 그 값이 **언제** 바뀌는가              — 종료 상태에서도 바뀌어야 하는가
③ 우변을 계산할 **정본이 실재**하는가     — "그런 버킷"은 정본이 아니다
④ 우변의 **부분집합을 고를 키**가 있는가  — 범위가 붙은 등식은 그 범위를 든 필드가 필요하다
```

> ★ **"다른 애그리게이트의 상태가 막아준다"는 ③의 근거가 될 수 없다.** 그건 등식도 경계도 탐지도 아니다. 실제로 그렇게 처리한 필드는 **예외 없이 자금 사고를 냈다.**

#### 자기 점검

```
이 필드를 저장하는 대신 매번 계산하면 무엇이 안 되는가?
  → 답이 "성능"뿐이면 ③이고, 위 세 가지를 적어야 한다
  → 답이 안 나오면 ①이다 (저장할 이유가 없다)
  → 그 값에 상태·수명·개별 규칙(보류 등)이 붙는다면 ②다
```

### 부수 효과를 `〃`로 적지 않는다 ★★

전이·조작 표의 부수 효과 열에서 **앞 행과 같다는 뜻의 `〃`**(ditto)를 쓰지 않는다.
길어지더라도 **매번 풀어 쓴다.**

이 프로젝트에서 `〃`가 **네 라운드 연속으로 결함을 만들었다**:

| 라운드 | 무엇을 복사했나 | 결과 |
|---|---|---|
| 1차 | 만료 전이가 승인취소의 *"홀딩 전액 해제"* | 이미 풀린 홀딩을 또 해제 → **초과 승인** (치명) |
| 3차 | 부분 환불이 전액 환불의 *"대응 미수 소멸"* | 부분 환불이 미수를 전액 소멸 → **채권 손실** (치명) |
| 4차 | 미수 전이 2건 | 조건이 다른데 효과가 같아짐 |

> **조건이 한 줄 다르면 부수 효과도 다르다.** `〃`는 *"같다"* 를 주장하는데,
> 그 주장을 **검증하는 사람이 아무도 없다** — 쓰는 사람은 같다고 믿고, 읽는 사람은 확인하지 않는다.
>
> ★ **이 규칙을 써 놓고 같은 문서에서 두 번 더 어겼다.** 규칙만으로는 안 되고
> **grep 한 줄이 검사에 들어가야 한다** (`〃` 0건).

### 번호를 옮기면 잔재를 검사한다 ★

`INV-10`을 대사 불변식 `RC-1`로 옮기는 것 같은 **재분류**는 한 곳만 고치면
**옛 번호와 옛 내용이 다른 곳에 남는다.**

실측: INV-10을 RC-1으로 옮기면서 상한을 `withdrawnAmount` →
`withdrawnAmount + 미수.recoveredAmount`로 넓혔는데, **필드 설명에는 옛 상한과
옛 번호가 그대로 남았다.** 그대로 구현하면 미수를 갚은 고객이 그만큼 못 돌려받는다.

```
옮긴 뒤 반드시:  grep -c 'INV-10' → 0 이어야 한다
                 (0이 아니면 아직 안 옮긴 것이다)
```

### 경계 정하는 법

```
① 불변식을 먼저 나열한다
② 각 불변식이 "무엇과 무엇이 동시에 참이어야 하는가"를 본다
③ 그 최소 묶음이 애그리게이트다
```

**크기 판단 기준**:

| 증상 | 진단 | 대응 |
|---|---|---|
| 동시 요청이 자주 충돌한다 | 너무 크다 | 불변식을 다시 보고 쪼갠다 |
| 규칙이 애플리케이션 서비스에 새어 있다 | 너무 작다 | 함께 참이어야 하는 것을 합친다 |
| 한 트랜잭션에서 여러 애그리게이트를 바꾼다 | 경계가 틀렸거나 프로세스가 필요 | 이벤트/Saga로 분리 |

> **원칙: 하나의 트랜잭션은 하나의 애그리게이트만 변경한다.**
> 이걸 지킬 수 없다면 경계를 다시 본다. 정말 필요하면 **의식적으로 예외로 기록**한다.

### 다른 애그리게이트 참조

**반드시 ID로만 참조한다.**

| 나쁜 예 | 좋은 예 |
|---|---|
| `private Account account;` | `private AccountId accountId;` |

객체 참조를 두면:
- 로딩 범위가 애그리게이트를 넘어간다
- 남의 애그리게이트를 바꿀 수 있게 된다
- 트랜잭션 경계가 흐려진다

### 조작(커맨드) 쓰는 법

**사전조건 / 사후조건을 반드시 채운다.** 이게 그대로 테스트가 된다.

```
| 부분취소 | cancelPartially | 상태가 정산완료가 아니다 | 누적취소액이 요청분만큼 증가 | PartiallyCancelled |
```

**조작 이름은 도메인 언어로.** `setStatus`, `update` 같은 이름은 도메인 개념이 아니다.

### 값 객체 판별

| 애그리게이트/엔티티 | 값 객체 |
|---|---|
| **식별자로 구분** | **값으로 구분** |
| 값이 바뀌어도 같은 것 | 값이 바뀌면 다른 것 |
| 생명주기가 있다 | 없다 |
| 계좌, 승인 | 금액, 이메일, 카드번호 |

**값 객체는 불변으로 만든다.** 그러면 공유해도 안전하고 검증을 생성 시점에 한 번만 하면 된다.

### 의문을 닫는 법 — 선택지와 기각 이유를 남긴다

의문이 결정되면 표에서 지우지 말고 **닫힌 의문**으로 옮긴다. 이때 **결론만 적으면 안 된다.**

| 남길 것 | 왜 |
|---|---|
| **검토한 선택지 전부** | 나중에 "이건 왜 안 했나"가 반드시 다시 나온다. 그때 재검토 비용을 없앤다 |
| **기각 이유** | 채택 이유보다 **기각 이유가 더 오래 쓸모 있다.** 상황이 바뀌면 기각 이유가 아직 유효한지만 확인하면 된다 |
| **어떤 규칙·불변식이 됐는가** | 결정이 코드로 강제되는 지점을 가리킨다 |

결정이 **업무 규칙 수준**이면 `01-business-rules.md`에 BR로 승격하고, 애그리게이트 문서에는 **선택지와 이유**를 남긴다. 규칙 본문은 한 곳(BR), 결정 과정은 한 곳(애그리게이트) — 중복하지 않는다.

> **분기를 규칙으로 적기 전에 한 번 의심한다.** "A이면 X, B이면 Y"로 보이는 것이 사실은 **한 문장으로 쓰면 결과로 갈라지는** 경우가 많다. 분기를 규칙에 적으면 A/B 판정 자체가 경합 지점이 된다.

## 5. 흔한 실수

| # | 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|---|
| 1 | **불변식이 없다** | 애그리게이트가 아니라 데이터 묶음이다 | 불변식을 못 찾으면 애그리게이트로 만들지 않는다 |
| 2 | **테이블 = 애그리게이트** | 저장 구조가 도메인을 지배한다 | "함께 변해야 하는가"로만 판단 |
| 3 | **객체로 다른 애그리게이트 참조** | 경계가 무너진다 | ID 참조로 바꾼다 |
| 4 | **너무 크게 잡음** | 락 경합으로 동시성이 죽는다 | 불변식이 요구하는 최소로 |
| 5 | **조작 이름이 CRUD** | 도메인 의도가 사라진다 | 업무 언어로 (`승인한다`, `해제한다`) |
| 6 | **불변식 검증에 외부 조회 필요** | 애그리게이트 안에서 못 지킨다 | 경계를 다시 보거나 정책으로 분리 — **어느 쪽인지 판정한다** |
| 10 | ★ **밖을 읽어야 아는 명제를 INV로 적음** | "항상 참"이라 선언하면서 정작 아무도 검사하지 않는다 | 교차 애그리게이트 술어 분류 4종 중 하나로 |
| 11 | ★ **등식을 적었는데 우변을 계산할 정본이 없음** | 탐지가 실행 불가 — ③이 성립하지 않는다 | 구성 요소의 소유 위치를 대거나, 못 대면 ②로 |
| 7 | ★ **다른 애그리게이트들의 합계를 필드로 들고 "저쪽이 막아준다"로 넘김** | 구조가 아니라 약속이다. 조용히 틀린다 | **합계 필드 판정** 3안 중 하나를 고르고, ③이면 등식·경계·탐지를 적는다 |
| 12 | ★ **부수 효과를 `〃`로 적음** | 조건이 다른데 효과가 복사된다 — 4라운드 연속 결함 | 매번 풀어 쓴다. `〃` 0건을 검사에 넣는다 |
| 13 | ★ **번호를 옮기고 옛 번호가 남음** | 두 개의 다른 계약이 공존한다 | 옮긴 뒤 옛 번호 grep 0건 |
| 14 | ★ **집계 수치를 손으로 씀** | *"● 2개 이상인 행 7개"* ← 실제 10개 | 표에서 세어 생성한다 |
| 8 | **사전/사후조건 빈칸** | 테스트할 것이 불명확 | 반드시 채운다 |
| 9 | **의문을 닫으면서 결론만 남김** | 몇 달 뒤 같은 논의를 처음부터 다시 한다 | 선택지와 **기각 이유**를 함께 남긴다 |

## 6. 완료 기준

- [ ] **불변식이 최소 1개** 있고, 각각 근거 규칙(BR-nn)이 연결돼 있다
- [ ] 모든 불변식이 **이 애그리게이트 안에서 검증 가능**하다
- [ ] 다른 애그리게이트 참조가 **전부 ID**다
- [ ] 모든 조작에 **사전조건·사후조건**이 있다
- [ ] 조작 이름이 **도메인 언어**다 (CRUD 아님)
- [ ] **경계 근거 4문항**(왜 이 범위 / 왜 더 크지 않은가 / 왜 더 작지 않은가 / 트랜잭션 단위인가)이 채워져 있다
- [ ] 값 객체와 엔티티가 구분돼 있다
- [ ] 용어사전의 코드명과 **일치**한다
- [ ] 닫힌 의문에 **선택지와 기각 이유**가 남아 있다 (결론만 있는 것은 미완)
- [ ] **다른 애그리게이트들의 합계를 필드로 드는 것이 있는지** 훑었고, 있다면 ①②③ 중 하나로 판정했다
- [ ] ③(의식적 예외)을 골랐다면 **등식·트랜잭션 경계·어긋남 탐지**가 전부 적혀 있다
- [ ] ★ **등식의 우변을 계산할 정본이 실재하는가** — 구성 요소가 어느 애그리게이트의 어느 필드인지 댈 수 있어야 한다. 못 대면 탐지가 실행 불가이므로 ③이 성립하지 않는다
- [ ] ★ **트랜잭션 경계가 그 필드를 바꾸는 경로를 전부 덮는가** — 생성만 덮고 해제·복원을 빠뜨리지 않았는가
- [ ] §3의 각 명제가 **INV / PRE / 사후조건 / 대사 불변식** 중 무엇인지 분류돼 있다
- [ ] 부수 효과 열에 **`〃`가 0건**이다
- [ ] 번호를 옮겼다면 **옛 번호가 문서 전체에 0건**이다
