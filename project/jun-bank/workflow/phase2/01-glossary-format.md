# 용어사전 — 양식과 작성법

---

## 1. 목적

**하나의 개념에 하나의 이름을 고정한다.**

DDD에서 말하는 **유비쿼터스 언어(Ubiquitous Language)** 를 문서로 만든 것이다. 대화·문서·코드·DB·API가 **같은 단어를 같은 뜻으로** 쓰게 만드는 것이 전부다.

> **이게 없으면 벌어지는 일**
> 같은 개념이 코드에서 `amount`, `price`, `money`, `value` 로 흩어진다. 그 순간 "이 둘이 같은 건가?"를 매번 확인해야 하고, 결국 값 객체가 여러 벌로 복제된다.

---

## 2. 독자

| 독자 | 이 문서에서 얻는 것 |
|---|---|
| 모든 문서 작성자 | 쓸 단어 |
| 구현자 | 클래스·필드·API·이벤트 이름 |
| 신규 합류자 | 도메인 입문서 |
| 리뷰어 | "이 이름이 맞나"의 기준 |

## 4. 작성법

### 무엇을 넣는가

| 넣는다 | 넣지 않는다 |
|---|---|
| 업무 개념 (계좌, 승인, 전표) | 기술 용어 (Kafka, JPA, DTO) |
| 업무에서 쓰는 약어 | 일반 영어 단어 |
| 혼동되는 개념 쌍 | 사전에 있는 상식 |
| 컨텍스트별로 뜻이 다른 단어 | |

**기준**: **도메인 전문가가 쓰는 말**인가? 그렇다면 넣는다. 개발자만 쓰는 말이면 안 넣는다.

### 정의 쓰는 법

**한 문장으로, 다른 용어에 의존하지 않게.**

| 나쁜 예 | 좋은 예 |
|---|---|
| 승인: 승인 처리하는 것 | 승인: 지불 능력을 확인하고 해당 금액을 점유하는 절차. **이 시점에 자금은 이동하지 않는다** |
| 홀딩: 홀딩된 금액 | 홀딩: 승인으로 인해 가용잔액에서 차감된 금액. 매입되면 확정되고 만료되면 해제된다 |

**요령**: 정의 뒤에 **"~가 아니다"** 를 붙이면 경계가 선명해진다.

### 코드명 붙이는 법

| 원칙 | 예 |
|---|---|
| 한글 개념 ↔ 영문명이 **1:1** | 승인 → `Authorization` (`Approval` 과 혼용 금지) |
| 업계 표준 용어가 있으면 그것을 쓴다 | 매입 → `Capture` (직역 `Purchase` 아님) |
| **약어를 만들지 않는다** | `AuthTx` ❌ → `Authorization` ✅ |
| 복수형·단수형을 정한다 | 테이블은 복수, 클래스는 단수 |

**코드명이 정해지지 않은 용어는 코드에 등장할 수 없다.** 이게 이 문서의 강제력이다.

### 🔒 불변식 표시

**그 용어에 지켜야 할 규칙이 붙어 있으면 🔒를 단다.** 이 표시가 Phase 2-4 애그리게이트 명세로 이어진다.

```
| **전표** 🔒 | `JournalEntry` | 하나의 거래를 표현하는 기록 단위. **차변 합계 = 대변 합계**여야 한다 |
```

### ⚠️ 혼동 주의 표시

**실무에서 자주 틀리는 것**을 명시적으로 경고한다. 이 표시 하나가 나중에 버그 여러 개를 막는다.

```
> ⚠️ **가장 흔한 오해**: "승인 = 결제 완료". 아니다. 승인만 되고 매입되지 않은 거래는 만료되어 소멸한다.
```

### 분류하는 법

용어가 20개를 넘으면 분류가 필요하다. **업무 흐름을 따라** 나눈다.

일반적으로 잘 맞는 분류:
- 참여자 (누가)
- 라이프사이클 (무엇이 언제 일어나는가)
- 정정·예외 (무엇이 잘못될 수 있는가)
- 값·수량 (무엇을 세는가)
- 기록·증빙 (무엇이 남는가)
- 식별자 (무엇으로 구분하는가)
- 시간·주기 (언제)

### 컨텍스트별로 뜻이 다른 용어

**통일하려 하지 마라.** 같은 단어가 컨텍스트마다 다른 뜻인 것은 정상이며, 그게 바로 **경계가 존재한다는 증거**다.

```
| 계좌 | 뱅킹 컨텍스트: 고객의 예금 계좌 | 원장 컨텍스트: 회계 계정과목 | 원장 쪽은 LedgerAccount 로 구분 |
```

이 표가 **Phase 2-3 컨텍스트 맵의 번역 계층(ACL) 설계 근거**가 된다.

## 5. 흔한 실수

| # | 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|---|
| 1 | **기술 용어가 섞임** | 도메인 언어가 아니다 | 도메인 전문가가 쓰는 말만 남긴다 |
| 2 | **정의가 순환** ("승인: 승인하는 것") | 아무것도 설명하지 않는다 | 상위 개념 + 구별점으로 다시 쓴다 |
| 3 | **코드명이 없다** | 번역이 매번 달라진다 | 모든 용어에 영문명을 붙인다 |
| 4 | **한 개념에 코드명이 여럿** | 코드에서 같은 것이 다른 이름으로 존재하게 된다 | 하나를 정하고 나머지는 "쓰지 않음"으로 명시 |
| 5 | **컨텍스트 차이를 무시하고 통일** | 억지로 합친 개념이 어느 쪽에서도 안 맞는다 | 차이를 인정하고 번역 규칙을 정한다 |
| 6 | **모델링 후에 작성** | 이미 이름이 흩어진 뒤라 정리 비용이 크다 | **모델링 전에** 작성한다 |
| 7 | **한 번 쓰고 갱신 안 함** | 코드와 갈라진다 | 새 용어는 코드보다 먼저 여기에 |

## 6. 완료 기준

- [ ] 모든 용어에 **코드명(영문)** 이 있다
- [ ] 모든 정의가 **한 문장**이고 순환하지 않는다
- [ ] **혼동되는 쌍**이 별도 표에 정리돼 있다
- [ ] 불변식이 있는 용어에 **🔒 표시**가 있다
- [ ] 컨텍스트별로 뜻이 다른 용어가 **명시**돼 있다
- [ ] 아직 정의 못 한 용어가 **별도 절에 모여 있다**
- [ ] 도메인을 모르는 사람이 이 문서만 읽고 **핵심 흐름을 설명할 수 있다**
