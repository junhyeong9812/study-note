# 이벤트 스토밍 — 양식과 작성법

---

## 1. 목적

**"무슨 일이 일어나는가"를 나열해서 애그리게이트와 바운디드 컨텍스트를 도출한다.**

이벤트 스토밍(Event Storming)은 알베르토 브란돌리니(Alberto Brandolini)가 만든 워크숍 기법이다. 원래는 벽에 포스트잇을 붙이며 여럿이 하지만, **혼자서도 같은 순서로 사고하면 같은 결과를 얻는다.**

**핵심 발상**: 데이터(명사)가 아니라 **사건(동사)** 에서 출발한다. 데이터에서 출발하면 DB 테이블 설계가 되고, 사건에서 출발하면 도메인 모델이 된다.

---

## 2. 독자

| 독자 | 이 문서에서 얻는 것 |
|---|---|
| 설계자 | 애그리게이트·컨텍스트 후보 |
| 구현자 | 도메인 이벤트 목록 |
| 리뷰어 | "이 흐름에 빠진 게 없나"의 점검표 |

---

## 3. 양식

> 복사해서 `docs/domain/event-storming.md` 로 붙인다.

```markdown

- 작성일: <YYYY-MM-DD>
- 상태: 작성중 | 검토대기 | 확정
- 입력: `product/00-product-definition.md` §5 시나리오
- 산출: 애그리게이트 후보 · 바운디드 컨텍스트 후보
```

## 4. 작성법

### 순서 — 이 순서를 지킨다

```
① 도메인 이벤트 나열      "~되었다" — 과거형으로, 떠오르는 대로
② 시간순 정렬             흐름이 드러난다. 여기서 빠진 이벤트가 보인다
③ 커맨드 붙이기           각 이벤트를 일으킨 의도
④ 액터 붙이기             그 커맨드를 누가 발생시키는가
⑤ 정책 찾기               "~하면 자동으로 ~한다" — 이벤트와 커맨드 사이의 규칙
⑥ 읽기 모델 찾기          커맨드를 판단하려면 무엇을 알아야 하는가
⑦ 애그리게이트 묶기        같은 규칙으로 함께 변하는 것끼리
⑧ 컨텍스트 묶기           같은 용어가 같은 뜻으로 통하는 범위로
⑨ 핫스팟 표시             애매한 지점을 빨간색으로 남긴다
```

**⑦⑧을 먼저 하려 하지 마라.** 이벤트를 충분히 나열하기 전에 묶으면 기존 선입견(또는 기존 코드 구조)대로 묶게 된다.

### ① 이벤트 나열 — 형식

**과거형, 도메인 언어로.**

| 나쁜 예 | 좋은 예 |
|---|---|
| 결제 처리 | 결제가 승인되었다 |
| INSERT INTO payment | 승인 내역이 기록되었다 |
| 사용자 정보 업데이트 | 연락처가 변경되었다 |

**기술 이벤트를 넣지 않는다.** "메시지가 발행되었다", "트랜잭션이 커밋되었다"는 도메인 이벤트가 아니다.

**빠뜨리기 쉬운 이벤트**:
- **실패 이벤트** — "승인이 거절되었다", "잔액이 부족했다"
- **시간 기반 이벤트** — "홀딩이 만료되었다", "마감 시각이 도래했다"
- **외부에서 오는 이벤트** — "정산 파일이 수신되었다"
- **취소·정정 이벤트** — "승인이 취소되었다"

> **경험칙**: 성공 흐름만 있으면 절반도 못 쓴 것이다. **실패와 정정이 도메인의 본론**인 경우가 많다.

### ⑤ 정책 (Policy)

**"~하면 ~한다"** 형태의 자동 반응. 사람이 개입하지 않고 일어나는 것.

```
결제가 승인되었다  →  [정책] 원장에 홀딩 전표를 기록한다
홀딩 만료 시각이 되었다  →  [정책] 홀딩을 해제한다
```

정책은 나중에 **이벤트 핸들러 / Saga 단계**가 된다. **동기여야 하는지 비동기여도 되는지**를 여기서 표시해두면 Phase 3 트랜잭션 설계가 쉬워진다.

### ⑦ 애그리게이트 묶기

**기준은 "함께 변하는가"가 아니라 "함께 변해야만 규칙이 지켜지는가"다.**

| 질문 | 예 |
|---|---|
| 이 둘이 **동시에** 바뀌지 않으면 깨지는 규칙이 있는가? | 승인과 홀딩: 승인 생성 없이 홀딩만 생기면 안 됨 → 같은 애그리게이트 후보 |
| 잠깐 어긋나도 되는가? | 승인과 알림: 알림이 늦어도 규칙이 안 깨짐 → 다른 애그리게이트 |

**크기 판단**:
- **너무 크면**: 락 범위가 커져 동시성이 죽는다
- **너무 작으면**: 불변식을 지킬 수 없어 규칙이 서비스로 샌다

> **원칙**: **불변식이 요구하는 최소 범위**로 만든다.

### ⑧ 컨텍스트 묶기

**기술이 아니라 언어로 나눈다.**

| 나쁜 경계 | 좋은 경계 |
|---|---|
| 조회 컨텍스트 / 배치 컨텍스트 | 결제 컨텍스트 / 원장 컨텍스트 |
| API 서버 / 워커 | 뱅킹 컨텍스트 / 카드 컨텍스트 |

**경계를 발견하는 신호**:
- 같은 단어가 **다른 뜻**으로 쓰인다 → 경계가 그 사이에 있다
- 한쪽 규칙이 바뀌어도 **다른 쪽이 안 바뀐다** → 다른 컨텍스트
- 다루는 **액터가 다르다** → 다른 컨텍스트일 가능성

### ⑨ 핫스팟 🟥

**애매한 것을 애매한 채로 남기는 것이 이 기법의 핵심 가치다.**

핫스팟으로 표시할 것:
- "이건 누가 결정하지?"
- "이 경우엔 어떻게 되지?"
- "이 둘이 같은 건가 다른 건가?"

**핫스팟을 그럴듯하게 채우면 그 추정이 구현까지 간다.** 빨간색으로 남기고 `결정 필요`로 올린다.

## 5. 흔한 실수

| # | 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|---|
| 1 | **명사(데이터)부터 시작** | DB 설계가 된다 | 이벤트(동사)부터 |
| 2 | **성공 흐름만 나열** | 도메인의 절반이 빠진다 | 실패·취소·만료 이벤트를 찾는다 |
| 3 | **기술 이벤트를 섞음** | 도메인 모델이 인프라에 오염된다 | "커밋되었다", "발행되었다" 제거 |
| 4 | **기존 코드 구조대로 묶음** | 기존 잘못이 그대로 재생산된다 | 코드를 보지 않고 이벤트만 보고 묶는다 |
| 5 | **핫스팟을 채워버림** | 추정이 구현까지 간다 | 🟥로 남긴다 |
| 6 | **애그리게이트를 테이블로 봄** | 저장 구조에 끌려간다 | "함께 변해야 하는가"만 본다 |
| 7 | **컨텍스트를 기술로 나눔** | 경계가 도메인과 무관해진다 | 용어 체계로 나눈다 |
| 8 | **한 번에 완성하려 함** | 진도가 안 나간다 | 확신도(높음/중간/낮음)를 붙이고 넘어간다 |

## 6. 완료 기준

- [ ] 제품 정의서의 **모든 시나리오(S<n>)** 가 다뤄졌다
- [ ] **실패·취소·만료 이벤트**가 포함돼 있다
- [ ] 모든 이벤트에 **커맨드와 액터**가 붙어 있다
- [ ] **정책(자동 반응)** 이 별도로 식별돼 있고 동기/비동기가 표시됐다
- [ ] 애그리게이트 후보마다 **함께 변해야 하는 이유(불변식)** 가 적혀 있다
- [ ] 컨텍스트 후보마다 **경계 근거**가 적혀 있다
- [ ] **핫스팟이 채워지지 않고 남아 있다** (하나도 없으면 대개 대충 한 것이다)
- [ ] 확신도가 낮은 항목이 표시돼 있다
