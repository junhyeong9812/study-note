# 토대 변경 절차 (Design Change)

> **이미 합의된 설계를 되돌려 다시 쪼개는 절차.** 개별 결함을 고치는 것(패치)과 다르다.
>
> 이 절차는 **어느 Phase에서도 발동**할 수 있다. Phase 순서를 벗어나 앞 단계 산출물을 여는 유일한 정식 경로다.

---

## 1. 왜 별도 절차가 필요한가

리뷰에서 결함이 나오면 고친다. 그게 정상이다. **그런데 고친 자리가 또 깨지면, 고치는 행위 자체가 문제를 감춘다.**

| 패치 | 토대 변경 |
|---|---|
| 이 결함을 없앤다 | **이 결함이 계속 나오는 구조**를 없앤다 |
| 지적된 곳을 본다 | **왜 그 자리만 반복해서 지적되나**를 본다 |
| 리뷰 라운드 안에서 끝난다 | 라운드를 **멈추고** 시작한다 |

> **핵심**: 패치를 반복하는 동안에는 "고쳐지고 있다"는 신호가 계속 나온다. 라운드마다 결함 수가 줄어들기까지 한다. **그 신호가 토대 문제를 가장 오래 숨긴다.**

---

## 2. 발동 조건 ★

**하나라도 해당하면 패치를 멈추고 이 절차로 들어간다.**

| # | 조건 | 왜 이것이 신호인가 |
|---|---|---|
| **T1** | **같은 자리를 2회 이상 고쳤는데 또 깨진다** | 고친 것이 증상이었다는 뜻이다 |
| **T2** | 리뷰 라운드마다 **같은 뿌리**에서 결함이 나온다 | 뿌리를 안 건드리고 가지만 쳤다 |
| **T3** | 어떤 불변식을 **사람이 지켜야 한다** — 구조가 막아주지 않는다 | 규칙을 문서에만 적어 둔 상태 |
| **T4** | 어떤 선택지를 기각한 근거가 **채택한 안에도 그대로 적용된다** | 기각이 실제로는 성립하지 않았다 |
| **T5** | 한 결함을 고치면 **다른 곳이 깨지는 것이 반복**된다 | 책임이 잘못 나뉘어 있다 |
| **T6** | 수정이 **새 결함을 만든 비율**이 라운드마다 줄지 않는다 | 손대는 면적이 문제의 크기를 넘었다 |

> **T4가 가장 놓치기 쉽다.** 결정을 내릴 때 쓴 기각 근거를, 채택안이 실제로 어떻게 구현되는지 본 뒤에 다시 읽어야 드러난다.

### 발동 조건이 아닌 것

- 결함이 많다 — 개수는 신호가 아니다. **분포**가 신호다.
- 리뷰가 어렵다 — 어려운 도메인은 원래 어렵다.
- 더 나은 설계가 떠올랐다 — **지금 것이 실제로 실패하고 있어야** 한다.

---

## 3. 절차

```
① 패치 중단          진행 중인 수정을 멈춘다. 미적용 findings는 보류로 표시
② 실패 이력 수집      라운드별로 "어디가 깨졌나"를 표로
③ 공통 뿌리 지목      그 실패들이 공유하는 단 하나의 결정을 특정
④ 기각 근거 재심      과거에 그 뿌리를 이렇게 정한 이유가 아직 유효한가 (T4)
⑤ 대안과 영향 범위    선택지 + 각각이 여는 문서 수
⑥ 사용자 합의        ★ 여기서 멈춘다. 자율 진행 금지
⑦ 변경 실행          기준소스부터 — 규칙 → 애그리게이트 → 상태 머신 순
⑧ 기존 findings 재판정 ★ 토대가 바뀌면 일부는 무효가 된다
⑨ 재리뷰             ②의 실패 이력이 재현되지 않는지 확인
⑩ 반증 신호 채점 ★   ⑤에서 등록한 "실현되면 무엇을 보나"를 판정
```

### ⑥에서 멈추는 이유

토대 변경은 **되돌리기 비싼 결정**이다. 앞 Phase 산출물을 열고, 이미 합의된 규칙을 바꾸고, 사용자가 이미 답한 질문의 답을 무효로 만들 수도 있다. **자율 실행 대상이 아니다.**

### 단계마다 커밋한다 ★

⑦은 여러 문서를 순서대로 여는 단계다. **한 번에 몰아 커밋하면 안 된다.**

| 몰아 커밋하면 | 단계별 커밋하면 |
|---|---|
| 어느 단계에서 무엇이 깨졌는지 되짚을 수 없다 | 실패 지점이 커밋 하나로 좁혀진다 |
| 중간에 멈추면 **일관성 없는 상태**가 남는다 | 어느 커밋에서 멈춰도 그 단계까지는 정합 |
| 리뷰어가 diff를 통째로 받는다 | 기준소스 변경과 파생 변경을 **따로** 검토할 수 있다 |

> **커밋 단위 = 변천 문서 §7의 행 하나.** §7 표에 커밋 해시를 적어 두면, 나중에 "이 규칙이 언제 왜 바뀌었나"가 문서와 이력 양쪽에서 추적된다.

### ⑦의 커밋은 실제 diff를 확인하고 쓴다 ★

**커밋 메시지에 "무엇을 바꿨다"고 적기 전에 `git diff`로 실제 변경을 확인한다.**

문서 수정은 문자열 치환으로 하는 일이 많고, **대상 문장이 이미 바뀌어 있으면 치환이 조용히 실패**한다. 그때 커밋 메시지만 남으면:

| 결과 | 왜 치명적인가 |
|---|---|
| 정본에 없는 것을 파생 문서가 참조 | *"이 목록에 없는 것은 예외가 아니다"* 같은 선언이 깨진다 |
| **변천 문서 §7이 ✅인데 실제로는 안 바뀜** | 다음 리뷰가 그 자리를 다시 지적하고, 이력은 이미 완료라고 말한다 |
| 단계별 커밋의 목적이 무효 | **추적하려고 나눴는데 커밋을 믿을 수 없다** |

> **바꿨다고 주장하는 문장을 커밋 전에 한 번 grep한다.** 30초면 된다.

#### 치환은 **실패를 검출하도록** 쓴다

이 프로젝트에서 **같은 치환이 두 번 조용히 실패했다** — 단계 2와 단계 10b에서 같은 문장을 고쳤다고 커밋해 놓고 둘 다 안 바뀌었다.

| 왜 실패했나 | 대응 |
|---|---|
| **여러 줄을 한 덩어리로 치환** — 그중 한 줄이 이미 다르면 전체가 안 맞는다 | **한 줄씩** 치환한다 |
| 치환 결과를 확인하지 않음 | **치환 전에 대상이 실재하는지 단언**하고, 후에 결과를 grep한다 |
| 커밋 후에 검사 | **커밋 전에** 한다 — 커밋된 거짓 이력은 다음 라운드까지 남는다 |

> **"바꾼 뒤 사라져야 할 문자열"을 grep해서 0건인지 본다.** 있으면 치환이 실패한 것이다.

#### 손으로 고치지 말고 **표로 만들어 기계 검산한다** ★

이 프로젝트에서 **여섯 라운드 동안 손으로 고치며 매번 한 곳씩 빠뜨렸다.** 여섯 번째 리뷰가 내린 진단은 *"반복되는 것은 설계가 아니라 **동기화**다"* 였고, 처방은 **빈 칸이 곧 결함인 표**였다.

| 표 | 무엇을 잡나 |
|---|---|
| **변경 매트릭스** (조작 × 애그리게이트) | 2개 이상 켜진 행이 트랜잭션 경계에 매핑되는가 — **참여자 누락** |
| **폐기 심볼 목록** | 없어진 필드·이벤트·번호가 계약 문서에 0건인가 — **잔재** |
| **판정 체크리스트** | 각 대상에 요구 항목이 전부 채워졌는가 — **형식적 충족** |

> ★ **표를 만든 뒤에는 스크립트로 돌린다.** 사람이 표를 읽으며 확인하면 그것도 손으로 고치는 것과 같다.
>
> **성립 조건과 한계는 [verification-by-construction.md](../verification-by-construction.md)** — 표를 만드는 것만으로는 부족하고, **행·열을 문서에서 생성**하고 **각 칸을 정본과 대조**해야 한다. 형태만 구조 기반이면 **거짓 안심**을 주어 사람 리뷰보다 위험하다.
>
> **판정 기준**: 문서 리뷰가 잡아낸 결함이 *"목록에서 하나 빠졌다"* 계열로 수렴하면, 그건 **사람 리뷰를 한 번 더 돌릴 문제가 아니라 검산을 기계화할 문제**다.

### ⑧이 이 절차의 고유 단계다 ★

토대를 바꾸면 **기존 findings의 상당수가 저절로 사라진다.** 재판정 없이 목록대로 고치면:

| 판정 | 뜻 | 처리 |
|---|---|---|
| **소멸** | 그 결함이 **존재할 구조가 없어졌다** | 고치지 않는다. **소멸했다는 사실을 기록**한다 |
| **잔존** | 토대와 무관하게 여전히 결함 | 고친다 |
| **변형** | 같은 문제가 다른 형태로 남았다 | **새 finding으로 다시 쓴다** — 옛 서술을 고치면 안 된다 |

> **소멸을 기록하지 않으면 다음 리뷰가 같은 것을 또 지적한다.** "이건 이미 없앴다"의 근거가 변천 문서다.

#### ⚠️ 소멸 판정의 함정 — **메커니즘 소멸 ≠ 결과 소멸**

지적된 **경로**가 사라졌다고 **결과**까지 사라진 것은 아니다.

```
원 지적:  "T15가 SETTLED에서 열려 있어 소멸한 채권을 회수한다"
수정:      T15를 제거했다
잘못된 판정: "T15가 없으니 소멸"
실제:      SETTLED 환불이 refund()를 안 타므로 미수가 OPEN으로 남고
           후속 입금이 회수한다 — 같은 결과, 다른 경로  → 변형
```

**판정 질문은 "그 메커니즘이 있는가"가 아니라 "그 나쁜 결과에 도달하는 경로가 하나라도 남았는가"다.**

| 이렇게 물으면 틀린다 | 이렇게 물어야 한다 |
|---|---|
| 지적된 코드·전이·필드가 아직 있나? | **그 사고가 일어나는 시나리오를 하나라도 구성할 수 있나?** |

> **소멸 판정에는 반드시 "이 결과에 도달할 경로가 없다"의 근거를 적는다.** 경로 부재를 못 보이면 **변형**이다.

---

### ⑩ 반증 신호 채점 ★

⑤에서 *"안고 가는 위험 — 실현되면 무엇을 보나"* 를 적는다. **그 기준을 채점하는 단계가 없으면 등록이 무의미하다.**

```
⑤에 적은 신호마다:
  발화했나?  →  아니오  →  아직 유효, 다음 라운드로
             →  예     →  판정한다 (아래 셋 중 하나)
```

| 판정 | 뜻 | 처리 |
|---|---|---|
| **기각** | 발화했으나 다른 근거로 결정이 유지된다 | **그 근거를 적는다** — 안 적으면 무시한 것과 같다 |
| **수용** | 신호가 맞았다 — 결정을 되돌리거나 좁힌다 | 새 변천 문서 또는 이 문서의 후속 단계 |
| **보류** | 아직 판단할 데이터가 없다 | 언제 다시 볼지 적는다 |

> ⚠️ **채점하지 않은 반증 기준은 다음 토대 변경에서 반복된다.** 신호를 세워 두는 이유는 *"내가 틀렸을 때 알아채기 위해서"* 인데, 채점을 안 하면 **틀렸어도 모른 채 지나간다.** 그러면 그 기준은 장식이다.

## 4. 산출물

| 무엇 | 어디에 | 언제 |
|---|---|---|
| **변천 문서** (`DC-nnn`) | `docs/design-changes/` | ②~⑧ 전 과정을 여기 쓴다 |
| **단계별 커밋** | git | ⑦ — §7 표의 행마다 하나. 해시를 표에 적는다 |
| 기준소스 수정 | 해당 Phase 산출물 | ⑦ |
| 각 문서 변경 이력 1행 | 수정된 문서 | ⑦ — `DC-nnn` 참조 |
| **§9 검증 결과** · **반증 신호 채점표** | 변천 문서 | ⑨·⑩ |

**변천 문서는 결정이 아니라 과정을 남긴다.** 결정만 남기면 다음에 같은 자리에서 또 흔들릴 때 "그때 왜 이렇게 정했나"를 재구성할 수 없다.

## 5. ADR과 무엇이 다른가

| | ADR | 변천 문서 |
|---|---|---|
| 언제 | **결정할 때** | 이미 한 결정이 **실패했을 때** |
| 무엇을 남기나 | 선택지와 근거 | **실패 이력** + 뿌리 진단 + 선택지와 근거 |
| 범위 | 하나의 결정 | 그 결정이 **퍼진 모든 문서** |
| 후속 | 없음 | **기존 findings 재판정**(⑧) |

> 토대 변경도 결정이므로 ADR을 함께 남길 수 있다. 다만 **실패 이력과 재판정은 ADR 양식에 자리가 없다** — 그래서 별도 문서다.

## 6. 흔한 실수

| # | 실수 | 왜 문제인가 |
|---|---|---|
| 1 | **발동 조건을 확인하지 않고 시작** | "더 나은 설계"는 발동 조건이 아니다. 실제로 실패하고 있어야 한다 |
| 2 | 실패 이력을 **요약해서** 적음 | 라운드별 원문이 있어야 뿌리가 보인다. 요약하면 "비슷한 문제들"로 뭉뚱그려진다 |
| 3 | **⑥ 없이 진행** | 되돌리기 비싼 결정을 혼자 내린 것 |
| 4 | **⑧을 건너뛰고** 기존 findings를 그대로 소화 | 이미 사라진 결함을 고치느라 새 결함을 만든다 |
| 5 | 상태 머신부터 고침 | 기준소스(규칙)가 안 바뀐 채 파생 문서만 바뀌면 **다음 리뷰가 원복을 요구**한다 |
| 6 | 변천 문서에 **결정만** 남김 | 다음에 같은 자리가 흔들릴 때 재구성 불가 |
| 7 | **전 단계를 한 커밋으로** | 실패 지점을 못 좁히고, 중간에 멈추면 일관성 없는 상태가 남는다 |
| 8 | ★ **커밋 메시지를 실제 diff 확인 없이 씀** | 치환이 조용히 실패하면 **정본은 안 바뀌었는데 이력은 완료라고 말한다.** 이 프로젝트에서 같은 치환이 **두 번** 실패했다 |
| 9 | ★ **메커니즘이 사라진 것을 결과가 사라진 것으로 판정** | 결함이 목록에서 지워진 채 다른 경로로 살아 있다 |
| 10 | ★ **반증 신호를 등록만 하고 채점하지 않음** | 틀렸어도 모른 채 지나간다 — 그 기준은 장식이 된다 |
| 11 | ★ **"목록 누락" 계열 결함을 사람 리뷰로 반복** | 매번 한 곳씩 빠뜨린다. **검산을 기계화할 문제**를 리뷰로 풀려는 것 |

## 7. 완료 기준

- [ ] 발동 조건(§2) 중 **어느 것에 해당하는지** 변천 문서에 적혀 있다
- [ ] 실패 이력이 **라운드별·원문 인용**으로 있다
- [ ] 공통 뿌리가 **하나의 결정**으로 특정돼 있다
- [ ] 과거 기각 근거를 **다시 읽고 판정**했다 (T4)
- [ ] 사용자 합의가 기록돼 있다
- [ ] 기존 findings가 **소멸 / 잔존 / 변형**으로 전부 재판정됐고, **소멸에는 "그 결과에 도달할 경로가 없다"의 근거**가 있다
- [ ] 수정 순서가 **기준소스 → 파생** 이었다
- [ ] **단계마다 커밋**했고 §7 표에 해시가 적혀 있다
- [ ] 영향받은 모든 문서에 `DC-nnn` 참조가 남았다
- [ ] **커밋 메시지가 실제 diff와 일치**한다 — **커밋 전에** "사라져야 할 문자열"을 grep해 0건 확인
- [ ] 결함이 "목록에서 하나 빠졌다" 계열로 수렴하면 **표 + 스크립트로 기계 검산**했다
- [ ] ⑤에 등록한 **반증 신호를 전부 채점**했다 (발화 여부 · 기각이면 근거)
