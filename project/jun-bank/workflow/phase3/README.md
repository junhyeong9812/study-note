# Phase 3 — 아키텍처 설계

> **입력이 비어 있으면 이 Phase는 시작할 수 없다.**
> 근거: 『아키텍트 첫걸음』 3장

---

## 목적

**되돌리기 어려운 결정을 근거와 함께 내린다.**

Phase 2는 *"무엇이 있는가"* 를 정했다. Phase 3은 *"그것을 어떤 구조로 실행하는가"* 를 정한다.
클래스는 나중에 바꿀 수 있지만 **서비스 경계·데이터 저장 위치·통신 방식**은 그렇지 않다.

---

## 선행 조건 (없으면 시작하지 않는다)

| # | 입력 | 어디서 | 왜 필요한가 |
|---|---|---|---|
| 1 | **컨텍스트 맵** (경계 · 관계 유형 · 데이터 소유권) | Phase 2 | 서비스 분할의 **유일한 근거**다. 없으면 기술적 직관으로 나뉜다 |
| 2 | **애그리게이트 + 트랜잭션 경계** | Phase 2 | 한 트랜잭션이 서비스를 넘으면 안 된다 — 분할이 이것을 지켜야 한다 |
| 3 | **제품 정의서의 범위 밖** | Phase 1 | 안 만들 것에 아키텍처를 쓰지 않는다 |
| 4 | **Phase 2 인계 문서** | Phase 2 | 열린 의문 중 **수치 미확정**이 이 Phase에서 근거를 얻는다 |

### 순서를 지키는 이유

```
제약        선택지를 좁힌다        ← 이것 없이 품질을 논하면 못 고를 안을 논한다
  ↓
품질 속성    무엇을 포기하는지 정한다 ← 이것 없이 ADR을 쓰면 "좋아 보여서" 고른다
  ↓
품질 시나리오 측정 방법을 정한다      ← 이것 없이 결정하면 검증할 수 없다
  ↓
ADR         근거를 남기고 결정한다
  ↓
뷰·기술서    결정을 전달한다
```

> ⚠️ **가장 흔한 순서 오류는 ADR부터 쓰는 것이다.** 그러면 근거 칸에
> *"확장성이 좋아서"* 같은 말이 들어가고, **그것을 반증할 방법이 없다.**

## 완료 기준

| # | 기준 | 왜 |
|---|---|---|
| 1 | **되돌리기 어려운 결정에 전부 ADR이 있다** | 없으면 왜 그랬는지 몇 달 뒤 아무도 모른다 |
| 2 | 각 ADR에 **기각한 대안과 기각 이유**가 있다 | 결론만 있으면 같은 논의를 처음부터 다시 한다 |
| 3 | 각 ADR에 **되돌리는 조건**이 비어 있지 않다 | 되돌릴 수 없는 결정은 없다. 조건을 안 적으면 못 되돌린다 |
| 4 | 각 품질 속성에 **품질 시나리오가 최소 1개** 있다 | 측정할 수 없는 품질은 선언일 뿐이다 |
| 5 | 각 품질 시나리오에 **수치와 측정 방법**이 있다 | *"빠르게"* 는 시나리오가 아니다 |
| 6 | **포기한 품질**이 명시돼 있다 | 다 잘하겠다는 것은 아무것도 안 고른 것이다 |
| 7 | 서비스 분할이 **컨텍스트 맵에서 도출**됐다 | 기술적 직관으로 나누면 나중에 못 고친다 |
| 8 | **한 트랜잭션 경계가 서비스를 넘지 않는다** | 넘으면 분산 트랜잭션이 되고, Phase 2가 막으려던 사고가 돌아온다 |
| 9 | Phase 2 인계의 **수치 미확정 항목**이 품질 시나리오에서 근거를 얻었다 | 근거 없는 상수가 코드에 박히는 것을 막는다 |

### 완료 기준이 **아닌** 것

> **"모든 기술을 정했다"는 완료 기준이 아니다.**

Phase 3은 **되돌리기 어려운 것**만 정한다. 라이브러리 선택·프레임워크 버전처럼
**나중에 바꿀 수 있는 것**은 Phase 5~7에서 정한다.

| 지금 정한다 | 나중에 정한다 |
|---|---|
| 서비스 경계 · 데이터 소유 위치 | ORM · 로깅 라이브러리 |
| 동기/비동기 · 통신 방식 | 메시지 브로커 제품 |
| 일관성 모델 (강함/최종) | 커넥션 풀 크기 |
| 배포 단위의 수 | CI 도구 |

## 흔한 실패

| 실패 | 증상 | 대응 |
|---|---|---|
| **컨텍스트 = 서비스로 자동 매핑** | 컨텍스트 6개니까 서비스 6개 | 컨텍스트는 **모델 경계**, 서비스는 **배포·운영 단위**다. 하나가 여럿을 담을 수 있다 |
| **품질 속성을 다 채택** | *"성능·확장성·가용성·보안 전부 중요"* | 포기할 것을 못 고르면 **아무것도 안 고른 것**이다 |
| **수치 없는 시나리오** | *"응답이 빨라야 한다"* | 자극·측정 지점·수치·환경을 채운다 |
| **ADR에 기각 대안 없음** | 결론만 있다 | 고려한 안과 **왜 안 골랐는지**를 남긴다 |
| **되돌리는 조건 빈칸** | *"이 결정은 최종"* | 최종인 결정은 없다. 무엇이 관찰되면 다시 여는지 적는다 |
| ★ **트랜잭션 경계를 쪼갬** | 서비스를 나누다 E2가 둘로 갈렸다 | Phase 2의 경계가 **분할의 제약**이다. 못 지키면 분할을 바꾼다 |

## 이 Phase가 다음 Phase에 넘기는 것

```
서비스 분할 + 통신 방식   ──▶ Phase 4 계약(API·이벤트) 설계
품질 시나리오             ──▶ Phase 9 성능·가용성 테스트의 기준
ADR                       ──▶ 전 Phase (왜 이렇게 하는지의 근거)
일관성 모델               ──▶ Phase 5 애플리케이션 기반 구현
아키텍처 뷰               ──▶ Phase 6 개발자용 문서
```

**넘어가지 않는 것**: 클래스 구조, 패키지 배치, 함수 시그니처. 그것은 Phase 4~5의 일이다.
