## 왜 지금 양식을 안 만드나

각 Phase의 양식은 **그 Phase의 입력이 확정된 뒤에** 만든다.
지금 Phase 4~6 양식을 쓰면 **Phase 3이 정하지 않은 것을 전제**하게 되고,
그것은 이 프로젝트가 Phase 2에서 열 라운드에 걸쳐 겪은 실패와 같은 형태다.

> ★ **특히 Phase 5는 "미리 만들면 안 되는" 이유가 구조적이다.**
> 기반이 없으면 유스케이스를 못 만들고, 유스케이스가 없으면 **어떤 기반이 필요한지 모른다**.
> 그래서 **샘플 유스케이스 하나를 끝까지 얇게** 구현하며 기반이 드러나게 한다(Walking Skeleton).
> **기반 12종을 목록으로 먼저 만들면 안 쓰는 것을 만들게 된다.**

## Phase 5 — 애플리케이션 기반

### 공통 기능 후보 (12종)

인증 · 승인(인가) · 세션 · 오류 처리 · 로깅 · 보안 · **트랜잭션 제어** ·
**데이터베이스 접근** · 국제화 · 문서 출력 · 캐시 관리 · **비동기 처리**

> ⚠️ **목록이지 계획이 아니다.** 샘플 유스케이스가 요구하지 않은 것은 만들지 않는다.
> 굵은 넷은 이미 Phase 2·3이 요구를 만들어 둔 것들이다.

### 이미 확정된 요구가 붙어 있는 것

| 기반 | 어디서 온 요구 |
|---|---|
| **트랜잭션 제어** | 트랜잭션 경계 E1~E5가 **한 커밋**이어야 한다 (Phase 2) |
| **데이터베이스 접근** | ★ 아래 §"읽기/쓰기 혼용" 참조 — **정합성 1순위와 직결** |
| **비동기 처리** | 원장 기표는 별도 논리 단위이되 **유실되지 않아야** 한다 (BR-40) · Outbox |
| **로깅** | 탐지가능성 4순위. 단 실시간 관측은 포기(D-05) — **사후 추적이 목적** |
| **오류 처리** | 승인 거절 사유가 **구분**되어야 한다 (BR-15 · BR-36) |

### ★ 읽기/쓰기 혼용 — Phase 3 ADR로 올라간 항목

논의에서 나온 것 중 **이것만 Phase 5가 아니라 Phase 3 결정**이다.

```
같은 트랜잭션 안에서 ORM 쓰기 + JDBC 직접 조회를 섞으면
  → 영속성 컨텍스트가 flush되기 전에 JDBC가 DB를 직접 읽는다
  → JPQL/QueryDSL-JPA는 실행 전 자동 flush되지만 JdbcTemplate은 그 흐름 밖이다
  → 변경 전 데이터를 읽는다
```

**왜 Phase 3인가**: 이것은 스타일 문제가 아니라 **자금 판단이 오래된 값으로 이뤄지는 경로**다.
가용잔액을 JDBC로 읽고 홀딩을 ORM으로 쓰면 **초과 승인**이 난다 — Phase 2가 열 라운드에 걸쳐
막은 바로 그 사고다. 복제본 라우팅도 같은 범주이며, `HA-1`(*인스턴스 로컬 상태로 자금 판단 금지*)의
연장선이다.

| 정해야 할 것 | 후보 |
|---|---|
| E1~E5 트랜잭션 안에서 JDBC 직접 조회를 허용하는가 | 금지 / 명시적 flush 강제 |
| 조회 트랜잭션을 어떻게 분리하는가 | `readOnly` 별도 트랜잭션 |
| 자금 판단 조회를 복제본에서 하는가 | Primary 강제 라우팅 |
| **규약을 문서로 둘 것인가 구조로 막을 것인가** | ★ **문서로 둔 규약은 사문화된다** |

> ★ **마지막 행이 이 프로젝트의 결론이다.** Phase 2 실측 —
> **주의력에 의존하는 규칙은 지켜지지 않는다.** 타입·아키텍처 테스트로 막을 수 있으면 그렇게 한다.

### 조회 기술 선택 (Phase 5 — 지금 정하지 않는다)

논의에서 정리된 판단 기준만 남긴다.

| 관찰 | 내용 |
|---|---|
| 조립 방식은 병목이 아니다 | QueryDSL vs 문자열 조합의 **조립 비용은 마이크로초** |
| 실제 지배 변수 | **생성된 SQL의 품질·인덱스** · Entity vs DTO Projection · **페이징 방식**(offset vs 커서) |
| QueryDSL의 실질 이유 | 타입 안정성보다 **동적 조건 조립·재사용**. 조건 3개 이하면 불필요, 10개 넘으면 가치가 벌어진다 |
| 대가 | Q클래스 생성(APT) 빌드 이슈 · 복잡한 조인/윈도우함수에서 가독성 하락 · **DBA가 코드를 못 읽는다** |
| 실무 절충 | 고정 대형 조회는 정적 SQL · 동적 검색은 QueryDSL · 통계는 전용 뷰/집계 테이블 |

> **성능이 아니라 유지보수 비용으로 고르는 도구다.** 배타적 선택이 아니므로 혼용이 표준이 된다.

## Phase 6 — 개발자용 문서 (3계층)

**셋을 한 문서에 섞는 것이 가장 흔한 실패다.** 그러면 *"이건 필수인가 권장인가"* 가 불분명해진다.

| 구분 | 성격 | 강제력 | 위반 시 |
|---|---|---|---|
| **개발 규약** | 지켜야 할 것 (What) | 필수 | 리뷰 반려 / 빌드 실패 |
| **절차서** | 수행 순서 (How-to) | 준수 | 재작업 |
| **구현 참고자료** | 권장·예시 (Reference) | 참고 | 없음 |

| 문서 | 내용 |
|---|---|
| **코딩 규약** | 포맷 · 예외처리 · 로깅 방식 · 금지 패턴(`System.out`, 빈 catch, 하드코딩) |
| **명명 규약** | 패키지·클래스·메서드·변수·DB 객체·API URI·오류코드·로그키 |
| **형상 관리 규약** | 브랜치 전략 · 커밋 메시지 · PR 규칙 · 리뷰 승인 기준 · 버전·태그 |
| **개발 환경 구축 절차서** | 설치 목록·버전 · 설정값 · **검증 방법**(*"여기까지 되면 성공"*) |
| **도구 이용 절차서** | 형상관리 · 이슈트래커 · CI/CD · 정적분석 · 배포·롤백 |
| **구현 가이드라인** | 공통기능 사용법 · 레이어별 책임 |
| **튜토리얼** | 신규 인력이 따라 하며 CRUD 한 건 완성 |

### 추가 후보

DB 표준(용어사전·도메인) · API 설계 규약 · 테스트 규약 · 보안 코딩 규약

### ★ 실효성 — 문서로만 있는 규약은 사문화된다

**기계가 강제할 수 있는 항목은 문서에서 도구로 옮긴다.**

| 규약 | 도구로 |
|---|---|
| 코딩 규약 | 포맷터 설정 파일 + 정적분석 룰셋 (수동 점검 ✗) |
| 명명 규약 | 린트 룰 / DB 표준화 도구 |
| 형상 관리 규약 | PR 템플릿 · 브랜치 보호 규칙 · 커밋 훅 |
| 환경 구축 절차서 | **스크립트·컨테이너로 대체** — 문서는 절차 설명만 |

> ★ **이것이 `verification-by-construction.md`와 같은 결론이다.**
> Phase 2에서 검산 스크립트로 옮긴 것과 정확히 같은 이유다 — **셀 수 있는 것은 세게 한다.**

### 리버스 엔지니어링으로 표준을 뽑는다

**규약을 먼저 쓰고 코드를 맞추는 것이 아니라, 참조 구현에서 규약을 뽑는다.**
