# 비즈니스 규칙서 — 양식과 작성법

---

## 1. 목적

**업무 규칙을 번호가 붙은 독립 항목으로 관리한다.**

규칙이 여러 문서에 흩어져 서술되면 반드시 갈라진다. 한 곳에 번호를 붙여 모아두고, 다른 문서는 **참조만** 한다.

> **규칙(rule)과 요구사항(requirement)은 다르다.**
> - 요구사항: "잔액을 조회할 수 있어야 한다" — 시스템이 **하는 일**
> - 규칙: "가용잔액은 계좌잔액에서 홀딩을 뺀 값이다" — 업무가 **참이라고 정한 것**
>
> 이 문서는 **규칙**만 다룬다.

---

## 2. 독자

| 독자 | 이 문서에서 얻는 것 |
|---|---|
| 도메인 모델러 | 애그리게이트 불변식의 원천 |
| 구현자 | 코드에 들어갈 판단 조건 |
| 테스트 작성자 | 검증할 대상과 경계값 |
| 리뷰어 | "이 코드가 규칙을 지키는가"의 기준 |

## 4. 작성법

### 규칙 문장 쓰는 법

**"~해야 한다"가 아니라 "~이다"로 쓴다.** 규칙은 명령이 아니라 **참인 명제**다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 잔액을 잘 관리해야 한다 | 가용잔액은 계좌잔액에서 홀딩 합계를 뺀 값이다 |
| 취소를 적절히 처리한다 | 누적 취소액은 원거래 금액을 초과할 수 없다 |
| 빠르게 응답해야 한다 | 승인 응답은 요청 수신 후 3초 이내에 반환된다 |

**검증 가능해야 한다.** "적절히", "충분히", "가능한 한" 같은 말이 들어가면 규칙이 아니다.

### 분류

규칙을 성격별로 나누면 **어디에 구현될지**가 드러난다.

| 분류 | 예 | 어디에 구현되나 |
|---|---|---|
| **계산 (Computation)** | 가용잔액 = 계좌잔액 − 홀딩 | 도메인 모델 메서드 |
| **제약 (Constraint)** | 취소액 ≤ 원거래 금액 | 도메인 불변식 |
| **상태 전이 (Transition)** | 정산 완료 건은 취소 불가 | 상태 머신 |
| **권한 (Authorization)** | 본인 계좌만 조회 가능 | 인가 계층 |
| **시간 (Temporal)** | 마감 이후 거래는 다음 영업일 귀속 | 도메인 + 배치 |
| **파생 (Derivation)** | 연체 여부는 결제일 경과로 판단 | 도메인 |

### 수치는 반드시 근거와 함께

| 나쁜 예 | 좋은 예 |
|---|---|
| 타임아웃 5초 | 타임아웃 3초 — **근거**: 상대 시스템 타임아웃이 5초이므로 여유를 두어 3초 |
| 한도 100만원 | 1일 한도 100만원 — **근거**: 미정. 업계 관행 참고 필요 → 미확정 수치 표에 등재 |

**근거를 못 쓰면 그 수치는 미확정이다.** "일단 5초로 하자"는 것도 정직하게 "임시값"이라고 적는다.

### 예외를 반드시 적는다

**예외가 없는 규칙은 거의 없다.** "예외 없음"이라고 명시적으로 적는 것과, 빈칸으로 두는 것은 다르다.

```
| **예외** | 없음 (확인함) |
| **예외** | 관리자 강제 처리 시 BR-15에 따라 우회 가능 |
```

### 검증 방법

**이 규칙이 지켜지는지 어떻게 확인할 것인가**를 미리 적는다. 이게 나중에 테스트가 된다.

```
| **검증 방법** | 동시 승인 요청 후 승인 합계 ≤ 가용잔액 검산 |
| **검증 방법** | 전표 시산 결과 차변 합 = 대변 합 |
```

**검증 방법을 못 쓰는 규칙은 규칙이 아니라 희망이다.**

### 규칙 간 충돌

규칙이 늘면 반드시 충돌한다. 충돌을 **발견 즉시 표에 기록하고 우선순위를 정한다.**

예:
- BR-03 "홀딩은 7일 후 자동 해제된다" ↔ BR-09 "분쟁 중인 거래는 상태를 변경하지 않는다"
- → 분쟁 중이면 BR-09 우선. 근거: 분쟁 처리 중 자동 해제는 자금 손실 위험

## 5. 흔한 실수

| # | 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|---|
| 1 | **규칙을 여러 문서에 서술** | 반드시 갈라진다 | 여기에만 두고 다른 곳은 BR-nn 참조 |
| 2 | **번호를 재사용** | 예전 문서의 BR-05가 다른 규칙을 가리키게 된다 | 번호는 **영구 고정**. 폐기해도 번호는 비워둔다 |
| 3 | **"~해야 한다"로 씀** | 검증할 수 없다 | "~이다"로 바꾼다 |
| 4 | **수치에 근거가 없음** | 나중에 아무도 못 바꾼다 (왜 그 값인지 모르니까) | 근거 또는 "임시값" 명시 |
| 5 | **요구사항과 섞임** | 규칙 목록이 기능 목록이 된다 | "업무가 참이라고 정한 것"만 남긴다 |
| 6 | **예외 칸이 빈칸** | 예외가 없는 건지 안 쓴 건지 모른다 | "없음 (확인함)"이라고 명시 |
| 7 | **충돌을 방치** | 구현 시점에 임의로 한쪽을 택하게 된다 | 충돌 표에 등재하고 우선순위 결정 |

---

## 6. 완료 기준

- [ ] 모든 규칙에 **고유 번호(BR-nn)** 가 있다
- [ ] 모든 규칙이 **검증 가능한 명제**다 — 권장 어미는 "~이다/~된다/~하지 않는다". "~해야 한다"처럼 **당위만 서술해 참·거짓을 판정할 수 없는 문장은 금지**
- [ ] 모든 수치에 **근거** 또는 "임시값" 표시가 있다
- [ ] 모든 규칙에 **예외 칸이 채워져 있다** (없으면 "없음"이라고 명시)
- [ ] 모든 규칙에 **검증 방법**이 있다
- [ ] 발견된 **규칙 간 충돌이 표에 기록**되어 있고 우선순위가 정해졌다
- [ ] 미확정 수치가 **별도 표에 모여 있다**
- [ ] 제품 정의서의 시나리오(S<n>)와 **상호 참조**되어 있다
