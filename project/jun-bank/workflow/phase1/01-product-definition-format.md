# 제품 정의서 — 양식과 작성법

---

## 1. 목적

**"이 시스템은 무엇이고, 어디까지가 우리 일인가"에 답한다.**

이 문서 하나로 아래 질문에 답할 수 있어야 한다:

- 한 문장으로 이 시스템은 무엇인가?
- 누가 쓰는가?
- 무엇을 하고, **무엇을 하지 않는가**?
- 어떤 규칙 아래 동작하는가?

---

## 2. 독자

| 독자 | 이 문서에서 얻는 것 |
|---|---|
| 설계자 | 도메인 경계와 서비스 분할의 출발점 |
| 개발자 | "이건 우리가 할 일인가"의 판단 근거 |
| 신규 합류자 | 시스템의 전체 그림 |
| 미래의 나 | 3개월 뒤 "왜 이걸 범위 밖으로 뒀지"의 답 |

---

## 3. 양식

> 아래를 복사해서 `docs/product/00-product-definition.md` 로 붙인 뒤 채운다.
> **`<>` 로 표시된 곳이 채울 자리다. 빈 채로 남기지 말고 "미정"이라고 쓰거나 `결정 필요`로 올린다.**

```markdown

- 작성일: <YYYY-MM-DD>
- 상태: 작성중 | 검토대기 | 확정
- 이 문서의 역할: 이후 모든 문서의 기준점. 여기서 정해지지 않은 것은 아래 층에서 임의로 정하지 않는다.

## 1. 한 줄 정의

<이 문장에서 가장 중요한 단어가 무엇인지, 왜 그 단어인지 2~3줄로>

## 2. 포지션 — 전체 생태계에서 어디에 서 있는가

```
<외부 액터>          <시스템>          <외부 시스템>
    │                   │                   │
    └───── 무엇을 ──────┴───── 무엇을 ──────┘
```

**이 포지션을 고른 이유**:
1. <근거 1>
2. <근거 2>

**이 포지션이 확정하는 경계**:
- <이 포지션이면 자동으로 범위 밖이 되는 것>

> **결정 필요 #<n>**: <포지션이 미확정이면 여기에>

## 3. 범위

### 3.1 범위 안 (In Scope)

| 영역 | 내용 |
|---|---|
| <영역> | <무엇을 하는가> |

### 3.2 범위 밖 (Out of Scope)

- <하지 않는 것> — <왜 안 하는가>
- <하지 않는 것> — <왜 안 하는가>

> ★ **범위 밖이 범위 안보다 중요하다.** "안 한다"가 적혀 있지 않으면 언젠가 하게 된다.

---

## 4. 액터

| 액터 | 유형 | 설명 | 주요 관심사 |
|---|---|---|---|
| <이름> | 사람 / 외부 시스템 / 배치 | <누구인가> | <무엇을 걱정하는가> |

> 사람이 아닌 액터(배치, 스케줄러, 외부 시스템)를 빠뜨리지 않는다.

## 5. 핵심 시나리오

각 시나리오는 **액터가 무엇을 달성하려는가**로 쓴다. 화면·API가 아니다.

### S1. <시나리오 이름>
<2~3줄 서술>
`[이 시나리오가 불러오는 기술적 문제]`

### S2. <시나리오 이름>
…

> 시나리오 뒤의 `[ ]`는 **이 시나리오가 어떤 설계 문제를 요구하는지** 적는다.
> Phase 3에서 "영향력 있는 기능 요구사항"을 고를 때 이 표시가 근거가 된다.

| # | 이름 | 상태 |
|---|---|---|
| BR-01 | <규칙 이름> | 확정 / 초안 / 미정 |

## 7. 이 프로젝트의 목표와의 매핑 (선택)

> 학습·실험이 목적인 프로젝트라면, **각 시나리오가 어떤 학습 대상을 불러오는지** 표로 남긴다.

| 목표 | 요구하는 시나리오 | 없으면 벌어지는 일 |
|---|---|---|
| <기법·개념> | S<n> | <구체적 실패> |
```

## 4. 작성법

### §1 한 줄 정의

**"누구에게 / 무엇을 / 어떻게" 세 요소가 들어가야 한다.**

| 나쁜 예 | 왜 나쁜가 |
|---|---|
| "최신 기술을 활용한 금융 플랫폼" | 누가 쓰는지, 무엇을 하는지 없음 |
| "MSA 기반 은행 시스템" | **기술이 정의에 들어갔다.** 기술은 Phase 3의 결론이지 제품의 정의가 아니다 |

| 좋은 예 |
|---|
| "고객에게 계좌와 카드를 발급하고, 그 카드로 발생한 결제를 승인·정산·기록하는 리테일 은행" |

**요령**: 문장을 쓴 뒤 **가장 중요한 동사에 밑줄**을 쳐 본다. 그 동사가 시스템의 핵심 책임이다.

### §2 포지션

**우리가 생태계의 어느 자리에 서는가.** 같은 도메인이라도 자리가 다르면 완전히 다른 시스템이 된다.

- 결제 도메인: 발급사 / 매입사 / PG / VAN / 브랜드사
- 커머스: 판매자 / 중개 플랫폼 / 물류
- 구독: 서비스 제공자 / 결제 대행

**포지션을 정하면 범위가 자동으로 상당 부분 결정된다.** 그래서 범위보다 먼저 쓴다.

### §3 범위

**범위 밖부터 쓴다.** 범위 안은 쓰기 쉽고 계속 늘어나지만, 범위 밖은 의식적으로 쓰지 않으면 절대 안 적힌다.

각 항목에 **"왜 안 하는가"**를 붙인다. 이유 없이 "안 함"만 적으면 나중에 "그건 왜 안 했더라?"가 되고, 결국 다시 논의된다.

> **"나중에 할 것"과 "안 할 것"은 다르다.** 나중에 할 것은 범위 밖이 아니라 **후속 단계**로 표시한다.

### §4 액터

**빠뜨리기 쉬운 액터 유형**:

| 유형 | 예 |
|---|---|
| 외부 시스템 | 연동 상대, 파일을 보내오는 쪽 |
| **배치·스케줄러** | 사람이 아니지만 시스템을 움직인다 |
| 운영자 | 장애·예외를 처리하는 사람 |
| **간접 이해관계자** | 직접 쓰지 않지만 결과에 영향받는 사람 |

각 액터의 **관심사(concern)** 를 함께 적는다. 이것이 Phase 3의 품질 속성으로 이어진다.

### §5 핵심 시나리오

**형식**: `<액터>가 <목적>을 위해 <무엇>을 한다.`

| 나쁜 예 | 좋은 예 |
|---|---|
| 사용자 목록 조회 API | 운영자가 이상 거래를 찾기 위해 거래 내역을 검색한다 |
| 결제 테이블에 INSERT | 매입사가 보낸 승인 요청을 판단해 승인 또는 거절한다 |

**개수**: 5~10개. 너무 많으면 추상화 수준이 낮은 것이다(기능 목록이 되고 있다).

**각 시나리오 뒤에 `[기술적 문제]` 표시를 붙인다.** 예: `[분산 트랜잭션 / 멱등성]`. 이게 Phase 3에서 "아키텍처를 좌우하는 기능"을 고르는 근거가 된다.

### §6 비즈니스 규칙

**번호와 이름만 둔다. 규칙 문장·수치를 복사하지 않는다.**

복사하면 반드시 갈라진다. 규칙서의 수치가 바뀌었는데 여기가 안 바뀌면, **두 문서가 서로 다른 값을 말하는 상태**가 되고 어느 쪽이 맞는지 알 수 없다. 실제로 이 함정에 빠지기 쉬우니 처음부터 색인만 둔다.

### §8 확정되지 않은 것

**이 절이 비어 있으면 대개 거짓말이다.** 첫 작성에서 모든 게 확정될 수는 없다.

각 항목에:
- 무엇이 미확정인가
- **선택지가 무엇인가**
- 이게 안 정해지면 무엇이 막히는가

를 쓴다. 그래야 나중에 결정할 때 맥락을 다시 복원하지 않아도 된다.

## 5. 흔한 실수

| # | 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|---|
| 1 | **기술이 등장한다** ("MSA로", "Kafka로") | 기술은 Phase 3의 **결론**이다. 여기 쓰면 결론을 전제로 깔게 된다 | 전부 삭제. 기술 없이 다시 쓴다 |
| 2 | **범위 밖이 비어 있다** | 범위가 정해진 게 아니다 | 범위 밖부터 다시 쓴다 |
| 3 | **시나리오가 기능 목록** | 액터의 목적이 안 보인다 | "누가 무엇을 달성하려는가"로 다시 쓴다 |
| 4 | **액터가 사람만 있다** | 배치·외부 시스템이 빠지면 나중에 통째로 새 요구가 된다 | 사람이 아닌 액터를 찾아 추가 |
| 5 | **미확정을 그럴듯하게 채움** | Phase 2가 그 추정 위에 쌓인다 | `결정 필요 #n`으로 올린다 |
| 6 | **번호가 없다** | 다른 문서가 참조할 수 없어 규칙이 복사된다 | S1, BR-01 같은 ID를 붙인다 |
| 7 | **너무 길다** | 아무도 안 읽는다 | 상세는 하위 문서로 빼고 여기는 지도 역할만 |

## 6. 완료 기준

아래가 전부 만족되면 이 문서는 끝난 것이다.

- [ ] 한 줄 정의에 **구현 기술 용어**(프레임워크·미들웨어·아키텍처 스타일·DB 제품명)가 없다 — **도메인 용어는 허용한다**
- [ ] 범위 밖 항목이 **하나 이상** 있고, 각각 이유가 붙어 있다
- [ ] 액터에 **사람이 아닌 것**이 포함되어 있다
- [ ] 시나리오에 **번호(S1, S2…)** 가 붙어 있다
- [ ] 각 시나리오에 `[기술적 문제]` 표시가 있다
- [ ] 비즈니스 규칙에 **번호(BR-nn)** 가 붙어 있다
- [ ] `결정 필요 #n` 항목이 **§8에 모여 있다** (문서 곳곳에 흩어져 있지 않다)
- [ ] 다른 사람이 이 문서만 읽고 **"그건 범위 밖입니다"라고 판단할 수 있다**
