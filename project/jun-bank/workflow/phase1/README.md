# Phase 1 — 제품 정의

> 책 대응: 없음 (책은 아키텍처부터 다루지만, 그 입력이 되는 단계다)
> 선행 조건: **없음. 여기가 시작점이다.**

---

## 목적

**"이 시스템은 무엇인가"를 고정한다.**

이 Phase가 흔들리면 아래 모든 Phase가 흔들린다. 도메인 모델도, 서비스 경계도, 아키텍처 결정도 전부 "무슨 시스템을 만드는가"에서 파생되기 때문이다.

가장 흔한 실패는 **이 단계를 건너뛰는 것**이다. 만들 것이 머릿속에 있다고 생각해서 바로 설계로 넘어가면, 나중에 "그건 범위 안이었나?"를 매번 다시 판단하게 된다.

## 완료 기준

| # | 기준 | 왜 |
|---|---|---|
| 1 | **범위 밖 항목이 명시되어 있다** | **있는 것보다 없는 것이 더 중요하다.** 범위 밖이 없으면 범위가 정해진 게 아니다 |
| 2 | 액터가 전부 나열되어 있다 | 빠진 액터는 나중에 통째로 새 요구사항이 되어 돌아온다 |
| 3 | 핵심 시나리오가 나열되어 있다 | 이후 유스케이스·품질 시나리오의 원천 |
| 4 | 비즈니스 규칙에 **번호(BR-nn)가 붙어 있다** | 다른 문서가 참조할 수 있어야 한다. 번호가 없으면 규칙이 복사된다 |
| 5 | **미확정이 `결정 필요 #n`으로 남아 있다** | 추정으로 채워 넘기면 Phase 2가 그 추정 위에 쌓인다 |

**완료 판정**: 위 5개가 전부 ✅이면 Phase 2로 넘어간다. 하나라도 ❌이면 아직 Phase 1이다.

## 흔한 실패

| 실패 | 증상 | 대응 |
|---|---|---|
| **범위를 안 정함** | "그것도 하면 좋죠"가 반복된다 | 범위 밖 목록을 먼저 쓴다 |
| **기능 목록으로 대체** | 시나리오가 아니라 화면·API 목록이 나온다 | 액터가 **무엇을 달성하려는가**로 다시 쓴다 |
| **규칙에 수치가 없음** | "빠르게", "적절히" 같은 말이 남는다 | 수치 + **그 수치의 근거**를 함께 쓴다 |
| **미확정을 숨김** | 애매한 걸 그럴듯하게 채운다 | `결정 필요 #n`으로 남긴다 |
| **한 번 쓰고 안 봄** | 이후 문서가 정의서를 참조하지 않는다 | 시나리오·규칙에 번호를 붙여 참조 가능하게 만든다 |

## 이 Phase가 다음 Phase에 넘기는 것

```
제품 정의서
├── 시나리오        ──▶ Phase 2 이벤트 스토밍의 입력
├── 액터            ──▶ Phase 2 컨텍스트 도출, Phase 3 이해관계
├── 범위 in/out     ──▶ Phase 2 도메인 경계
└── 도메인 용어(초벌) ──▶ Phase 2 용어사전

비즈니스 규칙서
├── 규칙 BR-nn      ──▶ Phase 2 애그리게이트 불변식
└── 수치            ──▶ Phase 3 품질 시나리오의 측정 기준
```

**여기서 넘어가지 않는 것**: 기술 선택, 서비스 분할, 데이터 모델. 그건 Phase 2~3의 일이다. 제품 정의서에 "Kafka를 쓴다"가 등장하면 잘못 쓴 것이다.
