# 개발 사이클 — 한 바퀴를 실제로 도는 절차 (how-to)

이 문서는 마일스톤 하나를 여는 것부터 태그를 찍고 되돌리는 것까지, 개발 사이클을 **실제로 한 바퀴 도는 순서**를 적는다. 규칙이 "어떤 모양이어야 하나"는 [`git-conventions.md`](../../git-conventions.md)(GC-1~36)가 정본이고, 이 문서는 그 규칙들을 실행 순서로 엮어 "지금 무엇을 하나"에 답한다. 목적은 보여주기가 아니라, 추적·되돌림·이유가 남는 사이클을 몸에 익히는 것이다 — 그리고 **혼자서도 팀처럼 도는 것**이다. 지금 정석으로 익혀두면, 나중에 사람이 합류했을 때 규약을 새로 만들지 않고 도는 사이클에 역할만 배정하면 된다. 아래 절차는 **역할**(구현자·리뷰어·승인자)로 적었고, 지금은 그 셋을 사용자가 겸한다 — 사람이 늘면 역할을 나눠 배정한다.

이 절차는 처음 돌리는 것이라 불편하거나 안 맞는 자리가 나올 수 있다. 그럴 때는 규약을 우회하지 말고 규약을 고친다 — 그 개정 자체가 이 연습의 산출물이다.

## 0. 준비 — 리포마다 한 번

새 리포에서 사이클을 처음 돌리기 전에 세 가지가 서 있어야 한다: `.github/`(이슈·PR 템플릿·`config.yml`의 `blank_issues_enabled: false` — GC-15), `.github/labels.yml`(type·stakes·특수 3축 — GC-22·23), 브랜치 보호(main 직접 push 금지 — dev-conventions PR-1). org 공통 템플릿은 `.github` 리포가 대신하지만, 라벨과 보호는 리포별로 세운다.

## 1. 마일스톤을 연다

작업 묶음 하나 = 마일스톤 하나다. 이름은 슬라이스 단위(`S0 기반`·`S1 UC-03` — GC-26)로 짓고 마감일을 채운다. 마일스톤이 우선순위를 표현하는 자리이므로, 지금 무엇을 먼저 하는지가 여기서 드러나야 한다. `gh api`로 만든다:

```
gh api repos/jun-bank/<repo>/milestones -f title='S0 기반' -f state=open -f description='...' -f due_on='2026-..T..Z'
```

## 2. 이슈로 작업을 규격화한다

마일스톤 안의 각 작업을 이슈로 뗀다. 이슈는 빈 채로 열지 않고(GC-15) 템플릿의 칸을 채운다 — 목표(결론 먼저)·정본 근거(BR·ADR ID와 각 한 구절)·완료 조건(검증 가능한 형태)·검증 방법(머지 게이트가 요구하는 것)·범위 밖. 이슈 본문은 사람이 읽는 문서이므로 글쓰기 방법론(WM)을 따른다. 라벨은 type 하나 + stakes 하나를 최소로 붙인다 — stakes가 검증 강도를 정한다(test-strategy.md).

이슈를 잘 쓰면 그것이 곧 PR의 근거가 되고, 나중에 "왜 이렇게 했나"의 답이 이슈에 남는다. 이것이 히스토리의 시작점이다.

## 3. 이슈 기반 브랜치에서 작업한다

브랜치 이름은 `type/issue-<N>-<slug>`(예: `feat/issue-12-deploy-lock`)로, 이슈 번호를 담는다(GC — 브랜치가 이슈를 가리킨다). 브랜치는 짧게 산다(2일 이내가 목표) — 오래 살면 main과 벌어져 머지가 위험해진다. 커밋은 단계마다 남기고(몰아서 하지 않는다), 메시지는 `type(scope): 제목` + 본문(무엇·왜), 이모지·AI attribution 금지(GC-1·PR-7).

## 4. PR을 연다

작업이 서면 PR을 연다. 본문은 템플릿대로 — 결론(`Closes #N`으로 이슈 결박)·무엇을 왜(구현 선택의 이유)·검증(실행한 명령과 결과)·리뷰 포인트. 머지 게이트(test-strategy.md §3.0)가 요구하는 것을 검증 칸에 채운다: 단위·통합·계약 green, 머지 전 안전선(스모크·diff 셀프리뷰·반증 질문 1회). 리뷰 코멘트는 Conventional Comments 형식(GC-25)으로 — `nitpick`·`note`는 머지를 막지 않는 것이 형식으로 보인다.

리뷰는 듀얼 1패스가 기본이고(구현물은 green이 있으므로 stakes에 따라 루프), **승인 판정은 승인자 역할**이 한다(지금은 사용자가 겸함 — 사람이 늘면 구현자와 리뷰어를 분리해 생성≠검증 절단선을 실제로 세운다).

## 5. 머지한다

머지는 rebase로 한다(GC-13) — squash는 3의 단계별 커밋을 머지 순간 지워서 히스토리를 잃는다. 머지되면 이슈가 자동으로 닫히고(`Closes #N`), 마일스톤 완료 퍼센트가 오른다. 이 지점에서 "무엇이 언제 들어갔나"가 커밋·PR·이슈 세 곳에서 대조된다.

## 6. 버전을 찍는다 — 릴리스 단위에서

마일스톤이 릴리스 단위면 태그를 찍는다. SemVer(`vMAJOR.MINOR.PATCH`)·`v` 접두·annotated 태그(GC-30·31). fix는 PATCH, feat는 MINOR, 호환 깨짐은 MAJOR다. 릴리스 노트는 `release.yml`이 PR 라벨을 읽어 자동 생성한다(그래서 라벨이 정확해야 한다 — GC-23의 무음 실패가 여기서 드러난다). Changelog는 Keep a Changelog 형식.

⚠️ 커밋에서 버전을 자동 도출하는 정평 있는 Gradle 경로가 없다(리서치 발견 — release-please는 Gradle 전략이 없고 axion은 커밋을 안 읽는다). 그래서 v1은 **수동 태그 + 자동 노트**다. common을 한 번 태깅·발행해보면 이 수동 절차가 감당되는지가 드러난다 — 안 되면 그때 자동화 도입 조건이 관찰된 것이다.

## 7. 되돌린다 — 되돌릴 수 있어야 버전 관리다

배포된 버전을 되돌리는 것이 버전 관리의 완성이다. 코드 롤백은 이전 태그로 되돌리고(ADR-024 RL-5 — 이미지 태그 재기동, 재빌드 없음), 되돌림 판정은 사람이 한다(자동 롤백 없음 — RL-11). 되돌릴 수 없는 것(데이터 변경·스키마 축소)은 그 사실이 이슈·ADR에 기록돼 있어야 하고, 되돌림을 시도하는 순간이 아니라 실행 전에 알아야 한다.

## 사이클이 한 바퀴 돌면 남는 것

이슈(왜 했나)·커밋(무엇을 단계별로)·PR(어떻게 검증했나)·마일스톤(어디까지)·태그(언제 배포)·롤백 경로(되돌릴 수 있나) — 이 여섯이 대조 가능하게 남으면 사이클이 한 바퀴 돈 것이다. 6개월 뒤의 자신이든 새로 합류한 사람이든 "이게 왜 이렇게 됐지"를 물었을 때 답이 이 여섯 곳에 있으면, 원저자에게 묻지 않고도 유지보수할 수 있다 — 그것이 상호 유지보수의 조건이고 이 연습의 도착점이다.
