# 개발 일지 — 2026-08-07

오늘은 인프라(infra) 리포를 처음으로 실제 코드가 도는 상태까지 끌어올린 날이다. 아침에는 아직 결정되지 않았던 아키텍처를 ADR로 못박고(데이터 접근·배포 오케스트레이션·언어·내부 아키텍처), 그 위에서 인프라 리포를 스캐폴드해 S0 기반과 S1 인증 게이트 8건을 닫았다. 오후에는 S2 배포 창 락에 착수했고, 이건 아직 진행 중이다. 구현과 나란히 학습 문서와 ADR 개정도 여러 편 썼다 — 왜 병행했는지는 뒤에서 따로 적는다. 이 일지는 오늘 남은 PR 리뷰 이력과 커밋을 근거로 재구성한 회고이며, 미래의 유지보수자가 "왜 이렇게 됐나"를 되짚을 때 읽으라고 남긴다.

핵심만 먼저 말하면, 오늘 가장 값진 건 완성한 게이트가 아니라 **리뷰가 잡아낸 것들**이다. 네 라운드의 리뷰에서 medium·high 결함이 나왔고, 그중 몇은 한쪽 리뷰어만 봤다면 그대로 배포됐을 것들이었다. 그 대목을 이 일지의 중심에 둔다.

## 타임라인 — 결정에서 락까지

### 아키텍처를 먼저 못박고 구현에 들어갔다 (ADR-026~029)

구현에 앞서 네 개의 결정을 ADR로 확정했다. ADR-026은 데이터 접근을 Spring Data JDBC로 채택하고 JPA 도입 조건을 잠갔다(사용자 결정). ADR-027은 배포 오케스트레이션 컴포넌트 모델을 정하고(단일 바이너리·역할별 .env·HTTP+JSON·watchdog 별도), 전송 방식을 위성 SSH에서 호스트별 로컬 agent 서명 RPC로 개정 예정 표식까지 달았다. ADR-028은 언어를 서비스=Kotlin/JVM+Spring, 인프라=Go로 확정했고, ADR-029는 컴포넌트별 내부 아키텍처를 정하면서 헥사고날 전면 채택은 철회하고 필요한 포트만 쓰기로 강등했다. 이 결정들은 선검증을 거쳐 반영됐다 — 배포 아키텍처에서 선검증 14건(DO-10~20), 내부 아키텍처에서 선검증 7건이 문서에 들어갔다.

### 인프라 리포를 스캐폴드하고 단일 바이너리로 정리했다

인프라 리포는 초기화(96c7541)부터 시작해 Go 멀티커맨드 레이아웃 스캐폴드, 배포 스키마 DDL, store 골격, HTTP 진입 골격(POST 수신·미들웨어 체인·body 상한) 순으로 뼈대를 세웠다. 그다음 구조를 한 번 정리했다 — dispatcher를 agent 모드 내부 실행 모듈로 옮기고(f287968), 단일 바이너리가 ROLE(main|agent)로 분기하도록 바꿨다(f81cd85). README의 구조 절도 이 단일 바이너리·ROLE 구조에 맞춰 갱신했다(49f4e01). 이 정리 덕에 이후 게이트 배선이 main HTTP 기동 경로 하나로 모였다.

### S1 인증 게이트 — HMAC에서 OIDC, 모드 fail-closed까지 (8/8 닫힘)

S1은 요청이 agent에 닿기까지의 인증을 세 겹으로 쌓았다. 게이트 1은 HMAC 서명 검증과 신선도 판정(fc11681), 그 뒤에 멱등 원장 Reserve 3분기 구현과 통합 테스트(62f3176), 그리고 이 둘을 체인에 배선했다(74d4fde). 게이트 2는 OIDC claim 검증 행렬(c7f594a)을 체인에 배선하고 jti를 선점에 연결했다(5abe25c·13a820e). 마지막으로 배포 모드 조회·append(114618d)와 게이트 후 모드 판정·fail-closed·version 원자 검증(aec56cc)을 올렸다. S0 기반은 2/2, S1 agent 진입·인증은 8/8로 닫혔고 v0.1.0 태그를 찍었다.

### S2 배포 창 락에 착수했다 — 아직 0/6, 진행 중

오후에 S2 오케스트레이션(로컬 배포 실행)으로 넘어가 배포 창 락의 정상 경로를 배선했다 — 획득·fencing 재확인·해제(PR #16, CD-3, #13). 이 마일스톤은 아직 0/6이다. 뒤에서 보듯 이 락은 리뷰에서 high 3건이 나와 수정 방향은 확정됐지만 검증이 아직 착지 중이다.

## 리뷰에서 나온 문제와 해결 (핵심)

이 절이 오늘의 중심이다. 라운드별로 무엇이 나왔고 왜 문제이며 어떻게 고쳤는지를, 리뷰어와 심각도를 그대로 적는다. 파일·행 번호는 리뷰 원문에 남은 것을 옮긴 것이라 미래에 그 자리를 다시 찾을 때 쓸 수 있다.

### S1-2 (PR #8) — requestId 빈값과 0 스큐, medium 2건

게이트 1의 듀얼 리뷰(codex와 Opus)는 보안 코어(HMAC·신선도·멱등·fail-closed)에 medium 이상 결함이 없음을 확인했지만, 그 바깥에서 medium 2건이 나왔다. 첫째, codex가 `internal/httpentry/httpentry.go:180-205,230-236`에서 requestId 필수 검증이 없다고 지적했다 — 빈 ID도 올바르게 서명하면 인증·예약을 통과하고, 모든 무-ID 요청이 동일한 멱등 키 `""`를 공유해 충돌/DoS가 난다. 둘째, 양 리뷰어가 `internal/auth/auth.go:109-114,136-139`에서 `AGENT_CLOCK_SKEW=0s`를 유효하게 파싱한 뒤 기본값 60초로 치환하는 문제를 봤다 — 운영자가 요구한 무-skew 정책보다 미래·만료 요청을 넓게 허용한다. 앞의 것은 빈 requestId를 게이트 1에서 거절하도록(be1621f), 뒤의 것은 Config.Skew를 포인터로 바꿔 "미설정 vs 명시적 0"을 구분하도록(c85c66d) 고쳤다. codex 판정은 not clean이었다. 잔여 low/info(서버측 max-TTL 부재·reserve 후 수신 실패 재실행 갭)는 수용하고 후속 이슈 #9로 추적한다.

### S1-3 (PR #10) — malformed nbf와 aud 포함 검사, codex가 Opus 통과 지점을 잡았다

게이트 2(OIDC)의 듀얼 리뷰는 인증 우회형 치명점이 없음을 확인했다 — alg 방어 이중화(타입검사 + WithValidMethods RS256)로 none·HS256 혼동을 막고, claim 행렬 전 칸 AND·jti는 검증된 토큰에서만·부작용 전 선점·전 오류 fail-closed가 서 있었다. 그럼에도 medium 2건이 나왔다. codex가 `oidc.go:176,270`에서 malformed `nbf`가 "미설정"으로 취급돼 통과 가능함을 지적했다 — `mapUnix`가 비수치 `nbf`를 `0`으로 바꾸고 `checkClaims`는 `0`이면 검증을 생략하므로, 서명된 `"nbf":"invalid"`가 거절되지 않는다. ★ 이 지점은 Opus가 통과로 봤던 자리다. 또 `oidc.go:164,238`에서 `aud` "전용값"을 정확 일치가 아니라 포함 관계로 검사해, 배포 전용 aud와 다른 서비스 aud가 섞인 토큰도 통과한다고 봤다. 둘 다 무음 스킵 2건 제거로 고쳤다 — absent와 invalid를 구분하고, aud를 정확 단일 일치로 좁혔다(e82a79e). codex는 여기서도 High 하나를 함께 냈다 — `main.go:147,169`의 운영 배선이 항상 오류를 반환하는 `jwksScaffold`를 써서 모든 정상 OIDC 토큰이 401로 거절된다는 것이다. fail-closed 자체는 맞고 에이전트가 아직 미배포라 안전하지만, 실제 JWKS 페치는 출시 차단 사항으로 후속 이슈 #11에 남겼다. codex 판정은 not clean이었다.

### S1-4 (PR #12) — 단조 version 미강제와 TOCTOU, HIGH 2건

배포 모드 fail-closed는 codex 리뷰를 받았다. 정상 동작(저장 실패·mode 부재·미지 문자열을 모두 operational로 닫음, 행 부재를 지어내지 않고 ErrNoMode 반환)은 확인됐지만 HIGH 2건이 나왔다. 첫째, `store.go:290`과 `deploy/schema/01_tables.sql:85`에서 단조 version이 강제되지 않았다 — `UNIQUE(target, mode_version)`은 중복만 막고 더 작은 새 version 삽입을 허용하므로, `dev/v2`에서 `operational/v1`을 삽입해도 `Current`가 계속 `dev/v2`를 반환해 성공한 운영 토글이 무반영되는 fail-open이 된다. 둘째, `mode.go:88`의 `VerifyModeUnchanged`가 독립 SELECT 후 version만 비교해, 검증 직후 락 획득 전에 operational 토글이 나면 이미 반환된 `OK=true`로 dev 자동 배포가 이어지는 TOCTOU였다. 수정은 `sp_mode_append`가 max+1을 원자 삽입해 단조 version을 강제하고, `VerifyModeUnchanged`가 재조회 mode의 유효성까지 검사하도록 했다 — 실 MySQL 통합 테스트로 회귀를 막았다(24d70d8). codex 판정은 not clean이었다. TOCTOU를 진짜로 닫는 락·모드 단일 트랜잭션 원자성은 S2로 이월했다(#14).

### S2-1 (PR #16) — Opus는 clean, codex는 High 3건, 정반대 판정 (수정 방향 확정·검증 착지 중)

배포 창 락은 두 리뷰어가 **정반대 판정**을 낸 자리다. Opus는 락 경로 코드 4종(store.go·lock.go·02_procedures.sql·통합 테스트)을 전부 읽고 6개 렌즈(원자성·fencing·좀비 차단·커넥션 고정·양방향·fail 방향)로 정본 CD-3/DT-12와 대조해 **프로덕션 코드를 clean으로 판정**했다 — 유일한 미흡은 테스트 커버리지 한 곳(동시성 코어의 단일 승자 불변식이 순차 테스트로만 덮여 있어 N-goroutine 동시 Acquire 검증이 없다)이었다. 같은 코드를 codex는 **실제 MySQL로 익스플로잇해 High 3건**을 실증했다.

codex가 실행으로 잡은 셋은 이렇다. 하나, `02_procedures.sql:37`에서 `p_holder_kind` 검증이 없어 `NONE`으로도 획득이 성공한다 — 실행에서 `Acquire("NONE") → token=1, ok=1`인데 행이 계속 `NONE`이라 바로 다음 `Acquire("AGENT") → token=2, ok=1`도 성공했다. "경합 시 하나만 성공" 계약을 정면으로 위반한다. 둘, `store.go:225`가 `lease.Seconds()`를 `int`로 절삭해 `500ms → 0`이 되고 SQL도 양수 검증이 없어, 0초 Acquire가 `ok=1`을 반환하고 즉시 만료돼 다음 획득도 성공했다 — `Renew(..., 0)`가 살아 있는 lease를 `NOW()`로 줄이며 `true`를 반환하면 좀비 차단이 무너진다. 셋, `02_procedures.sql:70,192`·`03_grants.sql:60`에서 잡지 않은 반대 계정도 타 주체 락을 갱신·해제할 수 있어, `cutoff_lock` 계정이 AGENT의 락을 읽어 `sp_lock_release`를 호출하니 `ok=1`이 됐다 — "잡은 주체가 해제" 위반이다. 여기에 medium 하나로, 통합 테스트가 실제 경합을 만들지 않아 이 결함들을 못 잡는다는 지적이 붙었다. 주목할 대비가 있다 — 0초 lease 절단(store.go:225)을 Opus는 "실패 방향이 안전(만료 쪽)"이라 낮음으로 봤고, NONE 획득 경로를 Opus의 원자성 렌즈는 stale 회수 조건으로 읽어 clean으로 판정했는데, codex는 그 둘을 실제로 실행해 락이 실제로 뚫리는 High로 드러냈다.

수정 방향은 codex의 처방으로 확정됐다 — 프로시저에서 `AGENT/BATCH_CUTOFF`만 허용하고 계정 역할과 kind를 결박, Go와 프로시저 양쪽에서 최소 1초 이상을 강제하고 잘못된 값은 fail-closed, 역할별 wrapper 프로시저에 kind를 하드코딩하고 각각에만 EXECUTE를 준다. 다만 이 수정의 검증은 아직 착지 중이다 — S2 마일스톤은 0/6이고, 세션 변수 격리는 두 리뷰어 모두 안전으로 판정했지만(단일 conn에서 CALL과 SELECT @…를 연속 수행) codex 최종 판정은 High 3건 때문에 배포 불가(not clean)였다. 완료로 적지 않는다.

### 듀얼 리뷰의 값 — 한쪽 리뷰만 믿으면 놓친다

오늘 리뷰의 교훈을 한 문단으로 모으면 이렇다. S1-2의 requestId 빈값은 codex가 단독으로 잡은 것이고(0 스큐만 양 리뷰어가 봤다), S1-3의 malformed nbf는 codex가 잡았지만 Opus는 통과로 봤던 자리다 — 같은 코드를 두 리뷰어가 봐도 한쪽만 보는 결함이 실제로 있었다는 뜻이다. S2-1은 가장 극명한 사례다 — 같은 락 코드를 두고 Opus는 6개 렌즈로 정독한 뒤 프로덕션 코드를 clean으로 판정(테스트 갭만 지적)했는데, codex는 실제 MySQL로 익스플로잇해 High 3건을 실증했다. 정반대 판정이 갈린 이유는 방법의 차이다 — Opus는 SQL 의미를 논증해 원자성을 clean으로 읽었고, codex는 그 논증이 실제 MySQL에서 성립하지 않는 지점(NONE 획득·0초 lease·반대 계정 해제)을 실행으로 뚫었다. 정리하면, 오늘의 결함들은 "리뷰어를 늘리는 것"만으로는 부족했고 "실제로 실행해 보는 것"이 있어야 잡혔다 — 정적 정독이 clean이라 판정한 코드가 실행에서 뚫린 것이 그 증거다.

## 문서 작업 — 왜 구현과 병행했나

오늘은 구현과 나란히 문서를 여러 편 썼다. 학습 문서로는 보안 5편(HMAC·SHA-256/digest·OIDC·게이트1 패턴 — S1 게이트 1 구현의 개념 정리), JPA·Spring Data JDBC 3편, 언어 심층 5편(java-jvm·kotlin·go·rust·c-cpp-csharp)이 나왔고, 언어 문서가 포인터로 참조하는 측정 프로그램 4종(고루틴 RSS·GC 정지·기동/크기·Kotlin 별칭)도 실측 근거로 보존했다. 결정 문서로는 위의 ADR 네 편과 배포 아키텍처 개정(ADR-024 v0.3·ADR-027 신설·cicd v1.4·infrastructure.md 신설), 규약 개정 GC-9b(산출물 언어 한국어, 코드 식별자·규약 키워드는 영어 예외)가 있었다.

이걸 구현과 함께 한 이유는 두 가지로 읽힌다. 하나는 개념 정리가 구현의 입력이었다는 것 — 보안 학습 5편은 S1 게이트 1을 구현하며 개념을 실검증해 날조를 막으려고 쓴 것이고, 언어·데이터 접근 문서는 ADR 결정을 뒷받침한다. 다른 하나는 결정과 구현이 같은 날 움직였다는 것 — ADR을 확정하지 않으면 인프라 리포를 스캐폴드할 수 없었기에, 대화에서 나온 결정을 정본화하는 문서 작업이 구현의 선행 조건이었다. 문서 작성에는 글쓰기 방법론의 사람 층 서식을 적용했다.

## 오늘 배운 것

오늘 이력에서 관찰된 것을 근거 있는 것만 남긴다. 첫째, "테스트 통과 ≠ 검증 완료"가 S2-1에서 그대로 재현됐다 — race 검출과 통합 테스트가 통과했는데 실제 경합을 만들지 않는 테스트라 High 3건을 못 잡았다. 둘째, fail-open이 실제로 나오는 사고 형태다 — S1-4의 단조 version 미강제(성공한 토글 무반영)와 S1-2의 skew 0 무시(요청을 넓게 허용)가 둘 다 "닫혀야 할 게 열린" 방향의 결함이었다. 셋째, 리뷰의 값은 리뷰어 수와 실행 검증 둘 다에서 온다(위 듀얼 리뷰 절). 넷째, 결정을 ADR로 먼저 못박고 선검증(DO-10~20 등)을 거쳐 구현에 들어가는 순서가 오늘 실제로 돌아갔다. 다섯째, 닫지 못한 것을 정직하게 이월했다 — JWKS 실기능(#11)·reserve 후 수신 실패 갭(#9)·S2 배선 세 건(#13·#14·#15)이 OPEN으로 남아 다음 마일스톤이 닫는다.
