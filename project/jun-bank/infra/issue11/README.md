# issue11 — 블루-그린 전환: 정리는 미전환이 보증됐을 때만

- 원본 PR: infra #27 · devlog: `jun-bank/infra/docs/devlog/pr-27-blue-green.md`

## 1. 무엇이 문제였나

배포가 green 슬롯 기동·헬스까지만 하고 멈춰 있었다.\
실제 라우트 전환·드레인·구 슬롯 종료(CD-4 ⑤⑥⑨)가 남아, 새 컨테이너는 떠 있지만 트래픽은 여전히 옛 슬롯으로 갔다.

> **블루-그린** — 새 버전을 옆 슬롯에 띄운 뒤 라우트를 통째로 넘겨 무중단 교체하는 방식.\
> 예: green(신)이 준비되면 트래픽을 green으로 넘기고 blue(구)를 내린다.

> **드레인(drain)** — 옛 슬롯을 바로 죽이지 않고, 처리 중인 요청이 끝날 시간을 준 뒤 내리는 것.

핵심 난점은 두 부작용이 서로 다른 곳에 있다는 데 있었다.\
배포 창 락은 DB에 있고 라우트 write는 게이트웨이에 있어, 락 재확인과 SCG write 사이의 창에서 lease를 잃은 낡은 실행자의 write가 최종 라우트로 남을 수 있다.

> **fencing token** — "지금 권리자는 나"를 증명하는 단조 증가 번호.\
> 예: 뒤늦게 깨어난 옛 실행자의 낮은 token은 거부돼, 승자의 라우트를 덮지 못한다.

## 2. 무엇을 고민했나

전환 수단 자체의 대안은 앞선 설계(ADR-031)가 이미 기각해 뒀고, 구현 완주 뒤 사용자가 다시 물어 그 답까지 기록됐다.

- **큐 기반 라우팅.** — 핫패스에 상시 큐 홉이 붙는다.
- **엣지 nginx.** — 공유 엣지를 매 배포마다 건드려 반경이 넓다.
- **compose 포트 스왑.** — 라우팅 결정이 두 곳으로 흩어진다.
- **서비스별 nginx.** — reload가 드레인을 내장하는 장점은 인정하되, conf를 쓰는 쪽이 곧 실행자라 fencing을 거부할 지점(sink)이 없다.
- **SCG(Spring Cloud Gateway) 라우트.** — 채택. 게이트웨이 전환 API가 token을 검증하는 sink-side가 되어, 자원 쪽에서 낡은 write를 거부한다.

> **sink-side 검증** — 권리 확인을 명령을 내리는 쪽이 아니라 최종적으로 쓰는 자원(sink) 쪽에서 하는 것.\
> 예: 게이트웨이가 token을 보고 거부하면, 창 사이 낡은 write가 실제로 반영되지 않는다.

## 3. 그래서 이렇게

블루-그린은 target=core에만 성립한다 — 슬롯 배선과 게이트웨이 라우트가 core 하나에 결박돼 있기 때문이다.\
대상을 안 보고 이 경로로 들어오면 다른 서비스 이미지가 core 슬롯을 덮고 그 위로 core 라우트가 전환되는 치명 경로가 열린다.

```text
전환 실패 응답 도착
        ↓
게이트웨이가 실은 보증 수준
        ↓
   ┌─ stale(409): 소유권 상실 → 승자 슬롯 건드리지 않음(정리 생략) = UNKNOWN
   ├─ ROLLED_BACK: 라우트가 구 슬롯 그대로 보증됨 → 올린 slot 정리 = net-0 복원
   └─ 그 밖(불명): 정리 금지 · UNKNOWN (내리면 트래픽 가는 쪽을 끊는다)
```

"정리는 미전환이 보증됐을 때만 한다"가 원리다.

## 4. 코드 — 실제 커밋에서

대상을 안 보고 core 슬롯으로 흘려보내지 않고, 시작 전에 요란하게 거절한다(부작용 0).

```go
// internal/deploy/dispatcher.go:176-199 (발췌) — 대상 결박
case m.Target == TargetCore:
    return d.dispatchBlueGreen(ctx, imageRef, token, plan)
case m.Target == TargetGateway:
    return d.runSinglePath(ctx, imageRef, plan)   // 자기 전환 불가 — 재기동 교체
default:
    // 조용히 core 슬롯으로 흘려보내지 않고 시작 전에 요란하게 거절한다(부작용 0).
    return StateUnexecuted, fmt.Errorf("... target=%q ... fail-closed · 대상 뒤바뀜 방지", m.Target)
```

## 5. 구현 중 마주친 문제

최초 구현은 전환 실패(409든 500이든 전송 실패든)를 일괄 "미전환"으로 접고 green을 정리(down)했다.\
409는 소유권 상실 신호인데, 그 순간 내려가는 슬롯은 새 소유자(승자)가 방금 올린 라이브 슬롯일 수 있다 — 이것이 치명으로 잡혀 실패 계약이 통째로 뒤집혔다.

1차 처방("정리 전 라우트 재조회")도 기각됐다 — 재조회 역시 registry 기준이라 실상태 보증이 아니다.\
최종 해법은 게이트웨이가 실패 응답에 보증 수준을 싣고 infra가 그 보증으로 3분기하는 것이었다.

그 밖에 함께 바뀐 것들이다.\
rollback이 fencing token 최고수위를 후퇴시키던 것을 slot만 복구하고 token은 유지하게 바꿨고, 게이트웨이 재시작이 env로 복귀해 죽은 슬롯을 라우팅하던 것을 상태 파일 지속화 + write-ahead 커밋 순서로 막았다.\
예산 합산 전 개별 검증(overflow fail-open 차단)과, state를 상태 코드와 무관하게 파싱하던 것(502/400 위조 body 승격 가능 → 500에서만 신뢰)도 이때 닫혔다.

## 6. 결론

실서버 무중단 관측 3회 누계 5,475건에서 실패 0으로 양방향 전환이 관통했고, 게이트웨이 정지를 넣은 부분 실패 1회는 503 + 부작용 0 + 락 해제로 안전하게 거동했다.\
이 실패 계약으로 ADR-031이 v1.2로 개정됐다.

이 PR이 만든 상황이 곧바로 다음 이슈들을 낳았다.\
target=gateway가 정식 배포 대상이 되면서 "core 워크플로의 정상 토큰으로 gateway를 배포하는 것을 막지 못한다"가 즉시 문제가 돼 issue12(repo↔target 결박)로, 슬롯별 compose 파일이 생기며 넓어진 "호스트 compose 변조" 표면이 issue14(compose 동봉)로 이어졌다.
