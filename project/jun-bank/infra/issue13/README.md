# issue13 — Outcome 분리·서비스 결박: 두 결함의 한 근원

- 원본 PR: infra #30 · devlog: `jun-bank/infra/docs/devlog/pr-30-outcome-identity.md`

## 1. 무엇이 문제였나

앞선 리뷰가 남긴 두 이슈(#20·#21)를 한 슬라이스로 닫았다.

**#20** — pull 실패나 헬스 실패 후 정리 같은 실행 계층 실패가 `FAIL_CLOSED`로 접혔다.\
그런데 그 상수의 정의된 의미는 "저장 접근·검증 불가로 자동 배포를 시작하지 않음"이다.\
관제 화면이 Outcome을 축으로 삼는데, "인프라가 막았다"와 "배포가 실패했다"가 구별되지 않았다.

> **Outcome** — 관제 화면이 배포 결과를 분류하는 축.\
> 예: 인프라가 시작을 막은 것과 배포 자체가 실패한 것은 대응이 달라, 같은 코드로 뭉치면 안 된다.

**#21** — `docker compose ps -a`로 프로젝트 전체를 보고 "실행중 하나라도 pinned digest면 통과"였다.\
여기서 두 결함이 나온다 — orphan/사이드카가 우연히 pinned digest를 실행 중이면 현재 app이 틀린 이미지여도 가려지는 fail-open(H2), 그리고 정상 종료하는 one-shot 컨테이너가 있으면 부분기동으로 오판하는 fail-closed 오탐(M1).

> **사이드카 / orphan** — 배포 대상 app이 아닌, 같은 프로젝트에 함께 뜨는 곁 컨테이너나 남은 컨테이너.

이슈가 근원을 한 줄로 적었다 — 둘의 근원이 같다, 어느 서비스가 배포 대상 app인지 결박하지 않는다.

## 2. 무엇을 고민했나

- **실행 실패의 상태 코드 — 503 그대로 vs 502 신설.**\
  502를 골랐다. 위임한 하류(docker·레지스트리)가 요청을 완수하지 못한 것이라 Bad Gateway가 의미상 맞고, "우리가 시작조차 못 했다"인 503과 갈려야 관제에서 두 범주가 구별된다.
- **서비스 식별 — 컨테이너명 규칙 파싱 vs compose 라벨.**\
  라벨(`com.docker.compose.service`)을 골랐다. 라벨이 compose가 소유하는 계약이라 이름 규칙보다 안정적이다.
- **매치 판정 — ≥1-match vs all-match.**\
  결박된 경로는 all-match로 강화했다(아래 §5). 결박 없는 하위호환 경로는 그 전제가 없어 ≥1-match를 유지하는 비대칭이 됐다.

## 3. 그래서 이렇게

`OutcomeExecutionFailed`(HTTP 502)를 신설해 인프라 축 거절(503)과 코드로 갈랐다.\
그리고 `DEPLOY_APP_SERVICE`(compose 서비스 라벨 기준)로 판정 대상을 결박해, 프로젝트 전체가 아니라 대상 서비스만 본다.

```text
docker compose ps -a 로 프로젝트 전체를 봄
        ↓  (바뀌기 전: 하나라도 pinned면 통과)
DEPLOY_APP_SERVICE 라벨로 대상 서비스만 필터
        ↓
   ┌─ H2 닫힘: 사이드카·orphan이 pinned여도 app의 매치를 대신 못 함
   └─ M1 닫힘: one-shot·정지 orphan은 다른 서비스라 부분기동 판정에 안 듦
```

이 결박이 닫지 못하는 축(설정이 엉뚱한 서비스를 가리키는 오설정)까지 주석에 명시하고, 그 축은 issue14가 닫는다고 남겼다 — "무음 이연 아님"이 반복되는 규율이다.

## 4. 코드 — 실제 커밋에서

판정 대상을 이 배포의 대상 app 서비스 컨테이너로 결박하는 것이 두 결함의 근원을 함께 닫는다.

```go
// internal/dispatch/dispatch.go:502-530 (발췌)
// 판정 대상은 이 배포의 대상 app 서비스 컨테이너다. 프로젝트 전체가 아니라 대상 서비스만
// 보는 것이 두 결함의 근원을 함께 닫는다:
//   - H2 닫힘: 사이드카·orphan이 우연히 pinned digest여도 app의 매치를 대신해 주지 못한다.
//   - M1 닫힘: 정상 종료하는 one-shot·정지 orphan은 다른 서비스라 부분기동 판정에 안 든다.
```

## 5. 구현 중 마주친 문제

두 가지가 더해졌다.\
하나는 결박된 경로를 all-match로 강화한 것이다 — 같은 서비스의 replica가 [pinned + 틀린 이미지]로 섞여 뜨면 ≥1-match는 그 mixed-replica를 COMPLETED로 위장한다.\
다른 하나는 `(COMPLETED, err)` 모순 조합을 이력 기록 전에 UNKNOWN으로 정규화한 것이다 — 그대로 두면 이력엔 COMPLETED, 응답엔 실패가 남아 재전송이 최초 응답과 영구히 어긋난다.

실측이 인프라 변경을 하나 낳았다.\
단일 경로 모드에서 서비스명이 타깃마다 다르다는 지적이 나왔는데, 실측으로 gateway 라벨이 `"gateway"`(core는 `"app"`)임이 확인돼, 배포 단계에서 gateway compose 서비스명을 `app`으로 통일해 해소했다.

세션 중단 사고도 하나 있었다.\
작업 도중 호스트 프로세스 종료로 워커가 중단됐는데, #20 커밋은 완료·#21은 미커밋 워킹트리 잔존 상태였다 — 워커 transcript가 보존돼 있어 컨텍스트를 유지한 채 재개해 무손실 복구했다.

## 6. 결론

결박을 끄면 5건이 실패함을 확인하는 방식(red-first)과 실서버 회귀 배포로 검증했다.

이 PR이 스스로 적은 한계 — AppService가 엉뚱한 서비스를 가리키는 오설정은 이 층이 닫지 못한다 — 가 issue14로 직결됐다.\
issue14가 appService를 서명된 manifest에 담고 호스트 env와 3자 일치로 대조하면서 그 축이 닫히고, `DEPLOY_APP_SERVICE`는 거기서 동봉 필수 모드의 기동 필수 env로 승격된다.
