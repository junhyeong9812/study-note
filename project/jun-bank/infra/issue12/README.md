# issue12 — repo별 allowlist: 확장이 곧 구멍이 되지 않게

- 원본 PR: infra #29 · devlog: `jun-bank/infra/docs/devlog/pr-29-oidc-allowlist.md`

## 1. 무엇이 문제였나

배포 대상이 넷이 되면서 등재된 어느 repo든 어느 target이든 배포할 수 있게 됐다.\
이슈 본문 한 문장이 문제를 요약한다 — "결박이 없으면 확장이 곧 구멍이다."

근원은 인증과 인가가 분리되지 않은 데 있었다.

> **인증** — "우리 파이프라인에서 왔다"를 증명하는 것.\
> 예: GitHub Actions가 발급한 토큰의 서명이 진짜인지 확인한다.

> **인가** — "무엇을 할 수 있다"를 정하는 것.\
> 예: core 워크플로 토큰은 core만 배포할 수 있어야 한다.

대상이 하나일 때는 인증이 곧 인가였지만, 넷이 되는 순간 갈라진다.\
게이트 2의 저장소 정책이 단일 env 하나뿐이라, core 워크플로의 정상 토큰으로 gateway를 배포하는 것을 아무것도 막지 못했다.

## 2. 무엇을 고민했나

두 결정을 저울질했다 — 결박을 어디에 둘 것인가, 그리고 무엇을 매칭 키로 삼을 것인가.

- **결박 자리 — coordinator가 manifest 파싱 직후 대조.**\
  게이트 2는 진입 층이라 manifest.target을 모르니 파싱 뒤가 자연스러워 보였다.\
  그러나 재전송 경로가 그 층을 안 지나 결박이 통째로 우회된다 — 기각됐다.
- **결박 자리 — 진입 미들웨어(멱등 선점 이전).**\
  채택. 모든 경로가 지나는 미들웨어에서 끊고, 선점 이전이라 거절 시 부작용이 0이다.
- **매칭 키 — 저장소 이름.**\
  이름은 이전·재생성으로 재사용되므로 개명 스쿼팅에 약하다 — 기각.
- **매칭 키 — 수치 repository_id.**\
  채택. 수치 ID는 재사용되지 않아 안정적이다.

> **멱등 선점** — 같은 요청이 두 번 와도 한 번만 실행되게, 요청 ID를 먼저 원장에 잡아두는 것.\
> 예: 선점 뒤에 거절하면 정당한 재시도가 이미 소모된 ID 때문에 재전송으로 오인된다.

## 3. 그래서 이렇게

allowlist를 수치 ID로 매칭하고, 결박을 진입 미들웨어의 선점 이전 지점에 뒀다.\
하나라도 성립하지 않으면 부분 적재하지 않고 통째로 거부한다 — 반쯤 읽힌 allowlist는 절반만 아는 문지기다.

```text
요청 도착
        ↓
진입 미들웨어 — target 부분 디코드
        ↓
allowlist 대조 (repository_id ↔ target 1:1)
        ↓
   ┌─ 불일치 → 403 + 이력 TARGET_FORBIDDEN + 선점 0행 (부작용 0)
   └─ 일치 → 멱등 선점 → 오케스트레이션
```

403 본문은 일반 문구고, 허용 대상·등재 이름은 이력에만 남긴다.\
허용 대상을 응답에 돌려주면 토큰을 쥔 쪽이 무엇을 배포할 수 있는지 응답만으로 알아내기 때문이다.

## 4. 코드 — 실제 커밋에서

allowlist는 부분 적재를 금지하고, 유일성을 세 축에서 본다.

```go
// internal/auth/oidc_allowlist.go:73-111 (발췌)
// 하나라도 성립하지 않으면 부분 적재하지 않고 통째로 거부한다(A4) — 반쯤 읽힌 allowlist는
// "누가 무엇을 배포할 수 있는가"의 절반만 아는 문지기이며, 그 상태로 문을 여는 것이 이
// 경계의 유일한 치명적 실패다.
// 유일성은 셋을 본다: repository_id 중복 · target 중복(1:1) · 이름 중복(ASCII fold 후).
```

결박 자리가 선점 이전이어야 하는 이유를 코드가 직접 적었다.

```go
// internal/httpentry/httpentry.go:333-348 (발췌)
// ★ 자리가 여기인 이유: 대조는 **멱등 선점 이전**이어야 한다.
//   - 선점 뒤에 대조하면 권한 없는 요청이 requestId·jti를 소모한다(같은 토큰의 정당한
//     재시도가 재전송으로 취급된다). 여기서 끊으면 부작용이 0이다.
//   - 오케스트레이션에서 대조하면 재전송 경로가 그 층을 지나지 않아 결박이 통째로 우회된다.
//     미들웨어는 모든 경로가 지난다.
```

## 5. 구현 중 마주친 문제

이 구조는 코드 한 줄 쓰기 전에 한 번 뒤집혔다.\
최초 설계(coordinator가 파싱 직후 대조)가 재전송 경로 우회로 무너져, 결박을 진입 미들웨어로 옮겼다.\
단일 env 모드의 "결박 없음 유지"가 무결박 우회 모드를 존속시킨다는 것도 이때 함께 드러나 닫혔다.

CD 워크플로의 셸 주입과 브랜치 미검증도 함께 고쳐졌는데, 같은 결함이 core repo에도 있어 두 repo에 동시 수정이 갔다.\
기존 동시성 테스트가 선언한 실패모드를 실제로는 통과시키던 공허 단언도, "무엇이 깨지면 이 테스트가 붉어지는가"에 답하도록 교체됐다.

## 6. 결론

음성 검증에서 뜻밖의 실증이 나왔다.\
core repo가 gateway를 배포하도록 allowlist를 한 줄만 스왑했더니 1:1 위반으로 agent가 기동 자체를 거부했다("target을 두 저장소가 주장한다").\
교차 스왑으로 다시 만든 위반 요청은 HTTP 403 + 이력 `TARGET_FORBIDDEN` + 원장 선점 0행으로 거절됐다 — 결박이 부작용 전에 끊는다는 불변식의 실증이다.

이 PR이 세운 것들이 issue14로 이어진다.\
target을 한 칸만 읽는 부분 디코드(락 이전의 관용 파서)와 락 보유 중의 엄격 파서를 가르는 분업이 여기서 시작됐고, 사유 코드 + detail JSON 패턴도 뒤로 이어졌다.
