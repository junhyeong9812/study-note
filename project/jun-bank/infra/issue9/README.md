# issue9 — JWKS 실 공개키 페치: 인증의 뿌리에서 샌 fail-open

- 원본 PR: infra #24 · devlog: `jun-bank/infra/docs/devlog/pr-24-jwks.md`

## 1. 무엇이 문제였나

게이트 2(OIDC)는 "존재하지만 작동하지 않는" 상태였다.\
앞선 작업에서 claim(주장) 행렬은 세웠지만, 서명 검증에 쓸 공개키를 실제로 가져오는 부분은 스캐폴드(전건 거절) 뒤에 있었다.

> **OIDC / 게이트 2** — GitHub Actions가 발급한 토큰으로 "우리 파이프라인에서 왔다"를 증명하는 관문.\
> 예: 토큰의 서명이 진짜인지 보려면 발급자의 공개키가 필요한데, 그 키를 가져오는 통로가 JWKS다.

> **JWKS(JSON Web Key Set)** — 발급자가 공개키들을 담아 공개하는 JSON 문서.\
> 예: 토큰 헤더의 `kid`(키 식별자)로 이 집합에서 맞는 공개키를 골라 서명을 검증한다.

페치 자체는 3단계로 단순하다.\
문제는 이 코드가 **인증의 뿌리**라는 점이었고, 리허설과 테스트를 통과한 코드에서 두 개의 fail-open이 나왔다.

- **만료 + throttle 시 stale 키 반환** — 캐시가 만료돼 재페치를 부르는데, 요청 폭주 방지 throttle 창 안이면 재페치가 갱신 없이 nil을 낸다.\
  호출부는 그 nil을 "방금 페치했다"로 오인해 만료된 캐시의 키를 그대로 검증에 쓴다.\
  발급자 장애 동안 회전으로 철회됐을 수 있는 키로 무기한 검증하게 된다.
- **리다이렉트 HTTPS 다운그레이드** — https 강제가 정적 문자열 검사라, `CheckRedirect`가 없으면 302로 http(또는 공격자 https)로 끌려가도 그대로 따라간다.

> **stale(오래된) 키** — 회전으로 이미 폐기됐을 수 있는데 캐시에 남아 계속 쓰이는 키.\
> 예: 발급자가 열쇠를 바꿨는데 옛 열쇠로 계속 문을 열어 주는 셈이다.

## 2. 무엇을 고민했나

- **JWK 파싱에 새 라이브러리를 쓸까, stdlib로 수동 파싱할까.** — stdlib 수동 파싱을 택했다(도구 최소주의).\
  인증 뿌리에 새 의존성을 들이는 비용이 파싱 코드 몇 줄보다 크다.
- **throttle 창 중 발급자가 회전한 새 kid가 잠깐 거절되는 것을 감수할까.** — 감수했다.\
  이건 미확인 키를 통과시키는 게 아니라 아직 못 집은 키를 잠깐 거절하는 것이고, 그 반대(폭주로 발급자를 두드리는 것)가 더 나쁘다.\
  GitHub Actions OIDC가 키를 겹쳐 회전하므로 옛 kid와 새 kid가 한동안 공존한다는 근거까지 코드 주석에 남겼다.

## 3. 그래서 이렇게

fail-open 수정의 핵심은 **TTL을 staleness 상한으로 삼는 것**이다.\
"재페치가 nil을 냈다"를 신선함의 증거로 쓰지 않고, 키를 돌려주기 전에 캐시 나이를 다시 잰다.

> **TTL(Time To Live)** — 캐시가 유효한 기간.\
> 예: TTL을 신선함의 상한으로 쓰면, 그 시간이 지난 키는 재페치 결과와 무관하게 stale로 거절된다.

```text
캐시 만료 → 재페치 호출
        ↓
throttle 창 안?  ── 예 ──> 재페치는 갱신 없이 nil
        ↓ 아니오               ↓
     새로 페치           캐시 여전히 만료 상태
        ↓                     ↓
   fresh = true          fresh = false → 키 거절(ErrJWKSStale)
```

빈 kid는 페치 없이 즉시 거절한다 — 키를 특정할 수 없는 요청이 발급자를 두드리게 두지 않는다.\
리다이렉트는 각 hop의 scheme을 강제한다.

## 4. 코드 — 실제 커밋에서

재페치 뒤 신선함을 다시 확인하는 곳이 이 수정의 심장이다.

```go
// internal/auth/jwks.go:189-204 (발췌) — 재페치 후 freshness 재확인
// 재페치가 nil을 냈다고 해서 "방금 신선히 페치했다"는 보장은 없다 — storm throttle
// 창 안이면 refetch는 갱신 없이 nil을 낸다. 따라서 keys[kid]를 반환하기 전에 freshness를
// 재확인한다: 캐시가 여전히 만료 상태면 그 키는 stale이므로 거절한다(TTL = staleness 상한).
fresh := ks.clock.Now().Sub(ks.fetchedAt) < ks.ttl
key, ok := ks.keys[kid]
if !fresh {
    return nil, ErrJWKSStale
}
```

## 5. 구현 중 마주친 문제

리다이렉트 다운그레이드를 막으려던 **1차 수정이 새 fail-open을 만들었다**.\
주입된 클라이언트의 기존 `CheckRedirect`를 무조건 덮어써, 호출자가 이미 건 정책(리다이렉트 전면 금지 등)을 잃었다.

수정 뒤 재점검이 이를 잡아, https 검사를 먼저 하고 기존 정책이 있으면 이어서 적용하는 **정책 합성**으로 바꿨다.\
"한 fix가 다른 fail-open을 판다"는 것을 인증 뿌리에서 직접 겪은 자리다.

## 6. 결론

JWKS가 실동작으로 바뀌면서 게이트 2가 "존재하지만 작동 안 함"에서 벗어났다.\
e2e — 유효 GitHub 토큰이 실제로 게이트 2를 통과하는지 — 는 에이전트 배포 후에만 가능하므로 `[구현 검증]`으로 이연했다.

그것이 실제로 통과한 것은 2026-08-12 첫 실배포다.\
그런데 바로 그 배포가 false-UNKNOWN 사건이 된다 — issue10.\
`[구현 검증]` 값(발급자 URL·TTL·timeout·크기 상한)의 중앙 대장 등재는 후속으로 남았다.
