# issue4 — 게이트 2: OIDC claim을 sub 하나로 판정하지 않는다

- 원본 PR: infra #10 · devlog: `jun-bank/infra/docs/devlog/pr-10-oidc-gate2.md`

## 1. 무엇이 문제였나

게이트 1(HMAC)이 통과해도 "누가 보냈는지"는 모른다.\
아무 저장소·아무 워크플로에서 발급된 GitHub OIDC 토큰도 형식상 유효하기 때문이다.

> **OIDC / claim** — GitHub Actions가 발급하는 신원 토큰과 그 안의 항목들.\
> 예: 토큰에는 발급자(iss)·수신자(aud)·저장소·워크플로 같은 claim이 들어 있고, 게이트 2는 이 항목들로 "우리 파이프라인에서 왔는가"를 판정한다.

> **sub(subject)** — 저장소·ref 등을 하나로 합성한 문자열 claim.\
> 예: `repo:org/name:ref:refs/heads/main` 같은 형태라, 형식이 바뀌면 같은 신원인데도 문자열이 달라진다.

`sub` 하나를 그대로 문자열 비교하면, 형식이 바뀔 때 조용히 통과하거나 조용히 거절된다.\
이 관문의 설계적 핵심은 **무엇을 보지 않기로 했는가**에 있다.

## 2. 무엇을 고민했나

- **JWT 서명 검증을 직접 구현할까, 라이브러리에 맡길까.** — golang-jwt에 맡겼다.\
  서명 검증은 정평 있는 코드에 두는 게 낫다.\
  단 claim 판정은 라이브러리에 맡기지 않고 `WithoutClaimsValidation()`으로 끈 뒤, 모든 대조를 `checkClaims` 한 곳이 소유한다 — claim 규칙은 우리 도메인이라 단일 출처로 둔다.

- **sub를 대조할까, 구성 요소를 각각 볼까.** — 각각 보기로 했다.\
  sub는 합성 문자열이라 대조하면 형식 변화에 조용히 무너진다.\
  sub를 "대조 대상이 아니라 파생값"으로 규정하고, iss·aud·저장소·job_workflow_ref를 각각 본다.

- **저장소를 이름으로 볼까, 수치 ID로 볼까.** — 둘 다 본다.\
  이름은 이전·삭제 후 재생성으로 재사용될 수 있지만, 수치 ID는 재사용되지 않는다.

JWKS 실 공개키 페치는 이 관문의 범위 밖으로 두었다.\
스캐폴드 뒤에 두고, 키를 얻지 못하면 게이트 2가 fail-closed로 전건 거절하는 상태를 의도적으로 유지했다.

## 3. 그래서 이렇게

서명 검증(라이브러리)과 claim 행렬(우리 소유)을 두 조각으로 나눴다.\
알고리즘은 RS256으로 고정해 `"alg":"none"`·대칭키 혼동 공격을 타입 검사와 `WithValidMethods`로 이중으로 막았다.

```text
토큰 도착
        ↓
서명 검증 (golang-jwt · RS256 고정)      alg:none·대칭키 혼동 거절
        ↓
claim 행렬 대조 (checkClaims 단일 출처)
   iss   = 우리 발급자인가
   aud   = 배포 전용값 · 원소 정확히 1개인가
   저장소 = 이름 + 수치 ID 둘 다
   job_workflow_ref = 이 워크플로가 맞는가
   sub   = 보지 않는다 (합성 파생값)
        ↓
jti 선점 (부작용 전 · 토큰 재사용 = 재전송)
```

## 4. 코드 — 실제 커밋에서

"무엇을 보지 않는가"의 결정을 판정 함수 머리에 못박았다.

```go
// internal/auth/oidc.go:317-318
// ★ sub는 검사하지 않는다(DO-11 각주). claims.Subject는 위 칸들의 합성일 뿐이라
// 대조하면 형식 변화에 조용히 무너진다 — 구성 요소를 각각 본 것으로 판정이 끝난다.
```

## 5. 구현 중 마주친 문제

두 곳에서 코드가 바뀌었고, 둘 다 fail-open 방향이었다.

> **fail-open** — 막아야 할 자리에서 판단이 안 서니 통과시키는 방향으로 무너지는 것.

첫째는 **malformed nbf의 무음 통과**였다.\
수치가 아닌 `"nbf":"invalid"`가 0으로 치환되고, 0이면 검증을 생략하므로 서명된 형식 오류 토큰이 거절되지 않았다.\
"키 부재"와 "존재하나 형식 오류"를 구분하도록 고쳤다.

```go
// internal/auth/oidc.go:247-267 (발췌)
// malformed는 키가 존재하나 수치가 아님을 나타낸다 — 이때 0으로 무음 치환하지 않고
// 거절 대상으로 표시해야 한다(있는데 형식 오류 → 거절 · absent와 구분).
func mapUnix(mc jwt.MapClaims, key string) (seconds int64, malformed bool) {
    raw, ok := mc[key]
    if !ok {
        return 0, false // 부재 — 무음 스킵이 아니라 "없음"이다
    }
    ...
}
```

둘째는 **audience 포함 검사**였다.\
"전용값"을 정확 일치가 아니라 포함 관계로 검사해, 우리 값에 다른 audience가 섞인 다중 aud 토큰도 통과했다.\
배열이면 원소가 정확히 1개이고 그 값이 우리 audience여야 한다로 좁혔다.

## 6. 결론

게이트 2의 claim 판정은 섰지만, 실제 JWKS 페치가 스캐폴드로 남아 정상 토큰도 전건 401이 되는 상태였다.\
fail-closed 자체는 맞고 에이전트가 아직 미배포라 안전했으므로, 실 JWKS 페치는 출시 차단 사항으로 이슈 #11에 남겼다 — 그 이슈를 닫는 것이 issue9다.

"운영 승인은 자기 신고"라는 한계는 `OPERATIONAL_APPROVAL_SELF_REPORTED` 표식으로 이력에 남겼다.\
행렬은 배포 대상이 넷이 되면서, "우리 저장소 하나"라는 전역 기대가 "등재된 저장소들 중 하나 + repo↔target 결박"으로 확장된다(PR #29).
