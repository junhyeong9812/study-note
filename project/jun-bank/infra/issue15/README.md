# issue15 — 위성으로 배포를 넓히다: 모른다를 상태로

- 원본 PR: infra #34·#37·#38·#36 · devlog: `jun-bank/infra/docs/devlog/pr-34-38-satellite-transport.md`

## 1. 무엇이 문제였나

.9 한 대에서만 돌던 배포를 정산(.158)·원장(.164) 두 대로 넓히는 일이었다.\
단순히 "CD를 하나 더 붙이는" 일이 아니라, 로컬에서는 없던 문제를 안전하게 다루는 일이었다.

> **위성(satellite)** — 오케스트레이터(.9의 main)의 명령을 받아 자기 호스트에서 배포를 실행하는 별도 서버.\
> 예: main이 HTTP+HMAC 서명 RPC로 명령을 보내고, 위성의 agent가 자기 호스트에서 pull·up 한다.

로컬엔 없던 그 문제는 이렇다 — 다른 서버에 명령을 보냈는데 응답이 오지 않으면 무슨 일이 일어났는지 모른다.\
같은 프로세스가 아니라 네트워크 건너의 일이라, "성공 아니면 실패"라는 이분법이 가장 흔한 사태(응답 유실)를 통째로 빠뜨린다.

## 2. 무엇을 고민했나

처음엔 전송·실행자·복구를 한 작업(#34+#35)으로 담으려 했다.

- **한 슬라이스로 — 전송 + 실행자 + 자동 재개까지.**\
  코드 전에 설계를 검증하자 14개 근본 문제가 나왔고, 그중 다섯이 서로 물려 있었다.\
  매듭의 중심은 자동 재개였다 — "UNKNOWN이면 다시 보낸다"가 중복 실행·영구 미완·만료된 락으로 재실행을 연쇄로 낳았다.
- **세 조각으로 — A(전송·실행자) / B(실행 중 권리 확인) / C(자동 재개).**\
  채택. 정지 규칙에 따라 설계를 되돌려 매듭을 셋으로 갈랐다.\
  자동 재개를 A에서 빼는 것만으로 네 문제가 사라졌다.

> **정지 규칙** — 같은 자리가 반복해 깨지면 패치를 멈추고 토대(슬라이스)를 되돌리는 규율.

## 3. 그래서 이렇게

세 조각을 순서대로 쌓았다 — 단순한 안전장치를 먼저 세우고, 똑똑한 복구를 맨 위에만 얹는다.

```text
조각 A (#34) — 전송·실행자, 최소한
        ↓  "UNKNOWN이면 자동 재개 안 하고 사람에게 올린다"
조각 B (#37) — 실행 중 권리(fencing) 확인
        ↓  역방향 fence-confirm RPC로 "내가 아직 권리자인가"
조각 C (#38) — 자동 재개, 대가를 알고
           attempt 축분리로 "중복 재전송"과 "의도적 재개"를 가름
```

**조각 A** — 응답도 HMAC으로 서명해 위조를 막고(가짜 완료뿐 아니라 가짜 미실행→중복 배포까지 차단), 위성에 crash-safe 원장을 둬 "접수했으나 결과 불명" 상태를 재기동 후에도 UNKNOWN으로 회복한다.\
미실행과 UNKNOWN은 `DialContext` 성공 전후로 보수적으로 가른다 — 연결 전 실패만 미실행, 연결 후 모든 오류는 UNKNOWN.

**조각 B** — 위성이 각 mutation 직전에 main에 fence-confirm RPC를 보내 권리를 되묻는 역방향 채널이다(위성이 .9의 DB에 직접 붙는 건 계정 경계 위반이라).\
sticky guard(한 번 실패하면 영구 denied로 고정해 cleanup의 down까지 차단), DB 시각으로 lease 만료를 한 문장에서 판정하는 것, 그리고 fence-confirm과 실제 docker 실행 사이 창은 남으므로 "봉쇄가 아니라 창을 좁히는 완화"라고 정직하게 표기한 것이 세 장치다.

**조각 C** — command digest(내용)를 충돌 축으로, attempt를 재개 축으로 분리해 "네트워크 중복 재전송"과 "의도적 재개"를 가른다.\
replay 방어는 조각 B의 nonce 패턴을 재사용해, main이 상태를 durable하게 안 들고도 재기동에 안전하게 했다.

> **fencing token** — "지금 배포 권리자는 나"를 증명하는 값.\
> 예: lease를 잃은 위성의 mutation은 fence-confirm에서 거부돼 승자의 배포를 덮지 못한다.

## 4. 코드 — 실제 커밋에서

이 devlog는 실파일 스니펫을 담고 있지 않아, 여기 옮길 코드가 없다(날조 금지).\
대신 조각 A의 crash-safe 원장이 세 번에 걸쳐 좁혀진 핵심 불변식이 산문으로 남아 있다.

정상 원장은 항상 개행으로 끝난다.\
그렇지 않으면 마지막 write가 미완이라는 확실한 신호이고, 그 미완 레코드는 fsync 전이라 버려도 안전하다 — "디스크에 개행까지 도달한 것만 진실"이 그 근본화다.

## 5. 구현 중 마주친 문제

조각 C의 선검증은 놀랍게도 "이 조각을 하지 말자"에 가까웠다.\
위성에서 durable UNEXECUTED가 남는 건 대부분 결정론적 거절(pull 실패·preflight)이라 재실행해도 같은 거절을 재현하고, 실익은 "레지스트리 일시 불통 → 회복 후 성공"이라는 좁은 창 하나뿐이었다.\
그럼에도 완성하기로 하고 조각 A를 의식적으로 재오픈했다 — 선검증이 그 대가를 코드 전에 명확히 해줘 무음 부채가 없었다.

#36에서 실서버에 배선하자, 앞서 만든 계약들이 boot에서 하나씩 fail-closed로 작동했다.\
조각 C의 lease 하한이 ".9의 lease 6분이 재개 사이클 12분을 못 덮는다"며 기동을 거부했고(13분으로 올려 해결), compose-embed의 workspace 배타성이 "0700이 아니다"라며, dispatch 배선이 "COMPOSE_FILE도 함께 필수"라며 거부했다.\
이 거부들이 배선 세부를 순서대로 지도해줬다 — 계약이 문서가 아니라 실행 가능한 안전장치라는 증거다.

뜻밖의 단순화도 있었다 — 이미지가 public이라 대비했던 "호스트별 GHCR pull 자격" blocker가 실무상 없었다.

## 6. 결론

배선이 끝나고 정산·원장을 실제로 배포했다 — CD → main(.9) → 서명 RPC → 위성 → fence-confirm HELD → pull·up.\
양쪽 컨테이너가 healthy로 떴고 applied 원장이 승격됐으며, fence guard가 STALE을 내지 않고 완주한 것이 fence-confirm 왕복이 실서버에서 성공했다는 증거다.\
"위성 배포·롤백 실행 불가"로 오래 남아 있던 칸이 닫혔고, 배포 대상 넷(코어·정산·원장·게이트웨이)이 전부 실동작한다.

이 여정이 남긴 두 교훈이다.\
첫째, 모른다는 것을 상태로 만들어야 한다 — "성공 아니면 실패"는 응답 유실을 빠뜨린다.\
둘째, 똑똑한 복구는 단순한 안전장치 위에서만 안전하다 — 자동 재개는 멱등 원장·권리 확인·시간 예산이 다 선 뒤에야 얹을 수 있고, 그 전에는 "모르면 사람을 부른다"가 옳은 기본값이다.
