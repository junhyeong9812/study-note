# issue3 — 게이트 1: HMAC 서명만으로는 재전송을 못 막는다

- 원본 PR: infra #8 · devlog: `jun-bank/infra/docs/devlog/pr-08-hmac-gate1.md`

## 1. 무엇이 문제였나

배포 API는 인터넷에서 도달 가능한 원격 코드 실행이라, 첫 관문에서 서명이 실패하면 적용하지 않는다.\
그런데 이 관문의 진짜 주제는 서명이 아니라 **재전송**이었다.

> **HMAC** — 공유 비밀키로 요청을 돌려 만든 인증 코드.\
> 예: 같은 키를 가진 쪽만 같은 서명 값을 다시 만들 수 있어, 서명이 맞으면 "우리가 보낸 것"이 증명된다.

> **재전송(replay)** — 유효한 요청을 가로채 그대로 다시 보내는 것.\
> 예: 배포 한 건의 유효 요청을 탈취하면, 서명이 진짜이므로 같은 배포를 언제든 다시 실행할 수 있다.

HMAC은 진위를 증명할 뿐 신선도(freshness)를 보장하지 않는다.\
유효 요청 한 건을 탈취하면 같은 배포를 언제든 다시 실행할 수 있고, 프록시·CI의 타임아웃 재시도와 응답 유실도 같은 결과를 만든다.\
공격과 사고가 같은 모양이라는 것이 핵심이다.

배포는 "실패한 재실행이 조용히 성공으로 보이는" 조작이라, 무음 무시 금지가 더 세게 적용된다.

## 2. 무엇을 고민했나

- **멱등 판정을 writer 코드가 검사하게 할까, DB 제약이 하게 할까.** — DB의 UNIQUE 제약을 택했다.\
  writer의 선의에 기대면 그 코드의 버그·경쟁 하나가 재전송 방어를 통째로 연다.\
  제약은 INSERT 시점에 판정이 서므로, 어떤 코드 경로로 들어오든 무관하다.

> **멱등(idempotent)** — 같은 요청을 여러 번 받아도 결과가 한 번 받은 것과 같은 성질.\
> 예: 배포 채널의 멱등 키는 requestId이고, 같은 requestId 재수신은 재실행하지 않고 최초 결과를 되돌린다.

- **정규화를 서명자와 검증자가 각각 구현할까, 한 곳에서만 정의할까.** — `Canonicalize` 한 곳을 택했다.\
  CI 서명자와 이 검증자는 반드시 같은 형태를 만들어야 하는 실계약이다.\
  두 곳에 두고 한쪽만 바꾸면 모든 서명이 조용히 불일치하는데, 그 어긋남은 눈에 보이지 않는다.

- **진위와 신선도 중 무엇을 먼저 볼까.** — 진위(상수 시간 비교)를 먼저 본다.\
  서명이 위조면 그 안의 시각 값은 믿을 것이 못 되기 때문이다.

## 3. 그래서 이렇게

서명 범위는 정규화된 method·path·body digest·requestId·issuedAt·expiresAt이다.\
멱등 선점은 부작용 전에 requestId(와 OIDC의 jti)를 내구적으로 예약하는 것이고, 판정은 UNIQUE 제약에 의해 INSERT 시점에 선다.

```text
요청 도착 (method·path·body·requestId·issuedAt·expiresAt)
        ↓
진위 검증 (HMAC 상수 시간 비교)      위조면 거절
        ↓
신선도 검증 (issuedAt·expiresAt)     만료면 거절
        ↓
멱등 선점 (requestId·jti INSERT)
        ↓
   UNIQUE 충돌?
        ↓ 아니오               ↓ 예
   신규 → 예약 성립        저장된 digest와 대조 (3분기)
```

## 4. 코드 — 실제 커밋에서

중복이 잡히면 저장된 body digest와 대조해 세 갈래로 나눈다.

```go
// internal/store/store.go:459-476 (발췌) — 멱등 3분기
switch {
case errors.Is(qErr, sql.ErrNoRows):
    // requestId는 신규인데 INSERT가 중복으로 실패했다 = jti 재사용(토큰 재전송).
    return ErrReplay
case storedDigest == bodyDigest:
    // 동일 requestId + 동일 digest = 같은 요청의 재전송 → 재실행 금지.
    return ErrReplay
default:
    // 동일 requestId + 다른 digest = 거절·기록해야 하는 충돌.
    return ErrDigestConflict
}
```

## 5. 구현 중 마주친 문제

두 곳에서 "닫혀야 할 것이 열리는" 방향(fail-open)이 나와 코드가 바뀌었다.

> **fail-open** — 실패했을 때 막지 않고 통과시키는 방향으로 무너지는 것.\
> 예: 판단이 안 서면 거절해야 할 자리에서, 판단이 안 서니 그냥 통과시키는 것.

첫째는 **빈 requestId**였다.\
빈 ID도 올바르게 서명하면 인증과 예약을 통과하는데, 그러면 모든 무-ID 요청이 멱등 키 `""`를 공유해 서로의 예약과 충돌한다(선점 붕괴).\
예약에 닿기 전, 게이트 1에서 거절하도록 고쳤다.

```go
// internal/auth/auth.go:199-206 (발췌)
// 비었거나 공백만 있으면 모든 무-ID 요청이 멱등 키 ""를 공유해 서로의 예약과 충돌한다
// (선점 붕괴·DoS). 예약(Reserve)에 닿기 전 게이트 1에서 거절한다.
if strings.TrimSpace(req.RequestID) == "" {
    return Decision{Accepted: false, Reason: "requestId 비어 있음 (멱등 키 필수)"}, nil
}
```

둘째는 **시계 편차(skew) 0의 무시**였다.\
운영자가 `0s`(엄격)를 명시해도 값 타입의 0과 "미설정"이 구별되지 않아, 기본값 60초로 조용히 완화됐다.\
`Config.Skew`를 포인터로 바꿔 "미설정(nil)"과 "명시적 0s"를 구분했다.

```go
// internal/auth/auth.go:93-101 (발췌)
// 포인터로 두어 "미설정(nil)"과 "명시적 0s(엄격)"를 구분한다 — 값 타입이면 둘 다
// 0이라, 운영자가 명시한 무-skew(엄격)가 기본값(60s)으로 조용히 완화된다.
Skew *time.Duration
```

## 6. 결론

게이트 1이 섰고, 검증은 거절 경로 red-first(위조·만료·재전송이 실제로 거절되는지 먼저 실패시켜 확인)와 실 MySQL 통합으로 했다.
