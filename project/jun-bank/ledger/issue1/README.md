# issue1 — CD 신설: 원격 위성 배포 대상이 되다

- 원본 PR: ledger #2 · devlog: `jun-bank/ledger/docs/devlog/pr-02-cd.md`

---

## 1. 무엇이 문제였나

원장(ledger)은 배포 대상 넷 중 하나로 이미 정해져 있었지만, 정작 배포될 수 없었다.\
ADR-027이 "원장은 .164로 배포한다"까지 정해 뒀는데, 정작 배포를 요청할 워크플로(CD)가 없었기 때문이다.\
서비스는 스켈레톤 상태로 빌드 CI(이미지 빌드)만 있었고, 만들어진 이미지를 배포로 연결할 마지막 칸이 비어 있었다.

> **ADR** — Architecture Decision Record. "무엇을 왜 이렇게 정했다"를 한 건씩 남기는 결정 기록.\
> 예: ADR-027이 "배포 대상은 core·gateway·정산·원장 넷이고 원장은 .164에 둔다"를 못 박아 둔 문서다.

> **CD** — Continuous Deployment. 여기서는 "빌드된 이미지를 배포해 달라는 서명된 요청을 발행하는 워크플로"를 가리킨다.\
> 예: 이미지가 GHCR에 올라가면 CD가 "이 이미지를 이 대상에 배포해 달라"는 요청 하나를 서명해 내보낸다.

그리고 원장은 core·gateway와 배포 형태부터 다르다 — **원격 위성**이다.\
core·gateway는 배포 오케스트레이터가 사는 .9에서 그대로 실행되지만, 원장은 .9의 main이 서명 RPC로 다른 호스트(.164)의 agent에 명령을 보내야 그 agent가 실행한다.\
"배포 대상이지만 실행 경로가 없다"는 칸(CDT-1)이 오래 비어 있던 이유가 여기 있다.

> **원격 위성(remote satellite)** — 오케스트레이터와 다른 호스트에 떨어져 있어, 명령을 원격으로 받아 스스로 실행하는 배포 대상.\
> 예: .9의 main이 직접 컨테이너를 올리는 게 아니라, .164에 있는 agent에게 "올려라" 하고 서명된 요청만 보낸다.

## 2. 무엇을 고민했나

원장의 CD를 **새로 설계할지, core의 원형을 복제할지**가 첫 갈림이었다.

- 새로 설계 — 원장에 맞춰 입력·검증을 처음부터 짠다. 자유롭지만, core가 이미 정착시킨 입력 하드닝·compose 동봉·서명 계약을 다시 발명해야 하고 미묘하게 어긋날 위험이 있다.
- core 원형 복제 — core의 `deploy.yml`을 바이트 수준으로 그대로 옮기고, 대상만 바꾼다. 검증된 방어선을 그대로 물려받는 대신, "무엇이 원장 고유인가"를 5줄로 좁혀야 한다.

복제를 골랐다 — 배포 요청의 계약은 대상이 로컬이든 위성이든 같아야 하므로, 원형을 벗어날 이유가 없었다.

두 번째 고민은 **이미지 변수를 무엇으로 쓰나**였다.

- per-target 변수 `${LEDGER_IMAGE}` — 대상 이름이 그대로 드러나 직관적이다. 하지만 agent의 검증기가 걸러낸다(§5).
- 전역 단일 `${CORE_IMAGE}` — 대상 이름과 무관해 보여 어색하지만, agent가 요구하는 형태다.

전역 변수를 골랐다 — 어색함보다 "검증기를 통과하는 형태"가 계약이기 때문이다.

세 번째로, **배포 모드(로컬이냐 위성이냐)를 CD가 정할지 agent가 정할지**를 저울질했다.\
CD가 만드는 것은 "서명된 배포 요청 하나"뿐이고, 그것이 로컬 배포로 풀리든 원격 위성 배포로 풀리든 요청의 계약은 같다.\
그래서 배포 모드는 CD가 아니라 **agent 쪽이 정하게** 두었다 — CD는 모드를 모른 채 요청만 발행한다.

## 3. 그래서 이렇게

core의 `deploy.yml`을 원형으로 **바이트 수준 복제**하고, 원장 고유의 5줄(target·이미지 저장소·concurrency 그룹·요청 ID 접두)만 바꿨다.\
입력 하드닝(브랜치·fork 우회를 막는 4항 AND 가드, 표현식 보간을 env로 격리, SHA 40hex 검증), compose 동봉, 배포 대상 SHA로 checkout — 이 방어선은 전부 core에서 그대로 물려받았다.

> **compose 동봉** — 배포 요청 안에 실행할 compose 정의를 함께 실어 보내는 것. 한 번 읽은 버퍼에서 sha256과 base64를 함께 산출해 요청(manifest)에 담는다.\
> 예: agent는 "이 이미지를 올려라"만 받는 게 아니라 "이 compose 그대로 올려라"를 서명과 함께 받으므로, 실행 정의가 중간에 바뀔 수 없다.

원장의 정본 compose는 최소형이다 — 스켈레톤이라 상태 볼륨도 환경변수도 없어, 서비스 하나(`app`)에 이미지·포트·healthcheck만 있다.

배포 요청 하나가 지나가는 경로는 이렇다.

```text
.9  main (ROLE=main)          배포 요청을 서명해 발행 (모드는 모름)
        ↓  서명 RPC
.164 위성 agent               서명·compose 검증 후 실행 (여기서 배포 모드 결정)
        ↓  fence-confirm
pull · up                     GHCR digest 받아 compose 그대로 기동
        ↓
ledger-app-1  healthy         healthcheck 통과
```

> **fence-confirm(펜싱 확인)** — 실행 직전에 "지금 이 요청이 유효한 최신 요청이 맞나"를 한 번 더 확인해, 오래되거나 중복된 요청이 실행되는 것을 막는 단계.\
> 예: 이전 배포 요청이 뒤늦게 도착해도, 펜싱 확인에서 걸러져 최신 것만 올라간다.

바뀌기 전과 후를 나란히 놓으면 이 작업이 채운 칸이 보인다.

```text
수정 전                               수정 후
+---------------------------+        +---------------------------+
| 빌드 CI (이미지 빌드)만    |        | 빌드 CI + CD (요청 발행)   |
| CD 없음 → 배포 요청 불가   |        | main → 서명 RPC → .164     |
+---------------------------+        +---------------------------+
  → 배포 대상이나 실행 못 함           → 위성으로 실배포 완주
```

CD는 원장을 "배포 대상"에서 "실제로 배포되는 대상"으로 옮긴 마지막 칸이다.

## 4. 코드 — 실제 커밋에서

원장의 정본 compose. 이미지 변수가 전역 `${CORE_IMAGE}`인 점이 핵심이다(§5).

```yaml
# deploy/compose.yml — 최소 정본(agent allowlist 통과 형태)
services:
  app:
    image: ${CORE_IMAGE}                    # 전역 DEPLOY_IMAGE_ENV 계약(agent가 digest 주입)
    ports: ["${DEPLOY_HOST_PORT}:8080"]
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://127.0.0.1:8080/actuator/health || exit 1"]
      ...
```

> **digest 주입** — agent가 이미지 태그가 아니라 내용 해시(digest)로 고정된 이미지를 변수에 넣어 주는 것. "그 순간의 정확히 그 이미지"가 뜬다.\
> 예: `${CORE_IMAGE}` 자리에 agent가 `...@sha256:...` 형태의 고정 참조를 주입하므로, 같은 태그가 나중에 다른 내용으로 바뀌어도 배포본은 흔들리지 않는다.

`...`은 devlog 정본에서 healthcheck 세부(interval·timeout 등)를 줄인 자리다 — 원본 devlog가 그렇게 축약해 실었다.

## 5. 구현 중 마주친 문제

**이미지 변수 함정.**\
직관적으로는 `${LEDGER_IMAGE}`를 써야 할 것 같았지만, agent의 검증기는 **전역 단일** `DEPLOY_IMAGE_ENV`(현재 `CORE_IMAGE`)를 모든 대상에 적용한다.\
per-target 변수를 쓰면 정확 일치 검증에 걸려 정본이 allowlist를 통과하지 못한다 — 그래서 gateway와 마찬가지로 `${CORE_IMAGE}`로 맞췄다.

> **allowlist(허용 목록) 검증** — agent가 "미리 정해 둔 정확한 형태와 한 글자도 다르지 않은가"로 compose를 통과시키는 방식.\
> 예: 변수 이름이 `LEDGER_IMAGE`면 목록의 `CORE_IMAGE`와 다르므로 통째로 거절된다.

**실배포는 CD만으로 닫히지 않았다.**\
CD를 머지해도 .164에 위성 agent가 아직 배선되지 않아, 실제 배포는 곧바로 되지 않았다.\
CD 시점의 검증은 로컬에서 할 수 있는 데까지만 했다 — core와의 diff가 의도된 5줄(compose는 헤더 1줄)뿐임을 확인하고, agent의 실제 검증기로 정본이 allowlist를 통과함을, self-assertion 스모크로 manifest 조립을 확인했다.\
실배포는 위성에 agent가 배선된 뒤(infra#36)에야 가능했다.

## 6. 결론

지금 상태 — 원장의 CD가 머지되며 이미지가 GHCR에 올랐고, infra#36에서 .164에 위성 agent가 배선된 뒤 실배포가 완주됐다.\
main → 서명 RPC → .164 위성 → fence-confirm → pull·up으로 `ledger-app-1`이 healthy로 떴다.\
오래 "위성 배포 실행 불가"로 남아 있던 칸(CDT-1)이 정산·원장의 실배포로 닫혔다.

남은 빚·경계.\
배포 모드(로컬/위성)는 CD가 모르는 채 agent가 정하므로, 대상별 배포 방식은 CD가 아니라 agent 배선에 달려 있다.\
이미지 변수도 전역 단일 `CORE_IMAGE` 계약에 묶여 있어, agent가 `DEPLOY_IMAGE_ENV`를 바꾸면 모든 대상 compose가 함께 움직여야 한다.\
분산 실행 층의 전체 이야기는 infra의 위성 여정 devlog(`jun-bank/infra/docs/devlog/pr-34-38-satellite-transport.md`)에 있다.
