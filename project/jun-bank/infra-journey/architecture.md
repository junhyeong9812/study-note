# 배포 인프라 아키텍처 — 구조와 신뢰 경계

이 문서는 배포 파이프라인의 정적 구조를 읽는다 — 배포 요청이 어디서 출발해 어떤 단계를 거쳐 실행되는지, 각 컴포넌트가 무엇을 소유하는지, 신뢰 경계가 어디에 그어져 있는지. 여정([README.md](README.md))이 "어떻게 자랐나"라면 이 문서는 "지금 어떻게 서 있나"다. 각 구조의 결정 근거는 ADR이 소유하고, 여기서는 그 결과물을 조감한다.

## 전체 흐름 — 발행에서 실행까지

배포 한 건은 여섯 구간을 지난다.

**⑴ 발행 (각 서비스 repo의 CI/CD).** main 머지가 `build-and-push` 워크플로를 깨워 이미지를 빌드하고 GHCR에 커밋 SHA 태그로 올린다. 그 성공이 `deploy-request` 워크플로를 깨우고, 이 워크플로가 배포 요청 manifest를 조립한다 — 배포 대상·커밋 SHA·이미지 digest·compose 내용(base64)·compose revision(그 내용의 sha256)·app 서비스명·요청 ID·발급/만료 시각. 그리고 두 서명을 붙인다: 워크플로가 가진 HMAC 키로 요청 본문을, GitHub OIDC 토큰으로 "이 요청이 정말 이 repo의 main에서 나왔다"를 증명한다.

**⑵ 엣지 (오라클 클라우드).** 공개 도메인(`deploy.junproject.xyz`)이 집의 공인 IP로 요청을 프록시한다. 엣지는 인증하지 않는다 — 전달만 한다. 판정 주체가 둘이 되면 "거절이 어디 기록되나"가 흐려지기 때문이다(ADR-027 DO-1).

**⑶ 게이트 1 — HMAC (배포 agent).** agent가 요청 본문의 digest와 요청 ID·시각을 정규화해 HMAC을 재계산하고 대조한다. 서명이 맞아도 발급/만료 시각으로 신선도를 보고, requestId를 부작용 전에 원장에 선점한다(재전송 = 같은 배포의 재실행).

**⑷ 게이트 2 — OIDC (배포 agent).** GitHub 발급자의 JWKS 공개키로 토큰 서명을 검증하고, claim을 행렬로 대조한다 — 발급자·audience·저장소 수치 ID·ref·워크플로 경로. 그리고 저장소가 이 배포 대상을 배포할 권한이 있는지(repo↔target allowlist) 확인한다. 두 게이트는 AND다.

**⑸ 오케스트레이션 (배포 agent).** 모드 판정(dev 자동 / 운영 승인) → 배포 창 락 획득 → mode version 재검증 → manifest 엄격 검증 → dispatch 직전 fencing 재확인. 각 단계의 실패가 "락을 풀 실패"인지 "락을 쥔 채 사람을 부를 실패"인지 갈린다.

**⑹ 실행 (배포 agent + gateway).** compose 정의를 검증(strict YAML·allowlist)한 뒤 workspace에 해시 명명 파일로 굳히고, 이미지 pull(digest 고정) → compose up → 이미지 무결성 대조 → 헬스체크. core면 여기에 라우트 전환·드레인·구 슬롯 종료가 더해진다(블루-그린). gateway면 재기동 교체다.

## 컴포넌트 — 무엇이 무엇을 소유하나

배포 agent는 단일 Go 바이너리이고, 역할은 `ROLE` env로 정한다(`main`/`agent`) — 프로세스를 나누지 않고 모드로 가른다. 내부는 소비 지점 인터페이스로 평평하게 짜여 있다(클린 4겹 폴더를 이식하지 않음 — Go를 고른 이유인 작은 코드 표면을 지키기 위해). 주요 패키지가 소유하는 것:

**httpentry** — HTTP 진입 미들웨어 체인. 전송 제한(method·body 크기)·게이트 1·게이트 2·repo↔target 결박·멱등 선점을 순서대로 엮는다. 순서 자체가 계약이다. 상태를 가진 오케스트레이션은 이 층 밖이다.

**auth** — HMAC 서명 검증과 OIDC claim 행렬. 서명 정규화(`Canonicalize`)와 claim 판정(`checkClaims`)이 각각 단일 출처다 — CI 서명자와 이 검증자가 같은 형태를 만들어야 하므로 정규화가 한 곳에만 있다.

**store** — 배포 스키마(MySQL)로의 유일한 통로. 일반 Exec/Query를 노출하지 않아 raw DML이 코드에서 도달 불가능하다 — DB GRANT에서 금지한 것을 코드도 금지한다.

**deploy (coordinator·dispatcher)** — 락·모드·manifest 검증의 오케스트레이션과, pull·up·헬스·전환의 실행. 실행 결과를 세 상태(미실행/완료/UNKNOWN)로 판정하는 로직이 여기 있다.

**dispatch** — 특권 명령(docker·compose)의 실제 실행. 열거된 명령만 argv 슬라이스로 실행해 raw shell을 원천 차단한다.

**compose** — 동봉 compose의 strict 검증기와 workspace 세대 관리. YAML을 노드째 순회해 검증기와 compose가 같은 구조를 보게 한다.

gateway repo는 이 흐름의 두 지점에 관여한다 — 자신도 배포 대상(재기동 교체)이면서, core 블루-그린의 라우트 전환을 실행하는 지점이다. 라우트 상태(활성 슬롯·fencing token)의 정본은 게이트웨이의 SCG 라우트 한 곳이고, 상태 파일로 재기동 너머까지 보존된다.

## 신뢰 경계 — 어디까지 믿나

이 아키텍처가 그은 경계 몇 개가 구조를 규정한다.

**서명 안 vs 밖.** 판정에 쓰는 값은 서명 범위 안의 것뿐이다 — OIDC 토큰처럼 서명 밖이지만 스스로를 증명하는 것은 예외적으로 쓰되, 그 재사용은 jti 선점이 막는다. compose는 서명에 동봉되어 내용째 결박되지만, 설정 값·시크릿은 서명 밖(호스트 소유)이라 manifest는 버전 식별자만 싣는다 — compose는 내용 결박, config는 버전 단언 결박이라는 강도 차이가 있다.

**digest·content-address로 고정.** 이미지는 태그가 아니라 digest로, compose는 이름표가 아니라 sha256으로 참조된다. "무엇이 실행되는가"가 이름이 아니라 내용으로 고정되어, 낡거나 변조된 것이 이름만 맞아 실행되는 길이 없다.

**파일시스템 공존-쓰기자는 경계 밖.** agent workspace에 쓸 권한을 가진 프로세스는 신뢰 경계 밖이다 — 그 프로세스는 applied 인덱스도 agent env도 조작할 수 있으므로, 그 층의 완전 봉쇄는 이 설계의 목표가 아니다. 방어선은 장기 보관 파일의 우발 손상·드리프트(재해시)와 검증-실행 사이 창(불변 스냅샷)까지다.

**두 게이트의 순서.** 서명이 SSH보다 먼저다 — 순서가 뒤집혀 전달이 먼저면 서명 없는 요청이 호스트에 닿는 경로가 생긴다. 이 순서가 패키지 구조로 인코딩되어 관례가 아니라 구조적 속성이 됐다.

## 데이터 — 배포 스키마

배포의 상태는 MySQL의 `deploy` 스키마에 있다. 세 종류다 — 배포 창 락(단일 행, 저장 프로시저로만 전이, fencing token 단조), 재전송 방어 원장(append-only, requestId·jti UNIQUE), 배포 이력·모드(append-only). "자유롭게 갱신되는 행"이 하나도 없다는 것이 이 스키마의 성질이고, agent 계정은 다른 어느 스키마에도 접근이 없다 — 그 부재가 곧 강제다.

## 배포 위상 — 세 집 서버 + 클라우드 엣지

현재 실물은 집의 세 서버(.9 허브·.158 임베딩·.164 LLM)와 오라클 클라우드 엣지다. .9가 상태 저장(DB·볼륨)과 배포 오케스트레이션을 겸한다 — 디스크가 넉넉하지만 CPU가 가장 약한 특성에 맞춘 배치다. 인프라 도구 자체는 컨테이너로 띄우지 않는다(docker·systemd를 제어해야 하므로) — 네이티브 바이너리로 systemd 유닛 상주한다. 이 위상이 "각 호스트가 자기 서버를 배포한다"는 토폴로지 결정의 결과이고, 그 결정이 초기의 SSH 기반 구조를 HTTP+서명 RPC로 갈아엎은 계기였다([infra pr-07](../../../../infra/docs/devlog/pr-07-http-skeleton.md)).
