# issue3 — 이미지 발행 전 테스트: 발행 관문

- 원본 PR: gateway #5 · devlog: `jun-bank/gateway/docs/devlog/pr-05-ci-test.md`

## 1. 무엇이 문제였나

그때까지 CI는 `docker build`만 했다.\
그래서 깨진 코드의 이미지가 GHCR에 올라가고, 배포 agent가 그 digest를 집어갈 수 있었다.

> **GHCR / digest** — GHCR은 GitHub이 제공하는 컨테이너 이미지 저장소, digest는 그 이미지를 가리키는 내용 기반 지문(sha256)이다.\
> 예: agent는 "가장 최근 digest"를 집어 배포하므로, 깨진 이미지가 올라가면 그게 그대로 배포된다.

원인은 빌드 구조에 있었다.\
Dockerfile의 빌드 스테이지는 `bootJar`만 만들고 테스트를 실행하지 않는다.\
CI 잡에도 테스트 스텝이 없으니, 어디에서도 테스트가 돌지 않은 채 이미지가 발행되고, 그 이미지는 CD를 통해 자동으로 배포 요청이 됐다.

issue1에서 만든 21건의 테스트가 정작 배포 경로를 지키지 못하는 상태였다.

## 2. 무엇을 고민했나

"어떻게 발행을 막을 것인가"에서 갈래는 둘이었다.

- **별도 게이트/조건문으로 발행 차단** — 테스트 결과를 보고 push 여부를 분기한다.\
  안전장치를 하나 더 얹는 방식이라 유지할 조건이 늘어난다.
- **스텝 순서 자체를 보증 수단으로** — 테스트를 GHCR 로그인·빌드·push **앞에** 둔다.\
  GitHub Actions의 스텝은 순차 실행이고 실패하면 잡이 중단되므로, 앞에서 막으면 이미지가 발행되는 경로 자체가 사라진다. (채택)

채택안은 별도 게이트나 조건문이 필요 없다는 게 값어치다.\
"이미지가 발행되려면 그 앞의 테스트를 반드시 통과해야 한다"가 순서만으로 성립한다.

## 3. 그래서 이렇게

테스트 스텝을 로그인·빌드·push 앞에 뒀다.

```text
checkout
        ↓
JDK 21 셋업
        ↓
테스트 (gradlew test)          여기서 실패하면 잡 중단 → 아래로 못 감
        ↓
GHCR 로그인
        ↓
빌드 · push                    테스트를 통과해야만 여기 도달
```

## 4. 코드 — 실제 커밋에서

주석이 채택 논리를 그대로 담고 있다.

```yaml
# .github/workflows/build.yml:21-33 (발췌)
# 테스트를 이미지 빌드보다 **먼저** 돌린다.
# Dockerfile 의 빌드 스테이지는 bootJar 만 만들 뿐 테스트를 실행하지 않으므로,
# 이 스텝이 없으면 깨진 코드로 만든 이미지가 그대로 GHCR 에 push 되고
# 배포-agent 가 그 digest 를 집어간다(ADR-027). 스텝은 순차 실행이고 실패 시
# 잡이 중단되므로, 여기서 막으면 이미지 자체가 발행되지 않는다.
- name: 테스트
  run: ./gradlew --no-daemon test
```

채택 시점에 비용도 기록됐다.\
컴파일이 2회(테스트용 + Docker 빌드용) 돌아 잡 시간이 는다.\
이 잔여가 나중에 issue5(#7 CI 정비 — 빌드 1회화·wrapper 검증)로 이어졌다.

## 5. 구현 중 마주친 문제

검증에서 UP-TO-DATE 함정을 짚었다.\
Gradle은 입력이 안 바뀌면 테스트를 캐시로 건너뛰고 성공을 보고할 수 있다.

> **UP-TO-DATE 함정** — 빌드 도구가 "입력이 그대로면 다시 안 돌려도 된다"며 캐시 결과로 성공을 보고하는 것.\
> 예: 테스트를 안 돌렸는데 초록불이 뜬다 — "통과했다"가 "실제로 돌았다"가 아닐 수 있다.

그래서 로컬 확인을 `--rerun-tasks`로 강제 재실행해, 테스트가 실제로 돌았는지를 확인했다.\
이 변경의 계약은 스텝 순서 그 자체이므로, YAML 파싱과 순서 확인(checkout → JDK 21 → test → 로그인 → 빌드·push)이 검증의 본체였다.

## 6. 결론

issue1의 잔여 목록 중 "테스트가 배포 경로를 못 지킨다"가 닫혔다.\
이제 테스트를 통과하지 못한 이미지는 발행 경로에 오르지 못한다.

남은 것들 — `/internal` 인가(issue4), 드레인 실계수 — 은 각자의 이슈로 진행되고, 빌드 1회화는 issue5가 이어받는다.
