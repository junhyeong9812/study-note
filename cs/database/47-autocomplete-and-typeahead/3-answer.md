# database/47-autocomplete-and-typeahead — 정답

## 정답

### 1. 자동완성이 다른 점

1. 질의가 완성된 용어가 아니라 **단어의 앞부분**이다.
2. 요청이 **키 입력 수만큼** 온다. 한 검색어에 요청이 여러 개다.
3. 결과는 관련도보다 **인기도 상위 k개**가 중요하다. 짧은 접두사는 후보가 수만 개라 모아서 정렬하면 늦다.

### 2. 접두사 LIKE와 인덱스

- `CREATE INDEX … ON suggest (term text_pattern_ops);`
  - C가 아닌 로케일에서는 기본 연산자 클래스가 로케일 정렬 규칙으로 비교한다. `text_pattern_ops`는 글자 단위로 비교해 `LIKE '접두사%'`를 구간 조건으로 바꿀 수 있다.
- `Index Cond: ((term ~>=~ '삼성') AND (term ~<~ '삼섲'))` — 접두사 이상, 마지막 글자를 하나 올린 값 미만.
- `LIKE '삼%'`: 20만 행 중 6만 행(30%)이 맞는다. 선택도가 나빠 planner가 병렬 순차 스캔 + top-N heapsort를 골랐다.

### 3. 한글 음절 산술

- '삼' = 0xC0BC = 49340, SIndex = 49340 − 44032 = 5308.
  - 초성 = 5308 ÷ 588 = **9** (ㅅ)
  - 중성 = (5308 mod 588) ÷ 28 = 16 ÷ 28 = **0** (ㅏ)
  - 종성 = 5308 mod 28 = **16** (ㅁ)
- 합성: `0xAC00 + (9 × 21 + 4) × 28 + 21` = 44032 + 193 × 28 + 21 = 44032 + 5404 + 21 = 49457 = U+C131 = '성'.

### 4. "삼ㅅ" 0건과 자모 분해

- "삼ㅅ"의 마지막 글자는 호환 자모 ㅅ(U+3145)이다. 어떤 완성형 음절도 "ㅅ"으로 시작하지 않는다. 그래서 음절 문자열 `'삼ㅅ%'`와 맞는 용어가 없다(재현 0행).
- 자모로 풀면 `ㅅㅏㅁㅅ`이 되고 `삼성` = `ㅅㅏㅁㅅㅓㅇ`의 접두사다(재현 20000행).
- 겹모음·겹받침
  - "과"를 치는 도중 IME는 "고"를 보낸다. "과"를 `ㄱㅘ`로 두면 `ㄱㅗ`가 접두사가 아니다. `ㄱㅗㅏ`로 펴야 한다.
  - "닭"을 치는 도중 "달ㄱ"이 온다. `ㄷㅏㄹㄱ`로 펴야 맞는다.

### 5. edge n-gram vs completion

| | edge n-gram / search_as_you_type | completion suggester |
|---|---|---|
| 자료구조 | 역색인에 접두사 용어를 펼쳐 넣는다 | 메모리의 가중 FST |
| 속도 | 일반 검색 질의 | 가장 빠름(ES 문서: 속도 최적화) |
| 순위 | 질의 시점 점수(BM25, 함수 점수) | 색인 때 넣은 `weight` |
| 갱신 | 문서 재색인 | weight 변경 = 재색인. FST는 만들기 비싸다 |
| 기능 | 중간 단어 완성·필터 결합 쉬움 | 접두사 완성 중심 |

- 색인 때 "삼성전자"를 "삼·삼성·삼성전·삼성전자"로 펼쳐 둔다. 검색어 "삼성"까지 펼치면 "삼"도 질의 용어가 되어 "삼겹살"이 섞인다. 그래서 검색어는 자르지 않는 `search_analyzer`를 둔다.

### 6. QPS 폭증

- 서버
  - 짧은 접두사마다 후보 수만 개를 정렬한다 → 접두사별 top-k를 미리 계산한다.
  - 캐시가 없다 → 사용자 무관 접두사 응답을 공유 캐시에 둔다.
  - 자동완성이 검색과 같은 노드를 쓴다 → 인덱스·노드를 분리해 장애가 번지지 않게 한다.
- 클라이언트
  - 디바운스가 없다 → 입력이 멈춘 뒤 100~200ms(예시) 뒤에 요청한다.
  - 최소 길이가 없다 → 1~2글자는 요청하지 않거나 사전 결과만 쓴다.

### 7. 응답 순서 역전

- 원인: "삼" 요청이 "삼성" 요청보다 늦게 도착했다. 클라이언트가 도착 순서대로 그렸다.
- `AbortController`만으로는 부족할 수 있다.
  - 취소가 닿기 전에 응답이 이미 도착해 처리 중일 수 있다.
  - 캐시·서비스 워커를 거치는 경로가 섞이면 순서를 다시 확인해야 한다 [?].
- 그래서 응답에 질의 문자열(또는 요청 번호)을 담고, 현재 입력과 같을 때만 그린다.
- 취소만으로 서버 부하가 준다는 보장은 없다. 이미 서버에 도착한 요청은 계속 처리될 수 있다. 서버가 연결 종료를 감지해 작업을 취소하는 구성(예: Elasticsearch 검색)에서만 서버 쪽 일도 준다.

### 8. max_gram 3과 "apple"

- 색인 용어는 `a`·`ap`·`app`까지만 있다. 검색어 "apple"은 자르지 않으므로 맞는 용어가 없어 **0건**이다.
- `truncate`로 검색어를 "app"으로 자르면 찾기는 하지만 "apply", "approximate"도 함께 나온다(ES 문서 예). 검색어가 길수록 정밀도가 떨어진다.
- 대안: `max_gram`을 늘리거나(색인 증가, 재색인 필요), 원문 필드 일반 match를 함께 건다.
