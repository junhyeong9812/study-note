# database/06-pages-and-tuple-layout — 정답

## 정답

### 1. 왜 페이지 + 슬롯 배열인가

- 디스크는 블록 단위로 읽고 쓴다. 그래서 DB도 고정 크기 페이지 단위로 파일을 다룬다(PostgreSQL 기본 8KB, InnoDB 기본 16KB).
- 행 길이는 제각각이다. 페이지 안 어디에 어떤 행이 있는지 적어 둘 목차가 필요하다. 그것이 슬롯 배열이다.
- 슬롯이 없으면 곤란한 점
  - 행을 "바이트 오프셋"으로 가리켜야 한다. 빈 공간을 모으려고 행을 옮기면 그 행을 가리키던 인덱스를 전부 고쳐야 한다.
  - 슬롯이 있으면 행 주소는 (페이지, 슬롯 번호)다. 행이 페이지 안에서 움직여도 슬롯의 오프셋만 고치면 된다(PG 17 문서 65.6).

### 2. 행 3개 넣은 PostgreSQL 페이지

```text
  0        24      36                          8080           8120    8152        8192
  +--------+-------+------- 빈 공간 ------------+--------------+-------+-----------+
  | 헤더   | 1 2 3 |                              | 행 3 (34B)   | 행 2  | 행 1(34B) |
  +--------+-------+------------------------------+--------------+-------+-----------+
                   ^ pd_lower                     ^ pd_upper
```

- `pd_lower` = 헤더 24 + 슬롯 3 × 4 = **36**. 빈 공간의 시작이다.
- `pd_upper` = 가장 마지막에 들어간 행의 시작 = 8080(로컬 재현, 예시 PostgreSQL 17.11). 빈 공간의 끝이다.
- 슬롯은 앞에서 뒤로, 행은 뒤에서 앞으로 자란다. 둘이 만나면 페이지가 찬 것이다.
- 행은 8바이트 경계에 놓인다. 그래서 34바이트 행 뒤에 6바이트 여백이 생긴다.

### 3. UPDATE 한 번의 흔적

- PostgreSQL(로컬 재현)
  - 옛 튜플(슬롯 2): `t_xmax` = 갱신한 트랜잭션 번호(1347), `t_ctid` = `(0,4)`. 자기 자신 대신 새 버전을 가리킨다.
  - 새 튜플: **새 슬롯 4**에 들어간다. `t_xmin = 1347`, `t_xmax = 0`, `t_ctid = (0,4)`.
  - `SELECT ctid, *`에서 id=2의 `ctid`가 `(0,2)`에서 `(0,4)`로 바뀐다. `pd_lower` 36→40, `pd_upper` 8080→8040.
  - 옛 튜플은 VACUUM(또는 페이지 정리)이 치울 때까지 자리를 차지한다.
- MySQL InnoDB
  - 클러스터드 인덱스 레코드를 **제자리**에서 고친다. `DB_TRX_ID`가 새 트랜잭션으로, `DB_ROLL_PTR`가 undo 레코드를 가리킨다.
  - 옛 값 `'bob'`은 undo 로그에 있다. 옛 스냅숏을 읽는 트랜잭션은 undo로 옛 버전을 재구성한다(MySQL 8.4 17.3).

### 4. HOT의 조건

- 가능: 두 조건을 모두 만족할 때(65.7).
  - 인덱스가 참조하는 칼럼을 바꾸지 않는다(BRIN 같은 요약 인덱스는 제외).
  - 옛 행이 있는 **같은 페이지**에 새 버전이 들어갈 빈자리가 있다.
- 불가능: 인덱스 칼럼을 바꿀 때, 또는 페이지가 꽉 찼을 때.
- 이득: 인덱스에 새 항목을 넣지 않는다. 중간 버전은 평소 SELECT 중에도 정리될 수 있다.
- `fillfactor`를 낮추면 페이지를 처음 채울 때 빈자리를 남긴다. 그래서 두 번째 조건이 더 자주 맞는다.
  - 로컬 재현: 기본(100)에서는 5만 번 UPDATE 중 HOT 0번, `fillfactor = 50`에서는 30,056번.
  - 대가: 처음부터 테이블이 크다(재현에서 45 → 89페이지).

### 5. 칼럼 순서와 패딩

- `(a bool, b bigint, c bool, d bigint)` → **56바이트**: 헤더 24 + `a` 1 + 패딩 7 + `b` 8 + `c` 1 + 패딩 7 + `d` 8.
- `(b bigint, d bigint, a bool, c bool)` → **42바이트**: 24 + 8 + 8 + 1 + 1.
- 이유: 고정 길이 값은 타입의 정렬 경계(bigint는 8바이트)에 맞춰 놓인다. 작은 칼럼 뒤에 큰 칼럼이 오면 사이에 패딩이 들어간다.
- 로컬 재현(PostgreSQL 17.11)의 `lp_len`이 56과 42였다.

### 6. TOAST 판단

- 기준: 행이 `TOAST_TUPLE_THRESHOLD`(보통 2kB)보다 크면 TOAST가 돈다. 기본 전략 `EXTENDED`는 **압축을 먼저** 시도하고, 그래도 크면 밖으로 뺀다(65.2).
- `'aaaa…'` 10,000바이트: pglz로 125바이트까지 줄었다. 행이 2kB 아래가 되어 **행 안에 압축된 채 남는다**(`lp_len 153`).
- 무작위 16진 9,600바이트: 거의 압축되지 않는다. **TOAST 테이블로** 약 2000바이트 청크로 잘려 들어간다. 본 행에는 18바이트 포인터만 남는다(`lp_len 46`).
- 즉 "원래 크기"가 아니라 "압축 후에도 행이 목표 크기를 넘는가"가 기준이다.

### 7. InnoDB의 긴 행

- DYNAMIC 행 형식(8.4 기본): 행이 최대 행 길이(16KB 페이지면 8KB 조금 아래)를 넘으면, 가장 긴 **가변 길이** 칼럼부터 통째로 오버플로 페이지로 보낸다. 레코드에는 20바이트 포인터만 남는다(17.10, 17.11.2).
- `CHAR(255) latin1` × 40 = 10,200바이트는 전부 768바이트 미만 **고정 길이**라 밖으로 뺄 수 없다(768바이트 이상 고정 길이, 예: utf8mb4 `CHAR(255)`는 가변 길이로 인코딩돼 밖으로 갈 수 있다, 17.10). 그래서 `CREATE TABLE`이 `ERROR 1118 (42000): Row size too large (> 8126)`로 실패한다(로컬 재현, MySQL 8.4.10, strict 모드).
- `TEXT`·`VARCHAR`로 바꾸면 가변 길이가 되어 밖으로 뺄 수 있다. 에러 메시지도 "Changing some columns to TEXT or BLOB may help"라고 알려 준다.

### 8. UPDATE 5번에 6배

- 원인: PostgreSQL UPDATE는 새 버전을 새 자리에 쓴다. 5번이면 행마다 버전 6개(살아 있는 1 + 죽은 5)가 된다. 로컬 재현에서 힙 45 → 266페이지, `dead_tuple_percent 73.43`.
  - 페이지가 꽉 차 HOT도 못 했다. 그래서 PK 인덱스도 245,760 → 909,312바이트로 커졌다.
- `VACUUM` 뒤: 죽은 튜플 자리를 **재사용 가능으로 표시**한다. 파일 크기는 대개 그대로다(테이블 끝 페이지들이 통째로 비면 잘라 내 줄어든다, 24.1.2)(재현: 2,179,072바이트 유지, `free_percent 83.09`). 이후 UPDATE는 그 빈자리를 써서 파일이 더 커지지 않는다.
- 되돌리기: `VACUUM FULL`(또는 `CLUSTER`, 테이블을 다시 쓰는 `ALTER TABLE`)로 새 파일을 만든다(재현: 368,640바이트로 복귀).
  - 대가: `ACCESS EXCLUSIVE` 락 동안 읽기·쓰기가 모두 막힌다. 테이블 크기만큼 디스크가 더 든다(24.1.2).
- 평소 대책: autovacuum이 따라가게 두고, 긴 트랜잭션을 없애고, fillfactor·인덱스 설계로 HOT을 늘린다.

### 9. 넓어진 행과 느려진 스캔

- `EXPLAIN (ANALYZE, BUFFERS)`의 `Buffers: shared hit/read` 합이 크게 늘어 있다.
  - 로컬 재현: 10만 행 `narrow`는 443버퍼, `char(500)` 칼럼이 붙은 `wide`는 6667버퍼. 페이지당 행 226 → 15.
- 원인: 행 저장은 필요한 칼럼이 `v` 하나여도 행 전체가 든 페이지를 읽는다. 행이 넓으면 페이지가 많아진다. 버퍼 풀에 담기는 행 수도 줄어 캐시 적중률도 떨어진다.
- 고치는 법
  - 큰 칼럼을 별도 테이블로 분리한다. `char(n)`처럼 고정으로 넓은 타입을 가변 길이로 바꾼다.
  - 분석 쿼리가 많으면 컬럼 저장(37번)이나 분석용 복제본으로 보낸다.
