# database/37-row-vs-column-storage — 정답

## 정답

### 1. 세 배치

```text
  NSM   [1,KR,PAID,120][2,US,SHIPPED,300][3,KR,PAID,80]

  DSM   id:      [1][2][3]
        country: [KR][US][KR]
        status:  [PAID][SHIPPED][PAID]
        amount:  [120][300][80]

  PAX   행 그룹 1 = { id:[1 2 3] country:[KR US KR] status:[…] amount:[…] }
        행 그룹 2 = { … }
```

- 다시 맞추는 법(CMU L5)
  - **고정 길이 오프셋**: 모든 칼럼에서 i번째 값이 같은 행이다. 가장 흔하다. 값 길이를 고정해야 한다(가변 값은 사전 코드 등으로 고정 길이화).
  - **내장 행 ID**: 값마다 행 ID를 붙인다. 드물다. 공간을 많이 쓴다.

### 2. 읽는 바이트

- 행 저장은 테이블을 스캔하면 필요한 칼럼이 두 개여도 **행 전체가 든 페이지**를 읽는다(커버링 인덱스로 끝나면 예외). 칼럼이 40개면 38개는 버리려고 읽는다.
- 컬럼 저장은 필요한 칼럼 파일만 읽는다: `country`, `amount`, 그리고 WHERE가 있으면 그 칼럼(`created_at`). 게다가 압축돼 있어 더 적다.
- 로컬 재현(예시, PostgreSQL 17.11): `wide`의 `sum(v)`는 **6667페이지(약 52MB)** 를 훑었다. `Buffers: shared hit=6667` — 전부 공유 버퍼 적중이라 디스크 읽기는 아니었지만, 접근한 양이 테이블 전체다. 필요한 값은 4바이트 × 10만 = 약 400KB였다.

### 3. 컬럼 저장이 느린 곳

- CMU L5: DSM은 점 조회·삽입·갱신·삭제가 느리다. 행을 칼럼별로 **쪼개 쓰고 다시 붙여 읽어야** 하기 때문이다.
- 압축까지 하면 더하다. 값 하나를 바꾸려면 그 값이 든 압축 블록을 풀고 다시 써야 한다.
- ClickHouse
  - `ALTER TABLE … UPDATE`는 **뮤테이션**이다. 비동기로 돌며 해당 데이터 파트를 다시 쓴다(ALTER 문서).
  - 문서가 "OLTP DB와 달리 무거운 연산이고 자주 쓰라고 만든 것이 아니다"라고 적는다(ALTER UPDATE 문서).
  - 뮤테이션은 원자적이지 않다. 실행 중에 시작한 SELECT는 바뀐 파트와 안 바뀐 파트를 섞어 본다.

### 4. 압축 크기 예측

- 로컬 재현(예시, Python 3 zlib 레벨 6)
  - 행 단위: 659,979바이트.
  - 칼럼별: 572,576바이트. 칼럼마다 비슷한 값이 모여 조금 더 준다.
  - 정렬 후 칼럼별: `country` 46,088 → **333**바이트, `status` 39,160 → **1,592**바이트.
- 거의 안 주는 칼럼: `amount`(무작위 숫자, 274,482바이트 그대로)와 `id`(212,846바이트).
  - `amount`는 값에 반복·패턴이 없어 배치를 바꿔도 소용없다.
  - `id`는 1씩 느는 패턴이 있지만 zlib 같은 범용 압축은 그것을 못 살린다. 델타 인코딩(차이 = 1의 반복)이면 거의 사라진다.
- 정렬 효과: status 연속 구간이 66,609개 → 15개, country는 5개가 됐다. RLE가 거의 공짜가 된다.

### 5. 세 인코딩

| 인코딩 | 한 줄 | 맞는 칼럼 |
|---|---|---|
| RLE | 같은 값의 연속 구간을 (값, 시작, 길이)로 | 정렬된 칼럼, 긴 연속 구간 |
| 딕셔너리 | 값을 작은 정수 코드로 바꾸고 사전을 따로 | 값 종류가 적거나 중간 정도인 문자열 |
| 비트맵 | 값마다 "그 행이 이 값인가" 비트 벡터 | 값 종류가 아주 적은 칼럼(많으면 비트맵이 커짐) |

- 순서 보존 사전(코드 순서 = 원래 값 순서)이면 **압축된 코드끼리** 범위 비교·정렬을 할 수 있다. 풀지 않고 필터링한다(CMU L5).

### 6. 주문 서비스 설계

- 상세 조회·상태 변경: 행 저장 OLTP DB(PostgreSQL·MySQL). 한 건을 ID로 읽고 트랜잭션으로 고친다.
- 월간 매출 리포트: 컬럼 저장(ClickHouse 테이블, Parquet 기반 웨어하우스). 운영 DB에서 CDC나 배치로 넘긴다.
- 상태가 바뀌면
  - 행을 고치지 말고 "상태 변경 이벤트"를 새 행으로 추가한다. 읽을 때 주문별 최신을 고른다(`argMax(status, updated_at)`, ReplacingMergeTree).
  - 갱신이 꼭 필요하면 모아서 드물게, 파티션을 좁혀서 한다.

### 7. 리포트 시간대의 p99 상승

- 확인
  - PG: `pg_stat_activity`에서 리포트 쿼리가 `active`로 오래 도는지. `EXPLAIN (ANALYZE, BUFFERS)`에서 `Seq Scan`과 거대한 `Buffers: read=`. `pg_stat_database.blks_read` 증가.
  - MySQL: 슬로 쿼리 로그의 `Rows_examined`가 테이블 크기. `SHOW ENGINE INNODB STATUS`의 버퍼 풀 적중률 하락.
  - 주문 API 느린 구간과 리포트 실행 시각이 겹치는지.
- 원인: 행 저장 풀 스캔이 디스크 I/O를 쓰고, 버퍼 풀의 뜨거운 페이지를 밀어낸다(07번).
- 고치기
  - 근본: 리포트를 읽기 복제본이나 컬럼 저장으로 옮긴다.
  - 당장: 필요한 칼럼만 담은 요약 테이블을 미리 만든다. 리포트를 한산한 시간에, keyset으로 나눠 돌린다.

### 8. 뮤테이션 적체

- 원인
  - 행마다 `ALTER TABLE … UPDATE` = 행마다 뮤테이션이다. 뮤테이션마다 해당 파트를 다시 쓴다. 한 행 때문에 큰 파트를 여러 번 다시 쓴다.
  - 비동기라 제출과 반영 사이가 벌어진다. 원자적이지 않아 중간 상태가 보인다.
- 대처
  - 쓰기 모델을 추가형으로 바꾼다. 상태 변화를 새 행으로 넣고 최신을 골라 읽는다.
  - 갱신이 필요하면 한 번에 모아 한 번의 뮤테이션으로, `IN PARTITION`으로 범위를 좁힌다.
  - 잦은 단건 갱신이 본질인 데이터는 행 저장 DB에 둔다.
