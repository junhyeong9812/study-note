# database/55-distributed-databases — 정답

## 정답

### 1. 샤딩이 앱에 넘기는 것

| 앱으로 넘어오는 일 | 분산 DB의 장치 |
|---|---|
| 여러 샤드에 걸친 원자적 커밋(saga·직접 2PC) | 내장 분산 트랜잭션(2PC, 코디네이터 상태는 합의 그룹에) |
| 샤드 간 일관된 스냅숏 읽기 | 전역 타임스탬프(TSO·TrueTime·HLC) + MVCC |
| 샤드를 넘는 조인·집계(scatter-gather) | 분산 실행 계획(푸시다운·방송·셔플) |
| 샤드별 페일오버·재샤딩 | 파티션마다 합의 그룹(자동 리더 교체), 자동 분할·이동 |

### 2. shared-nothing vs shared-disk

| | shared-nothing | shared-disk |
|---|---|---|
| 노드 추가 | 데이터를 물리적으로 새 노드로 옮긴다 | 계산 노드만 붙인다. 데이터 배치는 저장 계층이 그대로 |
| 노드끼리 | 쿼리 조각·결과·트랜잭션 조정 메시지 | 캐시된 페이지가 바뀌면 무효화 등 상태 메시지 |
| 장점 | 성능·효율 | 계산과 저장을 따로 늘림, 계산 노드 무상태 |

- 클라우드 네이티브 DBMS(Snowflake·BigQuery·Redshift 등)는 대개 shared-disk 기반이다(CMU L24).

### 3. 분산 OLTP 구조

```text
  파티션1 [a~f)  → Raft 그룹 {L, F, F}
  파티션2 [f~m)  → Raft 그룹 {F, L, F}
  파티션3 [m~z]  → Raft 그룹 {F, F, L}
  파티션1·3을 건드리는 트랜잭션 → 두 그룹의 리더 사이 2PC
```

- 2PC는 일반형이다. CockroachDB는 합의 두 번을 한 번으로 줄인 변형 *Parallel Commits*를 쓴다(Transaction Layer 문서).

- 각 파티션의 쓰기는 **과반 사본이 로그에 기록한 뒤** 커밋으로 친다. 리더가 죽어도 과반 중 누군가는 그 기록을 갖고 있고, 새 리더는 그 로그를 가진 사본 중에서 뽑힌다. 그래서 "성공 응답을 받은 쓰기"가 사라지지 않는다.
- 32번 비동기 복제는 커밋 응답이 "리더 로컬 flush"뿐이라 팔로워 승격 시 지연만큼 잃는다.

### 4. 준비된 XA와 끊긴 연결

- 로컬 재현(MySQL 8.4.10): 연결이 끊겨도 트랜잭션은 **준비 상태로 남는다**. `XA RECOVER`에 `w20x`가 보이고, `performance_schema.data_locks`에 `acct PRIMARY X,REC_NOT_GAP GRANTED lock_data 1`이 남았다.
- 다른 세션의 같은 행 `UPDATE`는 기다리다 `ERROR 1205 (HY000): Lock wait timeout exceeded`(세션 타임아웃 2초로 재현).
- 정리: 코디네이터(또는 사람)가 결정한다. `XA COMMIT 'w20x'` 또는 `XA ROLLBACK 'w20x'`. 준비한 참가자는 스스로 결정할 수 없다. 이것이 2PC의 막힘이다.

### 5. 2PC vs Paxos

- 2PC: 참가자가 준비 뒤 코디네이터가 죽으면, 코디네이터가 돌아올 때까지 참가자가 막힌다(CMU L23). 참가자 하나라도 응답이 없으면 커밋할 수 없다.
- Paxos·Raft: 2F+1개 중 F+1개(과반)만 살아 있으면 진행한다. 소수의 장애로는 막히지 않는다(CMU L23: 2PC는 F = 0인 Paxos의 퇴화형).
- Spanner: 2PC의 코디네이터와 참가자 각각이 Paxos 그룹이다. 코디네이터 "노드"가 죽어도 그 그룹의 다른 사본이 결정을 이어 받는다. 논문: "Running two-phase commit over Paxos mitigates the availability problems."

### 6. commit wait

- 기대 대기 ≥ 2ε. ε이 4 ms라면 약 **8 ms**다. 실제로는 Paxos 통신과 겹쳐 진행된다.
- 논문의 1-복제본 실험에서 잰 commit wait는 약 5 ms로 이보다 작았다. 실험 당시의 ε 값은 확인하지 못했다 [?]. "평균 4 ms"는 운영 환경의 톱니형 ε(1~7 ms)에 대한 설명이다.
- 이유: 커밋 타임스탬프 s를 `TT.now().latest` 이상으로 잡았으니, `TT.after(s)`(earliest > s)가 될 때까지 기다리면 s는 **확실히 과거**다. 그 뒤에야 결과를 보인다.
- 보장(외부 일관성): T1이 커밋을 마친 뒤 T2가 시작하면, T1의 커밋 타임스탬프 < T2의 커밋 타임스탬프. 타임스탬프 순서가 실제 시간 순서와 어긋나지 않는다(선형화와 같은 말).

### 7. 전역 순서 세 방식

| | 의존 | 대가 |
|---|---|---|
| TSO(TiDB PD, 기본 구성) | 발급자의 가용성·왕복 | 트랜잭션마다 발급자 왕복, 발급자가 병목·단일 지점(HA로 보완) |
| TrueTime(Spanner) | GPS·원자시계 기반 시계 인프라와 오차 한계 ε | 커밋마다 약 2ε 대기 |
| HLC(CockroachDB) | NTP 수준 시계 동기 + 설정된 최대 오프셋 | 불확실성 구간 재시도(40001), 오프셋 초과 시 노드 종료 |

- TiDB TSO 64비트 = 앞 **46비트** 물리 시각(UNIX ms) + 뒤 **18비트** 논리 카운터(같은 밀리초 안의 순번, 시계 역행 시에도 증가).

### 8. 40001 폭증 + 노드 종료

- 원인 후보
  - 시계 동기 흔들림 → 노드 간 오프셋 증가 → 읽기가 불확실성 구간 안의 쓰기를 자주 만나 `ReadWithinUncertaintyIntervalError`(40001)로 재시작. 오프셋이 클러스터 절반 이상과 최대 오프셋의 80%를 넘은 노드는 스스로 종료한다.
  - 또는 핫 키 경합(같은 행 동시 쓰기)으로 직렬화 충돌.
- 앱: 트랜잭션 전체 재시도(횟수 제한 + 지수 백오프 + 지터). 재시도 안에 외부 부수 효과를 두지 않는다.
- 운영: 모든 노드 NTP·시간 서비스, 오프셋 지표 경보, 가상화 시계 점프 점검. 핫 키는 키 쪼개기.

### 9. 5 ms → 150 ms

- 시간이 드는 곳
  - 파티션마다 합의: 리더 → 과반 사본 왕복. 사본이 다른 리전에 있으면 리전 간 RTT.
  - 파티션 간 2PC: 준비 왕복 + 커밋 왕복. 참가 파티션의 리더가 다른 리전이면 그 RTT가 또 붙는다.
  - (Spanner라면) commit wait.
  - 단일 PostgreSQL의 커밋은 기본 설정(`synchronous_commit = on`, 동기 복제 없음)에서 로컬 WAL fsync 한 번이다. `off`면 그것도 기다리지 않고, 동기 복제면 standby 응답까지 기다린다.
- 줄이는 설계
  1. 한 트랜잭션이 한 파티션에서 끝나도록 키를 잡는다(co-location). 단일 파티션이면 2PC를 생략할 수 있다(제품의 1PC 최적화, 예: TiDB `tidb_enable_1pc` 기본 ON).
  2. 사용자 가까운 리전에 그 데이터의 리더·과반 사본을 둔다(지역 배치). 강한 일관성이 필요 없는 읽기는 과거 시점 스냅숏 읽기로.

### 10. 분산 조인 네 경우

| 경우 | 방법 | 비용 |
|---|---|---|
| S가 모든 노드에 복제 | 각 노드 로컬 조인 → 결과 모음 | 작다 |
| R·S가 조인 키로 같이 분할 | 각 노드 로컬 조인 | 작다 |
| 다른 키 분할, S가 작다 | S를 모든 노드에 방송(broadcast join) | S 크기 × 노드 수 |
| 둘 다 조인 키로 분할 안 됨 | 둘 다 조인 키로 재분배(shuffle join) | 가장 크다. 디스크 부족 시 실패 |

- 피하는 설계: 자주 조인하는 큰 테이블은 같은 조인 키로 분할, 작은 차원 테이블은 모든 노드에 복제.
- 노드 장애: 대부분의 shared-nothing 분산 OLAP은 실행 중 장애를 가정하지 않는다. 쿼리 전체가 실패하고 처음부터 다시 돈다. 중간 결과 스냅숏은 가능하지만 느려서 흔치 않다(CMU L24).
