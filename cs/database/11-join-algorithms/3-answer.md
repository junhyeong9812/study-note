# database/11-join-algorithms — 정답

## 정답

### 1. 준비와 반복

| 알고리즘 | 한 번 준비 | 반복 |
|---|---|---|
| 중첩 루프 | 없음(인덱스 중첩 루프는 기존 인덱스를 쓴다) | 바깥 행마다 안쪽을 훑거나 인덱스로 찾는다 |
| 해시 조인 | 작은 쪽으로 해시 테이블(빌드) | 큰 쪽 행마다 해시 버킷을 찾는다(프로브) |
| 정렬 병합 | 양쪽을 조인 키로 정렬(이미 정렬돼 있으면 생략) | 두 커서를 나란히 전진 |

- 해시는 **같은 값을 같은 버킷**에 보낼 뿐, 값의 대소 순서를 보존하지 않는다. 그래서 `a < b` 같은 조건은 버킷 하나로 좁힐 수 없다. 해시로 짝을 좁히는 해시 조인은 등호 조건이 필요하다(CMU L12).
- 예외처럼 보이는 것: MySQL 8.4는 등호가 없는 조인에도 `Inner hash join (no condition)`을 쓴다. 이때 해시는 짝을 좁혀 주지 못한다. 모든 짝을 만든 뒤 비등호 조건을 `Filter`로 거른다(MySQL 8.4 10.2.1.4).

### 2. 비용 계산

- 단순 중첩 루프: M + m × N = 1000 + 100,000 × 500 = **50,001,000** I/O
- 블록 중첩 루프: M + ⌈M / (B − 2)⌉ × N = 1000 + ⌈1000 / 98⌉ × 500 = 1000 + 11 × 500 = **6,500** I/O
- Grace 해시 조인: 3 × (M + N) = 3 × 1500 = **4,500** I/O (분할 때 읽고 쓰기 2 × (M + N), 프로브 때 읽기 M + N)
- CMU L12는 I/O 하나를 0.1 ms로 두고 단순 중첩 루프 1.4시간, 해시 조인 0.45초라고 적는다. 표의 블록 중첩 루프 행(50초)은 버퍼를 바깥 블록 하나로만 쓰는 M + M × N 식이다.

### 3. 작은 조인과 큰 조인

- 고객 5명: **중첩 루프**. 바깥(고객 5행)이 작고 안쪽 `orders.customer_id`에 인덱스가 있다. 안쪽 인덱스 탐색 5번이면 끝난다. 로컬 재현(예시, PostgreSQL 17.11)에서 `Nested Loop` → `Bitmap Index Scan on orders_cust (loops=5)`, 0.09 ms였다.
- 전체 집계: **해시 조인**. 30만 행 각각에 인덱스 탐색을 하는 것보다, 고객 5만 행으로 해시 테이블을 만들고 주문을 한 번 훑는 편이 싸다. 로컬 재현에서 `Hash Join`, 빌드 쪽 `Buckets: 65536 Batches: 1 Memory Usage: 2466kB`였다.

### 4. 추정 오류 + 중첩 루프

- 바깥 행 수를 5로 추정했지만 실제는 500이었다. 옵티마이저는 "5번만 돌면 된다"고 보고 중첩 루프를 골랐다(질문 속 상황). 안쪽에 인덱스가 없어 바깥 행마다 안쪽 전체를 비교했다(4,974만 행 버림).
- 로컬 재현(예시): 상관된 두 컬럼(`region`, `grade`)의 등호 조건을 독립으로 보고 곱해 5행으로 추정했다. 이 재현에서 플래너는 원래 해시 조인을 골랐고, 비용 비교를 위해 중첩 루프를 강제했다. 강제하면 3292 ms, 해시 조인이면 15.6 ms였다.
- 근본 대처
  - `ANALYZE`로 통계를 갱신한다. 상관 컬럼에는 `CREATE STATISTICS … (dependencies)`를 만든다. 로컬 재현에서 추정이 5 → 513으로 맞아졌다.
  - 안쪽 조인 키에 인덱스를 둔다. 추정이 틀려도 반복 비용이 작아진다.
- 긴급 대처: 그 쿼리를 도는 세션에서만 `SET enable_nestloop = off`. 서버 전역으로 끄면 중첩 루프가 맞는 다른 쿼리가 망가진다.

### 5. 해시 배치

- 해시 테이블이 메모리 한도를 넘어 **32개 배치로 나눴다**는 뜻이다. 배치마다 양쪽 입력 일부를 임시 파일에 썼다가 다시 읽는다. Grace 해시 조인의 분할과 같은 방식이다.
- 한도는 `work_mem × hash_mem_multiplier`다. PostgreSQL 17 기본값은 4MB × 2.0이다(19.4). 로컬 재현에서 `work_mem`을 64kB로 낮추자 `Batches: 1` → `32`가 됐다.
- 한도는 **연산 하나당**이다. 쿼리 하나에 해시·정렬이 여럿이고 세션도 여럿이면 곱으로 는다. 세션 단위로 올리는 편이 안전하다.
- MySQL 8.4: 한도는 `join_buffer_size`다. 넘으면 디스크 파일을 쓰고, 파일 수가 `open_files_limit`을 넘으면 조인이 실패할 수 있다(10.2.1.4).

### 6. 정렬 병합이 나은 경우

- 양쪽이 조인 키로 **이미 정렬**돼 있을 때(인덱스 순서, 앞 단계의 정렬). 정렬 비용 없이, 키가 대체로 고유하면 약 M + N으로 끝난다(모든 키가 같은 최악은 M × N). 로컬 재현에서 `ORDER BY c.id`가 붙은 전체 조인은 양쪽 인덱스 스캔 + `Merge Join`이었다.
- 결과를 조인 키 순서로 내야 할 때(`ORDER BY`가 조인 키). 조인 결과가 이미 정렬돼 있어 추가 정렬이 필요 없다.
- CMU L12는 정렬 기반 조인이 나은 경우로 "비균일(쏠린) 데이터, 이미 정렬된 데이터, 정렬된 결과가 필요한 경우"를 든다. 쏠린 키는 해시 분할에서 한 파티션을 비대하게 만들기 때문이다.
- MySQL 8.4에는 정렬 병합 조인 연산자가 없다. 중첩 루프 계열(10.2.1.7)과 해시 조인(10.2.1.4)으로 실행한다. 조인 조건에 쓸 인덱스가 있으면 보통 인덱스 중첩 루프를 검토하고, 조인 조건에 쓸 인덱스가 없는 등호 조인이면 기본적으로 해시 조인이 된다(`optimizer_switch`의 `block_nested_loop`·`NO_BNL` 힌트로 끌 수 있다).

### 7. 조인 키 타입 불일치

- PostgreSQL 17: `integer = character varying` 연산자가 없어 에러다. 캐스트를 **인덱스가 있는 쪽**(`c.id::text`)에 걸면 `c.id` 인덱스를 못 쓴다. 로컬 재현에서 양쪽 `Seq Scan` + `Hash Cond: ((c.id)::text = (e.code)::text)`였다.
- 캐스트는 **인덱스가 없는 쪽**에 건다(`c.id = e.code::integer`). 로컬 재현에서 `Index Only Scan using customers_pkey`를 쓰는 중첩 루프가 됐다. 단 `e.code`에 숫자가 아닌 값이 있으면 캐스트가 에러를 낸다.
- MySQL 8.4: 에러 없이 암묵 변환한다. 로컬 재현에서 조건이 `cast(e.code as double) = cast(c.id as double)`로 바뀌었다. `code` 인덱스로는 탐색하지 못하고 인덱스 전체를 훑었다.
- 근본 해결: 스키마에서 조인 키 타입을 맞춘다. PostgreSQL은 타입이 호환되지 않는 FK를 거부한다. FK를 걸면 불일치가 처음부터 드러난다.

### 8. N+1 = 앱이 하는 중첩 루프

- 바깥 루프(주문 1000건)가 앱에 있고, 안쪽 탐색(고객 PK 조회)이 쿼리 한 번씩(영속성 컨텍스트에 이미 있는 고객이면 생략)인 **인덱스 중첩 루프 조인**이다. 반복마다 네트워크 왕복·실행이 붙고(준비된 문장을 재사용하지 못하면 파싱도) DB 안의 중첩 루프보다 훨씬 비싸다.
- DB에 조인을 맡기면(`join fetch`, 한 번의 SQL) 옵티마이저가 크기를 보고 해시 조인이나 병합 조인을 고를 수 있다. 왕복은 한 번이다.
