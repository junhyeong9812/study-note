# database/30-caching-with-databases — 질문

## 질문

1. (왜) cache-aside에서 쓰기 때 캐시를 갱신(set)하지 않고 삭제(delete)하는 이유는? Facebook 논문이 든 한 단어 이유는?
2. (그림) `@Transactional` 메서드 안에서 `UPDATE` 직후 `cache.delete(k)`를 호출했다. 옛 값이 캐시에 다시 들어가는 시간축을 그려라. 어떻게 고치나(Spring)?
3. (그림) 삭제를 커밋 뒤로 옮겼는데도 옛 값이 고착되는 경합을 그려라. Facebook의 리스는 이것을 어떻게 막나?
4. (연결) 읽기를 복제본으로 보내는 시스템에서 캐시 miss를 복제본 조회로 채우면 어떤 문제가 생기나? Facebook은 여러 지역에서 이 문제를 어떤 장치로 줄였나?
5. (경계) write-through에서 "DB 커밋 성공 + 캐시 set 실패"와 "캐시 set 성공 + DB 커밋 실패"는 각각 어떤 상태를 남기나? 흔한 설계 규칙은?
6. (계산) 캐시 히트율 95%인 서비스가 초당 20,000건을 읽는다. 평소 DB 읽기 부하와 캐시 전체 장애 시 DB 읽기 부하는? 몇 배인가?
7. (장애 진단) 매시 정각 DB CPU가 치솟고 같은 쿼리가 `pg_stat_activity`에 수백 개 보인다. 원인과 대처 세 가지는? Facebook 리스는 이 문제를 어떻게 완화했고, 측정 결과는?
8. (장애 진단) 캐시 히트율은 높은데 DB 부하가 줄지 않는다. `pg_stat_statements`에서 무엇을 보면 관통을 의심할 수 있나? 대처는?
9. (장애 진단) 신버전 배포 직후 신버전 인스턴스에서만 캐시 읽기 예외가 나고 DB 쿼리가 급증했다. 원인과 대처는?
10. (경계) MySQL 8.4에서 "DB 쿼리 캐시를 켜면 되지 않나?"라는 제안에 어떻게 답하나? DB 버퍼 풀과 앱 캐시는 일관성 면에서 무엇이 다른가?
