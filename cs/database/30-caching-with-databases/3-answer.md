# database/30-caching-with-databases — 정답

## 정답

### 1. 갱신 대신 삭제

- 두 쓰기가 동시에 set하면 도착 순서가 뒤바뀔 수 있다. 늦게 도착한 옛 값이 이긴다.
- 삭제는 몇 번, 어떤 순서로 해도 결과가 "없음"이다. 다음 읽기는 캐시 miss가 나서 DB로 간다. 최신값인지는 어디서 읽느냐에 달렸다(복제본이 지연 중이면 옛 값, 4번).
- Facebook 논문(NSDI 2013 §2): "We choose to delete cached data instead of updating it because deletes are **idempotent**."

### 2. 커밋 전 삭제

```text
  W: BEGIN; UPDATE price=2000; delete(k) ──────────────── COMMIT
  R:                           get miss → SELECT → 1000 → set(k, 1000)
  → DB 2000, 캐시 1000 (TTL까지)
```

- R은 W가 커밋하기 전이라 옛 값을 읽는다(READ COMMITTED에서 커밋 안 된 값은 안 보임). 로컬 재현(PostgreSQL 17.11)에서 W의 커밋 전 3초 동안 R은 1000을 읽었다.
- 고치기: 삭제를 커밋 후로 옮긴다.

```java
@Transactional
public void changePrice(long id, int price) {
    repo.updatePrice(id, price);
    events.publishEvent(new ProductChanged(id));
}
@TransactionalEventListener   // 기본 AFTER_COMMIT
public void on(ProductChanged e) { cache.delete("product:" + e.id()); }
```

### 3. 늦게 도착한 옛 set과 리스

```text
  R: miss → SELECT(1000) ───── 지연 ─────────────▶ set(k, 1000)   ✘
  W:              UPDATE → COMMIT → delete(k)
```

- 리스: miss 때 캐시 서버가 그 키에 묶인 64비트 토큰을 준다. set에는 토큰이 필요하다. 그 사이 delete가 오면 토큰이 무효가 되어 R의 set이 거절된다. 논문은 load-link/store-conditional과 비슷하다고 설명한다.
- 리스가 없으면: 짧은 TTL(낡은 항목 수명의 상한), 지연 이중 삭제, 값에 버전을 넣은 조건부 set으로 확률·시간을 줄인다.

### 4. 복제본에서 채우기

- 쓰기 직후 복제가 도착하기 전에 miss가 나면, 복제본의 옛 값이 캐시에 들어간다. 삭제는 이미 끝났으므로 TTL까지 고착된다.
- Facebook(§5): 비-마스터 지역에서 쓸 때 **원격 마커**를 먼저 세우고, 마스터에 쓰고, 로컬 캐시를 지운다. 이후 miss 때 마커가 있으면 마스터 지역으로 읽는다. 지연을 더 내는 대신 낡은 값을 읽을 확률을 줄인다.
- 작은 시스템: 방금 쓴 키는 프라이머리에서 읽어 채운다. 복제 지연을 지표로 본다.

### 5. write-through의 두 실패

| 경우 | 남는 상태 |
|---|---|
| DB 커밋 ✔, 캐시 set ✘ | 캐시에 옛 값(TTL까지 낡음) |
| 캐시 set ✔, DB 커밋 ✘ | 캐시에만 있는 유령 값(DB에 없는 값이 보임) |

- 두 저장소를 원자적으로 묶는 일반적 방법은 없다.
- 규칙: DB가 원본, 캐시는 파생이다. 커밋된 변경만 무효화하고(커밋 후 훅, CDC·아웃박스), 캐시 쪽 실패는 삭제 + TTL로 수렴시킨다.

### 6. 히트율과 DB 부하

- 평소: miss 5% → 20,000 × 0.05 = **1,000건/초**.
- 캐시 전체 장애: **20,000건/초**.
- 1/(1 − 0.95) = **20배**. 히트율이 높을수록 캐시 장애 때의 배수가 커진다.

### 7. 매시 정각 스탬피드

- 원인: 인기 키가 정각에 동시에 만료(같은 TTL로 같은 시각에 채움)되어, 동시 miss가 같은 쿼리로 DB에 몰렸다.
- 대처: (1) 싱글플라이트/뮤텍스 — 키당 한 요청만 DB로 (2) TTL 지터 — 만료 시각 분산 (3) 확률적 조기 갱신 또는 만료 후 옛 값 제공 + 백그라운드 갱신.
- Facebook 리스(§3.2 "Leases"): 캐시 서버가 키당 **10초에 한 번만** 토큰을 준다(기본 설정). 나머지 요청은 잠깐 기다렸다 재시도하고, 그때는 대개 값이 채워져 있다. 스탬피드에 취약한 키 집합에서 DB 최대 조회율이 **17K/s → 1.3K/s**로 줄었다.

### 8. 관통 의심

- `pg_stat_statements`에서 호출 수(`calls`)가 많은데 `rows / calls`가 0에 가까운 쿼리. "없는 행 조회"가 반복된다는 뜻이다.
- 대처: 널 캐싱(짧은 TTL로 "없음"도 저장), 블룸 필터로 존재하지 않는 키 차단, ID 형식 검증, 레이트 리밋. 의도적 공격 가능성을 본다.

### 9. 배포 직후 역직렬화 실패

- 원인: 값의 직렬화 형식(클래스 구조)이 바뀌었는데 키가 같았다. 구버전이 쓴 값을 신버전이 못 읽고, 예외 처리로 DB에 간다. 반대로 신버전이 쓴 값을 구버전이 못 읽기도 한다.
- 대처: 형식을 바꿀 때 키에 버전을 넣는다(`product:v2:42`) — 원고 08 §1 "포맷 바꿀 땐 키를 바꾼다". 역직렬화 실패는 miss로 취급하되 DB 보호(레이트 리밋)를 둔다. 상세는 31번 노트.

### 10. 쿼리 캐시와 버퍼 풀

- MySQL 쿼리 캐시는 8.0에서 **제거**됐다(8.0 "What Is New": "The query cache was removed"). 8.4에는 켤 수 있는 쿼리 캐시가 없다.
- 버퍼 풀: 페이지 단위이고, DB가 트랜잭션·MVCC와 일관되게 관리한다. 캐시 때문에 틀린 값이 보이지 않는다.
- 앱 캐시: 결과·객체 단위이고, DB 트랜잭션 밖이다. 무효화 책임이 앱에 있고, 커밋 순서·복제 지연 때문에 낡은 값이 보일 수 있다. 그래서 조금 낡아도 되는 데이터에 둔다.
