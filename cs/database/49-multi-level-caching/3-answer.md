# database/49-multi-level-caching — 정답

## 정답

### 1. L1을 더 두는 이유와 새 문제

- 이유
  - 네트워크 왕복을 없앤다. L1 적중은 프로세스 메모리 조회다.
  - 핫키 부하를 나눈다. Redis의 키 하나는 슬롯 하나(마스터 하나)라 샤드를 늘려도 안 나뉜다. L1이 그 부하를 인스턴스 수 수준으로 줄인다.
- 새 문제
  - L1은 인스턴스마다 따로라 무효화를 전파해야 한다.
  - L1은 앱 힙을 쓰므로 크기 제한이 없으면 GC·OOM 문제가 된다.

### 2. 라운드로빈과 옛 값

```text
  t1  A: DB 90 커밋, Redis 삭제, A의 L1 삭제
  t2  새로고침 → A: L1 miss → Redis miss → DB 90   → 90
  t3  새로고침 → B: L1 hit (100)                    → 100
  t4  새로고침 → A: L1 hit (90)                     → 90
  ... B의 L1 TTL이 끝날 때까지 90/100이 번갈아 보인다
```

- 쓰는 인스턴스는 자기 L1만 지울 수 있다. B에게 알리는 장치(방송·서버 추적)가 없었다.

### 3. Pub/Sub 무효화의 보장

- **최대 한 번(at-most-once)**이다. 구독자가 처리 못 하거나 연결이 끊겨 있으면 그 메시지는 사라진다(Redis 문서).
- 함께 둘 것
  - 짧은 L1 TTL — 메시지를 놓쳐도 L2가 이미 새 값이면 불일치가 L1 TTL 안에서 끝난다.
  - 재연결 시 L1 전체 비우기 — 끊긴 사이 무엇을 놓쳤는지 알 수 없다.

### 4. CLIENT TRACKING 기본 모드 vs BCAST

| | 기본(추적) 모드 | BCAST |
|---|---|---|
| 서버 메모리 | 무효화 테이블(키 → 읽은 클라이언트 ID). 추적 키 수 × 클라이언트 수에 비례 | 쓰지 않는다(접두사 표만) |
| 전달 범위 | 그 키를 실제로 읽은 클라이언트에게만 | 접두사에 맞는 모든 변경을 구독자 전원에게 |

- 테이블이 `tracking-table-max-keys`(기본 1M)에 닿으면, Redis는 바뀌지 않은 키도 바뀐 척 무효화를 보내고 항목을 지운다. 클라이언트는 멀쩡한 L1 항목을 잃어 적중률이 떨어진다.

### 5. 무효화가 응답보다 먼저 도착

- 대비가 없으면: 무효화 도착 때 L1에 "foo"가 없어 지울 것이 없다. 그다음 늦게 온 옛 값 "bar"를 L1에 넣는다. 다음 무효화가 올 때까지 옛 값을 계속 쓴다.
- 자리표시자
  1. `GET` 전에 L1["foo"] = "caching-in-progress"를 넣는다.
  2. 무효화가 오면 "foo" 항목을 지운다.
  3. 응답이 오면, 자리표시자가 그대로 있을 때만 값을 넣는다. 지워졌으면 버린다.
- 연결 하나(RESP3)로 받으면 순서가 정해져 이 경쟁이 없다.

### 6. 크기 제한 없는 L1

- 의심: 캐시에 크기 상한이 없다(`new ConcurrentHashMap<>()`, `Caffeine.newBuilder().build()`만). 키 공간이 계속 늘어 항목이 Old 영역에 쌓인다. 결국 전체 GC가 길어지고 `OutOfMemoryError`나 컨테이너 OOM kill(exit 137)로 끝난다.
- Caffeine javadoc: 기본값으로 어떤 축출도 하지 않는다. `maximumSize`/`maximumWeight`나 만료를 걸어야 한다.
- `softValues()` 경고: 대부분의 경우 캐시별 최대 크기를 두는 편이 낫다. soft reference는 메모리 압박 때 전역 LRU처럼 치워져 예측하기 어렵다.

### 7. 핫키와 L1

- 인스턴스마다 TTL 1초에 한 번 채우므로 Redis는 이 키를 초당 약 **20회**(인스턴스 수) 받는다. 5만 → 20.
  - 동시 miss가 몰리면 인스턴스 안에서 여러 번 채울 수 있다. Caffeine `Cache.get(key, fn)`은 키당 한 번만 계산하므로 인스턴스당 1회로 묶인다.
- 샤드를 늘려도 안 되는 이유: 키 하나는 `CRC16(key) mod 16384` 슬롯 하나에(해시 태그 `{…}`가 있으면 태그만 해시), 슬롯 하나는 마스터 하나에 있다. 그 키의 부하는 그대로 한 노드에 남는다.

### 8. W-TinyLFU와 스캔

- 입장 창(LRU, 작음): 새 항목이 먼저 들어가는 곳. 막 인기가 오르는 항목(최근성)을 잠깐 품는다.
- 빈도 스케치(4비트 Count-Min Sketch): 키별 과거 조회 빈도를 적은 메모리로 근사한다. 주기적으로 절반으로 줄여 옛 인기를 잊는다.
- 본 공간(Segmented LRU): 창에서 밀려난 후보와 본 공간의 희생자를 빈도로 비교해, 후보 빈도가 더 클 때만 들인다(예외: 해시 충돌 공격 대비로, 빈도가 일정 이상인 "따뜻한" 후보는 1/128 확률로 받아들인다 — `BoundedLocalCache.admit`).
- 스캔에서 한 번만 읽힌 키는 빈도가 낮아 본 공간에 들지 못하고 창에서 버려진다. 인기 항목은 본 공간에 남는다. LRU는 최근에 읽혔다는 이유만으로 스캔 항목을 앞에 두고 인기 항목을 밀어낸다.
