# database/49-multi-level-caching — 질문

## 질문

1. (왜) Redis(L2)만 있어도 되는데 로컬 L1을 더 두는 이유 두 가지는? L1을 두는 순간 생기는 새 문제는?
2. (그림) 인스턴스 A·B가 L1에 price=100을 들고 있다. A에서 가격을 90으로 바꿨고 A는 자기 L1과 Redis를 지웠다. 로드밸런서가 라운드로빈일 때 사용자가 새로고침을 반복하면 무엇을 보나? 시간축으로 그려라.
3. (경계) Redis Pub/Sub으로 L1 무효화를 방송한다. 전달 보장 수준은? 이 때문에 L1에 함께 둬야 하는 것 두 가지는?
4. (연결) `CLIENT TRACKING`의 기본 모드와 BCAST 모드를 서버 메모리·전달 범위로 비교하라. 기본 모드에서 추적 테이블이 가득 차면 무슨 일이 생기나?
5. (예측) 데이터 연결과 무효화 연결을 따로 쓰는 클라이언트에서 `GET foo` 응답보다 `Invalidate foo`가 먼저 도착했다. 아무 대비가 없으면 L1은 어떻게 되나? 자리표시자로 어떻게 막나?
6. (장애 진단) 배포 며칠 뒤부터 p99가 튀고 결국 인스턴스가 재시작된다. GC 로그에서 Old 사용량이 계단식으로 오른다. 캐시 코드의 어떤 점을 의심하나? Caffeine의 기본 축출 동작과 `softValues()`에 대한 javadoc의 경고는?
7. (계산) 핫키 하나에 초당 5만 조회가 온다. 앱 인스턴스 20개에 L1 TTL 1초를 두면 Redis가 받는 이 키 조회는 대략 초당 몇 회인가? Redis 샤드를 늘리는 것만으로 이 문제가 풀리지 않는 이유는?
8. (왜) W-TinyLFU는 LRU와 달리 "전체 목록 한 번 훑기"에 L1이 망가지지 않는다. 입장 창·빈도 스케치·본 공간이 각각 무엇을 하는지로 설명하라.
