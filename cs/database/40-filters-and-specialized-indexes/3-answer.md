# database/40-filters-and-specialized-indexes — 정답

## 정답

### 1. 앞 `%`와 뒤 `%`

- B-tree는 값 전체의 정렬 순서다. `'%키보드%'`는 "어디든 '키보드'가 있는 값"이라 정렬의 어느 연속 구간에도 대응하지 않는다. 그래서 풀스캔이다.
- `'키보드%'`는 "'키보드'로 시작하는 값"이다. 정렬에서 이런 값들은 한 구간에 붙어 있다. 그래서 "`'키보드'` 이상, 다음 접두어 미만"의 범위 스캔으로 바꿀 수 있다.
- PostgreSQL에서는 데이터베이스 collation이 `C`가 아니면 일반 B-tree로는 안 되고 `text_pattern_ops` 연산자 클래스 인덱스가 필요하다(PostgreSQL 17 11.2, 11.10). 로컬 재현(`en_US.utf8`)에서 일반 B-tree는 `Seq Scan`, `text_pattern_ops`는 `Index Cond: ((title ~>=~ 'product abc12') AND (title ~<~ 'product abc13'))`였다.

### 2. 블룸 필터 조회

- 켜진 비트: 2, 7, 9, 11, 14.
- C(2, 9, 11): 셋 다 1 → **"있을 수도"**. 실제로는 넣지 않았으니 거짓 양성이다.
- D(3, 7, 9): 비트 3이 0 → **"확실히 없음"**.
- 블룸 필터는 **거짓 음성**을 내지 않는다. 넣은 키에 대해 "없음"이라고 답하는 일은 없다(CMU L9).

### 3. DB 안의 블룸 필터

1. LSM 엔진(RocksDB 등): SST 파일마다 필터를 두어, 키가 없는 파일은 읽지 않는다. 키당 약 10비트면 거짓 양성 약 1%(RocksDB 위키).
2. 해시 조인: 빌드 쪽 키로 필터를 만들어 프로브 쪽 행을 해시 테이블에 가기 전에 거른다(CMU L12).
3. PostgreSQL `bloom` 확장 인덱스: 행마다 여러 컬럼 값을 서명 하나(기본 80비트)에 담는다.
- `bloom` 인덱스 조회는 **인덱스 전체를 순차로** 읽는다. 로컬 재현(예시)에서 20만 행 인덱스 393 페이지를 모두 읽었다. 대신 인덱스가 작고(같은 컬럼 B-tree의 약 절반), 컬럼의 임의 등호 조합 어디에나 쓸 수 있다. 조합 하나만 쓰면 B-tree가 더 빠르다(F.6).

### 4. '삼성' 검색

| 방법 | 결과 | 이유 |
|---|---|---|
| PG `to_tsquery('simple','삼성')` | 못 찾음 | 공백 단위 토큰 `'삼성전자'`와 `'삼성'`은 다른 키다. `'삼성:*'` 접두어 검색은 찾는다 |
| MySQL 기본 파서 `AGAINST('삼성')` | 못 찾음 | 공백 단위 토큰이고, `innodb_ft_min_token_size`(기본 3)보다 짧은 두 글자 단어는 색인되지 않는다 |
| MySQL ngram 불리언 `AGAINST('삼성')` | 찾음 | '삼성전자'가 '삼성' '성전' '전자'로 색인됐다. 검색어 '삼성'도 bigram 하나다 |

- 모두 로컬 재현(PostgreSQL 17.11, MySQL 8.4.10)에서 확인했다.

### 5. ngram 모드별 변환

- 자연어 모드: 검색어를 n-gram들의 **합집합**으로 바꾼다. `'삼성전자'` → `삼성 OR 성전 OR 전자`.
- 불리언 모드: n-gram **구(phrase) 검색**으로 바꾼다. `'삼성전자'` → `"삼성 성전 전자"`가 이어서 나오는 문서만(MySQL 8.4 14.9.8).
- 로컬 재현: 불리언은 문서 1(삼성전자…)만, 자연어는 1·2·3·4 모두. '성전 이야기'(문서 4)는 `성전` 조각 하나로 **자연어 모드에만** 걸렸다.

### 6. GIN 쓰기 비용

- 원인: 행 하나가 트라이그램 키 수십 개를 만들어 역색인에 넣는다. `fastupdate`(기본 켜짐)는 이를 대기 목록에 모은다. 대기 목록이 `gin_pending_list_limit`(기본 4MB)을 넘기면 **그 쓰기**가 정리를 떠맡아 느려진다. 검색은 대기 목록을 추가로 훑어 느려진다(PostgreSQL 17 64.4.4.1).
- 확인: `SELECT * FROM pgstatginindex('idx')`의 `pending_pages`. 로컬 재현(예시)에서 10만 행 적재가 인덱스 없이 75 ms, GIN이 있으면 2982 ms였고 직후 `pending_pages = 315`였다.
- 대처
  - autovacuum이 자주 돌게 해 대기 목록을 백그라운드에서 비운다.
  - 응답 시간 일관성이 중요하면 `fastupdate = off`. 쓰기는 느려지지만 튀지 않는다.
  - 백그라운드 작업에서 `gin_clean_pending_list()`를 부른다.
  - 대량 적재는 인덱스를 지우고 다시 만든다(64.4.5).

### 7. BRIN과 물리 순서

- 시간순 테이블: 블록 범위마다 `ts` 최솟값~최댓값이 겹치지 않는다. 1시간 구간과 겹치는 범위만 읽는다. 로컬 재현(예시)에서 `Heap Blocks: lossy=256`, 3.2 ms였다. 인덱스는 24 kB(B-tree 6600 kB).
- 섞인 테이블: 모든 범위가 거의 전체 기간을 덮는다. 어떤 구간 조건이든 모든 범위가 겹친다. 로컬 재현에서 플래너는 `Seq Scan`을 골랐다. BRIN을 강제해도 테이블 전체를 lossy로 읽었다.
- 미리 아는 법: `pg_stats.correlation`. 로컬 재현에서 시간순 1, 섞인 쪽 0.004였다. 범위 조회용 기본 `minmax` BRIN은 1(또는 −1)에 가까울 때만 쓴다(등호용 `bloom` BRIN 등 다른 연산자 클래스는 기준이 다르다, 64.5.2).

### 8. 공간 검색

- PostgreSQL: GiST 인덱스(`USING gist (loc)`, PostGIS의 geometry도 GiST). 영역은 `loc <@ box '…'`, 가까운 순은 `ORDER BY loc <-> point '…' LIMIT 3`으로 인덱스가 거리 순서대로 돌려준다. 로컬 재현에서 `Index Scan using shop_gist … Order By`였다.
- MySQL 8.4: `SPATIAL INDEX`(R-tree, 13.4.10)와 공간 함수(`ST_Contains`·`MBRContains` 등). 컬럼을 `NOT NULL` + 명시적 `SRID`로 정의해야 옵티마이저가 인덱스를 쓴다(10.3.3). 가까운 순 KNN을 인덱스로 하는지는 확인하지 못했다 [?].
- R-tree는 노드마다 자식들을 감싸는 **최소 경계 사각형(MBR)**을 둔다. 질의 영역과 MBR이 겹치지 않으면 그 가지 전체를 건너뛴다. KNN은 MBR까지의 거리 하한이 작은 가지부터 내려간다.

### 9. 요약되지 않은 범위

- 이미 요약된 범위에 들어온 행은 요약에 반영되지만, 마지막 요약 범위를 벗어난 새 블록 범위는 자동으로 요약되지 않는다. VACUUM(자동 포함)이나 `brin_summarize_new_values()`가 요약을 만든다. `autosummarize`는 기본 꺼짐이다(PostgreSQL 17 64.5.1.1).
- 요약이 없는 범위는 조건과 상관없이 **통째로 결과 후보에 넣는다**(`brin.c`: "For page ranges with no indexed tuple, we must return the whole range"). 그래서 적재 직후 구간은 BRIN이 걸러 주지 못한다.
- 대처: 적재 뒤 `brin_summarize_new_values('idx')`를 부르거나, 인덱스에 `autosummarize = on`을 설정한다.
