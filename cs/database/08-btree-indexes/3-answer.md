# database/08-btree-indexes — 정답

## 정답

### 1. 왜 B+트리인가

- 디스크 비용은 "몇 페이지를 읽나"로 센다. B+트리는 노드 하나를 페이지 하나에 맞춘다. 한 번 읽을 때 키 수백 개를 비교해 수백 갈래 중 하나로 내려간다.
  - 이진 탐색 트리는 한 노드에 키 하나다. 노드마다 페이지를 읽으면 높이 log₂N만큼 읽어야 한다.
  - 정렬 배열은 찾기는 좋지만, 중간 삽입마다 뒤를 밀어야 한다.
- 값을 잎에만 두면 내부 노드에 구분 키만 들어가 갈래가 더 많아진다.
- 잎을 형제 포인터로 이으면 범위 조회(`BETWEEN`, `ORDER BY`, `>`)가 한 번 내려간 뒤 옆으로 걷기가 된다(CMU L8).

### 2. 높이 계산

- 잎당 키: 200,000 / 547 ≈ **366개**. `avg_leaf_density` 90%(오른쪽 끝 삽입의 fillfactor 90)와 맞는다.
- 3층: 400 × 400 × 366 ≈ **5,800만** 행(예시 계산).
- 4층: 400 × 5,800만 ≈ **230억** 행.
- 행이 400배 늘어도 층은 1 는다. 루트·내부는 몇 페이지뿐이라 거의 늘 버퍼 풀에 있다. 실제 디스크 읽기는 잎과 행 정도다.

### 3. 분할

```text
  [30 35 40 50 55] 에 45
  → 나눈다  [30 35 40]  [45 50 55]
  → 부모에 (45, 새 잎 포인터)를 넣는다
  → 부모도 꽉 찼으면 부모도 나누고 그 부모에 구분 키를 올린다
  → 루트까지 차면 루트를 나누고 그 위에 새 루트를 만든다 → 높이 +1
```

- 트리는 **위로** 자란다. 그래서 모든 잎의 깊이가 늘 같다(PG 17 문서 64.1.4.1 "cascade upwards", 루트 분할로 새 층).
- 분할점을 어디로 잡을지는 구현이 정한다. PG는 오른쪽 끝 삽입이면 왼쪽을 fillfactor까지 채우고 나눈다.

### 4. 순차 vs UUIDv4

- 로컬 재현(예시, PostgreSQL 17.11)
  - 순차 bigint: 밀도 **90%**, 조각화 **0%**, 잎 547.
  - UUIDv4: 밀도 **65.69%**, 조각화 **49.71%**, 잎 1052.
- 이유
  - 순차 키는 늘 오른쪽 끝 잎에 들어간다. 그 잎을 90%까지 채우고 새 잎을 파일 끝에 붙인다. 논리 순서 = 물리 순서라 조각화가 0이다.
  - 무작위 키는 아무 잎에나 들어간다. 꽉 찬 잎은 반씩 나뉘고, 나뉜 잎들은 다시 무작위로 채워진다. 평균이 반과 가득 사이에 머문다. 새 잎은 파일 끝에 붙지만 논리 위치는 중간이라 조각화가 생긴다.
- `REINDEX` 뒤: 정렬해서 잎부터 채우므로 밀도 **89.96%**, 조각화 0%, 잎 767. 같은 UUID인데 잎이 1052 → 767로 줄었다.
- MySQL 8.4 InnoDB도 같은 방향이다. 무작위 BINARY(16) PK 3049페이지 → 재생성 후 2149페이지. 문서도 순차 삽입 약 15/16, 무작위 1/2~15/16로 적는다(17.6.2.2).

### 5. 반쯤 빈 잎

- PostgreSQL: **완전히 빈** 잎만 VACUUM이 지운다. 반쯤 빈 잎끼리 합치지 않는다. 항목을 좌우로 옮기면 반대 방향으로 가는 스캔이 항목을 놓칠 수 있어서다(nbtree README). 대신 분할 직전에 bottom-up deletion·deduplication으로 자리를 만든다.
- InnoDB: 페이지 채움이 `MERGE_THRESHOLD`(기본 50%) 아래로 내려가면 이웃 페이지와 합치려 한다(17.6.2.2).
- 대량 삭제 뒤 PG 인덱스가 안 주는 이유: 지운 키가 여러 잎에 흩어지면 어느 잎도 완전히 비지 않는다. 회수할 페이지가 없다. `REINDEX INDEX CONCURRENTLY`로 다시 만든다.

### 6. 트리를 몇 번 내려가나

- InnoDB
  - `SELECT *`: 보조 인덱스 `ix_email`을 내려가 PK를 얻고 → **PK 트리를 한 번 더** 내려가 행을 읽는다. 두 번이다.
  - `SELECT id`: 보조 인덱스 레코드에 PK `id`가 이미 있다. 한 번으로 끝난다. `EXPLAIN FORMAT=TREE`가 `Covering index lookup`이라고 쓴다(로컬 재현).
- PostgreSQL
  - `SELECT *`: 인덱스를 내려가 `ctid`를 얻고 힙 페이지 하나를 읽는다(재현: `shared hit=1 read=3`, 인덱스 3층 + 힙).
  - `SELECT id`: `email` 인덱스 잎에는 `(email, ctid)`만 있고 `id`가 없다. 그래서 `SELECT *`와 똑같이 인덱스 → 힙이다. InnoDB와 달리 PK가 보조 인덱스에 들어 있지 않기 때문이다.
  - `(email) INCLUDE (id)` 인덱스를 만들거나 `SELECT email`만 고르면 `Index Only Scan`이 가능하다. 단 가시성 지도에서 그 힙 페이지가 "모두에게 보임"이어야 힙을 건너뛴다. 재현에서는 VACUUM 뒤 `Heap Fetches: 0`.
- 커버링 조건
  - InnoDB: 조회 칼럼이 (인덱스 칼럼 + PK 칼럼) 안에 있다.
  - PostgreSQL: 조회 칼럼이 인덱스(키 + `INCLUDE` 칼럼) 안에 있고, 페이지가 all-visible이다.

### 7. 인덱스를 타나

| 조건 | 결과 | 이유 |
|---|---|---|
| `lower(email) = ?` | ✗ | 인덱스는 `email` 순서다. `lower(email)` 순서가 아니다 |
| `date(created_at) = ?` | ✗ | 칼럼을 함수로 감쌌다 |
| `created_at >= ? AND created_at < ?` | ✓ | 칼럼이 맨몸이다. 범위 스캔 |
| `email = 777` (MySQL) | ✗ | 문자열과 숫자 비교라 칼럼 쪽이 숫자로 변환된다(재현 `Table scan`) |
| `email LIKE '%777@ex.com'` | ✗ | 앞부분이 정해지지 않아 트리의 어디서 시작할지 모른다 |

- 로컬 재현(PostgreSQL 17.11, MySQL 8.4.10) 실행 계획이 위와 같았다.
- 고치기: 범위로 고쳐 쓰기, 식 인덱스(PG `(lower(email))`, MySQL `((lower(email)))`), 바인딩 타입 맞추기.

### 8. `timestamptz::date` 식 인덱스

- 결과: `ERROR: functions in index expression must be marked IMMUTABLE`(로컬 재현).
- 이유: `timestamptz`를 날짜로 바꾸는 결과는 세션 `TimeZone`에 따라 달라진다. 같은 행이 세션마다 다른 인덱스 키를 가지면 인덱스가 틀어진다. 그래서 PG는 IMMUTABLE 함수만 식 인덱스에 허용한다.
- 대신: 조건을 반열린 범위(`created_at >= '2026-03-01 00:00+09' AND created_at < '2026-03-02 00:00+09'`)로 고쳐 기존 `created_at` 인덱스를 탄다.
- 시간대를 식 안에 못 박으면 결과가 세션과 무관해진다. `((created_at AT TIME ZONE 'Asia/Seoul')::date)` 식 인덱스는 로컬 재현에서 만들어졌다. 단 쿼리도 똑같은 식을 써야 그 인덱스를 탄다. 시간대 처리 전반은 27번에서 다룬다.

### 9. UUIDv4 PK 장애

- 확인 지표
  - PG: `pgstatindex`의 `avg_leaf_density`(약 66%), `leaf_fragmentation`(약 50%), 인덱스 크기 추이. `EXPLAIN (ANALYZE, WAL, BUFFERS)`의 `fpi`·`dirtied`. 재현: 10만 행 삽입에 WAL 12.9MB → 21.3MB, FPI 4 → 1,064, dirtied 721 → 1,963.
  - MySQL: `data_length`가 재생성 뒤보다 크다. 버퍼 풀 적중률이 떨어진다(`Buffer pool hit rate`).
- 원인: 삽입마다 다른 잎을 건드린다. 잎이 반쯤 찬 채 쪼개진다. `full_page_writes = on`(기본값)이면 체크포인트 뒤 처음 고치는 페이지마다 전체 페이지 이미지가 WAL에 실린다. 인덱스가 버퍼 풀보다 커지면 삽입마다 디스크 읽기까지 붙는다.
- 고치기
  - 내부 PK는 단조 증가(bigint 시퀀스·시간 순 ID)로 두고 외부 노출 ID를 따로 둔다(28번).
  - UUID가 꼭 필요하면 시간 순으로 정렬되는 UUIDv7(RFC 9562).
  - 이미 부푼 인덱스는 `REINDEX INDEX CONCURRENTLY`·`OPTIMIZE TABLE`로 재구성한다.
