# database/28-key-strategy-surrogate-natural-public-id — 정답

## 정답

### 1. 네 질문

| 질문 | 깨지면 |
|---|---|
| 값이 바뀌나? | FK로 복사된 모든 행을 연쇄 수정(자연키 PK) |
| 밖에서 보이나? | 열거·추측·사업 규모 추정(순차 ID 노출) |
| 어떤 순서로 생기나? | 랜덤 삽입 → 페이지 분할·반쯤 빈 페이지·버퍼 풀 적중률 하락(UUIDv4) |
| 어떤 타입으로 나가나? | JSON 숫자 64비트 → JavaScript에서 끝자리 변형 |

### 2. 이메일은 UNIQUE, PK는 대리키

```sql
CREATE TABLE users (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email  text NOT NULL UNIQUE
);
CREATE TABLE orders (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id  bigint NOT NULL REFERENCES users(id)
);
```

- 이메일 변경: `UPDATE users SET email = ? WHERE id = ?` 한 행이다. orders 등은 `user_id`만 가지므로 바뀔 것이 없다.
- 이메일이 PK였다면 참조하는 모든 테이블의 FK 값을 고쳐야 한다(`ON UPDATE CASCADE`면 한 문장이 여러 테이블 행을 잠근다. 없이 기본 `NO ACTION`/`RESTRICT`면 참조 행이 있을 때 FK 위반으로 실패).
- 대소문자 무시 유일성 같은 비교 규칙은 10번 노트(collation)의 주제다.

### 3. 순차 vs 랜덤 삽입

```text
  bigint 시퀀스                          UUIDv4
  [..90개][..90개][..90개][새 키 ▶]       [  ][새 키][  ][  ][새 키][  ]
  항상 오른쪽 끝 한 페이지에만 삽입          매 삽입이 무작위 리프로
  꽉 차면 새 페이지를 오른쪽에 붙임          가득 찬 중간 페이지를 반으로 분할
```

- 버퍼 풀: 순차 키는 오른쪽 끝 리프와 그 위 경로만 뜨겁다. 작은 메모리로도 삽입이 캐시에서 끝난다. 랜덤 키는 모든 리프가 번갈아 필요하다. 인덱스가 버퍼 풀보다 커지면 삽입마다 디스크 읽기가 생기고 적중률이 떨어진다.

### 4. avg_leaf_density

| PK | 로컬 재현(PostgreSQL 17.11, 20만 행) |
|---|---|
| bigint | 90% (단편화 0) |
| UUIDv4 | 65.9% (단편화 50.2) |
| UUIDv7(밀리초 미만 비트 포함) | 90.0% (단편화 0) |

- bigint가 90%인 이유: B-tree 기본 fillfactor가 90이다. 문서: 오른쪽 끝에 새 최대 키를 붙일 때 리프를 이 비율까지 채운다.
- v4는 중간 분할로 약 2/3만 찬다. 인덱스 크기도 8456 kB로 bigint(4408 kB)의 약 1.9배였다(키 크기 8→16바이트 몫 포함).

### 5. UUIDv7

```text
  0          47 48  51 52      63 64 65 66                      127
  [ unix_ts_ms ][ ver ][ rand_a  ][var][        rand_b           ]
    밀리초 시각    0111   12비트       10    62비트
```

- 장점: 바이트 순 정렬이 곧 밀리초 단위 시간순이라 인덱스 지역성이 좋다(RFC 9562 §6.11). 같은 밀리초 안의 순서는 §6.2 단조 증가 방식으로 만들 때만 생성 순서와 맞는다. 분산 환경에서 조율 없이 만든다.
- 대가: 앞 48비트에서 생성 시각이 드러난다. 키가 16바이트라 bigint보다 크다.
- RFC 9562 §8: 보안 목적이 조금이라도 있으면 v4를 써야 한다(SHOULD). 동시에 UUID가 추측하기 어렵다고 가정하지 말고(SHOULD NOT), 보안 수단으로 쓰지 말라(MUST NOT)고 한다.

### 6. InnoDB가 더 민감한 이유

1. PK가 곧 테이블이다(클러스터드 인덱스). 랜덤 PK면 **행 데이터 페이지 자체**가 분할되고 반쯤 빈다. 재현(MySQL 8.4.10)에서 `data_length`가 bigint 6.8 MB, 랜덤 16바이트 14.2 MB였다.
2. 모든 보조 인덱스 레코드가 PK 값을 담는다(문서 17.6.2.1). PK가 8바이트에서 16바이트가 되면 보조 인덱스가 모두 커진다.

- `UUID()`는 버전 1(시간 기반)이다. `UUID_TO_BIN(u, 1)`은 시간 필드의 앞뒤를 바꿔, 천천히 변하는 부분이 앞에 오게 한다. 그래서 거의 순차로 삽입된다(재현: 8.9 MB, 545페이지). `BIN_TO_UUID(b, 1)`로 되돌린다.

### 7. 끝자리 변형 404

- 원인: JavaScript Number는 IEEE 754 배정밀도라 2^53 − 1(9007199254740991)까지만 정수가 정확하다. 서버가 ID를 JSON **숫자**로 보냈고, 브라우저의 `JSON.parse`가 가장 가까운 double로 바꿨다. 모바일(64비트 정수 파서)은 멀쩡했다.
- 서버: ID를 문자열로 직렬화한다(Jackson `@JsonSerialize(using = ToStringSerializer.class)`). 호환을 위해 `id_str` 같은 문자열 필드를 먼저 추가하고 옮긴다.
- 클라이언트: ID 타입을 `string`으로 두고 산술하지 않는다. `BigInt`는 `JSON.stringify`가 직렬화하지 못한다(재현: `TypeError: Do not know how to serialize a BigInt`).

### 8. 순차 ID 열거

- 1순위: **객체 단위 권한 검사**다. "이 주문의 소유자가 요청자인가"를 서버에서 확인한다. 이것이 빠진 것이 진짜 결함이다.
- UUID만으로 부족한 이유: ID는 URL·로그·공유 링크·리퍼러로 새어 나간다. 새어 나간 ID는 누구나 쓸 수 있다. RFC 9562 §8은 UUID를 보유만으로 접근을 주는 수단으로 쓰면 안 된다(MUST NOT)고 적는다.
- 그다음: 외부 ID를 랜덤 공개 ID로 분리해 추측과 규모 추정(월초·월말 번호 차이)을 막는다.

### 9. 시퀀스 빈틈

- 결과: 1, 3. 롤백된 트랜잭션이 받은 2는 재사용되지 않는다(로컬 재현, PostgreSQL 17.11).
- 시퀀스는 "연속"을 보장하지 않는다. 유일성도 시퀀스가 아니라 PK·UNIQUE 제약이 보장한다(재설정·수동 입력이면 겹칠 수 있다, PG 17 문서 5.3).
- 빈틈이 없어야 하는 번호(예: 빈 번호가 있으면 누락·삭제를 의심받는 전표 번호처럼 업무가 연속을 요구하는 번호)는 시퀀스가 아니라 별도 채번 테이블 + 행 락 등으로 설계한다. 그 대가로 채번이 직렬화된다.
