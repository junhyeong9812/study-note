# database/32-replication-leader-follower — 정답

## 정답

### 1. 푸는 것과 못 푸는 것

- 푼다
  - 가용성: 리더가 죽으면 팔로워를 승격한다.
  - 읽기 확장: 읽기를 팔로워들로 나눈다.
- 못 푼다
  - 쓰기 부하: 모든 팔로워가 리더와 **같은 쓰기를 전부** 재생한다. 쓰기는 리더 한 대가 받는다.
  - 데이터 크기: 모든 노드가 전체 데이터를 갖는다.
  - 사람의 실수: `DROP`도 그대로 전파된다(20번 백업).
- 쓰기·크기 확장은 분할(33번)의 몫이다.

### 2. 무엇을 보내나

| | PostgreSQL 물리 복제 | MySQL binlog ROW |
|---|---|---|
| 내용 | WAL — 어느 파일·블록을 어떻게 바꿨나 | DML은 행 이벤트 — 어떤 행이 어떻게 바뀌었나(`Table_map`·`Update_rows`). DDL은 문장으로 기록 |
| 장점 | 팔로워가 블록 단위로 같은 데이터를 갖는다(힌트 비트 등 WAL 밖 바이트·`UNLOGGED` 테이블 제외). WAL에 남는 변경(DDL·인덱스)이 자동 | 버전·구성이 다른 서버로도 보낼 수 있다. 행 단위로 읽어 CDC 등에 쓴다 |
| 단점 | 같은 메이저 버전·아키텍처여야 한다. 일부 테이블만 보낼 수 없다 | 대량 변경이면 행마다 이벤트라 크다(`binlog_row_image = FULL`이면 전/후 전체 행) |

- ROW가 안전한 이유: 문장을 다시 실행하면 `UUID()`·`RAND()`·`SYSDATE()`·`ORDER BY` 없는 `LIMIT` 같은 비결정 요소가 팔로워에서 다른 결과를 낼 수 있다. 행 이미지는 결과 자체라 같은 순서로 적용하면 같은 상태가 된다(상태 기계 복제).

### 3. 동기 수준별 커밋 응답

| `synchronous_commit` | 커밋 응답이 기다리는 것 |
|---|---|
| `remote_write` | 리더 로컬 flush + s1이 받아 **OS에 쓴** 응답 |
| `on` | 리더 로컬 flush + s1이 **디스크에 flush**한 응답 |
| `remote_apply` | 리더 로컬 flush + s1이 **재생까지** 해서 조회에 보이는 응답 |

- "커밋 직후 s1 조회에서 반드시 보인다"는 **`remote_apply`**만 성립한다. `on`은 s1 디스크에는 있지만 아직 재생 전일 수 있다.
- 대가: `remote_apply`가 가장 느리다. 그리고 s1이 죽으면 세 경우 모두 커밋이 멈출 수 있다(후보를 여럿 두는 이유).

### 4. AFTER_SYNC vs AFTER_COMMIT, 타임아웃

- `AFTER_SYNC`(8.4 기본): binlog 기록·sync → 복제본 ack 대기 → ack 뒤 스토리지 엔진 커밋 → 클라이언트 응답. 커밋은 ack 뒤에야 보이므로 모든 클라이언트가 같은 시점에 본다. 준동기가 유지되는 동안에는 리더가 죽어도 리더에서 커밋된 것이 최소 1개 복제본 relay log에 있다(타임아웃으로 비동기로 떨어진 구간은 예외). 대신 옛 리더는 버리고 다시 만들어야 한다(binlog에 커밋 안 된 트랜잭션이 있을 수 있음).
- `AFTER_COMMIT`: 엔진 커밋 **뒤에** ack를 기다린다. ack 전에 다른 클라이언트가 그 커밋을 볼 수 있다. 그때 리더가 죽으면 "봤던 데이터"가 새 리더에 없을 수 있다.
- 타임아웃: `rpl_semi_sync_source_timeout`(기본 10000 ms) 안에 ack가 없으면 **비동기로 되돌아간다**. 그 동안의 커밋은 비동기처럼 유실될 수 있다. 복제본이 따라잡으면 다시 준동기가 된다.

### 5. "내 글이 없다"

1. 읽기를 팔로워로 보내는지, 쓰기 직후 읽기인지 확인한다.
2. 지연을 본다
   - PostgreSQL(리더): `pg_stat_replication`의 `replay_lag`, `pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)`.
   - MySQL(복제본): `SHOW REPLICA STATUS`의 `Seconds_Behind_Source`(0이어도 항상 따라잡았다는 뜻은 아님).
3. 고친다
   - 쓴 사용자는 N초간 리더에서 읽기, 또는 자기 데이터는 항상 리더.
   - 정확하게: 커밋 뒤 위치를 세션에 저장 → PostgreSQL은 `pg_last_wal_replay_lsn() >= 저장 LSN`인 팔로워만, MySQL(GTID)은 `WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)` 후 실패 시 리더.
   - 지연 임계치를 넘은 팔로워는 풀에서 뺀다.

### 6. 세 가지 읽기 보장

| 보장 | 깨진 예 | 지키는 법 |
|---|---|---|
| read-your-writes | 내가 쓴 댓글이 새로고침 직후 안 보인다 | 쓴 사람은 리더에서, 또는 커밋 LSN/GTID를 따라잡은 팔로워에서 읽기 |
| monotonic reads | 댓글이 3개 보였다가 다시 2개로 보인다 | 세션(사용자)을 한 팔로워에 고정 |
| consistent prefix reads | 답글이 원글보다 먼저 보인다 | 인과 관계가 있는 쓰기를 같은 파티션에 두기, 또는 인과 순서 추적(버전) |

### 7. 비동기 페일오버의 결과

- 승격된 팔로워에는 커밋 4·5가 없다. 클라이언트는 "성공"을 받았으니 **확인된 쓰기 유실**이다.
- 새 리더가 4'·5'를 받으면 같은 ID·같은 키가 다른 뜻으로 재사용될 수 있다. 다른 저장소가 그 ID를 참조하면 어긋난다.
- PostgreSQL: 승격하면 새 타임라인이 시작된다. 옛 리더는 타임라인이 갈라져 그대로 팔로워로 붙을 수 없다. `pg_rewind`로 옛 리더의 데이터 디렉터리를 새 리더 기준으로 되감고(바뀐 블록만 복사) 팔로워로 붙인다. 되감으면 4·5는 사라지므로, 필요하면 그 전에 따로 뽑아 둔다.

### 8. 복구 충돌로 취소

- SQLSTATE `40001`(`ERRCODE_T_R_SERIALIZATION_FAILURE`). 같은 메시지라도 복구와의 버퍼 교착이면 `40P01`이다(`standby.c`).
- 원인: 리더의 vacuum이 옛 튜플 버전을 지운 기록을 팔로워가 재생해야 한다. 팔로워의 리포트가 그 버전을 아직 볼 수 있다. 받은 WAL의 적용이 `max_standby_streaming_delay`(기본 30초, 조회마다가 아니라 적용 지연의 총량)를 넘어 조회를 취소했다.
- 대처와 대가
  1. `max_standby_streaming_delay`를 늘린다 → 그만큼 재생이 멈춰 그 팔로워의 복제 지연이 커진다.
  2. `hot_standby_feedback = on` → 리더가 그 버전을 지우지 않는다 → 리더 테이블 bloat.
  3. 긴 분석을 리포트 전용 복제본(지연 허용)이나 별도 분석 DB·논리 복제로 옮긴다 → 운영 대상이 늘어난다.

### 9. 팔로워를 내렸을 때

- (a) 커밋 정지: `synchronous_standby_names`에 그 팔로워 하나만 있었다. `synchronous_commit`이 `on`(또는 `remote_write`·`remote_apply`)이면 그 응답을 끝없이 기다린다(`wait_event = SyncRep`). 예방: `ANY 1 (s1, s2)`처럼 후보를 여럿, 점검 전 설정에서 빼고 reload.
- (b) 디스크 풀: 그 팔로워의 복제 슬롯이 WAL을 붙잡았다. `max_slot_wal_keep_size` 기본 -1이면 무제한이다. 예방: 상한을 두고, `pg_replication_slots`의 보존량(`pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)`)을 경보하고, 오래 못 돌아올 팔로워의 슬롯은 지운다.

### 10. GitHub 2012

- 피해: 뒤처진 노드가 7분간 쓰기를 받았다. MySQL이 만든 ID로 Redis를 조회하던 관계가 어긋나 일부 이벤트가 엉뚱한 사용자 대시보드에 보였고, 비공개 저장소 16개가 7분간 권한 없는 사람에게 접근 가능했다.
- 교훈
  1. 승격 대상은 "가장 앞선 복제본"이어야 한다. 다수결 설정이 있어도 클러스터 분할 때 소프트웨어가 두 결정을 동시에 내릴 수 있다. 승격 도구가 복제 위치를 확인하고, 옛 리더를 확실히 막아야(펜싱) 한다.
  2. DB가 만든 ID가 다른 저장소의 키로 쓰이면, 페일오버로 되감긴 ID는 **보안 사고**가 된다. 승격 뒤 시퀀스를 크게 건너뛰거나, 재사용되지 않는 ID(외부 발급)를 쓴다.
