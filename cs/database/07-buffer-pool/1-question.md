# database/07-buffer-pool — 질문

## 질문

1. (그림) 실행기가 페이지 하나를 요청했을 때 버퍼 풀이 하는 일을 hit / miss로 나눠 순서대로 적어라. page table은 무엇이고, 디스크의 page directory와 무엇이 다른가?
2. (경계) 핀(pin)과 페이지 락(latch)은 각각 무엇을 막나? 핀이 잡힌 페이지를 다른 스레드가 읽을 수 있나?
3. (왜) 버퍼 풀은 고친 페이지를 바로 디스크에 쓰지 않는다. 왜 미루며, 미뤄도 커밋한 데이터가 안전한 근거는 무엇인가? dirty 희생자를 쓸 때 지켜야 할 순서는?
4. (그림) CLOCK 교체를 그려라. PostgreSQL clock sweep은 기본 CLOCK에서 무엇을 더했나(usage_count의 상한 포함)?
5. (예측) PostgreSQL 17, `shared_buffers = 128MB`에서 6667페이지 테이블과 443페이지 테이블을 각각 한 번 풀 스캔했다. 스캔 직후 각 테이블의 페이지가 버퍼 풀에 몇 개쯤 남나? 근거가 되는 조건과 크기는?
6. (예측) MySQL 8.4 InnoDB에서 처음 읽힌 페이지는 LRU 리스트 어디에 들어가나? 그 페이지가 0.5초 뒤, 그리고 3초 뒤 다시 읽히면 각각 어떻게 되나?
7. (연결) PostgreSQL은 `shared_buffers`를 RAM의 25%에서 시작하라 하고, InnoDB 문서는 버퍼 풀에 최대 80%까지 준다고 한다. 두 권고가 이렇게 다른 이유를 운영체제 페이지 캐시와 연결해 설명하라.
8. (장애 진단) 새벽 3시 리포트 배치가 돈 뒤 아침 9시까지 OLTP p99가 높다. 어떤 지표로 "버퍼 풀 오염"을 확인하고, 엔진별로 어떻게 막나?
9. (장애 진단) 버퍼 풀을 키웠더니 컨테이너가 exit code 137로 재시작을 반복한다. 무슨 일이고 어떻게 크기를 정해야 하나?
