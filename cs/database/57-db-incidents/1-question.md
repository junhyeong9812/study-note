# database/57-db-incidents — 질문

## 질문

1. (연결) GitLab 2017-01-31 사고에서 보조 서버의 복제가 끊긴 직접 원인은 무엇이고, 어떤 설정·장치가 있었다면 수동 재구축 없이 따라잡을 수 있었나? 관련 leaf를 말하라.
2. (장애 진단) GitLab 포스트모템이 나열한 백업·복구 절차 넷을 들고, 각각이 사고 당일 왜 쓸 수 없었는지 말하라. 결국 무엇으로 복구했나?
3. (왜) GitLab의 `pg_dump` 백업은 왜 실패했고, 그 실패는 왜 아무도 몰랐나? 포스트모템의 5 Whys가 도달한 조직 원인은?
4. (왜) GitLab은 복구 과정에서 모든 DB 시퀀스를 100,000씩 올렸다. 왜 필요했나? 같은 원리가 비동기 페일오버 뒤에도 적용되는 이유는?
5. (규칙) PostgreSQL XID wraparound 보호는 무엇을 막고 무엇은 허용하나? 경고·거부 문턱이 9.4·13판과 14·17판에서 어떻게 다른가?
6. (장애 진단) Sentry 2015 사고에서 autovacuum이 끝났는데도 쓰기 거부가 풀리지 않았다. 원인은 무엇이었고 Sentry는 어떻게 5분 만에 복구했나? 단일 사용자 모드에 대한 PostgreSQL 17 문서의 입장은?
7. (연결) Sentry가 밝힌 autovacuum 설정 문제와 바꾼 설정은? `maintenance_work_mem` 정정은 PostgreSQL 17에서도 맞는 말인가?
8. (예측) GitHub 2018-10-21 사고에서 43초 네트워크 단절이 24시간 11분 저하로 이어진 사슬을 설명하라. 옛 주 서버가 죽지 않았다는 점이 왜 중요한가?
9. (경계) GitHub가 동부로 "그냥 되돌리지" 못하고 백업 복원을 택한 이유는? 복원 뒤에도 사용자가 오래된 데이터를 본 이유와, 복구 예상 시간이 빗나간 이유는?
10. (연결) 세 사건에서 공통으로 뽑을 수 있는 "마지막 방어선이 실패한 이유"를 하나씩 말하고, 내 시스템에 옮길 점검 항목을 사건마다 두 개씩 들어라.
