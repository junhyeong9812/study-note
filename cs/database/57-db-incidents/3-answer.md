# database/57-db-incidents — 정답

## 정답

### 1. GitLab 복제가 끊긴 이유

- 약 23:00 UTC, 부하 증가로 보조 서버(db2)의 복제가 뒤처졌다. 보조가 필요로 한 WAL 세그먼트가 주 서버에서 **이미 지워져** 복제가 실패했다(포스트모템).
- GitLab은 WAL 아카이빙을 쓰지 않았다. 그래서 보조의 데이터 디렉터리를 지우고 `pg_basebackup`으로 처음부터 다시 받는 수동 절차밖에 없었다.
- 따라잡을 수 있게 하는 장치
  - WAL 아카이빙: 보조가 아카이브에서 빠진 세그먼트를 가져온다(20번).
  - 복제 슬롯이나 `wal_keep_size`(12 이하는 `wal_keep_segments`) 같은 보존 설정: 주 서버가 보조가 받지 않은 WAL을 지우지 않는다(19·32번). 대신 슬롯은 보조가 오래 멈추면 주 서버 디스크를 채울 수 있다.
- 포스트모템은 당시 보존 설정 값을 적지 않았다. 위 장치 목록은 이 노트의 판단이다.

### 2. 백업 절차 넷과 실패 이유

| 절차 | 당일 상태 |
|---|---|
| `pg_dump` → S3 (24시간마다) | S3 버킷이 비어 있음. 9.2 `pg_dump`가 9.6 서버에서 오류로 끝남 |
| LVM 스냅숏 (24시간마다, 스테이징 복사용) | 약 24시간 전 것과, 엔지니어가 작업 전 수동으로 뜬 약 6시간 전 것이 있었음 |
| Azure 디스크 스냅숏 | DB 서버에는 켜져 있지 않음(다른 절차로 충분하다고 가정, 복원에 며칠 걸릴 수 있음) |
| 복제(hot standby) | 페일오버용. 복제가 끊겼고, 재구축하며 보조 데이터를 이미 지움 |

- 복구: 약 6시간 전 수동 LVM 스냅숏에서 만든 **스테이징 DB**의 데이터 디렉터리를 운영으로 복사했다. 느린 디스크(약 60 Mbps) 탓에 약 18시간 걸렸다. 결과는 1월 31일 17:20 UTC 상태였다.
- 포스트모템이 나열한 절차는 넷이다. 커리큘럼의 "5종"은 이 글에서 확인하지 못했다.

### 3. `pg_dump` 실패와 조직 원인

- 왜 실패: Omnibus 패키지는 데이터 디렉터리의 `PG_VERSION`을 보고 바이너리 판을 고른다. 덤프는 데이터 디렉터리가 없는 앱 서버에서 돌아 기본값 9.2가 쓰였다. 서버는 9.6이었다. `pg_dump`는 자기보다 새 메이저 판 서버를 덤프하지 않아 오류로 끝났다.
- 왜 몰랐나: cron 오류 알림이 메일로만 갔다. 그 메일이 DMARC 서명이 없어 받는 쪽에서 거절됐다.
- 5 Whys의 끝: "백업 절차를 정기적으로 시험하지 않은 이유 — 책임자(ownership)가 없어 아무도 책임지지 않았다." 개선 항목에도 "데이터 내구성 책임자 지정"이 있다.

### 4. 시퀀스 +100,000

- 복구 시점(17:20 UTC) 이후에 발급된 ID는 DB에서 사라졌지만 바깥(알림 메일, 링크, 외부 시스템, 사용자 기억)에 남아 있을 수 있다. 시퀀스를 그대로 두면 같은 ID가 **다른 행에 다시 발급**된다. GitLab은 "사고 전에 쓰였을 수 있는 ID를 다시 쓰지 않도록" 100,000씩 올렸다.
- 비동기 페일오버도 같다. 새 리더에는 옛 리더가 마지막에 발급한 ID가 없다. 그 ID가 다른 저장소의 키로 쓰였다면 재사용 사고가 난다. 32번은 페일오버 뒤 시퀀스를 크게 건너뛰라고 한다.

### 5. XID wraparound 보호

- XID는 32비트 원형 카운터다. 동결되지 않은 행이 약 20억 트랜잭션보다 오래되면 "미래"로 보여 사라진다. 이를 막으려고 PostgreSQL은 한계에 다가가면 **새 XID 할당(쓰기)을 거부**한다. 읽기는 된다(16번).
- 문턱(각 판의 "Routine Vacuuming" 문서)

| 판 | 경고 시작 | 거부 |
|---|---|---|
| 9.4 | 1천만 남음 | 1백만 미만 (`database is not accepting commands to avoid wraparound data loss`) |
| 13 | 1,100만 남음 | 1백만 미만 |
| 14~16 | 4천만 남음 | 3백만 미만 (문구는 9.4와 같음) |
| 17 | 4천만 남음 | 3백만 미만 (`... not accepting commands that assign new transaction IDs ...`) |

- Sentry 글도 "백만 개 미만"이라고 적었다. Sentry가 쓴 판은 글에 없다.

### 6. Sentry — 풀리지 않은 이유와 복구

- 원인: 내부 통계로 보니 autovacuum이 **한 테이블만 빼고** 모두 끝났다. 그 테이블은 이벤트마다 한 행이 쌓이는 거대한 매핑 테이블(이벤트 → 롤업)이었다. 이 테이블의 동결이 끝나지 않아 데이터베이스의 가장 오래된 XID가 전진하지 못했다.
- 복구: 그 테이블은 ID 조회와 중복 방지에만 쓰여 중요도가 낮았고, 복제본에 전체 사본도 있었다. Sentry는 데이터를 포기하고 `TRUNCATE`했다. 5분 뒤 완전 복구됐다. 이틀 뒤에도 옛 하드웨어 시험 기계의 단일 사용자 모드 VACUUM은 24시간째 돌고 있었다.
- PostgreSQL 17 문서 24.1.5: 예전에는 단일 사용자 모드가 필요했지만 지금은 대개 필요 없고 피해야 한다. 시스템을 내려야 하고 wraparound 보호를 끄는 위험이 있어서다. 이 모드가 필요한 유일한 이유로 문서가 드는 것은 불필요한 테이블을 `TRUNCATE`·`DROP`해 VACUUM을 피하려는 경우다(거부 상태의 일반 모드에서는 TRUNCATE가 실패한다). 3백만 여유분이 그 작업을 위해 있다.

### 7. Sentry의 설정

- 문제(글): `autovacuum_freeze_max_age`가 너무 높았다. autovacuum 작업자가 기본값 3이었다. vacuum 지연이 너무 커서 부하는 낮았지만 유지보수가 느렸다.
- 변경: `autovacuum_freeze_max_age = 500000000`, `autovacuum_max_workers = 6`, `autovacuum_naptime = '15s'`, `autovacuum_vacuum_cost_delay = 0`, `maintenance_work_mem = '10GB'`, `vacuum_freeze_min_age = 10000000`. 하드웨어도 메모리 256GB·RAID 셋(OS·WAL·데이터)으로 늘렸다.
- 정정(글 갱신): `maintenance_work_mem`에는 관련 경로에서 1 GB 내부 한도가 있어 큰 값이 쓰이지 않았다.
- PostgreSQL 17에서는 맞지 않는다. 17.0 릴리스 노트가 "vacuum이 더는 1GB로 조용히 제한되지 않는다"고 적는다. 이 정정은 16 이하 판의 이야기다.

### 8. GitHub — 43초가 24시간이 된 사슬

1. 22:52 광장비 교체 중 동부 허브와 동부 주 DC 사이가 43초 끊겼다.
2. 그 사이 Orchestrator(Raft)의 서부 DC + 동부 클라우드 노드가 정족수를 이뤄 쓰기를 서부로 페일오버했다.
3. 연결이 돌아오자 앱이 곧바로 서부의 새 주 서버로 쓰기를 보냈다(원문은 조사 시점에 "거의 40분"이라 쓴다. 23:13 항목에 있지만 22:52부터 21분이므로 그 뒤 조사 중의 시점으로 읽힌다).
4. 동부에는 서부로 복제되지 않은 몇 초의 쓰기가 남아 있었다. 양쪽이 서로 없는 쓰기를 가져 안전하게 되돌릴 수 없었다.
5. 데이터 무결성을 우선해 백업 복원 → 복제 재구성 → 원래 토폴로지 복귀 → 백로그 처리 순으로 갔다. 원격 저장소에서 수 TB를 받는 데 상당한 시간이 들었고, 압축 해제·체크섬·준비·적재가 시간의 대부분을 차지했다.

- 옛 주 서버가 죽지 않았다는 점이 중요한 이유(이 노트의 해석): 동부 DB가 43초 만에 다시 보였고, 거기에는 서부로 복제되지 않은 몇 초의 쓰기가 그대로 남아 있었다. 그사이 서부는 새 쓰기를 받았다. 그래서 **두 갈래의 역사**가 생겼다. 어느 한쪽이 다른 쪽의 앞선 사본이 아니다.

### 9. GitHub — 복원을 택한 이유, 오래된 데이터, 빗나간 예상

- 되돌리지 못한 이유: 동부에만 있는 쓰기가 서부로의 역복제를 막았다. 서부에는 이미 30분 넘게 쌓인 사용자 쓰기가 있어 버릴 수 없었다. GitHub는 "fail-forward" 외의 선택지가 없다고 판단했다.
- 오래된 데이터: 11:12에 모든 주 서버가 동부로 돌아왔지만 읽기 복제본 수십 대가 몇 시간 뒤처져 있었다. 읽기가 넓은 복제본 풀에 퍼져 요청마다 지연된 복제본에 닿을 수 있었다(32번 read-your-writes).
- 빗나간 예상: 복제 텔레메트리로 **선형 보간**해 2시간이라 공지했다. 실제로는 유럽·미국 업무 시작 부하로 쓰기가 늘어 따라잡기가 "power decay"로 느려졌다. 동부 퍼블릭 클라우드에 읽기 복제본을 추가해 복제본당 부하를 낮추자 따라잡았다.

### 10. 공통 교훈과 점검 항목

| 사건 | 마지막 방어선이 실패한 이유 | 점검 항목 두 개 |
|---|---|---|
| GitLab | 백업이 **시험되지 않았다**. 알림은 거절됐고 책임자가 없었다 | 정기 자동 복원 + 마지막 복원 성공 시각 경보 / 백업 도구 판과 서버 판 일치, WAL 아카이빙 |
| Sentry | autovacuum이 부하에 비해 **느리게 설정**돼 있었고, 상세 로그가 없어 진행을 몰랐다 | `age(datfrozenxid)`·`age(relfrozenxid)` 경보 / 거대 쓰기 테이블 분할과 "버려도 되는 테이블" 분류 |
| GitHub | 승격 도구 설정이 **앱의 한계**(리전 간 지연)를 반영하지 않았다. 복원은 원격 전송과 압축 해제·적재 시간에 묶였다 | 승격 범위를 리전 안으로 제한 + 옛 주 서버 펜싱 / 백업 위치까지 포함한 복원 시간 측정, 승격 뒤 남은 트랜잭션(binlog·GTID) 추출 절차 |

공통점: 모두 "있다"와 "작동한다"를 혼동했다. 백업이 있었고, autovacuum이 있었고, 자동 페일오버가 있었다.
