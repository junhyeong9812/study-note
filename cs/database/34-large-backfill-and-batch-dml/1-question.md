# database/34-large-backfill-and-batch-dml — 질문

## 질문

1. (왜) 운영 테이블 1억 행을 `UPDATE … SET … ;` 한 문장으로 바꾸면 락, 옛 버전(undo·dead tuple), 복제, 실패 복구에서 각각 무엇이 생기나?
2. (예측) `WHERE v2 IS NULL ORDER BY id LIMIT 1000 OFFSET k*1000`으로 10,000행을 10번에 나눠 `v2`를 채웠다. 잡은 무엇을 보고하고, 실제로 몇 행이 남나? 에러는 나나? 조건이 바뀌지 않는 UPDATE라면 어떤 반대 문제가 생길 수 있나?
3. (설계) keyset 청크의 한 반복을 SQL로 적어라. OFFSET과 달리 행을 건너뛰거나 두 번 처리하지 않는 이유는? 처리 중 새로 들어오는 행은 누가 맡나?
4. (예측) `won = won * 2` 백필이 5,000행 처리 후 죽어 처음부터 다시 돌렸다. 값 분포는 어떻게 되나? 재시작해도 안전하려면 무엇 두 가지가 필요한가?
5. (적용) 체크포인트 테이블의 `last_id` 갱신을 청크 UPDATE와 같은 트랜잭션에 넣는 이유는? 따로 커밋하면 생기는 두 가지 어긋남은?
6. (연결) gh-ost는 무엇을 기준으로 복사를 멈추고, 그 값을 어떻게 재나? PostgreSQL과 MySQL에서 복제 지연을 직접 볼 때는 각각 무엇을 보나?
7. (장애 진단) PostgreSQL에서 오래된 로그 절반을 DELETE하고 VACUUM까지 했는데 디스크 사용량이 그대로다. 왜인가? 공간을 돌려받는 방법과 그 대가, 그리고 애초에 피하는 설계는?
8. (장애 진단) 백필 중 MySQL 주문 API에 `ERROR 1205 (HY000): Lock wait timeout exceeded`가 쏟아진다. 무엇이 무엇을 막고 있고, 긴급 조치와 근본 조치는? PostgreSQL에서는 백필 쪽에 어떤 설정을 걸어 두면 좋은가?
9. (경계) 백필 잡이 "에러 없이 완료"를 보고했다. 이것만으로 끝났다고 할 수 없는 이유는? 무엇으로 완료를 증명하나?
10. (장애 진단) 청크로 잘 나눴는데 InnoDB의 `History list length`가 계속 늘고 읽기가 느려진다. 무엇을 의심하고 어디서 찾나?
