# database/19-wal-and-logging — 질문

## 질문

1. (왜) 커밋할 때마다 바뀐 데이터 페이지를 모두 디스크에 쓰는 방식은 왜 느린가? WAL은 무엇을 먼저 써서 이 문제를 푸나?
2. (그림) UPDATE 한 번부터 페이지가 디스크에 쓰이기까지를 시간축으로 그리고, WAL 규칙 두 개를 LSN으로 설명하라. PostgreSQL 소스에서 규칙 2는 어디서 지켜지나?
3. (경계) steal·no-steal, force·no-force는 각각 무엇을 허용·요구하나? STEAL + NO-FORCE를 쓰면 복구 때 무엇이 필요하고, 왜 대부분의 DB가 이 조합을 쓰나?
4. (예측) PostgreSQL 17에서 `pgbench` 클라이언트를 1에서 8로 늘렸다. 커밋 수와 `wal_sync` 증가량의 비율은 어떻게 변하리라 예상하나? 이유는? 로컬 재현 수치를 대라.
5. (경계) PostgreSQL `synchronous_commit = off`와 `fsync = off`는 크래시 때 각각 무엇을 잃나? 왜 전자는 트랜잭션 단위로 써도 되고 후자는 안 되나?
6. (연결) MySQL 8.4 `innodb_flush_log_at_trx_commit` 0·1·2는 각각 언제 write·flush하고, 어떤 크래시에서 무엇을 잃나? `sync_binlog`는 왜 함께 1이어야 하나?
7. (왜) fsync가 성공했는데도 정전 뒤 커밋된 데이터가 사라질 수 있는 이유는? 찢어진 페이지는 무엇이고 PostgreSQL과 InnoDB는 각각 어떻게 막나?
8. (장애 진단) PostgreSQL의 WAL 볼륨이 가득 차 DB가 내려갔다. 어떤 메시지가 보이고, 흔한 원인 세 가지와 확인 쿼리, 대처·예방책은?
9. (경계) 체크포인트를 자주 하면 무엇이 좋고 무엇이 나쁜가? `max_wal_size`가 "소프트 한도"라는 것은 무슨 뜻인가?
10. (장애 진단) 코드 변경 없이 모든 쓰기 API의 p99가 수 배로 늘었다. WAL 관점에서 무엇을 확인하고 어떻게 대처하나?
