# database/20-backup-and-pitr — 정답

## 정답

### 1. 세 장치가 살리는 것

| 사고 | 크래시 복구 | 복제본 | 백업 + PITR |
|---|---|---|---|
| 프로세스·OS 크래시 | 살린다 | — | — |
| 디스크·서버 소실 | 못 살린다 | 살린다(비동기면 최근 커밋 유실 가능) | 살린다 |
| 실수로 `DROP`·잘못된 `UPDATE` | 못 살린다(WAL에 실수도 기록됨) | 같이 망가진다(실수도 전파) | 사고 직전 시점으로 |
| 버그·랜섬웨어로 오염 | 못 살린다 | 같이 망가진다 | 오염 전 시점으로 |

- 크래시 복구는 "마지막 커밋 상태"로만 간다. 복제는 변경을 **전파**하는 장치다. "과거로 가기"는 백업만 한다.

### 2. 방식 비교와 선택

| | 논리(`pg_dump`·`mysqldump`) | 물리(`pg_basebackup`) | 연속 아카이브(베이스 + WAL) |
|---|---|---|---|
| 이식성 | 버전·플랫폼 넘나듦 | 같은 메이저 버전·플랫폼 | 같은 메이저 버전·플랫폼 |
| 복원 속도 | 느림(재적재 + 인덱스 재생성) | 빠름(파일 복사 + 짧은 WAL 재생) | 베이스 복사 + 목표까지 WAL 재생 |
| 복원 시점 | 백업 시점 하나 | 백업 시점 하나 | 베이스 이후 아무 시점 |

- RPO 5분: 백업 시점 하나짜리로는 안 된다. **연속 아카이브**가 필요하다. WAL이 적은 서버는 `archive_timeout`으로 세그먼트 전환 상한을 5분 안쪽으로 둔다.
- RTO 30분: 논리 덤프 재적재는 크기에 따라 넘길 수 있다. 물리 베이스 백업을 자주 떠서 재생할 WAL 양을 줄이고, 실제 복원 시간을 **측정**해 확인한다.

### 3. 덤프 + DDL = 전체 대기열

- `pg_dump`는 테이블마다 `ACCESS SHARE` 락을 잡고 끝까지 쥔다.
- `ALTER TABLE`은 `ACCESS EXCLUSIVE`가 필요하다. `ACCESS SHARE`와 충돌하므로 **대기**한다.
- 이후의 `SELECT`(`ACCESS SHARE`)는 덤프와는 충돌하지 않지만, 앞에서 기다리는 `ACCESS EXCLUSIVE` **뒤에 줄을 선다.**
- 로컬 재현(PostgreSQL 17.11): `pg_blocking_pids`가 `SELECT` → `{ALTER}`, `ALTER` → `{덤프}`로 이어졌다. 덤프가 끝날 때까지 그 테이블의 모든 요청이 멈춘다.
- 대처: DDL에 `lock_timeout`, 덤프와 배포 시간 분리.

### 4. `mysqldump --single-transaction`

- 동작: 격리 수준을 REPEATABLE READ로 두고 `START TRANSACTION` 후 덤프한다. InnoDB는 그 시점의 일관된 상태가 락 없이 나온다. 단 `--source-data`를 함께 쓰면 시작할 때 binlog 좌표를 읽느라 전역 읽기 락(`FLUSH TABLES WITH READ LOCK`)을 짧게 잡는다.
- 보장하지 못하는 것
  - MyISAM·MEMORY 같은 비트랜잭션 테이블의 일관성.
  - 덤프 중 다른 연결의 `ALTER`·`CREATE`·`DROP`·`RENAME`·`TRUNCATE TABLE`. 일관된 읽기가 이들과 격리되지 않아 내용이 틀리거나 실패할 수 있다.
- 옵션이 없으면: 기본으로 켜진 `--opt` 안의 `--lock-tables`가 DB별로 테이블 읽기 락을 잡는다. 덤프 동안 쓰기가 막히고(`READ LOCAL`이라 MyISAM의 동시 INSERT만 예외), DB 사이의 일관성도 보장되지 않는다.

### 5. 아카이브의 exit code 계약

- 성공했을 때**만** 0을 돌려준다. 0이면 서버는 그 WAL 세그먼트를 지우거나 재활용한다. 0이 아니면 성공할 때까지 다시 시도한다.
- 이미 있는 파일은 덮어쓰지 않는다(다른 내용이면 0이 아닌 값).
- 거짓 0이면: 서버는 세그먼트를 지웠고 아카이브에는 없다. 평소에는 아무 증상이 없다. **복원하는 날** 재생이 그 번호에서 끊겨 목표 시점까지 못 간다.
- 그래서 `pg_stat_archiver`의 실패 카운터와 아카이브 파일 번호의 연속성을 평소에 감시하고, 주기적 시험 복원으로 드러낸다.

### 6. DROP 직전으로

```ini
restore_command = 'cp /mnt/archive/%f %p'
recovery_target_xid = '1525'
recovery_target_inclusive = off      # 1525를 포함하지 않는다 = 직전에서 멈춤
recovery_target_action = pause       # 기본값. 확인 후 pg_wal_replay_resume()
```

- 데이터 디렉터리에 베이스 백업을 풀고 `recovery.signal`을 만든 뒤 시작한다.
- `recovery_target_lsn = '0/9B698090'` + `inclusive = off`도 같은 효과를 노릴 수 있다. 목표는 하나만 지정할 수 있다.
- 시각보다 나은 이유: 같은 밀리초 부근에 다른 세션의 커밋이 섞여 있다. 로컬 재현에서도 DROP 커밋(22:17:58.783) 직전 80ms 안에 다른 트랜잭션의 커밋이 셋(.705·.717·.720) 있었다. xid·LSN은 트랜잭션 하나를 정확히 가리킨다.

### 7. 타임라인과 pause

- 복구가 끝나면 새 타임라인이 생긴다. 타임라인 ID가 WAL 파일 이름의 앞 8자리(16진수)에 들어간다. 예: `00000001…` → `00000002…`. 그래서 새 기록이 옛 기록을 덮지 않고, 옛 타임라인의 다른 시점으로 다시 복구할 수도 있다.
- `recovery_target_action` 기본값 `pause`: 목표에 닿으면 재생을 멈추고 읽기 조회를 받는다(`hot_standby`가 켜져 있을 때). 맞으면 `pg_wal_replay_resume()`으로 복구를 끝내고 운영을 시작한다. 더 나중 시점이 필요하면 서버를 내리고 목표를 더 나중으로 바꿔 재시작해 이어 간다. 더 이른 시점이면 베이스 백업 복원부터 다시 한다(19.5.6).

### 8. 증분 백업의 조건

- 서버: `summarize_wal = on`(기본 off). WAL 요약이 없거나 요약기가 따라오지 못하면 증분 백업이 실패한다.
- 백업: `pg_basebackup --incremental=<이전 백업의 backup_manifest>`. 서버 17 이상.
- 복원: 증분 하나만으로는 못 쓴다. 기대는 **모든 이전 백업**을 따로 풀고 `pg_combinebackup`으로 합성한 뒤, 평소처럼 WAL 재생과 `recovery.signal`이 필요하다.
- 날짜만 보고 지우면: 전체 백업이 사라진 순간 그 뒤 증분 사슬이 전부 복원 불가가 된다. PostgreSQL은 의존 관계를 추적하지 않으니 보존 정책이 사슬 단위로 지켜야 한다.

### 9. GitLab 원인 사슬

1. 백업 cron이 DB 서버가 아닌 앱 서버에서 돌았다.
2. 거기에는 데이터 디렉터리가 없어 패키지가 기본 `pg_dump` 9.2를 골랐다. 서버는 9.6이었다.
3. `pg_dump`는 자기보다 새 메이저 버전 서버를 덤프하지 않는다 → 매번 오류로 끝났다.
4. 실패 알림 메일은 DMARC 설정 문제로 수신 측에서 거절됐다 → 아무도 몰랐다.
5. S3 버킷은 비어 있었다. 결국 6시간 전 수동 LVM 스냅숏으로 복구했고 그 사이 DB 변경을 잃었다.

- 판정 기준: "작업이 돌았다"가 아니라 **"격리된 곳에 복원해서 행 수·합계·스모크 쿼리를 원본과 대조했다"**. 마지막 성공 복원 시각을 지표로 두고, 오래되면 경보한다. 알림 경로 자체도 시험한다.

### 10. MySQL 덤프 + binlog PITR

1. 덤프에 좌표가 있어야 한다: `mysqldump --single-transaction --source-data=2`. 파일 머리의 주석 `SOURCE_LOG_FILE='binlog.000002', SOURCE_LOG_POS=94422530`이 시작점이다.
2. 사고 위치를 찾는다: `SHOW BINLOG EVENTS IN 'binlog.000002' FROM 94422530` 또는 `mysqlbinlog -v`로 `Delete_rows` 이벤트를 찾는다. 그 트랜잭션이 시작되는 위치(로컬 재현에서 `94423109`, 직전 트랜잭션의 `Xid` 끝)가 멈출 곳이다.
3. 덤프를 재적재한다: `mysql app < app.sql`.
4. binlog를 재생한다: `mysqlbinlog --start-position=94422530 --stop-position=94423109 binlog.000002 | mysql app`. 여러 파일에 걸치면 파일을 순서대로 넘긴다.
5. 행 수·합계를 기대값과 대조한다.

- binlog 보존 기간(`binlog_expire_logs_seconds`)이 덤프 주기보다 짧으면 2번의 시작점이 이미 지워져 사슬이 끊긴다.
