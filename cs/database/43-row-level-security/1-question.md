# database/43-row-level-security — 질문

## 질문

1. (왜) 공유 테이블의 테넌트 격리를 `WHERE tenant_id = ?`에만 맡기면 무엇이 문제인가? RLS는 이 조건을 쿼리의 어디에, 사용자 조건보다 먼저인가 나중인가로 끼워 넣는가?
2. (경계) 슈퍼유저, BYPASSRLS 롤, 테이블 소유자, 일반 롤 중 누가 정책을 받는가? RLS를 켜고 정책을 하나도 안 만들면 일반 롤과 소유자에게 각각 몇 행이 보이나?
3. (예측) `CREATE POLICY p ON orders USING (tenant_id = 설정값)` 하나만 있다(`FOR ALL`, WITH CHECK 없음). 테넌트 1 세션이 `tenant_id = 2`로 INSERT하면 어떻게 되나? 쓰기 구멍이 실제로 생기는 정책 모양은?
4. (경계) 테넌트 정책 옆에 "admin이면 통과" 정책을 기본값으로 더했다. 결과가 어떻게 바뀌나? 조건을 좁히려면 무엇으로 만들어야 하나?
5. (예측) 같은 커넥션에서 ① 새 세션 ② `SET LOCAL app.tenant_id='1'` 트랜잭션 ③ 커밋 뒤 순서로 `current_setting('app.tenant_id', true)`는 무엇을 돌려주나? 정책이 `…::bigint` 캐스트를 쓰면 ③에서 무슨 일이 생기나?
6. (장애 진단) A사 화면에 가끔 B사 주문이 보인다. 에러는 없고 재현이 어렵다. 어떤 코드·풀 조합을 의심하고, 무엇으로 막나?
7. (연결) 테이블 직접 조회는 2행인데 같은 테이블 위의 리포트 뷰는 3행을 돌려준다. 왜인가? 두 가지 고치는 법은?
8. (경계) RLS가 걸린 테이블에서 다른 테넌트의 행 존재가 드러나는 경로를 둘 대라. 정책으로 막을 수 없는 이유는?
9. (장애 진단) 새 기능 배포 후 보안 점검에서 `invoices`가 다른 테넌트 데이터를 돌려준다는 신고가 왔다. 정책 목록에는 문제가 없어 보인다. 무엇을 어떤 쿼리로 확인하나?
10. (적용) 원본 노트는 "정책의 `::bigint` 캐스트를 빠뜨리면 인덱스를 못 탈 수 있다"고 적었다. PostgreSQL 17에서 실제로는 어떻게 되고, 정책 술어가 인덱스를 탔는지는 무엇으로 확인하나?
