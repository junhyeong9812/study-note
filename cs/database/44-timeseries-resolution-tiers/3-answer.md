# database/44-timeseries-resolution-tiers — 정답

## 정답

### 1. 원본을 영원히 두면

- 조회: 넓은 창(6개월) 그래프가 약 1,580만 행을 읽어 1000픽셀에 그린다(예시). 대부분은 화면에서 어차피 버려진다.
- 저장: 지우는 작업이 없으면 테이블·디스크가 선형으로 자란다. 결국 디스크 풀이다.
- 계층이 푸는 법
  - 오래된 구간은 굵게 접은 롤업만 남긴다(행 수 감소).
  - 넓은 창 조회는 굵은 계층을 읽는다(읽는 행 감소).
  - 계층마다 보존 기간을 두어 지운다(저장 상한).

### 2. 계층별 행 수 (지표 하나, 예시)

| 계층 | 계산 | 행 수 |
|---|---|---|
| raw 1초·7일 | 7 × 86,400 | 604,800 |
| 1분·90일 | 90 × 1,440 | 129,600 |
| 1시간·2년 | 730 × 24 | 17,520 |

- 6개월 창은 1분 계층의 보존(90일)을 넘는다. **1시간 계층**을 읽는다. 약 4,380행이다(182.5 × 24).

### 3. 다시 접을 때

- 정확(수학적으로): n = Σn, sum = Σsum, min = min(min), max = max(max), avg = Σsum / Σn. 단 `double precision` 합은 합산 순서에 따라 끝자리 오차가 날 수 있다. 정확한 합이 필요하면 `numeric`.
- 불가: 중앙값·p95 같은 분위수, 고유 개수. 원본이나 머지 가능한 스케치가 필요하다.
- 평균의 평균 = (100 + 200) / 2 = **150**.
- 실제 평균 = (10 × 100 + 1000 × 200) / 1010 = **199.0099…**(로컬 재현).
- 평균의 평균은 버킷 크기가 다르면 틀린다.

### 4. BETWEEN vs date_bin

- `BETWEEN`은 양 끝을 포함한다.
  - 00:00 버킷은 00:00:00~01:00:00 → **3601**.
  - 01:00 버킷도 01:00:00~02:00:00 → **3601**.
  - 02:00 버킷은 데이터가 02:59:59에서 끝나서 **3600**.
  - 합은 **10,802**다. 원본보다 2 많고, 에러는 없다(로컬 재현).
- `date_bin('1 hour', ts, origin)`은 행마다 버킷 하나를 준다. 3600 × 3 = **10,800**(로컬 재현).

### 5. 그래프가 두 배

- 확인: 롤업 테이블에서 같은 `(bucket, metric)` 행이 여러 개인지 본다.

```sql
SELECT bucket, metric, count(*) FROM m_1h GROUP BY 1, 2 HAVING count(*) > 1;
```

- 원인: 롤업이 INSERT만 해서 재시도·스케줄 겹침·수동 백필이 같은 구간을 다시 넣었다(로컬 재현: n 합 21,600 = 2배).
- 고치기: `(bucket, metric)`에 PK를 걸고 원본에서 버킷 전체를 다시 계산해 **덮어쓴다.**
  - PostgreSQL: `ON CONFLICT … DO UPDATE SET n = EXCLUDED.n …`
  - MySQL: `ON DUPLICATE KEY UPDATE n = x.n …`
  - 두 번 돌려도 10,800이다(로컬 재현).
- `n = n + EXCLUDED.n`은 다시 돌 때마다 더한다. 멱등이 아니다. 재실행하면 또 두 배가 된다.

### 6. 늦게 온 행

- 00:00 버킷은 롤업 3600, 원본 3601로 **조용히 어긋난다.** 에러는 없다(로컬 재현).
- 흡수: 롤업 잡이 매번 "최근 N개 버킷"을 원본에서 다시 계산해 덮어쓴다. N × 버킷 폭 ≥ 허용 지연 + 잡 실행 간격. 실행 간격을 빼면 놓친다: 1시간 버킷·허용 지연 1시간·매시 05분 실행에서 N = 1이면 01:59에 온 00:59:30 행은 01:05 잡보다 늦고, 02:05 잡은 [01:00, 02:00)만 본다. 로컬 재현에서 재계산 뒤 불일치 0이었다.
- 원본 보존 기간 > 허용 지연 + 재계산 창이어야 한다. 원본이 먼저 지워지면 재계산할 재료가 없다.
- 그보다 늦은 행은 버리되 버린 수를 센다(ops-patterns/17 lateDrops).

### 7. DELETE 보존

- 파일 크기는 거의 줄지 않는다.
  - DELETE는 dead tuple을 남긴다. 로컬 재현: 21,600행 DELETE 뒤 `n_dead_tup = 21600`, 크기 2208 kB 그대로.
  - 표준 VACUUM은 그 자리를 재사용 가능하게 표시할 뿐이다. 테이블 끝의 빈 페이지 외에는 OS에 돌려주지 않는다(PostgreSQL 17 24.1).
- 파티션 DROP은 파일째 지운다. 로컬 재현: DETACH 3.4ms + DROP 4.0ms. dead tuple도 VACUUM 부담도 없다.
- 구조는 **링 버퍼**다. 새 칸(미래 파티션)을 열고 가장 오래된 칸을 버린다. RRDtool의 round robin archive와 같은 발상이다.

### 8. 자정마다 실패

- 에러
  - PostgreSQL 17: `ERROR: no partition of relation "raw_p" found for row` + `DETAIL: Partition key of the failing row contains (ts) = (…)`(로컬 재현).
  - MySQL 8.4: `ERROR 1526 (HY000): Table has no partition for value from column_list`(로컬 재현).
- 원인: 다음 날 파티션을 만드는 잡이 멈췄다.
- 대처: 며칠 앞까지 미리 만든다. "미래 파티션 수 < 2"에 경보를 둔다.
- DEFAULT 파티션은 쓰기 실패를 막을 뿐 해결이 아니다. 행이 DEFAULT로 들어간 뒤 그 범위 파티션을 만들면 `updated partition constraint for default partition … would be violated by some row`로 거부된다(로컬 재현). 행을 옮기는 작업이 따로 필요하다.

### 9. 디스크 풀

- 빠진 것: 보존(삭제) 작업. 또는 작업은 있는데 멈췄고 감시가 없었다. 기록·조회는 정상이라 신호가 없다.
- 긴급
  - 가장 오래된 원본 파티션부터 `DETACH` → `DROP`한다.
  - DELETE + `VACUUM FULL`은 ACCESS EXCLUSIVE 락이라 운영 중 테이블이 멈춘다. 게다가 새 사본을 쓰는 동안 테이블 크기만큼 디스크를 더 쓴다(24.1). 디스크 풀 상황에는 맞지 않는다.
- 재발 방지 경보
  - `now() - min(ts)` > 보존 + 여유
  - 디스크 여유율
  - 미래 파티션 수
  - 롤업·원본 건수 불일치
