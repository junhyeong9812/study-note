# database/52-offline-concurrency-patterns — 질문

## 질문

1. (왜) 모든 DB 트랜잭션이 ACID를 지켰는데도 편집 화면에서 lost update가 나는 이유를 시간축 그림으로 설명하라. DB 트랜잭션을 편집 내내 열어 두면 안 되는 이유는?
2. (예측) `doc(id=1, version=0)`을 A와 B가 읽었다. B가 먼저 `UPDATE … SET version = version + 1 WHERE id = 1 AND version = 0`을 실행하고, 이어서 A가 같은 문장을 실행한다. 각각의 결과(영향 행 수)와 최종 상태는? 검사를 SELECT와 UPDATE 두 문장으로 나누면 무엇이 달라지나?
3. (장애 진단) 엔티티에 `@Version`을 달았는데도 lost update가 난다. 저장 코드는 `em.find`로 엔티티를 읽고 폼 값을 복사해 커밋한다. 왜 충돌이 안 잡히나? 어떻게 고치나?
4. (설계) 비관적 오프라인 락을 PostgreSQL 테이블로 설계하라. 획득·해제 SQL과, 두 사람이 동시에 획득할 때 한 명만 이기는 근거는?
5. (장애 진단) "다른 사용자가 편집 중" 표시가 퇴근한 직원 이름으로 다음 날까지 남는다. 원인과 대처는? 락이 만료되어 남에게 넘어간 뒤 원래 주인이 저장을 누르면 어떻게 해야 하나?
6. (예측) 주문 불변식이 "줄 수량 합계 ≤ 10"이고, 줄마다 버전 컬럼이 있다. 합계 8(4+4)인 주문에서 A는 1번 줄을, B는 2번 줄을 각각 6으로 바꾼다. 결과는? Coarse-Grained Lock으로 어떻게 막고, JPA에서는 무엇을 쓰나? JPA가 자식만 바뀌었을 때 부모 버전을 올리지 않는 이유는?
7. (경계) Implicit Lock은 무엇을 막으려는 패턴인가? JPA·저장소·HTTP API에서 각각 어떤 형태로 구현하나?
8. (연결) 낙관적 오프라인 락을 HTTP 계약으로 옮기면 어떤 헤더와 상태 코드가 쓰이나? `If-Match`가 없는 요청을 거부하려면?
9. (경계) DB 교착(40P01·1213)은 자동 재시도해도 되는데, 낙관적 오프라인 락 충돌은 왜 자동 재시도하면 안 되나? PostgreSQL 세션 수준 advisory lock을 오프라인 락으로 쓰면 커넥션 풀에서 무슨 일이 생기나?
