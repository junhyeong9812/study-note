# database/13-transactions-acid — 정답

## 정답

### 1. 이체 사이의 세 문제

| 문제 | 막는 글자 |
|---|---|
| 출금 뒤 서버가 죽어 입금이 안 됨 | A(원자성) + D(지속성: 재시작 때 로그로 복구·폐기) |
| 두 번째 문장이 실패해 반쪽 상태 | A(원자성) — 되돌릴 수 있음 |
| 동시 요청이 중간 상태를 읽음, 또는 (잔액을 읽어 계산값으로 덮어쓰는 코드라면) 한쪽 출금이 사라짐 | I(격리) |

- C는 여기서 "잔액 합이 보존된다"는 규칙인데, 그 규칙을 지키는 코드는 애플리케이션이 쓰고 A·I가 그것을 받쳐 준다.

### 2. 원자성의 뜻

- 동시성과 **관련이 없다.** "트랜잭션이 도중에 실패하면 이미 한 변경을 전부 되돌릴 수 있다"는 뜻이다.
- DDIA 1판 7장: abortability(중단 가능성)가 더 나은 이름이었을 것이라 쓴다.
- 구현(CMU L16)
  - 로그: 이전 값을 undo 기록으로 남겨 중단 시 되돌린다. 거의 모든 현대 시스템.
  - 섀도 페이징: 복사본 페이지에 쓰고 커밋 때 바꿔 끼운다. 드물다.

### 3. CHECK 위반 뒤 COMMIT (로컬 재현)

```text
  PostgreSQL 17.11                                   MySQL 8.4.10 InnoDB
  두 번째 UPDATE: ERROR ... violates check constraint  ERROR 3819 ... Check constraint ... violated
  다음 SELECT:    ERROR: current transaction is        정상 실행 (트랜잭션은 열려 있음)
                  aborted ... (25P02)
  COMMIT:         ROLLBACK 으로 처리                   첫 UPDATE가 커밋됨
  최종:           (1,100), (2,0)                      (1,100), (2,50)
```

- PostgreSQL은 오류 난 트랜잭션을 통째로 실패 상태로 만든다.
- InnoDB는 실패한 **문장만** 되돌리고, 트랜잭션을 끝낼지는 애플리케이션에 맡긴다. 오류 뒤 `ROLLBACK` 대신 `COMMIT`하면 반쪽이 커밋된다(커밋 없이 세션이 끝나면 롤백된다).

### 4. 일관성의 범위

- 맞는 부분: DB는 **선언된** 제약(NOT NULL, UNIQUE, FK, CHECK, 트리거)을 모든 트랜잭션에 강제한다.
- 틀린 부분: "당직자 1명 이상", "하루 한도" 같은 규칙은 선언하지 않으면 DB가 모른다.
- CMU L16의 두 종류
  - 데이터베이스 일관성: 무결성 제약을 지킨다 → DB.
  - 트랜잭션 일관성: 시작 때 일관적이면 끝날 때도 일관적 → **애플리케이션 책임**.
- DDIA 1판은 그래서 C가 애플리케이션의 성질이며 ACID에 속하지 않는다고까지 쓴다(2판은 "DB 혼자의 성질이 아니다"로 완화).

### 5. 충돌 그래프

```text
  R1(A) R2(A) W1(A) W2(A)
    R1(A) → W2(A) : T1 → T2
    R2(A) → W1(A) : T2 → T1
    W1(A) → W2(A) : T1 → T2
  T1 ⇄ T2  사이클 → 충돌 직렬화 불가능
```

- 현실의 버그: **갱신 손실**. 재고 10을 둘 다 읽고 각자 9로 써서, 두 번 팔았는데 재고는 1만 줄었다.
- `R1(A) W1(A) R2(A) W2(A)`: 간선은 T1 → T2뿐, 사이클 없음 → T1 다음 T2의 직렬 실행과 같다.

### 6. 지속성

- 커밋 기록이 들어간 **WAL(redo 로그)이 디스크에 fsync된 상태**여야 한다. 데이터 페이지는 나중에 써도 재시작 때 로그로 재생한다.
- PostgreSQL 17
  - `synchronous_commit` 기본 `on`. `off`면 최근 트랜잭션 일부를 잃을 수 있다(손상은 아님). 위험 구간 최대 `wal_writer_delay`의 3배.
  - `fsync` 기본 `on`. `off`는 OS·하드웨어 장애 때 임의의 손상까지 가능하다.
- MySQL 8.4
  - `innodb_flush_log_at_trx_commit` 기본 1. 0·2면 대략 1초에 한 번 플러시 → 충돌 시 약 1초분 트랜잭션 유실 가능(0은 mysqld 크래시에도, 2는 OS 크래시·정전 때만). 1초 주기는 보장되지 않고, `innodb_flush_log_at_timeout`(기본 1초)을 늘리면 그만큼 더 잃을 수 있다(17.14).
  - `sync_binlog` 기본 1. 0이면 바이너리 로그 동기화를 OS에 맡겨, 커밋됐지만 binlog에 없는 트랜잭션이 생길 수 있다.

### 7. 롤백됐는데 메일 발송

- 원인: 트랜잭션 안에서 메일을 보냈다. DB는 자기 변경만 되돌린다. 바깥으로 나간 효과는 되돌릴 수 없다.
- 고치는 법
  1. `@TransactionalEventListener`(기본 `AFTER_COMMIT`)로 커밋 뒤에만 발송한다.
  2. 같은 트랜잭션에서 아웃박스 테이블에 "보낼 메일" 행을 쓰고, 별도 발송기가 커밋된 행만 읽어 보낸다.
- 덤: 트랜잭션 안 외부 호출은 커넥션과 락을 그 시간만큼 쥐어 풀 고갈로 번진다.

### 8. 첫 UPDATE만 반영

- 원인 1: 커넥션이 **자동 커밋 모드**였다. `setAutoCommit(false)`를 안 했거나, `@Transactional`이 적용되지 않았다(같은 클래스 안 자기 호출 등). 문장마다 이미 커밋됐다.
- 원인 2: MySQL InnoDB에서 예외를 잡고 `ROLLBACK` 없이 `COMMIT`했다. 실패한 문장만 되돌려진 상태로 커밋됐다.
- JDBC `Connection` 기본값: **자동 커밋 켜짐**(`java.sql.Connection` 문서). 자동 커밋 모드에서 `rollback()`을 부르면 `SQLException`이 난다.

### 9. `25P02`

- SQLSTATE `25P02`(`in_failed_sql_transaction`).
- 원인: 같은 트랜잭션의 앞선 문장이 실패했다. PostgreSQL은 그 트랜잭션을 실패 상태로 두고 `ROLLBACK` 전까지 모든 명령을 거부한다. 애플리케이션이 첫 예외를 삼키고 계속 쿼리했다.
- 대처
  - 첫 예외에서 트랜잭션을 롤백하고, 필요하면 처음부터 재시도한다.
  - 실패를 예상하는 문장은 `SAVEPOINT` → 실패 시 `ROLLBACK TO SAVEPOINT`로 감싼다.
  - 가능하면 `INSERT … ON CONFLICT DO NOTHING`처럼 실패 자체를 없앤다.
