# database/33-partitioning-and-sharding — 정답

## 정답

### 1. 분할이 푸는 것

- 복제는 모든 노드가 전체 데이터를 갖고 모든 쓰기를 재생한다. 샤딩은 노드마다 **일부 키만** 맡겨 쓰기 처리량과 저장 용량을 노드 수에 가깝게 늘린다(부하가 고르게 나뉠 때. 핫 키가 있으면 못 미친다). 한 인스턴스 안 분할은 노드를 늘리지 않는다.
- 먼저 한 인스턴스 안 분할을 보는 이유
  - 조인·트랜잭션·유니크(파티션 키 포함 시)가 DB 안에서 그대로 된다. 샤딩은 이것들을 앱·미들웨어로 넘긴다.
  - 가장 흔한 요구(오래된 데이터 삭제, 최근 데이터만 조회)는 `DROP/DETACH PARTITION`과 가지치기로 풀린다. 대량 `DELETE`보다 훨씬 빠르고 `VACUUM` 부담이 없다(PostgreSQL 5.12.1).
  - 샤딩은 되돌리기 어렵다(원본 확장 사다리의 마지막 단계).

### 2. 범위 vs 해시

| | 키 범위 | 해시 |
|---|---|---|
| 범위 조회 | 파티션 몇 개로 끝난다 | 보통 모든 파티션을 훑는다(MySQL 8.4는 파티션 수보다 짧은 정수 범위만 예외적으로 가지치기) |
| 쓰기 분포 | 단조 증가 키면 최신 파티션에 몰린다 | 키가 다양하면 고르게 |
| 핫 키 | 못 푼다 | 못 푼다 |

- 해시는 **서로 다른 키들**을 고르게 흩을 뿐이다. 한 키에 요청이 몰리면 그 키가 사는 파티션 하나가 뜨겁다. 핫 키는 키 뒤에 접미사(예: 0~9)를 붙여 여러 파티션에 쪼개 쓰고, 읽을 때 10곳을 모은다.

### 3. EXPLAIN 예측

- (a) 가지치기: `Aggregate → Seq Scan on ev_2026_09`. 8월 파티션은 계획에서 빠진다.
- (b) 파티션 키가 조건에 없다: `Append` 아래 파티션마다 `Bitmap Heap Scan` + `Bitmap Index Scan on ev_2026_08_user_id_idx`, `… ev_2026_09_user_id_idx`. 인덱스는 파티션별(로컬)이라 모든 파티션의 인덱스를 각각 탄다.

### 4. PK에 파티션 키가 없으면

- PostgreSQL 17: `ERROR: unique constraint on partitioned table must include all partitioning columns`, `DETAIL: PRIMARY KEY constraint on table "ev" lacks column "created" which is part of the partition key.`
- 이유: 유니크 인덱스는 파티션마다 따로 있다. 각 인덱스는 자기 파티션 안의 유일성만 안다. 파티션 키가 제약에 들어 있어야 "같은 값은 같은 파티션에만 있을 수 있다"가 보장되어, 로컬 인덱스만으로 전체 유일성이 성립한다.
- 해결: `PRIMARY KEY (id, created)`.
- MySQL 8.4: 테이블의 모든 유니크 키(PK 포함)가 분할 식의 모든 컬럼을 포함해야 한다. `ERROR 1503 (HY000): A UNIQUE INDEX must include all columns in the table's partitioning function`.

### 5. 로컬 vs 글로벌 인덱스

| | 로컬(문서 기준) | 글로벌(용어 기준) |
|---|---|---|
| 읽기 | 인덱스 컬럼 조회는 모든 파티션에 질의(scatter-gather) | 해당 값의 인덱스 조각 하나만 |
| 쓰기 | 자기 파티션만 | 행이 있는 파티션 + 인덱스 조각이 있는 다른 파티션 → 분산 트랜잭션 또는 비동기 갱신(잠깐 틀림) |

- 이메일 중복 금지: 각 샤드의 유니크 인덱스로는 샤드 안에서만 막힌다. 방법
  - `email`을 키로 하는 조회 테이블(`email → user_id`)을 둔다. 가입 시 거기에 먼저 유니크 삽입(수동 글로벌 인덱스). 사용자 행 삽입과의 원자성은 같은 샤드에 두거나, 실패 시 되돌리는 보상으로 맞춘다.
  - 또는 이메일 자체를 샤드 키로 쓰는 전용 테이블을 둔다.

### 6. 이동량 계산

- `hash % 4 → % 5`: 키가 제자리에 남을 확률 ≈ 1/5 → 약 **80%** 이동. 로컬 시뮬레이션 79.7%.
- 일관 해싱(4 → 5 노드, 시뮬레이션)
  - vnode 1개: 54.5% 이동, 5노드 부하 `[20215, 3851, 8062, 13384, 54488]`. 새 노드가 긴 구간을 우연히 차지해 이동도 많고 부하도 치우쳤다.
  - vnode 100개: 19.7% 이동(이상적 1/5 = 20%), 부하 `[19879, 19325, 22202, 18938, 19656]`.
  - 두 경우 모두 "새 노드가 아닌 노드로 옮겨진 키"는 0이었다. 옮겨지는 키는 전부 새 노드로 간다.

### 7. 재조정 전략 비교

| 전략 | 키 → 파티션 대응 | 이동 단위 |
|---|---|---|
| `hash % N` | N이 바뀌면 거의 전부 바뀐다 | 키 하나하나(대부분) |
| 고정 파티션 수(사전 분할) | 파티션 수를 바꾸지 않는 한 안 바뀐다 | 파티션 통째 |
| 동적 분할 | 파티션이 커지면 둘로 쪼개진다 | 쪼갠 파티션 통째 |
| 일관 해싱 + vnode | 새 노드가 끼어든 구간만 바뀐다 | 구간(약 1/n) |

- 사전 분할을 권하는 이유: 파티션 수를 바꾸지 않는 한 키 → 파티션이 고정이라 앱·라우터의 계산이 바뀌지 않는다. 노드 추가는 "파티션 몇 개를 옮기고 파티션 → 노드 맵만 고친다". 이동·검증 단위가 명확하다. 대가는 처음에 파티션 수를 넉넉히 정해야 한다는 것(너무 많으면 관리 비용, 너무 적으면 나중에 못 나눔).

### 8. 샤드를 늘렸더니 느려짐

- 확인
  - 그 화면의 쿼리가 샤드 키를 조건에 갖는지. 없으면 샤드 수만큼 하위 쿼리로 퍼진다.
  - 라우터·코디네이터의 하위 쿼리 수, 샤드별 지연 분포. scatter-gather의 지연은 **가장 느린 샤드**가 정한다. 샤드가 늘면 그중 하나가 느릴 확률이 커진다(꼬리 지연).
  - 샤드별 커넥션 수(쿼리 하나가 샤드 수만큼 커넥션을 쓴다).
- 고침: 조회 테이블로 샤드를 먼저 찾기, co-location·참조 테이블 복제로 조인 지역화, 전역 집계·검색은 분석 DB·검색 엔진으로, 깊은 페이지네이션은 커서로.

### 9. 이중 쓰기 경쟁

```text
  시간 →
  백필:  R 읽음(v1) ─────────────────────── 새 샤드에 v1 씀
  앱:          원본 v2 씀 → 새 샤드 v2 씀
  결과:  원본 v2 / 새 샤드 v1
```

- 행 수는 같으니 행 수 비교로는 안 보인다. 에러도 없다.
- 재발 방지
  1. 앱 이중 쓰기 대신 원본의 변경 로그(binlog·논리 복제·CDC)를 **한 순서로** 새 샤드에 적용한다. 일관된 스냅숏과 그 시점의 로그 위치를 짝지어, 로그를 그 위치부터 적용한다.
  2. 이중 쓰기를 해야 한다면 행 버전을 두고 "내 버전이 더 클 때만 쓴다"는 조건부 쓰기.
  3. 전환 전 행 단위 체크섬(또는 해시 합) 대조를 필수 관문으로 둔다. 전환 직전에는 짧게 쓰기를 멈추고 로그 끝까지 적용한 뒤 샤드 맵을 바꾼다.

### 10. 매달 1일 INSERT 실패

- PostgreSQL: `ERROR: no partition of relation "ev" found for row` / `DETAIL: Partition key of the failing row contains (created) = (…)`.
- MySQL: `ERROR 1526 (HY000): Table has no partition for value 2027` 형태(값 자리에 분할 식의 결과).
- 원인: 다음 달 파티션을 미리 만들지 않았다. 해결: 몇 달 앞서 만드는 스케줄 작업 + "남은 미래 파티션 수" 경보.
- `DEFAULT` 파티션의 대가: 실패는 막지만 행이 거기 쌓인다. 나중에 그 달의 파티션을 붙일 때 PostgreSQL은 `DEFAULT` 파티션을 스캔해 옮겨야 할 행이 없는지 검사하고, 그동안 `DEFAULT`에 `ACCESS EXCLUSIVE` 락을 쥔다. 행이 있으면 붙이기가 실패한다. `DEFAULT`는 "안전망 + 경보"로만 쓴다.
