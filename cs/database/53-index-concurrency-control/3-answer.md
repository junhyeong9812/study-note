# database/53-index-concurrency-control — 정답

## 정답

### 1. 락과 래치

| | 락 | 래치 |
|---|---|---|
| 보호 대상 | DB 내용(행·테이블) — 논리 | 내부 자료구조(페이지·버킷) — 물리 |
| 보유 기간 | 트랜잭션 동안(보통 끝까지) | 연산 하나, 아주 짧게 |
| 교착 | DB가 탐지하고 희생자를 롤백 | 탐지 없음 — 잡는 순서 규율로 예방 |

- 격리 수준은 트랜잭션 사이의 **논리적** 정합성을 다룬다. 스레드 A가 페이지를 읽는 순간 스레드 B가 같은 페이지를 분할하면, 격리 수준과 무관하게 A는 **반쯤 바뀐 페이지**를 볼 수 있다. 이것은 물리적 정합성 문제라 래치가 필요하다(CMU L10).

### 2. 크래빙 삽입

```text
  1) 루트에 쓰기 래치
  2) 내부 노드에 쓰기 래치 → 내부 노드는 꽉 차지 않음 = 안전 → 루트 래치를 놓는다
  3) 리프에 쓰기 래치 → 리프는 꽉 참 = 안전하지 않음 → 내부 노드 래치를 계속 쥔다
     (리프 분할이 내부 노드에 새 포인터를 넣어야 하기 때문)
  4) 분할·삽입을 마치고 모든 래치를 놓는다
```

- 안전한 노드 = 이번 연산으로 분할·병합·재분배가 일어나지 않는 노드.
  - 삽입: 꽉 차지 않은 노드.
  - 삭제: 절반보다 많이 찬 노드(하나 빠져도 최소 점유를 지킨다).
- 조회는 안전 조건이 필요 없다. 자식을 잡으면 바로 부모를 놓는다(CMU L10).

### 3. 낙관적 크래빙

- 병목: 기본 프로토콜은 모든 삽입·삭제가 **루트에 쓰기 래치**를 잡는다. 트리 전체가 루트에서 직렬화된다.
- 가정: 분할·병합은 드물다. 그래서 읽기 래치로 크래빙해 리프까지 내려가고, **리프에만** 쓰기 래치를 잡는다.
- 가정이 틀리면(리프가 안전하지 않으면): 쥔 래치를 모두 놓고 기본 프로토콜(쓰기 래치 크래빙)로 처음부터 다시 한다(CMU L10). 분할이 잦으면 재시도 비용이 붙는다.

### 4. 리프 스캔 교착

```text
  스레드 1: 리프 L2 쓰기 래치 쥠 → 왼쪽 L1이 필요
  스레드 2: 리프 L1 읽기 래치 쥠 → 오른쪽 L2로 이동하려 함
  서로 반대 방향 → 원형 대기
```

- 형제 사이의 이동은 "위→아래" 전순서에 들어가지 않는다. 그래서 원형 대기가 생길 수 있다.
- 래치에는 교착 탐지가 없으므로 **no-wait**로 짠다. 형제 래치를 즉시 못 얻으면 기다리지 않고, 쥔 래치를 모두 놓고 연산을 다시 시작한다(CMU L10).

### 5. B-link 트리의 오른쪽 이동

```text
  L:  [10 20 30 | high=40] ──right──> L': [40 44 50 | high=60]

  A: L 도착 → 찾는 키 44 > L의 high key 40
     → "그 사이 분할됐다" → right-link를 따라 L'로 이동 → 44 발견
```

- 두 가지 추가 정보: **high key**(이 노드에 올 수 있는 키의 상한)와 **right-link**(오른쪽 형제 포인터).
- 분할은 "형제에 절반을 옮기고 right-link를 잇는다" → "부모에 포인터를 넣는다"의 두 단계다. 그 사이에도 탐색은 오른쪽 이동으로 올바른 노드를 찾는다. 그래서 탐색이 부모 래치를 쥔 채 내려갈 필요가 없다(PostgreSQL `nbtree/README`).

### 6. PostgreSQL의 변경점

- 공유 버퍼를 여러 백엔드가 같이 쓰므로, 페이지를 읽는 동안에는 짧은 **페이지 단위 읽기 락**을 잡는다. L&Y 논문은 메모리 사본이 공유되지 않는다고 가정해 읽기 락이 필요 없다고 봤다.
- 역방향 스캔을 위해 **left-link**를 추가했다. 분할 때 옛 오른쪽 형제의 left-link도 갱신한다.
- 루트 분할: 루트를 보통 페이지처럼 나누고 새 루트를 만든 뒤 메타 페이지의 루트 포인터를 바꾼다.
- 분할이 중간에 끊기면 `INCOMPLETE_SPLIT` 표시가 남고 나중 연산이 마무리한다.
- 방향: 다음 페이지를 먼저 잡고 현재를 놓는 것은 **오른쪽·위로** 갈 때만 안전하다. **왼쪽·아래로** 그렇게 하면 교착 가능성이 생긴다(README). 그래서 대부분은 현재 페이지를 먼저 놓고 다음 페이지를 잡는다.

### 7. InnoDB `index->lock`

- 모드: S, SX, X. 호환성(`sync0rw.cc`): S–S 공존, S–SX 공존, SX–SX 배타, X는 모두와 배타.
- `btr0cur.cc`(mysql-8.4.10) 기준
  - 일반 검색: `index->lock` S.
  - 낙관적 삽입(`BTR_MODIFY_LEAF`): `index->lock` S + 리프 페이지 쓰기 래치. 리프 안에서 끝난다.
  - 분할을 동반한 삽입(`BTR_MODIFY_TREE`, 비관적): `index->lock` SX + 바뀌는 경로 페이지들의 X 래치. 공간 인덱스, history list가 길고 읽기 I/O가 밀린 때의 삭제 의도(퍼지) 연산은 X.
- 의미: 한 스레드가 분할(SX) 중이어도 다른 스레드의 검색(S)은 `index->lock`에서 막히지 않는다. 분할이 X 래치를 쥔 페이지를 지나야 하는 검색만 그 페이지에서 기다린다. 대신 SX끼리는 배타라 **한 인덱스의 트리 구조 변경은 한 번에 하나**다.

### 8. 핫 리프 진단과 대처

- 볼 것: `pg_stat_activity`의 `wait_event_type`·`wait_event`를 짧은 간격으로 여러 번 표본 추출한다. `LWLock` / `BufferContent`가 지배적이면 페이지 래치 경합이다. 로컬 재현(예시, PostgreSQL 17.11)에서 bigserial PK는 20회 표본에서 `BufferContent` 36건, uuid PK는 0건이었다.
- 커밋의 WAL 쓰기·fsync 병목은 `LWLock` / `WALWrite`(WAL 버퍼를 디스크에 쓰는 락 대기 — 쥔 세션이 쓰기·fsync 중), `IO` / `WalSync`(fsync 자체 대기)로 보인다. `WALWrite`만으로 fsync라고 단정하지 말고 `WalSync`·`WalWrite`(IO)와 함께 본다. 로컬 재현에서도 `synchronous_commit`을 끄기 전에는 이것이 지배적이었다. 이 경우 래치 분산은 소용없고 커밋 묶기(배치, group commit)가 답이다.
- 대처와 대가
  1. 해시 파티셔닝: 파티션마다 인덱스가 따로라 오른쪽 리프가 여러 장이 된다. 대가: 파티션 관리, 파티션 키 없는 조회는 모든 파티션을 본다.
  2. 키 분산(`(shard_id, seq)` 또는 랜덤 키): 리프가 흩어진다. 대가: 순차 범위 조회가 흩어지고, 랜덤 키는 인덱스가 커지고 분할·버퍼 적중률이 나빠진다(로컬 재현에서 uuid PK 인덱스가 행당 약 1.9배).
  3. 배치 삽입(자동 커밋을 끄고 한 트랜잭션으로): 왕복·커밋 횟수가 준다. 인덱스 리프 래치는 행마다 잡으므로 그대로다. 대가: 요청 지연이 늘고, 실패 시 묶음 단위로 재시도한다.

### 9. 조용한 멈춤

- 락이 아니라 **래치 경합**을 의심한다. 래치 대기는 락 관리자에 기록되지 않는다(`pg_locks`, `performance_schema.data_locks`에 안 나온다). 래치에는 교착 탐지도 없어 교착 오류가 나지 않는다.
- 볼 곳
  - PostgreSQL: `pg_stat_activity`의 `wait_event_type = 'LWLock'`와 `wait_event`(예: `BufferContent`, `BufferMapping`, `WALWrite`).
  - MySQL: `SHOW ENGINE INNODB STATUS`의 SEMAPHORES 절, performance_schema의 `wait/synch/sxlock/innodb/*` 계측기(기본 꺼짐 — 켜야 모인다).
- 대기가 짧게 풀리기를 반복하면 경합이다. 정말 풀리지 않는 래치 대기라면 DB 버그 영역이므로 스택과 버전을 모아 제보한다.
