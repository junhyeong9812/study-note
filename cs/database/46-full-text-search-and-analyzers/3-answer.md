# database/46-full-text-search-and-analyzers — 정답

## 정답

### 1. LIKE와 역색인

- B-tree는 키를 **앞에서부터** 정렬해 둔다. 앞이 `%`면 어디서 시작할지 몰라 전부 읽는다.
- 역색인은 문서를 미리 용어로 잘라 "용어 → 문서 목록"을 만든다. 질의 용어의 목록만 읽고 교집합을 낸다.
- LIKE 대비 이점
  - 순위: BM25 등으로 관련 있는 문서를 먼저 낸다.
  - 정규화: 어간 추출·소문자화·동의어로 "running"과 "run", "냉장고를"과 "냉장고"를 같게 본다.
  - (그 밖에 구·근접 검색)

### 2. 분석기 세 단계

```text
  원문 → [문자 필터: HTML 제거 등] → [토크나이저: 어디서 자르나] → [토큰 필터: 소문자·불용어·어간·동의어] → 용어
```

- `to_tsvector('english', 'The runners were running quickly')` → `'quick':5 'run':4 'runner':2`
  - "The", "were"는 불용어라 빠진다. 위치 번호(1·3)는 비어도 남는다.
  - "running" → "run", "quickly" → "quick"(어간 추출). "runners" → "runner".

### 3. MySQL 공백 파서 vs ngram 파서

- 공백 파서: **0건**.
  - "삼성전자"는 한 토큰이라 "삼성"과 다르다.
  - "삼성"(두 글자)은 `innodb_ft_min_token_size` 기본 3보다 짧아 색인되지 않았다.
- ngram 파서: **2건**(두 문서 모두).
  - "삼성전자"가 "삼성·성전·전자"로 잘려 "삼성" bigram이 있다.
  - ngram 파서는 최소·최대 토큰 길이 옵션을 무시한다.

### 4. 한국어 토큰화의 실패와 decompound_mode

| 방식 | 실패 |
|---|---|
| 공백 단위 | 조사가 붙은 어절("주가가")·붙여 쓴 복합어("삼성전자")가 한 토큰이라 부분 검색이 누락된다 |
| n-gram | 단어 경계를 몰라 과다 매칭한다("성전" → "삼성전자"). 색인이 커진다 |
| 형태소 | 사전에 없는 신조어·상품명을 잘못 자를 수 있다(미등록어 후보는 만들지만 원하는 분할이 아닐 수 있다). 사전 관리와 재색인 비용이 든다 |

- `none`: 복합어를 분해하지 않는다.
- `discard`(기본): 분해하고 원형을 버린다. `가곡역 → 가곡, 역`
- `mixed`: 분해하고 원형도 남긴다. `가곡역 → 가곡역, 가곡, 역`

### 5. BM25 계산

- idf = ln(1 + (N − n + 0.5)/(n + 0.5))
  - A(n = 10): ln(1 + 990.5/10.5) = ln 95.33 ≈ **4.56**
  - B(n = 500): ln(1 + 500.5/500.5) = ln 2 ≈ **0.69**
- dl = avgdl이면 tf = f / (f + k1) = f / (f + 1.2)
  - f = 1 → **0.45**, f = 10 → **0.89**
- 10번 나와도 두 배가 안 된다(포화). 드문 용어 A 하나가 흔한 용어 B보다 훨씬 크게 기여한다.

### 6. ts_rank와 BM25

- PostgreSQL 17 문서: `ts_rank`는 일치 lexeme의 빈도로 매기고, 두 순위 함수 모두 **전역 정보를 쓰지 않는다**.
- 그래서 idf가 없다. "삼성 이어폰"처럼 흔한 단어("삼성")와 드문 단어("이어폰")를 함께 찾을 때, 흔한 단어를 여러 번 담은 문서가 드문 단어를 담은 문서를 이길 수 있다.
- 길이 정규화는 `normalization` 비트마스크로 고른다(기본 0 = 길이 무시).
- 관련도가 핵심이면 BM25를 쓰는 검색 엔진이나 별도 순위 로직을 둔다.

### 7. 배포 뒤 0건

- 의심: 색인 분석기와 검색 분석기가 다르다. 에러 없이 용어만 안 맞는다.
- PostgreSQL
  - 인덱스 정의의 설정 이름과 쿼리의 설정 이름을 비교한다. `to_tsvector('english', …)`로 만들었는데 `to_tsquery('simple', …)`나 `default_text_search_config`로 질의하고 있지 않나.
  - 직접 비교: `SELECT to_tsvector('english','running') @@ to_tsquery('simple','running')` → `f`.
  - 식 인덱스라면 `EXPLAIN`에서 인덱스를 타는지도 본다.
- Elasticsearch
  - 매핑의 `analyzer`·`search_analyzer`를 확인한다.
  - `_analyze` API로 같은 문자열을 색인 분석기와 검색 분석기에 넣어 토큰을 비교한다.

### 8. 사전 추가 후 기존 문서 누락

- 기존 문서의 용어는 **색인할 때의 사전**으로 만들어져 저장돼 있다. 질의는 새 사전으로 분석된다. 둘이 어긋난다.
- 재현(PostgreSQL): 매핑 변경 전 행은 `'running'`, 후 행은 `'run'`. `'run'` 질의는 새 행만 찾았다.
- 재색인 필요: 색인 분석기에 쓰이는 사용자 사전·토크나이저·색인 시점 동의어·PostgreSQL thesaurus(문서가 명시) 변경.
- 재색인 불필요: 검색 분석기에만 둔 `synonym_graph`(`updateable: true` + reload).

### 9. 트라이그램 인덱스와 두 패턴

- `'%냉장고%'`: `Bitmap Index Scan on product_name_trgm` → `Bitmap Heap Scan`. 세 글자라 트라이그램을 뽑을 수 있다.
- `'%삼성%'`: 인덱스가 있어도 `Parallel Seq Scan`이었다(로컬 재현).
  - 양쪽이 `%`인 두 글자에서는 온전한 트라이그램이 나오지 않는다.
  - pg_trgm 문서: 추출할 트라이그램이 없는 패턴은 인덱스 전체 스캔으로 떨어진다. 그래서 planner가 순차 스캔을 고른다.
