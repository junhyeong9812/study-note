# web-platform/14-image-optimization — 정답

## 정답

### 1. 원본 하나의 문제와 네 갈래

- 나빠지는 것
  - 바이트: 작은 화면이 큰 원본을 받는다 → 전송량·LCP 악화.
  - 안정성: 크기 정보가 없으면 도착할 때 레이아웃이 밀린다 → CLS.
  - 순서: 시점을 구분하지 않으면 첫 화면 이미지와 아래 이미지가 대역폭을 다툰다.
- 네 갈래
  - 포맷(AVIF·WebP·JPEG 폴백): 같은 화질의 바이트를 줄인다.
  - 해상도(`srcset`·`sizes`·`<picture>`): 화면에 필요한 화소만 보낸다.
  - 시점(`loading=lazy`·`fetchpriority`): 첫 화면 아래는 늦게, 히어로는 먼저.
  - 공간(`width`/`height`·`aspect-ratio`): 도착 전에 자리를 잡아 CLS를 막는다.

### 2. srcset 선택

(실험, headless Chrome 151)
- ① 뷰포트 400·DPR 2: 400 < 800이므로 `100vw` = 400px 슬롯, 필요 화소 800 → **800w**(14KB).
- ② 뷰포트 400·DPR 3: 필요 1200 → **1600w**(38KB). (실험은 `sizes="100vw"` 페이지에서 쟀다 — 폭 400에서는 이 `sizes`도 100vw로 평가되므로 계산이 같다.)
- ③ 뷰포트 1280·DPR 1: `50vw` = 640px 슬롯 → **800w**(14KB).
- 관찰된 경우들은 "필요 화소(슬롯 폭 × DPR) 이상인 가장 작은 후보"와 맞는다. 명세는 마지막 선택을 구현 재량으로 남긴다.
- `sizes`를 생략하면 `100vw`로 본다.

### 3. picture의 type 폴백

- Chrome 151: `image/x-unknown`은 지원하지 않는 type이라 건너뛰고, 다음 `image/avif` source의 `img-800.avif`(5KB)를 받았다(`currentSrc`로 확인).
- AVIF를 모르는 브라우저: `image/avif`도 건너뛰고 `image/webp`, 그것도 모르면 `<img>`의 JPEG로 내려간다. 브라우저가 지원 여부로 고르므로 서버 협상 없이도 안전하다.

### 4. 포맷 vs 해상도

(실험, 실제 사진 1장, sharp 0.33.5)
- PSNR 약 41.8dB: JPEG q75 38.4KB, AVIF q50 12.6KB → **약 3배**(AVIF가 1/3).
- 같은 JPEG q75: 3840w 154KB → 800w 14KB → **약 11배**.
- 이 사진·이 설정에서는 해상도를 맞추는 효과가 더 컸다. 포맷 비율은 사진 종류와 척도(PSNR은 거친 척도)에 따라 달라진다.

### 5. width/height 속성의 의미

- HTML 표준 렌더링 절: `img`의 `width`·`height` 속성은 `width`·`height` 속성값과 함께 `aspect-ratio: auto 800 / 450` 표현 힌트로 대응된다. 그래서 CSS가 폭만 정해도 높이를 비율로 계산해 자리를 잡는다.
- `width:100%`만 주고 `height:auto`를 빼면, 속성의 `height=450`이 그대로 높이로 쓰여 폭 400px에서 높이 450px — 그림이 세로로 늘어난다(실험: 이동은 0, 최종 높이 450px).
- 크기 정보가 없으면 로드 전 높이 0 → 도착 시 아래가 밀림. 실험 CLS **0.22**(폭 400px, 600ms 지연). 속성+`height:auto` 또는 `aspect-ratio`는 0.

### 6. 히어로 lazy의 비용

(실험, CPU 4×·RTT 150ms·1.6Mbps, 5회)

| | 요청 시작 | 서버 도착 | LCP | 우선순위 |
|---|---|---|---|---|
| eager | 188~202ms | 190~203ms | 1460~1472ms | Medium → High |
| lazy | 268~314ms | 4929~4994ms | 5384~5412ms | Low → High |

- 시작은 80~110ms만 늦지만, 서버 도착은 4.9초다.
- 이유(해석): lazy는 레이아웃 뒤 거리를 판정한 다음 요청을 만든다. 그 사이 아래쪽 eager 이미지 6장이 HTTP/1.1 호스트당 연결 6개를 모두 차지했다. 히어로는 우선순위가 High로 올라가도 연결이 빌 때까지 기다렸다.

### 7. lazy 임계 거리와 반추적 규칙

- Chromium: 유효 연결 유형별 기본 거리 안에 들어오면 요청한다 — 4G 1250px, 3G 2500px, 2G 6000px, slow-2G 8000px(Blink `settings.json5`. web.dev는 "3G 이하 2500px"로 줄여 말한다).
- HTML 표준: 스크립트가 꺼진 문서에서는 lazy를 적용하지 않는다. 스크립트 없이도 lazy가 동작하면, 서버가 이미지 요청이 언제 오는지로 사용자의 스크롤 위치를 추적할 수 있기 때문이다(스크립트가 켜져 있으면 어차피 스크립트로 알 수 있다).

### 8. CDN 포맷 변환 뒤 깨진 이미지

- 의심: CDN이 `Accept` 요청 헤더로 AVIF/WebP/JPEG를 고르는데, 캐시 키에 `Accept`가 빠졌다(`Vary: Accept` 누락). AVIF 지원 브라우저가 먼저 채운 캐시를 미지원 클라이언트도 받는다.
- 확인: 같은 URL을 `Accept`만 바꿔 요청해 응답 `Content-Type`·`Vary`를 비교한다.
- 고침: `Vary: Accept` 또는 CDN의 포맷별 캐시 키 설정. 마크업 `<picture type>` 방식은 브라우저가 고르므로 이 문제가 없다.

### 9. 알고리즘 구조와 이중 압축

- 해상도 선택: 폭으로 정렬된 후보에서 "목표 이상인 첫 후보"를 찾는 하한 탐색(이분 탐색 모양). 브라우저 재량(망·캐시)이 더해질 수 있다.
- 손실 압축: 블록을 주파수로 바꾸는 변환(DCT 등) → 양자화로 덜 보이는 정보를 버림 → 엔트로피 부호화(무손실). WebP 손실 모드는 VP8 키프레임식 예측을, AVIF는 AV1 인트라 프레임을 쓴다.
- 이중 압축: 이미 엔트로피 부호화된 데이터라 거의 안 줄어든다. 실험: 1600w JPEG 39,300B → gzip −2.3%, brotli −3.7%. AVIF 12,913B → −0.4%.
