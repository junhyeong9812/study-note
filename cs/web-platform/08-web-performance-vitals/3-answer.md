# web-platform/08-web-performance-vitals — 정답

## 정답

### 1. onload 하나로는 부족한 이유

- `onload`는 "문서와 이미지 같은 하위 자원 로드가 끝난 시각"이다. 사용자는 그보다 먼저 본문을 읽기 시작하거나, 반대로 onload 뒤에도 버튼이 굼뜨고 화면이 밀릴 수 있다.
- 세 지표
  - LCP: 로딩 — 가장 큰 콘텐츠가 그려진 시각("주요 내용이 보였나").
  - INP: 반응성 — 클릭·탭·키 입력부터 다음 페인트까지의 지연("누르면 바로 반응하나").
  - CLS: 시각적 안정성 — 예상 못 한 레이아웃 이동의 가장 큰 묶음("화면이 흔들리나").

### 2. 경계값과 집계

| 지표 | 좋음 | 나쁨 |
|---|---|---|
| LCP | ≤ 2.5s | > 4.0s |
| INP | ≤ 200ms | > 500ms |
| CLS | ≤ 0.1 | > 0.25 |

- 사이는 "개선 필요"다.
- 집계: 페이지 로드의 **75번째 백분위**, 모바일과 데스크톱을 **나눠서**(web.dev Web Vitals). `web-vitals` 6.2.2 소스 상수도 같다.

### 3. LCP 후보 순서

- 항목 2개: 먼저 문단 `P`(실험에서 176ms, 넓이 6,766), 다음 `IMG`(800ms, 넓이 240,000).
- 더 큰 요소가 그려질 때마다 새 항목이 나오고, LCP는 마지막 항목이다.
- 이미지 도착 전에 사용자가 스크롤(또는 탭·키 입력)하면 브라우저는 새 항목을 내지 않는다. LCP는 그때까지의 후보(문단)로 확정된다.

### 4. 이동 점수 계산

- 이전 사각형: y 129.875 ~ 329.875. 이후 사각형: y 429.875 ~ 600(뷰포트로 자름, 170.125).
- 둘은 겹치지 않는다. 합집합 높이 = 200 + 170.125 = 370.125.
- 영향 비율 = (800 × 370.125) / (800 × 600) = 0.6169.
- 거리 비율 = 300 / max(800, 600) = 0.375.
- 점수 = 0.6169 × 0.375 = **0.2313**. 실험의 `layout-shift` 값과 같다(headless Chrome 151).
- 바운딩 박스(129.875 ~ 600 = 470.125)로 잡으면 0.7835 × 0.375 = 0.2938로 더 크게 나온다. 측정값과 맞는 것은 합집합 쪽이다.

### 5. 핸들러 길이별 INP

(실험, headless Chrome 151, 스로틀 없음)
- 20ms 핸들러: `click` 24~32ms, INP 32ms → "좋음". 이 32는 첫 상호작용의 `first-input` 항목 값이다(`web-vitals` 기본 `durationThreshold` 40 미만인 `event` 항목은 보지 않는다).
- 300ms 핸들러: `click` 304~312ms, INP 312ms → "개선 필요"(200 초과 500 이하).
- 300ms 쪽 조각: input delay 1~2ms, processing 300~301ms. **processing이 거의 전부**다. 다른 긴 태스크가 먼저 메인 스레드를 쥐고 있었다면 input delay가 커졌을 것이다.

### 6. INP 선택 규칙

- 한 상호작용(`pointerdown`·`pointerup`·`click` 또는 `keydown`·`keyup`)의 지연 = 같은 `interactionId` 항목들의 `duration` 최댓값. `duration`은 8ms 단위로 반올림된다.
- 페이지 INP = 가장 나쁜 상호작용. 단 상호작용 50번마다 가장 높은 것 1개를 무시한다. `web-vitals`는 가장 긴 10개만 유지하고 `min(목록 길이 − 1, floor(상호작용 수/50))`번째를 고른다 — 500번 이상이면 10번째에 묶이는 근사다.
- 상호작용이 없으면 INP 값이 없다.
- 호버·스크롤·확대는 대상이 아니다. 클릭·탭·키 입력만 센다.

### 7. 섞인 분포의 p50·p75

(실험, headless Chrome 151, 3회 실행)
- 조건별 LCP: 데스크톱 244~300ms, 모바일 2136~2168ms, 저사양 7904~8096ms.
- 섞은 20개 표본: p50 292~300ms(데스크톱 값), p75 2136~2160ms(모바일 값), p95 7916~7944ms(저사양 값).
- p50은 다수인 빠른 사용자만 대변한다. p75는 "4명 중 3명은 이보다 좋다"는 선이라 느린 사용자 구간을 판정에 넣는다. 그래서 web.dev는 p75를 쓰고, 모바일·데스크톱을 나눠 보라고 한다.

### 8. 랩 초록 · 필드 개선 필요

- 차이 이유(web.dev "Why lab and field data can be different")
  - 기기·망: 랩은 한 조건, 필드는 실제 사용자 분포. 저사양 기기 꼬리가 랩에 안 보인다.
  - 캐시: 필드에는 재방문자의 캐시 효과가 섞인다(필드가 더 좋을 수도 있다).
  - LCP 요소: 화면 크기·`#fragment`에 따라 필드의 LCP 요소가 다를 수 있다.
  - CLS: 로드만 재는 랩(Lighthouse 탐색 등)은 로드 중·첫 화면만, 필드는 페이지 수명 전체. 상호작용을 넣은 랩 기록·DevTools 실시간 측정은 로드 뒤 이동도 잡는다.
  - INP: 사용자 입력 없이 로드만 재는 Lighthouse 탐색 감사는 INP가 없어 TBT로 대신한다. 스크립트·DevTools로 직접 누르면 그 상호작용의 INP는 랩에서도 잰다(5번 실험).
  - 기간: CrUX는 28일 기간이라 배포 효과가 늦게 반영된다.
- 확인 순서: ① 필드에서 어느 지표·어느 기기 구간인가 → ② RUM attribution으로 어느 페이지·요소인가 → ③ 랩에서 CPU 4×·느린 망으로 재현 → ④ 원인 조각(TTFB·로드 지연·로드 시간·렌더 지연)별 처방.

### 9. 모바일 RUM 누락

- 의심: 지표를 `unload`·`beforeunload`에서 보내는 코드. 모바일에서는 페이지가 이 이벤트 없이 사라질 수 있다.
- CLS·INP는 페이지 수명 전체를 보고 마지막에 확정되므로, 떠날 때 보내지 못하면 통째로 빠진다.
- 고침: `visibilitychange`에서 `visibilityState === 'hidden'`일 때 `navigator.sendBeacon`으로 보낸다(`web-vitals` README 권장). 한 페이지에서 여러 번 보고될 수 있으므로 `metric.id`로 서버에서 덮어쓴다.
- INP는 상호작용이 있어야 생기므로 LCP보다 건수가 적은 것 자체는 정상이다 — 비율 변화를 본다.

### 10. 알고리즘과 백분위 합산

- CLS 세션 창: 시간순 이동을 훑으며 "직전 이동과 1초 미만, 창 시작과 5초 미만"이면 현재 창에 더하고 아니면 새 창을 연다. 최댓값을 기억한다. 한 번 훑기 O(n).
- INP: 고정 크기(10) 상위 k 목록을 정렬해 유지하고 `min(목록 길이 − 1, floor(n/50))`번째를 고른다(정의의 근사). 힙으로도 할 수 있지만 k가 작아 정렬 배열이면 충분하다.
- 백분위 평균의 오류: p75는 선형이 아니다. 페이지 A(사용자 1만 명)의 p75와 페이지 B(100명)의 p75를 평균 내면 사용자 수 가중도 없고 분포 모양도 잃는다. 원자료나 히스토그램 버킷을 합친 뒤 다시 p75를 구한다.
