# web-platform/18-ui-rerender-and-memoization — 정답

## 정답

### 1. 재렌더 ≠ DOM 갱신

- 재렌더 = 컴포넌트 함수를 다시 불러 새 요소 트리를 만드는 것. DOM 갱신은 재조정이 찾은 차이만 반영한다.
- React는 상태가 바뀐 컴포넌트를 다시 렌더하고, 그 컴포넌트가 반환한 자식들도 기본적으로 다시 렌더한다. 그래서 공통 조상의 상태 하나가 하위 트리 전체를 다시 실행시킨다.

### 2. O(n) 휴리스틱

- 가정 ① 타입이 다른 두 요소는 다른 트리를 만든다(비교 없이 교체) ② `key`로 같은 자식을 알려 준다.
- 일반 트리 diff(트리 편집 거리)는 고전 알고리즘이 O(n³)(legacy.reactjs.org "Reconciliation"). 가중치 없는 경우 최근 결과는 약 O(n^2.69)이지만 여전히 n²보다 크다(ESA 2025 논문 서론).
- 타입이 바뀌면 하위 트리를 버리고 새로 만든다 → 그 아래 컴포넌트 상태와 DOM이 사라진다.

### 3. plain과 memo-broken (실험, headless Chrome 151, CPU 4×, React 19.2.8 프로덕션, 3회 + 사실 점검 재실행 6회)

- plain: 키 5번에 Row 15,000회(= 3000 × 5). 스크립트 578~770ms, 키 상호작용 160~424ms.
- memo-broken: 여전히 15,000회. 인라인 객체·함수는 렌더마다 새 참조라 `Object.is` 비교가 항상 다르다. 스크립트 672~850ms로 plain과 같거나 조금 많았다(범위는 겹치고, 묶음별 중앙값은 늘 plain보다 컸다 — 비교 비용만 추가, 해석).

### 4. 고친 두 가지

| | Row 렌더 | 스크립트(5번 합) | 키 상호작용 |
|---|---|---|---|
| ① memo-ok | 0 | 164~213ms | 120~240ms |
| ② colocate | 0 | 47~87ms(대부분 47~55) | 104~264ms |

- ②가 더 쌌다. ①은 List가 재렌더되며 3000개 요소 생성 + 3000번 props 비교가 남는다. ②는 입력창 컴포넌트만 재렌더된다(목록 없는 baseline 39~60ms와 비슷).

### 5. 세 도구

| | 기억하는 것 | 비교 |
|---|---|---|
| `memo(C)` | 직전 렌더 결과 | props 각 키를 `Object.is`(얕은 비교) |
| `useMemo(calc, deps)` | 직전 계산 결과 | deps 각 항목 `Object.is` |
| `useCallback(fn, deps)` | 직전 함수 객체 | deps 각 항목 `Object.is` |

- DP 메모이제이션은 계산한 부분 문제의 결과를 지우지 않고 쌓아 재사용한다. `useMemo`는 **직전 한 번**만 기억한다(캐시 크기 1) — 입력이 번갈아 바뀌면 적중하지 않는다.

### 6. memo 남발

- 원인 ① props가 매번 새 참조라 비교가 항상 실패(비교 비용만 추가) ② 원래 재렌더가 싼 컴포넌트라 아낄 것이 없음.
- 먼저: 측정(Profiler·Event Timing)으로 비싼 곳을 찾고, 상태를 쓰는 곳 가까이 내리거나 children 패턴으로 재렌더 범위를 줄인다. memo는 그다음, 자주·같은 props로·비싸게 재렌더되는 곳에만.

### 7. 제자리 변경

- `push`는 같은 배열 객체를 바꾼다 → `setItems(items)`가 이전과 같은 참조 → React가 `Object.is`로 "같다"고 보고 갱신을 건너뛸 수 있다.
- memo된 자식도 같은 참조를 받으면 변경을 못 보고 건너뛴다.
- 대처: `setItems([...items, x])`처럼 새 객체로 갱신한다.

### 8. 남은 비용

- colocate의 키 상호작용 104~264ms vs baseline 16~64ms. 스크립트·스타일·레이아웃 증가분은 비슷했다.
- `keydown` 항목을 세 조각으로 나누면 차이는 presentation delay(103~187ms vs 12~35ms)에 있다(사실 점검 재실험).
- 해석: 3000행 문서의 페인트·합성 등 렌더링 비용(어느 단계인지는 분해하지 않음).
- 처방: DOM 자체를 줄이는 **17 목록 가상화**.

### 9. 정렬 후 값 이동

- 원인: 인덱스를 key로 써서 재정렬 뒤 다른 데이터가 같은 key(같은 컴포넌트 인스턴스·상태)에 짝지어졌다. `Math.random()` key면 매번 새로 만들어 상태가 사라진다.
- 대처: 데이터의 안정적 ID를 key로 쓴다.
