# web-platform/19-hydration-cost-and-partial-hydration — 정답

## 정답

### 1. 되살리는 세 가지

- 리스너(어느 DOM에 어떤 핸들러), 컴포넌트 트리(프레임워크 내부 구조), 애플리케이션 상태(서버 데이터) — Qwik 문서 "Resumable"의 정리.
- 트리를 되살리려면 컴포넌트 코드를 클라이언트에서 다시 실행하고, 그 출력을 기존 DOM과 대조해야 한다.
- 정적 텍스트도 컴포넌트로 만들었다면 이 재실행·대조 대상에 들어간다. 그래서 반응할 일이 없는 부분도 비용을 치른다.

### 2. JS가 오기 전 클릭

`(실험, headless Chrome 151, React 19.2.8, 2026-10-04)`

```text
① 클릭 시각 328ms, 하이드레이션 끝 2232ms → 버튼: 장바구니 0
   하이드레이션 뒤 다시 클릭 → 버튼: 장바구니 1
```

- 첫 클릭은 버려진다(0). 그 시점에는 리스너도, 클릭을 기록해 둘 React 코드도 없다.
- 하이드레이션 뒤 클릭은 처리된다(1).

### 3. 무엇을 줄이나

| 방법 | 줄이는 것 |
|---|---|
| 점진 하이드레이션 | 한 번에 하는 양(조각별 부팅) |
| 선택적 하이드레이션 | 순서(상호작용한 경계 먼저) |
| 부분 하이드레이션·islands | 대상(정적 부분은 하지 않음) |
| 서버 컴포넌트 | 대상과 코드(서버 전용 컴포넌트의 코드·입력이 번들에 없음) |
| 재개(resumability) | 재실행 자체(리스너·상태를 HTML에 직렬화, 필요할 때 코드 로드) |

### 4. 코드가 오는 중인 경계 클릭

```text
② 셸 하이드레이션 153ms, B 클릭 202ms 직후 B: 리뷰 0
   청크 도착 뒤 B: 리뷰 0 / A: 찜 0
   다시 클릭 → B: 리뷰 1
```

- 청크 도착 뒤에도 0이다. 클릭은 재생되지 않았다.
- 소스 구조(react-dom 19.2.8 `dispatchEvent`)
  - 연속 이벤트(`focusin` 등)만 `queueIfContinuousEvent`로 대기열에 넣는다.
  - 클릭 같은 이산 이벤트는 막는 경계를 동기 하이드레이션하려 한다. 코드가 없어 여전히 막혀 있으면 `stopPropagation()`으로 끝낸다.
- 이 방향은 React PR #22448("dont replay discrete events")에서 정해졌다.
- 비교: 코드가 이미 와 있고 하이드레이션만 진행 중인 경계를 누르면, React가 그 경계를 먼저 동기 하이드레이션하고 클릭을 처리한다(실험 ②-b, `리뷰 1`). 사라지는 것은 React 루트가 아직 설치되지 않았거나(실험 ① — `hydrateRoot` 호출 전에는 루트 리스너가 없다), 그 경계의 코드가 없어 동기 하이드레이션을 못 할 때다(②-a).

### 5. 전체 vs 섬 하나

`(실험, CPU 4×, 각 5회)`

```text
③ n=500 full   하이드레이션 177~256ms | … | HTML 58852B
③ n=500 island 하이드레이션 79~115ms | … | HTML 25500B
③ n=5000 full   하이드레이션 478~657ms | 최장 태스크 446~618ms | HTML 593744B
③ n=5000 island 하이드레이션 70~114ms | 최장 태스크 0~68ms | HTML 250446B
```

- 전체 방식은 행 수를 따라 늘었다(n=2000에서 254~326ms). 섬 하나는 행 수와 거의 무관했다(70~122ms 안).
- 사실 점검 재실행(동시 부하 있음)에서는 full 203~865ms, island 92~176ms로 절대값이 컸지만 같은 경향이었다.
- n=5000의 HTML은 593,744B vs 250,446B, 약 2.4배(2.37)다. 차이는 하이드레이션 입력 JSON과 버튼 마크업이다.

### 6. 섬이 줄인 것과 못 줄인 것

- 줄인 것: 하이드레이션 작업(대조·리스너 대상 노드 수), 하이드레이션 입력 JSON.
- 못 줄인 것: 라이브러리 크기. 두 방식 모두 react-dom 번들을 받았다. 이 실험의 정적 목록 컴포넌트는 원래 번들에 거의 없었다.
- 섬 프레임워크(Astro 등)는 `client:*` 지시어가 없는 UI 프레임워크(React 등) 컴포넌트의 JS를 번들에서 뺀다. 단 `.astro` 컴포넌트 안의 `<script>`는 지시어 없이도 번들되어 브라우저로 간다(Astro 문서 "Scripts and event handling"). 섬마다 필요한 코드만 싣는다(22번).

### 7. 보일 때 하이드레이션

- `IntersectionObserver`로 섬 요소를 관찰한다. 교차하면 `unobserve`하고 섬 코드를 동적 `import()`한 뒤 `hydrateRoot(요소, 컴포넌트(props))`.
- `rootMargin`(예: `200px`)으로 화면에 들어오기 조금 전에 시작한다.
- 섬마다 그 섬의 props만 `data-props`처럼 직렬화한다. 페이지 전체 상태를 넣지 않는다.
- 한가할 때 시작하려면 `requestIdleCallback`을 쓴다(Astro의 `client:idle`과 같은 생각).

### 8. 서버 컴포넌트 이점이 안 보임

- 상위 파일(레이아웃 등)에 `'use client'`가 붙어 그 아래 모듈이 전부 클라이언트 그래프에 들어갔을 가능성.
- 확인: 번들 분석에서 마크다운 파서가 어느 `'use client'` 모듈을 통해 들어왔는지 추적한다.
- 대처: `'use client'`를 상호작용하는 잎 컴포넌트로 내린다. 서버 컴포넌트가 클라이언트 컴포넌트를 `children`으로 감싸게 구조를 바꾼다.

### 9. 하이드레이션이 원인인지 확인하고 줄이기

- 확인
  - Performance 패널(CPU 4×)에서 긴 태스크의 호출 스택이 `hydrateRoot`·프레임워크 하이드레이션 함수에서 시작하는지 본다.
  - `longtask`·LoAF 관찰로 하이드레이션 구간과 겹치는지 본다.
- 줄이는 순서
  1. 정적 부분을 하이드레이션 대상에서 뺀다(서버 컴포넌트·islands).
  2. 남은 부분을 `<Suspense>` 경계로 쪼갠다.
  3. 첫 화면 밖은 보일 때·한가할 때로 미룬다.
  4. 하이드레이션 입력 JSON을 필요한 필드로 줄인다.

### 10. JS 없이 막기

- 핵심 동작을 `<form action="/cart" method="post">`, `<a href>`처럼 HTML만으로 작동하게 만든다(점진적 향상). 하이드레이션 전 클릭은 브라우저 기본 동작으로 처리된다.
- 10번과의 연결: SSR·SSG를 고르면 HTML이 먼저 오고 반응은 늦게 온다. 그 간격을 메우는 것이 점진적 향상과 하이드레이션 대상 줄이기다. CSR에는 이 간격이 없지만 첫 화면이 늦다.
