# web-platform/19-hydration-cost-and-partial-hydration — 질문

## 질문

1. (왜) 하이드레이션이 되살려야 하는 세 가지는 무엇인가? 그 때문에 화면의 정적 텍스트까지 비용을 치르는 이유를 설명하라.
2. (예측) SSR 페이지의 JS를 서버가 2초 늦게 보낸다. 버튼이 보이자마자(약 0.3초) 누르고, 하이드레이션 뒤 한 번 더 누르면 카운터는 각각 몇이 되나? 왜 그런가?
3. (경계) 점진 하이드레이션, 선택적 하이드레이션, 부분 하이드레이션(islands), 서버 컴포넌트, 재개(resumability)를 "무엇을 줄이나"로 구분하라.
4. (예측) 셸은 하이드레이션됐고 B 버튼이 든 `<Suspense>` 경계의 코드(`React.lazy` 청크)는 아직 오는 중이다. 이때 B를 누르면, 청크 도착 뒤 B의 카운터는? React 19.2.8 소스의 어떤 구조가 이 결과를 설명하나?
5. (예측) 상품 n=500·2000·5000 페이지를 전체 하이드레이션과 섬 하나 하이드레이션으로 비교했다(CPU 4×). 행 수가 늘 때 두 방식의 하이드레이션 시간은 각각 어떻게 변하나? n=5000의 HTML 크기 차이는?
6. (경계) 실험 ③에서 섬 방식도 react-dom 번들(약 194KB)을 똑같이 받았다. 그렇다면 이 실험의 섬은 무엇을 줄였고 무엇을 못 줄였나? 섬 프레임워크는 그 외에 무엇을 더 줄이나?
7. (적용) 리뷰 위젯을 화면에 보일 때 하이드레이션하려 한다. 바닐라 JS로 어떤 API를 써서 짜나? 섬마다 무엇만 직렬화해야 하나?
8. (장애 진단) 서버 컴포넌트를 도입했는데 번들에 마크다운 파서가 그대로 있고 하이드레이션 시간도 줄지 않았다. 무엇을 의심하나?
9. (장애 진단) 로드 직후 몇 초간 입력이 버벅이고, Performance 패널에 FCP 뒤 수백 ms 긴 태스크가 있다. 하이드레이션이 원인인지 어떻게 확인하고, 어떤 순서로 줄이나?
10. (연결) "하이드레이션 전 클릭이 무시된다"를 JS 없이도 막는 HTML 수준의 방법은? 10번의 렌더링 방식 선택과 어떻게 이어지나?
