# web-platform/03-event-loop — 정답

## 정답

### 1. 규칙이 없으면

- 순서가 깨진다: 비동기 콜백이 다른 핸들러 중간에 끼어들면 반쯤 바뀐 상태를 보게 된다.
- "태스크 하나를 끝까지"는 **실행 중 끼어들기 없음**을 지켜 준다. 한 태스크의 동기 코드는 다른 태스크에 선점되지 않는다. 다만 비동기 작업 사이의 순서(다른 태스크 큐끼리의 선택 순서는 구현 정의)에 기대는 코드는 여전히 경쟁 조건을 가질 수 있다.
- 대가: 선점이 없어서, 한 태스크가 길면 입력·타이머·렌더링이 모두 기다린다(응답성 저하).

### 2. 한 바퀴 그림

```text
 ① 태스크 큐 하나 고름(구현 정의) → 첫 실행 가능 태스크 실행
 ② 마이크로태스크 체크포인트 — 빌 때까지
 ③ (병렬) 렌더링 기회 → "update the rendering" 태스크를 렌더링 태스크 소스에 넣음
    그 태스크: resize → scroll → 미디어 쿼리 → 애니메이션 → 전체화면 → [rAF 콜백] → 스타일·레이아웃 → … → 페인트 갱신
```

- rAF는 스타일·레이아웃 **직전**에 돈다. rAF 안의 쓰기는 그 프레임 계산에 들어간다.

### 3. 두 문장

- "Task queues are sets": 이벤트 루프는 큐에서 맨 앞을 빼지 않고 "첫 실행 가능 태스크"를 고른다(예: 비활성 문서의 태스크는 건너뜀).
- "The microtask queue is not a task queue": ①의 선택 대상이 아니다. 체크포인트(태스크 끝, 스크립트 실행 스택이 빌 때)에서만 비워진다.
- 큐 사이 순서가 구현 정의라는 것은 브라우저가 **우선순위 스케줄링**(입력 우선, 렌더링 우선, 백그라운드 후순위)을 할 수 있다는 뜻이다. 같은 태스크 소스 안의 순서만 보장된다.

### 4. 실행 순서

(실험, headless Chrome 151, 스로틀 없음, 2026-10-04 — 10/10회 같음)

```text
sync-끝 → micro-1 → micro-2 → micro-1이 넣은 micro → timeout-1 → timeout-1 안의 micro → timeout-2 → message → rAF → rAF 안의 micro
```

- 표준 보장
  - 동기 → 마이크로태스크 전부(실행 중 추가된 `micro-1이 넣은 micro`까지) → 첫 태스크.
  - `timeout-1 안의 micro`가 `timeout-2`보다 먼저(태스크마다 체크포인트).
  - `timeout-1` → `timeout-2`(같은 타이머 소스, 같은 지연).
  - `rAF 안의 micro`는 그 rAF 콜백 직후.
- 관찰일 뿐
  - 타이머 대 `message`의 순서(다른 태스크 소스).
  - rAF가 맨 끝인 것(렌더링 기회 시점에 좌우).

### 5. 긴 태스크 중 클릭

(실험, headless Chrome 151, 2026-10-04 — 3회)

```text
긴 태스크 300ms 중 클릭 run1: 핸들러 시작 - event.timeStamp = 249ms; Event Timing ["pointerup:delay=248 dur=256","click:delay=249 dur=256"]
```

- 약 250ms(집필 249~250ms, 사실 점검 재실행 246~251ms) 늦게 시작했다. 300ms 태스크의 남은 시간이다. 바쁘지 않을 때는 3~4ms였다.
- `duration`은 Event Timing 표준이 **8ms 단위**로 제공한다(고해상도 타이머로 악용되는 것을 막기 위해). 그래서 `dur=256`(바쁘지 않을 때 16)처럼 8의 배수다. `delay=248·249`는 `processingStart − startTime`이라 8ms 반올림 대상이 아니다(248이 8의 배수인 것은 우연).

### 6. 마이크로태스크 연쇄 vs 태스크 연쇄

(실험, headless Chrome 151, 2026-10-04 — 마이크로태스크 쪽은 매번 0회, 태스크 쪽은 재실행 포함 31~32회)

```text
마이크로태스크 연쇄 500ms run1: 그동안 rAF 0회, 먼저 걸어 둔 setTimeout(0) 실행 시각 501ms
태스크(setTimeout) 연쇄 500ms run1: 그동안 rAF 31회, 먼저 걸어 둔 setTimeout(0) 실행 시각 1ms
```

- 마이크로태스크: rAF 0회, 선행 타이머 501ms(루프가 끝난 뒤). 체크포인트가 "빌 때까지"라 다음 태스크가 오지 않는다.
- 태스크: rAF 31~32회, 선행 타이머 0~1ms. 태스크 사이마다 다른 큐·렌더링이 끼어든다.

### 7. INP 세 단계

| 단계 | 뜻 | 이벤트 루프와의 대응 |
|---|---|---|
| 입력 지연 | 핸들러가 시작되기까지 | 앞선 태스크가 끝나길 기다림(5번) |
| 처리 시간 | 핸들러 실행 | 이벤트 디스패치 태스크 + 체크포인트 |
| 표시 지연 | 다음 프레임이 그려질 때까지 | 렌더링 기회 → update the rendering → 페인트 |

- 임계값(web.dev INP): p75 기준 200ms 이하 좋음, 500ms 초과 나쁨.

### 8. 스피너가 안 보임

- 원인: `await Promise.resolve()`의 이어짐은 마이크로태스크다. 같은 체크포인트 안에서 바로 `heavy()`가 돌아, 렌더링 태스크가 끼어들 틈이 없다. 스피너 DOM은 바뀌었지만 페인트 전에 무거운 작업이 메인 스레드를 잡는다.
- 고치기: 렌더링 기회를 넘긴 뒤 시작한다 — `await new Promise(r => requestAnimationFrame(() => setTimeout(r, 0)))`. 근본적으로는 작업을 쪼개 태스크로 양보하거나 워커로 옮긴다.

### 9. 숨은 탭의 rAF

- 근거: 표준의 렌더링 업데이트는 "Filter non-renderable documents" 단계에서 `visibilityState`가 `"hidden"`인 문서를 뺀다. rAF는 그 업데이트 안에서 돌므로 숨은 동안 오지 않는다.
- 대처: 비시각 로직은 rAF에 두지 않는다(타이머·이벤트 기반). `visibilitychange`로 멈춤·재개를 명시하고, 돌아왔을 때 경과 시간으로 상태를 보정한다.
