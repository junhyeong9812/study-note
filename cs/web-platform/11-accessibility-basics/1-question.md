# web-platform/11-accessibility-basics — 질문

## 질문

1. (왜) 스크린리더 같은 보조 기술은 화면 그림 대신 무엇에서 역할·이름을 얻나? 그 구조의 노드가 갖는 세 값은 무엇이고, WCAG 2.2의 어느 성공 기준이 이 셋을 요구하나?
2. (예측) `<div onclick="pay()">결제하기</div>`, `<button onclick="pay()">결제하기</button>`, `<div role="button" tabindex="0" onclick="pay()">결제하기</div>`가 있다. Chrome 151에서 각각의 접근성 트리 역할, Tab 도달 여부, 포커스 후 Enter·Space를 눌렀을 때 `click` 횟수를 예측하라.
3. (경계) "ARIA는 의미를 바꿀 뿐 동작을 주지 않는다"는 말을 2번의 세 번째 요소로 설명하라. 키보드로 쓸 수 있게 하려면 무엇을 더 넣어야 하나?
4. (예측) `<span role="button" aria-hidden="true" tabindex="0">`은 접근성 트리와 Tab 순서에서 각각 어떻게 되나? 사용자는 무엇을 겪고, Using ARIA의 어느 규칙을 어긴 것인가?
5. (예측) DOM 맨 끝에 `<input tabindex="3">`이 있고 앞쪽에 버튼·링크가 있다. 페이지에서 처음 Tab을 누르면 포커스는 어디로 가나? 이것이 왜 문제인가?
6. (경계) axe-core 같은 자동 검사기가 잡는 문제와 놓치는 문제를 실험 결과로 하나씩 들고, 왜 놓치는지 설명하라.
7. (연결) 접근 가능한 이름은 어떤 우선순위로 계산되나? `<button aria-label="닫기">X</button>`와 레이블 없이 `placeholder="이메일"`만 있는 입력칸의 이름은 각각 무엇이 되고, 후자가 왜 여전히 문제인가?
8. (장애 진단) SPA에서 라우트를 바꾼 뒤 스크린리더가 아무 말도 하지 않고, Tab을 누르면 페이지 처음부터 다시 시작한다. 원인과 대처는?
9. (장애 진단) 모달을 열 때 배경 요소에 `aria-hidden="true"`만 걸었더니 키보드 사용자가 모달 뒤 버튼으로 이동한다. 무엇이 빠졌고, 어떻게 고치나?
10. (연결) WCAG 2.2에서 새로 생긴 포커스·포인터 관련 AA 기준 두 개는 무엇이고, 각각 어떤 UI 패턴에서 깨지기 쉬운가?
