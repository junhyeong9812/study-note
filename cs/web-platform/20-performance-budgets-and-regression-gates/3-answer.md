# web-platform/20-performance-budgets-and-regression-gates — 정답

## 정답

### 1. 리뷰로 못 잡는 이유와 해법

- 회귀는 `import` 한 줄, 이미지 하나처럼 diff에서 작게 보인다. 번들 크기·로드 시간은 diff에 나타나지 않고, 작은 악화가 여러 PR에 쌓인다.
- 성능 예산: 넘지 않기로 정한 지표의 한계값(KB·LCP 등).
- 회귀 게이트: CI가 변경마다 지표를 재서 예산·기준선과 비교하고, 넘으면 빌드를 실패시킨다. 숫자가 PR마다 자동으로 나오므로 "어느 PR이 넘겼나"가 바로 보인다.

### 2. 예산 세 종류

| 종류 | 예 | 노이즈 | 이유 |
|---|---|---|---|
| 양 | JS KB, 요청 수 | 작음 | 빌드 산출물은 같은 코드면 같다. 요청 목록도 광고·A/B 같은 비결정 콘텐츠가 없으면 같다(실험의 고정 페이지: 9회 min = max) |
| 시점 | FCP·LCP·TBT | 큼 | CPU 스케줄링·네트워크·자원 경합에 따라 실행마다 다르다(실험: 같은 코드의 LCP 폭 70~260 ms, 재실행 포함) |
| 규칙 | Lighthouse 점수 | 큼 | 지표별 점수의 가중 평균(LCP 25%·TBT 30%·CLS 25% 등)이라 그 흔들림을 물려받는다 |

- 빌드 단계에서 엄격히 걸 것: **양 예산**. 결정적이라 오탐이 거의 없다.

### 3. lodash vs lodash-es

(실험, esbuild 0.28.1)
- `lodash` 전체: 축소 72.3 KB, gzip 26.3 KB.
- `lodash-es`의 `debounce`: 축소 3.0 KB, gzip 1.5 KB.
- 이유: `lodash`는 CommonJS 한 파일이라 번들러가 쓰지 않는 함수를 잘라 낼 수 없다. `lodash-es`는 함수마다 ES 모듈이라, 번들러가 import 그래프에서 도달하는 모듈만 남긴다(트리 셰이킹).

### 4. 동기 스크립트 회귀

(실험, headless Chrome 151, 9회 중앙값)
- LCP 480 → 872 ms, TBT 근사 0 → 216 ms. 게이트 `GATE FAIL (exit 1)`.
- 동기 `<script>`는 내려받고 실행이 끝날 때까지 파서를 멈춘다. 그 뒤의 본문이 아직 DOM에 없으니 첫 렌더(=LCP 후보 텍스트)도 늦어진다. 4× CPU에서 72 KB 스크립트의 파싱·실행이 50 ms를 넘는 긴 태스크가 됐다. 단 이 측정은 FCP 이전 태스크까지 합친 근사다. 스크립트가 첫 렌더 전에 실행되므로, FCP 이후만 세는 실제 TBT가 216 ms만큼 늘었다고 단정할 수는 없다.

### 5. A/A 오탐

- 한계 = 484 × 1.05 ≈ 508 ms.
- 같은 코드 단일 실행: 15번 중 **3번** 오탐(바쁜 프로세스 2개를 함께 돌린 묶음은 5번). 사실 점검 재실행에서는 1번이었다 — 오탐 횟수도 실행마다 흔들린다.
- 5회 중앙값끼리 비교: 3묶음 중 **0번**(476·484·492). 재실행도 0번.
- 허용 10%(한계 532)면 단일 실행 오탐이 1번으로 줄었다.

### 6. 노이즈 대처

- 여러 번 실행해 중앙값을 쓴다(Lighthouse 문서: "5회 점수 중앙값이 1회보다 두 배 안정" — 성능 점수에 대한 말이다).
- 전용 하드웨어: 전용 코어 2개 이상(권장 4), 메모리 2 GB 이상(권장 4~8). 버스트형 인스턴스·서버리스는 피한다.
- 같은 기계에서 측정을 동시에 돌리지 않는다(자원 경합).
- 페이지 비결정성(A/B 테스트·광고)을 측정 환경에서 고정한다.
- Lighthouse CI 대응: `collect.numberOfRuns`(기본 3)를 늘리고, 단언에 `aggregationMethod: 'median'`(지정하지 않으면 기본이 가장 통과하기 쉬운 값인 `optimistic`), 처음엔 `warn` 수준으로 운영해 오탐률을 본 뒤 `error`로 올린다.

### 7. 랩 ≠ 현장

- 랩 조건(기기·네트워크)이 실제 사용자 분포보다 좋을 수 있다.
- 랩 페이지에 로그인 상태·개인화·광고·서드파티 스크립트가 없을 수 있다.
- INP는 실제 상호작용이 있어야 나온다. 페이지 로드 랩 측정에는 없다(TBT로 간접 확인).
- "좋음" 기준: LCP 2.5 s 이하, INP 200 ms 이하, CLS 0.1 이하. 모바일·데스크톱을 나눠 페이지 로드의 75번째 백분위로 판정한다(web.dev "Web Vitals").

### 8. 조용히 무력화된 게이트

- 의심: 게이트가 기대던 설정을 새 판이 더는 읽지 않는다. Lighthouse 12.0.0은 breaking change로 budgets를 제거했다("remove budgets (#15950)"). 옛 `budgets` 설정·`performance-budget` 단언이 결과 0개가 되어 아무것도 강제하지 않은 사례가 공개 PR에 보고됐다.
- 확인: CI 로그에서 단언 개수·결과 목록이 비었는지 본다.
- 재발 방지: 지원되는 단언(`resource-summary:script:size` 등)으로 옮긴다. 일부러 예산을 넘는 카나리 페이지를 두고 "게이트가 실패하는지"를 정기적으로 시험한다(실험의 `full-lodash` 변형이 그 역할). 도구 메이저 업그레이드 PR에서 이 카나리를 같이 돌린다.

### 9. 게이트를 끄기 전에

1. A/A로 노이즈 폭을 잰다 — 같은 커밋을 여러 번 측정해 시간 지표의 폭을 본다.
2. 측정을 단일 실행에서 N회 중앙값으로 바꾼다.
3. 러너를 고정·전용으로 하고 측정을 직렬로 돌린다.
4. 허용 폭을 노이즈 폭보다 넓게 다시 잡는다. 결정적 지표(KB·요청 수)는 엄격히 유지하고, 시간 지표만 느슨하게 한다.
5. 그래도 흔들리면 시간 지표 단언을 `error`에서 `warn`으로 내린다. 게이트 전체를 끄는 것은 마지막이다.

### 10. 중앙값과 p75

- 중앙값: 튀는 실행 하나(예: 백그라운드 작업이 겹친 1회)가 평균은 크게 끌지만 중앙값은 거의 움직이지 않는다. 회귀 판정에 필요한 "평소 값"을 안정적으로 준다.
- p75: 페이지 조회 분포의 꼬리를 본다. 평균·중앙값이 좋아도 느린 기기·네트워크에서 조회 4번 중 1번이 나쁜 경험일 수 있다. p75가 기준을 넘지 않으면 조회의 75%가 그 기준 이상이다(web.dev: "75th percentile value of all page views"). 한 사용자가 여러 번 방문하므로 사용자 비율로 바로 바꿀 수는 없다.
