# web-platform/10-rendering-strategies — 정답

## 정답

### 1. 어디서, 언제

| 방식 | 어디서 | 언제 |
|---|---|---|
| CSR | 브라우저(JS가 DOM 생성) | 페이지를 연 뒤 |
| SSR | 서버 | 요청마다 |
| SSG(정적 렌더링) | 서버(빌드 머신) | 빌드 때 한 번 |

- SSR과 SSG는 도착하는 HTML이 같을 수 있다(실험에서 둘 다 198,212B).
- 차이는 **서버 쪽 시간**에 드러난다. SSR은 요청마다 데이터를 조회하고 렌더링하므로 그 시간이 TTFB에 더해진다. 실험에서 SSR TTFB 339~370ms(DB 300ms 포함), SSG 7~8ms.
- SSG는 URL마다 파일을 미리 만들어야 한다. 사용자별·요청별로 다른 페이지에는 쓸 수 없다.

### 2. 보이는 시점 vs 반응하는 시점

```text
  CSR  [HTML]─[JS 다운로드·실행]─[데이터 fetch]─[렌더] ── 보임 = 반응
  SSR  [서버 렌더]─[HTML] ── 보임 ··· [JS 다운로드]─[하이드레이션] ── 반응
```

- CSR은 JS가 DOM을 만들면서 리스너도 같이 붙인다. 그래서 보이는 순간 반응한다.
- SSR은 HTML이 먼저 그려진다. 리스너는 JS가 도착해 하이드레이션해야 붙는다. 그 사이가 "보이지만 (JS 동작이) 반응하지 않는 구간"이다. `href` 링크 이동 같은 브라우저 기본 동작은 그 전에도 된다.

### 3. CSR vs SSR 실측

- FCP: CSR 3652~4380ms, SSR 632~748ms → SSR이 약 5배 빠르다.
- SSR의 반응 시작은 3070~3623ms. 범위끼리 빼서 어림하면 FCP 뒤 약 2.3~3.0초 동안 반응하지 않았다.
- CSR이 느린 이유: HTML(943B) → JS 195KB → `/api/items` → 렌더를 차례로 기다린다. 2000개 목록을 처음부터 만드는 최장 태스크도 811~1517ms였다.
- 조건: headless Chrome 151, React 19.2.8, 5회 최소~최대. 실사용자 기기의 값과는 다르다.

### 4. 셸과 나중 조각

- 셸 = `<Suspense>` 경계 밖 부분. `onShellReady`에서 바로 보낸다.
- 먼저 가는 HTML: 셸 + 대체 UI. 경계는 `<!--$?--><template id="B:0"></template><p>불러오는 중…</p><!--/$-->`처럼 주석과 자리 표시자로 표시된다.
- 나중 HTML: 데이터가 오면 `<div hidden id="S:0">…목록…</div>`와 `$RC("B:0","S:0")` 스크립트가 온다.
- 스크립트가 `B:0` 자리의 대체 UI를 지우고 `S:0`의 내용을 옮겨 넣는다. 경계 주석은 `$`(완료)로 바뀐다.
- 실험에서 스트리밍 FCP 320~372ms로 가장 빨랐다(셸이 DB 대기 없이 갔다).

### 5. mismatch 예측

`(실험, headless Chrome 151, React 19.2.8, 2026-10-04)`

```text
{"text":"브라우저에서 렌더","sameNode":false,"recoverable":["Minified React error #418; …"]}
```

- 화면 글자는 `브라우저에서 렌더`로 바뀐다.
- 노드는 그대로가 아니다(`sameNode:false`). React가 서버 DOM을 버리고 그 트리를 클라이언트에서 다시 만들었다.
- 운영 빌드는 `Minified React error #418`(번호만). 개발 빌드는 `Hydration failed because the server rendered text didn't match the client. As a result this tree will be regenerated on the client.`
- 실험에서는 `onRecoverableError`로 메시지를 받았다.

### 6. 로캘 날짜 mismatch 처리

- **두 번 그리기**: 첫 렌더는 서버와 같은 값(예: ISO 문자열)을 내고, `useEffect`에서 `isClient`를 true로 바꿔 로캘 형식으로 다시 그린다.
  - 한계: 화면이 한 번 바뀐다(깜빡임). 렌더가 한 번 더 일어난다.
- **`suppressHydrationWarning`**: 피할 수 없는 한 단계 차이의 경고를 끈다.
  - 한계: 한 단계 깊이에만 적용된다. react.dev는 탈출구로만 쓰라고 한다. 경고만 끌 뿐 React는 어긋난 텍스트를 고치지 않는다 — 서버가 렌더한 값이 그대로 남는다.
- 근본 대책은 서버가 사용자 로캘·시간대를 알고 같은 값을 렌더하게 하는 것이다(12번 국제화와 연결).

### 7. 다른 사람 화면이 보인다

- 의심: 사용자별 HTML이 공유 캐시(CDN·리버스 프록시·앱 메모리 캐시)에 URL만 키로 저장됐다. 앱 로그에 요청이 없는 것은 캐시가 응답했다는 신호다.
- 재현: 쿠키가 다른 두 세션으로 같은 URL을 차례로 연다. 실험 출력:

```text
cookie user=alice /me → alice님의 주문 내역
cookie user=bob /me → alice님의 주문 내역
cookie user=bob /me?nocache → bob님의 주문 내역
```

- 확인: 응답 헤더의 `Cache-Control`, CDN의 캐시 적중 헤더, CDN 규칙(쿠키 있는 요청을 우회하나).
- 대처: 개인화 응답에 `Cache-Control: private`(또는 `no-store`). 공통 부분만 캐시하고 개인화 부분은 분리한다. 노출 범위를 파악해 알린다.
- 실사건: Steam 2015-12-25. Valve 성명 — DoS 대응 중 넣은 캐시 설정이 인증 사용자 트래픽을 캐시해, 일부 사용자가 다른 사용자용 페이지를 봤다. 11:50~13:20 PST 사이 약 34k 사용자의 스토어 페이지 요청이 다른 사용자에게 보였을 수 있다(Steam 공지).

### 8. 캐시 없이 부하 때만 섞임

- SSR 서버 모듈의 전역 상태를 찾는다. 예: `let currentUser = …`를 요청 처리 중에 대입하고 렌더에서 읽는 코드.
- 한 Node 프로세스는 여러 요청을 동시에 처리한다. 비동기 대기 사이에 다른 요청이 그 전역을 덮어쓴다. 동시 요청이 겹칠 때만 재현되는 이유다.
- 대처: 요청별 값은 인자·React 컨텍스트·요청 범위 저장소(`AsyncLocalStorage`)로만 전달한다. 부하 테스트에 "응답의 사용자 = 요청의 사용자" 검사를 넣는다.

### 9. HTML 속 JSON

- 하이드레이션은 컴포넌트를 클라이언트에서 다시 실행해 서버와 같은 출력을 내야 한다. 그러려면 서버가 쓴 입력 데이터가 클라이언트에도 있어야 한다.
- 실험(상품 2000개): 마크업 109,251B, JSON 87,981B. 같은 정보가 HTML과 JSON 두 형태로 갔다.
- 줄이는 방향
  - 반응이 필요 없는 부분은 하이드레이션하지 않는다(부분 하이드레이션·islands — 19·22번). 그 부분의 데이터는 JSON으로 보낼 필요가 없다.
  - 서버 컴포넌트: 서버에서만 실행하는 컴포넌트의 코드와 입력은 클라이언트로 가지 않는다(19번).
