# distributed/24-conflict-resolution-and-crdt — 정답

## 정답

### 1. 충돌이 생기는 이유와 세 방식

- 단일 리더는 한 키의 쓰기를 한 곳에서 순서대로 적용하므로 같은 키에 서로 모르는 쓰기가 생기기 어렵다.
- 다중 리더·리더리스는 여러 복제본이 각자 쓰기를 받는다. 동기화 전까지 서로 모르는(동시) 쓰기가 같은 키에 쌓인다.
- 세 방식: 하나만 남기기(LWW), 둘 다 남겨 앱·사람이 고르기(버전 벡터 + 형제), 자료형 규칙으로 합치기(CRDT).

### 2. LWW 예측

- A: ts 1000, B: ts 1050−100 = 950 → 병합 결과 `blue`. 인과적으로 나중인 `green`이 진다.
- 실험 출력: `A=Lww[value=blue, ts=1000, node=A]  B=Lww[value=green, ts=950, node=B]  → 병합 결과 blue`.

### 3. Cassandra 5.0 LWW

- 타임스탬프: 클라이언트가 주면 그 값, 없으면 코디네이터 노드 시계. 삭제에도 붙는다. 컬럼마다 따로 비교한다.
- 요구: "정확성이 시계에 의존하므로 NTP 같은 시계 동기화를 돌려라".
- 행 단위로는 LWW-Element-Set CRDT라고 부른다(문서 Data Versioning).

### 4. 버전 벡터와 context

- `{A:2}` vs `{A:1, B:1}`: 앞은 A 칸이, 뒤는 B 칸이 크다 → 동시(CONCURRENT). 둘 다 형제로 남긴다.
- 합친 값을 쓸 때 두 벡터를 칸별 max한 context(`{A:2, B:1}`)를 보내야 저장소가 새 값을 두 형제의 후손(AFTER)으로 보고 둘을 대체한다. context 없이 쓰면 또 하나의 동시 버전이 되어 형제가 늘어난다. 실험의 `vM vs vA: AFTER, vM vs vB: AFTER`가 대체되는 경우다.

### 5. SEC 조건

- 상태 기반: 상태가 반격자를 이루고, 갱신이 상태를 단조 증가시키며, merge가 최소 상계(LUB)를 계산하면, 최종 전달·종료 가정에서 SEC다(Theorem 2.1). LUB는 교환·결합·멱등이다.
- 연산 기반: 인과 순서 전달을 가정하고, 동시 연산들이 서로 교환 가능하면 SEC다(Theorem 2.2).

### 6. G-Counter 예측

- 칸별 max: `{A:3, B:5, C:2}` → 10. 실험에서 1000가지 순서 모두 `[10]`.
- 그냥 더하면 3+5+2+5+3 = 18(실험 `나이브 합 ... 18`).
- 같은 칸 A를 두 인스턴스가 4, 6 올리면 max(4, 6) = 6. 증가분 4가 사라진다(실험 `병합 값 6`).

### 7. OR-Set vs LWW 원소 집합

- OR-Set: B의 remove는 자기가 본 태그 `A:1`만 지운다. A가 동시에 넣은 `A:2`는 본 적이 없으니 남는다 → 사과 있음(add 승). 실험에서 병합 순서와 무관하게 `[사과]`.
- LWW 원소 집합: add·remove 시각을 비교한다. 다시 넣은 A의 시계가 느려 add=105, remove=110이면 사과가 사라진다(실험 `[]`). 시계에 따라 결과가 달라진다.

### 8. 잔액

- PN-Counter는 동시 차감을 모두 받아들이고 나중에 합칠 뿐이다. 두 복제본이 각자 "잔액 100에서 70 차감"을 허용하면 합친 값은 −40이다. 차감 시점에 전역 잔액을 아는 장치가 없다.
- 불변식이 걸린 데이터는 합의·단일 리더(11번)나 트랜잭션으로 직렬화한다. 합의 없이 가려면 차감 권한을 복제본에 미리 나눠 주는 bounded counter(Balegas 외 2015)를 쓴다. 몫이 모자라면 거절하거나 권한을 넘겨받는다.

### 9. 지운 상품 부활

- 원인 1: 형제를 합집합으로 합쳤다. 합집합은 삭제를 표현하지 못한다(Dynamo 논문). 대처: OR-Set·2P-Set처럼 삭제를 표현하는 자료형으로 바꾼다.
- 원인 2: 툼스톤을 너무 일찍 정리했고, 오래 끊겼던 복제본이 옛 값을 다시 퍼뜨렸다. 대처: 모든 복제본이 삭제를 받은 뒤에만 툼스톤을 정리한다.
- Cassandra 5.0의 `gc_grace_seconds`(기본 864000초 = 10일)는 툼스톤을 지우기 전 유예 기간이다. 그보다 오래 끊긴 노드가 돌아오면 지운 데이터가 "zombie"로 되살아날 수 있다(문서).

### 10. 고쳐도 옛 주소로 남음

- 확인: `SELECT address, WRITETIME(address) FROM users WHERE id = ?;` — 타임스탬프(µs)가 현재보다 미래인지 본다.
- 원인: 시계가 앞선 노드·클라이언트가 미래 타임스탬프로 썼다. LWW라 그 시각이 올 때까지 이후 쓰기가 모두 진다.
- 재발 방지: 노드·클라이언트 시계 오프셋 감시와 알람, 클라이언트 타임스탬프 사용 지양, 인과가 중요한 필드는 HLC·버전 벡터로 순서를 정한다.
