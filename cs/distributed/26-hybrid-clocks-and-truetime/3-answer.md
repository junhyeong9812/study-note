# distributed/26-hybrid-clocks-and-truetime — 정답

## 정답

### 1. 벽시계만, 램포트만의 한계

- 벽시계만: 노드마다 어긋나 인과적으로 나중인 트랜잭션이 더 작은 타임스탬프를 받을 수 있다.
- 램포트만: 인과는 지키지만 물리 시각과 관계가 없어 "10:00 기준 스냅샷" 같은 질의를 못 한다. 시스템 밖 채널(사용자)의 순서도 모른다.
- 외부 일관성: T1이 커밋을 마친 뒤 T2가 시작했다면 T2의 커밋 타임스탬프가 T1보다 크다(Spanner 논문).

### 2. HLC 계산

- 받기: l' = 1000, l = max(1000, 1040, 1005) = 1040. l == l.m(1040)이고 l ≠ l'이므로 c = c.m + 1 = 1 → (1040, 1).
- 보내기(pt=1006): l' = 1040, l = max(1040, 1006) = 1040 = l' → c = 2 → (1040, 2).
- 서머리 실험 1의 `B recv #0 ... (1040,1)`, `B send #0 ... (1040,2)`와 같다.

### 3. HLC의 성질

- 인과 보존: e → f이면 (l.e, c.e) < (l.f, c.f) (정리 1).
- l ≥ pt (정리 2).
- 유계: |l − pt| ≤ ε (따름정리 1, pt는 자기 물리 시계), c ≤ N·(ε+1) (따름정리 3 — "연속 사건 사이 물리 시계가 최소 한 단위 오른다"는 제약도 쓴다).
- 시계 동기 가정이 필요한 것: 유계성(따름정리 1·3). 인과 보존과 l ≥ pt는 가정 없이 성립한다.

### 4. 앞선 시계의 전파

- 실험: X(pt=15000)의 메시지를 받은 Y(pt=5001)는 (15000, 1)이 되고, 이후 약 10초 동안 l=15000에 묶인 채 c만 2, 3, 4로 오른다. Y의 pt가 15000을 넘어선 뒤에야 (15002, 0)으로 돌아왔다.
- 문제: 그동안 HLC의 물리 성분은 실제 시각보다 최대 약 10초 미래다. "시각 t 기준 스냅샷"·TTL·감사 로그 시각이 틀어진다. 여러 노드로 퍼지면 클러스터 전체가 미래 시각을 쓴다.
- 대처: 받은 타임스탬프가 자기 시계 + 상한을 넘으면 거부·경고(서머리 적용 2의 방어 정책), 시계 앞섬 감시.

### 5. TrueTime

```text
  TT.now()    → [earliest, latest]   진짜 시각이 이 안에 있다
  TT.after(t) → t가 확실히 지났다      TT.before(t) → t가 확실히 안 왔다
```

- ε은 구간 반폭. 운영 환경에서 폴링 주기마다 약 1~7ms 톱니, 대부분 약 4ms(평균 ε̄).
- 톱니 이유: 동기화 직후에는 작고, 다음 폴링(30초)까지 최악 드리프트(200µs/s)를 가정해 ε을 계속 키운다. 30초 × 200µs/s = 6ms가 0~6ms 톱니를 만들고, 마스터와의 통신 지연 약 1ms가 더해진다(논문 §3).

### 6. 외부 일관성 증명

1. `s1 < t_abs(T1 커밋)` — commit wait: TT.after(s1)이 참이 될 때까지 커밋을 보이지 않는다.
2. `t_abs(T1 커밋) < t_abs(T2 시작)` — 가정.
3. `t_abs(T2 시작) ≤ t_abs(T2 서버 도착) ≤ s2` — 인과, start 규칙(s2 ≥ TT.now().latest).
4. 이행성으로 `s1 < s2`.

- 기대 대기: 최소 2ε̄(§4.2.1). Paxos 통신과 겹친다. 실험에서 ε=4ms일 때 평균 8001µs.

### 7. commit wait 시뮬레이션

- ±4ms, ε 4ms, 켬: 0/100000. 시계 오차가 구간 안이므로 1번 단계가 성립한다.
- ±4ms, ε 4ms, 끔: 46940/100000. T1 노드 시계가 앞서고 T2 노드 시계가 뒤처지면 s2 ≤ s1이 된다.
- ±7ms, ε 4ms, 켬: 8432/100000. 구간이 진짜 시각을 포함한다는 가정이 깨져 기다려도 s1이 과거가 아닐 수 있다.
- 비율 자체는 시뮬레이션 분포에 따른 값이다. 요지는 "가정이 맞으면 0, 깨지면 0이 아니다".

### 8. CockroachDB

- 비용 위치: 커밋 쪽 대기 대신, 읽기가 불확실성 구간 안의 미래 쓰기를 만나면 타임스탬프를 올린다(`ReadWithinUncertaintyIntervalError`). 앞선 읽기의 refresh가 통과하면 계속하고, 실패하면 재시도한다. 비차단 범위의 미래 타임스탬프 쓰기는 commit-wait를 한다.
- `--max-offset` 기본 500ms.
- 클러스터 절반 이상의 노드와의 시계 차이가 최대 오프셋의 80%를 넘었다고 감지하면 스스로 종료한다.

### 9. 저장 직후 옛 값

- 확인: 신고 시각 전후의 노드별 시계 오프셋 지표(`chronyc tracking`의 오프셋, CockroachDB 오프셋 지표)가 설정 상한(ε·max-offset)을 넘었는지. 같은 시각 소스·같은 윤초 smearing 방식을 쓰는지.
- 원인: 외부 일관성 장치(commit wait·불확실성 구간)는 "실제 오차 ≤ 상한"을 가정한다. 넘으면 보장이 깨진다.
- 막기: 상한보다 낮은 문턱의 오프셋 알람, 넘는 노드 격리(CockroachDB는 80%에서 자동 종료), 시각 인프라 점검. 상한을 키우면 안전하지만 지연·재시작이 는다.

### 10. VM 이동 뒤 낡은 시계

- 원인: 정지 동안 시계가 멈췄다가 재개 뒤 앞으로 점프한다. 그 사이 노드는 과거 시각으로 읽고 쓴다.
- 감지: `server.clock.forward_jump_check_enabled`로 앞쪽 점프를 알린다.
- 예방: `--clock-device`로 PTP 하드웨어 시계를 쓴다. 이때는 점프가 예상된 무해한 동작이라 점프 검사를 켜지 않는다(CockroachDB FAQ).
