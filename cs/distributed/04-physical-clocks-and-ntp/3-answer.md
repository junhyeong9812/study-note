# distributed/04-physical-clocks-and-ntp — 정답

## 정답

### 1. 벽시계 vs 단조 시계

| | 벽시계 | 단조 시계 |
|---|---|---|
| Linux | `CLOCK_REALTIME` | `CLOCK_MONOTONIC` |
| Java | `System.currentTimeMillis()`, `Instant.now()` | `System.nanoTime()` |
| 뒤로 가나 | 간다(수동 설정·NTP step) | 안 간다 |
| NTP 영향 | 불연속 점프 + 속도 조정 | 속도 조정만 |

- 두 JVM의 `nanoTime()` 차이는 의미가 없다. Java 21 문서: 기준점이 임의이고, 같은 JVM 안에서 얻은 두 값의 차이만 의미가 있다. 다른 JVM은 기준점이 다를 가능성이 크다.

### 2. 3초 되감기 실험

- 실험(libfaketime, Temurin 21.0.12): `currentTimeMillis` 차이 **−1991 ms**, `nanoTime` 차이 **1008 ms**.
  - 계산: 실제 1초 경과 − 3초 되감김 ≈ −2초.
- `Instant.now()`도 벽시계라 끝 시각(…:16.918Z)이 시작(…:18.910Z)보다 앞섰고 `Duration.between`은 음수였다.

### 3. Cloudflare 2017-01-01

- 음수의 출처: RRDNS가 업스트림 리졸버 RTT를 `time.Now().Sub(start)`로 쟀다. 윤초 순간 시간이 1초 뒤로 가 RTT가 음수가 됐다. 당시 Go `time.Now()`는 단조성을 보장하지 않았다.
- panic까지: 측정값을 이동 평균으로 쌓아 몇 번 뒤 평균이 음수가 됐다. 가중치 선택이 그 값을 `rand.Int63n()`에 넣었고, `Int63n`은 음수 인자에 panic한다.
- 영향(보고서 원문): 00:00 UTC 시작, 정점에 DNS 질의 약 0.2%, HTTP 요청 1% 미만이 오류. CNAME 레코드 고객만, 102개 데이터센터 중 일부 머신. 가장 영향이 큰 머신은 90분 안에 패치, 06:45 UTC 종료.
- 수정: 시간이 뒤로 가면 업스트림 성능 기록을 버리고 다시 쌓도록 해 음수가 선택 코드로 새지 않게 했다. 일반 원칙은 경과 시간을 단조 시계로 재는 것(Go 1.9부터 `time.Now()`가 단조 시계 값을 함께 담는다).
- 실험 A의 Java 재현: srtt −100.2 ms → `nextLong(-99)` → `IllegalArgumentException: bound must be positive`.

### 4. NTP 공식

- δ = (T4 − T1) − (T3 − T2), θ = ((T2 − T1) + (T3 − T4)) / 2 (RFC 5905 §8).
- 가는 길 13, 오는 길 10, 진짜 +20: 추정 오차 = (13 − 10)/2 = +1.5 → θ ≈ 21.5 ms. 실험 C 표본 1과 같다(δ = 23 ms).
- 일반적으로 추정 오차 = (가는 길 − 오는 길)/2. 가는 길·오는 길이 같다고 가정한 대가다. 상한은 |오차| ≤ δ/2(계산).

### 5. clock filter

- 최근 8개 표본(`NSTAGE = 8`)을 δ 오름차순으로 정렬해 **δ가 가장 작은 표본**의 θ를 쓴다(RFC 5905 §10).
- 이유: 오차 상한이 δ/2라 지연이 작을수록 비대칭 오차의 **상한**이 작다. 실제 오차가 꼭 작은 것은 아니다(실험 C: δ 23 표본은 +1.5, δ 25 표본은 +0.5). 큐잉으로 한쪽만 막힌 표본은 δ가 커서 자연히 빠진다.
- 실험 C: 단순 평균 24.1 ms(오차 +4.1), clock filter 21.5 ms(오차 +1.5). 한쪽만 막힌 표본(3·6·7)이 평균을 끌었다.

### 6. 드리프트와 NTP 조정

- 200 ppm = 하루 86400초 × 0.0002 ≈ 17초(DDIA 8장: 30초마다 맞추면 6 ms, 하루 한 번이면 17초).
- 속도 조정 한도: DDIA 8장 "최대 0.05%" = 500 ppm. Google 스미어 문서도 "NTP의 500 ppm 최대".
- RFC 5905 참조 설계(§11.3): 오프셋이 125 ms(`STEPT`)보다 작으면 천천히 맞추고(slew), 크면 한 번에 뛴다(step). 단 정상 동기 중에는 큰 오프셋이 `WATCH`(900 s) 동안 이어진 뒤에 뛴다. 시계를 처음 맞출 때(NSET·FSET 상태)는 기다리지 않고 바로 뛴다(Figure 28). 1000 s(`PANICT`)를 넘으면 진단 메시지와 함께 끝내야 한다(SHOULD). 실제 데몬의 기본값은 다를 수 있다.

### 7. 윤초

```text
  UTC   23:59:59 → 23:59:60 → 00:00:00
  POSIX 23:59:59 → 23:59:59(한 번 더) → 00:00:00   ← 커널 방식: 1초 되감음
  smear  하루에 걸쳐 1초를 조금씩 늦게 감음          ← 시계가 뒤로 가지 않음
```

- POSIX 시간은 윤초를 세지 않아 23:59:60을 표현하지 못한다. 커널은 1초를 되감아 같은 초를 두 번 지난다(Cloudflare: "time goes back a second").
- smear는 NTP 서버가 1초를 하루에 펴 발라 클라이언트 시계가 뒤로 가지 않게 한다. 대신 그날은 UTC와 다르다. 윤초를 가운데 둔 정오~정오 선형 스미어면 차이는 윤초 순간에 가장 커서 0.5초다(계산 — Google 문서는 가운데 두는 것이 최대 오프셋을 줄인다고 적는다).
- Google 권장: 정오~정오 24시간 선형 스미어, 속도 변화 약 11.6 ppm(1 s / 86400 s).

### 8. LWW 역전

- A 타임스탬프 1005(진짜 1000 + 5), B 타임스탬프 1003(진짜 1003). LWW는 큰 값 1005를 남긴다 → 최종 `x=1`. 인과적으로 나중인 `x=2`가 사라진다(실험 C).
- 오류 로그는 없다. 데이터가 **조용히** 사라진다(DDIA 8장).

### 9. 한 서버에서만 JWT 거절

- 원인: 그 서버(검증자)의 시계가 느리거나 발급자 시계가 빠르다. `nbf`가 검증자 기준 미래가 된다(실험 C: 30초 어긋남 + leeway 0 → 거절).
- 확인: 양쪽에서 `timedatectl timesync-status`/`chronyc tracking`, 지표 `node_timex_offset_seconds`, 동기 상태.
- 근본: 양쪽 NTP 정상화, 오프셋 알람.
- 완화: 검증에 leeway. RFC 7519 §4.1.4–4.1.5는 시계 어긋남을 위해 "보통 몇 분 이하의 작은 여유"를 둘 수 있다고 한다(MAY).

### 10. 오프셋 −19.48 ms, 지연 188.9 ms

- 비대칭 오차 상한이 δ/2 ≈ 94 ms다. "−19 ms"는 그 정도 폭 안의 추정이라, ms 단위 정밀도를 믿으면 안 된다. 이 표본 하나로는 실제 오프셋이 약 −114 ~ +75 ms 어디든 될 수 있다(계산). 수십 ms 이내라고 보장할 수 없다.
- `Frequency: +15.189ppm`은 진동자 속도 보정값이다.
- `systemd-timesyncd`의 한계: SNTP만 구현한다(man 페이지). 큰 어긋남은 step, 작은 차이는 천천히 맞춘다. 여러 서버를 겹쳐 이상치를 빼는 완전한 NTP(selection·cluster)가 필요하면 chrony·ntpd를 쓴다.
