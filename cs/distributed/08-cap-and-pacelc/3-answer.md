# distributed/08-cap-and-pacelc — 정답

## 정답

### 1. C·A·P 정의

- C: 원자적(= 선형화) 읽기/쓰기 객체. 모든 연산이 한 순간에 일어난 것처럼 보이는 전체 순서가 있다.
- A: 고장 나지 않은 노드가 받은 모든 요청이 결국 응답을 받는다.
- P: 네트워크가 노드 사이 메시지를 임의로 많이 잃을 수 있다.
- ACID의 C와 다르다. Gilbert–Lynch 2002 각주 3: ACID의 일관성은 트랜잭션에 대한 것이고, 원자적 일관성은 개별 요청/응답 연산들의 순서(실행 이력)에 대한 성질이다. 트랜잭션 묶음이 아니라 연산 하나하나가 실시간 순서를 지키는 전체 순서에 놓일 수 있느냐를 본다.

### 2. 불가능성 그림

```text
  G1: [n1] ──✘── [n2] :G2      (G1↔G2 메시지 모두 유실)
  client → n1: write(x=1) → OK
  client → n2: read(x)
    A를 지키면 n2가 답해야 함 → n1 소식이 없으니 x=0 → 쓰기가 끝난 뒤의 읽기가 옛 값 = C 위반
    C를 지키면 n2는 x=1을 알아야 함 → 메시지가 안 옴 → 답할 수 없음 = A 위반
```

- 가정: 비동기 네트워크 모델(시계 없음, 지연 상한 없음, 메시지 유실 가능)(§3.1 정리 1). 시계와 지연 상한이 있는 부분 동기 모델에서도 유실이 있으면 같은 결론이다(§4.2 정리 2).

### 3. "CA"의 무의미함과 CAP의 범위

- 분할은 고르는 것이 아니라 일어나는 일이다. "CA"는 분할이 없다고 가정했다는 뜻이고, 분할이 나면 무엇을 할지 정의되지 않았다.
- CAP이 다루지 않는 것(Kleppmann 2015)
  - 여러 객체 트랜잭션(대상은 레지스터 하나).
  - 분할 밖의 장애(노드 다운, 디스크 가득 참, 버그).
  - 지연(A는 "언젠가" 답하면 된다).

### 4. etcd 소수 쪽 노드

(실험, etcd 3.6.5 3노드, 2026-10-01)

```text
소수 쪽(etcd3) 직렬화 읽기(--consistency=s): v1  [89ms]
소수 쪽(etcd3) 선형화 읽기(기본): Error: context deadline exceeded  [3097ms]
소수 쪽(etcd3) put v3: Error: context deadline exceeded  [3086ms]
```

- 기본 읽기·쓰기: 리더·과반과 통신할 수 없어 3초 타임아웃으로 실패.
- `--consistency=s`: 로컬 상태로 바로 답한다. 다수 쪽이 이미 v2로 바꿨는데 v1.
- 기본 경로로 보면 살아 있는 노드가 답하지 않으므로 CAP의 A가 아니다. 직렬화 읽기는 답하지만 선형화가 아니다. 같은 노드가 옵션에 따라 다른 선택을 한다.

### 5. Redis `min-replicas-to-write`

(실험, Redis 7.4.9, 2026-10-01 — 발췌)

```text
min-replicas-to-write=0 ... t=+15s 리더 SET → OK | 복제본 GET → before
min-replicas-to-write=1 ... t=+9s 리더 SET → OK
                            t=+12s 리더 SET → NOREPLICAS Not enough good replicas to write.
```

- 0(기본): 분할 내내 쓰기를 받는다. 복제본은 내내 옛 값 `before`를 답한다.
- 1: 지연이 10초 이하인 복제본이 1개 미만이 되자(끊긴 지 약 10초 뒤) `NOREPLICAS`로 거절했다.
- 유실 창: 끊긴 직후부터 약 10초 동안 받은 쓰기(`after-0`·`after-3`·`after-6`·`after-9` 네 건)는 복제본에 없는데 OK였다. 복제가 비동기라 "복제본이 이 쓰기를 받았다"를 확인하지 않는다. 문서도 유실 창을 묶는 최선 노력이라고 적는다.

### 6. PACELC의 E와 분류

- E(평시 L vs C)는 **데이터를 복제하는 시스템**에만 해당한다(Abadi 2012).
- Dynamo·Cassandra·Riak 기본값: PA/EL. 분할 때 가용성, 평시엔 지연을 위해 일관성을 낮춘다. R+W를 키우면 평시 일관성이 늘지만 R+W>N이어도 Gilbert–Lynch 의미의 완전한 일관성은 아니다.
- PNUTS: PC/EL. 평시엔 어느 복제본에서나 읽어 일관성을 낮추고, 분할 때 소수 쪽에 갇힌 마스터의 데이터는 갱신을 막는다.
- PC/EL은 "분할 때 더 일관해진다"는 뜻이 **아니다**. 분할 때 기본 수준보다 더 낮추지 않는다는 뜻이다.

### 7. 평시 지연 차이

(실험, etcd 3.6.5 3노드, 한 호스트, 2026-10-01)

```text
sn-dw-w06-etcd1  선형화 읽기 p50 1.93ms ... | 직렬화 읽기 p50 1.17ms ...
sn-dw-w06-etcd2  선형화 읽기 p50 1.49ms ... | 직렬화 읽기 p50 1.00ms ...
sn-dw-w06-etcd3  선형화 읽기 p50 1.65ms ... | 직렬화 읽기 p50 0.92ms ...
```

- p50 차이 0.5~0.8ms였다(재실행 0.7~1.4ms, 실행마다 다르다). 방향(직렬화가 더 빠름)은 세 노드 모두 같았다.
- 선형화 읽기는 리더 확인(ReadIndex) 왕복이 더 든다. 리전에 흩어지면 그 왕복이 수십 ms가 되어 차이도 그만큼 커진다.
- 이유: 끝난 쓰기를 다른 곳의 읽기가 보려면 둘 사이 통신이 필요하고, 누군가 그것을 기다려야 한다(6.5840 L8).

### 8. 특정 영역만 타임아웃

- 원인: 그 영역의 etcd 노드가 분할로 소수 쪽에 갇혔다. 프로세스는 살아 있지만 선형화 읽기·쓰기는 리더·과반 없이 답하지 않는다. 설계대로의 C 선택이다.
- 대처
  - 클라이언트에 엔드포인트 여러 개를 주어 다수 쪽 노드로 옮기게 한다.
  - 옛 값이 괜찮은 읽기만 `--consistency=s`(직렬화)로 바꾼다.
  - `etcdctl endpoint status`·`endpoint health`로 어느 노드가 고립됐는지 본다.

### 9. 끊긴 걸 모르는 복제본

- Redis 복제본은 링크 끊김을 `repl-timeout`(이 컨테이너 60초) 동안 알아채지 못할 수 있다. 실험에서 분할 15초 내내 `up`이었다.
- 그동안 복제본은 옛 값을 경고 없이 답한다. 앱은 `master_link_status`만 보고 "정상"으로 판단한다.
- 끊김 탐지에도 시간이 든다는 점이 "분할인가 느린가"를 구분하기 어려운 이유다(02번).

### 10. GitHub 2018-10-21

- 43초 분할: Raft 기반 Orchestrator의 정족수 쪽(서부·클라우드)이 진행해 MySQL 리더를 서부로 옮겼다. 정족수로 결정한 것은 **리더 선출(제어)** 이다. MySQL 데이터는 C가 아니었다. 동부에서 받았지만 서부로 복제되지 못한 쓰기가 남아 수동 조정이 필요했다(해석).
- 복구: 서부에 30분 넘게 쓰인 데이터를 지키려고 forward로 갔다. 동부 앱은 DB 호출 대부분이 대륙 횡단 왕복이 됐다. 평시 L 대신 C를 택한 것이다(해석). 이 원거리 지연은 10-22 11:12 UTC에 모든 리더가 동부로 돌아오며 끝났고, 그 뒤엔 몇 시간 뒤처진 읽기 복제본이 옛 데이터를 보여 줬다. 24시간 11분은 이를 합친 전체 저하 기간이다. 원문: "the extended degradation of service was worth ensuring the consistency of our users' data".
- 재발 방지책: Orchestrator가 리전 경계를 넘어 리더를 승격하지 않게 설정 변경.
