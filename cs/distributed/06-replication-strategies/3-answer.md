# distributed/06-replication-strategies — 정답

## 정답

### 1. 복제의 이유와 어려운 점

- 이유(DDIA 5장 서두)
  - 가용성: 노드 하나가 죽어도 다른 사본으로 계속 쓴다.
  - 지연: 사용자 가까이 사본을 둔다.
  - 읽기 확장: 읽기를 여러 사본에 나눈다.
- 어려운 점은 복사가 아니라 **바뀌는 데이터**다. 쓰기를 누가 받고, 변경을 어떤 순서로 다른 사본에 퍼뜨리나. 이 답이 세 전략으로 갈린다.

### 2. 세 전략 비교

```text
 단일 리더     client → [L] → F1, F2        순서: L이 정함        충돌: 없음
 다중 리더     client → [L1] ⇄ [L2] ← client  순서: 리더마다 따로   충돌: 있음(복제 도착 때 발견)
 리더리스      client → A, B, C (W개 확인)    순서: 정하는 곳 없음  충돌: 있음(버전으로 판정)
```

- 단일 리더는 페일오버가 필요하고, 다중 리더·리더리스는 충돌 해소가 필요하다.

### 3. 쓰고 바로 팔로워에서 읽기

(실험, Redis 7.4.9 리더 1 + 복제본 1, 2026-10-01)

```text
== 직결(지연 프록시 없음) ==
[1] SET(리더) 직후 GET(팔로워): 300회 중 옛 값 0회 (0.0%)
== 복제 링크 50ms 지연 프록시 ==
[1] SET(리더) 직후 GET(팔로워): 300회 중 옛 값 300회 (100.0%)
[2] SET + WAIT 1 100 뒤 GET(팔로워): 300회 중 옛 값 0회, WAIT가 0을 돌려준 횟수 0
```

- 직결이면 같은 호스트라 복제가 클라이언트 왕복보다 빨라 0번이었다.
- 50ms 지연이면 300번 모두 옛 값이었다. 클라이언트의 다음 요청이 복제보다 먼저 도착한다.
- `WAIT 1 100`은 복제본 1개가 받았다고 확인할 때까지 기다린다. 그 뒤 읽기는 0번이었다. 대신 쓰기마다 그만큼 늦어진다.

### 4. 비동기 페일오버 유실

(실험, Redis 7.4.9, 복제 링크 3000ms 지연 프록시, 2026-10-01)

```text
리더 OK 응답 수: 1000
승격 직후 새 리더(옛 팔로워)의 w06:o:* 키 수: 0
옛 리더의 w06:o:* 키 수: 1000
```

- 0건이 남았다. 리더는 복제를 기다리지 않고 OK를 줬고, 3초 늦는 링크로는 아무것도 도착하지 않은 상태에서 승격했다.
- 50ms에서 1000건이 남은 것은 마지막 `SET`과 승격 명령 사이(셸이 `docker exec`를 다시 띄우는 시간)에 복제가 따라잡았기 때문이다.
- 결론: 잃는 양은 **승격 순간의 지연**에 달렸다. 평소 지연이 작아도 유실이 없다는 보장이 아니다.

### 5. LWW의 수렴과 유실

(실험, Java 21 시뮬레이션, 2026-10-01)

```text
LWW    B 시계    +0ms | OK 받은 추가 182 | 최종 A 154개, B 154개, A==B true | 조용히 사라짐 28
LWW    B 시계  -500ms | OK 받은 추가 182 | 최종 A 100개, B 100개, A==B true | 조용히 사라짐 82
```

- LWW는 타임스탬프가 큰 쓰기 하나를 남긴다. 두 리더가 같은 값이 되므로 "수렴"은 맞다.
- 진 쓰기는 클라이언트가 이미 OK를 받았는데 **에러 없이** 버려진다. 182건 중 28건이 그랬다.
- 시계가 늦은 리더(B, −500ms)에서 나중에 쓴 값은 작은 타임스탬프 때문에 진다. 사라진 수가 82건으로 늘었다.

### 6. 충돌을 다루는 네 방법

| 방법 | 내용 | 맞는 데이터 |
|---|---|---|
| 충돌 회피 | 키마다 홈 리더 하나로만 쓰기 | 대부분의 사용자 소유 데이터 |
| 수렴(LWW) | 큰 타임스탬프·ID가 이김 | 마지막 값만 의미 있는 데이터 |
| 병합 | 합집합·CRDT로 합침 | 추가만 하는 집합, 카운터 |
| 앱에 맡기기 | 충돌 판을 모두 보관, 읽을 때 앱이 고르거나 합침(Dynamo 장바구니는 합침) | 규칙을 앱만 아는 데이터 |

- 장바구니 "항목 추가": 병합(합집합)이 맞다. 시뮬레이션에서 UNION은 0건 유실이었다. 삭제까지 있으면 단순 합집합은 지운 항목이 되살아나므로 OR-Set 같은 CRDT가 필요하다(24번).
- 닉네임 변경: 마지막 값만 의미가 있어 LWW로 충분할 수 있다. 다만 시계가 어긋난 리더의 변경이 지는 문제는 남으니, 홈 리더(충돌 회피)가 더 안전하다.

### 7. 리더리스의 오래된 값

- 원인: 장애 중 쓰기를 놓친 복제본이 옛 값을 그대로 들고 있다. R+W≤N인 읽기(예: R=1)가 그 복제본에 가면 옛 값이 나온다. 힌트(hinted handoff)는 보관 기간이 지나면 버려진다(Cassandra 5.0 `max_hint_window` 기본 3시간).
- 읽기 복구만으로 부족한 이유: 읽힌 키, 읽힌 복제본만 고친다.

(실험, Java 21 시뮬레이션 N=3, 2026-10-01)

```text
[B] 복구 없음          1바퀴 옛 값  274/3000  2바퀴(R=1) 옛 값  283/3000
[B] 읽기 복구(R=2)     1바퀴 옛 값   34/3000  2바퀴(R=1) 옛 값  108/3000
[B] anti-entropy   1바퀴 옛 값  274/3000  2바퀴(R=1) 옛 값    0/3000
```

- 대처: 정기 anti-entropy(Cassandra `nodetool repair`, 기본 gc grace 10일이면 7일 안에 전 노드). 중요한 읽기는 R+W>N(09번).

### 8. 확인된 쓰기 유실 진단

- 지표: 새 리더의 마지막 복제 위치가 옛 리더보다 뒤다(Redis 오프셋, PostgreSQL LSN, MySQL GTID 집합). 옛 리더가 돌아오면 새 리더에 없는 쓰기를 갖고 있다.
- 재발 방지
  - 쓰기 확인: 준동기·동기 복제, Kafka `acks=all` + `min.insync.replicas`, Redis `WAIT`(이번 쓰기의 복제 확인).
  - 쓰기 거부 조건: Redis `min-replicas-to-write`·`min-replicas-max-lag` — 최근 응답한 복제본이 모자라면 쓰기를 거부해 유실 창을 줄인다. 이번 쓰기의 도착을 기다리지는 않는다.
  - 승격 후보는 가장 앞선 팔로워.
- GitHub 2018-10-21: 43초 연결 끊김 동안 Orchestrator가 리더를 서부 데이터센터로 옮겼다. 동부에서 받았지만 서부로 복제되지 못한 쓰기가 남았고, 가장 바쁜 클러스터 하나에 954건이었다. binlog를 꺼내 대조했다(분석 글 2018-10-30).

### 9. 단일 리더에 충돌이 없는 이유

- 리더 하나가 쓰기 순서를 정해 복제 로그에 적는다. 팔로워는 그 로그를 같은 순서로 재생한다.
- 상태 기계 복제: 같은 초기 상태 + 같은 순서의 결정적 연산 = 같은 결과. 순서가 하나라 "동시에 다르게 바꾸기"가 생기지 않는다.
- 문장 기반 로그는 연산이 결정적이지 않으면 깨진다. `RAND()`·`UUID()` 같은 비결정 함수, `ORDER BY` 없는 `LIMIT`이 팔로워에서 다른 결과를 낼 수 있다(MySQL 8.4는 `NOW()`는 문장 기반으로도 올바르게 복제한다고 적는다). 그래서 행 기반(논리) 로그를 쓴다(DDIA 5장, [database/32](../../database/32-replication-leader-follower/2-summary.md)).
