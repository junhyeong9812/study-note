# distributed/33-collaborative-editing-ot-and-sequence-crdt — 정답

## 정답

### 1. 변환 없이 적용

- 사용자 1: "abXcd" + ins(2, Y) → "abYXcd".
- 사용자 2: "abYcd" + ins(2, X) → "abXYcd".
- 두 문서가 다르다(발산). 정수 위치는 상대 연산이 앞에 끼어들면 가리키는 글자가 바뀐다.

### 2. OT 변환

- 사이트 1(X, 번호 1)은 Y를 받아 `T(ins(2,Y), ins(2,X))`: 위치가 같고 Y의 사이트(2)가 더 크므로 +1 → ins(3, Y). "abXcd" → "abXYcd".
- 사이트 2는 X를 받아 `T(ins(2,X), ins(2,Y))`: X의 사이트(1)가 작으므로 그대로 ins(2, X). "abYcd" → "abXYcd".
- 둘 다 "abXYcd". 실험 출력 `tieBreak=true  site1="abXYcd"  site2="abXYcd"  수렴`.

### 3. TP1·TP2

- TP1: `a ∘ T(b, a) ≡ b ∘ T(a, b)`. 두 동시 연산을 어느 순서로 적용해도 같은 문서. 연산이 사이트마다 다른 순서로 실행될 수 있으면 필요하다.
- TP2: 세 번째 연산을 서로 다른(하지만 동등한) 두 연산 순서에 대해 변환해도 같은 결과. 같은 연산이 서로 다른 문맥에서 변환될 수 있으면 필요하다.
- 중앙 서버(Jupiter): 모든 연산이 중앙 변환 서버를 거친다. Wikipedia 비교표 분류로는 제어 알고리즘이 TP2를 맡고 변환 함수는 TP1만 만족하면 된다.
- + ack 대기(Wave): 클라이언트가 확인을 받을 때까지 다음 연산을 보내지 않고 모아 둔다. 클라이언트가 서버의 변환 경로를 추론할 수 있어 서버 구현이 더 단순해진다(Wave 백서).

### 4. 동률 버그 예측

- 실험: 같은 위치 동시 삽입 354쌍이 전부 발산(354건), 그 밖의 경우는 0건.
- 늦게 발견되는 이유: 특정 경우(같은 위치·같은 순간)에서만 드러나고, 평소 편집에서는 정상 동작한다. 드러나면 에러가 아니라 사용자마다 다른 문서로 남는다.

### 5. RGA류와 Yjs Item

```text
  글자 = (id=(램포트, 사이트), 왼쪽 기준 글자 id)
  root ─ H ─ i ─┬─ " Alice"
                ├─ " Bob"
                └─ "!"
  같은 기준을 가진 형제는 id 큰 쪽이 앞, 트리를 깊이 우선으로 읽으면 문서
```

- Yjs `Item`: `ID(clientID, clock)`(램포트 타임스탬프), 삽입 당시 왼쪽 이웃 `origin`과 오른쪽 이웃 `originRight`. 문서 순서로 `left`·`right` 링크가 있는 이중 연결 리스트에 들어간다. 같은 클라이언트가 연달아 친 글자는 `Item` 하나로 합친다.

### 6. 수렴 vs 끼워짐

- 수렴: 같은 연산을 받은 복제본이 같은 문서. CRDT의 정의다.
- 끼워짐 없음: 동시에 입력한 연속 텍스트가 섞이지 않고 덩어리로 남는다. 수렴과 별개다. 실험 3의 분수 위치 방식은 모든 실행에서 수렴했지만 "Hi B oAlbice!"처럼 섞였다.
- Kleppmann 외 2019: Logoot·LSEQ는 글자 단위 끼워짐이 생긴다. RGA는 그 형태는 없지만 비순차 삽입(예: 거꾸로 입력)에서 약한 끼워짐이 있다.

### 7. Yjs 상태 크기

- 실험(GC 켬): (a) 끝에 이어 쓴 1만 글자 → 다 지운 뒤 16바이트. (b) 무작위 위치 1만 글자 → 다 지운 뒤 78586바이트. 바이트 수는 clientID·무작위 위치에 따라 실행마다 다르다(점검 재실행: 22~24 B vs 158498 B). 경향은 같다.
- 이유: (a)는 하나의 run(`Item` 하나)이라 지우면 GC 구조체 하나로 줄어든다. (b)는 글자마다 따로 `Item`이 생겨, GC가 내용은 버려도 순서를 위한 구조체(툼스톤) 1만 개는 남긴다.

### 8. 커서와 프레즌스

- 정수 커서는 원격 사용자가 앞에 글을 넣으면 다른 글자를 가리킨다. 실험: 문서 "xxac"에서 정수 1 → "x|xac".
- 해법: `RelativePosition`(글자 id 기준). 실험에서 원래 `c` 앞("xxa|c", 인덱스 3)을 유지했다.
- 프레즌스는 일시적 상태다. 문서 CRDT에 넣으면 커서 이동마다 영구 기록·툼스톤이 쌓인다. y-protocols awareness처럼 별도 채널로 보내고, 30초 갱신이 없으면 지운다.

### 9. Figma

- OT를 쓰지 않은 이유(블로그): 구현이 어렵고 상태 조합이 폭발한다. 텍스트 편집기가 아니라 디자인 도구라 그 힘이 필요 없었다.
- 대신: 서버가 권위를 갖는 중앙 구조에서 객체 속성마다 마지막으로 서버에 도착한 값이 이기는 LWW 레지스터 비슷한 방식, 객체 생성·삭제는 LWW 집합 비슷한 방식, 자식 순서는 분수 인덱싱.
- 같은 텍스트 값 동시 편집: "B"를 하나는 "AB", 하나는 "BC"로 고치면 결과는 둘 중 하나이고 "ABC"는 되지 않는다.

### 10. 문서가 부푼다

- 원인: 지운 글자의 구조체(툼스톤)와 편집 이력이 남는다. 흩어진 편집은 run으로 합쳐지지 않아 더 크다. Local-first 논문: 글자 단위 이력이 쌓이고, 몇 달 뒤 접속할 사람이 있을 수 있어 쉽게 자르지 못한다.
- 대처: GC를 켠다(지운 내용 폐기). 상태 크기 / 글자 수 비율을 지표로 감시한다. 모든 참여자가 특정 시점 이후 상태를 가졌다고 확인되면 그 시점으로 새 문서를 만들어 이력을 끊는다.
- 대가: 끊은 시점 이전 상태에서 오프라인 편집하던 클라이언트는 병합할 수 없게 된다. 버릴지, 수동 병합할지 정책이 필요하다.
