# distributed/15-saga — 정답

## 정답

### 1. 왜 사가인가, 무엇을 잃나

- 서비스마다 DB가 다르고, 결제사 같은 외부 시스템은 XA 참가자가 아니다. 2PC는 참가자 전원이 살아 있어야 진행하고, in-doubt 동안 락을 쥔다(14번).
- 사가는 각 걸음을 자기 DB에서 바로 커밋하고, 실패하면 보상으로 의미상 되돌린다. 락을 오래 쥐지 않는다.
- 잃는 것: **격리(I)** — 중간 상태가 남에게 보인다. **자동 원자성(A)** — 롤백 대신 보상을 직접 설계해야 한다(microservices.io "Saga"의 drawbacks).

### 2. 사가의 보장과 원래 문제

- 보장: `T1, T2, …, Tn` 전부 실행 **또는** `T1, …, Tj, Cj, …, C1`.
- 원래 문제: 단일 DB에서 오래 걸리는 트랜잭션(LLT)이 자원·락을 오래 쥐어 짧은 트랜잭션들을 크게 지연시키는 것. 사가는 LLT를 다른 트랜잭션과 끼워 실행할 수 있는 짧은 트랜잭션들로 쪼갠다.

### 3. 절대값 보상의 결과

- 기대보다 **많다.** 실험(PostgreSQL 17.11, 사가 200·스레드 8)에서 다섯 번 돌려 +56~+63이 나왔다.
- 실행마다 다르다. 어떤 사가의 차감이 언제 끼어들었는지에 따라 덮어써지는 양이 달라진다.
- 이유: 보상이 "읽었던 옛 값"을 쓰면서 그사이 다른 사가가 한 차감을 지운다. 원논문 1절(서론)이 좌석 수 예로 바로 이것을 금지한다.

### 4. 중복 보상

- 최종 재고 920(기대 860보다 +60). 실패한 60건이 모두 두 번 복구됐다.
- 막는 방법: 보상 ID(사가 id + 걸음)를 처리 기록 표에 PK로 넣고, 새로 들어갔을 때만 복구한다. 실험에서 +0.
- 같은 로컬 트랜잭션이어야 하는 이유: 기록만 커밋되고 복구 전에 죽으면 복구가 영영 안 된다. 복구만 커밋되고 기록 전에 죽으면 다음 재전달 때 또 복구된다. 둘을 한 트랜잭션에 넣어야 "한 번만"이 된다.

### 5. 역방향 vs 순방향 복구

- 역방향: 실행된 Tj…T1을 Cj…C1로 보상한다. 보상 트랜잭션이 필요하다.
- 순방향: 실패 지점부터 남은 트랜잭션을 다시 실행해 끝까지 간다. 원논문에 따르면 어디까지 했는지(save-point)와 남은 트랜잭션의 코드를 안정적으로 보관해야 한다.
- 실무에서는 섞는다. 피벗 전은 역방향, 피벗 뒤는 순방향(재시도).

### 6. 세 종류의 트랜잭션과 메일 발송

- 보상 가능: 실패하면 보상으로 되돌린다(재고 예약, 결제 승인).
- 피벗: 돌아올 수 없는 지점. 성공하면 사가는 끝까지 가야 한다(결제 확정 등).
- 재시도: 피벗 뒤. 멱등하게 만들어 성공할 때까지 재시도한다.
- 메일 발송은 보상할 수 없다(정정 메일을 또 보낼 뿐). 그래서 **피벗 뒤 재시도 구간**에 둔다.

### 7. 상태 기계와 STUCK

```text
  STARTED → RUNNING → PAST_PIVOT → COMPLETED
               │ 실패
               ▼
          COMPENSATING → COMPENSATED
               │ 보상이 계속 실패
               ▼
             STUCK
```

- 원논문 6절: 보상 코드에 버그가 있으면 다시 돌려도 같은 오류가 나서 시스템이 "stuck"이 된다.
- STUCK에서 할 일: 알림을 보내고, 사람이 처리할 수 있게 상태·마지막 오류를 남긴다. 조용히 넘기지 않는다.

### 8. 재고가 실제보다 많을 때

- 후보: 절대값 보상(옛 값 복원)이 동시 사가의 차감을 덮어쓴다. 또는 보상이 중복 실행된다.
- 확인
  - 보상 코드가 `SET qty = ?`(값 덮어쓰기)인지 `SET qty = qty + ?`인지.
  - 같은 사가 id의 보상 로그가 두 번 이상 있는지.
  - 취소가 몰린 시간대에 차이가 커지는지(동시성 의존이면 그렇다).
- 대처: 상대 연산 + 보상 ID 멱등. 값 비교가 꼭 필요하면 버전 조건부 갱신.

### 9. 격리 부재의 이상 현상과 대응

| 이상 현상 | 대응책 |
|---|---|
| lost update — 한 사가가 다른 사가의 변경을 덮어씀 | commutative updates(교환 가능한 상대 연산), reread values(갱신 직전에 다시 읽어 바뀌었으면 중단·재시작) |
| dirty read — 다른 사가가 아직 끝내지 않은(보상될 수 있는) 변경을 읽음 | semantic lock(`PENDING` 같은 진행 중 표시를 보고 판단), pessimistic view(위험한 갱신을 재시도 트랜잭션 쪽으로 옮기도록 단계 순서를 바꿈) |
