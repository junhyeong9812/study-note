# distributed/01-why-distributed-and-fallacies — 정답

## 정답

### 1. 분산의 이유와 대가

- 6.5840 L1(2026)의 네 가지
  - 병렬 처리로 용량을 늘린다.
  - 복제로 장애를 견딘다.
  - 장치의 물리적 위치에 맞춘다(센서 등).
  - 격리로 보안을 높인다.
- 대가: **부분 실패** — 일부만 고장 나고 나머지는 멀쩡한 상태. 같은 강의는 어려움으로 동시성·복잡한 상호작용·성능 병목도 함께 꼽는다.

### 2. 한 대 / 슈퍼컴퓨터 / 인터넷 서비스

- 한 컴퓨터: 내부 오류가 나면 틀린 결과를 내기보다 통째로 멈추도록 설계한다(커널 패닉). "되거나 안 되거나"(DDIA 8장).
- 슈퍼컴퓨터: 한 노드가 고장 나면 작업 전체를 멈추고 체크포인트에서 다시 시작한다. 부분 실패를 **전체 실패로 키워** 다룬다.
- 인터넷 서비스가 못 하는 이유
  - 온라인이라 멈추면 안 된다.
  - 범용 장비 수천 대라 늘 무언가는 고장 나 있다. 다 멈추고 기다리면 일을 못 한다.
  - 그래서 부분 실패를 견디는 코드를 소프트웨어로 짠다.

### 3. 8가지 오류

1. 네트워크는 믿을 만하다 2. 지연은 0이다 3. 대역폭은 무한하다 4. 네트워크는 안전하다 5. 토폴로지는 바뀌지 않는다 6. 관리자는 한 명이다 7. 전송 비용은 0이다 8. 네트워크는 균질하다

- 코드 모양 예
  - 1번: 타임아웃 없는 원격 호출, 멱등 키 없이 재시도하는 결제 호출.
  - 2번: 루프 안의 원격 호출(항목 수만큼 왕복).
  - 5번: 설정 파일에 IP 하드코딩, 이름 조회 결과를 영원히 캐시.
  - (그 밖에) 3번: 페이지네이션 없는 목록 API. 4번: 내부망이라 평문 HTTP. 8번: 롤링 배포 중 구·신 메시지 형식 불일치.

### 4. 응답이 없을 때의 여섯 경우

```text
  ① 요청 ──X                       요청 유실
  ② 요청 ──[큐 대기]────→           늦게 도착
  ③ 요청 ──────────→ ✝             상대가 죽어 있음
  ④ 요청 ──────────→ (멈춤…)        상대가 잠시 멈춤(GC 등), 나중에 응답
  ⑤ 요청 ──────────→ 처리 완료 ──X  응답 유실
  ⑥ 요청 ──────────→ 처리 완료 …[큐 대기]… 응답 지연
```

- 요청자가 보는 것은 모두 "아직 응답 없음" 하나다(DDIA 8장 "Unreliable Networks"의 여섯 경우 목록, 그림 8-1은 그중 세 경우).
- 상대가 일을 한 경우: ⑤·⑥은 확실히 했다. ②·④는 나중에 할 수 있다. 그래서 타임아웃 뒤에도 "안 했다"고 단정할 수 없다.

### 5. 타임아웃 없음 vs 1초

- 타임아웃 없음: 실험에서 호출 스레드가 1~5초 내내 `WAITING`이었다. Java 21 문서대로 타임아웃을 안 주면 "영원히 막힌다". 연결은 성립했으니 오류도 오지 않는다.
- 1초: `1002 ms 뒤 HttpTimeoutException: request timed out`. 5초 시점에는 이미 예외를 받고 다음 일을 할 수 있다.
- 단, 1초 타임아웃은 "실패"가 아니라 "모름"이다(4번 ②·④·⑤·⑥).

### 6. 왕복 1000번 vs 1번

- 실험(같은 호스트 Docker 브리지, Redis 7.4.9): `GET` 1000번 55.5 ms(왕복당 55.5 µs), `MGET` 1번 1.58 ms → 약 35배. 세 번 돌려 23~43배였다. 프로세스 안 `HashMap`은 1 ms 미만.
- 다른 대륙이면 왕복 하나가 수백 ms다(etcd 문서 예: 미국–일본 350~400 ms). 1000번 왕복은 수백 초가 되고, 묶음 1번은 왕복 한 번 + 처리 시간이다(계산). 차이는 더 벌어진다.

### 7. `connectTimeout`만으로는 부족하다

- Java 21 문서: `connectTimeout`은 **새 연결을 맺어야 할 때** 연결 단계에 거는 상한이다. 재사용 연결에는 걸릴 일이 없다(해석).
- 연결이 맺어진 뒤 응답을 기다리는 시간은 `HttpRequest.timeout`이 맡는다. 이것을 안 주면 영원히 기다린다.
- 실험의 서버도 연결은 즉시 받아 줬다. 연결 타임아웃은 한 번도 걸리지 않는다.

### 8. 세 목표의 상충

- 내결함성·일관성·성능.
- 내결함성은 복제본에 데이터를 보내야 하고, 일관성은 캐시가 최신인지 물어봐야 한다. 둘 다 통신이다.
- 통신은 느리고 규모를 키우기 어렵다. 그래서 성능과 충돌한다.
- 흔히 포기하는 것: 일관성 일부. 예: `read(x)`가 가장 최근 `write(x)`를 못 볼 수 있다(6.5840 L1).

### 9. 페일오버 뒤 옛 IP

- 5번 착각("토폴로지는 바뀌지 않는다").
- 확인
  - 설정에 IP가 박혀 있나, 이름인가.
  - 이름이면 JVM 이름 캐시 시간. Temurin 21 `java.security` 주석: 보안 관리자가 없으면 성공한 조회 30초, 실패한 조회 10초(`networkaddress.cache.negative.ttl=10`).
  - 커넥션 풀이 옛 연결을 계속 쥐고 있나(최대 수명 설정).
- 막는 법: 이름으로 접속, 캐시 시간을 페일오버 목표 시간에 맞춤, 풀 연결의 최대 수명, TCP keepalive·user timeout으로 반쯤 열린 연결 정리(network/21).
