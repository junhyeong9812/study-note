# distributed/36-distributed-incidents — 질문

## 질문

1. (왜) 43초 네트워크 단절이 왜 24시간 11분의 서비스 저하가 됐나? GitHub 보고서의 사실과 이 노트의 해석을 구분해, 분할 → 정족수 결정 → 결정의 대가 → 복구의 꼬리 순서로 설명하라.
2. (경계) GitHub 사건에서 Orchestrator의 Raft 정족수는 무엇을 막아 주었고, 무엇은 판단하지 못했나? 보고서가 든 원인 진술과 후속 조치는?
3. (연결) GitHub 복구 중 10-22 11:12 UTC 이후 사용자가 "요청마다 다른 데이터"를 본 이유는? 이것은 어떤 일관성 보장의 위반인가? 복구 예상 시간이 빗나간 이유와 13:15에 한 조치는?
4. (장애 진단) 장애가 끝나 밀린 웹훅을 처리하는데 일부가 사라진다. GitHub 사건에서 이 일이 어떻게 일어났고(수치 포함), 평시에 합리적인 어떤 장치가 복구 때 해가 됐나? 대처는?
5. (그림) Cloudflare RRDNS에서 음수가 생겨 panic이 나기까지의 코드 경로를 그려라. 음수가 측정 순간이 아니라 "조금 뒤"에 터진 이유는? 원문이 밝힌 근본 원인과 수정은?
6. (경계) Go 1.9 이후라면 Cloudflare 코드의 `time.Now().Sub(start)`는 어떻게 동작하나? Java에서 같은 실수를 피하려면 무엇을 쓰나? 그래도 음수 방어를 두는 이유는?
7. (그림) AWS EBS 2011 재미러링 폭풍의 되먹임 고리를 그려라. 방아쇠, 노드의 판단, 악화 요인 둘, 그리고 사고가 다른 가용 영역의 API까지 번진 경로를 포함하라.
8. (연결) EBS는 재미러링 중 볼륨 접근을 막았고, RDS 다중 AZ 인스턴스 2.5%는 자동 페일오버하지 않았다. 둘은 각각 분산 시스템의 어떤 선택을 보여 주나? AWS가 밝힌 재발 방지 중 재시도 로직 변경의 두 방향은?
9. (예측) 이 노트의 유체 모델(DB 300 QPS, 1초 타임아웃 + 재시도 1회, 10초 단절)에서 부하 140 + 재시도, 280 + 재시도, 280 + 재시도 끔의 세 경우는 단절 뒤 각각 어떻게 되나? 280 + 재시도에서 시도율은 얼마로 수렴하나? 왜 그런가?
10. (장애 진단) 사후 분석이 "네트워크 단절이 원인, 조치 완료"로 닫혔는데 몇 달 뒤 배포를 계기로 같은 모양의 장애가 났다. metastable 관점에서 무엇을 놓쳤나? Bronson 외와 Huang 외가 말하는 근본 원인·대응·특성 지표·숨은 용량을 써서 답하라.
