# distributed/36-distributed-incidents — 정답

## 정답

### 1. 43초가 24시간 11분이 된 사슬

- 사실(보고서)
  - 10-21 22:52 UTC, 광장비 교체 작업으로 동부 네트워크 허브 ↔ 동부 주 데이터센터 연결이 끊겼고 43초 만에 복구됐다.
  - 그 사이 서부 데이터센터와 동부 퍼블릭 클라우드의 Orchestrator 노드들이 Raft 정족수를 이뤄 클러스터들의 쓰기를 서부로 페일오버했다. 연결이 돌아오자 앱은 곧바로 서부 주 서버에 썼다.
  - 동부 DB에는 서부로 복제되지 않은 짧은 구간의 쓰기가 남아, 양쪽에 서로 없는 쓰기가 생겼다. 동부로 안전하게 되돌릴 수 없었다.
  - 서부 데이터를 지키려 fail-forward를 택했다. 동부 앱은 대부분의 DB 호출이 대륙 횡단 왕복이 되어 많은 사용자에게 쓸 수 없었다.
  - 백업 복원, 복제 따라잡기, 적체 처리 끝에 10-22 23:03 녹색. 총 24시간 11분.
- 해석: 짧은 방아쇠가 **되돌릴 수 없는 자동 동작**(리전 간 승격)을 일으켰고, 그 순간 짧은 장애가 긴 복구로 바뀌었다. 탐지 문턱만이 아니라 승격의 범위가 문제였다.

### 2. 정족수가 막은 것과 못 본 것

- 막은 것: 리더 둘. 정족수 쪽(서부 + 클라우드)만 진행했고, 고립된 동부 노드는 혼자 결정하지 못했다(10 §1, 11).
- 못 본 것
  - 비동기 복제의 미전송분. 승격 시점에 동부에만 있던 몇 초의 쓰기(06 §3).
  - 리전 간 지연을 앱이 감당하는지. 선출 알고리즘의 관심 밖이다(08 §4).
- 보고서의 원인 진술: Orchestrator는 "설정된 대로" 동작했지만 앱 계층은 이 토폴로지 변경을 감당하지 못했다. 리전 안의 리더 선출은 대체로 안전하지만 갑작스러운 대륙 횡단 지연이 주요 원인 중 하나였다. 이런 규모의 내부 분할을 처음 겪어 생긴 창발적 동작이었다.
- 후속 조치: 리전 경계를 넘는 승격을 막도록 Orchestrator 설정 조정, active/active/active 설계 가속, 장애 주입·카오스 엔지니어링 도구 투자.

### 3. 요청마다 다른 데이터

- 11:12에 주 서버는 모두 동부로 돌아왔지만, 읽기 복제본 수십 대가 몇 시간 뒤처져 있었다. 읽기를 큰 복제본 풀에 퍼뜨리므로 요청마다 지연이 다른 복제본에 닿았다.
- 해석: 한 사용자가 새 값을 본 뒤 다음 요청에서 옛 값을 볼 수 있으니 **monotonic reads** 위반이다(07 §3).
- 예상이 빗나간 이유: 06:51의 "2시간"은 복제 원격 측정에서 선형 보간한 값이었다. 실제 따라잡기는 "power decay"를 따랐다. 유럽·미국 업무 시작으로 쓰기 부하가 늘어 따라잡는 속도가 줄었다.
- 13:15 조치: 미리 준비하던 동부 퍼블릭 클라우드의 읽기 복제본을 투입해 읽기 부하를 더 많은 서버에 나눴다. 복제본당 부하가 줄자 복제가 따라잡았다.

### 4. 적체 처리 중 TTL로 버려진 웹훅

- 16:45 기준 대기: 웹훅 이벤트 5백만 건 이상, Pages 빌드 8만 건.
- 처리를 다시 켜자 내부 TTL을 넘긴 웹훅 페이로드 약 20만 건이 버려졌다. GitHub는 이를 발견하고 처리를 멈춘 뒤 TTL을 올렸다.
- 해석: 만료는 평시에 "낡은 메시지를 버리는" 합리적 장치다(19 §4). 복구 적체에서는 대기 시간이 TTL을 넘어 **유효한 작업**을 버리는 장치가 됐다.
- 대처: 복구 런북에 만료 정책을 넣는다(적체 중 상향 또는 업무 기준 만료). 버린 건수를 지표로 내고 처리를 멈출 수 있게 한다. 하위 파트너로 가는 속도를 조절한다.

### 5. Cloudflare 코드 경로

```text
  start := time.Now()  →  리졸버에 질의(수 ms)  →  rtt := time.Now().Sub(start)
       윤초에 시간이 1초 뒤로  →  rtt 음수
  →  측정값 여러 개를 평활  →  몇 번 뒤 평활값이 음수
  →  가중 선택이 업스트림 시간 값을 rand.Int63n()에 넣음  →  음수면 panic
  →  Go recover로 잡힘  →  그 CNAME 해석 실패
```

- "조금 뒤"인 이유: 측정 하나는 평활값을 바로 음수로 만들지 않았다. 음수 측정이 몇 번 쌓인 뒤 평활값이 음수가 됐고, 그 값을 쓰는 **다른 코드**(서버 선택)에서 터졌다.
- 근본 원인(원문): "시간은 뒤로 갈 수 없다"는 믿음. 두 시각의 차이가 최악이어도 0이라고 가정했다.
- 수정(원문): 시간이 뒤로 가면 업스트림 성능 기록을 잊고 다시 쌓게 해 음수가 서버 선택 코드로 새지 않게 했다. 이후 모든 RRDNS 서버를 재시작했다. 영향은 00:00에 시작해 06:45 UTC에 끝났다.

### 6. 단조 시계와 음수 방어

- Go 1.9부터 `time.Now()`는 단조 시계 값을 함께 담는다. 두 `Time`이 모두 그 값을 가지면 `t.Sub(u)`는 단조 값만 쓰므로 벽시계 되감기에 음수가 되지 않는다(Go 1.9 릴리스 노트, `time.go` 주석). 원문 당시 Go에는 단조 시간 소스가 없었다(issue 12914).
- Java: 경과 시간은 `System.nanoTime()` 차이로 잰다. `System.currentTimeMillis()`는 벽시계다(04).
- 그래도 방어하는 이유: 한쪽 값이 직렬화·다른 프로세스·벽시계에서 온 경우처럼 단조 값이 없는 경로가 섞일 수 있다. 음수가 상태(평활값)에 누적되면 나중에 다른 곳에서 터지므로 경계에서 막는 것이 싸다.

### 7. EBS 재미러링 폭풍의 고리

```text
  방아쇠: 12:47 AM PDT 용량 업그레이드 중 트래픽을 저용량 보조 네트워크로 잘못 전환
     → 일부 노드가 주·보조 네트워크를 동시에 잃고 고립
  되돌림 → 연결 복구
     → 노드들: "복제 상대가 죽었다" 가정 → 동시에 새 공간을 찾아 재미러링
     → 여유 용량 고갈 → 공간을 찾는 루프(약 13% 볼륨 stuck)
        ├ 악화 ①: 공간이 없는데 충분히 물러서지 않고 반복 탐색
        └ 악화 ②: 연결 폭증이 낮은 확률의 경쟁 조건 crash를 자주 터뜨림 → 더 많은 볼륨이 재미러링 필요 ─┐
                                                                                         (되먹임) ◀┘
  번짐: create volume API가 느려짐 → 제어 평면의 긴 타임아웃 → 리전 공용 스레드 풀 고갈
        → 다른 가용 영역 API도 실패 (2:40 AM 해당 영역 Create Volume 차단, 2:50 AM 회복)
```

### 8. 일관성 선택과 재시도 방향

- 재미러링 중 접근 차단: 새 주(쓰기 가능) 복제본이 정해질 때까지 볼륨을 막았다. 사본 하나만 쓰기 가능하게 하는 협상은 리더 선출·펜싱과 같은 역할이다. 가용성(stuck 볼륨) 대신 일관성을 택했다(08, 10, 12).
- RDS 다중 AZ 2.5%: 분할 직후 주 복제본의 stuck I/O가 이어지며 이전에 없던 버그가 주 복제본을 "데이터 유실 위험 없이 자동 페일오버하기에 안전하지 않은" 고립 상태로 남겼다. 자동 페일오버가 멈추고 사람 개입이 필요했다. 해석: 리더 둘·비동기 유실을 피하는 쪽을 택한 것이다(10 §1, 06 §3).
- 재시도 로직 변경의 두 방향(원문): ① 큰 중단 때 **더 공격적으로 물러선다** ② 새 노드를 헛되이 찾기보다 **이전 복제본과의 연결 회복**에 집중한다. 여기에 여유 용량 확보와 경쟁 조건 수정을 더해 세 겹 보호라고 적었다.

### 9. 유체 모델 예측과 실행 결과

- 실행 출력(Node.js 18.19.1, 20초 구간별 초당 goodput)
  - 140 + 재시도: 단절 직후 거의 0(20~40초 구간 1, 그 뒤 0)이었다가, 120~140초 구간에서 36, 그다음부터 140으로 회복.
  - 280 + 재시도: 단절 뒤 끝까지(400초) 0 근처(20~40초 구간 1, 그 뒤 0).
  - 280 + 재시도 끔: 120~140초 구간까지 0, 140~160초 구간 221, 그 뒤 280으로 회복.
- 280 + 재시도의 시도율은 초당 560으로 수렴한다. 모든 첫 시도가 1초를 넘겨 재시도가 붙으므로 280 × 2다. Bronson 외 2.1절의 "560 QPS"와 같다.
- 이유: 560 > 300(DB 처리량)이라 대기열이 줄지 않는다. 대기열이 길면 모든 시도가 1초를 넘기고, 그래서 다시 재시도가 붙는다(지속 효과). 140 + 재시도는 280 < 300이라 대기열이 천천히 줄어 빠져나오고, 280 + 재시도 끔은 280 < 300이라 빠져나온다.
- 주의: 이 노트가 만든 단순 모델이다. DB가 기한 지난 요청을 버리면 회복 모양이 달라진다.

### 10. 방아쇠를 원인으로 적은 사후 분석

- 놓친 것: 근본 원인은 방아쇠(네트워크 단절)가 아니라 **지속 효과의 되먹임 고리**(재시도·캐시 비움 등)다. 같은 상태로 가는 방아쇠는 많아서, 배포·캐시 재시작 같은 다른 방아쇠로 다시 갇힌다(Bronson 외 3절).
- 대응
  - 과부하 때 정책 바꾸기: 재시도 예산, 장애 조치·재시도 끄기, LIFO, 내부 큐 줄이기, 우선순위, 부하 차단, 서킷 브레이커.
  - 지속 과부하와 순간 급증 가르기: 슬라이딩 윈도 안 최소 대기 지연(CoDel처럼).
  - 빠른 오류 경로: 실패 기록을 크기 제한 큐로, 넘치면 카운터만.
- 특성 지표: 방아쇠에 튀고 장애가 끝나야 돌아오는 지표(대기 지연·요청 지연·타임아웃률·캐시 적중률 등). 사후 분석에서 "방아쇠 제거 뒤에도 이 지표가 높았나"를 본다.
- 숨은 용량: 스스로 회복하는 한계. look-aside 캐시 예에서 광고 용량은 3,000 QPS, 숨은 용량은 DB 혼자 감당하는 300 QPS다. 방아쇠를 주입해 스스로 회복하는지 보는 부하 시험으로 잰다.
- Huang 외의 보탬: 방아쇠는 부하 급증형과 용량 감소형(배포한 비효율 코드 등) 두 종류다. 이 사례의 "배포"는 용량 감소형 방아쇠일 수 있다. 공개 사례에서 지속 효과로 재시도가 50% 넘게 관여했고, 완화에는 부하 차단이 55% 넘게 쓰였다.
