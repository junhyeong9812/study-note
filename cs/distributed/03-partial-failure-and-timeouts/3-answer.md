# distributed/03-partial-failure-and-timeouts — 정답

## 정답

### 1. 성공·실패·모름

- 응답을 못 받으면 상대가 요청을 받았는지, 처리했는지 알 수 없다. 그래서 성공·실패 외에 **모름**이 생긴다(DDIA 8장, 6.5840 L2).
- 모름을 실패로 처리하면
  - 실제로는 처리된 일을 "안 됨"으로 기록한다 → 내부 기록과 외부 기록이 어긋난다(돈은 빠졌는데 주문은 실패).
  - 실패니까 다시 보낸다 → 같은 일이 두 번 된다.

### 2. 여섯 경우 분류

| 경우 | 피호출자가 일을 했나 |
|---|---|
| ① 요청 유실 | 안 함 |
| ② 요청이 큐에서 대기 | 타임아웃 뒤에 할 수 있음 |
| ③ 피호출자 죽음 | 안 함 |
| ④ 피호출자 멈춤(GC 등) | 깨어난 뒤 할 수 있음 |
| ⑤ 응답 유실 | 이미 함 |
| ⑥ 응답 지연 | 이미 함 |

- 타임아웃 뒤에 일어날 수 있는 경우: ②·④. 그래서 "타임아웃 났으니 안 했다"고 확정할 수 없다.

### 3. 결제 실험

- 멱등 키 없음: 세 시도 모두 약 1초 뒤 타임아웃 → 클라이언트는 "실패"로 기록. 서버의 실제 결제 횟수는 **3**.
- 멱등 키 `order-42`: 첫 시도 타임아웃, 둘째 시도는 첫 결제가 끝나길 기다려 523 ms 뒤 같은 결과(`charged #1`)를 받았다. 결제 **1**번.
- 덧붙여 타임아웃을 3초(처리 시간보다 길게)로 하면 첫 시도에 1504 ms 뒤 성공, 결제 1번.

### 4. 모름을 다루는 세 길

- (a) 재시도 + 멱등 키: 상대가 키별 첫 결과를 저장했다가 돌려줘야 한다(예: Stripe `Idempotency-Key`).
- (b) 결과 조회: 상대가 키·거래 ID로 상태를 물을 수 있는 조회 API를 줘야 한다.
- (c) 대사: 상대가 정산 파일·거래 목록처럼 맞춰 볼 기록을 줘야 하고, 우리 쪽은 대사 키(외부 거래 ID나 멱등 키)를 저장해 둬야 한다.

### 5. 타임아웃 후보별 "모름" 비율

- 평균의 2배(70 µs): 실험에서 800건 / 20000 = 4.00%. 다른 실행에서는 5.6~8.1%였다(꼬리 모양에 달렸다).
- p99(123 µs): 정의상 약 1%(실험 200건).
- 부하와의 관계: "모름"이 된 요청은 보통 재시도된다. 4%가 모름이면 하류에 4%의 추가 요청이 붙는다. 하류가 느려질수록 꼬리가 길어져 비율이 커지고, 재시도가 더 붙는 되먹임이 생긴다.
- 값은 실행마다 다르다(두 번째 실행 p99 153 µs, 사실 점검 재실행 176~373 µs). 꼬리가 길다는 경향은 같다.

### 6. `2d + r`의 조건

- 조건: 네트워크가 패킷을 최대 d 안에 전달하거나 버리고, 고장 나지 않은 노드가 요청을 항상 r 안에 처리한다는 **보장**이 있을 때. 그러면 성공한 요청은 `2d + r` 안에 응답이 온다(DDIA 8장).
- 실제 비동기 네트워크와 대부분의 서버는 그런 상한이 없다. 큐잉·GC·이웃 부하로 지연이 얼마든 길어질 수 있다.
- 대신
  - 여러 기계에서 오래 RTT 분포를 재서 실험으로 고른다.
  - 응답 시간과 흔들림을 계속 재서 자동으로 조정한다(TCP 재전송 타이머). 노드 장애 탐지라면 하트비트 간격 분포를 쓰는 φ accrual(02번)이 같은 생각이다.

### 7. 타임아웃 계층

- 바깥이 더 길고 안쪽이 더 짧아야 한다(예: 게이트웨이 3 s > 주문 2 s > 결제 1.5 s).
- 거꾸로면 바깥이 먼저 포기했는데 안쪽은 계속 일한다. 결과를 받을 사람이 없는 헛일이 쌓이고, 바깥은 다시 보내 부하가 늘어난다.
- 근본적으로는 데드라인(절대 만료 시각)을 요청과 함께 전파하고, 각 층이 남은 예산을 계산해 예산이 없으면 시작하지 않거나 중단한다(ops-patterns/deadline-propagation).

### 8. GitHub 2018-10-21

- 사고 보고서 원문: 22:52 UTC, 동부 네트워크 허브와 동부 주 데이터센터 사이 연결이 끊겼고 **43초** 만에 복구됐다. 서비스 저하는 **24시간 11분**.
- 그 43초 동안 Orchestrator(Raft 합의)가 서부 데이터센터로 MySQL 페일오버를 진행했다. 동부에는 서부로 복제되지 않은 몇 초 분량의 쓰기가 남아, 안전하게 되돌릴 수 없었다.
- 보고서의 원인 진술: Orchestrator는 설정대로 동작했지만, 애플리케이션 계층이 리전을 넘는 주 DB 승격을 감당하지 못했다. 후속 조치는 리전 경계를 넘는 승격을 막는 설정 조정이다. 보고서는 탐지 타임아웃이 짧았다고 하지 않는다.
- 해석: 43초 끊김만으로 되돌리기 어려운 페일오버가 시작될 수 있었고, 그 페일오버가 애플리케이션이 감당 못 하는 토폴로지를 만들었다. 오판 한 번의 비용이 컸다. 되돌리기 어려운 동작일수록 페일오버 범위를 제한하고, 탐지 문턱을 길게 하거나 사람 확인을 두고, 옛 주인의 쓰기를 펜싱해야 한다.

### 9. 멱등 키가 있는데도 중복

| 원인 | 대처 |
|---|---|
| 재시도할 때 키를 새로 만들었다 | 키를 첫 시도 전에 만들어 저장하고 재시도에 재사용 |
| "조회 후 없으면 삽입"이라 동시 요청이 둘 다 "없음"을 봄 | 유일 제약·`putIfAbsent` 같은 원자적 삽입 |
| 처리 결과와 키 기록을 다른 트랜잭션으로 씀 | 결과와 키를 같은 트랜잭션에 기록 |
| 키 보존 기간이 재시도 기간보다 짧음 | 보존 기간 ≥ 최대 재시도 기간(Stripe는 24시간 이상 지난 키를 지울 수 있다고 명시) |
