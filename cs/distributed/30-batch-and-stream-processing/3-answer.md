# distributed/30-batch-and-stream-processing — 정답

## 정답

### 1. MapReduce 흐름

```text
  split ─> map ─> (k,v) ─ hash(k) mod R ─> map 로컬 디스크의 R개 파일
                                                │ reduce가 원격으로 당겨 옴
  reduce r: 자기 몫을 모두 읽음 → 키로 정렬 → 같은 키 묶음마다 reduce(k, [v...]) → out-r
```

- 분할: 사용자가 정한 분할 함수(기본 예 `hash(key) mod R`)로 중간 키 공간을 R조각으로 나눈다(Dean–Ghemawat 2004 §3.1).
- 정렬하는 이유: 한 reduce 태스크에 여러 키가 오므로, 같은 키를 붙여 한 번 훑으며 넘기기 위해서다.
- 메모리를 넘으면 외부 정렬을 쓴다(§3.1). 정렬된 런을 디스크에 쓰고 병합한다.

### 2. map은 다시, reduce는 그대로

- 끝난 map의 출력은 **그 워커의 로컬 디스크**에 있다. 워커가 죽으면 읽을 수 없으므로 다시 돌린다.
- 끝난 reduce의 출력은 **전역 파일 시스템**(GFS)에 있다. 워커가 죽어도 남아 있다(§3.3).
- 원자적 rename: reduce는 임시 파일에 쓰고 끝나면 최종 이름으로 바꾼다. 같은 태스크가 두 번 돌아 rename이 두 번 일어나도, 파일 시스템의 원자적 rename 덕분에 최종 파일에는 한 번의 실행 결과만 남는다.

### 3. 결정적 함수라는 전제

- 전제: map·reduce 함수가 입력에 대해 결정적이어야 한다(§3.3).
- 깨는 예: map에서 `Math.random()`으로 표본을 뽑거나, 현재 시각·외부 API 값을 쓴다.
- 생기는 일: 재실행된 map이 첫 실행과 다른 출력을 낸다. 어떤 reduce는 첫 실행 결과를, 다른 reduce는 재실행 결과를 읽어 서로 맞지 않는 출력(중복·누락)이 생긴다.

### 4. 스큐 예측

- `user-42`가 가는 리듀서 하나가 절반(약 5만) + 나머지 키의 1/4(약 1만 2천 5백)을 받는다. 나머지 셋은 약 1만 2천 5백씩.
- 실험: `[62469, 12468, 12460, 12603]`, `user-42 → 리듀서 0`.
- 백업 태스크로는 줄지 않는다. 백업 태스크는 **기계가 느린** straggler를 고친다. 이 경우는 **데이터가 몰린** 것이라 어느 기계에서 돌려도 같은 양을 처리한다.

### 5. 솔팅

1. 뜨거운 키에 소금을 붙여 쪼갠다: `user-42` → `user-42#0..#3`. 1단계 집계를 하면 네 조각이 다른 리듀서로 흩어진다.
2. 부분 결과에서 소금을 떼고 다시 집계한다: `user-42#0..#3`의 부분 합 넷 → `user-42` 하나.

- 실험: 1단계 입력 `[24807, 24925, 25066, 25202]`(고르게), 2단계 입력 `[252, 249, 251, 251]`(부분 합이라 가벼움), 결과는 그냥 집계와 같음(`true`).
- 그대로 못 쓰는 집계: 부분 결과로 합칠 수 없는 것. 정확한 중앙값·분위수, 정확한 고유 개수(부분 결과에 집합 전체를 실어야 함) 등. 결합 법칙이 성립하는 합·개수·최대·최소는 된다.

### 6. 이벤트 시간 vs 처리 시간

- 이벤트 시간: 이벤트가 생산 기기에서 일어난 시각. 데이터 안에 있다.
- 처리 시간: 처리하는 기계의 시스템 시계.
- 재처리 뒤 결과가 달라졌다면 처리 시간 윈도일 가능성이 크다. 재처리한 레코드가 "재처리한 시각"의 윈도에 몰린다. 이벤트 시간으로 묶으면 같은 입력은 같은 윈도에 들어간다.

### 7. 늦은 이벤트 예측

| 도착 | 이벤트 시간 | 그때 stream time | 판정 |
|---|---|---|---|
| 1 | 1s | 1 | [0,10) → count 1 |
| 2 | 3s | 3 | [0,10) → count 2 |
| 3 | 12s | 12 | [10,20) → count 1 |
| 4 | 4s | 12 | 12 < 10+5 → [0,10) count 3 |
| 5 | 20s | 20 | [20,30) → count 1 |
| 6 | 5s | 20 | 20 > 10+5 → **버려짐** |
| 7 | 13s | 20 | 20 < 20+5 → [10,20) count 2 |

- 실험(Kafka Streams 4.1) 출력과 같다. `t=5s`는 출력이 없고, ERROR 대신 `dropped-records-total = 1.0` 지표와 WARN 로그 `Skipping record for expired window` 한 줄로만 보인다(로깅 바인딩을 켠 재실행에서 확인).
- 결과적으로 [0,10)의 최종 count는 3이다. 실제 이 윈도에 속한 이벤트는 4개다.

### 8. 워터마크

- 정의: Watermark(t)는 "이 스트림의 이벤트 시간이 t에 도달했다, t 이하의 이벤트는 더 오지 않을 것이다"라는 선언이다. 데이터와 함께 흐른다(Flink 문서).
- 여러 입력을 받는 연산자의 현재 이벤트 시간 = 입력 스트림들의 이벤트 시간 중 **최솟값**.
- 장애: 입력 하나(유휴 파티션)에 새 이벤트가 없으면 최솟값이 전진하지 않아 어떤 윈도도 닫히지 않는다. 결과가 아예 안 나온다. 유휴 입력을 계산에서 빼는 설정이나 하트비트 이벤트로 푼다.
- (Kafka Streams는 워터마크 대신 stream time을 쓴다. 새 레코드가 와야 전진한다는 점에서 같은 성질이 있다.)

### 9. exactly_once_v2의 범위

- 원자적으로 묶는 세 가지: 입력 토픽 오프셋 커밋, 상태 저장소 갱신, 출력 토픽 쓰기(Kafka Streams Core Concepts).
- 외부 API 호출은 이 묶음 밖이다. 트랜잭션이 abort되고 재처리되면 그 호출은 다시 일어난다. 외부 호출은 멱등 키를 쓰거나, 출력 토픽까지만 Streams로 처리하고 외부 반영은 멱등 싱크로 분리한다(17번 §4).
