# distributed/16-outbox-and-dual-write — 정답

## 정답

### 1. 이중 쓰기의 위험

- 커밋 뒤 발행 전에 죽으면: 주문은 있는데 이벤트가 없다(유실). DB만 보면 정상이라 아무도 신고하지 않는다.
- 순서를 바꿔 발행을 먼저 하고 커밋이 실패·롤백되면: 없는 주문의 이벤트가 나간다(유령 이벤트). `@Transactional` 안에서 `send()`해도 전송은 롤백되지 않는다.
- 재시도로 못 고치는 이유: 프로세스가 죽으면 재시도할 코드도 같이 죽는다.

### 2. 2PC를 쓰지 않는 이유 (microservices.io)

- DB 그리고/또는 브로커가 2PC를 지원하지 않을 수 있다(예: Kafka 4.1 프로듀서 트랜잭션은 XA 참가자가 아니다).
- 지원하더라도 서비스를 DB와 브로커 둘 모두에 결합시키는 것이 바람직하지 않다.

### 3. 구조와 보장

```text
  [서비스 트랜잭션] INSERT orders + INSERT outbox → COMMIT
          │
  [릴레이] 미발행 outbox 행 읽기 → send → 표시 (또는 CDC로 WAL에서 읽기)
          │
  [브로커] 메시지 저장 → 소비자
```

- 보장: 메시지는 DB 트랜잭션이 커밋될 때, 그리고 그때만 보내진다. 서비스가 쓴 순서대로 브로커에 보내진다(microservices.io). 단, 릴레이가 같은 메시지를 두 번 보낼 수 있다(at-least-once).

### 4. 실험 예측

- 직접 발행: 토픽 180건(크래시 20번 = 유실 20). DB에는 200건이 다 있다.
- outbox + 릴레이 크래시 22번: 서로 다른 메시지 200(유실 0), 중복 127(전체 327).
- 중복이 크래시 수보다 많은 이유: 릴레이가 배치 10건을 보내고 **배치 끝에 표시를 한 번 커밋**한다. 배치 중간에 죽으면 그 배치에서 이미 보낸 행 전부가 미발행으로 남아 다시 나간다. 크래시당 평균 약 5.8건이었다.
- 근거: 실험(전용 PostgreSQL 17.11 + Kafka 4.1.0, Java 21, 2026-10-01).

### 5. 프로듀서 멱등성의 범위

- `enable.idempotence=true`는 **한 프로듀서 인스턴스가 브로커 장애 등으로 재시도할 때** 같은 메시지가 두 번 쓰이지 않게 한다(Kafka 4.1 producer configs).
- 릴레이 프로세스가 죽고 새로 뜨면 새 프로듀서다. outbox 행이 미발행으로 남아 있으니 애플리케이션이 같은 내용을 **새 메시지로** 다시 보낸다. 브로커 입장에서는 중복이 아니다.
- 그래서 실험의 중복 127건이 기본값(`true`)에서 나왔다. 이 중복은 소비자 멱등(이벤트 id)으로 흡수한다.

### 6. 릴레이 2개

- 좋아지는 것: 처리량.
- 깨질 수 있는 것: 같은 aggregate의 이벤트 순서. 실험에서 주문 100건 × 이벤트 3개를 릴레이 2개로 보내자 키별 순서 역전이 15번 나왔다(1개일 때 0).
- 챙길 구간
  - outbox → 릴레이: 릴레이 1개(리더 선출로 이중화) 또는 aggregate 단위로 분담.
  - 릴레이 → 파티션: 메시지 키 = aggregate id.
  - 프로듀서 재시도: 멱등 프로듀서(기본값)면 재시도 중에도 순서가 보존된다.
  - 소비자: seq를 보고 오래된 이벤트를 걸러 한 번 더 방어한다.

### 7. 진행 0, 재발행 폭주

- 릴레이가 배치 안의 같은 지점에서 매번 죽어 표시를 커밋하지 못한다. 같은 앞부분 행들만 계속 다시 나간다.
- 실험: 실행마다 7번째 발행 후 죽게 하자 94번 재시작 동안 658건이 나갔는데 서로 다른 것은 7건, 미발행은 계속 200이었다.
- 고치기: 표시를 행 단위(작은 배치)로 커밋, 반복 실패 행을 격리(별도 상태·DLQ), "가장 오래된 미발행 행의 나이"에 알람.

### 8. CDC

- 폴링: 릴레이가 outbox 표를 주기적으로 조회하고, 보낸 뒤 표시한다. 조회 부하와 폴링 주기만큼의 지연이 있다.
- CDC: DB 트랜잭션 로그(Postgres WAL, MySQL binlog)에서 outbox INSERT를 읽는다. 표시 갱신이 필요 없다. 그래도 중복 발행은 생길 수 있다(microservices.io "Transaction log tailing").
- 실험(PostgreSQL 17.11 `test_decoding`): 롤백한 트랜잭션은 아예 나오지 않았다. 커밋한 트랜잭션은 `BEGIN <xid>` → orders INSERT → outbox INSERT → `COMMIT <xid>` 묶음으로 나왔다.
- 슬롯을 버려 두면: 소비자가 없어도 WAL을 붙잡는다(실험: 쓰기 2만 건 뒤 2548 kB). `max_slot_wal_keep_size` 기본 -1이면 상한이 없어 디스크가 찰 수 있다.

### 9. 배포 직후 배송 누락

- 확인: 배포(재시작) 시각 전후의 주문을 DB에서 뽑고, 토픽(또는 하위 시스템)에 해당 이벤트가 있는지 대조한다. 오류 로그가 없는 것이 정상인 유실이다.
- 복구: 빠진 주문의 이벤트를 다시 발행한다. 이벤트를 원천 상태에서 다시 만들 수 있을 때만 된다(29번 — 상태형/사건형).
- 근본 대처: outbox로 바꾼다. 소비자는 멱등하게.
