# distributed/22-event-sourcing — 정답

## 정답

### 1. 상태 저장의 한계와 이벤트 로그의 기능

- 상태만 있으면 답하지 못하는 질문(예)
  - "왜 이 값이 됐나?" — 바꾼 원인이 덮어써져 사라진다.
  - "3월 5일 자정의 잔액은?" — 과거 상태가 없다. 당시에 묻지 않은 집계도 나중에 못 뽑는다.
- Fowler 2005의 세 기능
  - Complete Rebuild: 상태를 버리고 이벤트를 다시 돌려 재구축.
  - Temporal Query: 어느 시점까지만 접어 그 시점 상태를 얻음.
  - Event Replay: 잘못된 과거 이벤트를 고쳐 그 뒤를 다시 계산.

### 2. 동시 출금

| | 최종 잔액 | 이벤트 수 | 결과 |
|---|---|---|---|
| (a) 이벤트 ID PK | −400 | 5 | 둘 다 붙음, 불변식 깨짐 |
| (b) (stream_id, version) PK | 300 | 4 | 늦은 쪽 거절 |

- 실험(PostgreSQL 17.11) 출력 그대로다: `fold 결과 잔액 = -400, 이벤트 5건` / `잔액 = 300, 이벤트 4건`.
- (b)의 늦은 쪽은 먼저 넣은 트랜잭션이 끝날 때까지 **기다렸다가**, 그쪽이 커밋하면 `ERROR: duplicate key value violates unique constraint "events_pkey"`(SQLSTATE 23505)를 받는다. 먼저 쪽이 롤백했다면 성공한다(PostgreSQL 17 문서 62.5).
- 거절된 쪽은 다시 읽고(잔액 300) 다시 판단해 명령을 거절한다.

### 3. 재생 중 검증 금지

- 이벤트는 "이미 일어난 사실"이다. 그때의 규칙으로 승인됐다.
- 재생 중 오늘의 규칙으로 검증하면, 규칙이 바뀐 뒤 옛 이벤트가 걸려 예외가 난다. 그 스트림은 더 이상 접히지 않고, 거절된 이벤트 뒤의 상태가 모두 틀어진다.
- 예: 예전에 마이너스 통장이 허용돼 잔액이 −4000이 된 계좌. 재생에서 `잔액 < 0`을 검사하면 이 계좌는 조회조차 안 된다. 검증은 명령을 이벤트로 바꿀 때 한 번만 한다(원본 ops-patterns/16).

### 4. 재생 vs 스냅샷

- 결과는 같다(실험: 둘 다 `잔액 50,500,000, v1000000`).
- 시간: 처음부터는 333~1196ms(실행마다 다름, 첫 회는 JIT 워밍업), 스냅샷 + 137건은 0.05~0.10ms. 메모리 안 측정이라 실제로는 DB에서 100만 행을 읽는 시간이 더해진다.
- 스냅샷이 틀렸으면 버리고 이벤트에서 다시 만든다. 정본은 이벤트이고 스냅샷은 캐시다.

### 5. 필드 이름 변경 후 재생

- 기본 설정: `UnrecognizedPropertyException: Unrecognized field "amount" ...`로 재생이 실패한다.
- `FAIL_ON_UNKNOWN_PROPERTIES=false`: 예외 없이 `Deposited[amountMinor=0, currency=null]`로 읽힌다(실험).
- 더 위험한 것은 후자다. 잔액이 조용히 틀리고 아무도 모른다. 전자는 적어도 드러난다. 이름 변경은 업캐스터로 명시적으로 옮긴다.

### 6. 이벤트 형식 변경 다루기

- 관대한 읽기: 모르는 필드는 무시, 없는 필드는 기본값. **필드 추가**에 맞다(기본값을 정해 둔다).
- 업캐스터: 읽을 때 옛 형식을 현재 형식으로 변환한다. 저장된 이벤트는 그대로 둔다. **이름 변경·구조 변경**에 맞다. 이벤트에 `schema_ver`가 있어야 무엇을 변환할지 안다.
- 새 이벤트 타입: 의미가 바뀌면 `DepositedV2`처럼 새 타입을 만들고 둘 다 접는다.
- (덧붙여) 복사·변환: 변환한 이벤트를 새 스트림·저장소에 다시 쓰고 전환한다. 원본은 보관한다.

### 7. 재생과 외부 세계

- 안전: 프로젝션(읽기 모델) 재구축. 지우고 다시 만들어도 같은 결과가 나온다.
- 사고: 부작용이 있는 구독자(메일·결제 API·다른 서비스 통지)까지 재생에 끼면 과거의 부작용이 다시 일어난다.
- External Updates: 외부 시스템은 재생과 실제 처리를 구별하지 못한다. 외부 호출을 게이트웨이로 감싸 재생 중에는 끈다.
- External Queries: 12월 5일 이벤트를 12월 20일에 재생하면 12월 5일의 환율이 필요하다. Fowler의 처방은 과거 날짜의 값을 줄 수 있는 외부 시스템에 묻거나, 게이트웨이가 질의 응답을 기억해 두었다가 재생 때 돌려주는 것이다. 결정에 쓴 외부 값을 이벤트에 담아 두는 것도 같은 효과다.

### 8. Kafka를 이벤트 저장소로 쓸 때의 빈 곳

1. 애그리게이트별 기대 버전 조건부 쓰기가 없다 — 동시 명령의 불변식 보호를 다른 곳에서 해야 한다.
2. 보존이 기본으로 시간 기준 삭제다(`retention.ms` 7일, `retention.bytes`는 기본 −1이라 따로 줄 때만). compaction은 키별로 적어도 마지막 값을 남기고 같은 키의 옛 값은 지울 수 있다. 영구 보존 설정이 필요하다.
3. 한 애그리게이트의 이벤트만 읽는 인덱스가 없다 — 파티션 전체를 훑어야 한다.
- 흔한 구성: 이벤트는 DB에 (stream_id, version) 유일 제약으로 저장, 전파는 아웃박스·CDC로 Kafka에.

### 9. 오래된 계좌의 조회 지연

- 확인
  - 스트림 길이 상위: `SELECT stream_id, max(version) FROM events GROUP BY 1 ORDER BY 2 DESC LIMIT 10`.
  - 스냅샷 뒤 꼬리 길이: 이벤트 최대 version − 스냅샷 version.
  - 지연이 스트림 길이에 비례하는지 본다.
- 고치기: N개마다 스냅샷을 만들고 "스냅샷 + 그 뒤 이벤트"만 읽는다. 끝없이 길어지는 모델이면 기간 마감 이벤트로 스트림을 끊는다.
- 경계 버그: 스냅샷 뒤를 읽는 조건을 `version >= snap.version`으로 쓰면 스냅샷에 이미 반영된 이벤트를 한 번 더 접는다. `version > snap.version`이 맞다. 처음부터 접은 결과와 비교하는 검증 테스트를 둔다.
