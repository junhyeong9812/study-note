# distributed/09-quorums — 정답

## 정답

### 1. 정족수의 역할

- 리더리스에는 최신 값을 아는 리더가 없다. 여러 곳에 쓰고 여러 곳에서 읽어 최신을 골라야 한다.
- R + W > N이면 쓴 W개와 읽은 R개가 적어도 한 노드에서 겹친다. 읽은 R개 중 하나는 마지막으로 성공한 쓰기를 갖고 있다(Dynamo §4.5).
- 그 하나를 골라내려면 응답마다 버전이 있어야 한다. 버전 없이 먼저 온 응답을 쓰면 겹쳐도 옛 값을 고를 수 있다.

### 2. 조합별 옛 값

(실험, Java 21 시뮬레이션, 2026-10-01)

```text
  N=3 R=1 W=1  R+W<=N  옛 값 읽기 17.93%
  N=3 R=1 W=2  R+W<=N  옛 값 읽기 6.30%
  N=3 R=2 W=1  R+W<=N  옛 값 읽기 1.94%
  N=3 R=1 W=3  R+W>N  옛 값 읽기 0.00%
  N=3 R=3 W=1  R+W>N  옛 값 읽기 0.00%
  N=3 R=2 W=2  R+W>N  옛 값 읽기 0.00%
```

- 0%: (1,3), (3,1), (2,2). 모두 R+W>N.
- 나머지의 비율은 메시지 지연 분포가 정한다. 이 실험은 1ms + 지수분포(평균 5ms)를 가정했다. 실제 시스템 값이 아니다.

### 3. R·W < N의 이유

- get·put의 지연은 기다리는 R개(W개) 중 가장 느린 것이 정한다. N개 모두를 기다리면 가장 느린 복제본이 지연을 정한다(Dynamo §4.5).
- 흔한 설정: (N,R,W) = (3,2,2)(Dynamo §6).

### 4. R+W>N이어도 옛 값

- sloppy quorum: W개가 원래 N개 밖의 노드일 수 있다.
- 동시 쓰기: LWW로 해소하면 하나가 사라진다.
- 읽기와 쓰기가 동시: 일부 복제본에만 도착한 순간의 읽기.
- W 미만에서 실패한 쓰기: 성공한 복제본의 값이 남아 보였다 안 보였다 한다.
- 새 값을 가진 노드가 옛 복제본에서 복구됨: 새 값의 사본 수가 W보다 줄어든다.
- (DDIA 5장 "Limitations of Quorum Consistency". Abadi 2012·Kleppmann 2015도 R+W>N이 선형화가 아니라고 적는다.)

### 5. sloppy quorum 그림

```text
  분할: [클라이언트, A, D]  |  [B, C, 반대편 클라이언트]
  쓰기 v2 W=2: A ✔, D ✔(힌트 "B 몫")  → OK
  반대편 읽기 R=2: B(v1), C(v1) → v1   (R+W=4>3인데 옛 값)
  분할 해소: D → B로 v2 전달, D는 삭제 → A=v2, B=v2, C=v1
```

(실험, Java 21 시뮬레이션, 2026-10-01)

```text
  반대편 클라이언트 R=2 읽기(B,C) → v1   (R+W=4>N=3인데 옛 값)
  분할 해소 후 hinted handoff(D→B) → 상태 {A=2, B=2, C=1, D=0}, R=2(B,C) 읽기 → v2
```

- 남는 일: C는 여전히 v1이다. 읽기 복구나 anti-entropy가 맞춰야 한다.

### 6. Cassandra 5.0과 Dynamo의 차이

- Dynamo 논문: 대체 노드(D)가 W 정족수에 포함된다(sloppy quorum, §4.6).
- Cassandra 5.0: 응답 없는 복제본 몫은 코디네이터가 힌트로 저장했다가(최대 `max_hint_window` 3시간) 돌아오면 보낸다. 그러나 일관성 수준은 진짜 복제본 응답으로 센다.
- 힌트만으로 성공하는 수준은 `ANY`이고, 쓰기에만 쓸 수 있다.

### 7. 복구 장치별 둘째 바퀴

(실험, Java 21 시뮬레이션, 2026-10-01)

```text
[B] 복구 없음          1바퀴 옛 값  274/3000  2바퀴(R=1) 옛 값  283/3000
[B] 읽기 복구(R=2)     1바퀴 옛 값   34/3000  2바퀴(R=1) 옛 값  108/3000
[B] anti-entropy   1바퀴 옛 값  274/3000  2바퀴(R=1) 옛 값    0/3000
```

- (a) 거의 그대로(274 → 283). 저절로 낫지 않는다. 차이는 R=1이 고르는 복제본이 무작위라서다.
- (b) 108. 읽기 복구는 읽은 두 복제본만 고친다. 세 번째 복제본이 옛 값이면 둘째 바퀴 R=1이 그것을 고를 수 있다.
- (c) 0. anti-entropy는 읽기와 상관없이 전체를 맞춘다.

### 8. Merkle 비교량

(실험, Java 21 시뮬레이션, 2026-10-01)

```text
[D] Merkle anti-entropy: 키 1024개 중 다른 키 [17, 500, 1000], 비교한 해시 55개 (전수 비교면 1024개)
```

- 55개. 루트에서 다른 가지로만 내려간다. 높이 10인 트리에서 다른 잎 하나마다 경로 10단계쯤이 들고, 경로가 위쪽에서 겹치는 만큼 줄어든다.
- 다른 키가 많아지면 내려가야 할 가지가 늘어 이득이 줄어든다. 전부 다르면 전수 비교보다 많아진다(내부 노드까지 비교).

### 9. 정족수 미달

- Cassandra Java 드라이버 4.x: `UnavailableException`. 형식 `Not enough replicas available for query at consistency QUORUM (2 required but only 1 alive)`(드라이버 소스).
- etcd 3.6.5: 과반(2)을 잃으면 put이 `context deadline exceeded`로 실패한다.

(실험, etcd 3.6.5 일회용 3노드, 2026-10-01)

```text
2/3 살아 있음(etcd3 정지): put → OK
1/3 살아 있음(etcd2·3 정지): put → Error: context deadline exceeded [3091ms]
```

- 대처: 복제본을 랙·영역으로 나눠 동시 장애를 줄인다. 가용성이 더 중요한 연산만 일관성 수준을 낮추고 기록한다. 노드 복구 뒤 repair.

### 10. 되살아난 삭제

- 원인: 삭제 표시(tombstone)가 다른 복제본에서 gc grace(기본 10일) 뒤 지워졌는데, 삭제를 놓친 노드에는 옛 값이 남았다. 그 뒤 읽기 복구·repair가 옛 값을 퍼뜨린다.
- 문서(Cassandra 5.0 "Repair"): 출발점으로 증분 repair 1~3일, 전체 repair 1~3주. 최소한 gc grace가 지나기 전에 — 기본값이면 모든 노드를 7일마다 — repair한다.
