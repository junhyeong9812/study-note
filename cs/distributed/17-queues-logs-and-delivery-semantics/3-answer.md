# distributed/17-queues-logs-and-delivery-semantics — 정답

## 정답

### 1. 큐와 로그의 차이

- 큐: 브로커가 메시지마다 전달·ack 상태를 추적하고, ack가 오면 지운다. 같은 큐의 소비자는 메시지를 나눠 가진다.
- 로그: 지우지 않고 뒤에 붙이기만 한다. 브로커는 그룹·파티션별 커밋된 오프셋 숫자 하나만 둔다. 지우는 것은 보존 기간이 지난 세그먼트 단위다.
- 로그에서 쉬운 일
  - 재처리: 오프셋을 되감으면 된다.
  - 새 소비자 추가: 새 그룹이 `auto.offset.reset=earliest`(4.1 기본은 `latest`)로 보존 중인 처음부터 전체를 읽는다. 실험에서 `--from-beginning`으로 시작한 그룹 두 개가 같은 15건을 각각 전부 받았고, 기본값으로 시작한 새 그룹은 0건이었다.
- 큐에서 쉬운 일: 메시지 하나하나의 재전달·지연 전달·우선순위 같은 작업 단위 관리. Kafka 4.1은 이를 위해 share group(KIP-932)을 미리보기로 넣었다.

### 2. 커밋 순서별 유실·중복

| | 커밋 위치 | 재시작 지점 | 유실 | 중복 | 보장 |
|---|---|---|---|---|---|
| (a) 처리 전 커밋 | 50 | 50 | 15건(35..49) | 0 | at-most-once |
| (b) 처리 후 10건마다 | 30 | 30 | 0 | 5건(30..34) | at-least-once |

- 실험(Kafka 4.1.0) 출력이 그대로다: `유실 15건, 중복 0건` / `유실 0건, 중복 5건`.
- 일반화(오프셋이 연속이고 순서대로 처리한 구간에서): 유실 = 커밋 위치 − 처리 위치, 중복 = 처리 위치 − 커밋 위치.

### 3. exactly-once의 세 범위

- 멱등 프로듀서: 한 프로듀서 세션 안의 재시도가 로그에 중복을 만들지 않는다(PID + 시퀀스 번호). 프로세스가 재시작해 새 PID를 받으면 그 사이의 재발행 중복은 못 막는다(KIP-98).
- Kafka 트랜잭션: 여러 파티션에 쓴 레코드와 소비 오프셋 커밋을 한 단위로 반영·폐기한다. Kafka → Kafka 처리까지다. 외부 DB 쓰기는 묶지 못한다.
- 멱등 소비: 같은 메시지를 두 번 처리해도 결과가 한 번과 같게 만든다. 외부 DB까지 포함하는 실무 방법이다. 전달 자체는 at-least-once 그대로다.

### 4. 트랜잭션과 isolation level

- 기본(`read_uncommitted`) 소비자: 10건. abort된 5건도 받는다.
- `read_committed` 소비자: 커밋된 5건만.
- 실험 출력에서 오프셋 5와 11이 비었다. 트랜잭션의 끝을 표시하는 컨트롤 레코드(abort 마커, commit 마커)가 그 오프셋을 차지하고, 소비자에게는 전달되지 않는다.

### 5. 3파티션 발행 순서 vs 소비 순서

- 실험 출력: `A1 A2 A3 A4 A5 F1 F2 F3 F4 F5 D1 D2 D3 D4 D5`. 다시 돌리면 `F… A… D…`처럼 파티션 묶음의 순서는 바뀔 수 있다. 파티션별로 묶인다는 모양은 같다.
- 보장되는 것: 같은 키(=같은 파티션) 안의 순서. A1→A5는 순서대로다.
- 안 되는 것: 키 사이·파티션 사이의 순서. 발행은 A1 D1 F1이었지만 소비는 파티션별로 묶여 나왔다. 어떤 파티션을 먼저 가져올지는 정해져 있지 않다.

### 6. 같은 키에서도 순서가 깨지는 경우

1. 파티션 수를 늘렸다 — `murmur2(키) % N`의 N이 바뀌어 같은 키가 다른 파티션으로 간다. 옛 파티션의 밀린 메시지와 새 파티션 메시지가 동시에 처리된다.
2. 멱등을 끄고 `max.in.flight.requests.per.connection` > 1로 재시도했다 — 실패한 배치가 재전송되는 사이 뒤 배치가 먼저 들어간다. 멱등을 켜면 5 이하에서 순서가 지켜진다.
3. 소비 쪽에서 실패 메시지를 재시도 토픽으로 넘겼다 — 그 메시지는 같은 키의 뒤 메시지보다 늦게 처리된다(18번).
- (덧붙여) Kafka 4.1 share group처럼 파티션을 여럿이 나눠 읽는 방식은 순서를 기대하지 않는다.

### 7. 인박스와 메시지 ID

- 오프셋은 "같은 내용이 로그의 어디에 놓였나"다. 발행자가 재시작 후 같은 이벤트를 다시 발행하면(아웃박스 릴레이 재시도 등) 새 오프셋을 받는다. 오프셋을 키로 쓰면 이 중복을 못 잡는다. 생산자가 만든 안정적 ID를 써야 한다.
- 인박스 INSERT와 비즈니스 UPDATE가 다른 트랜잭션이면
  - INSERT만 커밋되고 UPDATE 전에 죽으면 → 다음 재전달은 "이미 처리됨"으로 건너뛴다 → 유실.
  - UPDATE만 커밋되고 INSERT 전에 죽으면 → 다음 재전달이 다시 처리한다 → 중복.

### 8. exactly_once_v2인데 외부 DB 중복

- 트랜잭션은 Kafka 안의 출력 레코드와 입력 오프셋만 묶는다. 처리 중 외부 DB에 쓴 뒤 트랜잭션이 abort되고 재처리되면, DB 쓰기는 이미 한 번 일어났다.
- 대처
  1. DB 쓰기를 멱등하게 한다 — 메시지 ID 유니크 제약, 업서트, 조건부 UPDATE.
  2. 오프셋을 DB에 결과와 같은 트랜잭션으로 저장하고, 시작할 때 그 오프셋으로 `seek`한다(Kafka 문서 4.6의 처방). 또는 Kafka 출력 토픽까지만 Streams로 하고, DB 적재는 멱등 싱크(Connect 등)로 분리한다.

### 9. 배포 직후 중복 적립 진단

- 좁히는 법
  - 처리 로그에서 같은 이벤트 ID가 두 번 찍혔는지, 그 시각이 배포(재시작·리밸런스) 시각과 겹치는지 본다. 컨슈머 로그의 파티션 회수·그룹 재합류(리밸런스) 직후 재처리 구간을 찾는다.
  - `kafka-consumer-groups.sh --describe --group …`으로 커밋 위치와 lag을 보고, 커밋 주기(자동 커밋 간격·배치 단위 커밋)를 확인한다.
- 원인: 처리 후 커밋 전 종료(at-least-once의 정상 동작). 실험의 "중복 5건"과 같은 구조다.
- 근본 대처: 커밋 간격 조정은 창을 줄일 뿐이다. 적립 처리를 메시지 ID 기준으로 멱등하게 만든다(인박스 또는 `INSERT … ON CONFLICT DO NOTHING`).
