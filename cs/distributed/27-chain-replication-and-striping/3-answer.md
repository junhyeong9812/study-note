# distributed/27-chain-replication-and-striping — 정답

## 정답

### 1. 설정 서버와 데이터 복제의 분리

- 설정 서버는 누가 헤드·테일·프라이머리인지, 어느 서버가 어느 샤드를 갖는지 정한다. 분할 때 split brain을 막아야 하므로 보통 Raft·Paxos·ZooKeeper로 만든다(6.5840 L13).
- 데이터 복제(프라이머리-백업, 체인)는 split brain 판단을 설정 서버에 맡겨 단순해진다. 재구성 뒤에는 복제본 하나만 남아도 진행할 수 있다.
- 6.5840 CR FAQ: Raft는 큰 데이터를 복제하기에 적합하지 않고, 프라이머리-백업이 더 단순하다.

### 2. 체인의 흐름

```text
  쓰기:  client → [Head] → [Mid] → [Tail] → OK
  읽기:  client → [Tail]
  ack:   [Head] ← [Mid] ← [Tail]   (보관분 정리)
```

- 테일이 본 갱신은 체인의 모든 노드가 이미 갖고 있다. 테일이 답한 값은 허용된 장애 뒤에도 남는다. 읽기도 테일에서 하므로 갱신과 조회가 한 곳에서 직렬로 정해진다(van Renesse–Schneider 2004 §3).
- 헤드가 일찍 답하면, 클라이언트가 OK를 받은 뒤 테일에서 읽어도 그 갱신이 아직 테일에 없을 수 있다. 끝난 쓰기 뒤의 읽기가 옛 값 → 선형화 위반(6.5840 L13의 질문).

### 3. 견디는 장애 수

- 체인: t대 중 t−1대(논문 §3). 커밋된 값을 모든 노드가 갖기 때문이다(write all).
- 과반 정족수: N대 중 N/2 미만.
- 체인이 잃는 것: 서버 하나만 느리거나 죽어도 쓰기가 멈추거나 느려진다. 설정 서버가 재구성할 때까지 기다린다. 정족수는 일시적으로 느린 소수를 견딘다(6.5840 L13).

### 4. 세 방식의 지연

(실험, Java 21 스레드 시뮬레이션, 2026-10-01)

```text
[A] 세 노드 모두 처리 2ms
  chain           p50   6.5ms ...
  primary-backup  p50   4.3ms ...
  quorum Qa=2     p50   2.1ms ...
[B] 가운데 노드(1번)만 처리 20ms
  chain           p50  24.5ms  p99  25.6ms  (응답 뒤 남은 일 처리 0ms)
  primary-backup  p50  22.3ms  p99  22.7ms  (응답 뒤 남은 일 처리 0ms)
  quorum Qa=2     p50   2.1ms  p99   2.4ms  (응답 뒤 남은 일 처리 3593ms)
```

- 체인 = 합(2+2+2, 2+20+2). 프라이머리-백업 = 프라이머리 + 가장 느린 백업. 정족수 = 2번째로 빠른 노드.
- 정족수의 남는 문제: 느린 노드에도 계속 보내므로 일이 쌓인다. 200건 응답 뒤에도 3593ms 동안 밀린 일을 처리했다. 그동안 그 엔트리들의 실제 복제 수는 Qw보다 적다.

### 5. write quorum 계산

| entry | write quorum |
|---|---|
| 0 | B1 B2 B3 |
| 1 | B2 B3 B4 |
| 2 | B3 B4 B1 |
| 3 | B4 B1 B2 |
| 4 | B1 B2 B3 |
| 5 | B2 B3 B4 |

- 규칙: 앙상블에서 `(entryId % E)` 위치부터 Qw개(BookKeeper 프로토콜 문서). 서로 다른 write quorum은 E = 4개다. Qw = E면 하나뿐이라 스트라이핑이 없다.

### 6. 견디는 bookie 장애 수

- Qa − 1 = 1대. 프로토콜 문서: "The system can tolerate Qa – 1 failures without data loss."
- 성공 응답은 Qa(2)벌 영속화를 확인한 시점에 나간다. 나머지 1벌은 쓰는 중이거나 실패했을 수 있다. 그래서 Qw(3)벌을 기준으로 "2대까지 안전"이라고 하면 틀리다.

### 7. 펜싱

- write quorum마다 (Qw − Qa) + 1개(E=5·Qw=3·Qa=2면 2개)의 펜싱 응답이 필요하다.
- 이유: 한 write quorum의 Qw개 중 (Qw − Qa) + 1개가 펜싱되면, 펜싱 안 된 bookie는 Qa − 1개 이하다. 옛 writer는 어느 write quorum에서도 Qa개 확인을 모을 수 없다.
- `LedgerFenced`는 "그 엔트리가 안 쓰였다"가 아니라 "쓰였을 수도 안 쓰였을 수도 있다"이다. 복구가 끝나 원장이 닫힌 뒤에야 안다. 타임아웃처럼 다룬다(프로토콜 문서).

### 8. 배치 편중

(실험, Java 21, 2026-10-01)

```text
    항상 앞 3대    Bookie별 entry [28000, 28000, 28000, 0, 0]  최대/평균 1.67
    무작위 3대     Bookie별 entry [21000, 17000, 12000, 23000, 11000]  최대/평균 1.37
    시작 위치 순환   Bookie별 entry [20000, 20000, 20000, 12000, 12000]  최대/평균 1.19
```

- "항상 앞 3대"는 두 대가 논다. 무작위는 원장 수가 적으면 운에 따라 편중된다.
- 순환 배치도 1.19다. 핫 원장 0(9000)이 bookie 0·1·2에 얹혔다. 스트라이핑은 원장 **안의** 부하만 나눈다. 원장 간 쏠림은 배치와 원장 크기가 정한다. 큰 원장은 롤오버로 쪼갠다.

### 9. 체인 쓰기 지연 급증

- 의심: 체인의 어느 한 노드가 느리다(GC, 디스크). 체인 쓰기는 노드 처리의 합이라 한 대가 전체를 붙잡는다. 읽기는 테일만 쓰므로 멀쩡할 수 있다.
- 볼 지표: 노드별 처리 시간 p99, 각 노드의 "보냈지만 테일 확인 전" 버퍼 길이(뒤쪽이 느리면 앞쪽 버퍼가 는다).
- 딜레마(6.5840 L13): 서버 하나만 멈춰도 체인 전체가 멈추니 빨리 장애로 판정하고 싶다. 그러나 너무 빨리 판정하면 멀쩡한 서버를 빼고 새 서버에 데이터를 복사하느라 시간을 버린다.

### 10. 옛 테일의 옛 값

- 원인: 옛 테일이 살아 있는데 설정 서버와만 끊겼다. 더 이상 갱신을 못 받지만 그에게 붙은 클라이언트의 읽기에는 답한다. split brain이다. 논문은 이것을 다루지 않는다(6.5840 CR FAQ).
- 대처: 설정 서버가 테일에 리스를 주고, 리스가 끝난 뒤에만 새 테일을 정한다. 클라이언트·노드가 설정 세대 번호를 확인해 옛 세대의 테일을 거른다(12번 펜싱).
