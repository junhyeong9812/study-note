# distributed/20-data-ownership-and-cross-service-queries — 정답

## 정답

### 1. 두 방식과 Shared Database의 결합

- Shared Database: 여러 서비스가 한 DB를 쓰고, 서로의 표를 로컬 ACID 트랜잭션으로 직접 읽고 쓴다.
- Database per Service: 각 서비스의 데이터는 그 서비스 전용이고, 다른 서비스는 그 서비스의 API로만 접근한다.
- Shared Database의 결합(microservices.io)
  - 개발 시점: 주문 팀이 고객 표를 쓰면, 고객 팀의 스키마 변경을 주문 팀과 조율해야 한다.
  - 런타임: 고객 서비스의 긴 트랜잭션이 주문 표에 락을 쥐면 주문 서비스가 막힌다.

### 2. 열 이름 변경

- (a) 성공한다. DB는 다른 서비스가 그 열을 쓰는지 모른다(DB 객체 의존이 없으면).
- (b) `ERROR: column c.full_name does not exist` — 배포하지 않은 다른 팀의 서비스가 깨진다(실험, PostgreSQL 17.11).
- *분산 모놀리스*: 서비스는 나눴지만 공유 DB 때문에 함께 깨지는 구조.

### 3. 서버 하나로 하는 Database per Service

- 된다. private tables per service, schema per service, database server per service 중 고를 수 있다.
- 장벽: 서비스마다 다른 DB 사용자를 두고 grant로 자기 데이터에만 접근하게 한다. 장벽이 없으면 개발자는 API를 우회하고 싶어진다.
- 실험: 권한을 거두자 주문 서비스의 직접 조회가 `ERROR: permission denied for table customers`로 막혔다. 우회가 운영 장애가 아니라 개발 중 오류로 드러난다.

### 4. 호출 수와 지연

- naive: 1 + 2 × 20 = 41호출. batch·병렬: 1 + 2 = 3호출.
- 실험(Java 21 HttpServer 3개, 호출당 서버 2ms, nodelay=true, 꼬리 없음): naive p50 149ms, batch p50 7ms.

### 5. 꼬리 지연의 증폭

- 0.95^20 ≈ 0.36. 한 페이지가 느린 호출을 하나도 안 만날 확률은 약 36%다.
- 그래서 절반 이상의 페이지가 100ms짜리 호출을 적어도 하나 만나고, p50부터 오른다(실험: 226ms). batch는 상품을 한 번만 불러 기대상 약 5%의 페이지만 느리다(실험: 14/200 = 7% 페이지가 100ms 이상, p99 104ms).

### 6. Command-side Replica vs Materialized View

- Command-side Replica: **명령을 처리하는 서비스**가 검증·계산에 쓸 남의 데이터(예: 주문 생성 시 상품 가격)를 이벤트로 복제해 둔다. 제공자를 런타임에 부르지 않는다.
- Materialized View: **조회**를 위해 여러 원천의 데이터를 조회에 맞는 모양으로 미리 만들어 둔다(CQRS의 읽기 모델).
- 공통으로 감수하는 것: 데이터가 오래될 수 있다(최종 일관성). 원천은 이벤트를 믿을 만하게 발행해야 한다.

### 7. 뷰 지연

- 평소에도 보이지 않았다. 실험에서 주문 직후 조회 200/200이 미반영이었고, 발행 ack부터 보이기까지 p50 15ms·p99 28ms였다.
- 프로젝터 3초 정지: 그 주문은 약 3초(max 3006ms) 동안 목록에 없었다.
- 피하는 법: 쓰기 응답으로 화면을 그린다(방금 만든 주문을 목록 위에 붙임). 또는 응답에 버전·오프셋을 주고 조회 서비스가 그만큼 반영할 때까지 짧게 기다린다. LAG·뷰 최신성 알람.

### 8. 영원히 어긋난 뷰

- 후보 1: 원천 변경 뒤 이벤트 발행이 실패했다(이중 쓰기 유실). 이벤트가 없으니 LAG는 0이다.
- 후보 2: 프로젝터가 그 이벤트 처리에 실패하고 건너뛰었다.
- 대처: 원천 발행을 outbox로. 프로젝터 실패는 DLQ + 알람. 뷰는 원천에서 다시 만들 수 있으므로 재구축 절차를 둔다(Azure "Materialized View": 뷰는 버려도 되는 사본).

### 9. Index Table

- 구성: 완전 비정규화(행 전체 복사), 정규화 인덱스(기본 키만 참조, 조회 2번), 부분 비정규화(자주 쓰는 열만 복사).
- 같은 트랜잭션이 불가능하면: 최종 일관성으로 설계하고, 원천 갱신 뒤 따로 색인 메시지를 발행하지 말라고 한다(그 사이 실패하면 색인이 오래된 채 남는다). 변경 피드나 transactional outbox를 쓰라고 권한다.
- 16번과의 연결: 이것이 정확히 이중 쓰기 문제이고, outbox·CDC가 그 해법이다.

### 10. 알고리즘·자료구조

- API Composer의 메모리 조인: 해시 조인. 한쪽 결과로 ID → 객체 해시맵을 만들고 다른 쪽을 훑으며 찾는다.
- 뷰 프로젝터: 이벤트 → 프로젝션 폴드. `뷰 = fold(apply, 빈 뷰, 이벤트들)`로 이벤트를 순서대로 접어 상태를 만든다.
