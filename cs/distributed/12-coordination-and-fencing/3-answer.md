# distributed/12-coordination-and-fencing — 정답

## 정답

### 1. 네 가지 재료

| 재료 | ZooKeeper | etcd | 락에서의 쓰임 |
|---|---|---|---|
| 합의로 정렬된 쓰기 | linearizable 쓰기, zxid | Raft, revision | 누가 먼저 잡았는지 모두가 같게 본다 |
| 생존 표시 | 세션 + ephemeral znode | lease | 소유자가 죽으면 락이 저절로 풀린다 |
| 줄 세우기 | sequential znode 순번 | create_revision | 대기 순서 = 소유 순서, 그리고 토큰의 재료 |
| 변경 알림 | watch | watch | 앞사람이 풀릴 때까지 폴링 없이 기다린다 |

### 2. herd effect 없는 락

```text
 /lock/
   lock-07  A  ← 가장 작음 = 소유
   lock-08  B  ← 07만 watch
   lock-09  C  ← 08만 watch
 A 죽음 → 세션 만료 → 07 삭제 → B만 깨어남
```

- 깨어난 B는 자식 목록을 다시 읽어 "내가 가장 작은가"를 확인한다.
- 이유: 앞사람이 소유자가 아니라 **기다리다 포기한 대기자**였을 수도 있다. 그 경우 B보다 작은 번호가 아직 남아 있다(논문 2.4절: "The previous lock request may have been abandoned").
- 앞사람만 watch하므로 해제 하나에 한 명만 깨어난다.

### 3. 멈춘 소유자의 늦은 쓰기

(실험, etcd 3.6.5 + Java 21)

| | 결과 |
|---|---|
| 토큰 검사 없음 | `A 쓰기 'A-stale' (토큰 검사 없음) → 반영`, `최종 acct = A-stale` — B의 쓰기가 조용히 사라짐 |
| 토큰 검사 | `A 쓰기 'A-stale' 토큰=41 → 거절(저장소가 본 토큰 42 > 41)`, `최종 acct = B-1` |

- A는 두 경우 모두 "아직 내가 락을 쥐었다"고 믿었다. 차이는 받는 쪽의 검사뿐이다.

### 4. "쓰기 직전에 확인"이 틀린 이유

- 확인과 쓰기는 두 단계다. 그 사이에 GC 멈춤·스케줄링·네트워크 지연이 들어갈 수 있고, 이 틈을 클라이언트 쪽에서 없앨 방법이 없다.
- 저장소가 검사하면 "토큰 비교 + 쓰기"가 저장소 안의 원자 연산 하나가 된다(etcd txn, SQL 조건부 UPDATE). 클라이언트가 언제 멈췄든, 저장소에 도착한 시점의 최대 토큰과 비교된다.

### 5. 토큰의 조건

- 조건: (1) 락을 잡을 때마다 **단조 증가** (2) 자원이 **검사에 참여**(지금까지 본 최대값보다 작으면 거절).
- etcd: 락 키의 `create_revision`. ZooKeeper: Kleppmann은 zxid나 znode 버전을 들었다. 다만 획득마다 새 znode를 만드는 락 레시피에서는 znode 버전이 매번 0부터라 쓸 수 없고, 락 znode의 `czxid`를 쓴다.
- 31·32, 41·42: 문제없다. etcd revision은 클러스터 전역이라 다른 키 쓰기에도 커진다. 연속일 필요는 없고 새 소유자의 토큰이 옛 소유자의 것보다 크기만 하면 된다.

### 6. Redis 단일 노드 락

(실험, Redis 7.4.9)

- 그냥 `DEL`: `1`을 돌려주고 **B의 락이 지워졌다**(남은 값 없음). 다음 대기자가 곧바로 잡을 수 있다.
- 소유자 확인 Lua(`GET == A-uuid`일 때만 `DEL`): `0`을 돌려주고 B의 락(`B-uuid`)이 남았다.
- 아직 없는 것: **단조 증가 토큰**. 고유값은 "남의 락을 지우지 않기"에는 쓰이지만, 자원이 늦은 쓰기를 거절하는 순서 비교에는 쓸 수 없다.

### 7. Redlock 논쟁

- 갈리는 지점
  1. 자원 쪽 검사의 재료: Kleppmann은 단조 증가 토큰이 필요하다고 본다. antirez는 고유 랜덤 값으로 check-and-set을 하면 같은 목적을 이룬다고 본다.
  2. 시간 가정: Kleppmann은 안전성이 키 만료 시간·지연·멈춤에 관한 가정에 기대는 것을 문제로 본다. antirez는 단조 시계를 쓰고 시계를 건드리지 않으면 흐른 시간은 오차 범위 안에서 잴 수 있다고 본다.
- 동의하는 지점: 자동 만료 락은 **멈췄다 깨어난 소유자**를 락만으로 막지 못한다. antirez도 이것이 모든 자동 만료 분산 락의 공통 문제라고 적는다.
- 덧붙임: redis.io 문서는 지금 fencing token 구현을 권하고, Redis TTL 만료가 단조 시계를 쓰지 않는다고 적는다.

### 8. ZooKeeper 세션 종료로 충분하지 않은 이유

- 세션이 끝나면 ZooKeeper는 그 세션의 ephemeral 노드를 지우고 **ZooKeeper에 대한** 이후 요청을 거절한다. ZooKeeper 안의 데이터는 이것으로 펜싱된다(6.5840 L9).
- 하지만 락으로 보호하려던 자원은 보통 ZooKeeper 밖(DB·파일 저장소)에 있다. 그 자원은 세션 상태를 모른다. 옛 소유자의 쓰기는 그대로 도착한다. 그래서 자원이 검사할 토큰이 필요하다.

### 9. 조용히 덮인 정산 값

- 볼 것: 두 서버의 락 획득·만료 시각, 각 서버 GC 로그(TTL보다 긴 멈춤), 락 저장소 페일오버·시각 변경 이력, 자원 쪽 마지막 쓰기의 출처.
- 좁히기: 한 서버의 긴 멈춤과 다른 서버의 획득 시각이 겹치면 1번 시나리오(멈춘 소유자). Redis 페일오버나 시각 변경과 겹치면 2번(시계·복제).
- 막기: 토큰을 모든 쓰기에 싣고 자원이 검사한다(`UPDATE ... WHERE last_token <= ?`). 거절 횟수를 지표로 낸다. 정확성용이면 합의 저장소로 옮긴다.

### 10. 토큰을 못 싣는 외부 API

- 멱등 키(요청 ID)를 API에 함께 보내 같은 요청의 두 번째 실행을 상대가 무시하게 한다.
- 지원하지 않으면 락을 잃는 즉시 멈추는 규칙(짧은 기한·세션 끊김 핸들러)으로 겹침을 줄인다. 그래도 남는 이중 호출은 사후 대사(대조)로 찾는다. 락만으로 막을 수는 없다.
