# distributed/32-distributed-cache-consistency — 정답

## 정답

### 1. 여기서 말하는 일관성

- 선형화는 "읽기가 그보다 먼저 끝난 쓰기를 반영한다"는 보장이다(07번 주제). memcache는 그것을 목표로 하지 않는다.
- L16 노트: 이 논문의 일관성은 "읽기가 최근 쓰기보다 얼마나 뒤처지나"라는 사용자 경험 관점이다. 보장된 성질이 아니다.
- 목표 두 가지
  - 최종 일관성 — 논문 §5는 "최선 노력(best-effort) 최종 일관성"이라고 적는다. 낡은 값이 고착되지 않고 결국 따라잡는다.
  - 자기가 쓴 것 읽기(read-your-own-writes) — 쓴 웹 서버가 자기 클러스터 캐시를 직접 지워, 같은 사용자 요청 안에서 자기 쓰기를 본다(§4.1).
- 이유: 대상이 뉴스피드·좋아요 같은 데이터라 몇 초 낡아도 사람이 견딘다(L16). 대신 쓰기는 DB 트랜잭션으로 정확하게 한다.

### 2. set 대신 delete

```text
  C1: DB ← v1 ─────────────── mc.set(k, v1)
  C2:      DB ← v2 ── mc.set(k, v2)
  DB 도착 순서: v1 → v2 (최종 v2)
  캐시 도착 순서: v2 → v1 (최종 v1)   ✘ 캐시와 DB가 영구히 다를 수 있다
```

- 갱신(`set`)은 도착 순서에 따라 결과가 달라진다. DB와 캐시에 닿는 순서가 다르면 옛 값이 남는다(L16).
- 삭제는 어느 순서로 와도 결과가 "없음"이다. 논문 §2: "deletes are idempotent". 다음 읽기가 DB에서 최신 값을 채운다.
- 캐시는 원본이 아니므로 지워도 정확성은 깨지지 않는다. 부하만 는다(§5).

### 3. stale set과 lease

```text
  C1: get miss → [lease t7] → DB 읽기 v1 ─────────────(느림)──────▶ set(k, v1, t7) → 거절 ✔
  C2:                          DB ← v2 커밋 → delete(k) → t7 무효
       lease 없으면 여기서 set(k, v1)이 성공해 v1이 고착된다 ✘
```

- 원인: 쓰기보다 **먼저** DB를 읽은 채우기 요청의 set이 삭제보다 **늦게** 도착했다. 삭제를 커밋 뒤로 옮겨도 이 순서는 생긴다.
- lease: miss 때 캐시 서버가 키에 묶인 64비트 토큰을 준다. delete가 오면 그 토큰을 무효로 만든다. set은 토큰이 유효할 때만 저장된다(§3.2.1, LL/SC와 비슷).
- 로컬 실험(Redis 7.4.9 + Lua, 순서 고정): lease 없이 `SET v=1 -> OK`, 결과 `cache=1 db=2`. lease로 `LSET(token=1, v=1) -> 0`, 결과 `cache=null db=2`. 키 200개 3초 경합에서는 고착 키가 lease 없이 3·4개, lease로 0·0개였다(점검 재실행 10번: lease 없이 2~7개, lease로 모두 0개).

### 4. 동시 miss 50개

(실험, Redis 7.4.9 + Java 21, DB 조회 3ms 시뮬레이션, 2026-10-01)

```text
herd       lease=false concurrent misses=50  db reads=26
herd       lease=true  concurrent misses=50  db reads=1
```

- lease 없이: 50개 중 상당수(이 실행에서 26개, 점검 재실행 5회에서는 31~50개 — 4회는 50개 전부)가 DB로 간다. 정확한 수는 실행마다 크게 다르다. 먼저 채운 값이 보이기 전에 출발한 요청은 모두 DB로 간다.
- lease로: 첫 miss만 토큰을 받아 DB에 가고, 나머지는 `WAIT` 뒤 재시도해 hit한다 → DB 1회.
- 논문 실측(§3.2.1): 허드에 취약한 키 집합의 일주일치 miss에서 DB 최대 조회율이 17K/s → 1.3K/s. 설정은 키당 10초에 토큰 하나.

### 5. 커밋 로그 무효화 vs 웹 서버 방송

| | mcsqueal(커밋 로그) | 웹 서버 직접 방송 |
|---|---|---|
| 무엇을 지우나 | **커밋된** SQL에 붙은 키 | 웹 서버가 아는 키 |
| 패킷 | 데몬이 묶어서 mcrouter로 → 패킷당 삭제 수 중앙값 18배 | 묶음이 어려워 패킷 부담 큼 |
| 잘못됐을 때 | 로그를 재생해 잃거나 잘못 간 무효화 복구 | 되돌릴 방법이 거의 없음(예전엔 캐시 전체 순차 재시작) |

- 논문이 든 웹 서버 방송의 두 문제(§4.1): ① 묶음 전송을 잘 못해 패킷 부담이 크다. ② 설정 오류로 삭제가 잘못 라우팅되는 등 체계적 문제가 나면 복구 수단이 없다.
- 그래도 자기 클러스터는 직접 지운다: 한 사용자 요청 안에서 자기 쓰기를 보게 하고(read-after-write), 자기 클러스터에 낡은 값이 머무는 시간을 줄이려고(§4.1).
- 참고: 발행한 삭제 중 실제 캐시 데이터를 지운 것은 4%였다. 대부분 "없는 것을 지운다".

### 6. 복제 지역의 쓰기와 remote marker

- 문제: 복제 지역의 사용자가 쓰면 쓰기는 원본 지역 DB로 간다. 자기 지역 DB 복제본은 복제 지연만큼 늦다. 그 사이 miss가 로컬 복제본에서 옛 값을 읽어 캐시에 넣으면, 사용자가 방금 쓴 것이 보이지 않고 옛 값이 캐시된다(§5).
- remote marker 세 단계(§5)
  1. 지역에 마커 `rk`를 세운다.
  2. 원본 DB에 쓰면서 `k`와 `rk`를 무효화 대상으로 SQL에 넣는다(해석: 복제가 그 지역 DB에 도착하면 그 지역의 무효화 데몬이 `k`와 함께 마커도 지운다 — §5 Operational considerations의 "복제 DB에도 같은 삭제 시스템을 둔다").
  3. 자기 클러스터에서 `k`를 지운다.
  - 이후 `k` miss 때 `rk`가 있으면 원본 지역에서 읽는다.
- 비용: miss 때 지역 간 지연이 붙는다. 같은 키를 동시에 고치면 한 작업이 다른 작업의 마커를 지워 낡은 정보가 보일 수 있다. 마커는 캐시와 달리 지워지면 정확성에 영향을 준다(논문은 실제로는 드물다고 적는다).

### 7. 캐시 서버 장애와 Gutter

- 의심: 죽은 서버의 키를 남은 서버로 재해시했다. 핫키 하나가 서버 요청의 20%를 차지할 수 있어, 그것을 받은 서버도 넘친다(§3.3). 넘친 서버가 느려지면 클라이언트가 DB로 가서 연쇄가 된다.
- Gutter: 클러스터 서버의 약 1%인 놀고 있는 예비 풀. get에 응답이 없으면 클라이언트가 Gutter에 다시 묻고, miss면 DB에서 읽어 Gutter에 넣는다. 부하를 바쁜 서버가 아니라 놀고 있는 서버로 보낸다.
- 효과(§3.3): 클라이언트가 보는 실패 99% 감소, 매일 실패의 10~25%를 hit로 바꿈, 서버가 통째로 죽으면 대개 4분 안에 Gutter 적중률 35% 초과.
- 빨리 만료시키는 이유: Gutter에는 무효화를 보내지 않는다. 짧은 수명이 낡은 기간의 상한이 된다. L16 노트의 추측으로는, Gutter는 어떤 키든 가질 수 있어 무효화를 보내려면 삭제 트래픽이 최소 두 배가 되기 때문이다.

### 8. 추적 테이블 상한과 가짜 무효화

(실험, 전용 `redis:7-alpine` 7.4.9, `--tracking-table-max-keys 100`, 2026-10-01)

```text
keys read=1000, writes after read=0, invalidation messages=900 (keys invalidated=900), tracking_total_keys:100
```

- 약 900건. 쓰기가 0이어도 테이블이 100개를 넘으면 서버가 옛 항목을 "바뀐 척" 무효화하고 지운다(Redis 문서 "Client-side caching"). 1,000 − 100 = 900.
- 로컬 캐시는 그 키들을 지운다. 적중률이 떨어진다. 대처는 상한 조정, `OPTIN`, BCAST.

### 9. cold cluster warmup의 무기한 옛 값

```text
  cold 클라이언트 A: DB ← v2 → cold.delete(k)
  cold 클라이언트 B:                 cold miss → warm.get(k) = v1(아직 무효화 전) → cold.add(k, v1)
  warm 클러스터:                                                      ← 늦게 무효화 도착
  결과: cold에 v1이 무기한 남는다(그 키가 다시 쓰일 때까지)
```

- 원인: warm 클러스터에 무효화가 닿기 전에, cold 클라이언트가 warm의 옛 값을 가져와 넣었다(§4.3).
- 대책: cold 클러스터의 삭제를 2초 hold-off로 낸다. hold-off 동안 같은 키의 `add`는 거절된다. `add` 실패는 "DB에 더 새 값이 있다"는 신호이므로 클라이언트가 DB에서 다시 읽는다. 2초보다 늦는 삭제는 이론상 가능하지만 드물다고 논문이 적는다. 적중률이 안정되면 warmup을 끈다.
- 로컬 실험(Redis 7.4.9): 2초 묘비 + `SET NX`로 흉내 내자 hold-off 안의 옛 값 채우기가 nil로 거절됐고, 만료 뒤 v2가 들어갔다.
