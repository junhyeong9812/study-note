# distributed/32-distributed-cache-consistency — 질문

## 질문

1. (왜) memcache 논문과 6.5840 L16이 말하는 "일관성"은 선형화와 무엇이 다른가? 이 시스템이 목표로 하는 두 가지 성질은?
2. (왜) 쓰기 때 캐시를 `set`으로 갱신하지 않고 `delete`로 지우는 이유를, 두 클라이언트가 같은 키에 동시에 쓰는 시간축으로 설명하라.
3. (그림) "커밋 뒤 삭제"를 지켜도 오래된 값이 고착되는 stale set 경합을 시간축으로 그리고, lease가 이 경합의 어느 지점에서 무엇을 거절하는지 표시하라.
4. (예측) Redis 위 Lua lease 실험에서 핫키 하나를 지운 직후 동시 miss 50개를 출발시켰다. lease가 없을 때와 있을 때 DB 조회 수는 대략 어떻게 나올까? 논문의 실측 수치(DB 최대 조회율)도 함께 말하라.
5. (경계) mcsqueal 방식(커밋 로그에서 무효화)과 "웹 서버가 모든 클러스터에 직접 삭제 방송"을 비교하라. 논문이 든 웹 서버 방송의 두 문제는? 그런데도 웹 서버가 자기 클러스터에는 직접 지우는 이유는?
6. (연결) 원본 지역이 아닌 복제 지역에서 쓰기가 일어날 때, 복제 지연 때문에 생기는 문제와 remote marker의 세 단계를 설명하라. 이 장치가 내주는 비용은?
7. (장애 진단) 캐시 서버 한 대가 죽은 뒤 다른 캐시 서버들이 차례로 과부하에 빠졌다. 무엇을 의심하고, Gutter는 어떻게 다르게 대응하나? Gutter 항목을 빨리 만료시키는 이유는?
8. (예측) `tracking-table-max-keys`를 100으로 둔 Redis 7.4에서, 한 클라이언트가 `CLIENT TRACKING`을 켜고 키 1,000개를 읽기만 했다. 이후 쓰기가 0건이면 무효화 메시지는 몇 건쯤 올까? 이유는?
9. (장애 진단) 빈 클러스터를 다른 클러스터 캐시로 데우는 중(cold cluster warmup)에 일부 키가 무기한 옛 값으로 남았다. 경합의 순서와 논문의 hold-off 대책을 설명하라.
