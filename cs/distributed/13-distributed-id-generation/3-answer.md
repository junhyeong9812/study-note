# distributed/13-distributed-id-generation — 정답

## 정답

### 1. 비교와 Snowflake의 동기

| | 조율 | 정렬 | 크기 |
|---|---|---|---|
| DB 시퀀스 1개 | 매번 DB 왕복 | 있음 | 64비트 |
| UUIDv4 | 없음 | 없음 | 128비트 |
| Snowflake | worker ID 배정만 | 대체로 시간 순 | 64비트 |
| UUIDv7 | 없음 | 대체로 시간 순 | 128비트 |
| 시퀀스 블록 | 구간마다 한 번 | 구간 안에서만 | 64비트 |

- 트위터 README: MySQL에서 Cassandra로 옮기는데 Cassandra에 순차 ID 기능이 없었다. 요구는 조율 없음, k-sorted(대략 시간 순), 64비트 이하, 프로세스당 초당 1만 개 이상.

### 2. Snowflake 배치

```text
  [0][ 시각 41비트 (twepoch부터 ms) ][ DC 5 ][ 워커 5 ][ 순번 12 ]
```

- 2^41 ms ≈ 69.7년(실험 출력 `41비트 시각 한계(년): 69.7`). twepoch는 1288834974657(2010-11-04 UTC).
- 같은 ms에 순번이 4095를 넘어 0으로 돌면 `tilNextMillis`로 다음 ms가 올 때까지 바쁜 대기 후 발급한다.

### 3. 시계 역행 — 실행 중 vs 재시작

- 실행 중: `now < lastTs`라서 예외(`Clock moved backwards. Refusing for 499ms`). ID는 나오지 않는다.
- 재시작: `lastTs`가 메모리 변수라 사라졌다. 되돌아간 500ms 구간의 ID를 다시 낸다. 실험에서 2500개 중 2500개가 중복.
- 결론: 재시작 역행까지 막으려면 마지막 발급 시각을 영속화하고, 기동 시 그 시각이 지날 때까지 기다린다.

### 4. worker ID 중복

- 6000개 중 3000개 중복(실험). 두 인스턴스가 같은 시각·같은 worker·같은 순번 계열을 쓰므로 한쪽이 내는 ID가 다른 쪽과 정확히 같다.
- 시각이 ms마다 같이 흐르면 거의 모든 쌍이 겹친다. 부하가 달라 순번이 어긋나도 같은 (ms, 순번)이 나오면 겹친다.

### 5. "시간 순"의 범위

- 한 노드 안: 시계가 뒤로 가지 않는 한 엄격히 증가한다.
- 노드 사이: 시계 어긋남만큼 흐트러진다. 실험에서 B 시계가 3ms 느리자 나중에 만든 B의 ID가 더 작았다.
- 같은 ms 안의 다른 노드: worker 번호가 순서를 정한다. 실제 발생 순서와 관계가 없다.

### 6. UUIDv7

```text
  [ unix_ts_ms 48 ][ver 4 = 7][ rand_a 12 ][var 2][ rand_b 62 ]
```

- 세 방법(RFC 9562 §6.2): Method 1 고정 길이 카운터, Method 2 무작위 시작 단조 증가, Method 3 ms 미만 시각으로 rand_a 채우기.
- PostgreSQL 18 `uuidv7()`: Method 3(rand_a 12비트 = ms 미만 시각). 같은 백엔드(세션) 안에서는 직전보다 최소 한 단계 큰 시각을 쓰므로 증가한다. 세션 사이 순서는 보장하지 않는다(`uuid.c`).

### 7. PostgreSQL 18 인덱스 비교

- 실험 결과

| PK | 크기 | 리프 | 밀도 | 단편화 |
|---|---|---|---|---|
| bigint | 4408 kB | 547 | 89.95 | 0 |
| v4 | 8376 kB | 1039 | 66.46 | 49.18 |
| v7 | 6184 kB | 767 | 89.91 | 0 |

- v4 행은 실행마다 조금 다르다(재실행: 8608 kB·밀도 64.66·단편화 49.81, 8392 kB·66.33·49.47). 경향은 같다.
- v4는 무작위 위치에 꽂혀 중간 페이지가 반씩 갈라진다 → 밀도 약 2/3, 단편화 약 절반.
- v7·bigint는 오른쪽 끝에만 붙는다 → 밀도 약 90%(B-tree 기본 fillfactor 90).
- v7이 bigint보다 큰 것은 키가 16바이트(vs 8바이트)라서다. 순서 때문이 아니다.

### 8. 시퀀스 블록

- 장점: 구간(예: 100개)마다 한 번만 중앙과 통신한다. 실험에서 500개에 왕복 6번, 중복 0.
- 부작용 1: 인스턴스 사이 순서가 없다. 실험에서 시간 순으로 나열하면 247/499가 앞보다 작았다.
- 부작용 2: 재시작하면 남은 구간이 버려져 번호 공백이 생긴다(451~500).
- PostgreSQL `CACHE n`은 세션이 n개를 미리 받는 같은 구조이고 문서도 구멍과 세션 간 순서 비보장을 적는다. JPA `allocationSize`(기본 50)도 시퀀스에서 그만큼 미리 받는 같은 생각이다.

### 9. JavaScript 정밀도

- 원인: JSON 숫자를 `Number`로 읽으면 2^53−1(9007199254740991)을 넘는 정수가 정확하지 않다. 실험: `2102038470456406017` → `2102038470456406000`.
- 대처: API에서 ID를 문자열로 내보낸다. JS에서 연산하려면 `BigInt`.
- 시점: 시각이 22비트 위에 있으므로 epoch 뒤 2^31 ms(약 25일)를 넘으면 2^53을 넘는다. 실서비스 ID는 사실상 처음부터 걸린다.

### 10. etcd 리스 배정

- 원자적 생성: 트랜잭션 비교 `create("/…/worker/7") = "0"`(키가 없을 때만)으로 `put --lease`. 실험에서 host-a는 SUCCESS, host-b는 FAILURE였다.
- 리스만으로 부족한 경우: 리스를 쥔 인스턴스가 GC·VM 정지로 멈췄다 깨어나면 리스가 이미 끝나 다른 인스턴스가 같은 번호를 잡았는데도 옛 인스턴스가 발급을 계속할 수 있다.
- 대처: keep-alive가 실패하면 즉시 발급을 멈춘다. 회수한 번호는 옛 주인의 마지막 발급 시각이 지난 뒤 재사용한다. 필요하면 세대 번호(etcd revision 등)를 함께 기록한다(12번 fencing).
