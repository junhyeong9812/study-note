#### 1. `HeapDijkstra.distances` (TODO 1~3)

정답 구현 (impl):

```java
public static long[] distances(CountedGraph g, int start, CountedHeap heap) {
    int n = g.vertices();
    if (start < 0 || start >= n) {
        throw new IndexOutOfBoundsException("시작 정점이 범위 밖이다: " + start);
    }

    long[] dist = new long[n];
    Arrays.fill(dist, Long.MAX_VALUE);      // TODO 1: 무한대 = 아주 큰 값. -1 이면 비교가 안 된다
    boolean[] done = new boolean[n];

    dist[start] = 0;
    heap.push(0, start);

    while (!heap.isEmpty()) {
        CountedHeap.Entry top = heap.pop();
        int v = top.vertex();
        // TODO 2: 낡은 항목이면 버린다. 이미 더 짧은 거리로 확정된 정점이다.
        if (done[v]) {
            heap.markStale();
            continue;
        }
        done[v] = true;

        for (int i = 0; i < g.degree(v); i++) {   // TODO 3: 이웃 완화
            CountedGraph.Edge e = g.edge(v, i);
            long candidate = dist[v] + e.weight();
            if (candidate < dist[e.to()]) {       // 더 짧아졌을 때만 힙에 넣는다
                dist[e.to()] = candidate;
                heap.push(candidate, e.to());
            }
        }
    }

    for (int i = 0; i < n; i++) {                 // 내부 표현 -> 외부 계약
        if (dist[i] == Long.MAX_VALUE) {
            dist[i] = UNREACHABLE;                // -1
        }
    }
    return dist;
}
```

- 논리: "미확정 중 거리가 가장 작은 정점을 꺼내 확정"만 반복한다. 힙은 그 "가장 작은 것 꺼내기"를 log V에 해주는 도구다.
- 논리: 감소 키가 없으니 **고치는 대신 하나 더 넣는다**(게으른 방식) — 대가로 낡은 항목이 쌓이고, 그것은 꺼낼 때 걸러낸다.
- 비용: O(E log V)가 상한. 실측은 훨씬 아래다 — 힙 삽입은 간선 수가 아니라 "거리가 개선된 횟수"를 따른다(3절).
- 한계: 음수 간선이 하나라도 있으면 확정 논증이 무너진다. 그래서 `CountedGraph.addEdge`가 입력 단계에서 막는다.

**질문별 답**

- Q: 거리 초기값을 -1로 두면 왜 비교가 안 되고, 대신 무엇으로 두는가?
  A: 완화는 `새 거리 < dist[이웃]`이라는 **크기 비교**로 한다.
  -1은 어떤 실제 거리보다도 작아서 "이미 더 짧다"로 읽히고, 그러면 갱신이 영영 안 일어난다.
  그래서 `Long.MAX_VALUE`(무한대 역할)로 채우고, 마지막에 남아 있는 MAX_VALUE만 UNREACHABLE(-1)로 바꾼다.

- Q: 그 큰 값(`Long.MAX_VALUE`)에 간선 가중치를 더하면 무슨 일이 생기고, 구현은 그 덧셈을 어떻게 피하는가?
  A: 넘친다 — `long`이라도 `MAX_VALUE + 1`은 음수(MIN_VALUE)가 되어 **갑자기 가장 짧은 길**이 된다.
  힙 판은 힙에 들어간 정점만 꺼내는데, 힙에는 거리가 확정 가능한 유한 값일 때만 들어간다 — 그래서 `dist[v]`가 무한대인 상태로 완화를 시도하는 일이 없다.
  배열 판은 후보 선택에서 `dist[v] != Long.MAX_VALUE`를 명시적으로 걸러 같은 일을 한다.

- Q: "감소 키가 없다"는 것은 무슨 뜻이고, 게으른 방식은 그것을 어떻게 우회하는가?
  A: 감소 키(decrease-key)는 힙 **안에 이미 들어 있는 항목의 값을 제자리에서 줄이는** 연산인데, 자바 `PriorityQueue`에는 없다.
  게으른 방식은 고치는 대신 `(줄어든 거리, 정점)`을 **새로 하나 더 넣는다**.
  같은 정점이 여러 번 들어가지만 가장 작은 것이 먼저 나오므로, 뒤에 나오는 낡은 것들은 꺼낼 때 버리면 답은 맞는다.

- Q: 힙에서 꺼낸 정점이 이미 확정된 것일 수 있는 이유는 무엇인가?
  A: 그 정점이 거리가 줄 때마다 힙에 하나씩 더 들어갔기 때문이다.
  가장 짧은 항목이 먼저 나와 확정되고, 같은 정점의 더 긴 옛 항목들은 힙에 그대로 남아 나중에 나온다.
  테스트 `distanceImprovesLater`가 이 경우다 — 3의 거리가 10으로 잡혔다가 3으로 줄어, `(10,3)`이 낡은 항목으로 정확히 하나 나온다.

- Q: 낡은 항목은 무엇으로 걸러내고, 걸러낼 때 `markStale()`을 안 부르면 무엇이 잘못되는가?
  A: `done[v]`(이미 확정 표시)로 걸러낸다 — 확정된 정점이 또 나오면 `continue`로 버린다.
  `markStale()`을 안 불러도 **답은 똑같이 맞는다** — 그래서 더 위험하다.
  이 박스의 핵심 측정(낡음 비율 24%↔76%)이 0이 되어, 결과에 안 나타나는 비용이 아예 안 보이게 된다.

- Q: 이웃 갱신에서 "더 짧아졌을 때만" 힙에 넣는 이유는 무엇이고, 항상 넣으면 실측이 어떻게 달라지는가?
  A: 더 짧아지지 않은 후보는 답에 아무 영향이 없으므로 넣어봐야 나중에 낡은 항목으로 버려질 뿐이다.
  V=300 완전 그래프 측정: 간선 조회 89,700번인데 힙 삽입은 1,273번 — **70배 차이**다.
  항상 넣으면 삽입이 간선 수(89,700)를 따라가고 힙 최대 크기도 그만큼 부풀어, O(E log V)라는 상한에 실제로 붙게 된다.

- Q: 힙에서 가장 작은 거리를 꺼내면 그 거리가 더는 안 줄어든다 — 논증을 말해보라?
  A: 꺼낸 거리를 d라 하자. d보다 짧은 다른 길이 있다면 그 길은 아직 확정 안 된 어떤 정점 u를 지나야 하고, u의 현재 거리는 힙에서 최소인 d 이상이다.
  거기서 더 지나가면 간선 가중치가 붙어 거리는 늘기만 한다 — 그러니 그 길의 총 거리는 d 이상이다.
  즉 d보다 짧은 길이 존재할 수 없으므로 d를 확정해도 된다.

- Q: 그 논증에서 "가중치가 음수가 아니다"는 어느 자리에 쓰였는가?
  A: "거기서 더 지나가면 거리는 **늘기만 한다**"는 한 줄이다.
  음수 간선이 있으면 이미 d 이상인 정점을 지나고도 총합이 d보다 작아질 수 있어, 이 문장이 바로 거짓이 된다.
  논증 전체가 이 한 줄에 걸려 있다.

- Q: 음수 가중치를 그래프 쪽에서 막는 이유는 무엇인가(막지 않으면 어떻게 되나)?
  A: 막지 않으면 **예외 없이 조용히 틀린 답**이 나오기 때문이다 — 이미 확정한 정점의 거리가 나중에 더 줄어드는데 다시 볼 방법이 없다.
  틀린 답은 그럴듯해 보여서 알아채기 어렵다. 그래서 `CountedGraph.addEdge`가 입력 시점에 `IllegalArgumentException`으로 잘라, 실패를 계산 뒤가 아니라 입력 때 드러낸다.
  음수 간선이 필요한 경우는 다익스트라의 영역이 아니라 15번(벨만-포드)의 영역이다.

- Q: BFS(11번)의 큐를 힙으로 바꾼 것이 다익스트라라는 관점에서, 무엇이 같고 무엇이 달라졌는가?
  A: 같은 것: "정점 하나를 꺼내 확정하고 이웃을 완화한다"는 뼈대와 방문/확정 표시.
  달라진 것: 꺼내는 순서를 **넣은 순서(큐)**가 아니라 **거리가 작은 순서(힙)**로 바꿨다.
  BFS는 모든 간선 비용이 같아서 "넣은 순서 = 거리 순서"였다 — 그 등식이 깨지는 순간 힙이 필요해진다.

#### 2. `DenseDijkstra.distances` (TODO 4~6)

정답 구현 (impl, 핵심부):

```java
public static long[] distances(CountedGraph g, int start, long[] scans) {
    long[] dist = new long[n];
    Arrays.fill(dist, Long.MAX_VALUE);
    boolean[] done = new boolean[n];
    dist[start] = 0;

    for (int round = 0; round < n; round++) {        // TODO 4: 라운드 = 정점 수만큼
        int best = -1;
        for (int v = 0; v < n; v++) {                // TODO 5: 선형 탐색으로 최솟값 고르기
            scans[0]++;                              // 이게 이 판의 비용이다
            if (!done[v] && dist[v] != Long.MAX_VALUE && (best == -1 || dist[v] < dist[best])) {
                best = v;                            // 무한대인 정점은 후보에서 제외
            }
        }
        if (best == -1) {                            // 남은 정점에 닿을 수 없으면 끝
            break;
        }
        done[best] = true;

        for (int i = 0; i < g.degree(best); i++) {   // TODO 6: 완화 — 힙 판과 완전히 같다
            CountedGraph.Edge e = g.edge(best, i);
            long candidate = dist[best] + e.weight();
            if (candidate < dist[e.to()]) {
                dist[e.to()] = candidate;            // 힙에 넣는 줄이 없다
            }
        }
    }
    // ... MAX_VALUE -> UNREACHABLE
}
```

```
두 판의 차이는 "다음 정점 고르기" 한 곳뿐이다

  힙 판    : heap.pop()            -> log V
  배열 판  : 0..V-1 을 전부 훑기   -> V

 라운드별 훑기 (확정된 것도 계속 훑는다)

  라운드 0: [ . . . . . . . . ]   V 칸
  라운드 1: [ x . . . . . . . ]   V 칸
  라운드 2: [ x x . . . . . . ]   V 칸
       ...
  라운드 V-1                      V 칸
                                  --------
                                  V x V 칸
```

- 논리: 힙을 아예 안 쓴다 — 감소 키 문제도, 낡은 항목도 없다. 대신 매 라운드 V칸을 훑는다.
- 논리: 완화 부분은 힙 판과 글자까지 같다(힙에 넣는 줄만 없다) — 그래서 두 판의 간선 조회 수가 정확히 같다(89,700).
- 비용: O(V²). 간선 수를 아예 안 본다.
- 한계: 성긴 그래프에서 낭비가 크다 — V=2,000·E=7,884에서 3,944,000번 훑는다(간선 수의 500배).

**질문별 답**

- Q: 라운드는 최대 몇 번 돌고, 한 라운드에 무엇이 확정되는가?
  A: 최대 정점 수(V)번이다 — 한 라운드에 정점 하나가 확정되므로 V번이면 전부 확정된다.
  다만 닿을 수 없는 정점이 남으면 후보가 없어 그 전에 멈춘다.
  그래서 실측 탐색 수는 V²보다 조금 적을 수 있다(측정 테스트가 `<= V*V`로만 주장한다).

- Q: 아직 안 닿은 정점(거리 무한)을 후보로 고르면 무슨 일이 생기는가?
  A: **거리가 무한인 정점을 확정해버린다.**
  확정된 뒤에는 나중에 실제로 닿는 길이 생겨도 다시 안 보므로 그 정점은 영영 UNREACHABLE로 남는다.
  게다가 그 무한대에서 완화를 시도하면 `MAX_VALUE + 무게`가 넘쳐 음수가 된다 — 그래서 `dist[v] != Long.MAX_VALUE` 조건이 오답과 오버플로를 한 번에 막는다.

- Q: 후보가 하나도 없으면 어떻게 해야 하고, 계속 돌면 무엇이 낭비되는가?
  A: 거기서 `break` — 남은 정점에는 영영 못 닿으므로 더 할 일이 없다.
  계속 돌면 라운드마다 V칸을 훑고 매번 `best == -1`만 확인하는 헛일이 쌓인다.
  끊어진 그래프에서 그 낭비가 그대로 (남은 라운드 × V)만큼 붙는다.

- Q: 이웃 갱신에서 힙 판과 달리 안 해도 되는 일은 무엇인가?
  A: **힙에 넣는 일**(`heap.push`)이다.
  다음 정점을 어차피 배열을 훑어 찾으므로 "줄어든 거리를 어딘가 기록해 둘" 곳이 `dist` 배열 하나뿐이다.
  그래서 낡은 항목이라는 개념 자체가 없고, `markStale()`도 없다.

- Q: `scans`를 배열(길이 1)로 받는 이유는 무엇인가?
  A: 자바는 값 전달이라 `long`을 그냥 받으면 함수 안의 증가가 호출자에게 안 돌아간다.
  계측값을 밖으로 내보내려면 참조로 담을 그릇이 필요한데, 길이 1짜리 배열이 가장 싼 그릇이다.
  반환값은 이미 거리 배열이 쓰고 있어 거기에 비용을 섞을 수 없다는 사정도 있다. (마지막 문장은 원본에 근거 없음 — 내 추론)

- Q: 두 판에서 간선을 훑는 부분이 완전히 같다는 말의 의미는 무엇인가?
  A: 알고리즘의 본체(완화)는 하나고, 두 판의 차이는 "다음 정점을 어떻게 고르나" 딱 한 곳이라는 뜻이다.
  측정이 그것을 숫자로 보인다 — V=300 완전 그래프에서 두 판의 간선 조회가 둘 다 89,700으로 같다.
  그래서 비용 차이는 전부 "고르기" 값(log V 대 V)에서 온다.

**질문별 답**

- Q: V=300 완전 그래프에서 간선 조회와 힙 삽입은 각각 몇 번이었고, 왜 70배나 차이 나는가?
  A: 간선 조회 89,700번, 힙 삽입 1,273번 — 정확히 70배다.
  간선은 전부 한 번씩 보지만, 힙에는 **그중 거리가 실제로 줄어든 경우만** 넣기 때문이다.
  완화를 시도하는 것과 힙에 넣는 것은 다른 사건이다.

- Q: "O(E log V)는 최악의 상한이지 실제로 도달하는 값이 아니다"의 근거는 무엇인가?
  A: 힙 삽입 횟수는 E가 아니라 "거리가 개선된 횟수"를 따르는데, 무작위 가중치에서 그 값은 V log V 근처다.
  측정: 1,273회 대 300 × ln300 ≈ 1,711 — E(89,700)와는 자릿수가 다르다.
  E log V는 "모든 간선이 매번 개선을 만든다"는 최악을 가정한 값이고, 그런 입력은 무작위에서 안 나온다.

- Q: 낡은 항목 비율이 밀도에 따라 어떻게 변했고(24% 대 76%), 왜 촘촘할수록 오르는가?
  A: 성긴 그래프(V=2,000, E=7,884)는 꺼내기 2,621 중 낡음 650으로 24%, 촘촘한 그래프(V=300, E=89,700)는 1,273 중 973으로 76%였다.
  촘촘하면 한 정점으로 들어오는 간선이 많아 **그 정점의 거리가 여러 번 줄어들고**, 줄어들 때마다 항목이 하나씩 더 쌓이기 때문이다.
  꺼낸 것의 4분의 3이 헛일인데 결과에는 전혀 안 나타난다 — 세지 않으면 알 방법이 없다.

- Q: 힙 최대 크기가 정점 수(V=300)를 넘어 1,154까지 가는 이유는 무엇인가?
  A: 감소 키가 없어 **같은 정점이 여러 번 들어가기** 때문이다 — 힙 크기는 정점 수가 아니라 삽입 누적을 따라간다.
  넣은 것이 1,273인데 최대가 1,154이라는 것은 거의 안 빠지고 쌓이기만 했다는 뜻이다(3.8배).
  감소 키가 있는 힙이면 정점당 항목이 하나라 최대가 V로 묶인다.

- Q: 성긴 그래프에서 배열 판의 탐색량은 간선 수의 몇 배였는가?
  A: **500배**다 — 간선 7,884개인 그래프에서 정점을 3,944,000번 훑는다(V=2,000).
  선형 탐색은 간선을 아예 안 보고 매 라운드 V칸을 훑으므로, 간선이 아무리 적어도 V²는 그대로 낸다.
  성긴 그래프에서 배열 판을 쓰면 안 되는 이유가 이 한 줄이다.

- Q: 촘촘한 그래프에서는 배열 판의 V² 훑기가 왜 "공짜나 마찬가지"가 되는가?
  A: V=300 완전 그래프에서 선형 탐색 90,000(V²) 대 간선 조회 89,700(E) — 차이가 300(=V)뿐이다.
  E가 V²에 가까우면 어차피 간선을 보느라 V²만큼 일하고 있어서, 고르기에 V²를 더 쓰는 것이 총량을 2배 정도로만 만든다.
  대신 힙의 log V를 통째로 안 낸다 — 그쪽 이득이 더 크다.

- Q: 힙을 쓸지 말지는 무엇으로 정하는가?
  A: **밀도**로 정한다.
  E가 V에 가까우면(성김) 힙 판 — V²를 안 훑는다.
  E가 V²에 가까우면(촘촘) 배열 판 — 힙의 log를 안 낸다.

**질문별 답**

- Q: 감소 키가 있는 힙을 직접 만들면 최대 크기가 V로 묶이는데, 대가로 무엇을 관리해야 하는가?
  A: **각 정점이 힙 배열의 어느 자리에 있는지**를 따로 들고, 힙이 원소를 옮길 때마다 그 위치표를 같이 고쳐야 한다.
  MeasurementTest 주석이 그 선택을 기록해 두었다 — "직접 만들면 되지만 그 대가로 힙 안의 위치를 따로 관리해야 한다. 지금은 메모리를 더 쓰고 코드를 단순하게 두는 쪽을 골랐다."
  즉 메모리(3.8배 부푼 힙)와 코드 복잡도를 맞바꾼 것이다.

- Q: 목적지가 하나뿐이면 그 정점을 꺼낸 순간 멈춰도 되는가, 왜 되는가?
  A: 된다. 힙에서 꺼낸 거리는 더 줄어들지 않는다는 것이 다익스트라의 확정 논증이고, 목적지를 꺼낸 순간 그 거리가 이미 최종이기 때문이다.
  뒤에 확정될 정점들은 전부 그보다 먼 곳이라 목적지의 답을 바꿀 수 없다.
  이 "목적지를 꺼내면 멈춘다"가 20번 A*가 서 있는 자리이기도 하다. (원본에 근거 없음 — 내 추론)

- Q: 최단 경로가 여러 개일 때 그 개수를 세려면 무엇을 더 기억해야 하는가?
  A: 정점마다 **최단 경로 개수** `cnt[]`를 하나 더 둔다.
  완화에서 더 짧아지면 `cnt[u] = cnt[v]`로 덮고, **같은 거리**(`candidate == dist[u]`)면 `cnt[u] += cnt[v]`로 더한다.
  지금 코드는 `<`만 보고 `==`를 그냥 지나치므로, 동점 경로를 세려면 그 분기를 새로 만들어야 한다. (원본에 근거 없음 — 내 추론)

- Q: 20번 A*는 다익스트라에 무엇을 더한 것이고, 휴리스틱이 0이면 무엇이 되는가?
  A: 힙의 우선순위를 "여기까지 온 거리 g"가 아니라 "g + 목적지까지 남은 거리 짐작 h"로 바꾼 것이다.
  h가 목적지 쪽을 가리키므로 엉뚱한 방향을 덜 펼친다.
  h가 항상 0이면 우선순위가 g 그대로라 **다익스트라와 완전히 같아진다** — A*는 다익스트라의 일반화다.

#### 5. 파생 질문 (서머리 기반)

```
11 BFS  -> 14 다익스트라 -> 20 A*

  BFS        : 큐(넣은 순서)        모든 간선 비용이 같을 때
  다익스트라 : 힙(거리 순서)        비용이 다를 때. 음수는 금지
  A*         : 힙(거리 + 짐작 순서) 목적지가 하나일 때
              ^ 셋 다 "하나 꺼내 확정하고 이웃 완화" 라는 같은 뼈대
```

**질문별 답**

- Q: 다익스트라의 핵심 불변식("확정된 정점의 거리는 다시는 안 바뀐다")은 어떤 순서 보장에서 나오는가?
  A: **꺼내는 거리가 절대 줄어들지 않는 순서**로 나온다는 보장이다(예시에서 0,2,3,5,7,8).
  힙이 최솟값을 주고, 음수 간선이 없어 지나갈수록 거리가 늘기만 하므로 이 단조 순서가 유지된다.
  그 단조 순서가 있으면 "지금 꺼낸 것보다 짧은 길은 앞으로 나올 수 없다"가 되어 확정이 정당해진다.

- Q: 11번 0-1 BFS와 다익스트라의 관계는 — 언제 힙이 필요 없어지는가?
  A: 간선 가중치가 0과 1 두 가지뿐이면 힙 없이 **덱(양쪽 큐)**으로 같은 일을 한다 — 0짜리는 앞에, 1짜리는 뒤에 넣으면 덱 안의 거리 순서가 저절로 지켜진다.
  가중치의 종류가 적어서 "정렬"이 필요 없어지는 경우다.
  값이 두 가지를 넘는 순간 그 요령이 깨지고 힙이 필요해진다.

- Q: 낡은 항목이 "결과에 전혀 안 나타난다"는 것은 어떤 종류의 문제이고, 11·12·13번의 어떤 주제와 이어지는가?
  A: **답은 맞는데 비용만 새는** 문제, 즉 계측 없이는 존재 자체를 모르는 부류다.
  힙 판은 낡은 항목을 다 걸러내므로 거리 배열은 완벽하고, 다만 힙이 3.8배로 부풀 뿐이다.
  같은 계측 주제가 11·12·13번에도 이어진다 — "방문 표시를 언제 찍나"(큐에 넣을 때냐 꺼낼 때냐)로 중복 방문 수가 달라지고, 13번 백트래킹에서는 가지치기로 잘라낸 경우의 수가 결과에 안 보이는 비용이었다. (11·12·13번 대응은 원본에 근거 없음 — 내 추론)

- Q: 다익스트라가 음수 간선에서 틀리는 구체적인 반례를 하나 만들어보라?
  A: `0->1(1)`, `0->2(2)`, `2->1(-5)`.
  힙은 거리 1인 1을 먼저 꺼내 확정하는데, 실제 최단 거리는 `0->2->1 = 2 + (-5) = -3`이다.
  확정한 뒤로는 1을 다시 안 보므로 답이 1로 굳고, **예외 하나 없이** 틀린 값이 나온다. (원본 테스트가 보인 `0->1(1), 1->2(-5)` 모양을 답이 실제로 틀어지게 확장한 것 — 구체 반례는 내 구성)

- Q: 두 판 모두 마지막에 `MAX_VALUE`를 `UNREACHABLE`(-1)로 바꾸는데, 내부 표현과 외부 계약을 나누는 이유는?
  A: 계산 중에는 "무한대"가 **비교와 덧셈이 되는 큰 수**여야 완화 코드가 단순해진다 — -1이면 비교가 뒤집힌다.
  반면 부르는 쪽에는 `Long.MAX_VALUE` 같은 구현 부스러기가 아니라 "못 간다"는 뜻이 분명한 값(-1)을 주는 것이 낫다.
  그래서 계산용 표현과 반환용 표현을 나누고, 마지막 한 번의 훑기로 번역한다.

- Q: `done` 배열(확정 표시)과 11번 BFS의 방문 표시는 무엇이 같고 무엇이 다른가?
  A: 같은 것: 둘 다 "이 정점은 끝났으니 다시 보지 않는다"는 표시이고, 없으면 같은 정점을 무한히 다시 넣는다.
  다른 것: BFS의 방문 표시는 **큐에 넣는 순간** 찍어도 되지만(넣은 순서 = 거리 순서라 첫 도달이 곧 최단), 다익스트라는 나중에 더 짧은 길이 나올 수 있어 **꺼내서 확정하는 순간**에만 찍을 수 있다.
  그 시차가 바로 낡은 항목이 생기는 자리다.
