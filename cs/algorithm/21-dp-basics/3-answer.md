### A. 문제 (src/main 의 TODO 1~9)

#### 1. 피보나치 (TODO 1~3)

**정답 코드 (impl 기준)**

```java
public static long naive(int n, long[] calls) {
    calls[0]++;
    if (n <= 1) {
        return n;
    }
    return naive(n - 1, calls) + naive(n - 2, calls);
}

public static long memoized(int n, CountedTable table) {
    if (n <= 1) {
        return n;
    }
    if (table.isFilled(n)) {
        return table.get(n);
    }
    long value = memoized(n - 1, table) + memoized(n - 2, table);
    table.set(n, value);
    return value;
}

public static long tabulated(int n, CountedTable table) {
    if (n <= 1) {
        return n;
    }
    table.set(0, 0);
    table.set(1, 1);
    for (int i = 2; i <= n; i++) {
        table.set(i, table.get(i - 1) + table.get(i - 2));
    }
    return table.get(n);
}
```

```
naive(5) 의 호출 트리 (일부)          memoized(5) 는 각 n 을 한 번만 계산
        5                                     5
      /   \                                 /   \
     4     3   <- 3 이 또 나옴             4     (표 적중)
    / \   / \                             / \
   3   2 2   1 <- 2 가 세 번             3   (표 적중)
```

**질문별 답**

- Q: naive 는 n 이 1 늘 때마다 호출 수가 대략 몇 배로 느는가, 왜 그런가?
  A: 약 1.6 배(황금비 φ ≈ 1.618)씩 는다.
  호출 수 자체가 피보나치 수열과 같은 점화식(`calls(n) ≈ calls(n-1) + calls(n-2)`)을 따르기 때문이다.
  피보나치 수열의 이웃 항 비율이 φ 로 수렴하므로 호출 수도 지수적으로 는다.
  실측: n=35 에서 29,860,703번 — README 표 기준으로 n 이 5 늘 때마다 약 11배씩 늘었다.

- Q: 표 하나를 두는 것만으로 지수가 선형이 되는 이유는 무엇인가?
  A: 서로 다른 부분 문제가 n+1 개(0..n)뿐이기 때문이다.
  표가 없으면 같은 n 을 지수 번 다시 푼다.
  표가 있으면 각 n 은 정확히 한 번만 계산되고, 두 번째부터는 O(1) 조회다.
  총비용 = 상태 수(n+1) × 상태당 일(덧셈 1회) = O(n). 실측: n=35 에서 쓰기 34번, 적중 32번.

- Q: memoized 에서 `isFilled` 대신 `get` 결과를 EMPTY 와 비교해도 답은 맞는데, 계수기는 어떻게 달라지는가?
  A: `isFilled` 는 적중/빗나감을 세지 않고, `get` 은 reads 를 올리고 채워져 있으면 hits, 비었으면 misses 를 센다.
  `get` 으로 확인하면 "확인만 한 것"도 전부 읽기·빗나감으로 잡혀 계측이 부풀어진다.
  답(수치 결과)은 같지만 "몇 번 재계산을 아꼈나"라는 측정의 의미가 흐려진다.
  이 챕터의 목적이 횟수 측정이므로 확인은 `isFilled`, 실제 사용은 `get` 으로 역할을 나눈다.

- Q: tabulated 는 재귀 깊이 걱정이 없는 대신 무엇을 더 하게 되는가?
  A: 필요 여부와 무관하게 0 부터 n 까지 모든 칸을 채운다.
  메모이제이션은 "필요해진 칸"만 채우는데, 타뷸레이션은 도달 불가능한 칸도 채운다.
  피보나치는 모든 칸이 필요해서 손해가 없지만, 배낭에서는 44% 를 헛채운다.
  또 채우는 순서를 직접 정해야 한다 — 재귀는 순서를 호출 구조가 알아서 정해준다.

- Q: tabulated 에서 n 이 0 이나 1 이면 표를 안 채우고 바로 답해도 되는가?
  A: 된다. impl 도 `if (n <= 1) return n;` 으로 표를 건드리기 전에 반환한다.
  n=0, n=1 의 답은 정의 자체(0, 1)라 계산할 것이 없다.
  이 분기가 없으면 `table.set(1, 1)` 이 크기 1짜리 표에서 범위를 벗어날 수도 있다(표 크기는 호출자가 잡는다).
  바닥값(base case)은 점화식이 아니라 정의에서 온다는 것을 코드로 보여주는 분기다.

- Q: 적중(hit)이 0 이라면 그것은 무엇을 뜻하는가?
  A: 표에서 이미 계산된 값을 한 번도 꺼내 쓰지 않았다는 뜻 = 같은 부분 문제가 두 번 나오지 않았다는 뜻이다.
  적중은 "다시 계산하지 않은 횟수"다.
  겹치는 부분 문제가 없다면 표는 쓰기만 하고 읽어주는 곳이 없다.
  그러면 표를 쓸 이유가 없다 — DP 는 "겹치는 부분 문제"가 있을 때만 이득이다.

```java
private static long naiveFrom(
        int[] weights, int[] values, int index, int remaining, long[] calls) {
    calls[0]++;
    if (index == weights.length) {
        return 0;
    }
    long without = naiveFrom(weights, values, index + 1, remaining, calls);
    if (weights[index] > remaining) {
        return without;
    }
    long with = values[index]
            + naiveFrom(weights, values, index + 1, remaining - weights[index], calls);
    return Math.max(with, without);
}
```

**질문별 답**

- Q: naive 에서 물건의 무게가 남은 무게보다 크면 "넣는 경우"를 시도할 수 있는가?
  A: 없다. `weights[index] > remaining` 이면 "안 넣는 경우"(without)만 돌려준다.
  넣으면 남은 무게가 음수가 되어 상태 자체가 성립하지 않는다.
  impl 은 without 을 먼저 계산해두고, 들어갈 때만 with 를 추가로 시도해 `Math.max` 를 취한다.
  이 가드가 메모이제이션·타뷸레이션에도 똑같이 들어간다(`weights[index] <= remaining` 일 때만 with).

- Q: naive 에서 물건을 다 봤으면 무엇을 돌려주는가?
  A: 0 이다. `index == weights.length` 면 더 담을 수 있는 물건이 없다.
  "앞으로 얻을 수 있는 가치"가 이 함수의 반환값인데, 남은 선택지가 없으니 0 이다.
  이미 담은 가치는 위쪽 호출들이 `values[index] +` 로 더해 올라간다.
  이 바닥값이 타뷸레이션에서 `index == n` 행을 0 으로 채우는 것과 정확히 같다.

- Q: 상태를 무엇으로 잡는가, 그리고 "어떤 순서로 여기까지 왔나"는 왜 상태에 안 들어가는가?
  A: `(물건 번호 index, 남은 무게 remaining)` 둘이다.
  앞으로의 최적 답은 "몇 번째 물건부터 볼 수 있고 무게가 얼마 남았나"에만 달려 있다.
  어떤 조합으로 그 남은 무게에 도달했는지는 앞으로 담을 수 있는 것에 아무 영향을 안 준다.
  그래서 상태가 2^n 개(경로)에서 n×W 개(요약)로 준다 — 이것이 최적 부분 구조다.

- Q: 그 성질(최적 부분 구조)이 없으면 왜 DP 를 못 쓰는가?
  A: 표의 한 칸이 "하나의 답"을 갖지 못하기 때문이다.
  같은 (index, remaining) 인데 온 경로에 따라 앞으로의 답이 달라진다면, 그 칸에 무엇을 적어야 할지 정할 수 없다.
  적어둔 값을 재사용하는 것이 DP 인데, 재사용이 틀린 답을 만든다.
  그럴 때는 경로 정보를 상태에 넣어 상태를 쪼개거나(상태 확장), DP 를 포기해야 한다.

- Q: 2차원 상태 `(index, remaining)` 을 1차원 표 한 자리로 누르는 식은 무엇인가?
  A: `key = index * (capacity + 1) + remaining` 이다.
  remaining 이 0..capacity 의 capacity+1 가지이므로, index 마다 폭 capacity+1 짜리 구간을 배정하는 것이다.
  2차원 배열 `[index][remaining]` 을 행 우선으로 펴 놓은 것과 같다.
  CountedTable 이 1차원이라서 이렇게 누른다 — 계측기를 하나로 쓰기 위한 선택이다.

- Q: 그 식에서 capacity 가 아니라 `capacity + 1` 을 곱해야 하는 이유는?
  A: remaining 의 가짓수가 capacity 가 아니라 capacity+1 개(0 포함)이기 때문이다.
  capacity 를 곱하면 `(index, capacity)` 와 `(index+1, 0)` 이 같은 key 로 겹친다.
  겹치면 서로 다른 상태가 같은 칸을 읽고 써서 조용히 틀린 답이 나온다 — 예외도 안 난다.
  "범위가 0 부터 capacity 까지"라는 TODO 의 경고가 정확히 이 함정을 가리킨다.

- Q: 타뷸레이션은 index 를 어느 방향으로 채워야 하는가, 거꾸로 채우면 무슨 값이 나오는가?
  A: `index = n` 부터 0 까지 **거꾸로(큰 쪽부터)** 내려온다.
  index 의 답이 index+1 의 답(다음 물건부터의 최적)을 읽기 때문에, 읽히는 쪽을 먼저 채워야 한다.
  index = 0 부터 올라가면 아직 안 채운 칸을 읽는다 — CountedTable 은 빈 칸에서 EMPTY(Long.MIN_VALUE)를 돌려준다.
  그 값이 max·덧셈에 섞여 터무니없는 답이 나온다(예외가 아니라 오답 — 조용히 틀린다).

- Q: 같은 문제에서 메모이제이션이 표의 56% 만 채우는 이유는 무엇인가?
  A: 도달할 수 없는 (index, remaining) 조합이 많기 때문이다.
  남은 무게는 항상 "capacity − (담은 무게들의 합)" 꼴인데, 무게가 3, 7, 11 뿐이면 남은 무게 1 이나 2 는 어떤 조합으로도 안 만들어진다.
  메모이제이션은 재귀가 실제로 도달한 상태만 채우므로 그런 칸에 가지 않는다.
  실측: 물건 20개·한도 200 에서 표 4,221칸 중 메모 2,363칸(56%), 타뷸 4,221칸(100%).

- Q: 피보나치에서는 왜 그 차이(메모 56% vs 타뷸 100%)가 안 보였는가?
  A: 피보나치는 0..n 모든 칸이 실제로 필요하기 때문이다.
  fib(n) 은 fib(n-1), fib(n-2) 를 거쳐 결국 모든 작은 n 에 도달한다 — 도달 불가능한 상태가 없다.
  그래서 메모도 100% 를 채우고, 두 방법의 채움 수가 같다.
  메모/타뷸의 차이는 "도달 불가능한 상태가 많은 문제"에서만 관측된다 — 배낭이 그 첫 문제다.

#### 3. 최장 증가 부분수열 (TODO 7~9)

**정답 코드 (impl 기준, 핵심부)**

```java
// quadratic: 표[i] = "i 로 끝나는" 최장 증가 수열의 길이
int best = 1;
for (int i = 0; i < n; i++) {
    long longest = 1;
    for (int j = 0; j < i; j++) {
        if (a[j] < a[i]) {
            longest = Math.max(longest, table.get(j) + 1);
        }
    }
    table.set(i, longest);
    best = Math.max(best, (int) longest);
}
return best;   // 마지막 칸이 아니라 전체 최댓값

// logarithmic: tails[k] = 길이 k+1 인 증가 수열의 마지막 값 중 최솟값
for (int value : a) {
    int lo = 0, hi = length;
    while (lo < hi) {              // "value 이상인 첫 자리" = lowerBound
        int mid = lo + (hi - lo) / 2;
        comparisons[0]++;
        if (tails[mid] < value) lo = mid + 1;
        else hi = mid;
    }
    tails[lo] = value;             // 덮어쓴다
    if (lo == length) length++;    // 맨 끝에 붙었으면 길이 증가
}

// reconstruct: 표 최댓값 자리에서 출발해 뒤에서 앞으로,
// 길이가 need 인 자리를 만나면 잡고 need 를 1 줄인다 (값 비교는 없다 — 증명으로 지웠다)
```

```
a    =  3   1   4   1   5   9   2   6
표   =  1   1   2   1   3   4   2   4     <- "그 자리로 끝나는" 최장 길이
답   =  전체 최댓값 4 (마지막 칸 아님)

tails 의 변화: [3] -> [1] -> [1,4] -> [1,4] -> [1,4,5] -> [1,4,5,9] -> [1,2,5,9] -> [1,2,5,6]
마지막 tails [1,2,5,6] 은 실제 부분수열이 아니다 (a 에서 그 순서로 못 고른다)
```

**질문별 답**

- Q: quadratic 에서 표의 i 번 칸은 정확히 무엇을 담는가?
  A: "a[i] 로 **끝나는**" 최장 증가 부분수열의 길이다.
  "i 까지 봤을 때의 답"이 아니다 — 반드시 a[i] 를 마지막 원소로 포함하는 것 중 최장이다.
  이렇게 잡아야 `a[j] < a[i]` 인 j 의 칸에 1 을 더하는 점화식이 성립한다.
  칸의 의미를 "i 까지의 답"으로 잘못 잡으면 점화식을 세울 수 없다 — 상태 정의가 점화식을 결정한다.

- Q: 그 칸의 최솟값은 얼마이고 왜 그런가?
  A: 1 이다. a[i] 하나만으로 이루어진 길이 1 짜리 수열이 항상 존재한다.
  앞에 자기보다 작은 값이 하나도 없어도 자기 혼자는 된다.
  그래서 impl 은 `longest = 1` 에서 시작한다.
  0 으로 시작하면 감소 수열 입력에서 답이 0 이 되는 오답이 나온다.

- Q: 답은 표의 마지막 칸인가 전체의 최댓값인가, 왜 그런가?
  A: 전체의 최댓값이다.
  가장 긴 수열이 배열의 마지막 원소에서 끝난다는 보장이 없다.
  예: `[3,1,4,1,5,9,2,6]` 에서 표는 `[1,1,2,1,3,4,2,4]` — 마지막 칸은 4지만, `[1,4,5,9]` 처럼 9(6번째)에서 끝나는 길이 4 도 있다. 마지막 원소가 작으면(예: 끝이 2) 마지막 칸은 최댓값보다 작다.
  impl 은 채우면서 `best = Math.max(best, longest)` 로 최댓값을 같이 추적한다.

- Q: 빈 배열이면 무엇을 돌려주는가?
  A: 0 이다. impl 은 `if (n == 0) return 0;` 으로 먼저 처리한다.
  증가 부분수열이 하나도 없으니(빈 수열의 길이) 0 이 맞다.
  이 분기가 없으면 `best = 1` 초기값이 그대로 반환되어 오답이다.
  logarithmic 판은 루프가 안 돌아 `length = 0` 이 자연스럽게 나온다 — 별도 분기가 필요 없다.

- Q: logarithmic 의 tails[k] 는 무엇을 담는가?
  A: "길이 k+1 인 증가 부분수열의 **마지막 값** 중 가장 작은 것"이다.
  마지막 값이 작을수록 뒤에 더 많은 값을 이어 붙일 수 있으므로, 각 길이마다 "가장 유리한 끝값"만 기억하는 것이다.
  수열 자체가 아니라 끝값 하나만 담는다.
  이 정의 때문에 tails 는 항상 증가 상태고, 그래서 이진 탐색이 가능해진다.

- Q: 값마다 tails 에서 찾는 자리는 어떤 자리인가?
  A: "그 값 **이상**인 첫 자리"(lowerBound)다 — 06-binary-search 의 lowerBound 와 같다.
  `tails[mid] < value` 면 오른쪽(`lo = mid + 1`), 아니면 `hi = mid` 로 접는다.
  그 자리를 value 로 덮으면 "그 길이의 끝값 최솟값"이 갱신되거나 유지된다.
  같은 값이 오면 자기 자리를 자기 값으로 덮어 길이가 안 는다 — "증가"(strictly increasing)라서 같은 값은 못 잇는다.

- Q: tails 가 항상 증가 상태라는 것을 왜 믿을 수 있는가?
  A: 덮어쓰기가 증가 상태를 깨지 않기 때문이다(불변식).
  lowerBound 로 찾은 자리 lo 는 `tails[lo-1] < value <= tails[lo]` 를 만족한다.
  거기에 value 를 쓰면 왼쪽보다는 크고 오른쪽보다는 작거나 같은 값이 들어가므로 증가 상태가 유지된다.
  처음(빈 배열)은 자명하게 증가이므로, 귀납적으로 항상 증가다.

- Q: 자리를 찾았을 때 전체 길이가 늘어나는 경우는 언제인가?
  A: `lo == length`, 즉 찾은 자리가 tails 의 맨 끝 다음일 때다.
  기존의 어떤 끝값보다도 커서 어느 길이의 수열 뒤에도 붙일 수 있는 새 최장이 생긴 것이다.
  그때만 `length++` 한다.
  중간 자리를 덮은 경우는 길이는 그대로고 "그 길이의 끝값"만 더 유리해진 것이다.

- Q: tails 자체가 답인 부분수열인가, 그렇게 생각하면 어떤 입력에서 틀리는가?
  A: 아니다. **길이만 맞고 내용은 안 맞는다.**
  `[3,1,4,1,5,9,2,6]` 의 최종 tails 는 `[1,2,5,6]` 인데, a 에서 2(7번째)는 5(5번째)보다 뒤에 있어 1→2→5 순서로는 못 고른다.
  나중에 온 작은 값이 앞 자리를 덮어쓰기 때문에, tails 의 원소들은 서로 다른 수열의 끝값이 섞인 것이다.
  계약 테스트가 tails 를 그대로 답으로 쓰면 깨지는 입력을 준다 — 실제 수열이 필요하면 reconstruct 를 쓴다.

- Q: reconstruct 는 어디서 시작해 어떤 자리를 이어 붙이는가?
  A: 표 전체에서 값이 가장 큰 자리(bestIndex)에서 시작한다.
  `need = 표[bestIndex]` 로 놓고, bestIndex 부터 **뒤에서 앞으로** 훑는다.
  `표[i] == need` 인 자리를 만나면 a[i] 를 결과의 뒤에서부터 채우고 need 를 1 줄인다.
  need 가 1씩 줄며 0 이 될 때까지 반복하면 길이가 1씩 줄어드는 사슬이 곧 실제 수열 하나다.

- Q: "값도 증가하는지" 검사는 왜 필요 없는가(증명의 뼈대만이라도)?
  A: "길이가 need 인 자리 중 j 앞의 첫(가장 오른쪽) 자리는 항상 값이 a[j] 보다 작다"가 증명되기 때문이다.
  뼈대: a[i] >= a[j] 라고 가정하면, dp[j] = need+1 이므로 j 앞에 a[i'] < a[j], dp[i'] = need 인 i' 가 있다.
  i 가 그런 자리 중 가장 오른쪽이므로 i' <= i 인데 — i'==i 면 a[i] < a[j] 라 가정에 모순, i'<i 면 a[i'] < a[j] <= a[i] 에서 dp[i] >= need+1 이라 dp[i]=need 에 모순.
  변종 테스트·무작위 200개로도 못 깨서 증명했고, 필요 없음이 확인되어 지웠다 — "일어날 수 없는 경우의 검사는 코드가 아니라 증명으로 지운다"의 사례다.

### B. 개념

- Q: (원본 생각해볼 것) 배낭의 표를 1차원으로 줄일 수 있다 — 무게 루프를 어느 방향으로 돌아야 하는가?
  A: (원본에 답 없음 — 내 추론) 무게를 **큰 쪽에서 작은 쪽으로(capacity → weights[i])** 돌아야 한다.
  1차원 표 `dp[w]` 는 "이번 물건까지 봤을 때 무게 w 의 최대 가치"인데, 갱신식 `dp[w] = max(dp[w], dp[w - weights[i]] + values[i])` 의 오른쪽 `dp[w - weights[i]]` 는 **이전 물건까지의** 값이어야 한다.
  작은 쪽부터 돌면 이번 물건으로 이미 갱신된 칸을 다시 읽어 같은 물건을 두 번 넣게 된다(0-1 이 아니라 무한 배낭이 된다).
  거꾸로(큰 쪽부터) 돌면 읽는 칸이 아직 이번 물건으로 안 덮인 상태라 0-1 이 유지된다.

- Q: (원본 생각해볼 것) 무게가 아니라 가치를 상태로 잡으면 점화식이 어떻게 바뀌는가?
  A: (원본에 답 없음 — 내 추론) `dp[v]` = "가치 합이 정확히 v 가 되게 담을 때의 **최소 무게**"로 뒤집는다.
  갱신식은 `dp[v] = min(dp[v], dp[v - values[i]] + weights[i])`.
  답은 `dp[v] <= capacity` 인 v 중 최댓값이다.
  표의 크기가 W+1 에서 (가치 총합)+1 로 바뀐다.

- Q: (원본 생각해볼 것) 가치를 상태로 잡는 쪽이 유리한 것은 언제인가?
  A: (원본에 답 없음 — 내 추론) capacity 는 아주 큰데 가치 총합은 작을 때다.
  비용이 O(n × W) 대 O(n × V총합) 이므로 작은 축을 상태로 잡는 쪽이 이긴다.
  예: W = 10^9, 가치 총합 = 10^4 면 무게 축 표는 만들 수도 없다.
  "상태를 무엇으로 잡느냐"가 가능/불가능을 가르는 사례다 — README 가 "상태를 잡는 것이 전부"라고 한 말의 연장이다.

- Q: (원본 생각해볼 것) LIS 를 O(n log n) 으로 풀면서 복원까지 하려면 무엇을 더 기억해야 하는가?
  A: (원본에 답 없음 — 내 추론) 원소마다 두 가지를 더 기억한다: ① 그 원소가 tails 의 몇 번 자리에 들어갔는가(= 그 원소로 끝나는 수열의 길이), ② 들어가던 시점에 바로 앞 자리(lo-1)에 있던 원소의 인덱스(prev 링크).
  tails 는 덮어쓰기로 과거를 잃어버리므로, 덮기 전에 "누구 뒤에 붙었는지"를 따로 남겨야 한다.
  끝나고 나서 길이가 최장인 원소에서 prev 링크를 거슬러 올라가면 실제 수열이 나온다.
  추가 공간 O(n) — impl 의 O(n²) 표 복원과 달리 표 없이도 된다.

- Q: (원본 생각해볼 것) 메모이제이션은 재귀라 깊이가 쌓인다 — 언제 위험한가?
  A: 재귀 깊이가 상태 사슬의 길이만큼 쌓일 때 — 피보나치·배낭은 깊이가 n 에 비례하므로 n 이 수만~수십만이면 StackOverflowError 가 실제로 난다.
  12번 챕터(DFS)의 측정이 그것을 보여줬다 — 재귀 깊이는 공짜가 아니다.
  타뷸레이션은 루프라 깊이가 안 쌓인다. 깊이가 걱정되면 타뷸레이션으로 바꾸는 것이 답이다.
  (원본 README 는 "12번의 측정을 떠올리면"이라고만 했다 — 구체 수치 연결은 내 추론)

- Q: DP 를 쓸 수 있는 조건(최적 부분 구조)을 한 문장으로 말하면 무엇인가?
  A: "여기까지 **어떻게** 왔는지가 앞으로의 최적 답에 영향을 주지 않아야 한다."
  즉 상태 몇 개의 숫자가 과거를 완전히 요약해야 한다.
  그래야 같은 상태의 답을 한 칸에 적어두고 재사용할 수 있다.
  덤으로 "겹치는 부분 문제"(같은 상태가 여러 번 나옴)가 있어야 표가 이득을 낸다 — 적중 0 이면 표를 쓸 이유가 없다.

- Q: "같은 것을 두 번 계산하지 않는다"는 주장은 왜 결과만 봐서는 확인이 안 되는가?
  A: 표를 안 써도 답은 같기 때문이다.
  naive 와 memoized 는 같은 값을 돌려준다 — 다른 것은 답이 아니라 **횟수**다.
  그래서 CountedTable 이 쓰기·읽기·적중을 센다: n=35 에서 재귀 호출 29,860,703 vs 표 쓰기 34.
  "결과에 안 나타나는 주장은 세어서 확인한다"가 이 챕터의 방법론이다.

- Q: 메모이제이션과 타뷸레이션 중 무엇을 언제 고르는가?
  A: 도달 불가능한 상태가 많으면 메모이제이션 — 필요한 칸만 채운다(배낭에서 56%).
  재귀 깊이가 위험하거나(상태 사슬이 길거나) 채우는 순서가 자명하면 타뷸레이션 — 깊이 걱정이 없다.
  타뷸레이션은 채우는 순서를 직접 정해야 하고, 거꾸로 하면 빈 칸을 읽는 함정이 있다.
  메모이제이션은 순서를 재귀가 알아서 정해주는 대신 스택을 쓴다.

- Q: LIS 의 O(n²) 판과 O(n log n) 판은 "관리하는 정보"가 어떻게 다른가?
  A: O(n²) 판은 "각 i 로 끝나는 최장 길이"를 전부 관리한다 — 정직하고, 복원도 이 표로 한다.
  O(n log n) 판은 "길이별 끝값의 최솟값"(tails)만 관리한다 — 답(길이)을 내는 데 필요한 최소한만 남긴 것이다.
  관리하는 정보를 줄인 대가로 실제 수열은 잃는다(tails 는 부분수열이 아니다).
  같은 문제라도 관리하는 정보를 바꾸면 차수가 바뀐다 — 실측 n=2,000 에서 표 읽기 1,013,183 vs 비교 11,452 (88배).

- Q: n=2,000 실측에서 표 읽기 1,013,183 인데 계측기는 왜 "훑기의 절반만" 세고 있다고 하는가?
  A: O(n²) 판은 쌍 (j, i) 를 1,999,000 개 전부 훑지만, 표를 읽는 것은 `a[j] < a[i]` 일 때뿐이기 때문이다.
  무작위 입력이면 절반 정도만 그 조건에 걸린다 — 읽기 1,013,183 ≈ 훑기의 절반.
  즉 계측기가 세는 것은 "훑기"가 아니라 "표 읽기"고, 조건에 안 걸린 비교는 계측 밖이다.
  측정을 믿으려면 **측정이 무엇을 안 세는지**도 알아야 한다 — 이 챕터의 두 번째 교훈이다.

- Q: 이 챕터의 이진 탐색(tails 자리 찾기)은 06-binary-search 의 무엇과 같은 것인가?
  A: lowerBound(그 값 **이상**인 첫 자리 찾기)와 같다.
  `tails[mid] < value` 면 `lo = mid + 1`, 아니면 `hi = mid` — 값이 아니라 **경계**를 찾는 탐색이다.
  경계 탐색이 성립하는 조건(범위가 정렬/단조 상태)을 tails 의 불변식이 보장한다.
  06번의 도구가 다른 챕터의 부품으로 재사용되는 사례다.
