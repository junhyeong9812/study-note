# algorithm/43-alg-incidents — 정답

## 정답

### 1. 깨진 가정과 공통 이유

- Bloch 2006: "`low + high`는 `int`에 들어간다." 배열이 약 10억 원소를 넘자 깨졌다.
- Stack Overflow 2016: "공백 구간이 짧다." 공백 약 2만 개가 든 글 하나로 깨졌다.
- Cloudflare 2019: "규칙의 정규식은 입력 길이에 무난한 시간에 끝난다." `.*(?:.*=.*)`가 깼다.
- 공통 이유: 셋 다 입력의 **크기·모양이 가정 밖으로 나갈 때만** 터진다. 평소 테스트 입력은 가정 안에 있었다. 정규식 두 사건은 결과(매칭 성공·실패)가 맞아서, 결과만 보는 테스트로는 원리적으로 보이지 않는다.

### 2. 넘치는 최소 n

- 넘치려면 `low + high >= 2^31`. 루프 안에서 `low + high <= 2n - 2`이므로 `2n - 2 >= 2^31`, 즉 n >= 2^30 + 1.
- 실험 D: n = 1,073,741,824(2^30)에서는 버그 판도 `found@1073741823`. n = 1,073,741,825(2^30 + 1)에서 `AIOOBE: Index -1073741824 out of bounds for length 1073741825`.
- Bloch 원문은 "2^30 or greater (roughly a billion elements)"라고 쓴다. 정확한 경계는 2^30 + 1이지만 "약 10억부터"라는 요지는 같다(계산에 의한 해석).

### 3. 세 식의 비교

- 실험 D 마지막 줄(lo = 1,073,741,824, hi = 2,147,483,646): `lo + hi = -1073741826`(넘침), `(lo + hi) / 2 = -536870913`, `(lo + hi) >>> 1 = 1610612735`, `lo + (hi - lo) / 2 = 1610612735`.
- `>>> 1`이 맞는 이유: `lo`, `hi`는 0 이상 2^31 - 1 이하라 진짜 합은 0 이상 2^32 - 2 이하다. 32비트 패턴은 부호 없는 수로 읽으면 정확한 합이고, 부호 없는 오른쪽 시프트(0 채움)가 그 값을 2로 나눈다.
- C의 2008 갱신: 원래 제안한 C 수정은 부호 있는 덧셈을 먼저 하는 꼴이었는데, C99에서 부호 있는 정수 오버플로는 정의되지 않은 동작이라 보장되지 않는다는 지적을 받았다. 그래서 `((unsigned int)low + (unsigned int)high) >> 1`처럼 부호 없는 수로 바꾼 뒤 더하는 꼴로 고쳤다(원문 게시글의 식에는 닫는 괄호가 하나 더 있는 오타가 있다).

### 4. Stack Overflow 2016-07-20

- 원문 수치: 14:44 UTC부터 34분 장애. 원인 파악 10분, 수정 코드 작성 14분, 사이트가 다시 열릴 때까지 배포 10분.
- 경로
  1. 공백 약 2만 개가 든 이상한 글(malformed post)이 올라왔다.
  2. 그 글이 홈페이지 목록에 있어 홈페이지를 볼 때마다 공백 자르기 정규식(`^[\s\u200c]+|[\s\u200c]+$`)이 그 글에 돌았다.
  3. 정규식이 O(n²)으로 웹 서버 CPU를 많이 써 홈페이지가 느려졌다.
  4. 로드 밸런서의 헬스 체크가 홈페이지였다. 서버들이 순환에서 빠졌다.
  5. 사이트 전체가 접속 불가가 됐다(원문: 헬스 체크가 아니었다면 홈페이지 외에는 접근 가능했을 것).

### 5. 실험 E

- `\s+$`(OpenJDK 21.0.12, `--cpus=2`, 집필 두 번): 공백 2만 개 4.49초·3.93초, 4만 개 15.65초·15.34초. 두 배에 약 3.5~3.9배, 1만 → 2만은 약 4.4~4.6배. 사실 점검 재실행은 3.68초 → 14.52초(약 3.9배), 1만 → 2만은 약 4.8배.
- 원문의 차수 "O(n²), not exponential"과 맞는다(두 배에 약 4배).
- 원문은 20,000 + 19,999 + … + 1을 "199,990,000"으로 적었다. 실험 마지막 줄의 계산은 `1+2+...+20000 = 200,010,000`이다. 원문 수치가 조금 어긋나지만 규모(약 2억 번)는 같다.

### 6. `.*.*=.*`의 O(n³)

- `find()`는 시작 위치 n+1곳에서 시도한다.
- 한 시작 위치(남은 글자 m개)에서 첫 `.*`가 먹을 개수 m+1가지, 각각에 대해 둘째 `.*`가 최대 m+1가지를 시도하고 `=`에서 실패한다 → 약 m²/2.
- 전체는 Σ m²/2 ≈ n³/6, 약 O(n³)이다(단순화한 셈 — 엔진 최적화에 따라 상수·차수가 달라질 수 있다). Java 측정에서 n 두 배에 약 7~8배였다.
- 단계 수 표에서 읽을 것
  - 입력이 한 글자씩 늘 때 23 → 33 → 45로 증가 폭이 커진다 — 선형이 아니다.
  - 20자짜리 매칭 실패(x 20개, 4,067)가 그보다 긴 22자짜리 성공(`x=` + x 20개, 555)보다 훨씬 비싸다 — 실패하면 모든 분할을 다 시도해야 끝난다.
  - 끝에 `;` 하나를 더 요구하면 `x=x`가 23 → 90, `x=` + x 20개가 555 → 5,353으로 는다.

### 7. 실험 F

- `[^=]*=`(두 번): 2,000 → 4,000 → 8,000 → 16,000에서 26 → 104 → 400 → 1,589 ms, 25 → 91 → 392 → 1,491 ms. 두 배마다 약 3.7~4.3배 — 제곱에 가깝다.
- 선형이 아닌 이유: 겹치는 `.*`는 없앴지만 `find()`가 시작 위치마다 다시 시도한다. 각 시작 위치에서 `[^=]*`가 남은 글자를 다 먹고 `=`를 못 찾아 되돌아간다 → 시작 위치 n × 남은 길이 = O(n²).
- 의도가 "`=`가 있나"면 정규식이 필요 없다. `in.indexOf('=') >= 0`은 16,000자에서도 수십 µs 이하였다. 정규식이 꼭 필요하면 선형 엔진을 쓴다.

### 8. 배포 직후 CPU 급증의 진단과 재발 방지

- 확인 순서
  1. 덤프 2~3장: 요청 처리 스레드 맨 위가 정규식 엔진(`java.util.regex.Pattern$…`, PCRE 함수 등)인가.
  2. 직전 배포의 규칙·패턴 변경 목록에서 `.*`가 이어지거나 중첩 수량자가 있는 패턴을 찾는다.
  3. 느린 요청의 입력을 꺼내 모양을 유지한 채 길이를 두 배씩 늘리며 앱과 같은 엔진으로 시간을 잰다 — 4배면 O(n²), 8배면 O(n³), 한 글자에 2배면 지수.
- 막을 테스트: 규칙마다 적대적 입력(긴 반복, 매칭 실패, 구분자 없음)으로 매칭 시간 예산을 검사하고, 넘으면 CI를 실패시킨다([engineering-practice/20](../../engineering-practice/20-practice-incidents/2-summary.md) 실험 C). Cloudflare 후속 조치의 "테스트 묶음에 규칙별 성능 프로파일링"이 이것이다.

### 9. RE2 계열로 바꿀 때

- 문제: 선형 시간 보장을 위해 RE2는 역참조(`\1`, `\k<name>` 등)와 전후방 탐색(`(?=re)` 등)을 지원하지 않는다(문법 문서 "NOT SUPPORTED"). 이런 패턴은 컴파일 오류가 난다. 엔진마다 문법·의미 차이로 매칭 결과가 다를 수도 있다.
- 전환 전 확인
  - 기존 규칙 전부를 새 엔진으로 컴파일해 본다.
  - 정상·공격 입력 모음으로 두 엔진의 결과를 대조한다.
  - 지원 안 되는 패턴은 재작성하거나, 시간 예산을 건 별도 경로로 둔다.

### 10. 노출 범위와 HashDoS

- 노출 범위
  - Bloch: 표준 라이브러리(`java.util.Arrays`) — 그 함수를 부르는 모든 프로그램.
  - Stack Overflow: 홈페이지 목록 → 홈페이지가 헬스 체크 → 서버들이 순환에서 이탈.
  - Cloudflare: 단계 배포 없이 전역 배포된 규칙 → 전 세계 HTTP 처리 CPU.
- HashDoS와 같은 모양: 평균·보통 입력에서는 빠른 알고리즘이 **남이 고른 최악 입력**(같은 해시의 키 / 긴 공백)에서 다항 시간으로 폭주하고, 요청 하나가 CPU 한 코어를 오래 잡는다. 처방도 같은 갈래다 — 입력 상한, 최악이 보장된 알고리즘(트리 버킷 / 선형 엔진).
