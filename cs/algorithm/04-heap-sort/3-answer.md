### A. 과제 (TODO 1~9)

#### 1. 내려꽂기 sink (BottomUpHeapSort.sink, TODO 3)

기준 코드 (impl):

```java
static <T> void sink(CountedArray<T> a, int k, int n) {
    while (2 * k + 1 < n) {                 // 왼쪽 자식이 힙 안에 있는 동안
        int child = 2 * k + 1;
        if (child + 1 < n && a.compare(child, child + 1) < 0) {
            child++;                        // 두 자식 중 큰 쪽
        }
        if (a.compare(k, child) >= 0) {     // 등호 포함 — 같으면 안 바꾼다
            break;
        }
        a.swap(k, child);
        k = child;
    }
}
```

- 자식은 `2k+1`(왼쪽), `2k+2`(오른쪽), 부모는 `(k-1)/2` — 완전 이진 트리를 배열에 눕힌 인덱스 계산이다.
- 부모 자리에 올라오는 값은 **두 자식 모두보다** 크거나 같아야 한다. 작은 쪽과 바꾸면 새 부모가 남은 자식보다 작을 수 있어 힙 성질(부모 ≥ 자식)이 그 자리에서 깨진다. 그래서 먼저 자식끼리 비교해 큰 쪽을 고른다.
- `child + 1 < n` 검사를 빼면 오른쪽 자식이 없는(힙 밖) 칸을 읽어 범위를 넘거나, 정렬 단계에서는 **이미 정렬 완료된 구역**의 값을 힙으로 끌어들여 답이 틀린다.
- `compare(k, child) >= 0` — 같으면 이미 힙 성질을 만족하므로 안 바꾼다. 등호를 빠뜨리면 값이 같을 때도 교환하는데, 결과는 여전히 올바른 힙이라 **어떤 결과 테스트에도 안 걸린다**(README 함정 — 전부 같은 값 입력에서 교환 계수로만 잡힌다).
- 힙 크기를 배열 길이로 고정하면 정렬 단계에서 뒤에 쌓아둔 **정렬 완료 원소들**(구간 밖)을 다시 힙에 넣어 섞어버린다. 그래서 n 을 매개변수로 받아 `sink(a, 0, end)` 처럼 줄어든 크기를 알려준다.

#### 2. 상향식 구성 (BottomUpHeapSort, TODO 1~2)

기준 코드 (impl):

```java
public <T> void heapify(CountedArray<T> a) {
    int n = a.size();
    for (int k = n / 2 - 1; k >= 0; k--) {   // 잎이 아닌 마지막 노드부터 거꾸로
        sink(a, k, n);
    }
}
public <T> void sort(CountedArray<T> a) {
    int n = a.size();
    heapify(a);
    for (int end = n - 1; end > 0; end--) {
        a.swap(0, end);        // 꼭대기(최댓값) -> 구간 맨 뒤
        sink(a, 0, end);       // 힙 크기는 end 로 줄었다
    }
}
```

- `n/2 - 1` — n/2 부터는 전부 잎이고, 잎은 이미 크기 1짜리 힙이라 건드릴 필요가 없다. 잎이 아닌 마지막 노드가 n/2 - 1 이다.
- sink 는 "내 아래 두 서브트리는 이미 힙"일 때만 성립한다. 0부터 앞으로 훑으면 아래쪽이 아직 힙이 아니라 내려꽂아도 결과가 힙이 되지 않는다. 거꾸로(아래에서 위로) 훑으면 항상 그 전제가 만족된다.
- 시작을 n-1 이나 n/2 로 잡아도 결과·비교·교환이 전부 같다(impl 주석 — 변종 확인): 잎에 sink 를 걸면 `2k+1 < n` 이 거짓이라 while 에 들어가지도 않는다. **틀린 게 아니라 헛도는 것**이고 어떤 계수기에도 안 잡힌다 — 주석이 유일한 기록.
- 꼭대기(최댓값)를 구간 맨 뒤(`end`)와 교환하고 힙 크기를 1 줄인다(`end` 가 그대로 새 크기). 뒤에서부터 큰 값이 쌓여 오름차순이 된다.
- 최소 힙이면 최솟값이 꼭대기인데, 그걸 꺼내 **앞**에 쌓으려면 나머지를 밀어야 한다(O(n)). 최대 힙은 최댓값을 **맨 뒤**(어차피 비는 자리)와 바꾸면 끝이라 제자리가 된다.
- 힙이 배열 그 자체 위에 있고(포인터 없는 완전 이진 트리), 빼낸 값은 줄어든 힙의 바로 뒤 칸에 쌓이므로 보조 배열이 필요 없다 — 제자리 정렬.

#### 3. 하향식 구성 (TopDownHeapSort, TODO 4~6)

기준 코드 (impl):

```java
public <T> void heapify(CountedArray<T> a) {
    for (int i = 1; i < n; i++) swim(a, i);  // [0..i-1] 이 힙이라 보고 i 를 밀어 넣기
}
static <T> void swim(CountedArray<T> a, int k) {
    while (k > 0) {                           // 종료 1: 꼭대기
        int parent = (k - 1) / 2;
        if (a.compare(parent, k) >= 0) break; // 종료 2: 부모가 크거나 같음
        a.swap(parent, k);
        k = parent;
    }
}
```

- swim = 새 원소를 힙 끝에 붙이고 부모보다 크면 부모와 바꾸며 올라간다. 종료 조건은 ① 꼭대기 도달(`k > 0` 거짓) ② **부모가 크거나 같음**(제자리 도착).
- 부모 식은 `(k - 1) / 2`. k=0 에 대입하면 (0-1)/2 = 0 — 자바 정수 나눗셈이 0 을 줘서 "자기 자신이 부모"가 된다. `k > 0` 검사가 없으면 꼭대기에서 자기 자신과 비교하며 헛돈다. 시작을 i=0 으로 잡아도 같은 이유로 즉시 빠져 헛돌 뿐이다(계수기에 안 잡히는 낭비).
- 구성 방법이 달라도 만들어진 힙은 같은 성질(부모 ≥ 자식)을 갖는다. 정렬 단계는 성질에만 의존하므로 `BottomUpHeapSort.sink` 를 그대로 불러도 된다 — sink 를 먼저 채우라는 이유.
- 하향식: 원소마다 자기 깊이만큼 올라갈 수 있고 힙의 **절반이 잎**(깊이 log n)이라 총 O(n log n). 상향식: 잎 절반은 일 안 하고, 깊이 d 만큼 내려갈 수 있는 노드는 위쪽에 소수뿐 — 급수를 더하면 2n 아래 = O(n).
- 결과는 같아도 "많은 노드가 얼마나 움직이는가"가 반대다: 하향식은 다수(잎)가 멀리 움직일 수 있고, 상향식은 다수(잎)가 아예 안 움직인다. 오름차순 입력 실측 1,982 vs 7,987(4배)이 그 증거.

#### 4. 3진 힙 (TernaryHeapSort, TODO 7~9)

기준 코드 (impl):

```java
public <T> void heapify(CountedArray<T> a) {
    for (int k = (n - 2) / 3; k >= 0; k--) sink(a, k, n);
}
static <T> void sink(CountedArray<T> a, int k, int n) {
    while (3 * k + 1 < n) {
        int child = 3 * k + 1;
        for (int c = child + 1; c <= 3 * k + 3 && c < n; c++) {
            if (a.compare(child, c) < 0) child = c;   // 셋 중 최대
        }
        if (a.compare(k, child) >= 0) break;
        a.swap(k, child);
        k = child;
    }
}
```

- 자식이 3k+1, 3k+2, 3k+3 이므로 자식 c 의 부모는 (c-1)/3 — 마지막 원소 n-1 의 부모는 `(n-2)/3`. 이진 힙의 n/2-1 을 그대로 쓰면 시작이 어긋난다(더 크면 잎에 헛돌고, 3진 기준 마지막 부모보다 작으면 일부 부모를 안 꽂아 힙이 안 된다).
- 없는 자식은 `c < n` 조건으로 걸러낸다 — 후보 루프가 3k+3 까지 가되 힙 크기를 넘으면 멈춘다.
- 한 단계당 비교: 이진 2번(자식끼리 1 + 부모와 1), 3진 3번(자식끼리 2 + 부모와 1). 깊이: log2 n → log3 n = 0.631배.
- 계산: 3 × 0.631 = 1.89 < 2 — 3진이 근소하게 이긴다. 실측(무작위 10,000개)도 비교 226,580 vs 235,322로 3진 승. 크게 벌어지는 건 **교환**(83,512 vs 124,144, 33% 적음) — 트리가 낮아 원소 이동 거리가 짧다.

### B. 개념

#### 5. 생각해볼 것 (원본 README 이관)

- 자식 d개의 단계당 비교는 d(자식끼리 d-1 + 부모와 1), 깊이는 log_d n = log2 n / log2 d. 비교 총량 ∝ d / log2 d — d=2: 2.0, d=3: 1.89, d=4: 2.0, d=8: 2.67. **4에서 이진과 같아지고 그 너머는 손해다** — 최적은 3~4 부근. (원본은 "계산으로 예측하고 재봐라"만 — 계산은 impl 주석의 방식을 d로 일반화한 내 추론)
- 안정으로 만들려면 값에 원래 인덱스를 붙여 (값, 인덱스) 쌍으로 비교하는 방법이 있다 — 대가는 추가 메모리 O(n)과 비교 비용 증가. 제자리 그대로는 안 된다: swap(0, end)가 멀리 있는 원소를 건너뛰게 하는 구조 자체가 순서를 뒤집는다. (원본에 근거 없음 — 내 추론)
- 교환 대신 "꼭대기 값을 빼 들고 → 구멍을 sink 시키고 → 마지막에 꽂는" 삽입 정렬식 밀기가 가능하다(쓰기 절감). 다만 이 코드베이스의 sink 구조(swap 기반)를 바꿔야 한다 — 교환은 필수가 아니라 구현 선택이다. (원본에 근거 없음 — 내 추론)
- 계측기는 비교·교환·읽기·쓰기 **횟수**만 센다. 참조 지역성은 "접근한 주소가 서로 가까운가"의 문제라 횟수에 안 나타난다 — sink 는 2k+1 로 점프하며 캐시 라인을 벗어나지만 계수는 같은 1회다. 실제 시간을 재야 보인다. (원본은 질문만 — 내 추론)

#### 6. 측정이 알려준 것 (파생)

- n=1,000에서 1,878번, n=10,000에서 18,803번 — **10배에 정확히 10배**(n log n 이면 13.3배). 둘 다 2n 아래.
- 노드의 절반은 잎이라 아예 안 움직이고, 멀리 내려갈 수 있는(깊이 큰) 노드일수록 개수가 적다. "이동 가능 거리 × 노드 수"의 급수가 2n 으로 수렴한다.
- 무작위에서는 올려보낼 원소 대부분이 한두 칸에서 멈춰 16% 차이뿐. 오름차순 입력은 새로 넣는 원소가 **매번 지금까지의 최댓값**이라 꼭대기까지 풀 코스로 올라간다 — 하향식의 최악(7,987 vs 1,982, 4배).
- 내림차순 배열은 부모가 항상 자식보다 커서 **이미 최대 힙**이다. 구성이 검사(비교 999)만 하고 교환 0으로 끝난다 — 세 판이 똑같아지는 입력.
- 비교 이득은 1.89 vs 2로 근소하지만, 트리 높이가 0.63배라 원소가 오르내리는 **거리** 자체가 짧다 — 교환(이동)이 33% 준다.
- 오름차순 17,583 / 무작위 16,857 / 내림차순 15,965 — 최대·최소가 11% 안. 로무토 퀵은 같은 크기에서 45배(11,183~499,500)를 오갔다. 대가: 평균이 퀵보다 느리다(16,857 vs 11,618). **평균을 내주고 최악을 산다.**
- 세 판의 차이는 사실상 1단계(구성)뿐인데 2단계(정렬)가 지배적이라 전체 합에서는 묻힌다(1.7%). 차이를 **관측 가능하게** 만들려고 API를 `heapify`/`sort` 로 나눴다 — 측정 가능성이 API 설계를 정한 사례.

#### 7. 구조와 경계 (파생)

- 힙 성질이 보장하는 것: 모든 부모 ≥ 자식, 따라서 꼭대기 = 전체 최댓값. 보장하지 않는 것: 형제·사촌 간 순서, 배열을 앞에서 읽었을 때의 정렬 — 힙은 정렬된 배열이 아니다(계약 테스트가 힙 성질을 "직접" 검사하는 이유).
- 완전 이진 트리는 빈틈없이 채워져 있어 위치가 인덱스로 유일하게 결정된다: 자식 2k+1, 2k+2 / 부모 (k-1)/2. 포인터를 저장할 필요가 없다.
- "1단계 끝 표시"를 구현에 시키면, 표시를 빠뜨린 실수와 알고리즘이 틀린 실수가 **같은 실패로** 보인다 — 실패의 원인을 구분할 수 없는 계측은 신뢰할 수 없다. 그래서 API 분리(heapify 를 밖에서 따로 호출)로 해결했다.
- 틀림 = 결과가 다름(테스트에 잡힘). 헛돎 = 결과도 계수도 같은데 일 없는 반복만 추가됨 — 잎의 sink 는 while 조건에서 즉시 탈락해 비교조차 안 하므로 어떤 계수기에도 안 잡힌다. 이런 차이는 코드 리뷰·주석만이 방어선이다(02번 오버플로 mid 와 같은 교훈).
- 우선순위 큐 = 같은 최대(최소) 힙 구조에서 "꼭대기 꺼내기 + sink"(= 힙 정렬 2단계의 1회분)와 "끝에 넣기 + swim"(= 하향식 구성의 1회분)을 제공하는 자료구조. 힙 정렬은 그 연산을 끝까지 돌린 것이다.
- 비교: 퀵 — 평균 최속, 최악 O(n^2)(전략에 달림), 제자리, 비안정. 병합 — 항상 O(n log n), 추가 메모리 O(n), 안정. 힙 — 항상 O(n log n), 제자리, 비안정, 평균은 퀵보다 느림. "무엇을 보장받고 무엇을 내줄 것인가"의 삼각형.
