### A. 과제 (구현 대상 — src TODO 1~9)

#### 1. `Kruskal.mst` / `Kruskal.weight` (TODO 1~4)

impl 정답의 뼈대:

```java
List<CountedGraph.Edge> sorted = g.edgeList();       // 사본
sorted.sort((a, b) -> {
    g.countComparison();
    return Long.compare(a.weight(), b.weight());     // 정렬이 비용의 대부분
});

List<CountedGraph.Edge> chosen = new ArrayList<>();
for (CountedGraph.Edge e : sorted) {
    if (uf.union(e.from(), e.to())) {                // false = 이미 같은 덩어리 = 사이클
        chosen.add(e);
        if (chosen.size() == g.vertices() - 1) {     // V-1개면 더 볼 필요 없다
            break;
        }
    }
}
return chosen;
```

- Q: 가장 가벼운 간선이 반드시 어떤 MST에 들어간다는 것을 어떻게 증명하는가?\
  A: 교환 논증이다.\
  그 간선 e가 어떤 MST에도 안 들어간다고 가정하고, 한 MST에 e를 넣어보면 사이클이 생긴다.\
  그 사이클에는 e보다 무거운(적어도 e 이상인) 간선이 반드시 있고, 그것을 빼면 다시 신장 트리인데 합이 더 작거나 같다.\
  더 작다면 원래 것이 최소가 아니었다는 모순, 같다면 e를 포함하는 MST가 존재한다는 뜻 — 어느 쪽이든 "e가 드는 MST가 있다"가 성립한다.

> **교환 논증(exchange argument)** — "이 선택이 안 들어간다"고 가정한 뒤, 답 하나를 골라 그 선택과 무언가를 맞바꿔도 손해가 없음을 보이는 증명법.\
> 예: e를 넣어 생긴 사이클에서 e보다 무거운 간선을 빼면 합이 더 작거나 같다 — 그래서 e를 쓰는 MST가 반드시 있다.

- Q: 그 논증이 두 번째, 세 번째 간선에도 계속 적용되는 이유는 무엇인가?\
  A: impl javadoc의 표현으로 "그 논증이 남은 간선들에도 그대로 적용된다".\
  이미 고른 간선들로 묶인 덩어리들을 각각 한 점으로 접어놓고 보면, 남은 그래프에서 또 "가장 가벼운(사이클 안 만드는) 간선"을 고르는 같은 문제가 된다.\
  매 단계가 같은 모양의 선택이므로 귀납적으로 끝까지 정당하다.

- Q: "사이클을 만드나"를 유니온 파인드는 어떻게 한 번의 호출로 판정하는가?\
  A: 간선을 넣어 사이클이 생긴다 = 양 끝이 이미 같은 덩어리다.\
  `uf.union(e.from(), e.to())`는 두 끝의 뿌리를 찾아(같은 덩어리인지 판정) 다르면 합치기까지 한 번에 한다.\
  판정과 합치기가 한 호출이라 따로 `find` 두 번을 부를 필요가 없다.

> **유니온 파인드(union-find, disjoint set)** — "두 원소가 같은 덩어리인가"(find)와 "덩어리 합치기"(union)를 거의 상수 시간에 하는 자료구조.\
> 예: `uf.union(a, b)` 한 번이 "같은 덩어리인가" 판정과 "합치기"를 동시에 해준다.

- Q: `uf.union(a, b)`가 돌려주는 boolean은 각각 무엇을 뜻하는가?\
  A: true = 두 끝이 딴 덩어리였고 지금 합쳤다 → 이 간선은 채택.\
  false = 이미 같은 덩어리다 → 넣으면 사이클이므로 버림.\
  impl 주석: "union 이 false 를 돌려주면 이미 같은 덩어리다.\
  넣으면 사이클이 된다."

- Q: 간선을 몇 개 고르면 멈춰도 되고, 그 수는 어디서 나오는가?\
  A: `g.vertices() - 1`개, 즉 V-1개다.\
  정점 V개를 사이클 없이 전부 잇는 트리의 간선 수가 정확히 V-1이기 때문이다 — 하나 적으면 끊기고 하나 많으면 사이클이다.\
  impl: `if (chosen.size() == g.vertices() - 1) break;`

- Q: 안 멈추고 끝까지 봐도 답이 같은 이유는 무엇이고, 무엇이 달라지는가?\
  A: V-1개를 고른 뒤에 오는 간선은 양 끝이 전부 같은 덩어리라 union이 모두 false — 아무것도 추가되지 않는다.\
  달라지는 것은 답이 아니라 비용뿐이다: 남은 간선마다 union 호출(find 두 번)이 낭비된다.\
  결과 동일 + 비용 차이 — 이 문제집에서 반복되는 "계측기 없이는 안 보이는 차이"의 한 예다.

- Q: 조기 종료의 실익이 작다는 것을 측정은 어떤 숫자로 보여줬는가?\
  A: V=400, E=79,800에서 앞쪽 2,184번만 보고 끝났다 — 간선의 36분의 1.\
  그런데 정렬은 이미 다 해버린 뒤라 비교 1,086,307번은 그대로다.\
  아끼는 것이 이미 싼 유니온 파인드뿐이다 — README의 결론: "'최적화했다'와 '빨라졌다'는 다른 말."

> **조기 종료(early exit)** — 답이 확정된 순간 남은 일을 안 하고 루프를 빠져나오는 것.\
> 예: 간선을 V-1개 고른 뒤에는 어떤 간선도 채택될 수 없으니 `break` 한다 — 다만 정렬은 이미 끝난 뒤라 아끼는 양이 작다.

- Q: `weight`의 합을 int가 아니라 long으로 받아야 하는 이유는 무엇인가?\
  A: 간선 하나의 가중치가 int 범위 안이어도, V-1개를 더한 합은 int 최대값(약 21억)을 넘을 수 있다.\
  예: 가중치가 10억인 간선 3개만 더해도 넘친다 — 조용히 음수로 감기는(overflow) 버그가 된다.\
  그래서 impl은 `long sum = 0`에 누적하고 반환형도 long이다.

> **오버플로(overflow, 넘침)** — 계산 결과가 자료형의 최댓값을 넘어 값이 조용히 뒤집히는 것.\
> 예: 가중치 10억짜리 간선 3개만 더해도 int 최대(약 21억)를 넘어 음수가 된다.

- Q: 크루스칼의 비용은 어디가 지배하고, 유니온 파인드는 측정에서 얼마나 나왔는가?\
  A: 정렬 O(E log E)가 사실상 전부다.\
  정점 2,000에서 `find` 7,994회, 올라간 걸음 7,043회 — find 한 번에 평균 0.88걸음, 정렬 비용의 약 6분의 1이다.\
  경로 압축 덕에 한 번 올라간 자리는 다음에 한 걸음이다 — "크루스칼의 비용은 사실상 전부 정렬이다."

- Q: 정렬 비교 횟수가 이론값 E log E보다 적게 나온 이유는 무엇인가?\
  A: E=19,900에서 이론값 284,181 대비 실측 255,246이었다.\
  자바 `List.sort`는 팀소트라 이미 정렬된 구간(run)을 찾아 재활용한다.\
  02번(병합 정렬)에서 비교가 하한에 2.4%까지 붙던 것과 같은 이야기다.

> **팀소트(Timsort)** — 자바·파이썬 기본 정렬. 이미 정렬된 구간(run)을 찾아 재활용한다.\
> 예: 그래서 E=19,900에서 이론값 284,181보다 적은 255,246번만 비교한다.

- Q: 그래프가 안 이어져 있을 때 크루스칼의 결과는 무엇이 되는가?\
  A: 각 덩어리의 MST를 합친 것(최소 신장 숲)이 나온다 — impl javadoc에 명시.\
  간선 목록을 전부 보므로 어느 덩어리의 간선도 빠뜨리지 않는다.\
  단 이 경우 채택 수가 V-1에 못 미치므로 조기 종료 조건에는 안 걸리고 끝까지 돈다.

> **최소 신장 숲(minimum spanning forest)** — 안 이어진 그래프에서 덩어리마다 MST를 하나씩 만들어 모은 것.\
> 예: 덩어리가 2개면 간선이 V-1개가 아니라 V-2개 나온다.

#### 2. `Prim.mst` / `Prim.weight` (TODO 5~9)

impl 정답의 뼈대:

```java
boolean[] inTree = new boolean[n];
PriorityQueue<CountedGraph.Edge> heap = new PriorityQueue<>(...weight 비교...);

for (int seed = 0; seed < n; seed++) {     // 안 이어진 그래프: 덩어리마다 새로 시작
    if (inTree[seed]) continue;
    inTree[seed] = true;
    pushIncident(g, heap, seed, inTree);
    while (!heap.isEmpty()) {
        CountedGraph.Edge e = heap.poll();
        if (inTree[e.to()]) continue;      // 반대쪽이 이미 트리 안 = 낡은 항목, 버림
        inTree[e.to()] = true;
        chosen.add(e);
        pushIncident(g, heap, e.to(), inTree);
    }
}

// pushIncident: 반대쪽이 이미 트리 안인 간선은 안 넣는다 — 답은 같고 힙만 작아진다
if (!inTree[e.to()]) heap.add(e);
```

- Q: 크루스칼이 간선 전부를 정렬하는 것과 달리, 프림은 무엇만 후보(힙)에 두는가?\
  A: **트리에 닿아 있는 간선**만 힙에 둔다 — 채택된 정점의 인접 간선들.\
  그래서 전체 정렬이 필요 없고, "지금 트리 밖으로 나가는 것 중 최소"만 물으면 된다.\
  impl javadoc: "트리에 닿아 있는 간선만 후보로 두므로 전체를 정렬할 필요가 없다."

> **힙 / 우선순위 큐(heap / priority queue)** — 지금 들어 있는 것 중 최솟값을 빨리 꺼내주는 자료구조. 넣기/꺼내기 각각 O(log 크기).\
> 예: 프림은 트리에 닿은 간선만 여기 넣고 "지금 트리 밖으로 나가는 것 중 최소"를 묻는다.

- Q: 프림이 정답인 근거(절단 논증)는 무엇이고, 크루스칼의 논증과 어떤 관계인가?\
  A: 트리와 나머지를 가르는 어떤 절단에서든, 그 절단을 건너는 가장 가벼운 횡단 간선은 반드시 어떤 MST에 들어간다.\
  증명은 크루스칼과 같은 교환 논증 — 안 들어간다 치고 넣어보면 사이클이 생기고, 그 사이클에는 절단을 건너는 다른(더 무거운) 간선이 있어 그걸 빼면 더 싸진다.\
  impl javadoc: "크루스칼의 논증과 같은 것을 절단에 대해 말한 것이다" — 같은 논증의 두 얼굴이다.

> **절단(cut)** / **횡단 간선(crossing edge)** — 정점을 두 편으로 나누는 것 / 그 두 편 사이를 건너는 간선.\
> 예: "지금까지 만든 트리"와 "나머지"로 가르면, 그 사이를 건너는 간선 중 최소가 다음 채택감이다.

- Q: 힙에서 꺼낸 간선의 반대쪽이 이미 트리 안이면 어떻게 하고, 그냥 넣으면 무엇이 되는가?\
  A: 그냥 버린다 — `if (inTree[e.to()]) continue;`.\
  넣으면 양 끝이 모두 트리 안인 간선이라 사이클이 된다.\
  힙에 넣을 때는 트리 밖이었는데 꺼낼 때는 이미 다른 경로로 편입된 경우가 이렇게 생긴다.

> **낡은 항목(stale entry)** — 힙에 넣을 때는 유효했지만 꺼낼 때는 이미 쓸모없어진 항목.\
> 예: 넣을 때 트리 밖이던 정점이 꺼낼 때는 다른 경로로 이미 편입돼 있는 간선.

- Q: 그것이 14번 다익스트라의 "낡은 항목"과 같은 모양이라는 말은 무슨 뜻인가?\
  A: 힙에 넣은 시점의 정보가 꺼낼 때는 낡아 있을 수 있고, 그 무효화를 **꺼낼 때 확인해서 버리는** 방식으로 처리한다는 공통 구조다.\
  다익스트라는 "더 짧은 거리로 이미 확정된 정점"의 항목을, 프림은 "이미 트리에 편입된 정점"으로 가는 간선을 버린다.\
  힙 안의 항목을 직접 고치는(decrease-key) 대신 중복을 허용하고 꺼내서 거르는, 같은 설계 선택이다.

> **감소 키(decrease-key)** — 힙 안에 이미 들어 있는 항목의 우선순위를 직접 낮추는 연산.\
> 예: 그 대신 같은 정점을 여러 번 넣어두고 꺼낼 때 거르는 쪽을 택하면 구현이 훨씬 단순해진다.

- Q: 씨앗 하나에서만 시작한 프림은 안 이어진 그래프에서 무엇을 놓치는가?\
  A: 시작 정점이 속한 덩어리만 훑고 끝난다 — 힙이 비면 종료인데, 다른 덩어리의 간선은 힙에 들어올 길이 없다.\
  나머지 덩어리들의 MST가 통째로 빠진 답이 나온다.\
  예외도 안 나는 조용한 누락이라 결과 검증(간선 수·합)이 없으면 모른다.

- Q: impl은 안 이어진 그래프를 어떻게 처리하는가?\
  A: 모든 정점을 씨앗 후보로 도는 바깥 루프를 둔다 — `for (int seed = 0; seed < n; seed++)`.\
  이미 트리에 들어간 정점은 건너뛰고, 아직 밖인 정점을 만나면 "이 덩어리를 처음 만났다"는 뜻이니 거기서 새로 키운다.\
  결과는 크루스칼과 같은 최소 신장 숲이 된다.

- Q: 크루스칼에는 왜 그 문제가 없는가?\
  A: 크루스칼은 특정 정점에서 출발하지 않고 **간선 목록 전체**를 보기 때문이다.\
  어느 덩어리의 간선이든 정렬된 목록에 들어 있으니 빠짐없이 심사된다.\
  탐색 시작점이라는 개념 자체가 없다 — 그래프를 보는 모양(간선 목록 vs 인접 리스트)의 차이가 여기서 드러난다.

- Q: 이미 트리 안인 정점으로 가는 간선을 힙에 넣을 때 거르면 무엇이 달라지고, 답은 왜 그대로인가?\
  A: 답은 같고 힙만 작아진다 — impl `pushIncident` 주석: "여기서 걸러도 답은 같고 힙만 작아진다.\
  그 차이를 MeasurementTest 가 잰다."\
  안 거르고 넣어도 꺼낼 때 `inTree` 검사가 어차피 버리므로 정답에는 영향이 없다.\
  거르면 힙 크기가 줄어 넣기/꺼내기 각각의 log 비용과 총 힙 연산 수가 준다 — 결과가 아니라 비용이 갈리는 최적화다.

- Q: 배열로 짠 프림(O(V²))을 만들면 어느 밀도에서 크루스칼을 이기는가, 계산으로 먼저 예측하면?\
  A: 배열 프림의 비교는 대략 V², 크루스칼은 E log E다 — V² < E log E, 즉 E가 V²/log E보다 커지는 **촘촘한** 쪽에서 배열 프림이 이긴다.\
  측정된 촘촘 V=400(E=79,800)으로 예측해보면: 배열 프림 ≈ 400² = 160,000 vs 크루스칼 실측 1,086,307 — 약 7배로 배열 프림 승.\
  반대로 성긴 V=2,000(크루스칼 42,725)에서는 배열 프림이 2,000² = 4,000,000으로 100배 가까이 진다.\
  "촘촘하면 프림"은 이 구현에 대한 말이다.\
  (원본에 근거 없음 — 내 추론, 실측 수치는 README 표에서)

- Q: 간선을 전부 정렬하지 않고 힙에서 하나씩 꺼내면 크루스칼이 빨라지는가, 어떤 그래프에서?\
  A: 조기 종료가 일찍 오는 그래프에서 빨라진다.\
  힙 구성은 O(E)이고, V-1개를 고를 때까지 꺼낸 만큼만 log 비용을 낸다.\
  측정에서 촘촘 V=400은 앞쪽 2,184개만 보고 끝났다 — 정렬 전체(1,086,307 비교) 대신 heapify + 2,184번 pop이면 되니 크게 아낀다.\
  반대로 성긴 그래프는 간선 대부분을 꺼내야 해서, 팀소트보다 상수가 큰 힙 연산 때문에 오히려 손해일 수 있다.\
  (원본에 근거 없음 — 내 추론, 조기 종료 수치는 README에서)

- Q: 최대 신장 트리는 어떻게 구하고, 코드를 얼마나 고쳐야 하는가?\
  A: 비교자 한 줄만 고치면 된다 — 내림차순 정렬(크루스칼) 또는 최대 힙(프림).\
  가중치를 전부 음수로 뒤집어 그대로 돌려도 같다.\
  교환 논증이 부등호 방향만 바뀐 채 그대로 성립하므로 알고리즘 구조는 손댈 곳이 없다.\
  (원본에 근거 없음 — 내 추론)

- Q: 간선 하나의 가중치가 바뀌면 MST를 처음부터 다시 만들어야 하는가?\
  A: 아니다, 국소 수선으로 된다.\
  트리 밖 간선이 싸졌으면: 그 간선을 넣어 트리에 생기는 유일한 사이클에서 가장 무거운 간선과 비교해, 새 간선이 더 싸면 교체한다 — O(V).\
  트리 안 간선이 비싸졌으면: 그 간선을 빼서 트리가 두 조각으로 갈라지고, 두 조각을 잇는 횡단 간선 중 최소를 다시 고른다 — O(E).\
  어느 쪽도 전체 재계산(정렬부터)보다 싸다.\
  (원본에 근거 없음 — 내 추론, 표준 기법)

#### 4. 파생 질문 (서머리 기반)

- Q: 신장 트리의 간선이 정확히 V-1개인 이유는 무엇인가?\
  A: 간선 하나를 채택할 때마다 덩어리 수가 정확히 1 줄어든다(사이클을 안 만드는 간선은 항상 두 덩어리를 합치므로).\
  V개의 낱개 덩어리에서 1개 덩어리까지 가려면 정확히 V-1번 합쳐야 한다.\
  V-1개보다 적으면 아직 안 이어졌고, 더 넣으면 이미 같은 덩어리를 잇는 것이라 사이클 — 곧 낭비다.

- Q: 가중치가 같은 간선이 여럿이면 왜 두 알고리즘의 간선 집합을 비교하면 안 되고, 무엇을 비교해야 하는가?\
  A: 답이 여러 개이기 때문이다 — 네 변이 전부 1인 정사각형은 MST가 4개다.\
  크루스칼과 프림이 각자 다른(둘 다 정답인) 간선 집합을 고를 수 있으니 집합 비교는 틀린 검증이다.\
  비교할 것은 **가중치 합** — 어떤 MST든 합은 같다.\
  테스트가 무엇을 계약으로 삼아야 하는지의 문제다.

- Q: "성긴 그래프는 크루스칼, 촘촘한 그래프는 프림"이라는 통설은 측정에서 왜 안 맞았는가?\
  A: 밀도와 무관하게 크루스칼이 약 4배 이겼다(성긴 V=2,000: 42,725 vs 175,892 / 촘촘 V=400: 1,086,307 vs 4,778,296).\
  이 프림(힙)은 트리에 닿은 간선을 전부 힙에 넣으므로 O(E log E) — 크루스칼과 **차수가 같다**.\
  그런데 힙은 넣기와 빼기를 각각 하므로 상수가 크다.\
  같은 빅오끼리는 상수가 승부를 가른다.

- Q: "촘촘하면 프림"이라는 말이 원래 가리키던 프림은 어떤 구현인가?\
  A: 힙이 아니라 **배열로 짠 프림(O(V²))**이다 — 정점마다 "트리까지의 최소 간선"을 배열로 들고 매번 선형 탐색하는 판.\
  촘촘한 그래프(E ≈ V²)에서는 V²이 E log E보다 작아져 이긴다.\
  14번에서 배열 판 다익스트라가 촘촘한 그래프에서 이기던 것과 정확히 같은 이야기다.

- Q: 무거운 간선도 MST에 반드시 들어가는 경우는 언제인가?\
  A: 그 간선이 두 부분을 잇는 유일한 길(다리)일 때다 — 빼면 그래프가 끊어진다.\
  "가벼운 것부터"는 심사 **순서**일 뿐 채택 **조건**이 아니다 — 조건은 "사이클을 안 만드나"뿐이다.\
  다리는 어느 시점에 심사되든 양 끝이 딴 덩어리이므로 반드시 채택된다.

> **다리(bridge)** — 빼면 그래프가 두 조각으로 끊어지는 간선.\
> 예: 아무리 무거워도 그 간선이 유일한 길이면 MST에 반드시 들어간다.

- Q: 크루스칼과 프림이 같은 그래프를 "다른 모양으로 본다"는 말은 코드에서 어떻게 드러나는가?\
  A: 크루스칼은 `g.edgeList()`(간선 목록)만 쓰고 인접 리스트를 아예 안 본다.\
  프림은 `g.degree(v)`/`g.incident(v, i)`(인접 리스트)만 쓰고 간선 목록을 안 본다.\
  같은 그래프에 대한 두 표현이 각각 다른 알고리즘의 출발점이 된다 — 자료구조 선택이 알고리즘 모양을 정한다.

- Q: 경로 압축이 `find` 한 번의 평균 걸음을 어디까지 내렸는가(실측)?\
  A: 정점 2,000에서 find 7,994회에 올라간 걸음 7,043회 — 평균 **0.88걸음**이다.\
  한 번 올라간 자리는 찾는 길에 만난 정점들을 전부 뿌리에 바로 붙여두므로 다음엔 한 걸음이다.\
  그래서 유니온 파인드는 "사실상 상수"고, 크루스칼의 병목은 정렬만 남는다.

> **경로 압축(path compression)** — find가 뿌리를 찾으며 지나온 정점들을 전부 뿌리에 바로 붙여, 다음 find를 한 걸음으로 만드는 기법.\
> 예: 정점 2,000에서 find 7,994회에 올라간 걸음이 7,043회 — 한 번에 평균 0.88걸음이다.

- Q: 이 챕터의 측정이 14번(다익스트라)에서 재확인해준 교훈은 무엇인가?\
  A: 같은 빅오라도 상수가 다르면 승부가 갈리고, 통설("촘촘하면 X가 낫다")은 어떤 구현에 대한 말인지 확인해야 한다는 것.\
  힙 기반끼리 비교하면 통설이 깨지고, 통설이 전제한 배열 판을 가져와야 성립한다.\
  결과가 같은 두 구현의 차이는 계측기(비교·조회 횟수)로만 보인다 — 이 문제집이 CountedGraph를 주는 이유다.
