# algorithm/02-asymptotic-analysis — 정답

## 정답

### 1. 세 표기

- 양의 상수 c, c₁, c₂, n₀가 있어 모든 n ≥ n₀에서(CLRS 3판 3.1)
  - f = O(g): 0 ≤ f(n) ≤ c·g(n) — 상한
  - f = Ω(g): 0 ≤ c·g(n) ≤ f(n) — 하한
  - f = Θ(g): c₁·g(n) ≤ f(n) ≤ c₂·g(n) — 꽉 낀 한계, O이면서 Ω
- "삽입 정렬은 O(n³)"은 정의상 참이다(상한이므로). 다만 쓸모없는 상한이다.
- 실무에서 "O(n²)"는 흔히 "n²로 자란다", 즉 Θ(n²) 뜻으로 쓴다. Princeton COS226 슬라이드는 분류에는 Θ, 상한 증명에는 O를 쓰라고 용도를 나눈다.

### 2. 삽입 정렬 비교 횟수(n = 4,000)

- 정렬됨: n − 1 = 3,999(최선)
- 무작위: 약 n²/4 = 4,000,000 근처. 실험(`Random(42)`) 3,965,190
- 역순: n(n−1)/2 = 7,998,000(최악)
- 비교 횟수라 실행마다 같다(무작위는 시드 고정 시).

### 3. 평균 경우 vs 기대 실행 시간

- 평균 경우: **입력 분포**(예: 모든 순열이 같은 확률)를 가정하고 그 분포에 대해 평균 낸 비용. 실제 입력이 그 분포가 아니면 맞지 않는다.
- 기대 실행 시간: 알고리즘이 **스스로 난수**를 쓸 때, 임의의 고정 입력에 대해 난수에 대해 평균 낸 비용(무작위 피벗 퀵 정렬). CLRS 3판 5장이 구분한다.
- 최악을 기본으로 쓰는 이유: 어떤 입력에도 성립하는 상한이라 보장으로 쓸 수 있다. 공격자나 편향된 데이터가 평균 가정을 깨도 유지된다(CLRS 2.2).

### 4. 복사 합

- 1.5배 확장: 2,430,972(원소당 약 2.43). 실제 `ArrayList`의 `elementData.length`를 리플렉션으로 관찰한 값과 시뮬레이션이 같았다. 마지막 확장 직전 용량의 약 3배 이하 → 3n 이하.
- 10칸씩 확장: 49,999,500,000(원소당 약 5만). 복사 합 ≈ n²/20 → O(n²).

### 5. 분할상환 ≠ 평균 경우

- 분할상환: 확률 없이 **어떤 연산 순서에도** n번 합이 O(n)이라는 보장. 한 번은 O(n)일 수 있다(CLRS 17장).
- 평균 경우: 입력 분포 가정 아래의 기대값.
- 실험(OpenJDK 21, --cpus=2, G1 1 GB): `add` 3천만 번 평균 약 120 ns(측정 오버헤드 포함)인데, size 20,767,725에서의 한 번이 688~826 ms(집필 3회 + 점검 2회)였다. 그 시점 GC 로그에 431~536 ms짜리 `G1 Humongous Allocation` 일시 정지가 있었다(2회). 느린 add 6개의 size가 1.5배 용량 수열(2,734,845 … 20,767,725)과 정확히 같다 → 확장 복사 순간이다.

### 6. 두 배 비율

- 실험(집필 3회 + 점검 2회 범위): O(n) ×1.65~×2.56(수 ms라 흔들림이 크다), `Arrays.sort` ×2.05~×2.34, 모든 쌍 ×3.48~×4.56.
- 선형과 제곱은 뚜렷이 갈린다. n log n은 이론 비율이 n=100만에서 약 2.10이라 잡음 속에서 선형(2.0)과 가르기 어렵다. COS226 슬라이드도 "Cannot identify logarithmic factors with doubling hypothesis"라고 단서를 단다. log 인자는 코드 분석으로 확인한다.

### 7. 100건 → 100만 건

- 비교 횟수: n(n−1)/2. 100건 4,950번, 100만 건 약 5×10¹¹번. 1억 배 차이다.
- 외삽: T(10⁶) ≈ 0.73초 × (10⁶ / 40,000)² = 0.73 × 625 ≈ 456초(약 8분). 같은 차수·상수가 유지된다는 가정의 추정이다.
- 대처: 한쪽을 `HashSet`으로 만들어 기대 O(n), 또는 둘 다 정렬 후 투 포인터로 O(n log n). 운영 최대 n과 그 두 배로 성능 테스트해 비율을 본다.

### 8. 작은 구간의 삽입 정렬

- 모순이 아니다. 점근 표기는 n ≥ n₀에서의 증가 모양만 말하고 상수와 작은 n은 버린다.
- 작은 n에서는 상수가 작은 O(n²) 삽입 정렬이 재귀·분할 오버헤드가 있는 O(n log n)보다 빠를 수 있다. 그래서 JDK는 가장 왼쪽 구간이 길이 44(`MAX_INSERTION_SORT_SIZE`) 미만이면 삽입 정렬로, 그 밖의 작은 구간은 길이 65(+보정) 미만이면 혼합 삽입 정렬로 바꾼다. 같은 이유로 분할이 깊어지면 힙 정렬로 바꿔 최악 O(n log n)을 지킨다(`MAX_RECURSION_DEPTH`).

### 9. 꼬리 지연과 humongous 할당

- 동적 배열·해시 맵의 확장은 분할상환 O(1)이지만 확장하는 그 한 번은 O(n) 복사 + 큰 새 배열 할당이다. 큰 배열은 G1에서 humongous 객체(영역 크기 절반 이상)가 되어 GC 일시 정지를 부를 수 있다. 실험에서 2천만 칸 확장 한 번이 688~826 ms였고 그중 431~536 ms가 GC였다.
- 줄이는 법: 예상 크기로 미리 용량을 잡는다(`new ArrayList<>(expectedMax)`, `HashMap.newHashMap(n)` — Java 19+). 거대 단일 컬렉션 대신 청크로 나눈다. 지연 지표는 평균이 아니라 p99·최대로 본다.
