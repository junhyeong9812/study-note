#### 1. 체와 최소 소인수 표 (`Sieve` — TODO 1~3)

**impl 정답 코드**

```java
public static List<Integer> primesUpTo(int n, CountedArith arith) {
    List<Integer> primes = new ArrayList<>();
    if (n < 2) {
        return primes;
    }
    boolean[] composite = new boolean[n + 1];
    for (int i = 2; i <= n; i++) {
        if (composite[i]) {
            continue;
        }
        primes.add(i);
        // i*i 가 int 를 넘을 수 있다. long 으로 올려서 비교한다.
        for (long j = (long) i * i; j <= n; j += i) {
            arith.iterate();
            arith.write();
            composite[(int) j] = true;
        }
    }
    return primes;
}

public static int[] smallestPrimeFactor(int n, CountedArith arith) {
    int[] spf = new int[n + 1];
    for (int i = 2; i <= n; i++) {
        if (spf[i] != 0) {
            continue;
        }
        for (long j = i; j <= n; j += i) {
            arith.iterate();
            if (spf[(int) j] == 0) {
                arith.write();
                spf[(int) j] = i;
            }
        }
    }
    return spf;
}

public static List<Integer> factorize(int x, int[] spf, CountedArith arith) {
    List<Integer> factors = new ArrayList<>();
    while (x > 1) {
        arith.iterate();
        int p = spf[x];
        factors.add(p);
        arith.divide();
        x /= p;
    }
    return factors;
}
```

- Q: 시행 나눗셈과 체는 질문의 방향이 어떻게 반대인가?\
  A: 시행 나눗셈은 **수마다** "너는 나누어지나?" 를 묻는다 — 수 하나에 나눗셈 여러 번.\
  체는 **소수마다** "내 배수를 지운다" 를 한다 — 소수 하나가 여러 칸에 쓰기.\
  같은 답(소수 목록)인데 주어가 반대고, 그 방향이 연산 종류와 횟수를 정한다.

> **에라토스테네스의 체(sieve)** — 소수를 만날 때마다 그 배수를 무더기로 지워 n 이하의 소수를 모두 찾는 방법.\
> 예: 나눗셈 없이 덧셈(`j += i`)과 배열 쓰기로만 돈다.

> **시행 나눗셈(trial division)** — 수 x를 2, 3, …, √x로 직접 나눠보는 방법.\
> 예: 소수가 최악이다 — 999,983 은 끝까지(998 번) 나눠봐야 소수인 걸 안다.

- Q: 체가 나눗셈을 한 번도 안 쓴다는 것은?\
  A: 배수를 지우는 일이 `j += i` — 덧셈과 배열 쓰기뿐이라는 뜻이다.\
  "나누어지나" 를 묻지 않고 "배수를 만들어 가며" 지우기 때문이다.\
  실측: n=100 만에서 체는 쓰기 2,122,048 / 나눗셈 0, 시행은 나눗셈 67,740,404 — 32 배.

- Q: 지우기를 `i*i` 부터 시작해도 되는 이유는?\
  A: `i*2, i*3, ..., i*(i-1)` 은 각각 2, 3, ..., i-1 의 배수이기도 해서, i 보다 작은 소수 차례에 이미 지워졌기 때문이다.\
  i 의 배수 중 "아직 아무도 안 지운 것" 의 최솟값이 i*i 다.\
  (i 가 합성수면 애초에 `composite[i]` 라서 지우기 자체를 건너뛴다.)

- Q: `(long) i * i` 로 올려야 하는 이유는?\
  A: i 가 int 범위에서 크면(예: 5 만 이상) `i*i` 가 int 상한(약 21.4 억)을 넘어 **음수로 넘쳐** 루프 조건이 엉망이 된다.\
  자바는 int 곱을 int 로 계산하고 넘쳐도 예외를 안 낸다.\
  그래서 impl 은 루프 변수 j 자체를 long 으로 두고 `(long) i * i` 에서 시작한다.

> **오버플로(overflow)** — 계산 결과가 타입의 표현 범위를 넘어 조용히 엉뚱한 값이 되는 것.\
> 예: int 곱이 21.4 억을 넘으면 음수가 되는데 자바는 예외를 안 낸다.

- Q: 최소 소인수 표는 왜 `i` 부터 돌아야 하는가?\
  A: 두 가지다.\
  첫째, `spf[i] = i` (소수 자신의 최소 소인수) 를 기록해야 한다 — i*i 부터 돌면 놓친다.\
  둘째, "누가 **처음** 지웠나" 가 곧 최소 소인수라, 이미 채워진 칸을 지나가며(`if (spf[j] == 0)` 가드) 첫 기록을 지켜야 한다.\
  체는 "지워졌다" 는 사실만 필요해 i*i 부터가 최적화지만, 표는 기록의 주인이 중요해서 순회 범위가 다르다.

> **최소 소인수 표(spf)** — 각 수마다 "나를 나누는 가장 작은 소수"를 적어둔 표.\
> 예: 체가 지우는 김에 "누가 처음 지웠나"를 기록하면 공짜로 얻는다 — spf[12] = 2.

- Q: 이미 채워진 칸을 덮어쓰면 어떤 수에서 틀리는가?\
  A: 소인수가 둘 이상인 모든 합성수에서 틀린다.\
  예: spf[6] — i=2 차례에 2 로 기록되는데, i=3 차례에 덮어쓰면 3 이 된다.\
  6 의 최소 소인수는 2 이므로 오답이고, factorize(6) 도 [3, 2] 처럼 어긋난다.

- Q: 표 타는 소인수분해의 반복이 log2(x) 를 안 넘는 이유는?\
  A: 매 반복 x 를 자기 최소 소인수 p 로 나누는데, p ≥ 2 라 x 가 적어도 절반이 되기 때문이다.\
  절반씩 줄어드는 반복은 log2(x) 번을 넘을 수 없다.\
  나눗셈 후보를 찾는 일이 표 조회 `spf[x]` 한 번(O(1))이라는 것이 핵심이다.

> **소인수분해(factorization)** — 수를 소수들의 곱으로 쪼개는 것.\
> 예: 12 = 2×2×3 — 표를 타면 12 → 6 → 3 → 1 로 나눗셈 3 번이다.

- Q: 소수가 시행 나눗셈 소인수분해의 최악인 이유는?\
  A: 소수는 sqrt(x) 까지 **전부 나눠봐야** 소수인 걸 알기 때문이다 — 중간에 끊을 계기가 없다.\
  999,983 은 sqrt ≈ 1000 이라 998 번 나눗셈, 표 타기는 spf[999983] = 999983 조회로 1 번 — 998 배.\
  고르게 뽑은 1,000 개 합계로도 189,895 대 3,421 — 55 배였다.

- Q: 쓰기로는 표가 싸 보이는데 순회로는 비싼 이유는?\
  A: 표는 빈 칸에만 쓰므로 쓰기 = 수마다 1 번 = 999,999 로 체(2,122,048)의 절반이다.\
  하지만 **모든 소수가 자기 배수 전부를 지나가며 확인**은 하므로 순회는 2,853,708 — 체보다 1.34 배다.\
  쓰기만 세면 결론이 뒤집힌다.\
  측정 도구가 무엇을 읽고 있는지도 확인해야 한다(24 번과 같은 교훈).

#### 2. 유클리드 호제법과 역원 (`Euclid` — TODO 4~6)

**impl 정답 코드**

```java
public static long gcd(long a, long b, CountedArith arith) {
    a = Math.abs(a);
    b = Math.abs(b);
    while (b != 0) {
        arith.iterate();
        arith.divide();
        long r = a % b;
        a = b;
        b = r;
    }
    return a;
}

public static long[] extendedGcd(long a, long b, CountedArith arith) {
    if (b == 0) {
        return new long[] {a, 1, 0};
    }
    arith.iterate();
    arith.divide();
    long[] sub = extendedGcd(b, a % b, arith);
    long g = sub[0];
    long x1 = sub[1];
    long y1 = sub[2];
    arith.divide();
    arith.multiply();
    return new long[] {g, y1, x1 - a / b * y1};
}

public static long modInverse(long a, long m, CountedArith arith) {
    long[] g = extendedGcd(Math.floorMod(a, m), m, arith);
    if (g[0] != 1) {
        return -1;
    }
    return Math.floorMod(g[1], m);
}
```

- Q: `gcd(a, b) = gcd(b, a mod b)` 가 반드시 끝나는 이유는?\
  A: 나머지는 나누는 수보다 **반드시 작기** 때문이다(`a mod b < b`).\
  두 번째 인자가 매 반복 순감소하는 음이 아닌 정수라 언젠가 0 이 된다.\
  b = 0 이 되면 gcd(a, 0) = a 로 종료한다.

> **유클리드 호제법(Euclidean algorithm)** — gcd(a, b) = gcd(b, a mod b)를 반복하는 방법.\
> 예: "호제"는 서로 나눈다는 뜻이다 — (48,18) → (18,12) → (12,6) → (6,0), 답은 6.

- Q: 반복이 log 인 이유는?\
  A: 두 번 돌면 값이 절반 아래가 되기 때문이다.\
  a ≥ b 일 때 `a mod b < a/2` 다 — b ≤ a/2 면 나머지가 b 보다 작아서, b > a/2 면 나머지가 `a - b < a/2` 라서.\
  절반씩 줄면 반복은 값의 비트 수, 즉 O(log) 다.

- Q: 최악이 피보나치 수 쌍인 이유는?\
  A: `F(n) mod F(n-1) = F(n-2)` — 매 반복 피보나치 **한 칸씩만** 내려가기 때문이다.\
  몫이 항상 1 이라 "나머지로 확 줄어드는" 이득이 가장 작은 배치다.\
  이것이 라메 정리의 내용이고, 실측에서 gcd(F40, F39)(1 억 급)가 38 회로 최악이었다.

> **라메 정리(Lamé)** — 유클리드 호제법의 최악 입력이 피보나치 쌍이고 반복이 log에 비례한다는 정리.\
> 예: 1 억 급 수 gcd(F40, F39)도 38 회면 끝난다.

- Q: 1 억짜리 수의 최악이 38 회라는 것의 요점은?\
  A: 최악조차 log 라서 gcd 는 사실상 **공짜 연산**이라는 것이다.\
  같은 크기의 보통 수들은 최대 16 회, 바로 옆 수 200 개는 최대 10 회 — 최악(38)도 상수 수준이다.\
  "최악을 아는 것" 과 "최악이 무섭지 않다는 것" 을 같이 확인한 측정이다.

- Q: `gcd(0, 0)` 과 음수는 어떻게 정해두는가?\
  A: impl 은 먼저 `Math.abs` 로 절댓값을 취한다 — 음수는 절댓값으로 본다.\
  gcd(0, 0) 은 루프에 안 들어가고 a = 0 을 그대로 돌려준다 — "0 으로 정해둔다" 가 이 구현의 계약이다.\
  javadoc 의 "항상 0 이상을 준다" 가 그 명세다.\
  정해두지 않으면 호출자마다 다른 가정을 하게 된다.

- Q: 확장 유클리드의 x, y 가 하나가 아니라는 것은 테스트를 어떻게 바꾸는가?\
  A: `(x + k·b/g, y - k·a/g)` 전부가 해라서, 특정 값(예: x == 3)을 기대하면 맞는 구현도 깨진다.\
  그래서 값이 아니라 **항등식** `a*x + b*y == gcd` 를 확인해야 한다(원본 함정).\
  "결과가 유일하지 않은 함수는 성질로 검증한다" 는 테스트 설계 원칙의 사례다.

> **확장 유클리드(extended gcd)** — gcd와 함께 a·x + b·y = gcd를 만족하는 정수 x, y까지 구하는 판.\
> 예: x, y는 유일하지 않아서 테스트는 값이 아니라 항등식으로 해야 한다.

- Q: 역원이 존재하는 조건과, 없을 때 impl 이 주는 것은?\
  A: `gcd(a, m) == 1` (서로소)일 때만 존재한다.\
  a*x + m*y = g 에서 mod m 을 취하면 a*x ≡ g — 이것이 1 이 되려면 g 가 1 이어야 한다.\
  impl 은 g ≠ 1 이면 `-1` 을 돌려준다 — 예외 대신 값으로 알리는 계약이다.

> **모듈러 역원(modular inverse)** — 법 m의 세계에서 곱해서 1이 되는 짝. "나누기"를 대신한다.\
> 예: 법 7에서 3의 역원은 5 (3×5=15, 15 mod 7 = 1) — gcd(a, m)=1일 때만 존재한다.

- Q: x 를 왜 `Math.floorMod(x, m)` 으로 접는가?\
  A: 확장 유클리드가 준 x 는 음수일 수 있기 때문이다.\
  역원은 `0 <= x < m` 범위의 대표값으로 주는 것이 계약이다.\
  자바 `%` 는 음수를 그대로 주므로 `floorMod` (항상 0 이상)를 쓴다 — 27 번의 `+ mod` 와 같은 함정을 표준 함수로 푼 것.

> **floorMod** — 자바에서 항상 0 이상 나머지를 주는 함수.\
> 예: `%`는 음수 입력에 음수를 준다는 함정을 피하는 도구다.

#### 3. 이진 거듭제곱 (`ModPow.power` — TODO 7)

**impl 정답 코드**

```java
public static long power(long a, long e, long m, CountedArith arith) {
    if (m == 1) {
        return 0;
    }
    long result = 1;
    a = Math.floorMod(a, m);
    while (e > 0) {
        arith.iterate();
        if ((e & 1) == 1) {
            arith.multiply();
            result = result * a % m;
        }
        arith.multiply();
        a = a * a % m;
        e >>= 1;
    }
    return result;
}
```

- Q: 곱셈이 왜 비트 수만큼으로 주는가?\
  A: a^e 를 "a 를 e 번 곱하기" 가 아니라 `a^1, a^2, a^4, a^8, ...` 제곱 사슬로 만들기 때문이다.\
  지수의 켜진 비트 자리 것만 골라 곱하면 e = 비트들의 합이므로 답이 된다.\
  제곱 (비트 수)번 + 곱하기 (켜진 비트 수)번 — 둘 다 log e 다.

> **이진 거듭제곱(binary exponentiation)** — 지수를 이진수로 보고 제곱을 거듭하며 켜진 비트만 곱해 O(log e)로 거듭제곱하는 방법.\
> 예: a^13 = a^8 × a^4 × a^1 — 13 = 1101(2) 의 켜진 자리만 곱한다.

- Q: 곱셈 27 번은 어떻게 나온 수인가?\
  A: 1,000,000 의 이진수가 20 자리이고 그중 1 이 7 개다.\
  제곱 20 번 + 켜진 자리 곱하기 7 번 = 27.\
  순진하게 곱하면 1,000,000 번 — 37,000 배 차이가 실측됐다.

- Q: 밑을 먼저 줄여두지 않으면 생기는 두 가지 문제는?\
  A: 음수 밑 — 자바 `%` 가 음수를 그대로 주므로 결과가 음수로 나온다.\
  큰 밑 — `a * a` 가 long 을 넘어 **조용히** 엉뚱한 값이 된다(m 이 10 억 근처면 곱이 10^18 로 상한에 아슬아슬한데, a 가 m 을 넘으면 확실히 넘친다).\
  그래서 impl 첫 줄이 `a = Math.floorMod(a, m)` 이다 — 이후로는 항상 `a < m` 이 유지된다.

- Q: "조용히 엉뚱한 값" 이 예외보다 위험한 이유는?\
  A: 실패가 **보이지 않기** 때문이다 — 프로그램은 정상 종료하고 값만 틀린다.\
  작은 입력 테스트는 다 통과하고, 큰 입력에서만 어긋나므로 원인 추적이 어렵다.\
  체의 `(long) i * i` 함정과 같은 종류다 — 오버플로는 항상 명시적으로 막아야 한다.

> **조용한 실패(silent failure)** — 프로그램이 에러를 내지 않고 정상처럼 끝나는데 결과만 틀린 것.\
> 예: 오버플로는 예외 없이 값만 어긋나서 작은 입력 테스트를 전부 통과한다.

- Q: `m == 1` 을 따로 처리하는 이유는?\
  A: 법이 1 이면 모든 수의 나머지가 0 이라 답이 무조건 0 이기 때문이다.\
  가드 없이 돌리면 e = 0 같은 경우 초기값 result = 1 이 그대로 나와 틀린다.\
  경계 입력을 계약(항상 `0 <= 답 < m`)에 맞추는 한 줄이다.

- Q: 24 번 분할 정복의 거듭제곱과 무엇이 같고 다른가?\
  A: 아이디어는 같다 — `a^e = (a^(e/2))^2` 로 문제를 절반으로 접는다.\
  24 번은 재귀로 위에서 내려갔고, 여기는 반복문으로 지수의 비트를 아래 자리부터 읽으며 올라간다.\
  재귀 호출 없이 변수 두 개(result, a)로 도는 것이 반복판의 이점이다.

- Q: 역원 두 방법의 비용·조건 차이는?\
  A: 실측 — 확장 유클리드: 반복 8, 곱셈 8, 나눗셈 16.\
  페르마(a^(m-2)): 반복 30, 곱셈 45, 나눗셈 0.\
  반복 기준으로 확장 유클리드가 약 4 배 싸다.\
  대신 나눗셈을 쓴다.\
  더 중요한 차이는 **조건**이다 — 페르마는 법이 소수여야만 맞다.\
  확장 유클리드는 서로소이기만 하면 된다.

> **페르마 소정리(Fermat's little theorem)** — 법 p가 소수이고 a가 p의 배수가 아니면 a^(p-1) ≡ 1 (mod p).\
> 예: 그래서 a^(p-2)가 역원이지만, p가 소수가 아니면 조용히 틀린 값을 준다.

- Q: 법이 소수가 아닐 때 페르마가 "오류도 안 내고" 틀린다는 것의 교훈은?\
  A: 법 12 에서 5 의 역원은 5 인데(5×5=25≡1), 페르마는 다른 값을 주고 예외도 안 낸다.\
  전제 조건(법이 소수)이 깨져도 코드는 그냥 돈다 — **전제는 코드가 검사해 주지 않는다.**\
  조건이 붙은 빠른 방법과 조건이 느슨한 방법 중 무엇을 쓸지는 입력의 보장을 보고 정해야 한다.

### B. 개념

#### 4. 생각해볼 것 (원본 README 이관)

- Q: 체를 홀수만 담으면 인덱스 계산은 어떻게 되나?\
  A: (원본에 근거 없음 — 내 추론) 2 는 따로 처리하고, 배열 칸 i 가 홀수 `2i + 3` (또는 `2i + 1`)을 대표하게 매핑한다.\
  수 x → 인덱스 `(x - 3) / 2`, 인덱스 i → 수 `2i + 3`.\
  지우기 보폭도 바뀐다 — 홀수 p 의 배수 중 홀수만 지우면 되므로 수 기준 보폭이 `2p`, 인덱스 기준 `p` 다.\
  메모리 절반의 대가로 이 환산이 코드 전체에 끼어드는 거래다.

- Q: 최소 소인수 표를 1 억까지 만들면 메모리가 얼마인가, 그때도 유리한가?\
  A: `int[]` 1 억 칸 = 4 바이트 × 10^8 = **약 400MB** 다.\
  (원본에 근거 없음 — 내 추론) 힙 기본 설정으로는 버겁고, 캐시에도 전혀 안 들어간다.\
  그래도 "분해 질의가 아주 많다" 면 질의당 log x 로 만드는 이 거래가 성립할 수 있다 — 전처리·메모리를 내고 질의를 사는 구조 자체는 그대로다.\
  질의가 적거나 메모리가 없으면 시행 나눗셈(질의당 O(√x))이나, 상한이 더 크면 구간을 잘라 도는 세그먼트 체로 물러선다.\
  "그때도 유리한가" 의 답은 질의 수와 메모리 예산이 정한다.

> **세그먼트 체(segmented sieve)** — 전체 범위를 한 번에 담지 않고 구간을 잘라 차례로 체질하는 방식.\
> 예: 상한이 커서 배열을 통째로 못 잡을 때 메모리를 구간 크기만큼만 쓴다.

- Q: 확장 유클리드의 x 가 여러 개인데 어느 것을 주는 게 좋은가?\
  A: 해는 `x + k·(b/g)` 꼴로 무한하다.\
  (원본에 근거 없음 — 내 추론) 재귀 구현이 자연히 주는 값을 그대로 주고, **용도에 맞는 대표값으로 접는 일은 호출자가** 하는 것이 깔끔하다 — impl 의 modInverse 가 `floorMod(x, m)` 으로 0~m-1 대표를 만드는 것이 그 예다.\
  계약으로 하나를 못박고 싶다면 "절댓값이 최소인 x" 나 "0 ≤ x < b/g" 처럼 범위로 명세한다.\
  어느 쪽이든 테스트는 항등식으로 하는 것이 안전하다(값은 구현마다 다르므로).

- Q: `a*b mod m` 에서 m 이 long 의 절반을 넘으면 어떻게 하나?\
  A: a, b < m 이어도 곱이 long 을 넘는다(10^10 × 10^10 = 10^20 > 9.2×10^18).\
  (원본에 근거 없음 — 내 추론) 방법: ① `Math.multiplyHigh`(자바 9+)로 128 비트 곱을 조립하거나 ② `BigInteger` 로 그 곱만 처리하거나 ③ 곱셈을 "덧셈의 이진 거듭제곱" 으로 바꾼 mulmod(더블링) — 이진 거듭제곱과 똑같은 구조를 곱셈 한 단계 아래에 한 번 더 쓰는 것이다.\
  요점: 이 챕터의 `% m` 트릭은 전부 "중간값 < m² ≤ long 상한" 전제 위에 서 있고, m 이 커지면 그 전제부터 다시 세워야 한다.

#### 5. 파생 — 왜 그렇게 생겼는가

- Q: "같은 답, 다른 연산" 을 체 대 시행 나눗셈으로 설명하면?\
  A: 둘 다 n 이하 소수 목록을 내지만, 시행은 나눗셈 6,700 만 번, 체는 덧셈·쓰기 212 만 번에 나눗셈 0 번이다(n=100 만).\
  알고리즘 선택이 "횟수" 만이 아니라 **어떤 연산을 쓰는가** 자체를 바꾼다.\
  질문의 방향(수마다 묻기 ↔ 소수마다 지우기)이 그 차이의 뿌리다.

- Q: 최소 소인수 표는 어떤 거래이고 10 번과 무엇이 같은가?\
  A: **전처리를 한 번 하고 질의를 계속 싸게 만드는 거래**다(원본 README).\
  누적 합이 O(n) 전처리로 구간 합 질의를 O(1) 로 만들었듯, 표는 O(n log log n)급 전처리로 분해 질의를 O(log x) 로 만든다.\
  실측: 소수 하나 분해가 998 대 1, 1,000 개 합계가 55 배.

> **전처리(preprocessing)** — 질의를 받기 전에 미리 계산해 두는 것.\
> 예: 표 만들기 한 번(O(n log log n)급)으로 분해 질의가 질의당 O(log x)가 된다.

- Q: n 10 배에 체 11 배·시행 24.7 배의 복잡도 설명은?\
  A: 체는 O(n log log n) — 거의 선형이라 10 배에 11 배(log log 의 미세한 증가분)로 붙는다.\
  시행 나눗셈은 수마다 최대 √x 급 나눗셈이라 초선형 — 그래서 24.7 배로 벌어진다.\
  같은 n 에서의 배수(32 배)만이 아니라 **성장률의 차이**가 측정에 드러난 것이다.

- Q: "측정 도구가 무엇을 읽는지 확인하라" 는 어디서 나왔는가?\
  A: 측정 둘 — n=100 만에서 쓰기 수는 표(999,999)가 체(2,122,048)의 절반인데, 순회 수는 표(2,853,708)가 1.34 배 비싸다.\
  어느 카운터를 보느냐로 "누가 싼가" 의 결론이 뒤집힌다.\
  24 번에서 배운 것과 같다 — 측정값 이전에 측정 대상부터 의심하라.

- Q: 시행 나눗셈에서 sqrt(x) 까지만 보면 되는 이유는?\
  A: x = a×b 로 쪼개지면 a ≤ b 인 쪽이 반드시 `a ≤ √x` 이기 때문이다.\
  √x 까지 약수가 없으면 그 위에도 없다 — 있다면 짝이 √x 아래 있었어야 한다.\
  같은 이유로 소인수분해에서 √x 보다 큰 소인수는 많아야 하나라, 루프 뒤에 `if (x > 1)` 로 줍는다.

- Q: 이 챕터가 27 번 해싱·RSA 와 만나는 지점은?\
  A: 27 번의 법 선택 — 충돌을 줄이는 큰 **소수** 법(10^9+7)이 여기의 소수 이야기다.\
  RSA — 모듈러 거듭제곱(power)이 암·복호화 연산 그 자체고, 키 생성이 역원(modInverse)을 쓴다.\
  조합 계산(nCr mod p)도 나눗셈 대신 페르마 역원을 쓴다 — "법 아래에서 나눗셈 = 역원 곱하기" 가 공통 다리다.
