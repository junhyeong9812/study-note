### A. 과제 (구현 대상 — src/main TODO 1\~13)

#### 1. 계수 정렬 (`CountingSort` — TODO 1\~5)

> **계수 정렬(counting sort)** — 키별 개수를 센 뒤 누적합으로 자리를 정해 꽂는 정렬.\
> 예: O(n + 범위)에 비교는 0번이다.

> **키(key)** — 원소에서 꺼낸 정렬 기준 정수. 계측기의 `key(i)`가 꺼내준다(음수도 가능).\
> 예: 이 장에서는 비교 대신 이 값을 배열 인덱스로 쓴다 — `key(i) = 7`이면 7번 칸.

정답 구현 (impl):

```java
public <T> void sort(CountedArray<T> a) {
    int n = a.size();
    if (n < 2) return;

    // TODO 1: 키의 범위. 음수 키도 있으므로 최솟값을 빼서 0 부터 맞춘다.
    int min = a.key(0), max = min;
    for (int i = 1; i < n; i++) {
        int k = a.key(i);
        if (k < min) min = k;
        if (k > max) max = k;
    }

    int range = max - min + 1;
    int[] count = a.allocateCounts(range);          // TODO 2: 이 칸 수가 진짜 비용이다

    for (int i = 0; i < n; i++) count[a.key(i) - min]++;

    // TODO 3: 누적합. count[v] 가 "키 v 가 들어갈 구간의 시작"이 된다.
    int sum = 0;
    for (int v = 0; v < range; v++) {
        int here = count[v];
        count[v] = sum;
        sum += here;
    }

    CountedArray<T> out = a.allocate(n);
    // TODO 4: 앞에서부터 넣어야 안정. 키가 아니라 원소(a.get(i))를 옮긴다.
    for (int i = 0; i < n; i++) out.set(count[a.key(i) - min]++, a.get(i));
    for (int i = 0; i < n; i++) a.set(i, out.get(i));
}

@Override
public boolean handlesWideRange() {
    // TODO 5: 키 범위만큼 배열을 잡는다. 32 비트 전체를 쓰면 40 억 칸이다.
    return false;
}
```

```
처리 과정 : 키 [5, 2a, 8, 2b, 9, 1, 4]   (2a·2b = 키가 같은 서로 다른 원소)

 1) 세기 (min=1, max=9 -> 9칸)
    키:      1  2  3  4  5  6  7  8  9
    count:  [1][2][0][1][1][0][0][1][1]

 2) 누적합 -> "그 키가 시작할 자리"
    시작:   [0][1][3][3][4][5][5][5][6]
             ^  ^        ^
             |  |        +-- 4 는 3번 자리부터
             |  +-- 2 는 1번 자리부터 (두 칸 차지)
             +-- 1 은 0번 자리부터

 3) 앞에서부터 훑으며 꽂고 시작값을 +1
    5 -> out[4]   2a -> out[1](시작 1->2)   8 -> out[5]   2b -> out[2]  ...

    out: [ 1 | 2a | 2b | 4 | 5 | 8 | 9 ]
                ^^^^^^^ 먼저 훑인 2a 가 먼저 자리를 받는다 = 안정
```

- 논리: 비교를 한 번도 안 한다 — 키를 세는 배열의 **인덱스**로 쓰고, 누적합으로 자리를 계산한다.

> **누적합(prefix sum)** — 앞에서부터 차례로 더한 합.\
> 예: 여기서는 "키 v 구간이 시작하는 자리"를 만든다 — 1은 0번부터, 2는 1번부터.

- 논리: 안정성은 "앞에서부터 훑으며 꽂기 + 시작 자리 누적합" 조합에서 나온다.

> **안정 정렬(stable)** — 같은 키의 원래 순서 유지.\
> 예: 먼저 훑인 2a가 2b보다 앞자리를 받는다.

- 비용: 키 읽기 3n(범위 구하기 n + 세기 n + 배치 n), 쓰기 2n(버퍼 n + 되돌리기 n), 비교 0.

> **출력 버퍼(buffer)** — 결과를 임시로 담는 같은 크기의 배열.\
> 예: `a.allocate(n)`으로 잡는 `out` 이 그것이다 — 계수·기수 정렬이 제자리로 안 되는 이유.

- 한계: **메모리 = 키 범위**.\
  원소가 1,000개여도 범위가 100만이면 99만 칸을 잡는다 — 이게 쓸 수 있는지 없는지를 정한다.

**질문별 답**

- Q: 계측기에서 `compare`를 뺀 것이 왜 이 박스의 전부인가?\
  A: 비교로만 정렬하는 알고리즘은 최악에 `log2(n!)`번보다 적게 비교할 수 없다 — 이 하한 아래로 내려가려면 비교를 **덜** 하는 게 아니라 **아예 안** 해야 한다.\
  계측기에 `compare`가 없고 `Comparator`도 안 받으면 그 규칙이 코드로 강제된다 — 실수로도 비교할 수 없다.\
  대신 `key(i)`가 있고, 그 키를 배열 인덱스로 쓰는 것이 하한을 우회하는 유일한 방법이다.

> **비교 정렬 / 비교 하한 log2(n!)** — 원소끼리의 대소 비교만으로 정렬하는 방식 / 그런 방식이 최악에 반드시 치러야 하는 최소 비교 횟수.\
> 예: n개의 배치 n!가지를 예/아니오로 구분하는 데 필요한 질문 수 — n=1,000이면 8,530이다.

- Q: 음수 키를 배열 인덱스로 쓰려면 무엇을 기준으로 옮기고, 잡아야 할 칸 수는 몇 개인가?\
  A: **최솟값(min)을 빼서** 0부터 시작하게 맞춘다(`key - min`).\
  칸 수는 `max - min + 1` — 양 끝을 둘 다 포함해야 하므로 +1이다.\
  이 보정이 없으면 키 -100에서 `count[-100]`을 건드려 바로 예외가 난다.

- Q: 누적합을 "v까지의 개수"로 만드는 것과 "v가 시작할 자리"로 만드는 것은 다음 단계를 어떻게 바꾸는가?\
  A: "시작 자리"로 만들면 **앞에서부터** 훑으며 `out[count[k]++]`로 꽂는 판이 된다(impl이 이쪽).\
  "v까지의 개수"로 만들면 그 값이 구간의 **끝 다음**을 가리키므로 `out[--count[k]]`로 **뒤에서부터** 넣어야 안정이 유지된다.\
  둘 다 안정하게 만들 수 있지만, 누적합의 의미와 훑는 방향이 짝으로 묶여 있어서 한쪽만 바꾸면 안정성이 깨진다.

- Q: 원소를 앞에서부터 넣는 것과 뒤에서부터 넣는 것 중 어느 쪽이 안정이고, 그 이유는?\
  A: impl의 "시작 자리" 누적합에서는 **앞에서부터**가 안정이다.\
  같은 키끼리는 훑는 순서대로 시작 자리부터 차례로 받으므로, 먼저 훑인 2a가 2b보다 앞자리를 받는다.\
  뒤에서부터 넣으면 같은 키의 순서가 뒤집힌다 — LSD에서는 그것만으로 최종 결과가 틀린다.

- Q: 키만 세서 되써넣으면 무엇이 사라지고, 어떤 테스트가 그것을 잡는가?\
  A: 키가 같은 서로 다른 원소의 **위성 데이터**(키 말고 원소에 붙은 나머지 정보)가 뭉개진다.\
  "2가 두 개"만 알고 2를 두 번 써넣으면 2a와 2b의 구분이 사라진다.\
  계약 테스트의 `keepsSatelliteData`가 그것을 본다 — 그래서 impl은 키가 아니라 `a.get(i)`, 즉 원소 자체를 옮긴다.

> **위성 데이터(satellite data)** — 키 말고 원소에 붙어 있는 나머지 정보.\
> 예: 키만 세서 되써넣으면 2a와 2b를 구분하던 이 정보가 사라진다.

- Q: 계수 정렬을 제자리로는 못 하는 이유는 무엇인가?\
  A: 각 원소가 갈 자리는 정해지는데, 그 자리에 이미 다른 원소가 있어서 덮으면 잃어버린다.\
  제자리로 하려면 순환 교환을 추적해야 하고, 그 과정에서 같은 키의 순서 보장(안정성)을 지키기 어렵다.\
  그래서 출력 버퍼 O(n)을 따로 잡고 옮긴 뒤 되돌려 쓴다. (순환 교환 설명은 원본에 근거 없음 — 내 추론)

- Q: `handlesWideRange()`가 계수 정렬만 `false`인 이유는(키가 0과 20억 둘뿐인 원소 2개를 넘기면)?\
  A: 범위가 `20억 - 0 + 1`이라 `allocateCounts`로 20억 칸짜리 `int[]`를 잡으려 한다 — 원소는 둘뿐인데 8GB다.\
  impl 주석이 그대로 말한다: "키 범위만큼 배열을 잡는다. 32비트 전체를 쓰면 40억 칸이다."\
  기수 정렬은 한 번에 8비트만 보므로 범위와 무관하게 256칸이라 `true`다.

- Q: 그 선언 하나가 계약 테스트의 무엇을 바꾸는가?\
  A: `SorterContractTest`의 `wideKeyRange`와 `extremeValues`(`Integer.MIN_VALUE`\~`MAX_VALUE`)를 **건너뛴다**.\
  즉 이 메서드는 주석이 아니라 "나에게 어디까지 물어봐도 되는가"를 테스트에 알려주는 **계약 선언**이다.\
  구현의 한계를 문서가 아니라 타입/메서드로 말하게 만든 자리다.

- Q: 원소 1,000개를 정렬할 때 키 범위가 0\~100일 때와 0\~100만일 때의 키 읽기·쓰기·메모리는 각각 얼마인가(측정치)?\
  A: 키 읽기 3,000·쓰기 2,000으로 **둘이 완전히 같고**, 메모리만 1,100칸 대 998,871칸이다.\
  908배 차이다 — 원소가 1,000개인데 칸을 99만 개 잡는다.\
  1,100 = 세는 배열 100 + 출력 버퍼 1,000이다.

- Q: 그 측정에서 "계수 정렬의 진짜 비용"은 무엇으로 드러나는가?\
  A: 시간이 아니라 **메모리**다 — 읽기·쓰기는 키 범위에 전혀 반응하지 않고 칸 수만 908배로 튄다.\
  그래서 `allocateCounts`의 크기를 계측기가 세지 않으면 계수 정렬이 그냥 공짜로 보인다.\
  "무엇을 세느냐가 무엇이 보이느냐를 정한다"의 사례다.

#### 2. LSD 기수 정렬 (`LsdRadixSort` — TODO 6\~8)

> **기수(radix) / 기수 정렬** — 진법(자릿수의 밑) / 키를 자리 단위로 쪼개 자리마다 계수 정렬을 반복하는 정렬.\
> 예: 32비트 키를 8비트씩 네 자리로 보는 것이 이 장의 기수 정렬이다.

> **LSD / MSD** — Least/Most Significant Digit — 가장 낮은/높은 자리부터 처리하는 방식.\
> 예: `[52, 25, 94, 21, 13, 45, 22]`를 LSD는 일의 자리부터, MSD는 십의 자리부터 분류한다.

정답 구현 (impl, 핵심부):

```java
public <T> void sort(CountedArray<T> a) {
    CountedArray<T> buffer = a.allocate(n);     // TODO 6: 버퍼는 하나만
    CountedArray<T> src = a, dst = buffer;

    for (int pass = 0; pass < PASSES; pass++) { // PASSES = 4
        int shift = pass * BITS;                // BITS = 8
        int[] count = a.allocateCounts(BUCKETS);// BUCKETS = 256 고정

        // TODO 7: 한 통과 = 그 자리에 대한 계수 정렬 (TODO 1~4 와 같은 순서)
        for (int i = 0; i < n; i++) count[bucket(src.key(i), shift, pass)]++;

        int sum = 0;
        for (int b = 0; b < BUCKETS; b++) { int here = count[b]; count[b] = sum; sum += here; }

        for (int i = 0; i < n; i++)
            dst.set(count[bucket(src.key(i), shift, pass)]++, src.get(i));  // 앞에서부터 = 안정

        CountedArray<T> tmp = src; src = dst; dst = tmp;   // 핑퐁
    }

    // 통과가 짝수면 결과가 원래 배열로 돌아와 있다. 홀수면 버퍼에 있다.
    if (src != a) for (int i = 0; i < n; i++) a.set(i, src.get(i));
}

private static int bucket(int key, int shift, int pass) {
    // TODO 8: >>> 를 >> 로 바꿔도 결과가 같다(변종으로 확인). & MASK 가 위 비트를 자르기 때문.
    //   그래도 >>> 로 쓴다 — 마스크를 나중에 빼면 >> 는 그 순간 틀린다.
    int b = (key >>> shift) & MASK;
    return pass == PASSES - 1 ? b ^ 0x80 : b;   // 마지막 통과에서 부호 비트 뒤집기
}
```

> **통과(pass)** — 배열 전체를 한 번 훑는 것.\
> 예: LSD는 32비트를 8비트씩 나눠 `PASSES = 4` 통과 고정이다.

> **버킷(bucket)** — 같은 키(또는 같은 자릿값)의 원소들이 들어가는 칸.\
> 예: 한 자리의 값이 0\~255뿐이라 `BUCKETS = 256`으로 고정된다.

> **핑퐁(ping-pong)** — 원본↔버퍼를 통과마다 번갈아 읽기/쓰기 대상으로 바꾸는 것.\
> 예: `tmp = src; src = dst; dst = tmp;` 한 줄이 그 맞바꿈이다.

```
안정성이 전제인 이유 : [52, 25, 94, 21, 13, 45, 22]

 1통과 (일의 자리)
   일의 자리:  2   5   4   1   3   5   2
   결과:      [21 | 52, 22 | 13 | 94 | 25, 45]
                     ^^^^^^ 52 가 22 보다 먼저 (원래 순서 유지)

 2통과 (십의 자리)
   결과:      [13 | 21, 22, 25 | 45 | 52 | 94]
                    ^^^^^^^^^^ 십의 자리가 다 2 인 셋
                    1통과가 만든 순서(21<22<25)를 안정성이 지켜준 것

 만약 2통과가 안정하지 않았다면 -> [25, 21, 22] 같은 순서가 나온다
 예외 없이 "그냥 틀린 결과"
```

- 논리: "넓은 범위"를 "좁은 자리 여러 개"로 쪼개 계수 정렬을 반복한다 — 한 자리는 항상 0\~255라 세는 배열이 256칸 고정.
- 논리: 낮은 자리부터 올라가므로, 높은 자리 단계가 앞 단계 결과를 보존(안정)해야 최종 결과가 맞는다.
- 비용: 키 읽기 4n×2 = 8n(통과마다 세기 1번 + 배치 1번), 쓰기 4n, 메모리 4×256 + n = n=1,000에서 2,024칸 고정.
- 한계: 키 범위가 좁아도 4통과를 다 돈다 — 범위를 미리 알면 계수 정렬이 확실히 싸다.

**질문별 답**

- Q: 8비트씩 보면 세는 배열이 항상 256칸으로 고정되는 이유는 무엇인가?\
  A: 8비트가 표현할 수 있는 값이 0\~255뿐이기 때문이다 — 한 자리의 값 범위가 키 전체와 무관하게 256으로 묶인다.\
  계수 정렬의 메모리는 "키 범위"에 비례하는데, 자리 하나만 보면 그 범위가 항상 256이다.\
  이것이 계수 정렬의 메모리 폭발을 피하는 요령 전부다.

- Q: 통과가 4번인 이유는 무엇이고, 키 범위가 좁아도 4번을 다 도는가?\
  A: `int`가 32비트이고 한 번에 8비트를 보므로 32/8 = 4다.\
  그렇다 — 범위가 0\~100이어도 상위 세 자리가 전부 0일 뿐 통과는 4번 다 돈다.\
  측정: 범위 0\~100인 10,000개에서 LSD 키 읽기 80,000 대 계수 정렬 30,000이다.

- Q: 매 통과마다 새 버퍼를 만들면 계측기의 무엇이 늘어나는가?\
  A: `allocations`(할당 횟수)와 `allocatedCells`(총 칸 수)다.\
  버퍼 하나를 재사용하면 할당이 5번(버퍼 1 + 세는 배열 4)에 2,024칸인데, 통과마다 새로 만들면 버퍼만 4개가 되어 칸이 3,000칸 더 붙는다.\
  `CountedArray.allocate`가 세고 있으므로 이 낭비가 숫자로 드러난다.

- Q: 통과가 끝났을 때 결과가 원본에 있는지 버퍼에 있는지는 무엇이 정하고, 코드는 그것을 어떻게 처리하는가?\
  A: **통과 횟수의 짝/홀**이 정한다 — 매 통과마다 `src`와 `dst`를 맞바꾸므로 짝수면 원래 배열로 돌아온다.\
  여기서는 4번(짝수)이라 늘 원본에 있지만, impl은 그것을 가정하지 않고 `if (src != a)`로 확인한 뒤에만 되복사한다.\
  통과 수를 바꿔도(예: 16비트씩 2통과, 또는 일부만 도는 최적화) 깨지지 않게 하는 방어다.

- Q: LSD에서 안정성이 "부가 성질이 아니라 전제"라는 말은 무슨 뜻인가?\
  A: 다른 정렬에서 안정성은 "있으면 좋은 성질"이지만, LSD에서는 **정확성의 조건**이라는 뜻이다.\
  낮은 자리에서 맞춰 둔 순서를 높은 자리 통과가 보존한다는 가정 위에 알고리즘 전체가 서 있다.\
  그래서 `Sorter` 인터페이스 주석이 "셋 다 안정이어야 한다. 여기서 안정성은 선택이 아니다"라고 못박는다.

- Q: 안정성이 깨지면 예외가 나는가, 아니면 무엇이 나는가?\
  A: 예외가 아니라 **그냥 틀린 결과**가 나온다.\
  자리마다의 정렬은 멀쩡히 끝나고, 다만 앞 통과가 맞춰 둔 순서가 흐트러져 최종 배열이 정렬되지 않을 뿐이다.\
  계약 테스트의 `isStable`과 `matchesLibrarySort`가 그것을 잡는 자리다.

- Q: 2의 보수에서 음수를 그냥 정렬하면 왜 양수보다 뒤로 가는가?\
  A: 2의 보수에서 음수는 **최상위 비트가 1**이다 — `-1`의 최상위 바이트는 255다.\
  그 바이트를 그냥 버킷 번호로 쓰면 -1이 128\~255 구간에 들어가, 최상위 바이트가 0\~127인 어떤 양수보다도 뒤로 간다.\
  비트 패턴을 부호 없는 수로 읽은 결과라, 부호를 손보지 않으면 순서가 통째로 어긋난다.

> **2의 보수 / 부호 비트** — 컴퓨터의 음수 표현법 / 그 최상위 비트(음수면 1).\
> 예: `-1`의 최상위 바이트는 255라, 손보지 않으면 어떤 양수보다도 뒤로 간다.

- Q: `b ^ 0x80`이 그 순서를 바로잡는 원리는 무엇인가?\
  A: `0x80`(=128)과의 XOR은 최상위 비트 하나만 뒤집는다 — 음수의 1→0, 양수의 0→1.\
  그러면 음수 바이트가 0\~127로, 양수 바이트가 128\~255로 옮겨가 **부호 있는 순서 = 부호 없는 순서**가 된다.\
  impl 주석 표현대로 "최상위 바이트에 128을 더해" 구간을 맞바꾸는 것과 같다.

- Q: 부호 처리를 마지막 통과에만 하는 이유는 무엇인가?\
  A: 부호 비트는 최상위 바이트에만 있고, LSD에서 그 바이트를 보는 것은 마지막 통과(`pass == PASSES - 1`)뿐이기 때문이다.\
  아래 세 자리는 순수한 비트 패턴이라 손댈 이유가 없고, 손대면 오히려 그 자리의 순서가 망가진다.\
  그래서 `bucket()`이 `pass`를 인자로 받는다 — 자리마다 규칙이 다르다는 뜻이다.

- Q: `>>>`를 `>>`로 바꿔도 결과가 같은 이유는 무엇이고, 그런데도 `>>>`로 쓰는 이유는?\
  A: 뒤에 `& MASK`가 붙어 위쪽 비트가 어차피 잘려나가기 때문이다 — 부호 확장은 잘려나가는 자리에만 영향을 준다(impl 주석: 변종을 심어 확인했다).\
  그래도 `>>>`로 쓰는 이유는 여기서 하려는 일이 "부호와 무관하게 비트를 꺼내기"이고, 코드가 그 의도를 말해야 하기 때문이다.\
  실용적 이유도 있다 — 마스크를 나중에 빼거나 옮기면 `>>`는 그 순간 틀린다.

> **비트 시프트 `>>>`, 마스크 `& 0xFF`** — 비트를 오른쪽으로 밀기(빈자리는 0), 아래 8비트만 남기기.\
> 예: 둘을 합치면 "8비트 자리 하나 꺼내기"가 된다 — `(key >>> shift) & MASK`.

    int shift = pass * BITS;
    int[] count = a.allocateCounts(BUCKETS + 1);        // TODO 11: 한 칸 더 잡는다

    for (int i = lo; i <= hi; i++) count[bucket(a.key(i), shift, pass) + 1]++;   // 한 칸 밀어 센다

    // 한 칸 민 누적합 -> count[b] = 구간 시작, count[b+1] = 구간 끝
    for (int b = 0; b < BUCKETS; b++) count[b + 1] += count[b];

    int[] cursor = a.allocateCounts(BUCKETS);           // 경계를 지키려고 커서를 따로 복사
    for (int b = 0; b < BUCKETS; b++) cursor[b] = count[b];

    for (int i = lo; i <= hi; i++)
        buffer.set(cursor[bucket(a.key(i), shift, pass)]++, a.get(i));   // 버퍼 = 상대 위치
    for (int i = lo; i <= hi; i++)
        a.set(i, buffer.get(i - lo));                                    // 되돌릴 때 i - lo

    for (int b = 0; b < BUCKETS; b++)                   // TODO 12: 재귀 경계 = 절대 위치
        sort(a, buffer, lo + count[b], lo + count[b + 1] - 1, pass - 1);

- 논리: 높은 자리에서 이미 갈라진 원소는 다시 볼 필요가 없다 — LSD의 "무조건 4통과"를 "갈릴 때까지만"으로 바꾼 것.
- 논리: 그 대가로 재귀 구간마다 세는 배열을 새로 잡는다(통과를 아끼고 메모리를 내주는 거래).
- 비용: 잘 갈라지면 키 읽기 절반 이하(4,048 대 8,000), 메모리는 36배(73,333 대 2,024칸).
- 한계: 키 범위가 좁으면 상위 자리가 전부 0이라 **아무것도 안 갈라지고**, 이득 0에 쓰기만 2배가 된다.

**질문별 답**

- Q: MSD가 멈추는 조건 둘은 각각 무엇인가?\
  A: `pass < 0` — 자리를 다 봤을 때(더 볼 비트가 없다).\
  `lo >= hi` — 구간에 원소가 하나 이하일 때(더 가를 것이 없다).\
  두 번째가 MSD를 MSD답게 만드는 조건이고, LSD에는 아예 없는 조건이다.

- Q: 구간에 원소가 하나만 남았는데 남은 자리를 계속 보면 무엇을 낭비하는가?\
  A: 그 원소에 대한 남은 통과의 **키 읽기와 쓰기 전부**, 그리고 구간마다 새로 잡는 세는 배열(257칸 + 256칸)을 낭비한다.\
  혼자 남은 원소는 이미 자기 자리가 확정됐으므로 아래 자리를 본들 순서가 안 바뀐다.\
  측정에서 MSD의 키 읽기가 LSD의 절반(4,048 대 8,000)인 것이 정확히 이 조건 덕이다.

- Q: "누적합을 한 칸 밀어서 만든다"는 것은 구체적으로 무엇을 어떻게 만드는 것인가?\
  A: 셀 때부터 `count[버킷 + 1]++`로 한 칸 뒤에 세고, 누적도 `count[b+1] += count[b]`로 돌린다.\
  그러면 `count[b]`가 버킷 b의 **시작**, `count[b+1]`이 **끝 다음**을 가리켜 구간 경계가 배열 하나에 다 들어온다.\
  그래서 세는 배열을 `BUCKETS + 1`칸(257칸)으로 잡는다.

- Q: 원소를 옮기면서 `count`를 증가시키면 왜 재귀 구간 경계가 망가지고, 코드는 어떻게 피하는가?\
  A: 배치할 때 `count[b]++`를 하면 버킷을 다 채운 뒤 `count[b]`가 시작이 아니라 **끝**을 가리키게 된다 — 재귀할 때 쓸 경계가 사라진 것이다.\
  impl은 `cursor`라는 배열을 따로 잡아 `count`를 복사한 뒤, 배치에는 `cursor`만 증가시킨다.\
  즉 "경계용 값"과 "쓰기 커서"를 물리적으로 분리한다 — 한 배열에 두 역할을 겹치지 않게 한 것이다.

- Q: 인덱스 두 종류(절대·상대)는 각각 어디에 쓰이는가?\
  A: 절대 위치는 원본 배열 `a`에서의 자리(`lo`\~`hi`)로, 훑기와 재귀 경계에 쓴다.\
  상대 위치는 이 구간 안에서의 자리(0\~`hi-lo`)로, 버퍼에 쓴다 — `count`/`cursor`가 0부터 세므로 자연히 상대값이다.\
  둘을 섞으면 조용히 엉뚱한 칸을 건드린다.

- Q: 버퍼에 옮길 때와 되돌려 쓸 때 각각 어느 쪽 인덱스를 쓰는가?\
  A: 버퍼에 옮길 때는 **상대**(`cursor[...]`가 0부터 시작하므로 그대로).\
  되돌려 쓸 때는 원본은 절대, 버퍼는 상대라 `a.set(i, buffer.get(i - lo))`로 `- lo` 변환이 들어간다.\
  재귀 경계는 절대여야 하므로 `lo + count[b]`처럼 `+ lo`를 붙인다 — `-lo`와 `+lo`가 한 함수에 같이 있다는 것이 이 코드가 헷갈리는 이유다.

- Q: MSD에서 부호 처리는 어느 통과에 필요하고, LSD와 무엇이 다른가?\
  A: 똑같이 `pass == PASSES - 1`, 즉 최상위 바이트를 보는 통과다 — `bucket()` 코드가 LSD와 글자까지 같다.\
  다른 것은 **순서**뿐이다: LSD는 그 통과가 마지막(4번째), MSD는 첫 번째다.\
  그래서 MSD에서는 부호 처리가 최상위 분류 한 번에 끝나고, 그 아래 재귀는 부호를 신경 쓰지 않는다.

- Q: 키가 32비트에 고루 퍼진 1,000개에서 LSD와 MSD의 키 읽기·할당 횟수·메모리는 각각 얼마인가(측정치)?\
  A: LSD는 키 읽기 8,000·할당 5번·2,024칸.\
  MSD는 키 읽기 4,048·할당 283번·73,333칸.\
  키 읽기는 절반인데 메모리는 36배다.

- Q: MSD가 그 이득을 무엇으로 사는가?\
  A: **재귀 구간마다 새로 잡는 세는 배열**이다 — 할당이 5번에서 283번으로 늘어난다.\
  상위 2바이트만 봐도 원소들이 거의 다 갈라져 남은 자리를 안 보게 되는 이득을, 구간 수만큼의 배열 할당으로 산다.\
  시간(통과)과 메모리(할당)를 맞바꾼 전형적인 거래다.

- Q: 키 범위가 0\~100인 1,000개에서 MSD의 키 읽기는 얼마이고, 왜 LSD와 같아지는가?\
  A: **8,000** — LSD와 똑같다.\
  범위가 0\~100이면 상위 두 바이트가 전부 0이라 첫 두 통과에서 **아무것도 안 갈라지고**, 구간이 계속 통째로 남아 네 자리를 다 본다.\
  MSD가 아끼는 근거("일찍 갈라진다")가 성립하지 않는 입력이다.

- Q: 같은 입력에서 MSD의 쓰기가 LSD의 정확히 2배인 이유는 무엇인가?\
  A: LSD는 원본과 버퍼를 **번갈아** 쓰므로 통과마다 쓰기가 1번(4,000).\
  MSD는 매 구간에서 버퍼로 옮겼다가 **되돌려 쓰므로** 통과마다 2번(8,000)이다.\
  MSD의 재귀는 각 구간이 원본 자리에 있어야 성립해서 되돌리기를 뺄 수 없다.

- Q: "키 분포를 모르면 MSD를 고를 근거가 없다"는 말이 알고리즘 선택에 대해 말하는 것은 무엇인가?\
  A: MSD의 이득은 알고리즘 자체가 아니라 **데이터가 상위 자리에서 갈라지느냐**에서 나온다는 뜻이다.\
  같은 코드가 고루 퍼진 키에서는 읽기 절반, 좁은 키에서는 이득 0에 쓰기 2배가 된다.\
  즉 여기는 "알고리즘 선택이 데이터를 알아야 가능한 자리"고, 분포를 모르면 안전한 쪽(LSD 또는 범위를 아는 계수)이 낫다.

- Q: 자리를 8비트가 아니라 16비트씩 보면 통과가 2번으로 주는데, 무엇이 늘어나고 어디가 손익분기인가?\
  A: 세는 배열이 256칸에서 **65,536칸**으로 늘어난다 — 통과가 2번이어도 counts 총량이 1,024칸에서 131,072칸으로 128배다.\
  키 읽기는 8n에서 4n으로 절반이 되므로, n이 세는 배열 크기에 비해 충분히 커야(대략 n이 수십만 이상) 이득이 난다.\
  n=1,000에서는 원소 1,000개를 정렬하려고 13만 칸을 잡는 셈이라 계수 정렬의 메모리 문제가 그대로 돌아온다. (구체 수치는 코드에서 계산한 것이고, 손익분기 규모는 내 추론)

- Q: 계수 정렬은 왜 제자리로 못 하고, 출력 버퍼 없이 하려면 무엇을 포기해야 하나?\
  A: 원소가 갈 자리에 이미 다른 원소가 있어서, 버퍼 없이 덮으면 그 원소를 잃기 때문이다.\
  버퍼 없이 하려면 (ㄱ) 순환 교환으로 자리를 밀어내며 옮기고 **안정성을 포기**하거나, (ㄴ) 키만 세서 되써넣고 **위성 데이터를 포기**해야 한다.\
  (ㄴ)는 키가 곧 원소 전부인 경우(단순 정수 배열)에만 쓸 수 있는 특수해다. (원본에 근거 없음 — 내 추론)

- Q: 문자열을 기수 정렬하려면 무엇이 달라지고, 길이가 다른 문자열은 어떻게 다루나?\
  A: 자리 = 문자 위치, 버킷 = 문자 코드 범위(ASCII면 128칸)가 된다 — 자리 수가 `int`처럼 4로 고정되지 않고 **가장 긴 문자열의 길이**가 된다.\
  길이가 다르면 "끝난 문자열"을 어떤 문자보다도 작은 **가상의 0번 버킷**으로 보내면 사전순이 맞는다("ab" < "abc").\
  길이가 제각각이면 LSD는 자리 맞추기가 번거로워 보통 MSD를 쓴다 — 앞에서 갈라진 문자열은 뒤를 안 봐도 되기 때문이다. (원본에 근거 없음 — 내 추론)

- Q: MSD에서 구간이 짧아지면 삽입 정렬로 넘기는 판이 흔한데, 그러면 이 박스의 전제(비교 없음)가 깨지나?\
  A: 깨진다 — 삽입 정렬은 비교 정렬이므로 그 순간 `compare`가 필요하고, 이 박스의 계측기로는 아예 컴파일이 안 된다.\
  다만 하한 `log2(n!)`은 **n이 클 때의 점근적 하한**이라, 구간이 10\~20개로 짧아진 뒤의 비교는 전체 비용을 지배하지 않는다.\
  즉 실무에서는 유효한 최적화지만, "비교를 아예 안 한다"는 이 박스의 규칙과는 양립하지 않는다 — 그래서 여기서는 안 한다. (원본에 근거 없음 — 내 추론)

#### 5. 파생 질문 (서머리 기반)

```
하한을 우회하는 한 줄

  비교 정렬   :  "둘 중 누가 크냐?" 를 반복   -> 최악 log2(n!) 번 (n=1000 이면 8,530)
  비교 없는 정렬 : 키를 배열 인덱스로 사용    -> 질문 자체를 안 한다

                  key(i) = 7  ->  7번 칸에 넣는다. 끝.

  하한이 깨진 게 아니라, 하한이 서 있던 전제(비교만 쓴다)가 사라진 것이다
```

**질문별 답**

- Q: 비교 정렬의 하한 `log2(n!)`은 무엇을 세는 값이고, 어떤 전제 위에 서 있는가?\
  A: n개 원소의 가능한 배치 n!가지를 예/아니오 질문으로 구분하는 데 필요한 **최소 질문 수**다.\
  비교 하나가 답을 최대 절반으로 줄이므로 최악에 `log2(n!)`번은 물어야 한다.\
  전제는 "원소에 대해 알 수 있는 것이 대소 비교 결과뿐"이다 — 이 전제가 하한 전체를 떠받친다.

- Q: 키를 배열 인덱스로 쓰면 그 하한이 왜 "깨지는" 것이 아니라 "적용되지 않는" 것인가?\
  A: `key(i) = 7`을 보고 7번 칸에 넣는 것은 비교가 아니라 **값 자체를 읽어 쓰는** 연산이라, 하한이 가정한 정보 모델 밖이기 때문이다.\
  하한은 "비교만 쓰는 알고리즘"에 대한 참인 명제고, 계수·기수 정렬은 그 부류에 속하지 않는다.\
  그래서 8,530 아래로 내려가도 모순이 아니다 — 다른 게임을 하는 것이다.

- Q: n=1,000에서 하한은 8,530인데 계수 정렬의 키 읽기는 3,000이다 — 그 3,000은 무엇 셋의 합인가?\
  A: 범위 구하기 n + 세기 n + 배치 n = 3n이다(측정 테스트 주석 그대로).\
  각 원소의 키를 정확히 세 번 읽는다는 뜻이다.\
  하한의 3분의 1 남짓한 일로 끝나고, 비교는 0번이다.

- Q: 기수 정렬은 계수 정렬의 무엇을 무엇으로 바꾼 것인가?\
  A: "한 번에 키 전체"를 "한 번에 자리 하나"로 바꾼 것이다.\
  그러면 한 통과의 키 범위가 항상 0\~255가 되어 메모리가 키 범위에서 **떨어져 나온다** — 대신 통과를 여러 번 돈다.\
  메모리 O(범위)를 시간 O(자릿수 × n)으로 바꾼 거래다.

- Q: 계수·LSD·MSD 셋 다 안정인데, 안정성의 무게가 셋에서 어떻게 다른가?\
  A: 계수 정렬에서 안정성은 **결과의 성질**이다 — 잃어도 정렬 자체는 맞는다(같은 키의 순서만 달라진다).\
  LSD에서는 **정확성의 전제**다 — 한 통과라도 안정을 잃으면 앞에서 맞춘 자리가 흐트러져 결과가 그냥 틀린다.\
  MSD는 구간이 이미 상위 자리로 갈라져 있어 LSD만큼 치명적이진 않지만, 같은 구간 안 원소의 순서를 지키려면 역시 안정이어야 한다. (MSD 부분은 원본에 근거 없음 — 내 추론)

- Q: 세 정렬의 선택 기준을 한 문장으로 말하면?\
  A: **키의 범위와 분포를 아느냐**로 정한다.\
  범위가 좁고 알 만하면 계수(측정: 범위 0\~100에서 키 읽기 30,000 대 LSD 80,000), 범위가 넓거나 모르면 LSD, 상위 자리에서 일찍 갈라진다는 것을 아는 경우에만 MSD다.\
  알고리즘 우열이 아니라 데이터에 대한 지식의 문제다.

- Q: 02번 병합 정렬은 하한의 2.4% 위까지 붙었는데, 그런데도 이 챕터가 필요한 이유는?\
  A: 병합 정렬은 하한에 **거의 도달했다** — 비교 정렬로는 더 잘할 여지가 사실상 없다는 뜻이다.\
  더 빨라지려면 잘하는 게 아니라 **다른 것을 해야** 한다 — 그게 비교를 버리는 것이다.\
  "최적에 붙었다"가 곧 "더 좋아질 수 없다"가 아니라 "전제를 바꿔야 한다"는 신호라는 것이 이 챕터의 요점이다.

- Q: 계수 정렬의 메모리가 "원소 수와 아무 상관이 없다"는 것이 실무에서 어떤 사고로 나타나는가?\
  A: 작은 입력에서 잘 돌던 코드가 **키 값 하나가 커진 순간** 메모리를 통째로 먹는다 — 원소는 그대로 1,000개인데 칸이 1,100에서 99만으로 튄다.\
  입력 크기(n)만 보고 용량을 산정하면 절대 못 잡는 사고다.\
  그래서 계수 정렬을 쓸 때는 n이 아니라 **키의 범위**에 상한을 걸어야 한다. (실무 표현은 원본에 근거 없음 — 내 추론)

- Q: 계측기에서 메서드 하나(`compare`)를 빼서 규칙을 강제한 설계는 어떤 종류의 방어이고, 문서로 적어두는 것과 무엇이 다른가?\
  A: "하지 말라"고 적는 대신 **할 수 없게 만드는** 방어다 — 컴파일이 안 되므로 실수로도 어길 수 없다.\
  문서는 읽어야 효력이 있고 어겨도 조용히 통과하지만, 없는 메서드는 시점이 앞당겨져 작성 중에 즉시 드러난다.\
  같은 발상이 `handlesWideRange()`에도 있다 — 한계를 주석이 아니라 계약으로 말하게 해서 테스트가 그것을 읽게 했다.
