# algorithm/40-complexity-p-np — P·NP·NP완전·환원·근사 — 정리 (힌트)

## 해결하는 문제

어떤 문제는 아무리 똑똑하게 짜도 입력이 조금 커지면 끝나지 않는다. 그런 문제인지 **미리 알아보지 못하면**, 정확한 답을 고집하다 배치가 몇 시간째 돈다.

```text
  변수 n개짜리 논리식이 참이 될 수 있나? (SAT) — 무차별 대입
  n = 20 → 할당 1,048,576개        29 ms   (아래 실험)
  n = 26 → 할당 67,108,864개      1679 ms
  n = 46 → 할당 2^46 ≈ 7×10^13개   1679 ms × 2^20 ≈ 20일 (외삽, 예시)
  변수 하나 = 시간 두 배
```

- 이 분야가 주는 것: "이 문제는 다항 시간 알고리즘이 알려져 있지 않고, 아마 없을 것이다"라는 **판정 도구**(환원)와, 그때 고를 **대안의 지도**(근사·휴리스틱·특수 구조·솔버)다.

쉬운 예: 친구 20명을 서로 사이 나쁜 사람이 없게 두 방에 나누기는 쉽다(이분 그래프 판정, 선형 시간). 세 방에 나누기(그래프 3-색칠)는 다항 시간 알고리즘이 알려져 있지 않다.

똑같은 구조다. 문제 설명이 조금만 바뀌어도 "쉬운 문제"와 "어려운 문제"가 갈린다.

실무 예:
- 교대 근무표·회의실 배정(스케줄링), 컨테이너·VM을 서버에 담기(빈 패킹), 배송 경로(TSP 계열).
- 패키지 의존성 해결: 설치 가능성 판정이 NP-완전임이 보여졌다(Mancinelli 외, ASE 2006). openSUSE의 libsolv는 "a free package dependency solver using a satisfiability algorithm"이다.
- 레지스터 할당(그래프 색칠), 테스트 케이스 최소화(집합 덮개).

## 동작·원리

### 1. P — 다항 시간에 풀린다

- *결정 문제(decision problem)*: 답이 예/아니오인 문제. "길이 k 이하 경로가 있나?"처럼 최적화 문제를 결정 문제로 바꿔 다룬다(CLRS 34.1).
- *다항 시간(polynomial time)*: 입력 길이 n에 대해 O(n^c) 단계 안에 끝나는 것(c는 상수).
- *P*: 다항 시간에 풀리는 결정 문제의 모임. 정렬·최단 경로·이분 매칭은 다항 시간에 풀리고, 그 결정 버전("길이 k 이하 경로가 있나?" 등)과 2-SAT이 P에 있다.
  - 흔한 오해: "배낭 문제 DP는 O(nW)니까 다항 시간이다." W는 입력에서 log W 비트로 적힌다. O(nW)는 입력 길이에 대해 지수일 수 있다. 이를 *의사 다항 시간(pseudo-polynomial)*이라 부른다.

### 2. NP — 답이 주어지면 다항 시간에 확인된다

```text
  풀기 (어렵다?)                         확인하기 (쉽다)
  "이 식을 참으로 만드는 할당이 있나?"     "x1=T, x2=F, x3=T 이면 참인가?"
   후보 2^n개                             절을 한 번씩 → 리터럴 수에 선형 (3-CNF면 O(m))
                    인증서(certificate) = 그 할당
```

- *NP*: "예"인 경우에 다항 길이의 인증서가 있고, 그것을 다항 시간에 검증할 수 있는 결정 문제의 모임(CLRS 34.2, Sipser 7.3).
  - 흔한 오해: "NP = Non-Polynomial(다항 시간이 아님)." 아니다. Nondeterministic Polynomial이다. P ⊆ NP이므로 P의 문제도 전부 NP에 속한다.
- P = NP인지는 풀리지 않은 문제다(Clay 수학연구소 밀레니엄 문제).

### 3. 환원 — 어려움을 옮기는 화살표

```text
         다항 시간 변환 f
   A의 입력 x ───────────────> B의 입력 f(x)
   "x가 A의 예"  ⇔  "f(x)가 B의 예"

   A ≤p B 이고 B가 쉬우면 → A도 쉽다
   A ≤p B 이고 A가 어려우면 → B도 어렵다
```

- *다항 시간 환원(polynomial-time reduction, A ≤p B)*: A의 입력을 다항 시간에 B의 입력으로 바꾸되, 답이 같게 바꾸는 변환(CLRS 34.3, Karp 1972).
  - 흔한 오해: 방향. "내 문제 B가 어렵다"를 보이려면 **이미 어렵다고 알려진 A를 B로** 환원한다(A ≤p B). B를 A로 환원하면 "B는 A보다 쉽거나 같다"만 나온다.

### 4. NP-완전·NP-hard

```text
                     NP-hard (NP의 어떤 문제든 여기로 환원된다)
                 ┌──────────────────────┐
     NP ┌────────┼────┐                 │
        │   P    │ NP-│   (정지 문제처럼   │
        │ 정렬    │완전 │    NP 밖의 것도)  │
        │ 2-SAT  │SAT │                 │
        │        │3-SAT, CLIQUE, VC ... │
        └────────┼────┘                 │
                 └──────────────────────┘
   (P ≠ NP 라고 가정한 그림. P = NP 이면 P·NP·NP-완전이 겹친다)
```

- *NP-hard*: NP의 어떤 문제든 그 문제로 다항 시간 환원되는 문제. NP에 속할 필요는 없다.
- *NP-완전(NP-complete)*: NP-hard이면서 NP에 속하는 문제.
- 시작점: Cook(1971, STOC)이 SAT가 NP-완전임을 보였다(Cook–Levin 정리, Sipser 7.4). Karp(1972)는 SAT에서 21개 조합 문제로 환원해 전부 NP-완전임을 보였다(CLIQUE, 해밀턴 사이클, 색칠, 분할 등).
- 결과: NP-완전 문제 하나에 다항 시간 알고리즘이 나오면 NP 전체가 P가 된다. 그래서 하나가 NP-완전이라는 것은 "수십 년간 아무도 못 찾았다"는 강한 신호다.

### 5. 환원 하나를 직접 — 3-SAT → 독립 집합

```text
  φ = (x1 ∨ x2 ∨ ¬x3) ∧ (¬x1 ∨ x3 ∨ x2)        절 2개 → 목표 k = 2

  절마다 삼각형 하나             반대 리터럴끼리 간선
     x1 ─── x2                     x1(절1) ──── ¬x1(절2)
       \   /                       ¬x3(절1) ──── x3(절2)
        ¬x3
     ¬x1 ─── x3
       \   /
        x2

  크기 2짜리 독립 집합 = 절마다 정점 하나, 서로 모순 없게 → 그 리터럴들을 참으로 = 충족 할당
  예) {x2(절1), x2(절2)} → x2 = T 이면 두 절 모두 참
```

- *독립 집합(independent set)*: 서로 간선이 없는 정점들의 집합.
- 왜 동치인가
  - 삼각형 안에서는 한 개만 고를 수 있다. 크기 k(= 절 수) 독립 집합은 절마다 정확히 하나를 고른다.
  - 반대 리터럴끼리 간선이 있으니, 고른 리터럴들은 서로 모순이 없다. 그것들을 참으로 두면 절마다 참인 리터럴이 하나 있다.
  - 반대로 충족 할당이 있으면, 절마다 참인 리터럴 하나씩을 고르면 크기 k 독립 집합이다.
- 변환 비용: 정점 3m개, 간선 O(m²). 다항 시간이다. CLRS 34.5.1은 같은 생각으로 3-CNF-SAT를 CLIQUE로 환원한다.

### 실험: 환원이 답을 보존하는지 — 무작위 3-SAT 500개

```java
static boolean[][] toGraph(int[][] f) {          // 리터럴: +v = x_v, -v = ¬x_v
    int V = f.length * 3; boolean[][] g = new boolean[V][V];
    for (int i = 0; i < V; i++) for (int j = 0; j < V; j++) {
        if (i == j) continue;
        boolean sameClause = i / 3 == j / 3;
        boolean opposite = f[i / 3][i % 3] == -f[j / 3][j % 3];
        if (sameClause || opposite) g[i][j] = true;
    }
    return g;
}
// sat(n, f): 2^n 할당을 다 본다.  hasIS(g, m): 절마다 정점 하나씩 고르는 조합을 백트래킹으로 본다.
```

(실험, OpenJDK 21.0.12 Temurin, `docker --cpus=2`, 2026-10-05, 변수 4~8개·절 5~34개, `Random(2026)`)

```text
[1] 무작위 3-SAT 500개: 충족 가능 411, 불가 89, SAT 결과 == 독립집합(k=절 수) 결과: 500/500
```

- 충족 가능한 식과 불가능한 식 양쪽에서, 두 쪽 판정이 500개 전부 같았다.
- 이 실험은 환원의 정확성을 작은 사례로 확인할 뿐이다. 증명은 위의 "왜 동치인가"가 한다.

### 실험: 변수 하나 = 시간 두 배

충족 불가능한 식(첫 두 절 `x1`·`¬x1`)이라 무차별 대입이 2^n개를 끝까지 본다.

```text
[2] 무차별 SAT: 변수 하나 늘 때 시간(충족 불가 식 — 2^n 전부 확인)
  n=20 할당   1,048,576개      29 ms  sat=false
  n=21 할당   2,097,152개      54 ms  sat=false
  n=22 할당   4,194,304개      98 ms  sat=false
  n=23 할당   8,388,608개     198 ms  sat=false
  n=24 할당  16,777,216개     416 ms  sat=false
  n=25 할당  33,554,432개     817 ms  sat=false
  n=26 할당  67,108,864개    1679 ms  sat=false
```

- 변수 하나마다 약 2배(54→98→198→416→817→1679 ms). 사실 점검 재실행(같은 환경)은 23→41→83→169→377→727→1432 ms로 단계마다 1.8~2.2배였다(절대값은 실행마다 다르다). 이 식은 첫 두 절에서 대부분 걸러져 할당 하나의 비용이 작다. 절 검사가 길어지면 상수는 커지고 두 배 비율은 그대로다.
- 이것은 "무차별 대입이 지수"라는 것만 보인다. SAT 자체가 지수 시간이 필요하다는 증명은 아니다(그것이 P vs NP 문제다).

### 6. 정확해를 포기하는 대신 — 근사

- *근사 비율(approximation ratio) ρ*: 최소화 문제에서 알고리즘 답 ≤ ρ × 최적해가 어떤 입력에서든 성립하는 것(CLRS 35장 머리말).
- 정점 덮개 2-근사(CLRS 35.1 APPROX-VERTEX-COVER): 아직 덮이지 않은 간선 하나를 골라 **두 끝점을 다** 넣고, 그 간선에 닿은 간선을 지운다. 반복한다.

```text
  고른 간선들은 서로 끝점을 공유하지 않는다 (매칭 M)
  최적 덮개는 M의 간선마다 끝점을 최소 하나 가져야 한다 → OPT ≥ |M|
  알고리즘 답 = 2|M| ≤ 2·OPT
```

### 실험: 2-근사 vs 정확해

(같은 환경, 정점 16개 무작위 그래프 300개, 정확해는 2^16 부분집합 전수)

```text
[3] 정점 덮개 근사(2-근사) vs 정확해, 정점 16개 무작위 그래프 300개
  근사/정확 비율: 평균 1.576, 최대 2.000 (정리: 2 이하)
```

- 평균 1.58배, 최대는 정확히 상한 2였다. 상한을 넘은 경우는 없었다.

근사가 늘 가능한 것은 아니다.
- 집합 덮개는 탐욕으로 로그 배 근사가 된다(CLRS 35.3).
- 삼각 부등식이 있는 TSP는 2-근사가 있다(CLRS 35.2.1). 삼각 부등식이 없는 일반 TSP는 P ≠ NP이면 상수 배 근사도 없다(CLRS 35.2.2).

### 7. 실무 선택 지도

```text
  문제가 NP-hard로 보인다
   ├─ 입력이 작다 (n ≲ 20~40, 예시) ─> 정확해: 비트마스크 DP·가지치기 백트래킹·분기 한정
   ├─ 특수 구조가 있다 ─────────────> 다항 시간: 트리·이분 그래프·2-SAT·간격 그래프 …
   ├─ 품질 보장이 필요하다 ─────────> 근사 알고리즘 (비율 ρ 보장)
   ├─ 좋은 답이면 된다 ─────────────> 휴리스틱·지역 탐색 (보장 없음, 시간 상한을 둔다)
   └─ 제약이 복잡하다 ──────────────> SAT/ILP/CP 솔버 (최악 지수. 실무 인스턴스 성능은 측정해서 판단)
```

- NP-hard의 정의는 "NP의 모든 문제가 이 문제로 다항 시간 환원된다"다. 그래서 다항 시간 알고리즘이 나오면 P=NP가 되고, 현재는 **최악** 입력에서 다항 시간 알고리즘이 알려져 있지 않다(정지 문제처럼 알고리즘 자체가 없는 NP-hard도 있다). 실제 데이터가 최악이 아닐 수 있다. 그래서 솔버·휴리스틱에도 **시간 상한과 중간 해 반환**을 둔다.

## 적용 — 풀어나가는 법

### 1. "이거 NP-hard 아닌가?" 알아보는 법

- 문제를 결정 문제로 다시 쓴다. "비용 ≤ K인 배정이 있나?"
- 알려진 NP-완전 문제와 닮았는지 본다.
  - 부분집합 고르기 + 합 제약 → 부분집합 합·배낭.
  - 그릇에 담기 → 빈 패킹.
  - 서로 충돌하지 않게 고르기 → 독립 집합·색칠.
  - 다 한 번씩 돌기 → 해밀턴 경로·TSP.
  - 불리언 제약 → SAT.
- 닮았다면 그 문제를 내 문제로 환원해 본다(방향 주의: 알려진 것 → 내 것).
- 조건 하나가 문제를 쉽게 만드는지 본다. 절당 리터럴 2개(2-SAT)는 P다. 그래프가 트리면 독립 집합은 DP로 선형 시간이다.

### 2. 코드 — 정확해에는 시간 상한을

```java
// 교대표 배정: 작은 n이면 정확 탐색, 시간 초과 시 지금까지의 최선 반환
long deadline = System.nanoTime() + Duration.ofSeconds(5).toNanos();
Assignment best = greedyInitial(problem);                 // 휴리스틱으로 시작 해부터
search(problem, partial, best, deadline);                 // 가지치기 백트래킹, deadline 넘으면 중단
return best;                                              // 최적 증명 여부를 함께 기록한다
```

- 배치·API가 정확해 탐색을 한다면 "최적임을 증명했나 / 시간 초과로 멈췄나"를 결과에 남긴다.

### 3. 코딩 테스트 — 입력 크기에서 거꾸로

- n ≤ 20: 2^n·n 정도의 부분집합 탐색이 가능한 크기(예시 기준).
- n ≤ 100에 "부분집합" 문제: 숫자 범위가 작으면 의사 다항 DP(배낭).
- n이 10^5인데 NP-hard처럼 보이면: 문제에 숨은 특수 구조(트리·정렬 가능·이분)를 찾는다.

### 4. 진단 — "배치가 몇 시간째"

- 스레드 덤프(`jcmd <pid> Thread.print`)에서 같은 재귀 탐색 프레임이 계속 보이는지 확인한다.
- 입력 크기를 1씩 늘린 실행 시간 비율이 상수(2배 등)면 지수 시간을 의심한다. 두 배 크기에 4배면 n² 같은 다항 시간을 의심한다. 유한한 측정 비율은 단서일 뿐이고, 복잡도 확정은 알고리즘 분석으로 한다.
- 대처: 시간 상한 + 근사·휴리스틱 대체, 또는 솔버.

## 장애 시나리오와 대처

### 1. NP-hard 문제에 정확해 고집 → 무한 대기

- 현상: 근무표·배송 경로 배치가 직원·지점이 몇 명 늘자 끝나지 않는다.
- 보이는 형태: 배치 타임아웃. CPU 한 코어 100% 지속. 스레드 덤프에 같은 탐색 프레임. 입력 +1마다 실행 시간 약 2배(위 실험처럼).
- 원인: 지수 시간 정확 탐색(무차별 대입·순열 전수)을 작은 테스트 데이터로만 검증했다.
- 대처: 시간 상한과 중간 해 반환. 근사(보장 필요)·휴리스틱(보장 불필요)·솔버로 교체. 입력 크기 상한을 문서화한다.
- ⚠ 커리큘럼: "NP-hard 문제에 정확해 고집 → 무한 대기".

### 2. 근사·휴리스틱 선택 기준 부재

- 현상: 팀마다 다른 휴리스틱을 붙여 결과 품질이 들쭉날쭉하다. "최적에서 얼마나 먼지" 아무도 모른다.
- 보이는 형태: 같은 입력에 버전마다 비용이 크게 다르다. 회귀 테스트가 "더 나빠짐"을 못 잡는다.
- 원인: 근사 비율(보장)과 휴리스틱(보장 없음)을 구분하지 않았다. 품질 지표·하한(lower bound)을 정하지 않았다.
- 대처: 보장이 필요하면 근사 알고리즘(비율 명시, 예: 정점 덮개 ≤ 2·OPT). 휴리스틱은 작은 입력에서 정확해와 비교한 비율 분포(위 실험처럼 평균·최대)를 회귀 지표로 둔다. 가능하면 LP 완화 등으로 하한을 계산해 격차를 기록한다.
- ⚠ 커리큘럼: "근사·휴리스틱 선택 기준 부재".

### 3. 의사 다항 DP의 메모리 폭발

- 현상: 배낭식 DP가 테스트에서는 빠르다. 운영에서 `java.lang.OutOfMemoryError: Java heap space`.
- 보이는 형태: 금액 단위를 원 → 0.01원으로 바꾼 뒤부터 실패. DP 표 크기 `n × W`.
- 원인: O(nW)는 W의 **값**에 비례한다. 단위를 100배로 쪼개면 표도 100배다.
- 대처: 단위를 거칠게(근사 스케일링), 또는 다른 축(가치)으로 DP. 정밀해야 하면 분기 한정·ILP 솔버.

### 4. 환원 방향을 거꾸로 해서 "쉬운 문제"를 포기

- 현상: "이건 NP-완전 문제로 바꿀 수 있으니 어렵다"며 근사를 붙였는데, 실은 다항 시간 해법이 있었다.
- 보이는 형태: 설계 문서의 근거가 "내 문제 → SAT로 변환 가능".
- 원인: 내 문제 B를 어려운 A로 환원(B ≤p A)한 것은 B가 쉽다는 증거도 어렵다는 증거도 아니다. 어렵다고 하려면 A ≤p B가 필요하다.
- 대처: 방향 확인. 특수 구조(2-SAT, 이분 그래프, 트리) 먼저 확인.

## 핵심 문장

- P는 다항 시간에 풀리는 문제, NP는 답이 주어지면 다항 시간에 확인되는 문제다. NP는 "다항이 아님"이 아니다.
- "B가 어렵다"를 보이려면 이미 어려운 A를 B로 환원한다(A ≤p B). 방향을 거꾸로 하면 아무것도 증명되지 않는다.
- NP-완전 문제 하나라도 다항 시간에 풀리면 NP 전체가 P가 된다. P = NP인지는 아직 풀리지 않았다.
- NP-hard는 최악 입력 이야기다. 실무에서는 작은 n의 정확해, 특수 구조, 근사(보장), 휴리스틱(보장 없음), 솔버 중에서 고르고 시간 상한을 둔다.
- 근사 비율은 증명된 보장이다. 정점 덮개 탐욕 매칭은 최적의 2배를 넘지 않는다.
