# algorithm/11-external-sort-and-k-way-merge — 정답

## 정답

### 1. 왜 외부 정렬인가

- 전부 올리면 힙 한도를 넘는다. 실험: `-Xmx64m`에서 128MB `long[]`을 만들자 `java.lang.OutOfMemoryError: Java heap space`.
- 두 단계: ① 메모리만큼 읽어 정렬해 런 파일로 쓴다 ② 런들의 맨 앞만 메모리에 두고 k-way 병합한다. 메모리 사용이 입력 크기와 무관해진다.

### 2. 4-way 병합

```text
  run0 [1 5 9]  run1 [2 7 8]  run2 [3 4 6]  run3 [0 10 11]
  힙: (0,run3) (1,run0) (2,run1) (3,run2)
  pop (0,run3) → 출력 0 → run3의 다음 값 10을 push
  pop (1,run0) → 출력 1 → run0의 다음 값 5를 push
  …  힙이 비면 끝
```

- 힙에는 런마다 "현재 맨 앞 값 + 런 번호" 하나씩, 최대 k개가 있다.

### 3. 공식과 계산

- 런 수 ⌈N/B⌉, 병합 패스 ⌈log_(B−1) ⌈N/B⌉⌉, 총 패스 1 + 그 값, 총 I/O 2N × 총 패스(CMU 15-445 L11).
- N = 1,000, B = 11: 런 ⌈1000/11⌉ = 91개. 팬인 10이면 91 → 10 → 1로 병합 패스 2. 총 패스 3, I/O 2 × 1,000 × 3 = 6,000 블록.

### 4. 팬인별 실험 결과

| 팬인 | 병합 패스 | 쓴 바이트 / 입력 |
|---|---|---|
| 8 | 1 (8→1) | 2.0 |
| 4 | 2 (8→2→1) | 3.0 |
| 2 | 3 (8→4→2→1) | 4.0 |

- 쓴 바이트 = (런 만들기 1 + 병합 패스) × 입력. 세 경우 모두 정렬·개수·합 검증을 통과했다.

### 5. 팬인의 맞바꿈

- 팬인이 크면 패스가 줄어 전체 I/O가 준다.
- 대신 같은 메모리를 더 많은 런이 나눠 써서 런당 버퍼가 작아진다. 읽기가 잘게 쪼개져 HDD에서는 탐색이 늘고, 여는 파일 수도 늘어난다(Hadoop `io.sort.factor` 설명: "여는 파일 핸들 수").

### 6. 비교 수

- 선형: 원소당 k − 1(실험 k=512에서 510.75 — 끝에 빈 런이 생기면 조금 준다).
- 힙: O(log k). 실험 k=512에서 17.22.
- `PriorityQueue`는 `poll`의 아래로 내리기(층마다 비교 2번)와 `add`의 위로 올리기를 따로 해 약 2 log₂ k가 든다. 루트를 바꿔 끼우고 한 번만 내리거나 패자 트리를 쓰면 줄어든다.

### 7. 대체 선택

- 힙에서 최솟값을 내보내고, 새로 읽은 값이 마지막 출력보다 크거나 같으면 이번 런, 작으면 다음 런으로 표시해 힙에 넣는 런 만들기 방법이다.
- 실험(M=10,000, n=2,000,000): 무작위 → 런 101개, 평균 19,801(약 2M, Knuth 5.4.1과 일치). 정렬 → 런 1개. 역순 → 200개(M 그대로).
- PostgreSQL은 9.6에서 런 만들기를 퀵소트로 바꾸고(대체 선택은 튜플 수가 `replacement_sort_tuples`(기본 150,000)보다 작을 때 첫 런에만 남김), 11에서 그 설정과 대체 선택을 없앴다. 이유: 9.6 릴리스 노트는 퀵소트가 "CPU 캐시를 더 잘 쓴다", 11.0 릴리스 노트는 대체 선택이 "더 이상 유용하지 않다"고 적는다. 해석: 힙 기반 런 만들기는 캐시 효율이 나빠, 런이 길어지는 이득보다 CPU 손해가 컸다.

### 8. external merge

- 정렬 대상이 `work_mem`(PostgreSQL 17 기본 4MB)을 넘어 디스크 런 + 병합으로 넘어갔다. 패스마다 데이터 전체를 읽고 쓴다(단 PostgreSQL은 마지막 병합 결과를 디스크에 쓰지 않고 바로 소비자에게 넘긴다 — `tuplesort.c`).
- 대처: 필요한 열만 정렬, `LIMIT`이면 Top-N 힙, 정렬 순서와 맞는 인덱스, 해당 세션·쿼리만 `work_mem`을 올린다. 전역 상향은 동시 쿼리 × 정렬 노드 수만큼 곱해져 위험하다(database/41).
- 디스크가 실제로 읽히는지는 별개다. database/41 로컬 재현에서는 페이지 캐시 덕에 스필이 곧 느림이 아니었다.

### 9. 조용한 누락

- 원인: 마지막 덜 찬 런을 버리는 경계 버그, EOF 처리 실수, 런 만들기와 병합이 다른 비교자(로캘·대소문자)를 써서 "각 런이 같은 순서로 정렬됨" 전제가 깨짐.
- 검증: 출력의 개수·합(체크섬)을 입력과 비교하고, 출력이 단조인지 훑는다. 이는 일부 오류를 싸게 잡는 검사다 — `[1,2,3,4]` → `[1,1,4,4]`처럼 값끼리 상쇄되면 통과하므로, 완전히 확인하려면 원소별 개수(다중집합)까지 비교한다. 실험 코드의 `검증: 정렬됨=true 개수 16,000,000/16,000,000 합 일치=true`가 그 예다.

### 10. 같은 연산이 나오는 곳

- LSM compaction: 정렬된 SSTable(런) 여러 개를 k-way 병합해 새 SSTable을 만든다. 같은 키의 옛 버전은 그 값을 보는 스냅숏이 없으면 버리고 최신만 남긴다(RocksDB는 살아 있는 스냅숏에 보이는 버전을 보존한다 — Snapshot 위키 "Flush/compaction").
- 정렬 병합 조인: 두 입력을 조인 키로 (외부) 정렬한 뒤 두 포인터로 나란히 읽는다.
- MapReduce: 맵 쪽이 버퍼를 정렬해 spill 파일(런)로 쓰고, `io.sort.factor`(기본 10)개씩 병합한다. 리듀스 쪽도 받은 조각들을 병합한다.
