#### 1. lowerBound / upperBound (TODO 1·2·5·6)

> **이진 탐색(binary search)** — 정렬된 범위에서 가운데를 보고 절반을 버리기를 반복하는 탐색. O(log n).\
> 예: `[10, 20, 20, 20, 30, 40, 50]` 에서 20을 찾을 때 가운데(a[3])부터 본다.

> **lowerBound / upperBound** — key 이상인 첫 자리 / key 초과인 첫 자리. 둘의 차이가 그 값의 개수.\
> 예: 위 배열에서 lowerBound(20)=1, upperBound(20)=4 이고 4 - 1 = 3 이 20 의 개수다.

> **반열린 구간 `[lo, hi)`** — lo는 포함, hi는 제외인 구간. 닫힌 구간 `[lo, hi]`는 양끝 다 포함.\
> 예: 길이 7인 배열이면 반열린 판은 `hi = 7`(구간 밖)로, 닫힌 판은 `hi = 6`(구간 안)으로 시작한다.

**반열린 판** (`impl/com/algo/bsearch/HalfOpenSearch.java`):

```java
public <T> int lowerBound(CountedArray<T> a, T key) {
    int lo = 0;
    int hi = a.size();
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a.compareTo(mid, key) < 0) {
            // mid 는 key 보다 작다. 답이 될 수 없으니 구간에서 뺀다.
            lo = mid + 1;
        } else {
            // mid 는 답일 수 있다. 그래서 hi 를 mid + 1 이 아니라 mid 로 줄인다.
            hi = mid;
        }
    }
    return lo;
}
```

upperBound 는 위 코드에서 `< 0` 이 `<= 0` 으로 바뀐 것뿐이다(부등호 하나).

```
처리 과정 : [10, 20, 20, 20, 30, 40, 50], lowerBound(20) — 반열린 [lo, hi)

    idx    0    1    2    3    4    5    6
         +----+----+----+----+----+----+----+
         | 10 | 20 | 20 | 20 | 30 | 40 | 50 |
         +----+----+----+----+----+----+----+
          lo=0                                hi=7 (구간 밖)

 [1] mid=3 : a[3]=20 ≥ 20 → 답 후보다 → hi = mid = 3   (mid 를 구간에 남긴다)
 [2] mid=1 : a[1]=20 ≥ 20 → 답 후보다 → hi = mid = 1
 [3] mid=0 : a[0]=10 < 20 → 답 못 된다 → lo = mid+1 = 1
 [4] lo == hi == 1 → 루프 끝 → return lo = 1

 upperBound(20) 은 같은 흐름에서 "≤ 면 lo 를 민다" 라서 4 가 나온다.
 upperBound - lowerBound = 4 - 1 = 3 = 20 의 개수
```

**닫힌 판** (`impl/com/algo/bsearch/ClosedIntervalSearch.java`):

```java
public <T> int lowerBound(CountedArray<T> a, T key) {
    int lo = 0;
    int hi = a.size() - 1;
    // 아무것도 못 찾으면 size 다. "전부 key 보다 작다"는 뜻이다.
    int answer = a.size();

    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (a.compareTo(mid, key) < 0) {
            lo = mid + 1;
        } else {
            answer = mid;
            hi = mid - 1;
        }
    }
    return answer;
}
```

```
처리 과정 : 같은 배열, lowerBound(20) — 닫힌 [lo, hi]

 시작       : lo=0, hi=6, answer=7(size)   루프 조건 lo <= hi
 [1] mid=3 : a[3]=20 ≥ 20 → answer=3 기억 → hi = mid-1 = 2
 [2] mid=1 : a[1]=20 ≥ 20 → answer=1 기억 → hi = mid-1 = 0
 [3] mid=0 : a[0]=10 < 20 → lo = mid+1 = 1
 [4] lo(1) > hi(0) — 엇갈렸다 → 루프 끝 → return answer = 1

 lo/hi 가 엇갈린 값(1, 0)으로 답을 복원하려 들면 헷갈린다.
 그래서 후보를 만날 때마다 answer 에 기억해 뒀다가 그걸 돌려준다.
```

**질문별 답**

- Q: lowerBound와 upperBound는 코드에서 정확히 무엇 하나만 다른가?\
  A: 비교의 부등호 하나다 — `a.compareTo(mid, key) < 0` 이 `<= 0` 으로 바뀐다.\
  "mid 가 key 와 같을 때"를 왼쪽(작은 쪽)으로 보느냐가 갈림길이다.\
  lowerBound 는 같으면 답 후보로 남기고(`hi = mid`), upperBound 는 같으면 버린다(`lo = mid + 1`).\
  그래서 lowerBound 는 같은 값 구간의 첫 자리에, upperBound 는 그 구간 바로 다음 자리에 선다.

- Q: `upperBound - lowerBound` 가 왜 그 값의 개수가 되는가?\
  A: 정렬된 배열에서 같은 값은 반드시 붙어 있다.\
  lowerBound 는 그 구간의 시작(key 이상인 첫 자리), upperBound 는 그 구간의 끝 다음(key 초과인 첫 자리)이다.\
  반열린 구간 `[lowerBound, upperBound)` 안의 원소는 전부 key 와 같으므로, 길이 = 개수다.\
  위 그림에서 4 - 1 = 3 이 20 의 개수다. key 가 없으면 두 값이 같아 0 이 나온다.

> **정렬(sorted)** — 값이 작은 것부터(오름차순) 순서대로 놓여 있는 상태. 절반을 버려도 되는 근거.\
> 예: `[10, 20, 20, 20, 30, 40, 50]` 처럼 놓여 있어야 같은 값 20 들이 한 덩어리로 붙는다.

- Q: 반열린 판에서 처음 `hi` 는 size 인가 size-1 인가, 왜인가?\
  A: size 다.\
  반열린 `[lo, hi)` 에서 hi 는 구간 밖(제외)이기 때문이다.\
  답이 될 수 있는 자리는 0부터 size 까지다 — "전부 key 보다 작으면" 답이 size(배열 끝)여야 하니까.\
  hi = size 로 시작해야 lo 가 size 까지 갈 수 있다.\
  size - 1 로 시작하면 마지막 원소(size-1)가 답인 경우와 "없음(size)"인 경우가 깨진다.

- Q: mid 가 답 후보일 때 `hi = mid` 로 줄여야지 `mid - 1` 로 줄이면 안 되는 이유는?\
  A: mid 가 답일 수 있는데 `mid - 1` 로 줄이면 mid 를 구간에서 빼버린다.\
  진짜 답이 mid 였다면 그 답을 영영 잃는다 — 무한 루프가 아니라 오답이 나온다.\
  반열린에서 `hi = mid` 는 안전하다: mid 는 항상 hi 보다 작게 계산되므로 구간은 반드시 준다.\
  원칙 한 문장: **답 후보일 수 있는 것을 구간에서 빼면 안 된다.**

- Q: 반대로 닫힌 판에서는 왜 `hi = mid - 1` 로 줄여야 하는가?\
  A: 닫힌 `[lo, hi]` 에서는 hi 가 구간 안이라서 `hi = mid` 로 두면 구간이 안 줄 수 있다.\
  lo == hi == mid 인 순간 `hi = mid` 는 아무것도 안 바꾸고 루프가 영원히 돈다 — 무한 루프.\
  그래서 mid 를 구간에서 빼되(`hi = mid - 1`), 빼기 전에 answer 변수에 기억해 둔다.\
  같은 "한 칸 차이"가 반열린에서는 오답을, 닫힌에서는 무한 루프를 만든다 — 판에 따라 반대다.

> **무한 루프(infinite loop)** — 구간이 안 줄어서 루프가 영원히 도는 버그.\
> 예: 닫힌 판에서 `lo == hi == mid` 일 때 `hi = mid` 로 쓰면 구간이 그대로라 영원히 돈다.

- Q: 닫힌 판의 답 후보 변수(answer)의 초기값은 무엇이고 그 값의 의미는?\
  A: `a.size()` 다.\
  의미는 "아무것도 못 찾았다 = 전부 key 보다 작다"이고, 그때 넣을 자리는 배열 끝(size)이다.\
  루프에서 답 후보를 한 번도 못 만나면 이 초기값이 그대로 반환된다.\
  반열린 판에서 lo 가 저절로 size 로 가는 것과 같은 결과를, 닫힌 판은 초기값으로 만들어 둔다.

- Q: key 가 배열의 모든 값보다 클 때 반열린 판은 무엇을 돌려주고, 그게 왜 "저절로" 되는가?\
  A: size 를 돌려준다.\
  모든 비교가 `a[mid] < key` 라서 매번 `lo = mid + 1` 만 실행되고, lo 는 오른쪽으로만 민다.\
  결국 lo == hi == size 에서 루프가 끝나고 lo 를 그대로 돌려준다.\
  "못 찾았다"를 검사하는 코드가 한 줄도 없는데 맞는 답이 나온다 — 구간 설계가 경계 처리를 대신한다.

- Q: 두 판의 비교 횟수(성능)는 다른가, 같다면 고르는 기준은 무엇인가?\
  A: 완전히 같다.\
  MeasurementTest 가 n=1,000 과 n=1,000,000 에서 두 판의 lowerBound 비교 횟수가 정확히 같음을 확인한다.\
  갈리는 것은 성능이 아니라 **코드의 실수 여지**다.\
  반열린은 answer 변수도, "못 찾음" 처리도 필요 없어 코드가 짧다.\
  닫힌은 교과서에 더 자주 나오는 형태라 읽을 줄은 알아야 한다 — 결국 취향과 실수 여지로 고른다.

#### 2. find (TODO 3·7)

**반열린 판 — lowerBound 로 파생 (두 줄)**:

```java
public <T> int find(CountedArray<T> a, T key) {
    int i = lowerBound(a, key);
    // 범위 검사를 먼저 해야 한다. 순서를 바꾸면 배열 끝에서 터진다.
    if (i < a.size() && a.compareTo(i, key) == 0) {
        return i;
    }
    return -1;
}
```

**닫힌 판 — 직접 찾기 (비교 3갈래)**:

```java
public <T> int find(CountedArray<T> a, T key) {
    int lo = 0;
    int hi = a.size() - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        int c = a.compareTo(mid, key);
        if (c == 0) {
            return mid;   // 같으면 그 자리에서 바로 끝
        }
        if (c < 0) {
            lo = mid + 1;
        } else {
            hi = mid - 1;
        }
    }
    return -1;
}
```

```
처리 과정 : [0, 2, 4, 6, 8, 10, 12] (짝수 배열) 에서 find(6)

 직접 찾기(닫힌 판):
   [1] mid=3 : a[3]=6 == 6 → 비교 1번 만에 return 3   ← 운이 좋으면 여기서 끝

 파생 find(반열린 판): lowerBound 는 같아도 멈추지 않는다
   [1] mid=3 : a[3]=6 ≥ 6 → hi=3      (같아도 "후보"로만 두고 계속 좁힌다)
   [2] mid=1 : a[1]=2 < 6 → lo=2
   [3] mid=2 : a[2]=4 < 6 → lo=3
       lo==hi==3 → lowerBound=3, 비교 3번
   [4] a[3]==6 확인 +1번 → 총 4번 만에 return 3

 없는 값 find(5) — 파생 쪽:
   lowerBound(5)=3 까지 좁히는 비교 + "a[3] 이 정말 5 인가?" 마지막 1번 → 아니다 → -1
   이 마지막 1번이 측정의 "10 대 11" 이다. 빼먹으면 없는 값을 찾았다고 답한다.
```

**질문별 답**

- Q: lowerBound 로 find 를 파생시키는 두 줄은 무엇인가?\
  A: `int i = lowerBound(a, key);` 로 "key 가 있어야 할 자리"를 받는다.\
  그리고 `if (i < a.size() && a.compareTo(i, key) == 0) return i; return -1;` — 그 자리가 범위 안이고 정말 key 인지 확인한다.\
  lowerBound 는 "넣을 자리"를 줄 뿐 "그 값이 있다"를 말하지 않으므로 확인이 꼭 필요하다.\
  경계 찾기(lowerBound)가 본체이고 값 찾기(find)는 파생이라는 이 챕터의 관점이 코드 두 줄로 드러난다.

> **경계(boundary)** — 조건이 거짓에서 참으로 바뀌는 자리. 이진 탐색이 실제로 찾는 것.\
> 예: lowerBound 가 찾는 "key 이상이 처음 되는 자리"가 바로 그 경계다.

- Q: 범위 검사와 값 확인의 순서를 바꾸면 어떤 입력에서 어떻게 터지는가?\
  A: key 가 배열의 모든 값보다 클 때 터진다.\
  그때 lowerBound 는 size 를 돌려주는데, 값 확인을 먼저 하면 `a.compareTo(size, key)` 가 `items[size]` 를 읽는다.\
  배열의 유효 인덱스는 size - 1 까지라서 ArrayIndexOutOfBoundsException 이다.\
  `i < a.size()` 를 먼저 두면 자바 `&&` 의 단축 평가로 뒤쪽 접근이 아예 실행되지 않는다.

- Q: 직접 찾기(3갈래 비교)는 파생 find 와 평균 비교 횟수가 어떻게 다른가(측정치)?\
  A: n=1,000 의 모든 키를 찾아본 측정에서 평균 **8 대 10** — 직접 찾기가 약 20 퍼센트 싸다.\
  최악은 **10 대 11** 로 거의 같다.\
  이유는 직접 찾기는 mid 가 key 와 같으면 그 자리에서 바로 멈추기 때문이다 — 운이 좋으면 첫 비교에서 끝난다.\
  파생 쪽은 같아도 멈추지 않고 경계까지 좁힌 뒤 한 번 더 확인하므로 항상 log n + 1 근처다.

- Q: 그 이득이 공짜가 아닌 이유는(분기 예측)?\
  A: 같음을 따로 검사하려면 비교 결과를 세 갈래(같다/작다/크다)로 나눠야 한다.\
  분기 예측은 CPU 가 if 의 결과를 미리 찍고 달리는 기능인데, 갈래가 많고 패턴이 없으면 자주 틀려서 느려진다.\
  그래서 비교 횟수로는 이기고 실제 시간으로는 질 수 있다.\
  그리고 CountedArray 계측기는 비교 횟수만 세므로 **이 부분이 안 보인다** — 계측기가 무엇을 못 보는지도 알아야 한다.

> **분기 예측(branch prediction)** — CPU가 if의 결과를 미리 찍고 달리는 기능.\
> 예: 갈래가 많고 패턴이 없으면 자주 틀려서 느려진다.

- Q: 없는 값을 찾을 때 비교를 한 번 더 하는(10 대 11) 이유는?\
  A: 측정치는 있는 값(500) 찾기 비교 10번, 없는 값(1) 찾기 11번이다.\
  구간이 한 칸으로 다 줄어든 뒤에도 "그 자리가 정말 찾는 값인가"를 한 번 더 물어야 하기 때문이다.\
  lowerBound 는 "넣을 자리"를 주는 함수지 "그 값이 있다"를 보장하는 함수가 아니다.\
  그 한 번을 빼먹으면 없는 값을 찾았다고 답한다 — 조용한 오답이다.

#### 3. firstTrue (TODO 4·8)

> **술어(predicate)** — 값 하나를 받아 참/거짓을 돌려주는 조건 함수. "이 자리는 조건을 만족하나?"\
> 예: `i -> i >= 4` 는 인덱스 하나를 받아 4 이상인지 판정한다.

**반열린 판** (impl):

```java
public int firstTrue(int lo, int hi, IntPredicate p) {
    int end = hi + 1;
    while (lo < end) {
        // lo + (end - lo) / 2 로 써야 한다. (lo + end) / 2 는 큰 인덱스에서 넘친다.
        int mid = lo + (end - lo) / 2;
        if (p.test(mid)) {
            end = mid;
        } else {
            lo = mid + 1;
        }
    }
    return lo;
}
```

구조는 lowerBound 와 똑같다 — `a.compareTo(mid, key) < 0` 자리에 `!p.test(mid)` 가 들어갔을 뿐이다.\
(닫힌 판은 `answer = hi + 1` 로 시작해 참이면 `answer = mid; hi = mid - 1`.)

```
처리 과정 : firstTrue(0, 6, i -> i >= 4) — 술어가 F F F F T T T 로 단조

 idx     0    1    2    3    4    5    6
 술어    F    F    F    F    T    T    T
                             ^ 이 자리(4)를 찾는다. 배열은 없다 — 인덱스와 술어뿐.

 [1] end=7, mid=3 : p(3)=F → lo = 4
 [2] mid=5        : p(5)=T → end = 5
 [3] mid=4        : p(4)=T → end = 4
 [4] lo == end == 4 → return 4
```

> **단조(monotonic)** — 거짓...거짓, 참...참처럼 한 번 바뀌면 되돌아오지 않는 성질. 이진 탐색의 전제.\
> 예: 위 그림의 `F F F F T T T` 는 단조지만, 중간에 T 가 다시 F 로 돌아가면 아니다.

```
넘침(오버플로) : int 최대는 약 21.47억 (2,147,483,647)

 mid = (lo + hi) / 2        lo=10억, hi=20억 → 합 30억 > 21.47억 → 음수로 뒤집힘
                            → mid 가 음수 → 엉뚱한 곳을 보거나 무한 루프

 mid = lo + (hi - lo) / 2   차이(10억)는 int 범위 안 → 안전

 SearcherContractTest 가 실제로 이 입력을 준다:
   int lo = 1_000_000_000;  int hi = 2_000_000_000;  threshold = 1_500_000_007
   assertTrue(lo + hi < 0, "이 두 값의 합이 안 넘치면 이 테스트가 의미가 없다");
```

> **오버플로(overflow, 넘침)** — int가 담을 수 있는 최대값(약 21억)을 넘어 음수로 뒤집히는 것.\
> 예: `(lo + hi) / 2` 에서 lo=10억, hi=20억이면 합 30억이 안 담겨 mid 가 음수가 된다.

**질문별 답**

- Q: firstTrue 가 배열을 안 받는다는 것이 왜 중요한가(무엇이 가능해지는가)?\
  A: 탐색 대상이 "메모리에 있는 값들"에서 "인덱스 범위 + 판정 함수"로 넓어진다.\
  메모리에 없는 것(계산으로만 존재하는 값, DB 조회 결과, 시뮬레이션 결과)도 탐색할 수 있다.\
  10억 칸짜리 배열을 만들지 않고도 10억 구간을 좁힐 수 있다.\
  그리고 07번 매개변수 탐색이 이 일반성 위에 선다 — 배열 이분보다 술어 이분이 더 일반적인 형태다.

- Q: lowerBound 의 `a.compareTo(mid, key) < 0` 자리에 firstTrue 에서는 무엇이 들어가는가?\
  A: `!p.test(mid)` 다 — "mid 가 아직 거짓인가".\
  lowerBound 에서 "mid 가 key 보다 작다 = 답이 못 된다"였던 것이 "술어가 거짓이다 = 답이 못 된다"로 바뀐 것뿐이다.\
  거짓이면 `lo = mid + 1`, 참이면(답 후보) 위쪽 끝을 mid 로 줄인다.\
  lowerBound 는 사실 firstTrue 의 특수형이다 — 술어를 "a[i] >= key" 로 놓은 것.

- Q: `hi < Integer.MAX_VALUE` 가 계약인 이유는?\
  A: firstTrue 는 "전부 거짓이면 hi + 1 을 돌려준다"고 약속했다.\
  hi 가 int 최대값이면 hi + 1 자체가 넘쳐서 그 약속을 지킬 수 없다.\
  그래서 호출자가 지켜야 할 입력 조건(계약)으로 못박고 javadoc 에 적어 두었다 — 버그가 아니다.\
  계약은 함수가 지키기로 한 입출력 규칙이고, 어길 입력을 주면 결과는 보장 밖이다.

> **계약(contract)** — 함수가 지키기로 약속한 입출력 규칙.\
> 예: firstTrue의 "전부 거짓이면 hi+1" — 그래서 hi < int 최대값이어야 한다.

- Q: `mid = (lo + hi) / 2` 는 어떤 입력에서 왜 터지고, 어떻게 고치는가?\
  A: lo 와 hi 의 합이 int 최대(약 21.47억)를 넘는 입력 — 테스트는 lo=10억, hi=20억을 준다.\
  합 30억이 int 에 안 담겨 음수로 뒤집히고(넘침), mid 가 음수가 되어 엉뚱한 판정을 한다.\
  고치는 법은 `mid = lo + (hi - lo) / 2` — 차이(hi - lo)는 항상 int 범위 안이라 안전하다.\
  결과값은 두 식이 수학적으로 같다. 넘치느냐만 다르다.

- Q: 02번 병합 정렬의 같은 넘침 결함은 왜 테스트로 못 잡았고, 여기서는 왜 잡히는가?\
  A: 02번에서 넘치려면 원소가 10억 개를 넘는 배열이 필요한데 그런 배열은 만들 수 없었다.\
  변종을 심었더니 68개 테스트가 전부 통과했고, 그래서 주석에만 적어 두었다.\
  여기는 배열이 없다 — firstTrue 는 인덱스 범위만 받으므로 테스트가 lo=10억, hi=20억을 그냥 준다.\
  같은 결함인데 API 모양이 바뀌니 잡을 수 있게 됐다 — "테스트로 못 잡는 것"이 알고리즘이 아니라 인터페이스의 성질일 때가 있다.

- Q: 10억 개짜리 구간을 몇 번 만에 좁히는가, 술어가 비쌀 때 이 횟수는 무엇이 되는가?\
  A: 30번이다 — log2(10억) = 29.9 를 올림한 값이고, 측정 테스트가 정확히 30을 확인한다.\
  배열 탐색에서는 비교가 싸지만 firstTrue 의 술어는 비쌀 수 있다 — DB 조회, 시뮬레이션, 외부 API.\
  그때 "몇 번 부르는가"는 성능 지표가 아니라 **설계 제약**이 된다.\
  호출당 1초면 100만 구간(20번)에 20초짜리 작업이다 — 횟수 자체가 설계를 정한다.

- Q: 07번 매개변수 탐색은 firstTrue 의 무엇 위에 서는가?\
  A: "배열 없이, 단조인 술어의 경계를 찾는다"는 일반성 위에 선다.\
  배열 이분 탐색은 정렬된 데이터에서 자리를 찾고, 술어 이분 탐색은 거짓에서 참으로 바뀌는 자리를 찾는다 — 뒤가 더 일반적이다.\
  매개변수 탐색은 답을 배열에서 찾는 게 아니라 **답 후보를 판정한다** — "답이 x 이하로 가능한가?" 같은 술어를 이분한다.\
  그 술어가 단조이기만 하면 firstTrue 가 그대로 경계(최적 답)를 찾아준다.

### B. 개념

#### 4. 생각해볼 것 (원본 README 이관)

- Q: 균등 분포를 알면 중간 대신 예상 위치를 찍을 수 있다(보간 탐색) — 평균 log log n 인데 왜 안 쓰나?\
  A: 평균 log log n 은 "값이 균등하게 퍼져 있다"는 가정 위의 숫자이기 때문이다.\
  분포가 치우치면(한쪽에 몰린 값, 극단값) 예상 위치가 계속 빗나가 최악 O(n)까지 떨어진다 — 이진 탐색은 분포와 무관하게 log n 을 보장한다.\
  게다가 예상 위치 계산에는 값의 뺄셈·나눗셈이 필요해서 비교만 하면 되는 이진 탐색보다 한 걸음이 비싸고, 정수 아닌 키(문자열 등)에는 "위치를 계산"하는 것 자체가 어렵다.\
  log n 이 이미 충분히 작아서(10억에 30번) 그 위를 더 깎을 동기도 약하다. (원본에 근거 없음 — 내 추론)

- Q: 술어가 단조가 아니면 이진 탐색은 무엇을 돌려주나 — 그것이 "틀린 답"인가 "정의되지 않은 답"인가?\
  A: 어떤 인덱스 하나를 돌려주긴 한다 — 루프는 끝나니까. 하지만 그 값에는 아무 의미가 없다.\
  Searcher 의 javadoc 이 그대로 적고 있다: "그 전제가 깨지면 이진 탐색은 아무 의미가 없는 답을 낸다."\
  "틀린 답"이 아니라 "정의되지 않은 답"이다 — 단조는 계약(전제 조건)이고, 계약을 어긴 입력에 대해서는 맞고 틀림 자체가 정의되지 않는다.\
  더 위험한 건 예외도 안 던진다는 점이다. 조용히 그럴듯한 숫자가 나와서 틀린 줄도 모른다.

- Q: `Arrays.binarySearch` 는 못 찾으면 `-(삽입위치) - 1` 을 돌려준다 — 왜 그렇게 설계했을까?\
  A: 반환값 int 하나에 "찾았다(어디에)"와 "못 찾았다(어디에 넣으면 되는지)"를 둘 다 담기 위해서다.\
  찾으면 0 이상(그 자리), 못 찾으면 음수 — 부호만 보면 성공/실패가 갈린다.\
  그냥 `-삽입위치` 로 하면 삽입 위치가 0일 때 "찾은 자리 0"과 구분이 안 되므로, -1 을 더 빼서 항상 음수로 만든다.\
  호출자는 `-(반환값) - 1` 로 삽입 위치를 복원한다.\
  이 챕터의 언어로 말하면 find 와 lowerBound 를 한 반환값에 욱여넣은 설계다 — 편리하지만 호출부에 복호화 코드가 필요해진다. (원본에 근거 없음 — 내 추론)

#### 5. 파생 질문 (서머리 기반)

```
삽입 위치·개수·구간이 전부 경계 두 개에서 나온다:

    [10, 20, 20, 20, 30, 40, 50], key = 20

    idx    0    1    2    3    4    5    6
         +----+----+----+----+----+----+----+
         | 10 | 20 | 20 | 20 | 30 | 40 | 50 |
         +----+----+----+----+----+----+----+
                ^lower(1)        ^upper(4)

    삽입 위치 : lowerBound = 1  (여기 넣으면 정렬 유지)
    개수      : upper - lower = 4 - 1 = 3
    구간      : [lower, upper) = [1, 4) 가 20 이 있는 자리 전부
    find      : lower 가 범위 안이고 그 자리가 20 이면 1, 아니면 -1
```

**질문별 답**

- Q: 이진 탐색의 본체가 "값 찾기"가 아니라 "경계 찾기"라는 말은 무슨 뜻인가?\
  A: 이 챕터의 네 연산 중 셋(lowerBound, upperBound, firstTrue)이 "조건이 거짓에서 참으로 바뀌는 자리"를 찾는다.\
  값 찾기(find)는 그중 특수한 경우 하나일 뿐이고, 실제로 lowerBound 두 줄로 파생된다.\
  경계만 있으면 삽입 위치·개수 세기·구간 잡기·값 찾기가 전부 나온다 — 반대 방향 파생은 안 된다.\
  firstTrue 까지 가면 배열조차 없어진다 — "정렬된 값"이 아니라 "단조인 술어"가 진짜 전제였음이 드러난다.

- Q: 한 번의 비교로 절반을 통째로 버릴 수 있는 근거는 무엇인가?\
  A: 정렬, 더 일반적으로는 단조성이다.\
  a[mid] < key 라면 정렬 덕분에 mid 왼쪽 전부가 key 보다 작다는 것이 **보지 않고도** 보장된다.\
  그래서 왼쪽 절반을 통째로 버려도 답을 잃지 않는다 — 업다운 게임에서 "업"이 "그 이하 전부 아님"을 뜻하는 것과 같다.\
  이 보장이 깨지면(정렬 안 됨, 술어 비단조) 버린 절반에 답이 있을 수 있고, 그 순간 알고리즘 전체가 무너진다.

- Q: 정렬 전제를 함수 안에서 확인하지 않는 이유는?\
  A: 확인하려면 배열 전체를 한 번 봐야 해서 O(n) 이다.\
  log n 번 보려고 만든 알고리즘 앞에 n 번짜리 검사를 붙이면 배보다 배꼽이 커진다.\
  그래서 CountedArray 의 javadoc 대로 "정렬은 호출자의 책임"으로 계약에 넘긴다.\
  빠른 알고리즘의 전제 조건은 대개 이렇게 계약으로 넘어간다 — 대신 어기면 조용히 틀린다는 비용이 따라온다.

- Q: 원소를 1000배 늘리면 비교 횟수는 몇 배 느는가, 선형 탐색과의 격차는?\
  A: 2배만 는다 — 측정으로 n=1,000 에 10번, n=1,000,000 에 20번이다.\
  log2(1,000) = 9.97, log2(1,000,000) = 19.93 — 올림하면 측정치와 딱 맞는다.\
  선형 탐색이었다면 100만 개에서 평균 50만 번 — **2만 5천 배** 차이다.\
  "데이터가 늘면 느려진다"가 로그에서는 거의 성립하지 않는다.

> **O(log n)** (빅오 표기) — n을 반으로 쪼개는 횟수만큼 걸린다는 뜻.\
> 예: 100만 개면 약 20번, 10억 개면 약 30번.

- Q: 정렬이 깨진 배열을 넣으면 어떤 일이 생기는가 — 예외인가 조용한 오답인가?\
  A: 조용한 오답이다.\
  예외는 나지 않는다.\
  루프는 정상적으로 끝나고 그럴듯한 인덱스가 나오지만, 버린 절반에 답이 있었을 수 있어 의미가 없다.\
  CountedArray 는 정렬 여부를 확인하지 않으므로(호출자 책임) 어디서도 걸러지지 않는다.\
  이런 실패가 제일 위험하다 — 틀렸다는 신호가 없어서 틀린 값이 그대로 다음 계산에 들어간다.

- Q: 삽입 위치·개수 세기·구간 잡기가 전부 lowerBound/upperBound 에서 나온다는 것을 예로 설명하면?\
  A: 위 그림의 `[10, 20, 20, 20, 30, 40, 50]`, key=20 으로: lowerBound=1, upperBound=4.\
  삽입 위치 — lowerBound(20)=1 에 넣으면 정렬이 유지된다.\
  key 가 없어도 성립한다(25라면 lowerBound=4).\
  개수 — upperBound - lowerBound = 4 - 1 = 3. 없으면 두 경계가 같아 0.\
  구간 — `[1, 4)` 가 20 이 차지한 자리 전부다. 경계 두 개면 세 가지 일이 전부 끝난다.

- Q: 연결 리스트에서 이진 탐색이 무의미한 이유는?\
  A: 가운데(mid)로 가는 비용이 O(1)이 아니기 때문이다.\
  연결 리스트는 인덱스 접근이 안 되고, i 번째에 가려면 처음부터 i 번 따라가야 한다 — O(n).\
  비교 횟수는 log n 으로 줄어도 매 라운드 mid 까지 걸어가는 비용이 쌓여 전체가 O(n)이 된다 — 그냥 순서대로 보는 것과 같다.\
  이진 탐색의 이득은 "절반 버리기 + 가운데로 점프가 공짜"의 곱이다. 점프가 비싸면 이득이 사라진다. (원본에 근거 없음 — 내 추론)

- Q: git bisect 가 이진 탐색인 이유를 firstTrue 의 언어로 설명하면?\
  A: 커밋 나열을 인덱스 구간으로, "이 커밋에 버그가 있는가"를 술어 p 로 놓으면 정확히 firstTrue(첫 정상 커밋 ~ 현재, p)다.\
  버그가 한 번 들어온 뒤 안 고쳐졌다면 술어는 거짓...거짓, 참...참으로 단조다 — firstTrue 의 전제가 성립한다.\
  bisect 는 가운데 커밋을 체크아웃해 시험(술어 호출)하고 절반을 버리기를 반복해, 1000개 커밋도 약 10번 시험으로 "버그가 처음 생긴 커밋(경계)"을 찾는다.\
  술어(빌드+테스트)가 비싸므로 "몇 번 시험하는가"가 곧 비용이라는 점까지 firstTrue 와 같다 — 그리고 중간에 버그가 고쳐졌다 재발했다면(비단조) 엉뚱한 커밋을 지목한다.
