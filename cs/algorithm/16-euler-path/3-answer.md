#### 1. `EulerPath.exists` (TODO 1)

impl 정답의 뼈대:

```java
public static boolean exists(CountedGraph g) {
    if (g.edgeCount() == 0) {
        return true;
    }
    return degreesAllow(g) && edgesAreConnected(g);
}

// degreesAllow — 방향 그래프면 정점마다
int diff = g.degree(v) - g.inDegree(v);   // 나간 수 - 들어온 수
if (diff == 1) startLike++;
else if (diff == -1) endLike++;
else if (diff != 0) return false;
// 회로면 둘 다 0, 경로면 시작 하나 끝 하나.
return (startLike == 0 && endLike == 0) || (startLike == 1 && endLike == 1);

// 무방향이면 홀수 차수 정점 수를 세어
return odd == 0 || odd == 2;
```

- Q: 무방향 그래프에서 홀수 차수 정점이 0개 또는 2개여야만 하는 이유는 무엇인가?\
  A: 시작점·끝점이 아닌 정점은 "들어간 만큼 나가야" 하므로 간선이 짝으로 소모된다 — 차수가 짝수여야 한다.\
  홀수 차수 정점은 들어왔는데 못 나가는 순간이 한 번 생기므로 시작점 또는 끝점만 될 수 있다.\
  시작점과 끝점은 둘뿐이니 홀수 차수 정점은 최대 2개(경로), 시작=끝이면 0개(회로)다.

> **차수(degree)** — 한 정점에 붙은 간선의 개수. 방향 그래프에서는 나가는 차수(out)와 들어오는 차수(in)를 따로 센다.\
> 예: 삼각형의 정점들은 저마다 간선 2개가 붙어 있으니 차수가 2(짝수)다.

- Q: 홀수 차수 정점이 정확히 1개인 무방향 그래프가 존재할 수 있는가?\
  A: 없다.\
  모든 정점의 차수 합 = 간선 수 x 2 로 항상 짝수다(간선 하나가 양끝 차수를 1씩 올리므로).\
  홀수 차수 정점이 홀수 개면 차수 합이 홀수가 되어 모순이다.\
  그래서 홀수 차수 정점 수는 항상 짝수 — 0, 2, 4, ... 만 가능하다. (원본에 근거 없음 — 내 추론, 표준 정리)

- Q: 방향 그래프에서는 정점마다 무엇을 세어 판정하는가?\
  A: `나간 수 - 들어온 수`(`g.degree(v) - g.inDegree(v)`)를 본다.\
  +1인 정점은 시작점 후보(startLike), -1인 정점은 끝점 후보(endLike)로 세고,\
  그 외의 값(±2 이상)이 하나라도 나오면 즉시 false다.

- Q: 회로일 때와 경로일 때 `나간 수 - 들어온 수`의 전체 모양은 각각 어떤가?\
  A: 회로면 모든 정점이 0 — `startLike == 0 && endLike == 0`.\
  경로면 +1이 정확히 하나(시작), -1이 정확히 하나(끝)이고 나머지는 전부 0 — `startLike == 1 && endLike == 1`.\
  impl은 이 둘 중 하나면 통과시킨다.

> **오일러 회로(Euler circuit)** — 모든 간선을 정확히 한 번씩 지나되 시작점과 끝점이 같은 오일러 경로.\
> 예: 무방향에서 홀수 차수 정점이 0개면 회로, 2개면 시작과 끝이 다른 경로다.

- Q: 차수 조건만 보면 어떤 그래프에 속는가?\
  A: 떨어진 삼각형 두 개.\
  여섯 정점 전부 차수 2(짝수)라 차수 조건은 통과한다.\
  그런데 두 덩어리 사이에 간선이 없어 연필을 공중으로 들어야 하니 한붓그리기가 안 된다.\
  그래서 `edgesAreConnected` — 간선이 붙은 정점들이 한 덩어리인지 — 를 반드시 같이 본다.

- Q: 연결 검사에서 고립된 정점(차수 0)을 빼야 하는 이유는 무엇인가?\
  A: 간선이 없는 정점은 한붓그리기와 무관하기 때문이다 — 지나갈 선 자체가 없다.\
  포함시키면 "삼각형 하나 + 고립 정점 하나" 같은 멀쩡한 그래프를 불가능이라고 잘못 답한다.\
  impl은 DFS 후 `g.degree(v) > 0 && !seen[v]` — 간선 붙은 정점만 도달 여부를 검사한다.

> **고립 정점(isolated vertex)** — 간선이 하나도 안 붙은 정점. 연결 검사와 시작점 선택에서 제외한다.\
> 예: "삼각형 하나 + 고립 정점 하나"는 멀쩡히 한붓그리기가 되는 그래프인데, 고립 정점을 연결 검사에 넣으면 불가능이라고 잘못 답한다.

> **DFS(깊이 우선 탐색)** — 갈 수 있는 데까지 들어갔다가 막히면 되돌아 나오는 탐색 방법.\
> 예: 연결 검사는 간선이 붙은 정점 전부에 닿는지를 이 DFS로 확인한다.

- Q: 간선이 하나도 없는 그래프에는 무엇을 답해야 하는가?\
  A: true다.\
  impl 첫 줄이 `if (g.edgeCount() == 0) return true;`.\
  지나야 할 간선이 0개면 "모든 간선을 한 번씩"이라는 조건이 공허하게 참(비어 있으니 어길 수 없다)이다.\
  단 `findTrail`은 이 경우 빈 목록을 준다 — 지나갈 것이 없으니 경로도 없다.

- Q: `inDegree(v)`를 판정 루프 안에서 정점마다 부르면 비용이 어떻게 되고, 측정은 그것을 어떤 숫자로 보여줬는가?\
  A: `inDegree(v)`는 한 번 부를 때 모든 인접 리스트를 훑는다 — 정점마다 부르면 O(VE)다.\
  정점 200개 사이클에서 무방향 판정은 호 조회 400회, 방향 판정은 40,200회 — 100배다.\
  미리 한 번만 세어 배열에 담으면 없어지는 비용이다.\
  둘 다 "O(V+E) 판정"이라 부르니 계측기 없이는 이 차이가 안 보인다.

> **O(V+E), O(VE)** (빅오 표기) — 일의 양이 정점 수(V)·간선 수(E)에 얼마나 비례하는지 나타내는 표기.\
> 예: 같은 판정이라도 `inDegree(v)`를 정점마다 새로 세면 O(VE)로 튀어 호 조회가 400회에서 40,200회가 된다.

- Q: "될까?"만 판정하는 데도 O(E)가 드는 이유는 무엇인가?\
  A: 연결 조건 때문이다.\
  연결 검사는 간선이 붙은 정점 전부에 닿는지 DFS로 확인해야 하니 양쪽 호를 다 본다.\
  측정: 정점 1,000 사이클에서 `exists()`만 불러도 호 조회 2,000회(경로까지 찾으면 6,000회).\
  "될까?"를 차수만으로 싸게 답할 방법은 없다 — README가 기록해놓은 결론이다.

#### 2. `EulerPath.startVertex` (TODO 2)

static int startVertex(CountedGraph g) {
    // 방향: 나간 수가 하나 많은 정점 / 무방향: 홀수 차수 정점을 먼저 찾고

    for (int v = 0; v < n; v++) {

            return v;
        }
    }
    return 0;

- Q: 경로일 때는 왜 반드시 홀수 차수 정점에서 시작해야 하는가?\
  A: 홀수 차수 정점은 "나가는 횟수와 들어오는 횟수가 안 맞는" 정점이라 경로의 양 끝일 수밖에 없다.\
  중간 정점에서 시작하면 시작점에서 간선 하나가 홀로 남아 어딘가 중간에서 막힌다 — 모든 간선을 못 쓴다.\
  방향 그래프면 나간 수가 하나 많은(diff == +1) 정점이 시작점이다.

- Q: 회로에서 "아무 데나"로 0번을 골랐는데 0번이 고립되어 있으면 무슨 일이 생기는가?\
  A: 시작하자마자 안 쓴 간선이 0개라 바로 막히고, 답은 `[0]` 한 칸짜리가 된다.\
  간선 E개를 하나도 못 지났으니 완전히 틀린 답이다.\
  그래서 impl은 회로에서도 `g.degree(v) > 0`인 첫 정점을 고른다 — "아무 데나"에는 "간선이 붙은"이라는 단서가 붙는다.

- Q: 이 함수를 망가뜨린 변종이 계약 테스트에서 처음에 안 잡힌 이유는 무엇인가?\
  A: 계약 테스트의 그래프에서 0번이 마침 홀수 차수였거나 간선이 붙어 있었기 때문이다.\
  `startVertex`가 무조건 0을 돌려주는 변종도 그 그래프들에서는 우연히 정답 시작점을 돌려준다.\
  "0번부터 그리기 시작하는 습관이 그대로 테스트의 사각지대가 된다" — 테스트 데이터를 편하게 만들면 검증력을 잃는다(15번과 같은 종류).

- Q: 그것을 잡으려고 추가한 테스트 그래프 두 개는 각각 어떤 모양인가?\
  A: 하나는 0번이 짝수 차수인 그래프(삼각형 + 1번에 달린 꼬리) — 경로의 시작은 홀수 차수인 1번 쪽이어야 한다.\
  다른 하나는 0번이 고립되어 있고 회로는 다른 데 있는 그래프 — 0에서 시작하면 즉시 막힌다.\
  둘 다 "0번이 우연히 맞는 시작점"이라는 조건을 깨뜨리는 그래프다.

#### 3. `EulerPath.findTrail` — 히어홀저 (TODO 3~6)

> **히어홀저(Hierholzer) 알고리즘** — 막히면 그 정점을 답에 확정하고 물러나는 방식으로 오일러 경로를 O(E)에 찾는 알고리즘.\
> 예: 막힌 정점을 `trail`에 넣고 한 칸 물러난 뒤, 그 자리에 안 쓴 간선이 있으면 거기서 다시 내려간다.

```java
boolean[] usedEdge = new boolean[g.edgeCount()];
int[] cursor = new int[n];      // 정점마다 "다음에 볼 호"의 위치

stack.push(startVertex(g));
while (!stack.isEmpty()) {
    int v = stack.peek();
    while (cursor[v] < g.degree(v) && usedEdge[g.arc(v, cursor[v]).id()]) {
        cursor[v]++;            // 안 쓴 호를 찾을 때까지 커서를 민다
    }
    if (cursor[v] == g.degree(v)) {
        trail.add(stack.pop()); // 막혔다. 되돌리지 않고 답에 넣은 뒤 물러난다
        continue;
    }
    CountedGraph.Arc a = g.arc(v, cursor[v]);
    usedEdge[a.id()] = true;
    stack.push(a.to());
}
Collections.reverse(trail);
```

- Q: "썼다" 표시의 대상은 정점인가 간선인가, 왜 그쪽인가?\
  A: 간선이다 — `boolean[] usedEdge = new boolean[g.edgeCount()]`.\
  오일러 경로의 규칙이 "간선을 한 번씩"이지 정점이 아니기 때문이다.\
  정점은 여러 번 지나도 된다.\
  정점에 방문 표시를 하면 두 삼각형이 만나는 정점 2 같은 곳을 두 번째로 못 지나가 경로가 끊긴다.

- Q: 간선을 정점 쌍으로 기억하면 중복 간선(다중 그래프)에서 무엇이 잘못되는가?\
  A: 같은 두 정점 사이에 간선이 여러 개면 "(1,2)를 썼다"는 표시가 그중 어느 것인지 구분을 못 한다.\
  하나만 썼는데 전부 쓴 것으로 치거나, 엉뚱한 것을 지운다.\
  그래서 `CountedGraph.Arc`가 간선마다 고유 번호 `id`를 들고 있고, 표시는 `usedEdge[a.id()]`로 한다.

> **다중 그래프(multigraph)** — 같은 두 정점 사이에 간선이 여러 개 있을 수 있는 그래프.\
> 예: "(1,2)를 썼다"는 표시로는 그중 어느 간선인지 구분이 안 되므로, 간선을 정점 쌍이 아니라 고유 번호(id)로 구분한다.

- Q: 무방향 간선은 양쪽 인접 리스트에 저장되는데, 한쪽만 표시하는 실수를 `Arc`의 id는 어떻게 막는가?\
  A: 한 간선의 양쪽 호(arc)가 **같은 id를 공유**한다.\
  `usedEdge[id] = true` 한 번이면 어느 방향에서 봐도 "쓴 간선"으로 걸러진다.\
  정점 쌍이나 호 단위로 표시했다면 반대쪽 호가 남아 같은 간선을 두 번 지나게 된다.

- Q: 막혔을 때 보통의 백트래킹과 히어홀저는 각각 무엇을 하는가?\
  A: 보통의 백트래킹(13번)은 마지막 선택을 취소하고 다른 간선을 다시 시도한다 — 지수적 재시도가 생길 수 있다.\
  히어홀저는 안 물린다: 막힌 정점을 `trail`에 넣고(`trail.add(stack.pop())`) 한 칸 물러날 뿐이다.\
  물러난 자리에 안 쓴 간선이 있으면 거기서 다시 내려간다.\
  간선마다 한 번씩만 건드리므로 O(E)다.

> **백트래킹(backtracking)** — 막히면 마지막 선택을 취소하고 다른 선택을 시도하는 방식. 히어홀저는 이걸 **안 한다**.\
> 예: 백트래킹은 막힌 간선을 물리고 다른 간선을 다시 시도해 지수적 재시도가 생길 수 있지만, 히어홀저는 막힌 정점을 답에 확정하고 물러날 뿐이다.

- Q: 막힌 정점을 답에 넣고 물러난 뒤 다시 내려가서 생긴 조각은 답의 어디에 끼워지는가?\
  A: 물러나던 정점(우회로의 분기점) 자리에 자연스럽게 끼워진다.\
  trail은 "간선을 다 쓴 정점"부터 확정되므로, 분기점에서 새로 돈 사이클이 먼저 답에 쌓이고 그다음 분기점이 쌓인다.\
  서머리 예시: 0→1→2→0에서 막힌 뒤 2에서 2→3→4→2를 다시 돌면 trail은 [0,2,4,3,2,1,0] — 뒤집으면 0→1→**2→3→4→2**→0으로 우회로가 2 자리에 삽입된 모양이 된다.

- Q: 히어홀저가 선택을 물리지 않아도 정답이 되는 근거는 무엇인가?\
  A: 차수 조건이 맞으면 어느 정점이든 들어간 횟수와 나온 횟수가 맞아떨어진다(impl javadoc).\
  그래서 어떤 순서로 내려가든 막히는 곳은 시작점(회로) 또는 끝점(경로)뿐이다.\
  잘못된 선택이란 게 없고, 남은 간선은 물러나는 길에 반드시 다시 만나 소진된다 — 그래서 되돌릴 필요가 없다.

- Q: 시작점·끝점이 아닌 중간 정점에서는 막히는 일이 없는 이유는 무엇인가?\
  A: 중간 정점은 차수가 짝수(방향이면 in == out)라 들어올 때마다 나갈 간선이 하나 남아 있다.\
  중간에서 막혔다면 그 정점의 차수가 홀수라는 뜻인데, 그런 그래프는 `exists`의 차수 조건에서 이미 걸렀다.\
  판정과 탐색이 한 세트인 이유다.

- Q: 이미 지나간 호를 매번 처음부터 훑으면 전체 비용이 어떻게 되는가?\
  A: O(E²)가 된다.\
  정점에 돌아올 때마다 그 정점의 호 목록을 0번부터 다시 훑으면,\
  쓴 호들을 매번 반복해서 건너뛰는 비용이 누적된다.\
  E가 2,000이면 400만 번 수준 — 알고리즘은 그대로인데 조회만으로 제곱이 된다.

> **커서(cursor)** — 정점마다 "다음에 볼 간선 위치"를 기억해, 이미 쓴 간선을 다시 훑지 않게 하는 장치.\
> 예: `cursor[v]`를 밀어 안 쓴 호를 찾으므로, 정점에 다시 돌아와도 0번부터 훑지 않는다.

- Q: 정점별 커서의 유무를 측정은 어떤 숫자로 보여줬는가?\
  A: 자기 간선(self loop 포함 간선) 2,000개(인접 리스트 4,000)짜리 그래프에서\
  커서 있음 = 호 조회 12,000회, 커서 없음(추정) = 8,000,000회 — **660배**다.\
  결과는 완전히 같다.\
  계측기가 없으면 이 차이는 안 보인다.

- Q: 끝난 뒤 답을 왜 뒤집는가?\
  A: trail에는 막다른 골목(간선을 다 쓴 정점)부터 쌓이기 때문이다.\
  회로면 시작점이, 경로면 끝점이 가장 먼저 들어가고 시작점이 마지막에 들어간다.\
  `Collections.reverse(trail)` 한 번으로 시작점→끝점 순서가 된다.

- Q: 결과 정점 수가 간선 수 + 1인 이유는 무엇인가?\
  A: 간선 하나를 지날 때마다 정점이 하나씩 추가되는데, 시작점은 간선 없이 먼저 세기 때문이다.\
  간선 E개 = 이동 E번 = 정점 E+1개.\
  impl javadoc: "간선이 E 개면 정점이 E+1 개 나온다. 시작점부터 세기 때문이다."

- Q: `useEdge()` 호출 수와 결과 길이를 따로 세는 이유는 무엇인가?\
  A: 결과 길이만 보면 "하나를 두 번 쓰고 하나를 안 썼다" 같은 **상쇄**를 놓친다 — 길이는 그대로 E+1이 나온다.\
  `useEdge()` 호출 수 == 간선 수, 결과 길이 == 간선 수 + 1을 **따로** 확인하면\
  "정확히 한 번씩"이라는 계약 자체를 검증하게 된다.

### B. 개념

#### 4. 원본 README "생각해볼 것" (이관)

- Q: 홀수 차수 정점이 4개면 간선을 몇 개 더해야 한 붓 그리기가 되는가(중국인 우편배달부 문제)?\
  A: 간선 하나를 더하면 양끝 정점의 차수가 1씩 바뀐다 — 홀수 정점 둘을 이으면 둘 다 짝수가 된다.\
  홀수 4개면: 두 쌍으로 짝지어 간선 2개를 더하면 회로가 되고, 한 쌍만 이어 1개를 더하면 홀수 2개가 남아 경로가 된다.\
  실제 우편배달부 문제는 새 길을 못 놓고 기존 길을 **다시 걷는** 것이므로, 홀수 정점들을 짝지을 때 쌍 사이 최단 경로 길이의 합이 최소가 되는 짝짓기를 찾아 그 경로의 간선들을 복제한다. (원본에 근거 없음 — 내 추론, 표준 이론)

> **중국인 우편배달부 문제** — 모든 길을 최소 비용으로 다 도는 경로 찾기. 홀수 차수 정점이 4개 이상일 때 간선을 덧대어 오일러 회로로 만드는 문제다.\
> 예: 홀수 차수 정점이 4개면 두 쌍으로 짝지어 간선 2개를 더하면 회로가 된다.

- Q: 방향 그래프의 연결성 검사를 왜 방향을 무시하고 하는가, 강연결이어야 하는 것 아닌가?\
  A: 강연결은 필요 조건이 아니다 — 경로(회로 아님)가 있는 그래프는 끝점에서 시작점으로 돌아갈 수 없어 애초에 강연결이 아니다.\
  방향 오일러 정리의 조건이 "차수 균형 + 간선 있는 정점들의 약연결(방향 무시 연결)"이다: 차수가 균형이면 방향 무시로 이어진 덩어리 안에서 간선이 실제로 순환/관통할 수밖에 없다.\
  강연결 검사는 역방향 DFS까지 필요해 더 비싸기도 하다.\
  impl `edgesAreConnected`가 양방향 인접 리스트를 만들어 검사하는 이유다. (근거: impl 주석 "방향은 무시하고 본다" + 내 추론)

- Q: 히어홀저를 재귀로 쓰면 어디가 위험한가?\
  A: 재귀 깊이가 경로 길이만큼 — 최악 E까지 — 자란다.\
  간선 수십만 개짜리 사이클이면 JVM 콜 스택이 터진다(StackOverflowError).\
  12번 DFS에서 깊이를 측정해 확인한 것과 같은 위험이다.\
  그래서 impl은 `ArrayDeque`를 명시적 스택으로 쓴다 — 힙에 쌓이므로 깊이 한계가 사실상 없다.

- Q: 해밀턴 경로는 왜 이렇게 못 푸는가, 오일러와 무엇이 다른가?\
  A: 오일러는 "가능한가"가 차수·연결이라는 **국소적으로 셀 수 있는 조건**으로 완전히 환원되고, 그 조건이 맞으면 어떤 탐욕적 선택도 실패하지 않는다(히어홀저가 안 물리는 근거).\
  해밀턴(모든 **정점**을 한 번씩)에는 그런 판정 조건이 알려져 있지 않다 — 지금의 선택이 한참 뒤의 성공/실패를 좌우해 사실상 전부 시도해봐야 하고, NP-완전이다.\
  같아 보이는 문제라도 "무엇을 한 번씩 지나느냐"가 난이도를 하늘과 땅으로 가른다. (원본에 근거 없음 — 내 추론, 표준 이론)

> **해밀턴 경로(Hamiltonian path)** — 모든 **정점**을 정확히 한 번씩 지나는 길.\
> 예: 간선을 한 번씩 지나는 오일러 경로는 O(E)로 풀리지만, 한 글자 차이인 이 문제는 사실상 전부 시도해봐야 한다.

> **NP 난해(NP-hard)** — 입력이 커지면 현실적인 시간 안에 정확히 풀 방법이 알려져 있지 않은 문제 부류.\
> 예: 해밀턴 경로에는 차수·연결 같은 판정 조건이 알려져 있지 않고, NP-완전이다.

#### 5. 파생 질문 (서머리 기반)

- Q: 오일러 경로와 오일러 회로의 차이는 무엇이고, 판정 조건은 어디서 갈리는가?\
  A: 회로는 시작점 == 끝점인 경로다.\
  무방향: 홀수 차수 0개면 회로, 2개면 경로.\
  방향: diff 전부 0이면 회로, +1/-1 한 쌍이면 경로.\
  impl `exists`는 둘 다 "있다"로 답한다 — javadoc "회로도 경로에 포함한다".

- Q: 홀수 차수 정점은 왜 시작점 또는 끝점만 될 수 있는가?\
  A: 중간 정점은 지나갈 때마다 간선을 (들어옴, 나감) 짝으로 소모한다 — 소모량이 항상 짝수다.\
  차수가 홀수면 마지막에 간선 하나가 홀로 남아 "들어왔는데 못 나가는" 순간이 생긴다.\
  그 순간이 허용되는 자리는 여정을 시작하는 곳(나가기만 1회 초과)과 끝내는 곳(들어오기만 1회 초과)뿐이다.

- Q: 같은 DFS 기반인데 12번 DFS의 방문 표시와 히어홀저의 사용 표시는 대상이 어떻게 다른가?\
  A: 12번 DFS는 **정점**에 방문 표시를 한다 — 목적이 "모든 정점을 한 번씩 방문"이므로.\
  히어홀저는 **간선**에 사용 표시를 한다 — 목적이 "모든 간선을 한 번씩 통과"이므로 정점은 몇 번이고 다시 밟는다.\
  표시 대상은 알고리즘의 편의가 아니라 문제의 정의("무엇을 한 번씩")에서 나온다.

- Q: 겉보기에 비슷한 두 문제의 난이도가 갈리는 데서 무엇을 배울 수 있는가?\
  A: 문제의 난이도는 문장의 겉모양이 아니라 구조에서 나온다 — "정점 한 번씩"과 "간선 한 번씩"은 한 글자 차이인데 NP 난해와 O(E)다.\
  실무에서 요구사항을 어느 쪽 문제로 모델링하느냐가 풀 수 있냐 없냐를 가른다.\
  낯선 문제를 만나면 "이게 아는 쉬운 문제로 환원되는가"부터 확인할 가치가 있다. (내 추론)

- Q: 판정(`exists`)을 생략하고 `findTrail`만 돌리면 조건이 안 되는 그래프에서 어떤 잘못된 결과가 나오는가?\
  A: 루프는 정상 종료하지만 답이 계약을 어긴다 — 홀수 차수가 4개면 중간에 막혀 일부 간선을 못 쓴 채 끝나고, 끊어진 그래프면 시작 덩어리의 간선만 지난 목록이 나온다.\
  즉 예외 없이 "그럴듯한" 목록이 나오는 조용한 실패(silent failure)다.\
  길이가 E+1이 아님을 검사해야 잡힌다.\
  그래서 impl `findTrail` 첫 줄이 `if (!exists(g)) return List.of();` — 불가능이면 빈 목록으로 명시적으로 답한다.

> **조용한 실패(silent failure)** — 프로그램이 에러를 내지 않고 정상처럼 끝나는데, 결과만 틀린 것.\
> 예: 판정을 건너뛰고 `findTrail`만 돌리면 예외 없이 목록이 나오지만, 그 목록은 일부 간선을 빠뜨린 채 끝난 것이다.

- Q: 커서 최적화가 "계측기 없이는 안 보인다"는 말은 무슨 뜻인가?\
  A: 커서가 있든 없든 **결과는 완전히 같다** — 정답 비교 테스트로는 차이가 0이다.\
  차이는 호 조회 횟수(12,000 vs 8,000,000)라는 내부 비용에만 있고, 작은 입력에서는 시간으로도 체감이 안 된다.\
  `CountedGraph`가 조회 횟수를 세기 때문에 이 차이를 테스트로 기록해놓을 수 있다 — "같은 O 표기"의 함정을 숫자로 잡는 이 문제집의 방식이다.
