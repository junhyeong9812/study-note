### A. 문제 (src/main 의 TODO 1~4)

#### 1. 좌표 압축 (`Compress` — TODO 1~2)

**정답 코드 (impl 기준, 핵심부)**

```java
/** 정렬하고 중복을 없앤 값들. 이것이 등수 표다. */
public static int[] distinctSorted(int[] values, CountedSweep sweep) {
    int[] sorted = values.clone();          // 입력을 안 건드린다
    Arrays.sort(sorted);
    int size = 0;
    for (int i = 0; i < sorted.length; i++) {
        sweep.compare();
        if (i == 0 || sorted[i] != sorted[i - 1]) {
            sorted[size++] = sorted[i];     // 같은 배열 앞쪽에 눌러 담는다
        }
    }
    return Arrays.copyOf(sorted, size);
}

/** 값의 등수. 표에 없으면 -1. */
public static int rankOf(int[] table, int value, CountedSweep sweep) {
    int lo = 0;
    int hi = table.length - 1;
    while (lo <= hi) {
        sweep.compare();
        int mid = lo + (hi - lo) / 2;       // (lo+hi)/2 가 아니라 오버플로 안전한 형태
        if (table[mid] == value) {
            return mid;
        }
        if (table[mid] < value) {
            lo = mid + 1;
        } else {
            hi = mid - 1;
        }
    }
    return -1;
}
```

```
원래 값   10   1,000,000,000   10   50        범위 10 억 -> 배열을 못 만든다

[1] 정렬 + 중복 제거   [10, 50, 1000000000]    <- 등수 표
[2] 각 값을 등수로      10 -> 0,  50 -> 1,  1000000000 -> 2

압축된 값  [0, 2, 0, 1]        배열 크기가 10 억에서 3 으로
```

**질문별 답**

- Q: 좌표 압축이 하는 일을 한 문장으로 말하면 무엇인가?
  A: **값을 그 값의 등수로 바꿔치기해, 배열 크기를 값의 "범위"에서 값의 "개수"로 줄이는 일**이다.
  10, 10억, 10, 50 → 0, 2, 0, 1 이 되면 필요한 배열이 10억 칸에서 3 칸이 된다.
  README 의 표현으로는 "좌표를 훑기"를 "이벤트를 훑기"로 바꾸는 준비 작업이다.
  값 자체가 아니라 **값 사이의 순서만** 옮겨 담는 변환이다.

- Q: 압축이 가능한 조건은 무엇인가 — 어떤 문제에서는 쓰면 안 되는가?
  A: **값이 무엇인지는 중요하지 않고 순서만 중요할 때**만 쓸 수 있다(impl javadoc).
  쓰면 안 되는 문제: 구간의 **길이·넓이·거리·합**이 답에 들어가는 문제 — 등수는 그 정보를 버린다.
  예: "가장 오래 겹친 시간이 몇 분인가"는 압축 후 등수로 계산하면 틀린다. "동시에 최대 몇 개가 겹치나"는 순서만 필요해서 괜찮다.
  판별 요령: 답을 구하는 식에 뺄셈이 들어가면 의심한다.

- Q: 입력 배열을 `clone()` 해서 정렬하는 이유는?
  A: 부르는 쪽의 배열을 말없이 바꿔 놓지 않기 위해서다.
  `Arrays.sort(values)` 를 그대로 하면 호출자가 넘긴 배열의 순서가 바뀌는데, 이것은 함수 이름만 봐서는 알 수 없는 **부작용**이다.
  원래 순서가 의미를 갖는 경우(각 원소의 등수를 원래 자리에 다시 써야 할 때)에는 그 부작용이 바로 버그가 된다.
  "질의 함수는 입력을 바꾸지 않는다"는 계약을 코드로 지킨 것.

- Q: 중복 제거를 새 배열이 아니라 같은 배열의 앞쪽에 눌러 담는 방식은 무엇을 아끼는가?
  A: **추가 배열 하나**(메모리 O(n))와 그 복사 비용을 아낀다.
  `size` 라는 쓰기 포인터와 `i` 라는 읽기 포인터가 같은 배열 위를 가는 08번 투 포인터의 모양이다.
  쓰기 포인터가 읽기 포인터를 절대 앞지르지 않으므로 아직 안 읽은 값을 덮어쓸 위험이 없다 — 이것이 이 기법의 안전 조건이다.
  마지막에 `Arrays.copyOf(sorted, size)` 로 뒤쪽 쓰레기를 잘라낸다.

- Q: 등수를 이분 탐색으로 찾을 수 있는 전제는 무엇인가?
  A: **표가 정렬되어 있을 것** 하나다(impl javadoc 이 명시).
  `distinctSorted` 가 정렬된 표를 돌려주므로 전제가 자동으로 만족되지만, 다른 경로로 만든 표를 넘기면 조용히 틀린 등수를 준다.
  이런 "전제가 깨지면 예외가 아니라 오답"인 함수는 전제를 문서에 적어 두는 것이 계약의 일부다.
  비용은 O(log n) — 표가 2,000개여도 11번쯤 비교한다.

- Q: 표에 없는 값에 대해 `rankOf` 가 -1 을 주는 것과, 들어갈 자리(하한)를 주는 것은 어떻게 다른 계약인가?
  A: -1 은 "그 값은 표에 없다"는 **존재 여부**만 알려주고, 하한(lower bound)은 "있었다면 여기였다"는 **위치**까지 알려준다.
  압축의 용도(표에 있는 값을 인덱스로 바꾸기)에는 -1 로 충분하다 — 표는 등장한 값 전부로 만들었으니 못 찾으면 입력 오류다.
  반면 "이 값 이하가 몇 개인가" 같은 질의를 하려면 하한이 필요하다.
  impl 은 -1 계약을 택했고, javadoc 에 그렇게 적어 뒀다 — 어느 쪽이 맞고 틀린 게 아니라 **용도가 계약을 정한다**.

- Q: 압축한 값으로 차이나 합을 계산하면 왜 안 되는가? (원본 함정)
  A: 등수는 **순서만 보존**하고 값 사이의 거리는 보존하지 않기 때문이다.
  10 → 0, 50 → 1, 10억 → 2 로 바뀌면 "0 과 1 사이"와 "1 과 2 사이"가 같아 보이지만 실제 거리는 40 과 약 10억이다.
  그래서 압축 좌표에서 길이·넓이·합을 구하면 완전히 다른 값이 나온다.
  필요하면 등수 표를 들고 있다가 **계산 직전에 원래 값으로 되돌려서** 계산해야 한다.

- Q: 10 과 50 의 "거리 40"은 압축 후 어디로 갔는가?
  A: **사라졌다** — 압축된 배열 어디에도 없다.
  남아 있는 곳은 등수 표(`[10, 50, 1000000000]`) 하나뿐이라, 거리가 필요하면 `table[1] - table[0]` 으로 표를 다시 봐야 한다.
  즉 압축은 정보를 버리는 변환이고, 버린 정보는 표에만 남는다.
  "표를 같이 들고 다녀야 한다"는 것이 좌표 압축을 쓸 때의 숨은 비용이다.

#### 2. 최대 겹침 (`Sweep.maxOverlap` — TODO 3)

**정답 코드 (impl 기준, 핵심부)**

```java
public static int maxOverlap(List<Interval> intervals, boolean closedEnd, CountedSweep sweep) {
    if (intervals.isEmpty()) {
        return 0;
    }
    // {좌표, 변화량}. 변화량은 시작이 +1, 끝이 -1.
    int[][] events = new int[intervals.size() * 2][];
    int at = 0;
    for (Interval interval : intervals) {
        events[at++] = new int[] {interval.start(), +1};
        events[at++] = new int[] {interval.end(), -1};
    }

    Arrays.sort(events, (a, b) -> {
        sweep.compare();
        if (a[0] != b[0]) {
            return Integer.compare(a[0], b[0]);
        }
        // 같은 좌표에서 무엇을 먼저 볼 것인가. 이 한 줄이 구간의 정의다.
        return closedEnd ? Integer.compare(b[1], a[1]) : Integer.compare(a[1], b[1]);
    });

    int active = 0;
    int best = 0;
    for (int[] event : events) {
        sweep.processEvent();
        active += event[1];
        sweep.reportActive(active);      // 계측기에도 알린다 — 교차 확인용
        best = Math.max(best, active);
    }
    return best;
}
```

**질문별 답**

- Q: 구간 하나가 이벤트 몇 개가 되고, 각 이벤트의 변화량은 얼마인가?
  A: **두 개**다 — `(start, +1)` 과 `(end, -1)`.
  그래서 구간 n 개면 이벤트가 정확히 `2n` 개이고, 배열을 `intervals.size() * 2` 로 잡는다.
  `active` 에 변화량을 누적하면 그 좌표에서 열려 있는 구간 수가 된다.
  +1/−1 을 누적하는 이 모양이 10번 누적 합(차분 배열)과 정확히 같은 아이디어다.

- Q: "구간 안쪽에서는 아무 일도 안 일어난다"가 왜 볼 곳을 `2n` 개로 줄이는가?
  A: 열린 구간 수(`active`)는 **구간이 시작하거나 끝날 때만** 바뀌기 때문이다.
  두 이벤트 사이에서는 값이 상수이므로, 그 사이의 좌표를 아무리 많이 봐도 새로 알게 되는 것이 없다.
  그러니 최대치는 이벤트 지점에서만 확인하면 충분하다 — 볼 곳이 값의 범위가 아니라 경계 개수 `2n` 이 된다.
  실측: 구간 1,000개·범위 10억에서 좌표 훑기 10억 칸 vs 이벤트 2,000개 — **50만 배**.

- Q: 같은 좌표에서 시작과 끝 중 무엇을 먼저 처리하느냐가 무엇을 가르는가? (원본 함정)
  A: **닫힌 구간 `[a,b]` 와 반열린 구간 `[a,b)` 를 가른다.**
  시작(+1)을 먼저 처리하면 같은 좌표에서 앞 구간이 아직 안 닫힌 채 새 구간이 열려 겹침으로 세어진다 → 닫힌 구간.
  끝(−1)을 먼저 처리하면 앞 구간이 닫힌 뒤에 새 구간이 열려 안 겹친 것이 된다 → 반열린 구간.
  즉 이것은 구현 취향이 아니라 **문제의 정의**를 고르는 일이다.

- Q: 그 규칙이 코드의 어디 한 줄에 들어 있는가 — 닫힌 구간이면 비교자가 어떻게 되는가?
  A: 정렬 비교자의 마지막 한 줄이다: `closedEnd ? Integer.compare(b[1], a[1]) : Integer.compare(a[1], b[1])`.
  닫힌 구간(`closedEnd=true`)이면 변화량을 **내림차순**으로 비교해 +1 이 −1 보다 앞에 온다.
  반열린이면 오름차순이라 −1 이 먼저 온다.
  **계약이 비교자 한 줄에 있다** — 그래서 이 줄에 주석을 달고, 테스트가 두 모드를 모두 검증한다.

- Q: `[1,3]` 과 `[3,5]` 의 답이 닫힌/반열린에서 각각 몇인가?
  A: 닫힌 구간이면 **2**(좌표 3 에서 둘 다 살아 있다), 반열린이면 **1**(3 에서 앞의 것은 이미 끝났다).
  같은 입력, 같은 코드인데 불린 플래그 하나로 답이 달라진다.
  회의실로 비유하면 "10시에 끝나는 회의와 10시에 시작하는 회의가 방을 두 개 필요로 하는가"의 문제다.
  현실의 답은 도메인이 정한다 — 그래서 `Interval` record 는 끝점 포함 여부를 스스로 정하지 않고 부르는 쪽에 맡긴다.

- Q: 끝점 규칙이 "구석 사례가 아니다"라는 실측은 어떤 수치였는가? (원본 측정 셋)
  A: 구간 20개를 0~30 범위에 무작위로 놓고 1,000번 시험했을 때, 닫힌 구간과 반열린 구간의 답이 다른 경우가 **687 / 1,000** 이었다.
  좁은 범위에 구간이 여럿 있으면 끝점이 맞닿는 일이 흔하기 때문이다.
  즉 이 규칙은 "아주 드문 입력에서만 문제되는 예외 처리"가 아니라 **대부분의 입력에서 답을 바꾸는 본체**다.
  경계 규칙을 구석 사례로 미뤄 두는 습관이 왜 위험한지를 수치로 보여준 실측이다.

- Q: 정하지 않고 짜면 "3분의 2 확률로 틀린다"는 말은 무슨 뜻인가?
  A: 규칙을 명시하지 않고 짜면 비교자에서 우연히 둘 중 하나가 나오는데, 입력의 약 2/3 에서는 두 해석의 답이 다르므로 의도와 어긋날 확률이 그만큼이라는 뜻이다.
  "동전 던지기로 계약을 정한 셈"이라는 표현이 적절하다.
  더 나쁜 것은 **틀려도 예외가 안 나고 그럴듯한 숫자가 나온다**는 점 — 코드 리뷰에서도 안 보인다.
  그래서 계약을 코드(비교자)와 테스트 양쪽에 못박아 둔다.

- Q: 대조군(`maxOverlapByScan`)의 진짜 비용은 칸 수인가 무엇인가? (원본 측정 둘)
  A: **칸 × 구간**이다.
  코드를 보면 좌표 한 칸마다 **모든 구간을 다시 훑어** 안에 있는지 검사하는 이중 루프다.
  칸만 세면(`visitCell()`) 바깥 루프만 세는 것이라 안쪽 루프가 통째로 빠진다.
  실측(구간 200개·범위 약 10만): 칸 100,680 vs 칸×구간 **20,136,000**.

- Q: 칸만 세면 30배, 안쪽 루프까지 세면 6,000배 — 이 차이가 주는 교훈은?
  A: **무엇을 세는지가 결론을 정한다.**
  같은 두 구현을 비교하는데, 계측 지점을 어디 두느냐에 따라 "30배 차이"와 "6,000배 차이"라는 200배 다른 결론이 나온다.
  성능 논쟁이 갈릴 때 먼저 확인할 것은 알고리즘이 아니라 **계측 정의**다.
  28번(체 vs 시행 나눗셈에서 쓰기 수 대 순회 수)·29번에서도 같은 함정이 나왔다 — 반복해서 나오는 실수 유형이다.

- Q: 구간 1,000개·범위 10억에서 50만 배 차이가 난다는 것은 무엇과 무엇의 비교인가? (원본 측정 하나)
  A: **좌표를 훑을 때의 1,000,000,000 칸**과 **이벤트를 훑을 때의 2,000 개**의 비교다.
  압축 후 유일값도 2,000개 — 값의 범위가 아니라 값의 개수가 비용이 된다는 것이 이 표의 요지다.
  같은 실행에서 정렬 비교는 19,204번으로 `2n log 2n`(2,000 × 11 ≈ 22,000) 근처다.
  즉 전체 비용은 "이벤트 개수"가 아니라 "이벤트 정렬"이 지배한다.

- Q: 계측기가 기록한 최대치를 답의 교차 확인에 쓸 수 있는 이유와, 그것이 완전한 독립 검증이 아닌 이유는? (원본 측정 다섯)
  A: `sweep.reportActive(active)` 가 매 이벤트마다 열린 개수를 받아 `maxActive` 를 따로 기록하므로, 함수가 돌려준 `best` 와 비교해 어긋나면 둘 중 하나가 틀린 것이다.
  특히 마지막에 `max` 를 잘못 잡거나 갱신을 빠뜨리는 실수를 잡는다.
  완전한 독립이 아닌 이유: 두 값 모두 **같은 `active` 변수**를 보고 만들어진다 — 이벤트 생성이나 정렬이 틀리면 둘 다 똑같이 틀린다.
  "싸게 얻는 부분적 교차 확인"으로는 유용하지만 독립 구현(대조군 `byScan`)을 대체하지는 못한다.

- Q: 빈 입력에서 답이 0 이어야 하는 것은 알고리즘이 정하는가 계약이 정하는가?
  A: **계약이 정한다** — impl 은 `if (intervals.isEmpty()) return 0;` 로 먼저 막는다.
  알고리즘을 그냥 돌려도 0 이 나오긴 하지만, `maxOverlapByScan` 쪽은 lo/hi 초기값이 `MAX_VALUE`/`MIN_VALUE` 라 빈 입력에서 루프가 이상하게 돌 수 있어 명시적으로 막는 편이 안전하다.
  경계 입력(빈 것, 하나짜리)은 "어쩌다 맞는" 것이 아니라 **의도해서 맞는** 상태여야 한다.
  두 구현이 같은 답을 내야 하므로 양쪽에 같은 가드를 둔다.

#### 3. 구간 병합 (`Sweep.merge` — TODO 4)

**정답 코드 (impl 기준, 핵심부)**

```java
public static List<Interval> merge(List<Interval> intervals, boolean touching, CountedSweep sweep) {
    List<Interval> merged = new ArrayList<>();
    if (intervals.isEmpty()) {
        return merged;
    }
    List<Interval> sorted = new ArrayList<>(intervals);
    sorted.sort((a, b) -> {
        sweep.compare();
        return a.start() != b.start()
                ? Integer.compare(a.start(), b.start())
                : Integer.compare(a.end(), b.end());
    });

    int start = sorted.get(0).start();
    int end = sorted.get(0).end();
    for (int i = 1; i < sorted.size(); i++) {
        sweep.processEvent();
        Interval next = sorted.get(i);
        long gap = (long) next.start() - end;          // long 으로 올려 오버플로를 막는다
        boolean joins = touching ? gap <= 1 : gap <= 0;
        if (joins) {
            end = Math.max(end, next.end());           // 덮어쓰기가 아니라 max
        } else {
            merged.add(new Interval(start, end));
            start = next.start();
            end = next.end();
        }
    }
    merged.add(new Interval(start, end));              // 마지막 것은 루프 밖에서
    return merged;
}
```

```
전:  [1,3] [2,6] [8,10]     (정렬 먼저! 시작 순으로)

[1]  [1,3] 을 잡는다                       start=1, end=3
[2]  [2,6]: 2 <= 3 (겹침)  -> end = max(3, 6) = 6
[3]  [8,10]: 8 > 6 (안 겹침) -> [1,6] 확정, 새로 시작

후:  [1,6] [8,10]
```

**질문별 답**

- Q: 병합에서 정렬을 먼저 하지 않으면 무엇을 놓치는가? (원본 함정)
  A: **뒤에 오는 겹침**을 놓친다.
  `[8,10], [1,3], [2,6]` 순으로 들어오면, `[8,10]` 다음에 `[1,3]` 이 와서 "안 겹침"으로 판정되고 끊어진다 — 실제로는 `[1,3]` 과 `[2,6]` 이 합쳐져야 한다.
  한 번 훑기가 성립하는 근거가 "시작 순으로 정렬돼 있으니, 지금 구간과 안 붙으면 그 뒤의 것들과도 안 붙는다"이기 때문이다.
  정렬이 그 불변식을 만들어 준다 — 정렬은 준비 작업이 아니라 **정확성의 전제**다.

- Q: 끝을 `max` 로 늘리지 않고 덮어쓰면 어떤 입력에서 무엇이 틀리는가? (원본 함정)
  A: 앞 구간 안에 **통째로 들어간** 구간이 있을 때 틀린다.
  `[1,10]` 다음에 `[2,3]` 이 오면, 덮어쓰기는 end 를 10 에서 **3 으로 줄여** `[1,3]` 을 내놓는다 — 구간이 짧아진다.
  `Math.max(end, next.end())` 면 10 이 유지된다.
  시작 순 정렬만으로는 끝의 순서가 보장되지 않기 때문에 생기는 함정이다(그래서 시작이 같을 때만 끝으로 2차 정렬을 한다).

- Q: `touching` 이 true 와 false 일 때 이어붙임 조건이 각각 어떻게 달라지는가?
  A: `gap = next.start() - end` 라 할 때, `touching=false` 면 `gap <= 0`, `touching=true` 면 `gap <= 1` 이다.
  즉 true 면 `[1,3]` 과 `[4,6]` 처럼 틈이 정확히 1 인 것도 붙인다 — 정수 구간에서 3 과 4 사이에는 아무것도 없으니 붙어 있다고 보는 계약.
  false 면 실제로 겹치거나 끝점이 같아야(`gap <= 0`) 붙는다.
  최대 겹침의 `closedEnd` 와 같은 계열의 **계약 플래그**다 — 정수 구간인지 실수 구간인지에 따라 답이 달라진다.

- Q: 틈을 계산할 때 `long` 으로 올리는 이유는?
  A: `next.start() - end` 가 `int` 범위를 넘을 수 있기 때문이다.
  start 가 `Integer.MIN_VALUE` 근처이고 end 가 `MAX_VALUE` 근처면 뺄셈이 오버플로해 **부호가 뒤집힌다** — 안 붙어야 할 것이 붙거나 그 반대가 된다.
  오버플로는 예외가 아니라 조용한 오답이라 테스트 입력이 좁으면 안 잡힌다.
  24번의 `% mod`·`floorDiv` 와 같은 계열의 방어다 — 비용이 거의 0 인 안전장치는 그냥 둔다.

- Q: 마지막 구간을 루프 밖에서 한 번 더 `add` 해야 하는 이유는?
  A: 루프 안에서는 "**다음 구간이 안 붙을 때**" 현재 구간을 확정해 넣기 때문이다 — 마지막 구간에는 그 "다음"이 없다.
  그래서 루프가 끝난 뒤 `merged.add(new Interval(start, end))` 로 손에 남은 것을 넣어 준다.
  빼먹으면 결과에서 항상 마지막 구간 하나가 사라진다 — 계약 테스트가 바로 잡는 종류의 버그다.
  "누적하다 조건이 바뀔 때 방출"하는 루프의 전형적인 마무리 처리다.

- Q: 시작이 같을 때 끝으로 한 번 더 정렬하는 것은 필요한가, 없으면 무엇이 달라지는가?
  A: **결과의 정확성에는 필요하지 않다** — 시작이 같으면 어느 쪽을 먼저 잡든 `max` 로 늘리므로 최종 끝이 같아진다.
  달라지는 것은 **결정성**이다: 2차 기준이 없으면 정렬이 안정적이지 않을 때 순서가 입력에 따라 달라질 수 있고, 계측값(비교 횟수)도 흔들린다.
  `Arrays.sort`/`List.sort` 는 객체에 대해 안정 정렬이지만, 비교자가 전순서를 명확히 주는 편이 의도를 드러낸다.
  (원본에 근거 없음 — 내 추론: impl 이 2차 기준을 둔 이유는 정확성보다 결정성·가독성 쪽으로 보인다.)

- Q: 병합 비용의 89퍼센트가 정렬이라는 실측은 실무에서 어떤 질문으로 바뀌는가? (원본 측정 넷)
  A: **"이미 정렬돼 들어오나?"** 가 가장 큰 질문이 된다.
  실측(구간 1,000개): 정렬 비교 8,693 vs 훑기 999 — 훑기 알고리즘을 아무리 다듬어도 전체의 11%만 건드리는 것이다.
  DB 에서 `ORDER BY` 로 받아오거나, 애초에 정렬된 순서로 쌓이는 자료구조를 쓰면 그 89%가 통째로 사라진다.
  최적화는 "내 루프"가 아니라 **파이프라인 전체**에서 봐야 한다는 실무 교훈.

- Q: 병합과 최대 겹침은 같은 "정렬 후 한 번 훑기" 틀인데 무엇이 다른가?
  A: **무엇을 정렬하고 무엇을 들고 가느냐**가 다르다.
  최대 겹침은 구간을 `2n` 개의 **이벤트**로 쪼개 정렬하고, 상태로 `active`(정수 하나)를 들고 최대치를 기록한다.
  병합은 구간 `n` 개를 **시작 순**으로 정렬하고, 상태로 "지금 만들고 있는 구간"(start, end)을 들고 결과 목록을 쌓는다.
  공통 틀: 정렬로 순서를 만든 뒤 되돌아가지 않고 한 번 훑으며 상태를 갱신 — 23번 그리디, 17번 MST 와 같은 모양이다.

### B. 개념

- Q: (원본 생각해볼 것) 겹침이 가장 큰 **구간**(자리 하나가 아니라)을 알려면 무엇을 더 들고 있어야 하는가?
  A: (원본에 답 없음 — 내 추론) **직전 이벤트의 좌표**를 들고 있어야 한다.
  지금 구현은 `best` 라는 숫자 하나만 갱신하는데, 최대치가 갱신된 시점의 좌표와 그 상태가 끝나는 다음 이벤트의 좌표를 함께 기록하면 `[그 좌표, 다음 이벤트 좌표]` 구간이 나온다.
  같은 최대치가 여러 구간에서 나올 수 있으므로 "전부 모을지 첫 번째만 낼지"도 계약으로 정해야 한다.
  끝점 규칙(닫힘/반열림)이 그 구간의 양 끝 포함 여부에도 그대로 영향을 준다 — 여기서도 계약이 먼저다.

- Q: (원본 생각해볼 것) 구간이 계속 추가되고 질의도 계속 들어와 정렬 한 번으로 안 되면 무엇을 쓰는가?
  A: (원본에 답 없음 — 내 추론) **동적 자료구조**로 간다.
  선택지: 좌표 압축 + 펜윅 트리/세그먼트 트리(구간 갱신 + 구간 최댓값 질의), 균형 이진 탐색 트리(자바의 `TreeMap`)로 이벤트를 좌표 순으로 유지하며 삽입 O(log n).
  좌표가 미리 다 안 알려져 있으면 압축을 못 하므로 `TreeMap` 쪽이나 동적 세그먼트 트리가 필요하다.
  핵심 차이: 정적 문제는 "한 번 정렬 후 한 번 훑기", 동적 문제는 "삽입마다 O(log n) 을 내고 순서를 유지" — 무엇을 미리 아는가가 자료구조를 정한다.

- Q: (원본 생각해볼 것) 2차원 직사각형의 합집합 넓이는 어떻게 구하는가 — 스위핑을 한 축에만 쓰면 다른 축은 무엇으로 다루는가?
  A: (원본에 답 없음 — 내 추론 + 알려진 기법) x 축을 왼쪽에서 오른쪽으로 훑고, 각 직사각형을 (왼쪽 변, +1)·(오른쪽 변, −1) 두 이벤트로 만든다.
  **다른 축(y)은 "지금 덮여 있는 y 길이"를 유지하는 자료구조**로 다룬다 — y 좌표를 압축한 뒤 세그먼트 트리에 구간 +1/−1 을 넣고 "덮인 총 길이"를 질의한다.
  넓이는 이벤트 사이의 x 폭 × 그 구간에서 덮인 y 길이를 누적해 얻는다.
  즉 1차원 스위핑의 `active`(정수 하나)가 2차원에서는 **자료구조 하나**로 커진 것 — 구조는 같고 상태가 무거워진다.

- Q: (원본 생각해볼 것) 좌표 압축을 하면 "빈 칸" 정보가 사라지는데, 그게 문제가 되는 질문은 어떤 것인가?
  A: (원본에 답 없음 — 내 추론) **길이·거리·개수를 묻는 질문**이다.
  예: "어느 구간에도 안 덮인 빈 길이의 총합은?", "가장 긴 빈 구간은?", "덮인 넓이는?" — 등수 사이의 실제 간격이 사라졌으므로 압축 좌표에서는 계산할 수 없다.
  해결: 등수 표를 들고 있다가 `table[i+1] - table[i]` 로 실제 간격을 곱해 준다(구간 넓이 스위핑이 하는 일이 이것이다).
  또 하나의 함정: 정수 문제에서 "값 사이에 빈 정수 칸이 있는가"를 따져야 할 때는 압축 좌표에 **경계+1 지점을 추가로 넣어** 두는 기법을 쓴다.

- Q: 등수 찾기가 06번(원본 표기 02번) 이분 탐색 그대로인 이유는?
  A: 등수 표가 **정렬된 배열**이고, 등수는 곧 그 배열에서의 위치이기 때문이다.
  정렬된 배열에서 위치를 찾는 문제가 이분 탐색의 정의 그 자체다 — `lo/hi` 를 좁혀 절반씩 버린다.
  impl 의 `rankOf` 는 교과서 이분 탐색과 한 글자도 다르지 않고, 다만 `sweep.compare()` 로 비교를 세는 줄이 추가됐을 뿐이다.
  "새 기법처럼 보이는 것이 사실은 아는 기법의 조합"이라는 것이 이 챕터가 앞 챕터들과 만나는 방식이다.

- Q: 압축 후 배열에 +1/−1 을 누적하면 10번 누적 합이 되는데, 그때 얻는 것은 무엇인가?
  A: **모든 지점의 겹침 수를 한 번에** 얻는다 — 최대치 하나가 아니라 분포 전체다.
  차분 배열에 구간 시작에 +1, 끝 다음에 −1 을 넣고 누적 합을 취하면 각 칸의 값이 그 칸을 덮는 구간 수가 된다.
  좌표 압축 덕분에 그 배열의 크기가 값의 범위가 아니라 유일값 개수(예: 2,000)가 된다 — 압축이 없으면 못 만들 배열이다.
  `maxOverlap` 은 최대치만 필요해서 배열조차 안 만들지만, "각 구간이 몇 번 덮였나" 같은 질의에는 이 조합이 답이다.

- Q: 구간을 시작 순으로 정렬해 하나씩 처리하는 모양이 17번 그리디와 같다는 말은 무슨 뜻인가?
  A: **정렬로 순서를 만든 뒤 되돌아가지 않고 한 번 훑으며 결정을 확정한다**는 구조가 같다는 뜻이다.
  17번 MST(크루스칼)는 간선을 가중치 순으로 정렬해 앞에서부터 취하고, 병합은 구간을 시작 순으로 정렬해 앞에서부터 붙인다 — 둘 다 되돌리기가 없다.
  되돌리지 않아도 되는 근거도 같은 종류다: 정렬이 만든 불변식("뒤에 오는 것은 더 크다") 덕분에 지금 판정이 나중에 뒤집히지 않는다.
  23번 그리디의 활동 선택(끝 시각 순 정렬 + 한 번 훑기)도 정확히 같은 틀이다.

- Q: "무엇을 세는지가 결론을 정한다"는 교훈이 28·29번에서도 나왔는데, 공통된 실수의 모양은 무엇인가?
  A: **바깥 루프만 세고 안쪽 비용을 빼먹는 것**이다.
  30번: 칸만 세면 30배, 칸×구간을 세면 6,000배. 28번: 최소 소인수 표가 "쓰기 수"로는 싸 보이는데 "순회 수"로는 비싸다.
  공통 구조: 한 단위의 작업이 실제로는 여러 연산을 품고 있는데, 계측기를 단위 하나당 한 번만 올려서 그 안쪽이 안 보이게 된다.
  방어법: 계측 지점을 정할 때 "이 한 번이 진짜로 상수 시간인가"를 묻고, 두 구현을 비교할 때는 **같은 정의의 단위**로 세고 있는지 먼저 확인한다.

- Q: 스위핑을 실무에 적용할 때(동시 접속 피크, 일정 합치기, IP 대역 정리) 가장 먼저 확정해야 할 계약은 무엇인가?
  A: **끝점을 포함하는가**(닫힘/반열림), 그리고 **닿는 것을 붙일 것인가**(touching) 둘이다.
  세션 로그의 "10:00 종료"와 "10:00 시작"을 동시 접속 2로 셀 것인가, IP 대역 `1.0.0.0-1.0.0.255` 와 `1.0.1.0-...` 을 하나로 합칠 것인가 — 전부 이 두 플래그다.
  실측이 말하듯 이 규칙은 입력의 약 2/3 에서 답을 바꾸므로, 구현 전에 도메인 담당자와 합의해 테스트로 못박아야 한다.
  나머지(정렬·누적)는 기계적이다 — 어려운 부분은 알고리즘이 아니라 계약이다.

- Q: 이 챕터의 비용이 사실상 정렬 비용이라면, 성능을 더 끌어올릴 여지는 어디에 있는가?
  A: ① **정렬을 아예 없애기** — 입력이 이미 정렬돼 들어오게 만든다(DB `ORDER BY`, 시간순으로 쌓이는 로그). 실측 병합에서 89% 절감.
  ② **정렬을 싸게 하기** — 좌표가 작은 정수면 비교 정렬 대신 05번 계수·기수 정렬로 O(n).
  ③ **정렬 결과를 재사용하기** — 같은 구간 집합에 질의가 여러 번이면 한 번 정렬해 두고 여러 질의를 받는다.
  훑기 자체는 이미 O(n) 이라 거기서 깎을 것은 거의 없다 — **병목이 아닌 곳을 최적화하지 않는 것**이 이 실측의 실천적 결론이다.
