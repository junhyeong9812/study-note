# algorithm/41-computability-and-halting — 정답

## 정답

### 1. 완벽한 정적 분석기가 없는 이유

- "버그가 있나"(null 역참조, 비밀값 유출, 무한 루프 등)는 프로그램의 **실행 의미**에 대한 성질이다. 라이스 정리에 따르면, 자명하지 않은 의미 성질은 입력이 무엇이든 끝나면서 정확히 답하는 판정기가 없다. 그런 판정기가 있으면 정지 문제를 풀 수 있기 때문이다.
- 그래서 분석기는 하나를 포기한다.
  - 오탐 허용(건전 — "없다"고 하면 정말 없다).
  - 미탐 허용(확실한 것만 보고).
  - 끝나지 않을 수 있음 허용(실제 실행·상한 없는 탐색).

### 2. 결정 가능·인식 가능·결정 불가능

- 결정 가능: 입력이 무엇이든 멈추고 예/아니오를 맞게 답하는 프로그램이 있다.
- 인식 가능: "예"인 입력에서는 언젠가 멈추며 예라고 답한다. "아니오"면 멈추지 않을 수 있다.
- 결정 불가능: 결정하는 프로그램이 없다.
- 정지 문제
  - 인식 가능하다: (P, x)를 그냥 실행해 보고, 끝나면 "예"라고 한다.
  - 결정 불가능하다: 안 끝나는 경우 "아니오"를 언제 말할지 정할 수 없다. 대각선 논법으로 어떤 판정기도 틀리는 입력이 있음을 보인다(Sipser 4.2).

### 3. 대각선 표

```text
             입력 P1   P2   P3   P4
  P1          끝남    무한  끝남  끝남
  P2          무한    무한  끝남  무한
  P3          끝남    끝남  무한  끝남
  P4          무한    끝남  끝남  끝남
  D           무한    끝남  끝남  무한     ← 대각선 (i,i)를 뒤집음
```

- D는 i번째 칸에서 P_i와 다르다. 그러니 어떤 행과도 같지 않다.
- 그런데 D도 프로그램이므로 어떤 행 P_k여야 한다. 칸 (k, k)에서 자기 자신과 달라야 하니 모순이다.
- 이어짐: 표를 채우려면 정지 판정기 H가 필요하다. D는 "H(P_i, P_i)가 끝난다면 무한 루프, 아니면 끝"으로 구현된다. 모순이 나오므로 H가 없다.

### 4. 걸음 상한 판정기

(실험, OpenJDK 21.0.12 Temurin `--cpus=2`)

```text
[1] 500만 걸음 뒤 끝나는 프로그램: H(B=100만) = 안 멈춘다, 실제 = 끝남
[2] H(비관, B=1000) 예측 H(D,D) = 안 멈춘다, 실제 D(D) = 끝남
[2] H(낙관, B=1000) 예측 H(D,D) = 멈춘다, 실제 D(D) = 3초 안에 안 끝남(영원히 도는 루프)
```

- 느린 프로그램: "안 멈춘다"로 오판한다. 실제로는 끝난다.
- 비관 H의 D: H는 "안 멈춘다"고 했다. D는 그 답을 보고 바로 끝났다.
- 낙관 H의 D: H는 "멈춘다"고 했다. D는 그 답을 보고 무한 루프에 들어갔다(코드상 `while (true)`, 관찰은 3초).
- 어느 H든 그 H로 만든 D에서 정반대로 틀린다.

### 5. 라이스 정리의 조건

- ① 자명하지 않다: 성질을 만족하는 프로그램도, 안 만족하는 프로그램도 있다.
- ② 받아들이는 언어에만 의존한다: 같은 언어를 받아들이는 두 프로그램은 같은 답을 받는다.
- "소스에 `System.exit` 글자가 있나": 구문 성질이다. 텍스트를 훑으면 결정된다. 대상이 아니다.
- "실행 중 `System.exit`를 부를 수 있나": 실행 동작에 대한 의미 성질이다. 받아들이는 언어의 성질은 아니라서 라이스 정리를 글자 그대로 적용하지는 않지만, 같은 방식의 정지 문제 환원(요약 4절 스케치)으로 결정 불가능하다. 라이스식 논증이 겨누는 쪽은 이것이다.

### 6. `deleteAll` 분석기로 정지 문제 풀기

- 정지 문제 입력 (M, w)를 받는다. 다음 프로그램 Q를 만든다(M, w 안에는 `deleteAll` 호출이 없다고 하자).

```java
void Q() {
    run(M, w);        // M을 w로 실행
    deleteAll();
}
```

- Q가 `deleteAll`을 부른다 ⇔ M(w)가 끝난다.
- 그러니 A(Q)의 답이 곧 정지 문제의 답이다. 정지 문제는 결정 불가능하므로 A는 없다.

### 7. javac의 확정 대입

(실험, OpenJDK 21.0.12 `javac`)

```text
Conservative.java:6: error: variable x might not have been initialized
1 error
```

- 이유: JLS 16장의 흐름 분석은 `&&`·`||`·`!`·`? :`와 boolean 상수 식만 특별 취급한다. 그 밖의 식의 **값**은 보지 않는다. `n > 0`과 `n <= 0`이 서로 여집합이라는 사실을 쓰지 않는다.
- 규칙을 둔 이유: 초기화 안 된 변수 읽기가 컴파일된 코드에서 생기지 않게 한다(미탐 0). 대가가 이런 오탐이다.
- 고치기: `if (n > 0) x = 1; else x = 2;` 또는 `int x = n > 0 ? 1 : 2;`.
- `int x = 0;`의 위험: 나중에 분기를 추가하다 대입을 빠뜨려도 컴파일러가 잡지 못한다. 값 0이 조용히 쓰인다.

### 8. "infinite loop detected"로 죽은 정상 배치

- 착각: 시간·걸음 상한 초과를 "무한 루프"와 같은 것으로 봤다. 상한 판정기는 느리게 끝나는 것과 안 끝나는 것을 구분하지 못한다(4번 [1]).
- 바꾸기
  - 알림 문구를 "예산 초과"로 바꾼다.
  - 진행 지표(처리 건수·오프셋)를 함께 보고, 진행 중이면 연장하거나 분할 처리한다.
  - 예산을 입력 크기에 비례해 잡는다.
  - "진행 지표가 일정 시간 변하지 않음"은 멈춤 **의심** 경보·조사 기준으로 쓴다. 이후 다시 진행할 수 있으니 무한 루프의 증명은 아니다.

### 9. 사용자 제공 스크립트

- 업로드 시점 검사로 못 막는 이유: "이 스크립트가 어떤 입력에서든 끝나나"는 전역 종료성(totality) 문제다. 정지 문제를 이리로 환원할 수 있어 일반적으로 결정 불가능하다. 스크립트 언어가 임의의 계산을 표현할 수 있을 만큼(튜링 완전) 강하면 그렇다. 반복 횟수가 제한되거나 재귀가 구조적으로 줄어야 하는 언어(예: Agda의 종료 검사)는 종료를 보장할 수 있다.
- 실행 시점 대처
  - 시간·걸음·메모리 예산을 둔다. 초과하면 중단하고 "예산 초과"로 보고한다.
  - 평가 코드가 인터럽트를 확인하게 한다.
  - 별도 스레드 풀·프로세스로 격리해 다른 작업을 지킨다.
  - 이더리움 gas처럼 단계마다 비용을 매겨 한도에서 끊는다.
  - 또는 언어를 제한한다(반복 상한·재귀 금지). 정지가 구조로 보장된다.
