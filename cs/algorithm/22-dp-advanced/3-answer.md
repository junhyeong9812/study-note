### A. 문제 (src/main 의 TODO 1~12)

#### 1. 구간 DP — 행렬 곱 순서 (TODO 1~4)

**정답 코드 (impl 기준)**

```java
public static long minCost(int[] dims, CountedTable table) {
    int n = dims.length - 1;
    if (n <= 1) {
        return 0;
    }
    // 구간 길이를 2 부터 늘려간다. 길이 1 은 곱할 것이 없어 비용 0 이다.
    for (int i = 0; i < n; i++) {
        table.set(i * n + i, 0);
    }
    for (int length = 2; length <= n; length++) {
        for (int i = 0; i + length - 1 < n; i++) {
            int j = i + length - 1;
            long best = Long.MAX_VALUE;
            for (int k = i; k < j; k++) {
                long cost = table.get(i * n + k)
                        + table.get((k + 1) * n + j)
                        + (long) dims[i] * dims[k + 1] * dims[j + 1];
                best = Math.min(best, cost);
            }
            table.set(i * n + j, best);
        }
    }
    return table.get(n - 1);   // 구간 [0, n-1] 의 칸
}

public static long leftToRightCost(int[] dims) {
    int n = dims.length - 1;
    long total = 0;
    int rows = dims[0];
    for (int i = 1; i < n; i++) {
        total += (long) rows * dims[i] * dims[i + 1];
    }
    return total;
}
```

```
상태 = "구간 [i, j] 를 행렬 하나로 합치는 최소 비용"

[i ......... j] 를 마지막에 k 에서 자른다:
[i ... k] [k+1 ... j]
   |          |
dims[i] x dims[k+1]   dims[k+1] x dims[j+1]   <- 두 덩어리의 결과 크기
합치는 비용 = dims[i] * dims[k+1] * dims[j+1]

채우는 순서: 길이 1 (비용 0) -> 길이 2 -> 길이 3 -> ... -> 길이 n (전체)
```

**질문별 답**

- Q: 상태를 무엇으로 잡는가, 그리고 배낭처럼 "앞에서부터 하나씩" 결정하는 방식은 왜 여기서 안 통하는가?\
  A: 상태 = "구간 [i, j] 를 하나로 합치는 최소 비용"이다.\
  배낭은 물건마다 넣나/안 넣나의 독립 결정이라 "앞에서부터" 진행돼도 남는 것이 (index, remaining) 로 요약된다.\
  행렬 곱은 "어디를 자르나"가 문제를 왼쪽/오른쪽 **두 덩어리**로 쪼갠다 — 진행 방향이 한 줄이 아니다.\
  그래서 접두사가 아니라 **구간**이 상태가 된다.\
  이것이 구간 DP 라는 이름의 뜻이다.

> **구간 DP(interval DP)** — 상태를 구간 [i, j]로 잡고, 마지막에 자를 자리를 전부 시도해 양쪽 답을 합치는 DP.\
> 예: "[i, j]의 행렬들을 하나로 합치는 최소 비용"이 표의 한 칸이 된다.

> **접두사(prefix)** — 앞에서부터 잘라낸 앞 토막.\
> 예: 배낭은 "몇 번째 물건까지 봤나"라는 접두사만으로 상태가 되지만, 행렬 곱은 양쪽이 잘려 구간이 필요하다.

- Q: "마지막에 어디를 자르는가"(k)는 문제를 어떻게 두 개의 같은 모양 문제로 쪼개는가?\
  A: 마지막 곱셈이 [i..k] 의 결과와 [k+1..j] 의 결과를 합치는 것이라고 보면, 그 앞의 일은 "[i..k] 를 합치기"와 "[k+1..j] 를 합치기"다.\
  둘 다 "구간을 하나로 합치는 최소 비용"이라는 원래와 같은 모양의 문제다.\
  두 덩어리는 서로 간섭하지 않는다 — 왼쪽을 어떻게 합쳤는지가 오른쪽 비용에 영향을 안 준다(최적 부분 구조).\
  그래서 `비용(i,j) = min over k of [ 비용(i,k) + 비용(k+1,j) + 합치는 비용 ]` 이 성립한다.

> **최적 부분 구조(optimal substructure)** — 여기까지 온 경로·순서가 앞으로의 최적 답에 영향을 주지 않는 성질.\
> 예: 왼쪽 덩어리를 어떤 순서로 합쳤든, 오른쪽 덩어리의 최소 비용은 달라지지 않는다.

- Q: 표는 어떤 순서로 채워야 하는가 — i 를 바깥 루프에 두면 왜 안 되는가?\
  A: **구간 길이**를 바깥 루프에 두고 짧은 구간부터 채운다(길이 2 → n).\
  [i, j] 의 답은 [i, k] 와 [k+1, j] — 모두 자기보다 **짧은** 구간의 답을 읽는다.\
  i 를 바깥에 두고 j 를 안쪽에 두면, [0, 5] 를 계산할 때 [3, 5] 같은 뒤쪽 구간이 아직 안 채워져 있다.\
  빈 칸(EMPTY = Long.MIN_VALUE)을 읽어 조용히 틀린 답이 나온다.

- Q: 이 채우는 순서 문제는 15번 플로이드의 무엇과 같은 종류인가?\
  A: "k(경유지)를 바깥 루프에 둬야 한다"와 같은 종류다.\
  둘 다 "안쪽 계산이 읽는 값이 어느 단계의 값이어야 하는가"를 루프 순서가 결정한다.\
  플로이드는 "경유지를 k 까지 허용한 거리"가 단계였고, 여기는 "구간 길이"가 단계다.\
  루프 순서 = 표가 완성되는 순서라는 것.\
  타뷸레이션의 보편 함정이다.

> **채우는 순서(fill order)** — 타뷸레이션에서 표의 어느 칸부터 채울지의 순서. 읽히는 칸이 먼저 채워져 있어야 한다.\
> 예: 구간 DP는 구간 길이를 바깥 루프에 둬야 하고, 15번 플로이드는 경유지 k를 바깥에 둬야 한다.

- Q: k 의 범위는 어디부터 어디까지인가, j 를 포함하면 무슨 일이 생기는가?\
  A: `k = i` 부터 `k < j` 까지다(i 포함, j 제외).\
  k 는 "왼쪽 덩어리의 끝"이므로 왼쪽이 [i, k], 오른쪽이 [k+1, j] — k = j 면 오른쪽이 빈 구간이 된다.\
  k = j 를 포함하면 `table.get((j+1) * n + j)` 처럼 의미 없는(i > j) 칸이나 범위 밖을 읽는다.\
  k = i 는 왼쪽이 행렬 하나짜리 구간 [i, i](비용 0)인 정상 경우다.

- Q: 구간 [i, k] 의 결과 행렬은 몇 x 몇이고, 합치는 비용 식은 dims 로 어떻게 쓰는가?\
  A: [i, k] 의 결과는 `dims[i] x dims[k+1]` 이다 — 첫 행렬의 행 수와 마지막 행렬의 열 수만 남는다.\
  [k+1, j] 의 결과는 `dims[k+1] x dims[j+1]` 이다.\
  둘을 곱하는 비용 = `dims[i] * dims[k+1] * dims[j+1]` (p×q 와 q×r 의 곱셈은 p·q·r 회).\
  i 번째 행렬이 dims[i] x dims[i+1] 이라는 정의에서 인덱스가 하나씩 어긋나기 쉬우니 결과 크기부터 적어놓고 식을 쓰는 것이 안전하다.

- Q: 길이 1 짜리 구간의 비용은 얼마이고, 그것을 안 넣으면 무슨 값을 읽게 되는가?\
  A: 0 이다 — 행렬 하나는 곱할 것이 없다.\
  impl 은 루프 전에 `table.set(i * n + i, 0)` 으로 대각선을 먼저 채운다.\
  안 넣으면 길이 2 구간이 `table.get(i * n + i)` 에서 EMPTY(Long.MIN_VALUE)를 읽는다.\
  그 값이 min·덧셈에 섞여 오버플로에 가까운 쓰레기 답이 나온다 — 예외 없이 조용히 틀린다.

> **바닥값(base case)** — 점화식으로 더 쪼갤 수 없어 정의 자체로 답이 정해진 자리.\
> 예: 길이 1짜리 구간 [i, i]의 비용 0 — 이 대각선을 안 깔면 길이 2가 빈 칸을 읽는다.

- Q: leftToRightCost 에서 왼쪽부터 곱해 나갈 때 중간 결과의 크기는 어떻게 변하는가?\
  A: 중간 결과는 항상 `dims[0] x dims[i+1]` — 행 수는 첫 행렬의 dims[0] 으로 고정되고 열 수만 매 단계 바뀐다.\
  그래서 i 번째 곱셈의 비용이 `dims[0] * dims[i] * dims[i+1]` 이다.\
  dims[0] 이 크면 모든 곱셈에 그 큰 수가 계속 곱해진다 — 이것이 순서를 안 정한 대가다.\
  실측: 행렬 60개에서 왼쪽부터 10,382,856 vs 최적 순서 134,863 (76배).

#### 2. 비트마스크 DP — 외판원 순회 (TODO 5~8)

**정답 코드 (impl 기준, 핵심부)**

```java
public static final long IMPOSSIBLE = Long.MAX_VALUE / 4;

// naive: boolean[] visited 로 방문 표시, 다 돌면 출발점 복귀 비용
private static long naiveFrom(long[][] cost, int at, boolean[] visited, int count, long[] calls) {
    calls[0]++;
    int n = cost.length;
    if (count == n) {
        return cost[at][0];             // 출발점으로 돌아오는 비용
    }
    long best = IMPOSSIBLE;
    for (int next = 0; next < n; next++) {
        if (visited[next] || cost[at][next] >= IMPOSSIBLE) {
            continue;                   // 방문했거나 길이 없으면 거른다
        }
        visited[next] = true;
        long candidate = cost[at][next] + naiveFrom(cost, next, visited, count + 1, calls);
        visited[next] = false;          // 백트래킹
        best = Math.min(best, candidate);
    }
    return best;
}

// 비트마스크 DP: 상태 = (방문 집합 mask, 현재 도시 at)
private static long solve(long[][] cost, int mask, int at, int n, CountedTable table) {
    if (mask == (1 << n) - 1) {
        return cost[at][0];
    }
    int key = mask * n + at;
    if (table.isFilled(key)) {
        return table.get(key);
    }
    long best = IMPOSSIBLE;
    for (int next = 0; next < n; next++) {
        if ((mask & (1 << next)) != 0 || cost[at][next] >= IMPOSSIBLE) {
            continue;
        }
        long rest = solve(cost, mask | (1 << next), next, n, table);
        if (rest >= IMPOSSIBLE) {
            continue;                   // 갈 수 없는 미래에 비용을 더하지 않는다
        }
        best = Math.min(best, cost[at][next] + rest);
    }
    table.set(key, best);
    return best;
}
```

```
mask = 이진수 한 자리가 도시 하나
  도시:     3 2 1 0
  mask  = 0b1 0 1 1  = 11   <- 0, 1, 3 방문함, 2 아직

판정: (mask & (1 << next)) != 0   -> next 방문했나
표시: mask | (1 << next)          -> next 를 추가한 "새" 집합 (원본은 그대로)

n=12: 상태 = 2^12 x 12 = 49,152     vs   순서 = 11! = 39,916,800
```

**질문별 답**

- Q: naive 에서 모든 도시를 다 방문했으면 무엇을 더 더해야 하는가?\
  A: 현재 도시에서 출발점(0번)으로 돌아오는 비용 `cost[at][0]` 이다.\
  외판원 순회는 "다 들르고 **돌아오는**" 문제라 마지막 간선이 빠지면 답이 아니다.\
  impl 은 `count == n` 일 때 `return cost[at][0]` 으로 처리한다.\
  이 마지막 간선이 IMPOSSIBLE 이면 그 경로 전체가 IMPOSSIBLE 급으로 커져 min 에서 자연히 밀려난다.

- Q: naive 는 갈 수 없는 길(IMPOSSIBLE)을 어떻게 거르는가?\
  A: 다음 도시 후보를 고를 때 `cost[at][next] >= IMPOSSIBLE` 이면 continue 로 건너뛴다.\
  방문한 도시(`visited[next]`)와 같은 자리에서 함께 거른다.\
  들어가기 전에 거르므로 IMPOSSIBLE 이 덧셈에 섞이는 일이 애초에 없다.\
  후보가 하나도 없으면 best 가 IMPOSSIBLE 로 남아 "이 상태에서는 못 간다"를 값으로 전달한다.

- Q: 상태를 무엇으로 잡는가, "어떤 순서로 방문했나"는 왜 버려도 되는가?\
  A: `(방문한 도시 집합 mask, 현재 도시 at)` 이다.\
  앞으로 갈 곳(남은 도시들)과 다음 이동 비용(현재 위치 기준)은 이 둘로 완전히 정해진다.\
  0→1→2→4 로 왔든 0→2→1→4 로 왔든 "집합 {0,1,2,4}, 현재 4" 이후의 최적 비용은 같다.\
  그래서 (n-1)! 가지 순서가 2^n × n 가지 상태로 접힌다 — 실측 108,505,112 → 11,254 (9,641배).

- Q: 방문한 도시 집합을 정수 하나로 어떻게 표현하는가?\
  A: 비트 i 가 서 있으면 도시 i 를 방문한 것으로 본다.\
  집합 {0, 1, 3} = 이진수 1011 = 11 — 집합 하나가 int 하나다.\
  포함 검사·추가가 비트 연산 한 번(O(1))이고, 집합이 표의 인덱스로 바로 쓰인다.\
  이것이 "비트마스크 DP"라는 이름의 뜻이다.

> **비트마스크(bitmask)** — 집합을 정수 하나의 2진 비트로 표현하는 기법. i번 원소가 있으면 i번째 비트가 1이다.\
> 예: 집합 {0, 1, 3} = 이진수 1011 = 11 — 집합 하나가 int 하나다.

- Q: 표의 크기는 얼마이고, (mask, at) 을 하나의 key 로 누르는 식은 무엇인가?\
  A: `2^n × n` 칸이다.\
  key = `mask * n + at` — mask 마다 폭 n 짜리 구간을 배정한다.\
  21번 배낭의 `index * (capacity + 1) + remaining` 과 같은 행 우선 펴기다.\
  at 의 가짓수가 n 이므로 n 을 곱한다 — 배낭에서 capacity+1 을 곱한 것과 같은 이유다.

> **행 우선 평탄화(row-major flattening)** — 2차원 좌표를 `앞칸 × 뒤칸개수 + 뒤칸` 으로 눌러 1차원 배열 한 자리에 대응시키는 것.\
> 예: `key = mask * n + at` 이 그 식이고, 곱하는 수가 뒤칸의 가짓수와 정확히 같아야 한다.

- Q: n=12 에서 상태 수와 (n-1)! 은 각각 얼마인가?\
  A: 상태 수 = 2^12 × 12 = 49,152.\
  순서 수 = 11! = 39,916,800.\
  약 800배 차이인데, 실측 호출 수 차이는 108,505,112 vs 11,254 로 9,641배다.\
  게다가 49,152칸 중 실제 채워진 것은 11,254개(23%) — 도달 불가능한 상태(집합에 없는 도시에 서 있기, 0번 없는 집합)는 안 채워진다.

- Q: next 도시를 방문했는지는 mask 와 어떤 연산으로 판정하는가?\
  A: `(mask & (1 << next)) != 0` 이면 방문한 것이다.\
  `1 << next` 는 next 번 비트 하나만 선 수다.\
  AND 를 하면 그 비트가 mask 에 서 있을 때만 0 이 아니다.\
  == 1 이 아니라 != 0 으로 비교한다 — 결과는 `1 << next` 이지 1 이 아니다.

> **시프트 연산 `1 << i`** — 1을 왼쪽으로 i칸 밀어 i번 비트 하나만 선 수를 만드는 것.\
> 예: `1 << 3` = 이진수 1000 = 8 — AND 하면 그 비트만 남는다.

- Q: 방문 표시는 어떻게 하는가 — 원래 mask 를 고치면 왜 안 되는가?\
  A: `mask | (1 << next)` 로 **새 값을 만들어** 재귀에 넘긴다.\
  현재 스택 프레임의 mask 는 "이 상태"의 이름표이자 표 key 의 재료다 — for 루프가 남은 next 후보들에 대해 같은 mask 를 계속 써야 한다.\
  mask 자체를 고치면(예: `mask |= ...`) 다음 루프 회차가 "이미 next 를 방문한 집합"에서 출발해 다른 상태를 계산해버린다.\
  naive 의 `visited[next] = true ... false` 복원(백트래킹)을, 불변 값 만들기로 대신한 것이다 — 복원을 잊을 수가 없다.

> **백트래킹(backtracking)** — 상태를 고쳐가며 내려갔다가, 되돌아 나올 때 고쳤던 것을 원래대로 복원하는 방식.\
> 예: `visited[next] = true` 로 내려갔다 `false` 로 되돌리는 것 — 복원을 잊으면 조용히 틀린다.

> **불변 값(immutable value)** — 고치지 않고 새 값을 만들어 넘기는 방식.\
> 예: `mask | (1 << next)` 는 원래 mask를 그대로 두므로 복원 자체가 필요 없다.

- Q: 갈 수 없는 길에서 IMPOSSIBLE 을 그대로 더하면 무슨 일이 생기고, 코드는 어떻게 막는가?\
  A: IMPOSSIBLE 에 비용을 더하면 "갈 수 없음"이라는 의미가 사라지고, 심하면 오버플로로 음수가 되어 min 이 그쪽을 골라버린다.\
  impl 은 두 겹으로 막는다: 간선 자체가 막혔으면(`cost[at][next] >= IMPOSSIBLE`) 진입 전에 continue.\
  재귀 결과가 IMPOSSIBLE 급이면(`rest >= IMPOSSIBLE`) 더하기 전에 continue.\
  "불가능"을 값으로 나르는 설계에서는 그 값이 산술에 섞이는 순간이 곧 버그다.

- Q: IMPOSSIBLE 이 Long.MAX_VALUE 가 아니라 `Long.MAX_VALUE / 4` 인 이유는?\
  A: (원본에 명시 근거 없음 — 내 추론) 더하기 여유분이다.\
  MAX_VALUE 그대로면 비용을 한 번만 더해도 오버플로로 음수가 되어 min 비교가 망가진다.\
  /4 로 여유를 두면 IMPOSSIBLE 에 실비용이 한두 번 더해져도 여전히 "아주 큰 양수"라 `>= IMPOSSIBLE` 판정과 min 에서 안전하게 밀려난다.\
  15번 벨만-포드에서 무한대를 다룰 때와 같은 계열의 방어다.

> **센티널 값(sentinel)** — "정상 값이 될 수 없는 값"을 골라 특별한 뜻으로 쓰는 것.\
> 예: `IMPOSSIBLE = Long.MAX_VALUE / 4` 가 "갈 수 없음"을 뜻하고, /4 의 여유가 덧셈 오버플로를 막는다.

> **오버플로(overflow, 넘침)** — 계산 결과가 자료형의 최댓값을 넘어 값이 조용히 뒤집히는 것.\
> 예: `Long.MAX_VALUE` 에 비용을 한 번만 더해도 음수가 되어 min 비교가 망가진다.

#### 3. 트리 DP — 최대 독립 집합 (TODO 9~12)

**정답 코드 (impl 기준, 핵심부)**

```java
public static long maxIndependentSet(Tree tree, CountedTable table) {
    if (tree.size() == 0) {
        return 0;
    }
    visit(tree, 0, -1, table);
    return Math.max(table.get(0), table.get(1));   // 뿌리의 두 칸 중 큰 쪽
}

private static void visit(Tree tree, int v, int parent, CountedTable table) {
    long withoutV = 0;
    long withV = tree.weight(v);
    for (int child : tree.neighbors(v)) {
        if (child == parent) {
            continue;                               // 무방향 간선: 부모를 거른다
        }
        visit(tree, child, v, table);
        // v 를 안 고르면 자식은 골라도 되고 안 골라도 된다. 큰 쪽을 쓴다.
        withoutV += Math.max(table.get(child * 2), table.get(child * 2 + 1));
        // v 를 고르면 자식은 못 고른다.
        withV += table.get(child * 2);
    }
    table.set(v * 2, withoutV);        // 칸 0: v 를 안 고른 경우
    table.set(v * 2 + 1, withV);       // 칸 1: v 를 고른 경우
}
```

```
표 = 정점마다 두 칸
  table[v*2]   = v 를 안 고를 때, v 서브트리의 최대 가중치 합
  table[v*2+1] = v 를 고를 때,   v 서브트리의 최대 가중치 합

      v 고름   -> 자식들 전부 "안 고름" 칸만
      v 안 고름 -> 자식마다 두 칸 중 큰 쪽

답 = max(뿌리 안 고름, 뿌리 고름)   <- 한 칸만 보면 틀린다
```

**질문별 답**

- Q: 상태는 정점마다 몇 칸이고 각 칸은 무엇을 담는가?\
  A: 두 칸이다.\
  `table[v*2]` = v 를 **안 고른** 경우 v 서브트리에서의 최대 가중치 합, `table[v*2+1]` = v 를 **고른** 경우의 그것.\
  "골랐나/안 골랐나"가 자식의 선택 가능 범위를 바꾸므로 둘을 따로 들어야 한다.\
  하나로 합치면 부모가 "자식이 골라졌는지"를 알 수 없어 이웃 동시 선택을 못 막는다.\
  실측: 정점 20개에서 표 쓰기 40번(= 20 × 2) — naive 재귀 28,655번과 716배 차이.

- Q: v 를 고르면 자식들은 어떻게 되고, 안 고르면 어떻게 되는가?\
  A: 고르면 자식들은 전부 못 고른다 — `withV += table.get(child * 2)` (자식의 "안 고름" 칸만).\
  안 고르면 자식은 자유다 — `withoutV += max(안 고름, 고름)` (자식마다 큰 쪽).\
  "이웃한 두 정점을 같이 못 고른다"는 제약이 부모-자식 간선에만 걸리기 때문이다.\
  자식끼리는 서로 이웃이 아니므로 각자 독립적으로 큰 쪽을 고르면 된다.

- Q: 답은 뿌리의 어느 칸인가 — 한 칸만 보면 왜 틀리는가?\
  A: `Math.max(table.get(0), table.get(1))` — 두 칸 중 큰 쪽이다.\
  뿌리를 고르는 것이 최적일 수도, 안 고르는 것이 최적일 수도 있다.\
  예: 뿌리 가중치가 아주 크면 고르는 쪽이, 뿌리는 작고 자식들이 크면 안 고르는 쪽이 이긴다.\
  "답이 표의 어느 칸에 있는지는 문제마다 확인한다" — 21번 LIS(마지막 칸 아님)와 같은 교훈이다.

> **독립 집합(independent set)** — 서로 이웃인 정점이 하나도 없는 정점들의 모음. "최대"는 가중치 합 기준이다.\
> 예: 뿌리를 고르면 그 자식들은 전부 못 고른다.

- Q: 무방향 간선이라 이웃 목록에 부모도 있는데 어떻게 거르는가?\
  A: 재귀에 부모 번호를 같이 넘기고, 이웃 순회에서 `if (child == parent) continue;` 로 건너뛴다.\
  addEdge 가 양쪽 목록에 서로를 넣으므로 v 의 이웃 목록에는 자식들 + 부모가 섞여 있다.\
  안 거르면 부모로 되돌아가 무한 재귀(StackOverflowError)가 난다.\
  뿌리는 부모가 없으므로 -1 을 넘긴다.

> **무한 재귀(infinite recursion)** — 끝나는 조건에 못 닿고 자기 호출이 계속 이어지는 것.\
> 예: 부모를 안 거르면 자식→부모→자식으로 오가며 StackOverflowError로 죽는다.

- Q: 부모를 정점 번호 하나로 기억하는 것으로 충분한 조건은 무엇인가?\
  A: 트리에 중복 간선(같은 두 정점을 잇는 간선 둘)이 없어야 한다.\
  중복 간선이 있으면 "부모와 같은 번호인 이웃"이 두 번 나와, 하나는 걸러지지만 실제로는 같은 간선을 두 번 세는 문제가 아니라 — 같은 child 로 두 번 내려가는 문제가 생긴다.\
  단순 트리(정점 n, 간선 n-1, 중복 없음)라는 전제 아래에서만 번호 비교가 안전하다.\
  전제가 다르면(다중 그래프) 간선 자체의 식별이 필요하다.

- Q: 왜 이 문제가 일반 그래프에서는 NP 난해한데 트리에서는 선형인가?\
  A: 사이클이 없어서 어떤 정점의 결정이 자기에게 돌아오지 않기 때문이다.\
  트리에서 v 의 결정은 자식 서브트리들에게만 영향을 주고, 서브트리들은 서로 겹치지 않는다 — 독립적으로 최적을 구해 더할 수 있다.\
  사이클이 있으면 v 의 결정이 이웃을 타고 돌아 다시 v 의 이웃에 도달한다 — "자식들이 독립"이라는 전제가 깨진다.\
  그래서 정점마다 두 칸, 총 O(n) 계산으로 끝난다 — 구조(사이클 없음)가 복잡도를 결정한다.

> **NP 난해(NP-hard)** — 사실상 모든 경우를 보는 것 이상의 방법이 알려지지 않은 문제 등급.\
> 예: 최대 독립 집합은 일반 그래프에서 NP 난해지만, 트리라는 특수 구조에서는 선형이다.

> **서브트리(subtree)** — 어떤 정점과 그 아래로 매달린 정점 전부.\
> 예: 트리에서는 형제들의 서브트리가 서로 겹치지 않아, 각자 최적을 구해 그냥 더할 수 있다.

- Q: naive 는 무엇을 인자로 넘기며 내려가고, 왜 같은 정점을 여러 번 계산하게 되는가?\
  A: `parentTaken`(부모를 골랐는가)을 넘긴다 — 골랐으면 자기는 "안 고름"만 가능하다.\
  부모 쪽에서 without 계산(자식에 false)과 with 계산(자식에 true)을 **따로** 재귀하므로, 같은 서브트리를 두 번씩 내려간다.\
  그 두 배가 깊이를 타고 곱해져 지수가 된다.\
  DP 판은 자식을 한 번만 방문하고 두 칸을 동시에 채워서 이 중복을 없앤다.

- Q: 트리 naive 의 호출 수가 피보나치 수열의 증가율(약 1.6배)과 같은 모양인 이유는?\
  A: (원본은 "피보나치와 같은 모양"까지만 — 전개는 내 추론) 사슬(경로) 트리에서 호출 수 점화식이 피보나치와 같아지기 때문이다.\
  "부모 안 골림" 상태의 호출 수 F(n) = 1 + F(n-1)(자식 false) + T(n-1)(자식 true), "부모 골림" 상태 T(n) = 1 + F(n-1).\
  대입하면 F(n) ≈ F(n-1) + F(n-2) — 피보나치 점화식이다.\
  그래서 증가율이 황금비 φ ≈ 1.6 으로 수렴한다.\
  실측: 정점 12→16→20 에서 608 → 4,179 → 28,655.

> **황금비 φ** — 약 1.618. 피보나치 수열에서 이웃 항의 비가 수렴하는 값이다.\
> 예: 호출 수가 피보나치 점화식을 따르면 정점이 하나 늘 때마다 약 1.6배씩 는다.

### B. 개념

- Q: (원본 생각해볼 것) 구간 DP 로 풀 수 있는 다른 문제(팰린드롬 분할, 돌 합치기)의 공통점은 무엇인가?\
  A: (원본에 답 없음 — 내 추론) "연속 구간에 대한 답을, 구간을 어디서 자르느냐/마지막에 무엇을 합치느냐로 더 짧은 두 구간의 답으로 쪼갤 수 있다"는 구조다.\
  돌 합치기: [i, j] 무더기를 하나로 합치는 최소 비용 — 마지막 합치기 자리 k 로 쪼갠다(행렬 곱과 거의 동형).\
  팰린드롬 분할: [i, j] 를 팰린드롬 조각으로 나누는 최소 분할 — 자르는 자리로 쪼갠다.\
  공통 조건: 원소의 순서가 고정되어 있고(재배열 불가), 쪼갠 두 구간이 서로 간섭하지 않는다.

- Q: (원본 생각해볼 것) 비트마스크는 n 이 몇까지 쓸 수 있고, 어디서 메모리가 터지는가?\
  A: impl javadoc 기준 n 이 20 을 넘으면 못 쓴다 — 2^n 이 백만을 넘기 때문이다.\
  표가 2^n × n 칸이다: n=20 이면 약 2,100만 칸 — long 8바이트면 표만 약 160MB 다(계산상).\
  n=25 면 8억 칸 이상이라 할당 자체가 안 된다 — 시간보다 **메모리**가 먼저 터진다.\
  상태 수가 지수인 DP 는 "지수를 없앤" 것이 아니라 "지수의 밑을 줄인" 것임을 기억할 것.

- Q: (원본 생각해볼 것) 트리 DP 로 트리의 지름을 구하려면 상태를 무엇으로 잡는가?\
  A: (원본에 답 없음 — 내 추론) 정점마다 "v 에서 자식 방향으로 내려가는 가장 긴 경로 길이(depth)"를 상태로 잡는다.\
  각 v 에서 자식들의 depth 중 가장 큰 두 개를 더한 것(+ 간선 비용)이 "v 를 꼭대기로 꺾이는 경로"의 최대다.\
  지름 = 모든 v 에 대해 그 값의 최댓값 — 답이 뿌리 칸이 아니라 전체 최댓값에 있는 또 하나의 예다.\
  상태는 한 칸(내려가는 최장)이지만 답 계산에 "위에서 본 조합"(두 자식 합)이 붙는 것이 독립 집합과 다른 점이다.

- Q: (원본 생각해볼 것) 사이클이 하나만 있는 그래프(선인장/유니사이클)에서는 어떻게 하는가?\
  A: (원본에 답 없음 — 내 추론) 사이클 위의 간선 하나(u-v)를 골라 끊으면 트리가 된다.\
  끊은 간선의 제약("u 와 v 를 같이 못 고른다")만 수동으로 보장하면 된다: "u 를 안 고른다"로 고정한 트리 DP 와 "v 를 안 고른다"로 고정한 트리 DP 를 각각 돌린다.\
  두 결과의 최댓값이 답이다 — 어느 쪽이든 u, v 동시 선택이 불가능해진다.\
  사이클이 여러 개면 이 고정이 지수로 늘어난다 — 그것이 일반 그래프가 NP 난해한 이유의 감각적 설명이다.

- Q: 21번 배낭의 상태와 이 챕터 세 문제의 상태는 "무엇이 같으면 합칠 수 있나"라는 관점에서 어떻게 이어지는가?\
  A: 전부 같은 질문의 답이다: "과거의 무엇이 미래의 답에 영향을 주는가 — 그것만 남기고 나머지는 버려라."\
  배낭: 담은 조합이 아니라 (몇 번째, 남은 무게)만 / 행렬 곱: 바깥이 아니라 구간 [i, j] 만.\
  외판원: 방문 순서가 아니라 (방문 집합, 현재 위치)만 / 트리: 서브트리 밖이 아니라 (정점, 골랐나)만.\
  상태 설계 = "미래에 영향을 주는 최소한의 과거"를 찾는 일이고, 그것이 이 챕터의 제목이다.

- Q: 배낭 56% → 외판원 23% — 채워지는 칸의 비율이 왜 더 떨어졌는가, 무엇을 시사하는가?\
  A: 상태를 넓게 잡을수록 도달 불가능한 조합의 비율이 커지기 때문이다.\
  외판원 표에는 "집합에 없는 도시에 서 있는" 상태, "0번을 안 지난 집합" 같은 애초에 안 생기는 칸이 훨씬 많다.\
  메모이제이션은 그 칸에 안 가지만, 타뷸레이션이면 그 빈 칸까지 전부 채운다 — 상태 공간이 넓을수록 메모이제이션의 상대 이득이 커진다.\
  "표 크기 = 실제 계산량"이 아니라는 것 — 복잡도 2^n × n 은 상한이고 실측(23%)이 실제다.

> **도달 불가능한 상태(unreachable state)** — 문제 규칙상 생길 수 없는 상태 조합.\
> 예: "집합에 없는 도시에 서 있다", "0번을 안 지난 집합" — 메모이제이션은 안 가고 타뷸레이션은 모르고 채운다.

- Q: 구간 DP 표 3,600칸 중 쓰기가 정확히 1,830(= n(n+1)/2)인 이유는?\
  A: 의미 있는 칸이 i <= j 인 구간뿐이기 때문이다.\
  n=60 에서 i <= j 인 (i, j) 쌍 = 60 × 61 / 2 = 1,830 — 대각선 포함 위쪽 삼각형만이다.\
  i > j 인 칸은 "끝이 시작보다 앞"이라 정의가 안 되고, 아무도 쓰지 않는다.\
  1차원으로 눌러 담은 n × n 표의 절반이 낭비다 — "알고 쓰는 것과 모르고 쓰는 것은 다르다"(README).

- Q: "순서를 찾는 비용이 아끼는 비용의 0.7%"라는 실측은 무슨 의사결정을 정당화하는가?\
  A: "실행 전에 계획을 세우는 비용은 거의 항상 이득"이라는 결정이다.\
  행렬 60개에서 최적 순서 탐색에 표 읽기 71,981번을 쓰고, 곱셈 10,382,856 → 134,863 으로 1,020만 회를 아꼈다.\
  찾는 비용(7만)이 아끼는 비용(1,020만)의 0.7% — 계획 비용이 실행 절약에 묻힌다.\
  DB 쿼리 옵티마이저가 실행 계획을 먼저 세우는 것과 같은 구조다 — 계획 단계의 DP 가 실행 단계의 낭비를 지운다.

- Q: 외판원 상태 (mask, at) 에서 at 를 빼고 mask 만 상태로 잡으면 왜 틀리는가?\
  A: 다음 이동의 비용이 "지금 어느 도시에 있는가"에 달려 있기 때문이다.\
  같은 집합을 방문했어도 현재 위치가 다르면 남은 여정의 최소 비용이 다르다 — cost[at][next] 의 at 가 상태에 필요하다.\
  mask 만 잡으면 서로 다른 미래를 가진 상태들이 한 칸에 합쳐져 틀린 답이 나온다.\
  상태 설계의 양방향 오류다: 순서까지 넣으면(과잉) 지수를 못 벗어나고, 위치를 빼면(과소) 답이 틀린다 — "미래에 영향을 주는 것은 전부, 그 외는 하나도"가 기준이다.
