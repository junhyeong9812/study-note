# algorithm/34-modern-codecs-lz4-zstd-brotli — 정답

## 정답

### 1. 코덱별로 밀어붙인 축

| 코덱 | 축 | 수단 |
|---|---|---|
| LZ4 | 속도 | 엔트로피 부호 없음, 바이트 정렬 시퀀스 형식(LZ4 Block format 문서) |
| zstd | 넓은 속도↔비율 범위, 작은 데이터 | 큰 윈도, 리터럴 허프만 + 시퀀스 FSE, repeat offset, 학습 사전(RFC 8878) |
| Brotli | 웹 텍스트 비율 | 문맥 모델링(직전 2바이트), 내장 정적 사전 122,784바이트, 윈도 최대 16MiB−16B(RFC 7932) |

- DEFLATE는 윈도 32KB, 기호당 정수 비트 허프만, 사전 지원이 약한 형식이다(zlib 프리셋 사전은 있다). 각 코덱이 이 한계 하나씩을 넘는다.

### 2. zstd 레벨을 올리면

notes.txt(3,522,642바이트) 실험:

```text
zstd --fast=4    1911287   1.84       55~56         64.0    19~25
zstd -3          1164010   3.03       87~113        40.4    25~28
zstd -19          914070   3.85     4325~4736        0.8    25~30
```

- 압축 시간: 55ms → 4,325ms. 약 80배.
- 크기: 1.91MB → 0.91MB. 크게 줄지만 -9 → -19 구간의 이득은 작아진다.
- 해제 시간: 19~30ms 안(재실행 18~32ms). 거의 그대로다. 해제기는 매치를 찾지 않고 엔트로피 복호(허프만·FSE) 뒤 토큰대로 복사하므로, 압축기가 탐색에 얼마나 공들였는지와 거의 무관하다(zstd README, RFC 8878 §3.1.1.3).
- 커지는 일: log.jsonl에서 zstd -1(1,662,097)이 -3(1,685,777)보다 작았다. 레벨은 노력의 양이지 결과 크기의 보장이 아니다. 내 데이터로 재야 한다.

### 3. LZ4 시퀀스

```text
  [token: 상위4=리터럴 길이 | 하위4=매치 길이−4]
  [리터럴 길이 추가 바이트(상위4가 15일 때)]
  [리터럴 바이트들]
  [offset 2바이트 리틀 엔디언]
  [매치 길이 추가 바이트(하위4가 15일 때)]
```

- 빠른 이유
  - 엔트로피 단계가 없다. 비트 단위 허프만 해석이 없다.
  - 모든 필드가 바이트 경계라 분기·시프트가 적다. 복사도 바이트 블록 단위다.
- offset 최대 65535(0은 손상된 블록), 최소 매치 길이 4(LZ4 Block format 문서).
- 대가: 비율이 낮다. README의 lzbench 표(Silesia)에서 LZ4 기본 2.101, zstd -1 2.883(zstd 1.4.0 기준)이다. 이 환경에서는 lz4를 실측하지 않았다.

### 4. 허프만 vs rANS

```text
p=0.90  huffman 125000 bytes   rANS 58573 bytes (0.4686 bits/sym)
p=0.50  huffman 125000 bytes   rANS 125004 bytes (1.0000 bits/sym)
```

- p = 0.9: 허프만 1비트/기호, rANS 약 0.469비트/기호. 엔트로피(0.469)에 붙는다.
- p = 0.5: 둘 다 1비트. 치우침이 없으면 어떤 엔트로피 부호도 줄일 것이 없다.
- 방향: rANS 인코딩은 상태 x에 기호를 "쌓는다". 마지막에 쌓은 기호가 가장 위에 있다. 디코딩은 x에서 기호를 "꺼낸다". 그래서 스택처럼 거꾸로다. 실험 코드도 인코딩은 `i = n−1`부터, 디코딩은 0부터 돈다. RFC 8878 §4.1도 FSE 비트스트림을 끝에서부터 읽는다고 적는다.

### 5. 작은 레코드 세 방식

```text
  zstd -3 each        :  159773 bytes  ratio 1.10
  zstd -3 each + dict :   57874 bytes  ratio 3.03
  zstd -3 batch(1000) :   28355 bytes  ratio 6.18
```

- ① 하나씩: 1.10배. 레코드 안에 참조할 과거가 거의 없다. 헤더·체크섬 비용이 상대적으로 크다.
- ② 사전: 3.03배. 사전 내용이 레코드 앞의 "과거"가 되어 키 이름·형식 조각을 역참조한다. 엔트로피 표도 사전에 들어 있다(RFC 8878 §5).
- ③ 배치: 6.18배. 앞 레코드들이 그대로 과거가 된다. 사전보다 더 가까운, 정확히 같은 분포의 과거다.
- 선택: 배치가 가능하면 배치. 레코드 단위로 꺼내야 하면(키-값 저장, 개별 메시지) 사전.

### 6. zstd 프레임 헤더와 FCS

- 매직 `0xFD2FB528`(파일에는 `28 b5 2f fd`) → 프레임 헤더(윈도 기술자, 선택적 Dictionary_ID, 선택적 Frame_Content_Size) → 블록들 → 선택적 체크섬(XXH64 하위 4바이트)(RFC 8878 §3.1.1).
- 파이프 입력은 압축을 시작할 때 전체 크기를 모른다. 그래서 FCS를 적지 않았다. 실험: 파일 입력은 `Decompressed Size: 10.0 MiB (10506647 B)`가 있고, 파이프 입력은 그 줄이 없다.
- 영향: 받는 쪽이 출력 버퍼 크기를 미리 알 수 없다. 스트리밍으로 조금씩 풀어야 한다. FCS가 있어도 공격자가 적은 값일 수 있으니 해제 상한은 따로 둔다(33번의 폭탄 방어와 같다).

### 7. Brotli 정적 사전·문맥 모델링

- 정적 사전: RFC 부록 A의 122,784바이트 배열. 거리가 "지금까지의 출력"보다 크면 사전 단어 참조로 해석한다. 단어마다 121가지 변형이 있다(§8).
  - 효과: 처음 보는 짧은 문서도 첫 바이트부터 흔한 단어를 역참조한다. 작은 HTML·JS에서 "과거가 없음" 문제가 줄어든다.
- 문맥 모델링: 직전 두 바이트(p1, p2)로 Context ID(0..63)를 구하고, 그에 맞는 허프만표로 다음 리터럴을 부호화한다(§7.1). 문맥에 따라 다른 분포를 쓰니 기호당 비트가 준다.
- CLI 기본 품질: **11(최고)**(`brotli.md`: `--best` = 기본 = `-q 11`).
  - 함정: 빌드 시 한 번 압축하는 정적 파일에는 맞다. 이 설정을 요청마다 압축하는 동적 응답에 옮기면 CPU가 포화된다.
- 이 환경에서 Brotli는 실측하지 않았다(RFC·문서 근거).

### 8. Dictionary mismatch

- 원인: 프레임에는 사전 자체는 없고 사전 ID만 있을 수 있다(RFC 8878 §5, "대역 밖"). DictID는 선택 필드라(§3.1.1.1.3) 없으면 디코더가 쓸 사전을 따로 알아야 한다. 이 실험 프레임에는 DictID가 있었다. 생산자는 새 사전(v2)으로 압축했는데 소비자는 옛 사전(v1)만 가지고 있다. 실험에서 v1으로 압축한 프레임을 v2나 사전 없이 풀면 `Decoding error (36) : Dictionary mismatch`가 났다.
- 안전한 배포 순서
  1. 새 사전을 저장소에 추가한다(옛 사전 유지).
  2. **소비자**가 새 사전을 알게 배포한다. DictID로 골라 쓰게 한다.
  3. 그 뒤에 **생산자**를 새 사전으로 바꾼다.
- 보관: 그 사전으로 압축된 데이터가 하나라도 남아 있으면 사전을 지우지 않는다. 장기 보관 데이터는 사전을 함께 저장하거나 사전 없이 압축한다.
- 진단: 실패 로그에 프레임의 DictID(`zstd -lv`의 `DictID:`)를 남긴다. JDK zlib은 틀린 사전에 메시지 `null`인 `IllegalArgumentException`만 던지므로(실험) 기대 Adler-32(`Inflater.getAdler()`)를 직접 로그에 남겨야 한다.

### 9. 큰 윈도와 해제 거부

- 일어난 일: `--long=30`은 윈도 1 GiB다. 10.5MB 로그를 20번 이어 붙인 데이터에서 10.5MB 뒤의 반복까지 참조해 33.2MB → 1.65MB가 됐다. 해제기도 1 GiB 윈도를 잡아야 한다.
- zstd CLI는 기본 해제 메모리 상한 128MiB를 넘는 프레임을 거부한다. 실험 출력: `Window size larger than maximum : 1073741824 > 134217728`, `Use --long=30 or --memory=1024MB`.
- 대처
  - 복구 절차 문서에 `--long=30`(또는 `--memory`)을 함께 적는다. 복구 서버 메모리를 확인한다.
  - 다른 시스템과 주고받는 데이터는 윈도를 8MB 이하로 둔다(RFC 8878 권고, HTTP는 RFC 9659 상한).
- 상한을 무작정 올리면 안 되는 이유: 그 상한이 곧 신뢰하지 않는 입력에 대한 메모리 방어선이다. 공격자가 큰 윈도를 선언한 프레임을 보내면 해제기가 그만큼 메모리를 잡는다.

### 10. 동적 응답에 최고 레벨

- 확인
  - CPU 프로파일에서 압축 함수가 상위인지.
  - 설정의 압축 레벨·품질. Brotli는 설정을 안 바꾸면 도구에 따라 최고 품질(CLI 기본 11)일 수 있다. 서버 모듈의 기본값은 따로 확인한다 [?] (모듈마다 다름).
  - 압축률 대비 시간. 실험에서 zstd -19는 log를 0.5MB/s, -3은 74MB/s로 압축했다. 크기 차이는 1,685,777 → 1,210,673(약 28%)이다.
- 바꿀 것
  - 동적 응답: 낮은 레벨(zstd 1~3, Brotli 낮은 품질, gzip 1~5 (예시)).
  - 작은 응답은 압축하지 않는 최소 길이.
  - 레벨 변경 전후로 p99와 CPU를 비교한다.
- 정적 자원: 빌드 단계에서 최고 레벨로 `.br`·`.zst`를 미리 만들고, 서버는 그대로 내보낸다(network/39 §2). 한 번 압축·여러 번 해제이고, 해제 속도는 레벨과 거의 무관하므로 높은 레벨의 비용이 한 번만 든다.
