### A. 문제 (src/main 의 TODO 1~10)

#### 1. 활동 선택 (TODO 1~3)

**정답 코드 (impl 기준, 핵심부)**

```java
public static List<Activity> select(List<Activity> activities, CountedChoices choices) {
    List<Activity> sorted = new ArrayList<>(activities);
    sorted.sort((a, b) -> {
        choices.compare();
        return Integer.compare(a.end(), b.end());   // 끝나는 시각 기준
    });

    List<Activity> chosen = new ArrayList<>();
    int lastEnd = Integer.MIN_VALUE;
    for (Activity a : sorted) {
        choices.examine();
        if (a.start() >= lastEnd) {   // 끝 시각에 시작해도 된다 (>=)
            choices.take();
            chosen.add(a);
            lastEnd = a.end();
        }
    }
    return chosen;
}
// selectByStart 는 정렬 기준만 a.start() 비교로 바꾼 것 — 틀리는 반례용
```

```
끝이 이른 것부터:                시작이 이른 것부터 (틀림):

      |--B--|                      |--A--| |--B--| |--C--|
```

**질문별 답**

- Q: 그럴듯한 세 기준(짧은 것·일찍 시작·일찍 끝남) 중 맞는 것은 무엇인가?
  A: "일찍 **끝나는** 것부터"만 맞는다.
  일찍 끝날수록 뒤에 남는 시간이 넓어져, 다음 선택의 여지가 가장 커진다.
  나머지 둘은 그럴듯하지만 반례가 있다 — 계약 테스트가 각각 틀리는 입력을 준다.
  "그럴듯한 기준이 여러 개인데 맞는 것은 하나뿐" — 그래서 증명 없이 그리디를 쓰면 안 된다.

- Q: "끝나는 시각이 이른 것부터"가 최적임을 교환 논증으로 어떻게 보이는가?
  A: 최적해가 우리와 첫 선택부터 다르다고 하자.
  우리가 고른 것은 가장 일찍 끝나는 활동이므로, 최적해의 첫 활동보다 늦게 끝나지 않는다.
  그러면 최적해의 첫 활동을 우리 것으로 **바꿔도** 나머지와 안 겹치고 개수도 그대로다.
  이 교환을 반복하면 최적해 전체를 우리 답으로 바꿀 수 있다 — 그러니 우리 답도 최적이다.

- Q: "안 겹친다"는 마지막으로 고른 활동의 무엇 하나만 기억하면 판정되는가?
  A: 마지막으로 고른 활동의 **끝 시각**(lastEnd) 하나다.
  끝 시각 순으로 정렬되어 있으므로, 새 활동이 마지막 것과 안 겹치면 그 앞의 것들과도 안 겹친다.
  판정은 `a.start() >= lastEnd` 한 번 — 고른 목록 전체를 다시 볼 필요가 없다.
  이 "하나만 기억하면 된다"가 한 번 훑기(O(n))를 가능하게 하는 핵심이다.

- Q: 시작 시각이 이전 끝 시각과 같으면 겹치는가 — 그것은 누가(알고리즘/문제) 정하는 것인가?
  A: **문제(계약)가 정한다.** 알고리즘이 정하는 것이 아니다.
  이 문제는 "끝나는 시각에 다음 것이 시작해도 된다"고 못박았고, 그래서 코드가 `>` 가 아니라 `>=` 다.
  반대 계약(끝 순간도 점유)이면 `>` 로 바뀌어야 한다 — 코드 한 글자가 계약에서 나온다.
  경계 규칙을 계약으로 먼저 정하지 않으면 테스트도 구현도 기준이 없다.

- Q: 시작이 이른 것부터 고르는 판은 어떤 입력에서 틀리는가?
  A: 아주 긴 활동 하나가 제일 먼저 시작하는 입력이다.
  예: (0, 100) 과 (1,2), (3,4), (5,6) — 시작 기준은 (0,100) 을 먼저 골라 나머지를 전부 막는다.
  답 1개 vs 최적 3개.
  "일찍 시작했다"는 뒤에 무엇을 남기는지와 무관하다 — 기준이 미래의 여지를 안 본다.

- Q: "짧은 것부터" 기준이 틀리는 입력은 어떤 모양인가?
  A: 짧은 활동 하나가 긴 활동 두 개에 걸쳐 있는 모양이다.
  예: (1,5), (4,7), (6,10) — 짧은 것 기준은 가운데 (4,7) 을 먼저 골라 양쪽을 다 막는다.
  답 1개 vs 최적 2개((1,5) + (6,10)).
  짧다는 것도 "뒤에 남는 여지"의 보증이 아니다 — 끝나는 시각만이 그것을 보증한다.

- Q: 정렬을 빼면 select 의 비용은 얼마이고, 실측에서 실제 비용은 어디에 있었는가?
  A: 정렬을 빼면 O(n) — 후보를 정확히 한 번씩 보고 되돌리지 않는다.
  실측(활동 10만): 본 것 100,000(= n), 고른 것 7,905, 되돌린 것 **0**.
  실제 비용은 정렬이다 — 비교 1,534,897회(O(n log n)).
  그래서 전체는 O(n log n) 인데, 그리디 본체는 선형이라는 것이 측정으로 보인다.

#### 2. 동전 거스름돈 (TODO 4~6)

**정답 코드 (impl 기준, 핵심부)**

```java
public static int greedy(int[] coins, int amount, CountedChoices choices) {
    if (amount < 0) {
        throw new IllegalArgumentException("금액이 음수다: " + amount);
    }
    int used = 0;
    int remaining = amount;
    for (int coin : coins) {              // coins 는 내림차순
        choices.examine();
        while (coin <= remaining) {
            choices.take();
            remaining -= coin;
            used++;
        }
    }
    return remaining == 0 ? used : IMPOSSIBLE;
}

public static int optimal(int[] coins, int amount) {
    int[] best = new int[amount + 1];
    Arrays.fill(best, Integer.MAX_VALUE);
    best[0] = 0;
    for (int value = 1; value <= amount; value++) {
        for (int coin : coins) {
            if (coin <= value && best[value - coin] != Integer.MAX_VALUE) {
                best[value] = Math.min(best[value], best[value - coin] + 1);
            }
        }
    }
    return best[amount] == Integer.MAX_VALUE ? IMPOSSIBLE : best[amount];
}

public static int smallestCounterexample(int[] coins, int limit) {
    for (int amount = 1; amount <= limit; amount++) {
        if (greedy(coins, amount, new CountedChoices()) != optimal(coins, amount)) {
            return amount;
        }
    }
    return -1;   // "limit 까지 반례가 없었다" — "반례가 없다" 가 아니다
}
```

**질문별 답**

- Q: greedy 에서 다 쓰고도 금액이 남으면 무엇을 반환하는가?
  A: IMPOSSIBLE(-1) 이다 — `remaining == 0 ? used : IMPOSSIBLE`.
  가장 작은 동전까지 다 시도했는데 remaining 이 0 이 아니면 이 그리디로는 못 만든 것이다.
  개수 0 이나 예외가 아니라 **값으로** 실패를 알린다 — 호출자(반례 탐색)가 결과를 비교해야 하기 때문이다.
  주의: 그리디의 IMPOSSIBLE 은 "정말 못 만듦"이 아닐 수 있다 — (5,3) 의 6 처럼 그리디만 실패하는 경우가 있다.

- Q: 금액이 0 이면 답이 몇 개이고, 음수면 어떻게 하는가?
  A: 0 이면 0 개다 — while 이 한 번도 안 돌고 remaining == 0 이라 used = 0 을 반환한다.
  음수면 IllegalArgumentException 을 던진다 — "음수 금액을 거슬러 준다"는 입력 자체가 계약 위반이다.
  "못 만듦"(IMPOSSIBLE)과 "잘못된 입력"(예외)을 구분하는 것이 포인트다.
  optimal 도 같은 계약(음수 예외)을 지킨다 — 두 함수를 비교하는 코드가 있으므로 계약이 같아야 한다.

- Q: optimal 의 상태는 무엇이고, 21번 배낭과 어떤 점에서 같은 모양인가?
  A: 상태 = "금액 value 를 만드는 최소 동전 개수"(best[value]) — 표가 amount+1 칸이다.
  점화식: `best[value] = min over coin of best[value - coin] + 1` — "마지막에 어떤 동전을 썼나"로 쪼갠다.
  배낭과 같은 점: 어떤 조합으로 그 금액에 왔는지는 버리고 "남은 것"만 상태로 잡는다(최적 부분 구조).
  다른 점: 물건은 한 번씩(0-1)이지만 동전은 무한정 쓸 수 있어 같은 동전을 계속 빼도 된다.

- Q: 못 만드는 금액을 Integer.MAX_VALUE 로 표시할 때 무엇을 조심해야 하는가?
  A: MAX_VALUE 에 1 을 더하면 오버플로로 음수가 되어 min 이 그쪽을 골라버린다.
  그래서 impl 은 `best[value - coin] != Integer.MAX_VALUE` 를 확인한 뒤에만 +1 을 한다.
  "불가능"을 큰 값으로 표시하는 설계는 그 값이 산술에 섞이는 순간을 전부 막아야 한다.
  22번 외판원의 IMPOSSIBLE(Long.MAX_VALUE / 4) 거르기와 같은 계열의 방어다.

- Q: "못 만드는 금액"과 "그리디가 실패하는 금액"은 어떻게 다른가 — (5, 3) 화폐에서 7 과 6 의 차이는?
  A: 7 은 어떤 조합으로도 안 되는 "정말 못 만드는" 금액이다(5+3=8, 3+3=6, ...).
  6 은 3+3 으로 만들 수 있는데, 그리디는 5 부터 쓰고 남은 1 을 못 만들어 실패한다.
  즉 그리디의 IMPOSSIBLE 에는 두 가지가 섞여 있다: 진짜 불가능 vs 그리디의 선택 실수.
  둘을 가르는 방법이 optimal(DP)과의 대조다 — 그래서 이 박스에 두 구현이 나란히 있다.

- Q: (1, 3, 4) 화폐에서 6 원이 반례인 이유는(그리디 답과 최적 답)?
  A: 그리디는 4 를 먼저 쓰고 남은 2 를 1+1 로 채워 `4+1+1` = 3개.
  최적은 `3+3` = 2개.
  큰 동전을 먼저 쓰는 것이 나중 선택의 여지를 망가뜨린 것 — 교환 논증이 성립하지 않는 화폐다.
  실측: 1원을 포함한 무작위 화폐 300개 중 236개(79%)에서 이런 금액이 있었다 — 그리디가 되는 화폐가 오히려 특수하다.

- Q: smallestCounterexample 이 -1 을 돌려줬을 때 그것이 증명이 아닌 이유는?
  A: 1 부터 limit **까지만** 확인했기 때문이다.
  -1 은 "거기까지 반례가 없었다"이지 "반례가 없다"가 아니다 — limit+1 에 반례가 있을 수 있다.
  유한 확인은 반증(반례 발견)은 할 수 있어도 증명(반례 부재)은 못 한다.
  이 한계를 메서드 이름·문서에 적어두지 않으면 쓰는 쪽이 증명으로 착각한다 — README 가 별도 절로 강조한 함정이다.

- Q: 한국·미국 화폐에서 그리디가 되는 것은 일반적인 경우인가 특수한 경우인가?
  A: 특수한 경우다.
  무작위 화폐의 79%에서 그리디가 틀렸다 — 되는 쪽(정준 화폐)이 소수파다.
  한국(1,5,10,50,100,500)·미국(1,5,10,25) 화폐는 그리디가 되도록 **설계된** 체계다.
  "내 경험의 사례들에서 됐다"가 "일반적으로 된다"의 근거가 못 된다는 것을 수치로 보여주는 실측이다.

#### 3. 허프만 코딩 (TODO 7~10)

**정답 코드 (impl 기준, 핵심부)**

```java
public static long encodedBits(long[] frequencies, CountedChoices choices) {
    if (frequencies.length == 0) {
        return 0;
    }
    if (frequencies.length == 1) {
        // 글자가 한 종류면 코드 길이가 0 이 될 수 없다. 1 비트를 준다.
        return frequencies[0];
    }
    PriorityQueue<Long> heap = new PriorityQueue<>(Comparator.naturalOrder());
    for (long f : frequencies) {
        choices.examine();
        heap.add(f);
    }
    long total = 0;
    while (heap.size() > 1) {
        choices.compare();
        long a = heap.poll();          // 가장 적은 둘을
        long b = heap.poll();
        long merged = a + b;           // 합친다
        total += merged;               // 합친 값 = 그 두 덩어리가 한 단계 깊어진 비용
        choices.take();
        heap.add(merged);
    }
    return total;
}

public static long fixedLengthBits(long[] frequencies) {
    int symbols = frequencies.length;
    if (symbols <= 1) {
        return symbols == 0 ? 0 : frequencies[0];
    }
    int bitsPerSymbol = 32 - Integer.numberOfLeadingZeros(symbols - 1);  // ceil(log2 k)
    long total = 0;
    for (long f : frequencies) {
        total += f * bitsPerSymbol;
    }
    return total;
}
```

**질문별 답**

- Q: 트리를 안 만들고 "합칠 때마다 합을 누적"하면 왜 전체 비트 수가 되는가?
  A: 한 글자의 비트 수 = 트리에서 그 글자의 깊이이고, 합치기 한 번은 합쳐진 덩어리 속 모든 글자를 정확히 한 단계씩 깊게 만든다.
  그 한 단계의 비용 = 그 덩어리에 속한 글자들의 빈도 합 = 방금 만든 merged 값이다.
  글자마다 (깊이 × 빈도) 를 더한 총합은, 합치기마다의 merged 를 전부 더한 것과 같다.
  그래서 트리 구조를 들고 있을 필요가 없다 — 합계만 원하면 누적으로 충분하다.

- Q: 글자가 0 종류면 몇 비트이고, 1 종류면 왜 0 이 아닌가?
  A: 0 종류면 0 비트 — 부호화할 것이 없다.
  1 종류면 합치기가 한 번도 안 일어나 누적 합이 0 으로 나오는데, 그대로 두면 틀린다.
  코드 길이 0 짜리 부호는 "아무것도 안 쓰기"라서, 글자가 몇 번 나왔는지를 구분할 수 없다 — 복호화가 불가능하다.
  그래서 글자당 1 비트를 주어 `frequencies[0]` 을 반환한다 — 빼먹으면 계약 테스트가 잡는 경계다.

- Q: 글자 1 종류에서 코드 길이 0 을 허용하면 무엇을 못 하게 되는가?
  A: 복호화(원문 복원)를 못 한다.
  "AAAA" 를 0 비트로 부호화하면 수신 쪽은 빈 비트열에서 A 가 4번인지 400번인지 알 수 없다.
  부호의 계약은 "부호화한 것을 도로 풀 수 있다"인데 그것이 깨진다.
  합계 공식(합치기 누적)이 우연히 0 을 내는 것과 계약이 요구하는 답이 다른 경우 — 공식보다 계약이 먼저다.

- Q: 왜 "가장 적게 나오는 둘"을 합치는 것이 최적인가 — 교환 논증의 뼈대는?
  A: 가장 적게 나오는 두 글자는 어떤 최적 트리에서도 가장 깊은 곳에 형제로 있을 수 있다.
  거기 없다고 가정하면, 그 둘을 가장 깊은 자리의 두 글자와 바꿔치기할 수 있다 — 빈도 적은 것이 깊어지고 많은 것이 얕아지니 총 비트가 줄거나 같다.
  즉 원래 트리가 최적이었다면 바꿔치기해도 최적 — "그 둘이 가장 깊은 형제"인 최적 트리가 존재한다.
  그 둘을 합쳐 한 글자로 보면 글자가 하나 줄어든 같은 문제가 된다 — 활동 선택과 같은 모양(교환 논증 + 반복)이다.

- Q: 합치기는 정확히 몇 번 일어나는가, 그 수는 트리의 무엇과 같은가?
  A: 정확히 n−1 번이다(글자 n 종류).
  힙의 원소가 합치기마다 하나씩 줄어 n 개 → 1 개가 되기 때문이다.
  이 수는 잎 n 개짜리 이진 트리의 **내부 노드 수**와 같다 — 합치기 하나가 내부 노드 하나를 만든다.
  실측 "다섯"이 이것을 확인한다 — 알고리즘의 반복 횟수가 자료구조의 불변량과 일치하는지 세어보는 것.

- Q: 고정 길이 부호에서 글자 k 종류면 한 글자에 몇 비트가 필요한가?
  A: ceil(log2 k) 비트다 — k 가지를 구분하려면 2^비트 >= k 여야 한다.
  k = 20 이면 5비트(2^4 = 16 < 20 <= 32 = 2^5), k = 64 면 6비트.
  k 가 2 의 거듭제곱이 아니면 올림 때문에 일부 부호가 낭비된다.
  모든 글자가 같은 길이 — 빈도를 전혀 안 보는 것이 허프만과의 차이다.

- Q: 코드는 그 올림을 어떤 연산으로 구하는가?
  A: `32 - Integer.numberOfLeadingZeros(symbols - 1)` 이다.
  numberOfLeadingZeros 는 int 의 앞쪽 0 비트 수 — 32 에서 빼면 "그 수를 표현하는 데 필요한 비트 수"(최상위 1 의 위치)가 된다.
  symbols−1 에 적용하면 정확히 ceil(log2 symbols) 가 된다: symbols=2 → 1, 3 → 2, 4 → 2, 5 → 3.
  부동소수점 log 를 쓰지 않는 정수 연산이라 반올림 오차가 없다.

- Q: 허프만의 이득이 1.0배(전부 같은 빈도)에서 2.5배(2^i 치우침)까지 흔들리는 이유는?
  A: 허프만이 하는 일이 "자주 나오는 글자에 짧은 코드"인데, 빈도가 전부 같으면 짧게 줄 대상이 없기 때문이다.
  전부 같은 64종류: 모든 글자가 같은 깊이가 되어 고정 길이와 동일(1.0배, 38,400 비트).
  2^i 로 치우친 20종류: 압도적으로 잦은 글자가 아주 짧아져 2.5배(2,097,129 vs 5,242,875).
  "허프만을 쓰면 압축된다"가 아니라 "**데이터가 치우쳐 있으면** 압축된다"가 맞는 말이다 — 이득의 출처는 알고리즘이 아니라 데이터다.

### B. 개념

- Q: (원본 생각해볼 것) 활동에 가치가 있으면(가중 활동 선택) 그리디가 되는가, 안 되면 무엇으로 풀어야 하는가?
  A: (원본에 답 없음 — 내 추론) 안 된다.
  "일찍 끝나는 것"으로 바꿔치기하면 개수는 유지돼도 **가치 합**이 줄 수 있다 — 교환 논증의 "안 나빠진다"가 깨진다.
  반례: 가치 100짜리 긴 활동 하나 vs 가치 1짜리 짧은 활동 셋 — 개수 기준 그리디는 셋을 골라 가치 3 을 얻는다.
  DP 로 푼다: 끝 시각 정렬 후 "i 번째까지의 최대 가치 = max(i 를 버림, i 의 가치 + i 와 안 겹치는 마지막 활동까지의 답)" — 겹치지 않는 직전 활동은 이진 탐색으로 찾는다.

- Q: (원본 생각해볼 것) 쪼갤 수 있는 배낭(분할 배낭)에서는 왜 그리디가 맞는가 — 21번의 0-1 배낭과 무엇이 다른가?
  A: (원본에 답 없음 — 내 추론) 무게당 가치(값/무게)가 높은 것부터 담고, 마지막 물건은 **잘라서** 남은 자리를 정확히 채우면 되기 때문이다.
  교환 논증이 성립한다: 최적해에 비율 낮은 것이 들어 있다면 같은 무게만큼 비율 높은 것과 바꿔서 손해가 없다 — 쪼갤 수 있으니 "같은 무게만큼"의 교환이 항상 가능하다.
  0-1 배낭은 물건을 못 쪼개서 그 교환이 안 된다 — 무게가 안 맞으면 통째로 넣거나 빼야 하고, 그 순간 "안 나빠진다"가 보장되지 않는다.
  같은 문제 구조에서 "쪼갤 수 있냐" 하나가 그리디 가능/불가능을 가른다 — 제약 하나가 풀이법을 바꾸는 사례다.

- Q: (원본 생각해볼 것) 어떤 화폐가 정준인지 판정하려면 어디까지 확인하면 충분한가?
  A: (원본에 답 없음 — 외부에 알려진 결과, 본인 검증 필요) 유한 범위까지만 확인하면 충분하다는 정리가 있다.
  Kozen–Zaks 의 결과로, 반례가 존재한다면 가장 작은 반례는 가장 큰 동전 두 개의 합보다 작은 범위 안에 있다.
  그러니 smallestCounterexample 을 그 상한으로 돌려 -1 이면 "이 화폐는 정준"이라고 **증명**으로 승격할 수 있다.
  "유한 확인은 증명이 아니다"의 예외가 되는 조건은 "반례의 크기에 상한이 있다는 별도의 정리"다 — 상한 없는 유한 확인은 여전히 증명이 아니다.

- Q: (원본 생각해볼 것) 허프만 트리가 여러 개일 수 있는데 그래도 비트 수는 같은가?
  A: (원본에 답 없음 — 내 추론) 같다.
  같은 빈도가 여럿이면 어느 둘을 먼저 합치느냐에 따라 트리 모양(각 글자의 깊이 분포)은 달라질 수 있다.
  그러나 총 비트 수는 "최적 부호의 비용"이라는 하나의 값이고, 어느 허프만 트리든 그 최적값을 달성한다 — 교환 논증의 증명이 특정 트리가 아니라 비용에 대한 것이기 때문이다.
  encodedBits 가 트리 없이 합계만 내는 것이 이것과 맞물린다 — 트리는 여러 개라도 합계는 하나다.

- Q: 그리디와 13번 백트래킹의 결정적 차이는 무엇이고, 그것이 왜 지수와 선형을 가르는가?
  A: **되돌리기의 유무**다.
  백트래킹은 놓기와 되돌리기가 짝을 이룬다 — 안 되면 물리고 다른 갈래를 시도하므로 갈래가 곱해져 지수가 된다.
  그리디는 고르면 끝, 절대 되돌리지 않는다 — 실측: 활동 10만 개에서 되돌린 것 0번, 본 것 n 번.
  되돌리지 않아도 되는 **근거**가 교환 논증이다 — 증명이 없으면 되돌리지 않는 것은 그냥 도박이다.

- Q: 그리디와 DP(동전 실측 1,260배)는 무엇을 맞바꾸는 관계인가?
  A: **적용 범위와 비용**을 맞바꾼다.
  그리디는 화폐 6종류만 보고(1,260원 거스름), DP 는 1,260 × 6 = 7,560 칸을 채운다 — 1,260배 싸다.
  대신 그리디는 교환 논증이 성립하는 문제(정준 화폐)에서만 맞고, DP 는 최적 부분 구조만 있으면 항상 맞는다.
  "싸다는 것과 맞다는 것은 다른 이야기다" — 싼 쪽을 쓰려면 맞다는 증명이 선행돼야 한다.

- Q: "그럴듯한 기준이 여러 개"일 때 코드를 짜기 전에 무엇을 해야 하는가?
  A: 교환 논증을 시도한다 — "최적해의 선택을 내 선택으로 바꿔도 안 나빠지는가"를 설명해본다.
  설명이 되면 그리디를 쓰고, 안 되면 그 기준을 버린다(반례를 찾으면 더 빨리 버려진다).
  활동 선택의 세 기준 중 둘은 이 논증이 안 된다 — 긴 활동/걸친 활동 반례가 바로 나온다.
  "그럴듯하다"에서 멈추고 짜면 계약 테스트(반례 입력)가 잡는다 — 검증 순서를 코드 앞에 두는 습관의 문제다.

- Q: 허프만의 압축률이 알고리즘이 아니라 데이터에서 온다는 실측은 실무에서 무엇을 시사하는가?
  A: "이 기법을 쓰면 좋아진다"는 주장은 데이터 분포를 확인하기 전에는 믿을 수 없다는 것.
  같은 허프만이 치우친 데이터에서 2.5배, 균등 데이터에서 1.0배(이득 없음)였다.
  도입 전에 내 데이터의 분포를 재보는 것이 먼저다 — 벤치마크는 남의 데이터가 아니라 내 데이터로.
  캐시 적중률, 인덱스 효율, 압축률 등 "분포 의존적인 최적화" 전반에 같은 원리가 적용된다.

- Q: 활동 선택의 교환 논증과 허프만의 교환 논증은 어떤 공통 형태를 갖는가?
  A: "최적해가 내 첫 선택과 다르다고 가정 → 최적해의 그 부분을 내 선택으로 바꿔치기 → 나빠지지 않음을 확인 → 반복하면 내 답 전체가 최적"의 형태다.
  활동 선택: 최적해의 첫 활동 ↔ 가장 일찍 끝나는 활동 (개수 유지).
  허프만: 최적 트리의 가장 깊은 두 자리 ↔ 가장 적게 나오는 두 글자 (비트 수 줄거나 같음).
  공통 핵심은 "내 선택이 어떤 최적해의 일부일 수 있음"을 보이는 것 — 이것이 "되돌리지 않아도 된다"의 근거가 된다.
