### A. 과제 (TODO 1~10)

#### 1. 로무토 분할 (LomutoQuickSort, TODO 1~2)

기준 코드 (impl):

```java
private <T> void sort(CountedArray<T> a, int lo, int hi) {
    if (lo >= hi) return;
    int p = partition(a, lo, hi);
    sort(a, lo, p - 1);      // 피벗 자리 p 는 다시 안 본다
    sort(a, p + 1, hi);
}
private <T> int partition(CountedArray<T> a, int lo, int hi) {
    int i = lo - 1;                      // "작은 것들"의 끝. 시작은 구간 밖
    for (int j = lo; j < hi; j++) {      // hi(피벗)는 뺀다
        if (a.compare(j, hi) < 0) {      // 등호 없음
            i++;
            a.swap(i, j);
        }
    }
    a.swap(i + 1, hi);                   // 피벗을 경계 자리로
    return i + 1;
}
```

- 분할이 돌려준 자리는 이미 최종 위치인데, 그 자리를 재귀 범위에 넣으면 구간이 줄지 않는 경우가 생겨 **끝나지 않는다**(무한 재귀 → StackOverflow). 그래서 `p-1`, `p+1` 로 빼고 재귀한다.
- 처음에는 "피벗보다 작은 것"이 하나도 없으므로 그 구역의 끝은 구간 밖, 즉 `lo - 1` 이다. 하나 찾을 때마다 i 를 먼저 올리고 그 자리로 가져온다.
- `j < hi` — hi 는 피벗 자신이다. 포함하면 피벗을 자기 자신과 비교하게 된다(의미 없는 비교 + 등호 처리에 따라 오동작).
- 등호를 넣으면(`<= 0`) 같은 값이 전부 "작은 쪽"으로 몰린다. 전부 같은 배열이면 분할이 완전히 한쪽으로 쏠려 매번 n-1 대 0 — 최악 O(n^2)가 된다.
- 루프가 끝나면 `[lo..i]` 는 피벗보다 작은 것들, `[i+1..hi-1]` 은 크거나 같은 것들이다. 피벗(`hi`)을 그 경계인 `i + 1` 과 교환한다 — 왼쪽은 전부 자기보다 작고 오른쪽은 전부 크거나 같으니 그 자리가 정렬 후에도 변하지 않는 최종 위치다.
- 정렬된 입력에서는 마지막 원소(피벗)가 항상 구간의 **최댓값**이라 "큰 쪽"이 매번 텅 빈다. 구간이 1개씩만 줄어 비교 총합이 (n-1) + (n-2) + … = n(n-1)/2 — 정확히 선택 정렬의 비교 횟수.

#### 2. 3중앙값 + 호어 분할 (MedianOfThreeQuickSort, TODO 3~5)

기준 코드 (impl):

```java
private <T> void medianToFront(CountedArray<T> a, int lo, int hi) {
    int mid = lo + (hi - lo) / 2;
    if (a.compare(mid, lo) < 0) a.swap(mid, lo);
    if (a.compare(hi, lo) < 0)  a.swap(hi, lo);
    if (a.compare(hi, mid) < 0) a.swap(hi, mid);
    // 이제 a[lo] <= a[mid] <= a[hi]. 중앙값은 mid 에 있다.
    a.swap(lo, mid);
}
private <T> int partition(CountedArray<T> a, int lo, int hi) {
    medianToFront(a, lo, hi);
    int i = lo, j = hi + 1;
    while (true) {
        while (a.compare(++i, lo) < 0) { if (i == hi) break; }  // >= 피벗이면 멈춤
        while (a.compare(lo, --j) < 0) { if (j == lo) break; }  // <= 피벗이면 멈춤
        if (i >= j) break;
        a.swap(i, j);
    }
    a.swap(lo, j);   // j = 왼쪽 구역의 마지막
    return j;
}
```

- 세 번의 비교·교환으로 `a[lo] <= a[mid] <= a[hi]` 를 만들면 중앙값은 **mid** 에 있다. 그것을 `swap(lo, mid)` 로 lo 로 보내 피벗으로 삼는다.
- 정렬된 입력에서 앞·중간·뒤의 중앙값은 **정확히 구간의 가운데 값**이다 — 분할이 반반이 되어 로무토가 무너지던 입력에서 깊이 log n 이 잡힌다(정렬 1,000개에서 비교 10,542 vs 로무토 499,500 — 47배).
- 등호에서 멈추는 이유: 같은 값을 "지나쳐" 가면 전부 같은 배열에서 손가락이 끝까지 달려 분할이 한쪽으로 쏠린다(무한 루프/최악의 입구). 등호에서 멈추면 같은 값에서 양쪽이 번갈아 멈춰 교환하며 **분할이 반반**으로 나뉜다 — 계약 테스트의 "전부 같은 값" 입력이 이걸 검사한다.
- 엇갈리면(`i >= j`) j 는 왼쪽 구역(피벗 이하)의 마지막이다. 피벗(lo)을 j 와 교환해 경계에 앉히고 j 를 돌려준다.
- 위험한 쪽: 왼쪽 손가락 i — 피벗보다 작은 값만 계속 만나면 hi 를 넘어간다(`i == hi` 에서 break). 오른쪽 j 는 피벗 자신(lo)이 "작거나 같음"이라 lo 에서 자연히 멈추지만 방어로 `j == lo` 검사도 둔다.
- 로무토는 작은 값을 만날 때마다 교환하지만, 호어는 **어긋난 쌍(왼쪽의 큰 것 + 오른쪽의 작은 것)을 만났을 때만** 교환한다 — 한 번의 교환이 두 원소를 동시에 정리한다.

#### 3. 3분할 (ThreeWayQuickSort, TODO 6~7)

기준 코드 (impl):

```java
int lt = lo, gt = hi, i = lo + 1;
T pivot = a.get(lo);              // 값으로 든다. 인덱스는 교환 중에 바뀐다
while (i <= gt) {
    int c = a.compareTo(i, pivot);
    if (c < 0)      a.swap(lt++, i++);
    else if (c > 0) a.swap(i, gt--);   // i 는 안 올린다!
    else            i++;
}
// [lt..gt] 는 전부 피벗과 같다. 이미 제자리.
sort(a, lo, lt - 1);
sort(a, gt + 1, hi);
```

- 피벗을 인덱스(예: lo)로 들고 있으면 훑는 도중의 `swap(lt++, i++)` 가 lo 자리의 값을 바꿔버린다 — 비교 기준이 도중에 변한다. 그래서 `a.get(lo)` 로 **값을 복사해** 들고 `compareTo` 로 비교한다.
- 작으면: 작은 구역의 끝 바로 뒤(lt)와 교환하고 lt, i 둘 다 올린다. lt 자리에서 온 값은 이미 검사한 "피벗과 같은" 값이므로 i 를 올려도 된다.
- 크면: 큰 구역의 시작 바로 앞(gt)과 교환하고 gt 만 내린다. gt 에서 온 값은 **아직 안 본 값**이라 i 를 올리면 그 값을 검사하지 않고 건너뛴다.
- 같으면: 이미 가운데 구역의 연장선 위에 있다 — 그 자리가 맞으므로 i 만 올린다.
- 가운데 구역 `[lt..gt]` 는 전부 피벗과 같은 값 = 정렬상 서로 구별이 없고 위치도 확정이다. 재귀할 것이 없다.
- 값의 종류가 k 개면 재귀 한 층마다 한 종류(피벗과 같은 값 전체)가 통째로 빠진다 — 깊이가 **log k** 수준에 묶인다. 전부 같은 값(k=1)이면 한 번 훑고 끝: 비교 999, 교환 0, 쓰기 0.

#### 4. 퀵셀렉트 (QuickSelect, TODO 8~10)

기준 코드 (impl):

```java
public static <T> T select(CountedArray<T> a, int k) {
    if (k < 0 || k >= a.size())
        throw new IndexOutOfBoundsException("k=" + k + ", 길이=" + a.size());
    int lo = 0, hi = a.size() - 1;
    while (lo < hi) {
        int j = partition(a, lo, hi);
        if (j > k)      hi = j - 1;
        else if (j < k) lo = j + 1;
        else            return a.get(k);
    }
    return a.get(k);
}
```

- 검사를 지워도 배열 접근에서 결국 예외는 난다 — 하지만 그때는 이미 **배열 순서를 다 바꿔 놓은 뒤**다. 일을 시작하기 전에 `IndexOutOfBoundsException` 으로 막아야 부작용 없이 거부한다. "예외가 났다"만 확인하는 테스트는 이 차이(언제 났는가)를 못 잡는다 — README 함정.
- 세 경우: `j > k` → 답은 왼쪽에 있다, `hi = j - 1`. `j < k` → 답은 오른쪽, `lo = j + 1`. `j == k` → 그 자리가 답, 반환.
- 한쪽으로만 내려가는 꼬리 재귀인데 자바는 꼬리 재귀 최적화를 안 해준다 — 재귀로 두면 최악에서 깊이가 n 으로 쌓인다. 반복문이면 스택이 안 쌓인다.
- 루프가 끝나면(lo == hi) 구간이 1칸 = 그 칸이 k 번째다. 분할 과정에서 k 번째 자리는 확정돼 있으므로 `a.get(k)` 가 답이다.
- 분할마다 남은 구간이 (평균) 절반으로 줄고 한쪽만 본다: `n + n/2 + n/4 + ... → 2n` = 평균 O(n). 실측: 10,000개에서 31,995 vs 전체 정렬 161,944 — 약 1/5.
- 중복 코드 허용 이유: 이 문제집은 박스(챕터·클래스)마다 독립이고, 두 클래스는 서로 다른 것(정렬 vs 선택)을 가르친다. 추상화로 묶으면 학습 단위의 독립성이 깨진다 — 한 번 더 쳐보는 것이 손해가 아니다(뼈대 TODO 10 주석).

### B. 개념

#### 5. 생각해볼 것 (원본 README 이관)

- 무작위 피벗: 최악은 **사라지지 않는다** — 여전히 O(n^2) 인 실행이 존재한다. 다만 어떤 고정 입력도 최악을 "예약"할 수 없게 되어, 최악을 만날 확률이 무시할 만큼 작아질 뿐이다. (원본은 질문만 — 내 추론)
- 차이: "최악이 없다"(병합 정렬처럼 상한 보장)는 적대적 입력에도 안전하지만, "최악이 희귀하다"는 운(난수)에 기대는 것 — 보장이 필요한 자리(실시간·보안)에서는 다른 문제다. (원본에 근거 없음 — 내 추론)
- 짧은 쪽만 재귀 + 긴 쪽 반복: 재귀할 때마다 구간이 절반 이하로 줄어드는 것이 보장되므로 스택 깊이가 **O(log n)** 에 묶인다. 최악 시간이 나아지는 건 아니고 깊이(죽음)만 막는다. (원본은 질문만 — 내 추론)
- 3분할 + 3중앙값: `sort` 앞머리에서 medianToFront 로 중앙값을 lo 에 보낸 뒤 `pivot = a.get(lo)` 를 뜨면 된다. 잃는 것: 매 분할마다 비교·교환 3~4회의 고정 비용(보험료) — 중복 많은 입력에서의 압승 폭이 약간 줄어든다. 실제 라이브러리가 이 결합을 한다(README: "둘 다 필요하면 둘을 합쳐야 한다"). (결합 위치는 내 추론)
- 중앙값의 중앙값(median-of-medians): 최악 O(n)을 보장하지만 상수가 커서 평균 성능이 무작위/3중앙값 퀵셀렉트보다 한참 느리다 — 실무에서는 "평균 빠름 + 최악 희귀"가 "최악 보장 + 항상 느림"을 이긴다. (원본에 근거 없음 — 내 추론)

#### 6. 측정이 알려준 것 (파생)

- 정렬된 입력 + 마지막 원소 피벗 = 피벗이 항상 최댓값 → 분할이 n-1 대 0. 층마다 비교 (구간-1)이 n-1, n-2, … 로 내려가 총합 n(n-1)/2 — 선택 정렬과 같은 식이 되는 이유다(1,000개에서 499,500).
- 느림 vs 죽음: 정렬된 200개에서 로무토 깊이 214, 3중앙값 23. 200개면 그냥 느리지만, 수십만 개면 재귀 깊이가 스택 한계를 넘어 `StackOverflowError` 로 **프로세스가 죽는다** — 성능 문제가 아니라 가용성 문제.
- 3중앙값의 비용(무작위 200개에서 1,872 vs 로무토 1,464)은 피벗 셋 고르기가 매 분할 붙는 고정비다. 정렬된 입력이 들어오는 순간 47배로 회수된다 — 평시에 내는 **보험료**.
- 3분할에서 전부 같은 값이면 매 비교가 "같음" → i만 올라간다. 교환도 쓰기도 없이 한 번 훑고, 가운데 구역이 전체가 되어 재귀도 없다 — 비교 999, 교환 0, 쓰기 0. 로무토(499,500)와 500배.
- 중복이 없으면 가운데 구역이 항상 크기 1 — 3분할의 존재 이유가 사라진다. 그러면서 작은 값·큰 값을 만날 때마다 거의 매번 교환해 쓰기가 23,974 vs 7,212(3.3배)로 손해.
- 3분할이 첫 원소를 피벗으로 쓰므로 정렬된 입력에서 35,456 vs 3중앙값 10,542 — 중복 처리(분할 방식)와 피벗 선택(전략)은 **독립된 축**임을 숫자가 보여준다.
- 퀵셀렉트는 분할 후 한쪽만 보므로 일하는 구간이 n, n/2, n/4, … 로 줄어든다. 등비수열의 합이 2n — n 을 10배 늘렸을 때 비교 11.7배(n log n 이면 13.3배)라는 실측이 그 증거.

#### 7. 구조와 경계 (파생)

- 셋 다 **멀리 있는 원소끼리 교환**한다(로무토의 swap(i,j), 호어의 마주보는 교환, 3분할의 구역 교환). 같은 값을 건너뛰어 나르는 순간 상대 순서가 뒤집힌다 — 01번에서 선택 정렬이 안정을 잃는 것과 같은 이유.
- 병합은 합칠 때 일하므로 결과를 담을 **보조 배열 O(n)** 이 필요하다. 퀵은 쪼갤 때(분할) 제자리 교환으로 일하고 합치기가 공짜라 추가 메모리가 재귀 스택뿐이다.
- 병합의 분할은 **길이의 절반**(입력 값과 무관)이지만, 퀵의 분할은 **피벗 값**이 가른다 — 피벗이 극단값이면 분할이 0 대 n-1 로 쏠린다. 최악이 입력(과 피벗 전략의 궁합)에 달린 이유.
- 실무 데이터는 이미 정렬(또는 거의 정렬)된 경우가 많다 — "정렬된 입력에서 무너지는 판"(로무토, 그리고 첫 원소 피벗의 3분할)은 실무에서 위험하다. impl 주석이 이를 명시한다.
