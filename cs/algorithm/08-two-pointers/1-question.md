### A. 과제 (구현 대상 — src/main TODO 1~8)

#### 1. 두 수의 합 (TwoSum — TODO 1·2)

```java
/**
 * 합이 target 인 두 인덱스. 없으면 null.
 * 배열은 오름차순으로 정렬되어 있어야 한다.
 */
public static int[] findPair(CountedArray a, int target);

/** 합이 target 인 서로 다른 쌍의 개수. 같은 값이 여럿이면 그 조합만큼 센다. */
public static long countPairs(CountedArray a, int target);

// TODO 1: 양끝에서 하나씩 잡고 마주 보내라.
//   합이 target 보다 작으면 어느 쪽을 옮기나. 왜 반대쪽은 옮기면 안 되나.
//   지금 버리는 원소가 다른 어떤 짝에서도 답이 될 수 없다는 것을 설명할 수 있나.
//   두 int 를 더하면 넘칠 수 있다. 20 억 더하기 20 억은 int 로 무엇인가.
// TODO 2: 찾는 것이 아니라 세는 것으로 바뀌면 무엇이 달라지나.
//   [1, 1, 1, 2, 2] 에서 합이 3 인 쌍은 몇 개인가. 손으로 세어봐라.
//   남은 구간이 통째로 같은 값일 때(예: [2,2,2,2] 에서 합 4)는 위 방법이 안 통한다.
```

- 합이 target 보다 작으면 어느 쪽 포인터를 옮기는가, 반대쪽을 옮기면 왜 안 되는가?
- 포인터를 옮길 때 버리는 원소가 다른 어떤 짝에서도 답이 될 수 없다는 근거는 무엇인가?
- 루프 조건이 `lo < hi` 가 아니라 `lo <= hi` 면 어떤 입력에서 어떤 잘못된 답이 나오는가?
- 두 int 를 그냥 더하면 20억 + 20억은 무엇이 되고, 그러면 탐색이 어떻게 어긋나는가?
- 넘친 합이 우연히 target 과 같아지면 무슨 일이 생기는가?
- 답이 여럿일 때 어느 쌍이 나오는가 — 그것이 왜 계약의 일부인가?
- 개수를 셀 때 합이 맞은 자리에서 포인터를 한 칸씩만 옮기면 무엇을 놓치는가?
- `[1,1,1,2,2]` 에서 합 3 인 쌍은 몇 개이고, 그 개수는 무엇을 곱해서 나오는가?
- 남은 구간이 통째로 같은 값이면(`[2,2,2,2]` 합 4) 왜 곱셈이 안 통하고 무엇으로 세는가?
- 그 경우를 따로 처리하지 않으면 개수가 어떻게 잘못 나오는가?

#### 2. 세 수의 합 (ThreeSum — TODO 3·4·5)

```java
/**
 * 합이 0 인 세 값의 조합. 각 조합은 오름차순이고, 조합 자체도 오름차순으로 나온다.
 * 배열은 오름차순으로 정렬되어 있어야 한다.
 */
public static List<int[]> zeroTriplets(CountedArray a);

// TODO 3: 하나를 고정하고 나머지 둘을 TODO 1 처럼 찾는다.
//   바깥 루프는 어디까지 도나. n-1 까지 돌면 안쪽에 원소가 몇 개 남나.
// TODO 4: 중복을 만들지 마라. 만들고 나서 거르면 O(n^2) 가 아니게 된다.
//   같은 값을 첫 번째 자리에 두 번 고르면 무엇이 나오나.
//   조합을 하나 찾은 다음에도 할 일이 있다. 안 하면 [0,0,0,0] 에서 무엇이 나오나.
// TODO 5: 일찍 끝낼 수 있는 경우가 있다.
//   정렬되어 있는데 고정한 값이 양수면 뒤에는 무엇만 남아 있나.
```

- 하나를 고정하고 나머지를 투 포인터로 찾으면 왜 O(n³)이 O(n²)로 내려가는가?
- 바깥 루프는 어디까지 돌아야 하고, n-1 까지 돌면 무엇이 문제인가?
- 중복 조합을 만들고 나서 Set 으로 걸러도 답은 맞는데, 왜 그 방식이 안 되는가?
- 같은 값을 첫 번째 자리에 두 번 고르면 무엇이 나오는가?
- 조합을 하나 찾은 다음에도 해야 할 일은 무엇이고, 빠뜨리면 `[0,0,0,0]` 에서 무엇이 나오는가?
- 고정한 첫 값이 양수면 왜 그 자리에서 전체 탐색을 끝낼 수 있는가?
- 300개 입력에서 값이 7종류일 때와 2,000종류일 때 읽기가 40배 차이 나는 이유는?
- 전부 음수인 입력은 왜 바깥 루프의 범위 실수를 드러내는가?

#### 3. 물 담기 (MaxWater — TODO 6)

```java
/**
 * 물 담기. 기둥 둘을 골라 물을 담을 때 최대 넓이.
 * 넓이는 두 기둥 사이의 거리 곱하기 낮은 쪽 높이다.
 */
public static long largest(CountedArray heights);  // 기둥이 둘 미만이면 0

// TODO 6: 양끝에서 시작해 한쪽을 안으로 옮긴다. 어느 쪽인가.
//   그리고 그게 왜 옳은지 설명해봐라. 이게 이 문제의 전부다.
//   지금 왼쪽이 더 낮다고 하자. 왼쪽 기둥이 들어가는 짝 중 지금보다 나은 것이 있나.
//   두 높이가 같으면 어느 쪽을 옮기나. 왜 상관없나.
//   넓이가 int 를 넘길 수 있다. 높이 20 억에 거리 10 만이면 얼마인가.
```

- 두 기둥이 담는 넓이는 무엇과 무엇의 곱인가?
- 왜 낮은 쪽 포인터를 안으로 옮기는가 — 그 증명을 한 문장으로 쓰면?
- 높은 쪽을 옮기면 무엇이 잘못되는가?
- 두 높이가 같으면 어느 쪽을 옮기는가, 왜 상관없는가?
- `[0, 5, 0]` 의 답이 0 인 이유는 — "가장 높은 기둥을 쓰면 된다"는 짐작은 어디서 틀리는가?
- 높이 20억 기둥 10만 개에서 넓이 계산이 int 로 왜 터지고, 어떻게 막는가?
- "버려도 되는 이유"의 증명이 없으면 이 코드는 무엇이라 불러야 하는가?

#### 4. 제자리 중복 제거 (Dedup — TODO 7·8)

```java
/**
 * 정렬된 배열에서 중복을 없애고 남은 길이를 돌려준다.
 * 배열의 앞쪽 [0, 결과) 에 값이 들어 있고 그 뒤는 쓰레기다.
 */
public static int removeDuplicates(CountedArray a);

/** 같은 값을 최대 k 개까지만 남긴다. 비교 대상이 한 칸 더 앞이다. */
public static int removeExcess(CountedArray a, int k);

// TODO 7: 읽는 포인터와 쓰는 포인터를 따로 둔다.
//   읽는 쪽은 언제 나아가나. 쓰는 쪽은 언제 나아가나.
//   쓰는 쪽이 읽는 쪽을 앞지를 수 있나. 그럴 수 없다면 왜 그런가.
//   지금 값을 남길지 말지는 무엇과 비교해서 정하나.
// TODO 8: TODO 7 에서 "바로 앞에 쓴 값"을 무엇으로 바꾸면 되나.
//   아직 k 개를 안 썼을 때는 그 자리를 볼 수 있나. 어떻게 막나.
//   k 가 0 이나 음수로 들어오면 어떻게 하나.
```

- 읽는 포인터와 쓰는 포인터는 각각 언제 한 칸 나아가는가?
- 쓰는 쪽이 읽는 쪽을 앞지를 수 없는 이유는 무엇이고, 그 성질이 무엇을 가능하게 하는가?
- 지금 값을 남길지는 무엇과 비교해서 정하는가 — 원본의 직전 값과 마지막으로 쓴 값은 다를 수 있는가?
- 빈 배열이면 무엇을 돌려주는가?
- 1,000개(값 100종류)에서 쓰기가 남긴 개수보다 하나 적은 99번인 이유는?
- 중복이 하나도 없는 입력에서 999번 쓰는 낭비는 왜 생기고, 없애는 방법의 대가는 무엇인가?
- removeExcess 에서 비교 대상이 "바로 앞에 쓴 값"에서 어디로 바뀌는가?
- 아직 k개를 채우기 전(`write < k`)에는 왜 무조건 남기는가?
- k가 0이나 음수로 들어오면 어떻게 하는가?
- k=1 로 부르면 removeDuplicates 와 결과가 같은가?
