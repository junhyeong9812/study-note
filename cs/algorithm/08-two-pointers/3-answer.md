#### 1. 두 수의 합 (TwoSum — TODO 1·2)

impl 정답 코드 (findPair):

```java
public static int[] findPair(CountedArray a, int target) {
    int lo = 0;
    int hi = a.size() - 1;

    while (lo < hi) {
        // int 두 개를 더하면 넘칠 수 있다. 20 억 + 20 억은 int 로 음수다.
        long sum = (long) a.get(lo) + a.get(hi);
        if (sum == target) {
            return new int[] {lo, hi};
        }
        if (sum < target) {
            lo++;
        } else {
            hi--;
        }
    }
    return null;
}
```

처리 과정 — `[1, 3, 5, 7, 9]`, target 8:

```text
idx    0    1    2    3    4
     +----+----+----+----+----+
     |  1 |  3 |  5 |  7 |  9 |
     +----+----+----+----+----+
      lo^                  ^hi

[1] 1 + 9 = 10 > 8  → hi--   (9 는 남은 구간의 최소값 1 과 짝지어도 크다
                              → 9 가 들어가는 모든 짝을 통째로 버린다)
[2] 1 + 7 = 8       → 찾았다. [0, 3] 반환

3+5 도 8 이지만 1+7 이 나온다 — "양끝에서 먼저 만나는 쌍"이 계약이다.
```

impl 정답 코드 (countPairs — 합이 맞았을 때의 처리만 발췌):

```java
int left = a.get(lo);
int right = a.get(hi);
if (left == right) {
    // 남은 구간이 전부 같은 값이다. 그 안에서 두 개를 고르는 경우의 수다.
    long k = hi - lo + 1;
    count += k * (k - 1) / 2;
    break;
}
// 양쪽에서 같은 값이 몇 개씩인지 세고 곱한다.
long leftCount = 0;
while (lo <= hi && a.get(lo) == left) { leftCount++; lo++; }
long rightCount = 0;
while (hi >= lo && a.get(hi) == right) { rightCount++; hi--; }
count += leftCount * rightCount;
```

처리 과정 — `[1, 1, 1, 2, 2]`, target 3:

```text
     +----+----+----+----+----+
     |  1 |  1 |  1 |  2 |  2 |
     +----+----+----+----+----+
      lo^                  ^hi

[1] 1 + 2 = 3 ✓  양쪽 값이 다르다(1 ≠ 2)
    → 왼쪽에서 1 을 전부 센다: leftCount = 3 (lo 가 3 까지 전진)
    → 오른쪽에서 2 를 전부 센다: rightCount = 2 (hi 가 2 까지 후퇴)
    → count += 3 × 2 = 6
[2] lo(3) > hi(2) → 종료. 답 6

[2, 2, 2, 2] 에서 target 4 라면: 양쪽 값이 같다(left == right)
    → 남은 구간 전체가 같은 값 → k=4 개에서 2 개 고르기 = 4×3/2 = 6, break
```

**질문별 답**

- Q: 합이 target 보다 작으면 어느 쪽 포인터를 옮기는가, 반대쪽을 옮기면 왜 안 되는가?
  A: lo 를 오른쪽으로 옮긴다.
  합이 모자라면 더 큰 값이 필요한데, 지금 hi 는 남은 구간에서 가장 큰 값이다.
  hi 를 줄이면 합이 더 작아지기만 하므로 답에서 멀어진다.
  반대로 합이 크면 hi 를 줄인다 — 대칭이다.

- Q: 포인터를 옮길 때 버리는 원소가 다른 어떤 짝에서도 답이 될 수 없다는 근거는 무엇인가?
  A: 정렬 덕분이다. 합이 target 보다 작을 때의 lo 값은,
  남은 구간에서 가장 큰 hi 와 짝지어도 모자랐다.
  더 작은 값과 짝지으면 더 모자라므로 lo 가 들어가는 모든 짝이 탈락이다.
  이 "버려도 되는 이유"가 없으면 투 포인터가 아니라 그냥 운이다.

- Q: 루프 조건이 `lo < hi` 가 아니라 `lo <= hi` 면 어떤 입력에서 어떤 잘못된 답이 나오는가?
  A: `[5]` 에서 target 10 을 찾으면 lo = hi = 0 인 상태로 한 바퀴 돌아
  5 + 5 = 10 으로 자기 자신과 짝을 지어 `[0, 0]` 을 돌려준다.
  같은 원소를 두 번 쓸 수는 없으므로 정답은 null 이다.
  테스트 `missingPair` 가 정확히 이 입력을 준다.

- Q: 두 int 를 그냥 더하면 20억 + 20억은 무엇이 되고, 그러면 탐색이 어떻게 어긋나는가?
  A: int 최대(약 21억)를 넘어 음수가 된다.
  음수는 target 보다 작다고 판정되므로 lo 를 옮겨 답을 지나친다.
  그래서 더하기 전에 `(long) a.get(lo) + a.get(hi)` 로 long 승격을 한다.
  테스트가 `[2_000_000_000, 2_000_000_001]` 을 실제로 준다.

- Q: 넘친 합이 우연히 target 과 같아지면 무슨 일이 생기는가?
  A: 없는 답을 찾았다고 한다 — 답을 놓치는 것보다 나쁘다.
  40억1 은 int 로 -294,967,295 인데, target 이 딱 그 값이면
  int 덧셈 구현은 그 쌍을 정답이라고 돌려준다.
  테스트의 두 번째 단언 `findPair(a, -294967295) == null` 이 이 경우다.

- Q: 답이 여럿일 때 어느 쌍이 나오는가 — 그것이 왜 계약의 일부인가?
  A: 양끝에서 먼저 만나는 쌍이다. `[1,3,5,7,9]` 합 8 은 3+5 가 아니라 1+7.
  알고리즘의 진행 순서가 결과를 결정하므로,
  "답이 여럿이면 어느 것"인지를 정해두지 않으면 테스트를 쓸 수 없다.
  그래서 진행 순서 자체가 계약이 된다.

- Q: 개수를 셀 때 합이 맞은 자리에서 포인터를 한 칸씩만 옮기면 무엇을 놓치는가?
  A: 같은 값이 여럿일 때의 조합을 놓친다.
  `[1,1,1,2,2]` 합 3 에서 한 칸씩만 옮기면 (1,2) 를 두 번밖에 못 세는데
  실제로는 1 이 3개 × 2 가 2개 = 6쌍이다.
  그래서 합이 맞으면 양쪽에서 같은 값의 개수를 다 세고 곱한다.

- Q: `[1,1,1,2,2]` 에서 합 3 인 쌍은 몇 개이고, 그 개수는 무엇을 곱해서 나오는가?
  A: 6개다. 왼쪽 값 1 의 개수(3)와 오른쪽 값 2 의 개수(2)의 곱이다.
  인덱스가 다르면 다른 쌍으로 세므로 3 × 2 의 모든 짝이 유효하다.
  테스트 `countsWithManyDuplicates` 의 첫 단언이 이 값이다.

- Q: 남은 구간이 통째로 같은 값이면(`[2,2,2,2]` 합 4) 왜 곱셈이 안 통하고 무엇으로 세는가?
  A: 왼쪽 묶음과 오른쪽 묶음이 같은 원소 집합이라 "양쪽"의 구분이 없어진다.
  k개 중에서 순서 없이 2개를 고르는 조합 수 `k(k-1)/2` 로 센다.
  `[2,2,2,2]` 는 4×3/2 = 6.
  impl 은 `left == right` 를 감지하면 이 식으로 세고 break 한다.

- Q: 그 경우를 따로 처리하지 않으면 개수가 어떻게 잘못 나오는가?
  A: 같은 쌍을 겹쳐 센다. README 표현으로는 개수가 두 배로 나온다
  (순서쌍으로 세면 k(k-1) = 12 — 정답 6의 두 배).
  테스트 주석은 곱셈을 그대로 쓰면 4×4 = 16 이 나온다고 지적한다.
  구현에 따라 틀린 값은 다르지만 어느 쪽이든 조합 수 6 이 아니다.

#### 2. 세 수의 합 (ThreeSum — TODO 3·4·5)

impl 정답 코드 (뼈대):

```java
for (int i = 0; i < n - 2; i++) {
    int first = a.get(i);
    // 같은 값을 첫 번째로 두 번 고르면 같은 조합이 또 나온다.
    if (i > 0 && first == a.get(i - 1)) {
        continue;
    }
    // 정렬되어 있으므로 첫 값이 양수면 뒤는 전부 양수다. 합이 0 이 될 수 없다.
    if (first > 0) {
        break;
    }
    int lo = i + 1;
    int hi = n - 1;
    while (lo < hi) {
        long sum = (long) first + a.get(lo) + a.get(hi);
        if (sum < 0) { lo++; }
        else if (sum > 0) { hi--; }
        else {
            out.add(new int[] {first, a.get(lo), a.get(hi)});
            // 찾은 다음에도 같은 값을 건너뛰어야 한다. 여기가 빠지면 중복이 나온다.
            int leftValue = a.get(lo);
            while (lo < hi && a.get(lo) == leftValue) { lo++; }
            int rightValue = a.get(hi);
            while (lo < hi && a.get(hi) == rightValue) { hi--; }
        }
    }
}
```

처리 과정 — `[-4, -1, -1, 0, 1, 2]` (정렬됨):

```text
     +----+----+----+----+----+----+
     | -4 | -1 | -1 |  0 |  1 |  2 |
     +----+----+----+----+----+----+
       i    lo                  hi

i=0 (-4): -4-1+2 = -3 < 0 → lo++ … 계속 모자람 → 짝 없음
i=1 (-1): -1-1+2 = 0 ✓ → [-1,-1,2] 기록
          → 왼쪽 같은 값(-1) 건너뛰기, 오른쪽 같은 값(2) 건너뛰기
          → -1+0+1 = 0 ✓ → [-1,0,1] 기록
i=2 (-1): 직전(i=1)과 같은 첫 값 → continue (같은 조합이 또 나온다)
i=3 (0):  0+1+2 = 3 > 0 → hi-- → lo == hi → 짝 없음
          (첫 값이 양수가 되는 순간 break — 뒤는 전부 양수라 합 0 불가)
결과: [-1,-1,2], [-1,0,1]  — 조합도, 조합 안도 오름차순
```

**질문별 답**

- Q: 하나를 고정하고 나머지를 투 포인터로 찾으면 왜 O(n³)이 O(n²)로 내려가는가?
  A: 바깥 루프가 n 번, 그 안의 투 포인터가 남은 구간을 한 번(O(n))만 지나간다.
  n × n = n² 이다. 삼중 루프는 안쪽 두 겹이 모든 짝(n²)을 다 보므로 n³.
  한 겹을 투 포인터로 바꾸면 차수가 정확히 하나 내려간다.
  측정: 300개에서 읽기 74,581 대 삼중 루프 13,365,300 — 179배.

- Q: 바깥 루프는 어디까지 돌아야 하고, n-1 까지 돌면 무엇이 문제인가?
  A: `i < n - 2`, 즉 n-3 까지다.
  첫 수 뒤에 최소 두 원소가 남아야 세 수가 되는데,
  n-1 까지 돌면 안쪽에 원소가 하나뿐이거나 없어서 아무 일도 못 하고 헛읽기만 한다.
  전부 음수인 입력(조기 종료가 안 걸리는 입력)에서 이 차이가 읽기 횟수로 드러난다.

- Q: 중복 조합을 만들고 나서 Set 으로 걸러도 답은 맞는데, 왜 그 방식이 안 되는가?
  A: 만드는 비용 자체가 복잡도를 무너뜨리기 때문이다.
  값이 몇 종류 안 되는 큰 배열에서는 같은 조합이 조합 수만큼 쏟아져
  O(n²)로 안 끝난다 — 계약 테스트가 정확히 그런 배열(300개, 값 7종류)을 준다.
  `[0,0,0,0,0,0]` 이면 6개를 만들었다 1개로 줄이는 꼴이다. 만들 때 안 만들어야 한다.

- Q: 같은 값을 첫 번째 자리에 두 번 고르면 무엇이 나오는가?
  A: 똑같은 조합이 또 나온다.
  첫 값이 같으면 남은 구간에서 찾는 두 값의 후보도 (부분집합이라) 같기 때문이다.
  그래서 `i > 0 && first == a.get(i-1)` 이면 continue —
  같은 첫 값은 첫 번째 것만 쓴다.

- Q: 조합을 하나 찾은 다음에도 해야 할 일은 무엇이고, 빠뜨리면 `[0,0,0,0]` 에서 무엇이 나오는가?
  A: lo 쪽과 hi 쪽 양쪽에서 지금 값과 같은 값을 전부 건너뛰어야 한다.
  빠뜨리면 [0,0,0] 을 찾은 뒤 lo·hi 만 한 칸씩 옮겨 또 [0,0,0] 을 만든다 —
  같은 조합이 여러 개 나온다.
  테스트 `allZeros` 가 "조합은 1개"를 단언한다.

- Q: 고정한 첫 값이 양수면 왜 그 자리에서 전체 탐색을 끝낼 수 있는가?
  A: 정렬되어 있으므로 첫 값 뒤의 원소는 전부 그 이상, 즉 전부 양수다.
  양수 셋의 합은 0 이 될 수 없으니 남은 바깥 루프 전체가 무의미하다.
  continue 가 아니라 break 인 이유다.
  이 조기 종료 때문에 전부 음수인 입력에서만 바깥 루프가 끝까지 돈다.

- Q: 300개 입력에서 값이 7종류일 때와 2,000종류일 때 읽기가 40배 차이 나는 이유는?
  A: 바깥 루프의 "같은 첫 값 건너뛰기"가 값 종류에 반응하기 때문이다.
  값이 7종류면 바깥 n번 중 대부분이 continue 로 즉시 넘어가
  안쪽 투 포인터가 몇 번 안 돈다. 측정: 1,681 대 67,523 읽기.
  정확성(중복 방지) 장치가 성능 장치이기도 한 사례다.

- Q: 전부 음수인 입력은 왜 바깥 루프의 범위 실수를 드러내는가?
  A: 양수가 섞여 있으면 `first > 0` 조기 종료가 먼저 걸려
  루프 끝 범위(n-2 대 n-1)의 차이가 실행되지 않아 안 보인다.
  전부 음수면 조기 종료가 한 번도 안 걸려 바깥 루프가 끝까지 돌고,
  한 칸 더 돌 때의 헛읽기가 측정(200개, 읽기 30,877)에 나타난다.

#### 3. 물 담기 (MaxWater — TODO 6)

impl 정답 코드:

```java
public static long largest(CountedArray heights) {
    int lo = 0;
    int hi = heights.size() - 1;
    long best = 0;

    while (lo < hi) {
        int left = heights.get(lo);
        int right = heights.get(hi);
        long area = (long) Math.min(left, right) * (hi - lo);
        if (area > best) {
            best = area;
        }
        // 같을 때는 어느 쪽을 옮겨도 된다. 둘 다 버려도 되기 때문이다.
        if (left < right) {
            lo++;
        } else {
            hi--;
        }
    }
    return best;
}
```

처리 과정 — 높이 `[1, 8, 6, 2, 5, 4, 8, 3, 7]` (테스트 그림):

```text
 8 |    #              #
 7 |    #              #     #
 6 |    #  #           #     #
 5 |    #  #     #     #     #
   +---------------------------
idx  0  1  2  3  4  5  6  7  8
    lo^                      ^hi

[1] min(1, 7) × 8 = 8   → best 8.  왼쪽(1)이 낮다 → lo++
    (왼쪽 1 을 쓰는 다른 짝: 거리는 8 보다 짧고 높이는 여전히 1 에 눌림
     → 전부 8 이하 → 통째로 버린다)
[2] lo=1(8), hi=8(7): min(8, 7) × 7 = 49 → best 49.  오른쪽(7)이 낮다 → hi--
[3] 이후로는 거리가 계속 줄어 49 를 넘는 짝이 안 나온다 → 답 49
    (최댓값 짝 = 1번 기둥(높이 8)과 8번 기둥(높이 7): 거리 7 × min 7 = 49)
```

**질문별 답**

- Q: 두 기둥이 담는 넓이는 무엇과 무엇의 곱인가?
  A: 두 기둥 사이의 거리(hi - lo)와 낮은 쪽 높이(min)의 곱이다.
  물은 낮은 기둥 위로는 못 올라오므로 높이는 항상 min 이 정한다.
  가운데 낀 기둥들은 넓이에 아무 영향이 없다.

- Q: 왜 낮은 쪽 포인터를 안으로 옮기는가 — 그 증명을 한 문장으로 쓰면?
  A: "지금 낮은 쪽 기둥을 고정한 채 반대쪽을 아무리 당겨도
  거리는 줄고 높이는 여전히 그 낮은 기둥에 눌려 있으므로,
  그 기둥이 들어가는 모든 짝은 지금 넓이를 못 넘는다 — 통째로 버려도 된다."
  이 한 문장이 이 문제의 전부다.

- Q: 높은 쪽을 옮기면 무엇이 잘못되는가?
  A: 거리도 줄고 높이도 늘 수 없다(높이는 낮은 쪽이 정하는데 낮은 쪽이 그대로다).
  즉 나아질 가능성이 0 인 방향으로 움직이면서,
  낮은 쪽이 들어가는 더 나은 짝을 탐색에서 놓칠 수 있다.
  낮은 쪽을 옮겨야 "버린 것 중에 답이 없다"가 보장된다.

- Q: 두 높이가 같으면 어느 쪽을 옮기는가, 왜 상관없는가?
  A: 어느 쪽이든 된다(impl 은 else 로 hi 를 옮긴다).
  양쪽 다 "낮은 쪽"이므로 위 증명이 양쪽 모두에 적용된다 —
  왼쪽이 들어가는 나머지 짝도, 오른쪽이 들어가는 나머지 짝도 지금을 못 넘는다.
  둘 다 버려도 되니 순서는 상관없다.

- Q: `[0, 5, 0]` 의 답이 0 인 이유는 — "가장 높은 기둥을 쓰면 된다"는 짐작은 어디서 틀리는가?
  A: 가운데 5 가 아무리 높아도 짝이 되는 반대쪽이 0 이면 min 이 0 이라 넓이가 0 이다.
  넓이를 정하는 것은 최대 높이가 아니라 "짝의 낮은 쪽"이다.
  높은 기둥 하나로는 물을 못 담는다 — 벽이 둘 필요하다.
  테스트 `zeroHeights` 가 이 짐작을 직접 반증한다.

- Q: 높이 20억 기둥 10만 개에서 넓이 계산이 int 로 왜 터지고, 어떻게 막는가?
  A: 넓이 = 20억 × 99,999 = 2 × 10¹⁴ — 높이도 거리도 int 에 들어가는데 곱이 안 들어간다.
  int 곱셈은 int 로 계산된 뒤 넘친 값이 나오므로,
  곱하기 전에 `(long) Math.min(left, right) * (hi - lo)` 로 한쪽을 long 으로 만든다.
  07번 매개변수 탐색의 수확량 넘침과 같은 모양이다.

- Q: "버려도 되는 이유"의 증명이 없으면 이 코드는 무엇이라 불러야 하는가?
  A: 운 좋은 휴리스틱(증명 없이 대충 잘 맞는 어림법)이다.
  결과가 맞아도 왜 맞는지 모르면 언제 틀리는지도 모른다.
  투 포인터는 항상 이런 "한쪽을 통째로 버려도 되는 논증"을 요구한다 —
  그 논증이 이 챕터가 실제로 시키는 일이다.

#### 4. 제자리 중복 제거 (Dedup — TODO 7·8)

impl 정답 코드:

```java
public static int removeDuplicates(CountedArray a) {
    int n = a.size();
    if (n == 0) {
        return 0;
    }
    // 0 번은 항상 남는다. 쓰는 자리는 1 부터 시작한다.
    int write = 1;
    for (int read = 1; read < n; read++) {
        int value = a.get(read);
        // 바로 앞에 쓴 값과 다르면 남긴다. 정렬되어 있으므로 그것만 보면 된다.
        if (value != a.get(write - 1)) {
            a.set(write, value);
            write++;
        }
    }
    return write;
}

public static int removeExcess(CountedArray a, int k) {
    if (k < 1) {
        throw new IllegalArgumentException("k 는 1 이상이어야 한다: " + k);
    }
    int n = a.size();
    int write = 0;
    for (int read = 0; read < n; read++) {
        int value = a.get(read);
        // 앞의 k 개가 이미 같은 값이면 이 값은 k+1 번째다. 버린다.
        if (write < k || value != a.get(write - k)) {
            a.set(write, value);
            write++;
        }
    }
    return write;
}
```

처리 과정 — `[1, 1, 2, 2, 2, 3]` (removeDuplicates):

```text
idx    0    1    2    3    4    5
     +----+----+----+----+----+----+
     |  1 |  1 |  2 |  2 |  2 |  3 |    0 번은 항상 남는다.
     +----+----+----+----+----+----+    write = 1, read = 1 에서 시작
      (남음) ^w,r

read=1: 1 == a[w-1](1) → 중복, 건너뜀 (read 만 전진)
read=2: 2 != 1 → a[1] = 2 쓰고 write = 2
read=3: 2 == a[w-1](2) → 건너뜀
read=4: 2 == 2 → 건너뜀
read=5: 3 != 2 → a[2] = 3 쓰고 write = 3

     +----+----+----+----+----+----+
     |  1 |  2 |  3 | (2)| (2)| (3)|   반환 3. [0,3) 만 유효, 뒤는 쓰레기
     +----+----+----+----+----+----+
     write(3) <= read(6) 가 내내 성립 → 안 읽은 값을 덮은 적이 없다
```

처리 과정 — `[1, 1, 1, 2, 2, 3]`, k=2 (removeExcess):

```text
read=0: write(0) < k(2) → 무조건 남김. a[0]=1, write=1
read=1: write(1) < k(2) → 무조건 남김. a[1]=1, write=2
read=2: 1 == a[write-k] = a[0](1) → 이미 2 개 있는 값 → 버림
read=3: 2 != a[write-k] = a[0](1) → 남김. a[2]=2, write=3
read=4: 2 != a[write-k] = a[1](1) → 남김. a[3]=2, write=4
read=5: 3 != a[write-k] = a[2](2) → 남김. a[4]=3, write=5

결과 [1, 1, 2, 2, 3], 반환 5 — 1 은 3 개 중 2 개만 남았다
```

**질문별 답**

- Q: 읽는 포인터와 쓰는 포인터는 각각 언제 한 칸 나아가는가?
  A: read 는 매 칸 무조건 나아간다 — 전부 봐야 남길지 판단할 수 있다.
  write 는 남길 값을 만나 실제로 썼을 때만 나아간다.
  이 비대칭이 같은 방향 투 포인터의 뼈대다.

- Q: 쓰는 쪽이 읽는 쪽을 앞지를 수 없는 이유는 무엇이고, 그 성질이 무엇을 가능하게 하는가?
  A: 시작이 같고(1, 1), write 는 read 가 한 칸 갈 때 최대 한 칸 가므로
  `write <= read` 가 항상 성립한다.
  따라서 a[write] 에 써도 아직 안 읽은 자리를 덮는 일이 없다 —
  이 부등식 하나가 보조 배열 없이(제자리) 되는 근거의 전부다.

- Q: 지금 값을 남길지는 무엇과 비교해서 정하는가 — 원본의 직전 값과 마지막으로 쓴 값은 다를 수 있는가?
  A: impl 은 마지막으로 쓴 값 `a.get(write - 1)` 과 비교한다.
  정렬된 입력에서는 직전 원본 값 `a.get(read - 1)` 과 비교해도 결과가 같다(변종으로 확인).
  하지만 정렬 안 된 입력에서는 둘이 달라진다 —
  등가가 아니라 "정렬 전제 아래에서만" 등가다.

- Q: 빈 배열이면 무엇을 돌려주는가?
  A: 0 이다. impl 은 `n == 0` 이면 바로 return 0 한다.
  이 검사가 없으면 `write = 1` 에서 시작하는 코드가
  "남은 길이 1"을 돌려주거나 a.get(0) 에서 터진다.
  테스트 `tinyInputs` 가 빈 배열과 한 개짜리를 준다.

- Q: 1,000개(값 100종류)에서 쓰기가 남긴 개수보다 하나 적은 99번인 이유는?
  A: 0번 원소는 이미 제자리라 아예 안 쓴다(write 가 1에서 시작).
  나머지 99종류의 첫 원소만 한 번씩 쓰므로 99번이다.
  새 배열에 복사했다면 1,000번 썼을 것이다 —
  결과만 보면 같은 두 구현을 계측기의 쓰기 횟수가 구별한다.

- Q: 중복이 하나도 없는 입력에서 999번 쓰는 낭비는 왜 생기고, 없애는 방법의 대가는 무엇인가?
  A: 전 원소가 "남길 값"이라 write == read 인 자리에 자기 값을 다시 쓴다.
  "이미 제자리면(write == read) 건너뛴다" 분기를 넣으면 없어지지만,
  분기가 하나 늘고 중복이 많은 입력에서는 그 분기가 매번 헛돈다.
  어느 쪽이 나은지는 데이터를 알아야 정한다 — 02번 병합 정렬의 경계 비교와 같은 거래다.

- Q: removeExcess 에서 비교 대상이 "바로 앞에 쓴 값"에서 어디로 바뀌는가?
  A: k칸 앞에 쓴 값 `a.get(write - k)` 로 바뀐다.
  그 자리가 지금 값과 같으면 이미 같은 값이 k개 연속으로 남아 있다는 뜻이라
  지금 값은 k+1 번째 — 버린다. 개수를 따로 셀 필요가 없다.
  k=1 을 넣으면 removeDuplicates 의 비교식 그대로다.

- Q: 아직 k개를 채우기 전(`write < k`)에는 왜 무조건 남기는가?
  A: `write - k` 가 음수라 볼 자리가 없기 때문이다 — 검사하면 배열 밖 접근이다.
  `write < k || …` 의 단락 평가(왼쪽이 참이면 오른쪽을 안 본다)로 막는다.
  의미로도 맞다: 아직 k개를 안 썼으면 어떤 값이든 k개 초과일 수 없다.
  측정에서 k=3 의 읽기가 k=1 보다 2 적은(1,997 대 1,999) 이유가 이 건너뛰기다.

- Q: k가 0이나 음수로 들어오면 어떻게 하는가?
  A: `IllegalArgumentException` 을 던진다.
  "같은 값을 최대 0개 남긴다"는 전부 지우라는 뜻이 되어 이 문제의 계약 밖이고,
  음수는 아예 의미가 없다. 조용히 0을 돌려주는 것보다 즉시 거부가 낫다.
  테스트 `invalidK` 가 k=0 과 k=-1 모두에서 예외를 단언한다.

- Q: k=1 로 부르면 removeDuplicates 와 결과가 같은가?
  A: 같다. 비교식이 `a.get(write - 1)` 로 동일해진다.
  테스트 `kOneIsPlainDedup` 이 같은 입력에 두 함수를 돌려
  남은 길이와 내용이 같음을 단언한다.
  removeExcess 가 removeDuplicates 의 일반화라는 뜻이다 — "한 칸"이 "k칸"이 된 것뿐.

- Q: 정렬이 안 된 배열에서 두 수의 합을 찾으려면 — 정렬 비용(n log n)을 내는 것과 해시를 쓰는 것 중 어느 쪽인가?
  A: 한 번만 찾는다면 해시가 낫다 — 훑으면서 "target - 지금 값"이 이미 나왔는지 보면
  시간 O(n), 대신 추가 공간 O(n)이고 원본 인덱스도 그대로 보존된다.
  정렬(n log n)은 추가 공간을 아끼고, 이후 개수 세기·여러 target 질의처럼
  정렬을 계속 써먹을 일이 있을 때 이득이 남는다. (원본에 근거 없음 — 내 추론)

- Q: 네 수의 합은 어떻게 되나, 다섯은 — 어디서부터 다른 접근이 필요해지는가?
  A: 같은 틀의 확장이다 — 두 개를 고정하고 나머지를 투 포인터로 찾으면 O(n³),
  k 수의 합은 O(n^(k-1))이 된다.
  k가 커질수록 이 지수 증가가 감당이 안 되므로,
  "두 수 합들을 미리 해시에 넣고 반씩 맞추는" 식의 접근(4수 합 O(n²))이 필요해진다. (원본에 근거 없음 — 내 추론)

- Q: 물 담기에서 "낮은 쪽을 옮긴다"의 증명을 한 문장으로 쓸 수 있는가?
  A: "낮은 쪽 기둥을 고정한 채 반대쪽을 안으로 당기면 거리는 줄고
  높이는 여전히 그 낮은 기둥에 눌려 있으므로,
  그 기둥이 들어가는 모든 짝은 지금 넓이를 못 넘는다 — 통째로 버려도 된다."
  README 말대로, 이 문장을 못 쓰면 아직 이해한 것이 아니다.

- Q: 중복 제거의 읽기 횟수가 원소 수의 2배(1,998)다 — 1배로 줄일 수 있는가?
  A: 있다. 매 칸 `a.get(read)` 와 `a.get(write-1)` 두 번 읽어서 2배인데,
  "마지막으로 남긴 값"을 지역 변수에 들고 있으면 배열 읽기는 read 쪽 한 번만 남는다.
  정렬 전제 덕에 판정에 필요한 상태가 값 하나뿐이라 가능한 절약이다. (원본에 근거 없음 — 내 추론)

#### 6. 파생 질문 (서머리 기반)

**질문별 답**

- Q: 투 포인터가 이중 루프를 없앨 수 있는 조건을 한 문장으로 말하면?
  A: "포인터를 옮길 때 그쪽 원소가 들어가는 나머지 짝 전부를
  안 보고도 탈락시킬 수 있는 이유가 있을 것" — 그 이유가 문제마다 따로 있다.
  두 수의 합·물 담기는 정렬/최소 높이 논증이 그 이유고,
  이유를 설명 못 하면 우연히 맞는 코드다.

- Q: 양끝에서 마주 오기와 같은 방향으로 가기 — 각각의 성립 근거는 무엇에서 나오는가?
  A: 양끝 마주 오기의 근거는 정렬이다 — "지금 짝이 그 원소의 최선"이라는 보장이
  정렬에서 나와야 한쪽을 통째로 버릴 수 있다.
  같은 방향의 근거는 `write <= read` 부등식이다 —
  쓰는 쪽이 읽는 쪽을 앞지르지 않아 안 읽은 값을 덮지 않는다(그래서 보조 배열이 없다).

- Q: 이 챕터의 계측기는 왜 비교가 아니라 읽기를 세는가?
  A: 투 포인터의 요점이 "원소를 몇 번 보느냐"이기 때문이다.
  이중 루프는 같은 원소를 n번씩 다시 보고, 투 포인터는 대체로 한 번씩만 본다 —
  그 차이는 비교가 아니라 읽기에 나타난다.
  앞 챕터들의 비교 계수기 대신 CountedArray 가 reads/writes 를 센다.

- Q: n을 10배 늘리면 투 포인터와 이중 루프의 읽기는 각각 몇 배가 되는가?
  A: 투 포인터는 10배(198 → 1,998), 이중 루프는 100배(9,900 → 999,000)다.
  선형 O(n)과 제곱 O(n²)의 정의가 측정치로 그대로 보이는 것이다.
  n=1,000에서 격차는 500배이고, n을 10배 늘리면 격차도 10배가 된다.

- Q: 답이 맨 앞 두 개에 몰려 있으면 어느 쪽이 이기고, 그 거래는 04번 힙 정렬과 어떤 점이 같은가?
  A: 이중 루프가 이긴다 — 첫 쌍에서 맞아 읽기 2번, 투 포인터는 양끝에서
  좁혀 와야 해서 1,998번. 이 입력에서는 900배 느리다.
  투 포인터는 최악(n²)을 없애는 대신 최선(일찍 끝나기)을 포기한다 —
  04번 힙 정렬이 최악을 없애고 최선을 잃은 것과 같은 성격의 거래다.

- Q: 변종 실험에서 `a.get(write-1)` 을 `a.get(read-1)` 로 바꿔도 결과가 같은 이유와, 그 등가가 깨지는 조건은?
  A: 정렬돼 있으면 "직전 원본 값"과 "마지막으로 남긴 값"의 비교 결과가 같다 —
  건너뛴 원소는 전부 직전에 남긴 값과 같은 값들이기 때문이다.
  정렬 안 된 입력을 주면 둘은 달라진다 — 등가가 아니라 전제 딸린 등가다.
  전제를 지우는 리팩토링을 할 때 이런 자리가 조용히 깨진다.

- Q: 06번 이진 탐색과 이 챕터가 공유하는 전제는 무엇인가?
  A: 정렬 위에서 "보지 않고 버리기"다.
  이진 탐색은 비교 한 번으로 절반을 버리고(O(log n)),
  투 포인터는 포인터 이동 한 번으로 한 원소가 들어가는 짝 전부를 버린다(O(n)).
  둘 다 "버려도 되는 근거"가 정렬에서 나온다는 점이 같다.

- Q: 09번 슬라이딩 윈도우는 이 챕터의 어느 모양에서 나오는가?
  A: 같은 방향으로 가는 두 포인터에서 나온다.
  둘 다 앞으로만 가는 두 포인터 사이 구간을 "창(window)"으로 보면
  그것이 슬라이딩 윈도우다 — 서머리의 이웃 챕터 항목이 이 다리를 적어 두었다.
  양끝 마주 오기가 아니라 read/write 모양의 연장선이다.
