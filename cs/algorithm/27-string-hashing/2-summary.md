## 한눈에 — 쉽게 말하면

**문자열 해싱 = 긴 글 대신 짧은 "지문 번호"를 비교하기.**

- 두 문단이 같은지 알려면 한 글자씩 다 비교해야 한다. 대신 각 문단을 숫자 하나(해시)로 요약해 두면, 숫자 비교 한 번으로 끝난다.
- **지문이 다르면 원본도 확실히 다르다.** 하지만 반대는 아니다 — 다른 글이 우연히 같은 지문을 가질 수 있다(충돌). 그래서 지문이 같을 때만 원본을 실제로 비교해 **확인**한다.
- 창(부분 문자열)을 한 칸 옮길 때는 지문을 처음부터 다시 만들지 않는다. **나간 글자의 몫을 빼고, 들어온 글자를 더한다**(롤링 해시). 10번 누적 합처럼 경계만 손보는 구조다.
- 25번 KMP·26번 아호 코라식은 항상 정확한 알고리즘이다. 해싱은 다르다 — **틀릴 수 있는 판정을 싸게 만들고, 틀린 것만 걸러낸다.**

```text
  창을 한 칸 옮기기:  "abc" -> "bcd"

    (h - 'a'*B^2) * B + 'd'
     ~~~~~~~~~~~   ~~~   ~~~
     나간 글자 빼기  곱하기  새 글자 더하기      -> 창마다 O(1)
```

이 방식이 **똑같은 구조로** 파일 중복 검사, 표절 탐지, 대용량 로그에서 패턴 찾기에 쓰인다.

## 전체 흐름

```text
해시 정의        s[0]*B^(m-1) + s[1]*B^(m-2) + ... + s[m-1]  (mod 나머지)
   |             숫자가 금방 넘치니 법(mod)으로 나눈 나머지만 들고 다닌다
   v
롤링(굴리기)      창을 한 칸 옮길 때: 빼기·곱하기·더하기 세 번 = O(1)
   |
   v
라빈 카프        본문의 모든 창과 패턴의 해시를 비교
   |             해시 다름 -> 확실히 아님(건너뜀) / 해시 같음 -> 실제 비교로 확인
   v
응용             "두 번 이상 나오는 가장 긴 부분 문자열"
                 = 길이에 대한 이분 탐색(단조성) + 길이 판정을 굴리기로 O(n)
```

## 동작 — 롤링 해시 (`RollingHash`)

**언제 쓰나**: 같은 길이의 창을 옆으로 밀며 계속 비교해야 할 때.

`BASE=131`, 창 길이 3. `"abc"`의 해시는 `'a'*131² + 'b'*131 + 'c'`를 법으로 나눈 나머지다.

```text
  전 상태:  [a b c] d      h = 'a'*B^2 + 'b'*B + 'c'

  [1] 나간 글자 빼기    h - 'a'*B^2         맨 앞 글자에는 B^(m-1) 이 곱해져 있다
  [2] 전체에 B 곱하기   (h - 'a'*B^2) * B   남은 글자들의 자릿값이 한 칸씩 올라감
  [3] 새 글자 더하기    ... + 'd'

  후 상태:  a [b c d]      창마다 글자 연산 2번 = O(1), 창 길이 m 과 무관
```

그림 해설 (한 단계씩):

- 해시는 "B진법 수"라고 보면 된다. 맨 앞 글자의 자릿값이 `B^(m-1)`이다(`B^m`이 아니다 — 자리가 m개면 최고 자리는 m-1승).
- 법(mod)이 필요한 이유: `B^m`은 금방 어떤 정수 타입도 넘친다. 나머지만 들고 다니면 크기가 법 아래로 유지된다.
  - *법(modulus, mod)*: 나눗셈의 나머지를 취할 때 나누는 수. "시계가 12시를 넘으면 1시로 돌아오는" 것처럼 수를 일정 범위 안에 가둔다.
- **음수 함정**: 자바의 `%`는 음수를 그대로 준다(`(-5) % 3 == -2`). 빼기에서 음수가 나올 수 있으니 `+ mod`를 한 번 더해 양수로 만든다. 빼는 값이 이미 `% mod`를 거쳐 mod보다 작으므로 **한 번이면 반드시 충분하다.** `mod*mod`를 더해도 답은 같지만 법이 커지면 그쪽이 먼저 넘친다.
- 비용: 창 이동 1번에 O(1) — 빼고 곱하고 더하는 세 번뿐이라 창 길이가 비용에 안 들어간다.

## 동작 — 라빈 카프 (`RabinKarp.findAll`)

**언제 쓰나**: 본문에서 패턴이 나오는 모든 위치를 찾을 때 (KMP의 해시판).

본문 `"ababcab"`, 패턴 `"abc"`:

```text
  창       [aba] babc.. -> [bab] -> [abc] -> [bca] -> [cab]
  해시 비교   다름         다름     같음!      다름      다름
                                    |
                                    v
                          실제 문자열 비교로 확인
                          "abc" == "abc"  -> 위치 2 를 답에 추가
                          (만약 다르면: 충돌 — 헛일 1번 하고 버림)
```

그림 해설 (한 단계씩):

- 패턴의 해시를 한 번 계산해 두고, 본문의 창을 굴리며 해시끼리 비교한다.
- 해시가 다르면 **확실히** 패턴이 아니다. 건너뛴다 — 이 판정이 O(1)이라 싸다.
- 해시가 같으면 실제 문자열을 비교해 확인한다. 같으면 정답, 다르면 충돌(헛일)이다.
- **확인을 생략한 판(`findAllWithoutVerification`)은 원본에 반례로 들어 있다.** 충돌이 나면 없는 자리를 "찾았다"고 답한다.
- 비용: 평균 O(n + m) — 창마다 O(1) 해시 비교, 실제 비교는 해시가 같을 때만. 충돌이 잦으면(법이 작으면) 실제 비교가 늘어나 느려진다.

## 동작 — 가장 긴 중복 부분 문자열 (`DuplicateSubstring`)

**언제 쓰나**: 한 문자열 안에서 두 번 이상 나오는 가장 긴 조각을 찾을 때. 해시가 왜 필요한지 가장 잘 보여주는 문제다.

```text
  단조성:  길이 L 짜리 중복이 있으면 -> 그 일부인 길이 L-1 짜리도 반드시 있다

  가능    가능    가능    불가    불가    불가
  L=1     L=2     L=3     L=4     L=5     L=6      -> 경계를 이분 탐색 (06번)
                   ^
                   답

  "길이 L 되나?" 판정 = 길이 L 인 모든 창의 해시를 굴리며 해시맵에 담고,
                        같은 해시를 만나면 실제 비교로 확인      -> O(n)
```

그림 해설 (한 단계씩):

- "된다/안 된다"가 길이에 대해 단조로우므로, 답의 길이를 이분 탐색한다(O(log n)번 판정).
- 한 판정 안에서는 길이 L짜리 창 n-L+1개를 굴리며 해시맵에 시작 위치를 담는다. 같은 해시를 가진 위치들은 **목록(버킷)** 으로 담는다 — 충돌이 있을 수 있어서다.
- 같은 해시를 만나면 `regionMatches`로 실제 비교해 확인한다. 확인을 빼면 없는 답을 만들어낸다.
- 비용: O(n log n) — 판정 O(n) × 이분 탐색 O(log n). 해시 없이 부분 문자열을 만들어 비교하면 O(n² log n)이다.
- 원본의 변종 검증 기록: 이분 탐색 상한을 `hi = n-1`에서 `hi = n`으로 바꿔도 테스트가 통과하는데 **결함이 아니다** — 길이 n짜리 창은 하나뿐이라 중복일 수 없고 그 판정이 null을 주기 때문이다.

## 측정이 알려준 것 (원본 README 요약)

- **굴리기가 패턴 길이를 비용에서 없앤다.** 본문 10만·패턴 50글자에서 창마다 다시 계산하면 글자 연산 4,997,550번, 굴리면 200,000번 — 약 25배.
- **충돌은 실제로 일어난다. 법이 정한다.** 정답이 0개인 입력에서 법 101이면 충돌 955번 — 확인을 뺐다면 955개 전부 오답. 법 1,000,003이면 0.
- **법이 10억이어도 충돌 쌍은 존재한다.** `"dfdabcbhdfad"`와 `"edcgbcbgbbfd"`는 BASE=131, mod=10⁹+7에서 같은 해시다. **확률이 낮은 것과 불가능한 것은 다르다** — 입력을 남이 고를 수 있으면 확률 이야기는 의미가 없다.
- **법이 작으면 틀리는 게 아니라 느려진다.** (확인이 있으면) 답은 같지만 헛된 문자열 비교가 법 101에서 2천만 번 — 해시로 얻은 이득이 거의 사라진다. **확인은 정확성을, 큰 법은 속도를 지킨다. 하나를 빼면 각각 다른 방식으로 망가진다.**
- **이분 탐색 + 굴리기가 400배를 만든다.** 2만 글자에서 완전 탐색 약 2억 vs 488,463. 단조성과 O(n) 판정, **둘 중 하나만 있으면 안 된다.**

## 핵심 문장

- 해싱은 "틀릴 수 있는 판정을 싸게 만들고, 틀린 것만 확인해서 걸러내는" 구조다 — 해시가 다르면 확실히 다르고, 같으면 실제 비교로 확인한다.
- 롤링 해시는 누적 합과 같은 아이디어다: 전체를 다시 계산하지 않고 경계(나간 글자, 들어온 글자)만 손봐서 창 이동을 O(1)로 만든다.
- 확인은 정확성을 지키고, 큰 법은 속도를 지킨다 — 확인을 빼면 오답이 나오고, 법을 줄이면 헛비교가 폭발해 느려진다.
- 자바 `%`는 음수를 돌려주므로 빼기 뒤 `+mod` 한 번이 필요하고, 한 번이면 충분하다(빼는 값이 이미 mod보다 작으니까).
- 가장 긴 중복 부분 문자열은 "단조성 위의 이분 탐색 × 굴리기 O(n) 판정"의 합작이다 — O(n log n).

## 용어 풀이

- **해시(hash)**: 긴 데이터를 짧은 숫자 하나로 요약한 값. 지문 같은 것 — 지문이 다르면 원본도 다르지만, 지문이 같다고 원본이 같다는 보장은 없다.
- **충돌(collision)**: 서로 다른 문자열이 우연히 같은 해시를 갖는 것. 법으로 나눈 나머지를 쓰는 순간 피할 수 없다. 드문 것과 없는 것은 다르다.
- **확인(verification)**: 해시가 같을 때 실제 문자열을 비교해 진짜인지 검사하는 것. 이걸 빼면 "대부분 맞는" 알고리즘이 된다.
- **롤링 해시(rolling hash, 굴리기)**: 창을 한 칸 옮길 때 나간 글자를 빼고 새 글자를 더해 O(1)로 갱신하는 해시.
- **창(window)**: 본문 위에 놓인 고정 길이의 부분 문자열. 9번 슬라이딩 윈도우의 그 창이다.
- **기수(BASE, 기저)**: 해시를 만들 때 쓰는 진법의 밑. 글자마다 자릿값 `B^k`이 곱해진다. 알파벳 크기보다 커야 서로 다른 한 글자가 같은 값이 되지 않는다.
- **법(modulus, mod)**: 해시를 일정 범위에 가두려고 나머지를 취하는 수. 크면 충돌이 줄고(속도), 작으면 충돌이 늘어난다(헛비교).
- **라빈 카프(Rabin-Karp)**: 롤링 해시로 후보를 거르고 실제 비교로 확인하는 문자열 검색 알고리즘.
- **단조성(monotonicity)**: "L이 되면 L-1도 된다"처럼 한 방향으로만 변하는 성질. 이게 있어야 이분 탐색을 답에 댈 수 있다.
- **버킷(bucket)**: 해시맵에서 같은 해시를 가진 항목들을 담아두는 목록. 충돌을 다루기 위한 자리.
- **O(1) / O(n) / O(n log n)**: 데이터가 n개일 때 일의 양. O(1)은 한 번에 끝, O(n)은 개수에 비례, O(n log n)은 n에 "반씩 쪼개는 횟수"를 곱한 정도.
