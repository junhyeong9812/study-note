### A. 과제 (RollingHash·RabinKarp·DuplicateSubstring — TODO 1~6)

#### 1. 롤링 해시 (`RollingHash` — TODO 1~3)

**impl 정답 코드**

```java
/** 문자열 전체의 해시. */
public long hash(String s) {
    long h = 0;
    for (int i = 0; i < s.length(); i++) {
        hasher.charOp();
        h = (h * BASE + s.charAt(i)) % mod;
    }
    return h;
}

/** B^power mod m. */
public long basePower(int power) {
    long result = 1;
    for (int i = 0; i < power; i++) {
        result = result * BASE % mod;
    }
    return result;
}

/** 창을 한 칸 옮긴 해시. */
public long roll(long hash, char outgoing, char incoming, long topPower) {
    hasher.charOp();
    hasher.charOp();
    long without = (hash - outgoing % mod * topPower % mod + mod) % mod;
    return (without * BASE + incoming) % mod;
}
```

```
"abc" -> "bcd"  (BASE = B, 창 길이 3)

  h = 'a'*B^2 + 'b'*B + 'c'
  [1] 빼기    h - 'a'*B^2          나간 글자의 기여 제거 ('a' 의 자릿값 = topPower = B^2)
  [2] 곱하기  (h - 'a'*B^2) * B    남은 글자들의 자릿값이 한 칸씩 올라감
  [3] 더하기  ... + 'd'            새 글자는 1의 자리로
  = 'b'*B^2 + 'c'*B + 'd'          창마다 글자 연산 2번, 창 길이 m 과 무관
```

- Q: 해시를 `s[0]*B^(m-1) + ... + s[m-1]` 로 정의하는 것은 무엇에 비유되는가?
  A: 문자열을 **B진법 수** 하나로 읽는 것이다.
  글자가 숫자, 자리가 위치다 — 십진수 "234" 가 2×100 + 3×10 + 4 인 것과 같다.
  그래서 `hash` 는 호너 방식(`h = h * BASE + 글자`)으로 왼쪽부터 접으면 된다.

- Q: 법(mod)으로 나눈 나머지를 들고 다니는 이유와 그 대가는?
  A: `B^m` 이 금방 어떤 정수 타입도 넘치기 때문이다 — 나머지만 들면 크기가 법 아래로 유지된다.
  대가는 **충돌**이다. 서로 다른 문자열이 같은 나머지를 가질 수 있게 된다.
  법을 쓰는 순간 피할 수 없고, 그래서 확인(TODO 4)이 따라붙는다.

- Q: 맨 앞 글자의 자릿값이 `B^m` 이 아니라 `B^(m-1)` 인 이유는?
  A: 자리가 m 개면 최고 자리는 m-1 승이기 때문이다.
  십진수 3자리 수의 최고 자릿값이 10^3 이 아니라 10^2(백의 자리)인 것과 같다.
  그래서 `topPower = basePower(m - 1)` 이다 — `m` 을 넣는 것이 원본이 짚은 함정이다.

- Q: 창을 옮기는 세 단계는 각각 무엇을 하는가?
  A: 빼기 — 나가는 글자의 기여(`outgoing * topPower`)를 제거한다.
  곱하기 — 남은 글자들의 자릿값을 한 칸씩 올린다(`* BASE`).
  더하기 — 들어오는 글자를 1의 자리로 넣는다(`+ incoming`).
  10 번 누적 합이 구간 합을 뺄셈으로 구한 것처럼, 전체 재계산 없이 경계만 손본다.

- Q: 자바의 `%` 가 음수를 준다는 것은 어디서 문제가 되고, 어떻게 고치는가?
  A: 빼기 단계에서다 — `hash - outgoing*topPower` 가 음수일 수 있다.
  자바는 `(-5) % 3 == -2` 처럼 음수를 그대로 돌려주므로, 해시가 음수가 되어 같은 문자열끼리도 비교가 어긋난다.
  impl 은 `(hash - outgoing % mod * topPower % mod + mod) % mod` — 빼기 뒤 `+ mod` 한 번으로 양수로 만든다.

- Q: `+ mod` 한 번이면 반드시 충분한 이유는?
  A: 빼는 값이 이미 `% mod` 를 거쳐 mod 보다 작기 때문이다.
  그러면 `hash - 그값` 은 `-mod` 보다 크다(hash ≥ 0 이므로).
  `-mod < x` 에 mod 를 한 번 더하면 반드시 0 이상이 된다.
  "몇 번 더할지는 빼는 값의 범위를 보고 정한다" — 범위를 보면 한 번이 답이다.

- Q: 넉넉하게 `mod*mod` 를 더하면 무엇이 문제인가?
  A: 답은 같지만 **법이 커질 때 그쪽이 먼저 넘친다**(원본 함정).
  mod 가 10^9 급이면 `mod*mod` 는 10^18 급 — long 상한(약 9.2×10^18)에 바짝 붙는다.
  "안전하게 크게" 가 오히려 오버플로 위험을 만드는 사례다.

- Q: 굴리기가 창 길이를 비용에서 없앤다는 말은?
  A: 창마다 글자 연산이 나간 글자·들어온 글자 2 번뿐이라, 창 길이 m 이 비용에 안 들어간다는 뜻이다.
  창마다 다시 계산하면 창마다 m 번 — 실측에서 본문 10 만·패턴 50 글자일 때 4,997,550 대 200,000, 약 25 배였다.

- Q: 이 구조는 10 번 누적 합의 무엇과 같은가?
  A: "전체를 다시 계산하지 않고 경계만 손본다" 는 구조다.
  누적 합이 구간 합을 두 값의 뺄셈으로 만들었듯, 굴리기는 창 이동을 빼기·곱하기·더하기 세 번으로 만든다.
  9 번 슬라이딩 윈도우의 "나간 것 빼고 들어온 것 더하기" 와도 같은 뿌리다.

#### 2. 라빈 카프 (`RabinKarp.findAll` — TODO 4)

**impl 정답 코드**

```java
public static List<Integer> findAll(String text, String pattern, long mod, CountedHasher hasher) {
    List<Integer> found = new ArrayList<>();
    int n = text.length();
    int m = pattern.length();
    if (m == 0) {
        for (int i = 0; i <= n; i++) {
            found.add(i);
        }
        return found;
    }
    if (m > n) {
        return found;
    }

    RollingHash rolling = new RollingHash(mod, hasher);
    long patternHash = rolling.hash(pattern);
    long topPower = rolling.basePower(m - 1);
    long windowHash = rolling.hash(text.substring(0, m));

    for (int start = 0; start + m <= n; start++) {
        hasher.compareHash();
        if (windowHash == patternHash) {
            hasher.compareFull();
            if (text.startsWith(pattern, start)) {
                found.add(start);
            } else {
                // 해시는 같은데 문자열이 다르다. 헛일을 한 것이다.
                hasher.collision();
            }
        }
        if (start + m < n) {
            windowHash = rolling.roll(
                    windowHash, text.charAt(start), text.charAt(start + m), topPower);
        }
    }
    return found;
}
```

- Q: "해시가 다르면 문자열도 다르다" 는 왜 확실하고, 그 역은 왜 아닌가?
  A: 해시는 문자열에서 **함수로** 계산된다 — 같은 문자열은 반드시 같은 해시가 나온다.
  그 대우로, 해시가 다르면 문자열이 같을 수 없다.
  역이 안 되는 이유는 법으로 접었기 때문이다 — 가능한 문자열은 무한한데 해시 값은 mod 가지뿐이라, 서로 다른 문자열이 같은 값에 겹치는 것(충돌)을 피할 수 없다.

- Q: 해시가 같을 때 실제 비교로 확인하는 이유는?
  A: 해시가 같아도 문자열은 다를 수 있기 때문이다(충돌).
  확인 없이 답에 넣으면 없는 자리를 "찾았다" 고 답하는 오답이 된다.
  확인은 후보(해시가 같은 창)에만 하므로 싸다 — 후보가 드물다는 전제(큰 법) 위에서.

- Q: `findAllWithoutVerification` 은 어떤 입력에서 어떻게 틀리는가?
  A: 충돌이 나는 입력에서 없는 위치를 답에 넣는다.
  실측: 정답이 0 개인 입력에서 법 101 이면 충돌 955 번 — 955 개 전부 오답.
  법 10^9+7 에서도 `"dfdabcbhdfad"` 와 `"edcgbcbgbbfd"` 가 같은 해시(612,860,855)라, 확인 없이 찾으면 `[2]`, 확인하면 `[]` 였다.

- Q: 확인이 있으면 법이 작아도 답은 같다 — 그러면 무엇이 망가지는가?
  A: 속도다.
  충돌마다 실제 문자열 비교(헛일)가 붙는데, 법이 작으면 충돌이 폭발한다.
  실측: 중복 부분 문자열 문제에서 법 101 이면 헛비교 21,245,549 번 — 완전 탐색(2 억)의 1/10 수준까지 이득이 사라진다. 법 10^9+7 이면 3 번이다.

- Q: "확인은 정확성을, 큰 법은 속도를 지킨다" 를 실측으로?
  A: 확인을 빼면 — 법 101 에서 955 개 전부 오답(정확성 붕괴).
  법을 줄이면 — 확인 덕에 답은 같지만 헛비교 2 천만 번(속도 붕괴).
  역할이 둘로 갈려 있어서, 하나를 빼면 각각 **다른 방식으로** 망가진다.

- Q: 법이 10 억이어도 충돌 쌍이 존재한다는 사실이 시사하는 것은?
  A: **확률이 낮은 것과 불가능한 것은 다르다**는 것이다.
  충돌 쌍은 언제나 존재한다 — 낮은 것은 "우연히 만날" 확률뿐이다.
  그래서 확인은 "법이 충분히 크면 생략해도 되는 것" 이 아니라 정확성의 필수 요소다.

- Q: 입력을 남이 고를 수 있으면 확률 이야기가 의미 없는 이유는?
  A: 확률은 입력이 무작위일 때의 이야기다.
  공격자는 BASE·mod 를 알면 충돌 쌍을 **일부러** 만들어 넣을 수 있다 — 그 입력에서 충돌 확률은 1 이다.
  (원본에 근거 없음 — 내 추론) 그래서 실무 해시맵들이 해시 시드를 무작위화하거나, 외부 입력을 받는 곳엔 확인 있는 구조를 쓴다.

- Q: KMP 와 비교해 라빈 카프는 무엇을 내주고 무엇을 얻는가?
  A: KMP 는 항상 정확하고 최악도 O(n+m) 이다 — 대신 실패 함수라는 전처리·논리가 필요하다.
  라빈 카프는 구조가 단순하고(해시 비교 + 확인) 여러 패턴·2차원 등으로 일반화가 쉽다 — 대신 최악(충돌 폭발)에서 느려질 수 있고 법·기수 선택이 성능을 좌우한다.
  (원본에 근거 없음 — 내 추론) 단일 패턴 정확 매칭만 필요하면 KMP, 해시값 자체를 재활용할 문제(중복 탐지 등)면 해싱이 자연스럽다.

#### 3. 가장 긴 중복 부분 문자열 (`DuplicateSubstring` — TODO 5~6)

**impl 정답 코드**

```java
/** 두 번 이상 나오는 가장 긴 부분 문자열. 없으면 빈 문자열. */
public static String longest(String s, long mod, CountedHasher hasher) {
    int lo = 1;
    int hi = s.length() - 1;
    String best = "";
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        String found = duplicateOfLength(s, mid, mod, hasher);
        if (found != null) {
            best = found;
            lo = mid + 1;
        } else {
            hi = mid - 1;
        }
    }
    return best;
}

static String duplicateOfLength(String s, int length, long mod, CountedHasher hasher) {
    int n = s.length();
    if (length <= 0 || length > n) {
        return null;
    }
    RollingHash rolling = new RollingHash(mod, hasher);
    long topPower = rolling.basePower(length - 1);
    long hash = rolling.hash(s.substring(0, length));

    // 같은 해시를 가진 시작 위치들. 충돌이 있을 수 있으므로 목록으로 담는다.
    Map<Long, List<Integer>> seen = new HashMap<>();
    for (int start = 0; start + length <= n; start++) {
        List<Integer> bucket = seen.get(hash);
        if (bucket != null) {
            for (int other : bucket) {
                hasher.compareFull();
                if (s.regionMatches(other, s, start, length)) {
                    return s.substring(start, start + length);
                }
                hasher.collision();
            }
        }
        seen.computeIfAbsent(hash, k -> new java.util.ArrayList<>()).add(start);
        if (start + length < n) {
            hash = rolling.roll(hash, s.charAt(start), s.charAt(start + length), topPower);
        }
    }
    return null;
}
```

```
단조성:  길이 L 짜리 중복이 있으면 그 일부인 L-1 짜리도 반드시 있다

  가능    가능    가능    불가    불가
  L=1     L=2     L=3     L=4     L=5      -> 경계를 이분 탐색 (06번)
                   ^ 답

한 판정(duplicateOfLength) = 길이 L 창 전부를 굴리며 해시맵에 담기 -> O(n)
```

- Q: 길이 이분 탐색이 성립하는 단조성은 무엇인가?
  A: "길이 L 짜리 중복이 있으면 L-1 짜리도 있다" — 중복 조각의 앞 L-1 글자도 두 번 나오기 때문이다.
  그래서 가능/불가능이 길이축에서 한 번만 뒤집힌다.
  06 번의 "답에 대고 이분 탐색" 그대로다 — `longest` 는 찾으면 기억하고 긴 쪽으로(`lo = mid+1`), 못 찾으면 짧은 쪽으로(`hi = mid-1`) 간다.

- Q: 해시맵의 값이 위치 목록이어야 하는 이유는?
  A: 해시가 같아도 문자열이 다를 수 있어서다(충돌).
  위치 하나만 담으면 충돌로 덮어써서 진짜 중복을 놓치거나, 충돌 상대와만 비교하고 끝낼 수 있다.
  목록(버킷)으로 담고 같은 해시의 **모든** 위치와 실제 비교해야 정확하다.

- Q: `substring` 대신 `regionMatches` 를 쓰는 이유는?
  A: `substring` 은 길이 L 짜리 새 문자열 객체를 만드는 데 O(L) 이 든다.
  해시로 창 이동을 O(1) 로 만들어 놓고 비교마다 O(L) 복사를 하면 이득이 샌다.
  `regionMatches(other, s, start, length)` 는 복사 없이 제자리에서 구간을 비교한다.
  (비교 자체는 최악 O(L) 이지만, 해시가 같을 때만 하므로 드물다.)

- Q: 전체 비용 O(n log n) 은 어떻게 나오고, 해시가 없으면?
  A: 판정 한 번이 O(n) — 창 n-L+1 개를 굴리며(창당 O(1)) 해시맵에 담는다.
  이분 탐색이 판정을 O(log n) 번 부른다 → O(n log n).
  해시 없이 부분 문자열을 만들어 비교하면 판정이 O(n·L) = O(n²) 급이라 전체 O(n² log n) 이다.
  실측: 2 만 글자에서 완전 탐색 약 2 억 대 이분+굴리기 488,463 — 약 400 배.

- Q: 이분 탐색과 굴리기 둘 중 하나만 있으면 왜 안 되는가?
  A: 이분 탐색만 있으면 — 판정이 O(n²) 이라 전체 O(n² log n), 완전 탐색과 급이 같다.
  굴리기만 있으면 — 길이를 1 부터 다 훑어야 해서 판정 O(n) × 길이 n 번 = O(n²) 이다.
  단조성(06 번)이 판정 횟수를 log 로, 굴리기가 판정 하나를 O(n) 으로 줄인다 — 400 배는 둘의 곱이다.

- Q: `hi = n` 으로 바꿔도 테스트가 통과하는데 왜 결함이 아닌가?
  A: 길이 n 짜리 창은 문자열 전체 하나뿐이라 두 번 나올 수 없고, `duplicateOfLength(s, n, ...)` 이 null 을 주기 때문이다.
  즉 `hi = n` 은 "항상 실패하는 판정 하나를 더 허용" 한 것일 뿐 답이 안 바뀐다.
  이분 탐색의 첫 mid 도 같아서 비용조차 안 변한다 — 테스트가 못 잡는 변종이 결함 은닉이 아니라 **의미상 동치**인 사례다(원본 변종 검증 기록).

#### 4. 생각해볼 것 (원본 README 이관)

- Q: 법을 두 개 써서 둘 다 같을 때만 후보로 치면 무엇이 좋아지나, 확인은 여전히 필요한가?
  A: (원본에 근거 없음 — 내 추론) 충돌 확률이 곱으로 준다 — 두 법에서 동시에 충돌해야 후보가 되므로, 헛비교(속도 손실)가 크게 준다.
  하지만 원리는 그대로다: 두 법을 써도 (해시쌍, 문자열) 대응은 여전히 다대일이라 충돌 쌍은 **존재한다**.
  그래서 정확성이 필요하면 확인은 여전히 필요하다 — 이중 해시는 "확인을 없애는 장치" 가 아니라 "확인을 드물게 만드는 장치" 다. 확률이 낮은 것과 불가능한 것은 다르다는 원본의 문장이 그대로 적용된다.

- Q: `BASE` 를 알파벳 크기보다 작게 잡으면 무엇이 깨지나?
  A: 서로 다른 한 글자가 같은 값 취급되는 것부터 깨진다 — 원본 주석("기수. 알파벳 크기보다 커야 한다")이 가리키는 지점이다.
  B진법으로 볼 때 각 글자는 "한 자리 숫자" 여야 하는데, 글자 값이 B 를 넘으면 자리 올림이 생겨 **다른 문자열이 mod 와 무관하게 같은 수**가 된다.
  (예: B=10 이면 글자값 (1, 2) 와 글자값 (0, 12) 가 똑같이 12 다 — 충돌이 아니라 정의 자체가 문자열을 구분 못 하는 것.)

- Q: 이 방식으로 접미사 배열을 만들 수 있나, 26 번의 트라이와 무엇이 다른가?
  A: (원본에 근거 없음 — 내 추론) 할 수 있다 — 두 접미사의 비교를 "일치하는 앞부분 길이(LCP)를 해시+이분 탐색으로 O(log n) 에 구하고, 그 다음 글자 하나로 대소 판정" 으로 만들면, 정렬 O(n log n) × 비교 O(log n) = O(n log² n) 으로 접미사 배열이 나온다.
  트라이(26 번)와의 차이: 트라이는 문자열들을 **구조로** 저장해 정확하게 비교하고 메모리를 노드로 낸다. 해싱은 구조 없이 **숫자 요약**으로 비교하고, 대신 충돌 가능성과 확인 비용을 진다.
  같은 "여러 문자열 다루기" 에서 트라이는 메모리를, 해싱은 확률을 지불하는 선택이다.

#### 5. 파생 — 왜 그렇게 생겼는가

- Q: 25·26 번의 "정확한" 알고리즘과 해싱의 근본적 차이는?
  A: KMP·아호 코라식은 판정 자체가 항상 참이다 — 실패 함수·트라이가 문자열 구조를 그대로 들고 있어서다.
  해싱은 판정이 틀릴 수 있다(같은 해시 ≠ 같은 문자열).
  대신 그 판정이 O(1) 로 싸고, 틀린 쪽(해시 같음)만 확인해서 걸러낸다 — "싸지만 불확실한 1차 필터 + 확실한 2차 확인" 의 2단 구조다.

- Q: 그 구조가 성립하려면 확인이 무엇이어야 하는가?
  A: 확인은 **확실하고**(실제 문자열 비교), 후보에만 걸려서 **드물어야** 한다.
  한쪽 방향은 절대 안 틀린다는 성질(해시 다름 → 확실히 다름)이 있어야 "거른 것" 은 확인 없이 버릴 수 있다.
  이 두 조건(false negative 없음 + 후보가 드묾)이 깨지면 각각 오답·속도 붕괴가 된다.

- Q: "틀리는 게 아니라 느려진다" 는 어떤 전제 위에서만 참인가?
  A: **확인이 있다**는 전제 위에서만이다.
  확인이 있으면 충돌은 헛비교(시간)로만 새고 답은 지켜진다 — 법 101 에서도 답은 같고 헛비교만 2 천만 번.
  확인이 없으면 같은 충돌이 그대로 오답이 된다 — 955 개 전부 오답.

- Q: 굴리기 실측 25 배의 차이는 복잡도로 어떻게 표현되는가?
  A: 창마다 다시 계산 = O(n·m), 굴리기 = O(n + m) 이다.
  실측의 25 배는 대략 창당 연산 m=50 대 2 의 비율에서 나온다.
  m 이 더 길수록 배율이 커진다 — "패턴 길이가 비용에서 사라진다" 의 수치 표현이다.

- Q: 이 패턴이 실무에서 쓰이는 곳 하나는?
  A: 파일/문서 중복 검사·표절 탐지가 대표다(서머리 한눈에 절).
  조각들의 해시로 후보 쌍을 싸게 추리고, 후보만 실제 내용을 비교한다.
  (원본에 근거 없음 — 내 추론) git 이 객체를 해시로 먼저 식별하는 것, 백업·스토리지의 중복 제거(dedup)도 같은 "요약으로 거르고 필요하면 원본 확인" 구조다.

- Q: 20 번 A* 의 부풀린 휴리스틱과 확인 생략은 어떤 점에서 같은 종류의 위험인가?
  A: 둘 다 "**대부분 맞는**" 알고리즘을 만든다는 점이다(impl 주석이 직접 이 비교를 한다).
  부풀린 휴리스틱은 대부분의 지도에서 최단 경로를 주지만 보장이 깨져 있고, 확인 생략은 대부분의 입력에서 맞지만 충돌에서 틀린다.
  테스트 몇 개가 통과한다고 정확성이 증명되지 않는다 — 보장을 깬 최적화는 언제 틀리는지 스스로 말해주지 않는다.
