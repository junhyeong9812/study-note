### A. 문제 (src/main 의 TODO 1~7)

#### 1. 나이브 검색 (`NaiveSearch` — TODO 1~2)

**정답 코드 (impl 기준, 핵심부)**

```java
public static List<Integer> findAll(CountedText text, String pattern) {
    List<Integer> found = new ArrayList<>();
    int n = text.length();
    int m = pattern.length();
    if (m == 0) {
        // 빈 패턴은 모든 자리에서 발견된다. 끝 다음 자리까지 포함한다.
        for (int i = 0; i <= n; i++) {
            found.add(i);
        }
        return found;
    }

    for (int start = 0; start + m <= n; start++) {
        int i = 0;
        while (i < m && text.matches(start + i, pattern.charAt(i))) {
            i++;
        }
        if (i == m) {
            found.add(start);
        } else if (i > 0) {
            // 여기서 본문 위치가 start+i 에서 start+1 로 되돌아간다.
            text.backtrack();
        }
    }
    return found;
}
```

```
본문: a a a a a a      패턴: a a b

start=0:  a a b        맞고 맞고 어긋남 -> 본문 2 칸 갔다가 1 로 되돌아감
start=1:    a a b      또 맞고 맞고 어긋남
start=2:      a a b    ...
시작 위치마다 m 에 가까운 비교 -> n x m
```

**질문별 답**

- Q: `"abc"` 안에서 빈 패턴을 찾으면 발견 자리가 몇 개이고, 그 수를 정하는 것은 알고리즘인가 계약인가?
  A: **4개**다 — 0, 1, 2, 3 으로 끝 다음 자리까지 포함한다(`for (int i = 0; i <= n; i++)`).
  이것은 알고리즘이 계산해 낸 값이 아니라 **계약이 정한 것**이다 — "빈 문자열은 어디에나 있다"를 어떻게 셀지는 선택의 문제다.
  끝 다음 자리를 빼는 계약도 가능하고, 그러면 3개가 된다.
  그래서 원본 TODO 1 이 "계약을 먼저 정해라"라고 하고, 계약 테스트가 그 선택을 고정한다.

- Q: 시작 위치는 어디까지 갈 수 있는가 — 조건을 식으로 쓰면?
  A: `start + m <= n` 이다 — 남은 글자가 패턴 길이보다 적으면 볼 필요가 없다.
  즉 시작 위치는 0 부터 `n - m` 까지, 전부 `n - m + 1` 개.
  최악 입력(n=10,000, m=101)에서 이 수가 9,900 이고, 그것이 비교 999,900 = 9,900 × 101 의 앞 인수다.
  조건을 `start < n` 으로 쓰면 배열 범위를 넘는다 — 경계는 식으로 못박아야 한다.

- Q: 어긋났을 때 본문 읽기 위치는 어디에서 어디로 되돌아가는가?
  A: `start + i` 에서 `start + 1` 로 되돌아간다.
  이미 `i` 글자를 읽어 놓고, 시작 위치를 한 칸만 옮겨 그 글자들을 **다시 읽는다**.
  버려지는 정보가 정확히 "방금 i 글자가 패턴 앞부분과 맞았다"는 사실이다 — KMP 가 살려 쓰는 것이 이것이다.
  impl 은 이 자리에서 `text.backtrack()` 을 불러 되돌림을 센다.

- Q: 되돌림(backtrack)을 `i > 0` 일 때만 세는 이유는?
  A: `i == 0` 이면 첫 글자부터 어긋난 것이라 본문을 앞으로만 갔지 되돌아간 적이 없기 때문이다.
  `start` 에서 한 글자 보고 틀렸고 다음은 `start+1` — 읽기 위치가 그대로 전진한다.
  `i > 0` 일 때만 이미 읽은 글자를 다시 읽게 된다.
  그래서 알파벳이 다양한 입력에서는 되돌림이 적다 — 실측 394번(본문 1만 글자의 4% 아래).

- Q: 나이브의 최악 입력은 어떤 본문과 어떤 패턴 조합인가?
  A: 본문 `"aaa...a"`(1만 글자), 패턴 `"aaa...ab"`(a 100개 + b, 101 글자)다.
  패턴이 본문과 마지막 한 글자만 빼고 전부 같아서, 시작 위치마다 100글자를 맞추고 마지막에 어긋난다.
  일반화하면 "패턴의 앞부분이 본문 어디에나 있고, 마지막에만 틀리는" 모양.
  실무에서는 반복 문자열(로그의 구분자, 압축 안 된 공백, DNA 서열 같은 좁은 알파벳)에서 이런 일이 생긴다.

- Q: 그 최악에서 비교 횟수가 `n × m` 에 가까워지는 이유는?
  A: 시작 위치가 `n - m + 1 = 9,900` 개이고 **각 위치마다 m = 101 번 전부 비교**하기 때문이다.
  9,900 × 101 = **999,900** — 실측값이 정확히 이 곱이다.
  "최악 O(n×m)"이라는 말이 곱셈 하나로 눈에 보이는 순간이다.
  KMP 는 같은 입력에서 29,899(= n 의 3배쯤)라 **33배** 차이가 난다.

- Q: 보통 입력에서 나이브가 사실상 O(n) 인 이유는?
  A: 알파벳이 다양하면 **첫 글자에서 대부분 어긋나기** 때문이다.
  시작 위치마다 비교가 평균 1~2번이면 전체가 n 에 비례한다 — 실측: 26종류 본문 1만 글자에서 비교 10,403(≈ n).
  그래서 실무의 단순 검색은 나이브로도 충분한 경우가 많다.
  나이브가 무너지는 것은 알파벳이 좁거나 패턴이 자기 자신과 겹칠 때 — 그 조건을 아는 것이 선택의 기준이다.

#### 2. 실패 함수 (`Kmp.failureFunction` — TODO 3~4)

**정답 코드 (impl 기준, 핵심부)**

```java
public static int[] failureFunction(String pattern, long[] comparisons) {
    int m = pattern.length();
    int[] failure = new int[m];
    int length = 0;

    for (int i = 1; i < m; i++) {
        // 어긋나면 실패 함수를 따라 뒤로 간다. 여기가 실패 함수를 자기 자신으로 만드는 자리다.
        while (length > 0 && pattern.charAt(i) != pattern.charAt(length)) {
            comparisons[0]++;
            length = failure[length - 1];
        }
        comparisons[0]++;
        if (pattern.charAt(i) == pattern.charAt(length)) {
            length++;
        }
        failure[i] = length;
    }
    return failure;
}
```

```
패턴     a  a  b  a  a  b  a  a  a
failure  0  1  0  1  2  3  4  5  2
                                 ^ 마지막 'a': length 5 에서 어긋남 (pattern[5]='b')
                                   5 -> failure[4] = 2, 또 어긋남 (pattern[2]='b')
                                   2 -> failure[1] = 1, pattern[1]='a' 맞음 -> length 2
                                   (한 번에 0 으로 떨어뜨리면 이 2 를 놓친다)
```

**질문별 답**

- Q: `failure[i]` 의 정의를 한 문장으로 말하면 무엇이고, "자기 자신 제외"가 왜 붙는가?
  A: `pattern[0..i]` 에서 **접두사이면서 동시에 접미사인 가장 긴 조각의 길이**다.
  자기 자신을 빼지 않으면 답이 항상 `i+1`(전체가 자기 자신의 접두사이자 접미사)이 되어 정보가 0 이 된다.
  되돌릴 자리를 알려주는 표인데 "제자리"를 알려주면 무한 루프다.
  그래서 `"a"` 의 failure 는 1 이 아니라 **0** 이다.

- Q: `"ababa"` 의 실패 함수 `[0,0,1,2,3]` 은 각 칸이 왜 그 값인가?
  A: i=0 `"a"` → 자기 자신 제외라 0.
  i=1 `"ab"` → 접두사 `"a"` 와 접미사 `"b"` 가 다르니 0.
  i=2 `"aba"` → `"a"` 가 앞뒤로 같으니 1. i=3 `"abab"` → `"ab"` 가 앞뒤로 같으니 2.
  i=4 `"ababa"` → `"aba"` 가 앞뒤로 같으니 3(전체 `"ababa"` 는 자기 자신이라 제외).

- Q: 실패 함수 값이 "어긋났을 때 다시 안 맞춰도 되는 길이"와 같은 뜻인 이유는?
  A: 지금까지 맞춘 부분 `pattern[0..matched-1]` 은 **본문에도 그대로 있다**.
  그 조각의 접미사 중 패턴의 접두사이기도 한 것이 있다면, 그 길이만큼은 본문의 현재 위치 바로 앞에 이미 맞아 있는 상태다.
  그러니 패턴을 그 길이로 되돌리면 "이미 맞은 셈" 치고 이어서 진행할 수 있다.
  가장 긴 것을 택하는 이유는, 더 짧게 되돌리면 그 사이에 있을 발견을 놓치기 때문이다(정확성), 더 길게는 맞는 보장이 없다.

- Q: 만드는 중에 어긋나면 `length` 를 어디로 되돌리는가 — 0 으로 한 번에 가면 무엇이 틀리는가? (원본 함정)
  A: `length = failure[length - 1]` 로 되돌린다 — **한 단계씩** 내려간다.
  0 으로 한 번에 떨어뜨리면, 중간 길이의 접두사=접미사가 여전히 성립하는 경우를 놓쳐 값이 작게 나온다.
  `"aabaabaaa"` 의 마지막 `a` 에서 정답은 2 인데, 0 으로 떨어뜨리면 1 이 되어 틀린다.
  실패 함수 값이 틀리면 검색도 조용히 틀리므로(발견 누락), 이 함정이 가장 비싸다.

- Q: `"aabaabaaa"` 의 마지막 `a` 에서 실제로 몇 단계를 내려가는가?
  A: **두 단계**다: length 5 → `failure[4]`=2 → `failure[1]`=1.
  5 에서 `pattern[5]='b'` 와 어긋나고, 2 에서 `pattern[2]='b'` 와 또 어긋나고, 1 에서 `pattern[1]='a'` 와 맞아 length 가 2 가 된다.
  `if` 로 짰다면 5 → 2 한 번만 내려가고 거기서 멈춰 `failure[8]` 이 0 이 된다.
  "여러 번 되돌려야 하는 입력이 있다"의 구체적인 증거가 이 한 칸이다.

- Q: `while` 을 `if` 로 쓰면 어떤 입력에서 틀리는가? (원본 함정)
  A: 위의 `"aabaabaaa"` 처럼 **패턴 안에 같은 조각이 여러 겹으로 겹친** 입력에서 틀린다.
  한 번 되돌려도 또 어긋나는 상황이 생기는데, `if` 는 그 두 번째 되돌림을 안 한다.
  짧고 단순한 테스트 패턴(`"abc"`, `"ababa"`)에서는 한 번이면 끝나서 통과해 버린다 — 그래서 계약 테스트가 겹침이 깊은 패턴을 일부러 넣는다.
  검색 쪽 `while` 도 같은 이유로 `if` 가 아니어야 한다.

- Q: "실패 함수를 만들 때 실패 함수를 쓴다"를 "패턴을 패턴 안에서 찾는다"로 바꿔 말하면 무슨 뜻인가?
  A: 실패 함수 만들기는 사실 **패턴을 본문 삼아 패턴 자신을 KMP 로 검색하는 것**과 같은 일이다.
  `length` 가 검색 쪽의 `matched` 에 해당하고, 어긋났을 때 되돌리는 방식도 동일하다.
  다른 점은 결과를 기록하며 만들어 가는 표를 그 자리에서 바로 참조한다는 것 — 이미 확정된 앞칸(`failure[length-1]`, 항상 `length-1 < i`)만 보므로 순환 참조가 아니다.
  "아직 만들다 만 표를 쓴다"가 아니라 "이미 완성된 앞부분을 쓴다"로 이해하면 구조가 풀린다.

- Q: 안쪽 `while` 이 있는데도 만들기가 O(m) 인 이유는 — 되돌리기 총량이 `m` 을 못 넘는 논증은? (원본 측정 다섯)
  A: **상환 분석**이다: `length` 는 한 바퀴에 최대 1 만 늘고, 되돌릴 때만 준다.
  전체를 통틀어 늘어난 총량이 `m` 을 못 넘으므로, 줄어든 총량도 `m` 을 못 넘는다 — 즉 안쪽 while 의 총 실행 횟수가 `m` 이하다.
  그래서 바깥 루프 m 번 + 되돌리기 m 번 = 비교가 **2m 을 안 넘는다**.
  실측: 패턴 101 글자에서 199번(2m = 202 안쪽), 그리고 길이 1,000 짜리 여러 패턴에서도 전부 2m 이하.

- Q: 그 논증은 09번 슬라이딩 윈도우의 무엇과 같은 것인가?
  A: 슬라이딩 윈도우에서 "왼쪽 포인터는 전체를 통틀어 n 칸만 움직인다"는 논증과 **같은 구조**다.
  둘 다 안쪽 while 을 보고 "중첩 루프니까 O(n²)"이라고 겁먹기 쉬운데, 안쪽의 총 실행 횟수가 바깥과 묶여 있어 선형이다.
  판별 요령: 안쪽 루프가 줄이는 값이 **바깥에서만 늘어나는 값**인지 본다 — 그렇다면 총량이 묶인다.
  "한 번의 최악"이 아니라 "전체의 합"으로 비용을 재는 것이 상환 분석의 핵심이다.

#### 3. KMP 검색 (`Kmp.findAll` — TODO 5~7)

**정답 코드 (impl 기준, 핵심부)**

```java
public static List<Integer> findAll(CountedText text, String pattern, long[] patternComparisons) {
    List<Integer> found = new ArrayList<>();
    int n = text.length();
    int m = pattern.length();
    if (m == 0) {
        for (int i = 0; i <= n; i++) {
            found.add(i);
        }
        return found;
    }

    int[] failure = failureFunction(pattern, patternComparisons);
    int matched = 0;

    for (int i = 0; i < n; i++) {
        // 어긋나면 패턴만 되돌린다. i 는 절대 안 줄어든다.
        while (matched > 0 && !text.matches(i, pattern.charAt(matched))) {
            matched = failure[matched - 1];
        }
        if (text.matches(i, pattern.charAt(matched))) {
            matched++;
        }
        if (matched == m) {
            found.add(i - m + 1);
            // 겹치는 것도 찾으려면 여기서도 실패 함수를 쓴다.
            matched = failure[matched - 1];
        }
    }
    return found;
}
```

```
본문:  a b a b a b c        패턴: a b a b c      failure = [0,0,1,2,0]

       a b a b a b c
       a b a b c
               ^ i=4 에서 어긋남 ('a' != 'c')
       -> matched 4 -> failure[3] = 2   ("ab" 는 이미 맞은 셈)

       a b a b a b c
           a b a b c        <- 본문 i=4 는 그대로. 이어서 맞춤
                   ^ 위치 2 에서 발견
```

**질문별 답**

- Q: KMP 에서 `text.backtrack()` 을 부를 일이 정말 없는가, 그것이 왜 "KMP 의 전부"인가?
  A: 없다 — 본문 인덱스 `i` 는 `for` 문에서만 바뀌고 오직 증가한다.
  되돌리는 것은 `matched`(패턴 쪽)뿐이라, 본문 글자를 다시 읽는 일이 구조적으로 불가능하다.
  그래서 최악에서도 본문 훑기가 n 번으로 묶이고 O(n×m) 이 사라진다 — 이 한 가지가 KMP 의 존재 이유다.
  실측 계약: 최악 입력에서 나이브 되돌림 **9,900**, KMP **0**.

- Q: 어긋났을 때 보는 값이 `failure[matched]` 가 아니라 `failure[matched-1]` 인 이유는?
  A: `matched` 는 "맞춘 **개수**"이고 failure 의 인덱스는 "맞춘 **마지막 글자의 위치**"라서 하나 차이가 난다.
  `matched` 글자를 맞췄다면 마지막으로 맞은 글자는 `pattern[matched-1]` 이고, 그 접두사=접미사 길이가 `failure[matched-1]` 이다.
  `failure[matched]` 를 보면 아직 맞지도 않은 글자까지 포함한 값이라 과하게 되돌린다(또는 배열 끝을 넘는다).
  "개수인가 인덱스인가"를 헷갈리면 한 칸 어긋나는 전형적인 버그다.

- Q: 되돌린 뒤 또 어긋날 수 있으니 `if` 가 아니라 `while` 이어야 하는 이유는?
  A: `failure[matched-1]` 로 줄인 자리에서도 현재 본문 글자와 다시 어긋날 수 있기 때문이다.
  그러면 또 `failure` 를 따라 내려가야 하고, 맞거나 `matched == 0` 이 될 때까지 반복한다.
  `if` 로 쓰면 한 번만 내려가고 그대로 진행해 발견을 놓친다 — 실패 함수 만들 때와 똑같은 함정이다.
  `matched > 0` 조건이 종료를 보장한다(0 에서는 더 내려갈 곳이 없으니 그냥 다음 글자로).

- Q: 다 맞췄을 때 발견 시작 위치는 `i` 에서 무엇을 빼는가?
  A: `i - m + 1` 이다.
  `i` 는 패턴의 **마지막** 글자와 맞은 본문 위치이고, 패턴 길이가 m 이므로 시작은 m−1 칸 앞이다.
  `i - m` 으로 쓰면 한 칸 앞을 가리키는 오프바이원이 된다.
  경계 확인: m=1 이면 시작 위치가 `i` 그대로여야 하는데 `i - 1 + 1 = i` 로 맞는다.

- Q: 발견 직후 `matched` 를 0 으로 두면 무엇을 놓치는가 — `"aaa"` 속 `"aa"` 는 몇 개인가? (원본 함정)
  A: **겹치는 발견**을 놓친다. `"aaa"` 속 `"aa"` 는 위치 0 과 1 로 **2개**이고, `"aaaa"` 에서는 0·1·2 로 3개다.
  0 으로 두면 발견 뒤 패턴을 처음부터 다시 맞춰야 해서, 방금 발견과 한 글자만 겹친 다음 발견이 사라진다.
  이것은 성능 문제가 아니라 **정답이 틀리는** 문제다.
  "겹침을 셀 것인가"도 계약이지만, 이 챕터의 계약 테스트는 겹침을 센다.

- Q: 그래서 발견 직후에도 `failure[m-1]` 을 쓰는데, 그것이 뜻하는 상태는 무엇인가?
  A: "패턴 전체를 맞춘 상태에서, 그 접미사 중 패턴의 접두사이기도 한 가장 긴 만큼은 여전히 맞아 있다"는 상태다.
  즉 발견을 어긋남과 똑같이 취급해 `failure` 를 따라 되돌리는 것 — 발견도 "더 진행할 수 없는 지점"이라는 점에서 같다.
  `"aa"` 의 `failure[1]` 은 1 이므로, 발견 직후 matched 가 1 로 남아 바로 다음 글자에서 또 발견된다.
  코드가 어긋남과 발견을 같은 도구로 처리한다는 것이 이 알고리즘의 단정함이다.

- Q: 빈 패턴을 나이브와 KMP 가 똑같이 다뤄야 하는 이유는?
  A: 두 함수가 **같은 계약을 구현한 두 판**이기 때문이다 — 계약 테스트가 같은 입력에 같은 결과를 요구한다.
  빈 패턴의 답(0..n 전부)은 알고리즘에서 유도되는 것이 아니라 계약이 정한 값이라, 양쪽에 같은 특수 처리를 넣어야 한다.
  실제로 impl 의 두 파일이 같은 `for (int i = 0; i <= n; i++)` 블록을 각각 갖고 있다.
  일반 교훈: 대체 구현이 둘 이상이면 **경계 계약을 문서나 테스트 한 곳에 고정**해야 갈라지지 않는다.

- Q: 최악 입력에서 되돌림이 나이브 9,900번 대 KMP 0번이라는 수는 무엇을 세는 것인가? (원본 측정 하나·둘)
  A: **본문 읽기 위치를 뒤로 되돌린 횟수**다(`CountedText.backtrack()`).
  나이브는 시작 위치 9,900 곳 각각에서 100 글자를 맞춘 뒤 어긋나 되돌아가므로 9,900번.
  KMP 는 구조상 한 번도 안 되돌리므로 0.
  이 계측이 중요한 이유: 두 구현은 **결과가 같아서**, 결과만 보면 어느 쪽이 KMP 인지 구분할 수 없다 — 비용을 세야 주장이 검증된다.

- Q: 알파벳 26종류·패턴 5글자에서 KMP 가 오히려 4번 더 비교하는 이유는? (원본 측정 셋)
  A: 알파벳이 다양하면 첫 글자에서 대부분 어긋나, 나이브도 사실상 본문을 한 번만 훑는 셈이 되기 때문이다(10,403 ≈ n).
  KMP 는 그 위에 되돌리기 `while` 의 판정 비교가 조금 붙어 10,407 — **4번 더** 한다.
  즉 나이브가 헛일을 거의 안 하는 구간에서는 KMP 의 안전장치가 순수한 오버헤드가 된다.
  **최악을 없애는 대신 평균에서 아주 조금 손해 보는 거래** — 04번 힙 정렬, 08번 투 포인터와 같은 모양이다.

- Q: "패턴이 자기 자신과 겹칠수록 KMP 가 이긴다"를 배수 표(0.99 → 33)로 설명하면? (원본 측정 넷)
  A: 26종류·패턴 5 → 0.99배(KMP 가 짐), 2종류·패턴 8 → 1.06배, `"abab..."` 에 `"ababababac"` → 2.2배, `"aaa..."` 에 `"aaa...ab"` → **33배**.
  아래로 갈수록 패턴이 자기 자신과 많이 겹치고, 그만큼 나이브가 "맞추다 끝에서 어긋나 되돌아가는" 헛일을 많이 한다.
  그 겹침을 미리 계산해 둔 것이 실패 함수이므로, 겹침이 클수록 KMP 가 아끼는 양도 크다.
  결론: **"KMP 를 쓸까"는 데이터가 정한다. 알고리즘만 보고 정할 수 없다.**

- Q: 검색이 O(n) 인 상환 논증은 실패 함수 만들기의 논증과 어떻게 같은가?
  A: 같은 문장이 변수 이름만 바꿔 성립한다: `matched` 는 본문 글자당 최대 1 만 늘고, 되돌릴 때만 준다.
  전체 증가량이 n 이하이므로 감소 총량도 n 이하 — 안쪽 while 의 총 실행 횟수가 n 으로 묶인다.
  그래서 전처리 O(m) + 검색 O(n) = **O(n+m)** 이다.
  실측의 "KMP 는 n 의 3배 정도(29,899)"는 자리마다 while 판정 + if 판정이 붙어 상수가 3 쯤이라는 뜻이지, 차수가 아니다.

### B. 개념

- Q: (원본 생각해볼 것) 보이어 무어는 패턴을 뒤에서부터 맞추는데, 왜 그게 더 빠를 수 있고 언제 안 그런가?
  A: (원본에 답 없음 — 내 추론 + 알려진 결과) 뒤에서부터 맞추면 **한 번의 어긋남으로 여러 칸을 건너뛸 수 있기** 때문이다.
  본문의 그 글자가 패턴에 아예 없으면 패턴 길이 m 만큼 통째로 점프한다(나쁜 문자 규칙) — 글자를 다 안 보고 지나가므로 평균 비용이 n/m 에 가까워질 수 있다.
  잘 안 되는 경우: 알파벳이 좁아 어떤 글자든 패턴에 들어 있을 때(점프가 1~2칸으로 줄어듦), 패턴이 짧아 점프 이득이 작을 때.
  KMP 와의 대비: KMP 는 **최악을 보장**하는 쪽, 보이어 무어는 **평균을 줄이는** 쪽이다(원형 보이어 무어의 최악은 여전히 나쁘고, 갈릴-규칙 등을 더해야 선형이 된다 — 본인 확인 필요).

- Q: (원본 생각해볼 것) 실패 함수로 "이 문자열의 최소 반복 단위"를 구하려면 어떻게 하는가?
  A: (원본에 답 없음 — 내 추론) `p = m - failure[m-1]` 을 계산하고, `m % p == 0` 이면 **p 가 최소 반복 단위의 길이**다.
  이유: `failure[m-1]` 이 길이 `failure[m-1]` 짜리 접두사=접미사가 있다는 뜻이므로, 문자열을 p 칸 밀면 자기 자신과 겹친다 — p 가 주기다.
  `m % p != 0` 이면 전체가 그 단위의 정수 배가 아니므로 "반복 문자열이 아니다"(최소 단위는 m 자신).
  예: `"ababab"`(m=6, failure[5]=4) → p=2, 6%2=0 → `"ab"` 가 3번. `"ababa"`(m=5, failure[4]=3) → p=2 이지만 5%2≠0 → 반복 문자열이 아니다.

- Q: (원본 생각해볼 것) 패턴이 여러 개면 하나씩 KMP 를 돌리면 되는가 — 26번이 답하는 것은 무엇인가?
  A: (원본에 답 없음 — 내 추론) 되긴 하지만 비용이 `O(k·n + Σm)` 으로 **패턴 개수 k 에 비례해 본문을 k 번 훑는다**.
  k 가 크면(금칙어 수천 개, 로그 룰 수백 개) 이것이 그대로 병목이다.
  26번 아호-코라식은 패턴 전부를 하나의 트라이로 합치고, 실패 함수를 그 트라이 위의 **실패 링크**로 일반화해 본문을 **한 번만** 훑는다 — `O(n + Σm + 발견 수)`.
  즉 "KMP 의 실패 함수를 여러 패턴으로 확장한 것"이 26번이고, 이 챕터가 그 전제 지식이다.

- Q: (원본 생각해볼 것) 본문이 스트림으로 들어와 되감을 수 없다면 어느 알고리즘을 써야 하는가?
  A: (원본에 답 없음 — 내 추론) **KMP** 다. 본문 위치를 절대 되돌리지 않으므로 글자를 한 번 읽고 버려도 된다.
  상태로 들고 있어야 하는 것은 `matched` 하나(+패턴과 실패 함수)라 메모리가 본문 길이와 무관하다.
  나이브는 어긋나면 `start+1` 로 되돌아가야 해서 최소 m 글자를 버퍼링해야 하고, 보이어 무어는 앞뒤로 움직여 스트림에 더 안 맞는다.
  "되돌아가지 않는다"는 성질이 성능만이 아니라 **적용 가능한 입력의 종류**까지 넓힌다는 것이 요점이다.

- Q: "본문에서 되돌아가지 않는다" 하나가 왜 최악 O(n×m)을 O(n+m)으로 바꾸는가?
  A: 나이브의 `n×m` 에서 `m` 은 "같은 본문 글자를 최대 m 번까지 다시 읽는다"에서 나온 인수이기 때문이다.
  본문 인덱스가 단조 증가라면 본문 글자를 보는 횟수가 n 으로 묶이고, `m` 인수 자체가 사라진다.
  남은 비용은 전처리 `m` 과 패턴 쪽 되돌리기인데, 되돌리기는 상환 논증으로 n 안에 묶인다.
  그래서 곱셈이 덧셈이 된다 — `n×m` → `n+m`.

- Q: 나이브가 버리는 정보는 정확히 무엇인가 — KMP 는 그것을 어떻게 보관하는가?
  A: 버리는 정보는 "방금 본문의 이 자리 앞 `i` 글자가 패턴의 앞 `i` 글자와 같았다"는 사실이다.
  나이브는 시작 위치를 옮기면서 그 사실을 통째로 잊고 처음부터 다시 맞춘다.
  KMP 는 그 사실을 `matched` 라는 **정수 하나**로 들고 있고, 어긋나면 버리는 대신 `failure` 로 "얼마까지는 여전히 유효한가"로 줄인다.
  정보를 저장하는 비용이 상수(정수 하나) + 전처리 O(m) 이라는 것이 이 설계의 값이다.

- Q: KMP 의 거래(최악 제거 ↔ 평균 소폭 손해)는 04번 힙 정렬·08번 투 포인터의 어떤 거래와 같은가?
  A: "**최악을 보장하는 대신 평균의 상수를 조금 내주는**" 같은 거래다.
  04번 힙 정렬: 퀵 정렬보다 평균 상수가 크지만 최악 O(n log n) 을 보장한다.
  08번 투 포인터: 정렬·단조성이라는 전제를 갖추는 비용을 내고 이중 루프의 최악을 없앤다.
  실무 판단 기준도 같다 — 최악이 서비스에 치명적인가(타임아웃·SLA), 아니면 평균 처리량이 더 중요한가.

- Q: "KMP 를 쓸까는 데이터가 정한다"는 판단을 실무에서 하려면 무엇을 먼저 재야 하는가?
  A: ① 본문의 **알파벳 크기**(글자 종류가 몇인가 — 좁을수록 KMP 유리), ② 패턴의 **자기 겹침 정도**(실패 함수 값들이 큰가), ③ 같은 패턴을 **몇 번 재사용**하는가(전처리 O(m) 의 상각), ④ 최악이 실제로 일어날 수 있는 입력인가(적대적 입력을 받는가).
  네 가지가 전부 "데이터의 성질"이지 알고리즘의 성질이 아니다.
  실측 없이 정하면 26종류 케이스처럼 **더 느려지는 최적화**를 하게 된다.
  23번 허프만의 "이득의 출처는 알고리즘이 아니라 데이터"와 같은 교훈이다.

- Q: 전처리 비용 O(m)이 언제 무시할 수 없게 되는가?
  A: 패턴이 본문에 비해 길거나(`m` 이 `n` 에 필적), 같은 패턴을 한 번만 쓰고 버릴 때다.
  본문이 짧고 패턴이 긴 상황(예: n=200, m=150)에서는 전처리 2m 이 전체의 큰 몫이 된다.
  반대로 같은 패턴으로 수천 개 문서를 검색한다면 전처리는 한 번이라 사실상 공짜다.
  그래서 실무 API 는 보통 "패턴 컴파일"과 "검색"을 분리한다(자바 `Pattern.compile` / `matcher`) — 재사용을 노출하는 설계다.

- Q: 27번 문자열 해싱은 같은 문제를 어떤 다른 방식으로 푸는가, 무엇을 맞바꾸는가?
  A: 글자 비교 대신 **구간의 해시값을 비교**한다 — 롤링 해시로 본문의 길이 m 짜리 창의 해시를 O(1)에 갱신하며 훑는다.
  얻는 것: 패턴이 여러 개여도, 길이가 바뀌어도 같은 틀로 다루기 쉽고 구현이 짧다.
  내주는 것: **확률적 정확성** — 해시 충돌로 다른 문자열이 같은 값을 낼 수 있어, 후보에서 실제 비교를 한 번 더 하거나 충돌 확률을 관리해야 한다.
  KMP 는 결정적으로 정확하고 최악이 보장되지만 패턴 하나에 특화된 표를 만든다 — 정확성과 유연성의 맞바꿈이다.

- Q: 실패 함수는 26번 아호-코라식의 무엇으로 일반화되는가?
  A: **실패 링크(failure link)** 로 일반화된다.
  KMP 의 failure 는 "패턴 한 줄" 위에서 되돌아갈 자리를 가리키는 화살표인데, 아호-코라식은 패턴 여러 개를 합친 **트라이의 각 노드**마다 같은 화살표를 둔다.
  가리키는 대상의 정의도 그대로다 — "지금까지 읽은 문자열의 접미사이면서, 어떤 패턴의 접두사인 가장 긴 것".
  즉 자료구조가 배열에서 트리로 바뀌었을 뿐 개념은 같다 — 이 챕터를 제대로 이해하면 26번은 확장에 가깝다.
