#### 1. 고정 폭 — FixedWindow (TODO 1~4)

impl 정답 (`impl/com/algo/window/FixedWindow.java`):

```java
public static long maxSum(CountedArray a, int k) {
    int n = a.size();
    if (k < 1 || k > n) {
        throw new IllegalArgumentException("창 폭이 잘못됐다: k=" + k + ", 길이=" + n);
    }

    long sum = 0;
    for (int i = 0; i < k; i++) {
        sum += a.get(i);
    }
    long best = sum;

    for (int i = k; i < n; i++) {
        // 나간 것을 빼고 들어온 것을 더한다. 창 안을 다시 훑지 않는다.
        sum += a.get(i) - a.get(i - k);
        if (sum > best) {
            best = sum;
        }
    }
    return best;
}
```

`sums`는 같은 뼈대에서 최댓값 갱신 대신 `out[0] = 첫 창의 합`, 이후 `out[i - k + 1] = sum`으로 전부 모은다. 결과 배열 길이는 `n - k + 1`.

**질문별 답**

- Q: k가 0, 음수, 배열 길이보다 클 때 조용히 0을 돌려주지 않고 예외로 막는 이유는?
  A: k ≤ 0이면 창이 무엇인지 정의가 안 되고, k > n이면 창을 하나도 못 놓는다.
  조용히 0을 돌려주면 부르는 쪽이 "합이 0인 창이 있다"로 읽는다.
  답이 없는 것과 답이 0인 것을 구별해야 하므로 `IllegalArgumentException`으로 막는다.
  테스트(`invalidWidth`)가 k=0, -1, n+1, 빈 배열 전부에서 예외를 요구한다.

- Q: 창을 한 칸 밀 때 나가는 원소의 인덱스는 무엇인가?
  A: 들어오는 원소가 `a[i]`일 때 나가는 원소는 `a[i - k]`다.
  창이 `[i-k+1, i]`가 되므로 직전 창의 왼쪽 끝이었던 `i - k`가 빠진다.
  README가 "창을 밀 때 나가는 원소의 인덱스가 가장 자주 어긋난다"고 못박은 자리다.
  `i - k + 1`이나 `i - k - 1`로 쓰면 답이 조용히 틀어진다.

- Q: 창 안을 다시 더하는 방식과 밀어내기 방식의 읽기 횟수는 각각 얼마인가(10,000개·폭 100 측정치)?
  A: 다시 훑기 990,100번(창 9,901개 × 폭 100), 밀어내기 19,900번(첫 창 100 + 이후 칸마다 2).
  약 50배 차이고 **결과는 완전히 같다.**
  격차는 창 폭 k에 비례한다 — 밀어내기는 폭이 얼마든 칸마다 2번이라서.
  k=1이면 차이가 없고 k가 커질수록 벌어진다.

- Q: 합을 int가 아니라 long에 담아야 하는 이유는 — 원소 10만 개에 각 2만~3만이면 합이 얼마인가?
  A: 원소 하나는 int라도 합은 int 범위(약 21.4억)를 넘을 수 있다.
  10만 개 × 2만 = 20억으로 이미 한계에 닿고, 테스트(`sumOverflowsInt`)는 10만 개 × 3만 = 30억으로 확실히 넘긴다.
  int로 담으면 넘친 값이 음수로 돌아 조용히 틀린다.
  그래서 `maxSum`·`sums` 모두 반환형과 누적 변수가 long이다.

- Q: best의 초기값을 0으로 두면 어떤 입력에서 틀리는가?
  A: 전부 음수인 입력. `[-5, -3, -1, -2]`, k=1의 답은 -1인데 0을 돌려주게 된다.
  "최대 합"이 음수일 수 있다는 것을 놓친 것이다.
  테스트(`negatives`)가 정확히 이 입력으로 잡는다.
  impl은 best를 0이 아니라 **첫 창의 합**으로 초기화해서 이 문제가 없다.

- Q: best를 초기화하지 않고 MIN_VALUE로만 두고 첫 창을 비교에 안 넣으면 어떤 입력에서 걸리는가?
  A: 답이 첫 창인 입력. `[10, 9, 1, 1, 1]`, k=2의 답은 첫 창 19다.
  MIN_VALUE로 두고 두 번째 창부터 비교하면 첫 창이 후보에서 빠진다.
  테스트(`bestAtFront`)가 이 실수를 잡는다.
  impl처럼 `best = 첫 창의 합`으로 시작하면 두 실수(0 초기화·첫 창 누락)를 한 번에 피한다.

- Q: 결과 배열(sums)의 길이가 왜 n-k+1인가?
  A: 폭 k 창의 왼쪽 끝이 설 수 있는 자리가 0부터 n-k까지, 총 n-k+1개라서다.
  k = n이면 창이 하나뿐이고(1개), k가 커질수록 놓을 자리가 준다.
  i번째로 미는 창(오른쪽 끝 i)의 합은 `out[i - k + 1]`에 들어간다.
  왼쪽 끝 기준으로 세면 창의 번호가 곧 배열 인덱스다.

- Q: 폭을 10에서 1,000으로 100배 넓혔는데 읽기가 19,990에서 19,000으로 오히려 준 이유는?
  A: 밀어내기는 나가는 것과 들어오는 것만 보므로 폭 자체는 비용에 안 들어간다.
  읽기 = 첫 창 k + 이후 (n-k)칸 × 2 — 폭이 넓으면 창을 놓을 자리(n-k+1)가 줄어 뒤 항이 준다.
  폭 10: 10 + 9,990×2 = 19,990. 폭 1,000: 1,000 + 9,000×2 = 19,000.
  다시 훑는 방식이었다면 폭 1,000에서 약 900만 번을 읽었을 것이다.

```java
public static int shortestAtLeast(CountedArray a, long target) {
    if (target <= 0) {
        throw new IllegalArgumentException("target 은 1 이상이어야 한다: " + target);
    }
    int n = a.size();
    int best = Integer.MAX_VALUE;
    long sum = 0;
    int lo = 0;

    for (int hi = 0; hi < n; hi++) {
        sum += a.get(hi);
        // 조건을 만족하는 동안 왼쪽을 당긴다. 더 짧은 답이 있는지 보는 것이다.
        while (sum >= target) {
            int length = hi - lo + 1;
            if (length < best) {
                best = length;
            }
            sum -= a.get(lo);
            lo++;
        }
    }
    return best == Integer.MAX_VALUE ? 0 : best;
}

public static int longestDistinct(CountedArray a) {
    int n = a.size();
    Map<Integer, Integer> lastSeen = new HashMap<>();
    int best = 0;
    int lo = 0;

    for (int hi = 0; hi < n; hi++) {
        int value = a.get(hi);
        Integer seen = lastSeen.get(value);
        // seen 이 lo 보다 왼쪽이면 이미 창 밖이다. 그때 lo 를 되돌리면 안 된다.
        if (seen != null && seen >= lo) {
            lo = seen + 1;
        }
        lastSeen.put(value, hi);

        int length = hi - lo + 1;
        if (length > best) {
            best = length;
        }
    }
    return best;
}
```

**질문별 답**

- Q: 왼쪽을 당기는 것이 `if`가 아니라 `while`이어야 하는 이유는?
  A: 오른쪽이 한 칸 전진했을 때 조건(sum ≥ target)이 여러 칸 연속으로 유지될 수 있어서다.
  위 그림의 hi=4에서 두 번 연속 당긴 것이 그 예다.
  `if`로 쓰면 한 칸만 당기고 멈춰 더 짧은 답을 놓친다.
  "한 칸 전진에 여러 칸 당김"이 가변 폭의 기본 모양이다.

- Q: 답의 길이를 당기기 전에 재야 하는 이유는 — 당긴 뒤에 재면 무엇이 틀리는가?
  A: 조건이 참인 순간의 창이 답 후보이기 때문이다.
  impl도 while 안에서 `length = hi - lo + 1`을 먼저 재고 그다음에 빼고 당긴다.
  당긴 뒤에 재면 이미 조건이 깨졌을 수 있는 한 칸 짧은 창을 재서 답이 한 칸씩 짧아진다.
  README가 함정 절에 "당긴 뒤에 재면 한 칸씩 짧아진다"로 명시한 자리다.

- Q: 답이 없을 때 무엇을 돌려주고, 그것을 "합이 0인 답"과 어떻게 구분하는가?
  A: 0을 돌려준다(`못 채우면 0` 테스트).
  구현 안에서는 best를 `Integer.MAX_VALUE`로 두고, 끝까지 갱신이 없으면 0으로 바꿔 돌려준다.
  길이가 0인 정상 답은 존재하지 않으므로(구간 길이는 최소 1) 0이 "없음"의 표지로 쓸 수 있다.
  target ≤ 0을 계약으로 막았기에 "빈 구간이 답"인 경우도 생기지 않는다.

- Q: 안쪽 while이 있는데도 전체 읽기가 2n(측정 19,822)을 못 넘는 이유는?
  A: hi는 n칸, lo도 **전체를 통틀어** 최대 n칸 움직이고 둘 다 되돌아가지 않는다.
  안쪽 while이 한 번에 여러 칸을 갈 수는 있지만 총합이 n을 못 넘는다.
  읽기는 hi 전진마다 1번 + lo 당김마다 1번이라 합계 ≤ 2n — 측정 19,822 ≤ 20,000.
  한 번의 최악(while이 n번 도는 경우)이 아니라 전체의 합을 보는 것 — 이게 상환 분석이다.

- Q: 값에 음수가 섞이면 이 방법이 왜 무너지는가?
  A: "창을 줄이면 합이 반드시 준다"가 왼쪽을 당겨도 되는 근거인데, 음수가 있으면 그 보장이 사라진다.
  음수를 빼면 합이 오히려 늘 수 있어, 당기고 지나친 구간에 더 짧은 답이 숨어 있을 수 있다.
  "줄여도 되는 이유"가 사라지는 순간 기법째 못 쓴다.
  그 문제는 10번 누적 합으로 푼다(테스트 주석에도 명시).

- Q: target이 0 이하일 때 답이 모호해지는 이유와 예외(계약)로 막은 이유는?
  A: 빈 구간의 합이 0이라 target ≤ 0이면 빈 구간이 이미 조건을 만족한다.
  그러면 "가장 짧은 길이"가 0인지 1인지 말로 정하기 나름이고, 정하지 않으면 구현마다 다르다.
  모호한 답을 조용히 주면 부르는 쪽이 구현의 우연에 기대게 된다.
  그래서 `IllegalArgumentException`으로 막았다 — 모호한 입력을 계약으로 막는 것도 답이다.

- Q: longestDistinct에서 같은 값을 다시 만나면 lo를 어디로 옮기는가?
  A: 그 값을 마지막으로 본 자리(seen)의 **바로 다음 칸**, 즉 `lo = seen + 1`로 옮긴다.
  그래야 창 안에 그 값이 한 번만 남는다.
  한 칸씩 당기는 대신 기억해 둔 자리로 한 번에 점프하는 것이 요점이다.
  옮긴 뒤 `lastSeen.put(value, hi)`로 현재 자리를 새로 기억한다.

- Q: 다시 만난 값의 자리가 이미 창 밖이면 왜 lo를 옮기면 안 되는가?
  A: `seen < lo`이면 그 중복은 이미 창에 없으므로 창은 여전히 유효하다.
  그런데도 `lo = seen + 1`로 옮기면 lo가 **뒤로 되돌아가** 창이 커지고 중복이 다시 들어온다.
  테스트 예: `[1, 9, 1, 2, 3, 4]`에서 되돌리는 판은 답 5 대신 4를 준다.
  그래서 조건이 `seen != null && seen >= lo`다 — lo = max(lo, seen+1)과 같은 뜻.

- Q: longestDistinct의 읽기가 2n이 아니라 정확히 n(측정 10,000)인 이유는?
  A: 배열 읽기는 `a.get(hi)` — 각 원소를 hi가 지나갈 때 딱 한 번뿐이다.
  왼쪽을 당길 때 값을 다시 읽지 않는다 — 해시맵(값→마지막 자리)이 그 정보를 대신 들고 있다.
  lo를 한 칸씩 당기며 다시 읽는 판이었다면 shortestAtLeast처럼 2n이 됐을 것이다.
  기억해두는 것으로 다시 읽기를 없앤 거래다 — 같은 상환 선형인데 상수가 절반이다.

#### 3. 단조 덱 — SlidingMax (TODO 7~9)

impl 정답 (`impl/com/algo/window/SlidingMax.java`):

```java
public static int[] maxOfEachWindow(CountedArray a, int k, CountedDeque deque) {
    int n = a.size();
    if (k < 1 || k > n) {
        throw new IllegalArgumentException("창 폭이 잘못됐다: k=" + k + ", 길이=" + n);
    }

    int[] out = new int[n - k + 1];
    for (int hi = 0; hi < n; hi++) {
        int value = a.get(hi);

        // 뒤에서부터, 새 값보다 작거나 같은 것들을 버린다.
        while (!deque.isEmpty() && a.get(deque.peekLast()) <= value) {
            deque.pollLast();
        }
        deque.addLast(hi);

        // 앞쪽이 창 밖으로 나갔으면 버린다. 창이 한 칸씩만 움직이므로 if 로 충분하다.
        if (deque.peekFirst() <= hi - k) {
            deque.pollFirst();
        }

        if (hi >= k - 1) {
            out[hi - k + 1] = a.get(deque.peekFirst());
        }
    }
    return out;
}
```

```
 hi=1(3)  : 뒤 a[0]=1 <= 3 -> 버림 -> 넣음 [1(3)]        창 미완성
 hi=2(-1) : 3 > -1 -> 그냥 넣음 [1(3), 2(-1)]            out[0] = a[1] = 3
 hi=3(-3) : [1(3), 2(-1), 3(-3)]  앞 1 <= 3-3=0 ? 아니오 out[1] = 3
 hi=4(5)  : -3, -1, 3 전부 <= 5 -> 셋 다 버림 -> [4(5)]   out[2] = 5
 hi=5(3)  : 5 > 3 -> [4(5), 5(3)]                        out[3] = 5
 hi=6(6)  : 3, 5 <= 6 -> 버림 -> [6(6)]                  out[4] = 6
 hi=7(7)  : 6 <= 7 -> 버림 -> [7(7)]                     out[5] = 7
 결과: [3, 3, 5, 5, 6, 7]

 덱은 항상 값 내림차순 — 앞이 최댓값 후보의 우두머리.
 뒤에서 빠짐 = 새 값에 밀려남 / 앞에서 빠짐 = 창 밖으로 나감. 나간 원소는 다시 안 들어온다.
```

**질문별 답**

- Q: 새 값이 들어올 때 덱의 뒤에서 무엇을 버리는가, 버려도 되는 근거는 무엇인가?
  A: 새 값보다 작거나 같은 뒤쪽 원소들을 전부 버린다(`a.get(peekLast()) <= value`인 동안 pollLast).
  근거: 새 값보다 작으면서 더 왼쪽에 있는 값은 앞으로 어떤 창에서도 최댓값이 될 수 없다.
  그 값이 들어 있는 미래의 창에는 새 값도 반드시 같이 들어 있기 때문이다(새 값이 더 오른쪽이라 더 늦게 나간다).
  08번 투 포인터의 "버려도 되는 이유" 논증과 같은 종류다.

- Q: 버릴 때 등호를 포함해(`<=`) 같은 값까지 버리는 이유는?
  A: 답은 `<`로 해도 같다 — 테스트(`allEqual`)도 두 판 모두 통과한다고 명시한다.
  같은 값이면 오른쪽 것이 창에 더 오래 살아남으므로 왼쪽 것은 있어도 쓸모가 없다.
  왼쪽을 버리면 덱이 짧게 유지돼 비용(덱 크기·빼기 횟수)이 준다.
  `[7,7,7,7]`에서 `<=`는 덱에 하나만 남고 `<`는 전부 남는다.

- Q: 덱에 값이 아니라 인덱스를 담아야 하는 이유는?
  A: 값만으로는 그 원소가 창 밖으로 나갔는지 알 방법이 없다.
  같은 값이 여러 번 나오면 어느 것이 나간 것인지도 구분이 안 된다 — `[5, 1, 5, 1, 4]`에서 5가 두 개다.
  인덱스를 담으면 "자리 ≤ hi - k" 하나로 창 밖 판정이 끝난다.
  값이 필요할 때는 인덱스로 배열을 다시 읽는다(`a.get(deque.peekFirst())`).

- Q: "앞쪽이 창 밖으로 나갔다"를 인덱스로 어떻게 판정하는가?
  A: 현재 창은 `[hi - k + 1, hi]`이므로, 창 밖은 인덱스가 `hi - k + 1`보다 작다는 것이다.
  코드로는 `deque.peekFirst() <= hi - k`.
  참이면 pollFirst로 앞에서 버린다.
  이 검사를 빼먹으면 이미 나간 옛 최댓값을 계속 답으로 준다(내림차순 테스트가 잡는다).

- Q: 앞쪽 버리기가 `while`이 아니라 `if`여도 되는 이유는, 언제 깨지는가?
  A: 창이 **한 칸씩만** 움직여서, 한 번의 전진에 창 밖으로 나가는 원소가 최대 하나이기 때문이다.
  덱 안 원소는 인덱스 오름차순이라 앞 하나만 검사하면 충분하다.
  창이 두 칸씩 움직이는 변형을 만들면 이 줄이 조용히 틀린다 — README 「생각해볼 것」의 그 자리다.
  impl 주석은 이 검사를 addLast 앞으로 옮겨도 결과가 같다는 것도 변종으로 확인했다(대신 isEmpty 검사가 하나 더 필요).

- Q: 답을 언제부터 기록하는가 — 창이 아직 다 안 찼을 때도 기록하면 어떻게 되는가?
  A: 첫 창이 완성되는 `hi = k - 1`부터, 조건 `hi >= k - 1`일 때만 `out[hi - k + 1]`에 기록한다.
  그 전에 기록하면 폭이 k가 안 되는 "덜 찬 창"의 최댓값이 결과에 섞인다.
  결과 배열 길이도 n-k+1이라 인덱스 계산 자체가 어긋난다.
  위 그림에서 hi=0,1은 "창 미완성"으로 기록을 건너뛴다.

- Q: 덱의 맨 앞이 왜 항상 현재 창의 최댓값인가?
  A: 세 규칙의 합작이다: ① 뒤에서 새 값 이하를 버리므로 덱은 항상 값 내림차순이고
  ② 앞에서 창 밖 인덱스를 버리므로 덱에 남은 것은 전부 창 안이며
  ③ 창 안의 최댓값은 덱에서 절대 안 버려진다(자기보다 큰 새 값이 없었으니까).
  따라서 "창 안에 있는 후보들 중 가장 큰 것"이 맨 앞에 있다.

- Q: 넣기 횟수가 입력(무작위·오름·내림차순)과 무관하게 정확히 n인 이유는, 이 숫자가 왜 "O(n)" 주장의 증명인가?
  A: `deque.addLast(hi)`가 for 루프에서 원소마다 무조건 한 번 실행되기 때문이다 — 측정도 세 입력 전부 넣기 10,000.
  한 번 나간 원소는 다시 안 들어오므로 전체 빼기는 전체 넣기(n)를 못 넘는다(무작위 9,996 ≤ 10,000).
  그래서 안쪽 while이 한 창에서 여러 번 돌아도 전체 덱 연산은 최대 2n — 이게 O(n)의 근거 전부다.
  코드만 보면 O(nk)처럼 보이는 것을 전체 합산 숫자가 반증한다 — 상환 분석이 숫자로 드러난 자리.

- Q: 오름차순 입력과 내림차순 입력에서 빼기가 일어나는 자리(앞/뒤)는 어떻게 다른가?
  A: 오름차순(빼기 9,999)은 새 값이 항상 앞의 것들을 밀어내 **뒤에서** 빠진다 — 덱에 한 개씩만 남는다.
  내림차순(빼기 9,900)은 밀려나는 것이 없고 창 밖으로 나가서만 **앞에서** 빠진다.
  합계는 비슷한데 안에서 일어나는 일이 정반대다 — 숫자 하나만 보면 그 차이를 놓친다.
  테스트도 "두 입력을 다 넣어야 앞뒤 두 가지 빼기가 모두 실행된다"고 적어 두었다.

- Q: 덱 방식의 격차(25배)가 고정 폭 밀어내기(50배)보다 작은 이유는?
  A: 덱에 인덱스만 담으므로 값을 확인할 때마다 배열을 다시 읽기 때문이다.
  뒤에서 버릴 때 `a.get(peekLast())`, 답을 적을 때 `a.get(peekFirst())` — 측정 읽기 39,685 대 다시 찾기 990,100.
  인덱스와 값을 같이 담으면 읽기가 줄지만 메모리가 는다 — 또 하나의 거래다.
  기법이 나빠서가 아니라 표현(인덱스만 저장)의 대가다.

- Q: 덱을 함수 안에서 만들지 않고 밖에서 주입받는 이유는?
  A: 테스트가 넣고 뺀 횟수를 세기 위해서다.
  "단조 덱이 O(n)"이라는 주장은 "각 원소가 최대 한 번 들어가고 한 번 나온다"에 기대는데,
  안쪽 while만 보면 그게 안 보인다 — 창 하나에서 여러 개를 뺄 수도 있어서다.
  전체를 통틀어 세야 확인되므로, 계측기(CountedDeque)를 밖에서 만들어 넘긴다.

### B. 개념

#### 4. 생각해볼 것 (원본 README 이관)

- Q: 창이 두 칸씩 움직이는 문제라면 어디가 깨지나 — `if`로 쓴 자리가 있다?
  A: SlidingMax의 앞쪽 버리기 `if (deque.peekFirst() <= hi - k)`가 깨진다.
  이 줄이 if로 충분한 근거가 "한 칸에 나가는 원소는 최대 하나"였는데, 두 칸씩 움직이면 한 번에 둘이 나갈 수 있다.
  if는 하나만 버리므로 창 밖 원소가 덱 앞에 남아 틀린 최댓값을 준다 — 그것도 조용히.
  고치려면 while로 바꿔 창 밖 원소를 전부 버려야 한다.

- Q: 각 창의 **중앙값**을 구하려면 — 덱으로 되나, 안 되면 무엇이 필요한가?
  A: 단조 덱으로는 안 된다 — 덱은 "최댓값이 될 수 없는 후보"를 버리는데, 버린 원소도 중앙값에는 필요하다.
  중앙값은 창 안 **전체**의 순서 정보를 요구하므로 원소를 버릴 수 없다.
  창 안 원소를 정렬 상태로 유지하며 넣고 빼는 구조(예: 힙 두 개 — 아래 절반 최대 힙 + 위 절반 최소 힙, 또는 균형 탐색 트리)가 필요하다. (원본에 근거 없음 — 내 추론)
  비용도 원소당 O(log k)로 올라간다. (원본에 근거 없음 — 내 추론)

- Q: 가변 폭에 음수를 허용하려면 무엇으로 바꿔야 하나(10번 누적 합이 힌트다)?
  A: 창을 밀며 줄이는 방식 자체를 버리고, 10번 챕터의 누적 합(prefix sum)으로 바꾼다.
  가변 폭의 전제 "창을 줄이면 합이 준다"가 음수에서 깨지기 때문에 고쳐서 될 문제가 아니다.
  누적 합은 구간 합을 `prefix[j] - prefix[i]`로 계산하므로 값의 부호에 기대지 않는다.
  서머리·테스트 주석 모두 "그 문제는 10번 누적 합으로 푼다"고 연결해 두었다.

- Q: `longestDistinct`의 해시맵을 배열로 바꿀 수 있나, 그 조건이 무엇인가?
  A: 값의 범위가 작고 미리 알려져 있으면 된다 — `lastSeen[value]` 배열로 값→마지막 자리를 담는다. (원본에 근거 없음 — 내 추론)
  예를 들어 값이 0~255의 문자 코드라면 크기 256짜리 int 배열이면 충분하다. (원본에 근거 없음 — 내 추론)
  해시 계산과 박싱(int→Integer)이 없어져 상수가 준다.
  범위가 크거나 모르면(임의의 int) 배열이 너무 커져 해시맵으로 돌아간다.

#### 5. 파생 질문 (서머리 기반)

- Q: 슬라이딩 윈도우의 본질("창 안을 다시 계산하지 않는다")을 일상 예 하나로 설명하면?
  A: "최근 7일 매출 합"을 매일 보는 편의점 사장님.
  매일 7일 치를 다시 더하면 하루 7번이지만, 어제의 합에서 8일 전 매출을 빼고 오늘 매출을 더하면 2번이다.
  결과는 완전히 같고, 나간 것과 들어온 것만 처리한다는 점이 핵심이다.
  그래서 창 폭이 얼마든 칸마다 하는 일이 상수다.

- Q: 세 가지 모양(고정 폭·가변 폭·단조 덱)의 창 움직임은 각각 어떻게 다른가?
  A: 고정 폭은 양끝이 붙어서 같이 간다 — 폭 k가 일정하다.
  가변 폭은 오른쪽은 매 칸 나아가고 왼쪽은 조건이 만족될 때만 따라간다 — 폭이 늘었다 줄었다 한다.
  단조 덱은 고정 폭 창에 "최댓값 후보 목록"(덱)을 하나 더 얹은 것이다.
  문제가 "구간 합"이면 앞 둘, "구간 최댓값"이면 셋째다.

- Q: 셋 다 O(n)인 공통 근거는 무엇인가?
  A: **되돌아가지 않는다** — lo도 hi도, 덱의 원소도.
  포인터는 전체를 통틀어 각각 최대 n칸만 움직이고, 덱 원소는 한 번 나가면 다시 안 들어온다.
  그래서 안쪽 루프가 있어도 전체 연산 총합이 2n 안쪽이다.
  한 번의 최악이 아니라 전체의 합으로 세는 것이 성립 조건이다.

- Q: 상환 분석이란 무엇이고, 이 챕터의 어떤 측정 숫자가 그것을 보여주는가?
  A: 연산 한 번의 최악이 아니라 전체 수행의 총합으로 비용을 재는 방법이다.
  가변 폭: 안쪽 while이 있는데 전체 읽기 19,822 ≤ 2×10,000.
  단조 덱: 안쪽 while이 있는데 전체 넣기 정확히 10,000, 빼기 9,996 ≤ 넣기.
  둘 다 "코드만 보면 O(n²)/O(nk)처럼 보이는데 총합은 선형"을 숫자로 보여준다.

- Q: 08번 투 포인터와 슬라이딩 윈도우는 어떤 관계인가?
  A: 슬라이딩 윈도우는 같은 방향 투 포인터의 연장이다 — lo·hi 두 포인터가 같은 방향으로만 간다.
  거기에 "창"이라는 해석(두 포인터 사이가 유지하는 구간 상태 — 합·중복 여부·최댓값 후보)이 얹힌다.
  O(n)의 근거(포인터가 되돌아가지 않는다)도 08번과 같다.
  단조 덱의 "버려도 되는 이유" 논증도 08번의 재등장이다.

- Q: 단조 덱의 "버려도 되는 이유" 논증은 08번의 어떤 사고방식의 재등장인가?
  A: "이 후보는 앞으로 어떤 경우에도 답이 될 수 없다 — 그러니 지금 버려도 안전하다"는 배제 논증이다.
  단조 덱에서는: 새 값보다 작고 더 왼쪽인 원소는, 그것이 든 모든 미래의 창에 새 값도 들어 있으므로 최댓값이 못 된다.
  후보를 미리 버리는 것이 곧 일을 줄이는 것이고, 정당성은 "버린 것이 답일 수 없다"는 증명에서 온다.
  버리는 근거를 말로 설명 못 하면 그 최적화는 믿으면 안 된다.

- Q: "O(n)이다"라는 주장을 코드 모양이 아니라 계측 숫자로 확인한다는 말의 뜻은?
  A: 코드 모양(루프 중첩)은 O(n²)처럼 보이는데 실제 총 연산 수는 선형일 수 있다 — 모양은 증거가 아니다.
  그래서 계측기(CountedArray 읽기, CountedDeque 넣기/빼기)로 전체 횟수를 직접 센다.
  "넣기 = 정확히 n, 빼기 ≤ n" 같은 숫자가 나오면 그것이 주장의 증명이다.
  이 챕터 제목의 문장 "안쪽 루프가 있는데도 O(n)이다를 숫자로 확인한다"가 정확히 이 뜻이다.

- Q: 가변 폭이 못 푸는 문제(음수 섞인 구간 합)는 어느 챕터의 어떤 도구가 푸는가?
  A: 10번 챕터의 누적 합(prefix sum)이다.
  가변 폭은 "창을 줄이면 합이 준다"(전부 양수)는 단조성 전제가 있어야 성립한다.
  음수가 섞이면 그 전제가 깨져 기법째 못 쓴다.
  누적 합은 구간 합을 두 누적값의 차로 계산하므로 부호와 무관하다.
