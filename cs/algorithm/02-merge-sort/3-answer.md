### A. 과제 (TODO 1~10)

#### 1. 병합 — 공유 부품 (TopDownMergeSort.merge, TODO 3)

기준 코드 (impl):

```java
static <T> void merge(CountedArray<T> a, CountedArray<T> aux, int lo, int mid, int hi) {
    for (int k = lo; k <= hi; k++) aux.copyFrom(k, a, k);  // 통째로 복사

    int i = lo, j = mid + 1;
    for (int k = lo; k <= hi; k++) {
        if (i > mid)                  a.copyFrom(k, aux, j++);  // 왼쪽 소진
        else if (j > hi)              a.copyFrom(k, aux, i++);  // 오른쪽 소진
        else if (aux.compare(j, i) < 0) a.copyFrom(k, aux, j++); // 오른쪽이 "엄격히" 작을 때만
        else                          a.copyFrom(k, aux, i++);   // 같으면 왼쪽 먼저 → 안정성
    }
}
```

- a 에 순서대로 되돌려 **쓰면서** 동시에 a 를 읽으면 아직 안 옮긴 원소를 덮어쓴다. 그래서 먼저 aux 로 스냅샷을 떠 놓고, 읽기는 aux 에서 쓰기는 a 에 한다.
- 왼쪽 소진(`i > mid`): 남은 오른쪽을 그대로 이어 붙인다. 오른쪽 소진(`j > hi`): 남은 왼쪽을 이어 붙인다. 두 경우를 **비교보다 먼저** 검사해야 한다.
- 안 다루면 소진된 쪽 손가락이 구간 밖(mid 너머 / hi 너머)을 읽어 범위를 넘는다(ArrayIndexOutOfBounds 계열).
- 같으면 **왼쪽을 먼저** 가져온다(`compare(j, i) < 0` — 오른쪽이 엄격히 작을 때만 오른쪽). 같은 값의 원래 순서(왼쪽 구간이 원래 앞)가 유지된다 — 이 한 줄이 병합 정렬의 안정성 전부다.
- 값만 보면 같은 값 두 개의 순서는 구별되지 않으므로 결과 배열의 **내용**은 어느 쪽이든 같다. 깨지는 것은 내용이 아니라 같은 값끼리의 상대 순서다.

#### 2. 하향식 (TopDownMergeSort, TODO 1~2)

기준 코드 (impl):

```java
public <T> void sort(CountedArray<T> a) {
    if (a.size() < 2) return;
    CountedArray<T> aux = a.allocate(a.size());  // 한 번만 만든다
    sort(a, aux, 0, a.size() - 1);
}
private <T> void sort(CountedArray<T> a, CountedArray<T> aux, int lo, int hi) {
    if (lo >= hi) return;
    int mid = lo + (hi - lo) / 2;   // (lo+hi)/2 는 큰 인덱스에서 넘친다
    sort(a, aux, lo, mid);
    sort(a, aux, mid + 1, hi);
    merge(a, aux, lo, mid, hi);
}
```

- 병합마다 만들어도 결과·비교 횟수는 같다(매번할당 판이 그 증거). 다른 것은 **할당 횟수와 총 할당 칸**(1회 1,000칸 vs 999회 9,976칸)뿐 — 위에서 한 번 만들어 돌려 쓰는 게 낭비를 없앤다.
- 종료 조건은 `lo >= hi` — 원소가 하나 이하인 구간은 이미 정렬돼 있으므로 그냥 돌아온다.
- `(lo + hi) / 2` 는 lo + hi 가 int 최대값(약 21억)을 넘는 순간 음수로 넘쳐 엉뚱한 mid 가 나온다. 원소가 10억 개를 넘는 배열에서 터진다 — 자바 라이브러리가 2006년에 고친 그 버그.
- 테스트로 못 잡는다: 그런 크기의 배열을 테스트에서 만들 수 없다. 변종을 심어도 68개 테스트가 전부 통과했다(README). **테스트가 없는 규칙은 주석이 유일한 방어선**이다.
- 올바른 식: `int mid = lo + (hi - lo) / 2;` — 차(hi-lo)는 절대 안 넘친다.

#### 3. 매번할당 (NaiveMergeSort, TODO 4~5)

기준 코드 (impl, 병합부):

```java
private <T> void merge(CountedArray<T> a, int lo, int mid, int hi) {
    CountedArray<T> aux = a.allocate(hi - lo + 1);      // 병합마다 새로
    for (int k = lo; k <= hi; k++) aux.copyFrom(k - lo, a, k);  // aux 는 0부터

    int i = 0;                  // 하향식의 lo 가 여기서는 0
    int j = mid - lo + 1;       // 하향식의 mid+1 이 여기서는 mid-lo+1
    int end = hi - lo;          // 하향식의 hi 가 여기서는 hi-lo
    ...
}
```

- 하향식은 aux 가 a 와 같은 크기라 `lo..hi` 인덱스가 그대로 통했다. 여기서는 aux 가 구간 길이만큼이라 **전부 lo 만큼 당겨야** 한다: 복사는 `k - lo` 로, 손가락은 `i = 0`, `j = mid - lo + 1`, 끝은 `end = hi - lo`. 이 어긋남이 가장 자주 틀리는 지점이다.
- n 개 정렬 = 병합 n-1 번 = 할당 n-1 번. 1,000개 실측: 할당 999회, 총 9,976칸(하향식은 1회 1,000칸).
- 비교 8,731·쓰기 19,952·결과 배열까지 하향식과 **완전히 같다**. 다른 것은 할당뿐이다.
- 할당은 결과에 아무 흔적을 남기지 않는다 — 반환값도 배열 내용도 똑같으니 "돌려보니 잘 되던데요"가 통한다. 비용(GC 압력·메모리)을 **세는 계측기**가 있어야만 나쁨이 숫자로 보인다.

#### 4. 상향식 (BottomUpMergeSort, TODO 6~7)

기준 코드 (impl):

```java
for (int width = 1; width < n; width *= 2) {
    for (int lo = 0; lo < n - width; lo += 2 * width) {
        int hi = Math.min(lo + 2 * width - 1, n - 1);   // 짧은 마지막 조각 자르기
        TopDownMergeSort.merge(a, aux, lo, lo + width - 1, hi);
    }
}
```

- 폭이 n 이상이면 배열 전체가 한 조각이라 합칠 상대가 없다 — `width < n` 에서 멈춘다. `width <= n` 으로 잘못 써도 결과·비교 횟수는 같다(impl 주석 — width = n 이면 안쪽 조건 `lo < n - width` 가 `lo < 0` 이 되어 한 번도 안 돈다). 01번 셸의 간격 시작값과 같은 종류 — 틀림이 아니라 빈 바퀴 하나의 낭비.
- 병합 한 번이 왼쪽 조각(width) + 오른쪽 조각(width) = `2 * width` 개를 소비한다. 다음 병합 쌍은 그 뒤에서 시작하므로 lo 는 `2 * width` 씩 건너뛴다.
- 짧은 경우: `hi = Math.min(lo + 2*width - 1, n - 1)` — 배열 끝을 넘지 않게 자른다. 이걸 빼면 범위를 넘는다.
- 아예 없는 경우: 오른쪽 조각이 시작하려면 `lo + width < n` 이어야 한다. 안쪽 루프 조건 `lo < n - width` 가 그것 — 왼쪽 조각만 남았으면 병합할 게 없으니 돌지 않는다.
- 하향식은 항상 절반으로 자르지만 상향식은 앞에서부터 고정 폭으로 자른다. n 이 2의 거듭제곱이 아니면 마지막 조각이 짧거나 없어서 경계 처리 둘(TODO 7)이 필요하다 — 계약 테스트가 길이 0~64를 전부 도는 이유.
- 재귀가 없으므로 스택 깊이 문제가 없다. 배열이 아주 커도 안전하다.

#### 5. 손본것 (TunedMergeSort, TODO 8~10)

기준 코드 (impl):

```java
private <T> void sort(CountedArray<T> a, CountedArray<T> aux, int lo, int hi) {
    if (hi - lo + 1 <= CUTOFF) { insertion(a, lo, hi); return; }   // TODO 8
    int mid = lo + (hi - lo) / 2;
    sort(a, aux, lo, mid);
    sort(a, aux, mid + 1, hi);
    if (a.compare(mid, mid + 1) <= 0) return;                      // TODO 9: 병합 생략
    TopDownMergeSort.merge(a, aux, lo, mid, hi);
}
private <T> void insertion(CountedArray<T> a, int lo, int hi) {    // TODO 10
    for (int i = lo + 1; i <= hi; i++)
        for (int j = i; j > lo && a.compare(j, j - 1) < 0; j--)
            a.swap(j, j - 1);
}
```

- 짧은 구간(CUTOFF=7 이하)에서는 재귀 호출과 복사가 비교보다 비싸다. O(n^2) 라도 상수가 작은 삽입 정렬이 이긴다. 단, 위쪽 병합이 이 구간을 "정렬됨"으로 믿으므로 삽입 정렬이 정말 정렬을 마쳐야 한다.
- 왼쪽 구간의 마지막(`mid`)이 오른쪽 구간의 처음(`mid+1`)보다 크지 않으면 두 구간을 이어 붙인 전체가 이미 정렬돼 있다 — 병합할 필요가 없다.
- 비교 1번으로 그 구간의 복사 전체(aux 왕복 2·(hi-lo+1)회)를 아낀다. 정렬된 입력 1,000개에서 비교 999·**쓰기 0** — 배열을 한 번도 안 건드리고 끝난다. 반대로 경계 비교가 한 번도 성립하지 않는 입력(무작위·역순)에서는 그 비교가 전부 헛돌아 비교가 3.6%~19% 늘어난다.
- `i = lo + 1` 시작과 안쪽 루프의 `j > lo` 경계 — 01번 버릇대로 0 을 쓰면 구간 밖(다른 재귀가 맡은 영역)을 건드린다.
- 인접 교환(`swap(j, j-1)`)만, 그것도 엄격 부등호(`< 0`)일 때만 하므로 같은 값끼리는 자리를 바꾸지 않는다 — 안정성 유지.

### B. 개념

#### 6. 생각해볼 것 (원본 README 이관)

- 쓰기가 입력과 무관한 이유: 병합은 조건과 상관없이 매번 "구간을 aux 로 복사 + a 로 되돌려 쓰기"를 하고, 분할 모양은 입력 값이 아니라 **길이만으로** 정해진다. 그래서 쓰기 = 층수 × 2n 으로 고정(1,000개에서 19,952). 비교만 입력에 따라 조금 변한다.
- 장점이자 단점이다: 예측 가능성(최악이 없다, 실시간·외부 저장 병합에 유리)은 장점, 이미 정렬된 입력에서도 똑같이 다 쓰는 낭비는 단점 — 그 낭비를 줄인 게 손본 판(정렬됨에서 쓰기 0)이다. (원본은 질문만 — 판정은 내 추론이나, 손본 판의 측정이 근거)
- 역순이 비교가 적은 이유: 병합에서 비교가 최대(구간 길이-1)가 되는 건 양쪽이 번갈아 나올 때다. 역순은 병합 때마다 **한쪽이 통째로 먼저 소진**되는 극단 — 소진 뒤의 나머지는 비교 없이 복사만 되므로 비교가 최소 쪽(n/2 수준)으로 붙는다. (원본은 질문만 — merge 코드의 소진 분기에서 추론)
- 보조 배열 없는(in-place) 병합: 가능하지만 원소를 회전·블록 이동으로 밀어야 해서 시간이 늘거나(쓰기 O(n log n) 초과) 구현이 극도로 복잡해지고 안정성 유지가 어렵다 — 메모리 O(n) 을 아끼는 대가로 시간·단순성을 내준다. (원본에 근거 없음 — 내 추론)
- 팀소트는 **손본것**에 가장 가깝다: 짧은 구간 삽입 정렬(컷오프) + 이미 정렬된 구간(런)을 감지해 병합을 건너뛰는 아이디어의 확장판이다. (원본은 질문만 — 판정은 내 추론)

#### 7. 측정이 알려준 것 (파생)

- 매번할당의 나쁨: 반환값·결과 배열·비교·쓰기가 전부 같으니 **관측 가능한 출력에 차이가 없다**. 할당(GC 부담)은 결과에 흔적을 안 남긴다 — 세지 않으면 안 보인다. 그래서 이 챕터가 계측기에 할당 계수기를 붙였다.
- `log2(n!)`: n개의 순열 n! 가지를 비교(예/아니오)로 구별하려면 최소 log2(n!) 번 필요하다는 정보 이론적 하한. n=1,000에서 8,530이고 병합 정렬은 8,731 — 2.4% 차이까지 붙는다.
- 그 이상 잘하려면 **비교 자체를 포기**해야 한다 — 값을 자릿수·인덱스로 직접 쓰는 05번(계수·기수 정렬)으로 이어진다.
- 손본 판: 정렬됨에서 비교 999·쓰기 0 으로 압도적이지만, 무작위에서 비교 +3.6%(9,042 vs 8,731), 역순에서 +19%(5,867 vs 4,932) — 경계 비교가 성립 안 하면 전부 헛돈다. 특정 입력의 이득을 다른 입력의 비용으로 산 **맞바꾸기**다.
- n 이 2의 거듭제곱이면 하향식의 "항상 절반"과 상향식의 "고정 폭 1,2,4,…"가 **같은 분할 모양**이 된다. 같은 조각을 같은 순서 구조로 병합하니 비교 횟수까지 같다(1,024개에서 둘 다 8,966).

#### 8. 구조와 경계 (파생)

- 분할이 입력 값과 무관하게 길이 절반으로 정해지므로 층수는 항상 log n, 층마다 병합 총량은 n — 입력이 무엇이든 O(n log n). (퀵 정렬과의 대비: 그쪽은 분할이 값에 달려 최악 O(n^2))
- 안정성 = merge 의 `else if (aux.compare(j, i) < 0)` 한 줄 — 오른쪽이 **엄격히** 작을 때만 오른쪽을 가져오고 같으면 왼쪽 먼저.
- 01번과의 거래: 추가 메모리 O(n)(+ 재귀 스택)을 내주고 "입력과 무관한 O(n log n) + 안정성"을 샀다. 01번은 제자리 O(1)이지만 최악 O(n^2)였다.
- 스택이 걱정되면 **상향식** — 재귀 없이 반복문만 쓰므로 스택 깊이 문제가 없다.
