# algorithm/02-merge-sort — 정리 (힌트)

## 해결하는 문제

01번의 네 정렬은 n이 커지면 O(n²)의 벽에 부딪힌다 — 100만 건이면 비교가 5×10¹¹번이다.\
그리고 "입력이 어떻게 생겼든 같은 시간"과 "같은 값의 순서 유지(안정)"를 **둘 다** 주는 정렬이 필요할 때가 있다 — 이름순 명단을 점수순으로 다시 정렬해도 동점자는 이름순이어야 하는 경우.

```text
정렬된 두 묶음이 있으면 합치기는 쉽다 — 맨 앞끼리만 비교해 작은 쪽을 꺼낸다
  A: [2, 5, 8]      B: [1, 4, 9]
      ^                 ^          1 < 2 -> 1 꺼냄
  A: [2, 5, 8]      B: [4, 9]
      ^                 ^          2 < 4 -> 2 꺼냄   ... n번이면 끝: O(n)
```

쉬운 예: 두 반의 키순 명단을 합쳐 전교 키순 명단 만들기 — 두 명단의 맨 앞만 보면 된다.\
똑같은 구조다: "1장짜리는 이미 정렬"에서 시작해 이 합치기를 log n층 반복한 것이 병합 정렬이다.\
실무 예: 자바 `Arrays.sort(Object[])`(팀소트)가 객체 정렬에 이 계열을 쓰고, 메모리보다 큰 파일을 정렬하는 외부 정렬이 "정렬된 조각 여러 개를 합치기"로 돈다.

  - *안정 정렬(stable)*: 같은 값의 원래 순서가 정렬 후에도 유지되는 정렬.
  - *외부 정렬(external sort)*: 데이터가 메모리에 다 안 올라갈 때 조각으로 나눠 정렬해 디스크에 두고 합치는 방식.

### 한눈에 — 쉽게 말하면

**병합 정렬 = 시험지 묶음을 반씩 나눠 각자 정렬시킨 뒤, 두 묶음을 한 장씩 비교하며 합치기.**

- 이미 점수순으로 정렬된 두 묶음이 있으면 합치기는 쉽다: 두 묶음의 **맨 위 장끼리만** 비교해서 작은 쪽을 새 묶음에 놓기를 반복하면 끝.
- 그럼 "정렬된 두 묶음"은 어디서 오나? 각 묶음을 또 반으로 나눠 같은 방법으로.\
  장이 1장이 될 때까지 나누면 1장짜리는 저절로 정렬돼 있다.
- 나누는 깊이는 log n번, 각 층에서 합치는 일은 총 n번 — 그래서 O(n log n).\
  입력이 어떻게 생겼든 이 비용이 거의 안 변한다.
- 대가는 합칠 때 쓸 **보조 배열 O(n)** 하나.\
  제자리 정렬이 아니다.

> **분할 정복(divide and conquer)** — 문제를 반씩 쪼개 각각 풀고 합치는 전략.\
> 예: 병합 정렬이 대표 — "반을 정렬해 와" + "정렬된 둘을 합치기"의 조합이다.

```text
[5, 2a, 8, 2b]   [9, 1, 4]        <- 반으로 나누기를 반복 (1장까지)
      |               |
  정렬: [2a,2b,5,8]  [1,4,9]      <- 각자 같은 방법으로 정렬됨
      \               /
       한 장씩 비교하며 합치기(merge)
      [1, 2a, 2b, 4, 5, 8, 9]
```

이 장은 **같은 알고리즘의 네 가지 판**을 나란히 놓는다: 하향식(기준), 상향식(재귀 없음), 매번할당(보조 배열을 병합마다 새로 만듦), 손본것(라이브러리식 최적화).\
결과는 물론 **비교 횟수까지 같은 쌍이 있는데**, 보조 배열을 1번 만드는 판과 999번 만드는 판이 갈린다 — 실무에서 자바 `Arrays.sort(Object[])`(팀소트)가 이 계열이다.

> **O(n log n)** — n개를 log n층에 걸쳐 층마다 n번씩 처리하는 비용.\
> 예: 100만 개면 층이 약 20개.

> **팀소트(Timsort)** — 자바 `Arrays.sort(Object[])`가 쓰는 실전 정렬.\
> 예: 병합 정렬 계열 + 컷오프/병합 생략류 손질 — 아래 "손본것" 판이 그 축소판이다.

## 동작·원리

### 사전 지식 3줄

> **재귀(recursion)** — 함수가 더 작은 입력으로 자기 자신을 다시 부르는 것.\
> 예: "반을 정렬해 와"를 반이 1칸이 될 때까지 반복.

> **보조 배열(aux)** — 병합할 때 원본을 덮어쓰지 않으려고 잠깐 복사해 두는 같은 크기의 배열.\
> 예: 병합 정렬의 추가 메모리 O(n)의 정체가 이것이다.

- 이 장의 계측기 `CountedArray`에는 01번에 없던 `allocate(size)`(보조 배열 만들기)와 할당 계수기가 붙었다 — **할당은 결과에 흔적을 안 남기므로** 세지 않으면 안 보인다.

> **할당(allocation)** — 새 배열(메모리)을 만드는 것.\
> 예: 하향식은 1번, 매번할당 판은 999번 — 결과 배열은 똑같아서 계측기 없이는 이 차이가 안 보인다.

### 전체 흐름

```text
나누기(분할)                 합치기(병합)
[5 2a 8 2b 9 1 4]            [1 2a 2b 4 5 8 9]
   /        \                    ^        ^
[5 2a 8 2b] [9 1 4]          [2a 2b 5 8] [1 4 9]
  /    \      /   \              ^    ^    ^   ^
[5 2a][8 2b][9 1][4]         [2a 5][2b 8][1 9][4]
 (1장까지 쪼개면 정렬 끝)      (한 장씩 비교하며 위로)

네 가지 판: 하향식 = 위 그림 그대로(재귀), 보조 배열 맨 위에서 1개
            상향식 = 밑에서부터 폭 1,2,4,...로 반복문 병합, 재귀 없음
            매번할당 = 하향식인데 병합마다 보조 배열 새로 만듦 (비교 횟수는 동일!)
            손본것 = 하향식 + 짧으면 삽입 정렬 + 이미 정렬이면 병합 건너뜀
```

### 동작 — 병합(merge) 한 번 (`TopDownMergeSort.merge`)

**언제 쓰나**: 네 판이 전부 이 한 함수를 공유한다(상향식·손본것이 그대로 호출).\
여기가 심장이다.

> **병합(merge)** — 각각 정렬된 두 구간을 맨 앞끼리 비교하며 하나의 정렬된 구간으로 합치는 작업.\
> 예: `[2a, 5]` 와 `[2b, 8]` 을 합쳐 `[2a, 2b, 5, 8]` 로 만드는 아래 4단계.

전 상태 — 왼쪽 구간과 오른쪽 구간이 각각 정렬된 배열, 그리고 통째로 복사한 보조 배열:

```text
원본 a   [ 2a | 5 | 2b | 8 ]      (왼쪽 [2a,5] / 오른쪽 [2b,8] 각각 정렬됨)
복사     [ 2a | 5 | 2b | 8 ]  <- aux (여기서 읽고, a에 쓴다)
            ^i       ^j           두 손가락: i = 왼쪽 맨 앞, j = 오른쪽 맨 앞
```

단계 — 두 손가락 중 작은 쪽을 a에 채워 넣기:

```text
k=0: aux[j]=2b < aux[i]=2a ?  같음 -> 왼쪽 먼저!  a[0]=2a, i++
k=1: aux[j]=2b < aux[i]=5  ?  예   ->            a[1]=2b, j++
k=2: aux[j]=8  < aux[i]=5  ?  아니오 ->          a[2]=5,  i++
k=3: 왼쪽(i)이 바닥남       -> 오른쪽 것          a[3]=8,  j++
```

후 상태: `a = [2a, 2b, 5, 8]` — 같은 값 2의 원래 순서 유지(안정 O).

그림 해설 (한 단계씩):

- 먼저 구간 전체를 aux로 복사한다.\
  그다음 aux에서 읽으며 원본 a에 순서대로 쓴다 — 복사 없이 하면 아직 안 읽은 값을 덮어쓴다.
- 비교는 "오른쪽이 **엄격히** 작을 때만 오른쪽을 가져온다".\
  같으면 왼쪽 먼저 — **이 한 줄이 안정성을 만든다.**

> **안정 정렬(stable)** — 같은 값의 원래 순서 유지.\
> 예: 병합 정렬은 "같으면 왼쪽 먼저" 한 줄로 안정이 된다 — 위에서 `2a` 가 `2b` 보다 앞에 남는 것이 그 결과다.

- 한쪽이 먼저 바닥나는 경우(i > mid 또는 j > hi)를 둘 다 다뤄야 한다.\
  하나라도 빼면 범위를 넘는다.
- 병합 한 번의 비용: 구간 길이만큼 쓰기, 최대 그만큼 비교 — O(구간 길이).

### 동작 — 하향식 (`TopDownMergeSort`) : 기준이 되는 판

**언제 쓰나**: 병합 정렬의 표준형.\
나머지 판은 전부 이것과의 차이로 이해한다.

> **하향식(top-down)** — 위에서 반씩 쪼개 내려가는 재귀 방식.\
> 예: `sort(0..6)` 이 `sort(0..3)` 과 `sort(4..6)` 을 부르고, 그 둘이 또 자기를 쪼개는 아래 그림.

전 상태: `[5, 2a, 8, 2b, 9, 1, 4]` + 맨 위에서 **한 번만** 만든 aux(7칸).

단계:

```text
sort(0..6): mid=3
  sort(0..3): mid=1
    sort(0..1) -> merge -> [2a,5]           sort(2..3) -> merge -> [2b,8]
    merge(0..3)          -> [2a,2b,5,8]
  sort(4..6): mid=5
    sort(4..5) -> merge -> [1,9]            sort(6..6) -> 1칸, 그대로
    merge(4..6)          -> [1,4,9]
  merge(0..6)            -> [1,2a,2b,4,5,8,9]
```

후 상태: `[1, 2a, 2b, 4, 5, 8, 9]`.

그림 해설 (한 단계씩):

- 구간이 1칸 이하면(`lo >= hi`) 그냥 돌아온다 — 재귀가 끝나는 바닥.
- aux는 맨 위에서 1개만 만들고 재귀 전체가 돌려 쓴다.\
  병합마다 만들어도 정답은 같지만(아래 매번할당 판) 할당이 n-1번이 된다.
- 중간 지점은 `lo + (hi - lo) / 2`로 쓴다.\
  `(lo + hi) / 2`는 원소가 10억 개를 넘으면 덧셈이 int 범위를 넘쳐 틀린다 — 자바 라이브러리가 2006년에 고친 그 버그이고, **테스트로 못 잡는 종류**라 주석이 유일한 방어선이다(원본 주석: 변종을 심어도 테스트 68개 전부 통과).

> **오버플로(overflow)** — 계산 결과가 자료형이 담을 수 있는 범위를 넘어 엉뚱한 값이 되는 것.\
> 예: `(lo+hi)/2` 에서 lo+hi 가 int 최대값을 넘으면 음수가 되어 엉뚱한 mid 가 나온다.

**비용**: 비교 O(n log n)(층 log n개 × 층당 n), 추가 메모리 O(n), 안정 O.\
쓰기는 입력 내용과 무관하게 고정(1,000개에서 19,952).

### 동작 — 상향식 (`BottomUpMergeSort`) : 재귀 없음

**언제 쓰나**: 재귀 스택이 부담스러울 때.\
배열이 아주 커도 스택 안전.

> **상향식(bottom-up)** — 폭 1부터 반복문으로 합쳐 올라가는 방식.\
> 예: 아래처럼 width = 1 → 2 → 4 로 폭을 2배씩 키우며 앞에서부터 둘씩 병합한다.

> **스택 / StackOverflowError** — 재귀 호출이 쌓이는 메모리 공간 / 그것이 넘칠 때의 오류.\
> 예: 상향식은 재귀가 없어 이 걱정이 없다.

전 상태: 같은 배열.\
폭(width) 1짜리 조각 7개로 본다.

단계 — 고정 폭으로 앞에서부터 둘씩 병합, 폭을 2배씩:

```text
width=1: [5][2a] [8][2b] [9][1] [4]  -> [2a,5] [2b,8] [1,9] [4]
width=2: [2a,5]+[2b,8]  [1,9]+[4]    -> [2a,2b,5,8] [1,4,9]
width=4: [2a,2b,5,8]+[1,4,9]         -> [1,2a,2b,4,5,8,9]
```

후 상태: 동일.\
병합 함수는 하향식의 것을 그대로 호출한다.

그림 해설 (한 단계씩):

- 하향식은 "항상 절반"으로 자르고, 상향식은 "앞에서부터 고정 폭"으로 자른다.\
  n이 2의 거듭제곱이면 두 모양이 완전히 겹쳐 비교 횟수까지 같아진다(1,024개에서 둘 다 8,966; 1,000개에서는 8,731 vs 8,761).
- 마지막 조각은 폭이 모자랄 수 있다(위의 `[4]`).\
  `hi = min(lo + 2*width - 1, n-1)`로 잘라줘야 하고, 빼면 범위를 넘는다 — n이 2의 거듭제곱이 아닐 때만 터지는 함정.
- `width < n`을 `<= n`으로 잘못 써도 결과가 같다(원본 주석·변종 실험) — 빈 바퀴 하나가 더 돌 뿐.\
  01번 셸의 gap 시작값과 같은 종류의 "틀림이 아니라 낭비".

**비용**: 하향식과 같은 O(n log n), aux 1개, 안정 O.\
재귀 깊이 0.

### 동작 — 매번할당 (`NaiveMergeSort`) : 손이 먼저 가는 판

**언제 쓰나**: 쓰지 말라고 있는 판.\
"돌려보니 잘 되던데요"가 왜 위험한지 보여준다.

단계: 하향식과 완전히 같은데, merge 안에서 `aux`를 **병합할 때마다 구간 길이만큼 새로 만든다.**

```text
하향식:   aux 할당 1번  ->  모든 merge가 나눠 씀
매번할당: merge마다 할당 -> n개 정렬에 n-1번 할당
          (보조 배열이 구간 길이라 인덱스도 k-lo 로 어긋나게 다시 맞춰야 함)
```

그림 해설:

- 무작위 1,000개에서 비교 8,731·쓰기 19,952가 하향식과 **소수점까지 같고** 결과도 같다.\
  다른 것은 할당 1 vs 999, 총 할당 칸 1,000 vs 9,976뿐.
- 할당은 결과에 아무 흔적을 안 남긴다.\
  계측기가 없으면 이 구현이 왜 나쁜지 알 방법이 없다.

**비용**: 비교·쓰기는 하향식과 동일.\
할당 O(n)번, 총 할당량 O(n log n)칸 — GC 압력으로 나타나는 숨은 비용.

### 동작 — 손본것 (`TunedMergeSort`) : 라이브러리가 하는 것

**언제 쓰나**: 실전형.\
두 가지 손질이 들어간다.

> **컷오프(cutoff)** — 구간이 이 길이 이하면 다른(더 단순한) 알고리즘으로 처리하는 경계값.\
> 예: 여기서는 7 — 7칸 이하 구간은 재귀 대신 삽입 정렬로 끝낸다.

단계:

```text
1) 컷오프: 구간이 7칸 이하면 재귀 대신 삽입 정렬로 끝냄
   (짧은 구간에선 재귀+복사가 비교보다 비싸다)

2) 병합 건너뛰기: merge 직전에 딱 1번 비교 —
   [ ... 왼쪽 끝 | 오른쪽 처음 ... ]
         a[mid] <= a[mid+1] 이면 이미 통째로 정렬됨 -> 병합 생략
```

그림 해설 (한 단계씩):

- 컷오프의 삽입 정렬은 0이 아니라 `lo`부터 돈다(함정).\
  인접 교환만 하는 판이라 안정성 유지.
- 병합 건너뛰기는 비교 1번으로 복사 전체(구간 길이만큼의 읽기+쓰기)를 아낀다.\
  정렬된 입력에서 극적이다.
- 이건 개선이 아니라 **맞바꾸기**다(아래 측정): 정렬된 입력에서 크게 이기는 대신, 무작위·역순에서는 경계 비교가 헛돌아 비교가 조금 늘어난다.

**비용**: 여전히 O(n log n)·안정 O·aux 1개.\
상수만 달라진다.

## 쓰이는 자료구조·알고리즘

- **팀소트(TimSort)** — 자바 `Arrays.sort(Object[])`·`Collections.sort`, 파이썬 `sorted`. 정렬된 조각(run)을 찾아 병합하는 병합 정렬 계열이고, 이 챕터의 "손본것"(컷오프·병합 건너뛰기)이 같은 발상의 작은 판이다(팀소트는 run 탐지·갤로핑 등을 더 얹는다).
- **외부 정렬 · DB `ORDER BY`** — 많은 DB(예: PostgreSQL은 `work_mem`을 넘으면 external merge)가 정렬 메모리를 넘는 결과는 조각을 디스크에 정렬해 두고 k개 조각을 동시에 병합한다(k-way merge). 이 챕터의 `merge`가 2-way의 원형이다.
- **LSM 트리 컴팩션** — 정렬된 SSTable 파일 여러 개를 하나로 합칠 때 병합 한 번의 논리 그대로다([data-structure/24-lsm-tree](../../data-structure/24-lsm-tree/2-summary.md)).
- **MapReduce 셔플·sort-merge join** — 키로 정렬된 두 입력을 맨 앞끼리 맞춰 가며 합치는 조인이 병합 그 자체다.
- **연결 리스트 정렬** — 임의 접근이 없는 연결 리스트에서는 퀵 정렬보다 병합 정렬이 자연스럽다(자바 `LinkedList`는 `List.sort`의 기본 구현대로 배열로 복사해 `Arrays.sort`(객체면 팀소트)로 정렬한 뒤 되써 넣는다 — `List.sort` Javadoc).
- **유닉스 `sort -m`** — 이미 정렬된 파일들을 병합만 한다.

## 적용 — 풀어나가는 법

병합 정렬을 고를지, 골랐다면 어느 판인지는 세 질문으로 정한다.\
① 같은 값의 순서를 지켜야 하나(그러면 퀵·힙 대신 병합) → ② 보조 배열 O(n)을 감당할 수 있나(못 하면 03·04) → ③ 재귀 깊이가 부담인가(그러면 상향식), 입력이 자주 정렬돼 있나(그러면 손본것).\
아래 과제는 네 판의 결과가 같은데 비용이 갈리는 지점을 계측기로 직접 본다.

### 비교 — 측정이 알려준 것 (원본 README·MeasurementTest, n=1,000)

| 1,000개 | 비교 | 쓰기 | 할당 | 총 칸 |
|---|---|---|---|---|
| 하향식 | 8,731 | 19,952 | **1** | 1,000 |
| 매번할당 | 8,731 | 19,952 | **999** | 9,976 |

- **비교 하한에 2.4%까지 붙는다**: 비교로만 정렬하는 어떤 알고리즘도 최악에 `log2(n!)`번보다 적게 비교할 수 없다.\
  n=1,000에서 하한 8,530, 병합 정렬 8,731.\
  이보다 잘하려면 비교 자체를 포기해야 한다 — 그게 05번(계수·기수).

> **하한(lower bound)** — "이보다 덜 할 수는 없다"는 이론적 최소치.\
> 예: n=1,000 에서 비교 정렬의 하한은 8,530 이고, 병합 정렬은 8,731 로 거기에 2.4%까지 붙는다.

- **손본것은 맞바꾸기**: 정렬된 입력에서 비교 999·쓰기 0(배열을 한 번도 안 건드림) vs 손 안 본 것 5,044·19,952.\
  그런데 무작위에선 비교 9,042 vs 8,731(3.6% 손해), 역순은 5,867 vs 4,932(19% 손해).
- **쓰기 19,952는 입력 내용과 무관하게 고정** — 병합은 뭐가 들었든 구간 전체를 복사한다.\
  예측 가능하다는 장점이자, 이미 정렬된 입력에도 같은 값을 치른다는 단점(손본것이 그걸 공략).

## 장애 시나리오와 대처

**1. 대용량에서 OOM**

- 현상: 작은 데이터에서 잘 돌던 정렬이 큰 배열에서 죽는다.
- 보이는 형태: `java.lang.OutOfMemoryError: Java heap space`. 힙 덤프에 원본과 같은 크기의 배열이 하나 더 보인다.
- 원인: 보조 배열 O(n). 남은 힙에 원본 배열과 같은 크기의 배열을 더 만들 자리가 없으면 사본을 못 만든다(객체 배열이면 복사되는 것은 참조 배열이다 — 객체 자체는 복사되지 않는다).
- 대처: 원시 타입은 제자리 정렬(03 퀵·04 힙)로, 객체 정렬은 조각으로 나눠 외부 정렬로. 힙 크기를 정할 때 "원본 × 2"를 셈에 넣는다.

**2. GC가 자주 돌고 처리량이 떨어진다**

- 현상: 정렬 자체는 맞게 끝나는데 서비스 전체가 느려진다.
- 보이는 형태: GC 로그에 젊은 세대 수집이 빈발, 할당률 급증. 프로파일에서 `new` 호출이 정렬 안에서 n번 근처.
  - *GC(가비지 컬렉터)*: 안 쓰는 객체를 치우는 자동 청소부. 할당이 많을수록 자주 돈다.
- 원인: 병합마다 보조 배열을 새로 만드는 "매번할당" 판. 비교·쓰기 횟수는 정상 판과 같아서 결과 테스트로는 안 잡힌다.
- 대처: 보조 배열을 맨 위에서 한 번만 만든다. 할당 횟수를 계측해 테스트로 고정한다(정답 7번 참고).

**3. 10억 개를 넘는 순간 음수 인덱스**

- 현상: 아주 큰 배열에서만 예외가 난다.
- 보이는 형태: 음수 인덱스의 `ArrayIndexOutOfBoundsException`(예: `lo + hi`가 정확히 2³¹이면 mid = -1073741824).
- 원인: `mid = (lo + hi) / 2`에서 `lo + hi`가 int 최대(약 21억)를 넘어 음수로 뒤집힌다. 원소 2³⁰개 이상에서만 터져 테스트가 못 잡는다.
- 대처: `lo + (hi - lo) / 2` 또는 `(lo + hi) >>> 1`. 06번은 배열 없는 API로 이 결함을 테스트로 잡는다.

## 핵심 문장

- 병합 정렬 = "정렬된 두 묶음 합치기는 쉽다(O(n))"에 "1장짜리는 이미 정렬"을 얹은 분할 정복 — 그래서 입력이 어떻게 생겼든 O(n log n)이 보장된다.
- 안정성은 병합에서 값이 같을 때 **왼쪽을 먼저** 가져오는 한 줄이 만든다.
- 네 판의 결과와 비교 횟수가 같아도 좋은 코드와 나쁜 코드가 갈린다 — 할당처럼 결과에 흔적이 없는 비용은 계측 없이는 안 보인다.
- `(lo+hi)/2` 오버플로처럼 테스트가 도달할 수 없는 버그가 있다 — 그 자리의 방어선은 주석뿐이다.
- 손본 최적화(컷오프·병합 건너뛰기)는 공짜가 아니라 특정 입력(정렬됨)에 유리하게 거는 보험이다.

### 용어 풀이

- **분할 정복(divide and conquer)**: 문제를 반씩 쪼개 각각 풀고 합치는 전략.\
  병합 정렬이 대표.
- **재귀(recursion)**: 함수가 더 작은 입력으로 자기 자신을 부르는 것.\
  바닥 조건(여기선 1칸 구간)이 있어야 끝난다.
- **병합(merge)**: 각각 정렬된 두 구간을 맨 앞끼리 비교하며 하나의 정렬된 구간으로 합치는 작업.
- **보조 배열(aux, auxiliary array)**: 병합 중 원본을 덮어쓰지 않도록 구간을 복사해 두는 배열.\
  병합 정렬의 추가 메모리 O(n)의 정체.
- **할당(allocation)**: 새 배열(메모리)을 만드는 것.\
  결과에 흔적을 남기지 않는 비용이라 계측기로 세야 보인다.
- **하향식(top-down)**: 위에서 반씩 쪼개 내려가는 재귀 방식.\
  **상향식(bottom-up)**: 폭 1부터 반복문으로 합쳐 올라가는 방식.
- **컷오프(cutoff)**: 구간이 이 길이 이하면 다른(더 단순한) 알고리즘으로 처리하는 경계값.\
  여기서는 7.
- **안정 정렬(stable)**: 같은 값의 원래 순서 유지.\
  병합 정렬은 "같으면 왼쪽 먼저" 한 줄로 안정이 된다.
- **비교 정렬의 하한 log2(n!)**: 비교만으로 정렬하는 알고리즘이 최악의 경우 반드시 치러야 하는 최소 비교 횟수.\
  n개의 가능한 배치 n!가지를 예/아니오 비교로 구분하려면 log2(n!)번 필요.
- **오버플로(overflow)**: 계산 결과가 자료형이 담을 수 있는 범위를 넘어 엉뚱한 값이 되는 것.\
  `(lo+hi)/2`의 함정.
- **스택/StackOverflowError**: 재귀 호출이 쌓이는 메모리 공간/그것이 넘칠 때의 오류.\
  상향식은 재귀가 없어 이 걱정이 없다.
- **팀소트(Timsort)**: 자바 `Arrays.sort(Object[])`가 쓰는 실전 정렬.\
  병합 정렬 계열 + 컷오프/병합 생략류 손질.
