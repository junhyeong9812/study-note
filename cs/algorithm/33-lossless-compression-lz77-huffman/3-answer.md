# algorithm/33-lossless-compression-lz77-huffman — 정답

## 정답

### 1. LZ77과 허프만이 각자 없애는 것

- LZ77은 **반복**을 없앤다. 앞에 나온 문자열이 다시 나오면 `<거리, 길이>` 역참조 하나로 바꾼다.
- 허프만은 **빈도 치우침**을 없앤다. 자주 나오는 기호(리터럴·길이·거리 기호)에 짧은 비트열을 준다.
- 하나만 쓰면
  - 허프만만: 바이트를 독립으로 보므로 H₀ 근처에서 멈춘다. 실험에서 `log.jsonl`은 허프만 단독 6.57MB, gzip 1.47MB였다. 차이가 LZ77의 몫이다.
  - LZ77만: 토큰 자체(리터럴 바이트, 거리·길이 숫자)를 고정 길이로 적으면 자주 나오는 토큰에도 같은 비트를 쓴다. 허프만이 이 치우침을 줄인다.

### 2. ABRACADABRA 허프만 트리

```text
  ① C1 + D1 → (CD)2
  ② B2 + R2 → (BR)4
  ③ (CD)2 + (BR)4 → 6
  ④ A5 + 6 → 11

              (11)
            0/    \1
           A5      (6)
                 0/    \1
              (CD)2    (BR)4
              0/ \1    0/ \1
              C   D    B   R
```

- 부호 길이: A 1, B·C·D·R 3.
- 총 비트 = 5·1 + 2·3 + 2·3 + 1·3 + 1·3 = **23비트**. 기호 5종 고정 길이 부호는 3비트씩 11개 = 33비트.
- 실험(`HuffDemo.java`) 출력도 `total bits=23 (fixed 3-bit code: 33)`이었다. H₀ = 2.0404비트/기호 → 22.4비트가 하한이고, 허프만 평균은 2.0909비트다.
- 같은 빈도의 기호(B 2, R 2, (CD) 2)를 합치는 순서는 여러 가지다. 트리 모양은 달라져도 총 비트는 같다.

### 3. `<1, 19>` 겹치는 복사

- 1바이트씩 복사하면 매번 방금 쓴 `a`를 다시 읽는다. `a` 19개가 더해져 `a`가 모두 20개가 된다.
  - 실험: `aaaaaaaaaaaaaaaaaaaa -> a<1,19>  roundtrip=true`.
- `System.arraycopy(buf, n-1, buf, n, 19)`는 겹치는 영역을 **원본을 임시로 복사한 것처럼** 처리한다(Javadoc의 겹침 규칙). 원본 영역 `buf[n-1..n+17]` 중 `a`는 첫 칸뿐이고 나머지는 아직 쓰이지 않은 값이다. 그래서 첫 바이트만 `a`가 되고 나머지 18바이트는 쓰레기(새 배열이면 0)가 된다.
- 해법: 거리 < 길이이면 1바이트씩 앞으로 복사한다(RFC 1951 §3.2.3의 X,Y,X,Y,X 예와 같은 의미).

### 4. 네 입력의 gzip 결과

실험(OpenJDK 21 `GZIPOutputStream`) 출력:

```text
small:    2 bytes -> gzip   22 bytes
small:  100 bytes -> gzip   24 bytes
random: 1048576 bytes -> gzip 1048914 bytes
bomb: 1073741824 bytes of zeros -> gzip 1043656 bytes (ratio 1029:1)
```

- ① `hi` → 22바이트로 **커진다**. gzip 헤더 10 + 꼬리 8바이트에 최소 DEFLATE 블록이 붙는다.
- ② 무작위 1MiB → 338바이트 **커진다**. 반복도 치우침도 없다.
- ③ 0 1 GiB → 약 1MB로 **크게 줄어든다**(1029:1). 역참조 하나(최소 2비트)가 최대 258바이트를 만들기 때문에 DEFLATE 한계는 약 1032:1이다(zlib 기술 문서).
- ④ 같은 문자 100개 → 24바이트로 **줄어든다**. `x<1,99>`류의 역참조 하나로 끝난다.

### 5. 0.469비트 원천과 허프만·gzip

- 허프만은 기호마다 정수 비트 부호를 준다. 기호가 둘이면 각 1비트다. 1,000,000기호 → 125,000바이트.
- 엔트로피 0.469비트는 **기호를 서로 독립으로 볼 때**의 하한이다.
- gzip이 81,557바이트로 더 작아진 것은 한계를 어긴 것이 아니다.
  - LZ77이 `aaaa…` 연속을 하나의 역참조로 묶는다. 기호 하나가 아니라 **여러 기호 묶음**에 부호를 주는 셈이다.
  - 묶음 단위로 보면 기호당 1비트 제한이 사라진다. 그래도 이 원천의 진짜 하한(기호당 0.469비트, 약 58,600바이트)보다 평균적으로 작게는 못 간다(기호가 서로 독립인 무작위 원천이라 엔트로피가 곧 엔트로피율이다). 81,557바이트는 그 위에 있다.
- 기호당 정수 비트의 한계를 직접 넘는 방법이 산술 부호·ANS다(34번 실험: rANS 0.4686비트/기호).

### 6. 부호 길이만 보내는 이유와 15비트 제한

- 트리를 그대로 실으면 부호표가 커진다. 동적 허프만 블록마다 표를 새로 싣는 DEFLATE에서는 비용이 크다(고정 허프만 블록은 표를 안 싣는다).
- RFC 1951 §3.2.2의 두 규칙
  - 같은 길이의 부호는 기호 순서대로 연속된 값이다.
  - 짧은 부호가 긴 부호보다 사전순으로 앞선다.
- 이 규칙이면 길이 목록만으로 부호가 하나로 정해진다(정규 허프만). 실험에서 길이 (2,1,3,3) → `10, 0, 110, 111`로 RFC 예시와 같았다.
- 15비트 제한(§3.2.7) 때문에 평범한 허프만 결과를 그대로 쓸 수 없는 경우가 있다.
  - 실험: 한국어 노트 3.5MB의 바이트 허프만 최대 깊이는 21이었다.
  - 압축기는 길이 제한 안에서 최선의 길이를 따로 계산해야 한다. RFC는 이것이 "길이 계산 알고리즘을 복잡하게 만든다"고만 하고 방법은 참고문헌으로 넘긴다.

### 7. 해시 체인과 탐색 깊이

- 구조: `head[해시(앞 3바이트)]` → 가장 최근 위치, `prev[위치]` → 같은 해시의 이전 위치. 해시 테이블 + 위치별 단일 연결 리스트다(RFC 1951 §4).
- 해시 충돌이 있으므로 후보마다 실제 바이트를 비교한다.
- 체인을 길게 따라가면
  - 얻는 것: 더 긴 일치 → 토큰 수 감소 → 보통 더 작은 출력. 단 이 실험은 토큰 수만 쟀다. 길이·거리 부호와 추가 비트 비용이 토큰마다 달라 토큰이 적어도 비트가 더 많을 수 있으니, 크기는 실제 부호화 결과로 비교한다(RFC 1951 §3.2.5).
  - 잃는 것: 위치마다 비교 횟수 증가 → CPU 시간.
- 실험 토큰 수: 체인 1 → 846,332, 8 → 675,564, 128 → 621,542, 4096 → 619,671.
  - 128 → 4096은 탐색 상한을 32배 올렸는데 토큰은 0.3%만 줄었다. 높은 레벨일수록 "같은 CPU에 얻는 압축"이 줄어든다. 34번에서 zstd -19가 -9보다 훨씬 느린데 크기는 조금만 작은 것과 같은 모양이다.

### 8. 압축 폭탄 OOM

- 의심: 압축 폭탄. 1MB가 1 GiB로 풀릴 수 있다(실험 1029:1). 해제 결과를 `readAllBytes()`처럼 한 번에 메모리로 모으면 힙이 넘친다.
- 해제 코드
  - 스트리밍으로 읽으며 누적 크기를 센다. 상한을 넘으면 즉시 중단·거부한다(정리의 `safeGunzip`).
  - 결과를 메모리에 다 모으지 않고 조각마다 처리한다.
  - 압축률 상한, 중첩 아카이브 깊이 제한을 함께 둔다.
- ISIZE를 믿으면 안 되는 이유
  - 보내는 쪽이 적은 값이라 거짓일 수 있다.
  - 원래 길이 mod 2³²라 4 GiB 이상이면 작은 값으로 감긴다(RFC 1952 §2.3.1).
  - 실제로 풀어 보며 센 바이트 수만 믿는다.

### 9. 두 가지 해제 예외

- `EOFException: Unexpected end of ZLIB input stream`
  - 원인: 스트림이 중간에 끝났다. 보내는 쪽이 `GZIPOutputStream`을 `close()`/`finish()` 하지 않았거나, 전송 중 잘렸다.
  - 실험: `flush()`만 하고 닫지 않은 스트림은 2,300바이트 입력에 10바이트(헤더)만 나와 있었고, 읽으면 이 예외가 났다.
  - 확인: 바이트 길이, `gzip -t`, 보내는 코드의 try-with-resources.
- `ZipException: Not in GZIP format`
  - 원인: 첫 2바이트가 `1f 8b`가 아니다. 평문이거나, zlib 포장(`deflate`)이거나, 이미 풀린 본문에 `Content-Encoding: gzip`이 남은 경우다.
  - 실험: 평문 `plain text`를 읽으면 이 예외가 났다.
  - 확인: `xxd file | head -1`로 매직 바이트(gzip `1f8b`, zlib은 흔히 `78`로 시작). HTTP라면 프록시가 이미 풀었는지 헤더를 본다(network/39).
- 덤: 꼬리 CRC가 맞지 않으면 `ZipException: Corrupt GZIP trailer`다(같은 실험).

### 10. 세는 논증과 "암호화 후 압축"

- 길이 n비트 입력은 2ⁿ개다. n비트보다 짧은 출력은 2⁰+…+2ⁿ⁻¹ = 2ⁿ−1개뿐이다.
- 무손실이면 서로 다른 입력은 서로 다른 출력으로 가야 한다. 그래서 적어도 하나는 줄지 않는다(RFC 1951 §1.1).
- 압축기가 실제로 줄이는 것은 "반복·치우침이 있는" 입력이다. 그 대가로 그렇지 않은 입력은 조금 커진다(DEFLATE는 32K 블록당 최대 5바이트).
- 좋은 암호문은 무작위와 구별되지 않는다. 그러면 반복도 치우침도 없어 줄일 것이 없다. 실험에서 무작위 1MiB는 gzip 후 338바이트, 2,000,000바이트는 339바이트 커졌다.
- 그래서 압축은 암호화 **전**에 한다. 단, 비밀과 공격자 입력을 함께 압축하면 길이로 비밀이 새는 문제(CRIME·BREACH, network/43)는 별도로 막는다.
