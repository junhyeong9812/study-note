### A. 문제 (ArrayProblems)

#### 1. 정렬된 배열 중복 제거 (제자리)

정렬되어 있으므로 **같은 값은 반드시 붙어 있다.** 그래서 "이미 살린 값"과 지금 값만 비교하면 된다.
같은 문제에 두 가지 풀이가 있고, 둘의 차이가 이 챕터의 핵심 레슨이다.

**접근 1 — 뒤에서부터 `remove`** (내가 먼저 도출한 정답, 테스트 통과)

```java
public static int removeDuplicatesSorted(DynamicArray<Integer> array) {
    if (array.size() == 0) return 0;
    for(int i = array.size() - 1; i >= 0; i--) {
        if (i != 0 && array.get(i) == array.get(i - 1)) array.remove(i);
    }
    return array.size();
}
```

- 논리: 앞에서부터 지우면 지운 뒤 인덱스가 당겨져 순회가 어긋난다. **뒤에서부터 지우면 아직 방문하지 않은 앞쪽 인덱스가 흔들리지 않는다.**
- 남은 구멍: `Integer` 를 `==` 로 비교하면 **참조 비교**다. 자바의 Integer 캐시(-128~127) 덕분에 작은 값에서는 우연히 맞지만,
  `[1000, 1000]` 처럼 캐시 밖 값에서는 `false` 가 되어 중복이 안 지워진다. → `equals` 를 써야 한다.
  (테스트 데이터가 전부 작은 값이라 통과했을 뿐이다. **"테스트 통과" ≠ "맞다"**의 사례.)
- 비용(왜): 중복이 m 개, 살아남는 뒤쪽 원소가 k 개일 때 `remove(i)` 한 번마다 뒤쪽 k 개가 앞으로 복사된다 → 총 **m x k**.
  `m + k <= n` 이므로 최악은 `m = k = n/2` 일 때 **(n/2)^2 = O(n^2)**.
  - 최악 입력: `[1,1,1,...,1, 2,3,4,...,k]` — 앞에 중복 덩어리, 뒤에 서로 다른 값들.
  - 반대로 `[7,7,7,7]` 처럼 지우는 자리가 항상 맨 뒤면 복사가 0번이라 순식간에 끝난다. 하지만 **복잡도는 최악 기준**이다.

**접근 2 — 두 포인터(read/write)로 덮어쓰고 꼬리만 자르기** (최적화한 최종 코드)

```java
public static int removeDuplicatesSorted(DynamicArray<Integer> array) {
    if (array.size() == 0) return 0;
    int writePlace = 1;
    for (int read = 0; read < array.size(); read++) {
        if (!array.get(read).equals(array.get(writePlace - 1))) {
            array.set(writePlace, array.get(read));
            writePlace++;
        }
    }
    for (int i = array.size() - 1; i >= writePlace; i--) {
        array.remove(i);
    }
    return array.size();
}
```

- 불변식: **`array[0 .. writePlace)` = 지금까지 읽은 구간의 중복 없는 결과.** 루프가 한 바퀴 돌 때마다 이 성질이 유지된다.
- 비교 대상은 미래(`read + 1`)가 아니라 **마지막으로 쓴 값(`array.get(writePlace - 1)`)** 이다.
  "다음 값과 다르면 살린다"가 아니라 "이미 살린 마지막 값과 다르면 살린다"로 봐야 중복이 3개 이상 이어져도 무너지지 않는다.
- `writePlace` 는 **배열에서 무언가를 찾는 위치가 아니라 "쓴 만큼 올라가는 카운터"** 다. 그래서 끝나면 곧 남은 개수와 같다.
- 0번 칸은 무조건 살아남으므로 `writePlace = 1` 에서 시작한다. (`read` 는 0부터 돌아도 무방하다 —
  `read == 0` 이면 `get(0).equals(get(0))` 이라 항상 걸러진다. 정답 구현은 `read = 1` 부터 돈다. 결과는 같다.)
- 순회를 마치면 `writePlace` 뒤는 전부 쓰레기다. **맨 뒤부터** 지우면 시프트가 없어 한 번에 O(1) 이다.
- 비용(왜): 읽기 n 번 + 삭제 최대 n 번 = **2n → O(n)**. 상수배는 무시한다.
- **두 접근의 차이 — 순회 방향의 이유가 다르다.**
  - `remove` 방식이 뒤에서부터 도는 이유: **아직 안 본 인덱스를 보호**하려고.
  - 두 포인터가 앞에서부터 도는 이유: **아직 안 읽은 값을 write 가 덮어쓰지 않도록**(항상 `write <= read`) + 쓰레기를 뒤로 몰아 한 번에 자르려고.
  - 결과는 같지만 **O(n^2) 과 O(n)** 이다. 지우지 말고 **살릴 것만 앞으로 모아라**가 이 문제집의 관통 주제다(문제 4와 같은 기법).

#### 2. k 칸 오른쪽으로 회전

```java
public static <E> void rotate(DynamicArray<E> array, int k) {
    int n = array.size();
    if (n == 0) {
        return;
    }
    int shift = ((k % n) + n) % n;
    if (shift == 0) {
        return;
    }
    reverse(array, 0, n - 1);
    reverse(array, 0, shift - 1);
    reverse(array, shift, n - 1);
}

private static <E> void reverse(DynamicArray<E> array, int from, int to) {
    while (from < to) {
        E tmp = array.get(from);
        array.set(from, array.get(to));
        array.set(to, tmp);
        from++;
        to--;
    }
}
```

- 핵심 아이디어: **세 번 뒤집기.** 전체를 뒤집으면 뒤 k 개가 앞으로 오지만 각 덩어리의 내부 순서가 거꾸로다.
  그 두 덩어리를 각각 다시 뒤집으면 제자리로 돌아온다.
  ```
  [1,2,3,4,5] k=2
  전체 뒤집기     -> [5,4,3,2,1]
  앞 k 개 뒤집기   -> [4,5,3,2,1]
  나머지 뒤집기    -> [4,5,1,2,3]
  ```
- 정규화: k 가 n 보다 클 수 있고 음수일 수도 있다. 자바의 `%` 는 음수에 음수를 주므로 `((k % n) + n) % n` 으로 0 이상으로 만든다.
  `n == 0` 이면 `%` 가 ArithmeticException 이므로 **빈 배열을 먼저 막는다**. `shift == 0` 이면 할 일이 없다.
- 비용(왜): 각 원소가 정확히 두 번 자리를 옮긴다(전체 뒤집기 1회 + 부분 뒤집기 1회) → **시간 O(n), 추가 공간 O(1)**.
  임시 배열로 옮기는 풀이도 O(n) 시간이지만 **추가 공간이 O(n)** 이다. 여기가 두 풀이의 갈림이다.

#### 3. 정렬을 유지하며 삽입

```java
public static int insertSorted(DynamicArray<Integer> array, int value) {
    int lo = 0;
    int hi = array.size();
    while (lo < hi) {
        int mid = (lo + hi) >>> 1;
        if (array.get(mid) <= value) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    array.add(lo, value);
    return lo;
}
```

- 핵심 아이디어: 찾는 것은 "값이 있는 자리"가 아니라 **"value 보다 큰 첫 위치"(upper bound)** 다.
  비교를 `<=` 로 해야 같은 값들을 전부 건너뛰어 **그 뒤**에 들어간다. `<` 로 하면 같은 값들 **앞**에 들어간다.
  (테스트 `insertsAfterEqualValues`: `[1,3,3,5]` 에 3을 넣으면 반환 3.)
- `hi` 를 `size()` 로 두면 "맨 뒤에 붙이기"도 자연스럽게 나온다. 빈 배열이면 루프를 한 번도 안 돌고 `lo = 0` 이다.
- `(lo + hi) >>> 1` 은 `(lo + hi) / 2` 의 오버플로 안전판이다(합이 int 범위를 넘어도 부호 없는 시프트라 음수가 안 된다).
- 비용(왜): 자리 찾기 **O(log n)** + 삽입 시프트 **O(n)** = **O(n)**.
  큰 항이 지배하므로 이진 탐색이 **전체 복잡도를 바꾸지는 못한다.** 그래도 비교 횟수(n → log n)는 크게 준다 —
  비교가 비싼 타입이면 실측 이득이 있다. **복잡도가 같다고 무의미한 것은 아니다.**

#### 4. 조건에 맞는 원소를 모두 제거 (`removeAllIf`)

```java
public static <E> int removeAllIf(DynamicArray<E> array, Predicate<? super E> predicate) {
    int n = array.size();
    int write = 0;
    for (int read = 0; read < n; read++) {
        E value = array.get(read);
        if (!predicate.test(value)) {
            if (write != read) {
                array.set(write, value);
            }
            write++;
        }
    }
    truncate(array, write);
    return n - write;
}

/** 뒤에서부터 지운다. 맨 뒤 삭제는 시프트가 없어 O(1) 이다. */
private static void truncate(DynamicArray<?> array, int newSize) {
    while (array.size() > newSize) {
        array.remove(array.size() - 1);
    }
}
```

- 핵심 아이디어: **지우지 않는다.** 살릴 값만 앞으로 모으고(문제 1의 접근 2와 같은 두 포인터) 마지막에 꼬리를 한 번에 잘라낸다.
- 함정(순진한 풀이의 비용): `remove(i)` 한 번은 뒤쪽 원소를 전부 당기므로 O(n).
  n 개 중 절반을 지우면 **n/2 x (평균 n/2) = n^2/4** 번의 복사다. n = 1,000,000 이면 약 2.5 x 10^11 회 —
  테스트 `mustBeLinear` 의 5초 제한에 걸린다. **루프를 n 번 도는 게 문제가 아니라, 그 안에서 O(n) 짜리를 부르는 게 문제다.**
- `truncate` 가 O(n) 안에 들어오는 이유: 맨 뒤(`size - 1`) 삭제는 `moved = size - index - 1 = 0` 이라 시프트가 없다.
  O(1) 짜리를 최대 n 번 = O(n). (중간에 `maybeShrink` 의 복사가 섞이지만 축소도 배수 전략이라 상환 O(1) 이다.)
- 비용(왜): 읽기 n + 쓰기 최대 n + 자르기 최대 n = **O(n)**, 추가 공간 O(1).

#### 5. 정렬된 두 배열 병합

```java
public static DynamicArray<Integer> merge(DynamicArray<Integer> a, DynamicArray<Integer> b) {
    DynamicArray<Integer> result = new DynamicArray<>(a.size() + b.size());
    int i = 0;
    int j = 0;
    while (i < a.size() && j < b.size()) {
        if (a.get(i) <= b.get(j)) {
            result.add(a.get(i++));
        } else {
            result.add(b.get(j++));
        }
    }
    while (i < a.size()) {
        result.add(a.get(i++));
    }
    while (j < b.size()) {
        result.add(b.get(j++));
    }
    return result;
}
```

- 핵심 아이디어: 양쪽에 포인터를 두고 **작은 쪽을 먼저 담는다.** 각 원소를 정확히 한 번씩만 본다.
  한쪽이 먼저 소진되면 남은 쪽을 그대로 이어 붙인다(이미 정렬되어 있으므로 비교가 필요 없다).
- 왜 O((n+m) log(n+m)) 이 O(n+m) 이 되는가: 정렬은 "순서를 모르는 상태"에서 시작하기 때문에 비교 기반 하한이 log 배 붙는다.
  **이미 정렬되어 있다는 것은 그 정보를 이미 가지고 있다는 뜻**이라, 남은 일은 "두 줄을 지퍼처럼 합치기"뿐이다.
- 확장 횟수: 결과 크기가 `a.size() + b.size()` 로 **미리 정해져 있으므로** 그만큼 용량을 잡고 시작한다 →
  `ensureCapacity` 가 항상 조기 반환하고 **확장(=전체 복사)이 한 번도 안 일어난다.** 안 그러면 log(n+m) 번 확장 + 총 2(n+m) 복사가 더 붙는다.
- 원본 불변: `get` 만 하고 `set`/`add`/`remove` 를 원본에 부르지 않는다. 결과는 **새 배열**이다(테스트 `doesNotMutateInputs`).
- `<=` 로 비교하면 같은 값일 때 a 쪽이 먼저 들어간다 — 정렬의 **안정성(stability)** 에 해당하는 선택이다.
- 비용(왜): **시간 O(n+m), 공간 O(n+m)**(결과 배열).

### B. 자료구조의 특성

#### 6. 왜 필요한가 / size 와 capacity 의 역할

- 자바 배열은 **길이가 고정**이다. 만들 때 크기를 정해야 하고, 나중에 늘릴 수 없다.
  그런데 실제 프로그램은 "몇 개가 들어올지 모르는" 경우가 대부분이다. 크게 잡으면 낭비, 작게 잡으면 넘친다.
- 동적 배열은 **내부에 배열을 하나 두고**, 꽉 차면 더 큰 배열을 만들어 옮겨 담는 방식으로 "늘어나는 것처럼" 보이게 한다.
  `ArrayList` 가 하는 일이 정확히 이것이다.
- `size`(담긴 원소 수)와 `capacity`(내부 배열 길이)의 분리가 그 핵심이다.
  **미리 여유를 잡아두고(capacity) 실제로 쓴 만큼만 세면(size)**, 대부분의 add 는 빈 칸에 값 하나 쓰는 O(1) 로 끝난다.
  둘이 같다면(= 매번 딱 맞는 배열) add 마다 새 배열 복사가 필요해 O(n) 이 된다.
  capacity 8 에 3개가 들어 있으면 size=3, capacity=8 이다.

#### 7. 적합한 경우 / 부적합한 경우 (연결 리스트와의 비교)

- **적합**: 인덱스로 임의 접근이 잦을 때(O(1) 주소 계산), 맨 뒤에 쌓고 순회하는 패턴,
  원소 수가 안정적이거나 대략 예측 가능할 때. 메모리에 붙어 있어 **캐시 지역성**도 좋다.
- **부적합**: 앞이나 중간에서의 삽입·삭제가 잦을 때(매번 O(n) 시프트), 크기가 크게 요동칠 때(복사 비용).
- 연결 리스트(02번)와의 교환:
  | | 동적 배열 | 연결 리스트 |
  |---|---|---|
  | 인덱스 접근 | O(1) | O(n) — 처음부터 따라가야 |
  | 위치를 이미 안 상태의 삽입·삭제 | O(n) 시프트 | O(1) 참조만 갈아끼움 |
  | 메모리 | 연속, 원소만 | 흩어짐, 노드마다 포인터 오버헤드 |
- **교환의 뿌리는 "연속 저장" 하나다.** 연속이라서 주소 계산으로 즉시 찾아가지만(O(1) 접근),
  연속이라서 중간을 비우거나 끼우면 뒤를 전부 밀거나 당겨야 한다(O(n)). 얻는 것과 잃는 것이 같은 뿌리에서 나온다.

#### 8. 왜 2배로 키우는가 / 상환 O(1)

- **1씩 키우면**: add 마다 새 배열로 전체 복사 → 총 복사량 `1 + 2 + ... + n = n(n+1)/2 = O(n^2)`.
- **2배로 키우면**: 초기 용량 c 에서 확장은 `c, 2c, 4c, ...` 지점에서만 일어나므로 **약 log2(n/c) 번**.
  총 복사량은 마지막 확장부터 거꾸로 더하면 `n + n/2 + n/4 + ... < 2n = O(n)`.
  등비급수라 **항이 무한히 있어도 합이 2n 을 못 넘는다** — 이게 배수 전략의 전부다.
- **상환(amortized) O(1)** = "add 한 번이 항상 O(1)"이 아니라,
  **연속된 n 번의 add 총비용이 O(n) 이므로 1회 평균이 O(1)** 이라는 뜻이다.
  개별 add 는 확장이 걸리는 그 순간 O(n) 이다. 최악 1회 비용과 평균 1회 비용을 구분하는 개념이다.
  (그래서 응답 지연이 중요한 실시간 시스템에서는 "가끔 튀는 O(n)" 자체가 문제가 되기도 한다.)
- 구현 함정 둘:
  - **capacity 가 0 이면 `0 * 2 = 0`** 이라 영원히 안 큰다 → `elements.length == 0` 이면 `DEFAULT_CAPACITY` 로(테스트 `growsFromZeroCapacity`).
  - **첫 확장만 크게 하고 이후 1씩 늘려도** 단순 테스트는 통과한다 → 그래서 `keepsDoubling` 이 2 → 4 → 8 → 16 을 계속 확인한다.
  - `newCapacity < minCapacity` 분기는 지금 공개 API 로는 도달하지 않지만(항상 `size+1` 로만 호출),
    `addAll` 같은 대량 삽입이 생기면 쓰이고, `length * 2` 가 오버플로해 음수가 되는 경우도 받아낸다.

#### 9. 왜 1/4 에서 절반으로 줄이는가 (thrashing)

- 늘리기만 하고 안 줄이면, 한 번 커진 배열은 원소를 다 빼도 그 크기 그대로 메모리를 붙잡는다. 그래서 축소가 필요하다.
- **1/2 에서 줄이면 안 되는 이유**: capacity 16 / size 8 상태에서 add 와 remove 를 번갈아 하면
  add → 9개라 확장(32로), remove → 8개라 축소(16으로) … 매 연산이 **전체 복사 O(n)** 이 된다. 상환 O(1) 이 무너진다. 이것이 **thrashing**.
- **1/4 로 두면**: 축소 직후 size 는 새 capacity 의 **정확히 1/2** 이다.
  다시 확장하려면 size 가 2배가 되어야 하고, 다시 축소하려면 절반이 되어야 한다.
  **늘리는 문턱과 줄이는 문턱 사이에 여유(hysteresis)를 둔 것**이고, 그 여유가 왕복을 막는다.
  경계에서 왕복해도 확장/축소 사이에 최소 O(n) 번의 연산이 들어가므로 상환 비용은 O(1) 로 유지된다.
- **하한(`halved >= DEFAULT_CAPACITY`)이 없으면**: 매번 절반이 되어 4 → 2 → 1 → 0 까지 내려간다.
  capacity 0 이면 확장이 다시 특수 처리에 걸리고, 작은 배열에서 확장/축소가 반복돼 이득 없는 복사만 늘어난다(테스트 `doesNotShrinkBelowMinimum`).
- 테스트가 이 규칙을 **그대로** 검사한다(`shrinksAtQuarter`, `doesNotThrashAtBoundary`) — 즉 축소 정책은 구현 재량이 아니라 **계약**이다.

#### 10. remove(index) 의 비용이 자리마다 다른 이유

- `remove` 가 하는 일은 "지우기"가 아니라 **"뒤에 있는 것들을 앞으로 당기기"** 다.
  당길 개수는 `moved = size - index - 1` — 즉 **지운 자리보다 뒤에 몇 개가 있느냐**로 결정된다.
- **맨 뒤(`index == size - 1`)**: `moved == 0` → 복사 없음 → **O(1)**.
- **맨 앞(`index == 0`)**: `moved == size - 1` → 거의 전부 복사 → **O(n)**. 중간은 평균 n/2 → 역시 O(n).
- 시사점: **여러 개를 지워야 하면 "앞에서부터 하나씩 remove"가 아니라 "살릴 것을 앞으로 모으고 꼬리를 뒤에서 자르기"** 다.
  문제 1의 접근 2, 문제 4의 `truncate` 가 정확히 이 전략이다.
- (부수: `remove(int)` 와 `remove(Object)` 는 다른 메서드다. `DynamicArray<Integer>` 에서 `remove(1)` 은 인덱스 1,
  `remove(Integer.valueOf(1))` 은 값 1 — `ArrayList` 의 대표적 함정이고 테스트에도 박혀 있다.)

#### 11. 최악 입력을 직접 만들기

- **`add(0, x)` 를 n 번**: 매번 기존 원소 전부를 한 칸씩 뒤로 민다 → `0 + 1 + 2 + ... + (n-1) = n(n-1)/2 ≈ n^2/2` 번 복사 → **O(n^2)**.
  (여기에 확장 복사 `< 2n` 이 더 붙지만 n^2 에 묻힌다.) 앞쪽 삽입이 필요한 워크로드라면 **자료구조 선택이 틀린 것**이다(→ 연결 리스트/덱).
- **중간 remove 를 n/2 번**: 매번 평균 n/2 개를 당긴다 → `n/2 x n/2 = n^2/4` → **O(n^2)**. 문제 4의 100만 케이스가 이걸 시간으로 보여준다.
- **문제 1 접근 1의 최악**: `[1,1,...,1, 2,3,...,k]` — 중복 m 개를 지울 때마다 뒤쪽 k 개를 당긴다 → m x k, 최악 (n/2)^2.
- **최선(선형에 머무는 패턴)**:
  - 맨 뒤에만 `add(x)` → 총 복사 `< 2n` → **O(n)**, add 1회 상환 O(1).
  - 맨 뒤에서만 `remove(size-1)` → 시프트 0, 축소 복사도 상환 O(1) → **O(n)**.
  - `get`/`set` 으로만 훑기 → 복사 0.
  - 즉 **꼬리에서만 늘리고 줄이고, 나머지는 인덱스로 읽고 쓰는** 패턴이 동적 배열의 최적 사용법이다.

#### 12. 지운 자리의 참조 / toArray 가 복사본인 이유

- `remove(index)` 에서 뒤를 당기면 마지막 칸에는 **옛 참조가 그대로 남는다.**
  size 밖이라 논리적으로는 없는 값인데, **배열이 여전히 그 객체를 붙잡고 있어서 GC 되지 않는다.** 조용한 메모리 누수다.
  그래서 `elements[--size] = null;` 로 명시적으로 끊는다. `clear()` 도 같은 이유로 size 만 0 으로 만들면 안 되고 칸을 전부 null 로 지운다.
- **공개 API 로는 관측할 수 없다**: `toArray()` 가 size 만큼만 복사하므로 참조를 끊었든 안 끊었든 결과가 같다.
  그런데 그게 이 자료구조의 핵심 레슨이라, 테스트(`TestSupport.raw`)가 **리플렉션으로 `elements` 필드를 직접 들여다본다.**
  → 그래서 **필드 이름 `elements` 가 계약의 일부**가 되었다. 바꾸면 테스트가 깨진다.
  (일반적으로는 냄새다. "테스트하려고 내부를 연다"는 예외적 선택이고, 그 대가로 필드명이 굳었다.)
- **`toArray()` 가 복사본인 이유** 둘:
  1. 내부 배열을 그대로 주면 호출자가 우리 상태를 마음대로 바꿀 수 있다(캡슐화 붕괴 — 테스트 `returnsDefensiveCopy`).
  2. 내부 배열은 **capacity 만큼 길다.** 그대로 주면 뒤에 null 이 붙어 나온다. `Arrays.copyOf(elements, size)` 로 size 만큼만 준다.
  - 같은 맥락: `capacity()` 를 공개한 것은 예외다 — 확장/축소 전략을 테스트로 확인하려고 열어둔 것이지 정상적인 공개 API 가 아니다.

#### 13. 루프 횟수가 아니라 루프 안 비용을 곱해야 하는 이유

- 총비용 = **반복 횟수 x 반복 1회의 비용**이다. 루프가 n 번 돈다는 사실만으로는 O(n) 이라고 말할 수 없다.
  **루프 안에서 부르는 메서드가 O(1) 인지 O(n) 인지를 먼저 확인해야 한다.**
- `2n` 이 O(n) 인 이유: 상수배는 빅오에서 무시한다(n 이 커질 때의 **증가율**만 본다). 읽기 n + 삭제 n 은 여전히 선형이다.
- `n번 x O(n)` 이 O(n^2) 인 이유: 이건 상수배가 아니라 **n 에 비례하는 일을 n 번** 하는 것이라 항 자체가 제곱으로 커진다.
- **이 문제집에서 그 차이가 시간으로 드러나는 곳**: 문제 4 `mustBeLinear` — 100만 건 / 5초 제한.
  `remove(i)` 반복(약 2.5 x 10^11 회 복사)은 못 끝내고, 두 포인터(약 2 x 10^6 회)는 즉시 끝난다.
  **"정답은 나오는데 통과 못 하는" 구현**이 존재한다는 것을 손으로 겪게 하는 장치다.
- 같은 원리의 반대 사례가 문제 3이다. O(log n) 을 O(n) 에 더하면 **큰 항이 지배**해 전체는 O(n) 이다 —
  곱해지는 자리(루프 안)와 더해지는 자리(순차 실행)를 구분해야 한다.
