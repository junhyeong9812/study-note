### A. 문제 (ArrayProblems)

#### 1. 정렬된 배열에서 중복 제거 (제자리)

**접근 1 — 새 배열에 살릴 것만 담기** (가장 먼저 떠오르지만 문제 조건에 걸린다)

```java
// 의사코드
DynamicArray<Integer> result = new DynamicArray<>();
for (int i = 0; i < array.size(); i++) {
    if (result.size() == 0 || !result.get(result.size() - 1).equals(array.get(i))) {
        result.add(array.get(i));
    }
}
return result.size();
```

- 논리: 정렬되어 있으므로 결과의 마지막 값과 다르면 그것이 새 값이다.
- 논리: 원본은 읽기만 하고 살릴 값을 새 배열에 쌓는다.
- 논리: 판정에 필요한 정보가 "직전에 살린 값" 하나뿐이라 순회 한 번이면 끝난다.
- 비용(왜): 읽기 n 번 + 쓰기 최대 n 번 → 시간 O(n).
- 비용(왜): 결과 배열이 최악에 n 칸 → 추가 공간 O(n).
- 한계: 문제가 "새 배열을 만들지 말고 주어진 배열을 직접 줄여라"라고 못박았다.
- 한계: 반환값만 맞고 원본은 `[1,1,2,2,2,3]` 그대로다. 호출자가 다시 읽으면 중복이 보인다.
- 한계: 개수만 검사하는 테스트는 통과해버린다. 그래서 조용히 틀린 채로 넘어가기 쉽다.

**접근 2 — 뒤에서부터 `remove`** (내가 먼저 도출한 정답, 테스트 통과)

```java
public static int removeDuplicatesSorted(DynamicArray<Integer> array) {
    if (array.size() == 0) return 0;
    for(int i = array.size() - 1; i >= 0; i--) {
        if (i != 0 && array.get(i) == array.get(i - 1)) array.remove(i);
    }
    return array.size();
}
```

- 논리: 정렬되어 있으니 바로 앞 칸과 같으면 그 칸은 중복이다.
- 논리: 앞에서부터 지우면 지운 뒤 인덱스가 당겨져 아직 안 본 원소를 건너뛴다.
- 논리: 뒤에서부터 지우면 당겨지는 구간이 이미 지나온 뒤쪽이라 앞쪽 인덱스가 흔들리지 않는다.
- 논리: 순회 방향의 목적은 **아직 방문하지 않은 인덱스를 보호**하는 것이다.
- 비용(왜): 루프는 n 번이지만 루프 안의 `remove(i)` 가 O(n) 이다.
- 비용(왜): 중복이 m 개, 지우는 자리보다 뒤에 남은 원소가 평균 k 개면 총 복사 = m x k.
- 비용(왜): `m + k <= n` 이므로 곱이 최대인 지점은 `m = k = n/2` → `(n/2)^2 = n^2/4` → **O(n^2)**.
- 한계: `Integer` 를 `==` 로 비교하면 값 비교가 아니라 **참조 비교**다.
- 한계: 자바 Integer 캐시(-128~127) 덕에 작은 값에서는 우연히 맞는다.
- 한계: `[1000, 1000]` 처럼 캐시 밖 값이면 `false` 가 되어 중복이 안 지워진다. `equals` 를 써야 한다.
- 한계: 테스트 데이터가 전부 작은 값이라 통과했을 뿐이다. **"테스트 통과" ≠ "맞다"** 의 사례.

**접근 3 — 두 포인터(read/write)로 덮어쓰고 꼬리만 자르기** (최적화한 최종 코드)

```java
public static int removeDuplicatesSorted(DynamicArray<Integer> array) {
    if (array.size() == 0) return 0;
    int writePlace = 1;
    for (int read = 0; read < array.size(); read++) {
        if (!array.get(read).equals(array.get(writePlace - 1))) {
            array.set(writePlace, array.get(read));
            writePlace++;
        }
    }
    for (int i = array.size() - 1; i >= writePlace; i--) {
        array.remove(i);
    }
    return array.size();
}
```

- 논리: 불변식은 `array[0 .. writePlace)` = 지금까지 읽은 구간의 중복 없는 결과다.
- 논리: `read` 는 매 칸 전진하고, `writePlace` 는 살릴 값을 만났을 때만 전진한다.
- 논리: `writePlace` 는 배열에서 자리를 찾는 포인터가 아니라 "쓴 만큼 올라가는 카운터"다.
- 논리: 0번 칸은 무조건 살아남으므로 `writePlace = 1` 에서 시작한다.
- 논리: `read` 가 0부터 돌아도 무방하다 — `read == 0` 이면 `get(0).equals(get(0))` 이라 항상 걸러진다. impl 은 `read = 1` 부터 돈다. 결과는 같다.
- 논리: 순회 방향이 앞인 이유는 `write <= read` 를 유지해 아직 안 읽은 값을 덮지 않기 위해서다.
- 논리: 쓰레기가 전부 뒤로 몰리므로 꼬리를 **맨 뒤부터** 지우면 시프트가 없다.
- 비용(왜): 읽기 n + 쓰기 최대 n + 꼬리 삭제 최대 n = `3n` → **O(n)**. 상수배는 무시한다.
- 비용(왜): 맨 뒤 삭제는 `moved = size - index - 1 = 0` 이라 한 번이 O(1) 이다.
- 비용(왜): 추가 공간은 인덱스 변수 두 개뿐 → **O(1)**.
- 한계: 원본 순서를 유지한 채 제자리로 줄이는 문제에만 쓸 수 있다. 정렬이 깨져 있으면 성립하지 않는다.
- 한계: 배열 원소가 아니라 외부에서 인덱스를 들고 있던 코드가 있다면 그 인덱스는 전부 무효가 된다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 새 배열에 담기 | O(n) | O(n) | 원본을 보존해야 할 때 | 제자리 요구가 있을 때 · 메모리가 빠듯할 때 |
| 2. 뒤에서부터 remove | 최악 O(n^2) | O(1) | n 이 작고 중복이 끝에 몰릴 때 | n 이 크고 중복이 앞에 몰릴 때 |
| 3. 두 포인터 | O(n) | O(1) | 기본값. 제자리 + 선형이 둘 다 필요할 때 | 정렬되어 있지 않을 때 |

**데이터 규모가 커지면**

- n = 1,000 이면 접근 2의 최악도 계산상 약 25만 회 복사라 체감되지 않는다.
- n = 1,000,000 이면 접근 2의 최악은 계산상 약 2.5 x 10^11 회 복사 — 초당 10^9 회를 가정해도 수백 초다.
- 같은 조건에서 접근 3은 약 3 x 10^6 회 연산으로 끝난다. 여기서 두 풀이가 갈린다.
- n = 1억이면 접근 1의 추가 배열이 문제가 된다. `Integer` 참조 배열만 계산상 400~800MB(참조 4~8바이트)에 박싱된 객체까지 따로 든다.
- 배열이 메모리에 다 안 올라가면 제자리 두 포인터도 못 쓴다. 파일을 순차로 읽으며 직전 값과 비교해 스트리밍으로 걸러내는 방식으로 바뀐다(정렬되어 있으므로 가능하다).
- 다른 스레드가 같은 배열을 읽고 있다면 접근 2·3 모두 위험하다. 제자리 변경은 중간 상태가 관측되므로, 동시 접근이 있으면 접근 1(새 배열)로 만들고 참조를 원자적으로 갈아끼우는 쪽이 안전하다.

**질문별 답**

- Q: "정렬되어 있다"는 조건에서 무엇을 끌어낼 수 있는가?
  A: 같은 값은 반드시 서로 붙어 있다는 것.
  그래서 중복 판정에 배열 전체를 뒤질 필요가 없다.
  직전 값(또는 마지막으로 살린 값) 하나만 보면 끝난다.
  정렬이 없으면 `Set` 으로 추가 공간 O(n) 을 쓰거나 전수 비교로 O(n^2) 을 써야 한다.

- Q: 새 배열에 담아 개수만 반환하는 풀이는 왜 정답이 아닌가?
  A: 문제가 제자리(in-place) 변경을 요구했기 때문이다.
  원본이 줄어들지 않아 호출자가 다시 읽으면 중복이 그대로 있다.
  추가 공간 O(n) 을 쓰는 것도 문제의 제약을 어긴다.
  반환값만 맞아 개수 검사 테스트는 통과해버린다 — 그래서 더 위험하다.

- Q: 순회하면서 `remove(i)` 를 부르는 풀이는 왜 뒤에서부터 돌아야 하는가?
  A: `remove(i)` 가 뒤쪽 원소를 전부 한 칸씩 앞으로 당기기 때문이다.
  앞에서부터 돌면 지운 직후 아직 방문하지 않은 원소들의 인덱스가 1씩 줄어든다.
  거기서 `i++` 를 하면 당겨져 온 원소를 건너뛰어 `[1,1,1]` 같은 입력에서 중복이 남는다.
  뒤에서부터 돌면 당겨지는 구간이 이미 방문한 뒤쪽이라 앞쪽 인덱스가 흔들리지 않는다.

- Q: 그 풀이는 왜 최악에 O(n^2) 이 되는가?
  A: 루프가 n 번 도는 것이 문제가 아니라, 그 안에서 O(n) 짜리 `remove` 를 부르기 때문이다.
  중복 m 개를 지울 때마다 뒤에 남은 k 개가 당겨지므로 총 복사는 `m x k`.
  `m + k <= n` 이라는 제약 아래 곱이 최대가 되는 지점은 `m = k = n/2`.
  `(n/2)^2 = n^2/4` → O(n^2).

- Q: 그 최악을 만드는 입력을 하나 지어보라.
  A: `[1,1,1,...,1, 2,3,4,...,k]` — 앞에 1이 n/2 개, 뒤에 서로 다른 값이 n/2 개.
  앞쪽 1을 하나 지울 때마다 뒤쪽 n/2 개가 통째로 당겨진다.
  지우는 횟수 n/2 x 당기는 개수 n/2 = `n^2/4` 회 복사.
  n = 1,000,000 이면 계산상 약 2.5 x 10^11 회다.

- Q: 반대로 그 풀이가 빠르게 끝나는 입력은 어떤 모양인가?
  A: `[7,7,7,7]` 처럼 지울 자리가 항상 맨 뒤인 모양.
  뒤에서부터 도니 `moved = 0` 이라 복사가 한 번도 안 일어난다.
  `[1,2,3,4,5]` 처럼 중복이 아예 없는 입력도 `remove` 호출이 0번이다.
  다만 복잡도는 최선이 아니라 **최악** 기준으로 말한다 — 빠른 입력이 있다고 O(n) 이 되지 않는다.

- Q: 한 번의 순회, O(n) 으로 끝내는 풀이는 무엇인가?
  A: 두 포인터(read/write)다.
  `read` 는 매 칸 전진하며 값을 읽는다.
  `write` 는 살리기로 한 값을 만났을 때만 그 자리에 쓰고 전진한다.
  순회가 끝나면 `write` 뒤는 전부 쓰레기이므로 맨 뒤부터 잘라낸다.

- Q: 그 풀이에서 `write` 는 무엇을 뜻하고, 왜 배열을 뒤져서 정하면 안 되는가?
  A: `write` 는 "지금까지 살린 개수"이자 "다음에 쓸 자리"다.
  배열 위의 어떤 값을 가리키는 포인터가 아니라 단조 증가하는 카운터다.
  매번 쓸 자리를 배열에서 찾으면 그 탐색이 O(n) 이라 전체가 O(n^2) 로 되돌아간다.
  카운터로 두면 자리 결정이 O(1) 이고, 끝났을 때 그 값이 곧 남은 개수가 된다.

- Q: 그 풀이는 왜 앞에서부터 돌아야 하는가?
  A: `write <= read` 가 항상 성립해야 아직 읽지 않은 값을 덮어쓰지 않기 때문이다.
  앞에서부터 돌면 `write` 는 `read` 보다 뒤처지기만 하므로 이 관계가 저절로 유지된다.
  덤으로 쓰레기가 전부 뒤쪽으로 몰려 꼬리 자르기가 O(1) 삭제만으로 끝난다.
  접근 2가 뒤에서 도는 이유(아직 안 본 인덱스 보호)와 목적이 다르다 — 여기서는 아직 안 읽은 **값**을 보호한다.

- Q: 비교 대상이 "다음 값"이 아니라 "마지막으로 쓴 값"이어야 하는 이유는?
  A: 판정이 아직 오지 않은 미래가 아니라 이미 확정된 결과에만 의존하게 하려는 것이다.
  불변식 `array[0 .. write)` = 중복 없는 결과가 매 반복마다 그대로 유지된다.
  `[2,2,2]` 처럼 중복이 3개 이상 이어져도 기준값이 "마지막으로 살린 2"로 고정되어 흔들리지 않는다.
  "다음 값" 기준은 배열 끝에서 `read + 1` 이 범위를 넘는 경계를 따로 처리해야 하고, `write` 가 앞쪽을 덮어쓰는 알고리즘에서 그 칸이 이미 덮였는지를 매번 따져야 한다.

- Q: 데이터가 100만 건이면 두 풀이 중 어느 쪽이 살아남는가?
  A: 두 포인터만 살아남는다.
  `remove` 반복은 최악에 계산상 약 2.5 x 10^11 회 복사다.
  두 포인터는 읽기 10^6 + 쓰기 최대 10^6 + 자르기 최대 10^6 = 약 3 x 10^6 회다.
  문제 4의 `mustBeLinear`(100만 건 / 5초 제한)가 이 차이를 실제 시간으로 보여준다.

#### 2. k 칸 오른쪽으로 회전

**접근 1 — 임시 배열에 옮겨 담기** (가장 직관적이다. 공간을 내주고 단순함을 산다)

```java
// 의사코드
int n = array.size();
if (n == 0) return;
int shift = ((k % n) + n) % n;
Object[] tmp = new Object[n];
for (int i = 0; i < n; i++) tmp[(i + shift) % n] = array.get(i);
for (int i = 0; i < n; i++) array.set(i, (E) tmp[i]);
```

- 논리: 원소 i 가 가야 할 최종 자리는 `(i + shift) % n` 이다. 그 자리를 바로 계산해 넣는다.
- 논리: 임시 배열을 쓰므로 아직 안 읽은 값을 덮어쓸 걱정이 없다.
- 논리: 다시 원본에 되쓰는 두 번째 루프가 필요하다.
- 비용(왜): 원소마다 두 번 옮긴다(tmp 로 1회 + 원본으로 1회) → 시간 **O(n)**.
- 비용(왜): 길이 n 짜리 배열을 하나 더 만든다 → 추가 공간 **O(n)**.
- 한계: n 이 커지면 순간적으로 메모리가 2배 필요하다.
- 한계: 그 순간에 할당이 실패하면(OOM) 회전이 아예 안 된다.

**접근 2 — 세 번 뒤집기** (impl 의 정답. 추가 공간을 O(1) 로 내린다)

```java
public static <E> void rotate(DynamicArray<E> array, int k) {
    int n = array.size();
    if (n == 0) {
        return;
    }
    int shift = ((k % n) + n) % n;
    if (shift == 0) {
        return;
    }
    reverse(array, 0, n - 1);
    reverse(array, 0, shift - 1);
    reverse(array, shift, n - 1);
}

private static <E> void reverse(DynamicArray<E> array, int from, int to) {
    while (from < to) {
        E tmp = array.get(from);
        array.set(from, array.get(to));
        array.set(to, tmp);
        from++;
        to--;
    }
}
```

- 논리: 전체를 뒤집으면 뒤 k 개가 앞으로 온다. 다만 두 덩어리의 내부 순서가 거꾸로다.
- 논리: 그 두 덩어리를 각각 다시 뒤집으면 내부 순서가 제자리로 돌아온다.
- 논리: 정규화가 먼저다 — k 가 n 보다 클 수 있고 음수일 수도 있다.
- 논리: `n == 0` 이면 `%` 가 ArithmeticException 이므로 빈 배열을 가장 먼저 막는다.
- 논리: 손으로 따라가면 이렇다.
  ```
  [1,2,3,4,5] k=2
  전체 뒤집기     -> [5,4,3,2,1]
  앞 k 개 뒤집기   -> [4,5,3,2,1]
  나머지 뒤집기    -> [4,5,1,2,3]
  ```
- 비용(왜): 각 원소가 정확히 두 번 자리를 옮긴다(전체 뒤집기 1회 + 부분 뒤집기 1회) → 시간 **O(n)**.
- 비용(왜): 쓰는 것은 스왑용 지역 변수 하나뿐 → 추가 공간 **O(1)**.
- 한계: 배열을 세 번 훑으므로 캐시 관점에서 접근 1보다 상수가 크지는 않아도 순회 자체가 3패스다.
- 한계: 중간 상태(`[5,4,3,2,1]`)가 배열에 그대로 보인다. 다른 스레드가 읽고 있으면 깨진 순서를 관측한다.

**접근 3 — `remove(0)` 을 k 번 부르고 뒤에 붙이기** (실격)

```java
// 의사코드
for (int i = 0; i < k; i++) array.add(array.remove(0));
```

- 논리: 앞의 원소를 떼서 뒤에 붙이는 동작이다.
- 논리: 그런데 이것은 **왼쪽으로** k 칸 회전이다. 오른쪽 k 칸을 원하면 `n - k` 번 돌려야 한다.
- 비용(왜): `remove(0)` 은 뒤 전부를 당기므로 한 번이 O(n).
- 비용(왜): 그것을 k 번 → **O(nk)**. `k ≈ n/2` 면 O(n^2).
- 한계: 방향이 반대라 결과부터 틀린다.
- 한계: 방향을 맞춰도 비용이 제곱이라 큰 입력에서 못 쓴다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 임시 배열 | O(n) | O(n) | n 이 작고 읽기 쉬운 코드가 중요할 때 | 메모리가 빠듯할 때 · n 이 아주 클 때 |
| 2. 세 번 뒤집기 | O(n) | O(1) | 기본값. 제자리 회전이 필요할 때 | 중간 상태가 관측되면 안 될 때 |
| 3. remove(0) 반복 | O(nk) | O(1) | (없음 — 방향도 틀리고 비용도 나쁘다) | 사실상 항상 |

**데이터 규모가 커지면**

- n = 1억짜리 참조 배열이면 접근 1의 임시 배열만 계산상 400~800MB(참조 4~8바이트)를 더 잡는다. 접근 2는 0바이트다.
- 접근 3은 `k = n/2`, `n = 10^6` 일 때 계산상 약 5 x 10^11 회 복사 — 애초에 완주하지 못한다.
- 데이터가 메모리에 안 올라가면 "회전"을 물리적으로 하지 않는 선택지가 생긴다. 시작 오프셋 하나를 들고 `get(i)` 를 `get((i + offset) % n)` 으로 읽는 링 버퍼로 바꾸면 회전이 **O(1)** 이 된다.
- 즉 규모가 커지면 알고리즘을 고르는 문제가 아니라 자료구조를 바꾸는 문제가 된다.
- 동시 읽기가 있으면 접근 2의 3패스 중간 상태가 그대로 노출된다. 접근 1로 만들어 참조를 한 번에 갈아끼우거나 링 버퍼로 가야 한다.

**질문별 답**

- Q: k 가 size 보다 크거나 음수일 때 가장 먼저 해야 할 일은 무엇인가?
  A: k 를 `0 <= shift < n` 범위로 정규화하는 것.
  `n` 칸 회전은 제자리로 돌아오므로 의미 있는 것은 `k % n` 뿐이다.
  그 전에 `n == 0` 을 먼저 막아야 한다. `%` 의 오른쪽이 0이면 ArithmeticException 이다.
  정규화 후 `shift == 0` 이면 할 일이 없으므로 바로 반환한다.

- Q: 자바의 `%` 가 음수를 줄 수 있는데 어떻게 0 이상으로 만드는가?
  A: `((k % n) + n) % n` 으로 만든다.
  `k % n` 의 결과는 `-(n-1) .. (n-1)` 범위다.
  거기에 `n` 을 더하면 `1 .. (2n-1)` 로 반드시 양수가 된다.
  다시 `% n` 을 하면 `0 .. (n-1)` 로 접힌다.

- Q: 임시 배열을 쓰는 풀이의 시간·추가 공간 복잡도는 각각 얼마인가?
  A: 시간 **O(n)** 이다.
  원소를 tmp 로 한 번, 원본으로 한 번 총 2n 번 옮긴다.
  추가 공간은 길이 n 짜리 배열 하나라 **O(n)** 이다.
  n 이 클 때 이 O(n) 이 실제 제약이 된다.

- Q: 세 번 뒤집기 풀이의 시간·추가 공간 복잡도는 각각 얼마인가?
  A: 시간 **O(n)** 이다.
  전체 뒤집기에서 n/2 번, 두 부분 뒤집기에서 합쳐 n/2 번 스왑한다 → 원소당 정확히 2회 이동.
  추가 공간은 스왑용 지역 변수 하나라 **O(1)** 이다.
  접근 1과 시간은 같고 공간에서 갈린다.

- Q: 세 번 뒤집기가 왜 회전과 같은 결과를 내는가?
  A: 배열을 앞 `n-shift` 개(A)와 뒤 `shift` 개(B) 두 덩어리로 보면 회전의 목표는 `AB → BA` 다.
  전체 뒤집기는 `AB` 를 `reverse(B) reverse(A)` 로 만든다.
  앞 `shift` 칸을 다시 뒤집으면 `reverse(B)` 가 `B` 로 돌아온다.
  나머지를 다시 뒤집으면 `reverse(A)` 가 `A` 로 돌아와 `BA` 가 완성된다.

- Q: `remove(0)` 을 k 번 부르고 뒤에 붙이는 풀이는 왜 안 되는가?
  A: 우선 방향이 반대다. 앞을 떼서 뒤에 붙이면 **왼쪽** 회전이다.
  오른쪽 k 칸을 얻으려면 `n - k` 번 돌려야 한다.
  방향을 맞춰도 `remove(0)` 한 번이 O(n) 시프트라 총 O(nk) 다.
  `k ≈ n/2` 면 O(n^2) 이라 큰 입력에서 완주하지 못한다.

- Q: 데이터가 커지면 두 풀이 중 어느 쪽이 먼저 한계에 닿는가?
  A: 임시 배열 쪽이 먼저 닿는다.
  시간은 둘 다 O(n) 이라 같은 속도로 늘지만, 공간은 한쪽만 n 에 비례해 늘어난다.
  n = 1억이면 참조 배열만 계산상 400~800MB 를 더 잡아 OOM 위험이 실제가 된다.
  세 번 뒤집기는 추가 공간이 상수라 n 이 커져도 공간 쪽에서는 한계가 오지 않는다.

#### 3. 정렬을 유지하며 삽입

**접근 1 — 앞에서부터 훑어 자리 찾기** (구현이 가장 단순하다)

```java
// 의사코드
int i = 0;
while (i < array.size() && array.get(i) <= value) i++;
array.add(i, value);
return i;
```

- 논리: `value` 보다 큰 첫 위치를 앞에서부터 하나씩 확인해 찾는다.
- 논리: `<=` 로 넘어가야 같은 값들을 전부 지나쳐 그 **뒤**에 선다.
- 논리: 끝까지 갔으면 `i == size` 라 맨 뒤 추가가 된다.
- 비용(왜): 자리 찾기 최악 n 번 비교 → O(n).
- 비용(왜): `add(i, value)` 가 뒤를 미는 시프트 O(n).
- 비용(왜): 둘을 더해 **O(n)**.
- 한계: 비교가 비싼 타입(긴 문자열·복합 키)이면 n 번 비교 자체가 병목이 된다.
- 한계: 배열이 디스크나 원격에 있어 원소 접근 비용이 크면 n 번 접근이 그대로 비용이다.

**접근 2 — 이진 탐색으로 upper bound 찾기** (impl 의 정답)

```java
public static int insertSorted(DynamicArray<Integer> array, int value) {
    int lo = 0;
    int hi = array.size();
    while (lo < hi) {
        int mid = (lo + hi) >>> 1;
        if (array.get(mid) <= value) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    array.add(lo, value);
    return lo;
}
```

- 논리: 찾는 것은 "값이 있는 자리"가 아니라 "value 보다 큰 첫 위치"(upper bound)라는 **경계**다.
- 논리: `array.get(mid) <= value` 면 답은 mid 오른쪽이므로 `lo = mid + 1`.
- 논리: 아니면 mid 자신이 답일 수 있으므로 `hi = mid` — 경계 탐색이라 `mid - 1` 이 아니다.
- 논리: `hi` 를 `size()` 로 잡으면 "맨 뒤에 붙이기"도 특수 처리 없이 나온다.
- 논리: 빈 배열이면 `lo == hi == 0` 이라 루프를 한 번도 안 돌고 `lo = 0` 이다.
- 논리: `(lo + hi) >>> 1` 은 `(lo + hi) / 2` 의 오버플로 안전판이다. 합이 int 범위를 넘어도 부호 없는 시프트라 음수가 되지 않는다.
- 비용(왜): 자리 찾기 **O(log n)** — 매 단계 후보 구간이 절반이 된다.
- 비용(왜): 삽입 시프트 **O(n)** — 뒤 원소를 전부 한 칸씩 민다.
- 비용(왜): `O(log n) + O(n) = O(n)`. 더해지는 항이라 큰 쪽이 지배한다.
- 한계: 이진 탐색은 임의 접근이 O(1) 이어야 성립한다. 연결 리스트에서는 `get(mid)` 자체가 O(n) 이라 무의미하다.
- 한계: 전체 복잡도를 O(n) 아래로 내리지 못한다. 병목은 탐색이 아니라 시프트다.

**접근 3 — 그냥 맨 뒤에 넣고 매번 다시 정렬**

```java
// 의사코드
array.add(value);
sort(array);   // 삽입 위치는 따로 찾아야 한다
```

- 논리: 정렬 조건을 알고리즘으로 지키지 않고 정렬 함수에 떠넘긴다.
- 논리: 삽입 위치를 반환해야 하므로 정렬 후 다시 찾아야 한다 — 문제 조건과 어긋난다.
- 비용(왜): 삽입 1회당 **O(n log n)**. 정렬이 시프트보다 비싸다.
- 한계: 삽입이 반복되는 워크로드면 매번 n log n 이라 접근 1·2보다 확실히 나쁘다.
- 한계: "이미 정렬되어 있다"는 조건을 통째로 버리는 선택이다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 선형 탐색 | O(n) | O(1) | n 이 작고 비교가 싼 원시 타입일 때 | 비교 비용이 클 때 |
| 2. 이진 탐색 | O(n) (탐색 O(log n)) | O(1) | 기본값. 임의 접근이 O(1) 인 저장소 | 임의 접근이 O(n) 인 자료구조 |
| 3. 넣고 재정렬 | O(n log n) | 정렬 구현에 따름 | 삽입이 아주 드물 때 | 삽입이 반복될 때 |

**데이터 규모가 커지면**

- n = 1,000,000 일 때 접근 1의 비교는 최악 10^6 번, 접근 2는 계산상 20번(log2 10^6 ≈ 20)이다.
- 그런데 두 접근 모두 시프트에서 최악 10^6 회 복사가 나므로 총 시간의 차수는 같다.
- 삽입을 n 번 반복하면 총 O(n^2) 이다. n = 10^6 이면 계산상 약 5 x 10^11 회 복사 — 완주 불가다.
- 그러니 규모가 커지면 답은 "탐색을 더 빠르게"가 아니라 "시프트가 없는 자료구조로"다. 균형 이진 탐색 트리(TreeMap)나 스킵 리스트는 삽입 1회가 O(log n) 이다.
- 데이터가 메모리에 안 올라가면 B-트리 계열(디스크 페이지 단위 삽입)이나 LSM 트리(정렬 삽입을 배치로 몰아 쓰기)로 간다. 둘 다 "한 칸 삽입에 전체를 미는" 구조를 피하려는 설계다.

**질문별 답**

- Q: 넣을 자리를 앞에서부터 훑어 찾는 풀이의 비용은 얼마인가?
  A: 자리 찾기가 최악 n 번 비교라 O(n) 이다.
  거기에 삽입 시프트 O(n) 이 더해진다.
  합쳐서 O(n) — 차수로는 이진 탐색 풀이와 같다.
  다만 실제 비교 횟수는 n 번 대 log n 번으로 크게 다르다.

- Q: 이진 탐색으로 찾는 풀이는 무엇을 찾는 것인가(값의 위치인가, 경계인가)?
  A: **경계**다. 정확히는 "value 보다 큰 첫 위치"(upper bound).
  값이 배열에 있든 없든 항상 하나의 답이 정해진다.
  값이 없어도 `-1` 이 아니라 "여기 넣으면 된다"는 자리를 준다.
  그래서 `add(lo, value)` 를 바로 부를 수 있고 그 `lo` 가 곧 반환값이다.

- Q: "같은 값이 있으면 그 뒤"라는 조건은 비교 연산자를 어떻게 바꾸는가?
  A: `<` 가 아니라 `<=` 를 쓰게 만든다.
  `array.get(mid) <= value` 면 `lo = mid + 1` 로 넘어가므로 같은 값들을 전부 지나친다.
  `<` 로 하면 같은 값을 만난 순간 `hi = mid` 로 접혀 같은 값들 **앞**에 들어간다.
  테스트 `insertsAfterEqualValues` 가 이것을 못박는다 — `[1,3,3,5]` 에 3을 넣으면 반환 3이다.

- Q: 자리 찾기를 O(log n) 으로 줄여도 전체 복잡도가 그대로인 이유는?
  A: 탐색과 삽입이 곱해지는 관계가 아니라 **더해지는** 관계이기 때문이다.
  `O(log n) + O(n)` 에서 n 이 커지면 `log n` 은 무시할 만큼 작아진다.
  큰 항이 지배하므로 합은 O(n) 이다.
  병목은 자리를 찾는 일이 아니라 뒤 원소를 전부 한 칸씩 미는 일이다.

- Q: 그래도 이진 탐색이 무의미하지 않은 이유는?
  A: 복잡도의 차수는 같아도 실제 연산 수가 다르기 때문이다.
  비교 횟수가 n 에서 log n 으로 준다 — n = 10^6 이면 10^6 대 약 20이다.
  시프트는 `System.arraycopy` 로 내려가는 저수준 블록 복사라 원소당 비용이 비교보다 훨씬 싸다.
  비교가 비싼 타입일수록 이 차이가 실측으로 드러난다. **복잡도가 같다고 무의미한 것은 아니다.**

- Q: 정렬 삽입이 계속 반복되는 워크로드라면 동적 배열이 맞는 선택인가?
  A: 아니다. 삽입 1회가 O(n) 이므로 n 번 반복하면 O(n^2) 이 된다.
  시프트는 "연속 저장"이라는 설계에서 필연적으로 나오는 비용이라 알고리즘으로 없앨 수 없다.
  삽입이 잦고 정렬을 유지해야 한다면 균형 이진 탐색 트리(삽입 O(log n))나 스킵 리스트가 맞다.
  반대로 삽입이 드물고 조회·순회가 압도적이면 동적 배열이 여전히 유리하다 — 워크로드의 비율로 정할 문제다.

#### 4. 조건에 맞는 원소를 모두 제거 (이 문제집의 핵심)

**접근 1 — 훑으면서 `remove(i)`** (문제가 말한 그 함정. 정답은 나오지만 통과하지 못한다)

```java
// 의사코드
int removed = 0;
for (int i = array.size() - 1; i >= 0; i--) {
    if (predicate.test(array.get(i))) { array.remove(i); removed++; }
}
return removed;
```

- 논리: 조건에 맞으면 그 자리를 지운다. 뒤에서부터 돌아야 인덱스가 어긋나지 않는다.
- 논리: 결과 자체는 맞다. 작은 입력에서는 아무 문제가 없다.
- 비용(왜): `remove(i)` 한 번이 뒤쪽 원소를 전부 당기므로 O(n).
- 비용(왜): n 개 중 절반을 지우면 `n/2 x (평균 n/2) = n^2/4` 회 복사 → **O(n^2)**.
- 비용(왜): 루프를 n 번 도는 것이 문제가 아니라 그 안에서 O(n) 짜리를 부르는 것이 문제다.
- 한계: n = 1,000,000 이면 계산상 약 2.5 x 10^11 회 복사 — `mustBeLinear` 의 5초 제한에 걸린다.
- 한계: "정답은 나오는데 통과 못 하는" 구현이라 작은 테스트만으로는 잡히지 않는다.

**접근 2 — 두 포인터로 살릴 것만 앞으로 모으고 꼬리를 자르기** (impl 의 정답)

```java
public static <E> int removeAllIf(DynamicArray<E> array, Predicate<? super E> predicate) {
    int n = array.size();
    int write = 0;
    for (int read = 0; read < n; read++) {
        E value = array.get(read);
        if (!predicate.test(value)) {
            if (write != read) {
                array.set(write, value);
            }
            write++;
        }
    }
    truncate(array, write);
    return n - write;
}

/** 뒤에서부터 지운다. 맨 뒤 삭제는 시프트가 없어 O(1) 이다. */
private static void truncate(DynamicArray<?> array, int newSize) {
    while (array.size() > newSize) {
        array.remove(array.size() - 1);
    }
}
```

- 논리: 핵심은 **지우지 않는 것**이다. 살릴 값만 앞으로 모은다.
- 논리: 조건에 걸리는 원소는 그냥 건너뛴다 — 건너뛴 자리는 나중에 덮이거나 잘린다.
- 논리: `write != read` 검사는 자기 자리에 자기를 다시 쓰는 낭비를 줄이는 최적화다. 없어도 정답이다.
- 논리: `n` 을 루프 전에 고정해 둔다. 순회 중 배열 크기를 바꾸지 않으므로 사실 변하지 않지만, 반환값 `n - write` 를 위해 원래 크기가 필요하다.
- 논리: 마지막에 `write` 뒤 꼬리를 잘라낸다. **맨 뒤부터** 지워야 시프트가 없다.
- 비용(왜): 읽기 n + `predicate.test` n + 쓰기 최대 n + 자르기 최대 n → **O(n)**.
- 비용(왜): 꼬리 삭제 한 번은 `moved = size - index - 1 = 0` 이라 O(1). O(1) 짜리를 최대 n 번 = O(n).
- 비용(왜): 중간에 `maybeShrink` 의 복사가 섞이지만 축소도 배수 전략이라 상환 O(1) 이다.
- 비용(왜): 추가 공간은 인덱스 변수뿐 → **O(1)**.
- 한계: 남는 원소들의 인덱스가 전부 바뀐다. 외부에서 인덱스를 들고 있었다면 무효가 된다.
- 한계: `predicate` 가 배열을 건드리면(순회 중 수정) 불변식이 깨진다. 순수 함수여야 한다.

**접근 3 — 새 배열에 살릴 것만 담아 교체**

```java
// 의사코드
DynamicArray<E> kept = new DynamicArray<>(array.size());
for (int i = 0; i < array.size(); i++)
    if (!predicate.test(array.get(i))) kept.add(array.get(i));
// 원본을 kept 로 되채운다
```

- 논리: 원본을 건드리지 않고 결과를 따로 만든 뒤 되채운다.
- 논리: 되채우는 단계가 없으면 원본이 안 줄어들어 계약을 못 지킨다.
- 비용(왜): 읽기 n + 쓰기 최대 n + 되채우기 최대 n → 시간 **O(n)**.
- 비용(왜): 결과 배열이 최악 n 칸 → 추가 공간 **O(n)**.
- 한계: 접근 2와 시간 차수는 같은데 메모리를 2배 쓴다.
- 한계: 반면 원본을 그대로 두고 새 컬렉션을 반환하는 API(자바 스트림 `filter`)라면 이쪽이 자연스럽다 — 요구 계약이 다를 뿐이다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. remove(i) 반복 | O(n^2) | O(1) | n 이 수백 이하로 확실할 때 | n 이 크면 즉시 무너진다 |
| 2. 두 포인터 + truncate | O(n) | O(1) | 기본값. 제자리 일괄 삭제 | predicate 가 배열을 수정할 때 |
| 3. 새 배열에 담기 | O(n) | O(n) | 원본 보존이 계약일 때 | 메모리가 빠듯할 때 |

**데이터 규모가 커지면**

- n = 1,000 이면 접근 1도 계산상 25만 회라 눈에 안 띈다. 그래서 함정이 프로덕션까지 살아남는다.
- n = 1,000,000 이면 접근 1은 계산상 약 2.5 x 10^11 회, 접근 2는 약 3 x 10^6 회다. 5자리 차이다.
- 이것이 `mustBeLinear` 테스트가 100만 건 / 5초 제한으로 잡아내는 정확히 그 지점이다.
- n = 1억이면 접근 3의 추가 배열이 계산상 400~800MB(참조만) 이라 접근 2만 남는다.
- 데이터가 메모리에 안 올라가면 제자리 압축 자체가 성립하지 않는다. 입력을 순차로 읽으며 조건에 안 걸리는 것만 출력 스트림으로 흘려보내는 방식이 된다 — 두 포인터의 read/write 를 입력 파일/출력 파일로 바꾼 것과 같다.
- 동시 접근이 있으면 접근 2는 위험하다. 순회 도중 다른 스레드가 보면 앞쪽은 압축되고 뒤쪽은 옛 값인 중간 상태가 보인다.

**질문별 답**

- Q: 훑으면서 `remove(i)` 를 부르는 풀이는 총 몇 번의 복사를 일으키는가(식으로)?
  A: `remove(i)` 한 번의 복사량은 `moved = size - i - 1` 이다.
  지우는 횟수를 m, 지울 때마다 뒤에 남은 평균 개수를 k 라 하면 총 복사는 `m x k`.
  n 개 중 절반을 지우고 위치가 고르게 흩어져 있으면 `m = n/2`, `k ≈ n/2`.
  총 `n/2 x n/2 = n^2/4` 회 → **O(n^2)**.

- Q: 그 풀이가 100만 건에서 통과하지 못하는 이유는?
  A: `n = 10^6` 을 식에 넣으면 `n^2/4 = 2.5 x 10^11` 회 복사다(계산상).
  블록 복사가 초당 10^9 회 진행된다고 낙관해도 수백 초가 필요하다.
  테스트 `mustBeLinear` 의 제한은 5초다.
  루프 횟수(10^6)만 보면 멀쩡해 보인다는 것이 함정의 본체다.

- Q: O(n) 풀이는 무엇에 기대는가?
  A: "지우는 대신 살릴 것을 앞으로 모은다"는 발상에 기댄다.
  `set(write, value)` 은 시프트가 없는 O(1) 연산이다.
  그리고 맨 뒤 삭제 역시 `moved = 0` 이라 O(1) 이다.
  즉 O(1) 짜리 연산만 n 번 쓰도록 문제를 재배치한 것이다.

- Q: 문제 1의 O(n) 풀이와 무엇이 같고 무엇이 다른가?
  A: 같은 것 — read/write 두 포인터, `write <= read` 불변식, 마지막에 꼬리 자르기, 전체 O(n)/O(1).
  다른 것 1 — 살릴지 판정하는 기준. 문제 1은 "직전에 살린 값과 다른가"(정렬 조건에 의존), 문제 4는 "predicate 가 false 인가"(값 자체만 본다).
  다른 것 2 — 문제 1은 정렬되어 있어야만 성립하고, 문제 4는 순서에 아무 조건이 없다.
  다른 것 3 — 문제 4는 원소 타입이 제네릭 `E` 라 값 비교 자체를 하지 않는다.

- Q: 마지막에 꼬리를 자르는 일은 왜 O(n) 안에 들어오는가?
  A: 맨 뒤(`size - 1`) 삭제는 `moved = size - index - 1 = 0` 이라 복사가 없다.
  즉 한 번이 O(1) 이다.
  그것을 최대 n 번 하니 `n x O(1) = O(n)`.
  중간에 `maybeShrink` 의 전체 복사가 섞이지만 축소도 배수 전략이라 상환 O(1) 이라 합계가 O(n) 을 넘지 않는다.

- Q: 꼬리를 앞에서부터 지우면 어떻게 되는가?
  A: `remove(write)` 를 반복하는 꼴이 되어 매번 뒤쪽 전부를 앞으로 당긴다.
  한 번이 O(n) 이므로 자르는 개수가 m 이면 `m x O(n)`.
  절반을 지우는 경우 `n^2/4` → **O(n^2)** 로, 앞의 두 포인터 최적화가 전부 무의미해진다.
  "어디를 지우느냐"가 비용을 결정한다는 것이 `remove` 의 핵심 성질이다.

- Q: `Predicate<? super E>` 로 받는 이유는 무엇인가?
  A: `E` 뿐 아니라 `E` 의 상위 타입을 받는 판정자도 쓸 수 있게 하려는 것이다.
  예를 들어 `DynamicArray<Integer>` 에 `Predicate<Number>` 나 `Predicate<Object>` 를 넘길 수 있다.
  판정자는 `E` 를 **소비**하기만 하므로 PECS 규칙의 consumer 쪽 — `super` 가 맞다.
  `Predicate<E>` 로 좁히면 이미 가지고 있는 범용 판정자를 재사용하지 못해 호출부가 불편해진다.

#### 5. 정렬된 두 배열 병합

**접근 1 — 두 배열을 이어붙인 뒤 정렬**

```java
// 의사코드
DynamicArray<Integer> result = new DynamicArray<>(a.size() + b.size());
for (int i = 0; i < a.size(); i++) result.add(a.get(i));
for (int j = 0; j < b.size(); j++) result.add(b.get(j));
sort(result);
```

- 논리: 입력이 정렬되어 있다는 사실을 전혀 쓰지 않는다.
- 논리: 순서를 모르는 데이터를 다루는 일반 해법을 그대로 적용한 것이다.
- 비용(왜): 복사 `O(n+m)` + 비교 기반 정렬 `O((n+m) log(n+m))` → **O((n+m) log(n+m))**.
- 비용(왜): 결과 배열 `O(n+m)`, 정렬 구현에 따라 임시 공간이 더 들 수 있다.
- 한계: 이미 아는 정보를 버리고 다시 계산하므로 `log` 배만큼 손해다.
- 한계: 쓰는 정렬이 불안정(unstable)하면 같은 값의 원래 순서가 보장되지 않는다.

**접근 2 — 두 포인터로 지퍼처럼 합치기** (impl 의 정답)

```java
public static DynamicArray<Integer> merge(DynamicArray<Integer> a, DynamicArray<Integer> b) {
    DynamicArray<Integer> result = new DynamicArray<>(a.size() + b.size());
    int i = 0;
    int j = 0;
    while (i < a.size() && j < b.size()) {
        if (a.get(i) <= b.get(j)) {
            result.add(a.get(i++));
        } else {
            result.add(b.get(j++));
        }
    }
    while (i < a.size()) {
        result.add(a.get(i++));
    }
    while (j < b.size()) {
        result.add(b.get(j++));
    }
    return result;
}
```

- 논리: 양쪽 맨 앞만 비교해 작은 쪽을 담는다. 각 배열이 정렬되어 있으므로 그 둘 중 하나가 전체 최솟값이다.
- 논리: 각 원소를 정확히 한 번씩만 본다.
- 논리: 한쪽이 소진되면 남은 쪽은 이미 정렬되어 있으므로 비교 없이 그대로 이어 붙인다.
- 논리: 결과 크기가 `a.size() + b.size()` 로 확정되므로 그만큼 용량을 잡고 시작한다.
- 논리: 원본에는 `get` 만 부른다. `set`/`add`/`remove` 를 쓰지 않으므로 입력이 불변이다.
- 비용(왜): 비교 최대 `n + m - 1` 번, 쓰기 정확히 `n + m` 번 → 시간 **O(n+m)**.
- 비용(왜): 용량을 미리 잡았으므로 `ensureCapacity` 가 항상 조기 반환한다 → 확장(전체 복사) **0회**.
- 비용(왜): 결과 배열 자체가 `n + m` 칸 → 공간 **O(n+m)**.
- 한계: 결과를 통째로 메모리에 올려야 한다. 입력이 아주 크면 이 O(n+m) 이 벽이 된다.
- 한계: 입력이 정렬되어 있지 않으면 조용히 틀린 결과를 낸다 — 전제를 검사하지 않는다.

**접근 3 — 한쪽을 다른 쪽에 `insertSorted` 로 하나씩 밀어넣기**

```java
// 의사코드
DynamicArray<Integer> result = copyOf(a);
for (int j = 0; j < b.size(); j++) insertSorted(result, b.get(j));
```

- 논리: 이미 만들어 둔 문제 3의 해법을 재사용한다.
- 논리: 결과는 맞다. 정렬도 유지된다.
- 비용(왜): 삽입 1회가 O(n+m) 시프트다.
- 비용(왜): 그것을 m 번 → **O(m(n+m))**. `n ≈ m` 이면 O(n^2).
- 한계: 접근 1보다도 나쁘다. 정렬 조건을 절반만 쓰고(한쪽만) 나머지는 시프트로 태운다.
- 한계: 원본 `a` 를 복사하지 않고 그대로 쓰면 "원본을 건드리지 않는다"는 계약도 깨진다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 합쳐서 정렬 | O((n+m) log(n+m)) | O(n+m) + 정렬 임시 | 한쪽이 정렬 안 돼 있을 때 | 정렬 조건이 있는데 낭비할 때 |
| 2. 두 포인터 | O(n+m) | O(n+m) (결과) | 기본값. 양쪽 다 정렬되어 있을 때 | 결과가 메모리에 안 올라갈 때 |
| 3. insertSorted 반복 | O(m(n+m)) | O(n+m) | (없음) | 사실상 항상 |

**데이터 규모가 커지면**

- n = m = 500,000 이면 접근 2는 약 10^6 회 비교·쓰기, 접근 1은 계산상 약 2 x 10^7 회 비교(log2 10^6 ≈ 20배)다.
- 접근 3은 계산상 약 5 x 10^11 회 복사라 이 규모에서 이미 완주하지 못한다.
- n = 1억씩 둘이면 결과 배열만 2억 칸이다. 접근 2도 공간에서 막힌다 — 시간이 O(n+m) 이어도 결과를 다 들고 있어야 하기 때문이다.
- 그때는 결과를 배열로 만들지 않고 **이터레이터/스트림으로 흘려보낸다.** 두 포인터 로직은 그대로 두고 `result.add` 자리를 "다음 원소를 내보낸다"로 바꾸면 추가 공간이 O(1) 이 된다.
- 파일 단위로 더 커지면 외부 병합 정렬(external merge sort)의 병합 단계가 정확히 이 알고리즘이다. 각 파일에서 한 줄씩 읽어 작은 쪽을 출력한다.
- 합칠 배열이 2개가 아니라 k 개로 늘면 매번 k 개를 비교하는 대신 최소 힙을 써서 `O((n+m+...) log k)` 로 만든다.

**질문별 답**

- Q: 합쳐서 정렬하는 풀이는 왜 O((n+m) log(n+m)) 인가?
  A: 비교 기반 정렬의 하한이 원소 수 N 에 대해 `N log N` 이기 때문이다.
  여기서 `N = n + m` 이다.
  이 하한은 "원소들의 순서에 대해 아무것도 모른다"는 전제에서 나온다.
  가능한 순열 `N!` 개를 비교 한 번(2갈래)으로 좁혀야 하므로 최소 `log2(N!) ≈ N log N` 번의 비교가 필요하다.

- Q: 이미 정렬되어 있다는 조건을 쓰면 왜 log 가 사라지는가?
  A: 정렬이 하려던 일(순서 정보 알아내기)이 이미 끝나 있기 때문이다.
  남은 일은 "두 줄을 지퍼처럼 합치기"뿐이다.
  각 단계에서 양쪽 맨 앞 둘만 비교하면 전체 최솟값이 결정된다 — 후보가 2개로 고정된다.
  단계마다 원소 하나가 확정되므로 총 `n + m` 단계, 비교도 단계당 1번이라 **O(n+m)** 이다.

- Q: 두 포인터로 합칠 때 한쪽이 먼저 소진되면 어떻게 하는가?
  A: 남은 쪽을 비교 없이 그대로 순서대로 이어 붙인다.
  남은 원소들은 이미 자기들끼리 정렬되어 있다.
  그리고 소진된 쪽에는 더 작을 수 있는 값이 하나도 없다.
  impl 의 두 번째·세 번째 `while` 이 이 처리다 — 둘 중 하나만 실제로 돈다.

- Q: 결과 배열의 최종 크기를 미리 잡으면 확장이 몇 번 일어나는가?
  A: **0번**이다.
  `new DynamicArray<>(a.size() + b.size())` 로 시작하면 capacity 가 처음부터 최종 size 와 같다.
  `add` 마다 불리는 `ensureCapacity(size + 1)` 에서 `minCapacity <= elements.length` 라 항상 조기 반환한다.
  전체 복사가 한 번도 일어나지 않는다.

- Q: 미리 잡지 않으면 확장과 복사가 얼마나 더 붙는가?
  A: 기본 용량 4에서 시작해 2배씩 커지므로 확장이 약 `log2((n+m)/4)` 번 일어난다.
  총 복사량은 등비급수 합으로 `(n+m) + (n+m)/2 + (n+m)/4 + ... < 2(n+m)`.
  차수는 여전히 O(n+m) 이라 복잡도는 안 변한다.
  하지만 실측으로는 원소당 약 2회의 추가 복사와 log 번의 배열 재할당·GC 압력이 붙는다.

- Q: 원본을 건드리지 않으려면 무엇을 지켜야 하는가?
  A: 원본에는 `get` 만 부르고 `set`/`add`/`remove` 를 부르지 않아야 한다.
  결과는 반드시 **새 배열**이어야 한다 — 입력 중 하나를 재사용하면 안 된다.
  원소 객체 자체도 변경하면 안 된다(여기서는 `Integer` 라 불변이지만, 가변 객체면 얕은 복사의 함정이 생긴다).
  테스트 `doesNotMutateInputs` 가 이것을 확인한다.

- Q: 같은 값이 양쪽에 있을 때 어느 쪽을 먼저 넣는가, 그 선택은 무엇과 관련 있는가?
  A: impl 은 `a.get(i) <= b.get(j)` 이므로 **a 쪽**을 먼저 넣는다.
  이것은 정렬의 **안정성(stability)** 에 해당하는 선택이다.
  같은 키를 가진 원소들의 상대 순서를 입력 순서(a 가 앞)대로 보존한다는 뜻이다.
  값 자체만 보면 `[1,2,3,3,5,6]` 으로 결과가 같지만, 키 외에 다른 필드를 가진 레코드라면 어느 쪽 레코드가 앞에 오는지가 달라진다. 병합 정렬이 안정 정렬인 근거도 이 한 글자다.

- Q: 두 배열이 메모리에 다 안 올라갈 만큼 크면 이 풀이는 어떻게 바뀌어야 하는가?
  A: 결과를 배열로 만들지 않고 흘려보내야 한다.
  두 포인터 로직은 그대로 두고 `result.add(...)` 를 "다음 원소를 출력 스트림에 쓴다"로 바꾼다 — 추가 공간이 O(1) 이 된다.
  입력도 전부 올릴 수 없으면 양쪽을 순차 읽기(이터레이터/파일 리더)로 바꾸고 한 번에 한 원소씩만 들고 있는다.
  이것이 외부 병합 정렬(external merge sort)의 병합 단계이고, 합칠 소스가 k 개로 늘면 최소 힙을 써서 `O(N log k)` 로 만든다.

### B. 자료구조의 특성

#### 6. 동적 배열은 왜 필요한가

- Q: 고정 길이 배열의 어떤 한계를 메우는가?
  A: 자바 배열은 만들 때 길이를 정하고 나중에 바꿀 수 없다는 한계다.
  그런데 실제 프로그램은 "몇 개가 들어올지 모르는" 경우가 대부분이다.
  크게 잡으면 안 쓰는 칸이 낭비되고, 작게 잡으면 넘쳐서 터진다.
  동적 배열은 그 결정을 실행 시점으로 미뤄준다.

- Q: 내부에서 실제로 무슨 일을 해서 "늘어나는 것처럼" 보이게 하는가?
  A: 내부에 고정 길이 배열(`elements`)을 하나 들고 있는다.
  꽉 차면 더 큰 배열을 새로 만든다.
  기존 원소를 그 새 배열로 전부 복사한다(`Arrays.copyOf`).
  참조를 새 배열로 갈아끼운다 — 밖에서 보면 "같은 배열이 커진 것"처럼 보인다.

- Q: `size` 와 `capacity` 를 분리해서 갖는 것이 그 한계 극복에서 하는 역할은 무엇인가?
  A: `capacity` 는 내부 배열의 길이, `size` 는 실제로 담긴 원소 수다.
  미리 여유를 잡아두고(capacity) 실제로 쓴 만큼만 센다(size).
  그 여유 칸 덕분에 대부분의 `add` 는 빈 칸에 값 하나 쓰고 `size++` 하는 O(1) 로 끝난다.
  즉 "비싼 복사"를 매 연산이 아니라 가끔으로 몰아주는 장치다. capacity 8 에 3개가 들어 있으면 size=3, capacity=8 이다.

- Q: 둘이 항상 같다면 add 의 비용은 어떻게 되는가?
  A: 매번 딱 맞는 배열이라는 뜻이므로 `add` 마다 배열이 꽉 차 있다.
  그래서 `add` 마다 새 배열을 만들고 전체를 복사해야 한다 → 한 번이 **O(n)**.
  n 번 `add` 하면 `1 + 2 + ... + n = n(n+1)/2` → 총 **O(n^2)**.
  여유 칸이 없으면 상환 O(1) 이라는 성질 자체가 성립하지 않는다.

**더 생각할 것**

- 원소 수를 대충이라도 알면 `new DynamicArray<>(예상치)` 로 시작하는 것이 가장 싼 최적화다 — 문제 5가 그 예다.
- 반대로 예상치를 크게 잡으면 안 쓰는 칸만큼 메모리를 계속 붙잡는다. 100만 개 리스트를 1000개 만들면 그 낭비가 GB 단위가 된다.
- 원소가 원시 타입인데 `DynamicArray<Integer>` 를 쓰면 박싱된 객체가 원소마다 따로 생긴다. 1억 건이면 참조 배열 외에 객체 헤더까지 계산상 수 GB다. 규모가 커지면 `int[]` 기반 특화 구조나 오프힙 버퍼로 간다.

#### 7. 어떤 데이터·접근 패턴에 적합한가

- Q: 어떤 접근 패턴에서 동적 배열이 유리한가?
  A: 인덱스로 임의 접근이 잦을 때 — 주소 계산 한 번이라 O(1) 이다.
  맨 뒤에 쌓기(`add`)와 맨 뒤에서 빼기 — 시프트가 없어 상환 O(1) 이다.
  처음부터 끝까지 순회 — 원소가 메모리에 붙어 있어 캐시 지역성이 좋다.
  읽기가 압도적이고 쓰기가 꼬리에 몰린 패턴이 최적이다.

- Q: 어떤 접근 패턴에서 불리한가?
  A: 앞이나 중간에 삽입·삭제가 잦을 때 — 매번 O(n) 시프트다.
  크기가 크게 요동칠 때 — 확장·축소의 전체 복사가 반복된다.
  값으로 찾기(`indexOf`, `contains`)가 잦을 때 — 순차 탐색이라 O(n) 이다(해시맵이면 O(1)).
  응답 지연 상한이 엄격할 때 — 확장 순간의 O(n) 이 튀는 지점이 된다.

- Q: 어떤 형태의 데이터를 담기에 좋은가(크기 변동, 순서, 접근 방식 기준으로)?
  A: 크기 변동 기준 — 대체로 늘어나기만 하거나 꼬리에서만 줄어드는 데이터.
  순서 기준 — 넣은 순서나 정렬 순서가 의미를 갖고 그 순서로 읽는 데이터.
  접근 방식 기준 — "몇 번째"로 찾는 데이터. "어떤 키"로 찾는 데이터는 맵이 맞다.
  원소 크기 기준 — 원소가 작고 균일할수록 연속 저장의 캐시 이득이 크다.

- Q: 연결 리스트(02번)와 비교했을 때 무엇을 얻고 무엇을 내주는가?
  A: 얻는 것 — 인덱스 접근 O(1), 캐시 지역성, 노드 포인터 오버헤드 없음.
  내주는 것 — 앞·중간 삽입·삭제가 O(n) 시프트, 확장 시 전체 복사.
  표로 보면 이렇다.

  | | 동적 배열 | 연결 리스트 |
  |---|---|---|
  | 인덱스 접근 | O(1) | O(n) — 처음부터 따라가야 |
  | 위치를 이미 안 상태의 삽입·삭제 | O(n) 시프트 | O(1) 참조만 갈아끼움 |
  | 메모리 | 연속, 원소만 | 흩어짐, 노드마다 포인터 오버헤드 |
  | 캐시 | 지역성 좋음 | 지역성 나쁨 |

- Q: 그 교환의 뿌리가 되는 설계 선택 한 가지는 무엇인가?
  A: **연속 저장**이다. 원소를 메모리에 붙여서 놓는다는 선택 하나다.
  연속이라서 `base + index * 원소크기` 로 주소를 바로 계산한다 → O(1) 접근.
  연속이라서 중간을 비우거나 끼우면 뒤를 전부 밀거나 당겨야 한다 → O(n) 시프트.
  얻는 것과 잃는 것이 같은 뿌리에서 나온다 — 하나만 고를 수 없다.

- Q: 데이터가 수천만 건이 되면 연속 저장이 어떤 문제를 만드는가?
  A: 그만한 크기의 **연속된** 메모리 덩어리를 하나 확보해야 한다. 전체 여유 메모리가 충분해도 단편화 때문에 실패할 수 있다.
  확장할 때 옛 배열과 새 배열이 동시에 살아 있으므로 순간적으로 1.5배(2배 확장 시)의 메모리가 필요하다.
  전체 복사 한 번이 수천만 원소를 옮기므로 그 순간의 지연이 밀리초~초 단위로 튄다.
  JVM 이라면 큰 배열이 GC 의 humongous/old 영역에 들어가 수집 비용까지 얹힌다. 그래서 규모가 커지면 하나의 큰 배열 대신 청크를 이어붙인 구조(rope, chunked list)나 오프힙으로 간다.

**더 생각할 것**

- "적합/부적합"은 자료구조 자체의 성질이 아니라 **워크로드 비율**의 문제다. 앞 삽입이 전체의 0.1% 면 O(n) 이어도 무해하다.
- 실무에서는 "읽기 99% / 쓰기 1%" 같은 비율을 먼저 재고 자료구조를 고른다. 재보지 않고 고르면 대개 틀린다.
- 규모가 커지면 자료구조 하나로 안 되고 조합이 된다 — 인덱스 접근용 배열 + 키 조회용 해시맵을 같이 들고 동기화하는 식이다.

#### 8. 확장할 때 왜 2배로 키우는가

- Q: 1씩 키우면 add 를 n 번 할 때 총 복사량은 얼마인가(식으로)?
  A: `add` 마다 꽉 차 있으므로 매번 전체를 새 배열로 복사한다.
  i 번째 `add` 에서 i 개를 복사한다.
  총 복사량 = `1 + 2 + ... + n = n(n+1)/2`.
  약 `n^2/2` → **O(n^2)**.

- Q: 2배로 키우면 확장은 몇 번 일어나고 총 복사량은 얼마인가(식으로)?
  A: 초기 용량 c 에서 확장 지점은 `c, 2c, 4c, ...` 뿐이므로 약 **log2(n/c) 번**이다.
  총 복사량은 마지막 확장부터 거꾸로 더하면 `n + n/2 + n/4 + ... < 2n`.
  등비급수라 항이 아무리 많아도 합이 `2n` 을 넘지 못한다.
  그래서 총 **O(n)**, `add` 1회 평균 O(1) 이다. 이것이 배수 전략의 전부다.

- Q: "상환(amortized) O(1)" 은 정확히 무슨 뜻인가?
  A: **연속된 n 번의 `add` 총비용이 O(n) 이므로 1회 평균이 O(1)** 이라는 뜻이다.
  개별 `add` 가 항상 O(1) 이라는 말이 아니다.
  비싼 연산(확장)이 드물게 일어나고 그 비용을 앞뒤의 싼 연산들이 나눠 갚는다는 회계다.
  "평균적으로 그럴 것 같다"는 확률적 진술이 아니라, 어떤 입력 순서에서도 성립하는 **보장**이다.

- Q: "언제나 O(1)" 과는 어떻게 다른가?
  A: "언제나 O(1)" 은 **개별 연산 1회의 최악**이 상수라는 뜻이다.
  동적 배열의 `add` 는 확장이 걸리는 그 한 번이 O(n) 이라 이 조건을 만족하지 못한다.
  상환 O(1) 은 **누적 총합**에 대한 보장이고, 최악 O(1) 은 **각 호출**에 대한 보장이다.
  총 처리량만 보면 둘이 같아 보이지만, 한 번의 지연이 문제가 되는 상황에서는 완전히 다르다.

- Q: capacity 가 0 일 때 2배를 하면 어떤 일이 생기고 어떻게 막는가?
  A: `0 * 2 = 0` 이라 새 용량도 0이다. 배열이 영원히 커지지 않는다.
  그 상태로 `elements[size++]` 를 하면 ArrayIndexOutOfBoundsException 이 나거나 무한히 확장 시도만 반복한다.
  impl 은 `int newCapacity = (elements.length == 0) ? DEFAULT_CAPACITY : elements.length * 2;` 로 0을 특수 처리한다.
  테스트 `growsFromZeroCapacity` 가 `new DynamicArray<>(0)` 에 `add` 한 뒤 `capacity() >= 1` 을 확인한다.

- Q: 2배가 아니라 1.5배나 3배면 무엇이 달라지는가?
  A: 배수가 1보다 크기만 하면 총 복사량은 등비급수 합 `n x r/(r-1)` 로 유한하므로 **상환 O(1) 은 그대로 유지된다.**
  1.5배면 총 복사가 약 `3n` 으로 늘고 확장 횟수도 `log1.5 n` 으로 잦아진다. 대신 최악의 빈 칸이 capacity 의 1/3 이라 메모리 낭비가 적다.
  3배면 총 복사가 약 `1.5n` 으로 줄고 확장도 `log3 n` 으로 드물다. 대신 최악의 빈 칸이 capacity 의 2/3 다.
  즉 **복사 횟수(시간)와 빈 칸 비율(공간)의 교환**이고, 2배는 그 중간의 관습적 선택이다. (1.5배는 해제된 옛 블록을 재사용하기 유리하다는 이유로 일부 구현이 택한다.)

- Q: 응답 지연이 중요한 시스템에서 "가끔 튀는 O(n)" 은 왜 문제가 되는가?
  A: 그런 시스템의 목표는 평균이 아니라 **꼬리 지연(p99, p999)** 이기 때문이다.
  평균이 1ms 라도 1000번에 한 번 500ms 가 나오면 p999 는 500ms 다.
  원소가 수천만 개면 확장 한 번의 전체 복사가 실제로 그만한 지연을 만든다.
  그래서 실시간·저지연 시스템은 용량을 미리 확보해 확장을 아예 없애거나, 청크 단위로 나눠 한 번의 최악을 상수로 묶는다.

**더 생각할 것**

- 총 처리량(throughput)만 보는 배치 작업이면 상환 O(1) 로 충분하다. 요청당 지연을 보는 온라인 서비스면 부족하다. 같은 지표가 워크로드에 따라 다르게 읽힌다.
- 크기를 미리 아는 상황에서는 배수 전략을 논할 필요 자체가 없다 — 초기 용량을 잡으면 확장이 0회다(문제 5).
- 규모가 아주 커지면 "한 번에 2배로 늘린 연속 메모리"를 확보하는 것 자체가 실패할 수 있다. 그때는 배수를 조정하는 게 아니라 연속성을 포기하는 쪽(청크 리스트)으로 간다.

#### 9. 왜 1/4 이하에서 절반으로 줄이는가

- Q: 늘리기만 하고 줄이지 않으면 무엇이 문제인가?
  A: 한 번 커진 배열은 원소를 다 빼도 그 크기 그대로 메모리를 붙잡는다.
  100만 개를 넣었다 999,999개를 뺐어도 capacity 는 100만 칸 그대로다.
  그런 리스트가 여러 개 살아 있으면 안 쓰는 칸이 메모리를 계속 점유한다.
  게다가 빈 칸에 옛 참조가 남아 있다면 그 객체들까지 GC 되지 않는다(→ 12번).

- Q: 1/2 에서 줄이면 무슨 일이 생기는가(thrashing)?
  A: capacity 16 / size 8 인 경계에서 `add` 와 `remove` 를 번갈아 하면 이렇게 된다.
  `add` → size 9 라 꽉 차서 32로 확장(전체 복사 O(n)).
  `remove` → size 8 이라 절반이므로 16으로 축소(전체 복사 O(n)).
  **연산 하나하나가 매번 전체 복사**가 되어 상환 O(1) 이 무너진다. 이것이 thrashing 이고 테스트 `doesNotThrashAtBoundary` 가 50회 반복으로 잡는다.

- Q: 1/4 에서 줄이면 왜 그 일이 안 생기는가?
  A: 축소 직후 size 는 새 capacity 의 **정확히 1/2** 이 되기 때문이다(capacity/4 였던 size 가 capacity/2 에 대해 1/2).
  거기서 다시 확장하려면 size 가 2배가 되어야 하고, 다시 축소하려면 절반이 되어야 한다.
  즉 늘리는 문턱과 줄이는 문턱 사이에 **여유(hysteresis)** 가 생기고, 그 여유가 왕복을 막는다.
  경계에서 오가더라도 두 전체 복사 사이에 최소 O(n) 번의 연산이 끼므로 상환 비용은 O(1) 로 유지된다.

- Q: 축소에 하한(최소 용량)을 두지 않으면 어떤 일이 벌어지는가?
  A: 매번 절반이 되어 `4 → 2 → 1 → 0` 까지 내려간다.
  capacity 0 이 되면 8번의 "0 * 2 = 0" 특수 처리에 다시 걸린다.
  작은 배열에서 확장·축소가 반복되면 이득 없는 재할당만 늘어난다 — 원소 몇 개 아끼자고 배열을 계속 새로 만드는 꼴이다.
  impl 은 `halved >= DEFAULT_CAPACITY` 조건으로 막고, 테스트 `doesNotShrinkBelowMinimum` 이 `capacity() >= 4` 를 확인한다.

- Q: 축소 정책이 구현 재량이 아니라 계약이 된 이유는?
  A: 테스트가 문턱과 결과 용량을 숫자로 못박고 있기 때문이다.
  `shrinksAtQuarter` — size 가 capacity/4 에 닿는 순간 capacity 가 정확히 절반이 되는지 본다.
  `doesNotThrashAtBoundary` — size 가 절반일 때는 줄지 않는지, 경계에서 50회 왕복해도 capacity 가 16 그대로인지 본다.
  `doesNotShrinkBelowMinimum` — 하한을 지키는지 본다. 정책을 바꾸면 이 셋이 깨진다 → 정책 자체가 공개 계약이다.

**더 생각할 것**

- 실제 `java.util.ArrayList` 는 자동 축소를 하지 않는다. 대신 `trimToSize()` 를 호출자가 명시적으로 부르게 한다 — "언제 줄일지는 호출자가 안다"는 다른 판단이다.
- 축소가 없으면 메모리를 낭비하고, 축소가 공격적이면 시간을 낭비한다. 어느 쪽 비용이 비싼지는 환경에 달렸다(메모리가 싼 서버 vs 빠듯한 임베디드).
- 규모가 커지면 축소 한 번의 전체 복사 자체가 지연 스파이크다. 대량 삭제 후 한 번만 줄이는 배치형 축소가 연산마다 판정하는 방식보다 유리해진다.

#### 10. `remove(index)` 의 비용이 자리마다 다른 이유

- Q: `remove` 가 실제로 하는 일은 무엇인가?
  A: "지우기"가 아니라 **"뒤에 있는 것들을 앞으로 당기기"** 다.
  연속 저장이라 중간에 구멍을 남길 수 없으므로 빈 자리를 메워야 한다.
  당길 개수는 `moved = size - index - 1` 이다.
  그다음 `elements[--size] = null` 로 마지막 칸의 참조를 끊고 `maybeShrink()` 를 부른다.

- Q: 맨 뒤를 지울 때 O(1) 인 이유는?
  A: `index == size - 1` 이면 `moved = size - (size-1) - 1 = 0` 이기 때문이다.
  당길 원소가 하나도 없으니 `System.arraycopy` 가 아예 실행되지 않는다.
  남는 일은 `size` 를 하나 줄이고 그 칸을 null 로 만드는 것뿐 — 상수 시간이다.
  (`maybeShrink` 의 복사가 가끔 섞이지만 배수 전략이라 상환 O(1) 이다.)

- Q: 맨 앞이나 중간을 지울 때 O(n) 인 이유는?
  A: `index == 0` 이면 `moved = size - 1` — 사실상 전체를 한 칸씩 앞으로 옮긴다.
  중간이면 평균 `n/2` 개를 옮긴다.
  둘 다 n 에 비례하므로 O(n) 이다.
  비용을 정하는 것은 "무엇을 지우느냐"가 아니라 **"지운 자리 뒤에 몇 개가 있느냐"** 다.

- Q: 이 사실은 "여러 개를 지워야 할 때" 어떤 전략을 시사하는가?
  A: 앞에서부터 하나씩 `remove` 하지 말라는 것 — 그러면 O(n) x m 이 된다.
  대신 **살릴 것을 앞으로 모으고(O(1) 짜리 `set`), 꼬리를 뒤에서 자른다(O(1) 짜리 `remove`).**
  O(1) 연산만 쓰도록 문제를 재배치하면 전체가 O(n) 이 된다.
  문제 1의 접근 3과 문제 4의 `truncate` 가 정확히 이 전략이고, 이 문제집의 관통 주제다.

- Q: `remove(int)` 와 `remove(Object)` 는 왜 헷갈리고, `DynamicArray<Integer>` 에서 무엇이 문제인가?
  A: 이름이 같고 인자 하나만 받는 오버로드인데 의미가 정반대이기 때문이다 — 하나는 **위치**, 하나는 **값**.
  `DynamicArray<Integer>` 에서 `remove(1)` 의 리터럴 `1` 은 `int` 라 자바가 `remove(int)`, 즉 **인덱스 1**로 해석한다.
  값 1을 지우려면 `remove(Integer.valueOf(1))` 처럼 명시적으로 래핑해야 한다.
  오버로드 해소는 오토박싱보다 우선하므로 컴파일 에러도 경고도 없이 조용히 다른 일을 한다. `ArrayList` 의 대표적 함정이고 테스트 `removeOverloadDistinguishesIndexFromValue` 에 박혀 있다.

**더 생각할 것**

- 큐가 필요해서 `remove(0)` 을 반복하고 있다면 자료구조가 틀린 것이다. `ArrayDeque` 는 링 버퍼라 앞 제거가 O(1) 이다.
- 삭제가 잦고 순서가 중요하지 않다면 "지울 자리에 마지막 원소를 옮기고 꼬리를 자르는" swap-remove 가 O(1) 이다. 순서를 포기하고 시간을 얻는 교환이다.
- 규모가 커지면 O(n) 삭제 한 번의 절대 시간이 커진다. 1억 원소 배열의 앞 삭제 한 번은 계산상 수백 MB 를 옮기는 일이다 — 차수만이 아니라 상수도 봐야 한다.

#### 11. 최악 입력을 직접 만들어보라

- Q: `add(0, x)` 를 n 번 하면 총 복사량은 얼마인가?
  A: i 번째 삽입에서 이미 들어있는 i 개를 전부 한 칸씩 뒤로 민다.
  총 `0 + 1 + 2 + ... + (n-1) = n(n-1)/2` ≈ `n^2/2` 회 복사.
  → **O(n^2)**.
  여기에 확장 복사 `< 2n` 이 더 붙지만 `n^2` 에 묻힌다.

- Q: 중간 `remove` 를 n/2 번 반복하면 총 복사량은 얼마인가?
  A: 한 번의 중간 삭제가 평균 `n/2` 개를 당긴다.
  그것을 `n/2` 번 → `n/2 x n/2 = n^2/4` 회 복사.
  → **O(n^2)**.
  n = 1,000,000 이면 계산상 약 2.5 x 10^11 회 — 문제 4의 `mustBeLinear` 가 이것을 시간으로 보여준다.

- Q: 반대로 총비용이 선형에 머무는 최선의 사용 패턴은 무엇인가?
  A: 맨 뒤에만 `add(x)` — 시프트 0, 확장 복사 총합 `< 2n` → **O(n)**, 1회 상환 O(1).
  맨 뒤에서만 `remove(size-1)` — `moved = 0`, 축소 복사도 상환 O(1) → **O(n)**.
  `get`/`set` 으로만 훑기 — 복사 0, 주소 계산뿐 → **O(n)**.
  즉 **꼬리에서만 늘리고 줄이고, 나머지는 인덱스로 읽고 쓰는** 패턴이 동적 배열의 최적 사용법이다(스택·버퍼·순회 대상 목록).

- Q: 최악 패턴이 실제 워크로드라면 무엇을 바꿔야 하는가?
  A: 알고리즘이 아니라 **자료구조**를 바꿔야 한다. 시프트는 연속 저장에서 필연적으로 나오는 비용이라 코드로 없앨 수 없다.
  앞쪽 삽입·삭제가 잦으면 `ArrayDeque`(링 버퍼, 양끝 O(1)) 또는 연결 리스트.
  정렬 유지 삽입이 잦으면 균형 이진 탐색 트리나 스킵 리스트(O(log n)).
  그것도 아니면 문제를 재배치한다 — 삭제를 모아 한 번의 O(n) 압축으로 처리하는 방식(문제 4)이 그 예다.

**더 생각할 것**

- 최악 패턴인지 아닌지는 코드가 아니라 **호출 방식**이 정한다. 같은 `DynamicArray` 가 스택으로 쓰이면 O(n), 큐로 쓰이면 O(n^2) 이다.
- 작은 n 에서는 최악 패턴도 안 드러난다. 문제가 되는 시점은 데이터가 커진 뒤라 대개 프로덕션에서 발견된다 — 그래서 `mustBeLinear` 같은 규모 테스트가 필요하다.
- 삭제를 즉시 하지 않고 "삭제 표시"만 해두었다가 한꺼번에 압축하는 방식(tombstone + compaction)은 규모가 커질수록 유리해진다. LSM 트리·GC 가 같은 발상이다.

#### 12. 지운 자리의 참조와 `toArray` 의 복사본

- Q: `remove` 뒤에 마지막 칸의 참조를 왜 끊어야 하는가?
  A: 뒤를 앞으로 당기고 나면 마지막 칸에는 **옛 참조가 그대로 남기** 때문이다.
  `size` 를 줄였으므로 논리적으로는 없는 값이다.
  하지만 배열이 여전히 그 객체를 가리키고 있으므로 GC 가 회수하지 못한다.
  그래서 `elements[--size] = null;` 로 명시적으로 끊는다.

- Q: 끊지 않으면 구체적으로 무슨 일이 생기는가?
  A: 논리적으로 지워진 객체가 메모리에 계속 살아 있다 — **조용한 메모리 누수**다.
  그 객체가 다른 큰 객체 그래프를 물고 있으면 딸려 있는 것 전부가 안 죽는다.
  리스트를 오래 재사용할수록(추가·삭제 반복) 누수량이 누적된다.
  공개 API 로는 아무 증상이 없어서 힙 덤프를 뜨기 전까지 발견되지 않는다.

- Q: `clear()` 에서 size 만 0 으로 만들면 왜 안 되는가?
  A: 같은 이유다 — 내부 배열의 칸들이 여전히 원소를 전부 가리킨다.
  `size = 0` 은 "논리적으로 비었다"고 선언할 뿐 참조를 놓지 않는다.
  `clear()` 이후에도 담겨 있던 객체 n 개가 통째로 살아남는다. 리스트를 비웠는데 메모리가 안 줄어드는 현상이다.
  그래서 impl 은 `for (int i = 0; i < size; i++) elements[i] = null;` 로 전부 끊은 뒤 size 를 0으로 만든다.

- Q: 참조를 끊었는지를 공개 API 로는 왜 관측할 수 없는가?
  A: `toArray()` 가 `Arrays.copyOf(elements, size)` 로 **size 만큼만** 복사하기 때문이다.
  size 밖 칸은 결과에 아예 포함되지 않는다.
  `get(index)` 도 `checkIndex` 가 `index >= size` 를 막으므로 size 밖을 볼 수 없다.
  즉 참조를 끊었든 안 끊었든 공개 API 의 모든 반환값이 똑같다.

- Q: 테스트는 그것을 어떻게 검사하는가?
  A: `TestSupport.raw(array)` 가 **리플렉션으로 `elements` 필드를 직접 꺼낸다.**
  `DynamicArray.class.getDeclaredField("elements")` → `setAccessible(true)` → `f.get(array)`.
  `clearsTrailingReference` 는 `assertNull(raw(array)[1])` 로 size 밖 칸이 null 인지 본다.
  `clearsButKeepsCapacity` 는 `Arrays.stream(raw(array)).allMatch(Objects::isNull)` 로 clear 후 전 칸이 null 인지 본다.

- Q: 그래서 무엇이 "계약의 일부"가 되었는가?
  A: **필드 이름 `elements`** 다.
  테스트가 그 이름으로 리플렉션을 걸기 때문에 이름을 바꾸면 `AssertionError("내부 배열 필드 이름은 elements 여야 한다")` 로 깨진다.
  보통 private 필드 이름은 구현 세부라 자유롭게 바꿀 수 있는데, 여기서는 그렇지 않다.
  "공개 API 로 관측 불가능한 성질을 검사하려고 내부를 열었다"는 선택의 대가로 이름이 굳었다. `capacity()` 를 public 으로 연 것도 같은 종류의 예외다.

- Q: `toArray()` 가 내부 배열이 아니라 복사본을 주는 이유는(두 가지)?
  A: 첫째, 캡슐화다. 내부 배열을 그대로 주면 호출자가 `result[0] = 999` 로 우리 상태를 마음대로 바꾼다(테스트 `returnsDefensiveCopy`).
  둘째, 길이다. 내부 배열은 **capacity 만큼** 길어서 그대로 주면 뒤에 null 들이 붙어 나온다.
  `Arrays.copyOf(elements, size)` 는 두 문제를 한 번에 푼다 — 새 배열이면서 길이가 size 다(테스트 `copiesOnlyElements`).
  다만 이 복사본은 얕은 복사다 — 배열은 분리되지만 원소 객체는 공유하므로, 원소가 가변이면 여전히 밖에서 바꿀 수 있다.

**더 생각할 것**

- 원소가 작고 개수가 많으면 `toArray()` 의 방어 복사 자체가 O(n) 비용이다. 뜨거운 경로에서 매번 부르면 그것이 병목이 된다.
- 규모가 커지면 "size 밖 참조 하나"가 아니라 **누수의 누적 속도**가 문제다. 초당 수만 건이 오가는 리스트면 끊지 않은 참조가 분 단위로 힙을 채운다.
- 테스트를 위해 내부를 여는 선택은 여기서는 레슨이 핵심이라 정당화되지만, 그 대가로 리팩토링 자유도를 잃는다. 관측 가능성이 필요하면 보통은 전용 훅이나 계측 API 를 두는 쪽이 비용이 작다.

#### 13. 루프 횟수가 아니라 루프 안 비용을 곱해야 하는 이유

- Q: 총비용을 셀 때 루프 횟수만 보면 무엇을 놓치는가?
  A: 총비용 = **반복 횟수 x 반복 1회의 비용**인데 뒤쪽 항을 통째로 빠뜨리게 된다.
  루프가 n 번 돈다는 사실만으로는 O(n) 이라고 말할 수 없다.
  루프 안에서 부르는 메서드가 O(1) 인지 O(n) 인지를 먼저 확인해야 한다.
  `remove`, `indexOf`, `add(0, x)` 처럼 이름은 짧은데 O(n) 인 연산이 특히 위험하다.

- Q: `2n` 은 왜 O(n) 인가?
  A: 빅오는 n 이 커질 때의 **증가율**만 보고 상수배는 버리기 때문이다.
  n 이 2배가 되면 `2n` 도 정확히 2배가 된다 — 선형이라는 성질이 그대로다.
  읽기 n 번 + 삭제 n 번을 순차로 하면 `n + n = 2n` 이고 여전히 O(n) 이다.
  다만 실측에서는 상수배가 그대로 시간에 나타난다 — 이론과 측정을 구분해야 한다.

- Q: `n번 x O(n)` 은 왜 O(n^2) 인가?
  A: 이것은 상수배가 아니라 **n 에 비례하는 일을 n 번** 하는 것이기 때문이다.
  n 이 2배가 되면 반복 횟수도 2배, 1회 비용도 2배 → 총비용은 4배가 된다.
  증가율 자체가 제곱이므로 항이 `n^2` 로 커진다.
  상수배는 버려도 되지만 n 배는 버릴 수 없다.

- Q: m x k 로 계산되는 비용을 왜 O(n^2) 이라고 부르는가?
  A: m 과 k 가 독립 변수가 아니라 같은 n 에 묶여 있기 때문이다.
  문제 1의 접근 2에서 m 은 지운 개수, k 는 지울 때 뒤에 남은 개수이고 `m + k <= n` 이다.
  이 제약 아래 `m x k` 의 최댓값은 `m = k = n/2` 일 때 `n^2/4` 다(합이 고정이면 곱은 두 값이 같을 때 최대).
  복잡도는 최악 기준이므로 `n^2/4` → 상수배를 버려 **O(n^2)** 이다.

- Q: 이 문제집에서 그 차이가 실제 시간으로 드러나는 곳은 어디인가?
  A: 문제 4의 테스트 `mustBeLinear` — 100만 건, 5초 제한이다.
  `remove(i)` 반복 구현은 계산상 약 `2.5 x 10^11` 회 복사라 제한 안에 못 끝낸다.
  두 포인터 구현은 약 `3 x 10^6` 회 연산이라 즉시 끝난다.
  둘 다 루프는 100만 번 도는데 결과가 갈린다 — **"정답은 나오는데 통과 못 하는" 구현**이 존재한다는 것을 손으로 겪게 하는 장치다.

- Q: 더해지는 비용(순차 실행)과 곱해지는 비용(루프 안)은 어떻게 구분하는가?
  A: 코드에서 두 블록이 **나란히** 있으면 더해지고, 하나가 다른 하나 **안에** 있으면 곱해진다.
  더해질 때는 큰 항이 지배한다 — 문제 3의 `O(log n) + O(n) = O(n)`.
  곱해질 때는 항의 차수가 올라간다 — 문제 4의 `n x O(n) = O(n^2)`.
  그래서 최적화할 자리를 찾을 때는 "가장 깊이 중첩된 곳에서 부르는 연산의 비용"부터 본다. 문제 3에서 이진 탐색이 전체 차수를 못 바꾼 이유(더해지는 자리)와 문제 4에서 `remove` 가 전체를 무너뜨린 이유(곱해지는 자리)가 같은 원리의 앞뒤다.

**더 생각할 것**

- 라이브러리 메서드는 이름만으로 비용을 알 수 없다. `list.contains()` 는 O(n), `set.contains()` 는 O(1) 인데 호출 코드는 똑같이 생겼다 — 루프 안에서 이 차이가 O(n) 과 O(n^2) 을 가른다.
- 차수가 같아도 상수는 다르다. 규모가 커지면 차수를 먼저 고치고, 차수가 맞은 뒤에는 상수(캐시 지역성·박싱·할당)를 본다.
- 분산·외부 저장소로 가면 "루프 1회의 비용"이 네트워크 왕복이 된다. n 번 도는 루프 안의 쿼리 한 번이 N+1 문제이고, 원리는 여기 `remove` 함정과 정확히 같다.
