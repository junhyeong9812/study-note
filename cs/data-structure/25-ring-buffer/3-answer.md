# data-structure/25-ring-buffer — 정답

## 정답

### 1. 고정 크기를 고르는 이유와 대가

- 크기 제한 없는 큐는 생산이 몰리는 동안 계속 커진다. 소비가 평균적으로 못 따라가면 메모리 고갈(OOM)로 끝난다.
- 링 버퍼는 배열 하나를 되감아 쓰므로 메모리가 고정되고, 새 할당이 없다.
- 대가: **가득 찼을 때의 정책**을 정해야 한다 — 거부(새것 버림), 덮어쓰기(옛것 버림), 블로킹(생산자 대기), 타임아웃. 그리고 버린 수·기다린 시간을 지표로 내보내야 한다.

### 2. 빈 것과 가득 찬 것

```text
  빈 링                    가득 찬 링
  [  ][  ][  ][  ]         [ A ][ B ][ C ][ D ]
   ^head=tail               ^head=tail
```

- 둘 다 `head == tail`이다. tail이 한 바퀴 돌아 head를 따라잡은 것과 아무것도 없는 것이 같은 모양이다.
- 해결법
  - 한 칸 비우기: `(tail+1)%N == head`면 가득 참. 실제 용량 N-1(리눅스 circ_buf 문서 방식).
  - 개수 세기: `size` 필드. 용량 N(`ArrayBlockingQueue`의 `count`).
  - 단조 증가 시퀀스: 위치를 되감지 않고 `long`으로 올린다. `tail - head == N`이면 가득 참. 용량 N, 칸은 `seq & (N-1)`.
- 실험(`RingFull.java`): 칸 4개에서 한 칸 비우기는 `offer 성공=3`, 개수 세기는 `offer 성공=4`.

### 3. 순진한 링

- 1..4를 넣으면 tail이 4 → 0으로 되감겨 `head=0 tail=0`이 된다. `isEmpty()=true`, `poll()=null`. 넣은 4개가 보이지 않는다.
- 1..6을 넣으면 5·6이 0·1번 칸(1·2)을 덮고 tail=2. 3·4는 배열에 남지만 head=0~tail=2 밖이라 꺼내면 `[5, 6]`만 나온다(실험 출력 `6개 넣은 뒤 poll 전부=[5, 6]`).
- 예외는 어디에도 없다. 정책을 정하지 않은 링이 "우연히 덮어쓰기"를 한 셈이다.

### 4. 마스크와 넘침

- `seq & (N-1) == seq % N`은 N이 2의 거듭제곱이고 seq가 0 이상일 때 성립한다. 아래 비트만 남기는 것이 2^k로 나눈 나머지이기 때문이다.
- N=6, 마스크 5(`0b101`): 실험 출력 `[16, 16, 0, 0, 14, 14]`. 2·3번 칸은 쓰이지 않고, 나머지 칸이 겹쳐 쓰인다(`%`이면 칸마다 10).
- `int` 넘침(실험 출력)
  - `seq & 7`: 7 → 0 → 1로 이어진다. 2의 보수에서 아래 비트는 넘쳐도 연속이다. `tail - head`도 3으로 맞았다.
  - `seq % 6`: 1 → -2 → -1. Java `%`는 피제수 부호를 따르므로 음수 인덱스가 나오고 `Index -1 out of bounds for length 6`.
- 그래서 시퀀스는 `long`, 크기는 2의 거듭제곱으로 하고 생성자에서 검사한다.

### 5. `ArrayBlockingQueue` 네 응답

- 실험(`AbqPolicy.java`, OpenJDK 21.0.12) 출력
  - `add(3)` → `java.lang.IllegalStateException: Queue full`
  - `offer(3)` → `false`(즉시)
  - `offer(3, 200ms)` → `false`, 200 ms 기다린 뒤
  - `put(3)` → 스레드가 멈춘다. 300 ms 뒤 상태 `WAITING`. 소비자가 `take()`로 1을 꺼내자 끝났다.
- 스레드 덤프(`jstack`·`jcmd <pid> Thread.print`)에서는 `WAITING` 상태, 스택에 `AbstractQueuedSynchronizer$ConditionObject.await` 아래 `ArrayBlockingQueue.put`이 있는 스레드로 알아본다.

### 6. SPSC와 다중 생산자

- SPSC에서는 `tail`을 생산자만, `head`를 소비자만 쓴다. 같은 변수를 두 스레드가 쓰지 않으므로 CAS·락이 필요 없다.
- 필요한 것은 순서다. 생산자는 칸에 값을 쓴 **뒤** tail을 release로 올리고, 소비자는 tail을 acquire로 읽은 뒤 칸을 읽는다. 그래야 소비자가 덜 쓰인 칸을 읽지 않는다.
- 생산자가 둘이면 같은 `tail` 값을 읽고 같은 칸에 쓴 뒤 같은 값으로 tail을 올릴 수 있다. 한쪽 값이 덮인다.
- 실험(`RingBugs.java`): 200만 개 중 소비 97만~114만 개(집필 3회 + 사실 점검 3회). 예외는 없었고, 끝난 뒤 `head == tail`이라 겉보기는 정상이었다.

### 7. 처리량 비교

- 실험(`SpscBench.java`, `--cpus=2`, 4라운드 × 2회) 범위: `long` 링 512~909 ms < `Long` 링 1205~2271 ms < `ArrayBlockingQueue<Long>` 7025~8191 ms.
- 조심할 점
  - 환경 한정: CPU 2개 제한 컨테이너, 이 크기(1000만 개, 용량 1024)에서만의 값이다.
  - 섞인 요인: 박싱(`long` vs `Long`)을 떼어 보려고 `Long` 링을 같이 쟀다. 그래도 바쁜 대기(락 없는 링은 CPU를 태우며 기다린다) vs 잠들기(조건 변수)의 차이가 남는다.
  - 측정 잡음: 1라운드는 JIT 워밍업이 섞였고 라운드마다 수백 ms 흔들렸다. 범위로 말하고, 운영 판단은 실제 부하에서 프로파일로 한다.

### 8. 블로킹 전파

- 원인 후보: 요청 스레드가 로그를 넣는 비동기 버퍼가 가득 찼고, 정책이 블로킹이다. 디스크가 느려져 소비(파일 쓰기)가 늦어지자 버퍼가 차고, 생산자인 요청 스레드가 `put`에서 멈췄다. CPU를 쓰지 않고 기다리므로 CPU는 낮다.
- Logback `AsyncAppender` 기본값(매뉴얼): `queueSize` 256, `neverBlock=false`(가득 차면 막는다), `discardingThreshold`는 남은 칸이 20% 이하일 때 TRACE·DEBUG·INFO를 버리고 WARN·ERROR만 넣는다. 즉 WARN·ERROR가 몰리면 블로킹된다.
- 대처: 요청 경로 로그는 `neverBlock=true` + 드롭 지표, 또는 타임아웃 정책을 검토한다. 잃으면 안 되는 로그(감사 등)는 블로킹을 유지하되 요청 경로와 분리한다. 스레드 덤프의 `put` 스택으로 확인한다.

### 9. 사라지는 패킷

- 보는 곳: `ip -s link`·`/proc/net/dev`의 drop 칸, `ethtool -S <dev>`의 드라이버별 드롭 카운터, `ethtool -g <dev>`로 현재·최대 링 크기. 앱에서는 주로 TCP 재전송으로 인한 지연이 보이고, 드롭이 계속되면 연결 시간 초과까지 간다(RFC 9293 §3.8.3).
- 수신 링이 차서 NIC가 새 패킷을 버리는 것은 "거부" 정책이다. 예외는 앱까지 오지 않는다.
- 링을 키우면(`ethtool -G`) 짧은 몰림은 흡수한다. 하지만 수신 처리(softirq·한 CPU에 몰린 처리)가 평균적으로 도착 속도를 못 따라가면 큰 링도 결국 찬다. 그때는 수신 처리 분산(RSS·RPS)이나 처리 비용 자체를 줄여야 한다([network/25](../../network/25-kernel-network-stack/2-summary.md)).
