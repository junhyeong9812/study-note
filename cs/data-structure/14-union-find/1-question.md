# data-structure/14-union-find — 질문

## 질문

1. 유니온 파인드는 왜 필요한가 — 08번 그래프의 BFS/DFS 로 "이 둘이 연결돼 있나"에 답할 때 무엇이 문제인가. 간선이 하나씩 들어오는 상황이 왜 결정적인가.
2. 이 구조가 포기한 것 둘은 무엇인가(경로를 모른다 · 쪼갤 수 없다). 경로 압축이 왜 "쪼갤 수 없음"의 원인이 되는가 — 조회가 자료구조를 바꾼다는 성질을 10번 LRU 의 get, 13번 lazy 의 rangeSum 과 함께 설명해 보라.
3. 두 최적화(크기로 붙이기 · 경로 압축)가 각각 무엇을 보장하는가. "깊이가 1 늘어나려면 나무 크기가 두 배가 돼야 한다"가 왜 log n 상한을 주는가. 둘을 합쳤을 때 α(n) 이 사실상 상수인 이유는.
4. 최악의 사용 패턴을 만들어 보라 — 두 최적화를 모두 끄고 0-1, 0-2, 0-3 … 순으로 합치면 깊이와 총 비용이 어떻게 되는가. 크기만 켰을 때, 둘 다 켰을 때는. 반대로 최선의 경우는 언제인가.
5. `sizeOf` 를 `treeSize[x]` 로 그냥 주면 왜 틀리는가 — 자식들의 treeSize 를 갱신하지 않는 결정은 무엇과 무엇을 맞바꾼 것인가. `groups()` 가 O(n) 인 것은 결함인가 설계인가.
6. 구현 전략의 트레이드오프 — 배열판과 맵판의 거래(05번·09번에서 본 그것)는 무엇인가. `DisjointSet<T>` 는 왜 상속이 아니라 포함 + 번호 매핑으로 임의 타입을 지원하는가.
7. `WeightedUnionFind` 에서 `weight[x]` 를 "x 의 값 - 부모의 값"으로 두면 왜 뿌리의 값을 끝까지 몰라도 되는가. find 에서 순서를 틀리면(재귀 호출 전에 더하면) 왜 작은 예제에서는 안 걸리고 조용히 틀리는가. 크기로 붙이기 때문에 union 에서 부호를 두 경우 다 써야 하는 이유는.
8. 다음 구조로의 연결 — 여기까지는 전부 메모리 안의 구조였다. 15번 B-트리가 "한 번 읽는 비용이 비싸다"는 전제를 깔면 06번 BST 의 자식 둘이 왜 수백 개로 바뀌는가.
