### A. 문제

#### 1. 조건에 맞는 원소를 모두 제거 (`removeAllIf`)

문제는 `predicate` 가 참인 원소를 전부 없애고 제거한 개수를 돌려주는 것이다.\
제약은 **O(n)** 이고, 테스트 `mustBeLinear` 가 10만 건 / 5초로 그것을 강제한다.

> **조건 함수(predicate)** — 원소 하나를 받아 "이걸 지울까?"를 참/거짓으로 돌려주는 함수.\
> 예: `v -> v % 2 == 0` 을 넘기면 짝수만 지우라는 뜻이 된다.

> **반복자(Iterator)** — 지금 어디까지 읽었는지를 스스로 기억한 채 "다음 것 주세요(`next()`)"만 반복하는 책갈피 객체.\
> 예: 인덱스로 매번 처음부터 세지 않고 서 있던 자리에서 이어 걷기 때문에 n번 순회가 O(n)으로 끝난다.

**접근 1 — 인덱스로 뒤에서부터 `remove(i)`** (01번에서 통했던 풀이. 여기서는 시간 초과다)

```java
// 의사코드
int removed = 0;
for (int i = list.size() - 1; i >= 0; i--) {
    if (predicate.test(list.get(i))) {
        list.remove(i);
        removed++;
    }
}
return removed;
```

```
list = [1,2,3,4,5,6], 조건 = 짝수. i 가 5 에서 0 까지 내려온다

head -> [1|o]-> [2|o]-> [3|o]-> [4|o]-> [5|o]-> [6|/]  <- tail
 idx      0       1       2       3       4       5

 i=5 : get(5)    -> head 에서 5 걸음 걸어야 6 을 본다
       6 은 짝수 -> remove(5) = removeLast() -> tail 의 "앞" 노드를 찾으러 또 4 걸음
 i=4 : get(4)    -> head 에서 4 걸음
       5 는 홀수 -> 통과
 i=3 : get(3)    -> head 에서 3 걸음
       4 는 짝수 -> remove(3) -> node(2) 찾으러 또 2 걸음
 i=2 : get(2)    -> head 에서 2 걸음, 통과
 i=1 : get(1)    -> head 에서 1 걸음, 2 는 짝수 -> remove(1) -> node(0) 찾으러 0 걸음
 i=0 : get(0)    -> 0 걸음, 통과

 get 만 세도 걸음 합계 = 5 + 4 + 3 + 2 + 1 + 0 = 15
 일반화             = n(n-1)/2  ->  O(n^2)
 remove 안의 탐색까지 더하면 계수만 커지고 차수는 그대로다

 01번(동적 배열)과의 대비
   배열   : get(i) 는 주소 계산 한 번이라 0 걸음. 느린 곳은 remove 의 "시프트".
   리스트 : remove 에 시프트가 아예 없다. 느린 곳은 get/remove 의 "탐색".
   증상(O(n^2))은 같은데 원인이 정반대편에 있다.
```

- 논리: 뒤에서부터 도는 이유는 01번과 같다 — 지우면 뒤 인덱스가 당겨지므로 아직 안 본 앞쪽을 보호하려는 것이다.
- 논리: 답 자체는 맞다.\
  `removesMatching` 같은 정확성 테스트는 전부 통과한다.
- 비용(왜): 연결 리스트에는 `elements[i]` 가 없다.\
  `get(i)` 는 `node(index)` 를 부르고, 그건 `head` 에서 `next` 를 `index` 번 따라가는 루프다.
- 비용(왜): 그래서 루프 한 바퀴마다 O(n) 짜리 탐색이 들어가고 전체가 `n(n-1)/2` → **O(n^2)** 이 된다.
- 비용(왜): `remove(i)` 도 마찬가지다.\
  `SinglyLinkedList.remove(index)` 는 `node(index - 1)` 을 걷고, 하필 맨 뒤면 `removeLast()` 라 또 `head` 부터 다시 센다.
- 한계: n = 100,000 이면 `get` 의 걸음만 계산상 약 `5 x 10^9` 회다.\
  테스트 `mustBeLinear` 의 5초 제한을 못 넘긴다.
- 한계: 테스트 실패 메시지가 원인을 그대로 적어 두었다 — `"get(i) 나 remove(i) 로 훑으면 탐색이 매번 O(n) 이라 여기서 막힌다."`
- 한계: 이중 연결이면 `node(index)` 가 가까운 끝에서 출발해 걸음이 절반이 되지만, `n^2/4` 라 차수는 그대로다.

> **탐색(traversal) vs 시프트(shift)** — 탐색은 "그 자리까지 걸어가는" 비용이고, 시프트는 "뒤에 있는 것들을 밀거나 당기는" 비용.\
> 예: 배열의 `remove` 는 탐색이 0이고 시프트가 O(n), 연결 리스트의 `remove(i)` 는 시프트가 0이고 탐색이 O(n)이다.

**접근 2 — 살릴 것만 새 리스트에 모았다가 `clear()` 후 다시 넣기** (O(n)은 되지만 공간을 O(n) 낸다)

```java
// 의사코드
List<E> keep = new DoublyLinkedList<>();
int removed = 0;
for (E e : list) {
    if (predicate.test(e)) removed++;
    else keep.add(e);
}
list.clear();
for (E e : keep) list.add(e);
return removed;
```

```
list = [1,2,3,4], 조건 = 짝수

 1단계 : 한 번 훑으며 살릴 것만 새 사슬에 쌓는다 (add 는 tail 이 있어 O(1))
   원본  head -> [1|o]-> [2|o]-> [3|o]-> [4|/]
                  살림    버림    살림    버림
   keep  head -> [1|o]-> [3|/]

 2단계 : 원본을 비운다  list.clear()
   원본  head -> null      (노드 사슬을 전부 끊는다 — 11번 참고)

 3단계 : keep 을 다시 원본에 붙인다
   원본  head -> [1|o]-> [3|/]  <- tail

 걸음 합계 = 훑기 n + 비우기 n + 다시 넣기 (n - removed)  ->  O(n)
 그런데 한때 노드가 2n 개 살아 있다 (원본 사슬 + keep 사슬)
```

- 논리: 인덱스를 한 번도 안 쓰므로 탐색이 사라진다 — 그래서 시간은 O(n) 으로 내려온다.
- 논리: `for (E e : list)` 는 `Iterable` 을 통해 `iterator()` 를 부르는 문법이라 이미 반복자를 쓰고 있는 셈이다.
- 비용(왜): 살릴 원소 수만큼 **노드를 새로 만든다**.\
  원소 하나를 살리는 데 객체 하나를 새로 할당하고 옛 노드는 버린다.
- 비용(왜): 추가 공간 O(n) 이고, 3단계 직전에는 옛 사슬과 새 사슬이 동시에 살아 있다.
- 한계: 연결 리스트로 이걸 하는 것은 자해에 가깝다.\
  링크만 고치면 될 일을 노드 재할당으로 바꿔 놓았다.
- 한계: 호출자가 특정 노드를 참조로 들고 있었다면(예: LRU 캐시의 노드 핸들) 전부 무효가 된다.
- 한계: `new DoublyLinkedList<>()` 를 안에 적는 순간 이 함수가 한 구현에 묶인다 — 문제 3이 `result` 를 인자로 받는 이유와 같은 문제다.

**접근 3 — `Iterator.remove()` 로 훑으면서 그 자리에서 지우기** (impl 의 정답)

```java
public static <E> int removeAllIf(List<E> list, Predicate<? super E> predicate) {
    int removed = 0;
    Iterator<E> it = list.iterator();
    while (it.hasNext()) {
        if (predicate.test(it.next())) {
            it.remove();
            removed++;
        }
    }
    return removed;
}
```

핵심은 `it.remove()` 가 **"방금 돌려준 노드"를 이미 손에 쥐고 있다**는 것이다.\
다시 찾을 필요가 없으니 탐색이 0이다.\
단일 연결에서는 그 노드의 **앞** 노드까지 따로 들고 있어야 지울 수 있다.

```java
// SinglyLinkedList.iterator() — 상태 네 개를 들고 있다
private Node<E> next = head;
private Node<E> prev = null;              // next 의 앞 노드
private Node<E> lastReturned = null;
private Node<E> beforeLastReturned = null;
```

```java
// SinglyLinkedList 의 iterator().remove()
public void remove() {
    if (lastReturned == null) {
        throw new IllegalStateException("next() 를 먼저 부르거나, 이미 지웠다");
    }
    if (beforeLastReturned == null) {
        head = lastReturned.next;
    } else {
        beforeLastReturned.next = lastReturned.next;
    }
    if (lastReturned == tail) {
        tail = beforeLastReturned;
    }
    lastReturned.next = null;
    lastReturned.item = null;
    bumpSize(-1);
    prev = beforeLastReturned;            // 한 칸 지웠으니 앞이 당겨진다
    lastReturned = null;
}
```

```
removeAllIf([1,2,3,4], v -> v % 2 == 0)  —  SinglyLinkedList 의 반복자로 추적

before  head -> [1|o]-> [2|o]-> [3|o]-> [4|/]  <- tail
        next = [1]   prev = null   lastReturned = null   beforeLastReturned = null

next() 1회 : 1 을 돌려준다. 홀수라 통과
        head -> [1|o]-> [2|o]-> [3|o]-> [4|/]
                 ^last   ^next
        beforeLastReturned = null,  prev = [1]

next() 2회 : 2 를 돌려준다. 짝수 -> remove()
        head -> [1|o]-> [2|o]-> [3|o]-> [4|/]
                 ^b      ^last   ^next
        b = beforeLastReturned = [1]      <- "방금 돌려준 노드의 앞"을 미리 잡아 뒀다
                                             이 변수가 없으면 [1] 을 찾으러 head 부터 다시 걸어야 한다

step1 : b.next = lastReturned.next        (앞 노드가 [2] 를 건너뛰게 만든다)
        head -> [1|o]-----------> [3|o]-> [4|/]
                       [2|o]------^                [2] 는 아직 [3] 을 가리키고 있다

step2 : lastReturned == tail 인가?  아니다 -> tail 그대로
        (맞았다면 tail = b 로 내려야 한다. 이걸 빼먹는 것이 여기서 제일 잘 나는 실수다)

step3 : lastReturned.next = null,  lastReturned.item = null   (떼어낸 노드의 링크를 끊는다)
        head -> [1|o]-----------> [3|o]-> [4|/]
                       [ |/]                        아무도 안 가리키고 아무것도 안 가리킨다 -> GC 대상

step4 : prev = b,  lastReturned = null
        지운 칸만큼 "현재 위치의 앞"이 한 칸 당겨진다
        lastReturned 를 null 로 되돌려야 remove() 를 연속 두 번 부르는 것이 막힌다

after (4 까지 같은 식으로 처리)
        head -> [1|o]-> [3|/]  <- tail      -> removed = 2

 걸음 합계 = 노드 하나를 딱 한 번씩 지나간다 = n  ->  O(n)
 추가 공간 = 반복자가 들고 있는 참조 네 개  ->  O(1)
```

- 논리: 반복자는 "어디까지 읽었는지"를 상태로 들고 있다.\
  그래서 다음 원소로 가는 데 걸음이 **1** 이다.
- 논리: `it.remove()` 는 `lastReturned` 를 이미 참조로 쥐고 있으므로 지울 노드를 **찾지 않는다**.
- 논리: 단일 연결이라 앞 노드로 되돌아갈 수 없으니 `beforeLastReturned` 를 따로 들고 다닌다.\
  이중 연결에서는 `lastReturned.prev` 로 바로 알 수 있어 이 변수 자체가 없다.
- 논리: 지운 노드가 `tail` 이었으면 `tail` 을 내려야 한다.\
  테스트 `removesEnds` 가 삭제 후 `list.add(9)` 를 해서 이 갱신을 확인한다.
- 비용(왜): 순회 n 번 x (다음으로 이동 O(1) + 판정 O(1) + 삭제 O(1)) = **O(n)**.
- 비용(왜): 추가 공간은 참조 몇 개뿐 → **O(1)**.
- 한계: 이 반복자는 `ConcurrentModificationException` 을 던지지 않는다.\
  순회 중에 `list.add(...)` 로 리스트를 직접 건드리면 반복자의 `next`·`prev` 가 조용히 어긋난다.
- 한계: `remove()` 는 `next()` 직후에만 유효하다.\
  `next()` 없이 부르거나 연속 두 번 부르면 `IllegalStateException` 이고, 테스트 `rejectsIllegalRemove` 가 둘 다 검사한다.
- 한계: 리스트가 아니라 `Iterable` 인 다른 소스(파일 스트림 등)는 `remove()` 를 지원하지 않는 경우가 많다.

> **구조적 변경(structural modification)** — 원소를 넣거나 빼서 리스트의 노드 개수를 바꾸는 일.\
> 예: 순회 중 구조적 변경을 반복자 밖에서 하면 반복자가 들고 있던 노드 참조가 사슬에서 떨어져 나가 엉뚱한 곳을 가리킨다.

> **상태 검사(state check)** — 메서드를 부를 수 있는 시점인지를 객체 스스로 확인하는 것.\
> 예: `lastReturned == null` 이면 아직 `next()` 를 안 불렀거나 이미 지운 것이므로 `IllegalStateException` 을 던진다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 인덱스로 뒤에서부터 remove | O(n^2) | O(1) | n 이 아주 작고 코드를 빨리 쓸 때 | n 이 수만 이상일 때 · 시간 제한이 있을 때 |
| 2. 살릴 것만 새 리스트에 모으기 | O(n) | O(n) | 원본을 보존해야 할 때 · 필터 결과를 따로 쓸 때 | 메모리가 빠듯할 때 · 노드 참조를 밖에서 들고 있을 때 |
| 3. Iterator.remove() | O(n) | O(1) | 기본값. 제자리 조건부 삭제 | 소스가 remove 를 지원하지 않을 때 · 동시 수정이 있을 때 |

**데이터 규모가 커지면**

- n = 1,000 이면 접근 1도 계산상 약 50만 걸음이라 체감되지 않는다.\
  그래서 작은 테스트만 돌리면 이 함정이 안 보인다.
- n = 100,000 이면 `get` 의 걸음만 계산상 약 `5 x 10^9` 회다.\
  테스트 `mustBeLinear` 의 5초 제한이 여기서 끊는다.
- 같은 n 에서 접근 3은 약 `10^5` 걸음으로 끝난다.\
  네 자리 수 이상의 차이다.
- 걸음 수가 같아도 연결 리스트는 배열보다 한 걸음이 비싸다 — 노드가 메모리에 흩어져 있어 매 걸음이 캐시 미스가 되기 쉽다.

> **포인터 추격(pointer chasing)** — 다음 데이터의 주소를 읽어야 비로소 다음으로 갈 수 있어서, CPU 가 미리 가져오지 못하고 매번 기다리는 접근 패턴.\
> 예: `n = n.next` 는 `n` 을 읽기 전에는 다음 주소를 모르므로 캐시 프리페치가 듣지 않는다.

- 원소가 수천만 개면 노드 오버헤드 자체가 문제가 된다.\
  값 하나에 객체 헤더 + 참조가 따라붙어 배열 대비 몇 배의 메모리를 쓴다(원본에 근거 없음 — 내 추론).
- 실무에서는 이 규모에서 "리스트에서 조건부 삭제"라는 연산 자체를 없앤다.\
  삭제 대신 **묘비(tombstone) 플래그**를 세워 두고 나중에 통째로 압축하거나, 애초에 인덱스 구조(해시·트리)를 얹어 지울 대상을 O(1)로 찾는다.

**질문별 답**

- Q: 문제 1(조건에 맞는 원소를 모두 제거 — `removeAllIf`)을 어떻게 푸는가.\
  A: `list.iterator()` 로 한 번 훑으면서, 조건이 참인 원소를 만나면 그 자리에서 `it.remove()` 를 부른다.\
  `it.remove()` 는 방금 `next()` 가 돌려준 노드를 이미 참조로 쥐고 있어 다시 찾지 않는다.\
  지운 횟수를 세어 반환한다.\
  인덱스를 한 번도 쓰지 않는 것이 이 풀이의 전부다.

- Q: 인덱스로 도는 풀이가 왜 O(n²)이 되는가.\
  A: 루프가 n 번 도는 것이 문제가 아니라, 루프 **안**의 `get(i)` 와 `remove(i)` 가 각각 O(n) 이기 때문이다.\
  연결 리스트에는 `elements[i]` 같은 바로가기가 없어서 `node(index)` 가 `head` 에서 `next` 를 `index` 번 따라간다.\
  걸음 합계는 `n(n-1)/2` → O(n²).\
  01번 배열에서도 O(n²)였지만 그때 원인은 `remove` 의 시프트였고, 여기서는 **탐색**이다 — 증상이 같고 원인이 정반대다.

- Q: O(n)으로 만드는 풀이는 무엇에 기대는가.\
  A: 반복자가 **위치를 상태로 기억한다**는 성질에 기댄다.\
  `next()` 는 서 있던 노드에서 한 걸음만 가므로 O(1) 이고, n 번 모아도 O(n) 이다.\
  `remove()` 는 `lastReturned`(그리고 단일 연결이면 `beforeLastReturned`)를 이미 들고 있어서 지울 자리를 **찾지 않고** 링크만 고친다.\
  즉 여기서 `Iterator` 는 for-each 를 예쁘게 쓰려는 문법 설탕이 아니라 **복잡도를 O(n²)에서 O(n)으로 바꾸는 장치**다.

- Q: 그 풀이가 조용히 깨지는 지점은 어디인가.\
  A: `tail` 갱신이다.\
  마지막 원소를 순회 중에 지우고 `tail` 을 그대로 두면, 앞에서 읽을 때는 결과가 멀쩡해 보이지만 다음 `add` 가 버려진 노드 뒤에 붙는다.\
  테스트 `removesEnds` 와 `removesAtBothEnds` 가 삭제 후 `add(9)` 를 해서 이것을 잡는다.\
  이중 연결이면 `unlink` 하나가 `head`/`tail` 갱신과 링크 끊기를 전부 처리하므로 이 실수가 덜 난다.

#### 2. 가운데 값 찾기 (`findMiddle`)

문제는 가운데 원소를 돌려주는 것이다.\
짝수 개면 뒤쪽을 고른다 — `[1,2,3]` → `2`, `[1,2,3,4]` → `3`.\
제약이 둘이다: **`size()` 를 쓰지 말 것**, **리스트를 한 번만 훑을 것**.

**접근 1 — `size()` 로 길이를 알아내고 `get(size / 2)`** (가장 먼저 떠오르지만 조건을 정면으로 어긴다)

```java
// 의사코드
if (list.size() == 0) throw new NoSuchElementException("비어 있다");
return list.get(list.size() / 2);
```

```
list = [1,2,3,4],  size() = 4  ->  get(4 / 2) = get(2) = 3

head -> [1|o]-> [2|o]-> [3|o]-> [4|/]
 idx      0       1       2       3
                          ^ 여기 -> 3   (짝수면 뒤쪽이라는 규칙과 우연히 맞다)

 size() 가 O(1) 인 것은 이 구현이 size 필드를 따로 세고 있기 때문이다.
 길이를 알 수 없는 소스(스트림)에서는 이 전제가 통째로 사라진다.
```

- 논리: 길이를 알면 가운데 인덱스는 `size / 2` 로 바로 나온다.
- 논리: 짝수일 때 `size / 2` 가 뒤쪽을 고르는 것도 규칙과 맞는다 — size 4면 인덱스 2다.
- 비용(왜): `size()` 는 필드 하나 읽기라 O(1), `get(size/2)` 는 절반까지 걷기라 O(n).\
  합쳐서 시간 O(n) 이므로 **속도만 보면 문제가 없다**.
- 한계: 문제가 `size()` 를 금지했다.\
  금지한 이유는 속도가 아니라 **적용 범위**다.
- 한계: 길이를 미리 모르는 소스에서는 아예 성립하지 않는다.\
  네트워크로 흘러오는 로그처럼 끝까지 읽어봐야 길이를 아는 데이터가 그렇다.
- 한계: `size()` 를 안 쓰고 직접 세더라도, 세느라 한 번 + 가서 읽느라 한 번 = **두 번 훑기**라 "한 번만"이라는 조건에 걸린다.

> **스트림(stream)** — 길이를 미리 알 수 없고 흘러오는 대로 한 번만 읽을 수 있는 데이터 흐름.\
> 예: 소켓으로 들어오는 로그는 되감아 다시 읽을 수 없으니 `size()` 를 물어볼 상대가 없다.

> **단일 패스(single pass)** — 데이터를 처음부터 끝까지 딱 한 번만 지나가며 답을 내는 것.\
> 예: 길이를 세려고 한 번 돌고 값을 읽으려고 또 한 번 도는 것은 두 번 패스라 이 조건을 어긴다.

**접근 2 — 훑으면서 전부 임시 배열에 담고 가운데를 꺼내기** (한 번만 훑는 건 맞는데 공간을 O(n) 낸다)

```java
// 의사코드
java.util.ArrayList<E> buf = new java.util.ArrayList<>();
for (E e : list) buf.add(e);
if (buf.isEmpty()) throw new NoSuchElementException("비어 있다");
return buf.get(buf.size() / 2);
```

```
list = [1,2,3,4,5]

 한 번 훑으며 버퍼에 복사
   head -> [1|o]-> [2|o]-> [3|o]-> [4|o]-> [5|/]
             |       |       |       |       |
             v       v       v       v       v
   buf    [  1  ][  2  ][  3  ][  4  ][  5  ]     <- n 칸을 새로 쓴다
                          ^ buf.get(5/2) = buf.get(2) = 3

 훑기는 한 번이 맞다. 대신 원소 전부를 손에 들고 있어야 한다 -> 추가 공간 O(n)
```

- 논리: `size()` 도 안 쓰고 순회도 한 번이라 조건의 글자는 지킨다.
- 논리: 길이를 모르는 소스에도 적용된다 — 끝까지 다 받아 두면 되니까.
- 비용(왜): 시간 O(n), **추가 공간 O(n)**.
- 한계: 이 기법을 배우려는 목적을 놓친다.\
  원래 노림수는 "다 들고 있지 않고도" 가운데를 아는 것이다.
- 한계: 데이터가 메모리보다 크면 쓸 수 없다.\
  100GB 로그의 가운데 줄을 찾는 상황이 바로 그렇다.

**접근 3 — 반복자 두 개를 한 칸/두 칸씩 굴리기** (impl 의 정답)

> **토끼와 거북이(fast/slow, tortoise-hare)** — 한 칸씩 가는 느린 주자와 두 칸씩 가는 빠른 주자를 같이 출발시키는 기법.\
> 예: 빠른 쪽이 끝에 닿았을 때 느린 쪽은 정확히 절반 지점에 있다 — 길이를 세지 않고 한 번의 순회로 가운데를 찾는다.

```java
public static <E> E findMiddle(List<E> list) {
    Iterator<E> slow = list.iterator();
    Iterator<E> fast = list.iterator();
    if (!slow.hasNext()) {
        throw new NoSuchElementException("비어 있다");
    }
    E middle = slow.next();
    while (fast.hasNext()) {
        fast.next();
        if (!fast.hasNext()) {
            break;
        }
        fast.next();
        middle = slow.next();
    }
    return middle;
}
```

```
[1,2,3,4,5] (홀수 5개) — s = slow 가 방금 돌려받은 자리, f = fast 가 방금 돌려받은 자리

시작    head -> [1|o]-> [2|o]-> [3|o]-> [4|o]-> [5|/]
        middle = slow.next() = 1
                 ^s                                        f 는 아직 출발 전

1바퀴   fast.next()=1, hasNext 참 -> fast.next()=2, middle = slow.next() = 2
        head -> [1|o]-> [2|o]-> [3|o]-> [4|o]-> [5|/]
                         ^s,f                           f 가 s 보다 1 칸 앞

2바퀴   fast.next()=3, hasNext 참 -> fast.next()=4, middle = slow.next() = 3
        head -> [1|o]-> [2|o]-> [3|o]-> [4|o]-> [5|/]
                                 ^s      ^f             f 가 s 보다 1 칸 앞... 이 아니라
                                                        s 가 2칸, f 가 4칸 갔다 (항상 2배)

3바퀴   fast.hasNext() 참 -> fast.next()=5, hasNext 거짓 -> break
        head -> [1|o]-> [2|o]-> [3|o]-> [4|o]-> [5|/]
                                 ^s              ^f

return middle = 3     <- 5개의 가운데. 맞다

  불변식 : slow 가 k 칸 갔으면 fast 는 2k 칸 갔다.
           fast 가 끝(n)에 닿는 순간 slow 는 n/2 에 있다.
```

```
[1,2,3,4] (짝수 4개) — 짝수면 왜 "뒤쪽"이 나오는지

시작    head -> [1|o]-> [2|o]-> [3|o]-> [4|/]
        middle = slow.next() = 1
                 ^s

1바퀴   fast.next()=1, hasNext 참 -> fast.next()=2, middle = slow.next() = 2
        head -> [1|o]-> [2|o]-> [3|o]-> [4|/]
                         ^s,f

2바퀴   fast.next()=3, hasNext 참 -> fast.next()=4, middle = slow.next() = 3
        head -> [1|o]-> [2|o]-> [3|o]-> [4|/]
                                 ^s      ^f

3바퀴   fast.hasNext() 거짓 -> while 종료

return middle = 3     <- [1,2,3,4] 의 "뒤쪽 가운데". 테스트가 요구하는 값

  왜 뒤쪽인가 : middle = slow.next() 가 fast 를 두 칸 전진시킨 "뒤에" 실행된다.
               두 칸 전진이 성공할 때만 slow 를 한 칸 올린다는 뜻이다.
               그래서 4개일 때 slow 가 2번(1->2->3) 올라가 3에서 멈춘다.
               순서를 바꿔 slow 를 먼저 올리면 2가 나온다 — 짝수 규칙이 뒤집힌다.
```

```
경계 [9] (1개) 와 [] (0개)

[9]  : slow.hasNext() 참 -> middle = slow.next() = 9
       1바퀴 : fast.next()=9, hasNext 거짓 -> break
       return 9

[]   : slow.hasNext() 거짓 -> NoSuchElementException("비어 있다")
       테스트 emptyThrows 가 이 경로를 본다
```

- 논리: 반복자를 **두 개** 만드는 것이 핵심이다.\
  인덱스가 없으니 "서로 다른 두 위치"를 표현할 방법이 반복자뿐이다.
- 논리: 느린 쪽이 k 칸 갔을 때 빠른 쪽이 2k 칸 간다는 관계가 불변식이다.\
  빠른 쪽이 끝(n)에 닿으면 느린 쪽은 n/2 다.
- 논리: `fast.next()` 를 두 번 부르는 사이에 `hasNext()` 를 다시 확인한다.\
  안 하면 홀수 개에서 `NoSuchElementException` 이 난다.
- 논리: `middle = slow.next()` 를 **두 칸 전진에 성공한 뒤에만** 실행하는 것이 "짝수면 뒤쪽" 규칙을 만든다.
- 논리: `middle` 을 루프 밖에서 `slow.next()` 로 한 번 초기화해 두므로 원소가 1개인 경우가 저절로 처리된다.
- 비용(왜): 느린 쪽이 n/2 걸음, 빠른 쪽이 n 걸음 → 합쳐 `1.5n` → **O(n)**.
- 비용(왜): 들고 있는 것은 반복자 두 개와 값 하나 → **추가 공간 O(1)**.
- 비용(왜): 리스트 노드를 실제로 지나가는 횟수 기준으로는 "한 번만 훑는다"가 맞다 — 되감기가 없다.
- 한계: 반복자 두 개가 **같은 리스트**를 본다.\
  순회 중에 리스트가 바뀌면 둘의 관계가 조용히 깨진다.
- 한계: 진짜 스트림이라면 반복자를 두 개 못 만든다.\
  그때는 값 하나를 버퍼에 들고 위치만 따로 세는 식으로 바꿔야 한다(원본에 근거 없음 — 내 추론).
- 한계: "짝수면 뒤쪽"이라는 규칙이 코드의 **문장 순서**에 숨어 있다.\
  주석 없이 읽으면 왜 그런지 안 보인다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. size() + get(size/2) | O(n) | O(1) | 길이를 O(1)로 알 수 있는 자료구조 | 길이를 모르는 소스 · size() 금지 조건 |
| 2. 전부 버퍼에 담기 | O(n) | O(n) | 어차피 전체가 또 필요할 때 | 데이터가 메모리보다 클 때 |
| 3. 느린/빠른 포인터 | O(n) (1.5n 걸음) | O(1) | 기본값. 길이를 몰라도 되고 한 번만 훑는다 | 반복자를 하나만 만들 수 있는 소스 |

**데이터 규모가 커지면**

- n 이 커져도 접근 3의 추가 공간은 그대로 O(1) 이다 — 이 기법의 값어치가 전부 여기에 있다.
- 접근 2는 n = 1억이면 버퍼만으로 메모리가 터진다.\
  100GB 로그 파일의 가운데 줄을 찾는 상황이 정확히 그 예다.
- 파일·네트워크처럼 되감기가 불가능한 소스에서는 접근 1·2가 아예 선택지가 아니다.\
  남는 것은 두 주자 방식뿐이다.
- 같은 기법이 "순환 감지(cycle detection)"에도 그대로 쓰인다.\
  사슬에 고리가 있으면 빠른 쪽이 느린 쪽을 반드시 따라잡는다 — 이것도 길이를 모른 채 O(1) 공간으로 판정한다.
- 걸음 수는 `1.5n` 이라 단순 순회(`n`)보다 50% 많다.\
  캐시가 안 듣는 연결 리스트에서는 그 50%가 실제 시간에 그대로 나타난다(원본에 근거 없음 — 내 추론).

**질문별 답**

- Q: 문제 2(가운데 값 찾기 — `findMiddle`)를 어떻게 푸는가.\
  A: 같은 리스트에 반복자를 두 개 만든다.\
  `slow` 는 한 칸씩, `fast` 는 두 칸씩 나아간다.\
  `fast` 가 끝에 닿으면 `slow` 가 서 있는 자리가 가운데다.\
  비어 있으면 첫 `hasNext()` 에서 걸러 `NoSuchElementException` 을 던진다.

- Q: `size()`를 못 쓴다는 조건이 왜 이 기법을 강제하는가.\
  A: `size()` 를 막는 것은 "길이를 안다"는 전제를 빼앗는 것이다.\
  전제가 없으면 가운데 인덱스를 계산할 수가 없고, 남는 방법은 **두 위치의 상대 속도**로 절반을 표현하는 것뿐이다.\
  느린 쪽이 k, 빠른 쪽이 2k 라는 관계가 곧 "절반"의 정의를 대신한다.\
  이 조건은 연결 리스트만의 제약이 아니라, 길이를 모르는 스트림에서도 통하는 풀이를 배우게 하려는 장치다.

- Q: 한 번만 훑는다는 조건이 왜 이 기법을 강제하는가.\
  A: 두 번 훑어도 된다면 "세고 나서 다시 가기"가 가장 쉽다.\
  그런데 되감을 수 없는 소스에서는 두 번째 패스 자체가 없다.\
  한 번의 패스 안에서 답을 내려면 지나가는 동안 필요한 정보를 **상태로** 들고 있어야 하고, 여기서 그 상태가 느린 주자의 위치다.\
  덕분에 전체를 버퍼에 담지 않고도 추가 공간 O(1)로 끝난다.

- Q: 짝수 개일 때 왜 뒤쪽이 나오는가.\
  A: `middle = slow.next()` 가 **`fast` 를 두 칸 전진시키는 데 성공한 뒤에만** 실행되기 때문이다.\
  `[1,2,3,4]` 에서 두 칸 전진이 두 번 성공하므로 `slow` 가 `1 → 2 → 3` 으로 두 번 올라가 3에서 멈춘다.\
  `[1,2,3]` 에서는 두 칸 전진이 한 번만 성공해 `1 → 2` 로 한 번만 올라간다.\
  코드 순서를 바꿔 `slow` 를 먼저 올리면 짝수에서 앞쪽(2)이 나온다 — 규칙이 루프의 문장 순서에 박혀 있다.

#### 3. 정렬된 두 리스트 병합 (`mergeSorted`)

문제는 오름차순인 두 리스트 `a`, `b` 를 합쳐 `result` 에 오름차순으로 담는 것이다.\
`a` 와 `b` 는 건드리지 않는다.\
제약은 **O(n+m)** 이고, 결과를 담을 리스트를 인자로 받는다.

> **결합(coupling)** — 코드가 특정 구현의 이름을 직접 알아서 다른 구현으로 갈아탈 수 없게 되는 것.\
> 예: 함수 안에 `new DoublyLinkedList<>()` 라고 적으면 이 코드가 그 한 구현에 묶인다 — 그래서 `result` 를 인자로 받는다.

**접근 1 — 양쪽을 그냥 이어 붙이고 정렬** (제일 쉽게 떠오르지만 정렬 비용을 새로 만든다)

```java
// 의사코드
for (Integer x : a) result.add(x);
for (Integer y : b) result.add(y);
sort(result);   // 연결 리스트를 인덱스로 정렬하면 비교마다 탐색이 O(n)
```

```
a = [1,3,5], b = [2,3,6]

 이어 붙이기
   result  head -> [1|o]-> [3|o]-> [5|o]-> [2|o]-> [3|o]-> [6|/]
                   +--- a 그대로 ---+       +--- b 그대로 ---+

 정렬
   result  head -> [1|o]-> [2|o]-> [3|o]-> [3|o]-> [5|o]-> [6|/]

 "이미 정렬되어 있다"는 입력의 성질을 통째로 버리고 처음부터 다시 정렬한다.
 게다가 연결 리스트에서 인덱스 기반 정렬을 돌리면 비교/교환마다 탐색이 붙는다.
```

- 논리: 결과는 맞다.\
  테스트 `merges` 의 기댓값 `[1,2,3,3,5,6]` 도 나온다.
- 비용(왜): 정렬만으로 O((n+m) log(n+m)) 이다 — 목표인 O(n+m) 보다 log 배 느리다.
- 비용(왜): 연결 리스트를 `get(i)`/`set(i)` 기반 정렬 알고리즘에 넣으면 비교 한 번마다 탐색 O(n) 이 붙어 훨씬 더 나빠진다.
- 한계: 입력이 이미 정렬되어 있다는 가장 값진 정보를 안 쓴다.
- 한계: `result` 에 다 담아야만 정렬을 시작할 수 있다 — 스트리밍으로 흘려보낼 수 없다.

**접근 2 — 인덱스 커서 두 개로 비교** (병합 논리는 맞는데 인덱스가 다시 함정이다)

```java
// 의사코드
int i = 0, j = 0;
while (i < a.size() && j < b.size()) {
    if (a.get(i) <= b.get(j)) result.add(a.get(i++));
    else                      result.add(b.get(j++));
}
while (i < a.size()) result.add(a.get(i++));
while (j < b.size()) result.add(b.get(j++));
```

```
a = [1,3,5], b = [2,3,6]

 i=0, j=0 : a.get(0) -> head 에서 0 걸음
            b.get(0) -> head 에서 0 걸음   1 <= 2  -> result += 1, i=1
 i=1, j=0 : a.get(1) -> head 에서 1 걸음
            b.get(0) -> head 에서 0 걸음   3 > 2   -> result += 2, j=1
 i=1, j=1 : a.get(1) -> head 에서 1 걸음   <- 같은 자리를 또 걸어서 간다
            b.get(1) -> head 에서 1 걸음   3 <= 3  -> result += 3, i=2
 ...

 문제는 커서가 앞으로만 가는데도 매 비교마다 head 에서 다시 센다는 것이다.
 a 쪽 걸음 합계 = 0 + 1 + 2 + ... = n(n-1)/2
 전체            = O(n^2 + m^2)
 병합 논리는 O(n+m) 인데 자료구조 접근이 그것을 무너뜨린다.
```

- 논리: 병합 논리 자체는 정답과 똑같다 — 양쪽 앞머리를 비교해 작은 쪽을 꺼낸다.
- 논리: 배열이라면 이 코드가 그대로 최적해다.\
  `get(i)` 가 O(1) 이기 때문이다.
- 비용(왜): 연결 리스트에서는 `get(i)` 가 매번 `head` 부터 세므로 O(n) 이다.\
  그걸 n+m 번 부르면 O(n² + m²) 이 된다.
- 한계: 문제 1과 완전히 같은 함정이다 — 인덱스를 쓰는 순간 탐색이 살아난다.
- 한계: `size()` 를 매 비교마다 부르는 것은 이 구현에서는 O(1) 이라 문제가 아니지만, 커서 위치를 반복자로 바꾸면 그 호출조차 필요 없어진다.

**접근 3 — 양쪽에서 한 칸씩 "손에 들고" 비교** (impl 의 정답)

`Iterator` 에는 `peek()` 이 없다.\
`hasNext()` 는 "다음이 있냐"만 알려주고 `next()` 는 값을 돌려주면서 **동시에 커서를 전진시킨다**.\
그러니 값을 보고 나서 "역시 안 쓸래"가 불가능하다.\
우회법은 간단하다 — **한 칸 미리 당겨서 손에 들고 있는다.**

> **미리 보기(peek / lookahead)** — 커서를 전진시키지 않고 다음 값만 들여다보는 연산.\
> 예: `Iterator` 에는 이게 없어서 `next()` 로 꺼낸 값을 변수에 들고 있는 것으로 대신한다.

```java
public static void mergeSorted(List<Integer> a, List<Integer> b, List<Integer> result) {
    Iterator<Integer> ia = a.iterator();
    Iterator<Integer> ib = b.iterator();
    Integer x = ia.hasNext() ? ia.next() : null;
    Integer y = ib.hasNext() ? ib.next() : null;

    while (x != null && y != null) {
        if (x <= y) {
            result.add(x);
            x = ia.hasNext() ? ia.next() : null;
        } else {
            result.add(y);
            y = ib.hasNext() ? ib.next() : null;
        }
    }
    while (x != null) {
        result.add(x);
        x = ia.hasNext() ? ia.next() : null;
    }
    while (y != null) {
        result.add(y);
        y = ib.hasNext() ? ib.next() : null;
    }
}
```

```
a = [1,3,5], b = [2,3,6]   ->  기대 결과 [1,2,3,3,5,6]

준비    a: head -> [1|o]-> [3|o]-> [5|/]      손에 든 값 x = 1  (ia 는 [3] 앞에 서 있다)
        b: head -> [2|o]-> [3|o]-> [6|/]      손에 든 값 y = 2  (ib 는 [3] 앞에 서 있다)
        result: (비어 있음)

step1   x=1, y=2  ->  1 <= 2  ->  x 를 쓴다
        result: [1]
        쓴 쪽만 다시 채운다 : x = ia.next() = 3
        a: ... [3|o]-> [5|/]   x = 3
        b: ... [2|o]-> ...     y = 2      <- b 는 손도 안 댔다

step2   x=3, y=2  ->  3 > 2   ->  y 를 쓴다
        result: [1,2]
        y = ib.next() = 3

step3   x=3, y=3  ->  3 <= 3  ->  x 를 쓴다   <- 같으면 a 를 먼저 (안정성)
        result: [1,2,3]
        x = ia.next() = 5

step4   x=5, y=3  ->  5 > 3   ->  y 를 쓴다
        result: [1,2,3,3]
        y = ib.next() = 6

step5   x=5, y=6  ->  5 <= 6  ->  x 를 쓴다
        result: [1,2,3,3,5]
        ia.hasNext() 거짓 -> x = null      <- null 이 "이쪽은 다 떨어졌다"는 표시

        while (x != null && y != null) 종료

꼬리    while (y != null) : result += 6, y = null
        result: [1,2,3,3,5,6]     <- 기대와 일치

 핵심 : "한 칸 미리 당겨 손에 든다"가 peek() 의 대용이다.
        쓴 쪽만 다시 채우므로 한 원소를 두 번 꺼내는 일이 없다.
        a 는 ia 로 n 번, b 는 ib 로 m 번 — 각 노드를 딱 한 번씩 지나간다 -> O(n+m)
```

```
한쪽이 비어 있을 때 (테스트 handlesEmptySide)

a = [], b = [1,2]
 준비   x = null (ia.hasNext() 거짓),  y = 1
 while (x != null && y != null) : 첫 조건에서 바로 거짓 -> 안 돈다
 while (x != null) : 안 돈다
 while (y != null) : result += 1, += 2  ->  [1,2]

 세 루프로 나눈 이유가 이것이다. 한쪽이 먼저 떨어지면 남은 쪽을 통째로 흘려보낸다.
```

- 논리: `next()` 가 값 반환과 커서 전진을 한꺼번에 하므로, 꺼낸 값을 버릴 수 없다.\
  그래서 꺼낸 값을 변수(`x`, `y`)에 **들고 있는** 것으로 `peek()` 을 대신한다.
- 논리: 비교에서 **진 쪽은 건드리지 않는다**.\
  그 값이 다음 비교에 그대로 다시 쓰인다.
- 논리: `null` 이 "이쪽 반복자는 소진됐다"는 표시다.\
  이게 가능한 건 이 문제의 입력에 `null` 이 없다고 **계약**했기 때문이다.
- 논리: `x <= y` 에서 등호가 `a` 쪽 손을 들어준다.\
  값이 같을 때 `a` 의 원소가 먼저 나가므로 **안정(stable)** 병합이 된다.
- 논리: 세 개의 `while` 이 각각 "둘 다 남음 / a 만 남음 / b 만 남음"을 처리한다.
- 비용(왜): `a` 의 노드를 각각 한 번, `b` 의 노드를 각각 한 번 지나간다 → **O(n+m)**.
- 비용(왜): `result.add` 는 `tail` 이 있어 O(1) 이므로 총 n+m 번 불러도 O(n+m) 이다.
- 비용(왜): 추가 공간은 반복자 둘 + 값 둘 → **O(1)** (결과 리스트는 제외).
- 한계: 입력에 `null` 원소가 있으면 그 자리를 "끝"으로 오해한다.\
  계약으로 막았을 뿐 코드가 스스로 막지는 않는다.
- 한계: `x <= y` 는 `Integer` 언박싱 비교라 `x`, `y` 가 null 이 아님을 루프 조건이 보장해야만 안전하다.\
  세 루프의 조건이 그 역할을 하고 있다.
- 한계: `result` 가 `a` 나 `b` 와 같은 객체면 무한 루프나 오염이 생긴다.\
  테스트 `doesNotMutateInputs` 는 원본 불변만 보고 별칭 여부는 검사하지 않는다.

> **안정 정렬(stable)** — 값이 같은 원소들의 원래 순서가 결과에서도 유지되는 성질.\
> 예: `x <= y` 로 등호를 `a` 쪽에 주면 값이 같을 때 항상 `a` 의 원소가 먼저 나가 순서가 보존된다.

> **별칭(aliasing)** — 서로 다른 변수 이름이 실은 같은 객체를 가리키는 상황.\
> 예: `mergeSorted(a, b, a)` 처럼 결과 리스트가 입력과 같은 객체면, 읽는 도중에 쓰는 셈이 되어 결과가 망가진다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 이어 붙이고 정렬 | O((n+m) log(n+m)) 이상 | O(1)~O(n+m) | 입력이 정렬돼 있는지 보장이 없을 때 | 선형 시간 요구가 있을 때 · 스트리밍일 때 |
| 2. 인덱스 커서 두 개 | O(n^2 + m^2) | O(1) | 배열 기반 리스트일 때 | 연결 리스트일 때 (탐색이 되살아난다) |
| 3. 반복자 + 한 칸 들고 있기 | O(n+m) | O(1) | 기본값. 정렬된 두 소스를 합칠 때 | 입력에 null 이 섞일 수 있을 때 |

**데이터 규모가 커지면**

- n = m = 100,000 이면 접근 2는 계산상 약 `10^10` 걸음이고 접근 3은 `2 x 10^5` 걸음이다.\
  둘 사이에 다섯 자리 수 차이가 난다.
- 합칠 소스가 2개가 아니라 k 개가 되면 "가장 작은 앞머리 고르기"가 k 번 비교가 된다.\
  총 `O(N k)` 가 되므로 **최소 힙(min-heap)** 을 써서 `O(N log k)` 로 낮춘다.
- 입력이 메모리에 다 안 올라가면 반복자를 파일 리더로 바꾼다.\
  손에 든 값이 양쪽 한 개씩뿐이라 코드 구조는 그대로다 — 이것이 **외부 병합 정렬(external merge sort)** 의 병합 단계다.
- 결과도 메모리에 못 담으면 `result.add(...)` 를 "출력 스트림에 쓴다"로 바꾼다.\
  추가 공간이 O(1) 로 유지된다.
- 연결 리스트끼리 합칠 때는 새 노드를 만들지 않고 **기존 노드의 링크만 다시 걸어** 붙이는 최적화가 가능하다.\
  다만 그러면 `a`·`b` 가 파괴되므로 "원본을 건드리지 않는다"는 이 문제의 계약과 충돌한다.

**질문별 답**

- Q: 문제 3(정렬된 두 리스트 병합 — `mergeSorted`)을 어떻게 푸는가.\
  A: 양쪽에 반복자를 하나씩 만들고, 각 쪽에서 값 하나씩을 미리 꺼내 변수 `x`, `y` 에 들고 있는다.\
  `x <= y` 면 `x` 를 `result` 에 넣고 `a` 쪽만 다음 값으로 채우고, 아니면 `y` 를 넣고 `b` 쪽만 채운다.\
  한쪽이 떨어지면(`null`) 남은 쪽을 통째로 흘려보낸다.\
  `a`, `b` 는 읽기만 하므로 원본이 변하지 않는다.

- Q: `Iterator`에 "미리 보기"가 없다는 제약을 어떻게 우회하는가.\
  A: `next()` 는 값을 돌려주면서 커서까지 전진시키므로, 값을 보고 나서 무르는 것이 불가능하다.\
  그래서 **한 칸 미리 당겨 손에 들고 있는다** — 꺼낸 값을 변수에 보관하는 것이 곧 `peek()` 의 대용이다.\
  비교에서 진 쪽은 변수를 그대로 두므로 그 값이 다음 비교에 다시 쓰이고, 이긴 쪽만 `next()` 로 새로 채운다.\
  반복자가 소진되면 변수에 `null` 을 넣어 "이쪽 끝"을 표시하는데, 이건 입력에 `null` 이 없다는 계약이 있어야 성립한다.

- Q: 왜 O(n+m)인가.\
  A: 매 반복마다 결과에 원소가 정확히 하나 들어가고, 그 원소를 낸 쪽만 한 칸 전진한다.\
  그래서 `a` 의 노드는 `ia` 로 딱 한 번, `b` 의 노드는 `ib` 로 딱 한 번 지나간다 — 총 이동이 `n + m` 걸음이다.\
  비교는 반복마다 한 번이므로 이것도 `n + m` 번이다.\
  `result.add` 는 `tail` 덕분에 O(1) 이라 총합이 O(n+m) 으로 유지된다 — 여기서 인덱스를 쓰면 이 성질이 즉시 무너진다.

- Q: 결과 리스트를 인자로 받는 이유는 무엇인가.\
  A: 함수 안에서 `new DoublyLinkedList<>()` 라고 적으면 이 코드가 그 한 구현에 묶이기 때문이다.\
  어떤 구현에 담을지는 호출자가 정하는 것이 맞다.\
  실제로 테스트 `ListProblemsTest` 는 같은 함수를 `SinglyLinkedList` 와 `DoublyLinkedList` 양쪽으로 돌린다.\
  함수는 `List` 인터페이스만 알고 있으므로 코드 한 줄 안 바꾸고 두 구현에서 같게 동작한다.

### B. 자료구조 특성

#### 4. 연결 리스트가 왜 필요한가

- Q: 연결 리스트가 왜 필요한가?\
  A: 동적 배열이 못 하는 것 하나를 하기 위해서다 — **중간과 앞을 싸게 고치는 것**이다.\
  배열은 원소를 메모리에 붙여 놓는다는 선택 때문에 중간을 비우거나 끼우면 뒤를 전부 밀거나 당겨야 한다.\
  연결 리스트는 "다음이 어디냐"를 노드 안의 참조에 적어 두므로, 자리를 옮기는 대신 **화살표만 고친다**.\
  그 결과 노드를 이미 손에 쥐고 있다면 삽입·삭제가 O(1) 이 된다.

- Q: 01-dynamic-array로는 무엇이 안 되는가 — 맨 앞 삽입/삭제에서 배열이 치르는 비용은 무엇인가?\
  A: 맨 앞에 넣으려면 0번 칸을 비워야 하고, 그러려면 **원소 n 개를 전부 한 칸씩 뒤로 민다** → O(n).\
  맨 앞을 지우면 뒤의 n-1 개를 전부 한 칸씩 당긴다 → O(n).\
  이 비용은 원소가 크든 작든 개수에 비례해 그대로 든다.\
  연결 리스트에서는 `head = new Node<>(element, head)` 한 줄, 즉 참조 대입 두 번이면 끝난다.

```
맨 앞 삽입 — 같은 일을 두 구조가 어떻게 하는가

배열      before  [ A ][ B ][ C ][ D ][   ]
                    -->  -->  -->  -->          네 칸을 전부 한 칸씩 뒤로 민다
          step    [ A ][ A ][ B ][ C ][ D ]     뒤에서부터 4칸을 민다 -> O(n)
          after   [ X ][ A ][ B ][ C ][ D ]

리스트    before  head -> [A|o]-> [B|o]-> [C|/]
          step1   새 노드를 만들며 옛 head 를 그 next 에 담는다
                          [X|o]-> [A|o]-> [B|o]-> [C|/]
          step2   head 를 새 노드로 옮긴다
          after   head -> [X|o]-> [A|o]-> [B|o]-> [C|/]
                  A, B, C 는 한 칸도 안 움직였다 -> O(1)
```

- Q: 중간 삽입/삭제에서 배열이 치르는 비용은 무엇인가?\
  A: 인덱스 i 에 끼우면 i 뒤의 `n - i` 개를 밀고, 지우면 `n - i - 1` 개를 당긴다 → 평균 n/2, 최악 n → **O(n)**.\
  연결 리스트는 **자리 찾기**와 **끼우기**가 분리된다.\
  인덱스로 찾아가면 탐색이 O(n) 이지만, 그 노드를 이미 참조로 들고 있으면 끼우기·빼기는 링크 두세 개만 고쳐 O(1) 이다.\
  즉 배열은 "옮기는 비용"을 내고 리스트는 "찾아가는 비용"을 낸다 — 무엇을 이미 알고 있느냐에 따라 승자가 갈린다.

> **임의 접근(random access)** — 몇 번째든 같은 비용으로 바로 꺼낼 수 있는 성질.\
> 예: 배열은 `base + index * 원소크기` 로 주소를 계산해 한 번에 가지만, 연결 리스트는 계산할 주소가 없다.

**더 생각할 것**

- "배열은 느리다"가 아니라 **어디가 느린지가 다르다**가 맞는 표현이다.\
  배열은 옮기기가 비싸고 리스트는 찾아가기가 비싸다.
- 실무에서 순수 연결 리스트를 그대로 쓰는 일은 드물다.\
  대신 연결 구조가 다른 자료구조 **안에** 들어간다 — LRU 캐시(이중 연결 + 해시맵), 해시 테이블의 체이닝, 스케줄러의 대기열 같은 것들이다.
- 자바의 `LinkedList` 를 쓸 자리는 생각보다 적다.\
  "앞에서 빼고 뒤에 넣는" 큐가 대표적이고, 그마저도 `ArrayDeque` 가 더 빠른 경우가 많다(원본에 근거 없음 — 내 추론).
- 노드를 손에 쥐고 있다는 전제가 이 구조의 전부다.\
  그래서 실무 코드는 "노드 핸들"을 따로 보관하는 설계를 같이 가져간다 — LRU 캐시가 해시맵에 노드를 담아 두는 이유가 그것이다.

#### 5. 어떤 데이터·접근 패턴에 적합한가

- Q: 어떤 형태의 데이터·접근 패턴에 연결 리스트가 적합한가?\
  A: 접근 지점이 **양 끝이나 이미 아는 노드**에 몰려 있는 패턴이다.\
  큐처럼 앞에서 빼고 뒤에 넣는 흐름 — 양쪽 다 O(1) 이다.\
  전체 순회는 하되 "몇 번째"로는 안 찾는 패턴 — 반복자로 O(n) 이면 충분하다.\
  중간 삽입·삭제가 잦고 그 위치를 노드 참조로 이미 들고 있는 패턴 — 링크만 고쳐 O(1) 이다.\
  크기가 예측 불가능하게 요동치는 데이터 — 확장 시 전체 복사가 없고 필요한 만큼만 노드를 만든다.

- Q: 언제 쓰면 안 되는가?\
  A: 인덱스로 임의 접근이 잦을 때 — 매번 O(n) 이다.\
  이진 탐색처럼 "가운데로 점프"가 필요한 알고리즘 — 점프가 안 되니 정렬해 둬도 이득이 없다.\
  원소가 작고 아주 많을 때 — 값 하나에 노드 객체 하나가 붙어 메모리가 몇 배로 든다.\
  순차 순회 속도가 중요한 데이터 처리 — 노드가 흩어져 있어 캐시가 안 듣는다.

- Q: 인덱스 임의 접근이 잦은 워크로드에서 왜 무너지는가?\
  A: 연결 리스트에는 **계산할 주소가 없다**.\
  `get(i)` 는 `node(i)` 를 부르고 그건 `head` 에서 `next` 를 i 번 따라가는 루프다 → 한 번이 O(n).\
  그걸 루프 안에서 부르면 전체가 O(n²) 이 된다 — 문제 1의 함정이 정확히 이것이다.\
  게다가 걸음 하나하나가 포인터 추격이라, 걸음 수가 같아도 배열보다 실제 시간이 더 든다.

```
같은 "n개 순회"의 총비용 — 인덱스로 vs 반복자로

인덱스     get(0) : 0 걸음
           get(1) : 1 걸음
           get(2) : 2 걸음
            ...
           get(n-1) : n-1 걸음
           합계 = n(n-1)/2   ->  O(n^2)

           head -> [A]-> [B]-> [C]-> [D]
                    ^                      get(0) 은 여기서 멈추고
                    ^---->---->            get(2) 는 다시 여기서 출발한다  <- 매번 되돌아간다

반복자     서 있던 자리에서 한 걸음씩
           head -> [A]-> [B]-> [C]-> [D]
                    1     2     3     4     합계 = n  ->  O(n)
```

**더 생각할 것**

- "적합/부적합"은 자료구조의 성질이 아니라 **워크로드 비율**의 문제다.\
  인덱스 접근이 전체의 0.1% 면 O(n) 이어도 무해하다.
- 배열과 리스트 중 무엇이 빠른지는 벤치마크를 재 봐야 안다.\
  n 이 수백 이하면 캐시 지역성 때문에 배열이 삽입·삭제에서도 이기는 일이 흔하다(원본에 근거 없음 — 내 추론).
- 실무에서 연결 리스트가 남아 있는 자리는 대개 **"노드 참조를 이미 들고 있다"** 는 전제가 성립하는 곳이다.\
  그 전제가 없으면 이 구조의 장점은 대부분 사라진다.

#### 6. `get(i)`는 O(n)인데 `addFirst`는 O(1)인 구조적 이유

- Q: `get(i)`가 O(n)인 구조적 이유는 무엇인가?\
  A: 원소들이 메모리에서 **붙어 있지 않기** 때문이다.\
  i 번째 노드가 어디 있는지는 오직 i-1 번째 노드의 `next` 안에만 적혀 있다.\
  그래서 그 주소를 알려면 i-1 번째를 먼저 읽어야 하고, 그러려면 i-2 번째를 먼저 읽어야 한다.\
  결국 `head` 에서 출발해 i 번 따라가는 것 외에 방법이 없다 → O(n).

```java
// SinglyLinkedList — 인덱스 접근의 전부
private Node<E> node(int index) {
    Node<E> n = head;
    for (int i = 0; i < index; i++) n = n.next;
    return n;
}
```

- Q: `addFirst`가 O(1)인 구조적 이유는 무엇인가?\
  A: 앞에 끼우는 데 필요한 정보가 `head` 하나뿐이고, 고칠 참조가 상수 개이기 때문이다.\
  새 노드를 만들면서 그 `next` 에 옛 `head` 를 담고, `head` 를 새 노드로 옮기면 끝이다.\
  기존 노드는 단 하나도 움직이지 않고 값도 복사하지 않는다.\
  리스트가 3개든 300만 개든 하는 일이 똑같다 → O(1).

```java
// SinglyLinkedList
public void addFirst(E element) {
    head = new Node<>(element, head);
    if (tail == null) tail = head;
    bumpSize(1);
}
```

- Q: "주소를 계산한다"와 "세면서 간다"의 차이가 어디서 오는가?\
  A: **연속 저장이냐 아니냐**라는 단 하나의 설계 선택에서 온다.\
  배열은 원소를 붙여 놓으므로 `base + index * 원소크기` 라는 **산술식**으로 주소가 나온다 — 개수와 무관하게 곱셈·덧셈 한 번이다.\
  연결 리스트는 위치가 흩어져 있어 계산할 식이 없고, 다음 주소를 **읽어서** 알아내야 한다.\
  같은 뿌리에서 반대 결과도 나온다 — 연속이라서 배열은 중간을 고칠 때 뒤를 전부 밀어야 하고, 연속이 아니라서 리스트는 화살표만 고치면 된다.

```
왜 한쪽은 계산이고 한쪽은 걷기인가

배열 (연속)     주소 = base + index * 원소크기
                +-----+-----+-----+-----+
                |  A  |  B  |  C  |  D  |     base
                +-----+-----+-----+-----+
                   0     1     2     3        index 3 -> base + 3*크기 로 즉시
                실제 위치가 규칙적이라 "식"이 존재한다

리스트 (흩어짐) 주소 = ??? 아무 규칙도 없다
                0x7f10 [A|->0x7f88]
                0x7f88 [B|->0x7a20]      다음 주소가 앞 노드 안에만 적혀 있다
                0x7a20 [C|->0x7f44]      -> 읽어야만 알 수 있다 -> 세면서 간다
                0x7f44 [D|/]
```

> **캐시 지역성(cache locality)** — 쓸 데이터가 메모리에서 서로 붙어 있어 CPU 가 근처 값을 한 덩어리로 미리 가져와 쓰게 되는 성질.\
> 예: 배열은 옆 칸이 곧 다음 원소라 한 번 가져온 캐시 라인을 계속 쓰지만, 노드가 흩어진 연결 리스트는 매번 새로 가져와야 한다.

**더 생각할 것**

- 복잡도 표기는 걸음 수만 세고 한 걸음의 가격을 안 센다.\
  둘 다 O(n) 순회여도 배열이 실제로 몇 배 빠른 경우가 흔하다.
- `addFirst` 가 O(1) 인 것은 참조를 고정된 개수만 고친다는 사실에서 나온다.\
  "값을 옮기지 않는다"가 연결 구조의 값어치 전부라고 봐도 된다.
- 이 대비가 03-stack 에서 다시 나온다 — 같은 계약을 배열과 연결 두 가지로 구현하면서 어떤 연산이 비싸지는지가 갈린다.

#### 7. `tail`이 있는데도 `removeLast()`가 O(n)인 이유

- Q: `tail`을 들고 있는데도 `SinglyLinkedList.removeLast()`가 O(n)인 이유는 무엇인가?\
  A: 마지막 노드를 아는 것과 **그것을 지우는 것**이 다른 문제이기 때문이다.\
  마지막 노드를 떼어내면 그 앞 노드가 새 `tail` 이 되어야 하고, 그 노드의 `next` 를 `null` 로 만들어야 한다.\
  그런데 단일 연결에서는 화살표가 앞으로만 있어 `tail` 에서 **뒤로 한 칸도 갈 수 없다**.\
  그래서 `head` 부터 다시 걸으며 `pred.next == tail` 인 노드를 찾는다 → O(n).

```java
// SinglyLinkedList.removeLast() — 문제의 while 한 줄
Node<E> pred = head;
while (pred.next != tail) {       // <- 여기가 O(n)
    pred = pred.next;
}
E value = tail.item;
tail.item = null;
pred.next = null;
tail = pred;
bumpSize(-1);
```

```
removeLast() 를 단계로 — [A,B,C] 에서 C 를 뺀다

before   head -> [A|o]-> [B|o]-> [C|/]  <- tail
                  ^                 ^
                  |                 | tail 은 알지만
                  +--- 여기가 필요한데 tail 에서 되돌아갈 화살표가 없다

step1    pred = head 에서 출발해 pred.next == tail 이 될 때까지 걷는다   <- O(n)
         pred: [A] -> [B]        ([B].next == [C] == tail 이므로 멈춘다)

step2    tail.item = null                (값 참조를 끊는다)
         head -> [A|o]-> [B|o]-> [ |/]

step3    pred.next = null                (사슬에서 떼어낸다)
         head -> [A|o]-> [B|/]      [ |/]

step4    tail = pred                     (표지를 내린다 — 이걸 빼먹는 것이 대표 실수다)
after    head -> [A|o]-> [B|/]  <- tail

 이중 연결이었다면 step1 이 통째로 사라진다 : pred = tail.prev  (한 번 읽기)
```

- Q: 반대로 `addLast`는 왜 O(1)인가?\
  A: 뒤에 붙이는 데 필요한 것이 마지막 노드 **자신**뿐이고, 그것을 `tail` 이 이미 들고 있기 때문이다.\
  `tail.next = node` 로 새 노드를 걸고 `tail = node` 로 표지를 옮기면 끝이다.\
  뒤로 갈 필요가 전혀 없으므로 단방향이라는 제약에 걸리지 않는다.\
  `tail` 필드가 없었다면 마지막 노드를 찾으러 `head` 부터 걸어야 해서 O(n) 이 된다 — 그래서 `tail` 을 둔다.

```java
// SinglyLinkedList — tail 이 있으므로 앞에서부터 갈 필요가 없다
public void addLast(E element) {
    Node<E> node = new Node<>(element, null);
    if (tail == null) {
        head = node;
    } else {
        tail.next = node;
    }
    tail = node;
    bumpSize(1);
}
```

- Q: 그래서 `tail` 이 해결하는 것과 못 하는 것은 각각 무엇인가?\
  A: 해결하는 것 — "마지막 노드가 어디냐"는 질문이다.\
  그래서 `addLast` 와 `getLast` 가 O(1) 이 된다.\
  못 하는 것 — "그 앞이 어디냐"는 질문이다.\
  그 답은 `prev` 참조에만 있고 단일 연결에는 `prev` 가 없다 — 이 한 가지가 이중 연결 리스트가 존재하는 이유다.

**더 생각할 것**

- `tail` 갱신을 빼먹는 것이 이 챕터에서 제일 잘 나는 버그다.\
  앞에서 읽을 때는 멀쩡해 보이고 다음 `add` 에서야 드러난다.
- 그래서 `SinglyLinkedListTest.assertSound` 가 `tail.next == null` 과 "`tail` 이 정말 마지막 노드인가"를 매번 확인한다.\
  테스트가 `head`·`tail` 같은 내부 필드를 직접 보는 이유가 이것이고, 그래서 이 **이름들이 계약의 일부**다.
- 큐를 단일 연결 리스트로 만들 때 "앞에서 빼고 뒤에 넣기"로 방향을 잡는 것도 같은 이유다.\
  반대로 잡으면 매 `dequeue` 가 O(n) 이 된다.

#### 8. 최악의 사용 패턴과 `Iterator` 가 여기에만 있는 이유

- Q: `for (int i = 0; i < list.size(); i++) list.get(i)` 로 n개를 순회하면 총 비용이 얼마인가?\
  A: `get(i)` 가 매번 `head` 에서 i 걸음이므로 총 걸음은 `0 + 1 + 2 + ... + (n-1) = n(n-1)/2` 다.\
  약 `n²/2` → **O(n²)**.\
  `size()` 는 필드 읽기라 O(1) 이니 여기서는 죄가 없다.\
  이중 연결이면 가까운 끝에서 출발해 `n²/4` 정도가 되지만 차수는 그대로다.

- Q: `Iterator`로 돌면 얼마인가?\
  A: 반복자는 지금 서 있는 노드를 상태로 들고 있으므로 `next()` 한 번이 `n = n.next` 한 걸음이다.\
  n 번 모아도 총 n 걸음 → **O(n)**.\
  되돌아가는 일이 한 번도 없다는 것이 차이의 전부다.

```
n = 100,000 일 때 (테스트 mustBeLinear 의 규모)

인덱스 순회 : 계산상 약 5 x 10^9 걸음   -> 5초 제한을 못 넘긴다
반복자 순회 : 약 1 x 10^5 걸음          -> 사실상 즉시

  같은 "전부 훑기"인데 네 자리 수 차이가 난다.
  달라진 것은 알고리즘이 아니라 "다음 원소로 가는 방법" 하나뿐이다.
```

- Q: 최악의 사용 패턴을 만들어 보라.\
  A: 인덱스 순회 안에서 인덱스 수정을 또 하는 것이다 — 문제 1의 접근 1이 정확히 그 모양이다.\
  `for (int i = size-1; i >= 0; i--) if (test(get(i))) remove(i)` 는 `get` 으로 O(n), `remove` 로 또 O(n) 을 쓴다.\
  여기에 `remove(size-1)` 이 `removeLast()` 로 빠지면 `tail` 앞 노드를 찾느라 한 번 더 전체를 걷는다.\
  n = 100,000 에서 테스트가 5초 안에 못 끝난다.

- Q: 왜 이 챕터에만 `Iterator`가 있는가?\
  A: 여기서만 `Iterator` 가 **복잡도를 바꾸기** 때문이다.\
  연결 리스트는 인덱스 순회가 O(n²) 이고, 인덱스를 안 쓰고 순회하는 유일한 방법이 반복자다.\
  01번 배열은 `get(i)` 가 이미 O(1) 이라 반복자를 써도 O(n) 그대로 — 복잡도가 안 바뀌니 넣을 이유가 없다.\
  03번 스택과 04번 큐는 순회 자체가 자료구조의 의도(접근 지점을 양 끝으로 제한한다)와 어긋나서 없다.

- Q: `remove()` 까지 지원해야 하는 이유는 무엇인가?\
  A: 순회만 O(n) 으로 만들어도 "조건부 삭제"가 여전히 O(n²) 이기 때문이다.\
  반복자로 훑다가 지울 원소를 찾아도, 지우는 일을 `list.remove(i)` 로 하면 그 자리를 다시 찾느라 O(n) 이 든다.\
  `it.remove()` 는 방금 돌려준 노드를 이미 참조로 쥐고 있어 **찾는 일이 없다**.\
  그래서 순회하면서 지우는 것이 이 자료구조에서 조건부 삭제를 O(n)으로 하는 유일한 방법이다.

> **문법 설탕(syntactic sugar)** — 동작은 그대로인데 코드만 짧고 읽기 좋게 해 주는 문법.\
> 예: 배열에서 for-each 는 문법 설탕이지만, 연결 리스트의 `Iterator` 는 O(n²)를 O(n)으로 바꾸므로 설탕이 아니다.

**더 생각할 것**

- `for (E e : list)` 는 컴파일되면 `list.iterator()` 호출로 바뀐다.\
  그래서 연결 리스트에서는 for-each 와 인덱스 for 문이 **복잡도가 다른 서로 다른 코드**다.
- 코드 리뷰에서 `list.get(i)` 를 루프 안에서 보면 그 `list` 의 실제 구현부터 확인하는 습관이 필요하다.\
  타입이 `List` 인터페이스면 겉으로는 구분이 안 된다.
- 자바 표준 `LinkedList` 도 똑같은 함정을 가진다.\
  그래서 `RandomAccess` 라는 표시 인터페이스가 있고, "이 리스트는 인덱스 접근이 싸다"를 코드가 물어볼 수 있게 해 준다(원본에 근거 없음 — 내 추론).

#### 9. 단일 연결과 이중 연결의 트레이드오프

- Q: 참조 하나를 더 두는 대가로 무엇을 얻는가?\
  A: 얻는 것은 **"뒤로 갈 수 있다"** 하나이고, 거기서 나머지가 전부 파생된다.\
  `removeLast` 가 O(n) 에서 O(1) 로 떨어진다 — `tail.prev` 로 앞 노드를 바로 안다.\
  뒤쪽 인덱스 접근의 평균 이동 거리가 절반이 된다 — 가까운 끝에서 출발한다.\
  `Iterator.remove()` 의 구현이 단순해진다 — 앞 노드를 따로 들고 다닐 필요가 없다.\
  노드 하나를 손에 쥐면 그 앞뒤를 다 알 수 있으므로, 리스트 객체 없이 노드만으로 삭제가 가능해진다.

```java
// DoublyLinkedList — 절반을 넘어가면 tail 에서 거슬러 온다
private Node<E> node(int index) {
    if (index < (size >> 1)) {
        Node<E> n = head;
        for (int i = 0; i < index; i++) n = n.next;
        return n;
    }
    Node<E> n = tail;
    for (int i = size - 1; i > index; i--) n = n.prev;
    return n;
}
```

- Q: 무엇을 잃는가?\
  A: 노드마다 참조 하나가 더 붙어 메모리가 늘어난다.\
  고칠 링크가 늘어 코드가 복잡해진다 — 중간 삽입이 링크 2개에서 4개로 늘고, 삭제도 양쪽을 다 손봐야 한다.\
  틀릴 자리가 늘어난다 — `prev` 를 안 잇는 버그는 앞에서 읽으면 멀쩡해 보여서 **가장 늦게 발견되는 버그**다.\
  그래서 `DoublyLinkedListTest.assertSound` 가 "앞으로 훑은 결과와 뒤로 훑은 결과가 서로의 역순인지"를 매번 확인한다.

| | 단일 연결 | 이중 연결 |
|---|---|---|
| `addFirst`, `removeFirst`, `addLast` | O(1) | O(1) |
| `removeLast` | **O(n)** (앞 노드를 찾아야) | **O(1)** (`tail.prev`) |
| 뒤쪽 인덱스 접근 | 언제나 `head` 부터 | 가까운 끝에서 (평균 절반) |
| 노드당 참조 | 1개 (`next`) | 2개 (`prev`, `next`) |
| 중간 삽입 시 고칠 링크 | 2개 | 4개 |
| `reverse` | 포인터 3개를 굴린다 | `prev`/`next` 를 맞바꾼다 |
| `Iterator.remove()` | 앞 노드를 따로 추적 | `unlink(lastReturned)` 재사용 |

- Q: `reverse`의 방식은 어떻게 달라지는가?\
  A: 단일은 `prev`, `cur`, `next` **세 포인터**를 굴리며 각 노드의 `next` 를 뒤로 돌린다.\
  이중은 각 노드에서 `prev` 와 `next` 를 **맞바꾸고** 마지막에 `head`/`tail` 을 교환한다.\
  둘 다 O(n) 시간 · O(1) 공간이고 값은 한 개도 옮기지 않는다.\
  공통점이 더 중요하다 — 둘 다 "링크를 고치기 전에 다음으로 갈 길을 먼저 잡는다"(10번).

```java
// SinglyLinkedList.reverse() — 포인터 세 개
Node<E> oldHead = head;
Node<E> prev = null;
Node<E> cur = head;
while (cur != null) {
    Node<E> next = cur.next;      // 먼저 잡는다
    cur.next = prev;
    prev = cur;
    cur = next;
}
head = prev;
tail = oldHead;
```

```java
// DoublyLinkedList.reverse() — prev 와 next 를 맞바꾼다
Node<E> node = head;
while (node != null) {
    Node<E> next = node.next;     // 먼저 잡는다
    node.next = node.prev;
    node.prev = next;
    node = next;
}
Node<E> oldHead = head;
head = tail;
tail = oldHead;
```

```
reverse 한 노드에서 벌어지는 일

단일     before   ... [B|o]-> [C|o]-> [D|/]
                       prev    cur     next(미리 잡아 둠)
         step     cur.next = prev
                  ... [B]<-[C]   [D|/]        <- 이 순간 C 에서 D 로 가는 길이 사라졌다
                                               미리 안 잡았으면 여기서 리스트가 끊긴다
         after    prev = C, cur = D 로 한 칸 전진

이중     before   [o|B|o] <-> [o|C|o] <-> [o|D|/]
         step     next = C.next(=D) 를 먼저 잡고
                  C.next = C.prev(=B),  C.prev = next(=D)
         after    [o|B|o] <-> [o|C|o] <-> [o|D|/]   화살표 방향만 반대
                  값은 한 개도 안 옮겼다
```

**더 생각할 것**

- "참조 하나를 더 둘까"는 **공간 대 시간**의 교환이 아니라 **공간 + 복잡도 대 시간**의 교환이다.\
  늘어난 코드가 곧 늘어난 버그 자리다.
- `prev` 를 안 잇는 구현도 계약 테스트를 대부분 통과한다 — 앞으로 읽을 땐 멀쩡하기 때문이다.\
  그래서 `assertSound` 같은 **구조 건전성 단언**이 이 문제집에서 가장 중요한 단언으로 꼽힌다.
- 표준 라이브러리의 `java.util.LinkedList` 는 이중 연결이다.\
  `Deque` 를 구현하려면 양 끝에서 O(1) 삭제가 필요하고, 그건 `prev` 없이는 불가능하다.
- 단방향 사슬이 더 나은 자리도 있다 — 노드가 아주 많고 메모리가 빠듯하며 삭제가 앞에서만 일어나는 구조(스택, 해시 체이닝)가 그렇다.

#### 10. `reverse()`와 `Iterator.remove()`가 사실 같은 문제인 이유

- Q: 둘이 왜 같은 문제인가?\
  A: 둘 다 **링크를 덮어쓰기 전에 그 링크로만 갈 수 있는 곳을 먼저 붙잡아야 하는** 문제다.\
  `reverse` 는 `cur.next` 를 `prev` 로 돌리는 순간 원래 다음 노드로 가는 유일한 길이 사라진다.\
  `Iterator.remove()` 는 지울 노드의 앞 노드를 알아야 하는데, 단일 연결에서는 지우고 나서는 그 앞으로 돌아갈 수 없다.\
  해법도 같다 — **필요해지기 전에 미리 변수에 담아 둔다**(`next` 를 먼저 잡기 / `beforeLastReturned` 를 미리 들고 다니기).

```
같은 실수, 같은 해법

reverse 에서 순서를 틀리면
  before   ... [B|o]-> [C|o]-> [D|o]-> [E|/]
                        cur
  잘못      cur.next = prev  를 먼저 한다
           ... [B]<-[C]        [D|o]-> [E|/]
                               ^ D 로 가는 유일한 화살표가 방금 지워졌다
                                 D, E 가 통째로 사라진다 (그리고 GC 된다)
  옳게      next = cur.next   <- 먼저 잡는다
           cur.next = prev
           cur = next         <- 잡아 둔 길로 간다

Iterator.remove() 에서 순서를 틀리면
  before   head -> [A|o]-> [B|o]-> [C|/]
                            ^ lastReturned (지울 노드)
  잘못      lastReturned.next = null 을 먼저 한다
           head -> [A|o]-> [B|/]      [C|/]
                                      ^ C 로 가는 유일한 길이 사라졌다
                                        A 를 B 와 이어 줄 방법이 없다
  옳게      beforeLastReturned.next = lastReturned.next   <- 먼저 잇고
           lastReturned.next = null                      <- 그다음에 끊는다

같은 규칙 : "끊기 전에 이어라. 덮어쓰기 전에 잡아라."
```

- Q: 링크를 고치는 순서가 왜 중요한가?\
  A: 연결 리스트에서 어떤 노드로 가는 길이 **딱 하나뿐**이기 때문이다.\
  배열이라면 인덱스로 언제든 다시 갈 수 있지만, 여기서는 그 화살표를 덮어쓰는 순간 그 뒤가 통째로 도달 불가능해진다.\
  도달 불가능해진 노드는 잃어버린 데이터일 뿐 아니라 GC 대상이 되어 되찾을 수도 없다.\
  그래서 규칙이 하나다 — **덮어쓸 참조가 유일한 길이면, 덮기 전에 다른 이름을 붙여 둔다.**

- Q: 이중 연결에서는 이 문제가 사라지는가?\
  A: 아니다.\
  `DoublyLinkedList.reverse()` 도 `Node<E> next = node.next;` 로 먼저 잡고 시작한다 — `node.next` 를 `node.prev` 로 덮으면 다음 노드를 잃기 때문이다.\
  `linkBefore` 도 `succ.prev` 를 덮기 전에 `pred = succ.prev` 로 먼저 붙잡는다.\
  달라지는 것은 `Iterator.remove()` 뿐이다 — `lastReturned.prev` 로 앞 노드를 언제든 알 수 있어 "미리 들고 다니기"가 필요 없고, `unlink` 한 번으로 끝난다.

```java
// DoublyLinkedList.linkBefore — 여기도 "먼저 붙잡기"가 첫 줄이다
private void linkBefore(E element, Node<E> succ) {
    Node<E> pred = succ.prev;        // 먼저 잡는다
    Node<E> newNode = new Node<>(pred, element, succ);
    succ.prev = newNode;
    if (pred == null) {
        head = newNode;              // succ 가 head 였다
    } else {
        pred.next = newNode;
    }
    size++;
}
```

**더 생각할 것**

- 이 규칙은 연결 리스트만의 것이 아니다.\
  트리 회전, 그래프 간선 재배치, 파일 시스템의 inode 조작이 전부 같은 모양의 문제다.
- "먼저 잡아 두는 임시 변수"는 군더더기처럼 보이지만 알고리즘의 본체다.\
  리팩토링으로 없애려 들면 바로 깨진다.
- 실무에서는 순서를 지켜도 **중간에 실패하면** 사슬이 반쯤 고쳐진 상태로 남는다.\
  그래서 DB 나 파일 시스템의 링크 조작은 트랜잭션·저널로 "전부 아니면 전무"를 보장한다(원본에 근거 없음 — 내 추론).

#### 11. 떼어낸 노드의 링크와 `clear()`

- Q: 떼어낸 노드의 `prev`/`next`를 끊지 않으면 무슨 일이 생기는가?\
  A: 그 노드 **하나만** 밖에서 참조되고 있어도 리스트 전체가 GC 되지 않는다.\
  떼어낸 노드가 여전히 다음 노드를 가리키고, 그 노드가 또 다음을 가리키는 사슬이 통째로 살아남기 때문이다.\
  이중 연결이면 `prev` 로 앞쪽까지 붙잡으므로 **양방향으로 전부** 살아남는다.\
  겉으로는 리스트에서 지워졌으니 메모리도 줄었으려니 하고 넘어가서, 전형적인 **조용한 누수**가 된다.

> **GC(가비지 컬렉터)** — 아무도 가리키지 않는 객체를 자동으로 치우는 청소부.\
> 예: 어떤 객체에 도달할 수 있는 참조가 하나라도 남아 있으면 GC 는 그것을 살아 있다고 보고 치우지 않는다.

> **메모리 누수(memory leak)** — 더 이상 쓰지 않는데도 참조가 남아 있어 회수되지 않는 메모리.\
> 예: 리스트에서 뗀 노드의 `next` 를 안 끊으면, 그 노드를 들고 있는 코드 한 곳 때문에 사슬 전체가 회수되지 않는다.

```
떼어낸 노드의 링크를 안 끊으면 — [A,B,C,D] 에서 B 를 뺀 뒤

끊지 않은 경우
   리스트    head -> [A|o]-----------> [C|o]-> [D|/]  <- tail
   떼어낸 B         [B|o]--------------^
                     ^
                     +-- 외부 코드가 B 를 변수 하나로 들고 있다
   결과 : B 가 C 를 붙잡고, C 가 D 를 붙잡는다 -> B 하나 때문에 C, D 가 못 치워진다
          (이중 연결이면 B.prev 로 A 까지 붙잡아 리스트 전체가 살아남는다)

끊은 경우
   리스트    head -> [A|o]-----------> [C|o]-> [D|/]  <- tail
   떼어낸 B         [ |/]      item = null, next = null, prev = null
   결과 : B 는 아무것도 안 가리키고 아무것도 B 를 필요로 하지 않는다
          B 만 회수되고 나머지는 리스트가 정상적으로 붙잡는다
```

```java
// SinglyLinkedList.removeFirst() — 마지막 세 줄이 그 일을 한다
public E removeFirst() {
    if (head == null) throw new NoSuchElementException("비어 있다");
    Node<E> removed = head;
    E value = removed.item;
    head = removed.next;
    if (head == null) tail = null;
    removed.next = null;      // 사슬을 붙잡지 않도록
    removed.item = null;      // 담고 있던 값도 놓아준다
    bumpSize(-1);
    return value;
}
```

- Q: `item` 까지 `null` 로 두는 이유는 무엇인가?\
  A: 노드가 회수되지 않고 어딘가에 남더라도 **담고 있던 값**만큼은 놓아주기 위해서다.\
  값이 큰 객체(이미지 버퍼, 세션 데이터)라면 노드보다 값 쪽이 훨씬 무겁다.\
  `item = null` 은 "이 노드는 더 이상 이 값을 책임지지 않는다"는 선언이다.\
  테스트 `removedNodeIsDetached` 는 `next`(이중은 `prev` 까지)가 `null` 인지를 직접 확인한다.

- Q: `clear()`에서 `head`/`tail`만 `null`로 두면 충분한가?\
  A: 충분하지 않다.\
  리스트 객체에서 보면 비어 보이지만, 노드들은 여전히 서로를 가리키고 있다.\
  그중 **하나라도** 외부에서 참조되고 있으면 사슬 전체가 살아남는다.\
  그래서 `clear()` 는 노드를 하나씩 순회하며 `item`·`next`(·`prev`)를 전부 끊는다 — O(n) 이지만 그 값을 한다.

```java
// DoublyLinkedList.clear() — 사슬을 직접 끊는다
public void clear() {
    Node<E> n = head;
    while (n != null) {
        Node<E> next = n.next;    // 먼저 잡는다 (10번과 같은 규칙)
        n.item = null;
        n.prev = null;
        n.next = null;
        n = next;
    }
    head = null;
    tail = null;
    size = 0;
}
```

```
clear() 를 head/tail 만 null 로 했을 때

   리스트 객체   head = null,  tail = null,  size = 0     <- 비어 보인다
   실제 메모리   [A|o]-> [B|o]-> [C|/]                    <- 사슬은 그대로 살아 있다
                  ^
                  +-- 외부 코드가 A 를 들고 있으면 B, C 까지 전부 못 치운다

clear() 가 사슬을 끊었을 때
   실제 메모리   [ |/]   [ |/]   [ |/]                    <- 서로 안 가리킨다
                  ^
                  +-- A 를 들고 있어도 A 하나만 살아남는다
```

- Q: 자바에 GC 가 있는데도 이런 것을 신경 써야 하는 이유는?\
  A: GC 는 **도달 가능성**만 본다 — "쓸모없다"를 판단하지 않는다.\
  참조가 하나라도 남아 있으면 그 객체는 살아 있는 것으로 취급된다.\
  그래서 "논리적으로 지웠다"와 "물리적으로 회수 가능하다"를 코드가 맞춰 줘야 한다.\
  01번 동적 배열에서 `remove` 후 빈 칸에 `null` 을 넣는 것도 정확히 같은 이유다.

**더 생각할 것**

- 이 누수는 테스트로 잡기 어렵다.\
  기능 테스트는 전부 통과하고 메모리만 안 줄어들기 때문에, 운영 중 힙 덤프를 떠야 보인다.
- 그래서 이 문제집은 `removedNodeIsDetached` 와 `clearDetachesChain` 이라는 **내부 필드를 직접 보는** 테스트를 따로 둔다.\
  `Node` 필드가 패키지 공개인 이유가 이것이다.
- 캐시나 세션 저장소처럼 오래 사는 자료구조에서 특히 위험하다.\
  수명이 긴 구조가 수명이 짧아야 할 객체를 붙잡는 것이 실무 누수의 전형이다.

#### 12. 03-stack 으로의 연결

- Q: 연결 리스트의 한계(인덱스 접근 O(n))가 왜 문제가 되지 않는 자료구조가 있는가?\
  A: 그 자료구조가 **인덱스 접근을 계약에서 아예 빼 버렸기** 때문이다.\
  스택은 `push`/`pop`/`peek` 만 있고 "3번째 원소"를 물어볼 방법이 없다.\
  큐도 `enqueue`/`dequeue`/`peek` 뿐이다.\
  없는 연산은 느릴 수가 없다 — 연결 리스트의 유일한 약점이 계약에서 사라지므로 약점이 아니게 된다.

```
계약이 접근 지점을 제한하면 비용 표가 이렇게 줄어든다

리스트(02)                     스택(03)
  get(i)      O(n)   <- 약점     push   O(1)
  addFirst    O(1)               pop    O(1)
  addLast     O(1)               peek   O(1)
  removeFirst O(1)
  removeLast  O(n)   <- 약점     (get(i) 도 removeLast 도 계약에 없다)
  순회        O(n)

  연결 리스트의 두 약점이 둘 다 "계약에 없는 연산"이 된다.
  스택을 단일 연결로 만들 때 top 을 head 로 잡으면 모든 연산이 O(1) 이다.
```

- Q: 스택을 연결 리스트로 만들 때 주의할 점은?\
  A: **`top` 을 `head` 쪽으로 잡아야 한다**는 것이다.\
  `head` 를 `top` 으로 쓰면 `push` = `addFirst`, `pop` = `removeFirst` 라 둘 다 O(1) 이다.\
  `tail` 을 `top` 으로 잡으면 `pop` = `removeLast` 가 되어 단일 연결에서 O(n) 이 된다 — 7번의 그 약점이 그대로 튀어나온다.\
  같은 자료구조인데 "어느 끝을 쓰느냐"만으로 O(1)과 O(n)이 갈린다.

- Q: 큐라면 어느 끝을 쓰는가?\
  A: 넣는 쪽은 `tail`(`addLast`), 빼는 쪽은 `head`(`removeFirst`) 다 — 둘 다 O(1) 이다.\
  반대로 잡으면 `dequeue` 가 `removeLast` 가 되어 단일 연결에서 O(n) 이다.\
  즉 단일 연결 리스트 하나로 스택과 큐가 둘 다 되는데, 방향 선택만 틀리지 않으면 된다.\
  양쪽 끝에서 모두 빼야 하는 덱(Deque)이라면 `prev` 가 필요하므로 이중 연결이어야 한다.

- Q: 접근 지점을 양 끝으로 제한하면 배열 구현과 연결 구현 중 무엇이 유리해지는가?\
  A: **둘 다 O(1)이 되어 복잡도로는 갈리지 않는다** — 그래서 판단 기준이 복잡도에서 다른 것으로 옮겨간다.\
  배열이 유리한 점 — 메모리가 연속이라 캐시가 잘 듣고, 노드 객체 오버헤드가 없으며, 원소당 메모리가 훨씬 적다.\
  연결이 유리한 점 — 확장 시 전체 복사가 없어 **최악 지연이 튀지 않고**, 용량 한계가 없으며, 미리 크기를 정할 필요가 없다.\
  실무에서는 대개 배열 쪽이 이긴다 — 총 처리량과 메모리가 중요하고, 확장 지연이 문제 되는 상황이 드물기 때문이다(원본에 근거 없음 — 내 추론).

> **상환 O(1)(amortized)** — 연속된 n 번의 연산 총비용이 O(n) 이라 1회 평균이 O(1) 이라는 뜻.\
> 예: 배열 스택의 `push` 는 확장이 걸리는 그 한 번만 O(n) 이고 나머지가 O(1) 이라 평균으로는 O(1)이다.

> **꼬리 지연(tail latency, p99/p999)** — 느린 쪽 상위 1%·0.1% 요청이 실제로 얼마나 걸리는지를 보는 지표.\
> 예: 배열 확장의 전체 복사 한 번이 평균에는 안 보이지만 p999 에는 그대로 찍힌다.

| | 배열 기반 스택/큐 | 연결 기반 스택/큐 |
|---|---|---|
| push / pop | 상환 O(1) | 언제나 O(1) |
| 최악 한 번의 비용 | 확장 시 O(n) | O(1) |
| 원소당 메모리 | 값(+빈 칸) | 값 + 노드 객체 + 참조 |
| 캐시 | 지역성 좋음 | 포인터 추격 |
| 용량 | 확장 필요 | 제한 없음 |
| 큐로 쓸 때 | 원형 버퍼가 필요 | head/tail 로 자연스럽게 |

> **원형 버퍼(circular buffer)** — 배열의 끝과 처음을 이어 붙은 것처럼 쓰는 기법.\
> 예: 배열로 큐를 만들면 앞에서 빼는 자리가 계속 비므로, 인덱스를 `% 길이` 로 감아 그 빈 앞부분을 재사용한다.

**더 생각할 것**

- 03-stack 에서 01번과 02번이 만난다 — 같은 계약을 배열과 연결 두 가지로 구현하면서, 지금까지 배운 두 저장 방식의 차이가 같은 표 위에 놓인다.
- 자료구조 설계에서 **계약을 좁히는 것 자체가 최적화**다.\
  할 수 있는 일을 줄이면 구현이 고를 수 있는 선택지가 늘어난다.
- 인터페이스에 `get(i)` 하나를 추가하는 순간 연결 구현이 다시 불리해진다.\
  "편의를 위해 메서드 하나쯤"이 구현 선택지를 좁히는 일이 실제로 자주 벌어진다.
- 그래서 스택·큐에 순회(`Iterator`)를 넣지 않은 것도 같은 맥락이다.\
  순회를 허용하면 "양 끝으로만 접근한다"는 약속이 깨지고, 그 약속에서 나오던 구현 자유도도 사라진다.
