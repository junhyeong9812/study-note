### A. 문제

#### 1. 편집 목록을 순서대로 적용한다 — `applyEdits`

**접근 1 — 저장소를 고치고 반환값을 버린다** (계약을 못 읽으면 가장 먼저 떠오른다)

```java
// 하면 안 되는 구현
for (Edit edit : edits) {
    switch (edit) {
        case Edit.Insert i -> doc.insert(i.index(), i.text());   // 반환값을 버렸다
        case Edit.Delete d -> doc.delete(d.from(), d.to());
    }
}
return doc;
```

- 한계: `CharSequenceStore` 의 계약은 **값(value)** 이다 — 모든 편집 연산이 저장소를 돌려주고, 호출자는 언제나 그 반환값을 써야 한다.
- 한계: `Rope` 도 `StringBuilderStore` 도 자기 자신을 고치지 않는다.\
  둘 다 새 객체를 만들어 돌려주므로 반환값을 버리면 편집이 **한 건도 반영되지 않는다**.
- 한계: 그런데 컴파일은 되고 예외도 없다 — 답만 틀린다.

**접근 2 — 반환값을 다음 편집의 입력으로 넘긴다** (impl 의 정답)

```java
public static CharSequenceStore applyEdits(CharSequenceStore doc, List<Edit> edits) {
    if (doc == null || edits == null) {
        throw new IllegalArgumentException("문서와 편집 목록이 필요하다");
    }
    CharSequenceStore current = doc;
    for (Edit edit : edits) {
        current = switch (edit) {
            case Edit.Insert i -> current.insert(i.index(), i.text());
            case Edit.Delete d -> current.delete(d.from(), d.to());
        };
    }
    return current;
}
```

- 논리: `current` 가 "지금까지의 편집이 다 반영된 문서"라는 불변식을 들고 한 칸씩 전진한다.
- 논리: `Edit` 는 `sealed interface` 라 `Insert` 와 `Delete` 둘뿐이고, 스위치가 두 갈래를 다 덮으므로 default 가 필요 없다.
- 논리: 편집 목록이 비면 루프가 안 돌고 받은 객체가 그대로 나간다 — 테스트가 `assertSame(doc, applyEdits(doc, List.of()))` 로 그것을 단언한다.

> **값 계약(value semantics)** — 연산이 대상을 고치지 않고 결과를 새 값으로 돌려주는 계약.\
> 예: `rope.insert(3, "x")` 는 `rope` 를 그대로 두고 새 로프를 돌려주므로 반환값을 안 받으면 아무 일도 안 한 것이 된다.

- Q: "반환값을 다음 편집에 넘긴다"가 왜 **계약의 일부**인가?\
  A: 구현이 자기를 고칠지 새 것을 만들지를 호출자가 알 수 없게 인터페이스가 설계됐기 때문이다.\
  `CharSequenceStore` 의 주석이 그 자리를 못 박았다 — "구현이 새 것을 만들어 줄 수도 있고 자기 것을 고쳐 줄 수도 있는데, 그 차이가 이 문제의 절반이다. 옛 참조를 계속 쓰면 어느 쪽인지에 따라 답이 달라진다".\
  반환값을 쓰는 코드는 **양쪽 구현 모두에서 옳고**, 옛 참조를 쓰는 코드는 한쪽에서만 우연히 맞는다.\
  그리고 로프의 이득(옛 버전이 그대로 살아 있다)은 이 계약 위에서만 성립한다.

**편집 m 개를 n 자 문서에 적용할 때 총 복사량**

```
같은 편집 1000번을 두 저장소에 똑같이 준다 (4096자 문서, leafMax 32, 흩뿌린 자리)

  StringBuilderStore   4,595,500 글자
  Rope                    12,502 글자          367 배

  RopeProblemsTest.copyCostOfTheSameEdits
      assertEquals(12_502, rope.charsCopiedTotal());
      assertEquals(4_595_500, sb.charsCopiedTotal());
      assertEquals(367, sb.charsCopiedTotal() / rope.charsCopiedTotal());

  4,595,500 은 손으로 나온다:
      편집 i 번째 시점의 문서 길이가 4096 + i 이고 매번 그 전부를 새 버퍼로 옮긴다
      sum(i=0..999) (4096 + i) = 1000 x 4096 + (0+1+...+999)
                               = 4,096,000 + 499,500 = 4,595,500
```

- 기준선이 그렇게 되는 이유: `StringBuilderStore.insert` 가 **길이 n + s 짜리 새 버퍼를 만들어 앞 조각·넣을 글자·뒤 조각을 차례로 담고** `copied = n` 을 기록한다.\
  즉 편집 한 번에 문서 전체다 — 총합이 `Σ(문서 길이)` 라 `O(m x n)` 이다.
- 로프가 그렇게 되는 이유: `insert` 가 실제로 옮기는 글자는 **쪼개진 잎 하나**뿐이다.

```java
public Rope insert(int index, String s) {
    // ... 검사 생략
    long[] copied = new long[1];
    Node[] parts = splitNode(root, index, copied);   // 쪼개진 잎 하나만 copied 에 더해진다
    Node middle = buildLeaves(s, leafMax, copied);   // s 가 leafMax 이하면 여기서도 0
    Node next = concatNodes(concatNodes(parts[0], middle), parts[1]);
    return new Rope(next, leafMax, copied[0], copiedTotal);
}
```

```java
static Node[] splitNode(Node node, int index, long[] copied) {
    if (index == 0) {
        return new Node[]{EMPTY, node};              // 경계 -> 복사 0
    }
    if (index == node.length) {
        return new Node[]{node, EMPTY};              // 경계 -> 복사 0
    }
    if (node.isLeaf()) {
        copied[0] += node.length;                    // 여기서만 글자가 움직인다
        return new Node[]{new Node(node.text.substring(0, index)),
                new Node(node.text.substring(index))};
    }
    if (index < node.weight) { ... }                 // 왼쪽으로 내려간다
    if (index > node.weight) { ... }                 // 오른쪽으로 내려간다
    return new Node[]{node.left, node.right};        // 정확히 경계 -> 복사 0
}
```

- 그래서 로프의 총 복사량은 **문서 길이 n 과 무관**하고 `편집 수 x 잎 크기` 언저리다 — `O(m x leafMax)`.
- 10만 자 문서에서 같은 실험을 하면 기준선은 `100,499,500`(= `Σ(i=0..999)(100000+i)` = 100,000,000 + 499,500), 로프는 흩뿌려 쳐도 `29,376` 이다.\
  `29,376 / 32 = 918` — 1000번의 삽입 중 918번이 32자짜리 잎을 통째로 쪼갰고 나머지 82번은 이미 잎 경계라 공짜였다는 뜻이다.
- 커서가 한 자리에 머물면 로프는 **32 글자**로 끝난다 — 처음 한 번만 잎을 쪼개고 그 뒤로는 그 자리가 이미 잎 경계다(`thousandKeystrokesInTheMiddle`).

> **잎(leaf)과 내부 노드(internal node)** — 글자를 실제로 들고 있는 맨 아래 노드와, 글자 없이 자식 둘과 `weight` 만 들고 있는 위 노드.\
> 예: `Node(String text)` 로 만들면 잎이고 `Node(Node left, Node right)` 로 만들면 내부 노드다.

**질문별 답**

- Q: 문제 1을 어떻게 푸는가?\
  A: `current` 변수 하나를 두고 편집을 앞에서부터 적용하되 **매번 반환값을 `current` 에 다시 담는다**.\
  `Edit` 가 sealed 라 `Insert` / `Delete` 두 갈래 스위치면 끝이고, 빈 목록이면 받은 객체가 그대로 나간다.
- Q: 총 복사량이 각각 어떻게 되는가?\
  A: `StringBuilderStore` 는 편집마다 문서 전체라 `Σ(문서 길이)` = `O(m x n)` — 4096자·1000편집에서 4,595,500 글자다.\
  `Rope` 는 편집마다 쪼갠 잎 하나라 `O(m x leafMax)` — 같은 조건에서 12,502 글자이고 문서가 커져도 거의 안 늘어난다.
- Q: 왜 그렇게 갈리는가?\
  A: 배열은 **글자를 연속으로 놓겠다는 약속**을 지켜야 해서 한 칸을 끼워 넣으려면 뒤를 전부 밀어야 한다.\
  트리는 그 약속을 버리고 "어느 조각이 어느 순서로 오는가"만 유지하므로, 조각의 연결만 바꾸면 글자는 제자리에 둔 채 문서가 달라진다.

**더 생각할 것**

- 두 구현의 복사량을 같은 자로 재기 위해 `StringBuilderStore` 도 일부러 제자리 편집을 안 한다.\
  그 이유가 javadoc 에 적혀 있다 — "계약이 값이기 때문이다… 제자리 편집을 허용해도 가운데 삽입이 O(n) 이라는 사실은 안 바뀐다".
- 시간이 아니라 글자 수를 세는 이유는 27번에서 비교 횟수를 센 것과 같다.\
  기계·JIT·GC 가 흔들어도 값이 안 변해야 단언에 쓸 수 있다.
- 편집 목록을 값으로 들고 다니는 형태(`List<Edit>`)는 그 자체로 되돌리기·재생·전송의 단위가 된다.\
  협업 편집기가 이 모양에서 출발한다(원본에 근거 없음 — 내 추론).

#### 2. 두 문서의 공통 접두사 — `longestCommonPrefix`

**접근 1 — 한 글자씩 `charAt` 으로 비교한다** (나이브. 답은 맞는다)

```java
public static Lcp naiveLongestCommonPrefix(CharSequenceStore a, CharSequenceStore b) {
    int n = Math.min(a.length(), b.length());
    long compared = 0;
    for (int i = 0; i < n; i++) {
        compared++;
        if (a.charAt(i) != b.charAt(i)) {
            return new Lcp(i, compared);
        }
    }
    return new Lcp(n, compared);
}
```

- 비용(왜): 비교가 최대 `min(|a|,|b|) + 1` 번이고, 로프에서는 `charAt` 자체가 O(log n) 이라 총 `O(k log n)` 이다.
- 한계: 두 문서가 같은 문서에서 갈라져 나왔다는 사실을 하나도 못 쓴다.

**접근 2 — 같은 노드 객체를 만나면 그 부분트리를 통째로 건너뛴다** (impl 의 정답)


- 논리: 로프의 `Node` 는 모든 필드가 `final` 이고 아무도 고치지 않는다.\
  그래서 **"참조가 같다 ⇒ 내용이 같다"** 가 성립한다 — 26번 영속 자료구조와 같은 추론이다.
- 논리: 두 스택을 왼쪽부터 동시에 훑되, 양쪽 버퍼를 다 소진한 **노드 경계**에서만 그 지름길을 쓴다.\
  경계가 아니면 글자 단위로 비교해야 자리가 어긋나지 않기 때문이다.
- 논리: 지름길이 안 걸리면 잎 텍스트를 버퍼에 담아 겹치는 만큼(`step`) 한 글자씩 비교한다.

> **구조 공유(structural sharing)** — 새 버전이 옛 버전의 노드를 복사하지 않고 같은 객체로 가리키는 것.\
> 예: `base.insert(4096, "1")` 로 만든 로프는 4096자 전체를 `base` 의 뿌리 노드 **그 객체**로 들고 있다.

**33 글자만 비교하는 근거와 그 33의 정체**

- 33 = **잎 하나(32) + 갈리는 첫 글자(1)** 다.\
  지름길이 "양쪽 버퍼가 비었을 때"만 발동하므로 첫 잎 한 개는 언제나 글자 단위로 비교하게 된다.
- 가운데를 고친 쌍(`base.insert(2048, ...)`)도 33이고 답의 길이만 2048로 바뀐다.\
  맨 앞을 고친 쌍은 첫 글자에서 갈려 비교가 **1** 이다.
- "124배"는 테스트 메시지 문자열에만 있고 단언되지 않는다 — 단언된 값은 33 과 4097 이다.

- Q: 로프 둘일 때 나이브보다 적게 비교할 수 있는 근거는?\
  A: **불변 + 구조 공유**다.\
  아무도 노드를 고치지 않으므로 두 트리에서 같은 객체를 만나면 그 밑 글자 전체가 같다고 **비교 없이** 단정할 수 있다.\
  27번 머클 트리가 "부모 해시가 같으면 밑이 같다"로 가지를 잘랐던 것과 정확히 같은 모양이고, 여기서는 해시 대신 **객체 동일성**이 그 역할을 한다.
- Q: 그 근거가 성립하지 않는 입력은?\
  A: **편집 이력이 없는 두 로프**다 — 같은 문자열로 따로 만들면 노드가 공유되지 않아 나이브와 똑같이 4097번 비교한다.\
  기준선처럼 배열을 복사해 만든 저장소도 마찬가지다.\
  즉 이 최적화는 자료구조의 성질이 아니라 **두 값의 계보**에 달려 있다.
- Q: 비용은 왜 그런가?\
  A: 지름길이 걸리는 경우 비용은 "갈린 지점까지 내려간 경로 + 실제로 비교한 잎"에 비례한다.\
  갈리는 자리가 하나면 경로가 O(log n) 이고 비교는 잎 한두 개라 `O(log n + leafMax)` 언저리다.\
  지름길이 하나도 안 걸리면 최악에 `O(k)` 로 나이브와 같다 — **상한은 나이브와 같고 아래로만 좋아진다**.

**더 생각할 것**

- "참조가 같으면 내용도 같다"는 **불변일 때만** 참인 추론이다.\
  가변 구조에서 같은 최적화를 하면 조용히 틀린 답을 낸다 — 이 한 줄이 26번·28번을 관통한다.
- 반대 방향은 성립하지 않는다 — 내용이 같아도 참조는 다를 수 있다.\
  그래서 이 알고리즘은 "빠르면 이득, 아니면 본전"이라는 한쪽 방향의 최적화다.
- 27번의 `diffBlocks` 와 나란히 놓으면, 둘 다 "덩어리가 같다는 것을 싸게 확인해 통째로 건너뛴다"는 같은 전략이다.\
  다른 것은 그 확인 수단(해시 대 참조)과 그 수단이 요구하는 조건(충돌 저항성 대 불변성)이다.

### B. 자료구조 특성

#### 3. 로프가 왜 필요한가

- Q: 01번 동적 배열과 자바 `String`/`StringBuilder` 로는 무엇이 안 되는가?\
  A: **가운데 편집이 전부 O(n)** 이라는 것이 안 고쳐진다.\
  셋은 전부 글자를 메모리에 **연속으로** 놓는다 — 연속이라는 약속 덕에 `charAt` 이 O(1) 인데, 바로 그 약속 때문에 한 칸을 끼워 넣으려면 뒤를 전부 밀어야 한다.\
  `String` 은 불변이라 이어붙이기마다 전체를 새로 복사하고, `StringBuilder` 는 끝에 붙이는 것만 상환 O(1) 이지 가운데는 여전히 뒤를 민다.
- Q: 10MB 문서 가운데에 한 글자를 넣는 일이 세 구조에서 각각 몇 글자를 옮기는가?\
  A: README 의 도입부가 그 셋을 적어뒀다 — `String` 은 **10MB 전부**, `StringBuilder` 는 **뒤쪽 5MB**, 로프는 잎 하나(이 구현이면 `leafMax` 글자)다.\
  그리고 그것이 **타자 한 번마다** 일어난다.\
  (10MB 규모를 직접 재는 테스트는 없다 — 테스트의 최대 규모는 10만 자다. 위 셋 중 테스트로 확인되는 것은 로프 쪽의 "잎 하나"이고 `assertEquals(32, rope.charsCopiedTotal())` 이 그 값이다.)

```
문서: [ ............ 10,000,000 글자 ............ ]
                        ^ 여기에 'x' 한 글자

  String          새 문자열을 만들어 10,000,000 글자를 전부 옮긴다
  StringBuilder   가운데부터 뒤 5,000,000 글자를 한 칸씩 민다
  Rope            그 자리를 품은 잎(32글자)만 둘로 쪼개고 조각을 다시 매단다
                  -> 나머지 9,999,968 글자는 그 자리에 그대로 있다
```

- Q: 로프는 그 대신 무엇을 내주는가?\
  A: **임의 접근**이다 — `charAt` 이 O(1) 에서 O(log n) 이 된다.\
  10만 자 문서를 끝까지 `charAt` 으로 읽으면 노드를 1,268,928 번 지나고, 조회 한 번에 평균 12.7 노드다(테스트는 정수 몫 `assertEquals(12, visits / 100_000)` 를 단언한다).\
  배열이었으면 1 이다.

> **로프(rope)** — 문자열을 조각으로 나눠 이진 트리의 잎에 담고, 내부 노드는 왼쪽 부분트리의 길이만 들고 있는 자료구조.\
> 예: `"Hello world"` 를 `["Hello ", "world"]` 두 잎으로 나누고 뿌리가 `weight = 6` 을 든다.

> **weight(왼쪽 길이)** — 내부 노드가 들고 있는, 자기 왼쪽 부분트리의 글자 수.\
> 예: `charAt(i)` 는 `i < weight` 면 왼쪽, 아니면 `i -= weight` 하고 오른쪽으로 내려간다.

**더 생각할 것**

- "연속으로 놓는다"는 결정 하나가 조회를 싸게 하고 편집을 비싸게 한다.\
  01번과 28번은 같은 데이터에 대해 그 결정을 반대로 내린 두 구조다(질문 8).
- 실제 에디터는 로프 말고도 gap buffer·piece table 을 쓴다.\
  셋 다 "한 번에 바뀌는 곳은 좁다"는 같은 관찰에서 출발한다(원본에 근거 없음 — 내 추론).
- 트리로 옮기면 편집이 싸지는 대신 **메모리 상수**가 커진다.\
  4096자를 leafMax 1 로 담으면 노드가 8191개다 — 글자 하나에 객체 두 개꼴이다(질문 7).

#### 4. 어떤 데이터와 접근 패턴에 적합하고 언제 쓰면 안 되는가

- Q: 어떤 데이터·접근 패턴에 적합한가?\
  A: **문서가 크고, 편집이 잦고, 편집 지점이 좁고, 옛 버전을 들고 있고 싶을 때**다.\
  텍스트 에디터·협업 편집기·대용량 로그 뷰어가 그 모양이고, 특히 "타자 한 번 = 편집 한 번"이라 편집 수 m 이 매우 큰 워크로드가 이 구조의 자리다.\
  여기에 실행 취소(undo)가 붙으면 이득이 한 번 더 커진다 — 버전 1000개를 다 들고 있어도 로프가 옮긴 글자는 12,502 개이고 기준선은 4,595,500 개다.
- Q: 읽기가 압도적으로 많으면 왜 배열이 이기는가?\
  A: 로프는 **읽기마다 트리를 내려가기 때문**이다.\
  배열의 `charAt` 은 주소 계산 한 번이라 노드 방문이 1인데, 로프는 4096자·leafMax 32 에서 조회 한 번에 8 노드를 지난다(깊이 7 + 잎 1).\
  게다가 노드가 힙에 흩어져 있어 캐시 지역성이 나쁘다 — 걸음 수보다 실제 시간이 더 벌어진다.\
  편집이 없으면 그 비용을 회수할 이득 자체가 없으므로, 읽기 전용 문자열은 배열로 두는 것이 옳다.
- Q: 작은 문서에서 로프가 지는 이유는(한계 1)?\
  A: **트리를 유지하는 값이 이득보다 크기 때문**이다.\
  10글자 문서에서 세 글자를 지우면 로프는 잎 둘을 쪼개느라 8글자를 옮기고, 기준선은 7글자만 옮긴다.

```
  "abcdefghij" (leafMax 4) -> 잎 ["abcd"]["efgh"]["ij"]
  delete(3, 6) 을 시킨다

  Rope        splitNode(3) 이 "abcd" 를 쪼개고(4글자 복사)
              splitNode(3) 이 "efgh" 를 쪼갠다(4글자 복사)      -> 합계 8
  기준선      남는 7글자를 새 버퍼에 담는다                      -> 합계 7

  CopyCostTest.ropeLosesOnSmallDocuments
      assertEquals(8, ...);  assertEquals(7, ...);
      assertTrue(로프 > 기준선)
```

- Q: 그 밖에 언제 쓰면 안 되는가?\
  A: 셋 더 있다.\
  첫째, **문서 전체를 자주 문자열로 뽑아 쓸 때** — `toString` 이 잎을 전부 훑어 새 버퍼를 만드는 O(n) 이라 이득이 사라진다.\
  둘째, **깊이가 깊어질 수 있는데 자동 균형이 없을 때**(한계 3, 질문 6).\
  셋째, **편집 지점이 넓을 때** — 문서의 절반을 한 번에 갈아치우면 쪼개고 붙이는 이득이 없다(원본에 근거 없음 — 내 추론).

**더 생각할 것**

- "적합한가"의 기준은 자료의 크기가 아니라 **편집 대 조회의 비율**이다.\
  같은 10만 자 문서라도 편집기에서는 로프가 이기고 읽기 전용 뷰어에서는 배열이 이긴다.
- 실무 에디터는 둘을 섞는다 — 화면에 보이는 구간만 평평한 버퍼로 캐시하고 문서 본체는 트리로 둔다(원본에 근거 없음 — 내 추론).
- 손익분기는 leafMax 에도 걸린다.\
  leafMax 를 키우면 작은 문서에서 배열과 같아지고(잎 하나짜리 로프는 배열과 같은 값을 낸다), 줄이면 편집은 싸지고 조회가 비싸진다(질문 7).

#### 5. `concat` O(1), `insert`/`delete` O(log n), `charAt` O(log n) 의 구조적 이유

- Q: 내부 노드가 `weight` 하나만 들고 있다는 사실에서 셋이 각각 어떻게 따라 나오는가?\
  A: `weight` 는 **왼쪽 부분트리의 길이**이고, 이 값 하나면 "i 번째 글자가 왼쪽에 있나 오른쪽에 있나"를 O(1) 에 판정할 수 있다.\
  그 판정을 깊이만큼 반복하는 것이 `charAt` 이고, 그 판정으로 자를 자리를 찾아 내려가는 것이 `splitNode` 이며, 자를 필요 없이 새 뿌리 하나만 얹는 것이 `concat` 이다.

```java
// charAt — 재귀가 아니라 반복문이다 (깊이가 10만이어도 스택이 안 터진다)
Node node = root;
int i = index;
while (!node.isLeaf()) {
    visits++;
    if (i < node.weight) {
        node = node.left;          // 왼쪽에 있다 — i 는 그대로
    } else {
        i -= node.weight;          // 오른쪽에 있다 — 왼쪽 길이만큼 빼고 내려간다
        node = node.right;
    }
}
```

```
"Hello_World_of_the_Rope" 를 잎 넷으로 담은 로프에서 charAt(14)

                (weight=12, len=23)
                /                  \
      (weight=6, len=12)      (weight=7, len=11)
       /        \               /          \
  "Hello_"   "World_"      "of_the_"      "Rope"
   (6)         (6)           (7)           (4)

  뿌리   : 14 >= 12 -> 오른쪽, i = 14 - 12 = 2
  오른쪽 : 2 < 7   -> 왼쪽
  잎     : "of_the_".charAt(2) = '_'      (문서 전체로 세어도 14번째 글자가 '_' 다)

  방문 노드 3개 = 깊이 2 + 잎 1  -> O(log n)
```

- `concat` 이 O(1) 인 이유: 새 내부 노드 하나를 만들어 양쪽을 자식으로 삼으면 끝이다.\
  `weight = left.length` 는 이미 알고 있는 값이라 계산이 없고, **글자는 한 개도 안 움직인다**.

```java
static Node concatNodes(Node a, Node b) {
    if (a.length == 0) return b;
    if (b.length == 0) return a;
    return new Node(a, b);       // 노드 하나 할당이 전부다
}
```

- `insert`/`delete` 가 O(log n) 인 이유: 둘 다 `splitNode` 위에 얹혀 있고, `splitNode` 는 **뿌리에서 자를 자리까지 한 갈래로 내려가며** 돌아오는 길에 노드를 다시 매단다.\
  내려간 경로 길이가 깊이라 `O(log n)` 개의 새 내부 노드가 생기고, 실제 글자 복사는 쪼개진 잎 하나뿐이다.\
  `insert` = split 1 + concat 2, `delete` = split 2 + concat 1 이다.
- Q: `concat` 의 복사가 0인 근거로 "불변"이 왜 필요한가?\
  A: 복사하지 않는다는 말은 **두 로프가 같은 노드를 동시에 가리킨다**는 뜻이기 때문이다.\
  누군가 그 노드를 고칠 수 있으면 한쪽을 고쳤을 때 다른 쪽 문서가 조용히 바뀐다 — 그 순간 "양쪽 다 안 바뀐다"는 `concat` 의 계약이 깨진다.\
  `Node` 의 여섯 필드가 전부 `final` 이고 로프가 `final class` 인 것이 그 계약의 코드 쪽 표현이고, 26번 영속 자료구조가 서 있던 바로 그 자리다.

```
4096자 문서(leafMax 32, 노드 255개) 를 한 번 고친다

  Rope edited = base.insert(2050, "X");

  base   노드 255개
  edited 노드 259개  그중 247개가 base 와 **같은 객체**
                     새로 만든 12개 = 쪼갠 잎 2개 + 넣은 잎 1개 + 경로의 내부 노드들
  옮긴 글자 32개     (쪼갠 잎 하나)

  RopeStructureTest.editSharesAlmostEverything
      assertEquals(255, base.nodeCount());
      assertEquals(259, edited.nodeCount());
      assertEquals(247, sharedNodeCount(base, edited));
      assertEquals(32, edited.charsCopiedByLastOp());
```

> **불변(immutable)** — 한 번 만든 뒤 내용이 절대 바뀌지 않는 것.\
> 예: `Rope.Node` 의 `text·left·right·weight·length·depth` 가 전부 `final` 이라 고칠 방법이 문법적으로 없다.

**더 생각할 것**

- 셋의 비용이 전부 "깊이"로 환원된다는 것이 이 구조의 요약이다.\
  그래서 깊이가 망가지면 셋이 동시에 망가진다(질문 6).
- `weight` 가 **왼쪽 길이**이지 전체 길이가 아닌 것이 중요하다.\
  전체 길이는 `length` 로 따로 들고 있는데, 탐색에 쓰는 것은 왼쪽 길이 하나다 — 13번 세그먼트 트리가 구간 합을 들고 내려가며 자르는 것과 같은 모양이다.
- `substring` 은 O(log n + 길이) 다.\
  경로를 타고 내려가 겹치는 잎만 이어 붙이기 때문인데, 결과 문자열을 실제로 만들어야 하므로 길이 항은 피할 수 없다.

#### 6. 최악의 사용 패턴과 최선

- Q: 앞에만 1000번 이어붙이면 깊이가 얼마가 되고 옮긴 글자는 몇인가?\
  A: 깊이 **999**, 옮긴 글자 **0** 이다.

```java
Rope rope = new Rope("", 32);
for (int i = 0; i < 1000; i++) {
    rope = new Rope(TestText.of(4), 32).concat(rope);   // 앞에만 붙인다
}
// assertEquals(999, rope.depth());     assertEquals(0, rope.charsCopiedTotal());
// assertEquals(1000, rope.leafCount()); assertEquals(1999, rope.nodeCount());
```

```
  한쪽으로만 붙이면 트리가 한 줄이 된다

      (new)                          이어붙이기 한 번 = 뿌리 하나 추가 = 깊이 +1
      /   \
   잎    (이전 뿌리)
          /      \
        잎     (이전 뿌리)
                /     \
              잎     ...

  1000번 붙이면 깊이 999, 노드 1999(잎 1000 + 내부 999), 복사 0
  기준선은 같은 일에 5,005,000 글자를 옮긴다
      10 + 20 + ... + 10000 = 10 x (1+2+...+1000) = 10 x 500,500 = 5,005,000
```

> **깊이(depth)** — 뿌리에서 가장 먼 잎까지의 간선 수.\
> 예: 앞에만 1000번 이어붙인 로프의 깊이는 999 이고, `rebalance()` 뒤에는 10 이다.

- Q: 그래서 "공짜가 아니라 외상"이라는 말은 무슨 뜻인가?\
  A: `concat` 이 내지 않은 비용이 **깊이**로 쌓여 나중에 청구된다는 뜻이다.\
  깊이가 999면 `charAt` 한 번에 노드를 1000개 지난다 — O(log n) 이어야 할 조회가 O(n) 이 된다.
- Q: 그 외상이 어디서 청구되는가(한계 3)?\
  A: **재귀로 짠 연산들의 스택**이다.\
  `toString`(`appendAll`)·`collectLeaves`·`nodeCount`·`countLeaves` 가 전부 재귀라 깊이만큼 스택 프레임을 쌓는다.\
  README 는 이 기계에서 **깊이 19,628 은 살고 19,726 에서 `StackOverflowError`** 라고 적었다 — 다만 이 두 수는 **테스트에 단언되어 있지 않다**(기계·JVM 스택 크기에 따라 달라지는 측정값이라 단언할 수 없다).\
  반면 `charAt` 은 반복문이라 깊이가 커도 산다 — 테스트는 10만 번 앞붙이기로 **깊이 99,999** 를 만들고 그 상태에서 `charAt(0)` 과 `charAt(99_999)` 가 정상 동작함을 단언한다(README 가 적은 78,903 보다 강한 사실이 테스트에 있다).
- Q: `rebalance()` 가 무엇을 고치고 무엇을 못 고치는가(한계 4)?\
  A: **모양은 고치고 잎은 못 고친다**.

```java
public Rope rebalance() {
    List<Node> leaves = new ArrayList<>();
    collectLeaves(root, leaves);                 // 기존 잎 "객체"를 순서대로 모은다
    Node next = leaves.isEmpty() ? EMPTY : balancedOver(leaves, 0, leaves.size());
    return new Rope(next, leafMax, 0, copiedTotal);   // 복사 0
}
```

```
  깊이 999 짜리 로프를 rebalance 하면

      깊이      999  ->  10          (잎 1000개의 균형 트리 높이)
      잎 개수  1000  ->  1000         그대로
      노드 수  1999  ->  1999         그대로. 내부 노드 999개만 새로 만든다
      옮긴 글자   0  ->  0            잎 객체를 그대로 다시 매단다
      공유       -      잎 1000개가 같은 객체다 (rebalanceReusesLeaves)

  못 고치는 것: 잘게 부서진 잎
      편집을 반복하면 잎이 1글자짜리까지 쪼개지는데 rebalance 는 그것을 합치지 않는다
      합치려면 글자를 새 버퍼로 옮겨야 하고, 그 순간 "복사 0" 이 깨진다
```

- 잎이 잘게 부서지는 것이 왜 문제인가: 잎 수가 늘면 깊이도 늘어 조회가 비싸진다.\
  같은 자리를 1000번 치면 잎이 4126개가 되고 깊이가 513이 된다(`middleEditsLeanToo`) — rebalance 뒤에도 깊이 13이라 처음의 12보다 크다.
- Q: 반대로 최선은 어떤 편집 패턴인가?\
  A: **같은 자리를 계속 치는 것**이다 — 두 번째부터 복사가 0이다.\
  처음 한 번은 그 자리를 품은 잎(32글자)을 쪼개야 하지만, 쪼개고 나면 커서 자리가 **이미 잎 경계**라 `splitNode` 의 `index == node.weight` / `index == node.length` 지름길로 빠져 복사가 0이 된다.\
  10만 자 문서 한가운데를 1000번 쳐도 로프가 옮긴 글자는 **32** 다.
- 최악의 조합은 "커서를 문서 전역에 흩뿌리는 편집"이다 — 매번 새 잎을 쪼개야 해서 1000번 중 918번이 32글자를 옮긴다(29,376 글자).\
  그래도 기준선의 100,499,500 글자에 비하면 3421배 싸다.

**더 생각할 것**

- 이 구조의 최악은 "데이터"가 아니라 **연산의 순서**가 만든다.\
  같은 1000번의 편집이라도 어디를 치느냐에 따라 32 글자와 29,376 글자로 갈린다.
- `rebalance` 를 언제 부를지는 자료구조가 아니라 호출자가 정한다.\
  실무 구현이 자동 균형을 거는 이유가 그것이고, 이 문제집은 일부러 수동으로 두어 "외상"을 눈에 보이게 했다.
- 06번 BST·23번 스플레이 트리와 같은 자리다 — 균형을 안 잡으면 정렬된(한쪽으로 치우친) 입력에서 트리가 한 줄이 된다.\
  30번 인터벌 트리도 같은 함정을 그대로 안고 있다.

#### 7. `leafMax` 의 트레이드오프

- Q: 1 / 4 / 32 / 256 / 4096 에서 노드 수·조회 방문 노드·편집 복사량이 어떻게 움직이는가?\
  A: 아래 표가 전부다 — **작으면 노드가 폭발하고 크면 복사가 폭발한다**.

```
4096자 문서를 짓고, 전체를 한 번 훑고(4096번 조회), 정해진 자리 200곳에 한 글자씩 넣는다

  leafMax   깊이   노드 수   4096번 조회의 방문 노드   편집 200번이 옮긴 글자
  -------   ----   -------   -----------------------   ----------------------
        1     12      8191                   53,248                        0
        4     10      2047                   45,056                      536
       32      7       255                   32,768                    4,902
      256      4        31                   20,480                   17,834
     4096      0         1                    4,096                   48,931

  RopeStructureTest.theTable 이 다섯 줄 전부를 정확값으로 단언한다
  (깊이 열과 "편집 후 노드 수" 열은 테스트에만 있고 README 표에는 없다)

  방문 노드는 손으로 나온다 : 4096 x (깊이 + 1)
      leafMax 32  -> 4096 x 8  = 32,768
      leafMax 1   -> 4096 x 13 = 53,248
      leafMax 256 -> 4096 x 5  = 20,480
      leafMax 4096-> 4096 x 1  =  4,096
```

- 노드 수도 손으로 나온다: 잎이 `4096 / leafMax` 개이고 완전 이진 트리라 노드가 `2 x 잎 - 1` 이다.\
  `leafMax 32` → 잎 128개 → `255`, `leafMax 1` → 잎 4096개 → `8191`.
- 복사량이 leafMax 에 비례하는 이유: 편집 한 번이 잎 하나를 쪼개고 그 잎의 길이만큼 옮기기 때문이다.\
  `leafMax 1` 이면 쪼갤 것이 없어 0이고, `leafMax 4096` 이면 문서 전체가 잎 하나라 편집 한 번이 4096 글자다 — **잎 하나짜리 로프는 배열과 같은 값을 낸다**.
- 양 극단의 정체: `leafMax 1` 은 "글자마다 노드", `leafMax = 문서 길이` 는 "배열".\
  즉 leafMax 는 **트리와 배열 사이의 다이얼**이고, 중간 어디가 좋은지는 워크로드가 정한다.

> **leafMax(잎 최대 길이)** — 잎 하나가 담는 글자 수의 상한.\
> 예: 이 구현의 기본값은 `DEFAULT_LEAF_MAX = 32` 이고, `new Rope(text)` 는 그 값을 쓴다.

> **캐시 지역성(cache locality)** — 다음에 읽을 데이터가 방금 읽은 데이터 근처에 있어 캐시에 이미 올라와 있는 성질.\
> 예: 잎 안의 연속된 글자를 훑는 것은 싸고, 흩어진 노드를 포인터로 따라가는 것은 비싸다.

- Q: 실제 에디터가 표의 최적값보다 훨씬 큰 값을 쓰는 이유는?\
  A: **캐시 때문**이다(README 가 그렇게 적었다).\
  이 표가 세는 것은 "방문한 노드 수"이지 시간이 아니다 — 실제 기계에서는 노드를 따라가는 포인터 추적이 캐시 미스를 내고, 잎 안의 연속된 글자를 훑는 것은 캐시에 매우 싸다.\
  그래서 걸음 수로는 손해인 큰 잎이 실제 시간으로는 이득이 된다.
- Q: `StringBuilderStore` 를 제자리 편집으로 바꿔도 안 바뀌는 사실은 무엇인가?\
  A: **가운데 삽입이 O(n) 이라는 사실**이다 — javadoc 이 그 문장을 그대로 적어뒀다.\
  제자리로 고치면 상수는 줄어든다(전체 복사 n 이 뒤쪽만 미는 `n - index` 가 되고 append 는 상환 O(1) 이 된다).\
  그러나 차수는 그대로이고, 대신 **옛 버전이 사라져** 두 구현을 같은 자리에 놓고 비교할 수 없게 된다.\
  이 문제집이 기준선도 값 계약으로 둔 이유가 그것이다.

**접근 비교**

```
  선택                    조회         편집 복사       메모리(노드)      쓸 자리
  ---------------------   ----------   ------------   --------------   -------------------
  leafMax 아주 작게       비싸다       0에 가깝다     폭발한다         편집만 극단적으로 많을 때
  leafMax 중간(32 근처)   중간         중간           중간             이 문제집의 기본값
  leafMax 아주 크게       싸다         문서 전체      1개              사실상 배열
  배열(StringBuilder)     가장 싸다    문서 전체      1개              읽기 전용·작은 문서

  다이얼 하나로 배열과 트리 사이를 오간다. 공짜 지점은 없다.
```

**더 생각할 것**

- "최적값"은 표에 없다 — 표는 **어느 쪽도 공짜가 아니라는 것**만 보여준다.\
  조회와 편집의 비율, 그리고 캐시가 실제 값을 정한다.
- 걸음 수와 시간이 갈리는 대표적인 자리다.\
  29번 이중 해싱이 탐사 횟수는 가장 적은데 캐시 지역성이 최악인 것과 같은 종류의 함정이다.
- 잎이 편집으로 잘게 부서지면 처음 정한 leafMax 가 의미를 잃는다.\
  실무 구현이 "작은 잎 합치기"를 하는 이유이고, 그 값으로 복사 0을 포기한다(한계 4).

#### 8. 이 구조의 한계가 다음 구조를 어떻게 부르는가

- Q: 01번은 연속으로 놓아 조회를 샀고 28번은 트리에 흩어 놓아 편집을 샀다 — 이 말을 지금까지의 구조들로 어떻게 정리할 수 있는가?\
  A: **자료구조는 데이터를 바꾸는 것이 아니라 데이터를 놓는 방식을 고르는 것**이고, 그 선택은 언제나 "무엇을 싸게 하고 무엇을 비싸게 할 것인가"의 교환이다.

```
  같은 데이터, 다른 배치, 다른 워크로드

  배치                       산 것                   내준 것              대표
  ------------------------   ---------------------   -----------------   ----------------------
  연속으로 놓는다            임의 접근 O(1)          가운데 편집 O(n)    01 동적 배열, 18 비트셋
  연결로 놓는다              양끝 삽입·삭제 O(1)     임의 접근 O(n)      02 연결 리스트
  해시로 흩는다              키 조회 O(1)            순서·범위          05 해시맵, 29 개방 주소법
  정렬 트리로 놓는다         범위·이웃 질의 O(log n) 상수와 캐시        06 BST, 15 B-트리
  트리에 조각으로 흩는다     가운데 편집 O(log n)    임의 접근 O(log n)  28 로프
  요약을 위로 접어 올린다    "그대로인가" O(log n)   내용 질의          27 머클 트리
  옛 버전을 남긴다           시점 조회·되돌리기      쓰기마다 노드 생성  26 영속, 28 로프
```

- Q: 로프 자신이 남긴 한계는 무엇이고 그것이 무엇을 부르는가?\
  A: 셋이다.\
  첫째, **깊이가 스스로 안 잡힌다** — 06번 BST 가 16번 레드블랙 트리를 부른 것과 같은 자리이고, 실무 구현은 자동 균형으로 답한다.\
  둘째, **`charAt` 이 어떤 방법으로도 O(1) 이 안 된다** — 잎을 키우면 조회가 싸지지만 편집이 비싸져서 다이얼을 돌릴 뿐 없앨 수 없다(한계 2).\
  셋째, **잎 조각화를 되돌릴 수 없다** — 되돌리려면 복사 0을 포기해야 한다(한계 4).
- Q: 27번에서 여기로 넘어온 것은 무엇인가?\
  A: **"바뀐 경로만 새로 만들고 나머지는 같은 객체로 가리킨다"** 는 발상이 그대로 넘어왔다.\
  27번은 잎의 **값**만 갈았고(자리·개수 고정), 28번은 잎을 **자르고 붙인다**(자리가 계속 움직인다).\
  그래서 27번에는 삽입·삭제가 아예 없었고, 28번은 그 연산을 O(log n) 으로 만드는 것이 목표가 됐다.
- Q: 다음(29번 개방 주소법)은 어떤 질문으로 넘어가는가?\
  A: 배치의 축이 트리에서 **평평한 배열 한 장**으로 돌아간다.\
  29번은 "충돌한 키를 어디에 놓을 것인가"를 다섯 가지 규칙으로 풀어보며, 여기서 본 것과 같은 종류의 교환(평균 대 꼬리, 걸음 수 대 캐시)을 다시 만난다.

**더 생각할 것**

- 이 장에서 가장 오래 남는 문장은 "복사 0"이 아니라 **"공짜가 아니라 외상"** 쪽이다.\
  비용을 안 낸 것이 아니라 다른 계정으로 미룬 것이고, 그 계정이 어디인지를 아는 것이 설계다.
- 걸음 수를 세는 계기(`charsCopiedTotal`, `charAtVisits`)를 자료구조에 심어둔 것이 이 장의 방법론이다.\
  27번의 `comparisons()`, 29번의 `lastProbeCount()`, 30번의 `visitedNodes()` 가 전부 같은 장치다.
- 한계 5(테스트가 못 잡는 동치 변종 둘)도 기억할 자리다.\
  `splitNode` 의 `index == node.weight` 지름길을 지워도, `appendRange` 의 가지치기를 `Math.min` 으로 눌러 써도 110개가 다 통과한다 — **노드 객체까지 같은 동치 변환**이었기 때문이다.\
  성능이 달라지는 변종(훑어 자르는 O(n) 구현)은 성능 테스트가 잡지만, 같은 결과·같은 구조를 내는 변종은 어떤 테스트로도 구별할 수 없다.
