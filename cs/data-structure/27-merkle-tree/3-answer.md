### A. 문제

#### 1. 다른 블록 전부 찾기 — `diffBlocks`

**접근 1 — 잎을 처음부터 끝까지 비교한다** (가장 먼저 떠오르고, 답도 맞는다)

```java
// 의사코드 — TestSupport.naiveDiff 가 실제로 이렇게 생겼다
List<Integer> out = new ArrayList<>();
for (int i = 0; i < local.size(); i++) {
    if (!Arrays.equals(local.get(i), remote.get(i))) {
        out.add(i);
    }
}
return out;
```

- 논리: 블록마다 한 번씩 비교하면 다른 자리를 빠짐없이 찾는다.
- 논리: 왼쪽부터 돌므로 결과가 저절로 오름차순이다.
- 비용(왜): 비교가 정확히 n 번 → 블록 1024개면 1024번.
- 한계: **이 답은 맞다.** 그래서 위험하다.\
  `diffBlocks` 의 답만 보는 테스트는 이 구현도 통과시킨다.
- 한계: rsync 나 카산드라의 상황에서는 상대의 블록 1024개를 **전부 받아와야** 이 비교가 가능하다.\
  "다른 것만 보내려고" 시작한 일인데 전부 보내고 나서야 어디가 다른지 알게 된다.

> **머클 트리(Merkle tree)** — 데이터 조각(블록)마다 해시를 뜨고 그 해시 둘씩을 다시 해시해 위로 접어 올려, 맨 위에 값 하나(뿌리)를 남긴 이진 트리.\
> 예: 블록 4개면 잎 해시 4개 → 내부 2개 → 뿌리 1개, 총 노드 7개다.

> **잎(leaf) / 내부(internal) 노드** — 실제 블록 하나를 요약한 맨 아래층 노드 / 자식 해시 둘을 합쳐 요약한 위층 노드.\
> 예: `MerkleTree` 에서 `levels[0]` 이 잎 층이고 `levels[height]` 이 뿌리 한 칸짜리 층이다.

**접근 2 — 뿌리에서 내려가되 같은 부분트리는 통째로 건너뛴다** (impl 의 정답)

```java
public static List<Integer> diffBlocks(MerkleTree local, MerkleTree remote) {
    // ... null·잎 개수 검사 생략
    List<Integer> out = new ArrayList<>();
    collect(local, remote, local.height(), 0, out);
    return out;
}

private static void collect(MerkleTree local, MerkleTree remote, int level, int index, List<Integer> out) {
    if (local.sameNode(remote, level, index)) {
        return;                      // 여기가 이 문제의 전부다
    }
    if (level == 0) {
        out.add(index);
        return;
    }
    int left = 2 * index;
    int right = left + 1;
    collect(local, remote, level - 1, left, out);
    if (right < local.levelSize(level - 1)) {
        collect(local, remote, level - 1, right, out);
    }
}
```

```
1024블록 중 {17, 600, 1023} 이 다를 때 · 뿌리에서 내려간다

  10층                     [뿌리]                  다르다 -> 자식 둘로
                          /      \
   9층              [0]              [1]           둘 다 다르다(왼쪽에 17, 오른쪽에 600·1023)
                   /    \          /    \
   8층         [0]   [1]        [2]      [3]       [1] 은 같다 -> 512..767 블록 256개를 한 번에 버린다
              / \     X                            X = 비교 한 번으로 통째로 잘린 가지
             ...      (더 안 내려간다)

   0층    ... [17] ...            ... [600] ... [1023]     세 잎만 답에 담긴다

  같은 가지를 만나는 순간 그 밑의 잎 전부를 안 본다.
  "다르다"가 뿌리에서 잎까지 이어진 길 위에만 있기 때문이다.
```

- 논리: 부모 해시는 자식 해시로만 만들어졌다.\
  그래서 **부모가 같으면 그 밑은 전부 같다** — 한 번의 비교로 부분트리를 통째로 버린다.
- 논리: 부모가 다르면 자식 중 최소 하나가 다르다.\
  그래서 다른 가지만 따라 내려가면 답을 빠뜨리지 않는다.
- 논리: 왼쪽 자식을 먼저 부르므로 답이 저절로 오름차순이다(나중에 정렬할 필요가 없다).
- 논리: 오른쪽 자식은 없을 수 있다 — 짝 없는 노드를 그대로 올리는 승격 규칙 때문이다.\
  그래서 `right < local.levelSize(level - 1)` 로 막는다.
- 비용(왜): 비교 횟수 = 방문한 노드 수이고, 방문하는 노드는 "다른 노드의 자식들"뿐이다.
- 한계: 차이가 흩어져 많아지면 트리를 거의 다 내려가 전수보다 **더** 본다(질문 6).

**비교 횟수 55번은 어디서 나오는가 (손계산)**

```

(잎 인덱스를 층 수만큼 2로 나누면 그 층의 조상 번호다)

   층    그 층의 노드 수    17의 조상  600의 조상  1023의 조상   서로 다른 조상 수
   10          1               0          0           0              1
    9          2               0          1           1              2

    7          8               0          4           7              3

    0       1024              17        600        1023              3

  10층부터 1층까지 "다른 내부 노드" 합계 = 1 + 2 + (3 x 8) = 27
  다른 내부 노드는 저마다 자식 2개를 부른다 -> 호출 27 x 2 = 54
  거기에 맨 처음 뿌리 호출 1번을 더한다
  총 비교 = 1 + 54 = 55      <- DiffTest.threeOutOfAThousand 의 assertEquals(55, ...)

  전수 비교는 1024번이다. 55 x 15 = 825 < 1024 이므로
  "적어도 15배는 적어야 한다"는 두 번째 단언도 같이 통과한다.
```

- 왜 60번 안쪽인가: 다른 잎 하나가 만드는 조상은 최대 10개(높이)이고, 다른 잎이 3개면 조상은 많아야 30개다.\
  그 조상들이 저마다 자식 2개를 부르니 호출은 많아야 60번 언저리이고, 뿌리 근처에서 세 경로가 겹쳐 27개로 줄어 실제로는 55다.
- 일반식: 다른 잎이 k 개면 방문 노드는 대략 `2 x k x log2(n)` 이하다.\
  `k = 3`, `log2(1024) = 10` 이면 60 — README 가 "60번 안쪽"이라고 쓴 근거가 이 곱이다.
- 같은 규칙으로 256블록·차이 3개를 세면 43번이다.\
  `MerkleProblemsTest.repairOnlyWhatDiffers` 는 `assertTrue(lookups < 60)` 로 부등식만 단언한다 — **43 은 내가 코드 규칙대로 센 값이고 테스트가 박아둔 값이 아니다.**

**"같으면 건너뛴다"를 빼면 무엇을 잃는가**

```java
// 1번 줄을 지운 버전 — 답은 똑같이 맞는다
private static void collect(...) {
    // if (local.sameNode(remote, level, index)) return;   <- 지웠다
    if (level == 0) {
        if (!local.sameNode(remote, 0, index)) out.add(index);
        return;
    }
    ...
}
```

- 잃는 것 1: 비교 횟수가 55 → 2047(노드 전부) 수준이 된다.\
  전수 비교(1024)보다도 많아진다.
- 잃는 것 2: rsync·카산드라가 이 구조를 쓰는 **유일한 이유**가 사라진다.\
  실무에서 이 비교는 네트워크 너머의 노드를 가져오는 일이라 횟수가 곧 왕복 횟수다.
- 잃는 것 3: 아무것도 안 잃은 것처럼 보인다는 것 자체가 손해다.\
  README 가 "79개 중 76개가 통과한다"고 적어뒀다 — 갈리는 것은 **횟수를 세는 테스트 셋뿐**이다.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 목적만 달성하지 못한 상태.\
> 예: 건너뛰기를 지운 `diffBlocks` 는 답이 맞고 예외도 없지만 자료구조를 쓰는 이유를 잃었다.

> **anti-entropy(안티 엔트로피)** — 복제본끼리 주기적으로 대조해 어긋난 조각만 고쳐 맞추는 복구 방식.\
> 예: 카산드라는 노드끼리 머클 트리를 주고받아 다른 구간만 다시 보낸다.

- 그래서 `DiffTest` 는 시간이 아니라 **`local.comparisons()` 를 센다**.\
  `MerkleTree.sameNode` 안에서 `comparisons++` 가 돌고, 테스트는 재기 직전에 `resetComparisons()` 를 부른다.
- 시간을 재면 기계·JIT·GC 에 흔들리지만 횟수는 언제 어디서 돌려도 같은 값이라 단언에 쓸 수 있다.

**질문별 답**

- Q: 문제 1을 어떻게 푸는가?\
  A: 뿌리 `(height, 0)` 에서 재귀를 시작해 세 갈래로 나눈다.\
  같으면 즉시 반환(부분트리 통째로 버림), 0층이면 인덱스를 답에 담기, 아니면 왼쪽·오른쪽 자식으로 내려가기다.\
  오른쪽 자식은 승격 때문에 없을 수 있으므로 `levelSize` 로 막는다.
- Q: 1024개 중 3개가 다를 때 왜 60번 안쪽인가?\
  A: 다른 잎 k 개가 뿌리까지 끌고 올라가는 경로가 최대 `k x log2(n)` 개이고, 방문 노드는 그 경로 노드들의 자식이라 대략 그 두 배다.\
  `2 x 3 x 10 = 60` 이 상한이고, 뿌리 근처 두 층에서 경로가 겹쳐 실제 값은 55다.
- Q: "같으면 건너뛴다"를 빼면 무엇을 잃는가?\
  A: 답은 그대로이고 **비용만** 잃는다 — 55번이 트리 전체(2047노드)로 늘어 전수 비교보다 나빠진다.\
  이 자료구조의 존재 이유가 통째로 그 숫자에 들어 있어서, 답으로는 정답과 오답이 갈리지 않는다.\
  그래서 테스트가 답이 아니라 걸음 수를 단언한다.

**더 생각할 것**

- 이 구조가 이기는 조건은 "대부분 같다"이고, 그것은 자료구조가 아니라 **워크로드가 정한다**.\
  복제본 대조·증분 백업·재전송은 거의 같은 상태를 전제하므로 이 가정이 맞는 자리다.
- 실무에서는 비교 한 번이 네트워크 왕복이라 55 대 1024 의 차이가 밀리초 대 초로 벌어진다.\
  다만 이 문제집은 시간을 재지 않는다 — 결정적인 숫자만 단언한다.
- 재귀 깊이는 트리 높이라 100만 블록이어도 20이다.\
  28번 로프처럼 깊이가 수만이 되는 구조와 달리 여기서는 스택이 문제가 되지 않는다.

#### 2. 증명 배치 검증 — `verifyBatch`

**접근 1 — 통과한 개수를 세서 비율로 판정한다** (절대 하면 안 되는 쪽. 왜 안 되는지가 이 문제의 핵심)

```java
// 하면 안 되는 구현
int ok = 0;
for (int i = 0; i < proofs.size(); i++) {
    if (proofs.get(i).verify(leafHashes.get(i), root)) ok++;
}
return ok * 2 > proofs.size();   // "절반 넘게 맞으면 통과"
```

- 한계: 이 자료구조가 파는 물건은 **"이 블록이 그 파일에 들어 있다"는 확정적 판정** 하나뿐이다.\
  절반만 맞아도 통과시키면 그 판정이 확률 판정이 된다.
- 한계: 11번 블룸 필터는 정확성을 팔아 메모리를 샀지만, 여기서는 **아무것도 팔지 않는 것**이 상품이다.\
  깎을 자리가 없다.
- 한계: 공격자 입장에서 보면 "위조 하나를 진짜 여럿에 섞어 넣으면 통과한다"가 된다.\
  검증의 의미가 사라진다.

**접근 2 — 짝을 지어 하나씩 검증하고 하나라도 실패하면 즉시 false** (impl 의 정답)

```java
for (int i = 0; i < proofs.size(); i++) {
    MerkleProof proof = proofs.get(i);
    byte[] leafHash = leafHashes.get(i);
    if (proof == null || leafHash == null) {
        throw new IllegalArgumentException("증명과 잎 해시는 null 일 수 없다: " + i + "번");
    }
    if (!proof.verify(leafHash, root)) {
        return false;
    }
}
return true;
```

- 논리: `proofs.get(i)` 와 `leafHashes.get(i)` 가 짝이다 — 짝이 어긋나면 값이 안 맞아 false 다(`mismatchedPairing`).
- 논리: 하나라도 실패하면 즉시 반환한다 — 나머지를 더 볼 이유가 없다.
- 논리: 개수가 다르거나 null 이 섞이면 예외다 — 조용히 넘어가면 "검증했다"는 말이 거짓이 된다.
- 비용(왜): 증명 하나가 log n 번 해시하므로 총 `증명 수 x log n` 번이다.

> **포함 증명(inclusion proof)** — 파일 전체 없이, 경로의 형제 해시들만으로 "이 블록이 그 뿌리 밑에 있다"를 보이는 증거.\
> 예: 잎 1024개짜리 트리면 형제 해시 10개(SHA-256 이면 320바이트)로 끝난다.

**배치로 묶으면 무엇이 줄고 무엇이 안 줄어드는가**

```
증명 8개를 검증한다 (잎 64개짜리 트리, 높이 6)

  하나씩 8번 부를 때        배치로 한 번에 부를 때
  ---------------------     ----------------------
  해시 계산 6 x 8 = 48      해시 계산 6 x 8 = 48      <- 안 줄어든다
  왕복(요청) 8번            왕복(요청) 1번            <- 이것만 줄어든다

  MerkleProblemsTest.batchingSavesRoundTripsNotHashes
      assertEquals(48, counter.calls(), "증명 8개 * 6걸음 = 48번. 하나씩 부를 때와 같다")
```

- 줄어드는 것: 호출·왕복(round trip) 횟수, 그리고 뿌리를 한 번만 넘기면 된다는 편의.
- 안 줄어드는 것: **해시 계산량**이다 — 증명 하나당 log n 번이 그대로 든다.\
  이름이 "배치"라고 무언가 합쳐지는 것처럼 들리지만 합쳐지는 것이 없다.
- 실무에서 진짜로 계산을 줄이려면 **여러 증명이 공유하는 경로 노드를 한 번만 계산하는** 다중 증명(multiproof)이 필요하고, 그것은 이 구현에 없다.\
  (원본에 근거 없음 — 내 추론. 코드와 README 는 "줄어드는 것은 왕복이지 계산이 아니다"까지만 말한다.)

> **왕복(round trip)** — 요청을 보내고 응답을 받기까지의 한 번의 오감.\
> 예: 증명 8개를 따로 요청하면 왕복이 8번이고, 한 번에 묶어 요청하면 1번이다.

**빈 목록에 true 를 주는 자리 (한계 5)**

```java
// proofs.size() == 0 이면 루프가 한 번도 안 돌고 곧장 true
assertTrue(MerkleProblems.verifyBatch(root, List.of(), List.of()));   // MerkleProblemsTest.emptyBatch
```

- "전부 통과했다"와 "검증할 것이 없었다"가 같은 값 `true` 로 나온다.
- 이것은 논리적으로는 옳다(공허한 참).\
  그러나 부르는 쪽이 "증명 0개를 받았다"는 사실을 따로 보지 않으면 검증을 건너뛴 것과 통과한 것이 구별되지 않는다.
- 자료구조가 대신 정해줄 수 없는 자리다 — 개수를 세는 것은 호출자의 계약이다.

> **공허한 참(vacuous truth)** — "모든 X 가 참이다"를 X 가 하나도 없을 때 참으로 보는 논리 규칙.\
> 예: 증명이 0개면 "틀린 증명이 하나도 없다"가 자동으로 성립한다.

**질문별 답**

- Q: 문제 2를 어떻게 푸는가?\
  A: i 번째 증명과 i 번째 잎 해시를 짝지어 `proof.verify(leafHash, root)` 를 부르고, 하나라도 false 면 즉시 false 를 반환한다.\
  개수 불일치와 null 은 예외로 막고, 전부 통과하면 true 다.
- Q: 배치로 묶으면 무엇이 줄고 무엇이 안 줄어드는가?\
  A: 줄어드는 것은 왕복(요청 8번 → 1번)이고, 해시 계산은 48번 그대로다.\
  테스트가 `assertEquals(48, ...)` 로 그 자리를 못 박았다.
- Q: "절반 넘게 맞으면 true" 로 완화하면 왜 이 자료구조가 파는 물건이 사라지는가?\
  A: 이 구조의 상품은 "해시 충돌이 없다면 이 판정은 확정적이다" 하나뿐이기 때문이다.\
  비율 판정으로 바꾸는 순간 위조 하나를 진짜 여럿에 섞는 공격이 통과하고, 판정은 확률적 추정이 된다.\
  11번 블룸 필터는 처음부터 오탐률을 값으로 내놓고 팔았지만 여기서는 팔 것이 없다 — 깎으면 상품 자체가 없어진다.

**더 생각할 것**

- 검증 함수의 반환형이 `boolean` 이라 "몇 개가 틀렸는지"는 알 수 없다.\
  운영에서 원인 분석이 필요하면 실패한 인덱스를 돌려주는 별도 API 가 필요하다(원본에 근거 없음 — 내 추론).
- 즉시 반환은 성능만이 아니라 **의미**의 문제다.\
  "전부 맞다"를 묻는 질문에 하나라도 틀리면 더 볼 것이 없다.
- 빈 배치 문제는 이 코드만의 것이 아니다.\
  "검사 대상이 0건이면 통과"는 배포 게이트·린트·스키마 검증에서 반복해서 사고를 만드는 형태다.

### B. 자료구조 특성

#### 3. 머클 트리가 왜 필요한가

- Q: 01~26번의 자료구조는 전부 "무엇이 들어 있나"에 답했는데 여기서 묻는 질문은 무엇인가?\
  A: **"이게 그대로인가"** 다.\
  05번 해시맵은 "이 키가 있나", 09번 트라이는 "이 접두사로 시작하는 것들", 13번 세그먼트 트리는 "이 구간의 합"에 답한다.\
  전부 **내용**을 묻는 질문이고, 답하려면 그 내용을 손에 들고 있어야 한다.\
  27번은 내용이 아니라 **동일성**을 묻는다 — 내 손의 1024블록과 상대의 1024블록이 같은가, 다르면 어디가 다른가, 그리고 이 블록 하나가 그 파일에 들어 있다는 것을 파일 없이 보일 수 있는가.

> **해시(hash)** — 임의 길이 데이터를 짧은 고정 길이 값으로 줄이는 함수.\
> 예: `Sha256Hash` 는 입력이 1바이트든 10MB 든 32바이트를 돌려준다.

- Q: 해시 **하나**로 요약하는 것으로는 무엇이 안 되는가?\
  A: 두 가지가 안 된다.\
  첫째, **다를 때 어디가 다른지 모른다** — 값이 다르다는 사실만 알고 1024블록 중 어느 것인지 알 길이 없어 결국 전부 다시 보내야 한다.\
  둘째, **블록 하나만 증명할 수 없다** — "3번 블록이 이 파일에 있다"를 보이려면 파일 전체를 해시해 봐야 하므로 파일을 통째로 들고 있어야 한다.\
  README 의 표가 그 둘을 나란히 적어뒀다.

```
  질문                    해시 하나        머클 트리
  ---------------------   -------------    ------------------------
  같은지 안다             된다             된다
  어디가 다른지           모른다           O(log n)  (1024블록에서 11번 비교)
  블록 하나만 증명        파일 전체 필요   해시 log n 개 (1024블록에서 10개 320바이트)
  블록 하나 갱신          전부 다시 해시   경로만 (1024잎에서 2047번 -> 11번)
```

- Q: 그 차이는 어디서 나오는가?\
  A: **중간 결과를 버리지 않고 층으로 남겨둔 것** 하나에서 나온다.\
  해시 하나짜리 요약도 내부적으로는 블록을 순서대로 먹어 값 하나를 만들지만 중간 상태를 남기지 않는다.\
  머클 트리는 접어 올리는 과정의 중간값을 전부 `levels` 배열에 보관한다 — 그래서 위에서 내려가며 "이 절반은 같다"를 물을 수 있고, 옆가지 값을 꺼내 증명으로 쓸 수 있다.
- Q: 코드에서 그 "보관"은 어디인가?\
  A: `MerkleTree.build` 가 층을 하나씩 만들어 `List<byte[][]> out` 에 쌓고 `byte[][][] levels` 로 굳히는 자리다.

```java
List<byte[][]> out = new ArrayList<>();
out.add(current);                       // 0층 = 잎
while (current.length > 1) {
    byte[][] next = new byte[(current.length + 1) / 2][];
    for (int i = 0; i < next.length; i++) {
        int left = 2 * i;
        int right = left + 1;
        next[i] = right < current.length
                ? hashing.nodeHash(current[left], current[right])
                : current[left];        // 짝이 없으면 그대로 올린다 (승격)
    }
    out.add(next);
    current = next;
}
```

**더 생각할 것**

- 이 구조는 "믿을 수 있는 값 하나(뿌리)"를 다른 경로로 받았다는 전제 위에 선다.\
  그 전제가 없으면 아무것도 증명하지 못한다(질문 8).
- git 의 커밋 해시, 비트코인 블록, CT 로그, IPFS 의 주소가 전부 같은 발상이다 — 내용 자체가 아니라 **내용의 지문**을 주고받는다.
- 11번 블룸 필터와 짝지어 보면 대비가 선명하다.\
  블룸은 "있을 수도 있다"를 팔아 메모리를 샀고, 머클은 아무것도 팔지 않는 대신 **해시 가정**이라는 조건을 달고 있다.

#### 4. 어떤 형태의 데이터·접근 패턴에 적합하고 언제 쓰면 안 되는가

- Q: 어떤 데이터·접근 패턴에 적합한가?\
  A: **자리가 고정된 블록 목록**이고, 두 벌이 대체로 같고, 대조가 반복되는 패턴이다.\
  파일을 4KB 블록으로 자른 것, 복제본 둘이 들고 있는 같은 키 구간, append 만 되는 로그가 그 모양이다.\
  여기에 "전체를 옮기지 않고 확인해야 한다"는 제약이 붙으면 이 구조가 정확히 그 자리에 들어간다.
- Q: 왜 "자리가 고정된 목록"이라는 조건이 붙는가?\
  A: 잎의 **인덱스가 곧 이름**이기 때문이다.\
  `findFirstDifference` 는 두 트리의 `(level, index)` 를 자리로 맞대 비교하고, `proofFor(leafIndex)` 도 인덱스로 경로를 찾는다.\
  그래서 `requireComparable` 이 잎 개수가 다르면 아예 예외를 던진다 — "잎 개수가 다르면 자리를 맞출 수 없다".
- Q: 블록을 끼워 넣거나 빼면 무슨 일이 일어나는가?\
  A: 그 뒤 **모든 잎의 자리가 한 칸씩 밀린다**.\
  내용이 하나도 안 변한 블록들의 인덱스가 달라지므로 같은 자리끼리의 비교가 전부 어긋나고, 트리는 처음부터 다시 지어야 한다(한계 3).\
  `withLeafReplaced` 는 **갈아끼우기**만 있고 삽입·삭제가 없는 것이 그 사실의 코드 쪽 표현이다.

```
  갈아끼우기 (있다)                     끼워 넣기 (없다)
  [b0][b1][b2][b3]                      [b0][b1][b2][b3]
        |                                     |
        v  b1 -> b1'                          v  b1 과 b2 사이에 x 를 넣는다
  [b0][b1'][b2][b3]                     [b0][b1][ x ][b2][b3]
   같은  바뀜  같은 같은                  자리: 0   1    2    3    4
   -> 경로 11개만 새로 만든다             -> b2 가 2번에서 3번으로, b3 가 3번에서 4번으로 밀린다
                                          -> 내용이 같은데 자리가 달라 비교가 전부 어긋난다
                                          -> 트리를 처음부터 다시 짓는다 (해시 2047번)
```

- Q: 언제 쓰면 안 되는가?\
  A: 넷이다.\
  첫째, **대부분 다를 때** — 64블록이 전부 다르면 노드 127개를 다 보는데 전수 비교는 64번이면 된다(질문 6).\
  둘째, **블록이 자주 삽입·삭제될 때** — 위의 이유로 매번 다시 짓는다.\
  셋째, **블록이 몇 개 안 될 때** — 트리를 짓는 해시 비용이 그냥 비교하는 비용보다 크다.\
  넷째, **한 번 쓰고 버릴 대조** — 트리를 짓는 값(1024블록에 해시 2047번)을 대조 한 번으로 회수하지 못한다.
- Q: 그 마지막 조건은 왜 중요한가?\
  A: 머클 트리는 **미리 지어두고 여러 번 쓰는** 구조이기 때문이다.\
  rsync 는 전송 한 번을 위해 짓지만 블록 수가 커서 이득이 나고, 카산드라는 지어둔 트리를 반복되는 repair 에 쓴다.\
  "한 번 비교하려고 짓는 작은 트리"는 계산을 두 번 하는 셈이 된다(원본에 근거 없음 — 내 추론).

**더 생각할 것**

- 자리 고정 제약은 **경계(블록 자르는 지점)** 를 고정하라는 말이기도 하다.\
  가변 길이 청킹(rolling hash 로 경계를 내용에 맞춰 잡는 방식)을 쓰면 삽입에도 자리가 덜 밀리지만, 그것은 이 문제집 밖의 장치다(원본에 근거 없음 — 내 추론).
- "대체로 같다"는 가정은 측정 가능한 것이다.\
  실제로 다른 비율이 얼마인지 모른 채 도입하면 한계 2의 구간에서 조용히 손해만 본다.
- 잎 개수가 다르면 예외를 던지는 선택은 "되는 척하지 않는다"는 쪽이다.\
  31번 점프 해시가 가운데 노드 제거를 예외로 드러내는 것과 같은 자세다.

#### 5. `findFirstDifference` 가 O(log n) 이고 포함 증명이 log n 개인 구조적 이유

- Q: `findFirstDifference` 가 왜 O(log n) 인가?\
  A: 뿌리에서 잎까지 **한 갈래로만** 내려가고 층마다 비교를 한 번만 하기 때문이다.\
  1024잎이면 층이 11개(0층~10층)이고 높이는 10이라, 뿌리 비교 1번 + 10층 각 1번 = 11번이다.

```java
public int findFirstDifference(MerkleTree other) {
    requireComparable(other);
    int level = levels.length - 1;
    if (sameNode(other, level, 0)) {
        return -1;                       // 뿌리가 같다 -> 비교 1번으로 끝
    }
    int index = 0;
    while (level > 0) {
        int left = 2 * index;
        int right = left + 1;
        if (right >= levels[level - 1].length || !sameNode(other, level - 1, left)) {
            index = left;                // 왼쪽이 다르다(또는 오른쪽이 아예 없다)
        } else {
            index = right;               // 왼쪽이 같으니 오른쪽이 다르다
        }
        level--;
    }
    return index;
}
```

```
1024잎, 777번이 다르다 · 비교 11번

  10층  뿌리          다르다(비교 1)
   9층  왼쪽[0] 비교 -> 같다      -> 오른쪽[1] 로 간다 (오른쪽은 안 본다)
   8층  왼쪽[2] 비교 -> 같다      -> [3]
   7층  왼쪽[6] 비교 -> 다르다    -> [6]
   ...  (층마다 딱 한 번)
   0층  왼쪽 비교 -> 결정          -> 777

  비교 1 + 10 = 11        <- DiffTest.oneDifferenceCostsLogN 의 assertEquals(11, ...)
  전수 비교는 1024번이다. 그리고 777이 맨 앞이든 맨 뒤든 11로 같다
  (costDoesNotDependOnWhere 가 0, 1, 511, 512, 1023 에서 전부 11을 단언한다)
```

- Q: 층마다 비교가 왜 한 번이면 충분한가 — 오른쪽 자식을 비교하지 않고 내려가도 되는 근거는?\
  A: **부모가 다르다는 것을 이미 알고 내려왔기 때문**이다.\
  부모 해시는 자식 둘로만 만들어졌으므로 부모가 다르면 자식 중 최소 하나가 다르다.\
  그러니 왼쪽을 한 번 보면 끝난다 — 왼쪽이 다르면 왼쪽으로 가고(가장 왼쪽 차이를 찾는 것이 계약이다), 왼쪽이 같으면 **오른쪽이 다를 수밖에 없다**.\
  오른쪽을 확인하는 비교는 이미 아는 사실을 한 번 더 확인하는 것이라 정보를 늘리지 않는다.
- Q: 오른쪽 자식이 아예 없는 층은 어떻게 되는가?\
  A: `right >= levels[level - 1].length` 가 먼저 걸려 **비교 없이** 왼쪽으로 내려간다.\
  승격 규칙에서 부모 값은 왼쪽 자식 값 그대로이므로, 부모가 다르면 왼쪽도 반드시 다르다 — 비교할 필요가 없다.\
  그래서 승격이 섞인 모양에서는 비교가 `1 + 높이` 보다 적을 수도 있다.
- Q: 포함 증명이 왜 log n 개인가?\
  A: 잎에서 뿌리까지 올라가는 길이 log n 걸음이고, **걸음마다 형제 하나**만 있으면 부모를 계산할 수 있기 때문이다.

```java
public MerkleProof proofFor(int leafIndex) {
    int index = requireLeafIndex(leafIndex);
    List<MerkleProof.Step> steps = new ArrayList<>();
    for (int level = 0; level < levels.length - 1; level++) {
        byte[][] current = levels[level];
        boolean even = index % 2 == 0;
        int sibling = even ? index + 1 : index - 1;
        if (sibling < current.length) {
            steps.add(new MerkleProof.Step(current[sibling], !even));
        }
        index /= 2;
    }
    return new MerkleProof(steps, hashing);
}
```

```
잎 4개 · 1번 잎의 증명

        뿌리 = node(h01, h23)
        /            \
   h01=node(h0,h1)   h23          <- 1층: 형제는 h23, 내 오른쪽에 있다 (siblingIsLeft = false)
    /      \
  h0       h1                      <- 0층: 형제는 h0, 내 왼쪽에 있다 (siblingIsLeft = true)
           ^ 증명하려는 잎

  증명 = [ (h0, 왼쪽), (h23, 오른쪽) ]     크기 2 = 높이
  검증  current = h1
        걸음1: 형제가 왼쪽 -> current = node(h0, current)   = h01
        걸음2: 형제가 오른쪽 -> current = node(current, h23) = 뿌리
        마지막에 expectedRoot 와 견준다
```

- Q: 증명에 형제 해시만으로는 부족하고 **방향**까지 담아야 하는 이유는?\
  A: `nodeHash(left, right)` 가 **순서를 값에 넣기 때문**이다.\
  `nodeHash(a, b)` 와 `nodeHash(b, a)` 는 다른 값이므로, 검증하는 쪽이 형제를 왼쪽에 놓아야 할지 오른쪽에 놓아야 할지 모르면 부모를 계산할 수 없다.\
  코드가 그 갈림을 `step.siblingIsLeft()` 한 비트로 들고 있다.

```java
current = step.siblingIsLeft()
        ? hashing.nodeHash(sibling, current)
        : hashing.nodeHash(current, sibling);
```

- 방향이 틀리면 검증이 거부된다 — `MerkleProofTest.flippedDirection` 이 `Step.flipped()` 로 뒤집어 그 자리를 못 박는다.
- 방향 비트는 사실 **잎 인덱스의 이진 표현**과 같다.\
  `index % 2 == 0` 이면 내가 왼쪽이므로 형제는 오른쪽이고, 그 판정을 층마다 반복하면 인덱스의 비트를 아래에서부터 읽는 것과 같다.

> **접두사(prefix)** — 데이터 앞에 붙이는 표시 바이트.\
> 예: 이 구현은 잎에 `0x00`, 내부 노드에 `0x01` 을 붙여 두 값 공간을 갈라놓는다.

- Q: 잎 하나를 바꿀 때 1024잎에서 해시 계산이 2047번에서 11번이 되는 이유는?\
  A: **바뀌는 노드가 경로 위에만 있기 때문**이다.\
  잎 하나를 갈면 그 잎의 부모, 그 부모의 부모… 뿌리까지 10개가 바뀌고, 옆가지는 입력이 하나도 안 바뀌었으므로 값도 그대로다.\
  그래서 다시 계산할 것이 `잎 1 + 경로 10 = 11` 개다.

```
1024잎 트리를 처음부터 지을 때 vs 잎 하나를 갈 때

  처음부터 짓기            잎 하나 갈기 (withLeafReplaced)
  0층 잎  해시 1024번      0층 잎  해시    1번
  1층     해시  512번      1층     해시    1번
  2층     해시  256번      2층     해시    1번
  ...                      ...
  10층    해시    1번      10층    해시    1번
  ------------------       -------------------
  합계   2047번            합계   11번 = 높이 + 1

  DiffTest.hashCallsDropToLogN
      assertEquals(2047, counter.calls(), "잎 1024 + 내부 1023")
      assertEquals(11,   counter.calls(), "잎 1 + 경로 10")
      다시 지으면 또 2047번이다

  1024 + 512 + 256 + 128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = 2047
  (2의 거듭제곱 잎 n 개면 노드가 2n - 1 개다)
```

- Q: 나머지 노드는 어떻게 되는가?\
  A: **옛 배열의 객체를 그대로 가리킨다** — 복사하는 것은 층 배열의 참조뿐이다.

```java
byte[][][] copy = new byte[levels.length][][];
for (int level = 0; level < levels.length; level++) {
    copy[level] = levels[level].clone();   // 얕은 복사 — 해시 배열 자체는 공유한다
}
copy[0][index] = hashing.leafHash(newBlock);
```

- `DiffTest.onlyThePathIsNew` 가 `before.hashAt(level, i) == after.hashAt(level, i)` 로 **객체 동일성**을 세어 바뀐 것 11개, 공유 2036개를 단언한다.\
  `11 + 2036 = 2047` 로 노드 총수와 맞는다.
- 이것이 26번 영속 자료구조의 **경로 복사**와 같은 발상이다 — 26번은 트리 노드를, 여기서는 층 배열을 복사한다.

> **경로 복사(path copying)** — 바뀐 자리에서 뿌리까지의 길 위에 있는 노드만 새로 만들고 나머지는 옛 객체를 그대로 가리키는 방법.\
> 예: 1024잎 트리에서 잎 하나를 갈면 11개만 새 값이고 2036개는 옛 배열을 그대로 쓴다.

**더 생각할 것**

- 이 셋(차이 찾기 O(log n), 증명 log n 개, 갱신 log n 번)은 전부 **"부모는 자식으로만 만들어진다"** 한 문장에서 나온다.\
  구조가 다른 셋을 파는 것이 아니라 성질 하나가 세 얼굴로 보이는 것이다.
- 100만 블록이면 높이가 20이라 증명이 해시 20개다.\
  블록이 4KB 면 파일이 4GB 인데 그중 한 블록의 증명이 640바이트다 — 증명 크기가 **파일 크기와 무관**하다.\
  (`oneMillionLeaves` 가 20걸음을 단언하고, 640바이트는 README 의 산술이다. 테스트가 바이트를 단언하는 곳은 1024잎에서 `assertEquals(320, bytes)` 다.)
- 반대로 이 성질 때문에 "블록 하나를 바꾸면 뿌리가 반드시 바뀐다"도 따라온다.\
  바뀌지 않는다면 그것은 해시 충돌이고, 질문 6이 그 경우를 다룬다.

#### 6. 최악의 입력과 최선, 그리고 `ToyHash` 가 만드는 거짓말

- Q: 64블록이 전부 다르면 총 비용이 어떻게 되는가?\
  A: 노드 127개를 전부 본다 — 즉 비교 127번이다.

```
64잎 트리의 노드 수 = 64 + 32 + 16 + 8 + 4 + 2 + 1 = 127

  전부 다르면 "같다"로 잘리는 가지가 하나도 없다
  -> 뿌리부터 잎까지 모든 노드를 방문한다
  -> 비교 127번                 전수 비교는 64번

  DiffTest.everythingDiffers
      assertEquals(64, diff.size());
      assertEquals(127, a.comparisons(), "노드 127개를 다 봤다. 전수 비교는 64번이면 됐다")
```

- Q: 전수 비교와 비교하면 어느 쪽이 이기는가?\
  A: **전수 비교가 이긴다** — 64번 대 127번이고, 거기에 트리를 짓는 해시 127번이 따로 든다.\
  차이가 흩어져 많아질수록 머클 트리는 노드 `2n - 1` 개를 다 보게 되므로 전수의 두 배에 가까워진다.\
  머클 트리가 이기는 것은 **"대부분 같다"** 일 때뿐이다(한계 2).
- Q: 최선은 어떤 경우인가?\
  A: **두 벌이 완전히 같을 때**다 — 뿌리 비교 한 번으로 끝난다.

```
  DiffTest.identicalTreesCostOneComparison
      assertEquals(-1, local.findFirstDifference(remote));
      assertEquals(1, local.comparisons(), "블록 1024개가 같다는 것을 뿌리 비교 한 번으로 답한다")

  블록이 100만 개여도 1번이다. n 과 무관하다.
```

- 그 다음으로 좋은 것은 **차이가 한곳에 뭉쳐 있을 때**다.\
  이웃한 잎들은 조상을 공유하므로 경로가 겹쳐 방문 노드가 줄어든다.\
  반대로 차이가 고르게 흩어지면 경로가 안 겹쳐 `2 x k x log n` 의 상한에 붙는다.

**`ToyHash` 로 충돌을 만들면 무슨 일이 일어나는가**

```java
// ToyHash: 바이트를 그냥 더해 4바이트로 낸다 — 순서를 무시한다
hash({1, 2}) == hash({2, 1}) == hash({3, 0})
```

```
local  = [ {1,2}, {7} ]          remote = [ {2,1}, {7} ]
              ^ 다른 블록                       ^

  잎 해시:  leafHash({1,2}) = 0x00 + 1 + 2 = 3
            leafHash({2,1}) = 0x00 + 2 + 1 = 3      <- 같다!
  -> 잎이 같으니 뿌리도 같다

  findFirstDifference  ->  -1 ("같다")       실제로는 0번이 다르다
  diffBlocks           ->  []                실제로는 [0]
  전수 비교(naiveDiff) ->  [0]                정확히 답한다
```

- Q: `findFirstDifference` 가 어떻게 거짓말을 하는가?\
  A: **-1(같다)** 을 돌려준다 — 다른 파일인데 같다고 답한다(`SecondPreimageTest.diffGoesBlind`).\
  같은 자리에서 전수 비교는 `[0]` 이라고 정확히 답한다.\
  즉 충돌이 있으면 이 자료구조는 전수 비교보다 **덜 정확해진다**.
- Q: 포함 증명은 어떻게 거짓말을 하는가?\
  A: **파일에 없는 블록의 증명이 통과한다**(`proofsBecomeMeaningless`).\
  `{3, 0}` 은 파일에 없는데 `leafHash({3,0})` 이 `leafHash({1,2})` 와 같은 값이라 그 잎 해시로 증명을 돌리면 뿌리가 맞아떨어진다.
- Q: "확정적"이라는 말이 왜 무조건이 아니라 조건부인가?\
  A: 조건이 둘 달려 있기 때문이다.\
  첫째, **잎과 내부를 구별한다**(접두사) — 안 하면 질문 7의 두 번째 원상 공격이 성립한다.\
  둘째, **해시 충돌을 찾을 수 없다** — 찾히면 위의 셋이 전부 무너진다.\
  `SecondPreimageTest` 의 주석이 그 둘을 나란히 적어두고 **둘 다 실제로 깨본다** — 코드는 그대로이고 규칙 하나, 해시 하나만 바꾼다.

> **충돌(collision)** — 서로 다른 입력이 같은 해시 값을 내는 것.\
> 예: `ToyHash` 는 바이트 합만 보므로 `{1,2}` 와 `{2,1}` 이 같은 값을 낸다.

> **충돌 저항성(collision resistance)** — 충돌을 실제로 찾아내기가 계산적으로 불가능하다는 성질.\
> 예: SHA-256 에서는 같은 시도가 통하지 않아 `sha256Separates` 가 0번이 다르다고 정확히 답한다.

**더 생각할 것**

- "확정적"과 "무조건"은 다르다.\
  확정적은 **조건이 참일 때 확률이 개입하지 않는다**는 뜻이지 조건을 면제한다는 뜻이 아니다.
- 11번 블룸 필터는 오탐률을 숫자로 내놓고 팔았으므로 사용자가 위험을 계산할 수 있었다.\
  머클 트리는 위험을 "해시가 안전하다"는 가정 안에 접어 넣었다 — 그 가정이 깨지는 날은 계산이 아니라 사건으로 온다.
- 그래서 실무 구현은 해시 알고리즘을 **교체 가능하게** 둔다.\
  이 코드도 `HashFunction` 인터페이스로 그 자리를 열어뒀고, `ToyHash` 와 `Sha256Hash` 가 같은 구멍에 꽂힌다.

#### 7. 구현 전략의 트레이드오프 — 접두사 규칙과 홀수 잎 규칙

**(a) 접두사를 붙이는 규칙과 안 붙이는 규칙**

```java
// PrefixedHashing — 잎에 0x00, 내부에 0x01
input[0] = LEAF_PREFIX;   // leafHash
input[0] = NODE_PREFIX;   // nodeHash

// UnprefixedHashing — 아무것도 안 붙인다 (공격당하려고 두는 클래스)
return function.hash(block);                  // leafHash
return function.hash(left ++ right);          // nodeHash
```

- Q: 접두사가 없으면 무엇이 성립하는가?\
  A: `leafHash(x || y) == nodeHash(x, y)` 가 성립한다 — 잎과 내부 노드가 **같은 값 공간에 산다**.

```
정직한 파일 (블록 4개, 접두사 없음)

        뿌리 = H( H(h0||h1) || H(h2||h3) )
        /                      \
   H(h0||h1)               H(h2||h3)
    /     \                 /     \
   h0     h1               h2     h3
  (b0)   (b1)             (b2)   (b3)

위조 파일 (블록 2개) — 공격자는 "블록"으로 h0||h1 과 h2||h3 을 낸다

        뿌리' = H( H'(h0||h1) || H'(h2||h3) )      H' = 잎 해시
              = H( H(h0||h1)  || H(h2||h3)  )      접두사가 없어 H' 와 H 가 같은 함수다
              = 뿌리                                <- 같은 값!
        /              \
   H(h0||h1)      H(h2||h3)        <- 이제는 "잎"이다
   (64바이트 블록)  (64바이트 블록)

  SecondPreimageTest.differentFilesSameRoot
      assertEquals(4, honest.leafCount());  assertEquals(2, forged.leafCount());
      assertArrayEquals(honest.rootHash(), forged.rootHash());
      뿌리 = 925a61bb3ca2f6ab3f841f0abcca50a4fa8b6c79344472a6642cba718a637126
```

> **두 번째 원상 공격(second preimage attack)** — 주어진 데이터와 **같은 해시 값을 내는 다른 데이터**를 만들어내는 공격.\
> 예: 블록 4개짜리 파일과 뿌리가 같은 블록 2개짜리 위조 파일을 만들면 없는 블록의 증명이 통과한다.

- Q: 두 번째 원상 공격이 성립하는 조건이 "접두사를 붙였나"가 아니라 정확히 무엇인가?\
  A: **"잎과 내부에 서로 다른 값을 붙였나"** 다.\
  README 가 변종으로 확인해 적어뒀다 — 잎 접두사만 지워도 두 공간이 아직 갈라져 있어 공격이 안 되고, **둘을 같은 값으로 만드는 순간** 성립한다.\
  즉 막아주는 것은 "0x00 이라는 바이트"가 아니라 **두 해시 공간의 분리**다.

```
  잎 접두사   내부 접두사   두 공간이 겹치나   공격
  ---------   -----------   ----------------   -----
  0x00        0x01          아니다             안 된다   <- PrefixedHashing
  없음        0x01          아니다             안 된다   <- 잎만 지워도 아직 갈라져 있다
  0x00        0x00          겹친다             된다
  없음        없음          겹친다             된다      <- UnprefixedHashing
```

- 접두사가 내주는 것: 해시 입력이 블록마다 1바이트 길어진다.\
  `input = new byte[block.length + 1]` 로 배열을 새로 만들어 복사하므로 할당도 한 번 더 한다.
- 접두사가 사는 것: 잎으로 위장한 내부 노드를 원천 봉쇄한다.\
  인증서 투명성 로그(RFC 6962)가 정확히 이 규칙을 쓴다.
- 대가가 이렇게 작고 이득이 이렇게 큰 트레이드오프는 흔치 않다 — 사실상 "안 할 이유가 없는" 쪽이다.

**(b) 짝 없는 마지막 노드: 승격 대 자기 자신과 짝짓기**


```
      뿌리 = node(n0, h2)                   뿌리 = node(n0, node(h2, h2))
```

> 예: `[a,b,c]` 와 `[a,b,c,c]` 의 루트가 같아져 블록을 위조로 무효화시킬 수 있었다.

- Q: 승격은 대신 무엇을 흘리는가?\
  A: **증명 길이**를 흘린다(한계 4).\
  잎 3개짜리 트리에서 높이는 2인데 2번 잎의 증명은 걸음이 1개뿐이다 — 0층에 형제가 없기 때문이다.\
  그래서 증명의 길이만 봐도 "이건 마지막 승격된 잎이다"를 알 수 있다.

```
  OddLeafCountTest.promotionShortensTheProof
      assertEquals(2, tree.height());
      assertEquals(2, tree.proofFor(0).size());
      assertEquals(2, tree.proofFor(1).size());
      assertEquals(1, tree.proofFor(2).size(), "승격된 잎은 한 걸음")
```

- 흘리는 것이 치명적이냐: 자리 정보 일부이지 내용이 아니다.\
  그래서 이 문제집은 "증명 길이가 샌다"를 감수하고 CVE 쪽을 피하는 선택을 했다.
- Q: 잎이 2의 거듭제곱이면 왜 두 규칙이 구별되지 않는가?\
  A: **승격이 한 번도 일어나지 않기 때문**이다.\
  모든 층의 노드 수가 짝수라 항상 짝이 맞고, 짝 없는 노드가 생기지 않으니 두 규칙이 갈릴 자리 자체가 없다.\
  `thePowerOfTwoCaseIsIdentical` 이 n = 1, 2, 4, 8, 16 에서 두 규칙의 값이 같음을 단언한다.
- 그래서 **8블록으로만 테스트하면 이 취약점이 안 보인다**.\
  홀수 잎(3, 5, 6, 7, 9, 11)에서만 두 규칙이 갈리고, `theTwoRulesDisagreeWhereverThereIsAnOddLevel` 이 그 자리를 훑는다.
- 참고로 n = 6 도 목록에 들어 있다 — 잎 수가 짝수여도 **위층에서 홀수가 되면**(6 → 3) 승격이 일어난다.\
  "2의 거듭제곱"이 조건이지 "짝수"가 조건이 아니다.

**접근 비교**

```
  규칙                    서로 다른 목록이 같은 뿌리를 낼 수 있나   증명 길이가 일정한가
  ---------------------   ---------------------------------------   --------------------
  승격 (이 구현)          아니다                                   아니다 (마지막이 짧다)
  자기 자신과 짝짓기      **된다** (CVE-2012-2459)                 그렇다
  잎 수를 2의 거듭제곱    아니다                                   그렇다
  으로 패딩               (대신 빈 잎을 채우는 값이 든다)

  이 문제집은 첫 줄을 골랐고, 무엇을 흘리는지를 테스트로 적어뒀다.
```

**더 생각할 것**

- 두 규칙 중 무엇을 고르느냐보다 **골랐다는 사실을 테스트로 못 박았느냐**가 중요하다.\
  `OddLeafCountTest` 의 머리말이 그 말을 하고 있다 — "규칙을 고른 것만으로는 아무것도 못 박은 것이 아니다".
- 기댓값 hex 를 파이썬 hashlib 으로 따로 계산해 옮겼다는 `TestSupport` 주석도 같은 자세다.\
  구현이 스스로 만든 값을 기대값으로 쓰면 그 테스트는 아무것도 검증하지 못한다.
- 한계 6(`verify` 가 뿌리의 앞 4바이트만 비교해도 79개가 다 통과했다)도 같은 종류의 이야기다.\
  위조 테스트 일곱 개가 있어도 **검사 범위**를 재는 테스트가 없으면 부분 비교를 못 잡는다.\
  `everyByteOfTheRootMatters` 가 뿌리의 바이트를 하나씩 뒤집어 그 구멍을 막았다.

#### 8. 이 구조의 한계가 다음 구조를 어떻게 부르는가

- Q: 증명은 무엇까지만 보이는가?\
  A: **"이 잎이 이 뿌리 밑에 있다"** 까지다.\
  `MerkleProof.verify(leafHash, expectedRoot)` 는 걸음을 합쳐 올라간 값이 `expectedRoot` 와 같은지만 본다 — `expectedRoot` 가 진짜인지는 묻지 않는다.\
  검증하는 쪽이 가짜 뿌리를 믿고 있으면, 그 가짜 뿌리에 맞는 증명은 당연히 통과한다.
- Q: 그래서 실무는 무엇을 하는가?\
  A: **뿌리를 서명해 배포한다**.\
  CT 로그는 로그 서버가 서명한 STH(signed tree head)를 내놓고, 비트코인은 블록 헤더의 머클 루트를 작업증명 체인이 떠받치고, git 은 커밋에 GPG 서명을 걸 수 있다.\
  즉 신뢰의 뿌리(root of trust)는 **이 자료구조 밖**에 있다 — 머클 트리는 "그 값 하나만 믿으면 나머지는 내가 보장한다"까지만 한다.\
  (서명·STH 의 구체적 형태는 원본에 근거 없음 — 내 추론. README 는 "실무가 뿌리를 서명해 배포한다"까지만 적는다.)

> **신뢰의 뿌리(root of trust)** — 그 위의 모든 검증이 참이려면 반드시 먼저 믿어야 하는 값 하나.\
> 예: 머클 증명에서는 `expectedRoot` 가 그 값이고, 그것을 믿게 만드는 장치는 서명처럼 이 구조 밖에 있다.

- Q: 26번 경로 복사와 여기의 `withLeafReplaced` 는 같은 발상인데, 그 둘과 rope 의 차이는 무엇인가?\
  A: **바뀌는 것이 "값"이냐 "모양"이냐**가 다르다.\
  26번과 27번은 잎의 **값**만 갈고 자리(구조)는 그대로다 — 그래서 경로 위의 노드만 다시 만들면 되고 옆가지는 옛 객체를 그대로 가리킨다.\
  28번 로프에서는 잎을 **자르고 붙인다** — 길이가 달라지므로 그 위 내부 노드들이 들고 있는 `weight`(왼쪽 부분트리의 길이)가 바뀌고, 트리의 **모양 자체**가 달라진다.

```
  27번 머클 트리 — 잎을 갈면 경로만 다시 만든다
     [b0][b1][b2][b3]  ->  [b0][b1'][b2][b3]
     노드 7개 중 3개(잎1 + 경로2)만 새로 만든다. 자리·개수는 그대로다.

  28번 로프 — 잎을 자르고 붙인다
     "hello world"  ->  가운데에 "X" 를 넣는다
     잎 하나가 둘로 쪼개지고(split) 새 잎이 끼어들어 concat 된다.
     내부 노드의 weight 가 바뀌고 트리 모양이 달라진다. 대신 글자 복사는 여전히 O(log n) 어치뿐이다.

  공통점: 둘 다 옛 버전이 그대로 살아 있다 (아무도 노드를 안 고치므로)
  차이:   27번은 자리가 고정된 목록, 28번은 자리가 계속 움직이는 문자열
```

- Q: "자리가 고정된 목록"이 깨지면 27번에서는 무슨 일이 일어났는가?\
  A: 질문 4에서 본 대로 **트리를 다시 지어야 한다**(한계 3).\
  즉 로프가 매 편집마다 하는 일(잎을 쪼개고 붙이기)은 머클 트리에서는 "다시 짓기"에 해당한다.\
  로프는 그 연산을 O(log n) 으로 만들기 위해 잎에 **해시가 아니라 글자**를 담고, 내부 노드에 **왼쪽 길이 하나**만 두는 설계를 택한다.
- Q: 그래서 다음 구조가 답하는 질문은 무엇인가?\
  A: "이게 그대로인가"가 아니라 **"같은 데이터를 어떻게 놓아야 편집이 싸지는가"** 다.\
  01번 동적 배열은 연속으로 놓아 조회 O(1) 을 샀고 가운데 삽입에 O(n) 을 냈다.\
  28번 로프는 트리에 흩어 놓아 가운데 삽입 O(log n) 을 사고 조회에 O(log n) 을 낸다 — **같은 데이터, 다른 배치, 다른 워크로드**다.

**더 생각할 것**

- 27번에서 "블록을 끼워 넣을 수 없다"는 한계가 28번의 존재 이유를 정확히 가리킨다.\
  한계가 다음 장을 부르는 이 문제집의 배치가 여기서도 그대로다.
- 반대 방향의 조합도 실제로 쓰인다 — 로프의 노드에 해시를 들려 "편집 가능한 머클 트리"를 만들면 버전 대조와 편집을 함께 얻는다.\
  다만 그때는 편집마다 경로의 해시를 다시 계산해야 하므로 편집 비용에 해시 log n 번이 얹힌다(원본에 근거 없음 — 내 추론).
- 이 장에서 가장 오래 남는 문장은 성능이 아니라 검증의 자세 쪽이다.\
  "답이 맞는다"와 "옳게 동작한다"가 다르다는 것을 걸음 수 세는 테스트가, "검증했다"와 "검증할 게 없었다"가 다르다는 것을 빈 배치가, "확정적"과 "무조건"이 다르다는 것을 `ToyHash` 가 각각 보여줬다.
