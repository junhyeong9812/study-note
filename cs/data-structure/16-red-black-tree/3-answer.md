## 정답

### B. 자료구조 특성

#### 1. 왜 네 번째 답이 또 필요한가

- Q: 06번 이진 탐색 트리는 정렬 입력에서 정확히 무엇이 무너졌는가?\
  A: 모양이다.\
  BST 는 "새 키를 비교해서 내려가다가 빈 자리에 매단다"가 전부라, 들어오는 순서가 그대로 모양이 된다.\
  1, 2, 3, ... 을 순서대로 넣으면 새 키가 늘 최댓값이라 항상 오른쪽 끝에 붙는다.\
  결과는 오른쪽으로만 뻗은 한 줄 — 사실상 연결 리스트이고 높이가 n 이다.\
  찾기·넣기·지우기가 전부 O(log n) 이 아니라 O(n) 이 된다.

```text
  1,2,3,4,5 를 순서대로 넣은 BST(06번)        같은 입력을 넣은 레드블랙 트리(16번)

     (1)                                              (2B)
       \                                            /     \
        (2)                                      (1B)      (4B)
          \                                                /  \
           (3)                                          (3B)  (5B)
             \
              (4)                              높이 3  -- 어떤 순서로 넣어도 log n 근처
                \
                 (5)
  높이 5 = n. 찾기가 O(n) 으로 떨어진다
```

> **균형(balance)** — 뿌리에서 잎까지 가는 길들의 길이가 서로 크게 벌어지지 않는 성질.\
> 예: 높이가 log n 근처면 균형이 잡힌 것이고, 높이가 n 이면 한쪽으로 쏠린 것이다.

- Q: 12번 스킵 리스트는 무엇을 대가로 치렀는가?\
  A: **보장**을 내주고 **확률**을 받았다.\
  어느 노드를 몇 층까지 올릴지를 동전으로 정하기 때문에, 나쁜 입력이라는 개념 자체가 사라진다.\
  대신 나쁜 **동전 운**이 남는다 — 확률이 아주 낮을 뿐 최악 O(n) 을 막지는 못한다.\
  README 의 표현 그대로 "최악을 막지 못합니다. 확률이 낮을 뿐입니다".\
  응답 지연의 상한을 약속해야 하는 자리에서는 "거의 항상 빠르다"가 답이 되지 못한다.

- Q: 15번 B-트리는 무엇을 대가로 치렀는가?\
  A: **노드의 크기**를 내줬다.\
  B-트리는 회전 없이 균형을 잡는다 — 노드를 뚱뚱하게 만들고 뿌리가 쪼개질 때만 위로 자라기 때문에 모든 잎이 언제나 같은 깊이다.\
  그 대신 노드 하나가 키를 수백 개 담는 덩어리가 된다.\
  디스크에서는 그게 장점이다(블록 한 번 읽어 키 수백 개를 본다).\
  메모리 안에서는 낭비다 — 캐시 한 줄에 안 들어가고, 쓰지도 않을 키를 같이 끌고 다닌다.

> **캐시 라인(cache line)** — CPU 가 메모리에서 한 번에 퍼오는 고정 크기 덩어리(보통 64바이트).\
> 예: 노드가 그 안에 들어가면 노드 하나 읽는 데 메모리 접근이 한 번이고, 넘치면 여러 번이 된다.

- Q: 세 번째 답은 무엇인가?\
  A: 06번 BST 자신이다 — 균형 장치가 하나도 없는 원형이 첫 번째 답이고, 12번·15번이 그 뒤를 잇는다.\
  README 는 대안으로 12번과 15번 둘만 이름을 대고 "네 번째 답"이라고 쓴다.\
  그래서 앞의 셋은 06번(장치 없음) · 12번(확률) · 15번(뚱뚱한 노드)로 읽는 것이 자연스럽다.\
  (원본이 셋을 명시적으로 나열하지는 않는다 — 내 해석이다.)

- Q: 레드블랙 트리는 그 대가를 어떻게 피하는가?\
  A: 노드는 **이진 트리 그대로** 두고, 색 비트 하나만 더 든다.\
  그래서 15번처럼 노드가 커지지 않는다 — 메모리 안에서 쓰기 좋다.\
  균형은 동전이 아니라 **회전과 색 뒤집기로 강제**한다 — 그래서 12번과 달리 확률이 아니라 보장이다.\
  자바 `TreeMap`/`TreeSet`, C++ `std::map`, 리눅스 커널 스케줄러가 이것을 쓰는 이유다.

- Q: 그 대신 레드블랙 트리가 치르는 대가는 무엇인가?\
  A: **코드의 복잡도**다.\
  12번은 균형 유지 코드가 아예 없고, 15번은 회전이 없다.\
  16번은 회전 2종 + 색 뒤집기 + `balance` 3검사 + 삭제 쪽의 `moveRedLeft`/`moveRedRight` 를 전부 정확히 짜야 한다.\
  그리고 회전은 부모–자식 관계를 바꾸므로 넓은 범위를 건드린다 — 동시성에서는 12번의 국소적 갱신보다 불리하다.\
  이 챕터의 거래는 한 줄로 "코드를 늘려서 최악을 산다"다.

| | 06번 BST | 12번 스킵 리스트 | 15번 B-트리 | 16번 LLRB |
|---|---|---|---|---|
| 균형을 어떻게 얻나 | 못 얻는다 | 동전(확률) | 뚱뚱한 노드 + 위로 자라기 | 회전 + 색 |
| 정렬 입력 | O(n) 붕괴 | 상관없다 | 상관없다 | 상관없다 |
| 최악 보장 | 없다 | 확률적 | 있다 | **있다** |
| 노드 크기 | 작다 | 작다(층 포인터 배열) | **크다** | 작다(+색 1비트) |
| 균형 유지 코드 | 없다 | 없다 | split/merge | **회전 + flip** |
| 주 무대 | — | 메모리·동시성 | **디스크** | **메모리** |

**더 생각할 것**

- "네 번째 답"이 나왔다는 것은 앞의 셋이 틀렸다는 뜻이 아니다.\
  각자 다른 제약(디스크 · 동시성 · 코드 단순함) 아래서 최선이고, 16번은 "메모리 + 보장"이라는 칸을 채운다.
- 실무에서 정렬 자료구조를 고를 때 먼저 물어야 하는 것은 "어디에 사는가"다.\
  디스크면 15번, 락 경합이 문제면 12번, 단일 스레드 메모리면 16번이 기본값이다.
- 규모가 커지면 셋이 섞인다 — RocksDB 는 메모리에 스킵 리스트(memtable), 디스크에 정렬된 블록을 쓴다.\
  한 시스템 안에서 계층마다 다른 답을 쓰는 것이 보통이다.

#### 2. 검은 높이가 왜 균형의 정체인가

- Q: "모든 뿌리-잎 경로의 검은 링크 수가 같다"가 왜 균형인가?\
  A: 그 규칙 하나가 **모든 경로의 길이를 서로 묶어버리기** 때문이다.\
  경로의 길이는 검은 링크 수 + 빨간 링크 수다.\
  검은 링크 수는 규칙에 의해 모든 경로에서 똑같다(그 값을 검은 높이 b 라고 하자).\
  빨간 링크 수는 "빨강이 연달아 나올 수 없다"는 규칙에 의해 검은 링크 수를 넘을 수 없다.\
  그래서 경로 길이는 최소 b, 최대 2b 사이에 갇힌다 — 어떤 두 경로도 길이가 2배 넘게 벌어지지 못한다.

> **검은 높이(black height)** — 뿌리에서 잎까지 내려가며 지나는 검은 링크의 개수.\
> 예: 이 구현의 `blackHeight()` 가 왼쪽 한 줄만 훑으며 세는 값이고, 모든 경로에서 같아야 한다.

- Q: 가장 짧은 경로와 가장 긴 경로는 각각 어떤 모양인가?\
  A: 가장 짧은 경로는 **전부 검정**이다 — 길이 b.\
  가장 긴 경로는 **검정과 빨강이 번갈아** 나오는 모양이다 — 검정 b 개 사이사이에 빨강이 최대 b 개, 길이 2b.\
  빨강이 연달아 못 나오므로 빨강 하나 뒤에는 반드시 검정이 따라온다.\
  그래서 빨강의 개수가 검정의 개수를 넘을 수 없고, 2b 가 상한이 된다.

```text
  같은 트리 안의 두 경로 -- 검은 링크 수는 같고 전체 길이만 다르다

  가장 짧은 경로 (전부 검정)          가장 긴 경로 (검빨검빨...)
      (root B)                            (root B)
         |  검                               |  검
        (B)                                 (R)      <- 빨강
         |  검                               |  빨
        (B)                                 (B)
         |  검                               |  검
        (B)                                 (R)
       길이 3, 검은 링크 3                    |  빨
                                            (B)
                                            |  검
                                           (B)
                                      길이 6, 검은 링크 3

  검은 링크 수 b 는 같다 -> 길이는 b 와 2b 사이 -> 두 배를 못 넘는다
```

- Q: 높이 `2*log2(n+1)` 상한은 어떻게 나오는가?\
  A: 검은 높이가 b 인 트리는 최소한 **검은 노드만으로 된 깊이 b 의 완전 이진 트리**를 품고 있다.\
  그 완전 이진 트리의 노드 수가 `2^b - 1` 이므로 전체 노드 수 n 은 그보다 작을 수 없다.\
  `n >= 2^b - 1` → `2^b <= n + 1` → `b <= log2(n+1)`.\
  앞에서 본 것처럼 높이 h 는 2b 를 넘지 못하므로 `h <= 2b <= 2*log2(n+1)`.\
  이 식이 README 와 테스트에 그대로 박혀 있는 상한이다.

`RedBlackTreeMapTest.java` — 그 상한을 숫자로 못박는 테스트다.

```java
        @Test
        @DisplayName("정렬된 순서로 넣어도 높이가 log n 근처다")
        void sortedInsertStaysBalanced() {
            int n = 100_000;
            SortedTree<Integer, String> t = create();
            for (int i = 0; i < n; i++) {
                t.put(i, "v");
            }
            // 레드블랙 트리의 높이는 2*log2(n+1) 을 절대 안 넘는다. **확률이 아니라 보장이다.**
            int bound = (int) (2 * (Math.log(n + 1) / Math.log(2)));
            assertTrue(t.height() <= bound,
                    "높이 " + t.height() + " 가 상한 " + bound + " 을 넘었다");
            assertEquals(n, t.size());
            assertEquals(0, t.firstKey());
            assertEquals(n - 1, t.lastKey());
        }
```

- Q: 그 테스트가 쓰는 실제 숫자는 얼마인가?\
  A: n = 100,000 이면 `log2(100001) ≈ 16.6` 이므로 `bound = (int)(2 * 16.6) = 33` 이다.\
  10만 개를 **정렬된 순서로** 넣고도 높이가 33 이하여야 한다는 뜻이다.\
  같은 입력을 06번 BST 에 넣으면 높이가 100,000 이다.\
  `otherAdversarialOrders` 는 n = 50,000 으로 역순과 톱니(0, n-1, 1, n-2, ...) 두 순서를 같은 상한으로 검사한다.

- Q: 12번의 "확률적 균형"과 무엇이 다른가?\
  A: 상한이 **입력에 대한 명제**냐 **동전에 대한 명제**냐가 다르다.\
  레드블랙 트리의 `h <= 2*log2(n+1)` 은 어떤 입력 순서에서도, 매 순간, 예외 없이 참인 구조적 사실이다 — 불변식에서 유도된다.\
  스킵 리스트의 `O(log n)` 은 난수의 기대값이다 — 운이 나쁘면 한 층에 다 몰려 O(n) 이 될 수 있고, 확률이 낮을 뿐 0 은 아니다.\
  그래서 16번의 상한은 **반증하려면 불변식을 깨야** 하고, 12번의 상한은 **운이 나쁘면 그냥 안 지켜진다**.\
  p99.9 같은 꼬리 지연을 계약으로 약속해야 하는 시스템에서 이 차이가 갈린다.

> **보장(worst-case guarantee) 대 기대값(expected)** — 전자는 "어떤 경우에도 이 값을 넘지 않는다", 후자는 "평균적으로 이 정도다".\
> 예: 레드블랙 트리의 높이는 보장이고, 스킵 리스트의 높이는 기대값이다.

- Q: 불변식은 왜 계약 테스트와 별도로 검사해야 하는가?\
  A: **색만 엉망이고 답은 맞는 구현**이 얼마든지 가능하기 때문이다.\
  `put`/`get`/`remove` 의 반환값만 보는 테스트는 색을 한 번도 안 뒤집는 평범한 BST 도 통과시킨다.\
  그 구현은 정렬 입력에서 높이가 n 이 되어 조용히 느려질 뿐 답은 맞다.\
  그래서 `RedBlackTreeInvariantTest` 가 넣는 내내·지우는 내내 네 규칙을 직접 확인한다.

`RedBlackTreeInvariantTest.java` — 불변식을 직접 뜯어보는 헬퍼다.

```java
    private void checkNode(RedBlackTree.Node<Integer, String> h) {
        if (h == null) {
            return;
        }
        assertTrue(!RedBlackTree.isRed(h.right),
                "오른쪽으로 기운 빨간 링크가 있다 (키 " + h.key + "). 좌편향이 아니다");
        if (RedBlackTree.isRed(h)) {
            assertTrue(!RedBlackTree.isRed(h.left),
                    "빨간 노드가 연달아 있다 (키 " + h.key + ")");
        }
        checkNode(h.left);
        checkNode(h.right);
    }

    /** 검은 높이. 좌우가 다르면 -1. */
    private int blackHeightOrMinusOne(RedBlackTree.Node<Integer, String> h) {
        if (h == null) {
            return 0;
        }
        int l = blackHeightOrMinusOne(h.left);
        int r = blackHeightOrMinusOne(h.right);
        if (l < 0 || r < 0 || l != r) {
            return -1;
        }
        return l + (RedBlackTree.isRed(h) ? 0 : 1);
    }
```

- Q: `blackHeightOrMinusOne` 이 -1 을 전파하는 이유는?\
  A: "어느 한 곳이라도 좌우 검은 높이가 다르면 트리 전체가 실격"이라는 것을 한 번의 순회로 잡기 위해서다.\
  좌우가 다르면 -1 을 만들고, 위로 올라가면서 `l < 0 || r < 0` 조건이 그 -1 을 계속 끌고 간다.\
  그래서 뿌리에서 받은 값이 0 이상인지만 보면 전 노드의 균형을 확인한 것이 된다.\
  구현 쪽 `blackHeight()` 는 왼쪽 한 줄만 세는데, 그것으로 충분한 이유가 바로 이 불변식이 이미 보장돼 있기 때문이다.

**더 생각할 것**

- 불변식이 "성능을 만든다"는 관계가 이 챕터의 핵심이다.\
  코드 어디에도 "높이를 33 이하로 유지하라"는 문장은 없다 — 색 규칙 네 줄이 그 결과를 낳는다.
- 실무에서 자기가 만든 자료구조를 믿으려면 계약 테스트만으로 부족하다.\
  "구조가 지켜지는가"를 별도로 검사하는 테스트가 있어야 조용한 성능 붕괴를 잡는다.
- 규모가 커질수록 이 차이가 커진다.\
  n = 100 이면 BST 가 무너져도 티가 안 나고, n = 10^6 이면 O(n) 탐색이 곧 장애다.

#### 3. 2-3 트리로 읽기 — 빨간 링크는 무엇인가

- Q: 빨간 링크는 2-3 트리의 무엇에 대응하는가?\
  A: **3-노드(키 2개짜리 노드) 안쪽의 접착제**다.\
  빨간 링크로 이어진 두 노드를 한 덩어리로 감싸 보면 그게 키 2개를 담은 노드 하나다.\
  즉 빨간 링크는 트리의 "층"을 만드는 진짜 간선이 아니라, 한 노드 안에서 키 두 개를 붙여 놓는 표시다.\
  그래서 검은 높이를 셀 때 빨간 링크는 세지 않는다 — 층이 아니기 때문이다.

- Q: 검은 링크는 무엇에 대응하는가?\
  A: 2-3 트리의 **진짜 간선**이다.\
  부모 노드에서 자식 노드로 내려가는, 층이 하나 깊어지는 그 선이다.\
  그래서 검은 링크만 세면 그것이 곧 2-3 트리의 층수가 된다.

> **2-3 트리** — 한 노드에 키를 1개(2-노드) 또는 2개(3-노드) 담고, 모든 잎이 같은 깊이인 균형 트리.\
> 예: LLRB 에서 빨간 링크로 묶인 두 노드가 3-노드 하나에 해당한다.

```text
  레드블랙(이진) 그림                        같은 것을 2-3 트리로 읽으면

      (BB)                                        [ B ]            2-노드
      검은 링크로만 매달린 홀몸 노드

      (FB)                                        [ E F ]          3-노드
      //                                          키 두 개가 한 덩어리
   (ER)
      빨간 링크로 붙은 두 노드

      (DB)                                            [ D ]
     /    \                                          /     \
  (BB)     (FB)                    ->            [ B ]     [ F ]
  /  \     /  \                                  /   \     /   \
(AB)(CB) (EB)(GB)                              [A]  [C]  [E]  [G]
  검은 링크 2 개 = 2-3 트리 2 층
```

- Q: `flipColors` 는 15번 B-트리의 어느 동작인가?\
  A: **split(분할)** 이다 — 꽉 찬 노드를 쪼개고 가운데 키를 부모로 올리는 동작.\
  양쪽 자식이 모두 빨갛다는 것은 2-3 트리로 읽으면 키 세 개가 한 덩어리로 붙은 4-노드라는 뜻이다.\
  2-3 트리에는 4-노드가 없으므로 쪼개야 한다.\
  `flipColors` 는 아래 두 링크를 검게(자식을 독립시키고) 위 링크를 붉게(가운데 키를 부모 쪽으로 붙임) 만든다 — 그게 정확히 split 이다.

> **split / merge / borrow** — B-트리 용어. 꽉 찬 노드 쪼개기 / 빈약한 노드 합치기 / 형제에게서 키 하나 빌려오기.\
> 예: LLRB 의 `flipColors` 가 split, `moveRedLeft` 의 두 갈래가 각각 merge 와 borrow 다.

`impl/RedBlackTree.java` — split 을 수행하는 세 줄이다.

```java
    private void flipColors(Node<K, V> h) {
        h.color = !h.color;
        h.left.color = !h.left.color;
        h.right.color = !h.right.color;
    }
```

```text
  flipColors 전 (4-노드)                   flipColors 후 (쪼개짐)

        (FB)                                    (FR)   <- F 로 들어가는 링크가 붉어졌다
       //   \\                 ->               /   \     = F 가 부모 덩어리로 올라간 것
    (ER)     (GR)                            (EB)    (GB)

  2-3 트리로 읽으면
    [ E F G ]  <- 있을 수 없는 4-노드          [ F ] 가 부모로 올라가고
                                              [ E ] 와 [ G ] 가 그 아래 2-노드로 독립

  검은 높이 : 아래 두 링크가 같이 검어져 모든 경로가 동시에 +1
              어느 한 경로만 늘어나는 일이 없으므로 불변식 [5] 가 유지된다
```

- Q: "검은 높이가 곧 2-3 트리의 높이"라는 말을 테스트가 어떻게 숫자로 확인하는가?\
  A: 2-3 트리는 노드마다 자식이 2개 또는 3개이므로, 키 n 개를 담은 2-3 트리의 높이는 `log3(n)` 과 `log2(n)` 사이다.\
  그래서 `blackHeightIsTwoThreeHeight` 는 10만 개를 넣은 뒤 검은 높이가 그 구간에 들어오는지를 본다.\
  그리고 전체 높이가 검은 높이의 2배를 넘지 않는지도 같이 본다.

`RedBlackTreeInvariantTest.java` — 2-3 대응을 숫자로 확인하는 테스트다.

```java
        @Test
        @DisplayName("검은 높이가 2-3 트리의 높이다")
        void blackHeightIsTwoThreeHeight() {
            // 빨간 링크로 이어진 두 노드가 2-3 트리의 키 2개짜리 노드다.
            // 그래서 **검은 링크만 세면** 그게 2-3 트리의 층수다.
            RedBlackTree<Integer, String> t = new RedBlackTree<>();
            for (int i = 0; i < 100_000; i++) {
                t.put(i, "v");
            }
            int bh = t.blackHeight();
            double log2 = Math.log(100_000) / Math.log(2);
            double log3 = Math.log(100_000) / Math.log(3);
            assertTrue(bh >= log3 - 1 && bh <= log2 + 1,
                    "검은 높이 " + bh + " 가 log3(n)=" + (int) log3
                            + " 과 log2(n)=" + (int) log2 + " 사이여야 한다");
            assertTrue(t.height() <= 2 * bh,
                    "전체 높이가 검은 높이의 두 배를 넘었다: " + t.height() + " 대 " + bh);
        }
```

- Q: 좌편향 규칙이 있는 이유는 무엇인가?\
  A: **모양의 가짓수를 줄이려고** 있다.\
  빨간 링크를 좌우 아무 데나 허용하면 3-노드를 표현하는 이진 모양이 두 가지가 된다(왼쪽에 붙은 것 / 오른쪽에 붙은 것).\
  좌편향은 그중 하나만 합법으로 못박는다 — 3-노드의 표현이 딱 하나가 된다.\
  표현이 하나면 "고쳐야 할 상황"도 그만큼 줄고, `balance` 가 세 줄로 끝난다.

> **좌편향(left-leaning)** — 빨간 링크가 부모의 왼쪽 자식으로만 갈 수 있게 제한하는 규칙.\
> 예: 오른쪽에 빨간 링크가 생기면 `rotateLeft` 가 즉시 왼쪽으로 눕힌다.

- Q: 좌편향이 없으면 왜 코드가 두 배가 되는가?\
  A: 좌우를 다 허용하면 대응 구조가 2-3 트리가 아니라 **2-3-4 트리**가 되기 때문이다.\
  노드가 키를 3개까지 담을 수 있으니 표현해야 할 덩어리가 2-노드·3-노드(2가지 모양)·4-노드로 늘어난다.\
  고쳐야 할 상황이 왼쪽-왼쪽, 왼쪽-오른쪽, 오른쪽-왼쪽, 오른쪽-오른쪽 네 가지로 갈라지고, 그 각각을 거울상으로 두 벌 써야 한다.\
  고전적(CLRS) 구현이 "삼촌 노드의 색"을 따로 보고 여러 케이스를 분기하는 이유가 그것이다.\
  LLRB 는 그 경우의 수를 `balance` 의 세 검사로 압축한다 — README 가 "코드가 두 배가 된다"고 쓴 그 차이다.

- Q: 좌편향의 대가는 없는가?\
  A: 있다.\
  오른쪽에 생긴 빨간 링크를 **매번 눕혀야** 하므로, 좌우를 다 허용하는 구현이면 안 했을 회전이 추가로 일어난다.\
  또 삭제 쪽이 대칭이 아니게 되어 `moveRedLeft` 와 `moveRedRight` 가 서로 다른 모양이 된다(거울상이지만 줄 수가 다르다).\
  즉 "삽입 쪽 코드를 줄인 대신 회전을 조금 더 하고, 삭제 쪽의 비대칭을 떠안는" 거래다.

**더 생각할 것**

- 이 대응을 한 번 보고 나면 `balance` 의 세 줄이 암기가 아니라 번역이 된다 — "4-노드면 쪼갠다", "3-노드는 왼쪽으로 붙인다".\
  15번을 먼저 풀라는 README 의 요구가 그 때문이다.
- 실무에서 쓰는 `TreeMap` 은 고전적(좌우 허용) 레드블랙 트리다.\
  즉 LLRB 는 "가르치기 좋은 단순화"이고, 표준 라이브러리는 회전 횟수를 줄이려고 복잡한 쪽을 택했다.
- 같은 자료구조를 다른 모델로 읽는 것(이진 트리 ↔ 2-3 트리)은 이 문제집 전체의 도구다.\
  14번 유니온 파인드를 숲으로 읽는 것, 17번 펜윅을 비트 패턴으로 읽는 것이 같은 종류다.

#### 4. 회전의 색 · 새 노드의 색

- Q: 회전이 링크만 옮기고 색을 안 옮기면 어떤 불변식이 즉시 깨지는가?\
  A: **[5] 검은 높이가 같다**가 깨진다.\
  회전은 부모와 자식의 상하 관계를 바꾸는데, 색은 "그 노드로 들어오는 링크의 색"이다.\
  위치가 바뀌었는데 색을 그대로 두면, 위에서 보이는 링크의 색이 달라져 그 부분트리를 지나는 경로의 검은 링크 수가 달라진다.\
  README 가 "빠뜨리면 26개 중 16개가 무너진다"고 적어둔 자리다.

`impl/RedBlackTree.java` — 마지막 두 줄이 색을 옮기는 부분이다.

```java
    private Node<K, V> rotateLeft(Node<K, V> h) {
        Node<K, V> x = h.right;
        h.right = x.left;
        x.left = h;
        x.color = h.color;
        h.color = RED;
        return x;
    }
```

- Q: 구체적으로 어떻게 깨지는지 그림으로 보면?\
  A: 위로 올라간 x 가 원래 빨강이었다면, 색을 안 옮길 경우 위에서 그 부분트리로 들어오는 링크가 검정에서 빨강으로 바뀐다.\
  그러면 그 부분트리를 지나는 모든 경로의 검은 링크 수가 1 줄어든다.\
  형제 쪽 경로는 그대로이므로 좌우 검은 높이가 갈린다.\
  `x.color = h.color; h.color = RED;` 두 줄이 "위에서 본 색은 그대로, 안쪽에 빨강 하나"를 유지시켜 그 일을 막는다.

```text
  rotateLeft(h) -- 색까지 옮기는 경우 (정상)

  before                                  after
       (h:검)                                  (x:검)   <- h 가 쓰던 색을 물려받았다
       /   \\                                 //    \
    (A)     (x:빨)          ->             (h:빨)     (C)
            /   \                          /    \
         (B)     (C)                    (A)      (B)

  위에서 h 로 들어오던 링크 = 검정        위에서 x 로 들어오는 링크 = 검정  (그대로)
  A 로 가는 경로의 검은 링크 : h(검) 1개   A 로 가는 경로 : x(검) 1 + h(빨) 0 = 1개  (그대로)


  rotateLeft(h) -- 색을 안 옮기는 경우 (버그)

  before                                  after
       (h:검)                                  (x:빨)   <- 빨간 채로 위에 올라갔다
       /   \\                                 //    \
    (A)     (x:빨)          ->             (h:검)     (C)
            /   \                          /    \
         (B)     (C)                    (A)      (B)

  위에서 x 로 들어오는 링크 = 빨강 -> 이 부분트리를 지나는 모든 경로의 검은 링크가 1 줄었다
  형제 쪽은 그대로다 -> 좌우 검은 높이가 갈린다 -> 불변식 [5] 붕괴
```

- Q: 회전이 순서(BST 성질)를 깨지 않는 이유는 무엇인가?\
  A: 옮기는 것이 "가운데 부분트리" 하나뿐이기 때문이다.\
  회전 전후 모두 `A < h < B < x < C` 라는 대소 관계가 그대로 유지된다.\
  A 와 C 는 손대지 않고, B 만 h 의 오른쪽에서 x 의 왼쪽으로 자리를 바꾼다 — B 는 양쪽 모두 "h 보다 크고 x 보다 작은" 자리다.\
  그래서 중위 순회 결과가 회전 전후로 동일하다(테스트 `assertInvariants` 가 매번 `keys()` 의 정렬을 확인한다).

- Q: 새 노드를 검은색으로 넣으면 무엇이 깨지는가?\
  A: 역시 **[5] 검은 높이**다.\
  잎에 검은 링크를 하나 새로 매달면 그 경로만 검은 링크가 1개 늘어난다.\
  다른 경로는 그대로이므로 즉시 불균형이다.\
  더 나쁜 것은 이 위반이 **국소적으로 고쳐지지 않는다**는 점이다 — 검은 높이는 트리 전체의 성질이라 뿌리까지 올라가며 모든 경로를 맞춰야 한다.

- Q: 빨강으로 넣으면 왜 안 깨지는가?\
  A: 빨간 링크는 검은 높이 계산에 들어가지 않기 때문이다.\
  2-3 트리로 읽으면 "새 노드를 새 층에 만드는 것"이 아니라 **"기존 노드에 키를 하나 더 끼워 넣는 것"** 이다.\
  층이 안 늘어나니 검은 높이도 그대로다.\
  README 의 "2-3 트리로 읽으면 기존 노드에 키를 하나 더 끼워 넣는 것"이 바로 이 말이다.

`impl/RedBlackTree.java` — 새 노드는 항상 RED 다.

```java
    private Node<K, V> put(Node<K, V> h, K key, V value, Object[] old) {
        if (h == null) {
            size++;
            return new Node<>(key, value, RED);
        }
        int cmp = key.compareTo(h.key);
        if (cmp < 0) {
            h.left = put(h.left, key, value, old);
        } else if (cmp > 0) {
            h.right = put(h.right, key, value, old);
        } else {
            old[0] = h.value;
            h.value = value;
        }
        return balance(h);
    }
```

```text
  (AB) 하나만 있는 트리에 B 를 넣는다. 검은 높이는 "잎 아래의 null 까지" 센다

  넣기 전                검은색으로 넣으면              빨간색으로 넣으면
     (AB)                   (AB)                          (AB)
     /  \                   /   \                         /   \\
  null  null            null     (BB)                  null     (BR)
                                 /  \                           /  \
                              null  null                     null  null

  왼쪽 null 까지 : A = 1   왼쪽 null 까지 : A = 1        왼쪽 null 까지 : A = 1
  오른쪽 null 까지 : A = 1  오른쪽 null 까지 : A,B = 2    오른쪽 null 까지 : A(검)+B(빨) = 1
                           좌우가 1 대 2 -> [5] 붕괴      좌우가 1 대 1 -> [5] 그대로

  검게 넣으면 : 검은 높이가 그 경로만 +1. 고치려면 트리 전체의 경로를 다시 맞춰야 한다
  빨갛게 넣으면 : [5] 는 그대로. 대신 [3] 좌편향(오른쪽에 빨강)이 깨진다
                 -> balance 의 [1] rotateLeft 가 O(1) 로 눕히면 끝
```

- Q: 그럼 빨강으로 넣으면 무엇이 깨지고, 누가 고치는가?\
  A: [3] 좌편향(새 노드가 오른쪽에 붙었을 때)과 [4] 연속 빨강(부모가 이미 빨간 링크였을 때)이다.\
  둘 다 **한 노드와 그 자식 두 개만 보면 판정되는 국소적 위반**이다.\
  그래서 `balance(h)` 가 회전 한두 번과 색 세 개를 바꾸는 O(1) 작업으로 고친다.\
  고치는 과정에서 위반이 위로 한 칸 올라갈 수는 있는데, 재귀가 돌아 나오는 길에 부모의 `balance` 가 다시 잡는다.

- Q: 뿌리는 왜 마지막에 검게 강제하는가?\
  A: `flipColors` 가 뿌리까지 올라오면 뿌리가 빨개질 수 있기 때문이다.\
  뿌리 위에는 부모가 없으므로 그 빨강을 받아줄 곳이 없다 — `root.color = BLACK` 이 그 자리다.\
  이때 모든 경로의 검은 링크가 동시에 1 늘어난다.\
  **트리가 위로 자라는 유일한 지점**이고, 15번 B-트리에서 뿌리가 쪼개질 때만 높이가 느는 것과 똑같다.

**더 생각할 것**

- "색을 옮긴다"가 헷갈리는 이유는 색이 노드 필드인데 뜻은 링크이기 때문이다.\
  구현을 읽을 때 `x.color` 를 "x 로 들어오는 부모 링크의 색"으로 소리 내어 바꿔 읽으면 회전 코드가 훨씬 쉬워진다.
- 새 노드를 빨강으로 넣는다는 선택은 "고치기 쉬운 위반을 일부러 만든다"는 설계다.\
  전역 불변식(검은 높이)은 지키고 국소 불변식(색 배치)만 깨는 쪽으로 문제를 옮긴 것이다.
- 규모가 커져도 이 성질은 그대로다 — 위반이 국소적이라 고치는 비용이 n 과 무관하다.\
  전역 위반이었다면 삽입 한 번이 O(n) 이 되어 구조 자체가 성립하지 않는다.

#### 5. `balance` 세 검사의 순서가 계약인 이유

- Q: 세 검사는 각각 무엇을 고치는가?\
  A: [1] `isRed(h.right) && !isRed(h.left)` → `rotateLeft` — 불변식 [3] 좌편향 위반을 고친다.\
  [2] `isRed(h.left) && isRed(h.left.left)` → `rotateRight` — 불변식 [4] 연속 빨강을 고친다.\
  [3] `isRed(h.left) && isRed(h.right)` → `flipColors` — 4-노드를 쪼갠다(split).\
  셋 다 조건이 맞을 때만 실행되고, 실행되면 `h` 가 새 부분트리 뿌리로 바뀐다.

`impl/RedBlackTree.java` — 이 메서드가 이 챕터의 심장이다.

```java
    private Node<K, V> balance(Node<K, V> h) {
        if (isRed(h.right) && !isRed(h.left)) {
            h = rotateLeft(h);
        }
        if (isRed(h.left) && isRed(h.left.left)) {
            h = rotateRight(h);
        }
        if (isRed(h.left) && isRed(h.right)) {
            flipColors(h);
        }
        return h;
    }
```

- Q: [1] 이 왜 맨 앞이어야 하는가?\
  A: **[1] 만이 오른쪽을 본다**.\
  [2] 와 [3] 의 조건은 `h.left`, `h.left.left` 처럼 전부 왼쪽 말로 쓰여 있다.\
  그래서 빨간 링크가 아직 오른쪽에 남아 있으면 [2] 는 그것을 아예 보지 못한다 — 연속 빨강이 오른쪽에 있어도 검사가 통과해버린다.\
  [1] 은 "빨강을 왼쪽으로 정규화하는 단계"이고, 그 정규화가 끝나야 나머지 검사가 의미를 갖는다.

> **정규화(normalization)** — 여러 모양으로 나타날 수 있는 상태를 미리 한 가지 모양으로 바꿔 두어, 뒤따르는 처리에서 경우의 수를 없애는 것.\
> 예: `balance` 의 [1] 이 오른쪽 빨강을 왼쪽으로 눕혀 두면, [2]·[3] 은 왼쪽만 보면 된다.

```text
  [1] 이 하는 일 = "오른쪽 빨강을 왼쪽으로 정규화"

  before                       rotateLeft(h)              after
      (AB)                                                    (BB)
          \\                        ->                        //
           (BR)                                            (AR)

  이 단계를 건너뛰면, 아래 [2] 의 조건 isRed(h.left) && isRed(h.left.left) 은
  h.left 가 null 이라 false 가 되어 그냥 지나간다 -> 위반이 고쳐지지 않은 채
  return h 로 부모에게 올라간다 (README : "불변식이 깨진 채로 위로 올라간다")
```

- Q: [2] 가 [3] 의 조건을 어떻게 만들어 주는가?\
  A: **[2] 가 실행되면 [3] 의 조건이 반드시 성립한다.**\
  `rotateRight(h)` 는 `x = h.left; h.left = x.right; x.right = h; x.color = h.color; h.color = RED;` 다.\
  실행 전제가 `isRed(h.left) && isRed(h.left.left)` 였으므로, 새 뿌리 x 의 왼쪽 자식은 원래의 `h.left.left`(빨강)이고 오른쪽 자식은 원래의 h 인데 마지막 줄에서 RED 가 됐다.\
  즉 양쪽 자식이 모두 빨강 — [3] 의 조건 그대로다.\
  그래서 [2] 와 [3] 은 사실상 "세우고 나서 쪼갠다"는 한 동작의 두 박자다.

```text
  [2] -> [3] 연쇄 : 한 줄로 선 빨강 두 개를 세운 뒤 반드시 쪼갠다

  들어올 때                 [2] rotateRight(G)          [3] flipColors(F)
      (GB)                       (FB)                        (FR)
      //                        //    \\           ->         /   \
    (FR)          ->         (ER)      (GR)                (EB)   (GB)
    //
  (ER)                    양쪽이 다 빨강 = [3] 조건 성립      4-노드가 쪼개지고
  연속 빨강 = [4] 위반     (이건 우연이 아니라 코드가 만든다)   F 가 부모 쪽으로 올라간다

  put() 이 끝나면 root.color = BLACK 으로 (FR) 이 (FB) 가 된다
```

- Q: 반대로 [1] 뒤에 [2] 가 이어지는 일은 있는가?\
  A: 없다 — 코드에서 바로 따라 나온다.\
  [1] 의 실행 전제가 `!isRed(h.left)` 이고, `rotateLeft` 후 새 뿌리의 `left` 는 옛 h(빨강)이며 그 `left` 는 손대지 않은 옛 `h.left`(빨강 아님)이다.\
  [2] 의 조건 `isRed(h.left) && isRed(h.left.left)` 에서 뒤쪽이 false 라 걸리지 않는다.\
  [1] 이 만드는 다음 단계는 [3] 쪽이다 — 옛 `h.right.right` 가 빨강이었다면 회전 후 양쪽이 빨개져 [3] 이 걸린다.\
  그리고 [2] 의 조건은 보통 **자식 쪽에서 [1] 이 한 번 돌고 올라온 결과**로 만들어진다(아래 3-노드 오른쪽에 새 키가 들어온 경우).

- Q: 순서를 바꾸면 무슨 일이 생기는가?\
  A: [2]·[3] 을 [1] 앞에 두면, 위에서 본 대로 오른쪽에 있는 빨강을 못 보고 지나쳐 위반이 부모로 새어 올라간다.\
  [3] 을 [2] 앞에 두면, 4-노드를 **엉뚱한 자리에서** 쪼개게 된다 — 부모로 올려야 할 키는 가운데 키인데 [2] 를 안 거친 상태에서는 `h` 가 가운데 키가 아니다.\
  결과는 2-3 대응이 어긋난 트리이고, 그 어긋남은 몇 번의 삽입 뒤 다른 자리에서 불변식 위반으로 터진다.\
  README 가 "순서가 계약"이라고 못박은 이유다.

- Q: `else if` 가 아니라 연달아 일어나야 하는 이유는?\
  A: [2] 가 실행되면 **[3] 의 조건이 항상 성립하기 때문**이다(위에서 증명).\
  `else if` 로 묶으면 [2] 가 걸린 순간 [3] 이 건너뛰어지고, 쪼개지지 않은 4-노드가 그대로 남는다.\
  2-3 트리로 읽으면 있을 수 없는 노드를 만든 것이고, 다음 삽입이 그쪽으로 오면 연속 빨강이나 좌편향 위반이 생긴다.\
  즉 세 `if` 는 "셋 중 하나를 고르는 분기"가 아니라 **"순서대로 통과시키는 파이프라인"** 이다.

- Q: 세 검사가 `h` 를 계속 재대입하는 것(`h = rotateLeft(h)`)의 의미는?\
  A: 각 단계의 검사가 **직전 단계의 결과 위에서** 이뤄진다는 뜻이다.\
  회전은 부분트리의 뿌리를 바꾸므로, 재대입하지 않으면 [2]·[3] 이 이미 밀려난 옛 노드를 검사하게 된다.\
  그리고 마지막 `return h` 가 그 최종 뿌리를 부모에게 돌려준다 — 7번에서 볼 "반환값 재대입" 방식의 한쪽 끝이다.\
  재대입을 빼먹으면 회전은 일어나는데 그 결과가 트리에 반영되지 않아, 조용히 옛 모양이 남는다.

- Q: `balance` 는 삽입에서만 쓰이는가?\
  A: 아니다 — `put`, `deleteMin`, `delete` 셋 다 마지막 줄이 `return balance(h);` 다.\
  삽입에서는 "새로 붙인 빨강"을 정리하고, 삭제에서는 "내려가며 일부러 만들어 둔 빨강"을 되정리한다.\
  즉 같은 세 줄이 두 방향의 뒷정리를 전부 맡는다.\
  이 재사용이 LLRB 가 짧은 이유의 절반이고, 나머지 절반이 6번의 `flipColors` 양방향성이다.

**더 생각할 것**

- "각 단계가 다음 단계의 조건을 만든다"는 구조는 컴파일러 패스나 데이터 파이프라인과 같은 모양이다.\
  단계를 독립적인 규칙 셋으로 보면 순서가 자유롭지만, 앞 단계가 뒤 단계의 전제를 생산하는 순간 순서가 계약이 된다.
- 이런 코드는 리팩토링에서 가장 잘 깨진다 — "세 개의 if 를 else if 로 합치면 깔끔하다"는 유혹이 정확히 버그다.\
  주석이 아니라 테스트(불변식 검사)가 그것을 막아야 한다.
- 규모가 커져도 `balance` 는 O(1) 이다.\
  비용이 늘어나는 것은 호출 횟수(경로 길이 = O(log n))뿐이라, 삽입 한 번은 언제나 O(log n) 이다.

#### 6. `flipColors` 는 왜 대입이 아니라 반전인가

- Q: 넣기에서 `flipColors` 는 어느 방향인가?\
  A: **검(h) + 빨빨(두 자식) → 빨(h) + 검검(두 자식)** 방향이다.\
  4-노드를 쪼개고 가운데 키를 부모 쪽으로 올리는 split 이다.\
  모든 경로의 검은 링크가 동시에 +1 된다(아래 두 링크가 검어지고 위 링크 하나가 붉어지므로).

- Q: 지우기에서는 어느 방향인가?\
  A: **빨(h) + 검검(두 자식) → 검(h) + 빨빨(두 자식)** 방향이다 — 정확히 반대다.\
  `moveRedLeft` 의 첫 줄이 그것이고, "내가 쥐고 있던 빨강을 두 자식에게 나눠 준다"는 뜻이다.\
  이번엔 모든 경로의 검은 링크가 동시에 -1 된다.\
  2-3 트리로 읽으면 부모의 키 하나를 내려 자식 둘과 합치는 merge 쪽 동작이다.

```text
  같은 세 줄이 양방향으로 쓰인다

  넣기 (split, 검은 높이 +1)              지우기 (merge 준비, 검은 높이 -1)

      (hB)                                     (hR)
     //   \\        --- flipColors --->        /   \
  (LR)     (RR)                             (LB)   (RB)

      (hR)                                     (hB)
      /   \         <--- flipColors ---       //   \\
   (LB)   (RB)                             (LR)     (RR)

  반전(!)이라서 어느 방향에서 들어와도 같은 코드가 맞는 결과를 낸다
  대입(h.color = RED; h.left.color = BLACK; ...)이면 한쪽 방향만 맞다
```

- Q: 대입으로 쓰면 무엇이 깨지는가?\
  A: 삽입 쪽을 기준으로 `h.color = RED; h.left.color = BLACK; h.right.color = BLACK;` 이라고 못박았다고 하자.\
  삽입에서는 맞는다 — 들어올 때 h 가 검정, 자식이 빨강이었으니까.\
  삭제의 `moveRedLeft` 에서는 정반대 상태(h 빨강, 자식 검정)로 들어오는데, 이 코드는 h 를 다시 빨강으로 두고 자식을 검정으로 둔다 — **아무 일도 일어나지 않는다.**\
  자식에게 빨강을 넘겨주지 못했으므로 "빨강을 확보하고 내려간다"는 삭제의 전제가 무너지고, 검은 노드를 그냥 떼어내 [5] 가 깨진다.\
  README 가 "대입으로 쓰면 지우기 쪽이 깨진다"고 쓴 그 자리다.

> **자기 역원(involution)** — 두 번 적용하면 원래대로 돌아오는 연산.\
> 예: 불리언 반전 `!x` 는 두 번 하면 제자리다. `flipColors` 가 그 성질 덕에 양방향으로 쓰인다.

`impl/RedBlackTree.java` — 반전이라서 방향을 묻지 않는다.

```java
    private void flipColors(Node<K, V> h) {
        h.color = !h.color;
        h.left.color = !h.left.color;
        h.right.color = !h.right.color;
    }
```

- Q: 왜 같은 코드가 양방향에 쓰일 수 있는가?\
  A: 반전이 **현재 상태를 읽어서 뒤집는** 연산이기 때문이다.\
  대입은 "결과 상태"를 코드에 적어 넣는 것이라 들어오는 상태를 가정해야 한다.\
  반전은 결과를 적지 않고 관계만 적는다 — "h 와 두 자식의 색을 서로 반대로 만든다".\
  그 관계가 split 과 merge 양쪽에서 똑같이 필요한 관계라서 코드 하나로 충분하다.

- Q: 색을 뒤집는데 왜 검은 높이 불변식이 안 깨지는가?\
  A: 세 링크를 **동시에** 뒤집기 때문이다.\
  h 를 지나 아래로 가는 모든 경로는 h 링크 하나와 두 자식 링크 중 하나를 반드시 지난다.\
  split 방향이면 `h: 검→빨`(-1) 과 `자식: 빨→검`(+1) 이 상쇄되고, 그 부분트리 밖에서 볼 때는 h 링크가 빨개진 만큼 위쪽 경로가 -1 이 되며 아래쪽이 +1 이 되어 전체적으로 균형이 유지된다.\
  한쪽만 뒤집으면 상쇄가 안 되므로 즉시 깨진다 — 그래서 세 줄이 한 덩어리여야 한다.

`impl/RedBlackTree.java` — `moveRedLeft` 안에 `flipColors` 가 두 번 나온다.

```java
    private Node<K, V> moveRedLeft(Node<K, V> h) {
        flipColors(h);
        if (isRed(h.right.left)) {
            h.right = rotateRight(h.right);
            h = rotateLeft(h);
            flipColors(h);
        }
        return h;
    }
```

- Q: `moveRedLeft` 의 두 번째 `flipColors` 는 또 어느 방향인가?\
  A: 다시 split 방향(검 + 빨빨 → 빨 + 검검)이다.\
  첫 번째 flip 으로 두 자식을 빨갛게 만든 뒤, 회전 두 번으로 형제 쪽 키 하나를 h 자리로 끌어왔다.\
  그 시점에서 h 는 검정이고 두 자식이 빨강인 상태라, 다시 뒤집어 "빌려온 키를 부모 자리에 앉히고 왼쪽에만 빨강을 남기는" 정리가 된다.\
  같은 메서드 안에서 한 번은 merge 방향, 한 번은 split 방향으로 쓰이는 것이 이 코드의 압권이다.

- Q: `moveRedRight` 는 왜 줄 수가 다른가?\
  A: 좌편향이라 좌우가 대칭이 아니기 때문이다.\
  `moveRedRight` 는 `flipColors(h); if (isRed(h.left.left)) { h = rotateRight(h); flipColors(h); }` 로 회전이 한 번뿐이다.\
  왼쪽은 이미 빨강이 붙어 있는 쪽이라 한 번만 세우면 되고, 오른쪽은 빨강을 왼쪽에서 끌어와야 해서 두 번 돌린다.\
  좌편향이 삽입 코드를 줄인 대가를 삭제 쪽에서 이렇게 치른다(3번의 마지막 갈래와 같은 이야기다).

**더 생각할 것**

- "상태를 적지 말고 관계를 적어라"는 이 절의 교훈은 자료구조 밖에서도 통한다.\
  토글 기능을 `set(true)` 로 구현하면 호출 지점마다 현재 상태를 알아야 하고, `toggle()` 로 구현하면 몰라도 된다.
- 대신 반전은 **잘못된 상태로 들어오면 잘못된 상태를 내놓는다**.\
  `flipColors` 가 안전한 것은 호출 지점 두 곳이 모두 전제 조건을 확실히 만들어 두기 때문이다 — 반전이 마법이라서가 아니다.
- 규모와 무관하게 세 줄이다.\
  이 챕터에서 "코드가 늘었다"는 부담의 상당 부분이 이런 재사용으로 상쇄된다.

#### 7. 반환값 재대입은 왜 부모 포인터를 없애는가

- Q: 재대입 방식이 정확히 무슨 일을 하는가?\
  A: 모든 내부 메서드가 **"고친 부분트리의 새 뿌리"를 반환**하고, 부모가 그 반환값을 자기 슬롯에 다시 넣는 방식이다.\
  `h.left = put(h.left, key, value, old);` 한 줄이 전부다.\
  내려갈 때는 평범한 BST 탐색이고, 돌아 나올 때 각 노드가 `return balance(h);` 로 자기 자리를 갱신한다.\
  뿌리는 `root = put(root, key, value, old);` 가 같은 일을 한다.

`impl/RedBlackTree.java` — 공개 `put` 이 뿌리 슬롯을 맡는다.

```java
    public V put(K key, V value) {
        requireKey(key);
        if (value == null) {
            throw new IllegalArgumentException("값은 null 일 수 없다");
        }
        Object[] old = new Object[1];
        root = put(root, key, value, old);
        root.color = BLACK;
        @SuppressWarnings("unchecked")
        V result = (V) old[0];
        return result;
    }
```

```text
  put(root, "C") 한 번의 흐름 -- 슬롯이 스스로 갱신된다

  내려가기                       올라오며 고치기

  root ---> (B)                  (B) 의 balance 가 새 뿌리 x 를 반환
              \                       |
               (D)  <- 여기서 왼쪽     v
               /                 root = x            <- root 슬롯이 덮어써진다
             null                     ^
                                      |
                                 (D).left = balance(...) <- D 의 left 슬롯이 덮어써진다
             새 노드 (CR)              ^
                                      |
                                 새 노드가 반환됨

  회전이 일어나 부분트리의 뿌리가 바뀌어도, 그 새 뿌리가 그대로 반환값이 되어
  호출한 쪽의 left / right 슬롯에 들어간다 -> 부모 링크가 저절로 맞는다
```

- Q: 회전으로 부분트리 뿌리가 바뀌면 부모 링크는 왜 저절로 맞는가?\
  A: 부모가 자식 슬롯을 **읽는 것이 아니라 덮어쓰기** 때문이다.\
  부모는 "누가 내 자식인가"를 기억하지 않고, 재귀 호출이 돌려준 것을 자기 슬롯에 넣는다.\
  회전이 새 뿌리 x 를 만들어 반환하면 부모의 슬롯이 x 로 바뀐다 — 부모가 x 의 존재를 알 필요가 없다.\
  즉 "링크를 고치는 책임"이 아래에서 위로 한 방향으로만 흐른다.

- Q: 부모 포인터를 두면 무엇이 늘어나는가?\
  A: 노드마다 참조 하나가 더 붙어 메모리가 늘고, 무엇보다 **회전할 때마다 갱신해야 할 포인터가 늘어난다**.\
  `rotateLeft` 하나에도 h.parent, x.parent, 옮겨진 자식의 parent, 그리고 "h 가 조부모의 왼쪽이었나 오른쪽이었나"까지 따져야 한다.\
  하나라도 빠뜨리면 트리가 조용히 끊어지고, 그 증상은 한참 뒤 다른 연산에서 나타난다.\
  CLRS 구현이 길어지는 이유의 큰 부분이 이 포인터 관리다.

> **NIL sentinel** — "자식 없음"을 null 대신 나타내는 가짜 검정 노드. 경계 검사를 줄이려고 쓴다.\
> 예: CLRS 구현은 부모 포인터와 함께 이것을 쓰고, 이 구현은 `isRed(null) == false` 로 대신한다.

- Q: `isRed` 가 null 을 받아도 되는 것이 이 방식과 어떻게 맞물리는가?\
  A: 재대입 방식은 "자식이 없으면 null 을 그대로 슬롯에 둔다"는 전제 위에서 돌아간다.\
  그래서 `balance` 의 조건들이 `h.left` 가 null 인 경우를 늘 만난다.\
  `isRed` 가 null 을 검정으로 처리해 주기 때문에 별도 null 검사 없이 세 조건을 그냥 쓸 수 있다.\
  NIL sentinel 없이도 경계 케이스가 사라지는 셈이다.

`impl/RedBlackTree.java` — 이 한 줄이 NIL sentinel 을 대신한다.

```java
    static <K, V> boolean isRed(Node<K, V> node) {
        return node != null && node.color == RED;
    }
```

- Q: 반환 슬롯이 하나뿐인데 "옛 값"은 어떻게 돌려주는가?\
  A: `Object[] old` 라는 길이 1 짜리 배열을 인자로 함께 내려보낸다.\
  반환값은 이미 "새 부분트리 뿌리"에 쓰이고 있으므로, 옛 값은 그 배열 칸에 써서 밖으로 흘려보낸다.\
  공개 `put` 이 `(V) old[0]` 으로 꺼내 반환한다.\
  이 구조가 `RedBlackTreeSet.add` 를 한 줄로 만든다 — `return map.put(key, PRESENT) == null;` 로 "새로 들어갔는지"를 별도 조회 없이 안다.

> **아웃 파라미터(out parameter)** — 반환값 대신 인자로 받은 그릇에 결과를 써서 밖으로 내보내는 방식.\
> 예: `Object[] old` 가 옛 값을 담아 나오는 그릇이다.

- Q: 이 방식의 대가는 무엇인가?\
  A: **재귀 스택**이다 — 깊이가 O(log n) 만큼 쌓인다.\
  높이 상한이 `2*log2(n+1)` 이라 n 이 10억이어도 60 정도라 실제로는 문제가 없다.\
  또 매 노드에서 슬롯에 다시 대입하는 쓰기가 한 번씩 더 일어난다(값이 안 바뀌어도).\
  그 대신 포인터 관리 버그가 구조적으로 사라지므로, 이 챕터에서는 명백히 남는 장사다.

**더 생각할 것**

- "고친 것을 돌려주고 호출자가 자기 자리에 꽂는다"는 패턴은 불변 자료구조(persistent data structure)의 기본형이다.\
  같은 코드에서 노드를 수정하는 대신 새로 만들면 그대로 영속 트리가 된다.
- 실무의 재귀 깊이 걱정은 이 구조에서는 기우다 — 높이가 보장되기 때문이다.\
  같은 방식을 06번 BST 에 쓰면 정렬 입력에서 스택 오버플로가 난다. 보장의 가치가 여기서도 드러난다.
- 반환 슬롯이 하나라는 언어 제약이 `Object[] old` 같은 우회를 낳는다.\
  튜플이나 다중 반환이 있는 언어면 이 부분이 훨씬 깔끔해진다 — 자료구조의 문제가 아니라 언어의 문제다.

#### 8. 지우기가 어려운 이유와 `moveRedLeft` 의 두 갈래

- Q: 검은 노드를 지우면 무엇이 깨지는가?\
  A: **[5] 검은 높이**다.\
  검은 링크를 하나 떼어내면 그 경로만 검은 링크 수가 1 줄어든다.\
  다른 경로는 그대로이므로 즉시 불균형이고, 이것은 국소적으로 못 고치는 전역 위반이다.\
  4번에서 "검은 노드를 새로 붙이면 안 되는" 이유와 정확히 같은 이유의 뒷면이다.

- Q: 왜 빨간 노드는 그냥 떼도 되는가?\
  A: 빨간 링크는 검은 높이 계산에 안 들어가기 때문이다.\
  2-3 트리로 읽으면 빨간 노드는 3-노드 안에 끼어 있는 두 번째 키라, 떼어내면 그 노드가 2-노드가 될 뿐 층수가 안 바뀐다.\
  그래서 LLRB 삭제의 전략은 단순하다 — **떼어낼 노드를 빨갛게 만들어 놓고 떼어낸다.**

- Q: 그 전략이 15번 B-트리의 무엇과 같은 발상인가?\
  A: **"내려가면서 미리 준비한다"** 는 발상이다.\
  15번의 삽입은 내려가는 길에 꽉 찬 노드를 미리 쪼개서, 잎에 도착했을 때 위로 되돌아갈 일이 없게 만든다.\
  15번의 삭제도 같은 식으로 빈약한 노드를 미리 채우고 내려간다.\
  LLRB 삭제는 "현재 노드를 계속 빨갛게 유지하며 내려간다" — 잎에 도착하면 이미 뗄 수 있는 상태다.\
  사후 수리(고전적 방식의 double-black 전파) 대신 사전 준비를 택한 것이다.

> **사전 준비(proactive) 대 사후 수리(reactive)** — 문제가 생길 조건을 내려가는 길에 미리 없애는 방식과, 생긴 뒤 위로 올라가며 고치는 방식.\
> 예: LLRB 삭제는 전자, CLRS 삭제의 double-black 전파는 후자다.

> **double-black** — 고전적 레드블랙 삭제에서 "검정이 하나 모자란 상태"를 임시로 표시하는 개념.\
> 예: LLRB 는 미리 빨강을 만들어 내려가므로 이 표시 자체가 필요 없다.

`impl/RedBlackTree.java` — 삭제의 뼈대 세 줄이 전략을 그대로 보여준다.

```java
    public V remove(K key) {
        requireKey(key);
        V old = get(key);
        if (old == null) {
            return null;
        }
        // 표준 구현의 관례. 지워도 테스트가 전부 통과한다(README 참고).
        if (!isRed(root.left) && !isRed(root.right)) {
            root.color = RED;
        }
        root = delete(root, key);
        if (root != null) {
            root.color = BLACK;
        }
        size--;
        return old;
    }
```

- Q: `moveRedLeft` 는 언제 불리는가?\
  A: 왼쪽으로 내려가기 **직전**에, 왼쪽 자식이 2-노드여서 빌려줄 여유가 없을 때다.\
  조건이 `!isRed(h.left) && !isRed(h.left.left)` 다 — "왼쪽 자식으로 가는 링크도 검고, 그 자식의 왼쪽 링크도 검다" = 왼쪽이 3-노드가 아니다.\
  그 상태로 내려가면 거기서 검은 노드를 떼게 되므로, 내려가기 전에 빨강을 만들어 준다.

`impl/RedBlackTree.java` — `deleteMin` 이 그 패턴의 가장 짧은 형태다.

```java
    private Node<K, V> deleteMin(Node<K, V> h) {
        if (h.left == null) {
            return null;
        }
        if (!isRed(h.left) && !isRed(h.left.left)) {
            h = moveRedLeft(h);
        }
        h.left = deleteMin(h.left);
        return balance(h);
    }
```

- Q: 첫 갈래(형제도 빠듯할 때)는 B-트리의 무엇에 대응하는가?\
  A: **merge(병합)** 다.\
  `flipColors(h)` 한 줄로 끝나고, h 가 쥐고 있던 빨강을 두 자식에게 나눠 준다.\
  2-3 트리로 읽으면 부모의 키 하나를 내려서 왼쪽 자식·오른쪽 자식과 한 덩어리로 합치는 것이다.\
  합쳐진 덩어리 안에서는 키가 넉넉하므로, 왼쪽으로 내려가 지워도 층수가 안 줄어든다.

```text
  갈래 [1] merge -- 오른쪽 형제도 빌려줄 게 없다 (isRed(h.right.left) == false)
  예 : A B C 세 개짜리 트리에서 최솟값 A 를 지울 때

   들어올 때                flipColors(h)               A 를 떼고 balance
      (BR)                      (BB)                         (CB)
      /   \       ->            //   \\        ->             //
   (AB)   (CB)               (AR)     (CR)                 (BR)
                              ^ 이제 붉으니 떼어내도
                                검은 높이가 안 변한다

  2-3 트리로 읽으면 : [B] 의 키를 내려 [A][B][C] 를 한 덩어리로 합쳤다 = merge
  검은 높이 : flipColors 가 모든 경로에서 동시에 -1 -> 상대적 균형은 유지된다
```

- Q: 두 번째 갈래(형제가 빌려줄 게 있을 때)는?\
  A: **borrow(빌리기)** 다.\
  `isRed(h.right.left)` 가 참이면 오른쪽 형제가 3-노드라는 뜻이고, 키 하나를 떼어 줄 여유가 있다.\
  `h.right = rotateRight(h.right); h = rotateLeft(h); flipColors(h);` 세 줄이 그 키를 h 자리로 끌어올리고, 원래 h 의 키를 왼쪽으로 내려보낸다.\
  2-3 트리에서 "부모를 거쳐 형제의 키 하나를 빈약한 쪽으로 옮기는" 회전 그대로다.

```text
  갈래 [2] borrow -- 오른쪽 형제가 3-노드다 (h.right.left 가 붉다)
  예 : 1..6 이 든 트리에서 deleteMin, h = 2 인 지점

  flipColors(h) 직후      rotateRight(h.right)     rotateLeft(h)        flipColors(h)
       (2B)                     (2B)                   (3B)                 (3R)
      //   \\                  //   \\                 //   \\              /    \
   (1R)     (4R)            (1R)     (3R)           (2R)     (4R)       (2B)     (4B)
            //                           \\         //                  //
         (3R)                            (4R)    (1R)                (1R)

  형제 쪽 키 3 이 h 자리로 올라오고, 원래 h 의 키 2 는 왼쪽 덩어리로 내려간다
  1 은 붉은 채로 남아 안전하게 지워진다
```

- Q: 두 갈래를 가르는 판정은 왜 `isRed(h.right.left)` 인가?\
  A: 좌편향이라 3-노드의 두 번째 키는 **항상 왼쪽 빨간 링크**로 붙어 있기 때문이다.\
  그래서 "오른쪽 형제가 3-노드인가?"라는 질문이 "오른쪽 형제의 왼쪽 링크가 빨간가?"와 같은 질문이 된다.\
  좌우를 다 허용했다면 오른쪽에 붙은 경우도 따로 봐야 했다 — 3번에서 말한 "경우의 수를 줄인다"가 여기서 값을 한다.\
  `flipColors(h)` 를 먼저 하고 판정하는 것도 중요하다 — 뒤집기 전과 후의 색이 다르므로 순서가 계약이다.

- Q: `delete` 가 내부 노드를 지울 때는 어떻게 하는가?\
  A: **후행자로 바꿔치기**해서 문제를 잎 쪽으로 옮긴다.\
  `Node<K,V> x = min(h.right); h.key = x.key; h.value = x.value; h.right = deleteMin(h.right);` 다.\
  오른쪽 부분트리의 최소 키를 h 에 복사하고, 실제로 떼어내는 노드는 `deleteMin` 이 처리하는 잎 쪽 노드다.\
  15번 B-트리에서 선행자/후행자로 바꿔치기하던 것과 같은 수법이다.

> **후행자(successor)** — 어떤 키보다 큰 것 중 가장 작은 키.\
> 예: 내부 노드를 지울 때 그 자리에 앉히면 정렬 순서가 그대로 유지된다.

- Q: 뿌리를 빨갛게 만드는 줄은 왜 있는가?\
  A: 표준 구현의 관례다 — "내려가기 전에 빨강을 확보한다"를 뿌리에서도 지키기 위한 줄이다.\
  그런데 README 가 정직하게 기록해 두었듯, **그 줄을 지워도 이 문제집의 테스트가 전부 통과한다**.\
  크기 1~6 트리의 모든 삭제 순서 전수 + 무작위 3000스텝 + TreeMap 대조 2만스텝을 다 통과한다.\
  뿌리에서 `flipColors` 가 어차피 색을 뒤집어 같은 효과를 내고, 마지막에 `root.color = BLACK` 이 덮어쓰기 때문으로 보인다 — 그래도 관례로 남겨 두었다.

**더 생각할 것**

- "테스트가 구별하지 못하는 코드"가 있다는 기록이 이 챕터에서 가장 실무적인 대목이다.\
  커버리지 100% 가 "모든 줄이 필요하다"를 뜻하지 않는다. 필요 없는 줄도 커버된다.
- 삭제가 삽입보다 어려운 것은 이 구조만의 이야기가 아니다.\
  15번 B-트리도 `removeFrom` 이 "이 문제집에서 경우가 가장 많은 메서드"였다. 값을 빼는 쪽이 늘 경우가 많다.
- 규모가 커지면 삭제 빈도가 설계를 바꾼다.\
  삭제가 잦으면 tombstone 을 찍고 나중에 한꺼번에 정리하는 방식(LSM 트리)이 유리해진다 — 매 삭제마다 구조를 정확히 유지하는 비용을 미루는 것이다.

#### 9. `delete` 의 key 비교를 두 번 하는 이유

- Q: 두 번의 비교 사이에서 무슨 일이 일어나는가?\
  A: **`h` 가 다른 노드가 된다.**\
  `if (isRed(h.left)) h = rotateRight(h);` 와 `h = moveRedRight(h);` 가 각각 h 를 다른 노드로 갈아치운다.\
  회전은 부분트리의 뿌리를 바꾸는 조작이므로, 회전 뒤의 `h.key` 는 회전 전의 `h.key` 와 다른 키다.\
  그러니 "지울 키가 지금 이 h 인가?"를 회전 전에 물어봤던 답으로는 회전 후를 판단할 수 없다.

`impl/RedBlackTree.java` — 비교가 나오는 세 자리를 그대로 본다.

```java
    private Node<K, V> delete(Node<K, V> h, K key) {
        if (key.compareTo(h.key) < 0) {
            if (!isRed(h.left) && !isRed(h.left.left)) {
                h = moveRedLeft(h);
            }
            h.left = delete(h.left, key);
        } else {
            if (isRed(h.left)) {
                h = rotateRight(h);
            }
            if (key.compareTo(h.key) == 0 && h.right == null) {
                return null;
            }
            if (!isRed(h.right) && !isRed(h.right.left)) {
                h = moveRedRight(h);
            }
            if (key.compareTo(h.key) == 0) {
                Node<K, V> x = min(h.right);
                h.key = x.key;
                h.value = x.value;
                h.right = deleteMin(h.right);
            } else {
                h.right = delete(h.right, key);
            }
        }
        return balance(h);
    }
```

```text
  else 가지에서 h 가 두 번 바뀐다 -- 그래서 == 0 비교가 두 번 있다

  [들어올 때]   h = H0        key.compareTo(H0.key) >= 0  (첫 번째 비교로 여기 왔다)
                   |
                   |  if (isRed(h.left)) h = rotateRight(h);
                   v
  [1차 변경]    h = H1        H1 은 원래 H0.left 였던 노드 -- 키가 다르다!
                   |
                   |  if (key.compareTo(h.key) == 0 && h.right == null) return null;   <- 두 번째 비교
                   |     "지금 h 가 목표이고 잎이면 그냥 뗀다"
                   v
                   |  if (!isRed(h.right) && !isRed(h.right.left)) h = moveRedRight(h);
                   v
  [2차 변경]    h = H2        moveRedRight 안의 rotateRight 로 또 바뀔 수 있다
                   |
                   |  if (key.compareTo(h.key) == 0) { 후행자로 바꿔치기 }               <- 세 번째 비교
                   |  else { h.right = delete(h.right, key); }
                   v
              return balance(h)

  H0 / H1 / H2 는 서로 다른 노드다 -> 매번 새로 물어야 한다
```

- Q: 정확히 몇 번 비교하는가?\
  A: 코드상 한 번의 `delete` 호출에서 최대 세 번이다.\
  첫 번째 `key.compareTo(h.key) < 0` 이 왼쪽/오른쪽 갈래를 정한다.\
  `else` 갈래 안에서 `== 0` 비교가 두 번 더 나오고, 그 둘 사이·앞에 h 를 바꾸는 조작이 끼어 있다.\
  README 가 "두 번 한다"고 말하는 것은 이 `== 0` 두 번을 가리킨다.

- Q: 두 번째 비교(`== 0 && h.right == null`)의 역할은 무엇인가?\
  A: **잎에 도달한 경우를 여기서 끝내는 것**이다.\
  지울 노드가 오른쪽 자식이 없는 잎이면 후행자로 바꿔칠 것도 없고 `min(h.right)` 가 NPE 를 낼 것이다.\
  그래서 그 자리에서 `return null` 로 슬롯을 비운다 — 부모가 그 null 을 자기 자리에 꽂아 노드를 떼어낸다.\
  앞서 `rotateRight` 로 h 가 바뀌었을 수 있으므로, 이 판정은 반드시 그 뒤에 있어야 한다.

- Q: 세 번째 비교의 역할은?\
  A: `moveRedRight` 로 h 가 또 바뀐 뒤 "지금 h 가 목표인가"를 다시 묻는 것이다.\
  맞으면 후행자로 바꿔치기하고, 아니면 오른쪽으로 더 내려간다.\
  `moveRedRight` 안의 `rotateRight(h)` 가 h 를 옛 `h.left` 로 바꿀 수 있기 때문에, 직전의 판정을 재사용할 수 없다.

- Q: 비교를 한 번만 하고 결과를 재사용하면 왜 **조용히** 틀리는가?\
  A: 예외가 안 나고 크기도 맞게 줄어들기 때문이다.\
  들어올 때 `key == H0.key` 여서 `cmp = 0` 을 캐싱했다고 하자.\
  `rotateRight` 후 h 는 H1(키가 더 작은 노드)인데, 캐싱한 `cmp == 0` 은 "지금 h 가 목표"라고 말한다.\
  그래서 H1 의 키를 후행자로 덮어쓰고 그 후행자를 `deleteMin` 으로 떼어낸다 — **목표가 아닌 키가 사라지고 목표는 살아남는다.**\
  `remove` 는 `get` 으로 미리 확인한 옛 값을 반환하고 `size--` 도 정상으로 하므로, 반환값만 보는 테스트는 전부 통과한다.

- Q: 그 조용한 오류를 무엇이 잡는가?\
  A: **대조 테스트와 불변식 테스트**다.\
  `matchesTreeMap` 이 20,000 스텝 동안 `java.util.TreeMap` 과 매 연산의 반환값·크기를 맞춰 보고, 마지막에 `keys()` 전체를 비교한다.\
  `shuffled` 는 5,000개를 지우면서 **매 삭제마다** `keys()` 전체를 기준 `TreeMap` 과 비교한다.\
  `tinyTreesUnderPressure` 는 크기 1~6 트리의 모든 삭제 순서를 전수로 돌면서 매번 불변식을 확인한다 — 뿌리 근처 특수 케이스가 여기서 걸린다.\
  즉 "키 하나가 조용히 다른 키로 바뀌는" 버그는 전체 키 목록을 비교해야만 드러난다.

**더 생각할 것**

- "변수를 캐싱해서 최적화"가 버그가 되는 전형적인 패턴이다.\
  캐싱해도 되는 값은 **변하지 않는 것**뿐인데, 여기서 `h` 는 같은 함수 안에서 두 번 바뀐다.
- 함수 안에서 참조 변수를 재대입하는 스타일(`h = rotateRight(h)`)은 짧지만 이런 함정을 만든다.\
  읽을 때 "이 시점의 h 는 누구인가"를 매번 새로 물어야 한다.
- 조용히 틀리는 버그를 잡는 유일한 방법은 **독립적인 기준(oracle)과의 대조**다.\
  여기서는 `TreeMap` 이 그 기준이고, 실무에서는 기존 시스템의 출력이나 단순하지만 확실히 맞는 참조 구현이 그 역할을 한다.

#### 10. 최악의 입력과 `floorKey` 의 후보 들기

- Q: 정렬된 키를 순서대로 넣으면 어떤 모양이 되는가?\
  A: 06번 BST 라면 오른쪽으로 뻗은 한 줄이지만, LLRB 에서는 **거의 완전 이진 트리**가 된다.\
  새 키가 늘 최댓값이라 오른쪽 끝에 붙는데, `balance` 의 [1] 이 그 빨간 링크를 즉시 왼쪽으로 눕히기 때문이다.\
  A~G 를 순서대로 넣으면 2-summary 의 그림처럼 D 를 뿌리로 하는 완전 이진 트리가 나온다.\
  테스트 `sortedInsertStaysBalanced` 가 10만 개로 높이 33 이하를 확인하는 것이 이 사실이다.

```text
  A..G 를 순서대로 넣는 동안 실제로 걸리는 케이스 (impl 코드를 손으로 따라간 것)

  put A : (AB)                                            회전 0, flip 0
  put B : (AB)\\(BR) -> [1] rotateLeft -> (BB)//(AR)      rotateLeft 1
  put C : (BB) 양쪽이 빨강 -> [3] flipColors               flip 1
          -> (BB) / (AB) (CB)
  put D : C 밑에 D 가 붙음 -> C 에서 [1] rotateLeft        rotateLeft 1
          -> (BB) / (AB), (DB)//(CR)
  put E : D 에서 [3] flip -> D 가 빨개짐                   flip 1
          -> B 에서 [1] rotateLeft -> D 가 뿌리로          rotateLeft 1
          -> (DB) / (BR)(A,C), (EB)
  put F : E 에서 [1] rotateLeft                            rotateLeft 1
          -> (DB) / (BR)(A,C), (FB)//(ER)
  put G : F 에서 [3] flip, D 에서 [3] flip                 flip 2
          -> (DB) / (BB)(A,C), (FB)(E,G)   <- 완전 이진 트리

  합계 : rotateLeft 4 회, rotateRight 0 회, flipColors 4 회 / 삽입 7 회
```

- Q: 이 추적에서 `rotateRight` 가 한 번도 안 나오는 이유는?\
  A: [2] 의 조건이 "왼쪽으로 연속된 빨강"인데, 오름차순 삽입은 새 키가 항상 오른쪽 끝에 붙기 때문이다.\
  오른쪽에 생긴 빨강은 [1] 이 즉시 눕히고, 그 결과로 만들어지는 빨강은 하나뿐이라 연속이 되지 않는다.\
  반대로 **내림차순 삽입**은 새 키가 늘 왼쪽 끝에 붙어 왼쪽 연속 빨강이 생기므로 [2] `rotateRight` 가 주로 걸린다.\
  좌편향 구조 때문에 오름차순과 내림차순에서 걸리는 케이스가 다르고, 불변식 테스트에 `ascending()` 과 `descending()` 이 따로 있는 이유가 그것이다.\
  (위 추적과 이 관찰은 내가 impl 코드를 손으로 따라간 것이다 — 원본 문서에 이 수치는 없다.)

- Q: 한 번의 `put` 에서 회전은 최대 몇 번인가? 총 비용은?\
  A: `balance` 한 번에 회전은 최대 2번(`rotateLeft` 1 + `rotateRight` 1)이고 `flipColors` 최대 1번이다.\
  `balance` 는 내려간 경로의 노드마다 한 번씩, 즉 최대 `2*log2(n+1)` 번 불린다.\
  따라서 `put` 한 번의 최악은 `O(log n)` 회전이고, 비용은 `내려가기 O(log n) + 노드마다 O(1) 수리 = O(log n)`.\
  n 번 넣으면 `n x O(log n) = O(n log n)` 이다 — 위 추적처럼 실제로는 삽입당 회전이 1회 남짓이라 상수가 작다.

- Q: 그럼 LLRB 의 진짜 최악 입력은 무엇인가?\
  A: **없다** — 그게 이 챕터의 요점이다.\
  06번 BST 에는 "정렬 입력"이라는 명확한 최악이 있었고, 12번 스킵 리스트에는 "나쁜 동전 운"이 있었다.\
  LLRB 는 어떤 순서로 넣어도 높이가 `2*log2(n+1)` 을 넘지 못한다 — 입력이 상한을 건드릴 수 없다.\
  테스트도 그렇게 짜여 있다: `otherAdversarialOrders` 가 역순과 톱니(0, n-1, 1, n-2, ...) 두 적대적 순서를 같은 상한으로 잡는다.\
  남는 차이는 상수 수준의 회전·flip 횟수뿐이다.

> **적대적 입력(adversarial input)** — 자료구조의 약점을 노리고 일부러 만든 입력 순서.\
> 예: 06번 BST 의 정렬 입력, 해시 테이블의 충돌 유발 키가 그것이다.

- Q: `floorKey` 는 왜 "찾으면 바로 반환"이 안 되는가?\
  A: 찾는 것이 **정확히 일치하는 키가 아니라 "key 이하 중 가장 큰 키"** 이기 때문이다.\
  탐색 도중 만나는 노드가 key 보다 작으면 그것은 **후보**일 뿐이다 — 더 오른쪽에 key 에 더 가까운 키가 있을 수 있다.\
  그래서 후보를 `best` 에 적어 두고 오른쪽으로 더 내려가 본다.\
  더 내려갔다가 null 에 도달하면, 마지막으로 적어 둔 후보가 답이다.

`impl/RedBlackTree.java` — `best` 를 갱신하는 자리가 딱 한 줄이다.

```java
    public K floorKey(K key) {
        requireKey(key);
        Node<K, V> cur = root;
        K best = null;
        while (cur != null) {
            int cmp = key.compareTo(cur.key);
            if (cmp == 0) {
                return cur.key;
            }
            if (cmp < 0) {
                cur = cur.left;
            } else {
                best = cur.key;
                cur = cur.right;
            }
        }
        return best;
    }
```

```text
  floorKey(25) -- 10, 20, 30, 40 이 든 트리에서

        (20)                cmp = 25.compareTo(20) > 0
        /   \               -> 20 은 후보다. best = 20. 오른쪽으로 더 가 본다
     (10)    (30)           cmp = 25.compareTo(30) < 0
             /              -> 30 은 너무 크다. 후보 아님. 왼쪽으로
          null              cur == null -> 루프 끝

        return best = 20     <- "찾으면 바로 반환"이었다면 20 에서 멈춰도 답이 같지만,
                                트리에 25 보다 작은 더 큰 키(예 22)가 오른쪽에 있었다면 틀린다

  best 를 갱신하는 자리는 cmp > 0 일 때뿐이다 = "현재 노드가 key 보다 작을 때만 후보"
  cmp == 0 일 때만 즉시 반환한다 = 정확히 일치하면 더 볼 것이 없다
```

- Q: `ceilingKey` 는 무엇이 뒤집히는가?\
  A: 후보를 적는 조건과 내려가는 방향이 통째로 뒤집힌다.\
  `cmp > 0`(현재 노드가 key 보다 작다)이면 오른쪽으로 내려가기만 하고, `cmp < 0`(현재 노드가 key 보다 크다)이면 `best = cur.key` 로 적은 뒤 왼쪽으로 내려간다.\
  `cmp == 0` 에서 즉시 반환하는 것만 같다.\
  두 메서드 다 트리를 한 줄로 내려가므로 비용은 `O(log n)` 이고, 값을 못 찾아도 최대 높이만큼만 본다.

- Q: 이 "후보 들고 다니기"가 다른 곳에서도 나오는가?\
  A: 나온다 — 경계 질의(range query)의 기본형이다.\
  `firstKey`/`lastKey` 는 후보 없이 한 방향 끝까지 가면 되지만, floor/ceiling 은 "지나쳤다가 되돌아오지 않기 위해" 후보가 필요하다.\
  이진 탐색으로 "삽입 위치 찾기"를 할 때도 같은 모양이 나온다.\
  15번 B-트리의 범위 조회, 17번 펜윅의 `findPrefixIndex` 도 "지나온 것 중 조건을 만족하는 마지막 것"을 들고 다니는 같은 형태다.

**더 생각할 것**

- 최악 입력이 없다는 것은 공짜가 아니다 — 매 삽입·삭제마다 `balance` 를 부르는 고정 비용으로 산 것이다.\
  입력이 원래 무작위임을 확신할 수 있으면 평범한 BST 가 더 빠를 수도 있다. 다만 그 확신은 대개 틀린다.
- 실무에서 적대적 입력은 악의가 아니라 자연스럽게 생긴다 — 자동 증가 ID, 타임스탬프, 정렬된 파일 읽기가 전부 정렬 입력이다.\
  "무작위일 것"이라는 가정이 깨지는 곳이 보통 이런 자리다.
- floor/ceiling 이 필요 없다면 해시맵이 더 싸다(조회 O(1)).\
  정렬 자료구조를 고르는 이유의 대부분이 이 경계 질의와 범위 순회다 — 그 둘을 안 쓰면서 `TreeMap` 을 쓰고 있다면 자료구조가 틀린 것이다.

#### 11. 17번 펜윅 트리로의 연결 — "덜 하면 더 싸다"

- Q: 16번까지 균형을 지키려고 무엇을 늘렸는가?\
  A: 코드다.\
  회전 2종, `flipColors`, `balance` 세 검사, 삭제 쪽의 `moveRedLeft`/`moveRedRight`/`deleteMin`/`delete`.\
  그리고 그 코드가 맞는지 확인하기 위한 불변식 테스트까지 따라붙는다.\
  얻은 것은 "어떤 입력에도 O(log n)"이라는 보장 하나다.

- Q: 17번 펜윅 트리는 반대로 무엇을 포기하는가?\
  A: **일반성**이다.\
  13번 세그먼트 트리는 결합법칙만 있으면 무엇이든 접었다 — 합, 최소, 최대, GCD, 행렬 곱.\
  펜윅 트리는 **역연산이 있는 연산만** 한다. 사실상 합이다.\
  `rangeSum(l, r) = prefixSum(r) - prefixSum(l-1)` 처럼 앞쪽을 통째로 구해 놓고 **빼서** 가운데를 얻기 때문이다.\
  최소값에는 그 뺄셈이 없다 — `min(a..r)` 과 `min(a..l-1)` 을 알아도 `min(l..r)` 을 모른다.

> **역연산(inverse operation)** — 결과에서 한쪽을 되돌려 뺄 수 있는 성질.\
> 예: 덧셈에는 뺄셈이 있어 `prefixSum(r) - prefixSum(l-1)` 이 성립하지만, min 에는 그런 되돌리기가 없다.

- Q: 그 포기의 대가로 무엇을 받는가?\
  A: 코드가 열 줄이 되고 메모리가 4분의 1이 된다.\
  노드도 링크도 없이 배열 하나이고, **인덱스의 비트 패턴이 트리 구조를 대신한다**.\
  `tree[i]` 는 `i` 에서 왼쪽으로 `i & -i` 개를 덮고, 걸음 수가 곧 1비트의 개수라 `log n` 이하다.\
  조회·갱신은 여전히 O(log n) 이지만 상수가 더 작다.

| | 13번 세그먼트 트리 | 17번 펜윅 트리 |
|---|---|---|
| 결합 함수 | 아무거나 (모노이드) | **역연산이 있어야 한다** |
| 최소/최대 | 된다 | **안 된다** |
| 메모리 | 4n | **n + 1** |
| 조회/갱신 | O(log n) | O(log n), 상수가 더 작다 |
| 코드 | 수십 줄 | **열 줄** |

- Q: 16번과 17번의 거래는 방향이 어떻게 다른가?\
  A: 16번은 **기능을 유지한 채 코드를 늘려 보장을 샀다**.\
  17번은 **기능을 줄여 코드와 메모리를 샀다**.\
  둘 다 "무엇을 내주고 무엇을 받는가"라는 같은 질문의 다른 답이다.\
  16번에서 내준 것은 코드의 단순함이고, 17번에서 내준 것은 쓸 수 있는 연산의 범위다.

- Q: "덜 하면 더 싸다"의 계보는?\
  A: 07번 힙 — 전체 정렬을 포기하고 부분 순서만 유지해 삽입/최솟값 추출을 O(log n) 으로 만든다.\
  11번 블룸 필터 — 정확성을 포기하고(거짓 양성 허용) 메모리를 극단적으로 줄인다.\
  14번 유니온 파인드 — 실제 경로 모양을 포기하고(경로 압축) 속도를 얻는다.\
  17번 펜윅 — 일반성을 포기하고 코드와 메모리를 얻는다.\
  네 번 다 "필요한 질문만 답하도록 구조를 좁히면 값이 싸진다"는 같은 문장이다.

- Q: 그렇다면 레드블랙 트리는 언제 필요한가?\
  A: **키 집합이 동적으로 변하고, 순서 질의가 필요할 때**다.\
  펜윅·세그먼트 트리는 인덱스가 고정된 배열 위의 구조라, 키를 넣고 빼면서 정렬 순서를 유지하는 일을 못 한다.\
  `floorKey`/`ceilingKey`/범위 순회/최소·최대 키를 O(log n) 에 답하면서 삽입·삭제도 받아야 하면 16번이 맞는 답이다.\
  반대로 "값은 정해진 인덱스에 있고 구간 합만 필요"하면 17번이고, "구간에 아무 결합 연산"이면 13번이다.\
  자료구조를 고르는 질문은 항상 "무엇을 안 해도 되는가"부터다.
