# data-structure/11-bloom-filter — 질문

## 질문

### B. 자료구조 특성

1. 블룸 필터가 왜 필요한가. 05-hash-table 의 해시 집합으로는 무엇이 안 되는가 — 원소 100만 개를 담을 때 수십 MB 와 1.2MB 의 차이는 무엇을 포기해서 생기는가.
2. 어떤 형태의 데이터·접근 패턴에 블룸 필터가 적합하고, 언제 쓰면 안 되는가. "비싼 조회 앞단 필터"가 되려면 뒤에 무엇이 있어야 하고, 담은 원소를 꺼내야 하거나 정확한 답이 필요한 워크로드에서는 왜 무너지는가.
3. `mightContain` 이 false 면 확실히 없고 true 면 아마 있다 — 이 비대칭이 나오는 구조적 이유는 무엇인가. 누락(false negative)이 불가능한 근거가 코드의 어느 성질에서 오는가(한 번 켠 비트를 끄지 않는다는 것과 어떻게 연결되는가).
4. `m = -n ln(p) / (ln2)^2`, `k = (m/n) ln2` — 이 두 공식이 왜 그 모양인가. 1% 오탐일 때 원소당 9.586비트라는 값이 원소가 int 든 100자 URL 이든 같은 이유는 무엇인가. k 를 더 키우면 오탐이 왜 오히려 늘어나는가(골짜기가 있다는 말의 의미).
5. 해시 함수를 k 개 만들지 않고 64비트 해시 하나를 반으로 갈라 `idx_i = h1 + i*h2` 로 쓰는 이중 해싱의 함정 셋은 무엇인가. 그중 `h2 == 0` 방어선이 **이 설계에서는 어떤 테스트로도 못 잡히는** 이유는 무엇이고, 19번에서는 왜 잡을 수 있게 되는가 — "테스트가 못 잡는다"가 코드의 성질이 아니라 설계의 성질이라는 말은 무슨 뜻인가.
6. 최악의 사용 패턴을 만들어 보라 — 용량 100만으로 잡은 `BloomFilter` 에 1000만 개를 넣으면 오탐률이 어떻게 되고, 그 시점에 왜 이미 늦었는가. 05번 해시맵은 리사이즈로 복구했는데 여기서는 왜 다시 만들 수조차 없는가. 최선의 경우는 언제인가.
7. 기본형이 왜 삭제를 못 하는가(A 와 B 가 3번 비트를 함께 켠 상황). `CountingBloomFilter` 는 그걸 어떻게 풀고, 대신 치르는 값 셋은 무엇인가 — 특히 오탐인 원소를 지우면 왜 "누락 없음" 보장 자체가 깨지는가. 포화된 계수기(255)를 내리면 안 되는 이유는.
8. `ScalableBloomFilter` 는 늘리는 게 아니라 잇는다 — 왜 새 필터일수록 용량은 2배로 키우면서 오탐률은 절반으로 조이는가. 전체 오탐률 `1 - (1-p)(1-p/2)(1-p/4)...` 가 2p 를 넘지 않는 이유는 무엇이고, 그 대가로 `mightContain` 비용은 어떻게 되는가. 세 구현 중 언제 무엇을 고르는가.
9. 12-skip-list 로의 연결 — 여기서 처음 만난 "확률에 기대는 자료구조"가 다음 챕터에서 어떤 모양으로 다시 나오는가. 06-tree 의 BST 가 정렬 입력에서 무너진 문제를 회전 없이 확률로 푼다는 것은 무슨 뜻이고, 무작위를 **주입받게** 만드는 규칙이 성능·재현성만이 아니라 검증 가능성까지 바꾼다는 말(5번 질문과 이어진다)은 무엇인가.
