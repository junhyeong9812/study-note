### B. 자료구조의 특성

#### 1. 블룸 필터가 왜 필요한가 — 무엇을 포기해서 수십 MB가 1.2MB가 되는가

**질문**: 05-hash-table 의 해시 집합으로는 무엇이 안 되는가 — 원소 100만 개를 담을 때 수십 MB 와 1.2MB 의 차이는 무엇을 포기해서 생기는가.

**해시 집합이 쓰는 메모리**

```
 HashSet<Integer> 에 100만 개를 담으면 무엇이 저장되는가

   원소 자체        Integer 객체 (헤더 12~16바이트 + int 4바이트)
   엔트리 객체      HashMap.Node (헤더 + hash + key 참조 + value 참조 + next 참조)
   버킷 배열        Object[] (적재율 0.75 기준 약 200만 칸 x 참조 크기)

   합치면 원소 하나에 대략 40~60바이트
   -> 100만 개면 40~60MB
   (원본에 근거 없음 -- 내 추론: 객체 크기는 JVM·압축 oops 설정에 따라 다르다.
    README 는 "수십 MB" 라고만 적는다)

 왜 이렇게 드는가 : 원소를 '담기' 때문이다
   원소를 담아야 무엇을 할 수 있나
     - 꺼낼 수 있다 (순회, 목록 출력)
     - 정확히 비교할 수 있다 (해시 충돌이 나도 equals 로 확정한다)
     - 지울 수 있다
```

**블룸 필터가 쓰는 메모리**

```java
@Test
@DisplayName("1% 오탐이면 원소당 약 9.6비트다")
void bitsPerElement() {
    BloomFilter<Integer> f = new BloomFilter<>(1_000_000, 0.01);
    double perElement = (double) f.bitSize() / 1_000_000;
    assertTrue(perElement > 9.5 && perElement < 9.7, "원소당 " + perElement + "비트");
    assertEquals(7, f.hashCount());

    // 정확한 HashSet<Integer> 은 원소 하나에 최소 수십 바이트를 쓴다.
    // 여기서는 1.2MB 로 100만 개를 담는다.
    assertTrue(f.bitSize() / 8 < 1_300_000, "약 1.2MB 여야 한다");
}
```

```
 비트 수 m = optimalBits(1,000,000, 0.01) = 9,585,059    (테스트 assert 값)
 바이트로  = 9,585,059 / 8 ≈ 1,198,132 바이트 ≈ 1.2MB

 원소당 = 9,585,059 / 1,000,000 ≈ 9.585 비트   (약 1.2 바이트)

 비교
   HashSet   원소당 40~60 바이트
   블룸      원소당 약 1.2 바이트
   -> 30~50배 차이
```

**무엇을 포기해서 이 차이가 생기는가**

```
 블룸 필터에는 원소가 '없다'

   add(x) 가 하는 일 = x 의 해시로 정해지는 k 개 자리의 비트를 켠다
   그게 전부다. x 자체는 어디에도 적히지 않는다

   그래서 잃는 것 셋

   (1) 꺼낼 수 없다
       "지금까지 넣은 것 목록을 줘" 라는 질문에 답할 방법이 없다
       계약(ProbabilisticSet)에 그런 메서드가 아예 없다

   (2) 정확할 수 없다
       해시 집합은 버킷에서 후보를 찾은 뒤 equals 로 확정한다
       블룸 필터는 확정할 원본이 없다 -> 비트가 켜져 있으면 믿는 수밖에 없다
       다른 원소들이 켜 둔 비트가 우연히 겹치면 '있다'고 잘못 말한다  -> 오탐

   (3) 지울 수 없다
       비트 하나를 여러 원소가 공유하므로 끄면 남까지 사라진다 (7번)

 대신 얻는 것 : 메모리가 '원소 크기와 무관하게' 원소당 몇 비트로 고정된다
```

> **오탐(false positive) / 누락(false negative)** — 없는데 "있다"고 답하는 것 / 있는데 "없다"고 답하는 것.\
> 예: 블룸 필터는 오탐만 허용하고 누락은 절대 내지 않는다 — 이 비대칭이 쓸모의 전부다.

> **확률적 자료구조(probabilistic data structure)** — 정확성을 일부 포기하는 대신 메모리나 시간을 크게 줄이는 자료구조.\
> 예: 블룸 필터, HyperLogLog, Count-Min Sketch가 같은 계열이며 전부 "정해진 방향으로만 틀린다".

**비대칭 — 이것이 쓸모의 전부다**

```java
@Override
public boolean mightContain(T item) {
    for (int idx : indexes(item)) {
        if ((words[idx >>> 6] & (1L << (idx & 63))) == 0) {
            return false;          // 한 자리라도 꺼져 있으면 -> 확실히 없다
        }
    }
    return true;                   // 전부 켜져 있으면 -> 아마 있다
}
```

```
   mightContain 이 false  ->  확실히 없다.  오답이 아예 불가능하다
   mightContain 이 true   ->  아마 있다.    없는데 있다고 할 수 있다

 "없다"가 확실하니까 비싼 조회를 건너뛰는 앞단 필터로 쓸 수 있다
   false -> 디스크를 안 읽는다 (여기서 이득이 난다)
   true  -> 읽어서 확인한다 (틀려도 한 번 더 읽을 뿐 답은 안 틀린다)

 실제 쓰임 (README/계약 주석)
   카산드라·HBase 의 SSTable 조회
   크롬의 악성 URL 목록
   CDN 캐시의 "한 번만 요청된 것은 캐시하지 않기"
```

**비교표** (`ProbabilisticSet.java` 주석의 표)

| | 정확한 집합(HashSet) | 블룸 필터 |
|---|---|---|
| 원소 100만 개 저장 | 수십 MB (원소 자체를 담는다) | **약 1.2MB** (1% 오탐 기준) |
| 원소를 꺼내기 | 된다 | **안 된다** — 담은 적이 없다 |
| 삭제 | 된다 | **안 된다** (`CountingBloomFilter` 가 푼다) |
| 오답 | 없다 | 오탐만 있다. **누락은 없다** |

- 논리: 10번 LRU 캐시와의 대비가 README의 한 줄에 있다 — **"10번에서 일부러 잊어서 한정했다면, 여기서는 일부러 헷갈려서 한정한다."**
- 논리: 10번의 답은 늘 참이었고(아는 범위가 좁을 뿐) 11번의 답은 한쪽 방향으로만 참이다.

**질문별 답**

- Q: 05-hash-table 의 해시 집합으로는 무엇이 안 되는가?\
  A: 기능으로 안 되는 것은 없다 — 오히려 해시 집합이 더 많이 할 수 있다(꺼내기·삭제·정확한 답).\
  안 되는 것은 **메모리**다.\
  원소를 실제로 담으므로 원소 하나에 수십 바이트가 들어, 100만 개면 수십 MB가 필요하다.

- Q: 수십 MB와 1.2MB의 차이는 무엇을 포기해서 생기는가?\
  A: **원소를 담는 것 자체**를 포기해서 생긴다.\
  블룸 필터는 해시로 정해지는 몇 개 자리의 비트만 켜고 원소는 어디에도 적지 않는다.\
  그래서 (1) 꺼낼 수 없고, (2) 확정할 원본이 없어 오탐을 낼 수 있고, (3) 비트를 공유하므로 지울 수 없다.\
  대신 메모리가 원소 크기와 무관하게 **원소당 약 9.6비트(1% 오탐)** 로 고정되어 1.2MB가 된다.

#### 2. 언제 적합하고 언제 쓰면 안 되는가

**질문**: "비싼 조회 앞단 필터"가 되려면 뒤에 무엇이 있어야 하고, 담은 원소를 꺼내야 하거나 정확한 답이 필요한 워크로드에서는 왜 무너지는가.

**앞단 필터가 성립하는 조건**

```
 구조

   질의 x
     |
     v
   블룸 필터 --- false ---> "없다" 고 답하고 끝.  뒤를 안 본다   <- 여기서 이득이 난다
     |
    true
     |
     v
   진짜 저장소(디스크·DB·네트워크) 조회 --- 있으면 값, 없으면 "없다"

 성립 조건 셋

 (1) 뒤에 '진짜 저장소'가 반드시 있어야 한다
     true 는 "아마"이므로 확정할 곳이 필요하다
     블룸 필터만 있으면 오탐을 걸러낼 방법이 없다 -> 그냥 틀린 답이 된다

 (2) 뒤의 조회가 '비싸야' 한다
     앞단 필터의 이득 = (건너뛴 횟수) x (뒤 조회 한 번의 비용)
     뒤가 메모리 해시맵이면 필터를 거치는 비용이 더 클 수도 있다

 (3) '없는 질의'가 많아야 한다
     전부 있는 것만 물으면 필터가 늘 true 를 주어 한 번도 못 건너뛴다
     -> 순수한 오버헤드가 된다
     (원본에 근거 없음 -- 내 추론: README 는 (1)(2)만 명시한다)
```

- 논리: 카산드라/HBase의 SSTable 조회가 정확히 이 모양이다 — 뒤가 **디스크**라 비싸고, 여러 SSTable 중 대부분에 없는 키를 묻게 된다.
- 논리: 크롬의 악성 URL 목록도 같다 — 대부분의 URL은 목록에 **없으므로** 대부분의 질의가 false로 끝나 서버를 안 부른다.

**적합한 패턴**

- 논리: 뒤가 디스크·네트워크·DB라 조회가 비싸고, 질의의 상당수가 "없음"으로 끝난다.
- 논리: 메모리가 빠듯해 정확한 집합을 못 올린다 — 임베디드, 대용량 스트림, 분산 노드마다 복제해야 하는 경우.
- 논리: 원소 수를 대략 알고 있고 오탐률 목표를 정할 수 있다(4번의 공식을 쓰려면 `n` 과 `p` 가 필요하다).
- 논리: 틀려도 **한 번 더 확인하면 되는** 질의다 — 오탐의 대가가 "비용 조금"이지 "잘못된 답"이 아니다.

**쓰면 안 되는 패턴**

- 한계: **담은 원소를 꺼내야 할 때** — 계약에 그런 연산이 아예 없다.\
  원소를 저장하지 않으므로 목록·순회·이터레이터가 원리적으로 불가능하다.
- 한계: **정확한 답이 필요할 때** — 뒤에 확인할 저장소가 없으면 오탐이 곧 틀린 답이다.\
  결제·권한 판정처럼 오탐의 대가가 큰 곳에는 못 쓴다.
- 한계: **삭제가 필요할 때** — 기본형은 못 한다(7번).\
  `CountingBloomFilter` 가 풀지만 "누락 없음" 보장을 잃는다.
- 한계: **원소 수를 모를 때** — 용량을 잘못 잡으면 오탐률이 무너지고 되돌릴 수 없다(6번).\
  `ScalableBloomFilter` 가 풀지만 조회가 필터 수만큼 든다(8번).
- 한계: 뒤의 조회가 싸거나, 질의가 대부분 "있음"으로 끝날 때 — 이득이 없다.

**"정확한 답이 필요할 때 왜 무너지는가"의 정확한 의미**

```
 블룸 필터가 줄 수 있는 답

   false  -> "없다"           확정.  이 답은 증명된다
   true   -> "아마 있다"      미확정. 이 답은 '힌트'다

 뒤에 저장소가 있으면
   true -> 저장소 조회 -> 진짜 답     => 시스템 전체의 답은 정확하다
   블룸 필터의 부정확이 시스템 밖으로 새지 않는다

 뒤에 저장소가 없으면
   true -> 그대로 사용자에게 간다     => 시스템의 답이 틀린다
   부정확이 그대로 새어 나간다

 즉 "무너진다"는 것은 자료구조가 고장 난다는 뜻이 아니다
    자료구조는 계약대로 동작하는데, 그 계약이 그 워크로드가 요구하는 것과 다를 뿐이다
```

- 논리: 10번의 "가정이지 정리가 아니다"와는 **다른 종류의 한계**다.\
  LRU는 워크로드에 따라 성능이 무너졌고, 여기서는 **계약 자체가 부정확**하다.
- 논리: 그래서 판단 기준이 명확하다 — "이 질의의 답이 틀리면 어떻게 되는가"를 물으면 된다.\
  "한 번 더 읽는다"면 써도 되고, "사용자에게 틀린 답이 간다"면 쓰면 안 된다.

**질문별 답**

- Q: "비싼 조회 앞단 필터"가 되려면 뒤에 무엇이 있어야 하는가?\
  A: **진짜 저장소**(디스크·DB·네트워크)가 있어야 한다.\
  `true` 는 "아마"라서 확정할 곳이 필요하고, 그 뒤 조회가 비싸야 "건너뛰기"에서 이득이 난다.\
  덧붙여 질의의 상당수가 "없음"으로 끝나야 실제로 건너뛸 기회가 생긴다.

- Q: 담은 원소를 꺼내야 하거나 정확한 답이 필요한 워크로드에서는 왜 무너지는가?\
  A: 원소를 **저장하지 않기** 때문이다 — 꺼내기는 원리적으로 불가능하고 계약에도 그런 연산이 없다.\
  정확한 답이 필요한 경우는 자료구조가 고장 나서가 아니라, `true` 가 "아마"인 계약이 그 워크로드의 요구와 다르기 때문이다.\
  뒤에 확인할 저장소가 있으면 부정확이 시스템 밖으로 안 새지만, 없으면 오탐이 그대로 틀린 답이 된다.

#### 3. false는 확실하고 true는 아마인 이유 — 누락이 불가능한 구조적 근거

**질문**: 이 비대칭이 나오는 구조적 이유는 무엇인가. 누락(false negative)이 불가능한 근거가 코드의 어느 성질에서 오는가(한 번 켠 비트를 끄지 않는다는 것과 어떻게 연결되는가).

**두 연산**

```java
@Override
public void add(T item) {
    for (int idx : indexes(item)) {
        words[idx >>> 6] |= 1L << (idx & 63);      // OR 로 켠다. 끄는 코드가 없다
    }
    inserted++;
}
```

```java
@Override
public boolean mightContain(T item) {
    for (int idx : indexes(item)) {
        if ((words[idx >>> 6] & (1L << (idx & 63))) == 0) {
            return false;
        }
    }
    return true;
}
```

- 논리: `add` 는 `|=` (OR 대입)만 쓴다 — **비트를 켜기만 하고 끄지 않는다**.\
  `clear()` 말고는 0으로 되돌리는 코드가 이 클래스에 아예 없다.
- 논리: `mightContain` 은 자리 k개가 **전부** 켜져 있는지 본다 — 하나라도 꺼져 있으면 즉시 `false`.

**누락이 불가능한 증명**

```
 주장 : add(x) 를 부른 적이 있으면 mightContain(x) 는 반드시 true 다

 증명

   (1) indexes(x) 는 결정론적이다
       같은 x 에 대해 언제 불러도 같은 k 개 자리를 준다
       (테스트 deterministic 이 확인한다: assertArrayEquals(f.indexes(42), f.indexes(42)))

   (2) add(x) 는 그 k 개 자리를 전부 1 로 만든다

   (3) 비트는 한 번 1 이 되면 0 으로 돌아가지 않는다
       add 에 |= 만 있고 &= ~... 이 없다
       다른 원소를 넣어도 |= 라 1 을 0 으로 바꿀 수 없다

   (4) 따라서 add(x) 이후 어느 시점에 물어도 그 k 개 자리는 여전히 1 이다

   (5) mightContain(x) 는 같은 k 개 자리를 보고 전부 1 이면 true 를 준다

   => 누락(넣었는데 false)이 발생할 방법이 없다.  구조적으로 불가능하다
```

```
 비트의 일생 (단조 증가)

   0 ---- add 로 켜짐 ----> 1 ---- (끄는 연산이 없다) ----> 1 ----> 1 ...
                             ^
                             여기서 되돌아가는 화살표가 없다는 것이 전부다
```

> **단조성(monotonicity)** — 상태가 한 방향으로만 변하고 되돌아오지 않는 성질.\
> 예: 블룸 필터의 비트는 0에서 1로만 가고, 그 단조성이 "누락 없음" 보장의 근거다.

> **비트 마스크 연산** — `|=` 로 특정 비트를 켜고, `&` 로 특정 비트가 켜져 있는지 검사하는 방식.\
> 예: `words[i>>>6] |= 1L << (idx & 63)` 은 idx번째 비트 하나만 1로 만들고 나머지는 건드리지 않는다.

**오탐은 왜 생기는가**

```
 비트는 '누가 켰는지'를 기억하지 않는다

   원소 A 의 자리 : 3, 17, 42
   원소 B 의 자리 : 17, 55, 91
   원소 C 의 자리 : 3, 42, 55        <- C 는 넣은 적이 없다

   A 와 B 를 넣으면 3, 17, 42, 55, 91 이 켜진다

   mightContain(C) 를 물으면 3, 42, 55 를 본다 -> 전부 켜져 있다 -> true
   그런데 C 는 넣은 적이 없다   ->  오탐

 원인 : 비트가 '켜졌다'만 기록하고 '누가 켰다'는 안 기록한다
        원소를 저장하지 않기로 한 결과가 정확히 여기서 나타난다

 오탐이 나려면 k 개 자리가 '전부' 남의 비트로 덮여 있어야 한다
   -> k 가 클수록 그 확률이 줄어든다 (자리가 많으니 전부 겹치기 어렵다)
   -> 그런데 k 가 크면 켜지는 비트도 많아진다 (겹치기 쉬워진다)
   -> 두 힘이 반대라서 최적 k 에 골짜기가 생긴다 (4번)
```

**비대칭이 한쪽으로만 향하는 이유**

```
 가능한 오답 두 가지

   누락 : "넣었는데 없다고 한다"
          -> 켜 둔 비트가 꺼져 있어야 가능하다
          -> 끄는 연산이 없으므로 불가능

   오탐 : "안 넣었는데 있다고 한다"
          -> 안 켠 자리가 남의 비트로 켜져 있으면 가능하다
          -> 비트를 공유하므로 언제든 가능

 즉 '비트를 켜기만 한다'는 성질 하나가
      누락을 불가능하게 만들고
      동시에 오탐을 가능하게 만든다
    같은 성질의 양면이다
```

**테스트가 이 계약을 최우선으로 검사한다**

```java
@Test

    // 오탐률은 치솟지만 **누락은 여전히 0 이어야 한다.**
    ProbabilisticSet<Integer> f = create(100, 0.01);
    for (int i = 0; i < 5000; i++) {
        f.add(i);
    }
    for (int i = 0; i < 5000; i++) {
        assertTrue(f.mightContain(i), "과부하 상태에서도 누락은 안 된다: " + i);
    }
}
```

- 논리: 용량의 **50배**를 넣어도 누락이 0이어야 한다는 것이 이 보장의 강도다.\
  오탐률은 무너져도 이것만은 안 무너진다.
- 논리: 계약 테스트의 중첩 클래스 이름이 아예 `NoFalseNegatives` — "계약의 핵심"이라고 적혀 있다.
- 논리: 이 보장이 있어야 "false면 디스크를 안 읽는다"가 안전하다.\
  누락이 한 번이라도 가능하면 **있는 데이터를 못 찾는** 사고가 나므로 앞단 필터로 쓸 수 없다.
- 한계: `CountingBloomFilter.remove` 가 이 단조성을 깨뜨린다 — 계수기를 내리기 때문이다.\
  그래서 거기서는 누락이 실제로 발생할 수 있다(7번).

**질문별 답**

- Q: 이 비대칭이 나오는 구조적 이유는?\
  A: `add` 가 **비트를 켜기만 하고 끄지 않기** 때문이다.\
  이 한 성질이 누락을 불가능하게 만들고(켜 둔 비트가 꺼질 일이 없다) 동시에 오탐을 가능하게 만든다(비트가 "누가 켰는지"를 기억하지 않아 남의 비트로 덮일 수 있다).\
  같은 성질의 양면이다.

- Q: 누락이 불가능한 근거가 코드의 어느 성질에서 오는가?\
  A: 세 가지가 맞물린다.\
  (1) `indexes(x)` 가 **결정론적**이라 같은 원소는 언제나 같은 k개 자리를 준다.\
  (2) `add(x)` 가 그 k개 자리를 전부 1로 만든다.\
  (3) `add` 에 `|=` 만 있고 비트를 끄는 코드가 없어 한 번 켠 1이 **절대 0으로 돌아가지 않는다**.\
  따라서 `add(x)` 이후 언제 물어도 그 자리들은 여전히 1이고, `mightContain(x)` 는 반드시 `true` 다 — 확률이 아니라 **구조적으로** 불가능하다.

#### 4. 두 공식이 왜 그 모양인가 — 9.586비트와 k의 골짜기

**질문**: `m = -n ln(p) / (ln2)^2`, `k = (m/n) ln2` — 이 두 공식이 왜 그 모양인가. 1% 오탐일 때 원소당 9.586비트라는 값이 원소가 int 든 100자 URL 이든 같은 이유는 무엇인가. k 를 더 키우면 오탐이 왜 오히려 늘어나는가.

**impl 코드**

```java
static int optimalBits(int n, double p) {
    double m = -n * Math.log(p) / (Math.log(2) * Math.log(2));
    return (int) Math.max(1, Math.ceil(m));
}

static int optimalHashCount(int m, int n) {
    int k = (int) Math.round((double) m / n * Math.log(2));
    return Math.max(1, k);
}
```

**공식의 유도**

```
 기호 : m = 비트 수,  n = 넣은 원소 수,  k = 해시 개수,  p = 오탐률

 1단계. 특정 비트 하나가 '아직 0' 일 확률

     add 한 번이 k 개 비트를 켠다
     어떤 비트가 그 k 번에서 안 걸릴 확률 = (1 - 1/m)^k
     n 개를 넣으면                        = (1 - 1/m)^(kn)
     m 이 크면 (1 - 1/m)^m ≈ 1/e 이므로   ≈ e^(-kn/m)

 2단계. 오탐률

     오탐 = 안 넣은 원소의 k 개 자리가 '전부' 켜져 있다
     비트 하나가 켜져 있을 확률 = 1 - e^(-kn/m)
     k 개가 전부 켜져 있을 확률 = (1 - e^(-kn/m))^k

     p = (1 - e^(-kn/m))^k          <- 이것이 expectedFalsePositiveRate 의 식이다
```

```java
@Override
public double expectedFalsePositiveRate() {
    return Math.pow(1 - Math.exp(-(double) hashCount * inserted / bits), hashCount);
}
//                                ^^^^^^^^^  ^^^^^^^^   ^^^^
//                                    k         n        m     -- 위 식 그대로다
```

```
 3단계. p 를 최소로 만드는 k

     t = e^(-kn/m) 로 두면 p = (1-t)^k
     ln p 를 k 로 미분해 0 이 되는 지점을 찾으면

         k* = (m/n) ln 2                <- 두 번째 공식

     이때 e^(-k*n/m) = e^(-ln2) = 1/2
     즉 '비트의 정확히 절반이 켜져 있을 때' 가 최적이다  (외우면 편한 형태)

 4단계. 최적 k 를 넣어 m 을 역산

     p = (1 - 1/2)^k* = (1/2)^((m/n) ln2)
     양변에 ln :  ln p = -(m/n)(ln2)^2
     m 에 대해 풀면

         m = -n ln(p) / (ln2)^2         <- 첫 번째 공식
```

- 논리: 두 공식은 **독립된 두 개가 아니다**.\
  `k` 를 최적으로 골랐다는 가정 아래 `m` 이 유도되고, 그 `m` 에서 다시 `k` 를 계산한다 — 그래서 코드도 `optimalBits` → `optimalHashCount` 순서로 부른다.

```java
this.bits = optimalBits(expectedInsertions, falsePositiveRate);
this.hashCount = optimalHashCount(bits, expectedInsertions);
```

**숫자로 확인** (테스트 `Sizing`)

```
 optimalBits(1000, 0.01)
    ln(0.01) = -4.60517
    -1000 x (-4.60517) = 4605.17
    (ln2)^2 = 0.693147^2 = 0.480453
    4605.17 / 0.480453 = 9585.06  -> ceil -> 9586        (테스트 assert 9586)

 optimalBits(1000, 0.001)  -> 14378
 optimalBits(1000, 0.1)    -> 4793
 optimalBits(1,000,000, 0.01) -> 9,585,059

 optimalHashCount(9586, 1000)
    9586 / 1000 = 9.586
    9.586 x 0.693147 = 6.6444  -> round -> 7             (테스트 assert 7)

 optimalHashCount(14378, 1000) -> 14.378 x 0.6931 = 9.965 -> 10
 optimalHashCount(4793, 1000)  -> 4.793 x 0.6931 = 3.322  -> 3
```

- 논리: 비트 수는 **올림**이다 — 내리면 계산한 것보다 비트가 적어져 목표 오탐률을 못 지킨다.\
  `p` 는 상한 약속이므로 넘으면 계약 위반이다.
- 논리: 해시 개수는 **반올림**이다 — `k` 는 골짜기의 위치라 위아래 어느 쪽으로 가도 조금 나빠질 뿐이다.\
  가장 가까운 정수를 고르는 것이 맞다.

```java
@Test
@DisplayName("k = (m/n) ln2, 최소 1")

    assertEquals(1, BloomFilter.optimalHashCount(145, 100), "1.45 -> 1");
    assertEquals(1, BloomFilter.optimalHashCount(1, 1000),
            "정수로 나누면 0 이 나온다. 최소 1 이어야 한다");
}
```

- 논리: `(double) m / n` 의 캐스팅이 없으면 `1 / 1000` 이 **정수 나눗셈으로 0**이 되어 `k = 0` 이 나온다.\
  `k = 0` 이면 자리가 하나도 없어 `mightContain` 이 **항상 true** 를 주는 쓸모없는 필터가 된다.
- 논리: `Math.max(1, ...)` 이 그 최후 방어선이다.\
  07번 `MedianFinder` 의 `/ 2.0`, 10번 `hitRatio` 의 `(double)` 캐스팅과 **같은 계열의 함정**이 세 챕터 연속으로 나온다.

**왜 원소 크기와 무관한가**

```
 공식에 등장하는 변수를 다시 보면

     m = -n ln(p) / (ln2)^2
          ^        ^
          |        오탐률 목표
          원소 '개수'

 원소의 '크기'가 어디에도 없다

 왜 없는가 : add 가 원소로 하는 일이 '해시 한 번'뿐이기 때문이다

     long h = mix64(item == null ? 0 : item.hashCode());

     int 하나든 100자 URL 이든 -> hashCode() 가 int 하나를 준다
     -> mix64 가 long 하나를 준다
     -> 거기서 k 개 자리를 뽑는다
     -> 켜는 비트 수는 k 개로 같다

 그래서 100만 개를 담는 데 필요한 비트가
     int 100만 개든, 100자 URL 100만 개든, 1MB 짜리 파일 100만 개든
     전부 9,585,059 비트(약 1.2MB)다

 대비
     HashSet 은 원소를 담으므로 100자 URL 100만 개면 최소 100MB 가 넘는다
     -> 원소가 클수록 블룸 필터의 이득이 커진다
     README 의 "이 '원소 크기와 무관'이 이기는 지점입니다" 가 이 뜻이다
```

> **해시(hash)** — 임의 크기의 입력을 고정 크기 값으로 줄이는 함수.\
> 예: 100자 URL도 64비트 하나로 줄어들므로, 그 뒤의 모든 계산이 원소 크기와 무관해진다.

**k 를 더 키우면 왜 오탐이 오히려 늘어나는가**

```
 k 가 커질 때 반대 방향으로 작용하는 두 힘

   힘 A (좋아짐) : 검사할 자리가 늘어난다
       오탐이 나려면 k 개가 '전부' 켜져 있어야 한다
       k 가 크면 그 조건이 까다로워진다
       -> p = (...)^k 에서 지수가 커지는 효과

   힘 B (나빠짐) : add 한 번이 켜는 비트가 늘어난다
       n 개를 넣으면 켜지는 비트가 대략 kn 개
       -> 비트 배열이 빨리 찬다 -> 개별 비트가 켜져 있을 확률이 올라간다
       -> p = (1 - e^(-kn/m))^k 에서 괄호 안이 커지는 효과

   k 가 작을 때 : A 의 이득이 크다 -> k 를 늘리면 좋아진다
   k 가 클 때   : B 의 손해가 크다 -> k 를 늘리면 나빠진다
   -> 사이 어딘가에 최소점(골짜기)이 있다.  그 위치가 정확히 k* = (m/n) ln2
```

```
 m/n = 9.586 (1% 설계) 일 때 k 를 바꿔 가며 p 를 계산하면 (원본에 근거 없음 -- 내 추론)

   k = 1  :  (1 - e^(-1/9.586))^1   = (1-0.9006)^1  ≈ 0.0994   (9.9%)
   k = 3  :  (1 - e^(-3/9.586))^3   = (1-0.7310)^3  ≈ 0.0195   (1.9%)
   k = 5  :  (1 - e^(-5/9.586))^5   = (1-0.5934)^5  ≈ 0.0111   (1.1%)
   k = 7  :  (1 - e^(-7/9.586))^7   = (1-0.4816)^7  ≈ 0.0100   (1.0%)  <- 골짜기
   k = 10 :  (1 - e^(-10/9.586))^10 = (1-0.3499)^10 ≈ 0.0113   (1.1%)
   k = 20 :  (1 - e^(-20/9.586))^20 = (1-0.1225)^20 ≈ 0.0693   (6.9%)  <- 도로 나빠진다

        p
      10% |*
          | \
          |  \
       2% |   \_
       1% |     \___*___/          <- k=7 근처가 바닥
          |            /
       7% |           /
          +---------------------- k
           1  3  5  7  10    20

 k = 20 이면 k = 1 일 때보다는 낫지만 k = 7 보다 7배 나쁘다
 "많을수록 좋다"가 성립하지 않는다는 것이 요점이다
```

- 논리: 골짜기의 바닥에서 **비트의 정확히 절반이 켜져 있다**(3단계 유도의 `e^(-kn/m) = 1/2`).\
  "반쯤 찼을 때가 최적"이 이 공식의 직관적 형태다.
- 논리: k를 키우는 것은 공짜가 아니다 — `add`/`mightContain` 이 **k번 자리를 계산하고 접근**하므로 시간도 k에 비례한다.\
  느려지면서 오탐도 늘어나는 구간이 존재한다.

**질문별 답**

- Q: 두 공식이 왜 그 모양인가?\
  A: 비트 하나가 아직 0일 확률이 `e^(-kn/m)` 이므로 오탐률이 `p = (1 - e^(-kn/m))^k` 가 된다.\
  이 `p` 를 `k` 에 대해 최소화하면 `k = (m/n) ln2` 가 나오고(그 지점에서 비트의 정확히 절반이 켜진다), 그 최적 `k` 를 다시 `p` 식에 넣어 `m` 에 대해 풀면 `m = -n ln(p)/(ln2)^2` 가 나온다.\
  두 공식은 독립된 것이 아니라 **한 최적화의 앞뒤**이며, 코드도 `optimalBits` → `optimalHashCount` 순서로 부른다.

- Q: 9.586비트가 원소가 int든 100자 URL이든 같은 이유는?\
  A: 공식에 원소의 **크기**가 어디에도 없고 **개수**와 **오탐률**만 있기 때문이다.\
  `add` 가 원소로 하는 일은 `hashCode()` → `mix64` 로 64비트 하나를 얻어 k개 자리를 뽑는 것뿐이라, 원소가 무엇이든 켜는 비트 수가 k로 같다.\
  `HashSet` 은 원소를 담으므로 원소가 클수록 메모리가 늘어난다 — **원소가 클수록 블룸 필터의 이득이 커진다**.

- Q: k를 더 키우면 오탐이 왜 오히려 늘어나는가?\
  A: 반대 방향의 두 힘이 있기 때문이다.\
  k가 크면 "전부 켜져 있어야 한다"는 조건이 까다로워져 좋아지지만, 동시에 `add` 한 번이 켜는 비트가 늘어 배열이 빨리 차 나빠진다.\
  작은 k에서는 앞의 힘이, 큰 k에서는 뒤의 힘이 이겨 그 사이에 **골짜기**가 생기며, 바닥이 `k = (m/n) ln2` 다.\
  `m/n = 9.586` 에서 k=7이 약 1.0%인데 k=20이면 약 6.9%로 도로 나빠진다(계산은 내 추론).

#### 5. 이중 해싱의 함정 셋, 그리고 테스트가 못 잡는 방어선

**질문**: 해시 함수를 k 개 만들지 않고 64비트 해시 하나를 반으로 갈라 `idx_i = h1 + i*h2` 로 쓰는 이중 해싱의 함정 셋은 무엇인가. 그중 `h2 == 0` 방어선이 이 설계에서는 어떤 테스트로도 못 잡히는 이유는 무엇이고, 19번에서는 왜 잡을 수 있게 되는가 — "테스트가 못 잡는다"가 코드의 성질이 아니라 설계의 성질이라는 말은 무슨 뜻인가.

**impl 코드**

```java
static long mix64(long z) {
    z += 0x9E3779B97F4A7C15L;
    z = (z ^ (z >>> 30)) * 0xBF58476D1CE4E5B9L;
    z = (z ^ (z >>> 27)) * 0x94D049BB133111EBL;
    return z ^ (z >>> 31);
}

int[] indexes(T item) {
    long h = mix64(item == null ? 0 : item.hashCode());
    int h1 = (int) h;
    int h2 = (int) (h >>> 32);
    if (h2 == 0) {
        h2 = 1;
    }
    int[] out = new int[hashCount];
    for (int i = 0; i < hashCount; i++) {
        out[i] = Math.floorMod(h1 + i * h2, bits);
    }
    return out;
}
```

> **이중 해싱(double hashing)** — 독립적인 해시 두 개 `h1`, `h2` 로 `h1 + i·h2` 형태의 수열을 만들어 여러 해시를 대신하는 기법.\
> 예: Kirsch & Mitzenmacher(2006)가 블룸 필터에서 이 방식이 진짜 k개 해시와 이론상 같은 성능을 낸다는 것을 보였다.

- 논리: 해시 함수를 k개 만들면 계산도 k배 들고 함수끼리 독립인지도 보장하기 어렵다.\
  64비트 하나를 반으로 갈라 쓰면 **해시 계산이 한 번**으로 끝난다.

**함정 1 — 음수 인덱스**

```
 h1 + i * h2 는 int 연산이다

   h1 도 h2 도 32비트 int 이므로 음수일 수 있다
   곱셈에서 오버플로도 난다
   -> 결과가 음수일 수 있다

 (A) % 를 쓰면
     자바의 % 는 '피제수의 부호'를 따른다
        -5 % 10 == -5      (수학의 나머지 5 가 아니다)
     -> out[i] 가 음수 -> words[음수 >>> 6] -> ArrayIndexOutOfBoundsException
        또는 (>>> 로 양수가 되어) 엉뚱한 자리를 건드린다

 (B) Math.floorMod 를 쓰면 (impl)
        Math.floorMod(-5, 10) == 5      '제수의 부호'를 따른다
     -> 항상 [0, bits) 범위

 이것이 05번 해시맵에서 본 '음수 해시' 함정과 같은 것이다
   (README: "함정이 셋이고, 그중 하나는 05번 음수 해시와 같은 함정입니다.")
```

```java
@Test
@DisplayName("자리가 k 개이고 전부 범위 안이다")
void countAndRange() {
    BloomFilter<Integer> f = new BloomFilter<>(1000, 0.01);
    for (int key : new int[]{0, 1, -1, 42, Integer.MIN_VALUE, Integer.MAX_VALUE}) {
        int[] idx = f.indexes(key);
        assertEquals(f.hashCount(), idx.length);
        for (int i : idx) {
            assertTrue(i >= 0 && i < f.bitSize(),
                    "자리 " + i + " 가 범위 밖이다. floorMod 를 안 썼을 수 있다");
        }
    }
}
```

- 논리: 테스트가 `Integer.MIN_VALUE`, `-1` 같은 **음수 경계**를 콕 집어 넣는다.\
  양수만 넣으면 `%` 를 써도 통과해 버린다.

> **floorMod** — 나머지의 부호를 제수(나누는 수)의 부호에 맞추는 나머지 연산.\
> 예: `-5 % 10` 은 자바에서 -5지만 `Math.floorMod(-5, 10)` 은 5다 — 배열 인덱스에는 후자가 필요하다.

**함정 2 — 해시를 안 섞으면 몰린다**

```
 자바의 Integer.hashCode() 는 '값 그대로' 다

    (42).hashCode() == 42

 mix64 없이 쓰면
    h = 42
    h1 = (int) 42 = 42
    h2 = (int) (42 >>> 32) = 0      <- 상위 32비트가 전부 0이다!
    -> h2 == 0 방어선이 매번 발동한다 -> h2 = 1
    -> 자리 = 42, 43, 44, 45, ...   연속된 칸이 된다

 그러면 0..999 를 넣을 때 비트 배열 앞쪽 1000여 칸에 전부 줄을 선다
   -> 나머지 8500칸은 텅 비고 앞쪽만 꽉 찬다
   -> 오탐률이 공식보다 훨씬 나빠진다

 mix64 (splitmix64 계열의 비트 섞기)를 통과시키면
   입력이 1씩 달라져도 출력의 비트가 절반쯤 달라진다(눈사태 효과)
   -> 상위 32비트도 골고루 채워진다 -> h2 가 제대로 된 보폭이 된다
```

```java
@Test
@DisplayName("연속된 정수가 한곳에 몰리지 않는다")
void spreadsSequentialKeys() {
    // Integer 의 hashCode 는 값 그대로다. 섞지 않고 쓰면 0..999 가
    // 비트 배열 앞쪽 1000칸에 그대로 줄을 선다.
    BloomFilter<Integer> f = new BloomFilter<>(1000, 0.01);
    int firstTenth = 0;
    int total = 0;
    for (int key = 0; key < 1000; key++) {
        for (int i : f.indexes(key)) {
            total++;
            if (i < f.bitSize() / 10) {
                firstTenth++;
            }
        }
    }
    double share = (double) firstTenth / total;
    assertTrue(share > 0.05 && share < 0.15,
            "앞 10% 구간에 자리의 " + share + " 가 몰렸다. 해시를 안 섞은 것이다");
}
```

- 논리: 앞 10% 구간에 자리의 약 10%가 있어야 정상이다 — `0.05 ~ 0.15` 범위가 그 허용폭이다.
- 논리: 이 테스트는 **잡을 수 있는** 함정이다 — `mix64` 를 빼면 실제로 실패한다.

> **눈사태 효과(avalanche effect)** — 입력이 1비트만 달라져도 출력 비트의 절반쯤이 달라지는 성질.\
> 예: `mix64` 가 그 성질을 만들어, 연속된 정수 키가 비트 배열 전체에 고르게 퍼지게 한다.

**함정 3 — `h2 == 0`**

```
 h2 가 0 이면 어떻게 되는가

    idx_i = h1 + i * 0 = h1        모든 i 에 대해 같다
    -> k 개 자리가 전부 같은 한 칸이다
    -> 실질적으로 k = 1 인 필터가 된다
    -> 오탐률이 목표치보다 크게 나빠진다 (4번 표의 k=1 칸: 1% 설계에서 약 9.9%)

    누락은 생기지 않는다 (같은 자리를 켜고 같은 자리를 보므로)
    -> 계약은 안 깨지고 '품질'만 조용히 나빠진다

 방어선
    if (h2 == 0) { h2 = 1; }
```

```java
@Test
@DisplayName("해시 하나가 같아도 자리 전체가 같지는 않다")
void notAllSame() {
    BloomFilter<Integer> f = new BloomFilter<>(1000, 0.01);
    int[] idx = f.indexes(12345);
    boolean allEqual = true;
    for (int i = 1; i < idx.length; i++) {
        if (idx[i] != idx[0]) {
            allEqual = false;
            break;
        }
    }
    assertTrue(!allEqual, "자리 " + idx.length + "개가 전부 같다. h2 가 0 이었을 수 있다");
}
```

- 논리: 이 테스트가 `h2 == 0` 을 노린 테스트다 — 그런데 **키를 `12345` 하나로 고정**하고 있다.\
  그 키가 하필 `h2 == 0` 을 만들지 않는 한 이 테스트는 방어선이 있든 없든 통과한다.

**왜 이 설계에서는 어떤 테스트로도 못 잡는가**

```
 테스트가 통제할 수 있는 입력 = 원소 item 하나뿐이다

    indexes(item) 의 h2 = (int)(mix64(item.hashCode()) >>> 32)

 h2 == 0 을 만들려면
    mix64(x) 의 상위 32비트가 전부 0이 되는 x 를 찾아야 한다

 문제 1 : mix64 를 거꾸로 풀어야 한다
    mix64 는 비트 섞기 함수라 '어떤 입력이 그 출력을 내는가'를 손으로 못 구한다
    (수학적으로는 가역이지만, 테스트에 역함수를 구현해 넣는 것은 테스트가 아니다)

 문제 2 : 그런 x 가 존재하지 않을 수도 있다
    item 이 Integer 면 입력이 될 수 있는 값은 int 범위 2^32 개뿐이다
    mix64 의 출력 공간은 2^64 이고, 그중 상위 32비트가 0인 것은 2^32 개
    -> 2^32 개 입력이 2^64 공간에 흩어질 때 그 표적에 맞을 기대 개수가 '대략 1 개'다
    -> 있을 수도, 없을 수도 있다.  보장되지 않는다
    (원본에 근거 없음 -- 내 추론: README 는 "못 잡는다"만 단언한다)

 문제 3 : 무작정 탐색도 안 된다
    2^32 개를 다 훑는 테스트는 실행 시간이 현실적이지 않고,
    다 훑어서 못 찾으면 그것이 곧 '못 잡는다'의 증명이다

 => 그래도 방어선은 남긴다
    해시 함수를 바꾸는 순간(다른 mix, 다른 타입의 item) 살아나는 방어선이기 때문이다
    "지금 못 잡는다"가 "필요 없다"가 아니다
```

**19번에서는 왜 잡을 수 있게 되는가**

```
 README 가 그 차이를 적어 뒀다

   "19번에서는 해시가 seed 를 주입받아 입력이 (원소, seed) 쌍이 되고,
    그러면 걸리는 짝을 실제로 구성할 수 있습니다."

 11번 (이 설계)
     해시 입력 = item 하나           -> 탐색 공간이 1차원이고 테스트가 통제 못 한다
                                       (item 을 바꿔도 h2 가 어떻게 될지 예측 불가)

 19번 (seed 주입)
     해시 입력 = (item, seed) 쌍     -> 탐색 공간이 2차원이고 seed 는 테스트가 '고른다'
     -> item 을 고정하고 seed 를 0, 1, 2, ... 로 돌려가며
        h2 == 0 이 되는 짝을 실제로 찾아낼 수 있다
     -> 찾은 짝을 테스트에 하드코딩하면 방어선이 실제로 검증된다
```

**"테스트가 못 잡는다"가 설계의 성질이라는 말**

```
 같은 방어선, 같은 코드 한 줄

     if (h2 == 0) { h2 = 1; }

 11번에서는 검증할 수 없고, 19번에서는 검증할 수 있다

 무엇이 달라졌나 -- 코드는 하나도 안 달라졌다
   달라진 것은 '해시 함수가 무엇을 입력으로 받는가' 라는 설계 결정이다

     해시가 원소만 받는다        -> 테스트가 통제할 수 있는 축이 하나
     해시가 (원소, seed) 를 받는다 -> 테스트가 통제할 수 있는 축이 둘

 즉 검증 가능성(testability)은
   "테스트를 잘 썼는가"가 아니라
   "그 코드가 테스트에게 어떤 손잡이를 주는가"로 정해진다

 그래서 README 의 결론이 나온다
   무작위(또는 해시 파라미터)를 '주입받게' 만드는 규칙이
   성능·재현성만이 아니라 검증 가능성까지 바꾼다
```

> **검증 가능성(testability)** — 어떤 동작을 테스트가 실제로 확인할 수 있는 정도. 테스트 작성 기술이 아니라 대상 코드의 설계가 정한다.\
> 예: 무작위나 해시 파라미터를 밖에서 주입받게 만들면 테스트가 특정 경로를 강제로 밟게 할 수 있다.

> **의존성 주입(dependency injection)** — 필요한 부품(비교자·난수원·seed)을 객체가 스스로 만들지 않고 밖에서 받는 설계.\
> 예: 07번 힙이 `Comparator` 를 받았듯, 12번 스킵 리스트는 `Random` 을 받아 테스트가 동전 던지기 결과를 고를 수 있게 한다.

- 논리: 07번에서 `Comparator` 를 주입받아 `MinHeap`/`MaxHeap` 이 코드 중복 없이 나왔던 것과 **같은 기법이 다른 목적**으로 쓰이는 사례다.\
  거기서는 재사용, 여기서는 검증 가능성이다.

**질문별 답**

- Q: 이중 해싱의 함정 셋은?\
  A: (1) **음수 인덱스** — `h1 + i·h2` 가 int 오버플로/음수가 되므로 `%` 가 아니라 `Math.floorMod` 를 써야 한다(05번 음수 해시와 같은 함정).\
  (2) **해시를 안 섞음** — `Integer.hashCode()` 가 값 그대로라 섞지 않으면 상위 32비트가 0이고 연속 키가 앞쪽에 줄을 선다 → `mix64` 가 필요하다.\
  (3) **`h2 == 0`** — 보폭이 0이 되어 k개 자리가 전부 같은 한 칸이 되고, 실질적으로 k=1인 필터가 되어 오탐률이 조용히 나빠진다.

- Q: `h2 == 0` 방어선이 왜 어떤 테스트로도 못 잡히는가?\
  A: 테스트가 통제할 수 있는 입력이 **원소 하나뿐**이기 때문이다.\
  `h2 == 0` 을 만들려면 `mix64(x)` 의 상위 32비트가 0이 되는 `x` 를 찾아야 하는데, `mix64` 를 거꾸로 풀어야 하고 `Integer` 입력 범위(2³²) 안에 그런 값이 **존재한다는 보장도 없다**.\
  그래도 방어선은 남긴다 — 해시 함수나 원소 타입을 바꾸는 순간 살아나는 방어선이기 때문이다.

- Q: 19번에서는 왜 잡을 수 있게 되는가?\
  A: 해시가 **seed를 주입받아** 입력이 `(원소, seed)` 쌍이 되기 때문이다.\
  테스트가 원소를 고정하고 seed를 0, 1, 2… 로 돌려가며 `h2 == 0` 이 되는 짝을 실제로 **구성**할 수 있고, 그 짝을 테스트에 넣으면 방어선이 검증된다.

- Q: "테스트가 못 잡는다"가 코드의 성질이 아니라 설계의 성질이라는 말은?\
  A: 방어선 코드(`if (h2 == 0) h2 = 1;`)는 11번과 19번이 **완전히 같은데** 한쪽은 검증할 수 없고 한쪽은 할 수 있다는 뜻이다.\
  달라진 것은 "해시가 무엇을 입력으로 받는가"라는 **설계 결정**이고, 그것이 테스트가 통제할 수 있는 축의 개수를 정한다.\
  즉 검증 가능성은 테스트를 잘 쓰는 기술이 아니라 **대상 코드가 테스트에게 어떤 손잡이를 주는가**로 정해진다 — 무작위·파라미터를 주입받게 만드는 규칙(12번)이 성능·재현성만이 아니라 검증 가능성까지 바꾸는 이유다.

#### 6. 최악의 사용 패턴 — 용량을 넘기면 왜 이미 늦었는가

**질문**: 용량 100만으로 잡은 `BloomFilter` 에 1000만 개를 넣으면 오탐률이 어떻게 되고, 그 시점에 왜 이미 늦었는가. 05번 해시맵은 리사이즈로 복구했는데 여기서는 왜 다시 만들 수조차 없는가. 최선의 경우는 언제인가.

**용량이 고정이라는 사실**

```java
@Test
@DisplayName("원소를 담지 않으므로 크기가 고정이다")
void fixedSize() {
    BloomFilter<Integer> f = new BloomFilter<>(1000, 0.01);
    long before = f.bitSize();
    for (int i = 0; i < 5000; i++) {
        f.add(i);
    }
    assertEquals(before, f.bitSize(), "용량의 5배를 넣어도 크기가 그대로다");
}
```

- 논리: 생성자에서 `bits` 와 `hashCount` 가 **`final` 로 확정**된다 — 그 뒤에 바꿀 방법이 없다.
- 논리: 넣어도 크기가 안 늘어난다는 것은 **장점이자 함정**이다.\

#### 7. 왜 삭제를 못 하는가, `CountingBloomFilter` 는 무엇을 치르는가

**질문**: 기본형이 왜 삭제를 못 하는가(A 와 B 가 3번 비트를 함께 켠 상황). `CountingBloomFilter` 는 그걸 어떻게 풀고, 대신 치르는 값 셋은 무엇인가 — 특히 오탐인 원소를 지우면 왜 "누락 없음" 보장 자체가 깨지는가. 포화된 계수기(255)를 내리면 안 되는 이유는.

**기본형이 삭제를 못 하는 이유**

```
 원소 A 의 자리 : 3, 17, 42
 원소 B 의 자리 : 3, 55, 91           <- 3번 비트를 A 와 공유한다

 A 와 B 를 넣으면
    비트 3, 17, 42, 55, 91 이 켜진다

 A 를 지운다고 A 의 자리를 끄면
    3 -> 0,  17 -> 0,  42 -> 0

    이제 mightContain(B) 를 물으면
       3 : 꺼짐!  -> false
    B 는 넣은 적이 있는데 없다고 한다  ->  누락(false negative)

 => 이 자료구조의 유일한 보장("누락 없음")이 깨진다

 근본 원인 : 비트가 '몇 명이 켰는지'를 기억하지 않는다
             1 이라는 값은 "최소 한 명이 켰다"만 뜻하고
             "A 만 켰다"인지 "A 와 B 가 켰다"인지 구분할 수 없다
             -> 끌지 말지 판단할 정보가 없다
```

- 논리: 09번 트라이의 `remove` 와 **같은 종류의 문제**다.\
  거기서도 `"apple"` 을 지우다 `"app"` 을 날릴 수 있었고, 해법도 같았다 — **몇 명이 쓰고 있는지 세어 두는 것**(`wordsBelow`).
- 논리: 즉 `CountingBloomFilter` 의 계수기는 09번 `wordsBelow` 와 같은 **참조 계수**다.

> **참조 계수(reference counting)** — 자원을 쓰는 사용자 수를 세어 두고, 0이 될 때만 해제하는 기법.\
> 예: 트라이의 `wordsBelow`, 카운팅 블룸 필터의 계수기가 같은 발상이다 — 0이 아니면 아직 누군가 쓰고 있다는 뜻이다.

**`CountingBloomFilter` 의 해법**

```java
static final int MAX_COUNT = 255;
private final byte[] counters;      // 비트 1개 -> 바이트 1개
```

```java
@Override
public void add(T item) {
    for (int idx : indexes(item)) {
        int c = counters[idx] & 0xFF;
        if (c == MAX_COUNT) {
            saturations++;
        } else {
            counters[idx] = (byte) (c + 1);
        }
    }
    inserted++;
}

public boolean remove(T item) {
    if (!mightContain(item)) {
        return false;
    }
    for (int idx : indexes(item)) {
        int c = counters[idx] & 0xFF;
        if (c != MAX_COUNT && c > 0) {
            counters[idx] = (byte) (c - 1);
        }
    }
    inserted--;
    return true;
}

@Override
public boolean mightContain(T item) {
    for (int idx : indexes(item)) {
        if ((counters[idx] & 0xFF) == 0) {
            return false;
        }
    }
    return true;
}
```

```
 비트 대신 계수기를 둔다

   A 넣기 : counters[3]++ counters[17]++ counters[42]++     3번 = 1
   B 넣기 : counters[3]++ counters[55]++ counters[91]++     3번 = 2

   A 지우기 : counters[3]-- counters[17]-- counters[42]--   3번 = 1  (0 이 아니다!)

   mightContain(B) : 3번=1, 55번=1, 91번=1 -> 전부 0 보다 크다 -> true
   B 가 살아남는다
```

- 논리: `& 0xFF` 는 자바의 `byte` 가 **부호 있는 8비트**(-128~127)이기 때문이다.\
  128 이상을 담으려면 읽을 때 부호 없는 값으로 해석해야 한다.
- 논리: `mightContain` 이 "전부 0보다 크면 true"인 것은 기본형의 "전부 1이면 true"와 같은 판정이다.

```java
@Test
@DisplayName("자리를 공유하는 다른 원소는 살아남는다")
void sharedSlotsSurvive() {
    // 기본형이 삭제를 못 하는 이유가 바로 이것이다.
    // 비트를 끄면 같은 자리를 쓰는 원소가 같이 사라진다.
    CountingBloomFilter<Integer> f = counting(1000, 0.01);
    for (int i = 0; i < 1000; i++) {
        f.add(i);
    }
    for (int i = 0; i < 500; i++) {
        assertTrue(f.remove(i), i + " 를 못 지웠다");
    }
    for (int i = 500; i < 1000; i++) {
        assertTrue(f.mightContain(i),
                i + " 가 사라졌다. 남의 계수기를 0 까지 내렸다는 뜻이다");
    }
    assertEquals(500, f.insertedCount());
}
```

**치르는 값 1 — 메모리 8배**

**치르는 값 2 — 포화된 계수기는 영원히 안 내려간다**

```

    계수기가 1바이트라 256 이상을 담을 수 없다
    257 번째 add 에서 올리면 오버플로로 0 이 되어버린다 -> 즉시 누락이 생긴다
    -> 그래서 255 에서 '멈추고' saturations 만 센다

 왜 내리면 안 되는가
    255 는 "255 이상"을 뜻하는 값이지 "정확히 255"가 아니다
    실제로는 300 이었을 수도, 1000 이었을 수도 있다

    만약 포화 자리도 내린다면
       300번 넣고(계수기는 255에서 멈춤) 300번 지우면 255 - 300 -> 0 아래로
       -> 아직 그 자리를 쓰는 원소가 있어도 0 이 되어 사라진다
       -> 누락 발생

    그래서 코드가 c != MAX_COUNT 조건을 건다

        if (c != MAX_COUNT && c > 0) { counters[idx] = (byte) (c - 1); }

 선택의 의미
    포화 자리를 얼려 두면 -> 그 자리는 영원히 1 이상 -> '영구 오탐' 이 생긴다
    포화 자리를 내리면    -> '누락' 이 생길 수 있다

    누락(치명적) 대신 영구 오탐(감수 가능)을 택한 것이다
    -> 계약의 우선순위가 코드의 조건문 하나로 드러난다
```

> **포화(saturation)** — 계수기가 표현 범위의 최댓값에 도달해 더 못 세는 상태.\
> 예: 1바이트 계수기는 255에서 멈추고, 그 뒤로는 몇 번 더 들어왔는지 알 수 없게 된다.

**치르는 값 3 — 오탐인 원소를 지우면 "누락 없음"이 깨진다**

```
 시나리오

   x 는 넣은 적이 없다. 그런데 x 의 자리 k 개가 남들 때문에 전부 켜져 있다 (오탐)

   remove(x) 를 부르면
     mightContain(x) 가 true 다 -> 필터는 x 가 진짜라고 믿는다
     -> x 의 자리 k 개의 계수기를 전부 1 씩 내린다

   그중 계수기가 '1' 이던 자리가 있으면 그 자리는 0 이 된다
   그 자리를 쓰던 진짜 원소 y 는 이제 mightContain(y) 가 false 다

   -> 누락 발생

 왜 항상 생기지는 않는가 (테스트 주석의 설명)
   그 자리의 계수기가 2 이상이면 하나 내려도 0 이 안 된다
   그래서 '계수기가 1 인 자리를 밟는 오탐' 이어야 한다
```

```java
@Test
@DisplayName("넣은 적 없는 것을 지우면 넣은 것이 사라진다")
void falseNegativeAppears() {
    int ghost = -1;
    int lost = 0;

    for (int candidate = 1000; candidate < 50_000 && lost == 0; candidate++) {
        CountingBloomFilter<Integer> f = counting(200, 0.5);   // 자리 하나짜리 해시
        for (int i = 0; i < 100; i++) {
            f.add(i);
        }
        if (!f.mightContain(candidate)) {
            continue;
        }
        assertTrue(f.remove(candidate), "필터는 이걸 진짜라고 믿는다");
        int missing = 0;
        for (int i = 0; i < 100; i++) {
            if (!f.mightContain(i)) {
                missing++;
            }
        }
        if (missing > 0) {
            ghost = candidate;
            lost = missing;
        }
    }

    assertTrue(lost > 0,
            "넣은 적 없는 원소를 지워 누락이 생기는 경우를 못 찾았다");
    assertTrue(ghost >= 0);
}
```

```
 테스트가 조건을 일부러 만든다

   counting(200, 0.5)
     p = 0.5 로 아주 느슨하게 잡는다
     -> m = -200 x ln(0.5) / (ln2)^2 = 200 x 0.6931 / 0.4805 ≈ 288.5 -> 289 비트
     -> k = round(289/200 x 0.6931) = round(1.0016) = 1      <- 자리가 하나뿐이다
        (주석의 "자리 하나짜리 해시")

   k=1 이면
     오탐이 자주 난다 (p=0.5 설계에 100개를 넣었으니 비트가 절반쯤 켜져 있다)
     그리고 오탐 하나를 지우면 그 '한 자리'만 내려가는데,
     그 자리가 딱 1이었으면 즉시 누락이 생긴다

   candidate 를 1000부터 훑으며 그런 경우를 실제로 찾아낸다
```

- 논리: 이것이 **가장 중요한 대가**다 — 삭제를 얻는 대신 이 자료구조의 **유일한 보장을 잃는다**.
- 논리: 기본형은 "오탐만 있고 누락은 절대 없다"였는데, Counting은 `remove` 를 쓰는 순간 그 말을 할 수 없게 된다.
- 논리: 그래서 앞단 필터 용도로는 **위험하다** — "false면 디스크를 안 읽는다"가 더 이상 안전하지 않다.\
  있는 데이터를 못 찾는 사고가 날 수 있다.
- 한계: 대응책은 "삭제한 적이 있으면 그 보장을 포기한다"를 명시하거나, 삭제를 아예 안 쓰는 것이다.\
  (원본에 근거 없음 — 내 추론)

**보조 성질 — 계수기는 진짜 개수다**

```java
@Test
@DisplayName("같은 원소를 두 번 넣으면 두 번 지워야 한다")
void countsAreRealCounts() {
    CountingBloomFilter<Integer> f = counting(100, 0.01);
    f.add(5);
    f.add(5);
    assertTrue(f.remove(5));
    assertTrue(f.mightContain(5), "두 번 넣었으니 한 번 지워도 남아 있어야 한다");
    assertTrue(f.remove(5));
    assertFalse(f.mightContain(5));
}
```

- 논리: 기본형의 `add` 는 **멱등**이다(같은 것을 두 번 넣어도 비트는 그대로).\
  Counting은 멱등이 아니다 — 넣은 횟수만큼 지워야 한다.
- 논리: 계약 주석에 그 차이가 적혀 있다 — "같은 원소를 두 번 넣어도 비트는 그대로다(**계수기형은 다르다**)".

> **멱등성(idempotence)** — 같은 연산을 여러 번 해도 결과가 한 번 한 것과 같은 성질.\
> 예: 기본 블룸 필터의 `add` 는 멱등이지만, 카운팅 블룸 필터의 `add` 는 계수기를 올리므로 멱등이 아니다.

**질문별 답**

- Q: 기본형이 왜 삭제를 못 하는가?\
  A: 비트가 **"몇 명이 켰는지"를 기억하지 않기** 때문이다.\
  A와 B가 3번 비트를 함께 켰는데 A를 지운다고 3번을 끄면 B의 판정이 `false` 가 되어 **누락**이 생긴다.\
  1이라는 값은 "최소 한 명이 켰다"만 뜻해서 끌지 말지 판단할 정보가 없다 — 09번 트라이에서 `"apple"` 을 지우다 `"app"` 을 날리는 문제와 같은 구조다.

- Q: `CountingBloomFilter` 는 그걸 어떻게 푸는가?\
  A: 비트 대신 **계수기**를 둔다 — `add` 가 1씩 올리고 `remove` 가 1씩 내리며, `mightContain` 은 전부 0보다 큰지를 본다.\
  09번 `wordsBelow` 와 같은 **참조 계수**이고, 0이 아니면 아직 누군가 그 자리를 쓰고 있다는 뜻이다.

- Q: 대신 치르는 값 셋은?\
  A: (1) **메모리 8배** — 자리 하나가 1비트에서 1바이트가 된다(실무의 4비트 계수기면 4배).\
  (2) **포화된 계수기는 영원히 안 내려간다** — 그 자리에 영구 오탐이 남는다.\
  (3) **오탐인 원소를 지우면 누락이 생긴다** — 이 자료구조의 유일한 보장이 깨진다.

- Q: 오탐인 원소를 지우면 왜 "누락 없음" 보장이 깨지는가?\
  A: `remove(x)` 는 `mightContain(x)` 가 `true` 면 진짜라고 믿고 x의 자리 계수기를 전부 내리는데, x는 넣은 적이 없으므로 그 감소분이 **남의 몫**이기 때문이다.\
  내린 자리 중 계수기가 1이던 곳이 0이 되면, 그 자리를 쓰던 진짜 원소가 즉시 사라진다.\
  (계수기가 2 이상이면 0이 안 되므로 항상 생기지는 않는다 — `falseNegativeAppears` 가 `k=1` 짜리 필터로 그런 경우를 실제로 찾아 보여준다.)

- Q: 포화된 계수기(255)를 내리면 안 되는 이유는?\
  A: 255는 "정확히 255"가 아니라 **"255 이상"** 을 뜻하는 값이기 때문이다.\
  실제로 300번 들어왔을 수 있는데 255에서 시작해 내리면, 아직 그 자리를 쓰는 원소가 남아 있어도 0이 되어 **누락**이 생긴다.\
  포화 자리를 얼려 두면 영구 오탐이 남고 내리면 누락이 생기는데, **누락(치명적) 대신 영구 오탐(감수 가능)** 을 택한 것이다 — `c != MAX_COUNT` 조건 하나에 그 우선순위가 드러난다.

#### 8. `ScalableBloomFilter` — 늘리는 게 아니라 잇는다

**질문**: 왜 새 필터일수록 용량은 2배로 키우면서 오탐률은 절반으로 조이는가. 전체 오탐률 `1 - (1-p)(1-p/2)(1-p/4)...` 가 2p 를 넘지 않는 이유는 무엇이고, 그 대가로 `mightContain` 비용은 어떻게 되는가. 세 구현 중 언제 무엇을 고르는가.

**impl 코드**

```java
static final double TIGHTENING = 0.5;
static final int GROWTH = 2;

private void grow() {
    filters.add(new BloomFilter<>(nextCapacity, nextFpr));
    nextFpr = nextFpr * TIGHTENING;        // 오탐률은 절반으로 조인다
    nextCapacity = nextCapacity * GROWTH;  // 용량은 두 배로 키운다
}

@Override
public void add(T item) {
    BloomFilter<T> current = filters.isEmpty() ? null : filters.get(filters.size() - 1);
    if (current == null || current.insertedCount() >= current.capacity()) {
        grow();
        current = filters.get(filters.size() - 1);
    }
    current.add(item);
    inserted++;
}

@Override
public boolean mightContain(T item) {
    for (BloomFilter<T> f : filters) {
        if (f.mightContain(item)) {
            return true;
        }
    }
    return false;
}
```

```
 구조

   필터 0 : 용량 n,   오탐률 p       <- 처음 n 개가 여기
   필터 1 : 용량 2n,  오탐률 p/2     <- 다음 2n 개가 여기
   필터 2 : 용량 4n,  오탐률 p/4     <- 다음 4n 개가 여기
   ...

   add        : 마지막 필터가 꽉 찼으면 새 필터를 잇고 거기에 넣는다
   mightContain : 필터를 전부 물어보고 하나라도 true 면 true

 "늘리는 게 아니라 잇는다"
   기존 필터는 절대 안 건드린다 -> 이미 넣은 원소의 자리가 안 바뀐다
   -> 6번의 '다시 배치할 수 없다' 문제를 우회한다
```

**왜 용량을 2배로 키우는가**

```
 이유 1 : 필터 개수를 로그로 묶기 위해

   용량이 n, 2n, 4n, 8n, ... 으로 커지면
   원소 N 개를 담는 데 필요한 필터 수는 약 log2(N/n + 1) 개다

   실제 숫자 (테스트 capacityDoubles)
     100 + 200 + 400 + 800 + 1600 = 3100 까지 필터 5개
     그 다음 원소 하나만 더 들어와도 6개가 된다

   테스트 lookupCostsGrow
     초기 100 에 10만 개를 넣으면 필터가 9~12개
     -> 원소는 1000배인데 필터는 10개쯤이다

 이유 2 : mightContain 이 필터 수에 비례하므로
          필터 수를 선형으로 늘리면 조회가 선형으로 느려진다
          2배씩 키워야 조회 비용이 로그로 묶인다
```

**왜 오탐률을 절반으로 조이는가**

```
 mightContain 은 '하나라도 true 면 true' 다
   -> 필터가 늘어날수록 오탐이 날 기회도 늘어난다
   -> 필터마다 p 를 그대로 두면 전체 오탐률이 계속 올라가 1 에 수렴한다

     전부 p 라면 : 1 - (1-p)^t     (t = 필터 수)
     t 가 커지면 1 로 간다.  유계가 아니다

 그래서 새 필터일수록 더 엄격하게 만든다

     필터 i 의 오탐률 = p / 2^i

   그러면 뒤에 붙는 필터가 기여하는 오탐이 기하급수적으로 작아져
   전체가 수렴한다

 대가 : 오탐률을 조이면 비트가 더 든다
   m = -n ln(p)/(ln2)^2 에서 p 가 절반이 되면 m 은 약 n x ln2 만큼 늘어난다
   -> 용량도 2배가 되므로 필터 i 의 비트 수는 대략 2^i 에 비례해 커진다
   (원본에 근거 없음 -- 내 추론)
```

**왜 2p 를 넘지 않는가**

```
 전체 오탐률 = 1 - (전부 false 라고 할 확률)
             = 1 - (1-p)(1-p/2)(1-p/4)(1-p/8)...

 상한 증명 (합집합 상한, union bound)

   "어느 필터든 하나라도 오탐" 의 확률 <= 각 필터의 오탐 확률의 합

       1 - prod(1 - p/2^i)  <=  sum(p/2^i)
                             =  p x (1 + 1/2 + 1/4 + 1/8 + ...)
                             =  p x 2
                             =  2p

   여기서 쓰인 것이 등비급수의 합 :  1 + 1/2 + 1/4 + ... = 1/(1 - 1/2) = 2

   -> 필터를 무한히 이어도 전체 오탐률은 2p 를 절대 못 넘는다.  유계다
```

> **합집합 상한(union bound)** — 여러 사건 중 하나라도 일어날 확률은 각 확률의 합을 넘지 않는다는 부등식.\
> 예: 필터 t개 중 하나라도 오탐일 확률 ≤ 각 필터 오탐률의 합 — 이 합이 등비급수라 2p로 수렴한다.

> **등비급수(geometric series)** — 항이 일정 비율로 줄어드는 급수. 비율이 1보다 작으면 유한한 값에 수렴한다.\
> 예: `1 + 1/2 + 1/4 + …` 는 무한히 더해도 2를 넘지 않는다 — 조이는 비율 0.5가 이 성질을 쓴다.

```java
@Test
@DisplayName("필터가 늘어도 예상 오탐률이 2p 를 안 넘는다")
void staysUnderTwiceTarget() {
    ScalableBloomFilter<Integer> f = scalable(100, 0.01);
    for (int i = 0; i < 50_000; i++) {
        f.add(i);
    }
    assertTrue(f.filterCount() >= 8, "필터가 " + f.filterCount() + "개 생겼다");
    double rate = f.expectedFalsePositiveRate();
    assertTrue(rate < 0.021,
            "예상 오탐률 " + rate + " 가 2p=0.02 를 넘었다. 오탐률을 안 조인 것이다");
}
```

**확률은 더하는 것이 아니라 곱으로 구한다**

```java
@Override
public double expectedFalsePositiveRate() {
    double allMiss = 1.0;
    for (BloomFilter<T> f : filters) {
        allMiss *= (1 - f.expectedFalsePositiveRate());   // 전부 빗나갈 확률
    }
    return 1 - allMiss;                                   // 그 여집합
}
```

```java
@Test
@DisplayName("확률은 더하는 것이 아니라 곱으로 구한다")
void notASum() {
    // 필터 둘의 예상 오탐률이 각각 약 0.498, 0.249 다.
    // 더하면 0.748, "둘 다 빗나갈 확률의 여집합"으로 구하면 0.623 이다.
    // 확률을 더하면 1 을 넘을 수도 있다. 애초에 틀린 계산이다.
    ScalableBloomFilter<Integer> f = scalable(100, 0.5);
    for (int i = 0; i < 300; i++) {
        f.add(i);
    }
    assertEquals(2, f.filterCount());
    double r = f.expectedFalsePositiveRate();
    assertTrue(r > 0.60 && r < 0.65,
            "예상 오탐률 " + r + " - 0.623 근처여야 한다. 0.75 근처면 더한 것이다");
}
```

```
 계산 확인

   필터 0 : 용량 100, p=0.5   -> 100개 담김 -> 예상 오탐률 약 0.498
   필터 1 : 용량 200, p=0.25  -> 200개 담김 -> 예상 오탐률 약 0.249

   더하면       : 0.498 + 0.249 = 0.747        <- 틀린 계산
   곱으로 구하면 : 1 - (1-0.498)(1-0.249)
                = 1 - 0.502 x 0.751
                = 1 - 0.377
                = 0.623                        <- 맞는 계산

 왜 더하면 안 되는가
   "둘 다 오탐" 인 경우를 두 번 세기 때문이다 (포함-배제)
   그래서 확률을 더하면 1 을 넘을 수도 있다 -- 확률이 아니게 된다

   앞의 2p 상한은 '상한'으로만 쓰는 것이지 실제 값이 아니다
   (상한은 더해서 구하고, 실제 값은 곱으로 구한다)
```

- 논리: `neverExceedsOne` 테스트가 2만 번 넣으며 매번 `0 <= r <= 1` 을 확인한다 — 더하기로 구현하면 여기서 걸린다.

**대가 — `mightContain` 비용**

```java
@Test
@DisplayName("조회가 필터 수만큼 든다")
void lookupCostsGrow() {
    ScalableBloomFilter<Integer> f = scalable(100, 0.01);
    for (int i = 0; i < 100_000; i++) {
        f.add(i);
    }
    // 100 * 2^k 의 합이 10만을 넘는 지점 - 10개 정도
    assertTrue(f.filterCount() >= 9 && f.filterCount() <= 12,
            "필터 " + f.filterCount() + "개. 원소 수의 로그로 는다");
}
```

```
 기본형    : mightContain 이 k 번 비트 검사 -> O(k), 상수
 Scalable : 필터 t 개를 전부 물어본다      -> O(t x k)

   t = O(log(N/n0))  이므로  O(k log N)

 게다가 '없는 것'을 물을 때가 가장 비싸다
   하나라도 true 면 즉시 반환하지만, false 는 t 개를 전부 확인해야 나온다
   -> 앞단 필터의 주 용도(없는 것 거르기)가 정확히 최악 경로다
   (원본에 근거 없음 -- 내 추론)

 그 외의 대가
   - 메모리도 필터를 이어 붙이는 만큼 늘어난다 (bitSize 가 전부의 합이다)
   - 삭제는 여전히 불가능하다
   - add 가 마지막 필터에만 넣으므로 '중복 삽입'을 걸러내지 못한다
     같은 원소를 두 필터가 각각 담을 수 있다 (insertedCount 는 add 횟수다)
     (원본에 근거 없음 -- 내 추론)
```

**과부하에서 셋을 비교하면**

```java
@Test
@DisplayName("실측 오탐률도 유계 안에 있다")
void measuredStaysBounded() {
    ScalableBloomFilter<Integer> f = scalable(1000, 0.01);
    for (int i = 0; i < 100_000; i++) {      // 100배 과부하
        f.add(i);
    }
    // ... 누락 0 확인 ...
    double measured = fp / 100_000.0;
    assertTrue(measured < 0.03,
            "실측 오탐률 " + measured + " - 100배 과부하인데도 3% 안이어야 한다");
}
```

```
 같은 조건(초기 용량 1000, p=0.01, 원소 10만 개 = 100배 과부하)

   BloomFilter      실측 오탐률 > 90%    (plainFilterCollapses)
   ScalableBloom    실측 오탐률 <  3%    (measuredStaysBounded)

 이 대비가 ScalableBloomFilter 의 존재 이유다 (테스트 주석: "대비가 이 클래스의 존재 이유다")
```

**세 구현 중 언제 무엇을 고르는가**

| | 고르는 조건 | 얻는 것 | 치르는 것 |
|---|---|---|---|
| `BloomFilter` | 원소 수를 알고, 삭제가 필요 없을 때 | 가장 작은 메모리 · 상수 시간 조회 | 용량 고정(넘기면 복구 불가) · 삭제 불가 |
| `CountingBloomFilter` | **삭제가 꼭 필요할 때** | `remove` | 메모리 8배 · 포화 자리 영구 오탐 · **누락 없음 보장 상실** |
| `ScalableBloomFilter` | **원소 수를 모를 때**(스트림·계속 자람) | 오탐률이 2p로 유계 | 조회가 필터 수(로그)에 비례 · 메모리 증가 · 삭제 불가 |

- 논리: 세 가지가 **서로 다른 문제를 푼다** — 하나가 다른 것의 상위 호환이 아니다.\
  `Counting` 은 삭제를, `Scalable` 은 용량 불확실성을 푼다.
- 논리: 둘 다 필요하면(삭제 + 가변 용량) 둘을 합쳐야 하는데, 원본에는 그런 구현이 없다.\
  (원본에 근거 없음 — 내 추론)
- 논리: **기본값은 `BloomFilter`** 다 — 원소 수를 알 수 있으면 넉넉히 잡고 기본형을 쓰는 것이 가장 싸다(6번의 "최선의 경우").

**질문별 답**

- Q: 왜 새 필터일수록 용량은 2배로 키우면서 오탐률은 절반으로 조이는가?\
  A: 용량을 2배로 키우는 것은 **필터 개수를 로그로 묶기** 위해서다 — `mightContain` 이 필터 수에 비례하므로 선형으로 늘리면 조회가 선형으로 느려진다.\
  오탐률을 절반으로 조이는 것은 `mightContain` 이 "하나라도 true면 true"라 **필터가 늘수록 오탐 기회도 늘기** 때문이다.\
  전부 같은 `p` 로 두면 전체 오탐률이 1로 수렴해 유계가 아니게 된다.

- Q: `1 - (1-p)(1-p/2)(1-p/4)...` 가 왜 2p를 넘지 않는가?\
  A: 합집합 상한으로 `1 - ∏(1 - p/2^i) ≤ Σ p/2^i` 인데, 이 합이 **등비급수** `p(1 + 1/2 + 1/4 + …) = 2p` 이기 때문이다.\
  조이는 비율이 0.5라 급수가 수렴하고, 그래서 필터를 무한히 이어도 전체 오탐률이 2p 아래로 유계다.\
  (단 실제 값은 더하기가 아니라 **"전부 빗나갈 확률의 여집합"으로 곱해서** 구해야 한다 — 더하면 1을 넘을 수도 있어 확률이 아니게 된다.)

- Q: 그 대가로 `mightContain` 비용은 어떻게 되는가?\
  A: 기본형의 O(k) 상수에서 **O(k × 필터 수) = O(k log N)** 이 된다.\
  게다가 `false` 를 내려면 필터를 전부 확인해야 해서, 앞단 필터의 주 용도인 "없는 것 거르기"가 정확히 최악 경로다(내 추론).\
  메모리도 이어 붙인 만큼 늘고 삭제는 여전히 안 된다.

- Q: 세 구현 중 언제 무엇을 고르는가?\
  A: **기본값은 `BloomFilter`** — 원소 수를 알고 삭제가 필요 없으면 가장 작고 빠르다(용량을 넉넉히 잡는 것이 안전하다).\
  **삭제가 꼭 필요하면 `CountingBloomFilter`** — 메모리 8배와 "누락 없음 보장 상실"을 감수할 수 있을 때만이다.\
  **원소 수를 모르면 `ScalableBloomFilter`** — 오탐률이 2p로 유계이지만 조회가 필터 수에 비례한다.\
  셋은 서로 다른 문제를 푸는 것이지 상위 호환 관계가 아니다.

#### 9. 12-skip-list 로의 연결 — 확률에 기대는 자료구조

**질문**: 여기서 처음 만난 "확률에 기대는 자료구조"가 다음 챕터에서 어떤 모양으로 다시 나오는가. 06-tree 의 BST 가 정렬 입력에서 무너진 문제를 회전 없이 확률로 푼다는 것은 무슨 뜻이고, 무작위를 **주입받게** 만드는 규칙이 성능·재현성만이 아니라 검증 가능성까지 바꾼다는 말(5번 질문과 이어진다)은 무엇인가.

**확률이 두 챕터에서 맡는 역할이 다르다**

```
 11-bloom-filter
     확률이 '답' 에 들어간다
        mightContain 의 true 가 확률적으로 틀린다
        -> 정확성을 판다
        -> 대가로 메모리를 얻는다

 12-skip-list
     확률이 '구조' 에 들어간다
        어떤 노드를 몇 층까지 올릴지를 동전 던지기로 정한다
        -> 답은 100% 정확하다 (있으면 있다고 하고 없으면 없다고 한다)
        -> 확률적인 것은 '성능' 이다 (기대값 O(log n), 최악은 O(n))

 즉 같은 '확률에 기댄다'인데
     11 : 정확성이 확률적
     12 : 성능이 확률적
```

> **기대 시간(expected time)** — 무작위 선택에 대한 평균 비용. 최악 시간과 다르다.\
> 예: 스킵 리스트의 탐색은 기대 O(log n)이고 최악은 O(n)이지만, 최악이 나올 확률이 극히 낮다.

**BST가 정렬 입력에서 무너진 문제**

```
 06-binary-search-tree

   1, 2, 3, 4, 5 를 순서대로 넣으면

        1
         \
          2
           \
            3
             \
              4
               \
                5

   높이가 n 이다. 사실상 연결 리스트다 -> 탐색이 O(n)
   -> "정렬된 데이터를 넣는 것"은 아주 흔한 일인데 거기서 최악이 난다

 기존 해법 : 회전(rotation)으로 다시 균형을 잡는다
   AVL, 레드-블랙 트리
   -> 삽입/삭제마다 균형 조건을 확인하고 회전 규칙을 적용한다
   -> 경우의 수가 많고(LL, LR, RL, RR / 여러 색 조합) 구현이 길고 까다롭다
   -> 16번 red-black-tree 가 그것을 다룬다
```

**스킵 리스트가 회전 없이 푸는 방법**

```
 정렬된 연결 리스트에 '고속도로 층' 을 얹는다

   층 3:  head ------------------------------> 9
   층 2:  head --------> 4 -----------------> 9
   층 1:  head --> 2 --> 4 --------> 7 -----> 9
   층 0:  head --> 2 --> 3 --> 4 --> 7 --> 8 --> 9      (전부 있는 층)

   탐색 : 위층에서 크게 건너뛰다가, 지나치면 한 층 내려간다
   -> 매 층에서 구간이 절반쯤으로 줄어든다 -> 기대 O(log n)

 몇 층까지 올릴지를 어떻게 정하나?
   동전을 던진다. 앞면이면 한 층 더 올리고, 뒷면이면 멈춘다
   -> 원소의 절반이 층 1, 그 절반이 층 2, ... 로 자연스럽게 배분된다

 왜 정렬 입력에 안 무너지나
   층 높이가 '입력 순서' 나 '키 값' 과 무관하게 정해지기 때문이다
   1,2,3,...,n 을 순서대로 넣어도 층 분포는 똑같이 기하분포다
   -> BST 처럼 '입력이 구조를 결정하는' 고리가 끊긴다

 대가
   최악은 여전히 O(n) 이다 (동전이 계속 뒷면만 나오면)
   그러나 그 확률이 극히 작아서 실용상 문제가 안 된다
   회전 로직이 통째로 사라진다 -> 구현이 훨씬 짧다
```

- 논리: **"입력이 구조를 결정하는 고리를 끊는다"** 가 핵심이다.\
  BST의 최악은 "적대적 입력"에서 나오는데, 구조를 무작위로 정하면 입력이 최악을 만들 수 없다.
- 논리: 같은 발상이 퀵소트의 랜덤 피벗, 해시의 랜덤 시드(해시 DoS 방어)에도 쓰인다.\
  (원본에 근거 없음 — 내 추론)

**무작위를 주입받게 만드는 규칙**

```
 나쁜 설계 : 클래스 안에서 new Random() 을 한다

     class SkipList<E> {
         private final Random rnd = new Random();    // 안에서 만든다
         ...
     }

   문제
     - 실행할 때마다 구조가 달라진다 -> 버그 재현이 안 된다
     - 특정 층 구조를 만들어 테스트할 방법이 없다
     - "층이 5까지 올라간 경우"를 검사하고 싶어도 강제할 수 없다

 좋은 설계 : 밖에서 주입받는다

     class SkipList<E> {
         private final Random rnd;
         SkipList(Random rnd) { this.rnd = rnd; }    // 밖에서 받는다
         ...
     }

   얻는 것 셋

   (1) 재현성 : new Random(42L) 을 넘기면 언제나 같은 구조가 나온다
                실패한 테스트를 그대로 다시 돌릴 수 있다

   (2) 성능 제어 : 실제 운영에서는 좋은 난수원을, 테스트에서는 고정 시드를 쓸 수 있다

   (3) 검증 가능성 : 원하는 동전 결과를 '고를 수 있다'
                     - 항상 앞면인 가짜 Random 을 넘기면 -> 모든 원소가 최고층까지
                     - 항상 뒷면이면 -> 전부 층 0 (= 연결 리스트, 최악의 경우)
                     -> 최악 경로를 '실제로 실행해' 검증할 수 있다
```

**5번 질문과 어떻게 이어지는가**

```
 11번의 h2 == 0 방어선

   해시 입력 = item 하나뿐
   -> 테스트가 h2 를 통제할 수 없다
   -> 방어선이 있는지 없는지 테스트로 구분할 수 없다

 19번의 같은 방어선

   해시 입력 = (item, seed)
   -> 테스트가 seed 를 고른다
   -> h2 == 0 이 되는 짝을 구성할 수 있다 -> 방어선이 검증된다

 12번의 층 높이

   층 높이의 입력 = 주입받은 Random
   -> 테스트가 Random 을 고른다
   -> 원하는 층 구조를 구성할 수 있다 -> 최악 경로를 검증할 수 있다

 셋이 같은 이야기다

   "무작위(또는 파라미터)를 밖에서 주입받게 만든다"
     = 테스트가 통제할 수 있는 축을 하나 더 준다
     = 검증 가능성이 올라간다

   그리고 이것은 테스트를 잘 쓰는 기술이 아니라
   대상 코드의 '설계 결정' 이다  (5번의 결론)
```

- 논리: 07번에서 `Comparator` 를 주입받은 것, 08번에서 `Graph` 인터페이스로 구현을 갈아 끼운 것, 10번에서 `ThreadSafeLRUCache` 가 `Cache` 를 감싼 것이 전부 **같은 기법**이다.\
  주입 대상이 비교자·구현·난수원으로 바뀔 뿐이다.
- 논리: 이 문제집이 12번에서 그 규칙을 처음 명시하고, 11번에서 **그 규칙이 없을 때 무슨 일이 생기는지**를 먼저 겪게 한 셈이다.\
  순서가 거꾸로인 것처럼 보이지만, 결핍을 먼저 겪어야 규칙의 값을 안다.

**질문별 답**

- Q: "확률에 기대는 자료구조"가 다음 챕터에서 어떤 모양으로 다시 나오는가?\
  A: 확률이 맡는 **자리가 바뀐다**.\
  11번은 확률이 **답**에 들어가 `mightContain` 의 `true` 가 확률적으로 틀리고(정확성을 판다), 12번은 확률이 **구조**에 들어가 답은 100% 정확한데 **성능**이 확률적이다(기대 O(log n), 최악 O(n)).

- Q: BST가 정렬 입력에서 무너진 문제를 회전 없이 확률로 푼다는 것은?\
  A: BST는 트리 모양이 **입력 순서로 결정**되어 정렬된 입력에서 높이가 n이 되고, AVL·레드블랙은 회전이라는 복잡한 재균형 장치로 그것을 고쳤다.\
  스킵 리스트는 각 원소를 몇 층까지 올릴지를 **동전 던지기로** 정해, 층 분포가 입력 순서·키 값과 무관해진다 — **입력이 구조를 결정하는 고리를 끊는** 것이다.\
  그러면 정렬된 입력을 넣어도 기대 높이가 `log n` 이라 회전 로직이 통째로 필요 없어진다(최악은 여전히 O(n)이지만 확률이 극히 낮다).

- Q: 무작위를 주입받게 만드는 규칙이 검증 가능성까지 바꾼다는 말은?\
  A: 클래스 안에서 `new Random()` 을 하면 테스트가 동전 결과를 통제할 수 없어 **원하는 구조를 만들 수 없고**, 실패도 재현할 수 없다.\
  밖에서 주입받으면 고정 시드로 재현할 수 있고, 항상 앞면/항상 뒷면인 가짜 난수원을 넘겨 **최악 경로를 실제로 실행해** 검증할 수 있다.\
  이것이 5번과 같은 이야기다 — 11번은 해시 입력이 원소 하나뿐이라 `h2 == 0` 방어선을 검증할 수 없었고, 19번은 seed를 주입받아 검증할 수 있게 된다.\
  즉 검증 가능성은 테스트를 잘 쓰는 기술이 아니라 **코드가 테스트에게 어떤 손잡이를 주는가**라는 설계 결정이 정한다.

**더 생각할 것**

- 이 챕터의 모든 성질이 **"원소를 저장하지 않는다"** 한 줄에서 나온다.\
  메모리가 원소 크기와 무관한 것도, 꺼낼 수 없는 것도, 오탐이 생기는 것도, 과부하를 복구할 수 없는 것도 전부 같은 결정의 결과다.
- 세 챕터 연속으로 **같은 타입 함정**이 나왔다.\
  07번 `MedianFinder` 의 `/ 2` vs `/ 2.0`, 10번 `hitRatio` 의 `(double)` 캐스팅, 11번 `optimalHashCount` 의 `(double) m / n`.\
  전부 정수 나눗셈이고, 전부 컴파일 에러 없이 조용히 틀린다.
- "테스트로 못 잡는 방어선"을 남겨 두는 판단이 이 챕터의 가장 실무적인 대목이다.\
  커버리지로 보면 죽은 코드지만, 해시 함수나 원소 타입이 바뀌면 살아나는 방어선이다 — **검증할 수 없다고 필요 없는 것이 아니다.**
