## 질문

1. 문제 1(서로 다른 부분 문자열 개수)을 어떻게 푸는가 — `n(n+1)/2 - sum(lcp)` 에서 왜 하필 `sum(lcp)` 가 중복해서 센 양인가(정렬해 두면 겹치는 상대가 바로 앞 하나뿐인 이유). 09번의 트라이 방식과 비교해 무엇이 달라졌는가. `long` 으로 계산해야 하는 이유는.
2. 문제 2(가장 긴 반복 부분 문자열)를 어떻게 푸는가 — 두 번 나오는 부분 문자열이 왜 "접미사 두 개의 공통 접두사"인가. 가장 많이 겹치는 두 접미사가 **반드시 이웃**인 이유는(그래서 이웃만 보는 lcp 로 충분한 이유). 동률일 때 사전순 앞선 답이 자연히 나오는 이유는. 비용은.
3. 문제 3(두 문자열의 가장 긴 공통 부분 문자열)을 어떻게 푸는가 — 구분자를 안 끼우면 왜 답이 조용히 틀리는가(a="a", b="aa" 예시). 구분자가 유일해야 하는 이유는. 이웃 쌍 중 "서로 다른 쪽에서 온 것"을 어떻게 가려내는가. 비용은.
4. 접미사 배열이 왜 필요한가 — 09번에서 모든 접미사를 트라이에 넣으면 노드가 O(n^2) 인 것이 길이 10만에서 무엇을 뜻하는가. 접미사를 **저장하지 않고 시작 위치 숫자만** 남기는 것이 O(n) 공간의 정체인 이유는.
5. 이 구조가 무엇을 대가로 치르는가 — "직관을 버린다"는 말의 뜻은. 트라이의 O(m) 검색이 여기서 O(m log n) 이 되는 구조적 이유는(트라이는 한 글자에 한 걸음, 배열은 log n 번 찔러본다).
6. 배가법이 재활용하는 것은 무엇인가 — "순위가 이미 k 글자를 요약하고 있다"가 왜 정렬을 log n 번으로 줄이고 비교를 상수로 만드는가. 나이브 정렬과 비교해 `ab` 를 1000번 반복한 입력에서 비용이 어떻게 갈리는가.
7. `reRank` 가 왜 이 문제의 핵심인가 — 정렬한 뒤 같은 쌍끼리 같은 순위로 묶지 않으면 무엇이 깨지는가. `comparePair` 에서 범위 밖을 0 이 아니라 **-1** 로 봐야 하는 이유는(`a` 가 `ab` 보다 앞인 이유).
8. Kasai 가 O(n) 인 이유는 훑는 **순서**에 있다 — 순위 순서가 아니라 원문 순서로 가는 것이 왜 상각으로 O(n) 을 만드는가. 같은 글자 2000개에서 결과값의 합은 1,999,000 인데 훑는 글자가 1,999 인 것을 설명해 보라. 매번 0부터 세게 바꾸면 답과 비용이 각각 어떻게 되는가.
9. 검색이 이진 탐색 **두 번**인 이유는. 찾은 위치를 그대로 주면 안 되는 이유는(banana 에서 `a` 를 찾으면 5, 3, 1 순으로 나오는 것).
10. 최악의 사용 패턴을 만들어 보라 — 문자열이 자주 바뀌면 이 구조는 왜 맞지 않는가. `int[]` 를 Comparator 로 정렬할 수 없어 `Integer[]` 로 박싱하는 상수 비용은 어디에 붙는가. 반대로 최선은 언제인가.
11. 구현 전략의 트레이드오프 — NaiveSuffixArray(다섯 줄, 답도 맞다) · 배가법 O(n log^2 n) · 기수 정렬 O(n log n) · SA-IS O(n) 은 각각 무엇을 맞바꾸는가. 검색을 O(m) 으로 되돌리려면 무엇이 더 필요한가.
12. "테스트가 구별하지 못하는 코드"가 여기서 셋 나온다(Kasai 의 `h = 0` 되돌리기 · `reRank` 의 `< 0` 대 `!= 0` · 문제 3의 구분자 접미사 거르기). 11번 · 16번 · 18번 · 20번에 이은 같은 계열이다 — 불변식을 지키는 코드가 여럿일 때 무엇이 일어나는가. 종료 조건을 `k >= n` 으로 바꿔도 답이 같은 것은 무엇을 뜻하는가.
13. 다음 구조로의 연결 — 여기까지는 "미리 만들어 두고 조회를 빠르게" 했다. 22번 스파스 테이블은 **갱신을 아예 포기하는 대신 조회를 O(1)** 로 만든다. 13번 세그먼트 트리가 갱신을 위해 O(log n) 조회를 받아들인 것과 어떻게 정반대인가.
