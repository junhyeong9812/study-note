# data-structure/19-lsm-merge-model — 정답

## 정답

### 1. 병합 정책과 세 증폭

- 같은 데이터·같은 엔진이라도 언제·무엇을·몇 개씩 합치느냐에 따라 디스크 쓰기, 조회 비용, 디스크 사용량이 몇 배씩 달라진다.
- 쓰기 증폭 = 저장 장치에 쓴 바이트 ÷ 사용자가 쓴 바이트. 읽기 증폭 = 조회 하나에 읽는 run·블록 수. 공간 증폭 = 디스크 크기 ÷ 살아 있는 데이터 크기.
- 한 줄: 자주 합치면(쓰기 비용) run이 적고 옛 버전이 빨리 사라져 읽기·공간이 싸지고, 덜 합치면 반대다.

### 2. 레벨 vs 티어 그림

```text
  레벨:  Level i  [■■■■■■■■] run 하나 ← 내려온 run과 기존 run을 합쳐 다시 씀
  티어:  Level i  [■■] [■■] [■■] run 여러 개 ← T개가 차면 그것들끼리 합쳐 다음 레벨에 run으로 추가
```

- 레벨당 하나인 것은 **sorted run**이다. RocksDB L1 이상은 키 범위로 나뉜 SST 파일 여러 개가 run 하나를 이루고, L0는 겹치는 파일 여러 개다(wiki Leveled Compaction).

### 3. 비용 모델 (Dostoevsky 그림 3·4)

| | 레벨 | 티어 |
|---|---|---|
| 엔트리당 쓰기 I/O | O(T·L / B) | O(L / B) |
| 점 조회 최대 run 수 | L | (T−1)·L |
| 최악 공간 증폭(추가분) | O(1/T)(가장 큰 레벨이 차 있거나 용량을 동적으로 맞출 때) | O(T) |

- 레벨에서 한 엔트리는 레벨이 찰 때까지 평균 T/2번 다시 병합된다(논문 "on average T/2, or O(T), times per level").

### 4. 시뮬레이션 예측

- T=10, 새 키만: 레벨 WA 13.24·run 3개, 티어 WA 2.80·run 7개(실험).
- 덮어쓰기(키 10만 개에 100만 번): 공간 증폭 티어 3.47(T=10)·4.37(T=4), 레벨 1.33·1.71. 티어가 옛 버전을 여러 run에 오래 둔다.
- 단순 모델(레벨 전체 병합, 블룸 필터·삭제 없음)의 값이라 실제 엔진 설정으로 옮기면 안 된다.

### 5. T의 양 끝

- T=2: 레벨 수가 같고 두 번째 run이 오면 바로 병합하므로 두 정책의 동작이 같아진다(논문). 같은 단순 모델에서는 12.09 vs 7.12로 가장 가까웠지만 모델 차이로 같지는 않았다.
- T=T_lim: 레벨은 정렬된 배열 하나(쓰기마다 전체 재작성), 티어는 병합 없는 로그(조회는 전부 훑기)로 퇴화한다.

### 6. 하이브리드

- RocksDB 기본 Level compaction은 L0가 겹치는 run 여러 개(티어), L1부터 레벨마다 run 하나(레벨)라서 Tiered+Leveled다. wiki: 레벨보다 쓰기 증폭이, 티어보다 공간 증폭이 작다.
- lazy leveling: 가장 큰 레벨만 레벨, 나머지는 티어. 쓰기를 O((T+L)/B)로 줄이면서 점 조회·긴 범위 조회·공간 증폭 상한은 레벨과 같게 둔다. 점 조회는 레벨별 블룸 필터 오탐률을 최적 배분했을 때의 기대 I/O 기준이다(블룸 필터 없이는 작은 레벨마다 run을 최대 T−1개 본다). 공간과 긴 범위 조회 비용이 가장 큰 레벨에서 나오기 때문이다.

### 7. 워크로드별 선택

- (a) 쓰기 위주, 최근 위주 조회, TTL → 시간 창(TWCS)이나 FIFO·티어. TTL로 오래된 파일을 통째로 버릴 수 있으면 다시 쓰기가 거의 없다.
- (b) 갱신 많고 점 조회 p99 중요 → 레벨(LCS·Level). run이 적고 옛 버전이 빨리 정리된다. 블룸 필터 비트도 넉넉히.
- (c) 디스크 작고 덮어쓰기 많음 → 레벨. 티어는 공간 증폭이 O(T)까지 가고 큰 병합 때 일시적으로 2배 공간이 든다.

### 8. 쓰기 증폭 폭증 진단

- 잴 것: `iostat` 쓰기 MB/s ÷ 앱 쓰기 MB/s, RocksDB `rocksdb.stats`의 Compaction Stats 레벨별 W-Amp, compaction 대기 바이트·write stall 로그(database/38).
- 원인: 쓰기 위주 워크로드에 레벨 방식 — 엔트리당 O(T·L)번 다시 쓴다(시뮬레이션에서 티어의 2.3~4.7배).
- 대처: 티어·하이브리드로, memtable을 키워 레벨 수를 줄이고, 시간 순 + TTL이면 TWCS·FIFO. 배경 compaction 스레드·대역폭도 확인한다.

### 9. 병합 중 디스크 포화

- 티어(Universal·STCS)에서 더 잘 생긴다. 가장 큰 run들을 통째로 합치는 동안 입력과 출력이 동시에 있어 일시적으로 2배까지 든다(RocksDB Tuning Guide — Universal). 레벨은 파일 단위로 조금씩 합쳐 순간 필요 공간이 작다.
- 디스크 여유는 평소 사용량이 아니라 **가장 큰 병합이 진행 중일 때의 최대**를 기준으로 잡는다. 데이터를 여러 인스턴스로 나눠 한 번의 병합 크기를 줄이는 것도 방법이다.

### 10. FTL과의 비교

- 같은 점: 제자리 덮어쓰기를 피하고 새 위치에 쓰며, 무효가 된 옛 데이터를 나중에 모아 정리한다(compaction ↔ 가비지 컬렉션). 둘 다 그 정리 때문에 쓰기 증폭이 생긴다.
- 다른 점: FTL은 논리 페이지 → 물리 페이지 주소 변환과 "블록 단위로만 지울 수 있다"는 장치 제약을 다룬다. 키 정렬·머지 소트·조회 경로 같은 LSM의 핵심은 없다. 그래서 "정확히 같다"는 과장이고, "같은 발상의 다른 층"이 맞다. 해석: 장치까지 보면 두 층의 쓰기 증폭이 곱해진다(LSM WA × 장치 WA).
