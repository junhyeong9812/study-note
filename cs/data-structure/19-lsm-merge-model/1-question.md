# data-structure/19-lsm-merge-model — 질문

## 질문

1. (왜) LSM에서 병합 정책을 따로 고민해야 하는 이유는? 쓰기·읽기·공간 증폭을 각각 정의하고, 셋을 동시에 최소로 만들 수 없는 이유를 한 줄로 말하라.
2. (그림) 레벨 방식과 티어 방식에서 한 레벨이 어떤 모양인지, 위 레벨에서 run이 내려올 때 무엇을 합치는지 그려라. "레벨당 파일 1개"라는 설명은 어디가 부정확한가?
3. (계산) Dostoevsky의 비용 모델로 레벨과 티어의 엔트리당 쓰기 비용, 점 조회 시 최대 run 수(블룸 필터 없음), 최악 공간 증폭을 T·L로 비교하라. 레벨에서 한 엔트리가 레벨당 평균 몇 번 다시 쓰이나?
4. (예측) 단순 시뮬레이션(쓰기 100만, 버퍼 4,000, T=10, 새 키만)에서 레벨과 티어의 쓰기 증폭과 run 수는 대략 어떻게 나올까? 키 10만 개에 100만 번 덮어쓰면 공간 증폭은 어느 쪽이 커지나?
5. (경계) 크기 비율 T를 2로 줄이면 두 정책은 어떻게 되나? T를 T_lim(레벨 1개)까지 키우면 각각 무엇으로 퇴화하나?
6. (연결) RocksDB의 기본 Level compaction을 wiki가 "Tiered+Leveled"로 부르는 이유는? Dostoevsky의 lazy leveling은 무엇을 어디에 적용하나?
7. (적용) 다음 워크로드에 어떤 정책을 고르겠나? 이유와 함께. (a) 초당 수십만 건 로그 수집, 조회는 최근 1시간 위주, 7일 TTL (b) 사용자별 카운터를 초당 수만 번 갱신, 점 조회 p99가 중요 (c) 디스크가 작고 덮어쓰기가 많은 설정 저장소
8. (장애 진단) 수집 서버의 SSD 쓰기량이 앱 쓰기량의 수십 배이고 피크 때 쓰기가 멈춘다. 무엇을 재서 원인을 확인하고 어떻게 대처하나?
9. (장애 진단) 평소 디스크 50%인 노드가 compaction 중 디스크가 꽉 차 쓰기가 실패했다. 어느 정책에서 더 잘 생기고, 왜인가? 디스크 여유는 무엇을 기준으로 잡아야 하나?
10. (경계) 원본 노트는 "append-only + 불변이라는 발상은 SSD 내부 FTL과 정확히 같다"고 적었다. 무엇이 같고 무엇이 다른가?
