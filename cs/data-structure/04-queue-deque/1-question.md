## 질문

### A. 문제

1. 문제 1(회문 판별 — `isPalindrome`)을 어떻게 푸는가. 왜 큐로는 안 되고 데크여야 하는가, 원소가 하나 남았을 때 경계는 어떻게 처리하는가.
2. 문제 2(슬라이딩 윈도우 최댓값 — `slidingWindowMax`)를 어떻게 푸는가. 창마다 k 개를 훑는 풀이가 왜 O(n·k)이고, 데크에 "후보 인덱스"만 내림차순으로 남기면 왜 O(n)이 되는가(각 인덱스가 몇 번 들어가고 몇 번 나오는가).
3. 문제 3(스트림에서 처음으로 한 번만 나온 문자 — `firstUniqueStream`)을 어떻게 푸는가. 큐에 무엇을 담고, 앞의 문자가 이미 두 번 나왔을 때 무엇을 하는가. 이 문제가 `Deque` 가 아니라 `Queue` 만 받는다는 사실이 알려주는 것은 무엇인가.
4. 문제 4(k 칸 오른쪽으로 회전 — `rotate`)를 데크에서는 어떻게 푸는가. 01번(세 번 뒤집기)·02번(링크 재연결)과 무엇이 다른가. k 가 아주 클 때 비용을 어떻게 줄이는가.

### B. 자료구조 특성

5. 큐(FIFO)가 왜 필요한가. 03-stack(LIFO)으로는 무엇이 안 되는가 — "먼저 온 것이 먼저 나가야 하는" 문제를 스택으로 흉내내면 무슨 대가를 치르는가.
6. 어떤 형태의 데이터·접근 패턴에 큐/데크가 적합하고, 언제 쓰면 안 되는가. 접근 지점을 양 끝으로 제한한 대신 무엇을 포기했는가(인덱스 임의 접근, 중간 삽입·삭제, 탐색).
7. `enqueue`/`dequeue` 가 O(1)인 구조적 이유는 무엇인가. 원형 배열에서 `(head + i) % capacity` 한 줄이 무엇을 대신해 주는가, 연결 구현에서는 그 자리에 무엇이 오는가.
8. `ArrayQueue` 는 `Queue` 계약을 전부 지키고 테스트도 대부분 통과한다. 그런데 왜 "문제가 있다"고 하는가 — `ArrayQueueTest.wastesSpace` 와 `CircularQueueTest.reusesSpace` 가 같은 시나리오에서 용량 2048 과 4 로 갈리는 이유는 무엇인가. `dequeue` 로 비운 앞쪽 칸을 왜 되쓸 수 없는가.
9. `tail` 인덱스를 두지 않고 `head` + `size` 로 표현하는 이유는 무엇인가. `head == tail` 이 왜 모호한가, 한 칸 비워두기나 플래그 방식과 비교하면 무엇을 얻는가.
10. 원형 배열을 확장할 때 왜 `Arrays.copyOf` 로 통째 복사하면 안 되는가 — 01번 동적 배열에서는 통하던 방법이 여기서 깨지는 이유는 무엇인가. 그리고 `head` 를 뒤로 감을 때 `(head - 1)` 이 왜 위험한가.
11. 최악의 사용 패턴을 만들어 보라 — `ArrayQueue` 에 `enqueue`/`dequeue` 를 번갈아 n 번 하면 배열 길이와 총 비용이 어떻게 되는가. 같은 패턴을 `CircularQueue` 에 주면 어떻게 되는가. 반대로 `CircularQueue` 가 가장 잘 도는 경우는 언제인가.
12. 네 구현(`ArrayQueue`, `CircularQueue`, `ArrayDeque`, `LinkedDeque`)의 트레이드오프는 무엇인가. 연결 구현은 되감기·확장·용량이 전부 없는데도 항상 유리하지는 않은 이유는(노드당 메모리, 참조 추적, 지역성) 무엇인가. `Deque extends Queue` 로 두고 연결 기반 큐를 따로 만들지 않은 결정은 무엇을 얻었는가 — 그리고 `RecentCounter` 와 `firstUniqueStream` 이 굳이 `Queue` 만 받는 이유는 무엇인가.
13. 05-hashmap 으로의 연결 — 지금까지의 자료구조(배열·연결 리스트·스택·큐)는 전부 "순서"가 있는 구조였다. 큐에서 "특정 값이 들어 있는지" 묻는 순간 왜 무너지는가. 그 한계가 "키로 찾는" 구조를 어떻게 부르는가.
