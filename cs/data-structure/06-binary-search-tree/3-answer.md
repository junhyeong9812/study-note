### A. 문제 (BSTProblems)

#### 1. 가장 가까운 키 (`closestKey`)

문제는 "`target` 과 차이가 가장 작은 키를 반환하라"이다.\
비어 있으면 `NoSuchElementException`, 양쪽 차이가 같으면 작은 쪽을 반환한다.\
함정은 성능이다 — 테스트 `mustBeLogarithmic` 이 10만 개 트리에 10만 번 질의를 5초 안에 끝내라고 요구한다.

> **질의(query)** — 자료구조에 던지는 질문 한 번.\
> 예: `closestKey(map, 7)` 한 번이 질의 하나이고, 이 테스트는 그것을 10만 번 던진다.

**접근 1 — 전부 훑어 최소 차이를 찾는다** (가장 먼저 떠오르고, 정답이지만 시간 제한에 걸린다)

```java
// 의사코드
Integer best = null;
long bestDiff = Long.MAX_VALUE;
for (Integer key : map.keys()) {          // 중위 순회로 n 개 전부 받아온다
    long diff = Math.abs((long) target - key);
    if (diff < bestDiff || (diff == bestDiff && key < best)) {
        best = key;
        bestDiff = diff;
    }
}
if (best == null) throw new NoSuchElementException("비어 있다");
return best;
```

```
처리 과정 : map = {1, 5, 9}, target = 7
            of(1, 5, 9) 는 1 -> 5 -> 9 순서로 넣으므로 오른쪽으로만 늘어진 트리다

    [1]
       \
       [5]
          \
          [9]

    keys() 가 전부 꺼낸다 -> 1, 5, 9  (노드 3개 전부 방문)

    key=1 : |7 - 1| = 6   -> best = 1, bestDiff = 6
    key=5 : |7 - 5| = 2   -> 6 보다 작다 -> best = 5, bestDiff = 2
    key=9 : |7 - 9| = 2   -> 같다 -> 작은 쪽 유지 -> best = 5

    답은 맞다. 문제는 "노드 3개 전부 방문"이 n 개일 때 n 번이라는 것이다.
    이 트리에서 답 5 를 찾는 데 9 까지 볼 이유가 전혀 없었다.
```

- 논리: 모든 키와 거리를 재서 최소를 고른다 — 순서 구조를 전혀 쓰지 않는다.
- 논리: 이 풀이는 `SortedMap` 이 아니라 그냥 "키 목록"만 있어도 돌아간다.\
  즉 BST 를 쓰는 의미가 없다.
- 비용(왜): `keys()` 가 중위 순회로 n 개를 전부 모으므로 질의 한 번이 **O(n)**.
- 비용(왜): `keys()` 가 `ArrayList` 를 새로 만들어 n 개를 담으므로 질의마다 추가 공간 **O(n)**.
- 한계: 10만 개 × 10만 질의면 계산상 10^5 × 10^5 = **10^10 회** 비교다.\
  초당 10^9 회를 가정해도 10초가 넘는다 — 5초 제한을 못 넘긴다.
- 한계: 질의마다 10만 칸짜리 리스트를 새로 만들어 버리므로 GC 부담까지 얹힌다.
- 한계: 테스트 `findsClosest`·`prefersSmallerOnTie` 같은 작은 케이스는 전부 통과한다.\
  느리다는 사실만 안 드러난다 — 시간 제한 테스트가 없으면 이대로 넘어갔을 풀이다.

> **조용한 성능 실패** — 결과는 맞는데 규모가 커졌을 때만 무너지는 것.\
> 예: `{1, 5, 9}` 에서는 전수 탐색도 정답을 내므로 작은 테스트만 보면 아무 문제가 없어 보인다.

**접근 2 — 키를 한 번 배열로 뽑아 두고 이진 탐색** (전수보다 낫지만 계약이 흔들린다)

```java
// 의사코드
// 준비 단계 : 한 번만 만든다
List<Integer> sorted = new ArrayList<>();
for (Integer key : map.keys()) sorted.add(key);   // O(n)

// 질의 단계 : 매번 이진 탐색
int i = Collections.binarySearch(sorted, target); // O(log n)
if (i >= 0) return sorted.get(i);
int ins = -i - 1;                                  // 들어갈 자리
Integer lower = (ins > 0) ? sorted.get(ins - 1) : null;
Integer upper = (ins < sorted.size()) ? sorted.get(ins) : null;
// 이하 접근 3 과 같은 비교
```

```
처리 과정 : {1, 5, 9} 를 배열로 펴 놓고 target = 7 을 이진 탐색

    idx      0     1     2
          +-----+-----+-----+
          |  1  |  5  |  9  |
          +-----+-----+-----+

    binarySearch(7) -> 없다 -> 반환 -(1) - 1 = -3  (들어갈 자리 ins = 2)
                                ^ 자바의 관례: 못 찾으면 -(삽입점) - 1

          +-----+-----+-----+
          |  1  |  5  |  9  |
          +-----+-----+-----+
                   ^     ^
                lower   upper     ins - 1 = 1 번 칸 / ins = 2 번 칸

    -> lower = 5, upper = 9 -> 차이 2 대 2 -> 작은 쪽 5

    질의 자체는 빠르다. 문제는 이 배열을 "언제" 만드느냐다.
```

- 논리: 정렬된 배열에서는 이진 탐색이 되고, 삽입점 양옆이 곧 floor 와 ceiling 이다.
- 논리: 질의가 압도적으로 많고 맵이 안 변하면 이 방식이 실제로 가장 빠르다(배열은 캐시 지역성도 좋다).
- 비용(왜): 준비 O(n) 한 번 + 질의당 O(log n).\
  질의 q 번이면 총 `O(n + q log n)`.
- 한계: `closestKey(SortedMap, int)` 는 맵 하나만 받는 **정적 메서드**다.\
  배열을 어디에 캐시해 두겠는가 — 메서드 안에서 만들면 질의마다 O(n) 이라 접근 1과 같아진다.
- 한계: 맵이 중간에 `put`/`remove` 되면 캐시한 배열이 곧바로 낡는다.\
  무효화 로직을 얹는 순간 문제가 자료구조 문제에서 캐시 일관성 문제로 바뀐다.
- 한계: BST 가 이미 가진 능력(`floorKey`/`ceilingKey`)을 배열로 다시 만들어 쓰는 것이라 낭비다.

> **캐시 무효화(cache invalidation)** — 원본이 바뀌었을 때 복사본을 버리거나 갱신하는 일.\
> 예: 트리에 키 하나만 넣어도 펴놓은 배열은 즉시 틀린 것이 되므로 다시 만들어야 한다.

**접근 3 — `floorKey` 한 번 + `ceilingKey` 한 번** (impl 의 정답)

```java
public static Integer closestKey(SortedMap<Integer, ?> map, int target) {
    Integer lower = map.floorKey(target);
    Integer upper = map.ceilingKey(target);

    if (lower == null && upper == null) {
        throw new NoSuchElementException("비어 있다");
    }
    if (lower == null) return upper;
    if (upper == null) return lower;

    long toLower = (long) target - lower;
    long toUpper = (long) upper - target;
    return toLower <= toUpper ? lower : upper;
}
```

```
처리 과정 : map = {1, 5, 9}, target = 7

  floorKey(7) : "7 이하 중 가장 큰 키". 후보(best)를 들고 내려간다

    [1]      7 > 1  -> best = 1, 오른쪽으로 (더 큰 후보가 있을 수 있다)
       \
       [5]   7 > 5  -> best = 5, 오른쪽으로
          \
          [9]  7 < 9 -> 9 는 너무 크다. 답은 9 의 왼쪽뿐인데 왼쪽이 null
             \
             null    길이 끝났다 -> return best = 5

  ceilingKey(7) : "7 이상 중 가장 작은 키". 완전 대칭이다

    [1]      7 > 1  -> 1 은 너무 작다. 오른쪽으로 (후보로 남기지 않는다)
       \
       [5]   7 > 5  -> 역시 너무 작다. 오른쪽으로
          \
          [9]  7 < 9 -> best = 9 로 기억하고 왼쪽으로
         /
       null            길이 끝났다 -> return best = 9

  결정 : toLower = 7 - 5 = 2,  toUpper = 9 - 7 = 2
         2 <= 2 이므로 lower 를 고른다 -> 답 5

  왜 `<=` 인가 : 문제가 "차이가 같으면 작은 쪽"이라고 못박았기 때문이다.
                 `<` 로 쓰면 동점에서 upper(9) 가 나와 prefersSmallerOnTie 가 깨진다.

  왜 두 번이면 끝인가 : 정답 후보는 target 의 바로 왼쪽 이웃과 바로 오른쪽 이웃뿐이다.
                        그보다 더 왼쪽은 lower 보다 멀고, 더 오른쪽은 upper 보다 멀다.
                        정렬되어 있다는 사실이 "후보는 둘"을 보장해 준다.
```

- 논리: 수직선 위에서 `target` 의 양옆 이웃 둘만이 최소 거리 후보다.\
  세 번째 후보는 존재할 수 없다 — 더 바깥의 키는 이웃보다 반드시 멀다.
- 논리: `floorKey`/`ceilingKey` 가 그 두 이웃을 각각 한 번의 하강으로 찾아 준다.
- 논리: 정확히 일치하는 키가 있으면 `floorKey` 와 `ceilingKey` 가 둘 다 그 키를 돌려주므로 차이가 0 대 0 이 되어 자연히 그 키가 나온다(`findsClosest` 의 `closestKey(map, 5) == 5`).
- 비용(왜): 하강 두 번이므로 질의당 `2 × 높이` 비교 → 균형 잡히면 **O(log n)**.
- 비용(왜): 10만 개면 log2(100000) ≈ 16.6 이므로 질의당 계산상 약 34 회 비교다.\
  10만 질의면 약 3.4 × 10^6 회 — 5초 제한 안에서 여유가 크다.
- 비용(왜): 추가 공간은 지역 변수 몇 개뿐 → **O(1)**.\
  접근 1처럼 리스트를 만들지 않는다.
- 한계: 비용이 O(log n) 이 아니라 **O(높이)** 다.\
  트리가 편향되면 질의당 O(n) 으로 되돌아간다 — 그래서 테스트가 `(i * 7919) % n` 으로 일부러 흩어서 넣는다.
- 한계: `long` 뺄셈이 아니면 넘친다.\
  `target` 이 `Integer.MIN_VALUE` 근처이고 `lower` 가 양수면 `target - lower` 가 int 범위를 벗어나 부호가 뒤집힌다.

> **오버플로(overflow)** — 계산 결과가 자료형이 담을 수 있는 범위를 넘어 엉뚱한 값으로 도는 것.\
> 예: int 로 `Integer.MIN_VALUE - 1` 을 하면 음수가 아니라 `Integer.MAX_VALUE` 가 나온다.

- 한계: 위 오버플로를 테스트가 잡아주지 않는다.\
  `BSTProblemsTest` 의 경계값은 -100 과 100 뿐이라, `long` 캐스팅을 빼먹어도 전부 통과한다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 전부 훑어 최소 차이 | 질의당 O(n) | O(n) | n 이 아주 작을 때 · 자료구조가 순서를 모를 때 | 질의가 많을 때 — 10만 × 10만이면 계산상 10^10 |
| 2. 배열로 펴고 이진 탐색 | 준비 O(n) + 질의당 O(log n) | O(n) | 맵이 고정이고 질의만 반복될 때 | 맵이 계속 바뀔 때 · 캐시를 둘 자리가 없을 때 |
| 3. floor + ceiling | 질의당 O(높이) | O(1) | 기본값. 읽기·쓰기가 섞여 있을 때 | 트리가 편향됐을 때(O(n) 으로 되돌아간다) |

**데이터 규모가 커지면**

- n = 1,000 / 질의 1,000 번이면 접근 1도 계산상 10^6 회라 체감되지 않는다.\
  세 접근의 차이가 안 보인다.
- n = 100,000 / 질의 100,000 번이 테스트가 잡은 지점이다.\
  접근 1은 계산상 10^10 회, 접근 3은 약 3.4 × 10^6 회 — 여기서 갈린다.
- 질의가 읽기 전용이고 맵이 변하지 않는 배치라면 접근 2(배열 + 이진 탐색)가 실제로 가장 빠르다.\
  배열은 노드를 따라 포인터를 쫓지 않고 연속 메모리를 훑기 때문이다.
- 키가 수억 개가 되어 메모리에 다 못 올리면 트리 자체를 디스크로 내려야 한다.\
  노드 하나가 디스크 블록 하나인 구조 — 15번 B-트리가 그것이다.
- 질의가 여러 스레드에서 동시에 들어오면 `floorKey` 두 번 사이에 맵이 바뀔 수 있다.\
  `lower` 와 `upper` 가 서로 다른 시점의 트리에서 나온 값이 되므로, 동시성이 있으면 두 호출을 하나의 스냅샷 안에서 해야 한다(원본에 근거 없음 — 내 추론).

> **스냅샷(snapshot)** — 어느 한 시점의 자료구조 상태를 고정해 놓고 보는 것.\
> 예: floor 와 ceiling 을 같은 스냅샷에서 읽어야 "양옆 이웃"이라는 관계가 보장된다.

**질문별 답**

- Q: 문제 1(가장 가까운 키 — `closestKey`)을 어떻게 푸는가.\
  A: `floorKey(target)` 로 왼쪽 이웃, `ceilingKey(target)` 로 오른쪽 이웃을 각각 한 번씩 얻는다.\
  둘 다 없으면 트리가 빈 것이므로 `NoSuchElementException` 을 던진다.\
  하나만 없으면 있는 쪽이 답이다.\
  둘 다 있으면 `long` 으로 거리를 재서 가까운 쪽을, 같으면 작은 쪽(`<=`)을 반환한다.

- Q: 전부 훑어 최소 차이를 찾는 풀이가 왜 시간 제한에 걸리는가.\
  A: 질의 한 번이 n 개 노드를 전부 방문하기 때문이다.\
  `mustBeLogarithmic` 은 n = 100,000 짜리 트리에 100,000 번 질의하고 5초를 준다.\
  질의당 O(n) 이면 총 비용이 계산상 10^10 회 연산이라 5초에 들어갈 수 없다.\
  테스트의 실패 메시지가 그대로 그 말이다 — "전부 훑어서 최소 차이를 찾으면 O(n) 이라 여기서 막힌다. floor 와 ceiling 을 써라."

- Q: `floorKey`/`ceilingKey` 두 번으로 끝나는 이유는 무엇인가.\
  A: 키가 정렬되어 있으므로 `target` 과 가장 가까운 키는 반드시 **바로 왼쪽 이웃 아니면 바로 오른쪽 이웃**이다.\
  그보다 더 바깥의 키는 이웃을 지나쳐야 닿으므로 거리가 더 멀 수밖에 없다.\
  즉 후보가 n 개가 아니라 처음부터 2개다.\
  그 두 개를 각각 한 번의 하강(O(높이))으로 집어오면 되므로 전체가 O(log n) 이 된다.

- Q: 둘 중 하나가 없을 때는 어떻게 되는가.\
  A: `target` 이 최소 키보다 작으면 `floorKey` 가 null 이고, 이때 답은 `ceilingKey`(= 최소 키)다.\
  `target` 이 최대 키보다 크면 `ceilingKey` 가 null 이고, 답은 `floorKey`(= 최대 키)다.\
  테스트가 `closestKey(of(1,5,9), -100) == 1` 과 `closestKey(of(1,5,9), 100) == 9` 로 두 경우를 다 잡는다.\
  둘 다 null 이면 키가 하나도 없다는 뜻이므로 `NoSuchElementException` 을 던진다(`emptyThrows`).

- Q: 차이가 같을 때는 어떻게 되는가.\
  A: 문제가 "양쪽 차이가 같으면 작은 쪽"이라고 정했으므로 `toLower <= toUpper` 의 `=` 가 그 규칙이다.\
  `{1, 5, 9}` 에 target 7 이면 5 와 9 둘 다 차이 2 인데 5 가 나와야 한다.\
  `<` 로 쓰면 동점에서 upper 가 선택되어 `prefersSmallerOnTie` 가 깨진다.\
  동점 처리는 알고리즘이 정해 주는 것이 아니라 **문제 명세가 정해 주는 것**이라, 코드에서는 부등호 한 글자로 나타난다.

#### 2. 구간 합 (`rangeSum`)

문제는 "`from` 이상 `to` 이하인 키들의 값을 더하라"이다.\
`{1=10, 5=50, 9=90}` 에서 from=1, to=5 면 60 이다.\
뒤집힌 범위(`from > to`)는 0 이어야 한다.

**접근 1 — `keys()` 를 전부 돌며 범위 밖을 거른다** (답은 맞지만 트리를 안 쓴 것이다)

```java
// 의사코드
long sum = 0;
for (int key : map.keys()) {          // n 개 전부 받아온다
    if (key < from || key > to) continue;   // 범위 밖은 버린다
    Integer value = map.get(key);
    if (value != null) sum += value;
}
return sum;
```

- 논리: 전체를 정렬 순서로 받아 범위 밖을 버린다 — 순서는 쓰지만 **구조**는 안 쓴다.
- 비용(왜): `keys()` 가 n 개 노드를 전부 방문하므로 **O(n)**.\
  답의 개수 k 와 무관하게 항상 n 이다.
- 비용(왜): `keys()` 가 n 칸짜리 리스트를 만들므로 추가 공간 **O(n)**.
- 한계: 100만 개 중 3개를 뽑는 질의도 100만 노드를 전부 훑는다.\
  "3 이상 8 이하를 순서대로"라는 질문에 해시맵을 쓸 때와 비용이 똑같아진다 — BST 를 쓴 이유가 사라진다.
- 한계: 그런데 **테스트는 전부 통과한다.**\
  `RangeSum` 의 테스트들은 원소가 5개뿐이고 시간 제한이 없다.\
  문제 1과 달리 여기에는 성능을 잡아주는 테스트가 없으므로, 스스로 비용을 따져야 하는 자리다.

**접근 2 — `keysInRange` 의 가지치기를 쓴다** (impl 의 정답)

```java
/** keysInRange 가 가지치기를 하므로 범위 밖은 아예 보지 않는다. */
public static long rangeSum(SortedMap<Integer, Integer> map, int from, int to) {
    long sum = 0;
    for (int key : map.keysInRange(from, to)) {
        Integer value = map.get(key);
        if (value != null) sum += value;
    }
    return sum;
}
```

그 가지치기의 본체는 `BinarySearchTree.collectRange` 다.

```java
private void collectRange(Node<K, V> node, K from, K to, java.util.List<K> out) {
    if (node == null) return;
    int cmpFrom = node.key.compareTo(from);
    int cmpTo = node.key.compareTo(to);

    if (cmpFrom > 0) collectRange(node.left, from, to, out);
    if (cmpFrom >= 0 && cmpTo <= 0) out.add(node.key);
    if (cmpTo < 0) collectRange(node.right, from, to, out);
}
```

```
처리 과정 : 같은 트리, 같은 범위 [35, 65]. 이번에는 가지를 통째로 버린다

                    50         cmpFrom: 50 > 35 -> 왼쪽 재귀 O
                  /    \       수집   : 35 <= 50 <= 65 -> 수집 O
                30      70     cmpTo  : 50 < 65 -> 오른쪽 재귀 O
               /  \    /   \
             20    40 60     80

  [30 에서]  30 > 35 인가? -> 아니다(30 < 35)

                통째로 버린다. 20 은 방문조차 하지 않는다
             수집? 30 >= 35 가 아니다 -> 안 담는다
             30 < 65 -> 오른쪽(40) 만 본다

  [40 에서]  40 > 35 -> 왼쪽 재귀(null)
             35 <= 40 <= 65 -> 수집
             40 < 65 -> 오른쪽 재귀(null)

  [70 에서]  70 > 35 -> 왼쪽(60) 재귀
             수집? 70 <= 65 가 아니다 -> 안 담는다
             70 < 65 인가? -> 아니다
             => 70 의 오른쪽(80) 은 전부 70 보다 크다 = 전부 65 초과
                통째로 버린다. 80 은 방문조차 하지 않는다

  [60 에서]  35 <= 60 <= 65 -> 수집

    방문한 노드 : 50, 30, 40, 70, 60   (20, 80 은 안 봤다)
    결과        : 40, 50, 60  (오름차순 그대로)

    가지치기의 근거
        "지금 노드가 from 이하면 그 왼쪽 서브트리 전부가 from 미만"  <- 불변식이 보증한다
        "지금 노드가 to 이상이면 그 오른쪽 서브트리 전부가 to 초과"   <- 역시 불변식
        한 노드의 키 하나를 보고 서브트리 전체의 운명을 결정할 수 있다는 것이 핵심이다
```

- 논리: 판정 세 줄이 각각 "왼쪽을 볼까 / 나를 담을까 / 오른쪽을 볼까"를 따로 결정한다.\
  세 판정이 독립이라 `from`, `to` 가 트리 어디를 자르든 한 코드로 처리된다.
- 논리: 가지치기의 근거는 노드의 키 하나가 아니라 **서브트리 전체에 대한 보증**(불변식)이다.\
  "왼쪽 자식이 나보다 작다"만으로는 왼쪽 가지를 통째로 버릴 수 없다.
- 논리: 결과가 이미 오름차순이다 — 중위 순회의 뼈대를 그대로 쓰기 때문이다.\
  따로 정렬할 필요가 없다.
- 논리: `from > to` 면 `keysInRange` 가 애초에 빈 리스트를 돌려주므로 합이 0 이다(`sumsRange` 의 `rangeSum(map, 7, 3) == 0`).
- 비용(왜): 방문 노드는 "범위의 양 끝으로 내려가는 두 경로" + "그 사이에 실제로 담기는 k 개"뿐이다 → **O(높이 + k)**.
- 비용(왜): 균형 잡히면 O(log n + k).\
  답이 3개면 100만 개짜리 트리에서도 계산상 20 + 3 수준의 방문이다.
- 한계: impl 은 키를 받아 온 뒤 값을 `map.get(key)` 로 **다시 찾는다.**\
  `get` 하나가 O(높이) 이므로 전체는 O(높이 + k) 가 아니라 **O(높이 × k)** 다.
- 한계: 그 이유는 계약(`SortedMap`)에 "범위 안의 키-값 쌍"을 주는 메서드가 없기 때문이다.\
  `keys()`/`keysInRange()` 가 키만 준다 — 값이 필요하면 다시 내려가는 수밖에 없다.
- 한계: 고치려면 `entriesInRange` 같은 메서드를 계약에 더하거나, 순회 중에 값까지 같이 모아야 한다.\
  다만 계약은 주어진 것이라 이 챕터에서는 손대지 않는다(`SortedMap.java` 의 "이 인터페이스에는 TODO 가 없다. 계약은 주어지는 것이다").
- 한계: `if (value != null)` 은 값으로 null 을 담을 수 있기 때문이다(`allowsNullValue`).\
  이 검사를 빼면 언박싱에서 `NullPointerException` 이 난다.

> **언박싱(unboxing)** — `Integer` 같은 객체를 `int` 원시 값으로 자동 변환하는 것.\
> 예: `sum += value` 에서 `value` 가 null 이면 변환할 값이 없어 NullPointerException 이 난다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. keys() 전부 + 필터 | O(n) | O(n) | n 이 작고 범위가 거의 전체일 때 | n 이 크고 범위가 좁을 때 |
| 2. keysInRange (가지치기) | O(높이 + k) 수집 · impl 은 값 조회까지 O(높이 × k) | O(k) | 기본값. 좁은 범위를 자주 물을 때 | 트리가 편향됐을 때 |
| 2'. 순회 중 값까지 수집(계약 확장 필요) | O(높이 + k) | O(k) | 값이 항상 필요할 때 | 계약을 못 바꿀 때 |

**데이터 규모가 커지면**

- n = 5 인 테스트에서는 두 접근의 차이가 전혀 안 보인다.\
  `sumsRange` 는 둘 다 통과시킨다.
- n = 1,000,000 이고 범위 안이 10개면 접근 1은 10^6 노드를 훑고, 접근 2는 계산상 수십 노드만 본다.\
  범위가 좁을수록 차이가 커진다.
- 반대로 범위가 전체(`rangeSum(map, -100, 100)` 같은 `sumsAll` 케이스)면 두 접근이 사실상 같다.\
  가지치기로 버릴 가지가 없기 때문이다 — 가지치기의 이득은 **범위가 좁을 때** 나온다.
- 같은 범위 합을 아주 자주 묻는다면 트리 순회 자체를 없애는 쪽으로 간다.\
  노드마다 "내 서브트리의 값 합"을 들고 있게 하거나, 누적합 배열·펜윅 트리(17번)를 쓰면 O(log n) 이 된다.
- 값이 큰 정수들이면 `long sum` 이 필수다.\
  `int` 로 받으면 10만 건만 더해도 넘칠 수 있다 — impl 이 반환형을 `long` 으로 잡은 이유다.

**질문별 답**

- Q: 문제 2(구간 합 — `rangeSum`)를 어떻게 푸는가.\
  A: `keysInRange(from, to)` 로 범위 안의 키만 오름차순으로 받는다.\
  받은 키마다 `map.get(key)` 로 값을 꺼내 더한다.\
  값이 null 일 수 있으므로 null 이면 건너뛴다.\
  누적은 `long` 으로 받아 int 오버플로를 피한다.

- Q: `keys()` 를 전부 돌며 거르는 풀이와 `keysInRange` 를 쓰는 풀이의 비용 차이는 어디서 생기는가.\
  A: **방문하는 노드 수**에서 생긴다.\
  전자는 답의 개수와 상관없이 항상 n 개를 방문한다 — 범위 밖이라는 것을 "다 본 다음에" 알기 때문이다.\
  후자는 지금 노드의 키 하나를 보고 서브트리 전체를 볼지 말지를 먼저 결정한다 — 불변식이 "이 노드가 from 이하면 왼쪽 전부가 from 미만"을 보증해 주기 때문이다.\
  그래서 전자는 O(n), 후자는 O(높이 + k) 이고, 범위가 좁을수록(k 가 작을수록) 격차가 벌어진다.

#### 3. k 번째로 작은 키 (`kthSmallest`)

문제는 "정렬했을 때 k 번째(1부터 센다) 키를 반환하라"이다.\
`k` 가 범위를 벗어나면 `IndexOutOfBoundsException` 이다.

**접근 1 — 키를 전부 리스트로 받아 인덱싱** (가장 짧지만 가장 낭비가 크다)

```java
// 의사코드
List<Integer> all = new ArrayList<>();
for (Integer key : map.keys()) all.add(key);
if (k < 1 || k > all.size()) throw new IndexOutOfBoundsException("k=" + k);
return all.get(k - 1);
```

- 논리: 중위 순회가 이미 정렬 순서를 주므로 k-1 번 인덱스가 곧 답이다.
- 비용(왜): 순회 O(n) + 리스트 복사 O(n) → **O(n)**, 추가 공간 O(n).
- 한계: k = 1 을 물어도 n 개를 전부 담는다.\
  "가장 작은 키"는 `firstKey()` 로 O(높이) 에 끝나는데 그것보다 느리다.

**접근 2 — 중위 순회를 돌다가 k 번째에서 멈춘다** (impl 의 정답)

```java
public static Integer kthSmallest(SortedMap<Integer, ?> map, int k) {
    if (k < 1 || k > map.size()) {
        throw new IndexOutOfBoundsException("k=" + k + ", 크기=" + map.size());
    }
    int seen = 0;
    for (Integer key : map.keys()) {
        if (++seen == k) return key;
    }
    throw new IndexOutOfBoundsException("k=" + k);
}
```

```
처리 과정 : of(5, 3, 8, 2, 9) 에 k = 2
            넣은 순서 5 -> 3 -> 8 -> 2 -> 9 가 만드는 트리

                  5
                /   \
               3     8
              /       \
             2         9

  중위 순회(왼쪽 -> 자기 -> 오른쪽)가 방문하는 순서에 번호를 매기면

                  5 (3번째)
                /   \
    (2번째) 3         8 (4번째)
              /         \
  (1번째) 2               9 (5번째)

    나오는 순서 : 2, 3, 5, 8, 9     <- 이것이 곧 정렬 결과다

    seen=1 : key=2,  1 != 2 -> 계속
    seen=2 : key=3,  2 == 2 -> return 3     <- 여기서 멈춘다

    8 과 9 는 "논리적으로는" 볼 이유가 없다.
    k 번째를 찾는 데 필요한 것은 앞에서부터 k 개뿐이기 때문이다.

  경계 : k < 1 이거나 k > size 면 순회를 시작하기도 전에 예외를 던진다
         빈 맵에 k=1 이면 size=0 이라 1 > 0 -> 예외 (rejectsOutOfRange 가 확인한다)
```

- 논리: 중위 순회는 작은 키부터 내놓으므로, k 번째로 나온 것이 곧 k 번째로 작은 키다.
- 논리: 범위 검사를 **순회 전에** 한다 — 잘못된 k 로 n 개를 훑는 낭비를 막는다.
- 논리: `++seen == k` 의 전위 증가가 "1부터 센다"는 문제의 규칙을 그대로 옮긴 것이다.
- 논리: 마지막 `throw` 는 논리상 도달할 수 없는 줄이다.\
  앞의 범위 검사를 통과했다면 반드시 루프 안에서 반환되기 때문이다.\
  자바가 모든 경로의 반환을 요구하므로 남겨 둔 방어선이다.
- 비용(왜): **이 구현에서는 여전히 O(n)** 이다.\
  `keys()` 가 `ArrayList` 에 n 개를 전부 담아 돌려주고 나서야 for 문이 시작되기 때문이다.
- 비용(왜): 즉 `if (++seen == k) return` 의 조기 종료는 **루프 반복만** 줄이고 순회는 못 줄인다.\
  추가 공간도 리스트 때문에 O(n) 이다.
- 비용(왜): `keys()` 가 게으른 반복자였다면 O(높이 + k) 가 됐을 것이다.\
  그래도 O(log n) 은 아니다 — k 개를 실제로 지나가야 하기 때문이다.
- 한계: k 가 n 에 가까우면 어떤 순회 기반 풀이도 O(n) 이다.
- 한계: impl 의 주석("정렬 순회를 하다가 k 번째에서 멈춘다")은 의도를 말한 것이고, 현재 `keys()` 계약 아래에서는 그 절약이 실현되지 않는다.\
  스켈레톤 javadoc 도 "여기서는 순회로 충분하다"라고 적어 이 비용을 감수하기로 정해 두었다.

> **게으른 반복자(lazy iterator)** — 요청받을 때마다 다음 원소 하나씩만 만들어 내는 반복자.\
> 예: 전체 리스트를 먼저 만들지 않으므로 앞의 k 개만 쓰고 멈추면 뒤는 계산조차 안 한다.

**접근 3 — 노드마다 서브트리 크기를 들고 있는다** (O(log n) 으로 내려가는 길)

```java
// 의사코드 — Node 에 int count(자기 포함 서브트리 노드 수) 필드를 추가한다고 가정
Node<K, V> cur = root;
while (cur != null) {
    int leftCount = (cur.left == null) ? 0 : cur.left.count;
    if (k == leftCount + 1) return cur.key;      // 내가 바로 k 번째
    if (k <= leftCount) cur = cur.left;          // 답은 왼쪽에 있다
    else { k -= leftCount + 1; cur = cur.right; } // 왼쪽 전부와 나를 건너뛴다
}
```

```
처리 과정 : 각 노드에 (count) 를 적어 둔 트리. 같은 트리에 k = 4

                  5 (5)
                /      \
           3 (2)        8 (2)
          /                 \
       2 (1)                 9 (1)

  [5 에서] leftCount = 3 의 count = 2
           k(4) == 2 + 1 = 3 ?  아니다
           k(4) <= 2 ?          아니다
           => 왼쪽 2개와 나 자신 1개, 합 3개를 건너뛴다. k = 4 - 3 = 1
              오른쪽으로 간다

  [8 에서] leftCount = 0 (왼쪽 없음)
           k(1) == 0 + 1 = 1 ?  그렇다 -> return 8

    방문 노드 2개. 답 8 은 전체에서 4번째로 작은 키다 (2, 3, 5, 8, 9)
    k 가 몇이든 경로 하나만 내려가므로 O(높이) 다
```

- 논리: "왼쪽 서브트리에 몇 개가 있는지"를 알면 내가 몇 번째인지가 즉시 정해진다.\
  왼쪽 개수 + 1 이 내 순위다.
- 논리: 오른쪽으로 갈 때 k 에서 "왼쪽 전부 + 나"를 빼는 것이, 오른쪽 서브트리 기준으로 순위를 다시 매기는 일이다.
- 비용(왜): 경로 하나만 내려가므로 **O(높이)** = 균형이면 O(log n).\
  k 와 무관하다.
- 한계: `put`/`remove` 가 경로상의 모든 `count` 를 같이 고쳐야 한다.\
  유지할 상태가 늘면 깨뜨릴 곳도 늘어난다.
- 한계: 이 챕터의 `Node` 에는 그 필드가 없고 계약에도 없다.\
  impl 주석이 "17번 펜윅 트리에서 본격적으로 다룬다"라고 미뤄 둔 이유다.

> **순위 질의(rank/select)** — "이 키가 몇 번째인가"(rank)와 "k 번째는 무엇인가"(select)를 묻는 연산.\
> 예: 서브트리 크기를 들고 있으면 둘 다 O(log n) 이 되고, 없으면 순회로 O(n) 이다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 전부 리스트로 받아 인덱싱 | O(n) | O(n) | 어차피 전체 목록이 필요할 때 | k 가 작을 때 · 메모리가 빠듯할 때 |
| 2. 순회하다 k 에서 멈춤 (impl) | O(n) — keys() 가 미리 다 담으므로 | O(n) | 이 챕터의 계약 안에서 가장 단순한 풀이 | k 번째 질의가 아주 잦을 때 |
| 2'. 게으른 중위 순회 | O(높이 + k) | O(높이) — 스택 | k 가 작을 때 | k 가 n 에 가까울 때 |
| 3. 서브트리 크기 필드 | O(높이) | 노드당 int 하나 | 순위 질의가 잦을 때 | 쓰기가 잦아 유지 비용이 클 때 |

**데이터 규모가 커지면**

- n = 5 인 테스트에서는 네 접근이 전부 같아 보인다.\
  `findsKth` 는 어느 것으로 짜도 통과한다.
- n = 1,000,000 에 k = 1 이면 접근 2는 100만 개를 리스트에 담고 첫 원소를 반환한다.\
  `firstKey()` 였으면 계산상 20 번 비교로 끝났을 일이다.
- "중앙값을 계속 물어보는" 워크로드(k = n/2)라면 어떤 순회도 O(n) 이라 접근 3이 유일한 답이다.
- 키가 계속 들어오고 나가면서 순위를 물어야 하면(예: 실시간 리더보드) 서브트리 크기를 유지하는 트리나 펜윅 트리가 표준 도구다.
- 접근 2' 의 게으른 순회는 재귀를 명시적 스택으로 바꿔야 만들 수 있다.\
  그 스택 깊이가 트리 높이만큼이라, 편향 트리에서는 스택 자체가 O(n) 이 된다.

**질문별 답**

- Q: 문제 3(k 번째로 작은 키 — `kthSmallest`)을 어떻게 푸는가.\
  A: 먼저 `k < 1 || k > map.size()` 로 범위를 검사해 벗어나면 `IndexOutOfBoundsException` 을 던진다.\
  그다음 `map.keys()` 를 오름차순으로 돌면서 센다.\
  `++seen == k` 가 되는 순간의 키가 답이다.\
  중위 순회가 이미 정렬 순서이므로 따로 정렬할 필요가 없다.

- Q: 중위 순회를 끝까지 돌 필요가 없는 이유는 무엇인가.\
  A: 중위 순회는 작은 키부터 순서대로 내놓기 때문이다.\
  k 번째를 알고 싶으면 앞에서부터 k 개만 받으면 되고, k+1 번째 이후는 답에 아무 영향을 주지 않는다.\
  `{2, 3, 5, 8, 9}` 에서 k=2 면 5, 8, 9 를 보지 않아도 답이 3 임이 확정된다.\
  그래서 impl 은 `if (++seen == k) return key;` 로 그 자리에서 빠져나온다.

- Q: 그래도 이 풀이가 O(log n) 이 아닌 이유는 무엇인가.\
  A: 이유가 둘이다.\
  첫째, 이론적으로도 앞의 k 개를 **실제로 지나가야** 하므로 최선이 O(높이 + k) 이지 O(log n) 이 아니다 — k 가 n/2 면 그대로 O(n) 이다.\
  둘째, 이 구현에서는 `keys()` 가 `inOrder` 로 n 개를 `ArrayList` 에 전부 담은 뒤에 반환하므로, for 문이 돌기 전에 이미 O(n) 을 다 써버렸다 — 조기 종료가 순회를 줄이지 못한다.\
  O(log n) 으로 만들려면 노드마다 서브트리 크기를 들고 다니며 "왼쪽에 몇 개 있는지"로 경로 하나만 내려가야 하고, 그건 17번 펜윅 트리에서 다룬다.

### B. 자료구조 특성

#### 4. 이진 탐색 트리가 왜 필요한가

- Q: 이진 탐색 트리가 왜 필요한가.\
  A: **키들 사이의 순서를 물을 수 있게 하기 위해서**다.\
  05번 해시맵은 O(1) 조회를 얻는 대신 순서를 버렸다 — 키를 일부러 흩뿌리기 때문이다.\
  BST 는 "왼쪽 서브트리 전부 < 나 < 오른쪽 서브트리 전부"를 구조에 새겨서, 조회를 O(log n) 으로 내주는 대신 최소·최대·이웃·범위·정렬 순회를 전부 싸게 만든다.\
  README 의 표현대로 "어느 쪽이 낫냐는 질문이 잘못됐다 — 무엇을 물을 것인지가 자료구조를 정한다".

> **탐색 성질(BST invariant)** — 모든 노드에서 "왼쪽 서브트리의 모든 키 < 내 키 < 오른쪽 서브트리의 모든 키"가 성립한다는 규칙.\
> 예: 50 의 왼쪽에 20, 30, 40 이 매달려 있다면 그 셋 중 하나도 50 을 넘지 않는다.

- Q: 05-hash-map 으로는 무엇이 안 되는가.\
  A: 순서가 필요한 질문이 전부 안 된다.\
  README 의 표가 그 목록이다.

  | 질문 | 해시맵 | BST |
  |---|---|---|
  | `get(k)` | **O(1)** | O(log n) |
  | 가장 작은 키 | O(n) | **O(log n)** |
  | k 보다 큰 것 중 가장 작은 키 | O(n) | **O(log n)** |
  | 3 이상 8 이하를 순서대로 | O(n) | **O(log n + k)** |
  | 정렬 순회 | O(n log n) 정렬 필요 | **O(n)** |

- Q: "가장 작은 키"가 해시맵에서 왜 O(n) 인가.\
  A: 해시맵에는 "어느 버킷에 작은 키가 있다"는 정보가 전혀 없기 때문이다.\
  해시 함수는 키를 일부러 고르게 흩뿌리는 것이 목적이라, 1 과 2 가 완전히 다른 버킷으로 간다.\
  따라서 최소를 알려면 모든 버킷과 모든 체인을 다 열어 봐야 한다 → O(n).\
  BST 는 정반대다 — `firstKey()` 가 왼쪽으로만 계속 내려가면 되므로 O(높이) 다.

> **해시 함수(hash function)** — 키를 정수 하나로 바꿔 버킷 번호를 정하는 함수.\
> 예: 좋은 해시 함수일수록 비슷한 키를 서로 멀리 흩뿌리므로, 흩어진다는 장점이 곧 "이웃을 모른다"는 단점이 된다.

> **버킷(bucket)** — 해시맵에서 같은 해시값으로 모인 키들이 담기는 칸.\
> 예: 버킷 번호는 해시값으로 정해지므로 번호 순서와 키의 대소 순서는 아무 관계가 없다.

- Q: "k 보다 큰 것 중 가장 작은 키"가 해시맵에서 왜 O(n) 인가.\
  A: `get(k+1)`, `get(k+2)` … 로 하나씩 물어볼 수도 있지만, 다음 키가 얼마나 멀리 있는지 알 수 없다.\
  키가 1 과 10억뿐이면 `k=1` 다음을 찾느라 10억 번을 물어야 한다.\
  결국 전 버킷을 훑으며 "k 보다 크면서 지금까지 중 가장 작은 것"을 갱신하는 수밖에 없다 → O(n).\
  BST 의 `ceilingKey` 는 같은 일을 하강 한 번(O(높이))에 끝낸다.

- Q: "정렬 순회"가 해시맵에서 왜 O(n log n) 인가.\
  A: 버킷 순서는 해시값 순서라 키의 대소와 무관하기 때문이다.\
  그래서 키를 전부 꺼내서(O(n)) 새로 정렬해야(O(n log n)) 한다.\
  BST 는 중위 순회 한 번에 정렬 순서가 나오므로 O(n) 이고, 정렬 비용 자체가 존재하지 않는다.\
  차이는 "정렬을 매번 다시 한다" 대 "구조가 이미 정렬을 들고 있다"이다.

**더 생각할 것**

- 이 표를 외울 것이 아니라 "왜 그렇게 되는가"를 한 문장으로 말할 수 있어야 한다 — 해시는 순서를 파괴하는 것이 설계 목적이고, BST 는 순서를 보존하는 것이 설계 목적이다.
- 실무에서는 둘을 같이 쓰는 경우가 흔하다.\
  정확 일치 조회는 해시맵, 범위·정렬은 트리에 두고 동기화하는 식이다.
- DB 인덱스가 해시 인덱스와 B-트리 인덱스로 갈리는 것도 정확히 같은 갈림길이다.\
  `WHERE id = ?` 에는 해시가, `WHERE created_at BETWEEN ? AND ?` 에는 트리가 맞다.
- 자바 표준 라이브러리로 보면 `HashMap` 대 `TreeMap` 의 차이가 이 챕터의 주제 전체다.

#### 5. 어떤 데이터·접근 패턴에 적합한가

- Q: 어떤 형태의 데이터·접근 패턴에 BST 가 적합한가.\
  A: 키에 **자연스러운 대소 순서**가 있고, 그 순서를 실제로 묻는 워크로드다.\
  구체적으로는 범위 조회(기간·가격대·점수 구간), 이웃 조회(가장 가까운 값·바로 다음 값), 최소·최대 꺼내기, 정렬된 순회다.\
  키가 계속 들어오고 나가면서도 정렬 상태를 유지해야 할 때 — 정렬된 배열은 삽입이 O(n) 이라 이 자리를 못 채운다.\
  이 챕터의 세 문제가 전부 "가장 가까운 것"을 묻는 이유가 그것이다(impl 주석: "셋 다 '가장 가까운 것'을 묻는다").

> **워크로드(workload)** — 그 자료구조에 실제로 들어오는 연산의 종류와 비율.\
> 예: "읽기 99% / 쓰기 1% 이고 그중 범위 조회가 절반"처럼 재 봐야 자료구조를 고를 수 있다.

- Q: 언제 쓰면 안 되는가.\
  A: 키에 순서가 없거나 순서가 의미 없을 때 — UUID, 세션 토큰, URL 같은 키는 "다음 키"를 물어볼 일이 없다.\
  질의가 정확 일치(`get`)뿐일 때 — O(1) 을 O(log n) 으로 바꾸고 아무것도 못 받는 거래다.\
  키가 `Comparable` 이 아닐 때 — 이 구현은 `K extends Comparable<K>` 를 요구한다.\
  입력이 정렬된 순서로 들어오는데 재균형 장치가 없을 때 — 이 챕터의 BST 는 그대로 연결 리스트가 된다.

- Q: `get(k)` 가 O(1) 에서 O(log n) 으로 나빠지는 이 거래를 받아들일 이유가 없는 워크로드는 무엇인가.\
  A: **순서를 한 번도 묻지 않는** 워크로드다.\
  캐시(키로 값만 꺼낸다), 세션 저장소(세션 ID → 사용자), 중복 제거용 집합, 설정값 조회처럼 질의가 전부 "이 키 있어? 값 줘"인 경우다.\
  이런 곳에서는 `firstKey`·`floorKey`·`keysInRange` 를 한 줄도 쓰지 않으므로, 대가만 치르고 대가로 산 것을 안 쓰는 셈이다.\
  n = 100만이면 해시맵은 계산상 1~2 회 비교, BST 는 약 20 회 비교 — 10배 이상의 차이를 아무 이득 없이 감수하게 된다.

**더 생각할 것**

- "적합/부적합"은 자료구조의 성질이 아니라 **질문의 성질**이다.\
  같은 데이터라도 무엇을 묻느냐에 따라 답이 뒤집힌다.
- 순서 질의가 전체의 1% 라도, 그 1% 가 O(n) 이면 시스템 전체의 병목이 될 수 있다.\
  비율만 보지 말고 절대 비용을 같이 봐야 한다.
- 순서가 필요하지만 갱신이 거의 없다면 트리보다 **정렬된 배열 + 이진 탐색**이 더 빠르다.\
  캐시 지역성이 좋고 포인터가 없기 때문이다 — 문제 1의 접근 2가 그 경우다.
- 이 인터페이스(`SortedMap`)는 12번 스킵 리스트, 15번 B-트리, 16번 레드블랙 트리가 그대로 구현한다.\
  즉 "정렬 맵이 필요하다"는 판단과 "무엇으로 구현할까"는 분리된 결정이다.

#### 6. `get`/`put` 이 O(log n) 인 구조적 이유

- Q: "왼쪽은 작고 오른쪽은 크다"라는 규칙 하나가 왜 매 단계 볼 곳을 절반으로 줄이는가.\
  A: 비교 한 번의 결과가 **한 노드가 아니라 서브트리 전체**의 운명을 정하기 때문이다.\
  찾는 키가 지금 노드보다 작으면, 오른쪽 서브트리에 있는 모든 키는 지금 노드보다 크므로 전부 후보에서 사라진다.\
  즉 비교 한 번 = 후보 집합을 둘로 자르고 한쪽을 통째로 버리는 일이다.\
  균형 잡힌 트리면 두 쪽의 크기가 비슷하므로 매번 후보가 절반이 되고, n 을 1로 만들려면 절반 나누기를 log2(n) 번 해야 한다.

```
비교 한 번이 버리는 양 : get(40) 을 찾을 때

                    50            40 < 50 -> 왼쪽으로
                  /    \
                30      70        <- 여기 이하 전부(60, 70, 80)가 한 번에 사라진다
               /  \    /   \
             20    40 60     80

    [50] 에서의 비교 1회 :  후보 7개 -> 3개   (50 자신과 오른쪽 3개를 버린다)
    [30] 에서의 비교 1회 :  후보 3개 -> 1개   (30 자신과 왼쪽 1개를 버린다)
    [40] 에서의 비교 1회 :  찾음

    "왼쪽 자식 하나가 나보다 작다" 였다면 이 절단이 불가능하다.
    오른쪽 어딘가에 작은 값이 숨어 있을 수 있어 결국 다 봐야 하기 때문이다.
    버릴 수 있는 근거는 서브트리 전체에 대한 보증이다.
```

- Q: 그 비용이 사실은 무엇에 비례하는 값인가.\
  A: **트리의 높이 h** 다.\
  `findNode`·`put`·`remove`·`floorKey` 는 전부 루트에서 아래로 한 줄만 내려가고 되돌아오지 않는다.\
  그래서 비용은 "내려간 길이"이고, 그 상한이 높이다 — O(log n) 은 "높이가 log n 일 때"에만 성립하는 특수한 경우다.\
  `height()` 메서드를 굳이 열어 둔 것도 그 값을 눈으로 보라는 뜻이다(javadoc: "균형이 깨졌는지 눈으로 보려고 열어둔다").

> **높이(height)** — 루트에서 가장 깊은 잎까지의 노드 수.\
> 예: 이 구현은 빈 트리가 0, 노드 하나가 1 이다(`heightOf` 가 `1 + max(...)`).

- Q: n 개를 넣었을 때 높이는 얼마가 되는가.\
  A: 균형 잡히면 log2(n) 근처, 최악(정렬 입력)이면 n 이다.\
  `BinarySearchTree` 의 클래스 javadoc 이 "n 개를 넣었을 때 균형 잡힌 트리는 높이가 log2(n) 근처, 치우친 트리는 n" 이라고 그대로 적어 두었다.\
  테스트 `sortedInsertDegenerates` 가 1000개 정렬 입력에서 높이 1000 을, 흩어진 입력에서 높이 50 미만을 확인한다.

- Q: `put` 도 같은 이유로 O(높이) 인가.\
  A: 그렇다 — `put` 은 "내려갈 자리가 없을 때까지 내려가서 잎으로 붙이기"이기 때문이다.\
  탐색과 똑같은 경로를 밟고, 마지막에 `parent.left` 또는 `parent.right` 에 새 노드를 다는 O(1) 작업이 붙을 뿐이다.\
  기존 노드는 하나도 움직이지 않는다 — 회전도 재균형도 없다.\
  그래서 **넣는 순서가 트리 모양을 그대로 결정한다**.

```java
Node<K, V> node = new Node<>(key, value);
if (cmp < 0) parent.left = node; else parent.right = node;
size++;
return null;
```

- Q: 이 구현은 재귀인가 반복인가.\
  A: 쓰기·탐색 계열(`findNode`, `put`, `remove`, `firstKey`, `lastKey`, `floorKey`, `ceilingKey`)은 전부 **반복(while)** 이다.\
  스켈레톤 javadoc 이 "재귀와 반복 중 어느 쪽이든 된다. 반복이 스택을 안 쓴다"라고 힌트를 준 대로다.\
  반면 순회 계열(`inOrder`, `collectRange`, `heightOf`)은 **재귀**다 — 두 서브트리를 모두 방문해야 해서 되돌아올 지점이 필요하기 때문이다.\
  그 차이가 편향 트리에서 드러난다: 반복 코드는 높이가 100만이어도 메모리를 안 쓰지만, 재귀 코드는 호출 스택을 높이만큼 쌓는다.

> **호출 스택(call stack)** — 함수가 자기를 부를 때마다 쌓이는 되돌아갈 자리들의 더미.\
> 예: 높이 1000 인 트리에서 `inOrder` 는 프레임 1000개를 쌓았다가 하나씩 걷어낸다.

**더 생각할 것**

- "O(log n)"이라고 말하는 순간 이미 "균형 잡혀 있다"를 가정한 것이다.\
  이 챕터의 BST 는 그 가정을 **보장하지 않는다** — 보장하는 것이 16번 레드블랙 트리다.
- 트리에는 `parent` 필드가 없다(2-summary 의 구조 그림).\
  그래서 위로 올라갈 길이 없고, 링크를 고쳐야 하는 연산은 `parent` 를 손에 들고 내려간다.
- 비교 한 번의 비용도 상수가 아니다.\
  키가 긴 문자열이면 `compareTo` 하나가 이미 O(문자열 길이) 다 — "O(log n) 번 비교"가 "O(log n) 시간"과 같으려면 비교가 O(1) 이어야 한다.

#### 7. `floorKey` 가 왜 후보를 기억하면서 내려가야 하는가

- Q: `floorKey` 가 왜 후보를 기억하면서 계속 내려가야 하는가.\
  A: 지금 노드가 답일 **수도** 있지만 더 나은 답이 아래에 있을 수도 있기 때문이다.\
  `key` 이하인 노드를 만나면 그 노드는 "일단 가능한 답"이지만, 오른쪽으로 더 내려가면 `key` 이하이면서 더 큰 키가 나올 수 있다.\
  그래서 후보(`best`)로 붙잡아 두고 오른쪽으로 계속 내려간다.\
  길이 끝나면(null 에 닿으면) 마지막으로 잡아 둔 후보가 답이다.

```java
K best = null;
Node<K, V> cur = root;
while (cur != null) {
    int cmp = key.compareTo(cur.key);
    if (cmp == 0) return cur.key;
    if (cmp < 0) {
        cur = cur.left;          // 이 노드는 너무 크다. 답은 왼쪽에만 있다
    } else {
        best = cur.key;          // 후보로 기억하되, 오른쪽에 더 가까운 것이 있을 수 있다
        cur = cur.right;
    }
}
return best;
```

```
처리 과정 : floorKey(45) — "45 이하 중 가장 큰 키"

                    50
                  /    \
                30      70
               /  \    /   \
             20    40 60     80
                     \
                      45 은 트리에 없다

  [50] 45 < 50  -> 50 은 45 보다 크다. 답이 될 수 없다
                   best 는 그대로 null. 왼쪽으로

  [30] 45 > 30  -> 30 은 45 이하다. 답일 수 있다 -> best = 30
                   하지만 30 의 오른쪽에는 30 보다 크면서 45 이하인 키가 있을 수 있다
                   그래서 반환하지 않고 오른쪽으로

  [40] 45 > 40  -> 40 도 45 이하이고 30 보다 크다 -> best = 40 으로 갱신
                   오른쪽으로

  null           길이 끝났다 -> return best = 40

  만약 [30] 에서 바로 반환했다면 답이 30 이 되어 틀린다.
  "45 이하"라는 조건만 보면 30 도 자격이 있지만 "그중 가장 큰"이 아니기 때문이다.
```

- Q: 다른 탐색과 달리 "찾으면 바로 반환"이 안 되는 이유는 무엇인가.\
  A: `get` 은 조건이 **등호**라 답이 유일하기 때문이다 — 같은 키를 찾는 순간 더 나은 답이 있을 수 없다.\
  `floorKey` 의 조건은 부등호(`key 이하`)이고 거기에 "그중 최대"라는 최적화 조건이 붙어 있다.\
  조건을 만족하는 키가 여럿이므로, 하나 찾았다고 끝나는 것이 아니라 **더 나은 것이 없는지 끝까지 확인**해야 한다.\
  다만 `cmp == 0` 일 때는 즉시 반환한다 — `key` 자신이 `key` 이하 중 최대라서 더 나은 답이 있을 수 없기 때문이다.\
  README 의 표현대로 "찾으면 바로 반환이 안 되는 유일한 탐색"이다.

> **탐욕적 갱신(best-so-far)** — 내려가면서 "지금까지 본 것 중 가장 좋은 답"을 계속 덮어쓰는 방식.\
> 예: `best = cur.key` 는 이전 후보를 버리고 더 좋은 후보로 바꾸는 것이고, 오른쪽으로 갈수록 반드시 더 좋아지므로 비교 없이 덮어써도 된다.

- Q: 왼쪽으로 갈 때는 왜 후보를 남기지 않는가.\
  A: 왼쪽으로 가는 경우는 `key < cur.key` 일 때, 즉 지금 노드가 `key` 보다 **크다**는 뜻이기 때문이다.\
  `key` 보다 큰 키는 "key 이하"라는 조건 자체를 만족하지 못하므로 후보 자격이 없다.\
  그러니 기억할 것이 없고, 답은 오직 왼쪽 서브트리 안에만 있다.

- Q: `ceilingKey` 는 무엇이 대칭으로 뒤집히는가.\
  A: 부등호 방향과 내려가는 방향이 통째로 뒤집힌다.\
  `floorKey` 는 "지금 노드가 key 이하면 후보로 잡고 **오른쪽**", `ceilingKey` 는 "지금 노드가 key 이상이면 후보로 잡고 **왼쪽**"이다.\
  코드로는 `if (cmp < 0)` 이 `if (cmp > 0)` 으로, `cur = cur.left` 와 `cur = cur.right` 가 서로 바뀐 것뿐이다.\
  나머지(`cmp == 0` 즉시 반환, `best` 를 들고 내려가기, 끝나면 `best` 반환, 없으면 null)는 완전히 같다.

```
대칭 : ceilingKey(45) — "45 이상 중 가장 작은 키"

                    50
                  /    \
                30      70
               /  \    /   \
             20    40 60     80

  [50] 45 < 50 -> 50 은 45 이상이다 -> best = 50, 왼쪽으로
                  (왼쪽에 45 이상이면서 더 작은 키가 있을 수 있다)
  [30] 45 > 30 -> 30 은 45 미만이라 자격이 없다. 오른쪽으로
  [40] 45 > 40 -> 역시 자격 없음. 오른쪽으로
  null          -> return best = 50

  floorKey(45) = 40 과 ceilingKey(45) = 50 이 45 의 양옆 이웃이다.
  문제 1의 closestKey 가 쓰는 것이 바로 이 둘이다.
```

**더 생각할 것**

- `best` 를 "남은 후보 중 최선"이라는 불변식으로 읽으면 두 메서드가 하나의 패턴이 된다 — 루프가 끝날 때 `best` 는 지금까지 지나온 경로에서 조건을 만족하는 최선의 값이다.
- `floorKey`/`ceilingKey` 가 있으면 `closestKey`, "다음 예약 시각", "이 가격 바로 아래 호가" 같은 실무 질의가 전부 O(log n) 이 된다.\
  자바 `TreeMap` 의 `floorKey`/`ceilingKey`/`higherKey`/`lowerKey` 가 같은 계열이다.
- `floorKey` 는 `key` 자신을 포함하고(`floorKey(5) == 5`), `lowerKey` 는 제외한다.\
  경계 포함 여부는 이름으로 구분해야 하고, 틀리면 조용히 off-by-one 이 된다.
- 이 구현은 `key` 가 null 이면 null 을 반환한다.\
  `put` 은 null 키에 예외를 던지는데 조회 계열은 null 을 돌려주는 비대칭이 있다 — 계약(`SortedMap`)에 명시가 없는 부분이다.

#### 8. 중위 순회가 왜 정렬된 순서를 주는가

- Q: 중위 순회가 왜 정렬된 순서를 주는가 — 탐색 성질에서 어떻게 직접 따라 나오는가.\
  A: 불변식이 "왼쪽 전부 < 나 < 오른쪽 전부"이기 때문이다.\
  그러면 **왼쪽 전부를 먼저, 나를 그다음, 오른쪽 전부를 마지막**에 내놓는 순서가 곧 오름차순이다.\
  각 서브트리에서도 같은 규칙이 성립하므로(서브트리도 BST 다) 재귀적으로 전체가 정렬된다.\
  즉 정렬을 "하는" 것이 아니라, 불변식이 이미 정렬을 들고 있고 순회 순서가 그것을 꺼내는 것뿐이다.

```java
private void inOrder(Node<K, V> node, java.util.List<K> out) {
    if (node == null) return;
    inOrder(node.left, out);
    out.add(node.key);
    inOrder(node.right, out);
}
```

```
왜 이 순서인가 : 세 덩어리의 대소 관계가 이미 정해져 있다

                    50
                  /    \
                30      70
               /  \    /   \
             20    40 60     80

    [ 왼쪽 서브트리 전부 ] < [ 50 ] < [ 오른쪽 서브트리 전부 ]
      20, 30, 40                        60, 70, 80

    왼쪽 덩어리 안에서도 같은 규칙이 성립한다
        [ 20 ] < [ 30 ] < [ 40 ]

    그래서 왼쪽 -> 자기 -> 오른쪽 으로 펼치면

        20  30  40  50  60  70  80

    순회 순서를 바꾸면 정렬이 깨진다
        전위(자기 -> 왼쪽 -> 오른쪽) : 50 30 20 40 70 60 80   <- 구조 저장용
        후위(왼쪽 -> 오른쪽 -> 자기) : 20 40 30 60 80 70 50   <- 해제/계산용
        정렬을 주는 것은 오직 중위다
```

> **중위 순회(in-order traversal)** — 왼쪽 서브트리 → 자기 → 오른쪽 서브트리 순서로 트리를 도는 방법.\
> 예: BST 에서 이 순서로 모으면 따로 정렬하지 않아도 오름차순 결과가 나온다.

- Q: `keysInRange` 의 가지치기는 무엇을 근거로 가지를 통째로 건너뛰는가.\
  A: 노드 하나의 키가 서브트리 전체의 상한/하한 역할을 한다는 **불변식**이 근거다.\
  지금 노드의 키가 `from` 이하면, 그 왼쪽 서브트리의 모든 키는 지금 노드보다 작으므로 전부 `from` 미만이다 → 왼쪽은 답이 있을 수 없다.\
  지금 노드의 키가 `to` 이상이면, 오른쪽 서브트리의 모든 키는 지금 노드보다 크므로 전부 `to` 초과다 → 오른쪽은 답이 있을 수 없다.\
  코드에서는 `if (cmpFrom > 0) collectRange(node.left, ...)` 와 `if (cmpTo < 0) collectRange(node.right, ...)` 두 줄이 그 판정이다.

- Q: 가지치기가 없으면 왜 O(n) 인가.\
  A: 조건 없이 양쪽을 다 재귀하면 그냥 전체 중위 순회이기 때문이다.\
  범위 밖이라는 사실을 노드를 방문한 **뒤에** 알게 되므로, 답이 0개여도 n 개를 전부 방문한다.\
  100만 개에서 3개를 뽑는 질의도 100만 노드를 훑는다.\
  README 표현대로 "전부 훑고 걸러내도 답은 맞습니다. 다만 O(n)입니다".

- Q: 가지치기가 있으면 왜 O(log n + k) 인가.\
  A: 방문하는 노드가 세 종류로만 나뉘기 때문이다.\
  ① `from` 을 찾아 내려가는 경로 위의 노드 — 최대 높이만큼.\
  ② `to` 를 찾아 내려가는 경로 위의 노드 — 최대 높이만큼.\
  ③ 두 경로 사이에 통째로 들어가는 서브트리들 — 여기 있는 노드는 전부 결과에 담기므로 k 개다.\
  ①②가 O(높이) = 균형이면 O(log n), ③이 O(k) 이므로 합이 O(log n + k) 다.

```
방문 노드의 세 종류 : [35, 65] 를 뽑을 때

                    50   <- 두 경로가 아직 겹쳐 있는 구간
                  /    \
       (from 경로) 30      70  (to 경로)
               /  \    /   \
             20    40 60     80
             ^     ^   ^     ^
             |     |   |     +-- 안 본다 (70 의 오른쪽 전부가 65 초과)
             |     |   +-------- 결과에 담긴다 (k 에 포함)
             |     +------------ 결과에 담긴다 (k 에 포함)
             +------------------ 안 본다 (30 의 왼쪽 전부가 35 미만)

    "본 노드" = from 경로 + to 경로 + 결과 k 개
    결과가 0개여도 두 경로(2 x 높이)만 보고 끝난다
```

- Q: 이 재귀에는 어떤 위험이 있는가.\
  A: 호출 스택 깊이가 트리 높이만큼 쌓인다는 것이다.\
  `inOrder`·`collectRange`·`heightOf` 가 전부 재귀라, 편향 트리에서는 깊이가 n 이 된다.\
  1000개 정렬 입력(높이 1000)은 실제로 통과한다 — `sortedInsertDegenerates` 가 `sorted.height()` 를 부르고 그 안에서 `heightOf` 가 1000 단계 재귀하는데 테스트가 통과하기 때문이다.\
  하지만 같은 입력이 10만~100만 건이면 `StackOverflowError` 가 난다 — 키를 한 개도 못 꺼내고 죽는, 성능이 아니라 정확성의 실패다(정확한 한계 깊이는 원본에 근거 없음 — 내 추론).

**더 생각할 것**

- 재귀를 명시적 스택으로 바꾸면 스택 오버플로는 막을 수 있지만 메모리 O(높이) 는 그대로다.\
  근본 해결은 높이를 낮추는 것(16번 레드블랙 트리)이다.
- `keys()` 는 `ArrayList` 를 만들어 전부 담아 반환한다.\
  게으른 반복자였다면 문제 3의 조기 종료가 실제 이득이 됐을 것이다 — 계약 하나가 응용 문제의 복잡도를 좌우한다.
- 범위 조회는 DB 인덱스의 핵심 기능이다.\
  `WHERE score BETWEEN 35 AND 65` 가 바로 이 가지치기이고, B-트리는 같은 아이디어를 디스크 블록 단위로 한다.
- 가지치기 판정이 `cmpFrom > 0` / `cmpTo < 0` 로 **엄격 부등호**인 것에 주목할 것.\
  `>=` 로 쓰면 `node.key == from` 일 때 왼쪽으로 한 번 더 내려가 헛일을 한다(결과는 맞다).

#### 9. `remove` — 자식이 둘인 노드

- Q: 자식이 둘인 노드를 지울 때 아무 자식이나 올리면 무엇이 깨지는가.\
  A: 탐색 성질이 깨지거나 노드가 통째로 사라진다.\
  자식이 둘이면 올릴 자리는 하나인데 서브트리는 둘이므로, 한쪽을 올리면 다른 쪽을 어디에 붙일지가 남는다.\
  아무 데나 붙이면 "왼쪽 전부 < 나 < 오른쪽 전부"가 무너지고, 그냥 버리면 노드가 사라져 `size` 와 실제 노드 수가 어긋난다.\
  `BinarySearchTreeTest` 의 `assertSound` 가 그 둘을 각각 잡는다 — `assertBstProperty`(순서)와 `countNodes(root) == size`(개수).

- Q: 대신할 수 있는 값이 딱 둘뿐인 이유는 무엇인가.\
  A: 지울 노드의 자리에 앉으려면 "왼쪽 서브트리 전부보다 크고, 오른쪽 서브트리 전부보다 작다"를 만족해야 한다.\
  정렬된 키 목록에서 그 자리를 채울 수 있는 값은 지울 키의 **바로 앞**과 **바로 뒤**뿐이다.\
  바로 앞 = 왼쪽 서브트리의 최대(선행자), 바로 뒤 = 오른쪽 서브트리의 최소(후속자)다.\
  그보다 더 앞의 키를 올리면 왼쪽 서브트리에 그보다 큰 키가 남아 불변식이 깨지고, 더 뒤의 키를 올리면 오른쪽 서브트리에 그보다 작은 키가 남아 깨진다.

```
왜 둘뿐인가 : 정렬된 줄로 펴 보면 자명하다

    20   30   35   40   45   50   60   70   80
              ^^   ^^   ^^
              |    |    +-- 후속자 : 40 바로 뒤
              |    +------- 지울 키 40
              +------------ 선행자 : 40 바로 앞

    40 이 빠진 자리를 메울 수 있는 값은 그 자리의 양옆뿐이다.

    45 를 올리면 : 오른쪽에 남는 것은 50... -> 전부 45 초과 OK
    30 을 올리면 : 왼쪽에 35 가 남는다 -> 35 > 30 -> 깨진다
```

> **선행자(predecessor)** — 그 키 바로 앞(작은 쪽)의 키.\
> 예: 왼쪽 서브트리에서 오른쪽 끝까지 내려가면 나온다.

> **후속자(successor)** — 그 키 바로 다음(큰 쪽)의 키.\
> 예: 오른쪽 서브트리에서 왼쪽 끝까지 내려가면 나오고, 거기는 정의상 왼쪽 자식이 없다.

- Q: 그 값을 가져오면 원래 자리가 왜 더 쉬운 경우로 바뀌는가.\
  A: 후속자는 "오른쪽 서브트리의 최소"라서 **정의상 왼쪽 자식이 없기** 때문이다.\
  왼쪽 자식이 있으면 그것이 더 작으므로 최소가 아니게 된다 — 모순이다.\
  따라서 후속자 노드는 자식이 0개 또는 1개(오른쪽만)이고, 그 노드를 지우는 것은 경우 1 또는 경우 2다.\
  즉 "자식 둘" 문제를 한 번의 값 복사로 "자식 하나 이하" 문제로 **환원**한 것이고, 이 환원은 되풀이되지 않는다.

```java
if (cur.left != null && cur.right != null) {
    Node<K, V> successorParent = cur;
    Node<K, V> successor = cur.right;
    while (successor.left != null) {
        successorParent = successor;
        successor = successor.left;
    }
    cur.key = successor.key;
    cur.value = successor.value;
    parent = successorParent;
    cur = successor;            // 이제 지울 대상은 후속자다
}

Node<K, V> child = (cur.left != null) ? cur.left : cur.right;
if (parent == null) root = child;
else if (parent.left == cur) parent.left = child;
else parent.right = child;
```

- Q: 선행자와 후속자 중 무엇을 골라도 되는 이유는.\
  A: 둘 다 "그 자리에 앉아도 불변식이 유지되는 값"이라는 조건을 똑같이 만족하기 때문이다.\
  구조적으로도 대칭이다 — 후속자는 왼쪽 자식이 없고 선행자는 오른쪽 자식이 없으므로, 어느 쪽을 써도 남은 삭제가 "자식 하나 이하" 경우로 떨어진다.\
  결과 트리의 **모양**은 달라지지만 중위 순회 결과(정렬된 키 목록)는 완전히 같다 — 계약 테스트는 그 목록만 보므로 둘 다 통과한다.\
  impl 은 후속자를 골랐고, 주석에 "여기서는 후속자를 쓴다"라고 그 선택을 명시해 두었다.

> **환원(reduction)** — 어려운 경우를 이미 풀어 둔 쉬운 경우로 바꾸는 것.\
> 예: 자식 둘 삭제를 값 복사 한 번으로 자식 하나 이하 삭제로 바꾸면, 새로 짤 코드가 없다.

**더 생각할 것**

- 항상 후속자만 쓰면 왼쪽이 조금씩 무거워져 트리가 서서히 한쪽으로 기운다는 지적이 있다.\
  선행자와 후속자를 번갈아 쓰는 구현도 있다(원본에 근거 없음 — 내 추론).
- `cur.key = successor.key` 는 **노드가 아니라 내용을 옮기는** 방식이다.\
  바깥에서 노드 참조를 들고 있었다면 그 참조가 가리키는 키가 바뀌어 버린다 — 이 구현은 노드를 밖으로 노출하지 않으므로 안전하다.
- 삭제 후 `cur.left = null; cur.right = null;` 로 떼어낸 노드의 링크를 끊는다.\
  살아 있는 트리가 죽은 노드를 통해 참조되는 일을 막는 위생 처리다.
- 계약 테스트는 "정렬된 결과가 나오는가"만 본다 — README 말대로 그건 정렬해서 내놓기만 해도 통과한다.\
  그래서 `BinarySearchTreeTest` 가 노드를 직접 재귀로 훑어 구조를 검사한다.\
  **테스트가 무엇을 못 보는지**를 알고 그 구멍을 메우는 테스트를 따로 두는 패턴이다.

#### 10. 최악의 입력 — 정렬된 순서로 넣기

- Q: 최악의 입력을 만들어 보라.\
  A: 이미 정렬된 순서로 넣는 것이다 — `for (int i = 0; i < 1000; i++) tree.put(i, ...)`.\
  매 `put` 이 루트에서 오른쪽으로만 끝까지 내려가 잎으로 붙는다.\
  버려지는 후보가 한 번도 없다 — 비교 한 번이 절반을 버리기는커녕 한 개만 버린다.\
  역순(내림차순) 입력도 방향만 반대일 뿐 똑같이 최악이다.

```
편향 트리 : put(0), put(1), put(2), ... put(999)

    [0]
       \
       [1]
          \
          [2]
             \
             [3]
                \
                 ...
                    \
                    [998]
                        \
                        [999]

    왼쪽 가지가 하나도 없다 (테스트 : assertNull(t.root.left))
    높이 = 1000 = 노드 수        (테스트 : assertEquals(1_000, sorted.height()))
    사실상 next 포인터만 있는 연결 리스트다

    비교한 뒤 버리는 후보의 수
        균형 트리 : 비교 1회 -> 후보 절반이 사라진다
        이 트리   : 비교 1회 -> 후보 1개가 사라진다
        이것이 log n 과 n 의 차이 전부다
```

- Q: 1000개를 정렬된 순서로 넣으면 높이가 얼마가 되는가.\
  A: **1000** 이다.\
  테스트 `sortedInsertDegenerates` 가 `assertEquals(1_000, sorted.height(), "정렬 입력에서는 높이가 원소 수와 같아진다. 사실상 연결 리스트다")` 로 못박는다.\
  같은 테스트에서 흩어진 순서(`(i * 617) % 1000`)로 넣은 트리는 높이가 50 미만임을 확인한다.\
  작은 예로는 `correctWhenSkewed` 가 1,2,3,4,5 를 넣어 높이 5 를 확인한다.

- Q: 이후 조회 n 번의 총 비용은 얼마인가.\
  A: 편향 트리에서 키 i 를 찾으려면 i+1 개 노드를 지나야 한다.\
  1000개 키를 각각 한 번씩 조회하면 `1 + 2 + ... + 1000 = 1000 × 1001 / 2 = 500,500` 회 비교다(계산상).\
  일반화하면 `n(n+1)/2` ≈ n^2/2 → **O(n^2)**.\
  조회 하나하나로 보면 평균 O(n/2), 최악 O(n) 이다.

- Q: 균형 잡힌 경우와 비교하면 어떤가.\
  A: 균형 트리의 높이는 log2(1000) ≈ 10 이므로 조회 1000번의 총 비용이 계산상 약 `1000 × 10 = 10,000` 회다.\
  편향 트리의 500,500 회와 비교하면 약 **50배** 차이다.\
  n 이 커질수록 격차가 벌어진다 — n = 100만이면 균형은 약 2 × 10^7, 편향은 약 5 × 10^11 로 계산상 2만 배가 넘는다.\
  게다가 트리를 만드는 `put` 1000번의 비용도 편향에서는 `1 + 2 + ... + 999` ≈ 5 × 10^5 회로 이미 O(n^2) 이다.


- Q: 이걸 왜 이 챕터에서는 고치지 않고 `sortedInsertDegenerates` 테스트로 확인만 하는가.\
  A: 이것이 버그가 아니라 **이 자료구조의 성질**이기 때문이다.\
  올바르게 구현해도 똑같이 나온다 — 테스트 주석이 "이건 버그가 아니라 이 구조의 성질이다. 올바른 구현에서도 그대로 나온다"라고 적어 두었다.\
  고치려면 삽입·삭제마다 트리 모양을 바로잡는 회전과 색칠 규칙이 필요하고, 그것이 16번 레드블랙 트리의 전부다.\
  README 의 이유가 핵심이다 — "무엇을 고치는지 모르면 그 복잡한 회전이 그냥 복잡하기만 합니다".\
  즉 다음 챕터의 복잡함에 **동기를 만들어 주기 위해** 일부러 남겨 둔 결함이다.

> **재균형(rebalancing)** — 삽입·삭제 뒤에 트리 모양을 고쳐 높이를 낮게 유지하는 조작.\
> 예: 레드블랙 트리는 회전과 색 바꾸기로 높이를 항상 2·log2(n+1) 이하로 묶는다.

> **회전(rotation)** — 불변식을 유지한 채 부모-자식 관계를 바꿔 한쪽으로 기운 가지를 펴는 조작.\
> 예: 오른쪽으로만 길어진 세 노드를 가운데 노드를 위로 올려 균형 잡힌 삼각형으로 만든다.

**더 생각할 것**

- 최악의 입력이 "이상한 입력"이 아니라 **가장 흔한 입력**(정렬된 데이터)이라는 점이 무섭다.\
  DB 에서 `ORDER BY id` 로 읽어와 그대로 넣으면 바로 이 모양이 된다.
- 그래서 실무에서 직접 만든 BST 를 쓰는 일은 거의 없다.\
  `TreeMap`(레드블랙), B-트리, 스킵 리스트처럼 균형이 보장된 구조를 쓴다.
- 테스트가 `(i * 7919) % n`, `(i * 617) % 1000`, `(i * 37) % n` 처럼 서로소인 곱수로 키를 흩뿌리는 이유가 이것이다.\
  "치우친 트리는 이 구조의 한계지 알고리즘 문제가 아니다"라고 `mustBeLogarithmic` 주석이 밝혀 둔다.
- 편향은 성능만의 문제가 아니다.\
  재귀 순회(`inOrder`, `heightOf`)의 스택 깊이도 n 이 되어, 규모가 커지면 `StackOverflowError` 라는 정확성 실패로 번진다.

#### 11. `clear()` 가 `root = null` 한 줄인 이유

- Q: `clear()` 가 `root = null` 한 줄로 끝나는 이유는 무엇인가.\
  A: 트리의 모든 노드가 **오직 부모를 통해서만** 도달 가능하기 때문이다.\
  루트를 끊는 순간 트리 전체가 어디에서도 닿을 수 없는 덩어리가 되고, 자바 GC 는 "도달 불가능한 객체"를 회수한다.\
  노드가 서로를 가리키고 있어도 상관없다 — GC 는 참조 카운트가 아니라 루트에서의 도달 가능성으로 판단하기 때문이다.\
  테스트 `clearDetachesRoot` 가 `assertNull(t.root, "부모를 끊으면 아래가 통째로 GC 대상이 된다")` 로 이 설계를 못박는다.

```java
@Override
public void clear() {
    root = null;      // 트리는 부모만 끊으면 아래가 통째로 GC 대상이 된다
    size = 0;
}
```

```
왜 한 줄로 충분한가 : 도달 경로가 하나뿐이다

  before                          after (root = null 한 줄)

  [tree] --root--> 50             [tree] --root--> null
                 /    \
               30      70                  50          <- 여기로 오는 화살표가 없다
              /  \    /  \                /    \
            20   40  60    80           30      70     <- 서로를 가리키지만
                                       /  \    /  \       바깥에서 닿을 수 없다
                                     20   40  60    80

    GC 의 기준 = "GC 루트에서 화살표를 따라 닿을 수 있는가"
    50 에 닿을 길이 사라졌으므로 50 이하 전부가 한꺼번에 회수 대상이다
```

> **도달 가능성(reachability)** — GC 루트(스택 변수·정적 필드 등)에서 참조를 따라가 닿을 수 있는지 여부.\
> 예: 노드끼리 서로 가리켜도 바깥에서 닿을 길이 없으면 그 덩어리 전체가 회수 대상이다.

- Q: 01~04 에서는 참조를 하나하나 끊어야 했는데 여기서는 왜 아닌가.\
  A: 그 구조들은 **배열이 원소를 직접 붙들고 있었기** 때문이다.\
  동적 배열은 `elements` 배열 한 칸 한 칸이 원소 객체를 가리키므로, 배열 자체는 살아 있는 채로 `size` 만 0 으로 만들면 배열 칸에 남은 옛 참조가 그 객체들을 계속 붙잡는다 → 메모리 누수.\
  그래서 `clear()` 에서 칸마다 null 을 넣어 줘야 했다.\
  트리는 다르다 — 원소를 붙잡는 주체가 컬렉션의 배열이 아니라 **다른 노드**이고, 그 노드들도 함께 버려지므로 위에서 한 번 끊으면 아래가 전부 같이 떨어진다.

```
구조가 다르면 정리 방법도 다르다

  동적 배열 : 컬렉션이 원소를 직접 붙잡는다
      elements +-----+-----+-----+-----+
               |  A  |  B  |  C  |  D  |
               +-----+-----+-----+-----+
      size = 0 으로만 두면 배열은 그대로 살아 있고 A~D 도 계속 붙잡힌다
      -> 칸마다 null 을 써 넣어야 한다 (n 번의 작업)

  트리 : 노드가 노드를 붙잡는다
      root -> A -> B, C ...
      root 를 끊으면 A 가 버려지고, A 가 버려지면 A 가 붙잡던 B, C 도 같이 버려진다
      -> 한 번의 작업으로 끝난다
```

- Q: 그래도 `size = 0` 은 왜 필요한가.\
  A: `size` 가 노드 수를 따로 세고 있는 **파생 상태**이기 때문이다.\
  `root` 만 끊고 `size` 를 그대로 두면 `isEmpty()` 가 false 를 돌려주고, `keys()` 가 `new ArrayList<>(size)` 로 엉뚱한 크기를 잡으며, `kthSmallest` 의 범위 검사가 틀린 판단을 한다.\
  구조와 그 구조를 요약한 값이 항상 같이 움직여야 한다는 것이 여기서의 불변식이다.\
  `BinarySearchTreeTest.assertSound` 가 `countNodes(root) == size` 로 매번 그것을 확인한다.

**더 생각할 것**

- 이 말이 "트리는 메모리 누수가 없다"는 뜻은 아니다.\
  바깥 코드가 노드나 키 객체 참조를 따로 들고 있으면 그것이 붙잡혀 남는다.
- C++ 처럼 수동으로 메모리를 관리하는 언어였다면 `root = nullptr` 로는 끝나지 않는다.\
  후위 순회로 모든 노드를 직접 해제해야 한다 — GC 언어라서 한 줄인 것이다.
- 그래서 "`clear` 가 O(1) 이다"라는 말도 정확히는 **호출자 입장에서** O(1) 이라는 뜻이다.\
  회수 비용은 GC 가 나중에 치른다.
- 같은 이유로 노드 수가 아주 많으면 `clear()` 직후에 GC 가 크게 한 번 도는 일이 생긴다.\
  지연이 중요한 시스템에서는 그 순간이 튀는 지점이 된다(원본에 근거 없음 — 내 추론).

#### 12. 07-heap 으로의 연결

- Q: 전체 순서를 유지하는 이 구조의 비용이 아까워지는 상황은 언제인가.\
  A: 질문이 "가장 큰 것(또는 가장 작은 것) 하나"뿐일 때다.\
  BST 는 모든 키 쌍의 대소 관계를 구조에 새겨 두고, 그 대가를 삽입·삭제마다 O(높이) 로 치른다.\
  그런데 우선순위 큐 같은 워크로드는 "다음에 처리할 하나"만 물으므로, 나머지 키들 사이의 순서를 유지한 비용이 전부 버려진다.\
  게다가 BST 로 최대를 꺼내려면 오른쪽 끝까지 내려가 `remove` 까지 해야 하고, 그 과정에서 트리가 한쪽으로 기울기까지 한다.

> **우선순위 큐(priority queue)** — 넣은 순서가 아니라 우선순위가 가장 높은 것부터 꺼내는 자료구조.\
> 예: 작업 스케줄러는 "다음에 실행할 작업 하나"만 알면 되고 나머지 작업들끼리의 순서는 알 필요가 없다.

- Q: "가장 큰 것만 빨리 알면 되는" 요구에는 왜 부분적인 순서만 유지하는 구조가 더 맞는가.\
  A: 유지해야 할 불변식이 훨씬 약해서 유지 비용도 싸기 때문이다.\
  힙의 규칙은 "부모가 자식보다 크다(또는 작다)" 하나뿐이고, **형제끼리의 순서는 아무 상관이 없다.**\
  그러면 최대는 언제나 루트에 있으므로 조회가 O(1) 이고, 넣고 빼는 것은 한 경로만 타고 오르내리면 되므로 O(log n) 이다.\
  대신 포기하는 것이 명확하다 — 정렬 순회도, 범위 조회도, floor/ceiling 도 못 한다.

```
같은 7개 키, 두 구조가 유지하는 것의 차이

  BST — 전체 순서                     힙 — 부분 순서 (최대 힙)
            50                                  80
          /    \                              /    \
        30      70                          70      60
       /  \    /   \                       /  \    /   \
     20    40 60     80                  30    40 20     50

   왼쪽 전부 < 나 < 오른쪽 전부          부모 > 두 자식 (형제끼리는 무관)
   중위 순회 = 20 30 40 50 60 70 80      순회해도 정렬이 아니다
   최대를 찾으려면 오른쪽 끝까지 = O(h)   최대는 언제나 루트 = O(1)
   범위·이웃·정렬 전부 가능              그런 질문에는 답하지 못한다

   유지하는 약속이 강할수록 답할 수 있는 질문이 많고, 그만큼 유지 비용도 비싸다
```

- Q: 이 세 구조(해시맵 · BST · 힙)를 하나의 축으로 놓으면 어떻게 보이는가.\
  A: **"순서를 얼마나 유지하는가"** 라는 하나의 축 위의 세 지점이다.

  | | 유지하는 순서 | get(k) | 최소/최대 | 범위·정렬 |
  |---|---|---|---|---|
  | 해시맵(05) | 없음 (일부러 흩뿌린다) | O(1) | O(n) | O(n log n) |
  | 힙(07) | 부분 (부모-자식만) | O(n) | **O(1)** 꺼내기 O(log n) | 불가 |
  | BST(06) | 전체 | O(log n) | O(log n) | O(log n + k) |

  순서를 많이 유지할수록 답할 수 있는 질문이 늘고, 그만큼 갱신 비용을 더 낸다.\
  README 의 문장이 그 요약이다 — "무엇을 물을 것인지가 자료구조를 정한다".

**더 생각할 것**

- 힙은 배열 하나로 구현된다 — 포인터가 없고 캐시 지역성이 좋다.\
  같은 "트리"라도 저장 방식이 달라지면 성능 성격이 완전히 달라진다.
- "가장 큰 k 개"만 필요할 때도 전체 정렬(O(n log n))보다 크기 k 짜리 힙(O(n log k))이 싸다.\
  전체 순서를 만들지 않는다는 선택이 그대로 비용 절감이 된다.
- 반대로 힙으로는 이 챕터의 세 문제를 하나도 못 푼다.\
  `closestKey`, `rangeSum`, `kthSmallest` 전부 전체 순서를 요구하기 때문이다.
- 이 챕터의 BST 는 균형이 보장되지 않는다는 결함을 안고 끝난다.\
  그 결함을 고치는 것이 16번 레드블랙 트리이고, 디스크로 확장한 것이 15번 B-트리, 확률로 균형을 얻는 것이 12번 스킵 리스트다.\
  넷 다 같은 `SortedMap` 계약을 구현하므로 여기서 짠 `BSTProblems` 코드는 그대로 돌아간다.
