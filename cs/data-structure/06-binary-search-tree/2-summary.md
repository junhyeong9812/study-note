## 한눈에 — 쉽게 말하면

**비유: 스무고개(업다운 게임).**\
1~100 중 숫자 하나를 맞힐 때 "50보다 커? 작아?"라고 물으면\
한 번의 질문으로 후보 절반이 사라진다.

**이진 탐색 트리는 이 게임과 똑같은 구조다.**\
질문 하나하나를 아예 칸으로 만들어 둔 게임판이 트리다.

- 모든 칸(노드)이 규칙 하나만 지킨다: **내 왼쪽 아래는 전부 나보다 작고, 오른쪽 아래는 전부 나보다 크다.**

> **노드(node)** — 트리를 이루는 칸 하나.\
> 예: 값과 왼쪽/오른쪽 연결을 담은 상자 하나가 노드다.

> **탐색 성질(BST invariant)** — "왼쪽 아래는 전부 나보다 작고, 오른쪽 아래는 전부 나보다 크다"는 규칙.\
> 예: 이 규칙 하나 덕에 한 칸에서 비교 한 번이면 반대쪽 절반은 쳐다볼 필요가 없다.

- 그래서 찾을 때 한 칸에서 비교 한 번이면 반대쪽 절반은 쳐다볼 필요가 없다.
- 왼쪽 → 자기 → 오른쪽 순서로 읽으면 저절로 **작은 수부터 큰 수 순서**가 나온다.\
  (해시맵은 못 하는 것)

> **해시맵(hash map)** — 키를 계산으로 바로 자리에 꽂는 자료구조.\
> 예: 평균 O(1)로 빠르지만 "순서"라는 개념이 없어서 정렬 순회·범위 조회를 못 한다.

> **중위 순회(in-order traversal)** — 왼쪽 → 자기 → 오른쪽 순서로 트리를 도는 방법.\
> 예: BST에서는 이 순서가 곧 정렬 순서라, 따로 정렬하지 않아도 작은 키부터 나온다.

- 약점: 넣는 순서가 나쁘면(이미 정렬된 순서) 트리가 한 줄로 늘어져서 게임의 이점이 사라진다.
- 실무에서도 같은 구조를 쓴다: 자바 `TreeMap`, DB 인덱스(범위 검색 `BETWEEN`)가 이 "정렬 유지 트리" 계열이다.

```text
        "50보다 작아?"          [50]
                              /      \
       예 -> 왼쪽만 본다   [30]      [70]   <- 아니오면 이쪽만
                          /   \      /   \
                       [20] [40]  [60] [80]
    비교 1번 = 후보 절반 삭제
```

### 구조

```
BinarySearchTree — 노드마다 "왼쪽 전부가 나보다 작고, 오른쪽 전부가 나보다 크다"만 지킨다
+---------------------------+
| root ---+                 |
| size = 7|                 |
+---------|-----------------+
          v
                          +--------+
                          | key 50 |
                          | value  |
                          +--------+
                     left /        \ right
                    +--------+    +--------+
                    | key 30 |    | key 70 |
                    +--------+    +--------+
                    /       \      /       \
              +------+  +------+ +------+ +------+
              |  20  |  |  40  | |  60  | |  80  |
              +------+  +------+ +------+ +------+

    불변식 (모든 노드에서 성립)
        왼쪽 서브트리의 모든 키  <  자기 키  <  오른쪽 서브트리의 모든 키
        "왼쪽 자식 하나가 작다"가 아니라 "왼쪽 전체가 작다"이다.
        50 의 왼쪽에는 20, 30, 40 이 전부 들어 있고 그 중 하나도 50 을 넘지 않는다

    Node 에 parent 필드가 없다 -> 위로 올라갈 길이 없다.
    그래서 모든 연산이 root 에서 아래로만 내려가고, 링크를 고쳐야 하면 parent 를 손에 들고 간다

    이 불변식이 주는 것
        비교 한 번에 남은 후보의 절반을 버린다 -> 균형 잡히면 O(log n)
        중위 순회(왼쪽 -> 자기 -> 오른쪽)가 그대로 정렬 순서다   20 30 40 50 60 70 80
    해시맵에는 없는 성질이 바로 이 두 번째다 — 순서, 범위, 이웃 키를 물을 수 있다
```

### 동작 — 탐색

**언제 쓰나** — "이 키 있어?"(get/containsKey), "45 근처의 키는?"(floorKey/ceilingKey), "35~65 사이 전부 줘"(keysInRange).

```
findNode(key) : 루트에서 비교 결과대로 한쪽으로만 내려간다. 되돌아오지 않는다
    get(40)
                    [50]        40 < 50 -> 왼쪽
                    /
                 [30]           40 > 30 -> 오른쪽
                     \
                     [40]       같다 -> 찾음
    비용 = 뿌리에서 그 노드까지의 깊이

    firstKey() : 왼쪽 끝까지 내려간다 = 20      lastKey() : 오른쪽 끝까지 = 80
    height()   : 빈 트리 0, 노드 하나 1 (-1 규약이 아니다)

floorKey(45) : "45 이하 중 가장 큰 키". 후보(best)를 기억하면서 내려간다
                    [50]     45 < 50  -> 왼쪽. 50 은 45 보다 크니 답이 될 수 없다 (best 갱신 없음)
                    /
                 [30]        45 > 30  -> best = 30 으로 두고 오른쪽 (더 큰 후보가 있을 수 있다)
                     \
                     [40]    45 > 40  -> best = 40 으로 갱신하고 오른쪽
                         \
                         null         길이 끝났다 -> 답은 마지막 best = 40
    ceilingKey 는 완전 대칭 — 오른쪽으로 갈 때는 후보를 남기지 않고, 왼쪽으로 갈 때 남긴다

keysInRange(from, to) : 가지치기가 붙은 중위 순회. 양 끝 모두 포함
    node.key > from        이면 왼쪽 재귀    (아니면 왼쪽 전체가 from 미만 -> 통째로 버린다)
    from <= node.key <= to 이면 수집
    node.key < to          이면 오른쪽 재귀  (아니면 오른쪽 전체가 to 초과 -> 통째로 버린다)

    keysInRange(35, 65) 에서 잘려 나가는 가지
                        [50]
                       /    \
                    [30]    [70]        70 > 65 -> 70 의 오른쪽(80)은 보지도 않는다
                   /    \    /
                [20]  [40] [60]
                  ^ 20 < 35 -> 20 의 왼쪽 서브트리 전체를 버린다
    -> O(log n + 결과 개수). 전체를 훑어 거르는 것과 다르다
```

**그림에서 일어난 일 (쉽게)**
1. get(40): 갈림길마다 "크다/작다" 한 번 묻고 한쪽으로만 내려갔다.\
   왔던 길을 되돌아가지 않는다.
2. floorKey(45): 정확히 45가 없어도 된다.\
   내려가면서 "45 이하인 것 중 지금까지 최고 기록(best)"을 메모해 두고, 길이 끝나면 그 메모가 답이다.
3. keysInRange(35, 65): 범위 밖이 확실한 가지는 **들어가 보지도 않고 통째로 건너뛴다**(가지치기).

> **가지치기(pruning)** — 답이 있을 수 없는 쪽을 아예 탐색하지 않는 것.\
> 예: 지금 노드가 35보다 작으면 그 왼쪽 서브트리는 전부 35 미만이라, 한 칸도 안 들어가고 건너뛴다.

> **floorKey / ceilingKey** — floor는 "그 값 이하 중 가장 큰 키", ceiling은 "그 값 이상 중 가장 작은 키".\
> 예: 정확히 45가 없어도 `floorKey(45)` 는 40 을, `ceilingKey(45)` 는 50 을 돌려준다.

**비용** — 전부 "루트에서 한 줄로 내려가는 길이"만큼 = 트리 높이 = 균형 잡히면 O(log n).

### 동작 — 추가

**언제 쓰나** — 새 키-값을 넣을 때(put).\
이미 있는 키면 값만 바꾼다.

```
put(key, value) : 내려갈 자리가 없을 때까지 내려가서, 새 노드는 언제나 잎(leaf)으로 붙인다
    put(45)
                [50]        45 < 50 -> parent = 50, 왼쪽으로
                /
             [30]           45 > 30 -> parent = 30, 오른쪽으로
                 \
                 [40]       45 > 40 -> parent = 40, 오른쪽으로
                     \
                     null   빈 자리다 -> parent.right = new Node(45)

    after        [50]
                 /
              [30]
                  \
                  [40]
                      \
                      [45]      <- 새 노드. 기존 노드는 하나도 움직이지 않았다

    같은 키를 만나면 value 만 교체하고 옛 값을 돌려준다 (size 불변, 구조 불변)
    회전도 재균형도 없다 -> 넣는 순서가 트리 모양을 그대로 결정한다

편향(최악) — 이미 정렬된 순서로 넣으면
    put(10), put(20), put(30), put(40)
        [10]
            \
            [20]            내려갈 때마다 항상 오른쪽. 버려지는 후보가 없다
                \
                [30]        높이 = n. 사실상 연결 리스트다 -> 모든 연산이 O(n)
                    \
                    [40]
    "평균 O(log n)"은 입력이 뒤섞여 있을 때의 이야기다.
    이 편향을 회전으로 막는 것이 16 장 레드-블랙 트리다
```

**그림에서 일어난 일 (쉽게)**
1. 탐색과 똑같이 내려간다.\
   다른 점은 하나 — 빈 자리(null)를 만날 때까지 간다.
2. 그 빈 자리에 새 노드를 붙인다.\
   **기존 노드는 하나도 안 움직인다.**\
   새 식구는 항상 맨 끝(잎)에 들어온다.
3. 함정: 10, 20, 30, 40처럼 이미 정렬된 순서로 넣으면 매번 같은 방향으로만 붙어서 한 줄이 된다(편향).

> **잎(leaf)** — 자식이 하나도 없는 맨 끝 노드.\
> 예: 새로 넣은 노드는 언제나 잎으로 들어오고, 기존 노드는 하나도 안 움직인다.

> **편향(skew)** — 트리가 한쪽으로만 길게 늘어진 상태.\
> 예: 10, 20, 30, 40 순서로 넣으면 오른쪽으로만 붙어 사실상 연결 리스트가 되고, 스무고개의 "절반 버리기"가 안 된다.

**비용** — 내려간 길이만큼 = O(높이).\
균형이면 O(log n), 편향이면 O(n).

### 동작 — 삭제

**언제 쓰나** — 키 하나를 지울 때(remove).\
지운 자리를 어떻게 메우느냐가 문제의 전부다.

```
remove(key) : 자식 수에 따라 세 갈래다. parent 를 손에 들고 내려가야 링크를 고칠 수 있다

[1] 자식 0개 (잎) : 부모가 가리키던 자리를 null 로 바꾼다
    remove(20)
            [30]                    [30]
           /    \        ->            \
        [20]    [40]                   [40]

[2] 자식 1개 : 그 자식을 부모에 직접 이어 붙인다 (한 칸 끌어올리기)
    remove(20)
            [30]                    [30]
            /                       /
         [20]           ->       [25]
             \
             [25]
    child = (cur.left != null) ? cur.left : cur.right;
    parent == null ? root = child : (부모가 cur 을 가리키던 쪽) = child;
    자식이 하나면 그 자식을 통째로 올려도 불변식이 깨지지 않는다 — 부등호 방향이 그대로다

[3] 자식 2개 : 자리를 비울 수가 없다. 대신 "그 자리에 앉아도 되는 키"를 데려온다
    remove(30)
                [30]                후속자(successor) 찾는 길
               /    \               = 오른쪽 서브트리의 최소
            [20]    [40]              cur.right = 40 에서 왼쪽 끝까지
                    /   \                 [40]
                 [35]   [50]              /
                                       [35]   <- 왼쪽 자식이 없다. successor = 35

    (1) cur.key = successor.key;  cur.value = successor.value;   <- 값만 복사한다
                [35]                    노드 객체는 그대로 살아 있고 안의 내용만 바뀐다
               /    \
            [20]    [40]
                    /   \
                 [35]   [50]        <- 아직 남아 있는 중복. 이걸 지워야 끝난다

    (2) 삭제 대상을 successor 노드로 바꿔치고 [1] / [2] 로 처리한다
        후속자는 정의상 왼쪽 자식이 없다 -> 자식이 0개나 1개다 -> [3] 이 되풀이되지 않는다

    after       [35]
               /    \
            [20]    [40]
                        \
                        [50]

    왜 하필 "오른쪽 서브트리의 최소"인가
        그 키만이 왼쪽 전부보다 크면서 오른쪽 나머지 전부보다 작다.
        즉 불변식을 깨지 않고 그 자리에 앉을 수 있는 후보다 (대칭으로 왼쪽 서브트리의 최대도 가능)
```

**그림에서 일어난 일 (쉽게)** — 지울 노드의 자식 수에 따라 세 갈래.
1. 자식 0개: 그냥 떼어낸다.\
   부모의 연결만 끊으면(null) 끝.
2. 자식 1개: 그 자식을 한 칸 끌어올려 부모에 직접 잇는다.\
   줄이 하나뿐이라 순서가 안 깨진다.
3. 자식 2개: 자리를 비우면 안 되니 **대타를 데려온다** — 지울 키 바로 다음으로 큰 키(후속자).\
   대타의 값을 원래 자리에 복사한 뒤, 대타가 있던 노드를 지운다.\
   대타는 왼쪽 자식이 없다는 게 보장되니 그 삭제는 다시 1번 또는 2번 케이스다 — 무한 반복이 안 된다.

> **후속자(successor)** — 그 키 바로 다음으로 큰 키.\
> 예: 오른쪽 서브트리에서 왼쪽 끝까지 가면 나온다 — 거기는 왼쪽 자식이 없으므로 지우기가 쉬운 케이스로 바뀐다.

**비용** — 지울 노드까지 내려가기 + (케이스 3이면) 후속자까지 더 내려가기 = O(높이) = 균형이면 O(log n).

### 문제 1. 가장 가까운 키

> 문제 설명: `target` 과 차이가 가장 작은 키를 반환한다. 비었으면 `NoSuchElementException`.
> 양쪽 차이가 같으면 작은 쪽을 반환한다.
> `{1, 5, 9}, target=6` -> `5`
> `{1, 5, 9}, target=7` -> `5` (차이 2 대 2 이므로 작은 쪽)
> `{1, 5, 9}, target=0` -> `1`
> 함정 — 10만 개 × 10만 질의 시간 제한이 있다. 전부 훑어 최소 차이를 찾으면 O(n) 이다.

> 둘 중 하나가 없는 경우를 잊지 마라.
> 시그니처: `static Integer closestKey(SortedMap<Integer, ?> map, int target)` — O(log n) 이어야 한다.

## 용어 풀이

- **노드(node)**: 트리를 이루는 칸 하나.\
  키·값과 왼쪽/오른쪽 자식으로 가는 연결을 담는다.
- **루트(root)**: 트리의 맨 꼭대기 노드.\
  모든 연산이 여기서 출발한다.
- **잎(leaf)**: 자식이 하나도 없는 맨 끝 노드.
- **서브트리(subtree)**: 어떤 노드와 그 아래에 매달린 전부를 하나의 작은 트리로 본 것.
- **부모/자식(parent/child)**: 바로 위에서 나를 가리키는 노드가 부모, 내가 가리키는 아래 노드가 자식.
- **불변식(invariant)**: 어떤 조작을 해도 항상 참이어야 하는 규칙.\
  여기서는 "왼쪽 전체 < 자기 < 오른쪽 전체".
- **참조/포인터(reference/pointer)**: 다른 노드가 "어디 있는지"를 가리키는 값. left/right 필드가 그것이다.
- **중위 순회(in-order traversal)**: 왼쪽 → 자기 → 오른쪽 순서로 트리를 도는 방법.\
  BST에서는 이 순서가 곧 정렬 순서다.
- **재귀(recursion)**: 함수가 자기 자신을 다시 부르는 방식.\
  "서브트리도 똑같은 트리다"라는 성질 덕에 자연스럽다.
- **O(log n) / O(n)**: 데이터가 n개일 때 걸리는 일의 양.\
  O(log n)은 매번 절반씩 버려서 n이 100만이어도 약 20번, O(n)은 전부 다 보는 것.
- **편향(skew)**: 트리가 한쪽으로만 길게 늘어진 상태.\
  사실상 연결 리스트가 되어 O(n)으로 느려진다.
- **후속자(successor)**: 어떤 키 바로 다음으로 큰 키.\
  자식 2개인 노드를 지울 때 그 자리를 대신 채우는 후보.
- **floorKey / ceilingKey**: floor는 "그 값 이하 중 가장 큰 키", ceiling은 "그 값 이상 중 가장 작은 키".\
  정확히 일치하는 키가 없어도 이웃을 찾아 준다.
- **가지치기(pruning)**: 답이 있을 수 없는 가지를 아예 들어가지 않고 통째로 건너뛰는 것. keysInRange가 한다.
- **회전(rotation)**: 불변식을 유지하면서 노드들의 부모-자식 관계를 바꿔 트리 모양을 고치는 조작.\
  편향을 막는 도구(16장 레드-블랙 트리).
- **해시맵(hash map)**: 키를 해시 함수로 바꿔 자리를 정하는 자료구조.\
  평균 O(1)로 빠르지만 키의 순서·범위 질의는 못 한다.
- **연결 리스트(linked list)**: 노드가 다음 노드 하나만 가리키며 한 줄로 이어진 구조.\
  편향된 BST가 이 꼴이 된다.
