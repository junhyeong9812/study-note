### B. 자료구조 특성

#### 1. 일관된 해싱이 왜 필요한가

- Q: 05번 해시맵의 `hash(key) % N` 을 서버 목록에 그대로 쓰면 무엇이 안 되는가?\
  A: **서버 한 대가 죽는 순간 거의 전부가 자리를 옮긴다**는 것이 안 고쳐진다.

```
키 10만, 서버 10대. node-7 이 죽었다.

  ModuloSharding              89,905 개가 옮겨간다  (89.9%)
  ConsistentHashRing v=1      11,161 개
  ConsistentHashRing v=100    12,044 개            (12.0%)
  ConsistentHashRing v=500    10,288 개

  MovementTest.removingAMiddleNode 가 네 값을 전부 assertEquals 로 못 박는다.
  (README 표에는 89,905 와 12,044 만 있다. 11,161 과 10,288 은 테스트에만 있다.)
```

> **일관된 해싱(consistent hashing)** — 노드와 키를 같은 원 위에 올리고 키가 시계 방향으로 처음 만나는 노드가 그 키를 맡는 배정 방식.\
> 예: 노드가 하나 빠지면 그 노드가 맡던 구간만 다음 노드로 넘어가고 나머지 키는 그대로다.

> **모듈로 샤딩(modulo sharding)** — `hash(key) % N` 으로 담당 서버를 정하는 방식.\
> 예: 서버가 10대에서 9대가 되면 나눗셈의 나머지가 통째로 달라져 약 90%의 키가 자리를 옮긴다.

- Q: 왜 89.9% 인가?\
  A: **N 이 바뀌면 모든 키의 계산식이 바뀌기 때문**이다.\
  `h % 10` 으로 정해져 있던 자리가 `h % 9` 로 바뀌므로, 두 값이 우연히 같은 키만 제자리에 남는다.\
  우연히 같을 확률이 대략 `1/9` 이므로 남는 키가 약 11,111개, 움직이는 키가 약 88,889개 — 실측 89,905 와 거의 같다.\
  즉 **거의 전부가 움직이는 것이 정상 동작**이다. 버그가 아니다.
- Q: 맵 안에서는 맞던 식이 서버에서는 왜 틀리는가 — "다시 계산하면 된다"가 여기서는 무엇이 되는가?\
  A: 해시맵 안에서 리사이즈는 **배열 하나를 새로 만들어 전부 다시 넣는 일**이고, 그것이 메모리 안에서 마이크로초 단위로 끝난다.\
  같은 일이 서버 클러스터에서는 **키 9만 개가 캐시 미스를 내고 원본 저장소로 몰려가는 일**이 된다 — 캐시가 비고, 데이터를 다시 끌어오고, 그 사이 원본이 다 맞는다.\
  서버 한 대가 죽었는데 열 대가 전부 무너지는 이유가 이것이다.\
  즉 같은 식인데 **비용의 단위가 다르다** — 맵에서는 CPU 시간, 클러스터에서는 네트워크·장애 전파다.

> **캐시 스탬피드(cache stampede)** — 캐시가 한꺼번에 비면서 요청이 전부 원본 저장소로 몰리는 현상.\
> 예: 서버 한 대가 죽어 키 9만 개의 담당이 바뀌면 그 9만 개가 동시에 원본을 때린다.

- Q: 차이가 "N이 식 안에 있느냐"라는 말을 자기 말로 풀면?\
  A: **배정 규칙이 무엇에 의존하는가**의 차이다.

```
  모듈로        자리 = f(키, N)          N 이 규칙의 입력이다
                                         -> N 이 1 바뀌면 모든 키의 답이 바뀔 수 있다

  일관된 해싱   자리 = "키의 위치에서 시계 방향으로 처음 만나는 노드"
                                         -> 규칙 안에 N 이 없다. 자리들의 배치만 있다
                                         -> 노드 하나를 빼면 그 노드의 자리만 사라진다
                                         -> 그 자리가 맡던 구간만 다음 노드로 넘어간다
```

```java
// ModuloSharding.getNode — N(= nodes.size()) 이 식 안에 있다
return nodes.get(Hashing.bucketHash(key) % nodes.size());

// ConsistentHashRing.getNode — N 이 없다. 자리 배치와 "다음"만 있다
Map.Entry<Long, String> entry = ring.ceilingEntry(hash.position(key));
return entry != null ? entry.getValue() : ring.firstEntry().getValue();
```

- 이 차이가 만드는 것이 질문 6의 등식이다 — **옮겨간 키의 집합 = 죽은 노드가 맡던 키의 집합**.\
  모듈로는 node-9 가 맡던 9,996개 때문에 89,941개를 움직인다 — 나머지 약 8만 개는 **이유 없는 이동**이다.\
  (9,996 과 89,941 은 `assertEquals` 로 단언되고, "8만"은 그 둘의 차 79,945 를 어림한 값이다. 테스트가 단언하는 것은 `moduloMoved > 8 * moduloShare` 다.)

**더 생각할 것**

- 같은 공식이 문맥에 따라 옳기도 하고 재앙이기도 하다.\
  "해시맵에서 배운 것을 분산 시스템에 그대로 옮기면 안 된다"는 이 장의 첫 문장이다.
- 이 장이 재는 것은 **속도가 아니라 이동량**이다(질문 2).\
  자료구조 장에서 재는 값이 처음으로 바뀌는 자리다.
- 모듈로를 쓰면서 이동을 줄이는 길도 있다 — 노드 수를 고정된 큰 수(예: 4096 슬롯)로 두고 슬롯을 노드에 배정하는 방식이다.\
  그것이 사실상 "자리 배치"를 명시적으로 관리하는 것이고, Redis Cluster 의 해시 슬롯이 그 형태다(원본에 근거 없음 — 내 추론).

#### 2. 어떤 데이터·접근 패턴에 적합하고 언제 쓰면 안 되는가

- Q: 어떤 데이터·접근 패턴에 적합한가?\
  A: **노드 집합이 바뀌는데 키의 담당은 최대한 안 흔들려야 하는** 곳이다.\
  분산 캐시(memcached·Redis), CDN 의 엣지 선택, 샤딩된 저장소, 메시지 파티셔닝이 그 모양이다.\
  특히 **노드가 예고 없이 죽고 살아나는** 환경일수록 이득이 크다 — 이동량이 `1/N` 로 묶인다.
> **이동량(movement)** — 노드 집합이 바뀐 뒤 담당 노드가 달라진 키의 수.\
> 예: `RingMetrics.moved(before, after)` 가 두 배정표를 맞대 그 수를 센다.

- Q: 언제 쓰면 안 되는가?\
  A: 셋이다.\
  첫째, **노드가 절대 안 바뀌는** 곳 — 그러면 모듈로가 더 싸고 분포도 더 고르다(모듈로의 불균형 비가 1.05 미만이라고 단언되어 있다).\
  둘째, **정확한 비율 배분이 계약인** 곳 — 자리를 무작위로 찍는 이상 오차가 남는다(질문 5, 한계 6).\
  셋째, **키가 특정 노드에 있어야 하는** 곳 — 배정이 해시로 정해지므로 "이 키는 저 노드에"를 지정할 수 없다(원본에 근거 없음 — 내 추론).
- Q: 재는 것이 속도가 아니라 이동량인 이유는?\
  A: **비용이 조회에 있지 않고 재배치에 있기 때문**이다.\
  `getNode` 는 어느 구현이든 마이크로초 단위다 — 모듈로는 나눗셈 한 번, 원은 `TreeMap` 탐색 한 번이다.\
  진짜 비용은 담당이 바뀐 뒤에 일어나는 일(캐시 미스, 데이터 이관, 원본 부하)이고 그 양은 **옮겨간 키의 수**에 비례한다.\
  그래서 이 장의 모든 측정이 `RingMetrics.moved(before, after)` 로 키 수를 세는 형태다.

> **가상 노드(virtual node)** — 노드 하나를 원 위 여러 자리에 올려 담당 구간을 잘게 흩는 것.\
> 예: `node-0#0`, `node-0#1`, … 처럼 이름에 번호를 붙여 해시하면 같은 노드가 원 위 100곳에 선다.

- Q: 점프 해시처럼 가운데 노드를 못 빼는 제약이 어떤 환경에서 치명적이고 어떤 환경에서는 상관없는가?\
  A: **아무 노드나 죽을 수 있는 환경**에서는 치명적이고, **번호가 곧 규모인 환경**에서는 상관없다.

```
  치명적인 곳                              상관없는 곳
  ------------------------------------     --------------------------------------
  물리 서버 한 대가 아무 때나 죽는다        오토스케일링 — 뒤에서 늘리고 뒤에서 줄인다
  장애 노드를 즉시 제외해야 한다            샤드 수를 계획적으로 N -> N+1 로 바꾼다
  노드가 개별 신원(이름)을 갖는다           노드가 번호 0..N-1 로만 구별된다

  점프 해시는 번호가 0..N-1 로 이어져야 한다. 가운데를 빼면 뒤가 전부 당겨진다.
  목록을 밀어 흉내내면 28,682 개(28.7%)가 움직인다 — 1/N 인 10,000 개가 아니다.
      assertEquals(28_682, moved);
      assertTrue(moved > 25_000, "가운데 제거를 흉내내면 1/N 이 아니다");
```

- 그래서 이 구현은 되는 척하지 않고 예외를 던진다(질문 5의 마지막 항목).

**더 생각할 것**

- "적합한가"의 기준이 성능이 아니라 **운영 환경의 모양**이라는 것이 이 장의 특징이다.\
  같은 알고리즘이 오토스케일링 환경에서는 최선이고 장애 대응 환경에서는 못 쓴다.
- 이동량을 줄이는 것과 분포를 고르게 하는 것은 **다른 목표**다.\
  점프 해시는 분포가 원보다 좋은데(질문 5) 가운데 제거를 못 한다 — 한 축을 사면 다른 축을 낸다.
- 실무에서는 "이동량"이 곧 복구 시간이다.\
  12%와 90%의 차이는 그래프에서 스파이크의 높이로 나타난다(원본에 근거 없음 — 내 추론).

#### 3. 핵심 연산의 비용이 왜 그런가

- Q: `getNode` 가 왜 O(log(자리 수))인가?\
  A: **정렬된 자리 목록에서 "이 값 이상인 첫 자리"를 찾는 일**이고, 그것이 06번 BST 의 `ceilingKey` 이기 때문이다.

```java
Map.Entry<Long, String> entry = ring.ceilingEntry(hash.position(key));
return entry != null ? entry.getValue() : ring.firstEntry().getValue();
//                                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^ 원을 닫는 한 줄
```

```
원 (0 부터 2^32) 을 직선으로 펴면 정렬된 자리 목록이다

  자리:  100 ---- 900 ---- 2500 ---- 4000 ---- ... ---- 4,294,000,000
          A        B         C         A                     B
                     ^ 키 k 의 위치가 여기(1200)면
                       ceilingEntry(1200) = 2500 -> C 가 맡는다

  키가 마지막 자리보다 뒤에 있으면 ceilingEntry 가 null 이다
      -> 첫 자리로 되감는다 = **원이 닫힌다**
      (ConsistentHashRingTest 가 되감기가 필요한 키를 270개 세어 단언한다)

  TreeMap 은 레드블랙 트리라 탐색이 O(log(자리 수)) 다.
  자리 수 = 노드 수 x 가상 노드 수이므로, v=100 에 노드 10대면 1000개 -> 약 10걸음.
```

> **후속자 탐색(`ceilingKey`)** — 정렬된 키 목록에서 주어진 값 **이상**인 첫 키를 찾는 연산.\
> 예: 06번 BST 의 그 연산이 여기서는 "키의 위치에서 시계 방향으로 처음 만나는 자리"가 된다.

- Q: "원"이라는 것이 코드에서 실제로는 규칙 몇 줄인가?\
  A: **한 줄**이다 — `entry != null ? ... : ring.firstEntry().getValue()` 의 뒤쪽 절반.\
  자료구조는 그냥 정렬된 `TreeMap` 이고, "마지막에서 처음으로 돌아온다"는 그 한 줄이 직선을 원으로 만든다.\
  이 사실이 중요한 이유는, 구현할 때 **그 한 줄을 빠뜨려도 대부분의 키에서 정상 동작**하기 때문이다 — 마지막 자리 뒤에 떨어진 키에서만 `null` 이 나온다.
- Q: `addNode`/`removeNode` 가 왜 가상 노드 수에 비례하는가?\
  A: **자리를 하나씩 올리고 하나씩 지우기 때문**이다.

```java
// addSlots — count 개의 자리를 만든다
for (int i = 0; i < count; i++) {
    ring.put(hash.position(virtualName(node, i)), node);
}
placed.put(node, count);

// removeNode — 같은 이름 규칙으로 자리를 다시 계산해 지운다
for (int i = 0; i < count; i++) {
    long position = hash.position(virtualName(node, i));
    if (node.equals(ring.get(position))) {     // 남의 자리를 뺏지 않는다
        ring.remove(position);
    }
}
```

- 즉 `O(v log(자리 수))` 다 — 자리 v 개를 `TreeMap` 에 넣고 빼므로 넣기·빼기마다 `log` 가 붙는다.
- `if (node.equals(ring.get(position)))` 한 줄의 의미: 서로 다른 가상 이름이 **같은 자리로 해시될 수 있고**, 그때 나중에 올린 쪽이 앞의 것을 덮는다.\
  그 상태에서 검사 없이 지우면 **남의 자리를 지워버린다** — 테스트가 그 자리를 따로 잰다.
- 그래서 자리를 저장하지 않고 이름으로 다시 계산하는 설계에는 조건이 붙는다 — **`virtualName` 규칙과 해시가 add/remove 사이에 절대 안 바뀌어야 한다**.\
  주석이 "이 규칙이 바뀌면 원 위의 배치가 통째로 바뀐다"고 적어둔 이유다.
- Q: 점프 해시의 `getNode` 가 왜 O(log N)이면서 `slotCount` 가 0인가?\
  A: **자료구조가 없고 계산만 있기 때문**이다.

```java
public static int jumpHash(long key, int numBuckets) {
    long b = -1;
    long j = 0;
    while (j < numBuckets) {
        b = j;
        key = key * 2862933555777941757L + 1;
        j = (long) ((b + 1) * ((double) (1L << 31) / (double) ((key >>> 33) + 1)));
    }
    return (int) b;
}
```

```
  루프가 도는 횟수 = 이 키의 담당이 "바뀌는" 순간의 수

  버킷이 1 -> 2 -> 3 ... 로 늘어날 때 키가 새 버킷으로 옮겨갈 확률은 1/N 이다.
  그러니 N 까지 가는 동안 옮겨가는 기대 횟수 = 1/1 + 1/2 + 1/3 + ... + 1/N  (조화급수)
                                            ≈ ln N   -> **O(log N)**

  그리고 그 계산은 지역 변수 둘(b, j)로 끝난다. 저장하는 자리가 하나도 없다.
      @Override public int slotCount() { return 0; }
  BalanceTest·JumpConsistentHashTest 가 세 군데에서 assertEquals(0, ...) 로 못 박는다.
```

> **점프 해시(jump consistent hash)** — 자료구조 없이 정수 연산만으로 키를 `0..N-1` 버킷 하나에 대응시키는 알고리즘(Lamping·Veach 2014).\
> 예: 지역 변수 둘과 반복문 하나가 전부라 `slotCount()` 가 0이다.

- 즉 원은 **자리 수에 비례하는 메모리**를 내고 `log(자리 수)` 조회를 사고, 점프 해시는 **메모리 0** 을 내고 `log N` 계산을 산다.\
  둘 다 `log` 인데 로그의 밑에 들어가는 대상이 다르다 — 원은 자리 수(노드 수 × v), 점프는 노드 수다.

**더 생각할 것**

- `getNode` 가 `TreeMap` 한 줄로 끝나는 것이 이 장의 유쾌한 지점이다.\
  "새 자료구조"라고 부르지만 실제로는 **06번 BST + 되감기 한 줄 + 가상 노드**다.
- `removeNode` 가 자리를 저장하지 않고 다시 계산하는 것은 메모리와 정합성의 교환이다.\
  저장하면 규칙이 바뀌어도 안전하지만 노드마다 long 배열을 들어야 한다.
- 점프 해시의 루프 횟수가 확률적으로 `ln N` 이라는 것은, 최악에는 더 돌 수 있다는 뜻이다.\
  다만 N 이 작으면(수십~수천) 실질적으로 몇 번 안 돈다(원본에 근거 없음 — 내 추론).

#### 4. 최악의 사용 패턴과 최선

**(ㄱ) 노드마다 자리를 하나만 주면**

```
노드 10개, 키 10만개. 가상 노드 수를 바꿔가며 최대/최소 부하를 잰다

  가상 노드    자리 수    최소      최대      비(최대/최소)
  ---------    -------    ------    ------    -------------
          1         10       873    15,835    18배 초과
         10        100     8,381    14,717
        100      1,000     8,136    12,044
        500      5,000     9,301    10,288    약 1.11배
      1,000     10,000     9,278    10,513    약 1.13배   <- 500 보다 나쁘다

  BalanceTest.imbalanceShrinksAsVirtualNodesGrow 가 최소·최대 열 전부를 assertEquals 로 못 박는다.
  비(ratio)는 부등식으로만 단언된다: ratio[0] > 18,  ratio[3] < 1.15,  at1000 > at500.
  README 의 "18배"와 "1.11배"는 그 최소·최대에서 나오는 파생값이다(1.11 은 10,288/9,301 = 1.106).
```

> **불균형 비(imbalance)** — 가장 많이 맡은 노드의 키 수 ÷ 가장 적게 맡은 노드의 키 수.\
> 예: 한 대라도 0개를 맡으면 `RingMetrics.imbalance` 가 `∞` 를 돌려준다 — 뭉개지 않으려는 선택이다.

- 왜 자리 하나면 18배가 되는가: 자리를 하나만 찍으면 **원 위 10개 점이 만드는 10개 구간의 길이**가 곧 부하이고, 무작위로 찍은 점 사이의 간격은 매우 불균등하기 때문이다.\
  가장 긴 구간이 가장 짧은 구간의 수십 배가 되는 것이 정상이다.
- 자리를 여러 개 찍으면 각 노드의 담당이 **원 전체에 흩어진 여러 조각의 합**이 되어, 큰 수의 법칙으로 합이 평균에 수렴한다.
- Q: 가상 노드를 계속 늘리면 계속 좋아지는가?\
  A: **아니다** — 1,000개에서 500개보다 나빠진다(9,278/10,513 로 비가 1.13).\
  자리가 많아질수록 이웃 자리 사이의 간격이 잘게 쪼개지면서 무작위 변동이 다시 드러나는 구간이 있고, 이 데이터셋에서는 500 근처가 바닥이다.\
  그리고 대가는 메모리다 — 500개면 `TreeMap` 항목이 5,000개다(테스트는 `assertEquals(10 * virtualNodes[i], ring.slotCount())` 로 공식을 단언한다).

**(ㄴ) 안 섞는 해시(`Hashing.WEAK`)를 쓰면**

```java
public static final RingHash WEAK = name -> name.hashCode() & 0xffffffffL;
```

```
  자바 String.hashCode 는 node-0 과 node-1 을 정확히 1 만큼 다르게 만든다...
  가 아니라, 실제로 잰 값은 **961** 이다.
      assertEquals(961, positions[1] - positions[0], "이름 한 글자 차이가 곧 자리 차이다");
      assertEquals(8_649, span);      // 노드 10대가 차지한 폭
      assertTrue(span < Hashing.RING_SIZE / 400_000, "원 전체의 50만 분의 1 안에 뭉쳐 있다");

  2^32 짜리 원에서 폭 8,649 는 원 전체의 약 1/496,585 다.
  -> 열 대가 원의 한 점에 뭉쳐 있다.

  결과:
      assertEquals(KEYS.size(), counts.get("node-0"), "node-0 이 전부 가져간다");
      assertEquals(9, starved, "나머지 아홉 대는 논다");
      assertEquals(Double.POSITIVE_INFINITY, RingMetrics.imbalance(counts));
```

- 왜 node-0 이 전부 가져가는가: 열 대의 자리가 8,649 폭 안에 몰려 있으므로, 그 밖에서 떨어진 키(= 거의 전부)는 시계 방향으로 돌다가 **뭉친 덩어리의 첫 자리**를 만난다.\
  그 첫 자리의 주인이 전부를 가져간다.
- Q: 가상 노드를 500개로 늘리면 살아나는가?\
  A: **안 살아난다.**\
  테스트가 `{1, 100, 500}` 세 값에서 전부 불균형이 `∞`(0개를 받은 노드가 있다) 임을 단언한다.\
  이름이 `node-0#0`, `node-0#1` … 로 바뀌어도 `hashCode` 가 안 섞으니 새 자리들도 여전히 좁은 구간에 뭉친다 — **뭉친 것을 흩는 것은 자리 수가 아니라 섞는 해시다.**
- `imbalance` 가 0을 받은 노드에서 `∞` 를 돌려주는 것도 의도다 — "0개를 맡았다"는 사실이 이 측정에서 제일 중요한 값이라 1을 더해 뭉개지 않는다.

**(ㄷ) 점프 해시에서 가운데 노드를 목록 밀기로 빼면**

- 이동량이 **28,682개(28.7%)** 다 — `1/N` 인 10,000개의 약 2.9배다.\
  뒤쪽 노드의 번호가 전부 하나씩 당겨져서, 그 노드들이 맡던 키의 계산이 통째로 바뀌기 때문이다.\
  즉 **점프 해시에서 번호는 이름이고, 번호를 바꾸는 것은 노드를 전부 바꾸는 것**이다.

**최선은 어떤 설정인가**

- 섞는 해시(`Hashing.MIXED`) + 가상 노드 수백 개 + 노드가 뒤에서만 늘어나는 환경이다.\
  그 조합에서 원은 불균형 1.11 배, 이동량 `1/N` 근처가 되고, 점프 해시는 불균형이 더 낮으면서(최소 9,827 / 최대 10,080) 자리를 0개 들고 있다.
- 다만 "최선"이 하나가 아니다 — 가운데 제거가 필요하면 원, 필요 없으면 점프 해시다(질문 5).

**더 생각할 것**

- 세 최악이 각각 다른 것을 가리킨다.\
  (ㄱ)은 **파라미터**, (ㄴ)은 **해시 품질**, (ㄷ)은 **알고리즘의 구조적 제약**이다 — 앞의 둘은 고칠 수 있고 마지막은 못 고친다.
- "가상 노드를 늘리면 좋아진다"는 직관이 1,000에서 깨지는 것을 테스트가 그대로 적어둔 태도가 이 문제집답다.\
  좋아지는 방향만 적으면 문서가 광고가 된다.
- 해시 품질 문제는 05번·29번에서 계속 나온 이야기다.\
  05번은 체이닝 대 탐사, 29번은 군집화, 31번은 원 위의 뭉침 — **밑에 깔린 해시가 나쁘면 그 위에 얹은 것도 나쁘다.**

#### 5. 네 구현의 트레이드오프

```
  구현                          자리 메모리        한 대 죽을 때 이동      가중치    가운데 제거
  ---------------------------   ----------------   ---------------------   -------   -----------
  ModuloSharding                이름 목록만        89,905 (node-7)         안 된다   된다
  ConsistentHashRing            노드당 v 개        12,044 (v=100, node-7)  -         된다
  WeightedConsistentHashRing    무게에 비례        -                       **된다**  된다
  JumpConsistentHash            **0**              9,827 (node-9)          안 된다   **안 된다**

  주의: 이 표의 이동량 열은 같은 조건이 아니다.
    89,905 / 12,044 는 **node-7(가운데)** 를 뺀 값이고, 9,827 은 점프 해시가 가운데를 못 빼서
    **node-9(맨 뒤)** 를 뺀 값이다. 같은 node-9 조건이면 모듈로 89,941, 원(v=100) 10,039 이고
    셋 다 MovementTest 에 assertEquals 로 있다(10,039 는 README 에 없다).
```

- Q: 가중치를 자리 수로 표현할 수 있는 근거는?\
  A: **원 위에서 한 노드의 부하가 그 노드가 차지한 구간 길이의 합에 비례하고, 자리를 무작위로 찍으면 그 합의 기댓값이 자리 수에 비례하기 때문**이다.

```java
public void addNode(String node, int weight) {
    if (weight < 1) {
        throw new IllegalArgumentException("가중치는 1 이상이어야 한다: " + weight);
    }
    addSlots(node, virtualNodes() * weight);     // 자리를 weight 배로 준다
}
```

```
  small-a(1배), small-b(1배), big(2배) 를 넣는다 (virtualNodes = 100)

  자리 수 : small-a 100, small-b 100, big 200   합계 400
      assertEquals(400, ring.slotCount());
      (자리 배분 자체를 따로 재는 테스트도 있다 — 무게 1과 3을 넣으면 100 과 300, 합계 400 이다)

  키 배분 : small-a 24,226 / small-b 25,678 / big 50,096   (10만 키)
      big 의 몫 = 50,096 / 100,000 = 50.1%  -> 2/(1+1+2) = 50% 와 오차 0.1%
      그런데 small-a 와 small-b 는 같은 무게인데 24,226 대 25,678 로 6% 차이가 난다
      assertTrue(skew > 0.05, "오차가 " + skew + " 다. 없는 척하지 않는다")
```

- 즉 **기댓값은 맞고 실측은 안 맞는다** — 자리를 무작위로 찍는 이상 편차가 남는다(한계 6).\
  테스트가 그 오차를 "5%를 넘는다"고 **하한으로** 못 박은 것이 인상적이다 — 보통은 상한을 단언하는데, 여기서는 "오차가 실제로 있다"를 단언한다.
- Q: 모듈로에서 같은 것(가중치)을 하려면 왜 문제가 커지는가?\
  A: 모듈로의 결과가 `0..N-1` 의 **번호**라 "이 번호를 두 번 세는" 방법밖에 없기 때문이다.\
  가중치 2인 노드를 목록에 두 번 넣으면 `N` 이 커지고, 그러면 **N 이 식 안에 있다**는 원래 문제가 그대로 돌아온다 — 가중치를 조금만 바꿔도 거의 전부가 이동한다.\
  반면 원은 자리를 더 찍을 뿐 배정 규칙이 안 바뀌므로, 가중치를 바꿔도 **그 노드가 새로 차지한 구간의 키만** 움직인다.\
  즉 가중치를 얹을 수 있느냐는 "자리 배치가 규칙과 분리되어 있느냐"의 따름정리다.
- Q: 점프 해시가 못 하는 것을 되는 척하지 않고 예외로 드러낸 판단은 무엇을 지키는가?\
  A: **"조용히 틀린 답"을 막는다.**

```java
if (!nodes.get(nodes.size() - 1).equals(node)) {
    throw new UnsupportedOperationException(
            "점프 해시는 맨 뒤 노드만 뺄 수 있다. 뺄 수 있는 것은 "
                    + nodes.get(nodes.size() - 1) + " 인데 " + node + " 를 요청했다");
}
```

- 목록을 밀어 흉내내면 `getNode` 는 여전히 **답을 주고**, 그 답도 "틀린 답"은 아니다 — 그저 키 28.7%의 담당이 바뀌었을 뿐이다.\
  즉 `removeNode` 가 조용히 성공하면 호출자는 `1/N` 보장을 받았다고 믿는데 실제로는 못 받는다 — **계약이 깨진 것을 아무도 모른다.**
- 예외는 그 자리를 **호출 시점에** 드러낸다 — 27번 머클 트리가 잎 개수가 다르면 예외를 던지고, 30번 좌표 압축이 없는 좌표에 예외를 던진 것과 같은 자세다.
- 예외 메시지에 "뺄 수 있는 노드 이름"까지 넣은 것도 계약이다 — 테스트가 메시지에 `node-4` 가 들어 있는지 확인한다.

**접근 비교**

```
  무엇이 필요한가                      고를 것
  ---------------------------------    ----------------------------------------
  노드가 절대 안 바뀐다                ModuloSharding (제일 단순하고 분포도 제일 고르다)
  아무 노드나 죽을 수 있다             ConsistentHashRing
  서버 성능이 제각각이다               WeightedConsistentHashRing
  뒤에서만 늘리고 줄인다 + 메모리 0    JumpConsistentHash

  네 줄 중 무엇을 고를지는 성능이 아니라 **운영 시나리오**가 정한다.
```

**더 생각할 것**

- 표의 마지막 열("가운데 제거")이 제일 중요하다고 README 가 두 번 말한다.\
  성능 표에서 가장 중요한 칸이 성능이 아니라 **할 수 있느냐 없느냐**인 경우다.
- 가중치 구현이 상속으로 끝나는 것(부모의 `addSlots` 에 곱한 수를 넘기는 것)도 설계의 수확이다.\
  `addSlots(node, count)` 로 count 를 밖에서 받게 열어둔 덕에 자식이 한 줄로 끝났다.
- 점프 해시는 "자료구조 없는 자료구조"다.\
  이 문제집에서 `slotCount()` 가 0을 돌려주는 유일한 구현이고, 그 0이 이 알고리즘이 파는 물건이다.

#### 6. 이 구조의 한계가 다음 구조를 어떻게 부르는가

- Q: 여기서 모듈로와 원을 나란히 잰 방식이 32번에서는 왜 유일한 검증 수단이 되는가?\
  A: **"정답"을 따로 계산할 방법이 없는 문제이기 때문**이다.\
  31번에서는 이동량이라는 숫자가 있었고 그 숫자를 두 구현에서 재서 비교했다 — 어느 쪽이 맞다 틀리다가 아니라 **성질이 다르다**를 보였다.\
  32번 역전 인덱스는 답이 맞는 두 구현을 만들어 서로 맞대는데, 거기서는 그 대조가 정답의 유일한 근거가 된다 — 둘 다 답이 맞아야 하고, 어긋나면 어느 한쪽이 틀린 것이다.\
  (32번의 구체적 내용은 아직 안 읽었다 — 여기 적은 것은 31번 README 의 "다음" 절이 예고한 범위까지다.)
- 이 문제집이 반복해서 쓰는 검증 장치가 그것이다.\
  30번의 `NaiveIntervalStore`, 29번의 다섯 구현 교차 대조, 27번의 `TestSupport.naiveDiff`, 28번의 `StringBuilderStore` 가 전부 같은 도구다 — **느리지만 명백히 옳은 기준선**을 옆에 두는 것.
- Q: "이동량이 적다"가 아니라 **"옮겨간 키의 집합 = 죽은 노드가 맡던 키의 집합"** 이라는 등식은, 측정만으로는 왜 확인이 안 되는가?\
  A: **개수가 같아도 집합이 같다는 보장이 없기 때문**이다.

```
  노드 10대, 키 10만. node-7 을 뺀다.

  측정만 하면:  "12,044 개가 움직였다"
                -> 12,044 는 1/N 인 10,000 근처다. 좋아 보인다.
                -> 그런데 그중 절반이 node-7 과 무관한 키였다면?
                   개수는 그대로인데 등식은 깨진 것이고, 측정은 그것을 못 잡는다.

  등식을 확인하려면 **두 집합을 맞대야** 한다:
      shareOf(ring, "node-7")        = node-7 이 빠지기 전에 맡던 키 수
      movedOnRemoval(ring, "node-7") = 실제로 담당이 바뀐 키 수
      이 둘이 같은가?

  MovementTest.onlyTheVictimsKeysMove
      assertEquals(shareOf(new ConsistentHashRing(100), "node-7"),
              movedOnRemoval(new ConsistentHashRing(100), "node-7"),
              "원: 옮겨간 수와 맡던 수가 같아야 한다");
      assertEquals(shareOf(new JumpConsistentHash(), "node-9"),
              movedOnRemoval(new JumpConsistentHash(), "node-9"),
              "점프: 옮겨간 수와 맡던 수가 같아야 한다");
```

- Q: 그럼 무엇을 봐야 확인되는가?\
  A: **개수가 아니라 "누가 움직였는가"** 다.\
  이 테스트가 그 자리를 두 방식으로 좁힌다.\
  첫째, 위처럼 "맡던 수 == 옮겨간 수"를 단언한다 — 죽은 노드의 키가 전부 움직이는 것은 자명하므로, 개수가 같으면 남의 키는 한 개도 안 움직였다는 뜻이 된다.\
  둘째, 노드를 **더할** 때는 더 직접적으로 확인한다 — `assertEquals(0, strayed, "새 노드와 무관한 이동이 " + strayed + "건 있다")` 로 **새 노드로 가지 않은 이동이 0건**임을 단언한다(모듈로는 같은 상황에서 81,566건이다).
- 즉 "적다"는 **양**의 진술이고 "그것뿐이다"는 **집합**의 진술이다.\
  양은 재면 되지만 집합은 대조해야 한다 — 그리고 일관된 해싱이 파는 것은 뒤쪽이다.

**더 생각할 것**

- "숫자가 좋아 보인다"와 "성질이 성립한다"는 다르다.\
  이 구별은 27번의 `diffBlocks`(답은 맞는데 걸음 수가 다르다)와 30번의 가지치기(답은 맞는데 방문 수가 다르다)의 반대 방향이다 — 거기서는 숫자를 봐야 했고 여기서는 숫자만 봐서는 안 된다.
- 등식을 테스트로 쓰려면 **기댓값을 리터럴로 적지 않는 편이 낫다**.\
  `assertEquals(shareOf(...), movedOnRemoval(...))` 처럼 양쪽을 계산해 맞대면 시드나 해시가 바뀌어도 성질 자체를 검증한다.
- 반대로 `assertEquals(89_905, modulo)` 같은 리터럴 단언은 **회귀 감지용**이다.\
  둘은 목적이 다르고, 좋은 테스트 묶음에는 둘 다 있다 — 이 장의 `MovementTest` 가 그 두 종류를 나란히 들고 있다.
