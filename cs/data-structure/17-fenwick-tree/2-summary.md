### 구조

```
FenwickTree (n = 8, 원소 = [3,1,4,1,5,9,2,6])
+-------------------------------------------------------------------+
| int    n       (원소 개수)                                          |
| long[] tree    (길이 n+1. tree[0] 은 쓰지 않는다 -> 1-base)           |
+-------------------------------------------------------------------+

바깥 API 는 0-base, 안의 tree 는 1-base 다. 경계에서 늘 +1 이 붙는다.
   add(index, delta)   -> x = index + 1 부터 시작
   prefixSum(index)    -> x = index + 1 부터 시작
   tree[0] 을 비우는 이유: i & -i (최하위 1비트)가 0 에서는 0 이라 걸음이 멈추지 않는다.

핵심 규약 -- tree[i] 는 "원소 i-lowbit(i)+1 부터 i 까지"의 합을 갖는다  (lowbit(i) = i & -i)

                                   1     2     3     4     5     6     7     8
                                +-----+-----+-----+-----+-----+-----+-----+-----+
                                |  3  |  1  |  4  |  1  |  5  |  9  |  2  |  6  |
                                +-----+-----+-----+-----+-----+-----+-----+-----+
                                   0     1     2     3     4     5     6     7
       윗줄 = tree 가 쓰는 1-base 자리 / 아랫줄 = 바깥 API 가 쓰는 0-base 인덱스

tree[1] =  3   i=0001b  lowbit=1|=====|
tree[2] =  4   i=0010b  lowbit=2|===========|
tree[3] =  4   i=0011b  lowbit=1            |=====|
tree[4] =  9   i=0100b  lowbit=4|=======================|
tree[5] =  5   i=0101b  lowbit=1                        |=====|
tree[6] = 14   i=0110b  lowbit=2                        |===========|
tree[7] =  2   i=0111b  lowbit=1                                    |=====|
tree[8] = 31   i=1000b  lowbit=8|===============================================|

읽는 법: i = 6 = 0110b -> lowbit = 0010b = 2 -> 원소 5..6 (2칸)을 맡는다.
        i = 8 = 1000b -> lowbit = 1000b = 8 -> 원소 1..8 (8칸)을 통째로 맡는다.
        i 가 홀수면 lowbit = 1 -> 자기 자신 한 칸만 맡는다.

맡는 칸 수 = lowbit(i) = i 의 이진수 끝에 붙은 0 의 개수만큼의 2의 거듭제곱.
세그먼트 트리처럼 "노드"를 따로 두지 않는다. 인덱스의 비트 모양이 곧 트리다.
```

```
같은 것을 트리처럼 세워 보면 (부모 = i + lowbit(i), 이것이 add 가 올라가는 길이다)

                                  tree[8]  [1..8]
                    +---------------+---------------+
                 tree[4]  [1..4]                    (tree[8] 위는 없다)
            +-------+-------+
        tree[2] [1..2]      tree[6]  [5..6]
          +---+               +---+
      tree[1] tree[3]     tree[5] tree[7]
       [1..1]  [3..3]      [5..5]  [7..7]

  tree[3] 의 부모 = 3 + 1 = 4,  tree[6] 의 부모 = 6 + 2 = 8,  tree[4] 의 부모 = 4 + 4 = 8
  세그먼트 트리(4n칸, 노드 2n-1개)와 달리 칸이 n+1개뿐이다.
  대신 tree[i] 만으로는 "구간 [3..6] 의 합" 같은 것을 바로 못 읽는다
  -> 누적합의 차로만 답을 만든다 -> 뺄셈이 있는 연산(합)에만 쓸 수 있다.
```

### 동작 — 갱신

```
add(2, +10) : 0-base 인덱스 2 의 값에 10 을 더한다 -> 1-base 로 x = 3 부터

  for (int x = index + 1; x <= n; x += x & -x) tree[x] += delta;

  x = 3 = 0011b  -> lowbit 1 -> 다음 x = 4
  x = 4 = 0100b  -> lowbit 4 -> 다음 x = 8
  x = 8 = 1000b  -> lowbit 8 -> 다음 x = 16 > n = 8  -> 끝

                            1     2     3     4     5     6     7     8
                         +-----+-----+-----+-----+-----+-----+-----+-----+
                         |  3  |  1  |  4  |  1  |  5  |  9  |  2  |  6  |
                         +-----+-----+-----+-----+-----+-----+-----+-----+
tree[3] += 10   (0011b)              |=====|
tree[4] += 10   (0100b)  |=======================|
tree[8] += 10   (1000b)  |===============================================|

  원소 3(1-base)을 담고 있는 칸은 이 셋뿐이다. 위로 갈수록 구간이 감싸며 커진다.
  (tree[5], tree[6], tree[7] 은 원소 3 을 안 담으므로 건드리지 않는다)

왜 O(log n) 인가
  x += x & -x 는 끝의 1비트를 밀어 올려 그 위 비트로 올려붙인다
     0011 -> 0100 -> 1000  (1의 개수가 줄거나 자리가 한 칸 위로 간다)
  한 걸음마다 x 의 최하위 1비트 자리가 반드시 위로 올라간다
  -> 자리 수 = log2(n) 번을 넘길 수 없다.
```

### 동작 — 조회

```
prefixSum(6) : 0-base 인덱스 0..6 의 합 -> 1-base 로 x = 7 부터

  for (int x = index + 1; x > 0; x -= x & -x) sum += tree[x];

  x = 7 = 0111b  -> lowbit 1 -> 다음 x = 6
  x = 6 = 0110b  -> lowbit 2 -> 다음 x = 4
  x = 4 = 0100b  -> lowbit 4 -> 다음 x = 0  -> 끝

                            1     2     3     4     5     6     7     8
                         +-----+-----+-----+-----+-----+-----+-----+-----+
                         |  3  |  1  |  4  |  1  |  5  |  9  |  2  |  6  |
                         +-----+-----+-----+-----+-----+-----+-----+-----+
tree[7]  (0111b)                                             |=====|
tree[6]  (0110b)                                 |===========|
tree[4]  (0100b)         |=======================|

  조각 셋이 겹치지도, 비지도 않게 [1..7] 을 정확히 덮는다  -> 2 + 14 + 9 = 25
  겹치지 않는 이유: 다음 걸음이 시작하는 자리가 방금 조각의 왼쪽 끝 바로 앞이다
     (x 에서 lowbit 를 빼면 그 조각이 맡던 구간의 왼쪽 바깥으로 정확히 이동한다)

왜 O(log n) 인가
  x -= x & -x 는 끝의 1비트를 하나 지운다
     0111 -> 0110 -> 0100 -> 0000
  걸음 수 = x 의 이진수에 있는 1의 개수 <= log2(n)+1

add 는 1비트를 위로 올리며 올라가고, prefixSum 은 1비트를 지우며 내려온다.
같은 lowbit 규칙을 반대 방향으로 쓰는 한 쌍이다.
```

```
rangeSum(from, to) = prefixSum(to) - prefixSum(from - 1)

 rangeSum(2, 6)  (0-base 인덱스)

                           0     1     2     3     4     5     6     7
                        +-----+-----+-----+-----+-----+-----+-----+-----+
                        |  3  |  1  |  4  |  1  |  5  |  9  |  2  |  6  |
                        +-----+-----+-----+-----+-----+-----+-----+-----+
prefixSum(6) = 25       |=========================================|
prefixSum(1) =  4       |===========|   <- 빼서 없앤다
rangeSum(2,6) = 21                  |=============================|   25 - 4 = 21

 from == 0 이면 prefixSum(-1) 을 부르게 되는데, index < 0 이면 0 을 돌려주므로 그대로 성립한다.

이 한 줄이 자료구조의 한계를 정한다
   뺄셈이 있어야(역연산이 있어야) 구간 답을 만들 수 있다 -> 합, XOR 은 되고 min/max 는 안 된다
   (13장 세그먼트 트리는 노드에 구간 답이 통째로 있어서 역연산이 필요 없다)
   set(index, value) 도 대입이 아니라 add(index, value - get(index)) 로 돌아간다.
   tree 에는 원소값이 그대로 남아 있지 않기 때문이다 -- get 조차 rangeSum 을 거친다.
```

## 구현 — FenwickTree2D (`src/main/java/com/datastructure/fenwick/FenwickTree2D.java`)

### 구조

```
FenwickTree2D -- 같은 lowbit 규칙을 두 축에 각각 적용한다 (4 x 4 격자)

  long[][] tree = new long[rows+1][cols+1]    <- 두 축 모두 1-base, 0 행/0 열은 안 쓴다

  tree[x][y] 가 맡는 것 = 행 x-lowbit(x)+1 .. x  그리고  열 y-lowbit(y)+1 .. y
                          (1차원에서 "구간"이던 것이 여기서는 "직사각형"이 된다)

  예) tree[4][2] : x = 4 = 100b -> lowbit 4 -> 행 1..4
                   y = 2 = 010b -> lowbit 2 -> 열 1..2

                  열  1     2     3     4
                    +-----+-----+-----+-----+
            행 1    | ### | ### |     |     |
                    +-----+-----+-----+-----+
            행 2    | ### | ### |     |     |
                    +-----+-----+-----+-----+
            행 3    | ### | ### |     |     |
                    +-----+-----+-----+-----+
            행 4    | ### | ### |     |     |
                    +-----+-----+-----+-----+
                      ### = tree[4][2] 가 담는 칸 (4 x 2 직사각형)

  예) tree[3][3] : 3 = 011b -> lowbit 1 -> 행 3..3, 열 3..3  (1 x 1 짜리)
      tree[2][4] : 2 -> lowbit 2 -> 행 1..2 / 4 -> lowbit 4 -> 열 1..4  (2 x 4 짜리)

  1차원 FenwickTree 가 "선분"을 맡았다면 여기서는 "직사각형"을 맡는다.
  칸 수 = (rows+1) x (cols+1) -- 원본 격자와 거의 같다.
```

```
add(row, col, delta) : 두 축을 이중 루프로 각각 밀어 올린다

  for (x = row+1; x <= rows; x += x & -x)
      for (y = col+1; y <= cols; y += y & -y)
          tree[x][y] += delta;

  add(2, 0, delta) -> x 는 3, 4 로 / y 는 1, 2, 4 로 (rows = cols = 4)

              x \ y   1     2     3     4
                    +-----+-----+-----+-----+
              1     |     |     |     |     |
                    +-----+-----+-----+-----+
              2     |     |     |     |     |
                    +-----+-----+-----+-----+
              3     |  *  |  *  |     |  *  |
                    +-----+-----+-----+-----+
              4     |  *  |  *  |     |  *  |
                    +-----+-----+-----+-----+
                      * = 값이 갱신되는 tree 칸 (2 x 3 = 6칸)

  안쪽 루프의 시작값을 매 x 마다 col+1 로 다시 잡아야 한다.
  y 축 걸음은 x 와 무관하게 처음부터 다시 밟아야 하기 때문이다
  (앞 x 에서 올라간 y 를 이어 쓰면 아래쪽 y 칸들이 통째로 빠진다).
  비용 = O(log rows * log cols)

  prefixSum(row, col) 은 두 축 모두 x -= x & -x, y -= y & -y 로 내려오며 더한다.
  1차원에서 "조각 몇 개로 선분을 덮던" 것이 여기서는 "타일 몇 장으로 직사각형을 덮는" 것이 된다.
```

```
rangeSum(r1, c1, r2, c2) = A - B - C + D  (포함-배제)

  A = prefixSum(r2,   c2)     B = prefixSum(r1-1, c2)
  C = prefixSum(r2, c1-1)     D = prefixSum(r1-1, c1-1)

  구하려는 것 : 행 3..4, 열 3..4 (1-base)          네 개의 누적 직사각형

   +---+---+---+---+
   |   |   |   |   |
   +---+---+---+---+
   |   |   |   |   |
   +---+---+---+---+
   |   |   | # | # |
   +---+---+---+---+
   |   |   | # | # |
   +---+---+---+---+

           A         -         B         -         C         +         D
   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+
   | # | # | # | # |   | # | # | # | # |   | # | # |   |   |   | # | # |   |   |
   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+
   | # | # | # | # |   | # | # | # | # |   | # | # |   |   |   | # | # |   |   |
   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+
   | # | # | # | # |   |   |   |   |   |   | # | # |   |   |   |   |   |   |   |
   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+
   | # | # | # | # |   |   |   |   |   |   | # | # |   |   |   |   |   |   |   |
   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+   +---+---+---+---+

  A 에서 위쪽 띠(B)와 왼쪽 띠(C)를 빼면 왼쪽 위 모서리(D)가 두 번 빠진다
  -> 한 번 되돌려야 한다. 그래서 마지막 항의 부호가 + 다.

  r1 == 0 이나 c1 == 0 이면 prefixSum 의 인자가 -1 이 되는데
  row < 0 || col < 0 이면 0 을 돌려주므로 "뺄 것이 없다" 가 되어 식이 그대로 성립한다.
  (0 을 안 돌려주고 예외를 냈다면 경계마다 따로 분기해야 했을 것이다)
```
