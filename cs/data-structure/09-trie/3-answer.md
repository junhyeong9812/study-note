### A. 문제 (TrieProblems)

#### 1. 가장 긴 공통 접두사 — `longestCommonPrefix`

**질문**: 어떻게 푸는가. 뿌리에서 내려가다 언제 멈추는가 — 자식이 하나뿐인데도 멈춰야 하는 경우가 왜 있는가(`["a", "ab"]` 의 답이 `"a"` 인 이유).

**impl 코드** (`impl/TrieProblems.java`)

```java
public static String longestCommonPrefix(String[] words) {
    if (words == null || words.length == 0) {
        return "";
    }
    MapTrie trie = new MapTrie();
    for (String w : words) {
        trie.insert(w);
    }
    StringBuilder sb = new StringBuilder();
    MapTrie.Node cur = trie.root;
    while (cur.children.size() == 1 && !cur.end) {
        Map.Entry<Character, MapTrie.Node> only = cur.children.entrySet().iterator().next();
        sb.append(only.getKey().charValue());
        cur = only.getValue();
    }
    return sb.toString();
}
```

- 논리: 전부 트라이에 넣은 뒤 **뿌리에서 갈림길이 나올 때까지 외길을 따라 내려간다**.
- 논리: "모든 단어가 공유하는 접두사" = "모든 단어가 반드시 지나는 길" = **갈래가 하나뿐인 구간**이다.
- 논리: 트라이가 이 문제에 맞는 이유는 공유가 **구조로 표현되기** 때문이다.\
  단어를 서로 비교할 필요가 없다 — 같은 접두사는 같은 경로라 이미 합쳐져 있다.

**손으로 추적** — `["flower", "flow", "flight"]` → `"fl"`

```
트라이 (넣고 나면)

   (root)
      |
      f          children = {l}       size 1, end false  -> 'f' 붙이고 내려감
      |
      l          children = {o, i}    size 2             -> 갈림길! 멈춤
     / \
    o   i
    |   |
    w*  g        (* = end)
    |   |
    e   h
    |   |
    r*  t*

  결과 = "fl"

  왜 여기서 멈추는가 :
     l 노드에서 갈래가 둘이다 -> o 로 가는 단어와 i 로 가는 단어가 있다는 뜻
     -> 그 아래 어떤 글자도 '전부'가 공유하지 않는다
```

**두 가지 멈춤 조건**

```
while (cur.children.size() == 1 && !cur.end)
        ^^^^^^^^^^^^^^^^^^^^^^^     ^^^^^^^^
        조건 A: 갈림길이면 멈춤      조건 B: 여기서 끝나는 단어가 있으면 멈춤

 조건 A (갈림길) : 자식이 2개 이상 -> 단어들이 여기서 갈라진다
                   자식이 0개      -> 더 내려갈 곳이 없다 (전부 같은 단어일 때)

 조건 B (단어 끝) : 자식이 하나여도 여기서 끝나는 단어가 있으면 더 가면 안 된다
                   그 단어에게는 그 아래 글자가 아예 없기 때문이다
```

**`["a", "ab"]` 의 답이 `"a"` 인 이유** (`oneIsPrefixOfOther` 테스트)

```
트라이

   (root)
      |
      a*         children = {b}  -> size 1 (갈림길이 아니다!)
      |          end = true      -> "a" 라는 단어가 여기서 끝난다
      b*

 조건 A 만 보면 : children.size() == 1 이므로 계속 내려간다 -> "ab" 를 반환 (틀림)
 조건 B 를 보면 : cur.end == true 이므로 멈춘다 -> "a" 를 반환 (정답)

 왜 "ab" 가 틀리는가 :
    입력에 "a" 라는 단어가 있다. "a" 는 "ab" 로 시작하지 않는다.
    공통 접두사는 '모든 단어의' 접두사여야 하므로 "a" 를 넘어설 수 없다.
    한 단어가 다른 단어의 접두사이면, 그 짧은 단어가 곧 상한이다.
```

> **`end` 표시** — 이 노드까지의 경로가 실제로 등록된 단어인지를 나타내는 불리언.\
> 예: `"app"` 과 `"apple"` 이 둘 다 있으면 `p` 노드와 `e` 노드 양쪽에 `end = true` 가 찍힌다.

- 논리: 이 한 조건이 없으면 130개 중 몇 개가 아니라 **의미 자체가 틀린다**.\
  `oneIsPrefixOfOther` 가 `["a","ab"]`, `["ab","a"]`, `["apple","app","application"]` 세 케이스로 못 박는다.
- 논리: `["ab","a"]` 도 같은 답을 준다 — 트라이는 **입력 순서와 무관**하다.\
  삽입 순서가 달라도 만들어지는 트리가 같기 때문이다.

**경계 케이스**

```
 words = null  또는 길이 0     -> 앞의 if 로 "" 반환
 words = [""]                  -> insert("") 가 root.end = true 로 만든다
                                  -> 조건 B 로 루프가 한 번도 안 돈다 -> ""
 words = ["", "abc"]           -> root.end = true (빈 문자열 때문)
                                  -> 즉시 멈춤 -> ""   (맞다. "" 는 모든 것의 접두사이자 상한이다)
 words = ["apple"]             -> 외길을 끝까지 내려가 "apple"
                                  (마지막 노드에서 children.size() == 0 이라 조건 A 로 멈춤)
 words = ["ab","ab","ab"]      -> insert 가 중복을 무시하므로 단어 하나짜리와 같다 -> "ab"
```

- 논리: `MapTrie.insert` 가 `if (contains(word)) return;` 로 **중복 삽입을 무시**하는 덕에 `allSame` 케이스가 자동으로 처리된다.
- 비용(왜): 트라이 만들기 = 모든 단어의 글자 수 합 = **O(총 글자 수)**.
- 비용(왜): 내려가기 = 답의 길이만큼 = O(공통 접두사 길이) ≤ O(L).
- 비용(왜): 전체 O(N·L) — `manyWords` 테스트는 10만 단어를 15초 제한으로 돌린다.
- 한계: 트라이를 **한 번 쓰고 버린다** — 이 문제만 풀자면 세로 비교(단어들의 i번째 글자를 동시에 보기)가 메모리를 훨씬 덜 쓴다.\
  여기서 트라이를 쓰는 이유는 답이 "구조에서 읽힌다"는 것을 보이기 위해서다.\
  (원본에 근거 없음 — 내 추론)

**질문별 답**

- Q: 문제 1을 어떻게 푸는가?\
  A: 단어를 전부 트라이에 넣고 뿌리에서 외길을 따라 내려가며 지나온 글자를 모은다.\
  갈림길을 만나거나 그 노드에서 끝나는 단어를 만나면 멈춘다.

- Q: 언제 멈추는가 — 자식이 하나뿐인데도 멈춰야 하는 경우가 왜 있는가?\
  A: 조건이 둘이다 — **갈림길**(`children.size() != 1`)과 **단어의 끝**(`cur.end`).\
  자식이 하나뿐이어도 그 노드에서 끝나는 단어가 있으면 멈춰야 한다.\
  `["a","ab"]` 에서 `a` 노드는 자식이 `b` 하나뿐이지만 `"a"` 라는 단어가 거기서 끝나므로, 더 내려가면 `"a"` 가 `"ab"` 로 시작한다고 주장하는 셈이 된다.\
  한 단어가 다른 단어의 접두사이면 그 짧은 단어가 답의 상한이다.

#### 2. 접두사 자동완성 앞에서 k 개 — `autocomplete`

**질문**: 어떻게 푸는가. `keysWithPrefix(prefix).subList(0, k)` 는 답이 맞는데 왜 시간 제한에 걸리는가. 이 문제가 `Trie` 가 아니라 `MapTrie` 를 구체 타입으로 받는 이유는 무엇인가.

**impl 코드**

```java
public static List<String> autocomplete(MapTrie trie, String prefix, int k) {
    List<String> out = new ArrayList<>();
    if (k <= 0) {
        return out;
    }
    MapTrie.Node start = trie.findNode(prefix);
    if (start != null) {
        collectUpTo(start, new StringBuilder(prefix), out, k);
    }
    return out;
}

private static void collectUpTo(MapTrie.Node node, StringBuilder path, List<String> out, int k) {
    if (out.size() >= k) {
        return;
    }
    if (node.end) {
        out.add(path.toString());
        if (out.size() >= k) {
            return;
        }
    }
    for (Map.Entry<Character, MapTrie.Node> e : node.children.entrySet()) {
        path.append(e.getKey().charValue());
        collectUpTo(e.getValue(), path, out, k);
        path.deleteCharAt(path.length() - 1);
        if (out.size() >= k) {
            return;
        }
    }
}
```

- 논리: `collect` 와 **같은 재귀**인데 `out.size() >= k` 검사가 세 곳에 끼어 있다.
- 논리: 세 곳인 이유가 각각 다르다.\
  (1) 함수 진입 시 — 이미 찼으면 내려가지 않는다.\
  (2) 단어를 담은 직후 — 방금 k번째를 담았으면 즉시 끝낸다.\
  (3) 자식에서 돌아온 직후 — 그 아래에서 채웠으면 형제 가지로 넘어가지 않는다.
- 논리: `TreeMap` 을 쓰므로 자식 순회가 **문자 코드 오름차순**이고, 그 덕에 재귀 순서가 곧 사전순이다.\
  정렬을 따로 하지 않는다.

> **사전순(lexicographic order)** — 앞 글자부터 비교해 정하는 문자열 순서.\
> 예: `"car" < "card" < "care" < "careful" < "cars" < "cat"` — 짧은 쪽이 접두사면 짧은 쪽이 앞이다.

**왜 재귀 순서가 사전순인가**

```
MapTrie 의 자식 컨테이너가 TreeMap 이다 -> 키(문자) 오름차순으로 순회된다

 collect 의 순서
   1. 이 노드에서 끝나는 단어를 먼저 담는다 (node.end)   <- 접두사가 먼저
   2. 자식을 문자 순으로 돌며 재귀                         <- 그 다음이 확장

 "car" 노드에서 시작하면
   car          <- 노드 자신 (end)
   car + d...   <- 'd' 가지
   car + e...   <- 'e' 가지
   car + s...   <- 's' 가지
   결과 [car, card, care, careful, cars]   = 사전순

 이것이 "접두사 자신이 첫 결과가 된다" 테스트(prefixItselfComesFirst)의 근거다
```

**왜 `keysWithPrefix(prefix).subList(0, k)` 가 시간 제한에 걸리는가**

```java
@Test
@Timeout(20)
@DisplayName("10만 개가 걸린 접두사에서 10개만 뽑는다")
void stopsEarly() {
    // 전부 모으고 자르면 질의 하나가 10만 걸음이다. 그것을 10만 번 한다.
    MapTrie t = new MapTrie();
    for (int i = 0; i < 100_000; i++) {
        t.insert("a" + encode(i));
    }
    List<String> first = TrieProblems.autocomplete(t, "a", 10);
    assertEquals(10, first.size());
    for (int q = 0; q < 100_000; q++) {
        assertEquals(first, TrieProblems.autocomplete(t, "a", 10));
    }
}
```

```
접두사 "a" 에 걸린 단어 = 10만 개.  k = 10.  질의 횟수 = 10만 번

 (A) keysWithPrefix(p).subList(0, k)

     한 질의마다
        부분 트리를 끝까지 재귀로 훑는다            -> 노드 약 10만개 이상 방문
        단어 10만 개를 전부 String 으로 만들어 담는다 -> 문자열 10만 개 생성
        그중 앞 10개만 쓰고 99,990개를 버린다

     비용 = 10만 질의 x 10만 걸음 = 10^10 걸음
            + 매 질의마다 10만 개의 문자열 생성/폐기 (GC 압박)
     -> 20초 제한에 절대 못 들어간다

 (B) collectUpTo (impl)

     한 질의마다
        findNode("a")        -> 1걸음
        10개를 담는 즉시 종료 -> 방문 노드는 앞쪽 몇십 개뿐

     비용 = 10만 질의 x 약 (L + k x L) 걸음 ≈ 10^7 수준
     -> 여유롭게 통과

 핵심 : "답이 맞다"와 "제때 끝난다"는 다른 문제다
        출력 크기가 k 인데 비용이 전체 매칭 수에 비례하면 안 된다
```

- 논리: 이 함정의 이름은 **"전부 만들고 자르기"** 다.\
  같은 실수가 페이지네이션(전체 조회 후 앞 N개), 정렬(전부 정렬 후 상위 k개)에서 반복된다.
- 논리: 07번 `KthLargest` 와 정확히 같은 교훈이다 — 상위 k개만 필요하면 **k에 비례하는 비용**으로 끝나야 한다.
- 비용(왜): `agreesWithKeysWithPrefix` 테스트가 두 방식의 **답이 같음**을 별도로 검증한다.\
  즉 (A)는 틀린 풀이가 아니라 **느린 풀이**다 — 정확성 테스트만으로는 못 거른다.

**왜 `Trie` 가 아니라 `MapTrie` 를 받는가**

```
Trie 인터페이스가 주는 것 (계약)
    insert / contains / startsWith / remove / size / isEmpty / clear
    keysWithPrefix(prefix)   <- 전부 모아서 List 로 준다
    countWithPrefix(prefix)  <- 개수만 준다

 "중간에 멈춘다"를 하려면 무엇이 필요한가?
    -> 부분 트리를 '내가' 걸어야 한다
    -> 노드를 손에 쥐어야 한다 : trie.findNode(prefix) 와 MapTrie.Node
    -> 그런데 findNode 도 Node 도 계약에 없다 (package-private 내부 구조다)

 계약이 주는 것만으로는
    keysWithPrefix 가 List 를 '완성해서' 돌려주는 시점에 이미 비용을 다 치렀다
    반환값을 자르는 것은 사후 처리라 비용을 못 줄인다

 => 그래서 시그니처가 autocomplete(MapTrie trie, ...) 다
```

- 논리: README 가 이것을 한 문장으로 요약한다 — **"인터페이스가 주는 것만으로는 못 푸는 문제가 있다"는 것도 정보다.**
- 논리: 08번의 `GraphProblems` 와 대비된다.\
  거기서는 모든 함수가 `Graph` 인터페이스만 받았다 — 계약이 필요한 연산을 전부 제공했기 때문이다.
- 한계: 계약에 `keysWithPrefix(prefix, limit)` 같은 연산을 추가하면 인터페이스로도 풀린다.\
  즉 "인터페이스의 한계"가 아니라 **"이 인터페이스가 그 질의를 예상하지 않았다"** 는 것이다.
- 한계: 구체 타입을 받으면 `ArrayTrie` 로는 이 함수를 못 쓴다 — 재사용성을 비용과 맞바꾼 것이다.

> **게으른 계산(lazy evaluation)** — 결과를 미리 다 만들지 않고 필요한 만큼만 계산하는 방식.\
> 예: `keysWithPrefix` 가 `Iterator` 나 `Stream` 을 돌려줬다면 앞 k개만 소비하는 것으로 같은 효과를 낼 수 있었다.

**질문별 답**

- Q: 문제 2를 어떻게 푸는가?\
  A: `findNode(prefix)` 로 접두사 노드를 찾고, 거기서부터 `collect` 와 같은 재귀를 돌되 **`out.size() >= k` 가 되는 순간 모든 층에서 즉시 반환**한다.\
  `TreeMap` 자식 순회가 문자 오름차순이라 나오는 순서가 그대로 사전순이고, 노드 자신을 먼저 담으므로 접두사 자신이 첫 결과가 된다.

- Q: `keysWithPrefix(prefix).subList(0, k)` 는 답이 맞는데 왜 시간 제한에 걸리는가?\
  A: 비용이 **출력 크기 k가 아니라 전체 매칭 수에 비례**하기 때문이다.\
  접두사에 10만 개가 걸려 있으면 질의 하나가 부분 트리 전체를 훑고 문자열 10만 개를 만든 뒤 99,990개를 버린다.\
  그것을 10만 번 하면 약 10¹⁰ 걸음이라 20초 제한을 넘는다.\
  `agreesWithKeysWithPrefix` 가 두 방식의 답이 같음을 따로 검증하므로, 이것은 **틀린 풀이가 아니라 느린 풀이**다.

- Q: 왜 `MapTrie` 를 구체 타입으로 받는가?\
  A: 중간에 멈추려면 부분 트리를 직접 걸어야 하고, 그러려면 `findNode` 와 `Node` 를 써야 하는데 둘 다 `Trie` 계약에 없는 내부 구조이기 때문이다.\
  계약이 주는 `keysWithPrefix` 는 리스트를 **완성해서** 돌려주므로 반환값을 자르는 시점에는 이미 비용을 다 치른 뒤다.\
  "인터페이스가 주는 것만으로는 못 푸는 문제가 있다"는 것 자체가 이 문제의 메시지다.

#### 3. 서로 다른 부분 문자열 개수 — `countDistinctSubstrings`

**질문**: 어떻게 푸는가. 접미사를 전부 넣는데 왜 중복 제거를 따로 안 해도 되는가, 그리고 이 풀이는 n 이 커지면 왜 무너지는가.

**impl 코드**

```java
public static int countDistinctSubstrings(String s) {
    if (s == null || s.isEmpty()) {
        return 0;
    }
    MapTrie.Node root = new MapTrie.Node();
    int nodes = 0;
    for (int i = 0; i < s.length(); i++) {
        MapTrie.Node cur = root;
        for (int j = i; j < s.length(); j++) {
            char c = s.charAt(j);
            MapTrie.Node next = cur.children.get(c);
            if (next == null) {
                next = new MapTrie.Node();
                cur.children.put(c, next);
                nodes++;
            }
            cur = next;
        }
    }
    return nodes;
}
```

- 논리: `MapTrie` 클래스를 쓰지 않고 **`MapTrie.Node` 만 빌려** 날 트리를 직접 만든다.\
  `end` 표시도 `wordsBelow` 도 필요 없기 때문이다 — 세는 것은 **노드 개수**뿐이다.
- 논리: 바깥 루프가 시작 위치 `i`, 안쪽 루프가 끝 위치 `j` 다.\
  즉 `s[i..]` 라는 **접미사를 전부 밀어 넣는** 것이다.

> **접미사(suffix)** — 문자열의 뒤쪽 일부. `"anana"`, `"nana"`, `"ana"` … 는 `"banana"` 의 접미사다.\
> 예: 모든 부분 문자열은 "어떤 접미사의 접두사"이므로, 접미사를 전부 넣으면 부분 문자열이 전부 경로로 나타난다.

**핵심 등식 — 노드 하나 = 서로 다른 부분 문자열 하나**

```
모든 부분 문자열 s[i..j] 는
    '접미사 s[i..] 의 접두사' 다

 트라이에서
    접미사를 넣으면 그 모든 접두사가 '경로'로 만들어진다
    경로 하나 = 뿌리가 아닌 노드 하나

 따라서
    서로 다른 부분 문자열의 개수 = 뿌리를 뺀 노드의 개수

 "abc" 로 확인

   i=0 : "abc" 를 넣는다   -> 노드 a, ab, abc      (3개 새로 생김)
   i=1 : "bc"  를 넣는다   -> 노드 b, bc           (2개 새로 생김)
   i=2 : "c"   를 넣는다   -> 노드 c               (1개 새로 생김)
   합 6

   (root)
     +-- a --- b --- c        <- a, ab, abc
     +-- b --- c              <- b, bc
     +-- c                    <- c

   부분 문자열 : a, b, c, ab, bc, abc = 6개    테스트 allDistinct 의 기대값과 같다
```

**왜 중복 제거가 필요 없는가**

```java
MapTrie.Node next = cur.children.get(c);
if (next == null) {
    next = new MapTrie.Node();
    cur.children.put(c, next);
    nodes++;              // 새 노드를 만들 때만 센다
}
cur = next;
```

```
"aaa" 로 확인 (기대값 3)

 i=0 : "aaa"
     root -> 'a' 없다 -> 새 노드 (nodes=1)      경로 "a"
          -> 'a' 없다 -> 새 노드 (nodes=2)      경로 "aa"
          -> 'a' 없다 -> 새 노드 (nodes=3)      경로 "aaa"

 i=1 : "aa"
     root -> 'a' 이미 있다 -> 재사용, 안 셈      경로 "a"   (이미 셌다)
          -> 'a' 이미 있다 -> 재사용, 안 셈      경로 "aa"  (이미 셌다)

 i=2 : "a"
     root -> 'a' 이미 있다 -> 재사용, 안 셈

 nodes = 3   (a, aa, aaa)
 중복을 따로 거르지 않았는데 3이 나왔다

 왜 :
    "같은 부분 문자열" = "뿌리에서 같은 글자 순서를 따라간 것" = "같은 경로"
    트라이에서 같은 경로는 같은 노드다 -- 두 번 만들 수가 없다
    => 중복 제거가 자료구조에 내장되어 있다

 테스트가 이 지점을 직접 노린다 :
    assertEquals(3, countDistinctSubstrings("aaa"),
        "a, aa, aaa 뿐이다. 6 이 나오면 중복을 세고 있다")
    -- 6 은 n(n+1)/2 = 3x4/2, 즉 '중복을 안 걸렀을 때의 값'이다
```

- 논리: `HashSet<String>` 에 부분 문자열을 다 넣어 세는 방식과 답은 같다.\
  차이는 **문자열을 만들지 않는다**는 것이다 — 경로를 걷기만 한다.
- 비용(왜): `HashSet` 방식은 부분 문자열마다 `substring` 으로 새 문자열을 만들어 O(n^3) 시간·공간이 된다.\
  트라이 방식은 O(n^2) 이다.

**검증표** (테스트의 기대값)

| 입력 | 답 | 왜 |
|---|---|---|
| `"a"` | 1 | a |
| `"abc"` | 6 | 전부 다름 → n(n+1)/2 = 3x4/2 |
| `"aaa"` | 3 | a, aa, aaa (중복 제거됨) |
| `"abab"` | 7 | a, b, ab, ba, aba, bab, abab |
| `"banana"` | 15 | 21 - 6(중복) |
| `"mississippi"` | 53 | 66 - 13(중복) |
| `"x" x 500` | 500 | 길이마다 하나씩 |

- 논리: 위 표의 `n(n+1)/2` 가 **상한**이다 — 모든 부분 문자열이 서로 다를 때의 값.
- 논리: 겹치는 부분 문자열이 많을수록 답이 작아진다 — `"aaa"` 가 6이 아니라 3인 이유.

**왜 n 이 커지면 무너지는가**

```
노드 수 상한 = 부분 문자열의 최대 개수 = n(n+1)/2

  n =     100  ->     5,050
  n =   1,000  ->   500,500        <- quadraticGrowth 테스트의 상한
  n =  10,000  -> 50,005,000
  n = 100,000  -> 5,000,050,000    (50억)

 노드 하나의 실제 크기 (MapTrie.Node)
     TreeMap 객체 하나 + boolean + int + 객체 헤더
     비어 있는 TreeMap 도 수십 바이트를 쓴다 -> 노드 하나에 최소 50~100바이트
     (원본에 근거 없음 -- 내 추론)

 n = 100,000 이면 50억 노드 x 약 50바이트 = 250GB
 -> 아예 못 만든다. 시간도 O(n^2) = 10^10 걸음이라 끝나지 않는다
```

```java
@Test
@Timeout(20)
@DisplayName("길이 1000 이면 노드가 최대 50만 개다")
void quadraticGrowth() {
    // 주기적인 문자열을 쓰면 안 된다. "abcabcabc..." 는 부분 문자열이 몇 개 안 나온다.
    java.util.Random rnd = new java.util.Random(2026L);
    StringBuilder sb = new StringBuilder(1000);
    for (int i = 0; i < 1000; i++) {
        sb.append((char) ('a' + rnd.nextInt(26)));
    }
    int n = TrieProblems.countDistinctSubstrings(sb.toString());
    assertTrue(n > 450_000 && n <= 1000 * 1001 / 2,
            "부분 문자열 " + n + "개 - 길이의 제곱에 비례해서 늘어난다");
}
```

- 논리: 테스트 주석이 중요한 힌트를 준다 — **주기적인 문자열을 쓰면 안 된다**.\
  `"abcabcabc..."` 는 부분 문자열이 겹쳐서 몇 개 안 나오므로 O(n^2) 성질이 안 드러난다.
- 논리: 무작위 문자열이라야 부분 문자열이 거의 전부 달라 상한(50만)에 가까워진다 — 45만 이상을 요구하는 이유다.
- 논리: `singleCharRepeated`("x" 500개 → 500)가 그 반대 극단이다.\
  같은 입력 길이에서 답이 500일 수도 있고 12만일 수도 있다 — **내용에 따라 크기가 결정된다**.
- 한계: 그래서 실무에서는 **접미사 배열(suffix array)** 이나 **접미사 오토마타(suffix automaton)** 를 쓴다.\
  같은 정보를 O(n) 또는 O(n log n) 공간에 담는다 — README 가 "그것들이 존재하는 이유"라고 못 박는다.
- 한계: 이 풀이는 **트라이의 한계를 보여주기 위한 풀이**다.\
  접두사 공유로 노드를 아끼는 구조인데도, 입력이 접미사 전부이면 아낄 것이 별로 없어 제곱으로 터진다.

> **접미사 배열(suffix array)** — 모든 접미사를 사전순으로 정렬한 인덱스 배열. 트리 대신 정수 배열 하나로 같은 질의를 답한다.\
> 예: 길이 n 문자열에 대해 노드 n(n+1)/2개 대신 정수 n개만 쓴다 — 21번 챕터의 주제다.

**질문별 답**

- Q: 문제 3을 어떻게 푸는가?\
  A: 시작 위치 `i` 를 옮겨 가며 접미사 `s[i..]` 를 뿌리부터 한 글자씩 밀어 넣고, **새 노드를 만들 때만 센다**.\
  모든 부분 문자열은 어떤 접미사의 접두사이므로, 뿌리를 뺀 노드 개수가 곧 서로 다른 부분 문자열의 개수다.

- Q: 접미사를 전부 넣는데 왜 중복 제거를 따로 안 해도 되는가?\
  A: 같은 부분 문자열은 뿌리에서 **같은 경로**이고, 트라이에서 같은 경로는 같은 노드라 두 번 만들어질 수가 없기 때문이다.\
  `children.get(c)` 가 이미 있으면 재사용하고 카운터를 올리지 않는 한 줄이 중복 제거 전부다.\
  `"aaa"` 가 6이 아니라 3이 나오는 것이 그 증거다.

- Q: n 이 커지면 왜 무너지는가?\
  A: 노드 수가 최대 `n(n+1)/2` 로 **길이의 제곱에 비례**하기 때문이다.\
  n=1,000이면 50만 개로 견디지만 n=100,000이면 50억 개라 메모리로도 시간으로도 불가능하다.\
  접두사 공유로 노드를 아끼는 구조인데 입력이 접미사 전부라 아낄 것이 거의 없다 — 접미사 배열·접미사 오토마타가 존재하는 이유다.

### B. 자료구조의 특성

#### 4. 트라이가 왜 필요한가 — 해시맵과 BST가 못 하는 이유는 서로 다르다

**질문**: 05-hash-map 과 06-bst 로는 "car 로 시작하는 것 전부"가 왜 안 되는가 — 해시맵이 못 하는 이유와 BST 가 흉내는 내지만 비싼 이유는 서로 다른가.

**답: 다르다. 하나는 원리의 문제, 하나는 비용의 문제다.**

**해시맵 — 해싱이 접두사 관계를 파괴한다**

```
좋은 해시 함수의 목표 = '고르게 흩뿌리기' (충돌을 줄이려면 그래야 한다)

    hash("car")  -> 버킷 12
    hash("card") -> 버킷 3
    hash("care") -> 버킷 47
    hash("dog")  -> 버킷 12      <- car 와 같은 버킷일 수도 있다

 한 글자만 달라도 해시값이 완전히 달라지도록 설계되어 있다 (눈사태 효과)
 => "car 로 시작한다"는 성질이 저장 위치에 전혀 반영되지 않는다
 => 모으려면 모든 버킷의 모든 키를 꺼내 검사하는 수밖에 없다  ->  O(n x L)

 이건 '기능이 빠진 것'이 아니다
 해시맵의 강점(O(1) 조회)을 만드는 바로 그 성질이 접두사 관계를 지운다
 -> 원리적으로 못 한다
```

> **눈사태 효과(avalanche effect)** — 입력이 한 비트만 달라져도 해시값의 절반 가까이가 달라지는 성질.\
> 예: 좋은 해시 함수일수록 `"car"` 와 `"card"` 의 해시값이 아무 관계도 없게 나온다 — 그것이 충돌을 줄이는 방법이다.

**BST — 순서는 살아 있지만 비교가 비싸다**

```
BST 는 사전순으로 정렬해 둔다 -> 같은 접두사를 가진 키는 연속 구간에 모인다

    ... "cap", "car", "card", "care", "careful", "cars", "cat", ...
                ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                "car" 로 시작하는 것들 = 연속 구간

 흉내내는 법 : "car" 이상 "cas" 미만의 범위 질의
    -> 시작 위치 찾기 + 그 뒤로 순회

 왜 비싼가
    (1) 비교 한 번이 '문자열 비교' 라 최악 O(L) 이다
        -> 시작 위치 찾기가 O(L x log n)
    (2) 비교할 때마다 '공통 접두사를 처음부터 다시 읽는다'
        "car" vs "card" 를 비교하려면 c, a, r 을 또 읽는다
        "car" vs "care" 도 c, a, r 을 또 읽는다
        같은 세 글자를 log n 번 반복해서 훑는다

 트라이는
    c, a, r 을 딱 한 번씩만 읽고 그 자리에 도착한다 -> O(L)
    도착한 노드의 부분 트리가 곧 "car 로 시작하는 것 전부" 다
```

- 논리: BST는 **할 수는 있다** — 답이 나온다.\
  문제는 같은 글자를 반복해서 읽는 낭비가 `log n` 배 쌓인다는 것이다.
- 논리: 해시맵은 **할 수 없다** — 저장 구조가 그 정보를 버렸기 때문이다.
- 논리: 이 차이가 중요한 이유는 **개선의 방향이 다르기** 때문이다.\
  BST는 상수를 줄이는 문제이고, 해시맵은 자료구조를 바꿔야 하는 문제다.

**세 구조의 비용표** (원본 `Trie.java` 주석의 표)

| 질문 | 해시맵 | BST | 트라이 |
|---|---|---|---|
| `contains(w)` | **O(1)** 평균 | O(log n · L) | O(L) |
| "car로 시작하는 것 전부" | O(n) 전수 | O(log n · L + k) | **O(L + 출력)** |
| 공통 접두사 | O(n · L) | O(n · L) | **O(L)** |
| 정렬 순회 | O(n log n) | O(n) | O(n) |

- 논리: 트라이가 모든 칸에서 이기는 것이 아니다 — `contains` 는 해시맵이 더 싸다(평균 O(1)).
- 논리: 트라이가 유일하게 압도하는 칸이 **접두사 관련 질의**다.\
  그 질의를 안 한다면 트라이를 쓸 이유가 없다.

**트라이의 핵심 한 문장**

```
"키를 통째로 저장하지 않는다. 한 글자가 간선 하나이고, 경로가 곧 키다."

  해시맵 : 버킷 어딘가에 "card" 라는 String 객체가 통째로 들어 있다
  BST    : 노드 어딘가에 "card" 라는 String 객체가 통째로 들어 있다
  트라이 : 어디에도 "card" 라는 글자 뭉치가 없다
           c -> a -> r -> d 라는 '길'이 있을 뿐이다

  그래서 car, card, care 가 c-a-r 을 공유한다
  그래서 "car 로 시작하는 것"이 부분 트리 하나로 딱 떨어진다
```

> **공유 접두사(shared prefix)** — 여러 키가 같은 앞부분을 쓰는 것. 트라이에서는 같은 노드 경로가 된다.\
> 예: `MapTrieTest.prefixesShareNodes` 가 `car`, `card`, `care` 를 넣으면 노드가 11개가 아니라 **5개**(c,a,r,d,e)임을 확인한다.

**질문별 답**

- Q: 해시맵으로는 왜 안 되는가?\
  A: 해시 함수가 비슷한 키를 **일부러 멀리 흩뿌리기** 때문이다.\
  `"car"` 와 `"card"` 의 저장 위치에 아무 관계가 없으므로 모든 버킷을 전수 탐색(O(n·L))하는 수밖에 없다.\
  O(1) 조회를 만드는 바로 그 성질이 접두사 관계를 지운 것이라, 기능을 추가해서 고칠 수 있는 문제가 아니다.

- Q: BST가 흉내는 내지만 비싼 이유는?\
  A: 사전순 정렬 덕에 같은 접두사가 연속 구간에 모여 있어 범위 질의로 답을 낼 수는 있다.\
  그러나 비교 하나가 문자열 비교(O(L))이고, 비교할 때마다 **공통 접두사를 처음부터 다시 읽는다**.\
  같은 세 글자를 `log n` 번 반복해서 훑는 낭비가 쌓여 O(L log n + k)가 된다.

- Q: 두 이유가 서로 다른가?\
  A: 다르다.\
  해시맵은 **원리적으로 불가능**하고(정보 자체가 없다), BST는 **가능하지만 비싸다**(정보는 있는데 반복해서 읽는다).\
  트라이는 그 반복을 없앤다 — 글자를 한 번씩만 읽고 도착한 노드가 곧 답의 부분 트리다.

#### 5. 언제 쓰고 언제 쓰면 안 되는가

**질문**: 어떤 형태의 데이터·접근 패턴에 트라이가 적합하고, 언제 쓰면 안 되는가. `contains` 만 필요한 워크로드에서 해시맵 대신 트라이를 쓰면 무엇을 더 내고 무엇도 못 얻는가.

**적합한 패턴**

- 논리: 질의에 **접두사**가 들어간다 — 자동완성, 검색어 추천, 우편번호·전화번호 대역 조회.
- 논리: 키들이 **접두사를 많이 공유한다** — URL, 파일 경로, IP 주소, 도메인 이름.\
  공유가 많을수록 노드가 적게 들고 메모리 이득이 생긴다.
- 논리: **사전순 순회**가 필요하다 — 트라이는 순회가 곧 사전순이라 정렬이 공짜다.
- 논리: 문자 집합이 **작고 고정**이다(a~z, 0~9) — `ArrayTrie` 로 O(1) 자식 접근을 쓸 수 있다.
- 논리: `countWithPrefix` 처럼 **접두사 단위의 집계**가 필요하다.

**쓰면 안 되는 패턴**

- 한계: `contains` 만 필요하다 — 해시맵이 더 싸고 메모리도 덜 쓴다.
- 한계: 키가 **길고 공유가 거의 없다** — 랜덤 해시값, UUID, 암호화된 토큰.\
  노드 수가 총 글자 수에 가까워져 메모리만 폭발한다.
- 한계: 문자 집합이 **크다** — 한글(1만 자 이상)이나 유니코드 전체면 `ArrayTrie` 가 불가능하고 `MapTrie` 도 맵 오버헤드가 커진다.
- 한계: **값(value)을 함께 저장**해야 하고 접두사 질의는 없다 — 그냥 `HashMap<String, V>` 다.
- 한계: 키가 문자열이 아니다 — 트라이는 "글자의 열"이라는 구조에 기대므로 임의 객체에는 못 쓴다.

**`contains` 만 필요한 워크로드에서 트라이를 쓰면**

```
 무엇을 더 내는가

 (1) 메모리
     해시맵 : 키 문자열 하나 + 엔트리 하나 = 단어당 약 60~100바이트
     트라이 : 글자마다 노드 하나
              MapTrie 노드 = TreeMap + boolean + int + 헤더 ≈ 50~100바이트
              "application" 한 단어가 노드 11개 = 500~1000바이트
     공유가 없으면 단어 하나에 10배 이상 든다
     (원본에 근거 없음 -- 내 추론: 객체 크기는 JVM·구현에 따라 다르다)

 (2) 참조 추적(pointer chasing)
     해시맵 : 해시 계산 한 번 + 배열 인덱싱 한 번 = 메모리 접근 1~2회
     트라이 : 글자마다 노드 객체를 따라간다 = 메모리 접근 L회
              노드들이 메모리 여기저기 흩어져 있어 캐시 미스가 L번 날 수 있다

 (3) MapTrie 는 글자마다 TreeMap 조회 = O(log(자식 수))
     따라서 엄밀히는 O(L x log 26) 이지 O(L) 이 아니다

 무엇을 못 얻는가

     아무것도. contains 만 쓰면 접두사 능력을 한 번도 안 쓰는 것이다
     비싼 값을 치르고 산 기능을 쓰지 않는 상태다
```

> **참조 추적(pointer chasing)** — 포인터를 따라 객체를 하나씩 건너뛰며 메모리를 읽는 것. 연속 배열 접근보다 훨씬 느리다.\
> 예: 트라이에서 `"card"` 를 찾으려면 노드 4개를 차례로 따라가는데, 각 노드가 메모리 다른 곳에 있으면 캐시 미스가 4번 난다.

- 논리: 해시맵의 `contains` 가 **O(1) 평균**인 것은 "글자 수와 무관"이 아니다.\
  해시 계산에 O(L)이 들고, 비교에도 O(L)이 든다 — 다만 **한 번씩만** 든다.
- 논리: 트라이의 `contains` 도 O(L)이다.\
  차수(차원)는 같고 **상수가 다르다** — 트라이는 L번의 포인터 추적, 해시맵은 1번의 배열 접근.
- 논리: 그래서 "트라이가 O(L)이라 빠르다"는 말은 절반만 맞다.\
  트라이의 진짜 이득은 `contains` 가 아니라 **n에 의존하지 않는 접두사 질의**다.

**질문별 답**

- Q: 어떤 데이터·접근 패턴에 적합한가?\
  A: 질의에 접두사가 들어가고(자동완성·대역 조회), 키들이 접두사를 많이 공유하며(URL·경로·IP), 문자 집합이 작고 고정이며, 사전순 순회나 접두사 단위 집계가 필요한 경우다.

- Q: 언제 쓰면 안 되는가?\
  A: `contains` 만 필요할 때, 키가 길고 공유가 거의 없을 때(UUID·해시값), 문자 집합이 클 때, 값만 매달면 되고 접두사 질의가 없을 때다.

- Q: `contains` 만 필요한데 트라이를 쓰면 무엇을 더 내고 무엇을 못 얻는가?\
  A: 더 내는 것은 **메모리**(글자마다 노드 객체 — 공유가 없으면 단어당 10배 가까이), **참조 추적 비용**(글자마다 포인터를 따라가 캐시 미스 L번), 그리고 `MapTrie` 라면 글자마다 맵 조회(`O(L log Σ)`)다.\
  못 얻는 것은 **아무것도 없다** — 그게 문제다.\
  비싼 값을 치르고 산 접두사 능력을 한 번도 쓰지 않는 상태이기 때문이다.

#### 6. `contains(w)` 가 O(L) 이고 n 에 전혀 의존하지 않는 이유

**질문**: 구조적 이유는 무엇인가. "키를 통째로 저장하지 않는다 — 경로가 곧 키다"가 비용 표의 어느 칸으로 나타나는가.

**impl 코드**

```java
Node findNode(String s) {
    Node cur = root;
    for (int i = 0; i < s.length(); i++) {
        cur = cur.children.get(s.charAt(i));
        if (cur == null) {
            return null;
        }
    }
    return cur;
}

@Override
public boolean contains(String word) {
    requireWord(word);
    Node n = findNode(word);
    return n != null && n.end;
}
```

- 논리: 루프가 **`word.length()` 번** 돈다.\
  트라이에 단어가 몇 개 들어 있는지는 루프 조건에 나타나지 않는다.
- 논리: 한 번의 반복에서 하는 일은 "현재 노드의 자식 표에서 글자 하나를 찾기"다 — 그것도 n과 무관하다.

**왜 n이 비용에 안 나타나는가**

```
비교 : 선형 탐색 / BST / 트라이에서 "card" 를 찾는 비용

 선형 탐색 (배열)
     n 개를 하나씩 "card" 와 비교      -> n 번 비교 x 비교당 O(L) = O(n x L)
     n 이 늘면 비용이 그대로 는다

 BST
     트리 높이만큼 비교               -> log n 번 비교 x 비교당 O(L) = O(L log n)
     n 이 100만이면 20번쯤 비교한다 -> n 이 늘면 천천히 는다

 트라이
     c -> a -> r -> d 네 걸음          -> O(L)
     매 걸음에서 '어느 자식으로 갈지'가 글자 하나로 결정된다
     -> 다른 단어들이 몇 개 있든 갈 곳은 그 글자가 정한다
     -> n 이 100만이든 1개든 네 걸음

 핵심 : 탐색은 보통 '후보를 좁히는' 일인데
        트라이는 좁힐 후보가 없다. 글자가 곧 주소다
```

```
 트라이 한 걸음의 그림

     현재 노드
       +----------------------+
       | end = false          |
       | wordsBelow = 4823    |
       | children:            |
       |    'a' -> 노드A       |
       |    'r' -> 노드B       |   <- 'r' 을 찾아 그쪽으로 간다
       |    'u' -> 노드C       |
       +----------------------+

     그 아래에 단어가 4823개 걸려 있어도
     'r' 을 고르는 비용은 자식 표에서 'r' 을 찾는 비용뿐이다
     자식 표의 크기는 문자 집합 크기(Σ)로 묶여 있고 n 과 무관하다
```

- 비용(왜): `ArrayTrie` 는 자식 찾기가 배열 인덱싱이라 **O(1)** → `contains` 가 정확히 O(L)이다.
- 비용(왜): `MapTrie` 는 `TreeMap` 조회라 **O(log(자식 수))** → 엄밀히는 `O(L log Σ)` 다.\
  Σ가 26이면 `log 26 ≈ 4.7` 로 상수 취급되므로 표에는 O(L)로 적힌다.
- 비용(왜): 어느 쪽이든 **n이 식에 없다** — 그것이 이 질문의 답이다.

> **Σ(시그마, 문자 집합 크기)** — 쓰일 수 있는 서로 다른 문자의 개수.\
> 예: a~z만 쓰면 Σ=26이고, 유니코드 전체면 Σ가 10만 이상이라 자식 표의 비용이 무시할 수 없게 된다.

**"경로가 곧 키"가 비용 표의 어느 칸으로 나타나는가**

| 칸 | 값 | "경로가 곧 키"가 만든 결과 |
|---|---|---|
| `contains(w)` | O(L) | 키 비교가 없다 — 경로를 걸을 뿐이다. n이 사라진다 |
| "car로 시작하는 것 전부" | **O(L + 출력)** | 접두사가 노드 하나로 특정되고, 그 아래가 곧 답이다 |
| 공통 접두사 | **O(L)** | 공유 접두사가 이미 하나의 경로로 합쳐져 있다 |
| 메모리 | 총 글자 수에 비례 | 공유되는 앞부분이 한 번만 저장된다(이득)… |
| 메모리 | 노드마다 자식 표 | …대신 노드마다 표를 들어야 한다(대가) |

- 논리: 가장 선명하게 드러나는 칸은 **"공통 접두사 O(L)"** 이다.\
  해시맵도 BST도 O(n·L)인 자리에서 트라이만 O(L)이다.\
  다른 구조는 모든 키를 봐야 알 수 있는 것을, 트라이는 **뿌리에서 외길을 걷는 것만으로** 안다(문제 1).
- 논리: 두 번째는 `keysWithPrefix` 의 **O(L + 출력)** 이다.\
  "출력에 비례"가 가능한 것은 답이 부분 트리 하나로 모여 있기 때문이다.
- 논리: 대가는 **메모리 칸**에 나타난다.\
  키를 통째로 저장하지 않는 대신 글자마다 노드와 자식 표를 든다 — 11번의 5만 칸 계산이 그 대가의 구체적 모습이다.

**한계 — "n에 의존하지 않는다"의 정확한 의미**

- 한계: **비교 횟수**가 n에 의존하지 않는다는 뜻이지, 실제 시간이 n과 완전히 무관하다는 뜻은 아니다.\
  n이 커지면 트라이가 커져 캐시에 안 들어가고 메모리 지역성이 나빠진다.
- 한계: 긴 키에는 불리하다 — L이 크면 O(L)도 크다.\
  해시맵은 해시 계산에 O(L)을 한 번 쓰고 끝나지만 트라이는 L번 포인터를 따라간다.
- 한계: `contains("appl")` 이 `false` 인 것은 `end` 표시 덕이다.\
  경로가 있어도 단어가 아닐 수 있다는 것이 7번의 주제다.

**질문별 답**

- Q: `contains(w)` 가 O(L) 이고 n에 전혀 의존하지 않는 구조적 이유는?\
  A: 매 걸음에서 **어느 자식으로 갈지가 글자 하나로 완전히 결정되기** 때문이다.\
  탐색은 보통 후보를 좁히는 일이라 후보 수(n)가 비용에 들어가는데, 트라이는 좁힐 후보가 없다 — 글자가 곧 주소다.\
  그래서 루프가 `word.length()` 번 돌고 n은 식에 나타나지 않는다.\
  (엄밀히는 자식 표 조회 비용이 붙어 `ArrayTrie` 는 O(L), `MapTrie` 는 `O(L log Σ)` 다.)

- Q: "경로가 곧 키다"가 비용 표의 어느 칸으로 나타나는가?\
  A: 가장 선명한 것은 **공통 접두사 O(L)** 칸이다 — 해시맵·BST가 O(n·L)인 자리에서, 공유 접두사가 이미 하나의 경로로 합쳐져 있어 외길을 걷는 것만으로 답이 나온다.\
  다음은 **"car로 시작하는 것 전부" O(L + 출력)** 칸이다 — 답이 부분 트리 하나로 모여 있기 때문이다.\
  대가는 **메모리 칸**에 나타난다 — 키를 통째로 저장하지 않는 대신 글자마다 노드와 자식 표를 들어야 한다.

#### 7. `end` 표시와 `startsWith("")` 의 함정

**질문**: 노드가 있느냐만으로는 왜 부족한가. `end` 표시를 빼면 "app" 과 "apple" 이 왜 구분이 안 되는가. `startsWith` 를 `findNode(p) != null` 로 쓰면 빈 트라이에서 `startsWith("")` 가 왜 true 가 되는가 — 이걸 막는 조건은 무엇인가.

**노드의 존재 ≠ 단어의 존재**

```
"apple" 만 넣은 트라이

   (root)
      |
      a          노드가 있다.  하지만 "a" 는 단어가 아니다
      |
      p          노드가 있다.  하지만 "ap" 는 단어가 아니다
      |
      p          노드가 있다.  하지만 "app" 는 단어가 아니다
      |
      l          노드가 있다.  하지만 "appl" 는 단어가 아니다
      |
      e*         노드가 있고 end = true.  "apple" 만 단어다

 노드가 생기는 이유는 두 가지다
   (1) 여기서 끝나는 단어가 있어서
   (2) 더 긴 단어가 여기를 '지나가서'

 (2) 때문에 생긴 노드는 단어가 아니다
 => 노드 유무만으로는 둘을 구분할 수 없다 -> end 표시가 필요하다
```

```java
@Test
@DisplayName("접두사는 단어가 아니다")
void prefixIsNotWord() {
    WordDictionary d = dict("apple");
    assertFalse(d.search("app"), "end 대신 자식 유무를 보면 여기서 true 가 나온다");
    assertFalse(d.search("appl"));
    assertTrue(d.search("apple"));
}
```

**"app" 과 "apple" 이 둘 다 있을 때**

```
둘 다 넣으면

   (root) - a - p - p* - l - e*
                    ^        ^
                    |        end = true ("apple")
                    end = true ("app")

 end 가 없다면 :
    "app" 노드는 자식 'l' 을 갖고 있다
    -> "자식이 있으면 단어가 아니다" 라는 규칙을 쓰면 "app" 이 사라진다
    -> "자식이 없으면 단어다" 라는 규칙을 쓰면 "app" 을 못 찾는다
    어느 규칙으로도 둘을 동시에 만족시킬 수 없다

 => "여기서 끝나는 단어가 있다" 는 사실은 구조에서 유도되지 않는다
    독립된 정보이므로 따로 적어야 한다
```

- 논리: 이것이 `end` 가 **필수 정보**인 이유다 — 트리 모양에서 계산할 수 없다.
- 논리: README 가 숫자로 못 박는다 — **`end` 를 빼면 130개 중 13개가 무너진다.**
- 논리: `contains` 가 `n != null && n.end` 인 것도 같은 이유다.\
  `findNode` 는 "경로가 있나"를, `end` 는 "그 경로가 단어인가"를 답한다.

**`startsWith("")` 의 함정**

```java
@Override
public boolean startsWith(String prefix) {
    requireWord(prefix);
    // 노드가 있느냐로는 부족하다. **뿌리는 단어가 하나도 없어도 존재한다.**
    // 빈 트라이에 startsWith("") 를 물으면 그것만으로는 true 가 나온다.
    Node n = findNode(prefix);
    return n != null && n.wordsBelow > 0;
}
```

```
 빈 트라이 (아무것도 안 넣음)

    Node root = new Node();     <- 뿌리는 생성자에서 이미 만들어진다
                                   단어가 하나도 없어도 존재한다

 findNode("") 를 부르면
    for 루프가 한 번도 안 돈다 (s.length() == 0)
    return cur;   -> cur 은 아직 root 다
    => null 이 아니다!

 그래서 startsWith 를 findNode(p) != null 로 쓰면
    startsWith("") == true      <- 틀렸다. 단어가 하나도 없는데 "있다"고 답한다

 막는 조건 : n.wordsBelow > 0
    빈 트라이의 root.wordsBelow 는 0 이므로 false 가 된다
```

- 논리: 뿌리는 **데이터가 아니라 구조의 시작점**이다 — 단어 유무와 무관하게 존재한다.
- 논리: 그래서 "노드가 있다"와 "단어가 있다" 사이에 한 칸의 틈이 있고, `wordsBelow` 가 그 틈을 메운다.
- 논리: README 가 개발 과정을 적어 뒀다 — **"테스트를 먼저 써놓고 구현했는데 이 한 줄에서 걸렸습니다."**\
  테스트 우선이 아니었다면 못 잡았을 버그라는 뜻이다.

> **`wordsBelow`** — 그 노드를 지나는(그 노드 아래에서 끝나는) 단어의 개수. 노드 자신에서 끝나는 단어도 포함한다.\
> 예: `"car"`, `"card"`, `"care"` 가 있으면 `r` 노드의 `wordsBelow` 는 3이다.

- 논리: `end` 대신 `wordsBelow > 0` 을 쓰는 이유는 **접두사 노드 자신은 `end` 가 아닐 수 있기** 때문이다.\
  `"apple"` 만 있을 때 `startsWith("app")` 은 true여야 하는데, `app` 노드의 `end` 는 false다.
- 한계: `wordsBelow` 가 없다면 부분 트리를 훑어 단어가 하나라도 있는지 확인해야 한다 — O(부분 트리 크기)다.\
  `wordsBelow` 덕에 O(L)로 끝난다(8번).
- 한계: `wordsBelow` 를 증감시키는 코드가 `insert`/`remove` 양쪽에 흩어져 있어, 한쪽만 틀려도 **조용히 어긋난다**.\
  그래서 테스트가 `verify` 재귀로 저장값과 실제 개수를 대조한다(`wordsBelowIsAccurate`).

**질문별 답**

- Q: 노드가 있느냐만으로는 왜 부족한가?\
  A: 노드가 생기는 이유가 둘이기 때문이다 — **여기서 끝나는 단어가 있어서**와 **더 긴 단어가 지나가서**.\
  후자로 생긴 노드는 단어가 아니므로, 노드 유무로는 둘을 구분할 수 없다.

- Q: `end` 를 빼면 "app" 과 "apple" 이 왜 구분이 안 되는가?\
  A: `"app"` 노드는 단어이면서 동시에 자식 `'l'` 을 갖는다.\
  "자식이 있으면 단어가 아니다"로 판정하면 `"app"` 이 사라지고, "자식이 없으면 단어다"로 판정하면 `"app"` 을 못 찾는다.\
  "여기서 끝나는 단어가 있다"는 사실은 트리 모양에서 유도되지 않는 독립된 정보라, 따로 적어야 한다.\
  README 기준 이걸 빼면 130개 중 13개가 무너진다.

- Q: `startsWith` 를 `findNode(p) != null` 로 쓰면 빈 트라이에서 `startsWith("")` 가 왜 true 가 되는가?\
  A: `findNode("")` 는 루프를 한 번도 안 돌고 `root` 를 그대로 반환하는데, **뿌리는 단어가 하나도 없어도 생성자에서 이미 존재**하기 때문이다.\
  막는 조건은 `n.wordsBelow > 0` 이다 — 빈 트라이의 `root.wordsBelow` 가 0이라 false가 된다.\
  `end` 가 아니라 `wordsBelow` 를 보는 이유는 접두사 노드 자신은 단어가 아닐 수 있기 때문이다(`"apple"` 만 있을 때 `startsWith("app")` 은 true여야 한다).

#### 8. `wordsBelow` 가 동시에 해결하는 두 가지

**질문**: 무엇과 무엇인가. `countWithPrefix` 가 왜 부분 트리를 안 훑어도 되는가, 그리고 `remove` 에서 "이 노드를 끊어도 되는가"를 어떻게 판단해 주는가. "app" 과 "apple" 이 있을 때 "apple" 을 지우다 "app" 을 날리는 실수는 왜 안 나는가.

**해결 1 — `countWithPrefix` 가 O(L)**

```java
@Override
public int countWithPrefix(String prefix) {
    requireWord(prefix);
    Node n = findNode(prefix);
    return n == null ? 0 : n.wordsBelow;
}
```

```
 저장할 것인가 계산할 것인가

 (A) 계산 : 부분 트리를 훑어 end 를 센다
     비용 = O(부분 트리 노드 수) = O(매칭 단어 총 글자 수)
     접두사 "a" 에 10만 개가 걸려 있으면 10만 걸음

 (B) 저장 : 각 노드가 '내 아래에 단어가 몇 개인지'를 들고 있다 (impl)
     비용 = O(L) -- 접두사 길이만큼 내려가 그 칸을 읽으면 끝
     접두사 "a" 에 10만 개가 걸려 있어도 한 걸음

 대가 : insert / remove 마다 지나는 노드의 wordsBelow 를 전부 갱신해야 한다
        -> insert 비용은 어차피 O(L) 이므로 차수가 안 바뀐다
        -> 공짜나 다름없다

 Trie.java 의 주석이 이 지점을 가리킨다 :
   "keysWithPrefix(p).size() 와 답은 같다. 다만 비용이 달라야 한다.
    왜 이 메서드가 따로 있는지는 성능 테스트가 말해준다."
```

- 논리: 계약에 `countWithPrefix` 가 따로 있는 이유가 이것이다 — 답이 아니라 **비용**이 존재 이유다.
- 논리: 2번 문제의 `autocomplete` 와 같은 교훈의 다른 얼굴이다.\
  거기서는 "다 모으고 자르지 마라", 여기서는 "다 세지 말고 미리 세어 둬라"다.

> **미리 계산해 두기(precomputation)** — 질의 때마다 계산하는 대신, 갱신 시점에 결과를 유지해 두는 기법.\
> 예: `wordsBelow` 는 `insert`/`remove` 때 1씩 조정해 두므로 `countWithPrefix` 가 훑지 않고 읽기만 한다.

**해결 2 — `remove` 에서 끊을 자리 판정**

```java
@Override
public boolean remove(String word) {
    requireWord(word);
    if (!contains(word)) {
        return false;
    }
    root.wordsBelow--;
    Node cur = root;
    for (int i = 0; i < word.length(); i++) {
        char c = word.charAt(i);
        Node next = cur.children.get(c);
        next.wordsBelow--;
        if (next.wordsBelow == 0) {
            cur.children.remove(c);
            return true;
        }
        cur = next;
    }
    cur.end = false;
    return true;
}
```

- 논리: **위에서 아래로 내려가며 1씩 깎는다**.
- 논리: `wordsBelow` 가 0이 되는 노드를 만나면 "그 아래에 단어가 하나도 안 남았다"는 뜻이다.\
  그 순간 **통째로 끊고 즉시 반환**한다 — 그 아래는 더 볼 필요가 없다.
- 논리: 0이 되는 노드를 끝까지 못 만나면(다른 단어들이 그 경로를 계속 쓰고 있으면) 마지막 노드의 `end` 만 끈다.
- 논리: 즉 `wordsBelow` 가 "어디서 끊어야 하는가"를 **한 번의 하향 순회로** 알려준다.\
  재귀로 내려갔다가 올라오며 판단하는 방식(후위 순회)이 필요 없다.

**"app" 과 "apple" 이 있을 때 `remove("apple")`**

```
 시작 상태 ( "app", "apple" 두 단어 )

   (root)          wordsBelow = 2
      |
      a            wordsBelow = 2
      |
      p            wordsBelow = 2
      |
      p*           wordsBelow = 2   end=true ("app")
      |
      l            wordsBelow = 1
      |
      e*           wordsBelow = 1   end=true ("apple")

 remove("apple") 추적

   contains("apple") -> true  (통과)
   root.wordsBelow: 2 -> 1

   i=0 'a' : next = a 노드, wordsBelow 2 -> 1    0 이 아니다 -> 내려간다
   i=1 'p' : next = p 노드, wordsBelow 2 -> 1    0 이 아니다 -> 내려간다
   i=2 'p' : next = p* 노드, wordsBelow 2 -> 1   0 이 아니다 -> 내려간다
                                                  ^^^^^^^^^^^^^^^^^^^^
                                                  여기가 핵심.
                                                  "app" 이 아직 이 노드를 쓰고 있다
   i=3 'l' : next = l 노드, wordsBelow 1 -> 0    0 이다! -> p*.children.remove('l')
                                                  return true

 끝난 뒤

   (root)          wordsBelow = 1
      |
      a            wordsBelow = 1
      |
      p            wordsBelow = 1
      |
      p*           wordsBelow = 1   end=true ("app")   <- 살아 있다
                   children = {} (l 가지가 통째로 끊겼다)

 "app" 을 날리는 실수가 왜 안 나는가:
    a, p, p 노드의 wordsBelow 가 0 이 되지 않았기 때문이다
    그 값이 곧 "이 노드에 아직 걸린 단어가 있다"는 증거다
    끊는 판단이 '추측'이 아니라 '세어 둔 숫자'에 근거한다
```

- 논리: 반대 방향도 확인해 보면 이해가 굳는다 — `remove("app")` 이라면?\
  `a`, `p`, `p*` 를 내려가며 각각 2→1이 되고 0이 아니므로 끊지 않는다.\
  마지막 노드 `p*` 에 도달해 `cur.end = false` 만 끈다 — `"apple"` 의 경로 `l-e` 는 그대로다.
- 논리: 끊기와 `end` 끄기가 **서로 다른 두 가지 마무리**다.\
  아래에 아무도 없으면 가지를 끊고, 있으면 표시만 끈다.

**05번 tombstone 과 같은 계열인 이유**

```
 05-hash-map (개방 주소법)에서의 삭제

   키를 지운 자리를 그냥 비우면(null) 탐사(probe) 사슬이 끊긴다
   그 자리를 지나 뒤에 있던 키를 영영 못 찾게 된다
   -> 그래서 '지웠음' 표시(tombstone)를 남긴다

 09-trie 에서의 삭제

   단어를 지웠다고 그 경로를 통째로 끊으면
   그 경로를 공유하던 다른 단어까지 사라진다
   -> 그래서 '아직 쓰는 사람이 있는지'(wordsBelow)를 보고 끊을지 정한다

 공통 구조
   1. 자료구조가 자리를 '공유' 한다 (탐사 사슬 / 접두사 경로)
   2. 삭제가 그 공유를 깨뜨릴 수 있다
   3. 단순히 지우면 남아 있어야 할 데이터가 함께 사라진다
   4. 예외도 로그도 없다 -- 조용히 사라진다

 공통 해법
   '지운 자리를 어떻게 처리하는가'를 따로 설계한다
   05: tombstone 으로 사슬을 유지  /  09: 참조 계수로 끊을 자리를 판정
```

> **참조 계수(reference counting)** — 어떤 자원을 아직 쓰고 있는 사용자 수를 세어 두었다가, 0이 되면 해제하는 기법.\
> 예: `wordsBelow` 가 그 노드를 쓰는 단어 수이고, 0이 되는 순간 노드를 끊는다 — GC의 참조 계수와 같은 발상이다.

- 논리: `wordsBelow` 는 사실상 **참조 계수**다.\
  "이 노드를 지나는 단어가 몇 개인가"이고, 0이 되면 해제한다.
- 한계: 테스트가 이것을 두 방향으로 검사한다.\
  `wordsBelowIsAccurate` 는 저장값이 실제 단어 수와 같은지, `nodesAreActuallyDetached` 는 노드가 **실제로 끊겼는지**를 본다.
- 한계: 끊지 않고 `end` 만 끄는 구현도 **답은 맞는다**(`contains` 가 false를 준다).\
  그러나 노드가 계속 쌓여 메모리 누수가 된다 — `verify` 가 `assertTrue(actual > 0, "아래에 단어가 없는데 노드가 남아 있다")` 로 그것을 잡는다.
- 한계: `clear()` 가 `root = new Node()` 로 뿌리를 **갈아치우는** 것도 같은 맥락이다.\
  옛 뿌리를 그대로 두고 자식만 비우면 아래 전체가 GC되지 않는다(`clearReplacesRoot`).

**질문별 답**

- Q: `wordsBelow` 가 동시에 해결하는 두 가지는?\
  A: (1) `countWithPrefix` 를 부분 트리 순회 없이 **O(L)** 로 만드는 것, (2) `remove` 에서 **어느 노드부터 끊어도 되는지**를 판정해 주는 것이다.

- Q: `countWithPrefix` 가 왜 부분 트리를 안 훑어도 되는가?\
  A: 각 노드가 "내 아래의 단어 수"를 **미리 세어 들고 있기** 때문이다.\
  접두사 길이만큼 내려가 그 칸을 읽으면 끝이라, 접두사에 10만 개가 걸려 있어도 한 번의 읽기다.\
  대가는 `insert`/`remove` 마다 지나는 노드의 값을 갱신하는 것인데, 그 연산이 어차피 O(L)이라 차수가 바뀌지 않는다.

- Q: `remove` 에서 "이 노드를 끊어도 되는가"를 어떻게 판단해 주는가?\
  A: 위에서 아래로 내려가며 1씩 깎다가 **0이 되는 노드**를 만나면 그 아래에 단어가 하나도 없다는 뜻이므로 통째로 끊고 즉시 끝낸다.\
  끝까지 0을 못 만나면 다른 단어들이 그 경로를 쓰고 있다는 뜻이므로 마지막 노드의 `end` 만 끈다.

- Q: "apple" 을 지우다 "app" 을 날리는 실수는 왜 안 나는가?\
  A: `a`, `p`, `p` 노드의 `wordsBelow` 가 2→1이 되어 **0이 되지 않기** 때문이다.\
  그 값이 "아직 이 노드에 걸린 단어가 있다"는 증거이므로 끊지 않고 지나간다.\
  0이 되는 곳은 `l` 노드이고, 거기서부터만 끊긴다.\
  05번 tombstone과 같은 계열인 이유는 둘 다 **자리를 공유하는 구조에서 삭제가 공유를 깨뜨릴 수 있고, 그 손상이 조용하기** 때문이다 — 해법도 같다: 지운 자리를 어떻게 처리할지 따로 설계한다.

#### 9. `collect` 에서 `StringBuilder` 를 붙였다 떼는 이유

**질문**: 왜 붙였다 떼는가. 떼는 걸 빠뜨리면 결과가 어떻게 되는가. 매번 새 문자열을 만들면 비용이 어디에 붙는가.

**impl 코드**

```java
static void collect(Node node, StringBuilder path, List<String> out) {
    if (node.end) {
        out.add(path.toString());
    }
    for (Map.Entry<Character, Node> e : node.children.entrySet()) {
        path.append(e.getKey().charValue());
        collect(e.getValue(), path, out);
        path.deleteCharAt(path.length() - 1);
    }
}
```

- 논리: `path` 는 **뿌리에서 현재 노드까지의 경로**를 담은 하나의 버퍼다.\
  재귀 호출들이 그 버퍼 하나를 공유한다.
- 논리: 내려갈 때 글자를 붙이고, 돌아올 때 떼어 **버퍼를 원래대로 되돌린다**.\
  이것이 백트래킹의 기본형이다.

> **백트래킹(backtracking)** — 한 갈래를 시도해 보고 돌아올 때 상태를 원래대로 되돌린 뒤 다음 갈래를 시도하는 방식.\
> 예: `append` 로 내려가고 `deleteCharAt` 으로 되돌려야 형제 가지가 깨끗한 상태에서 시작한다.

**떼는 것을 빠뜨리면**

```java
@Test
@DisplayName("형제 가지로 넘어갈 때 글자를 떼어낸다")
void backtracksProperly() {
    // ab, ac, ad 를 넣으면 collect 가 a 로 내려갔다가
    // b 를 붙였다 떼고, c 를 붙였다 떼고, d 를 붙인다.
    // 떼는 것을 빠뜨리면 abcd 같은 것이 나온다.
    MapTrie t = mapTrie("ab", "ac", "ad");
    assertEquals(List.of("ab", "ac", "ad"), t.keysWithPrefix("a"));
}
```

```
 트라이 ( "ab", "ac", "ad" )

   (root) - a - b*
                c*
                d*

 (A) 올바른 경우 (떼기 있음)     path 의 변화

   collect(a 노드, path="a")
     'b' append   -> path = "ab"
       collect(b*) -> out.add("ab")
     deleteCharAt -> path = "a"          <- 되돌림
     'c' append   -> path = "ac"
       collect(c*) -> out.add("ac")
     deleteCharAt -> path = "a"          <- 되돌림
     'd' append   -> path = "ad"
       collect(d*) -> out.add("ad")
     deleteCharAt -> path = "a"

   결과 [ab, ac, ad]   OK

 (B) 떼기를 빠뜨린 경우

   collect(a 노드, path="a")
     'b' append   -> path = "ab"
       collect(b*) -> out.add("ab")
     (되돌리지 않음)                      <- path 가 "ab" 인 채로 남는다
     'c' append   -> path = "abc"
       collect(c*) -> out.add("abc")      <- "abc" 라는 단어는 없다!
     'd' append   -> path = "abcd"
       collect(d*) -> out.add("abcd")     <- 이것도 없다

   결과 [ab, abc, abcd]   X

 예외도 안 난다. 리스트 길이도 3으로 맞는다. 내용만 조용히 틀린다
```

- 논리: 깊이가 깊어질수록 **앞선 형제의 글자가 계속 누적**되어 결과가 뒤죽박죽이 된다.
- 논리: `deepThenShallow` 테스트가 이것을 더 강하게 잡는다 — `"abcdef"` 와 `"b"` 를 넣으면 깊은 가지에서 돌아온 뒤 얕은 가지를 처리해야 한다.\
  되돌리기가 없으면 `"b"` 가 `"abcdefb"` 로 나온다.
- 한계: 실수해도 **결과 개수는 맞는다** — 개수만 검사하는 테스트는 통과한다.\
  전형적인 조용한 실패다.

**왜 매번 새 문자열을 만들지 않는가**

```
 (A) 버퍼 하나를 공유하며 붙였다 떼기 (impl)

     path 객체 = 1개
     append / deleteCharAt = 각각 O(1) (StringBuilder 의 끝 조작)
     toString() 은 단어를 찾았을 때만 -> 출력 개수만큼만 문자열이 생긴다

     비용 = O(방문 노드 수) + O(출력 단어의 총 글자 수)

 (B) 재귀마다 새 문자열 만들기

     collect(child, path + c, out)    <- 이렇게 쓰면

     노드를 방문할 때마다 길이 d 짜리 문자열을 새로 만든다 (d = 그 노드의 깊이)
     비용 = sum over 모든 방문 노드 of (그 노드의 깊이)

     깊이 L 짜리 단어 n 개면 대략 n x L^2 / 2
     예: L=20, n=10만 -> 10^5 x 400 / 2 = 2 x 10^7 글자 복사
         게다가 그만큼의 String 객체가 생겼다 버려진다 -> GC 압박

 정리 : 비용이 '노드 수'가 아니라 '노드 수 x 깊이'로 커진다
        L 이 붙는 자리가 하나 늘어난다
```

- 비용(왜): 자바 `String` 은 **불변**이라 `path + c` 는 매번 새 배열 복사다.
- 비용(왜): 그래서 `StringBuilder` 를 쓰고, 그 대가로 **되돌리기 책임**을 떠안는다.\
  가변 버퍼를 공유하는 대신 상태 관리를 직접 하는 거래다.
- 논리: `keysWithPrefix` 가 `new StringBuilder(prefix)` 로 시작하는 것도 같은 이유다 — 접두사를 결과에 붙이려고 매번 앞에 이어 붙이지 않는다.\
  `prefixIsPrepended` 테스트가 결과가 전부 접두사로 시작함을 확인한다.
- 한계: 재귀 안에서 공유 버퍼를 쓰면 **멀티스레드에서 안전하지 않다**.\
  같은 `path` 를 두 스레드가 만지면 즉시 깨진다.\
  (원본에 근거 없음 — 내 추론)
- 한계: `MapTrie.collect` 가 `static` 이고 테스트가 직접 호출한다(`collectDirectly`).\
  경로 관리가 인자로 드러나 있어야 그게 가능하다 — 설계상 의도다.

**질문별 답**

- Q: `StringBuilder` 를 붙였다 떼는 이유는?\
  A: 재귀 호출들이 **버퍼 하나를 공유**하기 때문이다.\
  내려갈 때 붙인 글자를 돌아올 때 떼어야 형제 가지가 올바른 상태(= 그 부모까지의 경로)에서 시작한다.\
  새 문자열을 만들지 않기 위해 가변 버퍼를 쓰고, 그 대가로 되돌리기 책임을 진다.

- Q: 떼는 걸 빠뜨리면 결과가 어떻게 되는가?\
  A: 앞선 형제의 글자가 계속 누적되어 존재하지 않는 단어가 나온다 — `["ab","ac","ad"]` 가 `["ab","abc","abcd"]` 로 나온다.\
  예외도 없고 결과 개수도 맞아서, 개수만 검사하는 테스트는 통과한다.

- Q: 매번 새 문자열을 만들면 비용이 어디에 붙는가?\
  A: 노드를 방문할 때마다 그 깊이만큼의 글자를 복사하므로, 비용이 **"노드 수"가 아니라 "노드 수 × 깊이"** 로 커진다.\
  길이 L 단어 n개면 대략 `n·L²/2` 글자 복사이고, 그만큼의 `String` 객체가 생겼다 버려져 GC 압박도 붙는다.\
  자바 `String` 이 불변이라 `path + c` 가 매번 새 배열 복사이기 때문이다.

#### 10. 최악의 사용 패턴 — `WordDictionary` 의 와일드카드

**질문**: `"....."` 처럼 전부 점인 패턴을 물으면 총 비용이 얼마인가. 반대로 최선(`"apple"`)은 얼마인가. 왜 앞쪽부터 점이면 가지치기가 안 되는가. `"....e"` 를 빠르게 하려면 무엇을 더 만들어야 하는가.

**impl 코드**

```java
private static boolean search(MapTrie.Node node, String pattern, int i) {
    if (node == null) {
        return false;
    }
    if (i == pattern.length()) {
        return node.end;
    }
    char c = pattern.charAt(i);
    if (c == '.') {
        for (MapTrie.Node child : node.children.values()) {
            if (search(child, pattern, i + 1)) {
                return true;
            }
        }
        return false;
    }
    return search(node.children.get(c), pattern, i + 1);
}
```

- 논리: 글자가 정해져 있으면 갈 곳이 **하나**다 — 그냥 내려간다.
- 논리: `.` 이면 갈 곳이 **자식 전부**다 — 하나씩 시도하고 하나라도 성공하면 true를 되돌린다.
- 논리: **되돌아오기(backtracking) 코드가 따로 없다**.\
  재귀 호출이 false를 반환하고 for 루프가 다음 자식으로 넘어가는 것 자체가 되돌아오기다.

> **와일드카드(wildcard)** — 아무 글자 하나(또는 여럿)에나 맞는 자리 표시자.\
> 예: 여기서 `.` 은 정확히 한 글자에 맞으므로 `".ad"` 는 `"bad"`, `"dad"`, `"mad"` 에 맞고 `"ad"` 에는 안 맞는다.

**되돌아오기가 실제로 필요한 경우** (`needsBacktracking`)

```java
// .b 로 시작하는 갈래가 둘이다. ab 쪽으로 먼저 내려가면 막히고,
// 되돌아와 cb 쪽을 시도해야 답을 찾는다.
WordDictionary d = dict("abx", "cby");
assertTrue(d.search(".by"), "첫 갈래에서 막혔다고 false 를 반환하면 여기서 틀린다");
```

```
 트라이

   (root) - a - b - x*
          - c - b - y*

 search(".by")
   i=0, c='.'  -> 자식 {a, c} 를 순서대로 시도

   시도 1 : a 로 내려감
       i=1, 'b' -> a 의 자식에 b 있다 -> 내려감
       i=2, 'y' -> b 의 자식에 y 없다 -> children.get('y') = null
                   -> search(null, ...) -> false
       -> 이 갈래 실패, for 루프가 다음 자식으로 넘어간다   <- 이것이 되돌아오기

   시도 2 : c 로 내려감
       i=1, 'b' -> 있다 -> 내려감
       i=2, 'y' -> 있다 -> 내려감
       i=3 == pattern.length() -> node.end -> true

   -> true 반환 (중간 return true 로 즉시 빠져나온다)

 첫 갈래에서 false 를 그대로 반환하는 구현이면 여기서 틀린다
```

**비용 분석**

```
 문자 집합 크기 Σ, 패턴 길이 L, 단어 수 n

 (A) 최선 : 점이 하나도 없다  ("apple")
     갈 곳이 매 단계 하나로 정해진다
     비용 = O(L) (MapTrie 면 O(L log Σ))
     -- 그냥 contains 와 같다

 (B) 최악 : 전부 점 ("....." = 점 5개)
     매 단계에서 자식 전부로 갈라진다
     방문해야 하는 노드 = 깊이 5 이내의 모든 노드
     비용 = O(깊이 L 이내의 트라이 노드 수)
            상한은 min(n x L, Σ^L) 이다
              -- 단어가 적으면 n x L 로 묶이고 (트라이에 노드가 그만큼뿐)
              -- 단어가 많으면 Σ^L 로 묶인다 (그 깊이에 있을 수 있는 노드의 최대)
     Σ=26, L=5 면 Σ^L = 26^5 ≈ 1,190만
     즉 "길이 5짜리 단어가 하나라도 있나"를 묻는 것과 같고, 트라이 전체를 훑는다

 (C) 중간 : 접두사가 고정되고 뒤에 점 ("aaaaa.")
     앞 5글자로 노드 하나가 특정된다 -> 거기서 자식만 본다
     비용 = O(L + Σ)
     -- 사실상 최선에 가깝다
```

```java
@Test
@Timeout(15)
@DisplayName("접두사가 고정되면 점이 있어도 싸다")
void fixedPrefixIsCheap() {
    WordDictionary d = new WordDictionary();
    for (int i = 0; i < 100_000; i++) {
        d.addWord(encode(i));
    }
    for (int q = 0; q < 100_000; q++) {
        assertTrue(d.search("aaaaa."), "aaaaaa 는 0 을 인코딩한 것이다");
    }
}
```

- 논리: 이 테스트가 (C)를 못 박는다 — 10만 단어에 10만 질의인데 15초 안에 끝난다.\
  `"aaaaa."` 는 앞 5글자가 고정이라 한 경로만 내려가고 마지막에 자식 몇 개만 본다.
- 논리: 같은 사전에 `"......"`(점 6개)를 물으면 트라이 전체(약 10만 노드 이상)를 훑는다.\
  같은 자료구조, 같은 길이의 패턴인데 **점의 위치 하나로** 비용이 갈린다.

**왜 앞쪽부터 점이면 가지치기가 안 되는가**

```
 가지치기(pruning) = "이쪽에는 답이 없다"를 알아서 갈래를 버리는 것

 고정 글자는 가지를 Σ 분의 1 로 줄인다
     현재 노드의 자식이 26개라도, 'a' 를 요구하면 그중 하나만 남는다

 점은 가지를 하나도 못 줄인다
     자식 전부를 시도해야 한다

 그래서 '점이 앞에 있을수록' 비싸다

   "a...."  : 1단계에서 26 -> 1 로 줄인 뒤 아래로 퍼진다
              퍼지는 출발점이 노드 1개
   "....a"  : 1~4단계에서 계속 26배씩 퍼진다
              마지막 5단계에 와서야 걸러낸다
              이미 퍼질 대로 퍼진 뒤에 거르는 것이라 아낀 것이 없다

   26^4 = 456,976 배의 차이가 '거르는 시점' 하나에서 난다

 원리 : 좁히는 조건은 '빨리' 적용할수록 싸다
        (DB 쿼리에서 선택도 높은 조건을 먼저 태우는 것과 같은 이야기)
```

> **가지치기(pruning)** — 탐색 도중 "이 갈래에는 답이 없다"를 판정해 통째로 건너뛰는 것.\
> 예: 패턴의 글자가 고정되어 있으면 자식 26개 중 하나만 보면 되므로 나머지 25갈래가 통째로 잘린다.

**`"....e"` 를 빠르게 하려면**

```
 문제 : 끝 글자만 고정이면 앞에서 못 거른다

 해법 : 뒤집은 문자열로 트라이를 하나 더 만든다 (역방향 트라이)

   원본 트라이        : "apple" 을 a-p-p-l-e 로 저장
   역방향 트라이      : "apple" 을 e-l-p-p-a 로 저장 (뒤집어서 넣는다)

   질의 "....e" 가 들어오면
      패턴도 뒤집는다 -> "e...."
      역방향 트라이에서 "e...." 를 찾는다
      -> 1단계에서 'e' 로 26 -> 1 로 줄인다 -> 싸다

 대가
   - 메모리가 2배 (같은 단어를 두 번 저장)
   - insert / remove 를 두 곳에 해야 한다 (동기화 실수의 여지)
   - 가운데만 고정된 패턴("..p..")은 여전히 안 풀린다
     그런 것까지 하려면 접미사 트리/오토마타나 n-gram 색인이 필요하다

 README 가 이 해법을 그대로 적어 뒀다 :
   "`\"....e\"`를 빠르게 하려면 뒤집은 문자열로 트라이를 하나 더 만드는 식이 됩니다."
```

- 논리: 이것이 **색인을 추가해 질의 패턴에 맞춘다**는 일반 원리의 사례다.\
  DB에서 `WHERE col LIKE '%abc'` 를 위해 역방향 색인을 두는 것과 같다.
- 논리: 자료구조 하나로 모든 질의를 싸게 만들 수는 없다 — 자주 오는 질의 모양에 맞춰 색인을 고른다.
- 한계: `deepBranch` 테스트의 `"....."` + `"c"` 같은 패턴은 여전히 비싸다.\
  점이 앞에 몰려 있기 때문이다.

**질문별 답**

- Q: `"....."` 처럼 전부 점이면 총 비용은?\
  A: 깊이 L 이내의 **모든 노드를 방문**해야 하므로 `O(min(n·L, Σ^L))` 이다.\
  Σ=26, L=5면 `26^5 ≈ 1,190만` 이 상한이고, 사실상 "그 길이의 단어가 하나라도 있나"를 묻느라 트라이 전체를 훑는 것과 같다.

- Q: 최선(`"apple"`)은?\
  A: 점이 하나도 없으면 매 단계 갈 곳이 하나로 정해져 **O(L)** 이다(`MapTrie` 면 `O(L log Σ)`).\
  그냥 `contains` 와 같은 비용이다.

- Q: 왜 앞쪽부터 점이면 가지치기가 안 되는가?\
  A: 고정 글자는 자식 Σ개 중 하나만 남겨 **가지를 Σ분의 1로 줄이는데**, 점은 하나도 못 줄이기 때문이다.\
  `"a...."` 는 1단계에서 26→1로 좁힌 뒤 퍼지고, `"....a"` 는 4단계 동안 26배씩 퍼진 뒤에야 거른다 — 거르는 시점 하나로 `26^4 ≈ 46만` 배가 난다.\
  좁히는 조건은 빨리 적용할수록 싸다.

- Q: `"....e"` 를 빠르게 하려면 무엇을 더 만들어야 하는가?\
  A: **뒤집은 문자열로 트라이를 하나 더** 만든다.\
  질의도 뒤집어 `"e...."` 로 물으면 1단계에서 가지가 잘려 싸진다.\
  대가는 메모리 2배와 `insert`/`remove` 를 두 곳에 해야 하는 동기화 부담이고, 가운데만 고정된 패턴(`"..p.."`)은 여전히 못 푼다.

#### 11. `MapTrie` 와 `ArrayTrie` 의 트레이드오프

**질문**: 트레이드오프는 무엇인가. `ArrayTrie` 는 왜 사전순 정렬이 공짜로 따라오고, 그 대가로 무엇을 내는가 — 20글자 단어 100개에 참조 슬롯이 5만 칸 잡히는 계산이 어떻게 나오는가. 범위 밖 문자를 `insert`/`remove` 는 예외로, 조회는 false/빈 리스트/0 으로 처리하는 이유는?

**차이는 자식 표 하나**

```java
// MapTrie
static final class Node {
    final Map<Character, Node> children = new TreeMap<>();
    boolean end;
    int wordsBelow;
}
```

```java
// ArrayTrie
static final int ALPHABET = 26;

static final class Node {
    final Node[] children = new Node[ALPHABET];
    boolean end;
    int wordsBelow;
}
```

- 논리: 알고리즘은 **완전히 같다** — `insert`/`remove`/`collect` 의 흐름이 한 줄도 다르지 않다.\
  README 도 "달라지는 지점에만 TODO가 있다"고 적는다.
- 논리: 바뀌는 것은 "자식을 어떻게 찾고 어떻게 도는가" 딱 두 가지다.

| 축 | `MapTrie` | `ArrayTrie` |
|---|---|---|
| 문자 집합 | 아무거나 (한글·이모지·기호) | **a~z만** |
| 자식 접근 | `TreeMap.get` = O(log(자식 수)) | **배열 인덱싱 = O(1)** |
| 빈 자식의 비용 | 없다(있는 만큼만) | **26칸을 늘 잡는다** |
| 사전순 순회 | `TreeMap` 이 해준다 | **0~25로 돌면 그게 사전순** |
| 노드 크기 | `TreeMap` 객체 + 엔트리들 | 참조 26개 = 104~208바이트 |
| 범위 밖 문자 | 그냥 담긴다 | 예외 또는 "없음" |

**왜 사전순이 공짜인가**

```java
static void collect(Node node, StringBuilder path, List<String> out) {
    if (node.end) {
        out.add(path.toString());
    }
    for (int i = 0; i < ALPHABET; i++) {
        if (node.children[i] == null) {
            continue;
        }
        path.append((char) ('a' + i));
        collect(node.children[i], path, out);
        path.deleteCharAt(path.length() - 1);
    }
}

private static int requireIndex(char c) {
    int i = indexOf(c);
    if (i < 0) {
        throw new IllegalArgumentException("ArrayTrie 는 a~z 만 담는다: '" + c + "'");

    return i;
}

@Override
public void insert(String word) {
    requireWord(word);
    for (int i = 0; i < word.length(); i++) {
        requireIndex(word.charAt(i));      // 먼저 전부 검사한다
    }
    if (contains(word)) { return; }
    // ... 여기서부터 실제로 넣는다
}

```
 변경 연산 (insert / remove) -> 예외

   "Apple" 을 넣어 달라는 요청은 '들어줄 수 없는 요청'이다
   조용히 무시하면 호출자는 넣었다고 믿는다 -> 나중에 contains 가 false 를 주고 당황한다
   => 못 하는 일은 못 한다고 말해야 한다 (fail fast)

 조회 연산 (contains / startsWith / keysWithPrefix / countWithPrefix) -> "없다"

   "Apple 이 들어 있나?" 는 '들어줄 수 있는 요청'이다
   답은 명확하게 '아니오' 다 -- ArrayTrie 에는 대문자가 들어갈 수 없으므로
   확실히 없다는 것을 알 수 있다
   => 예외를 던질 이유가 없다. 정직한 답이 존재한다

> **빠른 실패(fail fast)** — 잘못된 요청을 즉시 예외로 알려, 손상된 상태가 퍼지기 전에 멈추는 설계.\
> 예: `insert("Apple")` 을 조용히 무시하면 호출자가 "넣었다"고 믿는 채로 진행하지만, 예외를 던지면 그 자리에서 알게 된다.

**전부 검사한 뒤에 넣는 이유 — all-or-nothing**

```java
@Test
@DisplayName("insert 는 한 글자만 벗어나도 통째로 거부한다")
void allOrNothing() {
    ArrayTrie t = new ArrayTrie();
    assertThrows(IllegalArgumentException.class, () -> t.insert("appleZ"));
    assertFalse(t.startsWith("a"), "앞부분만 넣어두고 예외를 던지면 반쯤 들어간 상태가 남는다");
    assertEquals(0, t.size());
}
```

```
 검사를 '넣으면서' 하면 (틀린 구현)

   'a','p','p','l','e' 까지 노드를 만들고 wordsBelow 를 올린다
   'Z' 에서 예외를 던진다

   -> 트라이에 a-p-p-l-e 경로가 남는다
   -> wordsBelow 가 올라가 있는데 end 는 안 찍혀 있다
   -> size() 가 이상해지고 startsWith("a") 가 true 가 된다
   => '반쯤 들어간 상태'

 검사를 '먼저 전부' 하면 (impl)

   for 루프로 모든 글자를 requireIndex 에 통과시킨다
   하나라도 걸리면 아무것도 건드리기 전에 예외를 던진다
   => 상태가 전혀 안 바뀐다 (원자성)
```

> **원자성(atomicity)** — 연산이 전부 성공하거나 전부 실패하고, 중간 상태가 남지 않는 성질.\
> 예: `insert("appleZ")` 는 `'Z'` 때문에 실패하는데, 검증을 먼저 몰아서 하므로 `"apple"` 부분이 남지 않는다.

- 논리: 08번의 `rejectsNegativeWeight` 테스트("실패한 추가가 개수를 늘리면 안 된다")와 정확히 같은 규칙이다.
- 논리: `remove` 도 같다 — `requireIndex` 루프를 먼저 돌린다.
- 한계: `indexOf` 의 범위 검사가 **양쪽**이어야 한다.\
  `'{'` 는 `'z'` 바로 다음 문자(123)라 `c - 'a'` 가 26이 되어 **음수 검사만으로는 안 걸린다**.\
  테스트 `aboveRange` 가 `'{'`, `'~'`, `'가'` 로 그것을 노린다.

**질문별 답**

- Q: 두 구현의 트레이드오프는?\
  A: **문자 집합의 자유 vs 자식 접근 비용과 정렬**이다.\
  `MapTrie` 는 어떤 문자든 담고 있는 만큼만 메모리를 쓰지만 자식 조회가 `O(log(자식 수))` 다.\
  `ArrayTrie` 는 a~z만 담고 노드마다 26칸을 늘 잡지만 자식 접근이 O(1)이고 사전순이 공짜다.

- Q: `ArrayTrie` 는 왜 사전순이 공짜인가?\
  A: **인덱스가 곧 문자**이기 때문이다(`i ↔ 'a'+i`).\
  0에서 25까지 오름차순으로 도는 것이 그대로 'a'에서 'z'까지 도는 것이라, 순서를 유지하는 장치가 하나도 없는데 결과가 정렬되어 나온다.\
  순서 정보가 자료 배치 속에 이미 들어 있는 것이다.

- Q: 5만 칸 계산은 어떻게 나오는가?\
  A: 무작위 20글자 단어 100개는 앞부분이 거의 안 겹쳐 노드가 약 2,000개(테스트 기준 **1,923개**) 생긴다.\
  노드마다 26칸이므로 `1,923 × 26 = 49,998` — 약 5만 칸이다.\
  실제로 쓰이는 자식 참조는 노드 하나당 하나씩이라 **1,922개**뿐이고, 나머지 96%는 `null` 로 비어 있다.

- Q: 범위 밖 문자를 변경은 예외로, 조회는 "없다"로 처리하는 이유는?\
  A: `insert`/`remove` 는 **들어줄 수 없는 요청**이라 조용히 무시하면 호출자가 넣었다고 오해하므로 즉시 예외를 던진다(fail fast).\
  조회는 **들어줄 수 있는 요청**이고, 대문자가 들어갈 수 없는 구조이므로 "확실히 없다"는 정직한 답이 존재한다 — 예외를 던질 이유가 없다.\
  덧붙여 `insert` 는 글자를 **전부 먼저 검사한 뒤** 넣기 시작한다 — 도중에 실패하면 반쯤 들어간 상태가 남기 때문이다.

#### 12. 10-lru-cache 로의 연결 — 유한한 공간에서 무엇을 버릴 것인가

**질문**: 트라이는 접두사를 공유해 노드를 아끼지만 그래도 노드 수가 폭발한다(문제 3의 n(n+1)/2). 저장 공간이 유한할 때 "무엇을 버릴 것인가"를 정하는 구조가 왜 따로 필요해지는가. 05번 `LinkedHashMap` 위에 접근 순서를 얹으면 LRU 가 된다고 했던 지점과 어떻게 이어지는가.

**01~09의 암묵적 전제**

```
 01 ~ 09 가 공통으로 깔고 있던 전제

     "넣은 것은 전부 들어 있다"
     "메모리는 필요한 만큼 쓸 수 있다"

 그래서 지금까지의 설계 질문은 전부 이것이었다
     같은 데이터를 '어떻게 배치하면' 원하는 질의가 싸지는가
     -> 배열이냐 링크냐, 정렬이냐 해시냐, 전 순서냐 부분 순서냐

 09 에서 그 전제가 처음으로 깨진다
     문제 3 : 길이 n 문자열의 부분 문자열을 전부 담으면 노드 n(n+1)/2 개
              n = 100,000 이면 50억 개 -> '배치'를 아무리 잘해도 안 들어간다
     ArrayTrie : 같은 트리인데 슬롯이 26배 -> 배치 선택으로 줄일 수 있는 한계가 있다

 배치로 못 줄이면 남는 선택은 하나뿐이다
     -> 전부 담기를 포기한다
     -> 무엇을 담고 무엇을 버릴지 정해야 한다      <- 10-lru-cache
```

- 논리: 09까지의 질문이 **"어떻게 담을 것인가"** 였다면, 10의 질문은 **"무엇을 담지 않을 것인가"** 다.
- 논리: 이것은 자료구조의 문제가 아니라 **정책(policy)** 의 문제다.\
  같은 해시맵 + 링크드 리스트로도 LRU·LFU·FIFO가 전부 가능하다 — 다른 것은 버리는 규칙이다.

> **축출 정책(eviction policy)** — 공간이 찼을 때 무엇을 버릴지 정하는 규칙.\
> 예: LRU는 "가장 오래 안 쓴 것", LFU는 "가장 적게 쓴 것", FIFO는 "가장 먼저 들어온 것"을 버린다.

**05번 `LinkedHashMap` 과 이어지는 지점**

```
 05-hash-map 에서 본 것

   HashMap       : 키 -> 값. 순서가 없다
   LinkedHashMap : HashMap + 원소들을 이중 연결 리스트로 꿰어 '순서'를 유지한다
                   기본은 '삽입 순서'

 10-lru-cache 에서 하는 것

   그 순서를 '삽입 순서'가 아니라 '접근 순서'로 바꾼다
      -> get(k) 를 부를 때마다 k 를 줄 맨 뒤로 옮긴다
      -> 그러면 줄의 맨 앞이 항상 '가장 오래 안 쓴 것'이 된다
   그리고 용량이 넘치면 줄의 맨 앞을 버린다

   자바에서는 두 스위치로 끝난다
      accessOrder = true            (생성자 인자)
      removeEldestEntry() 재정의    (언제 버릴지)

 즉 LRU 는 새 자료구조가 아니라
    "이미 있는 두 구조(해시맵 + 이중 연결 리스트)를 겹치고 정책을 얹은 것"이다
```

```
 왜 두 구조를 겹쳐야 하는가 (10번의 핵심)

   해시맵만 : "이 키가 어디 있나" O(1)  /  "가장 오래된 것이 뭔가" O(n)
   링크만   : "가장 오래된 것" O(1)     /  "이 키가 어디 있나" O(n)

   겹치면   : 둘 다 O(1)
              맵의 '값'을 값(V)이 아니라 '리스트의 노드'로 두는 것이 열쇠다
              -> 키로 노드를 O(1)에 찾고, 노드를 알면 링크 조작도 O(1)

   02번의 "노드를 알면 O(1), 인덱스로 찾으면 O(n)" 이 여기서 다시 쓰인다
```

- 논리: 09→10의 이동은 **자료구조에서 정책으로**의 이동이다.\
  구조는 이미 가진 것을 조합하고, 새로 배우는 것은 "무엇을 버릴지 정하는 규칙"이다.
- 논리: 10번 다음의 11-bloom-filter가 같은 흐름의 한 걸음 더다.\
  10은 **일부러 잊어서** 공간을 한정하고, 11은 **틀릴 수도 있게 해서** 공간을 더 줄인다.
- 논리: 세 챕터가 한 줄로 이어진다 — 전부 담기(09까지) → 일부만 담기(10) → 부정확하게 담기(11).

**트라이 자체에도 같은 질문이 온다**

- 논리: 실제 자동완성 서비스는 모든 검색어를 트라이에 넣지 않는다.\
  인기 있는 접두사만 유지하고 나머지는 버리거나 디스크로 내린다.
- 논리: 그때 필요한 것이 정확히 "무엇을 유지할 것인가"이고, 그 판단에 `wordsBelow` 같은 빈도 정보가 쓰인다.\

**질문별 답**

- Q: 저장 공간이 유한할 때 "무엇을 버릴 것인가"를 정하는 구조가 왜 따로 필요해지는가?\
  A: 01~09는 전부 **"넣은 것은 전부 들어 있다"** 를 전제로 배치만 고민했는데, 트라이에서 그 전제가 처음 깨지기 때문이다.\
  문제 3의 `n(n+1)/2` 는 n=10만이면 50억 노드라 **배치를 아무리 잘해도 안 들어간다**.\
  배치로 못 줄이면 남는 선택은 전부 담기를 포기하는 것뿐이고, 그러면 "무엇을 버릴지"라는 새로운 종류의 결정이 필요해진다 — 자료구조의 문제가 아니라 **정책의 문제**다.

- Q: 05번 `LinkedHashMap` 지점과 어떻게 이어지는가?\
  A: `LinkedHashMap` 은 해시맵에 이중 연결 리스트를 꿰어 **순서**를 유지하는 구조였고, 기본 순서가 '삽입 순서'였다.\
  그 순서를 **'접근 순서'로 바꾸고**(`get` 할 때마다 줄 맨 뒤로 옮긴다) 용량이 넘치면 줄 맨 앞을 버리면 그것이 LRU다.\
  자바에서는 `accessOrder = true` 와 `removeEldestEntry` 재정의 두 스위치로 끝난다.\
  즉 LRU는 새 자료구조가 아니라 **이미 있는 두 구조를 겹치고 그 위에 정책을 얹은 것**이며, 겹치는 이유는 해시맵의 약점("가장 오래된 것" O(n))과 링크의 약점("이 키가 어디 있나" O(n))이 정확히 서로를 메우기 때문이다.

**더 생각할 것**

- 같은 알고리즘을 자식 표만 바꿔 두 번 구현해 보는 것이 이 챕터의 뼈대다.\
  `MapTrie` 와 `ArrayTrie` 는 `insert`/`remove`/`collect` 의 흐름이 동일하고 "자식을 어떻게 찾고 어떻게 도는가"만 다르다 — **차이가 한 곳으로 모이게 설계하면 두 번째 구현이 싸진다**(07번 `MinHeap`/`MaxHeap` 과 같은 이야기).
- 이 챕터에는 "답은 맞는데 느린 풀이"가 둘 있다.\
  문제 2의 `keysWithPrefix().subList()` 와 `countWithPrefix` 를 부분 트리 순회로 구현하는 것.\
  둘 다 **정확성 테스트만으로는 못 걸러지고** 성능 테스트가 따로 필요했다 — 계약에 `countWithPrefix` 가 왜 따로 있는지가 그 증거다.
- 조용한 실패가 유난히 많은 챕터다.\
  `end` 를 빼면 접두사가 단어가 되고, `deleteCharAt` 을 빼면 없는 단어가 나오고, `wordsBelow` 갱신을 한쪽만 틀리면 개수가 어긋난다.\
  전부 예외 없이 결과만 틀리므로, 테스트가 **내부 구조를 직접 들여다보는**(`verify`, `findNode`, `children.size()`) 이유가 여기 있다.
