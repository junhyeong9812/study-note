## 정답

### B. 자료구조 특성

#### 1. 왜 세그먼트 트리가 필요한가 — 누적합·전수 훑기와의 갈림길

- Q: 세그먼트 트리는 왜 필요한가?\
  A: "값이 계속 바뀌는 배열"에 "구간 질문"이 쏟아지는 상황 때문이다.\
  구간 질문만 있으면 누적합으로 충분하고, 값 변경만 있으면 원본 배열에 대입 한 번이면 끝난다.\
  둘이 **같이** 오는 순간 기존 두 방법이 각각 한쪽에서 무너진다.\
  세그먼트 트리는 어느 쪽도 O(1) 로 만들지 않는 대신, **양쪽을 다 O(log n) 으로 묶는** 타협이다.

> **구간 질의(range query)** — 배열의 연속 구간 하나에 대해 접힌 답(합·최솟값·최댓값 등) 하나를 묻는 질문.\
> 예: `query(2, 6)` 은 `values[2]` 부터 `values[6]` 까지의 합을 묻는다.

> **누적합(prefix sum)** — `prefix[i] = a[0] + ... + a[i-1]` 을 미리 만들어 두고, 구간 합을 뺄셈 한 번으로 얻는 기법.\
> 예: `sum(l, r) = prefix[r+1] - prefix[l]` — 원소가 몇 개든 뺄셈 한 번이라 조회가 O(1) 이다.

- Q: 누적합으로는 무엇이 안 되는가?\
  A: **갱신**이 안 된다.\
  `prefix[i]` 는 `a[0..i-1]` 전부를 이미 삼켜 놓은 값이라, `a[2]` 하나를 고치면 `prefix[3]` 부터 `prefix[n]` 까지 전부 틀린 값이 된다.\
  즉 원소 하나를 고칠 때마다 뒤쪽 배열을 통째로 다시 계산해야 하므로 갱신 한 번이 **O(n)** 이다.\
  조회 O(1) 이라는 이득을 갱신 한 번이 전부 까먹는다.\
  README 표가 누적합을 "값이 안 바뀔 때"로 못박은 이유다.

원본 README 가 그 한 줄을 그대로 적어 놓았다.

```text
prefix[i] = a[0] + ... + a[i-1]
sum(l, r) = prefix[r+1] - prefix[l]
```

누적합의 갱신이 왜 O(n) 인지 그림으로 보면 이렇다.

```
a = [3, 1, 4, 1, 5, 9, 2, 6]
                                    a[2] 를 4 -> 10 으로 고치면

 prefix idx   0   1   2   3   4   5   6   7   8
 before      [0,  3,  4,  8,  9, 14, 23, 25, 31]
                          ^---------------------^
                          여기서부터 끝까지 전부 틀린다 (원소 하나에 n-2 칸)
 after       [0,  3,  4, 14, 15, 20, 29, 31, 37]

 세그먼트 트리에서 같은 변경:
                        tree[1]   <== 다시 계산
                       /        \
                 tree[2]        tree[3]   (그대로, 읽지도 않음)
                /      \
          tree[4]      tree[5]   <== 다시 계산은 tree[5] 쪽 한 줄뿐
          (그대로)      /    \
                  t[10]    t[11]
                  ^ 이 리프에 대입
 고치는 칸 = 뿌리에서 리프까지 한 줄 = 높이 = O(log n)
```

- Q: 매번 훑기로는 무엇이 안 되는가?\
  A: **조회**가 안 된다.\
  구간 `[from..to]` 를 매번 처음부터 더하면 한 번이 최악 **O(n)** 이다.\
  갱신은 `a[i] = v` 대입 한 번이라 O(1) 로 가장 싸지만, 조회가 쏟아지는 순간 전체가 n 에 끌려간다.\
  `SumSegmentTreeTest` 의 `naiveSum` 이 정확히 이 구현이고, 테스트는 이것을 "느린 정답"으로 두고 트리와 대조한다.

근거 — `src/test/java/com/datastructure/segment/SumSegmentTreeTest.java`

```java
    private static long naiveSum(long[] a, int from, int to) {
        long s = 0;
        for (int i = from; i <= to; i++) {
            s += a[i];
        }
        return s;
    }
```

- Q: 조회와 갱신의 비율이 선택을 어떻게 가르는가?\
  A: 세 방법의 총비용을 조회 q 번, 갱신 u 번, 원소 n 개로 써 보면 한눈에 갈린다.\
  매번 훑기 = `q x O(n) + u x O(1)`.\
  누적합 = `q x O(1) + u x O(n)`.\
  세그먼트 트리 = `(q + u) x O(log n)`.\
  즉 **한쪽이 0 에 가까우면 그쪽에 특화된 구조가 이기고, 둘이 비슷하면 세그먼트 트리가 이긴다.**\
  극단 예 — `q = 1, u = n` 이면 훑기는 `n + n = 2n`, 세그먼트 트리는 `(n+1) log n` 이라 **훑기가 log 배 빠르다.**\
  반대로 `q = n, u = n` 이면 훑기는 `n^2`, 세그먼트 트리는 `2n log n` 이라 차수 자체가 갈린다.

README 의 판단표를 그대로 옮기면 이렇다.

| | 조회 | 갱신 | 언제 |
|---|---|---|---|
| 매번 훑기 | O(n) | O(1) | 갱신이 압도적일 때 |
| 누적합 | **O(1)** | O(n) | **값이 안 바뀔 때** |
| 세그먼트 트리 | O(log n) | O(log n) | 둘 다 자주 일어날 때 |
| 펜윅 트리(17번) | O(log n) | O(log n) | 합만 필요할 때. 코드가 훨씬 짧다 |

- Q: 그 비율 차이를 코드로 못박은 자리는 어디인가?\
  A: `SumSegmentTreeTest.bothAreLogarithmic` 이다.\
  n = 200,000 배열에 `update` + `query(0, n-1)` 을 200,000 번 번갈아 돌리고 `@Timeout(20)` 을 건다.\
  테스트 주석이 이유를 직접 적어 놓았다 — "누적합이었다면 갱신 하나가 O(n) 이라 이 루프가 10^10 이 된다".\
  세그먼트 트리면 `2 x 200,000 x log2(200,000) ≈ 2 x 200,000 x 18 ≈ 7.2 x 10^6` 회 수준이라 즉시 끝난다.\
  "정답은 나오는데 시간 안에 못 끝내는 구현"을 손으로 겪게 하는 장치다.

**더 생각할 것**

- 실무에서 "조회 대 갱신 비율"은 먼저 재는 것이지 짐작하는 것이 아니다.\
  재보면 대개 한쪽으로 크게 쏠려 있고, 쏠려 있으면 세그먼트 트리보다 단순한 구조가 이긴다.
- 값이 "바뀐다"가 아니라 "뒤에 붙기만 한다"면 누적합을 버릴 필요가 없다 — append 는 `prefix` 한 칸 추가라 O(1) 이다.\
  세그먼트 트리가 필요한 것은 **중간이 바뀔 때**다.
- 규모가 커지면 갱신을 모아 배치로 반영하는 선택지가 생긴다.\
  초당 수만 건 갱신 + 초당 수 건 조회라면, 갱신은 배열에 그냥 쓰고 조회 직전에 누적합을 다시 만드는 쪽이 총비용이 낮을 수 있다.

#### 2. combine 이 결합법칙과 항등원을 요구하는 이유

- Q: combine 이 결합법칙을 요구하는 이유는 무엇인가?\
  A: **같은 구간이라도 트리가 어떻게 쪼개 접을지는 n 과 질문 구간이 정하기 때문**이다.\
  `build` 는 `mid = (lo + hi) >>> 1` 로 반씩 나누고, `query` 는 그 나뉜 모양대로 덩어리를 주워 담는다.\
  그래서 `[0..2]` 의 답이 `(a0 op a1) op a2` 로 계산될 수도, `a0 op (a1 op a2)` 로 계산될 수도 있다.\
  두 결과가 다르면 "같은 질문에 트리 모양에 따라 다른 답"이 나온다 — 자료구조가 성립하지 않는다.\
  그래서 `(a op b) op c = a op (b op c)` 가 **선택이 아니라 전제**다.

> **결합법칙(associative law)** — 묶는 순서를 바꿔도 결과가 같다는 성질. `(a op b) op c = a op (b op c)`.\
> 예: 덧셈은 `(1+2)+3 = 1+(2+3) = 6` 으로 같지만, 평균은 `avg(avg(1,2),3) = 2.25`, `avg(1,avg(2,3)) = 1.75` 로 다르다.

> **교환법칙(commutative law)** — 좌우를 바꿔도 결과가 같다는 성질. `a op b = b op a`.\
> 예: 문자열 잇기는 `"a"+"b" != "b"+"a"` 라 교환법칙이 없지만, 세그먼트 트리에는 그대로 올라간다.

- Q: 그런데 교환법칙은 왜 요구하지 않는가?\
  A: `combine` 이 항상 **왼쪽 자식을 첫 인자, 오른쪽 자식을 둘째 인자**로 받아 순서가 고정돼 있기 때문이다.\
  `build`·`update`·`query` 어디를 봐도 `combine(node*2, node*2+1)` 순서다.\
  좌우가 뒤바뀔 일이 없으니 교환법칙은 필요 없다.\
  `GenericSegmentTreeTest.concat` 이 이것을 일부러 증명한다 — 문자열 잇기는 교환법칙이 없는데도 `query(1, 2)` 가 `"Xc"` 로 순서를 지킨다.

근거 — `impl/SegmentTree.java` (세 메서드 모두 좌 → 우 순서가 고정이다)

```java
        int mid = (lo + hi) >>> 1;
        build(node * 2, lo, mid);
        build(node * 2 + 1, mid + 1, hi);
        tree[node] = combine(tree[node * 2], tree[node * 2 + 1]);
```

- Q: 항등원을 요구하는 이유는 무엇인가?\
  A: `query` 에 **"이 가지는 질문 구간과 전혀 안 겹친다"는 경우가 반드시 생기기** 때문이다.\
  그때 뭔가는 돌려줘야 하는데, 그 값이 상위의 `combine` 에 섞여도 답을 바꾸면 안 된다.\
  "섞여도 답을 바꾸지 않는 값"이 바로 항등원이다.\
  같은 값이 `from > to` 인 빈 구간의 답으로도 쓰인다 — `SegmentTree.query` 의 첫 분기가 그 자리다.

> **항등원(identity element)** — 그 연산에서 어느 값과 합쳐도 상대를 그대로 돌려주는 값. `a op e = e op a = a`.\
> 예: 합이면 0, 최솟값이면 `Long.MAX_VALUE`, 최댓값이면 `Long.MIN_VALUE`, 문자열 잇기면 `""`.

> **모노이드(monoid)** — 결합법칙이 성립하는 연산과 그 항등원의 쌍.\
> 예: (합, 0) · (min, +무한대) · (문자열 잇기, "") · (집합 합집합, 빈 집합) 은 전부 모노이드라 세그먼트 트리에 그대로 올라간다.

근거 — `impl/SegmentTree.java`

```java
    @Override
    public long query(int from, int to) {
        requireIndex(from);
        requireIndex(to);
        if (from > to) {
            return identity();
        }
        return query(1, 0, n - 1, from, to);
    }

    private long query(int node, int lo, int hi, int from, int to) {
        if (to < lo || hi < from) {
            return identity();
        }
```

- Q: 합·최소·최대·GCD 는 되는데 평균은 왜 안 되는가?\
  A: 앞의 넷은 전부 모노이드이기 때문이다 — (합, 0), (min, `Long.MAX_VALUE`), (max, `Long.MIN_VALUE`), (gcd, 0).\
  (gcd 의 항등원이 0 인 것은 `gcd(x, 0) = x` 이기 때문이다 — 이 코드베이스에 gcd 구현은 없다. 일반 수학 지식.)\
  평균은 결합법칙이 없다 — 반씩 접으면 **원소 개수가 다른 두 덩어리를 같은 무게로 섞어** 버린다.\
  `[1, 2, 3]` 을 트리가 `[0..1]` 과 `[2..2]` 로 쪼개면 `avg(avg(1,2), 3) = avg(1.5, 3) = 2.25` 인데 진짜 평균은 `6/3 = 2` 다.\
  덩어리의 크기를 잊어버리는 것이 결합법칙을 깨는 원인이다.

- Q: 그 오류가 "가끔 맞아서 더 위험한" 이유는 무엇인가?\
  A: 원소가 4개면 트리가 좌우를 2개씩으로 쪼개서 **무게가 우연히 같아지기** 때문이다.\
  `avg(avg(1,2), avg(3,4)) = avg(1.5, 3.5) = 2.5` 로 진짜 평균과 일치한다.\
  즉 2의 거듭제곱 크기 배열로만 테스트하면 버그가 한 번도 안 드러난다.\
  `naiveAverageIsWrong` 이 4개(맞음)와 3개(2.25 vs 2)를 나란히 놓고 그 함정을 직접 보여준다.

- Q: 그럼에도 평균을 구하려면 노드에 무엇을 들고 다녀야 하는가?\
  A: **평균 대신 (합, 개수) 쌍**을 들고 다니고, 마지막에 나눈다.\
  합도 결합법칙이 있고 개수도 결합법칙이 있으므로 쌍도 결합법칙이 있다 — `(s1+s2, c1+c2)` 로 합치면 된다.\
  항등원은 `(0, 0)` 이다.\
  나누기는 트리 안이 아니라 트리 **밖에서** 마지막에 한 번만 한다 — 결합법칙이 없는 연산을 모노이드 뒤로 밀어낸 것이다.\
  `carrySumAndCount` 가 `record SumCount(double sum, int count)` 로 정확히 이 방법을 쓴다.

근거 — `src/test/java/com/datastructure/segment/GenericSegmentTreeTest.java`

**더 생각할 것**

- "결합법칙이 없다"는 대개 **정보를 덜 들고 다녀서** 생긴다.\
  평균은 (합, 개수) 를, 최소·최대 동시 질의는 (min, max) 를, 최대 부분합은 (전체합, 왼쪽최대, 오른쪽최대, 최대부분합) 4칸을 들면 전부 모노이드가 된다.\
  질문은 "이 연산이 결합적인가"가 아니라 "무엇을 더 들면 결합적이 되는가"다.
- 노드가 무거워질수록 메모리와 `combine` 비용이 커진다.\
  4n 칸 x 노드 크기가 그대로 메모리이므로, 노드에 10칸을 들면 합 트리의 10배를 쓴다.
- 부동소수 합은 엄밀히는 결합법칙이 깨진다(반올림 순서에 따라 끝자리가 달라진다).\
  테스트가 `1e-9` 오차를 허용하는 이유가 그것이고, 금액처럼 정확해야 하는 값이면 정수·고정소수로 접어야 한다.

#### 3. query 의 세 경우와 O(log n) 의 구조적 이유

- Q: query 의 세 경우를 나누는 것이 왜 이 자료구조의 전부인가?\
  A: 세그먼트 트리가 파는 것은 "미리 접어 둔 덩어리"인데, **그 덩어리를 언제 쓰고 언제 쪼갤지를 정하는 것이 이 세 갈래뿐**이기 때문이다.\
  구조(4n 배열·번호 규약)는 그냥 저장 방식이고, `build` 는 초기화이며, `update` 는 한 줄 내려갔다 오는 단순한 일이다.\
  판단이 들어가는 자리는 `query` 의 세 줄이 전부다.\
  그래서 이 셋 중 하나만 틀려도 자료구조 전체가 무의미해진다 — 아래에서 보듯 답이 틀리거나, 맞아도 전수 조사가 된다.

근거 — `impl/SegmentTree.java` (세 갈래가 정확히 세 덩어리다)

```java
    private long query(int node, int lo, int hi, int from, int to) {
        if (to < lo || hi < from) {
            return identity();
        }
        if (from <= lo && hi <= to) {
            return tree[node];
        }
        int mid = (lo + hi) >>> 1;
        return combine(query(node * 2, lo, mid, from, to),
                query(node * 2 + 1, mid + 1, hi, from, to));
    }
```

> **완전 포함(total cover)** — 이 노드가 맡은 구간 `[lo..hi]` 가 질문 구간 `[from..to]` 안에 통째로 들어가는 경우. 조건은 `from <= lo && hi <= to`.\
> 예: 질문이 `[2..6]` 일 때 `[2..3]` 을 맡은 노드가 여기 해당한다 — 접어 둔 값을 그대로 쓰고 멈춘다.

> **걸침(partial overlap)** — 구간의 일부만 겹치는 경우. 안 겹침도 완전 포함도 아닌 나머지 전부.\
> 예: 질문이 `[2..6]` 일 때 `[0..3]` 을 맡은 노드 — 2·3 은 필요하고 0·1 은 필요 없으니 자식으로 쪼개야 한다.

- Q: "완전 포함에서 멈춘다"가 O(log n) 을 만드는 구조적 이유는 무엇인가?\
  A: **한 깊이에서 "걸치는" 노드가 최대 2개**이기 때문이다.\
  같은 깊이의 노드들이 맡은 구간은 서로 겹치지 않고 전체를 덮는다(형제끼리 `[lo..mid]`, `[mid+1..hi]` 로 잘랐으니까).\
  어떤 노드가 "걸친다"는 것은 그 구간 안에 **질문 구간에 드는 원소와 안 드는 원소가 동시에** 있다는 뜻이다.\
  그러려면 그 노드가 `from-1 | from` 경계나 `to | to+1` 경계 중 하나를 품고 있어야 한다.\
  경계는 둘뿐이고 같은 깊이 노드는 서로 안 겹치므로, **경계 하나당 노드 하나 → 깊이당 걸치는 노드 최대 2개**다.\
  걸치는 노드만 자식을 부르고, 걸치지 않는 자식은 첫째·둘째 분기에서 O(1) 로 끝난다.\
  따라서 깊이마다 방문은 최대 4개(걸침 2개 + 그 자식 중 즉시 끝나는 것들), 깊이는 `log2 n` 단 → 방문 노드 **O(log n)**.

> **경계(boundary)** — 질문 구간의 양 끝 바깥과 안 사이의 이음매. `from-1` 과 `from` 사이, `to` 와 `to+1` 사이의 두 곳뿐이다.\
> 예: 질문이 `[2..6]` 이면 1·2 사이와 6·7 사이가 경계다. 이 두 곳을 품은 노드만 쪼개진다.

`query(2, 6)` 을 n = 8 트리에서 깊이별로 세어 보면 그대로 보인다.

```
values = [3, 1, 4, 1, 5, 9, 2, 6],  질문 [2..6]
경계는 두 곳뿐:  1|2  (왼쪽)        6|7  (오른쪽)

깊이 0                        node1 [0..7]
                              걸침 (두 경계를 다 품음)         -> 걸침 1개
                    +--------------------+--------------------+
깊이 1        node2 [0..3]                              node3 [4..7]
              걸침 (1|2 를 품음)                         걸침 (6|7 을 품음)   -> 걸침 2개
          +--------+--------+                      +--------+--------+
깊이 2  node4[0..1]    node5[2..3]            node6[4..5]      node7[6..7]
        안 겹침        완전 포함                완전 포함        걸침 (6|7)    -> 걸침 1개
        identity       tree[5]=5 사용           tree[6]=14 사용   +----+----+
        (자식 안 봄)   (자식 안 봄)              (자식 안 봄)     |         |
깊이 3                                              node14[6..6]   node15[7..7]
                                                    완전 포함       안 겹침     -> 걸침 0개
                                                    tree[14]=2     identity

방문 노드 = 1, 2, 4, 5, 3, 6, 7, 14, 15 = 9개
답      = combine(5, 14, 2) = 21     (values[2..6] = 4+1+5+9+2 = 21)

깊이별 걸침 개수 = 1, 2, 1, 0  -- 어느 깊이에서도 2 를 넘지 않는다.
상한: 깊이당 방문 <= 4, 깊이 = log2(8) = 3  ->  4 x 3 = 12 >= 9
```

- Q: "걸치는 노드가 왜 2개를 못 넘는가"를 한 문장으로 다시 말하면?\
  A: **같은 깊이의 노드들은 서로 겹치지 않는 구간 분할이고, 쪼갤 이유는 두 경계뿐이니, 한 경계는 한 노드에만 들어간다.**\
  가운데에 있는 노드들은 질문 구간 안에 통째로 들어가거나 통째로 벗어나므로 자식을 볼 일이 없다.\
  즉 트리를 내려가는 흐름이 "왼쪽 경계를 따라가는 한 줄"과 "오른쪽 경계를 따라가는 한 줄" 두 개로 좁아진다.\
  그 두 줄의 길이가 각각 트리 높이이므로 전체가 `2 x log n` 규모다.

- Q: 완전 포함에서 멈추지 않으면 어떻게 되는가?\
  A: 답은 그대로 맞고 **비용만 O(n) 이 된다.**\
  둘째 분기를 빼면 어떤 노드도 "접힌 값"을 쓰지 않고 항상 자식으로 쪼개므로, 결국 리프까지 전부 내려가 원소를 하나씩 더한다.\
  미리 접어 둔 `tree[node]` 를 한 번도 쓰지 않는다 — 트리를 만들어 놓고 전수 조사를 하는 셈이다.\
  README 가 "한 경우에서 멈추지 않으면 답은 맞고 그냥 전수 조사가 됩니다"라고 적은 것이 이 말이다.\
  **테스트는 전부 통과하는데(정답이니까) `bothAreLogarithmic` 만 시간 초과로 죽는** 형태로 드러난다.

- Q: 첫째 분기(안 겹침)를 빼면 어떻게 되는가?\
  A: 그건 답까지 틀린다.\
  질문 구간 밖의 노드도 계속 쪼개 내려가다 결국 리프에서 `tree[node]` 를 반환하므로, 범위 밖 원소가 답에 섞인다.\
  합 트리면 엉뚱한 값이 더해지고 최소 트리면 범위 밖 최솟값이 이긴다.\
  또 `lo == hi` 리프에서 더 내려갈 곳이 없어 `node*2` 가 배열 밖으로 나가면 `ArrayIndexOutOfBoundsException` 이 될 수도 있다 — 즉 조용히 틀리기보다는 시끄럽게 죽을 가능성이 있는 쪽이다. (원본에 이 변형 테스트는 없다 — 내 추론.)

**더 생각할 것**

- 이 "두 경계만 따라 내려간다"는 성질은 세그먼트 트리만의 것이 아니다.\
  구간을 이진으로 분할하는 구조(펜윅·스파스 테이블·이진 인덱스 탐색) 전부가 같은 이유로 log 가 된다.
- 반대로 **경계가 없는 질문**(전체 구간)은 깊이 0 에서 끝난다 — 4번에서 다룬다.
- 재귀를 반복문으로 바꾼 "비재귀(iterative) 세그먼트 트리"도 결국 왼쪽 경계와 오른쪽 경계 두 포인터를 위로 올리는 형태다.\
  같은 논증의 다른 표현이고, 상수가 작아지지만 완전 포함 판정의 의미는 그대로다.

#### 4. 최악·최선의 요청 구간, 그리고 갱신 편중 워크로드

- Q: 요청 구간이 어떤 모양일 때 방문 노드가 가장 많아지는가?\
  A: **양 끝이 모두 트리의 분할선과 어긋나 있고, 구간이 거의 전체일 때**다.\
  두 경계가 둘 다 깊은 곳까지 살아남아야 하므로, 왼쪽 한 줄과 오른쪽 한 줄이 둘 다 리프 근처까지 내려간다.\
  n = 8 에서는 `[1..6]` 이 그 모양이다 — 왼쪽 경계 0|1 과 오른쪽 경계 6|7 이 둘 다 리프 바로 위까지 간다.\
  방문 11개, 덮는 데 쓰인 노드 4개다.

```
values = [3, 1, 4, 1, 5, 9, 2, 6]

최악  query(1, 6)  -- 양 끝이 다 어긋난다
                         node1 [0..7] 걸침
             +--------------+--------------+
        node2 [0..3] 걸침              node3 [4..7] 걸침
        +-----+-----+                  +-----+-----+
   node4[0..1]   node5[2..3]      node6[4..5]   node7[6..7]
   걸침          완전포함          완전포함       걸침
   +--+--+       tree[5]=5        tree[6]=14    +---+---+
 n8[0]  n9[1]                                 n14[6]  n15[7]
 안겹침 완전포함                               완전포함 안겹침
        tree[9]=1                              tree[14]=2

  방문 = 1,2,4,8,9,5,3,6,7,14,15 = 11개,  덮은 노드 = 4개 (n9, n5, n6, n14)
  답 = 1 + 5 + 14 + 2 = 22   (values[1..6] = 1+4+1+5+9+2 = 22)

최선  query(0, 7)  -- 경계가 아예 없다
                         node1 [0..7] 완전포함 -> tree[1] = 31 반환하고 끝
  방문 = 1개

거의 최선 query(0, 3)         node1 걸침 -> node2 [0..3] 완전포함 -> tree[2] = 9
  방문 = 1, 2, 3 = 3개 (node3 은 "안 겹침" 으로 즉시 반환)
```

- Q: 반대로 최선은 언제인가?\
  A: **질문 구간이 어떤 노드 하나와 정확히 일치할 때**다.\
  최선 중의 최선은 전체 구간 `[0..n-1]` — 뿌리가 곧 답이라 방문 1개, `O(1)` 이다.\
  그다음이 `[0..mid]`, `[mid+1..n-1]` 처럼 분할선에 정확히 맞는 구간 — 경로 길이만큼만 내려가고 끝난다.\
  일반적으로 **구간의 양 끝이 2의 거듭제곱 경계에 맞을수록** 방문이 준다.

- Q: 그렇다면 "구간이 좁을수록 빠른가"?\
  A: 아니다 — 여기가 직관이 어긋나는 지점이다.\
  원소 하나짜리 `query(i, i)` 도 뿌리에서 리프까지 한 줄을 내려가야 하므로 **O(log n)** 이다.\
  반면 원소 n 개짜리 `query(0, n-1)` 은 O(1) 이다.\
  비용을 정하는 것은 **구간의 길이가 아니라 구간 양 끝이 트리 분할선과 얼마나 어긋났는가**다.\
  참고로 `SegmentTree.get(index)` 가 트리를 안 타고 `values[index]` 를 바로 읽어 O(1) 인 이유가 여기에 있다.

근거 — `impl/SegmentTree.java`

```java
    @Override
    public long get(int index) {
        requireIndex(index);
        return values[index];
    }
```

- Q: 갱신이 압도적으로 많은 워크로드에서는 총 비용이 어떻게 되는가?\
  A: 갱신 u 번, 조회 q 번이고 `u >> q` 라면 세그먼트 트리의 총비용은 `u x O(log n)` 에 지배된다.\
  같은 워크로드를 **원본 배열 + 매번 훑기**로 하면 `u x O(1) + q x O(n)` 이다.\
  `q` 가 작으면 `u + q x n` 이 `u x log n` 보다 작다 — 즉 **갱신 편중이면 세그먼트 트리가 진다.**\
  구체적으로 `n = 200,000`, `u = 200,000`, `q = 1` 이면 훑기는 `2 x 10^5 + 2 x 10^5 = 4 x 10^5` 회, 세그먼트 트리는 `2 x 10^5 x 18 ≈ 3.6 x 10^6` 회로 약 9배 차이다. (계산은 내 추정 — 원본에 이 벤치마크는 없다.)\
  README 표의 첫 줄 "매번 훑기 … 갱신이 압도적일 때"가 그 결론이다.

- Q: 그래도 세그먼트 트리를 쓰게 되는 경우는?\
  A: **조회가 드물어도 그 조회가 늦으면 안 되는 경우**다.\
  훑기는 평균은 좋지만 조회 한 번이 O(n) 이라 그 순간의 지연이 튄다.\
  꼬리 지연(p99)이 계약인 시스템에서는 "평균 총비용이 낮은 쪽"이 아니라 "최악 한 번이 작은 쪽"을 고른다.\
  세그먼트 트리는 조회와 갱신 **둘 다 최악이 log n 으로 묶여 있다**는 것이 진짜 상품이다.

**더 생각할 것**

- 최악 구간 `[1..n-2]` 도 결국 O(log n) 이다 — 최악과 최선의 차이는 차수가 아니라 상수(11배 vs 1배)다.\
  차수가 같으므로 "최악 입력을 피하는 최적화"는 대개 의미가 없다.
- 조회 구간의 모양이 실제로 편향돼 있다면(예: 항상 `[0..i]` 형태의 접두 구간) 세그먼트 트리가 과한 선택이다.\
  접두 구간만 물으면 17번 펜윅 트리가 더 짧고 상수도 작다 — 7번에서 다룬다.
- 규모가 커지면 `4n` 배열 자체가 문제가 된다.\
  n = 10^8 이면 `long[4n]` 은 3.2 GB 다(8바이트 x 4 x 10^8). 차수가 아니라 상수 4 가 메모리를 결정한다.

#### 5. 조용히 틀리는 두 가지 — combine 누락과 항등원 0

- Q: update 가 돌아오는 길에 자식을 다시 combine 하지 않으면 무슨 일이 벌어지는가?\
  A: **리프만 새 값이 되고 그 위의 조상들은 옛 답을 그대로 들고 있게 된다.**\
  `update` 는 내려가면서 리프에 대입하고, **돌아 나오면서** 지나온 부모들을 `combine(자식, 자식)` 으로 다시 접는 구조다.\
  마지막 줄 하나(`tree[node] = combine(...)`)를 빼면 내려가기만 하고 갱신이 위로 전파되지 않는다.\
  그러면 `query` 가 완전 포함으로 그 조상을 집는 순간 낡은 값이 답에 섞인다.\
  README 가 "잎만 바뀌고 위쪽은 옛 답을 들고 조용히 틀립니다(37개 중 6개가 무너집니다)"라고 적은 그대로다.

근거 — `impl/SegmentTree.java` (마지막 줄이 "돌아오는 길의 할 일"이다)

```java
    private void update(int node, int lo, int hi, int index, long value) {
        if (lo == hi) {
            tree[node] = value;
            return;
        }
        int mid = (lo + hi) >>> 1;
        if (index <= mid) {
            update(node * 2, lo, mid, index, value);
        } else {
            update(node * 2 + 1, mid + 1, hi, index, value);
        }
        tree[node] = combine(tree[node * 2], tree[node * 2 + 1]);
    }
```

같은 트리에 같은 갱신을 넣고, 그 한 줄이 있을 때와 없을 때를 나란히 두면 이렇다.

```
values = [1, 2, 3, 4] 의 합 트리.  update(1, 20) 을 한다.

 before                          정상(combine 있음)            버그(combine 없음)
 tree[1]=10 [0..3]               tree[1]=28  <== 다시 접음      tree[1]=10   (낡음!)
   /      \                        /      \                      /      \
```

- Q: 최소 트리의 항등원을 0 으로 두면 왜 양수만 있는 배열에서도 틀리는가?\
  A: 항등원은 **답에 섞여도 무해해야** 하는데, `min` 에서 0 은 웬만한 양수보다 작아 **항상 이겨 버리기** 때문이다.\
  `query` 의 "안 겹침" 가지가 0 을 돌려주면 그 0 이 `Math.min` 을 통과해 최종 답이 된다.\
  배열에 음수가 있어야 깨지는 것이 아니다 — 양수 `{5, 7, 9, 11, 13, 17, 19, 23}` 에서도 "안 겹침" 가지가 한 번이라도 생기면 답이 0 이 된다.\
  올바른 항등원은 `Long.MAX_VALUE` 다 — `min(Long.MAX_VALUE, x) = x` 라 상대를 절대 이기지 않는다.\
  (같은 이유로 최대 트리의 항등원은 `Long.MIN_VALUE`, `MinMax` 의 항등원은 `(Long.MAX_VALUE, Long.MIN_VALUE)` 로 **뒤집혀** 있다.)

`query(1, 3)` 한 번으로 그 일이 일어나는 자리를 보면 이렇다.

```

                     node1 [0..7] 걸침
                     /
             node2 [0..3] 걸침
             /            \
     node4 [0..1] 걸침     node5 [2..3] 완전포함 -> tree[5] = min(9,11) = 9
     /          \

 안 겹침!        완전포함 -> tree[9] = 7
 여기서 identity() 가 나온다

  identity() = Long.MAX_VALUE 일 때   min(MAX_VALUE, 7) = 7   -> ... -> 답 7   맞음
  identity() = 0 일 때                min(0, 7)         = 0   -> ... -> 답 0   틀림
```

- Q: 두 실수 모두 "조용히 틀리는" 부류인 이유는 무엇인가?\
  A: 셋이 겹친다.\
  첫째, **예외가 안 난다** — 배열 범위를 벗어나지도, null 을 만지지도 않는다. 타입도 맞다. 그냥 `long` 하나가 다른 `long` 하나로 바뀔 뿐이다.\
  둘째, **일부 질문은 맞는다** — combine 누락은 "조상을 완전 포함으로 집는 질문"만, 항등원 0 은 "안 겹침 가지를 타는 질문"만 틀린다.\
  전부 틀리면 첫 테스트에서 잡히지만, 절반이 맞으면 눈으로 하는 확인을 통과해 버린다.\
  셋째, **눈에 띄는 입력이 의심 밖에 있다** — 항등원 0 은 "음수가 없으니 0 은 안전하겠지"라는 잘못된 안심과 정확히 맞물린다.\
  그래서 두 버그 모두 **전수 대조**로 잡는다 — `everyRange` 가 모든 `(from, to)` 쌍을 느린 구현과 맞춰 보고, `matchesNaive` 가 난수로 수백 스텝을 대조한다.

> **조용한 실패(silent failure)** — 오류가 예외·로그·중단 없이 "그럴듯한 값"으로 흘러가는 실패.\
> 예: 최소 트리가 0 을 돌려주는 것 — 타입도 형식도 맞아서 호출한 쪽은 그것이 진짜 최솟값인 줄 안다.

- Q: 그런 버그를 코드가 아니라 테스트 설계로 막는 방법은?\
  A: **느린 정답 구현(oracle)을 옆에 두고 모든 입력을 대조**하는 것이다.\
  `naiveSum`, `naiveMin` 이 그 오라클이고, 세그먼트 트리와 답이 다르면 곧바로 어느 구간에서 갈렸는지까지 메시지에 찍힌다.\
  대조할 입력은 "예쁜" 크기만 고르면 안 된다 — `matchesNaive` 는 `n ∈ {1, 2, 3, 7, 8, 9, 64, 100}` 으로 2의 거듭제곱과 그 앞뒤를 일부러 섞는다.\
  2번의 평균 함정(4개는 맞고 3개는 틀림)도 같은 이유로 홀수 크기에서만 드러난다.\
  즉 **분할선과 어긋나는 크기·구간**이 이 자료구조의 버그를 드러내는 입력이다.

#### 6. 구현 전략의 트레이드오프 — 상속·묶음·미루기

- Q: 상속으로 combine 을 정하는 SegmentTree 와 인자로 받는 GenericSegmentTree 는 무엇이 다른가(언제 정해지는가)?\
  A: **연산이 정해지는 시점**이 다르다.\
  `SegmentTree` 는 `abstract long combine(long, long)` 을 비워 두고 하위 클래스가 채운다 — 연산은 **클래스를 쓸 때(컴파일 시점)** 굳는다.\
  `GenericSegmentTree` 는 `BinaryOperator<T> combine` 을 **생성자 인자**로 받아 필드에 담는다 — 연산은 **객체를 만들 때(실행 시점)** 정해진다.\
  전자는 연산 하나당 클래스 하나가 필요하고, 후자는 클래스 하나로 합·최대·문자열 잇기·집합 합집합을 다 만든다.\
  하는 일은 같고 "언제 정하느냐"만 다르다 — README 가 05번 `LinkedHashMap`(상속)과 12번 `SkipListSet`(포함)의 대비와 같은 이야기라고 적은 지점이다.

> **동적 디스패치(virtual dispatch)** — 부모 타입으로 호출한 메서드가 실행 시점의 실제 객체 타입에 따라 골라지는 것.\
> 예: `SegmentTree.build` 안의 `combine(...)` 은 그 객체가 `SumSegmentTree` 면 `+`, `MinSegmentTree` 면 `Math.min` 으로 간다.

> **제네릭 소거(type erasure)** — 자바 제네릭의 타입 인자 `T` 가 컴파일 후 지워지는 것.\
> 예: `new T[4*n]` 을 만들 수 없어 `Object[]` 로 두고 꺼낼 때 `(T)` 로 캐스팅한다 — `GenericSegmentTree.at` 이 그 캐스팅을 한곳에 모은 메서드다.

두 클래스의 골격을 나란히 놓으면 차이가 두 줄뿐이다.

```
  SegmentTree (상속)                        GenericSegmentTree<T> (주입)
  +-------------------------------+         +------------------------------------+
  | protected final long[] tree   |         | private final Object[] tree        |
  | private   final long[] values |         | private final Object[] values      |
  | abstract long combine(a, b)   |         | private final BinaryOperator<T>    |
  | abstract long identity()      |         |                        combine     |
  |                               |         | private final T identity           |
  +-------------------------------+         +------------------------------------+
        ^                                            ^
        | 비어 있다. 하위 클래스가 채운다               | 생성자 인자로 들어온다
        |                                            |
  class SumSegmentTree extends SegmentTree     new GenericSegmentTree<>(
      combine -> a + b                             List.of("a","b","c","d"),
      identity -> 0L                               "", String::concat)
  -- 컴파일 시점에 굳는다                        -- 실행 시점에 정해진다

  build / update / query 의 본문은 글자 하나 차이로 같다.
  node*2, node*2+1, mid = (lo+hi)>>>1, 4*n 크기까지 전부 동일.
  바뀌는 것은 "칸에 무엇이 들어가는가" 뿐이다.
```

- Q: MinMaxSegmentTree 처럼 값을 묶는 것과 트리를 둘 두는 것의 차이는?\
  A: **답은 같고, 경로를 몇 번 밟느냐와 값들이 서로를 볼 수 있느냐가 다르다.**\
  `MinSegmentTree` 와 `MaxSegmentTree` 를 따로 두면 질의 한 번에 트리를 두 번 탄다 — 방문 노드도 2배, 갱신도 두 트리 각각에 해야 한다.\
  `MinMaxSegmentTree` 는 노드 한 칸에 `record MinMax(long min, long max)` 를 담아 **한 번 타면서 두 답을 같이** 얻는다.\
  대신 `long[]` 이 `MinMax[]` 가 되어 노드마다 객체 참조가 한 번 더 끼고, `merge` 가 호출될 때마다 새 `MinMax` 를 하나씩 만든다.\
  `agreesWithSeparateTrees` 가 난수 500 스텝으로 "`MinSegmentTree` 를 따로 돌린 것과 min 값이 같다"를 확인한다 — 즉 정확성 면에서는 완전히 교환 가능하다.

- Q: min·max 정도면 트리 둘로도 되는데, 묶는 것이 꼭 필요해지는 때는 언제인가?\
  A: **합칠 때 두 값이 서로를 참조해야 하는 순간**이다.\
  min 과 max 는 서로 독립이라 분리해도 되지만, 예컨대 평균은 (합, 개수)가 **같이** 있어야 접히고, 최대 부분합은 (전체합, 왼쪽에서 최대, 오른쪽에서 최대, 구간 최대) 네 값이 서로를 써서 합쳐진다.\
  네 값을 트리 네 개로 쪼개면 `combine` 을 쓸 수가 없다 — 한 트리가 다른 트리의 값을 봐야 하기 때문이다.\
  README 가 "이걸 밀면 최대 부분합 문제도 세그먼트 트리로 풀립니다"라고 적은 것이 그 확장이다.\
  즉 묶기는 성능 최적화이기 이전에 **표현력의 문제**다.

- Q: LazySegmentTree 의 push/apply 는 어떤 비용을 어떤 비용으로 바꾸는가?\
  A: **"구간 길이에 비례하는 갱신"을 "조회가 상태를 바꾸는 부담"으로 바꾼다.**\
  보통 트리로 `[from..to]` 전체에 5 를 더하려면 원소마다 `update` 를 불러 `O(k log n)` 이다(k = 구간 길이).\
  게으른 트리는 완전 포함 노드에서 **자기 값만 고치고 자식 몫은 쪽지(lazy)로 남긴 뒤 멈춰** `O(log n)` 으로 끝낸다.\
  대신 `lazy` 배열 `4n` 칸이 추가로 들고, **읽기인 `rangeSum` 이 `push` 로 트리를 수정한다**.\
  README 가 "`rangeSum` 이 자료구조를 바꿉니다. 10번 LRU 의 `get` 과 같은 성질이고, 그래서 이것도 동시성이 까다롭습니다"라고 적은 대가가 그것이다.

> **게으른 전파(lazy propagation)** — 구간 갱신을 자식까지 즉시 내리지 않고, "자식들이 얼마나 뒤처져 있는지"를 노드에 쪽지로 남겨 두는 기법.\
> 예: `lazy[2] = 5` 는 "노드 2 의 값은 이미 맞다. 그 자식들이 5 씩 뒤처져 있다"는 뜻이다.

> **apply** — 한 노드에 "내 구간 전체에 delta 더하기"를 반영하는 동작. 내 값은 즉시 고치고(폭 x delta), 자식 몫은 lazy 에 적는다.\
> 예: `apply(2, 0, 1, 5)` 는 `tree[2] += 5 * 2`, `lazy[2] += 5`.

> **push** — 자식으로 내려가기 직전에 그 쪽지를 두 자식에게 apply 하고 자기 쪽지를 비우는 동작.\
> 예: `push(1)` 이 `lazy[1]=5` 를 노드 2·3 에 나눠 주고 `lazy[1] = 0` 으로 만든다.

근거 — `impl/LazySegmentTree.java` (규약이 이 6줄에 전부 있다)

```java
    /** 미뤄둔 갱신을 자식에게 내린다. */
    private void push(int node, int lo, int hi) {
        if (lazy[node] == 0) {
            return;
        }
        int mid = (lo + hi) >>> 1;
        apply(node * 2, lo, mid, lazy[node]);
        apply(node * 2 + 1, mid + 1, hi, lazy[node]);
        lazy[node] = 0;
    }

    /** 이 노드가 덮는 구간 전체에 delta 를 더한 효과를 즉시 반영한다. */
    private void apply(int node, int lo, int hi, long delta) {
        tree[node] += delta * (hi - lo + 1);
        lazy[node] += delta;
    }
```

테스트 두 개가 "미룬다"와 "제때 내린다"를 각각 못박는다. 그 두 순간을 그림으로 보면 이렇다.

```
n = 4, 전부 0.  rangeAdd(0, 3, 5) -> rangeSum(0, 1) 순서

[1] rangeAdd(0, 3, 5) : 뿌리가 완전 포함이라 apply 하고 즉시 멈춘다
        before                              after
   tree[1]=0  lazy[1]=0                tree[1]=20  lazy[1]=5   <== 5 * (3-0+1)
      [0..3]                               [0..3]
     /      \               ->            /      \
 t[2]=0    t[3]=0                     t[2]=0    t[3]=0
 lazy=0    lazy=0                     lazy=0    lazy=0
  / \       / \                        / \       / \
 0   0     0   0                      0   0     0   0
                                      ^^^^^^^^^^^^^^^^
                                      전혀 손대지 않았다 (lazyStaysAtRoot 가 확인)

[2] rangeSum(0, 1) : 뿌리가 걸침이라 자식으로 내려가야 한다 -> 그 직전에 push(1)
        before push(1)                      after push(1)
   tree[1]=20 lazy[1]=5                 tree[1]=20  lazy[1]=0   <== 비웠다
     /      \               ->            /      \
 t[2]=0    t[3]=0                     t[2]=10   t[3]=10   <== 5*2 씩
 lazy=0    lazy=0                     lazy[2]=5 lazy[3]=5 <== 자식 몫은 또 미룬다

  tree[1] = 20 은 그대로다. push 는 자식만 고친다
  (부모에는 이미 반영돼 있었으니까 -- 이것이 lazy 규약의 핵심이다)
  그다음 node2 [0..1] 이 완전 포함 -> tree[2] = 10 반환.  (pushesOnDescent 가 확인)

  push 가 tree[node] 를 또 고치면 값이 두 배가 된다 -> doesNotDoubleApply 가 10회 반복 조회로 잡는다
```

- Q: `hi - lo + 1` 의 `+1` 이 왜 그렇게 자주 틀리는 자리인가?\
  A: 구간 `[lo..hi]` 의 **원소 개수**는 `hi - lo` 가 아니라 `hi - lo + 1` 이기 때문이다(양 끝 포함).\
  `[0..3]` 은 4개지 3개가 아니다.\
  합 트리에서는 그 개수가 그대로 `delta` 에 곱해지므로 개수를 하나 덜 세면 답이 `delta` 만큼 부족해진다.\
  `multipliesByLength` 가 4개짜리 0 배열에 5 를 더해 20 을 기대하고, 실패 메시지가 "15 가 나오면 +1 을 빠뜨린 것이다"라고 직접 지목한다.\
  README 기준으로 이 실수 하나가 37개 중 8개를 무너뜨린다.

- Q: 네 구현을 한 표로 비교하면?\
  A: 이렇게 갈린다.

  | 전략 | 무엇을 사는가 | 무엇을 치르는가 | 적합한 경우 |
  |---|---|---|---|
  | Sum/Min (상속) | `long[]` 연속 메모리, 박싱 없음, 컴파일 시점 안전 | 연산 하나당 클래스 하나 | 연산이 고정이고 성능이 중요할 때 |
  | MinMax (묶음 값) | 한 번의 경로로 두 답, 값들이 함께 접힘 | 노드마다 객체 참조 + `merge` 마다 할당 | 두 값이 늘 같이 필요하거나 서로를 참조할 때 |
  | Generic (인자 주입) | 클래스 하나로 모든 모노이드, 람다 한 줄로 새 연산 | `Object[]` + 캐스팅 + 박싱, 실행 시점 검사 | 연산이 호출자마다 다를 때 |
  | Lazy (미루기) | 구간 갱신이 길이와 무관하게 `O(log n)` | `lazy` 배열 4n, 조회가 상태를 바꿈, 코드 복잡도 | 구간 전체 갱신이 잦을 때 |

**더 생각할 것**

- 상속 대 주입은 세그먼트 트리만의 문제가 아니라 "확장점을 어디에 둘 것인가"의 일반 문제다.\
  주입은 유연하지만 잘못된 조합을 컴파일러가 막아 주지 못한다 — `GenericSegmentTree` 가 생성자에서 null 검사를 손으로 하는 이유가 그것이다.
- 자바에서 "값을 묶으면 캐시에 좋다"는 말은 조건부다.\
  `record` 는 힙에 흩어진 객체라 `long[]` 두 개보다 오히려 지역성이 나쁠 수 있다 — 값 타입(프로젝트 발할라)이 들어오기 전까지는 측정해 보고 판단할 일이다. (측정치는 원본에 없다 — 내 추론.)
- lazy 는 "조회가 쓰기를 한다"는 성질 때문에 읽기 전용 잠금으로 보호할 수 없다.\
  동시성이 필요하면 조회에도 쓰기 잠금을 걸거나, 스냅숏을 뜨거나, 아예 갱신을 단일 스레드로 몰아야 한다.

#### 7. 다음 구조로의 연결 — 펜윅 트리와 유니온 파인드

- Q: 세그먼트 트리의 한계가 17번 펜윅 트리를 어떻게 부르는가?\
  A: "**합만 필요한데 값을 다 치러야 한다**"는 불만이 부른다.\
  합만 쓰는 경우에도 `SegmentTree` 는 추상 클래스 + 하위 클래스 + 재귀 3종(`build`·`update`·`query`) + `4n` 배열을 전부 들고 간다 — impl 기준 100줄 안팎이다.\
  펜윅 트리는 같은 O(log n) 을 배열 `n+1` 칸과 루프 두 개로 낸다.\
  README 표의 마지막 줄이 그 결론이다 — "합만 필요할 때. 코드가 훨씬 짧다".\
  즉 **표현력을 좁히는 대가로 코드 길이와 상수를 얻는** 교환이다.

> **역원(inverse element)** — 어떤 값과 합치면 항등원이 되는 값. 합에서는 `-a`, 곱에서는 `1/a`.\
> 예: 합은 역원이 있어 `sum(l, r) = prefix(r) - prefix(l-1)` 로 뺄 수 있지만, min 은 "빼기"가 없어 이 수법이 통하지 않는다.

- Q: 펜윅 트리가 "합만" 되는 이유는 무엇인가?\
  A: 펜윅은 접두 합 `prefix(i)` 만 들고 있다가 **뺄셈으로** 구간 답을 만드는 구조이기 때문이다.\
  그래서 연산에 **역원**이 있어야 한다 — 합·XOR 은 되고, min·max·GCD 는 안 된다.\
  `min(a[0..6])` 과 `min(a[0..1])` 을 알아도 `min(a[2..6])` 을 복원할 방법이 없다.\
  세그먼트 트리는 뺄셈 없이 덩어리를 **주워 담기만** 하므로 모노이드면 무엇이든 올라간다 — 그 범용성이 정확히 코드 길이의 대가다.\
  (펜윅의 내부 구현은 이 코드베이스에 없다. 17번 주제의 내용이고, 여기서는 일반 지식으로 적는다.)

```
같은 O(log n) 인데 무엇이 다른가

  세그먼트 트리                          펜윅 트리(17번)
  +-----------------------------+       +-----------------------------+
  | long[4n] (+ long[4n] lazy)  |       | long[n+1]                   |
  | build / update / query 재귀  |       | update / prefix 루프 2개     |
  | 모노이드면 무엇이든           |       | 역원이 있는 연산만 (합, XOR)  |
  | 구간 갱신 -> lazy 쪽지 필요   |       | 접두 합이 곧 본체             |
  | 최소/최대/GCD/문자열/집합 OK  |       | 최소/최대 불가                |
  +-----------------------------+       +-----------------------------+
        넓다. 대신 길다                        좁다. 대신 짧고 빠르다

   "무엇을 포기하면 무엇을 얻는가" 의 한 사례
```

- Q: 구간 갱신에 쪽지가 필요하다는 한계는 어떻게 읽어야 하는가?\
  A: 세그먼트 트리의 기본형은 **점 갱신 + 구간 조회**까지만 공짜라는 뜻이다.\
  구간 갱신을 원하는 순간 `lazy` 배열·`push`·`apply` 라는 새 불변식이 통째로 얹힌다 — 코드가 길어지고, 조회가 상태를 바꾸고, `+1` 같은 새 실수 자리가 생긴다.\
  이것은 "구조가 부족해서"가 아니라 **한 자료구조가 커버하는 연산을 넓힐 때마다 대가가 붙는다**는 일반 현상이다.\
  (펜윅도 배열 두 개를 쓰는 기법으로 구간 갱신을 흉내낼 수 있다 — 일반 지식이고 이 코드베이스에는 없다.)

- Q: 14번 유니온 파인드처럼 "연산을 포기하고 속도를 얻는" 선택과는 어떻게 대비되는가?\
  A: 방향은 같고 **포기하는 것의 종류**가 다르다.\
  유니온 파인드는 "합치기"만 지원하고 **쪼개기를 아예 포기해서** 거의 O(1)(역아커만 함수)을 얻는다 — 포기한 것이 *연산*이다.\
  펜윅은 연산의 *종류*를 합 계열로 좁혀서 코드와 상수를 얻는다 — 포기한 것이 *표현력*이다.\
  세그먼트 트리는 아무것도 포기하지 않는 쪽에 가깝고, 그래서 어느 쪽 지표에서도 1등이 아니다.\
  README 가 마지막에 "여기서 본 '무엇을 포기하면 무엇을 얻는가'가 또 나옵니다"라고 예고한 것이 이 축이다.

- Q: 이 축을 이 문제집 전체로 넓히면 어떻게 정리되는가?\
  A: 표로 놓으면 같은 형식의 거래가 반복된다.

  | 구조 | 포기한 것 | 얻은 것 |
  |---|---|---|
  | 누적합 | 갱신 | 조회 O(1) |
  | 매번 훑기 | 조회 | 갱신 O(1) · 코드 0줄 |
  | 세그먼트 트리 | 양쪽의 O(1) | 둘 다 O(log n) · 모노이드면 무엇이든 |
  | 펜윅 트리(17번) | min·max 같은 비가역 연산 | 짧은 코드 · 작은 상수 · n+1 메모리 |
  | 유니온 파인드(14번) | 쪼개기 연산 | 거의 O(1) |
  | Lazy 세그먼트 트리 | 조회의 읽기 전용성 | 구간 갱신 O(log n) |

  A(이어서): 자료구조 고르기란 결국 **어떤 연산을 비싸게 둘지 고르는 일**이라는 것이 이 표의 요지다.

**더 생각할 것**

- 대회 코드에서는 "짧아서 실수를 덜 한다"가 진짜 성능 요소다.\
  펜윅이 세그먼트 트리보다 선호되는 이유의 절반은 차수나 상수가 아니라 타이핑 양과 버그 확률이다.
- 실무에서 세그먼트 트리를 직접 쓸 일은 드물지만, 같은 발상은 도처에 있다 — 시계열 집계의 롤업 테이블, OLAP 의 큐브, 데이터베이스의 구간 인덱스가 전부 "미리 접어 둔 덩어리로 덮기"다.
- "포기하면 얻는다"는 거래에서 위험한 쪽은 항상 **나중에 포기한 것이 필요해지는 경우**다.\
  펜윅으로 합을 올려 두었는데 요구사항에 "구간 최댓값"이 추가되면 자료구조를 통째로 갈아야 한다 — 그래서 요구 연산의 목록을 먼저 확정하고 고르는 순서가 중요하다.
