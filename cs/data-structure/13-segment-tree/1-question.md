## 질문

<!-- 직접 작성. 5~7개. 세부 암기 금지 — 지도 수준으로.
     유형: 왜(why) / 예측(what if) / 경계(어느 계층·모듈의 책임인가) / 연결(다른 주제와의 다리) -->

1. 세그먼트 트리는 왜 필요한가 — 누적합(prefix sum)과 매번 훑기로는 무엇이 안 되는가. 조회와 갱신의 비율이 선택을 어떻게 가르는가.
2. combine 이 결합법칙과 항등원을 요구하는 이유는 무엇인가. 합·최소·최대·GCD 는 되는데 평균은 왜 안 되고, 그럼에도 평균을 구하려면 노드에 무엇을 들고 다녀야 하는가.
3. query 의 세 경우(안 겹침 / 완전 포함 / 걸침)를 나누는 것이 왜 이 자료구조의 전부인가. "완전 포함에서 멈춘다"가 O(log n) 을 만드는 구조적 이유는 무엇인가.
4. 최악의 입력·사용 패턴을 만들어 보라 — 요청 구간이 어떤 모양일 때 방문 노드가 가장 많아지고, 반대로 최선은 언제인가. 갱신이 압도적으로 많은 워크로드에서는 총 비용이 어떻게 되는가.
5. update 가 돌아오는 길에 자식을 다시 combine 하지 않으면 무슨 일이 벌어지는가. 최소 트리의 항등원을 0 으로 두면 왜 **양수만 있는 배열에서도** 틀리는가 — 두 실수 모두 "조용히 틀리는" 부류인 이유는.
6. 구현 전략의 트레이드오프 — 상속으로 combine 을 정하는 SegmentTree 와 인자로 받는 GenericSegmentTree 는 무엇이 다른가(언제 정해지는가). MinMaxSegmentTree 처럼 값을 묶는 것과 트리를 둘 두는 것의 차이는. LazySegmentTree 의 push/apply 는 어떤 비용을 어떤 비용으로 바꾸는가.
7. 다음 구조로의 연결 — 세그먼트 트리의 한계(합만 필요해도 코드가 길다, 구간 갱신에 쪽지가 필요하다)가 17번 펜윅 트리를 어떻게 부르는가. 그리고 14번 유니온 파인드처럼 "연산을 포기하고 속도를 얻는" 선택과는 어떻게 대비되는가.
