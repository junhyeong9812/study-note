#### 1. 문제 1 — 슬라이딩 윈도우 최솟값

**접근 1 — 창마다 k 개를 전부 훑기** (가장 먼저 떠오르고, 가장 먼저 시간 초과가 난다)

```java
// 의사코드
int[] out = new int[n - k + 1];
for (int i = 0; i < out.length; i++) {
    int m = Integer.MAX_VALUE;
    for (int j = i; j < i + k; j++) {
        m = Math.min(m, values[j]);
    }
    out[i] = m;
}
return out;
```

```
처리 과정 : values = [1, 3, -1, -3, 5, 3, 6, 7], k = 3

  i=0   [ 1   3  -1]  -3   5   3   6   7     세 칸을 전부 비교 -> -1
  i=1    1  [ 3  -1  -3]  5   3   6   7      세 칸을 전부 비교 -> -3
  i=2    1   3  [-1  -3   5]  3   6   7      세 칸을 전부 비교 -> -3
  i=3    1   3  -1  [-3   5   3]  6   7      세 칸을 전부 비교 -> -3
  i=4    1   3  -1  -3  [ 5   3   6]  7      세 칸을 전부 비교 ->  3
  i=5    1   3  -1  -3   5  [ 3   6   7]     세 칸을 전부 비교 ->  3

  결과 [-1, -3, -3, -3, 3, 3]   (SparseTableProblemsTest.windowOfThree 의 기댓값과 같다)

  창이 한 칸 옮겨가도 겹치는 k-1 칸을 매번 다시 본다. 그것이 낭비의 전부다.
```

- 논리: 정의를 그대로 옮긴 것이라 틀릴 여지가 없다.
- 논리: 창 하나의 답을 구하는 데 그 창 안의 값을 전부 본다.
- 비용(왜): 창이 `n - k + 1` 개, 창 하나에 `k` 번 비교 → 총 `(n - k + 1) x k` → **O(n·k)**.
- 비용(왜): `k = n/2` 일 때 최악이라 `n^2/4` 규모가 된다.
- 한계: 04번 README 가 같은 문제를 100만 x k=5만 시간 제한으로 걸어 이 풀이를 떨어뜨린다(`/home/jun/project/myway/data-structure/04-queue-deque/README.md` 68~70줄).
- 한계: 창이 한 칸 움직일 때 새로 들어오는 값은 하나뿐인데 k 칸을 전부 다시 본다.\
  직전 창에서 알아낸 정보를 하나도 재사용하지 않는다.

> **슬라이딩 윈도우(sliding window)** — 고정 크기의 창을 배열 위에서 한 칸씩 밀며 창마다 답을 구하는 문제 형태.\
> 예: `[1,3,-1,-3,5,3,6,7]` 에 k=3 이면 창은 `[1,3,-1]`, `[3,-1,-3]` … 순으로 여섯 번 놓인다.

**접근 2 — 단조 덱** (04번의 정답. 이 문제만 보면 가장 빠르다)

```java
// 의사코드 — 04번 풀이
Deque<Integer> dq = new ArrayDeque<>();   // 값이 아니라 "인덱스"를 담는다
for (int i = 0; i < n; i++) {
    while (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst();   // 창 밖으로 나간 후보
    while (!dq.isEmpty() && values[dq.peekLast()] >= values[i]) dq.pollLast(); // 이길 수 없는 후보
    dq.addLast(i);
    if (i >= k - 1) out[i - k + 1] = values[dq.peekFirst()];
}
```

```
처리 과정 : 덱에는 "아직 최솟값이 될 수 있는 후보"의 인덱스만 값 오름차순으로 남는다

  i=2  창 [1, 3, -1]      -1 이 들어오며 1 과 3 을 뒤에서 몰아냈다
       덱: [2]                                  답 = values[2] = -1

  i=3  창 [3, -1, -3]      -3 이 -1 을 몰아냈다
       덱: [3]                                  답 = values[3] = -3

  i=4  창 [-1, -3, 5]      5 는 -3 보다 크므로 뒤에 그냥 붙는다
       덱: [3, 4]                               답 = values[3] = -3

  i=5  창 [-3, 5, 3]       3 이 5 를 몰아냈다
       덱: [3, 5]                               답 = values[3] = -3

  i=6  창 [5, 3, 6]        앞의 3(인덱스 3)이 창 밖으로 나가 앞에서 버려진다
       덱: [5, 6]                               답 = values[5] = 3

  각 인덱스는 평생 한 번 들어가고 한 번 나온다 -> 전체가 O(n).
```

- 논리: "내 오른쪽에 나보다 작은 값이 들어왔다"면 나는 앞으로 어떤 창에서도 답이 될 수 없다.
- 논리: 그 후보를 즉시 버리므로 덱 안은 항상 값 오름차순이다 — 맨 앞이 곧 창의 최솟값이다.
- 논리: 창의 왼쪽 끝이 지나간 인덱스는 맨 앞에서 버린다.\
  창이 **한 방향으로만** 가기 때문에 앞에서만 버리면 된다는 것이 성립한다.
- 비용(왜): 인덱스 하나가 덱에 최대 한 번 들어가고 최대 한 번 나온다 → 총 연산 2n → **O(n)**.
- 비용(왜): 덱 크기는 창을 넘지 않으므로 추가 공간 **O(k)**.
- 한계: 창 크기 k 가 고정이라는 전제 위에서만 성립한다.\
  k 가 바뀌면 덱에 남길 후보의 기준이 바뀌므로 처음부터 다시 훑어야 한다.
- 한계: 창이 왼쪽에서 오른쪽으로만 간다는 전제 위에서만 성립한다.\
  `[5, 9]`, `[1, 3]`, `[0, 7]` 처럼 제멋대로인 구간을 물으면 쓸 수 없다.

> **단조 덱(monotonic deque)** — 담긴 값이 항상 한 방향으로 정렬되도록 뒤에서 밀어내며 유지하는 덱.\
> 예: 최솟값용이면 새 값보다 큰 뒤쪽 후보를 전부 버려서 덱 안이 오름차순을 유지한다.

> **상환(amortized)** — 개별 연산은 비쌀 수 있어도 n 번 전체의 총비용이 O(n) 이라 1회 평균이 상수라는 뜻.\
> 예: 위 while 루프는 한 번에 여러 개를 버릴 수 있지만, 버려지는 총 개수가 n 을 넘지 못한다.

**접근 3 — 희소 테이블** (impl 의 정답)

```java
public static int[] slidingWindowMin(int[] values, int k) {
    if (values == null || values.length == 0) {
        throw new IllegalArgumentException("원소가 하나 이상 있어야 한다");
    }
    if (k <= 0 || k > values.length) {
        throw new IllegalArgumentException("창 크기가 범위를 벗어났다: " + k + " (원소 " + values.length + ")");
    }
    long[] a = new long[values.length];
    for (int i = 0; i < values.length; i++) {
        a[i] = values[i];
    }
    MinSparseTable t = new MinSparseTable(a);
    int[] out = new int[values.length - k + 1];
    for (int i = 0; i < out.length; i++) {
        out[i] = (int) t.query(i, i + k - 1);
    }
    return out;
}
```

```
처리 과정 : 표를 한 번 짓고, 창마다 query 를 한 번씩만 부른다

  1단계 (루프 밖)  MinSparseTable 을 한 번 짓는다      O(n log n)
        table[k][i] = [i, i + 2^k - 1] 의 최솟값

  2단계 (루프 안)  창 i 마다 query(i, i + k - 1)        O(1) x (n - k + 1)

        i = 0 : query(0, 2)   len = 3, 층 = log[3] = 1, 2^1 = 2
                  [ 1   3  -1] ...
                  |<- t[1][0] ->|        = min(1, 3)  =  1
                       |<- t[1][1] ->|   = min(3, -1) = -1
                       |<>|  1번 칸이 두 번 들어간다 - min 이라 상관없다
                  combine(1, -1) = -1

        i = 1 : query(1, 3)   -> -3
        ...
        i = 5 : query(5, 7)   -> 3

  창 크기 k 가 무엇이든 같은 표를 그대로 쓴다. 이것이 덱과 갈리는 지점이다.
```

- 논리: 슬라이딩 윈도우는 "시작점이 한 칸씩 늘어나는 구간 질의"일 뿐이다.\
  일반적인 구간 질의 구조로 풀면 창이라는 특수 조건이 아예 필요 없어진다.
- 논리: 전처리를 반드시 루프 **밖**에 둔다 — 창마다 표를 새로 지으면 O(n^2 log n) 이 된다.
- 논리: `int` 를 `long[]` 으로 옮겨 담는 것은 `MinSparseTable` 의 계약이 `long[]` 이기 때문이다.\
  결과는 다시 `(int)` 로 좁히는데, 입력이 `int` 였으므로 최솟값도 `int` 범위를 벗어날 수 없다.
- 비용(왜): 전처리 `O(n log n)` + 질의 `(n - k + 1) x O(1)` → 전체 **O(n log n)**.
- 비용(왜): 표가 `levels x n` 칸이므로 메모리 **O(n log n)** — 덱의 O(k) 보다 훨씬 크다.
- 한계: 이 문제 하나만 놓고 보면 덱보다 느리고 메모리도 더 쓴다.\
  `SparseTableProblemsTest.versusDeque` 가 그 사실을 주석에 그대로 적어 두었다.
- 한계: 값이 바뀌면 표 전체를 다시 지어야 한다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 창마다 훑기 | O(n·k) | O(1) | n 이 아주 작을 때 | n·k 가 커지는 순간 전부 |
| 2. 단조 덱(04번) | O(n) | O(k) | k 고정 · 창이 한 방향 · 질의가 이 한 종류 | k 가 여러 개 · 구간이 제멋대로 |
| 3. 희소 테이블 | O(n log n) 전처리 + 질의당 O(1) | O(n log n) | 구간 질의가 많고 종류가 제각각일 때 | 값이 바뀔 때 · 메모리가 빠듯할 때 |

**데이터 규모가 커지면**

- n = 1,000 이면 접근 1 도 최악 `1000 x 500 = 50만` 번이라 체감되지 않는다.\
  세 접근 중 무엇을 골라도 된다.
- n = 1,000,000, k = 50,000 이면 접근 1 은 `(10^6 - 5x10^4) x 5x10^4 ≈ 4.75 x 10^10` 회다.\
  04번 README 가 실제로 이 임계값(4.75e10)으로 올려야 O(n·k) 구현이 확실히 걸린다고 적어 두었다.
- 같은 입력에서 접근 2 는 약 `2 x 10^6` 회 연산으로 끝난다.
- 같은 입력에서 접근 3 은 전처리 `levels x n` 규모다.\
  `levels = floor(log2 10^6) + 1 = 19 + 1 = 20` 이므로 표가 `2 x 10^7` 칸이고, `long` 이면 계산상 160MB 다.\
  질의는 95만 번이지만 각 O(1) 이라 총 95만 번 combine 이다.
- n = 1억이면 접근 3 의 표는 `28 x 10^8` 칸으로 계산상 20GB 를 넘어 메모리에 올라가지 않는다.\
  이 규모에서 희소 테이블은 선택지에서 빠지고, 블록 단위로 쪼개는 변형이나 덱으로 간다.

**질문별 답**

- Q: 04번 덱 풀이가 O(n) 으로 더 빠른데도 여기서 희소 테이블을 쓰는 조건은 무엇인가(덱 풀이가 기대고 있는 두 전제).\
  A: 덱 풀이는 ① **창이 한 방향으로만 움직인다**, ② **창 크기 k 가 하나로 고정이다** — 이 두 전제에 기대고 있다.\
  `SparseTableProblemsTest.versusDeque` 의 주석이 그 두 전제를 그대로 적어 두었다("창이 한 방향으로만 움직이고 창 크기가 하나로 고정일 때는 그쪽이 더 싸다").\
  전제 ①이 깨지면(구간이 제멋대로이면) 앞에서만 버리는 규칙이 성립하지 않아 덱이 아예 못 쓰인다.\
  전제 ②가 깨지면(k 가 여러 개면) k 마다 처음부터 다시 훑어야 해서 `O(n) x (k 종류 수)` 가 된다.\
  희소 테이블은 표 하나로 `k = 1..n` 을 전부 답한다 — 같은 테스트가 n=64 에서 창 2,080 개를 표 하나로 답하고 `assertEquals(2080, answered)` 로 못 박는다.\
  2,080 은 `sum(k=1..64) (64 - k + 1) = 1 + 2 + ... + 64 = 64x65/2` 로 손계산이 맞는다.

- Q: 결과 길이가 `n - k + 1` 인 이유는.\
  A: 창의 시작점이 `0` 부터 `n - k` 까지만 놓일 수 있기 때문이다.\
  시작점이 `n - k + 1` 이면 창의 끝이 `n` 이 되어 배열 밖으로 나간다.\
  `0` 부터 `n - k` 까지는 **양끝 포함**이라 개수가 `n - k + 1` 이다.\
  impl 도 `int[] out = new int[values.length - k + 1];` 로 그대로 쓴다.\
  `SparseTableProblemsTest.resultLength` 가 n=20 에서 `k = 1..20` 전부에 대해 이 길이를 확인한다 — k=1 이면 20, k=20 이면 1 이다.

> **오프바이원(off-by-one)** — 경계에서 1 을 더하거나 빼는 자리를 틀리는 실수.\
> 예: `n - k` 로 쓰면 결과가 한 칸 짧고, 마지막 창의 답이 통째로 빠진다.

- Q: 비용은 왜 그런가.\
  A: 전처리는 표의 칸 수만큼 combine 을 부르므로 `O(n log n)` 이다.\
  질의는 층 번호를 `log` 표에서 O(1) 에 읽고 칸 두 개를 combine 하므로 창 하나당 **combine 정확히 한 번**이다.\
  `SparseTableStructureTest.queryIsAlwaysOneStep` 이 1000칸 구간도 한 칸 구간도 combine 1회임을 assert 한다.\
  창이 `n - k + 1` 개이므로 질의 전체가 `O(n)` 이고, 전처리가 지배해 총 **O(n log n)** 이다.\
  덱의 O(n) 보다 `log n` 배 느리지만, 이 비용은 **창 종류가 몇 개든 한 번만** 낸다.

#### 2. 문제 2 — 구간 gcd 질의

**접근 1 — 질의마다 구간을 훑기** (정의 그대로)

```java
// 의사코드
for (int i = 0; i < queries.length; i++) {
    long g = 0;
    for (int j = queries[i][0]; j <= queries[i][1]; j++) {
        g = gcd(g, values[j]);
    }
    out[i] = g;
}
```

```
처리 과정 : values = [12, 18, 24, 9, 27, 6, 15, 45], query = [2, 6]

  idx   0    1    2    3    4    5    6    7
      +----+----+----+----+----+----+----+----+
      | 12 | 18 | 24 |  9 | 27 |  6 | 15 | 45 |
      +----+----+----+----+----+----+----+----+
                 |<------- 다섯 칸 전부 --------|

  g=0 -> gcd(0,24)=24 -> gcd(24,9)=3 -> gcd(3,27)=3 -> gcd(3,6)=3 -> gcd(3,15)=3
  답 = 3   (SparseTableProblemsTest.knownValues 의 여섯 번째 기댓값)
```

- 논리: gcd 의 항등원이 0 이므로 누산기를 0 에서 시작하면 첫 값이 그대로 들어온다.
- 비용(왜): 질의 하나에 구간 길이만큼 gcd 호출 → `O(q x len)`, 최악 `O(q x n)`.
- 한계: `largeScale` 테스트가 n=20만, q=20만, 구간 길이 최대 5000 에 `@Timeout(20)` 을 건다.\
  최악 `2x10^5 x 5x10^3 = 10^9` 회 gcd 호출이고, gcd 한 번이 또 `O(log 값)` 이라 통과하지 못한다.

> **전처리(preprocessing)** — 질의를 받기 전에 미리 계산해 두는 단계. 질의를 싸게 만드는 대가를 여기서 한 번에 낸다.\
> 예: 희소 테이블은 길이 1, 2, 4, 8 … 구간의 답을 전부 미리 표에 적어 둔다.

> **유클리드 호제법(Euclidean algorithm)** — `gcd(a, b) = gcd(b, a % b)` 를 나머지가 0 이 될 때까지 반복해 최대공약수를 구하는 방법.\
> 예: `gcd(12, 18) -> gcd(18, 12) -> gcd(12, 6) -> gcd(6, 0) = 6`.

**접근 2 — 세그먼트 트리(13번)** (갱신도 되는 대신 질의가 O(log n))

```
처리 과정 : 구간을 "정확히 덮는" 노드들을 모아 접는다 - 겹치면 안 되므로 조각이 여러 개다

              [0..7]
        +-------+-------+
     [0..3]           [4..7]
   +---+---+        +---+---+
[0..1] [2..3]    [4..5] [6..7]

  query(2, 6) 이 쓰는 노드 :  [2..3]  [4..5]  [6..6]
                              조각 3개 -> combine 2번 (+ 내려가고 올라오는 재귀)

  조각이 겹치지 않아야 하므로 층마다 최대 두 개씩 -> O(log n) 개 조각.
```

- 논리: 결합법칙만 있으면 되므로 gcd 든 합이든 행렬곱이든 다 된다.
- 비용(왜): 질의 하나가 `O(log n)`, 전체 `O(n + q log n)`.
- 비용(왜): 메모리 `4n`.
- 한계: 질의가 아주 많으면 `log n` 배가 그대로 전체 비용에 남는다.\
  `SparseTableProblemsTest.sparseTableIsFlat` 이 n=4096, q=2000 에서 세그먼트 트리 combine 을 **37,798번**으로 assert 한다.

**접근 3 — 희소 테이블, 전처리를 루프 밖으로** (impl 의 정답)

```java
public static long[] rangeGcdQueries(int[] values, int[][] queries) {
    if (values == null || values.length == 0) {
        throw new IllegalArgumentException("원소가 하나 이상 있어야 한다");
    }
    if (queries == null) {
        throw new IllegalArgumentException("질의 배열이 필요하다");
    }
    long[] a = new long[values.length];
    for (int i = 0; i < values.length; i++) {
        a[i] = values[i];
    }
    GcdSparseTable t = new GcdSparseTable(a);     // <- 루프 밖. 여기가 이 문제의 전부다
    long[] out = new long[queries.length];
    for (int i = 0; i < queries.length; i++) {
        int[] q = queries[i];
        if (q == null || q.length != 2) {
            throw new IllegalArgumentException("질의는 {from, to} 두 칸이어야 한다: " + i + "번");
        }
        if (q[0] < 0 || q[1] >= values.length || q[0] > q[1]) {
            throw new IllegalArgumentException(
                    "질의 범위가 잘못됐다: [" + q[0] + ", " + q[1] + "] (원소 " + values.length + ")");
        }
        out[i] = t.query(q[0], q[1]);
    }
    return out;
}
```

```
처리 과정 : 표 한 번 -> 질의 q 번, 각 combine 1회

  전처리 (한 번)                        질의 (q 번)
  +---------------------------+        +------------------------+
  | GcdSparseTable 생성        |        | q[0], q[1] 검증         |
  | table[k][i] 채우기         |  --->  | k = log[len]           |
  | combine  n log n 회        |        | combine 1회            |
  +---------------------------+        +------------------------+
        O(n log n)                            O(1) x q

  n=4096 에서 (SparseTableProblemsTest 가 assert 하는 값)
     전처리 combine  40,974 회          <- preprocessingIsTheBill
     질의  combine    2,000 회 (q=2000) <- sparseTableIsFlat
     같은 질의를 세그먼트 트리로 하면 37,798 회
```

- 논리: gcd 는 멱등(`gcd(x, x) = x`)이므로 두 조각이 겹쳐도 답이 안 변한다 — 희소 테이블을 쓸 자격이 있다.
- 논리: 전처리는 질의와 무관하므로 루프 밖에 딱 한 번 둔다.
- 논리: 질의 검증을 `t.query` 앞에 두어, 잘못된 질의가 표에 닿기 전에 걸러지게 한다.
- 비용(왜): 전처리 combine 수는 `sum(k=1..levels-1) (n - 2^k + 1)` 이다.\
  n=4096 이면 `levels = log[4096] + 1 = 12 + 1 = 13` 이고 `12 x 4097 - (2^1 + ... + 2^12) = 49,164 - 8,190 = 40,974` — 테스트의 assert 값과 손계산이 일치한다.
- 비용(왜): 질의는 층 번호 한 번 읽고 combine 한 번 → `O(1)`, 전체 `O(n log n + q)`.
- 비용(왜): gcd 의 combine 자체가 상수 시간이 아니다.\
  "combine 호출 횟수"가 O(1) 인 것이고 한 번에 `O(log 값)` 이 붙는다.
- 한계: 값이 하나라도 바뀌면 표 전체를 다시 지어야 한다.
- 한계: 질의가 적으면 전처리 비용을 못 갚는다(질문 9 참조).

**접근 4(변종) — 전처리를 루프 안에 둔 경우** (컴파일도 되고 답도 맞는데 못 쓴다)

```
질의마다 표를 새로 짓는 그림

  q=1 : [표 짓기 40,974] + [질의 1]
  q=2 : [표 짓기 40,974] + [질의 1]
  ...
  q=2000 : [표 짓기 40,974] + [질의 1]

  총 combine = 2000 x 40,974 + 2000 = 81,950,000 회
  전처리를 밖에 두면 40,974 + 2,000 = 42,974 회
  같은 답을 내는 데 약 1,907 배를 쓴다.
```

- 논리: 답 자체는 맞으므로 "느린 구현과 같다" 류의 정확성 테스트는 전부 통과한다.
- 한계: `@Timeout(20)` 이 붙은 `largeScale` 에서만 잡힌다.\
  n=20만이면 `levels = floor(log2 200000) + 1 = 17 + 1 = 18`, 전처리 combine 이 `17 x 200,001 - (2^18 - 2) = 3,400,017 - 262,142 = 3,137,875` 회다.\
  질의 20만 번마다 이것을 반복하면 `6.3 x 10^11` 회라 20초 안에 끝나지 않는다.
- 한계: **정확성 테스트만 있으면 이 실수는 안 잡힌다** — 시간 제한 테스트가 성능 계약을 지키는 유일한 장치다.

**접근 비교**

| 접근 | 전처리 | 질의 1회 | 전체 | 갱신 | 언제 쓰나 |
|---|---|---|---|---|---|
| 1. 매번 훑기 | 없음 | O(len) | O(q·n) | O(1) | 질의가 몇 개 없을 때 |
| 2. 세그먼트 트리(13번) | O(n) | O(log n) | O(n + q log n) | O(log n) | 값이 바뀌고 질의도 있을 때 |
| 3. 희소 테이블 | O(n log n) | O(1) | O(n log n + q) | **불가능** | 값이 고정 · q 가 n 보다 훨씬 클 때 |
| 4. 전처리를 루프 안에 | — | O(n log n) | O(q·n log n) | — | 쓰지 않는다(버그) |

**데이터 규모가 커지면**

- n = 1,000, q = 10 이면 전처리 `levels = 10` 이라 combine 이 약 `9 x 1000 = 9,000` 회인데 질의는 10 회다.\
  세그먼트 트리가 `1,000 + 10 x 10 = 1,100` 회로 압승이다 — **q 가 작으면 진다.**
- n = 1,000,000, q = 1,000,000 이면 전처리가 약 `19 x 10^6 = 1.9 x 10^7` 회, 질의가 `10^6` 회다.\
  세그먼트 트리는 질의만 `10^6 x 20 = 2 x 10^7` 회이므로 이 지점에서 이미 비슷하고, q 가 더 늘면 희소 테이블이 앞선다.
- n = 1억이면 표가 `27 x 10^8` 칸이라 `long` 기준 계산상 20GB 를 넘는다.\
  메모리가 먼저 무너지므로 시간 이야기를 할 기회가 없다.
- 값이 바뀌는 상황이 하나라도 섞이면 규모와 무관하게 세그먼트 트리로 간다.

**질문별 답**

- Q: 전처리를 루프 밖으로 빼는 것이 왜 이 문제의 전부인가(안 빼면 비용이 어떻게 되는가).\
  A: 이 자료구조의 존재 이유가 "비용을 전처리로 몰아넣고 질의를 공짜로 만드는 것"이기 때문이다.\
  전처리를 질의 루프 안에 두면 몰아넣은 비용이 질의 수만큼 곱해져, 질의를 싸게 만들려고 도입한 구조가 가장 비싼 구조가 된다.\
  비용은 `O(n log n + q)` 에서 `O(q x n log n)` 으로 바뀐다.\
  n=4096, q=2000 이면 42,974 회가 81,950,000 회가 되어 약 1,907 배다(위 손계산).\
  그리고 이 실수는 **답이 맞기 때문에** 정확성 테스트로는 안 잡히고 `@Timeout` 으로만 잡힌다.

- Q: 세그먼트 트리의 O(q log n) 과 희소 테이블의 O(n log n + q) 는 언제 갈리는가.\
  A: `q` 와 `n log n` 의 크기 비교에서 갈린다.\
  희소 테이블이 이기려면 `n log n + q < q log n`, 즉 `n log n < q (log n - 1)` 이어야 한다.\
  대충 `q > n` 부터 이기기 시작하고, `q >> n` 이면 차이가 그대로 남는다.\
  테스트가 잰 실제 걸음 수로 보면 n=4096, q=2000 에서 조회만 37,798 대 2,000(18.9배)인데 희소 테이블은 전처리 40,974 를 먼저 낸다.\
  그래서 손익분기는 `40,974 + q = 18.899q` → `q ≈ 2,290` 이다 — 이 q 분포에서는 2,290 번쯤 질의해야 본전이다.\
  (18.899 = 37,798 / 2,000 으로, 이 테스트가 만든 구간 길이 분포에서의 질의당 평균이다. 다른 분포면 손익분기도 움직인다.)

- Q: 질의 검증을 빼먹으면 무엇이 예외로 새어 나가고 무엇이 조용히 답이 되는가 — 어느 쪽이 더 나쁜가.\
  A: `q[1] >= n` 이나 `q[0] < 0` 은 `SparseTable.requireIndex` 에 걸려 `IndexOutOfBoundsException` 으로 **새어 나간다**.\
  호출자가 기대한 `IllegalArgumentException` 이 아닌 다른 예외가 나오고, 메시지도 "질의가 잘못됐다"가 아니라 "인덱스가 범위를 벗어났다"라 원인 추적이 한 단계 멀어진다.\
  반대로 `q[0] > q[1]`(뒤집힌 구간)은 예외가 아니라 `from > to` 분기에 걸려 **`identity()` 를 조용히 정상 답으로 돌려준다** — gcd 면 0 이다.\
  `q.length != 2` 도 `q[1]` 접근에서 터지거나(길이 1) 세 번째 칸을 무시하고 조용히 답을 낸다(길이 3).\
  **조용히 답이 되는 쪽이 더 나쁘다.**\
  예외는 시끄럽게 실패해서 호출자가 반드시 마주치지만, 0 은 "이 구간의 gcd 가 0 이다"라는 그럴듯한 값이라 잘못된 질의가 그대로 통계나 리포트에 섞여 들어간다.\
  `SparseTableProblemsTest.badArgs` 가 이 여섯 갈래(`{0,2}`, `{1,0}`, `{-1,1}`, `{0}`, `null`, 전체 null)를 전부 `IllegalArgumentException` 으로 못 박는 이유가 그것이다.

> **조용한 실패(silent failure)** — 예외도 안 나고 멈추지도 않는데 결과만 틀린 것.\
> 예: 뒤집힌 구간에 gcd 0 을 돌려주면 호출자는 잘못된 질의를 보냈다는 사실을 영원히 모른다.

#### 3. 희소 테이블은 왜 필요한가 — 삼각형의 세 번째 꼭짓점

- Q: 13번(조회·갱신 O(log n))과 17번(역연산만, 코드 열 줄)에 이어 여기서는 무엇을 파는가.\
  A: 13번은 **일반성**을 샀다 — 결합법칙만 있으면 무엇이든 접는 대신 조회도 갱신도 O(log n) 이고 메모리가 4n 이다.\
  17번은 그 일반성을 **팔았다** — 역연산이 있는 연산(사실상 합)만 되는 대신 메모리가 n+1 이 되고 코드가 열 줄이 됐다.\
  22번은 **갱신 자체를 판다** — 값을 바꿀 수 없게 되는 대신 조회가 O(1) 이 된다.\
  세 구조가 각각 "무엇을 포기하고 무엇을 얻었는가"의 다른 답이고, README 의 표가 그 셋을 한 줄씩 늘어놓아 삼각형을 완성한다.

- Q: **갱신을 아예 포기하면** 무엇을 얻는가.\
  A: 표의 칸이 절대 틀어지지 않는다는 보장을 얻는다.\
  그래서 "구간을 겹치지 않게 덮어야 한다"는 제약을 버릴 수 있고, 겹쳐도 되면 **아무 구간이나 2의 거듭제곱 조각 딱 두 개로** 덮인다.\
  조각 수가 구간 길이와 무관하게 2 로 고정되므로 조회가 combine 한 번, 즉 O(1) 이다.\
  `SparseTableStructureTest.queryIsAlwaysOneStep` 이 1000칸 구간도 combine 1회임을 assert 해 이 말을 숫자로 못 박는다.\
  대가는 메모리 `n log n` 과 전처리 `O(n log n)` 이다.

- Q: 셋 중 무엇을 고를지는 무엇이 정하는가.\
  A: **조회와 갱신의 비율**이 정한다(README 14줄).\
  갱신이 섞여 있으면 희소 테이블은 후보에서 빠진다 — 한 칸만 바뀌어도 전체를 다시 지어야 하기 때문이다.\
  갱신이 없고 질의가 `n` 보다 훨씬 많으면 희소 테이블이다.\
  갱신이 없고 질의도 적으면 전처리를 못 갚으므로 세그먼트 트리나 그냥 훑기가 낫다.\
  연산이 합처럼 역연산을 가지면 17번이 같은 O(log n) 을 훨씬 작은 상수와 코드로 해낸다.

```
세 구조의 자리 (README 표를 코드로 확인한 것)

          조회      갱신       전처리      메모리        요구 조건
  13번  O(log n)  O(log n)    O(n)        4n          결합법칙(모노이드)
  17번  O(log n)  O(log n)    O(n)        n+1         역연산
  22번  O(1)      불가능      O(n log n)  n log n     멱등성 + 결합법칙

  실제로 잰 값 (n=4096)
     희소 테이블 : 전처리 40,974 회 / 조회 1회당 1 회 / 칸 53,248개
     세그먼트    : 조회 2000번에 37,798 회 / 칸 16,384개
     (SparseTableProblemsTest.preprocessingIsTheBill, sparseTableIsFlat)
```

**더 생각할 것**

- 이 표의 "요구 조건" 칸이 위로 갈수록 느슨하고 아래로 갈수록 빡빡하다.\
  자료구조를 빠르게 만드는 방법은 대개 **연산에 더 강한 성질을 요구하는 것**이다.
- 세 구조 모두 "구간을 조각으로 덮어 combine 한다"는 뼈대는 같다.\
  다른 것은 조각을 몇 개로 덮는가(O(log n) 개 / O(log n) 개 / 2개)와, 그래서 조각이 겹쳐도 되는가뿐이다.
- 실무에서는 "질의가 많다"를 재보지 않고 고르면 대개 틀린다.\
  q 와 n 의 실제 비율을 먼저 재는 것이 자료구조 선택의 첫 단계다.

#### 4. 어떻게 조회가 O(1) 이 되는가

- Q: 2의 거듭제곱 길이 구간의 답을 전부 미리 계산해 두면 아무 구간이나 왜 **딱 두 조각**으로 덮이는가.\
  A: 길이 `len` 에 대해 `k = floor(log2 len)` 로 잡으면 `2^k <= len < 2^(k+1)` 이 성립한다.\
  왼쪽 끝에 붙인 조각 `[from, from + 2^k - 1]` 과 오른쪽 끝에 붙인 조각 `[to - 2^k + 1, to]` 을 쓴다.\
  두 조각이 가운데서 만나려면 `to - 2^k + 1 <= from + 2^k`, 즉 `len <= 2^(k+1)` 이어야 하는데 이것이 위 부등식의 오른쪽이다 — **빈틈이 생길 수 없다.**\
  두 조각 모두 `2^k <= len` 이라 `[from, to]` 를 벗어나지도 않는다 — **밖의 값이 섞이지도 않는다.**\
  `2^k > len/2` 이므로 각 조각이 구간의 절반을 넘게 덮고, 그래서 둘이면 충분하다.

```
왜 두 조각이면 덮이는가 (len = 6, k = log[6] = 2, 2^k = 4)

  idx     0    1    2    3    4    5    6    7
       +----+----+----+----+----+----+----+----+
       |  5 |  2 |  9 |  1 |  7 |  4 |  6 |  3 |
       +----+----+----+----+----+----+----+----+
            |<--- table[2][1] = [1..4] --->|
                      |<--- table[2][3] = [3..6] --->|
                      |<-->|  겹침 = 2^(k+1) - len = 8 - 6 = 2 칸

  각 조각이 4칸 = 구간 6칸의 절반보다 크다 -> 반드시 가운데서 만난다.
  조각 길이가 len 을 넘지 않는다 -> 구간 밖으로 안 나간다.
```

- Q: 13번이 O(log n) 개 조각으로 덮은 것과 무엇이 다른가.\
  A: 13번은 조각이 **겹치면 안 되므로** 구간을 정확히 분할해야 한다.\
  정확히 분할하려면 트리의 정규 노드들만 쓸 수 있고, 그런 노드는 층마다 최대 두 개씩 모여 `O(log n)` 개가 된다.\
  22번은 조각이 **겹쳐도 되므로** 분할이 아니라 덮기만 하면 된다 — 덮기는 크기를 마음대로 겹쳐 고를 수 있어 두 개로 끝난다.\
  다시 말해 "조각 수 `O(log n)` → `2`" 를 사게 한 값이 **멱등성이라는 추가 요구 조건**이다.\
  구간이 백만 칸이어도 combine 은 한 번이고, 그것이 O(1) 의 정확한 뜻이다.

> **배증(doubling)** — 아래층의 답 두 개를 이어 붙여 길이가 2배인 위층 답을 만드는 쌓기 방식.\
> 예: `table[k][i] = combine(table[k-1][i], table[k-1][i + 2^(k-1)])` 로 길이 2 짜리 둘을 붙여 길이 4 를 만든다.

> **floor(log2 x)** — x 가 2의 몇 제곱 이상인지의 정수 부분. 구간을 덮을 조각의 층 번호가 된다.\
> 예: `floor(log2 6) = 2` 이므로 길이 6 구간은 길이 4 짜리 조각 두 개로 덮는다.

**더 생각할 것**

- 전처리에서 붙이는 두 조각은 **딱 맞닿고 겹치지 않는다**(`i` 와 `i + 2^(k-1)`).\
  겹침이 생기는 곳은 조회뿐이다 — 그래서 멱등성은 build 가 아니라 query 때문에 필요한 조건이다.
- `k` 를 구하는 일이 O(1) 이어야 전체가 O(1) 이다.\
  그래서 `log` 표를 미리 채운다(질문 11).
- 조각을 두 개가 아니라 정확히 하나로 덮을 수 있는 경우는 `len` 이 2의 거듭제곱일 때뿐이다.\
  그때는 두 조각이 통째로 같은 칸이 되어 `combine(x, x)` 를 부른다 — 멱등성이 가장 먼저 드러나는 자리다.

#### 5. 세 번째 대수적 조건 — 멱등성

- Q: 두 조각이 겹치기 때문이라는 것을 설명해 보라.\
  A: 조회는 `[from, from+2^k-1]` 과 `[to-2^k+1, to]` 두 조각을 combine 한다.\
  겹치는 칸 수는 `2^(k+1) - len` 이고, `len < 2^(k+1)` 이므로 이 값은 **항상 1 이상**이다.\
  즉 어떤 구간을 물어도 최소 한 칸은 두 번 접힌다.\
  두 번 접은 결과가 한 번 접은 결과와 같아야 답이 맞고, 그 조건이 `f(x, x) = x` — 멱등성이다.\
  `IdempotenceTest.overlapAlwaysExists` 가 `len = 1..4096` 전부에서 `overlap >= 1` 을 assert 해 이것을 못 박는다.\
  같은 테스트가 "길이 3 은 한 칸만 겹친다", "길이 4 는 두 창이 통째로 겹친다"도 확인한다.

> **멱등(idempotent)** — 같은 값을 두 번 넣어도 결과가 변하지 않는 성질, `f(x, x) = x`.\
> 예: `min(7, 7) = 7` 이라 7 을 두 번 세도 최솟값이 그대로지만, `7 + 7 = 14` 라 합은 달라진다.

- Q: 합·XOR 이 왜 안 되고 최소·최대·gcd·비트 AND/OR 은 왜 되는가.\
  A: 합은 `x + x = 2x` 라 겹친 칸이 두 번 더해진다.\
  XOR 은 `x ^ x = 0` 이라 겹친 칸이 아예 지워진다 — 더 심하다.\
  최소·최대는 `min(x,x) = x`, `max(x,x) = x` 로 몇 번을 접든 같은 값이다.\
  gcd 는 `gcd(x, x) = x` 이고, 비트 AND·OR 도 `x & x = x`, `x | x = x` 다.\
  `IdempotenceTest.whichOperationsQualify` 가 이 여섯 가지를 한 테스트에서 assert 로 나열한다 — min, max, AND, OR, gcd 는 `assertEquals`, 합·곱·XOR 은 `assertNotEquals` 다.

- Q: 13번은 모노이드를, 17번은 역원을 요구했다는 계보에서 이것의 자리는.\
  A: 멱등성은 앞의 조건을 **대체하는 것이 아니라 얹히는 것**이다.\
  13번이 요구한 결합법칙은 여기서도 여전히 필요하다 — 조각을 접는 순서가 답을 바꾸면 안 되기 때문이다.\
  `SparseTableContractTest.stillAssociative` 가 이것을 따로 테스트로 두고 주석에 "멱등성이 결합법칙을 대신하는 것이 아니다. 둘 다 있어야 한다"라고 적어 두었다.\
  17번의 역원은 이 계보에서 **다른 가지**다 — gcd 는 멱등이지만 역원이 없어서 펜윅에는 못 들어가고 희소 테이블에는 들어간다.\
  `GcdSparseTableTest.idempotentButNotInvertible` 이 바로 그 갈림을 보여준다("12 와 18 의 gcd 는 6 이지만, 6 과 12 만으로 18 을 되찾을 방법이 없다").

> **모노이드(monoid)** — 결합법칙이 성립하고 항등원이 있는 연산 구조. 13번 세그먼트 트리가 요구하는 최소 조건이다.\
> 예: `(합, 0)`, `(min, 무한대)`, `(gcd, 0)` 이 전부 모노이드다.

> **역원(inverse)** — `a` 를 되돌리는 값이 있어 `prefix(r) - prefix(l-1)` 처럼 빼서 가운데를 얻을 수 있는 성질.\
> 예: 합에는 뺄셈이 있어 펜윅 트리가 쓰지만, min 이나 gcd 에는 그런 뺄셈이 없다.

```
세 조건의 포함 관계 (원본 README 의 표를 코드로 확인한 것)

  연산       결합법칙(13)  역연산(17)  멱등성(22)
  합            예           예         아니오
  XOR           예           예         아니오  (x^x=0)
  최소, 최대    예         아니오         예
  gcd           예         아니오         예
  비트 AND/OR   예         아니오         예

  -> 13번에 들어갈 수 있는 연산이 제일 넓고,
     17번과 22번은 거기서 서로 다른 방향으로 잘라낸 부분집합이다.
```

**더 생각할 것**

- "멱등이면 겹쳐도 된다"는 곧 "중복 계산을 허용한다"는 뜻이다.\
  중복 계산을 허용하는 대신 조각 수를 2 로 고정한 것이 이 자료구조의 거래다.
- `DisjointSparseTable` 은 그 거래를 반대로 한다 — 중복을 없애고 멱등성 요구를 버린다(질문 7).
- 평균(average)은 멱등도 아니고 결합법칙도 없다.\
  13번 README 가 이미 "평균은 결합법칙이 없다"를 다뤘고, 여기서는 아예 후보에 오르지 못한다.

#### 6. 합으로 만들면 왜 조용히 틀리는가

- Q: 왜 컴파일도 되고 예외도 안 나는데 **조용히 틀리는가**.\
  A: `combine` 의 시그니처가 `long combine(long a, long b)` 뿐이라 타입 시스템이 검사할 수 있는 것이 거기까지이기 때문이다.\
  멱등성은 타입이 아니라 **의미론적 성질**이라 컴파일러가 볼 방법이 없다.\
  실행 중에도 배열 범위를 벗어나거나 0으로 나누는 일이 없으니 예외도 안 난다.\
  `IdempotenceTest.BrokenSumSparseTable` 이 정확히 그 클래스다 — `combine` 을 `a + b`, `identity` 를 `0L` 로 두면 문법적으로 완벽하다.\
  결과는 항상 진짜 답보다 크고, 크기가 그럴듯해서 눈으로 봐도 틀린 줄 모른다.

- Q: `[1,2,3]` 에서 `query(0,0)` 과 `query(1,2)` 가 각각 무엇이 되는가.\
  A: `query(0,0)` 은 **2**, `query(1,2)` 는 **10** 이다(`IdempotenceTest.everyRangeOfThree`).\
  손계산으로 따라가면 이렇다.

```
합으로 만든 표 : values = [1, 2, 3], n = 3
   log[2] = 1, log[3] = 1  ->  levels = log[3] + 1 = 2

   table[0] = [1, 2, 3]                       (원본 복사)
   table[1][0] = 1 + 2 = 3     [0..1]
   table[1][1] = 2 + 3 = 5     [1..2]
   (i + 2 <= 3 인 i 까지만 -> i = 0, 1)

 query(0, 0)  len = 1, k = log[1] = 0, 2^k = 1
      왼쪽 조각 table[0][0]           = [0..0] = 1
      오른쪽 조각 table[0][0 - 1 + 1] = [0..0] = 1     <- 똑같은 칸이다
      1 + 1 = 2        진짜 답은 1

 query(1, 2)  len = 2, k = log[2] = 1, 2^k = 2
      왼쪽 조각 table[1][1]           = [1..2] = 5
      오른쪽 조각 table[1][2 - 2 + 1] = table[1][1] = 5  <- 또 똑같은 칸이다
      5 + 5 = 10       진짜 답은 5

 query(0, 2)  len = 3, k = log[3] = 1, 2^k = 2
      왼쪽 조각 table[1][0] = [0..1] = 3
      오른쪽 조각 table[1][1] = [1..2] = 5
      3 + 5 = 8        진짜 답은 6, 가운데 2 만 두 번 세어 +2
```

- Q: "어떤 구간에서는 맞겠지"가 성립하지 않는 이유는.\
  A: 겹치는 칸 수가 `2^(k+1) - len` 인데 `len < 2^(k+1)` 이므로 **항상 1 이상**이기 때문이다.\
  겹침이 0 이 되려면 `len = 2^(k+1)` 이어야 하는데, 그러면 `k = floor(log2 len)` 의 정의상 k 가 하나 커져 다시 겹친다.\
  그래서 길이 1 짜리 구간도 틀린다 — `evenSingleElementIsDoubled` 가 `[7]` 에서 `query(0,0) = 14` 를 assert 한다.\
  틀리는 양에도 규칙이 있다: `errorIsExactlyTheOverlap` 이 n=1..32 의 모든 구간에서 `진짜 합 + 겹친 구간의 합 = 표의 답` 임을 확인한다.\
  즉 "가끔 맞는 버그"가 아니라 **모든 구간에서 예외 없이 틀리는** 버그다.

**더 생각할 것**

- 이런 종류의 잘못은 계약을 문서로 적어두는 것만으로는 못 막는다.\
  이 문제집은 대신 **일부러 틀린 클래스를 만들어 틀린 값을 assert** 하는 방식을 택했다(09번 트라이, 13번 평균과 같은 방식이라고 `IdempotenceTest` 주석이 적어 두었다).
- "컴파일이 된다"와 "쓸 수 있다"가 다르다는 것이 요점이다.\
  추상 클래스가 `combine` 을 받는 순간, 그 combine 이 멱등인지는 **호출자의 책임**으로 넘어간다.
- 합이 정말 필요하면 구조를 바꾼다 — `DisjointSparseTable` 이 같은 `[1,2,3]` 에서 `query(0,2) = 6` 으로 맞는 답을 낸다(`disjointGetsItRight`).

#### 7. DisjointSparseTable 은 그 조건을 어떻게 없애는가

- Q: 층마다 가운데를 기준으로 좌우로 누적하면 왜 두 조각이 겹치지 않게 되고, 그래서 합도 곱도 되는가.\
  A: 이 구조는 "i 에서 시작하는 길이 2^k 구간의 답"이 아니라 **"i 에서 그 블록의 중앙까지의 누적"** 을 저장한다.\
  층 `level` 의 블록 폭은 `2^(level+1)` 이고 그 한가운데가 `center` 다.\
  중앙 왼쪽 칸 `i` 에는 `[i .. center-1]` 의 답을, 오른쪽 칸 `i` 에는 `[center .. i]` 의 답을 넣는다.\
  조회에서 고르는 층은 `from` 과 `to` 의 비트가 **처음 갈라지는 자리**라, 그 층의 블록에서 `from` 은 중앙 왼쪽, `to` 는 중앙 오른쪽에 있다.\
  그러면 `[from .. center-1]` 과 `[center .. to]` 는 딱 맞물리고 **겹치는 칸이 0개**다.\
  겹침이 0 이면 두 번 세는 일이 없으므로 멱등성이 필요 없고, 결합법칙과 항등원만 있으면 된다 — 합도 곱도 행렬곱도 된다.

```java
// impl/DisjointSparseTable.java — build 의 핵심
for (int level = 0; level < levels; level++) {
    int range = 1 << level;
    long[] row = table[level];
    for (int center = range; center < width; center += range << 1) {
        row[center - 1] = padded[center - 1];
        for (int i = center - 2; i >= center - range; i--) {
            row[i] = combine.applyAsLong(padded[i], row[i + 1]);   // 왼쪽: 중앙 쪽으로 누적
        }
        row[center] = padded[center];
        for (int i = center + 1; i < center + range; i++) {
            row[i] = combine.applyAsLong(row[i - 1], padded[i]);   // 오른쪽: 중앙에서 바깥으로
        }
    }
}
```

```
query(1, 6) 의 그림 (values = [5,2,9,1,7,4,6,3], 합)

  1 = 001, 6 = 110  ->  1 ^ 6 = 111  ->  최상위 1 은 2번 자리  ->  level = 2
  level 2 의 블록은 [0..7], 중앙 center = 4

  idx      0    1    2    3    4    5    6    7
        +----+----+----+----+----+----+----+----+
 t[2]   | 17 | 12 | 10 |  1 |  7 | 11 | 17 | 20 |
        +----+----+----+----+----+----+----+----+
               ^                        ^
        t[2][1] = [1..3] = 2+9+1 = 12   t[2][6] = [4..6] = 7+4+6 = 17

               |<--- [1..3] --->|<--- [4..6] --->|
           맞닿기만 하고 겹치는 칸이 하나도 없다

  답 = 12 + 17 = 29     실제 2+9+1+7+4+6 = 29
```

> **XOR(^) 과 최상위 비트** — XOR 은 비트 자리별로 "다르면 1"을 놓는 연산이라, `from ^ to` 의 가장 높은 1 자리가 두 수가 처음 갈라지는 자리다.\
> 예: `1(001) ^ 6(110) = 7(111)` 이고 최상위 1 은 2번 자리이므로 층 2 를 고른다.

> **비가환(non-commutative)** — `a∘b` 와 `b∘a` 가 다른 연산. 인자 순서를 지켜야 한다.\
> 예: 행렬곱이나 "마지막 0 아닌 값"처럼, 왼쪽 조각을 먼저 놓느냐 오른쪽을 먼저 놓느냐가 답을 바꾼다.

- Q: 조회가 여전히 O(1) 인 이유는.\
  A: 층 번호를 `31 - Integer.numberOfLeadingZeros(from ^ to)` 로 **비트 연산 두 번**에 얻기 때문이다.\
  그 뒤로는 배열 읽기 두 번과 combine 한 번뿐이다.\
  구간 길이에 의존하는 루프가 어디에도 없다.\
  `DisjointSparseTableTest.queryIsOneCombine` 이 1000칸 구간도 combine 1회임을 assert 한다.\
  같은 테스트가 `t.query(500, 500)` 뒤에도 호출 수가 그대로임을 확인한다 — `l == r` 은 combine 조차 부르지 않는다.

- Q: `l == r` 을 따로 빼야 하는 이유는.\
  A: `l == r` 이면 `l ^ r == 0` 이라 **갈라지는 비트가 없기** 때문이다.\
  `Integer.numberOfLeadingZeros(0)` 은 32 이므로 `31 - 32 = -1` 이 되고, `table[-1]` 은 `ArrayIndexOutOfBoundsException` 으로 터진다.\
  그래서 impl 은 `if (from == to) return values[from];` 로 먼저 빼낸다.\
  n=1 이면 `levels` 가 아예 0 이라 표에 행이 하나도 없으므로(`singleton` 이 `levels() == 0`, `unitCount() == 0` 을 assert 한다) 이 분기가 없으면 어떤 조회도 못 한다.\
  README 는 이것을 빼지 않으면 90개 중 **12개가 무너진다**고 적는다(README 기준 — 테스트 코드에 그 숫자는 assert 되어 있지 않다).\
  `SameIndex` 라는 이름의 중첩 클래스를 따로 두고 "여기가 제일 틀리기 쉽다"고 주석을 단 것이 그 위험도의 표시다.

**더 생각할 것**

- 두 구조의 메모리는 같은 `n log n` 급이지만 Disjoint 쪽은 폭을 2의 거듭제곱으로 올림한다.\
  `memory` 테스트가 n=100 에서 `levels 7, unitCount 896`(= 7 x 128), n=1000 에서 `10,240`(= 10 x 1024) 을 assert 한다.\
  같은 n=1000 에서 `SparseTable` 은 10,000 이므로 Disjoint 가 약간 더 크다.
- 멱등한 연산은 **양쪽 다** 쓸 수 있다 — `agreesWithSparseTable` 이 min 에서 두 구조가 같은 답을 냄을 확인한다.\
  그때는 구조가 단순하고 메모리가 작은 쪽을 고른다.
- "겹침을 허용하고 멱등성을 요구한다" 대 "겹침을 없애고 요구 조건을 푼다" — 같은 O(1) 을 서로 다른 값으로 산 두 설계다.

#### 8. 항등원이 빈 구간에서만 쓰인다는 것

- Q: 13번에서는 조회마다 쓰였는데 여기서는 왜 빈 구간에서만 쓰이는가.\
  A: 세그먼트 트리의 조회는 재귀가 구간 밖 노드에 닿을 때마다 "아무 영향 없는 값"을 돌려줘야 하므로 항등원이 매 조회의 여러 지점에서 쓰인다.\
  희소 테이블의 조회는 미리 계산된 칸 두 개만 읽는다 — 그 두 칸은 **언제나 `[from, to]` 안에** 있다.\
  범위 밖을 항등원으로 메우는 경로 자체가 없다.\
  impl 의 `query` 에서 `identity()` 가 등장하는 곳은 `if (from > to) return identity();` 단 한 줄뿐이다.

```java
// impl/SparseTable.java — identity() 가 쓰이는 유일한 자리
public long query(int from, int to) {
    requireIndex(from);
    requireIndex(to);
    if (from > to) {
        return identity();          // <- 여기 하나뿐이다
    }
    int k = log[to - from + 1];
    return combine(table[k][from], table[k][to - (1 << k) + 1]);
}
```

> **항등원(identity)** — 연산에 넣어도 결과가 변하지 않는 값.\
> 예: 합의 0, min 의 `Long.MAX_VALUE`, max 의 `Long.MIN_VALUE`, gcd 의 0 이다.

- Q: 그래서 최소 테이블에 `identity() = 0` 을 넣어도 대부분의 테스트가 통과하는데, 이것이 왜 더 위험한가.\
  A: 버그가 **거의 모든 경로에서 관측되지 않기** 때문이다.\
  README 는 90개 중 87개가 통과한다고 적는다(README 기준 — 그 숫자 자체는 assert 되어 있지 않다).\
  코드로 따져보면 실제로 깨지는 것은 세 개다.\
  ① `SparseTableContractTest.reversedRangeIsIdentity`(Min 인스턴스) — `query(2,0)` 이 0 이 되어 `Long.MAX_VALUE` 와 어긋난다.\
  ② `SparseTableContractTest.identityIsNeutral`(Min 인스턴스) — `min(x, 0) = 0 ≠ x` 라 중립성이 깨진다.\
  ③ `MinSparseTableTest.zeroIdentityBreaksEvenWithPositives` — `query(3,1)` 이 `Long.MAX_VALUE` 여야 한다고 못 박는다.\
  90 - 3 = 87 로 README 의 숫자와 손계산이 맞는다.\
  위험한 이유는 이렇다: 정상 구간 조회는 **전부 정상**이라 개발 중에도 리뷰 중에도 아무 징후가 없다.\
  드러나는 순간은 호출자가 실수로 뒤집힌 구간을 넘길 때인데, 그때 `Long.MAX_VALUE`("빈 구간이다")가 아니라 `0`("최솟값이 0 이다")이 돌아온다 — 값이 그럴듯해서 조용한 실패가 된다.\
  13번이었다면 조회마다 항등원을 쓰므로 거의 모든 테스트가 즉시 빨개졌을 것이다.\
  **같은 버그라도 관측 표면이 좁을수록 위험하다.**

- Q: 그럼 항등원이 0 인 것이 늘 위험한가.\
  A: 아니다 — 기준은 "0 이냐"가 아니라 **"그 연산의 항등원이 무엇이냐"** 다.\
  gcd 는 `gcd(0, x) = x` 라서 0 이 정확히 항등원이고, impl 의 `GcdSparseTable.identity()` 는 `0L` 이 맞다.\
  `GcdSparseTableTest.zeroIsTheRightIdentity` 가 `query(1, 0) == 0` 과 `combine(12, 0) == 12` 를 assert 하며 주석에 "0 은 항상 위험하다가 아니라 그 연산의 항등원이 무엇이냐가 기준이다"라고 적어 두었다.\
  max 라면 `Long.MIN_VALUE` 여야 하고, `MaxSparseTableTest.allNegative` 가 "0 이 나오면 항등원이 새어 들어온 것"이라고 메시지에 써 둔다.

**더 생각할 것**

- 테스트를 설계할 때 "어느 경로에서 이 값이 실제로 읽히는가"를 먼저 세어 보면, 어떤 필드가 저검증 상태인지 바로 보인다.
- `Long.MAX_VALUE` 는 항등원이면서 동시에 **정상 값**일 수도 있다.\
  `MinSparseTableTest.extremes` 가 `[Long.MAX_VALUE, Long.MIN_VALUE, 0]` 에서 `query(0,0) == Long.MAX_VALUE` 를 확인한다 — 항등원과 값이 구분되지 않는다는 것 자체가 이 설계의 한계다.
- 빈 구간을 아예 예외로 막는 설계도 가능하다.\
  그러면 항등원이 조회 경로에서 완전히 사라지고, 대신 호출자가 빈 구간을 다뤄야 한다 — 어느 쪽이든 선택이지 정답은 아니다.

#### 9. 최악의 사용 패턴과 손익분기

- Q: 질의가 적을 때(n=4096, q=2000) 전처리 비용을 못 갚는 손익분기를 설명해 보라.\
  A: 테스트가 잰 값은 이렇다 — 희소 테이블은 전처리에 combine **40,974회**(`preprocessingIsTheBill`), 질의 2,000번에 **2,000회**(`sparseTableIsFlat`).\
  같은 질의를 세그먼트 트리로 하면 조회에만 **37,798회**다.\
  희소 테이블 총합 = `40,974 + 2,000 = 42,974` 회.\
  세그먼트 트리 총합(조회만) = `37,798` 회.\
  **이 조건에서는 세그먼트 트리가 이긴다** — 전처리를 못 갚았다.\
  손익분기를 풀면 `40,974 + q = 18.899q` → `q ≈ 2,290` 이다(18.899 = 37,798 / 2,000, 이 테스트의 구간 길이 분포에서의 질의당 평균).\
  즉 같은 배열에 2,300번 넘게 물어보기 시작해야 희소 테이블이 본전을 넘는다.\
  q 가 그보다 작으면 희소 테이블은 **더 많은 메모리를 쓰고 더 느린** 구조다.

```
손익분기 그림 (n = 4096, 위 테스트가 잰 값으로 그린 것)

  combine 호출 수
     |
  60k|                                   세그먼트 트리 (기울기 18.9/질의)
     |                              ..../
  45k|  희소 테이블 시작점 40,974   ../
     |  -----------------------------/---------------  희소 (기울기 1/질의)
  30k|                         .../
     |                     .../
  15k|                 .../
     |             .../
    0+---------/--------------------------------------> q
     0      1000   2290(손익분기)   3000        4000

  q < 2290 : 세그먼트 트리가 싸다
  q > 2290 : 희소 테이블이 싸고, q 가 커질수록 차이가 벌어진다
```

> **손익분기(break-even point)** — 선불 비용(전처리)을 이후의 절약분으로 다 갚는 지점.\
> 예: 전처리 40,974 회를 질의당 17.9 회씩 아껴 갚으면 약 2,290 번째 질의에서 본전이 된다.

- Q: 값을 한 칸만 바꾸면 무슨 일이 일어나는가(세그먼트 트리와 비교해).\
  A: 전부 다시 지어야 한다.\
  `SparseTableStructureTest.oneChangeRebuildsEverything` 이 n=16 에서 처음 짓는 데 combine **38회**, `a[7]` 을 바꾼 뒤 다시 짓는 데도 **또 38회**임을 assert 한다.\
  손계산으로도 맞는다 — `levels = log[16] + 1 = 5`, `k=1: 15, k=2: 13, k=3: 9, k=4: 1` 을 더하면 38 이다.\
  세그먼트 트리는 잎에서 뿌리까지 한 줄만 고치면 되므로 `log2(16) = 4` 번이다(같은 테스트 주석 기준 — 이 파일에서 세그먼트 트리를 실제로 돌려 센 값은 아니다).\
  **38 대 4 가 "갱신 불가능"의 실체다.** 이론상 불가능한 것이 아니라, 다시 짓는 것과 비용이 같아서 갱신이라고 부를 이유가 없다는 뜻이다.\
  이유는 한 원소가 층마다 여러 칸에 들어가 있기 때문이다 — 층 k 에는 그 값을 포함하는 칸이 최대 `2^k` 개다.

- Q: 메모리가 n=16 부터 역전되는 것은.\
  A: 칸 수가 `levels x n = (floor(log2 n) + 1) x n` 이고 세그먼트 트리는 `4n` 이므로, `floor(log2 n) + 1 > 4` 즉 `n >= 16` 에서 역전된다.\
  `crossesFourN` 이 세 지점을 assert 한다 — n=8 은 `4 x 8 = 32` 대 `4n = 32` 로 **같고**, n=16 은 `5 x 16 = 80` 대 `64` 로 **역전**, n=1000 은 `10 x 1000 = 10,000` 대 `4,000` 으로 **2.5배**다.\
  마지막 줄은 아예 `assertEquals(2.5, 10_000 / (double) segmentTreeCells(1000), 1e-9)` 로 배수를 못 박는다.\
  n 이 커질수록 배수가 `log n / 4` 로 계속 벌어진다 — n=10^6 이면 `20/4 = 5배`다.\
  **O(1) 조회는 공짜가 아니고, 그 값은 메모리와 전처리로 낸다.**

- Q: 반대로 최선의 경우는.\
  A: **값이 절대 안 바뀌고, 질의가 n 보다 훨씬 많고, 구간이 제멋대로일 때**다.\
  `largeScale` 테스트가 그 모양이다 — n=20만 배열을 한 번 짓고 질의 20만 번을 `@Timeout(20)` 안에 답한다.\
  전처리 combine 은 `17 x 200,001 - (2^18 - 2) = 3,137,875` 회이고 질의는 20만 회뿐이다.\
  세그먼트 트리였다면 질의에만 `200,000 x 18 ≈ 3.6 x 10^6` 회가 들었을 것이므로, 질의 수가 더 늘어날수록 차이가 그대로 누적된다.\
  여기에 "같은 배열에 여러 종류의 구간"까지 겹치면(질문 1의 창 크기 2,080개 예) 다른 구조로는 대체가 안 된다.

**더 생각할 것**

- "이 자료구조가 빠른가"가 아니라 **"이 워크로드에서 빠른가"** 를 묻는 것이 맞는 질문이다.\
  같은 코드가 q=100 에서는 최악, q=10^6 에서는 최선이 된다.
- 이 문제집이 시간을 재지 않고 **걸음 수(combine 호출 수)를 센** 것은 기계·JIT·캐시에 흔들리지 않는 숫자를 얻기 위해서다.\
  `sparseTableIsFlat` 주석이 "시간을 재지 않는다. 걸음 수를 센다"고 적어 두었다.
- 카운터 필드에 `= 0` 을 붙이면 안 된다는 주석이 두 테스트 파일에 모두 붙어 있다.\
  필드 초기화가 `super()` 뒤에 돌아 생성자에서 센 값을 지우기 때문이다 — 측정 코드 자체의 함정이다.

#### 10. 구현 전략의 트레이드오프 — 상속이냐 인자냐

- Q: `SparseTable`(상속으로 combine)과 `DisjointSparseTable`(인자로 combine)의 차이는 13번의 그 대비와 어떻게 같은가.\
  A: 13번 `SegmentTree` 는 상속으로 combine 을 정하고 `GenericSegmentTree` 는 인자로 받는다 — 13번 README 82~84줄이 "하는 일은 같고 **언제 정하느냐**가 다르다"로 요약한다.\
  22번도 똑같다.\
  `SparseTable` 은 `protected abstract long combine(long a, long b)` 라 **컴파일 시점**에 연산이 정해지고, 연산 하나에 클래스 하나가 필요하다(Min/Max/Gcd 세 개).\
  `DisjointSparseTable` 은 `LongBinaryOperator combine` 을 생성자 인자로 받아 **실행 시점**에 정해지고, 클래스 하나로 합·곱·min·비가환 연산을 전부 담는다.\
  상속 쪽은 타입이 곧 문서라 `MinSparseTable` 이라는 이름만으로 무엇을 하는지 알 수 있고, JIT 가 인라인하기도 쉽다.\
  인자 쪽은 새 연산에 클래스가 필요 없고 테스트에서 임의의 연산을 꽂아 넣을 수 있다 — `DisjointSparseTableTest` 가 곱, min, 비가환 연산을 전부 람다로 넣는 것이 그 이득이다.\
  13번 README 는 같은 대비가 05번 `LinkedHashMap`(상속)과 12번 `SkipListSet`(포함)에도 있다고 이어 붙인다.

```
같은 뼈대, 다른 결정 시점

  상속 (SparseTable)                   인자 (DisjointSparseTable)
  +---------------------------+        +-----------------------------+
  | abstract combine()        |        | LongBinaryOperator combine  |
  | abstract identity()       |        | long identity               |
  +-------------+-------------+        +-----------------------------+
      ^         ^         ^                     ^
  MinSparse  MaxSparse  GcdSparse        new DisjointSparseTable(a, 1L, (x,y) -> x*y)
  (연산마다 클래스 하나)                  (클래스 하나로 전부)

  컴파일 시점에 고정                      실행 시점에 주입
  이름이 곧 문서                          테스트에서 임의 연산 주입이 쉽다
```

- Q: 누적 방향과 인자 순서가 교환법칙 있는 연산에서 우연히 맞는다는 것을 잡으려면 어떤 테스트가 필요한가.\
  A: **교환법칙이 없는 연산을 넣어보는 테스트**가 필요하다.\
  합·최소·곱은 `f(a, b) = f(b, a)` 라 `combine(왼쪽, 오른쪽)` 을 `combine(오른쪽, 왼쪽)` 으로 뒤집어도 같은 답이 나온다 — 버그가 있어도 전부 통과한다.\
  `DisjointSparseTableTest.nonCommutative` 가 그 자리를 막는다: `f(x, y) = (y != 0 ? y : x)` 는 "구간의 마지막 0 아닌 값"이고, 결합법칙이 있고 항등원이 0 인데 **교환법칙만 없다**(`f(1,2)=2`, `f(2,1)=1`).\
  이 연산이면 왼쪽 조각과 오른쪽 조각의 순서, build 의 좌우 누적 방향이 전부 답에 드러난다.\
  README 는 90개 중 **이 하나만** 그 변종을 잡는다고 적는다(README 기준 — 테스트에 그 개수가 assert 되어 있지는 않다).\
  테스트 주석도 같은 말을 한다: "누적 방향이나 combine 의 인자 순서를 뒤집는 실수는 합, 최소, 곱 같은 교환법칙 있는 연산에서는 우연히 맞아서 안 잡힌다".

```java
// impl/DisjointSparseTable.java — 순서가 드러나는 세 자리
row[i] = combine.applyAsLong(padded[i], row[i + 1]);   // 왼쪽 누적: 바깥값이 앞
row[i] = combine.applyAsLong(row[i - 1], padded[i]);   // 오른쪽 누적: 누적값이 앞
return combine.applyAsLong(table[level][from], table[level][to]);   // 조회: 왼쪽 조각이 앞
```

**더 생각할 것**

- "우연히 맞는 경우가 있다는 것이 더 위험하다"는 문장이 13번 README(78~80줄, 평균 테스트의 원소 4개 함정)에도 그대로 나온다.\
  같은 교훈이 두 챕터에서 반복되는 셈이다.
- 테스트 데이터가 대칭적이면 비대칭 버그를 못 잡는다 — 값을 고를 때 **대칭성을 의도적으로 깨는 것**이 설계 요령이다.
- 인자로 받는 쪽은 유연한 대신 계약을 강제할 수 없다.\
  멱등도 결합법칙도 없는 람다를 넘겨도 컴파일된다 — 유연성의 값이 그것이다.

#### 11. Math.log 를 안 쓰는 진짜 이유 · 테스트가 못 잡는 코드

- Q: 흔히 말하는 부동소수점 오차가 아니라면 무엇인가.\
  A: **비용**이다.\
  `SparseTableStructureTest.mathLogIsNotWrongHereJustSlow` 가 `len = 1..200,000` 전부에서 `log[len] == (int)(Math.log(len) / Math.log(2))` 임을 assert 한다 — 이 JDK 에서 **한 번도 안 틀린다.**\
  명세가 보장하는 것이 1 ulp 이내라 다른 구현에서 틀릴 여지가 남아 있을 뿐, 여기서 관측된 오차는 0 이다.\
  안 쓰는 이유는 조회마다 `Math.log` 를 두 번 부르면 "조회 O(1)"이라는 말이 무색해지기 때문이다.\
  테스트 주석은 같은 기계에서 1천만 번을 재보면 비트 연산의 **16배** 차이가 났다고 적는다(주석 기준 — 그 16배는 assert 된 값이 아니라 기록된 실측 메모다).\
  대신 `log[i] = log[i >> 1] + 1` 로 표를 한 번 채워두면 조회는 배열 읽기 한 번이다.

```java
// impl/SparseTable.java — 시프트 한 번과 덧셈 한 번으로 표를 채운다
static int[] buildLogTable(int n) {
    int[] table = new int[n + 1];
    for (int i = 2; i <= n; i++) {
        table[i] = table[i >> 1] + 1;
    }
    return table;
}
```

> **ulp(unit in the last place)** — 부동소수점 수 하나와 그 다음 표현 가능한 수 사이의 간격. 오차의 단위로 쓴다.\
> 예: `Math.log` 는 결과가 참값에서 1 ulp 이내라고만 보장하므로, 구현에 따라 경계에서 층 번호가 하나 어긋날 여지가 남는다.

> **정직한 한계 기록** — "이론상 위험하다"와 "여기서 실제로 관측됐다"를 구분해 적는 태도.\
> 예: 이 테스트는 "오차로 틀린다"는 통념을 assert 로 반증하고, 실패하면 테스트를 고치지 말고 기록하라고 메시지에 써 둔다.

- Q: "테스트가 못 잡는 코드"가 여기서 또 나온다(`Arrays.fill` 패딩 · `log[to-from+1]` 대 `log[to-from]`).\
  A: 두 자리 모두 코드를 바꿔도 90개가 전부 통과한다.\
  ① `DisjointSparseTable.build` 의 `Arrays.fill(padded, identity)` 를 지워도(0 으로 남겨도) 전부 통과한다.\
  이유는 `query` 가 `requireIndex` 로 인덱스를 먼저 검사해 누적 구간이 `n` 을 절대 넘지 않고, **패딩 칸을 읽는 경로 자체가 없기** 때문이다(`paddingIsIdentity` 주석).\
  그래도 남기는 이유는 나중에 경계를 한 칸이라도 넓히면 그때 조용히 틀리기 때문이다.\
  ② 조회의 `log[to - from + 1]` 을 `log[to - from]` 으로 바꿔도 멱등 연산에서는 답이 같다(README 93~94줄 기준).\
  손으로 확인하면 이렇다: `len >= 2` 에서 `k' = floor(log2(len-1))` 이면 `2^k' <= len-1 < 2^(k'+1)` 이므로 `2^(k'+1) >= len` 이라 두 조각이 여전히 빈틈 없이 덮고, `2^k' <= len-1 < len` 이라 구간 밖으로도 안 나간다.\
  `len = 1` 이면 `log[0] = 0` 이라 `log[1] = 0` 과 같다.\
  즉 덮기 자체는 여전히 옳고, 겹침의 크기만 달라진다 — 멱등이면 겹침 크기가 답에 영향을 주지 않으므로 동치다.\
  README 는 이 변종을 잡는 것이 "합으로 만들면 얼마나 틀리는가" 둘뿐이라고 적는다(README 기준).

- Q: 11번 · 16번 · 18번 · 20번 · 21번에 이은 같은 계열에서 무엇이 반복되는가.\
  A: **"테스트가 못 잡는다"가 코드의 성질이 아니라 설계의 성질이라는 것**이 반복된다(11번 README 64줄의 문장).\
  각 챕터가 같은 모양의 자리를 하나씩 남겼다.\
  11번 — `h2` 가 0 인 경우는 이 설계에서 어떤 테스트로도 못 잡는다(README 58줄).\
  16번 — 뿌리를 검게 칠하는 표준 관례 줄을 지워도 전부 통과한다(README 83줄).\
  18번 — `1L << bit` 만 써도 우연히 맞고 98개가 전부 통과한다(README 56줄), 꼬리 비트 정리를 지워도 98개가 통과한다(62줄).\
  20번 — 도달할 수 없는 `common == 0` 가지를 넣어도 94개가 전부 통과한다(README 89줄).\
  21번 — Kasai 의 `h = 0` 되돌리기를 지워도 90개가 전부 통과한다(README 80줄).\
  22번 — 패딩 `Arrays.fill` 과 `log[to-from]` 변종, 둘 다 90개가 통과한다.\
  반복되는 교훈은 셋이다: ① **관측 경로가 없는 코드는 어떤 테스트로도 검증되지 않는다** — 테스트를 더 써도 안 된다.\
  ② 그럼에도 남기는 이유는 **경계를 나중에 넓힐 때를 위한 안전 여유**이지 지금의 정확성이 아니다.\
  ③ 그런 자리를 발견하면 지우거나 방치하지 말고 **못 잡는다는 사실을 명시적으로 기록한다** — 이 문제집이 README 의 "한계" 절과 테스트 주석 양쪽에 적어 두는 방식이 그것이다.

> **도달 불가 코드(unreachable branch)** — 어떤 입력으로도 실행되지 않는 분기. 커버리지 도구로도 "안 돈다"까지만 보이고 옳고 그름은 판정되지 않는다.\
> 예: 패딩 칸을 읽는 경로가 없으면 그 칸을 무엇으로 채우든 모든 테스트가 통과한다.

**더 생각할 것**

- 통념("`Math.log` 는 오차로 틀린다")을 assert 로 **반증한 뒤** 그래도 안 쓰는 이유를 따로 대는 것이 이 챕터의 방식이다.\
  근거가 바뀌면 결론이 아니라 근거를 고쳐 적는다.
- 변종을 실제로 만들어 돌려보고 "몇 개가 무너지는가"를 세는 것은 **테스트 스위트 자체를 검증하는** 방법이다(뮤테이션 테스팅).\
  README 의 41개·87개·12개·1개가 전부 그렇게 얻은 숫자다.
- 그 숫자들은 README 에만 있고 테스트 코드에 assert 되어 있지 않다.\
  코드가 바뀌면 조용히 낡을 수 있는 숫자이므로, 인용할 때 "README 기준"임을 붙이는 편이 안전하다.

#### 12. 다음 구조로의 연결 — LCA 이진 점프와 23번 스플레이 트리

- Q: "2의 거듭제곱 단위로 미리 접어두고 두 조각으로 덮는다"가 트리 위에서 어떻게 되풀이되는가.\
  A: 배열의 `table[k][i]` 가 트리에서는 `up[k][v]` 가 된다 — `v` 의 `2^k` 번째 조상이다(README 96~99줄).\
  점화식의 모양이 그대로다: `up[k][v] = up[k-1][ up[k-1][v] ]` 는 "절반을 두 번 올라가면 전체"라는 뜻이고, 희소 테이블의 `table[k][i] = combine(table[k-1][i], table[k-1][i+2^(k-1)])` 은 "절반 두 개를 이어 붙이면 전체"라는 뜻이다.\
  같은 배증(doubling)이 한쪽에서는 **구간을 잇는 데**, 다른 쪽에서는 **조상을 따라 올라가는 데** 쓰인다.\
  메모리도 같은 `n log n` 이고 전처리도 같은 `O(n log n)` 이다.\
  차이는 조각을 덮는 방식이다 — 희소 테이블은 겹쳐도 되는 두 조각이고, 이진 점프는 목표 깊이 차이를 이진법으로 분해해 **겹치지 않는 여러 점프**를 한다(그래서 O(1) 이 아니라 O(log n) 이다).\
  (이 비교의 뒷부분은 원본 repo 에 LCA 구현이 없어 코드로 확인하지 못했다 — `원본에 근거 없음 — 내 추론`.)

```
같은 배증, 다른 대상 (LCA 쪽은 개념 설명 - 원본에 코드가 없다)

  희소 테이블                           이진 점프(LCA)
  table[k][i] = [i, i+2^k-1] 의 답      up[k][v] = v 의 2^k 번째 조상

  table[k][i] = combine(               up[k][v] = up[k-1][ up[k-1][v] ]
      table[k-1][i],
      table[k-1][i + 2^(k-1)])

  조회: 겹쳐도 되는 두 조각             조회: 깊이 차 d 를 이진법으로 분해해
        -> combine 1회, O(1)                  켜진 비트마다 한 번씩 점프
                                              -> O(log n)

  두 구조 모두 "2의 거듭제곱 단위로 미리 접어둔다"는 한 문장에서 나온다.
```

> **이진 점프(binary lifting)** — 트리의 각 노드에 대해 2^k 번째 조상을 미리 표로 적어두고, 원하는 거리를 이진법으로 쪼개 점프하는 기법.\
> 예: 13칸 위로 올라가려면 13 = 8 + 4 + 1 이므로 `up[3]`, `up[2]`, `up[0]` 을 차례로 타면 세 번에 도착한다.

> **LCA(최소 공통 조상, lowest common ancestor)** — 트리에서 두 노드를 모두 조상으로 갖는 가장 깊은 노드.\
> 예: 파일 시스템에서 두 경로의 가장 깊은 공통 디렉터리가 그것이다.

- Q: 23번 스플레이 트리는 반대로 **갱신할 때마다 구조를 바꾸는** 쪽인데, 그 대비는 무엇인가.\
  A: 22번은 **구조를 얼려서** 조회를 싸게 만들고, 23번은 **조회할 때마다 구조를 바꿔서** 다음 조회를 싸게 만든다.\
  23번 README 6줄이 "균형을 아예 목표로 삼지 않는다. 대신 접근한 노드를 뿌리로 끌어올린다(splay). 그것뿐이다"라고 적는다.\
  같은 README 의 비교표는 "조회가 쓰기인가"라는 행을 따로 두고 레드블랙은 "아니다", 스플레이는 "**그렇다**"로 적는다 — 22번은 그 축의 정반대 끝이다(조회가 표를 한 글자도 건드리지 않는다).\
  비용 모델도 대비된다: 22번은 한 번의 조회가 **언제나 combine 1회**라는 최악 보장을 주고, 23번은 한 연산이 O(n) 일 수 있지만 m 연산 전체가 **O(m log n) 상환**이라는 총합 보장을 준다.\
  그리고 23번은 "최근에 쓴 것이 얕은 곳에 있다"는 성질을 공짜로 얻는데(같은 README), 22번은 질의 분포에 전혀 적응하지 못한다 — 백만 번 물어본 구간도 처음 물어본 구간과 정확히 같은 비용이다.\
  **정적 최적화(미리 다 계산)와 동적 적응(쓰면서 재배치)이라는 두 방향**이고, 워크로드가 고정인지 편향되는지가 갈림이다.

> **정적(static) 구조** — 만든 뒤 값이 바뀌지 않는다는 전제 위에 세운 구조. 바뀌면 처음부터 다시 짓는다.\
> 예: 희소 테이블은 한 칸만 바뀌어도 n=16 기준 combine 38회를 다시 치러야 한다.

> **자기 조정(self-adjusting) 구조** — 접근 패턴에 따라 스스로 모양을 바꾸는 구조.\
> 예: 스플레이 트리는 조회한 노드를 뿌리로 올려, 자주 쓰는 키가 저절로 얕아지게 한다.

**더 생각할 것**

- 22번 → LCA 는 **같은 기법의 다른 적용**이고, 22번 → 23번은 **반대 방향의 설계**다.\
  "다음 챕터"가 늘 발전인 것은 아니고, 이번처럼 대척점일 때도 있다.
- 두 방향을 섞는 자리도 있다 — LCA 를 오일러 투어로 펴면 "구간 최솟값" 문제가 되어 **희소 테이블이 그대로 쓰인다.**\
  트리 문제를 배열 문제로 바꾸는 이 변환이 22번이 23번 이후까지 살아남는 이유다.\
  (오일러 투어 + RMQ 변환은 원본 repo 에 코드가 없다 — `원본에 근거 없음 — 내 추론`.)
- 워크로드가 편향되어 있으면(같은 구간을 반복해서 묻는다면) 캐시 한 겹이 희소 테이블보다 싸다.\
  자료구조를 고르기 전에 질의 분포를 재는 것이 언제나 먼저다.
