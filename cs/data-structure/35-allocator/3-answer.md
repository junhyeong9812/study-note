### B. 자료구조 특성

#### 1. 메모리 할당자가 왜 필요한가 — `new` 가 실제로 하는 일

- Q: 01번부터 34번까지 쓴 `new` 가 실제로 무슨 일을 하는가?\
  A: **고정된 공간에서 연속된 자리를 떼어주고, 그 시작 주소를 돌려주는 일**이다.\
  `new int[16]` 은 "16칸이 연속으로 들어갈 자리를 찾아서 그 시작 위치를 달라"는 요청이고, 할당자가 그 요청을 받는다.\
  이 박스의 `Allocator` 인터페이스가 정확히 그 계약이다.

```java
// src/main/.../Allocator.java
/** 자리가 없을 때 주는 값. 음수라 주소와 섞이지 않는다. */
int FAIL = -1;

int allocate(int size);   // size 바이트를 떼어주고 시작 주소를 준다. 없으면 FAIL
void free(int address);   // 이 주소에서 시작하는 자리를 돌려받는다
```

- Q: 자리가 없을 때 왜 예외가 아니라 `FAIL` 인가?\
  A: **자리가 없는 것은 오류가 아니라 정상적인 결과**이기 때문이다.\
  요청이 잘못된 것이 아니라 공간이 모자란 것이다. `malloc` 이 `null` 을 주는 것과 같다.\
  반대로 **준 적 없는 주소를 `free` 하는 것은 오류**라서 던진다 — 그건 호출자의 버그다.\
  "정상적인 실패"와 "계약 위반"을 구별해 반환 방식을 다르게 한 것이 이 인터페이스의 설계다.

- Q: 앞의 자료구조들은 "무엇을 담을까"에 답했는데, 이 문제는 왜 그 어느 것으로도 대신할 수 없는가?\
  A: 앞의 구조들은 전부 **"담을 공간은 이미 있다"를 전제**하고, 그 위에서 무엇을 어떻게 배치할지를 풀었다.\
  01번 동적 배열은 `capacity` 를 두 배로 늘리며 새 배열을 받아왔다 — 그 배열이 **어디서 왔는지**는 안 물었다.\
  02번 연결 리스트는 노드를 하나씩 `new` 했다 — 그 노드가 **어디 놓였는지**는 안 물었다.\
  05번 해시맵은 버킷 배열을 잡았고, 09번 트라이는 자식 맵을 잡았다.\
  전부 할당자를 **쓰는 쪽**이었지 할당자 자체가 아니었다.\
  그리고 이 문제의 답은 다른 자료구조로 못 만든다 — **공간 자체가 자원**이라서, 관리 구조를 두는 것도 그 공간을 쓰는 일이기 때문이다.

```text
층으로 그리면

  01 동적 배열   "16칸짜리 배열 주세요"  ---+
  02 연결 리스트 "노드 하나 주세요"      ---+
  05 해시맵      "버킷 32개 주세요"      ---+---> 35 할당자
  09 트라이      "자식 맵 주세요"        ---+       고정된 공간 1024 바이트에서
  ...                                             어디를 떼어줄지 고른다
                                                  돌려받으면 다시 쓸 수 있게 정리한다

  앞의 구조들은 "무엇을 담을까" 를 풀었다 = 논리적 배치
  35 는 "어디에 놓을까" 를 푼다        = 물리적 배치

  35 의 README 마지막 문장이 그 연결을 못 박는다:
    01번 동적 배열이 capacity 를 두 배로 늘릴 때 그 새 배열을 어디서 받아왔는지가 이 박스다
```

- Q: 문제 자체가 어려운 이유는 무엇인가?\
  A: **코드는 짧은데 선택의 결과가 한참 뒤에 나타나기** 때문이다.\
  자리를 떼어주는 코드는 세 줄이면 된다(`BumpAllocator` 가 그 증거다).\
  어려운 것은 **어디를 떼어줄지**이고, 그 선택이 "지금"은 아무 차이를 안 만든다.\
  차이는 수백 번의 할당과 해제 뒤에 **"빈 공간은 많은데 할당이 실패한다"** 로 나타난다.\
  그래서 이 박스는 구현이 아니라 **재는 것**이 본론이다.

```text
남은 공간이 512인데 17을 못 준다

  16바이트 64개로 1024를 꽉 채운다             usedBytes = 1024, freeBytes = 0
  짝수 번째만 돌려준다 (32개)                   freeBytes = 512

    [사용][빈 ][사용][빈 ][사용][빈 ] ...   16바이트씩 번갈아
      16   16   16   16   16   16

  freeBytes         512   <- "절반이 비어 있다. 여유롭다"
  largestFreeBlock   16   <- 연속된 것은 16 뿐이다
  freeBlockCount     32   <- 32 조각으로 부서졌다

  allocate(17) -> FAIL

  freeBytes 만 보면 안 보인다. largestFreeBlock 을 같이 봐야 드러난다.
  FragmentationTest.alternatingFreeMakesTheSpaceUseless 가 네 값을 전부 assert 한다.
```

> **할당자(allocator)** — 고정된 공간에서 요청받은 크기의 연속된 자리를 떼어주고 돌려받는 것.\
> 예: `allocate(64)` 가 주소 0 을 주면 `[0, 64)` 가 그 요청의 자리다.

> **외부 단편화(external fragmentation)** — 남은 총량은 충분한데 연속된 자리가 없어 요청이 실패하는 상태.\
> 예: 16바이트 빈 자리 32개(총 512)가 있어도 `allocate(17)` 은 실패한다.

> **내부 단편화(internal fragmentation)** — 요청보다 더 떼어줘서 그 안에 갇히는 낭비.\
> 예: 버디에서 33을 달라면 64를 준다. 31바이트가 쓰이지도 돌려주지도 못한 채 갇힌다.

**더 생각할 것**

- 자료구조를 배우는 흐름에서 이 박스가 마지막인 것은 자연스럽다.\
  **앞에서 쓴 모든 `new` 의 아래층**을 들여다보는 일이기 때문이다.
- 실제 JVM 에서는 이 일이 더 복잡하다. (원본에 근거 없음 — 내 추론)\
  GC 가 살아 있는 객체를 옮겨 붙여(compaction) 외부 단편화를 아예 없애기도 하는데, 그건 "주소가 바뀌어도 된다"는 전제가 있어야 가능하다.\
  이 박스의 할당자는 주소를 돌려준 뒤 못 바꾼다 — 그래서 단편화를 피할 수 없고, 그 사실이 문제의 핵심이 된다.
- `wastedBytes` 라는 자를 인터페이스에 넣어둔 것이 중요하다.\
  다섯 구현 중 넷은 이 값이 항상 0 이다. **한 구현만을 위한 자를 계약에 두는 것**이 이상해 보이지만, 그게 없으면 버디의 대가가 어떤 숫자에도 안 잡힌다.

#### 2. 어떤 요청 패턴에 어떤 할당자가 적합한가

- Q: 수명이 다 같은 요청에 왜 bump 가 나쁜 설계가 아닌가?\
  A: **관리할 것이 없기 때문**이다.\
  전부 같이 살고 같이 죽으면, "어느 자리가 비었나"를 추적할 이유가 없다. 끝나면 통째로 버리면 된다.\
  그래서 `BumpAllocator` 는 빈 자리 목록도, 합치기도, 고르는 규칙도 없다.

```java
// impl/BumpAllocator.java — allocate 가 사실상 세 줄이다
if (next + size > capacity) {
    return FAIL;
}
int address = next;
next += size;
handedOut += size;
return address;
```

```text
bump 의 상태는 포인터 하나다

    0                                    next                   capacity
    +--------------------------------------+---------------------+
    |            이미 떼어준 구간           |       남은 구간      |
    +--------------------------------------+---------------------+
                                            ^ 늘 여기서 떼어준다

  남은 것은 늘 뒤쪽 한 덩어리다  ->  freeBlockCount = 1, 단편화가 0 이다
  free 는 아무것도 안 한다       ->  100번 떼어주고 99번 돌려받아도 freeBytes 그대로
  회수하는 유일한 방법 = reset() ->  통째로 버리고 처음으로
```

- Q: 실제로 어디에 쓰는가?\
  A: README 와 코드 주석이 셋을 든다 — **요청 단위 아레나**(HTTP 요청 처리 중에만 쓰고 응답하면 버린다), **컴파일러의 패스별 메모리**(한 패스가 끝나면 그 패스의 임시 자료를 통째로 버린다), **게임의 프레임 메모리**(한 프레임 동안만 쓴다).\
  셋 다 "수명이 다 같다"가 성립하는 자리다.\
  **관리 비용은 수명이 제각각일 때 생긴다** — `BumpAllocator` 주석의 문장 그대로다.

- Q: `free` 가 왜 던지지 않고 그냥 세기만 하는가?\
  A: 던지면 **이 할당자를 다른 것과 바꿔 끼울 수 없기** 때문이다.\
  계약은 지키되 회수를 안 하는 것이 이 설계의 정직한 표현이다.\
  그 대신 `ignoredFrees()` 로 몇 번 불렸는지 세어, **얼마나 낭비하고 있는지 볼 수 있게** 한다.\
  "안 한다"를 조용히 안 하는 게 아니라 **세어서 드러내는** 것이 이 박스의 태도다.

```java
// impl/BumpAllocator.java
@Override
public void free(int address) {
    if (address < 0 || address >= next) {
        throw new IllegalArgumentException("떼어준 적 없는 주소다: " + address);
    }
    freeCalls++;
}
```

- Q: 요청 크기가 2의 거듭제곱 근처일 때는 버디와 빈 자리 목록 중 어느 쪽이 유리한가?\
  A: **버디**다.\
  버디의 유일한 대가는 올림에서 오는 내부 단편화인데, 요청이 이미 2의 거듭제곱이면 **올림이 안 일어난다**.\
  대가가 0 이 되고, 대신 `O(1)` 합치기와 적은 외부 단편화를 그대로 얻는다.

```java
// src/test/.../BuddyAllocatorTest.java — exactPowersWasteNothing
BuddyAllocator a = new BuddyAllocator(1024);
for (int size : List.of(256, 128, 64, 32)) {
    a.allocate(size);
}
assertEquals(0, a.wastedBytes());
assertEquals(256 + 128 + 64 + 32, a.usedBytes());
```

- Q: 요청 크기가 제각각일 때는?\
  A: **빈 자리 목록**이 유리하다. 요청한 만큼만 떼어주므로 내부 단편화가 0 이다(`wastedBytes()` 가 늘 0 을 돌려준다).\
  버디는 크기를 올림하므로 제각각인 요청에서 올림 낭비가 계속 쌓인다.\
  최악은 **2의 거듭제곱 바로 위** 크기다 — 65를 달라면 128을 주고 63이 갇힌다.

```java
// src/test/.../BuddyAllocatorTest.java — roundingIsTheCost
a.allocate(33);
assertEquals(64, a.usedBytes(), "33 을 달라면 64 를 준다");
assertEquals(31, a.wastedBytes());

a.allocate(65);
assertEquals(64 + 128, a.usedBytes());
assertEquals(31 + 63, a.wastedBytes());
```

```text
요청 크기별 버디의 낭비 (FragmentationTest.justOverAPowerOfTwoIsTheWorst 가 찍는다)

  요청    떼어줌   낭비      2의 거듭제곱 바로 위가 제일 나쁘다
   16       16      0        딱 맞으면 0
   17       32     15        하나 더 달랬더니 15가 갇힌다
   32       32      0
   33       64     31
   64       64      0
   65      128     63        assertEquals(128, ...) / assertEquals(63, ...)

  낭비의 상한은 "요청한 크기 미만" 이다. 즉 최악에 거의 절반을 버린다.
```

- Q: 정리하면 어떤 요청 패턴에 무엇을 쓰는가?\
  A: 표로 적으면 이렇다.

| 요청 패턴 | 맞는 할당자 | 이유 |
|---|---|---|
| 수명이 전부 같다 | `BumpAllocator` | 회수할 일이 없으니 관리 구조 자체가 불필요 |
| 크기가 2의 거듭제곱 근처 | `BuddyAllocator` | 올림 낭비가 0 에 가깝고 합치기가 `O(1)` |
| 크기가 제각각 | 빈 자리 목록(first fit) | 요청한 만큼만 떼어줘 내부 단편화 0 |
| 크기가 다 같다 | 어느 쪽이든 | 같은 크기만 오가면 단편화가 안 생긴다 (README·테스트에 없는 항목 — 내 추론) |

- Q: 언제 쓰면 안 되는가?\
  A: bump — 수명이 제각각인데 쓰면 안 된다. 한 번 잡은 것을 절대 못 돌려받아 금방 꽉 찬다.\
  버디 — 요청이 2의 거듭제곱에서 멀 때 쓰면 안 된다. 절반 가까이를 버린다.\
  빈 자리 목록 — 요청 수가 아주 많고 빈 자리가 잘게 부서지는 워크로드에서는 **고르기 자체가 비싸진다**(`scanned` 가 그 비용이다).

> **아레나(arena) 할당** — 한 덩어리를 잡아놓고 그 안에서 밀어올리며 쓰다가, 끝나면 통째로 버리는 방식.\
> 예: HTTP 요청 하나를 처리하는 동안만 쓰는 임시 객체들을 한 아레나에 담고 응답 뒤 `reset()` 한다.

> **수명(lifetime)** — 그 자리가 언제 잡히고 언제 풀리는가. 할당자 선택을 정하는 가장 큰 요인이다.\
> 예: 수명이 다 같으면 회수 관리가 필요 없고, 제각각이면 빈 자리 목록과 합치기가 필요해진다.

**더 생각할 것**

- "이 설계는 아무것도 회수하지 않는다"가 **약점이 아니라 선택**일 수 있다는 것이 이 박스에서 가장 실용적인 교훈이다.\
  워크로드가 그 선택의 전제를 만족하면 가장 단순한 것이 가장 빠르다.
- 그래서 할당자를 고르기 전에 물어야 할 것은 "어느 알고리즘이 좋은가"가 아니라 **"우리 요청의 수명과 크기 분포가 어떤가"** 다.\
  33번에서 "워크로드를 먼저 재고 자료구조를 고른다"고 했던 것과 같다.
- 실무에서는 여러 개를 겹쳐 쓴다. (원본에 근거 없음 — 내 추론)\
  작은 고정 크기 요청은 슬랩/풀로, 큰 요청은 빈 자리 목록으로, 요청 단위 임시 메모리는 아레나로 — 하나로 다 하려 하지 않는다.

#### 3. 핵심 연산의 비용이 왜 그런가 — 고르기와 합치기

- Q: first fit 이 만나면 멈추고 best/worst fit 이 전부 훑어야 하는 구조적 이유는?\
  A: **"조건을 만족하는 것"과 "조건을 만족하는 것 중 최적"의 차이**다.\
  first fit 이 찾는 것은 `size 이상인 자리 하나`다. 그런 자리를 만나는 순간 조건이 끝난다 — 뒤를 볼 이유가 없다.\
  best/worst fit 이 찾는 것은 `size 이상인 자리들 중 최소(최대)`다. **최소인지 알려면 나머지를 다 봐야 한다** — 뒤에 더 작은 것이 있을지 모르니까.\
  탐색 문제의 성질이지 구현 요령이 아니다.

```java
// impl/FirstFitAllocator.java — 만나면 멈춘다
for (int i = 0; i < blocks.size(); i++) {
    countScan(1);
    if (blocks.get(i).size >= size) {
        return i;                    // 여기서 끝
    }
}
return -1;
```

```java
// impl/BestFitAllocator.java — 끝까지 본다
int best = -1;
for (int i = 0; i < blocks.size(); i++) {
    countScan(1);
    int blockSize = blocks.get(i).size;
    if (blockSize < size) {
        continue;
    }
    if (best < 0 || blockSize < blocks.get(best).size) {
        best = i;                    // 갱신만 하고 계속 돈다
    }
}
return best;
```

- Q: `scanned` 가 그것을 어떻게 드러내는가?\
  A: **빈 자리 하나를 들여다볼 때마다 1 씩 센다**(`countScan(1)`).\
  그래서 first fit 은 "몇 번째에서 만났나", best/worst 는 "목록 길이"가 그대로 값이 된다.

```java
// src/test/.../FragmentationTest.java — firstFitScansLeast
// 덩어리가 하나뿐일 때
assertEquals(32, first.scanned(), "맞는 것을 만나면 멈춘다");
assertEquals(32, best.scanned(), "여기서는 덩어리가 하나뿐이라 같다");

// 덩어리 16개일 때 한 번 더 할당하면
assertEquals(1, f2.scanned() - fBefore, "첫 덩어리에서 멈춘다");
assertEquals(17, b2.scanned() - bBefore, "전부 봐야 제일 작은 것을 안다");
```

```text
덩어리 16개 상태에서 allocate(16) 한 번

  first fit   [빈16][빈16][빈16] ...
               ^ 첫 칸이 이미 16 이상이다 -> 즉시 반환      scanned += 1

  best fit    [빈16][빈16][빈16] ... [빈16][맨끝 큰 덩어리]
               전부 보고 나서야 "제일 작은 것" 을 안다       scanned += 17

  1 대 17 이다. 목록이 길어질수록 격차가 벌어진다.
  그리고 "목록이 길어진다" 는 곧 단편화가 진행됐다는 뜻이라, 나쁠 때 더 나빠진다.
```

- Q: 버디의 합치기가 `O(1)` 인 이유는 무엇에 기대고 있는가?\
  A: **짝의 주소를 계산으로 구할 수 있다**는 것에 기댄다.\
  빈 자리 목록은 인접한 자리를 찾으려고 목록을 훑어야 했는데, 버디는 비트 하나를 뒤집으면 끝난다.

```java
// impl/BuddyAllocator.java
while (level < levels) {
    int buddy = address ^ (1 << level);
    if (!freeByLevel.get(level).remove(buddy)) {
        break;      // 짝이 안 비었다. 여기서 멈춘다
    }
    merges++;
    address = Math.min(address, buddy);      // 합친 자리의 시작은 둘 중 앞쪽이다
    level++;
}
```

```text
왜 주소 XOR 크기가 짝인가

  1024 를 반으로 쪼개면 [0, 512) 와 [512, 1024)
  512 를 반으로 쪼개면  [0, 256) 와 [256, 512)

  크기가 2^k 이고 주소가 그 배수이면, 짝은 k 번째 비트만 다르다

    크기 256 = 2^8            주소를 2진수로
      [0,   256)  ->  0000 0000 0000    8번 비트 = 0
      [256, 512)  ->  0001 0000 0000    8번 비트 = 1     <- 서로의 짝
      [512, 768)  ->  0010 0000 0000    8번 비트 = 0
      [768, 1024) ->  0011 0000 0000    8번 비트 = 1     <- 서로의 짝

    0   XOR 256 = 256    맞다
    256 XOR 256 = 0      맞다
    512 XOR 256 = 768    맞다
    768 XOR 256 = 512    맞다

  18번 비트셋의 "위치 계산을 산술로 바꾸기" 가 여기서 자료구조의 성질이 된다.
  목록을 뒤지는 O(n) 이 XOR 한 번의 O(1) 이 됐다.
```

- Q: 그 전제가 깨지면 — 쪼갤 때 앞쪽 반을 내놓으면 — 무엇이 언제 무너지는가?\
  A: 전제는 **"쪼갠 자리의 시작 주소가 그 크기의 배수"** 라는 정렬(alignment)이다.\
  현재 코드는 **뒤쪽 반을 빈 자리로 내놓고 앞쪽 반을 계속 쪼갠다** — 그래서 할당된 주소가 늘 큰 블록의 시작이고, 정렬이 유지된다.

```java
// impl/BuddyAllocator.java
int address = freeByLevel.get(found).pollFirst();
while (found > level) {
    found--;
    splits++;
    // 뒤쪽 반을 빈 자리로 내놓고 앞쪽 반을 계속 쪼갠다.
    freeByLevel.get(found).add(address + (1 << found));
}
```

```text
앞쪽 반을 내놓고 뒤쪽을 계속 쪼개면 (전제가 깨지는 경우)

  현재 방식 (뒤쪽을 내놓는다)
    1024 에서 시작, address = 0
      512 로 쪼갬 -> 빈 자리 [512], address 는 계속 0
      256 로 쪼갬 -> 빈 자리 [256], address 는 계속 0
      128 로 쪼갬 -> 빈 자리 [128], address 는 계속 0
    최종 address = 0.  0 은 128 의 배수다.  0 XOR 128 = 128 -> 짝이 맞다

  깨진 방식 (앞쪽을 내놓고 뒤쪽을 쓴다고 하면)
    1024 에서 address = 0 + 512 = 512
      -> 512 는 512 의 배수다. 아직 괜찮다
    다음 단계에서 address = 512 + 256 = 768
      -> 768 은 256 의 배수다. 여기까지도 우연히 맞는다

  실제로 무너지는 것은 "쪼갠 반쪽의 크기가 2의 거듭제곱이 아니게 되거나,
  주소가 그 크기의 배수가 아니게 되는" 순간이다.
  예를 들어 3등분하거나, 헤더 몇 바이트를 앞에 붙여 주소를 밀면 즉시 깨진다.

  깨졌을 때의 증상 : free 에서 address XOR size 가 "짝이 아닌 남의 자리" 를 가리킨다
                      그 자리가 우연히 비어 있으면 합치면 안 될 것을 합친다
                      -> 두 자리가 겹치게 되고, 그 손상은 한참 뒤에 드러난다
                      예외는 안 난다. 계약 테스트도 한동안 통과한다
```

- Q: 버디가 "인접한데 못 합치는" 자리가 있다는 것은 무슨 뜻인가?\
  A: **주소가 붙어 있어도 짝이 아니면 안 합친다**. 그것이 `O(1)` 합치기의 값이다.

```java
// src/test/.../BuddyAllocatorTest.java — adjacentIsNotEnough
int b0 = a.allocate(256);   // 0
int b1 = a.allocate(256);   // 256
int b2 = a.allocate(256);   // 512
int b3 = a.allocate(256);   // 768
a.free(b1);
a.free(b2);

assertEquals(512, a.freeBytes());
assertEquals(256, a.largestFreeBlock(), "붙어 있는데 512 를 못 만든다");
assertEquals(0, a.merges());
assertEquals(Allocator.FAIL, a.allocate(300), "빈 공간 512 인데 300 이 실패한다");
```

```text
[256,512) 와 [512,768) 은 붙어 있는데 왜 못 합치나

    0        256       512       768      1024
    +---------+---------+---------+---------+
    |  b0 사용 |  비었음  |  비었음  |  b3 사용 |
    +---------+---------+---------+---------+
                   \_______  _______/
                           붙어 있다. 합치면 512 짜리다

  그런데 256 의 짝은 256 XOR 256 = 0     -> b0 이고, 쓰는 중이다
         512 의 짝은 512 XOR 256 = 768   -> b3 이고, 쓰는 중이다

  둘 다 짝이 안 비었으므로 합치지 않는다. merges = 0

  같은 상황에서 first fit 은 성공한다 (aFreeListWouldSucceedThere)
    assertEquals(512, a.largestFreeBlock(), "주소가 붙어 있으면 합친다")
    assertNotEquals(Allocator.FAIL, a.allocate(300))

  대가는 합치기가 O(1) 이 아니라는 것이다. 목록에서 옆자리를 찾아야 한다.
```

- Q: 빈 자리 목록의 합치기는 어떻게 하는가? 왜 양옆을 다 봐야 하는가?\
  A: 주소 순서에 맞는 자리에 꽂고, **오른쪽 먼저 합치고 그다음 왼쪽**을 합친다.\
  한쪽만 보면 반쪽만 합쳐져서 천천히 부서진다.

```java
// impl/FreeListAllocator.java
free.add(i, block);

// 오른쪽을 먼저 합친다. 왼쪽부터 해도 되기는 하는데, 왼쪽을 지우면 i 가 한 칸 밀리므로
// 그것을 보정해야 한다. 보정을 빼먹으면 오른쪽 이웃을 엉뚱한 자리에서 찾아 못 합친다.
// 오른쪽부터 하면 i 가 안 밀려서 보정할 것이 없다. 순서가 취향이 아니라 이 이유다.
if (i + 1 < free.size() && free.get(i).end() == free.get(i + 1).start) {
    free.get(i).size += free.get(i + 1).size;
    free.remove(i + 1);
}
if (i > 0 && free.get(i - 1).end() == free.get(i).start) {
    free.get(i - 1).size += free.get(i).size;
    free.remove(i);
}
```

```text
합치기를 따라가면 : [0,16) 사용중, [16,32) 빈 자리, [32,48) 사용중 인 상태에서
                     [0,16) 을 돌려준다

  1. 주소 순서 자리 찾기 : free 목록에서 start < 0 인 것이 없으므로 i = 0
  2. free.add(0, [0,16))  ->  free = [ [0,16), [16,32) ]
  3. 오른쪽 검사 : free[0].end() = 16 == free[1].start = 16  ->  합친다
                    free = [ [0,32) ]
  4. 왼쪽 검사   : i > 0 이 아니므로 건너뜀

  결과 : 32짜리 한 덩어리. freeBlockCount = 1

  오른쪽만 봤다면? 앞에서 돌려받은 자리와 안 합쳐진다
  왼쪽만 봤다면?   그 반대다
  어느 쪽이든 반쪽만 합쳐져서 목록이 천천히 길어진다. 예외는 안 난다
```

> **합치기(coalescing)** — 돌려받은 자리를 옆의 빈 자리와 붙여 더 큰 덩어리로 만드는 것.\
> 예: 합치기가 있으면 16짜리 64개를 순서대로 돌려줬을 때 덩어리가 1개가 되고, 없으면 64개가 된다.

> **짝(buddy)** — 같은 크기의 블록을 둘로 쪼갰을 때 서로의 반쪽. `주소 XOR 크기` 로 구한다.\
> 예: 크기 256 에서 주소 256 의 짝은 `256 XOR 256 = 0` 이다.

> **정렬(alignment)** — 주소가 어떤 수의 배수라는 성질. 버디의 짝 계산이 여기에 통째로 기대고 있다.\
> 예: 크기 128 짜리 블록의 시작 주소는 늘 128 의 배수라서, 7번 비트 하나만 뒤집으면 짝이 나온다.

**더 생각할 것**

- 버디의 `O(1)` 합치기는 **공짜가 아니라 제약을 지불하고 산 것**이다.\
  "크기는 2의 거듭제곱만, 주소는 그 배수만" 이라는 제약을 받아들였기 때문에 XOR 한 줄이 성립한다.\
  제약을 풀면(임의 크기) 계산이 안 되고 목록을 훑어야 한다.
- 이 교환은 자료구조 전반에서 반복된다.\
  18번 비트셋이 "원소가 정수 범위"라는 제약으로 비트 연산을 샀고, 17번 펜윅 트리가 인덱스 비트 조작으로 부분합을 샀다.\
  **구조에 제약을 걸면 계산이 산술로 내려간다.**
- `scanned` 를 protected 메서드(`countScan`)로 부모에 두고 하위가 부르게 한 설계도 눈여겨볼 만하다.\
  세 전략이 각자 세면 빠뜨리거나 다르게 셀 수 있는데, 자를 부모가 소유하면 **셋의 수가 같은 단위로 비교 가능**해진다.

#### 4. 최악의 사용 패턴 — 한 칸 걸러 비우기, 그리고 33바이트

- Q: 16바이트 64개로 1024를 채우고 한 칸 걸러 돌려주면 세 값이 얼마가 되는가?\
  A: `freeBytes` 512, `largestFreeBlock` 16, `freeBlockCount` 32 다. 전부 assert 돼 있다.

```java
// src/test/.../FragmentationTest.java — alternatingFreeMakesTheSpaceUseless
assertEquals(512, a.freeBytes(), "절반이 남았다");
assertEquals(16, a.largestFreeBlock(), "그런데 연속된 것은 16 뿐이다");
assertEquals(32, a.freeBlockCount(), "32 조각으로 부서졌다");
assertEquals(Allocator.FAIL, a.allocate(17), "512 가 남았는데 17 을 못 준다");
```

- Q: 왜 `allocate(17)` 이 실패하는가?\
  A: **연속된 17바이트가 어디에도 없기** 때문이다.\
  빈 자리가 전부 16바이트짜리이고, 그 사이사이가 사용 중이라 합쳐질 수가 없다.\
  `largestFreeBlock` 이 곧 **실제로 떼어줄 수 있는 최대치**이고, 그게 16 이다.\
  `freeBytes` 512 는 여기서 아무 의미가 없는 숫자다 — **자 하나만 보면 안 되는** 이유가 이 한 줄이다.

```text
왜 합쳐지지 않나

  짝수 번째만 돌려줬다
    [빈16][사용][빈16][사용][빈16][사용] ...
      ^         ^         ^
      돌려받은 자리마다 양옆이 전부 사용 중이다

  insertAndCoalesce 가 양옆을 보지만
    free.get(i).end() == free.get(i+1).start  가 성립하지 않는다 (사이에 사용 중인 16이 있다)
    free.get(i-1).end() == free.get(i).start  도 마찬가지다

  합치기 코드는 멀쩡히 돌았다. 합칠 것이 없었을 뿐이다.
  이 최악은 구현 결함이 아니라 요청 패턴이 만든 것이다.
```

- Q: 버디도 같은 패턴에서 같은 일을 당하는가?\
  A: 그렇다. 똑같이 512 / 16 / 32 다.

```java
// src/test/.../FragmentationTest.java — buddyIsNotImmune
assertEquals(512, buddy.freeBytes());
assertEquals(16, buddy.largestFreeBlock(), "짝이 안 비어서 여기서도 16 이다");
assertEquals(32, buddy.freeBlockCount(), "빈 자리 목록과 똑같이 32 조각이다");
assertEquals(Allocator.FAIL, buddy.allocate(17));
```

  요청이 **이미 2의 거듭제곱(16)** 이라 올림이 안 일어나고, 그러면 버디의 이점이 통째로 사라진다.\
  테스트 주석이 그것을 못 박는다 — **이길 조건을 안 갖춘 채로 "이 구조가 낫다"고 말하면 안 된다.**

- Q: 버디에서 33바이트를 반복해 떼어가면 몇 번 만에 꽉 차고 몇 바이트가 갇히는가?\
  A: **16번**에 꽉 차고 **496바이트**가 갇힌다. 같은 요청을 first fit 은 **31번** 받는다.

```java
// src/test/.../FragmentationTest.java — nearlyHalfCanBeLost
assertEquals(16, count, "64 씩 떼어주므로 16 번이면 꽉 찬다");
assertEquals(1024, a.usedBytes());
assertEquals(0, a.freeBytes(), "남은 공간이 0 이다");
assertEquals(496, a.wastedBytes(), "그런데 496 은 아무도 안 쓴다");
...
assertEquals(31, listCount);
```

```text
손계산

  버디
    33 -> 올림하면 64.  1024 / 64 = 16 번
    실제로 쓰는 것   16 x 33 = 528
    갇힌 것          16 x 31 = 496
    usedBytes = 1024 (떼어준 크기의 합), freeBytes = 0, wastedBytes = 496
    496 / 1024 = 48.4 %  —  거의 절반이 갇혔다

  first fit
    33 을 그대로 떼어준다.  1024 / 33 = 31.03 -> 31 번
    31 x 33 = 1023.  남는 1 바이트는 아무 요청도 못 받지만 freeBytes 에는 잡힌다

  16 대 31.  같은 공간에서 버디가 절반도 못 받는다
  assertTrue(listCount > count * 1.9) 가 그 배율까지 못 박는다
```

- Q: 갇힌 바이트가 왜 `freeBytes` 에도 `largestFreeBlock` 에도 안 잡히는가?\
  A: **떼어준 것으로 세기 때문**이다.\
  `usedBytes()` 는 요청한 크기가 아니라 **실제로 떼어준 크기의 합**이다. 그래서 496 은 "쓰는 중"으로 분류된다.\
  `freeBytes()` 는 `capacity - usedBytes()` 이므로 0 이 된다.\
  `largestFreeBlock()` 은 빈 자리 목록만 보므로 역시 0 이다.\
  즉 **"꽉 찼다"로 보인다.** 그런데 실제로 프로그램이 쓰는 것은 528 뿐이다.

```java
// impl/BuddyAllocator.java
/** 실제로 떼어준 크기의 합이다. 요청한 크기가 아니다. */
public int usedBytes() {
    int total = 0;
    for (int[] record : allocated.values()) {
        total += record[0];          // record = [떼어준 크기, 요청한 크기]
    }
    return total;
}

/** 떼어준 것과 요청한 것의 차이. 이 할당자만 0 이 아니다. */
public int wastedBytes() {
    int total = 0;
    for (int[] record : allocated.values()) {
        total += record[0] - record[1];
    }
    return total;
}
```

```text
어떤 자에도 안 잡힌다는 말의 정확한 뜻

  freeBytes        0     "남은 게 없다" 고 보고한다
  largestFreeBlock 0     "떼어줄 수 있는 게 없다"
  usedBytes     1024     "전부 쓰고 있다"
  wastedBytes    496     <- 이 자가 없으면 496 은 어디에도 안 나타난다

  allocated 맵에 [떼어준 크기, 요청한 크기] 를 쌍으로 담아두지 않았다면
  이 값을 계산할 방법 자체가 없다.
  "재려면 먼저 기록해야 한다" 는 것이 이 구현의 결정이다.
```

- Q: 최선의 패턴은 어떤 것인가?\
  A: 셋이다.\
  하나 — **수명이 다 같은 요청**. 전부 잡았다가 통째로 버리면 단편화가 아예 안 생긴다(bump 가 이긴다).\
  둘 — **크기가 다 같은 요청**. 돌려받은 자리가 다음 요청에 정확히 맞으므로 재사용률이 100% 다.\
  셋 — **LIFO 로 돌려주는 요청**(나중에 잡은 것을 먼저 돌려준다). 합치기가 매번 성립해 목록이 짧게 유지된다.\
  `coalescingIsWhatKeepsItFromGettingWorse` 가 그 극단을 보여준다 — 16짜리 64개를 **순서대로 전부** 돌려주면 덩어리가 1개, 가장 큰 덩어리가 1024 로 완전히 회복된다.

```java
// src/test/.../FragmentationTest.java — coalescingIsWhatKeepsItFromGettingWorse
for (int i = 0; i < 64; i++) {
    a.free(addresses.get(i));
}
// 64 조각을 순서대로 돌려줬다. 합치기가 있으면 1 개, 없으면 64 개다.
assertEquals(1, a.freeBlockCount());
assertEquals(CAPACITY, a.largestFreeBlock());
```

> **`largestFreeBlock`** — 남은 것 중 연속된 가장 큰 덩어리. **실제로 떼어줄 수 있는 최대치**다.\
> 예: `freeBytes` 가 512 여도 이 값이 16 이면 17바이트 요청은 실패한다.

> **갇힌 바이트(trapped bytes)** — 떼어줬지만 쓰이지 않고, 돌려주지도 못하는 공간.\
> 예: 33을 달랬는데 64를 받으면 31바이트가 그 할당 안에 갇힌다. `free` 해야만 풀리고, 부분적으로는 못 푼다.

**더 생각할 것**

- 최악 패턴을 만드는 요령은 **합치기가 성립하지 못하게 하는 것**이다.\
  한 칸 걸러 비우기가 정확히 그 일을 한다 — 빈 자리마다 양옆을 사용 중으로 만든다.\
  그리고 이 패턴은 인위적이지 않다. 수명이 제각각인 실제 프로그램에서 자연스럽게 나온다.
- 버디의 최악 패턴은 반대 방향이다 — **합치기는 잘 되는데 올림이 계속 쌓이게** 만든다.\
  `2^k + 1` 크기 요청이 그것이고, 실제로 헤더 몇 바이트가 붙는 구현에서 흔히 생긴다(32바이트 데이터 + 8바이트 헤더 = 40 → 64).
- 그래서 두 최악은 **같은 자로 안 보인다**.\
  외부 단편화는 `largestFreeBlock` 이, 내부 단편화는 `wastedBytes` 가 본다.\
  자를 하나만 두면 반드시 한쪽을 놓친다 — 이 박스가 자를 여섯 개 둔 이유다.

#### 5. 다섯 구현의 트레이드오프 — 계약이 같은데 무엇이 갈리는가

- Q: 계약 테스트를 다섯이 다 통과하는데 무엇이 갈리는가?\
  A: **한참 쓰고 난 뒤의 모양**이다.\
  자리를 떼어주고 돌려받는 일은 어느 쪽으로 해도 맞다. 갈리는 것은 그 선택이 누적됐을 때의 단편화와 실패율이다.\
  (`AllocatorContractTest` 에 `@Test` 가 21개이고 5구현이 상속하므로 105개, 거기에 구현별 테스트(buddy 8 + bump 4)를 더하면 117개다.\
  전체 125개에서 `FragmentationTest` 8개를 뺀 수와 같다. README 의 "계약 테스트 117개"는 그 셈이다.)

- Q: best fit 의 "큰 자리를 아껴두자"와 worst fit 의 "남는 조각을 크게 만들자"가 둘 다 그럴듯한데, 재보면 어떤가?\
  A: **제일 단순한 first fit 이 이긴다.** 요청 300개를 같은 순서로 넣은 결과다.

```java
// src/test/.../FragmentationTest.java — sameWorkloadDifferentOutcomes
assertEquals(169, f[0], "first fit 실패");
assertEquals(170, b[0], "best fit 실패");
assertEquals(178, w[0], "worst fit 실패");

assertEquals(7, f[3], "first fit 덩어리");
assertEquals(7, b[3], "best fit 덩어리");
assertEquals(9, w[3], "worst fit 덩어리");

assertTrue(w[0] > f[0], "worst fit 이 더 실패한다: " + w[0] + " 대 " + f[0]);
assertTrue(worst.scanned() > first.scanned() * 1.5, worst.scanned() + " 대 " + first.scanned());
```

```text
요청 300개를 같은 순서로 넣는다 (용량 1024, 크기 8~63)

                실패    남은 덩어리    훑은 횟수
  first fit     169         7          1,467
  best fit      170         7          1,886
  worst fit     178         9          2,519

  주의 — 무엇이 assert 돼 있고 무엇이 아닌가
    실패 169 / 170 / 178      assertEquals 로 못 박혀 있다
    덩어리 7 / 7 / 9          assertEquals 로 못 박혀 있다
    훑은 횟수 1,467 / 1,886 / 2,519
                              README 와 테스트 출력에 찍히는 측정값이다.
                              테스트가 assert 하는 것은 부등식뿐이다:
                                worst.scanned() > first.scanned() * 1.5
```

- Q: 왜 그런 결과가 나오는가?\
  A: worst fit 이 지는 이유는 명확하다 — **큰 자리를 제일 먼저 깎아먹기** 때문이다.\
  가장 큰 덩어리부터 잘라 쓰므로 큰 덩어리가 금방 사라지고, 큰 요청이 나중에 오면 받을 자리가 없다.\
  best fit 이 first fit 보다 조금 더 실패하는 이유는 단정하기 어렵다.\
  "큰 자리를 아낀다"는 그럴듯한 이유가 **이 요청 열에서는** 안 통했고, 대신 훑는 비용은 확실히 더 들었다.\
  테스트 주석도 그 이상을 주장하지 않는다 — 169 대 170 은 1건 차이다.

- Q: 그것을 어떻게 설명해야 하는가?\
  A: **재기 전에는 어느 쪽이 맞는지 알 수 없다**로 설명해야 한다.\
  이 박스가 worst fit 을 넣어둔 이유가 "이기라고"가 아니다 — **그럴듯한 이유가 양쪽에 다 있는데 결과가 갈린다**는 것을 보여주려는 것이다.\
  그리고 best fit 이 "큰 자리를 아끼는" 대신 **쓸모없이 작은 조각을 만든다**는 반대급부가 있다는 것도 함께 봐야 한다.\
  100바이트 자리에서 99를 떼면 1바이트가 남는데, 그 1바이트는 앞으로 거의 아무 요청도 못 받고 목록만 길게 만든다.

```text
best fit 이 산 것과 판 것

  산 것 : 큰 덩어리를 덜 깎는다
  판 것 : 아주 작은 조각을 많이 만든다 + 매번 전부 훑는다

  worst fit 이 산 것과 판 것
  산 것 : 남는 조각이 크다 (쓸 수 있는 조각이다)
  판 것 : 큰 덩어리가 먼저 사라진다 + 매번 전부 훑는다

  first fit 이 산 것과 판 것
  산 것 : 만나면 멈춘다 (제일 싸다)
  판 것 : 앞쪽이 잘게 부서지고, 그 조각들을 매번 다시 훑는다
          (실제 구현이 "지난번 멈춘 자리부터" 로 고치는 이유 = next fit)

  결론 : 셋 다 그럴듯하다. 이 요청 열에서는 first fit 이 이겼을 뿐이다.
         다른 요청 열이면 다를 수 있다. 그래서 "재고 고른다" 가 답이다.
```

- Q: 외부 단편화와 내부 단편화 중 하나를 없애면 왜 다른 쪽이 생기는가?\
  A: **둘이 같은 하나의 결정에서 나오기** 때문이다 — **요청한 만큼만 줄 것인가, 정해진 단위로 줄 것인가.**\
  요청한 만큼만 주면 내부 단편화가 0 이다(빈 자리 목록의 `wastedBytes()` 는 상수 0 을 돌려준다).\
  대신 남는 조각의 크기가 제각각이 되어 합쳐지지 않는 조각이 생긴다 → 외부 단편화.\
  정해진 단위(2의 거듭제곱)로만 주면 조각의 크기가 몇 종류로 제한되어 합치기가 잘 된다 → 외부 단편화가 준다.\
  대신 요청과 단위의 차이가 통째로 갇힌다 → 내부 단편화.\
  **하나의 축의 양 끝**이지 별개의 두 문제가 아니다.

```java
// impl/FreeListAllocator.java
/** 요청한 만큼만 떼어준다. 내부 단편화가 없다. 그 대신 외부 단편화를 짊어진다. */
@Override
public int wastedBytes() {
    return 0;
}
```

```text
한 축의 양 끝

  요청한 만큼 정확히                      정해진 단위로 올림
  <---------------------------------------------------------->
  내부 단편화 0                            내부 단편화 최대 요청 크기만큼
  외부 단편화 큼                           외부 단편화 작음
  (first/best/worst fit)                  (buddy)

  중간도 있다 (원본에 근거 없음 — 내 추론)
    8바이트 배수로 올림하면 내부 단편화는 최대 7, 외부 단편화도 어느 정도 줄어든다
    실제 malloc 구현들이 대개 이 자리에 있다
```

- Q: 빈 자리 목록을 주소순으로 들 때와 크기순으로 들 때 각각 무엇을 얻고 잃는가?\
  A: **무엇을 정렬해 두느냐가 무엇을 할 수 있는지를 정한다.**

```text
주소 오름차순 (이 구현의 선택)
  얻는 것 : 인접한 빈 자리를 찾을 수 있다 -> 합치기가 가능하다
            insertAndCoalesce 가 i-1, i, i+1 만 보면 된다
  잃는 것 : 고르기가 느리다. 크기 조건에 맞는 것을 찾으려면 훑어야 한다
            best fit 은 매번 전부 훑는다

크기 오름차순
  얻는 것 : best fit 이 "첫 번째로 맞는 것" 이 곧 답이다 -> 만나면 멈춘다
            (원본에 근거 없음 — 내 추론) 트리나 스킵 리스트로 들면 O(log n) 도 된다
  잃는 것 : 합치기가 불가능하다. 주소가 옆인 자리가 목록에서 어디 있는지 모른다
            합치기가 없으면 잘게 부서진 채로 영영 회복이 안 된다

  FreeListAllocator 의 첫 주석이 그 결정을 그대로 적는다:
    "목록은 주소 오름차순으로 유지한다. 그래야 인접한 빈 자리를 합칠 수 있다.
     크기순으로 들면 고르기는 빨라지는데 합치기가 불가능해진다."

  실제 구현은 둘 다 든다 (원본에 근거 없음 — 내 추론)
    주소순 인덱스로 합치고, 크기별 버킷으로 고른다. 대신 둘을 동기화해야 한다
```

- Q: 합치기를 안 해도 계약 테스트가 거의 다 통과하는 것이 왜 위험한가?\
  A: **남은 총량이 맞기 때문**이다.\
  합치기를 빼먹어도 `freeBytes` 는 정확하다 — 돌려받은 바이트를 다 세니까.\
  `usedBytes` 도 맞고, `allocate`/`free` 도 동작한다. 예외도 안 난다.\
  틀리는 것은 `largestFreeBlock` 과 `freeBlockCount` 뿐이고, 그 둘을 안 보면 결함이 통째로 안 보인다.

```text
합치기를 뺀 구현이 통과하는 것과 걸리는 것

  통과한다
    freeBytes 가 맞다            돌려받은 총량은 그대로다
    usedBytes 가 맞다
    떼어준 자리가 안 겹친다
    준 적 없는 주소에 던진다
    -> 계약 테스트가 거의 다 초록불이다

  걸린다 (이 둘을 재는 테스트가 있을 때만)
    freeBlockCount   1 이어야 하는데 64 다
    largestFreeBlock 1024 여야 하는데 16 이다
    coalescingIsWhatKeepsItFromGettingWorse 가 정확히 그 둘을 assert 한다

  그래서 "자를 하나만 두면 안 되는" 자리이고, 이 박스가 자를 여섯 개 두는 이유다
  (usedBytes, freeBytes, largestFreeBlock, freeBlockCount, wastedBytes, scanned)

  8 바이트짜리 빈 자리 백 개가 생기면 9 바이트 요청이 실패한다.
  남은 공간은 800 바이트인데 말이다. 예외는 안 난다
```

- Q: 이중 `free` 를 조용히 넘어가면 왜 안 되는가?\
  A: **같은 자리를 두 번 세어 남은 공간이 부풀고, 그 뒤로는 없는 자리를 떼어주기** 때문이다.\
  그래서 `allocated` 맵에서 `remove` 한 결과가 `null` 이면 즉시 던진다.

```java
// impl/FreeListAllocator.java
public void free(int address) {
    Integer size = allocated.remove(address);
    if (size == null) {
        throw new IllegalArgumentException("떼어준 적 없거나 이미 돌려받은 주소다: " + address);
    }
    insertAndCoalesce(new Block(address, size));
}
```

  `remove` 를 쓰는 것이 요점이다 — **꺼내면서 지우므로 두 번째 `free` 는 자동으로 `null`** 이 된다.\
  그리고 빈 자리 목록에 겹치는 블록이 들어가려 하면 `insertAndCoalesce` 가 `IllegalStateException` 을 던진다 — 이중 방어선이다.\
  **손상은 한참 뒤에 드러난다**는 것이 이 방어가 필요한 이유다. 조용히 넘어가면 원인에서 멀리 떨어진 곳에서 터진다.

> **워크로드(workload)** — 실제로 들어오는 요청의 크기·순서·수명 분포. 전략의 우열을 정하는 것은 알고리즘이 아니라 이것이다.\
> 예: 같은 세 전략이 다른 요청 열에서는 다른 순위를 낼 수 있다. 169 대 170 은 1건 차이다.

> **`scanned`** — 자리를 고르느라 들여다본 빈 자리의 수. 전략별 고르기 비용을 재는 자다.\
> 예: 덩어리 16개에서 한 번 할당할 때 first fit 은 1, best fit 은 17 이다.

> **덩어리 수(`freeBlockCount`)** — 남은 빈 자리가 몇 조각인가. 늘어난다는 것은 잘게 부서지고 있다는 뜻이다.\
> 예: 합치기가 있으면 전부 돌려준 뒤 1 이고, 없으면 돌려준 횟수만큼이다.

**더 생각할 것**

- 다섯 구현을 한 표로 정리하면 이렇다.

| | 고르는 규칙 | 회수 | 외부 단편화 | 내부 단편화 | 고르기 비용 |
|---|---|---|---|---|---|
| `BumpAllocator` | 밀어올린다 | **안 한다** | **없다** | 없다 | 없음 |
| `FirstFitAllocator` | 맞는 것 중 제일 앞 | 한다 | 있다 | 없다 | 만나면 멈춘다 |
| `BestFitAllocator` | 맞는 것 중 제일 작은 것 | 한다 | 있다 | 없다 | 전부 훑는다 |
| `WorstFitAllocator` | 맞는 것 중 제일 큰 것 | 한다 | 있다 | 없다 | 전부 훑는다 |
| `BuddyAllocator` | 2의 거듭제곱으로 쪼갠다 | 한다 | 적다 | **있다** | 레벨을 올라가며 찾는다 |

- "그럴듯한 설명이 양쪽에 다 있다"는 상황을 만나면, 그건 **설명을 더 정교하게 만들 자리가 아니라 측정할 자리**다.\
  34번에서 "두 알고리즘이 둘 다 맞다"를 만났던 것과 같은 구도이고, 답도 같다 — 재고 고른다.
- README 의 변종 실험에서 하나가 살아남았는데, 확인해보니 **결함이 아니었다**는 대목이 좋다.\
  "왼쪽부터 합치기"는 인덱스를 보정하면 맞다. 테스트를 고치는 대신 **주석을 고쳤다**.\
  변종이 살아남았을 때 자동으로 테스트를 추가하는 게 아니라, **먼저 그게 진짜 결함인지 확인하는** 순서가 지켜져 있다.

#### 6. 이 구조는 지금까지 배운 것 중 무엇을 조합한 것인가

- Q: 빈 자리 목록(주소 오름차순 유지 · 인접 합치기)은 02번 연결 리스트 / 01번 동적 배열의 어떤 성질을 쓰는가?\
  A: **"정렬을 유지하면 이웃이 곧 옆자리"** 라는 성질을 쓴다.\
  주소 오름차순으로 들고 있으면 `free.get(i-1)` 과 `free.get(i+1)` 이 주소상 바로 앞뒤 빈 자리다.\
  그래서 합칠 후보를 찾는 일이 **양옆 두 칸 보기**로 끝난다 — 목록 전체를 뒤질 필요가 없다.\
  02번 연결 리스트의 "정렬 삽입 + 이웃 참조" 가 이 모양이고, 실제 C 의 할당자는 빈 블록 안에 링크를 넣어 연결 리스트로 만든다.\
  이 구현은 `ArrayList<Block>` 이라 01번 동적 배열의 성질도 쓴다 — **인덱스로 양옆에 O(1) 접근**하는 대신, 중간 삽입·삭제가 O(n) 시프트다.

```text
같은 불변식이 세 박스에서 반복된다

  02 연결 리스트   정렬 삽입 -> 이웃이 곧 값 순서의 앞뒤
  32 역색인        포스팅 리스트 오름차순 -> 한 번 훑기 병합이 성립
  35 빈 자리 목록  주소 오름차순 -> 양옆 두 칸만 보면 합칠지 알 수 있다

  셋 다 "정렬이 능력을 만든다" 이고
  셋 다 "정렬이 깨지면 조용히 틀린다" 이다
```

- Q: `allocated` 맵(주소 → 떼어준 크기)은 05번 해시맵의 무엇인가?\
  A: **키로 값을 O(1) 에 찾는 능력** 그 자체다.\
  `free(address)` 는 주소만 받는다 — 얼마를 돌려받아야 하는지를 모른다.\
  그 정보를 어디엔가 적어둬야 하고, "주소로 즉시 찾을 수 있어야" 하므로 해시맵이 정확히 맞는 도구다.\
  그리고 `remove` 가 "꺼내면서 지운다"는 성질이 **이중 free 방어**까지 겸한다 — 자료구조 하나가 두 일을 한다.\
  버디는 같은 자리에 `Map<Integer, int[]>` 로 `[떼어준 크기, 요청한 크기]` 쌍을 담는다. **재려면 먼저 기록해야 하기** 때문이다.

- Q: 버디의 `주소 XOR 크기` 는 18번 비트셋의 무엇이 자료구조의 성질로 바뀐 것인가?\
  A: **"위치 계산을 산술로 바꾸기"** 가 바뀐 것이다.\
  18번 비트셋에서는 원소 `x` 가 몇 번째 워드의 몇 번째 비트인지를 `x >> 6`, `x & 63` 으로 계산했다 — 찾는 대신 계산한다.\
  여기서는 **짝이 어디 있는지를 찾는 대신 계산한다**. `address ^ (1 << level)` 한 줄이다.\
  바뀐 지점은 그 계산이 **탐색을 통째로 없앤다**는 것이다.\
  빈 자리 목록은 인접 자리를 찾으려고 목록을 훑어야 했고(합치기가 O(목록 길이)), 버디는 그 탐색이 아예 없다(O(1)).\
  대가로 "크기는 2의 거듭제곱, 주소는 그 배수"라는 제약을 받아들였다 — **계산이 성립하도록 자료구조를 제약한 것**이고, 그래서 "산술"이 "성질"이 됐다고 말한다.

```text
계산으로 탐색을 없애는 패턴

  18 비트셋      x 가 어느 비트인가        ->  x >> 6, x & 63          (탐색 없음)
  17 펜윅 트리   다음에 볼 인덱스          ->  i += i & -i             (탐색 없음)
  35 버디        내 짝이 어디 있나          ->  address ^ (1 << level)  (탐색 없음)

  공통 조건 : 구조에 규칙을 걸어야 계산이 성립한다
              비트셋은 "원소가 정수 범위", 버디는 "크기가 2의 거듭제곱 + 정렬"
  공통 대가 : 그 규칙을 못 지키는 입력은 이 구조로 못 다룬다
              버디의 경우 그것이 내부 단편화로 나타난다
```

- Q: `freeByLevel` 의 `TreeSet` 은 왜 정렬 구조여야 하는가?\
  A: **답을 하나로 정하기 위해서**다.\
  같은 레벨에 빈 자리가 여럿이면 어느 것을 떼어줘도 맞다. 그런데 어느 것을 주느냐에 따라 **주소가 달라지고**, 이후의 합치기 양상도 달라진다.\
  `HashSet` 이면 순회 순서가 정해지지 않아 같은 요청 열에 다른 주소가 나올 수 있고, 그러면 기댓값을 쓸 수 없다.\
  `TreeSet` 에 `pollFirst()` 를 쓰면 **늘 가장 작은 주소**를 준다 — 답이 하나로 고정된다.\
  실제로 `adjacentIsNotEnough` 가 `assertEquals(List.of(0, 256, 512, 768), List.of(b0, b1, b2, b3))` 로 주소 자체를 못 박는다. 그게 가능한 이유가 `TreeSet` 이다.\
  05번의 "해시 순회 순서에 기대지 마라", 33번 `Node.children` 의 `TreeMap`, 34번 `DependencyGraph` 의 `TreeMap`/`TreeSet` 과 같은 결정이다.

```java
// impl/BuddyAllocator.java
/** 크기 지수 -> 그 크기의 빈 자리 주소들. 오름차순이라 답이 하나로 정해진다. */
private final List<TreeSet<Integer>> freeByLevel = new ArrayList<>();
...
int address = freeByLevel.get(found).pollFirst();
```

- Q: 01번 동적 배열이 `capacity` 를 두 배로 늘릴 때 그 새 배열을 어디서 받아왔는가?\
  A: **여기서 받아왔다.**\
  `Arrays.copyOf` 가 새 배열을 만드는 일은 결국 "연속된 `newCapacity` 칸을 떼어달라"는 할당 요청이다.\
  그리고 01번에서 배웠던 두 가지가 여기서 다시 읽힌다.\
  하나 — 확장할 때 **옛 배열과 새 배열이 동시에 살아 있으므로** 순간적으로 1.5배(2배 확장 시)의 공간이 필요하다.\
  그 순간 할당자는 `n` 짜리와 `2n` 짜리를 동시에 들고 있어야 하고, `largestFreeBlock` 이 `2n` 이상이어야 한다.\
  둘 — 01번의 "수천만 건이면 **연속된** 메모리 덩어리를 확보해야 하고, 전체 여유가 충분해도 단편화 때문에 실패할 수 있다"가 바로 **외부 단편화**였다.\
  그때는 이름을 안 붙이고 넘어갔던 것을 여기서 이름 붙이고 자로 재는 것이다.

```text
01 과 35 를 이어 읽으면

  01 동적 배열의 확장
    elements = Arrays.copyOf(elements, newCapacity)
      -> 새 배열 2n 을 할당한다
      -> 복사한다
      -> 옛 배열 n 을 놓는다

  35 할당자에서 본 그 장면
    allocate(2n) 이 성공하려면 largestFreeBlock >= 2n 이어야 한다
      freeBytes 가 10n 이어도 largestFreeBlock 이 1.5n 이면 실패한다
    성공한 뒤 free(옛 주소) 로 n 을 돌려주면
      그 n 짜리 구멍이 남는다 -> 다음 확장(4n)을 위해 합쳐져야 한다

  01 에서 "2배로 늘리는 이유" 를 시간(복사 횟수)으로만 봤다면
  35 는 그 결정이 공간에 어떤 자국을 남기는지를 보여준다.
  1.5배 확장이 "해제된 옛 블록을 재사용하기 유리하다" 던 말도 여기서야 뜻이 통한다
  (2배로 계속 늘리면 앞의 해제 블록들을 합쳐도 다음 요청을 못 받는데,
   1.5배면 언젠가 합쳐진 앞쪽에 들어갈 수 있다).
```

> **주소로 크기를 되찾기(allocation bookkeeping)** — `free(address)` 가 얼마를 돌려받아야 하는지 알려면 어딘가에 적어둬야 한다.\
> 예: `allocated.put(address, size)` 로 적고 `allocated.remove(address)` 로 꺼낸다. 실제 `malloc` 은 블록 앞에 헤더로 붙인다.

> **결정성을 위한 정렬 구조** — 답이 여럿일 때 어느 것을 고를지 자료구조의 순서로 고정하는 것.\
> 예: `freeByLevel` 의 `TreeSet` + `pollFirst()` 는 "늘 가장 작은 주소"를 골라 주소 기댓값을 쓸 수 있게 만든다.

**더 생각할 것**

- 이 박스가 마지막인 이유가 여기서 분명해진다 — **앞에서 배운 것들이 부품으로 다시 등장**한다.\
  정렬 유지(02·32), 해시맵의 O(1) 조회(05), 비트 산술(17·18), 결정성을 위한 정렬 구조(05·33·34), 계약 테스트 + 측정 테스트의 분리(23·32·33·34).\
  새로운 자료구조를 배운다기보다 **배운 것들을 조합해 한 층 아래를 만든다**.
- 그리고 마지막 교훈은 검증 쪽이다.\
  01번부터 35번까지 반복된 문장이 하나 있다 — **"계약 테스트를 다 통과해도 틀린(또는 나쁜) 구현이 있다."**\
  23번은 회전 수가, 32번은 대조와 비교 횟수가, 33번은 다시 쓴 키 수가, 34번은 방문 수가, 35번은 여섯 개의 자가 그것을 잡았다.\
  자료구조를 고르는 일은 언제나 **무엇을 재는지 먼저 정하는 일**이다.
- 실무로 옮기면 한 문장이 남는다.\
  `new` 한 줄이 공짜가 아니고, 그 비용은 "얼마나 자주 부르는가"보다 **"수명과 크기 분포가 어떤가"** 로 정해진다.\
  그리고 그 결과는 지금이 아니라 한참 뒤에 "빈 공간은 많은데 할당이 실패한다"로 나타난다.
