### B. 자료구조 특성

#### 1. 위상 정렬이 왜 필요한가 — 순회도 정렬도 아닌 것

- Q: 이 구조가 푸는 문제를 한 문장으로 적으면?\
  A: **"먼저 와야 하는 것"이라는 부분 순서만 주어졌을 때, 그 제약을 전부 지키는 전순서 하나를 만들어라.**\
  `npm install` 이 무엇을 먼저 받을지 정하는 일이고, 빌드 도구가 모듈 컴파일 순서를 정하는 일이다.

- Q: 08번 그래프의 순회(BFS/DFS)만으로는 무엇이 안 되는가?\
  A: 순회는 **"도달 가능한가 / 어디까지 갈 수 있는가"** 에 답한다.\
  방문 순서를 주기는 하는데, 그 순서가 의존 제약을 지킨다는 보장이 전혀 없다.\
  BFS 는 시작점에서 가까운 순이고, DFS 의 **전위(preorder)** 순서는 "내려가면서 적은" 순서다.\
  둘 다 "아직 안 끝난 것을 먼저 적는" 순서라 제약을 어긴다.

```text
왜 그냥 순회로는 안 되나

  그래프 (화살표 = "먼저 와야 한다")
      root ---> z ---> leaf
       |
       +------> b

  DFS 전위 순서로 적으면   root, z, leaf, b     <- 이건 우연히 맞다
  그런데 시작점을 z 로 잡으면  z, leaf          <- root 가 아예 안 나온다

  BFS 로 적으면  root, b, z, leaf              <- 이것도 우연히 맞다
  그런데 간선이 root -> z, b -> z 두 개면
    BFS 는 root, b 를 먼저 내고 z 를 나중에 내지만, 그건 우연이다.
    "z 앞의 것이 전부 나왔는가" 를 BFS 는 확인하지 않는다.

  요점: 순회는 "방문했는가" 를 관리하지 "선행 조건이 다 끝났는가" 를 관리하지 않는다.
        위상 정렬이 추가로 들고 있는 것이 정확히 그 정보다 (진입 차수, 또는 후위 순서).
```

- Q: 06번 BST 의 정렬만으로는 왜 안 되는가?\
  A: BST 가 다루는 것은 **전순서(total order)** 다 — 아무 두 원소나 집어도 대소가 정해진다.\
  의존 관계는 **부분 순서(partial order)** 다 — `a` 와 `b` 가 서로 상관없으면 둘 사이에 대소가 없다.\
  비교 함수를 만들 수가 없다. `compare(a, b)` 가 무엇을 돌려줘야 하는가? 같지도 않고 작지도 크지도 않다.\
  그래서 정렬 알고리즘을 그냥 못 쓴다.

- Q: 그러면 "부분 순서에서 전순서 하나를 만든다"가 왜 새로운 문제인가?\
  A: **답이 여러 개**이기 때문이다. 정렬은 답이 하나인데, 이건 아니다.\
  `a` 와 `b` 가 상관없으면 `a, b` 도 맞고 `b, a` 도 맞다.\
  그래서 이 박스의 검증 방식이 32번·33번과 달라진다 — "답이 같은가"를 못 묻고 "답이 성질을 만족하는가"를 물어야 한다.\
  그리고 구현마다 답이 다르게 나오는 것이 **버그가 아니라 정상**이다.

```java
// src/test/.../MeasurementTest.java — 같은 그래프에 두 답이 나온다
DependencyGraph g = new DependencyGraph();
g.dependsOn("z", "root");
g.dependsOn("b", "root");
g.dependsOn("m", "root");
g.dependsOn("leaf", "z");

assertEquals(List.of("root", "b", "m", "z", "leaf"), new KahnResolver(g).resolve());
assertEquals(List.of("root", "z", "m", "leaf", "b"), new DfsResolver(g).resolve());
assertNotEquals(kahn, dfs, "답이 같으면 이 박스의 전제가 무너진다");
```

> **위상 정렬(topological sort)** — 방향 간선 `u → v` 가 있으면 `u` 가 `v` 보다 앞에 오도록 노드를 한 줄로 늘어놓는 것.\
> 예: `lib → app` 이면 `[lib, app]` 이 답이고 `[app, lib]` 은 아니다.

> **부분 순서(partial order)** — 어떤 두 원소 사이에는 순서가 정해지고, 어떤 둘 사이에는 안 정해지는 관계.\
> 예: `b` 와 `m` 은 서로 아무 의존이 없으므로 둘 중 무엇이 앞에 와도 맞다.

> **전순서(total order)** — 아무 두 원소나 집어도 반드시 대소가 정해지는 관계. 정렬 알고리즘이 요구하는 것.\
> 예: 정수 `3` 과 `7` 사이에는 언제나 대소가 있다. 그래서 BST 가 성립한다.

- Q: 화살표의 방향은 어떻게 정했고, 왜 그것이 중요한가?\
  A: `dependsOn("앱", "라이브러리")` 는 "앱이 라이브러리에 기댄다"인데, 화살표는 **"먼저 와야 한다" 방향**으로 잡았다.\
  즉 `라이브러리 → 앱` 이다. 위상 정렬이 화살표 방향대로 늘어놓는 것이고, 우리가 원하는 순서가 "먼저 와야 하는 것이 앞"이기 때문이다.

```java
// impl/DependencyGraph.java
/** 이름 -> 그 이름 뒤에 와야 하는 것들. 화살표 방향이다. */
private final Map<String, TreeSet<String>> edges = new TreeMap<>();

public void dependsOn(String dependent, String dependency) {
    ...
    if (edges.get(dependency).add(dependent)) {   // dependency -> dependent
        inDegree.merge(dependent, 1, Integer::sum);
    }
}
```

- Q: 방향을 뒤집으면 무슨 일이 생기는가?\
  A: **답이 정확히 거꾸로 나온다. 예외는 안 난다.**\
  게다가 **순환 탐지는 멀쩡히 동작한다** — 순환은 방향을 뒤집어도 순환이기 때문이다.\
  그래서 "순환 테스트가 통과하니 그래프는 맞다"가 성립하지 않는다.\
  이 박스에서 가장 조용한 오답이 여기다.

- Q: 같은 의존을 두 번 걸면?\
  A: 진입 차수가 **한 번만** 올라야 한다. `TreeSet.add` 가 `false` 를 주면 `inDegree` 를 안 올린다.\
  두 번 올리면 그 노드는 영원히 0 이 안 되고, **순환이 없는데도 순환으로 보고된다**.\
  이것은 반대로 시끄러운 실패라 테스트에 걸린다 — 조용한 실패보다 낫다.

- Q: 자기 자신에게 기대면?\
  A: **길이 1 짜리 순환**으로 다룬다. 입구에서 막지 않고 순환 처리에 맡긴다.

```java
// impl/DependencyGraph.java
if (dependent.equals(dependency)) {
    // 자기 자신에게 기대는 것도 길이 1 짜리 순환이다. 여기서 막지 않고 순환으로 다룬다.
    add(dependent);
    if (edges.get(dependent).add(dependent)) {
        inDegree.merge(dependent, 1, Integer::sum);
    }
    return;
}
```

```text
왜 입구에서 막지 않는가 (33번과의 대비)

  33 파일 시스템 : 자기 안으로 mv 하는 것을 입구에서 던졌다
                   막을 수 있었던 이유 = 고리의 모양이 한 가지로 뻔했다

  34 의존 그래프 : a -> a 는 막을 수 있지만 a -> b -> c -> a 는 못 막는다
                   간선 하나하나는 전부 정상이고 합쳐져야 고리가 되기 때문이다
                   그러면 "길이 1 만 막고 길이 3 은 못 막는" 어중간한 계약이 된다

  그래서 전부 순환 처리에 맡긴다. 계약이 하나로 단순해진다
  DfsResolverTest.selfLoopPath : assertEquals(List.of("a", "a"), new DfsResolver(g).cycle())
```

**더 생각할 것**

- "정렬"이라는 이름 때문에 헷갈리기 쉬운데, 위상 정렬에는 **비교 함수가 없다**.\
  비교로 푸는 문제가 아니라 **제약 만족** 문제이고, 그래서 답이 여럿이고 그래서 검증 방식이 달라진다.
- 실무에서 이 구조를 만나는 자리는 아주 많다 — 패키지 매니저, 빌드 시스템(make/gradle), 스프레드시트 수식 재계산, DB 마이그레이션 순서, 태스크 스케줄러(Airflow).\
  전부 "부분 순서만 알고 전순서가 필요하다"는 같은 모양이다.
- 08번 그래프에서 배운 인접 리스트를 그대로 쓴다는 것도 중요하다.\
  `DependencyGraph` 는 새 자료구조가 아니라 **인접 리스트에 진입 차수 하나를 곁들인 것**이다.\
  새로운 것은 자료구조가 아니라 그 위에서 도는 알고리즘과 검증 방법이다.

#### 2. 어떤 의존 관계와 접근 패턴에 적합한가 · DAG 전제가 깨지면

- Q: 어떤 형태의 의존 관계에 적합한가?\
  A: **고리가 없는(DAG) 방향 관계**다. 그리고 관계가 **한 번 정해지면 잘 안 바뀌는** 것.\
  "이 일을 하려면 저 일이 먼저 끝나야 한다"가 명확하고, 그 제약이 전부인 문제.\
  가중치(비용·시간)가 없어도 되는 문제 — 이 구조는 순서만 답하고 "얼마나 걸리는가"는 안 본다.

- Q: 어떤 접근 패턴에 적합한가?\
  A: **그래프를 다 세워둔 뒤 한 번에 전체 순서를 묻는** 패턴이다.\
  `resolve()` 도 `layers()` 도 매번 그래프 전체를 처음부터 훑는다. 증분 계산이 없다.\
  그래서 "그래프를 만든다 → 순서를 묻는다 → 그대로 실행한다"가 한 사이클이면 잘 맞는다.

- Q: DAG 전제가 깨지면(순환) 무엇을 돌려줘야 하는가?\
  A: **아무것도 안 돌려주고 던져야 한다.** `CycleException` 이다.

```java
// impl/KahnResolver.java
if (order.size() != graph.size()) {
    // 부분 결과를 주지 않는다. 절반만 설치된 상태가 아무것도 안 한 상태보다 나쁘다.
    throw new CycleException(cycle());
}
```

- Q: 왜 부분 결과를 주면 안 되는가?\
  A: **절반만 설치된 상태가 아무것도 안 한 상태보다 나쁘기** 때문이다.\
  순환이 있으면 "전부 지킬 수 있는 순서"가 존재하지 않는다. 짧은 목록은 답이 아니라 **답이 없다는 사실을 숨긴 것**이다.\
  호출자가 그 목록을 그대로 실행하면 일부만 설치되고, 실패 원인은 한참 뒤에 엉뚱한 곳에서 드러난다.\
  README 가 "짧은 목록을 조용히 돌려주는 구현이 가장 위험하다"고 적은 이유다.

```text
칸 알고리즘이 순환을 알아채는 방식

  a -> b -> c -> a  (셋이 서로 물려 있다)

  진입 차수 : a=1, b=1, c=1        <- 0 인 것이 하나도 없다
  ready 가 처음부터 비어 있다  ->  while 루프가 한 번도 안 돈다
  order.size() = 0 != graph.size() = 3   ->  던진다

  노이즈가 섞여 있으면
    noise0 -> noise1 -> ... -> noise100  (정상적인 사슬 101개)
    a -> b -> c -> a                     (순환 3개)

  칸은 noise 101개를 전부 뽑아내고 a, b, c 셋이 남는다
  order.size() = 101 != 104   ->  던진다
  "다 못 뽑았다" 는 알지만 남은 것이 셋이라는 것 말고는 모른다
```

- Q: 간선이 계속 바뀌는 그래프에는 왜 이 구조로 답할 수 없는가?\
  A: **증분 갱신 수단이 없기** 때문이다.\
  간선 하나가 추가되면 순서 전체가 바뀔 수 있고, 이 구현은 그때 `resolve()` 를 처음부터 다시 돌리는 수밖에 없다.\
  `O(V + E)` 를 매번 내는 것이므로, 간선 추가가 `E` 번이면 총 `O(E(V + E))` 가 된다.\
  (원본에 근거 없음 — 내 추론) 이런 문제를 위한 동적 위상 정렬 알고리즘이 따로 있고, 이 박스의 범위 밖이다.\
  그리고 `DependencyGraph.dependenciesOf` 는 **역방향을 훑어서 만든다**는 것도 같은 성격의 한계다 — 반대 방향 질의는 매번 `O(V + E)` 다.

```java
// impl/DependencyGraph.java — 반대 방향은 저장돼 있지 않다
public List<String> dependenciesOf(String name) {
    List<String> out = new ArrayList<>();
    for (Map.Entry<String, TreeSet<String>> e : edges.entrySet()) {
        if (e.getValue().contains(name)) {
            out.add(e.getKey());
        }
    }
    return List.copyOf(out);
}
```

- Q: "가장 싼 순서"를 묻는 문제에는 왜 답할 수 없는가?\
  A: **비용이라는 개념이 구조에 없기** 때문이다.\
  `DependencyGraph` 에는 노드 이름과 간선만 있다. 노드의 소요 시간도, 간선의 비용도 담을 자리가 없다.\
  그리고 위상 정렬이 답하는 것은 "제약을 지키는 순서 하나"이지 "제약을 지키는 순서들 중 최선"이 아니다.\
  최선을 찾는 것은 다른 문제다 — 대개 제약 하에 목적 함수를 최소화하는 스케줄링 문제이고, 그중 많은 경우가 NP-난해다.\
  이 구조가 그 방향으로 줄 수 있는 유일한 정보가 `layers()` 다 — "무한한 코어가 있어도 이만큼은 걸린다"는 **하한**.

> **DAG(directed acyclic graph, 방향 비순환 그래프)** — 방향 간선만 있고 고리가 없는 그래프. 위상 정렬이 존재할 필요충분조건이다.\
> 예: `a → b → c` 는 DAG 이고, `a → b → c → a` 는 아니다. 뒤쪽에는 위상 정렬이 아예 없다.

> **진입 차수(in-degree)** — 그 노드로 들어오는 간선의 수. 여기서는 "그 앞에 와야 하는 것의 개수"다.\
> 예: `inDegreeOf("app")` 이 2 면 app 앞에 반드시 와야 하는 것이 둘이라는 뜻이다.

> **부분 결과(partial result)** — 작업이 실패했는데 도중까지의 산출물을 돌려주는 것.\
> 예: 순환일 때 뽑아낸 101개만 돌려주면, 호출자는 그게 전체인 줄 알고 실행한다.

- Q: 그래프를 세우는 쪽의 계약은 어떻게 되어 있는가?\
  A: **없는 이름은 만들어 넣는다**. 그래서 `dependsOn` 만 불러도 노드가 생긴다.\
  그리고 `add` 는 이미 있으면 아무 일도 안 한다(멱등).\
  이 둘이 있어서 그래프를 세우는 순서가 답에 영향을 주지 않는다 — 재현성의 일부다.

```java
// impl/DependencyGraph.java
public void add(String name) {
    require(name);
    edges.computeIfAbsent(name, k -> new TreeSet<>());
    inDegree.putIfAbsent(name, 0);
}
```

```text
간선이 없는 노드도 반드시 등록돼야 한다

  independent(100) 은 dependsOn 을 한 번도 안 부르고 add 만 100번 부른다
  이때 edges 에 빈 TreeSet 이 들어가고 inDegree 에 0 이 들어간다

  만약 add 가 edges 에만 넣고 inDegree 를 안 넣으면
    inDegreeOf 가 getOrDefault(name, 0) 이라 0 을 주긴 한다  -> 우연히 동작한다
  반대로 inDegree 에만 넣고 edges 에 안 넣으면
    names() 가 edges.keySet() 이라 그 노드가 목록에서 사라진다 -> 조용히 빠진다

  "노드가 통째로 빠지는" 실패는 계약 테스트의 성질 1번(개수 + 집합)이 잡는다
```

**더 생각할 것**

- "실패했을 때 무엇을 돌려주는가"는 계약의 일부다.\
  던질지, 빈 목록을 줄지, 부분 결과를 줄지가 호출자가 쓸 수 있는 코드를 정한다.\
  여기서는 **던지되 그 예외에 진단 정보를 실어 보낸다**를 골랐고, 그래서 `CycleException.path()` 가 있다.
- "적합하지 않은 문제"를 구분하는 연습이 중요하다.\
  순서를 묻는 문제와 비용을 묻는 문제는 겉보기에 비슷한데 난도가 완전히 다르다.\
  위상 정렬은 `O(V + E)` 이고, 같은 그래프에서 "총 시간 최소 스케줄"은 대개 훨씬 어렵다.
- 실무에서 순환이 발견되면 대개 **설계가 잘못된 신호**다.\
  모듈 A 가 B 에 기대고 B 가 A 에 기대면, 둘을 합치거나 공통 부분을 셋째 모듈로 빼야 한다.\
  그래서 "순환을 어떻게든 처리한다"보다 "순환이 어디인지 정확히 말해준다"가 더 쓸모 있다 — 질문 5의 주제다.

#### 3. `resolve` · `layers` 의 비용 · 검은색을 다시 파면 생기는 일

- Q: 칸 알고리즘의 `relaxations` 가 왜 간선 수와 같아야 하는가?\
  A: **간선 하나가 정확히 한 번만 소비되기** 때문이다.\
  노드를 큐에서 꺼낼 때 그 노드에서 나가는 간선을 전부 훑으며 상대의 진입 차수를 1 내린다.\
  각 노드는 진입 차수가 0 이 될 때 **딱 한 번** 큐에 들어가므로, 각 노드의 나가는 간선도 딱 한 번씩 훑인다.

```java
// impl/KahnResolver.java
while (!ready.isEmpty()) {
    String name = ready.poll();
    order.add(name);
    for (String next : graph.after(name)) {
        relaxations++;
        int left = remaining.merge(next, -1, Integer::sum);
        if (left == 0) {
            ready.add(next);
        }
    }
}
```

```text
상태 검사로서의 relaxations

  간선 수보다 크면  -> 같은 노드를 두 번 꺼냈다는 뜻이다
                       (0 이 된 순간이 아니라 0 이하일 때마다 넣었다든가)
  간선 수보다 작으면 -> 못 뽑은 노드가 있다는 뜻이다 = 순환이거나 버그다

  KahnResolverTest.everyEdgeIsRelaxedExactlyOnce

    assertEquals(4, r.relaxations())            // 다이아몬드: a<-b, a<-c, b<-d, c<-d

  MeasurementTest.neitherRevisits

```

- Q: DFS 의 `visits` 가 왜 노드 수와 같아야 하는가?\
  A: **흰색인 노드에만 내려가기** 때문이다.\
  `walk` 에 들어가는 순간 회색으로 칠하므로, 같은 노드로 두 번 내려갈 수 없다.\
  그래서 `visits` 가 정확히 노드 수다 — `assertEquals(100, dfs.visits())`.

```java
// impl/DfsResolver.java
private boolean walk(String name, Map<String, Integer> color,
                     List<String> path, List<String> postorder) {
    visits++;
    color.put(name, GRAY);
    path.add(name);

    for (String next : graph.after(name)) {
        int c = color.getOrDefault(next, WHITE);
        if (c == GRAY) {
            ...          // 순환이다
        }
        if (c == WHITE && !walk(next, color, path, postorder)) {
            return false;
        }
        // 검은색이면 이미 다 본 것이다. 다시 안 내려간다. 순환도 아니다.
    }

    path.remove(path.size() - 1);
    color.put(name, BLACK);
    postorder.add(name);
    return true;
}
```

- Q: 검은색 노드를 다시 파면 답은 왜 맞는가?\
  A: 다시 파도 **하는 일이 똑같기** 때문이다.\
  이미 끝난 노드를 다시 내려가면 같은 후위 순서를 다시 만들 뿐이고(중복 추가를 막는 코드가 있으면 결과가 같다), 순서 제약은 그대로 지켜진다.\
  그래서 계약 테스트는 전부 통과한다 — 순서도 맞고 개수도 맞다.

- Q: 그런데 왜 비용이 2의 거듭제곱으로 터지는가?\
  A: **다이아몬드가 겹쳐 쌓이면 경로의 수가 지수로 늘기** 때문이다.\
  DFS 가 세는 것은 노드가 아니라 **경로**가 된다.

```text
겹친 다이아몬드 18층 (DfsResolverTest.memoisationKeepsItLinear 의 그래프)

  l0        r0
   | \      / |
   |  \    /  |
   |   \  /   |
  l1        r1        각 층에서 l, r 이 다음 층의 l, r 둘 다에 간선을 건다
   | \      / |        (l(i) -> l(i+1), l(i) -> r(i+1), r(i) -> l(i+1), r(i) -> r(i+1))
   |  \    /  |
  l2        r2
   ...  (18층)

  노드 수 = 38 개뿐이다

  색을 쓰면          한 노드에 한 번씩만 내려간다      visits = 38
  검은색을 무시하면  0층에서 아래로 가는 경로를 전부 센다
                     각 층마다 갈래가 2배씩 늘어난다  ->  2^18 = 262,144 번

  테스트가 못 박는 것

    assertEquals(38, r.visits())
```

```text
작은 예로 감을 잡으면 (DfsResolverTest.everyNodeIsVisitedOnce)

    b   c

      d

                 visits = 4 = 노드 수          assertEquals(4, r.visits())

  검은색을 무시  a(1) -> b(2) -> d(3) -> 돌아옴 -> c(4) -> d(5)
                 visits = 5.  노드는 4개인데 5 다. 답은 여전히 맞다
```

- Q: 계약 테스트로는 왜 안 잡히고 방문 수 측정만 잡는가?\
  A: 계약 테스트가 보는 것은 **답의 성질**이기 때문이다 — 개수, 순서, 이름 집합.\
  중복 방문은 그 셋 중 아무것도 안 건드린다. 답이 똑같이 나온다.\
  32번의 병합 순서(231 대 683), 33번의 `mv` 비용(1 대 341)과 정확히 같은 자리다.\
  **"답이 같고 비용만 다른 선택"은 비용을 세는 자에만 잡힌다.**\
  그리고 여기서는 그 차이가 상수배가 아니라 **지수배**라, 재보지 않으면 운영에서 멈춰서야 안다.

- Q: `layers()` 의 비용은?\
  A: 칸 쪽은 `resolve` 와 같은 `O(V + E)` 다. 층을 통째로 꺼내는 것뿐이라 훑는 양이 같다.\
  DFS 쪽은 `resolve()` 를 한 번 부르고(`O(V + E)`) 그 결과를 한 번 더 훑어 깊이를 계산한다(`O(V + E)`) — 상수배만 더 든다.\
  둘 다 차수는 같고, 다른 것은 **부산물인가 따로 계산해야 하는가**다(질문 5).

> **완화(relaxation)** — 여기서는 "선행 조건 하나가 끝났다"고 진입 차수를 1 내리는 연산.\
> 예: `root` 를 뽑으면 `root → z`, `root → b`, `root → m` 세 간선이 완화되어 셋의 진입 차수가 각각 1 내려간다.

> **세 가지 색(white/gray/black)** — 안 봤다 / 지금 내려가는 중이다 / 다 보고 돌아왔다.\
> 예: 회색을 다시 만나면 순환, 검은색을 다시 만나면 정상(이미 끝난 가지)이다. 둘을 구별하는 것이 이 알고리즘의 전부다.

> **메모이제이션(memoisation)** — 이미 계산한 것을 다시 계산하지 않도록 표시해 두는 것.\
> 예: 검은색 칠하기가 그 표시다. 이것이 없으면 경로 수만큼 내려가 지수가 된다.

> **후위 순서(postorder)** — 자식을 다 본 뒤에 자기를 적는 순서.\
> 예: `a → b → d` 에서 후위는 `d, b, a` 이고, 뒤집으면 `a, b, d` 로 위상 정렬이 된다.

- Q: 왜 후위를 뒤집으면 위상 정렬이 되는가?\
  A: **후위는 "자기 뒤에 와야 하는 것들을 전부 끝낸 뒤에" 자기를 적는 순서**이기 때문이다.\
  그러니까 후위 목록에서 `u` 는 `u` 가 가리키는 모든 노드보다 **뒤**에 있다.\
  뒤집으면 `u` 가 그것들보다 **앞**에 오고, 그게 정확히 위상 정렬의 조건이다.

```text
손으로 따라가기 : a -> b, a -> c, b -> d, c -> d

  walk(a)  a 회색
    walk(b)  b 회색
      walk(d)  d 회색 -> 자식 없음 -> d 검은색, postorder = [d]
      b 검은색, postorder = [d, b]
    walk(c)  c 회색
      d 는 검은색 -> 안 내려감
      c 검은색, postorder = [d, b, c]
    a 검은색, postorder = [d, b, c, a]

  뒤집으면 [a, c, b, d]
  간선 확인: a -> b (a 가 앞), a -> c (앞), b -> d (앞), c -> d (앞). 전부 맞다

  칸 알고리즘은 같은 그래프에 [a, b, c, d] 를 낸다 (사전순 최소).
  둘 다 맞다. 그래서 assertIsTopologicalOrder 로만 검증한다.
```

- Q: `DfsResolver.cycle()` 의 비용은?\
  A: `resolve()` 를 **한 번 더 돌린다**. 순환이면 예외를 잡아 경로를 꺼내고, 아니면 빈 목록을 준다.

```java
// impl/DfsResolver.java
public List<String> cycle() {
    try {
        resolve();
        return List.of();
    } catch (CycleException e) {
        return e.path();
    }
}
```

  그래서 `resolve()` 가 던진 뒤 `cycle()` 을 또 부르면 전체를 두 번 훑는 셈이다.\
  `layers()` 도 내부에서 `resolve()` 를 부르므로 같은 성격이다.\
  차수가 바뀌지는 않지만(`O(V + E)` 그대로), **캐시하지 않는다는 선택**이 드러나는 자리다.\
  (원본에 근거 없음 — 내 추론) 캐시하면 그래프가 바뀌었을 때 무효화 문제가 생기고, 이 박스의 주제가 아니라서 안 한 것으로 보인다.

**더 생각할 것**

- 색이 셋이어야 하는 이유는 **"다시 만났다"에 두 종류가 있기** 때문이다.\
  회색(내려가는 길 위) = 순환, 검은색(이미 끝남) = 다이아몬드.\
  색이 둘이면 둘을 구별할 수 없고, 다이아몬드를 순환이라고 잘못 보고한다.\
  다행히 그 실수는 **시끄러운 쪽**이다 — 순환이 없는 그래프를 순환이라고 하므로 테스트에 걸린다.
- 반대 실수(순환을 놓치는 것)가 훨씬 나쁘다. 그건 조용한 실패다.\
  "시끄러운 실패가 조용한 실패보다 낫다"가 `DfsResolver` 주석에 그대로 적혀 있다.
- 지수 폭발은 **입력이 작을 때는 절대 안 보인다**.\
  노드 4개짜리 다이아몬드에서는 4 대 5 다. 눈에 안 띈다.\
  18층이 되면 38 대 262,144 다. 그래서 측정 테스트가 일부러 18층을 세운다.

#### 4. 최악·최선의 입력 · 층 수가 왜 못 줄이는 시간인가

- Q: 노드 100개를 세 모양으로 세우면 층이 각각 몇인가?\
  A: 사슬 100, 이진 트리 7, 전부 독립 1 이다. 셋 다 테스트가 못 박는다.

```java
// src/test/.../MeasurementTest.java — shapeDecidesParallelism
for (Resolver r : List.of(new KahnResolver(chain(100)), new DfsResolver(chain(100)))) {
    assertEquals(100, r.layers().size(), "사슬은 한 줄이라 못 줄인다");
}
assertEquals(7, treeLayers);     // binaryTree(100)
assertEquals(1, flatLayers);     // independent(100)
```

```text
같은 노드 100개, 모양만 다르다

  사슬 (chain)              n000 -> n001 -> n002 -> ... -> n099
                            층 100. 한 층에 하나씩이다

  이진 트리 (binaryTree)         n000
                              +--+--+
                            n001   n002
                            +-+-+  +-+-+
                          n003 n004 n005 n006  ...
                            층 7. 노드 99 에서 부모를 따라 올라가면
                            99 -> 49 -> 24 -> 11 -> 5 -> 2 -> 0 (간선 6개) = 0층~6층 = 7층

  전부 독립 (independent)    n000  n001  n002  ...  n099   (간선 0개)
                            층 1. 전부 0층이다

  층 수 = 가장 긴 사슬의 길이 = 임계 경로(critical path)
```

- Q: 층 수가 왜 "코어를 아무리 늘려도 못 줄이는 시간"인가?\
  A: **한 층 안의 노드들은 서로 의존이 없어서 동시에 할 수 있지만, 다음 층은 앞 층이 다 끝나야 시작할 수 있기** 때문이다.\
  그래서 코어가 무한히 많아도 걸리는 시간은 층 수다.\
  사슬 100 이면 코어가 100개여도 100 단위 시간이다 — n001 은 n000 이 끝나야 시작하니까.\
  전부 독립이면 코어 100개로 1 단위 시간이다.\
  이것을 임계 경로(critical path)라고 부른다. 계약 테스트가 층의 성질로 보증하는 것이 정확히 이 구조다.

```java
// src/test/.../ResolverContractTest.java — 층의 성질
for (String name : graph.names()) {
    for (String next : graph.after(name)) {
        assertTrue(layerOf.get(name) < layerOf.get(next), ...);
    }
}
```

- Q: 독립 200개에 길이 31짜리 사슬 하나를 붙이면?\
  A: 0층에 201개가 몰리는데 **전체는 31층**이다. 노드의 87%가 첫 층인데 시간은 31 단위다.

```java
// src/test/.../MeasurementTest.java — oneLongChainHoldsEverything
DependencyGraph g = independent(200);
assertEquals(1, new KahnResolver(g).layers().size());

for (int i = 0; i < 30; i++) {
    g.dependsOn("chain" + (i + 1), "chain" + i);
}
List<List<String>> after = new KahnResolver(g).layers();

assertEquals(31, after.size());
assertEquals(201, after.get(0).size(), "독립 200개 + 사슬의 머리");
for (int i = 1; i < after.size(); i++) {
    assertEquals(1, after.get(i).size(), i + "층");
}
```

```text
층의 모양을 그림으로

  0층 : [독립 200개 전부] + [chain0]          201개  <- 전체 231개의 87%
  1층 : [chain1]                                1개
  2층 : [chain2]                                1개
  ...
  30층: [chain30]                               1개

  총 231 노드, 31 층.
  코어를 231개 줘도 31 단위 시간이 걸린다. 사슬 하나가 전부를 붙든다.
  87% 를 1 단위에 끝내고, 나머지 13% 때문에 30 단위를 더 기다린다.
```

- Q: 25번·30번의 "평균이 아니라 최악이 정한다"와 어떻게 같은 자리인가?\
  A: **전체를 요약한 수(평균, 총합)가 실제 성능과 아무 상관이 없다**는 점이 같다.\
  25번 공간 색인에서 평균 거리가 아무리 좋아도 "모든 점이 같은 거리"인 질의 하나가 전수 조사가 됐다.\
  30번 구간 트리에서 평균 결과 크기가 작아도 "결과가 크면 진다"는 질의 하나가 전체를 훑었다.\
  여기서는 **평균 층 크기(231/31 ≈ 7.5)** 가 완전히 무의미하다 — 시간을 정하는 것은 층의 개수, 즉 가장 긴 사슬 하나다.\
  일반화하면 **병목은 평균에 안 나타난다**. 최악의 경로, 최악의 질의, 최악의 요청 하나가 정한다.

- Q: 최선의 입력과 최악의 입력을 정리하면?\
  A: 최선 — **전부 독립**. 층 1, 병렬화가 완전하고, `relaxations` 도 0 이다(간선이 없으니까).\
  최악(병렬성 기준) — **사슬**. 층이 노드 수와 같고, 코어를 늘려도 못 줄인다.\
  최악(DFS 방문 수 기준, 색을 안 쓸 때) — **겹친 다이아몬드**. 노드 38개에 방문 262,144 번.\
  그리고 `resolve()` 자체의 비용은 어떤 모양이든 `O(V + E)` 로 같다는 것도 기억할 것 — 모양이 정하는 것은 **병렬성**이지 순차 수행 비용이 아니다.

> **임계 경로(critical path)** — 그래프에서 가장 긴 의존 사슬. 무한한 병렬성이 있어도 이 길이만큼은 걸린다.\
> 예: 독립 200개 + 사슬 31개짜리 그래프의 임계 경로는 31 이고, 그래서 층이 31 이다.

> **층(layer)** — 서로 의존이 없어 동시에 할 수 있는 노드들의 묶음. 위상 정렬의 "동시 실행 가능 단위"다.\
> 예: 0층은 아무것에도 안 기대는 것들, 1층은 0층만 끝나면 되는 것들이다.

- Q: 모양이 `resolve()` 자체의 비용도 바꾸는가?\
  A: **안 바꾼다.** 셋 다 `O(V + E)` 다.\
  사슬 100 이든 독립 100 이든, 노드를 한 번씩 보고 간선을 한 번씩 훑는 양은 같다.\
  달라지는 것은 **순차로 계산하는 비용**이 아니라 **병렬로 실행할 때의 하한**이다.\
  둘을 섞으면 "사슬이라 위상 정렬이 느리다" 같은 틀린 결론이 나온다.

```text
두 가지 시간을 구별하라

  (1) 순서를 계산하는 시간          resolve() 의 비용.  모양과 무관하게 O(V + E)
  (2) 그 순서대로 실행하는 시간      층 수가 정하는 하한.  모양이 전부

  이 박스가 재는 relaxations / visits 는 (1) 의 자다
  layers().size() 는 (2) 의 자다

  MeasurementTest.neitherRevisits 가 (1) 을, CriticalPath 가 (2) 를 본다
  둘을 같은 테스트에 섞지 않은 것도 설계다
```

- Q: 이진 트리 100개에서 `relaxations` 가 99 인 이유는?\
  A: 간선이 99개이기 때문이다 — `binaryTree(100)` 은 `i = 1..99` 에 대해 `dependsOn(name(i), name((i-1)/2))` 를 걸어 간선 99개를 만든다.\
  트리에서 노드 `n` 개면 간선이 `n - 1` 개라는 성질 그대로다.\
  그리고 같은 그래프에서 `visits` 는 100 이다 — 노드 수.\
  **구조가 다른 것이 아니라 세는 대상이 다르다.** 둘 다 `O(V + E)` 다.

**더 생각할 것**

- `layers()` 가 `resolve()` 보다 실무에서 더 쓸모 있는 경우가 많다.\
  `resolve()` 는 "한 줄로 세운 순서" 하나를 주는데, 실제로는 병렬로 돌리고 싶기 때문이다.\
  층을 알면 "이 층을 전부 병렬로, 끝나면 다음 층" 이라는 실행 계획이 바로 나온다.
- 그래서 "얼마나 빨라질 수 있나"를 묻는 것은 층 수를 묻는 것과 같다.\
  빌드 시간을 줄이려면 코어를 늘리는 게 아니라 **가장 긴 의존 사슬을 짧게** 만들어야 한다.\
  의존을 끊는 리팩토링이 하드웨어 추가보다 효과가 큰 이유다.
- 층 수는 두 알고리즘이 **같은 값**을 낸다. `assertEquals(new KahnResolver(...).layers(), new DfsResolver(...).layers())` 가 그것을 못 박는다.\
  답(`resolve`)은 여럿인데 층은 하나로 정해지기 때문이다 — 층은 그래프의 성질이지 알고리즘의 선택이 아니다.

#### 5. 두 구현의 트레이드오프 — 답이 다른데 둘 다 맞을 때의 검증

- Q: 같은 그래프에서 답이 다른데 둘 다 맞다면 무엇으로 검증하는가?\
  A: **답이 아니라 성질을 검사한다.** 셋이다.

```java
// src/test/.../ResolverContractTest.java — assertIsTopologicalOrder
List<String> names = graph.names();
assertEquals(names.size(), order.size(), "개수가 다르다: " + order);
assertEquals(new HashSet<>(names), new HashSet<>(order), "이름 집합이 다르다: " + order);
assertEquals(order.size(), new HashSet<>(order).size(), "중복이 있다: " + order);

java.util.Map<String, Integer> position = new java.util.HashMap<>();
for (int i = 0; i < order.size(); i++) {
    position.put(order.get(i), i);
}
for (String name : names) {
    for (String next : graph.after(name)) {
        assertTrue(position.get(name) < position.get(next), ...);
    }
}
```

```text
성질 세 가지

  1. 모든 노드가 정확히 한 번씩 있다     개수 + 집합 + 중복 없음, 셋으로 나눠 본다
  2. 앞에 와야 하는 것이 실제로 앞에 있다  간선마다 위치를 비교한다
  3. 없는 이름이 섞이지 않았다            집합 비교가 이것도 같이 본다
```

- Q: 2번("앞에 와야 하는 것이 앞에 있다")만 보면 왜 안 되는가?\
  A: **노드를 통째로 빠뜨린 구현이 통과하기** 때문이다.\
  빠진 것은 순서를 어기지 않는다 — 없으니까 비교할 일이 없다.\
  극단적으로 **빈 목록**을 돌려주는 구현도 2번만 보면 완벽하다.\
  그래서 "빠진 게 없다"를 보는 1번이 반드시 같이 있어야 한다.

```text
2번만 보는 테스트를 통과하는 가짜 구현

  resolve() { return List.of(); }             빈 목록. 어길 간선이 없다 -> 통과
  resolve() { return List.of("root"); }       하나만. 역시 어길 것이 없다 -> 통과

  1번(개수 + 집합)이 들어오면 둘 다 즉시 실패한다.

  같은 함정이 layers 검증에도 있다.
  assertLayersAreValid 가 total 을 세어 graph.size() 와 비교하고,
  빈 층이 없는지도 따로 본다 ("층이 비었다").
```

- Q: 순환일 때 두 구현이 말해줄 수 있는 것이 왜 다른가?\
  A: **순환을 알아채는 방식이 다르기** 때문이다.\
  칸은 "다 못 뽑았다"로 안다 — 남은 것이 순환에 **연루된** 것들이라는 것까지는 아는데, 그중 어느 것이 실제로 도는 고리인지는 모른다.\
  순환 하나에 딸린(그 순환 뒤에 오는) 나머지도 전부 남기 때문이다.\
  DFS 는 "지금 내려온 길 위에서 다시 만났다"로 안다 — **그 길이 곧 고리**다.

```java
// impl/DfsResolver.java — 회색을 만나면 경로를 잘라낸다
if (c == GRAY) {
    // 지금 내려온 길 위에서 다시 만났다. 그 지점부터 여기까지가 도는 고리다.
    int from = path.indexOf(next);
    List<String> loop = new ArrayList<>(path.subList(from, path.size()));
    loop.add(next);         // 처음과 끝을 같게 해서 고리임을 드러낸다
    foundCycle = List.copyOf(loop);
    return false;
}
```

```java
// impl/KahnResolver.java — 모르는 것을 아는 척하지 않는다
/** 이 구현은 경로를 모른다. 빈 목록이 그 뜻이다. */
public List<String> cycle() {
    return List.of();
}
```

```text
MeasurementTest.onlyDfsLocatesTheCycle — 노드 104개 중 순환은 셋

  noise0 -> noise1 -> ... -> noise100     (정상 사슬 101개)
  a -> c, b -> a, c -> b                  (고리 셋: a -> b -> c -> a 방향)

  칸    path = []            assertEquals(0, byKahn.path().size())
  DFS   path = [a, b, c, a]  assertEquals(4, byDfs.path().size())
                             assertTrue(byDfs.path().containsAll(List.of("a","b","c")))
                             그리고 noise 가 하나도 안 섞였는지도 본다

  그래프가 아무리 커도 DFS 가 주는 경로는 순환의 크기만큼이다. 건초더미 속의 바늘을 짚는다.
```

- Q: 진단 능력의 차이가 왜 정상 동작 테스트로는 안 드러나는가?\
  A: 정상 동작에서는 **둘 다 예외를 안 던지므로 진단할 것이 없기** 때문이다.\
  차이는 실패 경로에만 있다. 그래서 실패 경로를 일부러 만드는 테스트가 따로 있어야 한다.\
  README 가 "두 알고리즘의 차이가 답이 아니라 진단 능력에 있다"고 적은 이유다.

- Q: `path` 에서 자기를 빼는 코드가 왜 필요한가?\
  A: **이미 끝난 가지가 고리 보고에 섞이는 것**을 막는다.

```java
// impl/DfsResolver.java — 돌아올 때 경로에서 자기를 뺀다
path.remove(path.size() - 1);
color.put(name, BLACK);
postorder.add(name);
```

```text
DfsResolverTest.completedBranchesAreNotPartOfTheCycle

  a -> n              (내려갔다 그냥 돌아온다)
  a -> p -> q -> a    (여기가 진짜 고리다)

  path 의 변화
    a 진입          path = [a]
    n 으로 내려감   path = [a, n]
    n 에서 돌아옴   path = [a]        <- 여기서 n 을 빼야 한다
    p 로 내려감     path = [a, p]
    q 로 내려감     path = [a, p, q]
    q 에서 a 를 만남 (회색) -> path.indexOf("a") = 0 -> [a, p, q] + a = [a, p, q, a]

  n 을 안 빼면 path = [a, n, p, q] 가 되어 보고가 [a, n, p, q, a] 로 나온다
  예외는 여전히 나지만 진단이 틀린다. 있지도 않은 고리를 가리킨다

  assertTrue(!path.contains("n"), "끝난 가지가 섞였다")

  그 상황을 만들려면 "고리로 내려가는 길에 먼저 끝나는 가지" 가 있어야 해서
  그 그래프를 따로 만들어 넣었다.
```

- Q: `layers` 가 한쪽에서는 부산물이고 다른 쪽에서는 따로 계산해야 하는 이유는?\
  A: **칸 알고리즘은 이미 층 단위로 일하고 있기** 때문이다.\
  진입 차수가 0 인 것들을 하나씩 꺼내는 대신 **그 시점의 것을 통째로** 꺼내면 그게 한 층이다. 알고리즘의 모양을 거의 안 바꾼다.\
  DFS 는 깊이 방향으로 내려가므로 "동시에 할 수 있는 것들"이라는 개념이 순서 어디에도 안 나타난다.\
  그래서 후위 순서를 한 번 더 훑으며 `깊이 = max(기대는 것들의 깊이) + 1` 을 계산해야 한다.

```java
// impl/KahnResolver.java — 층이 부산물이다
while (!ready.isEmpty()) {
    // 이 층을 통째로 확정한 뒤에 다음 층을 만든다.
    // 한 개씩 처리하면서 새로 0 이 된 것을 같은 층에 넣으면 층이 뭉개진다.
    List<String> layer = List.copyOf(ready);
    out.add(layer);
    ...
}
```

```java
// impl/DfsResolver.java — 층을 따로 계산한다
for (String name : order) {
    int mine = depth.getOrDefault(name, 0);
    for (String next : graph.after(name)) {
        depth.merge(next, mine + 1, Math::max);
    }
    deepest = Math.max(deepest, mine);
}
```

- Q: 층을 잘못 나눠도 펼쳐놓으면 순서가 맞는다는 것은 무슨 뜻인가?\
  A: 층을 잘게 쪼개거나 뭉개도 **평탄화한 목록은 여전히 위상 정렬**일 수 있다는 뜻이다.\
  예를 들어 층을 노드 하나씩 100개로 쪼개면 순서는 완벽하지만 층 나누기로서는 완전히 틀렸다(병렬성을 0 으로 보고한 것).\
  그래서 `assertLayersAreValid` 는 **층 안의 관계**를 따로 본다 — 간선의 양 끝이 반드시 다른 층이어야 하고, 앞 층이 더 앞이어야 한다.\
  칸 구현의 주석이 "한 개씩 처리하면서 새로 0 이 된 것을 같은 층에 넣으면 층이 뭉개진다"고 경고하는 것이 반대 방향의 실수다.

- Q: `TreeMap`/`TreeSet` 과 `PriorityQueue` 가 왜 취향이 아니라 계약인가?\
  A: **답이 여럿인 문제에서 자료구조의 순회 순서가 곧 답의 순서가 되기** 때문이다.\
  `HashMap` 을 쓰면 같은 입력에 같은 답이 나온다는 보장이 없고, 그러면 기댓값을 쓸 수 없다.\
  `DependencyGraph` 는 `TreeMap`/`TreeSet` 으로 이름 순회를 오름차순으로 고정한다.\
  `KahnResolver` 는 `PriorityQueue` 로 "꺼낼 것이 여럿일 때 이름이 작은 것부터"를 고정한다.\
  그 결과 칸의 답은 **사전순으로 가장 이른 위상 정렬** 하나로 정해진다.

```java
// src/test/.../KahnResolverTest.java — 이 구현만의 보장
DependencyGraph g = graphOf("a <- z", "a <- b", "a <- m");
// z, b, m 은 서로 상관없다. 어느 순서든 맞는데 이 구현은 b, m, z 로 고정한다.
assertEquals(List.of("a", "b", "m", "z"), new KahnResolver(g).resolve());
```

> **재현성(determinism)** — 같은 입력에 언제 어디서 돌려도 같은 출력이 나오는 성질.\
> 예: `HashMap` 순회 순서는 JDK 판에 따라 달라질 수 있어서, 그 위에 세운 기댓값은 언젠가 깨진다.

> **성질 검사(property-based assertion)** — 값을 못 박는 대신 "답이 반드시 만족해야 할 조건"을 검사하는 방식.\
> 예: "모든 노드가 한 번씩" + "간선마다 앞이 앞에" 를 보면, 답이 여럿이어도 옳음을 판정할 수 있다.

> **진단 능력(diagnosability)** — 실패했을 때 원인을 얼마나 정확히 말해줄 수 있는가.\
> 예: "순환이 있다"와 "순환이 a → b → c → a 다"는 둘 다 맞는 실패인데, 고치는 사람에게는 완전히 다른 값이다.

- Q: 고리가 둘 있으면 DFS 는 무엇을 주는가?\
  A: **먼저 만난 하나**만 준다. 둘 다 주려면 강한 연결 요소를 구해야 하고, 그건 이 박스의 범위 밖이다.

```java
// src/test/.../DfsResolverTest.java
DependencyGraph g = graphOf("a <- b", "b <- a", "x <- y", "y <- x");
List<String> path = new DfsResolver(g).cycle();
assertEquals(3, path.size(), path.toString());
assertEquals(path.get(0), path.get(2));
```

  이것도 정직한 한계 표시다 — "하나는 확실히 짚어준다"가 계약이고, "전부 찾아준다"는 약속하지 않는다.\
  그리고 예외 메시지에 경로를 실어 보낸다(`messageCarriesThePath` 가 `->` 와 이름이 들어 있는지 확인한다).\
  받는 쪽이 **고칠 수 있어야** 진단이 뜻이 있기 때문이다.

- Q: 테스트 구조에서 주의할 점이 하나 적혀 있는데?\
  A: 하위 클래스에서 `@Nested` 클래스 이름을 상위와 같게 지으면 **상위 테스트가 실패가 아니라 조용히 사라진다**.

```java
// src/test/.../KahnResolverTest.java 의 주석
// @Nested 클래스를 새로 만들지 않는다. 상위와 이름이 겹치면 상위 테스트가
// 실패가 아니라 조용히 사라진다.
```

  이 박스 전체의 주제("조용한 실패가 제일 나쁘다")가 테스트 코드 자체에서 한 번 더 반복되는 자리다.\
  검증 장치도 조용히 망가질 수 있고, 그때는 초록불이 아무 뜻이 없다.

|---|---|---|
| 답 | 사전순 최소 하나로 고정 | 노드 순회 순서에 따른 다른 답 |
| 비용 | `relaxations` = 간선 수 | `visits` = 노드 수 (둘 다 `O(V+E)`) |
| 순환 진단 | 있다는 것만 (`cycle()` 이 빈 목록) | 도는 경로까지 (`[a, b, c, a]`) |
| `layers` | 부산물 — 같은 루프에서 나온다 | 따로 계산 — 후위 순서를 한 번 더 훑는다 |
| 구현 난도 | 진입 차수 관리만 | 색 셋 + 경로 스택 관리 |
| 재귀 | 없음(반복문) | 있음(깊은 그래프에서 스택 위험) |

- "둘 다 맞는데 다르다"는 상황은 실무에서 생각보다 흔하다 — 해시 순회, 부동소수점 합, 동점 처리, 병렬 실행 순서.\
  그때마다 선택지는 둘이다: **답을 하나로 고정하는 규칙을 얹거나**(여기서는 사전순 최소), **답 대신 성질을 검사하거나**.\
  이 박스는 둘을 다 쓴다 — 계약은 성질로 보고, 구현별 보장은 값으로 못 박는다.
- 그리고 **어느 구현만의 보장은 그 구현의 테스트 파일에 둔다**는 원칙이 지켜져 있다.\
  사전순 최소는 `KahnResolverTest` 에, 순환 경로는 `DfsResolverTest` 에 있다.\
  공통 계약에 넣으면 다른 구현이 지킬 수 없는 것을 요구하게 된다.

#### 6. 이 구조의 한계가 다음 구조를 어떻게 부르는가 — 35-allocator

- Q: 34번이 답한 것과 35번이 답하는 것은?\
  A: 34번은 **"무엇을 먼저 할 것인가"** 에 답한다 — 시간 축의 순서.\
  35번은 **"어디에 놓을 것인가"** 에 답한다 — 공간 축의 자리.\
  둘은 직교한다. 순서를 완벽히 정해도 자리 문제는 그대로 남는다.

- Q: 순서가 정해진 뒤에도 남는 "빈 자리 관리"라는 문제는 무엇인가?\
  A: 순서대로 일을 하면 **그 일들이 공간을 잡았다 놓았다 한다**.\
  34번은 "n001 을 n000 다음에 하라"까지만 말한다. n001 이 실행되면서 메모리를 얼마나 잡고 언제 놓는지는 안 본다.\
  그런데 실제로는 그것이 병목이 된다 — 순서가 완벽해도 **놓을 자리가 없으면 못 한다**.\
  그리고 그 실패는 "총량이 부족해서"가 아니라 **"연속된 자리가 없어서"** 일어난다.\
  35번의 첫 문장이 그것이다: 남은 공간이 512인데 17을 못 준다.

```text
34 -> 35 로 넘어가는 자리

  34 가 답한 것
    작업 순서 = [n000, n001, n002, ...]
    "이 순서로 하면 제약을 다 지킨다"

  34 가 답하지 않은 것
    n000 이 100 바이트를 잡았다가 놓는다
    n001 이 200 바이트를 잡는다
    n002 가 150 바이트를 잡는다 ... 그 자리는 어디여야 하는가?

    잡았다 놓았다를 반복하면 남은 공간이 조각조각 흩어진다
    총량은 충분한데 연속된 자리가 없어서 실패한다  <- 외부 단편화

  즉 34 의 출력(순서)이 35 의 입력(요청 열)이 된다.
  그리고 35 는 그 요청 열에 대해 "어디를 떼어줄지" 를 고르는 문제다.
```

- Q: 34번과 35번의 검증 방식은 어떻게 이어지는가?\
  A: 34번에서 **"답이 여럿이라 대조가 성립하지 않는다"** 는 벽을 만났고, 그래서 성질 검사로 갔다.\
  35번에서는 벽이 한 겹 더 두껍다 — **다섯 구현이 계약을 다 통과하는데 무엇이 갈리는지가 계약 밖에 있다**.\
  거기서 갈리는 것은 답도 아니고 순서도 아니고, **한참 쓰고 난 뒤의 모양**(단편화)이다.\
  그래서 35번은 자를 여섯 개(`freeBytes`, `largestFreeBlock`, `freeBlockCount`, `wastedBytes`, `scanned`, `usedBytes`)나 둔다.\
  32번은 자가 둘(`visitedDocs`, `comparisons`), 33번도 둘(`visitedNodes`, `rewrittenEntries`), 34번도 둘(`relaxations`, `visits`)이었다.\
  **재야 할 것이 많아질수록 자가 늘어난다**는 흐름이 박스를 관통한다.

- Q: 34번이 35번에 넘겨주는 개념이 또 있는가?\
  A: 둘 있다.\
  하나 — **"그럴듯한 이유가 양쪽에 다 있는데 결과가 갈린다"**.\
  34번에서는 두 알고리즘이 둘 다 맞았고, 35번에서는 best fit("큰 자리를 아끼자")과 worst fit("남는 조각을 크게 만들자")이 둘 다 그럴듯한데 재보면 제일 단순한 first fit 이 이긴다.\
  둘 다 **재기 전에는 모른다**는 같은 교훈이다.\
  둘 — **부분 결과의 위험**.\
  34번은 순환일 때 부분 순서를 주지 않는다. 35번은 이중 free 를 조용히 넘어가지 않는다.\
  둘 다 "조용히 넘어가면 손상이 한참 뒤에 드러난다"가 이유다.

> **직교(orthogonal)** — 두 문제가 서로의 답에 영향을 주지 않아 따로 풀 수 있는 관계.\
> 예: 실행 순서를 바꿔도 "어디에 놓을지"라는 문제는 그대로 남는다. 다만 요청이 오는 순서는 바뀐다.

> **외부 단편화(external fragmentation)** — 남은 총량은 충분한데 연속된 자리가 없어서 요청이 실패하는 상태.\
> 예: 16바이트 빈 자리 32개(총 512)가 있어도 17바이트 요청은 실패한다.

**더 생각할 것**

- 이 문제집의 마지막 두 박스가 "순서"와 "자리"인 것은 우연이 아니다.\
