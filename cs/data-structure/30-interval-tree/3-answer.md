### A. 문제

#### 1. 겹치거나 맞닿은 구간 합치기 — `merge`

**접근 1 — 두 개씩 짝지어 합칠 수 있으면 합치기를 반복한다** (정렬을 안 하면 이렇게 된다)

```java
// 의사코드 — 정렬 없이 하면 몇 번을 돌아야 하는지 모른다
boolean changed = true;
while (changed) {
    changed = false;
    for (모든 쌍 (a, b)) {
        if (합칠 수 있으면) { 합치고 changed = true; }
    }
}
```

- 한계: 한 번 훑어서 끝나지 않는다 — 합친 결과가 또 다른 구간과 합쳐질 수 있어 몇 바퀴를 돌지 모른다.
- 비용(왜): 쌍이 `n²` 개이고 그것을 여러 바퀴 도니 최악 `O(n³)` 까지 간다.
- 한계: "합칠 수 있으면"의 순서가 결과에 영향을 주지 않는다는 것을 따로 논증해야 한다.

**접근 2 — 시작점으로 정렬한 뒤 한 번만 훑는다** (impl 의 정답)

```java
List<Interval> sorted = new ArrayList<>(intervals);
Collections.sort(sorted);       // start 오름차순. 이게 없으면 한 번 훑기가 성립하지 않는다

long curStart = sorted.get(0).start;
long curEnd = sorted.get(0).end;
for (int i = 1; i < sorted.size(); i++) {
    Interval next = sorted.get(i);
    if (next.start <= curEnd) {
        curEnd = Math.max(curEnd, next.end);     // 통째로 들어간 구간이 있으므로 max 다
    } else {
        out.add(new Interval(curStart, curEnd));
        curStart = next.start;
        curEnd = next.end;
    }
}
out.add(new Interval(curStart, curEnd));         // 마지막 하나가 남는다
```

```
  [1,4)  [3,6)  [8,10)  [9,12)  [15,20)  [12,13)   를 정렬한다
  -> [1,4) [3,6) [8,10) [9,12) [12,13) [15,20)

  cur = [1,4)
   [3,6)  : 3 <= 4  -> 합친다, cur = [1, max(4,6)) = [1,6)
   [8,10) : 8 >  6  -> [1,6) 을 내보내고 cur = [8,10)
   [9,12) : 9 <= 10 -> cur = [8,12)
   [12,13): 12 <= 12 -> **맞닿았다. 합친다** cur = [8,13)
   [15,20): 15 > 13 -> [8,13) 내보내고 cur = [15,20)
  끝: [15,20) 내보낸다

  결과 [1,6) [8,13) [15,20)
```

- 논리: 정렬하면 "앞으로 올 구간의 시작은 모두 지금 시작 이상"이라는 성질이 생긴다.\
  그래서 지금 뭉치와 안 겹치면 **앞으로도 영영 안 겹친다** — 그 순간 뭉치를 확정해 내보낼 수 있다.
- 논리: `Math.max` 가 필요한 이유는 **통째로 들어간 구간** 때문이다.\
  `[1,10)` 다음에 `[2,3)` 이 오면 `curEnd` 를 3으로 줄이면 안 된다.
- 비용(왜): 정렬 `O(n log n)` + 한 번 훑기 `O(n)` = **`O(n log n)`**.\
  지배항이 정렬이라 훑기를 아무리 최적화해도 차수가 안 바뀐다.
- 논리: 결과끼리는 절대 안 붙는다 — 테스트가 `merged.get(i-1).end < merged.get(i).start` 로 그것을 단언한다.

> **반개구간(half-open interval)** — 시작은 포함하고 끝은 포함하지 않는 구간 `[start, end)`.\
> 예: `[9,11)` 은 9시부터 11시 직전까지이고 11시는 안 들어간다.

**합치는 조건이 `overlaps` 와 어디서 갈라지는가**

```java
// Interval.overlaps — 등호가 없다
return this.start < other.end && other.start < this.end;

// merge 의 합치기 조건 — 등호가 있다
if (next.start <= curEnd) { ... }
```

```
  [9,11) 과 [11,13)

  겹치나?            9 < 13 이고 11 < 11 이 아니다  -> **안 겹친다**
  합쳐야 하나?       11 <= 11                       -> **합쳐야 한다**

  왜 다른가: 두 구간이 덮는 점의 집합을 보면
      [9,11) = {9, 10}          [11,13) = {11, 12}
      합집합 = {9, 10, 11, 12} = [9,13) 과 정확히 같다
  반개구간이라 11 이 딱 한 번만 들어가서 빈틈이 없다.
  그래서 "겹친다"와 "합쳐도 같은 집합이다"가 다른 질문이 된다.
```

- 즉 `overlaps` 는 **공유하는 점이 있나**를 묻고, `merge` 는 **이어 붙이면 틈이 없나**를 묻는다.\
  맞닿은 두 구간은 앞의 답이 아니오, 뒤의 답이 예다.
- 이 구별이 회의실 예약에서 실제 의미를 갖는다 — `[9,11)` 과 `[11,13)` 은 **붙여 잡을 수 있는** 두 회의이고, 그럼에도 달력에 표시할 때는 `[9,13)` 한 블록으로 그리는 것이 맞다.

**질문별 답**

- Q: 문제 1을 어떻게 푸는가?\
  A: 시작점으로 정렬하고 뭉치 하나(`curStart`, `curEnd`)를 들고 한 번 훑으며, `next.start <= curEnd` 면 `curEnd = max(curEnd, next.end)` 로 늘리고 아니면 뭉치를 확정해 내보낸다.\
  루프가 끝나면 마지막 뭉치 하나가 손에 남아 있으므로 그것을 내보내야 한다(빠뜨리기 쉬운 자리다).
- Q: 복잡도는 왜 그런가?\
  A: 정렬 `O(n log n)` 이 지배하고 훑기는 `O(n)` 이다.\
  훑기가 한 번으로 끝나는 근거는 정렬이 만들어준 "앞으로 올 시작은 전부 지금 시작 이상"이라는 성질이다 — 정렬이 알고리즘의 절반이다.
- Q: 합치는 조건이 `overlaps` 와 어디서 갈라지는가?\
  A: **맞닿은 경우(`next.start == curEnd`)** 에서 갈라진다 — `overlaps` 는 거짓, `merge` 는 참이다.\
  반개구간이라 경계점이 한 번만 들어가 두 구간의 합집합에 틈이 없기 때문이다.

**더 생각할 것**

- 이 문제에는 트리가 필요 없다 — 정렬 한 번이면 끝난다.\
  README 가 "트리가 필요 없는 문제를 일부러 넣었다"고 적은 이유이고, 질문 4의 주제로 이어진다.
- `merge` 는 "덮는 점의 집합을 보존하는 정규형"을 만드는 연산이다.\
  테스트가 답의 개수(60 → 48)만이 아니라 `pointsOf(given) == pointsOf(merged)` 로 집합 보존을 단언하는 것이 그 관점이다.
- 빽빽한 입력에서는 80개가 2개로 합쳐진다.\
  입력 개수가 아니라 **덮는 모양**이 결과 크기를 정한다.

#### 2. 동시에 겹치는 구간의 최대 개수 — `maxConcurrent`

**접근 1 — 모든 시작점에서 몇 개가 덮는지 센다** (테스트가 대조로 쓰는 방법)

```java
// IntervalProblemsTest.sweepMatchesPointCounting 의 기준선
int byCounting = 0;
for (Interval a : given) {
    int at = 0;
    for (Interval b : given) if (b.contains(a.start)) at++;
    byCounting = Math.max(byCounting, at);
}
```

- 논리: 덮는 개수가 늘어나는 순간은 언제나 **어떤 구간의 시작점**이다 — 그래서 시작점만 검사하면 최댓값을 놓치지 않는다.
- 비용(왜): 쌍을 전부 보므로 `O(n²)` 이다.
- 한계: 답은 맞지만 n 이 커지면 못 쓴다 — 그래서 정답이 아니라 **대조 기준선**으로만 둔다.

**접근 2 — 시작과 끝을 각각 정렬해 스위핑한다** (impl 의 정답)

```java
Arrays.sort(starts);
Arrays.sort(ends);

int best = 0, open = 0, i = 0, j = 0;
while (i < n) {
    if (starts[i] < ends[j]) {
        open++;
        best = Math.max(best, open);
        i++;
    } else {
        open--;
        j++;
    }
}
return best;
```

```
회의 [9,11), [10,12), [14,15)

  starts = [9, 10, 14]        ends = [11, 12, 15]
  시간축을 왼쪽에서 오른쪽으로 훑으며 "지금 열려 있는 회의 수"를 센다

   9  : starts[0]=9  <  ends[0]=11  -> open 1  (best 1)
  10  : starts[1]=10 <  ends[0]=11  -> open 2  (best 2)
  11  : starts[2]=14 >= ends[0]=11  -> open 1        끝을 처리
  12  : starts[2]=14 >= ends[1]=12  -> open 0        끝을 처리
  14  : starts[2]=14 <  ends[2]=15  -> open 1
  i 가 끝까지 갔으므로 종료. best = 2
```

- 논리: 구간 객체를 정렬하는 것이 아니라 **시작 배열과 끝 배열을 따로** 정렬한다.\
  어차피 "언제 하나 열리고 언제 하나 닫히는가"만 알면 되고, 어느 구간의 것인지는 필요 없다.
- 논리: `open` 이 최대가 되는 순간은 항상 **시작을 처리한 직후**라 `best` 갱신을 그 가지에서만 한다.
- 논리: `while (i < n)` 이면 충분하다 — 시작을 다 처리하고 나면 `open` 은 줄기만 하므로 `best` 가 더 커질 수 없다.
- 비용(왜): 정렬 두 번 `O(n log n)` + 훑기 `O(n)` = **`O(n log n)`**, 추가 공간 `O(n)`.

> **스위핑(sweep line)** — 좌표축을 한 방향으로 훑으며 "열림/닫힘" 이벤트를 순서대로 처리하는 기법.\
> 예: 시작 이벤트에서 `open++`, 끝 이벤트에서 `open--` 를 하고 그 최댓값을 본다.

**좌표가 같을 때 무엇을 먼저 처리해야 하는가**

```java
if (starts[i] < ends[j]) { open++; ... }   // 등호가 없다 = 같으면 else 로 간다 = **끝을 먼저**
else                     { open--; ... }
```

```
이어달리기 회의 넷 : [0,10) [10,20) [20,30) [30,40)

  끝을 먼저 (지금 코드, starts[i] < ends[j])
     0 : open 1                          10 : ends 먼저 -> open 0, 그다음 starts -> open 1
     ...                                 답 = 1   (회의실 하나면 된다)

  시작을 먼저 (starts[i] <= ends[j] 로 바꾼 변종)
     10 시에 새 회의를 먼저 열고 나서 옛 회의를 닫는다 -> 순간적으로 open 2
     답 = 2   (회의실 두 개가 필요하다고 나온다)

  IntervalProblemsTest.touchingMeetingsNeedOneRoom
      assertEquals(1, maxConcurrent(of(0,10, 10,20, 20,30, 30,40)),
              "이어달리기 회의 넷. 등호를 넣으면 2 가 나온다");
      assertEquals(1, maxConcurrent(of(9,11, 11,13)));
```

- Q: 어긋나면 어떤 답이 나오는가?\
  A: **붙여 잡은 회의가 겹친다고 나와 방이 하나 더 필요하다는 답**이 된다.\
  이어달리기 회의 넷에서 1 이 아니라 2 가 나오고, 회의가 길게 이어질수록 오차가 커지는 것이 아니라 **항상 딱 하나만 커진다**는 점이 더 위험하다 — 눈에 안 띈다.
- Q: 왜 끝이 먼저여야 하는가?\
  A: **반개구간이기 때문**이다.\
  `[9,11)` 은 11시를 포함하지 않으므로 11시에는 이미 끝난 회의이고, 같은 11시에 시작하는 회의와 한 순간도 공존하지 않는다.\
  닫힌 구간 `[9,11]` 이었다면 11시에 둘이 실제로 겹치므로 반대로 시작을 먼저 처리해야 맞다 — **이벤트 순서는 구간의 정의에서 따라 나오는 것**이지 취향이 아니다.

**셋의 부등호가 서로 다르다**

```
  자리                     부등호                         등호가 붙나
  ----------------------   ----------------------------   -----------
  Interval.overlaps        a.start < b.end && b.start < a.end   아니오
  Interval.contains        start <= point && point < end        한쪽만
  merge 의 합치기          next.start <= curEnd                 예
  maxConcurrent 의 순서    starts[i] < ends[j]                  아니오(= 끝 먼저)

  전부 "반개구간 [start, end)" 하나에서 따라 나온다.
  이 넷의 등호를 각각 왜 그렇게 두는지 설명할 수 있어야 이 박스를 이해한 것이다.
```

**질문별 답**

- Q: 문제 2를 어떻게 푸는가?\
  A: 시작 배열과 끝 배열을 따로 정렬하고, 두 포인터로 이른 이벤트부터 처리하며 `open` 을 올렸다 내렸다 하면서 최댓값을 기록한다.\
  좌표가 같으면 끝을 먼저 처리하도록 `starts[i] < ends[j]` 에 등호를 **넣지 않는다**.
- Q: 복잡도는 왜 그런가?\
  A: 정렬 두 번이 `O(n log n)` 이고 훑기는 각 포인터가 한 방향으로만 가므로 `O(n)` 이다 — 합쳐서 `O(n log n)`, 공간 `O(n)`.
- Q: 좌표가 같을 때 무엇을 먼저 처리해야 하고 어긋나면 어떤 답이 나오는가?\
  A: **끝을 먼저** 처리해야 하고, 어긋나면 맞닿은 회의를 겹친 것으로 세어 답이 1 커진다(이어달리기 회의 넷이 1이 아니라 2가 된다).

**더 생각할 것**

- 이 문제도 트리가 필요 없다 — "정렬 + 한 번 훑기"가 답이다.\
  같은 데이터를 담고도 질의가 한 번뿐이면 자료구조를 지을 이유가 없다(질문 4).
- 스위핑은 이 문제집 밖에서도 반복해서 나오는 도구다 — 구간 합집합의 길이, 직사각형 겹침, 일정 배치가 전부 같은 뼈대다(원본에 근거 없음 — 내 추론).
- `best` 를 시작 처리 직후에만 갱신하는 것은 최적화가 아니라 **정확성**이다.\
  끝 처리 직후의 `open` 은 최댓값 후보가 될 수 없다.

### B. 자료구조 특성

#### 3. 인터벌 트리가 왜 필요한가

- Q: 13번 세그먼트 트리와 25번 KD-트리로는 무엇이 안 되는가?\
  A: **담는 것과 묻는 것이 다르다.**

```
  구조                 무엇을 담나        무엇을 묻나                       왜 이 문제에 안 맞나
  ------------------   ---------------    -------------------------------   ---------------------------
  13 세그먼트 트리     배열의 값          인덱스 구간의 집계(합·최소)       인덱스가 미리 정해져 있어야 한다
                                                                            구간 자체를 자료로 담지 못한다
  25 KD-트리(공간)     점                 사각형 안의 점, 가까운 점         자료가 점이라 "겹침"이라는
                                                                            관계 자체가 정의되지 않는다
  30 인터벌 트리       **구간**           **겹치는 구간**                   -
```

- 13번으로 풀려면 좌표 한 개에 배열 한 칸을 줘야 해서 좌표 범위만큼 메모리가 든다(질문 7의 좌표 압축이 그 문제를 푼다).
- 25번의 점 질의로 바꿔 풀 수도 있지만(구간 `[s,e)` 를 점 `(s,e)` 로 보고 사각형 질의를 던지는 변환) 이 문제집은 그 길을 가지 않는다(원본에 근거 없음 — 내 추론).
- Q: 06번 BST 에 `maxEnd` 한 필드를 더한 것이 왜 새 자료구조가 되는가?\
  A: **그 한 필드가 "이 가지에는 답이 없다"를 한 번의 비교로 판정하게 해주기 때문**이다.

```java
static final class Node {
    Interval interval;
    long maxEnd;               // 이 부분트리에 있는 구간들의 end 최댓값
    Node left;
    Node right;
}
```

```
  시작점으로 정렬한 BST 는 "시작점"에 대한 정보만 준다.
  그런데 겹침은 start 와 end 둘 다 봐야 판정된다 -> BST 만으로는 가지를 못 자른다.

  maxEnd 가 그 구멍을 메운다:
      왼쪽 부분트리의 maxEnd <= 질의 시작   ->  왼쪽의 모든 구간이 질의보다 먼저 끝난다 -> 볼 것 없다
      지금 노드의 start >= 질의 끝          ->  오른쪽의 모든 start 는 그 이상 -> 볼 것 없다

  앞줄은 **끝점**에 대한 요약이고 뒷줄은 **정렬**이 주는 성질이다.
  둘이 합쳐져야 양쪽 가지를 다 자를 수 있다.
```

> **인터벌 트리(interval tree)** — 시작점으로 정렬한 이진 탐색 트리의 각 노드에 그 부분트리의 끝점 최댓값(`maxEnd`)을 들려 겹침 질의를 가지치기하는 구조.\
> 예: 이 구현은 06번 BST 의 `insert`/`remove` 에 `recomputeMaxEnd` 한 줄을 더한 것이 전부다.

> **maxEnd** — 그 노드를 뿌리로 하는 부분트리에 담긴 모든 구간의 `end` 중 최댓값.\
> 예: 왼쪽 자식의 `maxEnd` 가 30인데 질의가 `[32, 40)` 이면 왼쪽은 통째로 건너뛴다.

- 정리하면 인터벌 트리는 **새 뼈대가 아니라 06번 위에 얹은 요약값 하나**다.\
  이것은 13번 세그먼트 트리(구간에 집계를 얹는다)·17번 펜윅 트리와 같은 계열의 발상이다 — **부분트리의 요약을 들고 있으면 그 부분트리를 안 봐도 되는 조건이 생긴다**.

**더 생각할 것**

- 27번 머클 트리도 "부분트리의 요약(해시)을 들고 있어서 통째로 건너뛴다"였다.\
  요약의 종류만 다를 뿐(해시 대 최댓값) 전략이 같다.
- 요약값을 들고 있다는 것은 **갱신 때 그 값을 유지할 책임**이 생긴다는 뜻이다.\
  그 책임을 빠뜨리면 예외가 아니라 조용히 틀린 답이 나온다(질문 7).
- "무엇을 담나 / 무엇을 묻나"로 갈라 보는 습관이 이 장의 가장 큰 수확이다.\
  자료가 같아도 질문이 다르면 다른 구조가 필요하다.

#### 4. 어떤 데이터·질의 패턴에 적합하고 언제 쓰면 안 되는가

- Q: 어떤 데이터·질의 패턴에 적합한가?\
  A: **구간이 많고, 겹침 질의가 반복되고, 답이 작은** 패턴이다.\
  달력의 겹치는 일정 표시, 회의실 배정 검사, 게놈 구간 조회, 방화벽 규칙 매칭이 그 모양이다.\
  특히 "예약을 넣어도 되나"(`findAny`)처럼 **하나만 찾으면 끝나는** 질의가 이 구조에 가장 유리하다.
- Q: 언제 쓰면 안 되는가?\
  A: 넷이다.\
  첫째, **질의가 한두 번뿐일 때** — 트리를 짓는 값을 회수하지 못한다.\
  둘째, **답이 거의 전부일 때** — 가지치기가 한 번도 발동하지 않는다(질문 6).\
  셋째, **입력이 정렬된 순서로 들어올 때** — 균형이 없어 트리가 한 줄이 된다(질문 6).\
  넷째, 구간이 거의 안 바뀌고 질의만 많다면 **정렬 배열 + 이진 탐색**이 더 단순하고 캐시에도 좋다(원본에 근거 없음 — 내 추론).
- Q: `merge` 와 `maxConcurrent` 처럼 트리가 필요 없는 문제는 무엇이 다른가?\
  A: **질의가 한 번뿐**이라는 점이 다르다.

```
  같은 구간 n 개를 두고

  merge / maxConcurrent        "전체를 한 번 훑어 답 하나"
      정렬 O(n log n) + 훑기 O(n) -> 끝. 자료구조가 남지 않는다.

  인터벌 트리                  "겹치는 것을 q 번 묻는다"
      짓기 O(n log n) + 질의마다 O(log n + k)
      -> q 가 작으면 짓는 값이 안 빠지고, q 가 크면 전수 O(n q) 를 압도한다

  손익분기 : 트리 짓는 비용 < (전수 - 트리 질의) x q  가 되는 q
  -> **자료가 아니라 질의 횟수가 자료구조를 정한다**
```

- 이 말은 "정렬로 풀리는 문제에 트리를 쓰면 진다"는 뜻이기도 하다.\
  `merge` 를 인터벌 트리로 풀면 답은 같지만 더 비싸다 — 한 번 쓰고 버릴 구조를 짓기 때문이다.
- 반대로 "예약 시스템"처럼 **같은 자료에 질의가 계속 들어오는** 상황이면 트리를 미리 지어두는 것이 전부 이득이다.\
  그리고 그 상황에서는 삽입·삭제도 계속 일어나므로, 지어둔 것을 유지할 수 있는 구조여야 한다 — 정렬 배열은 삽입에 `O(n)` 이라 그 자리에서 밀린다.

**더 생각할 것**

- "자료구조를 정하는 것이 자료가 아니라 질의"라는 문장은 이 문제집 전체의 요약이기도 하다.\
  같은 문자열을 두고 01번과 28번이 갈렸고, 같은 키 집합을 두고 05번과 29번이 갈렸다.
- 질의 횟수 q 를 모르면 결정할 수 없다 — 그래서 설계 질문은 "데이터가 몇 개인가"가 아니라 **"이 데이터에 무엇을 몇 번 물을 것인가"** 가 되어야 한다.
- 트리가 필요 없는 문제를 같은 장에 일부러 넣은 것도 그 교훈을 위해서다.\
  자료구조를 배우는 사람이 가장 자주 하는 실수가 "배운 구조를 쓸 자리를 찾는 것"이다.

#### 5. `findAny` 와 `findAll` 의 비용, 그리고 가지치기 두 줄

```java
private void collectFrom(Node node, Interval query, List<Interval> out) {
    if (node == null) {
        return;
    }
    visitedNodes++;

    // 가지치기 1. 왼쪽 부분트리의 모든 end 가 질의 시작 이하면 거기엔 겹치는 것이 없다.
    if (node.left != null && node.left.maxEnd > query.start) {
        collectFrom(node.left, query, out);
    }

    if (node.interval.overlaps(query)) {
        out.add(node.interval);
    }

    // 가지치기 2. 시작점으로 정렬했으므로 오른쪽의 start 는 전부 이 노드의 start 이상이다.
    // 이 노드의 start 가 이미 질의 끝 이상이면 오른쪽도 전부 그렇다.
    if (node.interval.start < query.end) {
        collectFrom(node.right, query, out);
    }
}
```

- Q: 가지치기 1이 무엇을 버리게 하는가?\
  A: **질의보다 먼저 끝나버린 구간들**을 통째로 버린다.\
  왼쪽 부분트리의 `maxEnd` 가 질의 시작 이하라는 것은 그 안의 **모든** 구간이 질의가 시작하기 전에 끝났다는 뜻이므로, 하나도 겹칠 수 없다.
- Q: 가지치기 2가 무엇을 버리게 하는가?\
  A: **질의가 끝난 뒤에야 시작하는 구간들**을 통째로 버린다.\
  시작점으로 정렬했으므로 오른쪽 부분트리의 시작점은 전부 이 노드의 시작점 이상이고, 이 노드의 시작이 이미 질의 끝 이상이면 오른쪽도 전부 그렇다.
- 두 줄이 겹침 조건 `a.start < b.end && b.start < a.end` 의 **양쪽 부등호에 각각 대응**한다는 것이 핵심이다.\
  가지치기 1은 "끝이 너무 이르다" 쪽을, 가지치기 2는 "시작이 너무 늦다" 쪽을 자른다.

```
경계에서 딱 멈춘다 (PruningTest.stopsExactlyAtTheBoundary — 등호 하나가 갈리는 자리)

  왼쪽 부분트리의 maxEnd 가 질의 시작과 **정확히 같을 때**
      [ .. 왼쪽, maxEnd = 20 .. ]   질의 [20, 30)
      20 은 질의에 안 들어간다(반개구간) -> 왼쪽에는 답이 없다 -> 내려가면 안 된다
      조건이 maxEnd > query.start 라 정확히 멈춘다 (>= 로 쓰면 헛걸음한다)
      assertEquals(1, left.visitedNodes(), "... 안 내려가야 한다");

  노드의 시작이 질의 끝과 **정확히 같을 때**
      노드 [30, 40)   질의 [20, 30)
      30 은 질의에 안 들어간다 -> 오른쪽은 전부 그 뒤다 -> 내려가면 안 된다
      조건이 node.interval.start < query.end 라 정확히 멈춘다
      assertEquals(1, right.visitedNodes(), "... 안 내려가야 한다");
```

> **가지치기(pruning)** — 답이 없다는 것이 확실한 가지로는 아예 내려가지 않는 것.\
> 예: 왼쪽 부분트리의 `maxEnd` 가 질의 시작 이하면 그 밑을 한 노드도 안 본다.

- Q: `findAny` 가 한 갈래로만 내려가도 되는 이유는?\
  A: **왼쪽에서 못 찾으면 오른쪽에도 없기 때문**이다.

```java
while (node != null) {
    visitedNodes++;
    if (node.interval.overlaps(query)) {
        return node.interval;
    }
    if (node.left != null && node.left.maxEnd > query.start) {
        node = node.left;      // 왼쪽에 "늦게 끝나는 것"이 있다 -> 그쪽으로만 간다
    } else {
        node = node.right;
    }
}
```

```
  왼쪽으로 갔다는 것은 = 왼쪽 어딘가에 end 가 질의 시작보다 큰 구간 i 가 있다는 뜻이다.
  그 i 가 질의와 안 겹친다면, 안 겹치는 경우는 둘뿐인데
      i 가 질의보다 앞?  -> i.end > query.start 이므로 아니다
      i 가 질의보다 뒤?  -> 그렇다. 즉 i.start >= query.end
  그런데 오른쪽 부분트리의 모든 start 는 i.start 이상이다(시작점 정렬).
  -> 오른쪽의 모든 구간도 query.end 이상에서 시작한다 -> 하나도 안 겹친다.

  그래서 왼쪽으로 내려가 실패하면 되돌아올 필요가 없다. 한 갈래면 충분하다.
```

- 비용: `findAny` 는 뿌리에서 잎까지 한 갈래라 **O(높이)** 이고, 균형이 잡혀 있으면 `O(log n)` 이다.
- 비용: `findAll` 은 답 k 개를 다 담아야 하므로 **O(높이 + k)** 를 지향한다 — 가지치기가 "답이 있는 가지"로만 내려가게 하므로 방문이 답의 개수에 비례해 늘어난다.
- 실제 측정(구간 4000개·질의 200번):

```
              전수 조사      인터벌 트리
  findAll     800,000        5,229            약 153배
  findAny     182,017        2,688            약 68배

  README 의 표 값이고, 테스트는 값이 아니라 선을 단언한다:
      assertEquals(200L * n, naiveTotal)          // 전수는 질의마다 정확히 n 이다
      assertTrue(treeTotal * 20 < naiveTotal)     // 트리는 20배 이상 적다
      assertTrue(treeTotal < 200L * tree.height())// findAny 는 질의마다 한 갈래다
  (5,229 와 2,688 은 테스트에 리터럴로 없다. 다만 내가 impl 을 파이썬으로 1:1 포팅해
   같은 시드(Dice 55 / 31337 / 4711)로 돌려보니 800,000 · 5,229 · 182,017 · 2,688 이
   그대로 재현됐다. README 수치는 정확하다.)
```

- Q: 가지치기를 지워도 답이 맞는데 왜 그게 더 위험한가?\
  A: **아무도 모르게 O(n) 이 되기 때문**이다.

```
  같은 질의 200번의 방문 노드 수 (내가 impl 을 포팅해 직접 재본 값)

    가지치기 둘 다        5,229       답 1,943개
    가지치기 1만 지움   412,371       답 1,943개    <- README 의 "41만 번대"
    가지치기 2만 지움   392,858       답 1,943개
    둘 다 지움          800,000       답 1,943개    <- 전수 조사와 정확히 같다

  답은 네 경우 모두 똑같다. 갈리는 것은 걸음 수뿐이다.
  그래서 답만 보는 테스트는 네 구현을 구별하지 못한다 -> PruningTest 가 방문 수를 센다.
```

- 이것이 27번의 `diffBlocks`("같으면 건너뛴다"를 빼도 답이 맞는다)와 **정확히 같은 자리**다.\
  자료구조의 값어치가 답이 아니라 걸음 수에 들어 있으면, 걸음 수를 재지 않는 한 정답과 오답이 안 갈린다.
- 그리고 그 실패는 배포된 뒤에 드러난다 — 데이터가 작을 때는 안 보이다가 n 이 커지면 갑자기 느려진다.

**더 생각할 것**

- `visitedNodes` 를 `null` 검사 뒤에 올리는 것도 계약이다 — null 자식을 세면 값이 두 배 가까이 부풀어 비교가 흐려진다.
- 부등호 하나(`>` 대 `>=`)의 차이는 좌표가 **정확히 같을 때만** 드러난다.\
  그래서 무작위 대조로는 안 걸리고 경계 측정을 따로 넣어야 한다(README 한계 4: 변종 24개 중 `>=` 셋이 그랬다).
- `findAny` 의 한 갈래 하강에는 가지치기 2가 없다.\
  필요가 없어서다 — 되돌아오지 않으므로 "오른쪽을 버린다"가 아니라 "왼쪽이 아니면 오른쪽"이라는 선택만 남는다.

#### 6. 최악의 입력과 최선

**(ㄱ) 정렬된 순서로 넣으면**

```java
IntervalTree ordered = new IntervalTree();
for (int i = 0; i < 1_000; i++) ordered.insert(Interval.of(i * 10, i * 10 + 5));
assertEquals(1_000, ordered.height(), "정렬 입력에서는 높이가 원소 수와 같아진다. 사실상 연결 리스트다");
```

```
  정렬 입력                     흩어 넣은 입력 (k = (i * 617) % 1000)

    [0,5)                              [ 중간값 근처 ]
       \                                  /        \
      [10,15)                          ...          ...
          \                           균형이 대충 잡힌다
         [20,25)
             \
             ...                     높이 1000  vs  높이 30

  같은 질의 [5000, 5050) 에 대해 (내가 포팅해 재본 값 — README 와 일치)
      findAll  방문 506 대 17        (답은 양쪽 다 5개로 같다)
      findAny  방문 501 대 13

  테스트가 단언하는 것은 값이 아니라 선이다:
      assertEquals(1_000, ordered.height());
      assertTrue(shuffled.height() < 50);
      assertTrue(orderedVisits > shuffledVisits * 20);
      assertEquals(ordered.toList(), shuffled.toList(), "담긴 것은 같다. 모양만 다르다");
```

- 왜 그렇게 되는가: 이 구현에는 **회전(균형 조정)이 없다**.\
  06번 BST 와 똑같이 정렬된 입력이 들어오면 매번 오른쪽 자식으로만 붙어 연결 리스트가 된다.\
  그러면 `findAny` 의 "한 갈래"가 곧 n 칸이라 `O(log n)` 이 `O(n)` 이 된다(테스트가 500개짜리 트리에서 방문 400 초과를 단언한다 — 내가 재보니 정확히 500이다).
- 이것은 **버그가 아니라 성질**이다 — 올바른 구현에서도 그대로 나오고, 답은 언제나 맞는다.\
  무너지는 것은 답이 아니라 걸음 수다.

> **출력 민감 복잡도(output-sensitive complexity)** — 비용을 입력 크기만이 아니라 **답의 개수 k** 로도 표현한 복잡도.\
> 예: `findAll` 의 `O(log n + k)` 에서 k 는 실제로 겹친 구간의 수이고, k 가 n 이면 그냥 `O(n)` 이다.

**(ㄴ) 결과 k 가 n 이 되는 입력**

```java
// 1000개가 전부 한 점(500,000)을 덮게 만든다
long s = 500_000 - 1 - dice.next(400_000);
Interval iv = new Interval(s, 500_000 + 1 + dice.next(400_000));
// 질의는 그 점 하나
Interval query = Interval.of(500_000, 500_001);

assertEquals(tree.size(), tree.findAll(query).size(), "전부가 답이다");
assertEquals(tree.size(), tree.visitedNodes(), "노드를 하나도 안 건너뛴다");
assertEquals(naive.visitedNodes(), tree.visitedNodes(), "전수 조사와 정확히 같은 걸음 수다");
```

- `O(log n + k)` 에서 `k = n` 이면 그냥 `O(n)` 이다 — **가지치기가 한 번도 발동하지 않는다**.\
  건너뛸 것이 없기 때문이다. 모든 노드가 답이므로 모든 노드를 봐야 한다.
- 이것은 알고리즘의 결함이 아니라 **출력 크기의 하한**이다 — 답이 n 개면 답을 적는 데만 n 번이 든다.\
  이길 방법이 없다.
- Q: 25번의 "모든 점이 같은 거리"와 어디가 같은 자리인가?\
  A: **가지치기의 전제가 무너지는 자리**라는 점이 같다.\
  KD-트리의 최근접 이웃 탐색은 "이 가지의 최선이 지금 답보다 멀다"로 가지를 자르는데, 모든 점이 같은 거리에 있으면 그 조건이 한 번도 참이 되지 않아 전부 본다.\
  여기서도 `maxEnd` 와 정렬이 주는 두 조건이 한 번도 참이 되지 않아 전부 본다.\
  둘 다 **데이터의 모양이 가지치기를 무력화**한 것이지 구현이 틀린 것이 아니다.

**최선은 어떤 입력인가**

- 트리가 균형 잡혀 있고(무작위 순서로 삽입), 구간이 시간축에 고르게 흩어져 있고, 질의가 좁아 답이 0~몇 개인 경우다.\
  그때 `findAll` 이 `O(log n + k)` 로 붙고, `findAny` 는 겹치는 것을 일찍 만나면 **뿌리 근처에서 바로 끝난다**.
- 극단적으로는 "질의와 겹치는 것이 하나도 없고 뿌리에서 바로 잘리는" 경우가 최선이다 — 방문 1이다.\
  `IntervalTreeStructureTest` 가 "질의가 전부보다 앞이면 뿌리에서 오른쪽이 잘린다"로 방문 1을 단언한다.

**더 생각할 것**

- 최악 둘의 성격이 다르다 — (ㄱ)은 **고칠 수 있는** 최악(균형 트리를 쓰면 된다)이고 (ㄴ)은 **고칠 수 없는** 최악(출력 크기)이다.\
  이 구별을 못 하면 엉뚱한 곳을 최적화하게 된다.
- 실무에서 (ㄱ)은 흔하다 — 시간순으로 들어오는 로그·예약이 곧 정렬 입력이다.\
  그래서 자동 균형이 없는 BST 계열은 실무에서 거의 안 쓴다.
- (ㄴ)을 완화하려면 질의를 바꿔야 한다 — "전부 달라"가 아니라 "몇 개만", "개수만"으로 물으면 출력 하한이 내려간다(원본에 근거 없음 — 내 추론).

#### 7. 전략의 트레이드오프

```
  전략                          짓는 비용        질의 비용            메모리           균형
  ---------------------------   --------------   ------------------   --------------   -------
  NaiveIntervalStore(기준선)    O(n) 삽입만      O(n) 언제나          O(n)             무관
  IntervalTree                  O(n log n)       O(높이 + k)          O(n)             없음
  좌표 압축 + 13번 세그먼트     O(n log n)       O(log n) 집계 질의   O(좌표 수)       해당 없음

  기준선은 "쉽다는 것이 요점"이다. 트리가 진짜로 이기는지 대조할 자가 있어야 한다.
```

- `NaiveIntervalStore` 의 값어치: **답의 기준선**이자 **걸음 수의 기준선**이다.\
  `findAll` 의 방문 수가 언제나 정확히 n 이라 비교 분모로 쓰기 좋고, 무작위 대조에서 트리의 답이 맞는지 확인해준다.
- `IntervalTree` 가 사는 것: 가지치기로 평균 질의 비용을 `O(log n + k)` 로 낮춘다.\
  내주는 것: **균형이 없다** — 정렬 입력에서 `O(n)` 으로 무너지고, `maxEnd` 라는 파생 상태를 갱신할 책임이 생긴다.

**좌표 압축이 40억 칸을 8000칸으로 줄이는 근거**

```java
// 등장하는 좌표만 모아 정렬하고 중복을 없앤 뒤, 그 배열의 인덱스를 새 좌표로 쓴다
Arrays.sort(raw);
int unique = 0;
for (int i = 0; i < raw.length; i++) {
    if (i == 0 || raw[i] != raw[i - 1]) {
        raw[unique++] = raw[i];
    }
}
this.coordinates = Arrays.copyOf(raw, unique);
```

```
  좌표 범위 10억, 구간 1000개

  압축 없이 : 배열 한 칸 = 좌표 한 개, 13번의 4n 관행 -> 4 x 10억 = **40억 칸**
  압축하면  : 등장하는 좌표는 아무리 많아도 2n = 2000개 -> 4 x 2000 = **8000 칸**
              50만 배

  테스트가 단언하는 것 :

      assertTrue(rawCells / compressedCells > 100_000)// 10만 배 초과 (하한)

  (내가 같은 시드(Dice 2026)로 포팅해 세어보니 유일 좌표가 정확히 2000개였고,
   4 x 2000 = 8000, 40억 / 8000 = 500,000 으로 README 값이 그대로 나왔다.)
```

- Q: 근거가 무엇인가?\
  A: **겹침은 좌표의 크기 비교로만 정해지기 때문**이다.\
  `overlaps` 는 `a.start < b.end && b.start < a.end` 로 부등호뿐이고, 좌표의 절대값이나 간격은 한 번도 쓰이지 않는다.\
  그러니 순서만 보존하면 좌표를 0, 1, 2 … 로 갈아끼워도 답이 안 바뀐다.\
  그리고 아무 구간의 경계도 아닌 좌표는 있어도 답을 바꾸지 않으므로 지워도 된다.
- Q: 없는 좌표에 "가장 가까운 번호"를 주면 왜 안 되는가?\
  A: **왕복(round trip)이 조용히 깨지기 때문**이다.

```
  compressPoint(x) -> 번호,  decompressPoint(번호) -> 원래 좌표

  등장하지 않은 좌표 x 에 "가장 가까운 번호" y 를 준다면
      decompress(y) != x        -> 왕복이 깨진다
      그리고 x 와 y 사이에 있던 구간 경계를 넘어버리면 겹침 판정 자체가 뒤집힌다

  그래서 코드는 예외를 던진다:
      int at = Arrays.binarySearch(coordinates, value);
      if (at < 0) {
          throw new IllegalArgumentException("등장하지 않은 좌표다: " + value);
      }
  압축은 등장한 좌표에 대해서만 정의된다 — 되는 척하지 않는 쪽을 골랐다.
```

**빈 부분트리의 `maxEnd` 를 0으로 두면 무엇이 무너지는가**

```java
static long maxEndOf(Node node) {
    return node == null ? Long.MIN_VALUE : node.maxEnd;
}
```

- **최댓값의 항등원**이 무너진다.\
  `maxEnd` 는 "이 부분트리의 end 최댓값"이고, 빈 부분트리에는 원소가 없으므로 최댓값 계산에 **영향을 주지 않는 값**을 돌려줘야 한다 — 그것이 `Long.MIN_VALUE` 다.
- 0을 돌려주면 좌표가 음수일 때 `Math.max(-5, 0) = 0` 이 되어 **실제보다 큰 maxEnd** 가 올라간다.\
  그러면 "여기 아래에 늦게 끝나는 것이 있다"는 거짓말이 되어 **안 내려가도 될 가지로 내려간다** — 답은 맞고 방문 수만 는다.\
  반대로 낡은 값이 실제보다 **작으면** 답이 조용히 빠진다.
- README 가 그 변종의 증상을 적어뒀다 — 음수 좌표 대조 하나만 깨졌고 증상이 "답이 12개인데 null" 이었다.\
  (이 "12개"라는 수는 테스트·impl 어디에도 없다 — README 서술이다. 대응하는 테스트는 `CrossCheckTest` 의 음수 좌표 대조다.)
- 13번 세그먼트 트리의 "최소 트리에 항등원 0" 과 같은 계열의 함정이다 — **항등원은 자료형의 기본값이 아니라 연산이 정한다**.

> **항등원(identity element)** — 그 연산에 넣어도 결과를 바꾸지 않는 값.\
> 예: 최댓값 연산의 항등원은 `Long.MIN_VALUE` 이고 0이 아니다. 덧셈이면 0, 곱셈이면 1이다.

> **파생 상태(derived state)** — 다른 값들로부터 계산되어 저장된 값.\
> 예: `maxEnd` 는 자식들의 값으로부터 나오는 값이라 트리가 바뀔 때마다 다시 계산해줘야 한다.

- `maxEnd` 갱신을 빠뜨리면 예외가 안 난다는 것도 같은 계열이다.\
  삽입·삭제 재귀에서 **돌아오는 길에** `recomputeMaxEnd(node)` 를 부르는 한 줄이 그 책임의 전부인데, 빠뜨리면 낡은 값이 거짓말을 한다.\
  삭제 쪽은 틀리는 방향이 둘이라 더 위험하다 — 값이 실제보다 크면 방문만 늘고, 작으면 답이 빠진다.

- 좌표 압축은 "값 자체는 필요 없고 순서만 필요하다"는 관찰 하나로 메모리를 50만 배 줄인다.\
  같은 관찰이 21번 접미사 배열·순위 압축에서도 반복된다.
- 세 전략 중 무엇을 고를지는 질의의 종류가 정한다 — 겹침 목록이면 인터벌 트리, 구간 집계(합·개수)면 좌표 압축 + 세그먼트 트리다.
- 파생 상태를 두는 모든 구조는 "갱신 책임"을 같이 산다.\
  17번 펜윅 트리·13번 세그먼트 트리·27번 머클 트리가 전부 같은 세금을 낸다.

#### 8. 이 구조의 한계가 다음 구조를 어떻게 부르는가

- Q: 균형을 안 잡아 정렬 입력에 무너지는 것은 무엇을 가리키는가?\
  A: **16번 레드블랙 트리가 고치는 것**을 가리킨다.\
  1000개를 정렬 순서로 넣으면 높이가 1000이 되는데, 레드블랙 트리는 회전과 색칠로 높이를 `2 log(n+1)` 이하로 묶는다.\
  그리고 인터벌 트리에 그것을 얹는 것은 어렵지 않다 — **회전할 때 `maxEnd` 를 다시 계산해주면 된다**.\
  실제로 교과서의 인터벌 트리는 레드블랙 트리 위에 얹혀 있다(원본에 근거 없음 — 일반 지식).
- 즉 이 장의 한계 2는 "인터벌 트리의 한계"가 아니라 **"균형 없는 BST 의 한계"** 다.\
  가지치기(이 장이 새로 산 것)는 균형과 독립이고, 무너지는 것은 밑에 깔린 BST 쪽이다.
- Q: 31번 일관된 해싱으로 넘어가는 것은 무엇인가?\
  A: **"정렬된 좌표에서 이 키 다음에 오는 것을 찾는다"** 는 연산 하나가 그대로 넘어간다.

```
  30번                                   31번
  ----------------------------------     --------------------------------------
  시작점으로 정렬한 트리                 노드의 자리(해시값)를 정렬해 원에 올린다
  "이 질의와 겹치는 구간"                "이 키 다음에 오는 노드"
  가지치기로 O(log n + k)                ceilingKey 로 O(log(자리 수))
  좌표는 직선                            좌표는 **원** (끝에서 되감는다)

  06번 BST 의 ceilingKey 가 두 장 모두의 밑바닥이다.
  30번은 거기에 maxEnd 를 얹어 겹침을 샀고, 31번은 거기에 "되감기 한 줄"을 얹어 원을 만든다.
```

- 그리고 방법론도 그대로 넘어간다.\
  **걸음 수를 세는 계기**(`visitedNodes` → 31번의 이동한 키 수), **기준선과의 대조**(`NaiveIntervalStore` → `ModuloSharding`), **"답은 맞는데 비용만 무너진다"** 는 실패 모양이 31번에서도 반복된다.
- Q: 여기서 배운 것 중 31번에 그대로 쓰이는 것은?\
  A: 셋이다.\
  첫째, **정렬이 주는 성질**(어떤 값 다음에 오는 것을 `O(log n)` 에 찾는다) — 31번의 `getNode` 가 그것이다.\
  둘째, **경계의 부등호**(`>` 와 `>=` 중 무엇인가) — 원에서는 "자기 자리와 정확히 같은 해시"가 그 경계다.\
  셋째, **답이 맞는 것과 비용이 맞는 것은 다른 문제**라는 태도 — 31번에서 재는 것은 속도가 아니라 **이동량**이다.

**더 생각할 것**

- 30번은 "구조는 06번 그대로, 필드 하나 추가"로 새 질문에 답했다.\
  새 자료구조가 늘 새 뼈대를 요구하지는 않는다는 좋은 예다.
- 반대로 그 한 필드가 **갱신 책임**과 **항등원 선택**이라는 두 개의 새 실패 모드를 들여왔다.\
  기능을 하나 더하면 실패 모드도 같이 늘어난다.
- 이 장에서 가장 오래 남는 문장은 "질의가 자료구조를 정한다"와 "가지치기를 지워도 답은 맞는다" 둘이다.\
  앞은 설계의 기준이고 뒤는 검증의 기준이다.
