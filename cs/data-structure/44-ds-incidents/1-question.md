# data-structure/44-ds-incidents — 질문

## 질문

1. (왜) HashDoS와 JDK 7 `HashMap` 순환은 해시 맵 비용 계약의 어떤 가정을 각각 깨나? 두 사건이 "예외 없이 CPU만 쓴다"는 점이 진단에 주는 어려움은?
2. (계산) 같은 해시의 키 n개를 체이닝 해시 테이블에 차례로 넣을 때 `equals` 비교는 몇 번인가? 공격자의 비용과 서버의 비용을 비교해 advisory가 말한 "amplification effect"를 설명하라.
3. (사실) oCERT-2011-003이 든 원인 두 가지(해시 쪽, 웹 서버 쪽)는? advisory 표에서 Java의 "수정 판"은 무엇이었고, Python 2.7.3·3.2.3의 수정은 기본으로 켜져 있었나?
4. (구분) 런타임이 택한 두 갈래(해시를 예측 불가능하게 / 최악 비용을 줄이기)를 Python과 Java의 실제 조치(판·문서)로 대고, 각 갈래가 막지 못하는 경우를 하나씩 들어라.
5. (예측) 실험 A에서 같은 해시 키 32,768개를 넣는 시간은 `String`·비`Comparable`·보통 키에서 각각 얼마였나? 비`Comparable` 열이 n 두 배마다 몇 배로 늘었고, O(n²) 예상과 어떻게 달랐나?
6. (그림) jdk7u `transfer()`의 머리 삽입에서, 버킷 `A -> B`를 두 스레드가 겹쳐 옮길 때 `A.next = B, B.next = A`가 되는 순서를 단계별로 그려라. 실험 C는 무엇을 보였고 무엇은 보이지 않았나?
7. (장애 진단) 운영 서버가 CPU 100%이고 덤프에 `HashMap`이 보인다. 덤프 세 장으로 사건 1형과 사건 2형을 어떻게 가르나? 각각의 처방은?
8. (경계) JDK 8은 resize 순서를 보존한다. 그렇다면 공유 `HashMap`은 이제 안전한가? JDK 21 실험 수치와 `HashMap` Javadoc으로 답하라.
9. (연결) Python 서비스의 배포 설정에 `PYTHONHASHSEED=0`이 있다. 실험 B의 출력으로 이것이 무엇을 끄는지 설명하고, 이 설정이 필요했던 원래 이유를 대체할 방법을 말하라.
