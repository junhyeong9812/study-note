# data-structure/lsm-merge-model — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: 개인 학습 노트 「LSM 계열 저장 구조의 병합 모델」 · 이관일 2026-09-16.\
> 본문 절들(쓰기 경로·병합 비용·복제와 병합)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지).\
> 원고가 특정 학습용 저장 엔진 프로젝트에 묶어 쓴 「공부법」 절은 **일반 예시**와 「현장에서 만나는 상황」으로 승격·재배치했다.\
> 「한눈에」의 명단 비유와 일부 도식은 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**교정할 오해**: "LSM은 저장한 뒤에 재정렬한다"는 틀렸다.\
**정렬은 쓰기 시점에 이미 끝나 있고, 백그라운드 작업은 재정렬이 아니라 머지 소트다.** 이 한 문장이 이 노트의 전부다.

> **LSM(Log-Structured Merge-tree)** — 쓰기를 메모리의 정렬 구조에 먼저 받고, 정렬이 끝난 불변 파일을 디스크에 순차로 떨구는 저장 구조.\
> 예: RocksDB·LevelDB·Cassandra·ClickHouse의 저장 엔진이 이 계열이다.

---

## 한눈에 — 쉽게 말하면

**이미 각자 정렬된 명단들을 하나로 합치는 일**을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
세 사람이 각자 '이름순으로 정렬된 명단'을 들고 왔다
+---------------------------------------------+
| A 명단:  강 · 김 · 박                        |
| B 명단:  김 · 이 · 정                        |
| C 명단:  나 · 서 · 최                        |
+---------------------------------------------+
       ↓ 합칠 때 처음부터 다시 정렬하지 않는다
       ↓ 각 명단은 이미 정렬돼 있으니, 맨 앞끼리만 비교해 하나씩 뽑는다
통합 명단: 강 · 김 · 김 · 나 · 박 · 서 · 이 · 정 · 최
```

**LSM의 병합도 똑같은 구조다.** 디스크에 쌓인 파일들은 저장되는 순간 이미 각자 정렬돼 있고, 백그라운드 병합은 그 정렬된 파일들의 맨 앞을 비교해 하나의 정렬된 스트림으로 뽑아내는 **머지 소트**일 뿐이다.

쉽게 말하면 이렇다.\
**LSM은 "정렬을 언제 하느냐"를 옮긴 구조다.** 쓰기 시점에 메모리에서 정렬을 끝내고, 디스크에는 순차 쓰기만 내려보낸다. 그래서 병합의 비용은 "정렬이 느려서"가 아니라 "같은 데이터를 조회와 자원을 나눠 가며 여러 번 다시 쓰기 때문"이다.

> **머지 소트(merge sort)** — 이미 정렬된 조각 여럿을 맨 앞끼리 비교해 하나로 합치는 것. 정렬을 새로 하는 게 아니다.\
> 예: 정렬된 파일 N개를 합치는 비용은 비교 정렬 O(n log n)이 아니라 N-way merge O(n log N)이다(N = 파일 수).


## 전체 흐름

쓰기 한 건이 디스크의 불변 파일이 되고, 그 파일들이 병합되는 경로다.

```text
write
  ├─▶ WAL 에 append          내구성 확보 (순차 쓰기)
  └─▶ memtable 에 삽입         인메모리 정렬 구조 — 여기서 정렬이 끝난다
          ↓ 임계치 도달
     immutable memtable       더 이상 안 바뀜
          ↓ flush
     SSTable (디스크)          정렬 완료 · 불변
          ↓ 여러 개 쌓이면
     compaction               정렬된 파일들의 N-way 머지 소트
          ↓
     새 SSTable               다시 불변
```

- 왼쪽은 **거쳐 가는 자리**, 오른쪽은 **그 자리가 정하는 것**.
- 핵심은 두 번째 줄에서 정렬이 이미 끝난다는 점, 그리고 마지막 병합이 재정렬이 아니라는 점이다.

> **WAL(Write-Ahead Log)** — 실제 자료구조를 고치기 전에 "무엇을 쓸지"를 먼저 append해 두는 로그. 장애 시 재생으로 복구한다.\
> 예: 재시작하면 memtable은 날아가지만, WAL을 재생해 마지막 상태를 되살린다.

## 쓰기 경로 — 어디서 정렬이 끝나는가

> 출처: 개인 학습 노트 「LSM 병합 모델」 — §1

**언제 쓰나** — "LSM은 저장 후 재정렬한다"는 설명을 만났을 때. 정렬 시점을 바로잡는 절이다.

세 가지가 핵심이다.

```text
① 정렬은 memtable 에서 이미 일어난다
   인메모리 정렬 자료구조(skiplist / red-black tree)에 넣는 순간 순서가 잡힌다

② 디스크로 내려간 세그먼트(SSTable)는 불변이다
   수정도 삭제도 제자리에서 하지 않는다
     update = 새 버전을 append
     delete = tombstone(삭제 표시)를 append

③ compaction 은 재정렬이 아니다
   이미 정렬된 파일 N개를 읽어 하나의 정렬된 스트림으로 합치는 머지 소트
```

> **SSTable(Sorted String Table)** — 키로 정렬된 채 디스크에 저장되는 불변 파일. 한 번 쓰면 고치지 않는다.\
> 예: 같은 키를 수정하면 옛 SSTable은 그대로 두고 새 SSTable에 새 값을 쓴다. 읽을 때 최신 것이 이긴다.

> **tombstone(삭제 표시)** — "이 키는 삭제됨"이라는 마커. 실제 데이터를 지우는 대신 삭제 표시를 append한다.\
> 예: `id=42 삭제` → `(42, tombstone)`을 쓴다. 조회는 최신 표시를 보고 "없음"을 반환한다.

**비용** — 쓰기는 전부 순차 append라 싸다. 대신 같은 키가 여러 파일에 흩어져 읽기가 그 값을 치른다(아래 절).

## 병합 비용의 본질 — 락이 아니라 자원 경쟁

> 출처: 개인 학습 노트 「LSM 병합 모델」 — §2

**언제 쓰나** — "병합이 느린 건 락 경합/데드락 때문"이라는 직관을 만났을 때.

**틀린 직관**: 병합이 느린 건 락 경합·데드락 때문이다.\
**실제**: 병합 대상 파일은 불변이라 **락 자체가 거의 필요 없다.** 비용은 전부 자원 경쟁이다.

```text
비용 항목            무엇을 잡아먹나
─────────────────────────────────────────
병합 I/O            같은 데이터를 레벨을 내려가며 여러 번 다시 쓴다 → 쓰기 증폭
CPU                머지 · 압축(compression) · 체크섬
페이지 캐시 오염      병합이 캐시를 밀어내 조회 성능이 같이 떨어진다
디스크 대역폭 경쟁     조회의 랜덤 읽기 vs 병합의 순차 읽기/쓰기가 같은 장치를 놓고 싸운다
공간 증폭            병합 중에는 원본과 결과물이 동시에 존재한다
```

> 정리 문장: **"병합은 정렬 비용이 아니라, 조회와 자원을 나눠 쓰는 백그라운드 재작성 비용이다."**

> **쓰기 증폭(write amplification)** — 사용자가 쓴 바이트보다 실제로 디스크에 쓴 바이트가 몇 배 많은가.\
> 예: 한 키를 레벨 5개를 내려가며 다시 쓰면, 유저가 1KB 썼는데 디스크에는 5KB가 쓰인다 → 쓰기 증폭 5.

### 세 가지 증폭의 트레이드오프

병합 전략은 결국 셋 중 무엇을 포기할지의 선택이다.

```text
전략                          쓰기 증폭   읽기 증폭             공간 증폭
─────────────────────────────────────────────────────────────────
Leveled (예: RocksDB 기본)     높음        낮음(레벨당 파일 1개)   낮음
Tiered / Size-tiered          낮음        높음(겹치는 파일 다수)   높음
 (예: Cassandra)
```

읽기 증폭을 줄이는 보조 장치는 둘이다.

- **블룸 필터** — "이 SSTable에 이 키가 없음"을 싸게 확인해, 없는 파일은 아예 안 읽는다.
- **스파스 인덱스** — 파일 내 블록 위치를 대략 알려줘 탐색 범위를 좁힌다.

> **블룸 필터(Bloom filter)** — "확실히 없음"은 정확히, "있을 수 있음"은 오탐을 허용하며 답하는 작은 확률 자료구조.\
> 예: 블룸 필터가 "없음"이라 하면 그 파일은 건너뛴다. "있음"이라 하면 실제로 있을 수도, 없을 수도 있어 파일을 읽어 확인한다.

**비용** — Leveled와 Tiered는 정반대의 증폭을 감수한다. 쓰기 많은 워크로드면 Tiered, 읽기 중심이면 Leveled 쪽으로 기운다.

## 복제와 병합 — "한 노드가 병합, 나머지는 서빙" 모델은 없다

> 출처: 개인 학습 노트 「LSM 병합 모델」 — §3

**언제 쓰나** — "프라이머리가 정렬하고 레플리카는 읽기만 해서 가볍다"는 모델을 가정할 때. 이 모델은 대표적 검색·분석 엔진 어디에도 존재하지 않는다.

**전/후 대비 — 두 대표 엔진이 실제로 하는 일**

```text
Lucene 세그먼트 기반 엔진               컬럼형 분석 엔진(파트 기반)
+-----------------------------+       +-----------------------------+
| 레플리카에 '연산'이 복제된다   |       | 레플리카끼리 복제 로그로 조율  |
|  (문서 단위 / 시퀀스 번호)     |       |  (분산 코디네이터 경유)       |
| 레플리카가 자기 세그먼트를     |       | 기본은 각자 같은 병합을 수행   |
|  스스로 만들고 스스로 병합     |       | 단, 병합 결과를 fetch 하는     |
|                             |       |  경로가 설정으로 존재          |
+-----------------------------+       +-----------------------------+
  → 각자 색인 · 각자 병합             → 각자 병합이 기본이되 받아오기 옵션
  → 세그먼트 구성이 프라이머리와        → "누가 병합하나"는 아키텍처가 고정한 게
     같지 않고 병합 시점도 다르다          아니라 설정으로 고르는 트레이드오프
```

- 왼쪽 형태에서 실무 함의: **병합 부하는 레플리카에서도 똑같이 난다.** "레플리카는 읽기만 하니 가볍다"가 성립하지 않는다.
- 왼쪽의 관련 개념: `refresh`(새 세그먼트 생성 → 검색 가능) / `flush`(트랜스로그 비우고 커밋) / `force_merge`(수동 병합, 쓰기 끝난 인덱스에만).
- 오른쪽의 관련 설정: 한 레플리카만 병합하고 나머지는 받아오게 하는 시간 임계값, 큰/오래 걸리는 병합만 받아오게 하는 크기·시간 임계값, 항상 받아오기 옵션.

> 한 줄로: **한쪽은 각자 병합, 다른 쪽은 각자 병합이 기본이되 결과를 받아오는 옵션이 있다.** 어느 쪽도 "한 노드 전담 병합"이 기본은 아니다.

**비용** — 오른쪽의 fetch 옵션은 CPU·I/O를 아끼는 대신 네트워크를 쓴다. 공짜가 아니라 자원을 어디에 쓸지 옮기는 것이다.

### 현장에서 만나는 상황 — 직접 구현으로 체화하기

이 구조는 읽어서는 잘 안 박히고, **같은 인터페이스로 B-Tree 엔진 옆에 LSM 엔진을 하나 더 만들어 보면 코드로 남는다.** *(원고의 학습용 프로젝트 절을 일반 예시로 옮김)*

구현 순서(각 단계마다 동작하는 상태를 유지한다).

```text
단계  만드는 것                              확인할 것
──────────────────────────────────────────────────────────────
 1   memtable(정렬 맵) + WAL append          재시작 후 WAL 재생으로 복구되는가
 2   flush → SSTable 파일                    파일이 정렬돼 있는가
     (정렬 KV + 스파스 인덱스 + footer)
 3   조회 경로: memtable → 최신 SSTable → 과거   최신 버전이 이기는가
 4   tombstone 삭제                          삭제 후 조회가 '없음'을 반환하는가
 5   size-tiered compaction                 파일 수가 수렴하는가
 6   블룸 필터                               없는 키 조회의 디스크 접근이 주는가
 7   leveled compaction                     쓰기 증폭 vs 읽기 증폭 수치 비교
```

반드시 계측할 것(이게 실측 경험이 된다).

- **쓰기 증폭** = 실제 디스크에 쓴 바이트 / 유저가 쓴 바이트
- **읽기 증폭** = 키 하나 조회에 접근한 SSTable 수(블룸 필터 적용 전후)
- **공간 증폭** = 디스크 사용량 / 논리 데이터 크기
- **병합 중 조회 p99** = 병합 스레드를 켠 상태와 끈 상태의 조회 레이턴시 차이

마지막 항목이 핵심이다.\
이게 "병합 비용의 본질은 자원 경쟁"이라는 문장에 **본인 측정치를 붙여 주는** 실험이다.

## 한 문단 요약 (면접용)

> LSM은 쓰기를 인메모리 정렬 구조에 받고, 임계치에서 이미 정렬된 불변 세그먼트로 디스크에 떨군다. 그래서 백그라운드 컴팩션은 재정렬이 아니라 정렬된 파일들의 머지 소트고, 비용의 본질은 락이 아니라 쓰기 증폭과 조회와의 I/O·CPU 경쟁이다. Leveled는 쓰기 증폭을 대가로 읽기 증폭을 줄이고, tiered는 반대다. 복제 관점에서도 "한 노드가 병합하고 나머지는 서빙"이 기본은 아니다. Lucene 계열은 레플리카가 각자 색인하고 각자 병합하며, 컬럼형 분석 엔진은 각자 병합이 기본이되 병합 결과 파트를 fetch하도록 설정으로 바꿀 수 있다.

## 핵심 문장

- **정렬은 쓰기 시점(memtable)에 끝난다 — 백그라운드 컴팩션은 재정렬이 아니라 정렬된 파일의 머지 소트다.**
- **병합이 느린 건 락 때문이 아니다 — 파일이 불변이라 락이 거의 없고, 비용은 조회와 나눠 쓰는 자원 경쟁이다.**
- **Leveled ↔ Tiered는 쓰기·읽기·공간 증폭 중 무엇을 포기할지의 선택이다.**
- **복제 환경에서 "한 노드 전담 병합, 나머지 서빙"은 기본형이 아니다 — 대개 각자 병합한다.**
- **디스크 세그먼트는 불변이므로 수정=새 버전 append, 삭제=tombstone append다.**

## 용어 풀이

- **LSM(Log-Structured Merge-tree)** — 쓰기를 메모리 정렬 구조에 받고 정렬 끝난 불변 파일을 디스크에 순차로 떨구는 저장 구조.
- **memtable** — 쓰기를 먼저 받는 인메모리 정렬 자료구조(skiplist·red-black tree 등).
- **SSTable(Sorted String Table)** — 키로 정렬된 채 저장되는 디스크의 불변 파일.
- **WAL(Write-Ahead Log)** — 자료구조를 고치기 전에 무엇을 쓸지 먼저 append하는 내구성 로그.
- **compaction(컴팩션·병합)** — 쌓인 SSTable들을 머지 소트로 합쳐 파일 수를 줄이는 백그라운드 작업.
- **머지 소트(merge sort)** — 이미 정렬된 조각들을 맨 앞끼리 비교해 하나로 합치는 것.
- **tombstone(삭제 표시)** — "이 키는 삭제됨"을 나타내는 마커. 제자리 삭제 대신 append한다.
- **쓰기 증폭(write amplification)** — 유저가 쓴 바이트 대비 실제 디스크에 쓴 바이트의 배수.
- **읽기 증폭(read amplification)** — 키 하나를 조회하는 데 접근해야 하는 파일 수.
- **공간 증폭(space amplification)** — 논리 데이터 크기 대비 실제 디스크 사용량의 배수.
- **블룸 필터(Bloom filter)** — "없음"은 정확히, "있음"은 오탐을 허용하며 답하는 확률 자료구조.
- **스파스 인덱스(sparse index)** — 파일 내 대략적 위치만 담아 탐색 범위를 좁히는 색인.
- **Leveled / Tiered compaction** — 병합 전략 두 갈래. 각각 쓰기 증폭↑읽기·공간↓ / 쓰기↓읽기·공간↑.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **RUM Conjecture.** LSM의 트레이드오프를 이론으로 묶은 것이 RUM 추측이다 — **R**ead(읽기)·**U**pdate(쓰기)·**M**emory(공간) 세 비용 중 둘을 좋게 하면 나머지 하나가 나빠진다. 위 "세 가지 증폭"이 바로 이 삼각형의 실체다. 쓰기 많으면 LSM, 읽기 중심이면 B-Tree라는 선택이 여기서 나온다.
- **compaction 트리거.** 병합을 언제 돌릴지는 보통 "레벨별 파일 수·크기가 임계를 넘으면"으로 정해진다. 그래서 병합은 쓰기가 몰릴 때 같이 몰리고, 그 순간 조회 p99가 튄다 — 위 계측 항목의 마지막이 이 현상을 잡는다.
- **read-modify-write가 없다는 점.** B-Tree는 페이지를 읽어 고쳐 다시 쓰지만(random write), LSM은 무조건 새로 append한다. 이 append-only + 불변이라는 발상은 SSD 내부의 FTL(Flash Translation Layer)과 정확히 같다 — 제자리 덮어쓰기가 비싼 매체에서 반복해 나오는 패턴이다.
