### B. 자료구조 특성

#### 1. 트리가 왜 필요한가 — 평면 맵이 계약 테스트를 똑같이 통과하는데도

- Q: 먼저, 계약 테스트 68개를 둘이 똑같이 통과한다는 것은 무슨 뜻인가?\
  A: **답이 같다**는 뜻이다. 기능 차이가 없다는 말이다.\
  `FileSystemContractTest` 는 추상 클래스이고 `@Test` 가 34개다.\
  그것을 `TreeFileSystemTest` 와 `FlatPathFileSystemTest` 가 각각 상속하므로 34 × 2 = **68개**가 돌아간다.\
  두 하위 클래스에는 `create` 오버라이드 말고 아무 테스트도 없다 — 계약이 전부 공통이라는 표현이다.\
  (README 는 68개라고 하고 `MeasurementTest` 의 주석은 66개라고 한다. 코드 기준은 34 × 2 = 68 이다.)

    @Override
    protected FileSystem create() {

- Q: 그러면 트리는 왜 있는가?\
  A: **답이 같아도 일하는 양이 다르기** 때문이다.\
  그리고 그 차이는 "조금 느리다" 수준이 아니라 **구조적으로 다른 차수**다 — `mv` 에서 1 대 341 이다.\
  기능이 같은데 비용이 갈리는 선택은 기능 테스트로 절대 못 고른다. 그래서 `MeasurementTest` 가 따로 있다.\
  32번에서 병합 순서(231 대 683)가 대조로 안 잡혔던 것과 같은 자리다.

- Q: 경로를 "이름 → 자식 맵"으로 층층이 쌓는다는 것은 정확히 무엇인가?\
  A: 노드 하나가 `Map<String, Node>` 를 들고 있고, 그 값이 또 노드라서 **맵 안에 맵이 있는** 재귀 구조다.

```java
// impl/Node.java
public final class Node {
    private final String name;
    private final Blob blob;
    private final Map<String, Node> children;   // 디렉터리면 TreeMap, 파일이면 null
    ...
}
```

- Q: 09번 트라이가 글자로 내려간 자리에서 여기는 무엇으로 내려가는가?\
  A: **경로 조각(이름)** 으로 내려간다. `TreeFileSystem.lookup` 이 그 한 줄이다.

```java
// impl/TreeFileSystem.java
private Node lookup(String path) {
    Node current = root;
    visitedNodes++;
    for (String part : Paths.split(path)) {
        if (!current.isDirectory()) {
            return null;        // 파일을 뚫고 더 내려갈 수는 없다
        }
        current = current.children().get(part);
        visitedNodes++;
        if (current == null) {
            return null;
        }
    }
    return current;
}
```

```text
09 트라이와 33 트리의 대응

  트라이           "cat" 을 찾는다      c -> a -> t       한 걸음 = 글자 하나
  파일 시스템      "/a/b/f.txt" 를 연다  a -> b -> f.txt   한 걸음 = 이름 하나

  같은 것 : 키를 조각으로 쪼개 한 조각씩 자식 맵을 타고 내려간다
            중간 노드가 곧 "접두사(=조상 경로)" 를 뜻한다

  다른 것 : 트라이의 자식 수는 알파벳 크기로 유한하다 (배열로 잡아도 된다)
            파일 시스템의 자식 수와 이름 가짓수는 무한하다 (맵이어야 한다)
            그리고 트라이는 중간 노드가 "단어의 끝인가" 만 구별하는데
            여기서는 중간 노드가 디렉터리, 끝 노드가 파일이라 종류 자체가 다르다
```

> **트리(tree)** — 각 노드가 자식들을 직접 가리키고, 모든 자식의 부모가 하나뿐인 구조.\
> 예: `/a/b/f.txt` 에서 `f.txt` 노드는 `b` 의 자식 맵에만 들어 있다 — 그래서 `b` 를 옮기면 `f.txt` 도 따라온다.

> **평면 맵(flat path map)** — 전체 경로 문자열을 통째로 키로 쓰는 맵 하나. 층 구조가 없다.\
> 예: `entries.get("/a/b/f.txt")` 가 해시 한 번에 끝나지만, `/a` 의 자식이 누구인지는 어디에도 안 적혀 있다.

> **재귀 구조(recursive structure)** — 자기와 같은 종류를 자식으로 품는 구조.\
> 예: `Node.children` 의 값이 또 `Node` 다. 그래서 `find` · `size` · `cp` 가 전부 재귀로 쓰인다.

- Q: 트리에서 자식 맵이 왜 `TreeMap` 인가?\
  A: **`ls` 의 순서를 계약으로 만들기** 위해서다.\
  `HashMap` 을 쓰면 순회 순서가 기계와 JDK 판에 따라 달라지고, 그러면 답이 하나로 안 정해져 두 구현을 맞대볼 수가 없다.\
  `TreeMap` 이면 순회 자체가 오름차순이라 `ls` 가 따로 정렬할 필요가 없다.\
  평면 맵 쪽은 `HashMap` 이라 `ls` 안에서 `out.sort(null)` 을 직접 한다 — 같은 계약을 다른 방식으로 지키는 것이다.\
  05번의 "해시 순회 순서에 기대지 마라"가 여기서는 **검증 가능성의 전제**가 된다.

- Q: 같은 계약을 두 구조가 어떻게 다르게 지키는지 한 쌍만 보자면?\
  A: `mkdirs`(없는 부모를 만들며 내려간다)가 좋은 예다.\
  트리는 **한 걸음씩 내려가며 없으면 만든다**. 평면 맵은 **경로를 누적해 가며 키를 하나씩 넣는다**.

```java
// impl/TreeFileSystem.java — 노드를 타고 내려간다
Node current = root;
visitedNodes++;
for (String part : Paths.split(path)) {
    if (!current.isDirectory()) {
        throw new IllegalArgumentException("경로 중간이 파일이다: " + Paths.normalize(path));
    }
    Node next = current.children().get(part);
    if (next == null) {
        next = Node.directory(part);
        current.children().put(part, next);
    }
    current = next;
    visitedNodes++;
}
```

```java
// impl/FlatPathFileSystem.java — 경로 문자열을 누적하며 키를 넣는다
String here = Paths.ROOT;
for (String part : Paths.split(path)) {
    here = Paths.join(here, part);
    visitedNodes++;
    if (entries.containsKey(here)) {
        if (entries.get(here) != null) {
            throw new IllegalArgumentException("경로 중간이 파일이다: " + Paths.normalize(path));
        }
        continue;
    }
    entries.put(here, null);
}
```

```text
두 구현이 같은 계약을 다른 방식으로 지킨다

  "경로 중간이 파일이면 던진다"
    트리   : current.isDirectory() 로 본다 — 노드의 종류를 직접 물어본다
    평면 맵 : entries.get(here) != null 로 본다 — 값이 Blob 이면 파일이라는 규약

  README 의 변종 실험에서 살아남은 하나가 이 검사를 지운 것이었다.
  검사를 지워도 결국 다른 예외가 나서, "예외의 종류를 안 보는" 테스트로는 구별이 안 됐다.
  그래서 테스트를 더 넣었다 — 무엇이 던져지는지까지 봐야 한다는 교훈이다.
```

**더 생각할 것**

- "계약 테스트를 다 통과하는 더 쉬운 구현이 있다"는 것은 나쁜 소식이 아니라 **기준선을 얻었다**는 좋은 소식이다.\
  32번의 `LinearScanEngine` 과 똑같은 역할이다 — 쉬워서 믿을 수 있으니 대조의 기준이 된다.
- 반대로 말하면, 기준선보다 복잡한 구현을 도입할 때는 **그 복잡함이 무엇을 사는지 수치로 대야 한다**.\
  "트리가 자연스럽다" 같은 말로는 부족하다. 이 박스는 그 수를 1 대 341 로 적었다.
- 실무의 S3 가 "폴더가 진짜로는 없는" 이유가 이 박스의 평면 맵이다.\
  키가 곧 경로 문자열이라 `ls` 에 해당하는 연산이 접두사 스캔이고, 그래서 느리고 비싸다.

#### 2. 각각 어떤 접근 패턴에 적합한가 — "짚는 일"과 "묻는 일"의 경계

- Q: 트리에 적합한 접근 패턴은?\
  A: **관계를 묻는 일** 전부다.\
  "이 디렉터리의 자식은 누구인가"(`ls`), "여기부터 찾아라"(`find`), "이 서브트리의 크기는"(`size`), "이 서브트리를 통째로 옮겨라"(`mv`).\
  관계가 참조로 적혀 있으므로, 물으면 그 참조만 따라가면 된다. 관계없는 곳은 아예 안 본다.

- Q: 평면 맵에 적합한 접근 패턴은?\
  A: **경로 하나를 짚는 일**이다.\
  `read`, `write`, `exists`, `isDirectory` — 전부 키 하나를 해시로 찾으면 끝난다.\
  깊이가 얼마든 해시 한 번이다. 트리는 깊이만큼 내려가야 한다.

- Q: 그 둘의 경계는 어디인가?\
  A: **답을 내는 데 다른 항목을 봐야 하는가**가 경계다.\
  경로 하나의 내용만 필요하면 그 키만 보면 된다 → 평면 맵이 이긴다.\
  답이 "이 경로와 관계된 다른 항목들"이면 관계를 알아야 한다 → 트리가 이긴다.\
  한 문장으로: **평면 맵은 점(point) 질의에 강하고, 트리는 범위(range) 질의에 강하다.**\
  그리고 파일 시스템에서 "범위"는 곧 서브트리다.

```text
같은 연산이 두 구조에서 어떻게 갈리나 (MeasurementTest 가 assert 한 값)

  연산               트리      평면 맵    갈리는 이유
  ----------------- --------- ---------- --------------------------------------
  read (깊이 21)        22         1      트리는 조각 수만큼 내려간다 / 맵은 해시 한 번
  ls (/a 의 자식)        2       343      트리는 자기 자식만 / 맵은 전체를 훑어 부모를 되살린다
  find (/small 안)       3       345      트리는 서브트리만 / 맵은 관계없는 /big 까지 전부
  mv (디렉터리)          1       341      트리는 링크 하나 / 맵은 자손의 키를 전부 다시 쓴다
  cp (서브트리)         85        85      둘 다 내용을 새로 만들어야 한다. 구조가 안 구해준다
```

- Q: "평면 맵에는 부모·자식 관계가 어디에도 안 적혀 있다"는 사실이 무엇을 강제하는가?\
  A: **관계를 물을 때마다 전체를 훑어 문자열로 되살리는 것**을 강제한다.\
  `ls` 가 그 증거다 — 자식 셋을 얻으려고 항목 342개를 전부 본다.

```java
// impl/FlatPathFileSystem.java — 관계가 없으니 전부 훑어 되살린다
for (String key : entries.keySet()) {
    visitedNodes++;
    if (!key.equals(p) && Paths.parent(key).equals(p)) {
        out.add(Paths.name(key));
    }
}
out.sort(null);
```

```text
왜 전부 훑어야 하나

  entries 의 키는 "/a/d0", "/a/d0/f1.txt", "/big/d3/d2", ... 처럼 그냥 문자열이다
  "/a 의 자식" 을 알려면, 키 하나하나에 대해 Paths.parent(key) 를 계산해 "/a" 와 같은지 봐야 한다

  Paths.parent 는 문자열을 자르는 게 아니라 정규화 -> split -> 다시 잇기다
  즉 항목마다 문자열 연산이 한 벌씩 붙는다. 342개면 342벌이다

  트리는 node.children().keySet() 하나다. 이미 관계가 적혀 있기 때문이다
```

- Q: 각각 언제 쓰면 안 되는가?\
  A: 트리를 쓰면 안 될 때 — 경로가 아주 깊고 **관계를 거의 안 묻는** 워크로드.\
  깊이 21짜리 경로를 반복해서 여는 것만 한다면 트리는 매번 22번 내려가고 아무 이득이 없다.\
  평면 맵을 쓰면 안 될 때 — 항목이 많고 **관계를 자주 묻는** 워크로드.\
  항목 34만 개에 `ls` 를 하면 34만 번 훑는다. 자식이 셋이든 말든 상관없다.\
  그리고 디렉터리 `mv`·`rmr` 이 잦으면 치명적이다 — 자손 수에 정비례하는 일을 매번 한다.

> **점 질의(point lookup)** — 키 하나로 값 하나를 찾는 조회.\
> 예: `read("/a/b/f.txt")` 는 그 경로의 내용만 있으면 된다. 다른 항목을 볼 필요가 없다.

> **범위 질의(range query)** — 어떤 조건에 맞는 항목들을 한꺼번에 묻는 조회. 파일 시스템에서는 서브트리다.\
> 예: `ls("/a")`, `find("/a", "x.txt")`, `size("/a")` 는 전부 `/a` 아래 전체가 답의 재료다.

> **관계를 적어둔다(materialized relationship)** — 관계를 계산으로 되살리는 대신 참조로 저장해 두는 것.\
> 예: 트리는 `children` 맵에 부모-자식을 적어둔다. 평면 맵은 안 적어두고 `Paths.parent(key)` 로 매번 계산한다.

- Q: `size` 와 `rmr` 도 같은 구도인가?\
  A: 그렇다. 둘 다 "서브트리 전체"가 답의 재료라 트리가 이긴다.

```java
// impl/TreeFileSystem.java — 자기 서브트리만 재귀로 돈다
private long sizeOf(Node node) {
    if (!node.isDirectory()) {
        return node.blob().content().length();
    }
    long total = 0;
    for (Node child : node.children().values()) {
        visitedNodes++;
        total += sizeOf(child);
    }
    return total;
}
```

```java
// impl/FlatPathFileSystem.java — 전체를 훑으며 조상 판정을 한다
for (Map.Entry<String, Blob> e : entries.entrySet()) {
    visitedNodes++;
    if (e.getValue() != null && Paths.isAncestorOrSame(p, e.getKey())) {
        total += e.getValue().content().length();
    }
}
```

```text
비용의 모양이 다르다

  트리   : O(그 서브트리의 항목 수)          답의 크기에 비례한다
  평면 맵 : O(전체 항목 수) x O(경로 조각 수)  전체 크기에 비례하고, 항목마다 문자열 연산까지 붙는다

  작은 디렉터리의 size 를 물어도 평면 맵은 큰 시스템 전체를 훑는다.
  "답이 작으면 싸야 한다" 는 감각이 여기서 안 통한다 — 32번의 최악과 같은 형태다.

  rmr 도 똑같이 전체를 훑어 doomed 목록을 만든 뒤 지운다.
  그리고 평면 맵의 rmdir 은 안에서 ls 를 부르므로(비었는지 보려고) 거기서도 전체 훑기가 한 번 붙는다.
```

**더 생각할 것**

- "무엇을 적어두고 무엇을 계산할 것인가"는 자료구조 설계의 큰 축이다.\
  적어두면 그 질문이 싸지고, 대신 **바뀔 때마다 갱신해야** 한다(그 비용이 `mv` 에서 평면 맵이 지는 이유의 거울상이다).
- 32번의 역색인이 "항 → 문서" 관계를 적어둔 것과 정확히 같은 결정이다.\
  적어둔 방향은 싸고, 그 반대 방향(문서 삭제)은 비싸진다.
- 실제 파일 시스템은 둘 다 한다 — 트리(inode + 디렉터리 엔트리)로 관계를 적어두고, 경로 캐시(dentry cache)로 점 질의도 빠르게 만든다.\
  "둘 중 하나"가 아니라 "둘 다 들고 동기화"가 실무의 보통 답이다.

#### 3. `mv` · `ls` · `find` · `read` 의 비용이 왜 갈리는가 · `cp` 는 왜 같은가

- Q: `mv` 에서 트리가 1, 평면 맵이 341 인 구조적 이유는?\
  A: 트리에서 **경로는 값이 아니라 위치**다. 노드는 자기 이름만 알고 전체 경로를 모른다.\
  그래서 옮기는 것은 부모의 링크 하나를 고치는 일이고, 그 아래가 몇 개든 상관없다.\
  평면 맵에서 **경로가 곧 키**다. 옮기면 그 아래 있던 모든 항목의 키가 달라지므로 전부 다시 써야 한다.

```java
// impl/TreeFileSystem.java — 링크 둘을 고치고 끝
oldParent.children().remove(Paths.name(from));
newParent.children().put(newName, rename(node, newName));
// 링크 두 개를 고쳤을 뿐이다. 서브트리가 몇 개든 상관없다.
rewrittenEntries = 1;
```

```java
// impl/FlatPathFileSystem.java — 자손의 키를 전부 다시 쓴다
for (String key : entries.keySet()) {
    visitedNodes++;
    if (Paths.isAncestorOrSame(from, key)) {
        moving.add(key);
    }
}
for (String key : moving) {
    Blob blob = entries.remove(key);
    entries.put(to + key.substring(from.length()), blob);
    rewrittenEntries++;
}
```

```text
mv("/src", "/dst/moved") — /src 아래 항목 341개

  [트리]
    before                        after
      root                          root
       +-- src ---- (341개)          +-- dst
       +-- dst                             +-- moved ---- (341개)   <- 같은 서브트리 그대로

    고친 것 : oldParent 에서 "src" 링크 제거 + newParent 에 "moved" 링크 추가
    rewrittenEntries = 1    (assertEquals(1, tree.rewrittenEntries()))

  [평면 맵]
    "/src"                -> "/dst/moved"
    "/src/d0"             -> "/dst/moved/d0"
    "/src/d0/d1"          -> "/dst/moved/d0/d1"
    ... 341줄 전부 ...
    rewrittenEntries = 341  (assertEquals(341, flat.rewrittenEntries()))

  깊이를 1, 2, 3 으로 늘리면 평면 맵은 21 -> 85 -> 341 로 늘고 트리는 계속 1 이다
  (21/85/341 은 fill(fs, "/src", 4, depth) 가 만드는 항목 수다.
   깊이1 = 1+4+16, 깊이2 = 1+4+16+64, 깊이3 = 1+4+16+64+256.
   테스트는 세 깊이 모두에서 tree == 1 만 assert 하고 341 은 깊이 3 에서 assert 한다.)
```

- Q: `ls` 에서 2 대 343 인 이유는?\
  A: 트리는 **루트와 `/a` 만** 본다 — 내려가는 길이 두 걸음이고, 자식 목록은 이미 `/a` 안에 있다.\
  평면 맵은 `requireDirectory` 로 한 번(1) + 전체 항목 342개를 훑어(342) = 343 이다.\
  항목 342개는 `fill(fs, "/a", 4, 3)` 이 만든 것이다: 루트 1 + `/a` 1 + 디렉터리 4+16+64 + 파일 256 = 342.\
  요점은 **답의 크기(자식 4개)와 비용(343)이 아무 상관이 없다**는 것이다.

- Q: `find` 에서 3 대 345 인 이유는?\
  A: 트리의 `find` 는 `requireNode` 로 `/small` 까지 내려가고(root + small = 2) 그 서브트리만 훑는다(자식 1개 = +1) → 3.\
  평면 맵은 `requireExists` 1 + 전체 344개 훑기 = 345.\
  **옆에 있는 큰 서브트리 `/big`(341개)까지 전부 본다** — `/small` 을 찾으랬는데 `/big` 을 훑는다.\
  트리는 "여기부터"라는 말을 구조로 이해하고, 평면 맵은 그 말을 **필터 조건**으로만 이해한다.

```text
find("/small", "target.txt") — 옆에 /big(341개)이 있다

  [트리]   root -> small 로 내려가고(2), small 의 자식 하나를 본다(+1)  = 3
           /big 은 아예 안 본다. 다른 가지이기 때문이다

  [평면 맵] 키 344개를 전부 돌면서 Paths.isAncestorOrSame("/small", key) 를 계산한다
           /big/... 341개에 대해서도 그 계산을 한다. 전부 false 다              = 345

  "여기부터 찾아라" 를 트리는 출발점으로 쓰고, 평면 맵은 필터로 쓴다
```

- Q: `read` 에서 22 대 1 인 이유는? 그리고 이건 트리가 지는 자리인가?\
  A: 맞다, 여기서는 **트리가 진다**.\
  깊이 21인 경로를 읽으면 트리는 루트 + 조각 21개 = 22번 내려간다.\
  평면 맵은 경로 문자열 하나로 해시 한 번이다.\
  `assertEquals(22, tree.visitedNodes())` 와 `assertEquals(1, flat.visitedNodes())` 가 그대로 못 박혀 있다.\
  README 가 "정직하게 적어둔다"고 한 자리가 여기다 — **트리가 늘 이기는 것이 아니라 무엇을 물어보느냐가 정한다.**

- Q: `cp` 만 둘이 85 로 같은 것은 왜인가?\
  A: `cp` 는 **관계가 아니라 내용을 만드는** 연산이기 때문이다.\
  `mv` 는 "이 서브트리를 저 아래로"라는 관계 변경이라, 관계를 참조로 들고 있으면 한 번에 끝난다.\
  `cp` 는 사본이 원본과 **독립적이어야** 하므로, 항목 하나하나에 새 노드와 새 `Blob` 을 만들어야 한다.\
  그 일은 구조와 무관하게 서브트리 크기에 정비례한다.

```java
// impl/TreeFileSystem.java — cp 는 노드마다 새로 만든다
private Node deepCopy(Node node, String newName) {
    rewrittenEntries++;
    if (!node.isDirectory()) {
        return Node.file(newName, new Blob(node.blob().content()));
    }
    Node copy = Node.directory(newName);
    for (Map.Entry<String, Node> e : node.children().entrySet()) {
        visitedNodes++;
        copy.children().put(e.getKey(), deepCopy(e.getValue(), e.getKey()));
    }
    return copy;
}
```

```text
mv 와 cp 의 차이를 한 줄로

  mv  : 참조 하나를 옮긴다      -> 서브트리가 "따라온다"       -> 트리에서 O(1)
  cp  : 내용을 새로 만든다      -> 따라올 수 있는 것이 없다     -> 어디서나 O(서브트리 크기)

  fill(fs, "/a", 4, 2) 는 항목 85개다 (1 + 4 + 16 + 64)
  assertEquals(85, tree.rewrittenEntries()) / assertEquals(85, flat.rewrittenEntries())

  구조가 구해줄 수 있는 것은 "안 해도 되는 일" 뿐이다.
  반드시 해야 하는 일(내용 만들기)은 어떤 구조도 안 줄여준다.
```

- Q: 그러면 파일 하나를 `mv` 하면?\
  A: 둘 다 1 이다. `movingASingleFileIsTheSame` 이 `assertEquals(1, ...)` 을 양쪽에 건다.\
  트리의 이점은 **서브트리가 있을 때만** 나온다.\
  "트리가 빠르다"가 아니라 "트리는 서브트리 크기에 비례하는 일을 안 한다"가 정확한 진술이다.

> **관계 변경 대 내용 생성** — 무엇을 가리키는지만 바꾸는 연산과, 새 실체를 만들어야 하는 연산.\
> 예: `mv` 는 앞쪽, `cp` 는 뒤쪽. 앞쪽만 구조 선택으로 싸게 만들 수 있다.

> **경로가 값인가 위치인가** — 평면 맵에서 경로는 저장된 값(키)이고, 트리에서 경로는 걸어서 도달하는 위치다.\
> 예: 트리의 `Node` 는 자기 전체 경로를 모른다. 그래서 부모가 바뀌어도 노드를 안 고쳐도 된다.

**더 생각할 것**

- 비용이 갈리는 지점을 일반화하면 **"식별자에 위치 정보가 박혀 있는가"** 다.\
  박혀 있으면(평면 맵의 경로 키) 위치가 바뀔 때 식별자를 전부 다시 써야 한다.\
  실무의 예 — URL 에 카테고리를 넣으면 카테고리를 옮길 때 URL 이 전부 바뀐다. DB 에서 자연키 대신 대리키를 쓰는 이유도 같다.
- `rewrittenEntries` 라는 자를 따로 둔 것이 설계의 핵심이다.\
  "옮기기가 빠르다"를 시간으로 재면 기계 차이에 묻히는데, **다시 쓴 키의 개수**로 재면 1 대 341 이 선명하게 남는다.
- `cp` 가 같다는 사실을 표에 남긴 것도 중요하다.\
  자기 구조가 이기는 칸만 적으면 그건 측정이 아니라 홍보다.

#### 4. 트리가 지는 최악 패턴 · 평면 맵의 최악 · 각각의 최선

- Q: 트리가 평면 맵에 지는 최악의 사용 패턴은?\
  A: **깊은 경로 하나를 반복해서 여는 것**이다. 관계는 한 번도 안 묻는다.

```text
깊이 21 인 경로를 n 번 읽는 워크로드

  트리     : 한 번에 22 (루트 + 조각 21)   ->  총 22n
  평면 맵  : 한 번에 1 (해시)              ->  총 n

  n = 100만이면 2,200만 대 100만이다. 22배다.
  게다가 트리 쪽 22번은 매번 맵 조회 + 참조 따라가기라 캐시 지역성도 나쁘다.

  MeasurementTest.deepLookupFavoursTheFlatMap 가 한 번의 값을 assert 한다
    assertEquals(22, tree.visitedNodes())
    assertEquals(1, flat.visitedNodes())
  (총 비용 22n 은 그 값을 n 번 곱한 것 — 테스트가 assert 한 것은 한 번의 값이다.)
```

- Q: 트리가 그 패턴에서 지는 이유를 한 문장으로?\
  A: **트리의 비용은 답까지의 깊이에 붙고, 평면 맵의 비용은 항목 수에 붙는다.**\
  그래서 깊이가 크고 항목 수가 작으면 평면 맵이, 깊이가 작고 항목 수가 크면 트리가 유리하다.\
  그리고 "관계를 묻는가"가 그 위에 한 겹 더 얹힌다 — 관계를 물으면 평면 맵은 항상 항목 수 전체를 낸다.

- Q: 평면 맵의 최악은? 깊이 1·2·3 에서 21 → 85 → 341 로 느는 그 연산은 무엇인가?\
  A: **디렉터리 `mv`** 다. `theGapGrowsWithTheSubtree` 가 그 세 값을 찍는다.\
  정확히는 "`mv` 한 번에 다시 쓴 키의 개수"이고, 그 수가 곧 옮기는 서브트리의 항목 수다.\
  같은 성질이 `rmr`(서브트리 삭제)과 `size`, `find` 에도 그대로 있다 — 전부 전체 훑기다.

```text
평면 맵이 무너지는 워크로드 : 디렉터리 이름을 자주 바꾸는 시스템

  /project/v1 아래에 항목 10만 개가 있다
  mv("/project/v1", "/project/v2") 한 번 = 키 10만 개 삭제 + 10만 개 삽입

  게다가 이것이 원자적이지도 않다. 중간에 실패하면 절반만 옮겨진 상태가 남는다
  트리는 링크 하나를 바꾸는 일이라 그 문제 자체가 없다

  실무 대응 : S3 에는 "디렉터리 이름 바꾸기" API 가 아예 없다.
              복사하고 지우는 수밖에 없고, 그래서 비싸고 느리다.
```

- Q: 각각의 최선은 어떤 워크로드인가?\
  A: 트리의 최선 — **얕고 넓은 구조에서 관계를 자주 묻고, 서브트리를 통째로 옮기거나 지우는** 워크로드.\
  `ls`(2), `find`(3), `mv`(1) 이 전부 답의 크기에만 비례한다.\
  평면 맵의 최선 — **깊은 경로를 점으로만 찍어 읽고 쓰며, 구조를 거의 안 건드리는** 워크로드.\
  객체 저장소가 딱 그 모양이다 — 키로 `GET`/`PUT` 만 하고 목록 조회는 드물고 비싸다.

```text
정리하면

                        트리        평면 맵
  깊은 경로 점 조회     불리(22)     유리(1)
  얕은 구조             유리         상관없음
  관계 질의(ls/find)     유리         불리(항목 수 전체)
  서브트리 mv/rmr       유리(1)      불리(서브트리 크기)
  cp                     동률(85)     동률(85)
  항목이 아주 많음       영향 없음    전 연산이 같이 나빠진다

  한 줄 : "얼마나 깊은가" 가 트리의 비용을, "얼마나 많은가" 가 평면 맵의 비용을 정한다
```

- Q: 이것이 25번·30번의 "최악이 정한다"와 같은 이야기인가?\
  A: 성격이 조금 다르다. (원본에 근거 없음 — 내 추론)\
  25번·30번은 **같은 구조에서 입력 분포에 따라 최악이 나오는** 이야기였다(모든 점이 같은 거리 등).\
  여기는 **두 구조가 서로의 최악을 나눠 갖는** 이야기다 — 한쪽의 최악이 다른 쪽의 최선이다.\
  공통점은 "평균만 보면 못 고른다"는 것이고, 그래서 둘 다 워크로드를 먼저 재야 한다.

**더 생각할 것**

- 최악 패턴을 만들 때 요령은 **그 구조가 값을 파는 조건을 지우는** 것이다.\
  트리는 "관계를 묻는다"에 값이 있으니 관계를 안 묻는 워크로드가 최악이다.\
  평면 맵은 "항목이 적거나 관계를 안 묻는다"에 값이 있으니, 항목이 많고 관계를 묻는 워크로드가 최악이다.
- 실제 시스템은 깊이가 그렇게 깊지 않다는 사실이 트리 쪽에 유리하게 작용한다.\
  대부분의 경로가 깊이 5~10 이면 트리의 lookup 도 상수에 가깝다.\
  "최악이 22번"과 "보통 6번"은 다른 이야기이고, 설계는 보통 쪽을 본다.
- 그래서 실제 파일 시스템은 트리를 쓰되 **경로 캐시**로 점 조회를 상수로 만든다.\
  두 구조의 장점을 합치는 방향이지, 하나를 고르는 문제가 아니다.

#### 5. `Paths` 가 공통 조상이라는 사실이 검증에 무엇을 강제하는가

- Q: `Paths` 가 공통 조상이라는 것은 무슨 뜻인가?\
  A: 두 구현이 **같은 경로 규칙 코드를 그대로 호출한다**는 뜻이다.\
  `TreeFileSystem` 은 `Paths.split`, `Paths.parent`, `Paths.name`, `Paths.join`, `Paths.isAncestorOrSame` 을 쓴다.\
  `FlatPathFileSystem` 도 정확히 같은 것들을 쓴다.\
  두 구현의 "차이"는 경로를 해석한 뒤의 저장 방식뿐이고, 해석 자체는 공유다.

- Q: 그래서 무엇이 강제되는가?\
  A: **`Paths` 가 틀리면 두 구현이 똑같이 틀린다** → 무작위 대조가 그것을 절대 못 잡는다.\
  대조는 "두 답이 같은가"만 보는데, 둘 다 같은 방식으로 틀리면 둘은 여전히 같다.\
  그래서 `PathsTest` 가 별도 파일로 있고, README 도 "대조로 못 잡는 것은 대조 밖에서 봐야 한다"고 적는다.

```text
대조 테스트가 볼 수 있는 것과 볼 수 없는 것

  두 구현이 다르게 틀린다   ->  스냅샷이 갈린다    ->  CrossCheckTest 가 잡는다
  두 구현이 같게 틀린다     ->  스냅샷이 같다      ->  영영 못 잡는다

  같게 틀리는 경로는 하나뿐이다: 공유하는 코드가 틀리는 것 = Paths

  32번의 대조에도 같은 구멍이 있었다.
  거기서는 "분석기" 가 공유 부품이라, 분석기가 틀리면 두 엔진이 똑같이 0건을 냈다.
  AnalyzerMismatchTest 가 여기서의 PathsTest 와 같은 자리다.
```

> **공통 조상 결함(shared-dependency bug)** — 두 구현이 함께 쓰는 부품이 틀려서, 서로 대조해도 안 잡히는 결함.\
> 예: `Paths.normalize` 가 `..` 를 잘못 다루면 트리와 평면 맵이 똑같이 잘못된 자리를 가리킨다.

- Q: `..` 이 루트를 넘어가려 할 때 무엇이 조용히 깨지는가?\
  A: 안 막으면 **경로가 루트 밖을 가리킨다**.\
  `normalize` 는 조각을 스택에 쌓다가 `..` 을 만나면 하나 뺀다. 스택이 비었으면 아무것도 안 한다 — 그 한 줄이 방어선이다.

```java
// impl/Paths.java
if (part.equals("..")) {
    // 비었으면 아무것도 안 한다. 루트 위로는 못 올라간다.
    if (!stack.isEmpty()) {
        stack.remove(stack.size() - 1);
    }
    continue;
}
```

```text
그 한 줄이 없으면 (스택이 비어도 remove 를 시도하거나, 조각을 그냥 쌓으면)

  "/a/../../../etc"  ->  올바른 답은 "/etc"
                          안 막으면 "/../../etc" 같은 것이 남거나 예외가 난다

  PathsTest.cannotGoAboveRoot 가 다섯 줄로 못 박는다
    normalize("/..")            = "/"
    normalize("/../../..")      = "/"
    normalize("/../a")          = "/a"
    normalize("/../../a")       = "/a"
    normalize("/a/../../../etc") = "/etc"

  실제 시스템에서 이 자리가 취약점이다 (../../etc/passwd 류 경로 탈출).
  여기서는 취약점이 아니라 조용한 오답이 된다. 어느 쪽이든 테스트가 없으면 안 보인다.
```

- Q: 조상 판정을 문자열 접두사로 하면 무엇이 조용히 깨지는가?\
  A: **`/ab` 가 `/a` 의 자손으로 잡힌다.**\
  `"/ab".startsWith("/a")` 가 참이기 때문이다. 문자열은 조각 경계를 모른다.

```java
// impl/Paths.java — 조각 단위로 본다
public static boolean isAncestorOrSame(String ancestor, String path) {
    List<String> a = split(ancestor);
    List<String> b = split(path);
    if (a.size() > b.size()) {
        return false;
    }
    return a.equals(b.subList(0, a.size()));
}
```

```text
접두사 판정이 만드는 사고

  mv("/a", "/z") 를 한다. 평면 맵은 "from 의 자손" 을 전부 찾아 키를 다시 쓴다

  조각 단위 판정   isAncestorOrSame("/a", "/ab") = false
                    -> /ab 는 안 건드린다. 맞다

  문자열 접두사    "/ab".startsWith("/a") = true
                    -> /ab 가 /zb 로 끌려간다. 관계없는 형제가 통째로 이름이 바뀐다

  예외는 안 난다. mv 는 성공했다고 보고한다.
  PathsTest.prefixStringIsNotEnough 와
  FileSystemContractTest "접두사가 같을 뿐인 형제는 딸려가지 않는다" 가 이것을 잡는다
```

- Q: 디렉터리를 자기 안으로 옮기면 무엇이 조용히 깨지는가?\
  A: **서브트리가 트리에서 떨어져 나가 아무도 못 닿는 곳에 남는다.**\
  예외도 안 나고, 그냥 사라진 것처럼 보인다.

```text
mv("/a", "/a/b/c") 를 막지 않으면 (트리 기준)

  before                       "떼어내고 붙이기" 를 그대로 하면
    root                          root
     +-- a                         +-- (a 가 없어짐)
          +-- b
               +-- (여기로)         떼어낸 a 를, a 자신의 손자 자리에 붙인다
                                    -> a 는 자기 안에만 존재한다
                                    -> 루트에서 a 로 가는 길이 없다
                                    -> a 와 그 아래 전부가 도달 불가능해진다

  막는 방법 : from 이 to 의 조상이거나 같으면 던진다
    if (Paths.isAncestorOrSame(from, to)) { throw ... }

  그리고 이 판정을 문자열로 하면 위의 /ab 문제가 같이 따라온다.
  즉 "자기 안으로 못 옮기게 막기" 와 "형제를 안 끌고 가기" 가 같은 한 메서드에 걸려 있다.
```

- Q: 그래서 검증은 어떻게 짜여 있는가?\
  A: 세 겹이다.\
  하나 — `PathsTest`(12개): 공통 조상을 **대조 밖에서** 따로 본다.\
  둘 — `FileSystemContractTest`(34개 × 2구현 = 68): 두 구현이 같은 계약을 지키는지.\
  셋 — `CrossCheckTest`: 무작위 연산 3,200번(12 seed × 200 + 800)을 두 구현에 똑같이 넣고 **연산 하나마다** 전체 상태를 문자열로 찍어 비교한다.

```java
// src/test/.../CrossCheckTest.java — 매 연산마다 비교한다
assertEquals(snapshot(flat), snapshot(tree),
        "seed " + seed + " 의 " + step + "번째 연산 뒤에 갈렸다");
```

- Q: 왜 끝에서 한 번만 비교하지 않는가?\
  A: 갈린 지점을 바로 짚기 위해서다.\
  끝에서만 비교하면 "어디선가 갈렸다"만 알고, 어느 연산이 범인인지 찾으려면 처음부터 다시 재현해야 한다.\
  연산마다 비교하면 실패 메시지에 `step` 번호가 찍힌다.

- Q: 대조가 "그린 위장"에 빠지지 않게 하는 장치는?\
  A: 둘이다.\
  하나 — **한쪽만 예외를 던지면 그 자체를 불일치로 센다**(`assertEquals(threwA, threwB, "한쪽만 던졌다")`).\
  둘 — **실제로 수행된 연산 수를 따로 세어** 전체의 1/5 를 넘지 않으면 실패시킨다.\
  없으면 "둘 다 던졌다"만 3,200번 쌓여도 초록불이 나온다 — 아무것도 대조하지 않은 채로.

```java
// src/test/.../CrossCheckTest.java
// 전부 예외로 튕겨나가면 아무것도 대조하지 않은 것이다. 그린 위장을 막는다.
assertTrue(applied > operations / 5,
        "실제로 수행된 연산이 " + applied + "개뿐이다. 대조가 성립하지 않는다");
```

> **그린 위장(vacuous green)** — 테스트가 실제로는 아무것도 검사하지 않았는데 통과해버리는 상태.\
> 예: 무작위 연산이 전부 예외로 튕기면 스냅샷 비교가 매번 "빈 상태 == 빈 상태" 가 되어 항상 통과한다.

- Q: 스냅샷에 무엇을 담느냐가 왜 중요한가?\
  A: **담지 않은 것은 영영 대조되지 않기** 때문이다.\
  여기 `snapshot` 은 경로 + 내용 + 링크 수를 찍는다. 링크 수를 안 찍으면 하드 링크 관련 버그가 통째로 안 보인다.

```java
// src/test/.../CrossCheckTest.java
out.append(path).append(" = ").append(fs.read(path))
        .append(" (링크 ").append(fs.linkCount(path)).append(")\n");
```

- Q: 변종(mutant) 실험이 무엇을 말해주는가?\
  A: README 는 변종 10개를 심어 전부 잡혔다고 적는다. 살아남을 뻔한 하나가 `mkdirs` 중간의 파일 검사를 지운 것이었다.\
  지워도 결국 **다른 예외**가 나서, 예외의 종류를 안 보는 테스트로는 구별이 안 됐다.\
  교훈은 둘이다 — 하나, "던진다"만 보는 계약은 약하다.\
  둘, 변종을 심어보기 전에는 **내 테스트가 무엇을 못 잡는지 알 수 없다**.\
  (원본에 근거 없음 — 내 추론) 이것이 돌연변이 테스트(mutation testing)의 축소판이고, 커버리지 수치보다 훨씬 정직한 신호다.

> **돌연변이 테스트(mutation testing)** — 구현에 일부러 결함을 심어 테스트가 잡는지 확인해, 테스트의 힘을 재는 방법.\
> 예: `mkdirs` 의 파일 검사를 지운 변종이 통과하면 그 검사를 지키는 테스트가 없다는 뜻이다.

> **스냅샷 비교(snapshot / state equivalence)** — 전체 상태를 하나의 문자열로 찍어 두 구현을 통째로 견주는 방식.\
> 예: 여기 `snapshot` 은 경로·내용·링크 수까지 찍는다. 링크 수를 빼면 하드 링크 버그를 못 본다.

**더 생각할 것**

- 대조 테스트를 쓸 때 반드시 같이 물어야 할 질문이 **"두 구현이 무엇을 공유하는가"** 다.\
  공유하는 부분은 대조의 사각지대이고, 그만큼 따로 검증해야 한다.
- 그리고 **"대조가 실제로 무언가를 보고 있는가"** 도 물어야 한다.\
  `TheCrossCheckHasTeeth` 라는 중첩 클래스가 그 질문을 테스트로 만든 것이다 — 내용이 바뀌면 스냅샷이 바뀌는지, 한쪽만 던지면 잡히는지를 직접 확인한다.\
  **테스트를 테스트하는** 자리이고, 무작위 대조처럼 "왜 통과했는지 알기 어려운" 검증에는 이게 꼭 필요하다.
- 결정적 난수를 직접 만든 이유도 같은 맥락이다.\
  `java.util.Random` 을 쓰면 JDK 판이 바뀔 때 같은 seed 가 다른 수열을 내서 재현이 안 된다.\
  32번의 `TestSupport.Dice` 와 같은 코드를 여기서도 쓴다.

#### 6. 이름과 내용을 갈라놓으면 왜 트리가 아니게 되는가

- Q: 이름과 내용을 갈라놓는다는 것은 코드로 무엇인가?\
  A: `Node` 에 이름이 있고, `Blob` 에 내용이 있다. 노드는 블롭을 **가리킬 뿐 소유하지 않는다.**\
  실제 파일 시스템의 inode 가 `Blob` 자리다 — 이름은 디렉터리 엔트리에, 내용은 inode 에 있다.

```java
// impl/Blob.java — 갈라놓은 대가가 참조 수 관리다
private String content;
private int links;

void retain() {
    links++;
}

/** 이름 하나가 사라졌다. 0 이 되면 내용이 죽은 것이다. */
boolean release() {
    links--;
    return links <= 0;
}
```

- Q: 왜 그 순간 트리가 아니게 되는가?\
  A: 트리의 정의는 **"모든 노드의 부모가 하나"** 인데, 서로 다른 노드 둘이 같은 `Blob` 을 가리키면 내용 쪽에서 본 부모가 둘이 되기 때문이다.\
  이름은 여전히 트리에 하나씩 달려 있다 — 깨지는 것은 이름 층이 아니라 **내용 층**이다.\
  구조 용어로는 트리가 아니라 **DAG(방향 비순환 그래프)** 가 된다.

```text
하드 링크를 걸면

  [이름 층 — 여전히 트리]         [내용 층 — 트리가 아니다]
      root
       +-- a.txt  ------------------>  Blob("hello")   links = 2
       +-- b.txt  ------------------>       ^
                                            |
              두 이름이 같은 내용을 가리킨다. 내용에서 보면 부모가 둘이다

  link("/a.txt", "/b.txt") 가 하는 일
    node.blob().retain();                              links 1 -> 2
    newParent.children().put("b.txt", Node.file("b.txt", node.blob()));
                                                        같은 Blob 을 가리키는 새 노드
```

- Q: "지운다"의 뜻이 어떻게 바뀌는가?\
  A: **이름을 지우는 것**과 **내용을 지우는 것**이 갈라진다.\
  `rm` 은 부모의 자식 맵에서 이름을 빼고 `release()` 를 부른다. 링크가 0 이 될 때만 내용이 죽는다.

```java
// impl/TreeFileSystem.java
parent.children().remove(name);
// 이름 하나가 사라졌다. 내용은 마지막 이름이 사라질 때만 죽는다.
node.blob().release();
```

```text
세지 않으면 둘 중 하나가 일어난다 (Blob 의 주석 그대로)

  너무 일찍 죽인다   이름 하나를 지웠는데 다른 이름으로 읽던 것이 같이 사라진다
  영영 안 죽인다     이름을 다 지웠는데 내용이 남는다. 실제 시스템에서는 누수다

  FileSystemContractTest "이름 하나를 지워도 내용은 남는다" 가 앞쪽을 잡는다
```

- Q: 11번 블룸 필터의 "A를 지우면 B가 같이 사라진다"와 왜 같은 모양인가?\
  A: **하나의 저장 자리를 여럿이 나눠 쓰는데, 지우는 쪽은 자기 몫만 안다**는 점이 같다.\
  블룸 필터에서는 비트 하나를 여러 원소의 해시가 함께 세우므로, A 때문에 세운 비트를 내리면 그 비트에 의존하던 B 도 "없음"이 된다.\
  여기서도 `Blob` 하나를 여러 이름이 함께 가리키므로, 한 이름 때문에 지우면 다른 이름이 읽던 내용이 사라진다.

- Q: 그런데 여기서는 왜 고칠 수 있는가?\
  A: **몇이 쓰고 있는지 셀 수 있기** 때문이다.\
  블룸 필터의 비트는 0 또는 1 이라 "누가 몇 번 세웠는지"를 담을 자리가 없다 — 비트 하나에 정보가 1비트뿐이다.\
  `Blob` 은 `int links` 라는 칸이 있어서 세면 된다.\
  블룸 필터도 비트 대신 카운터를 두면 같은 방식으로 고칠 수 있다(counting Bloom filter). 대신 메모리가 몇 배가 된다.\
  즉 **"못 고친다"가 아니라 "그 구조가 값을 산 지점이 세는 것을 포기한 자리"** 였다.

> **참조 수 세기(reference counting)** — 공유되는 것을 몇이 쓰고 있는지 세고, 0 이 되면 버리는 방식.\
> 예: `Blob.links` 가 2 면 `rm` 한 번으로는 내용이 안 죽는다. 두 번째 `rm` 에서 0 이 되어 죽는다.

> **하드 링크(hard link)** — 같은 내용에 이름을 하나 더 붙이는 것. 사본이 아니라 또 하나의 이름이다.\
> 예: `link("/a.txt", "/b.txt")` 뒤에 `/b.txt` 에 쓰면 `/a.txt` 로 읽어도 바뀐 내용이 보인다.

- Q: 하드 링크가 되면 `write` 의 의미도 바뀌는가?\
  A: 바뀐다. **`Blob` 에 써야지 노드를 갈아끼우면 안 된다.**\
  기존 파일에 쓸 때 새 `Blob` 을 만들어 노드에 꽂으면, 링크로 이어진 다른 이름은 옛 내용을 계속 본다.

```java
// impl/TreeFileSystem.java — 노드가 아니라 Blob 에 쓴다
// Blob 에 쓴다. 하드 링크로 이어진 다른 이름에서도 같이 보여야 하기 때문이다.
existing.blob().setContent(content);
```

- Q: 디렉터리의 `linkCount` 는 왜 늘 1 인가?\
  A: 디렉터리에는 하드 링크를 못 걸게 막았으므로 이름이 하나뿐이고, 그리고 디렉터리에는 `Blob` 자체가 없다.\
  `return node.isDirectory() ? 1 : node.blob().links();` 가 그것을 그대로 적은 것이다.\
  (실제 유닉스에서 디렉터리의 링크 수가 2 이상인 것은 `.` 과 `..` 을 세기 때문인데, 이 구현에는 그 엔트리가 없다.)

- Q: 평면 맵도 하드 링크가 되는가?\
  A: 된다. 키 둘이 같은 `Blob` 을 가리키면 그만이다.\
  그래서 **하드 링크는 트리냐 맵이냐가 정하는 능력이 아니다** — 이름과 내용을 갈라놨느냐가 정한다.\
  구조가 정하는 것은 그 능력이 아니라 비용이다. 이 박스의 주제가 한 번 더 반복되는 자리다.

- Q: `cp` 와 `link` 가 한 글자 차이라는 것은?\
  A: **새 `Blob` 을 만드느냐, 그대로 가리키느냐** 딱 하나다.

```java
// cp — 새 Blob 을 만든다 (impl/TreeFileSystem.java deepCopy)
return Node.file(newName, new Blob(node.blob().content()));

// link — 같은 Blob 을 가리킨다 (impl/TreeFileSystem.java link)
node.blob().retain();
newParent.children().put(newName, Node.file(newName, node.blob()));
```

```text
그대로 가리키면 무슨 일이 생기나

  cp 를 했다고 생각하는데 실제로는 link 가 됐다면
    write("/copy.txt", "새 내용")  ->  /original.txt 도 같이 바뀐다

  예외는 안 난다. 복사 직후에는 내용이 같아서 테스트도 통과한다
  한참 뒤에 사본을 고쳤을 때 원본이 바뀐 것으로 드러난다

  FileSystemContractTest 가 그 둘을 따로 못 박는다
    "사본에 쓴 것이 원본에 비치면 안 된다"
    "cp 로 만든 것은 링크가 아니다"   (linkCount 가 1 인지 본다)
```

- Q: 26번 영속 자료구조는 구조를 공유해도 됐는데 `Blob` 은 왜 안 되는가?\
  A: **불변인가 가변인가**의 차이다.\
  26번의 공유 대상은 불변이라, 누가 무엇을 가리키든 값이 안 바뀐다. 그래서 공유가 안전하고 오히려 메모리를 아낀다.\
  `Blob` 은 `setContent` 로 내용이 바뀐다. 가변인 것을 공유하면 **한쪽의 쓰기가 다른 쪽에 비친다.**\
  그게 하드 링크에서는 원하는 동작이고, `cp` 에서는 버그다 — 같은 공유가 의도에 따라 기능이 되기도 하고 결함이 되기도 한다.\
  일반화하면 **공유해도 되는 것은 불변인 것뿐**이고, 가변인 것을 공유하려면 "공유하고 있다"는 사실을 계약에 적어야 한다.

- Q: 왜 디렉터리에는 하드 링크를 못 걸게 막는가?\
  A: **트리에 고리(cycle)가 생기기** 때문이다.

```java
// impl/TreeFileSystem.java
if (node.isDirectory()) {
    // 디렉터리에 하드 링크를 허용하면 트리에 고리가 생긴다.
    // 그러면 find 와 size 의 재귀가 안 끝난다. 실제 시스템도 같은 이유로 막는다.
    throw new IllegalArgumentException("디렉터리에는 하드 링크를 못 건다: " + existingPath);
}
```

```text
디렉터리에 링크를 걸면

    /a
     +-- b
          +-- link-to-a  ------> /a 를 가리킨다

  find("/", "x") 를 하면
    / -> a -> b -> link-to-a -> a -> b -> link-to-a -> ... 영원히

  collect 와 sizeOf 는 "자식이 없으면 멈춘다" 를 전제한 재귀다.
  고리가 있으면 그 전제가 깨지고 스택 오버플로로 끝난다.

  파일에 거는 하드 링크는 고리를 못 만든다. 파일에는 자식이 없기 때문이다.
  그래서 파일 링크는 허용하고 디렉터리 링크만 막는다. 실제 유닉스도 같다.
```

- Q: 이 구조의 한계가 34-dependency-resolver 의 "고리 찾기"를 어떻게 부르는가?\
  A: 여기서는 **고리가 생길 가능성을 입구에서 막았다**.\
  디렉터리 링크 금지, 자기 안으로 `mv` 금지 — 둘 다 "고리를 만들 수 있는 연산을 아예 거부"하는 방식이다.\
  막을 수 있었던 이유는 관계를 만드는 연산이 몇 개뿐이고, 각각 만들어질 고리의 모양이 뻔했기 때문이다.\
  34번에서는 그게 안 된다. **관계(의존)를 사용자가 자유롭게 아무 방향으로나 걸고**, 고리는 간선 여러 개가 합쳐졌을 때 비로소 생긴다.\
  간선 하나를 볼 때는 문제가 없다 — `a → b`, `b → c`, `c → a` 는 각각 정상이고 셋이 모여서야 고리다.\
  그래서 입구에서 못 막고 **전체를 훑어 찾아내야** 한다. 그 찾아내기가 34번의 본론이다.

```text
33번과 34번의 고리 문제

  33  고리를 만드는 연산이 유한하고 모양이 뻔하다
      -> 입구에서 거부한다 (isAncestorOrSame 판정 한 번, 디렉터리 링크 금지)
      -> 비용 O(경로 길이), 실패를 즉시 알려준다

  34  고리는 간선 여러 개가 합쳐져야 생긴다
      -> 입구에서 못 막는다. 전체를 훑어야 안다
      -> 비용 O(V + E), 그리고 "어디가 고리인지" 를 말해주는 것이 또 다른 문제다
         (칸 알고리즘은 있다는 것만 알고, DFS 는 경로까지 안다)

  같은 질문이 구조가 달라지면 난도가 달라진다.
```

**더 생각할 것**

- "왜 못 하게 막았나"를 묻는 것이 자료구조를 이해하는 좋은 방법이다.\
  막은 이유가 대개 **그 구조가 기대는 불변식**이기 때문이다.\
  여기서는 "재귀가 끝난다"가 그 불변식이고, 디렉터리 링크 금지가 그것을 지키는 방어선이다.
- 심볼릭 링크는 그 제약을 우회하는 다른 설계다. (원본에 근거 없음 — 내 추론)\
  경로 문자열을 담아두고 따라갈 때 다시 해석하므로 디렉터리도 가리킬 수 있고, 대신 고리가 생길 수 있어서 **따라가는 횟수에 상한**을 둔다.\
  "구조로 막기"와 "상한으로 막기"의 차이다.
- 33번까지 온 흐름을 한 줄로 이으면 — 32번은 **무엇을 키로 잡을지**, 33번은 **이름과 내용을 나눌지**를 물었다.\
  둘 다 답은 "그 결정이 무엇을 싸게 하고 무엇을 비싸게 하는지 재고 고른다"였고, 34번에서는 그 재는 방법 자체(대조 대 성질 검사)가 다시 문제가 된다.
