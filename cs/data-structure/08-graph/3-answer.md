### A. 문제 (GraphProblems)

#### 1. 최단 거리 — `bfsDistances`

**질문**: 어떻게 푸는가. 왜 깊이 우선이 아니라 너비 우선이어야 최단이 보장되는가. 방문 표시를 큐에 넣을 때 하느냐 꺼낼 때 하느냐가 무엇을 바꾸는가(정확성인가 비용인가).

**impl 코드** (`impl/GraphProblems.java`)

```java
public static int[] bfsDistances(Graph graph, int start) {
    int[] distance = new int[graph.vertexCount()];
    Arrays.fill(distance, -1);
    if (graph.vertexCount() == 0) return distance;

    Deque<Integer> queue = new ArrayDeque<>();
    distance[start] = 0;
    queue.addLast(start);

    while (!queue.isEmpty()) {
        int current = queue.removeFirst();
        for (int next : graph.neighbors(current)) {
            if (distance[next] == -1) {
                distance[next] = distance[current] + 1;
                queue.addLast(next);          // 넣을 때 표시했으므로 중복이 없다
            }
        }
    }
    return distance;
}
```

- 논리: `distance` 배열이 **두 역할을 겸한다** — 거리 저장소이자 방문 표시다.\
  `-1` 이면 아직 안 본 정점, `-1` 이 아니면 이미 거리가 확정된 정점이다.
- 논리: 배열 하나로 둘을 겸할 수 있는 이유는 "거리가 정해졌다 = 방문했다"가 BFS에서 동치이기 때문이다.
- 논리: 못 가는 정점은 `-1` 로 남는다 — `Arrays.fill(distance, -1)` 이 그 기본값을 깔아 둔다.
- 논리: `distance[next] = distance[current] + 1` 한 줄이 "한 칸 더 갔다"를 뜻한다.\
  가중치를 보지 않으므로 **간선 개수**만 센다(`ignoresWeights` 테스트).

> **너비 우선 탐색(BFS, breadth-first search)** — 시작점에서 가까운 것부터 층층이 넓혀 가며 방문하는 탐색.\
> 예: 거리 0의 정점 → 거리 1의 정점 전부 → 거리 2의 정점 전부 순으로 큐에서 나온다.

> **FIFO(first in, first out)** — 먼저 넣은 것이 먼저 나오는 규칙. 큐의 정의다.\
> 예: `addLast` 로 넣고 `removeFirst` 로 꺼내면 넣은 순서 그대로 나온다.

**왜 너비 우선이어야 최단인가**

```
큐의 내용을 시간 순으로 보면 거리가 '층'으로 묶여 나온다

  큐 : [ 시작점(0) ]                                <- 거리 0 층
       [ 거리1 정점들 ... ]                          <- 거리 1 층
       [ 거리2 정점들 ... ]                          <- 거리 2 층
       ...

  불변식 : 큐 안의 거리는 절대 감소하지 않는다(단조 비감소)
           거리 d 인 정점을 처리하면서 넣는 것은 전부 거리 d+1 이고,
           그것은 큐의 맨 뒤(= 거리 d 인 것들보다 뒤)에 붙는다

  따라서 어떤 정점 v 를 '처음' 만났을 때의 거리가 곧 최단 거리다
  나중에 다른 경로로 v 에 닿아도 그 경로의 길이는 반드시 같거나 더 길다
```

- 논리: FIFO 큐가 "거리 순 처리"를 공짜로 만들어 준다 — 정렬 장치가 따로 없는데 순서가 지켜진다.
- 논리: 그래서 `distance[next] == -1` 검사 하나로 "처음 만났는가"를 판정하면 그 값이 최단이 된다.
- 논리: 깊이 우선(스택, LIFO)은 그 단조성이 없다 — 나중에 넣은 것이 먼저 나오므로 **먼 길을 먼저 끝까지 파고든다**.

**깊이 우선이면 왜 틀리는가** (`shortestEvenWhenLongPathExploredFirst`)

```
방향 그래프 6개 정점. 간선 : 0->1, 0->2, 1->5, 2->3, 3->4, 4->5

              0
            /   \
          1       2
          |       |
          5       3
                  |
                  4
                  |
                  5        <- 4->5 (5 에 두 경로로 닿는다)

  정답 : 0->1->5 로 두 칸.  d[5] = 2

 BFS (큐, FIFO)
   큐 [0]           꺼냄 0 -> 이웃 1(d=1), 2(d=1) 넣음     큐 [1,2]
   큐 [1,2]         꺼냄 1 -> 이웃 5(d=2) 넣음             큐 [2,5]
   큐 [2,5]         꺼냄 2 -> 이웃 3(d=2) 넣음             큐 [5,3]
   큐 [5,3]         꺼냄 5 -> 이웃 없음                    큐 [3]
   ...
   결과 [0,1,1,2,3,2]   d[5] = 2   OK

 DFS (스택, LIFO) - 같은 이웃 순서 [1,2] 를 그대로 push 하면 2 가 먼저 나온다
   스택 [1,2]       꺼냄 2 (d=1) -> 3 넣음                 스택 [1,3]
   스택 [1,3]       꺼냄 3 (d=2) -> 4 넣음                 스택 [1,4]
   스택 [1,4]       꺼냄 4 (d=3) -> 5 넣음 (d=4)           스택 [1,5]
   스택 [1,5]       꺼냄 5 -> d[5] 가 4 로 굳는다          <- 틀림
   스택 [1]         꺼냄 1 -> 이웃 5 는 이미 방문됨 -> 2 로 못 고친다

   결과 d[5] = 4   X   (정답 2)
```

- 논리: 테스트 주석이 정확히 이 시나리오를 설명한다 — "2 쪽은 5까지 네 칸이고 1 쪽은 두 칸이다. 긴 쪽을 먼저 밟으면 5의 거리가 4로 굳는다".
- 한계: **작은 그래프에서는 깊이 우선으로도 우연히 맞는 답이 나온다**.\
  그래서 긴 경로를 먼저 탐색하게 만든 그래프가 테스트에 따로 필요했다.
- 한계: 이것이 "테스트가 통과했다 ≠ 맞다"의 그래프 판 사례다.\
  `findsDistances` 같은 기본 케이스만 있으면 DFS 구현도 통과해 버린다.

**방문 표시를 넣을 때 하느냐 꺼낼 때 하느냐**

```
 (A) 넣을 때 표시 (impl 이 택한 방식)

     for (next : neighbors) {
         if (distance[next] == -1) {      <- 판정
             distance[next] = ...;        <- 표시
             queue.addLast(next);
         }
     }

     같은 정점이 큐에 두 번 들어갈 수 없다
     큐 크기 <= V

 (B) 꺼낼 때 표시

     이웃을 조건 없이 전부 큐에 넣고, 꺼낸 뒤에 "이미 봤나"를 검사한다

     정점 v 의 이웃이 k 개면 v 는 최대 k 번 큐에 들어간다
     큐 크기 최대 = 간선 수 x 2 = O(E)

 정확성은?
     BFS 의 큐는 여전히 거리 단조 비감소다
     => 어떤 정점이 '처음 꺼내질 때'의 거리가 최단이라는 성질은 그대로다
     => 답은 맞는다. 바뀌는 것은 비용이다

 비용은?
     - 큐 메모리가 O(V) 에서 O(E) 로 커진다 (밀집 그래프면 V^2)
     - 같은 정점의 이웃 스캔을 중복해서 돌 위험이 생긴다
       (꺼낸 뒤 즉시 skip 하면 스캔은 한 번이지만, 큐 push/pop 횟수는 E 번)
```

- 논리: 그래서 답은 **비용**이다 — 정확성이 아니라 메모리와 큐 조작 횟수가 바뀐다.
- 한계: 단 이 코드처럼 `distance` 배열이 방문 표시를 겸하는 구조에서는 판정을 옮기면 거리 기록도 함께 옮겨야 한다.\
  표시만 옮기고 거리를 그대로 두면 같은 정점의 거리를 나중 경로로 덮어써 **정확성까지 깨진다**.\
  즉 "비용 문제"라는 답은 표시와 기록을 **한 덩어리로** 옮겼을 때의 이야기다.
- 비용(왜): 전체 비용은 인접 리스트에서 **O(V + E)** 다.\
  정점마다 한 번씩 꺼내고(V), 각 정점의 이웃 목록을 한 번씩 훑는다(합이 2E).
- 비용(왜): 인접 행렬 위에서는 `neighbors(v)` 가 매번 V 칸을 훑으므로 **O(V^2)** 이 된다(8번 참조).

**질문별 답**

- Q: 문제 1을 어떻게 푸는가?\
  A: `distance` 배열을 `-1` 로 채워 "미방문"을 표시하고, 시작점만 0으로 놓고 큐에 넣는다.\
  큐에서 하나 꺼내 이웃 중 `-1` 인 것에 `현재 거리 + 1` 을 써 주고 큐 뒤에 넣는다.\
  큐가 빌 때까지 반복하면 `-1` 로 남은 곳이 못 가는 정점이다.

- Q: 왜 너비 우선이어야 최단이 보장되는가?\
  A: FIFO 큐 덕에 큐 안의 거리가 **단조 비감소**로 유지되기 때문이다.\
  거리 d인 정점을 처리하며 넣는 것은 전부 d+1이고 그것들이 큐의 뒤에 붙으므로, 층이 순서대로 처리된다.\
  따라서 어떤 정점을 **처음 만난 순간의 거리가 곧 최단**이며, 그 뒤에 다른 경로로 닿아도 더 짧아질 수 없다.\
  깊이 우선은 나중에 넣은 것을 먼저 꺼내므로 이 단조성이 없어 먼 길을 먼저 굳혀 버릴 수 있다.

- Q: 방문 표시를 넣을 때 하느냐 꺼낼 때 하느냐가 무엇을 바꾸는가?\
  A: **비용**이다.\
  꺼낼 때 표시해도 큐의 거리 단조성은 유지되므로 첫 도달이 최단이라는 성질은 그대로다.\
  대신 같은 정점이 최대 자기 차수만큼 큐에 중복해 들어가 큐 메모리가 O(V)에서 O(E)로 커진다.\
  다만 이 코드처럼 거리 배열이 방문 표시를 겸하면 표시와 거리 기록을 함께 옮겨야 하고, 그러지 않으면 정확성까지 깨진다.

#### 2. 깊이 우선 방문 순서 — `dfsOrder`

**질문**: 어떻게 푸는가. 왜 재귀가 아니라 반복으로 짜야 하는가. 반복으로 짜면서 재귀와 같은 방문 순서를 내려면 이웃을 어떤 순서로 스택에 쌓아야 하는가.

**impl 코드**

```java
public static int[] dfsOrder(Graph graph, int start) {
    boolean[] visited = new boolean[graph.vertexCount()];
    List<Integer> order = new ArrayList<>();
    if (graph.vertexCount() == 0) return new int[0];

    Deque<Integer> stack = new ArrayDeque<>();
    stack.push(start);

    while (!stack.isEmpty()) {
        int current = stack.pop();
        if (visited[current]) continue;      // 스택에는 중복이 들어올 수 있다
        visited[current] = true;
        order.add(current);

        List<Integer> next = new ArrayList<>();
        for (int v : graph.neighbors(current)) next.add(v);
        for (int i = next.size() - 1; i >= 0; i--) {
            if (!visited[next.get(i)]) stack.push(next.get(i));
        }
    }
    return order.stream().mapToInt(Integer::intValue).toArray();
}
```

- 논리: BFS와 뼈대가 같다 — 컨테이너에서 하나 꺼내고 이웃을 넣는다.\
  **컨테이너가 큐에서 스택으로 바뀐 것뿐**이다.
- 논리: 그런데 방문 표시의 위치가 BFS와 반대다 — 여기서는 **꺼낼 때** 표시한다(`stack.pop()` 직후).
- 논리: 그래서 `if (visited[current]) continue;` 가 필요하다 — 스택에는 같은 정점이 중복해서 들어올 수 있기 때문이다.

> **깊이 우선 탐색(DFS, depth-first search)** — 갈 수 있는 데까지 끝까지 파고든 뒤 되돌아오는 탐색.\
> 예: 미로에서 한 갈래를 끝까지 가 보고 막히면 마지막 갈림길로 되돌아오는 방식이다.

> **LIFO(last in, first out)** — 나중에 넣은 것이 먼저 나오는 규칙. 스택의 정의다.\
> 예: `push` 로 쌓고 `pop` 으로 꺼내면 가장 최근에 쌓은 것이 먼저 나온다.

**왜 DFS는 꺼낼 때 표시하는가**

```
BFS 처럼 '넣을 때 표시' 하면 DFS 순서가 망가진다

  0 의 이웃이 [1, 2] 이고 1 -> 2 간선도 있다고 하자

  (A) 넣을 때 표시 :
      0 처리 시점에 1 과 2 를 동시에 '방문함'으로 찍어 버린다
      나중에 1 에서 2 로 내려가는 길을 못 밟는다
      -> 방문 '순서'는 나올지 몰라도 DFS 의 '경로를 따라 내려간다'는 의미가 사라진다

  (B) 꺼낼 때 표시 (impl) :
      스택에 1, 2 가 둘 다 들어 있어도 확정은 꺼낼 때 한 번뿐이다
      1 을 꺼내 처리하며 2 를 다시 push 할 수 있고,
      뒤에 남아 있던 옛 2 는 꺼낼 때 visited 검사로 걸러진다

  대가 : 스택에 중복이 쌓인다 (최대 O(E))
         그래서 pop 직후의 visited 검사가 필수다
```

- 논리: `if (!visited[next.get(i)]) stack.push(...)` 로 한 번 더 걸러 중복을 줄이지만, **완전히 막지는 못한다**.\
  push 시점에 미방문이던 정점이 pop 되기 전에 다른 경로로 방문될 수 있기 때문이다.
- 한계: 그래서 `pop` 직후의 `continue` 를 빼면 **같은 정점이 결과에 두 번 들어간다**.\
  `visitsAllReachableOnce` 테스트가 정확히 이것을 잡는다("정점 v 를 두 번 방문했다").

**왜 반복으로 짜야 하는가**

```java
@Test
@DisplayName("깊은 그래프에서 스택이 넘치지 않는다")
void handlesDeepGraph() {
    // 재귀로 구현하면 여기서 StackOverflowError 가 난다. 반복으로 짜야 한다.
    final int n = 100_000;
    AdjacencyListGraph g = new AdjacencyListGraph(n, true);
    for (int i = 0; i + 1 < n; i++) g.addEdge(i, i + 1);

    assertEquals(n, GraphProblems.dfsOrder(g, 0).length);
}
```

```
그래프 모양 : 0 -> 1 -> 2 -> 3 -> ... -> 99999   (한 줄로 10만 개)

 재귀 구현
     dfs(0) 안에서 dfs(1) 호출, 그 안에서 dfs(2) 호출, ...
     호출이 반환되기 전에 다음 호출이 쌓인다

     JVM 호출 스택
       +--------------------+
       | dfs(99999) frame   |   <- 10만 번째 프레임
       |        ...         |
       | dfs(2) frame       |
       | dfs(1) frame       |
       | dfs(0) frame       |
       +--------------------+
     기본 스레드 스택 크기(대략 512KB ~ 1MB)로는 이 깊이를 못 버틴다
     -> StackOverflowError (예외가 아니라 Error 다. 잡을 생각을 하면 안 된다)

 반복 구현 (impl)
     ArrayDeque 가 '힙 메모리' 위의 배열이다
     깊이가 10만이어도 그냥 배열 10만 칸이다 -> 아무 문제 없다
```

- 논리: 재귀의 호출 스택은 **JVM이 관리하는 고정 크기 영역**이고, 명시적 스택은 **힙 위의 일반 객체**다.\
  같은 "스택"이라도 한쪽만 한계가 빡빡하다.
- 논리: 즉 "재귀를 반복으로 바꾼다"는 것은 알고리즘을 바꾸는 것이 아니라 **스택을 어디에 둘지 옮기는 것**이다.

> **StackOverflowError** — 메서드 호출이 너무 깊어져 JVM의 호출 스택이 넘칠 때 발생하는 오류.\
> 예: 10만 개가 한 줄로 이어진 그래프를 재귀 DFS로 훑으면 10만 번째 프레임쯤에서 터진다.

- 한계: 현실의 그래프도 깊어질 수 있다 — 빌드 의존성 체인, 파일시스템 경로, 링크드 리스트 형태의 데이터가 그렇다.\
  "테스트 그래프는 작으니 재귀로 충분하다"가 운영에서 터지는 전형적 경로다.
- 비용(왜): 시간은 둘 다 O(V + E) 로 같다.\
  공간도 O(V) 로 같지만, 재귀는 그 O(V) 를 **호출 스택**에서 쓰고 반복은 **힙**에서 쓴다.

**재귀와 같은 순서를 내려면 — 이웃을 역순으로 쌓는다**

```java
for (int i = next.size() - 1; i >= 0; i--) {
    if (!visited[next.get(i)]) stack.push(next.get(i));
}
```

```
0 의 이웃 목록이 [1, 2, 3] 인 경우

 재귀라면 : dfs(1) 을 먼저 부른다 -> 방문 순서 0, 1, ...

 반복 + 정순 push (틀림)
     push 1, push 2, push 3
     스택 (위가 최근) :  3
                         2
                         1
     pop -> 3 이 먼저 나온다   -> 방문 순서 0, 3, ...    재귀와 다르다

 반복 + 역순 push (impl)
     push 3, push 2, push 1
     스택 (위가 최근) :  1
                         2
                         3
     pop -> 1 이 먼저 나온다   -> 방문 순서 0, 1, ...    재귀와 같다
```

- 논리: 스택은 **넣은 순서를 뒤집어서** 돌려준다.\
  그러므로 원하는 방문 순서를 얻으려면 그 역순으로 넣어야 한다.
- 논리: "뒤집힌 것을 한 번 더 뒤집어 원래대로 만든다"가 이 루프의 전부다.
- 한계: 이웃의 순서 자체는 **계약이 아니다**.\
  `Graph` 인터페이스가 "순서는 구현이 정한다"고 못 박았고, `GraphContractTest` 도 이웃을 `Set` 으로만 비교한다.\
  그래서 `dfsOrder` 의 구체적 방문 순서도 테스트가 검사하지 않는다 — 검사하는 것은 "빠짐없이 한 번씩"뿐이다.
- 한계: 역순 push 는 `neighbors` 를 `List` 로 한 번 복사해야 가능하다.\
  `Iterable` 만으로는 뒤에서부터 돌 수 없기 때문이다 — impl 이 `next` 리스트를 따로 만드는 이유다.

**순환이 있어도 안 도는 이유**

```java
Graph g = build(f, 3, true, new int[][]{{0, 1}, {1, 2}, {2, 0}});
assertEquals(3, GraphProblems.dfsOrder(g, 0).length);
```

- 논리: `visited` 배열이 **이미 본 정점을 다시 확정하지 않게** 막는다.
- 논리: 순환을 따라 0 → 1 → 2 → 0 으로 돌아와도 0은 이미 `visited` 라 `continue` 로 버려진다.
- 논리: 즉 방문 표시는 **최단 보장(BFS)** 이 아니라 여기서는 **종료 보장** 을 위한 장치다.\
  같은 `visited` 배열이 알고리즘마다 다른 역할을 한다.

**질문별 답**

- Q: 문제 2를 어떻게 푸는가?\
  A: 명시적 스택에 시작점을 넣고, 꺼낼 때마다 `visited` 를 검사해 이미 본 것이면 건너뛰고, 아니면 방문 순서에 기록한 뒤 이웃을 **역순으로** 스택에 쌓는다.\
  스택이 빌 때까지 반복하면 시작점에서 갈 수 있는 정점이 정확히 한 번씩 담긴다.

- Q: 왜 재귀가 아니라 반복으로 짜야 하는가?\
  A: 재귀는 JVM의 **고정 크기 호출 스택**을 쓰는데, 10만 개가 한 줄로 이어진 그래프에서는 그 깊이를 못 버텨 `StackOverflowError` 가 난다.\
  명시적 스택은 힙 위의 배열이라 깊이 제한이 사실상 없다.\
  알고리즘은 똑같고, 스택을 어디에 두느냐만 옮긴 것이다.

- Q: 재귀와 같은 방문 순서를 내려면 이웃을 어떤 순서로 쌓아야 하는가?\
  A: **역순**이다.\
  스택은 넣은 순서를 뒤집어 돌려주므로, 먼저 방문하고 싶은 이웃을 마지막에 push 해야 가장 먼저 pop 된다.\
  다만 이웃의 순서 자체는 `Graph` 계약이 아니므로(구현이 정한다), 이 순서 맞추기는 "재귀 버전과 눈으로 대조하기 좋게" 하는 것이지 테스트가 요구하는 것은 아니다.

#### 3. 위상 정렬 — `topologicalSort`

**질문**: 어떻게 푸는가. 진입 차수 0인 정점부터 빼 나가는 방식이 왜 별도의 순환 탐지 없이 순환을 알려주는가. 무방향 그래프는 왜 `IllegalArgumentException` 인가.

**impl 코드**

```java
public static int[] topologicalSort(Graph graph) {
    if (!graph.isDirected()) {
        throw new IllegalArgumentException("방향 그래프여야 순서를 정할 수 있다");
    }
    int n = graph.vertexCount();
    int[] inDegree = new int[n];
    for (int u = 0; u < n; u++) {
        for (int v : graph.neighbors(u)) inDegree[v]++;
    }

    Deque<Integer> ready = new ArrayDeque<>();
    for (int v = 0; v < n; v++) {
        if (inDegree[v] == 0) ready.addLast(v);
    }

    int[] order = new int[n];
    int filled = 0;
    while (!ready.isEmpty()) {
        int current = ready.removeFirst();
        order[filled++] = current;
        for (int next : graph.neighbors(current)) {
            if (--inDegree[next] == 0) ready.addLast(next);
        }
    }

    if (filled != n) {
        throw new IllegalStateException("순환이 있어 순서를 정할 수 없다");
    }
    return order;
}
```

> **위상 정렬(topological sort)** — 방향 그래프에서 "모든 간선 u→v 에 대해 u가 v보다 앞에 오는" 정점 나열.\
> 예: 빌드 의존성에서 "A를 먼저 컴파일해야 B를 컴파일할 수 있다"를 지키는 빌드 순서가 위상 정렬이다.

> **진입 차수(in-degree)** — 그 정점으로 **들어오는** 간선의 개수.\
> 예: `A → C`, `B → C` 가 있으면 C의 진입 차수는 2다 — C는 A와 B를 둘 다 기다린다.

> **DAG(directed acyclic graph)** — 방향이 있고 순환이 없는 그래프.\
> 예: 위상 정렬이 가능한 그래프가 정확히 DAG이며, 순환이 하나라도 있으면 불가능하다.

**핵심 발상 — "지금 당장 해도 되는 것"**

```
진입 차수 = "내가 기다려야 하는 선행 작업의 개수"

진입 차수 0  =  기다릴 것이 없다  =  지금 당장 해도 된다

알고리즘
  1) 모든 정점의 진입 차수를 센다
  2) 0 인 것들을 대기열(ready)에 넣는다
  3) 대기열에서 하나 꺼내 순서에 적는다
     그 정점이 끝났으므로 그가 가리키던 정점들의 '기다림'이 하나씩 줄어든다
     0 이 된 것이 새로 '지금 해도 되는 것'이 되어 대기열에 들어간다
  4) 대기열이 빌 때까지 반복
```

**손으로 추적** (`sortsDag`: 4개 정점, 0→1, 0→2, 1→3, 2→3)

```
그래프                진입 차수 초기값
      0                inDegree = [0, 1, 1, 2]
     / \                          v0 v1 v2 v3
    1   2
     \ /
      3

 초기 : ready = [0]           (진입 차수 0 인 것은 0 뿐)
        order = []

 꺼냄 0 : order = [0]
          0 의 이웃 1, 2 -> inDegree[1] 1->0 (ready 에 추가)
                            inDegree[2] 1->0 (ready 에 추가)
          ready = [1, 2]      inDegree = [0, 0, 0, 2]

 꺼냄 1 : order = [0, 1]
          1 의 이웃 3 -> inDegree[3] 2->1 (아직 0 아님)
          ready = [2]         inDegree = [0, 0, 0, 1]

 꺼냄 2 : order = [0, 1, 2]
          2 의 이웃 3 -> inDegree[3] 1->0 (ready 에 추가)
          ready = [3]         inDegree = [0, 0, 0, 0]

 꺼냄 3 : order = [0, 1, 2, 3]
          ready = []

 filled = 4 = n  -> 정상 반환
```

- 논리: `3` 이 대기열에 들어간 시점은 **마지막 선행 작업이 끝난 순간**이다 — 1과 2 중 늦게 끝난 쪽이 0으로 내렸다.
- 논리: 답이 **여러 개일 수 있다** — `[0,2,1,3]` 도 유효하다.\
  그래서 테스트는 순서를 직접 비교하지 않고 "모든 간선 u→v 에서 position[u] < position[v] 인가"만 검사한다(`assertValidOrder`).

**왜 별도의 순환 탐지가 필요 없는가**

```java
if (filled != n) {
    throw new IllegalStateException("순환이 있어 순서를 정할 수 없다");
}
```

```
순환이 있는 그래프 : 0 -> 1 -> 2 -> 0

      0 ---> 1
      ^      |
      |      v
      +----- 2

 진입 차수 : inDegree = [1, 1, 1]      <- 전부 1. 0 인 것이 하나도 없다

 초기 ready = []   (비어 있다)
 while 루프가 한 번도 안 돈다
 filled = 0 != 3   -> IllegalStateException

 왜 이것이 순환의 증거인가:
   순환에 속한 정점들은 서로를 기다린다
     0 은 2 를 기다리고, 2 는 1 을, 1 은 0 을 기다린다
   한 명이 먼저 끝나야 다른 쪽 진입 차수가 줄어드는데
   누구도 먼저 끝날 수 없다  -> 진입 차수가 영영 0 이 되지 못한다
   -> 대기열에 절대 못 들어간다 -> order 에 못 담긴다 -> filled < n
```

- 논리: 순환에 속한 정점은 **구조적으로** 진입 차수가 0이 될 수 없다.\
  순환 안의 모든 정점이 순환 안의 다른 정점에게 최소 1개의 진입 간선을 받기 때문이다.
- 논리: 그러므로 "다 돌았는데 못 담은 정점이 있다"와 "순환이 있다"가 **동치**다.\
  한쪽만 참인 경우가 없으므로 따로 탐지할 필요가 없다.
- 논리: README 의 표현이 정확하다 — **"알고리즘이 끝나는 방식 자체가 답을 준다."**
- 한계: 대신 **어느 정점이 순환에 속하는지**는 알려주지 않는다.\
  `filled != n` 만으로는 "남은 것들 중에 순환이 있다"까지만 안다 — 순환을 출력해야 하면 별도 탐지(색칠 DFS, SCC)가 필요하다.
- 한계: 순환에 **들어가는** 정점(순환 밖이지만 순환 뒤에 있는 정점)도 함께 못 담긴다.\
  그래서 "남은 정점 = 순환"이 아니라 "남은 정점 ⊇ 순환"이다.

> **Kahn 알고리즘** — 진입 차수 0인 정점을 대기열로 빼 나가며 위상 순서를 만드는 방법.\
> 예: 이 impl 이 그것이며, DFS 후위 순회를 뒤집는 다른 방법도 있다.

**왜 무방향 그래프는 `IllegalArgumentException` 인가**

```java
if (!graph.isDirected()) {
    throw new IllegalArgumentException("방향 그래프여야 순서를 정할 수 있다");
}
```

```
이유 1 (의미) : 위상 정렬의 정의가 '간선 u->v 이면 u 가 v 보다 앞'이다
                무방향 간선 u-v 는 방향이 없다 -> "누가 앞인가"를 물을 수 없다
                애초에 답이 정의되지 않는 질문이다

이유 2 (기계적) : 무방향 간선 하나는 양쪽 목록에 저장된다 (u->v 와 v->u 둘 다)
                 그러면 u 와 v 가 서로를 기다리는 길이 2 짜리 순환처럼 보인다

      0 --- 1  (무방향)
      저장은 : 0 -> 1 과 1 -> 0
      진입 차수 : inDegree[0] = 1, inDegree[1] = 1
      -> 0 인 정점이 없다 -> 순환으로 판정된다

      즉 검사를 빼도 IllegalStateException("순환") 이 나기는 한다
      그러나 그건 '순환이 있다'가 아니라 '애초에 물을 수 없는 질문이다'
      -> 에러의 종류가 달라야 한다
```

- 논리: 두 예외의 의미가 다르다 — `IllegalArgumentException` 은 **입력이 잘못됐다**, `IllegalStateException` 은 **입력은 맞는데 그 그래프에 답이 없다** 이다.
- 논리: 검사를 앞에 두는 것이 **더 정확한 진단**을 준다.\
  없어도 예외는 나지만 "순환 때문"이라는 틀린 이유를 말하게 된다.
- 한계: 간선이 하나도 없는 무방향 그래프는 사실 아무 순서나 유효하다.\
  그래도 거부한다 — 계약을 타입 수준(방향 여부)에서 단순하게 유지하는 쪽을 택한 것이다.\
  (원본에 근거 없음 — 내 추론)

- 비용(왜): 진입 차수 세기 = 모든 이웃 목록 한 번 훑기 = O(V + E).\
  메인 루프도 각 정점 한 번, 각 간선 한 번 = O(V + E).\
  전체 **O(V + E)** — 인접 행렬 위에서는 `neighbors` 가 V칸씩이라 O(V^2) 이다.

**질문별 답**

- Q: 문제 3을 어떻게 푸는가?\
  A: 모든 정점의 진입 차수를 세고, 0인 것들을 큐에 넣는다.\
  큐에서 꺼내 순서에 적고, 그 정점이 가리키는 이웃들의 진입 차수를 1씩 줄여 0이 된 것을 큐에 넣는다.\
  큐가 빌 때까지 반복한 뒤 담은 개수가 정점 수와 다르면 순환이다.

- Q: 왜 별도의 순환 탐지 없이 순환을 알려주는가?\
  A: 순환에 속한 정점은 서로를 기다리므로 **진입 차수가 영영 0이 되지 못하고**, 따라서 대기열에 절대 들어가지 못하기 때문이다.\
  그래서 "다 돌았는데 못 담은 정점이 있다(`filled != n`)"와 "순환이 있다"가 동치가 된다.\
  다만 어느 정점이 순환인지까지는 알려주지 않는다.

- Q: 무방향 그래프는 왜 `IllegalArgumentException` 인가?\
  A: 방향이 없으면 "u가 v보다 앞"이라는 질문 자체가 정의되지 않기 때문이다 — 잘못된 **입력**이지 답이 없는 상태가 아니다.\
  기계적으로도 무방향 간선은 양쪽에 저장되어 길이 2짜리 순환처럼 보여, 검사를 빼면 "순환 때문"이라는 틀린 이유로 실패하게 된다.

#### 4. 가중치 최단 거리 — `shortestPaths`

**질문**: 어떻게 푸는가. BFS로는 왜 안 되는가. 이미 확정된 정점이 다시 나오면 어떻게 하는가, 그리고 왜 음수 간선이 있으면 전제가 깨지는가.

**impl 코드**

```java
public static long[] shortestPaths(Graph graph, int start) {
    int n = graph.vertexCount();
    long[] distance = new long[n];
    Arrays.fill(distance, -1);
    if (n == 0) return distance;

    long[] best = new long[n];
    Arrays.fill(best, Long.MAX_VALUE);
    best[start] = 0;

    PriorityQueue<long[]> queue = new PriorityQueue<>((a, b) -> Long.compare(a[1], b[1]));
    queue.add(new long[]{start, 0});

    while (!queue.isEmpty()) {
        long[] top = queue.poll();
        int current = (int) top[0];
        if (top[1] > best[current]) continue;      // 낡은 항목이다

        for (int next : graph.neighbors(current)) {
            long candidate = best[current] + graph.weight(current, next);
            if (candidate < best[next]) {
                best[next] = candidate;
                queue.add(new long[]{next, candidate});
            }
        }
    }

    for (int v = 0; v < n; v++) {
        if (best[v] != Long.MAX_VALUE) distance[v] = best[v];
    }
    return distance;
}
```

- 논리: 배열이 두 개다 — `best` 는 작업용(`Long.MAX_VALUE` 가 무한대 역할), `distance` 는 반환용(`-1` 이 도달 불가)이다.\
  마지막 루프가 무한대를 `-1` 로 번역해 내보낸다.
- 논리: 반환 타입이 `long[]` 인 이유는 **거리 합이 int 범위를 넘을 수 있기** 때문이다.\
  `handlesLargeGraph` 에서 `2 x (100,000 - 1) = 199,998` 은 int 범위지만, 가중치가 크면 금방 넘친다.
- 논리: 우선순위 큐의 원소가 `long[]{정점, 그때의 거리}` 쌍이다 — 정점만 넣으면 "얼마짜리 항목인가"를 알 수 없어 낡은 항목을 못 거른다.

> **다익스트라(Dijkstra)** — 음수 없는 가중치 그래프에서 한 시작점부터 모든 정점까지의 최단 거리를 구하는 알고리즘.\
> 예: 매번 "아직 확정 안 된 것 중 가장 가까운 정점"을 확정해 나간다.

> **우선순위 큐(priority queue)** — 넣은 순서가 아니라 우선순위 순으로 나오는 대기열. 07번의 힙이 그 구현이다.\
> 예: 여기서는 거리가 작은 항목이 먼저 `poll` 되도록 `Long.compare(a[1], b[1])` 를 비교자로 준다.

**BFS로는 왜 안 되는가** (`picksCheaperPath`)

```java
// 0->3 직행은 100, 0->1->2->3 우회는 3. BFS 로는 직행이 최단이라 틀린다.
Graph g = build(f, 4, true,
    new int[][]{{0, 3, 100}, {0, 1, 1}, {1, 2, 1}, {2, 3, 1}});
assertArrayEquals(new long[]{0, 1, 2, 3}, GraphProblems.shortestPaths(g, 0));
```

```
        (100)
   0 ------------> 3
   |               ^
   |(1)            |(1)
   v               |
   1 --(1)--> 2 ---+

 BFS 가 세는 것   : 간선의 '개수'
     0 -> 3 직행  = 간선 1개    <- BFS 는 이쪽이 최단이라고 답한다
     0->1->2->3   = 간선 3개

 실제로 재야 할 것 : 가중치의 '합'
     0 -> 3 직행  = 100
     0->1->2->3   = 1 + 1 + 1 = 3     <- 이쪽이 최단이다

 BFS 의 전제 : 모든 간선의 비용이 같다 (그래서 '개수 = 거리')
 가중치가 다르면 그 전제가 깨진다 -> 층 구조가 거리 순서와 무관해진다
```

- 논리: BFS의 정확성은 **"한 걸음의 비용이 전부 같다"** 에 전적으로 기댄다.\
  그래야 큐의 FIFO 순서가 곧 거리 순서가 된다.
- 논리: 가중치가 있으면 "몇 걸음"과 "얼마"가 어긋나므로, 다음에 확정할 정점을 **거리 기준으로 골라 주는 장치**가 필요하다.
- 논리: 그 장치가 우선순위 큐다 — BFS의 `ArrayDeque` 를 `PriorityQueue` 로 갈아 끼운 것이 다익스트라다.\
  뼈대는 같고 **꺼내는 규칙**만 다르다.
- 한계: 모든 가중치가 같으면 다익스트라는 BFS와 같은 답을 주지만, 힙 조작 때문에 `log` 배 느리다.\
  가중치가 없으면 BFS를 써야 한다.

**낡은 항목(stale entry) — 확정된 정점이 다시 나오면**

```java
if (top[1] > best[current]) continue;      // 낡은 항목이다
```

```
왜 같은 정점이 큐에 여러 번 들어가는가

  best[v] 가 갱신될 때마다 (v, 새 거리) 를 큐에 새로 넣는다
  이미 큐에 있던 (v, 옛 거리) 는 지우지 않는다 -- 힙은 임의의 항목을 못 찾기 때문이다 (07번 3·10번)

  예: v 에 세 경로로 닿았다면 큐에 (v,9), (v,5), (v,3) 이 함께 들어 있다
      best[v] 는 그중 최솟값 3 을 들고 있다

  poll 순서는 거리 오름차순이므로 (v,3) 이 가장 먼저 나온다
      -> top[1]=3, best[v]=3   ->  3 > 3 이 거짓 -> 처리한다   (정상 처리)
  나중에 (v,5) 가 나오면
      -> top[1]=5, best[v]=3   ->  5 > 3 이 참   -> continue    (버린다)
  (v,9) 도 마찬가지로 버려진다

이 방식의 이름이 '지연 삭제(lazy deletion)' 다
  힙에서 항목을 찾아 고치는 대신(decrease-key), 새로 넣고 옛것은 꺼낼 때 버린다
```

- 논리: `continue` 한 줄이 **decrease-key 를 대체한다**.\
  힙에 없는 기능을 자료구조를 키워서가 아니라 알고리즘 쪽 한 줄로 우회한 것이다.
- 논리: 이 검사를 빼면 낡은 항목으로 이웃을 다시 갱신하려 시도한다 — `candidate < best[next]` 가 어차피 거짓이라 **답은 틀리지 않지만** 쓸데없는 일을 한다.\
  최악에는 이웃 스캔이 중복되어 비용이 커진다.

> **지연 삭제(lazy deletion)** — 지워야 할 항목을 즉시 제거하지 않고 남겨 뒀다가, 꺼냈을 때 무효로 판정해 버리는 기법.\
> 예: 다익스트라에서 거리가 갱신된 정점을 큐에 새로 넣고, 먼저 들어 있던 옛 항목은 꺼낼 때 `continue` 로 버린다.

- 비용(왜): 큐에 들어가는 항목 수가 정점 수 V 가 아니라 **최대 간선 수 E** 다.
- 비용(왜): 그래도 `log E <= log(V^2) = 2 log V` 이므로 전체는 **O(E log V)** 로 유지된다.\
  상수배만 늘어난다.
- 비용(왜): 인접 행렬 위에서는 `neighbors` 가 V칸씩이라 O(V^2 + E log V) 가 된다.

**왜 음수 간선이 전제를 깨는가**

```
다익스트라의 전제 (탐욕 선택 속성)

  "아직 확정 안 된 것 중 거리가 가장 작은 정점은,
   지금 그 값이 곧 최종 최단 거리다. 다시는 줄어들지 않는다"

  근거 : 앞으로 발견될 어떤 경로든 '지금 가장 가까운 정점'을 거쳐 가는데,
         거기에 간선을 더 붙이면 거리는 커지기만 한다 (가중치 >= 0)

 음수 간선이 있으면

        0 ---(1)---> 1
        |            |
       (5)         (-10)
        |            |
        v            v
        2 <----------+

   시작 0. 큐에서 거리 1 인 정점 1 을 먼저 확정하고, 거리 5 인 2 도 확정한다
   그런데 1 -> 2 의 가중치가 -10 이므로 실제 0->1->2 = 1 + (-10) = -9 다
   이미 확정해 버린 2 를 -9 로 고칠 기회가 없다  -> 답이 틀린다

   "간선을 더 붙이면 거리가 커지기만 한다"가 거짓이 되었기 때문이다
```

- 논리: 그래서 계약이 **입구에서** 음수를 막는다.

```java
if (weight < 0) {
    throw new IllegalArgumentException("음수 가중치는 담을 수 없다: " + weight);
}
```

- 논리: 알고리즘 안에서 검사하지 않고 **그래프가 애초에 음수를 못 담게** 한 것이 요점이다.\
  전제를 자료구조 수준에서 강제하면 알고리즘이 그 전제를 다시 확인할 필요가 없다.
- 논리: `rejectsNegativeWeight` 테스트는 예외뿐 아니라 `edgeCount` 가 0 그대로인지도 검사한다 — **실패한 추가가 상태를 바꾸면 안 된다**.

> **탐욕 선택 속성(greedy choice property)** — 매 단계에서 지역적으로 최선인 선택을 해도 전체 최적이 보장되는 성질.\
> 예: 다익스트라는 "지금 가장 가까운 것을 확정한다"는 탐욕 선택을 하는데, 음수 간선이 있으면 그 선택이 나중에 뒤집힐 수 있어 성질이 깨진다.

- 한계: 음수 간선이 필요하면 **벨만-포드**(O(VE))나 **SPFA** 로 바꿔야 한다.\
  (원본에 근거 없음 — 내 추론: 원본 코드는 음수를 아예 거부하므로 대안을 다루지 않는다)
- 한계: 음수 **순환**이 있으면 최단 거리 자체가 정의되지 않는다 — 돌수록 짧아지기 때문이다.

**질문별 답**

- Q: 문제 4를 어떻게 푸는가?\
  A: `best` 를 무한대로 채우고 시작점만 0으로 둔 뒤, `(정점, 거리)` 쌍을 거리 오름차순 우선순위 큐에 넣는다.\
  꺼낸 항목이 낡았으면(`top[1] > best[current]`) 버리고, 아니면 이웃마다 `best[current] + weight` 가 더 짧으면 갱신하고 큐에 새로 넣는다.\
  끝나면 무한대로 남은 정점을 `-1` 로 번역해 반환한다.

- Q: BFS로는 왜 안 되는가?\
  A: BFS는 간선의 **개수**를 세는데 여기서 필요한 것은 가중치의 **합**이기 때문이다.\
  BFS의 정확성은 "한 걸음의 비용이 전부 같다"에 기대는데 가중치가 다르면 그 전제가 깨진다.\
  테스트 `picksCheaperPath` 가 직행 100 vs 우회 3으로 그 차이를 못 박는다.

- Q: 이미 확정된 정점이 다시 나오면 어떻게 하는가?\
  A: `if (top[1] > best[current]) continue;` 로 **버린다**.\
  힙은 임의의 항목을 찾아 고칠 수 없으므로(07번의 한계), 갱신할 때마다 새 항목을 넣고 옛 항목은 꺼낼 때 무효 판정으로 버리는 **지연 삭제**를 쓴다.\
  큐 크기가 V에서 E로 커지지만 `log E <= 2 log V` 라 복잡도는 O(E log V) 로 유지된다.

- Q: 왜 음수 간선이 있으면 전제가 깨지는가?\
  A: "아직 확정 안 된 것 중 가장 가까운 정점은 그 값이 최종이다"라는 탐욕 선택 속성이 **간선을 더해도 거리가 커지기만 한다**는 사실 위에 서 있기 때문이다.\
  음수 간선이 있으면 나중에 더 싼 길이 나타날 수 있어 이미 확정한 값을 고칠 기회가 없다.\
  그래서 `addEdge` 가 입구에서 음수 가중치를 거부한다 — 전제를 자료구조 수준에서 강제한 것이다.

### B. 자료구조의 특성

#### 5. 그래프가 왜 필요한가 — 담는 것과 잇는 것

**질문**: 01~07의 자료구조로는 무엇이 안 되는가 — "원소를 담는 것"과 "원소 사이의 관계를 담는 것"의 차이는 무엇인가.

```
01 ~ 07 : "원소를 어떻게 담을까"

   자료구조가 원소들 사이에 정해 주는 관계는 딱 하나 -- '순서'였다
     01 동적 배열  : 인덱스 순서
     02 연결 리스트 : 앞뒤 순서
     03 스택 / 04 큐 : 들어온 순서(뒤집힌 순서 / 그대로)
     05 해시맵     : 순서조차 없다 (키 -> 값 대응만)
     06 BST       : 대소 순서 (전 순서)
     07 힙        : 부모-자식 순서 (부분 순서)

   공통점 : 관계는 '자료구조가 정하는 규칙'이었다.
            사용자가 "A와 B는 이어져 있다"를 따로 말해 줄 자리가 없었다

08 : "원소 사이의 관계 자체가 데이터"

   서울-대전 이 이어져 있다는 사실이 저장 대상이다
   그 관계는 어떤 규칙에서도 유도되지 않는다. 밖에서 주입해야 한다
   -> addEdge(u, v) 라는 연산이 필요한 이유
```

- 논리: 01~07 에서 "관계"는 **부수적**이었고, 08 에서는 **주인공**이다.
- 논리: 해시맵으로 `Map<Integer, List<Integer>>` 를 만들면 그래프를 흉내낼 수는 있다 — 실제로 인접 리스트가 그것에 가깝다.\
  차이는 자료구조가 아니라 **그 위에서 물을 수 있는 질문**이다.
- 논리: 그래프가 답하는 질문은 담는 구조가 못 답하는 것들이다.\
  "A에서 B로 갈 수 있나", "몇 단계 만에 갈 수 있나", "가장 싼 경로는", "순환이 있나", "이 순서대로 빌드해도 되나".
- 논리: 이 질문들은 전부 **경로(path)** 에 대한 질문이다 — 원소 하나가 아니라 원소들의 연쇄에 대한 것이다.

> **경로(path)** — 간선을 따라 이어지는 정점들의 연쇄.\
> 예: `0 → 1 → 5` 가 경로이고, 그래프 질의의 대부분이 경로에 대한 질문이다.

> **희소 그래프(sparse graph) / 밀집 그래프(dense graph)** — 간선 수 E가 V²보다 훨씬 적으면 희소, V²에 가까우면 밀집.\
> 예: 도로망·소셜 그래프·빌드 의존성은 전부 희소하고, 완전 그래프나 거리 행렬이 밀집이다.

**정점을 0..V-1 정수로 고정한 이유**

```java
/**
 * 정점은 0부터 vertexCount-1 까지의 정수다. 이름표를 붙이고 싶으면 바깥에서 매핑하면 된다.
 * 그 단순화 덕분에 인접 행렬이 그대로 배열이 된다.
 */
```

- 논리: 정점 이름이 문자열이면 인접 행렬을 만들 수 없다 — 배열 인덱스로 못 쓰기 때문이다.
- 논리: 이름표가 필요하면 바깥에 `Map<String, Integer>` 를 하나 두면 된다.\
  자료구조 안에 넣지 않고 **밖으로 뺀 것**이 설계 결정이다.
- 논리: 이 단순화 덕에 `int[][] matrix` 와 `List<Edge>[] adjacency` 둘 다 배열 인덱싱으로 O(1) 접근이 된다.
- 한계: 정점을 동적으로 추가·삭제할 수 없다 — `vertexCount` 가 생성자에서 고정된다.\
  현실의 그래프 라이브러리는 정점 추가를 지원하는 경우가 많다.\
  (원본에 근거 없음 — 내 추론)

**질문별 답**

- Q: 01~07의 자료구조로는 무엇이 안 되는가?\
  A: "A와 B가 이어져 있다"는 사실을 **저장할 자리가 없다**.\
  01~07에서 원소들 사이의 관계는 전부 자료구조가 규칙으로 정해 주는 '순서' 하나였고, 사용자가 임의의 연결을 주입할 연산이 없었다.\
  그래서 경로에 대한 질문(도달 가능성·최단 경로·순환·빌드 순서)을 아예 물을 수 없다.

- Q: "담는 것"과 "잇는 것"의 차이는?\
  A: 담는 구조에서는 관계가 **유도되는 것**(인덱스 순, 대소 순)이고, 잇는 구조에서는 관계가 **주입되는 데이터**다.\
  그래서 그래프에는 `addEdge` 라는 연산이 있고, 그 관계를 어떻게 저장할지(리스트냐 행렬이냐)가 새로운 설계 문제가 된다.

#### 6. 인접 리스트 vs 인접 행렬 — 밀도가 선택을 정한다

**질문**: 어떤 형태의 데이터·접근 패턴에 어느 쪽이 맞는가. 밀도(E와 V²의 관계)가 왜 그 선택을 정하는가 — 도로망·소셜 그래프·빌드 의존성은 어느 쪽인가.

**두 표현의 저장 방식**

```
같은 그래프 : 정점 4개, 무방향 간선 0-1, 1-2, 0-3

 인접 리스트 (AdjacencyListGraph)          인접 행렬 (AdjacencyMatrixGraph)
   adjacency[0] = [ (1,w), (3,w) ]              0    1    2    3
   adjacency[1] = [ (0,w), (2,w) ]         0 [  .    1    .    1  ]
   adjacency[2] = [ (1,w) ]                1 [  1    .    1    .  ]
   adjacency[3] = [ (0,w) ]                2 [  .    1    .    .  ]
                                           3 [  1    .    .    .  ]
   저장 항목 = 6개 (= 2E)                  칸 = 16개 (= V^2), 그중 6칸만 쓴다
                                            (. = NO_EDGE = Integer.MAX_VALUE)
```

- 논리: 인접 리스트는 **있는 것만** 저장하고, 인접 행렬은 **없는 것도** 자리를 잡는다.
- 논리: 그래서 메모리가 O(V + E) 대 O(V^2) 로 갈린다.

**밀도가 왜 선택을 정하는가**

```
밀도(density) = E / V^2   (방향 그래프 기준, 0 ~ 1)

 밀집 : E ≈ V^2   ->  O(V + E) 와 O(V^2) 이 같은 크기다
                      메모리에서 리스트가 이길 것이 없고, 오히려
                      항목마다 객체 헤더·참조가 붙어 리스트가 더 쓴다
                      => hasEdge 가 O(1) 인 행렬이 낫다

 희소 : E << V^2  ->  O(V + E) 가 O(V^2) 보다 압도적으로 작다
                      행렬은 대부분의 칸이 NO_EDGE 로 낭비된다
                      => 리스트가 낫다

 손익분기 감각 (원본에 근거 없음 -- 내 추론)
   행렬 한 칸 = int 4바이트
   리스트 항목 하나 = Edge 객체(헤더 + to + weight) + List 참조 ≈ 32~40바이트
   대략 E 가 V^2 의 1/8 ~ 1/10 을 넘어가면 행렬이 메모리에서도 유리해진다
```

- 논리: 정점 수 V가 커질수록 `V^2` 이 폭발하므로 **큰 그래프는 사실상 전부 리스트**다.\
  V가 10만이면 `V^2` 이 100억이라 밀도를 따질 것도 없이 행렬을 못 만든다.
- 논리: 즉 실무의 판단 기준은 밀도만이 아니라 **V의 절대 크기**이기도 하다.

**현실 그래프는 어느 쪽인가**

| 그래프 | 규모 감각 | 밀도 | 맞는 표현 |
|---|---|---|---|
| 도로망 | 교차로 수십만~수백만, 한 교차로에 도로 3~6개 | 극희소 | 인접 리스트 |
| 소셜 그래프 | 사용자 수억, 평균 친구 수백 | 극희소 | 인접 리스트 |
| 빌드 의존성 | 모듈 수천, 모듈당 의존 수개 | 극희소 | 인접 리스트 |
| 도시 간 거리 행렬 | 도시 수백, 모든 쌍에 거리 있음 | 밀집(1.0) | 인접 행렬 |
| 작은 상태 전이도 | 상태 수십 | 밀집이든 아니든 | 행렬(단순함) |

- 논리: README 가 "현실의 그래프는 대개 희소합니다"라고 단언하는 이유가 이 표다.\
  한 정점이 이을 수 있는 상대는 V개인데 실제로는 상수 개(도로 4개, 친구 수백)만 잇는다.
- 논리: 그래서 **기본값은 인접 리스트**이고, 행렬은 "밀집이거나 `hasEdge` 를 아주 자주 물을 때" 쓰는 예외다.

> **차수(degree)** — 한 정점에 붙은 간선의 개수. `deg(v)` 로 쓴다.\
> 예: 도로망에서 교차로의 차수는 보통 3~6으로 V와 무관한 상수다 — 이것이 희소성의 정체다.

- 비용(왜): 희소 그래프에서 모든 차수의 합 = 2E 이고, 평균 차수는 `2E/V` 다.\
  이것이 상수면 E가 V에 비례해 `O(V + E) = O(V)` 가 된다.
- 비용(왜): `handlesLargeSparseGraph` 테스트가 정확히 이 형태다 — 20만 정점에 간선 19만 9999개(한 줄), 평균 차수 약 2다.\
  행렬이라면 400억 칸이라 만들 수조차 없다.

**질문별 답**

- Q: 어떤 데이터·접근 패턴에 어느 쪽이 맞는가?\
  A: 간선이 V²보다 훨씬 적은 희소 그래프 + 순회(BFS/DFS) 위주면 **인접 리스트**다.\
  간선이 촘촘하고(밀집) `hasEdge(u,v)` 를 아주 자주 묻는 패턴이면 **인접 행렬**이다.\
  그리고 V가 수만을 넘어가면 밀도와 무관하게 리스트뿐이다 — `V^2` 을 메모리에 못 올린다.

- Q: 밀도가 왜 선택을 정하는가?\
  A: 두 표현의 메모리가 각각 `O(V + E)` 와 `O(V^2)` 이라, **E가 V²에 비해 얼마나 작은가**가 그대로 메모리 배수가 되기 때문이다.\
  E가 V²에 가까우면 두 값이 같아져 행렬의 O(1) `hasEdge` 가 공짜 이득이 되고, E가 V²보다 훨씬 작으면 행렬의 대부분 칸이 낭비된다.

- Q: 도로망·소셜 그래프·빌드 의존성은?\
  A: 전부 **극희소**라 인접 리스트다.\
  세 경우 모두 한 정점의 차수가 V와 무관한 상수 수준(도로 3~6개, 친구 수백, 의존 모듈 수개)이기 때문이다.

#### 7. `hasEdge` 와 `neighbors` 의 비대칭

**질문**: `hasEdge(u,v)` 가 리스트에서 O(deg(u))이고 행렬에서 O(1)인 구조적 이유는. 반대로 `neighbors(v)` 가 리스트에서 O(deg(v))인데 행렬에서는 이웃이 하나도 없어도 O(V)인 이유는.

**`hasEdge` — 찾아야 하는가, 계산되는가**

```java
// 인접 리스트
Edge findEdge(int from, int to) {
    for (Edge e : adjacency[from]) {
        if (e.to == to) return e;
    }
    return null;
}

@Override
public boolean hasEdge(int from, int to) {
    checkVertex(from);
    checkVertex(to);
    return findEdge(from, to) != null;        // 목록을 훑어야 한다. O(deg(from))
}
```

```java
// 인접 행렬
@Override
public boolean hasEdge(int from, int to) {
    checkVertex(from);
    checkVertex(to);
    return matrix[from][to] != NO_EDGE;    // 배열 한 번 읽기. O(1)
}
```

```
 인접 리스트 : "u 의 이웃 목록 어딘가에 v 가 있나?"
     adjacency[0] = [ (1,w), (3,w), (7,w), (9,w) ]
                       ^      ^      ^      ^
                       하나씩 훑으며 to == v 인지 본다
     목록은 정렬되어 있지도 않다 -> 이진 탐색도 못 한다
     => 최악에 deg(u) 번   =>  O(deg(u))

 인접 행렬 : "(u, v) 칸에 뭐가 적혀 있나?"
     matrix[0][7] 을 읽는다
     주소가 계산으로 나온다 : base + (0 * V + 7) * 4바이트
     => 탐색이 아예 없다   =>  O(1)
```

- 논리: 차이의 본질은 **"자리가 미리 정해져 있는가"** 다.
- 논리: 행렬은 간선 (u,v)의 자리를 **좌표로 계산**한다 — 07번 힙의 `2i+1` 과 같은 원리다(구조가 규칙적이면 계산으로 대신한다).
- 논리: 리스트는 자리가 정해져 있지 않고 "있는 것만 순서대로" 쌓여 있으므로 **찾아야 한다**.
- 비용(왜): `deg(u)` 가 상수 수준인 희소 그래프에서는 O(deg(u))도 사실상 상수다.\
  문제가 되는 것은 특정 정점의 차수가 큰 경우(허브 정점)다.
- 한계: 목록을 정렬해 두거나 `Set` 으로 바꾸면 리스트도 `hasEdge` 를 빠르게 할 수 있다.\
  대신 `addEdge` 가 비싸지거나 메모리가 더 든다 — 원본 구현은 단순한 `ArrayList` 를 택했다.

**`neighbors` — 결과를 모으는가, 전수 검사하는가**

```java
// 인접 리스트
@Override
public Iterable<Integer> neighbors(int from) {
    checkVertex(from);
    List<Integer> result = new ArrayList<>(adjacency[from].size());
    for (Edge e : adjacency[from]) result.add(e.to);
    return result;
}
```

```java
// 인접 행렬
@Override
public Iterable<Integer> neighbors(int from) {
    checkVertex(from);
    // 이웃이 하나도 없어도 V 칸을 다 봐야 한다. 그게 이 표현의 대가다.
    java.util.List<Integer> result = new ArrayList<>();
    for (int v = 0; v < vertexCount; v++) {
        if (matrix[from][v] != NO_EDGE) result.add(v);
    }
    return result;
}
```

```
 인접 리스트 : 이웃이 '이미 모여 있다'
     adjacency[v] 를 그대로 훑으면 끝. 훑는 횟수 = 실제 이웃 수
     => O(deg(v))

 인접 행렬 : 이웃이 '흩어져 있다'
     v 행의 V 칸 중 어느 칸이 이웃인지는 읽어 봐야 안다
     이웃이 0개여도 "0개다"를 알려면 V 칸을 다 봐야 한다
     => O(V)  (결과 크기와 무관하다)

 테스트 neighborsScansEveryColumn (정점 500개, 간선 1개)
     정점 499 의 이웃은 0개
     그래도 matrix[499] 의 500칸을 전부 읽어야 그 사실을 안다
```

- 논리: 행렬의 `neighbors` 는 **출력 크기에 비례하지 않는** 연산이다.\
  결과가 비어 있어도 비용은 항상 V다.
- 논리: 이것이 행렬 위에서 BFS/DFS가 O(V+E) 가 아니라 O(V^2) 이 되는 직접적 원인이다(8번).
- 논리: `hasEdge` 와 `neighbors` 의 비대칭이 **정확히 거울상**이라는 점이 중요하다.

| 연산 | 인접 리스트 | 인접 행렬 | 왜 |
|---|---|---|---|
| `hasEdge(u,v)` | O(deg(u)) — 찾아야 함 | **O(1)** — 자리가 정해짐 | "한 칸을 콕 집어 보기"는 좌표가 있는 쪽이 유리 |
| `neighbors(v)` | **O(deg(v))** — 모여 있음 | O(V) — 흩어져 있음 | "있는 것만 모으기"는 있는 것만 저장한 쪽이 유리 |

- 논리: 행렬은 **점 조회(point query)** 에 강하고, 리스트는 **집합 조회(scan)** 에 강하다.
- 논리: 어떤 표현이 "빠르다"가 아니라, 어떤 질의를 자주 하느냐가 표현을 정한다.

**질문별 답**

- Q: `hasEdge` 가 리스트에서 O(deg(u))이고 행렬에서 O(1)인 이유는?\
  A: 행렬은 간선 (u,v)의 **저장 자리가 좌표로 미리 정해져** 있어 주소 계산 한 번이면 읽을 수 있다.\
  리스트는 "있는 것만" 순서 없이 쌓아 두므로 목록을 처음부터 훑으며 `to == v` 인 항목을 찾아야 한다.\
  목록이 정렬되어 있지도 않아 이진 탐색으로 줄일 수도 없다.

- Q: `neighbors` 가 리스트에서 O(deg(v))인데 행렬에서 이웃이 없어도 O(V)인 이유는?\
  A: 리스트는 이웃이 **이미 한 곳에 모여** 있어 그 목록 길이만큼만 돌면 된다.\
  행렬은 이웃이 V칸에 **흩어져** 있어, 어느 칸이 이웃인지 읽어 보기 전에는 알 수 없다.\
  결과가 0개라는 사실조차 V칸을 다 읽어야 확정되므로 비용이 출력 크기와 무관하다.

#### 8. 최악의 사용 패턴 — 10만 정점 20만 간선을 행렬로

**질문**: 정점 10만 개에 간선 20만 개인 그래프를 인접 행렬로 만들면 무슨 일이 생기는가. 같은 그래프에서 BFS/DFS 전체 비용이 두 표현에서 각각 얼마인가, 그 차이가 어디서 오는가.

**메모리 계산**

```
V = 100,000,  E = 200,000

 인접 행렬
   칸 수 = V x V = 100,000 x 100,000 = 10,000,000,000 (100억 칸)
   int 하나 4바이트 -> 40,000,000,000 바이트 = 약 40GB

   게다가 자바의 int[][] 는 '배열의 배열'이다
     int[100000][] 이 먼저 잡히고, 그 안에 int[100000] 이 10만 개 잡힌다
     행마다 객체 헤더가 따로 붙는다
   생성자의 초기화 루프 for (int[] row : matrix) Arrays.fill(row, NO_EDGE);
     만으로도 100억 칸을 채워야 한다 -> 만들다가 OutOfMemoryError

 인접 리스트
   저장 항목 = 2E = 400,000 (무방향이면 양쪽에 저장)
   List 객체 V개 + Edge 객체 2E개
   대략 V x 40바이트 + 2E x 40바이트 ≈ 4MB + 16MB ≈ 20MB 수준
   (원본에 근거 없음 -- 내 추론: 객체 헤더·참조 크기를 40바이트로 잡은 어림값)

   차이 : 40GB  vs  20MB  =  약 2000배
```

- 논리: README 가 "아예 못 만듭니다"라고 쓴 것이 과장이 아니다 — 40GB는 일반 머신의 힙에 올라가지 않는다.
- 논리: **테스트로도 확인된다** — `handlesLargeSparseGraph` 는 20만 정점을 쓰는데, 주석이 "인접 행렬로는 이 크기를 아예 만들 수 없다. 20만^2 = 400억 칸이다"라고 못 박는다.\
  그래서 이 테스트는 `AdjacencyListGraphTest` 에만 있다.

```java
@Test
@DisplayName("한계: 간선이 하나여도 V x V 칸을 쓴다")
void allocatesSquareRegardlessOfEdges() {
    final int n = 1_000;
    AdjacencyMatrixGraph g = new AdjacencyMatrixGraph(n, true);
    g.addEdge(0, 1);

    long cells = (long) g.matrix.length * g.matrix[0].length;
    assertEquals((long) n * n, cells,
        "간선은 1개인데 칸은 " + cells + "개다. 인접 리스트라면 1개다.\n"
            + "정점이 10만 개면 100억 칸이라 아예 만들 수 없다.");
}
```

- 논리: 이 테스트도 **버그를 잡는 테스트가 아니다** — 올바른 구현에서도 통과한다.\
  "이 표현은 이런 대가를 치른다"를 숫자로 못 박는 것이 목적이다(클래스 주석).
- 논리: 대비되는 테스트가 `usesNoSpaceForAbsentEdges` 다 — 정점 1000개에 간선 1개면 리스트에 저장된 항목이 정확히 **1개**다.

**BFS/DFS 전체 비용**

```
BFS/DFS 의 뼈대
    각 정점을 한 번씩 꺼낸다             -> V 번
    꺼낼 때마다 neighbors(v) 를 훑는다   -> 여기가 표현에 따라 갈린다

 인접 리스트
    sum over v of deg(v) = 2E
    전체 = O(V) + O(E) = O(V + E)
    V=100,000, E=200,000 -> 약 100,000 + 400,000 = 5 x 10^5 회

 인접 행렬
    neighbors(v) 가 항상 V 칸
    sum over v of V = V x V = V^2
    전체 = O(V^2)
    V=100,000 -> 10^10 회 (100억)

 차이 = 10^10 / 5x10^5 = 20,000 배
```

- 논리: 차이가 나오는 지점은 **정확히 한 곳**이다 — `neighbors(v)` 한 번의 비용.
- 논리: 알고리즘 코드(`bfsDistances`)는 한 글자도 다르지 않다.\
  `Graph` 인터페이스만 보고 짜여 있기 때문이다.
- 논리: 즉 "어떤 구현을 넘겼는가"가 **호출 코드 바깥에서** 비용을 20,000배 바꾼다.

```
 시간 감각 (초당 10^9 회 연산 가정, 원본에 근거 없음 -- 내 추론)
   인접 리스트 : 5 x 10^5 회   -> 1밀리초 미만
   인접 행렬   : 10^10 회      -> 약 10초
   (애초에 40GB 메모리를 못 잡아 여기까지 가지도 못한다)
```

- 한계: 반대 방향의 최악도 있다 — **밀집 그래프에서 `hasEdge` 를 아주 많이 묻는 경우** 리스트가 불리하다.\
  완전 그래프에서 `deg(u) = V-1` 이므로 `hasEdge` 하나가 O(V)다.
- 한계: 리스트의 `addEdge` 도 `findEdge` 를 부르므로 O(deg(from))다 — 허브 정점에 간선을 계속 추가하면 누적 비용이 커진다.\
  `handlesLargeSparseGraph` 가 5초 안에 도는 이유는 평균 차수가 약 2로 작기 때문이다.

**질문별 답**

- Q: 10만 정점 20만 간선을 인접 행렬로 만들면?\
  A: 100억 칸이 필요하고 `int` 기준 약 40GB다 — 생성자의 초기화 루프에서 `OutOfMemoryError` 로 죽는다.\
  같은 그래프의 인접 리스트는 저장 항목이 40만 개, 대략 수십 MB 수준이다.

- Q: BFS/DFS 전체 비용은 각각 얼마이고 차이가 어디서 오는가?\
  A: 인접 리스트가 **O(V + E)**, 인접 행렬이 **O(V²)** 다.\
  차이는 딱 한 지점 — `neighbors(v)` 한 번의 비용이 리스트는 `deg(v)`, 행렬은 항상 `V` 라는 점에서 온다.\
  V=10만, E=20만이면 5×10⁵ 대 10¹⁰ 으로 약 2만 배 차이다.\
  알고리즘 코드는 한 글자도 다르지 않은데, 넘긴 구현이 인터페이스 뒤에서 비용을 바꾼다.

#### 9. 트레이드오프 한 문장, 그리고 왜 `GraphProblems` 는 그대로인가

**질문**: 두 표현의 트레이드오프를 한 문장으로 정리하면. 같은 `Graph` 계약을 구현하는데 왜 `GraphProblems` 의 코드는 그대로 두고 비용만 달라지는가.

**한 문장**

- 논리: **인접 리스트는 있는 것만 저장해 순회가 싸고, 인접 행렬은 모든 자리를 미리 잡아 점 조회가 싸다.**
- 논리: 다르게 말하면 "공간을 아끼고 점 조회를 포기할 것인가, 공간을 쓰고 점 조회를 살 것인가"다.

| | 인접 리스트 | 인접 행렬 |
|---|---|---|
| 메모리 | O(V + E) | O(V²) — 간선이 없어도 |
| `addEdge` | O(deg(u)) — 중복 확인 | O(1) — 칸을 보면 됨 |
| `hasEdge` | O(deg(u)) | **O(1)** |
| `weight` | O(deg(u)) | **O(1)** |
| `neighbors` | **O(deg(v))** | O(V) |
| BFS/DFS 전체 | **O(V + E)** | O(V²) |
| 큰 V | 수백만도 가능 | 수만이 한계 |

**왜 `GraphProblems` 코드가 그대로인가**

```
GraphProblems 의 모든 함수 시그니처

    public static int[] bfsDistances(Graph graph, int start)
    public static int[] dfsOrder(Graph graph, int start)
    public static int[] topologicalSort(Graph graph)
    public static long[] shortestPaths(Graph graph, int start)
                                 ^^^^^
                                 인터페이스 타입이다. 구체 클래스가 아니다

 이 함수들이 부르는 것은 계약에 적힌 연산뿐이다
    graph.vertexCount()   graph.neighbors(v)   graph.weight(u,v)   graph.isDirected()

 어떤 구현이 오든 '무엇을 돌려주는가'는 같다 (계약이 그렇게 정했다)
 다른 것은 '그 답을 만드는 데 얼마가 드는가'뿐이다
       -> 결과 동일, 비용 상이
```

```java
static Stream<Arguments> implementations() {
    return Stream.of(
        Arguments.of("AdjacencyList",
            (BiFunction<Integer, Boolean, Graph>) AdjacencyListGraph::new),
        Arguments.of("AdjacencyMatrix",
            (BiFunction<Integer, Boolean, Graph>) AdjacencyMatrixGraph::new)
    );
}
```

- 논리: `GraphProblemsTest` 가 **같은 테스트를 두 구현으로 모두 돌린다**(`@ParameterizedTest`).\
  테스트 클래스 주석이 그 의도를 못 박는다 — "결과는 같고 비용만 다르다".
- 논리: 이것이 **인터페이스를 쓰는 이유**의 교과서적 사례다.\
  알고리즘은 "무엇을 할 수 있는가"(계약)에만 의존하고 "어떻게 하는가"(구현)는 모른다.

> **계약(contract)** — 자료구조가 밖에 약속한 연산과 그 결과. 내부 구현과 무관하게 지켜야 한다.\
> 예: `Graph` 는 "`neighbors(v)` 는 v에서 갈 수 있는 정점들을 준다"만 약속하고, 순서도 저장 방식도 약속하지 않는다.

> **추상화 비용 누출(leaky abstraction)** — 인터페이스가 동작은 숨기지만 성능 특성은 숨기지 못하는 현상.\
> 예: `Graph` 뒤에 어떤 구현이 있느냐에 따라 같은 BFS 코드가 O(V+E)도 되고 O(V²)도 된다.

- 한계: 계약이 숨기지 못하는 것이 **비용**이다.\
  `neighbors(v)` 의 시그니처만 보고는 그것이 O(deg(v))인지 O(V)인지 알 수 없다.
- 한계: 그래서 성능 테스트(`handlesLargeSparseGraph`, `handlesDeepGraph`, `handlesLargeGraph`)는 **구체 타입을 직접 쓴다**.\
  "이 크기는 이 구현으로만 가능하다"를 명시해야 하기 때문이다.
- 한계: 이것이 01번 `list.contains()` vs `set.contains()` 와 같은 함정이다 — 호출 코드는 똑같이 생겼는데 비용이 다르다.

**이웃 순서가 계약이 아닌 것도 같은 이야기**

```java
/**
 * 이웃의 순서는 계약이 아니다. 구현마다 다르므로 집합으로만 비교한다.
 * 순서를 가정하는 순간 한쪽 구현에 묶인 테스트가 된다.
 */
```

- 논리: 인접 리스트의 이웃 순서 = **간선을 추가한 순서**.
- 논리: 인접 행렬의 이웃 순서 = **정점 번호 오름차순**(0부터 V-1까지 훑으므로).
- 논리: 둘이 다르므로 계약에 넣을 수 없다 — 넣으면 한쪽 구현이 계약 위반이 된다.
- 한계: 단 `reAddReplacesWeight` 테스트는 `neighborList` 로 **순서 있는 비교**를 한다.\
  이웃이 하나뿐인 경우라 순서가 문제되지 않기 때문이다("이웃 목록에도 하나만 있어야 한다"를 확인하는 것이 목적).

**질문별 답**

- Q: 트레이드오프를 한 문장으로?\
  A: **인접 리스트는 있는 것만 저장해 순회와 메모리가 싸고, 인접 행렬은 모든 자리를 미리 잡아 점 조회(`hasEdge`/`weight`)가 O(1)이다.**

- Q: 왜 `GraphProblems` 코드는 그대로인데 비용만 달라지는가?\
  A: 알고리즘이 구체 클래스가 아니라 `Graph` **인터페이스**에만 의존하고, 계약이 "무엇을 돌려주는가"만 정하기 때문이다.\
  두 구현 모두 계약대로 같은 답을 주므로 코드가 바뀔 이유가 없다.\
  계약이 정하지 않은 것이 **비용**이라, 같은 `neighbors(v)` 호출이 한쪽은 O(deg(v))이고 다른 쪽은 O(V)가 된다.\
  `GraphProblemsTest` 가 같은 테스트를 두 구현으로 모두 돌려 "결과는 같고 비용만 다르다"를 실제로 보여 준다.

#### 10. 무방향 간선 — 저장 두 번, 개수 하나, self loop는 한 번

**질문**: 무방향 간선에서 저장은 두 번 하는데 `edgeCount` 는 하나로 세야 하는 이유는. 자기 자신으로 가는 간선은 무방향이어도 왜 한 번만 저장해야 하는가.

**저장과 개수가 갈리는 이유**

```java
adjacency[from].add(new Edge(to, weight));
if (!directed && from != to) {
    adjacency[to].add(new Edge(from, weight));   // 저장은 두 번, 간선은 하나
}
edges++;
```

```
무방향 간선 0-1 하나를 저장하면

  adjacency[0] = [ (1, w) ]      <- 0 에서 1 을 볼 수 있어야 한다
  adjacency[1] = [ (0, w) ]      <- 1 에서 0 도 볼 수 있어야 한다

  저장 항목 2개.  그런데 사용자가 그은 선은 1개다

 왜 두 번 저장하는가:
   neighbors(v) 가 O(deg(v)) 이려면 v 의 이웃이 v 의 목록에 있어야 한다
   0-1 을 adjacency[0] 에만 넣으면 neighbors(1) 이 1 을 못 찾는다
   찾으려면 모든 정점의 목록을 뒤져야 한다 -> O(V + E)
   => '양방향 조회를 O(deg) 로 만들기 위해' 중복 저장한다

 왜 하나로 세는가:
   edgeCount 는 '저장 항목 수'가 아니라 '그래프에 그은 선의 개수'다
   그것이 사용자가 말한 의미이고, 계약에 그렇게 적혀 있다
     "간선 개수. 무방향 그래프에서 u-v 는 한 개로 센다."
```

- 논리: **내부 표현의 개수와 논리적 개수가 다르다**는 것이 요점이다.\
  계약은 논리적 개수를 약속했으므로 내부 사정을 노출하면 안 된다.
- 논리: `edges++` 가 `if` 블록 **밖에** 한 번만 있는 것이 그 구현이다.
- 논리: 행렬도 같다 — 두 칸(`matrix[u][v]`, `matrix[v][u]`)을 채우지만 `edges++` 는 한 번이다.

```java
// AdjacencyMatrixGraph
if (matrix[from][to] == NO_EDGE) {
    edges++;
}
matrix[from][to] = weight;
if (!directed) {
    matrix[to][from] = weight;    // 표의 두 칸을 채워도 간선은 하나다
}
```

- 논리: 행렬은 `edges++` 를 **칸이 비어 있을 때만** 한다 — 재추가를 개수로 세지 않기 위해서다(11번).
- 논리: 테스트가 양쪽을 다 검사한다.\
  `undirectedStoresBothSides` 는 "저장은 두 번이지만 간선은 하나", `undirectedFillsBothCells` 는 "두 칸을 채워도 간선은 하나"다.
- 비용(왜): 무방향 그래프의 저장 항목 총합은 `2E` 다.\
  `handlesLargeSparseGraph` 가 그것을 직접 센다 — `assertEquals(2 * (n - 1), total, "각 간선이 양쪽에서 한 번씩 보인다")`.

**self loop 는 왜 한 번만인가**

```java
if (!directed && from != to) {
    adjacency[to].add(new Edge(from, weight));
}
```

```
간선 1-1 (자기 자신으로) 을 무방향으로 추가한다면

 (A) from != to 검사가 있을 때 (impl)
     adjacency[1] = [ (1, w) ]              항목 1개
     neighbors(1) = {1}                     테스트 selfLoop 의 기대값
     edgeCount = 1

 (B) 검사가 없다면
     adjacency[1].add(Edge(1,w))   <- from 쪽
     adjacency[1].add(Edge(1,w))   <- to 쪽인데 to 도 1 이라 같은 목록이다
     adjacency[1] = [ (1,w), (1,w) ]        항목 2개, 같은 간선이 중복
     neighbors(1) = [1, 1]                  이웃 목록에 1 이 두 번 나온다
     -> BFS/DFS 가 같은 정점을 두 번 훑는다 (답은 안 틀리지만 낭비)
     -> findEdge 도 첫 번째만 찾아 고쳐 두 항목의 가중치가 어긋날 수 있다

 왜 이 문제가 self loop 에서만 생기는가:
     from != to 이면 두 번의 add 가 '서로 다른 두 목록'에 간다
     from == to 이면 두 번의 add 가 '같은 목록'에 간다 -> 중복
```

> **self loop(자기 순환 간선)** — 시작점과 끝점이 같은 간선.\
> 예: 상태 전이도에서 "그 상태에 머무른다"를 나타내거나, 소셜 그래프에서 자기 자신을 팔로우하는 경우다.

- 논리: 무방향에서 `u-v` 를 양쪽에 저장하는 것은 "두 정점 각각의 시야에 넣는다"는 뜻인데, `u == v` 면 시야가 하나뿐이다.
- 논리: 행렬은 이 문제가 **자동으로 없다** — `matrix[1][1] = w` 를 두 번 써도 같은 칸이라 덮어쓸 뿐이다.\
  그래서 `AdjacencyMatrixGraph.addEdge` 에는 `from != to` 검사가 없다.
- 논리: 같은 계약을 지키는데 **한쪽만 특수 케이스 처리가 필요하다** — 표현이 다르면 방어할 곳도 다르다.
- 한계: `selfLoop` 테스트는 방향 그래프로만 검사한다(`create(3, true)`).\
  무방향 self loop 는 계약 테스트에 직접 나오지 않지만, impl 코드가 `from != to` 로 방어해 둔 자리다.

**질문별 답**

- Q: 저장은 두 번인데 `edgeCount` 는 왜 하나인가?\
  A: 두 번 저장하는 것은 `neighbors(v)` 를 양쪽에서 O(deg(v))로 만들기 위한 **내부 사정**이고, `edgeCount` 가 약속한 것은 **사용자가 그은 선의 개수**이기 때문이다.\
  계약이 "무방향에서 u-v는 한 개로 센다"고 명시했으므로 내부 표현의 개수를 노출하면 계약 위반이다.\
  구현에서는 `edges++` 를 `if` 밖에 한 번만 두는 것으로 실현된다.

- Q: self loop는 무방향이어도 왜 한 번만 저장하는가?\
  A: `u != v` 일 때는 두 번의 저장이 **서로 다른 두 목록**으로 가지만, `u == v` 면 **같은 목록**에 두 번 들어가 중복이 되기 때문이다.\
  그러면 `neighbors(1)` 이 `[1, 1]` 이 되어 탐색이 같은 정점을 두 번 훑고, `findEdge` 가 첫 항목만 고쳐 가중치가 어긋날 수 있다.\
  인접 행렬은 같은 칸을 두 번 쓰는 것이라 이 문제가 없다 — 표현이 다르면 방어할 자리도 다르다.

#### 11. 이미 있는 간선을 다시 이으면

**질문**: 두 구현에서 각각 무슨 일이 벌어지는가. 인접 리스트는 왜 찾아서 덮어써야 하고 행렬은 왜 찾는 비용이 없는가 — 같은 계약인데 비용 구조가 다르다는 게 무슨 뜻인가.

**계약이 요구하는 것**

```java
/**
 * 가중치가 있는 간선을 잇는다. 같은 간선을 다시 이으면 가중치를 덮어쓴다.
 */
void addEdge(int from, int to, int weight);
```

```java
@Test
@DisplayName("같은 간선을 다시 이으면 가중치만 바뀐다")
void reAddReplacesWeight() {
    Graph g = create(3, false);
    g.addEdge(0, 1, 5);
    g.addEdge(0, 1, 9);

    assertEquals(1, g.edgeCount(), "간선이 두 개가 되면 안 된다");
    assertEquals(9, g.weight(0, 1));
    assertEquals(9, g.weight(1, 0));
    assertEquals(java.util.List.of(1), neighborList(g, 0), "이웃 목록에도 하나만 있어야 한다");
}
```

- 논리: 계약이 요구하는 것은 셋이다 — 가중치 덮어쓰기, `edgeCount` 안 늘리기, 이웃 목록에 중복 안 만들기.
- 논리: 무방향이면 **양쪽 다** 9로 바뀌어야 한다 — 저장이 두 벌이므로 둘 다 고쳐야 한다.

**인접 리스트 — 찾아야 한다**

```java
Edge existing = findEdge(from, to);
if (existing != null) {
    existing.weight = weight;            // 또 넣으면 같은 간선이 두 개가 된다
    if (!directed && from != to) {
        findEdge(to, from).weight = weight;
    }
    return;
}

adjacency[from].add(new Edge(to, weight));
if (!directed && from != to) {
    adjacency[to].add(new Edge(from, weight));   // 저장은 두 번, 간선은 하나
}
edges++;
```

```
 addEdge(0, 1, 5) 이후
     adjacency[0] = [ Edge(to=1, w=5) ]
     adjacency[1] = [ Edge(to=0, w=5) ]
     edges = 1

 addEdge(0, 1, 9) 를 '찾지 않고 그냥 add' 하면

     adjacency[0] = [ Edge(1,5), Edge(1,9) ]    <- 같은 간선이 두 개
     adjacency[1] = [ Edge(0,5), Edge(0,9) ]
     edges = 2                                   <- 개수도 틀린다

     neighbors(0) = [1, 1]                       <- 이웃이 두 번 나온다
     weight(0,1)  = 5                            <- findEdge 가 첫 항목을 찾아 옛 값을 준다
     => 계약 세 조항을 전부 어긴다

 올바른 구현 (impl)
     findEdge(0, 1) 로 기존 Edge 객체를 찾아 weight 필드만 9 로 바꾼다
     무방향이므로 반대쪽 findEdge(1, 0) 도 찾아 9 로 바꾼다
     edges 는 건드리지 않는다 (early return)

     비용 = findEdge 두 번 = O(deg(from)) + O(deg(to))
```

- 논리: 같은 `Edge` **객체**의 필드를 고치는 것이라 새 객체를 만들지 않는다.\
  `Edge.to` 가 `final` 이고 `weight` 만 가변인 이유가 이것이다.
- 논리: `reAddDoesNotGrowList` 테스트가 내부를 직접 들여다본다 — `g.adjacency[0].size()` 가 1이고 `get(0).weight` 가 9여야 한다.

**인접 행렬 — 찾을 것이 없다**

```java
// 인접 리스트와 달리 "이미 있는지" 찾는 데 비용이 없다. 칸을 바로 보면 된다.
if (matrix[from][to] == NO_EDGE) {
    edges++;
}
matrix[from][to] = weight;
if (!directed) {
    matrix[to][from] = weight;    // 표의 두 칸을 채워도 간선은 하나다
}
```

```
 간선 (0,1) 의 자리는 언제나 matrix[0][1] 한 칸이다
     "이미 있나?"  = 그 칸이 NO_EDGE 인가를 읽는다      -> O(1)
     "덮어쓰기"    = 그 칸에 새 값을 쓴다               -> O(1)
     중복이 생길 수 없다 -- 칸이 하나뿐이라 물리적으로 불가능하다

 edgeCount 를 정확히 세려면 '새 간선인가'만 판정하면 된다
     if (matrix[from][to] == NO_EDGE) edges++;
     -> 쓰기 전에 읽어 본다. 읽기도 O(1) 이라 공짜나 다름없다
```

- 논리: 행렬에서 중복은 **표현상 불가능**하다 — 한 간선에 자리가 하나뿐이기 때문이다.\
  리스트는 자리가 정해져 있지 않아 같은 간선이 여러 항목이 될 수 있다.
- 논리: 즉 "덮어쓰기"라는 계약이 행렬에서는 **연산의 기본 성질**이고, 리스트에서는 **따로 구현해야 하는 규칙**이다.
- 논리: 행렬의 `addEdge` 에 `from != to` 검사가 없는 것도 같은 이유다 — 같은 칸을 두 번 쓸 뿐이다(10번).

**"같은 계약인데 비용 구조가 다르다"의 뜻**

| | 인접 리스트 | 인접 행렬 |
|---|---|---|
| 새 간선 추가 | `findEdge` O(deg) + add O(1) | 칸 읽기 + 쓰기 O(1) |
| 재추가(덮어쓰기) | `findEdge` O(deg) x (무방향이면 2회) | 칸 쓰기 O(1) x (무방향이면 2칸) |
| 중복 가능성 | 있다 → 코드로 막아야 함 | 없다 → 표현이 막아 줌 |
| 계약 위반 위험 | 높음(세 조항 전부) | 낮음 |

- 논리: 계약은 **무엇을 보장하는가**만 말하고 **얼마가 드는가**는 말하지 않는다.\
  그래서 같은 `addEdge(0, 1, 9)` 호출이 한쪽은 목록 순회를 하고 한쪽은 배열 쓰기 한 번으로 끝난다.
- 논리: 더 중요한 차이는 **틀리기 쉬운 정도**다.\
  행렬 구현은 "덮어쓰기"를 실수로 어길 방법이 거의 없고, 리스트 구현은 `findEdge` 를 빼먹는 순간 조용히 중복이 쌓인다.
- 논리: 이것이 9번의 "추상화가 비용을 숨긴다"와 짝을 이룬다 — 추상화는 **구현 난이도의 차이**도 숨긴다.
- 한계: 리스트 쪽 재추가 비용을 줄이려면 `Map<Integer, Edge>` 같은 인덱스를 얹어야 한다.\
  그러면 메모리가 늘고 `neighbors` 순회의 캐시 지역성이 나빠진다 — 05번 해시맵의 거래가 여기서 다시 나온다.\
  (원본에 근거 없음 — 내 추론)

**질문별 답**

- Q: 이미 있는 간선을 다시 이으면 두 구현에서 각각?\
  A: 인접 리스트는 `findEdge` 로 기존 `Edge` 객체를 찾아 `weight` 필드만 바꾸고, 무방향이면 반대쪽도 찾아 바꾼 뒤 `edges` 를 건드리지 않고 반환한다.\
  인접 행렬은 `matrix[from][to]` 칸에 새 값을 쓰기만 하고, 쓰기 전에 그 칸이 `NO_EDGE` 였는지 읽어 새 간선일 때만 `edges++` 한다.

- Q: 리스트는 왜 찾아야 하고 행렬은 왜 찾는 비용이 없는가?\
  A: 행렬은 간선 (u,v)의 자리가 `matrix[u][v]` 한 칸으로 **미리 정해져** 있어 그 칸을 읽고 쓰면 끝이다 — 중복이 표현상 불가능하다.\
  리스트는 "있는 것만" 쌓아 두므로 자리가 정해져 있지 않고, 찾지 않고 넣으면 같은 간선이 두 항목이 되어 `edgeCount`·`weight`·`neighbors` 가 전부 틀어진다.

- Q: "같은 계약인데 비용 구조가 다르다"가 무슨 뜻인가?\
  A: 계약은 **결과**만 약속하고 **비용**과 **구현 난이도**는 약속하지 않는다는 뜻이다.\
  같은 `addEdge` 호출이 한쪽은 O(deg(u)) 목록 순회이고 한쪽은 O(1) 배열 쓰기이며, 한쪽은 중복 방지 코드를 직접 써야 하고 한쪽은 표현이 알아서 막아 준다.\
  호출하는 쪽 코드는 똑같이 생겼으므로, 비용을 알려면 구현을 알아야 한다.

#### 12. `neighbors` 는 왜 복사본이어야 하는가

**질문**: 내부 목록을 그대로 주면 무엇이 깨지는가 — 01번 `toArray` 에서 나왔던 문제와 어떻게 같은 문제인가.

**impl 코드와 테스트**

```java
@Override
public Iterable<Integer> neighbors(int from) {
    checkVertex(from);
    // 내부 목록을 그대로 주면 호출자가 그래프를 바꿀 수 있다. 복사본을 준다.
    List<Integer> result = new ArrayList<>(adjacency[from].size());
    for (Edge e : adjacency[from]) result.add(e.to);
    return result;
}
```

```java
@Test
@DisplayName("이웃 목록을 고쳐도 그래프는 안 변한다")
void neighborsIsDefensive() {
    Graph g = create(3, true);
    g.addEdge(0, 1);
    java.util.List<Integer> copy = neighborList(g, 0);
    copy.clear();

    assertEquals(Set.of(1), neighborSet(g, 0), "내부 목록을 그대로 주면 안 된다");
}
```

**내부 목록을 그대로 주면**

```
 (A) 복사본을 주는 경우 (impl)

    그래프 내부                     호출자
    adjacency[0] ---> [Edge(1,w)]
                                    copy = [1]         <- 새 ArrayList
                                    copy.clear()       <- copy 만 빈다
    adjacency[0] ---> [Edge(1,w)]   그래프는 그대로

 (B) 내부 목록을 그대로 주는 경우

    adjacency[0] ---+
                    |
                    +--> [Edge(1,w)]  <--+
                                         |
                                    copy -+     <- 같은 객체를 가리킨다

                                    copy.clear()
    adjacency[0] ---> [ ]  (비었다)   <- 그래프의 간선이 사라졌다!
    edgeCount 는 여전히 1              <- 개수와 실제가 어긋난다
    hasEdge(0,1) 은 false              <- 조용히 그래프가 손상됐다
```

- 논리: 참조를 넘기면 호출자와 자료구조가 **같은 객체를 공유**한다.\
  호출자의 `clear()`·`add()`·`remove()` 가 그대로 그래프의 변경이 된다.
- 논리: 더 나쁜 것은 `edges` 카운터가 따로 있다는 점이다 — 목록만 비면 **개수와 실제 내용이 어긋난다**.\
  그 뒤의 `edgeCount()` 는 거짓말을 하고, `topologicalSort` 의 진입 차수 계산도 틀어진다.
- 논리: 예외도 로그도 없다 — 전형적인 **조용한 실패**다.

> **방어적 복사(defensive copy)** — 내부 상태를 밖으로 내보낼 때 복사본을 만들어, 호출자가 내부를 바꾸지 못하게 하는 기법.\
> 예: `neighbors` 가 `adjacency[v]` 자체가 아니라 새 `ArrayList` 를 만들어 돌려준다.

> **캡슐화(encapsulation)** — 내부 표현을 감춰서, 밖에서는 정해진 연산으로만 상태를 바꿀 수 있게 하는 것.\
> 예: 그래프의 간선은 `addEdge` 로만 바뀌어야 하며, `neighbors` 의 반환값을 통해 바뀌면 캡슐화가 뚫린 것이다.

**01번 `toArray` 와 같은 문제인 이유**

```
01-dynamic-array 의 toArray

   잘못된 구현 : return elements;          <- 내부 배열을 그대로 준다
   결과 : 호출자가 배열 칸을 고치면 리스트 내용이 바뀐다
          게다가 size 밖의 쓰레기 칸까지 보인다

08-graph 의 neighbors

   잘못된 구현 : return adjacency[from];   <- 내부 목록을 그대로 준다
   결과 : 호출자가 목록을 고치면 그래프가 바뀐다

공통 구조
   1. 자료구조가 내부에 가변 컨테이너를 들고 있다
   2. 조회 메서드가 그 컨테이너의 '참조'를 밖으로 내보낸다
   3. 밖에서 그것을 고치면 자료구조의 불변식이 깨진다
   4. 자료구조는 그 변경을 관측할 방법이 없다 -> 조용히 망가진다

공통 해법
   조회는 '값의 복사본'을 준다. 변경은 정해진 연산(add/addEdge)으로만 받는다
```

- 논리: 같은 실수가 자료구조를 바꿔 가며 **반복해서 나온다**는 것이 이 문제의 요점이다.\
  "내부 가변 상태를 참조로 내보내지 마라"는 자료구조에 무관한 규칙이다.
- 비용(왜): 복사 비용은 O(deg(v))다 — 어차피 호출자가 순회할 크기라 **차수를 바꾸지 않는다**.
- 한계: 그래도 공짜는 아니다 — BFS가 `neighbors` 를 V번 부르면 매번 새 `ArrayList` 가 생겨 총 2E개의 임시 객체가 만들어진다.\
  GC 부담이 되지만 정확성과 바꿀 만한 값이다.
- 한계: 더 싼 대안은 **불변 뷰**(`Collections.unmodifiableList`)나 전용 `Iterator` 를 주는 것이다.\
  복사 없이 변경만 막는다 — 원본 구현은 단순함을 택했다.\
  (원본에 근거 없음 — 내 추론)
- 한계: 인접 행렬의 `neighbors` 는 **애초에 복사본밖에 못 준다**.\
  이웃 목록이라는 실체가 없고 매번 만들어 내기 때문이다 — 이 실수를 할 수 없는 구현이다.

**질문별 답**

- Q: `neighbors` 가 왜 복사본이어야 하는가?\
  A: 내부 목록의 참조를 주면 호출자와 그래프가 같은 객체를 공유하게 되어, 호출자의 `clear()`/`remove()` 가 곧 그래프의 변경이 되기 때문이다.\
  그러면 `edges` 카운터와 실제 간선이 어긋나 `edgeCount()` 가 거짓말을 하고, 그 위에서 도는 알고리즘이 조용히 틀린 답을 낸다.

- Q: 01번 `toArray` 와 어떻게 같은 문제인가?\
  A: 구조가 동일하다 — 자료구조가 가변 컨테이너를 내부에 들고, 조회 메서드가 그 **참조**를 밖으로 내보내고, 밖에서 고치면 불변식이 깨지는데 자료구조는 그것을 관측할 수 없다.\
  해법도 동일하다: 조회는 값의 복사본을 주고, 변경은 정해진 연산으로만 받는다.\
  자료구조가 달라도 같은 실수가 반복되므로, 이것은 그래프의 규칙이 아니라 **캡슐화의 규칙**이다.

#### 13. 09-trie 로의 연결 — 왜 "이 접두사로 시작하는 것 전부"를 못 묻는가

**질문**: 그래프/해시맵으로는 왜 "이 접두사로 시작하는 것 전부"를 물을 수 없는가. 관계를 명시적으로 잇는 구조와 문자열의 접두사를 공유하는 구조는 무엇이 다른가.

**해시맵이 못 하는 이유 (05번의 거래)**

```
해시맵 : 키를 해시 함수에 넣어 나온 숫자로 버킷을 정한다

   hash("car")     = 9382...  ->  버킷 12
   hash("card")    = 1047...  ->  버킷 3
   hash("cart")    = 8821...  ->  버킷 7
   hash("dog")     = 9382...  ->  버킷 12   <- car 와 같은 버킷일 수도 있다

   좋은 해시 함수의 목표는 '고르게 흩뿌리는 것'이다
   그래서 비슷한 키일수록 오히려 멀리 떨어뜨린다 (그게 충돌을 줄인다)

   => "car 로 시작하는 키"들이 저장 위치상 아무 관계가 없다
   => 전부 찾으려면 모든 버킷을 훑는 수밖에 없다 -> O(n)

 해시맵이 접두사 질의를 못 하는 이유는 '기능이 없어서'가 아니라
 그 자료구조의 핵심 성질(해싱)이 접두사 관계를 파괴하기 때문이다
```

**BST가 흉내는 내지만 비싼 이유**

```
BST : 키를 대소 순으로 정렬해 둔다. 문자열이면 사전순이다

   "car" 로 시작하는 키들은 사전순으로 연속 구간에 모여 있다
       ... "cap", "car", "card", "care", "cart", "cat", ...
                  ^^^^^^^^^^^^^^^^^^^^^^^^^
                  이 구간이 car 로 시작하는 것들

   그래서 "car" 이상 "cas" 미만의 범위 질의로 흉내낼 수 있다
   -> 시작 위치 찾기 O(log n), 그 뒤 k 개 순회

   비싼 이유
     비교 한 번이 문자열 비교다. 최악 O(L) (L = 문자열 길이)
     -> 시작 위치 찾기가 O(L log n)
     그리고 비교마다 공통 접두사를 '다시' 훑는다
       "car" vs "card" 를 비교할 때 c, a, r 를 또 읽는다
     => 같은 글자를 여러 번 읽는 낭비가 log n 번 쌓인다

 트라이는 : 경로를 한 번 내려가면 c-a-r 를 딱 한 번씩만 읽는다 -> O(L)
            그 자리가 곧 "car 로 시작하는 것 전부"의 부분 트리다
```

- 논리: 해시맵이 못 하는 이유(해싱이 접두사 관계를 파괴)와 BST가 비싼 이유(같은 접두사를 반복해서 비교)는 **서로 다른 종류의 문제**다.
- 논리: 전자는 **원리적 불가능**에 가깝고, 후자는 **비용의 문제**다.

**관계를 잇는 구조 vs 접두사를 공유하는 구조**

```
08-graph : 관계를 '명시적으로' 잇는다

    addEdge(u, v) 를 호출해야 관계가 생긴다
    관계는 데이터에서 유도되지 않는다 -- 사용자가 주입한다
    서울과 대전이 이어져 있다는 사실은 "서울"과 "대전"이라는 문자열에서 나오지 않는다

09-trie : 관계가 '데이터에서 자동으로' 나온다

    "car", "card", "cart" 를 넣기만 하면
    셋이 c-a-r 를 공유한다는 사실이 구조에 저절로 반영된다

              (root)
                |
                c
                |
                a
                |
                r*          <- "car" 끝  (* = end 표시)
               / \
              d*  t*        <- "card", "cart"

    간선을 따로 그은 적이 없는데 c-a-r 경로가 세 단어의 '공유 조상'이 되었다
    => 관계가 키의 '내용'에서 유도된다

 정리
    그래프  : 관계 = 주입된 데이터        (addEdge 가 필요하다)
    트라이  : 관계 = 키에서 유도된 구조    (insert 만 하면 된다)
```

- 논리: 트라이의 간선은 **글자 하나**이고, 뿌리에서 노드까지의 경로가 곧 키다.\
  키를 통째로 저장하지 않는다 — "경로가 곧 키"다.
- 논리: 그래서 "car 로 시작하는 것 전부"가 **부분 트리 하나**로 딱 떨어진다.\
  질의가 구조와 정확히 맞아떨어질 때 그 자료구조가 그 질의에 "맞는" 것이다.
- 논리: 05번과 같은 종류의 거래가 다시 나온다 — 트라이는 접두사 질의를 얻는 대신 **노드 수 폭발**이라는 메모리 비용을 낸다.

> **접두사(prefix)** — 문자열의 앞쪽 일부. `"car"` 는 `"card"` 의 접두사다.\
> 예: 자동완성은 "사용자가 친 글자를 접두사로 갖는 단어 전부"를 묻는 질의다.

> **트라이(trie)** — 글자를 간선으로 삼아 문자열을 경로로 저장하는 트리. 접두사를 공유해 노드를 아낀다.\
> 예: `"car"`, `"card"`, `"cart"` 가 `c-a-r` 경로를 함께 쓰고 그 아래에서만 갈라진다.

**질문별 답**

- Q: 해시맵으로는 왜 "car 로 시작하는 것 전부"를 못 묻는가?\
  A: 해시 함수가 **비슷한 키일수록 멀리 흩뿌리는 것을 목표로** 하기 때문이다.\
  `"car"` 와 `"card"` 의 저장 위치에 아무 관계가 없으므로, 접두사로 모으려면 모든 버킷을 훑는 O(n) 전수 탐색밖에 없다.\
  기능이 빠진 것이 아니라 그 자료구조의 핵심 성질이 접두사 관계를 파괴하는 것이다.

- Q: BST는 왜 흉내는 내지만 비싼가?\
  A: 사전순 정렬 덕에 같은 접두사를 가진 키들이 연속 구간에 모여 있어 범위 질의로 흉내낼 수 있다.\
  그러나 비교 한 번이 문자열 비교(O(L))이고, 비교할 때마다 **공통 접두사를 처음부터 다시 읽는다**.\
  그래서 시작 위치 찾기가 O(L log n)이 되고, 같은 글자를 `log n` 번 반복해서 훑는 낭비가 쌓인다.

- Q: 관계를 명시적으로 잇는 구조와 접두사를 공유하는 구조는 무엇이 다른가?\
  A: 그래프의 관계는 **주입된 데이터**다 — `addEdge(u, v)` 를 부르지 않으면 관계가 없고, 관계는 정점 값에서 유도되지 않는다.\
  트라이의 관계는 **키의 내용에서 유도된 구조**다 — 단어를 넣기만 하면 공통 접두사가 자동으로 공유 경로가 된다.\
  그래서 "이 접두사로 시작하는 것 전부"라는 질의가 트라이에서는 부분 트리 하나로 딱 떨어진다.

**더 생각할 것**

- 같은 계약을 두 구현으로 만들어 보는 경험이 이 챕터의 진짜 수확이다.\
  `GraphProblems` 는 한 글자도 안 바뀌는데 비용이 2만 배 갈린다 — **인터페이스는 동작을 숨기지만 비용은 숨기지 못한다**.
- BFS·DFS·위상 정렬·다익스트라가 전부 같은 뼈대다.\
  "컨테이너에서 하나 꺼내 이웃을 넣는다"에서 **컨테이너만 바뀐다**(큐 / 스택 / 큐+진입차수 / 우선순위 큐).\
  03·04·07에서 만든 것이 여기서 부품으로 꽂힌다.
- 방문 표시의 위치가 알고리즘마다 다르다.\
  BFS는 **넣을 때**(최단 보장 + 큐 크기 억제), DFS는 **꺼낼 때**(경로를 따라 내려가는 의미 유지), 다익스트라는 **꺼낸 뒤 낡음 판정**(decrease-key 우회).\
  같은 `visited` 배열이 알고리즘마다 다른 역할을 맡는다는 점을 놓치기 쉽다.
