# data-structure/01-data-structures-basics — 정답

## 정답

### 1. 배치가 비용을 정한다

```text
  배열      [10][20][30][40][50]      i번째 주소 = 시작 + i × 칸 크기
  연결 리스트 head → [10|•] → [20|•] → [30|null]   i번째 = next를 i번
```

- 배열: 칸이 붙어 있어 i번째 주소를 곱셈 한 번으로 구한다 → 위치로 읽기 O(1). 중간에 끼우면 그 뒤 칸을 전부 한 칸씩 민다 → O(n).
- 연결 리스트: 끼울 자리 바로 앞 노드를 쥐고 있으면 `next` 두 개만 바꾼다 → O(1). 대신 i번째를 찾으려면 head부터 i번 따라간다 → O(n).

### 2. 두 배 → 4배 vs 2배

- `list.pop(0)`은 꺼낼 때마다 뒤 원소를 전부 당긴다. n개를 다 꺼내는 총비용이 O(n²)이므로 두 배 → 약 4배.
- `deque.popleft()`는 O(1)이므로 총비용 O(n) → 두 배 → 약 2배.
- 실험(CPython 3.12.14, --cpus=2, 3회): `ListQueue` 103.2 → 404.8 → 1593.3 ms(×3.9, ×3.9 — 집필 3회 + 점검 2회 범위 ×3.3~×4.3), `DequeQueue` 3.6 → 7.8 → 15.2 ms(×2.2, ×2.0 — 범위 ×1.9~×2.2). 80,000건에서 약 100배 차이(이 환경 한정).

### 3. "연결 리스트가 삽입·삭제에 유리하다"의 조건

- 삽입·삭제할 위치의 노드(단일 연결 리스트면 바로 앞 노드)를 **이미 쥐고 있을 때**만 O(1)이다. 예: 반복자로 훑으면서 그 자리에 끼우기, LRU 캐시처럼 해시 맵이 노드를 직접 가리킬 때.
- 위치를 인덱스나 값으로 찾아야 하면 찾는 데 O(n)이 든다. 그러면 배열의 "뒤를 미는" O(n)과 같은 급이다. Java에서는 배열 쪽의 연속 메모리 복사(`System.arraycopy`)가 노드 따라가기보다 빨라 `ArrayList`가 이기는 경우가 많다([02-adt-and-cost-contracts](../02-adt-and-cost-contracts/3-answer.md) 실험).

### 4. 정렬된 입력과 BST 높이

- 1..2000을 차례로 넣으면 모든 새 키가 오른쪽 끝에 붙어 높이 = 2000(한 줄).
- 무작위 순서(seed 1)로 넣으면 실험에서 높이 24였다(n=1000은 20). log₂2000 ≈ 11의 두 배 남짓으로, CLRS 12.4의 "무작위로 만든 BST의 기대 높이 O(lg n)"과 맞는 범위다.
- 재귀 높이 함수는 깊이 2000까지 내려간다. CPython 기본 재귀 한도는 1000이라 `RecursionError: maximum recursion depth exceeded`가 났다(실험 첫 시도). 반복형으로 바꾸거나 균형 트리를 쓴다.

### 5. 후위 순회 오타

- 원본 §9 `postorder_traverse`가 오른쪽 서브 트리에 `self.preorder_traverse(cur.right, func)`를 부른다.
- 그래서 오른쪽 서브 트리 {3,6,7}이 전위 순서 `3 6 7`로 나온다. 정답은 `4 5 2 6 7 3 1`.
- `self.postorder_traverse(cur.right, func)`로 고친다. 순회 순서를 단위 테스트로 고정하면 이런 오타를 잡는다.

### 6. 없는 키 삭제와 중복

- `__remove_recursion`은 키가 없으면 `(None, None)`을 돌려준다. 그런데 `remove`는 검사 없이 `removed_node.left = removed_node.right = None`을 실행한다 → `AttributeError`.
- 고침: `if removed_node is None: return None`을 먼저 둔다. 원본 ADT 설명("데이터가 없으면 None 반환")과도 맞춰진다.
- 중복: 원본은 "중복 불가"라 쓰지만 `insert`의 `else` 가지가 같은 값을 오른쪽에 넣는다. 실험에서 6을 다시 넣자 중위 순회가 `[1, 3, 4, 6, 6, 7, ...]`이 됐다. 중복 금지면 `data == cur.data` 가지를 두고, 허용하면 ADT에 "같은 키는 오른쪽"이라고 적는다.

### 7. 컨테이너 메모리

- 실험(OpenJDK 21.0.12, 압축 참조, SerialGC, 2회 동일): `ArrayList` 4,861,992 B(원소당 4.9 B), `LinkedList` 24,000,032 B(원소당 24.0 B), 참고로 `int[]` 4,000,016 B.
- `ArrayList`는 참조 배열 하나다. 참조 4바이트 × 용량 1,215,487칸(1.5배 성장 때문에 원소 수보다 크다).
- `LinkedList`는 원소마다 `Node` 객체(헤더 + item·next·prev 참조)를 만든다 → 원소당 24 B.
- 두 수치 모두 `Integer` 객체 자체는 뺀 값이다. 원시형 배열은 박싱도 없다.

### 8. 연산을 줄이는 것이 장점인 이유

- ADT는 "무엇을 할 수 있나"와 함께 "무엇을 못 하게 하나"를 정한다. 스택은 top만, 큐는 양 끝만 건드리게 해서 구현이 그 연산을 O(1)로 보장할 수 있다.
- Sedgewick 1.3은 `java.util.Stack`이 i번째 접근·바닥에 추가 같은 연산까지 허용하는 것을 "보너스처럼 보이지만 저주"라고 비판한다. 요점은 비용이 아니라 인터페이스 범위다(`Stack`은 배열 기반 `Vector`를 상속해 `get(i)` 자체는 O(1)이다). 연산이 많으면 쓰는 쪽이 LIFO가 아닌 연산을 섞어 쓰게 되고, 구현을 바꿀 자유도 줄어든다.

### 9. 대기열 수만 건

- ① 가장 잦은 연산: 뒤에 넣고 앞에서 꺼내기. ② 비용: 앞에서 꺼내기가 O(1)이어야 한다. ③ 운영 n: 수만 건 → O(n) 꺼내기면 O(n²) 총비용이 실제로 드러나는 크기. ④ 상수·메모리: 노드 객체가 없는 원형 배열이 유리.
- Java: `ArrayDeque`의 `offerLast`/`pollFirst`(null 원소 불가). 동시 접근이면 `BlockingQueue` 구현을 쓴다. 피할 것: `ArrayList.remove(0)`.
- 파이썬: `collections.deque`의 `append`/`popleft`. 피할 것: `list.pop(0)`(원본 §5 방식).
- 대기열 길이가 끝없이 늘면 구조 문제가 아니라 처리량 문제다. 길이 상한과 배압을 둔다.
