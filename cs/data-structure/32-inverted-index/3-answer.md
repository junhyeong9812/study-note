### B. 자료구조 특성

#### 1. 역색인이 왜 필요한가 — 방향을 뒤집는다는 것

- Q: 정방향 색인(문서 → 항)으로는 무엇이 안 되는가?\
  A: 정방향 색인이 답할 수 있는 질문은 **"이 문서 안에 무엇이 들었나"** 하나다.\
  검색이 묻는 것은 정반대다 — **"이 말이 어느 문서에 있나"** 다.\
  정방향 색인에서 그 답을 내려면 문서를 하나씩 열어 그 안에 그 말이 있는지 보는 수밖에 없다.\
  그러면 색인이 있으나 없으나 전부 훑는 것이고, 그게 전수 조사다.\
  즉 정방향 색인이 못 하는 것이 아니라, **질문의 방향이 색인의 방향과 반대**라서 색인이 도움이 안 된다.

- Q: 전수 조사로는 정확히 무엇이 안 되는가?\
  A: 답은 나온다. 안 되는 것은 **비용**이다.\
  `LinearScanEngine.search` 는 `documents` 맵 전체를 한 번 돌면서 문서마다 다시 분석한다.\
  그래서 질의가 무엇이든 방문 수가 정확히 문서 수다.

```java
// impl/LinearScanEngine.java — 전수 조사의 본체
for (Map.Entry<Integer, String> entry : documents.entrySet()) {
    visitedDocs++;
    int[] counts = new int[t];
    for (String term : indexAnalyzer.analyze(entry.getValue())) {
        int i = terms.indexOf(term);
        if (i >= 0) {
            counts[i]++;
        }
    }
    ...
}
```

```text
MeasurementTest 가 못 박은 수 (문서 2,000개, 낱말 200종)

  전수 조사 (LinearScanEngine)          역색인 (InvertedIndexEngine)
    제일 흔한 낱말 t000   방문 2,000       제일 흔한 낱말 t000   방문   346  (df 346)
    제일 드문 낱말 t199   방문 2,000       제일 드문 낱말 t199   방문     2  (df 2)
    드문 낱말 둘          방문 2,000       드문 낱말 둘          방문     8

  전수 조사는 질의가 무엇이든 2,000 이다. 질의를 안 보고 문서만 보기 때문이다.
  역색인은 "그 말이 실제로 든 문서 수" 만큼만 본다. 2 대 2,000 이 이 박스의 전부다.
```

- Q: 이 수는 테스트에 assert 돼 있는가?\
  A: 전부 그렇다.\
  `MeasurementTest.VisitedDocuments.naiveAlwaysVisitsEveryDocument` 가 `assertEquals(DOCS, ...)` 를 세 번 한다.\
  `invertedIndexVisitsOnlyPostings` 가 `assertEquals(346, common)`, `assertEquals(2, rare)`, `assertEquals(8, both)` 로 못 박는다.\
  README 의 "2 대 2,000" 은 그 두 값을 나란히 적은 것이다.

> **역색인(inverted index)** — "항 → 그 항이 든 문서 목록" 방향으로 미리 만들어 둔 표.\
> 예: `index.get("고양이")` 가 `[문서 3, 문서 9, 문서 41]` 을 바로 준다. 나머지 문서는 열어보지도 않는다.

> **포스팅 리스트(posting list)** — 항 하나에 딸린 문서 목록. 이 구현에서는 `List<Posting>` 이고 늘 문서 번호 오름차순이다.\
> 예: `index.get("t199")` 의 길이가 2 이면 t199 가 든 문서가 2개뿐이라는 뜻이고, 질의 `t199` 는 그 2개만 본다.

> **df(document frequency, 문서 빈도)** — 그 항을 가진 문서의 개수. 역색인에서는 포스팅 리스트의 길이 그 자체다.\
> 예: `index.get(terms.get(i)).size()` 한 줄로 얻는다. 전수 조사는 같은 값을 얻으려고 문서를 전부 훑는다.

- Q: "색인의 방향을 뒤집는다"에서 뒤집히는 것은 정확히 무엇인가?\
  A: **맵의 키와 값이 뒤집힌다.**\
  정방향은 `Map<문서번호, 항 목록>` 이다 — 키가 문서, 값이 항들.\
  역색인은 `Map<항, 문서 목록>` 이다 — 키가 항, 값이 문서들.\
  `InvertedIndexEngine` 의 필드가 바로 그 모양이다.

```java
// impl/InvertedIndexEngine.java
/** 항 -> 포스팅 리스트. 리스트는 늘 문서 번호 오름차순이다. */
final Map<String, List<Posting>> index = new HashMap<>();
```

```text
같은 말뭉치를 두 방향으로 적으면

  정방향 (LinearScanEngine 이 들고 있는 것)
    0 -> [검은, 고양이, 담장]
    1 -> [고양이, 검은, 담장]
    2 -> [검은, 개, 담장]

  역색인 (InvertedIndexEngine 이 들고 있는 것)
    검은   -> [0, 1, 2]
    고양이 -> [0, 1]
    담장   -> [0, 1, 2]
    개     -> [2]

  담긴 정보는 같다. 같은 (항, 문서) 쌍을 다른 방향으로 늘어놓았을 뿐이다.
  달라지는 것은 "무엇을 키로 한 번에 찾을 수 있는가" 하나다.
```

- Q: 정보가 같은데 왜 성능이 달라지는가?\
  A: 자료구조가 주는 것은 정보가 아니라 **접근 경로**이기 때문이다.\
  같은 사실을 담고 있어도, 키로 잡아둔 축만 O(1) 로 열리고 나머지 축은 전부 훑어야 한다.\
  그래서 "무엇을 자주 물을 것인가"가 "무엇을 키로 둘 것인가"를 정한다.\
  33번에서 같은 파일 시스템을 트리와 평면 맵 둘로 만드는 이유가 정확히 이것의 반복이다.

- Q: 06번 이진 탐색 트리의 "정렬이 곧 능력"이 여기서 어떻게 되풀이되는가?\
  A: BST 에서 정렬이 능력이었던 이유는 **비교 한 번이 후보의 절반을 버려주기** 때문이었다.\
  정렬이 깨지면 그 버리기가 성립하지 않고, 트리는 그냥 이상하게 생긴 연결 리스트가 된다.\
  역색인에서 정렬이 능력인 이유는 **두 리스트를 한 번씩만 훑어 교집합을 낼 수 있기** 때문이다.\
  정렬이 깨지면 그 한 번 훑기가 성립하지 않고, 한쪽 원소마다 상대를 다 뒤져야 한다.\
  둘 다 "정렬이라는 불변식 하나가 알고리즘의 자격을 만든다"는 같은 모양이다.\
  그리고 둘 다 **정렬이 깨져도 예외가 안 난다** — 답이 조용히 줄어들 뿐이다.

- Q: 그 불변식은 코드 어디에 있는가?\
  A: `insertSorted` 다. 이 메서드 하나가 "포스팅 리스트는 문서 번호 오름차순"이라는 계약을 지킨다.

```java
// impl/InvertedIndexEngine.java — 정렬 불변식을 지키는 자리
private static void insertSorted(List<Posting> postings, Posting posting) {
    int low = 0;
    int high = postings.size();
    while (low < high) {
        int mid = (low + high) >>> 1;
        if (postings.get(mid).docId() < posting.docId()) {
            low = mid + 1;
        } else {
            high = mid;
        }
    }
    postings.add(low, posting);
}
```

- Q: 색인에 들어가는 과정을 처음부터 끝까지 따라가면?\
  A: 본문 하나가 항 목록이 되고, 항 목록이 문서 안에서 한 번 뭉쳐진 뒤, 항마다 포스팅 리스트에 꽂힌다.

```java
// impl/InvertedIndexEngine.java — index(docId, text) 의 전부
Map<String, Posting> perDocument = new LinkedHashMap<>();
List<String> terms = indexAnalyzer.analyze(text);
for (int position = 0; position < terms.size(); position++) {
    perDocument.computeIfAbsent(terms.get(position), term -> new Posting(docId))
            .addPosition(position);
}
for (Map.Entry<String, Posting> entry : perDocument.entrySet()) {
    insertSorted(index.computeIfAbsent(entry.getKey(), term -> new ArrayList<>()),
            entry.getValue());
}
```

```text
index(0, "the Black CAT and the cat") 을 따라가면

  1. 자르기        [the, Black, CAT, and, the, cat]
  2. 소문자화      [the, black, cat, and, the, cat]
  3. 불용어 제거   [black, cat, cat]            the, and 가 빠진다
     -> 위치는 이 목록에서의 인덱스다. black = 0, cat = 1, cat = 2

  4. 문서 안에서 항별로 뭉친다 (perDocument)
       black -> Posting(문서0, 위치 [0])
       cat   -> Posting(문서0, 위치 [1, 2])      같은 항이 두 번 나와도 포스팅은 하나다

  5. 항마다 포스팅 리스트에 오름차순으로 꽂는다
       index["black"] = [ ... Posting(0) ... ]
       index["cat"]   = [ ... Posting(0) ... ]

  요점 두 가지
    - 위치는 "원문의 글자 위치" 가 아니라 "분석 결과 목록의 인덱스" 다. 불용어를 뺀 뒤의 번호다
    - 한 문서 안에서 먼저 뭉치지 않으면 같은 항의 포스팅이 여러 개 생겨 포스팅 리스트가 망가진다
```

- Q: 왜 `Posting` 은 빈도를 따로 안 들고 위치 개수로 세는가?\
  A: 두 값을 다 들면 **둘이 어긋날 자리**가 생기기 때문이다.\
  어긋나면 조용히 점수가 틀린다 — `tf` 가 곧 빈도이므로 순위가 흔들리는데 예외는 안 난다.\
  그래서 `frequency()` 가 `positions.size()` 를 그대로 돌려준다.\
  "같은 사실을 두 군데 적지 않는다"는 원칙이 여기서는 **버그 하나를 구조적으로 없애는** 일이 된다.

- Q: `indexedDocIds` 가 왜 따로 있는가?\
  A: **항이 하나도 없는 문서도 한 개로 세야** 하기 때문이다.\
  분석 결과가 빈 문서(예: 불용어만 든 문서)는 `index` 어디에도 안 들어간다.\
  그런데 `docCount()` 는 TF-IDF 의 `N` 이라 그 문서도 세야 맞다.\
  포스팅 리스트로 문서 수를 세려 하면 그 문서가 조용히 사라지고, `N` 이 작아져 모든 점수가 미묘하게 틀린다.

**더 생각할 것**

- "색인을 만든다"는 것은 언제나 **질문의 방향으로 키를 잡는다**는 뜻이다.\
  RDB 의 보조 인덱스, 카프카의 오프셋 인덱스, 09번 트라이의 접두사 탐색이 전부 같은 동작이다.
- 그래서 색인은 공짜가 아니다 — 방향 하나를 빠르게 하려고 **그 방향으로 데이터를 한 벌 더 들고** 있는 것이다.\
  대가는 메모리와 쓰기 비용이고, 질문 3·5에서 그 수를 직접 잰다.
- 정방향 색인을 버려도 되는 것은 아니다.\
  검색 결과 화면에 "문서 제목과 본문 일부"를 보여주려면 문서 → 본문 방향이 필요하다.\
  실제 검색 엔진은 둘 다 들고 있다(여기서는 `LinearScanEngine` 이 정방향 쪽 역할을 겸한다).

#### 2. 어떤 데이터·질의 패턴에 적합하고 언제 쓰면 안 되는가

- Q: 어떤 데이터에 적합한가?\
  A: **문서가 많고, 한 문서에 든 서로 다른 항의 수는 문서 수에 비해 훨씬 적은** 데이터다.\
  그래야 포스팅 리스트가 전체 문서 수보다 짧아지고, 색인이 후보를 줄여준다.\
  그리고 **문서가 잘 안 변하는** 데이터다. 아래에서 보듯 이 구현에는 갱신·삭제가 아예 없다.

- Q: 어떤 질의 패턴에 적합한가?\
  A: **항에서 출발하는 질의** — "이 말이 든 문서", AND, 구문, 순위 매기기.\
  질의가 잦을수록 좋다. 색인은 넣을 때 한 번 일하고 찾을 때마다 갚아 받는 구조라, 질의 수로 나눠야 이득이 된다.\
  그리고 **드문 항을 묻는 질의**일수록 좋다 — 방문 수가 df 에 정비례하기 때문이다(t199 는 2, t000 은 346).

- Q: 언제 쓰면 안 되는가?\
  A: 문서 수가 적을 때 — 2,000개가 아니라 20개면 전수 조사로 20번 여는 것이 색인 유지보다 싸다.\
  모든 문서에 든 항을 주로 물을 때 — 질문 4에서 재는 그대로 색인이 전수 조사와 같아진다.\
  문서가 계속 바뀌거나 지워질 때 — 바로 아래 항목.\
  "항"으로 쪼갤 수 없는 질의일 때 — 부분 문자열 검색(`*고양*`), 정규식, 오타 허용 검색은 항 단위 키로는 못 잡는다(그래서 20번 radix trie, 21번 suffix array 같은 다른 구조가 따로 있다).

> **항(term)** — 분석기를 통과한 뒤의 검색 단위. 원문의 낱말과 같지 않다.\
> 예: `StandardAnalyzer` 는 "Black CAT" 을 `[black, cat]` 으로 만든다. 색인의 키는 `black` 이지 `Black` 이 아니다.

> **분석기(analyzer)** — 원문을 항 목록으로 바꾸는 파이프라인. 여기서는 자르기 → 소문자화 → 불용어 제거 순서다.\
> 예: `StandardAnalyzer.analyze("the Black CAT")` → `[black, cat]`. `the` 는 불용어라 사라진다.

- Q: 문서가 계속 바뀌거나 삭제되면 어떻게 되는가?\
  A: 이 구현은 **아예 못 한다**. 계약에 갱신·삭제가 없다.\
  `SearchEngine.index` 의 주석이 "지우기와 고쳐 넣기는 다루지 않는다"고 못 박고, 같은 docId 를 두 번 넣으면 던진다.

```java
// impl/InvertedIndexEngine.java
if (!indexedDocIds.add(docId)) {
    throw new IllegalArgumentException("이미 색인된 문서 번호다: " + docId);
}
```

- Q: 왜 그 기능이 어려운가?\
  A: 문서 하나의 흔적이 **색인 전체에 흩어져 있기** 때문이다.\
  문서 7을 지우려면 문서 7에 들었던 모든 항의 포스팅 리스트에서 문서 7을 빼야 한다.\
  그 항이 몇 개인지는 색인만 봐서는 모른다 — 원문을 다시 분석하거나, 문서 → 항 방향을 따로 들고 있어야 한다.\
  즉 **삭제를 하려면 정방향 색인이 또 필요하다**. 뒤집은 대가가 여기서 나온다.\
  전수 조사는 `documents.remove(docId)` 한 줄이면 끝난다. 원문 한 벌이 전부이기 때문이다.

- Q: 실제 검색 엔진은 그 문제를 어떻게 다루는가?\
  A: (원본에 근거 없음 — 내 추론) 대개 "지웠다"는 표시만 따로 두고 결과에서 걸러내다가, 나중에 색인을 통째로 다시 만들면서 진짜로 지운다.\
  24번 LSM 트리에서 본 tombstone + compaction 이 같은 모양이다.\
  이 박스는 그 주제를 빼고 "안 다룬다"고 명시하는 쪽을 골랐다.

- Q: 포스팅 리스트를 문서 번호 오름차순으로 유지하는 계약이 삽입 비용에 무엇을 강제하는가?\
  A: **넣을 자리를 찾아 중간에 꽂아야 한다**는 것을 강제한다.\
  `insertSorted` 는 이분 탐색으로 자리를 찾고(`O(log df)`) `postings.add(low, posting)` 으로 꽂는다.\
  그런데 `ArrayList` 의 중간 삽입은 뒤를 전부 한 칸씩 미는 일이라 **`O(df)`** 다.\
  즉 자리 찾기는 싸고 **밀기가 비싸다**. 01번 동적 배열에서 본 시프트 비용 그대로다.

```text
insertSorted 가 하는 일 : postings = [문서2, 문서5, 문서9] 에 문서7 을 꽂는다

  이분 탐색으로 자리를 찾는다 (low = 2)
    idx     0        1        2
        +--------+--------+--------+
        | 문서2  | 문서5  | 문서9  |
        +--------+--------+--------+
                           ^ 여기에 들어가야 오름차순이 유지된다

  add(2, 문서7) -> 뒤가 한 칸씩 밀린다 (복사 1회)
    idx     0        1        2        3
        +--------+--------+--------+--------+
        | 문서2  | 문서5  | 문서7  | 문서9  |
        +--------+--------+--------+--------+

  자리 찾기 O(log df) + 밀기 O(df)  ->  한 번의 삽입이 O(df)
```

- Q: 그런데 문서를 번호 순서대로 넣으면 그 비용이 안 나온다. 왜인가?\
  A: 넣는 문서 번호가 계속 커지면 이분 탐색의 결과가 **늘 맨 뒤(`low == size`)** 이기 때문이다.\
  맨 뒤 삽입은 밀 것이 없으므로 `ArrayList.add` 와 같고, 01번에서 본 상환 O(1) 이다.\
  실제로 `TestSupport.indexAll` 은 docId 를 0부터 순서대로 넣으므로 대부분의 테스트에서 이 비용이 안 보인다.

- Q: 그러면 `insertSorted` 대신 그냥 `add` 만 해도 되지 않는가?\
  A: 안 된다. 그리고 **그 실수가 조용히 지나간다**는 것이 이 박스의 핵심 중 하나다.\
  문서 번호가 뒤섞여 들어오는 순간 리스트의 정렬이 깨지고, 깨진 리스트로 병합하면 교집합이 답을 조용히 빠뜨린다.\
  `CrossCheckTest.shuffledDocIds` 가 문서 순서를 셔플해서 딱 이것만 노린다.

```java
// src/test/.../CrossCheckTest.java
// 포스팅 리스트를 append 만 하면 정렬이 깨지고, 깨진 리스트로 병합하면
// 답이 조용히 줄어든다. 문서를 번호 순으로 넣는 테스트로는 절대 안 잡힌다.
List<String> documents = new TestSupport.Dice(20260814L).documents(1200, 60, 8, 24);
List<Integer> order = inOrder(documents.size());
...
crossCheck("뒤섞인 문서 번호", documents, order, queries(88L, 200, 60), ...);
```

> **불변식(invariant)** — 자료구조가 어떤 연산을 겪어도 계속 참이어야 하는 성질.\
> 예: "포스팅 리스트는 늘 문서 번호 오름차순" 이 이 구조의 불변식이고, 교집합 병합이 그것을 그냥 믿고 동작한다.

- Q: 이 구조가 기대는 계약이 정렬 말고 또 있는가?\
  A: **분석기 파이프라인의 순서**가 계약이다. 자르기 → 소문자화 → 불용어 제거, 이 순서여야 한다.\
  뒤집으면 `"The"` 가 안 걸러지고 `"the"` 만 걸러져서, 같은 말이 두 항이 된다.\
  `StandardAnalyzer.DEFAULT_STOPWORDS` 가 전부 소문자로 적혀 있는 것이 그 순서를 전제한 표현이다.

```java
// impl/StandardAnalyzer.java
for (String token : tokenizer.tokenize(text)) {
    String lower = token.toLowerCase(Locale.ROOT);
    if (!stopwords.contains(lower)) {
        out.add(lower);
    }
}
```

- Q: `Locale.ROOT` 를 명시한 이유는?\
  A: 기본 로케일을 쓰면 **기계마다 답이 달라지기** 때문이다.\
  터키어 로케일에서는 `I` 가 점 없는 `ı` 로 내려가서, 같은 코드가 같은 입력에 다른 항을 만든다.\
  그러면 색인과 질의가 어긋나고 — 질문 5에서 볼 "조용한 0건" 이 환경 차이만으로 발생한다.\
  이런 것은 테스트가 개발자 기계에서 전부 통과하고 운영에서만 틀리는 종류라 특히 나쁘다.

- Q: `SimpleTokenizer` 가 마지막 버퍼를 흘려보내는 코드는 왜 있는가?\
  A: 마지막 토큰은 **경계를 못 만나고 끝나기** 때문이다.\
  `"검은 고양이"` 를 훑으면 `고양이` 는 뒤에 구분자가 없어서, 루프가 끝난 뒤 따로 담지 않으면 조용히 사라진다.\
  없어도 예외가 안 나고 대부분의 문서에서 "마지막 낱말 하나만" 빠진다 — 눈으로는 거의 안 보이는 결손이다.\
  01번에서 본 **경계 조건 하나가 조용한 오답이 되는** 패턴 그대로다.

**더 생각할 것**

- 불변식을 깨뜨리는 코드는 **깨진 그 순간에 안 터지고 그것을 믿는 코드에서 틀린 답으로 나타난다**.\
  그래서 "정렬을 유지한다"는 계약은 `insertSorted` 한 군데에 가둬 두는 것이 옳다.\
  여러 곳에서 각자 정렬하면 한 군데만 빠져도 전체가 무너진다.
- "이 구조는 갱신에 약하다"는 말은 **약하다**가 아니라 **뒤집은 방향의 반대로 일해야 해서 비싸다**로 읽는 것이 정확하다.\
  자료구조의 약점은 대개 그 구조가 판 것의 뒷면이다.
- 넣는 순서를 통제할 수 있으면(로그·크롤링 결과처럼 번호가 커지는 순서면) 정렬 유지 비용이 사실상 0 이다.\
  "최악이 O(df)" 와 "우리 워크로드에서 O(1)" 은 둘 다 참일 수 있다.

#### 3. AND 질의의 비용 · 구문 검색이 먼저 좁히는 이유 · 위치의 대가

- Q: 포스팅 리스트가 정렬돼 있으면 교집합을 왜 한 번 훑기로 낼 수 있는가?\
  A: 두 리스트를 앞에서부터 나란히 보면서 **작은 쪽만 전진**시키면 되기 때문이다.\
  둘 다 오름차순이므로, 왼쪽이 오른쪽보다 작다는 것은 "왼쪽의 이 값은 오른쪽에 영영 없다"는 뜻이다(오른쪽은 이제부터 더 커지기만 하니까).\
  그래서 그 값은 다시 볼 필요 없이 버리고 넘어갈 수 있다.\
  정렬이 주는 것은 **"앞으로 안 나올 것"을 확정해주는 능력**이고, 그래서 되돌아갈 일이 없다.

```java
// impl/InvertedIndexEngine.java — 한 번 훑기 병합
while (i < merged.size() && j < other.size()) {
    comparisons++;
    int left = merged.get(i);
    int right = other.get(j).docId();
    if (left == right) {
        next.add(left);
        i++;
        j++;
        visitedDocs += 2;
    } else if (left < right) {
        i++;
        visitedDocs++;
    } else {
        j++;
        visitedDocs++;
    }
}
```

```text
두 정렬 리스트의 교집합 : A = [1, 4, 7, 9] , B = [2, 4, 9]

  i,j 시작                 A: [1] 4  7  9        B: [2] 4  9
                               ^i                    ^j
  1 < 2  -> i++            A:  1 [4] 7  9        B: [2] 4  9
  4 > 2  -> j++            A:  1 [4] 7  9        B:  2 [4] 9
  4 == 4 -> 담고 i++ j++   A:  1  4 [7] 9        B:  2  4 [9]   결과 [4]
  7 < 9  -> i++            A:  1  4  7 [9]       B:  2  4 [9]
  9 == 9 -> 담고 끝        결과 [4, 9]

  포인터가 절대 뒤로 안 간다 -> 비교 횟수가 두 길이의 합을 못 넘는다 -> O(m + n)
```

- Q: 정렬이 안 돼 있으면 왜 못 내는가?\
  A: "앞으로 안 나올 것"을 확정할 수 없기 때문이다.\
  `[7, 1, 9, 4]` 에서 7 다음에 1 이 나오므로, 지금 본 값보다 작은 값이 뒤에 또 있을 수 있다.\
  그래서 한쪽 원소 하나마다 상대 리스트를 **끝까지** 뒤져야 하고, 총비용이 `O(m × n)` 이 된다.\
  해시셋에 한쪽을 통째로 넣으면 `O(m + n)` 시간으로 돌아올 수는 있는데, 그 대신 **`O(m)` 짜리 메모리를 질의마다 새로 잡아야** 한다.\
  정렬을 유지해 두는 것은 그 메모리를 색인 시점에 미리 지불해 두는 것이다.

- Q: 이 구현이 세는 `comparisons` 와 `visitedDocs` 는 각각 무엇인가?\
  A: `SearchStats` 가 단위를 못 박아 둔다.\
  `comparisons` — 병합에서 두 문서 번호를 견준 횟수. 전수 조사는 병합이 없으므로 늘 0.\
  `visitedDocs` — 포스팅 리스트에서 원소를 하나 읽으면 1. 전수 조사는 문서를 하나 여는 것이 1이라 질의마다 정확히 문서 수.\
  둘 다 **마지막 질의 하나**의 값이고 `search`/`searchPhrase` 시작 때 0으로 되돌린다.\
  시간이 아니라 걸음 수를 세는 이유는 기계와 JIT 에 흔들리지 않게 하려는 것이다.

- Q: `searchPhrase` 가 먼저 AND 로 좁히고 그 안에서만 위치를 보는 이유는?\
  A: 좁히지 않으면 **전수 조사가 되기 때문**이다.\
  구문의 답은 언제나 AND 답의 부분집합이다 — 붙어 있으려면 일단 둘 다 들어 있어야 하니까.\
  그래서 AND 로 후보를 줄인 뒤 그 후보 안에서만 위치 산술을 하면, 위치 검사를 후보 수만큼만 한다.\
  안 좁히면 모든 문서에 대해 위치를 확인해야 하고, 그건 원문을 다시 훑는 전수 조사와 같은 일이다.

```java
// impl/InvertedIndexEngine.java — 좁히고 나서 본다
List<Integer> out = new ArrayList<>();
for (int docId : intersect(SearchEngine.distinctTerms(terms))) {
    if (containsPhrase(terms, docId)) {
        out.add(docId);
    }
}
```

```text
"검은 고양이" 를 AND 로 묻는 것과 구문으로 묻는 것

  문서 0 : 검은(0) 고양이(1) 가(2) 담장(3) ...     -> 0 다음 칸이 1 이다. 붙어 있다
  문서 1 : 고양이(0) 가(1) 검은(2) 담장(3) ...     -> 검은은 2, 고양이는 0. 안 붙어 있다

  AND    답 [0, 1]   두 항이 들어 있기만 하면 된다
  구문   답 [0]      검은의 위치 p 에 대해 고양이가 p+1 에 있어야 한다

  PhraseTest.phraseIsStrictlyNarrower 가 이 두 줄을 그대로 assert 한다.
  위치를 안 보고 AND 결과를 그대로 주면 답이 늘어나는 쪽으로만 틀리고 예외는 안 난다.
```

- Q: 위치 검사는 어떻게 하는가?\
  A: 첫 항이 나온 자리 `start` 마다, i 번째 항이 `start + i` 에 있는지 본다.\
  위치 목록이 오름차순이라는 `Posting` 의 계약을 그대로 믿는 코드다.

```java
// impl/InvertedIndexEngine.java
private boolean containsPhrase(List<String> terms, int docId) {
    for (int start : positionsOf(terms.get(0), docId)) {
        boolean ok = true;
        for (int i = 1; i < terms.size(); i++) {
            if (!positionsOf(terms.get(i), docId).contains(start + i)) {
                ok = false;
                break;
            }
        }
        if (ok) {
            return true;
        }
    }
    return false;
}
```

- Q: 위치를 담는 대가는 실제로 얼마인가?\
  A: `MeasurementTest.IndexSize.positionsCostMoreThanPostings` 가 문서 2,000개 기준으로 못 박는다.

```text
  항 200종 (불용어 the, and 는 안 들어간다)
  포스팅 (항, 문서) 쌍      37,348
  위치 정수                 40,158
  위치 대 포스팅            1.08 배

  assertEquals(200, terms) / assertEquals(37_348, postings) / assertEquals(40_158, positions)
  셋 다 테스트에 assert 돼 있다.
```

- Q: 40,158 이 37,348 의 1.08 배인데 README 는 왜 "색인의 대부분"이라고 하는가?\
  A: 개수를 정수 단위로 세면 색인 안의 정수가 **포스팅의 문서 번호 37,348개 + 위치 40,158개**이고, 위치 쪽이 절반을 넘는다.\
  그 뜻에서 "대부분"이다. **1.08 배는 "포스팅 하나당 위치가 평균 1.08개"라는 뜻**이지 색인이 1.08배가 된다는 뜻이 아니다.\
  이 말뭉치는 문서가 8~40 낱말로 짧고 어휘가 200종이라, 한 문서 안에서 같은 낱말이 거의 안 겹친다 — 그래서 비율이 1에 가깝다.\
  문서가 길어질수록 한 포스팅에 위치가 여러 개 붙어 이 비율은 커진다.\
  (README 표현과 실제 수치의 관계는 위와 같다. 기준은 테스트가 assert 한 37,348 / 40,158 이다.)

- Q: 위치 정수의 개수가 40,158 이라는 것이 무엇을 뜻하는가?\
  A: **원문의 항 하나마다 정수 하나**가 색인에 들어간다는 뜻이다.\
  `everyTokenBecomesOnePosition` 이 말뭉치를 다시 분석해 토큰 수를 세고 `positionCount()` 와 같은지 확인한다.\
  이 등식이 깨지면 색인이 무엇을 흘렸거나 두 번 담은 것이고, **답이 맞는 동안에도 깨질 수 있어서** 따로 센다.

- Q: 그러면 위치를 버리면 되지 않는가?\
  A: 버리면 색인이 작아지고 **구문 검색을 아예 못 하게 된다**.\
  전수 조사는 원문을 들고 있으므로 위치가 공짜다 — 다시 분석하면 순서가 그대로 나온다.\
  역색인은 원문을 버렸기 때문에 **미리 담아두지 않으면 영영 못 한다**.\
  이것이 이 구조에서 "무엇을 버렸는가"가 "무엇을 못 하는가"를 정하는 가장 선명한 자리다.

> **구문 검색(phrase query)** — 항들이 그 순서 그대로 붙어 나오는 문서만 찾는 질의.\
> 예: `searchPhrase("검은 고양이")` 는 "고양이 가 검은 담장" 을 답으로 주지 않는다. `search("검은 고양이")` 는 준다.

> **한 번 훑기 병합(merge / linear scan intersection)** — 정렬된 두 목록을 포인터 둘로 동시에 훑어 교집합을 내는 기법.\
> 예: 둘 다 오름차순이므로 작은 쪽만 전진시키면 되고, 포인터가 뒤로 안 가서 비교가 두 길이의 합을 안 넘는다.

- Q: 점수를 매길 때 `tf` 는 어떻게 얻는가? 그것도 정렬 덕을 보는가?\
  A: 그렇다. 후보 문서마다 항의 `Posting` 을 **이분 탐색**으로 찾는다.\
  포스팅 리스트가 오름차순이라 `O(log df)` 이고, 정렬이 깨지면 이것도 같이 조용히 틀린다.

```java
// impl/InvertedIndexEngine.java — 오름차순을 두 번째로 써먹는 자리
private static Posting find(List<Posting> postings, int docId) {
    if (postings == null) {
        return null;
    }
    int low = 0;
    int high = postings.size() - 1;
    while (low <= high) {
        int mid = (low + high) >>> 1;
        int current = postings.get(mid).docId();
        if (current == docId) {
            return postings.get(mid);
        }
        if (current < docId) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return null;
}
```

```text
정렬 하나가 세 군데에서 일한다

  1. insertSorted      자리를 이분 탐색으로 찾는다          O(log df) + 밀기 O(df)
  2. intersect         한 번 훑기로 교집합을 낸다            O(m + n)
  3. find              후보의 tf 와 위치를 이분 탐색으로     O(log df)

  하나의 불변식이 세 연산의 비용을 동시에 정한다.
  거꾸로 말하면 정렬이 깨지면 셋이 한꺼번에 조용히 틀린다.
```

- Q: 구문 검색의 비용을 대략 적으면?\
  A: `AND 병합 비용` + `후보 수 × 첫 항의 위치 개수 × 나머지 항 수 × 위치 목록 탐색`이다.\
  `positionsOf(...).contains(start + i)` 가 `List.contains` 라 위치 목록 길이에 선형이다.\
  문서가 짧으면 위치 목록도 짧아서 문제가 안 되지만, 아주 긴 문서에서 아주 흔한 항으로 구문을 물으면 이 부분이 커진다.\
  (원본에 근거 없음 — 내 추론) 실제 엔진은 위치 목록도 정렬돼 있으므로 `contains` 대신 위치끼리 다시 한 번 훑기 병합을 한다.\
  `MeasurementTest.phraseNarrowsBeforeCheckingPositions` 는 그 세부 대신 **좁히기가 실제로 되는지**만 본다 — 전수 조사가 2,000 을 방문할 때 역색인은 `DOCS / 2` 미만을 방문해야 한다는 부등식이다.

**더 생각할 것**

- 실제 검색 엔진은 여기에 한 단계를 더 얹는다 — 포스팅 리스트에 **건너뛰기 포인터(skip list)** 를 달아, 병합 중에 확실히 없는 구간을 통째로 뛰어넘는다.\
  12번 스킵 리스트가 그 자리다.
- "먼저 좁히고 비싼 검사는 나중에"는 검색만의 요령이 아니다.\
  25번 공간 색인의 후보 상자 필터링, 30번 구간 트리의 겹침 판정도 같은 모양이다 — **싼 필터로 후보를 줄이고 비싼 판정은 후보에만** 한다.
- 위치를 담는 결정은 되돌리기 어렵다.\
  안 담고 운영하다가 나중에 구문 검색이 필요해지면 **색인을 전부 다시 만들어야** 한다. 원문이 있어야 다시 만들 수 있다는 것도 함께 따라온다.

#### 4. 역색인이 전수 조사에 지는 입력 · 그때 TF-IDF 가 0 인 이유

- Q: 지는 입력을 만들어 보라.\
  A: **모든 문서에 있는 항**을 물으면 된다. 테스트가 그 입력을 그대로 만들어 둔다.

```java
// src/test/.../MeasurementTest.java — commonTermIsNoBetterThanScanning
List<String> everywhere = new ArrayList<>();
for (int i = 0; i < 500; i++) {
    everywhere.add("alpha beta " + word(i % 20));
}
InvertedIndexEngine engine = new InvertedIndexEngine();
indexAll(engine, everywhere);

engine.search("alpha", 10);
long visited = engine.visitedDocs();

assertEquals(500, engine.postings("alpha").size(), "df 가 문서 수와 같다");
assertEquals(500, visited, "포스팅 리스트를 통째로 훑는다");
```

```text
문서 500개가 전부 "alpha beta t0xx" 로 시작한다

  index["alpha"] = [0, 1, 2, ... , 499]    <- 길이가 문서 수와 같다
  질의 "alpha"  ->  이 리스트를 통째로 훑는다  ->  방문 500

  전수 조사      방문 500 (문서를 전부 연다)
  역색인         방문 500 (포스팅을 전부 읽는다)

  같다. 게다가 역색인은 그 500 짜리 리스트를 메모리에 들고 있는 값까지 치렀다.
  색인은 후보를 줄여야 이기는데, 줄일 것이 없으면 줄일 수 없다.
```

- Q: 25번의 "모든 점이 같은 거리" · 30번의 "결과가 크면 진다"와 왜 같은 자리인가?\
  A: 셋 다 **가지치기(pruning)가 전제하는 조건이 무너진 경우**이기 때문이다.\
  공간 색인은 "대부분의 점이 멀어서 상자째 버릴 수 있다"를 전제한다. 모든 점이 같은 거리면 버릴 상자가 없다.\
  구간 트리는 "겹치는 구간이 적어서 서브트리째 버릴 수 있다"를 전제한다. 결과가 전부면 버릴 서브트리가 없다.\
  역색인은 "그 항을 가진 문서가 적어서 나머지를 안 열어도 된다"를 전제한다. 모두가 가졌으면 안 열 문서가 없다.\
  전부 **"답이 작다"에 값이 걸린 구조**고, 답이 크면 값이 0 이 된다.\
  더 정확히는 그냥 0 이 아니라 **마이너스**다 — 색인 유지 비용만큼 손해다.

- Q: 그때 TF-IDF 점수가 왜 0 이 되는가?\
  A: 식이 `tf × log(N / df)` 인데 `df == N` 이면 `log(1) = 0` 이라서다.

```java
// impl/TfIdfScorer.java
return termFrequency * Math.log((double) documentCount / documentFrequency);
```

```text
손계산 : 문서 5개짜리 색인에서 "회사" 가 5개 문서 전부에 있다

  df = 5, N = 5
  log(5 / 5) = log(1) = 0
  점수 = tf x 0 = 0        tf 가 5든 999든 0 이다

  ScoringTest.everywhereMeansZero 가 그대로 assert 한다
    assertEquals(0.0, scorer.score(1, 10, 10), DELTA)
    assertEquals(0.0, scorer.score(999, 10, 10), DELTA)
    assertEquals(0.0, scorer.score(1, 1, 1), DELTA)
```

- Q: 그것이 왜 버그가 아닌가?\
  A: **모든 문서에 있는 말은 문서를 가르지 못하기** 때문이다.\
  순위는 "이 문서가 다른 문서보다 나은 이유"를 점수로 적는 일인데, 전부가 가진 항은 그 이유가 될 수 없다.\
  0 점은 "이 항이 순위에 아무 기여도 하지 않는다"는 정확한 표현이다.\
  실제로 `ScoringTest.commonTermContributesNothing` 이 그것을 못 박는다 — `search("회사 환불")` 과 `search("환불")` 의 순위도 점수도 같다.\
  즉 흔한 항 "회사"가 더한 값이 정확히 0 이다.

- Q: 그 성질의 부작용은?\
  A: **문서가 하나뿐인 색인에서는 모든 항의 점수가 0 이고 순위가 문서 번호 순으로 무너진다.**\
  `CrossCheckTest.singleDocumentCorpus` 가 그 경우를 그대로 적어둔다 — `assertEquals(0.0, got.get(0).score(), DELTA)`.\
  그리고 동점이 많아지므로 `SearchResult` 의 동점 규칙(문서 번호 오름차순)이 없으면 답이 하나로 안 정해진다.\
  **점수 0 이 흔하다는 성질이 정렬 계약을 필수로 만든다** — 두 사실이 붙어 있다.

- Q: 최선의 입력은 어떤 것인가?\
  A: **df 가 아주 작은 항을 묻는 질의**다.\
  t199(df 2)를 물으면 방문이 2 다. 전수 조사의 2,000 대비 1,000분의 1 이다.\
  그리고 AND 로 드문 항 둘을 묶으면 더 좋아진다 — `word(198) + " " + word(199)` 의 방문이 8 이다.\
  일반화하면 "**질의어를 전부 가진 문서가 전체의 극히 일부**"일 때 색인이 가장 크게 이긴다.\
  실제 검색이 대개 그런 모양이라 이 구조가 표준이 됐다.

> **가지치기(pruning)** — 답이 될 수 없는 후보 덩어리를 통째로 버려서 훑는 양을 줄이는 것.\
> 예: 역색인에서 `index.get("t199")` 를 보는 순간, t199 가 없는 문서 1,998개는 열어보지도 않고 버려진다.

> **TF-IDF** — `tf × log(N / df)`. 이 문서에서 많이 나올수록 높고, 모든 문서에 흔할수록 낮은 점수.\
> 예: `score(3, 2, 10) = 3 × log(10/2) ≈ 4.828313737302301` — `ScoringTest.tfIdfFormula` 가 이 값을 assert 한다.

- Q: 최선의 입력에서 방문 8 이 어떻게 나오는지 따라가 보라.\
  A: 드문 항 둘(t198, t199)을 AND 로 묻는 경우다. 짧은 것부터 병합하므로 시작부터 작다.

```text
질의 = "t198 t199" , 두 항 다 df 가 아주 작다

  1. 두 포스팅 리스트를 꺼낸다. SHORTEST_FIRST 라 짧은 쪽이 lists[0] 이다
  2. lists[0] 을 merged 로 옮긴다  -> 그 길이만큼 visitedDocs 가 오른다
  3. merged 와 lists[1] 을 한 번 훑기로 병합한다
       같으면 visitedDocs += 2, 다르면 += 1

  측정 결과 방문 8, 전수 조사는 같은 질의에 방문 2,000
  assertEquals(8, both) 로 못 박혀 있다

  포인트: 색인의 방문 수는 "문서가 몇 개냐" 가 아니라
          "그 말이 든 문서가 몇 개냐" 로 정해진다. 그것이 색인이 파는 것 전부다.
```

- Q: 이 최악·최선을 한 문장으로 요약하면?\
  A: **역색인의 비용은 말뭉치 크기가 아니라 답의 크기에 붙는다.**\
  답이 작으면 거의 공짜고, 답이 전부면 전수 조사와 같다.\
  그래서 "문서가 몇 개냐"로 성능을 예측하면 틀리고, "질의가 몇 건을 맞히느냐"로 예측해야 맞는다.

**더 생각할 것**

- "이 구조가 언제 지는가"는 **그 구조가 무엇에 걸었는지**를 뒤집어 읽으면 나온다.\
  색인은 "후보가 줄어든다"에 걸었으므로, 후보가 안 줄어드는 입력이 곧 최악이다.
- 그래서 실제 검색 엔진은 흔한 항을 다르게 다룬다 — 불용어로 아예 빼거나, 흔한 항의 포스팅을 나중에 보거나(WAND 류), 상위 k 개를 확정하면 나머지 병합을 중단한다.\
  이 박스는 그 최적화를 안 넣고, 대신 **왜 필요한지가 보이는 최악 입력**을 측정으로 남겼다.
- 측정이 이 최악을 잡아준다는 것이 중요하다.\
  `CrossCheckTest` 는 답만 보므로 "색인이 전수 조사와 똑같이 일했다"를 절대 못 본다.\
  **성능의 한계는 성능을 재는 테스트에만 보인다.**

#### 5. 구현 전략의 트레이드오프 — 답이 갈리는 선택과 비용만 갈리는 선택

- Q: `LinearScanEngine` 대 `InvertedIndexEngine` — 색인 크기, 넣기, 찾기는 각각 어떤가?\
  A: README 의 표 그대로다. 코드로 확인하면 이렇다.

| | 색인 | 넣기(index) | 찾기(search) | 근거가 되는 코드 |
|---|---|---|---|---|
| `LinearScanEngine` | 없다(원문만) | `documents.put` 한 줄 → O(1) | 전 문서 훑고 매번 재분석 → O(문서 수 × 문서 길이) | `documents` 는 `TreeMap<Integer,String>` 하나 |
| `InvertedIndexEngine` | 포스팅 37,348 + 위치 40,158 | 분석 + 항마다 `insertSorted` → O(문서의 항 수 × log df …) | 포스팅만 훑음 → O(관련 포스팅 수) | `index` 는 `Map<String, List<Posting>>` |

- Q: 전수 조사가 `termCount()` 조차 비싼 이유는?\
  A: 저장해 둔 것이 없어서 **물을 때마다 전부 다시 분석**하기 때문이다.

```java
// impl/LinearScanEngine.java
public int termCount() {
    Set<String> terms = new HashSet<>();
    for (String text : documents.values()) {
        terms.addAll(indexAnalyzer.analyze(text));
    }
    return terms.size();
}
```

  역색인은 같은 값을 `index.size()` 한 줄로 준다.\
  `naiveStoresNothing` 이 두 값이 같다는 것만 assert 하고 **시간은 재기만 하고 판정하지 않는다** — 기계마다 다르기 때문이다.\
  (README·테스트 어디에도 두 시간의 기댓값은 없다. 수치로 인용할 것이 없다.)

- Q: `TermFrequencyScorer` 대 `TfIdfScorer` — 안 쓰는 인자 둘이 없으면 무슨 일이 생기는가?\
  A: **흔한 말을 많이 가진 문서가 이긴다.**\
  `TermFrequencyScorer` 는 `documentFrequency` 와 `documentCount` 를 안 본다. 그래서 "모든 문서에 있는 말"도 똑같이 점수를 준다.\
  `ScoringTest.tfIdfFlipsTheOrder` 가 채점기만 갈아끼워 첫 줄이 바뀌는 것을 그대로 못 박는다.

```text
말뭉치 (불용어 제거를 끈 상태)
  문서0 : 회사 회사 회사 회사 회사 환불
  문서1 : 회사 환불 환불 환불
  문서2 : 회사 배송
  문서3 : 회사 포장
  문서4 : 회사 문의

질의 "회사 환불"

  단순 빈도 (TermFrequencyScorer)
    문서0 = tf(회사)5 + tf(환불)1 = 6.0      <- 1등
    문서1 = tf(회사)1 + tf(환불)3 = 4.0
    답 [0, 1]        assertEquals(6.0, ...) / assertEquals(4.0, ...)

  TF-IDF (TfIdfScorer)    N = 5, df(회사) = 5, df(환불) = 2
    회사의 몫 = tf x log(5/5) = 0            <- 다섯 문서에 다 있으니 0 점
    문서0 = 0 + 1 x log(5/2) = 0.9162907318741551
    문서1 = 0 + 3 x log(5/2) = 2.7488721956224653   <- 1등
    답 [1, 0]        assertEquals(2.7488721956224653, ...) / assertEquals(0.9162907318741551, ...)

  같은 색인, 같은 질의, 같은 병합. 채점기 한 줄이 첫 줄을 바꿨다.
```

- Q: 그래서 인자가 셋인 것인가?\
  A: 그렇다. `Scorer` 의 주석이 "인자가 셋인 이유가 이 박스의 절반"이라고 적어둔다.\
  `tf` 만 보면 "의", "그리고" 가 이긴다 — `stopwordsMatterForTermFrequency` 가 "그리고"를 다섯 번 쓴 문서가 1등이 되는 것을 실제로 assert 한다.\
  `df` 와 `N` 이 그것을 고친다.\
  그리고 불용어 제거는 **같은 문제의 다른 해법**이다 — 아예 색인에서 빼버리는 쪽.\
  둘 다 하면 "흔한 말이 순위를 지배하는" 문제를 두 겹으로 막는다.

- Q: `MergeOrder.SHORTEST_FIRST` 대 `QUERY_ORDER` 는 무엇이 갈리는가?\
  A: **답은 같고 일하는 양만 갈린다.** 측정값이 이렇다.

```text
MeasurementTest.shortestFirstDoesLessWork
질의 = 흔한 말 둘 + 드문 말 하나 (t000, t001, t199), 문서 2,000개

  짧은 것부터 (SHORTEST_FIRST)   비교   231   방문   233
  준 순서대로 (QUERY_ORDER)      비교   683   방문 1,082

  네 값 다 assertEquals 로 못 박혀 있다.
  그리고 답이 같다는 것도 같은 테스트가 assert 한다 (docIds(a) == docIds(b)).
```

- Q: 왜 짧은 것부터 하면 줄어드는가?\
  A: **중간 결과는 절대 커지지 않기** 때문이다.\
  교집합을 계속 하는 것이므로 `merged` 는 매 단계에서 줄거나 그대로다.\
  작은 것으로 시작하면 그 뒤의 모든 병합이 **작은 쪽 길이에 묶인다**.\
  흔한 말부터 시작하면 첫 병합에서 긴 리스트를 통째로 훑고, 그 일은 되돌릴 수 없다.

```java
// impl/InvertedIndexEngine.java
if (mergeOrder == MergeOrder.SHORTEST_FIRST) {
    lists.sort(Comparator.comparingInt(List::size));
}
```

```text
df(t000) 약 346, df(t001) 그 다음, df(t199) = 2 라고 하자

  QUERY_ORDER     [t000] x [t001]  -> 첫 병합부터 긴 것 둘을 통째로 훑는다
                  그 결과 x [t199] -> 결과가 작아진 것은 마지막에야다
                  누적 비교 683

  SHORTEST_FIRST  [t199] x [t000]  -> 길이 2 짜리로 시작한다
                  그 결과 x [t001] -> 이미 2 이하다
                  누적 비교 231

  답은 같다. 교집합은 순서와 무관하기 때문이다(결합법칙).
```

- Q: 이 중 **답이 갈리는 선택**과 **비용만 갈리는 선택**은 각각 무엇인가?\
  A: 답이 갈리는 선택 — **Scorer**(순위가 뒤집힌다), 그리고 **분석기**(0건이 되기도 한다).\
  비용만 갈리는 선택 — **MergeOrder**, 그리고 **엔진 선택 자체**(`LinearScanEngine` 대 `InvertedIndexEngine`).\
  후자 둘은 `CrossCheckTest` 가 "답이 같다"를 적극적으로 확인하는 대상이다.\
  실제로 `mergeOrderDoesNotChangeAnswers` 는 `QUERY_ORDER` 로도 전수 조사와 답이 같다는 것을 못 박는다.

- Q: 비용만 갈리는 것은 왜 무작위 대조로 절대 안 잡히는가?\
  A: 대조는 **답만 보기** 때문이다. 구조적으로 못 본다 — 운이 나빠서 못 잡는 게 아니다.\
  `CrossCheckTest` 가 보는 것은 결과 개수, 문서 번호 순서, 점수(델타), 상위 k 뿐이다.\
  `SHORTEST_FIRST` 와 `QUERY_ORDER` 는 그 넷이 전부 같다. 그래서 `QUERY_ORDER` 로 돌려도 초록불이다.\
  그 선택을 보려면 **일한 양을 세는 자**가 따로 있어야 하고, 그게 `SearchStats`(`comparisons`, `visitedDocs`)다.\
  12번 스킵 리스트의 "답이 맞는데 느린 구현", 23번 스플레이 트리의 "회전 수가 잡는다"와 같은 자리다.

> **대조 테스트(cross-check / differential testing)** — 쉬워서 믿을 수 있는 구현과 빠른 구현에 같은 입력을 넣고 답을 견주는 검증.\
> 예: `CrossCheckTest` 가 문서 2,000개에 질의 250개를 넣고 두 엔진의 순위와 점수를 비교한다.

> **자(measure)가 하나면 안 되는 이유** — 답을 보는 자와 일한 양을 보는 자는 서로를 대신하지 못한다.\
> 예: 병합 순서 선택은 답의 자에는 안 잡히고 비교 횟수의 자에만 잡힌다. 35번 할당자의 `freeBytes` 와 `largestFreeBlock` 도 같은 구도다.

- Q: 대조를 무너뜨릴 수 있는 유일한 경로가 있다고 했는데?\
  A: **점수를 더하는 순서**다.\
  병합 순서대로 더하면 값이 거의 같은데 `double` 오차가 다르게 쌓여 전수 조사와 마지막 자리에서 갈린다.\
  그러면 구현이 정답인데도 대조가 실패한다 — 이 박스의 주력 검증이 무너지는 유일한 길이다.\
  그래서 두 엔진 모두 `SearchEngine.distinctTerms` 가 준 **질의어 순서**로 더하도록 계약이 고정돼 있다.

```java
// impl/InvertedIndexEngine.java
// 병합 순서가 아니라 질의어 순서로 더한다. 그래야 전수 조사와 합이 비트까지 같다.
for (int i = 0; i < t; i++) {
    sum += scorer.score(termFrequency(terms.get(i), docId), documentFrequency[i], n);
}
```

- Q: 분석기 불일치는 왜 "답이 갈리는 선택"의 가장 나쁜 형태인가?\
  A: **예외도 경고도 없이 0건**이 나오기 때문이다.\
  색인은 멀쩡하고 문서도 거기 있는데 아무것도 안 나온다. 로그에도 안 남는다 — 질의는 성공했으니까.\
  `AnalyzerMismatchTest` 가 그 조용한 0건만 따로 본다.

```text
AnalyzerMismatchTest 가 못 박는 네 가지

  1. 색인만 소문자화     색인에 cat, 질의는 CAT   ->  search("CAT") = []
                          그런데 search("cat") 은 [0, 1] 이다. 색인은 멀쩡하다
  2. 질의만 소문자화     0번 문서는 CAT 으로 색인돼 영영 안 나온다
                          게다가 같은 말이 대소문자별로 다른 항이 되어 색인이 쓸데없이 커진다
  3. 불용어 불일치       색인만 the 를 지우면 search("the black") 이 통째로 0건
                          질의에 흔한 말 하나만 섞여도 답이 사라진다
  4. 전수 조사도 똑같다   linearScanFailsTheSameWay 가 두 엔진에 같은 일이 남을 확인한다
```

- Q: 그런 "조용한 갈림"을 막으려고 계약으로 못 박아 둔 것이 또 있는가?\
  A: 둘 있다. 둘 다 "답이 하나로 정해지게" 만드는 장치다.\
  하나 — `SearchResult` 의 정렬 규칙: 점수 내림차순, 동점이면 문서 번호 오름차순.\
  둘 — `SearchEngine.distinctTerms`: 질의어 중복을 걷어내되 **처음 나온 순서를 지킨다**.

```java
// impl/SearchResult.java
public int compareTo(SearchResult other) {
    int byScore = Double.compare(other.score, this.score);
    if (byScore != 0) {
        return byScore;
    }
    return Integer.compare(this.docId, other.docId);
}
```

```text
두 계약이 없으면 무슨 일이 생기나

  동점 규칙이 없으면
    TF-IDF 는 흔한 항에서 0 점이 많이 나와 동점이 흔하다
    동점끼리의 순서가 정렬 구현에 맡겨지면 같은 색인에 같은 질의를 넣어도 순서가 흔들린다
    -> 두 엔진의 답을 비교하는 이 박스의 주력 검증이 성립하지 않는다

  Double.compare 대신 빼서 int 로 자르면
    0.4 점 차이가 0 이 되어 동점으로 보인다
    ScoringTest.tinyDifferencesStillOrder 가 그것을 잡는다

  distinctTerms 의 순서 고정이 없으면
    점수를 더하는 순서가 달라져 double 오차가 다르게 쌓인다
    값이 거의 같은데 마지막 자리가 갈려 대조가 실패한다 (정답인데도)
```

**더 생각할 것**

- 트레이드오프를 볼 때 첫 질문은 늘 **"이 선택이 답을 바꾸는가, 비용만 바꾸는가"** 여야 한다.\
  답을 바꾸는 선택은 계약으로 고정하고 테스트로 못 박는다(Scorer, 분석기, 정렬 규칙).\
  비용만 바꾸는 선택은 측정으로 고른다(MergeOrder).
- 그리고 **각각에 맞는 테스트가 따로 있어야 한다**.\
  답에 대한 테스트로 비용을 지키려 하면 영영 못 지킨다 — 초록불이 아무 말도 안 해주기 때문이다.
- 제일 위험한 것은 **답을 바꾸는데 예외를 안 내는 선택**이다.\
  분석기 불일치가 그것이고, 그래서 이 박스가 그 경우만 보는 테스트 파일을 따로 뒀다.

#### 6. 이 구조의 한계가 다음 구조를 어떻게 부르는가 — 33-filesystem

- Q: 역색인이 못 하는 것 중 무엇이 다음 주제를 부르는가?\
  A: 역색인의 키 공간은 **평평하다**.\
  `Map<String, List<Posting>>` 은 층이 없다. "고양이"와 "검은" 사이에 상하 관계가 없고, 키 하나가 곧 답으로 가는 한 걸음이다.\
  그런데 현실의 이름에는 층이 있다 — `/a/b/f.txt` 는 `a` 안의 `b` 안의 `f.txt` 다.\
  그 층을 담으려면 **맵 안에 또 맵이 있는** 구조가 필요하고, 그것이 33번의 트리다.

- Q: 09번 트라이가 글자로 내려간 자리에서 33번은 무엇으로 내려가는가?\
  A: **경로 조각(이름)** 으로 내려간다.\
  `TreeFileSystem.lookup` 이 그 한 줄이다.

```java
// 33-filesystem/impl/TreeFileSystem.java
for (String part : Paths.split(path)) {
    if (!current.isDirectory()) {
        return null;        // 파일을 뚫고 더 내려갈 수는 없다
    }
    current = current.children().get(part);
    ...
}
```

```text
같은 모양의 세 구조

  09 트라이        c -> a -> t        한 걸음이 글자 하나. 알파벳이 유한하다
  33 파일 시스템   a -> b -> f.txt    한 걸음이 이름 하나. 이름의 가짓수가 무한하다
  32 역색인        "고양이" 한 번에   층이 없다. 한 걸음이 곧 끝이다

  09 와 33 은 "한 걸음씩 내려간다" 가 같고, 걸음의 단위와 자식 수의 상한이 다르다.
  32 는 걸음 자체가 하나뿐이다. 그래서 층을 표현할 방법이 없다.
```

- Q: 역색인의 "항 → 목록" 매핑과 파일시스템의 "이름 → 노드" 매핑은 무엇이 같은가?\
  A: 셋이 같다.\
  하나 — 둘 다 **문자열 키로 한 번에 찾는** 맵이다. 그래서 그 방향 질의가 싸다.\
  둘 — 둘 다 **키를 정규화해야 맞는다**. 역색인은 분석기가, 파일 시스템은 `Paths.normalize` 가 그 일을 한다.\
  셋 — 둘 다 **정규화가 색인 쪽과 질의 쪽에서 같아야 한다**. 어긋나면 조용히 못 찾는다.\
  32번의 분석기 불일치와 33번의 경로 규칙 불일치는 정확히 같은 사고다.\
  다만 33번에서는 두 구현이 `Paths` 를 **공유**해서 어긋날 수가 없고, 대신 `Paths` 자체가 틀리면 둘이 똑같이 틀린다(그래서 `PathsTest` 가 따로 있다).

- Q: 무엇이 다른가?\
  A: 둘이다.\
  하나 — **값의 종류**가 다르다. 역색인의 값은 문서 목록이라 다대다다(한 항이 여러 문서에, 한 문서가 여러 항에).\
  파일 시스템의 값은 노드 하나이고, 그 노드가 또 맵을 들고 있어 **재귀적**이다. 층이 여기서 나온다.\
  둘 — **키의 유일성 범위**가 다르다. 역색인의 키는 전역 유일이다.\
  파일 시스템의 이름은 **부모 안에서만** 유일하다. `/a/f.txt` 와 `/b/f.txt` 가 공존한다.\
  그래서 파일 시스템에서는 "이름"이 아니라 "경로"가 신원이고, 33번의 평면 맵 구현은 그 사실을 그대로 키로 삼은 것이다.

- Q: 하드 링크 때문에 트리가 아니게 된다는 것은 무슨 뜻인가?\
  A: 이름과 내용을 갈라놓으면(`Node` 에 이름, `Blob` 에 내용) 서로 다른 노드 둘이 **같은 `Blob` 을 가리킬 수 있다**.\
  트리의 정의는 "모든 자식의 부모가 하나"인데, 내용 쪽에서 보면 부모가 둘이 된다.\
  그 순간 "지운다"의 뜻이 바뀐다 — 이름 하나를 지우는 것이 내용을 지우는 것과 달라진다.\
  그래서 `Blob` 이 참조 수를 세고, 마지막 이름이 사라질 때만 내용이 죽는다.\
  이 이야기는 33번의 질문 6에서 본격적으로 다룬다.

- Q: 그럼 32번과 33번이 이어지는 큰 줄기는 무엇인가?\
  A: **"무엇을 키로 잡는가"가 무엇을 싸게 할 수 있는지를 정한다**는 한 문장이다.\
  32번은 방향을 뒤집어 "항"을 키로 잡았고, 그래서 항 질의가 싸고 문서 갱신이 비싸졌다.\
  33번은 "이름을 층층이"와 "경로 전체를 통째로" 중에 무엇을 키로 잡을지를 놓고 같은 질문을 다시 한다.\
  답은 둘 다 옳고, 갈리는 것은 **어떤 질문을 자주 하느냐**다.

> **정규화(normalization)** — 같은 뜻의 여러 표기를 하나의 표준 표기로 바꾸는 것. 색인 쪽과 조회 쪽이 똑같이 해야 뜻이 있다.\
> 예: 32번은 `"Black"` → `"black"`, 33번은 `"//a///b/"` → `"/a/b"`.

> **평평한 키 공간 대 중첩 키 공간** — 키 하나가 곧 답인 구조와, 키를 여러 조각으로 나눠 한 조각씩 내려가는 구조.\
> 예: `index.get("고양이")` 는 한 걸음이고, `/a/b/f.txt` 는 `a`, `b`, `f.txt` 세 걸음이다.

**더 생각할 것**

- 32 → 33 → 34 → 35 의 흐름을 한 줄로 이으면 이렇다.\
  32 "무엇이 어디 있는가" → 33 "그것들을 어떻게 이름 붙여 담는가" → 34 "무엇을 먼저 할 것인가" → 35 "어디에 놓을 것인가".
- 세 박스가 공통으로 쓰는 검증 설계가 있다 — **쉬워서 믿을 수 있는 기준선 하나를 따로 만들어 대조한다**.\
  32번은 `LinearScanEngine`, 33번은 `FlatPathFileSystem` 이 그 자리다.\
  34번에서는 그것이 **성립하지 않고**(답이 여럿이라) 성질 검사로 바뀐다 — 그 차이가 34번의 핵심이다.
- 그래서 "다음 구조를 부른다"는 말은 기능뿐 아니라 **검증 방법까지 부른다**는 뜻으로 읽는 것이 좋다.\
  이 문제집이 박스마다 검증 파일을 하나씩 늘려가는 이유가 그것이다.
