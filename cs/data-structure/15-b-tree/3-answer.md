## 정답

### B. 자료구조 특성

#### 1. B-트리는 왜 필요한가 — 기준이 "비교 횟수"에서 "읽기 횟수"로 바뀐다

- Q: 06번 이진 탐색 트리로는 무엇이 안 되는가?\
  A: 이진 탐색 트리는 노드마다 갈림길이 **둘**뿐이라 높이가 `log2 n` 이다.\
  README 의 수치로, 100만 개면 높이 20이고 1억 개면 약 27이다.\
  메모리 안에서는 이것이 전혀 문제가 아니다 — 포인터 27번 따라가는 일이다.\
  그런데 트리가 디스크에 있으면 그 27번이 **디스크 읽기 27번**이 된다.\
  README 가 말하는 대로 디스크 읽기 한 번은 메모리 읽기의 수만 배라서, 27번이면 그게 전부다.\
  즉 BST 가 못 하는 것은 "탐색"이 아니라 "적은 횟수로 도달하기"다.

> **팬아웃(fanout)** — 노드 하나가 가진 자식의 최대 개수.\
> 예: 이진 탐색 트리는 2, B-트리는 노드 안 키 개수 + 1 이라 수십~수백이 된다.

> **디스크 블록(block)** — 디스크가 한 번에 읽고 쓰는 최소 덩어리(예: 4KB, 16KB).\
> 예: 1바이트만 필요해도 블록 하나가 통째로 온다 — 그래서 "한 번 읽을 때 많이 읽는" 것이 공짜에 가깝다.

- Q: "비교를 줄이자"가 "읽기 횟수를 줄이자"로 바뀌면 왜 노드가 뚱뚱해지는가?\
  A: 목적함수가 바뀌면 최적해가 바뀌기 때문이다.\
  비교 횟수를 줄이는 것이 목표면 한 번의 비교로 후보를 절반으로 줄이는 이진 분기가 이미 최선이다.\
  읽기 횟수를 줄이는 것이 목표면 줄여야 할 것은 **높이**이고, 높이는 `log_t n` 이므로 밑 t 를 키워야 한다.\
  t 를 키운다는 것은 노드 하나에 키를 더 많이 담는다는 뜻이다.\
  그리고 어차피 디스크는 블록 단위로 읽으니, 노드를 블록 하나 크기까지 키우는 것은 **추가 비용이 0** 이다.\
  키 하나를 담은 노드를 읽든 키 수백 개를 담은 노드를 읽든 디스크 읽기는 똑같이 한 번이다.\
  공짜인 방향으로 끝까지 밀면 노드가 뚱뚱해진다 — 그게 B-트리다.

  | | 이진 탐색 트리 | B-트리 (m=100) |
  |---|---|---|
  | 자식 수 | 2 | 최대 100 |
  | 1억 개의 높이 | 약 27 | 4 |
  | 어디에 사나 | 메모리 | 디스크 |

  (README 의 표 그대로다. `log_100(10^8) = 4` 로 계산이 맞는다.)

```text
같은 1억 건을 찾을 때 "디스크에 갔다 오는 횟수"

이진 탐색 트리 (팬아웃 2)                    B-트리 (팬아웃 100)

 root          <- 읽기 1                      root            <- 읽기 1
  |                                          / | ... \
 [ ]           <- 읽기 2                    [   100갈래   ]   <- 읽기 2
  |                                          / | ... \
 [ ]           <- 읽기 3                    [   100갈래   ]   <- 읽기 3
  |                                          / | ... \
 ...           ...                          [    잎      ]   <- 읽기 4
  |
 [ ]           <- 읽기 27                   끝.

 27번 x (디스크 1회)                         4번 x (디스크 1회)
```

- Q: 노드 안에서 키 99개를 훑는 비용이 사실상 공짜인 이유는?\
  A: 그 99개는 **이미 메모리에 올라와 있기** 때문이다.\
  디스크 읽기 한 번이 노드(=블록) 전체를 통째로 가져왔으므로, 그 안을 훑는 것은 메모리 접근이다.\
  메모리 접근은 디스크 접근의 수만 분의 1이라, 99번을 해도 디스크 읽기 한 번 앞에서는 반올림하면 0이다.\
  게다가 impl 은 노드 안을 선형으로 훑지도 않는다 — `lowerBound` 가 이분탐색이라 `log2(100) ≈ 7` 번 비교면 끝난다.\
  그래서 총비용은 `높이 O(log_t n) x 노드 안 O(log t)` = `O(log n)` 인데, **실제로 비싼 항은 앞쪽 하나뿐**이다.

`impl/BTree.java` — 노드 안 자리 찾기는 이분탐색이다

```java
    /** node.keys 에서 key 가 들어갈 자리. 같은 키가 있으면 그 자리. */
    int lowerBound(Node<K, V> node, K key) {
        int lo = 0;
        int hi = node.keys.size();
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (node.keys.get(mid).compareTo(key) < 0) {
                lo = mid + 1;
            } else {
                hi = mid;
            }
        }
        return lo;
    }
```

`impl/BTree.java` — get 은 "노드 안에서 자리를 잡고, 아니면 그 구간의 자식으로 한 층 내려간다"의 반복이다

```java
    @Override
    public V get(K key) {
        requireKey(key);
        Node<K, V> cur = root;
        while (true) {
            int i = lowerBound(cur, key);
            if (i < cur.keys.size() && cur.keys.get(i).compareTo(key) == 0) {
                return cur.values.get(i);
            }
            if (cur.leaf()) {
                return null;
            }
            cur = cur.children.get(i);
        }
    }
```

테스트가 이 성질을 숫자로 못박는다.\
`BPlusTreeStructureTest.wideIsShallow` — 차수 100 에 100만 개를 넣고 `height() <= 4` 를 확인한다.\
`SearchTreeContractTest.higherDegreeIsShallower` — 차수 64 로 2만 개를 넣고 `height() <= 4`, 그리고 최소 차수보다 낮은지를 확인한다.

**더 생각할 것**

- "비용 모델이 바뀌면 최적 자료구조가 바뀐다"가 이 챕터의 한 문장이다.\
  같은 데이터, 같은 연산인데 저장 매체가 달라졌다는 이유만으로 정답이 이진 트리에서 B-트리로 옮겨간다.
- 같은 논리가 한 층 더 올라가면 분산 시스템이 된다.\
  거기서는 "읽기 한 번"이 네트워크 왕복이고, 그래서 다시 "왕복 횟수를 줄이자"가 목적함수가 된다.
- SSD 는 탐색 시간이 거의 없지만 여전히 페이지 단위로 읽고 쓴다.\
  그래서 "블록에 맞춰 노드를 만든다"는 설계는 살아남았고, 대신 쓰기 증폭(같은 논리 쓰기 1회가 물리 쓰기 여러 번이 되는 현상)이 새 제약이 되었다. (원본에 근거 없음 — 내 추론)

#### 2. 위로 자라는 트리 — 균형이 결과가 아니라 구조다

- Q: B-트리가 뿌리에서 위로 자란다는 말은 구체적으로 무슨 뜻인가?\
  A: 트리의 **높이를 바꾸는 코드가 딱 한 군데**뿐이라는 뜻이다.\
  `put` 에서 뿌리가 꽉 찼을 때, 새 노드를 뿌리 위에 씌우고 옛 뿌리를 쪼갠다 — 여기서만 높이가 +1 이다.\
  그 밖의 모든 삽입은 잎에 키를 끼우거나 중간 노드를 쪼갤 뿐, 깊이를 건드리지 않는다.\
  삭제 쪽에서는 뿌리가 비었을 때 `root = root.children.get(0)` 로 한 층 벗겨내는 자리 하나뿐이다 — 여기서만 높이가 -1 이다.\
  BST 는 정반대다 — 새 노드를 잎에 매다는 것이 유일한 삽입 방식이라, 자라는 지점이 잎마다 흩어져 있다.

`impl/BTree.java` — 높이가 +1 되는 유일한 지점

```java
    @Override
    public V put(K key, V value) {
        requireKey(key);
        if (value == null) {
            throw new IllegalArgumentException("값은 null 일 수 없다");
        }
        if (root.keys.size() == maxKeys()) {
            Node<K, V> newRoot = new Node<>();
            newRoot.children.add(root);
            splitChild(newRoot, 0);
            root = newRoot;
        }
        return insertNonFull(root, key, value);
    }
```

`impl/BTree.java` — 높이가 -1 되는 유일한 지점

```java
    @Override
    public V remove(K key) {
        requireKey(key);
        if (get(key) == null) {
            return null;
        }
        V old = get(key);
        removeFrom(root, key);
        if (root.keys.isEmpty() && !root.leaf()) {
            root = root.children.get(0);
        }
        size--;
        return old;
    }
```

- Q: 왜 그 결과로 "모든 잎이 언제나 같은 깊이"가 되는가?\
  A: 높이를 바꾸는 조작이 **모든 잎에 동시에 똑같이 적용**되기 때문이다.\
  뿌리 위에 층을 하나 씌우면 뿌리 아래 있던 잎 전부가 한 칸씩 같이 깊어진다 — 어느 잎만 깊어지는 일이 없다.\
  반대로 뿌리를 벗겨내면 전부가 한 칸씩 같이 얕아진다.\
  잎과 잎의 상대적 깊이 차이를 만들 수 있는 연산 자체가 코드에 존재하지 않는다.\
  그래서 "균형이 깨진 상태"는 버그가 아니라 **도달 불가능한 상태**다.

```text
아래로 자라기(BST)                      위로 자라기(B-트리)

    (50)                                     [ 50 ]
      \                                      /     \
      (70)     <- 이 잎만 깊어진다       [ ... ]   [ ... ]   <- 잎들의 깊이 차이 0
         \
         (90)  <- 또 이 잎만                 뿌리가 꽉 차면 위에 한 층을 씌운다
            \
            (99)                             [ new root ]     <- 높이 +1
                                              /        \
  깊이가 잎마다 제각각 -> 최악 O(n)      [ 옛 뿌리 왼쪽 ] [ 옛 뿌리 오른쪽 ]
                                          |              |
                                        (모든 잎이 한 칸씩 "같이" 내려간다)
```

- Q: `height()` 가 왼쪽 자식만 따라 내려가며 세는 것이 왜 정당한가?\
  A: 모든 잎의 깊이가 같다는 성질이 코드로 굳어 있기 때문이다.\
  어느 한 경로의 길이가 곧 트리 전체의 높이라서 왼쪽 한 줄만 세면 된다.\
  BST 였다면 이렇게 쓸 수 없고 `1 + max(왼쪽 높이, 오른쪽 높이)` 로 전체를 훑어야 한다.\
  즉 이 4줄짜리 구현 자체가 "균형이 구조"라는 주장의 증거다.

`impl/BTree.java` — 왼쪽 한 줄만 세는 height

```java
    @Override
    public int height() {
        int h = 1;
        Node<K, V> cur = root;
        while (!cur.leaf()) {
            cur = cur.children.get(0);
            h++;
        }
        return h;
    }
```

- Q: 이것이 12번(확률)·16번(회전)의 균형과 어떻게 다른가?\
  A: 균형을 **보장하는 방식의 종류**가 다르다.\
  12번 스킵 리스트는 층을 동전으로 정하므로 균형이 **확률적 기댓값**이다 — 운이 아주 나쁘면 실제로 삐뚤어진 구조가 만들어질 수 있고, 다만 그럴 확률이 아주 낮을 뿐이다.\
  16번 레드블랙 트리는 삽입이 불변식을 **일단 깨뜨린 뒤** 회전과 색칠로 복구한다 — 균형은 "고쳐진 결과"다.\
  B-트리는 깨질 수가 없다 — 깊이는 개별 경로의 속성이 아니라 트리 전체의 속성이라 어긋날 자유도 자체가 없다.\
  표로 보면 이렇다.

  | | 12번 스킵 리스트 | 16번 레드블랙 | 15번 B-트리 |
  |---|---|---|---|
  | 균형의 근거 | 확률(동전) | 불변식 + 복구(회전·색칠) | 구조(위로만 자람) |
  | 보장의 성격 | 높은 확률로 | 최악에도 (h ≤ 2 log2(n+1)) | 항상, 정의상 |
  | 깨진 상태가 존재하나 | 존재 가능(운 나쁨) | 존재하지만 즉시 복구 | 존재 불가 |
  | 복구 코드 | 없음 | 회전·리컬러 | 없음(쪼개기는 복구가 아니라 자라기) |

> **불변식(invariant)** — 연산 전후로 언제나 참이어야 하는 성질.\
> 예: B-트리의 "뿌리가 아닌 노드는 키를 t-1 개 이상 2t-1 개 이하로 갖는다", "모든 잎이 같은 깊이다".

- Q: "균형이 결과가 아니라 구조"라는 말의 뜻은?\
  A: 균형을 **감지해서 고치는 코드가 없다**는 뜻이다.\
  레드블랙은 "지금 규칙이 깨졌나?"를 매 삽입 뒤에 판정하고 맞는 회전을 고른다 — 균형은 그 판정과 복구의 **결과**다.\
  B-트리에는 그런 판정이 없다 — 쪼개기는 "노드가 꽉 찼다"는 지역적 사정에만 반응할 뿐 트리 모양을 보지 않는다.\
  균형은 알고리즘이 지켜주는 것이 아니라, 자라는 방향이 하나뿐이라는 **구조에서 자동으로 따라 나오는 것**이다.\
  테스트 `sortedInsertStaysBalanced` 가 이것을 보여준다 — 1만 개를 오름차순으로, 또 1만 개를 내림차순으로 넣어도 높이 차가 1 이하이고 둘 다 30층 미만이다(BST 였다면 1만 층).

**더 생각할 것**

- "고쳐서 지키는 불변식"과 "깨질 수 없게 만든 불변식"은 유지보수 비용이 전혀 다르다.\
  전자는 새 연산을 추가할 때마다 복구 경로를 다시 증명해야 하고, 후자는 그럴 필요가 없다.
- 그 대신 B-트리는 "노드 하나가 가변 길이 배열"이라는 복잡도를 떠안았다.\
  공짜로 얻은 것이 아니라 복잡도를 다른 자리로 옮긴 것이다 — 10번에서 그 대가가 드러난다.
- 설계에서 일반화하면, 잘못된 상태를 **표현할 수 없게** 만드는 쪽이 잘못된 상태를 **검사해서 막는** 쪽보다 언제나 싸다.\
  타입으로 불가능한 값을 없애는 것과 같은 발상이다.

#### 3. 미리 쪼개고 미리 채우기 — 되돌아가지 않기, 그리고 쪼갠 직후의 함정

- Q: 넣기가 "내려가면서 미리 쪼개는" 이유는?\
  A: 부모가 항상 여유를 갖도록 미리 만들어 두기 위해서다.\
  쪼개기는 가운데 키 하나를 **부모로 올려보내는** 연산이라, 부모가 꽉 차 있으면 부모도 쪼개야 하고 그러면 위로 연쇄된다.\
  그런데 내려오는 길에 꽉 찬 노드를 전부 미리 쪼개 두었다면, 내가 지금 서 있는 노드는 반드시 여유가 있다.\
  그래서 자식을 쪼개 키 하나를 받는 일이 **절대 실패하지 않는다** — 연쇄가 원천 차단된다.\
  결과적으로 `put` 은 뿌리에서 잎까지 딱 한 번 내려가는 것으로 끝난다.

> **미리 쪼개기(preemptive split)** — 아직 넘치지 않았어도, 내려가는 길에 "꽉 찬" 노드를 만나면 지나가기 전에 먼저 쪼개 두는 방식.\
> 예: 키 2t-1 개짜리 자식을 만나면 거기 들어갈지 여부와 무관하게 먼저 쪼갠다.

> **승격(promote)** — 쪼갤 때 가운데 키가 부모 노드로 올라가는 것.\
> 예: `[30 40 50]` 을 쪼개면 40 이 부모로 올라가고 `[30]` 과 `[50]` 이 남는다.

- Q: 지우기가 "내려가기 전에 미리 채우는" 이유는?\
  A: 정확히 같은 논리의 거울상이다.\
  삭제는 노드에서 키 하나를 **빼는** 연산이라, 대상 노드가 최소치(t-1)뿐이면 규칙을 어기게 되고 그러면 부모에서 다시 고쳐야 한다 — 위로 연쇄된다.\
  그래서 내려가기 전에 "내려갈 자식이 t-1 개뿐이면" 먼저 형제에게 빌리거나 형제와 합쳐서 t 개 이상으로 만들어 둔다.\
  그러면 그 자식에서 키 하나를 빼도 여전히 t-1 개 이상이라 문제가 없다.\
  넣기의 "부모에 자리를 만들어 두기"와 지우기의 "자식에 여유를 만들어 두기"가 같은 발상이다.

> **underfull(부족)** — 키가 최소치(t-1)뿐이라 하나만 빠져도 불변식을 어기는 상태.\
> 예: t=2 인 트리에서 키가 1개뿐인 비-뿌리 노드.

- Q: 디스크를 전제하면 왜 되돌아가지 않는 것이 그렇게 중요한가?\
  A: 되돌아가기가 곧 **다시 읽기**이기 때문이다.\
  메모리라면 부모 참조를 스택에 들고 있다가 되돌아오는 것이 공짜지만, 디스크에서는 그 부모 블록을 버퍼에 계속 붙잡고 있거나 다시 읽어야 한다.\
  높이 4짜리 트리에서 왕복하면 읽기 4번이 최악 8번이 된다 — 1번 아끼려고 만든 구조에서 2배는 치명적이다.\
  또 내려가는 길에 끝낸다는 것은 그 노드를 **수정해서 바로 쓰고 놓아줄 수 있다**는 뜻이라, 버퍼 관리와 락 관리가 단순해진다.\
  실제 DB 는 여기서 한 발 더 나아가 "자식이 안전하면 부모 래치를 바로 푼다"는 최적화를 쓰는데, 그것이 성립하는 전제가 바로 이 미리 쪼개기다. (원본에 근거 없음 — 일반적으로 알려진 기법)

> **래치 커플링(latch coupling)** — 트리를 내려갈 때 자식 잠금을 잡은 뒤 부모 잠금을 바로 푸는 방식.\
> 예: 자식이 꽉 차 있지 않아 "위로 번질 일이 없다"고 확신할 수 있으면 부모를 즉시 놓아준다.

- Q: 쪼갠 바로 다음에 있는 함정은 무엇인가?\
  A: **쪼개고 나면 내가 방금 계산한 자식 인덱스 `i` 가 더 이상 맞지 않는다**는 것이다.\
  `splitChild(node, i)` 는 가운데 키를 `node.keys[i]` 자리에 끼워 넣고 새 오른쪽 노드를 `node.children[i+1]` 에 끼운다.\
  그래서 쪼개기 전의 "children[i] 로 내려간다"는 판단이 무효가 된다 — 찾는 키가 올라온 가운데 키보다 크면 이제 `children[i+1]` 로 가야 한다.\
  게다가 올라온 가운데 키가 **찾던 키 그 자체**일 수도 있다 — 그러면 더 내려갈 것도 없이 그 자리에서 값을 갱신하고 끝내야 한다.\
  impl 은 쪼갠 직후 `node.keys.get(i)` 와 다시 비교해서 이 세 갈래를 가른다.\
  README 가 "놓치면 48개 중 8개가 무너진다"고 경고한 지점이다.

`impl/BTree.java` — 쪼개기가 부모의 i 자리에 키를, i+1 자리에 새 자식을 끼운다

```java
    /** parent.children[i] 가 꽉 찼을 때 반으로 쪼개고 가운데 키를 부모로 올린다. */
    private void splitChild(Node<K, V> parent, int i) {
        Node<K, V> full = parent.children.get(i);
        int t = minDegree;
        Node<K, V> right = new Node<>();

        K midKey = full.keys.get(t - 1);
        V midValue = full.values.get(t - 1);

        for (int j = t; j < full.keys.size(); j++) {
            right.keys.add(full.keys.get(j));
            right.values.add(full.values.get(j));
        }
        if (!full.leaf()) {
            for (int j = t; j < full.children.size(); j++) {
                right.children.add(full.children.get(j));
            }
            full.children.subList(t, full.children.size()).clear();
        }
        full.keys.subList(t - 1, full.keys.size()).clear();
        full.values.subList(t - 1, full.values.size()).clear();

        parent.keys.add(i, midKey);
        parent.values.add(i, midValue);
        parent.children.add(i + 1, right);
    }
```

- Q: 이 함정은 왜 "쪼개기를 안 하는 구현"에서는 안 나타나는가?\
  A: 그 구현은 인덱스를 계산한 직후에 바로 그 자식으로 내려가기 때문이다.\
  계산과 사용 사이에 트리를 바꾸는 연산이 끼어들지 않으므로 인덱스가 낡을 틈이 없다.\
  미리 쪼개기는 "계산 → 구조 변경 → 사용"이라는 순서를 만들었고, 그래서 중간의 구조 변경이 앞의 계산을 무효화한다.\
  이것은 B-트리 고유의 함정이 아니라, 반복문 안에서 컬렉션을 수정할 때 인덱스가 어긋나는 것과 같은 종류의 버그다.

**더 생각할 것**

- "인덱스를 계산한 뒤 구조를 바꿨으면 인덱스를 다시 계산하라"는 규칙은 어디에나 적용된다.\
  리스트 순회 중 삭제, 배열 시프트 후의 포인터, DB 커서 중 갱신이 전부 같은 모양이다.
- 미리 쪼개기는 공짜가 아니다 — 지나가기만 하고 실제로는 안 들어갈 노드도 쪼갠다.\
  덕분에 노드 채움률이 떨어지지만, 디스크에서는 "읽기 횟수가 확정적"이라는 이득이 더 크다.
- 동시성까지 오면 이 선택이 더 중요해진다.\
  되돌아가는 구현은 경로 전체에 락을 잡아야 하고, 미리 하는 구현은 아래로 내려가며 락을 풀 수 있다. (원본에 근거 없음 — 내 추론)

#### 4. `fill` 이 인덱스를 돌려주는 이유 — 빌리기와 병합은 내려갈 자리가 다르다

- Q: `fill` 이 왜 인덱스를 돌려주는가?\
  A: **채우는 방법에 따라 내가 내려가려던 자식이 `children` 리스트의 다른 자리로 옮겨가기 때문**이다.\
  빌리기는 노드를 하나도 없애지 않으므로 `children` 의 길이도 순서도 그대로다 — 인덱스 `i` 가 여전히 맞는다.\
  병합은 자식 둘을 하나로 합치므로 `children.remove(i + 1)` 이 일어나고, 그 뒤 자식들이 한 칸씩 앞으로 당겨진다.\
  특히 내려가려던 자식이 **맨 오른쪽 자식**이면 오른쪽 형제가 없어서 `mergeChildren(node, i - 1)` 로 왼쪽과 합쳐야 하고, 그러면 합쳐진 노드는 `i - 1` 자리에 있다.\
  호출자가 이 세 경우를 다시 판정하지 않아도 되게 하려고, `fill` 이 "이제 여기로 내려가라"를 값으로 돌려준다.

`impl/BTree.java` — fill 의 네 갈래와 각각의 반환값

```java
    /** children[i] 의 키가 모자라면 형제에게 빌리거나 병합한다. 내려갈 자식 인덱스를 준다. */
    private int fill(Node<K, V> node, int i) {
        if (i > 0 && node.children.get(i - 1).keys.size() >= minDegree) {
            borrowFromLeft(node, i);
            return i;
        }
        if (i < node.children.size() - 1 && node.children.get(i + 1).keys.size() >= minDegree) {
            borrowFromRight(node, i);
            return i;
        }
        if (i < node.children.size() - 1) {
            mergeChildren(node, i);
            return i;
        }
        mergeChildren(node, i - 1);
        return i - 1;
    }
```

`impl/BTree.java` — 호출자는 돌려받은 인덱스를 그대로 쓴다

- Q: `mergeChildren` 이 정확히 무엇을 하길래 인덱스가 밀리는가?\
  A: 부모의 키 하나를 **끌어내려** 왼쪽 자식 끝에 붙이고, 오른쪽 자식의 내용물을 전부 왼쪽에 이어붙인 뒤, 오른쪽 자식을 `children` 에서 제거한다.\
  그래서 부모는 키 1개와 자식 1개를 동시에 잃는다 — 키 k 개면 자식 k+1 개라는 불변식이 그대로 유지된다.\
  합쳐진 노드의 키 수는 `(t-1) + 1 + (t-1) = 2t-1` 로 **정확히 꽉 찬 상태**다 — 넘치지 않으니 그 자리에서 더 쪼갤 일이 없다.\
  `children.remove(i + 1)` 때문에 그 뒤 자식들이 한 칸씩 앞으로 당겨진다 — 이것이 인덱스가 밀리는 물리적 이유다.

`impl/BTree.java` — 병합

```java
    /** children[i] 와 children[i+1] 을 keys[i] 를 가운데 끼워 하나로 합친다. */
    private void mergeChildren(Node<K, V> node, int i) {
        Node<K, V> left = node.children.get(i);
        Node<K, V> right = node.children.get(i + 1);

        left.keys.add(node.keys.remove(i));
        left.values.add(node.values.remove(i));
        left.keys.addAll(right.keys);
        left.values.addAll(right.values);
        left.children.addAll(right.children);
        node.children.remove(i + 1);
    }
```

- Q: 빌리기와 병합 중 무엇을 먼저 시도하는 것이 맞고 그 이유는?\
  A: **빌리기를 먼저** 시도하는 것이 맞다 — impl 의 `fill` 도 왼쪽 빌리기 → 오른쪽 빌리기 → 병합 순서다.\
  첫째, 빌리기는 **지역적**이다 — 형제와 부모의 키 하나를 회전시킬 뿐 노드 개수를 바꾸지 않으므로 부모가 여위지 않고, 위로 번질 가능성이 0이다.\
  병합은 부모의 키를 하나 빼가므로 부모가 다시 부족해질 수 있고, 최악에는 뿌리까지 연쇄된다.\
  둘째, 병합은 **정보를 버린다** — 노드 하나를 없애므로 다음에 키가 들어오면 다시 쪼개야 한다.\
  셋째, 디스크 관점에서 빌리기는 노드 2~3개를 고쳐 쓰는 일이고 병합은 노드 하나를 해제하며 공간 관리까지 건드리는 더 무거운 일이다.\
  즉 "싸고 파급이 작은 수단을 먼저, 비싸고 파급이 큰 수단을 나중에"라는 일반 원칙의 한 사례다.

> **빌리기(borrow, 회전)** — 여유 있는 형제의 끝 키를 부모를 거쳐 부족한 쪽으로 한 칸 돌리는 것.\
> 예: 부모 키 40 이 왼쪽으로 내려오고 오른쪽 형제의 첫 키 50 이 부모로 올라간다 — 정렬 순서가 그대로 유지된다.

`impl/BTree.java` — 빌리기가 "회전"인 이유가 코드에 그대로 보인다

```java
    private void borrowFromRight(Node<K, V> node, int i) {
        Node<K, V> child = node.children.get(i);
        Node<K, V> right = node.children.get(i + 1);

        child.keys.add(node.keys.get(i));
        child.values.add(node.values.get(i));
        node.keys.set(i, right.keys.remove(0));
        node.values.set(i, right.values.remove(0));
        if (!right.leaf()) {
            child.children.add(right.children.remove(0));
        }
    }
```

- Q: 빌리기에서 `if (!left.leaf())` / `if (!right.leaf())` 로 자식 포인터까지 옮기는 이유는?\
  A: 내부 노드는 "키가 k 개면 자식이 k+1 개"라는 불변식을 지켜야 하기 때문이다.\
  키를 하나 받은 쪽은 자식도 하나 받아야 하고, 키를 하나 내준 쪽은 자식도 하나 내줘야 한다.\
  잎은 자식이 애초에 없으므로 이 작업을 건너뛴다 — 그래서 `leaf()` 검사가 붙는다.\
  이 한 줄을 빠뜨리면 트리는 겉보기에 잘 도는데 `BTreeStructureTest.check` 의 "키가 k개면 자식이 k+1개다" 단언에서 잡힌다.

**더 생각할 것**

- "메서드가 자신이 바꾼 상태에 대한 새 좌표를 돌려준다"는 것은 넓게 쓰이는 패턴이다.\
  `List.remove` 뒤의 인덱스, 편집기의 커서 위치 보정, DB 의 갱신된 row id 반환이 같은 모양이다.
- 대안은 `fill` 이 인덱스를 안 돌려주고 호출자가 다시 `lowerBound` 를 계산하는 것이다.\
  정확하기는 하지만 같은 비교를 두 번 하게 되고, 무엇보다 "왜 다시 계산해야 하는지"가 코드에 안 남는다.
- 규모가 커지면 병합을 아예 미루는 전략이 유리해진다.\
  실제 DB 는 "노드가 완전히 비었을 때만 회수"하거나 백그라운드 압축으로 미루는 쪽이 흔하다 — 6번의 진동 문제와 직결된다. (원본에 근거 없음 — 일반적으로 알려진 기법)

#### 5. 내부 노드의 키를 지우기 — 06번 BST 의 그 문제 + "데려올 쪽의 사정"

- Q: 내부 노드의 키를 지우는 것이 06번 BST 의 그 문제인 이유는?\
  A: 키를 빼면 **그 자리가 구멍이 되는데, 그 구멍은 좌우 부분트리를 나누는 경계**이기 때문이다.\
  BST 에서 자식이 둘인 노드를 지울 때, 그 노드를 그냥 없애면 자식 두 개를 어디에 붙일지 정할 수 없었다.\
  B-트리의 내부 노드도 똑같다 — `keys[i]` 는 `children[i]` 와 `children[i+1]` 사이의 경계라서, 그냥 빼면 자식 둘 사이에 경계가 없어진다.\
  해법도 같다 — **바로 이웃한 키를 데려와 그 자리를 대신 채운다**.\
  왼쪽 부분트리의 최대 키(선행자)나 오른쪽 부분트리의 최소 키(후속자)는 그 경계 역할을 그대로 할 수 있는 유일한 후보다.\
  그리고 그 키는 잎에 있으므로, 실제 삭제는 잎으로 미뤄진다 — 문제를 "쉬운 경우"로 환원하는 것까지 BST 와 같다.

> **선행자(predecessor) / 후속자(successor)** — 정렬 순서에서 어떤 키 바로 앞 / 바로 뒤의 키.\
> 예: `keys[i]` 의 선행자는 `children[i]` 부분트리에서 가장 오른쪽 끝까지 내려간 잎의 마지막 키다.

```text
내부 키 40 을 지우는 세 갈래 (t=2, 부족 = 키 1개)

[a] 왼쪽 자식이 여유 있다 (키 >= t) -> 선행자를 올린다
      +------+                          +------+
      |  40  |            ->            |  30  |   선행자 30 이 40 자리를 메운다
      +------+                          +------+
      /     \                           /     \
 [10 20 30] [50 60]                 [10 20]  [50 60]     실제 삭제는 잎의 30

[b] 왼쪽은 빠듯한데 오른쪽이 여유 있다 -> 후속자를 올린다
      +------+                          +------+
      |  40  |            ->            |  50  |   후속자 50 이 40 자리를 메운다
      +------+                          +------+
      /     \                           /     \
   [ 30 ]  [50 60]                   [ 30 ]  [ 60 ]      실제 삭제는 잎의 50

[c] 양쪽 다 빠듯하다 -> 둘을 합치고, 합쳐진 노드에서 다시 지운다
      +------+                          +------------+
      |  40  |            ->  merge     | 30  40  50 |   부모의 40 이 아래로 끌려 내려온다
      +------+                          +------------+
      /     \                                 |
   [ 30 ]  [ 50 ]                             v   여기서 40 을 지운다 -> [30 50]
                                     (부모의 키가 0개가 되면 root 를 한 층 벗긴다 -> 높이 -1)
```

`impl/BTree.java` — 세 갈래가 코드에 그대로 나뉘어 있다

```java
        if (here) {
            Node<K, V> left = node.children.get(i);
            Node<K, V> right = node.children.get(i + 1);
            if (left.keys.size() >= minDegree) {
                Node<K, V> pred = left;
                while (!pred.leaf()) {
                    pred = pred.children.get(pred.children.size() - 1);
                }
                K pk = pred.keys.get(pred.keys.size() - 1);
                V pv = pred.values.get(pred.values.size() - 1);
                node.keys.set(i, pk);
                node.values.set(i, pv);
                removeFrom(left, pk);
            } else if (right.keys.size() >= minDegree) {
                Node<K, V> succ = right;
                while (!succ.leaf()) {
                    succ = succ.children.get(0);
                }
                K sk = succ.keys.get(0);
                V sv = succ.values.get(0);
                node.keys.set(i, sk);
                node.values.set(i, sv);
                removeFrom(right, sk);
            } else {
                mergeChildren(node, i);
                removeFrom(left, key);
            }
            return;
        }
```

- Q: 여기서 붙는 추가 조건("데려올 쪽의 사정")은 무엇인가?\
  A: **데려올 쪽 자식이 키를 t 개 이상 갖고 있어야 한다**는 조건이다 — `left.keys.size() >= minDegree`.\
  BST 에는 이런 조건이 없었다 — 노드가 키 하나짜리라 "빼도 되나?"를 물을 것이 없었다.\
  B-트리는 노드마다 키 개수 하한(t-1)이 있어서, 최소치뿐인 자식에서 선행자를 빼오면 그 자식이 즉시 부족해진다.\
  그래서 선행자를 데려오기 전에 "왼쪽 자식이 하나 내줘도 버티나?"를 먼저 묻는다.\
  못 버티면 오른쪽에게 같은 질문을 하고, 양쪽 다 못 버티면 포기하고 병합으로 간다.\
  요약하면 **"누구를 데려올까"가 아니라 "누가 내줄 여유가 있나"가 먼저**다.

- Q: 왜 `removeFrom(left, pk)` 로 다시 재귀하는가 — 선행자를 그 자리에서 빼면 안 되는가?\
  A: 선행자는 왼쪽 부분트리의 **맨 아래 오른쪽 끝 잎**에 있는데, 그 잎으로 가는 길목의 노드들이 부족할 수 있기 때문이다.\
  `left` 가 여유 있다는 것은 확인했지만 `left` 의 자손들은 확인하지 않았다.\
  그래서 직접 빼내지 않고 `removeFrom` 을 다시 부른다 — 그러면 내려가는 길에 `fill` 이 알아서 채워준다.\
  즉 "내려가면서 미리 채우기"라는 3번의 규율을 한 번 더 태우는 것이고, 특수 처리를 추가하는 대신 이미 맞다고 증명된 경로를 재사용하는 선택이다.

- Q: 병합으로 간 경우에는 왜 `removeFrom(left, key)` 로 원래 키를 그대로 넘기는가?\
  A: 병합이 부모의 `keys[i]`, 즉 **지우려던 키 자체를 아래로 끌어내렸기** 때문이다.\
  합쳐진 노드 `left` 는 `(t-1) + 1 + (t-1) = 2t-1` 개의 키를 갖고, 그 가운데 하나가 지우려던 키다.\
  그러니 대역 키를 찾을 필요 없이 원래 키를 그대로 지우면 된다 — 문제가 한 층 아래로 내려가면서 크기가 줄었다.\
  이것이 재귀가 끝난다는 보장이다 — 매 호출마다 깊이가 최소 1 내려가므로 잎에 닿으면 반드시 종료한다.

- Q: 테스트는 이 경우를 어떻게 잡는가?\
  A: `SearchTreeContractTest.removeFromInternal` 이 최소 차수로 100개를 넣은 뒤 짝수 키 50개를 지우고 남은 키가 정확히 홀수 50개인지 본다.\
  `BTreeStructureTest.heldDuringDelete` 는 차수 3에 400개를 넣고 무작위 순서로 전부 지우면서 **매 삭제마다** 불변식 전체(키 개수 하한·상한, 자식 개수, 정렬, 모든 잎 같은 깊이)를 확인한다.\
  `SearchTreeContractTest.matchesTreeMap` 은 `TreeMap` 과 나란히 돌리며 `put`/`remove`/`get` 의 반환값까지 대조한다.\
  내부 노드 삭제는 경우가 많아 "결과는 맞는데 구조가 깨진" 상태가 나오기 쉬운데, 계약 테스트만으로는 그것이 안 잡히므로 구조 테스트가 따로 있다.

**더 생각할 것**

- 06번 BST 의 "자식 둘인 노드 삭제"를 이해했다면 여기는 그 위에 조건 하나가 얹힌 것뿐이다.\
  자료구조를 순서대로 공부하는 이유가 이런 재사용이다.
- "여유가 있나 먼저 묻는다"는 패턴은 자원 할당 전반에 나온다.\
  커넥션 풀에서 빌려오기 전 잔량 확인, 예산 이관 전 잔액 확인이 같은 모양이다.
- 경우가 많은 메서드는 경우마다 테스트가 아니라 **불변식 하나**로 검사하는 편이 싸다.\
  `assertInvariants` 한 함수가 삭제의 모든 갈래를 한꺼번에 덮는 것이 그 예다.

#### 6. 어디에 맞고 어디에 안 맞는가 — 메모리에서의 낭비와 최악 패턴

- Q: 어떤 접근 패턴에 적합한가?\
  A: 데이터가 **메모리보다 커서 디스크에 있고**, 읽기 한 번의 비용이 지배적인 경우다.\
  키로 하나 찾기(점 조회)와 구간으로 훑기(범위 조회)가 둘 다 필요한 경우 — 정렬 순서를 유지하기 때문이다.\
  삽입 순서를 통제할 수 없는 경우 — 오름차순으로 들어와도 균형이 유지된다(`sortedInsertStaysBalanced`).\
  지연의 **상한**이 중요한 경우 — 높이가 확정적이라 "최악에 몇 번 읽는다"를 미리 말할 수 있다.\
  그래서 MySQL InnoDB·PostgreSQL·SQLite·MongoDB 의 인덱스와 NTFS·ext4·Btrfs 가 전부 이 구조다.

- Q: 언제 쓰면 안 되는가?\
  A: 키를 정확히 하나씩만 찾고 범위 질의가 전혀 없으면 해시가 낫다 — 해시는 O(1) 이고 B-트리는 O(log n) 이다.\
  쓰기가 압도적으로 많고 읽기가 드물면 LSM 계열이 낫다 — B-트리는 제자리 갱신이라 쓰기마다 페이지를 고쳐 써야 한다.\
  그리고 **전부 메모리 안에 있으면** B-트리를 쓸 이유 자체가 옅어진다 — 다음 질문이 그 이야기다.

- Q: 메모리 안에서만 도는 워크로드에 B-트리를 쓰면 무엇이 낭비인가?\
  A: 첫째, **존재 이유가 사라진다** — 노드를 크게 만든 유일한 이유가 디스크 읽기 횟수를 줄이는 것이었는데 그 비용이 없어졌다.\
  둘째, **빈 칸이 낭비다** — `splitChild` 를 보면 키 `2t-1` 개짜리를 쪼갠 뒤 양쪽이 각각 `t-1` 개를 갖는다.\
  즉 최악의 채움률이 약 절반이라, 노드 배열의 절반이 빌 수 있다.\
  셋째, **노드 안 배열 조작이 O(t) 다** — impl 의 `keys.add(i, key)` 는 리스트를 한 칸씩 미는 일이고, 키가 수백 개면 그 밀기가 실제 비용이 된다.\
  넷째, **자바 구현에서는 객체 오버헤드가 크다** — `Node` 하나가 `ArrayList` 3개를 들고 있고, 잎에서는 `children` 이 항상 빈 채로 할당된다.\
  다섯째, 메모리에서 의미 있는 단위는 블록(4KB)이 아니라 캐시 라인(보통 64바이트)이라 "블록에 맞춘 노드"라는 설계 전제가 성립하지 않는다. (캐시 라인 크기는 원본에 근거 없음 — 일반 지식)\
  그래서 메모리 안의 균형 트리는 노드를 최대한 작게 만드는 쪽으로 간다 — 16번 레드블랙 트리가 존재하는 이유다.

> **채움률(fill factor)** — 노드가 담을 수 있는 최대 키 수 대비 실제로 담고 있는 키 수의 비율.\
> 예: 쪼갠 직후 양쪽 노드는 `(t-1)/(2t-1)` 이라 절반 조금 아래다.

- Q: 최악의 사용 패턴을 만들어 보라 — 최소치 근처를 오가는 삽입/삭제 반복이면 총 비용이 어떻게 되나?\
  A: **B-트리에는 여유(hysteresis)가 없다**는 점을 찌르면 된다.\
  `splitChild` 가 `2t-1` 개를 쪼개면 양쪽이 각각 `t-1` 개 = **정확히 최소치**가 된다 — 다음 삭제 한 번에 바로 부족해진다.\
  `mergeChildren` 이 합치면 `(t-1)+1+(t-1) = 2t-1` 개 = **정확히 최대치**가 된다 — 다음 삽입 한 번에 바로 넘친다.\
  그래서 같은 자리에서 `put` 과 `remove` 를 번갈아 하면 쪼개기와 병합이 **연산마다** 왕복한다.\
  한 번의 쪼개기/병합은 노드 두세 개를 통째로 건드리는 O(t) 작업이고, 최악에는 뿌리까지 연쇄하므로 한 연산이 `O(t x log_t n)` 이 된다.\
  m 번 반복하면 총 `O(m x t x log_t n)` — 차수는 여전히 log 지만 **상수가 t 배로 부푼다**.\
  디스크라면 더 나쁘다 — 매 연산이 노드 2~3개를 다시 써야 하므로 논리 쓰기 1회가 물리 쓰기 여러 번이 되는 쓰기 증폭이 된다. (쓰기 증폭은 원본에 근거 없음 — 일반 지식)

> **여유(hysteresis)** — 늘리는 문턱과 줄이는 문턱을 일부러 벌려 두어 경계에서 왕복하지 않게 만드는 것.\
> 예: 01번 동적 배열은 확장은 꽉 찰 때, 축소는 1/4 이하일 때로 문턱을 떼어 놓아 이 왕복을 막았다.

```text
여유가 없어서 생기는 진동 (t = 2, maxKeys = 3, minKeys = 1)

  put               remove              put               remove
[1 2 3] --쪼갬--> [1] [3] --병합--> [1 2 3] --쪼갬--> [1] [3] --병합--> ...
 꽉 참    O(t)    최소치    O(t)      꽉 참    O(t)    최소치    O(t)
   ^                 ^                  ^                 ^
   |                 |                  |                 |
쪼갠 결과가 곧바로 "부족 직전"   병합 결과가 곧바로 "넘치기 직전"

01번 동적 배열과 비교
  동적 배열 : 확장 문턱 = 꽉 참, 축소 문턱 = 1/4   -> 사이에 여유가 있다 -> 상환 O(1)
  B-트리   : 쪼개기 결과 = t-1,  병합 문턱 = t-1   -> 여유가 0 -> 경계에서 매번 구조 변경
```

- Q: 그 최악 패턴이 실제 시스템에서 문제가 되면 무엇을 바꾸는가?\
  A: 구조를 바꾸는 것이 아니라 **문턱을 벌린다**.\
  병합을 즉시 하지 않고 노드가 완전히 빌 때까지 미루거나, 백그라운드로 모아서 압축하는 방식이다.\
  또는 쪼갤 때 반으로 가르지 않고 한쪽에 더 많이 남기는 비대칭 분할을 써서 다음 삽입에 여유를 준다.\
  01번에서 "1/2 이 아니라 1/4 에서 줄인다"로 스래싱을 막은 것과 정확히 같은 발상이다. (원본에 근거 없음 — 일반적으로 알려진 기법)

**더 생각할 것**

- "적합/부적합"은 자료구조의 성질이 아니라 **비용 모델과 워크로드 비율**의 문제다.\
  같은 B-트리가 디스크에서는 최선이고 메모리에서는 과설계다.
- 최악 패턴을 스스로 만들어보는 습관은 성능 회귀를 미리 잡는다.\
  "이 구조가 가장 싫어하는 입력은 무엇인가"를 한 번 묻는 것만으로 대개 드러난다.
- 진동 문제는 01번(배열 확장/축소), 15번(쪼개기/병합), 그리고 캐시 교체 정책까지 같은 얼굴로 반복된다.\
  해법도 늘 같다 — 문턱 사이에 여유를 둔다.

#### 7. B-트리와 B+트리의 교환 — 실무 인덱스가 전부 B+트리인 이유

- Q: 값의 위치에서 무엇이 갈리는가?\
  A: B-트리는 **모든 노드**가 키와 값을 함께 들고, B+트리는 **잎에만** 값이 있다.\
  impl 을 보면 그대로다 — `BTree.Node` 는 `keys`/`values`/`children` 세 리스트를 항상 나란히 유지한다.\
  `BPlusTree.Node` 도 같은 세 리스트를 갖지만 내부 노드에서는 `values` 가 빈 채로 남고, 테스트 `internalNodesHaveNoValues` 가 그것을 단언한다.\
  이 한 가지 선택에서 나머지 차이가 전부 따라 나온다.

- Q: 운 좋은 조회에서 무엇을 맞바꾸는가?\
  A: B-트리는 찾는 키가 뿌리에 있으면 **읽기 한 번으로 끝난다** — `internalNodesCarryValues` 가 뿌리의 키들을 `get` 으로 바로 꺼내 확인한다.\
  B+트리는 내부 노드에서 같은 키를 만나도 멈추지 않고 **항상 잎까지** 내려간다 — 값이 거기에만 있기 때문이다.\
  그래서 B+트리는 평균 읽기 횟수를 손해 본다.\
  대신 얻는 것은 **모든 조회의 비용이 똑같다**는 것이다 — 최선 1번 최악 4번이 아니라 언제나 4번이라, 응답 시간이 예측 가능해지고 p99 가 안정된다.

- Q: 범위 조회에서 무엇을 맞바꾸는가?\
  A: B+트리는 잎끼리 `next` 로 이어져 있어서 **시작 잎을 한 번만 찾고 옆으로 걷는다** — `O(log n + k)` 다.\
  B-트리는 값이 내부에도 있으므로 중위 순회를 해야 하고, "다음 키"를 찾으려면 위로 올라갔다 다시 내려와야 한다.\
  디스크에서는 이 차이가 더 벌어진다 — 잎 사슬 걷기는 대체로 순차 읽기가 되고, 트리 순회는 임의 읽기가 흩어진다. (순차/임의 읽기 대비는 원본에 근거 없음 — 일반 지식)\
  `doesNotScanWholeTree` 테스트가 차수 64에 30만 건을 넣고 폭 11짜리 범위 질의를 2만 번 돌려 20초 제한 안에 끝나는지 본다.

`impl/BPlusTree.java` — 범위 조회는 "한 번 내려가고 옆으로 걷기"다

```java
    /** from 이상 to 이하를 정렬 순서로. 잎 사슬을 따라 걷기만 하면 된다. */
    public List<K> keysInRange(K from, K to) {
        requireKey(from);
        requireKey(to);
        List<K> out = new ArrayList<>();
        if (from.compareTo(to) > 0) {
            return out;
        }
        Node<K, V> leaf = findLeaf(from);
        int i = lowerBound(leaf, from);
        while (leaf != null) {
            while (i < leaf.keys.size()) {
                K k = leaf.keys.get(i);
                if (k.compareTo(to) > 0) {
                    return out;
                }
                out.add(k);
                i++;
            }
            leaf = leaf.next;
            i = 0;
        }
        return out;
    }
```

`impl/BTree.java` — B-트리의 전체 순회는 자식과 자기 키를 번갈아 오가는 중위 순회다

```java
    private void collect(Node<K, V> node, List<K> out) {
        if (node.leaf()) {
            out.addAll(node.keys);
            return;
        }
        for (int i = 0; i < node.keys.size(); i++) {
            collect(node.children.get(i), out);
            out.add(node.keys.get(i));
        }
        collect(node.children.get(node.children.size() - 1), out);
    }
```

`impl/BPlusTree.java` — B+트리의 전체 순회는 첫 잎에서 사슬을 끝까지 따라가는 것뿐이다

```java
    @Override
    public List<K> keys() {
        List<K> out = new ArrayList<>(size);
        for (Node<K, V> leaf = firstLeaf(); leaf != null; leaf = leaf.next) {
            out.addAll(leaf.keys);
        }
        return out;
    }
```

- Q: 키 중복에서 무엇을 맞바꾸는가?\
  A: B-트리는 키가 트리 전체에서 딱 한 번 나온다 — `noDuplication` 테스트가 모든 노드의 키를 모아 정확히 200개인지 확인한다.\
  B+트리는 구분키가 잎에 한 번 더 있다 — `separatorsAreDuplicated` 가 잎만 훑어도 전부 나오는지 확인한다.\
  즉 B+트리는 **저장 공간을 조금 더 쓴다**.\
  대신 "모든 데이터는 잎에 있다"는 단순한 규칙을 얻고, 그 덕에 잎 사슬 하나로 전체 순회가 끝난다.\
  그리고 내부 노드에 값을 안 넣으므로 같은 블록에 키를 더 많이 담을 수 있어 실제로는 높이가 오히려 낮아진다. (원본에 명시 없음 — 일반적으로 알려진 이유)

  | | B-트리 | B+트리 |
  |---|---|---|
  | 값의 위치 | 모든 노드 | 잎에만 |
  | 운 좋은 조회 | 뿌리에서 바로 | 늘 잎까지 내려간다 |
  | 조회 비용의 분산 | 들쭉날쭉 | 항상 같다 |
  | 범위 조회 | 트리 순회 | 잎 사슬 걷기 O(log n + k) |
  | 키 중복 | 없다 | 구분키가 잎에 또 있다 |
  | 내부 노드의 정보 밀도 | 키+값 | 키만 (더 많이 담긴다) |
  | 쓰는 곳 | 파일 시스템 일부 | 거의 모든 DB 인덱스 |

- Q: 실무의 거의 모든 DB 인덱스가 B+트리인 이유는?\
  A: **실무의 질의가 점 조회보다 범위 조회 쪽에 압도적으로 쏠려 있기** 때문이다.\
  `WHERE age BETWEEN 20 AND 30`, `ORDER BY created_at`, `LIMIT/OFFSET` 페이지네이션이 전부 범위 조회다.\
  심지어 `WHERE id = ?` 만 있는 것처럼 보이는 워크로드도 풀스캔·인덱스 스캔·정렬이 섞이면 결국 잎을 순서대로 훑게 된다.\
  그러면 B+트리가 내준 것("운 좋은 조회 한 번")은 거의 발생하지 않는 이득이고, 얻은 것(범위 조회가 순차 걷기)은 매번 쓰는 이득이다.\
  교환의 양쪽을 **실제 질의 분포로 가중치를 매기면** 한쪽이 압도한다 — 그래서 선택이 갈리지 않는다.

**더 생각할 것**

- 트레이드오프의 승자는 구조의 성질이 아니라 **워크로드 분포**가 정한다.\
  같은 표를 놓고도 "범위 조회가 드문 시스템"이라면 결론이 달라진다.
- B+트리의 잎 사슬은 클러스터형 인덱스에서 테이블 자체의 물리적 순서가 되기도 한다.\
  그래서 기본 키를 무작위 UUID 로 잡으면 잎 삽입 위치가 흩어져 쪼개기가 폭증한다 — 6번의 최악 패턴과 이어진다. (원본에 근거 없음 — 일반적으로 알려진 사례)
- "값을 어디에 둘 것인가"는 저장 구조 설계의 거의 모든 곳에서 반복되는 질문이다.\
  인덱스에 값을 같이 담는 커버링 인덱스도 같은 축의 선택이다.

#### 8. `lowerBound` 와 `childIndex` — 부등호 하나와, 잎 분할이 내부 분할과 정반대인 이유

- Q: B+트리에서 `lowerBound` 를 `childIndex` 자리에 그대로 쓰면 왜 틀리는가?\
  A: 두 함수가 찾는 것이 다르기 때문이다.\
  `lowerBound` 는 `keys[mid] < key` 일 때만 오른쪽으로 가므로 "**key 이상**인 첫 자리"를 준다 — 같은 키를 만나면 그 자리에서 멈춘다.\
  `childIndex` 는 `keys[mid] <= key` 일 때 오른쪽으로 가므로 "**key 초과**인 첫 자리"를 준다 — 같은 키를 만나도 한 칸 더 간다.\
  B+트리의 구분키는 `왼쪽 자식 < s <= 오른쪽 자식` 이라는 규약이라, **구분키와 같은 키는 오른쪽 자식이 맡는다**.\
  `lowerBound` 를 쓰면 구분키와 같은 키가 왼쪽 자식으로 내려가는데, 그 키는 거기 없다 — `get` 이 조용히 `null` 을 돌려준다.\
  README 가 "쓰면 9개가 무너진다"고 말한 자리다.

`impl/BPlusTree.java` — 두 함수의 차이는 부등호 하나뿐이다

```java
    /** keys 에서 key 이상인 첫 자리. */
    static <K extends Comparable<K>, V> int lowerBound(Node<K, V> node, K key) {
        int lo = 0;
        int hi = node.keys.size();
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (node.keys.get(mid).compareTo(key) < 0) {
                lo = mid + 1;
            } else {
                hi = mid;
            }
        }
        return lo;
    }

    /** 내부 노드에서 key 를 찾아 내려갈 자식의 인덱스. */
    static <K extends Comparable<K>, V> int childIndex(Node<K, V> node, K key) {
        int lo = 0;
        int hi = node.keys.size();
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            if (node.keys.get(mid).compareTo(key) <= 0) {
                lo = mid + 1;
            } else {
                hi = mid;
            }
        }
        return lo;
    }
```

```text
get(70) : 구분키 70 과 "같은 키" 를 찾을 때 두 함수가 갈린다

                         +------+
                         |  70  |          구분키 s = 70
                         +------+
                         /      \
                 children[0]   children[1]
                    70 미만       70 이상
                      |             |
                 [ 50  60 ]     [ 70  80 ]     <- 70 은 오른쪽 잎에만 있다

  childIndex(node, 70) : keys[0]=70 <= 70  -> lo = 1   -> children[1] -> [70 80] 에서 발견 (정답)
  lowerBound(node, 70) : keys[0]=70 <  70 아님 -> hi = 0 -> children[0] -> [50 60] 에서 못 찾음
                                                                          -> get(70) == null

  조용히 틀린다. 예외도 안 나고, 다른 키들은 전부 멀쩡하다.
  "구분키와 정확히 같은 값"만 사라지므로 작은 테스트로는 잘 안 걸린다.
```

> **구분키(separator)** — B+트리 내부 노드의 키. 답이 아니라 "어느 쪽으로 갈지"만 알려주는 표지판.\
> 예: 구분키 70 은 "왼쪽은 70 미만, 오른쪽은 70 이상"을 뜻하며, 실제 70 의 값은 오른쪽 잎에 있다.

- Q: B-트리에는 왜 이 문제가 없는가?\
  A: B-트리에는 구분키라는 개념이 없고, 내부 노드의 키가 **그 자체로 답**이기 때문이다.\
  `BTree.get` 은 `lowerBound` 로 자리를 잡은 뒤 그 자리의 키가 찾는 키면 바로 값을 돌려준다 — 더 내려갈 이유가 없다.\
  같은 키를 만났을 때 "여기서 끝"이라는 동작이 정확히 `lowerBound` 의 의미와 맞아떨어진다.\
  B+트리는 같은 키를 만나도 "여기는 표지판일 뿐"이므로 지나가야 하고, 그래서 다른 부등호가 필요하다.\
  즉 부등호의 차이는 임의의 구현 취향이 아니라 **키가 답인가 길잡이인가**에서 나온다.

- Q: 잎 분할과 내부 분할이 정반대인 이유는 "값이 어디에 사는가"와 어떻게 연결되는가?\
  A: **모든 값은 잎에만 있으므로, 모든 키도 잎에 빠짐없이 남아 있어야 한다**는 제약에서 나온다.\
  잎을 쪼갤 때 올려보낼 키를 잎에서 빼버리면 그 키의 값이 트리에서 사라진다 — 그래서 **복사해서** 올린다(copy up).\
  `splitLeaf` 는 `right.keys.get(0)` 을 올려보내는데, 그 키는 `right` 에 그대로 남아 있다.\
  내부 노드의 키는 표지판일 뿐이라 여러 벌 있을 필요가 없다 — 그래서 **빼내서** 올린다(push up).\
  `splitInternal` 은 `keys[mid]` 를 올려보내면서 `subList(mid, ...).clear()` 로 아래에서 지운다.\
  요약하면 잎은 "데이터라서 남긴다", 내부는 "길잡이라서 한 곳에만 둔다"다.

> **copy up / push up** — 쪼갤 때 가운데 키를 복사해서 올리기(원본이 아래에 남는다) / 빼내서 올리기(아래에서 사라진다).\
> 예: 잎 분할은 copy up, 내부 분할은 push up 이다.

`impl/BPlusTree.java` — 잎 분할: 올려보낼 키가 오른쪽 잎에 그대로 남는다

```java
    private Split<K, V> splitLeaf(Node<K, V> node) {
        int mid = node.keys.size() / 2;
        Node<K, V> right = new Node<>(true);
        right.keys.addAll(node.keys.subList(mid, node.keys.size()));
        right.values.addAll(node.values.subList(mid, node.values.size()));
        node.keys.subList(mid, node.keys.size()).clear();
        node.values.subList(mid, node.values.size()).clear();
        right.next = node.next;
        node.next = right;
        return new Split<>(right.keys.get(0), right);
    }
```

`impl/BPlusTree.java` — 내부 분할: 올려보낼 키가 양쪽 어디에도 남지 않는다

```java
    private Split<K, V> splitInternal(Node<K, V> node) {
        int mid = node.keys.size() / 2;
        K up = node.keys.get(mid);
        Node<K, V> right = new Node<>(false);
        right.keys.addAll(node.keys.subList(mid + 1, node.keys.size()));
        right.children.addAll(node.children.subList(mid + 1, node.children.size()));
        node.keys.subList(mid, node.keys.size()).clear();
        node.children.subList(mid + 1, node.children.size()).clear();
        return new Split<>(up, right);
    }
```

- Q: 만약 잎 분할도 push up 으로 했다면 무엇이 깨지는가?\
  A: 올려보낸 키의 **값이 트리에서 사라진다**.\
  내부 노드에는 `values` 가 없으므로, 잎에서 뺀 키를 내부에 올려두면 그 키의 값은 어디에도 저장되지 않는다.\
  `get(50)` 은 잎까지 내려가서 50을 못 찾고 `null` 을 돌려준다.\
  `keys()` 는 잎만 훑으므로 50이 목록에서 빠지고, `separatorsAreDuplicated` 가 개수 불일치로 잡는다.\
  즉 "값은 잎에만"이라는 한 문장이 잎 분할 방식을 강제한다.

**더 생각할 것**

- 부등호 하나 차이로 갈리는 버그는 타입도 예외도 못 잡는다.\
  이런 자리는 이름으로 구분하는 것이 최선이다 — impl 이 `lowerBound` 와 `childIndex` 를 따로 둔 이유다.
- 경계 조건 버그는 "정확히 경계값일 때"만 나타나므로 무작위 테스트에서 잘 안 걸린다.\
  구분키와 같은 값을 일부러 질의하는 테스트가 따로 있어야 한다.
- 같은 구조의 함정이 이분탐색 전반에 있다 — `lower_bound` 와 `upper_bound`, 범위의 열림/닫힘, `BETWEEN` 의 포함 여부가 전부 같은 얼굴이다.

#### 9. 잎 병합의 `next` 와 "구분키는 값이 아니라 길잡이"

- Q: 잎 병합에서 `next` 를 안 이어주면 왜 조회는 멀쩡한데 범위 조회만 조용히 틀리는가?\
  A: 잎에 도달하는 **길이 두 개**이기 때문이다.\
  `get` 은 `findLeaf` 로 **트리 경로**(`children`)를 타고 내려가고, `keys()`·`keysInRange` 는 **잎 사슬**(`next`)을 탄다.\
  병합은 `node.children.remove(i + 1)` 로 트리 경로 쪽은 반드시 고친다 — 안 고치면 즉시 구조가 깨져 다른 데서 터진다.\
  하지만 `left.next` 는 여전히 방금 떼어낸 `right` 를 가리킨다 — 이쪽을 안 고쳐도 트리 탐색은 아무 영향이 없다.\
  그래서 `get`·`containsKey`·`size` 는 전부 정상이고, 사슬을 걷는 연산만 틀린다.\
  두 길이 같은 잎 집합을 가리켜야 한다는 불변식이 조용히 깨진 것이다.

`impl/BPlusTree.java` — 병합에서 잎과 내부의 처리가 다르고, 잎 쪽에만 `next` 잇기가 있다

```java
    private void merge(Node<K, V> node, int i) {
        Node<K, V> left = node.children.get(i);
        Node<K, V> right = node.children.get(i + 1);
        if (left.leaf) {
            left.keys.addAll(right.keys);
            left.values.addAll(right.values);
            left.next = right.next;
            node.keys.remove(i);
        } else {
            left.keys.add(node.keys.remove(i));
            left.keys.addAll(right.keys);
            left.children.addAll(right.children);
        }
        node.children.remove(i + 1);
    }
```

```text
잎 병합에서 next 를 고치는 경우와 안 고치는 경우

before (L 과 R 을 합치려 한다. R 뒤에는 X 가 있다)

  부모:  children = [ ... , L , R , X , ... ]
  사슬:  ... -> L -> R -> X -> ...

after (제대로)                            after (left.next = right.next 를 빠뜨림)

  부모:  [ ... , L(=L+R) , X , ... ]        부모:  [ ... , L(=L+R) , X , ... ]
  사슬:  ... -> L(=L+R) -> X -> ...         사슬:  ... -> L(=L+R) -> R -> X -> ...
                                                                    ^
                                                          트리에서 떨어져 나간 유령 노드
                                                          (keys 가 그대로 남아 있다)

  get / containsKey / size      : 트리 경로만 타므로 양쪽 다 정상
  keys / keysInRange            : 사슬을 타므로 오른쪽은 R 의 키를 두 번 센다

  게다가 이 유령의 next 는 그 시점의 스냅샷이라, 이후 splitLeaf 가
  (right.next = node.next; node.next = right) 로 새 잎을 끼워 넣어도 유령은 그것을 모른다
  -> 시간이 지나면 중복만이 아니라 "새로 생긴 잎이 통째로 빠지는" 누락으로도 번진다
```

- Q: 이 버그가 왜 특히 찾기 나쁜가?\
  A: 증상이 **결과의 조용한 오류**이지 예외나 충돌이 아니기 때문이다.\
  단위 테스트가 `get` 위주면 전부 통과한다 — 실제로 `SearchTreeContractTest` 의 `put`/`get`/`remove` 계약은 멀쩡히 지나간다.\
  범위 조회도 작은 데이터에서는 병합이 일어나지 않아 안 드러난다 — 병합이 나오려면 충분히 지워야 한다.\
  운영에서는 "가끔 조회 결과가 빠진다"거나 "COUNT 가 안 맞는다"로 나타나는데, 원인이 삭제 코드의 한 줄이라 연결 짓기가 어렵다.\
  그래서 `chainSurvivesDeletion` 이 500개를 넣고 짝수 250개를 지운 뒤 **사슬로 걸은 개수 = `size()` = `keys()`** 세 가지를 한꺼번에 대조한다.

`src/test/java/com/datastructure/btree/BPlusTreeStructureTest.java` — 사슬을 직접 걷는 테스트

```java
        @Test
        @DisplayName("지운 뒤에도 사슬이 안 끊긴다")
        void chainSurvivesDeletion() {
            // 잎을 병합할 때 next 를 안 이어주면 여기서 뒷부분이 통째로 사라진다.
            BPlusTree<Integer, String> t = tree(4, 500);
            for (int i = 0; i < 500; i += 2) {
                t.remove(i);
            }
            List<Integer> walked = new ArrayList<>();
            for (BPlusTree.Node<Integer, String> leaf = t.firstLeaf(); leaf != null; leaf = leaf.next) {
                walked.addAll(leaf.keys);
            }
            assertEquals(250, walked.size(), "사슬로 걸은 것과 크기가 같아야 한다");
            assertEquals(t.size(), walked.size());
            assertEquals(t.keys(), walked);
        }
```

> **잎 사슬(leaf chain)** — 잎끼리 한 방향으로 이어 둔 연결 리스트.\
> 예: `firstLeaf()` 에서 `next` 를 끝까지 따라가면 전체 키가 정렬 순서로 나온다.

> **이중 표현(redundant representation)** — 같은 정보를 두 가지 경로로 들고 있는 구조.\
> 예: B+트리의 잎 집합은 트리 경로로도, `next` 사슬로도 도달할 수 있어서 둘을 항상 같이 갱신해야 한다.

- Q: "구분키는 값이 아니라 길잡이"라는 말이 지우기에서 무엇을 면제해 주는가?\
  A: **내부 노드에 남은 구분키를 고칠 의무를 면제해 준다**.\
  구분키 s 가 지켜야 하는 것은 "왼쪽 자식의 키는 전부 s 미만, 오른쪽 자식의 키는 전부 s 이상"뿐이다.\
  오른쪽 자식에서 키를 지워 최솟값이 s 보다 커져도 그 성질은 여전히 참이다 — s 는 그냥 조금 헐거운 경계가 될 뿐이다.\
  심지어 지워진 키 자체가 구분키로 남아 있어도 된다 — 그 표지판을 따라가면 여전히 올바른 잎에 도착하고, 거기서 "없다"는 답이 나온다.\
  그래서 `removeFrom` 은 잎에서 지우고 나면 내부 노드를 손대지 않는다.\
  이것이 5번(B-트리의 내부 키 삭제)이 통째로 사라지는 이유다 — B+트리에는 "내부 노드에서 키를 지우는 경우"라는 갈래가 아예 없다.

`impl/BPlusTree.java` — 구분키를 안 고치는 이유가 주석으로 코드에 남아 있다

```java
        int i = childIndex(node, key);
        Node<K, V> child = node.children.get(i);
        removeFrom(child, key);
        if (child.keys.size() < minKeys()) {
            fix(node, i);
        }
        // 구분키를 여기서 더 고칠 필요는 없다.
        // 구분키 s 는 "왼쪽은 s 미만, 오른쪽은 s 이상"만 지키면 되고,
        // 지우기로 오른쪽의 최솟값이 s 보다 커져도 그 성질은 그대로다.
        // (빌려오기와 병합에서는 고쳐야 한다. 키가 실제로 경계를 넘어가기 때문이다)
```

- Q: 그러면 빌리기와 병합에서는 왜 구분키를 고쳐야 하는가?\
  A: 그때는 키가 **실제로 경계를 넘어가기** 때문이다.\
  빌리기는 형제의 키를 내 쪽으로 옮기므로 "여기서부터 오른쪽"이라는 경계선 자체가 이동한다 — 그래서 `node.keys.set(...)` 으로 새 경계를 써 넣는다.\
  잎을 빌릴 때는 오른쪽 자식의 새 최솟값이 곧 새 구분키다 — `borrowFromLeft` 의 `node.keys.set(i - 1, child.keys.get(0))` 이 그것이다.\
  병합은 자식 둘이 하나가 되므로 그 사이의 경계가 필요 없어진다 — 잎 병합은 `node.keys.remove(i)` 로 구분키를 **그냥 버린다**.\
  반면 내부 병합은 `left.keys.add(node.keys.remove(i))` 로 구분키를 **아래로 끌어내린다** — 내부 노드의 키는 아래 어디에도 사본이 없어서 버리면 경계가 사라지기 때문이다.\
  8번의 copy up / push up 과 정확히 같은 대칭이다.

`impl/BPlusTree.java` — 빌리기에서 잎과 내부의 구분키 갱신이 다르다

```java
    private void borrowFromLeft(Node<K, V> node, int i) {
        Node<K, V> child = node.children.get(i);
        Node<K, V> left = node.children.get(i - 1);
        if (child.leaf) {
            child.keys.add(0, left.keys.remove(left.keys.size() - 1));
            child.values.add(0, left.values.remove(left.values.size() - 1));
            node.keys.set(i - 1, child.keys.get(0));
        } else {
            child.keys.add(0, node.keys.get(i - 1));
            child.children.add(0, left.children.remove(left.children.size() - 1));
            node.keys.set(i - 1, left.keys.remove(left.keys.size() - 1));
        }
    }
```

  | 상황 | 잎에서 | 내부에서 | 이유 |
  |---|---|---|---|
  | 쪼개기 | 복사해 올린다(copy up) | 빼서 올린다(push up) | 잎은 데이터, 내부는 길잡이 |
  | 병합 | 구분키를 버린다 | 구분키를 끌어내린다 | 잎에는 사본이 있고 내부에는 없다 |
  | 그냥 삭제 | 아무것도 안 한다 | (해당 없음) | 경계가 헐거워져도 규약은 유지된다 |
  | 빌리기 | 새 최솟값으로 갱신 | 형제의 끝 키로 갱신 | 키가 경계를 실제로 넘어갔다 |

**더 생각할 것**

- 같은 정보를 두 경로로 들고 있으면 둘을 항상 같이 고쳐야 한다.\
  DB 의 테이블과 보조 인덱스, 캐시와 원본, 역인덱스와 정인덱스가 전부 같은 위험을 갖는다.
- "한쪽만 고쳐도 대부분의 연산이 멀쩡하다"는 것이 이런 버그를 위험하게 만든다.\
  그래서 두 경로가 같은 것을 가리키는지 **직접 대조하는 테스트**가 필요하다 — `chainSurvivesDeletion` 이 그 모양이다.
- "정확해야 하는 것"과 "힌트여도 되는 것"을 구분하면 고칠 일이 크게 준다.\
  구분키를 힌트로 규정한 덕에 삭제 경로 전체가 단순해졌다 — 계약을 느슨하게 잡는 것이 최적화가 되는 사례다.

#### 10. 다음 구조 — 레드블랙 트리는 t=2 B-트리의 이진 흉내다

- Q: B-트리의 한계(메모리에서는 노드가 너무 크다)가 16번 레드블랙 트리를 어떻게 부르는가?\
  A: 6번에서 본 낭비가 전부 "노드가 가변 길이 배열"이라는 데서 나오기 때문이다.\
  메모리에서는 블록 읽기를 아낄 것이 없으니 t 를 키울 이유가 없다 — 그러면 t 를 최소인 **2** 로 내리는 것이 자연스럽다.\
  t=2 면 노드가 키를 1~3개 갖는 2-3-4 트리다.\
  그런데 키가 1~3개로 **변하는** 노드는 여전히 불편하다 — 배열 밀기, 경우 분기, 빈 칸 낭비가 그대로 남는다.\
  그래서 "키 1~3개짜리 노드"를 **키 1개짜리 이진 노드 여러 개 + 색 비트 1개**로 펼쳐서 표현한다.\
  노드가 고정 크기가 되고, 배열 조작이 사라지고, 코드가 단일 노드 타입으로 통일된다 — 그것이 레드블랙 트리다.

  | | B-트리(디스크) | 2-3-4 트리(t=2) | 레드블랙 트리 |
  |---|---|---|---|
  | 노드 하나의 키 | t-1 ~ 2t-1 (수백) | 1 ~ 3 | 항상 1 |
  | 노드 크기 | 가변(블록) | 가변 | 고정 |
  | 균형의 근거 | 위로 자람 | 위로 자람 | 색 불변식 + 회전 |
  | 높이 | log_t n | log2 n ~ log4 n | ≤ 2 log2(n+1) |
  | 왜 쓰나 | 디스크 읽기 횟수 | (개념적 중간 단계) | 메모리 안 균형 |

- Q: "레드블랙 트리는 t=2 짜리 B-트리를 이진 트리로 흉내낸 것"이라는 대응을 설명해 보라.\
  A: **빨간 간선은 "같은 B-트리 노드 안"을 뜻하고, 검은 간선만 진짜 B-트리 간선**이라고 읽으면 그대로 포개진다.\
  키 1개짜리 2-노드는 검은 노드 하나.\
  키 2개짜리 3-노드는 검은 노드 하나에 빨간 자식 하나 — 둘은 같은 노드다.\
  키 3개짜리 4-노드는 검은 노드 하나에 빨간 자식 둘.\
  "빨강이 연속될 수 없다"는 규칙은 "한 노드에 키가 4개 이상일 수 없다"와 같은 말이다.\
  "뿌리에서 잎까지 검은 노드 수가 모두 같다"는 규칙은 **"모든 잎의 깊이가 같다"와 같은 말**이다 — 검은 간선만 세면 B-트리의 높이이기 때문이다.\
  그래서 레드블랙의 색 불변식은 새로 발명한 규칙이 아니라, 2번에서 본 B-트리 구조를 이진 노드 위에 번역해 적은 것이다.

> **검정 높이(black height)** — 어떤 노드에서 잎까지 가는 경로에 있는 검은 노드의 개수.\
> 예: 모든 경로의 검정 높이가 같다는 규칙은 대응하는 B-트리에서 모든 잎의 깊이가 같다는 뜻이다.

```text

  [ a ]          2-노드   ->        (a)B

  [ a  b ]       3-노드   ->        (b)B

  빨강이 둘 연속되면 -> 한 노드에 키가 4개라는 뜻 -> 금지되는 이유가 이것이다
```

- Q: 그러면 16번의 "회전"은 B-트리의 무엇에 대응하는가?\
  A: **대응하는 것이 없다** — 정확히 말하면, B-트리에서는 공짜라서 연산으로 존재하지 않는 일이다.\
  B-트리 노드 안의 키들은 정렬된 배열이라 "셋 중 누가 가운데인가"가 이미 정해져 있다.\
  레드블랙은 그 셋을 이진 노드로 펼쳤기 때문에 **누가 위에 있느냐**라는 자유도가 생겼고, 같은 3-노드라도 모양이 두 가지, 같은 4-노드라도 여러 가지다.\
  회전은 그 모양을 정규형으로 맞추는 작업이다 — B-트리로 번역하면 "노드 안에서 키를 정렬해 둔다"에 해당한다.\
  그래서 회전이 어려워 보이는 것은 연산 자체가 복잡해서가 아니라, **원래 한 덩어리였던 것을 쪼개 놓은 표현의 대가**를 치르는 것이다.\
  이 대응이 보이면 회전 케이스 분류가 "2-3-4 노드의 모양 맞추기"로 읽힌다 — README 의 마지막 문장이 그 말이다.

- Q: 그 번역의 대가로 무엇을 내주는가?\
  A: **높이**다.\
  한 B-트리 노드가 최대 3개의 이진 노드로 펼쳐지므로 경로 길이가 최대 2배가 된다 — 그래서 레드블랙의 높이 상한이 `2 log2(n+1)` 이다.\
  디스크였다면 이것은 읽기 2배라 치명적이지만, 메모리에서는 포인터 하나 더 따라가는 일이라 싸다.\
  대신 얻는 것이 고정 크기 노드, 배열 밀기 없음, 노드당 O(1) 작업이다.\
  즉 같은 균형 개념을 **비용 모델에 맞춰 다시 인코딩한 것**이고, 15번과 16번은 경쟁 구조가 아니라 같은 아이디어의 두 구현이다.

**더 생각할 것**

- "같은 추상 구조를 매체에 맞게 다르게 인코딩한다"는 관점은 여기서만 쓰이지 않는다.\
  같은 관계 모델을 행 지향/열 지향으로 저장하는 것, 같은 그래프를 인접 리스트/행렬로 담는 것이 같은 종류의 선택이다.
- 두 구조를 따로 외우면 규칙이 두 벌이지만, 대응을 알면 한 벌이다.\
  16번을 공부할 때 "이 색 규칙은 B-트리의 무엇인가"를 매번 되물으면 암기량이 절반이 된다.
- 이 대응의 실용적 가치는 디버깅에서 크다.\
  레드블랙 트리가 이상하면 대응하는 2-3-4 트리를 그려보는 것이 가장 빠른 진단법이다. (원본에 근거 없음 — 내 추론)
