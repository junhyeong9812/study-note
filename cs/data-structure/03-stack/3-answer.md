### A. 문제

#### 1. 괄호 짝 맞추기 (`isBalanced`)

**접근 1 — 종류별 카운터로 세기** (가장 먼저 떠오르지만 순서를 못 본다)

```java
// 의사코드
int paren = 0, bracket = 0, brace = 0;
for (char c : input.toCharArray()) {
    if (c == '(') paren++;
    if (c == ')') { paren--; if (paren < 0) return false; }
    if (c == '[') bracket++;
    if (c == ']') { bracket--; if (bracket < 0) return false; }
    if (c == '{') brace++;
    if (c == '}') { brace--; if (brace < 0) return false; }
}
return paren == 0 && bracket == 0 && brace == 0;
```

```
입력 "([)]" 를 왼쪽부터 처리 — 카운터 3개만 들고 간다

  문자     paren   bracket   판정
  -----    -----   -------   --------------------------------
  '('        1        0      아직 괜찮다
  '['        1        1      아직 괜찮다
  ')'        0        1      paren >= 0 이라 통과시킨다
  ']'        0        0      bracket >= 0 이라 통과시킨다
  -----    -----   -------
  끝        0        0      -> return true   (틀렸다. 정답은 false)

왜 틀렸나 : 카운터는 "몇 개가 열려 있나"만 안다
            "지금 열려 있는 것 중 가장 최근 것이 무엇인가"를 모른다
            ')' 를 만난 순간 짝지어야 할 상대가 '[' 라는 사실을 볼 방법이 없다
```

- 논리: 여는 괄호에서 세고 닫는 괄호에서 뺀다.
- 논리: 중간에 음수가 되면 닫는 괄호가 먼저 온 것이므로 그 자리에서 거절한다.
- 논리: 끝났을 때 전부 0이면 개수는 맞는 것이다.
- 비용(왜): 문자를 한 번씩만 보고 카운터 3개만 쓴다 → 시간 O(n), 추가 공간 O(1).
- 한계: **개수만 맞추고 순서는 못 본다.**\
  `"([)]"` 를 통과시킨다.
- 한계: 테스트 `rejectsUnbalanced` 의 `assertFalse(isBalanced("([)]", ...), "짝은 맞지만 순서가 어긋난다")` 에서 바로 걸린다.
- 한계: 괄호 종류가 늘어날 때마다 카운터 변수를 하나씩 더 만들어야 해서 확장도 나쁘다.

> **LIFO(Last In First Out, 후입선출)** — 마지막에 넣은 것이 가장 먼저 나오는 규칙.\
> 예: 괄호에서는 "가장 최근에 열린 괄호가 가장 먼저 닫혀야 한다"가 곧 LIFO다.

> **중첩(nesting)** — 괄호 안에 괄호가 들어가 층을 이루는 구조.\
> 예: `"([])"` 는 `(` 안에 `[` 가 들어간 2층이고, `"([)]"` 는 층이 서로 엇갈려 중첩이 아니다.

**접근 2 — 짝지어진 쌍을 반복해서 지우기** (정답은 맞지만 느리다)

```java
// 의사코드
String s = input.replaceAll("[^()\\[\\]{}]", "");   // 괄호 아닌 문자 제거
while (true) {
    String next = s.replace("()", "").replace("[]", "").replace("{}", "");
    if (next.equals(s)) break;   // 더 이상 지울 것이 없다
    s = next;
}
return s.isEmpty();
```

```
입력 "(a[b])" -> 괄호만 남기면 "([])"

  1회차   ( [ ] )      "[]" 를 지운다
          +---+
           지움
          -> "()"

  2회차   ( )          "()" 를 지운다
          +---+
           지움
          -> ""

  3회차   ""           더 지울 것이 없다 -> 빈 문자열이므로 true


입력 "([)]"

  1회차   ( [ ) ]      붙어 있는 "()" "[]" "{}" 가 하나도 없다
                       -> 문자열이 그대로다 -> 루프 종료
          결과 "([)]" 는 비어 있지 않다 -> false   (정답)

왜 맞나  : 안쪽에서부터 짝이 사라지는 것이 곧 중첩 구조다
왜 느리나: 한 번 훑어서 쌍 하나만 지워질 수도 있다
           그러면 훑기(O(n)) x 지우는 횟수(최대 n/2) = O(n^2)
```

- 논리: 올바른 괄호열이면 반드시 "바로 붙어 있는 짝"이 하나 이상 있다.
- 논리: 그 짝을 지우면 남은 것도 올바른 괄호열이다.\
  그래서 계속 지우면 끝내 빈 문자열이 된다.
- 논리: `"([)]"` 는 붙어 있는 짝이 아예 없어서 첫 회차에서 멈춘다.
- 비용(왜): `replace` 한 번이 문자열 전체를 훑고 새 문자열을 만든다 → O(n).
- 비용(왜): `"((((...))))"` 처럼 깊게 중첩되면 한 회차에 안쪽 한 쌍씩만 사라진다 → 회차가 n/2 → **O(n^2)**.
- 비용(왜): 회차마다 새 문자열을 만드므로 추가 공간도 O(n).
- 한계: 20만 자짜리 입력이면 계산상 약 2 x 10^10 회 문자 비교라 사실상 끝나지 않는다.
- 한계: "왜 맞는가"가 스택보다 오히려 설명하기 어렵다.\
  실제로 하는 일은 스택과 같은데 비용만 더 든다.

**접근 3 — 스택에 여는 괄호를 쌓는다** (impl 의 정답)

```java
public static boolean isBalanced(String input, Stack<Character> buffer) {
    for (int i = 0; i < input.length(); i++) {
        char c = input.charAt(i);
        switch (c) {
            case '(':
            case '[':
            case '{':
                buffer.push(c);
                break;
            case ')':
                if (buffer.isEmpty() || buffer.pop() != '(') return false;
                break;
            case ']':
                if (buffer.isEmpty() || buffer.pop() != '[') return false;
                break;
            case '}':
                if (buffer.isEmpty() || buffer.pop() != '{') return false;
                break;
            default:
                break;   // 괄호가 아닌 문자는 무시한다
        }
    }
    return buffer.isEmpty();
}
```

```
입력 "(a[b])" 를 왼쪽부터 한 글자씩 소비한다 — 매 단계의 스택 전체를 그린다

 '(' -> push               'a' -> 괄호 아님, 무시      '[' -> push
   +-----+                   +-----+                    +-----+
   |  (  | <- top            |  (  | <- top             |  [  | <- top
   +-----+                   +-----+                    +-----+
                                                        |  (  |
                                                        +-----+

 'b' -> 무시                ']' -> pop = '[' 짝 맞음    ')' -> pop = '(' 짝 맞음
   +-----+                   +-----+                    +-----+
   |  [  | <- top            |  (  | <- top             |     |  (비었다)
   +-----+                   +-----+                    +-----+
   |  (  |
   +-----+

 끝났을 때 스택이 비었다 -> return true


입력 "([)]" — 순서가 어긋난 입력이 어디서 걸리는가

 '(' -> push               '[' -> push                 ')' -> pop = '[' 
   +-----+                   +-----+                    맞아야 할 짝은 '(' 인데
   |  (  | <- top            |  [  | <- top             꺼낸 것은 '[' 다
   +-----+                   +-----+                    -> 즉시 return false
                             |  (  |
                             +-----+

 핵심 : pop 이 돌려주는 것은 "가장 최근에 열린 괄호" 다
        ')' 가 짝지어야 할 상대는 언제나 그것 하나뿐이다
        카운터는 이 정보를 못 들고 있고, 스택은 구조 자체가 이 정보다


입력 "((" — 다 훑었는데 스택이 안 빈 경우

 '(' -> push               '(' -> push                 입력 끝
   +-----+                   +-----+                    스택에 '(' 두 개가 남았다
   |  (  | <- top            |  (  | <- top             = 열어놓고 안 닫은 괄호 2개
   +-----+                   +-----+                    -> return buffer.isEmpty() = false
                             |  (  |
                             +-----+


입력 ")(" — 닫는 것이 먼저 온 경우

 ')' -> 스택이 비어 있다
   +-----+                   buffer.isEmpty() 가 true -> 즉시 return false
   |     |                   "짝지을 여는 괄호가 아예 없다" 는 뜻이다
   +-----+                   (이 검사가 없으면 빈 스택 pop 이라 EmptyStackException 이 난다)
```

- 논리: 여는 괄호는 "아직 닫히지 않은 약속"이므로 쌓아둔다.
- 논리: 닫는 괄호를 만나면 짝지을 상대가 유일하게 정해진다 — **가장 최근에 열린 것**이다.
- 논리: 그 "가장 최근"을 꺼내주는 것이 스택의 `pop` 이므로, 문제의 규칙과 자료구조의 규칙이 그대로 겹친다.
- 논리: `buffer.isEmpty() ||` 를 앞에 둔 것은 단락 평가라 빈 스택에서 `pop` 이 호출되지 않는다.

> **단락 평가(short-circuit evaluation)** — `||` 의 앞이 참이면 뒤를 아예 실행하지 않는 것.\
> 예: `buffer.isEmpty() || buffer.pop() != '('` 에서 스택이 비었으면 `pop()` 이 실행되지 않아 예외가 안 난다.

- 논리: `default: break;` 덕에 괄호가 아닌 문자는 스택을 건드리지 않는다 — 테스트의 `"a(b[c]d)e"` 가 이것을 본다.
- 논리: 끝난 뒤 `isEmpty()` 를 확인하는 것은 "약속을 전부 지켰나"를 묻는 것이다.
- 비용(왜): 문자 하나당 push 최대 1회 + pop 최대 1회 → 전체 연산이 2n 이하 → **시간 O(n)**.
- 비용(왜): 스택 깊이는 중첩 깊이만큼이라 최악(`"((((..."`)에 n/2 → **추가 공간 O(n)**.
- 한계: 추가 공간이 O(1) 이 아니다 — 다만 중첩을 판정하려면 깊이 정보를 어떻게든 들고 있어야 하므로 피할 수 없다.
- 한계: 괄호 종류가 늘어나면 `switch` 가 길어진다.\
  실무라면 `Map<Character, Character> closeToOpen` 하나로 바꾼다 (원본에 근거 없음 — 내 추론).
- 한계: `buffer` 를 인자로 받으므로 호출자가 비어 있지 않은 스택을 넘기면 결과가 틀어진다.\
  2-summary 의 시그니처 설명에 "`buffer` 는 비어 있는 상태로 들어온다"가 전제로 적혀 있다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 종류별 카운터 | O(n) | O(1) | 괄호가 **한 종류**뿐이고 순서가 자명할 때 | 종류가 둘 이상일 때 — `"([)]"` 를 통과시킨다 |
| 2. 짝 반복 제거 | 최악 O(n^2) | O(n) | 입력이 아주 짧고 정규식으로 한 줄에 끝내고 싶을 때 | 입력이 길 때 · 깊게 중첩될 때 |
| 3. 스택 (impl) | O(n) | O(n) (중첩 깊이) | 기본값. 종류가 여럿이고 순서를 봐야 할 때 | 없음 — 이 문제의 정답 형태다 |

**데이터 규모가 커지면**

- 접근 2는 20만 자 입력에서 계산상 약 2 x 10^10 회 문자 비교라 먼저 무너진다.\
  접근 3은 같은 입력에서 약 4 x 10^5 회 연산이다.
- 접근 3도 **중첩 깊이**가 스택 깊이다.\
  `"((((...))))"` 가 100만 겹이면 스택에 100만 개가 쌓인다.
- `Stack<Character>` 는 `char` 가 아니라 `Character` 객체를 담는다.\
  100만 겹이면 박싱된 객체가 100만 개 생긴다 — 자바 `Character` 캐시는 0~127 범위라 `(`, `[`, `{` 는 캐시에 걸려 객체가 재사용된다.

> **박싱(boxing)** — `char`·`int` 같은 원시 값을 `Character`·`Integer` 객체로 감싸는 것.\
> 예: `Stack<Character>` 에 `'('` 를 넣으면 실제로는 `Character` 객체 참조가 들어간다.

- 입력이 파일이라 메모리에 다 못 올린다면 문자열 전체를 들고 있을 필요가 없다.\
  스트리밍으로 한 글자씩 읽으며 스택만 유지하면 된다 — 접근 3은 이 변형이 자연스럽고 접근 2는 불가능하다.
- 깊이 제한을 걸고 싶으면(악의적 입력 방어) 스택 크기가 임계치를 넘는 순간 거절한다.\
  파서·JSON 리더가 실제로 이렇게 한다 (원본에 근거 없음 — 내 추론).

**질문별 답**

- Q: 문제 1(괄호 짝 맞추기 — `isBalanced`)을 어떻게 푸는가.\
  A: 여는 괄호를 만나면 스택에 쌓고, 닫는 괄호를 만나면 스택에서 하나 꺼내 짝이 맞는지 본다.\
  짝이 안 맞거나 꺼낼 것이 없으면 그 자리에서 `false` 다.\
  괄호가 아닌 문자는 무시한다.\
  다 훑고 나서 스택이 비어 있으면 `true` 다.

- Q: `"([)]"` 처럼 짝은 맞는데 순서가 어긋난 입력을 스택이 어떻게 걸러내는가.\
  A: `)` 를 만난 시점에 스택의 맨 위가 `[` 이기 때문이다.\
  `pop()` 이 돌려주는 것은 "가장 최근에 열린 괄호"이고, 닫는 괄호가 짝지어야 할 상대는 그것 하나뿐이다.\
  꺼낸 `[` 가 `(` 가 아니므로 즉시 `false` 를 반환한다.\
  개수만 세는 풀이는 "가장 최근"이라는 정보를 안 들고 있어서 이것을 못 잡는다 — 스택은 그 정보를 자료구조로 들고 있는 것이다.

- Q: 다 훑은 뒤 스택이 비어 있지 않다는 것은 무슨 뜻인가.\
  A: 열어놓고 끝내 닫지 않은 괄호가 남아 있다는 뜻이다.\
  스택에 남은 개수가 곧 안 닫힌 괄호의 개수다.\
  `"(("` 가 그 예이고 `false` 가 된다.\
  반대로 "닫는 것이 먼저 온" 경우(`")("`)는 끝까지 갈 것도 없이 `buffer.isEmpty()` 검사에서 도중에 잡힌다 — 두 종류의 불일치가 서로 다른 지점에서 잡힌다.

#### 2. 후위 표기식 계산 (`evaluatePostfix`)

**접근 1 — 두 번 꺼낸 것을 순서대로 left, right 로 쓰기** (한 줄 차이로 틀리는 풀이)

```java
// 의사코드 — impl 과 두 줄만 다르다
int left = buffer.pop();     // 먼저 꺼낸 것을 왼쪽으로 썼다
int right = buffer.pop();
buffer.push(apply(left, right, token));
```

```
입력 "3 4 -" 를 토큰 단위로 소비한다

 "3" -> push               "4" -> push                 "-" -> pop 두 번
   +-----+                   +-----+                    첫 pop = 4   (나중에 쌓인 것)
   |  3  | <- top            |  4  | <- top             둘째 pop = 3 (먼저 쌓인 것)
   +-----+                   +-----+
                             |  3  |
                             +-----+

 접근 1 : left = 4, right = 3 -> 4 - 3 = 1      <- 틀렸다
 impl   : right = 4, left = 3 -> 3 - 4 = -1     <- 맞다

 왜 그런가 : 입력 "3 4 -" 의 왼쪽 피연산자는 3 이다
             그런데 3 이 먼저 쌓였으므로 스택에서는 나중에 나온다(LIFO)
             따라서 "두 번째로 꺼낸 것" 이 왼쪽이다
```

- 논리: 값 두 개를 꺼내 연산하고 결과를 다시 쌓는다는 뼈대는 정답과 같다.
- 논리: 꺼내는 순서에만 의미를 잘못 붙였다.
- 비용(왜): 토큰당 상수 연산 → 시간 O(n), 공간은 스택 깊이 O(n) — 정답과 똑같다.
- 한계: `+`, `*` 처럼 교환법칙이 성립하는 연산에서는 결과가 같아서 **버그가 숨는다**.
- 한계: `-`, `/` 에서만 드러난다 — `"3 4 -"` 가 1, `"8 4 /"` 가 0(4/8의 정수 나눗셈)이 된다.
- 한계: 테스트 `operandOrderMatters` 가 정확히 이것만 잡으려고 존재한다.\
  `assertEquals(-1, ..., "3 - 4 이지 4 - 3 이 아니다")`, `assertEquals(2, ..., "8 / 4 이지 4 / 8 이 아니다")`, `assertEquals(-6, evaluatePostfix("2 8 -", ...))`.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 결과만 틀린 것.\
> 예: 피연산자를 뒤집어도 `"3 4 +"` 는 7로 맞게 나와서, 덧셈 테스트만 있으면 버그를 못 잡는다.

**접근 2 — 리스트에 토큰을 담고 연산자 자리에서 앞 두 개를 지우기** (스택을 안 쓰려다 느려진다)

```java
// 의사코드
List<String> t = new ArrayList<>(Arrays.asList(expression.trim().split("\\s+")));
int i = 0;
while (t.size() > 1) {
    if (isOperator(t.get(i))) {
        int left  = Integer.parseInt(t.get(i - 2));
        int right = Integer.parseInt(t.get(i - 1));
        t.set(i, String.valueOf(apply(left, right, t.get(i))));
        t.remove(i - 1);      // 뒤쪽 원소를 전부 한 칸씩 당긴다
        t.remove(i - 2);      // 또 한 번 당긴다
        i -= 2;
    } else {
        i++;
    }
}
return Integer.parseInt(t.get(0));
```

```
입력 "5 1 2 + 4 * + 3 -"

  idx      0    1    2    3    4    5    6    7    8
         +----+----+----+----+----+----+----+----+----+
         | 5  | 1  | 2  | +  | 4  | *  | +  | 3  | -  |
         +----+----+----+----+----+----+----+----+----+
                          ^ i=3 연산자. 앞 두 개(1, 2)를 3 으로 합친다

         +----+----+----+----+----+----+----+
         | 5  | 3  | 4  | *  | +  | 3  | -  |   뒤의 5칸이 왼쪽으로 당겨졌다
         +----+----+----+----+----+----+----+
                     ^ i=3 다시 연산자. 앞 두 개(3, 4)를 12 로

         +----+----+----+----+----+
         | 5  | 12 | +  | 3  | -  |   또 당겨졌다
         +----+----+----+----+----+

         +----+----+----+           +----+
         | 17 | 3  | -  |    ->     | 14 |   -> 14
         +----+----+----+           +----+

 비용 : remove(i) 한 번이 뒤쪽 전부를 한 칸씩 당긴다 -> O(n)
        연산자가 n/3 개쯤 있으니 O(n) x O(n) = O(n^2)
        스택은 "당길 뒤쪽"이 아예 없다 — 언제나 맨 끝만 만진다
```

- 논리: 후위 표기의 계산 규칙 자체는 같다 — 연산자를 만나면 바로 앞 두 값이 피연산자다.
- 논리: 스택 대신 리스트의 인덱스를 직접 관리했을 뿐이다.
- 비용(왜): `ArrayList.remove(i)` 가 뒤쪽 원소를 전부 한 칸 당기는 시프트라 O(n).

> **시프트(shift)** — 배열 중간에서 빼거나 넣을 때 뒤쪽 원소를 한 칸씩 밀거나 당기는 일.\
> 예: 리스트 한가운데를 지우면 뒤 전부가 당겨지고, 스택은 맨 끝만 만지므로 이 일이 0회다.

- 비용(왜): 연산자마다 `remove` 를 두 번 하므로 총 시프트가 계산상 `O(n^2)` 이다.
- 한계: 인덱스 `i - 1`, `i - 2` 를 직접 다뤄 경계 실수(피연산자 부족)를 잡기 어렵다.
- 한계: 결과를 다시 문자열로 넣었다 파싱하는 왕복이 생긴다.
- 한계: 결국 "맨 끝 두 개를 꺼내 하나를 넣는다"를 하고 있으므로, 그 접근 지점을 끝으로 제한하면 그게 곧 스택이다.\
  **리스트로 스택을 흉내 내면 스택의 이점만 잃는다.**

**접근 3 — 스택에 값을 쌓고 연산자에서 두 개를 꺼낸다** (impl 의 정답)

```java
public static int evaluatePostfix(String expression, Stack<Integer> buffer) {
    for (String token : expression.trim().split("\\s+")) {
        if (token.isEmpty()) {
            continue;
        }
        if (isOperator(token)) {
            if (buffer.size() < 2) {
                throw new IllegalArgumentException("피연산자가 모자란다: " + token);
            }
            int right = buffer.pop();
            int left = buffer.pop();
            buffer.push(apply(left, right, token));
        } else {
            try {
                buffer.push(Integer.parseInt(token));
            } catch (NumberFormatException e) {
                throw new IllegalArgumentException("알 수 없는 토큰: " + token, e);
            }
        }
    }
    if (buffer.size() != 1) {
        throw new IllegalArgumentException("식이 올바르지 않다. 남은 값 " + buffer.size() + "개");
    }
    return buffer.pop();
}
```

```
입력 "5 1 2 + 4 * + 3 -" (= 5 + (1+2)*4 - 3 = 14) — 토큰마다 스택 전체를 그린다

 "5"                "1"                "2"                "+"  right=2 left=1
   +-----+            +-----+            +-----+            push(1+2)=3
   |  5  |<-top       |  1  |<-top       |  2  |<-top
   +-----+            +-----+            +-----+            +-----+
                      |  5  |            |  1  |            |  3  |<-top
                      +-----+            +-----+            +-----+
                                         |  5  |            |  5  |
                                         +-----+            +-----+

 "4"                "*"  right=4 left=3  "+"  right=12 left=5  "3"
   +-----+            push(3*4)=12         push(5+12)=17
   |  4  |<-top
   +-----+            +-----+            +-----+            +-----+
   |  3  |            | 12  |<-top       | 17  |<-top       |  3  |<-top
   +-----+            +-----+            +-----+            +-----+
   |  5  |            |  5  |                               | 17  |
   +-----+            +-----+                               +-----+

 "-"  right=3 left=17 -> push(17-3)=14        입력 끝
   +-----+                                     size() == 1 이므로 올바른 식
   | 14  |<-top                                return pop() = 14
   +-----+

 꺼내는 순서가 왜 right 먼저인가
     후위식에서 왼쪽 피연산자가 항상 먼저 쓰인다 -> 먼저 쌓인다
     스택은 나중에 쌓인 것을 먼저 준다(LIFO)
     따라서 첫 pop = 오른쪽, 둘째 pop = 왼쪽
     즉 "입력의 순서"와 "꺼내는 순서"가 정확히 뒤집혀 있다
```

> **후위 표기(postfix notation)** — 연산자를 피연산자 뒤에 쓰는 표기법.\
> 예: `3 + 4` 를 `3 4 +` 로 쓴다 — 괄호도 우선순위 규칙도 필요 없어 스택 하나로 계산된다.

- 논리: 숫자는 "아직 쓰일 곳이 안 정해진 값"이므로 쌓아둔다.
- 논리: 연산자를 만난 순간 그 연산자가 먹을 두 값이 확정된다 — 스택의 맨 위 둘이다.
- 논리: 결과를 다시 쌓으므로 더 바깥 연산자의 피연산자가 되어 재귀 구조가 평평하게 펴진다.
- 논리: 계산 전에 `buffer.size() < 2` 를 검사해 "피연산자가 모자란다"를 명시적 예외로 만든다.\
  이 검사가 없으면 `EmptyStackException` 이라는 엉뚱한 예외가 밖으로 샌다.
- 논리: 끝난 뒤 `size() != 1` 검사가 `"3 4"` 처럼 **연산자가 모자란** 식을 잡는다.\
  두 검사가 각각 반대 방향의 불일치를 담당한다.
- 비용(왜): 토큰당 push/pop이 상수 회 → **시간 O(n)** (n = 토큰 수).
- 비용(왜): 스택 깊이는 최악에 피연산자 전부 → **추가 공간 O(n)**.\
  `"1 2 3 4 5 + + + +"` 같은 식이 그 최악이다.
- 한계: `int` 연산이라 오버플로가 조용히 일어난다.\
  자바 `int` 는 약 ±2.1 x 10^9 를 넘으면 값이 감긴다.
- 한계: `/` 는 정수 나눗셈이고 0으로 나누면 `ArithmeticException` 이 그대로 나간다 — 2-summary 의 문제 설명이 그렇게 정하고 있다.
- 한계: 단항 마이너스(`-3`)를 못 다룬다 — `Integer.parseInt("-3")` 은 되지만 `"3 -"` 같은 단항 연산자 표기는 정의되어 있지 않다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 꺼낸 순서를 뒤집어 씀 | O(n) | O(n) | 쓸 일 없다 (버그) | `-`, `/` 가 들어간 순간 — `"3 4 -"` 가 1이 된다 |
| 2. 리스트에서 지워가며 | 최악 O(n^2) | O(n) | 토큰이 몇 개뿐일 때 | 식이 길 때 · 성능이 필요할 때 |
| 3. 스택 (impl) | O(n) | O(n) | 기본값 | 없음 — 후위 표기가 스택을 전제로 만들어진 표기다 |

**데이터 규모가 커지면**

- 토큰 100만 개짜리 식이면 접근 2는 계산상 약 10^11 회 시프트다.\
  접근 3은 약 2 x 10^6 회 push/pop 이다.
- `Stack<Integer>` 라 값마다 박싱된 `Integer` 객체가 생긴다.\
  자바 `Integer` 캐시는 -128~127뿐이라 큰 수가 많으면 객체가 그만큼 생긴다.
- 스택 깊이가 문제 될 만큼 깊은 식(피연산자 수백만 개)이면 `ArrayStack` 은 확장 복사 지연이, `LinkedStack` 은 노드 오버헤드가 각각 문제가 된다(→ 9·10번).
- 식이 파일에 있고 메모리에 다 못 올린다면 `split` 으로 토큰을 한꺼번에 만드는 부분이 먼저 터진다.\
  토크나이저를 스트리밍으로 바꾸면 스택 깊이만 메모리에 남는다.
- 정확한 수치가 필요한 계산이면 `int` 대신 `long` 이나 `BigInteger` 로 바꾼다.\
  `BigInteger` 는 연산 하나가 O(자릿수)라 복잡도 자체가 달라진다.

**질문별 답**

- Q: 문제 2(후위 표기식 계산 — `evaluatePostfix`)를 어떻게 푸는가.\
  A: 공백으로 토큰을 나눠 왼쪽부터 소비한다.\
  숫자면 스택에 쌓는다.\
  연산자면 두 개를 꺼내 계산하고 결과를 다시 쌓는다.\
  끝났을 때 스택에 값이 정확히 하나 남아야 올바른 식이고, 그 값이 답이다.

- Q: 연산자를 만났을 때 **두 번째로 꺼낸 것이 왼쪽 피연산자**인 이유는 무엇인가.\
  A: 후위 표기에서 왼쪽 피연산자가 항상 먼저 쓰이기 때문이다.\
  먼저 쓰인 것은 먼저 스택에 쌓인다.\
  스택은 나중에 쌓인 것을 먼저 주므로(LIFO) 첫 `pop` 은 오른쪽 피연산자다.\
  그래서 `int right = pop(); int left = pop();` 순서가 되고, "입력 순서"와 "꺼내는 순서"가 정확히 뒤집힌다는 것이 요점이다.

- Q: 반대로 하면 `"3 4 -"` 가 왜 1이 되는가.\
  A: 먼저 꺼낸 값은 4이기 때문이다.\
  그것을 왼쪽이라고 부르면 계산식이 `4 - 3` 이 되어 1이 나온다.\
  정답은 `3 - 4 = -1` 이다.\
  `+` 나 `*` 는 순서를 바꿔도 답이 같아서 버그가 안 보이고, `-` 와 `/` 에서만 드러난다 — 테스트 `operandOrderMatters` 가 그 셋(`"3 4 -"`, `"8 4 /"`, `"2 8 -"`)을 콕 집어 검사한다.

#### 3. 오른쪽의 첫 번째 더 큰 값 (`nextGreater`)

**접근 1 — 각 원소마다 오른쪽을 훑는다** (가장 먼저 떠오르고, 이 문제집의 함정이다)

```java
// 의사코드
int[] result = new int[values.length];
for (int i = 0; i < values.length; i++) {
    result[i] = -1;
    for (int j = i + 1; j < values.length; j++) {
        if (values[j] > values[i]) { result[i] = values[j]; break; }
    }
}
return result;
```

```
입력 [1, 3, 2, 4]

  i=0 (1) : j=1 -> 3 > 1  찾음         result[0] = 3   (1회 비교)
  i=1 (3) : j=2 -> 2 > 3? 아니다
            j=3 -> 4 > 3  찾음         result[1] = 4   (2회 비교)
  i=2 (2) : j=3 -> 4 > 2  찾음         result[2] = 4   (1회 비교)
  i=3 (4) : 오른쪽이 없다               result[3] = -1  (0회 비교)

  -> [3, 4, 4, -1]  정답은 맞다


최악 입력 [5, 4, 3] 처럼 내림차순이면 — 테스트 mustBeLinear 가 쓰는 모양이다

  i=0 (5) : j=1, j=2 를 다 봤는데 없다   -> 2회 비교
  i=1 (4) : j=2 를 봤는데 없다           -> 1회 비교
  i=2 (3) : 오른쪽이 없다                 -> 0회 비교
  총 2 + 1 + 0 = 3 회 = n(n-1)/2

  n = 200,000 이면 계산상 약 2 x 10^10 회 비교
  테스트의 제한은 5초다 -> 여기서 막힌다
```

- 논리: 정의를 그대로 옮긴 풀이다 — "오른쪽에서 처음으로 나오는 더 큰 값".
- 논리: `break` 덕에 첫 번째로 큰 값을 찾자마자 멈춘다.
- 비용(왜): 안쪽 루프가 최악에 `n - i - 1` 번 돈다.
- 비용(왜): 총합은 `(n-1) + (n-2) + ... + 0 = n(n-1)/2` → **O(n^2)**.
- 비용(왜): 추가 공간은 결과 배열 말고는 없다 → O(1).
- 한계: `mustBeLinear` 테스트가 `n = 200_000`, `Duration.ofSeconds(5)` 로 이 풀이를 정확히 겨냥한다.\
  그 테스트가 쓰는 입력이 `values[i] = n - i` 즉 완전한 내림차순이라 최악이 그대로 나온다.
- 한계: **같은 정보를 계속 다시 본다** — i번 원소가 오른쪽을 훑을 때 봤던 구간을 i+1번 원소가 또 훑는다.\
  그 중복을 없애는 것이 접근 2다.

**접근 2 — "아직 답을 못 찾은 인덱스"를 스택에 쌓는다 (단조 스택)** (impl 의 정답)

```java
public static int[] nextGreater(int[] values, Stack<Integer> buffer) {
    int n = values.length;
    int[] result = new int[n];

    for (int i = 0; i < n; i++) {
        while (!buffer.isEmpty() && values[buffer.peek()] < values[i]) {
            result[buffer.pop()] = values[i];
        }
        buffer.push(i);
    }
    while (!buffer.isEmpty()) {
        result[buffer.pop()] = -1;
    }
    return result;
}
```

> **단조 스택(monotonic stack)** — 스택 안의 값이 항상 한 방향(여기서는 아래→위로 감소)으로 정렬된 상태를 유지하는 기법.\
> 예: 새 값이 그 정렬을 깨는 순간, 깨진 것들의 답이 한꺼번에 정해지고 전부 꺼내진다.

```
입력 [1, 3, 2, 4] — 스택에는 "인덱스"를 담고, 괄호 안은 그 인덱스의 값이다

 i=0 (값1)                   스택이 비어 있다 -> 그냥 push
   +---------+
   | 0 (1)   | <- top
   +---------+

 i=1 (값3)                   peek 의 값 1 < 3 -> 0번의 답이 지금 정해졌다
   꺼내며 답을 채운다         result[0] = 3, pop
   +---------+               스택이 비었다 -> push(1)
   |         |
   +---------+
   -> +---------+
      | 1 (3)   | <- top
      +---------+

 i=2 (값2)                   peek 의 값 3 < 2? 아니다 -> 아무도 안 꺼낸다
   +---------+               push(2)
   | 2 (2)   | <- top
   +---------+
   | 1 (3)   |               위에서 아래로 2, 3 — 아래로 갈수록 큰 "감소 스택"이다
   +---------+

 i=3 (값4)                   peek 의 값 2 < 4 -> result[2] = 4, pop
   while 이 두 번 돈다        peek 의 값 3 < 4 -> result[1] = 4, pop
                              스택이 비었다 -> push(3)
   +---------+
   | 3 (4)   | <- top
   +---------+

 입력 끝 — 스택에 남은 것은 "끝까지 더 큰 값을 못 만난 것들"이다
   result[3] = -1, pop -> 스택이 비었다

 결과 [3, 4, 4, -1]   (테스트 findsNextGreater 의 기대값과 같다)


왜 while 이 여러 번 도는데도 O(n) 인가 — 인덱스별 출입 장부를 보라

  인덱스   push 된 시점   pop 된 시점        총 출입
  ------   ------------   ---------------    -------
    0         i=0            i=1              1 + 1
    1         i=1            i=3              1 + 1
    2         i=2            i=3              1 + 1
    3         i=3            입력 끝난 뒤      1 + 1

  각 인덱스는 딱 한 번 들어가고 딱 한 번 나온다
  i=3 에서 while 이 두 번 돌았지만, 그 두 번은 다른 i 들이 "안 돈" 몫을 쓴 것이다
  전체 pop 횟수는 어떤 입력에서도 n 을 넘지 못한다 -> 총 2n 회 -> O(n)
```

> **상환 분석(amortized analysis)** — 한 번의 비용이 아니라 **n번의 총비용**을 보고 1회 평균을 말하는 분석법.\
> 예: 안쪽 `while` 이 한 번에 100번 돌아도, 그 100개는 앞에서 push된 것들이라 전체 pop은 n을 못 넘는다.

```
같은 값은 왜 "더 큰" 값이 아닌가 — 입력 [5, 5, 5]

 조건이 values[peek] < values[i] 라 등호가 빠져 있다

 i=0 : push 0
   +---------+
   | 0 (5)   | <- top
   +---------+

 i=1 : peek 의 값 5 < 5? 거짓 -> 안 꺼낸다 -> push 1
   +---------+
   | 1 (5)   | <- top
   +---------+
   | 0 (5)   |
   +---------+

 i=2 : 마찬가지 -> push 2         입력 끝 -> 남은 셋 전부 -1
   +---------+
   | 2 (5)   | <- top            result = [-1, -1, -1]
   +---------+
   | 1 (5)   |                    테스트 handlesEdges 의
   +---------+                    "같은 값은 '더 큰' 값이 아니다" 가 이것을 본다
   | 0 (5)   |
   +---------+

 조건을 <= 로 바꾸면 [5, 5, 5] 가 [5, 5, -1] 이 된다 — 부등호 하나가 문제 정의다
```

- 논리: 스택에 담는 것은 값이 아니라 **인덱스**다 — 답을 `result[인덱스]` 에 써야 하므로 위치 정보가 필요하다.
- 논리: 스택에 남아 있다는 것은 "아직 자기보다 큰 값을 못 만났다"는 뜻이다.
- 논리: 새 값 `values[i]` 가 들어오면, 스택 안에서 그보다 작은 것들은 **전부** 답이 `values[i]` 로 한꺼번에 정해진다.\
  스택이 감소 순서라서 위에서부터 꺼내면 자연히 그 그룹만 꺼내진다.
- 논리: 스택은 아래로 갈수록 값이 큰 감소 스택 상태를 항상 유지한다 — 이것이 불변식이다.

> **불변식(invariant)** — 루프가 도는 동안 언제 확인해도 참이어야 하는 조건.\
> 예: 여기서는 "스택을 위에서 아래로 읽으면 값이 증가한다(= 아직 답을 못 찾은 것들만 감소 순으로 쌓여 있다)"가 매 반복 끝에 유지된다.

- 논리: 마지막 `while` 은 "끝까지 더 큰 값을 못 만난 것들"에 `-1` 을 채운다.\
  이 루프가 빠지면 `result` 의 그 칸들이 자바 기본값 0으로 남아 조용히 틀린다.
- 비용(왜): 바깥 루프 n회 + 각 인덱스의 push 1회·pop 1회 → 전체 연산이 **최대 3n** 회 → **시간 O(n)**.
- 비용(왜): 안쪽 `while` 의 총 실행 횟수는 전체 pop 횟수와 같고 그것이 n 이하라는 것이 핵심이다.
- 비용(왜): 스택 깊이는 최악에 n (완전 내림차순 입력) → **추가 공간 O(n)**.
- 한계: 내림차순 입력에서 스택이 n개까지 쌓인다 — `mustBeLinear` 가 쓰는 입력이 정확히 그것이라 메모리도 최악으로 밟는다.
- 한계: `Stack<Integer>` 라 인덱스 20만 개가 전부 박싱된다 (테스트가 `Stack<Object>` 공급자를 `Stack<Integer>` 로 캐스팅해 넘긴다).
- 한계: `buffer` 를 인자로 받으므로 호출 전에 비어 있어야 한다.

**접근 3 — 오른쪽에서 왼쪽으로 훑으며 "후보"를 쌓는다** (같은 O(n), 다른 방향)

```java
// 의사코드 — impl 이 아니라 대조용이다
int[] result = new int[n];
for (int i = n - 1; i >= 0; i--) {
    while (!buffer.isEmpty() && values[buffer.peek()] <= values[i]) {
        buffer.pop();                    // 나보다 작거나 같으면 영원히 답이 될 수 없다
    }
    result[i] = buffer.isEmpty() ? -1 : values[buffer.peek()];
    buffer.push(i);
}
```

```
입력 [1, 3, 2, 4] 를 오른쪽부터 처리한다

 i=3 (값4) : 스택이 비었다 -> result[3] = -1, push 3
   +---------+
   | 3 (4)   | <- top

 i=2 (값2) : peek 의 값 4 <= 2? 아니다 -> result[2] = 4, push 2
   +---------+
   | 2 (2)   | <- top
   +---------+
   | 3 (4)   |
   +---------+

 i=1 (값3) : peek 의 값 2 <= 3 -> pop (2는 3에 가려 영원히 답이 못 된다)
   +---------+       peek 의 값 4 <= 3? 아니다 -> result[1] = 4, push 1
   | 1 (3)   | <- top
   +---------+
   | 3 (4)   |
   +---------+

 i=0 (값1) : peek 의 값 3 <= 1? 아니다 -> result[0] = 3, push 0

 결과 [3, 4, 4, -1]  — 접근 2와 같다

 무엇이 다른가
     접근 2 : 스택에 "질문"(답을 못 찾은 인덱스)을 쌓고, 새 값이 답을 나눠준다
     접근 3 : 스택에 "후보"(오른쪽에 있는 답 후보)를 쌓고, 내가 직접 peek 해 답을 읽는다
     둘 다 각 인덱스가 1번 push / 최대 1번 pop 이라 O(n) 이다
```

- 논리: 오른쪽부터 보면 "내 오른쪽의 후보들"이 이미 스택에 준비되어 있다.
- 논리: 나보다 작거나 같은 후보는 내가 가려버리므로 영원히 답이 될 수 없다 — 버린다.
- 논리: 버리고 남은 맨 위가 내 답이다.
- 비용(왜): 인덱스마다 push 1회·pop 최대 1회 → **O(n)**, 추가 공간 O(n) — 접근 2와 같다.
- 한계: 결과를 `result[i]` 에 즉시 쓰므로 `result` 를 끝에 한 번 더 훑는 마무리가 없다 — 그만큼 단순하다.
- 한계: 반대로 "한 번의 새 값이 여러 답을 한꺼번에 정한다"는 그림이 안 보여서, 상환 분석의 직관은 접근 2가 더 잘 보여준다.
- 한계: 부등호를 `<` 로 쓰면 같은 값이 후보로 남아 `[5,5,5]` 가 `[5,5,-1]` 이 된다 — 여기서는 `<=` 여야 한다.\
  접근 2와 부등호 방향이 반대라는 점이 헷갈리기 쉽다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 이중 루프 | 최악 O(n^2) | O(1) | n이 수천 이하이고 코드 단순함이 중요할 때 | n이 크면 — 20만 건 5초 제한을 못 넘는다 |
| 2. 단조 스택, 왼→오 (impl) | O(n) | O(n) | 기본값. "다음 큰 값" 류 전부 | 스택 깊이만큼의 메모리가 없을 때 |
| 3. 단조 스택, 오→왼 | O(n) | O(n) | 입력을 뒤에서부터 읽는 것이 자연스러울 때 | 스트리밍처럼 앞에서만 읽을 수 있을 때 |

**데이터 규모가 커지면**

- 테스트가 정한 벽이 `n = 200_000` / 5초다.\
  접근 1은 계산상 약 2 x 10^10 회 비교라 이 벽을 못 넘고, 접근 2는 약 6 x 10^5 회 연산이다.
- 접근 2·3은 내림차순 입력에서 스택 깊이가 n 이 된다.\
  20만 개면 `ArrayStack` 기준 용량이 4 → 8 → ... → 262,144 로 **16번** 확장하고, 총 복사량은 계산상 약 262,140회다 (4+8+...+131072).
- 같은 입력을 `LinkedStack` 에 주면 노드 20만 개가 생긴다.\
  복사 지연은 없지만 노드마다 객체 헤더 + `item` 참조 + `next` 참조가 붙는다.
- `Stack<Integer>` 의 박싱을 없애려면 `int[]` 와 `int sp` 로 직접 스택을 만든다.\
  복잡도는 그대로지만 상수와 메모리가 크게 준다 (원본에 근거 없음 — 내 추론).
- 입력이 스트림으로 들어오고 끝을 모르면 접근 3(오른쪽부터)은 아예 못 쓴다.\
  접근 2는 그대로 쓸 수 있고, 답이 정해지는 순간 바로 흘려보낼 수 있다.

**질문별 답**

- Q: 문제 3(오른쪽의 첫 번째 더 큰 값 — `nextGreater`)을 어떻게 푸는가.\
  A: 스택에 "아직 답을 못 찾은 인덱스"를 쌓으며 왼쪽부터 한 번 훑는다.\
  새 값 `values[i]` 가 들어올 때, 스택 맨 위의 값이 그보다 작으면 그 인덱스의 답이 `values[i]` 로 확정되므로 꺼내며 `result` 에 채운다.\
  더 이상 작은 것이 없으면 `i` 를 쌓는다.\
  다 훑은 뒤 스택에 남은 것들은 더 큰 값을 못 만난 것이므로 전부 `-1` 이다.

- Q: 각 원소마다 오른쪽을 훑는 풀이가 왜 O(n²)인가.\
  A: 안쪽 루프가 최악에 `n - i - 1` 번 돌기 때문이다.\
  `break` 가 있어도 더 큰 값이 아예 없으면 끝까지 간다.\
  총합은 `(n-1) + (n-2) + ... + 0 = n(n-1)/2` 다.\
  테스트 `mustBeLinear` 의 입력 `values[i] = n - i` 가 완전한 내림차순이라 이 최악을 그대로 만든다 — n = 200,000이면 계산상 약 2 x 10^10 회다.

- Q: "아직 답을 못 찾은 인덱스"를 스택에 쌓는 풀이는 왜 O(n)인가 — 안쪽 while이 여러 번 도는데도.\
  A: 안쪽 `while` 의 총 실행 횟수가 곧 **전체 pop 횟수**이기 때문이다.\
  각 인덱스는 딱 한 번 `push` 되므로 `pop` 도 최대 한 번이고, 따라서 전체 pop이 n을 넘지 못한다.\
  어떤 한 번의 `i` 에서 while이 100번 돌았다면, 그 100개는 앞의 100번의 `i` 가 while을 한 번도 안 돌고 넘어간 몫을 쓴 것이다.\
  그래서 바깥 n회 + push n회 + pop n회 = 최대 3n → O(n)이고, 이 회계가 상환 분석이며 01번의 배열 2배 확장과 같은 논리다.

#### 4. 스택 정렬 (`sortAscending`)

**접근 1 — 배열로 쏟아 정렬한 뒤 되넣기** (제일 쉽지만 문제 조건을 어긴다)

```java
// 의사코드
int[] tmp = new int[stack.size()];
for (int i = tmp.length - 1; i >= 0; i--) tmp[i] = stack.pop();
Arrays.sort(tmp);
for (int v : tmp) stack.push(v);   // 작은 것부터 넣으면 큰 것이 top 에 온다
```

```
입력 스택 (바닥 -> top) : 3, 1, 2

  전부 꺼내 배열로            정렬                   작은 것부터 다시 push
  +-----+                                            +-----+
  |  2  |<-top    tmp = [3,1,2]   ->  [1,2,3]        |  3  | <- top
  +-----+                                            +-----+
  |  1  |                                            |  2  |
  +-----+                                            +-----+
  |  3  |                                            |  1  |
  +-----+                                            +-----+

  결과는 맞다 (테스트의 기대값 [1,2,3] 과 같다)
  하지만 문제가 "배열이나 리스트로 옮기지 말라"고 못박았다
```

- 논리: 정렬은 이미 잘 풀린 문제이므로 라이브러리에 맡긴다.
- 논리: 작은 값부터 다시 넣으면 큰 값이 마지막에 들어가 `top` 이 된다.
- 비용(왜): `Arrays.sort` 가 O(n log n), 옮기기가 O(n) → **시간 O(n log n)** 으로 impl 보다 빠르다.
- 비용(왜): 배열 하나 → 추가 공간 O(n).
- 한계: 2-summary 의 문제 설명이 "배열이나 리스트로 옮기지 말고, 주어진 보조 스택 하나만 써서 해결하라"고 제약을 걸었다.
- 한계: 이 문제의 목적은 "정렬하기"가 아니라 **스택만 가지고 무엇을 할 수 있나**를 손에 익히는 것이다.\
  라이브러리로 우회하면 배울 것이 없다.
- 한계: 그래도 이 접근이 알려주는 것이 있다 — impl 이 O(n^2) 인 이유는 알고리즘이 나빠서가 아니라 **제약이 그렇게 만든 것**이다.

**접근 2 — 보조 스택을 정렬된 상태로 유지한다** (impl 의 정답)

```java
public static void sortAscending(Stack<Integer> stack, Stack<Integer> helper) {
    while (!stack.isEmpty()) {
        int value = stack.pop();
        while (!helper.isEmpty() && helper.peek() < value) {
            stack.push(helper.pop());
        }
        helper.push(value);
    }
    while (!helper.isEmpty()) {
        stack.push(helper.pop());
    }
}
```

> **삽입 정렬(insertion sort)** — 이미 정렬된 부분에 새 값을 알맞은 자리에 끼워 넣기를 반복하는 정렬.\
> 예: 이 코드에서 `helper` 가 "정렬된 부분"이고, 자리를 만들려고 위쪽을 `stack` 으로 잠시 덜어내는 것이 "끼워 넣기"다.

- 논리: 불변식은 "`helper` 는 항상 정렬되어 있고 `top` 이 가장 작다"이다.
- 논리: 새 값 `value` 를 넣을 자리를 만들려면, `value` 보다 작은 것들이 위에 있으면 안 된다.\
  그것들을 `stack` 으로 잠시 되돌려 자리를 비운다.
- 논리: 되돌린 값들은 다음 반복에서 다시 꺼내져 제자리를 찾아간다 — 버려지는 정보가 없다.
- 논리: 바깥 `while` 이 끝났다는 것은 `stack` 이 비었다는 뜻이고, 그 시점에 `helper` 가 전부를 정렬해 담고 있다.
- 논리: 마지막 이사가 순서를 한 번 더 뒤집어 요구된 방향(`top` 이 최댓값)을 만든다.
- 논리: 빈 스택과 원소 1개 입력에서도 루프가 자연히 0회·1회 돌고 끝난다 — 테스트 `handlesDuplicatesAndEdges` 가 이 경계를 본다.
- 논리: 비교가 `helper.peek() < value` 라 **등호가 없다**.\
  같은 값이면 되돌리지 않고 바로 위에 쌓아 안정적으로 처리된다 — `[2,1,2,1]` → `[1,1,2,2]` 가 그 예다.
- 비용(왜): 값 하나를 제자리에 넣을 때 `helper` 의 최대 k개를 되돌렸다 다시 가져온다.
- 비용(왜): 최악은 이미 내림차순으로 쌓인 입력이라 매번 `helper` 를 통째로 되돌린다.\
  총 이동이 `1 + 2 + ... + n = n(n+1)/2` → **시간 O(n^2)**.
- 비용(왜): 추가 공간은 `helper` 하나 → **O(n)**.
- 한계: `Arrays.sort` 보다 느리다.\
  다만 그것은 "스택 두 개만"이라는 제약이 만든 것이지 풀이의 실수가 아니다.
- 한계: 값 비교에 `int` 언박싱이 일어난다.\
  `helper.peek() < value` 에서 `Integer` 가 `int` 로 풀린다.

**접근 3 — 재귀로 한 개씩 끼워 넣기** (보조 스택 대신 호출 스택을 쓴다)

```java
// 의사코드
static void sort(Stack<Integer> s) {
    if (s.isEmpty()) return;
    int v = s.pop();
    sort(s);            // 나머지를 먼저 정렬한다
    insert(s, v);       // 정렬된 스택에 v 를 제자리로 끼운다
}
static void insert(Stack<Integer> s, int v) {
    if (s.isEmpty() || s.peek() <= v) { s.push(v); return; }
    int t = s.pop();
    insert(s, v);
    s.push(t);
}
```

```
[3, 1, 2] (top=2) 를 재귀로

  sort  : pop 2 -> sort([3,1]) -> pop 1 -> sort([3]) -> pop 3 -> sort([]) 반환
  insert: 3 을 빈 스택에 push          [3]
          1 을 끼운다 : peek 3 <= 1? 아니다 -> 3 을 잠시 꺼내 들고(호출 스택)
                        빈 스택에 1 push, 다시 3 push   [1, 3]
          2 를 끼운다 : peek 3 <= 2? 아니다 -> 3 을 잠시 들고
                        peek 1 <= 2 -> 2 push, 다시 3 push  [1, 2, 3]

  "잠시 들고 있는 값"이 자바 호출 스택의 지역 변수 t 다
  보조 스택을 명시적으로 안 쓸 뿐, 스택을 안 쓴 것이 아니다
```

- 논리: "나머지를 먼저 정렬하고 나를 끼운다"는 삽입 정렬의 재귀 표현이다.
- 논리: 되돌려 놓는 값들을 `helper` 대신 호출 스택의 지역 변수에 들고 있다.
- 비용(왜): `insert` 가 최악 O(n), 그것을 n번 → **시간 O(n^2)** — impl 과 같다.
- 비용(왜): 호출 깊이가 최악 n → **추가 공간 O(n)**, 다만 그 공간이 힙이 아니라 **호출 스택**이다.
- 한계: n이 커지면 `StackOverflowError` 가 난다.\
  자바 기본 스택 크기면 대략 수천~수만 깊이에서 터진다 (원본에 근거 없음 — 내 추론).

> **호출 스택(call stack)** — 함수 호출마다 지역 변수와 돌아갈 주소를 쌓아두는 런타임의 스택.\
> 예: 재귀가 깊어지면 이 스택이 넘쳐 `StackOverflowError` 가 난다 — 스택이 자료구조이면서 동시에 언어 런타임의 기반이라는 증거다.

- 한계: 문제가 "주어진 보조 스택 하나를 쓰라"고 했는데 이 풀이는 그 인자를 안 쓴다 — 시그니처와 어긋난다.
- 한계: 디버깅할 때 상태가 호출 스택에 흩어져 있어 눈으로 추적하기 어렵다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 배열로 쏟아 `Arrays.sort` | O(n log n) | O(n) 배열 | 제약이 없는 실무 코드 | 문제가 "스택만" 을 요구할 때 |
| 2. 보조 스택 (impl) | O(n^2) | O(n) 스택 | 이 문제. 스택 두 개만 허용될 때 | n이 수만을 넘을 때 |
| 3. 재귀 삽입 | O(n^2) | O(n) 호출 스택 | 코드를 짧게 쓰고 싶을 때 | n이 깊어 `StackOverflowError` 가 날 때 |

**데이터 규모가 커지면**

- n = 1,000 이면 접근 2의 최악이 계산상 약 50만 회 이동이라 체감되지 않는다.
- n = 1,000,000 이면 접근 2는 계산상 약 5 x 10^11 회 이동이다.\
  같은 입력에서 접근 1은 약 2 x 10^7 회 비교로 끝난다.
- 그래서 규모가 커지면 **제약을 다시 협상하는 것**이 옳은 대응이다.\
  "스택 두 개만"이 진짜 요구인지, 아니면 연습을 위한 것인지 먼저 확인한다.
- 접근 3은 규모가 커지면 복잡도 이전에 호출 깊이에서 먼저 죽는다.
- 값이 박싱된 `Integer` 라면 이동마다 언박싱·박싱이 섞인다.\
  `int[]` 기반 스택으로 바꾸면 상수가 크게 준다 (원본에 근거 없음 — 내 추론).

**질문별 답**

- Q: 문제 4(스택 정렬 — `sortAscending`)를 어떻게 푸는가.\
  A: 원래 스택에서 값을 하나 꺼내, 보조 스택의 알맞은 자리에 끼워 넣기를 반복한다.\
  보조 스택 위쪽에 그 값보다 작은 것들이 있으면 원래 스택으로 잠시 되돌려 자리를 만든다.\
  원래 스택이 빌 때까지 반복하면 보조 스택이 "top이 가장 작은" 정렬 상태로 전부를 담는다.\
  마지막에 보조 스택을 통째로 원래 스택으로 옮기면 순서가 한 번 더 뒤집혀 "top이 가장 큰" 오름차순이 된다.

- Q: 보조 스택을 정렬된 상태로 유지한다는 불변식이 왜 답을 만드는가.\
  A: 불변식이 유지되면 "새 값이 들어갈 자리"를 찾는 일이 맨 위에서만 결정되기 때문이다.\
  `helper.peek() < value` 인 동안만 덜어내면, 멈춘 지점이 곧 `value` 의 정확한 자리다.\
  덜어낸 값들은 버려지지 않고 원래 스택으로 돌아가 다음 반복에서 다시 제자리를 찾는다.\
  원래 스택이 비는 순간 모든 값이 `helper` 를 한 번씩 거쳤고 그때마다 불변식이 지켜졌으므로, 결과가 정렬되어 있다는 것이 귀납적으로 보장된다.

- Q: 이 풀이가 O(n²)인 것이 왜 "맞는" 답인가.\
  A: 스택 두 개만 쓴다는 제약 아래에서는 그것이 한계이기 때문이다.\
  스택은 맨 위 하나만 볼 수 있어서, 값 하나를 제자리에 넣으려면 위에 쌓인 것들을 물리적으로 덜어내는 수밖에 없다.\
  임의 위치를 볼 수 있는 배열이었다면 `O(n log n)` 정렬을 쓸 수 있지만, 그건 다른 자료구조를 허락받은 것이다.\
  README도 "`sortAscending`은 O(n²)입니다. 그게 맞습니다 ... **제약이 복잡도를 결정하는** 예입니다"라고 못박는다 — 복잡도를 자료구조와 따로 떼어 말할 수 없다는 것이 이 문제의 교훈이다.

#### 5. 중위 → 후위 변환 (`infixToPostfix`)

**접근 1 — 우선순위를 무시하고 나오는 대로 출력** (왜 스택이 필요한지를 보여주는 대조군)

```java
// 의사코드
StringBuilder out = new StringBuilder();
for (String token : expression.trim().split("\\s+")) {
    if (isOperator(token)) buffer.push(token.charAt(0));
    else out.append(token).append(' ');
}
while (!buffer.isEmpty()) out.append(buffer.pop()).append(' ');   // 남은 연산자 전부
```

```
입력 "3 + 4 * 2"  (정답은 "3 4 2 * +")

 "3" -> 출력      out = "3"
 "+" -> push
   +-----+
   |  +  | <- top
   +-----+
 "4" -> 출력      out = "3 4"
 "*" -> push      (우선순위를 안 본다)
   +-----+
   |  *  | <- top
   +-----+
   |  +  |
   +-----+
 "2" -> 출력      out = "3 4 2"
 끝   -> 전부 pop  out = "3 4 2 * +"      우연히 맞았다


입력 "3 * 4 + 2"  (정답은 "3 4 * 2 +")

 "3" -> 출력      out = "3"
 "*" -> push      +-----+
                  |  *  | <- top
                  +-----+
 "4" -> 출력      out = "3 4"
 "+" -> push      +-----+     여기서 '*' 를 먼저 내보냈어야 했다
                  |  +  | <- top
                  +-----+
                  |  *  |
                  +-----+
 "2" -> 출력      out = "3 4 2"
 끝   -> pop '+', pop '*'   out = "3 4 2 + *"

 이것을 계산하면 3 * (4+2) = 18 이다. 정답은 3*4 + 2 = 14 다.  -> 틀렸다

 왜 틀렸나 : 연산자를 "언제 내보낼지" 판단하지 않았다
             스택에 쌓기만 하고 우선순위 비교를 안 하면 순서가 통째로 뒤집힌다
```

- 논리: 숫자는 바로 출력하고 연산자는 미뤄둔다는 뼈대까지는 맞다.
- 논리: 하지만 "미뤄둔 연산자를 언제 꺼내는가"라는 판단이 통째로 빠져 있다.
- 비용(왜): 토큰당 상수 연산 → 시간 O(n), 공간 O(연산자 수).
- 한계: 우선순위가 섞이면 순서가 뒤집힌다 — 테스트 `respectsPrecedence` 의 `"3 * 4 + 2"` → `"3 4 * 2 +"` 에서 걸린다.
- 한계: 괄호를 아예 다루지 못한다 — `(` 가 출력에 섞여 나온다.

**접근 2 — 재귀 하강 파서로 트리를 만든 뒤 후위 순회** (정확하지만 더 무겁다)

```java
// 의사코드 — 문법 규칙을 함수로 옮긴다
// expr   := term (('+' | '-') term)*
// term   := factor (('*' | '/') factor)*
// factor := number | '(' expr ')'
Node expr()   { Node n = term();   while (peek is + or -) n = new Node(op, n, term());   return n; }
Node term()   { Node n = factor(); while (peek is * or /) n = new Node(op, n, factor()); return n; }
Node factor() { if (peek == '(') { next(); Node n = expr(); expect(')'); return n; } return leaf(number()); }
// 만든 트리를 후위 순회하면 곧 후위 표기다
```

```
"3 + 4 * 2" 의 트리

                 ( + )
                   |
            +------+------+
            |             |
           (3)          ( * )
                          |
                   +------+------+
                   |             |
                  (4)           (2)

 후위 순회(왼쪽 -> 오른쪽 -> 자기) : 3, 4, 2, *, +   ->  "3 4 2 * +"   정답과 같다

 우선순위는 어디에 들어 있나 : 문법 규칙의 계층(expr 이 term 을 부른다)에 들어 있다
 왼쪽 결합은 어디에 : while 루프가 왼쪽 노드를 계속 감싸는 모양에 들어 있다
 그런데 이 방법은 "스택을 명시적으로 안 쓸 뿐" 호출 스택을 쓴다 — 스택을 피한 게 아니다
```

- 논리: 문법을 함수의 호출 관계로 표현하면 우선순위가 구조에 박힌다.
- 논리: 트리로 만들어두면 후위뿐 아니라 전위·중위 출력도, 최적화도 할 수 있다.
- 비용(왜): 토큰당 상수 작업 → **시간 O(n)**.
- 비용(왜): 트리 노드 n개 + 호출 깊이 → **추가 공간 O(n)**, 다만 노드 객체가 실제로 생긴다.
- 한계: 코드가 길고, 연산자를 하나 추가하려면 문법 계층을 손봐야 한다.
- 한계: 깊게 중첩된 괄호에서 호출 깊이가 깊어져 `StackOverflowError` 위험이 있다.
- 한계: 이 과제가 요구한 것은 "스택 하나로 변환하기"라 목적과 어긋난다.\
  다만 실무 파서가 실제로 가는 길이라는 점은 알아둘 만하다.

**접근 3 — shunting yard: 연산자를 스택에 대기시킨다** (impl 의 정답)

```java
public static String infixToPostfix(String expression, Stack<Character> buffer) {
    StringBuilder out = new StringBuilder();

    for (String token : expression.trim().split("\\s+")) {
        if (token.isEmpty()) {
            continue;
        }
        char c = token.charAt(0);

        if (token.equals("(")) {
            buffer.push('(');
        } else if (token.equals(")")) {
            while (!buffer.isEmpty() && buffer.peek() != '(') {
                append(out, buffer.pop());
            }
            if (buffer.isEmpty()) {
                throw new IllegalArgumentException("여는 괄호가 없다");
            }
            buffer.pop();                       // 여는 괄호는 출력하지 않고 버린다
        } else if (isOperator(token)) {
            while (!buffer.isEmpty() && buffer.peek() != '('
                && precedence(buffer.peek()) >= precedence(c)) {
                append(out, buffer.pop());
            }
            buffer.push(c);
        } else {
            try {
                Integer.parseInt(token);
            } catch (NumberFormatException e) {
                throw new IllegalArgumentException("알 수 없는 토큰: " + token, e);
            }
            append(out, token);
        }
    }

    while (!buffer.isEmpty()) {
        char top = buffer.pop();
        if (top == '(') {
            throw new IllegalArgumentException("닫는 괄호가 없다");
        }
        append(out, top);
    }
    return out.toString();
}

private static int precedence(char operator) {
    return (operator == '*' || operator == '/') ? 2 : 1;
}
```

> **shunting yard(입환장) 알고리즘** — 연산자를 스택이라는 "대기 선로"에 세워뒀다가 우선순위 순서로 내보내 중위식을 후위식으로 바꾸는 방법.\
> 예: 기차역에서 차량을 곁선로에 잠깐 세워뒀다 순서를 바꿔 내보내는 것과 같다.

```
입력 "3 + 4 * 2"  ->  기대 "3 4 2 * +"

 토큰 "3"  숫자 -> 즉시 출력      out = "3"
   +-----+
   |     |  (스택은 비어 있다)
   +-----+

 토큰 "+"  연산자                out = "3"
   스택이 비어 while 을 안 돈다 -> push '+'
   +-----+
   |  +  | <- top
   +-----+

 토큰 "4"  숫자 -> 즉시 출력      out = "3 4"
   +-----+
   |  +  | <- top
   +-----+

 토큰 "*"  연산자
   peek = '+', precedence('+')=1 >= precedence('*')=2 ?  거짓 -> 안 꺼낸다
   push '*'                        out = "3 4"
   +-----+
   |  *  | <- top
   +-----+
   |  +  |
   +-----+

 토큰 "2"  숫자 -> 즉시 출력      out = "3 4 2"

 입력 끝 -> 남은 연산자를 전부 꺼내 출력
   pop '*'  out = "3 4 2 *"       pop '+'  out = "3 4 2 * +"
   +-----+                          +-----+
   |  +  | <- top                   |     |  (비었다)
   +-----+                          +-----+

 -> "3 4 2 * +"  (테스트 respectsPrecedence 의 기대값)
```

```
왜 "같거나 높은" 이어야 하는가 — "3 - 4 - 5" 를 두 조건으로 나란히 돌려본다
정답은 "3 4 - 5 -" ( = (3-4)-5 = -6 )

[A] impl 의 조건  precedence(peek) >= precedence(c)

  "3"  -> out = "3"
  "-"  -> 스택 비었다 -> push
     +-----+
     |  -  | <- top
     +-----+
  "4"  -> out = "3 4"
  "-"  -> peek '-' 의 우선순위 1 >= 1  참 -> pop 해서 출력
     +-----+                out = "3 4 -"
     |     |   그 다음 스택이 비었으므로 while 종료 -> push '-'
     +-----+
     -> +-----+
        |  -  | <- top
        +-----+
  "5"  -> out = "3 4 - 5"
  끝   -> pop '-'           out = "3 4 - 5 -"      맞다
          계산하면 (3-4)-5 = -6

[B] "높은" 만 볼 때  precedence(peek) > precedence(c)

  "3"  -> out = "3"
  "-"  -> push
     +-----+
     |  -  | <- top
     +-----+
  "4"  -> out = "3 4"
  "-"  -> peek '-' 의 우선순위 1 > 1  거짓 -> 안 꺼낸다 -> push
     +-----+
     |  -  | <- top          같은 연산자가 두 개 쌓였다
     +-----+
     |  -  |
     +-----+
  "5"  -> out = "3 4 5"
  끝   -> pop, pop          out = "3 4 5 - -"      틀렸다
          계산하면 3 - (4-5) = 4

 결론 : 같은 우선순위끼리 "먼저 온 것을 먼저 내보낸다" 는 규칙이 곧 왼쪽 결합이다
        부등호에 등호를 붙이느냐가 그 규칙의 전부다
        (오른쪽 결합인 거듭제곱 ^ 는 반대로 등호를 빼야 한다)
```

> **왼쪽 결합(left-associative)** — 우선순위가 같은 연산자가 나란히 오면 왼쪽부터 묶이는 성질.\
> 예: `3 - 4 - 5` 는 `(3-4)-5` 이지 `3-(4-5)` 가 아니다.

```
괄호는 어떻게 처리되나 — "( 3 + 4 ) * 2"  ->  기대 "3 4 + 2 *"

 "("  -> 그냥 push (벽 역할)        out = ""
   +-----+
   |  (  | <- top
   +-----+

 "3"  -> out = "3"

 "+"  -> while 조건에 peek != '(' 가 있다 -> peek 가 '(' 라 루프를 안 돈다
         push '+'                  out = "3"
   +-----+
   |  +  | <- top
   +-----+
   |  (  |          '(' 아래의 연산자들은 이 벽에 막혀 안 나온다
   +-----+

 "4"  -> out = "3 4"

 ")"  -> '(' 를 만날 때까지 꺼내 출력
         pop '+' -> out = "3 4 +"
   +-----+
   |  (  | <- top   여기서 while 종료 (peek == '(')
   +-----+
         비어 있지 않으므로 예외 없음 -> pop 해서 '(' 를 버린다 (출력하지 않는다)
   +-----+
   |     |  (비었다)
   +-----+

 "*"  -> 스택이 비었다 -> push      out = "3 4 +"
   +-----+
   |  *  | <- top
   +-----+

 "2"  -> out = "3 4 + 2"
 끝   -> pop '*'  ->  out = "3 4 + 2 *"      맞다

 '(' 가 하는 일 : 우선순위 비교의 "벽" 이다
                  괄호 안의 연산자는 괄호 밖 연산자와 절대 비교되지 않는다
                  그래서 괄호가 우선순위를 뒤집을 수 있다
```

```
괄호 불일치가 잡히는 두 시점

[시점 1] 닫는 괄호를 만났는데 여는 괄호가 안 나온 채 스택이 비었다 — "3 + 4 )"

 "3" -> out="3"    "+" -> push    "4" -> out="3 4"

 ")" -> while (peek != '(') 로 꺼내 출력
        pop '+' -> out = "3 4 +"
   +-----+
   |     |   스택이 비었다 -> while 종료
   +-----+
        if (buffer.isEmpty()) throw "여는 괄호가 없다"      <- 여기서 잡힌다

[시점 2] 입력이 다 끝났는데 스택에 '(' 가 남아 있다 — "( 3 + 4"

 "(" -> push    "3" -> out="3"    "+" -> push    "4" -> out="3 4"
   +-----+
   |  +  | <- top
   +-----+
   |  (  |
   +-----+

 입력 끝 -> 마지막 while 이 남은 것을 꺼낸다
        pop '+' -> 괄호가 아니다 -> out = "3 4 +"
        pop '(' -> 괄호다        -> throw "닫는 괄호가 없다"   <- 여기서 잡힌다

 두 시점이 각각 반대 방향의 불일치를 담당한다
     시점 1 = 닫는 것이 남았다(여는 것이 모자라다)
     시점 2 = 여는 것이 남았다(닫는 것이 모자라다)
 이건 문제 1의 isBalanced 에서 "도중 isEmpty 검사" 와 "끝난 뒤 isEmpty 검사" 가 하던 역할과 똑같다
```

- 논리: 숫자는 후위식에서도 순서가 안 바뀌므로 즉시 출력한다.
- 논리: 연산자는 "오른쪽 피연산자를 아직 못 봤으므로 출력할 때가 안 된 것"이라 스택에 대기시킨다.
- 논리: 새 연산자가 왔을 때 스택 위의 것이 **먼저 계산되어야 하면** 그것을 먼저 내보낸다.\
  "먼저 계산되어야 한다"의 판정이 `precedence(peek) >= precedence(c)` 다.
- 논리: `peek != '('` 가 while 조건에 있어 괄호가 비교의 벽이 된다.
- 논리: 닫는 괄호는 출력에 쓰이지 않고 짝과 함께 소멸한다 — 후위 표기에는 괄호가 없기 때문이다.
- 논리: 숫자 토큰도 `Integer.parseInt` 로 검증만 하고 원래 문자열을 출력한다.\
  값을 계산하지 않으므로 여러 자리 수가 그대로 보존된다 — `"42"` → `"42"` 가 그 예다.
- 비용(왜): 연산자 하나가 스택에 최대 한 번 들어가고 한 번 나온다 → 전체 push/pop이 토큰 수 이하 → **시간 O(n)**.\
  안쪽 `while` 이 여러 번 도는 것도 문제 3과 같은 상환 논리로 총합이 묶인다.
- 비용(왜): 스택 깊이는 최악에 연산자+괄호 개수 → **추가 공간 O(n)**.
- 한계: 우선순위가 `*`, `/` = 2 / 나머지 = 1 두 단계뿐이다.\
  단항 연산자, 거듭제곱(오른쪽 결합), 비교 연산자 등은 못 다룬다.
- 한계: `char c = token.charAt(0)` 이라 여러 글자 연산자(`**`, `>=`)를 못 다룬다.
- 한계: 토큰이 반드시 공백으로 나뉘어 있어야 한다 — `"3+4"` 는 숫자 파싱에서 예외가 난다.
- 한계: `Stack<Character>` 라 괄호와 연산자가 같은 스택을 쓴다.\
  타입으로 구분되지 않아 `peek != '('` 같은 문자 비교에 의존한다.

**접근 비교**

| 접근 | 시간 | 추가 공간 | 언제 쓰나 | 언제 안 통하나 |
|---|---|---|---|---|
| 1. 우선순위 무시 | O(n) | O(연산자 수) | 쓸 일 없다 (버그) | 우선순위가 섞이는 순간 · 괄호가 있는 순간 |
| 2. 재귀 하강 파서 | O(n) | O(n) 트리 + 호출 깊이 | 트리가 필요할 때(최적화·재출력·타입 검사) | 가볍게 후위식만 필요할 때 · 중첩이 아주 깊을 때 |
| 3. shunting yard (impl) | O(n) | O(n) 스택 | 기본값. 중위 → 후위 변환 | 문법이 복잡해질 때(단항·함수 호출·다양한 결합성) |

**데이터 규모가 커지면**

- 토큰이 아무리 많아도 세 접근 모두 O(n)이라 복잡도로는 갈리지 않는다.\
  갈리는 것은 상수와 메모리다.
- 접근 2는 노드 객체를 n개 만든다.\
  토큰 100만 개면 객체 100만 개 + GC 압력이다.
- 접근 3은 스택 깊이만 쓴다.\
  깊이는 중첩 괄호 수 + 대기 연산자 수라 보통 n보다 훨씬 작다.
- `StringBuilder out` 이 결과 전체를 메모리에 들고 있다.\
  아주 긴 식이면 출력을 스트림으로 흘려보내도록 바꾼다 — shunting yard 는 그 변형이 자연스럽다.
- 접근 2는 중첩 괄호가 수만 겹이면 호출 깊이에서 `StackOverflowError` 가 난다.\
  접근 3은 명시적 스택이라 힙을 쓰므로 그 한계가 훨씬 멀다.

**질문별 답**

- Q: 문제 5(중위 → 후위 변환 — `infixToPostfix`)를 어떻게 푸는가.\
  A: 토큰을 왼쪽부터 소비하면서, 숫자는 즉시 출력하고 연산자는 스택에 대기시킨다.\
  새 연산자를 만나면 스택 위에 우선순위가 같거나 높은 연산자가 있는 동안 꺼내 출력한 뒤 자신을 쌓는다.\
  여는 괄호는 그냥 쌓고, 닫는 괄호를 만나면 여는 괄호가 나올 때까지 꺼내 출력한 뒤 여는 괄호를 버린다.\
  입력이 끝나면 스택에 남은 연산자를 전부 꺼내 출력한다 — 이것이 shunting yard 다.

- Q: 연산자 조건이 "우선순위가 **같거나** 높은"이어야 하는 이유는 무엇인가.\
  A: 사칙연산이 왼쪽 결합이기 때문이다.\
  우선순위가 같은 연산자끼리는 먼저 온 것이 먼저 계산되어야 하므로, 새 연산자가 올 때 스택 위의 동급 연산자를 먼저 내보내야 한다.\
  등호를 빼면 동급 연산자가 스택에 쌓인 채 나중에 역순으로 나와 오른쪽 결합이 되어버린다.\
  즉 부등호에 등호를 붙이느냐 마느냐가 결합 방향을 결정한다 — 오른쪽 결합인 거듭제곱이라면 반대로 등호를 빼야 한다.

- Q: "높은"만 보면 `3 - 4 - 5` 가 어떻게 되는가.\
  A: `"3 4 5 - -"` 가 된다.\
  두 번째 `-` 를 만났을 때 스택의 `-` 를 안 꺼내고 그 위에 쌓기 때문이다.\
  끝에 두 개를 역순으로 꺼내므로 `3 - (4 - 5) = 4` 로 계산된다.\
  정답은 `(3 - 4) - 5 = -6` 이고, 테스트 `leftAssociative` 가 `"3 4 - 5 -"` 를, `chainsWithEvaluate` 가 그 결과를 계산한 `-6` 을 확인한다.

- Q: 괄호 불일치는 어느 두 시점에서 드러나는가.\
  A: 첫째, 닫는 괄호를 만나 꺼내다가 여는 괄호를 못 만난 채 스택이 비는 시점이다 — `"3 + 4 )"` 가 여기서 "여는 괄호가 없다"로 걸린다.\
  둘째, 입력이 다 끝나고 남은 것을 비우는데 `(` 가 나오는 시점이다 — `"( 3 + 4"` 가 여기서 "닫는 괄호가 없다"로 걸린다.\
  두 시점이 각각 "여는 것이 모자라다"와 "닫는 것이 모자라다"를 담당한다.\
  문제 1의 `isBalanced` 에서 "도중의 `isEmpty` 검사"와 "끝난 뒤의 `isEmpty` 검사"가 하던 일과 정확히 같은 구조다.

### B. 자료구조 특성

#### 6. 스택이 왜 필요한가 — 접근 지점을 제한해서 얻는 것

- Q: 02-linked-list나 01-dynamic-array를 그냥 쓰면 안 되는가?\
  A: 기능만 따지면 된다 — `DynamicArray` 의 `add(맨뒤)`/`remove(맨뒤)` 만 쓰면 그게 곧 스택이다.\
  `ArrayStack` 의 코드가 실제로 `DynamicArray` 의 꼬리 연산과 같은 모양인 것이 그 증거다.\
  문제는 "되느냐"가 아니라 "그 타입이 무엇을 약속하느냐"다.\
  `DynamicArray` 를 넘겨받은 코드는 `get(5)`, `remove(2)`, `insert(0, x)` 를 전부 할 수 있고, 그래서 아무것도 보장받지 못한다.

- Q: 접근 지점을 한쪽 끝으로 **제한하는** 것이 무엇을 얻어 주는가?\
  A: 첫째, **불변식의 보장**이다.\
  `Stack` 타입을 받은 순간 "중간을 건드리는 코드는 존재할 수 없다"가 컴파일 시점에 확정된다.\
  둘째, **성능의 보장**이다.\
  중간 삽입·삭제가 불가능하므로 시프트가 원천적으로 없고, 모든 연산이 O(1)로 고정된다.\
  셋째, **의도의 전달**이다.\
  시그니처에 `Stack<Character> buffer` 라고 적히면 읽는 사람이 "여기서는 LIFO 순서가 중요하구나"를 즉시 안다.

> **좁은 인터페이스(narrow interface)** — 할 수 있는 일을 일부러 줄여서, 못 하는 일을 보장으로 바꾸는 설계.\
> 예: `Stack` 에는 `get(int)` 가 없어서, `Stack` 을 받은 코드가 임의 접근을 하고 있지 않다는 것이 확실하다.

- Q: 그 제한이 구현에게는 무엇을 주는가?\
  A: 구현 자유다.\
  "중간 접근이 없다"를 전제할 수 있으니 `LinkedStack` 은 `prev` 링크를 아예 안 만들고, 꼬리 참조도 안 들고 있어도 된다.\
  `ArrayStack` 은 시프트 코드가 통째로 없다 — `push`/`pop` 이 각각 두 줄이다.\
  약속을 줄인 대가로 구현이 단순해지고 빨라진다.

**더 생각할 것**

- 자료구조를 고르는 일은 "무엇을 할 수 있나"보다 **"무엇을 못 하게 만들 것인가"** 를 고르는 일에 가깝다.
- 실무에서 `List` 를 스택처럼 쓰다가 누군가 `list.get(0)` 을 하면서 순서 가정이 깨지는 사고가 난다.\
  타입으로 막았으면 그 커밋이 컴파일되지 않았을 것이다.
- 반대로 과하게 좁히면 나중에 "중간 하나만 보고 싶다"에서 막힌다.\
  그래서 좁힐 때는 "이 제약이 앞으로도 참인가"를 먼저 묻는다.

#### 7. 스택이 맞는 상황의 공통점, 그리고 맞지 않는 상황

- Q: 스택이 맞는 상황에는 어떤 공통점이 있는가?\
  A: **가장 최근의 것이 가장 먼저 해소되어야 한다**는 것이다.\
  "나중에 만난 것을 먼저 처리해야 할 때"라는 표현이 정확히 그 뜻이다.\
  문제를 풀 때 "지금 필요한 정보가 언제나 가장 최근에 본 것 하나뿐인가"를 물어보면 판별된다.\
  그렇다면 그 정보를 쌓아두기만 하면 되고, 그 저장소가 스택이다.

- Q: 질문이 든 네 예에서 그 공통점이 어떻게 나타나는가?\
  A: 표로 보면 이렇다.

  | 상황 | 무엇을 쌓나 | 무엇이 꺼내는 사건인가 |
  |---|---|---|
  | 괄호 검사 | 아직 안 닫힌 여는 괄호 | 닫는 괄호를 만남 |
  | 연산자 우선순위 | 아직 출력할 때가 안 된 연산자 | 우선순위가 같거나 낮은 연산자·닫는 괄호를 만남 |
  | 되돌리기(Ctrl+Z) | 방금 한 작업의 역연산 | 사용자가 되돌리기를 누름 |
  | 함수 호출 | 돌아갈 주소와 지역 변수 | 함수가 `return` 함 |

- Q: 이 과제의 다섯 문제에서는 어떻게 나타나는가?\
  A: 문제 1은 "가장 최근에 열린 괄호"를 꺼낸다.\
  문제 2는 "가장 최근에 쌓인 두 값"이 연산자의 피연산자다.\
  문제 3은 "가장 최근에 답을 못 찾은 것들"이 먼저 해소된다.\
  문제 5는 "가장 최근에 대기시킨 연산자"가 먼저 출력된다 — 다섯 중 넷이 같은 문장이다.

- Q: 반대로 언제 스택을 쓰면 안 되는가?\
  A: 먼저 온 것을 먼저 처리해야 할 때다 — 그건 큐(FIFO)다.\
  작업 순서가 도착 순이 아니라 중요도 순일 때 — 그건 우선순위 큐다.\
  "몇 번째 원소"로 접근해야 할 때 — 스택에는 인덱스 접근이 없다.\
  중간을 보거나 빼야 할 때 — 위를 전부 꺼내야만 아래가 보이므로 O(n)이 된다.\
  전체를 순회하며 읽어야 할 때 — 스택은 읽으려면 파괴해야 한다.

> **FIFO(First In First Out, 선입선출)** — 먼저 넣은 것이 먼저 나오는 규칙. 스택의 정반대다.\
> 예: 줄 서기, 프린터 대기열, 메시지 큐가 전부 FIFO이고 04-queue-deque의 주제다.

- Q: 실무에서 "스택이 답인가"를 빠르게 판별하는 방법은?\
  A: 처리 순서를 그려보고, 나중에 들어온 것이 앞지르는 화살표가 생기는지 본다.\
  앞지르면 스택, 안 앞지르면 큐다.\
  또 하나는 "지금 열린 것이 나중에 반드시 닫혀야 하는가"를 묻는 것이다 — 열림/닫힘 쌍이 있으면 거의 항상 스택이다.\
  괄호, 태그(HTML), 트랜잭션 중첩, 락 획득/해제가 전부 그 모양이다.

**더 생각할 것**

- 스택과 재귀는 같은 것의 두 표현이다.\
  재귀 함수는 호출 스택에 자동으로 쌓고, 명시적 스택은 그것을 손으로 쌓는 것이다.\
  깊이가 문제 되면 재귀를 명시적 스택으로 바꾸는 변환이 실제 최적화 기법이다.
- 브라우저 뒤로 가기는 스택이지만, 뒤로 간 뒤의 "앞으로 가기"까지 하려면 스택 두 개가 필요하다.\
  현실의 요구는 순수한 LIFO보다 조금씩 더 복잡한 경우가 많다.
- 스택인 줄 알았는데 "중간을 봐야 한다"가 나중에 요구로 들어오면, 그건 스택이 아니라 덱(deque)이거나 리스트다.\
  요구를 먼저 확정하고 자료구조를 고른다.

#### 8. `push`/`pop`/`peek`이 전부 O(1)인 구조적 이유

- Q: 세 연산이 O(1)인 구조적 이유는 무엇인가?\
  A: **건드리는 위치가 입력과 무관하게 한 곳으로 고정**되어 있기 때문이다.\
  `ArrayStack` 은 언제나 `elements[top]` 또는 `elements[top - 1]` 만 만진다.\
  `LinkedStack` 은 언제나 `top` 노드만 만진다.\
  "어디를 건드릴지 찾는 일"이 없으므로 탐색 비용이 0이고, "그 위치 때문에 다른 원소가 움직이는 일"도 없으므로 이동 비용도 0이다.

- Q: 두 구현의 코드에서 그것이 어떻게 보이는가?\
  A: 줄 수가 답이다.

  | 연산 | ArrayStack | LinkedStack |
  |---|---|---|
  | `push` | `ensureCapacity(top + 1); elements[top++] = element;` | `top = new Node<>(element, top); size++;` |
  | `pop` | `E value = (E) elements[--top]; elements[top] = null;` | `Node<E> popped = top; top = popped.next; ...` |
  | `peek` | `return (E) elements[top - 1];` | `return top.item;` |

  어느 줄에도 루프가 없다 — `push` 의 `ensureCapacity` 만이 **가끔** 루프(복사)를 부른다.

- Q: 01번에서 배열의 약점이었던 "중간 삽입/삭제·앞쪽 시프트"가 스택에서는 왜 아예 나타나지 않는가?\
  A: 시프트가 필요한 이유는 "연속 저장된 배열에서 중간에 자리를 만들거나 없앨 때, 순서를 유지하려면 뒤쪽을 전부 밀거나 당겨야 하기 때문"이다.\
  스택은 자리를 만들거나 없애는 지점이 **항상 맨 끝**이다.\
  맨 끝 뒤에는 밀어야 할 원소가 0개다.\
  즉 시프트가 "빨라진" 것이 아니라 **필요한 상황 자체가 API에서 제거된** 것이다.

> **시프트(shift)** — 연속 저장된 배열의 중간에 넣거나 뺄 때 뒤쪽 원소를 한 칸씩 밀거나 당기는 일.\
> 예: `remove(0)` 은 뒤의 n-1개를 전부 당기지만, 스택의 `pop` 은 당길 뒤쪽이 없다.

- Q: 그러면 `ArrayStack.push` 는 정말 언제나 O(1)인가?\
  A: 아니다 — 확장이 걸리는 그 한 번은 O(n)이다.\
  `ensureCapacity` 가 `Arrays.copyOf` 로 전체를 새 배열에 복사한다.\
  그래서 `push` 는 **상환 O(1)** 이고, `pop`·`peek` 만이 **언제나 O(1)** 이다.\
  `LinkedStack` 은 확장이라는 개념 자체가 없어 `push` 도 언제나 O(1)이다 — README의 표가 `push` 행에서만 두 구현을 다르게 적는 이유다.

**더 생각할 것**

- "O(1)이다"라고 말할 때는 상환인지 최악인지를 붙여 말하는 습관이 필요하다.\
  둘을 뭉개면 9번의 지연 논의가 통째로 사라진다.
- `peek` 이 O(1)이라는 것은 "맨 위를 보는 것"만 O(1)이라는 뜻이다.\
  "두 번째를 보는 것"은 API에 없고, 굳이 하려면 `pop` 하고 다시 `push` 해야 한다.
- 배열 스택의 `push` 는 캐시 지역성까지 좋다.\
  방금 쓴 칸 바로 옆에 다음 값을 쓰므로 CPU 캐시에 이미 올라와 있을 확률이 높다.

#### 9. `ArrayStack`의 최악 사용 패턴과 상환 O(1)

- Q: `ArrayStack`에 최악의 사용 패턴을 만들어 보라.\
  A: `new ArrayStack<>()` 로 시작해 **한 번도 안 꺼내고 계속 `push` 만** 하는 패턴이다.\
  기본 용량 4에서 시작해 5번째, 9번째, 17번째 ... `push` 마다 확장이 걸린다.\
  테스트 `mustBeLinear` 가 만드는 상황이 정확히 이것이다 — 내림차순 20만 건이면 `nextGreater` 의 스택이 한 번도 안 줄고 20만까지 쌓인다.\
  덧붙이면 `ArrayStack` 에는 **축소가 없으므로** 01번의 thrashing(경계에서 늘렸다 줄였다)은 일어나지 않는다.

```
용량 4에서 시작해 계속 push 할 때 무슨 일이 일어나는가

 push 1~4  : 빈 칸에 쓰기만 한다. 각 O(1)
      +---+---+---+---+
      | a | b | c | d |     capacity 4, top 4 -> 가득 찼다
      +---+---+---+---+

 push 5    : ensureCapacity(5) -> capacity 4 -> 8 로 두 배
      +---+---+---+---+
      | a | b | c | d |
      +---+---+---+---+
        |   |   |   |       Arrays.copyOf 가 4개를 통째로 복사한다 (이 순간만 O(n))
        v   v   v   v
      +---+---+---+---+---+---+---+---+
      | a | b | c | d | e |   |   |   |   capacity 8
      +---+---+---+---+---+---+---+---+

 확장 지점만 모으면  4 -> 8 -> 16 -> 32 -> ...  (테스트 keepsDoubling 이 확인한다)
 복사량도 그때마다  4 +  8 +  16 +  32 + ...

 n = 200,000 까지 push 하면
     확장 횟수 : 4 x 2^16 = 262,144 >= 200,000 이므로 16회
     총 복사량 : 4 + 8 + ... + 131,072 = 262,140 회   (계산상)
     즉 총 복사 < 2n — 등비급수라 항이 아무리 많아도 2n 을 못 넘는다
```

- Q: 확장이 일어나는 순간의 비용은 얼마인가?\
  A: 그 시점에 담겨 있던 원소 수만큼의 복사다 → **O(n)**.\
  `Arrays.copyOf(elements, newCapacity)` 한 줄이 그 비용 전부다.\
  20만 개가 담긴 상태에서 확장이 걸리면 그 한 번의 `push` 가 20만 번 복사한다.\
  이것이 "지연이 튀는 지점"이다.

- Q: n번 push한 총 비용은 얼마인가?\
  A: 쓰기 n회 + 복사 총합이다.\
  복사 총합은 마지막 확장부터 거꾸로 더하면 `n/2 + n/4 + n/8 + ... < n` 이고, 초기 용량 4에서 시작하면 정확히는 `4 + 8 + ... < 2n` 이다.\
  따라서 총 비용은 **O(n)** 이다.\
  n = 200,000이면 쓰기 200,000회 + 복사 계산상 262,140회 ≈ 46만 회 연산이다.

- Q: 왜 상환 O(1)이라고 부르는가?\
  A: **연속된 n번의 `push` 총비용이 O(n)이므로 1회 평균이 O(1)** 이라는 뜻이다.\
  개별 `push` 가 항상 O(1)이라는 말이 아니다 — 16번은 O(n)이다.\
  비싼 연산이 드물게 일어나고 그 비용을 앞뒤의 싼 연산들이 나눠 갚는다는 회계다.\
  "평균적으로 그럴 것 같다"는 확률 진술이 아니라, 어떤 `push` 순서에서도 성립하는 보장이라는 점이 중요하다.

> **상환 O(1) vs 최악 O(1)** — 상환은 **n번의 총합**에 대한 보장이고, 최악은 **각 호출 하나하나**에 대한 보장이다.\
> 예: `ArrayStack.push` 는 상환 O(1)이지만 최악 O(n)이고, `LinkedStack.push` 는 최악도 O(1)이다.

- Q: 같은 입력을 `LinkedStack`에 주면 총 비용과 **최악 한 번의 지연**은 어떻게 다른가?\
  A: 총 비용은 같은 O(n)이다 — n번의 `push` 가 각각 노드 하나를 만들고 링크 하나를 고친다.\
  다른 것은 **최악 한 번**이다 — `LinkedStack.push` 는 어떤 호출도 O(1)이라 지연이 튀는 지점이 아예 없다.\
  테스트 `noResizeCost` 가 100번 push 후 노드 수가 정확히 100이라고 확인하는 것이 "확장 복사가 없다"를 구조로 보여주는 것이다.\
  표로 정리하면 이렇다.

  | | ArrayStack | LinkedStack |
  |---|---|---|
  | n번 push 총 비용 | O(n) (쓰기 n + 복사 < 2n) | O(n) (노드 생성 n) |
  | push 1회 최악 | O(n) — 확장 순간 | O(1) — 언제나 |
  | 확장 횟수 (n=200,000, 초기 4) | 16회 (계산상) | 0회 |
  | 메모리 | 원소 참조 + 남는 용량 | 원소 참조 + 노드마다 `next` 참조 + 객체 헤더 |

**더 생각할 것**

- 총 처리량(throughput)만 보는 배치라면 상환 O(1)로 충분하다.\
  요청당 지연을 보는 온라인 서비스라면 그 한 번의 O(n)이 p99를 만든다.

> **꼬리 지연(tail latency, p99/p999)** — 느린 쪽 상위 1%·0.1% 요청의 응답 시간.\
> 예: 평균이 1ms라도 1000번에 한 번 500ms가 나오면 p999는 500ms이고, 사용자가 체감하는 것은 그쪽이다.

- 크기를 대충이라도 알면 `new ArrayStack<>(예상치)` 로 시작하는 것이 가장 싼 최적화다 — 확장이 0회가 된다.
- 반대로 크게 잡으면 안 쓰는 칸이 계속 메모리를 붙잡는다.\
  `ArrayStack` 은 축소를 하지 않으므로, 한 번 20만까지 커진 스택은 다 꺼내도 용량 262,144칸을 그대로 들고 있다(→ 12번).

#### 10. `ArrayStack`과 `LinkedStack`의 트레이드오프

- Q: 시간(평균 대 최악 지연)에서 무엇이 다른가?\
  A: 평균은 `ArrayStack` 이 대체로 빠르다 — 노드 객체 생성이 없고 연속 메모리라 캐시 지역성이 좋다.\
  최악 한 번은 `LinkedStack` 이 낫다 — 확장 복사가 없어 지연이 튀지 않는다.\
  `pop`·`peek` 은 양쪽 다 언제나 O(1)이라 차이가 없다.\
  즉 차이는 **`push` 한 줄에 몰려 있다.**

> **캐시 지역성(cache locality)** — 쓸 데이터가 메모리에서 서로 붙어 있어 CPU가 한 덩어리로 미리 가져오는 성질.\
> 예: 배열 스택은 옆 칸이 곧 다음 원소지만, 연결 스택의 노드는 힙 여기저기에 흩어져 매번 새로 가져와야 한다.

- Q: 메모리(남는 용량 대 노드마다 참조 1개)에서 무엇이 다른가?\
  A: `ArrayStack` 은 원소 참조만 담지만 **안 쓰는 칸**을 들고 있다.\
  두 배 확장 직후가 최악이라 용량의 최대 절반이 빈 칸이다.\
  `LinkedStack` 은 빈 칸이 0이지만 원소마다 `Node` 객체가 하나씩 더 생긴다.\
  노드 하나에 객체 헤더 + `item` 참조 + `next` 참조가 들어가므로, 작은 원소일수록 오버헤드 비율이 커진다.

- Q: 그 교환의 뿌리가 되는 설계 선택 한 가지는 무엇인가?\
  A: **연속 저장이냐 흩어진 노드냐**다.\
  연속이라서 인덱스 산술 한 번에 자리를 찾고 캐시가 잘 먹는다 — 대신 자리가 모자라면 통째로 이사해야 한다.\
  흩어져 있어서 이사가 필요 없고 언제나 O(1)이다 — 대신 화살표를 원소마다 들고 다녀야 하고 캐시가 안 먹는다.\
  얻는 것과 잃는 것이 같은 뿌리에서 나오므로 하나만 고를 수 없다.

- Q: "스택은 배열과 잘 맞는다"는데도 `LinkedStack`이 필요한 경우는 어디인가?\
  A: README가 "실시간 처리처럼 **최악 지연이 중요한** 곳"이라고 답한다.\
  평균이 빨라도 가끔 튀면 곤란한 시스템 — 오디오/영상 처리, 게임 프레임 루프, 제어 시스템이 그렇다.\
  또 하나는 원소 수가 예측 불가하게 크고, "2배 크기의 연속 메모리 덩어리"를 통째로 확보하는 것 자체가 부담일 때다.\
  그리고 한 번의 확장 복사 동안 옛 배열과 새 배열이 동시에 살아 있어야 한다는 점도 메모리가 빠듯할 때 걸린다.

- Q: 그럼 실무에서는 무엇을 기본값으로 삼나?\
  A: `ArrayStack` 쪽이 기본값이다.\
  자바 표준의 `ArrayDeque` 도 배열 기반이고, "스택이 필요하면 `ArrayDeque`"가 관용이다.\
  `LinkedStack` 은 위의 특수 조건이 실제로 측정으로 확인됐을 때 꺼내는 카드다.\
  이 과제의 요점은 둘 중 하나를 고르는 것이 아니라 **같은 계약을 두 방식으로 구현했을 때 무엇이 달라지는지**를 손으로 확인하는 것이다.

**더 생각할 것**

- "어느 쪽이 빠른가"는 측정 전에는 대답할 수 없다.\
  캐시 효과는 복잡도 표에 안 나오지만 실측에서 몇 배 차이를 만든다.
- 두 구현이 겉으로 완전히 같게 동작해야 한다는 것이 이 챕터의 전제다.\
  그래서 계약 테스트를 한 곳에만 쓴다(→ 13번).
- 제3의 구현도 가능하다 — 청크(고정 크기 블록)를 연결 리스트로 잇는 방식이면 확장 복사 없이 캐시 지역성도 어느 정도 얻는다 (원본에 근거 없음 — 내 추론).

#### 11. `LinkedStack`이 단방향 노드로 충분한 이유

- Q: 단방향 노드로 충분한 이유는 무엇인가?\
  A: 스택이 만지는 지점이 `top` 하나뿐이고, `top` 에서 필요한 이동이 "아래로 한 칸"뿐이기 때문이다.\
  `push` 는 새 노드가 옛 `top` 을 가리키게 하면 끝이다 — 옛 `top` 은 자기를 누가 가리키는지 알 필요가 없다.\
  `pop` 은 `top = popped.next` 로 한 칸 내려가면 끝이다 — 위로 거슬러 올라갈 일이 없다.\
  `prev` 는 "위로 가기"를 위한 링크인데, 스택에는 위로 갈 상황이 없다.

```
push / pop 에서 실제로 고치는 링크가 몇 개인가

 push(E)   before   top -> [D] -> [B] -> [A] -> null
           after    top -> [E] -> [D] -> [B] -> [A] -> null
                            ^
                    새 노드의 next 하나만 세팅하고 top 을 옮긴다 = 고친 링크 1개
                    top = new Node<>(element, top);   (생성자 안에서 next 가 정해진다)

 pop()     before   top -> [E] -> [D] -> [B] -> null
           after           [E]    top -> [D] -> [B] -> null
                          버림
                    top 을 옮기고, 버린 노드의 item/next 를 끊는다 = 고친 링크 2개(정리 포함)

 만약 prev 가 있었다면 push 마다 "옛 top 의 prev = 새 노드" 를 추가로 세팅해야 한다
 그 링크를 읽는 코드는 어디에도 없다 -> 순수한 낭비 (메모리 + 실수 여지)
```

- Q: 02번에서 `prev`를 관리하느라 들었던 수고가 여기서 왜 사라지는가?\
  A: 02번의 이중 연결 리스트는 **양쪽 끝에서 넣고 빼고, 중간 노드를 그 자리에서 떼어내야** 했기 때문에 `prev` 가 필요했다.\
  중간 노드 하나만 들고 그것을 O(1)로 제거하려면 앞 노드를 알아야 하고, 그 정보가 `prev` 다.\
  스택에는 그 연산이 API에 없다 — 6번에서 말한 "좁은 인터페이스"가 여기서 구현 비용으로 돌아온다.\
  즉 수고가 사라진 것이 아니라, **그 수고를 요구하던 기능을 계약에서 뺀 것**이다.

- Q: `prev` 를 안 쓰면 구체적으로 무엇이 줄어드는가?\
  A: 메모리가 노드당 참조 하나씩 줄어든다.\
  고칠 링크가 절반으로 줄어 `push`/`pop` 이 각각 두세 줄로 끝난다.\
  링크를 고치는 순서를 틀려 사슬이 끊기는 버그의 여지가 줄어든다 — 이중 연결 리스트에서 가장 흔한 실수가 그것이다.\
  `tail` 참조도 필요 없다 — 스택은 바닥을 영원히 안 만지기 때문이다.

> **참조(reference)** — 값이 있는 곳을 가리키는 화살표. `null` 은 "아무것도 안 가리킴"이다.\
> 예: `Node.next` 는 아래 노드를 가리키는 참조이고, 맨 아래 노드의 `next` 는 `null` 이다.

- Q: 그 구조가 테스트로 어떻게 확인되나?\
  A: `LinkedStackTest.pushLinksToPreviousTop` 이 `assertSame(first, stack.top.next, "새 top 이 이전 top 을 가리켜야 한다")` 와 `assertNull(first.next, "맨 아래 노드의 next 는 null 이다")` 로 확인한다.\
  `topBecomesNullWhenDrained` 가 전부 꺼내면 `top == null` 임을 확인한다.\
  어느 테스트도 `prev` 를 보지 않는다 — 계약에 없기 때문이다.

**더 생각할 것**

- 자료구조를 만들 때 "이 필드를 읽는 코드가 어디인가"를 먼저 묻는 습관이 유용하다.\
  읽는 곳이 없으면 그 필드는 버그의 원료일 뿐이다.
- 반대로 나중에 "스택 중간을 훑고 싶다"가 요구로 들어오면 그건 스택이 아니게 되는 신호다.\
  그때 `prev` 를 추가하는 게 아니라 자료구조를 다시 고르는 것이 맞다.
- 04-queue-deque의 덱은 양 끝을 쓰므로 연결 구현이라면 `prev` 가 다시 필요해진다.\
  필요한 링크의 수는 **계약이 허용하는 연산의 함수**다.

#### 12. 꺼낸 자리를 정리하지 않으면 생기는 일

- Q: `ArrayStack.pop` 이 배열 자리를 비우지 않고 `top` 만 줄이면 무엇이 GC되지 않는가?\
  A: 방금 꺼낸 **그 원소 객체 하나**가 GC되지 않는다.\
  `top` 만 줄이면 그 값은 "논리적으로는 없는 값"이 되지만 배열 칸은 여전히 그 객체를 가리키고 있다.\
  배열 자체는 살아 있으므로 그 참조가 객체를 붙잡는다.\
  impl 은 `E value = (E) elements[--top]; elements[top] = null;` 로 읽고 곧바로 비운다.

```
pop 에서 null 을 안 넣으면

 정상 (impl)                          잘못된 구현
 +---+---+---+---+                    +---+---+---+---+
 | A | B | C |nul|  top=3             | A | B | C | D |  top=3
 +---+---+---+---+                    +---+---+---+---+
              ^ 비웠다                              ^ 아직 D 를 가리킨다
 D 를 아무도 안 가리킨다 -> GC 대상    D 는 "없는 값" 인데 배열이 붙잡고 있다 -> 누수

 새어 나가는 양 : pop 한 것 중 다시 덮이지 않은 칸 전부
                  100만까지 쌓았다가 전부 pop 하면 100만 개가 통째로 살아남는다
 테스트 clearsPoppedSlot 이 assertNull(stack.elements[1]) 로 이것을 본다
```

- Q: `LinkedStack.pop` 이 떼어낸 노드의 `next` 를 끊지 않으면 무엇이 GC되지 않는가?\
  A: **떼어낸 노드 아래의 사슬 전체**다.\
  꺼낸 노드를 호출자가 어딘가 들고 있으면(또는 오래 사는 객체가 참조하면), 그 노드의 `next` 를 타고 아래 노드 전부가 살아남는다.\
  원소 하나가 새는 배열 쪽과 달리 여기서는 **스택 전체가 통째로** 새는 것이 차이다.\
  impl 은 `popped.item = null; popped.next = null;` 로 두 링크를 다 끊는다.

```
next 를 안 끊으면 — 새는 양이 다르다

 정상 (impl)
   버린 노드 [E]        top -> [D] -> [B] -> null
              (next=null)
   [E] 만 GC 대상이 되고 아래 사슬은 스택이 계속 쓴다

 잘못된 구현
   버린 노드 [E] ----> [D] -> [B] -> null
   [E] 를 누가 하나라도 붙잡고 있으면 D, B 까지 전부 GC 불가
   -> 노드 하나가 스택 전체를 살려둔다

 테스트 poppedNodeIsDetached 가 assertNull(popped.next) 로 이것을 본다
 clearDetachesChain 은 clear() 후 assertNull(head.next) 로 사슬이 끊겼는지 본다
```

> **메모리 누수(memory leak)** — 더 이상 쓰지 않는데 참조가 남아 있어 GC가 회수하지 못하는 메모리.\
> 예: `pop` 한 배열 칸을 비우지 않으면, 프로그램은 그 값을 영영 안 쓰는데 힙에서는 계속 살아 있다.

> **논리적 삭제 vs 물리적 삭제** — 인덱스만 줄여 "안 보이게" 하는 것과, 참조까지 끊어 실제로 놓아주는 것.\
> 예: `top--` 만 하면 논리적 삭제, `elements[top] = null` 까지 해야 물리적으로 놓아준 것이다.

- Q: 두 구현의 정리 방식이 왜 다른가?\
  A: 붙잡는 주체가 다르기 때문이다.\
  배열 구현에서는 **배열 칸**이 값을 붙잡으므로 칸을 비워야 한다.\
  연결 구현에서는 **떼어낸 노드**가 아래 사슬을 붙잡으므로 그 노드의 링크를 끊어야 한다.\
  목적은 같고(참조를 놓아준다) 손질하는 자리만 다르다 — README가 "세 번째 반복이니 이제 반사적으로 나와야 합니다"라고 적은 것이 이 패턴이다.

- Q: `clear()` 에서 용량은 왜 유지하는가?\
  A: `clear` 의 목적이 "비우고 **다시 쓰는 것**"이기 때문이다.\
  용량까지 줄이면 다음에 다시 채울 때 확장을 처음부터 되풀이해야 한다.\
  스택을 재사용하는 코드(버퍼 풀, 루프 안에서 반복 사용)에서는 그 확장 복사를 다시 내는 것이 순수한 낭비다.\
  테스트 `clearDetachesButKeepsCapacity` 가 `assertEquals(before, stack.capacity())` 로 용량 유지를, 그리고 모든 칸이 `null` 인지를 함께 확인한다 — **참조는 놓아주되 용량은 들고 있는다**가 `clear` 의 계약이다.

**더 생각할 것**

- 용량을 유지한다는 것은 뒤집어 말하면 "안 쓰는 칸을 계속 붙잡는다"는 뜻이다.\
  `ArrayStack` 은 축소가 없으므로, 한 번 크게 커진 스택을 오래 살려두면 그 메모리가 계속 묶인다.\
  정말 놓아주고 싶으면 스택 객체 자체를 버리고 새로 만드는 쪽이 깔끔하다.
- 이런 누수는 테스트로 안 잡히기 쉽다 — 기능은 완벽히 동작하고 결과도 맞기 때문이다.\
  그래서 두 테스트가 `stack.elements`, `stack.top` 같은 **내부 필드를 직접** 들여다본다.\
  계약이 아니라 구현 고유 성질이므로 `StackContractTest` 가 아니라 각 구현 테스트에 있다.
- 실무에서 이 부류의 버그는 "메모리가 조금씩 늘다가 며칠 뒤 OOM"으로 나타난다.\
  재현이 어렵고 원인 추적이 오래 걸리는 대표적 유형이다.

#### 13. 왜 `Stack` 인터페이스와 작업용 스택을 인자로 받나

- Q: `StackProblems`의 다섯 메서드가 전부 구현체가 아니라 `Stack` 인터페이스를 인자로 받는 이유는 무엇인가?\
  A: 문제 풀이 코드가 **어떤 구현을 쓸지 정하지 않게** 하려는 것이다.\
  `Stack` 만 알면 `push`/`pop`/`peek`/`isEmpty`/`size` 의 계약만 쓰게 되고, 그 계약을 지키는 어떤 구현으로도 돌아간다.\
  덕분에 테스트가 같은 문제를 `ArrayStack` 과 `LinkedStack` 양쪽으로 돌려 결과가 같은지 볼 수 있다.\
  `StackProblemsTest.implementations()` 가 두 생성자를 나란히 놓고 `@ParameterizedTest` 로 모든 문제를 두 번씩 돌리는 것이 그 장치다.

> **의존성 역전(dependency inversion)** — 쓰는 쪽이 구체 클래스가 아니라 인터페이스(추상)에 의존하게 만드는 원칙.\
> 예: `isBalanced` 가 `ArrayStack` 이 아니라 `Stack` 을 받으면, 구현을 바꿔 끼워도 `isBalanced` 는 한 줄도 안 바뀐다.

- Q: 인터페이스를 받는 것에 더해 **스택 인스턴스 자체**를 인자로 받는 이유는 따로 무엇인가?\
  A: 안에서 `new` 를 하면 그 순간 구현이 코드에 박히기 때문이다.\
  인자로 받으면 **어떤 구현을 쓸지 정하는 책임이 호출자로 넘어간다.**\
  호출자는 상황에 맞게 고를 수 있다 — 지연이 중요하면 `LinkedStack`, 평균 처리량이 중요하면 `ArrayStack` 을 넘긴다.\
  덤으로 호출자가 스택을 재사용해 할당을 아낄 수도 있다 (원본에 근거 없음 — 내 추론).

> **의존성 주입(dependency injection)** — 필요한 협력 객체를 안에서 만들지 않고 밖에서 받아오는 방식.\
> 예: `isBalanced(input, buffer)` 의 `buffer` 가 주입된 협력 객체다.

- Q: 안에서 `new ArrayStack<>()`라고 쓰면 무엇을 잃는가?\
  A: 첫째, **구현 교체의 자유**를 잃는다 — 다섯 메서드 전부가 `ArrayStack` 에 묶인다.\
  둘째, **양쪽 구현을 같은 테스트로 검증할 방법**을 잃는다 — `StackProblemsTest` 의 파라미터가 무의미해지고, `LinkedStack` 은 응용 문제로는 한 번도 검증되지 않는다.\
  셋째, **호출자의 선택권**을 잃는다 — 초기 용량을 잡거나 특수 구현을 넘길 길이 없어진다.\
  넷째, 테스트에서 "스택이 몇 번 push/pop 됐나" 같은 것을 관찰할 계측 구현을 끼울 수 없다 (원본에 근거 없음 — 내 추론).\
  `StackProblems` 의 javadoc이 "여기서 `new ArrayStack<>()` 이라고 쓰는 순간 그 자유가 사라진다"라고 직접 적고 있다.

- Q: 계약 테스트(`StackContractTest`)를 한 곳에만 두는 것과 같은 이야기인가?\
  A: 같은 원칙의 **반대편 절반**이다.\
  둘 다 "계약은 하나, 구현은 여럿"이라는 같은 전제 위에 서 있다.\
  `StackProblems` 는 그 계약을 **쓰는 쪽**이 구현을 모르게 만든 것이고, `StackContractTest` 는 그 계약을 **검증하는 쪽**이 구현마다 복제되지 않게 만든 것이다.\
  계약이 하나가 아니면 둘 다 성립하지 않는다 — 구현마다 미묘하게 다른 계약이면 문제 코드가 구현을 골라 타야 하고, 테스트도 따로 써야 한다.

> **계약 테스트(contract test)** — 인터페이스가 약속한 동작을 한 번만 적고 모든 구현이 상속해 검증하게 만든 테스트.\
> 예: `StackContractTest` 를 `ArrayStackTest`·`LinkedStackTest` 가 상속하고, 서브클래스는 `create()` 만 채운다.

- Q: 계약 테스트를 구현마다 복사하면 구체적으로 무엇이 나빠지는가?\
  A: README의 표현대로 "둘이 조용히 어긋난다".\
  한쪽에만 케이스를 추가하고 다른 쪽은 잊게 되고, 잊힌 쪽은 검증 없이 통과한다.\
  계약이 늘어날 때 고칠 곳이 구현 수만큼 늘어나 유지비가 곱셈으로 는다.\
  반대로 한 곳에 두면 새 구현이 생겨도 `create()` 한 줄만 채우면 전체 계약이 즉시 적용된다.

- Q: 그러면 "어느 구현이 실패했는가"는 어떻게 아는가?\
  A: 클래스 이름으로 드러난다.\
  `ArrayStack.pop` 만 망가뜨리면 `ArrayStackTest` 만 실패하고 `LinkedStackTest` 는 통과한다 — README가 "실제로 확인했습니다"라고 적은 것이 이것이다.\
  구현 고유 성질(용량 두 배 확장, 노드 링크)은 계약이 아니므로 각 구현 테스트에만 둔다.\
  즉 **공통 계약은 한 곳, 고유 성질은 각자** 라는 분업이다.

**더 생각할 것**

- 이 구조는 자료구조에만 쓰는 게 아니다.\
  `Repository` 인터페이스에 인메모리 구현과 DB 구현을 두고 같은 계약 테스트를 물리는 것이 실무의 같은 패턴이다.
- 인자로 받는 방식은 호출자에게 "빈 스택을 넘겨야 한다"는 숨은 전제를 지운다.\
  계약으로 적거나(`@param buffer 비어 있어야 한다`) 안에서 `clear()` 를 부르는 편이 안전하다 (원본에 근거 없음 — 내 추론).
- 자유에는 비용도 있다 — 인터페이스 호출은 구체 클래스 호출보다 최적화가 덜 될 수 있다.\
  대부분의 경우 JIT가 단일 구현을 인라인해버려 무시할 만하지만, 두 구현이 섞여 쓰이면 그 최적화가 풀린다 (원본에 근거 없음 — 내 추론).

#### 14. 04-queue-deque로의 연결 — 왜 배열 큐는 원형이어야 하나

- Q: 넣는 쪽과 꺼내는 쪽을 **반대 끝**으로 바꾸면 배열 구현에서 무엇이 깨지는가?\
  A: 꺼내는 연산이 O(1)에서 O(n)으로 무너진다.\
  스택은 넣기와 꺼내기가 **같은 끝**이라 건드리는 칸이 하나였다.\
  큐는 뒤에서 넣고 앞에서 꺼내므로, 0번 칸을 꺼낸 뒤 순서를 유지하려면 뒤의 n-1개를 전부 한 칸씩 당겨야 한다.\
  8번에서 "스택에는 아예 나타나지 않는다"고 했던 **앞쪽 시프트가 되돌아온다.**

```
배열 큐를 순진하게 만들면 — 앞에서 꺼낼 때마다 전체를 당긴다

 enqueue A, B, C  (뒤에 넣는다)
   idx   0    1    2    3
       +----+----+----+----+
       | A  | B  | C  |    |
       +----+----+----+----+
         ^front       ^ rear

 dequeue()  -> A 를 꺼내고 뒤를 전부 당긴다
       +----+----+----+----+
       | A  | B  | C  |    |
       +----+----+----+----+
              |    |          B, C 가 한 칸씩 앞으로 (복사 n-1 회)
              v    v
       +----+----+----+----+
       | B  | C  |    |    |
       +----+----+----+----+

 dequeue 한 번이 O(n) -> n 번 dequeue 하면 O(n^2)
 스택이라면 맨 끝에서 꺼내므로 당길 것이 0개였다 — 같은 배열인데 방향 하나로 갈린다
```

- Q: 시프트를 피하려고 `front` 인덱스만 앞으로 옮기면 무슨 일이 생기는가?\
  A: `dequeue` 는 O(1)이 되지만 **배열 앞쪽이 영영 버려진다.**\
  `front` 가 전진할수록 앞의 칸들은 비었는데 다시 쓰이지 않는다.\
  그러다 `rear` 가 배열 끝에 닿으면, 앞에 빈 칸이 잔뜩 있는데도 "꽉 찼다"며 확장하게 된다.\
  넣고 빼기를 반복하는 큐는 원소 수가 늘지 않아도 배열이 무한히 자란다.

```
front 만 전진시키면 — 앞쪽이 버려진다

 A,B,C 를 넣고 A,B 를 꺼낸 상태
   idx   0    1    2    3
       +----+----+----+----+
       |    |    | C  |    |
       +----+----+----+----+
                   ^front    ^rear
         버려진 2칸

 enqueue D -> rear 가 3 에 쓴다
       +----+----+----+----+
       |    |    | C  | D  |
       +----+----+----+----+
                   ^front         ^ rear 가 배열 끝에 닿았다

 enqueue E -> 앞에 빈 칸이 2개인데도 자리가 없다고 판단 -> 확장
              원소는 3개뿐인데 배열만 계속 커진다
```

- Q: 왜 배열 큐는 원형이어야 하는가?\
  A: 버려진 앞쪽 칸을 **다시 쓰기 위해서**다.\
  인덱스를 배열 길이로 나눈 나머지로 감싸면(`(rear + 1) % capacity`), 끝에 닿은 `rear` 가 0번으로 돌아와 빈 앞칸을 채운다.\
  그러면 `enqueue`·`dequeue` 가 둘 다 O(1)이면서 배열도 낭비 없이 순환한다.\
  "배열의 끝과 시작을 이어 붙였다"고 보면 되고, 그래서 **원형 버퍼(circular buffer / ring buffer)** 라고 부른다.

> **원형 버퍼(circular buffer, ring buffer)** — 배열의 끝과 시작을 이어 붙인 것처럼 인덱스를 나머지 연산으로 감싸 쓰는 구조.\
> 예: 길이 4 배열에서 `rear` 가 3 다음에 0으로 돌아와, 앞서 비워진 칸을 다시 쓴다.

```
원형으로 감싸면

   idx   0    1    2    3
       +----+----+----+----+
       |    |    | C  | D  |        front=2, rear=3
       +----+----+----+----+
                   ^front  ^rear

 enqueue E -> rear = (3 + 1) % 4 = 0  -> 0번 칸에 쓴다
       +----+----+----+----+
       | E  |    | C  | D  |        논리적 순서는 C, D, E 다
       +----+----+----+----+
         ^rear      ^front
       배열 위에서는 끊겨 보이지만, 나머지 연산으로 읽으면 이어져 있다

 남은 문제 : front == rear 가 "비었다" 인가 "꽉 찼다" 인가?
             구분할 수 없다 -> size 필드를 따로 들거나, 한 칸을 일부러 비워둔다
```

- Q: 원형으로 만들면 새로 생기는 문제는 무엇인가?\
  A: `front == rear` 가 "비었다"와 "꽉 찼다" 둘 다에 해당해 구분이 안 된다.\
  해법은 두 가지다 — `size` 필드를 따로 들고 다니거나, 한 칸을 항상 비워둬 `rear + 1 == front` 를 "꽉 참"으로 정의한다.\
  또 하나는 확장이다 — 원형 상태에서 배열을 키우면 논리적 순서대로 재배치해야 해서 스택의 `Arrays.copyOf` 한 줄보다 복잡해진다.\
  이런 것들이 04-queue-deque에서 다뤄질 내용이다 (원본에 근거 없음 — 내 추론).

- Q: 연결 리스트로 큐를 만들면 이 문제가 있는가?\
  A: 없다 — 대신 `head` 와 `tail` **두 참조**를 다 들고 있어야 한다.\
  스택은 한쪽 끝만 쓰니 `top` 하나로 충분했는데(→ 11번), 큐는 넣는 끝과 꺼내는 끝이 달라 양쪽 표지가 필요하다.\
  덱(deque)이라면 양 끝에서 넣고 빼므로 `prev` 까지 필요해져 02번의 이중 연결 리스트로 돌아간다.\
  **필요한 링크·표지의 수는 계약이 허용하는 연산의 함수**라는 것이 세 챕터를 관통하는 문장이다.

**더 생각할 것**

- 같은 배열, 같은 연산 개수인데 "어느 끝을 쓰는가" 하나로 O(1)과 O(n)이 갈린다.\
  자료구조의 성능은 저장 방식만이 아니라 **접근 패턴과의 궁합**에서 나온다.
- 원형 버퍼는 큐 말고도 널리 쓰인다 — 오디오 버퍼, 로그 링, 네트워크 수신 버퍼가 전부 같은 구조다.\
  고정 크기로 잡고 오래된 것을 덮어쓰는 변형(overwrite ring)도 흔하다.
- 스택 → 큐 → 덱 순서로 보면 "계약을 넓힐 때마다 구현이 무엇을 더 들고 있어야 하는가"가 한 줄씩 늘어난다.\
  그 증가분이 곧 그 기능의 가격이다.
