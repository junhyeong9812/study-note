# cs/issue/kotlin/spring/serialization-contract-leak — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 객체를 직렬화기에 "그냥 맡기면" 외부에 나가는 JSON 필드명이 **코드 내부의 이름 관례**를 따라가고, 그 순간 내부 표현이 외부 계약으로 새어 나간다 — 계약이 되는 필드는 이름을 명시적으로 고정해야 한다.

```
[누출 경로 — 트리 API]                    [명시 경로 — 다른 API들]
data class ItemRef(val itemType: String)  mapOf("item_type" to meta.itemType, ...)
   │                                          │
   ▼ Jackson 리플렉션 자동 직렬화             ▼ 개발자가 키 이름을 직접 씀
JSON 키 = 코틀린 프로퍼티명 = "itemType"    JSON 키 = "item_type" (계약 그대로)
   │                                          │
   ▼ camelCase가 계약으로 샘 (누출)           ▼ 계약이 코드와 독립 (안전)

같은 응답 규약(snake_case)인데 트리만 달랐다 → 스모크가 doc["item_type"] 파싱 중 KeyError
```

핵심은 **"기본값이 곧 결정"** 이라는 점이다. 직렬화기에 아무 지시도 안 하는 것은 "필드명을 정하지 않음"이 아니라 "필드명을 코드 프로퍼티명에 묶겠다"는 **암묵적 결정**이다. 그 결정이 계약(front가 의존하는 필드명)을 코드 리팩토링에 종속시킨다. `itemType`를 `kind`로 바꾸면 컴파일도 테스트도 통과하는데 **외부 계약만 조용히 깨진다** — 아무도 계약을 검증하지 않기 때문이다.

이것은 **누출 추상화(leaky abstraction)** 의 한 사례다. "객체 ↔ JSON"이라는 추상은 "필드명은 신경 쓰지 마라"인 척하지만, 실제로는 내부 이름 관례가 그대로 밖으로 새어 추상이 감추기로 한 세부를 노출한다. ORM 엔티티를 그대로 API로 반환하거나 DB 컬럼명을 그대로 응답에 싣는 것도 같은 원리다.

방어는 **경계에서 계약을 명시**하는 것이다 — 계약이 되는 필드에 `@JsonProperty("item_type")`처럼 이름을 코드에 고정한다. 그러면 프로퍼티명을 리팩토링해도 계약은 그대로다. 그리고 스모크가 **응답 몸통을 실제로 파싱**해 계약 불일치를 즉시 잡게 한다("200 떴다"만 보면 못 잡는다).

## 핵심 문장

- 직렬화기에 "그냥 맡김" = "필드명을 코드 프로퍼티명에 묶겠다"는 암묵적 결정이다.
- 자동 직렬화는 편한 기본값인 동시에 내부 표현의 누출 — 계약이 코드 리팩토링에 종속된다.
- 계약 위반은 컴파일·테스트를 통과하고 조용히 깨진다(아무도 계약을 검증하지 않으니).
- 방어 = 경계에서 계약 명시(`@JsonProperty`) + 스모크가 상태코드 아닌 필드명·모양을 파싱.
- ORM 엔티티 직반환·DB 컬럼명 노출과 한 원리 — 내부 표현을 외부 계약으로 새게 하지 마라.
