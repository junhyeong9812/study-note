## 질문

1. (왜) data class를 Jackson(또는 아무 리플렉션 직렬화기)에 그대로 던지면 JSON 필드명은 무엇을 따라가는가? 그것이 왜 "편한 기본값"인 동시에 "누출"인가?

2. (경계) 같은 서비스의 다른 API는 `mapOf("item_type" to ...)`로 손수 응답을 조립해 필드명이 계약대로(snake_case) 나갔는데, 트리 API만 camelCase로 샜다. 두 경로의 **구조적 차이**는 무엇이고, 왜 자동 경로만 계약을 깼는가?

3. (연결) "누출 추상화(leaky abstraction)"란 무엇인가? data class → 자동 JSON은 어떤 추상을 어떻게 새게 하는가? 이 함정을 ORM 엔티티를 그대로 API로 반환하는 경우, DB 컬럼명을 그대로 노출하는 경우와 하나의 원리로 묶어 보라.

4. (예측) 자동 직렬화를 그대로 두고 나중에 코드 필드명을 `itemType → kind`로 리팩토링하면 무슨 일이 벌어지는가? 컴파일러·테스트는 이걸 잡아 줄까? 왜 "조용히" 깨지는가?

5. (연결) 이 사건은 스모크 스크립트가 응답 몸통에서 `doc["item_type"]`를 실제로 파싱한 덕에 `KeyError`로 즉시 드러났다. "200이 떴다"만 보는 스모크였다면 어떻게 됐겠는가? 계약 검증의 최소 단위는 왜 "상태코드"가 아니라 "필드명·모양"인가?

6. (경계) "계약이 되는 필드는 이름을 명시적으로 선언한다"를 원칙으로 삼을 때, 어디까지가 계약이고 어디부터는 자동이어도 되는가? 모든 필드에 `@JsonProperty`를 붙이는 것과 무엇이 다른가?
