# cs/issue/kotlin/spring/path-traversal-and-data-reality — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 사용자 경로로 파일을 서빙하는 API는 트래버설을 **처음부터** 닫아야 하고("LAN 전용"은 신뢰 경계가 아니다), 반대로 "버그처럼 보이는 증상"의 절반은 코드 결함이 아니라 **데이터 실태**라 코드를 고치기 전에 원본을 역추적해야 한다.

```
[관문 — /api/doc?path=...]
  ▼
[경로 검사 isSafe]  .md로 끝나나? /·~ 로 시작 안 하나?
                    경로 조각에 ".." · ".git" 없나? 빈 문자열 아닌가?
     ├─ 아니오 ─▶ 422 invalid_request  (트래버설·비md 거절)
     └─ 예    ─▶ 파일 읽기 ─ 없음 ─▶ 404 not_found / I/O 장애 ─▶ 500 봉투

[데이터 실태 역추적 — "빈 본문"이 버그인가?]
  증상: 한글 경로 문서 markdown = ""   ("또 인코딩 버그?"라는 유혹)
  ① 서버 clone 사본:  wc -c → 0바이트,  ES 청크 수 → 0   (일관됨)
  ② 로컬 원본:        wc -c → 0바이트,  0바이트 파일 94개 전수
  ③ rename 이전 커밋: git show <old>:problem.md → 0바이트  ◀ 결정타
  결론: 코드 결함 아님. 원래부터 빈 자리표. 고칠 것 없음.
```

**트래버설 차단:** 경로를 사용자가 주는 순간 "허용 폴더 밖으로 기어 올라가는" 입력(`..`)이 위험이다. 이 `isSafe`는 금지 목록(`..`·`.git` 차단) + 형식 제약(`.md`·절대경로·홈 확장 금지)의 조합이다. 더 견고한 원리는 **허용 목록** — 경로를 정규화(canonicalize)한 뒤 허용 루트의 prefix인지 확인하는 것이다. 금지 목록은 인코딩 변형(`%2e%2e`, 유니코드 우회)을 놓칠 수 있다는 원리적 약점이 있다. 어느 쪽이든 **신뢰 경계는 "입력이 시스템에 들어오는 지점"** 이지 "지금 누가 부르나"가 아니다 — LAN 전용이라도 front를 통해 외부가 들어오므로 처음부터 닫는다.

**데이터 실태:** 증상이 코드 버그처럼 보여도, 코드를 만지기 전에 **입력 데이터가 실제로 어떤 상태인지**부터 확인한다. 여기선 서버 사본 → 로컬 원본 → git 이력 순으로 거슬러 올라갔고, ③(우리 작업 이전 커밋에서도 0바이트)이 "시스템 어디서도 내용을 잃지 않았다 = 원래 빈 파일"을 확정했다. 이 역추적을 건너뛰고 "빈 본문 버그"를 고치러 갔다면 멀쩡한 코드를 망가뜨렸을 것이다.

## 핵심 문장

- 사용자 경로 서빙은 트래버설을 처음부터 닫는다 — 신뢰 경계는 "입력 진입점"이지 "현재 호출자"가 아니다.
- 금지 목록(`..`·`.git`)은 핵심 통로를 막지만, 정규화 후 허용 루트 prefix 확인(허용 목록)이 더 견고하다.
- "버그처럼 보이는 것"의 절반은 데이터 실태 — 코드를 고치기 전에 데이터가 실제로 어떤지 본다.
- 원인 역추적은 산출물→원본 방향으로: 서버 사본 → 로컬 원본 → git 이력.
- "우리 작업 이전에도 그랬나"를 이력으로 확정하면, 우리 변경이 원인일 가능성을 배제한다.
