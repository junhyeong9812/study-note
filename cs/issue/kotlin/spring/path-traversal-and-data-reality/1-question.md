## 질문

1. (왜) 사용자가 준 경로로 파일을 읽어 주는 API에서 `path=../../etc/passwd`류가 왜 위험한가? 경로 트래버설(path traversal)이 성립하는 조건과, "허용 폴더 밖으로 기어 올라간다"는 표현의 의미를 설명하라.

2. (경계) 트래버설 차단을 "금지 목록"(`..`·`.git`을 막음)으로 짜는 것과 "허용 목록"(정규화 후 허용 루트의 prefix인지 확인)으로 짜는 것의 차이는? 이 사례의 `isSafe`는 `.md`로 끝나고, `/`·`~`로 시작 안 하고, 경로 조각에 `..`·`.git`이 없어야 한다 — 이 조합이 왜 핵심 통로를 막는가, 그리고 금지 목록의 원리적 약점은 무엇인가?

3. (왜) "LAN 전용이라 외부에서 못 들어온다"는 이유로 입력 검증을 미뤄도 되는가? 이 API는 이후 front를 통해 외부 요청을 받게 된다 — "신뢰 경계(trust boundary)"는 어디에 그어야 하는가?

4. (왜) 스모크에서 한글 경로 문서의 본문이 **빈 문자열**로 나왔다. 지난번 인코딩 사고 때문에 "또 인코딩 버그인가" 싶었지만, 코드를 고치기 전에 무엇부터 확인했는가? "버그처럼 보이는 것의 절반은 데이터 실태"란 무슨 뜻인가?

5. (예측) 원인을 **서버 사본 → 로컬 원본 → git 이력**의 순서로 거슬러 올라가며 좁혔다. 왜 이 순서인가? 특히 마지막 "우리 rename 이전 커밋에서도 0바이트였나"를 git 이력으로 확정하는 단계가 왜 결정타인가?

6. (연결) 진단 결과 코드에는 결함이 없었고(빈 파일을 정상적으로 "청크 0개 → 건너뜀" 처리 중이었다), 94개 파일이 원래부터 빈 자리표였다. 만약 이 확인을 건너뛰고 곧장 "빈 본문 버그"를 고치러 갔다면 무슨 일이 벌어졌겠는가? 멀쩡한 코드를 고치는 것의 비용은?
