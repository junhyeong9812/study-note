## 질문

1. (왜) 검색 API가 "① llm 질의 재작성 → ② 키워드 검색 + 의미 검색 → ③ 결과 합치기"로 되어 있다. 여기서 불변식은 "llm이 죽든 임베딩 서버가 죽든 검색은 어떻게든 응답한다"였다. 왜 이걸 **불변식**으로 못 박아야 했는가? "보조 기능이 핵심 기능을 인질로 잡는다"는 어떤 실패 모양인가?

2. (경계) 결함 격리(fault isolation)와 우아한 성능 저하(graceful degradation)는 어떻게 다르고 어떻게 함께 작동하는가? "llm 재작성 실패 → 원본 질의로 진행", "임베딩 실패 → BM25 단독"은 각각 어느 쪽인가?

3. (예측) 두 검색기의 점수를 합치는 방법으로 (a) 원점수 그냥 더하기, (b) 각자 최대값으로 정규화 후 더하기, (c) 점수를 버리고 등수만 쓰기(RRF) 중 하나를 골라야 한다. (a)·(b)는 왜 실패하고, (c)가 왜 "한쪽 랭킹이 통째로 비어도 수식이 그대로 성립"하는가? 이 성질이 폴백과 왜 궁합이 좋은가?

4. (왜) llm이 rewrite에서 `filters.doc_kind = "question"`을 제안했고, 그걸 하드 필터로 적용하니 답 문서가 전멸했다. "약한 모델의 구조화 출력은 참고 자료지 결정권자가 아니다"를 이 사건으로 설명하라. 제안을 **버리지 않되 로그로만 축적**한 이유는?

5. (연결) 리뷰어 둘 다 "rewrite 제안을 쓰라"고 했는데 실측해 보니 제안을 쓰는 것 자체가 해로웠다. "리뷰는 설계와 코드의 불일치는 잡지만 설계 자체의 유해함은 실측만 잡는다"는 무슨 뜻인가?

6. (경계) 폴백이 동작했다는 것을 사용자·호출자가 알아야 할까? 응답에 `rewrite_used`·`dense_used` 같은 **상태 뱃지**를 싣는 이유는? "조용히 강등"과 "시끄럽게 강등"의 차이, 그리고 이것이 silent failure와 어떻게 연결되는가?
