## 질문

1. (왜) 파일을 다른 폴더로 옮겼더니 `import { log } from "./logger"` 같은 **상대 임포트**만 깨지고, `@/lib/logger` 같은 **절대(alias) 임포트**는 안 깨졌다. 왜 이런 차이가 나는가? 상대 임포트의 "기준점"이 무엇이기에 파일이 이사하면 깨지는가?

2. (경계) 일괄 치환(codemod)으로 임포트를 고쳤는데도 상대 임포트 잔재가 남아 빌드가 세 번에 걸쳐 깨졌다. 치환 도구가 절대 경로는 바꾸고 상대 경로는 못 바꾼 이유는 무엇인가? "고치고-빌드-고치고를 3회 반복"의 **근본 원인**은 개별 실수인가 정책 부재인가?

3. (예측) "같은 폴더 안이라도 상대 임포트를 쓰지 않고 절대경로(`@/...`)만 쓴다"를 정책으로 못 박으면 무엇을 얻는가? 이 정책이 방어하는 미래의 사고는 구체적으로 무엇인가?

4. (왜) 임포트를 `@/`로 바꾸자 빌드와 타입체크는 통과하는데 **테스트 러너(vitest)만** "모듈을 못 찾음"으로 죽었다. `@` alias는 `tsconfig.json`의 `paths`에 분명히 있는데 왜 한 도구만 못 찾았는가?

5. (연결) `@/foo` 같은 임포트 문자열을 실제 파일 경로로 바꿔주는 부품을 **리졸버(resolver)** 라 한다. "alias는 프로젝트 설정이 아니라 도구마다의 설정"이라는 문장을 리졸버 개념으로 설명하라. 빌드·타입체크·테스트 러너가 각자 무엇을 읽는가?

6. (경계) `tsconfig.json`의 `paths`는 정확히 누가 읽는 설정인가? 그것이 "런타임에 실제로 모듈을 찾는 방법"을 정의하는가, 아니면 다른 역할인가? (힌트: `moduleResolution: "bundler"`, `noEmit: true`)

7. (연결) 이 이슈는 두 원리가 한 세트다 — ①절대경로 임포트 정책, ②도구마다 alias를 따로 알려주기. 왜 이 둘이 붙어 다니는가? ①을 채택하는 순간 ②가 왜 필연적으로 따라오는가?
