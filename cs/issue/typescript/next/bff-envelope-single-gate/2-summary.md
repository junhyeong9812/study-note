# cs/issue/typescript/next/bff-envelope-single-gate — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 모든 응답이 `{success, data|error}` 봉투로 오면, 봉투 검사를 호출처마다 반복하지 말고 **반드시 거쳐야 하는 창구 하나**에서만 열어 정규화한다 — 그러면 "검사를 잊어 오류를 정상 데이터로 그리는" 사고가 구조적으로 불가능해진다.

봉투를 호출처마다 여는 방식은 이렇게 무너진다.

```
[페이지마다 봉투 검사]
  page A ─▶ if(body.success) data else error   ✅ 검사함
  page B ─▶ body.data 바로 사용                  ❌ success 검사 잊음
                     │
                     ▼
        오류 봉투({success:false})의 data(=undefined/에러객체)를
        정상 데이터인 척 화면에 렌더 → 조용한 사고(silent failure)
```

호출처가 N개면 "빠뜨릴 자리"도 N개다. 한 곳만 잊어도 그 페이지가 오류를 정상처럼 그린다. 이건 중복 코드 문제가 아니라 **잊을 수 있는 검사를 잊을 수 없게** 만드느냐의 문제다.

```
[단일 창구 apiGet — 봉투를 여기서만 연다]
  page A ─┐
  page B ─┼─▶ apiGet(path) ─▶ ① 네트워크 실패      → throw ApiError(503)
  page C ─┘        │              ② 봉투 아님          → throw ApiError(invalid_envelope)
                   │              ③ success=false      → throw ApiError(code)
                   ▼              ④ success=true       → return data (T)
             페이지는 data(T)만 받는다 — 봉투의 존재조차 모른다
```

세 실패 경우(네트워크·비봉투·오류봉투)를 모두 **예외 하나로 정규화**하니, 호출처는 "성공하면 data가 온다"만 알면 된다. 검사를 "안 하는" 게 아니라 검사를 **한 곳에 가둔** 것이다.

이 창구는 **BFF**(브라우저와 진짜 백엔드 사이의 전용 중간 서버) 안에 있다. 브라우저는 백엔드를 직접 모르고 BFF만 부르므로, 봉투 정규화를 여기 두면 "외부 노출 지점 = 검증 지점"이 하나로 겹친다. 신뢰 경계에서 한 번 검증하는 고전 원칙의 프론트엔드판이다.

부수로 두 가지가 같이 나온다.

- **가장 위험한 가정 먼저 실증**: 이 뼈대가 서는 자리(엣지 리버스 프록시 설정 재활용)가 틀리면 이후 전부가 재설계다. 그래서 배포 직후 **엣지를 통한 실호출부터** 확인했다(무수정 재활용이 200으로 통과). 가정을 맨 앞에서 깨뜨려 보면, 틀렸을 때 버리는 작업량이 최소다.
- **로그는 요청을 인질로 잡지 않는다**: 창구가 로그도 남기지만 로그 저장소가 죽어도 요청은 진행한다. 단일 창구에 부수 기능(로깅)을 얹되, 그 부수 기능의 실패가 본 기능(데이터 조회)을 막지 않게 격리한다.

## 핵심 문장

- 봉투 검사를 호출처마다 하면 "한 곳만 잊어도" 오류가 정상 데이터로 렌더된다 — 잊을 수 있는 검사는 잊을 수 없게 만든다.
- 방어는 검사를 없애는 게 아니라 **반드시 거치는 창구 하나에 가두는 것**(검증 DRY).
- 창구는 세 실패(네트워크·비봉투·오류봉투)를 **예외 하나로 정규화**해, 호출처가 "성공하면 data"만 알게 한다.
- BFF = 유일한 외부 노출 지점 = 봉투 정규화 지점. 신뢰 경계에서 한 번 검증하는 원칙과 같다.
- 가장 위험한 가정(엣지 재활용)은 맨 앞에서 실호출로 깨뜨려 본다 — 틀렸을 때 버릴 작업을 최소화.
- 창구에 로깅을 얹되, 로그 실패가 요청을 막지 않게 격리한다.
