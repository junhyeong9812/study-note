## 질문

1. (왜) 구독 함수가 해제 함수를 **Promise로** 돌려준다(`listen(...)` → `Promise<unlisten>`). effect cleanup에서 `unlisten?.()`만 부르면 왜 리스너가 남을 수 있는가? cleanup과 resolve의 실행 순서로 설명하라.

2. (예측) 개발 모드 StrictMode는 effect를 mount → unmount → mount로 두 번 돌린다. 위 구독 코드에 방어가 없으면 이벤트 하나에 콜백이 몇 번 불리는가? 증상이 "정확히 2배"로 나오는 이유는?

3. (경계) `disposed` 플래그 방식(`then(f => disposed ? f() : (un = f))`)과 cleanup에서 promise 자체를 해제하는 방식(`un.then(f => f())`)은 각각 무엇을 보장하는가? await가 **여러 번**(연결 생성 await → 구독 await) 있는 effect에서는 무엇을 더 해야 하는가?

4. (연결) 비동기 작업 결과(원격 연결·attach)가 늦게 도착했을 때 "받을 주인이 아직 유효한가"를 판정하는 **세대(generation) 번호**는 disposed 플래그와 무엇이 같고 무엇이 다른가? 닫기·언마운트도 세대를 올려야 하는 이유는?

5. (경계) 구독 **등록 자체가 실패**하면 무엇이 남는가? "이벤트가 구독보다 먼저 온 경우"만 다루고 "구독 실패"를 다루지 않으면 어떤 화면·자원 상태가 생기는가?

6. (연결) 재할당 가능한 disposable(레이아웃 변경 리스너·드래그 제스처 리스너)을 다시 설치할 때 **이전 것을 먼저 해제**하지 않으면 어떤 버그가 나는가? AbortController 하나로 제스처의 리스너를 묶는 방식은 이것을 어떻게 막는가?

7. (연결) 명령형 라이브러리 인스턴스(차트·에디터)를 선언형 렌더 위에서 다시 만들 때의 수명 관리는 이 카드의 원리와 어떻게 이어지는가? 실패한 promise를 캐시하면 왜 "영구 실패"가 되는가?
