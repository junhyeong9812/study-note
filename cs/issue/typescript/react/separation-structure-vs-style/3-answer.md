## 정답

<!-- 질문 1:1 대응 -->

1. 선이 안 보인 건 렌더러의 **버그가 아니다.** react-markdown(remark-gfm)은 마크다운 표를 `<table>`·`<th>`·`<td>` 같은 **HTML 구조로 바꾸는 것까지**가 자기 일이고, 그것을 정확히 해냈다. 그 이상(색·선 같은 표시)은 하지 않는다. 그리고 브라우저의 기본 `<table>` 스타일에는 테두리가 없다. 즉 렌더러는 자기 책임(구조 생성)을 다 했고, 빠진 것은 **표시(스타일)** 였다 — 이건 렌더러 결함이 아니라 소비자 쪽 스타일 부재다.
   > **remark-gfm** — 마크다운에 GitHub식 표·체크박스 등을 더해주는 플러그인. 표를 `<table>` 구조로 바꿔주지만 색·선 같은 스타일은 손대지 않는다.

2. 렌더러가 **한 일** = 마크다운 표 문법을 `<table>`/`<th>`/`<td>`라는 HTML 구조로 변환(구조 생성). 렌더러가 **안 한 일** = 그 구조가 화면에 어떻게 보일지(테두리·배경·간격) 정하는 것. 브라우저의 기본 `<table>` 스타일은 이 그림에서 "표시 층의 기본값"에 해당하는데, 그 기본값이 하필 "테두리 없음"이라 우리가 표시를 안 채우면 선이 없는 상태가 된다. 즉 표시 층 = 브라우저 기본값 + 우리 CSS인데, 우리 CSS가 비어 기본값(선 없음)이 그대로 나온 것이다.

3. 진짜 원인이 "스타일 부재"라면 고칠 곳은 **CSS**지 렌더러 설정이 아니다. 전역 `.markdown table` 규칙을 넣으면 모든 표에 일괄 적용되는 이유는, CSS 선택자가 "이 클래스 아래의 모든 `table`"이라는 **패턴**으로 매칭하기 때문이다 — 표마다 개별 스타일을 붙이는 게 아니라, "마크다운 렌더 영역(`.markdown`) 안의 표는 이렇게 보인다"를 **소비자 층에서 한 번** 선언하면, 렌더러가 언제 몇 개의 표를 만들든 전부 그 규칙을 받는다. 표시를 콘텐츠가 아니라 소비자 층에 두는 것의 이점이다.

4. 일반 원칙: **"구조를 만드는 층과 표시를 정하는 층을 분리하면, 각 층을 독립적으로 바꿀 수 있다"**(관심사 분리). 얻는 것: 렌더러(구조)는 표시를 몰라도 되고, CSS(표시)는 구조가 어떤 콘텐츠에서 왔는지 몰라도 된다 — 표시를 바꿔도 렌더러를 안 건드리고, 콘텐츠가 늘어도 스타일은 그대로 적용된다. **잊기 쉬운 함정**: 층을 나눴으면 **각 층이 자기 절반을 반드시 채워야** 하는데, "렌더러가 구조를 만들었으니 끝"이라고 착각해 표시 절반을 비워두면, 아무도 버그를 낸 적 없는데 결과가 불완전하다. 분리는 책임을 나누는 동시에 "각자 자기 몫을 채울 의무"를 만든다.
   > **관심사 분리(separation of concerns)** — 서로 다른 성격의 일(구조 생성 vs 표시 결정)을 다른 층/모듈이 맡게 나누는 설계 원칙. 각 층은 독립적으로 바뀔 수 있지만, 각자 자기 책임을 빠짐없이 채워야 전체가 완성된다.

5. `border-collapse: collapse`는 **인접한 셀의 테두리를 하나의 선으로 겹쳐 합친다.** 기본값 `separate`에서는 각 셀이 자기만의 테두리를 갖고 셀 사이에 간격(border-spacing)이 있어, 두 셀이 맞닿으면 각자의 테두리가 나란히 그려져 **선이 이중(두 줄)**으로 보인다. `collapse`는 맞닿은 두 셀의 테두리를 하나로 병합해, 셀과 셀 사이에 한 줄만 남게 한다. 그래서 표에 격자를 그릴 때는 보통 `collapse`를 준다.
   > **border-collapse** — 표의 인접 셀 테두리를 겹쳐 하나의 선으로 합칠지(`collapse`), 각자 따로 둘지(`separate`, 기본값) 정하는 CSS 속성. `separate`면 선이 이중으로 보인다.

6. `display: block; overflow-x: auto`를 표에 주면, 표가 자기 폭이 넘칠 때 **자기 안에서만** 가로 스크롤바를 갖는다. `display: block`으로 표를 블록 상자로 만들고 `overflow-x: auto`로 "내 콘텐츠가 내 폭을 넘으면 나만 가로 스크롤"하게 하면, 넘치는 표가 페이지의 다른 요소나 뷰포트를 밀지 않는다. 즉 넘침을 **표라는 스크롤 컨테이너에 격리**하는 것이다 — css-negative-margin-overflow 패턴의 "넘치는 요소(긴 코드블록·넓은 표)는 자기 `overflow-x: auto` 컨테이너에 담아 격리한다"와 정확히 같은 원리다. 페이지는 안 밀리고, 넓은 표만 필요할 때 옆으로 스크롤된다.

7. "렌더러 버그가 아니라 스타일 부재"라는 진단이 중요한 이유는, **원인을 엉뚱한 책임 경계에서 찾으면 헛되이 판다**는 데 있다. 이걸 렌더러 문제로 오진했다면 remark-gfm 옵션, 플러그인 교체, `<table>` 생성 로직 같은 **구조 층**을 파느라 시간을 버렸을 것이다 — 그런데 구조는 멀쩡했다(`<table>`이 정상 생성됨). 원인을 먼저 "구조의 문제인가, 표시의 문제인가"라는 책임 경계로 나누면, "구조는 있나?"에 "있다"가 나오는 순간 표시 층으로 좁혀진다. 관심사 분리는 코드를 나누는 설계 원칙일 뿐 아니라, **버그의 소재를 좁히는 진단 렌즈**로도 쓰인다.
