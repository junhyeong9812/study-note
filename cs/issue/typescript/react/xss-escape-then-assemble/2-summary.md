# cs/issue/typescript/react/xss-escape-then-assemble — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 강조를 위해 백엔드가 만든 HTML(`<mark>…</mark>`)을 그대로 꽂으면 노트 본문의 HTML까지 실행돼 XSS가 되므로, 강조 위치를 **일반 입력으로는 안 나올 마커**(`⟦m⟧…⟦/m⟧`)로 받아 텍스트를 통째로 이스케이프한 뒤 마커 위치에만 `<mark>` React 요소를 조립한다 — HTML 문자열을 삽입하는 경로 자체가 없어 XSS가 구조적으로 불가능해진다.

### 탈락 — 백엔드 HTML을 그대로 꽂기

```
[탈락] backend → "<mark>정렬</mark>정렬 알고리즘 <script>…</script>"
         front → dangerouslySetInnerHTML 로 그대로 삽입
       노트 본문의 <script> 도 브라우저가 HTML로 해석·실행 → XSS
```

`dangerouslySetInnerHTML`은 React가 평소 텍스트에 자동으로 해주는 이스케이프(`<`→`&lt;` 등)를 **끄고** 문자열을 날 HTML로 넣는 통로다. 그래서 강조를 위해 이걸 쓰는 순간, 강조뿐 아니라 본문에 섞인 모든 HTML이 실행 대상이 된다.

### 채택 — 마커 프로토콜: escape → assemble

```
[채택]
  backend (ES highlight)  pre_tags="⟦m⟧"  post_tags="⟦/m⟧"
     → "⟦m⟧정렬⟦/m⟧ 알고리즘 <script>x</script>"   (HTML 아님, 그냥 텍스트)
  front renderMarked:
     ① 텍스트를 "⟦m⟧"/"⟦/m⟧" 로 split (문자열 쪼개기)
     ② 조각들을 React 요소로 조립: 일반 조각은 텍스트(React가 이스케이프),
        마커 안 조각만 <mark>{marked}</mark>
     → 화면: [정렬](강조) 알고리즘 <script>x</script>  ← <script>가 "글자"로 보임
```

핵심은 **React에 문자열을 텍스트로 넣으면 React가 자동 이스케이프**한다는 것. `renderMarked`는 HTML을 만들지 않고 React 요소 배열을 만들 뿐이라, 본문의 `<script>`는 이스케이프돼 실행이 아니라 표시된다. 강조는 우리가 통제하는 `<mark>` 요소로만 들어가므로, "주입 가능한 HTML"이 애초에 존재하지 않는다.

### 마커의 조건 · 책임 분담 · 디바운스

- **마커 조건**: 일반 입력으로는 안 나올 문자여야 한다(여기선 `⟦ ⟧` 특수 괄호). 만약 본문에 진짜로 `⟦m⟧`가 있으면 오탐(엉뚱한 강조)이 생길 수 있으나, 그래도 **HTML 실행 위험은 없다**(여전히 텍스트로 이스케이프됨) — 최악이 "잘못된 강조"지 "코드 실행"이 아니라는 게 이 설계의 강함.
- **책임 분담**: 백엔드는 "어디가 일치인가"를 마커로만 표시(HTML을 만들지 않음), 프론트는 "이스케이프 후 마커→`<mark>` 조립". 강조라는 한 기능이 두 서비스에 걸친 **프로토콜**이고, 백엔드가 HTML을 만들지 않는 게 분담의 핵심.
- **디바운스**: 자동완성은 키 입력마다 호출될 수 있어, 입력이 멈추고 200ms 뒤에만 요청(타자마다 요청 쏟아짐 방지). XSS 방어(정확성)와 디바운스(부하)는 다른 축이지만, 사용자 입력을 실시간으로 다루는 기능엔 둘 다 필요하다.

## 핵심 문장

- 백엔드 HTML을 `dangerouslySetInnerHTML`로 꽂으면 본문의 HTML까지 실행 → XSS.
- 대안: 강조 위치를 **안 나올 마커**로 받아, 텍스트 전체 이스케이프 후 마커 위치에만 `<mark>` 요소 조립.
- 순서가 방어다 — **escape 먼저, assemble 나중**. React에 텍스트로 넣으면 자동 이스케이프되므로 HTML 주입 경로가 없다.
- 마커는 일반 입력에 안 나올 문자여야 하고, 설령 오탐이 나도 최악은 "잘못된 강조"지 "코드 실행"이 아니다.
- 강조는 백엔드(마커 표시)·프론트(이스케이프+조립)의 프로토콜 — 백엔드가 HTML을 만들지 않는 게 핵심.
- 디바운스(200ms)는 XSS와 다른 축(부하)의 방어 — 실시간 입력 기능엔 정확성·부하 방어가 함께 필요.
