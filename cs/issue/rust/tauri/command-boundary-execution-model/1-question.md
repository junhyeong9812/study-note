## 질문
1. (예측) 최대 120초 걸리는 외부 프로세스 호출을 Tauri 동기 커맨드(`fn`)에 두었다. 프런트엔드가 이 커맨드를 부르면 창 전체에 무슨 일이 일어나는가? 동기 커맨드와 async 커맨드는 각각 어느 스레드에서 실행되는가?
2. (경계) 커맨드를 `async fn`으로만 바꾸고 본문은 그대로 블로킹 표준 호출을 두면 문제가 해결되는가? `spawn_blocking`은 무엇을 추가로 해 주는가? 선택지 셋(동기 fn · async + 직접 블로킹 · async + spawn_blocking)의 순위를 매겨라.
3. (왜) 동기 커맨드가 bounded async 채널에 `blocking_send`로 입력을 보낸다. 소비자인 네트워크 루프가 호스트 키 확인을 기다리거나 연결 중이면 호출자에게 무슨 일이 일어나는가? "소비자의 지연이 호출 스레드로 전파된다"를 설명하라.
4. (경계) `try_send`로 바꾸면 절대 막히지 않는다. 대신 무엇을 포기하고, 그것을 어떻게 보완했는가(입력 큐 버퍼·resize 최신값 병합·상태 이벤트)?
5. (왜) 커맨드 경계에서 스레드 생성 실패를 `expect`로 처리했다. "커맨드 경계에서 panic 금지"라는 정책은 왜 필요한가? panic과 `Result`는 호출자(프런트엔드)에게 각각 무엇을 전달하는가?
6. (연결) `spawn_blocking`의 `JoinError`를 앱 에러로 매핑한 것과, 스레드 생성 실패를 `io::Result`로 전파한 것은 같은 원칙이다. 그 원칙은 무엇이고, 이 카드의 "블로킹을 UI 스레드 밖으로"와 어떻게 한 쌍을 이루는가?
