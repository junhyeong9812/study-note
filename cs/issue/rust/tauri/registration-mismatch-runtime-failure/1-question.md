## 질문
1. (왜) 데스크톱 앱 프레임워크의 **정적 capability**(빌드 시 바이너리에 박히는 권한 목록)에 창 열거 권한이 빠지자, 팝업도 에러 메시지도 없이 드래그아웃·도킹 기능이 **둘 다** 죽었다. 권한 하나 누락이 왜 "에러 표시"가 아니라 "기능 전체의 무음 사망"으로 나타났는가? 런타임 승인 절차가 없다는 사실과 호출부의 예외 처리를 함께 설명하라.
2. (경계) capability를 메인 창 파일에만 선언하고 팝아웃 창 파일에는 빠뜨렸다. 메인 창에서는 알림이 잘 되는데 팝아웃 창에서만 조용히 실패한다 — 권한이 "앱 단위"가 아니라 "창 라벨 패턴 단위"라는 것이 무엇을 뜻하는가?
3. (예측) 타입 키(TypeId)로 상태를 찾는 DI 컨테이너에 `manage(T)`로 등록하고, 커맨드는 `State<Arc<T>>`를 요구한다. 컴파일은 되는가? 단위 테스트는 통과하는가? 실제 앱에서 커맨드를 부르면 무엇이 일어나는가?
4. (왜) 3번의 결함을 **모든 테스트가 놓친** 이유는 무엇인가 — 테스트가 커맨드를 "평범한 함수"로 직접 부르는 것과 "DI 계층을 거쳐 invoke"하는 것은 무엇이 다른가?
5. (연결) 두 사건(권한 목록 누락, 타입 키 불일치)은 도메인이 전혀 다른데 한 패턴으로 묶인다. "선언과 사용이 서로 다른 곳에 있고, 둘을 대조하는 장치가 컴파일러에 없다"를 공통 구조로 설명하라. 그러면 재발 방지 장치는 어디에 둬야 하는가?
6. (경계) 권한을 추가한 뒤에도 호출부를 try/catch로 감싸 "열거 실패 → null(=새 창)"로 폴백하게 했다. 이것은 실패를 삼키는 silent failure를 새로 만드는 것 아닌가? 이 폴백이 정당한 조건은 무엇인가?
7. (연결) 권한 요청 API는 사용자 제스처 문맥과 요청 1회성을 요구한다. "요청은 in-flight Promise 하나를 공유하고, 거부·실패는 캐시해 발화 경로에서 재시도하지 않는다"는 설계가 막는 사고는 무엇인가?
