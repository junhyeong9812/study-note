## 질문
1. (왜) 데스크톱 GUI 프레임워크를 의존하는 크레이트 안에 있는 순수 함수(디렉터리 읽기)의 에러 경로를 헤드리스 CI에서 단위 테스트할 수 없었다. 함수 자체는 GUI와 무관한데 왜 테스트가 막히는가? "링크 단계"라는 말로 설명하라.
2. (경계) 이 문제와 이후 비동기 코드 격리에서 검토한 선택지는 셋이었다 — 그 자리에서 mock, 순수 크레이트 안에 feature-gated 모듈, 별도 크레이트로 분리. 앞의 둘은 왜 문제를 풀지 못하는가?
3. (예측) 2,000줄짜리 모듈 파일을 하위 모듈로 쪼갠다. (a) 부모가 자식의 private 헬퍼를 부르면? (b) 형제 모듈이 서로의 private 필드를 가진 struct를 생성하면? (c) 외부에서 쓰던 `crate::big::Item` 경로는? 각각 어떻게 되고 어떻게 해결하는가?
4. (검증) 순수 이동 리팩토링에서 "동작이 보존됐다"를 무엇으로 증명할 수 있는가? 공개 항목 집합·테스트 개수·매크로 컴파일은 각각 무엇을 보장하는가?
5. (예측) 워크스페이스에 `core`라는 이름의 로컬 크레이트를 만들었다. 이 크레이트를 의존하는 쪽에서 `use core::...`를 쓰면? 또 serde/clap derive나 `async-trait` 같은 절차 매크로를 쓰면 왜 "could not find marker/option in core" 류의 오류가 나는가?
6. (경계) 이름 충돌을 피하는 방법은 둘이다 — 라이브러리 타깃 이름을 바꾸기(`[lib] name`), 의존하는 쪽에서 별칭으로 들여오기(`alias = { package = "core" }`). 각각 누구에게 효과가 있고, 같은 패키지의 bin 타깃은 어느 쪽으로 해결되는가?
7. (연결) 이 세 가지(링크 의존·모듈 privacy·extern prelude 이름)는 모두 "컴파일러·빌드 도구의 규칙이 코드 구조를 결정한다"는 공통점이 있다. 이 규칙을 설계 신호로 읽으면 어떤 구조가 권장되는가?
