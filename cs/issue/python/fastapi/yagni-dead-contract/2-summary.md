# cs/issue/python/fastapi/yagni-dead-contract — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 예측으로 미리 만들어 둔 "예약 계약"(로직 없이 501만 주는 자리)은 현재 수요가 0이고 미래 수요도 불분명하면 유지비만 남기므로, 계약 자체는 지우고 **왜 지웠는지 결정의 흔적만** 설계 문서에 남긴다.

```
[예약석의 일생]
  issue1 : "나중에 소비자 수정 없이 켜자" → /digest 계약만 예약
           POST /digest ──▶ 501 {"success":false,"error":{"code":"not_implemented"}}
           (구현 0. 그러나 설계 D2에 입출력 계약 + domain 모델 3형 + 테스트 2건은 존재)
                     │
                     │  명분 재검토: 그 '나중'의 소비자 둘을 실제로 따져봄
                     ▼
   ┌───────────────────────────────────────────────┐
   │ 사람용 검색 : 목적이 "인출 학습"                 │  → 자동 요약은 목적과 정면 충돌
   │ MCP(Claude) : 소비자가 이미 강한 모델            │  → 8B 요약은 정보를 깎을 뿐
   └───────────────────────────────────────────────┘
           현재 수요 0 · 미래 수요도 불분명  → 명분 소멸
                     │
                     ▼
  issue5 : POST /digest ──▶ 404 (그런 경로 없음)
           핸들러·도메인 모델 3형·에러코드·테스트 = 삭제
           설계 D5에 "왜 지웠나"만 남김  ← 결정의 흔적은 지우지 않는다
```

**핵심 판단 = 명분의 검증.** 예약석의 유일한 명분은 "미래 소비자를 위해"였는데, 그 미래 소비자(사람용 검색 / MCP)를 하나씩 실제로 따져보니 둘 다 이 기능을 원하지 않았다 → 명분이 근거 없이 소멸.

**비용은 "낮다"지 "0"이 아니다.** 로직이 없어도 설계 문서·README·테스트가 계속 이 계약을 *설명*해야 하고, 읽는 사람(미래의 나)이 "이건 뭐지"를 반복해서 묻는다. 그리고 지금 상상해 고정한 입출력 모양은 정작 필요해지는 날엔 틀린 모양일 공산이 크다 — **틀린 예약석은 없느니만 못하다.**

**역설:** "지우기 쉬웠다"(삭제가 곧 끝)는 사실이, 그 예약석이 아무것도 지탱하지 않는 순수 비용이었다는 증거다. 아무도 안 쓰니까 아무것도 안 깨지고 지워진다.

**지운 것 ↔ 남긴 것.** 실행되는 계약(핸들러·모델·코드·테스트)은 전부 지운다. 그러나 "이 자리를 왜 없앴나"라는 *결정의 근거*는 D5에 남긴다 — 다음에 누가 같은 걸 또 예약하려 할 때 되풀이를 막는 기록이기 때문이다.

## 핵심 문장

- YAGNI: 미래를 위해 미리 만들어 두는 것을 경계한다 — 예측으로 만든 것은 대개 틀린 모양이다.
- 로직 없는 예약 계약도 유지비는 0이 아니다: 문서·테스트가 설명해야 하고, 읽는 이가 반복해서 되묻는다.
- 명분("나중에 켠다")은 그 '나중'의 소비자가 실제로 원하는지 확인해야 유효하다 — 소비자가 안 원하면 명분 소멸.
- "지우기 쉬웠다"는 예약석이 아무것도 지탱하지 않는 순수 비용이었다는 증거다.
- 계약은 지우되 결정의 흔적(왜 지웠나)은 남긴다 — 되풀이를 막는 기록.
