## 질문

1. (왜) 모든 응답을 `success` 깃발이 달린 하나의 봉투(envelope)로 통일하기로 했다. 그런데 라우터 함수의 모든 `return`을 봉투 공장에 통과시켰는데도 봉투 규약이 새는 경로가 남는다. 왜 "내 핸들러 코드를 다 고치는 것"만으로는 응답 계약이 완결되지 않는가?

2. (경계) FastAPI에서 pydantic 입력 검증이 실패하면, 그 응답은 **언제·누가** 만드는가? 내가 라우터 함수 안에 써 둔 `try/except`가 그 실패를 못 잡는 이유는 무엇인가? "라우터 함수에 진입하기 전"이라는 시점이 왜 결정적인가?

3. (예측) 소비자(backend)가 `body["success"]` 하나로 분기하도록 짰다고 하자. 그런데 입력 검증 실패 한 경로만 `{"detail": [...]}`라는 다른 모양으로 응답한다면, 소비자 쪽에서 무슨 일이 벌어지는가? "정규화의 값어치는 예외 없이 전부에서 나온다"를 이 상황으로 설명하라.

4. (연결) 이 구멍을 막은 방법은 전역 예외 핸들러(`@app.exception_handler`)로 그 경로를 **다시 가로채** 같은 봉투로 바꾸는 것이었다. 검증 실패(422)뿐 아니라 프레임워크가 내 코드 밖에서 만드는 다른 응답들(404 없는 경로, 500 미처리 예외)에도 같은 처방이 통한다. 이 처방의 일반형은 무엇인가?

5. (경계) 봉투를 씌우면서도 HTTP 상태코드(200·503·422)는 **그대로 남겼다**. 왜 상태코드와 봉투를 둘 다 유지하는가? 둘을 읽는 주체가 각각 누구인가?

6. (경계) 이 서버에는 봉투를 **일부러 안 씌운** 경로가 둘 있다 — `/health`(docker healthcheck)와 `/chat`의 스트리밍 본문(text/plain 청크). 정규화를 하기로 해 놓고 예외를 두는 것이 왜 틀린 게 아닌가? "규약에서 빼는 것"과 "규약이 새는 것"은 어떻게 다른가?

7. (연결) "프레임워크가 내 코드 바깥에서 만들어주는 응답이 늘 계약의 구멍이다"를 일반 원리로 확장하라. 봉투 정규화 말고, 로깅·인증·트레이싱 같은 다른 횡단 관심사에서도 같은 함정이 어떻게 나타나는가?
