# cs/issue/python/fastapi/handler-execution-model — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[요청] ──▶ 미들웨어 스택 (나중에 add 한 것이 바깥 = 먼저 실행, LIFO)
              │  add(Auth) add(RateLimit) add(Block) add(Context)
              │  실행: Context → Block → RateLimit → Auth
              │  💥 client_ip 를 Auth(마지막)만 채움 → 앞은 "unknown" 공유 키
              ▼
          핸들러 종류로 실행 장소가 갈린다
   ┌──────────────────────────────┬───────────────────────────────────┐
   │ def handler                   │ async def handler                   │
   │  → 스레드풀 워커에서 병렬       │  → 이벤트 루프 스레드에서 직접        │
   │  💥 check(stat) ─┐ 틈 ┌─ act   │  💥 안에서 동기 I/O(sync client)    │
   │     다른 요청이 끼어듦 (TOCTOU) │     = 루프 전체 정지                  │
   │  교정: 검사+행동을 한 락 안에   │     다른 요청 전부 대기 → 타임아웃     │
   │        (결정~등록까지 전부)     │  교정: await async client           │
   │                                │        / to_thread 오프로드          │
   │                                │        (workers↑ 는 우회)            │
   └──────────────────────────────┴───────────────────────────────────┘

[시점·경로가 다르면 존재하는 것이 다르다]
   앱 구성 시점: add_middleware 로 스택 빌드   (lifespan 자원은 아직 없음)
   lifespan 시점: 자원 생성 → app.state 에 저장 → 미들웨어가 요청 때 동적 참조
   HTTP 요청 경로: Request 스코프 존재
   이벤트 핸들러 경로(HTTP 밖): Request 없음 → 요청 스코프 의존 체인 실패
```

## 핵심 문장

- `def` 핸들러는 **스레드풀에서 병렬**로 돈다 — 단일 프로세스여도 check-then-act는 경쟁한다. 검사부터 등록까지 **한 임계구역**으로 묶는다.
- `async def` 핸들러는 **이벤트 루프 스레드에서 직접** 돈다 — 그 안의 동기 I/O는 호출 체인 몇 단계 아래에 있어도 루프 전체를 멈춘다.
- 교정 우선순위: async 클라이언트로 전환(근본) > 스레드 오프로드(동기 라이브러리밖에 없을 때) > 워커 수 증가(우회 — 워커 하나 안의 정지는 그대로).
- Starlette 미들웨어는 **나중에 등록한 것이 먼저 실행(LIFO)** — 뒤 단계가 쓸 상태는 가장 먼저 실행되는 미들웨어가 채운다.
- 미들웨어 스택은 **앱 구성 시** 빌드되고 lifespan 자원은 **그 뒤에** 생긴다 → 요청 시점에 `app.state`로 동적 참조한다.
- 요청 스코프 의존성은 **HTTP 요청 경로에만** 있다 — 이벤트 핸들러 같은 HTTP 밖 경로에서는 존재하지 않는다.
