# cs/issue/search-engine/mapping-is-schema — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[색인 시점]  문서 ──▶ 분석기(생성 시 매핑) ──▶ 역색인 토큰 저장   ← 이 순간에 표현이 굳는다
[이후]       매핑·분석기 코드를 바꿔도 ─▶ 이미 저장된 토큰은 다시 분석되지 않음
             기존 필드의 분석기·타입 변경 ─▶ PUT _mapping 거부 (새 필드 추가·search_analyzer 등 일부 파라미터는 가능)
             multi-field 서브필드      ─▶ 추가만 가능, 제거 불가 (재색인 전까지 dead weight)

[정의가 둘]  초기화 JSON ─┐
             앱 문서 클래스 ─┴─▶ "없으면 생성" 부트스트랩 ─▶ 먼저 만든 쪽이 승자
                                   └ 인덱스가 있으면 매핑 갱신 스킵 → 옛 매핑 유지 (조용히)

[타입 강제]  date 매핑 포맷 밖 값 1건 ─▶ 그 문서 거부 (bulk는 항목별 실패 — 값이 전 문서에 있으면 사실상 전량 실패)
             명시 없는 필드 ─▶ date detection이 첫 값으로 타입 고정 ─▶ 이후 값 거부
             dynamic:strict ─▶ 누락 OK · 미정의 필드 write ─▶ 거부

[교정 절차]
   정의 단일화 (한 JSON을 정본으로 · 사본은 byte 동일 계약 테스트)
        │
        ▼
   새 인덱스(신 매핑) ─▶ 재색인 ─▶ 표본 검증 ─▶ alias 스왑 ─▶ 옛 인덱스 보존(롤백용)
        │
        ▼
   가드: _meta.schema_version ≠ 코드 상수 → throw (모든 호출부가 전파해야 유효)
```

## 핵심 문장

- 기존 필드의 매핑은 **생성 시점에 고정되는 스키마**다(새 필드 추가와 일부 파라미터 변경만 가능) — 역색인 토큰은 색인할 때 한 번 계산된다.
- 분석기·매핑을 바꾸면 **재색인**이 필요하다 — 무중단은 새 인덱스 + alias 스왑(재색인 중 들어온 쓰기는 따로 따라잡아야 한다).
- "없으면 생성"은 **있으면 아무것도 안 한다** — 정의가 둘이면 먼저 만든 쪽이 조용히 이긴다.
- 엄격 타입은 포맷 밖 값 하나로 그 문서를 거부하고(`ignore_malformed`로 완화 가능), 동적 매핑은 **첫 값**으로 타입을 정한다 — 원문 보존이 목적이면 keyword + `date_detection: false`.
- 스키마 버전 가드는 **모든 호출부가 예외를 전파할 때만** 가드다.
