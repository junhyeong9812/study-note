## 질문
1. 이미 색인된 필드에 분석기를 추가하거나 바꾸려는 `PUT _mapping`은 왜 거부되는가. 분석기 플러그인 코드를 고쳐 재배포했는데 기존 문서의 토큰이 그대로인 이유를 역색인의 생성 시점으로 설명하라.
2. 무중단으로 매핑을 바꾸는 표준 절차(새 인덱스 → 재색인 → alias 스왑)의 각 단계는 무엇을 보장하는가. 옛 인덱스를 바로 지우지 않고 1~2주 남겨두는 이유는?
3. 매핑 정의가 초기화 JSON과 앱의 문서 클래스 두 곳에 있고, 부트스트랩은 "인덱스가 없으면 생성"만 한다. 운영 인덱스에 실제로 적용된 매핑은 무엇이 결정하는가 — 그리고 앱이 먼저 인덱스를 자동 생성하면 무엇이 빠지는가.
4. 예측: 날짜 필드 매핑이 `yyyy.MM.dd||yyyy-MM-dd`인데 원천 데이터에 `18701025`가 섞여 있다. bulk 색인 결과는? 명시 매핑이 없는 필드는 동적 매핑의 date detection이 어떻게 타입을 정하고, 그것이 왜 나중에 문제가 되는가.
5. `dynamic: strict` 인덱스는 필드 누락과 미정의 필드 쓰기를 각각 어떻게 다루는가. 코드가 새 필드를 쓰기 시작했는데 인덱스가 옛 매핑이면 어떻게 되는가.
6. 인덱스 `_meta.schema_version`을 코드 상수와 비교해 불일치면 예외를 던지는 가드를 넣었다. 그런데 한 호출 경로가 인덱스 준비 함수의 예외를 모두 삼키고 있었다 — 가드는 그 경로에서 무엇이 되는가?
7. 연결: 매핑·settings(분석기 정의)·분석기 플러그인 바이너리·빌드 파일은 서로 이름으로 참조한다. 이 묶음을 따로따로 버전 관리하면 어떤 종류의 실패("정의는 있는데 구현이 없음")가 생기는가 — 그리고 이 카드의 기본 방안(정의 단일화 + 재색인)과 어떻게 다른 층위의 해결인가.
