## 질문
1. 분석기는 char_filter → tokenizer → token filter 순서로 돈다. `asciifolding`을 원문 문자에 의존하는 언어별 음차(transliteration) 필터 **앞에** 두면 `München`은 어떻게 색인되는가. 폴딩을 없애지 않고도 두 요구(폴딩 매칭·원문 기반 변환)를 함께 만족시키는 옵션은?
2. 대문자 입력(`PH`)이 소문자 기준으로 짠 철자 정규화 char_filter 매핑(`ph => f`)에 걸리지 않았다. 왜 lowercase를 먼저 적용할 수 없었는가 — 그리고 선택한 해결은?
3. 예측: 특정 스크립트 전용 음차 필터에 다른 스크립트 문자나 숫자가 들어온다. 변환기의 "모르는 문자" 처리가 (a) 원문 그대로 통과 (b) 기본 출력값으로 덮어쓰기 중 무엇이냐에 따라 결과가 어떻게 갈리는가. 어느 쪽이 에러 없이 토큰을 파괴하는가?
4. 비대상 스크립트 입력에 대한 방어를 "루프 안 숫자 skip"과 "진입부 passthrough" 두 겹으로 둔 이유는? 상속 템플릿이 가드를 가졌는데 서브클래스가 메서드를 오버라이드하면 어떻게 되는가.
5. 공백으로만 split한 이름 필드에서 "비라틴 문자+쉼표+영어" 혼합 토큰이 생겼고, 부분 변환 결과(변환 문자+쉼표+영어)가 커스텀 토큰 필터를 `StringIndexOutOfBounds`로 죽였다. `_analyze`로는 재현되지 않았는데 실제 색인에서만 터졌다 — 이 차이는 무엇을 말해주는가. 최소 재현은 어떻게 좁혔는가.
6. 띄어쓰기가 없는 문자체계(태국어·중국어)에서 부분문자열(substring) 매칭은 왜 과매칭하는가. 과매칭을 줄이는 두 가지 방법은 무엇이고, 각각 단어 경계를 실제로 지키는가?
7. 연결: 형태소 분석기의 `decompound_mode: mixed`는 복합어를 여러 토큰 경로(그래프)로 내보낸다. 이것이 동의어 필터와 충돌하는 이유, Windows에서 만든 동의어 파일의 BOM·CRLF가 규칙을 오염시키는 이유, 편집거리 fuzziness가 한글 오타에 잘 안 맞는 이유는 모두 "체인의 각 단계가 전제하는 입력 형태"로 설명된다 — 각각의 전제를 말하라.
