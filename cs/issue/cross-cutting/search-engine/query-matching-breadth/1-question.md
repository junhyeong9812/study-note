## 질문
1. 형태소 분석 text 필드에 다단어 이름을 `match`로 걸었더니 거의 전체(300만 건)가 나왔다. `match`의 기본 연산자는 무엇이고, 흔한 토큰(`주식회사` 류) 하나가 왜 결과를 폭발시키는가. 이 과다매칭이 `should + minimum_should_match: 1`로 0건짜리 wildcard와 묶여 있을 때 왜 **눈에 안 띄는가**?
2. `match_phrase`로 바꾸면 무엇이 달라지는가. 단일 단어 검색에서는 결과가 같다는 것이 왜 이 변경을 "안전"하게 만드는가.
3. 예측: `match` + `fuzziness: AUTO`로 오타 검색을 한다. 분석기가 문서의 긴 단어를 두 토큰으로 쪼갰다면 퍼지는 어느 단위로 적용되는가 — 전체 값 단위로 비교하는 `fuzzy`(term-level)와 어떻게 다른가. 반대로 여러 토큰짜리 질의를 `fuzzy`에 통째로 넣으면 무엇이 되는가?
4. `ngram` 토크나이저에 `token_chars: [letter, digit]`을 주면 한글은 어떻게 쪼개지는가. 음절 하나가 의미 단위에 가까운 문자체계에서 짧은 검색어가 무관한 긴 단어에 대량으로 걸리는 이유는?
5. 여러 발음 후보의 음운 자질 토큰을 **합집합 배열** 하나로 색인하고, 검색어 자질을 100% AND로 매칭했는데도 수천 건이 나왔다. 왜 "검색어 자질 ⊂ 문서 자질" 조건이 거의 항상 참이 되는가 — 위치 정보의 역할을 설명하라.
6. n-gram 분석 필드에 `match_phrase` + `slop`으로 인접 검색("A adj3 B")을 했더니 0건이었다. phrase/slop은 무엇을 전제하는데 n-gram이 그 전제를 깨는가?
7. 연결: 음성 인코더(soundex·double metaphone)는 짧은 입력일수록 소수 코드로 붕괴한다. 이것과 위의 토큰 OR·토큰별 퍼지·n-gram 부분문자열·자질 합집합은 모두 "매칭 단위가 의도보다 작거나 거칠다"로 묶인다 — 쿼리 종류와 토큰화 단위를 의도에 맞춘다는 원칙을 한 표로 정리해 보라.
