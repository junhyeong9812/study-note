## 질문
1. `term` 쿼리로 대문자 검색어 `"ACME"`를 보냈더니 0건인데 `match`로는 잡힌다. `term`과 `match`는 검색어를 다루는 방식이 어떻게 다른가. `term`이 매칭하는 대상은 "원문 전체"인가 "토큰"인가 — 완전일치 의도를 유지하면서 고치는 가장 작은 변경은?
2. 색인용 접미 edge n-gram 분석기(reverse → edge n-gram(min_gram 1) → reverse)를 쓴 필드에 `search_analyzer`를 지정하지 않았다. 5글자 한글 검색어(예: "가나다라마")는 어떤 토큰들로 쪼개지는가. 같은 필드에서 1글자 토큰 "마"의 문서 빈도는 "라마"보다 클까 작을까 — "짧은 토큰이 희귀해서 IDF가 최대"라는 설명은 맞는가, 그리고 무관한 "…마" 문서가 결과에 섞이는 진짜 원인은 무엇이고 어떻게 검증하는가.
3. keyword 필드는 바이트 단위 정확일치다. 쿼리 쪽 코드가 `"09"`를 `str(int("09")) = "9"`로 바꿨고, 인덱스는 `"09"`를 저장했다 — 결과는? 쓰기 경로가 `"01"`과 `"001"`을 섞어 저장하면 집계에는 무슨 일이 생기는가(버킷 합이 전체 문서 수와 달라지는 건 이것 때문인가). 정규화는 어느 쪽에서 하는 것이 근본인가.
4. normalizer 없는 keyword 필드에 클라이언트가 `.lower()`한 값을 wildcard로 보냈다. 왜 대문자 데이터와 만나지 못하는가 — "질의측 정규화와 색인측 정규화는 대칭이어야 한다"를 이 사례로 설명하라.
5. 예측: 쿼리가 매핑에 없는 필드(예: 이미 keyword인 필드에 `.keyword`를 붙임)를 참조한다. 검색 절이면 엔진은 에러를 내는가? 같은 필드로 **정렬**하면? `multi_match`의 fields에 없는 필드가 섞이면? 이 성질이 왜 "쿼리 빌더만 보거나 매핑만 봐서는 dead 절을 발견할 수 없다"로 이어지는가.
6. `index: false` 필드는 무엇을 잃고 무엇이 남는가(타입·doc values에 따라) — nested 필드는 왜 루트 레벨의 일반 쿼리·정렬로 닿지 않는가. 각각의 해결은?
7. 연결: 쿼리 빌더는 검색어를 `join(lower, isalnum)`으로 붙인 한 덩어리(`"foo bar"` → `foobar`)로 term 질의하는데, 인덱스는 standard 분석 후 **단어별** n-gram을 저장했다. 공백 포함 검색어에 대해 이 필드는 무엇이 되는가(단일 단어 검색어라면?) — 그리고 로컬에서 엔진 매칭을 흉내 내는 구현(다른 방안)은 어떤 의미론까지 복제해야 "등가"라고 말할 수 있는가.
