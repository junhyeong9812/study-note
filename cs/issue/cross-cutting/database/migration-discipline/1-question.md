## 질문
1. 버전형 마이그레이션 도구는 적용 이력 테이블에 파일 체크섬을 저장한다. 이미 적용된 `V7` 파일을 고쳐 머지하면 다음 기동에서 왜 실패하는가. "한 번이라도 어딘가 적용됐을 수 있는 파일"의 경계를 왜 **push 시점**으로 잡는가.
2. 예측: push 된 `V20` 을 "아직 배포 안 됐겠지"라고 추정하고 제자리 수정했다. 그 사이 배포 파이프라인이 옛 `V20` 을 운영에 적용했다. 다음 배포에서 무슨 일이 일어나며, 어느 버전이 적용됐는지 어떻게 판별할 수 있었나.
3. 두 브랜치가 같은 base 에서 각자 "현재 최대 번호 + 1"로 `V32` 와 시드 PK `80` 을 잡았다. 병합하면 무엇이 깨지는가. 이 충돌이 "가끔"이 아니라 **결정적**인 이유는?
4. 번호 충돌을 피하려고 시드 INSERT 에 `WHERE NOT EXISTS (같은 id)` 멱등 가드를 걸었다. 다른 브랜치가 같은 id 를 다른 의미로 이미 넣었다면 결과는 무엇인가 — 오류와 무엇이 다른가.
5. 마이그레이션 파일 이름을 `V89` → `V90` 으로 바꿨을 뿐인데 "같은 버전의 마이그레이션이 둘 이상" 오류로 기동이 실패했다. 소스에는 하나뿐이다. 어디에 무엇이 남아 있었나 — 재사용 테스트 컨테이너에서 체크섬 불일치가 반복되는 것과 어떤 공통점이 있나.
6. ORM 모델 클래스를 정의했는데 테이블이 없다 / autogenerate 가 새 테이블을 감지하지 못한다 / DB 가 가리키는 리비전을 코드 트리에서 찾지 못해 컨테이너가 재시작 루프다 — 세 증상의 공통 원리는 무엇인가.
7. 경계: 빈 DB 에서 처음부터 모든 마이그레이션을 적용하는 통합 테스트는 왜 "먼저 적용된 뒤 사이에 끼어든 버전(out-of-order)"이나 "적용 후 수정" 문제를 **구조적으로** 잡지 못하는가.
