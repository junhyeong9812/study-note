## 정답
<!-- 질문 1:1 대응 -->

1. **체크섬 = 불변 강제.** 도구는 기동 시 이력 테이블의 (버전, 체크섬)과 현재 파일을 대조한다(validate). 적용된 `V7` 파일을 고치면 체크섬이 달라져 "checksum mismatch → validate failed"로 기동이 실패하고, 컨테이너라면 크래시 루프에 빠진다.\
   경계를 push 시점으로 잡는 이유는, push 된 순간부터 그 파일이 **어느 DB(운영·스테이징·동료 로컬·재사용 테스트 DB)에 적용됐는지 더는 알 수 없기** 때문이다. "아직 미배포일 것" 같은 추정은 검증할 수 없다.
   > **append-only 이력** — 이미 기록된 항목은 수정·삭제하지 않고 새 항목을 덧붙이기만 하는 기록 방식.

2. **추정 위의 제자리 수정.** 수정하는 사이 배포가 옛 `V20` 을 적용했으므로, 운영 이력에는 옛 체크섬이 남고 소스에는 새 파일이 있다 — 다음 배포가 체크섬 불일치로 기동 실패했다(같은 유형이 재발한 사례).\
   판별: 이 사례 도구(Flyway 계열)의 체크섬은 파일 내용의 CRC32(도구 규칙대로 줄 단위·줄바꿈 문자 제외·BOM 제거, signed 32bit — 규칙은 도구·버전마다 확인)이므로, 옛·새 파일 체크섬을 직접 재계산해 이력 값과 맞춰보면 **어느 버전이 적용됐는지** 확정된다.\
   복구: 파일을 적용본으로 되돌리고(재계산으로 일치 확인) 바꾸려던 내용은 `V21` 로 분리했다.

3. **공유 번호공간의 독립 채번.** 버전 번호와 시드 PK 는 모든 브랜치가 공유하는 전역 단조 번호인데, 각 브랜치가 자기 시점의 max 를 보고 +1 하면 같은 base 에서 출발한 두 브랜치는 **반드시 같은 번호**를 고른다.\
   병합하면 "같은 버전 마이그레이션이 둘 이상"·"Duplicate entry"로 전 통합 테스트 컨텍스트가 실패했다. 소스 브랜치에선 번호가 비어 보여도 다른 브랜치가 이미 선점한 경우도 있었다.\
   교정: 번호를 미리 예약하지 말고, 머지 직전 대상 브랜치 최신을 받아 max 를 재조회해 채번; 충돌 시 후머지 측이 리네임; 충돌을 고치기 전에 "상대가 이미 해결했나"를 먼저 확인(동시 수정으로 한쪽 픽스가 무의미해진 사례가 있었다).

4. **멱등 가드 = 무음 스킵.** `INSERT ... SELECT ... WHERE NOT EXISTS (id = X)` 는 X 가 이미 있으면 **0행 삽입으로 조용히 성공**한다.\
   다른 브랜치가 같은 id 를 다른 의미로 먼저 넣었다면, 내 행은 들어가지 않았는데 마이그레이션은 성공으로 기록된다 — 실제로 운영에 항목이 삽입되지 않은 채 배포됐다.\
   오류는 멈춰서 알려주지만, 멱등 가드는 충돌을 "이미 적용됨"으로 **오인**해 성공으로 위장한다.

5. **유령 산출물.** 증분 빌드는 소스에서 이름이 바뀐 옛 파일을 출력 디렉토리(classpath)에서 지우지 않는다. 도구는 classpath 를 스캔하므로 옛 `V89` 사본과 새 `V90` 을 **둘 다** 읽어 중복 버전 오류(또는 같은 DDL 이 두 번 실행돼 충돌)가 난다 — 5회 이상 반복됐다.\
   교정: 리네임·삭제 후에는 clean 빌드(또는 출력 디렉토리의 옛 파일 삭제).\
   공통점: 재사용 테스트 컨테이너도 **이전 실행의 이력(수정 전 체크섬)** 을 들고 있어, 파일을 고치면 체크섬 불일치가 반복된다(7회 이상). 캐시되는 인프라·산출물은 이전 상태를 기억하므로 변경 후엔 새로 만든다.

6. **스키마는 리비전이 만든다.** ① 모델 클래스만 정의하고 리비전을 생성·적용하지 않아 테이블 9개가 없었다 — 코드가 있어도 DB 스키마는 없다.\
   ② autogenerate 는 `env` 설정에서 **import 되어 메타데이터에 등록된 모델만** 비교하므로, import 하지 않은 신규 모델 3개를 감지하지 못했다.\
   ③ DB 의 현재 리비전이 코드 트리에 없으면 도구는 다음 단계를 계산할 수 없어 기동이 실패했다(테스트 DB 라 스키마 폐기 후 재생성으로 복구).\
   공통 원리: 스키마의 정본은 **적용된 리비전 이력**이고, 그 이력은 코드 트리·메타데이터와 명시적으로 동기돼야 한다.\
   같은 계열로, 공유 ORM Base 에 여러 서버의 모델을 모으면 테이블명 충돌이 나고, `create_all` 은 **그 프로세스에 import 된 모델만** 만들어 다른 서버의 테이블이 없는 사고가 났다.

7. **빈 DB 테스트의 사각지대.** 빈 DB 에서 V1..Vn 을 순서대로 적용하면 모든 파일이 "처음 적용"이다 — 체크섬 비교 대상인 옛 이력이 없으니 **적용 후 수정**은 드러나지 않는다.\
   또 번호 순서대로 적용하므로 "운영에는 V33 이 이미 있고, 나중에 머지된 V32 가 사이에 끼는" **out-of-order** 이력도 재현되지 않는다.\
   즉 이 테스트는 "SQL 이 문법적으로 돈다"만 증명하고, **실제 배포 대상 DB 의 이력 상태**에 대한 적용 가능성은 증명하지 못한다.

## 문제 구조 (추상화 코드)

### 변형 A — 적용된 마이그레이션 제자리 수정
```text
# ① 문제
db/migration/V20__add_col.sql          (push 후 수정)
history: (20, checksum=OLD)            ← 어딘가 이미 적용
validate: file checksum NEW ≠ OLD      → 기동 실패(크래시 루프)

# ② 고친 코드
db/migration/V20__add_col.sql          (적용본으로 복원: 재계산 checksum == OLD 확인)
db/migration/V21__alter_col.sql        (변경분은 새 버전)
# 복구 경로: 운영 데이터 = repair / 개발 데이터 = 스키마 재생성 후 재적용
#   (repair 는 이력의 체크섬을 현재 파일 값으로 덮을 뿐 스키마를 바꾸지 않는다 —
#    파일 내용이 실제 적용된 SQL 과 의미상 같을 때(주석·공백 차이 등)만 안전)
```
```python
# 어느 버전이 적용됐나 판별 — 도구 규칙대로 체크섬 재계산
crc = 0
for line in read_lines(path):          # 줄 단위 — 줄바꿈 문자 제외·BOM 제거(도구 규칙·버전별 확인)
    crc = zlib.crc32(line.encode(), crc)
signed = crc - 2**32 if crc >= 2**31 else crc   # signed 32bit 로 이력 값과 비교
```
무엇이 깨졌나: 이력(append-only)과 소스가 갈라져 validate 실패.\
같은 구조: 적용 후 파일이 수정돼 드리프트된 두 버전 → 빈 테이블 정리 + 이력 삭제 후 1회 out-of-order 기동으로 수습.\
같은 구조: 재사용 테스트 컨테이너에 수정 전 이력이 남아 통합 테스트 체크섬 불일치 반복 → 해당 컨테이너만 제거 또는 재사용 끔.\
같은 구조: 적용된 파일은 내용이 낡은 헤더 주석조차 고치지 않음(선택하지 않은 방법: 주석 정정); 적용된 버전의 잘못은 이후 버전으로 대체(supersede).

### 변형 B — 공유 번호공간의 브랜치별 채번
```text
# ① 문제
base: max(V) = 31, max(seed_id) = 79
branch-1: V32__x.sql  INSERT seed(id=80)
branch-2: V32__y.sql  INSERT seed(id=80)
merge → "more than one migration with version 32" / Duplicate entry '80'

# ② 고친 절차
merge 직전: fetch target → max 재조회 → 후머지 측 리네임(V32 → V35, 80 → 83)
커밋 직전: 대상 브랜치 트리에서 번호 미선점 확인
```
```sql
-- 무음 스킵 형태(문제)
INSERT INTO items (item_id, ...) SELECT 'X001', ... 
WHERE NOT EXISTS (SELECT 1 FROM items WHERE item_id = 'X001');   -- 다른 의미의 X001 이 이미 있음 → 0행
```
무엇이 깨졌나: 병합 시 결정적 충돌, 멱등 가드가 있으면 운영에 행이 빠진 채 "성공".

### 변형 C — 빌드 산출물 잔존

```text
# ① 문제
src/main/resources/db/migration/V89__x.sql  --(rename)-->  V90__x.sql
target/classes/db/migration/V89__x.sql                      (증분 빌드가 지우지 않음)
scan classpath:db/migration → V89(옛) + V90 → 중복 버전 / 같은 DDL 두 번

# ② 고친 절차
clean build   (또는 target 의 옛 파일 삭제)
```
무엇이 깨졌나: 소스에 없는 유령 파일이 도구에 보임.

### 변형 D — 리비전·메타데이터 미동기
```python
# ① 문제
class Job(Base): ...                   # 모델 정의만 — 리비전 미생성 → 테이블 없음
# env: target_metadata = Base.metadata  (신규 모델 모듈을 import 안 함 → autogenerate 누락)

# ② 고친 코드
# env
from app.models.job import Job         # noqa — 메타데이터 등록용 import
from app.models.task import Task       # noqa
target_metadata = Base.metadata
# $ revision --autogenerate -m "initial tables" && upgrade head   → 테이블 생성 확인
```
```python
# ① 문제: 여러 서버가 한 Base 공유
Base = declarative_base()              # 같은 테이블명 재정의 충돌, create_all 은 import 된 모델만

# ② 고친 코드
BaseA = declarative_base()             # DB(스키마 소유 단위)별 독립 Base

```
무엇이 깨졌나: "코드에 모델 있음 ≠ DB 에 스키마 있음" — 스키마 소유가 import·배포 단위에 묶여 있었다.\
같은 구조: DB 이력이 가리키는 리비전이 코드 트리에 없어 기동 불가 → (테스트 DB) 스키마 폐기 후 재생성.
