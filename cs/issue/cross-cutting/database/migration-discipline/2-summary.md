# cs/issue/database/migration-discipline — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
소스(db/migration/V*.sql)  ──빌드──▶  산출물(classpath)  ──기동──▶  DB 이력(version, checksum)
        │                                  │                               │
   [B] 브랜치별 채번                   [C] 지운 파일 잔존                [A] 적용 후 제자리 수정
   V32 × 2, PK 80 × 2                 V89(옛) + V90(새)                 이력 checksum ≠ 파일 checksum
   → 병합 시 중복 버전/PK              → "more than one migration"       → validate 실패, 크래시 루프
   → NOT EXISTS 가드면 무음 스킵                                           (재사용 테스트 DB 도 동일)
                                                          [D] 리비전 미생성·모델 미등록·DB 리비전 부재
                                                              → 테이블 없음 / autogenerate 누락 / 기동 불가

[원리] 마이그레이션 = append-only 이력 · 버전 번호 = 공유 번호공간 · 빌드 산출물 ≠ 소스

[교정]
 [A] 변경은 항상 새 버전 (적용본 복원 + 차분은 V(n+1))
     복구: 운영 = repair / 개발 = 스키마 재생성 · 적용본 판별 = 체크섬 재계산
 [B] 번호 예약 금지 · 머지 직전 대상 브랜치 최신 기준 max 재조회 · 후머지 측 리네임
 [C] 리네임·삭제 후 clean 빌드 · 테스트 컨테이너 재사용 끄거나 해당 컨테이너 제거
 [D] 리비전 생성·적용 확인 · 메타데이터에 모든 모델 import · 스키마 소유를 한 곳으로
```

## 핵심 문장

- 마이그레이션 도구는 적용 이력에 체크섬을 저장해 **불변(append-only)** 을 강제한다. 적용됐을 수 있는 파일(= push 된 파일)은 고치지 않고 **새 버전**으로 바꾼다.
- 버전 번호·시드 PK 는 **공유 번호공간**이다. 브랜치별 "max+1"은 병합에서 결정적으로 충돌한다.
- 멱등 가드(`NOT EXISTS`)는 충돌을 오류가 아니라 **무음 스킵**으로 바꾼다.
- 증분 빌드는 소스에서 지운 파일을 출력에서 지우지 않는다 — classpath 스캔 도구는 **유령 사본**까지 읽는다. 재사용 테스트 인프라도 이전 상태를 들고 있다.
- ORM 모델이 있어도 **리비전을 생성·적용하지 않으면 스키마는 없다**. autogenerate 는 메타데이터에 등록(import)된 모델만 본다.
- 빈 DB 에서 처음부터 도는 테스트는 **적용 순서 이력**을 재현하지 못한다.
