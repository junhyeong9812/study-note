## 질문
1. 노드 224개를 INSERT 한 뒤 같은 트랜잭션에서 엣지를 넣다가, 한 엣지의 CHECK 위반을 `except: rollback(); continue` 로 넘겼다. 마지막 `commit()` 은 에러 없이 끝났는데 노드도 엣지도 0개였다. 한 줄의 rollback 이 무엇을 되돌렸고, 이후 엣지들은 왜 연쇄 실패했나.
2. 위 사건에서 "에러 없이 commit 됨"은 왜 "데이터 적재됨"의 증거가 아닌가. 적재 작업의 완료를 무엇으로 확인해야 하나.
3. 예측: 한 비즈니스 단위(주문 처리)에서 결제 단계만 메시지 큐로 떼어 별도 소비자가 처리하게 했다. 결제는 성공했는데 후속 단계가 실패하면 어떤 상태가 남는가. 이 설계 문제를 어떻게 다시 묶었나.
4. Spring 선언적 트랜잭션(`@Transactional`)은 기본적으로 어떤 예외에서 롤백하는가. checked 예외를 던지는 업로드 메서드에서 무엇이 남았나.
5. 경계: 트랜잭션 **안에서** 커밋 전에 캐시를 비우면 어떤 두 가지 나쁜 결과가 생길 수 있나(동시 요청, 롤백 두 경우). 무효화는 언제 해야 하나.
6. 디스크 파일 쓰기 + DB insert 를 한 메서드에서 하고, 예외가 나면 메서드 안에서 파일을 지우는 보상을 넣었다. 커밋 **시점**에 실패하면 왜 보상이 동작하지 않나. 별도 저장소의 일회용 토큰을 사용자 조회보다 먼저 소비(consume)하면?
7. 연결: DB 쓰기와 메시지 발행을 "둘 다 하거나 둘 다 안 하게" 만드는 transactional outbox 는 어떤 구조인가. 구독자가 없을 때 Pub/Sub 이 메시지를 잃는 이유와, 영속 스트림 + 소비자 그룹으로 바꾼 이유를 함께 설명하라.
