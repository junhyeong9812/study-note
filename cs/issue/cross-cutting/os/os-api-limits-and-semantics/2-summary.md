# cs/issue/os/os-api-limits-and-semantics — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[UDS 경로 길이]
  bind(path) ─▶ sockaddr_un.sun_path[108]   (리눅스 고정 길이 버퍼, NUL 포함 — 다른 OS는 더 짧기도 함)
     긴 런타임 디렉토리 / 스크래치 경로 → 길이 초과 → 라이브러리·bind 거부 → 데몬 사망
  교정: 짧은 경로(/tmp/<name>-<pid>) 사용 + 배포 문서에 제약 명시
        (/tmp 바로 아래는 공유 — 이름 선점·아래 chmod 전제와 충돌 → 짧은 사설 하위 디렉토리가 더 안전)

[소유하지 않은 디렉토리 chmod]
  bind(path) ─▶ chmod(parent, 0700) ─▶ parent = /tmp (root 소유, 공유)
     → EPERM → 기동 실패, 원인 안 보임
  판단: 실패 방향이 "막힘"(안전) → 알려진 창으로 등재

[순회 중 수정]
  for e in read_dir(dir):
      write(dir/새 파일)      ← 새 엔트리가 순회에 보일지 = POSIX 미규정(unspecified)
  교정: 순회 중엔 목록에 모으고, 루프가 끝난 뒤 일괄 쓰기
```

## 핵심 문장

- OS API에는 **고정 한계**(UDS 경로 — 리눅스 108바이트 버퍼, NUL 포함)와 **미규정 동작**(순회 중 디렉토리 변경)이 있다. 설계 전에 전제를 확인한다.
- 권한 변경(chmod)은 **소유자(또는 특권)만** 할 수 있다. 소유하지 않은 공유 디렉토리(`/tmp`)에 chmod하면 EPERM.
- 순회 중 변경은 "보일 수도, 안 보일 수도" — 결과가 플랫폼·FS마다 다르다. **순회와 쓰기를 분리**하면 정의된 동작만 남는다.
- 실패가 **닫히는 방향**이면 알려진 창으로 등재할 수 있지만, 원인이 보이도록 기록은 남긴다.
