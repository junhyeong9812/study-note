## 질문
1. 유닉스에서 자식이 종료됐는데 부모가 `wait`하지 않으면 무엇이 남는가. `kill`만 보내고 끝내는 코드, 자식 stdin 쓰기 실패 시 바로 `return`하는 코드는 각각 어떤 문제를 남기는가(좀비와 진짜 오류 유실).
2. 부모가 자식의 stdout만 EOF까지 읽고 stderr는 읽지 않는다. 자식이 stderr에 로그를 많이 쓰면 왜 두 프로세스가 영원히 멈추는가. 파이프 버퍼 크기와 연결해 설명하라.
3. 예측: 타임아웃이 지나 자식을 kill하고 wait까지 했다. 그런데 stdout 드레인 스레드의 `join`이 끝나지 않는다. 누가 파이프를 쥐고 있는가. `join` 대신 무엇으로 기다려야 하는가.
4. stdio를 프로토콜 전송로(JSON-RPC 등)로 쓰는 자식에게 "stdout 순수성"이 왜 필수인가. 패키지 러너의 설치 확인 프롬프트가 끼어들면 어떻게 교착하는가.
5. 입력 파일을 주지 않은 필터형 명령이나 "추가 입력을 stdin에서 읽는" CLI를 비대화 환경에서 실행하면 왜 영원히 멈추는가. 가장 단순한 예방은 무엇인가.
6. 경계: 자식 출력을 소비하던 쪽(웹소켓 등)이 끊겼는데 생산자 루프가 `readline()`에서 계속 기다린다. 자식은 언제 회수되는가. 보조 스레드(폴링·relay)의 수명은 무엇에 묶어야 하는가.
7. 연결: 파이프에 연결된 Python 자식의 진행 로그가 실시간으로 안 보인다. 블록 버퍼링은 위 2번(파이프 교착)과 어떤 공통 원인(파이프 ≠ 터미널)을 공유하는가.
8. 다른 방안: "스폰한 프로세스가 끝나면 작업이 끝났다"는 전제가 깨지는 프로그램(단일 인스턴스 위임)이 있다. 이때 wait 기반 수명 관리를 어떻게 살릴 수 있는가.
