# cs/issue/testing/performance-measurement-validity — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[생성기] ──요청──▶ [대상 시스템] ──응답──▶ [수집·지표] ──▶ 결론
   │                    │                     │
   ├ 자원 한계          ├ JIT 워밍업 전        ├ 실패 요청이 분포에서 빠짐 (생존자)
   │ (VU 메모리·RTT)     ├ 캐시 수렴 전         ├ 무작위 기저선 미차감
   │ → 생성기가 먼저     │ (쿠폰 수집가)        └ 데이터 부재인데 정상처럼 보임
   │   죽거나 부하 미달  └ 분기예측·JIT가
   │                       복잡도 차이를 지움
   ▼
 결론이 측정 대상이 아니라 측정 장치·조건을 반영

[교정]
  생존자      : 성공 처리량(req/s)을 같이 본다 — 오류율 높은 조건의 지연은 비교 불가
  복잡도      : 입력 규모 상향 + 결정적 계수기(이동·방문·회전 수) + 루프 제거 방지 체크섬
  워밍업/수렴 : 워밍업 뒤 2차 측정 채택, 결정적 프리웜(전 키 1회)
  생성기      : 런 분리(런마다 VU 해제)·사전할당 상한·컨테이너 메모리 캡·유선 경로
  지표        : 무작위 기대값을 뺀 초과분
  데이터      : 측정 전에 입력 데이터 존재를 확인
```

## 핵심 문장

- 성공 요청만 집계하면 실패한 요청은 지연 분포에서 **빠진다** — 오류율이 높은 조건의 p95는 "살아남은 요청"의 지연이다(집계 방식은 도구·설정마다 다르니 먼저 확인).
- 이론 복잡도 차이는 작은 입력·예측하기 쉬운 데이터에서 벽시계로 드러나지 않는다 → **결정적 계수기**로 잰다.
- JVM 측정은 JIT 워밍업 전후가 다르고, 축출 없는 캐시의 히트율은 전 키를 한 번씩 볼 때까지 느리게 수렴한다.
- 부하 생성기도 **측정 대상과 같은 자원 제약**을 받는다 — 생성기의 한계가 결과가 되지 않게 상한을 둔다.
- 지표는 **무작위 기저선을 뺀 뒤**에야 신호다.
- 측정 파이프라인은 입력 데이터가 없어도 에러 없이 "좋은 숫자"를 낼 수 있다.
