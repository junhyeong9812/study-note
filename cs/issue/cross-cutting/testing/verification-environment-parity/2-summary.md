# cs/issue/testing/verification-environment-parity — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[코드]──┬──▶ 검증 환경 (테스트가 실제로 도는 곳)           ──▶ green
        │     헤드리스 · jsdom · H2(create-drop) · standalone MockMvc
        │     빌드 스테이지 · 낮은 JDK · curl
        │
        └──▶ 실행 환경 (사용자가 실제로 쓰는 곳)            ──▶ 결함
              대화형 TTY · 실브라우저 · MySQL+마이그레이션 · 전체 컨텍스트
              런타임 스테이지 · 대상 JDK · 브라우저 인코딩

실패 지점 = 두 환경의 "차이"가 바로 검증하려던 동작인 경우
   jsdom        : Tab 기본 포커스 이동 미구현  → "포커스가 안에 남았나" 단언은 항상 참
   create-drop  : 스키마를 엔티티에서 생성      → 엔티티↔DDL 불일치를 볼 수 없음
   빌드 스테이지 : 앱 소스 존재                  → 런타임 스테이지엔 없음 → MODULE_NOT_FOUND
   standalone   : advice·AOP 미로드              → 권한 검증 미커버
   헤드리스      : hover 능력 false · 출력 포맷 다름
   curl         : 비ASCII 미인코딩               → (엄격한 서버에서) 400 (서버 결함 아님)

   ⇒ 결과가 결함 유무와 "무관"해진다 (거짓 통과 / 거짓 실패)

[교정]
   1) 차이가 검증 대상이면 → 실제 경로로 검증 (Testcontainers 실 DB · 실 세션 로그 · 런타임 이미지 기동)
   2) 더블을 유지하면     → 더블이 재현하는 것만 단언 ("지정 위치로 옮겼나")
   3) 뮤테이션으로 검출력 실증 (결함을 되돌려 넣으면 테스트가 실패하나)
   4) 도구 차이 먼저 배제 (curl --data-urlencode 등)
   [다른 방안] 컴파일 OK ≠ 기동 OK → 기동까지 스모크
```

## 핵심 문장

- 테스트 결과는 **검증 환경이 실행 환경의 해당 동작을 재현할 때만** 의미가 있다. 재현하지 않으면 green도 red도 결함과 무관하다.
- 테스트 더블·에뮬레이터·대체 DB는 운영의 **일부만** 올린다 — 프록시·감사·마이그레이션·advice·모듈 등록 같은 횡단 동작은 전체 컨텍스트·실 DB 통합 테스트에서만 검증된다.
- `ddl-auto=create-drop`은 스키마를 엔티티에서 만들어 내므로 **엔티티와 마이그레이션 DDL의 불일치를 원리적으로 볼 수 없다**. 인메모리 DB는 방언 함수·예약어도 다르다.
- 멀티스테이지 빌드는 **빌드에 있던 파일이 런타임에 없을 수 있다** — 빌드 통과는 런타임 로드를 증명하지 않는다.
- 한 실행 모드에서 실측한 것을 다른 모드로 일반화하지 않는다(헤드리스 ≠ 대화형, 헤드리스 브라우저 ≠ 포인터 있는 브라우저).
- 검출력은 **뮤테이션(결함 재주입)** 으로 실증한다 — 결함을 넣어도 통과하는 테스트는 테스트가 아니다.
