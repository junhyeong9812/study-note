## 정답
<!-- 질문 1:1 대응 -->

1. **초록이 증거가 되는 조건.** 테스트가 증거가 되려면 "결함이 있었다면 이 테스트는 **실패했을 것**"이어야 한다.\
통과 개수는 이것을 알려주지 않는다 — 실측에서 방어 코드를 지운 변종 29개 중 12개가 "0 실패"였고, 인증 검사를 제거한 변종도 통과했다.\
뮤테이션은 방어 코드를 일부러 지우거나 수정 전으로 되돌려 **정확히 그 방어를 겨냥한 테스트가 red가 되는지** 보는 것이다.\
red가 되면 그 테스트에 이빨이 있고, 초록 그대로면 테스트가 약하거나(보강) 변종이 결함이 아니거나(설명 수정) 도달 불가 방어 코드다(지우지 않고 명시) — 세 가지로 판정해 기록한다.
   > **mutation testing** — 원본과 최소한으로 다른 결함 버전(변종)을 만들어 테스트가 그것을 잡는지로 테스트 자체의 판별력을 재는 방법.

2. **픽스처의 표현력.** 자식만 있는 픽스처에서는 그룹 kill과 단일 kill의 결과가 같다(자식 하나가 죽음).\
그래서 `killpg`→`kill` 변종이 전체 스위트를 초록으로 통과했다 — 주석은 "손자까지 테스트"라고 했지만 픽스처에 손자가 없었다.\
실제 손자를 만들고 SIGHUP을 무시하게(`trap "" HUP`) 해야 그룹 kill이 아닐 때 "손자 생존"으로 실패한다.\
픽스처가 표현할 수 없는 구조(손자, 여러 브랜치, 긴 경로가 먼저 탐색되는 그래프)의 결함은 테스트가 **영원히** 못 본다.
   > **fixture** — 테스트가 딛는 전제 상태(데이터·프로세스·저장소). 테스트가 관측할 수 있는 세계의 범위를 정한다.

3. **부재 단언이 공허해지는 때.** 비동기 스트림에서 "본문이 유출되지 않았다"를 메타데이터 도착 **순간에만** 확인하면, 본문이 한 틱 뒤에 따라 나오는 결함을 볼 수 없다 — 관측 시점이 유출 시점보다 이르면 아무것도 검증하지 않는다.\
폴 간격의 여러 배를 기다린 뒤 전체 이벤트를 훑어야 변종이 red가 된다(시간 대기는 여전히 확률적이다 — 스트림 종료 같은 결정적 끝 신호가 있으면 그것까지 받은 뒤 훑는 편이 낫다).\
문자열 부재 단언은 또 다른 함정이 있다: 결과가 없을 때 "'needle'에 대한 결과 없음"처럼 **입력을 에코**하면 `!contains(needle)`가 거짓이 되어 의미가 반전된다.\
부재는 문자열이 아니라 **구조**(히트 수 0, 경로 부재)로 판정한다.

4. **기대값의 독립성.** 계약 테스트가 생산자 타입 대신 같은 파일의 리터럴과 비교하면, 생산자에 필드가 늘어도 리터럴끼리 같으니 통과한다 — 계약의 한쪽을 실제로 잡지 않은 것이다.\
현재 구현의 출력을 그대로 기대값으로 박으면(자기참조) **틀린 동작이 정답으로 박제**되고, 그 테스트는 이후 올바른 수정을 막는 보호막이 된다.\
구현을 보고 테스트를 만들면 구현 중 바뀐 틀린 입력 모양까지 기대값이 된다.\
기대값은 생산자 타입·명세·손계산처럼 검증 대상과 **독립된 출처**에서 가져오고, 새 단언마다 "이 단언이 참이어야 할 이유가 픽스처 밖에도 있나"를 묻는다.

5. **실행 증명의 부재.** 전부 "테스트가 **실제로 돌았다**"가 빠져 있다.\
증분 빌드는 입력 해시가 같으면 테스트를 건너뛰고 이전 결과로 BUILD SUCCESSFUL을 낸다.\
Maven `test` 단계는 통합 테스트(failsafe)를 돌리지 않아 단위 228 초록 뒤에 통합 111건 전건 실패가 숨었다.\
러너 include 패턴에서 한 디렉터리가 빠져 그 테스트가 한 번도 실행된 적이 없었고, 리포트 형식에 따라 `@Nested` 케이스가 0건으로 집계됐다.\
러너 스크립트는 부산물(이전 실행의 XML, 필터된 출력)이 아니라 **이번 실행의 종료코드**로 판정하고, 결과 파일을 지운 뒤 실행하며, 대상이 0개면 실패로 본다.

6. **결과 vs 비용.** "정상·앞에서 죽음·뒤에서 죽음" 세 시나리오 모두 최종 결과가 같으면, 한 트랜잭션을 둘로 나눈 변종도 결과 비교로는 구별되지 않는다.\
스플레이 트리의 zig-zig을 "부모 먼저"(move-to-root)로 바꾼 변종도 답은 전부 맞고 **회전 수만 95배**였다(1000개 정렬 삽입 후 전체 조회 기준).\
이런 결함은 결과가 아니라 **비용**에서만 차이가 나므로, 커밋 횟수·회전 수·이동 횟수·방문 수 같은 **결정적 계수기**를 단언해야 드러난다.\
성질 검사도 한 성질("순서를 어기지 않음")만 보면 노드를 빠뜨린 결과가 통과한다 — 개수·집합·중복을 함께 본다.

7. **레드 위장과 대조군.** 음성 케이스가 목표 레이어(인증)에 도달하기 전에 앞 레이어(입력 패턴 검증)에서 거절되면, 테스트는 **의도한 실패 경로를 검증하지 못한다** — 초록이 결함 부재를 뜻하지 않듯, 이 red(또는 엉뚱한 코드의 실패)도 목표 동작에 대해 아무것도 말하지 않는다.\
입력을 앞 레이어는 통과하도록 구성해야 목표 레이어의 거절을 본다.\
대조군 확인은 "실패 조건이 실제로 재현되는가"를 먼저 보장한다 — 대조군도 실패하지 않는 환경에서 처치군이 통과하는 것은 처치의 효과가 아니다.

### 변형 A — 무단언·약한 단언
① 문제 코드
```java
@Test void hitRate() {
    for (Row r : corpus) if (r.matches(model.run(r.input))) hit++;
    System.out.printf("%d/%d%n", hit, n);            // assert 없음 → 어떤 성능에서도 초록
}
assertThat(messages.get(0)).isInstanceOf(Error.class);   // 에러 "종류"만 — 인증 없이 실행된 뒤의 파싱 에러도 통과
assertThat(list).anySatisfy(x -> { if (cond(x)) assertThat(x.v).isEqualTo(1); });  // 조건부 = fail-open
```
② 고친 코드
```java
double rate = holdoutHitRate(model, heldOut);     // 평가는 튜닝에 안 쓴 holdout 으로
assertThat(rate).isGreaterThanOrEqualTo(THRESHOLD);  // 측정값은 출력만 하지 말고 단언
assertThat(messages.get(0)).isEqualTo(Error.unauthenticated());                 // 내용까지
assertThat(list).filteredOn(this::cond).singleElement().extracting(x -> x.v).isEqualTo(1);
```
무엇이 깨졌나: "무엇이 깨지면 이 테스트가 붉어지는가"에 답이 없는 단언이었다.\
같은 구조: 평가 데이터와 튜닝 데이터가 같아 입력→정답 룩업만으로 점수 99.6% → holdout 분리 후 69.9%로 드러남.\
같은 구조: 동시성 테스트가 결과 존재만 봄 → 처리 수·선점 성공 1건·저장 1행·최대 동시성 1을 결합 단언.\
같은 구조: 하한 단언 `>= 20`이 절반만 스캔해도 통과 → 두 규칙이 같은 입력을 읽고 `assertEquals` 동수.\
같은 구조: hashCode 테스트가 이름 equals만 확인, 골든 비교기가 기준 파일이 없으면 `continue` → 없으면 실패.

### 변형 B — 대리 상태를 단언 (진짜 효과 대신 플래그)

같은 구조: 메시지 비교 헬퍼가 trim해서 후행 개행 손상을 못 봄 → 원시 바이트 비교.\
같은 구조: 신원 검사를 `is_alive`로 약화해도 통과 → 세 번째 인카네이션으로 신원 검사 고정.

같은 구조: 위조 검사가 해시 앞 4바이트만 비교해도 위조 테스트 통과 → 32바이트를 한 자리씩 뒤집어 확인.\
같은 구조: 변경 전후 같은 출력을 내는 입력은 판별력 0 → 판별력 있는 케이스로 보강.

같은 구조: 테스트가 다른 테스트가 설정한 **전역 환경변수**에 의존 → 단독 실행 시 실제 외부 바이너리가 뜸 → 테스트가 바이너리를 자체 설치.\
같은 구조: 네이티브 집계 SQL이 저장소 mock 뒤에 있어 어디서도 실행되지 않음 → 통합 테스트 권고.\
같은 구조: 서버 없이 디스패치만 보는 단위 테스트로는 키 불일치·인증 실패·타임아웃·취소를 재현 불가 → 프로세스 내 실제 프로토콜 서버로 왕복 테스트.\
같은 구조: 실패 주입 테스트의 주입이 목표 분기에 도달하지 않음(앞 단계에서 먼저 실패) → 수정 전 코드로 버그 재현(REPRO)부터 확인.\
같은 구조: 리뷰 입력 diff가 추적되지 않는 새 파일을 빠뜨려 리뷰가 무의미 → `git add -N` 후 재리뷰.

### 변형 G — 실행되지 않은 초록 (수집·캐시·생명주기·판정 근거)
① 문제 코드
```sh
./gradlew test || true                         # 종료코드 버림
parse build/test-results/**/*.xml              # 캐시 스킵·실패 시 이전 실행의 XML 을 읽음
mvn test                                       # 통합 테스트(failsafe)는 verify 단계
# include: ["src/**/*.test.ts"]               # 다른 디렉터리의 테스트는 한 번도 안 돎
```
② 고친 코드
```sh
rm -rf build/test-results
./gradlew test --rerun-tasks; rc=$?            # 캐시 무시, 이번 실행의 종료코드
[ "$(count_testcases build/test-results)" -gt 0 ] || rc=1   # 대상 0개 = 실패
exit $rc
mvn clean verify                               # 머지·마이그레이션 뒤엔 통합까지
# include 에 누락 디렉터리 추가 + 에러 주입으로 실제 실행 확인
# 케이스 수는 XML <testcase> 로 센다 (@Nested 가 0 으로 보이는 리포트 형식 회피)
```
무엇이 깨졌나: "실행 안 함"과 "실패 무시"가 "성공"으로 보였다.\
같은 구조: 뮤테이션 스크립트가 틀린 태스크 이름으로 호출돼 빌드 에러인데 낡은 XML을 읽어 모든 변종 "생존".\
같은 구조: 이미지 빌드 스테이지(패키징)는 테스트를 돌리지 않아 깨진 이미지가 발행·자동 배포 → 테스트 스텝을 로그인·빌드·push **앞에** 둬 스텝 순서로 보증.\
같은 구조: 존재하지 않는 심볼을 patch하는 픽스처로 한 파일 전체가 setup 에러 → 매번 제외돼 그 영역이 무방비 → `stash`로 수정 전에도 같은 실패인지 귀속 판정.\
같은 구조: 테스트 하네스 자체의 무음 실패(잠금 파일 미검증·선언 형식에 종속된 수집·source 실패 삼킴·green 케이스 exit 미검증·root에서 무력한 chmod 테스트) → 기대 실패 집합과 실제 실패 집합의 **정확 일치**만 통과, 부재 시 실행 거부.

### 변형 H — 레드 위장: 음성 케이스가 엉뚱한 레이어에서 실패
① 문제 코드
```java
login("user", "WrongPassword!@");   // 기대 401 — 비밀번호 패턴(숫자 포함) 검증에서 먼저 막혀 500
```
② 고친 코드
```java
login("user", "BadPassword1!@");   // 앞 레이어는 통과하는 입력 → 인증 레이어의 거절을 검증
```
무엇이 깨졌나: 요청이 여러 검증 레이어를 순서대로 지나는데, 입력이 목표 레이어에 닿지 못했다.

## 방안 비교

기본 방안(위 변형 A~H)은 "**뮤테이션·반증으로 기존 테스트의 이빨을 확인**하고 약한 곳을 보강한다"이다.\
같은 원리(초록불 불신)에 다른 방안이 쓰인 사례:

### 방안 1 — 라이브 결함 수정에 재현 회귀 테스트를 동반
```ts
// 문제: 실 스모크에서 본 결함(한 증분 안 같은 id 두 번)을 dedupe 로 고쳤지만 dedupe 를 빼도 전체 초록
// 고친: 결함 자체를 재현·단언
expect(new Set(delta.items.map(i => i.id)).size).toBe(delta.items.length);
// dedupe 제거 시 "seq 3 carried t1 twice (6 items, 1 distinct)" 로 실패
```

### 방안 2 — 대조군이 먼저 실패하는지 확인
```text
문제: 교착 방지 처치군 0/6 교착 → 성공처럼 보임. 그러나 대조군(옛 구조)도 0/6.
원인: (당시 라이브러리의) 기본 2MB 수신 윈도우에선 쓰기가 애초에 막히지(park) 않아 실패 조건 자체가 없음.
고친: 윈도우를 64KB 로 줄여 대조군이 결정론적으로 교착(5/5)하는 것을 먼저 확인 → 처치군 0/30.
      테스트 서버가 작은 윈도우를 광고하도록 헬퍼에 근거와 실측치를 주석으로 남김.
```

### 방안 3 — CI 테스트 나열 목록은 조용히 커버리지를 줄인다
```sh
# 문제: 외부 인프라가 필요한 테스트를 빼려고 안전한 테스트만 나열
./gradlew test --tests 'a.SafeTest' --tests 'b.SafeTest'   # 새 테스트는 목록 갱신 전까지 실행 안 됨
```
포함 목록 방식은 "새 테스트 = 자동 제외"가 기본값이 된다 — 제외 목록·태그 방식과 비교해 고른다.

### 방안 4 — 가정 스키마 mock 대신 실응답 계약 스모크
```text
문제: 외부 API 응답이 실제로는 한 단계 더 감싸여 있었는데(response > body > items),
      가정한 모양으로 만든 mock·파서는 그 가정을 재확인할 수 없음 → 첫 실호출에서 전부 null
      (역직렬화기 설정에 따라 기대한 필드가 없으면 조용히 null 로 둘 수 있음 — 일반론, 원 기록은 "전부 null" 현상까지.
       모르는 필드에 예외를 내는 설정이면 첫 호출에서 오류로 드러났을 것)
고친: 실응답 구조로 파싱·테스트 재작성, 실응답 샘플 계약 테스트 + 원본 보관 권고
```

### 방안 5 — grep "0건"은 그 패턴 표기만의 부재
```sh
grep -rn 'src="/static' app/          # 0건 → "잔여 없음" 판정
# 놓친 것: src={`/static/${name}.svg`}  (템플릿 리터럴) → 운영에서 404
```
전수 재스캔은 따옴표 종류·템플릿·문자열 연결 같은 **다른 표기**까지 포함하거나, 구문 단위(AST) 검사로 한다.

### 방안 6 — 대칭 사례: 의도된 변경을 못 따라간 낡은 기대값 (레드)
```python
assert parse_code(raw) == ["01.02.03"]   # 의도적으로 점 제거로 바꾼 로직을 기대값이 못 따라감
assert has_intl(raw) is True             # 반환 타입이 목록으로 바뀐 것도 못 따라감
# 고친: 로직 불변, 기대값만 새 명세로
assert parse_code(raw) == ["123"]
assert has_intl(raw) == ["has_foreign"]
```
운영에서 문제없이 동작하는 로직의 red는 로직보다 **기대값이 명세를 따라왔는지** 먼저 본다.

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 기본: 뮤테이션·반증으로 이빨 확인 | 방어 코드를 식별할 수 있다 | 변종마다 실행 시간 | 변종 세트 자체가 편향(미감사) | 이미 있는 스위트의 신뢰도 점검 |
| 1. 재현 회귀 테스트 동반 | 라이브 결함을 관찰했다 | 재현 픽스처 작성 | 재현이 실제 조건과 다름 | 버그 수정마다 |
| 2. 대조군 먼저 | 실패 조건을 조절할 수 있다 | 대조 실험 1회 | 조건을 과하게 줄여 비현실적 | 동시성·자원 한계 실험 |
| 3. 나열 목록 경계 | CI 에서 일부 테스트를 빼야 한다 | 목록 관리 | 새 테스트 자동 누락 | 인프라 의존 테스트가 섞인 CI |
| 4. 실응답 계약 스모크 | 외부 응답을 실제로 받을 수 있다 | 실호출·샘플 보관 | 샘플이 낡음 | 외부 API 파서 |
| 5. 구문 단위 잔여 검사 | 같은 의미의 표기가 여럿이다 | 파서·도구 | 도구가 모르는 표기 | 대량 치환 후 잔여 확인 |
| 6. 낡은 기대값 점검 | 의도된 동작 변경이 있었다 | 명세 대조 | 진짜 회귀를 기대값 수정으로 덮음 | red 가 운영 동작과 모순될 때 |

**결론**: 기존 스위트를 믿어도 되는지 모를 때는 **뮤테이션으로 이빨부터** 확인한다(기본).\
새 결함을 고칠 때는 그 결함을 재현하는 테스트를 같이 넣고(1), 실험·재현 조건이 불확실하면 **대조군이 먼저 실패하는지** 본다(2).\
외부 경계(외부 API·CI 선택 실행·문자열 치환)는 테스트 안이 아니라 **바깥 가정**이 틀리는 곳이므로 실응답·제외 방식·구문 검사로 가정 자체를 검증한다(3~5).\
red도 같은 기준으로 의심한다 — 명세가 바뀐 곳의 red는 기대값부터 본다(6).
