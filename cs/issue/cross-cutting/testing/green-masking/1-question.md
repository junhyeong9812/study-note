## 질문
1. "테스트가 통과했다"가 결함 부재의 증거가 되려면 어떤 조건이 필요한가. 뮤테이션(방어 코드를 일부러 지우거나 되돌리기)으로 "테스트의 이빨"을 확인한다는 것은 무엇을 확인하는 것인가.
2. 예측: 프로세스 그룹 전체를 죽이는(`killpg`) 코드를 테스트하는데, 픽스처가 자식만 만들고 손자는 만들지 않는다. `killpg`를 `kill`로 바꾸면 테스트는 어떻게 되는가. "테스트의 커버리지 상한은 픽스처의 표현력"이라는 말을 이 예로 설명하라.
3. 비동기 스트림에서 "X가 나오지 않았다"를 단언하는 부재(negative) 테스트는 언제 아무것도 검증하지 않게 되는가. "결과 없음" 메시지가 검색어를 인용하는 경우 `!contains(needle)`는 왜 뒤집히는가.
4. 계약 테스트의 기대값을 **같은 파일의 리터럴**이나 **현재 구현의 출력**에서 가져오면 무엇이 문제인가. "자기참조 금지·기대값 손계산" 규칙은 무엇을 막는가.
5. 경계: 증분 빌드의 UP-TO-DATE, 단위 테스트만 도는 생명주기 단계(`test` vs `verify`), 러너의 include 패턴 누락, 이전 실행의 결과 XML — 이들은 모두 "초록"을 내지만 공통으로 무엇이 빠져 있는가. 러너 스크립트는 무엇을 판정 근거로 삼아야 하는가.
6. 결과만 비교하는 테스트가 "트랜잭션을 둘로 나눈" 변종이나 "회전을 95배 더 하는" 변종을 못 잡는 이유는? 이런 결함은 무엇을 세어야 드러나는가.
7. 연결: 음성 케이스(비밀번호 오류 → 401)가 앞선 입력 검증 레이어에서 500으로 먼저 거절됐다. 이것은 그린 위장과 어떤 의미에서 대칭인가. 그리고 "대조군이 먼저 실패하는지 확인"은 실험 설계에서 무엇을 보장하는가.
