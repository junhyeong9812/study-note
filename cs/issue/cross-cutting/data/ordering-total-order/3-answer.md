## 정답
<!-- 질문 1:1 대응 -->

1. **순서 없는 dedup.** `keep="first"` 는 "먼저 나온 행"을 남기는데, ORDER BY 가 없으면 무엇이 먼저 나올지는 DB 가 고른 실행계획(풀스캔·인덱스 스캔·병렬 스캔)에 달려 있다.\
   그래서 같은 입력에서도 실행계획이 바뀌면 다른 행이 살아남아 산출물이 흔들릴 수 있다.\
   지금까지 결과가 같았던 건 대개 InnoDB 처럼 PK 순으로 저장된 **클러스터 순서**를 우연히 따라 읽었기 때문이다 — 계약이 아니라 구현 부산물이다.\
   고친 방식은 `ORDER BY <PK>` 를 명시하는 것이었고, PK 가 원래 클러스터 순서라 기존 산출물과의 차이가 0셀임을 확인해 "결정성을 사후에 보장"했다.
   > **결정성(determinism)** — 같은 입력이면 언제 몇 번 실행해도 같은 출력이 나오는 성질.

2. **동점 페이지 경계.** `ORDER BY created_at DESC` 에서 같은 timestamp 인 행끼리는 순서가 정해지지 않았다.\
   페이지 1 과 페이지 2 를 따로 조회하면 동점 그룹 안의 순서가 매번 다를 수 있어, 경계에 걸린 행이 **두 페이지에 중복되거나 어느 페이지에도 안 나온다**.\
   전순서가 되려면 비유일 키 뒤에 유일 키를 붙인다 — `ORDER BY created_at DESC, id ASC`.\
   검증은 동일한 고정 timestamp 로 시드를 넣어 동점을 강제로 만든 통합 테스트로 했다.
   > **전순서(total order)** — 임의의 두 원소에 대해 앞뒤가 항상 정해지는 순서. 비유일 키만으로는 부분 순서다.

3. **사전식 MAX 는 시간순이 아니다.** 문자열 비교는 첫 문자부터 코드값을 비교한다.\
   `'2026-12-31T...'` 와 `'20260325'` 는 앞 4글자 `2026` 이 같고, 5번째 문자에서 `'-'(0x2D)` 와 `'0'(0x30)` 을 비교한다 — `-` 가 더 작으므로 **ISO 값은 모든 숫자형 값보다 작게** 정렬된다.\
   즉 가장 최신의 ISO 값이 `MAX` 에서 절대 뽑히지 않을 수 있다.\
   사전식 비교가 시간순과 같아지는 조건은 **고정 폭 · 동일 포맷**뿐이다.\
   당시 데이터에서는 결과가 같아 실DB 교차 확인으로 머지 안전 판정을 하고, 포맷 표준화는 별도 과제로 남겼다 — 테스트가 정규 풀 타임스탬프만 써서 이 불변식을 보호하지 못했다는 점도 함께 지적됐다.

4. **LIMIT 표본 편향.** ORDER BY 없는 `LIMIT N` 은 보통 테이블을 클러스터(PK) 순서로 읽기 시작하므로 **가장 오래된(초기 배치) 행**이 표본이 된다.\
   데이터 품질이 시간에 따라 변했다면(초기엔 깨끗, 이후 오염) 표본은 전체를 대표하지 못한다 — 실측에서 표본 0.6% vs 전수 46.7%, 약 78배 과소평가였다.\
   대응: 권위 수치는 전수로 내고, 표본 수치는 "추정(과소평가 가능)"으로 표기한다.

5. **Set 순회 순서는 미보장.** 해시 기반 Set 의 순회 순서는 명세상 보장되지 않고 실행마다 달라질 수 있다.\
   JSON 비교는 객체 키 순서는 무시하지만 **배열 순서는 비교**하므로, Set 을 배열로 직렬화한 스냅샷은 재실행마다 달라진다.\
   그렇다고 모든 배열을 정렬하면 안 된다 — 어떤 배열은 **순서 자체가 의미**다(예: 가중치가 순서에 붙는 절 목록).\
   그래서 "어느 배열이 집합이고 어느 배열이 순서인가"를 판정해 **집합 배열만** 정렬했고, 순서가 의미인 곳은 반대로 삽입 순서를 보존하는 `LinkedHashSet` 으로 순서를 계약화했다.

6. **컷 키 ≠ 병합 키.** 각 청크가 score 단독으로 정렬해 상위 N 개를 자르면, score 가 같은 문서들 중 **어느 것이 N 번째 안에 드는지**는 청크 쪽의 임의 순서가 정한다.\
   병합은 `(score, id)` 로 하므로, 청크가 자른 동점 집합과 병합이 기대하는 동점 순서가 어긋나 윈도우 경계에서 **페이지 간 중복·누락**이 생긴다.\
   동점은 드물지 않다 — 점수가 이산적이거나 같은 조건으로 매칭되는 문서가 많으면 **상수적으로** 발생한다.\
   교정은 청크 정렬을 병합 comparator 와 **같은 3키 전순서**로 맞추고 동점 경계 테스트를 추가한 것이다.

7. **DP 동점은 비교 연산자가 정한다.** 최소 비용 분할에서 비용이 같은 후보가 여럿이면, 역추적 포인터를 갱신하는 조건(`<` 면 먼저 본 후보 유지, `<=` 면 나중 후보로 교체)이 **어느 해를 남길지 결정**한다.\
   이 규칙이 암묵적이면 결과는 "우연히 정해진 동점 해"다 — SQL 에서 비유일 키 정렬이 동점 순서를 실행계획에 맡기는 것과 같은 구조다.\
   교정: 동점 규칙을 명시적 조건으로 쓴다(예: 동점이면 앞 토큰이 긴 분할을 택함). 또 두 DP 의 상태 타입이 하나는 튜플·하나는 스칼라로 어긋나 인덱싱 에러가 났으므로 상태 타입도 통일했다.

## 문제 구조 (추상화 코드)

### 변형 A — ORDER BY 없는 "첫 행" 선택 (dedup · fetchFirst · LIMIT 표본)
```python
# ① 문제
rows = db.query("SELECT key, value, ... FROM t")          # 순서 미지정
df = pd.DataFrame(rows).drop_duplicates("key", keep="first")

# ② 고친 코드
rows = db.query("SELECT key, value, ... FROM t ORDER BY id")   # 유일 키(PK) 전순서
df = pd.DataFrame(rows).drop_duplicates("key", keep="first")
```
무엇이 깨졌나: "첫 번째"가 실행계획에 의존 — 지금 같은 결과는 클러스터 순서의 우연.\
같은 구조: 플래그를 "첫 행 조회(fetchFirst)"로 산출하던 것 → `exists(조건)` 으로 순서 무관하게 산출.\
같은 구조: ORDER BY 없는 `LIMIT N` 표본이 가장 오래된 행만 봐 오염률을 78배 과소평가 → 권위 수치는 전수.\
같은 구조: 작은 테이블에서 EXPLAIN 의 사용 인덱스·접근 방식이 비결정 → 테스트는 실행계획 산출만 단언하고 인덱스 선택은 단언하지 않음.

### 변형 B — 비유일 정렬 키로 페이징

```sql
-- ① 문제
SELECT * FROM posts ORDER BY created_at DESC LIMIT :size OFFSET :offset;

-- ② 고친 코드
SELECT * FROM posts ORDER BY created_at DESC, post_id ASC LIMIT :size OFFSET :offset;
```
무엇이 깨졌나: 동점 행이 페이지 경계에서 중복/누락.

## 방안 비교

같은 원리(전순서를 명시해야 결정적이다)를 세 지점에서 다르게 적용했다.

### 방안 1 — 조회·직렬화 지점에 전순서를 명시 (변형 A~D)
```sql
ORDER BY created_at DESC, id ASC      -- 비유일 키 + 유일 tie-breaker
```

### 방안 2 — 분할 컷과 병합을 같은 전순서로
```java
// ① 문제
chunkQuery.sort(score DESC).size(N);                               // 컷: score 단독
merged.sort(comparing(score).reversed().thenComparing(id));        // 병합: score + id

// ② 고친 코드
Comparator<Hit> ORDER = comparing(Hit::score).reversed()
        .thenComparing(Hit::key).thenComparing(Hit::partition);
chunkQuery.sort(score DESC).sort(key ASC).sort(partition ASC).size(N);   // 컷 == 병합
merged.sort(ORDER);
```
무엇이 깨졌나: 경계 동점 문서가 페이지 간 중복/누락. 부수: 청크 total 은 관측 하한이라 "수정"이 아닌 계약 예외로 기록.

### 방안 3 — DP 역추적의 동점 규칙 명시 + 상태 타입 통일
```python
# ① 문제
dp_a = [(INF, INF)] * (n + 1)      # 한 DP 는 (count, unmatch) 튜플
dp_b = [INF] * (n + 1)             # 다른 DP 는 스칼라 → dp_b[j][0] 접근 에러
if new_cost < dp[i]:               # 동점이면 먼저 본 후보가 암묵적으로 남음
    dp[i], back[i] = new_cost, j

# ② 고친 코드
dp_b = [(INF, INF)] * (n + 1); dp_b[0] = (0, 0)       # 상태 타입 통일
if new_cost < dp[i]:
    dp[i], back[i] = new_cost, j
elif new_cost == dp[i] and j > back[i]:               # 동점 규칙을 명시
    back[i] = j
```
기록된 시도: 규칙 ①(다른 방향의 길이 우선) 실패 → ②(비용을 튜플로 확장) 후에도 동점 남음 → ③ 명시적 동점 규칙 채택. 입력 사전을 정리해 동점 자체를 줄이는 보조책도 병행.

| | 방안 1: 조회 지점 전순서 | 방안 2: 컷 키 == 병합 키 | 방안 3: 동점 규칙 명시 |
|---|---|---|---|
| 전제 | 유일 키(PK 등)가 존재 | 조각별 정렬을 조정할 수 있음 | 해 공간의 동점을 규칙으로 가를 수 있음 |
| 비용 | 정렬 키 1개 추가(인덱스와 맞으면 거의 0) | 조각 쿼리 정렬 키 증가 | 규칙 설계·검증(기대 결과 합의 필요) |
| 실패 모드 | tie-breaker 누락 시 경계 흔들림 | 한쪽만 바뀌면 다시 어긋남(두 곳 동기화) | 규칙이 도메인 기대와 다르면 "결정적이지만 틀린" 결과 |
| 맞는 조건 | 단일 쿼리·단일 출력 | 분산·청크 top-K, 병합 페이징 | 최적화·탐색 알고리즘의 동률 해 |

결론: 순서를 쓰는 지점이 하나면 방안 1 로 충분하다.\
결과를 잘라서 합치는 구조라면 방안 1 만으로는 부족하고, 컷과 병합이 **같은 comparator** 를 공유하도록(방안 2) 한 곳에서 정의하는 편이 동기화 실패를 줄인다.\
동점이 알고리즘 내부 선택에서 생기면 방안 3 — 단, "어느 동점 해가 맞는가"는 원리가 아니라 요구사항이 정하므로 규칙을 테스트로 고정해야 한다.
