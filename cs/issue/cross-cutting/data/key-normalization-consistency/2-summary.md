# cs/issue/data/key-normalization-consistency — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
같은 값이 지나가는 지점들          각 지점의 정규화 규칙
─────────────────────             ──────────────────────
  검사 (중복 거부)                  case-sensitive   ← 하나만 다름
  저장 (맵·DB)                      case-insensitive
  조회 (get)                        원본 그대로       ← 하나만 다름
  조인 (다른 시스템)                 다른 표기(점·괄호·형식)
  비교 (DB 콜레이션)                 PAD SPACE / trim / NO PAD
        │
        └─ 한 곳이라도 다르면 → 매칭 조용히 실패(빈 결과·예외 메시지 엉뚱) 또는 검사 우회(중복 통과)

[실측]
   중복 검사 맵만 대소문자 구분     charset;CHARSET 통과, 뒤 값 채택
   소문자 저장 맵을 원본으로 조회    대문자 사용자만 "존재하지 않음"
   반환값 조회만 정규화 누락         선언 순서에 따라 OUT 값이 반환값으로
   앱만 trim, DB는 콜레이션          불일치 방향만 바뀜 (2회째 → 설계 되돌림)
   시스템 간 표기 차이               조인 0건 · 평가 지표 과소 측정
   요청값 echo                      소비자 대문자 필터가 전량 제외
   어말 ς vs σ                      사전 룩업 실패

[교정]
   정규화 규칙을 한 곳에 두고 모든 지점이 같은 함수를 거친다
   경계에서 정규형(canonical)으로 내보낸다 (파싱한 enum의 이름)
   두 축을 맞출 수 없으면 양쪽 raw 정확 일치 + 불일치 후보 검출·경고

[다른 방안/한계]
   동형문자     정규화로 안 잡힘 → 비ASCII 스크립트 스캔
   trim ≠ 검증  내부 공백은 contains(whitespace)로 따로 검사
   순서         공백 포함 접두 검사 전에 trim하면 접두가 깨짐
   URL 경로     대소문자 구분 — 케이스 정규화 금지
```

## 핵심 문장

- 검사·저장·조회·조인이 **같은 값**을 다룬다면 **같은 정규화**를 거쳐야 한다 — 한 곳의 차이가 조용한 매칭 실패나 검사 우회가 된다.
- 한쪽 축만 정규화하면 불일치는 사라지지 않고 **방향만 바뀐다**.
- 외부로 나가는 식별자는 입력 echo가 아니라 **정규형**으로.
- 정규화는 **검증이 아니고**, 적용 **순서**가 있으며, 정규화하면 **안 되는** 도메인(대소문자 구분 경로)이 있다.
- 사람 눈에 같은 글자라도 코드포인트가 다르면 다른 문자열 — 동형문자는 **기계 스캔**으로만 잡힌다.
