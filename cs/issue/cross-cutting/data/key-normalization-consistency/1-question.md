## 질문
1. MIME 파라미터 이름은 대소문자를 무시하고 최종 저장도 대소문자 무시 맵인데, 중복 파라미터 거부 로직의 누적 맵만 일반 해시 맵이었다. `charset=UTF-8; CHARSET=ISO-8859-1`은 어떻게 처리되는가. 맵 타입만 바꿔도 기존 거부 코드가 동작하게 된 이유는?
2. 저장할 때 키를 `toLowerCase(Locale.ROOT)`로 넣는 맵에서 한 메서드만 원본 이름으로 조회했다. 어떤 사용자에게서만 실패하며, 이름이 비슷한 기존 테스트가 "이미 커버됨" 착시를 준 이유는 무엇이었는가. 왜 `Locale.ROOT`인가.
3. 예측: 그룹 키가 DB(콜레이션·생성 컬럼)와 애플리케이션(원본 `equals`) 두 곳에서 계산된다. 애플리케이션 쪽만 `trim()`하면 불일치는 사라지는가? 같은 결함을 두 번 고쳐도 깨졌을 때 무엇을 해야 하는가.
4. 두 시스템이 같은 식별자를 서로 다른 표기(`A0101` vs `A-01-01`, 괄호 주석 유무)로 저장할 때, 동등 비교 조인은 왜 에러 없이 "빈 결과"만 내는가. 평가 지표에서는 이 불일치가 어떻게 나타났는가.
5. 경계: 응답에 식별자를 담을 때 요청값을 그대로 echo하면 소비자의 exact-match 필터가 어떻게 깨지는가. 경계에서 내보내는 형태는 무엇이어야 하는가.
6. 유니코드에서 "같은 글자"가 다른 코드포인트인 두 경우 — 문자 위치에 따른 형태(그리스어 어말 시그마)와 서로 다른 스크립트의 동형문자(키릴 С vs 라틴 C) — 는 각각 어떻게 다뤄야 하는가.
7. 연결: 정규화를 **하면 안 되는** 곳(URL 경로의 대소문자)과, 정규화를 **검증으로 착각한** 경우(`trim()` 후 "공백 없음"으로 간주), 정규화 **순서** 문제(`trim()` 후 `"Bearer "` 접두 검사)를 각각 설명하라.
