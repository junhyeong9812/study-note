# cs/issue/data/lookup-cost-and-indexing — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
레코드 n개를 처리한다 → 레코드마다 "조회" 1회
   조회 비용 = O(1)  → 전체 O(n)         (인덱스·해시가 있음)
   조회 비용 = O(n)  → 전체 O(n²)        (인덱스 없음 · 선형 탐색)

[실패 지점]
 (A) value→key 역검색을 dict 전체 순회        호출당 수백 ms × 수백만 건 = 수일
 (B) 조회 키 인덱스 없는 upsert              건당 풀스캔 → 80%에서 수 시간 정체
 (C) 조인 키 인덱스 없음                     페이지마다 대형 테이블 풀스캔
       └ 비용이 OFFSET 과 무관하게 평탄      = 고정비(풀스캔)가 지배
       └ 동기 리더 1개가 느림 → 병렬 워커 굶음 = 사실상 직렬
     인덱스 후엔 deep OFFSET 이 선형 병목     (건너뛸 행을 매번 읽음)
 (D) 인덱스는 있는데 못 탐                    LIKE '%kw%' (선행 와일드카드)
 (E) 해시 군집화                             hash(x)=x + 연속 키 + 선형 탐사
                                              → 미스 조회가 덩어리 끝까지 탐사

[교정]
 (A) 초기화 때 역인덱스 1회 구축 → .get() O(1)      (메모리·기동시간과 교환)
 (B) 빈 컬렉션 순수 insert 적재 → 인덱스는 적재 후
 (C) EXPLAIN(type=ALL) 로 확정 → 조인 키 인덱스(온라인 DDL) → OFFSET → keyset
 (D) 접두 길이 인덱스 + 부분일치는 FULLTEXT 검토
 (E) 벤치 입력을 흩뿌려 알고리즘을 재고, 군집화는 한계로 테스트에 문서화
```

## 핵심 문장

- 전체 비용 = **호출 수 × 조회 1회 비용**. 조회 1회가 O(n)이면 코드가 "O(n) 루프"처럼 보여도 전체는 O(n²)다.
- dict 는 key→value 만 (평균) O(1)이다. value→key 가 빈번하면 **역인덱스를 한 번** 만든다.
- upsert 는 매 건 조회를 동반한다 — 조회 키 인덱스가 없으면 적재가 O(n²).
- 페이지 비용이 OFFSET 과 무관하게 **평탄**하면 고정비(풀스캔)를, 병렬인데 **순차 진행**이면 느린 동기 리더를 의심한다.
- OFFSET 은 건너뛸 행을 매번 읽는다 → 깊을수록 선형 악화 → **keyset**(`WHERE key > :last`).
- B-tree 는 정렬된 **접두**로만 범위를 좁힌다 — 선행 와일드카드는 인덱스 범위 탐색을 못 쓴다(전체 스캔으로 떨어짐).
- 해시 성능은 해시 함수 × 키 분포 × 충돌 해결 방식의 성질이다 — 항등 해시 + 연속 키 + 선형 탐사 = 1차 군집화.
- 병목은 추측이 아니라 **프로파일링·EXPLAIN** 으로 특정한다.
