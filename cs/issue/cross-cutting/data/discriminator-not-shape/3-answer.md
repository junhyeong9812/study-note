## 정답
<!-- 질문 1:1 대응 -->

1. **모양 분기의 오분류.** "content가 bare 문자열이면 프롬프트"로 분기하면 assistant·system 레코드의 bare 문자열도 **turn을 연다**(거짓 turn). 반대로 "텍스트면 답"으로 잡으면 assistant가 아닌 텍스트가 **answer**가 된다.\
   "user 레코드 = 프롬프트"도 거짓이다 — 이 로그 형식에서는 도구 실행 결과(tool_result)도 user 역할 레코드로 기록되기 때문이다(역할 배치는 형식마다 다르다 — 도구 결과에 별도 role을 두는 형식도 있다).\
   같은 모양(문자열 content)이 역할에 따라 전혀 다른 의미를 가지므로, 모양은 판별 근거가 될 수 없다.

2. **판별자 먼저.** 레코드를 해석하기 전에 명시적 판별 필드(role·type)를 읽고, 그 값으로 해석 분기를 고른 **다음에** 모양을 본다.\
   판별자가 중첩 필드(`message.role`)나 최상위 필드(`kind`) 중 한 곳에 있으면 우선순위를 정해 합친다(`message.role ?? kind`).\
   그 뒤 같은 역할 안에서도 내용 종류를 거른다 — user여도 content 배열의 도구 결과 항목은 프롬프트에서 제외한다.
   > **판별자(discriminator)** — 다형 데이터에서 "이 레코드가 어떤 종류인지"를 명시하는 필드. 해석 분기를 결정한다.

3. **이중 기록 로그의 층.** 모델 입력 층은 모델에 실제로 들어간 모든 것 — 매 턴 앞에 시스템이 주입한 환경 컨텍스트, 개발자 시스템 프롬프트까지 포함한다.\
   이 층만 읽어 화면을 만들면 **주입 컨텍스트와 시스템 프롬프트가 사용자 발화로 뜬다**(수백 건).\
   대화는 사용자 가시 이벤트 층에서, 도구 호출·결과는 모델 입력 층에서 읽도록 **층을 분리**한다 — 층 자체가 판별자다.

4. **판별 유니온 스키마.** 판별 유니온은 `type` 값으로 어느 분기(예: stdio / sse / http)의 스키마를 적용할지 **먼저 고르고**, 그 분기의 필수 필드를 검사한다.\
   각 분기가 `type`을 필수로 선언한 판별 유니온이라면 `type`이 없을 때 분기를 고를 수 없으니 어느 분기의 검증도 통과하지 못해 "스키마 불일치"로 거부된다. (구현에 따라 `type` 누락을 기본 분기로 간주하기도 하는데, 그때도 기본 분기의 필수 필드가 없으면 같은 식으로 거부된다 — 어느 쪽이든 오류 메시지가 "판별자 누락"을 직접 말하지 않을 수 있다.)\
   모양으로 추론하는 스키마(필드 조합을 보고 짐작)는 누락을 관대하게 넘길 수 있지만 모호한 조합을 오분류할 수 있다 — 판별자 필수는 그 모호성을 없애는 대신 명시를 요구한다.
   > **discriminated union** — 공통 판별 필드의 값으로 여러 변형 중 하나를 확정하는 합 타입.

5. **해석 불가 레코드.** 비슷한 모양이라고 가장 가까운 종류로 보여 주면 **없는 내용을 날조**하게 된다(예: 요약이 빈 배열인 암호화된 추론 레코드를 추론 항목으로 표시).\
   항목을 만들지 않고 건너뛰되, 모르는 종류는 **세어서** 드러낸다. 코퍼스 전체를 재파싱해 미파싱 0건을 테스트로 고정하면 새 종류가 생겼을 때 알 수 있다.

## 문제 구조 (추상화 코드)

### 변형 A — 역할을 보지 않고 content 모양으로 분기

```rust
// 문제
match &rec.content {
    Content::Text(s) => open_turn(s),            // assistant/system 문자열도 turn
    Content::Blocks(b) => ...,
}
if rec.kind == "user" { open_turn(...) }         // 도구 결과도 user

// 고침: 판별자 먼저, 그다음 내용 종류
let role = rec.message.as_ref().and_then(|m| m.role.as_deref()).or(rec.kind.as_deref());
let is_user = role == Some("user");
let is_assistant = role == Some("assistant");
if is_user && !content_is_tool_result(&rec.content) { open_turn(...) }
if is_assistant { set_answer(...) }
```
무엇이 깨졌나: 거짓 turn과 잘못된 answer가 생겼다(회귀 테스트: 사용자 bare 문자열만 turn을 연다).

### 변형 B — 이중 기록 로그에서 잘못된 층을 읽음

```rust
// 문제: 모델 입력 층만 읽음
for item in log.filter(|r| r.layer == Layer::ModelInput) { timeline.push(as_message(item)); }
// → 주입 컨텍스트·시스템 프롬프트가 사용자 발화로

// 고침: 목적별 층 분리 + 해석 불가는 날조하지 않고 카운트
for r in log {
    match (r.layer, r.kind) {
        (Layer::UserVisible, Kind::Message) => timeline.push_message(r),
        (Layer::ModelInput,  Kind::ToolCall | Kind::ToolOutput) => timeline.push_tool(r),
        (_, Kind::Reasoning) if r.is_encrypted() => {}          // 항목 생성 안 함
        (_, _) => unknown += 1,                                  // 관대 스킵 + 카운트
    }
}
```
무엇이 깨졌나: 모델 입력 층만 읽었다면 주입 컨텍스트 232건과 시스템 프롬프트 251건이 사용자 발화로 뜰 구조였다(스키마 전수 조사 단계에서 발견해 층 분리로 확정, 테스트: 주입 컨텍스트는 사용자 turn이 아니다). 리뷰에서는 배열형 도구 출력 29건이 유실되는 결함이 잡혔다.

## 방안 비교

같은 원리("판별자로 해석")를 읽는 쪽이 아니라 **쓰는 쪽(설정)** 에서 강제한 사례.

### 방안 1 — 읽는 쪽이 판별자를 찾아 해석 (위 변형 A·B)
생산자 포맷을 바꿀 수 없는 로그·이벤트를 읽을 때. 판별자 위치가 여럿이면 우선순위로 합치고, 해석 불가는 카운트한다.

### 방안 2 — 스키마가 판별자를 필수로 요구 (설정 파일)

```json
// 문제: 전송 방식 판별자 누락 → "설정 스키마를 따르지 않음", 서버 미인식
{ "search": { "url": "http://<host>/sse" } }

// 고침: 판별자 명시
{ "search": { "type": "sse", "url": "http://<host>/sse" } }
```
전송 방식별로 필수 필드가 다른 판별 유니온이라, `type`이 없으면 어느 분기로도 검증되지 않았다.\
곁가지: 그 뒤 나온 초기화 관련 오류는 세션 초기화 실패라 재시작으로 해결.

### 비교

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 읽는 쪽 판별 | 판별자가 레코드에 (어딘가) 존재 | 판별 로직·층 지식이 소비자에 분산 | 판별자 위치·층을 잘못 고르면 조용한 오분류 | 생산자 포맷을 통제할 수 없는 로그·외부 이벤트 |
| 스키마 필수 판별자 | 스키마·검증기를 통제 | 작성자가 판별자를 매번 명시 | 누락 시 즉시 거부(시끄러움), 오류 메시지가 원인을 직접 말하지 않을 수 있음 | 설정·API 입력처럼 쓰는 쪽을 규약으로 묶을 수 있을 때 |

**결론**: 쓰는 쪽을 통제할 수 있으면 판별자를 스키마에서 **필수**로 만드는 편이 낫다 — 오분류가 조용한 결함이 아니라 즉시 거부로 드러난다.\
통제할 수 없는 로그·외부 데이터에서는 읽는 쪽이 판별자(와 기록 층)를 먼저 확인하고, 해석할 수 없는 것은 날조하지 말고 세어 드러낸다.
