## 정답
<!-- 질문 1:1 대응 -->

1. **복사의 세 축.** 현재값 필드는 "지금"만 안다. 과거 시점 D의 값을 만들려면 **언제**(D가 끝난 직후?) **무엇을**(어느 필드·어느 행) **어떤 값으로** 복사할지 정해야 하는데,\
   복사 시각이 늦으면 D+1 변경이 섞이고, 이르면 D의 늦은 변경을 놓친다.\
   결정타는 **늦게 도착한 과거 이벤트**다 — D-1 귀속 이벤트가 D 스냅샷 이후에 오면, 이미 만든 스냅샷들은 그 이벤트를 모르거나 잘못된 날에 귀속한다. 현재값에는 "이 변경이 언제 귀속되는가"라는 시간축이 없으므로 고칠 방법이 없다.

2. **세 번 실패 후.** 같은 결함을 세 번 다른 방식으로 고쳐도 깨지면, 틀린 **토대**(현재값 복사 모델)를 다듬고 있는 것이다.\
   다음 행동은 네 번째 패치가 아니라 **설계를 되돌려** 모델을 바꾸는 것 — 이 사례에서는 "복사" 자체를 버리고 이동 기록 합산으로 재설계했다.

3. **구성적 합.** 이동 기록은 수정되지 않고 쌓이기만 하며 각 기록이 **귀속일**을 갖는다.\
   `value_at(D) = Σ Δ (귀속일 ≤ D)`에서 덧셈은 교환·결합 법칙이 성립하므로, 기록이 어떤 순서로 도착하든 D 이하 귀속분의 합은 같다. 늦게 온 과거 이벤트는 그냥 한 행 더 쌓일 뿐, 이미 있는 행을 고칠 필요가 없다.\
   단, **재전송**에까지 무관하려면 각 이동 기록이 고유 id를 갖고 같은 id의 재도착은 무시(멱등 적재, 예: id unique + 충돌 시 무시)돼야 한다 — 그렇지 않으면 합은 순서엔 무관해도 중복 도착만큼 과대가 된다.
   > **append-only** — 기존 행을 수정·삭제하지 않고 새 행 추가만 허용하는 저장 방식. 이력이 그대로 남아 재계산이 가능하다.

4. **반증적 판정.** "중복 = 재처리 버그"라는 가설을 반증할 증거를 찾는다.\
   적재 단위(원천 배치 파일) 이름이 UNIQUE 제약인데도 같은 키의 버전이 여러 배치에 있다면 **같은 배치를 두 번 처리한 것이 아니다** — 원천이 배치마다 이력을 다시 보낸 것이다.\
   다른 테이블들도 **같은 배율**인지 교차 확인해 이를 뒷받침했다.

5. **소비 단계 dedup·합산.** 적재 단계는 원천을 받은 그대로 append만 하고, "키별 최신 버전 선택"(MAX(version))이나 합산은 **소비 단계**(검색 색인 적재, 조회)에서 한다. 그러면 재전송·중복이 적재를 오염시키지 않는다.\
   완료 판정식도 먼저 고정한다 — "소비처 문서 수 ≈ 적재의 COUNT(DISTINCT key)".\
   소급 보정(Δ 전파)은 스냅샷 모델(틀린 토대)을 그대로 둔 채 늦은 이벤트를 이후 스냅샷에 덧대는 **패치**로 판단돼 선택하지 않았다 — 정지 규칙(같은 자리 3회 실패)이 요구하는 것은 덧대기가 아니라 모델 교체다.

## 문제 구조 (추상화 코드)

### 변형 A — 현재값 복사로 과거 시점 값 만들기 (설계 리뷰 단계)

```sql
-- 문제: 시간축 없는 현재값을 어느 시점에 복사
UPDATE daily_close SET closing = (SELECT current_value FROM entity WHERE id = ?)
 WHERE entity_id = ? AND day = :D;          -- 늦게 온 D-1 이벤트는 이미 반영된 current_value 에 섞여 D 로 귀속

-- 고침: 이동을 귀속일과 함께 append, 값은 합으로
INSERT INTO movement(entity_id, attributed_day, delta) VALUES (?, ?, ?);
SELECT SUM(delta) FROM movement WHERE entity_id = ? AND attributed_day <= :D;
```
무엇이 깨졌나: 배치 스냅샷(다음 날 섞임) → 단일 필드(하루 어긋남) → 행 + 현재값 복사(늦은 과거 이벤트 역순 귀속)로 같은 자리가 세 번 깨졌다.

### 변형 B — 전량 재전송 원천의 append-only 스테이징

```sql
-- 적재: 원천이 보낸 그대로 append (배치 파일명 UNIQUE)
INSERT INTO staging(key, version, ...) SELECT ... FROM batch_file;

-- 소비: 키별 최신 버전만
-- (전량 재전송이면 같은 (key, version) 행이 여러 배치에 중복되므로 MAX(version) 조인은 한 키에 여러 행을 돌려줄 수 있다 → 키당 1행으로 자른다)
SELECT * FROM (
  SELECT s.*, ROW_NUMBER() OVER (PARTITION BY key ORDER BY version DESC, batch_id DESC) rn
    FROM staging s
) t WHERE rn = 1;

-- 완료 판정(선고정): index_doc_count ≈ SELECT COUNT(DISTINCT key) FROM staging
```
무엇이 깨졌나: 깨진 것은 없었다 — 적재 행 수가 고유 키의 4.7배라 버그로 의심됐지만, 반증 절차로 원천 누적임을 확정하고 소비 단계 dedup이 이미 흡수하고 있음을 확인했다.
