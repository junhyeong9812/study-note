# cs/issue/cross-cutting/security/secret-ownership-least-privilege — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 비밀은 **한 곳이 소유**하고(정본 = 실제 쓰이는 곳), 그 비밀을 검증하는 책임과 그것으로 얻는 권한은 **꼭 필요한 최소로** 국한한다.

세 축으로 나뉜다.

**(1) 단일 소유 — 정본은 실사용처(.env)다.** 사람이 보는 시크릿 대장(md 문서)은 *사본*일 뿐이다. 사본에서 값을 grep으로 긁으면 표 구조가 조금만 어긋나도 엉뚱한 값을 집는다 — 실제로 "첫 32자리 hex"를 집었더니 원하던 `DEPLOY_SECRET`이 아니라 표 첫 행의 `SYNC_SECRET`이 잡혀 배포가 401로 거절됐다. 정본(운영 서버의 .env)에서 직접 등록해야 맞다.

**(2) 단일 검증자 — 소유자만 검증한다, 나머지는 pass-through.** 비밀이 두 서버에 살면 교체(rotation)할 때마다 두 곳을 다 고쳐야 하고, 언젠가 한 곳만 고치고 다른 곳을 잊는다. 그래서 중계 서버(프록시)는 비밀을 **저장도 검증도 하지 않고 그대로 넘기고**, 판정은 진짜 소유자(backend)만 한다. 그러면 검증 로직이 한 곳에만 살고 교체도 한 곳만 고치면 된다.
> pass-through(패스스루): 받은 것을 열거나 바꾸지 않고 그대로 통과시키는 것.

**(3) 최소 권한 — 하는 일에 필요한 권한만.** 위험한 권한(호스트 도커 제어권 = docker.sock)은 그게 *일*인 쪽(agent)만 쥐어야 한다. 요청을 받아 라우팅만 하는 master가 같은 권한을 쥐면, 입구(외부 요청을 받는 master)가 뚫리는 순간 호스트 전체 + 저장소로 침해가 번진다(blast radius). 편의(compose 서비스 정의 하나 재사용)가 최소 권한을 침식하면 편의를 버린다 — profiles로 서비스를 분리해 master는 마운트 0개로.

이 셋을 떠받치는 부수 원칙:
- **정본이 git 밖(.env)** 이면 `git reset --hard`(추적 파일만 되돌림)에도 시크릿이 살아남는다 — (1)과 자연스럽게 맞물린다.
- 검증은 제대로 — **상수시간 비교**(타이밍 공격 차단) + **빈 비밀이면 무조건 거절(fail-closed)**.
- 원격 실행처럼 위험한 표면은 인증을 반드시 붙인다(브리지 X-Bridge-Secret).

## 핵심 문장

- 비밀의 정본은 문서(사본)가 아니라 실제 쓰이는 곳(.env)이다. 사본 grep은 엉뚱한 값을 집는다.
- 비밀을 두 곳에 두면 교체할 때 한 곳을 잊는다 — 프록시는 저장·검증 없이 pass-through.
- 검증은 소유자만. 검증 로직이 한 곳에만 살아야 교체가 안전하다.
- 위험한 권한은 그게 일인 쪽만 쥔다. 입구가 뚫려도 번지지 않게 권한을 하는 일에 맞춘다.
- 편의가 최소 권한을 침식하면 편의를 버린다.
- 정본이 git 밖이면 reset --hard에도 살아남는다 — 검증은 상수시간 + fail-closed로.
