# cs/issue/security/authorization-gate-placement — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[요청이 인가를 만나기까지]

  입력 경로 ①  ─┐
  입력 경로 ②  ─┼─▶ [단일 인가 지점] ─▶ [부작용: 선점·쓰기·실행] ─▶ 하류
  (구 필드·재전송)┘        ▲
                           │ 신원 = 런타임/인증 컨텍스트가 보증한 값
                           │ (클라이언트가 보낸 이름·URL·브랜치명 X)

[깨지는 자리]
  A 게이트를 도달 불가 단계에 둠     앞단 스텁이 먼저 거부/허용 확정 → 뒷단 게이트 무의미
  B 클라이언트 주장 신원             창 이름·URL prefix → 우회·권한 상승(confused deputy)
  C 같은 결정의 두 번째 입력         allowlist 옆의 자유 경로 필드 / 브랜치 "이름"만 비교
  D 부작용 이후·일부 경로에만 인가    멱등 키가 먼저 소모 / 재전송 분기는 그 층을 안 지남
  E 앞단 필터가 판정 조기 확정        무효 토큰 → 401 확정 → 공개 경로도 막힘

[교정]
  A 게이트는 권한 요청 단계에서 실제 선택을 기다림(미응답 = 거부)
  B 신원은 런타임 객체·SecurityContext에서 도출, 헤더는 set(덮어쓰기)
  C 필드를 와이어에서 제거 + unknown field 거부 / 출처 4항 AND
  D 인증 직후·멱등 선점 이전의 진입 미들웨어에서 대조, 체인 순서 고정
  E 인증 실패 = 익명 강등 + 사유는 서버 내부 속성 → 인가가 판단, 에러 코드는 EntryPoint가 복원
```

## 핵심 문장

- 인가는 **모든 경로가 지나는 단일 지점**, **부작용 이전**, **런타임이 보증하는 신원**으로 판정한다.
- UI 잠금은 인가가 아니다 — 서버가 호출자 신원을 스스로 확인해야 한다.
- 같은 결정을 내리는 입력이 둘이면 검사는 언젠가 한쪽에만 걸린다 → **제한이 아니라 제거**, 모르는 필드는 거부.
- 이름은 출처를 증명하지 못한다 — 브랜치 이름 대신 저장소 식별자까지 AND.
- 인가가 멱등 선점 뒤에 있으면 거절된 요청도 키를 소모한다. 체인 순서가 계약이다.
- 인증 필터는 "신원이 확실한가"만 안다. 응답 확정은 인가 계층의 몫이다.
