# cs/issue/security/regex-is-not-a-shell-parser — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[두 개의 의미 모델]

  명령 문자열 ──▶ 가드(regex)  : "이 글자들이 이 패턴과 맞나"
             └─▶ 셸(파서)     : 토큰화 · 인용 · heredoc · 리다이렉트 · cwd · 경로 해석

  두 모델이 어긋나는 곳 = desync
     ├ false-allow  같은 동작, 다른 표면형   git -C r push · /usr/bin/git push · command git push
     │              문자열 예외의 틈         "> 상태파일<TAB>.events"  · a/../b
     │              실행 문맥 무시           cd other && git commit → 가드는 자기 cwd 검사
     └ false-block  데이터 속 "언급"         커밋 메시지 · heredoc 본문 · grep 인자 · 테스트 입력
                    무관한 세그먼트          복합 명령의 다른 부분이 패턴에 걸림

[고치는 방식의 수렴 여부]
  패턴 하나 추가 → 새 변형 등장 → 패턴 추가 → ...   (리뷰 루프 18 → 11 → 3 + … : 비수렴)
  문자열 예외 추가 → 새 우회(P0) 신설

[근본 교정]
  경계 = 구조화된 신호 (행위 직전 네이티브 확인 UI 가 명령 전문을 보여주고 묻기)
  보호 훅에 문자열 예외 금지 · 경로는 정규화된 절대경로 도메인에서만 비교
  파싱 불가 폴백 = 가장 중요한 안전망 하나(보수적 확인)만
  오탐은 명령 분리 · 스크립트 파일 경유 · 패턴을 좁게(bare 단어 대신 구조 문자열)
```

## 핵심 문장

- 문자열 검사는 셸이 실제로 하는 **토큰화·리다이렉트·경로 해석**을 모른다 — 그 차이(desync)가 우회와 오탐을 **동시에** 만든다.
- 같은 동작은 옵션·경로·래퍼로 **여러 표면형**을 가진다. 표면형 하나를 고정한 패턴은 우회된다.
- 자연어 의도와 셸 문법은 변형이 무한하다 — 패턴 수정 루프는 **수렴하지 않는다**. 같은 곳 2회 churn이면 설계를 되돌린다.
- 보호 훅에 **문자열 예외**를 넣으면 공격자는 예외와 셸 의미의 틈을 판다.
- 명령 전체 문자열 매칭은 데이터 영역의 **"언급"을 실행으로** 오인한다.
- 폴백 경로는 정밀 판정이 아니라 **안전망 하나**만 책임진다.
