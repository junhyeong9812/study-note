# cs/issue/security/authorization-freshness-binding — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[승인 신호가 증명해야 하는 세 가지]
  진위    : 누가 만들었나          ← 서명(HMAC)·토큰 서명
  신선도  : 지금 것인가            ← issuedAt/expiresAt 창, 턴 카운터
  결속    : 이 행위 1회에 대한 것인가 ← 멱등 키 선점, 폐기(revoke)
  → 서명은 "진위"만 준다. 나머지 둘은 따로 세워야 한다.

[변형 A — 서명 통과 = 통과로 착각]
  요청(sig OK, requestId="") ─┐
  요청(sig OK, requestId="") ─┼─▶ 멱등 키 "" 하나를 전부 공유 → 선점 붕괴·DoS
  같은 요청 재전송          ─┘    (서명은 여전히 유효)
  교정: 진위(상수시간) → 신선도 창 → 빈 키 거절 → DB UNIQUE로 선점

[변형 B — 신선도가 다른 두 소스를 OR]
  이번 턴: "코드 봐줘"      → 사이드카(동기)   = 승인 없음
  지난 턴: "푸시해줘"       → 로그 tail(지연) = 승인 있음
  판정 = 사이드카 OR 로그  → 통과!  (과거 승인이 현재를 통과시킴)
  교정: 사이드카가 비어있지 않으면 그것만(authoritative), 로그는 부재 시 폴백
        캡처 쓰기 실패 → 옛 파일 삭제(inert), 턴·시각 창 밖 무효

[방안 비교 — stateless 토큰]
  비번 변경·탈퇴 → 토큰은 만료까지 유효 (서버가 상태를 안 봄)
  교정: 해당 흐름에서 명시 폐기(revoke by userId)
```

## 핵심 문장

- 서명은 **진위**(누가 만들었나)만 증명한다. **신선도**(지금 것인가)와 **결속**(이 행위 1회인가)은 별도 장치가 필요하다.
- 멱등 키가 비면 모든 요청이 **한 키로 충돌**한다 — 빈 키는 입구에서 거절한다.
- 선점 판정은 writer 코드가 아니라 **DB UNIQUE 제약**(INSERT 시점)에 둔다 — 동시 요청에서도 하나만 이긴다.
- 신선도가 다른 두 소스를 **OR로 합치면** 가장 오래된 긍정 신호가 현재 결정을 오염시킨다 → **우선순위**(신선한 소스 authoritative, 지연 소스는 부재 시 폴백).
- 쓰기 실패를 무시하면 **이전 턴의 승인 파일**이 남는다 → 실패 시 지운다.
- stateless 토큰은 서버가 **명시적으로 폐기**하지 않으면 만료까지 유효하다.
