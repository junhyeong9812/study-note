## 질문
1. (왜) HMAC 서명 검증을 통과한 요청은 "진짜"다. 그런데 왜 서명만으로는 **재전송(replay)** 을 막지 못하는가? 서명이 증명하는 것과 증명하지 못하는 것을 구분하라.
2. (예측) 멱등 키(`requestId`)로 중복 실행을 막는 서버에, 멱등 키가 **빈 문자열**인 요청이 올바른 서명과 함께 여러 건 들어오면 무슨 일이 생기는가?
3. (경계) 진위 확인 → 신선도 확인 → 멱등 키 선점. 이 순서는 왜 이 순서인가? 선점 판정을 애플리케이션 코드가 아니라 **DB UNIQUE 제약**에 맡기는 이유는?
4. (예측) 승인 신호가 두 곳에 있다 — 현재 턴을 동기로 캡처한 파일(신선), 비동기로 기록되는 대화 로그(지연). false-block을 고치려고 둘을 **OR로 합치면** 어떤 새 결함이 생기는가?
5. (왜) 비동기로 기록되는 로그를 "방금 일어난 일"의 판정 소스로 쓰면 안 되는 이유는? 두 소스를 쓸 때 "합집합" 대신 "우선순위(authoritative + 폴백)"를 택해야 하는 이유는?
6. (경계) 승인 캡처 파일의 쓰기 실패를 `|| true`로 무시하면, 다음 판정은 어떤 파일을 보게 되는가? 쓰기 실패 시 무엇을 해야 안전한가?
7. (연결) stateless 토큰(JWT)은 서버가 매 요청 사용자 상태를 재조회하지 않는다. 비밀번호 변경·탈퇴 이후에도 그 토큰이 유효한 이유는? "과거 승인이 현재를 통과시킨다"는 앞의 사례들과 어떻게 같은 문장으로 설명되는가?
