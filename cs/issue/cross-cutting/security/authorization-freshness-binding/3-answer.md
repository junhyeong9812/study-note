## 정답
<!-- 질문 1:1 대응 -->

1. **서명은 진위이지 신선도가 아니다.** HMAC 서명은 "비밀 키를 가진 쪽이 이 바이트를 만들었다"만 증명한다.\
   같은 바이트를 한 번 더 보내면 서명은 여전히 맞으므로, 서명 검증만으로는 **재전송**을 구분할 수 없다.\
   재전송을 막으려면 발급 시각·만료 창(issuedAt/expiresAt) 같은 **신선도**와, 그 요청 1회를 소모시키는 **멱등 키 선점**이 따로 필요하다.
   > **replay(재전송) 공격** — 정상적으로 서명된 과거 요청을 그대로 다시 보내 같은 행위를 한 번 더 일으키는 것.

2. **모든 무-ID 요청이 한 키를 공유한다.** 멱등 키가 `""`이면 "이 키는 이미 처리됨" 판정이 전 요청에 공통으로 걸린다.\
   첫 요청이 `""`을 선점하면 이후 다른 내용의 요청도 전부 "중복"으로 막히거나(가용성 붕괴·DoS), 선점 의미 자체가 무너진다.\
   서명이 맞다는 사실은 이 충돌과 무관하다 — 그래서 빈·공백 키는 **입구(첫 게이트)에서 거절**한다.
   > **멱등 키(idempotency key)** — 같은 요청을 여러 번 받아도 한 번만 실행되게 하는, 요청마다 고유한 식별자.

3. **싼 거절부터, 부작용은 마지막.** 진위가 틀린 요청은 신선도를 볼 가치도 없고, 신선도가 지난 요청으로 멱등 키를 소모하면 안 된다.\
   그래서 진위(상수시간 비교) → 신선도 → 선점 순이다. 선점은 곧 "키를 소비하는 쓰기"라서 앞의 검사를 모두 통과한 뒤에만 한다.\
   선점을 코드의 "조회 후 삽입"으로 하면 동시 요청 두 건이 모두 "없음"을 보고 둘 다 통과한다(check-then-act).\
   DB UNIQUE 제약은 INSERT 시점에 원자적으로 하나만 성공시키므로 선점의 진실 소스가 된다. 원장은 append-only로 두어 선점 기록을 지울 수 없게 한다.\
   중복이 나면 저장된 digest와 대조해 "같은 내용 = 재전송", "다른 내용 = 충돌"로 가른다.
   > **canonicalize(정규화)** — 서명 대상 바이트를 만드는 규칙. 서명자와 검증자가 다른 규칙을 쓰면 정상 요청도 거절되므로 한 곳에서만 정의한다.

4. **과거 승인이 현재를 통과시킨다.** 이번 턴에는 승인이 없어도, 지연 소스(로그 tail)에 **지난 턴의 "푸시해줘"** 가 남아 있으면 OR 판정이 참이 된다.\
   false-block(방금 한 승인을 못 봄)을 고치려던 수정이 false-pass(지난 승인으로 통과)를 새로 만든 것이다.
   > **false-pass** — 막아야 할 행위를 허용하는 판정 오류(보안 쪽 실패).

5. **비동기 로그는 최신 턴이 아직 안 써져 있을 수 있다.** "지금 막 일어난 일"을 판정하려면 그 일을 **동기로** 기록한 소스가 필요하다(read-your-writes).\
   두 소스를 합집합으로 쓰면 결과는 "둘 중 더 관대한 쪽"이 되고, 오래된 긍정 신호가 항상 이긴다.\
   우선순위로 쓰면 신선한 소스가 있을 때는 그것만 보고, 지연 소스는 신선한 소스가 **없을 때만** 폴백으로 본다.\
   존재 검사는 "파일 있음"이 아니라 "비어 있지 않음"으로 해야, 빈 파일이 폴백까지 막지 않는다.
   > **read-your-writes** — 방금 쓴 것을 곧바로 읽을 수 있음이 보장되는 일관성. 비동기 로그는 이를 보장하지 않는다.

6. **이전 턴의 승인 파일을 본다.** 쓰기가 실패했는데 오류를 삼키면 파일은 갱신되지 않고, 판정기는 그걸 "현재 턴"으로 읽는다.\
   안전한 처리는 쓰기 실패 시 **기존 파일을 지워 무효(inert)로 만드는 것**이다. 그러면 판정은 "승인 없음" 쪽으로 기운다.\
   덧붙여 턴 카운터와 시각 창(미래 시각·오래된 시각 무효)으로 파일이 "이 턴의 것"인지 확인한다.\
   이 계열은 결국 문자열 판정을 버리고, 행위 직전에 **네이티브 확인 UI**가 사용자에게 묻는 구조화 신호로 옮겨 끝났다.

7. **토큰은 발급 시점의 승인을 들고 다닌다.** 서버가 매 요청 사용자 상태를 재조회하지 않으면, 비번 변경·탈퇴 뒤에도 토큰의 서명과 만료만 보고 통과시킨다.\
   즉 "발급 당시의 승인"이 "지금의 상태"를 대신한다 — 변형 B의 stale 승인과 같은 문장이다.\
   해법은 그 흐름(비번 변경·탈퇴·삭제·권한 변경)에서 **사용자 단위로 토큰을 명시 폐기**하는 것이다.
   > **stateless 토큰** — 서버가 세션 상태를 보관하지 않고 토큰 자체의 서명·클레임만으로 인증하는 방식. 폐기는 별도 저장소가 있어야 가능하다.

## 문제 구조 (추상화 코드)

### 변형 A — 서명 검증만 하고 신선도·빈 멱등 키를 보지 않음
① 문제 코드
```go
func handle(req Request) Response {
    if !hmacValid(req) { return reject(401) }
    if ledger.Exists(req.RequestID) { return reject(409) }   // "" 도 하나의 키
    ledger.Insert(req.RequestID)                              // check-then-act
    return execute(req)
}
```
② 고친 코드
```go
func handle(req Request) Response {
    if !hmacConstantTimeValid(canonicalize(req)) { return reject(401) }  // 진위
    if !withinWindow(req.IssuedAt, req.ExpiresAt) { return reject(401) } // 신선도
    if strings.TrimSpace(req.RequestID) == "" { return reject(400) }     // 빈 키 거절
    err := ledger.Insert(req.RequestID, req.Jti, digest(req))            // UNIQUE(request_id), UNIQUE(jti)
    if isUniqueViolation(err) {
        prev := ledger.Get(req.RequestID)
        if prev.Digest == digest(req) { return reject(409 /* replay */) }
        return reject(409 /* conflict: 같은 키, 다른 내용 */)
    }
    return execute(req)
}
```
무엇이 깨졌나: 진위가 곧 허가로 쓰였고, 빈 키가 모든 요청을 한 슬롯에 몰았다.

### 변형 B — 신선도가 다른 두 승인 소스를 OR로 합침
① 문제 코드
```sh
APPROVAL="$(cat "$SIDECAR" 2>/dev/null) $(tail -n 50 "$TRANSCRIPT")"   # 합집합
approved "$APPROVAL" && exit 0
# 캡처 훅
echo "$PROMPT" > "$SIDECAR" || true        # 실패해도 지난 턴 파일이 남음
```
② 고친 코드
```sh
if [ -s "$SIDECAR" ] && fresh "$SIDECAR"; then     # 비어있지 않고 이 턴의 것
  APPROVAL="$(cat "$SIDECAR")"                     # authoritative
else
  APPROVAL="$(tail -n 50 "$TRANSCRIPT")"           # 부재 시에만 폴백
fi
# 캡처 훅
write_atomic "$SIDECAR" "$TURN $TS $PROMPT" || rm -f "$SIDECAR"   # 실패 = inert
# fresh(): 턴 번호 일치 && 0 <= now-ts <= 창, 미래 시각 무효
```
무엇이 깨졌나: 지연 소스의 오래된 긍정 신호가 현재 판정에 섞였고, 쓰기 실패가 옛 승인을 되살렸다.\
같은 구조: 대화 로그(비동기 기록)만 보던 시절에는 반대로 방금 한 승인을 못 봐 연속 false-block — 동기 캡처로 신선 소스를 만든 것이 출발점이었다.

## 방안 비교

기본 방안(위 변형 A·B)은 "승인 신호마다 신선도·1회성을 검사해 판정 시점에 결속한다"이다. 같은 원리에 다른 방안이 쓰인 사례:

### 방안 1 — stateless 토큰의 명시 폐기
```java
// 문제: 필터는 서명·만료·jti 활성만 봄 → 탈퇴·삭제 흐름이 폐기를 안 부르면 토큰이 계속 유효
void withdraw(long userId) { users.markWithdrawn(userId); }

// 고친
void withdraw(long userId) {
    users.markWithdrawn(userId);
    tokenStore.revokeAll(userId);       // 비번 변경·탈퇴·삭제·권한 변경 모두에서
}
```

| 방안 | 전제 | 비용 | 실패 모드 | 맞는 조건 |
|------|------|------|-----------|-----------|
| 기본: 판정 시 신선도·1회성 결속 | 요청마다 시각·키를 실을 수 있다 | 원장·창 관리, 저장소 쓰기 | 창 안의 재전송은 원장 없이는 못 막음 | 서명 요청·승인 신호처럼 1회 소모형 |
| 1. 상태 변화 시 명시 폐기 | 토큰 활성 여부를 서버가 조회한다(jti 레지스트리) | 폐기 호출 지점 전수 관리 | 폐기를 부르지 않는 흐름이 하나라도 있으면 그 경로로 유효 | 재사용되는 장기 토큰(세션형 JWT) |

**결론**: 1회 소모형 신호(서명 요청·승인)는 판정 시점에 신선도와 멱등 선점으로 결속하는 쪽이 맞다.\
여러 번 재사용되는 토큰은 요청마다 결속할 수 없으므로, 사용자 상태가 바뀌는 **모든** 흐름에서 명시 폐기해야 한다 — 폐기 지점 누락이 곧 우회 경로다.
