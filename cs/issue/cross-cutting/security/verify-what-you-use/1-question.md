## 질문
1. 파서 차이(parser differential)란 무엇인가. 검증기는 관대한 JSON 파서(미지 필드 무시·중복 키 뒤엣것 승리)로, 실제 소비자는 다른 규칙으로 같은 입력을 읽으면 어떤 입력이 "검증 통과 + 다른 의미"가 되는가.
2. 보안 모드 설정값을 `trim().lowercase()`로 관대하게 정규화한 뒤 비교했더니 무서명 요청이 통과했다. 정규화가 왜 "엄격 검증 계약"을 조용히 완화하는가 — 이런 설정값은 어떻게 비교해야 하는가.
3. 예측: 인가 필터와 라우터가 요청 경로를 서로 다른 방식으로 정규화한다. `%2e%2e`·중복 슬래시가 섞인 요청은 두 계층에서 각각 어떻게 해석될 수 있고, 무엇이 뚫리는가. 서명자와 검증자가 경로를 "디코드된 값" vs "원문"으로 쓰면 무엇이 깨지는가.
4. "URL이 `https://`로 시작하는지 검사"가 실제 통신의 HTTPS를 보장하지 못하는 이유는? 리다이렉트를 검사하도록 고칠 때 공유 HTTP 클라이언트의 기존 정책 훅을 덮어쓰면 무엇이 새로 깨지는가.
5. 검증 시점과 사용 시점 사이가 분 단위로 벌어진 파일(배포 정의서)을 "사용 직전에 다시 검증"하면 해결되는가. "검증한 바이트 자체를 불변 스냅샷으로 굳혀 실행기에 결박"은 무엇이 다른가.
6. 경계: 셸 명령 치환 `$(...)`은 후행 개행을 제거하고, 많은 정규식의 `$`는 "문자열 끝 또는 마지막 개행 앞"에 매칭된다. 이 두 성질이 입력 검증을 어떻게 우회시키는가. 불량 문자를 "삭제"하는 정규화는 왜 또 다른 문제를 만드는가.
7. 연결: 해시(식별자)와 내용을 **같은 in-memory 버퍼 한 번 읽기**에서 산출해야 하는 이유는? 그리고 "승인 화면에 보여준 대상"과 "실제 실행될 대상"이 다를 때 이것이 왜 같은 원리의 문제인가.
