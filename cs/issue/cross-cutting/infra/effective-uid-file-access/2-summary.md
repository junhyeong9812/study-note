# cs/issue/infra/effective-uid-file-access — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
"누가 명령을 쳤나" ≠ "누가 파일을 여나"

 [컨테이너]   sudo compose up  → 컨테이너 프로세스 uid = 이미지가 정한 1000
              bind 디렉터리 소유 root → lock·업로드 쓰기 거부 → 즉사/크래시 루프
              교정: 디렉터리를 그 uid로 chown (NFS root_squash·CIFS는 마운트 옵션으로)

 [존재≠읽기]  파일: -rw------- root (+ACL, umask 077)
              앱 uid 1000 → isReadable=false → 404 (빈 본문, 1ms)
              chown -R = 기존 파일만 → 다음 적재분은 다시 600 root
              교정: 생산자 umask/명시 권한 + default ACL 확인

 [셸]         sudo cmd > LOG
              └ LOG는 sudo가 아니라 "호출한 셸"이 먼저 연다 → 명령 실행 전 실패
              교정: 로그는 쓸 수 있는 곳, 권한은 명령에만

 [그룹]       usermod -aG docker  → 이미 뜬 프로세스의 보조 그룹은 그대로
              교정: 서비스 재시작(대화형은 재로그인/newgrp)

 [혼용 계정]  root 소유 파일 섞임 → pull 중간 실패 → 작업 트리 반쯤 갱신
              교정: 실사용 계정으로 chown, sudo pull 금지, 부분 파일 복원 후 재시도
```

## 핵심 문장
- 파일 권한은 **실제로 open()을 호출하는 프로세스**의 uid·gid·보조 그룹으로 판정된다.
- 컨테이너 프로세스는 호스트에서 누가 띄웠든 **이미지가 정한 uid**로 돈다.
- "존재"와 "읽기 가능"은 다르다 — 그리고 `chown -R`은 과거 파일만 고친다. 재발을 막으려면 **생산자**(umask·ACL)를 고친다.
- 리다이렉트는 sudo 권한이 아니다 — 호출한 셸이 연다.
- 보조 그룹은 프로세스 생성 시 확정된다 — 그룹 추가 후엔 재시작.
