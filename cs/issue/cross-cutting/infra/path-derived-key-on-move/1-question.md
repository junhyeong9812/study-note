## 질문
1. (왜) 앱이 프로젝트별 저장 키를 `basename + 절대경로 해시`로 만든다. 저장소 폴더 이름만 `mv`로 바꿨을 뿐인데 세션 목록·아카이브·설정 등록이 한꺼번에 "사라진" 것처럼 보이는 이유는. 데이터는 실제로 지워졌는가.
2. (예측) 폴더 개명 후 증분 빌드(`cargo build`)가 빌드 스크립트 단계에서 실패했다. `target/*/build` 아래 캐시에 무엇이 들어 있었길래 소스는 멀쩡한데 빌드가 옛 경로를 찾는가. 왜 빌드 도구는 이 캐시를 스스로 무효화하지 못했는가.
3. (설계) 키 이관을 안전하게 하려면 "새 키"를 어떻게 믿을 수 있는가 — 키 알고리즘을 코드 밖에서 재현해 기존 키와 대조하는 단계가 왜 먼저 와야 하는가.
4. (검증) 이관이 끝났음을 무엇으로 증명하는가. "앱이 떴다"가 아니라 record-level로 볼 항목은(예: 이관 전후 개수 diff).
5. (경계) 같은 개명 작업에서 **바꾸지 않기로 한** 식별자(예: 앱 번들 식별자)가 있었다. 왜 모든 이름을 새 이름으로 맞추지 않았는가 — 그 식별자에서 또 무엇이 파생되는가.
6. (연결) "가변 속성에서 파생한 키"를 피하는 일반 설계는 무엇인가(불변 ID 발급·경로는 속성으로만 저장). 경로 기반 키가 그래도 쓰이는 이유와, 쓴다면 이동 시 동반해야 할 절차는.
