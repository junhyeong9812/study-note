## 정답
<!-- 질문 1:1 대응 -->

1. **키가 경로에서 파생되기 때문이다. 데이터는 지워지지 않았다.** \
   저장 키 = `basename + 경로 해시`이므로 폴더를 옮기면 같은 프로젝트가 **다른 키**로 계산된다. \
   스냅샷·아카이브 디렉토리, workspace 설정, 도구 등록 파일, 메모리 슬러그가 모두 옛 키 이름으로 저장돼 있으니, 앱은 새 키로 찾고 아무것도 없다고 판단한다. \
   데이터는 옛 키 아래에 **고스란히 남아 있지만 아무도 가리키지 않는** 고아가 된다.
   > **파생 키(derived key)** — 엔티티의 다른 속성에서 계산해 만든 식별자. 원 속성이 바뀌면 키도 바뀐다.

2. **빌드 스크립트 산출물에 절대경로가 캐시돼 있었다.** \
   빌드 스크립트(`build.rs` 류)의 결과물은 `target/*/build/` 아래에 저장되고, 그 안에 소스·출력 위치가 절대경로로 기록된다. \
   증분 빌드는 "추적 대상 입력(파일 mtime·rerun-if 목록 등)이 바뀌었나"로 재실행을 결정하는데, `mv`는 내용·mtime을 보존하므로 변경이 없다고 보고 캐시를 재사용하고, 그 캐시는 이제 존재하지 않는 옛 경로를 가리킨다. \
   캐시의 무효화 조건에 **"소스 트리의 위치"가 들어 있지 않아서** 스스로 알아채지 못했다(이 메커니즘은 일반론적 설명 — 원 기록은 "옛 경로 참조로 실패 → 삭제 후 green"까지). `target/{debug,release}/build`를 지우고 재빌드하면 해결된다.

3. **틀린 새 키로 옮기면 데이터를 한 번 더 고아로 만든다.** \
   이관은 "옛 키 → 새 키"로 디렉토리 이름과 메타 안의 키를 바꾸는 일이다. 새 키가 앱이 실제로 계산할 값과 한 글자라도 다르면, 옮긴 데이터를 앱이 또 못 찾는다. \
   그래서 먼저 키 알고리즘을 코드 밖(스크립트)으로 재현해 **현재 경로로 계산한 값 = 실측 기존 키**임을 확인하고, 그 뒤에야 같은 재현으로 계산한 새 키를 신뢰한다.

4. **이관 전후 개수 diff 0.** \
   스냅샷·아카이브·기타 항목의 개수를 옮기기 전과 후에 세어 모두 같음을 확인했다(항목별 개수 일치, diff 0). 메타 안의 키 필드도 갱신 건수만큼 확인한다. \
   "앱이 뜬다"는 데이터가 **보인다**는 증거가 아니다 — 고아가 생겨도 앱은 빈 목록으로 정상 기동한다.

5. **그 식별자에서도 상태 경로가 파생되기 때문이다.** \
   앱 번들 식별자는 (플랫폼·앱 프레임워크에 따라) 앱 상태(설정·저장소) 디렉토리 경로를 정하는 데 쓰인다. 그것까지 새 이름으로 바꾸면 **같은 문제(경로 파생 키의 고아화)를 한 번 더** 일으킨다. \
   개명 범위는 "사람이 보는 표기"로 한정하고, 다른 상태가 매달린 식별자는 불변으로 둔다.

6. **불변 ID를 발급하고 경로는 속성으로 저장한다.** \
   프로젝트 생성 시 UUID 같은 불변 ID를 주고 경로는 그 ID의 가변 속성으로 두면, 이동은 속성 한 줄 갱신으로 끝난다. \
   경로 기반 키를 쓰는 이유는 "같은 경로 = 같은 프로젝트"를 별도 등록 없이 얻는 편의 때문이다. 쓴다면 이동은 **키 재계산 → 데이터·참조 이관 → 파생 캐시 무효화 → 개수 검증**을 한 묶음으로 수행하는 마이그레이션으로 다룬다.
   > **캐시 무효화(invalidation)** — 캐시가 기대는 입력이 바뀌었을 때 캐시를 버리는 것. 입력 목록에 빠진 속성이 바뀌면 캐시는 조용히 틀린 값을 준다.

## 문제 구조 (추상화 코드)

### 변형 A — 경로 해시로 만든 저장 키

① 문제 코드
```rust
fn project_key(path: &Path) -> String {
    let base = path.file_name().unwrap().to_string_lossy();
    format!("{}-{:016x}", base, fnv1a(path.to_string_lossy().as_bytes()))  // 경로 = 키 입력
}
// snapshots/<key>/ · archive/<key>/ · meta.project = <key> · 설정 파일들에 경로 기록
// $ mv /work/old-name /work/new-name   → project_key 가 바뀜 → 전부 조회 안 됨
```
② 고친 절차
```bash
# 0) 키 재현 검증: 외부 스크립트로 계산한 key(/work/old-name) == 실측 기존 키
# 1) mv /work/old-name /work/new-name
# 2) 새 키 계산(같은 재현) → snapshots/<old>/ → snapshots/<new>/, archive 도 동일
# 3) 각 meta 의 project 필드 <old> → <new>
# 4) workspace 설정 · 도구 등록 파일 · 메모리 슬러그 이관
# 5) 검증: 이관 전후 항목별 개수 diff 0
# (앱 번들 식별자 = 상태 경로의 파생 원천 → 변경하지 않음)
```
무엇이 깨졌나: 키가 가변 속성(경로)에서 계산돼, 이동만으로 모든 저장 데이터가 참조를 잃었다.

### 변형 B — 빌드 스크립트 캐시에 박힌 절대경로

① 문제 구조
```text
target/debug/build/<crate>-<hash>/output   ← 빌드 스크립트가 기록한 /work/old-name/... 절대경로
$ mv /work/old-name /work/new-name
$ cargo build   → 추적 입력(mtime 등) 불변 → 캐시 재사용 → 옛 경로 참조 → 실패   (메커니즘은 일반론)
```
② 고친 절차
```bash
rm -rf target/debug/build target/release/build   # 위치 의존 캐시만 제거
cargo build                                       # 빌드 스크립트 재실행 → 새 경로로 재기록
```
무엇이 깨졌나: 캐시의 무효화 입력에 "소스 트리 위치"가 없어, 위치가 바뀐 뒤에도 옛 절대경로를 담은 캐시가 유효하다고 판단됐다.\
같은 구조: 같은 개명의 다른 기록 2건 — 개명 후 증분 빌드가 옛 경로를 참조해 `target/*/build` 삭제로 해결(하나는 미머지 브랜치 바이너리와 혼동한 부수 증상 동반).
