# cs/issue/infra/path-derived-key-on-move — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
키 = f(가변 속성)  →  속성이 바뀌는 순간 키가 바뀐다  →  옛 키에 매달린 데이터는 고아

[변형 A — 앱 저장 키]
   key = basename(path) + "-" + hash(path)
   /work/old-name  → key_old ──┬─ snapshots/key_old/
                               ├─ archive/key_old/
                               ├─ workspace 설정·도구 등록·메모리 슬러그
   mv → /work/new-name → key_new → 전부 "없음" (데이터는 옛 키 아래 그대로)

   교정: 키 알고리즘을 외부에서 재현 → 기존 키와 일치 확인(= 새 키 신뢰)
         → mv → 디렉토리 rename(key_old→key_new) → 메타 안의 키 갱신
         → 설정·등록·메모리 이관 → 개수 diff 0 검증
         (앱 식별자처럼 또 다른 상태 경로가 파생되는 이름은 불변 유지)

[변형 B — 빌드 스크립트 캐시]
   target/*/build/<crate>/  ← 빌드 스크립트 산출물에 절대경로 기록
   mv → 증분 빌드가 캐시의 옛 절대경로 참조 → 실패
   교정: rm -rf target/{debug,release}/build → 재빌드
```

## 핵심 문장
- 파생 키가 **가변 속성(파일시스템 경로)**에서 계산되면, 그 속성이 바뀌는 순간 기존 데이터는 지워지지 않았는데도 **찾을 수 없게**(고아) 된다.
- 그래서 이동은 단순 `mv`가 아니라 **키 재계산 + 데이터 이관 + 무효화**를 동반하는 마이그레이션이다.
- 새 키를 믿기 전에 알고리즘을 재현해 **기존 키와 일치하는지** 먼저 대조한다 — 틀린 키로 이관하면 두 번 고아를 만든다.
- 완료 증명은 앱 기동이 아니라 **이관 전후 개수 diff 0**(record-level).
- 캐시가 절대경로를 품고 있으면 캐시 무효화 키에 "위치"가 없다 → 이동 후엔 그 캐시를 직접 지운다.
