# cs/issue/infra/state-drift-delete-propagation — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
문제의 뿌리: "복사"는 더하기만 하고 빼기를 못 한다.

[사건 A — rsync 잔재]
  로컬:  common/ 삭제, api/ 신설 (git mv)
  rsync -a (--delete 없음) → 서버에 common/ + api/ 둘 다 존재 (유령 파일)
  Docker COPY src → 옛/새 전부 컴파일 → Spring "같은 빈 이름 둘" → 기동 거부
  fix: rsync -a --delete --exclude .env   (사라진 건 서버에서도 지우되, .env는 보호)

[사건 B — 설정 채널 부재]
  파이프라인: 코드는 이미지에 담아 나름 → 하지만 compose 파일은 이미지 "밖"
  compose는 컨테이너를 밖에서 띄우는 정의 → 이미지 안에 넣어봐야 아무도 안 읽음
  → 호스트 compose는 옛 rsync 사본 그대로, GitHub 변경과 무관
  fix: 전달 채널을 git 하나로 수렴
       agent가 배포 직전 git fetch + reset --hard <sha> → compose·설정이 최신
       순서: 설정 동기화 → 컨테이너 갱신 (설정이 코드보다 먼저 도착)
```

공통 원인 = **state drift**: 정본(로컬/GitHub)과 대상(서버)이 조용히 어긋난다.
공통 해법 = 정본을 하나로 못박고, 대상을 그 정본으로 **재구성**(복사가 아니라 동기화)한다.

## 핵심 문장
- "복사"만 하는 배포는 **삭제를 전달하지 못한다** — 파일 이동이 큰 리팩토링일수록 서버에 잔재가 쌓인다.
- 이미지 채널은 "컨테이너 안의 코드"만 나른다. compose·env 같은 "컨테이너 밖 설정"은 별도 채널이 필요하고, 채널이 없으면 그 설정은 영원히 옛날 상태다.
- 채널을 둘로 두면 drift가 생긴다 → **git 하나로 수렴** → "배포된 것 = 그 커밋"이 항상 성립.
- `reset --hard`는 **추적 파일만** 되돌린다 → git 미추적인 `.env`(시크릿)는 살아남는다 = 안전장치.
- 이번엔 Spring이 기동을 거부(시끄러운 실패)해 즉시 잡혔다. 충돌 없는 잔재였다면 옛 코드가 **조용히** 섞여 돌았을 것 — silent failure가 더 무섭다.
