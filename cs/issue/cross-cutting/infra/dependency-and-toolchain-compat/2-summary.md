# cs/issue/infra/dependency-and-toolchain-compat — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
코드 ─ import ─▶ 선언(매니페스트) ─ 해석 ─▶ 실제 트리(lock·dependency:tree)
                                              │
                                              ▼
                        실행 런타임(JDK·Node·Python) ── 외부 상대(데몬·서버·OS)

 [A 선언]     import 추가 ≠ 매니페스트·이미지 갱신 → ModuleNotFound / 미해결 import
              이름 비슷한 포크 패키지 → 엉뚱한 구현
 [B 해석]     상위만 핀 → 전이 의존성 최신 → import 시점 폭발
              선언 삭제 → 다른 공급원이 전이로 계속 공급
              스코프·classifier·BOM 범위 → 어떤 버전이 컴파일 경로에 오나
              서로 위임하는 브리지 동시 존재 → 기동 거부
              peer 범위 불일치 → npm 7+ 트리 조작 거부
 [C 런타임]   개발 3.12 / 운영 3.10 · 로컬 Node 18 / 이미지 Node 22
              도구 자체도 런타임 위에서 돈다(빌드 도구 × JDK)
              셸 초기화에서만 PATH 주입 → 비대화형 셸은 구버전
 [D 상대편]   데몬 최소 API↑ × 클라이언트 구 API → 협상 실패
              shade된 사본엔 override가 안 닿음 → 라이브러리 자체 업그레이드
              서버 옵션 제거(메이저 업) / WS 구현 메이저 비호환

 확인은 "문서·README"가 아니라
   게시된 메타데이터(pom·module) · 실제 해석 트리 · 대상 런타임에서 실행
```

## 핵심 문장
- import를 추가해도 매니페스트와 이미지는 저절로 갱신되지 않는다 — 선언이 정본이다.
- 최종 해석 트리가 정본이다 — 상위만 핀하면 전이가 끌려오고, 선언을 지워도 다른 공급원이 남는다.
- 개발 런타임과 실행 런타임의 버전이 다르면 표준 API 가용성부터 갈린다 — 테스트도 실행 런타임(이미지)에서 돌린다.
- 클라이언트·서버는 **협상**한다 — 상대의 최소 요구가 오르면 구 클라이언트는 기동조차 못 한다. shade된 사본에는 외부 의존성 override가 닿지 않고, 설정도 라이브러리가 전달하지 않으면 닿지 않는다.
- 조용한 진단: 로거 바인딩이 없으면 라이브러리의 원인 로그가 버려진다 — 먼저 로그를 살린다.
