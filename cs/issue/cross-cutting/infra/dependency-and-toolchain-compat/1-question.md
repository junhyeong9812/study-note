## 질문
1. (예측) 로컬 Python 3.12에서 `from itertools import batched`로 쓴 스크립트를 3.10 서버에서 돌리면 어디서 깨지는가. 빌드 도구(Gradle)를 지원 범위 밖 JDK에서 돌리면 왜 에러 메시지가 버전 문자열 한 줄뿐일 수 있는가.
2. (왜) 호스트 셸에서는 `docker ps`가 되는데 테스트 JVM만 "유효한 Docker 환경 없음"이라 한다. 클라이언트 라이브러리와 데몬 사이 무엇이 협상되며, 진단 로그는 왜 안 보였는가.
3. (경계) 라이브러리가 의존성을 **shade**(자기 jar 안에 패키지 재배치해 내장)하면, 외부에서 그 의존성 버전을 override하거나 환경변수·프로퍼티로 설정해도 왜 닿지 않는가. 남는 대응은 무엇인가.
4. (예측) 상위 라이브러리 버전만 핀했더니 전이 의존성이 최신으로 끌려와 import 시점에 `NameError`가 났다. 반대로, 쓰지 않는 의존성 선언을 지웠는데 그 라이브러리가 클래스패스에 계속 남아 있다. 두 사건에서 "정본"은 무엇인가.
5. (왜) 로깅 브리지 두 개(`A → B` 위임과 `B → A` 위임)가 같은 클래스패스에 있으면 로깅 프레임워크가 기동을 거부한다. 왜인가.
6. (경계) npm 7+에서 `npm uninstall` 하나가 peer dependency 충돌로 실패했다. peer 의존성은 일반 의존성과 무엇이 다르며, 우회 플래그의 대가는 무엇인가.
7. (연결) 같은 원리의 다른 방안들: 커밋된 wrapper 스크립트 체크섬 검증, HTTP 클라이언트의 HTTP/2 협상 고정, GNU 전용 옵션의 폴백, 타입드 클라이언트가 모델링 안 한 옵션. 이들은 각각 "무엇과 무엇의 호환"을 확인하지 않아 생긴 일인가.
