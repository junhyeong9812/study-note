## 정답
<!-- 질문 1:1 대응 -->

1. **병목이 로더 CPU에서 디스크로 옮겨 갔다.**\
   DB와 검색 엔진 데이터가 같은 물리 디스크에 있었고, 로더를 늘리자 디스크 사용률이 65~95%로 포화됐다.\
   포화된 자원에 동시 요청을 더 얹으면 처리율은 기껏해야 제자리이고, HDD처럼 동시 스트림이 탐색(seek)을 늘리는 자원에선 경합 비용 때문에 오히려 떨어진다.\
   처방: 대상을 겹치지 않게(disjoint) 배정하고 동시 2~3개를 sweet spot으로, 경쟁하는 색인 작업은 적재가 끝날 때까지 보류했다.

2. **프로세스 CPU 사용률은 I/O 대기를 보여주지 않기 때문이다(iowait 지표도 힌트일 뿐 장치 포화의 증거는 아니다).**\
   프로세스가 디스크를 기다리는 동안 CPU는 놀고 있어 "여유"처럼 보인다.\
   추적 순서: 컨테이너 마운트(`docker inspect`) → 그 경로의 물리 장치(`lsblk`) → 장치 사용률(`%util`).\
   "SSD라고 들은" 장치가 실제로는 회전 디스크(ROTA=1)였던 것도 이 순서로 드러났다.\
   처리율·ETA는 일정 간격 두 번 차분으로 실측하고, 매체 비교는 양쪽에 같은 벤치마크 워크로드를 돌려 판정한다(경로를 잘못 주면 OS 디스크를 재게 되니 대상 경로 확인).
   > **%util** — 장치가 요청을 처리하느라 바빴던 시간 비율. 요청을 하나씩 처리하는 장치(HDD)에선 100%에 가까우면 포화지만, 병렬 처리하는 SSD·NVMe·RAID에선 100%여도 여유가 있을 수 있어 대기 시간(await)·큐 길이(aqu-sz)를 함께 본다.

3. **병목은 동시성 부족(지연 바운드)이다 — 워커를 늘리면 처리량이 오른다.**\
   세 쪽 모두 여유인데 느리다면 대개 요청 하나의 왕복 지연이 처리량을 묶고 있는 것이다(네트워크 대역폭·락·GC 같은 다른 병목이 없는지는 따로 확인).\
   소비자 스레드풀의 active 수를 기준으로 워커를 8 → 20으로 늘리자 처리량이 약 1,000 → 7,200/s로 올랐다.\
   비용: 워커당 메모리(배치 1000건 기준 약 1GiB)가 늘어 앱 메모리가 8.8 → 19GiB가 됐다 — 힙 상한 여유를 먼저 확인한다.
   > **지연 바운드(latency-bound)** — 자원은 남는데 요청마다 기다리는 시간 때문에 처리량이 묶인 상태. 처리량 ≈ 동시 요청 수 ÷ 지연.

4. **"어느 자원이 포화인가"를 동시에 본 결과다.**\
   어떤 자원(디스크 %util, 스레드풀 queue·rejected)이 포화면 자원 바운드 → 동시성을 줄이거나 경쟁을 뺀다.\
   전부 여유면 지연 바운드 → 동시성을 늘린다.\
   한 지표(CPU)만 보면 두 경우를 구분할 수 없다.

5. **HDD 랜덤 IOPS는 수백 수준이라 그 지연·처리량과 맞지 않기 때문이다.**\
   키 기반 단건 조회는 캐시(버퍼 풀·페이지 캐시)에 없으면 랜덤 액세스라 HDD의 탐색 지연에 묶인다 — 작업 집합이 메모리에 안 들어간다는 전제에서 랜덤 IOPS 100~200으로는 341 req/s·p95 12.7ms가 나오기 어렵다(캐시 적중률이 높으면 HDD 위에서도 가능하므로 적중률도 함께 확인).\
   조사 결과 실제로는 SSD로 옮긴 뒤의 수치였다.\
   교훈: 성능 수치는 매체의 물리 상한과 대조해 모순을 찾는다.\
   적재 순서로 지역성을 만드는 우회는 파이프라인 복잡도가 커서 선택하지 않고, 데이터 최소화로 SSD에 수용했다.

6. **기동 거부·쿼터 오류·OOM이 난다.**\
   검색 엔진은 write 스레드풀을 코어+1 이하로 강제해 `must be <= 7`로 기동을 거부했다.\
   컨테이너 CPU 쿼터 8.0은 호스트 범위(0.01~6.00) 밖이라 거부됐다.\
   JVM 힙 합계 48GB는 RAM 32GB를 넘는다 — 힙이 실제로 차오르면 OOM(커널 OOM killer 포함) 위험.\
   이 값들은 호스트 코어·메모리에 **상대적**이라, 원본은 두고 호스트별 override로 조정한다(그 테스트값이 운영에 새어 들어가지 않게 주의).

## 문제 구조 (추상화 코드)

### 변형 A — 포화된 공유 디스크 위의 병렬화
① 문제 코드
```yaml
loader: { replicas: 5 }       # CPU 42%라 "여유"로 판단
db:     { volumes: [ /data/db:/var/lib/db ] }        # 같은 물리 디스크
search: { volumes: [ /data/search:/usr/share/data ] }
```
② 고친 코드
```yaml
loader: { replicas: 2 }       # 대상 disjoint 배정, 동시 2~3이 sweet spot
# 색인은 적재 일단락까지 보류
# 진단: docker inspect → lsblk(ROTA) → iostat %util
```
깨진 것: CPU만 보고 동시성을 늘려, 포화된 디스크의 경합이 처리율을 1/10로 떨어뜨렸다.

### 변형 B — 지연 바운드를 자원 부족으로 오인
① 문제 코드
```http
POST /migration/start { "workers": 8, "batchSize": 1000 }   # CPU·DB·소비자 모두 여유인데 느림
```
② 고친 코드
```http
POST /migration/start { "workers": 20, "batchSize": 1000 }  # in-flight↑, 워커당 ~1GiB 확인
```
진단: 생산자 CPU + 소비자 `thread_pool(active/queue/rejected)` + 원천 processlist 동시 관찰.\
깨진 것: 병목이 자원이 아니라 동시 요청 수였는데, 자원만 보고 있었다.

### 변형 C — 매체의 물리 상한과 모순된 수치
① 문제 서술
```
저장: HDD 위의 DB  /  성능: 341 req/s, p95 12.7ms (키 기반 단건 조회 = 랜덤 I/O)
```
② 교정
```
HDD 랜덤 IOPS ≈ 100~200 → 모순 → 매체 확인 → 실제 SSD
```
깨진 것: 기록된 성능이 기록된 매체의 물리 상한과 맞지 않았다.

### 변형 D — 호스트 상대값의 절대값 이식
① 문제 코드
```yaml
search:
  environment: [ "thread_pool.write.size=20", "JAVA_OPTS=-Xmx..." ]   # 인스턴스 5개 힙 합계 48GB
  deploy: { resources: { limits: { cpus: '8.0' } } }
```
② 고친 코드
```yaml
# override 파일 (호스트별)
search:
  environment: [ "thread_pool.write.size=4", "JAVA_OPTS=-Xms2g -Xmx2g" ]
  deploy: { resources: { limits: { cpus: '2.0' } } }
# 검산: Σ heap + 힙 외 메모리 + OS 페이지 캐시 여유 < RAM, cpus ≤ 코어 수, write pool ≤ 코어+1(이 검색 엔진의 제약)
```
깨진 것: 코어·RAM에 비례해야 할 값을 절대값으로 옮겨 다른 호스트에서 기동 거부·OOM이 났다.
