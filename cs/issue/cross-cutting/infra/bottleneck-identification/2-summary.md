# cs/issue/infra/bottleneck-identification — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
처리량 설정(병렬도·스레드풀·힙) ── 은 ──▶ 실제 병목에 "상대적인" 값

 [진단] 생산자 CPU  ·  소비자 큐(active/queue/rejected)  ·  원천(DB processlist)
        ·  디스크(마운트 → 물리 장치 → %util)  을 "동시에" 본다

   ┌── 어느 자원이 포화 ──▶ 자원 바운드
   │     디스크 %util 65~95% → 동시성↑ = 경합↑ = 처리율↓
   │     처방: 동시 수를 sweet spot으로, 경쟁 작업(색인) 보류, 분리 배정
   │
   └── 전부 여유인데 느림 ──▶ 지연 바운드(왕복 대기)
         처방: in-flight 수(워커)↑ → 처리량↑  (워커당 메모리 비용 확인)

 [물리 상한 점검]
   HDD 랜덤 IOPS ~ 수백  vs  주장된 단건 조회 처리량/지연
   → 모순이면 "매체가 다르다"를 의심하고 확인

 [이식]
   스레드풀 · CPU 쿼터 · 힙 = 호스트 코어/RAM 상대값
   절대값 이식 → 기동 거부(검증 한도 초과) · 쿼터 범위 오류 · OOM
   처방: 호스트별 override, 합계 검산
```

## 핵심 문장
- 공유 자원(디스크)이 병목이면 동시성을 늘릴수록 경합만 늘어 **처리율이 떨어진다**.
- CPU idle은 I/O 포화를 보여주지 않는다 — "여유"는 마운트 → 물리 장치 → 사용률(%util)로 추적한다.
- 모든 자원이 여유인데 느리면 병목은 **지연(왕복 대기)**이다 — in-flight 요청 수를 늘려야 처리량이 오른다.
- 성능 수치는 매체의 물리 상한(HDD 랜덤 IOPS 수백)과 대조해 모순을 찾는다.
- 스레드풀·CPU 쿼터·힙은 호스트 사양에 상대적이다 — 절대값을 그대로 이식하면 기동 거부나 OOM.
