## 정답
<!-- 질문 1:1 대응 -->

1. **KV cache(와 워밍업의 동시 적재).** \
   생성 중에는 각 시퀀스의 이전 토큰 key/value를 GPU에 쌓아두는 KV cache가 필요하고, 그 크기는 **동시 시퀀스 수 × 컨텍스트 길이**에 비례한다. \
   서빙 엔진은 기동 시 기본 동시 시퀀스 상한(256)만큼 더미 요청을 한꺼번에 넣어 워밍업하므로, 가중치 5.2GB를 올린 뒤 남은 약 2.4GB에 256개 분 KV를 잡으려다 OOM이 났다. \
   원인은 모델이 아니라 **동시성 워밍업 버퍼**였다.
   > **KV cache** — 트랜스포머가 이미 처리한 토큰의 key·value 텐서를 재계산하지 않으려 저장하는 GPU 메모리. 시퀀스·토큰마다 늘어난다.

2. 동시 시퀀스 상한을 256→8로 줄이면 KV 예약량이 크게 줄어 VRAM에 들어간다. 대가는 **동시에 처리할 수 있는 요청 수(처리량)**가 줄어드는 것이다. \
   사용자가 한 명인 서비스에선 동시 요청이 8을 넘을 일이 드물어 잃는 것이 거의 없다. 함께 VRAM 사용 상한을 0.90으로 낮춰 여유를 두고, 할당자의 단편화 완화 옵션(`expandable_segments`)으로 큰 연속 블록 요구를 줄였다. \
   즉 "자원이 모자라면 동시성 상한으로 수요를 묶는다"는 자원 제한 원리다.

3. **prefill은 추론 요청이 올 때 비로소 실행된다.** \
   기동은 가중치 로드와 워밍업까지, health 엔드포인트는 "프로세스가 살아 응답한다"까지만 본다. \
   프롬프트를 인코딩하는 prefill 커널은 실제 추론 호출에서 처음 돌기 때문에, 그 커널이 이 GPU에서 깨진다는 사실은 첫 추론에서야 드러났다. \
   그래서 "에러 없이 떴다"는 완료가 아니고, **실제 추론 1건을 끝까지 통과**해야 검증이다.
   > **prefill / decode** — 입력 프롬프트 전체를 한 번에 처리해 KV를 채우는 단계 / 그 뒤 토큰을 하나씩 생성하는 단계. 서로 다른 커널을 쓴다.

4. **3단 인과.** \
   ① compute capability 7.5(Turing) GPU는 FlashAttention-2가 요구하는 8.0(Ampere)+를 충족하지 못한다. \
   ② 그래서 엔진이 attention 백엔드로 다른 커널 라이브러리(FlashInfer)를 **자동 선택**한다. \
   ③ 그런데 그 라이브러리의 paged prefill 커널이 Turing에서 동작하지 않아 `invalid argument`로 실패한다. \
   모델·양자화·메모리 문제가 아니라 **GPU 세대와 커널의 비호환**이다.
   > **compute capability** — NVIDIA GPU 세대별 기능 수준 번호. 커널 라이브러리는 이 번호로 지원 여부를 가른다.

5. **한 계층 위에서 바꾼다.** \
   외부 이미지라 코드를 패치할 수 없고, 백엔드 강제 env는 그 엔진 버전이 무시했다(로그에 여전히 같은 백엔드 선택). 설정 계층에서 우회가 불가능하면 남는 선택지는 GPU를 바꾸거나(아래) 엔진을 바꾸는 것(위)이다. \
   최신 커널에 의존하지 않는 다른 엔진(llama.cpp 계열)으로 교체했고, 오케스트레이터는 **OpenAI 호환 API라는 표준 계약**에만 의존했으므로 요청 본문·응답 파싱은 그대로, 바뀐 것은 포트와 모델명 2개뿐이었다.

6. OOM이 **그대로 재발**한다. \
   튜닝(동시 시퀀스 8·사용 상한 0.90·할당자 옵션)은 운영 설정에만 들어갔고 보존 사본은 초기 스냅샷이라, 새 GPU에서 그 사본으로 재시도하면 256 동시 시퀀스 워밍업이 다시 돈다. \
   실패한 스택을 복원점으로 보존하는 건 좋지만, **보존본이 마지막으로 알게 된 교정을 담고 있는지**를 함께 기록해야 한다(원문도 이를 경고로 남겼다).

## 문제 구조 (추상화 코드)

### 변형 A — VRAM 예산을 가중치로만 계산 (KV·동시성 누락)

① 문제 코드
```yaml
services:
  llm:
    image: <serving-engine>
    command: ["--model", "<7b-4bit>"]      # 기본 max_num_seqs=256 → 워밍업 256 동시 적재
    # VRAM ~7.6GB, 가중치 ~5.2GB → KV 몫 부족 → OOM
```
② 고친 코드
```yaml
services:
  llm:
    command: ["--model", "<7b-4bit>",
              "--max-num-seqs", "8",               # 동시성 상한 = KV 상한
              "--gpu-memory-utilization", "0.90"]  # 여유 확보
    environment:
      PYTORCH_CUDA_ALLOC_CONF: "expandable_segments:True"   # 단편화 완화
```
무엇이 깨졌나: 모델이 "들어가는지"만 보고 동시성에 비례하는 KV 예산을 계산하지 않아, 추론 전 워밍업에서 이미 메모리가 바닥났다.

### 변형 B — 기동·health 성공을 추론 가능으로 간주 (GPU 세대별 커널)

① 문제 구조
```text
engine.start()      → 백엔드 자동 선택: cc 7.5 → FA2 불가 → 대체 커널 선택
GET /health         → 200   (prefill 안 탐)
POST /v1/chat/...   → 500   BatchPrefill... invalid argument
env ATTENTION_BACKEND=<다른 커널>  → 해당 엔진 버전이 무시
```
② 고친 구조
```text
llm:  <serving-engine>  →  <llama.cpp 계열 엔진>     # 구세대 GPU 에서 안정적인 커널
client:
  base_url = "http://llm:<새 포트>/v1"               # 바뀐 것: 포트
  model    = "<새 모델 태그>"                         # 바뀐 것: 모델명
  body / 응답 파싱 = 그대로 (OpenAI 호환 계약)
검증: 배포 후 실제 추론 1건 통과를 확인 (health 200 으로 끝내지 않음)
보존: 옛 엔진 설정은 복원점으로 남김 — 튜닝 인자 포함 여부 기록
```
무엇이 깨졌나: 커널 선택이 GPU 세대에 묶여 있는데 확인하지 않았고, health가 prefill 경로를 타지 않아 "떴다"가 "추론된다"로 잘못 읽혔다.
