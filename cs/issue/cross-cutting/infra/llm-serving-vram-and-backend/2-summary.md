# cs/issue/infra/llm-serving-vram-and-backend — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
서빙 엔진이 겪는 단계와 각 단계의 벽

 [1] 가중치 로드            5.2GB  (7.6GB 중)            ✓
 [2] 워밍업                 동시 시퀀스 256개 더미 요청 적재
      VRAM = 가중치 + KV cache 풀 + 동시 요청 수에 비례하는 작업 버퍼(샘플러 logits 등) + 할당자 여유
      → 남은 약 2.4GB 안에 KV 풀과 256개 분 작업 버퍼를 함께 못 담음 → OOM   ✗  (벽 1)
        (paged KV 엔진은 KV 풀을 메모리 비율로 미리 잡고, 워밍업이 최대 동시성의 더미 요청을 돌린다 — 엔진마다 다름)
      교정: max_num_seqs 8 · gpu_memory_utilization 0.90 · 할당자 단편화 완화
 [3] 기동 완료 · /health 200                              ✓  ← 여기서 "성공"이라 믿기 쉬움
 [4] 첫 추론 요청 → prefill 커널 실행
      GPU cc 7.5 → FlashAttention-2(8.0+) 불가 → 엔진이 대체 백엔드 자동 선택
      → 그 paged prefill 커널이 이 세대에서 invalid argument  ✗  (벽 2)
      env 로 백엔드 강제 → 엔진 버전이 무시 → 설정 계층에서 우회 불가
      교정: 다른 엔진(구세대 GPU 안정 백엔드)으로 교체
            소비자는 OpenAI 호환 API 계약에만 의존 → 바뀐 것 = 포트·모델명 2개
            실패한 설정은 삭제 대신 복원점으로 보존 (단, 보존본에 튜닝 누락 주의)
```

## 핵심 문장
- VRAM 예산 = 가중치 **+ KV cache(동시성 × 컨텍스트) + 동시성에 비례하는 작업 버퍼**. 모델 크기만 보고 "들어간다"고 판단하면 워밍업에서 터진다.
- 빠듯한 VRAM에서 주요 손잡이 중 하나는 **동시 시퀀스 상한** — 동시성↓ = 동시 작업 버퍼·동시 KV 점유↓(처리량과 교환). 컨텍스트 길이 상한·메모리 사용 비율도 같은 예산을 움직인다.
- 이 엔진에서 추론 커널(prefill attention)은 **실제 요청에서야** 처음 실행됐다(워밍업이 어느 경로를 타는지는 엔진마다 다름) → 기동·health 성공은 추론 성공이 아니다. 끝까지 한 번 추론해봐야 검증이다.
- 엔진의 커널 선택은 **GPU 세대(compute capability)**에 묶인다 — 구세대는 최신 고성능 커널에서 배제되거나 깨진다. 먼저 확인한다.
- 설정으로 못 바꾸는 외부 이미지는 한 계층 위(엔진 선택)에서 해결한다. 표준 API 계약이 교체 비용을 낮춘다.
