## 정답
<!-- 질문 1:1 대응 -->

1. **비대칭의 출처.** 두 호스트가 서로 다른 서브넷에 있고, 홈랩의 라우팅 테이블에는 `default via 게이트웨이` 항목만 있어 **PC 대역 전용 경로가 없다** — PC 주소로 가는 패킷은 기본 게이트웨이로 넘어가지만 그 너머에서 PC의 사설 대역까지 닿는 길이 없어 unreachable이 된다(`ping`이 unreachable). 반대로 PC→홈랩은 뚫려 있다(배포 ssh가 매일 그 방향을 쓴다).\
   주의: TCP 연결은 응답 패킷도 돌아와야 하므로 "PC→홈랩 연결이 된다" 자체가 홈랩의 응답이 PC에 닿는다는 뜻이다. 이런 비대칭은 보통 PC 쪽 트래픽이 중간 장비에서 **주소 변환(NAT)**되어 홈랩은 변환된 주소(도달 가능한 주소)로 답하고, 장비가 연결 상태표로 그 응답을 PC에 되돌려 주기 때문에 생긴다 — 상태표에 없는, 홈랩이 먼저 PC의 실주소로 거는 연결은 갈 길이 없다(일반론 — 구체 원인은 중간 장비 구성에 따라 다르다).\
   핵심은 이것이 "포트가 닫혀서"가 아니라 **홈랩이 먼저 걸 때 패킷이 갈 길(route·변환 매핑)이 없어서**라는 것 — 그래서 "먼저 거는 쪽"에 따라 성립 여부가 갈린다.
   > **라우팅 테이블** — "이 대역 주소로는 어느 게이트웨이/인터페이스로 보내라"의 목록. 해당 항목이 없으면 그 대역은 unreachable.

2. **-L vs -R, 왜 -R.** `ssh -L`(로컬 포워딩)은 "**내가** 상대 포트로 나가는 통로를 내 쪽에 연다", `ssh -R`(원격 포워딩)은 "**상대가** 내 포트로 들어오는 통로를 상대 쪽에 연다". 막힌 방향(홈랩→PC)을 뚫으려면 **연결을 실제로 거는 주체가 나갈 수 있는 쪽(PC)**이어야 한다. PC가 `-R`로 걸면 SSH 세션 자체는 PC→홈랩(뚫린 방향)으로 나가지만, 그 세션 위에 홈랩→PC로 데이터가 흐르는 역방향 통로가 생긴다. 그래서 관건은 "누가 먼저 연결을 거느냐"이고, 답은 **부를 수 있는 쪽이 건다**.
   > **역(reverse) SSH 터널 `-R`** — 부를 수 없는 쪽이 부를 수 있는 쪽으로 나가서, 그 세션 위에 반대 방향 통로를 뚫는 것.

3. **socat이 잇는 것.** `-R`로 포워딩된 포트는 기본적으로 상대(홈랩) 호스트의 **루프백(127.0.0.1)**에만 바인딩된다(sshd의 `GatewayPorts` 설정으로 넓힐 수 있지만 노출도 함께 넓어진다) — 즉 홈랩 호스트 자신에서만 보인다. 그런데 요청을 보낼 backend는 **컨테이너 안**이라 호스트 루프백을 직접 못 본다(컨테이너의 `127.0.0.1`은 컨테이너 자신이다). 그래서 `socat`을 `0.0.0.0:<LAN포트> → 127.0.0.1:<터널이 연 포트>` 릴레이로 띄워, **호스트 루프백에만 있던 통로를 LAN 주소로 노출**한다. 그러면 backend가 LAN 주소:포트로 닿을 수 있다. 이때 socat이 컨테이너라면 **호스트 네트워크 모드**여야 `127.0.0.1`이 호스트 루프백을 가리킨다(일반 브리지 네트워크 컨테이너의 `127.0.0.1`은 자기 자신). 또 `0.0.0.0`은 LAN 전체에 통로를 여는 것이라, 아래 5번의 인증이 필수가 되고 가능하면 리슨 주소를 좁힌다.
   > **socat** — 한 소켓(TCP 포트 등)을 다른 소켓으로 이어주는 얇은 릴레이 도구.

4. **터널이 끊기면.** 역 SSH 터널은 PC가 건 **하나의 SSH 세션 위**에 있으므로, PC가 껐다 켜지거나 네트워크가 끊기면 세션이 죽고 통로도 함께 사라진다 — 즉 **상시 서비스가 아니라 세션 프로세스**다. 운영상 이는 "PC에서 스크립트로 기동하고 유지해야 한다"는 제약을 만든다(README에 절차 기록). 그래서 호출부(backend)는 브리지 URL이 비었거나 브리지가 오프라인이면 죽지 않고 `available=false` → `escalate_unavailable`로 **우아하게 부재를 안내**한다. 통로의 불안정성을 장애가 아니라 "지금은 로컬 답변만 가능"이라는 정상 분기로 흡수한 것.

5. **원격 실행 표면과 방어선.** 방향을 뒤집어 통로를 열면, 그 relay 포트에 닿는 누구든 PC에서 임의 프롬프트로 LLM CLI(`TOOL -p`)를 돌릴 수 있는 **원격 실행 표면**이 생긴다(배포 서버만큼 위험). 방어선 각각: **공유 시크릿 상수시간 검증(`hmac.compare_digest`)** — 인증 없는 실행을 막고, 빈 시크릿이면 전부 거절하며, 상수시간 비교로 타이밍 공격 차단. **도구 전면 차단(`--allowedTools ""`)** — 문서 안에 "파일 읽어라" 같은 지시가 있어도 도구를 못 써 순수 텍스트만 나오게(프롬프트 주입 완화). 단 "허용 목록 비우기"가 곧 "모든 도구 금지"인지는 CLI의 의미에 달려 있다 — 허용 목록이 '확인 없이 쓸 도구'를 뜻하고 권한 확인이 필요 없는 도구가 따로 있다면 비우기만으론 부족해 명시적 금지 옵션이 필요하므로, 실제 설치본으로 확인한다. **동시 1건(세마포어, 초과는 503)** — 느린 요청 하나가 전체를 점유하지 못하게. **크기 상한(프롬프트/출력)** — 폭주·자원 고갈 방지. **stderr 비노출(실패해도 `tool_failed`만)** — 내부 오류 정보 누출 차단. 각각 다른 위험(무인증 실행·주입·자원 점유·폭주·정보 누출)에 대응한다.
   > **상수시간 비교** — 문자열 길이/내용에 따라 걸리는 시간이 달라지지 않게 비교해, 시간차로 시크릿을 추측하는 공격을 막는 것.

6. **왜 socat을 컨테이너로.** 릴레이 하나를 위해서지만 컨테이너로 띄운 이유는 **호스트에 sudo로 손대지 않기 위해서**다. 호스트에 패키지를 설치하고 상시 데몬(서비스 유닛)을 등록하는 대신, 이미 가진 도커 권한으로 컨테이너를 띄우면 호스트 변경 없이 다른 서비스들과 같은 compose 운영 방식(기동·재시작 정책·로그)에 얹을 수 있다. 주의: 도커 제어 권한 자체가 사실상 root 동급이고, 호스트 루프백에 닿으려면 호스트 네트워크 모드라 네트워크 격리도 약하다 — 이득은 "권한 최소화"보다 **호스트 무변경·운영 일관성** 쪽이다.

7. **연결 — NAT 통과 일반.** 이건 "안에서 밖으로는 나가지만 밖에서 안으로는 못 들어오는"(NAT·불라우팅 서브넷) 상황을 우회하는 전형적 **NAT traversal**이다. 공통 아이디어는 **부를 수 없는 쪽이 먼저 밖으로 나가 연결을 유지**하는 것. 같은 발상의 사례: **웹훅 대신 폴링** — 서버가 클라이언트를 못 부를 때 클라이언트가 주기적으로 나가서 물어봄. **홀펀칭(hole punching)** — 양쪽이 동시에 아웃바운드를 쏴 NAT 매핑을 뚫음(STUN/WebRTC 계열). **아웃바운드 롱폴·웹소켓 기반 에이전트** — 방화벽 뒤 에이전트가 밖으로 상시 연결을 걸어두고 그 위로 명령을 받음(역터널과 정확히 같은 방향 뒤집기). 전부 "다이얼 방향을 가능한 쪽으로 뒤집는다"가 뼈대다.

```text
[서버 S] ip route: default via <게이트웨이>        # 클라이언트 PC 대역으로 가는 경로 없음
[서버 S 컨테이너] POST http://<PC주소>:<브리지포트>/ask   → unreachable
```

```sh
# PC(부를 수 있는 쪽)가 연결을 건다 — 세션은 PC → S 방향, 그 위로 S → PC 통로
ssh -N -R <원격포트>:localhost:<브리지포트> <user>@<서버S>      # S의 127.0.0.1:<원격포트>에 뜸
```

### 변형 B — NAT 뒤 호스트 원격 접근: 포트포워딩 대신 outbound 유지형 브로커 (설계)
① 문제 코드
```text
외부 클라이언트 ──▶ 공유기 공인IP:포트 ──(포트포워딩 + DDNS)──▶ NAT 뒤 호스트:22
# 공개 포트가 늘고, 공인 IP 변동을 따라가야 함 (비권장)
```
② 고친 코드
```sh
# NAT 뒤 호스트 → 자체 클라우드 엣지(브로커)로 outbound 연결을 상시 유지
ssh -N -R 2222:localhost:22 <broker>            # 브로커의 127.0.0.1:2222 에만 바인드
#   상시 유지: systemd --user 서비스 + linger, ServerAliveInterval 또는 autossh

# 클라이언트: 브로커를 경유해 점프
ssh -J <broker> -p 2222 user@localhost          # 공개 포트 추가 없음
```
