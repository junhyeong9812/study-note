# cs/issue/network/reverse-tunnel-nat-traversal — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[문제] 홈랩 서브넷과 PC 서브넷이 라우팅으로 안 이어짐
   홈랩의 ip route: default via 게이트웨이 (PC 대역으로 가는 경로 없음) → PC unreachable
   그런데 PC → 홈랩은 이미 뚫려 있음 (배포 ssh가 매일 그 경로를 씀) → 비대칭

[해법] 방향을 뒤집는다 — 부를 수 없는 쪽(홈랩)이 아니라 부를 수 있는 쪽(PC)이 연결을 건다
   PC:   ssh -N -R <원격포트>:localhost:<브리지포트> <user>@<홈랩호스트>
         = "홈랩의 루프백 원격포트를 PC의 브리지포트로 잇는 구멍을 PC가 뚫는다"

[그런데] -R로 포워딩된 포트는 홈랩의 루프백(127.0.0.1)에 바인딩됨
   → 홈랩의 backend는 컨테이너 안이라 그 루프백을 못 봄
   → socat 릴레이:  0.0.0.0:<포트> → 127.0.0.1:<원격포트>   (LAN에서 닿게, sudo 없이 컨테이너로)

[최종 사슬]
   backend → socat(홈랩 LAN:포트) → 역 SSH 터널(PC가 -R로 걺) → PC 브리지 → LLM CLI(TOOL -p)

[운영] 상시 서비스 아님 = 세션 프로세스 → PC에서 스크립트 기동. 미설정 시 available=false (우아한 부재)

[보안] 원격 실행 표면 → 공유 시크릿 상수시간 검증·도구 전면 차단·동시 1건·크기 상한·stderr 비노출
```

## 핵심 문장

- 라우팅 비대칭: 홈랩의 라우팅 테이블에 PC 대역으로 가는 경로가 없어 **홈랩→PC는 unreachable**. 반대로 PC→홈랩은 경로가 있어 뚫려 있다. "포트가 닫혀서"가 아니라 **경로 자체가 없어서** 한 방향만 막힌 것.
- 해법은 **연결 방향 뒤집기**. `-L`은 "내가 상대 포트로 나간다", `-R`은 "상대가 내 포트로 들어오게 구멍을 낸다". 부를 수 있는 쪽(PC)이 `-R`로 걸면, 막힌 방향(홈랩→PC)을 우회한다. 관건은 **누가 연결을 거느냐** — 나갈 수 있는 쪽이 걸면 된다.
- `-R`로 포워딩된 포트는 상대 호스트의 **루프백**에 뜬다. 컨테이너 안 앱은 호스트 루프백을 못 보므로, `socat`이 `0.0.0.0:포트 → 127.0.0.1:원격포트`로 **루프백을 LAN에 노출**해 다리를 놓는다.
- 이 연결은 상시 서비스가 아니라 **세션 프로세스**(PC가 스크립트로 기동). 끊기면 불통이라, 미설정·오프라인 시 호출부는 `available=false`로 **우아한 부재**를 안내한다.
- 방향을 뒤집어 뚫는 순간 **원격 실행 표면**이 열린다 → 공유 시크릿 상수시간 검증(인증)·도구 전면 차단(주입 완화)·동시 1건(자원 점유)·크기 상한(폭주)·stderr 비노출(정보 누출)로 좁힌다.
- 이것은 일반 **NAT 통과** 문제 — "부를 수 없는 쪽이 먼저 나가 연결을 유지"하는 아이디어는 웹훅 대신 폴링, 홀펀칭, 아웃바운드 롱폴/웹소켓 에이전트에서도 반복된다.
