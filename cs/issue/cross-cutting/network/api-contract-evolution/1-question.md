## 질문
1. 프로토콜 초기화 응답이 인증 방법 목록(`authMethods`)을 광고했는데, 막상 `authenticate`를 호출하니 "Method not implemented"가 돌아왔다. capability 광고와 구현은 왜 어긋날 수 있는가 — 그리고 상대 구현이 실제로 무엇을 하는지는 무엇으로만 확정할 수 있는가.
2. 서버가 initialize 요청의 protocolVersion을 **무조건 그대로 에코**했다. 버전 문자열은 단순한 라벨이 아니라 무엇을 약속하는가 — 지원하지 않는 버전을 요청받았을 때 서버는 어떻게 답해야 클라이언트가 "조용히 오동작"하지 않고 "명시적으로 실패"하는가.
3. 예측: 인터페이스 문서가 "모든 응답은 bounded다", "resume는 이전 세션을 이어간다"고 적었지만, 실제로는 상한 없는 명령이 있고 전사를 못 찾으면 조용히 새 세션을 연다. 소비자가 이 문구를 믿고 설계하면 어떤 종류의 버그가 생기는가. 문구를 고칠 때 "쓸 수 있는 문장"의 기준은 무엇인가.
4. 경계: 응답이 배열 `[..]`에서 래퍼 `{meta, rows}`로 바뀐다. 제공자를 먼저 배포하는 것과 소비자를 먼저 배포하는 것 중 어느 쪽이 안전한가 — 그 판단을 가르는 조건(소비자의 폴백 유무)은 무엇인가. 새 필드 추가는 왜 같은 문제가 아닌가.
5. 구현 문서의 코드 블록이 `load() { /* binary read */ }`처럼 본문을 주석으로 대체했고, 그 문서를 따라 친 코드는 컴파일은 되지만 테스트 6개가 실패했다. "문서가 코드와 일치한다"를 사람이 아니라 기계로 검증하려면 어떻게 해야 하는가.
6. 외부 런타임이 넘겨주는 JSON의 필드명이 문서(`user_message`)와 실제(`prompt`)가 다르다. 단일 필드명에 의존하는 소비자는 필드가 바뀌면 에러가 아니라 무엇을 겪는가 — 소비자 측에서 할 수 있는 방어와 그 한계는?
7. 연결: 계획이 외부 CLI의 특정 플래그를 전제했는데, 스크립트 3개를 쓰고 배포까지 한 뒤에야 설치본에 그 플래그가 없다는 걸 알았다. 1번(광고≠구현)과 이 사건은 같은 원리인가 — "상대 구현은 소스·스모크로만 확정한다"를 착수 **전** 절차로 바꾸면 무엇이 되는가.
