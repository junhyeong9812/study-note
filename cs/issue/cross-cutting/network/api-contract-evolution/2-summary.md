# cs/issue/network/api-contract-evolution — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
계약 = "이렇게 동작한다"는 주장         구현 = 실제로 그렇게 동작하는 코드
  capability 광고 (authMethods)          authenticate 미구현 → "Method not implemented"
  버전 선언 (protocolVersion 에코)        그 버전이 요구하는 batch를 봉투 검증이 거부
  문서 주석 ("모든 응답 bounded")          상한 없는 명령 4종 · resume 실패 시 조용히 새 세션
  문서 속 코드 (load() { /* ... */ })      따라 친 코드 = 영속화 빈 채 컴파일 성공
  외부 도구 전제 (--flag)                  설치본에 그 플래그 없음 (배포 뒤 발견)
  외부 입력 필드 (문서: a / 실제: b)        필드가 바뀌면 소비자는 조용히 빈 값
            │
            ▼  소비자가 "주장"을 근거로 설계 → 무음 유실·오동작

[교정 — 주장을 구현에 맞춘다]
  광고는 차단 조건으로 쓰지 않는다 → 실제 에러 코드(requires_auth)를 표면화
  버전은 화이트리스트: 실제 만족하는 것만 선언, 미지원 요청엔 지원 버전으로 답 → 클라가 명시 실패
  문서 문구는 코드로 역검증 → 불성립이면 조건부로 약화 + 잔여 명시 ("테스트가 받치는 문장만")

[계약 변경의 진화 — 방안들]
  문서 코드   : 정본 앵커 + 코드 블록 추출 → src 지우고 문서만으로 빌드·테스트 green
  응답 형태   : 소비자 폴백 먼저 → 소비자 선배포 안전 / 제공자 선배포 위험 → 동시 배포
  외부 도구   : 착수 전 실제 설치본으로 기능 확인 (없으면 옵션 비교 후 우회)
  외부 스키마 : 소비자가 폴백 필드 (.b // .a) + 감시 항목 등록
```

## 핵심 문장

- 광고(capability·버전·문서)는 **주장**이고 구현만이 **사실**이다 — 상대 구현은 소스와 스모크로만 확정한다.
- 버전 문자열은 구체 능력의 묶음을 약속한다 → 서버는 **실제로 만족하는 버전만** 선언하고, 모르는 버전은 에코하지 않는다.
- 문서가 코드보다 앞서 쓰이면 **없는 보장을 광고**하게 된다 → 문구를 코드로 역검증해, 테스트가 받치는 문장만 남긴다.
- 문서 속 코드도 실행물이다 → 문서에서 추출해 빌드·테스트해야 드리프트가 기계적으로 잡힌다.
- 비호환 응답 변경은 **배포 순서**의 문제다 — 폴백을 가진 쪽이 먼저 나가야 하고, 폴백이 없으면 동시 배포.
- 외부 도구·런타임의 기능과 필드는 **착수 전 실제 설치본·실제 입력**으로 확인하고, 소비자는 필드 변경에 폴백으로 방어한다.
