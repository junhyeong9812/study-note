# cs/issue/network/http-cache-policy — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
immutable = "이 URL의 바이트는 절대 안 바뀐다" → 만료 전엔 재검증조차 안 함

[맞는 자리]   /assets/app.3f9a1c.js      (내용이 바뀌면 URL이 바뀜 = 콘텐츠 주소화)
[틀린 자리]
  ① 상태코드 무관 부여     upstream 204/206에도 7일 immutable → 빈·부분 응답이 7일 고정
  ② 버전 없는 URL          /images/{id}  재적재(같은 URL·새 바이트) → 최대 7일 옛 바이트
  ③ 해시 없는 정적 자원     /public/modal.css, /static/deploy.js → 배포 후에도 구버전 사용
  ④ 상태 엔드포인트        /api/.../status 캐시 → 폴링이 옛 상태를 봄

[교정]
  ① 200 OK일 때만 캐시 헤더
  ② 리스크 인지 후 결정(상수 1곳 → 되돌리기 쉬움) / 근본은 URL에 버전 토큰
  ③ 해시 파일명 또는 짧은 캐시·재검증(ETag) — 당장은 하드 리프레시 안내
  ④ 상태 fetch 는 cache: 'no-store' (+ 서버 측 Cache-Control 정책은 후속 과제)
```

## 핵심 문장

- `immutable`은 **URL ↔ 바이트의 영구 대응 약속**이다 → 내용이 바뀌면 URL도 바뀌는 **콘텐츠 주소화 URL**에만 쓴다.
- 캐시 헤더는 **정상 전체 응답(200)**에만 — 204·206·오류를 장기 고정하면 비정상 응답이 오래 산다.
- 해시 없는 정적 자원과 상태 엔드포인트에 캐시 정책이 없으면 **서버 배포와 클라이언트 로직이 어긋난다**.
- 클라이언트 측 `no-store`는 그 호출만 보호한다 — 모든 소비자를 보호하려면 **서버가 정책을 명시**한다.
- 리스크를 아는 예외는 **되돌리기 쉬운 한 곳**에 두고 결정으로 기록한다.
