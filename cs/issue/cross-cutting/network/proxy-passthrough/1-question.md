## 질문
1. 투명 프록시(BFF)가 상류 응답을 클라이언트에 중계할 때 **원형 그대로 보존**해야 하는 것 세 가지는 무엇인가(스트림 타이밍·상태코드·상태성 헤더). 셋 중 하나라도 깨지면 각각 무엇이 죽는가.
2. 프록시가 스트림 본문을 **버퍼링**(다 모아 뒀다 한꺼번에 전달)하면 왜 "타자 효과"가 죽는가 — 스트리밍의 이점은 애초에 무엇이었길래 버퍼링이 그걸 무효화하는가. nginx라면 어떤 설정으로 끄는가.
3. 세션이 서려면 프록시가 `cookie`(브라우저→상류)와 `set-cookie`(상류→브라우저)를 **양방향으로** 왕복시켜야 한다. 한 방향만 넘기면 무슨 일이 벌어지는가 — 왜 "매 요청이 처음 온 사람"이 되는가.
4. 예측: 프록시가 상류의 봉투(`{success,data,error}`)를 **열어서 data만 꺼내 다시 포장**한다. 이때 상류가 준 422가 어떻게 되는가? 프록시가 상태코드를 재구성하면 왜 한 단계 뭉개지는가.
5. 프록시가 응답을 버퍼링하는 지점은 여러 층에 있다 — 애플리케이션 프레임워크(응답 body를 통째로 읽고 반환), 리버스 프록시(nginx `proxy_buffering`), 그리고 클라이언트. 각 층에서 버퍼링을 끄는 방법과 `X-Accel-Buffering: no`가 하는 일을 설명하라.
6. 경계: 같은 backend 응답인데 **페이지(SSR)는 봉투를 열어** 쓰고 **프록시(`/api/*`)는 원형 전달**한다. 왜 소비자에 따라 처리가 갈리는가 — "봉투를 여느냐"의 판단 기준은 무엇인가.
7. 연결: 프록시의 "상태코드 원형 보존"은 스트리밍의 "상태코드 잠김"([http-streaming-status-locked](../http-streaming-status-locked/))과 같은 뿌리인가? 프록시가 상류 200을 이미 흘리기 시작했다면 사후에 상태를 못 바꾼다 — 이 둘을 하나의 원리로 묶어라. 그리고 쿼리 파라미터 allowlist(정한 키만 상류로 전달)는 이 "원형 보존"과 상충하지 않는가?
