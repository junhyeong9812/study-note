# cs/issue/network/proxy-passthrough — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
투명 프록시(BFF)가 원형 보존해야 하는 3가지
   (a) 스트림 타이밍 : 버퍼링 X → 조각을 오는 대로 흘림 → 타자 효과 산다
   (b) 상태코드      : 상류 status 그대로 반환 → 봉투 열어 재포장하면 422→500 뭉개짐
   (c) 상태성 헤더   : cookie(브라우저→상류) + set-cookie(상류→브라우저) 양방향 왕복 → 세션 유지

깨지면
   (a) 죽으면  → 몇 초 멈춤 → 답 통째 등장 (스트리밍 무효)
   (b) 죽으면  → 오류 의미 상실 (클라가 상태코드로 분기 못 함)
   (c) 죽으면  → 매 요청이 "처음 온 사람" → 세션 안 섬

[코드 골자 — 스트림+쿠키 패스스루]
   upstream = fetch(BACKEND, { headers:{ cookie: req.cookie } , body })
   set-cookie 있으면 응답 헤더로 복사
   return Response(upstream.body, { status: upstream.status })   # 스트림 그대로, status 그대로

[버퍼링 끄기]  nginx: proxy_buffering off  (+ 필요시 X-Accel-Buffering: no)

[봉투 분기]  페이지(SSR)=봉투 열어 화면 그림 / 프록시(/api)=봉투·status 손대지 않음
[allowlist] 상류 URL 재조립 시 정한 키(q,topic,size,doc_kind)만 통과 — 주입면 축소
```

## 핵심 문장

- 투명 프록시는 자기가 중계하는 것의 **종단간(end-to-end) 의미를 보존**해야 한다: 스트림 타이밍·상태코드·상태성 헤더. 각각을 깨면 타자효과·오류의미·세션이 하나씩 죽는다.
- **버퍼링은 스트리밍의 반대**다. 스트리밍의 이점이 "완성 전에 첫 조각을 빨리 보기"인데 프록시가 다 모아 뒀다 보내면 그 이점이 사라진다. nginx `proxy_buffering off` (+ `X-Accel-Buffering: no`).
- 세션은 **양방향 쿠키 왕복**으로만 선다. `set-cookie`(상류→브라우저)로 발급이 도달하고 `cookie`(브라우저→상류)로 그 값이 되돌아가야 한다. 한쪽만 넘기면 매 요청이 새 세션.
- 프록시가 봉투를 열어 재포장하면 상류 상태코드가 **한 단계 뭉개진다**(422→500). 그래서 프록시는 봉투·status를 손대지 않고 **원형 반환**.
- **소비자에 따라 처리가 갈린다** — 화면을 그리는 페이지(SSR)는 봉투를 열어 `data`를 쓰고, 기계가 소비하는 프록시(`/api/*`)는 원형 전달. 용도가 다르면 처리도 다르다.
- 상태 원형 보존 ↔ 스트리밍 상태 잠김은 **같은 뿌리**: 한 번 흘리기 시작한 응답의 헤더/상태는 사후에 못 바꾼다. allowlist는 "본문·상태 보존"과 층이 달라(요청 파라미터 위생) 상충하지 않는다.
