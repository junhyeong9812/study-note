# cs/issue/network/payload-transfer-cost — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[스트림 전량 재전송]
  폴 스레드 150ms ─▶ 지문 비교(스트리밍 중엔 매 틱 변경) ─▶ 전체 상태 딥클론
     ─▶ 직렬화(JSON 문자열) ─▶ IPC emit (1회 ~24MB, 그중 77% = 이미 끝난 본문)
     ─▶ 웹뷰: off-heap 공유 매핑이 회수보다 빨리 쌓임 ─▶ RSS 5.22GB
  비용 = ~24MB × (1/0.15s) ≈ 167MB/s  ← "1회는 적당" 이 곱셈에서 무너짐
  진단: 힙 스냅샷 X (off-heap 못 봄) → 프로세스 메모리 매핑 분해가 정본

[교정 — deferred hydration]
  완료 항목 = 메타(id, 개수, 서명)만  ── 본문 필드 자체가 타입에 없음
  본문 = 사용자가 펼칠 때 별도 요청으로 회수 (정본 = 디스크)
  + 항목 본문 상한 32KB → 4KB · emit당 복사 제거(소유 → 차용)
  결과: RSS −89%, 공유 매핑 80개 → 4개
  선택하지 않은 방법: 증분 전송(병합 누락 = 화면이 조용히 낡음, 전량 재동기화 폴백 선행 필요)

[같은 구조]
  바이트 → JSON 숫자 배열(3~4배) + 전역 이벤트 수신 측 필터(구독자 K배)
     → base64(~1.33배) + 세션별 이벤트 이름(리스너 있는 곳에만 디스패치)
  검색 응답 _source 전체(10.6MB) → took 355ms / 왕복 33s
     → 구간 분리 로깅 + 반환 필드 화이트리스트 → 1.67MB
```

## 핵심 문장

- 전송 비용은 **크기 × 빈도**다 — 1회분이 "적당"해도 고빈도면 누적률이 된다.
- **바뀌지 않는 큰 본문을 매 틱 재전송**하지 말라 → 스트림엔 메타만, 본문은 요청 시 회수(deferred hydration).
- "본문 없음"은 **타입으로 보장**하고, 직렬화 결과에 본문이 없음을 테스트로 고정한다.
- 필터는 **보내는 쪽**에서 — 수신 측 필터는 비용을 구독자 수만큼 곱한다.
- 바이너리를 텍스트 포맷에 실을 때는 **인코딩 팽창률**을 본다(JSON 숫자 배열 ≫ base64).
- 서버 처리시간과 왕복시간의 차이는 주로 **엔진 밖 구간(응답 직렬화·전송·역직렬화) 비용**이다 → 구간을 분리해 측정하고 반환 필드를 좁힌다.
- 측정 도구의 **관측 범위**를 먼저 확인한다 — 힙 밖(off-heap) 메모리는 힙 스냅샷에 안 나온다.
