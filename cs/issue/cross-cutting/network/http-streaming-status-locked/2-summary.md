# cs/issue/network/http-streaming-status-locked — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
HTTP 응답 순서:  [상태줄 200] → [헤더] → [본문 ...........]
                 └── 이걸 보내는 순간 상태코드 확정 (되돌릴 수 없음)

스트리밍 = 결과를 다 알기 전에 본문을 흘리기 시작
   → 흘리는 도중 오류? 이미 200을 보냄 → "사실 503이었어" 못 함

[해결] 오류 계약을 시간으로 나눈다
   스트림 시작 전  (포화·입력 검증)  → 봉투 JSON  503/422   (아직 헤더 안 보냄)
   스트림 시작 후  (도중 오류)        → 텍스트 청크가 곧 계약. 오류는 로그만, 연결 끊김

[코드 골자]
   if sem.locked():  return 503 봉투            # 시작 전 → 상태코드 자유
   StreamingResponse( async for token: yield )   # 시작 = 200 확정
       except:  await log(...); raise             # 시작 후 → 로그 + 비정상 종료 (상태 못 바꿈)
```

## 핵심 문장

- HTTP 응답은 **상태줄→헤더→본문** 순. 상태코드는 본문보다 앞(상태줄)에 있어 **헤더가 커밋되는 순간(늦어도 본문 첫 바이트) 이미 확정·전송**되어 되돌릴 수 없다. 스트리밍은 정의상 "결과를 다 알기 전에 본문 시작"이므로 상태코드가 잠긴다.
- 그래서 **오류 계약을 시간으로 분할**한다: 스트림 시작 **전**에 판정 가능한 실패(포화 503, 입력 검증 422)는 봉투 JSON으로, 시작 **후**의 도중 오류는 상태코드로 못 알리니 텍스트 채널(청크)과 로그로 처리하고 연결을 끊는다.
- 이것은 우회가 아니라 **HTTP 스트리밍의 본질적 제약**이다. 오류를 상태코드로 알리려고 헤더 전송을 미루면 = 응답을 다 만들 때까지 버퍼링 = 스트리밍(첫 글자 빨리 보기)을 포기하는 것.
- 미완 신호는 상태코드가 아니라 **본문 채널의 규약**(정상 종료 표식의 유무, 연결 끊김)으로 준다 — 예: `done` 플래그, 종료 토큰, chunked trailer, gRPC trailing status.
- 프록시도 상류 200을 흘리기 시작하면 사후에 못 바꾼다(스트리밍 중계에선 **같은 제약** — 한 번 나간 헤더는 불변). 버퍼링 프록시의 "상태 원형 보존" 규칙은 여기에 더해 **정보 보존**이 근거다.
