## 질문
1. HTTP 응답은 어떤 순서로 나가는가(상태줄·헤더·본문), 그리고 왜 "200 헤더를 보내는 순간 상태코드가 확정된다"고 말하는가 — 이미 보낸 헤더를 나중에 바꿀 수 없는 구조적 이유는 무엇인가.
2. 스트리밍 응답은 "결과를 다 알기 전에 본문을 흘리기 시작"한다. 그런데 흘리는 도중 오류가 나면(모델 호출 실패 등) 이미 200을 보낸 뒤다 — 이 오류를 어떻게 알리는가. 이 시스템이 택한 "오류 계약의 시간분할"은 무엇을 어디로 나누는가.
3. 스트림 시작 **전**에 걸러낼 수 있는 것과 시작 **후**에만 알 수 있는 것을 각각 예로 들라. 왜 전자는 봉투 JSON(503/422)으로, 후자는 텍스트 청크·로그로 처리하는가.
4. 예측: 클라이언트는 200을 받고 토큰을 받다가 스트림이 중간에 끊겼다. 서버는 "완성"을 보낸 적이 없다 — 클라이언트는 이 응답이 **미완**임을 어떻게 아는가? 상태코드로는 못 알 텐데 무엇으로 아는가.
5. 경계: 저자는 이걸 "회피가 아니라 HTTP 스트리밍의 본질적 제약"이라 못 박았다. 왜 우회 트릭이 아니라 근본 제약인가 — 만약 오류를 알리려고 헤더 전송을 미룬다면 무엇을 잃는가.
6. 이 제약을 다른 방식으로 푸는 프로토콜/메커니즘은 무엇인가 — 예를 들어 HTTP chunked trailer, SSE의 이벤트 타입, gRPC의 trailing status. 각각 "본문 이후에 상태를 덧붙이는" 자리를 어떻게 마련하는가.
7. 연결: 이 상태코드 잠김은 프록시 패스스루 패턴과 어떻게 맞물리는가 — 중간 프록시가 상류의 200을 받아 이미 클라이언트에 흘리기 시작했다면, 프록시도 사후에 상태코드를 못 바꾼다. 프록시가 "상태를 원형 보존"해야 한다는 규칙과 이 제약은 같은 뿌리인가?
