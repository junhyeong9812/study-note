# cs/issue/network/bind-address-loopback-vs-lan — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
바인딩 주소 = 서버가 "어느 주소로 귀를 여느냐"
   0.0.0.0        모든 인터페이스 (루프백 + LAN + ...)
   LAN IP         그 IP로만 (127.0.0.1로는 거부)
   127.0.0.1      자기 자신(루프백)만

[사건]
   backend compose:  ${BIND_ADDR:?}:8090:8090   → LAN IP에만 연다 (fail-closed 보안)
   agent 헬스체크:    http://127.0.0.1:8090/...  → 루프백을 두드림
   결과:             배포는 정상 · 헬스 URL만 틀림 → connection refused → deploy_unhealthy

   "떠 있는데 127.0.0.1만 거부" = 프로세스 살아있고 특정 주소로만 안 열림 = 바인딩 문제

[교정]  바인딩을 바꾸지 않고(의도된 보안) 헬스 URL을 LAN 주소로 맞춤

[곁가지 함정]
   컨테이너 헬스체크에서 localhost → ::1(IPv6)로 풀림 → IPv4 바인딩 서버 unhealthy
   → 127.0.0.1 명시로 회피
   compose up 종료코드 0 ≠ 서비스 정상 → 배포 후 헬스 URL 실제 폴링(200 와야 ok)
   얕은 /health(살아있나) vs 깊은 /health/deep(약속한 일 실제로 하나)
```

## 핵심 문장

- 바인딩 주소는 서버가 **어느 주소의 접속만 받을지** 정한다. LAN IP에만 바인딩하면 그 포트가 "열려" 있어도 `127.0.0.1`로 온 접속은 커널이 **거부**한다(리스닝 소켓이 그 주소에 없음).
- **fail-closed**: 설정(BIND_ADDR)이 비면 열어두지 않고 **기동을 거부**. 보안 기본값은 "실수로 빠지면 노출"이 아니라 "실수로 빠지면 안 뜸"이어야 한다.
- 헬스체크가 루프백을 두드려 실패한 건 **거짓 음성이 아니라 정직한 보고**다 — "127.0.0.1로는 정말 안 열린다"를 사실대로 잡아냈다. 오히려 바인딩이 의도대로 걸렸음을 *증명*했다.
- 고치는 쪽은 **바인딩(의도된 보안 불변식)이 아니라 헬스체크 주소**. 헬스 프로브의 대상은 서비스가 실제로 여는 주소여야 한다.
- `compose up -d` 종료 0 = "컨테이너 띄웠음"일 뿐 "서비스 정상 응답"이 아니다 → 배포 후 **헬스 URL 실제 폴링**. 헬스체크는 "프로세스 살아있나"가 아니라 "**약속한 일을 실제로 하나**"(GPU 추론)를 봐야 한다.
- `localhost`는 컨테이너 안에서 `::1`(IPv6)로 풀릴 수 있어, 첫 주소만 시도하는 프로브 도구면 IPv4 바인딩 서버를 unhealthy로 만든다 → `127.0.0.1` 명시.
