## 질문
1. URL의 요청 라인에 한글 같은 비ASCII 문자를 그대로 넣으면 왜 HTTP 클라이언트가 요청을 보내기도 전에 실패하는가. 공백만 `%20`으로 바꾸는 방식은 왜 부분 해결인가.
2. 식별자 값에 `/`가 들어갈 수 있다(예: `AB/123/10`). 이 값을 경로 변수(`/items/{id}`)로 보내면 인코딩하지 않을 때와 `%2F`로 인코딩할 때 각각 무슨 일이 일어나는가. 왜 결국 쿼리 파라미터로 옮기게 되는가.
3. 예측: 표준 Base64로 만든 토큰을 URL 경로 세그먼트에 넣었다. 어떤 문자 때문에 어떤 식으로 깨지는가. URL-safe Base64는 무엇을 바꾸는가.
4. 테스트 클라이언트에 `"/items/%20"` 문자열을 넘겼는데 서버에는 공백이 아니라 `%20`이라는 글자가 도착했다. 어떤 단계에서 무엇이 한 번 더 일어났는가(이중 인코딩). 이미 인코딩된 URI를 그대로 보내려면 어떻게 해야 하는가.
5. 경계: 인코딩은 "보내는 쪽 한 번, 받는 쪽 한 번 해제"가 원칙이다. 여러 홉(프런트 → 중간 서버 → 백엔드)을 거치는 요청에서 이 원칙이 어디서 쉽게 깨지는가. 각 홉은 무엇을 책임져야 하는가.
6. 연결: 라우트(폴더명·경로 세그먼트)를 비ASCII로 지으면 빌드 목록에는 보이는데 런타임에서 404가 날 수 있다. 이것을 1번(요청 라인은 ASCII)과 어떻게 연결해 설명하겠는가. 왜 "사람이 읽는 이름은 데이터로, URL 세그먼트는 ASCII 슬러그로" 나누는 것이 안전한가.
