# cs/issue/network/uri-encoding-rules — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
값(임의 문자) ──[보내는 쪽: 퍼센트 인코딩 1회]──▶ URI(ASCII + 예약문자 규칙) ──[받는 쪽: 디코딩 1회]──▶ 값

실패 지점
  ① 비ASCII 그대로          q=한글        → 클라이언트가 요청 라인 생성 실패 (ascii codec)
  ② 경로 속 '/'
     - 인코딩 안 함          /items/AB/123 → 세그먼트가 쪼개짐 → 404/400
     - %2F로 인코딩          /items/AB%2F123 → 서블릿 컨테이너·보안 방화벽이 기본 거부 → 400
  ③ 표준 Base64            + / =          → 경로 구분자·공백·쿼리 구분 의미로 해석 → 토큰 깨짐
  ④ 이중 인코딩            "%20"을 템플릿으로 취급 → %2520 → 서버엔 글자 "%20" 도착
  ⑤ 비ASCII 라우트 이름     /admin/회원관리 → 빌드엔 있는데 매칭 실패 404

교정
  ① 값마다 quote()  (공백만 치환 X)
  ② 슬래시 가능 식별자 → 쿼리 파라미터 ?id=..., 쿼리 값도 URI 템플릿으로 인코딩 (모든 홉)
  ③ URL-safe Base64 (- _ , 패딩 제거)
  ④ 이미 인코딩된 문자열은 URI 객체로 넘김 (템플릿 오버로드 X)
  ⑤ URL 세그먼트 = ASCII 슬러그, 사람이 읽는 이름 = 메뉴 데이터
```

## 핵심 문장

- URI는 ASCII와 예약문자(`/ ? # & = + %` 등) 규칙 위에서만 안정적이다. 그 밖의 문자는 **경계에서 한 번** 퍼센트 인코딩한다.
- 경로 세그먼트 안의 `/`는 인코딩해도 컨테이너·방화벽이 막는다. 슬래시가 들어갈 수 있는 값은 **경로가 아니라 쿼리**로 보낸다.
- 표준 Base64의 `+ / =`는 URL에서 특수 의미다 → 경로·쿼리에 넣는 토큰은 **URL-safe 알파벳**.
- 문자열을 "템플릿"으로 받는 API는 `%`를 다시 인코딩한다 → 이미 인코딩된 값은 **URI 객체**로 넘긴다(이중 인코딩 방지).
- 여러 홉을 지나는 요청은 **홉마다 같은 규칙**을 지켜야 한다. 한 홉만 고치면 다른 홉이 여전히 막는다.
