## 정답
<!-- 질문 1:1 대응 -->

1. **컨테이너 안의 127.0.0.1.**\
   컨테이너는 자기만의 네트워크 네임스페이스(인터페이스·라우팅·루프백 한 벌)를 갖는다.\
   그래서 프록시 컨테이너 안의 `127.0.0.1`은 **프록시 컨테이너 자신**이고, 거기엔 8001을 듣는 프로세스가 없다 → 502.\
   호스트에서 `:8001`이 되는 건 호스트의 루프백·매핑 포트로 들어갔기 때문이며, 컨테이너 안에서 보는 "로컬"과는 다른 네트워크다.
   > **네트워크 네임스페이스** — 프로세스 묶음마다 독립된 네트워크 스택(인터페이스·루프백·라우팅 테이블)을 주는 리눅스 격리 단위.

2. **docker0 게이트웨이의 범위.**\
   `172.17.0.1`은 **기본 bridge(docker0)**의 게이트웨이이자 호스트가 docker0 인터페이스에 가진 주소다 — 기본 bridge 컨테이너에겐 "자기 서브넷의 호스트 쪽 출구"다.\
   사용자 정의 네트워크에 붙은 컨테이너는 다른 bridge·다른 서브넷에 있어, 이 주소로 가는 패킷은 자기 게이트웨이를 거쳐 **호스트로** 간다 — 닿느냐는 호스트 방화벽(다른 bridge 인터페이스에서 온 입력을 막는 규칙 등)·포트 게시 주소·데몬 설정에 달려 있어 환경마다 다르고, 닿더라도 컨테이너로 직접이 아니라 호스트 게시 포트를 경유하는 우회로다(일반론 — 이 사건에선 프록시 502에 이어 캐시 연결이 `Timeout`으로 실패).\
   답은 우회 주소를 찾는 게 아니라 **같은 사용자 정의 네트워크에 붙여 컨테이너 이름으로** 부르는 것이다.

3. **매핑 포트 vs 내부 포트.**\
   `ports: "6381:6379"`의 왼쪽 6381은 **호스트 쪽(호스트 자신·외부)에서 들어오는 트래픽의 NAT 입구**, 오른쪽 6379가 컨테이너가 **실제로 리슨하는 포트**다.\
   같은 네트워크의 컨테이너끼리는 NAT를 거치지 않고 컨테이너 IP로 직접 가므로, 이름은 IP로 잘 풀려도 그 IP의 6381에는 아무도 없다 → `Connection refused`.\
   "DNS 성공 + refused"는 "주소는 맞고 포트가 틀림"의 서명이다. 교정은 `컨테이너이름:6379`이고, 설정 우선순위(컨테이너 환경변수가 내부 값을 덮고, 코드 기본값의 호스트 포트는 로컬 개발 전용)를 문서화했다.

4. **내장 DNS의 범위.**\
   도커 임베디드 DNS는 **같은 사용자 정의 네트워크에 붙은 컨테이너 이름만** 해석한다 — 기본 bridge나 다른 compose 프로젝트의 기본 네트워크 컨테이너는 보이지 않는다.\
   즉시 조치는 `docker network connect <공유네트워크> <컨테이너>`, 영구 조치는 각 compose에 `networks: <공유네트워크>: external: true`를 선언하는 것(공유 네트워크는 사전에 `docker network create`로 만든다).
   > **external 네트워크** — compose가 만들지 않고 이미 존재하는 네트워크에 붙기만 하겠다는 선언. 여러 프로젝트가 한 네트워크를 공유할 때 쓴다.

5. **네트워크는 호스트 데몬 안에만 있다.**\
   (bridge 드라이버의) 사용자 정의 네트워크와 그 DNS 이름은 **그 호스트의 도커 데몬 안에서만** 존재한다(여러 호스트에 걸치는 overlay 네트워크는 Swarm 같은 클러스터 구성이 따로 필요하다) — 다른 호스트엔 그 external 네트워크도, 상대 컨테이너 이름도 없어 기동부터 실패한다.\
   그래서 dev 편의(공유 네트워크·컨테이너 이름)는 남기고, **배포용 compose를 분리**해 네트워크 참조를 빼고 `.env`의 호스트IP:publish 포트로 부르게 했다(재배포 때도 반드시 배포용 파일을 지정).

6. **분산 노드의 광고 주소.**\
   분산 시스템은 노드가 **스스로 알린 주소**(등록·하트비트에 실린 호스트명/IP)로 서로·클라이언트가 연결한다.\
   브리지 뒤 노드가 자기 기준 주소(브리지 내부 IP, 임시 파드 이름)를 광고하면, 다른 노드와 클라이언트는 그 주소에 닿지 못한다 — 워커가 리소스를 못 받고, 클라이언트가 데이터 노드에 직접 쓰지 못해 "0개 노드에 복제"가 되고, 역방향 DNS 실패로 등록이 거부되며, 랜덤 파드 이름은 해석되지 않는다.\
   교정은 "상대가 닿는 주소를 광고"하는 것: 데이터 노드 포트 노출, 호스트 네트워크 + 호스트 이름 매핑, 광고 IP 명시와 IPv4 우선 설정, 쿠버네티스에선 Headless Service + `hostname/subdomain`(고정 DNS)과 StatefulSet 고정 이름.
   > **advertised address** — 노드가 "나에게는 이 주소로 오라"고 클러스터에 알리는 주소. 바인드 주소와 다를 수 있다.

7. **하나의 질문 — 그 주소는 누구의 네트워크 기준인가.**\
   바인드 문제는 "서버가 귀를 연 주소가 클라이언트가 오는 주소를 포함하나"이고, 목적지 문제는 "클라이언트가 거는 주소가 **클라이언트의 네트워크에서** 서버를 가리키나"다.\
   둘 다 루프백·게이트웨이·매핑 포트·이름이 **어느 네임스페이스·어느 네트워크·어느 호스트 기준 값인지**를 확인하지 않아 생긴다.\
   광고 주소는 두 문제의 교차점이다 — 서버가 "나는 여기"라고 말한 주소가 듣는 쪽 네트워크에서 유효해야 한다.

## 문제 구조 (추상화 코드)

### 변형 A — 컨테이너에서 루프백·docker0 게이트웨이를 목적지로 사용
① 문제 코드
```nginx
upstream app {
    server 127.0.0.1:8001;        # 프록시 컨테이너 자신 → 502
    # server 172.17.0.1:8001;     # 기본 bridge 게이트웨이 → 호스트 경유 우회로, 방화벽·설정에 따라 안 닿음
}
```
② 고친 코드
```nginx
upstream app {
    server app-blue-1:8000;       # 같은 사용자 정의 네트워크의 컨테이너 이름 : 내부 포트
}
# 블루/그린 전환 시 전환 도구가 upstream의 컨테이너 이름을 생성
```
무엇이 깨졌나: 호스트 기준 주소를 컨테이너 네임스페이스 안에서 썼다.

### 변형 B — 호스트 매핑 포트를 컨테이너 간 통신에 사용
① 문제 코드
```yaml
# compose (cache)
ports: ["6381:6379"]
# 다른 컨테이너의 .env
CACHE_HOST=cache-primary
CACHE_PORT=6381                   # 이름은 풀림 → 6381엔 리스너 없음 → refused
```
② 고친 코드
```yaml
CACHE_HOST=cache-primary
CACHE_PORT=6379                   # 컨테이너가 실제 리슨하는 포트
# 6381은 호스트 쪽(로컬 개발 도구)에서 들어올 때만
```
무엇이 깨졌나: NAT 입구 번호를 컨테이너 IP의 포트로 착각했다.\
같은 구조: 캐시 주소를 `게이트웨이IP:매핑포트`로 적은 설정을 `컨테이너이름:내부포트`로 바꾸고 모든 서비스를 external 공유 네트워크에 편입(연쇄 장애 — 프록시 502·캐시 실패·DB 이름 해석 실패).

### 변형 C — 다른 네트워크(다른 프로젝트·다른 호스트)의 이름을 해석
① 문제 코드
```yaml
# 프로젝트 X (자기 기본 네트워크)
services:
  search: { environment: { DB_HOST: shared-db } }   # shared-db는 프로젝트 Y 네트워크 → 해석 실패
```
② 고친 코드
```yaml
services:
  search:
    networks: [shared]
    environment: { DB_HOST: shared-db }
networks:
  shared: { external: true }       # 사전: docker network create shared
```
무엇이 깨졌나: 내장 DNS가 네트워크 경계 밖 이름을 풀어 줄 것이라 가정했다.\
같은 구조(호스트 경계): dev compose의 external 네트워크·컨테이너 이름 호출을 다른 호스트에 올려 기동 실패 → 배포용 compose를 분리해 네트워크 참조 제거 + `.env`의 `호스트IP:publish포트`로 호출.

### 변형 D — 분산 노드가 자기 기준 주소를 광고
① 문제 코드
```yaml
# 파드 이름이 랜덤·내부 IP를 광고
kind: Deployment                  # coordinator-7f9c-xyz → 워커가 이 이름을 해석 못함
spec: { template: { spec: { containers: [ { name: coordinator } ] } } }
```
② 고친 코드
```yaml
kind: Service
metadata: { name: coord-headless }
spec: { clusterIP: None }         # Headless — 파드마다 고정 DNS
---
spec:
  template:
    spec:
      hostname: coordinator
      subdomain: coord-headless   # coordinator.coord-headless.<ns> 로 광고·해석
# + 광고 호스트명/IP 환경변수 명시, JVM은 IPv4 우선
```
무엇이 깨졌나: 노드가 자기 네트워크에서만 유효한 주소를 클러스터에 알렸다.\
같은 구조: 브리지 뒤 워커가 내부 IP를 보고 → 호스트 네트워크 + 호스트 이름 매핑 · 데이터 노드 전송 포트 미노출로 클라이언트 직접 쓰기 실패 → 포트 노출 · 역방향 DNS 실패로 등록 거부 → 등록 시 호스트명 검사 해제 · 호스트 네트워크 전환 뒤 이름 기반 접속 문자열 → 실제 IP로.
