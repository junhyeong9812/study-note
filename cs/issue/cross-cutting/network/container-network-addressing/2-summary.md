# cs/issue/network/container-network-addressing — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
호스트
 ├─ docker0 (기본 bridge, 게이트웨이 172.17.0.1) ── 기본 bridge 컨테이너의 출구 (다른 네트워크에선 방화벽·설정 따라 불확실)
 ├─ 사용자 정의 네트워크 net-A (내장 DNS 127.0.0.11: net-A 안 이름만 해석)
 │     ├─ proxy     (127.0.0.1 = proxy 자기 자신)
 │     ├─ app       :8000
 │     └─ cache     :6379   ← ports "6381:6379" (6381은 호스트 NAT 입구일 뿐)
 └─ 다른 compose 프로젝트의 기본 네트워크 net-B
       └─ db        (net-A의 DNS로는 안 보임)

[실패 지점]
  proxy → 127.0.0.1:8001        → 자기 자신 → 502
  proxy → 172.17.0.1:8001       → net-A 밖 호스트 경유 우회로 (이 사건에선 실패) → 신뢰 불가
  app   → cache:6381            → 이름은 풀림, 컨테이너는 6379만 리슨 → refused
  app   → db                    → net-A DNS에 없음 → name resolution 실패
  다른 호스트에 같은 compose     → external 네트워크·이름이 그 호스트 데몬에 없음 → 기동 실패
  분산 노드가 "나는 172.x / pod-xyz" 광고 → 다른 노드가 그 주소로 못 감

[교정 — 목적지를 "같은 네트워크 기준"으로]
  같은 사용자 정의 네트워크에 붙인다 (external 공유 네트워크)
  목적지 = 컨테이너이름:내부포트     (호스트 매핑 포트 X, 127.0.0.1 X, docker0 X)
  다른 호스트 = .env의 호스트IP:publish포트 (배포용 compose 분리)
  분산 노드 = 다른 노드가 닿는 주소를 광고 (고정 DNS·호스트 네트워크·광고 주소 명시)
```

## 핵심 문장

- 컨테이너는 자기 **네트워크 네임스페이스**를 갖는다 → 그 안의 `127.0.0.1`은 호스트가 아니라 **컨테이너 자신**이다.
- docker0 게이트웨이는 **기본 bridge 컨테이너의 출구**다 — 사용자 정의 네트워크 컨테이너에겐 호스트 방화벽·게시 설정에 달린 불확실한 우회로일 뿐 답이 아니다.
- `ports: "호스트:컨테이너"`의 왼쪽은 **호스트 쪽에서 들어오는 NAT 입구**, 같은 네트워크 컨테이너끼리는 **오른쪽(실제 리슨 포트)**으로 직접 붙는다.
- 도커 내장 DNS는 **같은 사용자 정의 네트워크 안의 이름만** 해석한다 → 다른 프로젝트는 공유 네트워크에 편입해야 보인다.
- (bridge) 네트워크와 그 DNS 이름은 **그 호스트의 도커 데몬 안에만** 존재한다 → 다른 호스트로 가면 IP:publish 포트로 부른다.
- 분산 시스템은 **노드가 스스로 광고한 주소**로 서로 연결한다 → 광고 주소는 "상대가 닿을 수 있는 주소"여야 한다.
