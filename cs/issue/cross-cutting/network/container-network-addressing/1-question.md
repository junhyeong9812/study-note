## 질문
1. 리버스 프록시 컨테이너의 upstream을 `127.0.0.1:8001`로 적었더니 502가 났다. 호스트에서 `:8001`로 직접 붙으면 정상이다. 컨테이너 안의 `127.0.0.1`은 누구인가 — 네트워크 네임스페이스로 설명하라.
2. 그래서 docker0 게이트웨이 주소(`172.17.0.1`)로 바꿨는데 여전히 실패했다. 이 주소는 누구의 무엇인가 — 사용자 정의 네트워크에 붙은 컨테이너에겐 왜 믿을 만한 답이 아닌가.
3. 예측: compose에 `ports: "6381:6379"`로 띄운 Redis에, 같은 네트워크의 다른 컨테이너가 `redis-primary:6381`로 붙었다. 이름은 IP로 잘 풀리는데 `Connection refused`다. 왜 "DNS는 되는데 거부"인가 — 매핑 포트의 왼쪽과 오른쪽은 각각 누구를 위한 번호인가.
4. 다른 compose 프로젝트로 띄운 DB 컨테이너를 이름으로 찾으니 `Temporary failure in name resolution`이 났다. 도커 내장 DNS는 어느 범위의 이름만 해석하는가 — 두 프로젝트를 잇는 영구적인 방법은?
5. 경계: 개발 호스트에서 external 네트워크와 컨테이너 이름으로 서로 부르던 compose를 다른 호스트에 그대로 올리니 기동부터 실패했다. 사용자 정의 네트워크와 그 DNS 이름은 어디에 존재하는가 — 배포용 compose를 따로 두는 이유는?
6. 분산 클러스터(연산 워커·스토리지 노드)를 컨테이너·파드로 띄우니 "리소스를 못 받음", "0개 노드에 복제", `UnknownHostException`이 났다. 노드들은 서로의 주소를 **어디서** 알게 되는가 — 노드가 자기 기준 주소(브리지 내부 IP·임시 파드 이름)를 광고하면 무엇이 깨지는가.
7. 연결: [bind-address-loopback-vs-lan](../bind-address-loopback-vs-lan/)은 "서버가 어느 주소로 귀를 여나"(바인드) 문제였다. 이 카드는 "클라이언트가 어느 주소로 전화를 거나"(목적지) 문제다. 두 문제를 하나의 질문 — "그 주소는 누구의 네트워크 기준인가" — 으로 묶어 설명하라.
