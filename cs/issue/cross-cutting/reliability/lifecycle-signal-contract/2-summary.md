# cs/issue/cross-cutting/reliability/lifecycle-signal-contract — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
수명주기 신호:  시작 ──▶ 준비(ready) ──▶ ... ──▶ 완료/종결(done, exit XOR error)

[부수 사건으로 추론할 때의 실패]
  "결과 있음" 으로 완료 추론    → 결과 없는 턴(도구만·취소·에러) 에서 완료 미통지 → 스피너 고착
  "첫 출력" 으로 준비 추론      → 첫 출력 = 환영/확인 화면 → 입력이 확인창에 들어감
  "요청 전송" 으로 성립 추론     → 원격 거부 → early return → 종결 이벤트 0개 → "실행 중" 오독
  "빈 값" 을 never 로 표현       → onComplete 안 옴 → 요청 무한 대기
  조회 좌표 없음 = 아무 상태 없음 → "불러오는 중" 영구 고착
  EOF 로 종료 추론               → EOF 뒤의 exit-status 유실
  N초 무활동 으로 완료 추론      → 긴 정상 작업 중 완료↔재활성 진동 / 정상 작업 취소
  started 로 준비 추론           → 모델 로딩·DB 초기화 중 호출 → 연결 거부
  ping 응답 으로 준비 추론       → 초기화용 임시 서버도 응답 → 적재 미완을 완료로
  출력 패턴 으로 준비 추론       → 청크 경계에 걸친 신호 놓침 / replay 청크를 지금 준비로 오인

[계약]
  완료 신호는 모든 경로에서 무조건 1회 (결과 유무와 독립)
  준비 신호는 명시 응답 뒤에 (Success 수신 후 Ready)
  모든 종료 경로가 Exit XOR Error 정확히 1회
  "빈 값" = 즉시 완료하는 값
  조회를 시작도 못 하면 error 상태를 명시
  채널은 Close 까지 드레인
  시간 상한 > 정상 최장 공백, 대기 상한 > 정상 최장 초기화
  기동 순서는 condition: service_healthy, 준비 판정은 실서버 기준
  스트림 패턴은 경계 교차 매칭 + live 청크만 증거
```

## 핵심 문장

- 준비·완료·종결은 **다른 사건의 부산물이 아니라 독립 사건**이다 — 명시적 계약으로 보내고, 추론으로 대신하지 않는다.
- 종결 신호는 성공·실패·거부·취소 **모든 경로에서 정확히 한 번**. 한 경로라도 빠지면 소비자는 "아직 진행 중"으로 오독한다.
- "보냈다"는 "상대가 받아들였다"가 아니다 — 성립 신호는 **원격의 명시 응답 뒤에** 낸다.
- 시간 기반 추론은 휴리스틱이다. 쓸 수밖에 없다면 상한을 **정상 작업의 최장 공백보다 길게** 잡는다.
- "떴다(started)"와 "준비됐다(ready)" 사이에는 초기화가 있다 — 의존은 **준비 완료**에 건다.
