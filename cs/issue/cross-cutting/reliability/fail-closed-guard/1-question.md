## 질문
1. 안전 가드에서 "조회 실패 → 기본값(빈 값·false·0)"이 왜 곧 "안전함"으로 읽히는가. `unwrap_or_default()`·`except: return []` 같은 한 줄이 가드를 어떻게 무력화하나. 같은 코드가 부가 작업(오래된 백업 정리)에서는 왜 오히려 맞는가.
2. "못 읽음"을 "없음"으로 세면 판정이 어느 쪽으로 뒤집히나. 오답 비용이 비대칭(잘못된 busy = 회색 버튼 / 잘못된 free = 파일 파괴)일 때 fail-open과 fail-closed 중 무엇을 고르는 기준은 무엇인가.
3. 예측: 인증 필터가 `if (token != null && !isValid(token)) reject()`로 쓰였다. 토큰 발급부가 필드 하나를 빠뜨려 `null`로 나가면 무슨 일이 생기나. "키가 설정돼 있으면 검사" 방식의 인증은 설정 누락 시 어떻게 되나.
4. `switch`의 `default`나 `if/elif`의 `else`가 "가장 흔한 경로"로 흐르면, 새 입력 종류가 추가됐을 때 무엇이 조용히 일어나나. 조건 빌더가 `None`을 반환하고 호출자가 `if q:`로 건너뛰면 검색 결과는 왜 "전체"가 되나.
5. 경계: "열거한 위험만 차단 + 판별 실패 시 안전 쪽"으로 만든 분류기가 리뷰 때마다 새 누수를 내는 이유는? 기본 거부(allowlist)로 반전하면 무엇이 달라지나. 사람이 읽는 오류 메시지(로케일)를 판정 신호로 쓰면 왜 안 되나.
6. 모든 "모름"을 차단하면 어떤 문제가 생기나. "대상인지 모름"과 "대상인데 허가 여부를 모름"을 왜 다르게 다뤄야 하나. 과차단을 줄이면서 fail-closed를 유지하는 방법(판정 범위 좁히기)의 예를 들어라.
7. 연결: 폴백(다른 키로 재검증·다른 신호로 재시도)은 어떤 오류에만 걸어야 하나. 필수 설정에 기본값을 두는 것, 검증기가 잘못된 입력을 "보정"하는 것, CLI가 여분 인자를 무시하는 것은 fail-open과 어떤 점에서 같은가.
