# cs/issue/cross-cutting/reliability/silent-failure-vs-artifact — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```text
  요청 ──▶ [실행] ──▶ [결과 보고] ──▶ [완료 판정] ──▶ [상태 신호] ──▶ [검증기]
            │            │               │               │               │
            │ 예외 삼킴  │ 실패 = 빈 값  │ 중간 흔적     │ "떴음"만      │ 보는 표현이
            │ 데이터     │ 2xx = 성공    │ (폴더·마커·   │ (프로세스     │ 결함과 다름
            │ 무음 탈락  │               │  처리 로그)   │  생존·rc 0)   │
            ▼            ▼               ▼               ▼               ▼
         ────────── 어느 한 곳이라도 실패를 삼키면 최종 "success"는 거짓 ──────────
            교정: 각 지점에서 "됐다면 참이어야 할 산출물"을 직접 되묻는다
                  (저장소 대조 · 최종 산출물 마커 · 실제 기능 헬스 · 실물 렌더)
            되물을 산출물이 없으면: 실패가 도달할 통로부터 만든다 (응답 요구 · 귀속 · 유예 · 부재 테스트)
```

**한 문장:** 시스템이 내놓는 "성공 신호"(로그의 success·exit 0·HTTP 202·초록불)는 *일이 일어났다는 주장*일 뿐이고, 검증은 그 주장을 믿지 말고 **실제 산출물(artifact)** 을 되물어 확인하는 것이다.

성공 신호와 산출물은 다르다.

- **성공 신호** = 어떤 단계가 스스로 "됐다"고 말하는 것. 삼켜진 실패·잘못된 판정 코드·관대한 도구가 이 신호를 거짓으로 만들 수 있다.
- **산출물** = 그 일이 정말 일어났다면 세상에 남았어야 할 흔적. 색인된 청크 개수, 컨테이너의 실제 이미지 해시, 빌드 라우트 표의 한 줄, 헬스 URL의 200 응답.

silent failure(조용한 실패)는 **실패가 발생했으나 위로 전파되지 못한** 상태다. 세 가지 흔한 통로:
1. 예외를 삼키는 설계("실패해도 무해"로 짠 경로 — 로그 전송 실패 등)
2. 성공 신호를 실패와 구분 못 하는 호출(`curl`에 `-f`가 없어 401을 성공으로 받음)
3. 관대한 도구(없는 라우트를 오류로 안 보는 빌드, exit 0만 보는 healthcheck, 상태코드만 보는 docker healthcheck)

파이프라인에서는 더 위험하다. `A→B→C`가 각자 앞 단계의 성공을 신뢰하면, **한 단계가 실패를 삼키는 순간 최종 신호 전체가 거짓**이 된다. 그래서 "머지됐고 Actions 초록불"이 "운영에 반영됨"을 뜻하지 않는다.

방어는 언제나 같은 모양이다 — **주장을 산출물로 되묻기**:
- 넣으려던 개수 == 실제 저장된 개수 (record-level 검증)
- "deploy ok" 대신 컨테이너의 image·created 시각
- "빌드 성공" 대신 라우트 목록에 기대 경로가 있나 grep
- "compose up 0" 대신 헬스 URL을 90초 폴링해 200
- "202 접수" 대신 실제 배포 이력·http 코드

특수 함정: **검증 장치 자신도 틀릴 수 있다.** 에러 메시지 조립 코드가 진짜 에러를 가리거나, "python -m pytest"로는 통과하고 "pytest"로는 깨지는 환경 차이가 초록불을 위장한다. "테스트 통과 ≠ 검증 완료".

## 핵심 문장

- 성공 신호는 *주장*, 산출물은 *증거*. 검증 = 주장을 증거로 되묻기.
- 한 단계가 실패를 삼키면 파이프라인 전체 신호가 거짓이 된다.
- "202 접수" ≠ "완료", "exit 0" ≠ "정상 동작", "초록불" ≠ "반영됨".
- 데이터 작업은 "에러 없이 돌았다"로 끝내지 말고 count·sample·orphan을 센다.
- 검증 코드·검증 도구도 틀릴 수 있다 — 관대한 도구는 실패를 초록불로 바꾼다.
- 실패와 "정상적으로 비어 있음"을 같은 값으로 표현하지 마라 — 빈 목록·null·rc 0이 둘을 섞는다.
- 완료는 중간 흔적(폴더·마커·처리 로그)이 아니라 최종 산출물로 정의한다 — 그래야 재실행이 자동 복구가 된다.
- 되물을 산출물이 없으면 먼저 실패가 도달할 통로를 만든다(응답 요구·관측 귀속·자격 유예·부재 테스트).
