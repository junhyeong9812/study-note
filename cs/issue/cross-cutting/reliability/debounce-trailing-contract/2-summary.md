# cs/issue/reliability/debounce-trailing-contract — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
디바운스 = "보류 상태"를 새로 만든다 → 두 계약이 생긴다
  ① trailing: 마지막 변경 뒤 반드시 한 번 더
  ② ordering: 보류분과 종결 이벤트(closed·stop·delete)의 순서

[계약 ① 위반]  폴 틱
   sleep → poll → if fp == last_fp { continue }  →  flush_if_dirty()   ✗ 변화 없는 틱엔 도달 불가
                                                    → 마지막 턴 저장 영영 안 됨
   교정: sleep → stop 재검사 → flush_if_dirty() → poll → fp 게이트   (틱 순서를 계약으로 고정)
         dirty는 성공 시에만 내림 / last_save는 항상 갱신 (재시도 간격 유지, 핫루프 방지)

[계약 ② 위반]  보류 emit
   t0 timeline 변경 → 보류(400ms)
   t1 프로세스 자연 종료 → closed 즉시 emit
   t2 보류분 flush → timeline 도착                    ✗ closed 뒤에 timeline → 역순 / 또는 유실
   점 패치: 종료 시 강제 flush → 역순 → 서브스트림 누락 → ... (3라운드 연속)
   교정: 디바운스 제거 (보류 개념이 없으면 역순이 구조적으로 불가)
         + 수신 쪽 "종결 우선": 닫힌 id의 늦은 이벤트는 최종 상태만 반영, 종료 표시 유지
```

## 핵심 문장

- 디바운스는 공짜 최적화가 아니라 **"마지막 뒤 한 번 더"와 "종결과의 순서"**라는 두 계약을 새로 떠안는 것이다.
- trailing 플러시는 **변화가 있어야만 도는 경로 안에 두면 안 된다** — 변화가 멎은 뒤에 와야 하는 실행이기 때문이다.
- 실패 시 **dirty는 유지**, 재시도 타이머는 갱신.
- 보류 전송은 종결 이벤트와 **순서 해저드를 클래스로** 만든다 — 같은 표면에서 결함이 반복되면 보류 자체를 걷어낸다.
- 채널 간 순서는 송신 쪽에서 보장하기 어렵다 → 수신 쪽 **종결 우선**으로 흡수한다.
