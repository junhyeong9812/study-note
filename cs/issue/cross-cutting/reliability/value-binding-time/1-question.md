## 질문

1. (왜) `.env`를 고치고 `docker compose restart`를 했는데 컨테이너는 옛 값으로 돈다. `restart`와 `up -d`(재생성)는 무엇이 다르고, 컨테이너 환경변수는 **언제** 정해지는가?

2. (예측) 모듈 A에 `session = None`이 있고, 앱 기동 때 `init()`이 `A.session = new_session()`으로 바꾼다. 모듈 B는 맨 위에서 `from A import session`을 했다. B의 핸들러가 `session`을 쓰면 무엇이 보이는가? `import A` 후 `A.session`으로 쓰면 왜 달라지는가?

3. (경계) 프론트엔드의 `NEXT_PUBLIC_*` 같은 공개 환경변수는 왜 런타임 컨테이너 env로 바꿔도 반영되지 않는가? 로컬 테스트는 통과하는데 도커 빌드 산출물만 틀린 이유는 무엇인가(빌드 컨텍스트에 무엇이 없었나)?

4. (연결) 다음은 모두 같은 원리의 다른 "고정 시점"이다 — 각각 언제 박제되는가? (a) 모듈 상수로 만든 인증 헤더 (b) 단일 파일 bind mount의 대상 (c) 부모 프로세스가 자식에게 넘기는 pass-through env (d) 이미지 빌드 때 설치한 플러그인 (e) 작업 생성 시 복사한 설정값 (f) 브로커가 첫 produce 때 자동 생성한 토픽의 파티션 수.

5. (왜) 호스트에서 설정 파일을 `sed -i`로 고쳤는데 단일 파일로 bind mount한 컨테이너는 옛 내용을 본다. rename 기반 편집과 bind mount의 inode 고정은 어떻게 충돌하는가?

6. (경계) 대시보드에서 배치 크기·워커 수를 바꿔도 이미 돌고 있는 작업에는 반영되지 않았다. 작업 목록을 시작 시 전부 만들어 두는 것(물질화)과 워커 풀 크기를 생성자 인자로 주는 것은 각각 어떻게 값을 박제하는가?

7. (연결) "값을 바꿨는데 반영이 안 된다"를 만났을 때의 대응은 크게 셋이다 — ① 사용 시점에 다시 읽게 한다 ② 바인딩 시점을 다시 통과시킨다 ③ 바인딩 시점에 올바른 값을 공급한다. 각각 어떤 상황에 맞는가?
