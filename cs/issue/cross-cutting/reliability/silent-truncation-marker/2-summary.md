# cs/issue/cross-cutting/reliability/silent-truncation-marker — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```text
  원천 ──▶ [상한 있는 단계] ──▶ 반환값 ──▶ 호출자
               │
               ├─ 완주      → Vec[100개]  ─┐
               └─ 예산 소진 → Vec[80개]   ─┴─▶ 같은 모양 → 호출자는 "전부"로 읽는다
                  (링 앞부분 drain → 잘린 JSON → "not JSON" 으로 오진)
                  (저장 시점 절단 → 원천 교체 후 복구 불가)

  교정
   1. 절단 표식: { items, truncated: true }  ← 값의 길이로 추론하지 않고 생산자가 명시
   2. 절단 위치: 저장은 전문, 자르는 건 표시·전송 경계에서만 (+ 필요 시 원문 lazy 조회)
   3. 상한 도달 = 오류로 취급해야 할 곳은 오류 (적용 불가 + 사유)
   4. 단계 간 상한 정렬: 앞 단계 최대 출력 ≤ 뒤 단계 입력 상한 → 절단이 구조적으로 불가
```

**한 문장:** 상한으로 자른 결과를 완전한 결과와 같은 모양으로 반환하면 호출자는 절단을 모른다 — 절단 표식을 동반하고, 절단은 표시 경계에서만 하고, 단계 간 상한을 정렬한다.

- 상한은 필요하다(자원 보호). 문제는 상한이 아니라 **상한 도달의 침묵**이다.
- 예산 소진형 스캔은 절단 지점이 트리 모양·파일시스템 순서(readdir 순서는 보장되지 않고, 트리가 바뀌면 달라진다)에 달려 실행마다 달라질 수 있다 — 인용할 성질은 개수가 아니라 침묵이다.
- 오래된 것을 버리는 링버퍼는 완결성이 필요한 응답 수집에 쓰면 머리를 잘라, 절단이 파싱 오류로 위장한다.
- 절단 여부를 결과 길이로 추론하면 경계 조건(공백 경계 등)에서 우회된다 — 생산자가 플래그로 말해야 한다.
- 표시용 슬라이스(`[:10]`)는 부분 집합을 전체처럼 보이게 한다. 상한만 올리면 문제가 뒤로 밀릴 뿐이다.
- 경고 로그는 손실을 알릴 뿐 막지 못한다 — 상한끼리의 부등식을 맞춰 절단을 없앤다(단 두 상한을 같은 단위 — 바이트·문자·토큰 — 로 비교해야 부등식이 성립한다).

## 핵심 문장

- 잘린 결과는 "잘렸다"는 표식을 달고 나와야 한다.
- 절단은 표시 경계에서만, 원천 저장은 전문으로.
- 절단 판정은 값의 모양에서 추론하지 말고 생산자가 명시한다.
- "제한 제거"가 목표가 아니라 "무음 손실 제거"가 목표다 — 폭주 안전핀은 절단이 아니라 명시 예외.
- 단계 간 상한 부등식을 맞추면 절단 자체가 일어나지 않는다; 경고는 안전벨트일 뿐.
