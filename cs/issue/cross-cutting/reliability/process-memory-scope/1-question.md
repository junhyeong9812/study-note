## 질문
1. 프로세스 메모리에 둔 상태(세션 테이블·토큰 레지스트리·레이트리미터·락·요청 대기 future)는 어떤 두 경계를 넘지 못하나. "단일 인스턴스·무재시작" 가정이 깨지는 대표 상황 세 가지를 들어라.
2. 예측: 토큰 유효성을 메모리 레지스트리 `isActive()`로 판정하고, 없으면 false를 반환한다. 서버를 재시작하면 이미 발송한 링크·발급한 토큰은 어떻게 되나. 사용자·개발자는 이 401을 어떻게 오진하기 쉬운가.
3. 같은 코드를 인스턴스 2대로 스케일아웃하면 인메모리 레이트리미터·"동시 1작업" 락은 무엇을 보장하지 못하게 되나.
4. 결과 링크 토큰을 DB로 영속화할 때 토큰 원문 대신 해시를 저장하고, 매 발송마다 새 토큰·만료 정리 스케줄러를 두는 이유는? 재시작을 어떻게 테스트로 흉내내나.
5. 멀티 워커 웹 서버에서 대용량 사전을 각 워커가 dict로 로드하면 메모리는 어떻게 되나. 파일 기반 저장소(읽기 전용 임베디드 DB)는 왜 물리 메모리를 한 번만 쓰나.
6. 경계: 오케스트레이터가 요청-응답 상관 정보를 메모리 맵에만 두고 재배포되면 진행 중이던 명령은 어떻게 되나. 재배포 완료를 "연결됨" 플래그로 확인하면 왜 틀리나.
7. 연결: 모든 메모리 상태를 영속화해야 하나? 영속화 대신 "단일 인스턴스 전제"를 문서화하는 선택은 언제 정당하며, 그때 반드시 남겨야 하는 것은 무엇인가.
