# cs/issue/cross-cutting/reliability/resource-bounding-last-defense — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

**한 문장:** 자원을 소유한 쪽에서 건 **상한(bound)** 만이 실제 자원 소비를 막는다 — 소비를 시작시키지 않는 클라이언트측 통제(타임아웃·연결 끊기)는 자원을 보호하지 못한다.

```
클라이언트 ──요청──▶ 서버(자원 소유자) ──▶ 생성·적재·대기 (토큰·본문·연결·작업 수)
    │ 타임아웃 ✂ 연결만 끊음               ▲
    └──────────── 서버 작업은 계속 ────────┘   ← 클라이언트측 통제는 방어선이 아님

방어선 = 소비 지점의 상한
  생성량(num_predict) · 본문 크기(읽기 전 검사) · 동시 수(세마포어/TryLock) · 대기 시간(요청 전체 deadline)
  넘치면 → 큐잉 대신 즉시 거절(413/503/409) 또는 절단
```

핵심 비대칭: **연결을 끊는 것 ≠ 작업을 멈추는 것.** 클라이언트가 5초 타임아웃으로 연결을 끊어도, 서버는 그 요청의 생성/계산/저장을 계속한다. LLM은 클라이언트가 사라진 뒤에도 3만 토큰을 계속 뽑았다(실측). 그러니 "요청이 오래 걸리면 자원이 위험하다"를 막는 통제는 **자원을 만들어내는 그 지점**(서버측)에 있어야 한다.

같은 원리의 네 얼굴 — 전부 "자원을 만드는 쪽에서 상한을 건다":
- **num_predict**(생성 토큰 상한) — 모델이 끝낼 생각이 없어도 N토큰에서 강제 종료. 클라이언트 타임아웃이 못 하는 일을 한다.
- **body limit**(본문 크기 상한) — 공개 URL이 인증 전에 거대 본문을 메모리에 올리지 못하게, 헤더의 content-length를 **읽기 전에** 검사(4KB 초과 413).
- **세마포어**(동시 처리 수) — GPU 1장이면 동시 2건까지. 넘으면 줄 세우지 않고 즉시 503.
- **single-flight / bounded goroutine**(동시 작업 1건) — 같은 종류 작업은 하나만. 진행 중이면 즉시 409. 요청마다 무한정 백그라운드 작업을 띄우던 것을 서비스별 1개로 유계화.

부하 처리 철학: **큐잉보다 fast-fail.** 자원이 1개인데 큐를 두면 (a) 하류가 이미 직렬화하는 걸 두 겹으로 하고 (b) 사용자 요청이 대기줄에 인질로 잡힌다. "기다리지 않고 즉시 거절"(sem.locked()면 바로 Busy, TryLock 실패면 바로 409)이 자원을 지키고 실패도 시끄럽게 만든다.

왜 다른 것들은 방어선이 못 되나:
- **클라이언트 타임아웃** — 연결만 끊고 서버 생성은 계속.
- **프롬프트 안의 소프트 스위치**(`/no_think` 같은) — 서빙 런타임이 특별 취급 안 하면 그냥 텍스트로 흘러 무효. 모델 제어는 런타임의 공식 API(`think:false`)로.
- **상위 프레임워크 기본값** — 무제한이 기본이면(타임아웃 없음, 0.0.0.0 바인딩) 깜빡하는 순간 노출. fail-closed로 뒤집는다.

**"열었으면 닫는다"** 도 자원 경계다: 스트리밍 emitter가 `complete()`(또는 오류 시 `completeWithError`)를 빠뜨리면 연결·스레드가 샌다.

## 핵심 문장

- 연결을 끊는 것과 작업을 멈추는 것은 다르다 — 자원 상한은 자원을 만드는 쪽(서버)에 둔다.
- 클라이언트 타임아웃은 서버 자원을 보호하지 않는다. 서버측 생성 상한이 최후 방어선이다.
- 자원이 1개면 큐잉이 아니라 fast-fail — 넘치면 기다리지 않고 즉시 거절(503/409).
- 공개 경로의 크기 상한은 본문을 **읽기 전에** 검사해야 인증 전 자원 소비를 막는다.
- 무한정 쌓일 수 있는 것(goroutine·본문·토큰·동시 요청)에는 반드시 상한이 있어야 한다.
- 열었으면 닫는다(complete) — 스트림·연결·스레드 누수 방지도 자원 경계다.
