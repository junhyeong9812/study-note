## 질문
1. (왜) UI 컴포넌트의 "언마운트 시 정리(cleanup)"에 세션 종료·자동 저장을 걸어 두었다. 창을 강제 파괴(destroy)하거나 프로세스가 끝날 때 이 정리가 실행된다는 보장이 없는 이유는? 그래서 정리는 어디에 명시적으로 걸어야 하는가.
2. (예측) 창 닫기 핸들러가 `preventDefault()` → `await teardown()` → `destroy()` 순서다. teardown 중에 예외가 나거나 멈추면 사용자는 무엇을 보게 되는가? try/finally + 워치독 타이머로 1차 수정했는데도, 이벤트 루프 자체가 멈추면 왜 여전히 안 닫히는가.
3. (경계) 최후 백스톱으로 "앱 종료 API"를 호출했는데 효과가 없었다. 그 API가 **멈춘 이벤트 루프를 경유해** 처리된다면 무슨 일이 생기는가? 백스톱이 "구하려는 경로에 의존한다"는 말의 의미와, OS 수준 즉시 종료(`process::exit`)로 바꾼 이유는.
4. (방법) 종료 경로의 정리 코드는 왜 **블로킹 대기(join)를 하면 안 되는가**? 응답 없는 원격 호스트로 연결 중인 스레드를 join하면 종료는 누구에게 종속되는가. 반대로 "패널 하나 닫기"에서는 왜 join을 유지하는가.
5. (경계) 다른 스레드가 패닉해 뮤텍스가 오염(poison)됐을 때 종료 경로의 `lock().unwrap()`은 어떻게 되는가? best-effort 정리에서 오염된 락을 어떻게 다뤄야 하는가.
6. (방법) 백스톱 타이머를 여러 겹 둘 때(정상 ack 대기 2.5초 · 화면 쪽 워치독 4초 · 런타임 백스톱 5초) 유예 시간의 **순서**는 왜 중요한가? X 버튼을 여러 번 누를 때 타이머가 쌓이지 않게 하려면.
7. (연결) 런타임이 "모든 창이 사라졌을 때만" 종료 이벤트를 보낸다면, 메인 창만 닫히고 보조 창이 남은 경우 어떻게 되는가? "메인 닫기 = 앱 종료" 같은 의미는 누가 보장해야 하는가.
