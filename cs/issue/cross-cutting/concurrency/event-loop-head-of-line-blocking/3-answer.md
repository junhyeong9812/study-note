## 정답
<!-- 질문 1:1 대응 -->

1. **줄 맨 앞이 뒤를 막는다.** 루프는 `handle(msg1)`이 끝나야 다음 메시지를 꺼내므로, 10분짜리 작업이 도는 동안 도착한 로그 요청·상태 조회 등은 읽히지도 않고 대기한다.\
   메시지들은 서로 무관한데도 하나의 순서 큐에 묶여 있어 처리 시간이 가장 긴 것에 맞춰진다.
   > **HOL(head-of-line) blocking** — 순서대로 처리되는 줄에서 맨 앞 항목이 막혀 뒤의 무관한 항목까지 진행하지 못하는 현상.

2. **await는 그 지점에서 루프의 진행을 멈춘다.** `await`는 이벤트 루프에 제어를 양보하므로 **다른 작업**은 돌 수 있지만, 이 `for` 루프 자신은 `handle`이 끝날 때까지 다음 반복으로 가지 않는다.\
   그래서 이벤트 루프 전체가 멈춘 것은 아니어도, 이 연결의 수신 경로는 완전히 직렬이 된다.\
   (처리 안에 동기 블로킹 호출이 있으면 이벤트 루프 전체가 멈추고 다른 연결까지 영향을 받는다 — 더 넓은 같은 문제.)

3. **무관한 응답이 타임아웃된다.** 수신 루프가 `await broadcast(msg)`에서 좀비 탭의 느린 send를 기다리는 동안 다른 메시지(에이전트 명령 응답)를 읽지 못한다.\
   결과적으로 한 브라우저 탭의 지연이 에이전트 명령 응답 전체를 300초 타임아웃으로 만들고 UI 전체가 느려졌다.\
   구독자의 속도가 생산자의 핵심 경로 속도를 결정해 버린 것이다.

4. **대가와 주의점.** 작업을 떼어 내면 루프는 즉시 다음 메시지로 가지만, (a) 만든 작업의 참조를 보관하지 않으면 가비지 컬렉션될 수 있다(기록된 주의점).\
   일반론으로 (b) 메시지 간 처리 순서가 더 이상 보장되지 않고, (c) 작업 수에 상한이 없으면 느린 작업이 쌓일 수 있다.\
   근본적으로 매우 긴 작업(10분+)은 요청-응답으로 붙잡지 말고 백그라운드 작업 + 상태 폴링 엔드포인트로 바꾸는 것이 제안됐다(후속).
   > **fire-and-forget** — 결과를 기다리지 않고 작업을 시작만 하는 호출. 예외·참조 관리를 따로 해야 한다.

5. **타임아웃은 한 구독자의 최대 피해를 묶는다.** send 타임아웃이 없으면 죽은 구독자 하나가 무기한 붙잡을 수 있으므로 2초 같은 상한을 건다.\
   그러나 생산 단위(로그 한 줄)마다 모든 클라이언트에 **순차로** 보내며 클라이언트당 2초씩 기다리면, 느린 클라이언트가 있을 때마다 줄 하나에 수 초가 더해져 지연이 누적된다 — 이 구조가 로그 스트리밍 hang의 원인으로 확인됐다.\
   해결(여러 줄을 묶어 보내는 윈도우화)은 후속 과제로 분리돼 아직 적용되지 않았다.

6. **keepalive 오진.** ping/pong은 "상대가 살아 있나"를 보는 장치인데, 상대 이벤트 루프가 무거운 작업으로 막혀 pong 응답이 늦으면 클라이언트는 연결이 죽었다고 판정(1011 keepalive ping timeout)하고 끊는다.\
   연결은 살아 있었으므로 오진이며, 끊긴 동안 메트릭 전송이 실패해 유계 버퍼(최근 100개)가 차면 오래된 것부터 버려졌다.\
   간격·타임아웃을 늘리는 시도는 효과가 없었고, ping을 비활성화했다 — 대가는 죽은 연결 감지를 TCP 수준에만 맡기는 것이며, 재연결은 지수 백오프로 보완했다.\
   (원인이 루프 블로킹이라는 것은 기록상 추정이다 — 근본 해결은 위의 루프 분리다.)

## 문제 구조 (추상화 코드)

### 변형 A — 수신 루프가 처리를 직접 await
```python
# ① 문제
async for raw in ws:
    msg = json.loads(raw)
    await handle_command(msg)            # 10분짜리 명령이 이후 모든 명령을 막음

# ② 고침
async for raw in ws:
    msg = json.loads(raw)
    asyncio.create_task(handle_command(ws, msg))   # 루프는 dispatch만
    # 주의점(기록됨): 작업 참조를 잃으면 GC될 수 있다
```
무엇이 깨졌나: 긴 명령 중계 동안 같은 연결의 다른 명령이 무반응이었다(두 서비스의 수신 루프에서 같은 증상).

### 변형 B — 수신 루프가 브로드캐스트를 await
```python
# ① 문제
if msg["type"] == "log_stream":
    await broadcast_to_dashboards(msg)   # 느린 구독자 1명 = 수신 루프 정지

# ② 고침
if msg["type"] == "log_stream":
    asyncio.create_task(broadcast_to_dashboards(msg))

async def broadcast_to_dashboards(msg):
    for client in list(clients):
        await asyncio.wait_for(client.send(msg), timeout=2)   # 구독자당 상한 2초
        # ... 타임아웃 처리
```
무엇이 깨졌나: 비활성 탭 하나의 send 지연이 무관한 명령 응답 전체를 300초 타임아웃으로 만들었다.\
같은 구조(미해결): 생산 단위(한 줄)마다 전 클라이언트 순차 전송 + 클라이언트당 2초 타임아웃 → 지연 누적으로 hang, 묶음 전송(윈도우화)은 후속.

### 변형 C — 루프 막힘의 2차 증상: keepalive 오진
```python
# ① 문제
ws = await connect(URL, ping_interval=20, ping_timeout=10)
# 상대 루프가 막혀 pong 지연 → 약 40초마다 1011 종료, 버퍼(deque maxlen=100) 넘쳐 오래된 것 폐기

# ② 고침 (중간 시도: 간격/타임아웃 30·30으로 증가, 효과 없음)
ws = await connect(URL, ping_interval=None, ping_timeout=None)   # ping 비활성화
# 대가: 죽은 연결 감지는 TCP 수준에만 의존 → 재연결 지수 백오프(3s → 30s)로 보완
```
무엇이 깨졌나: 응답 지연을 연결 사망으로 오진해 살아 있는 연결을 끊었다.
