# cs/issue/concurrency/single-writer-ownership — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[lost update — 두 writer, 한 저장 단위, 락 없음]

  writer A                 저장 단위 X              writer B
  read X  ───────────────▶ {v=1}
                           {v=1} ◀─────────────────  read X
  계산 v'=A의 변경
                                                     계산 v''=B의 변경
  write X(전체) ─────────▶ {A의 값}
                           {B의 값} ◀─────────────── write X(전체)
                           └─ A의 변경은 흔적 없이 사라짐 (예외·로그 없음)

[같은 구조의 변형]
  주기 overwrite 스레드 + 필드 하나 추가하는 기능  → 다음 tick에 필드 소실
  창별 메모리 사본으로 공유 맵 전체 저장           → 다른 창 항목 소실
  목록 시점 스냅샷을 들고 나중에 쓰기             → 그 사이 최신 갱신 덮음
  SELECT → 앱 계산 → UPDATE(절대값)              → 차감 한 건 증발
  exists? → insert / MAX()+1 / 조회 → claim       → 중복 행·PK 충돌·이중 실행
  ORM 전체 컬럼 UPDATE                            → 안 바꾼 컬럼을 옛 값으로 되돌림

[교정 — 둘 중 하나로 "단일 소유"를 강제]
  (1) 저장 단위 분리: writer마다 자기 파일/키/세션 상태만 쓴다 → 읽기 쪽이 합친다
      불가하면 락(flock·프로세스 락) 안에서 "쓰기 직전 신선 읽기 → 자기 몫만 병합 → temp+mv"
  (2) 원자 갱신: DB가 한 문장으로 판정+쓰기
      UPDATE ... SET c = c - ? WHERE ... AND c >= ?   → 영향 행 0 = 실패/선점 실패
      INSERT ... ON CONFLICT (upsert) · unique 제약 = 중복 "삽입"의 마지막 방어선
      (이미 있는 행의 이중 claim은 unique가 못 막음 → 조건부 UPDATE/CAS)
```

## 핵심 문장

- 락 없는 read-modify-write는 **나중에 쓴 쪽이 먼저 쓴 쪽을 조용히 덮는다(lost update)** — 틀려도 예외가 없다.
- "쓰기 직전 다시 읽기"는 창을 좁힐 뿐 닫지 못한다. 닫으려면 **저장 단위를 writer별로 분리**하거나 **락/원자 연산**이 필요하다.
- 저장 단위를 분리하면 (각 단위의 writer가 실제로 하나뿐인 한) 두 writer가 같은 바이트를 쓸 일이 없어 **구조적으로** 덮어쓰기가 불가능하다 — 합치는 책임은 읽기 쪽(load)이 진다. 단, 여러 단위에 걸친 정합성은 분리로 보장되지 않는다.
- DB에서는 판정과 쓰기를 **한 문장**으로 합친다(조건부 UPDATE·upsert). **영향 행 수**가 성공/선점 여부다.
- check-then-act(존재 확인 후 삽입·`MAX()+1`·조회 후 claim)는 재확인으로 닫히지 않는다(TOCTOU) — 중복 **삽입**은 **unique 제약/upsert**로, 기존 행의 **선점(claim)**은 조건부 UPDATE/CAS(영향 행 수)로 닫는다.
- 상태 전이 하나에 소유자 하나. 같은 상태를 여러 핸들러·프로세스가 쓰면 순서가 서로의 전제를 깬다.
