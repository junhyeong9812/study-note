## 질문
1. 검색 조건을 "A"로 보낸 뒤 곧바로 "B"로 바꿔 보냈다. 화면에는 조건 B인데 A의 결과가 떠 있고 스피너도 꺼져 있다. 왜 "마지막에 **도착한** 것이 이긴다"가 되는가. `finally { setLoading(false) }`는 여기에 무엇을 더 숨기는가.
2. 요청 순번(세대) 토큰으로 늦은 응답을 버리는 코드에서, 토큰 증가를 "빈 쿼리면 조기 return" 분기 **뒤에** 두면 무슨 구멍이 생기는가. 토큰 확인은 몇 번의 await 지점마다 필요한가.
3. 저장 버튼: 저장 요청이 진행 중일 때 사용자가 더 편집했다. 늦게 끝난 저장 성공이 `dirty=false`를 쓰면? 편집 버전을 캡처해 비교하는 방식은 어떻게 이를 막는가.
4. 비동기 작업을 받아들인다는 응답(202)과 작업 완료 콜백이 서로 다른 채널로 온다. 짧게 실패하는 작업에서 완료 콜백이 202보다 먼저 도착하면, 202 수신 후 `status = RUNNING`을 쓰는 코드는 무엇을 만드는가. 단조(forward-only) 전이 가드는 어떻게 쓰는가 — DB 수준 잠금이 왜 추가로 필요했나.
5. 요청 순번 가드(늦은 결과 폐기)만으로는 막지 못하는 것은 무엇인가 — 4초 폴링·포커스·수동 새로고침이 겹쳐 서브프로세스가 폭주하는 경우.
6. 재연결 코드가 옛 소켓을 close한 직후 `ws = new Socket()`을 대입했다. 옛 소켓의 `onclose`가 나중에 `ws = null`을 실행하면? 핸들러를 공유 변수가 아닌 인스턴스 동일성으로 가드하는 법은.
7. 연결: 늦은 응답 하나를 막는 가드 축이 하나(요청 순번)로 부족한 경우들 — 캐시 축출·다른 writer·세션 전환·데이터 서명, 낙관적 갱신의 기준선, 부모-자식 이벤트의 인과 순서 — 각각 어떤 축을 더 비교해야 하는가.
