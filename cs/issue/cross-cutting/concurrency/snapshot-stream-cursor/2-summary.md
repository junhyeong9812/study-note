# cs/issue/concurrency/snapshot-stream-cursor — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.

## 전체 흐름

```
[틀린 순서 1: 스냅샷 먼저]
   snapshot() ──── (틈) ──── listen()
                    ▲ 이 사이 도착한 청크 = 어느 쪽에도 없음 → 유실

[틀린 순서 2: 구독 먼저, 커서 없음]
   listen() ─ 청크 c5 수신 ─ snapshot()  (스냅샷에도 c5 포함)
   → c5 두 번 적용 → 중복

[맞는 순서]
   서버: 락 안에서 { seq += 1; buf.append(chunk) }      ← 위치와 내용이 함께 움직임
         snapshot() = 락 안에서 (bytes, last_seq) 원자 반환

   클라: ① listen()  → 도착분은 pending에 버퍼 (필터 키도 이 전에 설정)
         ② (bytes, last_seq) = snapshot()  → 화면에 백필
         ③ pending 드레인: seq > last_seq 만 적용
         ④ 이후 라이브: seq > lastApplied 만 적용
   → 유실 0 · 중복 0 (단, 링 버퍼 용량 범위 안에서만)

[커서 = epoch:seq]
   epoch  재기동마다 바뀜 → 이전 인스턴스 커서를 구조적으로 거부
   seq    단조 증가
   커서가 링 밖(오래됨)·미래·손상 → 명시적 Gap + 스냅샷으로 재동기 (조용한 유실 금지)

[커서는 로컬 상태와 짝]
   상태 버림(detach) + 커서 유지 → 서버 "놓친 것 없음"(정직) → 클라엔 그 세계가 없음
   → 상태를 버리면 커서도 버린다 (재접속 = fresh + 스냅샷)

[해석 못 한 메시지]
   seq 있음 → 소비한 것으로 치고 전진 + 알림
   seq 없음 → 전진 금지 + 알림
```

## 핵심 문장

- 스냅샷과 스트림을 이으려면 **구독을 먼저** 걸어 도착분을 버퍼링하고, 스냅샷의 **마지막 seq 이후만** 적용한다.
- 서버는 seq 증가와 버퍼 append를 **같은 락**에서 하고, 스냅샷은 `(내용, 위치)`를 **원자적으로** 돌려준다.
- 발행 순서가 "상태 변경 → publish"면 스냅샷은 커서보다 **앞설 수는 있어도 뒤처지지 않는다** — 앞선 중복은 멱등 병합이면 무해, 뒤처짐은 영구 유실.
- 커서는 `epoch:seq`로 인스턴스를 구분하고, 복구 불가면 **명시적 Gap → 스냅샷**으로 재동기한다.
- 커서는 **짝이 되는 로컬 상태와 함께만** 의미가 있다 — 상태를 버리면 커서도 버린다.
- replay 없는 push 버스는 구독 이전 사건을 보관하지 않는다 → 구독 먼저, seed 나중, 늦은 seed가 새 라이브를 덮지 않게 비교 병합.
