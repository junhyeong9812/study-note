## 질문
1. 화면을 복원할 때 "스냅샷 조회 → 리스너 등록" 순서면 무엇이 사라지고, "리스너 등록 → 스냅샷 조회"만 하면 무엇이 두 번 보이는가. 둘 다 막으려면 무엇이 추가로 필요한가.
2. 스냅샷이 `(bytes, last_seq)`를 **원자적으로** 반환해야 하는 이유는 무엇인가. 버퍼 append와 seq 증가를 같은 락 안에서 하지 않으면 무엇이 깨지는가.
3. 예측: 구독 필터 키(세션 id)를 스냅샷 호출 **뒤에** 설정했다. 스냅샷 계산과 키 대입 사이에 도착한 청크는 어떻게 되는가.
4. 발행자가 "상태 변경 → 락 해제 → publish" 순서일 때, 락 안에서 찍은 스냅샷은 커서보다 **앞설 수**는 있지만 **뒤처질 수**는 없다 — 왜 그런가. 앞서는 경우의 중복은 왜 무해할 수 있고, 순서를 뒤집으면 왜 영구 유실인가.
5. 재개 커서를 `seq` 하나가 아니라 `epoch:seq`로 만드는 이유는 무엇인가. 서버가 재기동되면 무엇이 달라지는가.
6. 경계: 붙어 있던 화면 상태를 버리고 커서만 들고 재접속하면 서버는 정직하게 "놓친 것 없음"이라 답한다. 그런데 왜 데이터가 사라져 보이는가.
7. 연결: 해석하지 못한 메시지(모르는 종류)를 만났을 때 커서를 전진시킬지 말지는 무엇으로 정하는가. replay가 없는 push 이벤트 버스에서 "리스너 등록 전 발행된 이벤트"는 어떻게 다뤄야 하는가.
