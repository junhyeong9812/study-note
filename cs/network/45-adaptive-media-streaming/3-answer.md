# network/45-adaptive-media-streaming — 정답

## 정답

### 1. 세그먼트 + 매니페스트가 해결하는 문제

- **망 속도 변화 대응**: 세그먼트마다 화질을 다시 고를 수 있다. 통파일은 받는 도중 화질을 바꿀 수 없다.
- **생방송**: 파일이 끝나지 않아도 세그먼트를 계속 추가하고 목록을 갱신하면 된다.
- **HTTP·CDN 친화**: 작은 정적 객체의 평범한 GET이라 캐시·재시도·분산이 쉽다.

### 2. 계층 대응

```text
  HLS                                   DASH (MPD)
  master.m3u8 (EXT-X-STREAM-INF 목록)    MPD > Period > AdaptationSet (트랙 종류별 묶음)
    -> 미디어 재생목록 (low/mid/hi.m3u8)      -> Representation (한 화질)
       -> 세그먼트 URI (EXTINF)                   -> SegmentBase / SegmentList / SegmentTemplate
```

- HLS의 변형 스트림(variant)이 DASH의 Representation에 해당한다.

### 3. 라이브 시작 지연

- `ENDLIST`가 없으면 플레이어는 재생목록 끝에서 **목표 길이 3개 미만** 떨어진 세그먼트에서 시작하지 않는 것이 좋다(SHOULD NOT, RFC 8216 §6.3.3).
- 목표 길이 6초면 끝에서 최소 약 18초 뒤에서 시작한다.
- 여기에 더해지는 것
  - 인코딩·패키징 시간(세그먼트가 다 만들어져야 목록에 오른다).
  - 재생목록 갱신 대기(목표 길이마다 한 번).
  - CDN 캐시가 옛 재생목록을 주는 시간.

### 4. 재생목록 재요청 간격

- 처음 받았거나 **바뀌었으면**: 그 요청을 시작한 시각부터 **최소 목표 길이만큼** 기다린 뒤 다시 요청해야 한다(MUST, §6.3.4).
- **바뀌지 않았으면**: **목표 길이의 절반** 뒤에 다시 시도해야 한다(MUST).
- 이 하한은 서버 전체 부하를 제한하려는 규칙이다. 더 자주 요청하면 안 된다(MUST NOT).

### 5. 화질 전환의 전제

- 변형 간 같은 내용은 **타임스탬프가 일치**해야 한다(MUST, §6.2.4).
- 모든 변형의 **목표 길이가 같아야** 한다(MUST, 자막·I-프레임 전용 VOD 예외).
- 비디오 세그먼트는 디코더를 초기화할 정보를 담는 것이 좋다. H.264면 IDR 프레임이 있어야 한다(SHOULD, §3). 실무에서는 세그먼트 경계마다 키프레임을 맞춘다.
- 안 맞으면: 전환 순간 화면이 깨지거나, 디코더가 다음 키프레임을 기다리느라 멈춘다.

### 6. 이중 EWMA와 버퍼 기반

- 빠른 EWMA(반감기 2초)는 급락을 빨리 반영한다. 느린 EWMA(5초)는 일시적 급등을 무시한다.
- 둘 중 **작은 값**을 쓰면 "내려갈 때는 빨리, 올라갈 때는 천천히"가 된다. 과대 추정으로 감당 못 할 화질을 고르는 위험을 줄인다(Shaka Player 코드 주석).
- 버퍼 기반 ABR은 **버퍼에 쌓인 재생 시간**을 입력으로 쓴다. 버퍼가 적으면 낮은 화질, 많으면 높은 화질이다.
  - Huang 외(SIGCOMM 2014)는 정상 상태에서는 용량 추정 없이 버퍼만으로 충분하고, 시작 구간에서만 직전 처리량 추정이 중요하다고 보고했다.

### 7. 역할별 캐시 TTL

| 대상 | TTL | 근거 |
|---|---|---|
| VOD 세그먼트 | 길게(예: 1년, `immutable`) | 내용이 안 바뀐다. URL이 곧 버전이다 |
| 라이브 세그먼트 | 길게 | 한 번 만들어지면 안 바뀐다. 창에서 빠진 뒤에도 잠시 받을 수 있어야 한다(RFC 8216 §6.2.2) |
| 라이브 미디어 재생목록 | 목표 길이보다 짧게 | 목표 길이마다 바뀐다. 오래 캐시하면 플레이어가 새 세그먼트를 모른다 |

- 수치는 예시다. 핵심은 "불변 객체는 길게, 자주 바뀌는 목록은 갱신 주기보다 짧게"다.

### 8. 라이브 지연 + 시퀀스 정체 진단

- 확인
  - `curl -D -`로 재생목록 응답의 `Cache-Control`·`Age`·CDN 캐시 상태 헤더를 본다.
  - `Age`가 목표 길이보다 크면 CDN이 옛 목록을 주고 있다.
- 원인: 라이브 재생목록 TTL이 목표 길이보다 길다. 플레이어는 "변경 없음"을 보고 TD/2씩 기다리며 끝에서 멀어진다.
- 대처
  - 재생목록과 세그먼트의 캐시 규칙을 분리한다. 재생목록 TTL을 목표 길이보다 짧게 둔다.
  - CDN 규칙이 원점의 `Cache-Control`을 덮어쓰지 않는지 확인한다.

### 9. 인기 라이브의 캐시 미스 → 리버퍼링

- 경로
  1. 새 세그먼트가 목록에 오르면, 수많은 플레이어가 거의 동시에 그 세그먼트를 요청한다.
  2. 모든 엣지에서 미스가 동시에 나고, 원점으로 요청이 몰린다.
  3. 원점이 느려지면 세그먼트 다운로드 시간이 재생 시간보다 길어진다.
  4. 버퍼가 줄어 0이 되면 리버퍼링이다.
- 대처
  - 계층 캐시·원점 방패로 원점 요청을 한 곳으로 모은다.
  - 같은 객체의 동시 미스를 하나로 합친다(요청 병합). CloudFront Origin Shield는 같은 객체 요청을 합쳐 원점 요청을 줄인다.
  - 세그먼트 캐시 기간을 길게 둔다.

### 10. 화질 진동

- 되먹임 구조
  - 추정치가 높게 나옴 → 높은 화질 선택 → 세그먼트가 커져 다운로드가 느려짐 → 추정치 하락 → 낮은 화질 → 다운로드 빨라짐 → 추정치 상승 → 반복.
  - 여러 플레이어가 같은 병목을 나누면 서로의 추정을 흔든다.
- 대처
  - 평활 강화(느린 EWMA, 최솟값 규칙).
  - 히스테리시스(올리는 문턱 > 내리는 문턱)와 최소 전환 간격.
  - 버퍼 기반 규칙 결합. 버퍼가 충분하면 순간 처리량 변화에 덜 반응한다.
