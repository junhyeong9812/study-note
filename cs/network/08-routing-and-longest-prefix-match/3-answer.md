# network/08-routing-and-longest-prefix-match — 정답

## 정답

### 1. 네 목적지의 다음 홉

```text
10.144.2.5  -> /8, /16, /24, /0 모두 맞음 -> 가장 긴 /24 -> r3
10.144.9.1  -> /8, /16, /0 맞음 (/24는 10.144.2.x만) -> /16 -> r2
10.9.9.9    -> /8, /0 맞음 -> /8 -> r1
8.8.8.8     -> /0만 맞음 -> isp
```

첫 줄은 RFC 1812 §5.2.4.3의 예와 같다.

### 2. 왜 가장 긴 프리픽스인가

- 긴 프리픽스는 **더 작은, 더 구체적인 범위**다. 누군가 그 작은 범위만 따로 다른 곳으로 보내려고 넣은 예외 규칙이다.
- 짧은 쪽을 고르면 예외가 무시된다. 예: `10.0.0.0/8 → 본사`, `10.144.2.0/24 → 지사`일 때, 지사 대역이 본사로 가 버린다.
- CIDR 집약(큰 블록 광고)과 예외(작은 블록)를 함께 쓸 수 있는 것도 이 규칙 덕분이다.

### 3. 홉마다 바뀌는 것

- **바뀌는 것**
  - 이더넷 출발지·목적지 MAC(A→R1, R1→R2, R2→B로 홉마다 새 프레임)
  - IP TTL(홉마다 최소 1 감소)
  - 그래서 IP 헤더 체크섬도 다시 계산된다.
- **그대로인 것**: IP 출발지 A, IP 목적지 B, 전송 계층 포트와 데이터.

### 4. 같은 서브넷 vs 다른 망

- 판단: `(목적지 AND 마스크) == (내 주소 AND 마스크)`(RFC 1122 §3.3.1.1).
- 같은 서브넷 → **목적지 호스트의 MAC**(ARP로 찾음)을 쓴다.
- 다른 망 → **기본 게이트웨이(다음 홉 라우터)의 MAC**을 쓴다. IP 목적지는 여전히 최종 목적지 B다.

### 5. TTL

- 패킷을 전달하는 **모든 라우터가, 전달할 때마다, 최소 1**을 줄여야 한다(MUST, RFC 1812 §5.3.1).
- 0이 되면 패킷을 버리고, 멀티캐스트가 아니면 출발지에 ICMP Time Exceeded Code 0을 보내야 한다(MUST).
- 이 규칙이 없으면 루프에 빠진 패킷이 영원히 돌며 링크를 채운다. TTL 덕분에 루프 피해는 "TTL 홉만큼"으로 제한된다.
- 리눅스가 새로 만드는 패킷의 기본 TTL은 64다(`ip_default_ttl`).

### 6. 트라이 조회 비용

- 트라이는 목적지 주소의 비트를 앞에서부터 따라 내려간다. 내려가는 깊이는 **최대 주소 길이(IPv4 32비트)**다.
- 경로가 백만 개여도 한 조회가 보는 노드는 경로 하나만큼(최대 32개)이다. 그래서 경로 수와 무관하다.
- 리눅스 FIB는 **LC-trie**다(kernel "LC-trie implementation notes").
  - 경로 압축: 갈라짐 없는 비트를 건너뛴다.
  - 레벨 압축: 한 노드가 여러 비트로 여러 자식을 한 번에 인덱싱한다.
  - 정확한 잎이 없으면 프리픽스 길이를 줄이며 위로 되돌아가 최장 일치를 찾는다.

### 7. `unreachable` / `prohibit` / `blackhole`

| 종류 | 원격 송신자가 받는 것 | 로컬 프로그램의 에러 |
|---|---|---|
| unreachable | ICMP host unreachable | `EHOSTUNREACH` |
| prohibit | ICMP communication administratively prohibited | `EACCES` |
| blackhole | **아무것도 없음** (조용히 버림) | `EINVAL` |

(ip-route(8)) blackhole은 원격에서 보면 타임아웃뿐이라 진단이 가장 어렵다.

### 8. 조용한 타임아웃 좁히기

1. 클라이언트에서 `ip route get <목적지>` — 내 쪽 경로가 의도한 게이트웨이로 가는지 본다.
2. `traceroute`(또는 `mtr`) — 어느 홉부터 `* * *`인지 본다. 그 근처가 의심 구간이다.
3. 그 홉의 장비에서 해당 목적지 경로를 조회한다. `blackhole`, 다운된 터널, 잘못된 집약이 있는지 본다.
4. 목적지 쪽 `tcpdump`로 패킷이 도착하는지 본다. 도착하지 않으면 경로 문제, 도착하는데 응답이 없으면 호스트·방화벽 문제다.

- 주의: `* * *`는 "그 라우터가 ICMP를 안 보냈다"일 수도 있다. 그 뒤 홉이 응답하면 그 홉은 정상이다(09번).

### 9. SYN-ACK만 사라짐

- **원인**: 비대칭 라우팅이다. SYN은 FW-A를, SYN-ACK는 FW-B를 지난다. FW-B는 그 연결의 SYN을 본 적이 없어 "상태 없는 패킷"으로 버린다.
- **대처**
  - 양방향이 같은 상태 장비를 지나도록 경로를 대칭으로 맞춘다.
  - 또는 소스 NAT로 응답이 들어온 장비로 돌아오게 하거나, 방화벽 간 상태를 동기화한다.
  - 리눅스 호스트 자체가 비대칭이라면 `rp_filter` strict(1)가 버리는지도 확인한다. 비대칭 환경에는 loose(2)가 권장된다(kernel ip-sysctl 문서).

### 10. VPN 뒤 `10.20.x.x`만 안 됨

- `ip route get 10.20.1.1`(예시 주소) — `dev tun0` 등 VPN 인터페이스로 나가는지 본다.
- `ip route` — VPN이 `10.0.0.0/8` 같은 넓은 대역을 밀어 넣었는지 본다. 원래 `10.20.x.x`가 기본 경로(`/0`)로 나갔다면, 새 `/8`이 더 길어서 이긴다.
- 대처
  - VPN의 split tunnel 목록을 필요한 대역(`10.8.0.0/16`)으로 좁힌다.
  - 또는 `10.20.0.0/16`을 원래 게이트웨이로 향하게 하는 더 긴 경로를 추가한다.
