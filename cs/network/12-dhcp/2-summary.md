# network/12-dhcp — 주소를 "빌려 주고" 돌려받는 법 — 정리 (힌트)

## 해결하는 문제

호스트가 다른 망(인터넷)과, 이름(도메인)으로 통신하려면 보통 네 가지 값이 필요하다.\
같은 서브넷 안에서 IP로만 통신한다면 게이트웨이·DNS 없이도 된다(RFC 1122 §3.3.1.1).

```text
  내 IP 주소        10.0.0.57
  서브넷 마스크      255.255.255.0   (/24)
  기본 게이트웨이    10.0.0.1
  DNS 서버          10.0.0.2
```

기기가 수백 대라면 사람이 하나씩 넣을 수 없다.\
손으로 넣으면 같은 주소를 두 번 주는 실수도 난다.\
노트북처럼 망을 옮겨 다니는 기기는 망마다 값이 다르다.

DHCP는 이 값을 서버가 **자동으로, 기한을 정해** 나눠 주게 한다.

  - *DHCP(Dynamic Host Configuration Protocol)*: 호스트에게 IP 주소와 망 설정값을 자동으로 나눠 주는 프로토콜이다. RFC 2131이 정의한다.

쉬운 예: 도서관 책 대출이다.\
책(주소)을 기한(리스)을 정해 빌려 준다.\
기한 중간에 연장 신청을 할 수 있다.\
반납하지 않고 사라지면, 기한이 지난 뒤 다른 사람에게 다시 빌려 준다.

똑같은 구조다.\
주소 풀이 서가이고, **리스(lease)** 가 대출 기한이다.

  - *리스(lease)*: 서버가 주소를 빌려 준 기간이다. 이 기간이 지나면 클라이언트는 그 주소를 쓰면 안 된다.

실무 예:
- 사무실·가정의 공유기가 기기에 주소를 준다.
- 클라우드 VPC의 인스턴스도 DHCP 서버에서 주소 리스와 DNS·라우터 주소를 받는다(AWS "DHCP option sets in Amazon VPC").
- 게스트 와이파이에 사람이 몰리면 주소가 모자라 새 기기가 인터넷을 못 쓴다.

## 동작·원리

### 첫 할당 — DORA 4단계

클라이언트는 아직 주소가 없다.\
그래서 처음에는 보통 **브로드캐스트**로 서버를 찾는다.\
(서버 주소를 이미 아는 클라이언트는 유니캐스트로 보낼 수도 있고, 답이 없으면 브로드캐스트로 돌아간다 — RFC 2131 §4.4.4.)

```text
  클라이언트 (주소 없음)                                 DHCP 서버
  src 0.0.0.0:68                                        src 10.0.0.1:67

  1. DHCPDISCOVER  ---- 브로드캐스트 ------------------->  "주소 줄 서버 있나요?"
  2. DHCPOFFER     <----------------------------------  "10.0.0.57 어때요? 리스 1일"
  3. DHCPREQUEST   ---- 브로드캐스트 ------------------->  "그 서버(10.0.0.1)의 57번 받을게요"
  4. DHCPACK       <----------------------------------  "확정. 리스 1일, 게이트웨이, DNS"

  5. (클라이언트) ARP로 10.0.0.57을 이미 누가 쓰는지 확인 -> 없으면 사용 시작
```

- 첫 글자를 따서 **DORA**라고 부른다(RFC 2131 §3.1, Figure 3).
- 클라이언트는 UDP 68번, 서버는 UDP 67번을 쓴다(§4.1).
- 주소를 받기 전의 브로드캐스트는 출발지 IP를 0으로 둔다(§4.1).
- 3번 REQUEST도 브로드캐스트다.
  - 서버가 여럿이면 여러 곳에서 OFFER가 올 수 있다.
  - REQUEST에 고른 서버의 식별자(server identifier, 옵션 54)를 넣는다. 나머지 서버는 "내 제안은 거절됐다"를 알게 된다(§3.1, RFC 2132 §9.7).
- 서버는 제안할 주소를 누가 쓰고 있지 않은지 확인해야 한다(SHOULD). ICMP echo로 찔러 보는 방식이 예로 나온다(§3.1 2단계).
- 클라이언트도 받은 주소를 ARP로 마지막 확인해야 한다(SHOULD). 이미 쓰이고 있으면 **DHCPDECLINE**을 보내야 한다(MUST, §3.1 5단계).

  - *브로드캐스트*: 같은 링크(서브넷)의 모든 호스트에게 보내는 것이다. 목적지 `255.255.255.255`로 보낸다. 라우터를 넘어가지 않는다.

### 메시지 8종

```text
  클라이언트 -> 서버                          서버 -> 클라이언트
  DISCOVER  서버 찾기                          OFFER  주소 제안
  REQUEST   제안 수락 / 재부팅 후 확인 / 연장    ACK    확정 (+ 설정값)
  DECLINE   "그 주소 이미 누가 씀"              NAK    "그 주소 틀렸음 (망 이동·만료)"
  RELEASE   "이제 반납"
  INFORM    "주소는 있음, 설정값만 줘"
```

(RFC 2131 §3.1 Table 2)

### 리스 수명 — T1·T2 타이머

```text
  리스 = 1일(86400초, 예시)

  0h            12h (T1 = 0.5)             21h (T2 = 0.875)        24h
  |-- BOUND ----|------ RENEWING ----------|---- REBINDING ---------| 만료
                 ^                          ^                        ^
                 준 서버에게 유니캐스트로      아무 서버에게나            주소 사용 중단
                 "연장해 주세요"              브로드캐스트로 연장 요청     -> INIT (처음부터)
```

- T1의 기본값은 리스의 0.5배, T2는 0.875배다(RFC 2131 §4.4.5).
  - 서버가 옵션 58(T1)·59(T2)로 다른 값을 줄 수 있다(RFC 2132 §9.11·9.12).
  - 모든 기기가 같은 순간에 갱신하지 않도록, 값에 무작위 흔들림(fuzz)을 주는 것을 권한다(SHOULD).
- **RENEWING**(T1~T2): 원래 서버에게 유니캐스트로 REQUEST를 보낸다.
- **REBINDING**(T2~만료): 원래 서버가 답이 없으니 아무 서버에게나 브로드캐스트한다.
- 응답이 없으면 재전송한다. 간격은 남은 시간(RENEWING은 T2까지, REBINDING은 리스 만료까지)의 절반이고, 최소 60초다(SHOULD, §4.4.5).
- **만료**되면 즉시 주소 사용을 멈춰야 한다(MUST). 그리고 INIT 상태에서 처음부터 다시 받는다(§4.4.5).

리스가 길면 서버가 잠깐 죽어도 기기는 모른다.\
리스가 짧으면 주소가 빨리 회수되지만, 서버 장애가 곧바로 기기 장애가 된다.

### 클라이언트 상태 기계

```text
            +--------+  DISCOVER 보냄   +-----------+  OFFER 고르고 REQUEST  +------------+
  부팅 ---> |  INIT  | ---------------> | SELECTING | ---------------------> | REQUESTING |
            +--------+                  +-----------+                        +------------+
               ^   ^                                                            | ACK
               |   | NAK / 만료                                                 v
               |   +------------------ +-----------+  T2  +-----------+  T1  +-------+
               |                       | REBINDING | <--- | RENEWING  | <--- | BOUND |
               |                       +-----------+      +-----------+      +-------+
               |                              | ACK             | ACK           ^
               |                              +-----------------+---------------+
          (주소를 기억하는 재부팅: INIT-REBOOT -> REBOOTING -> BOUND)
```

- 상태 이름은 RFC 2131 Figure 5를 따른다.
- 재부팅한 기기는 예전 주소를 기억하면 DISCOVER를 건너뛴다. REQUEST로 "이 주소 계속 써도 되나"를 묻는다(§3.2).
  - 다른 망으로 옮겨 왔다면 서버가 NAK를 준다. 기기는 INIT으로 돌아간다.

### 릴레이 — 서버가 다른 서브넷에 있을 때

브로드캐스트는 라우터를 넘지 못한다.\
그래서 서브넷마다 서버를 두거나, 라우터가 **릴레이**를 해 준다.

```text
  서브넷 A (10.1.0.0/24)            라우터(릴레이)               DHCP 서버 (10.9.0.10)
  클라이언트 --DISCOVER(브로드캐스트)--> 받아서 giaddr=10.1.0.1 채움 --유니캐스트--> 서버
                                                                  "giaddr가 10.1.0.1이니
                                                                   10.1.0.0/24 풀에서 주자"
  클라이언트 <------------------------ 릴레이 <--------------------- OFFER
```

- 서버는 giaddr가 0이 아니면 응답을 그 릴레이로 보낸다(§4.1).
- 새 주소는 메시지가 들어온 서브넷(giaddr가 0일 때) 또는 giaddr 주소를 기준으로 고른다(§4.3.1).

  - *giaddr(gateway IP address)*: 릴레이 에이전트가 자기 주소를 적는 DHCP 헤더 필드다. 서버는 이 값을 보고 어느 서브넷의 풀에서 줄지 정한다.

### 주소를 못 받으면 — 169.254.x.x

```text
  DHCP 응답 없음 (풀 고갈·서버 장애·망 단절)
        |
        v
  RFC 3927 구현 호스트: 169.254.1.0 ~ 169.254.254.255 중 하나를 고름
        | ARP probe 3번으로 충돌 확인 (PROBE_NUM)
        v
  169.254.x.x 사용 — 같은 링크끼리만 통신 가능, 라우터가 전달하지 않음
```

- `169.254/16`은 링크 로컬 대역이다. 앞 256개와 뒤 256개 주소는 쓰지 않는다(RFC 3927 §2.1).
- 이 대역을 출발지·목적지로 가진 패킷은 라우터로 보내면 안 되고, 전달해서도 안 된다(MUST NOT, RFC 3927 §2.7).
- 그래서 "IP는 있는데 인터넷이 안 된다"로 보인다.
- 링크 로컬 설정은 DHCP 클라이언트 동작을 바꾸지 않는다. DHCP 시도는 따로 계속된다(RFC 3927 §2.11).

## 쓰이는 자료구조·알고리즘

- **리스 테이블** — 서버의 핵심 자료구조다.
  - 키는 클라이언트 식별자(보통 MAC 주소 `chaddr`), 값은 (주소, 만료 시각)이다.
  - 새 주소를 줄 때는 "그 클라이언트의 현재 바인딩 주소 → 예전(만료·반납된) 바인딩 주소 → 요청한 주소 → 풀의 빈 주소" 순서로 고른다(SHOULD, RFC 2131 §4.3.1).
  - 앞 순위가 "현재·예전 주소"라서 같은 기기는 같은 주소를 자주 받는다.
  - 주소가 모자라면 리스가 만료된 주소를 재사용한다. 예로 "가장 오래전에 할당한 주소"를 고를 수 있다(§2.2).
- **만료 타이머** — 리스마다 만료 시각이 있다. 만료되면 풀로 돌아간다. 가장 먼저 만료되는 것을 꺼내는 문제라 [힙](../../data-structure/07-heap/2-summary.md)이나 정렬된 구조가 어울린다.
- **상태 기계** — 클라이언트의 INIT·SELECTING·REQUESTING·BOUND·RENEWING·REBINDING(Figure 5).
- **트랜잭션 ID 매칭** — 요청과 응답을 `xid`(32비트)로 짝짓는다. 맞지 않는 ACK는 조용히 버린다(§4.4.5).

리스 테이블을 코드로 옮기면 이런 모양이다(TypeScript, 개념 예시).

```ts
type Lease = { ip: string; mac: string; expiresAt: number };

class LeaseTable {
  private byMac = new Map<string, Lease>();   // 클라이언트 -> 리스
  private free: string[];                      // 빈 주소 풀

  constructor(pool: string[], private leaseSec: number) { this.free = [...pool]; }

  offer(mac: string, now: number): string | null {
    this.reclaimExpired(now);
    const prev = this.byMac.get(mac);
    if (prev) return prev.ip;                  // 같은 기기에는 같은 주소
    return this.free[0] ?? null;               // null = 풀 고갈 -> OFFER 못 함
  }

  ack(mac: string, ip: string, now: number): Lease {
    this.free = this.free.filter((x) => x !== ip);
    const lease = { ip, mac, expiresAt: now + this.leaseSec * 1000 };
    this.byMac.set(mac, lease);
    return lease;
  }

  private reclaimExpired(now: number) {
    for (const [mac, l] of this.byMac) {
      if (l.expiresAt <= now) { this.byMac.delete(mac); this.free.push(l.ip); }
    }
  }
}
```

- `offer`가 `null`이면 서버는 OFFER를 보내지 않는다. 클라이언트 쪽에서는 "응답 없음"이다.
- 실제 서버는 만료된 리스를 곧바로 남에게 주지 않는 경우가 많다. 위 코드는 단순화했다.

## 적용 — 풀어나가는 법

### 1. 풀 크기와 리스 시간을 같이 본다

- 동시 접속 기기 수 > 풀 크기면, 리스가 만료되기 전까지 새 기기는 주소를 못 받는다.
- 사람이 빠르게 드나드는 곳(게스트 와이파이, 행사장)은 리스를 짧게 한다. 떠난 기기의 주소가 빨리 돌아온다.
- 서버·프린터처럼 고정이어야 하는 기기는 **예약**(MAC → 고정 주소)이나 수동 설정을 쓴다.
- 서버가 하나면 서버 장애가 곧 망 장애다. 리스를 적당히 길게 두면 서버 장애를 견딜 시간이 생긴다.

### 2. 진단 명령

```bash
# 현재 주소와 그 수명(valid_lft) — 수명은 커널 주소 속성이지 DHCP 리스 기록 자체는 아니다
# DHCP로 받았는지·리스가 얼마 남았는지는 DHCP 클라이언트 쪽(아래 networkctl·journalctl)에서 본다
ip -4 addr show dev eth0
#   inet 10.0.0.57/24 ... dynamic eth0
#      valid_lft 43012sec preferred_lft 43012sec     <- 주소 수명 (예시 값)

# DHCP 패킷만 잡기 — DORA가 어디서 끊기는지
sudo tcpdump -ni eth0 -v 'udp port 67 or udp port 68'

# NetworkManager / systemd-networkd 로그
journalctl -u NetworkManager | grep -i dhcp
networkctl status eth0
```

- tcpdump에서 DISCOVER만 반복되고 OFFER가 없다 → 서버가 안 받거나 풀이 없다.
- OFFER는 오는데 REQUEST 뒤 ACK가 없다 → 서버·릴레이 쪽 문제다.
- NAK가 온다 → 서버가 요청한 주소를 인정하지 않았다. 흔한 예가 다른 망의 예전 주소를 요구한 경우다(RFC 2131 §4.3.2).

## 장애 시나리오와 대처

### 1. DHCP 풀 고갈 — 새 기기가 `169.254.x.x`

- **현상**: 새로 접속한 기기만 인터넷이 안 된다. 원래 붙어 있던 기기는 된다.
- **보이는 형태**
  - 기기 주소가 `169.254.x.x`다.
  - tcpdump에 DISCOVER만 반복되고 OFFER가 없다.
  - 서버 로그에 빈 리스가 없다는 메시지가 남는다. 문구는 서버 제품마다 다르다(예: ISC dhcpd는 `network <서브넷>: no free leases`, 소스 `server/dhcp.c`).
- **원인**
  - 풀 크기보다 기기가 많다.
  - 떠난 기기의 리스가 아직 만료되지 않아 주소가 묶여 있다.
- **대처**
  - 풀을 넓히거나(서브넷 확장), 리스를 줄인다.
  - 리스 테이블에서 오래된 항목을 확인한다.
  - 게스트 망은 별도 서브넷·짧은 리스로 나눈다.

### 2. DHCP 서버 장애 — 몇 시간 뒤에 한꺼번에 끊긴다

- **현상**: 서버가 죽은 직후에는 아무 문제 없다. 몇 시간 뒤 기기들이 줄줄이 망에서 떨어진다.
- **보이는 형태**: RENEWING·REBINDING 요청(REQUEST)이 응답 없이 반복된다. 리스가 만료된 기기부터 주소를 잃는다.
- **원인**: 기기는 리스가 끝날 때까지 주소를 계속 쓴다. 만료되면 즉시 사용을 멈춰야 한다(RFC 2131 §4.4.5 MUST).
- **대처**
  - DHCP 서버를 이중화한다.
  - 장애 감지는 "서버 프로세스 살아 있음"이 아니라 "ACK가 나가는가"로 한다.
  - 리스를 너무 짧게 두지 않는다.

### 3. IP 충돌 — 누군가 같은 주소를 손으로 넣었다

- **현상**: 두 기기가 번갈아 끊긴다. 통신이 간헐적으로 엉뚱한 곳으로 간다.
- **보이는 형태**: 클라이언트가 DHCPDECLINE을 보낸다. OS가 "주소 충돌"을 경고한다. ARP 표에서 같은 IP의 MAC이 바뀐다.
- **원인**: 풀 안의 주소를 누군가 수동으로 설정했다. 서버는 그 주소가 비었다고 믿는다.
- **대처**
  - 수동 주소는 풀 밖에 둔다.
  - 서버의 사전 확인(ICMP probe)을 켜 둔다.
  - DECLINE 로그를 보고 충돌 주소를 찾는다.

### 4. 가짜(rogue) DHCP 서버

- **현상**: 일부 기기의 게이트웨이·DNS가 엉뚱한 값이다. 특정 사이트가 이상하게 열린다.
- **보이는 형태**: tcpdump에 OFFER가 두 서버에서 온다. 기기의 DNS 서버가 알 수 없는 주소다.
- **원인**: 기본 DHCP(RFC 2131)에는 인증이 없다. 인증 옵션(RFC 3118, 옵션 90)을 쓰지 않는 망에서는 누구나 서버를 띄워 가짜 게이트웨이·DNS를 뿌릴 수 있다(RFC 2131 §7).\
  실수로 연결한 공유기가 흔한 원인이다.
- **대처**
  - 스위치에서 허가된 포트만 서버 응답을 보내게 막는다(벤더의 DHCP snooping 기능 [?]).
  - OFFER를 보낸 서버 식별자(옵션 54)를 확인한다.

### 5. 다른 서브넷에서 주소를 못 받는다 — 릴레이 누락

- **현상**: 새로 만든 VLAN·서브넷의 기기만 주소를 못 받는다.
- **보이는 형태**: 그 서브넷 안의 tcpdump에는 DISCOVER가 보인다. 서버 쪽에는 아무것도 도착하지 않는다.
- **원인**: 브로드캐스트는 라우터를 넘지 않는다. 라우터에 릴레이 설정이 없다.
- **대처**: 라우터 인터페이스에 릴레이(서버 주소)를 설정한다. 서버에 그 서브넷(giaddr) 풀을 만든다.

## 핵심 문장

- DHCP는 주소와 망 설정(마스크·게이트웨이·DNS)을 보통 **기한이 있는 리스**로 빌려 준다(무한 리스·영구 할당도 규격상 가능, RFC 2131 §1·§3.3).
- 첫 할당은 DISCOVER → OFFER → REQUEST → ACK(DORA)이고, 주소가 없으니 보통 브로드캐스트로 시작한다.
- 리스의 절반(T1)에 원래 서버에게, 87.5%(T2)에 아무 서버에게나 연장을 요청한다. 만료되면 즉시 주소를 버린다.
- 풀이 고갈되거나 서버가 없으면 RFC 3927 호스트는 `169.254.x.x`를 스스로 붙인다. 이 주소는 라우터를 넘지 못한다.
- 브로드캐스트는 라우터를 넘지 못하므로 다른 서브넷에는 릴레이(giaddr)가 필요하다. 기본 DHCP에는 인증이 없어(RFC 3118 인증 옵션을 쓰지 않으면) 가짜 서버에 약하다.
