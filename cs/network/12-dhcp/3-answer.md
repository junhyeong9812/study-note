## 정답

### 1. 필요한 값과 대여 방식의 이유

- 네 가지: IP 주소, 서브넷 마스크, 기본 게이트웨이, DNS 서버.
  - 게이트웨이는 다른 망으로 갈 때, DNS는 이름으로 찾을 때 필요하다. 같은 서브넷 안 IP 통신만이면 앞의 둘로 된다.
  - DHCP 옵션으로는 마스크(1), 라우터(3), DNS(6)가 따라온다(RFC 2132).
- 사람이 넣으면 기기가 많을 때 감당이 안 되고, 같은 주소를 두 번 주는 실수가 난다. 망을 옮기는 기기는 망마다 값이 다르다.
- "기한 있는 대여(리스)"로 주면, 떠난 기기가 반납하지 않아도 기한이 지나면 주소가 풀로 돌아온다.

### 2. DORA

```text
DISCOVER (클라 -> 브로드캐스트)  ->  OFFER (서버 -> 클라)
REQUEST  (클라 -> 브로드캐스트)  ->  ACK   (서버 -> 클라)
```

- DISCOVER·REQUEST는 보통 브로드캐스트다. 서버 주소를 아는 클라이언트는 유니캐스트로 보낼 수 있다(RFC 2131 §4.4.4).
- 주소를 받기 전의 브로드캐스트는 출발지 IP를 0(`0.0.0.0`)으로 둔다(RFC 2131 §4.1).
- 목적지는 브로드캐스트 `255.255.255.255`다. 포트는 클라이언트 68 → 서버 67이다.
- ACK를 받은 뒤 클라이언트는 ARP로 그 주소가 쓰이고 있지 않은지 확인해야 한다(SHOULD). 쓰이고 있으면 DECLINE을 보낸다(MUST).

### 3. 여러 OFFER 중 고르기

- REQUEST에 고른 서버의 **server identifier(옵션 54)** 를 넣는다(RFC 2132 §9.7).
- REQUEST를 브로드캐스트로 보내야 **모든** 서버가 받는다.
  - 뽑힌 서버는 확정하고 ACK를 보낸다.
  - 뽑히지 않은 서버는 "내 제안은 거절됐다"를 알고, 제안했던 주소를 풀에 돌려놓을 수 있다(RFC 2131 §3.1 Table 2 "implicitly declining offers from all others").

### 4. 리스 8시간의 타이머

- T1 = 0.5 × 8h = **4시간째**: RENEWING. 원래 서버에게 **유니캐스트**로 REQUEST를 보낸다.
- T2 = 0.875 × 8h = **7시간째**: REBINDING. **아무 서버에게나 브로드캐스트**로 REQUEST를 보낸다.
- **8시간째** 만료: 즉시 그 주소 사용을 멈춰야 하고(MUST), INIT으로 돌아가 DISCOVER부터 다시 한다(RFC 2131 §4.4.5).
- 실제 값은 서버가 옵션 58·59로 바꿀 수 있고, 동시 갱신을 피하려고 흔들림(fuzz)을 준다.

### 5. 짧은 리스 vs 긴 리스

| | 짧은 리스 | 긴 리스 |
|---|---|---|
| 풀 고갈 | 떠난 기기의 주소가 빨리 돌아온다 → 고갈에 강하다 | 떠난 기기가 주소를 오래 잡는다 → 고갈에 약하다 |
| 서버 장애 | 금방 만료 → 서버가 죽으면 곧 기기가 끊긴다 | 만료까지 오래 버틴다 → 서버 복구 시간이 생긴다 |
| 부하 | 갱신 메시지가 잦다 | 적다 |

- 드나듦이 잦은 망(게스트 와이파이)은 짧게, 기기가 고정된 망은 길게 둔다.

### 6. 새 기기만 169.254.x.x

- 기기가 DHCP 응답을 못 받아 RFC 3927 링크 로컬 주소를 스스로 붙였다. 이 주소는 라우터를 넘지 못한다.
- 가설 A: **풀 고갈** — 서버는 살아 있지만 줄 주소가 없다.
- 가설 B: **서버·릴레이 장애** — DISCOVER가 서버에 닿지 않는다.
- 구분
  - 서버 쪽에서 tcpdump를 떠서 DISCOVER가 도착하는지 본다. 도착하는데 OFFER가 없으면 A일 가능성이 크다. 서버가 정책상(미등록 기기 등) 응답하지 않는 경우도 있으니(RFC 2131 §4.2) 서버 로그에서 빈 리스 없음을 확인한다. 도착하지 않으면 B다.
  - 기존 기기의 RENEWING(유니캐스트 REQUEST)에 ACK가 나가는지도 본다. 나가면 서버는 살아 있는 것이다.

### 7. 서버가 9시에 죽고 리스가 24시간

- 새로 들어오는 기기는 9시부터 바로 주소를 못 받는다.
- 이미 붙어 있던 기기는 한동안 멀쩡하다.
  - 서버가 살아 있던 동안 기기들은 T1(12시간)마다 리스를 24시간으로 갱신해 왔다.
  - 그래서 9시 시점에 각 기기의 남은 리스는 대략 12~24시간이다(T1 fuzz는 무시한 계산).
- 9시 이후의 갱신(RENEWING·REBINDING)은 모두 실패한다. 그래도 리스가 끝날 때까지는 주소를 쓴다.
- 따라서 기존 기기는 **대략 21시(12시간 뒤)부터 다음 날 9시 사이에** 하나씩 주소를 잃는다.
  - 예: 8시 30분에 갱신한 기기는 다음 날 8시 30분에 끊긴다. 전날 21시 10분에 갱신했고 9시 10분 갱신에 실패한 기기는 오늘 21시 10분에 끊긴다.

### 8. 다른 서브넷과 릴레이

- DISCOVER는 보통 브로드캐스트라 라우터를 넘지 못한다. 라우터(또는 전용 장비)가 **릴레이 에이전트**가 되어 설정된 서버 주소로(보통 유니캐스트) 전달해야 한다(RFC 1542 §4.1.1).
- 릴레이는 자기 인터페이스 주소를 **giaddr**에 적는다. 서버는 giaddr를 보고 그 서브넷의 풀에서 주소를 고른다(RFC 2131 §4.3.1).
- 서버는 응답을 giaddr의 릴레이로 보낸다(§4.1).

### 9. 가짜 DHCP 서버

- 기본 DHCP(RFC 2131) 메시지에는 인증이 없다. RFC 3118 인증 옵션이 있지만 쓰지 않는 망이면 가짜 서버를 구분할 수 없다. 클라이언트는 흔히 먼저 온 OFFER를 고른다. RFC 2131 §7도 "quite insecure"(상당히 불안전하다)라고 적고, 허가받지 않은 서버를 쉽게 띄울 수 있다고 말한다.
- 가짜 서버가 게이트웨이를 자기로 주면 기본 경로로 나가는(따로 정해진 경로가 없는) 트래픽이 그쪽을 지난다(중간자).
- DNS를 자기로 주면 원하는 도메인을 가짜 주소로 돌릴 수 있다.
- 대처는 망 장비에서 한다. 허가된 포트만 서버 응답을 보내게 막는다.

### 10. 리스 테이블 설계

- 키: 클라이언트 식별자(보통 MAC, `chaddr`). 값: (주소, 만료 시각, 상태).
- 반대 방향 조회(주소 → 누가 쓰나)도 필요하다. 그래서 주소 기준 인덱스를 하나 더 둔다.
- 새 주소를 고르는 순서(RFC 2131 §4.3.1, SHOULD)
  1. 이 클라이언트의 현재 바인딩 주소, 없으면 예전(만료·반납된) 바인딩 주소(비어 있으면)
  2. 클라이언트가 요청한 주소(유효하고 비어 있으면)
  3. 풀의 빈 주소(giaddr 또는 받은 서브넷 기준)
- 만료 처리는 만료 시각 순서로 꺼내면 되므로 힙이 어울린다.
