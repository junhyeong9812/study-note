## 정답

### 1. 정적 라우팅의 한계

- 링크가 끊겨도 정적 경로는 모른다. 사람이 고치기 전까지 죽은 경로로 계속 보낸다.
- 라우터·접두사가 많으면 모든 경로를 손으로 넣고 맞추기 불가능하다. 실수로 루프·블랙홀이 생긴다.
- 라우팅 프로토콜은 (1) 이웃 발견·생존 확인, (2) 도달 가능한 망 정보 교환, (3) 변화 시 경로 재계산을 자동화한다.

### 2. 세 방식 비교

| | 보내는 것 | 계산 재료 | 알고리즘 | 대표 |
|---|---|---|---|---|
| 링크 상태 | 내 링크 정보(LSA)를 area 전체에 flooding | 망 전체 지도(LSDB) | 다익스트라 | OSPF |
| 거리 벡터 | 내 거리표를 이웃에게만 | 이웃이 말한 거리 | 벨만-포드(분산) | RIP |
| 경로 벡터 | 목적지별 경로(AS_PATH)와 속성을 이웃에게만 | 이웃이 말한 경로들 + 정책 | 결정 과정(정책 → 동점 깨기) | BGP |

### 3. counting to infinity

```text
초기:         C: N까지 1 (직접)   B: N까지 2 (C 경유)   A: N까지 3 (B 경유)
B-C 끊김:     B: C 경유 경로 잃음. A가 "3"이라고 말함 -> B: 4 (A 경유)
              A: B가 "4" -> A: 5 (B 경유)
              B: A가 "5" -> B: 6 ...
              ... RIP의 무한 16에 닿을 때까지 반복
```

- 원인: A의 "3"은 사실 B를 거친 값인데, 거리 벡터는 경로를 모르고 거리만 전한다.
- split horizon: A는 B에게서 배운 경로(N)를 B에게 다시 알리지 않는다. 그러면 B는 A의 잘못된 "3"을 듣지 않는다(RFC 2453 §3.4.3).
- poisoned reverse는 A가 B에게 "N은 무한"이라고 적극적으로 알린다.
- 한계: split horizon with poisoned reverse는 라우터 둘 사이의 루프만 막는다. 셋이 서로 속이는 모양은 남는다(RFC 2453 §3.4.4).

### 4. OSPF의 수렴

1. 끊긴 링크의 양 끝 라우터가 이웃 상실을 감지한다(Hello 미수신 또는 인터페이스 다운).
2. 자기 링크 정보가 바뀌었으니 새 LSA를 만들어 area 전체에 flooding한다.
3. area 안의 모든 라우터가 LSDB를 갱신하고 다익스트라를 다시 돌린다.
4. 새 최단 경로 트리로 라우팅 테이블을 바꾼다.

- 빠른 이유: 모두가 **같은 지도**를 갖고 각자 계산한다. 잘못된 소문을 여러 번 주고받으며 값을 고쳐 가는 과정이 없다.

### 5. BGP의 루프 방지와 우선순위

- 경로가 AS를 지날 때마다 그 AS 번호가 AS_PATH 앞에 붙는다.
- 받은 경로의 AS_PATH에 **내 AS 번호**가 있으면, 이 경로는 나를 이미 지난 것이다. 결정 과정에서 뺀다(RFC 4271 §9.1.2).
- BGP는 **정책**을 먼저 본다. Phase 1에서 정책·LOCAL_PREF로 선호도를 매기고, 동점일 때만 "AS_PATH가 짧은 것" 같은 규칙을 순서대로 쓴다(§9.1.1, §9.1.2.2).
- 그래서 더 짧은 경로가 있어도 비즈니스 관계(고객 경로 선호 등)에 따라 다른 경로를 고를 수 있다.

### 6. /24가 /22를 이긴 이유

- 포워딩은 **최장 접두사 매칭**이다. `208.65.153.x`는 /22와 /24 둘 다에 맞는다. 더 긴 /24가 이긴다.
- BGP는 Pakistan Telecom이 그 대역을 광고할 권한이 있는지 검사하지 않았다. 상위 ISP PCCW도 걸러내지 않고 전파했다.
- YouTube는 같은 /24를 광고해 경쟁하고, 이어 더 긴 /25 두 개를 광고해 최장 접두사 매칭으로 되찾았다(RIPE NCC: 20:07 /24, 20:18 /25).
- 최종 해결은 PCCW가 잘못된 경로를 거둔 것이다(21:01 UTC).

### 7. Facebook 2021

1. 정기 작업 중 백본 용량 점검 명령이 백본 연결 전체를 끊었다. 감사 도구의 버그로 막히지 않았다.
2. Facebook의 DNS 서버는 데이터센터와 통신이 안 되면 스스로 BGP 광고를 거두도록 설계돼 있었다.
3. 그래서 권한 DNS 서버 대역의 경로가 인터넷에서 사라졌다. 서버는 살아 있었지만 아무도 닿을 수 없었다.
4. 공용 리졸버(1.1.1.1, 8.8.8.8)는 이름을 풀지 못해 SERVFAIL을 돌려줬다.
- 앱과 사용자가 에러를 받아들이지 않고 재시도해, 리졸버 질의량이 평소의 30배가 됐다(Cloudflare). 장애가 남의 인프라 부하로 번졌다.

### 8. Hold Timer Expired 반복

- 상대에게서 Hold Time(권장 90초) 동안 KEEPALIVE·UPDATE가 하나도 오지 않아 세션을 끊었다. 그리고 다시 맺기를 반복한다(flapping).
- 세션이 끊길 때마다 그 peer의 경로를 모두 거뒀다가 다시 받는다. 트래픽이 끊겼다 붙고, 전 세계에 UPDATE가 퍼진다.
- 먼저 볼 것
  - 세션이 지나는 링크의 손실·혼잡·오류 카운터.
  - 양쪽 라우터의 CPU 사용량(BGP 프로세스가 KEEPALIVE를 제때 못 보냄).
  - 경로 MTU 문제로 큰 UPDATE만 사라지는지.

### 9. ExStart에서 멈춤

- 가장 흔한 원인은 **양쪽 인터페이스 MTU 불일치**다.
- OSPF는 Database Description 패킷의 Interface MTU가 자기가 조각 없이 받을 수 있는 크기보다 크면 그 패킷을 거부한다(RFC 2328 §10.6). 그래서 DB 교환이 시작되지 못한다.
- Hello 간격·Dead 간격·마스크가 다르면 더 앞 단계에서 Hello가 버려진다(§10.5). 이때는 2-Way에도 못 간다.

### 10. 하이재킹 방어 수단

| 수단 | 검사하는 것 |
|---|---|
| prefix·AS_PATH 필터, max-prefix | 이 이웃이 광고해도 되는 대역·AS만 받는다. 받는 경로 수가 상한을 넘으면 세션을 내린다(RFC 7454 §6·§8·§9) |
| RPKI 출발지 검증 | 경로의 출발 AS가 그 대역의 ROA에 적힌 AS와 맞는지 본다. Valid·Invalid·NotFound로 판정한다(RFC 6811) |

- 출발지 검증은 "출발 AS"만 본다. 경로 중간이 조작된 경우(경로 누출 등)는 따로 막아야 한다.
