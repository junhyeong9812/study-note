## 정답

### 1. 새 연결 vs 재사용의 왕복 수

- 새 연결(TLS 1.3): TCP 1 RTT + TLS 1 RTT가 지나야 요청을 보낸다. 요청 전송까지 2 RTT, 응답까지 3 RTT다.
- 재사용: 요청을 즉시 보낸다. 요청 전송까지 0 RTT, 응답까지 1 RTT다.
- 재사용이 아끼는 다른 것
  - TLS 핸드셰이크의 CPU(키 교환·서명 검증).
  - TCP slow start. 새 연결은 혼잡 윈도가 작게 시작하지만, 재사용 연결은 이미 커진 윈도를 쓸 수 있다(18번).
  - 단 리눅스 기본값(`tcp_slow_start_after_idle=1`)에서는 유휴가 RTO를 넘길 때마다 cwnd가 절반으로 줄어(min(IW, cwnd)에서 멈춤) 오래 쉰 연결은 이 이득이 줄어든다.
  - 서버·클라이언트의 소켓과 TIME_WAIT 항목.

### 2. 지속 여부와 본문 소비

- 가장 최근 메시지로 정한다(RFC 9112 §9.3).
  - `Connection: close`가 있으면 그 응답 뒤 닫힌다.
  - 없고 HTTP/1.1 이상이면 유지된다.
  - HTTP/1.0이면 `Connection: keep-alive`가 있고 조건이 맞을 때만 유지된다.
- 본문을 끝까지 읽어야 하는 이유
  - HTTP/1.1 연결은 바이트 스트림 하나다. 메시지 경계는 `Content-Length`나 chunked로만 안다.
  - 읽다 만 본문이 남아 있으면 다음 요청의 응답을 읽을 때 그 잔여 바이트가 응답 시작으로 해석된다.
  - 그래서 클라이언트는 재사용하려면 응답 본문을 끝까지 읽어야 한다(MUST). 서버도 요청 본문을 끝까지 읽거나 응답 뒤 닫아야 한다(MUST).
  - 라이브러리는 본문이 남은 연결을 풀에 돌려주지 않고 버린다. 그러면 재사용이 안 된다.

### 3. idle close 경합 시간축

```text
  t=0      요청/응답 끝. 연결 idle로 풀에 반납
  t=5.000  서버: idle 5초 -> close() -> FIN 전송 -----------+
  t=5.001  클라이언트: 풀에서 같은 연결 꺼냄 -> GET 전송 --+    |
                                        (FIN 도착 전)   \   v
  t=5.002  서버 커널: 닫힌 소켓에 데이터 -> RST
  t=5.003  클라이언트: ECONNRESET / socket hang up
```

- 클라이언트는 60초까지 idle 연결을 믿고 쓰지만, 서버는 5초에 닫는다.
- FIN이 도착하기 전, 또는 도착했어도 풀이 아직 알아채지 못한 순간 재사용하면 RST를 받는다.
- RFC 9112 §9.5가 이 상황을 예로 든다.

### 4. 구간별 정렬

- 원칙: 각 구간에서 **재사용하는 쪽(클라이언트) idle < 받는 쪽(서버) keep-alive**.
- 브라우저 → ALB: 브라우저 idle < ALB idle timeout(기본 60초).
- ALB → Node: ALB idle(60초) < Node `server.keepAliveTimeout`.
  - Node 기본값은 5초다. 기본값 그대로면 **이 구간이 역전**된다.
  - Node가 5초에 닫는 순간 ALB가 재사용하면 ALB가 502를 낸다. AWS ALB 문서도 애플리케이션 idle timeout을 LB보다 크게 두라고 권한다.
  - 대처: `server.keepAliveTimeout`을 60초보다 크게(예: 65초, 예시) 둔다.
- Node → 외부 API: Node 풀 idle < 외부 서버 keep-alive. 외부 서버 값을 모르면 짧게(수 초~수십 초) 두고 재사용 실패는 멱등 요청만 재시도한다.

### 5. 풀 대기 타임아웃

- 원인 후보
  1. **연결 누수**: 응답을 닫지 않거나 본문을 소비하지 않아 연결이 반납되지 않는다.
     - 확인: 풀 지표에서 leased가 max에 붙어 내려오지 않는다. 트래픽이 적어도 그렇다. 코드에서 `close()`·`EntityUtils.consume` 누락을 찾는다.
  2. **한도가 작다**: Apache HttpClient 5의 기본은 호스트당 5, 전체 25다. 동시 요청이 그보다 많다.
     - 확인: pending이 트래픽 피크와 함께 오르내린다.
  3. **상류가 느려져** 연결을 오래 붙잡는다. 상류가 "정상"으로 보여도 p99 지연이 늘었을 수 있다.
     - 확인: 호출 지연 분포, 연결당 사용 시간.
- 공통 확인: 스레드 덤프에서 풀 대기 스레드 수, `ss`로 상류 연결 수가 한도에 붙어 있는지.
- 대처: 응답을 반드시 닫고, 한도를 상류 용량 안에서 조정하고, 풀 대기 타임아웃을 짧게 둬 빠르게 실패시킨다.

### 6. nginx 1.29.7 이전의 keepalive

- 재사용되지 않는다.
  - 그 버전에서 `proxy_http_version`의 기본은 1.0이다. HTTP/1.0 요청은 연결을 닫는 쪽이 기본이다.
  - nginx 문서는 HTTP 상류 keepalive에 `proxy_http_version 1.1`과 `proxy_set_header Connection ""`이 필요하다고 적는다(1.29.7부터는 기본).
- 증상
  - 요청마다 nginx가 상류에 새 TCP 연결을 연다.
  - nginx 쪽에 TIME_WAIT가 수만 개 쌓이고, 결국 임시 포트가 모자라 `connect()`가 `EADDRNOTAVAIL`로 실패한다. 사용자에게는 502가 간다.
  - 상류 서버는 연결 수립 비용으로 CPU가 오른다.

### 7. HTTP keep-alive vs TCP keepalive

- HTTP keep-alive(지속 연결): 응답 뒤에도 연결을 닫지 않고 다음 요청에 재사용하는 것이다. 목적은 **재사용**이다.
- TCP keepalive: 데이터가 없는 연결에 커널이 주기적으로 탐침 패킷을 보내 상대가 살아 있는지 확인하는 기능이다. 목적은 **생존 확인**이다. 21번에서 다룬다.
- 둘은 독립이다. HTTP 지속 연결이어도 TCP keepalive가 꺼져 있을 수 있다.
- 혼동 예: Node `http.Agent`의 `keepAliveMsecs`는 TCP keepalive 탐침의 초기 지연이다. `keepAlive: true`는 HTTP 재사용을 켠다(Node 문서).

### 8. LIFO vs FIFO

- LIFO: 가장 최근에 반납된 연결을 먼저 꺼낸다.
  - 요청이 드물 때 방금 쓴 연결을 쓰므로, 서버가 idle로 닫았을 연결을 고를 위험이 낮다.
  - 열려 있는 연결 수를 적게 유지한다. 안 쓰이는 연결은 idle timeout으로 정리된다.
- FIFO: 가장 오래 쉰 연결을 먼저 꺼낸다.
  - 모든 연결을 고르게 써서 열린 연결 수가 많이 유지된다.
  - 요청이 드물면 오래 쉰(서버가 닫았을 수 있는) 연결을 먼저 집는다.
- Node `http.Agent`의 기본은 `lifo`다(v15.6.0/v14.17.0에서 fifo → lifo로 변경, Node 문서).

### 9. 새 인스턴스에 트래픽이 안 감

- 원인
  - 연결 단위 분산(L4 LB, DNS·클라이언트 측 분산)은 **새 연결**을 맺을 때 대상을 고른다. L7 LB(ALB·nginx)는 요청마다 고르므로 이 문제는 연결 단위로 분산하는 구간(L4 LB, 쿠버네티스 Service 같은 L4 경로, 클라이언트 측 분산)에서 주로 생긴다.
  - 클라이언트(또는 LB→대상 구간)가 지속 연결을 오래 재사용하면 기존 연결은 옛 인스턴스에 고정된다.
  - HTTP/2처럼 연결 하나에 요청을 몰아 싣는 경우 더 심하다(36번).
- 대처
  - 연결 최대 수명을 둔다. 서버 쪽 nginx `keepalive_time`·`keepalive_requests`, ALB HTTP client keepalive duration, 클라이언트 풀 TTL.
  - 서버가 `Connection: close`나 `GOAWAY`를 보내 재연결을 유도한다.
  - 필요하면 L7 분산(요청 단위)을 쓴다.

### 10. 재사용 연결의 ECONNRESET 재시도

- 무조건은 안 된다.
- 요청이 서버에 도착해 처리됐는지 클라이언트는 모른다. RST가 요청 처리 **뒤에** 왔을 수도 있다.
- 되는 경우
  - 멱등 메서드(GET·HEAD·PUT·DELETE 등)면 다시 보내도 효과가 같다(RFC 9110 §9.2.2).
  - 비멱등이라도 멱등 키로 서버가 중복을 걸러 내면 된다.
- 안 되는 경우: 멱등 키 없는 POST. 클라이언트는 자동 재시도하지 않아야 한다(SHOULD NOT), 프록시는 하면 안 된다(MUST NOT).
- Node 문서의 패턴: `req.reusedSocket && err.code === 'ECONNRESET'`일 때만 재시도한다. 여기에 "멱등 요청일 때만"을 더한다.
- 재시도는 한 번으로 제한한다. 실패한 자동 재시도를 다시 자동 재시도하지 않아야 한다(SHOULD NOT).
