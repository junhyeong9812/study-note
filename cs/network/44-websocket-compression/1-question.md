## 질문

1. (왜) WebSocket 메시지는 왜 HTTP `Content-Encoding`으로 압축할 수 없고, 별도 확장이 필요했나?
2. (그림) permessage-deflate의 협상 과정을 핸드셰이크 헤더로 그리고, "합의된 파라미터"가 어디서 정해지는지 표시하라.
3. (경계) 압축된 메시지를 수신자는 어떻게 알아보나? 메시지가 여러 프레임으로 나뉘면 어느 프레임에 표시가 붙나?
4. (그림) 같은 "Hello"를 두 번 보낼 때 컨텍스트 유지와 `no_context_takeover`의 페이로드가 어떻게 다른지 그리고, 그 차이의 대가를 말하라.
5. (예측) 동시 연결 2만 개인 서버가 zlib 기본값으로 양방향 컨텍스트를 유지한다. 압축 상태만으로 대략 몇 GB가 필요한가? 계산 과정을 보여라.
6. (적용) 메모리를 줄이려고 서버가 응답에 넣을 수 있는 파라미터는 무엇이고, 각각 무엇을 줄이나?
7. (연결) 컨텍스트 유지가 43번의 압축 사이드채널을 HTTP 응답 압축보다 더 넓게 만드는 이유는?
8. (장애 진단) 작은 프레임 하나를 받은 직후 서버 메모리가 수백 MB 뛰었다. 원인과 설정 대처는?
9. (장애 진단) 특정 프록시를 거치면 브라우저가 WebSocket 연결 직후 실패한다. 핸드셰이크 응답의 무엇을 확인하나?
