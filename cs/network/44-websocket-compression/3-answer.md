# network/44-websocket-compression — 정답

> 복습 시 이 파일은 **최후에만** 연다.
> ⚠️ 이 정답은 Claude 초안(2026-09-30). 본인 검수 후 이 줄을 `✅ 검수 완료(날짜)`로 바꾼다.

## 정답

### 1. 왜 별도 확장이 필요했나

- `Content-Encoding`은 HTTP 메시지(요청·응답) 하나의 본문에 붙는 헤더다.
- WebSocket은 여는 핸드셰이크(HTTP Upgrade) 뒤에는 HTTP 메시지를 더 주고받지 않는다. 그 뒤는 WebSocket 프레임뿐이다.
- 그래서 메시지마다 "압축됐다"를 표시할 자리가 프레임 헤더에 있어야 했다. RFC 7692가 RSV1 비트와 협상 방식을 정했다.

### 2. 협상 과정

```text
  Client -> Server
    Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits      (제안 offer)
  Server -> Client (101)
    Sec-WebSocket-Extensions: permessage-deflate; server_no_context_takeover  (응답 = 합의)
```

- 클라이언트는 여러 제안을 보낼 수 있다. 서버는 하나를 골라 수락하거나 모두 거절한다(RFC 7692 §1, §5).
- **합의된 파라미터는 서버 응답에 적힌 것**이다.
- 응답이 규칙을 어기면(정의되지 않은 파라미터, 잘못된 값, 중복) 클라이언트는 연결을 실패 처리해야 한다(MUST, §7).

### 3. 압축 표시

- 프레임 헤더의 **RSV1 비트**가 "Per-Message Compressed" 비트다(§6).
- 조각난 메시지는 **첫 프레임에만** RSV1을 켠다. 수신자는 모든 조각의 페이로드를 이어 붙인 뒤 한 번에 해제한다.
- RSV1이 꺼진 메시지는 원문 그대로다. 이 덕분에 압축 이득이 없는 메시지는 건너뛸 수 있다.

### 4. 컨텍스트 유지 vs no_context_takeover

```text
  컨텍스트 유지:      msg1 = f2 48 cd c9 c9 07 00   msg2 = f2 00 11 00 00   (msg1 역참조)
  no_context_takeover: msg1 = f2 48 cd c9 c9 07 00   msg2 = f2 48 cd c9 c9 07 00
```

(RFC 7692 §7.2.3.2)

- 컨텍스트 유지는 이전 메시지를 사전으로 써서 두 번째 메시지를 5바이트로 줄였다.
- 대가: 송신자는 압축기의 LZ77 윈도를, 수신자는 해제기의 윈도를 **연결 수명 동안** 들고 있어야 한다. 수신자는 이전 윈도로 해제해야 하기 때문이다(MUST, §7.2.2).

### 5. 2만 연결의 메모리 계산

```text
  deflate = (1 << (15 + 2)) + (1 << (8 + 9)) = 131072 + 131072 = 262144 B ≈ 256KB
  inflate = 1 << 15 = 32768 B ≈ 32KB
  연결당 ≈ 288KB
  2만 연결 ≈ 20,000 × 288KB ≈ 5.8GB   (+ 작은 객체·버퍼 별도)
```

- 공식은 Node.js zlib 문서(zconf.h 인용)의 것이다. 이 계산은 예시이고, 실제 값은 구현과 할당기에 따라 달라진다.

### 6. 메모리를 줄이는 응답 파라미터

| 파라미터 | 줄이는 것 |
|---|---|
| `server_no_context_takeover` | 서버 압축기가 메시지 사이에 윈도를 유지할 필요 제거(클라이언트 해제기도) |
| `client_no_context_takeover` | 클라이언트가 메시지마다 빈 윈도로 압축 → 서버 해제기가 메시지 사이 윈도를 들 필요 제거 |
| `server_max_window_bits=N` | 서버 압축 윈도를 2^N으로 제한 → 서버 압축기·클라이언트 해제기 메모리 감소 |
| `client_max_window_bits=N` | 클라이언트 압축 윈도 제한 → 서버 해제기 메모리 감소. 단 제안에 이 파라미터가 있어야 응답에 넣을 수 있다 |

- `*_no_context_takeover`는 프로토콜상 "윈도를 들고 있을 의무"만 없앤다. 메모리가 실제로 주는지는 구현 의존이다. Node `ws`는 메시지마다 zlib를 `reset()`만 하고, zlib reset은 내부 상태를 해제하지 않으므로 연결당 메모리가 그대로다(ws `lib/permessage-deflate.js`, zlib manual).
- zlib의 `memLevel`(해시 테이블 크기)은 협상 파라미터가 아니라 구현 설정이다. 압축기 메모리의 절반을 차지하므로 함께 줄인다.

### 7. 컨텍스트 유지와 사이드채널

- 일반 HTTP 응답 압축(gzip·br 등)의 사전은 **응답 하나** 안에서만 공유된다.
  - 예외: RFC 9842 사전 전송(`Use-As-Dictionary`/`Available-Dictionary`, `dcb`·`dcz`)을 쓰면 이전 응답이 다음 응답의 사전이 된다.
- 컨텍스트 유지는 사전을 **연결의 모든 이전 메시지**로 넓힌다.
- 그래서 예전 메시지에 들어 있던 토큰과, 나중 메시지에 반영된 공격자 문자열이 같은 사전에서 만난다. 둘이 한 메시지에 없어도 된다.
- RFC 7692 §8은 이력 기반 압축과 보안 전송을 섞을 때의 알려진 공격(CRIME)을 경고한다.
- 대처: 비밀이 든 메시지는 압축하지 않거나, `no_context_takeover`로 메시지 간 공유를 끊는다.

### 8. 압축 폭탄

- 원인: DEFLATE는 반복 데이터를 극단적으로 줄인다. 작은 페이로드가 거대한 메시지로 풀린다. 해제 전에는 크기를 모른다.
- 대처: 해제 후 메시지 크기 상한을 서비스에 맞게 낮춘다. Node `ws`의 `maxPayload`는 기본 100 MiB다. 넘으면 1009로 연결을 닫는다.
- 상한 초과 연결은 기록하고 반복되면 차단한다.

### 9. 협상 실패 진단

- 101 응답의 `Sec-WebSocket-Extensions` 값을 본다.
  - 제안에 없던 `client_max_window_bits`가 응답에 있으면 규칙 위반이다(MUST NOT, §7.1.2.2).
  - 같은 파라미터가 두 번 있거나 값이 8~15 범위를 벗어나면 규칙 위반이다.
  - 이런 응답이면 클라이언트는 연결을 실패 처리해야 한다.
- 확인은 `curl -i`로 Upgrade 핸드셰이크만 보내거나, 브라우저 개발자 도구 Network 탭의 WS 항목에서 한다.
- 대처: 프록시·서버 확장 구현을 고치거나 해당 경로에서 압축을 끈다.
