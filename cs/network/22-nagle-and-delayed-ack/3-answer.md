## 정답

### 1. 두 장치가 줄이는 낭비

- 1바이트 데이터에 IPv4 20 + TCP 20바이트 헤더가 붙어 41바이트 패킷이 된다. 오버헤드가 4000%다(RFC 896).
- **Nagle**은 송신 쪽에서 작은 조각을 모아 **작은 패킷 수**를 줄인다.
- **지연 ACK**는 수신 쪽에서 ACK를 잠깐 미뤄, 응답 데이터에 얹거나 여러 세그먼트의 ACK를 합친다. **ACK 패킷 수**를 줄인다(RFC 1122 §4.2.3.2 — 원격 로그인에서 세그먼트를 1/3로 줄인 예).

### 2. Nagle 보류 조건

- 보류 조건: 확인 안 된 데이터가 있다. 즉 `SND.NXT > SND.UNA`다. 이때 새 작은 데이터는 PSH 비트와 무관하게 모은다(RFC 9293 §3.7.4).
- 보류가 풀리는 조건
  1. 떠 있던 데이터가 모두 ACK됐다.
  2. 꽉 찬 세그먼트(Eff.snd.MSS 바이트)를 만들 만큼 모였다.

### 3. write-write-read 교환도

```text
  클라이언트                              서버
  write(헤더) -> 즉시 전송  --[헤더]-->    요청 미완성. 보낼 응답 없음 -> ACK 지연
  write(본문) -> 보류 (헤더가 미확인)
                            <--[ACK]--     지연 ACK 타이머 만료 (리눅스 최소 40ms)
  본문 전송                 --[본문]-->    요청 완성
                            <--[응답]--
```

- 지연은 "서버의 지연 ACK 타이머"와 "클라이언트의 Nagle 보류"가 겹치는 구간에서 생긴다.
- 서로 상대의 다음 행동(ACK, 나머지 데이터)을 기다린다. 타이머가 만료돼야 풀린다.

### 4. 한 번에 쓰면

- 지연이 사라진다.
- 떠 있는 데이터가 없는 상태에서 전체 요청이 한 세그먼트(또는 꽉 찬 세그먼트들)로 나간다. Nagle이 보류할 "다음 작은 조각"이 없다.
- 서버는 요청을 한 번에 받아 곧바로 응답한다. ACK는 응답 데이터에 얹혀 나간다(piggyback).

### 5. 지연 ACK 상한

- RFC: 지연은 0.5초 미만이어야 한다 — **MUST**(RFC 9293 MUST-40, RFC 1122 §4.2.3.2). 지연 ACK 구현 자체는 **SHOULD**(SHLD-18)다. 꽉 찬 세그먼트 2개마다 ACK도 **SHOULD**(SHLD-19)다.
- 리눅스: `include/net/tcp.h`의 `TCP_DELACK_MIN = HZ/25`(40ms), `TCP_DELACK_MAX = HZ/5`(200ms)다. 연결마다 이 범위에서 `ato`가 정해진다. `ss -ti`의 `ato:`로 볼 수 있다.

### 6. `TCP_NODELAY`의 한계와 부작용

- 한계: Nagle만 끈다. 앱이 잘게 여러 번 쓰는 습관은 그대로다. 수신 쪽 지연 ACK도 그대로다.
- 부작용: 잘게 쓰는 앱이면 작은 세그먼트가 하나하나 나간다. 패킷 수(pps)·CPU가 늘고, 대량 전송 효율이 떨어진다. RFC 896의 small-packet problem이 돌아온다.
- 그래서 1순위는 "메시지를 한 번에 쓰기"다. `TCP_NODELAY`는 그 위에 얹는다.

### 7. Minshall 변형으로도 안 풀리는 이유

- Minshall 변형은 "확인 안 된 **작은** 세그먼트가 있을 때만" 보류한다(RFC 9293 부록 A.3이 표준 밖 변형으로 소개, 리눅스 `tcp_nagle_check()`·`tcp_minshall_check()`).
- write-write-read에서는 첫 조각(헤더)이 바로 그 작은 세그먼트다.
- 그래서 둘째 조각은 여전히 보류되고, 서버의 지연 ACK와 맞물린다.

### 8. 초당 약 25건에서 막힘

- 1000ms / 40ms = 25다. 요청마다 리눅스 지연 ACK 최소값(40ms)만큼 멈춘다고 의심한다.
- 확인 순서
  1. `tcpdump -ni any -ttt 'tcp port <포트>'` — 데이터 없는 ACK가 약 40ms 간격 뒤에 오고, 그 직후 나머지 조각이 나가는지 본다.
  2. `strace -e trace=write,writev,sendto,sendmsg -p <pid>` — 요청 하나에 쓰기 호출이 2번 이상인지 본다.
  3. 소켓 설정에서 `TCP_NODELAY` 여부를 확인한다.
- 대처: 요청을 한 번에 쓰고, 요청-응답형이면 `TCP_NODELAY`를 켠다.

### 9. `TCP_CORK` 200ms 지연

- 원인: 코르크를 켠 뒤 해제하지 않았다. 마지막 부분 프레임이 코르크 상한 200ms가 지나서야 자동 전송된다(tcp(7) "there is a 200 millisecond ceiling").
- 대처
  - 응답을 다 쓰면 `TCP_CORK`를 0으로 되돌린다.
  - 또는 호출 단위인 `send(..., MSG_MORE)`를 쓰고, 마지막 조각에는 플래그를 뺀다.
- `TCP_CORK`·`MSG_MORE`는 리눅스 전용이다.

### 10. Go → Java 이식 뒤 지연

- Nagle 기본값이 다르다.
  - Go `TCPConn`은 기본 no delay(Nagle 꺼짐)다.
  - Java `Socket`은 `TCP_NODELAY` 기본 FALSE(Nagle 켜짐)다.
- 코드가 요청을 여러 번 나눠 쓰면, Go에서는 문제없던 것이 Java에서는 write-write-read 지연으로 드러난다.
- 대처: 소켓 생성 코드에서 `setTcpNoDelay(true)`를 명시하고, 요청을 한 번에 쓰도록 버퍼링한다.
