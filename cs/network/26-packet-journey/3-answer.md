## 정답

### 1. 구간 순서

```text
프로세스(이름 해석 27, socket/connect/write 23)
 -> 커널 TCP(15~18) -> 커널 IP·라우팅(08) -> 이웃/ARP(05) -> qdisc·드라이버·NIC(25)
 -> 스위치(06) -> 라우터+NAT(08, 11) -> 인터넷 라우터들(08, 13)
 -> 서버 쪽 방화벽·LB(48, 46) -> 서버 NIC·커널(25) -> 소켓 큐 -> 서버 프로세스(23)
응답은 같은 길을 거꾸로.
```

### 2. ARP 대상과 프레임 주소

- 목적지 203.0.113.50은 10.0.1.0/24 밖이다. 그래서 라우팅은 기본 게이트웨이(예: 10.0.1.1)를 다음 홉으로 고른다.
- ARP는 **게이트웨이 10.0.1.1의 MAC**을 찾는다. 서버의 MAC은 찾지 않는다.
- 프레임 목적지 MAC = 게이트웨이 MAC이다.
- IP 헤더 목적지 = 203.0.113.50(서버)이다.

### 3. 무엇이 어디서 바뀌나

| 필드 | 스위치 | R1(NAT) | R2 등 라우터 |
|---|---|---|---|
| src/dst MAC | 안 바뀜 | 둘 다 새로 씀 | 둘 다 새로 씀 |
| src IP | 안 바뀜 | 사설 → 공인으로 바뀜 | 안 바뀜 |
| dst IP | 안 바뀜 | 안 바뀜 | 안 바뀜 |
| TTL | 안 바뀜 | -1 | -1 |
| TCP src 포트 | 안 바뀜 | NAT가 바꿀 수 있음 | 안 바뀜 |
| TCP dst 포트 | 안 바뀜 | 안 바뀜 | 안 바뀜 |

- TTL이 바뀌므로 라우터마다 IPv4 헤더 체크섬도 갱신된다.
- L2를 새로 쓰므로 이더넷 FCS도 새로 계산된다.
- 서버 앞 L4 LB가 DNAT하면 dst IP·포트가 거기서 바뀐다.

### 4. 스위치 vs 라우터 vs NAT·방화벽

- 스위치: 이더넷 헤더(MAC)만 본다. MAC 주소·IP는 바꾸지 않고(VLAN 태그를 붙이거나 떼는 경우만 예외) MAC 표로 나갈 포트를 고른다. 모르면 플러딩한다.
- 라우터: 이더넷을 벗기고 IP 헤더를 본다. TTL을 줄이고 최장 접두사로 다음 홉을 고른 뒤 새 이더넷 헤더를 씌운다.
- NAT·방화벽: 연결 단위로 상태를 들고 있어야 한다. 그래서 IP뿐 아니라 TCP/UDP 포트까지 본다(5-튜플). NAT는 여러 내부 호스트가 공인 IP 하나를 나눠 쓰므로 포트로 구분해야 한다.

### 5. TTL 규칙과 traceroute

- 라우터는 전달할 때 TTL을 **최소 1 줄여야 한다(MUST)**. 1초 넘게 붙잡았다면 초마다 1씩 더 줄여도 된다(MAY)(RFC 1812 §5.3.1).
- TTL이 0 이하가 되면 **버려야 하고(MUST)**, 목적지가 멀티캐스트가 아니면 출발지에 ICMP Time Exceeded(Code 0)를 **보내야 한다(MUST)**.
- `traceroute`는 TTL을 1, 2, 3…으로 늘려 보낸다. 각 홉 라우터가 돌려보내는 Time Exceeded의 출발 주소로 경로를 그린다.

### 6. 조회하는 표

| 위치 | 표 | 키 | 자료구조 |
|---|---|---|---|
| 송신 커널 | 라우팅 표 | dst IP | 최장 접두사 매칭(트라이 계열) |
| 송신 커널 | 이웃(ARP) 캐시 | 다음 홉 IP | 해시 + 만료 타이머 |
| 스위치 | MAC 표 | dst MAC | 해시(CAM) + 에이징 |
| 라우터/NAT | NAT·conntrack 표 | 5-튜플 | 해시 + idle 타이머 |
| 라우터 | 라우팅 표 | dst IP | 최장 접두사 매칭 |
| 수신 커널 | 소켓 조회 표 | 4-튜플 / 리슨 포트 | 해시 |

### 7. `ETIMEDOUT` 좁히기

1. `getent hosts <이름>` — 이름 해석이 되고 기대한 IP인가
2. `ip route get <IP>` — 커널이 고르는 경로·출발 주소
3. `ip neigh show <게이트웨이>` — 다음 홉 MAC을 아는가
4. `tcpdump -ni <if> host <IP>` — SYN이 나가는가, SYN-ACK나 RST·ICMP가 돌아오는가
5. `mtr`/`traceroute -T -p <포트>` — 경로 중 어디서 끊기나
6. 서버에서 `ss -tlnp`, `ss -tn state syn-recv`, 서버 tcpdump — SYN이 서버에 닿는가

- SYN이 나가는데 아무 응답이 없으면, 경로나 방화벽이 조용히 버리는 것이다(DROP).
- RST가 오면 `ECONNREFUSED`가 났어야 한다. 그러니 `ETIMEDOUT`이면 "무응답"이 핵심 단서다.

### 8. 큰 응답에서만 멈춤

- 구간: 경로 중간(터널·VPN·오버레이 구간)이다.
- 원인: 그 구간의 MTU가 작다. 그런데 "fragmentation needed"(IPv6 "Packet Too Big") ICMP가 방화벽에 막혀 PMTUD가 실패했다. 큰 세그먼트만 계속 버려진다(10번).
- 단서: 핸드셰이크·작은 요청은 되고, MTU 크기 세그먼트의 재전송만 반복된다.
- 대처: 해당 ICMP를 허용하거나 MSS를 줄인다(MSS clamping).

### 9. SYN-ACK가 클라이언트에 안 닿음

- 비대칭 경로: 응답이 다른 NAT·방화벽으로 나갔다. 그쪽 상태 표에 이 연결이 없어 버려진다.
- 역경로 필터: 클라이언트 쪽(또는 중간) 호스트의 `rp_filter` 엄격 모드가 "이 인터페이스로 올 주소가 아니다"라며 버렸다.
- 그 밖에 클라이언트 쪽 방화벽이 들어오는 SYN-ACK를 막는 경우도 있다.

### 10. 오래 쉰 풀 연결의 첫 요청 실패

- 원인 표: 경로 중간 NAT(또는 상태 방화벽·LB)의 연결 추적 표다. idle timeout으로 항목이 지워졌는데 양 끝 호스트는 연결이 살아 있다고 믿는다(half-open).
- 결과: 첫 요청이 버려져 타임아웃이 나거나, 장비·상대가 RST를 보내 `ECONNRESET`이 난다.
- 대처
  - 풀의 idle timeout을 경로상 가장 짧은 idle timeout보다 짧게 둔다.
  - 또는 keepalive를 그보다 짧은 간격으로 보낸다.
  - 멱등 요청은 재시도를 허용한다.
