# network/43-compression-side-channels — 정답

## 정답

### 1. 암호화해도 압축이 비밀을 새게 만드는 이유

- 암호화는 내용을 숨기지만 암호문 **길이**는 평문 길이를 거의 그대로 따라간다.
- 압축은 내용에 따라 길이를 바꾼다. 그래서 "압축 → 암호화"를 하면 길이가 내용(반복 여부)에 대한 신호가 된다.
- RFC 7541 §7.1도 TLS는 내용을 보호하지만 길이는 제한적으로만 보호한다고 적는다.

### 2. LZ77 역참조 그림

```text
  본문:  value="csrf_token=7f3a9c" ... 검색어: csrf_token=7X
                ^^^^^^^^^^^^                   ^^^^^^^^^^^^
  추측이 "csrf_token=7" 까지 맞음 -> <거리, 길이 12> 역참조 + 리터럴 'X'
  추측이 "csrf_token=0" -> <거리, 길이 11> 역참조 + 리터럴 '0'
```

- 한 글자 더 맞으면 역참조가 한 글자 길어지고, 리터럴이 하나 줄어든다.
- 허프만 부호 때문에 차이가 비트 단위로 흔들린다. 공격자는 반복 측정으로 잡음을 줄인다.
- 실제 실행 예(예시): 추측 `csrf_token=7`은 120바이트, `csrf_token=0`은 121바이트였다.

### 3. 세 조건과 대처

| 조건 | 끊는 대처 |
|---|---|
| 공격자가 평문 일부를 고른다(반영·교차 사이트 요청) | CSRF 보호로 공격자가 요청을 못 보내게, 입력 반영 제거 |
| 그 입력과 비밀이 같은 압축 사전에 들어간다 | 해당 응답 압축 끄기, 비밀을 다른 응답으로 분리 |
| 공격자가 암호문 길이를 본다 | 완전히 막기 어렵다. 비밀을 요청마다 무작위화·마스킹해 길이 신호를 무의미하게 만든다 |

- 비밀을 마스킹하면 셋째 조건은 남지만, 신호가 가리키는 대상(고정 문자열)이 사라진다.

### 4. CRIME vs BREACH

- **CRIME(2012, Rizzo·Duong)**: TLS 레코드 압축을 노렸다. 비밀은 **요청 헤더의 쿠키**였다. 공격자가 고른 URL 경로와 쿠키가 같이 압축됐다.
- **BREACH(2013, Gluck·Harris·Prado)**: HTTP 응답 본문 압축(gzip/deflate)을 노렸다. 비밀은 **응답 본문의 CSRF 토큰·개인정보**였다.
- TLS 1.3은 TLS 수준 압축을 없앴다(RFC 8446 §1.2, `legacy_compression_methods`는 0만 허용). 그래서 CRIME의 전제가 사라진다.
- BREACH의 압축은 TLS 위, HTTP 층에서 일어난다. TLS는 이미 압축된 바이트를 암호화할 뿐이다. 그래서 TLS 버전·암호군과 상관없다(RFC 7457 §2.6, breachattack.com).

### 5. XOR 마스킹의 효과

- 서버는 세션의 비밀을 그대로 두고, HTML에는 `mask || (secret XOR mask)`를 내보낸다. mask는 응답마다 새로 뽑는다.
- 공격자의 추측은 "이번 응답에 박힌 문자열"과 비교된다. 이 문자열은 다음 응답에서 완전히 바뀐다.
- 한 글자씩 쌓아 가는 적응형 탐색은 여러 응답에 걸친 **같은 문자열**이 필요하다. 그래서 탐색이 수렴하지 않는다.
- Spring Security(`XorCsrfTokenRequestAttributeHandler`, 6.0+ 기본값 — 5.x는 명시 설정 필요)와 Django가 이 방식을 쓴다.

### 6. HPACK의 완화와 한계

- HPACK 동적 테이블은 헤더 값 **전체**가 같을 때만 참조한다. 한 글자씩 맞히는 공격이 "값 전체를 한 번에 맞히는" 무차별 대입으로 바뀐다(RFC 7541 §7.1.1).
- 한계
  - 엔트로피가 낮은 값(짧은 숫자 ID 등)은 전체를 무차별 대입해도 맞힐 수 있다.
  - 서로 믿지 않는 주체가 한 연결의 테이블을 공유하면(여러 클라이언트를 한 연결로 모으는 프록시) 상태를 탐지당할 수 있다.
- 그래서 `Cookie`·`Authorization` 같은 헤더는 never-indexed literal로 보낼 수 있고, 중간자는 그 표현을 인덱싱 표현으로 바꾸면 안 된다(MUST NOT, §7.1.3).

### 7. 패딩 vs 압축 끄기

- **압축 끄기(또는 비밀 분리·마스킹)를 먼저 고른다.**
- 무작위 패딩은 관측 횟수만 늘린다. 반복 측정 평균으로 잡음을 걷어 낼 수 있다.
- RFC 9113 §10.7: 패딩은 공격자가 관측해야 할 프레임 수를 늘릴 뿐이고, 압축 공격 대처로는 압축을 끄거나 제한하는 편이 나을 수 있다고 적는다.
- breachattack.com도 대처 목록에서 "압축 끄기"를 가장 앞에, "길이 숨기기"를 뒤쪽에 둔다.

### 8. TLS 압축 점검

```bash
openssl s_client -comp -connect legacy.example.com:443 -tls1_2 </dev/null 2>/dev/null \
  | grep -E '^(Compression|Expansion)'
```

- `Compression: NONE`이 아니면 TLS 압축이 협상된 것이다.
- `-comp`를 빼면 안 된다. OpenSSL 1.1.0+ 클라이언트는 압축을 기본으로 끄므로 서버가 지원해도 `NONE`이 나온다(거짓 음성). 빌드에 따라 `-comp`로도 압축을 제시하지 못할 수 있으니 [?], testssl.sh 같은 스캐너 결과와 함께 본다.
- 조치
  - 서버 TLS 라이브러리 설정에서 압축을 끈다.
  - 가능하면 TLS 1.3으로 올린다. 1.3에는 압축이 없다.
  - 라이브러리가 너무 오래됐으면 교체가 우선이다.

### 9. 전역 gzip off의 과잉

- 위험한 것은 "비밀 + 사용자 입력 반영"이 같은 본문에 있는 응답뿐이다.
- 정적 JS·CSS·이미지에는 둘 다 없다. 여기까지 압축을 끄면 전송량만 늘어난다.
- 대신 할 일
  - 민감 경로만 압축을 끈다(nginx `location`별 `gzip off`).
  - 근본적으로는 CSRF 토큰을 마스킹하거나 본문에서 분리한다.
  - 앞단 CDN이 다시 압축하지 않는지 확인한다.
