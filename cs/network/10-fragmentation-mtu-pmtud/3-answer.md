# network/10-fragmentation-mtu-pmtud — 정답

## 정답

### 1. MSS와 VXLAN 안쪽 크기

- IPv4: 1500 − 20(IPv4) − 20(TCP) = **1460**
- IPv6: 1500 − 40(IPv6) − 20(TCP) = **1440**
- VXLAN: 바깥 IPv4 20 + UDP 8 + VXLAN 8 + 안쪽 이더넷 14 = 50을 더하므로, 안쪽 IP 패킷은 **1450**까지다. VXLAN 헤더 8바이트는 RFC 7348 §5 기준이고, 50은 헤더 크기를 더해 계산한 값이다.

### 2. 4000바이트 단편화

- 데이터 = 4000 − 20 = 3980바이트.
- 조각당 데이터 ≤ 1500 − 20 = 1480이고, 8의 배수여야 하므로 1480을 쓴다.

```text
조각  데이터   offset(8바이트 단위)   MF
1     1480     0                     1
2     1480     185  (= 1480 / 8)     1
3     1020     370  (= 2960 / 8)     0
```

- 세 조각은 같은 Identification을 가진다(RFC 791).

### 3. 단편화가 나쁜 이유

- **포트가 첫 조각에만 있다.** TCP/UDP 헤더는 첫 조각에만 들어간다.
  - 포트로 거르는 방화벽이 뒤 조각을 제대로 판단하지 못한다.
  - 포트로 해시하는 부하 분산(ECMP)이 조각들을 다른 서버로 보내 재조립이 불가능해진다(Cloudflare).
- **손실 증폭**: 조각 하나만 잃어도 원본 전체를 잃는다. 조각이 빠졌다고 알릴 방법도 없다.
- **메모리 부담·공격 표면**: 재조립 전까지 조각을 붙잡고 있어야 한다. 메모리 고갈 공격에 쓰인다.

### 4. IPv4 vs IPv6 라우터

- IPv4 라우터: DF가 꺼져 있으면 **쪼개서** 보낸다. DF가 켜져 있으면 버리고 ICMP 3/4(다음 홉 MTU 포함)를 보낸다(RFC 791, RFC 1191 §4).
- IPv6 라우터: **쪼개지 않는다.** 단편화는 출발지만 한다(RFC 8200 §4.5). 너무 크면 버리고 ICMPv6 Packet Too Big(type 2)을 보낸다.
- IPv6 최소 링크 MTU는 **1280**이다(RFC 8200 §5).

### 5. PMTUD 과정과 RFC 1191 규칙

```text
보낸 사람 --[1500, DF=1]--> R (다음 링크 1400): 못 보냄
보낸 사람 <--[ICMP 3/4, Next-Hop MTU=1400]-- R
보낸 사람: 이 목적지 PMTU=1400 기억, MSS 축소
보낸 사람 --[1400, DF=1]--> ... --> 받는 사람
```

RFC 1191 호스트 규칙(§3)
- "너무 크다"를 받으면 PMTU 추정치를 줄여야 한다(MUST).
- 68바이트 아래로 줄이면 안 된다(MUST).
- 이 메시지를 근거로 PMTU를 늘리면 안 된다(MUST).
- 늘리는 시도는 줄인 뒤 5분 안에 하면 안 된다(MUST NOT). 10분을 권한다.

### 6. VPN 사용자만 큰 응답 멈춤

- **무슨 일인가: PMTUD 블랙홀**
  - VPN 터널 오버헤드로 경로 MTU가 1500보다 작아졌다.
  - 서버는 DF를 켜고 꽉 찬 세그먼트를 보낸다. 좁은 구간의 라우터는 버리고 ICMP 3/4를 보낸다.
  - 그 ICMP가 방화벽·ACL에 막혀 서버에 오지 않는다. 서버는 같은 크기로만 재전송한다.
  - 로그인·작은 응답은 MTU보다 작아 멀쩡하다.
- **근본 대처**: 경로의 방화벽·보안 그룹·네트워크 ACL에서 ICMP 3/4(IPv6는 type 2)를 허용한다.
- **즉시 우회**
  - VPN 게이트웨이에서 MSS 클램핑(`iptables ... -j TCPMSS --clamp-mss-to-pmtu`)을 건다.
  - 또는 터널 인터페이스 MTU를 낮춘다.
  - 서버에 `tcp_mtu_probing=1`을 둬 블랙홀 감지 시 탐침으로 줄이게 한다.

### 7. TLS가 멈추는 단계

- **서버가 인증서(체인)를 보내는 단계**에서 멈출 가능성이 높다.
- ClientHello는 작아서 통과한다. 서버의 인증서 체인은 수 KB라 꽉 찬 세그먼트 여러 개로 나뉘어 온다. 이것이 MTU 문제에 가장 먼저 걸린다.
- 클라이언트에서는 "ClientHello를 보낸 뒤 서버 응답을 기다리다 타임아웃"으로 보인다. TLS 설정 문제로 오인하기 쉽지만 IP 계층 문제다.

### 8. MSS 클램핑

- 경로 중간 장비가 지나가는 **TCP SYN의 MSS 옵션 값을 줄여서** 다시 쓴다(iptables TCPMSS).
- 양 끝은 그 작은 MSS를 믿고 처음부터 작은 세그먼트만 보낸다. 큰 패킷이 애초에 생기지 않으니 "너무 크다" ICMP가 필요 없다. 그래서 블랙홀을 우회한다.
- UDP에는 MSS 협상이 없다. 바꿀 옵션 자체가 없으므로 통하지 않는다. UDP 앱은 스스로 작은 크기로 보내거나 DPLPMTUD(RFC 8899)를 써야 한다. QUIC는 경로가 1200바이트 UDP 페이로드를 지원하지 않으면 쓰면 안 된다(RFC 9000 §14).

### 9. PLPMTUD/DPLPMTUD와 `tcp_mtu_probing`

- 전통 PMTUD(RFC 1191)는 라우터의 **ICMP "너무 크다"에 기댄다.** ICMP가 막히면 멈춘다.
- PLPMTUD(RFC 4821, TCP 등)와 DPLPMTUD(RFC 8899, UDP·QUIC 등)는 **전송 계층이 직접 크기를 바꿔 탐침을 보내고**, 성공(ACK)과 손실로 경로 MTU를 찾는다. ICMP가 없어도 동작한다.
- 리눅스 `tcp_mtu_probing`(tcp(7))
  - `0`: 끔(기본값)
  - `1`: 평소에는 끄고, ICMP 블랙홀을 감지하면 켠다
  - `2`: 항상 켠다. 초기 MSS는 `tcp_base_mss`다.

### 10. 경로 MTU 측정·블랙홀 확인 명령

```bash
ping -M do -s 1472 -c 3 <대상>        # 1500 바이트, DF 켬. 크기를 줄여 가며 통과 최대치 찾기
tracepath -n <대상>                   # 홉별 pmtu 변화
tcpdump -ni eth0 'icmp[icmptype] == icmp-unreach and icmp[icmpcode] == 4'   # "너무 크다"가 오나
tcpdump -ni eth0 'tcp and host <대상> and greater 1400'                      # 큰 세그먼트 재전송 반복?
ss -ti dst <대상>                     # mss, pmtu, retrans
```

- `ping -M do`가 **에러 없이 무응답**이면, 그 크기에서 "너무 크다" ICMP가 막히고 있다는 신호다.
- 큰 세그먼트의 재전송이 반복되는데 ICMP 3/4가 안 보이고 `mss`도 줄지 않으면 블랙홀이다.
