# network/47-cdn-and-edge — 정답

> 복습 시 이 파일은 **최후에만** 연다.
> ⚠️ 이 정답은 Claude 초안(2026-09-30). 본인 검수 후 이 줄을 `✅ 검수 완료(날짜)`로 바꾼다.

## 정답

### 1. 캐시 계층

```text
  브라우저(private) -> 엣지 PoP(shared, 다수) -> 상위 계층/shield(소수) -> 원점
```

- 상위 계층이 없으면, 엣지마다 미스가 나서 **엣지 수만큼** 원점 요청이 갈 수 있다.
- 상위 계층이 있으면 엣지의 미스가 소수의 상위 캐시로 모인다. 원점에는 상위 계층만 요청한다.
- Cloudflare Tiered Cache는 "상위 계층만 원점에 요청"하게 해 원점 연결도 소수 데이터센터로 모은다. CloudFront Origin Shield는 모든 지역 캐시의 원점 요청을 한 층으로 모은다.

### 2. 캐시 키

- 최소 구성: 요청 메서드 + 대상 URI(RFC 9111 §2). GET만 캐시하는 캐시는 사실상 URI만 쓴다.
- `Vary`: 응답이 지목한 요청 헤더 값이 저장 당시와 모두 일치할 때만 재사용할 수 있다(§4.1). 사실상 그 헤더들을 키에 더한 셈이다.
- 너무 적게 넣으면: 응답을 바꾸는 입력(쿠키·언어)이 키에 없어 **다른 사람의 응답**을 준다.
- 너무 많이 넣으면: 추적 쿼리·쿠키 전체처럼 값이 제각각인 입력 때문에 **히트율이 무너진다**.

### 3. max-age와 s-maxage

- 브라우저(사설 캐시): `max-age=60` → 60초.
- CDN(공유 캐시): `s-maxage=600`이 `max-age`보다 우선 → 600초(RFC 9111 §5.2.2.10).

### 4. Set-Cookie 가정의 위험

- RFC 9111 §7.3: `Set-Cookie`는 캐시를 막지 않는다. 캐시 가능한 응답은 `Set-Cookie`가 있어도 재사용될 수 있다. 막으려면 원점이 `Cache-Control`을 보내라고 권한다.
- Cloudflare 기본 동작과 nginx 프록시 캐시는 `Set-Cookie` 응답을 캐시하지 않는다. 하지만 이것은 **구현 기본값**이다.
- "모든 것을 캐시" 같은 CDN 규칙이나 헤더 무시 설정 하나로 이 기본값이 사라진다. 그러면 로그인 응답이 공유 캐시에 남는다.
- 결론: 개인화 응답은 원점이 `private`/`no-store`로 명시한다.

### 5. 부류별 정책과 배포 순서

| 부류 | 정책(예시) |
|---|---|
| 해시 파일명 정적 자원 | `public, max-age=31536000, immutable` |
| 진입점 HTML | 짧은 TTL 또는 `no-cache`(매번 재검증) |
| 공개 API | `s-maxage=60, stale-while-revalidate=...` |
| 개인화·인증 API | `private` 또는 `no-store` |

- 배포 순서
  1. 새 해시 이름의 정적 자원을 먼저 올린다(새 키라 퍼지 불필요).
  2. HTML을 배포한다.
  3. 필요한 HTML·API만 URL 또는 태그로 퍼지한다. 전체 퍼지는 피한다.

### 6. 요청 병합

- 이름: 요청 병합(request collapsing), single-flight, 캐시 락.
- 예: nginx `proxy_cache_lock on`은 새 캐시 항목에 대해 한 번에 한 요청만 원점에 보낸다. CloudFront Origin Shield도 같은 객체 요청을 합친다.
- 자료구조: 캐시 키 → "진행 중 요청 + 대기자 목록"을 담는 **맵(해시 테이블)**. 첫 요청만 원점에 가고, 뒤 요청은 대기열에서 같은 결과를 받는다.

### 7. 개인화 페이지 교차 노출 진단

- 확인
  - 문제 URL 응답 헤더: `cf-cache-status`/`x-cache` 같은 캐시 상태, `Age`, `Cache-Control`, `Vary`.
  - 쿠키만 바꿔 두 번 요청하고 본문 해시를 비교한다. 같으면 쿠키가 키에 없고 캐시가 응답을 공유하고 있다.
- 즉시 조치
  - 해당 경로를 퍼지한다.
  - CDN 규칙에서 개인화 경로를 캐시 대상에서 뺀다.
- 근본 조치
  - 원점이 개인화 응답에 항상 `Cache-Control: private` 또는 `no-store`를 붙인다.
  - 노출 범위를 로그로 조사한다.

### 8. 전체 퍼지 뒤 원점 5xx

- 원인: 모든 엣지가 동시에 비어, 인기 객체마다 엣지 수만큼 원점 미스가 몰렸다(스탬피드).
- 재발 방지
  1. 전체 퍼지 대신 URL·태그 퍼지. 가능하면 소프트 퍼지로 옛것을 주며 갱신한다.
  2. 요청 병합과 계층 캐시(origin shield)를 켠다.
  3. `stale-while-revalidate`·`stale-if-error`로 원점 부담을 뒤로 미룬다.

### 9. 웹 캐시 속임

- 해석 차이
  - 캐시는 `/account/profile/x.css`를 "확장자가 `.css`인 정적 자원"으로 보고 캐시한다.
  - 원점은 경로 뒤 `x.css`를 무시하고 계정 페이지를 준다.
  - 그 결과 피해자의 계정 페이지가 공격자가 아는 URL로 공유 캐시에 남는다(PortSwigger).
- 막는 방법
  - 동적 응답에 `no-store`/`private`를 붙이고 CDN이 존중하게 한다.
  - 확장자와 `Content-Type`이 어긋나면 캐시하지 않는 CDN 기능을 켠다.
  - 원점이 알 수 없는 경로 접미사를 404로 거절한다.
