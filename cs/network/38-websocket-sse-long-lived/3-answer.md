# network/38-websocket-sse-long-lived — 정답

> 복습 시 이 파일은 **최후에만** 연다.
> ⚠️ 이 정답은 Claude 초안(2026-09-30). 본인 검수 후 이 줄을 `✅ 검수 완료(날짜)`로 바꾼다.

## 정답

### 1. 네 방식의 시간축

```text
  짧은 폴링   req->  <-[]    req->  <-[]    req->  <-[ev]      주기마다 묻는다
  롱폴링      req-------------(보류)---------->  <-[ev]  req---...  응답을 늦게 준다
  SSE         GET ->  <-200 text/event-stream  <-ev1 <-ev2 ...    응답을 끝내지 않는다
  WebSocket   GET Upgrade ->  <-101  <======= 양방향 프레임 =======> 프로토콜을 갈아탄다
```

- 짧은 폴링: 서버는 먼저 말하지 못한다. 클라이언트가 자주 물을 뿐이다.
- 롱폴링: 서버가 요청을 붙잡아 두었다가 이벤트가 생기면 그 요청의 응답으로 말한다.
- SSE: 끝나지 않는 응답 본문에 이벤트를 한 블록씩 흘린다.
- WebSocket: 101 뒤로는 HTTP가 아닌 프레임 프로토콜이라 양쪽 모두 아무 때나 보낸다.

### 2. `Sec-WebSocket-Accept`의 역할

- 서버는 `Sec-WebSocket-Key`에 고정 GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`를 붙여 SHA-1을 구하고 base64로 돌려준다(RFC 6455 §1.3, §4.2.2).
- 클라이언트는 같은 값을 계산해 비교하고, 다르면 연결을 실패시킨다(§4.1).
- 목적은 "상대가 WebSocket을 실제로 이해하는 서버"임을 확인하는 것이다. WebSocket을 모르는 HTTP 서버나 캐시가 낸 응답을 핸드셰이크 성공으로 착각하지 않게 한다.
- 인증이나 암호화 장치가 아니다. 보안은 TLS(`wss://`)와 `Origin` 확인이 맡는다.

### 3. 마스킹 규칙

- 클라이언트→서버 프레임은 **모두 마스킹해야 한다**(MUST, §5.1). TLS 위에서도 마찬가지다.
  - 서버가 마스킹 안 된 프레임을 받으면 연결을 닫아야 한다(MUST). 이때 close 코드 1002를 보낼 수 있다(MAY).
- 서버→클라이언트 프레임은 마스킹하면 안 된다(MUST NOT).
  - 클라이언트가 마스킹된 프레임을 받으면 연결을 닫아야 한다(MUST).
- 이유: 공격 스크립트가 고른 바이트가 선로에 그대로 나가면, WebSocket을 모르는 중간 프록시가 그것을 HTTP 요청으로 오해해 캐시가 오염될 수 있다(§10.3). 매 프레임 무작위 키로 가려서 공격자가 선로 바이트를 고르지 못하게 한다.

### 4. `id:`와 `Last-Event-ID`

- 브라우저는 마지막으로 받은 이벤트의 `id` 값을 기억한다. 다시 붙을 때 `Last-Event-ID: <그 값>` 요청 헤더를 보낸다(WHATWG HTML §9.2.4).
- 이어 보내는 것은 서버 구현이다. 서버가 헤더를 무시하면 둘 중 하나가 된다.
  - 처음부터 다시 보냄 → 클라이언트에 **중복**
  - 현재 시점부터 보냄 → 끊긴 동안의 이벤트 **유실**
- 대처: 서버가 최근 이벤트를 번호 순으로 보관하고 커서 이후를 재전송한다. 클라이언트는 ID로 중복을 거른다.

### 5. close 코드 1006

- 선로에 실려 온 값이 아니다. RFC 6455 §7.4.1은 1006을 close 프레임에 **넣으면 안 된다**(MUST NOT)고 정한다.
- API가 "close 프레임을 주고받지 못하고 연결이 비정상적으로 닫혔다"를 표시하려고 쓰는 로컬 값이다.
- 원인은 알 수 없다. TCP RST, 프록시 idle timeout, 서버 프로세스 강제 종료, 네트워크 단절이 모두 1006이 된다.
- 원인은 서버 로그, 프록시 로그, 끊기는 **주기**(타임아웃 값과 같은지), 패킷 캡처로 좁힌다.

### 6. 조용한 방만 60초마다 끊긴다

- 의심: 경로 위 idle timeout이다. nginx `proxy_read_timeout`과 AWS ALB idle timeout의 기본값이 모두 60초다(각 문서).
- 바쁜 방은 데이터가 계속 흘러 타이머가 리셋되니 멀쩡하다.
- 고치는 두 방향
  1. 가장 짧은 타임아웃보다 짧은 주기로 heartbeat를 보낸다. WebSocket은 ping 프레임이나 앱 메시지, SSE는 주석 줄(`:`)이다. nginx 문서도 상류가 주기적으로 ping을 보내 타임아웃을 리셋하라고 한다.
  2. 경로 위 타임아웃을 늘린다(`proxy_read_timeout`, ALB 속성).
- 어느 쪽이든 "heartbeat 주기 < 경로 위 모든 idle timeout"을 유지한다.

### 7. 배포와 재연결 폭풍

- 한 인스턴스가 연결 수만 개를 동시에 끊는다. 클라이언트가 즉시·고정 간격으로 재연결하면 모두 같은 순간에 돌아온다. 핸드셰이크·인증·초기 데이터 로딩이 한 번에 몰린다.
- RFC 6455 §7.2.3은 이런 동시 재연결이 서비스 거부와 같다고 경고한다.
- 클라이언트
  - 첫 재연결을 무작위로 늦춘다(RFC 예: 0~5초).
  - 실패하면 지수 백오프로 늘리고 지터를 섞는다(SHOULD).
- 서버
  - 연결을 나눠서 드레이닝한다.
  - close 코드 1001(going away)이나 1012(Service Restart)로 의도된 재시작임을 알린다.
  - 인증 결과를 캐시하거나 재연결용 토큰을 두어 재접속 비용을 줄인다.

### 8. SSE가 몰아서 도착한다

- 원인 1: nginx `proxy_buffering`의 기본값이 `on`이다. 상류 응답을 버퍼에 모았다가 보낸다(nginx proxy 모듈 문서).
- 원인 2: 압축 필터(gzip 등)가 압축 블록이 찰 때까지 출력을 미룬다.
- 해결
  - SSE 경로에 `proxy_buffering off;`를 주거나, 앱이 `X-Accel-Buffering: no` 응답 헤더를 보낸다.
  - `text/event-stream`을 압축 대상에서 뺀다.
  - `curl -N`으로 원 서버와 프록시 경유를 비교해 어느 구간이 모으는지 찾는다.

### 9. SSE를 고르는 근거와 제약

- 근거
  1. 평범한 HTTP 응답이라 기존 프록시·인증·로깅을 그대로 쓴다. Upgrade 지원이 필요 없다.
  2. 브라우저가 자동으로 재연결하고, `Last-Event-ID`로 커서를 보내 준다.
  3. 이벤트 형식(`event`·`id`·`data`)과 파서가 표준에 정해져 있어 앱이 프레이밍을 만들 필요가 없다.
- 제약: HTTP/1.1에서 브라우저의 호스트당 동시 연결 한도에 걸린다. MDN은 이 한도를 6으로 적는다. 탭 여러 개가 SSE를 열면 같은 도메인의 다른 요청이 막힌다. HTTP/2에서는 스트림으로 다중화되어 완화된다.
- 덧붙여, SSE 데이터는 UTF-8 텍스트뿐이다. 바이너리는 인코딩해서 보내야 한다.

### 10. 롱폴링 타임아웃

- 길수록 빈 응답과 재요청이 줄어 좋다. 하지만 경로 위 서버·프록시는 그보다 먼저 포기할 수 있다.
  - 서버가 408, 프록시가 504를 돌려주면 클라이언트는 오류로 처리하게 된다(RFC 6202 §5.5).
- RFC 6202 §5.5: 실험상 120초까지 성공했지만 일반적으로 **30초가 더 안전한 값**이다.
- 실무에서는 경로 위 모든 타임아웃보다 짧게 잡고, 타임아웃 시 서버가 빈 200을 정상 응답으로 주어 클라이언트가 곧바로 다시 요청하게 한다.
