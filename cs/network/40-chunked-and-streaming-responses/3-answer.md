# network/40-chunked-and-streaming-responses — 정답

## 정답

### 1. chunked 본문 바이트

```text
  5\r\n
  hello\r\n
  6\r\n
  world!\r\n
  0\r\n
  \r\n
```

- 청크 = 16진 크기, CRLF, 데이터, CRLF다(RFC 9112 §7.1).
- `0\r\n`이 last-chunk다. 트레일러가 없으니 곧바로 빈 줄(`\r\n`)로 메시지가 끝난다.
- 크기가 10 이상이면 16진으로 적는다(예: 26바이트 → `1a`).

### 2. 본문 끝을 정하는 방법

1. `Transfer-Encoding`의 마지막 코딩이 chunked → 0 청크까지 해독한다.
2. `Content-Length: N` → N바이트를 읽는다.
3. (응답에서) 둘 다 없으면 → 서버가 연결을 닫을 때까지 읽는다. 연결을 재사용할 수 없다.

(RFC 9112 §6.3)

- 둘 다 오면 Transfer-Encoding이 Content-Length보다 우선한다.
- 위험: 경로 위 장비 중 하나라도 Content-Length를 기준으로 읽으면, 두 장비가 본문 끝을 다르게 본다. 그 차이에 숨긴 바이트가 다음 요청으로 해석되는 **요청 스머글링**이 된다.
- 그래서 RFC는 이런 메시지를 오류로 다루라고 하고(ought to), 전달하는 중계자는 Content-Length를 먼저 지우라고 한다(MUST).

### 3. HTTP/2와 chunked

- HTTP/2는 모든 데이터를 **길이 필드가 있는 프레임**에 싣는다. 이미 프레이밍이 있으니 chunked가 필요 없다.
- `Transfer-Encoding`은 연결 전용 헤더라 HTTP/2 메시지에 넣으면 잘못된 메시지가 된다(RFC 9113 §8.2.2).
- 본문의 끝: 마지막 DATA 프레임(또는 트레일러 HEADERS)의 `END_STREAM` 플래그(§8.1).
- 도중 실패: `RST_STREAM` 프레임(예: `INTERNAL_ERROR`)으로 그 스트림만 즉시 끝낸다(§6.4). 같은 연결의 다른 스트림은 영향이 없다.

### 4. 헤더를 보낸 뒤의 DB 타임아웃

- (a) 예외를 삼키고 정상 종료
  - HTTP/1.1이면 0 청크가 나가 **완전한 응답**으로 보인다. HTTP/2면 END_STREAM이 나간다.
  - 클라이언트는 30%짜리 파일을 성공으로 저장한다. 상태 코드 200, 오류 로그 없음. **조용한 데이터 손상**이다.
- (b) 비정상 종료
  - HTTP/1.1: 0 청크 없이 연결이 끊긴다. 클라이언트는 불완전 메시지로 기록해야 한다(MUST, RFC 9112 §8). curl은 `(18)`, 브라우저 `fetch`의 스트림 읽기는 오류를 낸다.
  - HTTP/2: RST_STREAM을 받아 그 스트림이 오류로 끝난다. curl은 `(92)` 계열 오류다.
  - 상태 코드는 여전히 200이지만, 적어도 "실패했다"는 사실은 전달된다.

### 5. 스트리밍 오류 계약

- **시작 전(헤더를 보내기 전)**: 상태 코드가 자유롭다.
  - 권한 없음 403, 입력 오류 422, 자원 포화 503(+`Retry-After`)을 JSON 오류 봉투로 답한다.
  - 판정 가능한 검사는 모두 첫 바이트 전에 끝낸다.
- **시작 후**: 상태 코드는 잠겼다.
  - 비정상 종료(HTTP/1.1 연결 끊기, HTTP/2 RST_STREAM)로 전송 층에 실패를 알린다.
  - 본문 규약에 "정상 끝" 표식을 둔다. 예: 마지막 줄 `{"done":true,"rows":1234}`. 클라이언트는 표식이 없으면 실패로 처리한다.
  - 가능하면 트레일러(gRPC의 `grpc-status`)를 쓴다. 단, 중계자가 트레일러를 버릴 수 있다(RFC 9110 §6.5.1).
- 서버 로그에는 "상태 코드"와 별도로 "완결 여부·보낸 바이트"를 남긴다.

### 6. nginx를 거치면 몰려서 온다

- 원인: nginx `proxy_buffering` 기본값이 `on`이다. 상류 응답을 버퍼(넘치면 임시 파일)에 받아 두었다가 보낸다(nginx proxy 모듈 문서). 압축(gzip)을 켰다면 압축기도 모은다.
- 해결
  1. 해당 location에 `proxy_buffering off;`를 준다.
  2. 앱이 응답 헤더 `X-Accel-Buffering: no`를 보낸다. 응답별로 끌 수 있다.
- 덧붙여 스트림 응답은 압축에서 빼거나 이벤트마다 flush한다.

### 7. `write()` 반환값 무시

- Node: 내부 버퍼가 highWaterMark를 넘으면 `write()`가 `false`를 돌려준다. 무시하고 계속 쓰면 Node가 청크를 **메모리에 계속 쌓는다**. 상대가 읽지 않으면 영원히 비워지지 않을 수 있다. 메모리 폭증, GC 악화, 최종적으로 프로세스 중단까지 간다(Node `stream` 문서). 해결은 `'drain'`을 기다리거나 `pipeline`을 쓰는 것이다.
- 블로킹 서블릿: 커널 송신 버퍼가 차면 `write()`가 **막힌다**. 생산이 자동으로 멈추니 메모리는 안 쌓인다. 대신 그 요청의 스레드가 묶인다. 느린 클라이언트가 많으면 스레드 풀이 고갈된다.

### 8. HTTP/2 창 vs TCP 창

- 같은 점: 둘 다 **수신자가 정하는 신용**이다. 송신자는 수신자가 허락한 바이트까지만 보낸다.
- 다른 점
  - TCP 창은 연결(바이트 스트림) 하나에 하나다.
  - HTTP/2 창은 **스트림별** 창과 **연결 전체** 창이 따로 있다. 느린 스트림 하나가 연결 전체를 막지 않게 한다.
  - HTTP/2 창은 DATA 프레임에만 적용된다. 제어 프레임은 막히지 않는다(RFC 9113 §5.2.1).
  - HTTP/2 흐름 제어는 한 홉 사이에서만 동작한다.
- 초기 창: 스트림·연결 모두 65,535바이트다(§6.9.2). 스트림 초기 창은 `SETTINGS_INITIAL_WINDOW_SIZE`로 바꾸고, 연결 창은 WINDOW_UPDATE로만 늘린다.

### 9. 청크 경계를 이벤트 경계로 쓰기

- 쓰면 안 된다.
- chunked는 홉마다 적용되는 전송 코딩이다. 프록시·로드밸런서가 풀었다가 다른 크기로 다시 짤 수 있다(RFC 9112 §7.1.1도 중계자가 청크를 다시 만든다고 적는다).
- HTTP/2로 바뀌면 청크 자체가 없어지고 DATA 프레임 경계로 바뀐다. 프레임 경계도 보장되지 않는다.
- 브라우저 `fetch`의 `read()`가 돌려주는 조각도 네트워크 도착 단위일 뿐이다.
- 이벤트 경계는 본문 안의 규약으로 만든다. 예: NDJSON의 줄바꿈, SSE의 빈 줄, 길이 접두 메시지.

### 10. curl `(18)`의 의미

- 알려 주는 것: 응답이 **본문 끝 표시 전에** 끊겼다. chunked면 0 청크를 못 받았고, Content-Length면 약속한 바이트보다 적게 받았다(`CURLE_PARTIAL_FILE`).
- 알려 주지 않는 것: **왜** 끊겼는지다. 서버가 도중 예외로 의도적으로 끊었는지, 프록시 타임아웃인지, 네트워크 단절인지 구분하지 못한다.
- 다음 단계: 서버 로그의 스트리밍 중 예외, 프록시의 타임아웃 로그(`send_timeout`·`proxy_read_timeout`), 끊긴 시점까지 걸린 시간이 타임아웃 값과 같은지 본다.
