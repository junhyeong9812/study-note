## 정답

### 1. 남은 문제 세 가지와 QUIC의 해법

- TCP head-of-line blocking
  - HTTP/2는 모든 스트림이 TCP 바이트 스트림 하나를 공유한다. 세그먼트 하나 손실이 그 뒤 데이터를 기다리는 모든 스트림을 멈춘다.
  - QUIC은 스트림마다 따로 순서를 지킨다(RFC 9000 §2.2). 손실은 그 데이터를 담은 스트림만 멈춘다.
- 연결 준비 비용
  - TCP 핸드셰이크 1 RTT + TLS 1.3 1 RTT가 요청 전에 든다.
  - QUIC은 전송·암호 핸드셰이크를 합쳐 1 RTT, 재개 시 0-RTT다(RFC 9000 §7).
- 주소에 묶인 연결
  - TCP 연결은 4-튜플로 식별되어 IP가 바뀌면 끊긴다.
  - QUIC은 연결 ID로 식별하고, 주소가 바뀌면 경로 검증 뒤 이어 간다(§5.1, §9).
- UDP 위에 새로 만든 이유
  - TCP는 OS 커널에 구현돼 있어 바꾸면 전 세계 OS가 업데이트돼야 한다.
  - 중간 장비가 TCP 헤더를 해석·수정해, 새 TCP 기능이 막히는 일이 흔하다.
  - UDP는 기존 중간 장비(NAT 포함)를 고치지 않고도 통과하고, 사용자 공간에서 구현할 수 있다(RFC 9308 §2).

### 2. 손실 시 스트림 동작

```text
  HTTP/2 over TCP
  세그먼트: #10[s1] #11[s3] #12[s5] #13[s1]      #11 손실
  커널: #12, #13 도착했지만 #11이 비어 앱에 전달 불가
  결과: s1, s3, s5 모두 재전송까지 대기

  HTTP/3 over QUIC
  패킷:     P10[s0]  P11[s4]  P12[s8]  P13[s0]   P11 손실
  QUIC:  s0 -> P10, P13 전달 / s4 -> 대기 / s8 -> P12 전달
  결과: s4만 재전송까지 대기
```

- QUIC도 **같은 스트림 안**에서는 순서를 지킨다. 그래서 손실된 조각이 속한 스트림은 기다린다.

### 3. 첫 요청까지의 왕복 수

- TCP + TLS 1.3: TCP 1 RTT + TLS 1 RTT = 요청 전송까지 2 RTT.
- QUIC(HTTP/3): 결합 핸드셰이크 1 RTT 뒤 요청을 보낸다.
- 재개 연결
  - TCP + TLS 1.3 0-RTT: TCP 1 RTT 뒤 ClientHello와 함께 요청을 보낸다. 1 RTT.
  - QUIC 0-RTT: 첫 비행(Initial + 0-RTT 패킷)에 요청을 싣는다. 0 RTT(RFC 9000 Figure 6).
- 0-RTT는 재전송 공격 위험이 있어 안전 요청에만 쓴다.

### 4. 첫 방문과 HTTP/3 발견

- 대개는 바로 못 한다.
  - `https` URI만으로는 서버가 HTTP/3를 지원하는지 알 수 없다.
  - 보통 첫 접속은 TCP(HTTP/1.1이나 h2)로 하고, 응답의 `Alt-Svc: h3=":443"`을 보고 다음부터 QUIC을 시도한다(RFC 9114 §3.1.1).
- 알리는 방법
  - `Alt-Svc` 응답 헤더 또는 HTTP/2 `ALTSVC` 프레임(RFC 9114 §3.1.1). `ma` 생략 시 24시간 유효(RFC 7838).
  - DNS HTTPS 레코드(RFC 9460). 첫 접속 전에 DNS 조회로 `h3` 지원을 알 수 있다.
- RFC 9114 §3.1은 클라이언트가 주소로 바로 QUIC 연결을 시도하는 것도 허용한다(MAY). 실패하면 TCP로 되돌아가야 한다(SHOULD).

### 5. Wi-Fi → LTE 전환

- TCP: 출발 IP가 바뀌어 4-튜플이 달라진다. 서버는 새 주소의 세그먼트를 모르는 연결로 본다. 연결이 끊기고 앱은 새 연결(핸드셰이크 포함)을 맺어야 한다.
- QUIC: 패킷의 연결 ID로 같은 연결을 찾는다. 연결이 유지된다(RFC 9000 §9).
- 서버가 하는 일
  - 주소 변경을 감지하면 경로 검증을 해야 한다(MUST, 전에 검증한 주소면 예외). 새 주소로 PATH_CHALLENGE(무작위 값)를 보내고, 같은 값의 PATH_RESPONSE를 받아야 그 경로를 쓴다(§8.2).
  - 검증 전에도 새 주소로 보낼 수는 있지만(MAY), 주소 위조 공격에 대비해야 한다(MUST, §9.3). 보내는 양을 제한하는 것이 그 방법이다(§9.3.1).
- 조건
  - 클라이언트만 주소를 옮긴다(서버 주소 변경은 `preferred_address` 경로뿐, §9.6). 핸드셰이크 확정 전에는 옮길 수 없다(§9).
  - 서버가 `disable_active_migration`을 보냈으면, 클라이언트는 다른 로컬 주소에서 핸드셰이크 때의 서버 주소로 보내면 안 된다(MUST NOT, 탐침 포함). 서버의 `preferred_address`로 옮긴 뒤라면 예외다(§9).
  - 클라이언트가 이를 어기고 새 주소에서 보내면, 서버는 Stateless Reset 없이 버리거나 경로 검증 뒤 받아들인다(MUST, §9). NAT rebinding 같은 의도치 않은 주소 변경은 이 파라미터로 막을 수 없다.
  - 관찰자가 연결을 추적하지 못하게, 새 경로에서는 다른 연결 ID를 쓴다.

### 6. 새 패킷 번호와 번호 공간

- TCP의 재전송 모호성
  - TCP는 재전송 때 같은 시퀀스 번호를 쓴다. ACK가 오면 원본에 대한 것인지 재전송본에 대한 것인지 모른다.
  - 그래서 RTT 표본이 틀리고, 불필요한 재전송을 알아채기 어렵다.
- QUIC은 잃은 프레임을 **새 패킷 번호**의 새 패킷에 싣는다. 패킷 번호 = 전송 순서라서 ACK가 가리키는 패킷이 명확하다(RFC 9002 §4.2).
  - 전달 순서는 STREAM 프레임의 오프셋이 따로 맡는다.
- 번호 공간이 셋(Initial, Handshake, Application)인 이유
  - 암호화 수준마다 다른 키를 쓴다. 한 수준의 ACK가 다른 수준 패킷의 가짜 손실 판정·재전송을 일으키지 않게 분리한다(RFC 9002 §4.1).
  - 0-RTT와 1-RTT는 같은 Application 공간을 쓴다.

### 7. 회사망에서 첫 로딩 지연

- 의심: 그 망이 UDP 또는 UDP 443을 막는다. 클라이언트가 QUIC을 시도하다가 실패를 판단한 뒤 TCP로 폴백한다. 그 대기 시간만큼 늦다.
  - RFC 9308 §2가 인용하는 측정에서 3~5%의 네트워크가 UDP를 전부 막았다.
- 확인 명령

```bash
curl -sI --http3-only https://site/ -o /dev/null -w '%{http_version}\n'   # 타임아웃이면 UDP 경로 문제
curl -sI --http3      https://site/ -o /dev/null -w '%{http_version}\n'   # 2 또는 1.1로 성공(폴백)
tcpdump -nn -i any 'udp port 443'    # Initial만 나가고 응답이 없는지
```

- 대처: 서버는 TCP 경로를 항상 제공한다. 클라이언트는 QUIC·TCP를 경주시킨다. 필요하면 `Alt-Svc`의 `ma`를 줄이거나 `clear`로 광고를 거둔다.

### 8. idle 뒤 첫 요청이 멈춤

- 방화벽·NAT
  - QUIC은 암호화돼 있어 중간 장비가 연결 시작·끝을 볼 수 없다. 장비는 타이머로 UDP 흐름 상태를 지운다(RFC 9312 §4.2).
  - 실제로 30~60초 타임아웃을 겪는다. 상태가 지워지면 클라이언트 패킷이나 서버 응답이 버려진다.
- NAT rebinding + 로드밸런서
  - NAT가 새 외부 포트를 주면 서버는 연결 ID로 같은 연결임을 안다.
  - 하지만 L4 LB가 4-튜플 해시로 서버를 고르면 패킷이 다른 서버로 간다. 그 서버는 이 연결을 모른다.
- 대처
  - 응답을 기다리는 동안에만 PING으로 유지하고, 오래 쉰 뒤에는 재개(0-RTT 포함)로 새로 연결한다(RFC 9308 §3.2).
  - 방화벽 UDP 상태 타임아웃을 QUIC에 대해 2분 이상으로 둔다(RFC 9312 권고).
  - LB는 연결 ID 기반 라우팅을 쓰거나, 못 쓰면 `disable_active_migration`을 광고한다(RFC 9000 §5.2.3).

### 9. HTTP/3 0-RTT의 필수 조치

- HTTP/3에서 0-RTT를 쓰면 RFC 8470의 재전송 대책을 적용해야 한다(MUST, RFC 9114 §10.9).
  - 서버·중간자는 재전송이 위험한 요청을 `425 Too Early`로 거절한다.
  - 중간자는 `Early-Data: 1`로 원 서버에 early data임을 알린다.
- QUIC 프레임 vs 앱 요청
  - QUIC 프레임 처리는 멱등하다. 프레임이 재전송·재정렬·손실돼도 잘못된 연결 상태를 만들지 않는다(RFC 9001 §9.2).
  - 하지만 그 안에 실린 **앱 요청**(예: 송금 POST)은 두 번 처리될 수 있다. 위험은 앱 프로토콜 쪽에 있다.
- 결론: 0-RTT에는 안전·멱등 요청만 허용하고, 쓰기 API는 멱등 키로 방어한다.

### 10. 증폭 제한과 1,200바이트

- 서버는 클라이언트 주소를 검증하기 전에는 받은 바이트의 **3배**까지만 보낸다(MUST, RFC 9000 §8.1).
  - 출발 주소를 위조한 작은 요청으로 큰 응답을 남에게 쏘는 증폭 공격을 막는다.
- 클라이언트 Initial 데이터그램을 1,200바이트 이상으로 채우는 이유(§14.1)
  - 경로가 최소 크기를 양방향으로 나를 수 있는지 처음부터 확인한다.
  - 클라이언트가 크게 보내면 서버의 3배 허용량도 커진다. 서버가 인증서 같은 큰 첫 응답을 한 번에 보낼 수 있다.
- 작은 MTU 경로
  - 경로가 1,200바이트 UDP 페이로드를 못 나르면 QUIC을 쓰면 안 된다(MUST NOT, §14).
  - UDP 데이터그램은 IP 단편화도 금지다(MUST NOT). 그래서 Initial이 버려져 핸드셰이크가 실패한다.
  - 클라이언트는 TCP로 폴백한다. 터널·VPN의 MTU를 점검한다(10번).
