# network/42-large-file-upload-patterns — 정답

> 복습 시 이 파일은 **최후에만** 연다.
> ⚠️ 이 정답은 Claude 초안(2026-09-30). 본인 검수 후 이 줄을 `✅ 검수 완료(날짜)`로 바꾼다.

## 정답

### 1. 단일 요청 5GB가 깨지는 지점

```text
  브라우저 --> LB --> nginx --> 앱 서버 --> 스토리지
  (1)         (2)     (3)        (4)
```

1. 브라우저·네트워크: 전송 중 끊기면 처음부터 다시 보낸다. 서버에 남는 상태가 없다.
2. LB: idle timeout(AWS ALB 기본 60초)이나 요청 시간 한도에 걸려 연결이 끊긴다. 클라이언트는 연결 리셋이나 502·504를 본다.
3. nginx
   - `client_max_body_size`(기본 1m)를 넘으면 `413`이다.
   - `proxy_request_buffering on`(기본)이면 5GB를 nginx가 먼저 다 받아 디스크에 쓴 뒤 상류로 보낸다.
   - `client_body_timeout`(두 번의 읽기 사이 60초)을 넘으면 408이다.
4. 앱 서버
   - Spring Boot `max-file-size` 1MB / `max-request-size` 10MB를 넘으면 `MaxUploadSizeExceededException`이다.
   - 파일을 힙에 통째로 올리면 OOM이다.

### 2. multipart 파일 부분의 필수 헤더와 `filename`

- 필수: `Content-Disposition: form-data; name="필드명"`(MUST, RFC 7578 §4.2). 파일이면 `filename`도 주는 것이 권장이다(SHOULD).
- 부분 `Content-Type`은 선택이다. 없으면 `text/plain`이다. 파일은 알맞은 타입이나 `application/octet-stream`을 붙인다(SHOULD, §4.4).
- `filename`을 그대로 쓰면 안 되는 이유
  - 공격자가 `../../app/config.yml` 같은 경로를 넣어 서버 파일을 덮어쓸 수 있다.
  - RFC 7578은 파일 이름을 맹목적으로 쓰지 말고, 로컬 규칙에 맞게 바꾸고, 경로 정보를 쓰지 말라고 한다(§4.2, §7).
  - 저장 키는 서버가 만든 ID(UUID 등)로 하고, 원래 이름은 표시용 메타데이터로만 둔다.

### 3. tus로 70바이트에서 끊긴 뒤 완료

```text
  POST /files   Upload-Length: 100, Tus-Resumable: 1.0.0
       <- 201 Created, Location: /files/abc
  PATCH /files/abc   Upload-Offset: 0, Content-Type: application/offset+octet-stream
       (70바이트 보낸 뒤 연결 끊김 — 서버는 받은 70바이트를 저장)
  HEAD /files/abc
       <- 200 OK, Upload-Offset: 70, Upload-Length: 100, Cache-Control: no-store
  PATCH /files/abc   Upload-Offset: 70   (남은 30바이트)
       <- 204 No Content, Upload-Offset: 100   -> 완료
```

- 서버는 끊긴 요청에서도 받은 데이터를 최대한 저장해야 한다(SHOULD). 그래서 HEAD가 70을 돌려준다.
- 모든 요청·응답에 `Tus-Resumable: 1.0.0`이 붙는다(OPTIONS 제외).

### 4. 오프셋 불일치와 체크섬 불일치

- 오프셋 불일치: `Upload-Offset`은 서버의 현재 오프셋과 같아야 한다. 다르면 서버는 업로드를 건드리지 않고 `409 Conflict`로 답해야 한다(MUST). 클라이언트는 `HEAD`로 현재 오프셋을 다시 묻는다.
- 체크섬 불일치(checksum 확장): 서버는 `460 Checksum Mismatch`로 답할 수 있다. 그 조각은 폐기되고 오프셋은 바뀌지 않는다(MUST). 알고리즘을 모르면 `400`이다.

### 5. S3 멀티파트로 60GB

- 파트 크기 하한은 두 가지가 정한다(S3 한도 문서).
  - 파트 최소 5 MiB(마지막 파트 제외).
  - 파트 수 최대 10,000. 그래서 파트 크기 ≥ 60GB / 10,000 ≈ 6MB다. 둘 중 큰 값(여유를 두어 예: 16 MiB (예시))을 쓴다.
- Complete 요청: UploadId와 **파트 번호·ETag 쌍의 목록**이다. S3는 파트 번호 오름차순으로 이어 붙인다.
- 목록은 **클라이언트가 각 UploadPart 응답의 ETag를 직접 기록**해서 만든다. S3 문서는 파트 목록 조회(ListParts) 결과를 Complete에 쓰지 말라고 경고한다.

### 6. 요금은 큰데 객체는 작다

- 확인: `aws s3api list-multipart-uploads`로 미완료 멀티파트 업로드를 본다. 객체 목록에는 안 보인다.
- 원인: 완료·중단하지 않은 업로드의 조각은 계속 저장되고 과금된다(S3 문서). 수명 주기 규칙이 없으면 알아서 정리되지 않는다.
- 막는 법
  - 버킷에 `AbortIncompleteMultipartUpload` 수명 주기 규칙을 둔다(S3 문서 권장).
  - 앱이 업로드 세션(UploadId·시작 시각)을 기록하고, 만료된 세션을 `AbortMultipartUpload`로 정리한다.
  - 클라이언트가 포기할 때 Abort를 호출하게 한다.

### 7. presigned URL의 이득과 위험

- 사라지는 문제
  - 앱 서버가 파일 바이트를 받지 않으니 대역폭·메모리(OOM)·요청 시간 한도·413 문제가 앱 경로에서 사라진다.
  - 스토리지의 멀티파트·병렬 업로드를 직접 쓸 수 있다.
- 위험
  - URL은 가진 사람 누구나 쓸 수 있는 bearer 토큰이다. 만료까지 여러 번 쓸 수 있다(S3 문서).
  - 새면 누군가 그 키에 다른 파일을 올리거나 덮어쓸 수 있다. 같은 키가 있으면 기존 객체가 교체된다.
- 만료 규칙(S3 문서)
  - SigV4 + IAM 사용자 자격 증명으로 최대 7일이다.
  - 임시 자격 증명으로 만들면 그 자격 증명이 만료될 때 함께 만료된다.
  - 만료는 요청 시작 시점에 검사한다. 끊긴 뒤 만료 후 재시도는 실패한다.
- 대처: 짧은 만료, 서버가 정한 키, 업로드 후 서버가 크기·체크섬을 확인한 뒤에만 "완료" 처리.

### 8. 조용한 손상

- 가능한 원인
  - 조각 하나가 전송 중 손상됐다. TCP 16비트 체크섬은 모든 손상을 잡지 못하고, 앱·디스크 단계 손상은 못 본다.
  - 같은 번호 조각이 재시도로 두 번 올라가 다른 내용으로 덮어써졌다.
  - 조립 순서가 틀렸다.
- 검증
  - 조각 단위: 조각마다 체크섬을 보내고 받는 쪽이 검사한다. tus `Upload-Checksum`(불일치 460), S3 `x-amz-checksum-*`.
  - 전체 단위: 클라이언트가 전체 해시를 계산해 보내고, 조립 후 서버가 비교한다. S3는 전체 객체 체크섬 불일치 시 `BadDigest`로 실패시킨다.
  - "업로드 완료" 상태는 체크섬 일치를 확인한 뒤에만 기록한다.
- S3 멀티파트의 최종 ETag는 MD5가 아닐 수 있으니 무결성 검증에 쓰지 않는다.

### 9. 비트맵과 머클 트리

- 수신 청크 비트맵: 병렬·순서 무관 업로드에서 "어느 조각을 받았나"를 기록한다. 비트 i = 조각 i 수신이다. 전부 1이면 조립하고, 0인 비트가 재전송 목록이다.
- 머클 트리: 조각 해시들을 다시 해시해 루트 하나로 묶는다.
  - 루트 하나로 전체를 검증한다.
  - 루트가 다르면 트리를 내려가며 어느 조각이 틀렸는지 찾는다. 틀린 조각만 다시 받는다.
  - S3의 composite 체크섬("checksum of checksums")이 한 단계짜리 예다.
- 순차 업로드(tus 코어)는 항상 앞에서부터 빈틈없이 채운다. 그래서 "여기까지 받았다"는 **오프셋 정수 하나**로 상태가 충분하다. 구멍이 생길 수 없다. 병렬 조각이 필요할 때 tus는 concatenation 확장으로 조각을 따로 올린 뒤 합친다.

### 10. `sendfile(2)`

- 없애는 것: 파일 데이터를 **사용자 공간 버퍼로 복사했다가 다시 커널 소켓 버퍼로 복사하는** 왕복이다. 커널 안에서 파일 디스크립터 사이로 바로 옮긴다(man 2 sendfile).
- 한 번에 다 간다고 가정하면 안 되는 이유
  - 한 호출은 최대 0x7ffff000(2,147,479,552)바이트까지만 보낸다(32·64비트 모두). 실제로 보낸 바이트 수를 돌려준다.
  - 논블로킹 소켓이면 버퍼가 찬 만큼만 보내고 돌아온다.
  - 그래서 반환값으로 오프셋을 옮기며 반복해야 한다. Java `FileChannel.transferTo`도 반환값을 보고 반복한다.
- 파일 → 소켓(다운로드) 경로에 쓰는 기술이다. 입력은 mmap 가능한 파일이어야 하고 소켓일 수 없다(예외: Linux 5.12+에서 출력이 파이프면 `splice(2)` 규칙).
