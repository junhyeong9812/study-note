## 질문

1. (그림) 5GB 파일을 POST 한 번으로 올릴 때 경로(브라우저→LB→nginx→앱→스토리지) 위에서 깨질 수 있는 지점을 그리고, 각 지점의 한도·증상을 적어라.
2. (경계) multipart/form-data 요청에서 파일 부분에 반드시 있어야 하는 헤더는 무엇인가? 서버가 `filename`을 그대로 저장 경로에 쓰면 왜 안 되나?
3. (그림) tus로 100바이트 업로드가 70바이트에서 끊긴 뒤 완료되기까지의 요청·응답을 순서대로 그려라.
4. (예측) tus 서버의 현재 오프셋이 70인데 클라이언트가 `Upload-Offset: 50`으로 PATCH했다. 서버의 응답은? 체크섬이 틀린 조각을 보냈다면?
5. (적용) S3 멀티파트 업로드로 60GB 파일을 올린다. 파트 크기의 하한은 무엇이 정하나? Complete 요청에는 무엇이 들어가고, 그 목록은 어디서 얻어야 하나?
6. (장애 진단) 버킷의 객체 총량은 작은데 스토리지 요금이 크다. 무엇을 확인하고 어떻게 막나?
7. (왜) presigned URL로 클라이언트가 스토리지에 직접 올리게 하면 앱 서버의 어떤 문제가 사라지나? 대신 생기는 위험과 만료 규칙은?
8. (장애 진단) 업로드는 성공으로 기록됐는데 가끔 파일이 중간부터 깨진다. 가능한 원인과, 조각·전체 단위에서 넣을 검증은?
9. (연결) 수신 청크 비트맵과 머클 트리는 이 주제에서 각각 무엇을 해결하나? 순차 업로드(tus 코어)에는 왜 비트맵이 필요 없나?
10. (연결) `sendfile(2)`는 무엇의 복사를 없애나? 한 번의 호출로 파일 전체가 간다고 가정하면 안 되는 이유는?
