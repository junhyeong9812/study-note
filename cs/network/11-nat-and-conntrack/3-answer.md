## 정답

### 1. NAT가 기억해야 하는 것

- 나갈 때 출발지를 공인 주소·포트로 바꾸는 것은 한쪽 방향일 뿐이다.
- 응답은 공인 주소·포트로 돌아온다. NAT는 이것이 **원래 어느 내부 주소·포트**의 것인지 알아야 되돌릴 수 있다.
- 그래서 연결마다 (원래 튜플 ↔ 변환된 튜플) 짝을 conntrack 표에 기억한다.
- 기억이 없으면 응답을 누구에게 줄지 모른다. 응답은 버려지거나 RST를 받는다.

### 2. SNAT vs DNAT

| | 바꾸는 필드 | 쓰이는 곳 |
|---|---|---|
| SNAT | 출발지 IP(와 포트) | 사설 서브넷 → NAT 게이트웨이 → 인터넷, 컨테이너의 masquerade |
| DNAT | 목적지 IP(와 포트) | 공인 주소:80으로 들어온 요청을 내부 서버:8080으로 보내기, 서비스 VIP → 백엔드 |

- 리눅스 iptables에서 SNAT는 nat 테이블 POSTROUTING(과 INPUT), DNAT는 PREROUTING·OUTPUT 체인에서 쓴다(iptables-extensions(8)).

### 3. 튜플이 두 개인 이유

- 한 연결의 패킷은 두 방향으로 온다. 나가는 패킷과 돌아오는 패킷의 5-튜플은 서로 다르다. NAT 뒤에는 주소까지 다르다.
- 그래서 original 튜플(보낸 방향)과 reply 튜플(돌아올 방향)을 둘 다 해시 테이블에 건다. 어느 방향 패킷이 와도 한 번에 항목을 찾는다(`tuplehash[IP_CT_DIR_MAX]`).
- 응답은 reply 튜플(`93.184.216.34:443 → 203.0.113.7:61001`)로 찾는다. 그리고 목적지를 original의 출발지(`10.0.0.5:40000`)로 되돌린다.

### 4. 같은 목적지로 동시 연결을 늘리면

- 리눅스 SNAT·AWS NAT GW처럼 목적지별로 포트를 재사용하는 NAT에서는 응답을 구분하는 키가 (공인 IP, 공인 포트, 목적지 IP, 목적지 포트, 프로토콜)이다.
- 목적지가 같으면 구분할 수 있는 값이 공인 포트뿐이다. 공인 포트가 떨어지면 새 연결을 만들 수 없다(**SNAT 포트 고갈**).
- 목적지가 다르면 같은 공인 포트를 다시 써도 키가 달라진다. 그래서 영향이 적다.
- 단, RFC가 요구하는 EIM NAT(RFC 4787·5382 REQ-1)에서는 공인 포트 하나가 내부 끝점 하나에만 묶인다. 그러면 목적지와 무관하게 전체 매핑 수가 공인 포트 수에 막힌다.
- AWS NAT GW는 IP당 고유 목적지마다 55,000 동시 연결을 지원하고, 넘으면 `ErrorPortAllocation`이 오른다.

### 5. RFC 최솟값과 실제 장비

- RFC 5382 REQ-5는 NAT 구현이 **지켜야 할 요구**다. 실제 장비와 클라우드 서비스가 그 요구를 따른다는 보장은 없다.
- AWS NAT 게이트웨이는 350초 idle이면 연결을 타임아웃시킨다(AWS 문서). RFC 최솟값보다 훨씬 짧다.
- 장비마다 값이 다르다. 그래서 연결 수명은 **경로에 있는 장비 중 가장 짧은 idle timeout**이 정한다.
- 결론: 경로의 실제 값을 확인하고, keepalive나 풀 idle 수명을 그 값보다 짧게 맞춘다.

### 6. 쉬고 난 첫 요청만 reset

- **가설**: 풀의 연결이 NAT idle timeout(예: AWS 350초)보다 오래 놀았다. NAT가 매핑을 지웠고, 그 연결에 쓰자 RST가 돌아왔다(AWS는 FIN이 아니라 RST를 돌려준다고 명시).
- **확인**
  - tcpdump로 요청 직후 RST가 오는지 본다.
  - AWS면 `IdleTimeoutCount` 지표가 오르는지 본다.
  - 실패가 idle 시간 350초 전후로 갈리는지 본다.
- **대처**
  - TCP keepalive를 NAT timeout보다 짧게 켠다(Java `TCP_KEEPIDLE`, Node `setKeepAlive(true, ms)`).
  - 또는 풀의 idle 연결 최대 수명을 NAT timeout보다 짧게 둔다.
  - 멱등 요청은 1회 재시도한다.

### 7. 새 연결만 실패 — conntrack 표 가득

- 커널 로그: `nf_conntrack: table full, dropping packet`.
- 확인
  - `sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max`로 count가 max에 붙어 있는지 본다.
  - `conntrack -S`의 `drop`이 오르는지 본다.
- 조정
  - `nf_conntrack_max`와 `nf_conntrack_buckets`를 함께 올린다.
  - 불필요하게 긴 상태 타임아웃을 줄인다(established 기본 432000초 = 5일).
  - 추적이 필요 없는 트래픽은 raw 테이블에서 `CT --notrack`으로 뺀다.
  - 연결을 재사용해 항목 수 자체를 줄인다.
- 기존 연결은 이미 항목이 있으므로 영향이 없다. 새 항목이 필요한 첫 패킷만 드롭된다.

### 8. conntrack 표의 자료구조

- 튜플을 키로 하는 **해시 테이블**이다. 항목마다 만료 **타이머**가 붙는다.
- `max`는 항목 수 상한이고, 버킷 수는 해시 테이블 크기다. 기본값은 max = 버킷 수다.
- max만 올리면 버킷당 평균 항목 수(로드 팩터)가 커진다. 체인이 길어져 패킷마다 조회 비용이 늘어난다.

### 9. 응답만 INVALID로 버려짐

- 가는 경로와 오는 경로가 다른 장비를 지났다(**비대칭 라우팅**).
- 응답 경로의 상태 방화벽은 그 연결의 SYN을 본 적이 없다. conntrack 항목이 없으니 SYN-ACK를 INVALID로 본다.
- 대처: 라우팅을 대칭으로 맞추거나, 상태 장비를 양방향이 모두 지나는 위치에 둔다.

### 10. 매핑이 조용히 지워진 연결에서 read만 기다리면

- 상대 서버가 보내는 데이터는 NAT에서 버려진다. 이쪽이 보내는 것도 버려진다(RST 없이 드롭하는 장비의 경우).
- 이쪽이 보낼 게 없으면 아무 패킷도 오가지 않는다. `read()`는 타임아웃이 없으면 영원히 블록한다.
- 19번 노트의 **half-open**과 같다. 한쪽(여기서는 NAT의 표)이 연결 정보를 잃었는데 다른 쪽은 모른다.
- 대처도 같다: read 타임아웃, keepalive, 앱 heartbeat.
