# network/46-load-balancers-and-proxies — 정답

## 정답

### 1. L4 vs L7의 선택 단위

- L4는 **연결** 단위로 고른다. 첫 패킷(TCP면 SYN)에서 흐름 해시(예: 5-tuple, AWS NLB는 TCP 시퀀스 번호도 씀)로 백엔드를 정하고, 그 연결의 패킷은 끝까지 같은 백엔드로 보낸다(연결 추적 표에 기록).
- L7은 **요청** 단위로 고른다. LB가 TCP·TLS를 끝까지 받고 HTTP 요청을 하나 읽을 때마다 백엔드를 정한다.
- keep-alive 연결 하나로 요청 100건이면
  - L4: 연결이 하나이므로 100건 전부 한 백엔드로 간다.
  - L7: 스티키 세션 같은 고정이 없으면 요청마다 고르므로 3대로 퍼진다(라운드로빈이면 약 33건씩). 스티키 세션을 켜면 이후 요청은 알고리즘을 건너뛰고 같은 대상으로 간다(ALB 대상 그룹 속성 문서). LB↔백엔드 쪽은 별도 연결이다.
- 그래서 오래 사는 연결이 많은 L4 구간에서는 연결에 최대 수명을 두거나 L7에서 분산한다(35번 장애 시나리오 4).

### 2. 느린 백엔드 하나 — 라운드로빈 vs least_conn

- 예측
  - 라운드로빈은 처리 중 개수를 보지 않는다. be1에도 정확히 1/3(200건)을 보낸다. be1 요청이 쌓여 전체 시간이 길어진다.
  - `least_conn`은 be1에 처리 중 연결이 쌓이면 be2·be3로 보낸다. be1 몫이 크게 준다.
- 실험 1 결과(3회, 점검 재실행 포함)
  - 라운드로빈: be1 200건(33.3%), 전체 6.94~7.09초.
  - least_conn: be1 32~36건(5~6%), 전체 3.09~3.52초.
  - 지연이 없을 때는 두 방식 모두 약 1/3씩이었다.
- "가장 무난한 기본값"이라는 말은 근거가 없다.
  - nginx 오픈소스·AWS ALB·HAProxy·Envoy의 기본은 라운드로빈이다(각 문서).
  - HAProxy 문서는 `leastconn`을 아주 긴 세션(LDAP·SQL)에 권하고, HTTP처럼 짧은 세션에는 잘 맞지 않는다고 적는다.
  - least_conn의 이득은 동시 처리 수가 느림을 드러낼 만큼 있을 때 생긴다. 새로 뜬 서버(처리 중 0개)로 쏠리는 함정도 있다. 그래서 슬로우 스타트를 같이 본다(제품마다 지원 조합이 다르다).

### 3. 죽은 백엔드와 nginx 수동 헬스체크·재시도

- 기본 설정(`max_fails=1`, `fail_timeout=10s`, `proxy_next_upstream error timeout`)
  - 사용자는 502를 보지 않는다(실험 4: 14건 전부 200).
  - be2 연결 거부 → 같은 요청을 be3로 재시도한다.
  - 로그: `up=172.28.0.2:9002, 172.28.0.2:9003 up_status=502, 200`. 한 요청 안의 두 시도가 쉼표로 찍힌다.
  - 그 뒤 be2는 `upstream server temporarily disabled`로 10초 이상 빠진다.
- `proxy_next_upstream off`
  - 재시도하지 않으므로 be2 차례의 요청이 502다.
  - 그러나 연결 거부(`error`)는 지시어와 무관하게 실패로 세므로 be2가 바로 빠진다. 실험에서 14건 중 502는 1건뿐이었다.
- `max_fails=0` + `off`
  - 실패를 세지 않아 be2가 빠지지 않는다. 차례가 올 때마다 502다(실험: 9건 중 3건).
- 덧붙여: `fail_timeout`이 지나도 be2가 곧바로 다시 시도되지는 않았다. nginx 소스가 실패한 서버의 `effective_weight`를 깎았다가 고를 때마다 1씩 올리기 때문으로 보인다(해석).

### 4. mod-N·해시 링·Maglev의 이동량

- 실험 2(모형, N=100, 키 100만 개, 제거 3회)
  - mod-N: 약 99%가 옮겨 갔다. N이 바뀌면 나머지가 거의 다 바뀐다.
  - 해시 링(가상 노드 100·160): 0.89~1.12%. 제거된 백엔드 몫만 옮겼다(그 밖 0.00%).
  - Maglev M=65537: 1.58~1.60%. 제거된 몫 말고도 0.6%쯤 더 옮겼다. M=655373이면 1.14~1.15%로 줄었다.
- Maglev를 쓰는 이유
  - 부하가 고르다. 테이블 칸이 백엔드마다 655~656으로 1칸 차이였다. 링(가상 노드 100)은 최다 백엔드가 평균의 1.22배였다.
  - 논문은 고른 부하를 앞세운다. 고르지 않으면 최고 부하에 맞춰 백엔드를 과하게 늘려야 하기 때문이다.
  - 연결이 같은 Maglev 장비로 계속 오는 평상시에는 연결 추적 표가 있어 테이블이 조금 바뀌어도 기존 연결은 그대로 간다. 장비 배정이 바뀌면 바뀐 칸만큼 리셋이 생긴다(논문 §3.3·§3.4).
  - 조회는 배열 한 칸 읽기라 빠르다. Envoy 문서는 링 대비 생성 약 10배·선택 약 5배 빠르다고 적는다(256K 링 기준).
- M이 소수인 이유: skip이 1~M-1 중 무엇이든 M과 서로소가 되어, (offset + j·skip) mod M이 0~M-1을 한 번씩 다 돈다(논문 §3.4).

### 5. 깊은 헬스체크 연쇄

- 원인: 헬스 엔드포인트가 전 인스턴스가 공유하는 DB를 검사한다. DB가 느려지면 세 인스턴스가 동시에 검사에 실패한다. LB는 보낼 곳이 없어 503을 낸다. DB를 쓰지 않는 요청도 LB에서 막힌다.
- 실험 3(모형): DB 1초 지연(3~9초) 동안 deep 모드는 약 4초 넘게 성공 0건, 280건 중 89건이 503이었다. shallow 모드는 0건이었다.
- 확인
  - LB 대상 상태 이력에서 전 대상이 같은 시각에 unhealthy로 바뀌었는지 본다.
  - 앱 로그에 오류가 거의 없는지 본다(요청이 앱까지 안 옴).
  - 헬스 엔드포인트 코드에 DB·캐시·외부 API 호출이 있는지 본다.
- 대처
  - liveness는 프로세스만, readiness는 인스턴스별 상태만 본다(이 노트의 선택 — 9번 참고).
  - 공유 의존성 장애는 앱의 타임아웃·서킷 브레이커·폴백으로 다룬다.
- 전부 비정상일 때
  - AWS ALB: fail open. 상태와 무관하게 전 대상에게 보낸다.
  - Envoy: 사용 가능한 호스트가 panic threshold(기본 50%) 아래면 헬스 상태를 무시하고 전 호스트에 보내거나, 설정에 따라 아무 데도 보내지 않는다.
  - nginx 오픈소스: `no live upstreams`와 502.

### 6. realip 세 설정의 결과

- 안쪽 nginx가 받는 헤더: `X-Forwarded-For: 203.0.113.9, 172.28.0.2, 127.0.0.1`(가장자리·중간 프록시가 하나씩 덧붙임), 소켓 상대는 127.0.0.1.
- `set_real_ip_from 127.0.0.1` + `recursive on`: 오른쪽부터 신뢰 주소(127.0.0.1)를 건너뛰고 처음 만난 비신뢰 주소 → **172.28.0.2**. 정답이다.
- 같은 설정 + `recursive off`: 헤더의 마지막 주소 → **127.0.0.1**. 중간 프록시 주소가 클라이언트로 잡힌다.
- `set_real_ip_from 0.0.0.0/0` + `on`: 전부 신뢰하므로 맨 왼쪽까지 간다 → **203.0.113.9**. 위조 값이 클라이언트가 된다.
- 실험 6의 출력이 셋 다 이와 같았다(1단 프록시인 I_all은 헤더가 `203.0.113.9, 172.28.0.2`).
- `$realip_remote_addr`는 세 경우 모두 127.0.0.1(바꾸기 전 소켓 주소)이다.

### 7. ip_hash vs hash consistent의 분포

- (a) 한 /24 안의 서로 다른 주소 250개에서 온 300건
  - `ip_hash`: IPv4 앞 세 옥텟만 키로 쓰므로 300건 전부 한 서버(실험 7: be1=300).
  - `hash $remote_addr consistent`: 전체 주소를 해시해 고르게 퍼진다(be1=103, be2=98, be3=99).
- (b) 60%가 NAT 주소 하나
  - 두 방식 모두 그 주소의 180건이 한 서버로 간다. 그 서버가 약 70%를 받는다(ip_hash be1=220, consistent be3=209).
  - 키 하나가 무거우면 해시 방식을 바꿔도 쏠림이 남는다. 세션을 서버 밖으로 옮겨 고정을 없애는 것이 근본 대처다.

### 8. 배포 때 502와 GET/POST 차이

- 원인: LB가 대상을 빼기 전, 또는 진행 중 요청이 끝나기 전에 백엔드가 연결을 닫았다. nginx는 응답 헤더를 읽던 연결이 닫혀 `upstream prematurely closed connection`을 남기고 502를 준다.
- 대처
  - LB에서 빼기 → 반영 대기 → 진행 중 요청 마치기(드레이닝) → 종료 순서를 지킨다(reliability/14).
  - LB 드레이닝 시간(ALB deregistration delay 기본 300초)을 가장 긴 정상 요청보다 길게 둔다.
  - nginx 설정 변경은 `nginx -s reload`로 한다. 옛 worker가 진행 중 요청을 마치고 끝난다(실험 5 ①: 빠진 서버의 6초 요청도 200).
- GET과 POST
  - 클라이언트에 아직 아무것도 보내지 않았으므로 nginx는 다음 서버로 넘길 수 있다.
  - GET은 넘겨서 200이 됐다. 대신 앞 서버에서 한 일을 버리고 처음부터 다시 해 느렸다(실험 5: 4초 요청이 5.64초).
  - POST·LOCK·PATCH 같은 비멱등 요청은 상류에 보낸 뒤에는 넘기지 않는다(`non_idempotent`를 켜야 넘김, proxy 모듈 문서). 그래서 502였다. 두 번 실행되면 안 되는 요청을 보호하는 동작이다.

### 9. 헬스체크 3종에 넣을 것

- liveness: 프로세스 자신이 회복 불가능한 상태인지(교착 등)만 본다. 실패하면 재시작되므로 외부 시스템은 넣지 않는다. Spring Boot 문서는 외부 시스템이 실패하면 전 인스턴스를 재시작해 연쇄 장애를 만들 수 있다고 적는다.
- readiness: 트래픽을 받을 준비가 됐는지 본다. 실패하면 엔드포인트에서 빠질 뿐 재시작되지 않는다. 종료 중·워밍업 전 같은 인스턴스별 상태를 넣는다.
- startup: 기동이 오래 걸리는 앱에 둔다. 성공할 때까지 liveness·readiness 검사를 미룬다(Kubernetes 문서).
- 두 문서가 갈리는 곳
  - Kubernetes 문서: 앱이 뒤쪽 서비스에 엄격히 의존하면 readiness가 필요한 뒤쪽 서비스까지 확인하게 할 수 있다고 적는다.
  - Spring Boot Actuator 문서: readiness에 외부 시스템을 넣을지 신중히 정하라고 하고, 기본으로 넣지 않는다. 인스턴스마다 따로인 외부 시스템은 넣을 수 있고, 필수가 아닌 것(서킷 브레이커·폴백이 있는 것)은 넣지 말라고 한다. 전 인스턴스가 공유하는 시스템은 판단의 문제라고 적는다. 넣으면 그 시스템 장애 때 앱이 서비스에서 빠지고, 빼면 호출 쪽 서킷 브레이커 등 위쪽에서 다룬다.
- 정리(이 노트의 선택 — Spring 문서는 두 길을 다 열어 둔다): 공유 의존성은 readiness에서 빼고 서킷 브레이커로, 인스턴스별 의존성만 readiness에 넣는다.
