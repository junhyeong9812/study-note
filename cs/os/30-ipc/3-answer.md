# os/30-ipc — 정답

## 정답

### 1. 주소 공간과 복사 횟수

- 주소는 각 프로세스의 **가상** 주소다. 같은 숫자라도 페이지 테이블이 달라 다른 물리 메모리(또는 없는 곳)를 가리킨다. 보호를 위해 일부러 갈라 놓았다.
- 파이프·소켓·메시지 큐: 보내는 쪽 버퍼 → **커널 버퍼**로 한 번, 커널 버퍼 → 받는 쪽 버퍼로 한 번. 데이터 전달 1번에 복사 2번이다. 커널이 중개하니 블로킹·깨우기가 따라온다.
- 공유 메모리: 같은 물리 페이지를 두 주소 공간에 매핑한다. 설정 뒤에는 복사가 없다. 대신 동기화를 직접 해야 한다.

### 2. 파이프 버퍼

```text
  쓰기 끝 fd -> [슬롯0][슬롯1] ... [슬롯15] -> 읽기 끝 fd
                 링 버퍼(head/tail), 슬롯마다 페이지 하나
```

- 기본 용량: 16페이지 = 65,536바이트(4 KiB 페이지, 리눅스 2.6.11+). `F_GETPIPE_SZ`로 확인하고 `F_SETPIPE_SZ`로 바꾼다(비특권 상한 `pipe-max-size` 기본 1 MiB).
- 예외: 비특권 사용자의 파이프 페이지 합계가 `pipe-user-pages-soft`(4.5+, 기본 16384)에 닿으면 새 파이프는 최소 크기(현재 커널 소스 2페이지)로 만들어지고 늘리기도 거부된다(pipe(7), fs/pipe.c).
- 가득 참: 블로킹 `write`는 공간이 날 때까지 잔다. 논블로킹이면 `EAGAIN`(작성 환경에서 65,536바이트 뒤 `EAGAIN`, 로컬 재현).
- 비었음: 쓰기 끝이 하나라도 열려 있으면 블로킹 `read`는 데이터가 올 때까지 자고, 논블로킹이면 `EAGAIN`. 쓰기 끝이 모두 닫혔으면 둘 다 즉시 0(EOF).

### 3. 60,000 vs 70,000바이트

- 60,000바이트: 버퍼(65,536)에 다 들어간다. 자식은 쓰고 끝난다. 부모는 `waitpid`에서 깨어나 버퍼를 읽는다. 정상 종료(작성 환경 재현).
- 70,000바이트: 65,536바이트를 쓴 뒤 버퍼가 가득 차 자식이 `write`에서 잔다. 부모는 자식이 끝나기를 `waitpid`에서 기다린다. 서로를 기다리는 **교착**이다(작성 환경에서 `timeout 3`에 걸림).
- 자는 곳: 부모 `wchan = do_wait`, 자식 `wchan = anon_pipe_write`(리눅스 7.0 이름, 로컬 재현). 둘 다 `S` 상태, CPU 0%.

### 4. EOF가 안 오는 이유

1. 부모 자신이 쓰기 끝 fd를 안 닫았다. 쓰기 끝을 가리키는 fd가 하나라도 남으면 EOF가 아니다(pipe(7)).
2. 쓰기 끝 fd가 다른 자식·손자(백그라운드 데몬 등)에게 상속돼 그쪽이 아직 살아 있다.

- 막는 법: `fork` 직후 안 쓰는 끝을 `close`한다. `pipe2(p, O_CLOEXEC)`로 만들어 `exec` 때 자동으로 닫히게 한다. `ls -l /proc/*/fd`에서 같은 `pipe:[번호]`를 쥔 프로세스를 찾는다.

### 5. `yes | head -1`

- `head`가 한 줄을 읽고 끝나면 읽기 끝이 모두 닫힌다. 그 뒤 `yes`의 `write`는 SIGPIPE를 받는다. 기본 동작은 종료이므로 exit code는 128 + 13 = **141**이다(작성 환경 재현 `PIPESTATUS=141 0`).
- 서버: SIGPIPE 한 번에 프로세스 전체가 죽으면 안 된다. SIGPIPE를 무시하거나 소켓 쓰기에 `MSG_NOSIGNAL`을 주고, `write`가 돌려주는 `EPIPE`를 연결 단위 에러로 처리한다. Node는 시작할 때 SIGPIPE를 `SIG_IGN`으로 두고(src/node.cc), HotSpot JVM은 아무것도 안 하는 핸들러를 걸어 무시와 같은 효과를 낸다(signals_posix.cpp).

### 6. `PIPE_BUF`

- `PIPE_BUF` 이하의 `write`는 **원자적**이다. 다른 writer의 데이터와 섞이지 않고 연속으로 들어간다. 리눅스는 4096바이트, POSIX는 최소 512바이트를 요구한다(pipe(7)).
- 그보다 큰 `write`는 다른 프로세스의 쓰기와 섞일 수 있다.
- 로그: 여러 프로세스가 한 파이프에 쓸 때 줄 하나를 `PIPE_BUF` 이하의 **한 번의 write**로 쓰면 줄이 안 섞인다.
- 메시지 경계는 **없다**. 파이프는 바이트 흐름이다. write 두 번이 read 한 번에 붙어 나올 수 있다. 경계가 필요하면 길이 접두나 구분자를 둔다.

### 7. 유닉스 소켓의 기능과 `EADDRINUSE`

- `SCM_RIGHTS`: 열린 파일(정확히는 열린 파일 설명에 대한 참조)을 상대 프로세스에 건넨다. 받는 쪽은 `dup`한 것과 같은 효과를 얻는다. fd 번호는 다를 수 있다(unix(7)).
- `SO_PEERCRED`: 연결한 상대의 pid·uid·gid를 커널이 알려 준다. 신원 확인을 커널이 보증한다.
- 둘 다 TCP로는 할 수 없다. 거기에 IP·TCP 스택을 거치지 않는다.
- `EADDRINUSE`: 경로 소켓은 닫아도 파일시스템의 소켓 파일이 남는다. 지우는 것은 호출자 몫이다(unix(7)). 비정상 종료로 `unlink`를 못 했으면 재시작 때 같은 경로에 `bind`가 실패한다. 시작 시 옛 파일을 정리한다(작성 환경 재현: 재 bind 98 `EADDRINUSE`).

### 8. 공유 메모리 카운터

- 원인: `counter++`는 읽기 → 더하기 → 쓰기 세 단계다. 공유 메모리에는 커널의 중개가 없어서 두 프로세스가 같은 값을 읽고 같은 값을 쓰면 하나가 사라진다(경쟁 조건, 15번). 작성 환경에서 2,812,951이 나왔다(`-O0`, 실행마다 다름).
- 해결: `atomic_fetch_add` 같은 원자 연산(같은 실험에서 4,000,000), 또는 공유 메모리 안의 프로세스 공유 뮤텍스·세마포어.
- 이전 값이 남는 이유: POSIX 공유 메모리는 **커널 지속성**이다. 모두 unmap하고 `shm_unlink`하거나 시스템이 꺼질 때까지 `/dev/shm`에 남는다(shm_overview(7)). 시작 시 초기화·정리 경로가 필요하다.

### 9. 외부 명령 출력 받기

- Java
  - `Process` 문서의 경고: 표준 입출력 버퍼가 작아 제때 읽지 않으면 자식이 막히거나 교착한다.
  - `redirectErrorStream(true)`로 스트림을 하나로 합치고, `getInputStream()`을 끝까지 읽은 **뒤** `waitFor()`한다.
  - 따로 받아야 하면 stdout·stderr를 서로 다른 스레드로 동시에 읽는다. 필요 없으면 `Redirect.DISCARD`나 파일로 보낸다.
- Node
  - `spawn`의 `stdout`·`stderr`에 `'data'` 핸들러를 걸어 계속 소비한다. 안 쓸 출력이면 `{ stdio: 'ignore' }`(Node 문서).
- `exec`의 `maxBuffer`(기본 1024 * 1024바이트)를 stdout이나 stderr가 넘으면 자식 프로세스를 종료하고 출력을 자른다(Node 문서). 큰 출력은 `spawn`으로 스트리밍한다.
