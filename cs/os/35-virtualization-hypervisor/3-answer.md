## 정답

### 1. 직접 실행을 한 층 더

- OS가 프로세스를 돌릴 때처럼, 하이퍼바이저도 게스트 코드를 **CPU에서 직접** 실행한다. 대부분의 명령은 누구의 것이든 결과가 같기 때문이다.
- 게스트가 민감한 일(특권 레지스터, I/O, 페이지 테이블 교체 등)을 할 때만 트랩(하드웨어 지원이면 VM exit)이 나서 하이퍼바이저가 끼어들어 흉내 낸다.
- OSTEP 부록 B는 이것을 "제한된 직접 실행의 확장"으로 설명한다. OS가 트랩 테이블로 프로세스를 통제하듯, 하이퍼바이저는 하드웨어가 핵심 사건마다 자기에게 오도록 설정해 게스트를 통제한다.

### 2. 가상화 가능 조건과 x86

- 조건(Popek·Goldberg 1974): **민감한 명령은 모두 특권 명령**이어야 한다. 그래야 덜 특권 있는 모드에서 돌리는 게스트 커널이 민감한 명령을 쓸 때 반드시 트랩이 나고, 하이퍼바이저가 가로챌 수 있다.
- 옛 x86에는 트랩 없이 조용히 다르게 동작하는 민감 명령이 있어 조건을 어겼다. 예: `POPF`는 특권 없이 실행하면 예외 없이 인터럽트 플래그 같은 비트만 안 바뀐다(Robin·Irvine 2000, 펜티엄의 이런 명령 17개).
- 해법 세 가지
  1. **이진 번역**(VMware): 게스트 커널 코드의 문제 명령을 실행 전에 안전한 코드로 바꿔 쓴다.
  2. **반가상화**(Xen): 게스트 OS를 고쳐 문제 동작 대신 하이퍼바이저를 직접 부른다.
  3. **하드웨어 지원**(Intel VT-x, AMD-V): root/non-root 모드와 VM exit를 CPU에 넣었다.

### 3. KVM의 모습

```text
  호스트: QEMU 프로세스 (VM 하나)
            vCPU 스레드 N개  --ioctl(KVM_RUN)-->  kvm.ko (VM entry)
                                                    |
                                     게스트 코드 CPU에서 직접 실행
                                                    |
                         게스트가 out 명령 -> VM exit -> kvm.ko
                         커널이 처리 못 하는 I/O -> KVM_RUN 반환(exit_reason=KVM_EXIT_IO)
                         -> QEMU(사용자 공간)가 장치를 흉내 -> 다시 KVM_RUN
```

- vCPU는 호스트 입장에서 **보통 스레드**다. 호스트 스케줄러가 다른 스레드와 함께 CPU를 나눠 준다.
- 작성 환경의 최소 KVM 프로그램에서 `out` 2번 + `hlt` 1번 = VM exit 3번이었고, 반복 측정에서 사용자 공간 exit 1번은 약 3.1 µs였다(로컬 재현, 예시).

### 4. 2차원 걷기 계산

- 게스트 페이지 테이블 4단계를 걷는다. 각 단계 표의 위치는 **게스트 물리 주소(GPA)**라서 읽기 전에 호스트 표 4단계로 번역해야 한다.
  - 단계마다 호스트 걷기 4번 + 게스트 항목 읽기 1번 = 5번, 4단계면 20번.
- 게스트 걷기 결과(데이터의 GPA)를 호스트 물리 주소로 바꾸는 호스트 걷기 4번.
- 합계 **24번** = (4 + 1) × (4 + 1) − 1.
- 가상화 없음: **4번**.
- 실제로는 페이지 걷기 캐시·TLB가 대부분을 가리지만, TLB 미스가 많은 워크로드에서 차이가 드러난다. 큰 페이지로 미스 수를 줄인다.

### 5. 섀도 vs 중첩

- **섀도 페이지 테이블**: 하이퍼바이저가 GVA → HPA 합성 표를 소프트웨어로 유지한다. TLB 미스 자체는 가상화 없음과 같은 비용이다. 대신 게스트가 **페이지 테이블을 바꿀 때마다** 트랩으로 섀도 표를 맞춰야 한다(프로세스 생성·문맥 교환·페이지 폴트가 많은 워크로드에서 비쌈).
- **중첩 페이지 테이블**: 게스트가 자기 표를 바꿔도 트랩이 없다. 대신 **TLB 미스마다** 하드웨어가 두 표를 2차원으로 걸어 비싸다(최악 24번 참조).

### 6. steal time

- vCPU가 **돌고 싶었는데**(실행할 일이 있었는데) 호스트에서 차례를 못 받아 못 돈 시간이다. KVM은 이 값을 나노초로 게스트와 공유하는 구조체(`MSR_KVM_STEAL_TIME`)에 채운다.
- vCPU가 idle인 시간은 steal로 치지 않는다(커널 문서 KVM MSR).
- 게스트 리눅스는 `/proc/stat`의 `steal`, `top`의 `st`, `mpstat`의 `%steal`로 보여 준다.
- 게스트 안에서는 줄일 수 없다. 원인이 호스트(이웃 VM, 과할당)에 있기 때문이다. 보고 판단하는 지표다.

### 7. 원인 모를 지연

1. 지연이 튄 시각을 앱 지표로 잡는다.
2. 같은 시각의 `%steal`(`mpstat -P ALL 1`, 모니터링의 cpu steal)을 본다.
3. steal이 함께 오르면 VM 밖 원인이다. 프로파일러는 "실행된 시간"만 세므로 실행되지 못한 시간(steal)은 안 보인다.
4. steal이 낮으면 VM 안 원인(GC, I/O, 락)으로 돌아가 31번 순서로 본다.

- steal이 원인일 때 대처
  - steal 경보를 건다.
  - 인스턴스를 교체해 다른 호스트로 옮긴다.
  - 고정 성능 유형이나 전용 호스트를 쓴다. 버스트형이면 크레딧 잔량을 본다.

### 8. VM vs 컨테이너의 CPU 제한 신호

- **VM**: 하이퍼바이저가 vCPU를 못 돌린 시간 → 게스트의 `steal`(`st`, `%steal`).
- **컨테이너**: 호스트 커널이 cgroup 쿼터 소진으로 멈춘 시간 → cgroup `cpu.stat`의 `nr_throttled`·`throttled_usec`. 컨테이너 안 `top`의 `st`에는 나오지 않는다. `/proc/stat`는 호스트 전체 값이다(28·31번).
