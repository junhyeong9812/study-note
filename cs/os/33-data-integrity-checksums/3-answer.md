# os/33-data-integrity-checksums — 정답

## 정답

### 1. fail-stop vs fail-partial

- fail-stop: 디스크는 완전히 동작하거나 완전히 죽는다. 죽으면 바로 알 수 있다(OSTEP 38.2).
- fail-partial: 살아 있는 디스크의 일부 블록이 읽기 불가가 되거나 틀린 내용을 담을 수 있다(OSTEP 45.1).
- LSE: 디스크가 "못 읽겠다"고 **에러**를 낸다(드라이브 ECC가 못 고침).
- 조용한 손상: 디스크가 성공을 알리며 **틀린 값**을 준다. 아무 신호가 없다.

### 2. 조용한 손상이 복제·백업을 뚫는 이유

- 에러가 없으니 앱은 틀린 값을 정상으로 알고 쓰고, 복제하고, 백업한다. 사본들도 같은 틀린 값이 될 수 있다.
- RAID1은 두 사본이 다르다는 것은 알아도(스크럽) 어느 쪽이 옳은지 모른다. `repair`는 한 사본으로 다른 쪽을 덮는다(md(4)).

### 3. 체크섬 흐름

```text
  쓰기: D -> C(D) 계산 -> [D][C(D)] 저장
  읽기: [D'][C] -> C(D') 계산 -> 같으면 정상 / 다르면 손상 -> 다른 사본으로 복구 또는 에러
```

- 체크섬은 4 KB를 4·8바이트로 요약한다. 가능한 입력이 훨씬 많으니 서로 다른 데이터가 같은 체크섬을 갖는 **충돌**을 피할 수 없다. 좋은 함수는 충돌을 줄이고 계산이 싸다(OSTEP 45.3).

### 4. 함수 비교

- XOR: 빠름. 같은 자리 비트 두 개가 함께 바뀌면 못 잡는다.
- 덧셈: 빠름. 데이터가 밀리면 못 잡는다.
- Fletcher: 두 합으로 순서를 반영한다. 1·2비트 오류를 모두, 많은 버스트 오류를 잡는다. CRC에 가깝다.
- CRC: 다항식 나눗셈의 나머지. 버스트 오류에 강하고 하드웨어로 빠르다.
- 같은 함수를 쓰면 안 된다. CRC류는 **우연한** 손상용이다. 충돌을 일부러 만들 수 있어 위조 방지에는 SHA-256 같은 암호학적 해시(+ 서명·MAC)를 쓴다.

### 5. misdirected write와 lost write

- misdirected: 데이터와 체크섬이 **짝을 이룬 채** 엉뚱한 위치에 쓰였다. 그 위치를 읽으면 체크섬이 맞는다. 해법: 체크섬에 **물리 ID**(디스크·블록 번호)를 함께 넣어 읽을 때 위치를 대조한다(OSTEP 45.5).
- lost write: 새 쓰기가 실제로 안 되었다. 자리에 남은 옛 블록은 옛 체크섬과 맞고 위치도 맞다. 해법: 쓰기 뒤 다시 읽기(느림), 또는 **부모가 자식의 새 체크섬**을 기억해 대조(ZFS)(OSTEP 45.6).

### 6. 부모에 둔 체크섬 = 머클 트리

- 부모 블록이 자식의 체크섬을 갖고, 그 부모는 다시 위에서 검증된다. 루트가 맞으면 아래 전체가 맞다. 이것이 **머클 트리**다.
- 못 잡는 경우: 부모와 자식의 쓰기를 **둘 다** 잃으면, 옛 부모와 옛 자식이 서로 맞아 보인다(OSTEP 45.6).

### 7. 스크러빙

- 대부분 데이터는 거의 읽히지 않는다. 읽을 때만 검사하면 몇 년 동안 손상이 쌓여도 모른다.
- 그 사이 다른 사본까지 손상되면 복구할 곳이 없다. 스크럽은 모든 블록을 주기적으로 읽어 **사본이 아직 멀쩡할 때** 고친다(OSTEP 45.7).
- 현장 연구에서 대부분의 LSE가 스크럽으로 발견되었다(OSTEP 45.1).

### 8. ext4 이미지 실험

- (a) 데이터 블록 변경: `debugfs cat`은 바뀐 값(`balance=9000`)을 **조용히** 돌려주고, `e2fsck -fn`은 exit 0, 문제 없음.
- (b) inode 변경: `debugfs cat`이 `Inode checksum does not match inode`, `e2fsck -fn`은 `Inode 12 passes checks, but checksum does not match inode.`(exit 4).
- 차이: ext4 `metadata_csum`은 **메타데이터만** crc32c로 보호한다. 데이터 블록에는 체크섬이 없다.

### 9. btrfs RAID1인데 깨진 VM 이미지

- 의심: 그 파일(또는 디렉터리)에 `+C`(NOCOW)가 있다. NOCOW는 **데이터 체크섬을 끈다**. 스크럽은 그 데이터를 검증·수리하지 못하고, 손상된 사본을 그대로 읽을 수 있다(btrfs 문서 Scrub 경고). libvirt 6.6+는 스토리지 풀 디렉터리에 기본으로 `+C`를 둔다.
- 확인: `lsattr <파일>`에 `C` 플래그. `btrfs device stats`로 장치 오류 누계를 본다.
- 대처: 그 파일은 앱 수준 체크섬에 의존한다고 보고 설계하거나, 필요 없으면 `C` 없는 디렉터리에 **새 파일로 복사**(`cp --reflink=never`)해 교체한다.
  - chattr(1)은 btrfs에서 `C`를 새 파일·빈 파일에 주라고 하고, 데이터가 있는 파일이면 언제 안정될지 정의되지 않는다고 적는다.
  - 현재 커널 소스(fs/btrfs/ioctl.c `btrfs_fileattr_set`)는 더 엄격하다. 크기 0인 일반 파일에만 `+C`·`-C`를 반영하고, 데이터가 있는 파일에서는 명령이 성공해도 플래그를 바꾸지 않는다. 그래서 이미 `C`가 붙은 파일에 `chattr -C`를 해도 풀리지 않는다(도입 버전 [?]).

### 10. 백업 설계

- 원본 쪽: 데이터 체크섬이 있는 저장 층(btrfs·ZFS) 또는 앱 체크섬, 그리고 정기 스크럽.
- 백업 쪽: 백업 시 파일마다 해시(SHA-256 등) manifest를 남긴다. 다음 백업 때 원본 해시가 **바뀌었는데 수정 기록이 없으면** 손상을 의심하고 경보한다.
- 보존: 여러 세대를 보존해, 늦게 발견해도 손상 전 버전이 남게 한다.
- 검증: 주기적으로 실제 복원해 해시를 비교한다. 복원해 보지 않은 백업은 백업이 아니다.
