# os/36-server-concurrency-architectures — 정답

## 정답

### 1. 다섯 아키텍처 표

| | 알림 | 스레드 수 비례 대상 | 핸드오프 큐 |
|---|---|---|---|
| 연결당 스레드 | 없음(블로킹 read/write) | 동시 연결 수 | 없음 |
| 리액터 | 준비(epoll) | 루프 수(≈코어 수) | 없음 |
| 프로액터 | 완료(IOCP·io_uring) | 적음(완료 처리 스레드) | 완료 큐 |
| 반동기/반비동기 | 준비(비동기 층) | 루프 수 + 워커 풀 크기 | **있음**(큐잉 층) |
| 리더/팔로워 | 준비 | 풀 크기 | 없음(이벤트 받은 스레드가 직접 처리) |

### 2. 유휴 스레드 1000개

- 로컬 재현(예시, 리눅스 7.0): `VmSize` 약 8.2GB(스레드당 8MB 스택 예약), `VmRSS` 약 10MB(스레드당 약 8.5KB 상주).
- 64비트에서는 가상 공간이 넉넉해 "가상 메모리 고갈"이 먼저 오지 않는다. Kegel의 "512개" 계산은 32비트 1GB 사용자 공간 기준이다.
- 먼저 오는 것
  - 스레드 수 한도: `ulimit -u`, `kernel.threads-max`, `pid_max`, `vm.max_map_count`, 컨테이너 cgroup `pids.max`.
  - 스케줄링 비용: 깨어나는 스레드가 많을수록 컨텍스트 스위칭·캐시 오염.
  - 스레드마다 쥔 버퍼·힙 객체, 커널 스택(x86-64 16KB, `VmRSS`에는 안 잡힌다).

### 3. 멀티 리액터

```text
  main reactor (accept 전용)
      | 새 연결을 라운드 로빈으로 배정
      v
  sub reactor 1 (epoll + 루프)   sub reactor 2   ...   sub reactor N (≈ 코어 수)
```

- 연결을 한 루프에 고정하면 그 연결의 상태는 한 스레드만 만진다. 루프 사이에 공유 상태가 없으니 락이 거의 필요 없고, 캐시 친화성도 좋다.
- accept를 나누는 방법
  1. main reactor 하나가 accept해서 sub에 배정한다(Netty boss group).
  2. 루프마다 리슨 소켓을 따로 두고 `SO_REUSEPORT`(3.9+)로 커널이 나눈다. socket(7)은 이것이 한 스레드가 나눠 주거나 여러 스레드가 한 소켓에서 경쟁하는 방식보다 분배가 낫다고 적는다.

### 4. 프로액터와 NIO.2

- 리액터는 "읽을 수 있다"(준비)를 받고 앱이 직접 `read`한다. 프로액터는 앱이 "읽어서 이 버퍼에 넣어 달라"를 먼저 시작하고, OS가 복사까지 끝낸 뒤 "읽었다"(완료)를 받는다(Proactor 논문).
- 그래서 프로액터는 버퍼를 작업 시작 때 넘기고, 완료 순서가 뒤섞일 수 있어 완료 토큰으로 짝을 맞춘다.
- NIO.2는 리눅스에서 **진짜 프로액터가 아니다**. OpenJDK `LinuxAsynchronousChannelProvider`가 `EPollPort`를 만들고, epoll 준비 알림 + 스레드 풀로 "완료 핸들러 호출"을 흉내 낸다. Windows에서는 OpenJDK `WindowsAsynchronousChannelProvider`가 `Iocp`를 쓰는 IOCP 기반이다.

### 5. 큐잉 층의 흐름 제어

- 도착률이 처리율보다 크면 큐는 끝없이 자란다. HS-HA 논문: "시스템은 큐잉 층의 버퍼에 무한한 자원을 쓸 수 없다." 그래서 층 사이 흐름 제어가 필요하다.
- 동기 층(워커)은 블록할 수 있다. 너무 많이 넣는 생산자를 재우고, 큐가 줄면 깨운다.
- 비동기 층(이벤트 루프)은 블록할 수 없다. 넘치면 메시지를 **버린다**. 논문의 "TCP면 보낸 쪽이 타임아웃 후 재전송"은 큐잉 층이 커널 안(BSD)이라 ACK 전에 버리는 경우다.
- 사용자 공간 루프가 이미 읽은 요청은 TCP가 ACK했으므로 버려도 재전송되지 않는다. 명시적으로 거절(503·연결 종료)하거나 읽기를 멈춰 TCP 윈도로 보낸 쪽을 늦춘다.
- 실무 번역: 유계 큐 + 거절(503) 또는 버림, 앞단 동시성 제한.

### 6. 리더/팔로워의 이득과 대가

- 줄이는 것(LF 논문 Consequences)
  - 요청마다의 동적 할당·데이터 공유: 이벤트를 받은 스레드가 자기 스택 버퍼로 바로 처리한다. CPU 캐시 친화성이 좋다.
  - 스레드 간 데이터 교환이 없어 락이 준다.
  - 이벤트마다의 컨텍스트 스위치(핸드오프)가 없다. 리더 승격 때만 필요하다.
  - 서버 안 추가 큐가 없어 우선순위 역전 가능성이 준다.
- 잃는 것
  - 구현 복잡도: 승격·복귀가 동시에 일어나 원자성을 지켜야 한다.
  - 유연성: 큐가 없으니 이벤트를 버리거나 우선순위를 다시 매길 수 없다.

### 7. 리틀의 법칙과 가상 스레드

- L = λW. 지금 L = 200 × 0.05 = 10. 초당 2000건이면 L = 2000 × 0.05 = **100**건을 동시에 처리해야 한다(JEP 444의 예).
- 요청당 스레드 스타일이면 스레드도 100개 이상 필요하다. 처리량이 늘수록 스레드 수가 비례해 는다. OS 스레드는 비싸서 이 스타일을 버리고 비동기로 가게 된다.
- 가상 스레드는 JVM이 많은 가상 스레드를 적은 OS 스레드에 얹어, 요청당 스레드 스타일을 유지하면서 이 동시성을 싸게 만든다.
- 지연은 줄이지 않는다. JEP 444: "가상 스레드는 더 빠른 스레드가 아니다. 속도(지연)가 아니라 규모(처리량)를 준다." CPU 바운드 작업에는 이득이 없다.

### 8. unable to create native thread

- 힙과 무관하다. **OS 스레드 생성**이 실패한 것이다(메시지 그대로 "process/resource limits reached"일 수 있다).
- 확인
  - `grep Threads /proc/<pid>/status`, `ps -o nlwp -p <pid>` — 현재 스레드 수.
  - `ulimit -u`(사용자당 프로세스·스레드 수), `cat /proc/sys/kernel/threads-max /proc/sys/kernel/pid_max /proc/sys/vm/max_map_count`.
  - 컨테이너면 `cat /sys/fs/cgroup/pids.max`와 `pids.current`.
  - `pidstat -w -t -p <pid> 1`로 컨텍스트 스위치 폭증 여부.
- 근본 대처: 스레드 수를 연결 수와 떼어 낸다(리액터·HS/HA). Java 21+면 가상 스레드. 임시로는 스택 크기(`-Xss`)를 줄이고 한도를 올린다.

### 9. newFixedThreadPool과 OOM

- 일어난 일
  1. DB가 느려져 워커 32개의 처리율이 도착률보다 낮아졌다.
  2. `Executors.newFixedThreadPool`은 **무한 큐**를 쓴다(Javadoc "shared unbounded queue"). 거절 없이 요청이 계속 쌓였다.
  3. 리틀의 법칙대로 큐 길이 L이 늘자 대기 시간 W = L/λ도 늘었다. 응답 시간이 수십 초가 됐다.
  4. 쌓인 요청 객체가 힙을 채워 GC가 폭증하고 `Java heap space`로 죽었다. 클라이언트는 이미 떠난 요청을 처리하느라 헛일도 했다.
- 고치기
  - `ThreadPoolExecutor`에 유계 큐(`ArrayBlockingQueue`) + 거절 정책(빠른 503)을 둔다.
  - 큐에서 오래 기다린 요청은 처리 전에 버린다(요청 타임아웃과 맞춤).
  - 앞단(`maxConnections`·LB)에서 동시성을 제한하고, 하류별로 풀을 나눈다(bulkhead).

### 10. 가상 스레드와 DB 풀 고갈

- 가상 스레드로 앱의 동시성 상한이 사실상 사라졌다. 그러나 DB 커넥션 풀(예: 10개)과 DB 처리량은 그대로다.
- 동시에 DB를 원하는 요청이 풀 크기를 크게 넘자 대기가 **풀 대기**로 옮겨 가고, `connectionTimeout`(메시지의 `after …ms`)을 넘긴 요청이 실패했다.
- 원칙: 동시성 한도는 **가장 좁은 하류 자원**에서 거꾸로 정한다. 하류 용량만큼 세마포어·풀로 제한하고, 넘치면 빠르게 거절한다. 풀 대기 타임아웃은 요청 전체 타임아웃보다 짧게 둔다.
