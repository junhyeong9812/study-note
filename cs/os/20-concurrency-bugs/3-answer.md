## 정답

### 1. Lu 외 연구의 숫자

- 대상: MySQL·Apache·Mozilla·OpenOffice에서 고쳐진 동시성 버그 105개(교착 아님 74, 교착 31).
- 첫 번째 97%: 교착 **아닌** 버그 74개 중 97%(72개)가 **원자성 위반 또는 순서 위반**이다(Finding 1).
- 두 번째 97%: **교착** 버그의 97%가 "스레드 2개가 자원 2개 이하를 두고 원형 대기"다(Finding 7).
- 96%(Finding 3): 버그의 96%는 **두 스레드 사이의 특정 부분 순서**만 강제하면 반드시 재현된다.
  - 테스트 전략: 많은 스레드·긴 부하보다 **두 스레드의 끼어들기 순서를 체계적으로 흔드는** 것이 효율적이다. 확인과 사용 사이에 지연을 주입하거나, 선점을 늘리는 식이다.

### 2. MySQL `proc_info` — 원자성 위반

```text
  스레드 1: if (thd->proc_info)  → NULL 아님
  스레드 2:                          thd->proc_info = NULL;
  스레드 1: fputs(thd->proc_info, …) → NULL 역참조 → 크래시
```

- 이름: **원자성 위반**. "원자적이어야 할 구역(확인+사용)에 원자성이 강제되지 않았다."
- 고치기: 확인과 사용을 락으로 감싸고, NULL로 바꾸는 쪽도 **같은 락**을 잡는다(OSTEP 그림 32.3).
- 빠뜨리기 쉬운 것: 그 필드를 건드리는 **다른 모든 코드**도 같은 락을 잡아야 한다. 한 곳만 고치면 다른 경로로 같은 버그가 남는다.

### 3. Node의 `await` 사이 초과 판매

- `await`는 그 자리에서 제어를 이벤트 루프에 돌려준다. A가 `db.read()`를 기다리는 동안 B의 `buy()`가 실행돼 역시 `read()`를 부른다.
- 둘 다 1을 읽고, 둘 다 `s > 0`을 통과해 `write(0)`을 한다. 스레드가 하나여도 **확인과 사용 사이에 다른 작업이 끼어들 수 있으면** 원자성 위반이다.
  - 로컬 재현(예시, Node 18): `[ 'A: ok (saw 1)', 'B: ok (saw 1)' ]`.
- 고치기
  - 확인과 차감을 DB 한 문장으로 한다: `UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0` → 영향받은 행이 0이면 품절.
  - 또는 같은 키의 작업을 직렬화한다(키별 큐, DB 행 잠금). 프로세스가 여러 개면 메모리 안의 뮤텍스로는 부족하다.

### 4. Mozilla `mThread` — 순서 위반

- `PR_CreateThread`가 반환되어 `mThread`에 대입되기 **전에** 새 스레드가 먼저 실행될 수 있다. 그러면 `mThread`는 아직 NULL이라 역참조에서 크래시한다(OSTEP 그림 32.4).
- 이름: **순서 위반**. "A가 항상 B보다 먼저여야 하는데 그 순서가 강제되지 않았다."
- 순서를 강제하는 도구
  1. 상태 변수 + 조건 변수: `mtInit = 1; signal` / `while (mtInit == 0) wait`(OSTEP 그림 32.5)
  2. 초깃값 0 세마포어: 초기화 후 `post`, 사용 전 `wait`(18번)
  3. Java `CountDownLatch`(`countDown` / `await`) 또는 `CompletableFuture`

### 5. 교착·기아·라이브락 구분

| | 시스템 전체 진행 | CPU 사용 | 예 |
|---|---|---|---|
| 교착 | 사이클에 든 스레드는 영원히 정지 | 대개 0(잠든 대기). 스핀락 교착이면 계속 돈다 | L1→L2 / L2→L1 |
| 기아 | 진행한다. 특정 스레드만 못 간다 | 다른 스레드들은 정상 사용 | 독자가 끊이지 않아 작가가 못 들어감 |
| 라이브락 | 진행이 0에 가깝다 | 높다(계속 재시도) | 백오프 없는 trylock-놓기-재시도 |

- 교착은 "모두 잠듦", 라이브락은 "모두 바쁨", 기아는 "남들은 되는데 나만 안 됨"으로 기억한다.

### 6. 백오프 없는 trylock 재시도

- 관찰: 두 스레드 모두 CPU를 쓰며 계속 실행하는데, 대부분의 시도가 실패한다. 멈추지는 않지만 진행이 거의 없다(라이브락).
  - 로컬 재현(예시, 리눅스 7.0, 1초): 성공 약 4만 번, 실패 재시도 약 194만 번(시도의 약 98%가 헛수고).
- 넣을 것: 재시도 전 **무작위 지연**(OSTEP 32.3). 로컬 재현에서 0~49µs 무작위 지연을 넣자 성공이 약 66만 번(약 16배), 재시도는 약 1만 3천 번이었다.
- 이유: 두 스레드가 같은 박자로 "잡기-실패-놓기"를 하니 계속 부딪친다. 무작위 지연은 박자를 흩뜨려, 한쪽이 두 락을 다 잡을 틈을 만든다.

### 7. 우선순위 역전

```text
  L: lock(R) ─[임계 구역]─┐                   ...(실행 못 함)...                     unlock(R)
  H:                      └ lock(R) 대기 ─────────────────────────────────────────── 진행
  M:                            깨어나 L을 선점 ──── 계속 실행 ────>
```

- 유한한 역전: H가 L의 임계 구역이 끝날 때까지 기다리는 것. 락을 공유하는 한 피할 수 없지만, 임계 구역 길이만큼으로 **한정**된다.
- 무한 역전: M이 L을 선점해 L이 임계 구역을 끝내지 못한다. H가 기다리는 시간이 M의 실행 시간에 달려 **정해지지 않는다**(docs.kernel.org rt-mutex-design).
- 스핀락 두 스레드 경우: L이 스핀락을 쥔 채 H가 깨어나 선점한다. H는 스핀락에서 돈다. 스케줄러는 실행 가능한 H를 항상 L보다 먼저 고르므로 L은 영원히 실행되지 못하고 락을 풀지 못한다. 시스템이 멈춘다(OSTEP 28장 aside).

### 8. Mars Pathfinder

- 무엇이 무엇을 막았나: 높은 우선순위 `bc_dist`(버스 데이터 분배)가 `select()` 메커니즘의 뮤텍스를 기다렸다. 그 뮤텍스는 낮은 우선순위 ASI/MET(기상 데이터) 작업이 쥐고 있었다. 여러 중간 우선순위 작업이 ASI/MET를 계속 선점했다(Reeves).
- 리셋: 다음 버스 주기를 준비하는 `bc_sched`가 "`bc_dist`가 제때 끝나지 않았다"(하드 마감 초과)를 감지해 오류를 선언했고, 우주선이 컴퓨터를 리셋했다. Jones의 요약은 이를 "워치독 타이머가 리셋"이라 표현했다.
- 원인 찾기: 지상의 복제 기체에서 VxWorks 전체 이벤트 트레이스를 켜고 수 시간 재현을 시도해 리셋을 재현했고, 트레이스에서 역전을 찾았다.
- 수정: VxWorks 뮤텍스는 생성 시 우선순위 상속 여부를 인자로 받는데, 그 뮤텍스는 꺼져 있었다. 우주선에 남아 있던 C 인터프리터로 전역 변수를 FALSE → TRUE로 바꾸는 짧은 프로그램을 올려 PI를 켰다. 이후 리셋이 사라졌다(Jones).
- 놓친 신호: 비행 전 몇 달의 시험 중 리셋이 한두 번 있었지만 재현·설명이 안 되어 "하드웨어 문제였을 것"으로 넘겼다(Jones).

### 9. 리눅스 PI와 JVM

- 켜는 법: `pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT)`로 속성을 만들어 뮤텍스를 초기화한다(POSIX). 리눅스는 이를 PI futex로 구현한다(futex(2)).
- strace 차이: 기본 뮤텍스의 경합은 `FUTEX_WAIT`/`FUTEX_WAKE`, PI 뮤텍스의 경합은 `FUTEX_LOCK_PI_PRIVATE`/`FUTEX_UNLOCK_PI_PRIVATE`다(로컬 재현, 리눅스 7.0). PI 모드에서는 커널이 락 주인을 알아야 우선순위를 올릴 수 있어서, 잠그고 푸는 경합 경로가 커널을 거친다.
- 전이성: H가 락 A를 기다리고, A의 주인 M'이 락 B를 기다리며, B의 주인이 L이라면, L까지 올려야 사슬이 풀린다. A의 주인만 올리면 그 주인도 여전히 막혀 있다. 그래서 사슬 전체가 H의 우선순위를 받아야 한다(futex(2), rt-mutex "PI chain").
- JVM: HotSpot은 리눅스에서 기본(`ThreadPriorityPolicy=0`)일 때 `Thread.setPriority`를 OS 우선순위에 반영하지 않는다(`os_linux.cpp` `os::set_native_priority`가 바로 반환). 그러니 Java 우선순위로는 역전을 만들지도, 해결하지도 못한다. 지연이 중요한 경로는 낮은 우선순위 작업과 락을 공유하지 않게 설계하고, 락 구간을 줄인다.
