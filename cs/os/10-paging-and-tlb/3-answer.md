# os/10-paging-and-tlb — 정답

> 복습 시 이 파일은 **최후에만** 연다.

## 정답

### 1. 4단계 워크

```text
   47..39    38..30    29..21    20..12    11..0
  [PGD 9b ] [PUD 9b ] [PMD 9b ] [PTE 9b ] [오프셋 12b]

  CR3 -> PGD[i1] -> PUD[i2] -> PMD[i3] -> PTE[i4] -> 프레임 번호(PFN) + 오프셋 = 물리 주소
```

- 각 표는 512칸 × 8 B = **4 KB**(페이지 하나)다(`PTRS_PER_* 512`).
- 하드웨어가 4단계면 리눅스의 P4D 단계는 접혀 없어진다(page_tables.rst).

### 2. 페이지 테이블 크기

- 32비트·4 KB: 2^20 항목 × 4 B = **4 MB**(프로세스마다, OSTEP 20).
- 48비트·4 KB·8 B: 2^36 항목 × 8 B = **512 GB**. 선형으로는 불가능하다.
- 다단계 해법: 윗단계의 한 칸이 아래 표 한 장을 가리킨다. 쓰지 않는 구간은 윗단계 칸을 "없음"으로 두고 아래 표를 만들지 않는다. 주소 공간이 희소하니 실제로 필요한 표는 몇 장뿐이다.
- 대가: TLB 미스 한 번에 표를 최대 4번 읽는다. 그래서 TLB가 필수다.

### 3. Present = 0

- 아직 한 번도 안 건드린 익명 페이지(요구 페이징, 첫 접근 때 0 페이지 할당).
- 스왑으로 나간 페이지(PTE에 스왑 위치가 들어 있다).
- 파일 매핑에서 아직 읽지 않은 페이지.
- VMA 밖이라 애초에 매핑이 없는 주소(→ SIGSEGV, 09번).
- 원고의 설명은 스왑·파일 경우만 맞다. 커널은 VMA와 PTE의 나머지 비트로 경우를 구분한다.

### 4. 64 MB `mmap` 후 절반 쓰기

- present 페이지: 16,384 중 약 **8,192**. `VmRSS`: 약 **32 MB 늘어남**.
- 로컬 재현(예시): 쓰기 전 present 0 · RSS 1616 kB → 쓴 뒤 present 8192 · RSS 34384 kB.
- `mmap`은 VMA만 만든다. 페이지는 처음 쓸 때 폴트로 생긴다.
- PFN이 0인 이유: 리눅스 4.2부터 `CAP_SYS_ADMIN`이 없으면 pagemap의 PFN을 0으로 가린다. 물리 주소 정보가 Rowhammer 공격을 돕기 때문이다(pagemap.rst).

### 5. TLB 히트·미스

```text
  va -> TLB 히트 -> pa
     -> TLB 미스 -> 페이지 테이블 워크 -> Present=1: TLB 채우고 재실행
                                     -> Present=0: 페이지 폴트 -> 커널 -> 재실행
```

- x86: **하드웨어**가 CR3부터 표를 걷는다(hardware-managed TLB).
- MIPS 등: TLB 미스가 트랩을 일으키고 **OS**가 표를 찾아 TLB에 채운다(software-managed, OSTEP 19).

### 6. TLB 도달 범위

- 4 KB: 2,048 × 4 KB = **8 MB**. 2 MB: 2,048 × 2 MB = **4 GB**.
- 256 MB 무작위 읽기는 4 KB 페이지의 도달 범위를 크게 넘어 대부분 미스다. 2 MB 페이지면 전체가 범위 안이다. **2 MB가 유리하다.**
- 폴트 수는 **512배** 차이다. 로컬 재현(예시): 4 KB 65,536번 → THP 128번. 접근 시간은 167.4 → 136.9 ns(약 18% 개선, 캐시 미스 비용 포함).

### 7. 문맥 전환과 TLB

- 방법 1 — **flush**: 전환마다 TLB를 비운다. 단순하지만 전환 직후 미스가 몰린다.
- 방법 2 — **ASID 태그**: 항목마다 주소 공간 ID를 붙여 여러 프로세스의 항목을 함께 둔다(OSTEP 19).
- x86 리눅스: PCID(x86의 ASID)로 CPU마다 최근 주소 공간 **6개**까지 구분한다(`TLB_NR_DYN_ASIDS 6`). 같은 프로세스의 스레드 간 전환은 CR3를 바꾸지도 않는다(07번).

### 8. TLB 슛다운 폭주

- 일어나는 일: 한 스레드가 매핑을 바꿀 때마다, 같은 주소 공간을 쓰는 다른 CPU들에 IPI를 보내 TLB를 비우게 한다. 인터럽트 처리와 대기가 커널 시간으로 잡힌다.
- 원인 패턴
  - 작은 `mmap`/`munmap` 반복, 할당기의 잦은 메모리 반환(`MADV_DONTNEED`).
  - JIT·GC·보안 기능의 잦은 `mprotect`.
- 로컬 재현(예시): 다른 CPU의 스레드 8개 + `munmap` 2만 번 → 슛다운 인터럽트 약 16만 번, 한 번 비용 3.86 → 11.15 µs.
- 확인: `strace -c -f -p <pid>`로 `munmap`·`madvise`·`mprotect` 빈도. 대처: 버퍼 재사용, 할당기 반환 빈도 낮추기.

### 9. Redis와 THP

- 원인: `BGSAVE`는 fork한다. 부모와 자식이 큰 페이지를 공유한다.
  - 리눅스 5.8 이전: 부모가 쓰면 **2 MB 단위로 복사**(COW)가 일어난다. 몇 번의 이벤트 루프만으로 거의 전체 메모리가 복사된다 → 큰 지연과 메모리 증가(Redis 문서).
  - 리눅스 5.8부터: PMD를 쪼개고 4 KB 한 장만 복사한다(커밋 3917c80280c9, `do_huge_pmd_wp_page`). 이때 남는 부담은 아래 압축 멈춤과 메모리 부풀림이다.
- 또 `defrag=always`면 큰 페이지 할당 실패 시 직접 압축하며 멈춘다(transhuge.rst).
- 대처: Redis 문서 권고대로 `echo never > /sys/kernel/mm/transparent_hugepage/enabled`. 또는 `madvise` 모드로 두고 Redis에는 주지 않는다.
- 도움이 되는 경우: fork를 하지 않고 큰 메모리를 오래 무작위 접근하는 프로세스(큰 JVM 힙, 가상 머신, 과학 계산). `madvise`로 그 구간만 켠다.

### 10. `PageTables` 계산

- 4 KB 페이지 512개(2 MB)를 PTE 표 한 장(4 KB)이 덮는다. 즉 매핑 크기의 **1/512**가 PTE 표다.
- 32 GB / 512 = **64 MB**(프로세스당, 전부 건드렸을 때). × 500 프로세스 = **약 32 GB**. 공유 메모리 크기만큼의 페이지 테이블이 더 생길 수 있다.
- 공유 메모리여도 **페이지 테이블은 프로세스마다 따로**다.
- 줄이는 법: huge pages(hugetlbfs, 2 MB). PMD 한 칸이 2 MB를 직접 가리켜 PTE 표가 필요 없다. 표 크기가 약 512분의 1로 준다. PostgreSQL 문서가 큰 `shared_buffers`에 huge pages를 권하는 이유다. 연결(프로세스) 수를 줄이는 것(커넥션 풀러)도 방법이다.
