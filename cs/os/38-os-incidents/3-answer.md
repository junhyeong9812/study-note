## 정답

### 1. Pathfinder 리셋의 사슬

```text
  (1) ASI/MET(낮음)가 select() -> pipeIoctl() -> selNodeAdd() 안에서 select 뮤텍스를 쥔 채 선점당함
  (2) 중간 우선순위 태스크 여럿이 실행
  (3) bc_dist(3위)가 ASI/MET에 데이터를 보내려 pipeWrite() -> 같은 뮤텍스를 요청 -> 대기
  (4) 중간 태스크가 계속 실행 -> ASI/MET가 뮤텍스를 못 놓음 -> bc_dist도 못 끝냄
  (5) 다음 8 Hz 주기에 bc_sched(최고)가 깨어나 "bc_dist 미완료"를 감지 -> 오류 선언 -> 전체 리셋
```

- 공유 자원: VxWorks `select()`가 fd 대기 목록을 보호하려 만든 **뮤텍스 세마포어**. 응용이 직접 만든 락이 아니었다.
- 리셋을 건 것: bc_sched의 주기 완료 확인(Reeves). Jones의 요약은 이를 "워치독 타이머"라고 적었다.
- 20번 노트의 우선순위 역전 그 자체다. 높은 태스크가 사실상 중간 태스크들보다 낮은 우선순위로 떨어졌다.

### 2. Pathfinder의 해법

- 해법: select 서비스가 쓰는 `semMCreate` 옵션 **전역 변수**에 우선순위 상속을 넣었다. 차이분을 올리는 전용 패치 절차로 우주선 소프트웨어를 바꿨다(Reeves).
- 바로 적용하기 어려웠던 이유(Reeves가 든 넷 중 둘)
  - 전역 변수라 이후 만드는 **모든** select 세마포어가 바뀐다. 문제의 파이프만 골라 바꿀 방법이 없었다. 시스템 나머지에 미칠 영향을 따져야 했다.
  - Wind River가 성능 때문에 select 기본값에서 상속을 **일부러** 뺐다. 켜면 성능이 얼마나 떨어지나, select의 동작이 바뀌나를 확인해야 했다. Wind River의 분석은 "영향은 작고, fd마다 기다리는 태스크가 하나뿐이면 동작도 같다"였다.
- 리눅스 유저 공간: `pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT)`로 PI 뮤텍스를 만든다. 커널은 PI futex(rt-mutex)로 상속을 처리한다(20번).

### 3. Jones와 Reeves

| 항목 | Jones(강연 요약) | Reeves(JPL 당사자) |
|---|---|---|
| 리셋 주체 | 워치독 타이머 | bc_sched의 완료 확인 |
| 공유 자원 | 정보 버스 뮤텍스 | select 내부 fd 목록 뮤텍스 |
| 패치 | C 인터프리터로 프로그램 업로드 | 셸 아님, 전용 차이분 패치 |
| 디버그 기능 | "다행히" 켜 둠 | 설계상 남겨 둠 |
| 데이터 | 리셋마다 손실 | 이미 모은 데이터는 보존 |

- 같은 점: 원인은 우선순위 역전, 해법은 우선순위 상속, 트레이스 없이는 못 찾았다.
- 세부가 다르면 **Reeves**를 따른다. Jones는 강연을 들은 제3자의 요약이고, Reeves는 비행 소프트웨어 팀을 이끈 당사자다. Reeves 스스로 "무슨 말이 나왔는지 찾는 대신 무슨 일이 있었는지 말하겠다"고 썼다.

### 4. 첫 fsync는 `EIO`, 재시도는 성공

```text
  write -> 페이지 캐시 dirty -> 백그라운드 writeback 실패
        -> 페이지를 clean으로 처리(데이터 버림 가능) + 매핑에 오류 표시(AS_EIO)
  fsync #1 -> 오류 표시를 보고 EIO 반환 -> 표시를 지움
  fsync #2 -> dirty 페이지 없음, 오류 표시 없음 -> 0(성공)
```

- Ringer의 표현: fsync 성공은 "마지막 fsync 이후의 쓰기"에 대한 것이다. PostgreSQL은 "마지막 **성공한** fsync 이후"로 믿었다.
- 버리는 이유(Ts'o, LWN): I/O 오류의 가장 흔한 원인은 USB 장치를 잘못 뽑는 것이다. 그 장치로 가던 dirty 페이지를 계속 쥐면 시스템 메모리가 바닥날 수 있다.

### 5. checkpointer와 errseq_t

- 두 번째 구멍: fsync를 하는 checkpointer는 파일을 늘 열어 두지 않고 fsync 직전에 연다. 4.13의 errseq_t는 "열기 **전**에 난 오류는 관심 없다"고 가정해, 그 fd에 오류를 보고하지 않았다. 그래서 fsync가 성공했다(LWN).
- 2018-04 수정(커밋 b4678df184b3 "errseq: Always report a writeback error once", 4.17 주기 병합, stable Cc): 아직 어느 fd에도 보고되지 않은 오류는 나중에 연 fd에도 한 번 보고한다. 커밋은 이전 동작을 PostgreSQL에 대한 회귀라고 적었다.
- 여전히 남은 것
  - 오류는 **한 번만** 보고된다. 재시도는 여전히 안전하지 않다.
  - 버퍼는 여전히 버려진다. 다시 읽으면 옛 내용이 나올 수 있다.
  - 다시 열기 전에 inode가 캐시에서 밀려나면 오류를 잃을 수 있다(병합 메시지, PostgreSQL 위키).

### 6. PostgreSQL의 대응과 내 앱

- PostgreSQL
  - 커밋 "PANIC on fsync() failure"(Craig Ringer 작성, Thomas Munro 수정·커밋, 2018-11-19): 데이터 파일 fsync 실패에 PANIC한다. 남은 유일한 사본은 WAL이므로 재시작해 WAL에서 다시 쓴다. WAL 파일에는 이미 그렇게 하고 있었다.
  - 설정 `data_sync_retry`(기본 off): 커널이 dirty 버퍼를 버리지 않는다고 확신할 때만 켠다.
  - 지원 중인 모든 판에 백포트. 11.2 등 릴리스(2019-02-14) 노트: "fsync() 실패 뒤 재시도 대신 panic".
- 내 앱
  - 할 일: fsync 실패를 "그 파일의 최근 쓰기를 잃었다"로 본다. 로그·복제본에서 다시 만들거나 멈춘다. 커널 로그의 I/O 오류를 경보로 올린다.
  - 하지 말 일: fsync를 재시도하고 성공했다고 계속 진행하기. fsync할 fd를 쓰기 뒤에 새로 열어 쓰기.

### 7. 윤초 CPU 폭주

- 커밋 "timekeeping: Fix leapsecond triggered load spike issue"(John Stultz)
  - 윤초 때 타임키핑 코드가 hrtimer 서브시스템 갱신(`clock_was_set()`)을 빠뜨렸다.
  - 그래서 벽시계와 hrtimer의 CLOCK_REALTIME 기준이 1초 어긋났다. 삽입이면 1초 **일찍**, 삭제면 1초 늦게 만료된다.
  - 다른 경로로 갱신될 때까지 이 차이가 영원히 남는다.
- ``date -s "`date`"``: 시계를 설정하면 `clock_was_set()`이 불려 hrtimer 기준이 갱신된다(같은 커밋).
- 수정: 윤초 때 `update_wall_time()`에서 갱신을 요청하되, 하드 인터럽트 문맥에서는 모든 CPU에 함수 호출을 못 보내므로 softirq로 미룬다(`clock_was_set_delayed()`). v3.5-rc7(2012-07-14)에 포함.
- 추론이 섞인 부분: "futex 기반 시간 제한 대기가 CLOCK_REALTIME 절대 기한을 쓰고, 기한이 1초 안쪽이면 즉시 만료되어 재시도 루프가 돈다"는 연결이다. Red Hat은 "futex를 많이 쓰는 앱, 특히 java"라고만 적는다. Java·MySQL의 정확한 코드 경로는 확인하지 못했다.

### 8. 윤초 사건의 예방 원칙

- 간격·기한 측정에는 벽시계(CLOCK_REALTIME)가 아니라 **단조 시계**(CLOCK_MONOTONIC)를 쓴다. 조건 변수는 `pthread_condattr_setclock(CLOCK_MONOTONIC)`이나 `pthread_cond_clockwait`를 쓴다(17번 시나리오 5).
- 시간 제한 대기가 즉시 끝나는 루프에는 상한·백오프를 둔다. 헛도는 것이 지표로 보이게 한다.
- "많은 서버가 같은 시각에 동시에": 배포·트래픽이 아니라 **공통 외부 사건**(시계 이벤트, 인증서 만료, 설정 일괄 배포)을 먼저 의심한다.

### 9. ext4 0바이트 파일

```text
  ext3 data=ordered : 5초마다 저널 커밋, 커밋 전에 바뀐 데이터 블록을 먼저 기록
                      -> 결과적으로 "5초면 데이터도 디스크에" (설계의 부산물, 약속 아님)
  ext4 지연 할당     : 데이터 블록이 아직 할당되지 않음 -> 다음 저널 커밋에 딸려 가지 않음
                      -> 크기 0·rename 같은 메타데이터가 먼저 영속
                      -> 데이터는 writeback 때(기본 설정에서 1분 가까이)
  크래시가 그 사이에 나면 -> 이름은 새것, 내용은 0바이트
```

- Ts'o의 세 패턴
  - (1) `open(O_TRUNC)` → `write` → `close`: 위험.
  - (2) 새 파일에 `write` → `close` → `rename`: 위험.
  - (3) 새 파일에 `write` → **`fsync`(오류 확인)** → `close` → `rename`: 이것만 데이터 손실이 없음을 보장한다.
- 오늘의 권장 순서는 여기에 **디렉터리 fsync**까지 더한다(24번).
- 2.6.30의 `auto_da_alloc`은 (1)(2)를 감지해 rename 커밋 전에 데이터를 내보내는 완화책이다. 보장이 아니다(23번).
