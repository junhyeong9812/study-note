## 정답

### 1. load/store 락의 실패

```text
  시간 ->
  스레드 A:  flag 읽음(0) ─┐                 flag = 1   [임계 구역]
  스레드 B:                └ flag 읽음(0)     flag = 1   [임계 구역]
                             ^ 둘 다 "비었다"를 봤다
```

- "flag가 0인지 확인"과 "flag를 1로 쓰기" 사이에 다른 스레드가 끼어들었다(OSTEP 28.6).
- 그래서 **확인과 쓰기가 한 동작**이어야 한다. 하드웨어가 주는 test-and-set(x86 `xchg`)·CAS·fetch-and-add가 그 한 동작이다.

### 2. test-and-set 스핀락 평가

- **상호 배제**: 된다. 원자 교환으로 0→1을 성공한 스레드 하나만 들어간다.
- **공정성**: 보장 없다. 풀릴 때마다 누가 먼저 교환에 성공할지는 운이다. 한 스레드가 계속 질 수 있다(기아)(OSTEP 28.8).
- **성능**
  - CPU 하나: 락 주인이 임계 구역 도중 선점되면, 스케줄러가 돌리는 다른 스레드들이 각자 타임 슬라이스를 통째로 헛돈다. 주인은 그동안 실행되지 못해 락을 풀지도 못한다.
  - 여러 CPU(스레드 수 ≈ CPU 수): 주인은 다른 CPU에서 계속 실행 중이다. 임계 구역이 짧으면 금방 풀리므로 잠깐 도는 것이 잠들고 깨는 것보다 싸다.

### 3. 티켓 락

- X는 fetch-and-add로 `ticket`의 옛값 **5**를 받는다(`myturn = 5`). `ticket`은 6이 된다.
- 지금 `turn = 3`이다. 3번(현재 주인)과 4번이 나가야 5가 된다. 즉 `unlock()`이 **2번** 더 일어나야 X가 들어간다.
- 공정한 이유: 번호표를 뽑은 순서대로 들어간다(FIFO). 뒤에 온 스레드가 앞지를 수 없으므로, 번호를 받은 스레드는 앞사람들이 다 나가면 반드시 들어간다(OSTEP 28.11). test-and-set은 순서 정보가 없어 이런 보장이 없다.
- 다만 기다리는 동안은 여전히 돈다. 공정성과 CPU 낭비는 별개의 문제다.

### 4. futex의 시스템 콜과 비교 인자

- 경합이 없으면 **0번**이다. 잠그기는 CAS(0→1), 풀기는 원자 교환(1→0, 옛값이 1이면 깨울 대기자 없음)으로 유저 공간에서 끝난다. 커널은 대기자가 있을 때만 끼어든다(futex(7)).
  - 로컬 재현(예시, 리눅스 7.0): 1스레드로 10만 번 lock/unlock했을 때 futex 호출은 1번(스레드 join)이었다. 4스레드 경합에서는 2,910번이었다.
- 비교가 필요한 이유 — 비교가 없다면:

```text
  스레드 B                                  스레드 A (주인)
  word 읽음: 잠김 → "자야겠다"
                                           unlock: word = 0, FUTEX_WAKE (대기자 없음 → 아무도 안 깨움)
  FUTEX_WAIT 진입 → 잠듦
  → 락은 풀렸는데 B는 깨워 줄 사람 없이 계속 잔다 (lost wake-up)
```

- `FUTEX_WAIT(uaddr, val)`는 "`*uaddr`가 아직 `val`이면 잠든다"를 커널 안에서 **원자적으로** 한다. 값이 이미 바뀌었으면 `EAGAIN`으로 곧바로 돌아온다. man 페이지는 이 비교의 목적을 "lost wake-up 방지"라고 적는다(FUTEX_WAIT(2const)).

### 5. glibc 뮤텍스 상태 변화

| 단계 | word | 시스템 콜 |
|---|---|---|
| 처음 | 0 | — |
| A `lock()` | CAS 0→1 성공 → **1** | 없음 |
| B `lock()` | CAS 실패 → `exchange(word, 2)`가 1을 돌려줌(아직 잠김) → **2** | `futex_wait(word, 2)` — 값이 2이므로 잠든다 |
| A `unlock()` | 원자적으로 0으로 바꾸며 옛값 2를 확인 → **0** | 옛값이 1보다 크니 `futex_wake(word, 1)` |
| B 깨어남 | `exchange(word, 2)`가 0을 돌려줌 → 획득, word는 **2** | 없음 |

- B는 획득 후에도 word를 2로 둔다. 다른 대기자가 있는지 모르기 때문이다. 그래서 B의 다음 `unlock()`은 대기자가 없어도 `futex_wake`를 한 번 부를 수 있다. 정확성을 위해 가끔 헛깨우기를 감수하는 설계다(glibc `lowlevellock.h`의 ">1: 대기자가 있을 수 있음", `lowlevellock.c` `__lll_lock_wait`).
- unlock은 `atomic_exchange_release(word, 0)`으로 "0으로 바꾸며 옛값 확인"을 한 동작으로 하고, 옛값이 1보다 크면 깨운다(glibc `lowlevellock.h` `__lll_unlock`, 2026-09 master 기준).

### 6. 스레드를 늘렸을 때 처리량

로컬 재현(예시, 리눅스 7.0, 24 CPU, 스레드당 20만 회 증가):

| 스레드 | test-and-set 처리량 | pthread_mutex 처리량 |
|---|---|---|
| 1 | 약 6,700만/s | 약 4,000만/s |
| 4 | 약 700만/s | 약 960만/s |
| 24 | 약 130만/s | 약 600만/s |

- 둘 다 **줄어든다**. 임계 구역은 한 번에 하나만 실행되는 직렬 구간이다. 스레드를 늘려도 빨라지지 않고, 락 변수의 캐시 라인이 코어 사이를 오가는 비용만 커진다.
- 스핀락이 더 크게 무너진다(약 50분의 1). 기다리는 스레드가 모두 같은 변수에 원자 교환을 계속 시도해 캐시 라인 경쟁을 키운다. 24스레드에서 CPU 시간은 67초였다(뮤텍스 14초).
- 뮤텍스는 기다리는 스레드를 재우므로 경쟁자 수가 줄어 덜 무너진다.

### 7. 스핀락 과점유 vs 뮤텍스 경합 구분

| 관측 | 스핀락 과점유 | 뮤텍스 경합 |
|---|---|---|
| `ps -L -o stat,wchan` | 대부분 `R`, wchan 없음 | 다수가 `S` + `futex_do_wait`(7.0 기준 이름) |
| `/proc/<pid>/status` ctxt | `voluntary_ctxt_switches` 거의 정지, `nonvoluntary`만 증가 | `voluntary`가 빠르게 증가 |
| `strace -f -c -e trace=futex` | futex 호출이 거의 없다 | futex 호출이 많다(`FUTEX_WAIT`·`FUTEX_WAKE`, `EAGAIN` 섞임) |
| user/sys 시간 | 거의 전부 user | futex 시스템 콜 때문에 sys 비중이 크다 |

- 로컬 재현 예(예시, 리눅스 7.0, `getrusage`로 잰 값)
  - 4스레드 × 100만 회: 뮤텍스는 voluntary 전환 약 10만 회, test-and-set 스핀은 1회였다.
  - 8스레드 × 20만 회: 스핀은 user 2.92초·sys 0초, 뮤텍스는 user 0.38초·sys 1.27초였다.

### 8. 유저 공간 스핀락의 사용 조건

- `pthread_spin_init(3)` NOTES
  - 실시간 정책(`SCHED_FIFO`, 또는 `SCHED_RR`)과 함께 쓰라고 한다.
  - `SCHED_OTHER`에서 쓰면 설계 실수일 가능성이 높다고 적는다. 락을 쥔 스레드가 CPU에서 내려오면, 다른 스레드들이 주인이 다시 스케줄될 때까지 헛돌기 때문이다.
  - 유저 공간 스핀락은 일반 해법이 아니며, 우선순위 역전과 끝없는 스핀에 취약하다고 적는다.
  - 스핀락으로 교착이 나면 해당 스레드들은 CPU를 쓰며 영원히 돈다.
- 현실적인 조건: 임계 구역이 아주 짧고, 스레드 수 ≤ 코어 수이며, 스레드를 코어에 고정하고, 우선순위를 통제할 수 있을 때다. 커널은 선점·인터럽트를 직접 다룰 수 있어 스핀락을 널리 쓰지만, 유저 공간은 스케줄러를 통제하지 못한다.

### 9. Java 공정 락

- 얻는 것: 경합 중 가장 오래 기다린 스레드에 우선권을 준다. 획득 시간의 편차가 작아지고 기아가 없다.
- 잃는 것: 처리량. 문서는 공정 락을 쓰는 프로그램이 "종종 훨씬 느릴 수 있다"고 적는다. 또 락의 공정성이 스레드 스케줄링의 공정성까지 보장하지는 않는다(Java SE `ReentrantLock` 문서).
- 시간 제한 없는 `tryLock()`은 공정 설정을 무시한다. 비어 있으면 대기자가 있어도 바로 잡는다(barging). 공정성을 지키려면 `tryLock(0, TimeUnit.SECONDS)`를 쓴다(같은 문서).
- 형식: `lock.lock(); try { … } finally { lock.unlock(); }`. 예외 경로에서 unlock을 빠뜨리면 락이 계속 잡혀 있어 **다른 스레드의** 호출이 영원히 기다린다(빠뜨린 스레드 자신은 재진입으로 통과한다).
