## 정답

### 1. 네 가지 분류

```text
  종류       계기                       동기/비동기   돌아가는 곳                 예
  인터럽트   CPU 밖 장치                  비동기        다음 명령                   타이머, 디스크 완료, 패킷 도착
  트랩       명령이 일부러                동기          다음 명령                   syscall, int3
  폴트       명령 실행 중 오류(복구 가능)  동기          같은 명령 재실행 또는 종료    페이지 폴트
  어보트     복구 불가 오류               동기          돌아가지 않음                머신 체크
```

- 기준은 CS:APP 3판 8.1이다. 문헌마다 개별 예의 분류는 조금 다를 수 있다(예: 모르는 명령).

### 2. 폴트가 같은 명령으로 돌아가는 이유

- 폴트를 낸 명령은 **아직 끝나지 못했다**. 예: `load`가 읽을 페이지가 메모리에 없었다.
- 핸들러가 원인을 고친다. 페이지를 메모리에 올리고 페이지 테이블을 채운다.
- 그 뒤 **같은 명령을 다시** 실행하면 이번엔 성공한다. 다음 명령으로 가면 `load`의 결과가 없는 채로 진행하게 된다.
- 고칠 수 없으면(잘못된 주소) 돌아가지 않고 시그널로 프로세스를 끝낸다.

### 3. 예외 번호와 exit code

- (a) `10/0`(정수): **#DE(0)** → SIGFPE → **136**.
- (b) `int3`: **#BP(3)** → SIGTRAP → **133**.
- (c) NULL 역참조: **#PF(14)** → 매핑 없는 주소라 SIGSEGV → **139**.
- (d) `1.0/0.0`(부동소수): 기본 설정에서 **트랩·시그널 없이 inf**가 나오고 계속 실행한다(로컬: exit 0). 대신 `FE_DIVBYZERO` 플래그가 선다(fenv(3)). `0.0/0.0`이면 NaN이다.
- 전부 로컬 재현(리눅스 7.0)으로 확인했다. exit code = 128 + 시그널 번호.

### 4. 페이지 폴트 = 버그?

- 아니다. 대부분은 **요구 페이징**의 정상 동작이다.
- **minor fault**: 디스크 I/O 없이 해결한다. 익명 메모리 첫 쓰기(0으로 채운 페이지를 줌), 이미 페이지 캐시에 있는 파일 페이지.
- **major fault**: 보통 디스크에서 읽어 와야 한다. 캐시에 없는 `mmap` 파일, 스왑된 페이지. 스레드가 I/O 동안 잠든다(zswap에서 복원한 경우처럼 디스크 없이 major로 세는 경우도 있다).
- **SIGSEGV로 끝나는 폴트**: 주소가 프로세스의 어떤 영역(VMA)에도 없거나, 권한(쓰기 금지 등)을 어겼다. 이것이 버그의 대표다.
  - 다른 모양도 있다. 파일 매핑에서 파일 끝을 넘은 페이지를 건드리면 `SIGBUS`다(mmap(2)).

### 5. 폴트 횟수 계산

- 64MB / 4KB = **16384** 페이지 → 첫 쓰기에 약 16384번 minor fault. 로컬 재현 16397번(나머지는 프로그램의 다른 폴트).
- 다시 돌면 **0번**. 이미 매핑되어 있다(그사이 스왑 아웃·`fork` 뒤 COW가 없었다면).
- 캐시에 있는 파일은 **fault-around** 때문에 줄어든다. 커널이 한 폴트에 주변 페이지를 함께 매핑한다. 기본 64KB = 16장 → 16384 / 16 = **1024**번(mm/memory.c `fault_around_pages`). 로컬 재현도 1024번이었다.
- 캐시를 비운 파일이면 major fault 16384번이었다(로컬, `MADV_RANDOM`으로 미리 읽기를 끈 상태).

### 6. syscall과 IDT

- (FRED가 꺼진 기존 방식 기준) 64비트 `syscall` 명령은 **IDT를 거치지 않는다**. CPU가 MSR에 등록된 진입 주소(`entry_SYSCALL_64`)로 바로 간다(entry_64.S 주석).
- `int 0x80`은 IDT의 0x80번 항목(`IA32_SYSCALL_VECTOR`)을 거친다. 32비트 호환 경로다(idt.c).
- FRED가 켜지면 둘 다 FRED 진입점으로 들어가 이벤트 종류로 나뉜다. `int 0x80`도 IDT를 거치지 않는다(entry_fred.c `fred_intx`).
- 어느 쪽이든 분류로는 "트랩"(일부러 들어가는 동기 사건)이다.

### 7. NIC 인터럽트 흐름

```text
  NIC 패킷 도착 -> 인터럽트 컨트롤러 -> 어떤 코어
     그 코어: 현재 명령을 마침 -> 커널 모드 -> IDT의 핸들러
       상반부(hard IRQ): 장치 확인, 추가 인터럽트 잠시 끔, NAPI poll 예약   (짧게)
       하반부(softirq NET_RX): 링에서 패킷을 꺼내 네트워크 스택으로          (길게)
     -> 원래 프로그램의 다음 명령
```

- 나누는 이유: 상반부가 도는 동안 같은 인터럽트가 막혀 있을 수 있다. 오래 붙잡으면 다른 사건을 놓치거나 늦게 받는다. 급한 것만 즉시 하고 무거운 처리는 미룬다.
- 자세한 수신 경로는 network/25-kernel-network-stack.

### 8. 배포 직후 p99 급등, CPU 낮음

- 의심: **major fault**. 코드·데이터 페이지가 아직 메모리(페이지 캐시)에 없어서, 요청마다 디스크를 기다린다.
- 확인
  - `pidstat -r -p <pid> 1`의 `majflt/s`, `/proc/vmstat`의 `pgmajfault` 증가량.
  - `vmstat 1`의 `b`·`wa`(스왑 쓰면 `si`), `ps`의 `D` 상태 스레드.
- 대처
  - 워밍업 트래픽 뒤에 실트래픽을 받는다.
  - 메모리를 충분히 두고 스왑을 확인한다.
  - 큰 매핑 파일은 `MADV_WILLNEED`, 꼭 필요한 영역은 `mlock`. JVM은 `-XX:+AlwaysPreTouch`로 힙의 첫 접근 폴트를 시작 시점으로 옮길 수 있다(이것은 minor fault 대책이다).

### 9. 한 코어만 %soft 90%

- 네트워크 인터럽트와 그 뒤의 softirq 처리가 **한 코어에 몰렸다**. 그 코어가 포화되어 처리량이 막힌다. 다른 코어는 놀고 있어 전체 평균은 낮다.
- 볼 곳
  - `cat /proc/interrupts`를 두 번 떠서 NIC 큐 줄의 증가가 어느 CPU 칸에 몰리는지.
  - NIC 큐 개수, `/proc/irq/<n>/smp_affinity`, `irqbalance` 동작 여부.
- 대처: 다중 큐 + IRQ를 여러 코어로 분산, 필요하면 RPS(network/25). 설정 변경은 root 권한이 필요하다.
