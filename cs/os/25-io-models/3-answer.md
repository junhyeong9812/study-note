## 정답

### 1. read 한 번의 두 단계

```text
  앱 스레드   read() ------------------------------------------------> 반환
  커널        [① 준비 대기]                 [② 복사]
              소켓: 패킷이 수신 버퍼에 올 때까지    커널 버퍼 -> 사용자 버퍼 (CPU memcpy)
              파일: 페이지 캐시에 없으면 디스크 읽기까지
```

- ①은 길고 예측할 수 없다(네트워크·디스크).
- ②는 짧지만 CPU가 한다.

### 2. 다섯 모델 표

| 모델 | ① 준비 대기 동안 | ② 복사 동안 | 완료를 아는 방법 |
|---|---|---|---|
| 블로킹 | `read()` 안에서 잠듦 | `read()` 안 | `read()` 반환 |
| 논블로킹 | `EAGAIN` 받고 재시도(또는 다른 일) | `read()` 안 | `read()` 반환 |
| I/O 다중화 | `select`/`poll`/`epoll_wait`에서 잠듦 | `read()` 안 | 준비 알림 → `read()` |
| 시그널 구동 | 다른 일, `SIGIO` 대기 | `read()` 안 | `SIGIO` → `read()` |
| 비동기 | 다른 일 | 다른 일(커널이 복사) | 완료 알림 |

- POSIX 3.371은 동기 I/O를 "요청한 스레드를 I/O가 끝날 때까지 막는 연산"으로 정의한다.
- 앞의 넷은 ②에서 `read()`가 스레드를 잡으므로 모두 **동기 I/O**다. 비동기(3.31)는 다섯 번째뿐이다.

### 3. 두 축은 다른 것의 성질이다

- 블로킹/논블로킹: **open file description의 속성**이다(POSIX 3.48·3.226). "못 끝내면 기다리나, 바로 돌아오나."
- 동기/비동기: **I/O 연산의 성질**이다(3.371·3.31). "요청한 스레드가 완료까지 막히나."
- epoll + 논블로킹 소켓은 ①에서 스레드를 묶지 않지만, ②는 여전히 내 `read()`가 한다. 그래서 정의상 동기 I/O다. 정확한 이름은 "논블로킹 I/O + 준비 알림(다중화)"이다.
- 실무에서 "비동기"를 느슨하게 쓰는 것은 흔하다. 다만 io_uring·IOCP 같은 완료 기반과 구분해야 설계가 헷갈리지 않는다(36번 리액터 vs 프로액터).

### 4. 논블로킹 read의 반환값

- 데이터가 없으면 `-1`, errno는 `EAGAIN` 또는 `EWOULDBLOCK`이다(read(2)).
- 소켓에 대해 POSIX는 둘 중 아무거나 돌려도 되고, 두 상수가 같을 필요도 없다. 그래서 둘 다 검사한다. 리눅스 x86-64에서는 둘 다 11이었다(로컬 재현).
- `0`은 EOF다. 상대가 쓰기 쪽을 닫았다. 연결을 정리해야 한다.

### 5. 정규 파일과 논블로킹

- open(2): `O_NONBLOCK`은 정규 파일·블록 장치에 효과가 없다. 장치 작업이 필요하면 (잠깐) 블록된다.
- `poll()`은 정규 파일을 항상 "읽기 가능"으로 알린다. 로컬 재현에서도 즉시 `POLLIN`이었다.
- epoll에는 넣을 수조차 없다. `epoll_ctl`이 `EPERM`을 돌려준다(epoll_ctl(2)).
- 그래서 libuv(Node)는 파일 시스템 작업을 **스레드 풀**에서 블로킹으로 돌리고, 끝나면 이벤트 루프에 알린다(libuv 설계 문서). libuv 1.45~1.48은 리눅스에서 일부 파일 작업에 io_uring도 썼고, 1.49부터는 그 io_uring 경로가 기본 꺼짐이다(libuv ChangeLog).

### 6. 리눅스 비동기 파일 I/O 세 가지

- **POSIX AIO**(`aio_read`): glibc가 사용자 공간 스레드로 구현한다. 스레드 유지 비용이 크고 확장이 나쁘다(aio(7)).
- **native aio**(`io_submit`): `O_DIRECT`(캐시 우회)에서만 제대로 비동기다. 버퍼드 I/O에서는 동기처럼 동작하고, 메타데이터가 필요하면 제출도 막힐 수 있다(Axboe 2019).
- **io_uring**(리눅스 5.1+): 앱과 커널이 공유하는 제출 링·완료 링으로 버퍼드 파일·소켓 I/O를 모두 비동기로 처리한다(34번).

### 7. CPU 100% + %sy 높음

- 예상: `strace`에 `read(fd, ...) = -1 EAGAIN (Resource temporarily unavailable)`가 초당 수십만 번 찍힌다.
- 원인: 논블로킹 fd에서 `EAGAIN`을 받자마자 다시 `read()`했다. 기다리는 단계가 없어 시스템 콜만 반복한다. 그래서 커널 시간(`%sy`)이 크다.
- 로컬 재현(예시, 리눅스 7.0): 1초 재시도 루프에서 `read`가 약 20만~40만 번 불렸고, 같은 1초를 `poll()`로 기다리면 CPU 시간이 0이었다.
- 고치기: `EAGAIN`이면 epoll·Selector에 관심을 등록하고 준비 알림까지 잠든다(26번).

### 8. 워커 스레드가 서서히 줄어든다

- 보기
  - `jstack <pid>`: 여러 스레드가 소켓 읽기(`socketRead0` 계열) 스택에 멈춰 있다.
  - `ps -L -o tid,stat,wchan:32 -p <pid>`: 해당 스레드들이 `S` 상태, `wchan`이 소켓 대기 함수다.
- 의심: 하류 서버·DB가 응답 없이 사라진 **half-open 연결**에서 타임아웃 없는 블로킹 read를 하고 있다.
- 막기
  - 모든 블로킹 소켓에 connect·read 타임아웃을 건다(`Socket.setSoTimeout`, 드라이버의 socketTimeout).
  - 연결 수준 감지는 keepalive·`TCP_USER_TIMEOUT`(network/21).
  - 느린 하류를 전용 풀로 격리한다(bulkhead, 36번).

### 9. readFileSync와 "모든" 요청의 정지

- Node의 JS 코드는 이벤트 루프 **한 스레드**에서 돈다(libuv: 루프는 스레드 안전하지 않고 한 스레드에서 돈다).
- `readFileSync`는 그 스레드에서 블로킹 `read`를 한다. 파일이 페이지 캐시에 없거나 디스크가 느리면 수백 ms를 기다린다.
- 그동안 다른 연결의 준비 알림·타이머·콜백은 아무도 처리하지 못한다. 그래서 그 순간 들어와 있던 **모든** 요청이 같이 늦는다(27번).
- 고치기: `fs.promises.readFile`·`fs.readFile`로 바꿔 스레드 풀(libuv 버전에 따라 io_uring)에 맡긴다. 시작 시 한 번 읽는 설정 파일 정도만 동기 API를 허용한다.
