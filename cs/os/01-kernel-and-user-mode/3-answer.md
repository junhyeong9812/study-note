## 정답

### 1. 제한된 직접 실행

- **직접 실행**: 명령마다 OS가 흉내 내면 명령 하나에 여러 명령이 더 든다. 그래서 프로그램 명령은 CPU가 그대로 실행한다.
- **제한**: 직접 실행만으로는 OS가 "그냥 라이브러리"가 된다(OSTEP 6.1). 그래서 하드웨어에 두 가지를 둔다.
  - 권한 모드: 유저 모드에서는 특권 명령·커널 메모리 접근을 CPU가 거부한다.
  - 타이머 인터럽트: 프로그램이 협조하지 않아도 커널이 주기적으로 CPU를 되찾는다.
- 위험한 일(I/O, 메모리 설정)은 시스템 콜로 커널에 부탁해야 한다.

### 2. 세 개의 문

```text
  유저 모드
     |  (1) 시스템 콜  — 프로그램이 원해서 (syscall 명령)
     |  (2) 예외       — 방금 실행한 명령 때문에 (0으로 나눔, 페이지 폴트, 특권 명령)
     |  (3) 인터럽트   — CPU 밖 장치 때문에 (타이머, 디스크, NIC)
     v
  커널 모드 — 트랩 테이블에 등록된 핸들러로만 진입
```

- 공통점: 셋 다 **커널이 미리 정한 입구(핸들러)** 로만 들어간다. 유저가 커널 코드의 임의 위치로 점프할 방법은 없다.
- 돌아올 때는 return-from-trap(x86-64 리눅스는 `sysret` 또는 `iret`, FRED가 켜져 있으면 `eretu`)으로 유저 모드가 된다.

### 3. 트랩 테이블 등록이 특권이어야 하는 이유

- 트랩 테이블은 "모드가 바뀔 때 어디로 점프하나"를 정한다.
- 유저가 이것을 바꿀 수 있으면, 자기 코드를 핸들러로 등록한다. 다음 시스템 콜·인터럽트 때 **자기 코드가 커널 모드로 실행**된다. 보호가 통째로 무너진다(OSTEP 6.2 "Could you take over the machine?").
- 그래서 등록 명령(x86의 `lidt`, syscall 진입 주소 MSR 쓰기 `wrmsr`)은 ring 0에서만 된다.

### 4. 무한 루프

- **협력형 OS**: 프로그램이 시스템 콜을 부르거나 양보해야만 OS가 CPU를 되찾는다. 무한 루프면 OS가 다시 돌 기회가 없다. 해결책은 재부팅뿐이었다(OSTEP 6.3).
- **현대 OS**: 타이머 인터럽트가 울린다(리눅스 `nohz_full` CPU처럼 태스크가 하나뿐이면 틱을 줄이는 설정도 있다). 그때 커널 핸들러가 돌고, 스케줄러가 다른 프로세스로 바꿀 수 있다. 일반 정책(`SCHED_OTHER`)의 무한 루프 프로세스는 CPU 한 개를 많이 쓸 뿐, 시스템을 멈추지 못한다.
  - 예외: 높은 우선순위 실시간 정책(`SCHED_FIFO`) 루프는 일반 태스크를 굶길 수 있다. 리눅스 6.11까지 기본값은 실시간 태스크에 CPU 시간의 95%까지만 준다(sched(7) `sched_rt_runtime_us`=950000). 6.12부터는 fair 데드라인 서버가 일반 태스크에 1초당 50 ms를 보장한다(08번).

### 5. `hlt`와 `ud2`

- `hlt`
  - 유저 모드(ring 3)라 CPU가 **#GP(벡터 13, 일반 보호 예외)** 를 낸다.
  - 커널은 유저 모드 #GP에 `SIGSEGV`를 보낸다(traps.c `gp_user_force_sig_segv`). `si_code`는 `SI_KERNEL`(128).
  - 셸 exit code = 128 + 11 = **139**.
- `ud2`
  - CPU가 정의되지 않은 명령으로 보고 **#UD(벡터 6)** 를 낸다.
  - 커널은 `SIGILL`(`ILL_ILLOPN`)을 보낸다. exit code = 128 + 4 = **132**.
- 로컬 재현(리눅스 7.0)에서 둘 다 확인했다. `cli`·`outb`·`mov %cr3`도 `hlt`와 같이 SIGSEGV 139였다.

### 6. 항상 즉시 죽나? — 아니다

- **UMIP 흉내**: `sgdt`·`sidt`·`smsw`는 UMIP가 켜진 CPU(커널이 `CR4.UMIP` 설정)에서 #GP가 나지만, 리눅스가 가로채 가짜 값을 돌려주고 프로세스를 계속 돌린다(traps.c `fixup_umip_exception`). 로컬에서 `sgdt`가 base=0xfffffffffffe0000, limit=0을 받고 살아남았다.
- **I/O 권한 부여**: `ioperm(2)`/`iopl(2)`로 권한(`CAP_SYS_RAWIO`)을 받은 프로세스는 허락된 포트에 `in`/`out`을 쓸 수 있다. 여전히 ring 3이다.
- 또 프로세스가 `SIGSEGV` 핸들러를 달았다면 "즉시 종료"가 아니라 핸들러가 먼저 돈다(06번).

### 7. root와 커널 모드

- root 프로세스도 **유저 모드(ring 3)** 다.
  - root(uid 0)와 capability는 커널 코드가 시스템 콜 안에서 확인하는 **소프트웨어 신원**이다.
  - ring은 CPU가 명령마다 확인하는 **하드웨어 모드**다. CPU는 uid를 모른다.
- `EPERM`/`EACCES`: 시스템 콜 안에서 커널이 uid·capability·seccomp를 보고 거부했다. 소프트웨어 층.
- `SIGSEGV`(특권 명령·커널 주소): CPU가 예외를 냈고 커널이 시그널로 바꿨다. 하드웨어 층.
- 그래서 특권 명령 크래시는 root나 privileged 컨테이너로 바꿔도 안 고쳐진다.

### 8. 특정 노드에서만 exit 132

- 132 = 128 + 4 → bash에서 **SIGILL** 종료로 읽는다. 대개 CPU가 모르는 명령(#UD)을 만났다는 뜻이다.
  - 단 프로그램이 `exit(132)`했거나 누가 `kill -ILL`을 보내도 같은 값이 나온다. 코어 덤프·`dmesg`의 trap 줄, `si_code`로 CPU 예외인지 확인한다.
- 의심: 빌드 머신의 새 명령(예: `-march=native`로 들어간 AVX-512)이 그 노드 CPU에 없다.
- 확인
  - 두 노드에서 `grep -o -w avx512f /proc/cpuinfo`처럼 CPU 플래그를 비교한다.
  - 코어 덤프를 `gdb`로 열어 `x/i $pc`로 죽은 명령을 본다.
- 대처: 최소 대상 CPU에 맞춰 빌드하거나, 실행 시 CPU 기능을 보고 분기한다.
- 권한 문제가 아니다. 특권 위반은 x86 리눅스에서 대개 SIGSEGV(139)다.

### 9. 프로파일러에 안 보이는 CPU

- 애플리케이션 프로파일러는 주로 **유저 모드** 코드를 본다. 시간이 커널 모드에서 쓰이면 뜨거운 함수가 안 보일 수 있다.
- 먼저 user/sys 비율을 본다.
  - `vmstat 1`의 `us`·`sy`, `pidstat -u -p <pid> 1`의 `%usr`·`%system`.
  - 한 번 실행하는 프로그램이면 `/usr/bin/time`의 user/sys.
- `sy`가 크면 커널에 자주 들어간다. `strace -c -p <pid>`로 시스템 콜 분포를 보고(02번, 운영 중 부하 주의), `pidstat -r`로 페이지 폴트를 본다(03번).
