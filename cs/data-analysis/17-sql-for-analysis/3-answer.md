# data-analysis/17-sql-for-analysis — 정답

## 정답

### 1. grain과 팬아웃

- grain: 결과 테이블의 한 행이 무엇 하나를 뜻하는지(사용자 1명, 주문 1건, 품목 1개).
- 세 테이블 조인 뒤의 grain은 "사용자 × 주문 × 품목"이다. 주문 없는 사용자는 1행, 주문이 있으면 주문의 품목 수만큼 행이 생긴다.
- 분모는 사용자 수(사용자 grain)인데 분자를 품목 grain의 행 수로 세면 단위가 어긋난다. 한 사용자가 여러 행이 되므로 분자가 사용자 수를 넘을 수 있다.

### 2. 실험의 팬아웃 수치

- 조인 행 716개 중 주문이 붙은 행 488개 ÷ 400명 = 1.22(122%).
- 맞는 전환율: `count(DISTINCT o.user_id) / count(DISTINCT u.user_id)` = 172/400 = 0.43.
- 매출: 품목 조인 뒤 `sum(amount)` 26,575,000 vs 주문 테이블 단독 13,635,000 → 약 1.95배.

### 3. 처방

- 선집계 후 조인: 주문을 사용자 단위로 먼저 `GROUP BY user_id`해 금액·건수를 만든 뒤 users에 붙인다.
- `count(DISTINCT 키)`: 세는 대상의 키(사용자 ID, 주문 ID)로 중복을 제거해 센다.
- `sum(DISTINCT amount)`는 "값"의 중복을 지운다. 금액이 같은 서로 다른 주문 두 건이 하나로 합쳐져 매출이 줄어든다. 키가 아니라 값으로 중복을 판단하므로 틀린다.

### 4. 코호트 미성숙 칸

- 0으로 세면 표의 오른쪽 아래(최근 코호트 × 먼 주차)가 0%·한 자릿수가 되어 "최근 코호트 리텐션 급락"처럼 보인다.
- 09-07 코호트 w3: 0으로 센 판(3a)은 6%(분모 88명 전원), 지난 사용자만 분모로 한 판(3b)은 5%(분모 41명). 나머지 47명은 관측 끝(10-08 00:00 KST)까지 w3가 끝나지 않았다.

### 5. 세션화와 연속 일수

```text
  시각     22:31  22:54  23:00 | 12:52(09-11)  12:58  13:05
  간격       —    22분    6분  | 37시간 52분     6분    7분
  ① 경계 표시 1      0      0  |      1          0      0     (lag 없음 또는 간격 > 30분이면 1)
  ② 누적 합   1      1      1  |      2          2      2     = 세션 번호
```

- 연속 방문일: 방문 날짜를 정렬해 `row_number()`를 매기고 `날짜 − 행 번호`를 계산한다. 연속한 날짜는 같은 값이 나와 그 값으로 묶으면 연속 구간이 된다.

### 6. 세션당 이벤트 수의 두 평균

- (b)가 크다. 크기 k인 세션은 이벤트 행이 k개라 평균에 k번 들어간다(크기 가중). 큰 세션이 과대 대표된다.
- 실험: (a) 4,680 ÷ 1,368 = 3.42, (b) 3.69.

### 7. 백분위 계산

- cont: 위치 = (n−1)×0.9 = 3.6 → 4번째 값(40, 0부터 셈 3)과 5번째 값(1000) 사이를 0.6만큼 보간 → 40 + 0.6×960 = 616.
- disc: 순서상 위치(누적 비율)가 0.9 이상인 첫 값 → 1000(입력에 있는 값).
- `616.0000000000001`: `percentile_cont`는 `double precision`으로 계산한다. 0.6과 같은 이진 부동소수점 근삿값 계산에서 마지막 자리 오차가 생겼다.

### 8. 일요일 매출이 작고 토요일이 크다

- 원인: 세션 시간대가 UTC인 채로 `date_trunc('day', ts)`·`ts::date`로 잘랐다. 한국 일요일 00:00~08:59 주문이 UTC로 토요일 15:00~23:59라 토요일로 넘어갔다.
- 확인: 같은 기간을 `date_trunc('day', ts)`와 `date_trunc('day', ts, 'Asia/Seoul')`로 나란히 집계해 차이가 자정 근처 9시간 구간에서만 나는지 본다(실험 [7]: 09-11 UTC 3 vs KST 6).
- 고치기: `date_trunc('day', ts, 'Asia/Seoul')`, 범위 조건은 `ts >= '2026-09-13 00:00+09' AND ts < '2026-09-14 00:00+09'`처럼 시간대를 붙인 반열린 구간.

### 9. `random()` 필터가 내려간다

- 조건 `random() < f(d)`는 `d`만 참조한다. 플래너가 이 필터를 `generate_series` 함수 스캔으로 내려 `d` 값마다 한 번(28번)만 평가했다. 살아남은 `d`(실험에서는 7 하나)가 모든 사용자와 교차 조인되어, 모든 사용자가 가입 후 같은 경과일에 방문한 데이터가 됐다(달력 날짜는 가입일에 따라 다르다).
- 확인: `EXPLAIN`에 `Function Scan on generate_series d` 아래 `Filter: (random() < …)`가 보인다. 결과를 `d`별로 집계하면 `d` 값이 1~몇 개뿐이고 `d`마다 사용자 수가 전원(400)이다(`pushdown.sql` [P1]: 400쌍, `d` 값 1개).
- 고치기: 조건이 외부 행도 참조하게 한다(`random() + 0 * hashtext(u.user_id) < f(d)`). 그러면 `EXPLAIN`에서 조건이 `Join Filter`로 올라가 쌍마다 평가된다. 고친 판은 1,399쌍·`d` 값 27개로 퍼졌다([P2]). `LATERAL` 하위 쿼리로 감싸는 것만으로는 안 된다. `random()` 조건이 `u`를 참조하지 않으면 그대로 함수 스캔으로 내려간다(같은 컨테이너에서 확인: 400쌍·`d` 값 1개). 합성 데이터도 분포를 한 번 집계해 확인한다.
