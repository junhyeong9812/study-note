# data-analysis/05-percentiles-and-latency-distributions — 정답

## 정답

### 1. 평균 대신 백분위, 그리고 표본 크기

- 지연처럼 오른쪽 꼬리가 긴 분포에서 평균은 꼬리 크기를 드러내지 않는다. 로그정규 예에서 평균 33ms, p99 205ms였다([math/08](../../math/08-expectation-variance-tails/2-summary.md) 실험 C).
- p50은 "요청 절반이 이보다 빠르다", p99는 "요청 약 1%가 이보다 느리다"를 뜻한다. 같은 값이 많으면 더 적을 수 있다(nearest-rank p99보다 큰 요청은 많아야 1%).
- 표본 1만 건이면 p99 위로 약 100건이 있다. 꼬리의 모양을 어느 정도 반영한다.
- 표본 100건이면 p99 위로 1건 남짓이다. p99는 사실상 최댓값 근처이고 크게 흔들린다(7번).

### 2. 같은 10개 값의 p90

| 계산 | p90 |
|---|---|
| nearest-rank (`ceil(0.9·10)` = 9번째) | 95 |
| PostgreSQL 17 `percentile_cont(0.9)` (위치 `1+(n−1)·p` = 9.1) | 115.5 |
| Python 3.12 `statistics.quantiles(n=10)` 기본 `exclusive` (위치 `(n+1)·p` = 9.9) | 279.5 |

- 실험 A의 실제 출력이다. PostgreSQL은 `115.49999999999993`으로 출력했다.
- 다른 이유: 정렬된 i번째 값을 몇 % 지점으로 볼지 정의가 다르다. `exclusive`는 모집단에 표본보다 극단인 값이 있을 수 있다고 보고 끝 쪽 분위를 바깥으로 민다(Python 문서).
- `percentile_disc(0.9)`는 95로 nearest-rank와 같다. Python `method='inclusive'`는 115.5로 `percentile_cont`와 같다.

### 3. 백분위 병합

- 실험 B 결과: `avg(p99)` 722.8ms, 요청 수 가중 평균 98.8ms, 전체 원자료 p99 155.4ms.
- 가장 큰 것은 `avg(p99)`다. 요청의 1%뿐인 C를 1/3 무게로 센다.
- 사용자 체감과 같은 것은 전체 원자료의 p99다.
- 가중 평균이 틀린 이유: 백분위는 순위에서 나오는 값이라 선형 결합으로 합칠 수 없다. 전체 순위 99% 근처의 요청은 B와 C의 꼬리가 섞인 구간에서 오며, 어느 인스턴스의 p99와도 같지 않다.
- PostgreSQL 17.11에서 같은 모양의 합성 데이터로 반복해도 676.7 / 97.5 / 155.8로 같은 모양이었다(난수가 달라 숫자는 조금 다르다).

### 4. 합칠 수 있는 것

- 히스토그램은 버킷별 **개수**다. 개수는 더하기만 하면 되므로, 같은 경계를 쓰는 히스토그램끼리는 버킷마다 더한 결과가 전체 데이터로 만든 히스토그램과 같다(실험 D: 둘 다 p99 154.4).
- 조건: **버킷 경계가 같아야** 한다. 경계가 다르면 한쪽 버킷을 다른 쪽 버킷으로 나눌 방법이 없다(Prometheus 문서: 경계가 바뀌지 않았을 때만 집계 가능).
- 남는 오차: 분위수를 버킷 안에서 추정하는 오차. 고정 경계면 분위수가 떨어진 버킷의 폭만큼까지, 로그 간격이면 설정한 상대 정밀도만큼이다.

### 5. 버킷 해상도

- 진짜 p99 155ms가 `100 < x ≤ 250` 버킷에 떨어진다. 그 버킷 폭이 150ms다.
- 고정 경계 히스토그램은 버킷 안을 직선 보간으로 추정한다. 버킷 안 값의 실제 분포가 직선과 다르면 크게 어긋난다. 실험 C에서 198.1ms(+27.5%)가 나왔다.
- 로그 간격(γ=1.02)에서 칸 `(γ^(k−1), γ^k]`의 대표값을 `2γ^k/(γ+1)`로 잡으면 상대 오차는 `(γ−1)/(γ+1)` ≈ 0.99% 이내다. 실험 C에서 p99 −0.62%, p99.9 −0.24%였다.

### 6. HdrHistogram과 t-digest

- HdrHistogram: 값 범위와 유효 숫자 자릿수를 정하면 어떤 값이든 상대 오차 안의 버킷에 넣는다. 유효 숫자 3자리면 양자화 오차가 그 값의 0.1% 이하다(HdrHistogram 소개 페이지). 큰 값에는 넓은 버킷, 작은 값에는 좁은 버킷이 간다. `add`로 합친다.
- t-digest: 값을 중심점(평균·개수) 묶음으로 요약하되 양 끝 분위에는 작은 묶음을 둔다. 초록은 꼬리에서 정확하고 정확도가 `max(q, 1−q)`에 상대적이라고 쓴다(Dunning–Ertl, arXiv 1902.04023). 꼬리 정확도의 근거는 본문 2.8절의 묶음 크기 제한이다(k1은 `√(q(1−q))`, k3는 `min(q, 1−q)`에 비례 — 양 끝일수록 묶음이 작다). 이 노트에서는 구현·실측하지 않았다.
- 합칠 수 있어야 하는 이유: 서버 여러 대, 시간 창 여러 개의 분위수를 원자료 없이 다시 계산할 수 있다. 미리 계산한 분위수(summary)로는 할 수 없다.

### 7. 표본 크기별 p99의 흔들림

- 실험 E(반복 2000, seed 7): n=100이면 p99 추정의 2.5~97.5% 범위가 101.1~340.0ms다. n=1000이면 161.8~253.1ms, n=10000이면 190.0~219.9ms다.
- 100건의 p99(nearest-rank 99번째 값)는 맨 끝 한두 건에 달려 있다. 1만 건이면 꼬리에 100건이 있어 훨씬 안정적이다.

### 8. 새벽에만 울리는 p99 알람

- 의심: 새벽에는 요청 수가 적어 창 하나의 p99가 최댓값 근처로 출렁인다(7번).
- 확인할 숫자: 같은 창의 요청 수(`_count`의 rate). 새벽 창의 표본이 수십~수백 건이면 p99는 1~몇 건으로 결정된다.
- 대처
  - 창을 늘리거나 최소 표본 수 조건을 붙인다.
  - "X ms 초과 요청 비율"로 알람한다. 분자·분모를 더해 창·인스턴스를 정확히 합칠 수 있다. 다만 표본이 적으면 이 비율도 흔들린다(참 비율 1%, 100건이면 SE `√(p(1−p)/n)` ≈ 1%p, 0건일 확률 약 37% — OpenIntro 5.1.3 식으로 계산). 최소 표본 수 조건과 함께 쓴다.
  - 정말 새벽에 느린지(배치·백업과 겹침)는 원자료나 트레이스로 따로 확인한다.

### 9. summary 분위수를 합친 SLO 보고서

- 잘못된 점: summary의 분위수는 각 인스턴스가 앱 안에서 미리 계산한 값이다. 합칠 수 없는데 평균을 냈다(Prometheus 문서 "Histograms and summaries", 3번).
- 앞으로
  - 모든 인스턴스가 **같은 버킷 경계의 histogram**(또는 native histogram)을 내보낸다.
  - 서비스 p99는 `histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))`로 버킷을 합친 뒤 계산한다.
  - SLI를 "300ms 이내 요청 비율"처럼 비율로 정하면 분자·분모 합으로 정확히 합칠 수 있다.
- 과거 기간은 원자료가 없으면 재계산할 수 없다. 보고서에 그 한계를 적는다.
