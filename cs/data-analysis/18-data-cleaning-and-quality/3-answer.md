# data-analysis/18-data-cleaning-and-quality — 정답

## 정답

### 1. tidy data

- ① 변수마다 열 하나 ② 관측마다 행 하나 ③ 관측 단위의 종류마다 테이블 하나.
- 논문은 이것이 Codd의 제3정규형을 통계 용어로 다시 쓴 것이라고 적는다(database/03 정규화와 같은 생각).
- 지우면 안 되는 결측: 측정했어야 했는데 안 된 값(실험 설계상 있어야 할 관측). 지워도 되는 결측: 원래 잴 수 없는 *구조적 결측*(예: 남성의 임신 횟수).

### 2. 결측 제외 vs 0 채움

- 제외: (12,000 + 31,000 + 18,000) / 3 = 20,333.
- 0 채움: (12,000 + 0 + 31,000 + 0 + 18,000) / 5 = 12,200.
- 0을 넣으면 합은 그대로인데 개수(n)가 늘어난다. 값이 모두 양수면 0은 기존 평균보다 작으므로 평균이 내려간다.

### 3. 제외가 안전한 조건

- 맞는 경우: 빠질 확률이 데이터의 어떤 값과도 무관할 때(MCAR). 실험 [1]에서 무작위 15% 누락의 제외 평균 23,662는 참 평균 23,738에 가깝다.
- 틀릴 수 있는 경우: 빠질 확률이 값에 따라 다를 때(큰 값이 더 잘 빠지면 내려간다). 실험 [1]의 마지막 줄(3만 원 초과 주문 40% 누락, 나머지 5%)에서 제외 평균이 22,537로 내려갔다.

### 4. 관대한 파싱과 스키마 드리프트

- 새 파일의 행에서 `r.get("amount")`는 `None`을 돌려준다. `or 0`이 0으로 바꿔 금액이 0이 된다. 에러는 나지 않는다(실험 [2]: 합계 44,000 → 20,000).
- 바꾸기: 필수 열 집합을 `fieldnames`와 비교해 없으면 즉시 예외를 던진다. 값은 `r["amount"]`로 읽고, 빈칸은 0이 아니라 `None`(결측)으로 둔다.

### 5. dedup 두 방식

```text
  수신           정확 일치        정규화 해시 sha256(strip(lower(id)))
  order_0042     키 A             H
  ORDER_0042     키 B (다름)      H (같음)
  " order_0042"  키 C (다름)      H (같음)
  결과           3건 남음          1건 남음
```

- 실험 [3]: 재전송 40건이 표기만 달라 정확 일치로는 540건이 남고 합계가 7.5% 부풀었다. 정규화 해시는 500건으로 되돌렸다.
- 규칙을 너무 넓히면 서로 다른 대상을 하나로 합친다(예: 대소문자를 구분하는 ID 체계에서 `abc`와 `ABC`가 다른 고객). 정규화 규칙은 원천 시스템의 ID 규칙을 확인해 정한다.

### 6. 소계의 합 < 전체

- 원인: 레코드 연결 실패. 차원 테이블(고객·지역)과 키 표기가 달라 내부 조인에서 일부 행이 빠졌다.
- 확인: `SELECT count(*), sum(amount) FROM orders o WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.user_id = o.user_id)`로 연결 안 되는 행의 규모를 본다. 정규화 키(`lower(trim(...))`)로 다시 이었을 때 얼마나 줄어드는지 본다.
- 리포트: LEFT JOIN + `coalesce(region, '(미연결)')` 칸을 둬 합이 전체와 맞게 하고 미연결 규모를 드러낸다(고객 테이블 키가 유일할 때 — 중복이면 팬아웃으로 합이 커진다). 실험 [4]에서 지역별 합 12,645,000 → 정규화 후 13,760,000(전체와 일치).

### 7. 시간대 문자열 혼합

- web 수집기의 UTC 문자열 때문에 KST 각 날짜의 00:00~08:59 이벤트가 전날로 밀린다.
- 첫날(10-01) 앞에 09-30이 새로 생기고(실험 113건), 마지막 날(10-03)은 다음 날로 넘어오는 몫이 없어 줄어든다(534건, 참 678). 중간 날짜는 들어오고 나가는 몫이 비슷해 차이가 작다.

### 8. 정확히 10,000행

- 의심: 내보내기 도구·형식의 행 한도에 닿아 넘친 행이 경고 없이 버려졌다(조용한 절단). 실험 [6]: 원천 12,345행 중 10,000행만, 합계 약 18.8% 누락.
- 재발 방지: 결과 옆에 원천 행 수·합계 대조 검사를 둔다. 결과 행 수가 한도·둥근 수와 정확히 같으면 경고한다. 한도가 있는 형식은 피하거나 나눠 내보낸다.
- 실사건: 영국 PHE 2020-10 — 구형 XLS 형식의 행 한도 문제로 양성 결과 15,841건이 일일 집계에서 빠졌다(data-engineering/17 정리, XLS 관련 내용은 BBC 보도 출처).

### 9. 이상치 처리 전 확인

- 이상치가 오류인지 실제 사건인지 확인한다(단위 실수·테스트 데이터·대량 주문). 생성 과정의 정보를 담고 있을 수 있어 이유 없이 지우거나 바꾸는 것은 위험하다. 오류로 판단되거나, 예측 목적이면 예측 기간에 재발하지 않는다고 가정할 수 있을 때 바꾸고(13.9), 규칙과 건수를 기록한다.
- 13.9: 정규 분포라면 IQR 1.5배 규칙은 1,000개 중 약 7개, 3배 규칙은 50만 개 중 약 1개를 이상치로 표시한다. 저자들은 3배 규칙을 선호한다고 적는다.
