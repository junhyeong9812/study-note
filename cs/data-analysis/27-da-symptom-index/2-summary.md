# data-analysis/27-da-symptom-index — 증상 사전: 실험 비율 틀어짐(SRM)·합계가 안 맞음·너무 좋은 결과·부분군 반전·날짜 경계 어긋남·백분위 병합 오류 → 보이는 형태·원인 후보(통계 원리)·확인 방법·leaf — 정리 (힌트)

## 해결하는 문제

이 영역의 다른 노트는 **원리에서 증상으로** 간다.\
"사용자로 배정하고 세션으로 분석했다 → 분산이 과소 → A/A에서도 유의가 자주 뜬다"처럼 쓴다.\
현장에서는 반대 방향이 필요하다.\
손에 든 것은 숫자 하나다. "B가 +6%, p = 0.001", "지역별 합이 전체보다 8% 적다", "전체는 떨어졌는데 기기별로는 다 올랐다".

이 노트는 그 **역방향 색인**이다.

```text
  다른 노트 (정방향)                                      이 노트 (역방향)
  통계 원리 --> 전제가 깨지는 조건 --> 틀린 숫자·판단           숫자·판단 --> 보이는 형태 --> 원인 후보 --> 확인 계산 --> leaf
  "50:50 설계에서 한쪽만 사용자를 잃으면 비교가 편향"          "50.8 : 49.2다. 먼저 카이제곱 적합도, 그다음 필터 전후 점수표"
```

쉬운 예: 반 평균이 갑자기 95점이 된 시험이다.\
"학생들이 갑자기 잘했다"고 축하하기 전에 교사는 다른 것부터 본다.\
시험지가 미리 돌았나. 채점 기준이 바뀌었나. 결석한 학생이 빠져서 평균이 오른 것은 아닌가.

똑같은 구조다.\
분석의 오류는 예외로 보이지 않는다. SQL은 끝나고, 검정은 p값을 내고, 그래프는 그려진다.\
그래서 에러 메시지 대신 **숫자가 틀린 모양**(비율이 설계와 다름, 합계가 원천과 다름, 결과가 지나치게 좋음, 전체와 부분의 방향이 반대, 날짜 경계에서만 다름, 도구마다 다름)이 첫 단서다.

실무 예:
- A/B 실험 리포트가 "B 전환율 +6%, p = 0.001"을 들고 온다. 출시 회의는 내일이다.
- 이때 효과 크기보다 먼저 볼 것이 있다. 두 그룹의 사용자 수 비율(SRM), 분석 단위와 배정 단위, 이 지표가 미리 정한 1차 지표였는지다. 이 셋이 통과해야 "+6%"를 읽을 수 있다.

  - *역색인*: "leaf → 증상" 목록을 "증상 → leaf" 목록으로 뒤집은 것([data-structure/32-inverted-index](../../data-structure/32-inverted-index/2-summary.md)).
  - *leaf 표기 `NN-k`*: 이 영역 NN번 노트의 「장애 시나리오와 대처」 k번째 시나리오다. 예: `15-1` = [15](../15-ab-pitfalls-srm-peeking/2-summary.md)의 시나리오 1(50:50 설계인데 50.8 : 49.2).
  - *첫 계산*: 증상을 받았을 때 원인 후보를 가르려고 가장 먼저 하는 작은 계산. 카이제곱 적합도, 원천 합계와의 비율, 층별 차이 같은 것이다. 확정이 아니라 후보 고르기다.
    - 흔한 오해: "p값이 작으니 결과는 믿을 만하다." p값은 데이터가 "정해진 통계 모형"과 얼마나 어긋나는지를 나타낸다(ASA 2016 성명 원칙 1). 그 모형에는 무작위 배정·독립 단위 같은 전제가 들어 있다. 배정·로깅이 한쪽으로 기울었으면(SRM) 작은 p값은 처리 효과가 아니라 그 기울기를 반영할 수 있다([15-1](../15-ab-pitfalls-srm-peeking/2-summary.md)).

### 0-2. 실험: 증상별 첫 계산 여섯 개 (`triage.py`)

증상마다 원인 후보를 가르는 계산 하나씩을 표준 라이브러리로 짰다. 입력 수치는 leaf 실험의 출력을 옮긴 것(표시)과 합성 데이터(예시)다. 분류 규칙은 이 노트가 만든 모형이고, 어떤 도구의 기능이 아니다.

```python
def srm(a, b, ra=0.5):                                   # (1) 실험 비율 — 카이제곱 적합도, 자유도 1
    n = a + b; ea, eb = n * ra, n * (1 - ra)
    x2 = (a - ea) ** 2 / ea + (b - eb) ** 2 / eb
    return x2, math.erfc(math.sqrt(x2 / 2))

def reconcile(report, source):                           # (2) 합계 — 원천 대비 비율의 모양
    r = report / source
    if abs(r - round(r)) < 0.06 and round(r) >= 2: return f"정수배 근처 x{r:.2f} -> 팬아웃·중복"
    ...

def simpson(strata):                                     # (3) 부분군 반전 — 전체 차이 vs 층별 차이 vs 층 크기로 표준화한 차이
    tn = sum(s[2] for s in strata); cn = sum(s[4] for s in strata)       # s = (층, 처리 전환율, 처리 n, 대조 전환율, 대조 n)
    overall = sum(s[1] * s[2] for s in strata) / tn - sum(s[3] * s[4] for s in strata) / cn
    w = [s[2] + s[4] for s in strata]
    std = sum(wi * (s[1] - s[3]) for wi, s in zip(w, strata)) / sum(w)

p99 = lambda xs: st.quantiles(xs, n=100, method="inclusive")[98]   # (4) p99의 평균 vs 합친 분포의 p99
d = t.astimezone(tz).date()                                          # (5) 같은 순간을 UTC·KST 날짜로
fwer = 1 - (1 - alpha) ** m                                          # (6) m개 중 하나 이상 우연히 유의할 확률(독립 가정)
```

(실험, 호스트 Python 3.12.3 표준 라이브러리(`math`·`random`·`statistics`·`datetime`), i7-13700HX, 2026-10-08. (4)는 `random.Random(7)` 고정이라 매번 같은 출력)

```text
(1) SRM
    50,800 : 49,200  X²=25.60  p=4.2e-07
    508 : 492  X²=0.26  p=0.61
(2) 합계 대조
    17-1 팬아웃 매출            정수배 근처 x1.95 -> 팬아웃·중복
    18-5 지역별 합 vs 전체       8.1% 부족 -> 연결 실패·절단·필터·결측
    18-1 0 채움 평균 vs 결측 제외  14.2% 부족 -> 연결 실패·절단·필터·결측
(3) 부분군 반전 (12번 실험 B의 출력 수치)
    전체 차이 -2.51%p  모바일 +0.57%p(처리군 중 80%)  PC +0.46%p(처리군 중 20%)  층 크기로 표준화 +0.51%p
(4) 백분위 병합 (합성, seed 7)
    큰 인스턴스 p99 123ms  작은 인스턴스 p99 527ms  p99의 평균 325ms  합친 분포 p99 255ms
(5) 날짜 경계 (합성: 2026-10-01 15:00Z부터 1시간 간격 24건)
    UTC 기준 {'2026-10-01': 9, '2026-10-02': 15}  KST 기준 {'2026-10-02': 24}
(6) 지표 20개 중 하나만 p=0.03 (나머지 0.2~0.95, 예시)
    m=20  효과가 전혀 없어도 하나 이상 p<0.05일 확률(독립 가정) 64.2%  Bonferroni 문턱 0.0025 -> 통과 0개  BH 통과 0개
```

- 관찰
  - (1) 같은 50.8 : 49.2도 총 10만 명이면 p ≈ 4×10⁻⁷, 총 1,000명이면 p = 0.61이다. "몇 %p 어긋나면 SRM"이라는 고정 문턱은 없다. 비율과 표본 크기를 함께 넣어 검정한다([15](../15-ab-pitfalls-srm-peeking/2-summary.md) 실험과 같은 값).
  - (2) 1.95배는 "정수배 근처"로, 8.1%·14.2% 부족은 "부족"으로 갈렸다. 모양은 후보만 고른다. 18-5(연결 실패)와 18-1(0 채움)은 같은 "부족"으로 나와 이 규칙만으로는 갈리지 않는다. 확인 계산(미연결 비율, 0 비율)이 따로 필요하다.
  - (3) 전체 차이는 −2.51%p인데 두 층 모두 +이고, 층 크기로 표준화하면 +0.51%p다. 12번 노트의 출력(−2.50%p)과 끝자리가 다른 것은 이 계산이 반올림된 전환율(3.53% 등)에서 다시 계산했기 때문이다.
  - (4) p99의 평균(325ms)은 합친 분포의 p99(255ms)와 다르다. 이 합성 데이터에서는 평균이 더 컸다. 아래 SQL 실험처럼 데이터에 따라 더 작을 수도 있다. 방향이 정해져 있지 않다는 점이 요점이다.
  - (5) 총 24건은 같고 날짜별 건수만 다르다. "며칠 합계는 같은데 날짜별만 다름"이 시간대 문제의 표지다.
  - (6) p = 0.03 하나는 m = 20 보정을 통과하지 못한다(Bonferroni 0.0025, BH 0개).
- 한계(모형): 각 계산은 원인 후보를 좁힐 뿐이다. 예를 들어 (3)의 표준화 차이가 "진짜 효과"인지는 층 변수(기기)가 교란인지 매개인지에 달렸다([12-5](../12-correlation-vs-causation/2-summary.md) · [25-1](../25-causal-inference-basics/2-summary.md)). 확정은 leaf의 확인 방법으로 한다.

#### 실험: 같은 첫 계산을 SQL로 (`first_queries.sql`)

(실험, `postgres:17` = PostgreSQL 17.11, docker `--rm --pull never --network none --cpus=2`, 세션 `TimeZone` = `Etc/UTC`(이미지 기본값), 합성 데이터, 2026-10-08)

```sql
-- (1) SRM: 그룹별 사용자 수와 X²
SELECT variant, count(*) AS n,
       round(sum((count(*) - total/2.0)^2 / (total/2.0)) OVER (), 2) AS x2
FROM (SELECT variant, count(*) OVER () AS total FROM assignment) s GROUP BY variant, total ORDER BY variant;
-- (3) 날짜 경계: 같은 24건을 UTC 날짜·KST 날짜로
SELECT 'UTC' AS tz, (ts AT TIME ZONE 'UTC')::date AS d, count(*) FROM events GROUP BY 2
UNION ALL SELECT 'KST', (ts AT TIME ZONE 'Asia/Seoul')::date, count(*) FROM events GROUP BY 2
UNION ALL SELECT 'KST 묶음 + UTC 세션 ::date', date_trunc('day', ts, 'Asia/Seoul')::date, count(*) FROM events GROUP BY 2;
-- (4) 백분위: 인스턴스 p99의 평균 vs 합친 원자료의 p99
SELECT (SELECT round(avg(p)::numeric, 1) FROM (SELECT percentile_cont(0.99) WITHIN GROUP (ORDER BY ms) AS p FROM lat GROUP BY instance) x) AS avg_of_p99,
       (SELECT round(percentile_cont(0.99) WITHIN GROUP (ORDER BY ms)::numeric, 1) FROM lat) AS pooled_p99;
```

```text
     UTC                        | 2026-10-01 |  9
     UTC                        | 2026-10-02 | 15
(4)  avg_of_p99 334.0 | pooled_p99 485.1                           -- big 9,000건(40~139ms), small 1,000건(40~535ms)
(5)  전체 new 4.53 / old 7.04,  mobile 3.53 / 2.96 (new 중 80%),  pc 8.52 / 8.06 (new 중 20%)
```

- 관찰
  - (2) 조인 뒤 합이 원천 합의 2배를 넘었다(130,000 vs 60,000). 품목이 많은 주문의 금액이 품목 수만큼 반복됐다. 원천 단독 합계와 나란히 두면 바로 보인다([17-1](../17-sql-for-analysis/2-summary.md)).
  - (3) `date_trunc('day', ts, 'Asia/Seoul')`은 24건을 한 묶음으로 바르게 묶었다. 그런데 그 결과(KST 자정의 순간)를 UTC 세션에서 `::date`로 바꾸자 이름표가 `2026-10-01`로 하루 앞이 됐다. 묶음은 맞고 날짜 이름표만 틀리는 함정이다. 이름표는 `(ts AT TIME ZONE 'Asia/Seoul')::date`로 붙인다([database/27](../../database/27-temporal-types-and-session-timezone/2-summary.md)).
    - 왜: `date_trunc`는 `timestamptz`를 그대로 돌려준다. PostgreSQL 17 문서(9.9.2)대로 "truncation to day produces a value that is midnight in that zone"이고, 그 값은 순간 `2026-10-01 15:00:00+00`이다. `timestamptz → date` 변환은 세션 `TimeZone`의 지역 날짜를 쓴다. UTC 세션에서는 그 순간이 10-01이다. 같은 식을 `TimeZone = 'Asia/Seoul'` 세션에서 돌리면 `2026-10-02`가 나온다(점검 재실행, 같은 컨테이너). 이름표가 세션 설정에 따라 바뀐다는 뜻이다.
  - (4) 이번에는 p99의 평균(334.0)이 합친 p99(485.1)보다 **작았다**. 위 Python 실험과 방향이 반대다.
    - 두 실험 모두 합친 1만 건의 상위 1%(100건)가 전부 작은 인스턴스(1,000건)에서 왔다. 그래서 합친 p99는 작은 인스턴스의 p90 근처가 된다(추가 계산: Python 데이터에서 작은 인스턴스 p90 = 255, SQL 데이터에서 485.5 — 같은 정의 `inclusive`).
    - p99의 평균은 이 순위 구조와 상관없이 **큰 인스턴스 p99와 작은 인스턴스 p99의 중간값**이다. 그래서 "작은 쪽 p99가 작은 쪽 p90보다 얼마나 위에 있나"와 "큰 쪽 p99가 작은 쪽 p90보다 얼마나 아래에 있나"의 크기 싸움이 방향을 정한다(이 두 데이터처럼 상위 1%가 모두 작은 인스턴스에서 올 때의 설명).
    - Python(로그정규에 일부 5배, 꼬리가 김): 527 − 255 = 272가 255 − 123 = 132보다 크다 → 평균 325가 합친 p99 255보다 컸다.
    - SQL(균등, 꼬리가 짧음): 530 − 485.5 = 44.5가 485.5 − 138 = 347.5보다 작다 → 평균 334.0이 합친 p99 485.1보다 작았다.
  - (5)는 12번 실험 B의 전환율·n에서 전환 건수를 역산해 넣은 것이다(예: 79,863 × 3.53% ≈ 2,819). `ROLLUP` 한 줄로 전체와 층별, 구성비를 같이 본다.

### 1. 실험 비율이 틀어졌다 (SRM) · 배정이 이상하다

```text
  "A 50.8% : B 49.2%"
     │
     ├─ 전체 점수표에도 SRM ──────────────────────────────▶ 배정·로깅 경로가 한쪽에서 사용자를 잃음        15-1 · 20-4
     ├─ 필터·트리거 점수표에만 SRM ─────────────────────────▶ 처리 이후 행동으로 사람을 거름                15-3
     ├─ 특정 부분군(느린 네트워크·구형 브라우저)만 ───────────────▶ 한쪽만 리다이렉트·느림·크래시               15-4
     └─ 비율은 정상인데 배정이 이상
          ├─ 한 사용자가 두 변형을 다 봄 ─────────────────────▶ 배정 키가 바뀜(익명 → 로그인)              14-4
          ├─ 두 실험의 B 그룹이 같음 ───────────────────────▶ 같은 salt                              14-3
          └─ 같은 사용자 세션들이 한 그룹에 몰림 ───────────────▶ 해시 섞임 부족                          14-5
```

| 보이는 형태 (숫자·리포트) | 원인 후보 (통계 원리) | 확인 방법 | leaf |
|---|---|---|---|
| 50:50 설계인데 사용자 수 50.8 : 49.2(10만 명 규모에서 p ≈ 4×10⁻⁷). 리포트 구석의 SRM 경고를 "1%p도 안 되니 괜찮다"고 넘김. B가 유의하게 좋아 출시했는데 지표가 움직이지 않음 | 배정·로깅·필터 어딘가가 한쪽에서 특정한 사용자를 더 잃었으면 남은 사용자끼리의 비교는 선택 편향이다. 배정 칸 수 버그처럼 무작위성은 남고 비율만 틀린 경우도 있다 — SRM은 경보이고, 어느 쪽인지는 원인 조사로 가린다 | 카이제곱 적합도 `X² = Σ(O−E)²/E`(자유도 1, 0-2절 (1)). 그다음 15번 적용 1절 순서: 전체 vs 필터 점수표 → 날짜별 → 부분군별 → 성능 지표 → 다른 실험·A/A | [15-1](../15-ab-pitfalls-srm-peeking/2-summary.md) · [20-4](../20-categorical-inference/2-summary.md) |
| 필터 후 점수표에만 SRM(B 49.24%), 필터 전에는 없음. 참여를 늘리려던 변경이 참여를 줄인 것으로 나옴 | 처리가 바꾼 행동(클릭 수)을 기준으로 봇을 걸렀다. 걸러진 사람이 B에 몰렸다 | 필터 전·후 점수표 각각의 SRM. 걸러진 사용자 수를 그룹별로 | [15-3](../15-ab-pitfalls-srm-peeking/2-summary.md) |
| B(리다이렉트로 붙인 새 랜딩)의 노출 로그가 적다. 느린 네트워크·구형 브라우저 부분군에서 더 적다 | 리다이렉트 중 이탈·실패한 사용자는 B 로그를 남기지 못한다(Fabijan 외 5.2) | 부분군별 비율. A도 같은 리다이렉트를 거치는지 | [15-4](../15-ab-pitfalls-srm-peeking/2-summary.md) |
| 로그인 전후 두 화면을 모두 본 사용자가 적지 않다. 이들이 양쪽 지표에 섞인다 | 익명일 때 기기 ID, 로그인 후 회원 ID로 해시 — 배정 키가 바뀌었다 | 사용자별로 본 변형 수(2 이상인 사용자 수)를 리포트에 표시 | [14-4](../14-ab-testing-design/2-summary.md) |
| 동시에 돈 두 실험이 같은 크기의 효과. 두 실험의 B 그룹 사용자 목록이 같음(10만 명 전원 일치) | 두 실험이 같은 salt를 썼다. 두 처리 효과가 한 그룹에 겹친다 | 실행 중인 실험 쌍의 배정 일치율(독립이면 50:50 분할에서 약 50%) | [14-3](../14-ab-testing-design/2-summary.md) |
| 세션 단위 실험에서 같은 사용자 세션 쌍의 그룹 일치율 64%(기대 50%) | 키가 `user_7#s0`처럼 끝만 다르고, 해시(FNV-1a 단독)의 마지막 바이트 섞임이 약하다 | 실제 키 형식으로 일치율·χ² 독립성 시험 | [14-5](../14-ab-testing-design/2-summary.md) |

- 처방의 방향: SRM이 있으면 **결과를 무효로 두고** 원인부터 찾는다. "효과는 보되 참고만"은 없다([15-1](../15-ab-pitfalls-srm-peeking/2-summary.md)). 실험 플랫폼이 SRM을 자동 검사해 점수표를 가리게 둔다.
- 작은 배정 버그는 SRM 검정으로 늦게 보인다. 15번 실험에서 0.1% 칸 하나가 덜 배정된 경우는 100만 명 규모에서 p = 0.32였다. 배정 설정 자체(칸 수·salt)를 따로 검사한다.

먼저 **검사 순서**를 지킨다. SRM(1절) → 분석 단위 = 배정 단위인가 → 이 지표가 미리 정한 1차 지표인가 → 몇 번 봤나 → 효과 크기와 구간.

| 전체 효과 없음 → "iOS 신규 30대에서 +8%". 유의한 칸이 표본이 작은 칸에 몰림 | 쪼갠 칸 하나하나가 검정이다. 데이터를 보고 유의한 칸을 골랐다(실험 C의 89%) | 쪼갠 칸 총수를 m으로 보정, 찾은 세그먼트만 대상으로 새 실험 | [11-2](../11-multiple-comparisons/2-summary.md) |
| 실험 대부분이 2~5일 만에 "유의"로 끝남. 종료일이 p값이 처음 0.05 아래로 내려간 날과 겹침 | 매일 보고 유의한 날 멈춤 — A/A로 같은 규칙을 20일 돌리면 약 23~24%가 "유의" | 종료 규칙·계획 표본 대조, 일별 p값 궤적 | [15-2](../15-ab-pitfalls-srm-peeking/2-summary.md) |
| 지난 분기 "유의한 승리"의 효과 합으로 예측한 매출보다 실제가 훨씬 작음 | 검정력이 낮으면 우연히 크게 나온 추정만 문턱을 넘는다 — 유의한 실험만의 평균 효과가 진짜의 2.4배, 일부는 부호까지 틀림(26건) | 승리 실험의 재실험(holdout), 설계 검정력 | [10-3](../10-power-and-sample-size/2-summary.md) |
| 사용자로 배정한 실험을 세션 단위로 분석해 "유의". 구간이 유난히 좁고 A/A에서도 약 13%가 유의 | 같은 사용자의 세션은 독립이 아니다 — 서로 닮으면(양의 상관) 분산 과소 | 정기 A/A의 거짓 양성률, 분석 단위 = 배정 단위인지 | [14-1](../14-ab-testing-design/2-summary.md) |
| CTR 실험이 거의 매번 유의. A/A 거짓 양성률 27.2% | 사용자로 배정하고 노출을 독립 표본으로 셌다 | 사용자 단위로 접기, 델타 방법·사용자 부트스트랩 | [16-4](../16-metrics-design/2-summary.md) |
| 페이지뷰 단위 분할표로 p = 0.001, 재실험에서 재현 안 됨. 표의 합계가 사용자 수의 몇 배 | 같은 사용자의 이벤트는 독립이 아니다 — 효과가 없어도 17.3%가 유의(명목 5%) | 표 합계 vs 사용자 수, 사용자 단위로 집계해 재검정 | [20-2](../20-categorical-inference/2-summary.md) |
| 세션 단위 전환율 차이가 "매우 유의"했는데 재실험에서 재현 안 됨. 실제 SE가 순진한 SE의 1.45배 | 같은 사용자의 세션이 서로 닮았다 | 사용자별 집계·사용자 단위 부트스트랩 | [07-3](../07-sampling-distributions-and-clt/2-summary.md) |
| 양측 p = 0.08 → "예상했던 방향"이라며 단측으로 바꿔 p = 0.04 보고. 분석 계획서와 보고서의 검정 방향이 다름 | 방향을 결과를 보고 고르면 실제 1종 오류율이 명목 α보다 커진다 | 사전 분석 계획(가설·방향·α·단위) 대조 | [09-4](../09-hypothesis-testing/2-summary.md) |
| 소수 카나리(10대)와 기존 40대를 합동 t로 비교, 같은 빌드끼리도 "유의" 경보. 귀무에서 28.3% 유의(명목 5%) | 작은 그룹의 분산이 큰데 합동 분산이 그것을 과소평가한다 | Welch t로 재계산(같은 조건 0.051), 그룹별 분산 | [21-3](../21-numerical-inference-t-anova/2-summary.md) |
| 인스턴스 타입 5종을 쌍별 t로 비교, 10쌍 중 1쌍만 p < 0.05. 다시 재니 차이 없음 | k = 5면 쌍이 10개 — 다중 비교 | ANOVA 먼저, 쌍별은 Bonferroni(0.05/10) | [21-4](../21-numerical-inference-t-anova/2-summary.md) |
| 광고 입찰 실험에서 B가 크게 이겼는데 전면 적용하자 전체 매출 그대로. 실험 기간에 A의 노출·낙찰이 평소보다 줄었다 | 공유 예산 간섭 — 측정된 차이 = B의 이득 + A의 손해 | 실험 기간 A의 지표를 실험 전과 비교 | [15-5](../15-ab-pitfalls-srm-peeking/2-summary.md) |
| 3일 실험 +6%로 출시, 한 달 뒤 지표 거의 그대로. 일별 효과가 첫날 최고에서 내려감 | 신규성 효과 — 짧은 실험은 초반만 본다 | 경과 일수별 효과 그래프, 신규 사용자 부분군 | [14-2](../14-ab-testing-design/2-summary.md) |
| 분기 내내 클릭률 실험 "성공"(CTR +2~4%), 분기 말 유지율 하락 | 대리 지표를 직접 올리는 수단이 생겨 대리와 목표의 상관이 끊겼다(굿하트) | 과거 실험에서 대리 변화와 목표 변화가 같은 방향이었나 | [16-1](../16-metrics-design/2-summary.md) |
| 실험 리포트에는 OEC +1%만. 운영 대시보드에서 p95가 실험 시작일부터 계단처럼 오름 | 지연·오류를 판정에 넣지 않았다(가드레일 없음), 평균 지연만 봤다 | 가드레일 지표(백분위·오류율)를 그룹별로 | [16-2](../16-metrics-design/2-summary.md) |

### 3-2. 너무 좋은 결과 — 모델·순위·상관

### 4. 부분군 반전 · 부호가 뒤집힌다

먼저 **두 비교 무리의 구성비**를 본다(0-2절 (3)·(5)). 그다음 그 층 변수가 처리보다 **앞에 정해지는지**(교란 후보) **뒤에 정해지는지**(매개·충돌 후보) 화살표를 그린다.

```text
  전체: 새 화면 −2.5%p          모바일: +0.57%p     PC: +0.46%p
             │
             ├─ 층 변수가 처리 전에 정해짐(기기·지역) + 처리군 구성비가 다름 ──▶ 교란 → 층별·표준화로 판단        12-1 · 03-1 · 03-2
             ├─ 층 변수가 처리 뒤에 정해짐(방문 수·장바구니 금액) ─────────▶ 매개 → 층별이 아니라 전체가 맞음   12-5 · 25-1 (5절)
             └─ 처리와 결과 둘 다의 영향을 받는 변수로 거름(문의 고객) ─────▶ 충돌 → 가짜 반전                 25-2
```

| 보이는 형태 | 원인 후보 | 확인 방법 | leaf |
|---|---|---|---|
| 점진 배포한 새 결제 화면이 전체 전환율 −2.5%p로 보여 롤백. 기기별 행은 모두 상승 | 노출이 모바일(원래 전환율이 낮음)에 치우쳤다 — 심슨의 역설 | 처리·대조군의 기기 구성비, 기기별 판단·표준화. 다음 배포는 기기 안에서 무작위 | [12-1](../12-correlation-vs-causation/2-summary.md) |
| "기능 X 사용자의 잔존 +28%p" → 기본값 ON. 전면 적용 뒤 잔존이 오히려 조금 내려감(설정한 진짜 효과 −2%p) | 원래 많이 쓰는 사용자가 기능을 켰다(교란). 관찰 차이의 부호가 진짜 효과와 반대 | 사용 빈도 층별 비교·균형표, 무작위 실험 | [03-1](../03-observational-vs-experimental/2-summary.md) |
| 베타 신청자 vs 미신청자 비교로 "신규 결제 흐름 전환 +15%(예시)" | 신청 여부가 관심도라는 교란과 묶였다(자기 선택) | 신청자 안에서 무작위로 나눠 비교 | [03-2](../03-observational-vs-experimental/2-summary.md) |
| 전체에서 양(+)인 관계가 "고객센터 문의 고객"으로 좁히자 음(−). 실험의 합격자 선택에서는 독립인 두 변수 사이에 상관 −0.68 | 충돌 변수(처리·결과 둘 다의 영향을 받는 변수)로 거르면 두 부모 사이에 가짜 연관이 생긴다 | DAG에서 필터·통제 변수가 처리·결과 이후에 정해지는지 | [25-2](../25-causal-inference-basics/2-summary.md) |
| "페이지뷰가 늘수록 구매가 준다." 다른 달 데이터로 다시 맞추면 부호가 바뀜. 방문 수와 페이지뷰 상관 0.99대, 계수 SE가 계수보다 큼 | 다중공선성 — 닮은 두 변수의 몫을 데이터가 가르지 못한다(실험 10개 중 8개 부호 뒤집힘) | 상관 행렬, 하나만 넣거나 합친 변수로 다시 적합 | [22-1](../22-multiple-and-logistic-regression/2-summary.md) |
| "프리미엄 기능을 쓰면 매출 1.4배"로 기능 사용 강제 정책 → 효과가 훨씬 작음. 회귀 계수 1.42가 IV 추정 0.54의 약 2.6배 | 측정 못 한 교란(열성도)이 기능 사용과 매출을 같이 올린다 | 무작위 실험 검토, DAG로 교란 목록, IV·DiD·민감도 분석 | [25-5](../25-causal-inference-basics/2-summary.md) |
| "캐시 미스가 많은 노드가 느리다(r ≈ 0.6)" → 캐시 증설, 지연 그대로 | 트래픽이 미스와 지연을 둘 다 늘렸다(교란). 트래픽을 고정하면 0.635 → 편상관 0.021 | 교란 후보로 층화·편상관, 한 노드만 바꾸는 실험 | [12-2](../12-correlation-vs-causation/2-summary.md) |

- 하지 말 것: "부분군이 언제나 정답"으로 외운다. 층 변수가 매개면 층별 차이가 0으로 나와 효과를 지운다(5절 [12-5](../12-correlation-vs-causation/2-summary.md)). 어느 쪽이 맞는지는 숫자가 아니라 인과 화살표가 정한다([12](../12-correlation-vs-causation/2-summary.md) 4절).
- 실사건: 부채가 많은 나라의 성장률 평균에서 "나라마다 같은 가중"과 "나라-연도마다 같은 가중"이 −0.1%와 2.2%로 갈린 Reinhart–Rogoff 재현([28 사건 3](../28-da-incidents/2-summary.md)). 구성(어느 나라가 몇 해 들어갔나)이 평균을 움직인 모양이다.

### 5. 효과가 안 보인다 · "효과 없음"으로 결론 냈다

먼저 **구간의 폭**을 본다. 구간이 넓어 0을 포함하면 "효과 없음"이 아니라 "모른다"다. 구간이 좁고 0 근처인데 이상하면 효과가 지나가는 길을 막았는지(매개 통제) 본다.

| 보이는 형태 | 원인 후보 | 확인 방법 | leaf |
|---|---|---|---|
| 군당 100명 실험 p = 0.82로 기능 폐기. 차이의 구간 −7.5~+9.5%p | 검정력이 낮아 기각하지 못했을 뿐 — 그 설정에서는 진짜 차이가 있어도 62%가 "유의하지 않음" | 구간 폭, "모른다"로 보고, 표본 크기 재설계 | [09-2](../09-hypothesis-testing/2-summary.md) |
| 군당 2,000명 A/B "유의하지 않음"으로 폐기. 설계 검정력 17% 남짓 | MDE에 맞는 n을 계산하지 않았다(80%면 군당 14,749명) | 검정력 계산, 끝난 실험은 "결론 보류" | [10-1](../10-power-and-sample-size/2-summary.md) |

### 9. 구간·p값을 잘못 읽었다

| 보이는 형태 | 원인 후보 | 확인 방법 | leaf |
|---|---|---|---|
| 의사결정 문서가 "전환율이 9.6~10.4%일 확률 95%"로 기대 매출을 계산 | 빈도주의 신뢰수준은 절차의 장기 포함률이지 구간 하나의 확률이 아니다 | "같은 방법을 반복하면 95%의 구간이 참값을 포함"으로 고쳐 쓰기. 확률 진술이 필요하면 사전을 명시한 베이즈 | [08-1](../08-confidence-intervals/2-summary.md) |
| 설문 응답 2만 건으로 만든 만족도 구간이 매우 좁은데 전체 사용자 조사와 크게 다름 | 구간은 표집 오차만 반영한다. 응답자만 모인 편향은 n을 키워도 줄지 않는다 | 수집 과정(무응답·자기 선택) 점검 | [08-4](../08-confidence-intervals/2-summary.md) |
| 부하 테스트 5회 평균으로 만든 "95% 구간"이 같은 빌드를 수백 번 돌린 기준 평균(참값에 가까운 값)을 자주 놓침. 정규 모집단에서도 n=5 z 구간은 87.8%만 덮음(6번째 측정 하나가 구간 밖인 것은 t 구간에서도 흔하다 — 구간은 평균에 대한 것) | s로 σ를 대신한 불확실성을 무시했다 | t 임계값(df 4 → 2.776) | [08-5](../08-confidence-intervals/2-summary.md) |
| "평균 결제액 95% 구간 [8,200원, 9,100원]", 다음 달 실제 평균이 구간 위. 로그정규(σ=1.5) n=30이면 포함률 77.3% | 꼬리가 긴 분포의 작은 표본에 정규 근사 | 히스토그램, 비슷한 분포로 시뮬레이션해 포함률 확인, 부트스트랩(한계 인지) | [07-1](../07-sampling-distributions-and-clt/2-summary.md) |
| "응답 시간 평균 120ms ± 80ms"라 쓰고 "구간이 넓어 차이를 말할 수 없다". 1만 건인데 100건과 같은 폭 | 표준편차(개별 요청의 퍼짐)와 표준오차(평균의 흔들림, 80/√10000 = 0.8ms) 혼동 | "SD"·"SE"·"95% CI" 이름 붙여 보고 | [07-2](../07-sampling-distributions-and-clt/2-summary.md) |
| 경영 보고서에 "이 효과가 우연일 확률은 3%" | p값을 가설이 참일 확률로 바꿔 말했다(ASA 원칙 2) | "차이가 없다면(귀무 모형이 맞다면) 이만큼 또는 이보다 더 큰 차이는 100번에 3번 꼴"로 고쳐 쓰기. 양측 검정이면 반대 방향의 큰 차이도 포함 | [09-3](../09-hypothesis-testing/2-summary.md) |
| 전환 3건 vs 7건(각 50명)에 z 검정 p값 보고 | 성공·실패 조건(각 군 n × 합동 비율 ≥ 10과 n × (1 − 합동 비율) ≥ 10) 미충족 — 정규 근사 전제가 깨졌다 | 순열 검정·정확 검정 | [09-5](../09-hypothesis-testing/2-summary.md) |
| 배포 전후 오류 유형 분포 p = 0.007 경보, 희귀 유형 3건이 전부(기대 0.6건). 근사 p 0.0073 vs 몬테카를로 p 0.0249 | 기대 빈도가 작은 칸에 카이제곱 근사 | 모든 칸의 기대 빈도 출력(5 미만 경고), 범주 합치기·몬테카를로·정확 검정 | [20-1](../20-categorical-inference/2-summary.md) |
| "P(B > A) = 0.92"를 "출시하면 92% 성공"으로 읽고 출시 → 기대한 효과 크기 미달 | "조금이라도 나을 확률" ≠ "의미 있게 나을 확률" | `P(p_B − p_A > 최소 의미 효과)`와 차이의 신용구간 | [26-4](../26-bayesian-thinking/2-summary.md) |
| IV 추정이 표본을 조금 바꿀 때마다 크게 달라짐. 1단계 0.02일 때 1.66 ~ 6.81 | 약한 도구 변수 — 작은 1단계로 나누면 분자의 잡음이 확대된다 | 1단계 크기와 불확실성을 먼저 보고 | [25-4](../25-causal-inference-basics/2-summary.md) |

### 11. 예측·모델이 운영에서 깨진다

| 보이는 형태 | 원인 후보 | 확인 방법 | leaf |
|---|---|---|---|
| 이용률 60%까지 잰 직선으로 "90%에서도 응답 3배 이내" 판단, 프로모션 날 10배. 직선 예측 3.10 vs 실측 10.00(이용률 0.9) | 외삽 — 지연은 1/(1−ρ)로 휘는데 낮은 구간만 보고 직선을 그렸다. R² 0.95는 잰 구간 안의 적합도일 뿐 | 예측하려는 x가 데이터 범위 안인지 | [13-1](../13-linear-regression/2-summary.md) |
| 요청당 비용 회귀의 기울기가 0.81 → 0.47 "효율 개선". 200점 중 x가 혼자 400인 점 하나, 그 잔차 −126 | 높은 레버리지(h = 0.48)가 직선을 자기 쪽으로 당긴다. 그래서 잔차가 작아 보인다 | 레버리지 상위 점을 빼고 재적합 | [13-2](../13-linear-regression/2-summary.md) |

| 앱(Python) 기울기 0.81과 SQL 리포트의 기울기 1.09가 다름. SQL이 `regr_slope(concurrency, latency_ms)` | PostgreSQL `regr_slope(Y, X)`는 첫 인자가 반응 변수. 바꾸면 기울기가 r²/b1(실험 1.0896) | 인자 순서, 같은 데이터로 앱 결과와 대조하는 테스트 | [13-4](../13-linear-regression/2-summary.md) |
| "쿠폰 계수 0.4 → 구매 확률 40%p 상승" 보고. 실제 그룹 간 구매율 차이는 몇 %p | 로지스틱 계수는 log-odds 단위다 | odds 배수(e^b), 대표 고객 몇 명의 예측 확률 차이 | [22-4](../22-multiple-and-logistic-regression/2-summary.md) |

- 누설·과적합으로 학습 성능만 좋은 경우는 3-2절. 실사건: 2011-08 ~ 2013-09에 108주 중 100주를 높게 추정한 Google Flu Trends([28 사건 2](../28-da-incidents/2-summary.md)).

| "B 안이 압도적"으로 회의가 끝났는데 실제 차이 3%p. y축이 50에서 시작, 막대 길이 비 2.5 vs 값의 비 1.06 | 막대 길이가 "50을 넘는 정도"를 나타냈다(잘린 축) | 축 시작값, 막대는 0에서 | [19-1](../19-data-visualization-principles/2-summary.md) |
| 앞쪽 채널의 비중을 실제보다 크게 기억. 같은 25% 조각이 앞에서 보이는 넓이 34.3%, 뒤에서 19.9%(단순 모형) | 3D를 2D로 투영하면 왜곡된다. 이 모형에서는 앞쪽 조각에만 옆면이 보여 커 보였다 | 숫자 레이블, 2D 정렬 막대 | [19-2](../19-data-visualization-principles/2-summary.md) |
| "가입자가 늘자 지연도 같이 늘었다"는 그래프로 증설 결정. 오른쪽 축이 210~216ms, 실제 지연 변화 +2.9% | 단위가 다른 두 축의 범위를 골라 모양을 맞췄다(이중 축) | 두 축의 범위, 같은 기준 지수(시작 = 100)로 한 축 | [19-3](../19-data-visualization-principles/2-summary.md) |
| 지역별 지연 지도의 노란 띠 지역이 "문제 지역"으로 지목, 값은 이웃과 비슷 | 무지개(색상환) 척도는 밝기가 단조롭지 않다(상대 휘도 0.928 지점에서 튐) | 밝기가 한 방향으로 변하는 순차 척도 | [19-4](../19-data-visualization-principles/2-summary.md) |
| 서비스 15개를 색 15개로 그린 그래프에서 아무도 특정 선을 못 찾음 | 범주 색이 너무 많다 | 상위 몇 개만 색, 나머지 회색, 작은 그림 여러 개 | [19-5](../19-data-visualization-principles/2-summary.md) |

## 쓰이는 자료구조·알고리즘

- **역색인**: 증상 → leaf 목록. 이 노트 자체가 손으로 만든 역색인이다([data-structure/32-inverted-index](../../data-structure/32-inverted-index/2-summary.md)).
- **카이제곱 적합도·분할표**: SRM 검사(1절)와 기대 빈도 점검(9절). 자유도 1이면 `p = erfc(√(X²/2))`로 꼬리를 바로 구한다([15](../15-ab-pitfalls-srm-peeking/2-summary.md) · [20](../20-categorical-inference/2-summary.md)).
- **해시 기반 결정적 배정**: 배정 일치율·해시 섞임 점검(1절)([14](../14-ab-testing-design/2-summary.md) · [algorithm/12-hash-functions](../../algorithm/12-hash-functions/2-summary.md) · [domain-modeling/advanced/27-ab-assign](../../domain-modeling/advanced/27-ab-assign/2-summary.md)).
- **가중 평균·표준화**: 합÷합 vs 평균의 평균(2절), 층 크기로 표준화한 차이(4절)([16](../16-metrics-design/2-summary.md) · [12](../12-correlation-vs-causation/2-summary.md)).
- **히스토그램 버킷 병합**: 백분위는 원자료나 버킷을 합친 뒤 계산한다(7절)([05](../05-percentiles-and-latency-distributions/2-summary.md) · [data-structure/19-probabilistic-counting](../../data-structure/19-probabilistic-counting/2-summary.md)).
- **정렬 기반 다중 비교 보정(BH)**: p값을 정렬해 순위 k의 문턱 `k/m × α`와 비교(3절)([11](../11-multiple-comparisons/2-summary.md) · [algorithm/09-sorting-in-practice](../../algorithm/09-sorting-in-practice/2-summary.md)).
- **이동 창·EWMA**: 기준선과 탐지 지연(12절)([23](../23-time-series-basics/2-summary.md) · [data-structure/25-ring-buffer](../../data-structure/25-ring-buffer/2-summary.md)).
- **인과 DAG 경로 판정**: 층·통제 변수가 교란·매개·충돌 중 무엇인가(4·5절)([25](../25-causal-inference-basics/2-summary.md) · [data-structure/08-graph](../../data-structure/08-graph/2-summary.md)).

## 적용 — 풀어나가는 법

### 1. 숫자를 받으면 묻는 순서

```text
  ① 단위가 맞나        배정 단위 = 분석 단위 = 표본 크기 공식의 단위?           아니면 → 3절(너무 좋음)·5절(검정력)
  ② 비율이 설계와 맞나   SRM 검정, 필터 전후 비교                                 어긋나면 → 1절, 결과 보류
  ③ 원천과 맞나         원천 행 수·합계 대비 비율의 모양                           어긋나면 → 2절
  ④ 몇 번째 비교인가     지표·세그먼트·엿보기·후보 모형 수, 사전 1차 지표            여럿이면 → 3절 보정
  ⑤ 구성이 같나         비교 무리의 층별 구성비, 층 변수의 시점(처리 전/후)         다르면 → 4절
  ⑥ 시간 축이 맞나       시간대·이벤트 시각·관측 끝, 비교 기간의 조건               → 6절
  ⑦ 정의가 같나         분위수 방법·도구·버전, 합÷합 vs 평균의 평균                 → 2절·7절
  ⑧ 모양을 봤나         히스토그램·산점도·잔차 그림                               → 8절·11절
```

- ①과 ②를 먼저 두는 이유: 둘이 깨지면 그 뒤의 숫자(효과 크기·구간·p값)가 전제부터 흔들린다. SRM은 효과 크기를, 단위 불일치는 구간·p값을 주로 흔든다. ③~⑧은 원인 후보를 좁히는 순서다.
- 각 단계는 후보를 고를 뿐이다. 원인을 고친 뒤에는 leaf의 확인 방법으로 같은 계산을 다시 돌려 숫자가 돌아왔는지 본다.

| 1 | SRM(전체 점수표, 필터 점수표) | 결과 무효, 원인 찾기 | [15](../15-ab-pitfalls-srm-peeking/2-summary.md) 적용 1절 |
| 2 | 배정 단위와 분석 단위, 최근 A/A의 거짓 양성률 | 분산 다시 계산(사용자 단위·델타 방법) | [14](../14-ab-testing-design/2-summary.md) · [16](../16-metrics-design/2-summary.md) |
| 3 | 1차 지표가 사전에 정한 것인가, 본 지표·세그먼트 수 | 보정 또는 "탐색 결과"로 강등 후 재실험 | [11](../11-multiple-comparisons/2-summary.md) |
| 4 | 종료 시점이 계획 표본인가 | 순차 검정이 아니면 결과 보류 | [15](../15-ab-pitfalls-srm-peeking/2-summary.md) |

### 3. 첫 쿼리 모음 (PostgreSQL 17 — 테이블·컬럼 이름은 예시)

```sql
-- 1절 SRM: 그룹별 단위 수 → X²(위 0-2절 SQL (1)), 날짜별로도
SELECT (first_exposure_at AT TIME ZONE 'Asia/Seoul')::date AS d, variant, count(DISTINCT user_id)   -- KST 날짜 이름표(0-2절 SQL (3)의 함정 회피)
FROM exposure GROUP BY 1, 2 ORDER BY 1, 2;
-- 2절 합계 대조: 리포트 쿼리 옆에 원천 단독 합계
SELECT (SELECT sum(amount) FROM orders WHERE ordered_at >= :from AND ordered_at < :to) AS source_sum;
-- 4절 구성비: 처리·대조의 층별 n과 비율을 한 표로
SELECT coalesce(device, '전체'), variant, sum(n), round(100.0 * sum(converted) / sum(n), 2)
FROM conv GROUP BY ROLLUP(device), variant ORDER BY 1, 2;
-- 6절 날짜 경계: 같은 기간을 UTC 날짜와 KST 날짜로 나란히
SELECT (ts AT TIME ZONE 'UTC')::date AS utc_d, (ts AT TIME ZONE 'Asia/Seoul')::date AS kst_d, count(*)
FROM events WHERE ts >= :from AND ts < :to GROUP BY 1, 2 ORDER BY 1, 2;
-- 7절 백분위: 원자료에서 한 번에, 정의(percentile_cont)를 명시
SELECT percentile_cont(0.99) WITHIN GROUP (ORDER BY latency_ms) FROM request_log WHERE ts >= :from AND ts < :to;
```

- 위 쿼리 중 실제로 돌린 것은 0-2절의 `first_queries.sql`(같은 구조, 합성 데이터)이다. 이 절의 쿼리는 그 구조를 실무 테이블 모양으로 옮긴 예시이고 실행하지 않았다. 실제 진단 쿼리와 출력 읽는 법은 각 leaf의 적용 절에 있다(15 적용 2절, 12 적용 2절, 17 적용, 05 적용).

## 장애 시나리오와 대처

증상 색인을 **잘못 읽어** 생기는 장애다.

### 1. "너무 좋은 결과"를 검사 순서 없이 발표한다 ⚠

- **현상**: "B +6%, p = 0.001"을 바로 경영 보고에 올렸다. 출시 뒤 지표가 움직이지 않는다.
- **보이는 형태**: 사후에 보니 점수표 사용자 수가 50.8 : 49.2였거나, 세션 단위로 분석했거나, 20개 지표 중 하나였다([15-1](../15-ab-pitfalls-srm-peeking/2-summary.md) · [14-1](../14-ab-testing-design/2-summary.md) · [11-1](../11-multiple-comparisons/2-summary.md)).
- **원인**: 효과 크기부터 읽었다. p값의 전제(정상 배정, 독립 단위, 한 번의 사전 검정)를 확인하지 않았다.
- **대처**: 적용 2절 판독 순서를 실험 템플릿에 고정한다. SRM·A/A 거짓 양성률을 플랫폼이 자동으로 보여 주게 한다.

### 2. 증상 하나에 첫 번째 원인 후보로 조사를 닫는다 ⚠

- **현상**: 지역별 합이 전체보다 적다는 보고에 "결측 때문"이라 답하고 결측 행을 채웠다. 차이가 그대로다.
- **보이는 형태**: 0-2절 (2)에서 "부족"은 연결 실패·절단·필터·결측을 모두 포함했다. 실제는 고객 ID 표기 불일치(미연결 8%)였다([18-5](../18-data-cleaning-and-quality/2-summary.md)).
- **원인**: 모양 분류를 확정으로 읽었다. 같은 모양에 원인 후보가 여럿이다.
- **대처**: 표의 "확인 방법" 칸을 후보마다 하나씩 실행한다. 미연결 비율, 행 수 한도, 0 비율, 필터 조건을 나란히 놓는다.

### 3. 두 숫자를 같게 만들려고 정의를 바꾼다

- **현상**: 두 대시보드의 CTR(0.14·0.22)이 다르다는 지적에 한쪽 쿼리를 다른 쪽에 맞췄다. 그 지표를 쓰던 다른 리포트의 추세가 하루 사이 꺾인다.
- **보이는 형태**: 숫자는 같아졌다. 과거 값과의 연속성이 끊기고, 왜 바꿨는지 기록이 없다.
- **원인**: 둘 다 맞는 정의였다([16-3](../16-metrics-design/2-summary.md)). 정의 차이를 버그로 다뤘다.
- **대처**: 지표 명세에 분자·분모·분석 단위·분위수 방법을 적고 이름을 나눈다("CTR(노출 가중)"·"사용자 평균 CTR"). 바꿔야 하면 변경 시점을 대시보드에 표시한다.

### 4. 부분군 반전을 보고 "부분군이 정답"으로 단정한다 ⚠

- **현상**: 전체는 효과 +, "같은 방문 수끼리"는 효과 0이라 기능을 폐기했다. 이후 구매가 줄었다.
- **보이는 형태**: 층 변수(방문 수·장바구니 금액)가 처리 이후에 정해지는 값이었다([25-1](../25-causal-inference-basics/2-summary.md) · [12-5](../12-correlation-vs-causation/2-summary.md)).
- **원인**: 4절의 심슨의 역설 처방(층별로 판단)을 매개 변수에도 적용했다.
- **대처**: 층을 나누기 전에 화살표를 그린다. 처리 전에 정해진 교란 변수(기기·가입 시점)는 층화·표준화하고, 처리 뒤에 정해진 변수는 전체 효과 추정에서 통제하지 않는다. 처리 전 변수라도 DAG에서 충돌 변수면 통제하지 않는다([25](../25-causal-inference-basics/2-summary.md) 뒷문 기준).

### 5. 고친 뒤 같은 증상을 다시 잡을 장치를 두지 않는다 ⚠

- **현상**: 시간대 문제를 고친 지 석 달 뒤 새 대시보드에서 같은 문제가 난다. 새 백분위 패널이 또 `avg(quantile)`로 만들어진다.
- **보이는 형태**: 같은 leaf 시나리오가 다른 화면에서 반복된다([17-2](../17-sql-for-analysis/2-summary.md) · [05-1](../05-percentiles-and-latency-distributions/2-summary.md)).
- **원인**: 고친 것이 쿼리 하나였다. 규칙(정의·검사)은 남기지 않았다.
- **대처**: 0-2절의 첫 계산을 자동 검사로 남긴다. 실험 플랫폼의 SRM 경보, 리포트 옆 원천 대조, 날짜 집계 함수의 시간대 인자 검사, 분위수 방법 명세다.

## 핵심 문장

- 분석의 오류는 예외가 아니라 **틀린 모양의 숫자**로 보인다. 첫 단서는 비율이 설계와 다름, 합계가 원천과 다름, 결과가 지나치게 좋음, 전체와 부분의 방향이 반대, 날짜 경계에서만 다름, 도구마다 다름 같은 모양이다.
- 실험 결과는 SRM과 분석 단위부터 본다. SRM은 효과 크기를, 분석 단위 불일치는 구간·p값을 전제부터 흔든다.
- "너무 좋은 결과"의 흔한 후보는 단위를 잘게 센 분산 과소, 여러 비교 중 하나 고르기, 엿보기, 누설이다. 효과가 전혀 없어도 독립 지표 20개면 하나 이상 유의할 확률이 약 64%다.
- 부분군 반전은 구성비를 먼저 본다. 대체로 층 변수가 처리 전에 정해지면(교란 후보) 층별·표준화로, 처리 뒤에 정해지면(매개·충돌 후보) 층으로 나누지 않고 판단한다. 다만 처리 전 변수도 충돌 변수일 수 있고(M-편향), 관찰 자료의 전체 차이는 교환가능성 같은 식별 가정이 있어야 인과 효과다. 그 판단은 숫자가 아니라 인과 화살표가 정한다.
- 백분위는 순위에서 나오는 값이라 평균으로 합칠 수 없고, 정의(보간·위치 공식)가 도구마다 다르다. 원자료나 버킷을 합친 뒤 한 정의로 계산한다.
- 모양은 원인 후보를 고를 뿐이다. 확정은 leaf의 확인 계산으로 하고, 고친 뒤에는 같은 계산을 자동 검사로 남긴다.
