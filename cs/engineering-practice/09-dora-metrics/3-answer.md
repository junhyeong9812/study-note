# engineering-practice/09-dora-metrics — 정답

## 정답

### 1. 왜 필요하고, 다섯 지표는 무엇인가

- 없으면: 개발은 "빨라졌다", 운영은 "장애가 늘었다"고 일화로 다툰다. 어디가 병목인지도 정할 수 없다.
- dora.dev 가이드(2026-01-05) 기준

| 묶음 | 지표 | 정의 요지 |
|---|---|---|
| 처리량 | 변경 리드 타임 | 커밋 → 운영 배포까지 걸린 시간 |
| 처리량 | 배포 빈도 | 기간당 배포 수 또는 배포 간격 |
| 처리량 | 실패 배포 복구 시간 | 즉시 개입이 필요한 실패 배포에서 복구까지 |
| 불안정성 | 변경 실패율 | 배포 뒤 즉시 개입(롤백·핫픽스)이 필요했던 배포 비율 |
| 불안정성 | 배포 재작업률 | 계획에 없었고 운영 사고 때문에 한 배포의 비율 |

### 2. 복구 시간의 분류와 2023년 변경

- 2015년 모델: 처리량(배포 빈도·리드 타임) vs **안정성**(MTTR·변경 실패율). 복구 시간은 안정성 쪽이었다.
- 지금 모델(2024년 이후, dora.dev 가이드·history 글): 실패 배포 복구 시간은 **처리량** 쪽이다. 어느 연도 보고서인지 밝혀야 하는 이유다.
- 2023년 변경 이유(history 글): MTTR·time to restore는 변경이 일으킨 장애와 외부 요인(데이터센터 장애 등)을 구분하지 않았다. 새 정의는 운영 변경이 일으킨 손상에서의 복구만 본다.

### 3. 게이밍 예측 — 실험 출력

| 지표 | honest | gamed |
|---|---|---|
| 배포 빈도 | 2.6회/주 (9회) | 7.6회/주 (26회) |
| 리드 타임 중앙값 | 50.0h | 50.0h (그대로) |
| 변경 실패율 | 22.2% (2/9) | 7.7% (2/26) |
| 복구 시간 중앙값 | 3.38h | 3.38h (그대로) |
| 재작업률 | 11.1% (1/9) | 0.0% (0/26) |

- 재배포는 새 커밋을 싣지 않는다. 그래서 리드 타임은 안 바뀐다.
- 변경 실패율은 분모만 커져서 내려간다. 재작업률은 분류를 바꿔서 0이 된다.
- 사고 건수(2)와 복구 시간은 그대로다. 사용자가 겪는 것은 바뀌지 않았다.

### 4. 게이밍과 진짜 개선을 가르는 신호

- 신호 1 — **지표들이 함께 움직이나.** gamed는 배포 빈도만 오르고 리드 타임은 50.0h 그대로였다. daily는 배포 빈도(5.8회/주)와 리드 타임(4.0h)이 같이 좋아졌다.
- 신호 2 — **원시 이벤트 감사.** 새 커밋 없는 배포 수가 gamed 17회, daily 0회였다. 사고 티켓과 연결된 배포 수를 재작업률과 대조하는 것도 같은 종류의 감사다.

### 5. `rev-list A..B`의 함정

- 범위 문법 `A..B`는 "B에서 도달 가능하고 A에서 도달 불가능한 커밋"이다. B가 A의 조상(또는 같은 커밋)이면 결과가 빈다. 롤백·옛 버전 재배포가 바로 이 경우다(A가 단지 시간상 새 커밋인 것만으로는 비지 않는다 — 갈라진 브랜치면 B 쪽 커밋이 나온다). 그다음 배포에서 옛 SHA부터 다시 세어 이미 배포된 커밋을 또 센다.
- 실험의 첫 버전이 이 버그로 커밋 21개를 24개로 셌다.
- 고침: 이미 배포된 커밋 집합을 기억하고, 배포마다 `git log <SHA>`(조상 전체) 중 처음 보는 커밋만 센다. 커밋 DAG의 도달 가능성 + 집합 차이다.

### 6. 리드 타임이 갑자기 짧아짐

- 원인 1 — 시작점 정의 변경: 예전 도구는 첫 커밋, 새 도구는 PR 머지 시각에서 잰다.
- 원인 2 — rebase(대화형 squash·fixup 포함)는 **커미터 날짜**를 바꾸고 작성자 날짜는 둔다. 실험: rebase 전 committer 2026-09-02, 후 2026-09-09, author는 2026-09-02 그대로. 커미터 날짜로 재면 rebase 직후 배포된 변경이 짧게 잡힌다.
  - `git merge --squash` 뒤의 커밋은 새 커밋이라 작성자 날짜까지 커밋한 시각이 된다(점검 재실험, git 2.43.0). 이때는 작성자 날짜로 재도 원래 시작점을 잃는다.
- 대처: 시작점을 문서로 정한다. 정의를 바꾼 날을 그래프에 표시하고, 전환 전후 몇 주는 두 정의로 함께 잰다.

### 7. "맞바꿈이 아니다"의 근거 종류

- DORA 설문 데이터에서 다섯 지표가 대부분의 팀에서 **상관**한다는 관찰이다(dora.dev 가이드 "Key insights").
- 상관은 인과가 아니다. 좋은 팀은 작은 묶음·자동화·테스트 같은 공통 원인 때문에 둘 다 좋을 수 있다.
- "배포 횟수만 늘리면 장애가 준다"고 하면 원인(작은 묶음·자동화)을 빼고 결과 숫자만 흉내 내는 셈이다. 3번의 gamed가 그 결과다.
- 가이드가 권하는 실제 지렛대는 변경 묶음 크기를 줄이는 것이다.

### 8. 팀별 순위 대시보드

- 해당 함정(dora.dev "Common pitfalls")
  - Making disparate comparisons — 지표는 앱·서비스 단위다. 다른 시스템끼리 비교하면 오해를 부른다.
  - Competing — 목표는 자기 팀의 개선이지 경쟁이 아니다.
  - Setting metrics as a goal — 순위는 사실상 목표가 되어 게이밍을 부른다(굿하트).
- 제안: 각 서비스를 **자기 과거와** 비교하는 추세 그래프를 둔다. 조직 수준에서는 분포만 본다. 팀마다 가장 큰 병목 하나를 골라 개선 계획을 세운다(가이드 "Next steps").
