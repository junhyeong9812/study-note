# engineering-practice/09-dora-metrics — DORA 지표: 배포 빈도·리드 타임·변경 실패율·복구 시간·재작업률 — 정리 (힌트)

## 해결하는 문제

"요즘 배포가 나아졌나?"라는 질문에 느낌으로만 답하면 논쟁이 끝나지 않는다.

- 개발팀은 "빨라졌다"고 하고, 운영팀은 "장애가 늘었다"고 한다. 둘 다 근거가 일화 한두 개다.
- 무엇을 고쳐야 하는지도 정할 수 없다. 리뷰가 느린지, 테스트가 느린지, 배포가 무서운지 모른다.

쉬운 예: 식당 주방이다.

```text
  주문 접수 ──> 조리 ──> 서빙 ──> (손님이 돌려보냄?) ──> 다시 조리해서 서빙
     │                      │              │                      │
     └── 주문→서빙 시간 ───┘              │                      │
          하루 서빙 접시 수               돌려보낸 비율           다시 내기까지 걸린 시간
```

- 주방이 빠른지는 "주문에서 서빙까지 걸린 시간"과 "하루에 낸 접시 수"로 본다.
- 주방이 안정적인지는 "돌려보낸 접시 비율"과 "다시 내기까지 걸린 시간"으로 본다.

똑같은 구조다. 소프트웨어에서는 커밋이 주문이고, 운영 배포가 서빙이다.

- *DORA(DevOps Research and Assessment)*: 2014년부터 소프트웨어 전달 성과를 설문·통계로 연구해 온 프로그램. 지금은 Google Cloud가 운영한다(dora.dev 하단 표기).
- *DORA 지표*: 이 연구가 소프트웨어 전달 성과를 재는 데 쓰는 지표 묶음. dora.dev 가이드(2026-01-05 갱신) 기준 다섯 개다.
  - 흔한 오해: "DORA 지표 = 4개(four keys)". 4개는 2023년까지의 모델이다. 2024년에 다섯 번째(배포 재작업률)가 추가됐다(dora.dev "A history of DORA's software delivery metrics", 2026-01-02).

실무 예:
- 경영진이 "연말까지 모든 서비스가 하루 여러 번 배포한다"는 목표를 내린다. dora.dev 가이드가 함정으로 든 문장이 바로 이 모양이다. 팀은 일하는 방식보다 숫자를 맞추는 쪽으로 움직이기 쉽다(굿하트의 법칙, 아래 장애 1).
- 대시보드 도구를 바꿨더니 리드 타임이 하룻밤 새 절반이 됐다. 일하는 방식은 그대로다. 측정 시작점의 정의가 바뀐 것이다(장애 3).

## 동작·원리

### 1. 다섯 지표가 재는 자리

```text
  커밋 ──────────────> 운영 배포 ──> 정상?
   │                     │            ├─ 예 ─────────────────────────────> (다음 배포)
   │                     │            └─ 아니오(즉시 개입 필요) ─> 롤백/핫픽스 ─> 복구
   │                     │                    │                         │      │
   └─ 변경 리드 타임 ────┘                    │                         │      │
      배포 빈도 = 기간당 배포 수                │                         │      │
                                 변경 실패율 = 실패 배포 / 전체 배포      │      │
                       배포 재작업률 = 계획에 없던(사고 대응) 배포 / 전체 배포    │
                                         실패 배포 복구 시간 = 실패 배포 → 복구 ──┘
```

dora.dev 가이드(2026-01-05) 정의를 그대로 옮긴다.

| 지표 | 정의(원문 요지) | 묶음 |
|---|---|---|
| 변경 리드 타임(change lead time) | 변경이 버전 관리에 커밋된 때부터 운영에 배포될 때까지 걸린 시간 | 처리량 |
| 배포 빈도(deployment frequency) | 주어진 기간의 배포 횟수, 또는 배포 사이 간격 | 처리량 |
| 실패 배포 복구 시간(failed deployment recovery time) | 실패해서 즉시 개입이 필요한 배포로부터 복구하는 데 걸린 시간 | 처리량 |
| 변경 실패율(change fail rate) | 배포 뒤 즉시 개입이 필요했던 배포의 비율. 보통 롤백이나 핫픽스로 이어진다 | 불안정성 |
| 배포 재작업률(deployment rework rate) | 계획에 없었지만 운영 사고 때문에 일어난 배포의 비율 | 불안정성 |

- *처리량(throughput)*: 일정 기간에 시스템을 통과해 운영까지 가는 변경의 양.
- *불안정성(instability)*: 배포가 얼마나 잘 되는지. 배포가 잘 될수록 더 자신 있게 더 많이 내보낸다.
- 지금의 묶음에서 **복구 시간은 처리량** 쪽이다(dora.dev 가이드·history 글 모두). 2015년 모델은 MTTR을 안정성(stability) 쪽에 두었다.
  - 흔한 오해: "복구 시간은 안정성 지표". 2015~2023년 모델에서는 맞았다. 2024년 이후 모델에서는 처리량으로 분류한다. 어느 연도 보고서를 읽는지 밝혀야 한다.

### 2. 정의는 해마다 바뀌었다

dora.dev "A history of DORA's software delivery metrics"(Nathen Harvey, 2026-01-02)의 연표다.

```text
 2014  변수 4개로 시작: 배포 빈도·리드 타임·MTTR·변경 실패율
       → 변경 실패율은 나머지와 하나의 잠재 구성개념으로 묶이지 않아, "IT 성과"는 3개로 정의
 2015  처리량(배포 빈도·리드 타임) vs 안정성(MTTR·변경 실패율) 두 축
 2018  가용성(availability) 추가 → "IT 성과" 대신 "SDO(소프트웨어 전달·운영) 성과"
 2021  가용성 → 신뢰성(reliability)으로 확장. 2021 보고서가 이를 "다섯 번째 지표"라 부른 것은
       부정확했다고 history 글이 정정 (신뢰성은 전달이 아니라 운영 성과)
 2023  MTTR / time to restore service → 실패 배포 복구 시간으로 이름·정의 변경
 2024  다섯 번째 지표: 배포 재작업률 추가 → 처리량 3 + 불안정성 2
 2025  보고서가 클러스터 분석으로 "팀 프로필(아키타입) 7개"를 제시 (Google Cloud 블로그 2025-09-23, 한국 시각 09-24)
```

- *MTTR(mean time to recover)*: 서비스 장애에서 복구하기까지의 평균 시간. 원인을 가리지 않는다.
- 2023년에 바꾼 이유(history 글): 옛 정의는 **변경이 일으킨 장애**와 **외부 요인(데이터센터 장애 등)** 을 구분하지 않았다. 새 정의는 운영 변경이 일으킨 손상에서의 복구만 본다.
- 2024년 재작업률을 넣은 이유(history 글): 변경 실패율이 팀이 해야 하는 재작업의 양을 대신 나타내는 지표(proxy)로 작동했다. 이를 확인하려고 재작업률을 따로 쟀다.
- 2025년 보고서의 프로필 7개 중 블로그가 이름을 밝힌 것은 둘이다("Foundational challenges", "Harmonious high achievers"). 이것이 예전의 엘리트·상·중·하 4군을 대체했는지는 블로그에 쓰여 있지 않다. 2차 출처들은 대체했다고 쓴다 `[?]`(보고서 본문 미열람).

### 3. 속도와 안정성은 맞바꿈이 아니다 — DORA의 연구 주장

```text
  흔한 직관                         DORA 데이터의 관찰
  빠름 ◄─────────► 안정             상위 팀: 다섯 지표 모두 좋음
   (하나를 얻으면 하나를 잃는다)     하위 팀: 다섯 지표 모두 나쁨  → 지표끼리 상관
```

- dora.dev 가이드: 연구가 "속도와 안정성은 맞바꿈이 아님"을 거듭 보였고, 대부분의 팀에서 지표들이 서로 **상관**한다.
- 이것은 설문 데이터의 상관 관찰이다. "배포를 늘리면 장애가 준다"는 인과를 보인 것이 아니다.
- 가이드가 권하는 개선 방향은 **변경 묶음(batch) 크기를 줄이는 것**이다. 작은 변경은 이해·전달이 쉽고, 실패해도 복구가 쉽다(가이드 "Next steps").

### 4. 지표가 목표가 되면 — 굿하트의 법칙

- *굿하트의 법칙(Goodhart's law)*: 측정값을 통제 목표로 삼아 압력을 주면, 그 측정값이 원래 나타내던 것을 더는 나타내지 않게 된다는 관찰. 경제학자 Charles Goodhart(1975)의 이름을 땄다. 흔히 인용되는 "측정이 목표가 되면 좋은 측정이 아니게 된다"는 문장은 인류학자 Marilyn Strathern(1997)의 표현으로 알려져 있다 `[?]`(원문 쪽수 미확인).
- dora.dev 가이드의 "Common pitfalls"(요지)

| 함정 | 가이드의 설명 |
|---|---|
| 지표를 목표로 삼기 | "모든 앱은 연말까지 하루 여러 번 배포" 같은 선언이 게이밍 가능성을 키운다 |
| 하나의 지표로 다 보기 | 서로 긴장 관계에 있는 여러 지표를 함께 본다 |
| 업종을 핑계로 삼기 | "규제 업종이라 못 바꾼다" |
| 다른 것끼리 비교 | 지표는 앱·서비스 단위. 모바일 앱과 메인프레임 비교는 오해를 부른다 |
| 소유권 쪼개기 | 다섯 지표를 개발·운영·릴리스가 함께 본다 |
| 경쟁 | 목표는 자기 팀의 시간에 따른 개선이지 다른 팀과의 경쟁이 아니다 |
| 개선보다 측정에 몰두 | 정밀한 수집 연동에 큰 투자를 하기보다 대화·Quick Check로 시작 |

### 실험: git 이력 + 배포 로그로 다섯 지표를 계산하고, 게이밍을 재현한다

**시뮬레이션이다.** 실제 팀 데이터가 아니다. 스크립트가 일회용 git 저장소에 커밋 시각을 정해 만들고, 배포 로그(CSV)를 함께 쓴다.

세 시나리오는 기능 커밋 20개(4주)와 실패 배포 2건(하나는 롤백으로 45분 뒤 복구, 하나는 핫픽스 배포로 6시간 뒤 복구)을 똑같이 갖는다.

| 시나리오 | 배포 방식 |
|---|---|
| honest | 3.5일마다 모아서 배포 8회 + 핫픽스 배포 1회(계획에 없음) |
| gamed | honest와 같은 배포 + 첫 배포 뒤의 기능 커밋마다(17개) **이미 배포된 버전을 다시 배포**(새 코드 없음) + 핫픽스를 "계획됨"으로 기록. 첫 배포 전 커밋 3개는 다시 배포할 버전이 없어 건너뛴다 |
| daily | 새 커밋이 있는 날마다 배포(작은 묶음). 실패 2건은 그대로 둔다(작은 묶음이 실패를 줄인다는 효과는 넣지 않았다) |

계산기 핵심(`dora.js`, Node 18). 리드 타임은 커밋마다 "그 커밋을 처음 포함한 배포 시각 − 커밋 시각"이다.

```js
// 배포 로그를 시간순으로 훑으며, 이번 배포 SHA에서 도달 가능한 커밋 중 처음 보는 것만 센다
const leads = [], seen = new Set();
let noop = 0;
for (const d of rows) {
  const before = seen.size;
  for (const line of git('log', '--format=%H %ct %s', d.sha).split('\n').filter(Boolean)) {
    const [h, ct] = line.split(' ');
    if (seen.has(h)) continue;          // 같은 버전 재배포·롤백 재배포에서 두 번 세지 않는다
    seen.add(h);
    leads.push((d.t - Number(ct) * 1000) / H);
  }
  if (seen.size === before) noop++;     // 새 커밋이 하나도 없는 배포
}
const failed = rows.filter(d => d.result === 'failed');      // 변경 실패율·복구 시간
const unplanned = rows.filter(d => d.planned === 'no');      // 배포 재작업률
```

- 단순화: 실패한 배포에 들어 있던 커밋도 그 배포 시각을 "배포됨"으로 셌다. 롤백된 커밋을 언제 배포된 것으로 칠지는 팀이 정해야 하는 정의 문제다.
- 배포 빈도의 기간은 첫 배포부터 마지막 배포까지다.

(실험, git 2.43.0 / Node 18.19.1, 2026-10-05 — 입력이 고정이라 실행마다 같은 출력)

```text
== honest
배포 빈도          2.6 회/주 (배포 9회, 3.4주)
변경 리드 타임     중앙값 50.0 h (커밋 21개)
변경 실패율        22.2 % (2/9)
실패 배포 복구 시간 중앙값 3.38 h (2건)
배포 재작업률      11.1 % (1/9)
(점검) 새 커밋 없는 배포 0회
== gamed
배포 빈도          7.6 회/주 (배포 26회, 3.4주)
변경 리드 타임     중앙값 50.0 h (커밋 21개)
변경 실패율        7.7 % (2/26)
실패 배포 복구 시간 중앙값 3.38 h (2건)
배포 재작업률      0.0 % (0/26)
(점검) 새 커밋 없는 배포 17회
== daily
배포 빈도          5.8 회/주 (배포 19회, 3.3주)
변경 리드 타임     중앙값 4.0 h (커밋 21개)
변경 실패율        10.5 % (2/19)
실패 배포 복구 시간 중앙값 3.38 h (2건)
배포 재작업률      5.3 % (1/19)
(점검) 새 커밋 없는 배포 0회
```

- 관찰 1: gamed는 배포 빈도가 2.6 → 7.6회/주로 세 배 가까이 늘었다. 변경 실패율은 22.2% → 7.7%, 재작업률은 0%가 됐다. **사고 수(2건)와 복구 시간(3.38h)은 그대로다.**
- 관찰 2: gamed의 리드 타임은 honest와 같은 50.0h다. 배포 빈도만 오르고 리드 타임이 그대로면 "배포가 실제 변경을 실어 나르지 않는다"는 신호다. 서로 긴장 관계인 지표를 같이 봐야 하는 이유다.
- 관찰 3: daily는 배포 빈도가 오르면서 리드 타임도 50.0h → 4.0h로 줄었다. 진짜 개선은 여러 지표가 **함께** 움직인다.
- 관찰 4: 변경 실패율은 분모(배포 수)를 부풀리면 내려간다. 원시 이벤트를 감사하는 점검 줄(새 커밋 없는 배포 17회)이 게이밍을 드러냈다.
- 해석: 이 실험은 숫자를 조작하는 방법이 얼마나 쉬운지를 보일 뿐이다. 실제 팀의 행동이 이렇게 변한다는 것을 측정한 것은 아니다.

## 쓰이는 자료구조·알고리즘

- **커밋 DAG의 도달 가능성** — "배포 N에 처음 들어간 커밋"은 `배포 N의 SHA에서 도달 가능한 커밋 − 이미 배포된 커밋`이다. 실험은 `git log <sha>`(조상 전체)와 집합 차이로 구했다. 배포가 순서대로만 나아가면 `git rev-list <직전 SHA>..<이번 SHA>`와 같다. 재배포·롤백으로 옛 SHA가 끼면 범위 문법은 같은 커밋을 다시 센다(실험 첫 버전에서 커밋 21개가 24개로 세어졌다).
  - 커밋 객체가 부모 해시를 가리키는 구조는 [data-structure/27-merkle-tree](../../data-structure/27-merkle-tree/2-summary.md), git 객체 모델은 [03-version-control-and-git-internals](../03-version-control-and-git-internals/2-summary.md).
- **중앙값·백분위** — 리드 타임·복구 시간은 꼬리가 길다. 평균은 긴 꼬리 몇 건에 끌려간다. 같은 이유를 SLI에서 다룬 것이 [reliability/02-slo-sli-error-budget](../../reliability/02-slo-sli-error-budget/2-summary.md) "평균은 꼬리를 숨긴다".
- **비율의 분모** — 변경 실패율·재작업률은 "배포 수"가 분모다. 분모의 정의(재배포 포함? 설정 변경 포함?)가 숫자를 정한다.
- **이벤트 조인** — 배포 이벤트(CI/CD)와 사고 이벤트(사고 관리 도구)를 시간·서비스·SHA로 이어 붙여야 "실패 배포"와 "복구 시각"이 생긴다.

## 적용 — 풀어나가는 법

### 1. 순서

1. **단위를 정한다.** 앱·서비스 하나씩 잰다(dora.dev: 지표는 앱·서비스 단위).
2. **이벤트 정의를 문서로 합의한다.** 아래 표의 빈칸을 팀이 채운다. 정의가 바뀌면 그날 이후 그래프에 표시한다.
3. **기준선을 잰다.** 처음엔 DORA Quick Check나 대화로도 된다. 가이드는 정밀 수집 연동보다 대화부터 권한다.
4. **가장 큰 병목 하나**를 고른다. 예: 리뷰 대기, 느린 테스트, 수동 배포 단계.
5. 그 병목을 줄일 **선행 지표**를 따로 잰다. 가이드의 예: 코드 리뷰 소요 시간, 테스트 품질.
6. 다시 재고 회고한다. 반복한다.

| 결정할 정의 | 선택지 예 | 이 노트 실험의 선택 |
|---|---|---|
| 리드 타임 시작점 | 커미터 날짜 / 작성자 날짜 / PR 생성 / 머지 | 커미터 날짜(`%ct`) |
| "배포" | 운영 반영만 / 설정 변경 포함 / 같은 버전 재배포 포함 | 로그의 모든 행(재배포 포함 — 그래서 게이밍이 통했다) |
| "실패" | 롤백 / 핫픽스 / 사고 선언 / 기능 플래그 끄기 | 로그의 `failed` |
| "복구" 시각 | 롤백 완료 / 핫픽스 배포 / 사고 종료 | 로그의 `recovered_at` |
| "계획에 없던 배포" | 사고 티켓에 연결된 배포 / 핫픽스 브랜치 | 로그의 `planned=no` |

### 2. 배포 이벤트를 남기는 법 (예시)

- 파이프라인 마지막 단계가 SHA·시각·결과를 기록하게 한다. 사람이 손으로 쓰는 "계획됨" 칸은 게이밍 통로가 되기 쉽다. 사고 티켓 연결처럼 다른 시스템이 남긴 사실로 정하는 편이 낫다.

```yaml
# (예시) CI 배포 잡의 마지막 단계 — 배포 이벤트 한 줄을 남긴다
- name: record deployment
  if: always()
  run: |
    planned=yes; [ -n "${INCIDENT_ID}" ] && planned=no   # 사고 대응 배포에만 INCIDENT_ID를 붙이는 규칙일 때
    echo "$(date -u +%Y-%m-%dT%H:%M:%SZ),${GIT_SHA},${DEPLOY_RESULT},,${planned}" >> deploys.csv
```

- 주의: DORA 정의는 "계획에 없었고 **운영 사고 때문에** 일어난 배포"다. 사고 티켓이 붙었어도 원래 계획된 릴리스라면 재작업이 아니다. 티켓 연결은 판정 규칙(예시)이지 정의 자체가 아니다.
- 집계 쪽은 Java로도 같은 원리다. "이 커밋이 이 배포에 들어 있나"는 `git merge-base --is-ancestor <커밋> <배포 SHA>`의 종료 코드(0 = 들어 있음)로 판정할 수 있다.

```java
// 커밋이 배포 SHA의 조상인지 (git merge-base --is-ancestor: 조상이면 종료 코드 0)
static boolean deployedIn(String commit, String deploySha, File repo) throws Exception {
    Process p = new ProcessBuilder("git", "merge-base", "--is-ancestor", commit, deploySha)
            .directory(repo).start();
    return p.waitFor() == 0;
}
```

### 3. 진단 — 숫자가 이상할 때 보는 것

- 배포 빈도가 뛰었는데 리드 타임이 그대로 → 새 커밋 없는 배포 수를 센다(실험의 점검 줄).
- 변경 실패율이 갑자기 떨어졌다 → 분모(배포 수)가 늘었는지, "실패" 정의가 바뀌었는지 본다.
- 리드 타임이 갑자기 짧아졌다 → 시작점 정의가 바뀌었는지, rebase·squash로 커미터 날짜가 바뀌었는지 본다(장애 3).

## 장애 시나리오와 대처

### 1. 지표를 목표로 → 게이밍 (⚠ 커리큘럼, 굿하트)

- 현상: "분기 말까지 배포 빈도 3배" 목표가 내려온 뒤 숫자가 달성됐다. 그런데 기능 출시 속도와 장애는 그대로다.
- 보이는 형태: 배포 빈도↑, 변경 실패율↓, 재작업률 0%. 리드 타임·사고 건수·복구 시간은 그대로. 실험의 gamed 출력이 이 모양이다(7.6회/주, 7.7%, 0.0%, 리드 타임 50.0h).
- 원인: 지표를 목표·평가에 직접 묶었다. 같은 버전 재배포, 핫픽스를 "계획됨"으로 표기하는 식으로 분모·분류가 조작된다.
- 대처
  - 지표는 팀의 개선 도구로 쓰고, 평가·순위에 쓰지 않는다(dora.dev "Competing" 함정).
  - 다섯 지표를 **묶음으로** 본다. 하나만 좋아지면 의심한다.
  - 원시 이벤트를 감사한다: 새 커밋 없는 배포 수, 사고 티켓과 연결된 배포 수.
  - 분류는 사람이 손으로 정하는 칸 대신 다른 시스템의 사실(사고 티켓 연결)로 정한다.

### 2. 팀끼리 순위를 매김 → 맥락 무시

- 현상: 전사 대시보드에 팀별 배포 빈도 순위가 걸린다. 펌웨어·결제 코어 팀이 늘 꼴찌다.
- 보이는 형태: 하위 팀이 지표 개선 대신 "우리는 다르다"는 설명 자료를 만든다. 또는 장애 1의 게이밍으로 간다.
- 원인: 서로 다른 시스템을 같은 잣대로 비교했다. dora.dev는 이를 "Making disparate comparisons" 함정으로 든다.
- 대처: 비교 대상은 **같은 서비스의 과거**다. 조직 수준에서는 분포와 추세만 보고, 팀 이름을 붙인 순위는 쓰지 않는다.

### 3. 정의가 바뀌어 숫자가 튐

- 현상: 측정 도구를 바꾼 날 리드 타임이 50h에서 4h로 떨어졌다. 일하는 방식은 그대로다.
- 보이는 형태: 그래프에 계단. 예전 도구는 "첫 커밋", 새 도구는 "PR 머지" 시각에서 잰다.
- 원인 하나 더 — rebase는 커미터 날짜를 바꾼다. 작성자 날짜는 둔다. 커미터 날짜로 재면 rebase 직후 배포된 변경의 리드 타임이 짧게 나온다.

(실험, git 2.43.0, 2026-10-05 — rebase 시각을 `GIT_COMMITTER_DATE`로 고정)

```text
rebase 전: author 2026-09-02T09:00:00+00:00 | committer 2026-09-02T09:00:00+00:00
rebase 후: author 2026-09-02T09:00:00+00:00 | committer 2026-09-09T09:00:00+00:00
```

- 대처: 시작점을 문서로 정하고(적용 1의 표), 정의를 바꾸면 그래프에 표시한다. 바꾸기 전후 몇 주는 두 정의로 함께 잰다.

### 4. 복구 시간에 외부 장애가 섞임

- 현상: 클라우드 리전 장애가 있던 달에 "복구 시간"이 폭등했다. 팀은 배포를 하지도 않았다.
- 원인: MTTR식 정의는 원인을 가리지 않는다. DORA가 2023년에 지표를 "실패 배포 복구 시간"으로 바꾼 이유가 바로 이것이다(history 글).
- 대처: 배포가 일으킨 사고와 외부 요인 사고를 나눠 기록한다. 외부 요인 장애는 [reliability/02](../../reliability/02-slo-sli-error-budget/2-summary.md)의 SLO·에러 버짓이나 [reliability/26](../../reliability/26-incident-response-and-postmortem/2-summary.md)의 사고 기록으로 본다.

### 5. 측정에 몰두하느라 개선을 안 함

- 현상: 지표 수집 파이프라인을 석 달째 만든다. 아직 병목 하나도 안 고쳤다.
- 원인: 정밀도에 과투자. dora.dev는 "Focusing on measurement at the expense of improvement"를 함정으로 든다.
- 대처: 대략의 기준선(대화·Quick Check)으로 시작해 가장 큰 병목부터 고친다. 수집 자동화는 개선이 돌기 시작한 뒤에 한다.

## 핵심 문장

- DORA 지표는 dora.dev 2026-01 기준 다섯 개다: 처리량(리드 타임·배포 빈도·실패 배포 복구 시간) + 불안정성(변경 실패율·배포 재작업률).
- 정의는 해마다 바뀌었다. 2023년에 MTTR이 실패 배포 복구 시간으로, 2024년에 재작업률이 추가됐다. 숫자를 인용할 때는 연도와 정의를 함께 쓴다.
- "속도와 안정성은 맞바꿈이 아니다"는 DORA 설문 데이터의 상관 관찰이다. 인과 증명이 아니다.
- 지표를 목표로 삼으면 분모·분류가 조작된다. 실험에서 같은 버전 재배포만으로 배포 빈도는 2.6 → 7.6회/주, 변경 실패율은 22.2% → 7.7%가 됐다. 사고 수는 그대로였다.
- 진짜 개선은 여러 지표가 함께 움직인다. 작은 묶음(daily)에서는 배포 빈도와 리드 타임(50.0h → 4.0h)이 같이 좋아졌다.
- 지표는 같은 서비스의 과거와 비교한다. 다른 팀과의 순위에 쓰지 않는다.
