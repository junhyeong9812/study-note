# engineering-practice/05-code-review — 질문

## 질문

1. (왜) 코드 리뷰의 목적이 "버그 잡기"뿐이라면 어떤 연구 결과와 어긋나나? Bacchelli & Bird(2013)와 Sadowski 외(2018)가 보고한 리뷰의 주요 효과·기대를 말하라.
2. (경계) Google에서 변경 하나가 병합되려면 어떤 세 가지 승인이 필요한가? 리뷰어가 몇 명이어야 하나?
3. (경계) Google eng-practices의 승인 기준은 무엇인가? "완벽해질 때까지 승인하지 않는다"와 어떻게 다른가? `Nit:`는 무엇을 표시하나?
4. (경계) PR 크기에 관한 다음 수치들을 출처와 성격(지침·측정·벤더 사례 연구)으로 짝지어라: 100줄/1000줄, 중앙값 24줄, 한 번에 200~400줄·60~90분 이하, 약 200줄.
5. (예측) 30개 호출부 이름 바꾸기와 경계 조건 1줄 변경을 한 PR에 섞은 경우와 두 커밋으로 나눈 경우, 총 변경 줄 수와 "동작을 판단해야 할 줄 수"는 각각 어떻게 되나? `git diff -w`는 도움이 되나?
6. (예측) 작은 커밋(2줄 변경)에 주석 한 줄을 더해 amend한 뒤 `git range-diff main v1 v2`를 기본값으로 돌리면 어떻게 표시될까? 왜 그런가, 어떻게 고치나?
7. (장애 진단) 2,000줄 PR이 10분 만에 댓글 없이 승인됐고, 그 안의 경계 조건 변경이 장애를 냈다. 무엇이 실패했고, 재발 방지책은?
8. (장애 진단) PR이 평균 사흘씩 리뷰를 기다리고 PR 크기가 점점 커진다. 이 악순환의 고리와, eng-practices·DORA가 권하는 대처는?
9. (연결) 리뷰 댓글의 절반이 들여쓰기·이름 취향이다. 무엇을 리뷰 밖으로 빼야 하나? 그리고 리뷰가 하지 못하는 일은 무엇에 맡겨야 하나?
