# engineering-practice/05-code-review — 정답

## 정답

### 1. 리뷰의 목적은 버그 잡기만이 아니다

- Bacchelli & Bird(ICSE 2013, Microsoft): 결함 찾기가 **주된 동기**였지만, 실제 리뷰는 기대보다 결함과 덜 관련됐다. 지식 전달, 팀 인식 향상, 대안 제시가 컸다. 리뷰의 핵심 요소는 코드와 변경의 **이해**였다.
- Sadowski 외(ICSE-SEIP 2018, Google — 인터뷰 12건·설문 44명·리뷰 로그 약 900만 변경): 인터뷰에서 나온 기대 주제 4가지 — 교육, 규범 유지, 게이트키핑, 사고 예방. 결함 찾기는 환영하지만 유일한 초점이 아니다.
- SWE@G 9장: 정확성 확인은 Google이 리뷰에서 얻는 주된 이점이 아니다.

### 2. Google의 세 승인

- LGTM(다른 엔지니어의 정확성·이해 확인), 코드 소유자 승인(이 영역에 맞나), readability 승인(언어 스타일·관례).
- 한 사람이 세 자격을 다 가지면 리뷰어 1명으로 된다. Sadowski 2018: 리뷰어가 2명 이상인 변경은 25% 미만, 리뷰어 수 중앙값 1.

### 3. 승인 기준

- CL이 시스템의 **코드 건강을 분명히 개선**하면 완벽하지 않아도 승인 쪽으로 기운다. "There is no such thing as 'perfect' code—there is only better code."
- "완벽해질 때까지"는 진행을 막고 리뷰를 느리게 해 품질까지 떨어뜨린다(eng-practices Speed 문서: 긴 리뷰는 질 낮은 코드 승인 압력·리팩터링 회피를 낳는다).
- `Nit:`는 고치면 좋지만 필수는 아닌 사소한 지적 표시다.

### 4. 크기 수치의 출처

| 수치 | 출처 | 성격 |
|---|---|---|
| 100줄 적당, 1000줄 대개 과대 | Google eng-practices "Small CLs" | 지침(최종 판단은 리뷰어) |
| 약 200줄 | SWE@G 9장 | 회사 관례(책) |
| 수정 줄 수 중앙값 24 | Sadowski 외 2018 | 측정(Google) |
| 200~400줄 이하·60~90분 이하 | Cohen 2006, Cisco 사례(SmartBear) | 벤더 사례 연구 |

- 모두 "작게"를 가리키지만 절대 기준이 아니다.

### 5. 섞기 vs 나누기

- 총 변경 줄 수는 같다: 둘 다 62줄(31 insertions + 31 deletions), 최종 트리도 같다(`same-tree`).
- 동작을 판단해야 할 범위
  - 섞으면 31개 파일 62줄 전체에서 동작 변경을 찾아야 한다.
  - 나누면 rename 커밋(62줄)은 컴파일·테스트로 기계적 확인, 동작 커밋은 **2줄**(`amount <= max` → `amount < max`)만 깊게 본다.
- `-w`는 공백만 무시하므로 이름 바꾸기를 걸러 내지 못한다(여전히 31 files changed). `--word-diff`는 줄 안의 `<=` → `<`를 드러내지만 파일을 다 넘겨야 하는 건 같다.

### 6. `range-diff`의 creation factor

- 기본값(60)에서는 수정된 커밋을 짝짓지 못하고 `2: f36f657 < -: -------`(삭제) + `-: ------- > 2: 1557497`(추가)로 표시했다.
- 이유: range-diff는 두 커밋의 "diff의 diff" 줄 수를 비용으로 최소 비용 할당을 푼다. 통째 삭제·추가에는 그 패치 크기에 creation factor(%)를 곱한 비용이 붙는다. 패치가 2줄로 작으면 주석 한 줄 추가가 상대적으로 큰 변화로 보여 "새로 만든 커밋"으로 판정된다.
- `--creation-factor=100`으로 올리자 `2: f36f657 ! 2: 1557497`로 짝이 맞고 바뀐 줄만 보였다. 문서도 큰 변경을 통째 재작성으로 오판하면 값을 키우라고 한다.

### 7. 거대 PR의 형식적 승인

- 실패한 것: 리뷰어가 이해할 수 있는 양을 넘었다. 기계적 변경 속에 동작 변경이 묻혔다. 리뷰 시간·댓글 수가 크기에 비해 비정상적으로 적은 것이 신호다. Cisco 사례에서 시간당 450줄 넘게 검토한 리뷰의 87%가 결함 밀도 평균 미만이었다.
- 재발 방지
  - PR 크기 경고·상한(팀이 정함), 구조 변경과 동작 변경 분리.
  - 리뷰어는 너무 크면 분할을 요청한다(eng-practices).
  - 동작 변경에는 회귀 테스트를 함께 넣어 리뷰어가 테스트로 확인하게 한다.

### 8. 리뷰 대기의 악순환

- 고리: 리뷰가 늦다 → 작성자가 위에 작업을 쌓는다 → PR이 커진다 → 리뷰가 더 늦고 얕아진다 → 브랜치가 오래 산다 → 머지 지옥(04).
- 대처
  - eng-practices: 응답은 최대 1영업일, 사소한 남은 댓글만 있으면 "LGTM with comments", 큰 CL은 나눠 달라고 요청.
  - DORA trunk-based 함정: 너무 무거운 리뷰(여러 승인 필수)와 비동기 대기를 줄인다. 필수 승인 수를 최소화한다(Google은 대부분 1명).
  - 소유자를 분산해 한 사람에게 몰리지 않게 한다.

### 9. 리뷰 밖으로 뺄 것

- 포맷·린트·스타일 규칙은 포매터·린터를 CI에서 강제한다(SWE@G 9장 "Automate Where Possible"). 사람은 설계·동작·이해에 집중한다. 남는 사소한 의견은 `Nit:`.
- 리뷰가 하지 못하는 일: 모든 실행 경로의 동작 보증. 그것은 테스트와 CI가 맡는다. 리뷰는 "테스트가 그 동작을 실제로 검증하나"를 본다.
