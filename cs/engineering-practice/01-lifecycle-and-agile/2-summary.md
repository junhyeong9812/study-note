# engineering-practice/01-lifecycle-and-agile — 개발 수명 주기·애자일·회고 루프 — 정리 (힌트)

## 해결하는 문제

소프트웨어를 만드는 일에는 순서가 필요하다. 무엇을 만들지 정하고, 만들고, 확인하고, 내보낸다.\
문제는 **언제 무엇을 배우느냐**다. 순서를 잘못 짜면 틀린 것을 늦게 안다.

```text
  한 번에 끝까지 (빅뱅)                       짧게 여러 번 (반복)
  ┌────────────── 6개월 ──────────────┐       ┌─2주─┐┌─2주─┐┌─2주─┐ ...
  요구 → 설계 → 구현 → 테스트 → 공개        만들기·보여주기·고치기를 반복
                                   ↑                ↑     ↑     ↑
                     여기서 처음 "이게 아닌데"     매번 "이게 아닌데"를 일찍 듣는다
```

- *개발 수명 주기(software development life cycle)*: 소프트웨어가 구상되어 만들어지고 운영되다 폐기될 때까지 거치는 단계와 그 순서.
- *반복(iteration)*: 같은 단계 묶음(계획·만들기·확인)을 짧게 여러 번 도는 것.
- *점진(increment)*: 반복마다 동작하는 결과물이 조금씩 커지는 것.

쉬운 예: 손님 요리다.
- 레시피대로 끝까지 만든 뒤 처음 맛보면, 짜도 되돌릴 수 없다.
- 중간중간 맛보면 간을 고칠 수 있다. 맛보고도 **간을 안 고치면** 맛본 의미가 없다.

똑같은 구조다.\
반복형 개발에서 "맛보기"는 스프린트 리뷰(제품)와 회고(일하는 방식)다. "간 고치기"는 회고에서 나온 행동을 실제로 하는 것이다.

실무 예:
- 6개월 만에 공개한 기능을 사용자가 거의 쓰지 않는다. 요구가 개발 중에 바뀌었는데 되돌릴 지점이 없었다.
- 스프린트·데일리 스크럼·회고를 다 하는데, 같은 배포 실패가 석 달째 반복된다. 회고에서 매번 같은 말이 나오지만 아무도 고치지 않는다. 커리큘럼이 이 영역의 ⚠로 든 **"의식만 남은 애자일"** 이다.

## 동작·원리

### 1. 수명 주기 모델 네 가지

```text
  (1) 순차형 — 단계를 한 번씩
      요구 ─▶ 설계 ─▶ 구현 ─▶ 테스트 ─▶ 운영

  (2) 반복·점진형 — 작은 전체를 여러 번
      [요구·설계·구현·테스트] ─▶ [요구·설계·구현·테스트] ─▶ ...   매번 동작하는 결과물

  (3) 나선형 — 위험이 큰 것부터 확인
          ┌───── 위험 분석 ─────┐
          │   위험 해소(시제품 등) → 평가 → 다음 바퀴 계획    바퀴마다 "가장 큰 위험"을 먼저 없앤다
          └─────────────────────┘

  (4) 지속적 전달 — 반복의 끝을 운영까지 붙인다
      커밋 ─▶ 빌드·테스트 ─▶ 배포 ─▶ 운영 지표 ─▶ 다음 커밋     (06·09번)
```

- *순차형(흔히 "폭포수")*: 앞 단계가 끝나야 다음 단계로 간다. 요구가 안정적이고 변경 비용이 큰 곳(예: 규제 인증 문서가 필요한 장비)에서 쓴다.
    - 흔한 오해: Royce의 1970년 논문(IEEE WESCON)이 폭포수를 권했다. 실제로는 순차 모델을 그린 뒤 "I believe in this concept, but the implementation described above is risky and invites failure."라고 쓰고, "STEP 3: DO IT TWICE"(첫 결과를 최종 제품의 이른 시뮬레이션으로)를 권했다. 논문 본문에는 "waterfall"이라는 단어가 없다(원문 PDF의 web.archive.org 사본에서 확인). 이 이름은 1976년 Bell–Thayer 논문이 처음 썼을 수 있다고 Wikipedia "Waterfall model"이 적는다(2차 출처, 그 문서도 더 나은 출처가 필요하다고 표시).
- *나선형*: Boehm이 낸 위험 주도 모델(1986 ACM SIGSOFT *Software Engineering Notes*에 먼저, 1988 IEEE *Computer*에 같은 제목으로). 바퀴마다 가장 큰 위험을 확인한다. 수단은 위험에 맞게 고른다. 1988년 원문은 시제품 말고도 시뮬레이션·벤치마킹·사용자 설문·분석 모델 등을 든다.
- SWEBOK v4는 수명 주기를 10장 Software Engineering Process에서 다룬다. v4는 애자일과 DevOps를 여러 지식 영역에 넣었다(IEEE Computer Society SWEBOK 소개 페이지).

### 2. 애자일 — 가치 4개, 원칙 12개

- 애자일 선언(2001)의 가치 4개와 "오른쪽도 가치 있지만 왼쪽을 더 중시한다"는 원본 노트에 정리돼 있다. 기초는 [원본 「애자일이란 무엇인가」](../../engineering/agile-and-squad/2-summary.md) 참고.
- 이 노트는 원칙 12개 중 수명 주기와 바로 닿는 것만 짚는다(agilemanifesto.org/principles.html 원문).

| 원칙 | 원문 요지 | 수명 주기에 주는 뜻 |
|---|---|---|
| 1 | 가치 있는 소프트웨어를 일찍, 지속적으로 전달 | 결과물이 반복마다 나온다 |
| 2 | 늦은 요구 변경도 환영 | 변경을 막는 대신 변경 비용을 낮춘다 |
| 3 | 몇 주~몇 달 간격으로, 짧을수록 좋게 | 반복 길이 |
| 7 | 작동하는 소프트웨어가 진척의 1차 척도 | "문서 90% 완료"는 진척이 아니다 |
| 10 | 단순함 — 안 해도 되는 일의 양을 최대화 | 범위 줄이기가 기본 수단 |
| 12 | 정기적으로 더 효과적인 방법을 돌아보고 행동을 조정 | **회고** |

- 12번 원칙은 "돌아본다(reflects)"에서 끝나지 않고 "**행동을 조정한다**(tunes and adjusts its behavior)"까지 간다. 의식만 남은 애자일은 앞 절반만 한다.

### 3. 스크럼의 검사·적응 루프

스크럼 가이드(2020년 11월판)는 스크럼을 *경험적 프로세스*로 정의한다. 기둥은 투명성·검사·적응이다.

```text
  투명성 ──▶ 검사 ──▶ 적응
  (보이게)    (보고)     (바꾼다)

  스프린트(1개월 이하, 길이 고정)
  ┌──────────────────────────────────────────────────────────────┐
  │ 스프린트 계획    데일리 스크럼(15분)        스프린트 리뷰   회고 │
  │ 무엇을·어떻게    스프린트 목표 진척 검사     제품을 검사      일하는 방식을 검사
  │                                                            │
  │                                      개선 행동 ─────────────┼──▶ 다음 스프린트 백로그
  └──────────────────────────────────────────────────────────────┘
```

- *경험적 프로세스(empirical process)*: 미리 짠 계획을 믿는 대신, 관찰한 결과로 다음 행동을 정하는 방식.
- *회고(Sprint Retrospective)*: 가이드 원문은 목적을 "품질과 효과를 높일 방법을 계획하는 것"으로 적고, 영향이 큰 개선은 **다음 스프린트 백로그에 넣을 수도 있다**고 쓴다.
    - 흔한 오해: 회고 = 불만을 말하는 자리. 가이드의 목적은 "계획"이다. 다음에 무엇을 바꿀지가 나오지 않으면 목적을 못 이룬 것이다.
- 타임박스(가이드 원문): 스프린트 1개월 이하, 계획 최대 8시간·리뷰 최대 4시간·회고 최대 3시간(모두 1개월 스프린트 기준), 데일리 스크럼 15분.
- 참고: 원본 노트 「스크럼」의 "역할 3가지(개발팀)"와 "데일리 스크럼 — 어제/오늘/장애물 공유"는 2017년판까지의 표현이다. 2020년판은 하나의 스크럼 팀 안의 세 *책임*(Product Owner·Scrum Master·Developers)으로 바꿨고 하위 팀이 없다고 쓴다. 데일리 스크럼의 세 질문도 빠졌고, 형식은 개발자가 고르되 스프린트 목표 진척에 집중하라고만 한다(scrumguides.org 2020판 본문·revisions 페이지).

### 4. 회고 루프는 어디서 끊기나

```text
  관찰 ──▶ 원인 ──▶ 행동 항목 ──▶ 백로그에 넣기 ──▶ 실행 ──▶ 효과 확인
   "배포가     "수동 단계가   "배포 스크립트에   담당·기한     다음 회고에서
    또 실패"    3개"          검증 추가"         있음          같은 문제가 줄었나?
       ✗ 끊김①      ✗ 끊김②         ✗ 끊김③         ✗ 끊김④        ✗ 끊김⑤
```

| 끊기는 곳 | 보이는 모습 |
|---|---|
| ① 관찰 없음 | 회고를 건너뛴다. "바빠서 이번엔 생략" |
| ② 원인 없이 증상만 | "다음엔 더 조심하자" |
| ③ 행동이 모호 | "소통을 잘하자" — 검증할 수 없다 |
| ④ 백로그에 안 들어감 | 담당·기한이 없다. 스프린트 일에 밀린다 |
| ⑤ 효과 확인 없음 | 행동은 했는데 문제가 줄었는지 아무도 안 본다 |

- 의식만 남은 애자일은 대개 ③·④에서 끊긴다. 회고는 열리는데 다음 스프린트 백로그에 아무것도 안 들어간다.
- ⑤가 빠지면 반대 방향의 낭비도 생긴다. 효과 없는 행동 항목을 매번 실행하며 시간만 쓴다. 아래 실험의 시나리오 B가 이 모습이다.

### 실험: 회고 루프의 세 모드 — 시뮬레이션

실측이 아니다. 가정한 수치로 돌린 **모델**이다. 주장은 하나다. "회고는 행동 항목이 실행되고, 그 행동이 반복되는 원인을 겨냥할 때만 이득이다."

- 모델(모든 수치는 예시): 팀의 반복당 가용 시간 100시간. 반복되는 문제 5종(발생 확률 0.6·0.5·0.4·0.3·0.3, 발생 시 잃는 시간 12·10·8·6·6시간).
  - NONE: 회고 없음.
  - RITUAL: 회고 2시간. 가장 비싼 문제를 이야기하지만 담당·기한이 없어 실행 확률 10%.
  - REAL: 회고 2시간. 가장 비싼 문제의 행동 항목을 다음 반복 백로그에 넣어 실행(8시간), 80% 확률로 그 원인이 사라진다.
  - 시나리오 A는 원인이 반복된다. 시나리오 B는 문제마다 원인이 새로워 고쳐도 사라지지 않는다.

```java
// RetroSim.java 핵심 — 회고에서 가장 비싼 문제 하나를 골라 행동 항목으로
if (worst >= 0 && mode != Mode.NONE) {
    double doProb = mode == Mode.REAL ? 1.0 : 0.1;   // RITUAL은 담당·기한이 없어 10%만 실행
    if (rnd.nextDouble() < doProb) {
        pendingFixCost = 8;                            // 다음 반복에서 8시간을 쓴다
        if (recurring && rnd.nextDouble() < 0.8) fixed[worst] = true;   // 원인 제거
    }
}
```

(실험, 시뮬레이션 — JDK 21 temurin 21.0.12, `java RetroSim.java 42`, 2000회 평균, 2026-10-05)

```text
== 시나리오 A: 같은 원인의 문제가 반복된다
모드     반복1  반복3  반복6  반복12 | 12회 합계 | 반복된 문제(12회 합)
NONE      81.0   80.7   81.1   81.2 |    972.1 |  20.21
RITUAL    78.9   79.4   80.5   82.4 |    968.7 |  17.65
REAL      78.6   80.2   88.5   96.1 |   1054.8 |   4.37
== 시나리오 B: 문제마다 원인이 새롭다(고쳐도 다른 이유로 또 난다)
모드     반복1  반복3  반복6  반복12 | 12회 합계 | 반복된 문제(12회 합)
NONE      81.0   80.7   81.1   81.2 |    972.1 |  20.21
RITUAL    79.2   77.9   77.8   78.2 |    940.1 |  20.24
REAL      79.2   71.1   71.2   71.4 |    865.7 |  20.24
```

- 시드 7·2026으로도 돌렸다. 시나리오 A의 12회 합계는 NONE 972.0~973.8, RITUAL 967.1~969.8, REAL 1054.5~1055.7이었다.
- 관찰
  - 시나리오 A: REAL은 반복 1·3에서 NONE보다 적게 낸다(회고·수정 비용). 반복 6에서는 앞선다(표에 없는 반복 4·5는 확인하지 않았다). 반복된 문제 수는 약 4로 준다(NONE 약 20).
  - RITUAL은 회고 비용만 내고 반복된 문제가 거의 그대로다(약 17.5). "의식만 남은 애자일"의 모습이다.
  - 시나리오 B: 행동 항목이 원인을 못 없애면 REAL이 가장 손해다(865.7). 효과 확인(끊김 ⑤)이 없으면 이 손해를 모른다.
- 해석: 회고의 가치는 "회고를 했나"가 아니라 "**다음 반복의 문제 수가 줄었나**"로 잰다. 이 결론은 모델 가정(문제가 반복된다, 고치면 사라진다)에 기대므로, 실제 팀에서는 회고 기록으로 같은 문제의 반복 횟수를 세어 확인해야 한다(적용 3).

### 5. 팀 구조 — 스쿼드와 콘웨이

- 스쿼드·트라이브·챕터·길드와 콘웨이의 법칙은 [원본 「스쿼드 방식」·「콘웨이의 법칙」](../../engineering/agile-and-squad/2-summary.md)에 정리돼 있다.
- 출처를 보탠다.
  - 스쿼드 모델의 원문은 Kniberg·Ivarsson의 2012년 백서 "Scaling Agile @ Spotify"다. Kniberg는 이를 "레시피가 아니라 지금 하는 일의 스냅숏"이라고 했다(2차 출처 인용으로 확인).
  - 전 Spotify 직원 Jeremiah Lee는 2020년 글 "Spotify's Failed #SquadGoals"에서, 백서의 모델이 회사 안에서도 그대로 작동하지 않았다고 썼다(한 사람의 증언이다).
- 참고: 원본 「콘웨이의 법칙」의 인용 연도 "(1967)"은 원 논문 게재 연도와 다르다. Conway의 "How Do Committees Invent?"는 *Datamation* 1968년 4월호에 실렸다(melconway.com의 논문 페이지). 원본 「관련 자료」의 1968년 표기가 맞다.

## 쓰이는 자료구조·알고리즘

- **피드백 제어 루프**: 회고는 "측정 → 목표와 비교 → 조정"을 도는 폐루프다. 측정(효과 확인)이 빠지면 열린 루프가 되어, 조정이 맞았는지 모른다(위 끊김 ⑤).
- **우선순위 큐에 가까운 목록**: 스크럼 가이드 2020은 제품 백로그를 "순서가 매겨진 목록(ordered list)"이라고만 쓴다. 순서의 기준을 우선순위 하나로 정하지 않는다. 스프린트 계획에서는 개발자가 PO와 논의해 항목을 고른다. 맨 앞부터 기계적으로 꺼내는 규칙은 없다. 비슷한 자료구조는 [data-structure/07-heap](../../data-structure/07-heap/) 참고. 실무에서는 사람이 다시 정렬하므로 힙보다 "정렬된 목록 + 재정렬"에 가깝다.
- **큐와 리틀의 법칙**: 칸반 보드는 단계마다 WIP 상한을 둔 큐다. 정상 상태에서 평균 리드 타임 = 평균 WIP ÷ 평균 처리율(L=λW). 처리율이 같으면 WIP를 줄일수록 리드 타임이 준다. 수식과 조건은 [reliability/21-scaling-principles](../../reliability/21-scaling-principles/2-summary.md)와 [math 영역 표 10 queueing-and-littles-law](../../math/README.md)(원고 있음) 참고.
- **시뮬레이션(몬테카를로)**: 위 실험은 난수로 같은 과정을 여러 번 돌려 평균을 낸다. 추정에 쓰는 법은 [12-estimation-and-planning](../12-estimation-and-planning/2-summary.md)에서 다룬다.

## 적용 — 풀어나가는 법

### 1. 수명 주기를 고르는 질문

| 질문 | 예 → 쪽으로 | 아니오 → 쪽으로 |
|---|---|---|
| 요구가 개발 중에 바뀔 가능성이 큰가? | 반복·점진 | 순차도 가능 |
| 한 번 내보낸 뒤 고치는 비용이 큰가?(펌웨어·규제 인증) | 앞 단계 검증을 두껍게(나선·순차 요소) | 자주 내보내기 |
| 가장 큰 위험이 기술적으로 미지인가? | 나선 — 위험부터 확인(시제품·시뮬레이션 등) | 반복 |
| 운영까지 한 팀이 책임지는가? | 지속적 전달(06번) | 인계 지점 명시 |

- 순수한 모델 하나를 고르기보다 섞는 경우가 많다. 예: 요구 대부분은 앞에서 정하고, 구현·테스트·배포만 짧게 반복한다. McConnell은 이 중간 지점을 따로 설명한다([12번](../12-estimation-and-planning/2-summary.md)의 불확실성 원뿔).

### 2. 회고를 행동으로 바꾸는 형식

```text
  회고 기록 (스프린트 23)
  ─────────────────────────────────────────────
  관찰: 배포 실패 2회 (태그: deploy-manual-step)
  원인: 마이그레이션 실행이 수동이고 체크리스트에 없음
  행동: 배포 스크립트가 마이그레이션 버전을 확인하고 다르면 중단
  담당: A · 기한: 스프린트 24 안 · 백로그 항목: OPS-118
  효과 확인: 스프린트 25 회고에서 태그 deploy-manual-step 재발 횟수
```

- 행동 항목에는 **담당·기한·백로그 링크·효과 확인 방법**을 붙인다. 넷 중 하나라도 빠지면 위 끊김 ③~⑤ 중 하나다.
- 한 번에 행동 1~3개만 고른다(예시). 많으면 다 밀린다.

### 3. 진단 — 같은 문제가 반복되나

회고 기록에 태그를 달아 두면, 반복 여부를 셀 수 있다.

```java
// 태그별로 그 태그가 달린 회고 기록 수를 센다(스프린트당 기록이 1건이면 = 등장 스프린트 수)
// threshold번 이상 나온 태그는 "다시 조사할 후보"
record RetroNote(int sprint, Set<String> tags) {}

static Map<String, Long> recurring(List<RetroNote> notes, int threshold) {
    return notes.stream()
        .flatMap(n -> n.tags().stream())
        .collect(Collectors.groupingBy(t -> t, TreeMap::new, Collectors.counting()))
        .entrySet().stream()
        .filter(e -> e.getValue() >= threshold)
        .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue, (a, b) -> a, TreeMap::new));
}
```

- 같은 태그가 계속 나오는 것은 다시 조사하라는 신호다. 원인을 증명하지는 않는다. 흔한 경우는 셋이다. 행동 항목이 실행되지 않았거나(④), 실행됐는데 원인을 못 건드렸거나(⑤), 같은 증상이 다른 원인으로 다시 났다(위 실험의 시나리오 B). 첫째면 백로그 넣기부터, 나머지는 원인 분석을 다시 한다.

### 4. DoD와 작은 증분

- *DoD(Definition of Done)*: 스크럼 가이드 원문 정의는 "증분이 제품에 요구되는 품질 기준을 만족한 상태에 대한 공식 서술"이다.
    - 흔한 오해: DoD = 스토리별 수용 기준. 수용 기준은 기능마다 다르고(02번), DoD는 모든 증분에 공통이다(예: 테스트 통과·리뷰·문서 갱신).
- DoD를 회고에서 고친다. 가이드도 회고에서 DoD를 검사 대상으로 든다.
- 혼자·소규모일 때 무엇을 살리고 버릴지는 [원본 「개인·소규모 개발에 애자일을 어떻게 적용하는가」](../../engineering/agile-and-squad/2-summary.md)에 있다.

## 장애 시나리오와 대처

### 1. 의식만 남은 애자일 — 회고 없음·같은 문제 반복 (⚠)

- 현상: 스프린트·데일리·회고 일정은 그대로인데 같은 사고가 반복된다.
- 보이는 형태: 회고 기록에 같은 문장("배포 조심", "요구 명확히")이 매번 나온다. 사고 기록의 원인 태그가 같다. 회고가 "이번엔 생략"으로 자주 빠진다.
- 원인: 회고 루프가 행동 항목·백로그·효과 확인에서 끊겼다(동작·원리 4).
- 대처: 행동 항목에 담당·기한·백로그 링크를 붙인다. 다음 회고는 지난 행동의 효과 확인부터 시작한다. 반복 태그를 센다(적용 3).

### 2. 스프린트 안의 미니 폭포수

- 현상: 스프린트 마지막 날 테스트가 몰리고, 못 끝낸 일이 다음 스프린트로 넘어간다.
- 보이는 형태: 번다운 차트가 마지막 2~3일까지 평평하다. "개발 완료, 테스트 대기"가 쌓인다.
- 원인: 스프린트 안에서도 설계 → 구현 → 테스트를 순차로 한다. 큰 스토리를 쪼개지 않았다.
- 대처: 스토리를 얇은 수직 조각으로 쪼갠다. 진행 중 작업 수를 제한한다(칸반의 WIP 상한). 테스트를 구현과 함께 쓴다.

### 3. 속도(velocity)를 목표로 삼음

- 현상: 스토리 포인트 합계는 오르는데 사용자에게 나가는 기능은 그대로다.
- 보이는 형태: 같은 크기의 일에 매기는 포인트가 점점 커진다. 팀 간 속도 비교표가 생긴다.
- 원인: 속도는 계획용 관찰값인데 성과 지표로 쓰였다. 지표를 목표로 삼으면 지표가 망가진다(굿하트의 법칙 — [09-dora-metrics](../09-dora-metrics/2-summary.md)에서 다룬다). 스크럼 가이드 2020년판에는 속도나 스토리 포인트가 나오지 않는다.
- 대처: 속도는 팀 안의 계획에만 쓴다. 성과는 전달된 결과(09번 지표·사용자 지표)로 본다.

### 4. 다른 회사의 조직 모델을 그대로 복사

- 현상: 팀 이름을 스쿼드·트라이브로 바꿨는데 일하는 방식은 그대로다.
- 보이는 형태: 스쿼드가 배포하려면 다른 팀 승인이 필요하다. 챕터 리드의 책임이 불분명하다.
- 원인: 해결하려는 문제 없이 모양을 복사했다. 원문 백서도 스스로를 스냅숏이라고 했다(동작·원리 5).
- 대처: "독립 배포가 안 되는 이유"처럼 구체적 문제에서 시작해, 조직과 아키텍처를 함께 바꾼다(콘웨이). 기초는 원본 「스포티파이 모델의 함정」.

### 5. 스프린트 중 범위가 계속 늘어남

- 현상: 스프린트 목표를 매번 못 이룬다.
- 보이는 형태: 스프린트 시작 뒤 추가된 항목 수가 많다. 회고마다 "외부 요청이 많았다"가 나온다.
- 원인: 스프린트 목표를 지킬 장치가 없다. 또는 일의 성격이 계획형이 아니라 유입형(운영·지원)이다.
- 대처: 추가 요청은 PO를 거친다. 스크럼 가이드 2020은 스프린트 중 "스프린트 목표를 위태롭게 하는 변경은 하지 않는다"고 쓰고, 범위는 PO와 다시 협의할 수 있다고 쓴다. 그래서 목표를 해치는 요청은 제품 백로그로 보내 다음 계획에서 다루고, 목표를 해치지 않는 범위 조정은 이번 스프린트 안에서 PO와 협의한다. 유입형 일이 많으면 칸반(WIP 상한)으로 바꾸거나 따로 떼어 둔다.

## 핵심 문장

- 수명 주기 모델은 "언제 무엇을 배우느냐"를 정한다. 반복형은 틀린 것을 일찍 알게 해 준다.
- 애자일 원칙 12번은 돌아보기에서 끝나지 않고 행동을 바꾸는 데까지 간다.
- 스크럼은 투명성·검사·적응의 루프이고, 회고는 일하는 방식을 검사해 다음 스프린트 백로그로 넘기는 자리다.
- 의식만 남은 애자일은 회고 루프가 행동 항목·백로그·효과 확인에서 끊긴 상태다.
- 회고의 가치는 회고를 했는지가 아니라 같은 문제가 줄었는지로 잰다. 효과 없는 행동 항목은 오히려 비용이다(시뮬레이션 시나리오 B).
