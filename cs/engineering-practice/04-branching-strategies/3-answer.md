# engineering-practice/04-branching-strategies — 정답

## 정답

### 1. 브랜치는 싸지만 갈라진 시간은 비싸다

- 비용은 브랜치 생성이 아니라 **merge-base 이후 양쪽에 쌓인 변경**이다.
- 쌓이는 것
  - 텍스트 충돌: 같은 영역을 서로 다르게 고친 곳.
  - 의미 충돌: 텍스트는 안 겹치는데 합치면 깨지는 곳.
  - 맥락 유실: 오래전 변경이라 충돌을 푸는 사람이 의도를 모른다.
  - 통합 공포: 병합이 아프니 더 미루는 악순환(Fowler 2020).

### 2. trunk-based의 출처별 기준

| 출처 | 기준 |
|---|---|
| trunkbaseddevelopment.com | 단일 trunk에서 협업, 장수 개발 브랜치를 만들지 않음. 짧은 기능 브랜치는 "a couple of days", 이틀 넘으면 위험. 한 사람(페어 둘) |
| DORA capability(2016·2017 보고서) | 활성 브랜치 3개 이하, 하루 1회 이상 trunk 병합, 코드 동결·통합 단계 없음 |
| SWE@G 16장 | trunk-based + 테스트·CI + 빌드 green + 미완성 기능은 런타임에 끔. 수치 기준은 제시하지 않음 |

- 공통: 짧게, 자주 합치고 미완성은 브랜치가 아닌 다른 수단으로 숨긴다.
- 차이: 이틀 / 하루 1회·3개 이하 / 수치 없음.

### 3. git-flow의 범위

- 2010-01-05 Driessen의 모델: `master`·`develop` + feature·release·hotfix.
- 2020-03-05 노트: 지속적으로 전달하는 웹 앱은 처음 염두에 둔 종류가 아니었다. 그런 팀에는 GitHub flow 같은 훨씬 단순한 흐름을 권한다. **명시적으로 버전을 매기는 소프트웨어, 또는 여러 버전을 동시에 지원해야 하는 소프트웨어**라면 여전히 맞을 수 있다고 쓴다.

### 4. 통합 주기 시뮬레이션

(시뮬레이션 — 스크립트로 만든 커밋, git 2.43.0, 시드 1~5)

| 주기 | 충돌 줄 합계 | 충돌 난 병합 1회당 줄 |
|---|---|---|
| 1일 | 94~151 | 6.6~9.8 |
| 20일 | 802~864 | 267.3~288.0 |

- 합계는 20일 주기가 약 5.3~9.1배. 그리고 전부가 마지막 날 한 번의 통합에 몰린다.
- 덩어리 수는 5일 주기(48~61)가 20일 주기(43~51)보다 많거나 같았다(시드 3은 둘 다 48). 오래 갈라지면 인접 충돌이 큰 덩어리 하나로 합쳐지기 때문으로 보인다(해석). 덩어리 수만 보면 "오래 갈라져도 충돌이 적다"고 오해한다.
- 한계: 줄 덮어쓰기·균등 무작위 위치 모델이며, 의미 충돌은 세지 않았다.

### 5. 의미 충돌

- git: 서로 다른 파일을 바꿨으므로 `Merge made by the 'ort' strategy.`, 충돌 표식 0.
- 빌드: `javac`가 `Refund.java:2: error: cannot find symbol ... method total(long)`로 실패(실험, OpenJDK 21.0.12).
- 그래서 병합마다(또는 병합 예정 결과에) CI 빌드·테스트가 돌아야 한다.

### 6. 브랜치에 숨기기 vs 런타임에 숨기기

- 브랜치: 코드가 병합일까지 `main`에 들어오지 않는다 → 통합이 병합일로 미뤄진다.
- 런타임(플래그): 코드는 매일 `main`에 들어가 통합·빌드·테스트되고, **켜는 결정**만 따로 한다.
- Hodgson 분류의 **Release toggle**. 수명은 짧게(주 단위), 정적. 전환 후 제거해야 한다 — "inventory which comes with a carrying cost".

### 7. Branch by Abstraction

1. 기존 결제 구현 주위에 추상(예: `PaymentGateway` 인터페이스)을 도입해 커밋한다. 여러 커밋이어도 되지만 빌드는 계속 green이어야 한다.
2. 추상 뒤에 새 구현을 작성하되 트렁크 안에서 꺼 둔다(다른 개발자가 아직 의존하지 않게).
3. 스위치(플래그·설정)를 켜서 새 구현으로 전환한다.
4. 옛 구현을 지운다.
5. 추상을 지운다(필요 없으면).

- 매 단계가 `main`에 들어가므로 장수 브랜치가 필요 없다(trunkbaseddevelopment.com).

### 8. 릴리스 브랜치 수정의 재발

- 원인: 수정이 릴리스 브랜치에만 들어가고 트렁크로 옮겨지지 않았다. 1.3은 트렁크에서 땄으므로 수정이 없다.
- 권장 방향: 트렁크에서 재현 → 테스트와 함께 수정 → CI 확인 → 릴리스 브랜치로 **체리픽**. 릴리스 브랜치는 트렁크로 병합하지 않고 수명이 끝나면 지운다.
- 점검: `git cherry -v main release/1.2`로 릴리스 브랜치에만 있는(트렁크에 같은 패치가 없는) 수정을 `+`로 찾는다. `git cherry <upstream> <head>`는 head에만 있는 커밋을 보여 주므로 순서가 중요하다(git-cherry 문서).

### 9. trunk-based의 함정(DORA)

- 함정
  - 너무 무거운 리뷰(여러 승인 필수).
  - 비동기 리뷰 — 요청해 두고 다른 일을 하며 기다림 → 병합 지연·충돌.
  - 커밋 전 자동 테스트를 돌리지 않음 → `main`이 빨개짐.
- 대처: 작은 PR과 빠른 리뷰([05](../05-code-review/2-summary.md) — Google eng-practices는 응답 최대 1영업일), 커밋 전·병합 전 CI, 빨간 `main`은 즉시 되돌리기.
