# engineering-practice/16-operational-standards — 정답

## 정답

### 1. 사고 때 커지는 이유

- 평소에는 서비스 하나만 보므로 그 서비스의 형식만 알면 된다.
- 사고 때는 한 요청을 여러 서비스에 걸쳐 따라가야 한다. 로그 검색·대시보드·경보 같은 **공용 도구**는 서비스들이 같은 필드·이름·단위를 쓸 때만 한 번에 동작한다. 형식이 다르면 서비스마다 검색어를 바꾸고, 시각을 손으로 맞추고, 단위를 환산해야 해서 복구가 늦어진다.

### 2. 계약 그림

```text
  서비스들 ──> [운영 표준] ──> 공용 도구
               로그 스키마        → 로그 검색(trace_id로 조인)
               지표 이름·단위      → 대시보드·지표 저장소
               SLI/SLO 정의       → SLO 대시보드·번 레이트 경보
               경보마다 런북       → 온콜 대응
               출시 전 점검(PRR)   → 출시 승인
```

### 3. 줄 수

(실험, Logback 1.5.12 기본 설정, 2026-10-05)

- 이벤트 3건이 **13줄**이었다(ERROR의 스택트레이스 10줄 포함).
- 줄 단위 수집에서는 ERROR 한 건이 메시지 줄 + 예외 줄 + `at ...` 줄들로 **11개 조각**이 된다. 조각에는 레벨·시각이 없어 검색·집계가 어긋난다.

### 4. JSON ≠ 표준

- 표준은 형식(JSON)만이 아니라 **필드 이름·값 형식·어휘**까지 정해야 서비스 사이에서 조인이 된다.
- Logback `JsonEncoder`: timestamp가 ISO-8601 문자열이 아니라 epoch 밀리초 숫자다. `service`·`trace_id` 필드가 없다(MDC가 비어 있었다). 검사 결과 `timestamp 형식(ISO-8601+오프셋) 아님=3, 필드 없음:service=3, 필드 없음:trace_id=3`.
- 서비스 D: 한 줄은 `ts`·`severity`·`traceId`·`msg`라는 다른 이름을 썼고, 다른 줄은 이름은 맞지만 timestamp에 오프셋이 없고(`2026-10-05 02:11:09`) level이 `warning`이었다.

### 5. 검색 결과 차이

(실험, 2026-10-05)

- 글자 검색: D **2건**. 표준 필드 검색: D **1건**.
- D의 첫 줄은 같은 값을 `traceId`라는 다른 필드 이름으로 남겼기 때문이다. 필드 기반 검색·집계(로그 저장소의 필드 질의)에서는 이 이벤트가 빠진다.

### 6. 지표 이름

- `payment_latency_ms`: 기본 단위(seconds)가 아니다. 히스토그램인데 `_seconds`/`_bytes` 접미사가 없다(시간·크기만 허용하는 팀 검사 규칙 — Prometheus 기본 단위는 그 밖에도 있다). 초 단위 지표와 한 그래프에 그리면 1000배 차이.
- `paymentRequestCount`: snake_case가 아니고, 카운터인데 `_total`로 끝나지 않는다.
- `shipping_label_user_10234_total`: 사용자 ID 같은 식별자 값이 이름에 들어갔다. 사용자 수만큼 지표가 생긴다(카디널리티). 문서는 이런 고카디널리티 값을 레이블에도 넣지 말라고 한다.
- 이름 검사기가 못 잡는 것: 이름은 `_seconds`인데 코드가 밀리초 값을 기록하는 경우. 계측 코드 리뷰나 값 범위 검사가 필요하다.

### 7. 공개 규격의 역할

- OpenTelemetry Logs Data Model(Stable): 로그 레코드의 필드 구성(Timestamp·ObservedTimestamp·TraceId·SpanId·SeverityText·SeverityNumber·Body·Resource·Attributes 등 12개)의 근거.
- W3C Trace Context: trace_id의 형식(16바이트, 소문자 16진 32자, 전부 0 무효)과 서비스 간 전파(`traceparent` 헤더)의 근거.
- SeverityNumber: 라이브러리마다 다른 레벨 이름(`WARNING`·`WARN`·`warning`)을 1~24 숫자 축(13~16 = WARN)으로 정규화해, "WARN 이상" 같은 질의를 서비스와 무관하게 쓸 수 있게 한다.

### 8. 타임라인 역전

- 확인: 서비스별 시각 표기(날짜 포함 여부, 오프셋·시간대, 정밀도), 수집기가 찍은 수신 시각과 이벤트 발생 시각 중 무엇으로 정렬했는지. 실험 A처럼 `02:10:59`(날짜·오프셋 없음), `Oct 05, 2026 2:11:01 AM`(현지), `…T17:11:04Z`(UTC)가 섞이면 글자 정렬은 의미가 없다.
- 표준: timestamp는 ISO-8601 + 오프셋 필수, 저장은 UTC. 발생 시각(Timestamp)과 수신 시각(ObservedTimestamp)을 구분해 남긴다.

### 9. 강제 수단과 PRR

- 약한 것 → 강한 것: 위키 문서 → 리뷰 지적 → CI 검사기(로그 샘플·지표 이름) → 서비스 템플릿·공용 라이브러리의 기본값(골든 패스).
- 출시 전 PRR(SRE Book 32장): 시스템 아키텍처와 서비스 간 의존성, 계측·지표·모니터링, 비상 대응, 용량 계획, 변경 관리, 성능(가용성·지연·효율). PRR 통과를 출시 조건으로 두면 "대시보드·경보·런북 없이 출시"가 막힌다. 다만 SRE Book의 PRR은 원래 SRE 팀이 운영 책임을 맡기 전의 전제 절차이고, 출시 조건으로 쓰는 것은 그 점검 영역을 빌려 온 것이다(해석).
