# engineering-practice/14-quality-standards — 정답

## 정답

### 1. 리뷰 편차의 원인

- 기준이 문서·도구가 아니라 **리뷰어 개인에게** 붙어 있으면, 판정은 누가 리뷰하느냐에 따라 달라진다.
- 25010만으로는 풀리지 않는다. 25010은 "analysability" 같은 **어휘**를 줄 뿐, "우리 팀은 빈 `catch`를 허용하지 않는다" 같은 **판정 가능한 문장**을 주지 않는다. 그 문장을 팀이 정하고(기준), 도구로 강제해야(강제) 편차가 줄어든다.

### 2. 세 층

```text
  ① 어휘   ISO/IEC 25010 9특성·하위 특성
  ② 기준   스타일 가이드·규칙 목록·DoD·리뷰 체크리스트
  ③ 강제   포매터 → 린터 → 품질 게이트 → 사람 리뷰
```

- ① 없음: "품질이 나쁘다"의 뜻이 사람마다 달라 논쟁이 사실 대화가 되지 않는다.
- ② 없음: 리뷰 판정이 리뷰어에 달린다(리뷰 편차).
- ③ 없음: 기준이 위키에만 있어 PR마다 같은 지적을 사람이 반복한다.

### 3. 기계 vs 사람

- 기준: **판정이 결정적인가**(같은 입력에 누구나 같은 결론인가).
- 기계: 들여쓰기(포매터), 빈 `catch`, `==` 문자열 비교(린터 — 실험의 PMD 규칙 EmptyCatchBlock·UseEqualsToCompareStrings).
- 사람: "이 추상화가 지금 필요한가", "테스트가 계약을 단언하나" — 맥락과 의도 판단이 필요하다.

### 4. Google eng-practices

- 스타일 가이드가 스타일의 최종 권한(원문 "the absolute authority")이다. 가이드에 없는 스타일 제안은 `Nit:`을 붙여 필수가 아님을 알리고, 개인 취향만으로 CL을 막지 않는다.
- 상위 원칙: CL이 완벽하지 않더라도 시스템 전체의 **코드 건강을 확실히 개선**하는 상태면 승인 쪽으로 기운다. 기술적 사실과 데이터가 의견·취향을 이긴다.
- 이것은 Google의 공개 지침(회사 관례)이지 표준이 아니다.

### 5. 기준선 키

(실험, PMD 7.7.0 · JDK 21.0.12, 2026-10-05)

```text
A 줄번호 키 -> 새 위반 5건 [EmptyCatchBlock:11, UseEqualsToCompareStrings:17, UnusedPrivateMethod:20, UnusedLocalVariable:23, EmptyCatchBlock:26]
B 지문 키   -> 새 위반 2건 [UnusedLocalVariable:23, EmptyCatchBlock:26]
```

- 실제 새 위반은 `refund` 메서드의 2건이다. 줄 번호 키는 3줄 밀린 옛 위반 3건까지 새 위반으로 본다(오탐 3).
- 지문 키(규칙 + 클래스·메서드 + 정규화된 줄 텍스트)는 줄 이동에 강하다. 실험은 파일 하나라 경로를 뺐지만, 저장소 전체 기준선에는 파일 경로(또는 패키지)도 키에 넣어야 다른 파일의 같은 이름 메서드가 합쳐지지 않는다.
- 한계: 같은 메서드 안에 같은 텍스트의 위반이 둘이면 하나로 합쳐진다. 줄의 글자를 고치면 옛 위반이 새 위반으로 보인다. 실제 도구의 지문 방식은 도구마다 다르다.

### 6. `unused` vs `tmp`

- `int tmp = 0;`만 걸린다(실험: v2 23행 UnusedLocalVariable, v1의 `unused`는 미검출).
- PMD 7.7.0 문서: UnusedLocalVariable은 이름이 `ignored`나 `unused`로 시작하는 변수를 거른다(의도적으로 안 쓰는 변수를 표시하는 관례).
- 위험: 규칙의 의도된 예외가 **우회로**가 된다. 위반 수를 목표로 삼으면 이름만 바꿔 수치를 맞추는 굿하트 현상이 생긴다. 억제·예외 사용 수를 따로 보고 리뷰해야 한다.

### 7. 레거시에 게이트를 켰다가 끈 사례

- 잘못: 기존 위반과 새 위반을 구분하지 않고 **전체 위반 수**로 게이트를 걸었다. 아무 PR도 통과할 수 없어 게이트가 꺼졌다.
- 해야 했던 것: 기존 위반을 기준선으로 동결하고 새 코드의 새 위반만 막는다(래칫). 기존 위반은 그 파일을 고칠 때 줄이고, 고친 지문은 기준선에서 지워 커밋한다. `pmd:check`만 걸면 기존 위반도 세므로 비교 단계가 따로 필요하다. 기준선 키는 줄 번호가 아닌 지문으로(5번).
- SonarQube "Sonar way": 조건이 전부 **새 코드** 기준이다 — 새 이슈 0, 새 Security Hotspot 100% 검토, 새 코드 커버리지 ≥ 80%, 새 코드 중복 ≤ 3%. 새 줄(커버리지는 커버 대상 새 줄)이 20줄 미만이면 중복·커버리지 조건은 무시한다(fudge factor). 같은 문서는 Security Hotspot을 단계적으로 없애는 중이라고 적으므로 둘째 조건은 제품 버전에 따라 다를 수 있다.

### 8. DoD와 품질 기준

- Scrum Guide 2020: DoD는 Increment가 제품에 요구되는 **품질 기준**을 충족한 상태의 공식 기술이다. DoD를 못 채운 항목은 릴리스할 수 없고 Sprint Review에도 내놓지 않는다. 조직 표준에 DoD가 있으면 각 스크럼 팀은 최소한 그것을 따른다.
- 품질 기준을 DoD에 걸면 기준은 **완료 조건**이 된다. "리뷰에서 지적하면 고친다"는 리뷰어가 잡아낼 때만 작동하므로 리뷰 편차를 그대로 남긴다. DoD 중 자동화 가능한 항목은 게이트로, 나머지는 체크리스트로 둔다.
