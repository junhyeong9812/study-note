# engineering-practice/02-requirements-engineering — 정답

## 정답

### 1. "빨라야 한다"가 재작업을 부르는 이유

- "빠르다"의 기준이 문장에 없다. 개발자와 기획자가 서로 다른 수치를 떠올려도 동의한 것처럼 보인다. 출시 뒤에야 어긋남이 드러난다.
- 통과·실패를 가를 기준이 없으니 테스트도 쓸 수 없다(실험 v1의 REQ-1: 테스트 0개).
- 고쳐 쓴 예(수치는 예시): "상품 검색 API는 상품 100000건, 초당 50요청에서 p95 응답 시간이 300ms 이하여야 한다." 대상·부하 조건·지표·임계값이 모두 있다.

### 2. 검증과 확인

- 요구 검증(29148 3.1.26): 요구가 **잘 형성됐는지** 검토로 확인한다. 모호어·단일성·측정 기준 같은 문장 품질이다.
- 요구 확인(3.1.25): 요구가 이해관계자가 의도한 **올바른 시스템**을 정의하는지 확인한다. 시제품·데모·인수 테스트로 본다.
- 예: "주문 목록은 최근 30일만 보여 준다"는 잘 쓴 문장이다(검증 통과). 그런데 고객지원팀은 1년치 조회가 필요했다(확인 실패).

### 3. 단일성

- 한 문장에 요구가 둘이면, 테스트 하나가 어느 요구를 확인하는지 흐려진다. 하나만 바뀌어도 문장 전체를 다시 봐야 한다.
- 단일하지 않은 예: "사용자는 주문을 취소할 수 있고, 환불은 3영업일 안에 완료된다."
- 쪼갠 예
  - REQ-A: 사용자는 배송 시작 전인 주문을 취소할 수 있다.
  - REQ-B: 취소된 주문의 환불은 3영업일 안에 완료된다.

### 4. 실험 결과 예측

- v1: 테스트 1개, 요구 커버 1/3. REQ-1·REQ-3은 테스트가 없다.
- v2: 테스트 7개(없는 요구 REQ-9를 가리키는 고아 테스트 1개 포함), 요구 커버 4/5.
- v2에서 테스트 0개로 남은 것은 REQ-5(주문 API 월간 가용성 99.9%)다. 비기능 요구라 단위 테스트로 확인되지 않는다. SLO 모니터링·대시보드를 매트릭스에 이어야 한다.
- 그 밖에 v2의 REQ-2는 "24시간" 경계가 생겨 경계값 테스트 3개(23:59·24:00·24:01)로 펼쳐졌다.

### 5. 단어 검사기의 한계

- v1 REQ-2 "사용자는 주문을 취소할 수 있다"는 모호어가 없다. 그런데 언제까지·어떤 상태에서 취소할 수 있는지 빠져 있다(불완전). 단어 목록으로는 못 잡는다.
- v2 REQ-3은 수치가 없지만 오류 코드 비교로 검증할 수 있다. "수치 기준 없음"이 곧 "검증 불가"는 아니다.
- 쓰임: 리뷰를 돕는 보조 장치. 모호어 후보를 표시해 주고, 판정은 사람이 질문과 리뷰로 한다.

### 6. 위로·아래로 추적

```text
  이해관계자 필요   "주문 실수를 되돌리고 싶다"
        ▲ 위로: "이 요구는 왜 있나?"
  요구 REQ-2       "결제 후 24시간 이내·배송 전이면 취소 가능"
        ▼ 아래로: "무엇이 이 요구를 구현·확인하나?"
  코드·테스트       OrderCancelTest.cancel_at_24h01m_after_payment_is_rejected
```

- 위로(부모 필요)는 범위 크리프·골드 플레이팅을 잡는다. 부모가 없는 요구는 왜 하는지 모른다.
- 아래로(자식 산출물)는 변경 영향 분석에 쓴다. 요구가 바뀌면 고칠 테스트·코드를 찾는다.
- 정의: 29148 3.1.23(도출 경로는 위로, 할당 경로는 아래로).

### 7. 추적 매트릭스 = 역색인 + 집합 차

- 테스트마다 붙은 요구 표식을 뒤집어 "요구 ID → 테스트 목록" 맵을 만든다. 검색 엔진의 "단어 → 문서 목록"과 같은 역색인이다.
- R = 요구 ID 집합, T = 테스트가 가리키는 ID 집합이라 하면
  - 테스트 연결이 없는 요구 = R − T (실험 v2: {REQ-5}). 다른 확인 수단(리뷰·모니터링)의 유무는 이 차집합으로 알 수 없다.
  - 고아 테스트가 가리키는 ID = T − R (실험 v2: {REQ-9})

### 8. 비기능 요구 누락

- 빠진 것: 성능(응답 시간·처리량) 요구가 처음부터 없었다. 도출 단계에서 사용자 기능만 물었다.
- 보이는 신호: 요구 목록의 비기능 항목이 0개다. 실험 v1의 "비기능 0"은 속도 요구(REQ-1)를 기능(F)으로 잘못 적은 결과다. 이렇게 분류가 틀려도 같은 신호로 보인다.
- 다음에는
  - 이해관계자 목록에 운영·보안·법무를 넣는다.
  - 품질 속성 체크리스트(성능·가용성·보안·보관 기한·관측성)로 도출한다.
  - 비기능 요구를 대상·조건·임계값으로 쓰고, 부하 테스트·SLO를 추적 매트릭스에 잇는다.

### 9. 규칙 변경이 일부에만 반영됨

- 원인: 요구와 코드·테스트 사이 추적이 없었다. 같은 규칙 값(24시간)이 여러 곳에 흩어져 있어, 바꿀 곳을 다 찾지 못했다.
- 재발 방지
  - 요구 ID를 테스트 태그(JUnit 5 `@Tag("REQ-2")`)·커밋 메시지·설정 키에 단다.
  - 규칙 값을 한 곳(설정·정책 객체)에 모은다.
  - 요구 변경 시 매트릭스에서 영향받는 테스트를 찾아 함께 고치고, Surefire `groups`로 해당 태그 테스트를 먼저 돌린다.
