# engineering-practice/12-estimation-and-planning — 정답

## 정답

### 1. 추정·목표·약속

- 추정: 일이 얼마나 걸리거나 얼마나 들지에 대한 예측. 치우치지 않은 분석이어야 한다.
- 목표: 바라는 사업 목표의 진술.
- 약속: 정의된 기능을 특정 품질로 특정 날짜까지 전달한다는 약속. 추정과 같을 수도, 더 공격적이거나 보수적일 수도 있다.
- "3개월 뒤 전시회"는 **목표**다. 근거: McConnell 『Software Estimation』 1.1·1.2.

### 2. 결과 분포의 모양

```text
  확률
   │     ╱╲
   │    ╱  ╲__
   │   ╱      ╲_____
   │  ╱             ╲___________
   └─┴──────────────────────────▶ 기간
     ↑ 왼쪽 잘림            오른쪽 긴 꼬리
```

- 잘 될 수 있는 정도에는 한계가 있다(아무리 잘해도 이보다 빨리는 못 끝낸다). 왼쪽이 잘린다.
- 나빠질 수 있는 정도에는 한계가 없다(문제는 계속 생길 수 있다). 오른쪽 꼬리가 길다.
- 근거: McConnell 1.4.

### 3. 불확실성 원뿔

- 초기 구상 시점: 위로 4배, 아래로 0.25배. 위아래 범위는 16배다.
- 좁히는 것: 결정. 제품 비전 정의(하지 않을 것 포함), 요구 정의, UI 설계가 변동을 없앤다. 정의가 나중에 바뀌면 다시 넓어진다.
- "일주일 더 주면 좁아진다"는 틀렸다. Construx 백서는 이 요청에 "가능하지 않다"고 답한다. 추정의 변동은 프로젝트 자체의 변동에서 오므로, 프로젝트의 변동을 줄여야 추정 변동이 준다.

### 4. PERT vs 삼각 분포

- PERT 기댓값: (4 + 4×6 + 15) / 6 = 43 / 6 ≈ 7.17일.
- 삼각 분포 평균: (4 + 6 + 15) / 3 = 25 / 3 ≈ 8.33일.
- 차이 이유: PERT 식은 베타 분포를 가정한 근사로, 가능성 최대값에 가중치 4를 준다. 삼각 분포의 평균은 세 값의 단순 평균이다. 꼬리가 긴 작업(최악 15)에서 차이가 커진다.
- 교훈: 분포 가정이 숫자를 바꾼다. 어떤 가정을 썼는지 함께 적는다.

### 5. 독립 합의 분포

- 시드 42 결과: P(합 ≤ 30일) = 1.0%, P50 38.5일, P90 44.1일, P99 48.7일.
- 시드 7·2026에서도 P(합 ≤ 30일) 1.0~1.1%, P90 44.0~44.1일이었다.
- 가능성 최대값의 합 30일은 약 1% 확률로만 지켜진다.
- 최악 합 68일은 P99 48.7일보다 훨씬 크다. 모든 작업이 동시에 최악일 확률은 매우 낮아서, 최악끼리 더하면 지나치게 비관적이다(McConnell 10.3).

### 6. 공통 원인을 넣으면

- P90이 44.1일(독립) → 53.2일(공통요인)로 늘어난다. P(합 ≤ 30일)는 0.6%로 더 낮다.
- 이유는 두 가지가 섞여 있다.
  - 실험의 공통 배수는 평균이 약 1.13이다. 그래서 평균 자체가 38.7 → 43.8일로 오른다.
  - 공통 원인은 여러 작업을 같은 방향으로 움직인다(실험 모델에서는 8개 전부). 작업끼리 오차가 상쇄되지 않아 퍼짐이 커진다. P90 − P50이 5.6 → 10.1일로, 평균 배수만으로 설명되는 약 6.3일보다 크다.
- 교훈: 독립 가정으로 구한 P90(44.1일)에 약속하면, 공통 원인(요구 변경·인력 이탈·외부 의존)이 있을 때 넘길 위험이 크게 커진다. 실험의 공통요인 모델에서 44.1일을 넘는 비율은 약 44%였다(독립 모델에서는 약 10%). 반드시 넘치는 것은 아니다. 공통 원인이 큰 프로젝트면 상관을 넣어 다시 계산하고, 공통 원인 자체를 위험 목록으로 관리한다.

### 7. 선후 관계와 임계 경로

- 병렬로 할 수 있는 작업이 있으면 전체 기간은 합보다 짧다. 반대로 기다림이 있으면 단순 합과도 다르다.
- 자원(사람)이 충분해 각 작업을 선행 작업이 끝나는 즉시 시작할 수 있으면, 전체 기간 = 작업 의존 그래프(DAG)에서 가장 긴 경로(임계 경로)의 길이. 이것은 의존 관계만 본 최소 기간이다. 한 사람이 독립 작업 둘을 맡는 것처럼 자원 제약이 있으면 더 길어진다.
- 구하는 법: 위상정렬 순서로 각 작업의 가장 이른 시작 시각 = max(선행 작업의 끝 시각)을 계산한다. 마지막 작업의 끝 시각이 전체 기간이다.
- 몬테카를로와 합치면, 매 반복에서 뽑은 기간으로 최장 경로를 다시 계산해 분포를 얻는다.

### 8. 목표가 추정으로 둔갑

- 잘못: 추정(치우치지 않은 분석)에 목표(원하는 날짜)가 들어갔다. 숫자가 분석이 아니라 바람에서 나왔다(McConnell 1.2).
- 바로잡는 질문(McConnell 1.3의 대화)
  - "기능 100%가 더 중요한가, 그 날짜에 무언가 내는 것이 더 중요한가?"
  - "날짜에 다 못 하면, 있는 만큼 내나 날짜를 옮기나?"
- 그 뒤 추정과 목표를 따로 적고, 차이를 범위 조정 계획으로 메운다.

### 9. 늦은 프로젝트에 인력 투입

- 원인: Brooks의 법칙 — 늦은 소프트웨어 프로젝트에 인력을 더하면 더 늦어진다(『The Mythical Man-Month』 2장).
  - 새 인원 교육·인계에 기존 인원 시간이 빠진다.
  - 사람이 늘수록 소통 경로가 늘어 조율 비용이 커진다.
  - 일을 잘게 나누는 데 한계가 있다.
- 대처: 범위를 줄이거나 날짜를 옮긴다. 인력 추가는 독립적으로 나눌 수 있는 일이 있고, 남은 기간이 교육 비용을 감당할 만큼 길 때만 고려한다.

### 10. 확률과 가정이 있는 문장

- 예: "P50 38일, P90 44일입니다. 30일 안에 끝날 확률은 약 1%입니다(독립 가정 몬테카를로). 가정: 결제 연동 외부 API 문서가 10/10까지 나온다. 요구가 바뀌면 이 범위는 넓어지므로 요구 완료 시점에 다시 추정합니다. 30일이 목표라면 범위를 줄인 계획을 함께 보겠습니다."
- 담긴 것: 범위(백분위), 목표 숫자의 확률, 가정, 다시 추정할 시점, 목표와의 차이를 메울 계획.
