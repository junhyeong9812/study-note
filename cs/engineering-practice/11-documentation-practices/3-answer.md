# engineering-practice/11-documentation-practices — 정답

## 정답

### 1. 틀린 문서가 더 나쁜 이유

- 문서가 없으면 사람은 묻거나 조심한다. 틀린 문서는 권위 있어 보이는 채로 잘못된 행동을 하게 만든다. 사고 중이면 2차 사고가 될 수 있다.
- SWE@G 10장 "Deprecating Documents": 쓸모없어진 문서는 지우거나 낡았다고 표시하고 새 정보가 있는 곳을 가리킨다. 주인 없는 문서라도 "이건 더는 안 됩니다!"라고 적어 두는 것이 아무 말 없는 것보다 낫다.

### 2. 나침반과 분류

- 두 질문: **행동인가 인지인가?** **습득(공부)인가 적용(일)인가?**

| | 행동/인지 | 습득/적용 | 유형 |
|---|---|---|---|
| (a) 설정 키 목록 | 인지 | 적용 | 레퍼런스 |
| (b) 처음 띄워 보기 | 행동 | 습득 | 튜토리얼 |
| (c) 장애 조치 런북 | 행동 | 적용 | 방법 가이드 |
| (d) 구조를 택한 이유 | 인지 | 습득 | 설명 |

### 3. 튜토리얼 vs 방법 가이드

- 튜토리얼: 배우는 사람에게 학습 경험을 준다. "가르쳐 줄래?"에 답한다. 한 길로 끝까지 데려간다.
- 방법 가이드: 이미 아는 사람이 특정 목표를 이루게 한다. "어떻게 하지?"에 답한다. 목표·단계만 둔다.
- 섞이면: 신입은 운영 옵션에서 길을 잃고, 숙련자는 필요한 단계를 찾으려 설명을 스크롤한다. diataxis.fr은 이 둘이 무너져 합쳐지는 것을 "최악의 경우"로 든다. 둘 중 어느 필요도 채우지 못한다.

### 4. 문서를 코드처럼

- SWE@G 10장의 항목: 내부 정책·규칙 / 소스 관리 / 분명한 소유자 / 변경 리뷰(기술하는 코드와 함께 바뀜) / 이슈를 버그처럼 추적 / 주기적 평가 / 가능하면 정확성·신선도 측정(책은 도구가 아직 못 따라왔다고 씀).
- GooWiki 문제: 주인이 없어 많은 문서가 낡았다. 새 문서를 추가하는 절차가 없어 중복이 생겼다. 평평한 이름 공간이라 계층이 없었다. Borg 설정 문서가 7~10개였다. 폐기 때 약 90%가 몇 달간 조회·수정이 없었다.
- 나아진 방법: 중요한 문서를 코드와 같은 소스 관리로 옮겼다. 소유자, 소스 트리 안 정본 위치, 버그 처리·코드 리뷰 흐름이 생겼다.

### 5. 점검 결과 예측 — 실험 출력

- 런북에서 6건: 링크 1(`./old-dashboard.md` 없음), 검토일 1(217일 경과 > 90), 뒤처짐 2(`config/application.yml`·`scripts/failover.sh`가 06-10에 바뀜), 옵션 1(`--promote` 분기 없음), 설정키 1(`db.replica.host` 없음).
- 전체는 7건이다. 나머지 1건은 architecture.md의 reviewed 메타데이터 없음.
- 런북 명령 `sh scripts/failover.sh --promote`를 실행하면 `unknown option: --promote`, 종료 코드 2.

### 6. 검토일만 올렸을 때

- 사라진 것: 검토일 경과, 뒤처짐 2건. 날짜 커밋이 reviewed와 문서의 마지막 수정일을 함께 올렸기 때문이다. 두 검사 모두 날짜를 비교한다.
- 남은 것: 링크·옵션·설정키(3건). 문서가 가리키는 대상이 **지금 실제로 있는지**를 본다. 날짜와 무관하다.
- 전체 7건 → 4건(architecture.md의 메타데이터 없음 포함).
- 교훈: 날짜는 대리값이라 목표가 되면 날짜만 바뀐다. 판정은 내용 검사로 한다.

### 7. 같은 주제 문서 여러 벌

- 원인: 소유자와 정본 위치가 없다. 누구나 새로 쓰고 아무도 지우지 않는다(GooWiki의 Borg 문서 7~10개).
- 대처: 정본 하나를 정해 기술하는 코드 옆에 둔다. 나머지는 정본으로 합치거나, 맨 위에 "정본: …"을 적어 폐기 표시한다. 정본에 소유자·검토일을 붙인다.

### 8. CI에서 막을 것과 알릴 것

- 머지를 막는다: 내용 검사 — 깨진 링크, 문서 속 명령 옵션이 스크립트에 없음, 설정 키가 설정에 없음. 검사기가 대상 형식을 제대로 읽는다면, 걸린 문서는 사람을 잘못 이끈다는 것이 거의 확실하고 거짓 양성이 날짜 검사보다 적다. 단, 실험의 단순 YAML 검사는 따옴표로 감싼 키(`"db":`)를 '없음'으로 볼 수 있다. 막는 검사로 쓰려면 실제 YAML 파서로 읽는다.
- 알림만: 검토일 경과, "참조 코드가 문서보다 나중에 바뀜". 앞의 것은 막으면 날짜만 올리는 게이밍을 부른다(실험 6번). 뒤의 것은 휴리스틱이라 문서와 무관한 코드 변경에도 걸린다(거짓 양성).
- 덧붙여, 코드 PR이 문서가 가리키는 파일을 바꾸면 문서 소유자를 리뷰어로 붙인다.
