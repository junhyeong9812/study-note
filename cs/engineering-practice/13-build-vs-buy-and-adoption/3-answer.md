# engineering-practice/13-build-vs-buy-and-adoption — 정답

## 정답

### 1. 범용 vs 전략

- 범용: 가장 큰 위험은 파국적 오류(하수관 파열, 급여 누락)다. 그것만 막고 비용은 낮을수록 좋다 → 패키지를 사고 업무를 소프트웨어에 맞춘다.
- 전략: 가장 큰 위험은 경쟁자보다 늦는 것이다. 기회비용이 개발비보다 훨씬 크다 → 직접 만든다. 남과 같은 소프트웨어는 차별화를 막는다.
- 기준은 기술의 성질이 아니라 **그 기능이 사업의 차별화 요소인가**다(Fowler 2010, Ross Pettit 인용). 고정된 구분도 아니다. 전략이 시간이 지나 범용이 된다.

### 2. TCO 예측 — 실험 A 출력

- 좁게 본 비교: 직접 초기 개발 6,000 < 구독료 10,800 → 직접이 싸 보인다.
- 3년 TCO: 직접 22,200 > 구매 13,600 → 뒤집힌다. 직접 쪽에 유지보수 10,800·온콜 3,600·인프라 1,800이 붙었다.
- 종료 비용 포함: 구매 16,600. 여전히 직접(22,200)보다 싸다.
- 모두 예시 가정이다. 결론은 가정에 달렸다.

### 3. 손익분기 인상률

- 약 46%/년. 연 50% 인상이면 구매+종료 22,900 > 직접 22,200.
- 결정 기록(ADR)에 재검토 조건으로 적는다. 예: "구독료가 연 40% 이상 오르거나 API 폐기 공지가 오면 재검토." 그러면 가격 공지가 왔을 때 처음부터 다시 논쟁하지 않는다.

### 4. 가중합의 민감도

- 차별화 가중치 1: SaaS 3.69(1위). 3: SaaS 3.47(1위). 5: 직접 구현 3.35, SaaS 3.29 → 직접 구현이 1위.
- 3.35 vs 3.29는 점수(1~5 정수, 주관적)의 정밀도를 생각하면 사실상 동점이다. "직접이 이겼다"가 아니라 "차별화를 이만큼 중시하면 두 선택이 비슷해진다"로 읽는다.
- 가중합은 결정을 대신하지 않고, 결론을 뒤집는 가정(여기선 차별화 가중치)을 드러낸다. 그 가중치가 맞는지는 1번 질문으로 정한다.

### 5. 종속의 층과 대책

- 층: 데이터 형식·반출 가능성, API 표면, 벤더 고유 기능, 계약 조건.
- 코드 층: 우리 언어의 포트 인터페이스 뒤에 어댑터로 벤더 SDK를 가둔다. 벤더 모델을 우리 모델로 번역한다(ACL, domain-modeling/19). 바꿀 때 어댑터만 다시 쓴다.
- 데이터 층: 실제로 내보내 다른 곳에 넣어 보는 반출 리허설. 반출 기능이 문서에 있다는 것과 이관 가능성은 다르다.

### 6. 낡은 Scorecard 결과

- `junit-team/junit5`는 `junit-team/junit-framework`로 이름이 바뀌었다(GitHub이 새 주소로 넘겨준다). API의 옛 이름 결과는 2025-06-22 스캔에 멈춰 있었다(8.3). 새 이름은 2026-10-04 스캔, 7.9였다.
- 확인 순서: 결과의 **스캔 날짜**(`date`)와 **저장소 이름**(`repo.name`)부터 본다. 그다음 개별 항목을 본다.

### 7. 집계 점수와 그 한계

- 계산: 항목 점수(0~10)의 위험 가중 평균. Critical 10, High 7.5, Medium 5, Low 2.5. 판정 불가(−1)는 뺀다. 실험 B에서 네 저장소 모두 재계산이 API 점수와 같았다.
- README "Project Non-Goals": 점검은 휴리스틱이라 거짓 양성·음성이 있다. 집계 점수는 무엇을 하고 안 하는지 알려 주지 않는다. 같은 점수에 이르는 길이 여럿이다.
- 그래서 "7점 미만 금지"는 성숙한 라이브러리를 거절하고, 낡은 결과로 승인할 수 있다. 우리에게 중요한 개별 항목(Maintained, Vulnerabilities, 보관 여부)을 정책으로 보는 편이 낫다.
- Guava의 Code-Review 0: 이 점검은 저장소에 남은 리뷰 흔적(GitHub/GitLab 승인, 병합자≠커미터, Prow·Gerrit 표식)을 센다. 그런 흔적이 남지 않는 곳에서 리뷰하는 프로젝트는 낮게 나올 수 있다. "리뷰를 안 한다"는 증거가 아니라 "조사하라"는 신호다(Guava의 실제 리뷰 방식은 노트에서 확인하지 않음).

### 8. 라이선스 변경 대응

- 이미 쓰던 버전: Redis·HashiCorp 모두 변경은 소급하지 않는다고 밝혔다. Redis 7.2 이하는 BSD 3-Clause로 계속 쓸 수 있다. Redis FAQ는 치명적 보안 패치를 BSD 버전에 Redis Community Edition 9.0 출시 때까지 백포트한다고 적었다.
- 당장: 옛 라이선스 버전에 고정한다. 보안 패치 공급 기한을 확인한다. 우리 사용 형태가 새 조건(예: 경쟁 관리형 서비스 금지)에 걸리는지 법무와 원문으로 확인한다(해석·법률 자문 아님).
- 중장기: 포크(Valkey — Redis 7.2.4 기반 BSD, 2024-03-28 발표), 상용 라이선스 계약, 다른 제품. 원 프로젝트가 조건을 다시 바꾸기도 한다(Redis 8의 AGPLv3 추가, 2025-05-01). 어느 쪽이든 의존성 라이선스를 CI에서 계속 감시한다.

### 9. 자체 로그인·MFA

- 계산: 초기 개발비가 아닌 3년 TCO를 다시 낸다. 유지보수·온콜·보안 패치·표준 대응(새 인증 방식)·핵심 개발자의 기회비용을 넣는다. 실험 A처럼 좁게 본 비교와 전체 TCO가 뒤집히는지 본다.
- 판단: 인증은 대부분의 회사에 범용(일반 서브도메인)이다. 차별화 요소가 아니면 사서 쓴다.
- 구조: `IdentityProvider` 같은 포트 뒤에 벤더 어댑터를 둔다. 사용자 데이터 반출 리허설을 한다. 결정과 재검토 조건(가격·API 수명)을 ADR로 남긴다. 풀려난 핵심 개발자는 차별화 기능으로 옮긴다.
