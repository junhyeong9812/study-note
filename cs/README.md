# cs — 일반 CS·설계 지식

특정 프로젝트에 속하지 않는 지식(설계 원칙, 클린코드, 디자인 패턴, 아키텍처 등)의 복습 노트.
어느 프로젝트에서 공부했든, 프로젝트 무관 지식은 여기로 모은다.
복습 접근 순서·간격 규칙은 루트 [README](../README.md)를 따르고, 파일 형식은 아래 「작성 규칙」이 정본이다 — cs 주제에 관해서는 루트 README 「작성 규칙」·[templates/](../templates/)·[reference/study-note-guide.md](../reference/study-note-guide.md) **전체**(3파일 골격·문법 주제 골격·원고와 보강의 경계·이관 출처 표기·체크리스트 등)보다 이 문서가 우선한다.

## 작성 규칙 (2026-09-27 개정 · 2026-09-28 보강 · 2026-10-08 정본화)

> 이전 규칙(따라 친 원고 → 원고 문체를 유지한 서머리 → 서머리 완성 후 질문·정답)은 폐기했다.
> 근거·결정 기록: `docs/plans/2026-09-27/issue-toplevel-cs-rule/`.
> 2026-10-08: 영역 브리핑에만 있던 형식 규칙을 이 절로 올렸다(근거 `docs/plans/2026-10-05/engineering-practice-writing/rules-vs-checker.md`).
> 규칙 끝의 **[E]** = 검사기 error, **[W]** = 검사기 warning, 표시 없음 = 사람 검수(§7).

### 1. 작성 주체 — Claude 완성본

- cs 문서는 **Claude가 완성본으로 쓴다.** 원고가 있는 주제도 새 골격으로 다시 쓴다(원고 문체 보존 규칙 없음).
- 기존 원고·따라 친 노트는 **입력 자료**로만 쓴다. 원본 위치·진행 기록은 cs 밖(아래 §5)에 둔다 — cs 문서에는 지식의 근거(교재 장·RFC·공식 문서)만 남긴다.
- 사실 주장은 교재·RFC·공식 문서와 대조한다. 확인하지 못한 주장은 `[?]`로 표시하고 단정하지 않는다.
  `[?]`는 확인 못 한 것에만 붙인다 — 확인했으면 근거(절·URL·소스 경로·실험)를 쓴다. 기억으로 쓴 절·장·페이지·연도 번호는 `[?]`.
- 수치·기본값·버전은 출처나 실험으로 확인했을 때만 쓴다. 지어내지 않는다. 설명용으로 든 수치는 "(예시)"를 붙인다.

### 2. 주제 = 3파일

`1-question.md`(퀴즈) · `2-summary.md`(서머리) · `3-answer.md`(정답·분석). 서머리를 먼저 쓰고 같은 패스에서 질문·정답을 쓴다.
세 파일은 섞지 않는다 — 서머리 안에 질문·정답을 두면 복습할 때 정답이 눈에 들어오는 경로가 생긴다.
**제목 아래 머리말(`>` 인용문으로 쓴 복습 안내·주제 요약·환경 설명·표식)은 두지 않는다** — 제목 다음 줄부터 바로 본문이다(2026-10-01). **[E]** 노트의 진행 단계는 같은 폴더의 `metadata.md`에 적는다(§4).

- **리프 폴더에는 md만** — `1-question.md` · `2-summary.md` · `3-answer.md` · `metadata.md`. 실험 코드·출력 파일은 두지 않는다. **[E]**
- **제목(H1) 형식** — 첫 줄이 H1이고 `# <cs/ 기준 폴더 경로> — …`로 시작하며(예: `database/16-mvcc`, `domain-modeling/advanced/27-ab-assign`), ` — `로 나눈 **마지막 조각**이 파일별로 `질문`·`정리`·`정답`으로 시작한다. **[E]**
  - `1-question.md`: `# database/16-mvcc — 질문`
  - `2-summary.md`: `# database/16-mvcc — <한 줄 제목> — 정리 (힌트)`
  - `3-answer.md`: `# database/16-mvcc — 정답`
- **질문·정답** — 질문은 `## 질문` 아래 `1. ` 번호 목록으로 **6~10개**, 정답은 같은 번호의 `### N. …` 헤딩으로 개수·번호를 맞춘다. **[E]** 질문 줄 머리에 유형 태그를 단다 — `(왜)` · `(예측)` · `(경계)` · `(연결)` · `(장애 진단)` 등. 예측형 질문은 실험 출력으로 답을 확인할 수 있게 쓴다.

### 3. 서머리 통일 골격 — 모든 주제 공통

개념이든 자료구조·알고리즘이든, 결국 어떤 문제를 풀려고 생겼고 쓰면 어떤 장애가 생기는지가 나온다. 그래서 전 주제가 같은 순서를 따른다.
`2-summary.md`의 최상위 `## ` 헤딩은 아래 **7개만, 이 순서로**, 이 이름 그대로 둔다(하위는 `###`). **[E]**

1. **해결하는 문제** — 이것이 없으면 무엇이 안 되나. 쉬운 예 → "똑같은 구조다" → 실무 예.
2. **동작·원리** — 어떻게 해결하나. 중심 절이다. ASCII 그림·흐름 먼저, 글은 그림 해설.
3. **쓰이는 자료구조·알고리즘** — 이 주제 안에 들어 있는 것(예: 라우팅 테이블=트라이, TCP=슬라이딩 윈도우, 인덱스=B+Tree). 해당 cs 주제로 링크한다.
4. **적용 — 풀어나가는 법** — 실제 문제에 어떻게 적용하나. 쉬운 예 먼저, 같은 구조를 실무 예로 다시. 실무 순서는 증상 → 원리 → 코드·명령으로 확인.
5. **장애 시나리오와 대처** — **3~6개**(절 안 `###` 수, 없으면 줄 머리 굵은 번호 수). **[W]** 각각 현상 → 애플리케이션에서 보이는 형태(에러·증상) → 원인 → 대처.
6. **핵심 문장** — 이 주제를 3~6개 불릿 문장으로(최상위 목록 항목 수). **[W]**
7. **관련 주제·근거** — 선행·후속 주제 링크, 교재 장·RFC 번호·문서 URL, **실험 목록**(무엇을 어떤 환경에서 돌렸나). 상대 링크는 실제로 있는 파일이어야 한다. **[E]**

**실험** — 편마다 실행으로 보일 수 있는 핵심 주장을 1개 이상 싣는다(영역 브리핑이 예외를 정할 수 있다). 실험은 `## 동작·원리`나 `## 적용` 안의 `### 실험: …` 절로 둔다. 출력 블록 앞에 `(실험, <환경·버전>, <날짜>)` 라벨을 단다 — 예: `(실험, JDK 21 temurin, 2026-10-03)`. 출력은 실제 출력만(손으로 만들지 않는다), 비결정적 값은 여러 번 돌린 범위로.

루트 [templates/](../templates/README.md)의 "대신 써주지 않는다" 방식(2-summary 작성 방식)은 cs에는 적용하지 않는다 — cs의 서머리 형식은 이 절이 정본이다.
문단 길이·표 사용 같은 형식 상한은 [reference/writing/](../reference/writing/README.md)을 따른다.

**코드 스니펫 언어** — 개념을 코드로 보일 때 기본은 **Java · JavaScript · TypeScript**다. Java로 표현하기 어려운 저수준(메모리 레이아웃·포인터·시스템콜·커널 경로 등)은 **C**, 또는 그 개념을 가장 쉽게 보여주는 언어로 쓴다. 셸은 진단·실험 구동에만. 흐름·구조는 ASCII 도식을 병행한다.
여는 코드 펜스에는 언어 태그를 반드시 단다(예: `java`·`sql`, ASCII 도식·출력은 `text`). **[E]**

**쓰는 방식** — 세 파일 공통.

- 용어는 처음 나오는 자리 바로 아래에서 푼다. 형식은 `  - *용어*: 설명`. 헷갈리기 쉬운 용어에만 그 아래 `    - 흔한 오해: …` 한 줄을 둘 수 있다(근거 있는 오해만, 선택).
- 한 문장에 한 개념. 용어가 셋 넘게 든 문장은 쪼갠다.
- '항상·반드시·절대'·'모든'을 조건 없는 단정으로 쓰지 않는다 — 예외가 있으면 조건을 적는다. **[W]**('항상·반드시·절대'가 코드 펜스 밖에 나오면 알린다 — 빈도 경고일 뿐, 조건이 붙은 쓰임은 그대로 둔다. '모든'은 사람 검수.)
- 빈 절(헤딩만 있고 본문 없음)·빈 불릿(`-`만 있는 줄)을 두지 않는다. **[E]**
- 노트 안에서 모순되지 않는다 — 그림과 글, 요약과 정답, 정답 N과 M, 실험 출력과 해석.

### 4. 상태 — 네 단계

| 상태 | 뜻 |
|---|---|
| `미작성` | 커리큘럼에만 있고 노트가 없다 |
| `원고 있음` | 기존 노트가 있다(이전 형식) — 통일 골격으로 보강 대상 |
| `초안(Claude)` | Claude가 쓴 3파일이 있다 — 검수 대기 |
| `검수 완료` | 배포 학습 사이트에서 읽고 LLM 질문으로 구체화한 뒤 확정했다 |

상태는 영역 README(생성 문서)의 표에 나오고, 생성 스크립트가 노트 폴더의 **`metadata.md`** 「단계」 칸을 보고 판정한다(2026-10-01부터 — 이전의 파일 상단 `Claude 초안`·`✅ 검수 완료` 표식을 대체).

```text
# metadata

| 항목 | 값 |
|---|---|
| 단계 | 초안 |              ← 원고 · 초안 · 검수 · 학습
| 초안 | 2026-09-30 (Claude) |
| 검수 | — |                 ← 검수를 확정한 날
| 학습 | — |                 ← 학습(복습)을 마친 날
```

- 단계 → 영역 표 상태: `원고` → `원고 있음`, `초안` → `초안(Claude)`, `검수`·`학습` → `검수 완료`. 노트가 없으면 `미작성`.
- 검수를 확정하면 「단계」를 `검수`로 바꾸고 「검수」 칸에 날짜를 적는다. 학습까지 마치면 `학습`과 날짜.
- `1-question.md`가 있는 폴더마다 하나 둔다. 새 노트는 쓸 때 함께 만든다. 없으면 검사기·생성기 모두 실패한다. **[E]**
- 「초안」·「검수」·「학습」 칸은 각각 한 줄, 값은 실재하는 `YYYY-MM-DD`(뒤에 ` (…)` 허용) 또는 `—`. 「단계」와 맞아야 한다 — 현재 단계의 날짜 칸은 채워져 있고(원고 제외), 그보다 뒤 단계의 날짜 칸은 `—`. **[E]**
- **옛 형식 표식** — 옛 노트를 7절 형식으로 옮긴 폴더는 표 끝에 「형식」 행을 둔다. 단계 행은 그대로다.
  - `| 형식 | 과제 이식 |` — myway 과제 컬렉션(algorithm·data-structure·domain-modeling basic/advanced·ops-patterns·api-design 22~27). 원래 번호·질문을 그대로 옮겼으므로 **질문 수 상한(10)만 면제**(하한 6·번호 일치는 그대로).
  - `| 형식 | 원고 이관 |` — 단독 원고 노트를 7절로 재구성한 것. 상한 면제는 같다. 원래 내용이 없는 절을 채운 보충은 첫머리에 `*(Claude 보충 — 노트 본문 요약)*` 표식을 단다(노트에 이미 있는 내용의 요약만 — 새 사실 없음).
  - 두 형식은 warning(§7) 대상에서 빠진다.

### 5. cs = 지식 본문만

**새로 쓰는 노트에는** 진행 기록(공부중·챕터 진도)·원본 저장소 대응표·구현·실험 연계를 두지 않는다 — [project/](../project/)·[lab/](../lab/)·[practice/](../practice/)로 보낸다. myway 컬렉션의 진도·원본 대응은 [project/myway/README.md](../project/myway/README.md)로 옮겼다(2026-09-28). [index.md](index.md) 아래쪽의 이관 이력 표와 컬렉션 README의 "원본:" 한 줄은 **출처 이력**으로 남긴다.
실전 이슈에서 뽑은 패턴 카드는 최상위 [issue/](../issue/)에 둔다.

### 6. 구조 — 영역 README + 기존 컬렉션 (2026-09-28)

- **19개 영역**(커리큘럼 기준): `math · data-structure · algorithm · architecture · os · language · network · security · database · distributed · reliability · software-design · domain-modeling · testing · api-design · web-platform · engineering-practice · data-engineering · data-analysis`.
- 영역마다 **생성 문서** 하나가 전체 주제 표(번호 = 권장 학습 순서 · 상태 · 노트 링크)를 가진다 — `cs/<영역>/README.md`, 기존 컬렉션과 이름이 겹치는 영역(algorithm·data-structure·domain-modeling·api-design)은 `cs/<영역>/curriculum.md`.
  정본은 [curriculum.md](../docs/plans/2026-09-27/cs-fundamentals-roadmap/curriculum.md)이고 표는 [scripts/notes/gen_area_readme.py](../scripts/notes/gen_area_readme.py)로 만든다 — **표를 직접 고치지 않는다.** **[E]**(`--check`)
- **기존 노트는 제자리에 둔다** — myway 컬렉션(algorithm·data-structure·domain-modeling basic/advanced·ops-patterns·api-design)은 원래 번호 그대로, foundations·systems·engineering 노트도 그대로. 영역 표의 노트 링크가 커리큘럼 주제와 기존 노트를 잇는다.
- 새 주제 노트는 집필할 때 해당 영역 폴더 아래 `NN-slug/`(커리큘럼 번호)로 만든다.
- 기초판과 심화판은 각각 둔다 — 심화 주제가 기초 주제를 선행으로 링크한다.

### 7. 검사 도구 — error와 warning (2026-10-08)

| 도구 | 실행 | 하는 일 |
|---|---|---|
| [scripts/notes/check_notes.py](../scripts/notes/check_notes.py) | `python3 scripts/notes/check_notes.py <노트 폴더…>` · `--all` = `cs/` 아래 `1-question.md`가 있는 폴더 전부 | 위 **[E]**·**[W]** 규칙 검사 |
| [scripts/notes/gen_area_readme.py](../scripts/notes/gen_area_readme.py) | 인자 없음 = 영역 표 재생성 · `--check` = 쓰지 않고 비교만 | 생성 문서가 생성기 출력과 다르면 실패 |

- **error** — 하나라도 있으면 FAIL, exit 1. 위반이 0이거나 거의 없어 기계로 확실히 판정되는 규칙만 둔다: 3파일·리프 md만 · 제목 H1 형식·머리말 금지 · 7절 순서 · 빈 절·빈 불릿 · 상대 링크 실재 · 질문 6~10·정답 번호 일치 · 코드 펜스 언어 태그 · metadata 단계·날짜 · 생성 문서 `--check`.
- **warning** — 출력만 하고 exit code에 영향이 없다: 장애 3~6 · 핵심 문장 3~6 · 펜스 밖 '항상·반드시·절대'. 새 기계 규칙은 warning부터 넣는다.
- **사람 검수** — 표시 없는 규칙(작성 주체, `[?]`·사실 대조, 질문 유형 태그, 용어 풀이 형식, "(예시)", '모든', 노트 안 모순, 코드 언어 선택, 실험 내용).
- **자동 실행** — GitHub Actions `.github/workflows/notes-check.yml`이 push·pull request마다 `check_notes.py --all`과 `gen_area_readme.py --check`를 돌린다. 실패는 빨간불로 보일 뿐 병합을 막지는 않는다. 집필 중에는 브리핑의 자기 검증으로 담당 폴더에 `check_notes.py`를 돌린다.
