### A. 문제 (구현 대상 TODO)

#### 1. SharedPool — 기준선

```java
// impl 정답 (release + call)
public void release(String key) {
    requireKey(key);
    AtomicInteger count = held.get(key);
    if (count == null || count.get() <= 0) {
        throw new IllegalStateException("잡은 적 없는 자리를 돌려준다: " + key);
    }
    if (count.decrementAndGet() < 0) {
        count.incrementAndGet();
        throw new IllegalStateException("잡은 적 없는 자리를 돌려준다: " + key);
    }
    permits.release();
}

public <T> T call(String key, Callable<T> task) throws Exception {
    if (!tryAcquire(key)) {
        throw new BulkheadFullException(key, available(key));
    }
    try {
        return task.call();
    } finally {
        release(key);   // 일이 예외로 끝나도 자리는 돌아와야 한다
    }
}
```

- Q: 칸을 안 나누는 SharedPool을 왜 먼저 만들게 하는가?\
  A: 대부분의 시스템이 처음에는 이 모양이고, 평소에는 이게 제일 낫기 때문이다(자리를 안 놀린다).\
  기준선을 손으로 만들어야 "추천이 물면 결제가 죽는다"는 마지막 줄의 사고가 실감되고, 칸을 나누는 대가(활용률)와 이득(격리)을 나란히 잴 수 있다.\
  01번의 FixedDelayRetry와 같은 자리의 교육 장치다.

> **벌크헤드(bulkhead)** — 배의 침수 방지 칸막이벽. 자원을 이름별 칸으로 나눠 한 곳의 폭주가 못 번지게 하는 패턴.\
> 예: 결제 10 / 배송 6 / 추천 4 로 나누면 추천이 폭주해도 자기 4칸에서 멈춘다.

- Q: 칸을 안 나누는데도 이름별 잡은 수·거절 수를 세는 이유는?\
  A: 어느 이름이 자리를 먹고 있는지 모르면 칸을 어떻게 나눌지 정할 근거가 없다.\
  격리보다 관측이 먼저다 — 통계가 다음 설계(쿼터 배분)의 입력이 된다.

- Q: 시간 제한 tryAcquire에서 0 이하를 직접 갈라내는 이유는?\
  A: Semaphore에 0을 주면 안 기다리지만, 음수를 주면 구현에 따라 동작이 갈린다.\
  계약("0 이하 = 기다리지 않는 쪽과 같다")을 라이브러리 구현의 우연에 맡기지 않고 경계에서 직접 가른다.

> **세마포어(Semaphore)** — "동시에 N명까지"를 세는 자물쇠. acquire 로 자리를 잡고 release 로 돌려준다.\
> 예: release 는 용량을 안 본다 — 부르는 만큼 자란다.

- Q: release가 "잡은 적 없으면 던진다"를 세마포어에 맡기지 못하는 이유는?\
  A: Semaphore.release는 용량 개념이 없어 부르는 만큼 자란다.\
  잡은 적 없는 반납을 세마포어는 오류로 보지 않으므로, 이름별 held 카운트로 우리가 직접 검사해야 한다.

- Q: call에서 release가 finally 안에 있어야 하는 이유는 — 밖에 두면 무엇이 얼마나 누적되는가?\
  A: task가 예외로 끝나면 finally 밖의 release는 실행되지 않는다.\
  예외가 날 때마다 자리가 하나씩 영영 줄고, 예외도 로그도 없이 누적된다.\
  풀 크기만큼 새면 그 풀은 영원히 아무것도 못 한다.

> **finally** — 예외가 나든 말든 반드시 실행되는 블록.\
> 예: 반납 누락(조용한 정원 감소)을 막는 유일한 방어선이다.

- Q: 자리가 없을 때 일을 시작조차 안 하는 것이 왜 "좋은 실패"인가?\
  A: 시작했다가 30초 뒤 타임아웃으로 죽으면 그동안 자원을 붙들고 결과도 없다.\
  시작 전 거절은 부작용이 확실히 없고 즉시 폴백으로 갈 수 있다.\
  실패를 피하는 게 아니라 실패의 비용을 최소로 만드는 선택이다.

> **거절(rejection)** — 자리가 없어 시작조차 안 하는 것.\
> 예: 시작했다가 타임아웃으로 죽는 것보다 나은 **좋은 실패**다.

- Q: 세마포어를 공정(fair) 모드로 만든 이유는?\
  A: 불공정이 처리량은 더 낫지만 굶는 스레드가 생겨 측정이 재현되지 않는다.\
  이 문제집은 측정으로 배우는 구조라 재현성을 처리량보다 우선했다.

#### 2. FixedBulkhead — 이름마다 자기 칸

```java
// impl 정답 (release + semaphoreOf)
public void release(String key) {
    Semaphore semaphore = semaphoreOf(key);
    if (semaphore.availablePermits() >= quotas.get(key)) {
        throw new IllegalStateException("잡은 적 없는 자리를 돌려준다: " + key);
    }
    semaphore.release();
}

private Semaphore semaphoreOf(String key) {
    SharedPool.requireKey(key);
    Semaphore semaphore = permits.get(key);
    if (semaphore == null) {
        throw new IllegalArgumentException(unknown(key));
    }
    return semaphore;
}
```

- Q: FixedBulkhead의 격리가 "완전하다"는 것은 무슨 뜻인가?\
  A: 한 이름이 무슨 짓을 해도 다른 이름의 자리를 못 건드린다는 뜻이다.\
  추천이 느려져도 추천은 자기 4칸까지만 물리고, 결제의 10칸은 아무 일 없다.\
  이름마다 독립 세마포어라 침범 경로 자체가 없다.

> **자원 격리(resource isolation)** — 스레드·커넥션 같은 내 자원을 용도별로 나눠 지키는 것.\
> 예: 추천이 스레드를 다 먹어도 결제 몫은 건드리지 못한다.

- Q: 그 격리의 대가는 무엇이고, 어떤 상황에서 그 손해가 드러나는가?\
  A: 활용률이다.\
  추천이 놀고 있어도 결제가 그 4칸을 못 쓴다 — 전체 20인데 결제는 영원히 10이다.\
  결제만 바쁜 평소에 손해가 드러난다(공용 풀이면 20을 다 썼을 것을 10만 쓴다).

> **활용률(utilization)** — 전체 자원 중 실제로 쓰이는 비율.\
> 예: 격리의 대가로 지불하는 것 — 추천이 놀아도 결제는 그 4칸을 못 쓴다.

- Q: release의 초과 반납 판정을 SharedPool과 달리 `availablePermits >= quota` 로 하는 이유는?\
  A: 이름마다 세마포어가 따로 있으니 "그 이름의 칸이 이미 다 차 있다"를 세마포어 자신의 남은 수로 판정할 수 있다.\
  available이 quota 이상인데 또 돌려주면 잡은 적 없는 것을 돌려주는 것이다.\
  SharedPool은 세마포어가 하나뿐이라 이름별 held 카운트가 따로 필요했다.

> **쿼터(quota)** — 이름마다 배정된 칸 수.\
> 예: 결제 10 / 배송 6 / 추천 4 가 쿼터다.

- Q: 칸을 받은 적 없는 이름이 왔을 때의 세 가지 선택지는 무엇이고, 여기서는 왜 던지는 쪽을 골랐는가?\
  A: ① 던진다(설정 실수를 즉시 드러내지만 운영 중 새 이름이 오면 장애) ② 0칸을 준다(늘 거절 — 조용하고 원인을 알기 어렵다) ③ 공용에서 준다(편하지만 그 순간 격리가 아니다).\
  이 상자에서 벌크헤드의 값은 "무엇이 어느 칸인지 정해져 있다"이므로, 정해지지 않은 것이 조용히 지나가면 그 값이 사라진다 — 그래서 던진다.\
  셋 다 말이 되는 설계 결정이라는 점이 핵심이다.

- Q: 조용히 통과시키면 오타 하나가 무엇을 만드는가?\
  A: "payment"를 "paymnet"로 잘못 쓴 호출이 조용히 새 칸을 만들어 쓴다.\
  진짜 결제 칸의 통계·격리에서 벗어난 트래픽이 생기는데 아무 오류가 없어 발견이 늦다.

#### 3. ElasticBulkhead.tryAcquire — 내 칸 먼저, 그다음 공용

```java
// impl 정답
public boolean tryAcquire(String key) {
    requireKnown(key);
    if (ownPermits.get(key).tryAcquire()) {
        return true;
    }
    if (sharedPermits.tryAcquire()) {
        borrowed.get(key).incrementAndGet();
        return true;
    }
    rejectionOf(key).incrementAndGet();
    return false;
}

public boolean tryAcquire(String key, long timeoutMillis) throws InterruptedException {
    requireKnown(key);
    if (timeoutMillis <= 0) {
        return tryAcquire(key);
    }
    if (ownPermits.get(key).tryAcquire()) {   // 자기 칸은 기다리지 않고 즉시 확인
        return true;
    }
    if (sharedPermits.tryAcquire(timeoutMillis, TimeUnit.MILLISECONDS)) {   // 기다림은 공용에서만
        borrowed.get(key).incrementAndGet();
        return true;
    }
    rejectionOf(key).incrementAndGet();
    return false;
}
```

- Q: 내 칸과 공용 중 내 칸을 먼저 쓰는 이유는 — 공용을 먼저 쓰면 무엇이 마르는가?\
  A: 공용을 먼저 쓰면 자기 보장 칸이 남아 있는데도 공용부터 소진된다.\
  남의 보장을 갉아먹지는 않지만 공용이 빨리 말라, 정작 자기 칸이 남았는데 남들이 못 빌리는 상태가 된다.\
  공용은 "자기 칸이 모자랄 때만" 쓰는 여유분이어야 오래 산다.

> **공용 여유분(shared pool)** — 탄력 방식에서 누구나 빌려 쓸 수 있는 칸.\
> 예: 빌린 것은 공용으로 갚아야 한다.

- Q: 빌린 개수를 이름마다 세어두는 이유는 무엇을 정하기 위해서인가?\
  A: 돌려줄 때 어디로 갚을지(자기 칸인가 공용인가)를 정하기 위해서다.\
  세마포어 자체는 "이 자리가 어디서 왔는지"를 기억하지 않으므로 빌림 장부(borrowed)가 유일한 근거다.

- Q: 시간 제한 쪽에서 자기 칸을 기다리지 않고 먼저 확인만 하는 이유는?\
  A: 자기 칸이 비어 있으면 즉시 잡아야 보장이 보장답다.\
  기다림은 공용에만 걸어 "자기 칸 즉시 확인 + 공용 대기"로 시간 제한을 한 번만 쓴다.

- Q: 자기 칸과 공용을 둘 다 기다리면 어떤 약속을 어기게 되는가?\
  A: 호출자가 준 timeoutMillis가 두 번 쓰여 최악 대기가 두 배가 된다.\
  "이 시간 안에는 결과를 준다"는 호출자와의 시간 계약을 어기는 것이다.

- Q: 자기 칸을 안 보고 공용만 기다리면 어떤 보장이 사라지는가?\
  A: 보장 칸이 비어 있는데도 공용 대기 끝에 거절될 수 있다.\
  "최소 N칸은 언제나 쓸 수 있다"는 보장을 팔아놓고 안 주는 것이라 이 설계의 값이 사라진다.\
  변종 검증에서 처음에 살아남았던 바로 그 결함이다.

#### 4. ElasticBulkhead.release — 빌린 것은 빌린 곳으로

```java
// impl 정답
public void release(String key) {
    requireKnown(key);
    AtomicInteger loans = borrowed.get(key);
    Semaphore own = ownPermits.get(key);

    // 빌린 것이 있으면 그것부터 갚는다. 공용을 오래 붙들고 있지 않는 쪽이 낫다.
    while (true) {
        int current = loans.get();
        if (current <= 0) {
            break;
        }
        if (loans.compareAndSet(current, current - 1)) {
            sharedPermits.release();
            return;
        }
    }
    if (own.availablePermits() >= guarantees.get(key)) {
        throw new IllegalStateException("잡은 적 없는 자리를 돌려준다: " + key);
    }
    own.release();
}
```

- Q: 전부 자기 칸으로 갚으면 시간이 지나며 무엇이 어떻게 변형되는가?\
  A: 공용에서 빌린 자리가 자기 칸으로 갚히므로 공용은 줄어든 채 안 돌아오고 자기 칸은 보장보다 커진다.\
  빌림-반납이 반복될수록 공용이 점점 말라 탄력(빌려 쓰기)이 사라진다.\
  사실상 고정 칸막이로 퇴화하는데 수치가 어긋난 고정이다.

- Q: 전부 공용으로 갚으면 무엇이 사라지는가?\
  A: 자기 보장 칸에서 잡은 자리가 공용으로 흘러가 보장 칸이 점점 줄어든다.\
  "최소 N칸 보장"이 사라져 격리가 통째로 없어진다 — 사실상 SharedPool로 퇴화한다.

- Q: 두 오류 모두 예외가 안 나고 몇 시간 뒤에 나타나는 이유는?\
  A: 반납 자체는 매번 성공하기 때문이다 — 세마포어는 어디로 갚든 오류로 보지 않는다.\
  칸의 총량은 맞는데 분포만 천천히 이동하므로, 트래픽이 몰려 "공용이 왜 0이지"가 될 때에야 드러난다.\
  전형적인 조용한 손상(silent corruption)이다.

- Q: 빌린 것부터 먼저 갚는(공용 우선 반납) 이유는?\
  A: 공용은 모든 이름이 함께 쓰는 자원이라 오래 붙들고 있을수록 남들의 기회가 줄기 때문이다.\
  빌린 것을 먼저 갚으면 공용이 빨리 회복되어 전체 활용률이 산다.

- Q: "읽은 값이 그대로일 때만 쓰는 방법"은 무엇이고, 왜 단순한 `loans.decrementAndGet()` 으로는 안 되는가?\
  A: CAS(compareAndSet) 루프다 — current를 읽고, 그 값이 그대로일 때만 current-1로 바꾼다.\
  decrementAndGet은 무조건 빼므로 두 스레드가 동시에 돌려줄 때 loans가 0인데도 음수로 내려가, 공용에서 빌린 적 없는 반납이 공용으로 가는 등 장부가 어긋난다.\
  "0 이하면 자기 칸으로" 분기와 감소가 원자적으로 묶여야 해서 읽기-검사-쓰기를 CAS로 한다.

> **CAS(compareAndSet)** — 락 없이 "이 값이면 저 값으로 바꿔라"를 원자적으로 하는 연산.\
> 예: 빌린 개수(borrowed)를 갚을 때 쓴다.

### B. 개념

#### 5. 왜 칸을 나누는가

- Q: 스레드 20개 풀 하나에서 추천이 느려지면 결제가 죽는 과정을 단계로 말하면?\
  A: ① 추천 응답이 30초씩 걸린다 ② 추천 요청이 스레드를 하나씩 잡고 안 놓는다 ③ 20개 전부가 추천에 물린다 ④ 결제 요청이 스레드를 못 얻는다.\
  추천 하나가 느려졌는데 결제가 죽는다 — 덜 중요한 것이 더 중요한 것을 끌고 내려간다.

- Q: 이 사고에서 "느림"이 "실패"보다 위험한 이유는?\
  A: 실패는 자리를 즉시 돌려주지만 느림은 자리를 오래 물고 있는다.\
  빠른 실패 1000번보다 30초짜리 느림 20개가 풀을 완전히 마르게 한다.\
  그리고 느림은 서킷 브레이커의 실패 창에 잡히기 전까지 "정상"으로 보인다.

- Q: 01·02번과 이 패턴은 시선이 어떻게 다른가(상대와 나)?\
  A: 01(재시도)·02(브레이커)는 상대가 아플 때 무엇을 할지 — 상대를 향한 정책이다.\
  벌크헤드는 내 자원이 남아나게 하는 것 — 상대를 못 고쳐도 나는 살아야 한다.\
  방향이 바깥에서 안으로 바뀐다.

- Q: "격리를 사면 활용률을 판다"를 세 구현의 표(0/20, 10/10, 6/14)로 설명하면?\
  A: 추천이 물고 안 놓을 때 결제가 잡을 수 있는 자리: SharedPool 0, Fixed 10, Elastic 6(보장).\
  결제만 바쁠 때 쓰는 자리: SharedPool 20, Fixed 10, Elastic 14(보장 6+공용 8).\
  두 열이 반대 방향이다 — 사고 때의 안전과 평소의 활용률은 같은 것을 나눠 갖는다.\
  Elastic이 그 사이를 메운다.

- Q: 이 맞바꿈이 보험과 같은 모양이라는 것은 무슨 뜻인가?\
  A: 평소에 보험료(놀리는 칸 = 활용률 손해)를 내고, 사고 때 보험금(보장 칸 = 생존)을 받는다.\
  사고가 안 나면 낸 보험료가 아깝게 보이지만, 그게 보험을 안 들 이유가 아닌 것과 같다.

#### 6. 보장과 최대는 다르다

- Q: 보장 6 + 공용 8에서 14는 왜 보장이 아닌가?\
  A: 14는 공용 8이 전부 비어 있을 때만 나오는 수이기 때문이다.\
  다른 이름이 공용을 빌려 쓰고 있으면 결제는 6+남은 공용만큼만 잡는다.\
  어떤 경우에도 지켜지는 것은 보장 6뿐이다.

> **보장(guarantee) / 최대(maximum)** — 어떤 경우에도 쓸 수 있는 수 / 공용이 비어 있을 때만 나오는 수.\
> 예: 계획은 보장으로만 한다 — 결제 보장 6 + 공용 8 의 14는 보장이 아니다.

- Q: 이 차이를 헷갈리면 무엇이 통째로 틀어지는가?\
  A: 용량 계획이다.\
  "결제는 14까지 되니까"로 트래픽을 계획하면, 사고 순간 실제로는 6밖에 없어 계획이 무너진다.

- Q: 용량 계획은 보장과 여유분을 각각 어떻게 쳐야 하는가?\
  A: 보장은 합해서 계획하고(그것이 확실히 있는 자원), 여유분(공용)은 없다고 치고 계획한다.\
  공용은 성능 보너스이지 계획의 근거가 아니다.

#### 7. 새는 자리와 늘어나는 자리

- Q: Semaphore.release가 용량을 안 본다는 것이 왜 위험한가?\
  A: 초기 정원과 무관하게 부르는 만큼 permits가 자라기 때문이다.\
  반납 버그가 격리 한도 자체를 바꿔버린다 — 4칸짜리가 5칸, 6칸이 된다.\
  라이브러리가 막아주지 않으니 우리 코드(held 카운트·quota 비교)가 막아야 한다.

- Q: 이중 반납 한 번이 만드는 손상은 왜 조용한가?\
  A: 자리가 늘어난 것은 아무도 오류로 신고하지 않기 때문이다.\
  당장은 오히려 여유가 생긴 것처럼 보이고, 격리가 깨진 것은 다음 사고 때에야 드러난다.

- Q: 반납 누락이 네 번 쌓이면 4칸짜리 이름에 무슨 일이 생기는가?\
  A: 정원이 하나씩 영구히 줄어 0이 되고, 그 이름은 영원히 아무것도 못 한다.\
  예외도 안 나고 로그도 안 남는다 — 어느 날 "이 기능이 왜 전부 거절되지"로 발견된다.

- Q: call 메서드가 존재하는 진짜 이유는 무엇인가?\
  A: 편의가 아니라 반납 누락의 구조적 차단이다.\
  잡기-일하기-돌려주기를 손으로 쓰면 언젠가 예외 경로에서 release를 빠뜨린다.\
  try/finally를 한 곳에 고정해 그 실수의 자리를 없앤다.

#### 8. 좋은 실패와 실패의 분류

- Q: 자리가 없어 시작조차 안 한 실패가 시작했다가 타임아웃으로 죽는 것보다 나은 이유는?\
  A: 자원을 안 썼고, 부작용이 없고, 사용자가 결말을 30초가 아니라 0ms 만에 안다.\
  같은 "실패"라도 비용이 다르다 — 02번의 CircuitBreakerOpenException과 같은 "좋은 실패"다.

- Q: BulkheadFullException을 02번 서킷 브레이커의 실패로 세면 어떤 엉뚱한 일이 생기는가?\
  A: 내 자원이 부족한 것 때문에 남(상대 서비스)의 회로가 열린다.\
  상대는 멀쩡한데 차단되고, 차단은 내 자원 부족을 하나도 해결하지 않는다.\
  실패의 원인이 누구에게 있는지로 분류해야 한다.

> **BulkheadFullException** — "내 자원이 부족하다"는 신호.\
> 예: 상대 장애와 섞어 세면 안 된다(02의 실패 술어 판단과 같은 자리).

- Q: 이 판단은 01·02번의 어떤 공통 질문과 이어지는가?\
  A: "이 실패가 누구 탓인가."\
  01: 재시도해도 되는 오류인가(내 요청 탓이면 재시도 무의미).\
  02: 실패로 세도 되는 오류인가(상대 건강의 정보가 아니면 표본에서 제외).\
  03: 이 거절은 내 자원 문제다 — 상대에 대한 어떤 판단의 근거도 아니다.

#### 9. 격리 단위와 한계

- Q: 격리 단위를 잘못 잡으면(결제와 추천을 한 칸에) 무슨 일이 생기는가?\
  A: "외부 호출"이라는 한 칸 안에서 추천이 느려지면 결제가 같이 죽는다 — 같은 사고가 칸 안에서 그대로 난다.\
  칸을 나눴다는 형식만 있고 막으려던 사고는 못 막는다.

- Q: "무엇을 같은 칸에 넣을지는 코드가 아니라 설계다"는 무슨 뜻인가?\
  A: 칸막이 코드는 어떤 배분이든 똑같이 잘 돌아간다 — 잘못된 배분도 성실히 지킨다.\
  중요도·장애 상관관계·트래픽 패턴을 보고 경계를 긋는 일은 사람의 판단이고, 테스트로도 검증되지 않는다.\
  이 패턴의 전부가 그 경계 긋기다.

- Q: 벌크헤드가 안 고치는 것은 무엇이고, 그것은 누구의 일인가?\
  A: 느린 것 자체를 안 고친다 — 번지는 것만 막는다.\
  느린 상대를 차단하고 회복을 기다리는 것은 02번 서킷 브레이커의 일이다.\
  그래서 둘은 대체가 아니라 같이 쓴다(ResilienceStrategy로 겹친다).

- Q: 대기 큐를 기본으로 두면 칸을 나눈 의미가 왜 사라지는가?\
  A: 스레드가 안 물리는 대신 큐가 무한히 자라 큐에 물릴 뿐이다.\
  묶이는 자원이 스레드에서 메모리·대기 시간으로 바뀌었을 뿐 "덜 중요한 것이 자원을 먹는" 구조는 그대로다.\
  그래서 tryAcquire는 즉시 false가 기본이고, 기다림은 시간 제한이 있는 쪽으로만 — 05번 백프레셔가 그 이야기다.

- Q: 변종 검증에서 "기다릴 때 자기 칸을 안 본다"가 처음에 살아남은 이유는?\
  A: 그 결함은 공용이 마른 상태에서 보장 칸이 비어 있어야만 드러나는데, 기존 테스트에 그 상황이 없었다.\
  결함이 사는 곳(특정 상태 조합)을 테스트가 안 만들면 변종은 산다 — 그 상황을 따로 만들어서야 잡았다.\
  테스트 커버리지가 아니라 상태 커버리지의 문제다.

#### 10. 다음 챕터로의 다리

- Q: 벌크헤드·레이트 리미터·백프레셔는 같은 문제의 어떤 세 층인가?\
  A: 과부하라는 같은 문제를 다른 위치에서 다룬다.\
  04 레이트 리미터 — 들어오는 쪽을 막는다(입구에서 속도 제한).\
  03 벌크헤드 — 이미 들어온 것을 나눈다(내부 자원 격리).\
  05 백프레셔 — 못 받겠다고 위로 말한다(신호를 거슬러 올려보냄).
