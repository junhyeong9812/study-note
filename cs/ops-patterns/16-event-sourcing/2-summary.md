## 한눈에 — 쉽게 말하면

**이벤트 소싱 = 잔액 대신 통장 거래내역을 원본으로 삼기.**

- 지갑에 얼마 있는지만 적어두면 "왜 8000원이지?"에 답할 수 없다. 통장 거래내역(입금 10000, 출금 2000)을 적어두면 잔액은 **위에서부터 접어 내려오면(계산하면)** 언제든 나온다.
- 이벤트 소싱은 똑같은 구조다: **상태(잔액)를 저장하지 않고 사건(입금되었다·출금되었다)을 저장한다.** 상태는 읽을 때마다 사건을 접어서 만든다.
  - *사건(event)*: 이미 일어난 일. 이름이 과거형("출금되었다")인 것 자체가 계약이다.
  - *접기(fold/replay)*: 빈 상태에서 시작해 사건을 순서대로 하나씩 반영해 지금 상태를 만드는 것.
- 그래서 감사 로그가 부산물이 아니라 **원본**이다 — "왜 이 값이 됐나"에 늘 답할 수 있다.
- 종이 장부와 같다: **줄을 긋거나 찢지 않는다.** 잘못 적었으면 반대 항목을 새로 적는다.

```text
보통 방식          이벤트 소싱
+--------+        +------------------+
| 잔액   |        | Opened(홍길동)    |
| 8000   |        | Deposited(10000) |   읽을 때 위에서부터 접는다
+--------+        | Withdrawn(2000)  |   -> 잔액 8000
 왜 8000인지 모름  +------------------+   왜 8000인지 전부 남아 있음
```

실무 예: 은행 원장, 회계 장부, git(커밋을 쌓고 현재 코드는 재생 결과), 카프카 기반 주문 이력.

## 전체 흐름

```text
명령("출금해라")이 들어오면 — AccountService
  1. 지금까지의 사건을 읽는다            (store.read)
  2. 접어서 지금 상태를 만든다           (projection.replay)
  3. 이 명령이 지금 상태에서 되는지 본다  <- 검증은 여기 한 번뿐
  4. 되면 사건("출금되었다")을 붙인다.
     내가 읽은 버전을 같이 준다          (store.append + 낙관적 잠금)

읽기("잔액 얼마?")가 들어오면
  사건 전부 읽기 -> 빈 상태부터 접기 -> 상태 반환 (여기엔 검증이 없다)
```

- *명령(command)*: "출금해라" — 아직 안 일어났고, **거절될 수 있다**.
- *사건(event)*: "출금되었다" — 이미 일어났고, **거절할 수 없다**. 이 구별이 이 상자의 핵심이다.

## 동작 — 사건을 붙이는 저장소 (EventStore)

**언제 쓰나**: 모든 변경의 종착지. 고치기·지우기가 없고 **붙이기(append)만 있다.**

전 상태 — acc-1 스트림에 사건 2개(버전 2):

```text
acc-1: [ Opened(홍길동) | Deposited(1000) ]   versionOf = 2 (= 사건 개수)
```

단계 (append의 규칙 — 한 단계 한 문장):

```text
[1] 붙이는 쪽이 "내가 본 버전"(expectedVersion)을 같이 준다
[2] 지금 사건 개수와 정확히 같으면 -> 뒤에 붙이고 새 버전을 돌려준다
[3] 다르면 -> 내가 읽은 상태가 이미 낡은 것 -> ConcurrentModificationException 으로 거절
```

후 상태 — expectedVersion=2로 Withdrawn을 붙이면:

```text
acc-1: [ Opened(홍길동) | Deposited(1000) | Withdrawn(500) ]   versionOf = 3
```

- 버전 검사 없이 그냥 붙이면 사건이 사라지지는 않는다 — **남의 사건 위에 내 것이 얹혀 순서가 뒤엉킬 뿐**이고, 접은 상태가 틀린다. 그런데 사건 목록만 보면 아무 이상이 없어 보인다.
- `readFrom(fromVersion)`은 스냅샷 뒤의 사건만 읽을 때 쓴다 — 경계를 한 칸 틀리면 사건 하나가 조용히 빠져서, 처음부터 접은 결과와 달라진다.

**비용/트레이드오프**: 붙이기는 싸다(리스트 끝에 추가). 대가는 전부 읽기 쪽으로 넘어간다(아래 "대가" 절).

## 동작 — 접기 (AccountProjection.replay/apply)

**언제 쓰나**: 상태가 필요할 때마다. 빈 상태에서 시작해 사건을 하나씩 `apply` 한다.

전 상태 — 어제까지 마이너스 통장이 허용됐던 계좌:

```text
저장된 사건: [ Opened(홍길동) | Deposited(1000) | Withdrawn(5000) ]
                                                 ^ 옛 규칙에서는 허용됐던 출금
```

단계:

```text
empty()          -> 없는 계좌
+ Opened(홍길동)  -> 홍길동, 잔액 0        <- Opened 는 상태를 "처음으로 되돌린다"
+ Deposited(1000)-> 잔액 1000
+ Withdrawn(5000)-> 잔액 -4000            <- 음수여도 그대로 접는다. 검증 안 한다
```

후 상태: 잔액 **-4000**. 이게 정답이다.

- **재생하면서 검증하면 안 된다.** `apply`에 `if`로 조건을 다는 순간, 어제 저장된 사건이 오늘 규칙에 걸려 터진다. 재생 중 거절은 **과거를 부정하는 것**이고 그 뒤의 모든 사건이 어긋난다. 오늘의 규칙은 오늘 들어오는 명령에만 적용한다.
- **Opened는 앞 상태를 물려받으면 안 된다.** 계좌를 닫고 같은 번호로 다시 열면(Opened, Deposited, Closed, Opened 스트림이 실제로 생긴다) 옛 주인의 잔액이 새 주인에게 넘어간다. "Opened는 늘 맨 앞"이라고 믿는 동안에는 안 드러나는 결함이다.
- **모르는 사건을 만나면 던진다.** 조용히 무시하면 그 사건이 통째로 사라지고 상태가 조용히 틀린다 — 새 사건 종류를 배포했다가 되돌린 뒤에 실제로 일어나는 일이다. (이 코드는 sealed interface라 컴파일이 막아주지만, 실전에서는 JSON을 사건으로 바꾸는 자리에서 터진다.)
  - *sealed interface*: 하위 타입을 코드에 열거해 두는 자바 문법. switch가 빠뜨린 종류를 컴파일러가 잡는다.
- 같은 사건을 다시 접으면 늘 같은 상태다(결정적) — 그래서 몇 번을 재생해도 안전하다.

**비용/트레이드오프**: 접기 자체는 사건당 O(1)이지만, 매 읽기마다 전부 접는다는 점이 대가다.

## 동작 — 명령 검증 (AccountService)

**언제 쓰나**: 명령을 사건으로 바꾸는 유일한 관문. **검증이 있는 유일한 자리다.**

전 상태 — 잔액 1000인 계좌에 "5000 출금해라" 명령:

```text
사건: [ Opened | Deposited(1000) ]  버전 2, 접으면 잔액 1000
```

단계:

```text
[1] version = store.versionOf("acc-1")   // 2 를 기억해 둔다
[2] state = replay(read("acc-1"))        // 잔액 1000
[3] 잔액 1000 < 5000                      -> RejectedException. 사건이 안 생긴다
[4] (됐다면) append("acc-1", version=2, Withdrawn)  // "내가 읽은" 버전으로 붙인다
```

후 상태: 사건은 그대로 2개, 잔액 그대로 1000, rejected 카운트만 +1.

- **명령은 거절되고 사건은 안 거절된다** — RejectedException(명령 거절)과 ConcurrentModificationException(버전 충돌)이 이 경계에 서 있는 두 예외다.
- **같은 계좌를 두 번 열면 거절해야 한다.** 안 막으면 Opened가 하나 더 붙고, 그 사건이 잔액을 0으로 되돌리고 주인을 바꾼다 — 사건 목록만 보면 이상한 게 없다.
- **붙일 때 versionOf를 다시 부르면 안 된다.** 자기가 [1]에서 읽은 버전으로 붙여야 한다. 다시 부르면 그 사이 남이 붙였어도 "지금 버전"이라 그냥 통과 — 낙관적 잠금이 통째로 무의미해진다.

**비용/트레이드오프**: 상태를 캐시로 들고 있으면 빠르지만 그 캐시가 낡았는지 알 방법이 없다. 그래서 매번 읽고 접고, 대신 버전으로 충돌을 잡는다.

## 동작 — 낙관적 잠금 (충돌은 나중에 잡는다)

**언제 쓰나**: 여러 프로세스가 같은 스트림에 동시에 붙일 때.

전 상태 — 내가 버전 1을 읽었는데 그 사이 남이 붙였다:

```text
나:   버전 1 을 읽음 ----------------------+
남:   append(v=1, Deposited(500)) 성공     | 스트림은 이제 버전 2
나:   append(v=1, Deposited(1000)) ------->| "기대 1, 실제 2" -> 거절!
```

단계: 거절당하면 **다시 읽고 다시 판단해서 다시 붙인다** — 고칠 수 있는 실패다.

후 상태: 내 사건은 안 붙었고, 재시도하면 새 버전(2) 위에 올바른 순서로 붙는다.

- 11번 분산 락의 펜싱 토큰과 같은 일을 한다. 다른 점은 **미리 잡지 않는다**는 것뿐 — 락은 먼저 잡고 일하고, 여기서는 일단 하고 충돌이면 다시 한다.
  - *낙관적 잠금(optimistic locking)*: "충돌은 드물 것"이라고 낙관하고 잠그지 않은 채 일한 뒤, 붙이는 순간 버전으로 충돌을 검사하는 방식.
- 측정(README): 스레드 8개가 50번씩 재시도 루프로 붙이면 **성공 400건, 충돌로 거절 146건** — 전부 결국 성공하고, 사건도 잔액도 하나도 안 사라진다(테스트가 400 = 최종 잔액을 확인). 충돌이 드물면 락보다 훨씬 싸다.

## 동작 — 실수는 지우지 않고 붙인다

**언제 쓰나**: 실수로 입금 버튼을 두 번 눌렀을 때.

```text
전: [ Opened | Deposited(10000) | Deposited(10000) ]        잔액 20000 (사건 3개)
                                  ^ 실수
후: [ Opened | Deposited(10000) | Deposited(10000) | Withdrawn(10000) ]
                                                     ^ 반대 사건을 붙임
    잔액 10000 (사건 4개 — 줄지 않고 "늘었다")
```

- 08번 사가의 보상과 같은 모양이다 — 롤백이 아니라 반대되는 일을 새로 한다.
- 그래서 "실수가 있었다"는 사실 자체가 기록에 남는다. 이것이 장부의 방식이다.

## 대가 — 무엇을 잃는가 (측정)

- **읽을 때마다 전부 접어야 한다.** 사건이 10,000개면 한 번 읽을 때 10,000번 접는다(테스트 실측: 사건 10/100/1,000/10,000개에서 접기 횟수 = 사건 수).
- 그래서 **스냅샷**이 필요해진다: 500번째까지 접은 상태를 저장해 두고, 그 뒤 사건만 이어 접으면(`replayFrom` + `readFrom`) 결과는 처음부터 접은 것과 같다.
  - *스냅샷(snapshot)*: 어느 버전까지 접어 둔 중간 저장 상태. 재생을 짧게 만드는 캐시.
- 단 스냅샷은 다시 "저장된 상태"라서 원래 문제를 조금 되가져온다 — 스냅샷이 틀리면 그 뒤가 전부 틀리는데 사건은 멀쩡하다. 그래서 **스냅샷은 언제든 버리고 다시 만들 수 있어야 한다**(원본은 항상 사건).
- **지울 수 없다는 것이 문제가 되기도 한다.** "이 사람 정보를 지워달라"는 요청에 붙이기만 하는 저장소는 답이 없다 — 개인정보를 사건에 안 담고 참조만 담는 설계가 필요하고, 그건 이벤트 소싱을 택하는 순간 같이 오는 숙제다.
- **변종 실험(README)**: 결함 10개를 심었더니 테스트가 전부 잡았는데, 처음에 살아남았던 셋은 ①Opened의 상태 초기화 ②읽은 버전으로 붙이기 ③중복 개설 막기 — **셋 다 정상 경로에서는 아무 차이가 없었다.** 이 패턴의 결함은 조용하다.

## 핵심 문장

- 상태 대신 사건을 저장한다 — 잔액은 접어서 얻고, "왜 이 값이 됐나"의 감사 로그가 부산물이 아니라 **원본**이다.
- 명령은 거절될 수 있고 사건은 거절될 수 없다 — 검증은 **명령을 사건으로 바꿀 때 한 번만**, 재생할 때는 절대 안 한다(과거 부정 금지).
- 잘못 붙인 사건은 지우지 않고 **반대 사건을 붙인다** — 사건은 늘기만 하고, 실수했다는 사실도 기록에 남는다.
- 붙일 때 "내가 읽은 버전"을 같이 주는 것이 낙관적 잠금이다 — 미리 잡는 락과 달리 일단 하고 충돌이면 다시 하며, 충돌이 드물면 이쪽이 훨씬 싸다.
- 대가는 읽기다 — 매번 전부 접어야 해서 스냅샷이 필요해지고, 스냅샷·삭제 불가라는 숙제가 같이 온다.

## 용어 풀이

- **이벤트 소싱(event sourcing)**: 상태가 아니라 사건들을 원본으로 저장하고, 상태는 사건을 접어 계산하는 패턴.
- **명령(command)**: "출금해라" — 하려는 일. 검증 대상이고 거절될 수 있다.
- **사건(event)**: "출금되었다" — 이미 일어난 일. 과거형이 계약이고 거절할 수 없다.
- **접기/재생(fold/replay)**: 빈 상태에서 사건을 순서대로 반영해 지금 상태를 만드는 것. 결정적이다.
- **투영(projection)**: 사건들을 접어 읽기용 상태를 만드는 부품(AccountProjection).
- **스트림(stream)**: 한 대상(계좌 하나)의 사건 목록. 버전 = 사건 개수.
- **append-only(붙이기 전용)**: 고치기·지우기 없이 뒤에 붙이기만 하는 저장 방식. 장부의 규칙.
- **낙관적 잠금(optimistic locking)**: 잠그지 않고 일한 뒤, 붙일 때 "내가 본 버전"이 그대로인지 검사해 충돌을 잡는 방식.
- **펜싱 토큰(fencing token)**: 11번의 장치 — 낡은 소유자의 쓰기를 번호로 막는다. 여기의 버전 검사와 같은 일을 한다.
- **보상(compensation)**: 08번 사가의 장치 — 롤백 대신 반대되는 일을 새로 하는 것. "지우지 않고 붙인다"와 같은 모양.
- **스냅샷(snapshot)**: 어느 버전까지 접어 둔 중간 상태. 재생을 짧게 하는 캐시 — 버리고 다시 만들 수 있어야 한다.
- **결정적(deterministic)**: 같은 입력(사건 목록)이면 몇 번을 돌려도 같은 결과가 나오는 성질. 재생의 전제.
