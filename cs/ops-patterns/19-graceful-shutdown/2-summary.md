## 한눈에 — 쉽게 말하면

**우아한 종료 = 가게 문 닫을 때 "새 손님은 안 받고, 안에 있는 손님은 끝까지 대접하기".**

- 영업 종료라고 손님이 식사 중인데 불을 꺼버리면? 손님(요청)이 밥을 먹다 만 채 쫓겨난다. 제대로 하는 가게는 ① 먼저 "영업 종료" 팻말을 걸어 새 손님을 막고 ② 안의 손님이 다 나갈 때까지 기다렸다가 ③ 그래도 안 나가면 마감 시간에 정리한다.
- 서버도 똑같은 구조다: 배포·재시작으로 프로세스를 끄는 순간, **처리 중이던 요청(in-flight)** 을 어떻게 하느냐가 이 상자의 전부다.
  - *in-flight(처리 중)*: 받았지만 아직 응답을 못 준 요청.
- 앞의 열여덟 상자가 만든 재시도·아웃박스·사가도, 프로세스가 하던 일을 버리고 죽으면 소용이 없다.
- 무서운 점: 즉시 종료는 **예외도 안 나고 로그도 안 남는다.** 사라진 요청은 클라이언트 쪽 타임아웃으로만 보여서 원인을 네트워크에서 찾게 된다 — "배포하면 가끔 오류가 난다"로 몇 달을 보내는 이유.

```text
즉시 종료(Abrupt)                     우아한 종료(Graceful)
stop() -> 그 자리에서 STOPPED          shutdown() -> DRAINING(새것 거절)
처리 중 10건: "0ms 기다렸는데            -> 하던 일 완료 대기 -> STOPPED
10건이 남았다" (조용히 증발)            처리 중 10건: "300ms 기다려 10건 완료"
```

실무 예: 쿠버네티스 롤링 배포(SIGTERM → 유예 시간 → SIGKILL), 로드밸런서의 헬스체크로 트래픽 빼기(드레이닝).

## 전체 흐름

```text
상태(Phase): RUNNING ──shutdown 시작──> DRAINING ──0건 또는 기한──> STOPPED
             평소                        새 요청 거절,               다 끝났(거나 버렸)다
                                        하던 일은 끝낸다

shutdown(timeoutMillis):
  1. 먼저 DRAINING 으로 바꾼다 (막는 것이 첫 일)
  2. inFlight 가 0 이 될 때까지 주기적으로 확인하며 기다린다 (ticker.sleep)
  3. 0 이 되면 clean 보고 / 기한(이상)이 되면 남은 것을 "세어서" 버리고 timedOut 보고

isHealthy(): DRAINING 이면 false  <- 로드밸런서가 이걸 보고 트래픽을 뺀다
```

## 동작 — 기준선: 즉시 종료 (AbruptServer)

**언제 쓰나**: 안 기다리면 무엇이 사라지는지 보여주는 기준선. 그리고 실제로 대부분의 서비스가 이 모양이다.

전 상태:

```text
RUNNING, inFlight = { r1 ... r10 }   (처리 중 10건)
```

단계: `stop()` — 즉시 STOPPED로 바꾸고 **기다리지 않는다.** 다만 몇 개를 버렸는지는 **센다**.

후 상태:

```text
STOPPED, inFlight 10건 증발  ->  보고: "0ms 기다렸는데 10건이 남았다"
```

- 이 코드에 틀린 곳이 없다는 것이 요점이다 — 예외도 로그도 없이 요청이 사라진다.
- **진짜 문제는 버리는 것이 아니라 보고하지 않는 것이다.** 잃은 것을 안 세면 잃는지도 모르고, 그 손실은 배포 직후 오류율로만 나타난다.

**비용**: 종료는 0ms. 대가는 처리 중이던 전부.

## 동작 — 우아한 종료 (GracefulServer.shutdown: 순서가 계약이다)

**언제 쓰나**: 종료 신호(SIGTERM)를 받았을 때. 이 메서드가 이 상자의 본체다.

전 상태:

```text
RUNNING, inFlight = { r1, r2, r3 }, 로드밸런서는 계속 트래픽을 보내는 중
```

단계 (한 단계 한 문장):

```text
[1] 먼저 phase = DRAINING           -> accept 가 새 요청을 거절하기 시작한다
[2] 이 시점의 완료 누적을 기억해 둔다  -> 보고는 "종료 시작 뒤" 완료만 세기 위해
[3] 루프: inFlight == 0 인가?
      0 이면        -> STOPPED, clean(기다린 시간, 종료 뒤 완료 수, 거절 수) 보고
      기한 >= 이면   -> STOPPED, 남은 것을 세고 비운 뒤 timedOut(…, abandoned, …) 보고
      아니면        -> ticker.sleep(확인 주기) 하고 다시 확인
```

후 상태 (기한이 넉넉했다면):

```text
STOPPED, inFlight = {}  ->  보고: "300ms 기다려 10건 완료 (거절 n)"
```

넷을 조심한다 (TODO 3 주석 그대로):

- **막는 것이 먼저다.** 안 막고 기다리면 기다리는 동안 계속 들어와 inFlight가 0이 안 된다 — 바쁜 서비스에서는 영원히 안 끝난다.
- **기한이 없으면 종료가 아니다.** 하나가 안 끝나면 영원히 기다리고, 그러면 오케스트레이터가 SIGKILL을 보내 **보고할 기회도 없이** 죽는다.
  - *SIGTERM / SIGKILL*: "정리하고 끝내라"는 신호 / "그냥 죽어라"는 신호(잡을 수 없다). 쿠버네티스는 SIGTERM 뒤 유예 시간이 지나면 SIGKILL을 보낸다.
- **기한 판정은 이상(≥)이다.** 초과(>)로 쓰면 확인 주기만큼 더 기다린다.
- **보고하는 완료 건수는 종료 시작 뒤의 것만이다.** 누적을 그대로 보고하면 종료와 상관없는 숫자가 되고, 기한이 맞는지 판단할 근거가 사라진다.

**비용/트레이드오프**: 종료가 기한만큼 느려진다. 기한이 지나 버리는 것은 즉시 종료와 같다 — 다른 것은 **몇 개를 버렸는지 아는 것**(ShutdownReport의 abandoned).

## 동작 — 밖에 알리기 (isHealthy: 안 알리면 우아해도 오류다)

**언제 쓰나**: 로드밸런서의 헬스체크가 주기적으로 부른다.

```text
안 알리면:                             알리면:
LB ──요청──> [DRAINING 서버] -> 전부 거절   LB: isHealthy()=false 를 보고
사용자가 오류를 본다                       트래픽을 다른 서버로 뺀다
```

- **DRAINING이면 건강하지 않다고 답해야 한다.** 안 알리면 로드밸런서가 계속 보내고 그 요청들이 전부 거절된다 — 서버는 우아하게 종료했는데 사용자는 오류를 보는 상태.
  - *드레이닝(draining, 배수)*: 새 물은 잠그고 남은 물을 빼는 것 — 새 요청은 거절, 하던 일은 완료.

## 기한을 얼마로 잡나 — 측정

요청 하나가 500ms 걸릴 때 (README 실측):

```text
기한 100ms -> 3건 잃음
기한 400ms -> 3건 잃음    <- 평균쯤으로 잡아도 잘린다
기한 600ms -> 0건         <- "제일 오래 걸리는 요청"보다 길어야 한다
```

- **기한은 최악 요청 기준으로 잡는다.** 평균으로 잡으면 절반이 잘린다.
- 기한 0은 "안 기다린다" — 즉시 종료와 같되 세어서 보고한다는 점만 다르다.

## 한계 — 이 패턴이 못 지키는 것

- **종료 신호를 안 받으면 아무 소용이 없다.** 이 상자는 "신호를 받았다"부터 시작하는데 실제로는 그 앞이 더 자주 문제다: SIGTERM 핸들러를 안 걸었거나, 컨테이너에서 PID 1이라 기본 핸들러가 없거나, 프로세스 매니저가 SIGKILL을 먼저 보내면 — 아무리 잘 만든 shutdown도 안 불리고, **증상은 즉시 종료와 똑같다.**
  - *PID 1*: 컨테이너의 첫 프로세스. 일반 프로세스와 달리 신호의 기본 동작이 없어서 SIGTERM을 그냥 무시하게 되기 쉽다.
- **기한 안에 못 끝나는 요청은 여전히 잃는다.** 30초짜리 배치가 요청 처리에 섞여 있으면 어떤 기한으로도 못 지킨다 — **우아한 종료는 짧은 요청을 지키는 것이지 긴 작업을 지키는 것이 아니다.** 긴 작업은 07번 아웃박스처럼 저장해 두고 따로 도는 구조로 옮겨야 한다.

## 만들면서 배운 것 (README)

- **변종 9개 중 8개가 테스트에 잡혔고 하나는 죽은 코드였다**: `complete`의 `notifyAll` — 이 구현의 대기 루프는 `wait`가 아니라 주기 확인 방식이라 부를 사람이 없었다. 테스트를 억지로 만드는 대신 그 줄을 지웠다. 안 쓰는 장치를 두면 읽는 사람이 "누군가 wait 하고 있다"고 잘못 읽는다.
- **테스트를 두 번 만들었다**: 처음엔 가짜 시계와 실제 스레드를 섞었는데, 시계가 순식간에 감기는 동안 스레드가 못 따라와 결과가 매번 달랐다. **시계를 주입하기로 한 이상 일도 시계에 태워야 한다** — 그래서 shutdown은 `ticker.sleep`으로 기다리고, 테스트는 10초를 실제로 안 기다린다.

## 핵심 문장

- 즉시 종료의 진짜 문제는 요청을 버리는 것이 아니라 **버렸다는 사실을 보고하지 않는 것**이다 — 예외도 로그도 없이, 배포 직후 오류율로만 나타난다.
- 종료는 한 단계가 아니라 세 단계다: RUNNING → DRAINING → STOPPED — "새 요청 막기"와 "하던 일 끝내기"를 섞으면 둘 중 하나를 반드시 잘못한다.
- **막는 것이 먼저고, DRAINING을 밖에 알려야** 로드밸런서가 트래픽을 뺀다 — 안 알리면 우아하게 종료했는데 사용자는 오류를 본다.
- **기한이 없으면 종료가 아니다** — SIGKILL은 보고할 기회도 안 준다. 기한이 지나 버리는 것은 즉시 종료와 같지만, 몇 개를 버렸는지 아는 것이 다르다.
- 열아홉 상자의 결론: **실패는 없앨 수 없고, 무엇을 잃을지 고를 수 있을 뿐이다. 고르지 않으면 제일 나쁜 것을 잃는다 — 대개 조용히.**

## 용어 풀이

- **우아한 종료(graceful shutdown)**: 새 요청을 막고, 하던 일을 끝내고, 기한이 지나면 세어서 버리고 끝내는 종료.
- **즉시 종료(abrupt stop)**: 하던 일을 안 기다리고 그냥 멈추는 것. 처리 중 요청이 조용히 사라진다.
- **in-flight(처리 중)**: 받았지만 아직 응답을 못 준 요청. 이 수가 0이 되기를 기다리는 것이 배수다.
- **드레이닝(draining)**: 새 요청은 거절하고 처리 중인 것만 끝내는 단계. 물을 잠그고 배수구로 빼는 그림.
- **기한(deadline/timeout)**: 배수를 기다려주는 최대 시간. 최악 요청 기준으로 잡는다 — 평균이면 절반이 잘린다.
- **abandoned(버린 건수)**: 기한이 지나 버린 처리 중 요청의 수. 세어서 보고하는 것이 즉시 종료와의 차이다.
- **SIGTERM**: "정리하고 끝내라"는 신호. 핸들러를 걸어야 shutdown이 불린다.
- **SIGKILL**: "그냥 죽어라"는 신호. 잡을 수 없어서 보고할 기회도 없다.
- **오케스트레이터(orchestrator)**: 컨테이너를 배포·재시작하는 관리자(쿠버네티스 등). SIGTERM 뒤 유예 시간이 지나면 SIGKILL을 보낸다.
- **PID 1 문제**: 컨테이너의 첫 프로세스는 신호 기본 동작이 없어 SIGTERM이 무시되기 쉽다 — 증상은 즉시 종료와 같다.
- **헬스체크(health check)**: 로드밸런서가 주기적으로 "건강하냐"고 묻는 것. DRAINING이면 false를 줘야 트래픽이 빠진다.
- **폴링(polling, 주기 확인)**: wait/notify 대신 일정 간격으로 조건을 다시 확인하는 대기 방식. 이 구현의 대기 루프가 이 방식이라 notifyAll은 죽은 코드였다.
- **시계 주입(Ticker)**: 시간과 대기를 인터페이스로 받아 테스트가 가짜 시계로 시간을 감게 하는 것. 일도 시계에 태워야 결과가 재현된다.
