### A. 문제 (구현 대상 TODO)

#### 1. CountBasedWindow — 최근 N개 (링 버퍼)

```java
// impl 정답
public void record(boolean success) {
    if (size == results.length) {
        // 나가는 것을 먼저 빼야 한다. 덮어쓴 뒤에는 그게 실패였는지 알 수 없다.
        if (!results[next]) {
            failures--;
        }
    } else {
        size++;
    }
    results[next] = success;
    if (!success) {
        failures++;
    }
    next++;
    if (next == results.length) {
        next = 0;
    }
}
```

- Q: 가장 오래된 것을 지울 때 뒤를 당기지 않고 덮어쓰는 이유는?
  A: 당기면 삭제 한 번이 O(n)이고, 이 코드는 모든 원격 호출 경로에 붙는다.
  링 버퍼(원형 큐)처럼 다음 쓸 자리(next)만 돌리면 O(1)이다.
  가장 오래된 자리가 곧 다음 쓸 자리이므로 덮어쓰기 = 삭제 + 삽입이다.

- Q: "덮어쓸 자리의 값을 먼저 보고 빼기"를 덮어쓴 뒤에 하면 무엇이 어떻게 틀리는가?
  A: 그 자리에는 이미 방금 쓴 새 값이 들어 있어 "나간 값이 실패였나"를 알 길이 없다.
  failures가 실제와 어긋난 채로 계속 굴러가 실패율이 조용히 틀린다.
  회로가 열려야 할 때 안 열리거나, 안 열려야 할 때 열린다.

- Q: 그 틀림이 창이 한 바퀴 돌기 전에는 안 드러나는 이유는?
  A: 덮어쓰기는 창이 가득 찬 뒤(size == length)에만 일어나기 때문이다.
  그 전까지는 순서가 틀려도 결과가 같아 테스트가 전부 통과한다.
  무작위 대조 테스트(정직한 전수 계산과 비교)가 잡는 것이 정확히 이것이다.

- Q: failures 개수를 들고 다니는 것과 매번 배열을 훑는 것의 비용 차이는 어디에 붙는가?
  A: 모든 원격 호출 경로에 붙는다.
  창이 1000개면 호출마다 1000칸을 훑는 것과, 한 번 빼고 한 번 더하는 것의 차이다.
  집계를 증분으로 유지하는 대신 "더하고 빼는 순서"라는 불변식 관리 부담을 진다.

- Q: `failureRate()` 에서 size가 0일 때 0.0을 바로 돌려주는 이유는(NaN이 무엇을 일으키는가)?
  A: 0/0은 NaN이고 NaN은 어떤 비교에도 false를 준다.
  `rate >= threshold` 가 영원히 false가 되어 회로가 조용히 안 열린다.
  예외도 없이 기능이 사라지는 silent failure라 경계에서 미리 잘라 0.0을 준다.

- Q: 이 창이 보는 "시간 길이"가 트래픽에 따라 달라진다는 것은 무슨 뜻인가?
  A: "최근 100개"는 초당 1000건이면 0.1초, 하루 10건이면 열흘이다.
  같은 설정이 트래픽에 따라 완전히 다른 "최근"을 본다.
  시간 길이를 고정하고 싶으면 TimeBasedWindow를 쓴다 — 그게 두 구현이 나뉜 이유다.

#### 2. TimeBasedWindow — 최근 T밀리초 (시간 버킷)

```java
// impl 정답
private void expire() {
    long current = epochAt(ticker.nowMillis());
    for (int i = 0; i < epochs.length; i++) {
        if (epochs[i] != EMPTY && current - epochs[i] >= epochs.length) {
            epochs[i] = EMPTY;
            calls[i] = 0;
            failures[i] = 0;
        }
    }
}

public void record(boolean success) {
    expire();
    long current = epochAt(ticker.nowMillis());
    int slot = (int) Math.floorMod(current, (long) epochs.length);
    if (epochs[slot] != current) {
        epochs[slot] = current;
        calls[slot] = 0;
        failures[slot] = 0;
    }
    calls[slot]++;
    if (!success) {
        failures[slot]++;
    }
}
```

- Q: 기록 하나하나에 시각을 붙이지 않고 버킷으로 뭉치는 이유는(무엇을 맞바꾸는가)?
  A: 개별 기록은 정확하지만 호출마다 전부를 훑어야 하고 트래픽만큼 메모리가 쌓인다.
  버킷은 메모리가 버킷 개수로 고정되고 갱신이 O(버킷 수)다.
  대가는 정확도 — 창 길이가 정확히 T가 아니라 T-버킷길이 ~ T 사이가 된다. 정확도와 메모리·시간의 맞바꿈이다.

- Q: expire의 창 밖 판정에서 `>=` 를 `>` 로 쓰면 무엇이 달라지는가?
  A: 창이 버킷 하나만큼 길어진다.
  버킷 10개짜리 1000ms 창에서 번호 차이가 정확히 10이면 1000ms 전이므로 이미 창 밖인데, `>` 는 그것을 창 안으로 남긴다.
  테스트가 999ms와 1000ms를 나눠 확인하는 이유다 — 경계는 한쪽으로 정하고 못 박는다.

- Q: 버킷 번호 → 배열 칸 계산에 `%` 대신 `Math.floorMod` 를 쓰는 이유는?
  A: 자바의 `%` 는 음수 피연산자에 음수를 준다.
  Ticker 원점이 임의라 버킷 번호가 음수일 수 있고, 그러면 배열 인덱스가 -3 같은 값이 되어 그대로 예외다.
  floorMod는 항상 0 이상을 준다.

- Q: `epochAt` 이 `/` 대신 `Math.floorDiv` 를 쓰는 이유는?
  A: `/` 는 0 쪽으로 자르기 때문에 -50/100과 50/100이 둘 다 0이다.
  0 근처에서 버킷 하나가 두 배로 넓어진다.
  floorDiv는 음수에서도 아래쪽으로 내려 버킷 폭이 일정하다.

- Q: 칸에 든 번호가 지금 번호와 다를 때 비우고 세는 단계는, expire를 먼저 부르면 도달하지 않는데 왜 남겨두는가?
  A: expire가 이미 창 밖 버킷을 비웠고 창 안의 번호들은 서로 다른 칸에 들어가므로, 지금 흐름에서는 도달하지 않는다(변종 검증 M08 — 지워도 테스트 전부 통과).
  그래도 남긴다 — record에서 expire를 안 부르는 구현으로 바뀌면 이 줄이 유일한 방어선이다.
  그때 빠지면 자리 재사용 때문에 10초 전 실패가 지금 것으로 부활한다.

- Q: 만료를 record에서만 하고 읽기(totalCalls·failureRate)에서 안 하면 어떤 시나리오가 터지는가?
  A: 트래픽이 끊긴 순간 창이 그대로 얼어붙는다.
  장애가 끝나고 아무도 안 부르는 동안 실패율 100%가 영원히 남아 회로가 안 닫힌다.
  그래서 읽기 메서드도 먼저 expire()를 부른다 — 여기서도 읽기처럼 생긴 것이 쓰기다.

- Q: 생성자가 창 길이가 버킷 개수로 나누어떨어지지 않으면 아예 예외를 던지는 이유는?
  A: 1000ms를 3개로 나누면 333ms씩에 1ms가 남고, 그 1ms가 매 바퀴 누적된다.
  틀린 창 길이는 조용히 틀리고 아무도 안 본다.
  조용히 틀리게 두느니 아예 못 만들게 한다 — 생성 시점의 계약 검사다.

#### 3. CircuitBreaker.currentState — 조회가 상태를 바꾼다

```java
// impl 정답
private State currentState() {
    if (state == State.OPEN
            && ticker.nowMillis() - openedAtMillis >= config.waitDurationMillis()) {
        transitionTo(State.HALF_OPEN);
    }
    return state;
}
```

- Q: OPEN → HALF_OPEN 전이를 별도 타이머 스레드가 아니라 조회 시점에 하는 이유는?
  A: 시간이 지났다는 사실은 아무도 알려주지 않기 때문이다 — 물어볼 때 알게 된다.
  타이머 스레드는 스레드·스케줄링·종료 관리라는 새 복잡도를 사는데, 어차피 다음 요청이 올 때만 전이가 의미 있다.
  요청이 안 오면 HALF_OPEN이 되어 있을 필요도 없다 — 게으른(lazy) 전이로 충분하다.

- Q: 이 성질이 자료구조의 어떤 것들과 같은가(두 가지)?
  A: 10번 LRU 캐시의 get(조회가 순서를 바꾼다), 13번 lazy 세그먼트 트리의 rangeSum(조회가 미뤄둔 갱신을 실행한다).
  셋 다 "읽기처럼 생긴 것이 쓰기"라 동시성에서 락이 필요해진다.

- Q: 시각 비교를 덧셈으로 쓰면 어떤 조건에서 무엇이 조용히 사라지는가?
  A: `openedAt + wait <= now` 는 원점이 임의인 시계에서 openedAt이 크면 덧셈이 넘쳐 음수가 된다.
  그러면 조건이 항상 참 — 대기 시간이 0이나 마찬가지가 되어 회로가 열리자마자 간 보기로 넘어간다.
  차단이 사실상 사라지는데 상태 이름은 멀쩡해서 아무도 눈치채지 못한다. `now - openedAt >= wait` 뺄셈 방향이 맞다.

- Q: 상태를 바꿀 때 직접 대입하지 않고 transitionTo를 거쳐야 하는 이유는?
  A: 전이에는 상태 대입 말고도 따라오는 일이 있다 — 통계(stateTransitions) 증가, 창 비우기, 새 상태의 시작 조건(openedAtMillis, halfOpenPermits) 세팅.
  직접 대입하면 그것들이 빠져 이전 상태의 실패 기록·정원이 새 상태로 샌다.
  전이 로직을 한 곳에 모으는 단일 출처이기도 하다.

#### 4. CircuitBreaker.acquirePermission — 통과냐 거절이냐

```java
// impl 정답
private void acquirePermission() {
    synchronized (lock) {
        State now = currentState();
        if (now == State.CLOSED) {
            return;
        }
        if (now == State.OPEN) {
            rejectedCount++;
            throw new CircuitBreakerOpenException(
                    "회로가 열려 있다. 호출하지 않는다", remainingWaitMillis());
        }
        if (halfOpenPermits <= 0) {
            rejectedCount++;
            throw new CircuitBreakerOpenException("간 보기 정원이 찼다. 결과를 기다린다", 0L);
        }
        halfOpenPermits--;
    }
}
```

- Q: state 필드를 직접 읽으면 회로에 무슨 일이 생기는가?
  A: OPEN에서 대기 시간이 지나도 전이시켜 줄 곳이 없어 계속 OPEN으로 보인다.
  전이는 currentState() 안에만 있으므로, 그것을 우회하면 회로가 영영 안 열린다(HALF_OPEN으로 못 간다).

- Q: 간 보기 정원을 결과가 돌아온 뒤가 아니라 허가 시점에 미리 깎는 이유는?
  A: 원격 호출은 느리다 — 응답을 기다리는 동안에도 요청이 계속 들어온다.
  결과가 돌아온 뒤에 깎으면 그 사이 들어온 요청이 전부 "정원 남음"으로 보여 통과한다.
  허가 시점에 깎아야 "동시에 나가 있는 간 보기"가 정원 이하로 묶인다.

- Q: 미리 깎지 않으면 어떤 폭풍이 재현되는가(01번의 무엇과 같은 구조인가)?
  A: 대기 시간이 끝나는 순간 막혀 있던 요청이 전부 한꺼번에 나가 회복 중인 서버를 다시 죽인다.
  01번의 재시도 폭풍과 같은 구조다 — 동기화된 무리가 한 순간에 몰리는 것.
  HALF_OPEN의 존재 이유가 이 몰림을 "한 번만"으로 줄이는 것이다.

- Q: HALF_OPEN에서 정원이 없어 거절할 때 남은 대기 시간을 0으로 주는 이유는?
  A: 기다림의 문제가 아니기 때문이다.
  이미 누군가 찔러보고 있어서 거절하는 것이므로 "얼마나 기다려라"라는 정보 자체가 성립하지 않는다.
  OPEN의 거절(remainingWaitMillis)과 의미가 다르다는 것을 값으로 드러낸다.

- Q: CircuitBreakerOpenException이 "실패했다"가 아니라 "시도조차 안 했다"인 것이 호출자에게 왜 중요한가?
  A: 대응이 다르기 때문이다 — 실행이 실패했으면 결과가 불확실할 수 있지만, 시도조차 안 했으면 부작용이 확실히 없다.
  호출자는 안전하게 폴백(캐시·기본값)으로 갈 수 있고, 이 예외를 상대 건강의 표본으로 세면 안 된다는 판단 근거도 된다.

#### 5. CircuitBreaker.onSuccess / onError — 결과 반영

```java
// impl 정답
private void onSuccess() {
    synchronized (lock) {
        successCount++;
        if (state == State.HALF_OPEN) {
            halfOpenSuccesses++;
            if (halfOpenSuccesses >= config.permittedCallsInHalfOpen()) {
                transitionTo(State.CLOSED);
            }
            return;
        }
        if (state == State.CLOSED) {
            window.record(true);
            evaluate();
        }
        // OPEN 이면 늦게 돌아온 호출 — 창은 이미 비워졌으므로 넣지 않는다
    }
}

private void onError(Throwable error) {
    synchronized (lock) {
        if (!config.isFailure(error)) {
            if (state == State.HALF_OPEN) {
                halfOpenPermits++;   // 간 보기 기회를 돌려준다
            }
            return;
        }
        failureCount++;
        if (state == State.HALF_OPEN) {
            transitionTo(State.OPEN);
            return;
        }
        if (state == State.CLOSED) {
            window.record(false);
            evaluate();
        }
    }
}
```

- Q: HALF_OPEN의 판단 근거가 실패율이 아니라 "정해진 수만큼 다 됐나"인 이유는?
  A: 간 보기는 표본이 몇 개 안 되기 때문이다.
  표본 3개로 비율을 내는 것은 minimumCalls를 두는 이유를 스스로 어기는 것이다.
  그래서 성공은 "정원만큼 다 성공했나"로 CLOSED를, 실패는 하나만 나와도 즉시 OPEN을 정한다.

- Q: OPEN 상태로 돌아온 성공을 창에 넣지 않는 이유는 — 그 성공은 어디서 온 것인가?
  A: 회로가 열리기 **전에** 나갔던 호출이 늦게 돌아온 것이다.
  전이 때 창을 비웠으므로 지금 창은 새 상태의 것이고, 거기에 과거 결과를 섞으면 "창에는 CLOSED에서 난 결과만 들어간다"는 불변식이 깨진다.

- Q: 그 결과를 넣어도 당장은 티가 안 나는 이유와, 그런데도 테스트로 못 박는 이유는?
  A: 다음 전이에서 창이 다시 비워지므로 잘못 들어간 값도 곧 사라져 겉으로 안 드러난다.
  하지만 전이 직전의 evaluate가 오염된 창으로 판단할 수 있고, 이런 "조용히 무너지는" 성질은 테스트로 못 박아두지 않으면 리팩토링에서 소리 없이 사라진다.

- Q: isFailure가 false인 예외를 성공으로도 세지 않는 이유는?
  A: 성공으로 세면 실패율이 희석된다.
  400이 쏟아지는 동안 진짜 실패(503)의 비율이 낮아 보여 회로가 열려야 할 때 안 열린다.
  상대 건강에 대한 정보가 아닌 것은 표본에서 완전히 빼는 것이 맞다.

- Q: HALF_OPEN에서 무시할 예외를 만났을 때 정원을 돌려주지 않으면 어떤 상태에 갇히는가?
  A: 회복 불가능한 HALF_OPEN에 갇힌다.
  정원은 이미 acquirePermission에서 깎였는데 성공도 실패도 아니어서 전이 조건이 영영 안 찬다.
  통과시킬 자리도 없고(정원 0) 성공한 것도 없어 CLOSED로도 OPEN으로도 못 간다 — 그래서 돌려준다.

- Q: HALF_OPEN에서 실패 하나에 즉시 OPEN으로 가는 이유는?
  A: 간 보기의 목적이 "회복됐나 조심스럽게 확인"이기 때문이다.
  찔러본 것이 실패했으면 아직 아프다는 증거로 충분하다 — 표본 몇 개로 비율을 낼 일이 아니다.
  즉시 물러나서 다시 대기 시간을 주는 것이 회복을 돕는다.

#### 6. CircuitBreaker.evaluate — 열 것인가

```java
// impl 정답
private void evaluate() {
    if (window.totalCalls() >= config.minimumCalls()
            && window.failureRate() >= config.failureRateThreshold()) {
        transitionTo(State.OPEN);
    }
}
```

- Q: 두 조건 중 표본 수 검사가 없으면 배포 직후 무슨 일이 생기는가?
  A: 첫 요청이 우연히 타임아웃 나면 실패율이 1/1 = 100%라 즉시 회로가 열린다.
  멀쩡한 서비스 전체를 첫 호출 하나로 끊는 것이다.
  비율은 표본 수가 있어야 뜻이 있다 — minimumCalls가 그 표본 수다.

- Q: 실패율 비교가 `>` 가 아니라 `>=` 인 이유는?
  A: 설정에 0.5를 적은 사람의 의도는 "절반이 실패하면 열린다"인데, `>` 는 정확히 절반일 때 안 열린다.
  경계는 한쪽으로 정해서 테스트로 못 박는다 — 의도와 구현의 경계 방향을 일치시키는 것이다.

- Q: transitionTo가 전이할 때마다 창을 비우는 이유는 — 안 비우면 회복 직후 무엇이 일어나는가?
  A: OPEN이 되기 전의 실패를 CLOSED로 돌아온 뒤에도 기억하게 된다.
  회복해서 CLOSED가 되자마자 새 실패 하나에 옛 실패들과 합산되어 즉시 다시 열린다.
  상태마다 새 표본으로 시작해야 "지금 상태의 건강"을 본다.

### B. 개념

#### 7. 왜 차단하는가, 무엇을 내주는가

- Q: 상대가 확실히 죽었을 때 재시도를 계속하면 잃는 것 셋은 무엇인가?
  A: ① 사용자가 타임아웃 × 재시도 횟수만큼 기다리다 결국 실패를 본다(빨리 실패하는 편이 낫다).
  ② 죽어가는 서버에 계속 요청을 꽂아 회복을 방해한다.
  ③ 우리 쪽 스레드·커넥션이 응답 없는 호출에 묶여 장애가 우리에게로 번진다.

- Q: 핵심 측정에서 브레이커가 1000건을 29건으로 줄였는데, 29건의 내역은 무엇인가?
  A: 창을 채우는 10건(minimumCalls만큼은 겪어봐야 안다) + 5초마다 한 번씩 찔러보는 간 보기 19건.
  나머지 971건은 아예 나가지 않았고 사용자는 그 실패를 1초가 아니라 0ms 만에 봤다.
  CircuitBreakerReliefTest가 시간이 아니라 호출 횟수로 이 숫자를 낸다.

- Q: 사용자가 실패를 1초가 아니라 0ms 만에 본다는 것은 왜 개선인가?
  A: 결과가 같은 실패라면 기다림은 순수한 낭비이기 때문이다.
  기다리는 동안 스레드·커넥션이 묶이고, 사용자는 폴백(캐시·안내)으로 넘어갈 기회를 늦게 받는다.
  빠른 실패는 실패를 없애는 게 아니라 실패의 비용을 줄인다.

- Q: 실패율 50%로 회로가 열리면 멀쩡했던 나머지 절반은 어떻게 되는가 — 이 거래가 맞는 조건은?
  A: 성공하고 있던 절반도 함께 차단된다 — 부분 장애에서는 스스로 만든 장애다.
  이 거래는 "빠른 실패가 느린 실패보다 나을 때"만 맞다.
  차단이 주는 이득(회복 시간·자원 보호)이 멀쩡한 요청을 버리는 손해보다 클 때다.

- Q: 브레이커 상태가 프로세스마다 따로라는 것은 서버 20대에서 무엇을 의미하는가?
  A: 20대가 각자 창을 채워야 하니 장애 감지가 20배 느리다.
  간 보기도 20갈래로 나가 회복 중인 상대에게 20배로 찔러본다.
  그리고 상태를 지키는 락이 각 프로세스의 병목이 될 수 있다.

#### 8. 비율은 표본 수가 있어야 뜻이 있다

- Q: minimumCalls가 없으면 첫 호출 하나가 회로를 여는 이유는?
  A: 실패 1건/호출 1건 = 실패율 100%로 임계를 넘기 때문이다.
  표본 하나의 100%는 정보가 아니라 소음이다.

- Q: "비율은 표본 수가 있어야 뜻이 있다"를 실패율 계산식으로 설명하면?
  A: failureRate = failures / totalCalls 에서 분모가 작으면 한 건이 비율을 극단으로 흔든다.
  분모가 minimumCalls 이상일 때만 비율을 판단에 쓰겠다는 것이 evaluate의 첫 조건이다.
  통계로 말하면 표본 크기가 충분해야 추정이 안정된다는 얘기다.

#### 9. 이 실패가 누구 탓인가

- Q: PermanentFailureException(400류)을 실패로 세면 안 되는 이유는?
  A: 400이 많이 온다는 것은 상대가 멀쩡히 받아서 검증하고 거절하고 있다는 뜻이다.
  내 요청 탓인 실패로 회로를 열면 멀쩡한 상대를 차단하는 것이다.
  실패로 세는 것은 상대 건강에 대한 정보(타임아웃·503 등)뿐이다.

- Q: CircuitBreakerOpenException을 실패로 세면 어떤 되먹임이 생기는가?
  A: 차단 자체가 실패로 쌓여 실패율을 높이고, 높아진 실패율이 차단을 연장한다.
  회로가 자기 거절을 근거로 계속 열려 있는 자기 강화 루프 — 한 번 열리면 영영 안 닫힌다.
  시도조차 안 한 것은 상대 건강의 표본이 아니다.

- Q: 이 판단이 01번의 어떤 판단과 "정확히 같은 자리"인가?
  A: "재시도해도 되는 오류인가"(retryable 판정)와 같은 자리다.
  패턴이 달라도 첫 질문은 같다 — 이 실패가 누구 탓인가.
  상대 탓이면 물러나거나(백오프) 차단하고(브레이커), 내 탓이면 아무 장치도 개입하면 안 된다.

#### 10. 읽기처럼 생긴 것이 쓰기다

- Q: "조회가 상태를 바꾼다"가 동시성을 까다롭게 만드는 이유는?
  A: 읽기라면 락 없이 여럿이 동시에 봐도 되지만, 이 조회는 전이(쓰기)를 일으킨다.
  락 없이 두 스레드가 동시에 물으면 전이가 두 번 일어나거나 반쯤 된 상태를 본다.
  그래서 state() 같은 겉보기 읽기도 락을 잡는다.

- Q: execute 전체를 synchronized로 감싸면 무엇이 무엇의 원인이 되는가?
  A: 느린 원격 호출 하나가 락을 쥐고 있는 동안 나머지 전부가 줄을 선다.
  장애를 막으려고 넣은 브레이커가 전체 처리량의 병목 — 장애의 원인이 된다.

- Q: 락 안에서 할 일과 락 밖에서 할 일은 각각 무엇인가?
  A: 락 안 — 상태를 만지는 전부: acquirePermission, onSuccess/onError, 상태·통계 조회.
  락 밖 — action.call() 실행(느린 원격 호출).
  execute의 순서가 계약이다: 허가(락) → 실행(락 밖) → 보고(락).

#### 11. 경계는 한쪽으로 정하고 못 박는다

- Q: 시각 비교를 덧셈으로 쓰면 "차단이 사실상 사라지는데 상태 이름은 멀쩡하다"는 것은 어떤 상황인가?
  A: `openedAt + wait` 이 오버플로로 음수가 되면 "대기 시간이 지났다" 판정이 항상 참이다.
  회로가 열리자마자 매 조회에서 HALF_OPEN으로 넘어가 사실상 차단 없이 계속 찔러본다.
  상태 값은 OPEN → HALF_OPEN으로 정상처럼 보여서 모니터링으로도 안 잡힌다.

- Q: 이 함정은 01번의 어느 계산과 같은 것인가?
  A: Retryer의 데드라인 계산과 같다 — `now + delay >= deadline` 이 아니라 `deadline - now <= delay`.
  원점이 임의인 단조 시계에서는 항상 뺄셈(간격) 방향으로 비교한다.

#### 12. 겹쳐 쓰기와 한계

- Q: 브레이커 안쪽에 재시도를 두면 회로가 왜 세 배 빨리 열리는가?
  A: 시도 하나하나가 브레이커를 통과하므로 요청 하나가 창을 세 칸 채운다.
  표본이 3배 빨리 차서 장애를 3배 빨리 감지하지만, 잠깐 흔들린 것에도 3배 쉽게 열린다.
  어느 쪽이 맞는지는 상황의 선택이고, 중요한 것은 겹치는 순서를 우연에 맡기면 안 된다는 것이다.

- Q: minimumCalls가 창 크기보다 크면 회로에 무슨 일이 생기고, 왜 생성자가 못 막는가?
  A: totalCalls가 창 크기를 넘을 수 없어 minimumCalls에 영영 못 미쳐 회로가 영원히 안 열린다.
  창(SlidingWindow 인터페이스)이 자기 크기를 드러내지 않으니 브레이커 생성자가 두 값을 비교할 수 없다.
  그래서 코드로 못 막고 `minimumLargerThanWindowNeverOpens` 테스트로 그 사실을 못 박아둔다.

- Q: TimeBasedWindow의 창 길이가 정확히 T가 아니라는 것은 무슨 뜻이고, 무엇과 맞바꾸는가?
  A: 버킷 경계 단위로 잘리므로 실제로 보는 구간은 T-버킷길이 에서 T 사이 어딘가다.
  버킷을 잘게 쪼개면 정확해지는 대신 배열(메모리)과 훑는 비용이 커진다.
  정확도 ↔ 메모리의 맞바꿈이다.

- Q: 변종 검증에서 안 잡힌 두 줄(M20·M08)은 왜 지우지 않고 남겼는가?
  A: 둘 다 지금 호출 구조에서는 도달하지 않는 방어 코드다(transitionTo의 같은 상태 검사, record의 버킷 초기화).
  하지만 부르는 자리가 하나 늘거나 expire 호출이 빠지는 순간 유일한 방어선이 된다.
  지우는 대신 "지워도 테스트가 통과한다"는 사실을 주석으로 남겨 정직하게 기록했다.

#### 13. 다음 챕터로의 다리

- Q: 회로는 상대별로 끊는데 못 막는 것은 무엇인가?
  A: 한 상대가 느려지는 동안(아직 회로가 열리기 전) 스레드 풀이 통째로 마르는 것.
  회로는 "실패가 쌓인 뒤" 반응하는데, 느림은 실패가 되기 전에 자원을 다 먹는다.
  그래서 03-bulkhead가 자원 자체를 상대별 칸으로 나눈다.

- Q: ResilienceStrategy 인터페이스가 03-bulkhead에서 하는 역할은?
  A: 브레이커와 벌크헤드가 같은 모양(`execute(Callable)`)을 갖게 해서 겹쳐 쓸 수 있게 한다.
  전략을 전략으로 감싸는 조합(데코레이터)이 가능해진다 — 벌크헤드 안에 브레이커, 또는 그 반대.
