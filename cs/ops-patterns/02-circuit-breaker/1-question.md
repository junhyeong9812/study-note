### A. 문제 (구현 대상 TODO — `src/main/java/com/ops/breaker/`)

#### 1. CountBasedWindow — 최근 N개 (링 버퍼)

```java
@Override
public void record(boolean success) {
    // TODO 1: 결과 하나를 넣는다. 창이 가득 차 있으면 가장 오래된 것을 덮어쓴다.
    //
    //   1. 이미 가득 찼나 (size 가 배열 길이와 같나)
    //      가득 찼으면 **덮어쓸 자리에 있던 값을 먼저 봐야 한다.**
    //      그게 실패였으면 failures 에서 빼고 나서 덮어쓴다
    //   2. 그 자리에 새 결과를 쓴다. 실패면 failures 를 늘린다
    //   3. next 를 한 칸 옮긴다. 끝에 닿으면 0 으로
    //
    // **1번의 순서가 전부다.** 덮어쓴 다음에 "그게 실패였나"를 물어보면 이미 늦다.
}
```

- 가장 오래된 것을 지울 때 뒤를 당기지 않고 덮어쓰는 이유는?
- "덮어쓸 자리의 값을 먼저 보고 빼기"를 덮어쓴 뒤에 하면 무엇이 어떻게 틀리는가?
- 그 틀림이 창이 한 바퀴 돌기 전에는 안 드러나는 이유는?
- failures 개수를 들고 다니는 것과 매번 배열을 훑는 것의 비용 차이는 어디에 붙는가?
- `failureRate()` 에서 size가 0일 때 0.0을 바로 돌려주는 이유는(NaN이 무엇을 일으키는가)?
- 이 창이 보는 "시간 길이"가 트래픽에 따라 달라진다는 것은 무슨 뜻인가?

#### 2. TimeBasedWindow — 최근 T밀리초 (시간 버킷)

```java
private void expire() {
    // TODO 1: 지금 버킷 번호를 구하고, 창 밖으로 나간 칸을 비운다.
    //
    //   - 비어 있는 칸(EMPTY)은 건드리지 않는다
    //   - 지금 번호와 그 칸의 번호 차이가 **버킷 개수 이상**이면 창 밖이다
    //
    // `>=` 인지 `>` 인지가 여기서 창 길이를 정한다.
}

@Override
public void record(boolean success) {
    // TODO 2: 지금 버킷에 결과 하나를 더한다.
    //
    //   1. 먼저 expire() 를 부른다
    //   2. 지금 버킷 번호를 구한다
    //   3. 그 번호가 들어갈 칸 = 번호를 버킷 개수로 나눈 나머지. **Math.floorMod 를 써야 한다**
    //   4. 칸에 든 번호가 지금 번호와 다르면 다른 시각의 잔재다. 비우고 나서 센다
    //   5. 호출 수를 늘리고, 실패면 실패 수도 늘린다
}
```

- 기록 하나하나에 시각을 붙이지 않고 버킷으로 뭉치는 이유는(무엇을 맞바꾸는가)?
- expire의 창 밖 판정에서 `>=` 를 `>` 로 쓰면 무엇이 달라지는가?
- 버킷 번호 → 배열 칸 계산에 `%` 대신 `Math.floorMod` 를 쓰는 이유는?
- `epochAt` 이 `/` 대신 `Math.floorDiv` 를 쓰는 이유는?
- 칸에 든 번호가 지금 번호와 다를 때 비우고 세는 단계는, expire를 먼저 부르면 도달하지 않는데 왜 남겨두는가?
- 만료를 record에서만 하고 읽기(totalCalls·failureRate)에서 안 하면 어떤 시나리오가 터지는가?
- 생성자가 창 길이가 버킷 개수로 나누어떨어지지 않으면 아예 예외를 던지는 이유는?

#### 3. CircuitBreaker.currentState — 조회가 상태를 바꾼다 (TODO 1)

```java
/** 락을 잡은 상태에서만 부른다. */
private State currentState() {
    // TODO 1: OPEN 인데 대기 시간이 지났으면 HALF_OPEN 으로 바꾸고, 지금 상태를 반환한다.
    //
    // **이 메서드가 이 클래스에서 제일 이상한 부분이다. 조회가 상태를 바꾼다.**
    // 시간이 지났다는 사실은 아무도 알려주지 않는다. **물어볼 때 알게 된다.**
    //
    // 경과 시간은 **뺄셈으로 비교한다.**
    //   now - openedAt >= wait      맞다
    //   openedAt + wait <= now      **덧셈이 넘친다**
}
```

- OPEN → HALF_OPEN 전이를 별도 타이머 스레드가 아니라 조회 시점에 하는 이유는?
- 이 성질이 자료구조의 어떤 것들과 같은가(두 가지)?
- 시각 비교를 덧셈으로 쓰면 어떤 조건에서 무엇이 조용히 사라지는가?
- 상태를 바꿀 때 직접 대입하지 않고 transitionTo를 거쳐야 하는 이유는?

#### 4. CircuitBreaker.acquirePermission — 통과냐 거절이냐 (TODO 2)

```java
private void acquirePermission() {

        //   CLOSED     그냥 통과
```

- 미리 깎지 않으면 어떤 폭풍이 재현되는가(01번의 무엇과 같은 구조인가)?

#### 5. CircuitBreaker.onSuccess / onError — 결과 반영 (TODO 3·4)

```java
    //   CLOSED 면 창에 실패를 기록하고 evaluate()
```

- 그 결과를 넣어도 당장은 티가 안 나는 이유와, 그런데도 테스트로 못 박는 이유는?
- isFailure가 false인 예외를 성공으로도 세지 않는 이유는?
- HALF_OPEN에서 무시할 예외를 만났을 때 정원을 돌려주지 않으면 어떤 상태에 갇히는가?
- HALF_OPEN에서 실패 하나에 즉시 OPEN으로 가는 이유는?
