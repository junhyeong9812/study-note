### A. 문제 (구현 대상 TODO — `src/main/java/com/ops/retry/`)

#### 1. FixedDelayRetry — 늘 같은 간격

```java
@Override
public long delayMillisAfter(int attempt) {
    requireAttempt(attempt);
    // TODO 1: 몇 번째든 같은 값이다. 한 줄이다.
    //
    // 이 한 줄이 왜 문제인지는 RetryStormTest 를 돌려보면 안다.
}
```

- 구현이 한 줄인데 왜 "가장 위험하다"고 하는가?
- 1000개 클라이언트가 같은 순간에 실패하면 100ms 뒤에 무슨 일이 일어나는가?
- 이 현상(thundering herd)이 장애를 "회복"이 아니라 "증폭"으로 만드는 이유는?
- 그런데도 이 정책을 먼저 만들어보게 하는 이유는 무엇인가?

#### 2. ExponentialBackoffRetry — 실패할수록 오래 기다린다

```java
@Override
public long delayMillisAfter(int attempt) {
    FixedDelayRetry.requireAttempt(attempt);
    // TODO 1: base * 2^(attempt-1). 단 maxMillis 를 넘지 않는다.
    //
    // **곱하기 전에 넘칠지 먼저 검사해야 한다.**
    //   곱한 뒤에 "상한보다 크면 상한" 으로 하면 이미 늦다. 오버플로가 음수를 만든다.
    //   base > (max >> shift) 이면 어차피 상한을 넘는다는 뜻이니 거기서 상한을 반환한다.
    //   shift 가 63 이상이면 시프트 자체가 정의되지 않으므로(자바는 64로 나눈 나머지를 쓴다)
    //   그 전에 걸러야 한다.
}
```

- 왜 선형(100, 200, 300…)이 아니라 2배씩 늘리는가?
- 상한(maxMillis)이 없으면 10번째·20번째 대기는 어떻게 되는가?
- "곱한 뒤에 상한과 비교"하는 구현은 왜 이미 늦은가?
- `base > (max >> shift)` 라는 검사는 무엇을 곱하기 전에 확인하는 것인가?
- shift가 63 이상일 때 자바의 `<<` 는 실제로 어떻게 동작하는가?
- 이 정책까지 넣어도 몰림이 안 깨지는 이유는 무엇인가?

#### 3. JitteredBackoffRetry — 무작위를 섞는다 (이 문제의 핵심)

```java
@Override
public long delayMillisAfter(int attempt) {
    // TODO 1: 감싼 정책의 백오프를 받아 무작위로 흔든다.
    //
    //   FULL  : [0, backoff] 균등
    //   EQUAL : [backoff/2, backoff] 균등
    //
    // `random.nextLong(bound)` 는 [0, bound) 다. **양끝을 포함하려면 bound 를 하나 키운다.**
    // EQUAL 에서 backoff 가 홀수면 half 와 나머지가 다르다.
    // backoff - half 로 계산해야 위쪽 끝이 정확히 backoff 가 된다.
}
```

- 지터가 별도 정책이 아니라 기존 정책을 감싸는 래퍼인 이유는?
- FULL과 EQUAL은 각각 어느 범위에서 뽑는가?
- `random.nextLong(backoff)` 가 아니라 `nextLong(backoff + 1)` 인 이유는?
- EQUAL에서 backoff가 홀수일 때 `half + random(half + 1)` 로 쓰면 무엇이 틀리는가?
- 그 틀림이 짝수만 테스트하면 안 걸리는 이유는?
- seed를 생성자로 받는 이유는 무엇과 같은 이유인가?

#### 4. Retryer — 언제 멈출까 (경우가 넷이라 제일 길다)

```java
public <T> T call(Callable<T> action, long deadlineMillis) throws Exception {
    // TODO 1: 성공할 때까지, 또는 멈출 이유가 생길 때까지 돈다.
    //
    //   1. action.call() 이 성공하면 그대로 반환한다
    //   2. 잡은 예외가 재시도 대상이 아니면 **즉시 다시 던진다.** 기다리지 않는다
    //   3. 이번이 마지막 시도였으면 다시 던진다
    //      (**시도 3번이면 대기는 2번이다.** 마지막 실패 뒤에는 기다릴 이유가 없다)
    //   4. 다음 대기 시간을 정책에서 받는다
    //   5. **남은 시간이 그 대기보다 짧거나 같으면 포기한다.** abandonedByDeadline 을 센다
    //   6. 아니면 자고 다음 시도로 간다
    //
    // 5번에 함정이 둘 있다.
    //   - `now + delay >= deadline` 으로 쓰면 **덧셈이 넘친다.**
    //   - **NO_DEADLINE 은 아예 검사에서 빼야 한다.**
}
```

- Retryer가 멈추는 네 가지 이유는 무엇인가?
- 재시도 불가 오류(2번)를 기다리지 않고 즉시 던지는 이유는?
- "시도 3번이면 대기는 2번"은 루프의 어떤 조건 순서로 구현되는가?
- 데드라인 검사를 `now + delay >= deadline` 으로 쓰면 언제 어떻게 틀리는가?
- `deadline - now <= delay` 로 쓰면 왜 안전한가?
- NO_DEADLINE(Long.MAX_VALUE)을 검사에서 통째로 빼야 하는 이유는?
- attempts·totalWaitMillis·abandonedByDeadline을 세어두는 이유는?
