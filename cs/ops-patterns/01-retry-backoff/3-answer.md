### A. 문제 (구현 대상 TODO)

#### 1. FixedDelayRetry — 늘 같은 간격

```java
// impl 정답
@Override
public long delayMillisAfter(int attempt) {
    requireAttempt(attempt);
    return delayMillis;
}
```

- Q: 구현이 한 줄인데 왜 "가장 위험하다"고 하는가?\
  A: 코드의 복잡도와 운영에서의 위험은 별개이기 때문이다.\
  모든 클라이언트가 같은 간격으로 기다리므로 재시도 시각이 완전히 동기화된다.\
  RetryStormTest 기준으로 1000개 실패 → 가장 붐비는 10ms 구간에 1000개 전부가 다시 온다.

> **동기화(synchronization)** — 여럿이 같은 규칙을 따라 같은 시각에 같은 행동을 하게 되는 것.\
> 예: 모두가 "실패하면 100ms 뒤"를 지키면 재시도 시각이 한 점에 겹친다.

- Q: 1000개 클라이언트가 같은 순간에 실패하면 100ms 뒤에 무슨 일이 일어나는가?\
  A: 1000개 전부가 정확히 100ms 뒤 같은 순간에 다시 때린다.\
  죽어가는 서버에 1000 RPS를 다시 꽂는 것이고, 또 실패하면 100ms 뒤에 또 온다.\
  서버에 회복할 틈을 주지 않는다.

- Q: 이 현상(thundering herd)이 장애를 "회복"이 아니라 "증폭"으로 만드는 이유는?\
  A: 상대가 아파서 실패했는데 전원이 동시에 다시 때리면 상대는 더 아파진다.\
  실패 → 동시 재시도 → 더 큰 실패 → 더 큰 동시 재시도로 되먹임(양의 피드백)이 걸린다.\
  재시도가 장애의 원인 제공자가 되는 것이다.

> **재시도 폭풍(retry storm)** — 재시도가 한꺼번에 몰려 장애를 증폭시키는 현상.\
> 예: 1000개 클라이언트가 같은 100ms를 세고 같은 순간에 다시 때리는 것.

- Q: 그런데도 이 정책을 먼저 만들어보게 하는 이유는 무엇인가?\
  A: 먼저 만들어보고 무엇이 문제인지 봐야 다음 것이 왜 필요한지 알기 때문이다.\
  원본 주석이 자료구조 문제집의 04번 나이브 큐, 07번 정렬 리스트 힙과 같은 자리라고 말한다 — 나쁜 기준선(baseline)을 손으로 만들어보는 교육 장치다.

#### 2. ExponentialBackoffRetry — 실패할수록 오래 기다린다

```java
// impl 정답
@Override
public long delayMillisAfter(int attempt) {
    FixedDelayRetry.requireAttempt(attempt);
    int shift = attempt - 1;
    if (shift >= 63 || baseMillis > (maxMillis >> shift)) {
        return maxMillis;
    }
    return baseMillis << shift;
}
```

- Q: 왜 선형(100, 200, 300…)이 아니라 2배씩 늘리는가?\
  A: 상대가 얼마나 아픈지 모르기 때문이다.\
  잠깐 흔들린 것이면 첫 재시도에서 끝나고, 오래 아프면 빠르게 물러난다.\
  선형으로 늘리면 물러나는 속도가 장애 길이를 못 따라간다.

> **백오프(backoff)** — 실패할수록 대기 시간을 늘리는 것.\
> 예: 지수 백오프는 base=100ms면 100 → 200 → 400 → 800ms 로 2배씩 늘린다.

- Q: 상한(maxMillis)이 없으면 10번째·20번째 대기는 어떻게 되는가?\
  A: base=100ms 기준 10번째가 100 << 9 = 51,200ms ≈ 51초, 20번째가 100 << 19 ≈ 14시간이다.\
  상한이 없으면 대기가 실용 범위를 벗어나고, 더 가면 시프트가 부호 비트를 침범해 음수가 된다.

- Q: "곱한 뒤에 상한과 비교"하는 구현은 왜 이미 늦은가?\
  A: 곱하는(시프트하는) 순간 long 범위를 넘으면 결과가 음수로 뒤집히기 때문이다.\
  음수는 maxMillis보다 작으므로 "상한보다 크면 상한" 검사를 그대로 통과한다.\
  음수 대기 → sleep 즉시 반환 → 즉시 재시도 = 정확히 막으려던 재시도 폭풍이다.

> **오버플로(overflow)** — 정수 최대값을 넘어 음수로 뒤집히는 것.\
> 예: 음수 대기는 sleep 이 즉시 반환하므로 대기 없는 즉시 재시도가 된다.

- Q: `base > (max >> shift)` 라는 검사는 무엇을 곱하기 전에 확인하는 것인가?\
  A: "base << shift 가 max를 넘는가"를 곱하기 전에 나눗셈 방향으로 확인하는 것이다.\
  `base << shift > max` 와 수학적으로 같은 조건을, 넘칠 수 있는 왼쪽 대신 안전한 오른쪽(max를 미리 줄여서)으로 계산한다.\
  참이면 어차피 상한을 넘는다는 뜻이니 바로 maxMillis를 반환한다.

- Q: shift가 63 이상일 때 자바의 `<<` 는 실제로 어떻게 동작하는가?\
  A: 자바는 long 시프트에서 시프트 양을 64로 나눈 나머지만 쓴다.\
  `x << 64` 는 x 그대로이고 `1L << 63` 은 음수다 — 의도한 "아주 큰 값"이 아니다.\
  그래서 시프트 자체가 의미를 잃는 63 이상은 검사 앞단에서 걸러 maxMillis를 반환한다.

- Q: 이 정책까지 넣어도 몰림이 안 깨지는 이유는 무엇인가?\
  A: 지수 백오프는 "얼마나 자주"를 줄일 뿐 "언제"를 흩뿌리지 않는다.\
  같은 시각에 실패한 클라이언트들은 같은 규칙으로 같은 100ms를 세고 같은 시각에 다시 온다.\
  모두가 같은 규칙을 따르기 때문에 동기화된다 — 깨려면 각자 다른 값(무작위)이 필요하다.

#### 3. JitteredBackoffRetry — 무작위를 섞는다

```java
// impl 정답
@Override
public long delayMillisAfter(int attempt) {
    long backoff = delegate.delayMillisAfter(attempt);
    if (backoff <= 0) {
        return 0L;
    }
    if (mode == Mode.FULL) {
        return random.nextLong(backoff + 1);
    }
    long half = backoff / 2;
    return half + random.nextLong(backoff - half + 1);
}
```

- Q: 지터가 별도 정책이 아니라 기존 정책을 감싸는 래퍼인 이유는?\
  A: 지터의 역할은 "얼마나"의 계산이 아니라 이미 계산된 값을 흩뿌리는 것뿐이기 때문이다.\
  delegate가 backoff를 계산하고, 지터는 그 범위 안에서 무작위로 뽑는다.\
  maxAttempts·retryable도 전부 delegate에 위임한다 — 어떤 정책과도 조합할 수 있다(데코레이터).

> **지터(jitter)** — 대기 시간에 섞는 무작위. 재시도 시각을 흩뿌리는 유일한 방법.\
> 예: FULL 은 `[0, backoff]`, EQUAL 은 `[backoff/2, backoff]` 에서 뽑는다.

- Q: FULL과 EQUAL은 각각 어느 범위에서 뽑는가?\
  A: FULL은 `[0, backoff]` 전체에서 균등하게 뽑는다.\
  EQUAL은 `[backoff/2, backoff]` — 절반은 반드시 기다리고 나머지 절반만 흔든다.

- Q: `random.nextLong(backoff)` 가 아니라 `nextLong(backoff + 1)` 인 이유는?\
  A: `nextLong(bound)` 는 `[0, bound)` 로 위쪽 끝을 제외하기 때문이다.\
  backoff 자신도 나올 수 있어야 하므로(양끝 포함) bound를 하나 키운다.

- Q: EQUAL에서 backoff가 홀수일 때 `half + random(half + 1)` 로 쓰면 무엇이 틀리는가?\
  A: 정수 나눗셈에서 half = backoff/2 는 내림이라, 홀수면 half + half = backoff - 1 이다.\
  상한이 backoff - 1 로 한 칸 모자라 "위쪽 끝이 정확히 backoff" 계약이 깨진다.\
  `half + random(backoff - half + 1)` 로 나머지를 따로 계산해야 상한이 정확해진다.

- Q: 그 틀림이 짝수만 테스트하면 안 걸리는 이유는?\
  A: 짝수 backoff에서는 half == backoff - half 라 두 식이 같은 값이기 때문이다.\
  홀수에서만 1의 차이가 드러난다 — 경계 버그가 특정 입력 모양에서만 보이는 전형이다.\
  README가 "짝수만 테스트하면 안 걸리는 함정"이라 부르는 것이 이것이다.

- Q: seed를 생성자로 받는 이유는 무엇과 같은 이유인가?\
  A: Ticker를 주입하는 이유, 그리고 12번 스킵 리스트에서 Random을 주입한 이유와 같다.\
  결정적으로 만들 수 없는 것은 검증할 수 없다 — seed를 고정하면 테스트가 같은 난수열로 재현된다.

> **결정적(deterministic)** — 같은 입력이면 항상 같은 결과.\
> 예: 시계·난수를 주입해야 테스트가 결정적이 된다 — seed 를 고정하면 같은 난수열이 나온다.

#### 4. Retryer — 언제 멈출까

```java
// impl 정답 (핵심 루프)
for (int attempt = 1; ; attempt++) {
    attempts++;
    try {
        return action.call();                                   // 이유 1: 성공
    } catch (Exception e) {
        if (!policy.retryable(e)) throw e;                      // 이유 2: 영구 실패
        if (attempt >= policy.maxAttempts()) throw e;           // 이유 3: 횟수 소진
        long delay = policy.delayMillisAfter(attempt);
        if (deadlineMillis != NO_DEADLINE
                && deadlineMillis - ticker.nowMillis() <= delay) {
            abandonedByDeadline++;
            throw e;                                            // 이유 4: 데드라인
        }
        totalWaitMillis += delay;
        ticker.sleep(delay);
    }
}
```

- Q: Retryer가 멈추는 네 가지 이유는 무엇인가?\
  A: ① 성공(값을 반환) ② 재시도 불가 오류(즉시 던짐) ③ 시도 횟수 소진(마지막 예외를 던짐) ④ 데드라인(남은 시간 ≤ 다음 대기면 자지 않고 포기).

> **데드라인(deadline)** — 이 절대 시각까지는 끝나야 한다는 약속.\
> 예: 남은 시간보다 긴 대기는 무의미하다 — 그래서 자지 않고 포기한다.

- Q: 재시도 불가 오류(2번)를 기다리지 않고 즉시 던지는 이유는?\
  A: 400 같은 영구 실패는 몇 번을 보내도 결과가 같기 때문이다.\
  기다리면 사용자 지연만 늘고 상대 서버 부하만 는다 — 얻는 것이 없다.\
  그래서 retryable 판정이 대기·횟수보다 앞에 온다.

- Q: "시도 3번이면 대기는 2번"은 루프의 어떤 조건 순서로 구현되는가?\
  A: 실패를 잡은 뒤 `attempt >= maxAttempts` 검사를 **sleep보다 먼저** 한다.\
  마지막(3번째) 시도가 실패하면 대기 계산에 들어가기 전에 던지므로 대기는 1·2번째 실패 뒤 두 번만 일어난다.\
  마지막 실패 뒤에 자면 아무도 기다리지 않는 잠이다.

- Q: 데드라인 검사를 `now + delay >= deadline` 으로 쓰면 언제 어떻게 틀리는가?\
  A: now가 이미 큰 값이면(원점이 임의라 가능) 덧셈이 long을 넘쳐 음수가 된다.\
  음수는 deadline보다 작으니 "시간이 남았다"고 오판해 데드라인을 지나서도 잔다.

- Q: `deadline - now <= delay` 로 쓰면 왜 안전한가?\
  A: 뺄셈은 "남은 시간"이라는 실제 크기의 값이라 두 값이 같은 시계 원점 위에 있는 한 넘치지 않는다.\
  남은 시간을 먼저 구해 delay와 비교하므로 원점이 어디든 결과가 같다.

- Q: NO_DEADLINE(Long.MAX_VALUE)을 검사에서 통째로 빼야 하는 이유는?\
  A: 센티널은 약속된 표식이지 계산에 넣을 수 있는 값이 아니기 때문이다.\
  `MAX_VALUE - now` 를 계산하면 now가 큰 원점일 때 남은 시간이 작게 나와, 데드라인이 없는데도 포기한다.\
  그래서 `deadlineMillis != NO_DEADLINE` 으로 검사 자체를 건너뛴다 — 원본 저자가 실제로 계산에 넣었다가 변종 검증에서 잡힌 결함이다.

> **센티널(sentinel)** — 특별한 의미를 약속해 둔 값.\
> 예: `NO_DEADLINE = Long.MAX_VALUE` 는 계산에 넣지 말고 비교로만 쓴다.

- Q: attempts·totalWaitMillis·abandonedByDeadline을 세어두는 이유는?\
  A: 테스트가 "몇 번 시도했고 얼마나 잤고 왜 멈췄나"를 밖에서 관측할 수 있어야 하기 때문이다.\
  반환값·예외만으로는 중간 동작(대기 횟수·데드라인 포기)이 안 보인다 — 계측값이 검증 표면이다.

#### 5. RetryBudget — 전체 부하의 상한

```java
// impl 정답
public void onRequest() {
    tokensScaled = Math.min(maxScaled, tokensScaled + ratioScaled);
}

public boolean tryRetry() {
    if (tokensScaled >= SCALE) {
        tokensScaled -= SCALE;
        return true;
    }
    return false;
}
```

- Q: 재시도 정책이 있는데 왜 예산이 또 필요한가?\
  A: 정책은 **한 요청**의 재시도를 3번으로 묶을 뿐이다.\
  상대가 완전히 죽으면 모든 요청이 3번씩 해서 전체 부하가 3배가 된다.\
  전체 트래픽 대비 재시도 비율은 요청 단위 정책 밖의 일이라 별도 장치(예산)가 필요하다.

> **재시도 예산(retry budget)** — 전체 트래픽 대비 재시도 비율의 상한.\
> 예: 토큰통에 요청마다 ratio만큼 채우고 재시도마다 1개 쓴다.

- Q: 토큰 상한(max)이 없으면 어떤 시나리오에서 폭주하는가?\
  A: 한가한 시간 동안 요청마다 쌓인 토큰이 무한정 모인다.\
  그러다 장애가 나면 모아둔 예산으로 재시도가 한꺼번에 터진다 — 상한이 "저축해 둔 폭주"를 막는다.

- Q: tryRetry에서 "빼고 나서 음수인지 확인"하면 무엇이 새는가?\
  A: 거절되는 호출에서도 토큰이 먼저 줄어 있게 된다.\
  거절이 반복될수록 예산이 조용히 새어나가, 실제로 허용해야 할 재시도까지 거절된다.\
  그래서 `tokensScaled >= SCALE` 를 먼저 확인하고 통과한 경우에만 뺀다.

- Q: 토큰을 double이 아니라 1/1000 단위 정수(tokensScaled)로 세는 이유는?\
  A: 0.1은 2진수로 딱 떨어지지 않아 `tokens += 0.1` 을 100번 하면 9.999…가 되기 때문이다.\
  그러면 "100 요청에 10%니까 10번"이 9번이 되고 그 1번을 아무도 설명 못 한다.\
  세는 것은 정수로 센다 — 원본도 double로 먼저 썼다가 테스트에서 걸렸다.

- Q: 이 예산이 정상 상황에서는 안 걸리고 장애 때만 걸리는 구조인 이유는?\
  A: 정상일 때는 재시도가 드물어 토큰 소비가 충전(요청당 ratio)을 못 따라가므로 통이 늘 차 있다.\
  장애로 재시도가 폭증하면 소비가 충전을 넘어서 토큰이 바닥나고 그때만 거절이 시작된다.\
  제약이 필요한 시점(전면 장애)에만 발동하는 것이 설계 의도다.

### B. 개념

#### 6. 재시도의 첫 번째 판단

- Q: 재시도 정책이 정하는 세 가지는 무엇이고, 왜 "재시도해도 되는가"가 첫 번째인가?\
  A: ① 재시도해도 되는 오류인가 ② 몇 번까지 ③ 얼마나 기다렸다가.\
  ①이 아니면 ②③은 의미가 없다 — 안 되는 오류를 재시도하면 지연과 부하만 늘고 결과는 같다.

- Q: 400 Bad Request를 다섯 번 재시도하면 누가 무엇을 잃는가?\
  A: 사용자는 5초를 더 기다리고도 같은 400을 받는다.\
  상대 서버는 의미 없는 요청 4번만큼 부하가 는다.\
  아무도 얻는 것이 없다.

- Q: 일시 실패(transient)와 영구 실패(permanent)를 가르는 기준은 무엇인가?\
  A: 원인이 상대(또는 환경)에 있어 다시 하면 될 수도 있는가(타임아웃·503·데드락) vs 원인이 내 요청 자체에 있어 몇 번을 해도 같은가(400·404·잔액 부족).\
  코드에서는 TransientFailureException / PermanentFailureException 두 예외 타입으로 나뉘고, `RetryPolicy.retryable` 기본 구현이 transient 만 재시도 대상으로 본다.

> **일시 실패(transient) / 영구 실패(permanent)** — 다시 하면 될 수도 있는 실패(타임아웃, 503, 데드락) / 몇 번을 해도 같은 실패(400, 404, 잔액 부족).\
> 예: 원인이 상대에 있나 내 요청에 있나로 갈린다.

#### 7. 지수 백오프는 왜 못 흩뿌리는가

- Q: 1000개 클라이언트 실험에서 지수 백오프의 "가장 붐비는 10ms 구간"이 여전히 1000개인 이유는?\
  A: 같은 시각에 실패한 1000개가 같은 규칙으로 같은 100ms를 계산하기 때문이다.\
  간격은 길어져도 재시도 **시각**은 여전히 완전히 겹친다.

- Q: 지수 백오프가 줄이는 것과 못 하는 것은 각각 무엇인가?\
  A: 줄이는 것은 "얼마나 자주"(재시도 빈도)다.\
  못 하는 것은 "언제"를 흩뿌리는 것 — 동기화 자체는 깨지 못한다.

- Q: 몰림을 깨는 방법이 무작위 하나뿐인 이유는?\
  A: 몰림의 원인이 "모두가 같은 규칙"이기 때문이다.\
  결정적인 규칙은 무엇으로 바꿔도 같은 입력(같은 실패 시각)에 같은 출력(같은 재시도 시각)을 준다.\
  각자 다른 값을 쓰게 하는 방법은 각자 무작위를 뽑게 하는 것뿐이다.

- Q: FULL 지터와 EQUAL 지터 중 무엇이 맞는가 — 이것이 "무엇을 살지의 문제"라는 말의 뜻은?\
  A: FULL은 가장 잘 흩어지지만 0ms(즉시 재시도)가 나올 수 있다.\
  EQUAL은 최소 간격(절반)을 보장하는 대신 덜 흩어진다(RetryStormTest 기준 500개 미만 vs FULL 200개 미만).\
  흩어짐을 살 것인가 최소 간격 보장을 살 것인가의 선택이지 한쪽이 옳은 것이 아니다.

- Q: 지터를 넣으면 총 대기 시간은 어떻게 되는가 — 흩어지는 대가로 느려지는가?\
  A: 느려지지 않는다.\
  FULL의 평균 대기는 backoff/2라 총 대기 시간이 오히려 짧다.\
  RetryStormTest가 흩어짐과 함께 이것까지 확인한다 — 지터는 공짜에 가깝다.

#### 8. 오버플로가 정확히 막으려던 것을 만든다

- Q: 대기 시간 계산이 음수로 넘치면 sleep은 어떻게 동작하고, 그 결과는 무엇인가?\
  A: `Ticker.sleep` 은 0 이하면 즉시 반환한다.\
  그래서 음수 대기 = 대기 없음 = 전 클라이언트 즉시 재시도 = 재시도 폭풍이다.\
  백오프를 넣은 이유(폭풍 방지)를 백오프 계산의 버그가 정확히 뒤집는다.

- Q: 이 실패가 "조용히 최악으로 간다"는 말의 뜻은?\
  A: 예외도 로그도 없이 정상 동작처럼 보이면서 최악의 동작(즉시 폭풍)을 한다는 뜻이다.\
  크래시하는 버그보다 위험하다 — 터지기 전까지 아무도 모른다.

- Q: 상한 검사를 곱하기 전과 후 중 어디에 둬야 하고, 왜 그것이 갈림길인가?\
  A: 곱하기 **전**이다.\
  곱한 뒤에는 이미 음수로 뒤집혀 있어 "상한보다 크면 상한" 비교가 통하지 않는다.\
  `shift >= 63 || base > (max >> shift)` 처럼 넘칠지 자체를 먼저 판정해야 한다.

#### 9. 시간 주입과 데드라인

- Q: `Ticker.nowMillis()`가 보장하는 것은 무엇뿐이고, 원점이 임의라는 것은 무슨 뜻인가?\
  A: 단조 증가(되돌아가지 않음)만 보장한다.\
  System.nanoTime 기반이라 0의 위치가 의미 없고 음수일 수도 있다 — 벽시계 시각이 아니다.\
  따라서 두 시각의 **차이**만 의미가 있고 절대값 계산에 쓰면 안 된다.

> **단조 증가(monotonic)** — 되돌아가지 않고 늘 커지기만 하는 성질.\
> 예: `Ticker.nowMillis` 가 보장하는 전부라, 두 시각의 차이만 의미가 있다.

- Q: 데드라인 계산 식을 어느 방향으로 쓰느냐에 따라 결과가 갈리는 이유는?\
  A: `now + delay` 방향은 덧셈 오버플로가 가능하고, `deadline - now` 방향은 안전하기 때문이다.\
  원점이 임의라 now가 얼마든지 클 수 있다는 전제에서만 이 차이가 보인다.

- Q: `Long.MAX_VALUE`를 "데드라인 없음"으로 그냥 계산에 쓰면 왜 데드라인이 없는데도 포기하는가?\
  A: `MAX_VALUE - now` 가 now만큼 깎인 유한한 값이 되기 때문이다.\
  now가 크면 남은 시간이 delay보다 작게 나올 수 있어, 없어야 할 데드라인에 걸린다.\
  센티널은 비교로만 쓰고 계산에 넣지 않는다.

- Q: 시도 3번이면 대기는 왜 2번인가?\
  A: 대기는 "다음 시도"가 있을 때만 의미가 있기 때문이다.\
  3번째(마지막) 실패 뒤에는 다음 시도가 없으므로 기다릴 이유가 없다 — 자면 호출자 지연만 는다.

- Q: 남은 시간보다 긴 백오프를 자면 누가 무엇을 붙들고 있게 되는가?\
  A: 호출자는 3초 타임아웃으로 이미 떠났는데 우리는 5초를 잔다.\
  그 5초 동안 아무도 결과를 기다리지 않는 작업이 스레드와 커넥션을 붙들고 있다.\
  그래서 남은 시간 ≤ 다음 대기면 자지 않고 포기한다(abandonedByDeadline).

- Q: Thread.sleep을 코드에 직접 박으면 테스트에 무슨 일이 생기는가?\
  A: 재시도 5번짜리 테스트 하나가 실제로 30초를 기다린다 — 아무도 안 돌리게 된다.\
  그리고 실시간에 의존하니 CI에서 흔들린다(flaky).\
  Ticker를 주입하면 테스트는 FakeTicker로 시간을 감아 즉시 끝난다.

> **플레이키(flaky)** — 코드는 그대로인데 돌릴 때마다 결과가 달라지는 테스트.\
> 예: 시간 의존이 주범이라, 가짜 시계를 주입하면 사라진다.

- Q: "결정적으로 만들 수 없는 것은 검증할 수 없다"가 이 챕터에서 적용된 두 군데는 어디인가?\
  A: 시간(Ticker 주입 — 테스트는 가짜 시계)과 무작위(JitteredBackoffRetry의 seed 주입 — 테스트는 고정 난수열).\
  자료구조 12번 스킵 리스트의 Random 주입과 같은 원리다.

#### 10. 정책과 예산의 경계

- Q: 재시도 3번짜리 정책은 무엇을 묶고, 무엇을 못 묶는가?\
  A: 한 요청이 만드는 재시도를 3번으로 묶는다.\
  전체 요청 수 × 3이라는 **총량**은 못 묶는다 — 정책은 요청 하나의 시야만 갖는다.

- Q: 상대가 완전히 죽으면 전체 부하는 왜 3배가 되는가?\
  A: 전면 장애면 모든 요청이 실패하고, 모든 요청이 각자 3번씩 시도하기 때문이다.\
  회복하려는 서버에 평소의 3배가 꽂힌다 — 정책이 요청별로는 올바르게 동작한 결과다.

- Q: 예산을 "전체 대비 10%"로 보는 설계가 정상일 때와 장애일 때 각각 어떻게 동작하는가?\
  A: 정상일 때는 재시도가 드물어 예산이 남아돌아 제약이 전혀 없다.\
  전면 장애 때만 재시도 총량이 트래픽의 10%에서 잘린다.\
  제약이 필요한 시점에만 발동한다 — 그게 정확히 설계 의도다.

- Q: `tokens += 0.1`을 100번 하면 왜 10.0이 아닌가?\
  A: 0.1이 2진 부동소수점으로 정확히 표현되지 않기 때문이다.\
  매번 아주 작은 오차가 쌓여 9.999999999999998 같은 값이 된다.

- Q: 그 오차가 "100 요청에 10번"을 어떻게 9번으로 만드는가?\
  A: 10번째 재시도 시점에 토큰이 10.0이 아니라 9.999…라 "1개 이상" 검사에서 10번째가 거절된다.\
  약속한 10%가 9%가 되고, 사라진 1번을 코드 어디에서도 설명할 수 없다.\
  그래서 1/1000 단위 정수(tokensScaled)로 센다.

- Q: 실무에서 이 모양(재시도 예산)을 쓰는 시스템 셋은 무엇인가?\
  A: 넷플릭스 Hystrix, 구글 SRE 책(의 retry budget), gRPC의 retry throttling.\
  전부 "전체 대비 비율 상한 + 정상 시 무제약" 모양이다.

#### 11. 다음 챕터로의 다리

- Q: 재시도와 서킷 브레이커는 실패를 대하는 태도가 어떻게 다른가?\
  A: 재시도는 "다시 하면 될지도 모른다"에 걸고 기다렸다 다시 한다.\
  서킷 브레이커는 "상대가 확실히 죽었다"고 판단되면 **재시도를 아예 하지 않기로 결정**한다.\
  빨리 실패하고 회복을 기다리는 쪽이다.

- Q: 상대가 확실히 죽었을 때 재시도가 낭비인 이유는?\
  A: 성공 확률이 0에 가까운 요청에 대기 시간·스레드·커넥션·상대 부하를 계속 쓰기 때문이다.\
  그 자원이면 즉시 실패를 돌려주고 상대에게 회복할 틈을 주는 편이 낫다.

- Q: 이 챕터의 Ticker가 02-circuit-breaker에서 맡는 역할은 무엇인가?\
  A: 상태 전이의 축이 된다.\
  OPEN 상태에서 "일정 시간이 지나면 HALF_OPEN으로" 같은 전이가 전부 시간 위에 서 있고, 그 시간을 Ticker로 주입해야 전이를 결정적으로 테스트할 수 있다.
