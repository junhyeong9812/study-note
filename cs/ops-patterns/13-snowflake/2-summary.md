# ops-patterns/13-snowflake — 정리 (힌트)

## 해결하는 문제

여러 대가 각자 id를 만들어야 하는데, 겹치면 안 되고 인덱스에도 잘 꽂혀야 한다.\
"조율 없이"와 "순서 있게"를 한 번에 주는 장치가 없으면 둘 중 하나를 포기해야 한다.

```text
                조율          순서
DB auto inc     필요(병목)     있음         샤드마다 따로 1부터 세면 겹친다 (간격·오프셋·구간 배정이 따로 필요)
UUID v4(무작위) 불필요         없음         인덱스 여기저기에 꽂힌다 (원본 측정: 1000개 중 앞보다 작은 것 496개 — 분할 횟수는 아님)
스노우플레이크  불필요         대체로       노드 사이의 실제 발급 순서는 보장 못 한다 (같은 밀리초 + 시계 오차)
```

쉬운 예: 전국 지점의 영수증 번호를 "날짜-지점-순번"으로 만들면 본사에 물어보지 않아도 절대 안 겹치고, 번호만 봐도 언제 어디서 발행됐는지 안다.\
똑같은 구조다: 시각(41비트) | 노드(10비트) | 일련번호(12비트)를 한 long에 붙인다. 앞이 시각이라 대체로 증가하고, 노드 번호가 달라 조율 없이 안 겹친다.\
실무 예: 주문·게시글·메시지 id, 샤딩된 DB의 기본 키, 트위터·디스코드·인스타그램의 id.

### 한눈에 — 쉽게 말하면
**스노우플레이크 = 날짜+지점번호+순번으로 만든 영수증 번호.**

- 전국 지점이 있는 가게에서 영수증 번호를 "20260914-지점7-0031"처럼 만들면, 본사에 물어보지 않아도(조율 없이) **절대 안 겹치고**, 번호만 봐도 언제 어디서 발행됐는지 안다.

> **스노우플레이크(Snowflake)** — 시각+노드+일련번호를 한 64비트 정수에 붙이는 분산 id 발급 구조. 트위터가 원조.\
> 예: "20260914-지점7-0031" 처럼 날짜+지점+순번을 이어 붙인 꼴이다.

- 서버 세계도 똑같은 구조다.\
  여러 대가 **조율 없이** 겹치지 않는 번호(id)를 만들어야 한다.

  > **id(식별자)** — 주문·글·사용자 하나하나에 붙는 고유 번호.\
  > 예: 영수증 번호 "20260914-지점7-0031" 처럼 하나하나에 붙는다.

- 기존 방법의 문제:

```text
DB auto increment   한 곳을 거쳐야 한다 -> 병목 + 단일 장애점. 샤딩하면 못 쓴다
UUID(무작위)        조율은 필요 없다 -> 그런데 순서가 없다
```

  > **샤딩(sharding)** — DB를 여러 조각으로 나눠 두는 것.\
  > 조각마다 1부터 세면 번호가 겹친다.\
  > 예: 그래서 샤딩한 DB 에서는 auto increment 를 못 쓴다.

> ⚠ 정정(2026-09-28): "샤딩하면 auto increment를 못 쓴다"는 과한 일반화다 — 각 샤드가 독립적으로 1부터 세면 겹칠 뿐, 샤드별 증가 간격·오프셋(MySQL `auto_increment_increment`/`auto_increment_offset`), 번호 구간 배정, (샤드 ID, 로컬 번호) 복합 키로 쓸 수 있다. 다만 전역 유일성을 위해 별도 배정 전략이 필요하다(MySQL 레퍼런스 매뉴얼 복제 옵션).

- UUID의 "순서 없음"이 실무에서 제일 아프다 — 인덱스에 무작위로 꽂혀 B-트리 페이지가 계속 쪼개진다.\
  측정: 무작위 id 1,000개 중 앞의 것보다 작은 것 **496개**, 스노우플레이크는 **0개**.

> **UUID** — 조율 없이 만드는 무작위(에 가까운) 식별자. 겹치진 않지만 순서가 없다.\
> 예: 무작위 id 1,000개 중 앞의 것보다 작은 것이 496개다.

실무 예: 트위터 Snowflake(원조), 인스타그램/디스코드의 id, MongoDB ObjectId(유사 구조).

## 동작·원리

### 전체 흐름
```text
한 long(64비트)에 셋을 붙인다:

  63       22        12        0
  |  시각   |  노드   | 일련번호 |
     41비트   10비트    12비트

시각 41비트     기준 시각(epoch)부터 약 69년
노드 10비트     1024대까지
일련번호 12비트  한 밀리초에 4096개. 넘치면 다음 밀리초를 기다린다
맨 앞 1비트     비워둔다. 쓰면 음수 id — 정렬·비교가 전부 어긋난다

앞이 시각이라 "대체로 증가", 노드 번호가 달라 "조율 없이 안 겹침"
시계가 뒤로 가면 -> 던진다 (ClockWentBackwardsException)
```

### 동작 — nextId (번호 하나 만들기)
**언제 쓰나**: 여러 대에서 초당 수만 건씩 id가 필요하고, DB 한 곳을 거치기 싫을 때.

전 상태 — 노드 7, 같은 밀리초에 이미 2개를 만들었다:

```text
lastTimestamp = T, sequence = 1
지금 시각 now = T (같은 밀리초)
```

단계 (그림 해설 — 한 단계 한 문장):

- 지금이 마지막으로 본 시각보다 **앞이면** 던진다(시계가 뒤로 갔다 — 아래 절).
- 같은 밀리초면 일련번호를 +1 한다.
- 일련번호가 한 바퀴 돌면(4096개 소진) **다음 밀리초까지 기다린다** — 안 기다리면 그 밀리초의 id가 통째로 다시 나온다.\
  기다리는 것이 유일한 방법.

> **일련번호(sequence)** — 같은 밀리초 안에서 0부터 세는 번호. 12비트 = 4096개.\
> 예: 4096개를 다 쓰면 0으로 되감기고, 그때 다음 밀리초를 기다린다.

- 밀리초가 바뀌었으면 일련번호를 0으로 되돌린다 — 안 되돌리면 쓸데없이 기다리고, id에서 "이 밀리초의 몇 번째"를 읽을 수 없게 된다.
- 기준 시각부터의 경과가 41비트를 넘으면 던진다 — 안 막으면 시각이 노드 자리를 침범해 **다른 노드의 id와 겹치기 시작**한다(약 69년 뒤 — 단 기준 시각을 잘못 잡으면 당장).

> **epoch(기준 시각)** — 시각 41비트를 세기 시작하는 기준점.\
> 예: 잘못 잡으면 69년 뒤가 아니라 당장 41비트를 넘긴다.

- 시각·노드·일련번호를 시프트해 붙인다: `(elapsed << 22) | (node << 12) | sequence`.

후 상태:

```text
id = [ T-epoch | 7 | 2 ]   -> timestampOf/nodeOf/sequenceOf 로 도로 꺼낼 수 있다
                              "언제 어느 노드에서 만들었나"가 id 안에 있다 (사고 조사에 크다)
```

**비용/트레이드오프**: 한도는 밀리초당 노드당 4096개.\
`waitedForNextMillis`(기다린 횟수)가 크면 한도에 닿은 것 — 안 세면 "id 발급이 가끔 느리다"로만 나타난다.\
측정: 10만 개 발급에 24번 이상 기다림.

### 동작 — 시계가 뒤로 가면 (실패 시나리오)
**언제 생기나**: NTP 보정, 윤초, 가상 머신 이전, 관리자의 date 명령 — **실제로 일어난다.**\
`System.currentTimeMillis`는 뒤로 갈 수 있다는 것이 계약이다.

> **NTP** — 서버들의 시계를 맞추는 프로토콜.\
> 맞추는 과정에서 시각을 **뒤로** 되돌리기도 한다.\
> 예: 보정하면서 시각을 5초 되돌리면 그때부터 시계 역행이다.

전 상태:

```text
lastTimestamp = T          (여기까지 id를 만들었다)
NTP가 시각을 5초 되돌렸다   now = T - 5000
```

단계 — 세 가지 선택지가 다 나쁘다:

```text
뒤로 간 시각으로 만든다   이미 만든 id와 겹칠 수 있다   <- 제일 나쁘다
기다린다                얼마나 기다릴지 모른다. 몇 분일 수도
마지막 시각을 쓴다        그 밀리초의 일련번호가 금방 바닥난다
```

- 겹친 id는 **조용하다** — "가끔 주문이 덮어써진다"로 나타나고 원인 찾는 데 몇 주가 걸린다.

> **시계 역행(clock going backwards)** — 시각이 마지막으로 본 값보다 작아지는 것. 이 구조의 대표 사고 — 답은 "던진다".\
> 예: NTP가 시각을 5초 되돌리면 `now = T - 5000` 이 된다.

- id를 못 만드는 것은 **시끄럽다** — 즉시 예외로 드러난다.\
  그래서 던진다.
- 영구히 죽는 것은 아니다 — 시각이 마지막으로 본 값을 넘어서면 다시 만든다.\
  같은 밀리초로 돌아오는 것은 뒤로 간 게 아니고, 일련번호로 처리한다.

후 상태:

```text
ClockWentBackwardsException("시계가 뒤로 갔다: 마지막 T -> 지금 T-5000 (5000ms)")
시계가 따라잡으면 -> 정상 발급 재개
```

### 동작 — "대체로 증가"의 한계
**언제 문제 되나**: id 순서를 "정확한 발생 순서"로 믿으려 할 때.

```text
같은 밀리초 안:
  먼저 만든 것(노드 900)  ->  더 크다
  나중 만든 것(노드 1)    ->  더 작다     <- 노드 번호가 순서를 정해버린다

밀리초가 다르면:  시각이 이긴다 (늦게 만든 것이 항상 크다)
한 노드 안에서는: 늘 증가 (뒤집힘 0)
```

- 같은 밀리초 안의 순서에는 **근거가 없다**.\
  완전한 순서가 필요하면 이 구조로는 안 된다 — 14번 논리 시계가 그 이야기.

**비용/트레이드오프**: 벽시계를 앞에 붙여 얻은 "대체로 정렬"이 인덱스 삽입 성능을 지키지만, 노드 간 순서 보장은 포기한 것이다.

## 쓰이는 자료구조·알고리즘

- **비트 필드 패킹(시프트·OR)** — `(elapsed << 22) | (node << 12) | seq`로 붙이고 시프트·마스크로 도로 꺼낸다. [algorithm/29-bit-manipulation](../../algorithm/29-bit-manipulation/2-summary.md). 맨 앞 부호 비트는 비운다.
- **B-트리 순차 삽입** — 대체로 증가하는 키는 삽입 위치가 인덱스 오른쪽 끝 부근에 모여 지역성과 페이지 활용에 유리하다. 페이지가 차면 분할은 여전히 일어나지만, 중간에 흩어져 반쯤 빈 페이지가 생기는 일이 줄어든다(여러 노드의 id는 완전한 단조 증가가 아니다). [data-structure/15-b-tree](../../data-structure/15-b-tree/2-summary.md)의 "정렬된 삽입이 유리하다"가 이 구조의 존재 이유다.
- **단조 시계 검사** — 마지막으로 본 시각보다 작으면 던진다. [04-rate-limiter](../04-rate-limiter/2-summary.md)의 `now()`가 같은 사고를 "마지막 시각을 준다"로 다르게 막는다.
- **밀리초 안 카운터** — 12비트 일련번호. 바닥나면 다음 밀리초를 기다린다(스핀).
- **노드 번호 배정** — 이 노트는 생성자 인자로 받지만, 실무에서는 [11-distributed-lock](../11-distributed-lock/2-summary.md)의 리스처럼 중앙에서 빌려 온다.
- 실제 시스템 — Twitter Snowflake(원조, 2010), Discord·Instagram의 변형(비트 배분이 다르다 — Discord 공식 문서: 시각 42·worker 5·process 5·increment 12비트, Instagram 엔지니어링 블로그 "Sharding & IDs at Instagram"(2012): 시각 41·샤드 13·순번 10비트), MongoDB `ObjectId`(초 단위 시각 4바이트 + 프로세스별 무작위 5바이트 + 카운터 3바이트 — MongoDB ObjectId 명세), UUIDv7(RFC 9562)·ULID — 시각을 앞에 두고 노드 조각을 무작위로 대신한 것(UUIDv7은 일부 비트를 카운터로, ULID도 단조 증가 변형을 쓸 수 있다).

## 적용 — 풀어나가는 법

### 문제 — 이 챕터가 시키는 것
DB auto increment 는 한 곳을 거쳐야 해서 병목·단일 장애점이고 샤딩하면 못 쓴다.\
UUID 는 조율이 필요 없는 대신 순서가 없다 — 인덱스에 무작위로 꽂혀 B-트리 페이지가 계속 쪼개진다.\
**여러 대가 조율 없이, 겹치지 않으면서, 대체로 증가하는 번호를 만드는 발급기(Snowflake)를 시각|노드|일련번호 세 조각으로 구현하라**는 챕터다.

> **auto increment** — DB가 1, 2, 3... 순서로 붙여주는 번호. 한 곳을 거쳐야 해서 병목·단일 장애점.\
> 예: 샤딩하면 조각마다 1부터 세게 되어 못 쓴다.

### 측정·검증 (원본 테스트 기준)
- 한 노드 10만 개, 10노드 × 1000라운드(같은 밀리초 동시 발급), 16스레드 × 500개 — 전부 **겹침 0**.
- 무작위 1000개 중 뒤집힘 496개 vs 스노우플레이크 0개.
- 테스트는 시계를 주입한다(FakeTicker) — 특히 **뒤로 감을 수 있어야** 한다.\
  진짜 시계로는 그 상황을 만들 수 없다.

> **FakeTicker(가짜 시계)** — 테스트용 주입 시계. 앞으로 감기(advance)뿐 아니라 되감기(rewind)가 되어야 이 챕터의 사고를 재현한다.\
> 예: 진짜 시계로는 시각이 뒤로 가는 상황을 만들 수 없다.

- 노드 범위(0~1023) 검사: 안 하면 노드 번호가 시각 자리를 침범 — id가 미래에서 온 것처럼 보이고 아주 늦게 발견된다.\
  기준 시각이 미래면 즉시 던짐(배포 직후 드러나서 다행인 실수).
- 변종 11개 중 10개가 잡혔다.\
  살아남은 하나는 `timestampOf`의 부호 없는 시프트(`>>>`)를 부호 있는 것(`>>`)으로 바꾼 것 — id가 늘 양수라 **결함이 아니었다**.\
  그래도 부호 없는 쪽을 남겼다.\
  누군가 시각 비트를 늘리면 그 순간 갈리는데, **어떤 테스트로도 이 선택은 검증할 수 없다.**

## 장애 시나리오와 대처

위 「동작」절이 다루는 것(시계 역행·일련번호 고갈·자리 침범·대체로 증가의 한계) 말고, 운영에서 따로 보이는 장애들이다.

**1. 두 인스턴스가 같은 노드 번호를 받는다**

- 현상: 오토스케일로 뜬 새 인스턴스가 기존 인스턴스와 같은 노드 번호로 id를 만든다. 가끔 주문이 덮어써진다.
- 보이는 형태: 기본 키 충돌(`duplicate key`)이면 시끄럽고, upsert라면 조용히 남의 행을 덮는다. 충돌한 두 id는 모든 필드가 같으므로 id만 봐서는 원인을 못 가린다 — 발급 로그에 남긴 인스턴스 식별자로 "같은 노드 번호를 쓴 인스턴스가 둘"인지 확인한다(재시작 후 같은 밀리초 재발급·시계 역행도 같은 모양을 만든다).
- 원인: 노드 번호가 설정 파일·환경 변수의 정적 값이거나, 재시작 때 무작위로 고른다. "노드 번호가 달라 안 겹친다"는 전제가 배정 단계에서 깨졌다.
- 대처: 노드 번호를 중앙 저장소(etcd·ZooKeeper·DB)에서 **리스로** 빌려 온다 — 기동 시 빈 번호를 잡고 심장 박동으로 유지, 죽으면 회수. 같은 번호를 둘이 잡을 수 없게 잡기는 원자 연산으로(11의 규칙 그대로).\
  리스만으로는 부족하다 — 멈췄다 깨어난 옛 인스턴스는 리스를 잃은 줄 모르고 계속 발급한다. 리스 갱신에 실패하면 발급을 즉시 멈추게 하고, 회수한 번호는 옛 주인의 마지막 발급 시각이 지난 뒤에 재사용한다(필요하면 세대 번호나 마지막 발급 시각을 영속화).

**2. JavaScript에서 id 끝자리가 깨진다**

- 현상: 프론트가 보낸 id로 조회하면 "없는 주문"이다. 서버 로그의 id와 브라우저의 id가 끝 두세 자리만 다르다.
- 보이는 형태: `1234567890123456789`가 `1234567890123456800`으로 바뀌어 온다.
- 원인: JSON 숫자를 JavaScript `Number`(IEEE 754 배정밀도)로 읽으면 안전한 정수 상한이 `Number.MAX_SAFE_INTEGER` = 2^53−1이다. 64비트 id는 그 범위를 넘어, 서로 다른 정수가 같은 `Number`로 반올림될 수 있다.
  - *배정밀도(double)*: 64비트 부동소수점. 모든 정수를 빠짐없이 정확히 표현하는 구간은 ±(2^53−1)(약 9천조)까지다. 그보다 큰 정수는 일부만 표현된다.
- 대처: id는 JSON에서 **문자열**로 직렬화한다. 트위터가 `id`와 별도로 `id_str`을 둔 이유가 이것이다.

**3. id가 사업 정보를 흘린다**

- 현상: 경쟁사가 하루 주문량을 안다. 또는 id를 하나씩 바꿔 가며 남의 주문을 열어 본다.
- 보이는 형태: 주문 id에서 `timestampOf`·`nodeOf`로 발급 시각과 노드가 드러난다. 표본을 많이 모으면(밀리초별 `sequenceOf` 분포 등) 추가 가정을 얹어 활동량을 추정할 수 있다. 순차에 가까운 id가 URL에 그대로 있다.\
  다만 일련번호는 밀리초마다 0으로 돌아가고 노드별로 따로 세므로(impl `nextId`), id 두 개의 차이로 하루 발급량이 바로 계산되지는 않는다.
- 원인: id 안에 시각·노드·순번이 들어 있다는 장점이 밖으로 나가면 단점이 된다.
- 대처: 외부 노출용 id는 따로 둔다(무작위 공개 id 또는 암호화한 값). 스노우플레이크 id는 내부 키와 인덱스에만 쓴다. 노출된 id로 접근할 때는 권한 검사를 반드시 한다.

## 핵심 문장

- 스노우플레이크는 **시각|노드|일련번호**를 한 long에 붙여, 조율 없이 안 겹치고 대체로 증가하는 id를 만든다.
- "대체로"의 뜻: 밀리초가 다르면 시각이 순서를 정하지만, 같은 밀리초 안에서는 노드 번호가 정한다 — 그 순서에는 근거가 없다.
- 일련번호가 바닥나면 기다리는 것이 유일한 방법이고, 시계가 뒤로 가면 던지는 것이 유일하게 안전한 선택이다 — **겹친 id는 조용하고, 못 만드는 것은 시끄럽다.**
- 무작위 id는 절반이 뒤집혀 인덱스를 흩뜨리고(496/1000), 스노우플레이크는 한 노드 안에서 뒤집힘 0이다.
- id 안에 시각과 노드가 있어서 번호만 보고 "언제 어디서"를 안다 — 사고 조사에서 이 정보가 아주 크다.

### 용어 풀이
- **스노우플레이크(Snowflake)**: 시각+노드+일련번호를 한 64비트 정수에 붙이는 분산 id 발급 구조.\
  트위터가 원조.
- **id(식별자)**: 데이터 하나하나에 붙는 고유 번호.
- **auto increment**: DB가 1, 2, 3... 순서로 붙여주는 번호.\
  한 곳을 거쳐야 해서 병목·단일 장애점.
- **UUID**: 조율 없이 만드는 무작위(에 가까운) 식별자.\
  겹치진 않지만 순서가 없다.
- **샤딩(sharding)**: DB를 여러 조각으로 나누는 것.\
  auto increment가 못 쓰이게 되는 이유.
- **epoch(기준 시각)**: 시각 41비트를 세기 시작하는 기준점.\
  잘못 잡으면 69년 뒤가 아니라 당장 사고가 난다.
- **일련번호(sequence)**: 같은 밀리초 안에서 0부터 세는 번호.\
  12비트 = 4096개.
- **비트 시프트(shift, `<<` `>>>`)**: 비트를 왼쪽/오른쪽으로 미는 연산.\
  세 조각을 붙이고 도로 꺼낼 때 쓴다.\
  `>>>`는 부호 비트까지 밀어내는 "부호 없는" 버전.
- **NTP**: 서버 시계를 맞추는 프로토콜.\
  시각을 뒤로 되돌릴 수 있다.
- **시계 역행(clock going backwards)**: 시각이 마지막으로 본 값보다 작아지는 것.\
  이 구조의 대표 사고 — 답은 "던진다".
- **B-트리 페이지 분할(page split)**: 정렬된 인덱스 중간에 끼워 넣을 때 페이지가 쪼개지는 것.\
  무작위 id가 이걸 계속 일으킨다.
- **단일 장애점(single point of failure)**: 거기가 죽으면 전체가 멈추는 한 곳.
- **FakeTicker(가짜 시계)**: 테스트용 주입 시계.\
  앞으로 감기(advance)뿐 아니라 되감기(rewind)가 되어야 이 챕터의 사고를 재현한다.
