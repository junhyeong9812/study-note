### A. 문제 (RandomIdGenerator · Snowflake 의 TODO)

#### 1. TODO 1 — RandomIdGenerator.nextId

정답 코드 (impl/RandomIdGenerator.java):

```java
generated++;
// 63비트. 맨 앞을 비워 음수가 안 나오게 한다.
return random.nextLong() >>> 1;
```

- 한 줄: `random.nextLong() >>> 1` — **부호 없는 오른쪽 시프트 1칸**이 맨 앞 비트를 0으로 만든다(63비트가 남는다).

> **비트 시프트(shift, `<<` `>>>`)** — 비트를 왼쪽/오른쪽으로 미는 연산. `>>>`는 부호 비트까지 밀어내는 "부호 없는" 버전.\
> 예: `random.nextLong() >>> 1` 은 맨 앞 비트를 0으로 만들어 63비트를 남긴다.

- 음수 id 가 어긋내는 것: **정렬과 비교** — id 를 정렬하면 음수가 전부 앞으로 가고, "나중 id 가 더 크다" 같은 성질이 전부 깨진다.\
  `Random.nextLong` 은 **절반이 음수**다.
- 잃는 것 셋(javadoc 원문): ① **id 로 시간 순서를 알 수 없다** ② **인덱스에 무작위로 꽂혀 B-트리 페이지가 계속 쪼개진다** ③ **범위 조회를 못 한다**("어제 만든 것" 같은 질의).

> **B-트리 페이지 분할(page split)** — 정렬된 인덱스 중간에 끼워 넣을 때 페이지가 쪼개지는 것.\
> 예: 무작위 id 는 인덱스에 무작위로 꽂혀 이것을 계속 일으킨다.

- 제일 아픈 것: **2번**.\
  15번 B-트리에서 "정렬된 삽입이 유리하다"고 했던 것의 정반대다 — 무작위 삽입은 페이지 분할을 계속 일으킨다.\
  측정: 무작위 1,000개 중 **앞의 것보다 작은 것이 496개**(스노우플레이크는 0개).

> **스노우플레이크(Snowflake)** — 시각+노드+일련번호를 한 64비트 정수에 붙이는 분산 id 발급 구조. 트위터가 원조.\
> 예: 무작위 1,000개 중 앞의 것보다 작은 것이 496개일 때 스노우플레이크는 0개다.

- seed 를 받는 이유: **무작위를 쓰면 seed 를 받아야 실패를 재현할 수 있다**(12번 스킵 리스트에서 정한 규칙).\
  seed 가 없으면 깨진 케이스를 다시 만들 수 없다.

#### 2. TODO 2 — Snowflake.nextId

정답 코드 (impl/Snowflake.java):

```java
long now = ticker.nowMillis();

if (now < lastTimestamp) {
    // 시계가 뒤로 갔다. 겹친 id 를 만드느니 못 만드는 쪽이 낫다.
    throw new ClockWentBackwardsException(lastTimestamp, now);
}

if (now == lastTimestamp) {
    sequence = (sequence + 1) & MAX_SEQUENCE;
    if (sequence == 0) {
        // 한 바퀴 돌았다. 다음 밀리초를 기다린다.
        now = waitForNextMillis(lastTimestamp);
        waitedForNextMillis++;
    }
} else {
    // 밀리초가 바뀌었다. 0 부터 다시 센다.
    sequence = 0;
}

lastTimestamp = now;
generated++;

long elapsed = now - epoch;
if (elapsed < 0) {
    throw new IllegalStateException("지금이 기준 시각보다 앞이다. 기준 시각을 잘못 잡았다: ...");
}
if (elapsed >= (1L << TIMESTAMP_BITS)) {
    // 41비트를 넘겼다. 여기서 안 막으면 시각이 노드 자리를 침범한다.
    throw new IllegalStateException("기준 시각으로부터 41비트를 넘겼다. 이 발급기는 수명이 다했다");
}
return (elapsed << TIMESTAMP_SHIFT) | ((long) node << NODE_SHIFT) | sequence;
```

- 선택지 셋과 답: ① **뒤로 간 시각으로 만든다** — 이미 만든 id 와 겹칠 수 있다 ② **기다린다** — 얼마나 기다려야 할지 모른다(NTP 가 몇 분을 되돌릴 수도) ③ **마지막 시각을 쓴다** — 그 밀리초의 일련번호가 금방 바닥난다.\
  셋 다 나쁜데 ①이 제일 나쁘다: **겹친 id 는 조용하다** — "가끔 주문이 덮어써진다"로 나타나고 원인을 찾는 데 몇 주가 걸린다.\
  **id 를 못 만드는 것은 시끄럽다**(즉시 예외).\
  그래서 던진다.

> **시계 역행(clock going backwards)** — 시각이 마지막으로 본 값보다 작아지는 것. 이 구조의 대표 사고다.\
> 예: NTP 가 시각을 5초 되돌리면 이미 만든 id 와 겹칠 수 있어 던진다.

- 안 기다리면: 일련번호가 0으로 돌아가 **그 밀리초의 id 가 통째로 다시 나온다** — 시각도 노드도 일련번호도 같은 id 가 재발급된다.

> **일련번호(sequence)** — 같은 밀리초 안에서 0부터 세는 번호. 12비트 = 4096개.\
> 예: 4096개를 다 쓰면 한 바퀴 돌아 0이 되고, 그때 다음 밀리초를 기다린다.

- 한 바퀴 판정: `sequence = (sequence + 1) & MAX_SEQUENCE` 로 올린 뒤 **`sequence == 0`** 이면 한 바퀴 돈 것이다(마스크가 4096에서 0으로 되감는다).
- 안 되돌리면 손해 둘: ① **쓸데없이 기다리게 된다**(새 밀리초인데 일련번호가 이미 높아 금방 바닥난다) ② **id 를 보고 "이 밀리초의 몇 번째"를 알 수 없게 된다.**
- 41비트 초과: **시각이 노드 자리를 침범한다** → 그때부터 **다른 노드의 id 와 겹치기 시작**한다.\
  약 69년 뒤지만 **기준 시각(epoch)을 잘못 잡으면 당장** 난다 — 경과 시간은 `now - epoch` 이라 epoch 이 너무 과거면 처음부터 41비트를 넘는다.

> **epoch(기준 시각)** — 시각 41비트를 세기 시작하는 기준점.\
> 예: 잘못 잡으면 69년 뒤가 아니라 당장 41비트를 넘긴다.

- 합치는 식: `(elapsed << 22) | (node << 12) | sequence` — **시각이 맨 앞**이어야 큰 자리를 차지해서 숫자 크기가 곧 시간 순서가 된다(대체로 증가).\
  순서를 바꾸면 노드 번호가 순서를 지배한다.
- synchronized 인 이유: `lastTimestamp` 와 `sequence` 가 **공유 상태**라서다.\
  두 스레드가 동시에 들어오면 같은 일련번호를 받아 같은 id 가 나온다 — 테스트가 16스레드 × 500개로 겹침 0 을 확인한다.

> **공유 상태(shared state)** — 여러 스레드가 함께 읽고 쓰는 변수.\
> 예: `lastTimestamp` 와 `sequence` 가 그것이라, 안 막으면 두 스레드가 같은 일련번호를 받는다.

#### 3. TODO 3 — waitForNextMillis

정답 코드:

```java
long now = ticker.nowMillis();
while (now <= last) {
    try {
        ticker.sleep(1);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException("기다리다 끊겼다", e);
    }
    now = ticker.nowMillis();
}
return now;
```

- 조건: **`<=`** 다.\
  같으면 **아직 그 밀리초 안**이므로 더 기다려야 한다.
- 틀리면: `<` 로 쓰면 `now == last` 인 채로 빠져나오고, 호출한 쪽은 새 밀리초로 알고 **일련번호를 0 부터 다시 시작한다** → 같은 밀리초에서 같은 일련번호가 다시 나와 **id 가 겹친다.**
- 인터럽트: **인터럽트 플래그를 복원하고**(`Thread.currentThread().interrupt()`) **던진다.**\
  삼키면 상위가 중단 요청을 못 본다.

#### 4. TODO 4·5 — nodeOf / sequenceOf

정답 코드:

```java
public int nodeOf(long id) {
    return (int) ((id >>> NODE_SHIFT) & MAX_NODE);
}

public int sequenceOf(long id) {
    return (int) (id & MAX_SEQUENCE);
}
```

- 시프트만 하면 안 되는 이유: 노드 자리는 **가운데**라서 오른쪽으로 12칸 밀면 **위쪽의 시각 비트가 그대로 딸려온다.**\
  `& MAX_NODE`(하위 10비트 마스크)로 잘라내야 한다.
- 일련번호에 시프트가 없는 이유: **맨 아래 자리**라 이미 제자리에 있다 — 마스크만 하면 된다.
- `>>` 로 바꿔도 같은 이유: **맨 앞 비트를 안 쓰기 때문에 id 가 늘 양수**다.\
  양수에서는 부호 확장이 일어나지 않아 두 시프트가 구별되지 않는다.
- 그래도 `>>>` 를 남기는 이유: **누군가 시각 비트를 41 에서 늘리면 그 순간 갈리기 때문**이다.\
  지금은 어떤 테스트로도 이 선택을 검증할 수 없다 — 테스트가 못 잡는 것은 코드의 성질이 아니라 **지금 이 설계의 성질**이다(11번 블룸 필터에서 본 그 자리).

### B. 개념

#### 5. 왜 스노우플레이크인가

- auto increment 가 못 쓰이는 상황: **한 곳을 거쳐야 하므로 병목** · **단일 장애점**(거기가 죽으면 전체가 멈춘다) · **샤딩하면 못 쓴다**(조각마다 1부터 세면 겹친다).

> **단일 장애점(single point of failure)** — 거기가 죽으면 전체가 멈추는 한 곳.\
> 예: id 를 DB 한 곳에서만 받으면 그 DB 가 죽을 때 전체가 멈춘다.

- UUID 의 순서 없음: **인덱스에 무작위로 꽂혀 B-트리 페이지가 계속 쪼개진다.**

> **UUID** — 조율 없이 만드는 무작위(에 가까운) 식별자. 겹치진 않지만 순서가 없다.\
> 예: 조율은 필요 없는 대신 인덱스에 무작위로 꽂혀 페이지가 계속 쪼개진다.

- 뒤집힘 수: 무작위 **496 / 1,000**, 스노우플레이크 **0**.
- 비트 배분: 시각 41비트 = 기준 시각부터 **약 69년** / 노드 10비트 = **1024대** / 일련번호 12비트 = **한 밀리초에 4096개**.
- 맨 앞 비트: **부호 때문**이다.\
  쓰면 음수 id 가 나오고 정렬과 비교가 전부 어긋난다.

#### 6. "대체로 증가"의 정확한 뜻

- 같은 밀리초 안: **노드 번호가 순서를 정한다**(시각 비트가 같으니 그 다음 자리가 크기를 결정).
- 노드 900 이 먼저, 노드 1 이 나중이면: **먼저 만든 노드 900 쪽이 더 크다** — 순서가 뒤집힌다.
- 한 노드 안: **늘 증가한다**(뒤집힘 0) — 같은 밀리초면 일련번호가 올라가고 밀리초가 바뀌면 시각이 올라간다.
- 완전한 순서가 필요하면: **14번 논리 시계** — 벽시계 없이 순서를 만든다.

#### 7. 일련번호와 한도

- 한도: **밀리초당 노드당 4096개.**\
  닿으면 **다음 밀리초까지 기다린다**(기다리는 것이 유일한 방법 — 안 기다리면 겹친다).
- 세는 이유: **기다린 횟수가 발급 속도의 자**다.\
  이 값이 크면 4096 한도에 닿은 것이고, 노드를 늘리거나 비트 배분을 다시 봐야 한다는 신호다.
- 안 세면: **"id 발급이 가끔 느리다"로만 나타난다** — 원인이 한도라는 것을 알 방법이 없다.

#### 8. 비트 자리 침범

- 노드 범위 미검사: 1023 을 넘는 노드 번호가 **시각 자리를 침범한다** → id 가 **미래에서 온 것처럼 보인다.**\
  늦게 발견되는 이유는 id 가 여전히 유일하고 정렬도 되는 것처럼 보이기 때문이다 — 시각을 꺼내보기 전에는 아무 데서도 안 걸린다.
- 41비트 초과: **노드 자리를 침범한다** → 그때부터 **다른 노드의 id 와 겹친다.**
- epoch 이 미래면: 경과가 음수가 되어 **즉시 던진다.**\
  배포 직후 드러나므로 다행인 실수다 — 조용히 잘못된 id 를 뿌리는 것보다 낫다.

#### 9. 검증할 수 없는 선택

- id 만 보고 아는 것: **언제**(시각) **어느 노드에서**(노드 번호) 만들었나.\
  **사고 조사에서 이 정보가 아주 크다** — 무작위 id 에는 없다.
- 살아남은 변종: `timestampOf` 의 **`>>>` 를 `>>` 로 바꾼 것.**\
  맨 앞 비트를 안 써서 id 가 늘 양수이므로 두 시프트의 결과가 같다 — **결함이 아니었다.**
- 성질의 귀속: **설계의 성질**이다.\
  지금 설계(맨 앞 비트를 비움)가 두 시프트를 구별 불가능하게 만든 것이지 테스트가 부실한 것이 아니다.
- 시계 주입: 진짜 시계로는 **뒤로 가는 상황을 만들 수 없다.**\
  그래서 FakeTicker 에 **앞으로 감기뿐 아니라 되감기**가 있어야 한다.

> **FakeTicker(가짜 시계)** — 테스트용 주입 시계. 앞으로 감기(advance)뿐 아니라 되감기(rewind)가 되어야 한다.\
> 예: 진짜 시계로는 시각이 뒤로 가는 상황을 만들 수 없다.

#### 10. 연결

- 12번과의 차이: 임기 번호는 **한 곳(합의 과정)에서 나왔다**.\
  여기서는 **조율 없이** 각자 만든다 — 그 대가로 완전한 순서를 포기했다.
- 14번으로: 여기서 **"대체로 증가"에서 멈춘 것**을 논리 시계는 **벽시계 없이** 해결한다 — 시계를 안 믿는 대신 사건 간 인과로 순서를 세운다.
- MongoDB ObjectId: **시각 + 머신/프로세스 식별 + 카운터**를 이어 붙인 12바이트 — 조각의 종류와 "시각을 앞에 둔다"는 배치가 같은 사상이다.\
  (원본 서머리의 유사 사례 언급 — 바이트 구성 세부는 내 추론)
