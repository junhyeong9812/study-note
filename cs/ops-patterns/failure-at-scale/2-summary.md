# ops-patterns/failure-at-scale — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/10-failure-at-scale/README.md` · 이관일 2026-09-16.\
> 본문 「양상 1~4」·「어느 양상이 실제로 걸리는지 세라」는 **원고**를 고쳐 쓴 것이다(논지·문체 유지).\
> 특정 프로젝트의 부하 수치·설계 문서 번호(ADR/BR/QS 등)는 「현장에서 만나는 상황」으로 **일반화**했다.\
> 「한눈에」·「전체 흐름」의 그림은 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**한 줄 논지: 규모가 커지면 시스템이 "느려지는" 게 아니라 "실패하는 방식"이 바뀐다.**\
그래서 "대규모니까 방어를 다 넣자"가 아니라, **내 실제 부하에서 어느 실패 양상이 진짜 걸리는지 먼저 세는 것**이 이 주제의 실용적 결론이다.

---

## 한눈에 — 쉽게 말하면

**출퇴근 도로**를 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
한산한 도로 (소규모)              막히는 도로 (대규모)
+----------------------+        +----------------------+
| 사고 나면 → 치운다     |        | 도로가 "멈추진" 않는다  |
| = 사고는 사건이다      |        | 대신 늘 일부가 정체 중  |
|                      |        | 차 하나 급정거 →       |
| 차선 늘리면 → 뚫린다   |        |   뒤차 줄줄이 브레이크   |
|                      |        | 차선 늘려도 합류구간은  |
|                      |        |   그대로 병목          |
+----------------------+        +----------------------+
  → 개별 사고를 쫓는다             → 정체율(분포)을 본다
```

**시스템도 똑같은 구조다.** 소규모에서 장애는 "고치는 사건"이지만, 규모가 커지면 다운이 안 나는 대신 **항상 몇 %는 실패 중**인 배경 상태가 된다.\
차 하나의 급정거가 뒤로 번지듯 **한 곳의 지연이 재시도를 타고 증폭**되고, 차선(서버)을 늘려도 **합류구간(DB·락 같은 상태 자원)은 그대로 병목**이다.

쉽게 말하면 이렇다.\
**규모가 바꾸는 것은 "처리 효율(속도)"이 아니라 "실패의 양상"이다.** 원리를 안다고 자동으로 대비되는 게 아니라, 어떤 양상이 실제로 내 시스템에 걸리는지를 먼저 판별해야 한다.

## 문제 — 이 문서가 답하려는 질문

> 출처: `jun-bank/docs/study/10-failure-at-scale/README.md` — 머리말·§6

이 주제에는 풀어야 할 코드 과제가 없다(운영 관점 정리다). 대신 두 질문에 답한다.

```text
Q1  "규모가 커지면 무엇이 달라지는가?"
     → 느려지는 게 아니라 실패하는 방식이 바뀐다 (양상 1~4)

Q2  "그럼 나는 무엇을 넣어야 하는가?"
     → 다 넣는 게 아니다. 내 실제 부하에 걸리는 양상만 센다 (반-과설계)
```

아래 서머리는 이 두 질문을 네 개의 실패 양상으로 쪼개 분석·정리한 것이다.\
각 양상은 **"규모가 커지면 무엇이 실패하는가 → 어떤 패턴이 그것을 막는가"**의 전/후로 읽는다.

---

## 전체 흐름

```text
규모가 커진다
     │
     ▼
실패의 "양상"이 바뀐다 (속도가 아니라)
     │
     ├─ 양상 1  부분 실패가 정상 상태가 된다   (개별 건 → 분포를 본다)
     ├─ 양상 2  재시도가 부하를 증폭시킨다      (지연 → 재시도 폭풍)
     ├─ 양상 3  균등 분산 가정이 깨진다         (샤딩 전제 → 핫스팟)
     └─ 양상 4  상태 있는 것은 늘려도 안 된다    (스케일아웃 → 뒷단 경합)
     │
     ▼
"대규모니까 다 넣자"가 아니라 →  내 실제 부하에 걸리는 양상만 센다
     │
     ▼
양상 2·4는 규모와 무관하게 대개 걸린다
양상 1·3은 진짜 대규모에서만 걸린다  → 안 걸리면 안 만드는 게 방어다
```

## 양상 1 — 부분 실패가 정상 상태가 된다

> 출처: `jun-bank/docs/study/10-failure-at-scale/README.md` — §1

**언제 쓰나** — 초당 수만 건처럼 규모가 큰 시스템. 여기서는 "다운"이 안 나는 대신 p99가 계속 나쁘다.

```text
[전] 무엇이 실패하나 — 소규모의 관제 방식이 더는 안 맞는다
+------------------------------------------+
| 소규모: 장애는 사건이다                    |
|   "다운 4회를 복구했다"                    |
|   관제 대상 = 가동 여부(살았나 죽었나)      |
|   → 개별 건을 하나씩 쫓을 수 있다          |
+------------------------------------------+
              ↓ 규모가 커지면
[후] 어떻게 봐야 하나 — 분포로 본다
+------------------------------------------+
| 대규모: 장애는 배경이다                    |
|   항상 몇 %는 실패 중이다                  |
|   관제 대상 = 분포(p50 / p95 / p99)       |
|   알림 기준 = 죽었나(X) → 나빠지는 추세(O) |
|   고칠 것 = 그 장애(X) → 꼬리를 만드는 구조 |
+------------------------------------------+
  → "어제 3건 실패"를 하나씩 보는 방식이
    "실패율 0.3% → 0.5%"를 보는 방식으로 바뀐다
```

그림 해설 — 소규모에서는 실패가 셀 수 있는 사건이라 하나씩 처리한다.\
대규모에서는 개별 건을 못 쫓는다 — **고칠 대상 자체가 "그 장애"에서 "꼬리(tail)를 만드는 구조"로 바뀐다.**

> **백분위 지연(p50/p95/p99)** — 응답시간을 빠른 순으로 줄 세웠을 때 그 지점의 값. p99 = 상위 1%가 이보다 느리다.\
> 예: 평균은 멀쩡한데 p99만 나쁘면, "대부분 빠른데 100명 중 1명은 아주 느린" 꼬리가 있다는 뜻이다.

비용 — 관제·알림 체계 자체를 갈아야 한다(가동 여부 → 분포·추세). 개별 건 추적이라는 소규모의 편의를 잃는다.

## 양상 2 — 재시도가 부하를 증폭시킨다

> 출처: `jun-bank/docs/study/10-failure-at-scale/README.md` — §2

**언제 쓰나** — 서비스들이 서로를 동기 호출하고, 실패 시 재시도가 걸려 있는 모든 구조(규모와 무관).

```text
[전] 무엇이 실패하나 — 지연이 재시도를 타고 번진다
   A 느려짐
      ↓
   B의 스레드가 A를 기다리며 물림
      ↓
   B도 느려짐  →  C까지 물림
      ↑
   재시도가 여기에 불을 붙인다
   (한 요청이 3번 재시도되면 부하 3배 — 이미 느린 곳에 3배가 들어간다)
```

이것이 **재시도 폭풍(retry storm)**이다. 느려서 재시도하는데, 그 재시도가 시스템을 더 느리게 만드는 되먹임 고리다.

```text
[후] 어떤 패턴이 막나
+----------------+-------------------------------------------+
| 서킷 브레이커    | 실패가 임계를 넘으면 즉시 거절 — 대기를 없앤다 |
| 지수 백오프+지터 | 재시도가 "동시에" 몰리는 것을 막는다          |
| 재시도 예산      | 전체 요청 대비 재시도 비율에 상한            |
| 벌크헤드         | 느린 대상 전용 풀 — 다른 경로가 안 물린다     |
| 타임아웃 계층    | 하위 타임아웃 < 상위 타임아웃                |
+----------------+-------------------------------------------+
```

그림 해설 — 서킷 브레이커는 "대기"라는 연료 자체를 끊고, 백오프+지터는 재시도가 한 순간에 겹치는 것을 흩는다.\
타임아웃 계층이 **거꾸로면**(상위 < 하위) 상위가 먼저 포기하는데 하위는 계속 돌아 — 헛일을 하는 좀비 요청이 쌓인다.

> **지터(jitter)** — 재시도 간격에 일부러 섞는 무작위 흔들림.\
> 예: 100개가 "3초 뒤 재시도"로 똑같이 맞춰지면 3초 뒤에 100개가 동시에 몰린다. ±무작위를 더하면 그 순간이 흩어진다.

비용 — 임계값·반열림(half-open) 대기시간·지터 폭은 **실측 없이 정할 수 없다.** "서킷 브레이커를 넣어봤다"와 "재시도 폭풍을 맞고 튜닝했다"는 다르다.

## 양상 3 — 균등 분산 가정이 깨진다

> 출처: `jun-bank/docs/study/10-failure-at-scale/README.md` — §3

**언제 쓰나** — 샤딩·파티셔닝으로 부하를 나눠 담는 구조. 이들은 "부하가 고르게 들어온다"는 전제 위에 있는데, 실제로는 안 그렇다.

```text
[전] 무엇이 실패하나 — 부하가 한 곳으로 쏠린다(핫스팟)
편중 원인
  인기 항목   한 상품·한 이벤트가 트래픽 대부분
  큰 테넌트   고객 하나가 전체의 절반
  시간 편중   특정 시각에 집중(급여일·정산 시각)
  키 설계     순차 키 → 마지막 샤드에만 쓰기가 몰린다

  샤드1   샤드2   샤드3(HOT)
  [  ]    [  ]    [######]  ← 한 키에 몰리면
                              그 키는 여전히 한 샤드다
  → 샤드를 늘려도 안 풀린다
```

```text
[후] 어떤 패턴이 막나
+------------------+--------------------------------------+
| 키에 엔트로피 추가 | accountId#bucket 처럼 쪼갠다           |
|                  |   단, 조회가 복잡해진다               |
| 핫 키 전용 처리   | 상위 N개만 별도 경로로                 |
| 읽기 캐시·복제    | 읽기 편중에만 유효(쓰기 편중엔 안 듣는다) |
+------------------+--------------------------------------+
```

그림 해설 — 핵심은 **"샤드를 늘려도 한 키는 한 샤드"**라는 점이다.\
그래서 분할 축을 바꾸거나(엔트로피 추가) 그 키만 따로 다뤄야 한다. 샤드 수를 늘리는 것으로는 못 푼다.

> **핫스팟/핫 키(hot key)** — 다른 곳은 한산한데 특정 키·파티션에만 부하가 몰리는 것.\
> 예: 순차 증가 ID를 샤드 키로 쓰면 새로 쓰는 데이터가 늘 "마지막 샤드"로만 가서, 그 샤드만 불탄다.

비용 — 엔트로피를 더하면 조회가 복잡해진다(한 계좌를 여러 버킷에서 긁어모아야 한다). 편중 원인마다 대응이 다르다.

## 양상 4 — 상태 있는 것은 늘려도 안 된다

> 출처: `jun-bank/docs/study/10-failure-at-scale/README.md` — §4

**언제 쓰나** — "느리니까 서버를 늘리자(스케일아웃)"를 하려는 모든 순간. 무상태 서버는 늘리면 되지만, 나머지는 아니다.

```text
[전] 무엇이 실패하나 — 앞단을 늘렸더니 뒷단이 먼저 죽는다
자원          왜 안 늘어나나
  커넥션 풀    앱 2배 → DB 커넥션 2배 → DB가 먼저 죽는다
  락 경합      같은 로우를 노리는 인스턴스가 늘면 경합 심화
  시퀀스·채번  중앙 채번은 인스턴스가 늘수록 병목
  캐시 일관성  노드가 늘면 무효화 전파 비용이 제곱으로
  분산 락      늘릴수록 락 서버가 병목

  앱앱앱앱  ← 늘림
     ↓↓↓↓
  [   DB / 락   ]  ← 여기가 병목이면 앞단을 늘릴수록 더 나빠진다
```

```text
[후] 무엇을 봐야 하나 — 증설이 듣는 자원과 안 듣는 자원을 가른다
+----------------------+----------------------------+
| 증설(스케일아웃)이     | 증설이 안 듣는 것            |
|   듣는 것             |                            |
| = 무상태 앱 CPU       | = DB 쓰기·락 경합·중앙 채번   |
| → 인스턴스 늘리면 됨   | → 샤딩/설계 변경이 필요      |
+----------------------+----------------------------+
```

그림 해설 — **"증설했는데 더 느려졌다"의 대부분이 여기다.** 앞단을 늘렸더니 뒷단 경합이 심해진 것이다.\
"증설이 먼저"라는 전략도 한계가 있다 — 증설이 듣는 것은 앱 CPU뿐이고, DB 쓰기·락 경합에는 안 듣는다. 그때는 샤딩이나 설계 변경으로 넘어간다.

> **스케일아웃 vs 스케일업** — 아웃 = 같은 걸 여러 대로(수평), 업 = 한 대를 더 크게(수직).\
> 예: 무상태 웹서버는 아웃이 잘 듣지만, 하나의 DB에 모두가 쓰는 구조는 아웃해도 그 DB가 병목이라 안 듣는다.

비용 — 상태 자원은 늘려도 병목이 안 풀리고, 오히려 경합이 커진다. 애초에 "무엇이 상태를 갖는가"를 판별해야 한다.

## 어느 양상이 실제로 걸리는지 세라 (반-과설계)

> 출처: `jun-bank/docs/study/10-failure-at-scale/README.md` — §5·§6

여기가 이 문서의 실용적 핵심이다. 네 양상을 알았다고 넷 다 방어하는 게 아니다.

```text
[나쁨] 근거 없는 큰 수                [좋음] 실제 부하에 걸리는 것만 센다
+---------------------------+      +---------------------------+
| "대규모니까 서킷 브레이커·   |      | 내 목표 부하는 얼마인가?     |
|  백프레셔·핫키 처리를        |      | 양상별로 걸리나 / 안 걸리나  |
|  전부 넣자"                 |      |   센다                     |
| → 안 걸리는 방어까지 짓는다   |      | → 걸리는 것만 만든다        |
+---------------------------+      +---------------------------+
  → 오버엔지니어링                    → 안 걸리는 걸 "안 만드는 것"도 방어다
```

그림 해설 — "다 넣자"는 근거 없이 용량을 크게 잡는 것과 같은 실수다(과잉 처리량).\
**어느 양상이 실제로 걸리는지 아는 것**이 안 걸리는 방어를 안 만드는 근거가 된다.

경험칙으로 갈리는 지점:

- **양상 2(재시도 증폭)·양상 4(상태 자원 한계)는 규모와 무관하게 대개 걸린다.** 수백 TPS에서도 난다.
- **양상 1(부분 실패 정상화)·양상 3(핫스팟)은 진짜 대규모에서만 치명적이다.** 중간 규모면 실패는 여전히 "쫓을 수 있는 사건"이다.

> **오버엔지니어링(over-engineering)** — 지금 걸리지도 않는 문제까지 미리 방어해 시스템을 무겁게 만드는 것.\
> 예: 초당 수백 건인데 초당 수만 건용 핫키 분산·백프레셔를 다 넣으면, 안 쓰는 복잡도가 유지비만 먹는다.

---

## 현장에서 만나는 상황

원고는 특정 프로젝트(결제 시스템)의 실제 수치·설계 결정을 근거로 이 판별을 했다. 그 결정을 일반화하면 이렇다.

**상황 A — 부하는 중간인데(예: 평시 수십, 피크 수백 TPS) 규모별 방어를 어디까지 넣을지 정해야 한다.**\
점검 질문은 하나다 — **이 부하에서 실패는 아직 "사건"인가, 아니면 "배경"인가.**\
사건이면 양상 1·3은 대개 안 걸리므로 짓지 않는 게 맞고, 양상 2·4만 챙긴다.

**상황 B — 재시도가 내 선택이 아니라 도메인의 전제인 경우.**\
결제의 망취소(reversal)처럼 **상대 시스템이 "응답을 받을 때까지" 재전송하고 횟수·간격을 규정하지 않는** 프로토콜이 흔하다.\
이때 나는 재시도를 "받는 쪽"이라, 내가 느려지면 상대의 재전송이 겹쳐 증폭된다.\
그래서 응답시간 목표(예: p99 3초)가 성능 지표가 아니라 **정합성 방어선**이 된다 — 느리면 중복 요청이 겹쳐 데이터가 어긋나기 때문이다.

**상황 C — 배치가 실시간 처리와 같은 DB를 친다.**\
대사(reconciliation) 배치처럼 무거운 작업이 실시간 승인과 같은 DB를 두드리면, 앱 인스턴스를 늘려도 DB 경합은 안 줄어든다(양상 4).\
게다가 도메인이 요구하는 직렬화(같은 계좌 동시 승인은 락으로 줄 세움)는 **늘려서 푸는 문제가 아니다** — 늘리면 오히려 락 경합만 커진다.

> 세 상황을 관통하는 원칙: **내가 어떤 실패 양상 위에 서 있는지 먼저 세고, 걸리는 것만 방어한다.**

## 핵심 문장

- **규모가 바꾸는 것은 속도가 아니라 실패의 양상이다.** 다운이 안 나는 대신 p99가 계속 나쁘다.
- **재시도는 이미 느린 시스템에 부하를 배로 얹는다** — 서킷 브레이커·백오프+지터·타임아웃 계층으로 되먹임 고리를 끊는다.
- **핫스팟은 샤드를 늘려도 안 풀린다** — 한 키에 몰리면 그 키는 여전히 한 샤드다.
- **상태 있는 것(DB·락·채번)은 앞단을 늘릴수록 뒷단 경합이 심해진다** — 증설이 듣는 건 앱 CPU뿐이다.
- **"대규모니까 다 넣자"는 근거 없는 큰 수와 같다** — 내 실제 부하에 걸리는 양상만 세는 것이 과설계를 막는다.

## 용어 풀이

- **꼬리 지연(Tail Latency)** — 분포의 끝(p95·p99). 대부분 빠른데 소수가 아주 느린 상태. 대규모에서 진짜 고칠 대상.
- **백분위 지연(p50/p95/p99)** — 응답시간을 줄 세웠을 때의 지점 값. p99는 상위 1%가 이보다 느리다.
- **서킷 브레이커(Circuit Breaker)** — 실패가 임계를 넘으면 호출을 즉시 거절해 대기 자체를 없애는 장치. 회복되면 반열림으로 시험 호출.
- **지수 백오프(Exponential Backoff)** — 재시도 간격을 점점 벌리는 것(1초 → 2초 → 4초). 몰림을 줄인다.
- **지터(Jitter)** — 재시도 간격에 섞는 무작위 흔들림. 재시도가 같은 순간에 겹치는 것을 흩는다.
- **재시도 예산(Retry Budget)** — 전체 요청 대비 재시도가 차지할 비율의 상한. 재시도 폭풍을 막는다.
- **벌크헤드(Bulkhead)** — 느린 대상 전용 자원 풀을 따로 두어, 한 곳의 지연이 다른 경로를 물지 않게 격리하는 것.
- **재시도 폭풍(Retry Storm)** — 느려서 재시도하는데 그 재시도가 시스템을 더 느리게 만드는 되먹임 고리.
- **타임아웃 계층** — 하위 타임아웃 < 상위 타임아웃이어야 한다. 거꾸로면 상위가 먼저 포기하고 하위는 헛되이 계속 돈다.
- **샤딩/파티셔닝(Sharding)** — 데이터를 키로 나눠 여러 저장소에 분산하는 것. "부하가 고르게 들어온다"는 전제 위에 있다.
- **핫스팟/핫 키(Hot Key)** — 다른 곳은 한산한데 특정 키·파티션에만 부하가 몰리는 것.
- **엔트로피 추가(Key Salting)** — 키에 버킷을 섞어(`id#bucket`) 한 키의 부하를 여러 샤드로 흩는 것. 대가로 조회가 복잡해진다.
- **스케일아웃/스케일업** — 아웃 = 같은 걸 여러 대로(수평), 업 = 한 대를 더 크게(수직). 상태 자원엔 아웃이 안 듣는다.
- **커넥션 풀(Connection Pool)** — 앱이 DB에 미리 열어두고 재사용하는 연결 묶음. 앱을 늘리면 이것도 늘어 DB가 먼저 죽는다.
- **락 경합(Lock Contention)** — 같은 자원(로우)을 여러 주체가 동시에 잡으려 다투는 것. 인스턴스가 늘수록 심해진다.
- **채번/시퀀스(ID Generation)** — 유일 번호를 발급하는 것. 중앙 집중이면 인스턴스가 늘수록 병목.
- **at-least-once** — "최소 한 번" 전달 보장. 중복은 있을 수 있으니 받는 쪽이 멱등(중복 무시)해야 한다.
- **아웃박스(Outbox)** — DB 트랜잭션과 메시지 발행을 한데 묶기 위해, 보낼 메시지를 같은 DB 테이블에 적어두고 릴레이가 나중에 발행하는 패턴.
- **백프레셔(Backpressure)** — 처리 속도를 넘는 유입을 상류로 되밀어 큐가 무한히 쌓이는 걸 막는 것.
- **오버엔지니어링(Over-engineering)** — 지금 걸리지도 않는 문제까지 미리 방어해 시스템을 무겁게 만드는 것.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **꼬리 지연이 왜 대규모에서만 아픈가.** 한 요청이 여러 하위 호출로 부챗살처럼 퍼지면(fan-out), 최종 응답은 그중 **가장 느린 하나**를 기다린다. 하위 호출이 100개면 각각의 p99(상위 1%)가 언젠가 하나는 걸려, 전체 요청의 상당수가 꼬리에 물린다. 그래서 규모가 커질수록 평균이 아니라 꼬리를 관리한다(구글의 "The Tail at Scale", 2013).
- **멱등성(idempotency)이 재시도의 짝이다.** at-least-once로 재시도가 오면 같은 요청이 두 번 처리될 수 있다. 받는 쪽이 "같은 요청 ID는 한 번만 반영"하도록 멱등하게 만들어야 재시도가 안전해진다. 재시도 방어(양상 2)는 보내는 쪽 장치이고, 멱등성은 받는 쪽 장치다 — 둘이 짝이다.
- **리틀의 법칙(Little's Law).** 큐 안 평균 건수 = 도착률 × 평균 체류시간. 재시도로 도착률이 3배가 되고 시스템이 느려져 체류시간도 늘면, 큐에 쌓이는 건수는 곱으로 폭증한다 — 재시도 증폭이 왜 그렇게 빨리 무너지는지의 수식적 설명이다.
- **"안 만드는 것이 방어"라는 관점의 이름.** YAGNI(You Aren't Gonna Need It) — 지금 필요하지 않은 것은 만들지 말라는 원칙이 이 문서의 §5·§6과 같은 결이다. 다만 여기서는 "미래에 필요할 수도"가 아니라 "내 실제 부하에 근거해" 판별한다는 점이 더 구체적이다.
