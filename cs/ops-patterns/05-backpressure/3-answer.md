### A. 문제 (구현 대상 TODO)

#### 1. UnboundedChannel.offer — 판단하지 않는다

```java
// impl 정답
@Override
public synchronized boolean offer(T item) {
    requireItem(item);
    queue.addLast(new Stamped<>(item, ticker.nowMillis()));
    accepted++;
    // 여기서 아무 판단도 안 한다. 그것이 이 구현의 전부이자 문제다.
    return true;
}
```

- Q: 이 구현이 "실패가 하나도 없는데 제일 위험한" 이유는?
  A: 실패가 없다는 것이 곧 아무 신호도 안 준다는 뜻이기 때문이다.
  코드가 제일 짧고 예외도 없어서 처음에는 늘 이 모양이 되는데, 문제가 생겨도 지표에 안 나타난다.
  버림 0, 에러 0, 성공률 100%인 채로 대기 시간만 무한히 자란다.

- Q: 이 구현의 실패는 왜 예외가 아니라 시간인가?
  A: 아무것도 안 버리므로 잃는 것이 "처리 시점"뿐이기 때문이다.
  소비자가 초당 100개인데 큐에 9,000개가 쌓였으면 지금 넣는 항목은 90초 뒤에 처리된다 — 리틀의 법칙 그대로다.
  90초 뒤의 응답은 성공으로 세지만 아무도 안 받는다.

- Q: 아무 판단도 안 하는 이 코드가 실무에서 어떤 한 줄로 나타나는가?
  A: `new LinkedBlockingQueue<>()` — 인자 없이 부르면 정원이 `Integer.MAX_VALUE` 다.
  이름은 Bounded 계열인데 사실상 무한 큐이고, 그렇게 쓰는 코드가 아주 많다.

- Q: `dropped()` 와 `rejected()` 가 늘 0을 돌려주는 것이 지표 대시보드에서 어떻게 보이는가?
  A: 완벽하게 보인다 — 유실도 거절도 없는 건강한 시스템.
  실제로 봐야 하는 것은 `maxWaitMillis` 와 `size` 인데, 그 둘을 안 그려놨으면 죽기 직전까지 초록이다.

- Q: 아무것도 안 버리는 이 큐의 최종 사망 원인은 무엇인가?
  A: 메모리다 — 예외 없이 잘 돌다가 `OutOfMemoryError` 로 죽는다.
  그 전까지 모든 지표가 초록이라 원인 추적도 늦다.

- Q: `capacity()` 가 0이 아니라 -1을 돌려주는 이유는?
  A: 0을 주면 "정원 없음(무한)"과 "정원이 0(아무것도 못 받음)"이 같은 값이 되어 호출자가 헷갈린다.
  있을 수 없는 값(-1)으로 "무한"이라는 뜻을 분명히 한다.

#### 2. UnboundedChannel.poll — 기다린 시간을 기록한다

```java
// impl 정답
@Override
public synchronized Optional<T> poll() {
    Stamped<T> head = queue.pollFirst();
    if (head == null) {
        return Optional.empty();
    }
    lastWaitMillis = ticker.nowMillis() - head.enqueuedAt();
    maxWaitMillis = Math.max(maxWaitMillis, lastWaitMillis);
    return Optional.of(head.item());
}
```

- Q: 항목마다 시각을 들고 있지 않고 큐 전체에 하나만 두면 측정이 어떻게 틀리는가?
  A: 먼저 온 것과 나중 온 것의 대기가 같은 값으로 나온다.
  큐가 길어질수록 벌어지는 차이가 정확히 이 상자가 재려는 것인데, 그 차이가 사라진다.
  그래서 `Stamped(item, enqueuedAt)` 로 항목마다 자기 시각을 붙인다.

- Q: `maxWaitMillis` 를 매번 덮어쓰면 그 값은 무슨 뜻이 되는가?
  A: 그냥 "방금 꺼낸 것의 대기"가 된다 — `lastWaitMillis` 와 같은 값이라 아무 뜻이 없어진다.
  최댓값은 안 내려가야 최악의 순간을 남긴다(`Math.max` 로 갱신).

- Q: 최댓값과 마지막 값 두 개를 같이 들고 있는 이유는?
  A: 마지막 값은 **지금** 얼마나 밀려 있는지(회복 중인지)를 보여주고, 최댓값은 **최악**이 얼마였는지를 남긴다.
  둘 중 하나만 보면 회복을 못 보거나 사고를 못 본다.

- Q: 빈 큐에서 `poll` 할 때 대기 시간을 건드리지 않아야 하는 이유는?
  A: 꺼낸 항목이 없으니 "기다린 시간"이 정의되지 않기 때문이다.
  0으로 덮어쓰면 한산한 순간마다 측정이 리셋되어 최댓값이 거짓말을 한다 — `Optional.empty()` 로 바로 빠져나온다.

#### 3. BoundedChannel.offer — 이 상자의 본체

```java
// impl 정답
@Override
public boolean offer(T item) throws InterruptedException {
    UnboundedChannel.requireItem(item);
    synchronized (this) {
        if (queue.size() < capacity) {
            return enqueue(item);
        }
        switch (policy) {
            case DROP_NEWEST -> { dropped++; return false; }          // 큐는 그대로
            case DROP_OLDEST -> { queue.pollFirst(); dropped++; return enqueue(item); }
            case FAIL        -> { rejected++; throw new ChannelFullException(capacity); }
            case BLOCK       -> { /* 아래에서 처리 */ }
            default -> throw new IllegalStateException("모르는 정책: " + policy);
        }
        long startedAt = ticker.nowMillis();
        while (queue.size() >= capacity) {   // if 가 아니라 while
            wait();
        }
        blockedMillis += ticker.nowMillis() - startedAt;
        return enqueue(item);
    }
}
```

- Q: 정원 판정의 부등호가 한 칸 틀리면 왜 DROP 정책에서는 티가 안 나는가?
  A: DROP 정책에서는 한 칸 더 들어가도 예외가 없고 반환값도 그대로라 겉보기 동작이 같기 때문이다.
  큐가 정원 + 1로 도는데 아무도 모르고, 크기를 직접 세는 테스트가 없으면 영영 안 잡힌다.
  BLOCK 에서만 "자리 없음"의 정의가 곧 대기 조건이라 어긋남이 드러난다.

- Q: DROP_OLDEST 만 반환값이 true 인 이유는?
  A: **새 항목은 실제로 들어갔기** 때문이다.
  `offer` 의 반환값은 "이 항목을 받았는가"를 뜻하고, 그 질문에 대한 답은 참이다.
  사라진 것은 다른 항목이라 반환값이 말해주지 않는다.

- Q: 그 true 가 "이 상자에서 제일 조용한 사고"인 이유와, 무엇을 같이 봐야 알 수 있는가?
  A: 예외도 없고 반환값도 정상인데 데이터 하나가 사라졌기 때문이다 — 호출자 코드에는 흔적이 전혀 없다.
  `dropped` 카운터를 같이 봐야만 알 수 있고, 그래서 이 정책을 쓰는 곳은 그 지표를 반드시 노출해야 한다.

- Q: DROP_OLDEST 를 쓰면 안 되는 데이터와 맞는 데이터는 각각 무엇인가?
  A: 안 되는 것 — 순서와 빠짐없음이 의미인 데이터(로그, 이벤트 소싱, 거래 내역). 조용히 구멍이 난다.
  맞는 것 — 최신만 의미 있는 데이터(센서 값, 시세, 대시보드 지표). 오래된 값은 붙들고 있어봐야 아무도 안 본다.

- Q: DROP_NEWEST 와 DROP_OLDEST 는 각각 무엇을 지키려고 무엇을 버리는가?
  A: DROP_NEWEST — 이미 받은 것(순서)을 지키려고 제일 최신 정보를 버린다.
  DROP_OLDEST — 최신을 지키려고 제일 오래된 것을 버린다.
  버리는 양은 같고 방향만 반대다.

- Q: `wait` 를 `if` 로 쓰면 정확히 어떤 상태가 되는가?
  A: 깨어난 뒤 조건을 다시 확인하지 않고 바로 넣기 때문에 **정원을 넘겨 들어간다.**
  정원이 있다고 믿는 큐가 실제로는 정원을 안 지키는 상태 — 대기 시간 보장이 조용히 사라진다.

- Q: 깨어났는데 자리가 없는 경우가 생기는 두 가지 이유는?
  A: ① 다른 생산자가 먼저 깨어나 그 자리를 가져갔다(notifyAll 이면 여럿이 함께 깨어난다).
  ② 가짜 깨어남(spurious wakeup) — 아무 이유 없이 wait 에서 깨어나는 일이 자바 명세상 허용된다.

- Q: `wait()` 가 `synchronized` 안에 있는데도 소비자가 `poll` 할 수 있는 이유는?
  A: `wait` 는 **잠금을 놓고** 잠들기 때문이다.
  깨어날 때 잠금을 다시 잡는다 — 그래서 자는 동안 소비자가 같은 객체의 `poll` 에 들어올 수 있다.

- Q: 막힌 시간(`blockedMillis`)이 "백프레셔가 실제로 돌고 있다는 유일한 증거"인 이유는?
  A: BLOCK 은 아무것도 안 버리고 아무 예외도 안 던지므로, 밖에서 볼 수 있는 흔적이 "생산자가 얼마나 붙잡혀 있었나"뿐이다.
  그 수가 0이 아니면 생산자가 소비자 속도에 끌려가고 있다는 뜻 — 그게 백프레셔의 정의다.

- Q: BLOCK 에서 대기 시작 시각을 wait 전에 찍고 끝나고 더하는 이유는?
  A: `while` 이 여러 번 돌 수 있어서(깨어났다 다시 자는 경우) 매 회차를 따로 재면 누락되거나 중복된다.
  루프 전체를 한 구간으로 재야 "이 offer 가 총 얼마를 붙잡혀 있었나"가 나오고, `+=` 로 누적해야 채널 전체의 압력이 된다.

#### 4. BoundedChannel.poll — 자리가 났다고 알린다

```java
// impl 정답
@Override
public synchronized Optional<T> poll() {
    Stamped<T> head = queue.pollFirst();
    if (head == null) {
        return Optional.empty();
    }
    lastWaitMillis = ticker.nowMillis() - head.enqueuedAt();
    maxWaitMillis = Math.max(maxWaitMillis, lastWaitMillis);
    notifyAll();   // 이것을 빼먹으면 BLOCK 생산자가 영원히 안 깨어난다
    return Optional.of(head.item());
}
```

- Q: `notifyAll` 을 빼먹으면 BLOCK 생산자에게 무슨 일이 생기는가?
  A: 자리가 나도 아무도 알려주지 않아 영원히 깨어나지 못한다 — 사실상 데드락이다.
  큐는 비어가는데 생산자들은 전부 자고 있고, 예외도 로그도 없다.

- Q: 그 결함이 테스트 셋을 통과하는 이유는?
  A: 나머지 세 정책(DROP_NEWEST·DROP_OLDEST·FAIL)은 애초에 기다리지 않기 때문이다.
  아무도 자지 않으니 깨울 일도 없고, 그래서 알림이 있든 없든 동작이 같다.
  네 정책 중 셋이 그대로 통과한다.

- Q: "테스트 대부분이 통과한다"가 결함의 위험도에 대해 말해주는 것은?
  A: 통과율이 안전의 지표가 아니라는 것이다.
  결함은 한 경로에만 있고 그 경로가 하필 제일 중요한 경로(진짜 백프레셔)다.
  그래서 정책마다 테스트를 따로 두고, 조용한 실패는 지표(blockedMillis·dropped)로 못 박는다.

- Q: `notify` 가 아니라 `notifyAll` 인 편이 안전한 이유는? (원본에 근거 없음 — 내 추론)
  A: `notify` 는 자고 있는 스레드 중 하나만 깨우는데, 그 하나가 조건을 만족하지 못해 다시 자면 다른 스레드는 여전히 모른다(lost wakeup).
  대기 이유가 한 가지뿐인 이 구조에서는 `notify` 로도 대체로 맞지만, 전부 깨우고 각자 `while` 로 다시 확인하게 두는 쪽이 실수에 강하다.

- Q: 소비자가 producer 를 깨우는 이 구조가 "백프레셔"라는 이름과 어떻게 맞아떨어지는가?
  A: 신호가 소비자 → 생산자, 즉 흐름을 **거슬러 올라간다**.
  소비자가 빼는 속도가 곧 생산자가 넣을 수 있는 속도가 되고, 그 압력이 생산자의 생산자에게까지 전파되어야 진짜 효과가 난다.

### B. 개념

#### 5. 지표가 전부 초록인 채로 죽는다

- Q: 생산 1000/s · 소비 100/s · 무한 큐일 때 30초 뒤 큐 길이와 최대 대기는?
  A: 큐 27,000, 최대 대기 28초.
  10초에 9,000/10초, 20초에 18,000/19초로 자라는 중이다 — 매초 900개씩 밀린다.

- Q: 그 상황에서 버림·에러·성공률은 각각 얼마이고, 그래서 무엇이 문제인가?
  A: 버린 것 0개, 에러 0건, 성공률 100%.
  실패가 지표에 안 나타나므로 알림도 안 울리고 아무도 안 본다 — **지표가 전부 초록인 채로 죽는다.**
  이 상자가 막으려는 것이 그 모양이다.

- Q: 03·04·05가 같은 문제의 세 층이라는 말에서 각 층은 무엇을 하는가?
  A: 03 벌크헤드 — 이미 들어온 것을 **나눈다**(자원을 칸으로).
  04 레이트 리미터 — 들어오는 속도를 **막는다**.
  05 백프레셔 — 소비자가 생산자에게 **천천히라고 말한다**.

- Q: 이 셋 중 05만이 하는 일은 무엇인가?
  A: 신호를 거꾸로 올려보내는 것 — 나머지 둘은 받는 쪽에서 처리하고 끝나지만, 백프레셔는 생산자의 속도 자체를 바꾼다.
  그래서 전파가 끊기면(중간에서 흡수하면) 효과가 사라진다.

#### 6. 큐 길이를 고르는 것 = 대기 시간을 고르는 것

- Q: 리틀의 법칙을 이 상자의 식으로 쓰면?
  A: `대기 시간 = 큐 길이 / 처리율`.
  큐에 9,000개가 있고 초당 100개를 처리하면 지금 들어간 항목은 90초 뒤에 처리된다.

- Q: 처리율을 우리가 못 고르는 이유는, 그래서 고를 수 있는 것은 무엇인가?
  A: 처리율은 소비자가 실제로 일을 처리하는 속도라 큐로는 못 바꾼다.
  식에서 우리가 고를 수 있는 값은 큐 길이뿐이고, 그러므로 **큐 길이를 고르는 것이 곧 대기 시간을 고르는 것**이다.

- Q: 정원 50과 100의 최대 대기가 똑같이 1,000ms 인 이유는?
  A: 두 경우 모두 소비자가 한 주기에 못 빼고 남기는 양이 정원보다 크기 때문에, 큐는 늘 꽉 찬 채로 돌고 실제 대기는 "정원 ÷ 처리율"이 아니라 소비 주기에 묶인다.
  정원이 이미 충분히 작으면 더 줄여도 대기는 더 안 줄고 버림만 는다(50에서 9,500개를 버린다).

- Q: 그렇다면 대기 시간은 무엇에 비례하는가?
  A: **소비자가 한 주기에 못 빼고 남긴 양**에 비례한다.
  그 양이 0이면(소비가 생산을 따라잡으면) 정원을 아무리 키워도 대기는 안 자란다.

- Q: 원본 저자가 측정에 반박당해 주장을 고친 대목은 어디인가?
  A: "지연이 정원에 비례한다"고 쓰려다 정원 50과 100의 대기가 같아서 막혔고, 주장을 고쳤다(README 9).
  측정이 글쓴이를 이긴 자리이고, 그래서 이 문서의 표가 믿을 만하다.

- Q: "큐를 크게 잡는 것은 안전이 아니라 지연을 사는 것"을 10초 대기 요청으로 설명하면?
  A: 정원 800이면 버림이 8,300으로 줄지만 최대 대기가 8,000ms 가 된다.
  10초 기다려 처리한 요청은 이미 사용자가 떠났거나 상위 타임아웃이 끊었다 — 일은 했는데 쓸모가 없다.
  안 버린 것처럼 보이지만 시간을 버린 것이다.

#### 7. 정원을 두면 반드시 무언가를 잃는다

- Q: 같은 부하에서 네 정책의 (받음·버림·거절·최대 대기)는 각각 얼마인가?
  A: 정원 100 / 생산 1000/s / 소비 100/s / 10초 기준 —
  DROP_NEWEST 1,000 · 9,000 · 0 · 1,000ms,
  DROP_OLDEST 10,000 · 9,000 · 0 · 1,000ms,
  FAIL 1,000 · 0 · 9,000 · 1,000ms,
  무한 큐 10,000 · 0 · 0 · **10,000ms**.

- Q: "잃는 양은 같고 잃는 것이 다르다"에서 각 정책이 잃는 것은 무엇인가?
  A: DROP_NEWEST — 최신 정보. DROP_OLDEST — 오래된 항목(과 순서).
  FAIL — 아무것도 안 잃고 생산자에게 넘긴다(생산자가 잃을지 고른다). BLOCK — 생산자의 속도(시간)를 잃는다.
  무한 큐 — 시간(유효한 응답 시점).

- Q: 무한 큐만 아무것도 안 잃는 것처럼 보이는데 실제로 잃는 것은 무엇인가?
  A: 시간이다 — 최대 대기가 10,000ms 로 다른 정책의 10배다.
  받음 10,000에 버림 0이라 표에서 제일 좋아 보이는 줄이 사실은 제일 나쁜 줄이다.

- Q: 10초 기다려 처리한 요청이 "일은 했는데 쓸모가 없다"인 이유는?
  A: 그 응답을 받을 쪽이 이미 없기 때문이다 — 사용자는 떠났고, 상위 호출자의 타임아웃은 진작 끝났다.
  자원은 다 썼는데 결과의 값이 0이라 사실상 버린 것보다 나쁘다(버리기라도 했으면 그 자원으로 다른 요청을 처리했다).

- Q: 무엇을 잃을지는 누가 정하는가?
  A: 데이터다.
  순서·빠짐없음이 의미면 DROP_NEWEST(또는 BLOCK/FAIL), 최신만 의미면 DROP_OLDEST — 정책은 큐의 성질이 아니라 그 안에 흐르는 것의 성질에서 나온다.

#### 8. 버리는 것과 던지는 것은 다르다

- Q: 버렸을 때와 던졌을 때 생산자가 각각 무엇을 아는가?
  A: 버리면 생산자는 **성공한 줄 안다**(DROP_NEWEST 는 false 를 주긴 하지만 DROP_OLDEST 는 true 다).
  던지면 `ChannelFullException` 으로 "큐가 찼다"를 알고, 재시도할지 포기할지 고를 수 있다.

- Q: 생산자에게 주는 그 선택권이 값인 이유는?
  A: 무엇이 중요한지는 생산자만 알기 때문이다 — 결제 요청이면 재시도해야 하고 지표 한 건이면 버려도 된다.
  채널이 대신 정하면 중요한 것과 안 중요한 것이 같은 취급을 받는다.

- Q: 그런데 "아는 쪽이 늘 낫지는 않다"는 이유는(01번과 어떻게 연결되는가)?
  A: 알면 재시도하게 되고, 재시도는 이미 버거운 시스템에 부하를 더한다(01번 재시도 폭풍).
  **고를 수 있게 하는 것과 잘 고르는 것은 다르다** — FAIL 을 고르면 생산자 쪽에 백오프·예산 같은 01번 장치가 같이 있어야 한다.

- Q: FAIL 의 `ChannelFullException` 이 03번의 무엇과 같은 모양인가?
  A: 03번 `BulkheadFullException` 이다.
  둘 다 "자리가 없다, 시도조차 안 했다"를 즉시 알려 호출자가 폴백을 고를 수 있게 한다 — 02번 `CircuitBreakerOpenException` 도 같은 계열이다.

- Q: DROP_OLDEST 가 순서 있는 데이터에 내는 구멍이 조용한 이유는?
  A: 예외도 없고 반환값도 true 라 호출 지점에는 아무 흔적이 없기 때문이다.
  구멍은 한참 뒤 로그를 읽거나 이벤트를 재생할 때 드러나는데, 그때는 원인을 되짚을 방법이 없다.

#### 9. 동시성 도구의 함정

- Q: `wait` 를 `while` 로 감싸는 이유 두 가지는?
  A: ① 깨어났을 때 다른 생산자가 먼저 그 자리를 가져갔을 수 있다.
  ② 가짜 깨어남(spurious wakeup) — 아무 이유 없이 깨어날 수 있다.
  둘 다 "깨어남 = 조건 충족"이 아니라는 뜻이라, 깨어나면 조건을 **다시 확인**해야 한다.

- Q: `poll` 의 알림 누락이 정책 셋에서 안 드러나는 이유는?
  A: 나머지 셋은 기다리지 않기 때문이다 — 자는 스레드가 없으니 깨우지 않아도 아무 일이 안 일어난다.
  결함이 특정 정책 한 경로에만 살아 있고 나머지는 초록이라, 통과율만 보면 멀쩡해 보인다.

- Q: 항목마다 자기 시각을 들고 있어야 하는 이유는?
  A: 큐 전체에 시각 하나만 두면 먼저 온 것과 나중 온 것의 대기가 같은 값으로 나온다.
  이 상자의 결론이 전부 대기 시간 숫자라서, 그 측정이 틀리면 결론이 통째로 틀린다.

- Q: 담는 그릇(ArrayDeque)을 직접 만들지 않은 이유는 — 이 챕터의 주제는 무엇 하나인가?
  A: 주제는 큐 자료구조가 아니라 **찼을 때 무엇을 하느냐** 하나이기 때문이다.
  그릇을 직접 만들면 코드가 길어지고 정작 봐야 할 정책·wait/notify 가 묻힌다.

#### 10. 기본값의 함정

- Q: `new LinkedBlockingQueue<>()` 의 실제 정원은 얼마인가?
  A: `Integer.MAX_VALUE`(약 21억) — 사실상 무한이다.
  이름에 Blocking 이 있어서 막아줄 것 같지만, 인자를 안 주면 아무것도 안 막는다.

- Q: 그 한 줄이 문서 맨 위의 상황과 같은 것인 이유는?
  A: 정원이 사실상 없으니 생산이 소비보다 빠른 순간부터 큐가 무한히 자란다.
  버림 0·에러 0·성공률 100%로 초록 지표를 유지하다 메모리로 죽는 그 시나리오가 바로 이 기본값에서 나온다.

#### 11. 한계

- Q: 정원을 1로 줄이면 대기와 버림은 각각 어떻게 되는가?
  A: 대기는 짧아지지만 **9,990개를 버린다.**
  대기를 사려면 버림으로 값을 치러야 한다 — 공짜인 설정값은 없다.

- Q: "큐는 완충재지 속도를 바꾸는 물건이 아니다"가 뜻하는 것은?
  A: 큐는 일시적인 몰림을 흡수할 뿐, 처리율 자체를 올리지 못한다.
  생산이 소비보다 계속 빠르면 큐 길이로는 못 고친다 — **잃는 것이 달라질 뿐이다.**
  진짜 해법은 소비자를 늘리거나(수평 확장) 생산을 줄이는 것(04번)이다.

- Q: 생산이 소비보다 계속 빠를 때 큐 길이로 고칠 수 있는 것과 없는 것은?
  A: 고칠 수 있는 것 — 무엇을 얼마나 잃을지(버림 대 지연의 배합).
  못 고치는 것 — 잃는다는 사실 자체. 총량은 생산과 소비의 차이가 정한다.

- Q: BLOCK 이 호출 스레드를 묶는다는 사실이 왜 03번이 막으려던 사고를 되살리는가?
  A: 자고 있는 스레드는 다른 일을 못 하기 때문이다.
  요청 스레드 풀에서 offer 하는 구조라면 BLOCK 이 풀을 통째로 말리고, 그 지점이 새 병목이 된다 — 03번 벌크헤드가 막으려던 "한 상대가 스레드 풀을 다 먹는" 사고 그대로다.

- Q: "백프레셔는 위로 전파되어야 의미가 있다"는 말에서 전파가 끊기는 지점은 어디인가?
  A: 중간에서 느려짐을 흡수해버리는 지점 — 예를 들어 offer 를 별도 스레드에 던져놓고 바로 성공을 돌려주는 계층.
  거기서 압력이 멈추고, 그 지점이 무한 큐 역할을 하며 앞의 사고가 그대로 재현된다.

#### 12. 다음 챕터로의 다리

- Q: 03·04·05를 한 문장씩으로 요약하면?
  A: 03 나누기 — 이미 들어온 것을 칸으로 나눠 번짐을 막는다.
  04 막기 — 들어오는 속도에 상한을 건다.
  05 말하기 — 못 받겠다고 생산자에게 알린다(또는 무엇을 버릴지 고른다).

- Q: 06번부터 바뀌는 주제는 무엇인가?
  A: 부하를 다루는 이야기가 끝나고 **"한 번만 실행되게"** 가 시작된다.
  05까지가 양(얼마나 받을까)이었다면 06부터는 정확히 한 번(중복·재시도·순서)의 문제다.
