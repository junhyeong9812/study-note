### A. 문제 (구현 대상 TODO — `src/main/java/com/ops/backpressure/`)

#### 1. UnboundedChannel.offer — 판단하지 않는다 (TODO 1)

```java
@Override
public synchronized boolean offer(T item) {
    requireItem(item);
    // TODO 1: 그냥 넣는다. 판단하지 않는다.
    //
    // **들어온 시각을 같이 담아라.** 그게 없으면 나중에 얼마나 기다렸는지 잴 방법이 없고,
    // 이 구현의 유일한 문제가 정확히 그 수로만 드러난다.
}
```

- 이 구현이 "실패가 하나도 없는데 제일 위험한" 이유는?
- 이 구현의 실패는 왜 예외가 아니라 시간인가?
- 아무 판단도 안 하는 이 코드가 실무에서 어떤 한 줄로 나타나는가?
- `dropped()` 와 `rejected()` 가 늘 0을 돌려주는 것이 지표 대시보드에서 어떻게 보이는가?
- 아무것도 안 버리는 이 큐의 최종 사망 원인은 무엇인가?
- `capacity()` 가 0이 아니라 -1을 돌려주는 이유는?

#### 2. UnboundedChannel.poll — 기다린 시간을 기록한다 (TODO 2)

```java
@Override
public synchronized Optional<T> poll() {
    // TODO 2: 머리에서 하나 꺼내고, 그 항목이 기다린 시간을 기록한다.
    //
    // 큐 전체에 시각 하나만 두면 안 된다. **항목마다 자기 시각을 들고 있어야** 한다.
    // 하나만 두면 먼저 온 것과 나중 온 것의 대기가 같은 값으로 나온다.
    //
    // 최댓값은 안 내려간다. 매번 덮어쓰면 방금 꺼낸 것의 값이 되어 아무 뜻이 없어진다.
}
```

- 항목마다 시각을 들고 있지 않고 큐 전체에 하나만 두면 측정이 어떻게 틀리는가?
- `maxWaitMillis` 를 매번 덮어쓰면 그 값은 무슨 뜻이 되는가?
- 최댓값과 마지막 값 두 개를 같이 들고 있는 이유는?
- 빈 큐에서 `poll` 할 때 대기 시간을 건드리지 않아야 하는 이유는?

#### 3. BoundedChannel.offer — 이 상자의 본체 (TODO 3)

```java
@Override
public boolean offer(T item) throws InterruptedException {
    UnboundedChannel.requireItem(item);
    synchronized (this) {
        // TODO 3: 자리가 있으면 넣고, 없으면 정책대로 한다. 이 상자의 본체다.
        //
        // 정원 판정의 부등호를 조심하라. 한 칸 넘치면 정원이 아니게 되고,
        // 그 한 칸은 DROP 정책에서는 티가 안 난다.
        //
        //   DROP_NEWEST   새 것을 안 넣는다. **반환값이 false** 다
        //   DROP_OLDEST   머리를 버리고 꼬리에 넣는다. **반환값이 true** 다
        //   FAIL          던진다. 버리는 것과 다르다. 생산자가 알고 고를 수 있다
        //   BLOCK         자리가 날 때까지 기다린다
        //
        // BLOCK 에서 wait 를 쓸 때 **if 가 아니라 while** 이다.
        //
        // 막힌 시간을 재라. 그 수가 0 이 아니면 생산자가 소비자에게 끌려가고 있다는 뜻이다.
    }
}
```

- 정원 판정의 부등호가 한 칸 틀리면 왜 DROP 정책에서는 티가 안 나는가?
- DROP_OLDEST 만 반환값이 true 인 이유는?
- 그 true 가 "이 상자에서 제일 조용한 사고"인 이유와, 무엇을 같이 봐야 알 수 있는가?
- DROP_OLDEST 를 쓰면 안 되는 데이터와 맞는 데이터는 각각 무엇인가?
- DROP_NEWEST 와 DROP_OLDEST 는 각각 무엇을 지키려고 무엇을 버리는가?
- `wait` 를 `if` 로 쓰면 정확히 어떤 상태가 되는가?
- 깨어났는데 자리가 없는 경우가 생기는 두 가지 이유는?
- `wait()` 가 `synchronized` 안에 있는데도 소비자가 `poll` 할 수 있는 이유는?
- 막힌 시간(`blockedMillis`)이 "백프레셔가 실제로 돌고 있다는 유일한 증거"인 이유는?
- BLOCK 에서 대기 시작 시각을 wait 전에 찍고 끝나고 더하는 이유는?

#### 4. BoundedChannel.poll — 자리가 났다고 알린다 (TODO 4)

```java
@Override
public synchronized Optional<T> poll() {
    // TODO 4: 하나 꺼내고, 기다린 시간을 기록하고, **자리가 났다고 알린다.**
    //
    // 알리는 것을 빼먹으면 BLOCK 정책의 생산자가 영원히 안 깨어난다.
    // 다른 세 정책에서는 아무 일도 안 일어나므로 **네 정책 중 셋은 그대로 통과한다.**
}
```

- `notifyAll` 을 빼먹으면 BLOCK 생산자에게 무슨 일이 생기는가?
- 그 결함이 테스트 셋을 통과하는 이유는?
- "테스트 대부분이 통과한다"가 결함의 위험도에 대해 말해주는 것은?
- `notify` 가 아니라 `notifyAll` 인 편이 안전한 이유는? (원본에 근거 없음 — 내 추론)
- 소비자가 producer 를 깨우는 이 구조가 "백프레셔"라는 이름과 어떻게 맞아떨어지는가?
