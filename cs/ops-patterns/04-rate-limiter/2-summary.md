## 해결하는 문제

서버의 용량은 유한한데, 부르는 쪽은 그 사실을 모른다.\
"단위 시간당 N개까지"를 세는 장치가 없으면 두 가지가 안 된다.

```text
제한 없음:   사용자 A 초당 10,000회 --> 서버 용량 소진 --> 사용자 B·C·D 전부 느려짐   (보호 실패)
             무료 요금제가 유료 요금제의 용량을 먹음                                  (공정성 실패)
제한 있음:   A 는 100회에서 429 --> 나머지 9,900회는 리미터에서 거절돼 비즈니스 로직·DB에 닿지 않음 --> B·C·D 무사
```

쉬운 예: 놀이공원 입장 제한 — "시간당 100명"이라고 정해도 매시 정각에 계수기를 0으로 하는지, 입장 시각을 전부 적는지, 입장권을 미리 나눠 주는지에 따라 실제로 들어가는 사람 수가 다르다.\
똑같은 구조다: 세는 방법 다섯이 정확도·메모리·몰림 허용 중 무엇을 살지가 다를 뿐, 계약(`tryAcquire`)은 하나다.\
실무 예: 공개 API의 `429 Too Many Requests`, 로그인 시도 제한, 요금제별 쿼터, 크롤러 차단.

  - *429*: "너무 많이 보냈다"는 HTTP 응답 코드(RFC 6585). 리미터가 거절할 때의 표준 답이다.

### 한눈에 — 쉽게 말하면
**레이트 리미터 = 놀이공원 입장 제한.**\
"시간당 100명까지"를 어떻게 셀 것인가가 문제의 전부다.

> **레이트 리미터(rate limiter)** — 단위 시간당 받아주는 요청 수에 상한을 거는 장치.\
> 예: API 의 429 Too Many Requests 가 이 장치의 응답이다.

- 01번은 **우리가 상대를 때리는 속도**, 02번은 **상대가 죽었을 때 멈추는 법**이었다.\
  여기는 방향이 반대다 — **남이 우리를 때리는 속도**를 제한한다.
- 왜 필요한가: 용량은 유한하다.\
  한 사용자가 초당 1만 번 부르면 나머지 전부가 느려진다.\
  그리고 **공정성** — 무료 요금제가 유료 요금제의 용량을 먹으면 안 된다.
- "시간당 100명"도 세는 방법이 여럿이다: 매시 정각에 계수기를 0으로(고정 창), 입장 시각을 전부 적기(로그), 토큰을 나눠주기(토큰 버킷)…
- 구현 다섯이 각각 **다른 것을 판다** — 정확도·메모리·몰림 허용 셋 중 무엇을 살 것인가가 이 문제의 전부다.

> **몰림(burst)** — 짧은 순간에 요청이 한꺼번에 오는 것.\
> 예: 실제 트래픽의 기본 모양이다 — 페이지 하나를 열면 호출 20개가 동시에 나간다.

```text
고정 창       가장 단순. 창 경계에서 2배가 통과한다
슬라이딩 로그  정확. 요청 시각을 전부 기억한다 (메모리 = 요청 수)
슬라이딩 카운터 근사. 메모리 상수 (저장 항목 2개)
토큰 버킷      몰림(burst)을 허용한다
누출 버킷      출력을 고르게 만든다. 몰림을 흡수하지 않는다
```

실무 예: API의 429 Too Many Requests, nginx limit_req, 요금제별 쿼터.

## 동작·원리

### 전체 흐름
```text
RateLimiter 계약: tryAcquire(permits) — 전부 되거나 전부 안 되거나, 절대 기다리지 않는다
                  availableTokens()  — 1 이상이면 반드시 통과, 0이면 반드시 거절
                  storedEntries()    — 메모리를 숫자로 본다
        │
AbstractRateLimiter (공통 뼈대)
  ├─ permits <= 0 도 거절로 센다 — 통계에서 조용히 사라지면 호출자 버그가 영원히 안 보인다
  ├─ now(): 뒤로 가지 않는 지금 — 시계가 되감기면(NTP·컨테이너 이주) 마지막 시각을 그대로 준다
  └─ allowed / rejected / clockRewinds 계측
        │
  다섯 구현이 doTryAcquire 만 채운다
```

### 동작 — 고정 창 (FixedWindowLimiter)
**언제 쓰나**: 제일 단순한 게 필요할 때, 특히 분산 환경(레디스 `INCR` 한 번이면 된다).

> **고정 창(fixed window)** — 절대 시각으로 자른 구간마다 계수기를 0으로 되돌리는 방식.\
> 예: 경계에서 2배가 샌다.

전 상태 — 한도 100 / 창 1000ms:

```text
|-- 창 0 (0~999ms) --|-- 창 1 (1000~1999ms) --|
      count=?                count=0 부터 다시
```

단계: 지금이 몇 번째 창인지 `floorDiv(now, windowMillis)`로 구하고 → 창이 바뀌었으면 count=0 → `count + permits > limit`이면 거절, 아니면 더한다.\
저장 항목 **1개**.

**실패 시나리오 — 경계 2배 (이 문제의 요점)**: t=999에 100개, t=1001에 100개 — 2ms 사이에 **200개가 전부 통과한다.**\
창이 바뀌는 순간 계수기가 0이 되기 때문이다.\
고칠 수 있는 버그가 아니라 "창을 절대 시각으로 자른다"는 **선택의 결과**고, 모두가 같은 벽시계를 보니 경계도 모두에게 같은 순간이다(01번 지수 백오프의 동기화와 같은 구조).

> **창 경계 문제(boundary problem)** — 고정 창이 바뀌는 순간 직전+직후로 한도의 2배가 통과하는 현상.\
> 예: t=999 에 100개, t=1001 에 100개가 2ms 사이에 전부 통과한다.

### 동작 — 슬라이딩 로그 (SlidingLogLimiter)
**언제 쓰나**: 정확도가 최우선일 때(과금·보안 한도).

> **슬라이딩 로그(sliding log)** — 요청 시각을 전부 기록해 "지금부터 T 전"을 정확히 세는 방식.\
> 예: 메모리가 요청 수에 비례한다.

단계: 요청 시각을 Deque에 전부 적는다 → 매 요청마다 창(1000ms) 밖으로 나간 시각을 앞에서부터 버린다 → `log.size() + permits > limit`이면 거절, 아니면 시각을 적는다.

- 경계 문제 없음: "지금부터 1초 전"을 항상 정확히 본다 → t=1001에서는 t=999의 100개가 아직 창 안이라 0개 통과.

**비용**: **요청 하나마다 시각 하나.**\
초당 10만이면 항목 10만 — 그게 사용자 하나당이다.\
사용자 100만이면 리미터가 서비스보다 크다.\
그리고 함정: **거절한 요청까지 기록하면** 막으려고 만든 것이 공격 수단이 된다(공격자가 로그를 무한히 키운다).

### 동작 — 슬라이딩 카운터 (SlidingWindowCounterLimiter)
**언제 쓰나**: 로그의 정확도는 못 사지만 고정 창의 경계 구멍은 막고 싶을 때.

> **슬라이딩 카운터(sliding window counter)** — 이전 창 count 를 남은 비율만큼 섞어 근사하는 방식.\
> 예: 저장 항목이 2개뿐이다.

단계: 창 두 개(이전 count, 현재 count)만 기억 → 추정치 = `이전 count × (창에서 아직 안 지난 비율) + 현재 count` → 추정치 + permits가 한도를 넘으면 거절.\
저장 항목 **2개**.

```text
     |---- 이전 창 (100개) ----|---- 현재 창 ----|
                                   ^ now (30% 지남)
     추정 = 100 × 0.7 + 현재 count   ← "이전 창이 고르게 왔다"고 가정하는 근사
```

**한계 — 양쪽으로 틀린다**: 경계에서 1개를 더 흘리고(101), 부하가 이전 창 앞쪽에 몰려 있었으면 최근 1초가 비었는데도 10개를 막는다.

### 동작 — 토큰 버킷 (TokenBucketLimiter)
**언제 쓰나**: 순간 몰림을 허용하고 싶을 때 — 실제 트래픽은 고르지 않다.\
페이지 하나 열면 호출 20개가 동시에 나가고 30초를 쉰다.\
평균으론 한가한데 고정 창은 그 20개 중 뒤쪽을 자른다.\
**버킷 크기 b가 정책이다.**

> **토큰 버킷(token bucket)** — 시간이 토큰을 채우고 요청이 토큰을 쓴다.\
> 예: 모아둔 토큰만큼 몰림을 허용한다.

전 상태 — 용량 100, 초당 10 충전:

```text
버킷 [●●●●●●●●●●] 가득(100)      요청 = 토큰 소비, 시간 = 토큰 충전(상한까지)
```

단계: 매 호출마다 지난 시간 × 충전 속도만큼 채우고(상한 캡) → 토큰이 permits만큼 있으면 빼고 통과, 없으면 거절.\
토큰은 1/1000 단위 **정수**(SCALE)로 센다 — 01번 RetryBudget과 같은 자리다.

> **정수 스케일(SCALE)** — 토큰을 1/1000 단위 정수로 세는 기법.\
> 예: double 오차와 정수 나눗셈 절단을 피한다.

**비용**: 버킷에 모인 100개가 **같은 밀리초에 나간다** — 몰림이 상대에게 그대로 간다.

### 동작 — 누출 버킷 (LeakyBucketLimiter)
**언제 쓰나**: 뒷단(DB, 외부 API)에 **고른 속도**로만 흘려보내야 할 때.

> **누출 버킷(leaky bucket)** — 요청을 줄 세우고 일정 속도로만 내보낸다.\
> 예: 몰림을 지연으로 바꾼다.

```text
         요청들 → [ 버킷(대기줄, 용량 100) ] → 초당 10개씩 일정하게 똑똑 떨어짐
```

단계: 지난 시간만큼 줄이 줄어들고(leak) → 줄 + permits가 용량을 넘으면 거절, 아니면 줄에 선다 → 실제로 나가는 시각은 줄 길이만큼 뒤로 밀린다(`lastExitMillis`).

- 토큰 버킷과의 차이 전부: 토큰 버킷은 **통과시키는 순간 나가고**, 누출 버킷은 받아주기만 하고 **나가는 시각은 줄 뒤로 민다.**

**비용**: 같은 100개를 10초에 걸쳐 내보내 붐비는 1초가 100 대 10(BurstShapeTest) — 대신 **100번째 요청은 10초를 기다린다.**\
몰림을 지연으로 바꾼 것이다.

## 쓰이는 자료구조·알고리즘

- **토큰 버킷(token bucket)** — 시간이 채우고 요청이 쓴다. 네트워크 장비의 트래픽 셰이핑이 원형이고, Guava `RateLimiter`(SmoothBursty — 쉬는 동안 허가를 쌓아 둔다)가 이 모양이다.\
  Resilience4j `RateLimiter`는 다르다 — `limitRefreshPeriod`마다 허가 수를 `limitForPeriod`로 다시 채우는 주기 재충전이라 고정 창 계열에 가깝다.\
  [01-retry-backoff](../01-retry-backoff/2-summary.md)의 `RetryBudget`은 "요청이 채우고 재시도가 쓰는" 토큰 버킷이다.
- **누출 버킷(leaky bucket)** — 줄을 세우고 일정 속도로 내보낸다. nginx의 `limit_req`가 이 방식이다(nginx 문서: "leaky bucket" 방식).
- **덱(Deque)** — 슬라이딩 로그. 앞에서 오래된 시각을 버리고 뒤에 새 시각을 붙인다. [data-structure/04-queue-deque](../../data-structure/04-queue-deque/2-summary.md).
- **`floorDiv` 창 번호** — 고정 창·슬라이딩 카운터. [02-circuit-breaker](../02-circuit-breaker/2-summary.md)의 `TimeBasedWindow`가 같은 산수로 다른 것을 센다.
- **가중 평균 근사** — 슬라이딩 카운터의 `이전 × (1 - 지난 비율) + 현재`. 계수기 둘로 창 하나를 흉내 낸다.
- **슬라이딩 윈도우** — 알고리즘 쪽 원형은 [algorithm/09-sliding-window](../../algorithm/09-sliding-window/2-summary.md).
- **정수 스케일 · `Math.multiplyExact`** — 나눗셈 절단과 곱셈 오버플로 방어. 01의 `tokensScaled`와 같은 자리.
- 분산 환경 — Redis `INCR` + `EXPIRE`(고정 창이 살아남는 이유), Lua 스크립트로 토큰 버킷의 "읽고-계산하고-쓰기"를 원자화(Redis는 스크립트 하나를 다른 명령과 섞지 않고 원자적으로 실행한다 — Redis EVAL 문서).

## 적용 — 풀어나가는 법

### 문제 — 이 챕터가 시키는 것
용량은 유한한데 한 사용자가 초당 1만 번 부르면 나머지 전부가 느려진다.\
**"단위 시간당 N개까지"를 세는 다섯 가지 방법을 직접 구현하고, 각 방법이 무엇을 팔고 무엇을 사는지(정확도·메모리·몰림 허용)를 숫자로 확인하라**는 챕터다.\
계약은 하나(`tryAcquire`)이고 다섯 구현이 `doTryAcquire`만 다르게 채운다.

> **허가(permit)** — 요청 하나가 소비하는 단위.\
> 예: `tryAcquire(n)` 은 전부 되거나 전부 안 되거나다.

과제(원본 README "하는 방법"):

1. `AbstractRateLimiter` 의 **TODO 1** — `now()`: 뒤로 가지 않는 지금(시계 되감김 방어 + `clockRewinds` 계측).\
   이 상자에서 제일 짧고 제일 많은 것을 막는 코드다.

> **시계 되감김(clock rewind)** — NTP 보정·컨테이너 이주로 시각이 뒤로 가는 것.\
> 예: `now()` 한 곳에서 막는다.

2. `FixedWindowLimiter` **2개** — `rollTo`(창 번호 `floorDiv`, 바뀌면 계수기 0) · `doTryAcquire`(`count + permits > limit` 이면 거절).
3. `SlidingLogLimiter` **2개** — `prune`(창 밖 시각 앞에서부터 버리기, 경계 `>=`) · `doTryAcquire`(통과 시 permits 개의 시각을 담고, **거절한 요청은 담지 않는다**).
4. `SlidingWindowCounterLimiter` **3개** — `roll`(바로 다음 창 / 더 건너뛴 창 구분) · `estimate`(가중 추정치, **곱하기가 먼저**) · `doTryAcquire`.
5. `TokenBucketLimiter` **2개** — `refill`(상한 넘지 않게 충전, 곱하기 전에 넘칠지 검사) · `doTryAcquire`(부분 소비 없음).
6. `LeakyBucketLimiter` **2개** — `leak`(0 아래로 안 내려가게) · `doTryAcquire`(자리 있으면 세우고 **나가는 시각**을 줄 뒤로 민다).

시작점: `cd ~/project/myway/ops-patterns && ./run.sh 04` — 129개 중 110개가 실패하는 상태에서 출발한다(통과하는 19개는 미리 채워둔 생성자 검사·설정 접근자·`permits <= 0` 거절만 보는 테스트다).

①이 틀리면 ②~⑤가 성실히 엉뚱한 것을 제한한다. 위 「문제」절의 TODO는 ③의 다섯 구현을 공통 뼈대(`now()`)부터 만든다.

### 측정 — 다섯 구현 비교
경계 측정(WindowBoundaryTest) — 한도 1000ms에 100개, **t=999에 100개 + t=1001에 100개**:

```text
              t=999   t=1001   합계   저장 항목
고정 창        100     100     200      1     ← 2ms 안에 제한의 2배
슬라이딩 로그   100       0     100    100
슬라이딩 카운터 100       1     101      2
토큰 버킷      100       0     100      1
누출 버킷      100       0     100      1
```

지속 부하(SustainedLoadTest) — 어떤 1000ms 구간의 최대 통과량: 로그 100, 카운터 101, 고정 창 104, **버킷 둘은 199.** **"한도 100"이라는 말이 구현마다 다른 뜻이다** — 버킷의 진짜 상한은 용량 + 충전량이다.

메모리(MemoryFootprintTest): 저장 항목 1, **1000**, 2, 1, 1 — 로그만 요청 수에 비례한다.

**공통 함정들**:

- **정수 나눗셈 순서 하나로 리미터가 통째로 꺼진다** — 토큰 충전·가중 평균 두 곳.\
  `elapsed * rate / 1000`을 `elapsed / 1000 * rate`로 쓰면 1초 미만이 전부 0이 된다.
- **곱하기 전에 넘칠지 검사한다**(`Math.multiplyExact`) — 넘친 long은 음수고, 음수는 상한 검사를 그냥 통과한다.

> **오버플로(overflow)** — 곱셈이 long 범위를 넘어 음수가 되는 것.\
> 예: 음수는 상한 검사를 통과해버린다.

- **시계는 뒤로 간다**(NTP 보정, 컨테이너 이주) — 구현마다 다른 방식으로 깨지므로 방어는 `AbstractRateLimiter.now()` **한 곳**이다.\
  시계 문제는 시계 경계에서 막는다.
- **조회가 상태를 바꾼다** — 창 만료와 토큰 충전이 availableTokens()에서 일어난다(02 브레이커의 OPEN 판정과 같은 성질).
- **전부 프로세스 안의 상태다** — 서버 20대면 한도가 20배(02와 같은 한계).
- 변종 검증 24개 중 4개가 안 잡혔다 — 동치 변환 1개 + `now()` 되감김 방어와 겹친 방어선 3개.\
  넷 다 지워도 테스트는 통과한다.

## 장애 시나리오와 대처

위 「측정」절의 산수 함정(정수 나눗셈·오버플로·시계 되감김)과 프로세스별 상태 말고, 운영에서 따로 보이는 장애들이다.

**1. 분산 카운터의 틈으로 한도가 샌다**

- 현상: 서버 20대가 Redis 카운터 하나를 보게 옮겼는데, 한도 100인 사용자가 110~120회를 통과한다.
- 보이는 형태: Redis의 count 값이 limit을 넘어 있다. 부하가 높을수록 초과분이 는다.
- 원인: "읽고(GET) → 비교하고 → 올리기(INCR)"가 세 단계라, 두 서버가 같은 값을 읽고 둘 다 통과시킨다.\
  [06-idempotency-store](../06-idempotency-store/2-summary.md)의 get-후-put과 같은 모양의 TOCTOU다.
  - *TOCTOU*: 검사한 시점과 실행한 시점 사이에 세상이 바뀌는 결함.
- 대처: 먼저 `INCR`하고 **돌아온 값으로** 판정한다(원자 연산 하나). 토큰 버킷처럼 계산이 끼면 Lua 스크립트로 읽기-계산-쓰기를 한 덩어리로 만든다.

**2. IP로 세서 회사 하나가 통째로 막힌다**

- 현상: 특정 회사 사용자 수백 명이 동시에 429를 받는다. 지원 문의 "회사에서만 안 돼요".
- 보이는 형태: 429가 한 IP에 집중되고, 그 IP 뒤에 서로 다른 계정 수백 개가 있다.
- 원인: 제한 키를 IP로 잡았다. 회사·학교는 NAT 뒤에서 IP 하나를 공유한다.
  - *NAT*: 여러 기기가 공인 IP 하나를 나눠 쓰게 하는 주소 변환.
- 대처: 인증된 요청은 사용자·API 키·테넌트 단위로 센다. IP 한도는 미인증 요청 보호용으로 따로, 넉넉하게 둔다.

**3. 거절이 재시도를 부른다**

- 현상: 리미터를 켰더니 요청 수가 줄지 않고 오히려 는다. 429 비율이 90%를 넘는다.
- 보이는 형태: 같은 클라이언트가 429를 받자마자 즉시 다시 보낸다. 거절 처리에 CPU를 쓴다.
- 원인: 429에 "언제 다시 오라"가 없다. 클라이언트는 실패를 일시 실패로 보고 즉시 재시도한다 — 01의 재시도 폭풍이 리미터 앞에서 난다.
- 대처: `Retry-After` 헤더로 다음 창까지의 시간을 알려주고, 클라이언트 SDK에 지터 있는 백오프를 넣는다. 반복 위반자는 더 긴 차단으로 승격한다.

## 핵심 문장

- 레이트 리미터는 "남이 우리를 때리는 속도"를 제한하고, 구현 다섯은 **정확도·메모리·몰림 허용 중 무엇을 살 것인가**가 갈릴 뿐 계약은 같다.
- 고정 창의 경계 2배는 버그가 아니라 **절대 시각으로 창을 자른다는 선택의 결과**다 — 고치면 다른 알고리즘이고, 그래도 살아남는 이유는 레디스 INCR 한 번으로 분산까지 가기 때문이다.
- **"한도 100"은 구현마다 다른 뜻이다** — 지속 부하에서 버킷 둘은 한 구간에 199까지 통과시킨다(용량 + 충전량).
- 토큰 버킷은 몰림을 **통과**시키고, 누출 버킷은 몰림을 **지연으로 바꾼다** — 붐비는 1초가 100 대 10이지만 100번째 요청은 10초를 기다린다.
- 정수 나눗셈 순서·곱셈 오버플로·시계 되감김 — 세 가지 산수 함정이 리미터를 조용히 끄고, 방어는 각각 한 곳에 둔다.

### 용어 풀이
- **레이트 리미터(rate limiter)**: 단위 시간당 받아주는 요청 수에 상한을 거는 장치.
- **허가(permit)**: 요청 하나가 소비하는 단위.\
  tryAcquire(n)은 전부 되거나 전부 안 되거나다.
- **고정 창(fixed window)**: 절대 시각으로 자른 구간마다 계수기를 0으로 되돌리는 방식.\
  경계에서 2배가 샌다.
- **슬라이딩 로그(sliding log)**: 요청 시각을 전부 기록해 "지금부터 T 전"을 정확히 세는 방식.\
  메모리가 요청 수에 비례.
- **슬라이딩 카운터(sliding window counter)**: 이전 창 count를 남은 비율만큼 섞어 근사하는 방식.\
  저장 항목 2개.
- **토큰 버킷(token bucket)**: 시간이 토큰을 채우고 요청이 토큰을 쓴다.\
  모아둔 토큰만큼 몰림을 허용.
- **누출 버킷(leaky bucket)**: 요청을 줄 세우고 일정 속도로만 내보낸다.\
  몰림을 지연으로 바꾼다.
- **몰림(burst)**: 짧은 순간에 요청이 한꺼번에 오는 것.\
  실제 트래픽의 기본 모양.
- **창 경계 문제(boundary problem)**: 고정 창이 바뀌는 순간 직전+직후로 한도의 2배가 통과하는 현상.
- **시계 되감김(clock rewind)**: NTP 보정·컨테이너 이주로 시각이 뒤로 가는 것.\
  now() 한 곳에서 막는다.
- **오버플로(overflow)**: 곱셈이 long 범위를 넘어 음수가 되는 것.\
  음수는 상한 검사를 통과해버린다.
- **정수 스케일(SCALE)**: 토큰을 1/1000 단위 정수로 세는 기법.\
  double 오차와 정수 나눗셈 절단을 피한다.
