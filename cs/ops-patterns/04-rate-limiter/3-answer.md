### A. 문제 (구현 대상 TODO)

#### 1. AbstractRateLimiter.now — 뒤로 가지 않는 지금

```java
// impl 정답
protected final long now() {
    long t = ticker.nowMillis();
    if (t < lastNowMillis) {
        clockRewinds++;
        return lastNowMillis;   // 되감긴 동안은 마지막 시각에 머문다
    }
    lastNowMillis = t;
    return t;
}
```

- Q: 시계 방어를 다섯 구현에 각자 넣지 않고 이 한 곳에 모은 이유는?
  A: 다섯 군데에 흩어놓으면 다섯 번 틀린다.
  게다가 되감김의 증상이 구현마다 달라서(창이 새로 열리거나, 토큰이 생기거나, 한도가 줄거나) 각자 방어하면 각자 다른 버그가 남는다.
  시계 문제는 시계 경계 한 곳에서 막는다 — 그래서 `tryAcquire` 가 final 이고 하위 구현은 `now()` 를 통해서만 시각을 본다.

- Q: 시계가 뒤로 갔을 때 고정 창·슬라이딩 카운터에서는 무엇이 조용히 두 배가 되는가?
  A: 창 번호가 바뀌어 **창이 통째로 새로 열린다** — 계수기가 0이 되므로 같은 1초에 한도가 두 배 통과한다.
  예외도 로그도 안 남는다. 고정 창의 경계 2배와 같은 증상이 시각과 무관하게 아무 때나 생기는 셈이다.

- Q: 같은 일이 토큰 버킷에서는 어떻게 나타나는가(두 가지 경로)?
  A: 경과 시간이 음수가 되는데, ① 순진하게 `tokensScaled += elapsed * rate` 를 하면 토큰이 **줄어들고**(멀쩡한 클라이언트가 막힌다), ② 검사만 하고 `lastRefillMillis` 를 옮겨두면 다음 호출에서 거대한 경과 시간을 보고 **무에서 토큰이 생긴다**(한도가 사라진다).
  방향이 반대인 두 사고가 같은 원인에서 나온다.

- Q: 슬라이딩 로그에서는 왜 반대로 한도가 줄어드는가?
  A: 덱에 담기는 시각의 오름차순 전제가 깨지기 때문이다.
  `prune` 은 맨 앞이 창 안이면 멈추는데, 앞에 더 옛날 것이 아니라 더 최근 것이 있으면 뒤에 남은 옛 기록을 영영 못 버린다.
  로그가 안 비워지니 한도가 조용히 줄어든다.

- Q: 막기만 하지 않고 `clockRewinds` 를 세는 이유는?
  A: 조용히 버티기만 하면 시계가 망가진 것을 아무도 모르기 때문이다.
  방어는 "막고 끝"이 아니라 밖에서 볼 수 있게 남기는 것까지다 — 운영에서 이 값이 0이 아니면 시계를 의심해야 한다.

- Q: "영원히 막으면 그것도 장애다"는 무슨 상황을 말하는가?
  A: 되감긴 시계가 원래 시각을 따라잡은 뒤에도 계속 옛 시각을 주면 리미터가 시간이 멈춘 상태로 굳는다.
  그래서 `t < lastNowMillis` 일 때만 막고, 따라잡아 다시 커지는 순간 정상으로 돌아온다.
  `ContractTest.recoversAfterRewind` 가 그것을 본다.

- Q: `tryAcquire` 를 final 로 막고 하위 구현에 `doTryAcquire` 만 채우게 한 이유는?
  A: 통계를 각자 세게 두면 어떤 구현은 `permits <= 0` 을 세고 어떤 구현은 안 세는 차이가 생긴다.
  그런 차이는 장애 분석 중에 대시보드를 못 믿게 만든다 — 계측은 한 곳에서 한 방식으로.

- Q: `permits <= 0` 을 조용히 무시하지 않고 거절로 세는 이유는?
  A: 통계에서 조용히 사라지면 호출자 버그(0이나 음수를 넘기는 코드)가 영원히 안 보인다.
  거절로 세어두면 "거절은 느는데 트래픽은 그대로"라는 신호로 드러난다.

#### 2. FixedWindowLimiter — 창마다 계수기 하나

```java
// impl 정답
private void rollTo(long now) {
    long epoch = Math.floorDiv(now, windowMillis);
    if (epoch != currentEpoch) {
        currentEpoch = epoch;
        count = 0;
    }
}

@Override
protected boolean doTryAcquire(int permits) {
    long now = now();
    rollTo(now);
    if (count + permits > limit) {
        return false;      // 거절할 때 count 는 건드리지 않는다
    }
    count += permits;
    return true;
}
```

- Q: 창 번호를 `/` 대신 `Math.floorDiv` 로 구하는 이유는(0 을 걸치는 창에 무슨 일이 생기는가)?
  A: 자바의 `/` 는 0 쪽으로 자르기 때문에 -500/1000 과 500/1000 이 둘 다 0이다.
  그러면 0을 걸치는 창 하나만 두 배로 넓어지고 그 창에서만 한도가 두 배가 된다.
  Ticker 의 원점은 임의이고 `System.nanoTime` 은 실제로 음수를 준다.

- Q: 이 계산이 02번의 어느 코드와 똑같은 자리인가?
  A: 02번 `TimeBasedWindow` 의 버킷 계산(`epochAt` 의 floorDiv, 칸 계산의 floorMod)과 같은 자리다.
  "시간을 일정 길이로 잘라 번호를 매긴다"는 계산이 나오면 늘 같은 함정이 따라온다.

- Q: 창 비교를 `!=` 대신 `>` 로 써도 테스트가 통과하는 이유는, 그런데도 `!=` 로 두는 이유는?
  A: `now()` 가 시각을 뒤로 못 가게 막고 있어서 창 번호도 줄지 않기 때문이다(변종 검증 M05 — 안 잡힌 넷 중 하나).
  두 방어가 겹친 자리이고, 겹친다고 지우지 않는다 — `now()` 를 안 거치는 구현으로 바뀌는 순간 여기가 유일한 방어선이 된다.

- Q: 한도 검사를 `>=` 로 쓰면 몇 개가 어디로 사라지는가?
  A: 한도 100이면 99개만 통과하고 100번째 하나가 사라진다.
  1%의 요청이 이유 없이 429를 받는데, 그 1개는 아무도 못 찾는다.
  경계는 한쪽으로 정하고 테스트로 못 박는다.

- Q: 거절할 때 count 를 먼저 더하고 나중에 되돌리면 무엇이 새는가(01번의 무엇과 같은 함정인가)?
  A: 되돌리기를 한 경로라도 빠뜨리면 거절한 요청이 창을 채워, 한 번 막힌 클라이언트가 창 내내 못 들어온다.
  01번 `RetryBudget.tryRetry` 와 같은 함정이다 — 빼고 나서 음수인지 보면 거절한 뒤에도 예산이 조용히 새어나간다.
  먼저 확인하고 나중에 더하면 되돌릴 일이 없다.

- Q: `availableTokens()` 가 읽기인데도 `rollTo` 를 부르는 이유는?
  A: 굴리지 않으면 트래픽이 끊긴 순간 상태가 얼어붙어 "왜 막혀 있느냐"는 질문에 10분 전 답을 준다.
  02번 `TimeBasedWindow` 가 조회에서도 `expire` 를 부른 것과 같다 — 읽기처럼 생긴 것이 쓰기다.

- Q: 저장 항목이 1개뿐이라는 성질이 분산 환경에서 무엇을 가능하게 하는가?
  A: 계수기 하나면 되니까 레디스 `INCR` 한 번으로 여러 서버가 한도를 공유할 수 있다.
  나머지 넷은 그렇게 안 된다 — 경계 2배라는 결함을 안고도 고정 창이 살아남는 이유가 이것이다.

#### 3. SlidingLogLimiter — 시각을 전부 담는다

```java
// impl 정답
private void prune(long now) {
    while (!log.isEmpty() && now - log.peekFirst() >= windowMillis) {
        log.pollFirst();
    }
}

@Override
protected boolean doTryAcquire(int permits) {
    long now = now();
    prune(now);
    if (log.size() + permits > limit) {
        return false;              // 거절한 요청은 담지 않는다
    }
    for (int i = 0; i < permits; i++) {
        log.addLast(now);          // permits 개를 담는다
    }
    return true;
}
```

- Q: 이 구현에 창 경계 문제가 아예 없는 이유는?
  A: 창이 절대 시각으로 잘려 있지 않고 요청마다 따라 움직이기 때문이다 — "지금부터 1000ms 전"을 매번 다시 본다.
  그래서 고정 창이 200을 흘리는 시나리오(t=999 / t=1001)에서 이쪽은 100만 통과시킨다.
  근사도 없고 경계도 없다 — 정의 그대로다.

- Q: 만료 판정이 `>` 가 아니라 `>=` 인 이유는(02번의 어디서 똑같이 따졌는가)?
  A: 창 길이가 1000이고 기록이 정확히 1000ms 전이면 이미 창 밖이기 때문이다.
  `>` 로 쓰면 창이 1ms 길어지고 그 1ms 는 아무도 안 본다.
  02번 `TimeBasedWindow.expire` 에서 똑같이 따졌던 자리다.

- Q: 맨 앞에서 창 안을 만나면 멈춰도 되는 근거는 무엇이고, 그 전제를 누가 지켜주는가?
  A: 담기는 시각이 오름차순이라는 전제 — 맨 앞이 창 안이면 뒤는 전부 창 안이다.
  전부 훑으면 요청마다 O(n)이 된다.
  그 전제를 지켜주는 것이 `now()` 다(뒤로 가지 않으므로 담기는 값이 줄지 않는다).

- Q: 허가 5개를 받아준 요청이 시각 하나가 아니라 다섯 개를 담아야 하는 이유는?
  A: 로그의 크기가 곧 "창 안에서 소비된 허가 수"이기 때문이다.
  하나만 담으면 5칸을 쓰고 1칸만 기록한 것이라 다음 판정이 4개만큼 헐거워진다.

- Q: 거절한 요청을 담으면 동시에 망가지는 두 가지는 무엇인가?
  A: ① 거절이 다음 요청까지 밀어내서 한 번 막히면 창 내내 못 들어온다.
  ② 공격자가 거절당하는 요청만 쏟아부어 메모리를 무제한으로 늘린다 — **막으려고 만든 것이 공격 수단이 된다.**

- Q: 이 구현이 맞는 자리와 절대 쓰면 안 되는 자리는 각각 어디인가?
  A: 맞는 자리 — 한도가 작고(초당 5회) 정확도가 돈인 곳: 로그인 시도, 비싼 외부 API 호출.
  안 되는 자리 — 초당 10만을 받는 공용 엔드포인트. 항목 10만 개가 사용자 **하나당**이라 사용자 100만이면 리미터가 서비스보다 크다.

- Q: 덱(Deque)을 고른 이유는 무엇이고, 그 선택의 전제는 무엇인가?
  A: 앞에서 버리고 뒤에 넣기 때문이다 — 양끝 연산이 O(1)이어야 한다.
  전제는 담기는 시각이 오름차순이라는 것이고, 그 전제가 깨지면 자료구조 선택 자체가 무너진다.

#### 4. SlidingWindowCounterLimiter — 계수기 둘로 근사

```java
// impl 정답
private void roll(long now) {
    long epoch = Math.floorDiv(now, windowMillis);
    if (epoch == currentEpoch) {
        return;
    }
    previousCount = (epoch == currentEpoch + 1) ? currentCount : 0;   // 멀면 둘 다 버린다
    currentCount = 0;
    currentEpoch = epoch;
}

private long estimate(long now) {
    roll(now);
    long elapsed = Math.floorMod(now, windowMillis);
    return previousCount * (windowMillis - elapsed) / windowMillis + currentCount;
}

@Override
protected boolean doTryAcquire(int permits) {
    long now = now();
    if (estimate(now) + permits > limit) {
        return false;
    }
    currentCount += permits;
    return true;
}
```

- Q: "바로 다음 창"과 "더 건너뛴 창"을 구분하지 않으면 어떤 증상이 나타나고, 왜 재현이 안 되는가?
  A: 3초 전 창을 "이전 창"으로 쓰면 이미 지나간 부하로 지금을 막는다.
  트래픽이 뜸한 서비스에서 "가끔 아무 이유 없이 429"로 나타나는데, 뜸하게 들어오는 타이밍에서만 생기므로 재현이 안 돼 아무도 못 잡는다.
  "이전 창"은 정말 직전 창일 때만 뜻이 있다.

- Q: 추정식에서 괄호를 `previousCount * ((window - elapsed) / window)` 로 묶으면 이 클래스는 무엇이 되는가?
  A: 괄호 안이 정수 나눗셈이라 창 안에서는 늘 0이고, 이전 창이 통째로 사라진다.
  추정치 = currentCount 가 되어 **고정 창과 똑같아진다** — 이름만 슬라이딩인 채로.
  경계 2배 구멍이 그대로 돌아오는데 테스트 말고는 아무도 모른다.

- Q: 그 사고를 04번의 다른 어느 구현에서 한 번 더 만나는가?
  A: `TokenBucketLimiter.refill` 의 충전 계산이다 — `(elapsed / 1000) * rate` 로 쓰면 1초 미만이 늘 0.
  같은 종류의 사고가 한 상자 안에 두 곳 있다.

- Q: "들어선 시간" 계산에 `Math.floorMod` 를 쓰는 이유는 — `%` 면 가중치가 어떻게 되는가?
  A: `%` 는 음수 피연산자에 음수를 준다.
  시계 원점이 음수면 "들어선 시간"이 음수가 되어 `(window - elapsed) / window` 가 1을 넘고, 추정치가 이전 창의 개수보다 커진다.
  없는 부하로 막는 꼴이다.

- Q: 생성자가 `Math.multiplyExact(limit, windowMillis)` 를 미리 해보는 이유는?
  A: 추정치가 `previousCount * (window - elapsed)` 곱하기부터 시작하기 때문이다.
  넘친 long 은 음수가 되고, 음수 추정치는 한도를 없앤다 — 이름은 멀쩡한 채로.
  01번 지수 백오프에서 `1L << 63` 이 음수가 되던 것과 같은 자리라 생성 시점에 막는다.

- Q: 이 근사가 깔고 있는 가정은 무엇이고, 그 가정이 틀리면 어느 쪽으로 틀리는가(두 방향)?
  A: 가정 — 이전 창의 요청이 그 창에 고르게 퍼져 있었다.
  부하가 창 **끝**에 몰려 있었으면 실제보다 적게 세어 한도를 조금 넘기고(경계에서 101),
  부하가 창 **앞**에 몰려 있었으면 실제보다 많이 세어 최근 1초가 비었는데도 막는다.

- Q: `availableTokens()` 의 `Math.max(0, ...)` 는 지워도 테스트가 통과한다 — 그런데도 남긴 이유는?
  A: 지금은 판정이 추정치를 한도 아래로 묶고 가중치가 작아지기만 해서 음수가 나오는 경로가 없다(변종 검증 M15).
  하지만 판정과 조회가 따로 놀기 시작하면 여기가 음수를 내보내고, 음수 잔량은 아무 뜻도 없다.
  겹친 방어선이라 지우지 않는다.

- Q: 추정치에 permits 를 더해 들고 있지 않고 지금 창의 개수에만 더하는 이유는?
  A: 추정치는 상태가 아니라 매번 시간에 따라 다시 계산되는 값이기 때문이다.
  상태는 `previousCount` 와 `currentCount` 둘뿐이고, 들어온 요청은 지금 창에 속한다.

#### 5. TokenBucketLimiter — 쉬면 모인다

```java
// impl 정답
private void refill(long now) {
    long elapsed = now - lastRefillMillis;
    if (elapsed <= 0) {
        return;
    }
    lastRefillMillis = now;
    if (tokensScaled >= capacityScaled) {
        return;
    }
    long room = capacityScaled - tokensScaled;
    long millisToFull = (room + refillPerSecond - 1) / refillPerSecond;   // 올림
    if (elapsed >= millisToFull) {
        tokensScaled = capacityScaled;        // 곱하지 않고 가득 채운다
    } else {
        tokensScaled += elapsed * refillPerSecond;
    }
}

@Override
protected boolean doTryAcquire(int permits) {
    long now = now();
    refill(now);
    long cost = (long) permits * SCALE;
    if (tokensScaled < cost) {
        return false;      // 부분 소비 없음
    }
    tokensScaled -= cost;
    return true;
}
```

- Q: 토큰을 개수가 아니라 1/1000 단위 정수(SCALE)로 세는 이유 두 가지는?
  A: ① double 을 쓰면 누적 오차가 쌓인다(01번 `RetryBudget` 이 정수로 센 것과 같은 이유).
  ② 1ms 에 채워지는 양이 r/1000 개라서 개수로 세면 1초가 안 지났을 때 늘 0이다. 1/1000 눈금으로 세면 1ms 에 정확히 r 이고 **나눗셈이 아예 사라진다.**

- Q: `(elapsed / 1000) * refillPerSecond` 로 쓰면 초당 10개짜리 리미터가 100ms 주기 클라이언트에게 무엇이 되는가?
  A: 완전 차단이 된다 — 매번 충전량이 0이라 토큰이 영영 안 는다.
  한도를 걸어둔 것이 아니라 기능을 꺼버린 것이다.

- Q: 그 클라이언트가 올리는 신고 문구가 "가끔 되는데 대부분 안 된다"인 이유는?
  A: 1초 이상 쉬는 순간에만 충전이 일어나기 때문이다.
  일정 주기로 두드리면 계속 막히고, 어쩌다 오래 쉬면 통과한다 — 재현 조건이 "쉬는 시간"이라 개발자가 짐작하기 어렵다.

- Q: 채울 양을 먼저 곱한 뒤 상한과 비교하면 하루 쉰 버킷에 무슨 일이 생기는가?
  A: `elapsed * refillPerSecond` 가 long 범위를 넘어 **음수**가 된다.
  음수 토큰은 상한 검사를 그냥 통과해 버킷을 조용히 비운다 — 쉬었더니 오히려 막히는 상태다.
  그래서 곱하기 전에 "가득 차는 데 필요한 시간"과 비교해서, 넘칠 만큼 오래됐으면 아예 곱하지 않고 상한을 대입한다.

- Q: `millisToFull` 을 올림으로 구하는 이유는?
  A: 내림하면 실제로는 아직 덜 찬 시점을 "다 찼다"로 보고 상한을 대입해 없는 토큰이 생긴다.
  `(room + rate - 1) / rate` 는 나머지가 있으면 한 칸 올리는 정수 올림 관용구다.

- Q: 비용 계산에서 `(long) permits * SCALE` 로 캐스팅을 앞에 두는 이유는?
  A: int 끼리 곱하면 큰 permits 에서 int 범위를 넘어 음수가 되고, 음수 비용은 `tokensScaled < cost` 검사를 그냥 통과한다.
  통과한 뒤에는 빼기가 오히려 토큰을 늘린다 — 한도가 사라진다.

- Q: 토큰이 모자랄 때 일부만 빼두면 어떤 상태가 만들어지는가?
  A: 한도 이상은 못 나가는데 아무도 못 들어오는 상태 — 거절당한 요청이 남의 토큰까지 갉아먹는다.
  계약이 "전부 되거나 전부 안 되거나"인 이유다.

- Q: 버킷을 빈 채가 아니라 가득 찬 채로 시작하는 이유는, 빈 채로 시작하면 배포 때 무슨 일이 생기는가?
  A: 빈 채로 시작하면 배포 직후 전부가 막힌다 — 재기동이 곧 장애가 된다.
  게다가 인스턴스를 늘려 대응하면 빈 버킷이 늘어나 더 나빠진다.

- Q: `elapsed <= 0` 검사는 `now()` 와 겹친 방어인데(M17) 남겨둔 이유는?
  A: `ticker` 를 직접 읽는 구현으로 바뀌면 여기가 유일한 방어선이 되기 때문이다.
  지워도 테스트는 다 통과한다는 사실을 주석으로 정직하게 적어두고 남긴다.

#### 6. LeakyBucketLimiter — 큐에 담아 고른 속도로

```java
// impl 정답
private void leak(long now) {
    long elapsed = now - lastLeakMillis;
    if (elapsed <= 0) {
        return;
    }
    lastLeakMillis = now;
    if (queuedScaled == 0) {
        return;
    }
    long millisToEmpty = (queuedScaled + leakPerSecond - 1) / leakPerSecond;   // 올림
    if (elapsed >= millisToEmpty) {
        queuedScaled = 0;
    } else {
        queuedScaled -= elapsed * leakPerSecond;
    }
}

@Override
protected boolean doTryAcquire(int permits) {
    long now = now();
    leak(now);
    long cost = (long) permits * SCALE;
    if (queuedScaled + cost > capacityScaled) {
        return false;                    // 거절 시 lastExitMillis 를 건드리지 않는다
    }
    queuedScaled += cost;
    lastExitMillis = now + queuedScaled / leakPerSecond;   // 세운 뒤의 길이로 계산
    return true;
}
```

- Q: 토큰 버킷은 가득 찬 채로, 누출 버킷은 빈 채로 시작하는 이유는(무엇을 세는 필드인가)?
  A: 토큰 버킷은 **남은 여유**를 세고 누출 버킷은 **밀린 일**을 센다 — 거울상이다.
  여유는 가득 차 있어야 처음부터 받아줄 수 있고, 밀린 일은 비어 있어야 처음부터 받아줄 수 있다.

- Q: 큐가 음수가 되면 다음 몰림 때 무슨 일이 생기는가?
  A: 음수 큐는 `queued + cost > capacity` 용량 검사를 여유롭게 통과해 용량보다 많이 받아준다.
  한도를 조용히 잃는다 — 토큰 버킷이 상한을 넘어 토큰을 만드는 것의 거울상이다.
  하루를 쉬어 곱하기가 넘쳐도 결과는 같다.

- Q: `lastExitMillis` 를 줄 세우기 **전** 길이로 계산하면 누구의 시각이 나오는가?
  A: 자기 앞사람이 나가는 시각이 나온다.
  방금 들어온 요청은 자기 앞의 전부가 빠진 뒤에야 나가므로 **세운 뒤의 길이**로 계산해야 한다.

- Q: 거절한 요청이 `lastExitMillis` 를 밀면 뒤에 오는 요청들은 어떻게 되는가?
  A: 못 들어온 요청 때문에 진짜 요청들이 그만큼 더 기다린 것처럼 보고된다.
  슬라이딩 로그가 거절한 요청을 담으면 안 되는 것과 같은 원리 — 거절은 상태에 흔적을 남기지 않는다.

- Q: 이 클래스가 진짜 큐를 들고 있지 않고 길이만 세는 이유는?
  A: 무엇이 줄 서 있는지는 리미터의 관심사가 아니기 때문이다.
  길이만 1/1000 단위로 세면 저장 항목이 1개로 끝난다 — 실제로 무엇을 담을지는 05번 백프레셔의 채널이 다룬다.

- Q: 용량이 곧 최대 지연이라는 말은 용량 100·초당 10에서 몇 초를 뜻하는가?
  A: 10초다 — 100번째 요청은 앞의 99개가 초당 10개씩 빠질 때까지 기다린다.
  큐를 무제한으로 두면 대기 시간도 무제한이 되고, 그건 장애를 지연으로 바꾼 것뿐이다.

- Q: 토큰 버킷과 누출 버킷의 차이를 "나가는 시각"으로 한 문장으로 말하면?
  A: 토큰 버킷은 통과시키는 순간 나가고(모아둔 100개가 같은 밀리초에 상대에게 간다), 누출 버킷은 받아주기만 하고 나가는 시각을 줄 뒤로 민다.

### B. 개념

#### 7. 다섯 구현은 각각 다른 것을 판다

- Q: 이 문제 전체가 "셋 중 무엇을 살 것인가"인데, 그 셋은 무엇인가?
  A: 정확도 · 메모리 · 몰림 허용.
  다섯 구현은 계약(`tryAcquire`)이 같고 이 셋의 배합만 다르다.

- Q: 고정 창을 그래도 쓰는 이유는?
  A: 계수기 하나라서 레디스 `INCR` 한 번으로 분산 환경까지 가기 때문이다.
  경계 2배는 못 고치지만(고치면 다른 알고리즘이다) 그 단순함이 나머지 넷이 못 주는 것을 준다.

- Q: 슬라이딩 로그를 초당 10만 공용 엔드포인트에 쓰면 안 되는 이유는?
  A: 요청 하나마다 시각 하나이고 그게 사용자 하나당이라, 사용자 100만이면 리미터가 서비스보다 크다.
  `MemoryFootprintTest` 가 다섯의 저장 항목을 1, 1000, 2, 1, 1로 센다.

- Q: 슬라이딩 카운터가 계수기 둘로 사는 것과 파는 것은 각각 무엇인가?
  A: 산 것 — 고정 창의 경계 구멍(200 → 101), 저장 항목 2개라는 상수 메모리.
  판 것 — 정확도. "이전 창이 고르게 왔다"는 틀린 가정 위에 서 있어 양쪽으로 틀린다.

- Q: 토큰 버킷과 누출 버킷은 같은 몰림을 각각 무엇으로 바꾸는가?
  A: 토큰 버킷은 몰림을 **그대로 통과**시키고(상대가 순간 부하를 받는다), 누출 버킷은 몰림을 **지연**으로 바꾼다(붐비는 1초가 100 대 10, 대신 100번째는 10초를 기다린다).

#### 8. 자로 재야 보인다

- Q: t=999에 100개, t=1001에 100개를 넣었을 때 다섯 구현의 통과량은 각각 얼마인가?
  A: 고정 창 100+100 = **200**, 슬라이딩 로그 100+0 = 100, 슬라이딩 카운터 100+1 = 101, 토큰 버킷 100+0 = 100, 누출 버킷 100+0 = 100.
  2밀리초 사이에 제한이 사실상 두 배가 되는 첫 줄이 이 문제의 요점이다(`WindowBoundaryTest`).

- Q: 고정 창의 200이 "고칠 수 있는 버그가 아니다"인 이유는?
  A: "창을 절대 시각으로 자른다"는 선택의 직접적인 결과이기 때문이다.
  그 선택을 바꾸면 슬라이딩 로그나 카운터가 된다 — 즉 고치면 다른 알고리즘이다.

- Q: 그 현상이 01번의 무엇과 같은 구조인가?
  A: 지수 백오프가 지터 없이 모두를 같은 시각에 동기화시킨 것과 같다.
  모든 클라이언트가 같은 벽시계를 보므로 창 경계도 모두에게 같은 순간이고, 그 순간에 전부가 몰린다.

- Q: 지속 부하로 재면 순위가 바뀌어 버킷 둘이 199가 되는데, 199는 어디서 나온 숫자인가?
  A: 버킷의 진짜 상한은 **용량 + 그 구간에 충전(누출)된 양**이다.
  용량 100을 모아둔 채로 1초 구간을 시작하면 그 1초 동안 충전되는 만큼이 더 나가 199가 된다.
  같은 지속 부하에서 로그 100, 카운터 101, 고정 창 104다(`SustainedLoadTest`).

- Q: "한도 100"이 구현마다 다른 뜻이라는 말을 이 숫자들로 설명하면?
  A: 어떤 1000ms 구간을 잡아도 로그는 100을 안 넘고, 카운터는 101까지, 고정 창은 104까지, 버킷 둘은 199까지 흘린다.
  같은 설정값 "100"이 구현에 따라 실제 상한이 두 배까지 차이 난다.

- Q: 메모리 측정(1, 1000, 2, 1, 1)에서 1000은 어느 구현이고 무엇에 비례하는가?
  A: 슬라이딩 로그다. 창 안에 살아 있는 **요청(허가) 수**에 비례한다 — 나머지 넷은 트래픽과 무관한 상수다.

#### 9. 정수 나눗셈은 순서 하나로 리미터를 통째로 끈다

- Q: 정수 나눗셈 함정이 있는 두 곳은 어디인가?
  A: `TokenBucketLimiter.refill` 의 토큰 충전과 `SlidingWindowCounterLimiter.estimate` 의 가중 평균.
  둘 다 "곱하기를 먼저, 나누기를 나중에"가 답이다.

- Q: 이 함정이 01번의 어느 코드와 같은 자리인가?
  A: 01번 `RetryBudget` 이 double 대신 정수로 예산을 센 자리다.
  비율을 정수로 다루는 순간 순서와 눈금이 계약의 일부가 된다.

- Q: "통째로 꺼진다"가 구현마다 어떻게 다르게 나타나는가(카운터 / 토큰 버킷)?
  A: 카운터 — 이전 창 가중치가 늘 0이 되어 슬라이딩이 사라지고 고정 창으로 퇴화한다(한도가 헐거워진다).
  토큰 버킷 — 충전량이 늘 0이 되어 버킷이 영영 안 차고 완전 차단이 된다(한도가 0이 된다).
  같은 실수가 한쪽은 너무 열고 한쪽은 너무 막는다.

#### 10. 곱하기 전에 넘칠지 검사한다

- Q: 넘친 long 이 왜 상한 검사를 그냥 통과하는가?
  A: 넘친 long 은 음수가 되고, 상한 검사는 "이 값이 한도보다 큰가"를 묻기 때문이다.
  음수는 어떤 양수 한도보다도 작으니 무조건 통과다 — 한도가 이름만 남는다.

- Q: 이 방어가 들어가 있는 자리 세 곳은 어디인가?
  A: ① 슬라이딩 카운터 생성자의 `Math.multiplyExact(limit, windowMillis)`,
  ② 토큰 버킷 `refill` 의 "가득 차는 데 걸리는 시간을 먼저 비교"(곱셈 자체를 피한다),
  ③ 누출 버킷 `leak` 의 같은 구조 + 두 버킷의 `(long) permits * SCALE` 캐스팅.

#### 11. 시계는 뒤로 간다

- Q: 시계가 뒤로 가는 실제 원인 셋은 무엇인가?
  A: NTP 보정, 컨테이너 이주, 가상화 계층의 시계 재설정.
  `Ticker` 는 단조 증가를 약속하지만 실무에서는 깨진다.

- Q: "시계 문제는 시계 경계에서 막는다"는 설계 원칙을 이 코드에서 어디가 실현하는가?
  A: `AbstractRateLimiter.now()` 한 곳이다.
  구현마다 깨지는 방식이 다르므로(창이 새로 열림 / 토큰이 생김 / 로그가 안 비워짐) 각자 막게 두면 각자 다르게 틀린다.

- Q: 방어가 겹친 자리 셋(M05·M15·M17)을 지워도 테스트가 통과하는데, 왜 지우지 않는가?
  A: 셋 다 `now()` 의 되감김 방어와 겹쳐 있어서 지금은 도달하지 않을 뿐이다.
  `now()` 를 안 거치는 구현으로 바뀌거나 판정과 조회가 따로 놀기 시작하면 그 줄이 유일한 방어선이 된다.
  지우는 대신 "지워도 테스트가 통과한다"는 사실을 주석에 정직하게 남겼다(안 잡힌 변종 4개 중 나머지 M08은 창 번호 초기화로, 실제 동치 변환이다).

#### 12. 조회가 상태를 바꾼다

- Q: 이 챕터에서 조회가 상태를 바꾸는 자리는 어디인가?
  A: `availableTokens()`·`storedEntries()`·`currentEpoch()`·`tokensScaled()`·`queuedScaled()` 전부 — 읽기 전에 창을 굴리거나(rollTo·roll) 만료시키거나(prune) 충전·누출한다(refill·leak).

- Q: 굴리지 않고 읽기만 하면 트래픽이 끊긴 뒤 무엇이 거짓말을 하는가?
  A: 잔량과 저장 항목 수가 옛날 숫자로 얼어붙는다.
  "왜 막혀 있느냐"는 질문에 10분 전 답을 주고, 메모리 측정도 거짓이 된다.

- Q: 같은 성질을 가진 다른 주제 둘은 무엇인가?
  A: 02번 브레이커의 OPEN → HALF_OPEN 판정(`currentState`), 10번 LRU 캐시의 `get`.
  셋 다 읽기처럼 생긴 것이 쓰기라서 동시성에서 락이 필요해진다.

#### 13. 막으려고 만든 것이 공격 수단이 된다

- Q: 슬라이딩 로그에서 거절한 요청을 기록하면 공격자는 무엇을 할 수 있는가?
  A: 어차피 거절당할 요청만 무한히 쏟아부어 로그(메모리)를 무제한으로 키운다.
  레이트 리밋이 걸려도 메모리는 계속 늘어나므로, 한도가 공격을 막지 못하고 오히려 증폭한다.

- Q: 이것이 다른 넷에는 없는 함정인 이유는?
  A: 나머지 넷은 상태 크기가 트래픽과 무관한 상수(계수기 1~2개, 스칼라 1개)이기 때문이다.
  요청 수에 비례해 자라는 상태를 들고 있는 구현만 이 공격 표면을 갖는다.

#### 14. 버킷 크기 b 가 정책이다

- Q: 실제 트래픽이 고르지 않다는 것이 구체적으로 어떤 모양인가?
  A: 사용자가 페이지 하나를 여는 순간 API 호출 20개가 동시에 나가고 그 뒤 30초를 쉰다.
  평균으로 보면 한가한데 고정 창은 그 20개 중 뒤쪽을 자르고, 사용자는 이유를 모른다.

- Q: b 를 충전 속도 r 과 같게 두면 무엇이 사라지는가?
  A: 몰림 허용이 사라진다 — 모아둘 수 있는 양이 1초치뿐이라 사실상 고른 속도 제한이 된다.

- Q: b 를 크게 두면 누가 대가를 치르는가?
  A: 상대(뒷단)다. 모아둔 b 개가 같은 밀리초에 전부 나가므로 상대가 받는 순간 부하가 b 만큼 커진다.
  그 순간 부하를 못 견디는 상대라면 누출 버킷이 맞다.

#### 15. 한계와 다음 챕터로의 다리

- Q: 슬라이딩 카운터가 "양쪽으로 틀린다"는 두 방향은 각각 무엇인가?
  A: 경계에서 1개를 더 흘린다(101 — 너무 열림).
  부하가 이전 창 앞쪽에 몰려 있었으면 최근 1초가 비었는데도 10개를 막는다(너무 닫힘).

- Q: 전부 프로세스 안의 상태라는 것이 서버 20대에서 무엇을 뜻하는가(02번의 어느 한계와 같은가)?
  A: 각 프로세스가 자기 한도를 따로 세므로 실제 한도가 20배가 된다.
  02번 브레이커의 상태가 프로세스마다 따로였던 것과 같은 한계다 — 진짜 공유 한도는 레디스 같은 공용 저장소가 필요하고, 그래서 고정 창이 살아남는다.

- Q: 02번 `SlidingWindow` 도 "최근"을 셌는데 여기서 새로 설계한 이유는?
  A: 세는 대상이 다르기 때문이다.
  02번은 결과(성공/실패)를 기록하고 실패율을 반환했고, 여기는 **판정과 소비를 한 번에** 한다(통과시키면서 자리를 차지한다).
  비슷하게 생겼다고 같은 추상을 억지로 쓰면 둘 다 이상해진다.

- Q: 누출 버킷이 몰림을 지연으로 바꿨는데, 큐가 무제한이면 그것은 무엇을 무엇으로 바꾼 것뿐인가?
  A: 장애를 타임아웃으로 바꾼 것뿐이다.
  사용자는 거절 대신 무한정 기다리다 타임아웃을 본다 — 용량이 곧 최대 지연이라 큐의 상한이 정책이다.

- Q: 05-backpressure 가 이어받는 질문은 무엇인가?
  A: **어디까지 줄을 세우고 언제 "못 받겠다"고 말할 것인가.**
  누출 버킷은 줄을 세워 지연으로 바꿨을 뿐이고, 넘칠 때 무엇을 버릴지(가장 오래된 것 / 새 것 / 막기 / 실패)는 거기 이야기다.
