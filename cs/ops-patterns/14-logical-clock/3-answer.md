### A. 문제 (구현 대상: LamportClock TODO 1\~3 · VectorClock TODO 4\~6)

#### 1. 램포트 시계 — tick / receive / compare (TODO 1\~3)

**정답 코드** (impl/LamportClock.java):

```java
public synchronized Long tick() {
    ticks++;
    return ++value;                          // TODO 1: 내 값 +1, 그 값을 준다
}

public synchronized Long receive(Long other) {
    receives++;
    value = Math.max(value, other) + 1;      // TODO 2: 큰 쪽 고르고 +1
    return value;
}

public Ordering compare(Long a, Long b) {
    if (a < b) return Ordering.BEFORE;       // TODO 3
    if (a > b) return Ordering.AFTER;
    return Ordering.CONCURRENT;              // 같으면 동시
}
```

```
receive 의 세 갈래 : A(값 3)가 B(값 0)에게 보낸다

  정답  max(0, 3) + 1 = 4     보낸 3 < 받은 4   — 인과가 값 순서로 남는다
  오답1 내 값 +1     = 1     보낸 3 > 받은 1   — 결과가 원인보다 작아진다
  오답2 max(0, 3)    = 3     보낸 3 = 받은 3   — 새 사건인데 새 값이 없다
```

- **램포트의 규칙 두 줄?**\
  → 일이 일어나면(tick) 내 값에 +1. 메시지를 받으면(receive) `max(내 값, 상대 값) + 1`.\
  이 두 줄이 전부다.

> **램포트 시계(Lamport clock)** — 숫자 하나로 세는 논리 시계. tick은 +1, receive는 max+1.\
> 예: B(0)가 A(3)의 메시지를 받으면 max(0, 3) + 1 = 4 가 된다.

- **max 를 안 고르고 +1 만 하면?**\
  → 상대가 앞서 있을 때 받은 쪽 값이 보낸 값보다 작아진다(위 오답1: 3을 받고 1이 된다).\
  "먼저 일어난 일이 더 작다"는 **이 시계의 유일한 보장**이 깨진다.
- **+1 을 안 더하면?**\
  → 받은 것과 같은 값이 된다(위 오답2).\
  "받았다"는 사건 자체가 새 사건인데 새 타임스탬프를 못 받아, 보낸 사건과 받은 사건이 같은 값으로 뭉개진다.
- **값이 같으면 왜 CONCURRENT?** → 서로 다른 노드에서 같은 값이 나오는 것은 흔하고(각자 혼자 3번씩 tick), 그 둘 사이에는 인과가 없다.\
  인과가 있었다면 receive 의 max+1 때문에 값이 반드시 달라졌을 것이다.\
  이것이 램포트가 CONCURRENT 를 말할 수 있는 **유일한** 경우다.

> **인과(causality)** — "이 일이 저 일의 원인이다"라는 관계. 메시지를 주고받아야 생긴다.\
> 예: A 가 만든 주문을 B 가 받아 배송을 만들었다면 그 둘 사이에 인과가 있다.

- **보장 방향과 그 역?**\
  → 보장은 "a 가 먼저 일어났다 → L(a) < L(b)" 한 방향뿐.\
  역(L(a) < L(b) → a 가 먼저)은 성립하지 않는다 — 서로 상관없는 두 사건도 값은 다르기 때문이다(A 혼자 3, B 혼자 2).
- **"답의 절반은 근거가 없다"?**\
  → compare 는 값이 다르면 무조건 BEFORE/AFTER 를 말하는데, 그중 인과가 실제로 있는 쌍만 근거가 있고, 인과 없이 값만 다른 쌍(동시 사건 대부분)에 대한 순서 판정은 지어낸 것이라는 뜻.

#### 2. 벡터 시계 — tick / receive / compare (TODO 4\~6, compare 가 본체)

**정답 코드** (impl/VectorClock.java):

```java
public synchronized VersionVector tick() {
    ticks++;
    value = value.increment(node);              // TODO 4: 내 칸 +1
    return value;
}

public synchronized VersionVector receive(VersionVector other) {
    receives++;
    value = value.merge(other).increment(node); // TODO 5: 합친 다음 올린다
    return value;
}

public Ordering compare(VersionVector a, VersionVector b) {   // TODO 6
    boolean aSmallerSomewhere = false;
    boolean bSmallerSomewhere = false;
    for (String name : VersionVector.union(a, b)) {   // 양쪽 키의 합집합
        long left = a.get(name);                       // 없으면 0
        long right = b.get(name);
        if (left < right)      aSmallerSomewhere = true;
        else if (left > right) bSmallerSomewhere = true;
    }
    if (aSmallerSomewhere && !bSmallerSomewhere) return Ordering.BEFORE;
    if (bSmallerSomewhere && !aSmallerSomewhere) return Ordering.AFTER;
    return Ordering.CONCURRENT;   // 둘 다 작은 칸이 있거나, 아무 칸도 안 다르다
}
```

```
receive 순서가 갈리는 곳 : 재기동한 A(빈 벡터 {})가 B 에게서
                          자기 옛 값이 든 {A=5, B=2} 를 되받는다

  정답  merge 먼저   {} merge {A=5,B=2} = {A=5,B=2} → increment(A) = {A=6, B=2}
                     -> 시계가 앞으로만 간다
  오답  올리고 merge  {} increment(A) = {A=1} → merge {A=5,B=2} = {A=5, B=2}
                     -> 내 칸 1 이 상대의 5 에 덮인다. 새 사건이
                        받은 것과 똑같은 타임스탬프를 갖는다
```

- **"합친 다음 올리기" 순서를 바꾸면?**\
  → 내 칸을 먼저 올린 값이 merge 의 max 에서 상대가 아는 내 옛 값에 덮인다(위 그림).\
  새 사건이 받은 것과 같은 타임스탬프를 가져 "받은 것보다 확실히 나중"이 안 남는다.

> **벡터 시계(vector clock)** — 노드마다 칸 하나씩 세는 논리 시계. 동시성을 표현할 수 있다.\
> 예: `{A=3}` 과 `{B=2}` 를 비교하면 CONCURRENT 라고 답한다.

- **왜 평소엔 안 드러나는가?**\
  → 평소에는 남이 나에 대해 나보다 많이 아는 경우가 없어서(내 칸은 항상 내가 최댓값) max 가 어느 쪽으로 돌아도 결과가 같다.\
  **재기동·스냅샷 복구**로 내 값이 뒤로 간 순간 그 경우가 생긴다.\
  원본도 변종 9개 중 이것만 처음에 살아남았고, 재기동 시나리오를 테스트에 넣어야 잡혔다.
- **왜 합집합을 도는가?**\
  → 한쪽 키만 돌면 상대에게만 있는 노드 칸을 아예 비교하지 않는다.\
  그러면 "내가 모르는 것을 상대가 안다"(= 상대가 앞선 칸)를 못 보고, 실제로는 동시인 쌍에 순서를 지어낸다.\
  `get` 이 없는 키에 0 을 주므로 합집합을 돌면 안전하다.

> **merge(합치기)** — 두 벡터를 칸마다 큰 쪽으로 합치는 것.\
> 예: `{}` 에 `{A=5, B=2}` 를 합치면 `{A=5, B=2}` 가 된다.

- **"a 에 작은 칸이 있다"만 보고 BEFORE 판정하면?**\
  → 둘 다 작은 칸이 있는 경우(서로 상대가 모르는 것을 아는 상태 = 진짜 동시)를 BEFORE 로 잘못 판정한다.\
  a 가 먼저이려면 a 에 작은 칸이 있고 **b 에는 작은 칸이 없어야** 한다.
- **완전히 같으면?**\
  → CONCURRENT. 아무 칸도 안 다르면 같은 상태이고, 그 사이에 인과의 방향이 없으니 동시로 본다(코드의 마지막 return 이 두 경우를 함께 처리한다).
- **0 과 없음이 같아야 하는 이유?**\
  → `{A=1}` 과 `{A=1, B=0}` 은 "B 소식을 하나도 못 들었다"는 같은 상태다.\
  다르게 취급하면 "아직 소식을 못 들은 노드"와 "아예 모르는 노드"를 구별해야 하는데 그 구별에는 의미가 없다.\
  그래서 `get` 은 없는 키에 0 을 주고, `equals` 도 합집합을 돌며 0 칸을 무시한다(VersionVector.java).

> **버전 벡터(VersionVector)** — `{A=3, B=1}` 꼴의 값 묶음. "A에서 3번, B에서 1번 일어난 것까지 안다".\
> 예: `{A=1}` 과 `{A=1, B=0}` 은 같은 상태다.

- **`width()` 가 재는 것?**\
  → 타임스탬프가 차지하는 칸 수(`value.nodes().size()`).\
  메시지마다 이 칸들을 다 붙여 보내므로 이 값이 곧 벡터 시계의 공간 비용이고, 노드가 사라져도 줄지 않는다.

### B. 개념

#### 3. 왜 벽시계로는 안 되는가

- **50ms 어긋나면 무슨 일이?**\
  → A 가 12:00:00.100 에 주문을 만들고, B 가 그것을 받아 12:00:00.050 에 배송을 만든 것으로 기록된다 — 결과(배송)가 원인(주문)보다 먼저인 로그가 남는다.

> **벽시계(wall clock)** — 실제 시각. 서버마다 어긋나 있는 것이 정상이다.\
> 예: B의 시계가 50ms 뒤처지면 배송이 주문보다 먼저 만들어진 것으로 기록된다.

- **왜 아무도 신고하지 않는가?**\
  → 값이 있기 때문이다.\
  타임스탬프 칸이 비어 있지 않고 그럴듯한 시각이 들어 있으니 에러로 보이지 않는다.\
  조용히 틀린 채 쌓인다.
- **NTP 로 해결되는가?**\
  → 안 된다.\
  NTP 를 잘 맞춰도 수 밀리초는 늘 어긋나 있고, 50ms 오차도 아주 흔하다.\
  오차를 줄일 뿐 0 으로 만들 수 없다.

> **시계 오차/스큐(clock skew)** — 두 서버의 시계가 어긋난 정도. 수 밀리초\~수십 밀리초가 흔하다.\
> 예: NTP 를 잘 맞춰도 50ms 오차는 아주 흔하다.

- **논리 시계는 무엇을 세는가?**\
  → 시각 대신 "누구에게서 무엇을 들었는가"를 센다.\
  메시지 주고받음이 만드는 인과 순서만 기록한다.

> **논리 시계(logical clock)** — 벽시계 없이 사건의 인과 순서를 기록하는 장치. 램포트 시계와 벡터 시계가 대표.\
> 예: 시각 대신 "누구에게서 무엇을 들었는가"를 센다.

#### 4. 램포트 vs 벡터 — 무엇을 사고 무엇을 파는가

- **A(3) vs B(2), 서로 안 주고받음** → 램포트: compare(3,2) = **AFTER** — 근거 없는 답.\
  벡터: compare({A=3},{B=2}) = **CONCURRENT** — 둘 다 상대 칸이 0 이라 서로 작은 칸이 있다. 정직한 답.
- **"동시"의 뜻?**\
  → 시각이 같다는 뜻이 아니다.\
  **서로 소식이 안 닿았다**(두 사건 사이에 인과가 없어 순서를 말할 수 없다)는 뜻이다.

> **동시(concurrent)** — 시각이 같다는 뜻이 아니라 서로 소식이 안 닿았다(인과가 없다)는 뜻.\
> 예: A(3)와 B(2)가 아무것도 주고받지 않았다면 두 사건은 동시다.

- **벡터가 파는 것 한 문장?**\
  → "없는 순서를 지어내지 않는 것" — 인과가 없으면 CONCURRENT 라고 믿을 수 있게 말해준다(양방향 보장: a 가 먼저다 ↔ V(a) ≤ V(b) 이고 하나는 작다).
- **공간 비용?**\
  → 노드 n 대면 타임스탬프가 n+1 칸꼴로 자란다 — 원본 측정: 2대→3칸, 50대→51칸, 200대→201칸.\
  (칸 수 = 등장한 노드 이름 수이므로 측정 시나리오에서 노드 수+1.) 램포트는 1000대여도 long 하나.
- **죽은 노드의 칸이 안 줄면 왜 치명적?**\
  → 한 번 나타난 이름은 영원히 남는다 — 워커 5개가 죽고 100번 더 일해도 칸은 6개 그대로.\
  오토스케일링으로 노드가 계속 생겼다 죽으면 칸이 단조 증가해, 메시지마다 붙는 비용이 계속 자란다.\
  실제 시스템에서 벡터 시계를 쓰기 어렵게 만드는 지점이다.
- **타임스탬프 > 본문?**\
  → 노드가 많아지면(예: 1000칸) 몇 바이트짜리 이벤트 하나를 보내는 데 그보다 큰 벡터를 붙여 보내게 된다 — 배보다 배꼽이 커지는 상황.

#### 5. 연결 — 앞뒤 챕터와의 다리

- **13번이 멈춘 자리?**\
  → 스노우플레이크는 벽시계를 ID 앞에 붙여 "대체로" 정렬했고, 같은 밀리초 안의 순서에는 근거가 없었다.\
  이 챕터는 순서에 근거가 없을 때 지어내는 대신 **"모른다"(CONCURRENT)를 말할 수 있게** 했다.
- **동시인 두 값을 합치는 책임?**\
  → 시계의 책임이 아니다.\
  시계는 "이 둘은 동시다"라는 판정까지만 하고, 동시인 두 값을 어떻게 합칠지는 자료구조 쪽(15-crdt — 합치는 것 자체가 답이 되는 자료구조)이 정한다.
- **이벤트 소싱에서 정렬이 뒤집히면?**\
  → 이벤트 소싱은 사건 목록을 순서대로 재생해 상태를 만든다(16번).\
  원인과 결과가 뒤바뀐 순서로 재생하면 잘못된 상태가 만들어진다 — 입금 전에 출금이 재생되는 식.

> **이벤트 소싱(event sourcing)** — 상태 대신 사건 목록을 저장하고 순서대로 재생해 상태를 만드는 방식(16번).\
> 예: 입금 전에 출금이 재생되면 잘못된 상태가 만들어진다.

- **Ticker 가 없는 이유?**\
  → 다른 상자들은 시간 의존 로직을 테스트하려고 벽시계를 주입(Ticker)받지만, 이 상자는 **벽시계를 아예 안 쓰는 것** 자체가 내용이라 주입할 시계가 없다.
