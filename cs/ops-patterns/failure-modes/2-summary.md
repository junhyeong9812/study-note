# ops-patterns/failure-modes — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/11-failure-modes/`(README + A/B/C 4파일, 총 1,559줄) · 이관일 2026-09-16.\
> 본문은 원고를 **일반화해 고쳐 쓴 것**이다(논지·문체 유지). 실사건 인용(Jepsen·GitHub·Knight Capital·Toss 등)은 일반 지식이라 **원고 그대로 보존**한다.\
> 프로젝트 고유 결정(ADR·BR·규칙 번호)은 「현장에서 만나는 상황」으로 **일반화**했고, C군(결제)은 결제 도메인 일반의 실패로 서술한다. 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

이 카탈로그의 한 문장은 이것이다.\
**막는 것에 이름을 댈 수 있으면 막히고, 계약 문장뿐이면 뚫린다.**\
주의력에 의존하는 규칙은 지켜지지 않는다 — 이 저장소가 사고를 겪고 얻은 실측 결론이다.

## 한눈에 — 쉽게 말하면

불을 막는 두 가지 방법을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
벽에 "화기주의" 표지판만              소화기가 걸려 있고 위치를 안다
+---------------------------+        +---------------------------+
| 문장만 있다                |        | 이름 붙은 장치가 있다        |
| "여기서 조심하라"           |        | "저기 소화기가 있다"         |
+---------------------------+        +---------------------------+
  → 불이 나면 아무것도 안 한다          → 불이 나면 실제로 끈다
```

**코드도 똑같은 구조다.**\
방어를 계약 문장(*"여기서는 순서를 지킨다"·"이 조회는 멱등하다"*)으로만 적어두면, 지키는 것은 사람의 주의력이고 부하가 걸리는 날 뚫린다.\
방어에 **이름 붙은 장치**(유니크 제약·낙관적 락·fencing token·DLQ)가 있으면 구조가 대신 막는다.

이 문서는 그런 실패를 **번호(F-01~F-25)로 정리한 카탈로그**다.\
셋으로 나눈다 — **A. 동시성·데이터베이스**(한 DB 안에서), **B. 분산·비동기**(프로세스가 갈릴 때), **C. 결제 도메인**(돈이 걸릴 때).

## 문제 — 이 카탈로그가 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(운영 패턴 정리다). 대신 실패 하나하나를 **네 칸**으로 세우고, 마지막 칸으로 판정한다.

```text
증상    겉으로 보이는 것 — 이것만 보면 원인을 못 찾는다
뿌리    실제 원인 — 동작 원리를 알아야 보인다
현장    이 실패와 같은 형태가 어디서 나오는가
막는 것 이름을 댈 수 있으면 막힘, 계약 문장뿐이면 뚫림
```

> ★ **"막는 것" 칸이 비어 있거나 문장뿐이면, 그것은 안 막고 있는 것이다.**\
> 이 판정이 카탈로그 전체의 목적이다 — 아래 서머리는 그 판정을 25개에 대해 수행한 것이다.

각 실패는 **원리부터** 본다.\
*무엇이 어떻게 동작하길래 그렇게 깨지는지*를 알아야 *"우리도 그런가"* 를 판단할 수 있기 때문이다.

## 전체 흐름 — 실패 하나를 읽는 순서

```text
증상 (겉)                에러 없음 · 간헐적 실패 · 갈수록 느려짐
      ↓
뿌리 (원리)              MVCC · 두 장군 문제 · GC 정지 · 온라인 DDL
      ↓
같은 구조인가 (판정)      "우리도 load-modify-save 하나?" "복제본에서 읽나?"
      ↓
막는 것이 무엇인가        이름 붙은 장치인가, 아니면 계약 문장인가
      ↓                        │                    │
   장치 → 막힘             문장 → 뚫림 (다음 작업 목록)
```

- 왼쪽은 **무엇을 보는 단계**, 오른쪽은 **그 단계에서 판정하는 것**.
- 마지막 칸이 카탈로그의 핵심이다. 나머지 세 칸은 그 판정을 세우기 위한 재료다.

## A. 동시성·데이터베이스 (F-01 ~ F-08)

> 출처: 원본 `A-concurrency.md` §F-01~F-08 · 일반 지식 보강.\
> 공통점: **부하가 걸릴 때만 틀리고, 에러 없이 조용히 틀리며, 늘려서 푸는 문제가 아니고, "정상 동작"이 원인이다.**

### 원리 — MVCC와 스냅샷 (F-01·F-05가 여기서 나온다)

많은 DB(예: MySQL InnoDB)는 **MVCC**로 동작한다 — 읽을 때 락을 안 잡는 대신 트랜잭션마다 *"그 시점의 사진"* 을 본다.

> **MVCC(다중 버전 동시성 제어)** — 같은 행의 여러 버전을 두고, 트랜잭션마다 자기 시점의 버전을 보게 하는 것.\
> 예: 내가 100원을 읽은 뒤 남이 200원으로 바꿔도, 내 트랜잭션은 계속 100원을 본다.

**격리 수준이 이 사진의 수명을 정한다.**

```text
READ COMMITTED (RC)     문(statement)마다 새 사진 — 매번 최신 커밋을 본다
REPEATABLE READ (RR)    트랜잭션 시작 시 한 장 — 끝까지 같은 사진을 본다
```

RR의 *"끝까지 같은 사진"* 은 **읽기에는 좋고 쓰기에는 위험하다.** 그 위험이 F-01이다.

### F-01 Lost update — 커밋된 변경이 조용히 사라진다

**언제 나오나** — 잔액·재고·카운터처럼 *읽고 → 고치고 → 저장하는* 값을 두 요청이 동시에 만질 때.

```text
계좌 잔액 100, 점유액(홀딩) 0

시각  T1 (30 점유)                     T2 (50 점유)
────────────────────────────────────────────────────────
 2    SELECT → 잔액100, 점유0
 4                                    SELECT → 잔액100, 점유0   ★ 같은 값
 5    가용 100-0=100, 30 승인
 6    UPDATE 점유 = 0 + 30
 7    COMMIT                          (T2는 아직 옛 사진을 본다)
 8                                    가용 100-0=100, 50 승인
 9                                    UPDATE 점유 = 0 + 50       ★ 30을 덮어쓴다
10                                    COMMIT

결과  점유 = 50  (80 이어야 한다) → 30만큼 초과 승인 가능
```

- **증상** — 에러가 안 난다. DB는 *"둘 다 유효한 UPDATE"* 로 본다. **숫자만 조용히 틀린다.**
- **뿌리** — ORM의 `load → modify → save`. ③ save가 `SET 점유 = 30`(절대값)이라 ①~③ 사이 남의 변경이 통째로 사라진다.
- **실사건** — Jepsen MySQL 8.0.34 (2023-12): *"load-modify-save 패턴에서 커밋된 변경을 조용히 버린다"* — 9,048 트랜잭션 중 **198건**.
- **막는 법** — **낙관적 락**(버전 컬럼 + `UPDATE … WHERE version = ?`, 0행이면 예외) + **아키텍처 테스트**(버전 필드 존재를 강제).

> ⚠️ **버전 필드를 안 붙여도 컴파일되고 테스트도 통과한다** — 동시 요청이 없으면 안 틀리기 때문이다.\
> 그래서 "필드가 있는지"를 검사하는 장치가 따로 필요하다.

> **낙관적 락(optimistic lock)** — 잠그지 않고, 저장 시점에 버전이 안 바뀌었는지만 확인하는 방식.\
> 예: `version=3`으로 읽었으면 `UPDATE … WHERE version=3` — 그새 4가 됐으면 0행 갱신 → 재시도.

### F-02 데드락 — 서로를 기다린다

- **증상** — 간헐적 실패. 부하가 오르면 급증한다.
- **뿌리** — 세 가지: ① **락 순서 불일치**(T1은 A→B, T2는 B→A) ② **중복 키 INSERT의 S락**(같은 유니크 키로 동시 INSERT 시 서로의 공유 락 때문에 교착) ③ **갭 락 vs INSERT**(RR의 범위 조회가 빈 공간까지 잠근다).
- **실사건** — ideeli: `autoinc_lock_mode`를 바꿔 한 문제를 풀었더니 **갭 락 충돌로 재발**, 결국 RC로 내려 해소.
- **막는 법** — **일관된 락 순서**(모두 같은 순서로 잠그면 교착 불가) + **INSERT 후 중복이면 조회**로 전환 + 갭 락이 문제면 **RC**.

> ★ 데드락 자체는 장애가 아니라 DB의 **정상 동작**이다(한쪽을 죽여 푼다). 문제는 **빈도**다.\
> 멱등을 *"같은 키면 무시"* 를 INSERT로 구현하면 ②가 그대로 재현된다.

### F-03 커넥션 풀 고갈 — 증설했더니 더 느려진다

```text
증설로 더 나빠지는 이유                한 작업 한 커넥션으로 고침
+---------------------------+        +---------------------------+
| 인스턴스 8 × 풀 20 = 160   |        | 한 작업이 커넥션 1개만 잡음  |
| DB 상한 150 → 초과로 죽음   |        | 채번용 두 번째 커넥션 없음   |
| 한 작업이 커넥션 2개 점유    |        | 풀 데드락이 원천 불가능      |
+---------------------------+        +---------------------------+
  → 앱을 늘리면 DB가 먼저 죽는다        → 풀을 나눠 배치가 실시간을 안 먹음
```

- **증상** — 앱 인스턴스를 늘렸더니 **더 느려진다**.
- **뿌리** — 총 커넥션 = 인스턴스 수 × 풀 크기 > DB `max_connections`. 더 나쁜 건 **한 작업이 커넥션을 둘 잡는 것**(비즈니스용 + 채번용) — 스레드가 각자 하나를 잡고 두 번째를 기다려 **풀 데드락**.
- **실사건** — 우아한형제들: 컨슈머 16 vs 풀 10, `GenerationType.AUTO` 채번이 두 번째 커넥션을 잡아 데드락. **풀을 키워도 안 풀렸다.**
- **막는 법** — **한 작업 한 커넥션** + **풀 분리**(배치/실시간) + **총 커넥션 상한 검증**.

### F-04 복제 지연 — 방금 쓴 것이 안 보인다

- **증상** — *"저장했는데 목록에 없다"* · **멱등 조회가 못 찾아 재처리**한다.
- **뿌리** — 쓰기는 Primary, 읽기는 Replica. 커밋~복제 적용 사이가 지연(평시 ms, 부하 시 초, 대량 DDL 중 시간).
- **실사건** — Airbnb Orpheus: *"replica에서 멱등 조회를 하면 이중 결제가 난다"* → 멱등 조회는 마스터에서만.
- **막는 법** — **자금·멱등 판단은 쓰기(마스터) 데이터소스에서만.** 복제본은 *"진짜가 아닐 수 있는 값"* 이라는 범주로 묶는다.

> read-your-writes 위반(*"방금 것이 안 보인다"*), monotonic read 위반(*"잔액이 아까보다 적다"*)이 같은 뿌리의 다른 얼굴이다 — 그중 **멱등이 안 먹는 것**이 가장 비싸다.

### F-05 롱 트랜잭션 — undo가 쌓여 전체가 느려진다

- **증상** — 시간이 갈수록 **쓰기와 무관한 SELECT까지 느려진다**.
- **뿌리** — MVCC의 옛 버전은 **undo 로그**에 있다가 아무도 안 보면 **purge**가 지운다. 오래 열린 읽기 트랜잭션 하나가 그 판정을 막아 undo가 무한히 쌓인다(History List Length).
- **실사건** — Percona: 940 ACTIVE 트랜잭션 → History List Length **6,000,000** → SELECT 저하, kill 후 회복.
- **막는 법** — 배치는 **RC + 짧은 트랜잭션.** RC라도 트랜잭션이 열려 있으면 그 자신의 undo는 남으므로, **짧게 끊는 것이 진짜 답**이다.

### F-06 마이그레이션 — 온라인 DDL이 온라인이 아니다

- **증상** — 배포 중 오류. 롤백이 더 나쁘다.
- **뿌리** — DDL 알고리즘(INSTANT/INPLACE/COPY)마다 제약이 다르다. ① **복제본에서는 논블로킹이 아니다**(Primary가 3시간 걸린 DDL을 Replica가 그대로 3시간 → 복제 지연 3시간). ② **컬럼 드롭이 앱을 깬다**(ORM이 SELECT에 컬럼 이름을 나열 → 배포 안 된 인스턴스가 없는 컬럼을 부른다).
- **실사건** — PlanetScale(INPLACE 3시간 = 복제 지연 3시간) · GitHub 2025-08(*"안 쓴다"* 던 컬럼을 드롭했는데 ORM이 이름을 불러 장애 — 한 달에 두 번).
- **막는 법** — **expand-contract**(새 컬럼 추가 → 배포 → 백필 → 배포 → 옛 컬럼 제거), **각 단계 사이에 전 인스턴스 배포 완료를 기다린다.** 그 대기가 없으면 F-17이 된다.

### F-07 ORM flush 타이밍 — 같은 트랜잭션인데 옛 값을 읽는다

- **증상** — 같은 트랜잭션 안에서 **내가 방금 쓴 게 안 보인다.**
- **뿌리** — ORM은 변경을 메모리(영속성 컨텍스트)에 모았다 flush 때 보낸다. JPQL 실행 전엔 자동 flush되지만 **직접 SQL(JdbcTemplate 등)은 ORM 흐름 밖**이라 flush가 안 일어나 옛 값을 읽는다.
- **막는 법** — 트랜잭션 안에서 **ORM과 직접 SQL 혼용 금지**를, 규약이 아니라 **모듈 분리로** 강제한다(그 모듈에 직접 SQL 타입이 아예 없게).

> ★ *"flush를 꼭 하세요"* 라는 문장이 아니라 **혼용 자체를 불가능하게** 만드는 것이 핵심 — F-03의 이중 커넥션까지 덤으로 막힌다.

### F-08 채번·시퀀스 병목

- **뿌리** — 전역 유일 번호(승인번호·전표번호)를 만드는 방법마다 성격이 다르다.

| 방법 | 병목 | 순서 |
|---|---|---|
| AUTO_INCREMENT | 테이블 단위 락 | 보장 |
| 중앙 시퀀스 테이블 | ★ **한 행에 UPDATE 집중**(직렬화 지점) | 보장 |
| UUID | 없음 | ❌ + **인덱스 단편화**(랜덤 삽입) |
| Snowflake류 | 없음 | 시간순 대략 |
| 채번 블록 할당 | 낮음(N개씩 미리) | 블록 내 보장 |

- **막는 법** — 위 트레이드오프 표를 근거로 고른다. 인스턴스 증가에 강하려면 **블록 할당**.

## B. 분산·비동기 (F-09 ~ F-19)

> 출처: 원본 `B-distributed.md` §F-09~F-19 · 일반 지식 보강.\
> 공통점: **두 장군 문제가 뿌리이고, "정상 동작"이 원인이며, 선언과 장치를 혼동하기 쉽고, 한 건이 전체를 막는다.**

### 전제 — 두 장군 문제 (F-10·F-11·F-12의 공통 뿌리)

```text
A가 B에게 요청 → 응답이 안 온다
  → B가 못 받았나?  아니면 처리했는데 응답이 유실됐나?
  ★ A는 원리적으로 구분할 수 없다

  재시도한다     → 중복 가능 (at-least-once)
  재시도 안 한다  → 유실 가능 (at-most-once)
```

> ★ **"정확히 한 번(exactly-once)"은 전달에서 불가능하다.**\
> 가능한 것은 **at-least-once 전달 + 수신측 멱등** = 결과적으로 한 번이다.

### F-09 재시도 폭풍 / 캐스케이딩 장애

```text
정상   요청 100 → 처리 100
느려짐 요청 100 → 30 타임아웃 → 재시도 30 → 실질 130
       더 느려짐 → 60 타임아웃 → 재시도 60 → 실질 160
       → ★ 느려질수록 부하가 는다 (양의 피드백)
```

- **증상** — A가 느려지면 그를 부르는 B·C까지 무너진다.
- **뿌리** — 재시도가 이미 느린 시스템에 부하를 곱한다. 동기 호출은 스레드를 묶어(A가 5초면 B 스레드가 5초 묶임) 전파된다.
- **실사건** — Twilio 빌링 (2013): 잔액 갱신 전에 카드를 긁고 확인이 안 되니 **무한 재과금**. 방어는 *"잔액을 쓸 수 없으면 긁지 않는다"*(fail-closed) + 복식부기 대조.
- **막는 법** — **서킷 브레이커**(대기 자체를 없앤다) + **지수 백오프 + 지터** + **벌크헤드**(대상별 전용 풀) + **재시도 예산** + **fail-closed**.

> ★ **지터가 없으면 백오프가 오히려 나쁘다** — 100개가 동시에 실패하면 1초 뒤 100개가 **동시에** 재시도해 파도가 된다.

### F-10 메시지 유실

- **뿌리** — 커밋과 발행 사이의 틈. `COMMIT` 후 `publish(event)` 전에 죽으면 사실은 바뀌었는데 아무도 모른다. 순서를 바꾸면 *일어나지 않은 일을 알린 것*이라 더 나쁘다. **두 저장소(DB·브로커)에 원자적으로 쓸 방법이 없다.**
- **막는 법** — **Outbox**.

```text
BEGIN
  UPDATE account ...
  INSERT INTO outbox (event)    ← ★ 사실과 이벤트가 같은 트랜잭션
COMMIT
별도 프로세스가 outbox를 읽어 전달 → 둘 다 있거나 둘 다 없다
```

### F-11 메시지 중복

- **뿌리** — Outbox는 유실을 막지만 **중복은 안 막는다.** 전달 성공 후 완료 표시 전에 죽으면 재전달. 전달과 완료 표시가 원자적일 수 없다(F-10이 한 계층 아래에서 반복).
- **막는 법** — **수신측 멱등**. 핵심은 *"본다"* 가 아니라 *"못 넣는다"*.

```text
조회 후 없으면 처리     ❌ 동시 요청에서 둘 다 "없다"를 본다
유니크 제약            ✅ DB가 두 번째를 거부한다
```

> ★ **필드가 있는 것과 제약이 있는 것은 다르다.** *"이벤트 ID를 이미 갖고 있으니 충족"* 은 착각 — **유일 제약**이 있어야 실제로 막힌다.

### F-12 순서 역전

- **뿌리** — 병렬 전달이면 나중 이벤트(출금)가 먼저 도착할 수 있다. **전역 순서**는 전달을 직렬화해 처리량을 무너뜨리므로 답이 아니다.
- **막는 법** — *"필요한 범위에서만"* 순서를 지킨다 — **키로 파티션 + 파티션당 단일 소비자**(소유권 구조: 한 키는 항상 한 소비자).
- **실사건** — 우아한형제들: *커넥터 단일 태스크 + 키→테이블 고정* 이라는 소유권 구조로 해결.

> ⚠️ **선언과 장치를 혼동하기 쉬운 대표 자리다.** *"순서는 파티션 키 안에서 보장"* 이라고 적어도, 릴레이가 2인스턴스면 같은 키를 병렬로 집는다 — 검증표가 중복만 재고 순서를 안 재면 못 잡는다.

### F-13 Head-of-line blocking — 독약 메시지

- **증상** — 이벤트 하나가 실패하는데 **뒤 전부가 멈춘다**. 유실이 아니라 **정체**라 대사가 *"아직 안 왔다"* 로만 본다.
- **뿌리** — 순서대로 훑는 릴레이 + 영구 실패 한 건.
- **막는 법** — **재시도 상한** + **DLQ**(독약을 옆으로 빼고 다음 진행) + **격리 알림**(사람이 본다).

> ★ **DLQ 없이 상한만 두면 유실이 된다.** 빼되 **버리지 않는 곳**이 필요하다.

### F-14 좀비 — lease 만료로는 못 막는다

```text
lease만 있을 때 (뚫림)                 fencing token (막힘)
+---------------------------+        +---------------------------+
| A가 파티션 임차(만료 30s)   |        | 임차마다 단조증가 번호 발급   |
| A가 GC로 40초 정지          |        |   A→17, B→18               |
| 30s: B가 만료 감지→임차     |        | 쓰기에 번호를 함께 보낸다     |
| 45s: A 깨어남, 자기 소유인  |        | 저장소가 "본 것보다 작은      |
|      줄 알고 쓰기            |        |   번호는 거부"               |
| → A·B가 같은 자원에 쓴다     |        | → A(17)의 늦은 쓰기 거부      |
+---------------------------+        +---------------------------+
```

- **뿌리** — GC 정지한 프로세스가 깨어나 자기가 아직 소유자인 줄 알고 쓴다. **lease는 "가져가는 것"을 조정할 뿐 "쓰는 것"을 막지 않는다.**
- **실사건** — Kleppmann, *"How to do distributed locking"* (2016)이 fencing token으로 정식화.
- **막는 법** — **fencing token**(단조 증가 번호를 쓰기에 실어 저장소가 오래된 번호를 거부). 원자적 할당·멱등·runId만으로는 못 막는다.

### F-15 배치 중복 실행

- **뿌리** — 스케줄러를 이중화하면 가용성은 오르지만 단일 실행이 깨진다(둘 다 트리거). **K8s CronJob도 컨트롤러 재시작 시 중복 생성이 가능**하다.
- **실사건** — Toss Payments (2025): *"K8s CronJob은 정확히 한 번을 보장 못 한다"* · 토스 자동이체 2026-06 38분 21.4억 원 · Santander £130m(2021 크리스마스 이브 중복 지급). *(연도 세부는 확인 필요)*
- **막는 법** — **파티션 할당**(파티션당 하나). 리더 선출·전역 락은 단일 실행은 되지만 병렬이 안 된다.

```text
리더 선출  ✅ 단일 실행  ❌ 리더가 전부 처리 (병렬 X)
전역 락    ✅ 단일 실행  ❌ 병렬 X
파티션 할당 ✅ 파티션당 하나 ✅ 병렬 O
```

### F-16 타임아웃 계층 역전

- **증상** — 상위가 포기했는데 **하위는 계속 돈다** — 락이 안 풀린다.
- **뿌리** — 하위 타임아웃 > 상위 타임아웃. 상위가 3초에 포기해도 DB 트랜잭션이 안 죽으면 행이 계속 잠기고, 다음 요청이 그 락을 기다려 줄줄이 느려진다(→ F-09).
- **막는 법** — **바깥에서 안으로 갈수록 타임아웃을 짧게** + 상위가 포기할 때 **하위를 실제로 취소(전파)**.

```text
외부 규약 25초 > 우리 응답 3초 > DB 쿼리 1초 > 락 대기 0.5초
```

> ⚠️ 목표값·요구사항은 **장치가 아니다.** 바깥 값만 알고 안쪽 계층이 없으면 여전히 뚫린다.

### F-17 배포 스큐 — 구/신 버전이 동시에 돈다

- **뿌리** — 롤링 배포는 정의상 두 버전이 공존하는 구간을 만든다. 깨지는 것: **스키마**(F-06) · **이벤트 스키마**(구 버전 파싱 실패 — 유실이 아니라 오해라 대사가 못 잡는다) · **동작 규칙**(구/신이 다른 판단).
- **실사건** — Knight Capital (2012): 8대 중 **1대만 구 코드**가 재사용된 플래그를 옛 의미로 해석 → 45분 **$460M**. **롤백이 상황을 악화**시켰다.
- **막는 법** — **판단이 바뀌는 변경은 플래그 뒤에** 두고, 스키마는 **expand-contract**로.

> ★ *"lazy close"*(*"거래가 영업일을 닫는다"*)처럼 **어느 버전의 코드가 닫는지**가 빠진 규칙이 이 위험을 그대로 갖는다 — 구 버전은 안 닫고 신 버전은 닫아 상태가 갈린다.

### F-18 Split-brain

- **뿌리** — 네트워크가 갈라지면 양쪽이 각각 *"상대가 죽었다"* 판단 → 양쪽이 리더 → 양쪽에 쓰기 → 합칠 때 충돌. **유니크 제약이 무력화**된다(두 DB가 각각 *"이 키는 처음"* ). 멱등이 유니크 제약에 기대고 있으면 그 순간 멱등이 사라진다.
- **실사건** — GitHub 2018-10: 43초 단절 → 크로스리전 페일오버 → **24시간 11분** 저하, 954건 미복제. 원칙: *"data integrity over site usability"*.
- **막는 법** — 단일 DB의 유니크 제약이 지금은 막지만, **그 전제(멱등이 단일 DB에 의존한다)를 문서에 명시**해야 한다. 다중화하는 순간 전제가 무너진다.

### F-19 핫스팟 — 늘려도 안 풀린다

- **뿌리** — 샤딩·파티셔닝은 *"부하가 키에 고르게 퍼진다"* 는 전제 위에 있다. 한 키에 몰리면 **샤드를 늘려도 그 키는 여전히 한 샤드**다(분할은 키를 못 쪼갠다).
- **막는 법** — **키 설계로 편중을 분산**한다(예: 파일 단위가 아니라 파일 내 **레코드 순번 범위**로 파티션).

> ★ **규모가 아니라 구조 문제다.** 일 1회 1개짜리 배치 파일이면 파티션이 **항상 1개** — 병렬도 1로 고정된다. 핫스팟이 "우리에겐 안 해당"이라는 판정도 **구조를 봐야** 갈린다.

## C. 결제 도메인 (F-20 ~ F-25)

> 출처: 원본 `C-payment.md` §F-20~F-25 · **결제 도메인 일반의 실패로 서술**(프로젝트 고유 식별자는 일반화).\
> 다른 점: **되돌리기가 비싸고, 상대(매입사·원장·정산)가 있고, 조용히 틀리는 것이 많고, 발견이 늦으면 배수로 는다.**\
> 그래서 이 도메인은 *"막는 것"* 보다 *"빨리 아는 것"* 에 더 투자한다.

### F-20 이중 결제·이중 출금

```text
① 요청 전달   전문이 두 번 온다        (F-11 중복)
② 내부 처리   재시도가 두 번 반영       (F-01 · F-09)
③ 응답 유실   상대가 못 받아 다시 보냄   (두 장군)  ★ 가장 흔하고 가장 안 보인다
```

- **뿌리** — ③에서 *우리는 성공했는데 상대는 모른다*. 그래서 **"성공/실패" 2분류가 부족**하다.
- **실사건** — 카카오페이(2022): 이것을 **성공/실패/`Unknown` 3분류**로 정면 인정. *"돈은 나갔는데 주문은 실패"* 가 그 상태의 이름이다.
- **막는 법** — **멱등 키(유니크 제약)** + **취소 예약(tombstone)**(취소가 원 승인보다 먼저 와도 나중 승인을 무효화) + **원자적 상태 이동**(*"격리 집합에 있다=미반영, 처리 집합에 있다=반영"* — 원자 이동이 곧 멱등).

> ★ **경계 배정 하나가 이중 출금 방어선이 되는 자리가 있다.** 후속 배치가 미반영인데 재시도가 또 출금하는 경로를, 그 조작을 배치의 참여자로 묶어 막는다.

### F-21 정산 불일치 — 탐지가 늦다

```text
우리 기록          상대 파일          원장
승인 100건    vs   매입 98건    vs    전표 99건
                       ↑                ↑
                  2건 미도착        1건 기표 누락
```

- **뿌리** — 세 곳이 각자 정본을 주장한다. 대사는 **어느 것이 틀렸는지 판정하지 않고 적재만** 한다(원인이 우리/상대 어느 쪽인지 모르므로).
- **실사건** — Revolut $20M (2022): 시스템 불일치로 거절된 거래를 자사 자금으로 환불. **자체 대사가 아니라 파트너 은행이 통보해서 알았다** — 탐지 시점이 핵심.
- **막는 법(세 가지 실패를 각각)** — ① **대사가 안 도는 것**(가장 나쁘다 — *"며칠째 안 돈다"* 를 누가 언제 보는지, 알림 임계 사슬) ② **허위를 쏟는 것**(노이즈가 신호를 죽인다 → 커트오프) ③ **틀린 기준으로 보는 것**.

### F-22 초과 승인

```text
계좌잔액  100      실제로 있는 돈
홀딩       30      이미 점유된 돈 (승인은 났고 매입 전)
가용잔액   70      ★ 새 승인이 쓸 수 있는 돈 = 계좌잔액 − 홀딩
```

- **뿌리** — 가용잔액이 아니라 **계좌잔액으로 판단하면 이미 점유된 돈을 다시 승인**한다. 뚫리는 네 경로: ① 동시성(F-01) ② 오래된 값(F-04) ③ **장애 중 검증 우회** ④ 가용화 시점(입금이 결제완료보다 먼저 쓸 수 있게 됨).
- **실사건** — Bank of Ireland 2023(장애 중 잔액 검증 우회 → ATM 인출 몰림) · Chase 2024(수표 가용화가 결제완료보다 빨라 *"무한 돈 버그"*).
- **막는 법** — **네 층**: 가용잔액 기준 + 홀딩·한도·승인을 **한 커밋**에 + **낙관적 락**(F-01) + **복제본 금지**(F-04).

> ★ **degraded 승인 모드가 설계에 아예 없는 것 자체가 방어다.** *"검증 불가 시 개별 요청 거절"* 이면 ③의 경로가 존재하지 않는다 — **없어서 못 뚫린다.**

### F-23 전표 누락·중복

- **뿌리** — 복식부기(*차변 합계 = 대변 합계*)는 **전표 하나의 균형만** 보장한다.

```text
보장하는 것              ★ 보장하지 않는 것
전표 내부의 차대 균형     있어야 하는 전표가 없는 것
                        같은 사실이 두 번 기표된 것 (각각은 균형)
                        금액이 틀린 것 (틀린 금액도 균형일 수 있다)
```

- **실사건** — Citi/Revlon $900M(2020, 체크박스 3개 중 1개, 3인 검토 전원 통과) · Deutsche Bank €28bn(2018) · 삼성증권(2018, 배당 오류로 **발행총수의 30배** 생성 — *"총량을 넘을 수 없다"* 는 불변식이 없어 아무 검사에도 안 걸림).
- **막는 법** — 누락은 **Outbox**(F-10), 중복은 **sourceEvent 유일 제약**(F-11), 어느 이벤트가 어느 줄을 쓰나는 **이벤트 소유 규칙**(한 이벤트는 자기가 단독 소유한 분개만 기표) + **총량 불변식**.

> ★ **시산표가 맞는데 틀린 상태가 가능하다** — 이것이 이 유형이 안 보이는 이유다.

### F-24 문서·설정 잔재 — 한 곳만 고친다

- **증상** — 본문은 맞는데 **요약표가 옛날 값**. 틀린 쪽이 스스로를 틀렸다고 말하지 않는다.
- **뿌리** — 같은 사실이 두 곳에 손으로 적혀 있고 한 곳만 고친다. 코드에서도 같다(*재사용된 플래그* — 의미는 바뀌었는데 이름은 그대로).
- **실사건** — Knight Capital(재사용된 플래그) · 삼성증권(발행총수 30배가 아무 검사에 안 걸림).
- **막는 법** — 같은 사실은 **단일 출처**로, 손으로 두 곳에 적었으면 **자동 대조 검사**. 사람은 *"지금 보는 문서"* 만 보지 두 곳을 동시에 펴 대조하지 않는다.

### F-25 조용한 실패 — 에러 없이 틀린다

```text
정상적 실패   예외·에러 코드·알림 → 안다
조용한 실패   그냥 진행된다        → ★ 모른다

비용(정상) = 그 건
비용(조용) = 그 건 × 발견까지의 기간
```

- **뿌리** — 부분 실패를 완료로 표시 · 무음 스킵 · 조용한 절단 · fail-open · **지표 자체가 없음**.
- **실사건** — Stripe RCA (2019): *"복제 지연 메트릭은 안 내면서 헬스체크는 정상 응답"* — 시스템이 *"나 괜찮다"* 고 말하고 있었다. *(연도 확인 필요)*
- **막는 법** — 부분 실패는 **모든 파티션 완료 전엔 완료가 아니다** + 무음 스킵 대신 **적재**(조용히 건너뛰지 않는다) + **지표 노출** + 검증이 실제로 도는지 감시.

> ★ **문서에도 조용한 실패가 있다** — *"이미 막고 있다"* 고 적어두면 아무도 다시 안 본다.\
> 그래서 이 카탈로그의 판정 기준을 **"이름을 댈 수 있으면 막힘, 문장뿐이면 뚫림"** 으로 둔 것이다. **silent failure는 실측 최다 사고 유형이다.**

## 핵심 문장

- **막는 것에 이름을 댈 수 있으면 막히고, 계약 문장뿐이면 뚫린다** — 주의력에 의존하는 규칙은 지켜지지 않는다.
- **"정상 동작"이 원인인 실패가 가장 어렵다** — 데드락 탐지·MVCC·온라인 DDL·GC 정지·롤링 배포는 전부 설계대로 동작한 결과다. 버그를 찾으면 안 나온다.
- **exactly-once 전달은 불가능하다** — at-least-once 전달 + 수신측 멱등(유니크 제약)이 결과적 한 번이다.
- **선언과 장치를 혼동하지 마라** — *"순서를 보장한다"·"멱등하다"* 는 문장이지 장치가 아니다. 목표값·요구사항도 장치가 아니다.
- **조용한 실패가 최다·최악이다** — 비용이 발견까지의 기간에 비례해 배수로 는다. 결제 도메인이 *"막는 것"* 보다 *"빨리 아는 것"* 에 투자하는 이유다.

## 용어 풀이

- **MVCC(다중 버전 동시성 제어)** — 행의 여러 버전을 두고 트랜잭션마다 자기 시점 버전을 보게 하는 것.
- **격리 수준(RC/RR)** — RC는 문마다 새 스냅샷(최신 커밋), RR은 트랜잭션 시작 시 한 스냅샷(끝까지 고정).
- **스냅샷** — 트랜잭션이 보는 *"그 시점의 사진"*. undo 로그로 옛 버전을 재구성해 만든다.
- **undo 로그 / purge** — 옛 버전 보관소(undo)와 그것을 지우는 청소(purge). 롱 트랜잭션이 purge를 막으면 undo가 쌓인다.
- **낙관적 락 / 비관적 락** — 전자는 잠그지 않고 저장 시 버전 확인, 후자는 `SELECT … FOR UPDATE`로 읽는 순간 잠금.
- **갭 락(gap lock)** — RR에서 범위 조회가 행 사이의 빈 공간까지 잠가 팬텀을 막는 것. INSERT와 충돌한다.
- **커넥션 풀** — DB 커넥션을 미리 만들어 두고 빌려 쓰는 것. 총 커넥션 = 인스턴스 × 풀 크기.
- **복제 지연(replication lag)** — Primary 커밋이 Replica에 적용되기까지의 시차. 이 사이 복제본은 옛 값을 준다.
- **read-your-writes / monotonic read** — *"내가 쓴 건 내가 본다" / "한 번 본 값보다 옛 값을 다시 안 본다"* 는 읽기 보장. 복제 지연이 깬다.
- **온라인 DDL(INSTANT/INPLACE/COPY)** — 메타데이터만/원본 재구성/새 테이블 복사. 복제본에선 논블로킹이 아닐 수 있다.
- **expand-contract** — 스키마를 새 것 추가 → 이행 → 옛 것 제거의 단계로 나눠, 구·신 버전이 공존해도 안 깨지게 하는 절차.
- **영속성 컨텍스트 / flush** — ORM이 변경을 모아두는 메모리와, 그것을 DB로 내보내는 시점.
- **채번** — 전역 유일 번호를 만드는 것. 중앙 시퀀스는 한 행에 직렬화, UUID는 인덱스 단편화.
- **두 장군 문제** — 네트워크로는 *"상대가 받았는지"* 를 확실히 알 수 없다는 근본 한계.
- **at-least-once / at-most-once / exactly-once** — 최소 한 번(중복 가능) / 최대 한 번(유실 가능) / 정확히 한 번(전달에선 불가능).
- **멱등(idempotent)** — 같은 요청을 여러 번 처리해도 결과가 한 번과 같은 것. 유니크 제약으로 구현해야 실제로 막힌다.
- **서킷 브레이커** — 실패율이 임계를 넘으면 즉시 거절해 대기(스레드 물림)를 없애는 장치.
- **지수 백오프 / 지터** — 재시도 간격을 1s→2s→4s로 늘리는 것 / 그 간격에 난수를 섞어 동시 재시도를 흩는 것.
- **벌크헤드** — 대상별 전용 풀을 둬 느린 대상이 다른 경로를 못 먹게 격리하는 것.
- **Outbox** — 사실과 이벤트를 같은 트랜잭션에 써 유실을 원천 차단하는 패턴.
- **DLQ(Dead Letter Queue)** — 영구 실패한 메시지를 옆으로 빼되 버리지 않고 사람이 볼 곳.
- **head-of-line blocking** — 앞의 한 건이 실패해 뒤 전부가 멈추는 것.
- **lease(임차) / fencing token** — 시한부 소유권 / 임차마다 받는 단조 증가 번호. lease만으론 좀비 쓰기를 못 막는다.
- **split-brain** — 네트워크 분단으로 양쪽이 각자 리더가 되어 양쪽에 쓰기가 들어가는 상태.
- **핫스팟 / 샤딩** — 한 키에 부하가 몰리는 것 / 키로 데이터를 나누는 것. 분할은 한 키를 못 쪼갠다.
- **가용잔액** — 계좌잔액 − 홀딩(점유액). 새 승인이 실제로 쓸 수 있는 돈.
- **복식부기** — 모든 전표에서 차변 합계 = 대변 합계. 전표 하나의 균형만 보장한다.
- **fail-closed / fail-open** — 확인이 안 되면 막는 것 / 통과시키는 것. 자금 경로는 fail-closed.
- **조용한 실패(silent failure)** — 에러 없이 틀리는 것. 부분 실패를 완료로, 무음 스킵, 조용한 절단, fail-open, 지표 부재.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문과 섞어 인출하지 않는다.

- **CAP 정리와 F-18.** split-brain은 CAP 정리(분단 P가 나면 일관성 C와 가용성 A 중 하나를 포기)의 실제 얼굴이다. GitHub이 택한 *"data integrity over site usability"* 는 **CP**(가용성을 버리고 일관성을 지킴)를 고른 것이다.
- **Saga와 F-10·F-20.** 두 저장소에 원자적으로 못 쓰는 문제(F-10)의 분산 트랜잭션판 해법이 **Saga**다 — 여러 로컬 트랜잭션 + 실패 시 보상 트랜잭션. Outbox는 그 각 단계의 이벤트를 안전하게 내보내는 하부 장치다.
- **멱등 키의 표준화.** 결제 API는 보통 `Idempotency-Key` 헤더(Stripe가 대중화)로 F-11·F-20을 처리한다 — 클라이언트가 요청마다 유일 키를 붙이고 서버가 그 키에 유니크 제약을 건다.
- **Little's Law로 F-03 보기.** 대기 시스템에서 *동시 처리 수 = 도착률 × 처리시간*. 처리시간(락 대기·느린 하위)이 늘면 같은 도착률에도 동시 커넥션 수요가 늘어 풀이 고갈된다 — F-16(타임아웃 역전)이 F-03·F-09로 이어지는 이유를 정량으로 설명한다.
- **"정상 동작이 원인"이라는 계열.** F-02(데드락 탐지)·F-05(MVCC purge)·F-06(온라인 DDL)·F-14(GC 정지)·F-15(스케줄러 이중화)·F-17(롤링 배포)은 모두 **기능이 설계대로 동작한 결과**가 장애다. 그래서 코드 리뷰로는 안 잡히고 **동작 원리를 알아야** 보인다 — 이 카탈로그가 *원리부터* 쓴 이유다.
