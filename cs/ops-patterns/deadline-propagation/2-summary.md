이 문서의 한 문장은 이것이다.\
**이 작업의 수명(lifetime)을 누가 소유하는가.**\
클라이언트에만 타임아웃이 있으면 수명의 소유자가 아무도 없다 — 클라이언트는 포기했는데 서버는 모르고, DB는 더더욱 모른다.\
그러면 클라이언트는 서버가 아직 하고 있는지 알 방법이 없어 다시 보낸다.\
중복 요청 문제는 이 방치의 **결과**다.

## 한눈에 — 쉽게 말하면

**데드라인 전파 = 주문서에 "몇 시까지"를 적어서 식당·라이더 모두가 같은 시각을 보게 하는 것.**

- 배달 앱에서 주문하고 30분을 기다리다 앱을 닫았다고 하자.\
  손님은 포기했지만 식당은 그 사실을 모른 채 조리를 계속하고, 라이더는 빈집에 배달한다.
- 손님은 "식당이 하고 있는지"를 알 길이 없으니 다시 주문한다.\
  이제 같은 음식이 두 벌이다.
- 주문서에 **"8시까지 도착"** 이라고 적혀 있고 식당·라이더가 그 시각을 본다면?\
  8시가 지난 주문은 조리를 시작하지 않고, 손님도 같은 8시에 포기한다.\
  **모두가 같은 시각을 보니 아무도 헛일을 하지 않는다.**

```text
타임아웃만 있을 때 (수명의 주인이 없다)  데드라인이 전파될 때 (한 시각을 공유)
+-------------------------------+        +-----------------------------------+
| 손님: 30분 기다리다 앱을 닫음 |        | 주문서: "8시까지 도착"            |
| 식당: 모른 채 조리를 계속함   |        | 식당·라이더가 같은 시각을 본다    |
| 라이더: 빈집에 배달           |        | 8시가 지나면 조리를 시작하지 않음 |
| 손님: 다시 주문 -> 두 벌이 됨 |        | 손님도 같은 8시에 포기            |
+-------------------------------+        +-----------------------------------+
  -> 포기가 아무에게도 전달되지 않는다     -> 만료된 주문은 시작조차 하지 않는다
```

서버도 **똑같은 구조다.**\
손님 = 클라이언트, 식당 = 애플리케이션 서버, 라이더 = DB·외부 API·큐 소비자.\
클라이언트 타임아웃은 "손님이 앱을 닫는 것"이고, 데드라인은 "주문서에 적힌 시각"이다.

> **타임아웃(timeout)** — 한쪽이 상대의 응답을 **얼마나 오래** 기다릴지 정한 상대 시간.\
> 예: "DB 응답을 3초까지 기다린다" — 내 인내심이지 작업의 수명이 아니다.

> **데드라인(deadline)** — 이 작업이 **언제까지** 끝나야 하는지 정한 절대 시각.\
> 예: "T+3초까지" — 호출을 타고 내려가며 모든 계층이 같은 시각을 본다.

> **고아 작업(orphaned work)** — 요청자가 이미 포기했는데 서버에서 계속 돌고 있는 작업.\
> 예: 사용자가 창을 닫았지만 서버는 30초짜리 집계 쿼리를 끝까지 돌린다.

실무 예: gRPC의 deadline(호출을 타고 자동 전파), Go `context.WithDeadline`, PostgreSQL `statement_timeout`, 큐 메시지에 동봉한 만료 시각.

## 문제 — 이 개념이 답하려는 질문

원본 코드 과제가 없는 개념 주제라, 이 문서가 답하려는 질문을 대신 둔다.

1. 클라이언트가 3초에 포기했다.\
   그 뒤 서버·DB·외부 API는 무엇을 하고 있고, 그 자원은 누가 돌려받나?
2. "남은 시간"을 어떻게 서버 진입점 → 작업 스레드 → DB 연결 → 외부 연결 → 큐로 넘기나?\
   각 계층에서 그 값은 **무슨 설정**이 되나?
3. 애플리케이션이 취소했는데 DB 서버에서 돌던 쿼리는 왜 따로 죽여야 하나?
4. 취소가 닿지 않는 곳(이미 커밋된 쓰기·보낸 메일·외부 결제 승인)에서는 무엇을 하나?
5. 취소된 작업의 기록은 성공 기록과 무엇이 다른가?
6. 앞단이 재시도하는데 뒷단은 아직 첫 요청을 처리 중이면 서버에는 무엇이 쌓이나?
7. 입구에서 만료된 요청을 **처리하지 않고 버리는** 층은 어떻게 생겼나?
8. 재시도·서킷브레이커·벌크헤드·백프레셔·멱등키·싱글플라이트·우아한 종료는 데드라인과 어디서 어긋나나?

아래 서머리는 이 여덟 질문을 순서대로 분석·정리한 것이다.

## 전체 흐름

```text
데드라인을 정한다       클라이언트(또는 최초 진입점)가 "T+3s 까지"를 절대 시각으로 정한다
      v
진입점에서 읽는다       헤더로 온 상대 시간을 내 시계의 절대 시각으로 바꿔 요청에 붙인다
      v
남은 예산을 센다        남은 예산 = 만료 시각 - 지금. 0 이하면 시작하지 않는다
      v
하위에 넘긴다           스레드(취소 신호) · DB(문장/락/유휴 제한) · 외부(연결+읽기 <= 남은 예산) · 큐(만료 시각 동봉)
      v
만료되면 취소한다       실행 중인 것에 취소 신호. DB 서버에서 도는 쿼리는 따로 죽인다
      v
취소가 안 닿는 곳       이미 커밋된 것·보낸 것은 "보상"으로 되돌린다
      v
기록한다                "취소됐다"와 "어디까지 했다"를 남긴다 — 성공 기록과 다른 종류의 기록
```

> **예산(budget)** — 데드라인까지 남은 시간.\
> 예: 만료가 T+3000ms 이고 지금이 T+180ms 면 예산은 2820ms 다 — 계층을 내려갈수록 줄기만 한다.

> **전파(propagation)** — 상위가 가진 만료 시각을 하위 호출에 그대로 넘기는 것.\
> 예: 앱 서버가 받은 "T+3s"를 DB 쿼리 제한과 외부 API 호출 타임아웃으로 바꿔 넘긴다.

## 1. 타임아웃 ≠ 데드라인 — 상대 시간은 곱해지고, 절대 시각은 하나다

**언제 쓰나**: "타임아웃은 다 걸어 뒀는데" 왜 사용자가 9초를 기다리는지 모를 때.

전 상태 — 게이트웨이·앱·DB·외부 API가 저마다 3초 타임아웃을 걸었다:

```text
타임아웃만 — 상대 시간, 구간마다 따로 센다
  게이트웨이 --(앱 응답을 3초 기다림)--> 앱 --(DB 응답을 3초 기다림)--> DB
                                        앱 --(외부 응답을 3초 기다림)--> 외부 API
  앱의 최악: DB 3초 + 외부 3초 = 6초를 쓰고 나서야 실패를 안다
  게이트웨이: 3초에 이미 떠났다 -> 나머지 3초는 아무도 안 기다리는 일

데드라인 — 절대 시각, 호출을 타고 내려간다
  게이트웨이  "T+3.0s 까지"
      v
  앱          "T+3.0s 까지" (같은 시각을 받는다. 남은 예산 = 만료 - 지금)
      v
  DB          남은 예산 안에 못 끝나면 쿼리 중단
  외부 API    남은 예산 안에 못 끝나면 호출 중단
  최악: 3초 — 모두가 같은 시각에 멈춘다
```

그림 해설 (한 단계씩):

- 타임아웃은 **각 구간이 자기 인내심을 따로** 센다.\
  구간이 직렬로 이어지면 최악 대기는 합이 되고, 재시도까지 있으면 곱이 된다.
- 게이트웨이는 3초에 떠났는데 앱은 6초까지 일한다.\
  그 3초 동안의 일은 결과를 받을 사람이 없다 — 이것이 다음 절의 고아 작업이다.
- 데드라인은 **시각 하나**를 모두가 공유한다.\
  각 계층은 "얼마나 기다릴까"를 정하지 않고 "만료까지 얼마 남았나"를 **계산**한다.
- 계층이 깊어져도 최악 대기는 늘지 않는다.\
  대신 깊은 계층일수록 받는 예산이 작다 — 그래서 예산이 0이면 시작하지 않는 규칙이 필요하다(§3).

**비용**: 만료 시각을 요청과 함께 **실어 나르는** 비용 — 헤더 하나, 그리고 모든 하위 호출이 그 값을 읽도록 만드는 규율.\
값을 안 읽는 계층이 하나라도 있으면 그 계층부터 다시 타임아웃 세상이다.

- "바깥이 길고 안쪽이 짧아야 한다"는 계층 규칙 자체는 [failure-modes F-16](../failure-modes/2-summary.md)에 있다.\
  이 문서는 그 규칙을 **어떻게 실어 나르는가**를 다룬다.

## 2. 고아 작업 — 클라이언트가 끊어도 서버는 모른다

**언제 쓰나**: 클라이언트 타임아웃은 걸려 있는데 서버 쪽에 아무 제한이 없을 때 — 대부분의 서비스가 처음엔 이 모양이다.

전 상태 — 클라이언트만 3초 타임아웃, 서버·DB는 제한 없음, 쿼리 하나가 30초 걸린다:

```text
t=0     클라 ---요청---> 서버 ---쿼리---> DB
t=3     클라 타임아웃, 소켓 닫음         서버: 모른다 (소켓을 읽거나 쓰기 전엔)
t=3~    클라 재시도 ---> 서버(2번째 스레드) ---> DB(2번째 쿼리)
                                         1번째 쿼리도 아직 실행 중 (고아)
t=30    1번째 쿼리 끝 -> 닫힌 소켓에 응답을 쓰려다 그제야 끊김을 안다
```

  ↓ 데드라인을 요청에 실어 보내고, 서버·DB가 그 시각을 본다

후 상태:

```text
t=0     클라 ---요청 (만료 t=3)---> 서버 ---쿼리 (남은 예산으로 문장 제한)---> DB
t=3     클라 포기                          DB: 쿼리 중단, 커넥션 반납
                                           서버: "취소됨" 기록
t=3~    클라 재시도 ---> 서버 ---> DB      이전 작업은 없다 — 겹치지 않는다
```

그림 해설 (한 단계씩):

- 클라이언트가 소켓을 닫아도 서버는 **그 소켓을 다시 읽거나 쓰기 전까지** 모른다.\
  끊김을 감시하는 서버도 있지만(Go `net/http` 는 클라이언트 연결이 닫히면 `Request.Context()` 를 취소한다), 그 신호를 **하위 호출에 넘기지 않으면** 감시해도 소용없다.
- 그 사이 서버 스레드·DB 커넥션·행 락은 **계속 잡혀 있다.**\
  결과를 받을 사람이 없는데 자원은 쓴다.
- 클라이언트는 서버 상태를 모르니 재시도하고, 재시도가 **두 번째 고아**를 만든다.\
  고아는 하나씩 는다.
- 데드라인이 전파되면 DB가 스스로 쿼리를 끊고 커넥션을 돌려준다.\
  재시도가 와도 앞 작업과 겹치지 않는다.

**비용**: 서버가 "어디까지 했나"를 기록해야 한다(§5).\
그냥 끊는 것과 **끊었다고 남기는 것**은 다르다 — [19-graceful-shutdown](../19-graceful-shutdown/)이 버린 건수(abandoned)를 세는 것과 같은 자리다.

> **협조적 취소(cooperative cancellation)** — 밖에서 강제로 죽이는 게 아니라, 실행 중인 코드가 취소 신호를 **스스로 확인**하고 멈추는 방식.\
> 예: Go 에서 `ctx.Done()` 을 확인하지 않는 루프는 데드라인이 지나도 안 멈춘다.

> **취소 신호(cancellation signal)** — "이제 그만하라"를 실행 중인 코드에 전달하는 통로 — Go 의 `context`, .NET 의 `CancellationToken`, gRPC 의 deadline 초과 등.\
> 주의: 신호를 만들어 놓고 하위 함수에 안 넘기면 그 함수부터는 신호가 없는 것과 같다.

## 3. 전파 경로 — 진입점 → 작업 스레드 → DB 연결 → 외부 연결 → 큐

**언제 쓰나**: 데드라인을 받긴 했는데 **각 계층에서 무슨 설정으로 바꿔야 하는지** 모를 때.\
이 절이 이 문서에서 가장 두껍다 — 계층마다 예산이 "되는 것"이 다르다.

전 상태 — 클라이언트가 만료 T+3000ms 를 정해 보냈다(가상의 예, 값은 직접 계산):

```text
계층                 도착 시각    남은 예산   이 계층이 하위에 넘기는 값
진입점(핸들러)       T+20ms       2980ms      만료 시각 그대로 (T+3000)
    v
풀에서 커넥션 획득   T+170ms      2830ms      획득 대기 상한 = 남은 예산 (여기서 150ms 를 썼다)
    v
DB 쿼리              T+180ms      2820ms      문장 제한 = 남은 예산에서 응답 처리 여유를 뺀 값
    v
외부 API 호출        T+900ms      2100ms      연결 + 읽기 합이 남은 예산 안. 상대에게도 만료 시각을 넘김
    v
큐에 후속 작업 넣기  T+2400ms     600ms       메시지에 만료 시각(T+3000) 동봉
    v
소비자가 꺼냄        T+3100ms     -100ms      만료 -> 처리하지 않고 버린다
```

그림 해설 (한 단계씩):

- 예산은 **줄기만 한다.**\
  어느 계층도 자기 아래에 자기가 받은 것보다 큰 값을 넘길 수 없다(Go `context.WithDeadline` 은 부모보다 늦은 만료를 주면 부모 값을 그대로 쓴다).
- 풀 획득 대기 150ms 는 **쿼리를 시작하기도 전에** 쓴 예산이다.\
  이 시간을 예산에서 안 빼면 쿼리 제한이 실제 남은 시간보다 길어진다.
- 큐에 넣은 작업은 만료 시각을 **메시지 안에** 들고 간다.\
  소비자가 꺼낸 시각이 만료 뒤면 처리하지 않는다.

이제 계층별로 본다.

### 3-1. 진입점 — 상대 시간으로 받아 절대 시각으로 바꾼다

- 서버 사이의 **시계는 서로 다르다.**\
  그래서 선로 위에는 절대 시각이 아니라 **남은 시간**(상대값)을 싣고, 받는 쪽이 자기 시계로 절대 시각을 다시 만든다.
- gRPC 가 이 모양이다 — 클라이언트는 절대 데드라인을 갖고, 요청 헤더 `grpc-timeout` 에는 남은 시간이 실리며, 서버는 받은 시점에 다시 절대 시각으로 만든다.\
  데드라인이 지나면 상태 코드 `DEADLINE_EXCEEDED` 로 끝난다.
- HTTP 에는 표준 헤더가 없다.\
  직접 정한 헤더(예: 남은 밀리초)를 쓰되, **모든 진입점이 같은 이름을 읽어야** 한다 — 하나가 안 읽으면 거기서 전파가 끊긴다.
- 프록시 계층에 이미 정해 둔 이름이 있으면 그것부터 본다 — Envoy 는 상류로 `x-envoy-expected-rq-timeout-ms` 를 붙인다.\
  다만 이 값은 **라우트에 설정된 타임아웃 값 그대로**라, 여기까지 오는 데 이미 쓴 시간을 뺀 "남은" 예산이 아니다.\
  이름이 비슷해도 **남은 시간 헤더가 아니라 "기대 처리 시간" 헤더**다 — 전파의 함정이 바로 이 자리다. 홉마다 자기 라우트 타임아웃을 다시 써 넣으면 예산은 줄지 않고 홉마다 되살아난다.
- 헤더가 없으면 **서버가 기본 데드라인을 만든다.**\
  "데드라인 없음"을 "무한"으로 두면 §2 의 고아가 그대로 생긴다.

> **시계 차이(clock skew)** — 서로 다른 기계의 시계가 같은 순간에 다른 값을 가리키는 것.\
> 예: 절대 시각 "12:00:03.000"을 그대로 보내면 받는 쪽 시계가 2초 느릴 때 예산이 2초 늘어난다 — 그래서 남은 시간으로 보낸다.

### 3-2. 작업 스레드 — 취소 신호를 넘기지 않으면 없는 것과 같다

- 진입점이 만든 데드라인은 **함수 인자로** 아래로 내려가야 한다.\
  Go 는 `ctx` 를 첫 인자로 넘기는 관례가 그것이고, gRPC 서버 구현에서 들어온 컨텍스트를 하위 gRPC 호출에 그대로 넘기면 데드라인이 자동으로 따라간다.
- 스레드 풀에 작업을 던지는 순간이 **가장 자주 끊기는 자리**다.\
  새 스레드는 부모의 데드라인을 모른다 — 작업 객체에 만료 시각을 같이 담아야 한다.
- 취소는 협조적이다.\
  CPU 만 도는 긴 루프는 취소 신호를 **주기적으로 확인**해야 멈춘다.

**비용**: 모든 시그니처에 데드라인(또는 컨텍스트)이 끼어든다.\
그 대신 "이 함수는 언제까지 끝나야 하는가"가 코드에 드러난다.

### 3-3. DB 연결 — 세 가지 제한, 풀 획득 대기, 그리고 서버에서 따로 죽이기

DB 쪽 제한은 하나가 아니라 **세 개**이고, 각각 막는 실패가 다르다(PostgreSQL 17 부터는 넷째가 더 있다 — 아래).\
아래 이름은 PostgreSQL 기준이다(MySQL 은 뒤에 따로).

```text
BEGIN
  v
UPDATE ... 락을 기다리는 중          <- lock_timeout: 락을 이만큼 기다리면 포기한다
  v
UPDATE ... 실행 중                   <- statement_timeout: 문장 하나가 이만큼 넘으면 중단한다
  v
(앱이 다른 일 하느라 세션이 노는 중) <- idle_in_transaction_session_timeout: 트랜잭션을 연 채
                                        이만큼 놀면 세션을 끊는다 (잡고 있던 락도 풀린다)
  v
COMMIT
```

그림 해설 (한 단계씩):

- **문장 수준 제한**(`statement_timeout`) — 쿼리 하나가 오래 걸리는 것을 막는다.\
  남은 예산을 여기에 넣는다 — PostgreSQL 은 `SET LOCAL statement_timeout` 으로 트랜잭션 단위로 바꿀 수 있다.
- **락 대기 제한**(`lock_timeout`) — 남이 잡은 락을 **기다리다** 예산을 다 쓰는 것을 막는다.\
  문장 제한과 다르다 — 실행이 느린 게 아니라 시작을 못 하고 있는 상태를 끊는다.
- **트랜잭션 연 채 노는 세션 제한**(`idle_in_transaction_session_timeout`) — 앱이 트랜잭션을 열어 두고 외부 API 를 기다리는 동안 **락과 커넥션을 물고 노는** 세션을 끊는다.\
  앱 스레드가 고아가 됐을 때 DB 쪽에서 스스로 정리하는 마지막 방어선이다.
- 세 값의 PostgreSQL 기본값은 모두 0 — **꺼져 있다.**\
  안 켜면 이 절의 어느 것도 일어나지 않는다.
- PostgreSQL 17 부터는 네 번째로 **`transaction_timeout`** 이 있다 — 트랜잭션 **하나의 총 수명**에 상한을 걸고, 명시 트랜잭션과 암묵(단일 문장) 트랜잭션 모두에 적용되며, 넘기면 문장만 끊는 게 아니라 **세션을 끝낸다.** 기본값은 역시 0(꺼짐).\
  주의: 위 세 제한 "위에 얹히는" 게 아니라 **더 짧은 쪽이 이긴다** — 문서는 `transaction_timeout` 이 `statement_timeout` 이나 `idle_in_transaction_session_timeout` 보다 짧거나 같으면 **더 긴 쪽이 무시된다**고 한다.
- MySQL 의 `max_execution_time` 은 **read-only 이고 top-level 인 SELECT 에만** 적용되는 밀리초 단위 제한이다.\
  "SELECT 전용"보다도 좁다 — 서브쿼리·파생 테이블에는 걸리지 않고, 스토어드 프로그램 안의 SELECT 에서는 **무시된다.**\
  락 대기는 InnoDB 의 `innodb_lock_wait_timeout`(초 단위, 기본 50초)이 따로 본다.\
  "DB 는 원래 이렇다"가 아니라 제품마다 제한의 범위가 다르다 — 쓰는 DB 의 문서로 확인해야 한다.

> **문장 제한(statement timeout)** — 쿼리 한 문장의 실행 시간 상한.\
> 예: PostgreSQL `statement_timeout`, MySQL `max_execution_time`(top-level read-only SELECT 전용).

> **락 대기 제한(lock wait timeout)** — 다른 트랜잭션이 잡은 락이 풀리기를 기다리는 시간의 상한.\
> 예: PostgreSQL `lock_timeout`, InnoDB `innodb_lock_wait_timeout` — 실행이 느린 게 아니라 시작을 못 하는 상태를 끊는다.

> **유휴 트랜잭션(idle in transaction)** — 트랜잭션을 열어 둔 채 아무 문장도 보내지 않고 노는 세션 상태.\
> 예: 앱이 `BEGIN` 뒤 외부 API 응답을 기다리는 동안 — 락은 잡혀 있고 커넥션은 반납되지 않는다.

**애플리케이션이 취소해도 DB 서버의 쿼리는 따로 죽여야 한다.**

- 앱 스레드가 취소 신호를 받고 함수를 빠져나와도, DB 서버 프로세스는 **자기가 받은 쿼리를 계속 실행한다.**\
  앱이 커넥션을 닫아 버려도 서버 쪽 실행이 즉시 멈춘다는 보장은 없다.
- 그래서 취소를 **서버에 알리는 별도 경로**가 있는데, 성격이 둘로 나뉜다 — 섞어 놓으면 "앱이 `pg_cancel_backend` 를 부르는구나"로 잘못 읽힌다.
  - **드라이버가 보내는 것(앱이 자동으로 타는 경로)** — PostgreSQL 프로토콜의 취소 요청(CancelRequest)은 드라이버가 **새 연결을 열어** 보내는 메시지다. MySQL 쪽에서 같은 자리에 오는 것이 `KILL QUERY` 이고, JDBC 에서 이 경로의 입구가 `Statement.cancel()` 이다.
  - **운영자가 부르는 것** — PostgreSQL 의 `pg_cancel_backend(pid)` 는 **다른 세션에서 부르는 SQL 함수**다. 사람이 쓰는 도구이고 권한이 필요하며, 앱이 자기 쿼리를 끊는 통로가 아니다.\
    `pg_terminate_backend(pid)` 는 한 단계 더 나가 **세션까지 끝낸다**(SIGTERM).
  - 그리고 PostgreSQL 문서는 취소 요청이 "효과가 있을 수도 없을 수도 있다(might or might not have any effect)"고 **못 박는다** — **보냈다고 멈춘다는 보장이 없다.**
- JDBC 의 `Statement.setQueryTimeout(초)` 도 "취소를 대신 보내 주는 설정"은 아니다.\
  **명세가 요구하는 것은 제한을 넘기면 `SQLTimeoutException` 을 던지는 것까지**이고, 그 순간 서버에 취소를 보낼지는 **드라이버마다 다르다**(MySQL Connector/J 는 `KILL QUERY`, pgJDBC 는 CancelRequest 를 보내지만 둘 다 명세 밖의 구현 선택이다).
- 드라이버가 컨텍스트 취소를 서버 취소 요청으로 **자동으로 바꿔 주는지도 드라이버마다 다르다.**\
  Go 공식 문서가 `database/sql` 에 대해 이 점을 직접 적는다 — **"Drivers that do not support context cancellation will not return until after the query is completed."** 컨텍스트 취소를 지원하지 않는 드라이버에서는 데드라인이 지나도 **쿼리가 끝나기 전에는 호출이 돌아오지도 않는다.**
- 요약하면 취소 경로는 **보장이 아니다** — 보낼 수 있는지도, 보내서 먹히는지도 확실하지 않다.\
  그래서 앱 쪽 취소에 기대지 않고 위의 **서버 쪽 제한(문장 제한·락 대기 제한)을 같이** 건다.

**커넥션 풀 — 얻기까지 기다리는 시간도 예산이다.**

```text
풀 크기 10, 요청마다 쿼리 1개, 클라이언트 타임아웃 3초, 느린 쿼리 하나가 30초 걸리기 시작
(가상의 예, 값은 직접 계산)

t=0   [c c c c c c c c c c]   전부 여유
t=3   [X c c c c c c c c c]   X = 클라는 떠났는데 쿼리는 30초 진행 중 (고아가 커넥션을 문다)
t=6   [X X c c c c c c c c]   재시도가 같은 느린 쿼리를 또 시작 -> 고아가 하나씩 는다
t=30  [X X X X X X X X X X]   10개 전부 고아. 새 요청은 풀 앞에서 대기
t=31  풀 획득 대기 -> 클라 타임아웃 -> 재시도 -> 또 풀 앞에서 대기      멀쩡한 요청도 여기서 죽는다
```

그림 해설 (한 단계씩):

- 고아 작업은 **커넥션을 물고** 있다.\
  풀은 유한하니 고아가 늘수록 남는 커넥션이 준다.
- 풀이 마르면 **느린 쿼리와 무관한 요청**까지 풀 앞에서 기다리다 타임아웃된다.\
  증상은 "DB 가 느리다"로 보이는데 DB 는 고아 쿼리 열 개를 열심히 돌리고 있을 뿐이다.
- 풀에서 커넥션을 **얻기까지 기다린 시간**(HikariCP 의 `connectionTimeout`, 기본 30000ms)도 예산 안에 있어야 한다.\
  남은 예산이 200ms 인데 획득 대기 상한이 30초면, 획득한 순간 이미 만료다 — 획득 대기 상한도 남은 예산으로 잘라야 한다.
- 반납이 빠지면 풀은 **영구히** 준다.\
  HikariCP 의 `leakDetectionThreshold`(기본 0 = 꺼짐)는 이 누수를 로그로 드러내는 설정이다.

> **커넥션 풀(connection pool)** — 미리 열어 둔 DB 연결을 빌려 쓰고 돌려주는 창고.\
> 예: 크기 10 이면 동시에 10개 쿼리까지 — 11번째는 누군가 돌려줄 때까지 기다린다.

> **획득 대기(acquire wait)** — 풀에서 커넥션을 빌리려고 줄 서는 시간.\
> 주의: 쿼리를 시작하기도 전에 쓰는 예산이라, 이 시간을 빼지 않으면 쿼리 제한이 실제보다 길어진다.

> **커넥션 누수(connection leak)** — 빌린 커넥션을 돌려주지 않아 풀이 영구히 줄어드는 것.\
> 예: 예외 경로에서 반납을 빠뜨리면 한 번에 하나씩 사라져, 며칠 뒤 "풀이 왜 0이지"로 나타난다.

- 풀 고갈이 증설로 더 나빠지는 사례는 [failure-modes F-03](../failure-modes/2-summary.md)에 있다.\
  이 문서의 초점은 **고아가 풀을 마르게 하는 경로**다.

### 3-4. 외부 연결 — 연결과 읽기는 다르고, 남은 예산을 빼서 넘긴다

```text
호출 하나의 시간 조각          어느 타임아웃이 보나
연결 수립 (TCP 핸드셰이크)     연결 타임아웃 — 상대가 살아 있나
    v
요청 전송                      (쓰기 타임아웃이 따로 있는 라이브러리도 있다)
    v
첫 바이트를 기다림             읽기 타임아웃 — 상대가 응답을 주고 있나
    v
본문을 끝까지 읽음             읽기 타임아웃이 "바이트 사이 간격" 기준이면 총 시간을 못 막는다
    v
합계                           데드라인이 보는 것은 이 합계다 — 조각 타임아웃의 합이 아니다
```

그림 해설 (한 단계씩):

- **연결 타임아웃**은 "상대에게 닿나"를, **읽기 타임아웃**은 "상대가 응답을 주고 있나"를 본다.\
  둘은 다른 실패를 잡는다 — 연결은 되는데 응답이 안 오는 상대에게 연결 타임아웃은 아무 소용이 없다.
- 읽기 타임아웃이 **바이트 사이 간격**인 라이브러리가 있다 — Python `requests` 문서는 read timeout 을 "서버가 보내는 바이트 **사이**를 기다리는 초 수(다만 **99.9% 의 경우 이것은 서버가 첫 바이트를 보내기까지의 시간이다**)"라고 적는다.\
  즉 문서가 나머지 **0.1%** 를 스스로 인정하는 것이고, 그 0.1% 는 천천히 한 바이트씩 오는 응답이다 — 그런 응답은 영원히 안 끊긴다.\
  "쓸모없다"가 아니라 "총 시간의 상한은 아니다"가 맞는 말이고, 그 상한은 데드라인이 따로 봐야 한다.
- 하위 호출에는 **남은 예산에서 여유를 뺀 값**을 넘긴다.\
  응답을 받은 뒤 처리할 시간, 결과를 쓸 시간이 그 여유다.
- 남은 예산이 **0 이하면 호출하지 않고 즉시 실패한다.**\
  이미 만료된 요청으로 상대를 때리는 것은 상대의 자원을 헛되이 쓰는 일이다.

> **연결 타임아웃(connect timeout) / 읽기 타임아웃(read timeout)** — TCP 연결이 맺어지기까지 기다리는 상한 / 응답 데이터를 기다리는 상한.\
> 예: 상대 호스트가 꺼져 있으면 연결 타임아웃, 상대가 살아 있는데 느리면 읽기 타임아웃이 잡는다.

**비용**: 많이 빼면 하위가 할 수 있던 일을 못 하고, 적게 빼면 하위는 끝났는데 상위가 결과를 못 쓴다.\
여유를 얼마나 뺄지는 계산이 아니라 **선택**이다.

### 3-5. 큐 — 꺼낸 작업이 이미 만료됐으면 처리하지 않고 버린다

```text
큐: [ m1(만료 T+3.0) | m2(만료 T+3.5) | m3(만료 T+9.0) ]      지금 = T+3.2
(가상의 예, 값은 직접 계산)

소비자가 m1 을 꺼냄 -> 만료 지남      -> 처리하지 않고 버린다 (버렸다고 세고 기록한다)
소비자가 m2 를 꺼냄 -> 0.3초 남음     -> 남은 예산 0.3초로 처리 (최소 처리 시간보다 짧으면 시작도 안 한다)
소비자가 m3 를 꺼냄 -> 5.8초 남음     -> 정상 처리
```

그림 해설 (한 단계씩):

- 큐에 앉아 있는 시간도 예산을 먹는다.\
  그래서 메시지가 **자기 만료 시각을 들고** 있어야 소비자가 판단할 수 있다.
- 줄에서 얼마나 기다릴지는 **리틀의 법칙**으로 대강 잡힌다 — **대기 시간 = 큐 길이 ÷ 처리율.**\
  처리율이 초당 100건인데 앞에 500건이 서 있으면 5초다 — 예산이 3초면 그 줄의 뒤쪽은 꺼내 보기도 전에 이미 전부 만료다.
- 꺼냈을 때 이미 만료면 **처리하지 않는다.**\
  결과를 받을 사람이 없고, 처리하는 동안 뒤의 멀쩡한 메시지가 더 늦어진다.
- 큐 제품의 메시지 TTL 은 **큐 안에 앉아 있는 동안**의 만료를 다룬다 — 제품에 따라 그마저 없기도 하다(SQS 에는 메시지마다 거는 TTL 이 없다).\
  꺼낸 뒤 처리하는 시간까지 데드라인 안에 들어가야 하니, 소비자가 만료 시각을 직접 보는 검사는 어차피 따로 필요하다.
- 버린 것은 **센다.**\
  [05-backpressure](../05-backpressure/)의 DROP 정책이 dropped 를 세는 것과 같은 이유다 — 안 세면 잃는지도 모른다.

## 4. 취소가 닿지 않는 곳 — 중단이 아니라 보상

**언제 쓰나**: 데드라인이 지나 취소했는데, 작업이 **이미 밖으로 나간 효과**를 남겼을 때.

롤백과 보상이 어떻게 다른지는 [08-saga](../08-saga/)가 정면으로 가르친다 — 여기서는 그 대비를 줄이고, **데드라인 고유의 질문** 하나만 본다: 초과 시점이 커밋 **전**이었나 **뒤**였나.

```text
단계                     데드라인이 지났을 때 할 수 있는 것
입력 검증                중단 (흔적 없음)
    v
DB 쓰기 (트랜잭션 안)     중단 = 롤백 (흔적 없음)
    v
COMMIT                   ---- 여기가 경계다 ----
    v
외부 결제 승인 호출       중단 불가. 승인 취소를 따로 요청해야 한다 (보상)
    v
메일 발송                중단 불가. 정정 메일을 보내는 수밖에 없다 (보상)
    v
응답 쓰기                클라이언트는 이미 없다. 기록만 남는다
```

그림 해설 (한 단계씩):

- 커밋 **전**이면 롤백이 곧 취소라 흔적이 없고, 커밋 **뒤**부터는 되돌릴 방법이 "반대 동작을 하는 것"뿐이다 — 그것이 보상이고, 취소가 아니라 새 작업이다(자세한 것은 08-saga).
- 외부 결제 승인·메일·SMS·타 시스템 호출도 커밋 뒤와 같은 자리다 — 보냈으면 보낸 것이고, 상대가 이미 처리했을 수 있다.
- 그래서 데드라인 초과 시점이 **어디였는지**가 중요하다.\
  같은 "취소"라도 커밋 전이면 없던 일, 커밋 뒤면 보상 작업이 생긴다.

> **보상(compensation)** — 이미 일어난 효과를 반대 동작으로 상쇄하는 것.\
> 예: 결제 승인은 못 되돌리니 "승인 취소"를 따로 요청한다 — 취소가 아니라 새 요청이다.

**비용**: 보상은 **실패할 수 있는 또 하나의 작업**이다.\
보상 자체에도 데드라인과 재시도가 필요하고, 그것이 사가([08-saga](../08-saga/))가 다루는 문제다.

## 5. 취소해도 남겨야 하는 것 — 감사 로그

**언제 쓰나**: "취소됐으니 아무 일도 없었다"고 생각하고 싶어질 때.

- **취소됐다는 사실 자체가 기록 대상이다.**\
  언제, 어느 계층에서, 남은 예산이 얼마일 때 취소됐는지 — 이것이 없으면 데드라인이 짧은 건지 일이 느린 건지 구별할 수 없다.
- **수행 기록과 성공 기록은 다르다.**\
  "실행했다"는 단계마다 남고, "성공했다"는 끝에 한 번 남는다.\
  취소된 작업은 수행 기록은 있는데 성공 기록이 없는 상태다.
- 그 차이가 **부분 효과의 추적**을 가능하게 한다.\
  §4 의 경계 어디까지 갔는지를 수행 기록이 말해 주고, 그것으로 보상이 필요한지 판단한다.

```text
성공한 작업            취소된 작업 (커밋 뒤에 취소됨)      (가상의 예, 값은 직접 계산)
수행: 검증 v           수행: 검증 v
수행: DB 쓰기 v        수행: DB 쓰기 v
수행: 커밋 v           수행: 커밋 v
수행: 결제 승인 v      취소: 데드라인 초과 (결제 승인 직전, 예산 -40ms)
수행: 메일 v           (성공 기록 없음)
성공: v                -> 커밋은 됐고 결제는 안 갔다: 보상은 DB 쪽만
```

- 기록이 없으면 "취소됐다"가 "안 일어났다"로 읽힌다.\
  [19-graceful-shutdown](../19-graceful-shutdown/)이 즉시 종료의 진짜 문제를 "버리는 것이 아니라 보고하지 않는 것"이라 한 것과 같은 자리다.

> **감사 로그(audit log)** — 무엇이 언제 누구에 의해 일어났는지를 남기는, 나중에 되짚기 위한 기록.\
> 예: "T+3040ms 결제 승인 직전 데드라인 초과로 취소" 한 줄이 있어야 보상 범위를 정할 수 있다.

> **부분 효과(partial effect)** — 작업이 끝까지 못 가고 멈췄을 때 이미 남긴 변경.\
> 예: 커밋은 됐는데 결제 승인은 안 간 상태 — 수행 기록이 어디까지 갔는지 말해 준다.

## 6. 중복 요청과 재시도 증폭 — 클라이언트가 서버 상태를 모를 때

**언제 쓰나**: 앞단이 타임아웃으로 재시도하는데 뒷단은 아직 첫 요청을 처리 중일 때.

전 상태 — 앞단 타임아웃 3초·**총 3시도**(최초 1 + 재시도 2), 뒷단 처리 10초, 데드라인 전파 없음(가상의 예, 값은 직접 계산):

```text
t=0   클라 시도 1 ---> 서버: 작업 A 시작 (10초짜리)
t=3   클라 포기, 시도 2 ---> 서버: 작업 B 시작        A 진행 중
t=6   클라 포기, 시도 3 ---> 서버: 작업 C 시작        A, B 진행 중
t=9   클라 최종 실패                                  A, B, C 전부 진행 중 (셋 다 고아)
t=10  A 완료 -> 결과 받을 사람 없음
t=13  B 완료 -> 같은 일이 두 번째로 끝남 (쓰기였다면 두 번 반영)
t=16  C 완료 -> 세 번째

서버 입장: 요청 1개가 일 3벌이 됐다.  클라 입장: 실패 1번.
```

그림 해설 (한 단계씩):

- 클라이언트는 A 가 돌고 있는지 **알 방법이 없다.**\
  그래서 §2 의 고아가 재시도 횟수만큼 **복제**된다.
- 서버는 같은 일을 세 벌 한다.\
  읽기면 자원 낭비로 끝나지만, 쓰기면 세 번 반영된다.
- 이것이 "타임아웃 × 재시도 = 증폭"이다.\
  재시도 정책이 좋아도(지터·백오프) 뒷단이 첫 요청을 안 버리면 곱셈은 그대로다.

  ↓ 데드라인이 전파되면

- 서버는 A 를 t=3 에 스스로 끊는다.\
  B 가 시작될 때 A 는 없다.
- 재시도가 와도 같은 데드라인을 들고 온다.\
  전체 예산이 3초면 시도 2·3 은 **예산이 0 이라 시작하지 않는다** — [01-retry-backoff](../01-retry-backoff/)의 Retryer 가 멈추는 이유 4(데드라인)가 정확히 이 자리다.

> **재시도 증폭(retry amplification)** — 앞단의 재시도가 뒷단에 같은 일을 여러 벌 쌓는 현상.\
> 예: 타임아웃 3초·총 3시도(최초 1 + 재시도 2) 앞에 10초짜리 작업이 있으면 요청 1개가 일 3벌이 된다.

- 재시도가 몰려 시스템 전체 부하를 밀어 올리는 쪽은 [failure-modes F-09 재시도 폭풍](../failure-modes/2-summary.md)이다.\
  **축이 다르다** — F-09 는 *여러 클라이언트의 총 부하*를 보고, 이 절은 *한 요청이 서버 안에 3벌로 남는 것*을 본다. 한 클라이언트만 재시도해도 이 절의 증폭은 일어난다.

**비용**: 데드라인이 전파되면 "느리지만 끝날 수 있던 일"도 끊는다.\
그것이 맞는 거래인 이유는 — 결과를 받을 사람이 이미 없기 때문이다.

## 7. 입구에서 서버를 지키는 층 — 만료된 요청은 처리하지 않고 버린다

**언제 쓰나**: §6 의 증폭을 서버 **입구**에서 막고 싶을 때.\
네 가지 장치가 있고, 각각은 자기 챕터가 있다 — 여기서는 **데드라인과 만나는 자리**만 본다.

```text
요청 도착
    v
[승인 제어]  남은 예산 <= 0 이거나 최소 처리 시간보다 짧으면 -> 받지 않고 즉시 실패
    v
[멱등키]     같은 키의 기록이 있으면 -> 재생 또는 409 (판정 자체가 예산 안에 끝나야 한다)
    v
[요청 병합]  같은 키의 계산이 진행 중이면 -> 그 결과를 기다린다 (내 예산이 먼저 끝나면 나만 떠난다)
    v
[부하 차단]  자리가 없으면 -> 만료에 가까운 것부터 버린다
    v
처리
```

- **승인 제어** — 서버가 요청을 **받을지 말지**를 입구에서 정한다.\
  데드라인 관점의 규칙은 하나다: **만료된 요청은 처리하지 않고 버린다.**\
  처리하면 결과를 받을 사람이 없고, 그 시간에 뒤의 멀쩡한 요청이 늦어진다.
- **멱등키** — 무엇인지는 [06-idempotency-store](../06-idempotency-store/).\
  데드라인과 만나는 자리: 키로 "같은 요청"을 알아보는 **판정 자체가 예산 안에** 끝나야 하고, 첫 요청이 IN_PROGRESS 인데 그 첫 요청이 고아라면 409 를 받은 재시도는 **그 기록의 TTL 이 끝날 때까지**(스트라이프처럼 24시간이면 하루 내내) 계속 "처리 중"을 본다.\
  06 은 기록에 `expiresAtMillis` 를 두고 만료된 것을 없는 것으로 보며 `purgeExpired` 가 지우니 IN_PROGRESS 는 **언젠가 스스로 풀리긴 한다** — 문제는 그 "언젠가"가 요청의 예산과 아무 상관이 없다는 것이다.\
  첫 요청에 데드라인이 있어야 IN_PROGRESS 가 **초 단위로** 풀린다.
- **요청 병합** — 무엇인지는 [09-stampede](../09-stampede/)의 싱글플라이트.\
  데드라인과 만나는 자리: 기다리는 99개 중 하나가 만료됐다고 **공유 계산을 취소하면 안 된다** — 그 하나만 떠나야 한다.\
  반대로 대표의 계산이 대표의 데드라인으로 끊기면 99개가 같이 실패한다 — 공유 계산의 데드라인은 대기자 중 가장 늦은 것 이상이어야 한다.
- **부하 차단** — 무엇인지는 [04-rate-limiter](../04-rate-limiter/)·[05-backpressure](../05-backpressure/).\
  데드라인과 만나는 자리: 버릴 때 **만료에 가까운 것부터** 버리면 잃는 것이 "어차피 못 쓸 결과"가 된다.\
  05 의 네 정책(새것/옛것/재움/던짐)에는 이 기준이 없다 — 만료 시각을 항목에 담아야 가능한 다섯 번째 선택이다.

> **승인 제어(admission control)** — 서버가 요청을 받을지 입구에서 결정하는 것.\
> 예: 남은 예산이 0 이하인 요청은 처리하지 않고 즉시 실패로 돌려보낸다.

> **부하 차단(load shedding)** — 감당 못 할 부하를 입구에서 일부러 버리는 것.\
> 예: 자리가 없을 때 만료에 가까운 요청부터 버린다 — 잃는 것이 "어차피 못 쓸 결과"가 된다.

> **요청 병합(request coalescing)** — 같은 키의 동시 요청을 하나의 계산으로 합치는 것.\
> 예: 09 의 싱글플라이트 — 대표 한 명이 계산하고 나머지는 결과를 받는다.

**비용**: 입구 층 자체가 시간을 쓴다.\
멱등키 조회·승인 판정이 느리면 그 시간만큼 예산이 줄고, 판정이 예산을 넘기면 지키려던 요청을 입구가 죽인다.

## 8. 패턴이 서로를 배신하는 자리

각 패턴이 무엇인지는 자기 챕터에 있다.\
여기는 **데드라인과 만나면 어긋나는 모양**과 맞추는 법만 적는다.\
표의 **괄호 안은 각 챕터의 장치 이름**이며, 이 문서에 처음 나오는 이름에는 반 줄 풀이를 같이 달았다.

| 패턴 | 데드라인과 만나는 자리 | 어긋나는 모양 | 맞추는 법 |
|---|---|---|---|
| [01 재시도](../01-retry-backoff/) | 시도마다 타임아웃, 사이에 백오프 | 타임아웃 × 시도 수가 전체 예산을 넘는다. 남은 시간보다 긴 백오프를 잔다 | 시도마다 남은 예산을 다시 센다. 백오프가 남은 예산보다 길면 자지 않고 포기(01 의 이유 4) |
| [02 서킷브레이커](../02-circuit-breaker/) | OPEN 이면 0ms 에 실패 | 남은 예산이 통째로 남는다 — 폴백에 쓸지 즉시 올려보낼지 정해진 게 없다. 반대로 내 예산이 짧아 난 DEADLINE_EXCEEDED 를 상대 실패로 세면 멀쩡한 상대의 회로가 열린다 | 즉시 실패 뒤의 예산 사용처를 정한다. 실패 술어(어떤 예외를 회로의 실패로 셀지 정하는 함수)에서 "내 예산 부족"과 "상대 장애"를 구별한다 |
| [03 벌크헤드](../03-bulkhead/) | 칸을 얻으려고 기다리는 시간 | 획득 대기가 예산을 먹는데 쿼리 제한은 대기 전 값으로 잡혀 있다 | 획득 대기 상한 = 남은 예산(03 은 보장 칸 + 공용 여유분 구조라 시간 제한 대기를 공용에서만 하는데, 내 칸도 기다리고 공용도 기다리면 호출자가 준 시간 약속이 두 배가 되기 때문 — 같은 자리다) |
| [04 레이트 리미터](../04-rate-limiter/) | 누출 버킷(요청을 줄 세워 일정 속도로만 내보낸다)의 줄 세우기 | 줄에서 기다리다 만료된 요청이 나간다 — 나가봐야 받을 사람이 없다 | 나가는 시각이 만료 뒤면 줄에서 빼서 버린다 |
| [05 백프레셔](../05-backpressure/) | 큐에 앉아 있는 시간 | 리틀의 법칙(대기 시간 = 큐 길이 ÷ 처리율)으로 대기가 예산을 넘는 큐 길이면 큐 뒤쪽은 전부 만료 — 그런데 지표는 초록이다(버린 것 0·에러 0 인데 대기만 자란다) | 항목에 만료 시각을 담고, 꺼낼 때 검사하고, 버릴 때 만료 임박부터 |
| [06 멱등키](../06-idempotency-store/) | IN_PROGRESS 기록("이 키는 지금 처리 중") | 첫 요청이 고아면 IN_PROGRESS 가 **기록 TTL 이 끝날 때까지**(24시간짜리면 하루 내내) 안 풀려 재시도가 계속 409 | 첫 요청에 데드라인 — 만료되면 기록을 FAILED 로 바꿔 재선점을 허용 |
| [09 싱글플라이트](../09-stampede/) | 99개가 대표의 계산을 기다림 | 대기자 하나의 만료가 공유 계산을 취소하거나, 대표의 만료가 99개를 같이 죽인다 | 대기자는 자기 예산이 끝나면 혼자 떠난다. 공유 계산의 데드라인은 대기자 중 가장 늦은 것 이상 |
| [19 우아한 종료](../19-graceful-shutdown/) | 배수 기한(배수 = 새 요청은 거절하고 처리 중인 것만 끝내는 단계, 기한 = 그것을 기다려 주는 최대 시간) | 기한을 "최악 요청"으로 잡으라는데 최악이 얼마인지 모른다 | 데드라인이 전파되면 최악 = 진행 중인 것들의 남은 예산 최댓값 — 배수 기한을 정할 근거가 생긴다 |

- 표의 공통 구조: 각 패턴은 **자기 시간**(백오프·대기·큐·기록 수명)을 갖고 있고, 그 시간이 요청의 예산과 **따로 놀 때** 배신이 일어난다.\
  맞추는 법도 하나다 — 그 시간을 남은 예산으로 자른다.

## 핵심 문장

- 타임아웃은 각 구간의 인내심(상대 시간)이라 **곱해지고**, 데드라인은 작업의 만료 시각(절대 시각)이라 **하나**다 — 계층이 깊어져도 최악 대기가 늘지 않는 대신 깊은 계층일수록 받는 예산이 작다.
- 클라이언트에만 타임아웃이 있으면 수명의 주인이 없다 — 서버·DB 는 포기를 모르고 자원을 계속 물며(고아), 클라이언트는 서버 상태를 몰라 다시 보낸다(중복). **중복은 방치의 결과다.**
- 전파는 계층마다 다른 설정이 된다 — 스레드엔 취소 신호, DB 엔 문장/락/유휴 세 제한, 풀엔 획득 대기 상한, 외부엔 연결+읽기 ≤ 남은 예산, 큐엔 메시지에 동봉한 만료 시각.\
  그리고 **앱이 취소해도 DB 서버의 쿼리는 따로 죽여야 한다.**
- 취소가 닿는 곳은 커밋 전까지다 — 그 뒤는 중단이 아니라 **보상**이고, 어디까지 갔는지는 **성공 기록이 아니라 수행 기록**이 말해 준다.\
  취소됐다는 사실도 기록이다.
- 만료된 요청은 처리하지 않고 **버린다** — 결과를 받을 사람이 없고, 처리하는 시간에 뒤의 멀쩡한 요청이 늦어진다.\
  각 패턴이 가진 자기 시간(백오프·대기·큐·기록 수명)을 남은 예산으로 자르지 않으면 패턴이 서로를 배신한다.

## 용어 풀이

- **타임아웃(timeout)**: 한쪽이 상대의 응답을 얼마나 오래 기다릴지 정한 상대 시간.\
  내 인내심이지 작업의 수명이 아니다.
- **데드라인(deadline)**: 작업이 언제까지 끝나야 하는지 정한 절대 시각.\
  호출을 타고 내려가며 모든 계층이 같은 시각을 본다.
- **예산(budget)**: 데드라인까지 남은 시간.\
  계층을 내려갈수록 줄기만 한다.
- **전파(propagation)**: 상위가 가진 만료 시각을 하위 호출에 그대로 넘기는 것.
- **고아 작업(orphaned work)**: 요청자가 이미 포기했는데 서버에서 계속 돌고 있는 작업.\
  스레드·커넥션·락을 물고 있다.
- **협조적 취소(cooperative cancellation)**: 실행 중인 코드가 취소 신호를 스스로 확인하고 멈추는 방식.\
  확인하지 않는 루프는 안 멈춘다.
- **취소 신호(cancellation signal)**: "그만하라"를 실행 중인 코드에 전달하는 통로(Go `context`, .NET `CancellationToken`, gRPC deadline 초과).
- **시계 차이(clock skew)**: 서로 다른 기계의 시계가 같은 순간에 다른 값을 가리키는 것.\
  그래서 선로에는 절대 시각이 아니라 남은 시간을 싣는다.
- **문장 제한(statement timeout)**: 쿼리 한 문장의 실행 시간 상한.\
  PostgreSQL `statement_timeout`, MySQL `max_execution_time`(top-level read-only SELECT 전용).
- **락 대기 제한(lock wait timeout)**: 남이 잡은 락이 풀리기를 기다리는 시간의 상한.\
  실행이 느린 게 아니라 시작을 못 하는 상태를 끊는다.
- **유휴 트랜잭션(idle in transaction)**: 트랜잭션을 열어 둔 채 아무 문장도 보내지 않고 노는 세션 상태.\
  락은 잡혀 있고 커넥션은 반납되지 않는다.
- **커넥션 풀(connection pool)**: 미리 열어 둔 DB 연결을 빌려 쓰고 돌려주는 창고.
- **획득 대기(acquire wait)**: 풀에서 커넥션을 빌리려고 줄 서는 시간.\
  쿼리를 시작하기도 전에 쓰는 예산.
- **커넥션 누수(connection leak)**: 빌린 커넥션을 돌려주지 않아 풀이 영구히 줄어드는 것.
- **연결 타임아웃 / 읽기 타임아웃(connect / read timeout)**: 연결이 맺어지기까지의 상한 / 응답 데이터를 기다리는 상한.\
  다른 실패를 잡는다.
- **보상(compensation)**: 이미 일어난 효과를 반대 동작으로 상쇄하는 것.\
  취소가 아니라 새 작업이다.
- **감사 로그(audit log)**: 무엇이 언제 일어났는지를 나중에 되짚기 위해 남기는 기록.\
  "취소됐다"도 기록 대상이다.
- **부분 효과(partial effect)**: 작업이 끝까지 못 가고 멈췄을 때 이미 남긴 변경.\
  수행 기록이 어디까지 갔는지 말해 준다.
- **재시도 증폭(retry amplification)**: 앞단의 재시도가 뒷단에 같은 일을 여러 벌 쌓는 현상.
- **승인 제어(admission control)**: 서버가 요청을 받을지 입구에서 결정하는 것.\
  만료된 요청은 받지 않는다.
- **부하 차단(load shedding)**: 감당 못 할 부하를 입구에서 일부러 버리는 것.\
  만료 임박부터 버리면 잃는 것이 어차피 못 쓸 결과가 된다.
- **요청 병합(request coalescing)**: 같은 키의 동시 요청을 하나의 계산으로 합치는 것.
- **IN_PROGRESS**(06 의 용어): 멱등 장부가 "이 키는 지금 처리 중"으로 표시해 둔 기록 상태.\
  기록에는 유효 기간(TTL)이 있어 만료되면 없는 것으로 친다.
- **409 Conflict**(06 의 용어): "지금 처리 중이니 나중에 다시 와라"는 HTTP 응답 코드.\
  기다리게 하지 않고 즉시 돌려보내는 선택이다.
- **재생(replay)**(06 의 용어): 같은 키가 또 왔을 때 작업을 다시 실행하지 않고 **저장해 둔 응답을 그대로 돌려주는 것.**
- **리틀의 법칙(Little's Law)**: 대기 시간 = 큐 길이 ÷ 처리율.\
  줄이 길고 처리율이 낮으면 뒤쪽은 꺼내기도 전에 만료다.
