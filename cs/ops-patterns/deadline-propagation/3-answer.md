# ops-patterns/deadline-propagation — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.\
> 이 파일은 [1-question.md](1-question.md)의 질문에 1:1로 대응한다. 근거는 [2-summary.md](2-summary.md)의 절 번호로 적었고, 이 주제는 원본 코드가 없어 근거가 개념(일반 지식)에만 있는 답에는 `(원본에 근거 없음 — 내 추론)` 을 붙였다.\
> 제품 설정 이름은 답에 필요한 곳에만 쓰고, 값은 서머리에서 확인한 것만 쓴다.

## 정답

**1. (왜)** 타임아웃은 **각 구간이 자기 인내심을 따로 세는 상대 시간**이라, 구간이 직렬로 이어지면 최악 대기가 합이 된다 — 앱은 DB 3초를 다 쓰고 나서 외부 API 3초를 또 쓸 수 있으니 6초, 게이트웨이의 3초까지 더하면 9초다.\
그동안 게이트웨이는 3초에 이미 떠났으므로 뒤의 6초는 아무도 안 기다리는 일이다.\
데드라인은 **만료 시각 하나를 모두가 공유**하므로 각 계층이 "얼마나 기다릴까"를 정하지 않고 "만료까지 얼마 남았나"를 계산한다.\
합칠 인내심이 없으니 곱셈이 사라지고, 계층이 깊어져도 최악 대기는 3초다 — 대신 깊은 계층일수록 받는 예산이 작아진다. (§1)

**2. (예측)** 순서는 이렇다. (§2·§3-3)\
① t=3 클라이언트가 소켓을 닫지만 서버는 그 소켓을 다시 읽거나 쓰기 전까지 모른다 — 스레드·커넥션·행 락은 그대로 잡혀 있다(고아).\
② 클라이언트는 서버 상태를 모르니 재시도하고, 재시도가 두 번째 스레드·두 번째 쿼리·두 번째 고아를 만든다.\
③ 고아마다 커넥션을 하나씩 물고 있으니 재시도가 반복될수록 풀의 남은 커넥션이 준다.\
④ 풀이 마르는 순간부터 **느린 쿼리와 무관한 요청**도 풀 앞에서 획득 대기를 하다 클라이언트 타임아웃을 맞는다 — 그 요청의 재시도가 또 풀 앞에 줄을 선다.\
⑤ t=30 첫 쿼리가 끝나 닫힌 소켓에 응답을 쓰려 할 때에야 서버는 끊김을 안다.\
멀쩡한 요청이 죽기 시작하는 지점은 "풀이 마르는 순간"이고, 증상은 "DB 가 느리다"로 보이지만 DB 는 고아 쿼리를 열심히 돌리고 있을 뿐이다.

**3. (경계)** 앱이 취소 신호로 함수를 빠져나와도 **DB 서버 프로세스는 자기가 받은 쿼리를 계속 실행한다** — 앱이 커넥션을 닫아도 서버 쪽 실행이 즉시 멈춘다는 보장은 없다.\
그래서 취소를 서버에 알리는 별도 경로가 있는데 성격이 둘로 갈린다: **드라이버가 보내는 것**(PostgreSQL 프로토콜의 CancelRequest — 드라이버가 새 연결을 열어 보낸다, MySQL 의 `KILL QUERY`, JDBC 에서는 `Statement.cancel()` 이 그 입구)과 **운영자가 부르는 것**(`pg_cancel_backend(pid)` 는 다른 세션에서 부르는 SQL 함수·권한 필요, `pg_terminate_backend` 는 세션까지 종료).\
어느 쪽도 보장이 아니다 — PostgreSQL 문서는 취소 요청이 "효과가 있을 수도 없을 수도 있다"고 못 박고, JDBC 명세가 요구하는 것은 `setQueryTimeout` 의 제한을 넘기면 `SQLTimeoutException` 을 던지는 것까지이지 서버에 취소를 보내는 것이 아니다(보낼지는 드라이버 구현 선택).\
드라이버가 컨텍스트 취소를 서버 취소 요청으로 자동으로 바꿔 주는지도 드라이버마다 다르다 — Go 문서는 `database/sql` 에 대해 "컨텍스트 취소를 지원하지 않는 드라이버는 쿼리가 끝나기 전에는 돌아오지 않는다"고 적는다.\
그래서 앱 쪽 취소에 기대지 않고 서버 쪽 제한을 **같이** 건다. (§3-3)\
세 제한이 막는 실패는 각각 다르다:\
- **문장 제한**(PostgreSQL `statement_timeout`) — 쿼리 하나가 *실행이 느린* 것을 끊는다.\
- **락 대기 제한**(`lock_timeout`) — 실행이 느린 게 아니라 남이 잡은 락 때문에 *시작을 못 하는* 상태를 끊는다.\
- **유휴 트랜잭션 제한**(`idle_in_transaction_session_timeout`) — 앱이 트랜잭션을 열어 둔 채 외부 응답을 기다리느라 *락과 커넥션을 물고 노는* 세션을 끊는다(잡고 있던 락도 풀린다) — 앱 스레드가 고아가 됐을 때 DB 쪽 마지막 방어선이다.\
세 값은 PostgreSQL 기본값이 0(꺼짐)이라 안 켜면 아무것도 일어나지 않고(17 의 `transaction_timeout` 은 트랜잭션 총 수명을 보되 "위에 얹히는" 게 아니라 더 짧은 쪽이 이긴다), MySQL 의 `max_execution_time` 은 top-level read-only SELECT 에만 걸리는 등 **제품마다 제한의 범위가 다르다.**

**4. (경계)** 하위에 넘기는 값은 **남은 예산(만료 시각 − 지금)에서 응답 처리 여유를 뺀 값**이다 — 어느 계층도 자기가 받은 것보다 큰 값을 아래로 넘길 수 없다. (§3·§3-4)\
남은 예산이 0 이하면 **호출하지 않고 즉시 실패**한다 — 이미 만료된 요청으로 상대를 때리는 것은 상대 자원을 헛되이 쓰는 일이다.\
연결·읽기 타임아웃만으로 부족한 이유는 둘이 **조각**을 보기 때문이다: 연결 타임아웃은 "상대에게 닿나", 읽기 타임아웃은 "응답을 주고 있나"를 보고, 읽기 타임아웃이 바이트 사이 간격 기준인 라이브러리(Python `requests` 가 문서에 그렇게 명시)에서는 한 바이트씩 천천히 오는 응답이 영원히 안 끊긴다.\
데드라인이 보는 것은 연결 + 전송 + 첫 바이트 + 본문의 **합계**이고, 조각 타임아웃의 합은 그 합계의 상한이 아니다.\
큐로 넘길 때도 같다 — 메시지에 만료 시각을 동봉하고, 꺼냈을 때 만료면 처리하지 않고 버리며 버린 것을 센다. (§3-5)

**5. (왜)** 경계는 **COMMIT** 이다 — 트랜잭션 안의 쓰기는 롤백이 곧 취소라 흔적이 없지만, 커밋 뒤와 외부 결제 승인·메일·SMS 처럼 이미 밖으로 나간 효과는 되돌릴 방법이 "반대 동작을 하는 것"뿐이고 그것이 보상이다. 보상은 취소가 아니라 실패할 수 있는 **새 작업**이다. (§4)\
"종류가 다르다"는 말은 **수행 기록**("이 단계를 실행했다" — 단계마다 남는다)과 **성공 기록**("끝났다" — 끝에 한 번 남는다)이 별개라는 뜻이다 — 취소된 작업은 수행 기록은 있는데 성공 기록이 없는 상태다. (§5)\
그리고 "취소됐다"는 사실 자체(언제·어느 계층·남은 예산 얼마일 때)가 기록 대상이다.\
이 기록이 없으면 ① 부분 효과가 어디까지 갔는지 몰라 보상 범위를 정할 수 없고 ② "취소됐다"가 "안 일어났다"로 읽히며 ③ 데드라인이 짧은 건지 일이 느린 건지 구별할 수 없다.

**6. (연결 — 01)** 서버에는 **일 3벌**이 쌓인다 — 총 3시도(최초 1 + 재시도 2)라 t=0 에 A, t=3 첫 재시도로 B, t=6 둘째 재시도로 C 가 시작되고 셋 다 10초짜리라 t=9 클라이언트가 최종 실패한 뒤에도 셋 다 진행 중이다(셋 다 고아). 쓰기였다면 세 번 반영된다. (§6)\
데드라인이 전파되면 서버가 A 를 t=3 에 스스로 끊어 B 와 겹치지 않고, 재시도는 같은 만료 시각을 들고 오므로 전체 예산 3초에서 시도 2·3 은 예산이 0 이라 시작하지 않는다.\
Retryer 의 넷(성공·영구 실패·횟수 소진·데드라인) 중 **이유 4 데드라인**이 이 자리다 — "다음 대기가 남은 시간보다 길면 자지 않고 포기"가 곧 "남은 예산 0 이면 시도하지 않는다"이다.\
재시도 정책(지터·백오프)이 아무리 좋아도 뒷단이 첫 요청을 안 버리면 곱셈은 그대로라, 증폭을 끊는 것은 정책이 아니라 뒷단의 데드라인이다. `(정책만으로 부족하다는 결론은 서머리 §6·§8의 정리 — 원본 코드 근거 없음, 내 추론)`

**7. (연결 — 06·09)** (§7·§8)\
- **멱등키**: 추가되는 판정은 둘이다 — ① "같은 요청인가"를 알아보는 장부 조회 자체가 **예산 안에** 끝나야 한다(판정이 예산을 넘기면 지키려던 요청을 입구가 죽인다), ② 첫 요청이 IN_PROGRESS 인데 그 첫 요청이 고아라면 재시도는 **그 기록의 TTL 이 끝날 때까지**(스트라이프처럼 24시간이면 하루 내내) 409 를 본다 — 06 의 `expiresAtMillis`·`purgeExpired` 가 언젠가 풀어 주긴 하지만 그 시점이 요청의 예산과 무관하다. 첫 요청에 데드라인이 있어야 만료 시 기록이 FAILED 로 바뀌어 06 의 "FAILED 자리 재선점"이 **초 단위로** 작동한다.\
- **싱글플라이트**: 추가되는 판정은 "누구의 만료가 무엇을 끊는가"다 — 대기자 99개 중 하나가 만료됐다고 **공유 계산을 취소하면 안 되고** 그 하나만 떠나야 하며, 반대로 대표의 계산이 대표의 데드라인으로 끊기면 99개가 같이 실패하므로 공유 계산의 데드라인은 대기자 중 가장 늦은 것 이상이어야 한다.\
- 어긋나는 모양은 공통이다 — 각 패턴이 가진 **자기 시간**(멱등 기록의 수명, 공유 계산의 수명)이 요청의 예산과 따로 놀 때 배신이 일어나고, 맞추는 법도 하나다: 그 시간을 남은 예산으로 자른다. `(멱등 기록을 FAILED 로 바꾸는 방식·공유 계산 데드라인의 하한은 서머리의 설계 제안 — 원본 코드 근거 없음, 내 추론)`
