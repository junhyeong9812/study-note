### A. 문제 (구현 대상 TODO)

#### 1. NonAtomicStore.tryBegin — 일부러 틀리게 쓴다

```java
// impl 정답 (일부러 틀린 기준선 — 고치지 않는다)
public boolean tryBegin(IdempotencyKey key, String fingerprint, long expiresAtMillis) {
    long now = ticker.nowMillis();

    // 1. 검사한다 (time of check)
    IdempotencyRecord existing = records.get(key);
    if (existing != null && !existing.isExpired(now) && existing.state() != RecordState.FAILED) {
        return false;
    }

    // ---- 여기가 틈이다 ----

    // 2. 실행한다 (time of use)
    records.put(key, IdempotencyRecord.beginning(key, fingerprint, expiresAtMillis));
    return true;
}
```

- Q: 이 클래스가 `ConcurrentHashMap` 을 쓰는데도 깨지는 이유는?
  A: `get` 도 `put` 도 각각은 원자적이지만 **두 연산 사이가 원자적이 아니기** 때문이다.
  자료구조가 스레드 안전하다는 것은 연산 하나하나가 안전하다는 뜻이지, 내가 만든 "보고 나서 쓴다"라는 복합 동작이 안전하다는 뜻이 아니다.

- Q: "스레드 안전한 자료구조를 썼다"와 "연산이 스레드 안전하다"는 무엇이 다른가?
  A: 앞의 것은 **자료구조의 단위**, 뒤의 것은 **내 로직의 단위**를 말한다.
  질문은 늘 "어느 단위가 원자적인가"이고, 여기서 원자적이어야 하는 단위는 "검사 + 선점"이라는 한 덩어리다.
  "ConcurrentHashMap 썼는데요"는 그 질문에 대한 답이 아니다.

- Q: 두 스레드가 동시에 들어오면 어느 줄과 어느 줄 사이에서 무슨 일이 벌어지는가?
  A: `get` 과 `put` 사이 — 둘 다 `get` 에서 null(또는 만료/FAILED)을 보고, 둘 다 `put` 하고, 둘 다 `true` 를 받는다.
  둘 다 "내가 선점했다"고 믿으므로 실행이 두 번 일어난다. TOCTOU(time-of-check to time-of-use) 결함의 교과서적인 모양이다.

- Q: 이 결함이 계약 테스트 22개를 전부 통과하는 이유는?
  A: 계약 테스트는 순서대로 부르기 때문이다 — 단일 스레드에서는 이 코드가 **완벽하게 동작한다.**
  틈은 두 스레드가 정확히 그 사이에 겹칠 때만 드러나고, 그런 상황은 경주 테스트(`StoreAtomicityTest`)를 따로 짜야 만들어진다.

- Q: 그래서 QA가 아무리 빨리 눌러도 재현이 안 되는 이유는?
  A: 사람의 두 번 클릭은 수십~수백 밀리초 간격이라 첫 요청의 `put` 이 이미 끝난 뒤이기 때문이다.
  이 결함은 마이크로초 단위로 겹쳐야 나타난다 — 그래서 운영에서 드물게, 재현 불가능한 형태로만 보고된다.

- Q: 500회 경주에서 승자가 둘 이상이던 라운드는 몇 번이었는가(두 저장소 비교)?
  A: `InMemoryIdempotencyStore`(compute) **0회**, `NonAtomicStore`(get 후 put) **17~53회**(3.4~10.6%, 한 라운드 최대 승자 4).
  드물지만 결제에서 3.4%는 재앙이다.

- Q: 틀린 코드를 남이 써준 것으로 보지 않고 직접 쓰게 하는 이유는?
  A: 남이 써준 코드가 깨지는 것과 **방금 자기가 친 코드**가 깨지는 것은 배움의 크기가 다르기 때문이다.
  게다가 이 모양이 사람이 처음 떠올리는 자연스러운 코드라, 직접 써봐야 "나도 이렇게 쓴다"는 사실을 인정하게 된다.

- Q: 이 클래스의 `complete`·`fail` 은 이미 `computeIfPresent` 로 원자적인데, 그럼에도 저장소 전체가 안전하지 않은 이유는?
  A: 안전성은 제일 약한 고리가 정하기 때문이다.
  선점(`tryBegin`)이 두 번 성공하는 순간 그 뒤의 모든 연산이 원자적이어도 실행은 이미 두 번 일어났다.
  원자성은 "필요한 그 자리"에 있어야 하고, 다른 자리에 있는 것은 보상이 안 된다.

#### 2. InMemoryIdempotencyStore.tryBegin — 이 문제의 전부

```java
// impl 정답
public boolean tryBegin(IdempotencyKey key, String fingerprint, long expiresAtMillis) {
    if (key == null) {
        throw new IllegalArgumentException("멱등성 키가 필요하다");
    }
    long now = ticker.nowMillis();
    boolean[] claimed = new boolean[1];          // 람다에서 바꿀 수 있는 그릇
    records.compute(key, (k, old) -> {
        if (old != null && !old.isExpired(now) && old.state() != RecordState.FAILED) {
            return old;                          // 못 잡았다 — 아무 일도 안 일어난다
        }
        claimed[0] = true;
        return IdempotencyRecord.beginning(k, fingerprint, expiresAtMillis);
    });
    return claimed[0];
}
```

- Q: 자리를 잡을 수 있는 세 경우는 각각 무엇이고, 왜 그 셋인가?
  A: ① 기록이 없다(처음 보는 키), ② 기록이 있는데 만료됐다(TTL이 지나 더 이상 유효하지 않다), ③ 기록이 있는데 FAILED 다(앞 요청이 실패했으니 다시 해볼 수 있어야 한다).
  나머지(살아 있는 IN_PROGRESS·COMPLETED)는 "남이 쓰고 있거나 이미 끝난 자리"라 잡으면 안 된다.

- Q: FAILED 자리를 다시 잡을 수 있게 하지 않으면 무슨 일이 생기는가?
  A: **일시 장애가 영구 실패로 승격된다.**
  DB가 잠깐 끊겨 실패한 결제가 그 키로는 영영 다시 시도되지 않고, 클라이언트는 같은 키를 다시 보낼 수밖에 없으니 계속 실패만 받는다.
  키를 바꿔서 보내면 그건 멱등성이 없는 새 요청이다.

- Q: `compute` 가 get-후-put 과 다른 점을 한 문장으로 말하면?
  A: **키마다 잠금을 잡고 람다를 부르기 때문에 판정과 쓰기가 한 연산 안에 있다** — 사이에 다른 스레드가 끼어들 틈이 없다.

- Q: 잡을 수 없을 때 람다가 `old` 를 그대로 반환해야 하는 이유는?
  A: `compute` 의 반환값이 곧 새 값이라, 다른 것을 돌려주면 남의 기록을 덮어쓰게 된다.
  `old` 를 그대로 돌려주는 것이 "아무 일도 안 일어난다"는 뜻이다(null 을 돌려주면 삭제가 된다).

- Q: `compute` 의 반환값으로 "내가 이겼나"를 판정하면 왜 틀리는가?
  A: 반환값은 최종 기록일 뿐 "누가 썼는지"를 말해주지 않기 때문이다.
  지문도 만료 시각도 같은 두 요청이면 최종 기록이 서로 구별되지 않아 **둘 다 자기가 이겼다고 판단한다.**
  그래서 람다 안에서 플래그를 세워 "이번 호출이 실제로 썼는가"를 직접 남긴다.

- Q: 그 실수를 우리 테스트가 잡아주는가(변종 검증 결과는)?
  A: 잡는다 — 반환값으로 판정하는 변종은 81개 테스트 중 4개를 무너뜨린다.
  틈이 아니라 판정 근거의 문제라 결정적으로 재현되기 때문이다.

- Q: 지역 변수 대신 `boolean[1]` 을 쓰는 이유는?
  A: 자바 람다는 바깥 지역 변수를 읽을 수만 있고(effectively final) 바꿀 수 없기 때문이다.
  배열 한 칸은 참조가 고정된 채로 내용만 바뀌므로 람다 안에서 값을 세울 수 있다.

- Q: 운영에서 이 자리에 Redis 나 RDB 가 올 때 요구되는 성질은 무엇 하나인가?
  A: **자리 선점이 원자적일 것** 하나다.
  Redis 면 `SET key value NX`, RDB 면 유니크 제약이 있는 INSERT — 저장 매체는 달라도 필요한 성질은 같다.

- Q: `now` 를 람다 밖에서 읽든 안에서 읽든 결과가 같은 이유는?
  A: `compute` 의 람다는 그 호출에서 키마다 **한 번만** 불리므로 시각을 읽는 위치가 결과를 바꾸지 않는다.
  그래서 우리 테스트가 이 둘을 구별하지 못하고(안 잡힌 변종 2개 중 하나), 구별할 필요도 없다 — 동치 변환이다.

#### 3. InMemoryIdempotencyStore.find — 만료는 없는 것으로

```java
// impl 정답
public Optional<IdempotencyRecord> find(IdempotencyKey key) {
    IdempotencyRecord record = records.get(key);
    if (record == null || record.isExpired(ticker.nowMillis())) {
        return Optional.empty();      // 지우지는 않는다
    }
    return Optional.of(record);
}
```

- Q: 만료를 여기서 안 거르면 구체적으로 무슨 사고가 나는가?
  A: 24시간 전 응답을 오늘 재생해준다.
  청소가 아직 안 돌았을 뿐인 기록을 유효한 것으로 취급하면, TTL 을 정한 의미가 사라지고 "언제까지 유효한가"가 청소 주기에 좌우된다.

- Q: 만료된 기록을 읽는 김에 지우지 않고 남겨두는 이유는(누구의 일인가)?
  A: 지우는 것은 `purgeExpired`(스위퍼)의 일이기 때문이다.
  읽기에서 지우면 조회가 쓰기가 되어 락·경합이 생기고, "만료는 없는 것으로 본다"는 판정과 "메모리를 돌려준다"는 청소가 뒤섞인다.
  판정과 청소를 나누면 청소 전략을 바꿔도 계약이 안 흔들린다.

- Q: 만료 판정이 `>` 가 아니라 `>=` 인 이유는?
  A: 만료 시각을 **유효하지 않은 첫 시각**으로 정했기 때문이다.
  `>` 로 쓰면 정확히 그 밀리초에 한 번 더 재생되어 경계가 한 칸 밀린다.

- Q: 그 경계를 어느 쪽으로 정하든 된다면, 그래도 정해야 하는 이유는?
  A: 정하지 않으면 구현마다 달라지고, 저장소를 갈아끼웠을 때 경계 하나에서 동작이 바뀌기 때문이다.
  경계는 한쪽으로 정하고 테스트로 못 박는다 — 04번 고정 창·02번 만료 판정에서 반복된 원칙이다.

#### 4. InMemoryIdempotencyStore.purgeExpired — 청소가 정확성을 깨면 안 된다

```java
// impl 정답
public int purgeExpired(long nowMillis) {
    int removed = 0;
    for (Map.Entry<IdempotencyKey, IdempotencyRecord> entry : records.entrySet()) {
        if (entry.getValue().isExpired(nowMillis)
                && records.remove(entry.getKey(), entry.getValue())) {   // 값이 아직 그것일 때만
            removed++;
        }
    }
    return removed;
}
```

- Q: 한 인자짜리 `remove(key)` 가 왜 정확성을 깨는가?
  A: "만료라고 판정한 시점"과 "지우는 시점" 사이에 다른 스레드가 그 키로 새 자리를 잡을 수 있기 때문이다(만료됐으니 잡을 수 있다).
  그러면 스위퍼가 **막 시작한 남의 IN_PROGRESS 기록을 지우고**, 그 요청은 나중에 다시 와서 두 번 실행된다.

- Q: 그 사고의 재현률은 얼마였는가?
  A: 2000회 중 55~60회다.
  청소는 정확성과 무관해 보이는데 실제로는 멱등성을 깨는 경로가 된다.

- Q: 두 인자짜리 `remove(key, value)` 가 막아주는 것은 정확히 무엇인가?
  A: "내가 만료라고 판정한 바로 그 기록일 때만 지운다"를 원자적으로 보장한다.
  그 사이에 값이 새 기록으로 바뀌었으면 지우지 않고 넘어간다 — compare-and-set 의 map 버전이다.

- Q: "청소는 메모리 얘기지 계약 얘기가 아니다"는 무슨 뜻인가?
  A: 청소는 저장소가 무한히 커지지 않게 하려는 최적화일 뿐, "한 번만 실행한다"는 계약에 영향을 주면 안 된다는 뜻이다.
  청소를 아예 안 돌려도 동작은 맞아야 하고(메모리만 커진다), 돌려도 동작이 달라지면 안 된다.

- Q: 이 결함이 `tryBegin` 의 원자성 결함과 구조적으로 같은 점은?
  A: 둘 다 **검사와 행동 사이의 틈**(TOCTOU)이다.
  `tryBegin` 은 "없는지 보고 쓴다", `purgeExpired` 는 "만료인지 보고 지운다" — 해법도 같다. 판정과 행동을 한 연산으로 묶는 API(`compute`, `remove(k,v)`)를 쓴다.

#### 5. IdempotentExecutor.execute — 네 갈래 판정

```java
// impl 정답
for (int attempt = 1; attempt <= MAX_SLOT_ATTEMPTS; attempt++) {   // MAX = 2
    if (store.tryBegin(key, requestFingerprint, expiresAt())) {
        executions.incrementAndGet();          // 실패해도 실행은 실행이다
        String response;
        try {
            response = action.call();
        } catch (Exception e) {
            store.fail(key);
            throw e;                            // 감싸지도 삼키지도 않는다
        }
        store.complete(key, response);
        return response;
    }

    IdempotencyRecord existing = store.find(key).orElse(null);
    if (existing == null) {
        continue;                               // 그 사이 만료·청소됐다
    }
    if (!existing.fingerprint().equals(requestFingerprint)) {
        throw new KeyReuseException(key, existing.fingerprint(), requestFingerprint);
    }
    if (existing.state() == RecordState.COMPLETED) {
        replays.incrementAndGet();
        return existing.response();
    }
    if (existing.state() == RecordState.IN_PROGRESS) {
        conflicts.incrementAndGet();
        throw new ConflictException(key);
    }
    // FAILED. 자리를 다시 잡으러 한 바퀴 더 돈다.
}
conflicts.incrementAndGet();
throw new ConflictException(key);
```

- Q: `executions` 를 `action.call()` **전에** 세는 이유는?
  A: 실패해도 실행은 실행이기 때문이다 — 부작용은 이미 일어났을 수 있다.
  뒤에서 세면 예외가 난 실행이 통계에서 사라지고, "몇 번 실제로 건드렸나"라는 질문에 거짓말을 한다.

- Q: action 이 던진 예외를 감싸거나 삼키면 호출자가 무엇을 못 하게 되는가?
  A: 재시도 가능 여부를 판단하지 못한다.
  타임아웃인지 400인지에 따라 재시도할지 포기할지가 갈리는데(01·02번의 "이 실패가 누구 탓인가"), 감싸면 그 정보가 가려진다.
  실행기는 판단을 대신하지 않고 그대로 전달한다.

- Q: 지문 검사가 상태 판정보다 먼저여야 하는 이유는?
  A: 같은 키에 다른 요청이 온 것은 **재시도가 아니라 클라이언트 버그**이기 때문이다.
  상태 판정을 먼저 하면 그 버그가 "정상적인 재생"으로 처리되어 조용히 틀린 응답이 나간다.

- Q: 1000원 결제 키로 50000원 결제가 오면 순서를 어기면 어떤 일이 벌어지는가?
  A: 1000원 결제의 옛 응답을 그대로 재생하고, 클라이언트는 **50000원이 결제됐다고 믿는다.**
  실제로는 아무 일도 안 일어났고 예외도 로그도 안 남는다 — 돈이 걸린 조용한 사고다.

- Q: 지문 검사를 COMPLETED 안쪽에만 두면 무엇이 빠지는가?
  A: IN_PROGRESS 인 경우가 빠진다.
  처리 중인 자리에 다른 요청이 와도 지문 불일치를 못 잡고 409만 주게 되는데, 그 클라이언트는 다시 와도 같은 상황이라 영영 원인을 모른다.

- Q: 같은 키에 다른 요청이 온 것을 "처리 중이니 다시 오라"로 답하면 왜 안 되는가?
  A: 다시 와도 같은 상황이기 때문이다 — 키가 같고 내용이 다르다는 사실은 시간이 지나도 안 바뀐다.
  409는 "잠시 뒤 해결될 일"에 쓰는 답이고, 이건 고쳐야 할 버그라 `KeyReuseException` 으로 분명히 거부한다.

- Q: COMPLETED 판정을 상태가 아니라 "응답이 null 인가"로 하면 무엇이 틀리는가?
  A: **null 은 정당한 응답**이다(void 에 가까운 작업).
  응답이 null 이라고 "안 한 것"으로 보면 이미 끝난 작업을 다시 실행한다 — 판정은 반드시 `state` 로 한다.

- Q: 재생할 때 `replays` 를 안 세면 운영에서 무엇을 모르게 되는가?
  A: "이 배포가 재시도를 얼마나 흡수했나"를 아무도 모른다.
  이 숫자는 운영에서 실제로 보는 값이고, 0이면 멱등성이 실제로는 안 돌고 있다는 신호일 수 있다(키를 시도마다 새로 만드는 경우처럼).

- Q: 자리 시도 횟수가 1이면 안 되고 무한이면 더 안 되는 이유는?
  A: 1이면 "졌는데 그 사이 만료됐다" 같은 순간에 멀쩡한 요청이 그냥 죽는다(find 가 빈 값을 주면 더 볼 것이 없다).
  무한이면 못 잡는 상황이 이어질 때 스레드가 거기 갇힌다 — 그래서 2로 정해두고, 다 돌고도 못 잡으면 409를 준다.

- Q: `find` 가 빈 값을 줬을 때 예외가 아니라 한 바퀴 더 도는 이유는?
  A: 선점에 졌는데 기록이 없다는 것은 그 사이 만료되거나 청소됐다는 뜻 — 즉 **지금은 자리가 비어 있다**는 뜻이다.
  여기서 실패로 끝내면 멀쩡히 처리할 수 있는 요청을 버린다.

- Q: `expiresAt()` 이 `now + ttl` 을 그냥 쓰지 않고 넘침을 검사하는 이유는(01번의 무엇과 같은 함정인가)?
  A: `Ticker` 는 단조 증가만 보장하고 원점이 임의라(System.nanoTime) 시각이 이미 크면 `now + ttl` 이 음수가 된다.
  그러면 기록이 태어나자마자 만료되어 **예외도 로그도 없이 멱등성이 통째로 꺼진다.**
  01번에서 백오프가 음수가 되어 재시도 폭풍이 됐던 것과 같은 함정이다.

### B. 개념

#### 6. 재시도의 말하지 않은 전제

- Q: "응답을 못 받았다 ≠ 실행이 안 됐다"를 결제 예로 설명하면?
  A: 서버가 포인트를 이미 깎고 응답을 보냈는데 그 응답만 네트워크에서 유실될 수 있다.
  클라이언트가 보기에는 "실패"지만 서버에서는 "성공"이고, 그 상태에서 재시도하면 두 번 깎인다.

- Q: `AtLeastOnceTest` 가 보여주는 숫자는 무엇이고 왜 그 숫자인가?
  A: 잔액이 9000이어야 하는데 8000이다.
  1000원짜리 결제 한 건이 응답 유실 + 재시도로 두 번 실행됐기 때문이다 — 이 챕터가 존재하는 이유를 한 줄로 보여준다.

- Q: 네트워크가 줄 수 있는 보장은 어디까지이고, exactly-once 는 누가 만드는가?
  A: 네트워크는 **at-least-once** 까지다(최소 한 번 도착, 대신 중복 가능).
  exactly-once 는 네트워크가 아니라 **수신자가 기록으로** 만든다 — 그 기록이 멱등성 키 저장소다.

- Q: 01번(재시도)과 06번은 어떤 관계인가?
  A: 01번이 만든 문제를 06번이 받는다.
  재시도는 가용성을 올리지만 중복 실행이라는 대가를 만들고, 그 대가는 보내는 쪽이 아니라 받는 쪽에서만 갚을 수 있다.

#### 7. 키를 누가 만드는가

- Q: 키를 서버가 만들면 왜 저장소와 원자적 선점이 다 있어도 두 번 실행되는가?
  A: 요청이 도착할 때마다 새 키가 생기므로 **재시도가 언제나 "처음 보는 키"** 가 되기 때문이다.
  저장소는 완벽하게 동작하지만 매번 다른 자리를 잡을 뿐이라 빈 껍데기가 된다.

- Q: 그때 측정 숫자(실행 횟수·재생 횟수)는 어떻게 나오는가?
  A: 실행 2회, 재생 0회(`WhoMakesTheKey`).
  멱등성 장치가 있는데 아무것도 흡수하지 못한 상태다.

- Q: 클라이언트가 만들어도 **시도마다** 새로 만들면 어떻게 되는가?
  A: 마찬가지다 — 재시도마다 키가 달라지면 서버가 만드는 것과 구별할 수 없다.
  키를 만드는 위치보다 **키가 재시도를 넘어 유지되는가**가 본질이다.

- Q: "키는 요청 단위지 시도 단위가 아니다"를 한 문장으로 풀면?
  A: 하나의 논리적 요청(같은 결제 건)에 키 하나를 붙이고, 그 요청을 몇 번 재시도하든 같은 키를 쓴다는 뜻이다.

- Q: `IdempotencyKey` 를 `String` 이 아니라 값 객체로 만든 이유 두 가지는?
  A: ① `String` 이면 주문번호·사용자 ID·지문이 전부 같은 타입이라 인자 순서를 바꿔 넣어도 컴파일된다.
  ② 검증(빈 값·공백·길이 상한)이 한 군데로 모인다.

- Q: 키 길이 상한 255가 필요한 이유는(상한이 없으면 무엇이 공짜가 되는가)?
  A: 키가 클라이언트 입력이고 저장소에서 인덱스 키가 되기 때문이다.
  상한이 없으면 1MB 짜리 키를 보내 인덱스를 부풀리는 것이 공짜가 된다 — 스트라이프도 255다.

#### 8. 기록에는 다섯 조각이 다 필요하다

- Q: `IdempotencyRecord` 의 다섯 조각과 각각의 역할은?
  A: `key`(무엇에 대한 기록인가) · `state`(지금 하는 중/끝남/실패) · `response`(뭐라고 답했는가 — 재생의 근거) · `fingerprint`(그때 요청이 무엇이었나 — 오용 탐지) · `expiresAtMillis`(언제까지 유효한가 — 무한 증가 방지).

- Q: `response` 를 빼먹는 설계가 흔한데, 그러면 클라이언트는 무엇을 끝내 모르는가?
  A: 결제 승인번호 같은 결과값이다.
  "이미 했다"까지는 알아도 첫 응답을 놓친 클라이언트는 성공인지 실패인지, 승인번호가 무엇인지 끝내 알 수 없다.
  재생할 응답이 없으면 멱등성의 절반만 만든 것이다.

- Q: 상태가 IN_PROGRESS·COMPLETED·FAILED 셋인 이유는 — 셋째가 아니라 첫째가 왜 필요한가?
  A: **"지금 하는 중"** 이라는 상태가 있어야 동시 요청에 409를 줄 수 있기 때문이다.
  끝남/실패만 있으면 처리 중인 자리를 표현할 방법이 없어 선점 자체가 성립하지 않는다.

- Q: 기록을 불변 객체로 두고 통째로 갈아끼우는 이유는?
  A: 필드를 제자리에서 바꾸면 다른 스레드가 **절반만 바뀐 기록**을 볼 수 있기 때문이다.
  새 객체를 만들어 map 에 한 번에 갈아끼우면 보는 쪽은 언제나 완결된 기록만 본다.

#### 9. 처리 중일 때 또 오면

- Q: 기다리기와 즉시 알리기 중 이 구현이 고른 쪽과 그 이유는?
  A: 즉시 알리기(`ConflictException`)다.
  **대기는 자원을 잡기 때문이다** — 기다리는 스레드가 묶이고, 그 스레드는 다른 일을 못 한다.

- Q: 대기가 자원을 잡는다는 말이 몰릴 때 무엇이 되는가?
  A: 대기 자체가 장애가 된다 — 같은 키로 몰린 요청들이 스레드 풀을 다 먹으면 무관한 요청까지 못 받는다.
  05번 BLOCK 정책이 스레드를 묶던 것, 03번 벌크헤드가 막으려던 사고와 같은 구조다.

- Q: 스트라이프가 주는 응답 코드는 무엇인가?
  A: **409 Conflict** — "지금 처리 중이니 나중에 다시 와라".

- Q: 이 선택이 05번 FAIL 정책·03번 BulkheadFullException 과 무엇이 같은가?
  A: 셋 다 "기다리게 하지 않고 즉시 알려서 호출자가 고르게 한다"는 모양이다.
  즉시 실패는 자원을 돌려주고, 무엇을 할지(재시도·폴백·포기)는 상황을 아는 호출자가 정한다.

#### 10. 기억의 대가 — TTL과 청소

- Q: 청소를 안 하면 요청 1만 건에서 보관량과 유효 기록은 각각 몇 개인가?
  A: 보관 10,000개, 그중 유효한 것은 99개.
  나머지는 이미 지난 기록이다.

- Q: TTL + 주기적 청소를 하면 그 숫자는 어떻게 바뀌는가?
  A: 보관량이 최대 198개로 떨어진다(유효 99개는 그대로).
  같은 정확성을 50배 작은 메모리로 유지한다.

- Q: 99%가 쓸모없는 기록이 되는 이유는?
  A: 재시도는 보통 몇 초 안에 오기 때문이다.
  그 몇 초가 지나면 기록은 "혹시 아주 늦게 올 재시도"를 위한 보험일 뿐이고, 실제로 쓰이는 일은 거의 없다.

- Q: 스트라이프의 24시간이 "계산이 아니라 선택"인 이유는?
  A: 어떤 공식으로 유도한 값이 아니라 저장 비용과 늦은 재시도 보호 사이의 균형점을 고른 것이기 때문이다.
  재시도가 24시간 뒤에 오는 일은 사람이 개입할 때뿐이고, 그때는 사람이 판단한다.

- Q: TTL이 길 때와 짧을 때 각각 무엇을 잃는가?
  A: 길면 저장소가 커진다(TTL 10배 = 보관량 10배).
  짧으면 그 뒤에 온 재시도가 두 번 실행된다 — 즉 정확성을 잃는다.

#### 11. 세 가지 함정

- Q: 지문 검사를 상태 판정 뒤에 두면 어떤 사고가 나고, 왜 로그도 안 남는가?
  A: 1000원 결제에 쓴 키로 온 50000원 결제에 옛 응답을 재생해주고, 클라이언트는 50000원이 결제됐다고 믿는다.
  정상 경로(재생)를 그대로 탔으므로 예외도 에러 로그도 없다 — 정상처럼 보이는 응답이 유일한 흔적이다.

- Q: FAILED 를 영구 기록으로 두면 무엇이 무엇으로 승격되는가?
  A: **일시 장애가 영구 실패로** 승격된다.
  잠깐 DB가 끊겨 실패한 요청이 그 키로는 영영 다시 시도되지 못한다.

- Q: 그 재선점 판정은 어느 계층의 책임인가(저장소인가 실행기인가)?
  A: 저장소다 — `tryBegin` 이 FAILED 자리를 잡을 수 있는 세 경우 중 하나로 본다.
  실행기는 그 결과를 받아 "false 인데 FAILED 면 한 바퀴 더 돈다"로 대응할 뿐이다.
  판정을 실행기에만 두면 저장소를 직접 쓰는 다른 경로에서 같은 보호가 사라진다.

- Q: 청소가 정확성을 깨는 순간은 언제이고 재현률은 얼마인가?
  A: 만료된 자리를 스위퍼가 지우는 그 순간 남이 같은 자리를 새로 잡았을 때 — 2000회 중 55~60회 재현된다.
  `remove(key, value)` 로 "내가 본 그 기록일 때만" 지워야 막힌다.

#### 12. 고칠 수 없는 것

- Q: 소유권 토큰이 없어서 생기는 사고는 무엇이고, 무엇이 필요한가?
  A: 만료된 자리를 남이 가져간 뒤 내가 뒤늦게 `complete` 하면 **남의 자리에 내 응답을 쓴다.**
  "이 자리의 주인이 아직 나인가"를 증명하는 펜싱 토큰이 필요하고, 이 문제집은 거기까지 가지 않는다.

- Q: 응답 저장과 실제 작업이 원자적이지 않다는 것은 어떤 장면인가?
  A: 포인트는 깎였는데 `store.complete` 직전에 프로세스가 죽는 장면이다.
  기록이 IN_PROGRESS 로 남아 그 키의 재시도는 계속 409를 받고, TTL 이 지나야 풀린다.
  07-outbox 가 이 한계(기록과 발행·작업을 원자적으로 묶기)를 정면으로 다룬다.

- Q: 안 잡힌 변종 2개는 무엇이었고, 왜 "구별할 필요도 없다"인가?
  A: 만료 시각을 반복문 밖에서 계산하는 것과 `compute` 람다 안에서 `now` 를 읽는 것.
  둘 다 실제로 동작이 같은 **동치 변환**이라 테스트가 구별하지 못하는 것이 정상이다.
  안 잡힌 변종이 전부 결함인 것은 아니다 — 04·02번의 "겹친 방어선"과는 성격이 다르다.

#### 13. 연결

- Q: 스트라이프·토스페이먼츠·GoCardless·AWS가 같은 계약에 도달한 것이 우연이 아닌 이유는?
  A: 업계가 각자 고민해서 우연히 만난 것이 아니라 **그것 말고 맞는 조합이 없기** 때문이다.
  키는 클라이언트가 만들고, 선점은 원자적이어야 하고, 응답을 저장해 재생하고, 처리 중이면 409, 보관은 유한 — 하나라도 빼면 깨진다.

- Q: `debugging/02-toctou-idempotency` 와 이 챕터는 같은 주제를 어떻게 다르게 보는가?
  A: 거기는 **진단**으로 "판정을 어디에서 하는가"만 본다.
  여기는 그 위에 얹히는 **기록 계약**(지문·상태·응답 재생·TTL)이다.
  `debugging/06-retry-duplication` 은 같은 문제의 소비자 쪽이다.

- Q: 07-outbox 가 정면으로 다루는 것은 이 챕터의 어느 한계인가?
  A: 한계 2번 — 응답 저장(기록)과 실제 작업·발행이 원자적이지 않다는 것.
  같은 트랜잭션에 기록과 발행 의사를 함께 남겨 "깎였는데 안 알려진" 틈을 없앤다.
