# systems/kafka-consumer-failure — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: 개인 학습 노트 「Kafka 소비 측 실패 처리 체계」 · 이관일 2026-09-16.\
> 본문 절들(pull 전제·재시도 두 자리·커밋 순서·인박스·재시도 계층·리밸런싱)은 **원고**를 고쳐 쓴 것이다(문체·순서·코드 유지).\
> 원고의 사내 문서 참조(「06번 아웃박스」)는 아직 이관 전이라 링크 대신 텍스트로 두었다.\
> 「한눈에」의 이어보기 비유는 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**놓치기 쉬운 자리**: 파이프라인 신뢰성을 말할 때 **소비 측 실패**를 빼먹기 쉽다.\
발행 측만 설명하면 "메시지를 보냈다"까지만 보장하고, **"처리됐다"는 보장하지 못한다.**

> **컨슈머 오프셋(consumer offset)** — 컨슈머가 "내가 이 파티션을 어디까지 읽었다"를 표시하는 커서(숫자 하나).\
> 예: 오프셋 105를 커밋했다면 재시작 시 106부터 읽는다. 이 커밋 시점이 모든 신뢰성 논의의 중심이다.

## 한눈에 — 쉽게 말하면

**영상 이어보기**(재생 위치)를 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
영상은 카탈로그에서 사라지지 않는다. 나는 '어디까지 봤나'만 기억한다
+-------------------------------------------+
| 영상은 그대로 있고, 재생 위치만 저장한다      |  ← Kafka = 보존형 로그 · 오프셋만 관리
| 보다가 멈추면 그 위치부터 다시 본다           |  ← 오프셋을 되돌리면 재처리
| "봤음" 표시를 언제 찍느냐가 관건            |  ← 커밋 시점이 유실/중복을 가른다
|   보기 전에 찍으면 → 못 본 구간 생김(유실)    |
|   보고 나서 찍기 직전 끊기면 → 다시 봄(중복)   |
+-------------------------------------------+
```

**Kafka 소비도 똑같은 구조다.** 메시지는 소비돼도 사라지지 않고(보존형 로그), 컨슈머는 "어디까지 읽었다"는 오프셋만 관리한다. 그래서 브로커에게 "받았니?"를 물어보는 확인 모델이 없고, **오프셋을 언제 커밋하느냐**가 유실이냐 중복이냐를 결정한다.

쉽게 말하면 이렇다.\
**소비 측 신뢰성은 세 가지로 요약된다.** ① 커밋을 처리 후에 해서 at-least-once를 택하고, ② 중복은 인박스/멱등으로 흡수하고, ③ 실패를 일시적/영구적으로 나눠 영구 실패는 즉시 DLT로 보낸다(안 그러면 poison pill이 파티션을 막는다).

## 문제 — 이 개념이 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(운영·신뢰성 개념 정리다). 대신 네 개의 질문에 답한다.

```text
1. 왜 ack 를 안 묻나  "Kafka는 왜 메시지별 확인이 없나? 대신 무엇이 중심인가?"
2. 커밋 순서          "처리 전/후 커밋이 각각 무슨 실패(유실/중복)를 만드나?"
3. 중복을 어떻게 흡수  "at-least-once를 택했으면 중복은 어떻게 없던 일로 만드나?"
4. 실패를 어떻게 나누나 "재시도해야 할 실패와 재시도하면 안 될 실패를 어떻게 가르나?"
```

아래 서머리는 이 네 질문을 하나씩 분석·정리한 것이다.

## 전체 흐름

메시지가 발행되고, 소비되고, 실패 시 격리되는 두 재시도 지점.

```text
[발행 측]                       [브로커]           [소비 측]
비즈니스 TX → 아웃박스              보존 로그          poll → 처리 → 오프셋 커밋
                │                                        │ 실패 시
            릴레이 재발행                              재시도 토픽 → DLT
            (ack 전 미완료 유지)
```

- 재시도가 붙는 자리는 **두 군데**다 — 발행 측(아웃박스+릴레이)과 소비 측(재시도 토픽+DLT).
- 이 노트는 오른쪽(소비 측)을 판다.

## 전제 — Kafka는 왜 ack를 "물어보지" 않는가

> 출처: 개인 학습 노트 「Kafka 소비 측 실패」 — §1

**언제 쓰나** — 푸시형 브로커(예: AMQP)의 메시지별 ack 모델과 헷갈릴 때.

**전/후 대비 — 푸시형 vs Kafka**

```text
              푸시형 (예: AMQP)              Kafka
────────────────────────────────────────────────────────────
전달          브로커가 컨슈머에게 밀어줌         컨슈머가 당겨감(pull)
메시지 상태     브로커가 메시지별 ack/unack 추적   브로커는 오프셋 숫자 하나만 기억
소비 후        ack 오면 삭제                   삭제 안 함 · 보존 기간까지 그대로
재처리         재전송 요청                     오프셋을 되돌리면 됨
```

핵심: **Kafka는 보존형 로그다.** 메시지는 소비돼도 사라지지 않고, 컨슈머는 "내가 어디까지 읽었다"는 **커서**(오프셋)만 관리한다.

→ 그래서 "받았는지 물어보는" 확인 모델이 필요 없다. 대신 **오프셋을 언제 커밋하느냐**가 모든 신뢰성 논의의 중심이 된다.

> **보존형 로그(retention log)** — 소비돼도 메시지를 지우지 않고 보존 기간 동안 그대로 두는 저장 방식.\
> 예: 컨슈머가 버그로 잘못 처리했어도, 오프셋만 되돌리면 같은 메시지를 다시 읽어 재처리할 수 있다.

**비용** — 보존형이라 재처리는 쉽지만, "언제 커밋하냐"를 잘못 정하면 유실 또는 중복이 조용히 난다(다음 절).

## 오프셋 커밋 순서 함정 (핵심)

> 출처: 개인 학습 노트 「Kafka 소비 측 실패」 — §3

**언제 쓰나** — 컨슈머의 커밋 설정을 정할 때. **"처리"와 "커밋"의 순서가 실패 계열을 결정한다.**

### 케이스 A — 처리 전 커밋 (`enable.auto.commit=true`가 사실상 이것)

```text
poll → 오프셋 커밋 → 처리 중 크래시
결과: 재시작 시 이미 커밋된 지점 이후부터 읽음 → 건너뜀 = 유실
```

자동 커밋은 백그라운드에서 주기적으로 커밋하므로, **처리 완료와 무관하게 커밋될 수 있다** → **at-most-once**.

### 케이스 B — 처리 후 커밋

```text
poll → 처리 완료 → 커밋 직전 크래시
결과: 재시작 시 같은 메시지를 다시 받음 → 중복 처리
```

→ **at-least-once**.

### 결론

```java
props.put(ENABLE_AUTO_COMMIT_CONFIG, false);  // 필수
// 처리 완료 후 수동 커밋 (Spring Kafka: AckMode.MANUAL / RECORD / BATCH)
```

> **"정확히 한 번"은 소비 측에서 공짜로 얻어지지 않는다.** 처리와 커밋이 서로 다른 시스템(외부 DB와 Kafka)에 걸쳐 있어 원자적으로 묶을 수 없기 때문이다. 그래서 **at-least-once + 멱등 소비**가 현실적 표준이다.

> **at-most-once / at-least-once / exactly-once** — 각각 "많아야 한 번(유실 가능)" / "적어도 한 번(중복 가능)" / "정확히 한 번".\
> 예: 처리 전 커밋 = at-most-once, 처리 후 커밋 = at-least-once. 외부 DB에 쓰는 이상 exactly-once는 공짜가 아니다.

> Kafka 트랜잭션(`read-process-write`, `isolation.level=read_committed`)은 **Kafka→Kafka 경로에서만** exactly-once를 준다. 외부 DB에 쓰는 순간 그 보장은 깨진다.

**비용** — at-least-once를 택하면 중복이 반드시 온다. 그 중복을 흡수하는 게 다음 절(인박스)이다.

## 멱등 소비 = 인박스 패턴 (전제 조건)

> 출처: 개인 학습 노트 「Kafka 소비 측 실패」 — §4

**언제 쓰나** — at-least-once를 골랐을 때. **중복 처리가 반드시 온다**는 전제 위에서 그것을 흡수한다.

```sql
CREATE TABLE processed_messages (
    message_id   VARCHAR(100) PRIMARY KEY,   -- 유니크 제약이 방어선
    consumer     VARCHAR(50)  NOT NULL,
    processed_at TIMESTAMP    NOT NULL DEFAULT now()
);
```

```java
@Transactional
public void handle(Event e) {
    try {
        inboxRepo.insert(e.messageId(), CONSUMER_NAME);  // 중복이면 여기서 예외
    } catch (DuplicateKeyException dup) {
        return;   // 이미 처리됨 → 조용히 스킵
    }
    businessLogic(e);   // 인박스 삽입과 같은 트랜잭션
}
```

**중요한 두 가지**

- **인박스 삽입과 비즈니스 로직이 같은 트랜잭션**이어야 한다. 아니면 "인박스만 기록되고 처리는 안 됨" 상태가 생긴다.
- **`message_id`는 생산자가 만든 안정적 ID**여야 한다. Kafka 오프셋은 재발행 시 달라지므로 부적합하다.

> **인박스 패턴(inbox pattern)** — 처리한 메시지 ID를 유니크 제약이 걸린 테이블에 남겨, 같은 ID가 다시 오면 스킵하는 멱등 장치.\
> 예: 같은 결제 이벤트가 두 번 와도, 두 번째 insert가 PK 충돌로 튕겨 나가 비즈니스 로직이 두 번 돌지 않는다.

**대안**: 비즈니스 로직 자체를 멱등하게 설계(`UPDATE ... SET status='PAID' WHERE id=? AND status='PENDING'`, upsert 등). 별도 테이블 없이 가능하면 이쪽이 더 낫다.

**비용** — 인박스는 처리마다 한 번의 insert를 더 문다. 대신 중복이 와도 안전하다. 멱등 로직으로 대체할 수 있으면 테이블 자체가 없어진다.

## 재시도 계층 설계

> 출처: 개인 학습 노트 「Kafka 소비 측 실패」 — §5

**언제 쓰나** — 처리 실패를 어떻게 되풀이할지 정할 때. **실패 종류를 먼저 나누지 않으면 설계가 틀어진다.**

### 실패 종류부터 나눈다

```text
종류              예시                          대응
──────────────────────────────────────────────────────────────
일시적(transient)  DB 커넥션 끊김 · 타임아웃 · 429  재시도 O
영구적(permanent)  역직렬화 실패 · 스키마 불일치 ·   재시도 무의미 → 즉시 DLT
                  검증 오류
```

> **poison pill(독이 든 알약)** — 영구 실패 메시지를 무한 재시도하면 **파티션 전체가 그 메시지에서 멈춘다.**\
> 예: 역직렬화 안 되는 메시지 하나를 계속 재시도하면, 뒤의 정상 메시지가 전부 밀린다. 실패 종류 구분이 필수인 이유.

### 블로킹 재시도 vs 논블로킹 재시도

**전/후 대비 — 무엇을 지키고 무엇을 깨나**

```text
블로킹 (같은 스레드에서 sleep 후 재시도)   논블로킹 (재시도 토픽으로 넘김)
+-----------------------------+        +-----------------------------+
| 순서 보존 ✅                  |        | 메인 파티션이 안 막힘 ✅       |
| 파티션 전체 정지 ❌            |        | 해당 키의 순서가 깨짐 ❌       |
| max.poll.interval.ms 넘기면   |        |                             |
|   컨슈머가 죽은 걸로 판단       |        | main → retry-1s → retry-10s |
|   → 리밸런싱(더 큰 사고)       |        |   → retry-1m → DLT           |
+-----------------------------+        +-----------------------------+
```

> 순서가 중요한 도메인(상태 전이)이면 논블로킹 재시도를 쓸 수 없다. 대신 **짧은 블로킹 재시도 후 바로 DLT로 보내고 알림**을 띄운다.

### 코드 형태 (Spring Kafka 예시)

```java
@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(delay = 1000, multiplier = 3.0),
    dltStrategy = DltStrategy.FAIL_ON_ERROR,
    exclude = { DeserializationException.class, ValidationException.class }  // 영구 실패는 즉시 DLT
)
@KafkaListener(topics = "orders")
public void consume(OrderEvent e) { ... }

@DltHandler
public void dlt(OrderEvent e, @Header(KafkaHeaders.ORIGINAL_TOPIC) String topic) {
    alertService.notify(...);   // DLT는 쌓아두는 곳이 아니라 알림 대상
}
```

### DLT 운영 (자주 빠뜨리는 부분)

- **DLT 유입 건수에 알림을 건다.** 안 그러면 조용히 유실된 것과 같다.
- 원본 토픽/오프셋/예외 스택을 **헤더에 보존**한다.
- **재처리(replay) 수단**을 미리 만들어 둔다 — DLT는 종착지가 아니라 대기소다.

> **DLT(Dead Letter Topic)** — 끝까지 실패한 메시지를 격리해 두는 별도 토픽.\
> 예: 4번 재시도 후에도 실패하면 DLT로 보내고 알림을 울린다. 나중에 원인을 고쳐 재처리(replay)한다.

**비용** — 논블로킹 재시도는 파티션을 안 막는 대신 키 순서를 깨뜨린다. DLT는 알림·replay 수단을 함께 만들어야 "조용한 유실"이 안 된다.

## 리밸런싱 관련 함정

> 출처: 개인 학습 노트 「Kafka 소비 측 실패」 — §6

**언제 쓰나** — 처리가 느리거나 배포가 잦을 때. 리밸런싱이 재처리 폭풍을 부른다.

- **`max.poll.records`가 크고 처리가 느리면** `max.poll.interval.ms`를 넘겨 컨슈머가 그룹에서 쫓겨난다 → 리밸런싱 → 커밋 못한 메시지 재처리 → 또 느림 → 무한 반복.
  - 처방: `max.poll.records` 축소 · 처리 시간 단축 · `max.poll.interval.ms` 상향 중 택.
- **리밸런싱 중 커밋 유실**: `ConsumerRebalanceListener.onPartitionsRevoked`에서 커밋한다.
- **정적 멤버십(`group.instance.id`)**: 배포로 인한 불필요한 리밸런싱을 억제한다.

> **리밸런싱(rebalancing)** — 그룹 내 파티션 배분을 다시 정하는 것. 이 동안 소비가 멈춘다.\
> 예: 처리가 느려 컨슈머가 죽은 걸로 판단되면 리밸런싱이 돌고, 그 사이 커밋 못한 메시지가 다른 컨슈머에서 재처리된다.

**비용** — 리밸런싱은 소비를 멈추고 재처리를 유발한다. 처리 시간·`max.poll.records`·정적 멤버십으로 빈도를 줄이는 게 표준 처방이다.

## 한 문단 요약 (면접용)

> Kafka는 pull 기반 보존 로그라 브로커가 메시지별 ack를 추적하지 않고, 컨슈머가 오프셋만 관리한다. 그래서 신뢰성의 중심은 커밋 시점이다. 자동 커밋은 처리 완료와 무관하게 커밋돼서 크래시 시 건너뜀 유실이 나고, 처리 후 커밋으로 바꾸면 커밋 직전 크래시 시 중복이 난다. 외부 DB에 쓰는 이상 처리와 커밋을 원자적으로 묶을 수 없으니 at-least-once를 택하고, 대신 인박스 테이블의 유니크 제약이나 멱등한 비즈니스 로직으로 중복을 흡수한다. 재시도는 실패를 일시적/영구적으로 먼저 나눠서 영구 실패는 바로 DLT로 보내고 — 안 그러면 poison pill이 파티션을 막는다 — 일시적 실패만 백오프 재시도 토픽에 태운다. 다만 재시도 토픽은 키 순서를 깨뜨리므로, 순서가 중요한 도메인에서는 쓸 수 없다.

---

## 핵심 문장

- **Kafka는 보존형 로그다 — 메시지별 ack가 없고, "오프셋을 언제 커밋하나"가 신뢰성의 전부다.**
- **처리 전 커밋 = at-most-once(유실), 처리 후 커밋 = at-least-once(중복). 자동 커밋은 사실상 전자다.**
- **외부 DB에 쓰면 exactly-once는 공짜가 아니다 — at-least-once + 멱등 소비가 현실적 표준이다.**
- **실패는 일시적/영구적으로 먼저 나눈다 — 영구 실패를 재시도하면 poison pill이 파티션을 막는다.**
- **논블로킹 재시도 토픽은 파티션을 안 막는 대신 키 순서를 깨뜨린다 — 순서 도메인엔 못 쓴다.**

---

## 관련 자료

- 발행 측의 "아웃박스+릴레이"와 async 쓰기의 "유실 창"은 아직 이관 전인 사내 문서 「아웃박스 vs 발송 로그」에 있어 링크 대신 텍스트로 둔다.
- 형제 주제 `clickhouse-mergetree`(이 배치에서 함께 이관) — `async_insert`의 유실 창이 여기 커밋 시점 선택과 정확히 같은 구조다. *(지금은 텍스트 참조)*

## 용어 풀이

- **컨슈머 오프셋(consumer offset)** — 컨슈머가 어디까지 읽었는지 표시하는 커서(숫자).
- **보존형 로그(retention log)** — 소비돼도 메시지를 지우지 않고 보존 기간 동안 두는 저장 방식.
- **at-most-once / at-least-once / exactly-once** — 각각 유실 가능 / 중복 가능 / 정확히 한 번의 전달 보장.
- **자동 커밋(auto commit)** — 처리 완료와 무관하게 주기적으로 오프셋을 커밋하는 설정. 사실상 at-most-once.
- **수동 커밋(manual commit)** — 처리 완료 후 코드가 명시적으로 커밋하는 방식. at-least-once의 전제.
- **인박스 패턴(inbox pattern)** — 처리한 메시지 ID를 유니크 제약 테이블에 남겨 중복을 스킵하는 멱등 장치.
- **멱등(idempotent)** — 같은 연산을 여러 번 해도 결과가 한 번 한 것과 같은 성질.
- **poison pill** — 무한 재시도되며 파티션을 막는 영구 실패 메시지.
- **일시적/영구적 실패(transient/permanent)** — 재시도로 풀리는 실패 / 재시도가 무의미한 실패.
- **블로킹/논블로킹 재시도** — 같은 스레드에서 대기 후 재시도 / 별도 재시도 토픽으로 넘김. 후자는 순서를 깬다.
- **DLT(Dead Letter Topic)** — 끝까지 실패한 메시지를 격리하는 별도 토픽. 알림·replay 대상.
- **리밸런싱(rebalancing)** — 그룹 내 파티션 배분을 다시 정하는 것. 이 동안 소비가 멈춘다.
- **정적 멤버십(static membership)** — `group.instance.id`로 배포 시 불필요한 리밸런싱을 억제하는 설정.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **인박스(소비 측)와 아웃박스(발행 측)는 대칭이다.** 아웃박스는 "비즈니스 TX와 발행 의도를 한 트랜잭션에 묶어 발행 유실을 막는" 발행 측 장치고, 인박스는 "비즈니스 TX와 처리 표시를 한 트랜잭션에 묶어 중복 처리를 막는" 소비 측 장치다. 둘 다 핵심은 "메시징과 DB를 한 로컬 트랜잭션으로 묶는다"는 같은 발상이다.
- **transactional outbox가 필요한 이유 = 이중 쓰기 문제.** "DB에 쓰고 Kafka에도 보낸다"를 두 번의 쓰기로 하면, 하나만 성공하는 순간이 반드시 생긴다(dual write). 아웃박스는 발행을 DB 쓰기의 일부로 만들어 이 틈을 없앤다 — 소비 측 인박스가 흡수하는 중복도 이 발행 측 재시도에서 나온다.
- **at-least-once + 멱등 = "실용적 exactly-once".** 업계에서 "effectively-once"라 부르기도 한다. 진짜 exactly-once 전달은 분산 환경에서 사실상 불가능하고, 대신 "여러 번 와도 결과가 한 번과 같게" 만드는 멱등성으로 같은 효과를 낸다. 면접에서 "exactly-once 쓰면 되지 않나"에 대한 답이 이것이다.
- **커밋 배치와 순서의 상충.** `AckMode.BATCH`는 여러 레코드를 모아 한 번에 커밋해 처리량이 좋지만, 배치 중간에 실패하면 이미 처리한 앞부분까지 재처리된다. 처리량(BATCH)과 재처리 최소화(RECORD)가 상충하며, 멱등 소비가 갖춰져 있어야 BATCH를 마음 편히 쓸 수 있다.
