# cs/thrashing — thrashing(스레싱) — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> 원고는 내가 직접 쓴 thrashing 노트(2026-08-23). 1~5절은 원고 그대로(오탈자만 교정).
> 「전체 흐름」「핵심 문장」은 원고를 압축한 것이고, 맨 아래 「[Claude 추가]」 절만 원고에 없던 내용이다.

## 전체 흐름

```text
정의    동적 배열(ArrayList 류)이 capacity를 늘렸다 줄였다 하는 재할당을 너무 자주 반복하는 현상
원인    확장 경계(size == capacity)와 축소 경계(size <= capacity/2)가 같은 자리에 붙어 있어, size가 경계 근처에서 오가기만 해도 매번 새 배열 생성 + 복사
해법    축소 조건을 훨씬 여유롭게(size <= capacity/4) 잡아 두 경계를 떨어뜨린다
핵심    1/4라는 숫자가 아니라 "올라갈 때 기준 ≠ 내려갈 때 기준" — 히스테리시스(hysteresis)
```

## 1. thrashing이란?

동적 배열(ArrayList 같은 구조)이 크기를 늘렸다가 줄였다 하는 재할당을 너무 자주 반복하는 현상이며,
thrashing 방지란 이러한 현상을 막는 것이다.

## 2. 확장은 보통 이렇게 일어난다

예를 들어 동적 배열의 capacity = 16이고 원소가 가득 차면 보통:

```text
size = 16
capacity = 16

원소 추가
↓
capacity = 32로 확장
↓
기존 16개 원소를 새 배열로 복사
```

이렇게 확장한다고 해보자.

## 3. 문제 — 축소 조건을 "절반"으로 잡으면

그런데 축소 조건을 단순히 "절반 이하가 되면 capacity를 절반으로 줄인다"라고 잡으면
아래와 같은 문제가 발생한다.

```text
capacity = 32
size = 16

삭제 → size = 15
↓
capacity를 16으로 축소
↓
새 배열 생성 + 복사

다시 2개 추가 → size = 17
↓
capacity를 32로 확장
↓
새 배열 생성 + 복사

몇 개 삭제
↓
다시 16으로 축소
...
```

즉 배열 사용량이 경계 근처에서 왔다 갔다 하면

```text
16 → 32 → 16 → 32 → 16 → 32
```

계속 배열을 새로 만들고 데이터를 복사하게 된다.
이게 여기서 말하는 thrashing이다.

## 4. 해법 — 축소 조건을 여유롭게 잡는다

그래서 보통 축소 조건은 훨씬 여유롭게 잡는 게 좋다.

```text
확장 조건
size == capacity
→ capacity × 2

축소 조건
size <= capacity / 4
→ capacity / 2
```

예를 들어 capacity가 32라면:

```text
capacity = 32

size = 16
→ 아직 안 줄임

size = 12
→ 아직 안 줄임

size = 8       ← 1/4
→ capacity를 16으로 축소
```

이렇게 되며, 축소 직후는

```text
size = 8
capacity = 16
```

여기서 다시 확장이 발생하려면 size가 16까지 증가해야 하며, 즉:

```text
축소 조건       확장 조건
    ↓               ↓
    8               16
----|---------------|----
  C/4              C/2
```

사이에 충분한 여유 구간이 생긴다.

## 5. 핵심 — 1/4라는 숫자가 아니라 경계의 간격

즉 1/4라는 비율 자체보다는,

**축소가 일어나는 경계와 확장이 일어나는 경계를 충분히 떨어뜨려 놓아서, 경계 근처에서 resize가 반복되는 것을 막는다**

위의 내용이 핵심이며, 올라갈 때의 기준과 내려갈 때의 기준을 다르게 두는 것을 일반적으로
히스테리시스(hysteresis)라고 볼 수 있다.

## 핵심 문장

- thrashing = size가 경계 근처에서 오갈 때 확장·축소 재할당(새 배열 + 복사)이 반복되는 것.
- 원인은 확장 경계와 축소 경계가 같은 자리(capacity/2)에 붙어 있다는 것.
- 축소 기준을 C/4로 내리면, 축소 직후 size는 새 capacity의 절반이라 다음 확장까지 size가 두 배가 되어야 한다.
- 본질은 1/4라는 숫자가 아니라 두 경계 사이의 여유 구간 — 히스테리시스.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 내용이다. 복습 대상은 1~5절이고, 이 절은 확장 읽을거리다.

### A. 왜 "×2 확장"이 싸고, thrashing이 그걸 깨뜨리는가 — amortized O(1)

- 확장 때마다 복사 비용은 O(n)이지만, 두 배씩 키우면 n번 append 하는 동안 복사 총량이 1 + 2 + 4 + … + n ≈ 2n이다. 한 번의 append당 평균 O(1) — 이것이 **분할상환(amortized) O(1)**이다.
- 이 계산은 "확장 사이에 최소 n번의 append가 끼어 있어 복사 비용을 갚을 시간이 있다"는 가정에 기댄다. thrashing은 경계에서 1~2번의 연산마다 O(n) 복사가 일어나므로 이 가정을 깨고, 연산당 비용이 O(n)으로 떨어진다.
- 히스테리시스(C/4 축소)는 그 가정을 복원하는 장치다: 축소 직후 size = C'/2이므로 다음 resize까지 최소 C'/2번의 연산이 보장된다. → 연산당 amortized O(1) 유지.

### B. 실제 구현은 어떻게 하나

- **Java `ArrayList`**: 확장은 1.5배(`oldCapacity + (oldCapacity >> 1)`), **자동 축소는 없다**. 줄이려면 `trimToSize()`를 명시 호출 — 축소 thrashing 문제를 "안 줄임"으로 회피한 설계.
- **CPython `list`**: 확장은 약 1.125배 + 상수의 완만한 over-allocation, 축소는 사용량이 할당량의 절반 아래로 떨어질 때 — 비율이 다를 뿐 "올라갈 때·내려갈 때 기준 분리"는 같다.
- **Go slice**: `append`는 작을 땐 2배, 커지면 1.25배로 성장. 자동 축소 없음.
- **Java `HashMap`**: load factor 0.75를 넘으면 2배로 rehash, 자동 축소 없음. 해시 테이블의 rehash도 같은 종류의 비용(전체 재배치)이라 동일한 thrashing 위험이 있다.

### C. 같은 이름, 다른 층 — OS의 thrashing

- 원래 thrashing은 OS 가상 메모리 용어다: 프로세스들의 working set 합이 물리 메모리를 넘어 **페이지 폴트 → 스왑 → 또 폴트**가 반복되어 CPU가 실제 일보다 페이지 교체에 시간을 쓰는 상태.
- 공통 구조는 같다 — "유용한 일보다 그 일을 위한 준비(복사·교체)가 더 많아지는 반복". 동적 배열의 thrashing은 이 용어를 빌려 쓴 것이다.

### D. 히스테리시스는 어디에나 있다

- **온도 조절기**: 20°C에 꺼지고 20°C에 켜지면 경계에서 계속 on/off — 그래서 19.5°C에 켜고 20.5°C에 끈다.
- **오토스케일링**: CPU 70% 넘으면 scale-out, 30% 아래면 scale-in + cooldown — 같은 임계값을 쓰면 인스턴스가 들락날락(flapping)한다.
- **헬스체크/서킷브레이커**: 실패 N회에 open, 성공 M회에 close — 하나 성공했다고 바로 닫지 않는 이유.
- **TCP 혼잡 제어·로드밸런서 가중치**도 같은 원리. 공통 질문은 하나다: *"올라가는 문턱과 내려가는 문턱이 같은가? 같다면 경계에서 진동한다."*
