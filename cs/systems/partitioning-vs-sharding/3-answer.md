# cs/partitioning-vs-sharding — Partitioning vs Sharding — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 기준 소스는 문서가 아니라 원전(원본 노트·코드)이다.

## 정답

1. 경계는 DB 인스턴스다. 파티셔닝은 논리적으로 하나인 테이블을 같은 인스턴스 안에서 물리적으로 쪼개고 DB가 투명하게 다룬다. 샤딩은 각 샤드가 독립 DB 인스턴스로 전체의 일부만 가지므로 애플리케이션/미들웨어가 어느 샤드인지 알아야 하고, 인스턴스를 넘는 조인·트랜잭션은 DB가 해주지 않는다. 나누는 기준(range/hash)은 같아도 "누가 경계를 넘는 일을 책임지나"가 바뀐다.

2. 파티셔닝: ① 파티션 프루닝으로 필요한 파티션만 스캔해 쿼리 성능 ② 오래된 파티션을 drop하는 손쉬운 삭제/아카이빙 등 관리 편의. 샤딩: 스케일 아웃 — 단일 서버의 용량·CPU·메모리·커넥션 한계를 넘고 부하를 분산. 파티셔닝은 한 서버 안에서 더 잘 쓰는 것이고 샤딩은 한 서버로 안 될 때 서버를 늘리는 것이라 목적 자체가 다르다.

3. 쿼리에 파티션 키(날짜)가 없으므로 프루닝이 안 되어 모든 파티션을 훑는다. 파티션마다 인덱스를 따로 타야 하므로 단일 테이블보다 오히려 느려질 수 있다. 파티션 키를 잘못 잡으면 역효과라는 단점의 전형이다. 키는 "어떻게 나누면 편한가"가 아니라 "쿼리가 무엇으로 들어오는가"로 정해야 한다.

4. 핫스팟(특정 샤드에 데이터·부하 집중)과 리밸런싱 비용. Range 기반은 단조 증가 키에서 핫스팟이 생기기 쉬우므로 Hash 기반(샤드 키를 해싱해 고르게)이나 Directory 기반(별도 매핑 테이블로 유연하게 배정)으로 바꾸거나, 해시라도 샤드 수 변경 시 재배정을 줄이는 기법(consistent hashing 계열)을 쓴다. 샤드 간 조인 불가·분산 트랜잭션 어려움과 함께 샤딩의 4대 단점이라 도입 전에 신중해야 한다.

5. 정규화는 중복과 이상(anomaly)을 없애기 위해 의미 단위로 테이블을 나누는 것이고, 수직 파티셔닝은 이미 정규화된 테이블을 성능 목적으로 더 쪼개는 것이다 — 자주 조회되는 컬럼(이름, 이메일)과 드물게 조회되는 대용량 컬럼(소개글, 이미지)을 분리해 자주 쓰는 쪽의 행을 작게 만든다. 결과 모양은 비슷해도 동기가 다르다.

6. 동작은 샤딩에 가깝다 — 각 파티션이 다른 브로커(독립 서버)에 놓이고, 파티션 간 순서·조인이 없으며, hash(key) % N으로 배정한다. 샤딩의 단점이 그대로 나타난다: 특정 key에 메시지가 몰리면 핫 파티션(핫스팟), 파티션 수를 늘리면 N이 바뀌어 기존 key의 배정이 깨진다(리밸런싱 — 순서 보장이 필요한 시스템에서 위험), 파티션을 넘는 순서 보장은 없다(분산 트랜잭션 어려움에 대응).
