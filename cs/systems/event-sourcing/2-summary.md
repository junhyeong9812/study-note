# systems/event-sourcing — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/08-event-sourcing/README.md` · 이관일 2026-09-16.\
> 본문 절들(무엇인가·얻는 것·내주는 것·거부 조건·부분 이벤트 소싱·판별·함께 오는 것)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지).\
> 「한눈에」의 일상 비유와 세로 도식들은 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다. 원본의 특정 프로젝트 결정(ADR·BR·Phase 번호, 품질 시나리오·마일스톤 번호)은 「현장에서 만나는 상황」으로 일반화했다.

**상태를 저장하는 대신, 상태를 바꾼 사건을 저장한다.**\
현재 값(잔액 = 15)을 덮어쓰며 보관하는 대신, 값을 바꾼 사건(입금 20, 출금 5)을 쌓아 두고 현재 값은 그 사건들을 **접어서(fold)** 얻는다.

---

## 한눈에 — 쉽게 말하면

**게임 리플레이 파일**을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
게임 리플레이 파일
+----------------------------------+
| 턴1: e2->e4                      |  ← 사건만 쌓는다 (INSERT 만)
| 턴2: e7->e5                      |  ← 이미 둔 수는 지우지 않는다
| 턴3: g1->f3                      |
|  ...                             |
+----------------------------------+
        ↓ 처음부터 다시 두면 (replay/fold)
현재 판 = 어느 시점이든 재구성된다
```

리플레이 파일은 **마지막 판**을 저장하지 않는다. **둔 수 전부**를 저장한다.\
그래서 어느 턴의 판이든 다시 만들 수 있고, "왜 졌는지"를 되짚을 수 있고, 특정 수부터 다시 둘 수 있다.

**저장소도 똑같은 구조다.**\
상태 저장은 `balance = 15`라는 **지금 값**만 안다 — 어떻게 15가 됐는지는 사라진다.\
이벤트 소싱은 `Deposited(20)`·`Withdrawn(5)`라는 **바뀐 사건**을 안다 — 지금 값은 접어서 얻는다.

쉽게 말하면 이렇다.\
**상태 저장은 "지금 어디 있나"만 알고, 이벤트 소싱은 "어떻게 여기 왔나"를 통째로 안다.** 전자는 값을 덮어쓰고, 후자는 값을 지우지 않는다.

---

## 문제 — 이 개념이 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(개념 정리다). 대신 다섯 개의 질문에 답한다.

```text
1. "상태 대신 사건을 저장한다는 게 정확히 뭔가?"
       → UPDATE 없는 저장, fold, 스냅샷 (§ 무엇인가)
2. "그렇게 하면 무엇이 좋아지나?"
       → 감사가능성·과거 재구성·재구축·소급 답변 (§ 무엇을 얻나)
3. "공짜가 아닐 텐데, 무엇을 내주나?"
       → 조회 난이도·스키마 고정·재생 비용 (§ 무엇을 내주나)
4. "그럼 언제 쓰지 말아야 하나?"
       → 모델이 흔들릴 때·이미 감사가 있을 때 (§ 거부가 합리적인 조건)
5. "전부 아니면 전무인가?"
       → 한 컨텍스트만 사건으로 = 부분 이벤트 소싱 (§ 부분 이벤트 소싱)
```

아래 서머리는 이 다섯 질문을 하나씩 분석·정리한 것이다.

## 전체 흐름

사건을 쌓고, 접어서 현재를 얻고, 비싸지면 스냅샷으로 접는 지점을 앞당긴다.

```text
사건 발생 (Deposited(20))          무슨 일이 일어났나
        ↓
저장소에 INSERT 만                  UPDATE 없음 — 사건을 지우지 않는다
        ↓
현재 상태 = fold(사건 전부)          처음부터 하나씩 접어서 계산
        ↓
스냅샷(v=9000)부터 fold            10만 개를 매번 접지 않으려는 최적화
        ↓
읽기 모델이 틀리면 지우고 재생       마이그레이션이 아니라 재구축
```

- 왼쪽은 **무슨 단계인가**, 오른쪽은 **그 단계가 정하는 것**.
- 흐름 어디에도 "이전 값을 덮어쓴다"가 없다는 점이 핵심이다.

## 무엇인가 — 상태 저장 vs 이벤트 소싱

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §1

**언제 쓰나** — 변경 이력 자체가 업무적으로 의미 있는 도메인(원장·주문·계약)에서 저장 방식을 고를 때.

두 방식을 같은 눈높이에 놓고 본다.

```text
상태 저장 (CRUD)                   이벤트 소싱
+---------------------+           +---------------------+
| Account             |           | AccountEvents       |
|   balance = 15      |           |   Deposited(20)     |
|                     |           |   Withdrawn(5)      |
| UPDATE 로 바꾼다     |           | INSERT 만 있다      |
| 이전 값은 사라진다   |           | balance=15 는 접어서 |
+---------------------+           +---------------------+
  → "지금 얼마"만 안다              → "어떻게 15가 됐나"까지 안다
```

**저장소에 UPDATE가 없다.** 모든 변경이 사건으로 쌓이고, 현재 상태는 처음부터 재생(replay)한 결과다.

- **비용** — 쓰기는 INSERT뿐이라 단순하지만, 현재 값을 볼 때마다 접어야 한다(아래 스냅샷으로 완화).

## 재생 비용과 스냅샷

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §1

**언제 쓰나** — 한 애그리게이트의 사건이 수만~수십만 개로 늘어 매번 처음부터 접기 부담될 때.

```text
Snapshot(v=9000, balance=1,200)  +  Event(9001..9137)  →  현재 상태
```

사건이 10만 개면 매번 10만 번 접을 수 없다. 그래서 특정 버전의 상태를 **스냅샷**으로 저장해 두고, 그 뒤 사건만 접는다.

> ⚠️ **스냅샷은 최적화이지 정본이 아니다.** 스냅샷이 틀리면 **버리고 처음부터 재생하면 된다.**\
> 정본은 언제나 사건들이다 — 이 성질이 이벤트 소싱의 가장 큰 장점 중 하나다.

- **비용** — 스냅샷 생성·보관·무효화가 운영 대상이 된다. 공짜가 아니라 관리해야 하는 캐시다.

## 무엇을 얻나

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §2

**언제 쓰나** — 아래 이득 중 하나라도 업무 요구로 강하게 걸릴 때가 채택의 근거가 된다.

| 얻는 것 | 왜 |
|---|---|
| **감사가능성이 공짜** | 모든 변경이 **원인과 함께** 남는다 — "왜 이 값이 됐나"에 항상 답한다 |
| **과거 시점 재구성** | "3월 5일 자정의 잔액"을 그 시점까지만 접어서 얻는다 |
| **파생 뷰 재구축** | 읽기 모델이 틀렸으면 지우고 재생한다 — 마이그레이션이 아니라 재구축이다 |
| **시간 여행 디버깅** | 사고 시점의 상태를 그대로 복원해 재현한다 |
| **새 질문에 소급 답변** | "작년 부분 환불이 몇 건이었나" — 사건이 남아 있으면 답할 수 있다 |

> ★ **마지막이 과소평가된다.** 상태만 저장하면 **당시에 묻지 않은 질문은 영원히 답할 수 없다.**\
> 사건을 남기면 "그때는 필요 없던 집계"를 몇 년 뒤에도 뽑아낼 수 있다.

- **비용(이득의 대가)** — 이 이득들은 아래 §무엇을 내주나의 대가와 맞바꾼 것이다. 공짜처럼 보이는 감사가능성도 저장량·조회 난이도를 대가로 얻는다.

## 무엇을 내주나

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §3

**언제 쓰나** — 채택을 검토할 때, 아래 대가를 감당할 수 있는지가 판정의 반이다.

| 대가 | 왜 |
|---|---|
| **조회가 어렵다** | "잔액 100만 이상 계좌"를 사건으로 못 찾는다 → **CQRS가 사실상 필수** |
| ★ **스키마를 못 고친다** | 과거 사건을 수정할 수 없다 — 필드를 잘못 설계하면 **upcasting**(변환 계층)을 영구히 안고 간다 |
| **재생 비용** | 스냅샷 관리가 운영 대상이 된다 |
| **저장량** | 상태 하나 대신 변경 전부를 남긴다 |
| **팀 학습** | 익숙한 CRUD 사고와 다르다 — 잘못 배우면 "이벤트 이름의 CRUD"가 된다 |

- **비용의 무게** — 이 중 되돌릴 수 없는 것은 **스키마 고정** 하나다. 나머지는 돈·운영으로 메울 수 있지만, 잘못 설계한 사건 필드는 영원히 변환 계층으로 떠안는다.

## 가장 흔한 실패 — 이벤트가 CRUD의 별명이 되는 것

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §3

**언제 쓰나** — 사건 이름을 지을 때. 여기서 틀리면 이벤트 소싱의 이득이 통째로 증발한다.

```text
나쁨   AccountUpdated(balance=15)        무슨 일이 있었는지 모른다
좋음   Deposited(20) · Withdrawn(5)      원인이 남는다
```

`AccountUpdated`는 결과 값만 담는다 — 입금이었는지 이자였는지 정정이었는지 알 수 없다.\
사건이 원인을 잃으면 "왜 이 값이 됐나"에 답할 수 없고, 그러면 상태 저장을 비싸게 흉내 낸 것에 불과하다.

> ★ **`XxxUpdated`는 거의 항상 신호다.** 도메인 사건이 아니라 **저장 동작에 이름을 붙인 것**이다.\
> 좋은 사건 이름은 "무엇을 바꿨나"가 아니라 "무슨 일이 있었나"를 과거형으로 말한다.

- **비용** — 이름 하나 잘못 지으면 스키마 고정(위)과 겹쳐, 그 나쁜 사건을 upcasting으로 영구히 데리고 다닌다.

## 언제 이벤트 소싱을 거부하는 게 합리적인가

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §4 (특정 프로젝트 결정을 일반 조건으로 승격)

**언제 쓰나** — "감사도 되고 과거 재구성도 되는데 왜 안 쓰지?"라는 물음에 답할 때.

거부의 핵심 근거는 대개 **성능도 복잡도도 아니다.**

> **이벤트 소싱의 진짜 대가는 "모델을 굳히는 것"이다.**\
> 한번 사건으로 스키마를 확정하면, 이후 도메인 모델을 고칠 때마다 **과거 사건 전부가 변환(upcasting) 대상**이 된다.

거부가 합리적인 조건은 이렇게 정리된다.

```text
모델이 아직 흔들리는가            → ★ 그렇다면 이르다 (굳히면 매 수정이 마이그레이션)
감사가능성을 이미 다른 수단으로     → 최대 이득이 이미 확보됨 → 더 얻을 게 적다
  확보했는가 (append-only 로그)
읽기 경로가 고빈도이고 현재 값을    → 스냅샷 운영 부담이 커진다
  즉시 계산해야 하는가
결정이 되돌릴 수 없는가           → 스키마가 틀리면 과거를 못 고친다 → 확신 없으면 미룬다
```

### 현장에서 만나는 상황

초기 단계 프로젝트에서 **도메인 모델을 여러 라운드에 걸쳐 갈아엎는** 일은 흔하다.\
예를 들어 환불·정산처럼 규칙이 자주 바뀌는 영역은 개발 중에 세 번 네 번 재설계된다.\
그 전에 사건으로 굳혔다면 재설계마다 과거 사건 전부가 변환 대상이었을 것이다 — 이게 "아직 이르다"의 실체다.

또한 시스템이 이미 **append-only 감사 로그**(뒤 절의 원장 등)를 갖고 있으면, 이벤트 소싱이 주는 최대 이득(감사가능성)은 이미 손에 있다.\
그러면 남은 이득을 위해 스키마 고정이라는 큰 대가를 치를 이유가 약해진다.

- **비용** — 거부를 택하면 §무엇을 얻나의 이득 일부(전면적 시간 여행·소급 답변)를 포기한다. 대신 모델을 자유롭게 고칠 수 있다.

## 부분 이벤트 소싱 — 한 컨텍스트만 사건으로

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §4 (프로젝트 결정 BR-40을 일반 절충으로 승격)

**언제 쓰나** — "전면 도입은 부담스럽지만 감사는 필요하다"는 자리. 실무에서 가장 흔한 절충이다.

```text
자금 이동 등 핵심 흐름  →  사건으로 (append-only 원장/전표)
나머지 상태            →  상태로 (계좌 잔액, 승인 상태)
```

**append-only 원장이 왜 "부분 이벤트 소싱"인가.**\
원장은 UPDATE 없이 자금 이동을 **전표(사건)로만** 쌓는다. 그 컨텍스트에 한해서는 저장 방식이 이벤트 소싱과 똑같다 — 사건이 정본이고, 감사가능성과 재생이 공짜다.\
차이는 범위뿐이다. 시스템 **전체**가 아니라 **한 컨텍스트**만 사건 기반이다. 전부 아니면 전무가 아니라는 뜻이다.

**그 대가는 대사(reconciliation)다.**\
상태(잔액)와 사건(전표)을 이중으로 두면 둘이 어긋날 수 있다.\
그래서 둘을 주기적으로 맞춰 보는 **대사** 장치가 반드시 따라온다 — **대사를 빼면 이 절충의 근거가 무너진다.**

> **언제 전면 전환을 다시 볼 것인가**: 상태와 사건의 **불일치가 구조적으로 반복되면** — 상태를 버리고 잔액을 **전표의 파생값(fold)**으로 돌리는 것이 신호다.

### 현장에서 만나는 상황

대부분의 실무 시스템이 이 절충 위에 있다 — 핵심 원장만 이벤트 기반으로 두고 나머지는 CRUD로 둔다.\
"이벤트 소싱을 도입할까"라는 물음은 실제로는 "**어느 한 컨텍스트**를 사건 기반으로 둘까"인 경우가 대부분이고, 대개 그것으로 충분하다.

- **비용** — 대사 장치(배치·정합성 점검)를 운영으로 떠안는다. 이 비용을 감당 못 하면 이 절충 자체를 택하면 안 된다.

## 판별 기준 — 언제 쓰나

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §5

**언제 쓰나** — 새 컨텍스트의 저장 방식을 고를 때 던지는 네 질문.

```text
"왜 이 값이 됐나"를 자주 묻는가       → 이벤트 소싱이 답이다
과거 시점 상태가 업무 요구인가         → 그렇다면 강한 근거
모델이 아직 흔들리는가                → ★ 아직 이르다
조회가 복잡한가                      → CQRS를 함께 감당할 수 있는가
```

| 잘 맞는 곳 | 안 맞는 곳 |
|---|---|
| 금융 원장 · 감사 · 규제 대응 | 단순 CRUD · 마스터 데이터 |
| 상태 변화 자체가 업무인 것(주문·계약) | 현재 값만 중요한 것(설정·프로필) |
| 사후 분석이 중요한 것 | 조회가 다양하고 즉시성이 필요한 것 |

> ★ **전부 아니면 전무가 아니다.** 한 컨텍스트(예: 원장)만 이벤트 기반으로 두는 것이 가장 흔하고, 대개 그것으로 충분하다.

- **비용** — 판별을 건너뛰고 "멋있어서" 전면 도입하면 스키마 고정·조회 난이도·팀 학습을 한꺼번에 떠안는다.

## 함께 오는 것들

> 출처: `jun-bank/docs/study/08-event-sourcing/README.md` — §6

**언제 쓰나** — 이벤트 소싱을 도입하면 딸려 오는 개념들을 정리할 때.

| 개념 | 관계 |
|---|---|
| **CQRS** | 조회가 어려워지므로 사실상 필수. 단 **CQRS는 이벤트 소싱 없이도 쓴다** |
| **프로젝션** | 사건 → 읽기 모델. 틀리면 **재생**한다 |
| **업캐스팅** | 옛 사건을 새 스키마로 변환. 스키마 변경의 유일한 길 |
| **사가(Saga)** | 여러 애그리게이트에 걸친 프로세스를 사건으로 조율 |

> ⚠️ **CQRS와 이벤트 소싱을 같은 것으로 오해하는 일이 흔하다. 별개다.**\
> CQRS는 읽기/쓰기 모델을 나누는 것이고, 이벤트 소싱은 저장을 사건으로 하는 것이다.\
> 한쪽만 쓰는 시스템이 흔하다(예: CQRS는 일부 쓰되 이벤트 소싱은 안 씀).

- **비용** — 이벤트 소싱 하나를 들이면 위 네 개가 함께 따라올 수 있다. "사건만 저장하면 끝"이 아니다.

## 핵심 문장

- **상태 저장은 "지금 값"을 덮어쓰고, 이벤트 소싱은 "바뀐 사건"을 지우지 않고 쌓아 접는다.**
- **스냅샷은 최적화이지 정본이 아니다 — 틀리면 버리고 재생하면 된다.**
- **이벤트 소싱의 진짜 대가는 성능이 아니라 "모델을 굳히는 것"이다 — 모델이 흔들리면 이르다.**
- **되돌릴 수 없는 유일한 대가는 스키마 고정이다 — 나쁜 사건 필드는 upcasting으로 영원히 데리고 다닌다.**
- **`XxxUpdated`는 사건이 CRUD의 별명이 됐다는 신호다 — 좋은 사건은 "무슨 일이 있었나"를 과거형으로 말한다.**
- **전부 아니면 전무가 아니다 — append-only 원장은 한 컨텍스트만의 부분 이벤트 소싱이고, 그 대가는 대사(reconciliation)다.**
- **CQRS ≠ 이벤트 소싱 — 조회 때문에 함께 오지만 서로 없이도 쓴다.**

## 용어 풀이

- **이벤트 소싱(Event Sourcing)** — 현재 상태 대신 상태를 바꾼 사건을 저장하고, 현재 값은 사건을 접어서 얻는 저장 방식.
- **fold / 재생(replay)** — 사건들을 처음부터 하나씩 적용해 현재(또는 과거 특정 시점) 상태를 계산하는 것.
- **스냅샷(Snapshot)** — 특정 버전의 상태를 미리 저장해 둔 것. 정본이 아니라 재생을 줄이는 최적화(캐시).
- **append-only** — 추가(INSERT)만 하고 수정·삭제하지 않는 저장. 원장·감사 로그가 대표.
- **감사가능성(Auditability)** — "왜 이 값이 됐나"를 원인과 함께 되짚을 수 있는 성질.
- **업캐스팅(Upcasting)** — 옛 스키마로 저장된 과거 사건을 읽을 때 새 스키마로 변환하는 계층. 사건을 못 고치므로 스키마 변경의 유일한 길.
- **프로젝션(Projection)** — 사건 스트림을 읽어 만든 조회용 읽기 모델. 틀리면 지우고 재생한다.
- **CQRS(Command Query Responsibility Segregation)** — 명령(쓰기)과 조회(읽기) 모델을 분리하는 설계. 이벤트 소싱과 자주 짝이지만 별개.
- **사가(Saga)** — 여러 애그리게이트·서비스에 걸친 긴 프로세스를 사건으로 조율하고 실패 시 보상하는 패턴.
- **대사(Reconciliation)** — 이중으로 둔 상태와 사건(예: 잔액과 전표)이 어긋나지 않았는지 주기적으로 맞춰 보는 것.
- **애그리게이트(Aggregate)** — 함께 변하고 함께 일관성을 지키는 도메인 객체 묶음. 사건이 쌓이는 단위.
- **부분 이벤트 소싱** — 시스템 전체가 아니라 한 컨텍스트만 사건 기반으로 두는 절충. 실무에서 가장 흔하다.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **git이 곧 이벤트 소싱이다.** git은 파일의 "현재 내용"을 덮어쓰는 대신 **커밋(사건)**을 쌓고, 어떤 시점의 트리든 커밋을 접어 재구성한다. `git checkout <해시>`가 과거 시점 재구성, packfile이 스냅샷에 해당한다. 이벤트 소싱이 낯설면 "저장소를 git처럼 쓰는 것"으로 이해하면 빠르다.
- **커맨드(Command)와 이벤트(Event)는 다르다.** 커맨드는 "입금해줘"라는 **요청**(거부될 수 있고 미래형·명령형), 이벤트는 "입금됨"이라는 **이미 일어난 사실**(거부 불가·과거형). 이벤트 소싱이 저장하는 것은 이벤트다. `XxxUpdated` 안티패턴은 사실 커맨드도 이벤트도 아닌 "저장 동작 로그"라서 나쁘다.
- **복식부기(double-entry bookkeeping)가 원조다.** 회계 장부는 수백 년간 잔액을 덮어쓰지 않고 차변·대변 전표만 쌓아 왔다 — append-only 원장·부분 이벤트 소싱은 이 관행을 소프트웨어로 옮긴 것이다.
- **전용 이벤트 스토어 제품이 있다.** EventStoreDB, Axon 등이 스냅샷·프로젝션·구독을 기본 제공한다. 다만 관계형 DB의 append-only 테이블 하나로 시작하는 경우가 실무에서 더 흔하다. *(제품 세부 기능은 확인 필요)*
- **temporal table과의 차이.** 일부 DB의 temporal table(시스템 버저닝)은 "과거 상태"를 자동 보존해 과거 시점 조회를 준다. 하지만 저장되는 것은 **상태의 버전**이지 "무슨 일이 있었나(원인)"가 아니다 — 감사가능성의 절반(값의 이력)만 주고 나머지 절반(원인)은 못 준다는 점이 이벤트 소싱과의 결정적 차이다.
