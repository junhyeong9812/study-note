# systems/architecture-styles — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/05-architecture-styles/README.md` (따라 친 원본 노트) · 이관일 2026-09-16.\
> 본문 스타일 절(레이어드~마이크로서비스)과 강점/약점·비교는 **원고**를 고쳐 쓴 것이다(문체·순서 유지).\
> 「한눈에」·「전체 흐름」의 그림과 몇몇 대비 도식은 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.\
> ★ 원고 3장의 "빈 비교 매트릭스"는 특정 프로젝트 판정용 빈 표라 이관에서 제외하고, 그 자리에 **모놀리식 vs 분산의 트레이드오프 개념**만 일반화해 옮겼다(「모놀리식 vs 분산 — 무엇을 맞바꾸나」 절).

**아키텍처 스타일** = "이 시스템은 무슨 모양인가"에 대한 답. 배포 단위가 하나면 **모놀리식**, 여럿이면 **분산형**이고, 그 안에서 다시 여러 스타일로 갈린다.

---

## 한눈에 — 쉽게 말하면

집 짓기를 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
한 채의 큰 집 (모놀리식)              여러 채로 나뉜 동네 (분산형)
+---------------------------+       +-----+  +-----+  +-----+
| 거실 · 주방 · 침실이       |       | 집A |  | 집B |  | 집C |
|   벽으로만 나뉨            |       +-----+  +-----+  +-----+
| 현관 하나로 드나든다       |       각자 문·수도·전기를 따로 가짐
| 리모델링하면 온 집이 멈춤   |       한 채가 무너져도 옆집은 산다
+---------------------------+       하지만 옆집 가려면 밖으로 나가야 한다
  → 오가기 쉽고 관리 하나              → 격리·독립은 좋고, 오가는 비용은 크다
```

**시스템도 똑같은 구조다.** 한 배포 단위 안에서 층·모듈로만 나누면 모놀리식이고(오가기 싸고 확장·격리가 약함), 여러 배포 단위로 쪼개면 분산형이다(독립 배포·장애 격리는 얻고, 네트워크·트랜잭션·운영의 대가를 치름).

쉽게 말하면 이렇다.\
**스타일은 "선택"이자 동시에 "발견"이다.** 처음엔 고르지만, 시간이 지나면 시스템이 실제로 어떤 모양인지가 드러난다. "우리는 마이크로서비스다"라고 선언해 놓고 DB를 공유하고 함께 배포한다면, 그건 **분산 모놀리스** — 분산의 대가는 다 치르면서 이점은 하나도 못 얻는 최악의 조합이다.

## 문제 — 이 개념이 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(아키텍처 설계 정리다). 대신 스타일 하나하나가 같은 질문에 서로 다르게 답한다.

```text
Q1  배포 단위를 하나로 둘까, 여럿으로 쪼갤까?          → 모놀리식 vs 분산형
Q2  (하나면) 무엇을 기준으로 내부를 나눌까?            → 레이어드 / 파이프라인 / 마이크로커널
Q3  (여럿이면) 데이터를 공유할까, 나눌까?              → 서비스 기반(공유) vs 마이크로서비스(분리)
Q4  서비스끼리 어떻게 대화할까?                        → 동기 호출 / 이벤트 / ESB
Q5  그렇게 나눈 대가로 무엇을 잃고 무엇을 얻나?         → 각 절의 강점/약점
```

아래 서머리는 이 질문들을 스타일별로 하나씩 분석·정리한 것이다.

## 전체 흐름

스타일 선택은 위에서 아래로 내려가는 결정 나무다.

```text
배포 단위가 하나인가?
        │
    ├─ 예 → 모놀리식 (§1)
    │        ├─ 레이어드      기술 층(표현·업무·영속)으로 나눔
    │        ├─ 파이프라인     변환 단계(필터)의 연속으로 나눔
    │        └─ 마이크로커널   변하지 않는 코어 + 붙였다 떼는 플러그인
    │
    └─ 아니오 → 분산형 (§2)  ⚠️ 네트워크·분산 트랜잭션·운영 N배의 대가를 먼저 각오
             ├─ 서비스 기반   굵은 서비스 4~12개 + 공유 DB (트랜잭션은 로컬 ACID)
             ├─ 이벤트 기반   비동기 이벤트로 느슨하게 (결과적 일관성 감수)
             ├─ 공간 기반     DB를 처리 경로에서 제거 (극한 부하용)
             ├─ SOA          ESB가 모든 통신을 중개 (쇠퇴)
             └─ 마이크로서비스 서비스별 DB + 독립 배포 (분산 트랜잭션 감수)
```

- 스타일 세 층은 추상화 레벨이 다르다: **아키텍처 스타일**(마이크로서비스) ⊃ **아키텍처 패턴**(Saga·Outbox·API Gateway·Circuit Breaker·CQRS) ⊃ **디자인 패턴**(Command·Observer·Strategy).
- 하나를 고른다고 다른 게 배제되지 않는다 — 분산형은 시스템 레벨, 레이어드·헥사고날은 애플리케이션 레벨이라 **한 마이크로서비스 내부가 헥사고날일 수 있다**.

## 1. 모놀리식 — 하나의 배포 단위 안에서 나눈다

> 출처: `jun-bank/docs/study/05-architecture-styles/README.md` — 1장

⚠️ **"모놀리식 = 나쁘다"는 오해다.** 모놀리식은 **배포 단위가 하나**라는 뜻일 뿐, 내부가 엉망이라는 뜻이 아니다. 잘 나뉜 모놀리식(모듈러 모놀리스)이 엉성한 마이크로서비스보다 훨씬 낫다.

### 1.1 레이어드 아키텍처 (Layered)

**언제 쓰나** — 아무 결정도 안 하면 자연히 도달하는 기본형. 가장 흔하고 누구나 안다.

```text
┌─────────────────────────────┐
│  프레젠테이션 (Presentation) │  ← HTTP, 화면
├─────────────────────────────┤
│  비즈니스 (Business)         │  ← 업무 규칙
├─────────────────────────────┤
│  영속화 (Persistence)        │  ← 데이터 접근
├─────────────────────────────┤
│  데이터베이스 (Database)      │
└─────────────────────────────┘
        ↓ 의존 방향은 아래로만
```

그림 해설 — 위 층이 아래 층을 부르고, 의존은 언제나 아래로만 흐른다.\
층 간 규칙은 두 가지다 — **엄격**(Closed)은 반드시 바로 아래 층만 부른다(변경 격리는 좋으나 단순 조회도 전 층을 거침), **완화**(Open)는 층을 건너뛴다(편하지만 층의 의미가 흐려짐).

**싱크홀 안티패턴** — 요청이 여러 층을 지나는데 **각 층이 아무 일도 안 하고 그냥 아래로 넘기기만** 하는 것.

```java
// 컨트롤러 → 서비스 → 리포지토리, 각 층이 그냥 전달만 한다
public UserResponse getUser(String id) { return userService.getUser(id); }   // 아무 일도 안 함
public UserResult   getUser(String id) { return userRepository.findById(id); } // 아무 일도 안 함
```

경험칙: 전체 요청의 **20% 이하**면 정상. 80%가 싱크홀이면 층이 과하다는 뜻이다.

비용(트레이드오프) —

| 강점 | 약점 |
|---|---|
| 이해하기 쉽다 (누구나 안다) | **변경이 수직으로 관통**한다 — 기능 하나 추가에 전 층을 건드림 |
| 관심사 분리가 명확 | 도메인이 아니라 **기술로 나뉜다** — "결제"가 3개 층에 흩어짐 |
| 개발 초기 속도가 빠름 | 배포 단위가 하나라 **부분 확장 불가** |

**헥사고날·클린 아키텍처와의 관계** — 레이어드의 **의존 방향 문제**를 고친 것이다.

```text
레이어드 (기술이 중심)                  헥사고날 (도메인이 중심)
비즈니스 ──의존──▶ 영속화               비즈니스 ──소유──▶ 포트 ◀──구현── 영속화
  (비즈니스가 DB를 안다)                  (DB가 비즈니스를 안다 — 의존이 뒤집힘)
```

핵심 차이 — 헥사고날은 도메인을 중심에 두고 기술을 바깥으로 밀어낸다. 층이 위아래가 아니라 **안팎**이 된다(의존 역전, DIP).

### 1.2 파이프라인 아키텍처 (Pipeline / Pipes and Filters)

**언제 쓰나** — 데이터가 일련의 변환을 **순서대로** 거치는 처리. 유닉스 파이프(`cat file | grep x | sort | uniq`)가 원형이다.

```text
[입력] → [필터1] → [파이프] → [필터2] → [파이프] → [필터3] → [출력]
          변환        전달       변환                  변환
```

그림 해설 — **필터**는 변환 하나만 하는 독립적·무상태 단위, **파이프**는 필터 사이의 단방향 통로다.\
필터를 순서대로 주입해 하나씩 통과시키는 것이 전부다.

```java
public interface DataFilter { Batch apply(Batch input); }   // 필터 하나 = 변환 하나

public class Pipeline {
    private final List<DataFilter> filters;   // 순서대로 주입
    public Batch run(Batch input) {
        Batch current = input;
        for (DataFilter f : filters) current = f.apply(current);   // 한 줄로 꿰어 통과
        return current;
    }
}
```

비용(트레이드오프) —

| 강점 | 약점 |
|---|---|
| 각 필터가 **독립적으로 테스트** 가능 | 트랜잭션 처리에 부적합 (중간 실패 처리가 까다로움) |
| 필터 **재조합·재사용**이 쉬움 | 필터 간 데이터 형식 합의가 필요 |
| 병렬화하기 좋음 | 흐름 전체를 한눈에 보기 어려움 |

### 현장에서 만나는 상황 (파이프라인)

정산·대사 같은 **배치 파이프라인**에 잘 맞는다 — 파일 파싱 → 검증 → 매칭 → 원장 반영 → 리포트가 정확히 파이프라인 형태다.\
관건은 **부분 실패 시 재처리**다. 필터마다 어디까지 처리했는지 지점을 기록해 두어야 중간에서 재개할 수 있다.

### 1.3 마이크로커널 아키텍처 (Microkernel / Plug-in)

**언제 쓰나** — **종류가 계속 늘어나는** 영역. IDE 플러그인, 브라우저 확장, 결제 수단이 대표적이다.

```text
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ 플러그인 A│  │ 플러그인 B│  │ 플러그인 C│
        └────┬─────┘  └────┬─────┘  └────┬─────┘
             └─────────────┼─────────────┘
                    ┌──────▼──────┐
                    │  코어 시스템  │  ← 최소한의 공통 로직 + 플러그인 등록·실행
                    └─────────────┘
```

그림 해설 — **코어**는 변하지 않는 최소 기능과 플러그인 등록·실행 메커니즘만 갖는다.\
**플러그인**은 독립적으로 추가·제거되는 기능 단위다.\
새 기능이 늘어도 코어 코드는 바뀌지 않는다(OCP) — 코어는 계약(인터페이스)만 알고, 타입으로 골라 위임한다.

```java
public interface MethodPlugin {                 // 코어가 정의하는 계약
    MethodType type();
    Result handle(Command command);
}

public class Kernel {                           // 코어 — 플러그인이 늘어도 안 바뀐다
    private final List<MethodPlugin> plugins;
    public Result handle(Command command) {
        return plugins.stream()
            .filter(p -> p.type() == command.type())
            .findFirst()
            .orElseThrow(() -> new UnsupportedException(command.type()))
            .handle(command);                   // 타입으로 골라 위임
    }
}
```

비용(트레이드오프) —

| 강점 | 약점 |
|---|---|
| **확장이 코어를 건드리지 않는다** | 코어의 계약(인터페이스) 설계가 어렵다 |
| 플러그인별 독립 개발·테스트 | 계약을 바꾸면 **모든 플러그인이 깨진다** |
| 필요한 것만 로드 가능 | 플러그인 간 협력이 필요해지면 구조가 무너진다 |

### 현장에서 만나는 상황 (마이크로커널)

**결제 수단(체크/신용/포인트), 인증 방식, 정산 파일 포맷**처럼 종류가 늘어나는 영역에 맞는다.\
단, **코어 계약을 정확히 그을 수 있을 때만** 유효하다 — 서로 다른 종류(예: 체크카드와 신용카드의 승인 흐름)가 실제로 같은 계약에 담기는지 먼저 확인해야 한다. 계약이 어긋나면 플러그인마다 예외가 새고 구조가 무너진다.

## 2. 분산형 — 여러 배포 단위로 나눈다

> 출처: `jun-bank/docs/study/05-architecture-styles/README.md` — 2장

⚠️ **공통 대가** — 분산형은 예외 없이 아래를 지불한다.

- 네트워크는 **느리고, 불안정하고, 실패한다**
- 트랜잭션이 **한 번에 끝나지 않는다**
- 디버깅이 **로그 한 곳으로 안 끝난다**
- 배포·운영 대상이 **N배**가 된다

이 대가를 상쇄할 이유가 없으면 분산하지 않는 게 맞다.

### 2.1 서비스 기반 아키텍처 (Service-Based)

**언제 쓰나** — 배포는 독립적으로 하고 싶지만 **분산 트랜잭션의 지옥은 피하고 싶을 때.** MSA로 가는 중간 단계로 최적이다.

```text
     [API Gateway / UI]
            │
   ┌────────┼────────┐
   ▼        ▼        ▼
[서비스A] [서비스B] [서비스C]     ← 굵직한 4~12개 단위, 독립 배포
   └────────┼────────┘
       ┌────▼────┐
       │  공유 DB │              ← ★ DB는 하나
       └─────────┘
```

그림 해설 — 서비스는 굵게 나뉘어 독립 배포되지만, **DB 하나를 공유**한다.\
이 한 가지가 모든 것을 바꾼다 — 트랜잭션이 로컬 ACID로 끝나므로 Saga가 필요 없다.

마이크로서비스와의 결정적 차이 —

```text
서비스 기반 (DB 공유)                    마이크로서비스 (DB 분리)
[A]  [B]  [C]                          [A]   [B]   [C]
 └────┼────┘                            │     │     │
   [공유 DB] 하나                       [DBa][DBb][DBc] 각자
  → 트랜잭션 로컬 ACID로 끝남            → 분산 트랜잭션(Saga) 필요
  → 정합성 쉬움, 스키마 변경이 전파      → 정합성 어려움, 독립성 최대
```

| | 서비스 기반 | 마이크로서비스 |
|---|---|---|
| DB | **공유** | 서비스별 분리 |
| 트랜잭션 | **로컬 ACID로 끝남** | 분산 트랜잭션 |
| 서비스 크기 | 굵다 (도메인 묶음) | 잘다 (바운디드 컨텍스트) |
| 서비스 수 | 4~12 | 수십~수백 |
| 데이터 정합성 | **쉽다** | 어렵다 |

비용(트레이드오프) —

| 강점 | 약점 |
|---|---|
| **트랜잭션이 여전히 단순** — Saga가 필요 없다 | DB 스키마 변경이 **모든 서비스에 영향** |
| 독립 배포의 이점은 얻는다 | 서비스 간 결합이 DB를 통해 남는다 |
| 운영 부담이 MSA보다 훨씬 작다 | 부분 확장이 DB 병목에 막힌다 |
| **MSA로 가는 중간 단계로 최적** | |

### 현장에서 만나는 상황 (서비스 기반)

실무에서 가장 저평가된 스타일이다. 대부분의 팀에게 마이크로서비스보다 이쪽이 정답인 경우가 많다 — 모놀리식의 배포 문제는 풀면서 분산 트랜잭션의 지옥은 피하기 때문이다.\
**다만 분산 트랜잭션 문제가 발생하지 않는다는 것이 함정일 수 있다** — 분산 환경의 문제를 직접 겪는 것이 목표(학습·역량 확보 등)라면, 이 스타일은 그 학습 목표의 절반을 없앤다. "실무 최선"과 "학습 최선"이 갈리는 지점이다.

### 2.2 이벤트 기반 아키텍처 (Event-Driven)

**언제 쓰나** — 서비스 간 결합을 극도로 낮추고, 비동기로 확장성·응답성을 얻고 싶을 때. 대신 결과적 일관성을 감수한다.

두 가지 토폴로지가 있다.

```text
① 브로커 토폴로지 (중앙 조율자 없음 = 코레오그래피)
[결제서비스] ─event─▶ [브로커] ─▶ [원장서비스] ─event─▶ [브로커] ─▶ [알림서비스]
                                                              └─▶ [정산서비스]
  각 서비스가 이벤트를 듣고 스스로 다음 행동을 결정 — 전체 흐름이 어느 코드에도 통째로 없다

② 중재자 토폴로지 (중앙 조율자 있음 = 오케스트레이션)
                  ┌──────────────┐
[요청] ──────────▶│   중재자      │
                  └───┬───┬───┬──┘
                      ▼   ▼   ▼
                     [A] [B] [C]
  중재자가 순서를 알고 각 서비스를 호출 — 흐름이 한 곳에 적혀 있다
```

그림 해설 — 브로커형은 흐름이 흩어져 결합이 낮지만 추적이 어렵고, 중재자형은 흐름이 한 곳에 모여 파악은 쉽지만 중재자가 커진다.

**결과적 일관성을 감수한다는 뜻** —

```text
14:00:00.000  결제 승인 완료 (승인 서비스)
14:00:00.010  이벤트 발행
14:00:00.150  원장 반영 (원장 서비스)
              ↑
     이 150ms 동안 "승인은 됐는데 원장엔 없는" 상태가 존재한다
```

이 중간 상태가 사용자에게 보이면 어떻게 설명할지가 설계 문제가 된다(예: "결제 예정" vs "결제 완료" 표시로 구분).

비용(트레이드오프) —

| 강점 | 약점 |
|---|---|
| **높은 확장성·응답성** — 비동기라 대기하지 않음 | **결과적 일관성**을 감수해야 함 |
| 서비스 간 결합이 매우 낮음 | 전체 흐름 파악이 어렵다 |
| 새 소비자 추가가 기존 코드를 안 건드림 | **디버깅이 극도로 어렵다** |
| 장애 격리가 좋음 | 이벤트 순서·중복 처리 문제 |

**디버깅이 왜 어려운가** — 동기 호출은 스택 트레이스 하나로 끝난다. 이벤트 기반은 발행 시점과 소비 시점이 **다른 스레드·다른 프로세스·다른 시각**이다. 그래서 **분산 추적(distributed tracing)이 선택이 아니라 필수**가 된다.

### 2.3 공간 기반 아키텍처 (Space-Based)

**언제 쓰나** — **극단적이고 예측 불가능한 부하.** 콘서트 티켓 오픈, 블랙프라이데이 세일, 실시간 입찰.

```text
   [요청] ──▶ [메시징 그리드] ──▶ 부하 분산
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   [처리유닛1]  [처리유닛2]  [처리유닛3]      ← 각자 인메모리 데이터 복제본을 가짐
        └───────────┼───────────┘
              [데이터 복제 엔진]
                    │
                    ▼
              [데이터베이스]                 ← 비동기로만 기록. 읽기 경로에 없다
```

그림 해설 — 핵심 발상은 **DB를 요청 처리 경로에서 제거**하는 것이다.\
대부분의 확장성 병목은 DB이므로, 처리 유닛이 인메모리 데이터로 작업하고 DB에는 나중에 비동기로 쓴다.\
"공간(Space)"은 튜플 스페이스(분산 공유 메모리) 개념에서 왔다.

비용(트레이드오프) —

| 강점 | 약점 |
|---|---|
| **극한의 확장성·탄력성** | 구현 복잡도가 매우 높다 |
| DB 병목 제거 | **데이터 정합성 보장이 어렵다** |
| 응답 시간이 매우 빠름 | 인메모리 데이터 유실 위험 |
| | 캐시 일관성 문제 |

**금융 원장에 쓸 수 있는가 — 대체로 아니다.** 이 스타일은 강한 일관성을 포기하는 대가로 확장성을 얻는데, 원장은 정확히 그 반대를 요구한다.\
다만 **조회 경로에는 부분 적용 가능**하다 — 잔액 조회 같은 읽기는 캐시 그리드로, 승인·기록 같은 쓰기는 강한 일관성 경로로 나누는 방식(CQRS와 결합).

### 현장에서 만나는 상황 (공간 기반)

**기능 정확성이 품질 1순위인 시스템(금융 원장 등)에서는 채택하지 않는다.** 인메모리 유실·정합성 위험이 그 시스템의 최우선 요구와 정면으로 부딪힌다. 개념만 알아 두고, 필요하면 읽기 경로에만 부분 적용한다.

### 2.4 서비스 지향 아키텍처 (SOA)

**언제 쓰나** — 지금은 거의 안 쓴다(쇠퇴). 전사 재사용과 중앙 통제가 목표였던 과거 대기업 통합에서 나왔다.

```text
   [서비스A]   [서비스B]   [서비스C]
       │           │           │
       └───────────┼───────────┘
            ┌──────▼──────┐
            │     ESB     │   ← Enterprise Service Bus
            │ 라우팅·변환  │      모든 통신이 여기를 지난다
            │ 오케스트레이션│
            └─────────────┘
```

그림 해설 — **ESB**는 서비스 간 통신을 중개하며 프로토콜 변환·메시지 변환·라우팅·오케스트레이션까지 맡는 중앙 미들웨어다.\
모든 통신이 ESB를 지난다는 것이 SOA의 특징이자 몰락의 씨앗이었다.

MSA와의 차이 —

| | SOA | 마이크로서비스 |
|---|---|---|
| 재사용 강조 | **매우 강함** (전사 재사용) | 약함 (**중복 허용**) |
| 통신 | **ESB 경유** (스마트 파이프) | 직접 통신 (**덤 파이프, 스마트 엔드포인트**) |
| 데이터 | 공유 DB 흔함 | 서비스별 분리 |
| 거버넌스 | 중앙집중 | 분산 (팀 자율) |
| 크기 | 크다 (전사 업무 단위) | 작다 (바운디드 컨텍스트) |

**왜 쇠퇴했나** —

1. **ESB가 단일 장애점이자 병목**이 되었다 — 모든 통신이 지나가니까
2. **ESB가 비즈니스 로직을 흡수**했다 — 라우팅 규칙에 업무 규칙이 섞여 아무도 이해 못하는 블랙박스가 됨
3. **중앙 거버넌스가 개발 속도를 죽였다** — 서비스 하나 바꾸려면 ESB 팀 승인 필요
4. **벤더 종속** — 상용 ESB 제품에 묶임

> 교훈: 마이크로서비스의 "덤 파이프, 스마트 엔드포인트" 원칙은 SOA의 실패에서 나왔다. **미들웨어를 똑똑하게 만들지 마라.**

### 현장에서 만나는 상황 (SOA의 교훈)

API Gateway가 ESB화되지 않도록 주의해야 한다. 게이트웨이는 **라우팅·인증까지만** 하고 업무 로직을 넣지 않는다.\
"통신을 중개하는 중앙 지점에 업무 규칙이 슬금슬금 쌓이는가"가 위험 신호다 — 쌓이기 시작하면 그것이 새로운 ESB다.

### 2.5 마이크로서비스 아키텍처 (Microservices)

**언제 쓰나** — 도메인 경계가 뚜렷하고, 팀·배포 자동화가 갖춰졌으며, 독립 배포·확장·장애 격리의 값이 분산의 대가를 넘어설 때.

```text
              [API Gateway]
                    │
       ┌────────┬───┴────┬────────┐
       ▼        ▼        ▼        ▼
   [서비스A] [서비스B] [서비스C] [서비스D]
       │        │        │        │
     [DB A]  [DB B]   [DB C]   [DB D]      ← ★ 서비스마다 자기 DB
       └────────┴───┬────┴────────┘
              [메시지 브로커]              ← 비동기 통신
```

그림 해설 — 서비스마다 자기 DB를 갖고(다른 서비스 DB를 직접 읽지 않는다), 게이트웨이로 들어와 브로커로 비동기 통신한다.

핵심 원칙 —

| 원칙 | 뜻 |
|---|---|
| **서비스별 DB** | 다른 서비스의 DB를 직접 읽지 않는다. **가장 중요하고 가장 자주 어겨지는 원칙** |
| **독립 배포** | 다른 서비스를 기다리지 않고 배포할 수 있다 |
| **바운디드 컨텍스트 정렬** | 서비스 경계 = 도메인 경계. 기술 경계가 아니다 |
| **중복 허용** | 결합을 피하려 코드·데이터 중복을 감수한다 (비중복 N ↔ 느슨한 결합 L 충돌) |
| **탈중앙 거버넌스** | 서비스마다 다른 기술 선택 가능 |

비용(트레이드오프) —

| 강점 | 약점 |
|---|---|
| 서비스별 독립 배포·확장 | **분산 트랜잭션** — Saga·보상 필요 |
| 장애 격리 | 네트워크 실패를 상시 다뤄야 함 |
| 기술 다양성 | 운영 복잡도 폭증 (배포·모니터링·로그) |
| 팀 자율성 | 데이터 정합성 보장이 어렵다 |
| 도메인 경계가 물리적으로 강제됨 | **로컬 개발 환경이 무거워진다** · 통합 테스트가 어렵다 |

**치르는 대가 (구체적으로)** —

1. **분산 트랜잭션** — 계좌 차감 + 원장 기록이 다른 서비스면 한 트랜잭션으로 못 묶는다 → Saga, 보상, 멱등성
2. **네트워크 실패** — 타임아웃, 부분 실패, "상태 불명" → 재시도, 서킷 브레이커, 망취소
3. **데이터 조회** — "이 사용자의 모든 거래"를 보려면 여러 서비스를 조합 → API 조합, CQRS 읽기 모델
4. **운영** — 서비스 N개 = 로그 N곳, 메트릭 N곳, 배포 N번 → 중앙 로깅, 분산 추적 필수
5. **개발 환경** — 로컬에서 전부 띄워야 한다 → Docker Compose, 메모리 요구량 증가

**언제 쓰면 안 되나** —

- **도메인 경계가 아직 불명확할 때** — 잘못 그은 경계는 모놀리식보다 고치기 훨씬 어렵다. "모놀리스 우선(Monolith First)"이 권장되는 이유
- **팀이 작을 때** — 서비스 수 > 개발자 수면 운영이 불가능
- **강한 일관성이 핵심일 때** — 금융 코어 원장 같은 영역
- **배포 자동화가 없을 때** — 수동 배포로 서비스 여러 개는 지옥

### 현장에서 만나는 상황 (마이크로서비스)

MSA를 "쓰는 이유"로 흔히 드는 것들(모듈 분리·팀 분리·도메인 경계·기술 부채 격리)은 상당수가 **잘 나뉜 모놀리식으로도 얻을 수 있다.** 그러니 정직한 물음은 하나다 — **이 시스템에서 분산의 대가를 치를 만큼 얻는 것이 무엇인가.**\
학습·역량 확보가 진짜 동인이라면 "MSA가 더 좋아서"가 아니라 "분산 환경의 문제를 직접 겪는 것이 목표라서"라고 적는 것이 정직하다.

## 모놀리식 vs 분산 — 무엇을 맞바꾸나

> ★ 원고 3장의 "빈 비교 매트릭스"는 특정 프로젝트가 자기 품질 우선순위에 맞춰 직접 채우는 판정용 빈 표라 이관에서 제외했다. 대신 그 표가 담으려던 **개념**(모놀리식과 분산의 트레이드오프)만 일반화해 남긴다. *(Claude 정리 — 원고의 각 축을 개념으로 압축)*

```text
모놀리식 (배포 단위 1)                  분산 (배포 단위 다수)
+-----------------------------+       +-----------------------------+
| 확장: 통째로만 늘림          |       | 확장: 필요한 서비스만 늘림   |
| 데이터 일관성: 로컬 ACID로 쉬움|       | 데이터 일관성: 분산되어 어려움|
| 장애 격리: 약함 (같이 죽음)   |       | 장애 격리: 강함 (한 곳만 죽음)|
| 개발/운영 난이도: 낮음        |       | 개발/운영 난이도: 높음(N배)  |
| 초기 개발 속도: 빠름          |       | 초기 개발 속도: 느림          |
| 변경 파급: 수직 관통          |       | 변경 파급: 서비스 안에 갇힘   |
| 흐름 가시성: 좋음 (한 프로세스)|       | 흐름 가시성: 나쁨(추적 필요) |
+-----------------------------+       +-----------------------------+
  → 얻는 것: 단순함·정합성·속도          → 얻는 것: 독립성·격리·부분 확장
  → 잃는 것: 부분 확장·격리              → 잃는 것: 단순함·정합성·가시성
```

판단하는 법 — 절대 점수가 아니라 **서로 비교한 상대적 우열**로 본다. 그런 다음 그 시스템의 **품질 속성 우선순위**(정확성·확장성·응답성·운영성 중 무엇이 위인가)에서 상위 몇 개만 보면 결론이 좁혀진다. 우선순위가 정합성·단순함이면 모놀리식/서비스 기반으로, 부분 확장·독립 배포·장애 격리면 분산으로 기운다.

---

## 핵심 문장

- **아키텍처 스타일은 "배포 단위를 하나로 둘까 여럿으로 쪼갤까"가 첫 갈림길이고, 나머지는 그 안의 선택이다.**
- **분산은 공짜가 아니다 — 네트워크·분산 트랜잭션·운영 N배를 상쇄할 이유가 없으면 분산하지 않는다.**
- **서비스 기반과 마이크로서비스를 가르는 단 하나는 "DB를 공유하는가"이며, 그 하나가 트랜잭션·정합성·결합을 전부 결정한다.**
- **"MSA다"라고 선언하고 DB를 공유·함께 배포하면 분산 모놀리스 — 대가는 다 치르고 이점은 못 얻는 최악이다.**
- **SOA의 실패가 준 교훈은 "미들웨어를 똑똑하게 만들지 마라(덤 파이프, 스마트 엔드포인트)"다.**
- **잘 나뉜 모놀리식이 엉성한 마이크로서비스보다 낫다 — 경계가 불명확하면 "모놀리스 우선".**

---

## 관련 자료

- 형제 주제(있다면): 클린 코드/CLEAN 5속성 — 마이크로서비스의 "중복 허용"이 곧 **N(비중복) ↔ L(느슨한 결합)의 충돌**을 서비스 경계에서 푸는 결정이다.
- 분산 트랜잭션 해법(Saga·Outbox), 코레오그래피/오케스트레이션은 별도 주제(이벤트·분산 트랜잭션)로 이어진다. *(Claude 보강 — 후속 주제 안내)*

## 용어 풀이

- **아키텍처 스타일(Style)** — 시스템 전체의 구조적 골격. "이 시스템은 무슨 모양인가"의 답.
- **아키텍처 패턴(Pattern)** — 스타일 안에서 반복되는 문제의 해법(Saga·Outbox 등). 스타일보다 작고 구체적.
- **디자인 패턴(Design Pattern)** — 클래스·객체 수준의 해법(Command·Observer 등).
- **배포 단위(Deployment Unit)** — 독립적으로 배포·기동되는 덩어리. jar 하나, 컨테이너 하나.
- **결합도(Coupling)** — 한쪽을 바꿀 때 다른 쪽도 바꿔야 하는 정도. 낮을수록 좋다.
- **바운디드 컨텍스트(Bounded Context)** — 하나의 용어 체계가 일관되게 통하는 경계. DDD 용어.
- **강한 일관성(Strong Consistency)** — 읽으면 항상 최신 값이 보이는 일관성.
- **결과적 일관성(Eventual Consistency)** — 지금은 달라도 시간이 지나면 결국 같아지는 일관성.
- **탄력성(Elasticity)** — 부하 변화에 맞춰 빠르게 늘리고 줄이는 능력.
- **장애 격리(Fault Isolation)** — 한 부분의 장애가 다른 부분으로 번지지 않는 성질.
- **싱크홀 안티패턴(Architecture Sinkhole)** — 요청이 여러 층을 지나는데 각 층이 그냥 아래로 넘기기만 하는 것. 20% 이하가 정상.
- **분산 모놀리스(Distributed Monolith)** — 분산으로 나눴으나 DB 공유·함께 배포로 이점을 못 얻는 최악의 조합.
- **ESB(Enterprise Service Bus)** — 모든 서비스 통신을 중개하며 변환·라우팅·오케스트레이션까지 맡는 중앙 미들웨어.
- **코레오그래피(Choreography)** — 중앙 조율자 없이 각 서비스가 이벤트를 듣고 스스로 다음 행동을 정하는 방식.
- **오케스트레이션(Orchestration)** — 중재자가 순서를 알고 각 서비스를 호출하는 방식.
- **튜플 스페이스(Tuple Space)** — 분산 공유 메모리 개념. 공간 기반 아키텍처의 어원.
- **분산 추적(Distributed Tracing)** — 여러 프로세스에 걸친 한 요청의 흐름을 하나로 잇는 추적. 이벤트/MSA에서 필수.
- **Saga** — 분산 트랜잭션을 여러 로컬 트랜잭션 + 보상으로 나눠 처리하는 패턴.
- **멱등성(Idempotency)** — 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. 재시도의 전제.
- **서킷 브레이커(Circuit Breaker)** — 상대가 계속 실패하면 호출을 잠시 끊어 장애 전파를 막는 패턴.
- **헥사고날(Hexagonal / 포트&어댑터)** — 도메인을 중심에 두고 기술을 바깥으로 밀어내 의존을 역전시킨 구조.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **분산 컴퓨팅의 오류(Fallacies of Distributed Computing).** 원고의 "분산 공통 대가"는 이 고전 목록의 실행판이다 — "네트워크는 신뢰할 수 있다 / 지연은 0이다 / 대역폭은 무한하다 / 네트워크는 안전하다 / 토폴로지는 안 바뀐다 / 관리자는 하나다 / 전송 비용은 0이다 / 네트워크는 균질하다"는 8가지 **틀린 가정**을 경계하라는 것. 분산을 처음 하는 사람이 꼭 밟는 지뢰들이다.
- **CAP 정리.** 분산 데이터에서 네트워크 분단(Partition)이 생기면 **일관성(C)과 가용성(A) 중 하나는 포기**해야 한다. 원고의 "강한 일관성 vs 결과적 일관성" 선택이 바로 이 정리의 실무판이다 — 금융 원장은 C를, 알림·집계는 A(가용성)를 택하는 식으로 경로마다 다르게 잡는다.
- **콘웨이의 법칙(Conway's Law).** "시스템 구조는 그 조직의 소통 구조를 닮는다." 마이크로서비스의 "서비스 경계 = 팀 경계 = 바운디드 컨텍스트"가 이 법칙을 역이용한 것(역콘웨이 전략)이다.
- **스트랭글러 무화과(Strangler Fig) 패턴.** 모놀리식 → 마이크로서비스 이전을 **한 번에 갈아엎지 않고** 기능을 하나씩 새 서비스로 떼어내며 기존을 서서히 감싸 죽이는 방식. "모놀리스 우선 후 필요할 때 쪼갠다"의 구체적 실행법이다.
- **스타일을 바꾸는 비용은 데이터 소유권 분리 정도에 비례한다.** 코드는 옮기기 쉽지만 데이터를 나누는 것(공유 DB → 서비스별 DB)이 가장 비싸다 — 이전 비용을 가늠할 때 코드 줄 수가 아니라 "DB가 얼마나 얽혀 있는가"를 본다. *(확인 필요 — 일반 통설이나 정량 근거는 상황마다 다름)*
