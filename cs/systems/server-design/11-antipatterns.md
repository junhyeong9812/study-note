# 11. 안티패턴 모음

> "무엇을 해야 하나"만큼 **"무엇을 하면 안 되나"**가 중요하다.\
> 아래는 대부분 **좋은 의도로 도입됐다가 문제를 키운** 것들이다.\
> 출처: `jun-bank/docs/study/notes/server-design/11-antipatterns.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(세로 도식)만 입힘. 각 항목은 "하면 벌어지는 일(실패) → 처방(방어)"으로 읽는다.

## 구조 안티패턴

### 1. 분산 모놀리스

**증상**: 마이크로서비스로 쪼갰는데, 기능 하나 바꾸려면 서비스 3개를 동시에 배포해야 한다.

- 원인: 경계를 **기술 계층**(API 서비스 / 로직 서비스 / DB 서비스)으로 그음
- 결과: 분산의 비용(네트워크, 관측, 배포 복잡도)은 다 내고 이점(독립 배포)은 없음
- **판별법**: "이 기능을 바꾸려면 몇 개를 동시에 배포해야 하나?" 2개 이상이면 경계가 틀렸다
- **처방**: 경계를 **비즈니스 능력** 단위로 다시 긋는다. 또는 **다시 합친다** (합치는 게 부끄러운 일이 아니다)

> **분산 모놀리스(distributed monolith)** — 물리적으로는 나뉘었지만 함께 배포해야만 하는, 결합이 그대로인 마이크로서비스.\
> 예: 기능 하나 바꾸는 데 서비스 3개를 같이 배포한다면 — 분산 비용만 내고 독립 배포 이점은 없는 최악의 조합이다.

### 2. 조기 마이크로서비스

**증상**: 팀 5명인데 서비스 15개.

- 경계가 확실해지기 전에 쪼개면 **틀린 경계가 코드에 굳는다**
- **모놀리스가 기본값이다.** 잘 모듈화된 모놀리스 → 경계가 명확해지면 그때 분리
- 조직 규모가 감당 못 하는 서비스 수는 그 자체로 장애 원인

### 3. 공유 데이터베이스

**증상**: 서비스는 나눴는데 여러 서비스가 같은 테이블을 직접 읽고 쓴다.

- 스키마를 못 바꾼다 (누가 쓰는지 모름)
- 한 서비스의 무거운 쿼리가 다른 서비스를 죽인다
- **결합도는 그대로인데 분산 비용만 추가됨**
- **처방**: 데이터 소유권을 명확히. 다른 서비스는 API나 이벤트로만 접근

### 4. 동기 호출 체인

**증상**: 요청 하나가 5개 서비스를 순차로 거친다.

- 가용성이 곱셈으로 떨어진다 (99.9%^5 = 99.5%)
- 지연이 누적된다
- 하나가 느려지면 전체가 느려진다
- **처방**: 병렬 호출, 데이터 사전 복제, 비동기 전환, 또는 경계 재설계

## 확장 안티패턴

### 5. 측정 없이 서버 늘리기

병목이 DB인데 앱을 늘리면 **DB 커넥션만 늘어나 상황이 악화된다.** 돈은 쓰고 성능은 그대로거나 나빠진다.\
→ 병목 확인이 먼저 (→ [`01-scaling-principles.md`](./01-scaling-principles.md))

### 6. 근본 문제를 캐시로 덮기

- 캐시 미스 경로가 여전히 느리고, **그게 p99가 된다**
- 캐시가 죽으면 시스템 전체가 죽는다 (캐시가 SPOF가 됨)
- 무효화 버그가 데이터 정합성 문제로 나타난다
- **처방**: **먼저 쿼리를 고치고, 그 다음 캐시.** 순서를 바꾸면 캐시를 걷어낼 수 없다

### 7. 조기 샤딩

샤딩은 **되돌리기 가장 어려운 결정**이다.

- 크로스 샤드 조인·트랜잭션·유니크·집계가 전부 어려워진다
- 운영 복잡도가 크게 는다
- **수직 확장 → 읽기 복제본 → 파티셔닝**을 다 해보고 마지막에

### 8. 무한 큐 / 무한 캐시

"큐를 넣었으니 괜찮다" — 실패와 방어를 대비하면:

```text
[무한 큐 (지표는 전부 초록)]          [유한 큐 (상한 + 백프레셔)]
유입 > 처리                           유입 > 처리
   ↓                                   ↓
큐가 무한히 쌓임                       큐가 상한에 도달
   ↓                                   ↓
지연 무한 증가 · 메모리 팽창           초과분은 즉시 거부 (느려짐이 보인다)
   ↓                                   ↓
어느 순간 OOM으로 죽는다               죽지 않고 부하를 밀어낸다
```

- 유입 > 처리면 **지연이 무한히 증가**한다. 큐는 피크 완충일 뿐
- 상한 없는 큐·캐시는 OOM의 대표 원인
- **모든 버퍼에 상한을 둔다**

> 대비의 결론: 무한 큐는 **지표가 초록인 채로 죽는다.** 유한 큐는 느려지는 게 눈에 보인다.

### 9. 오토스케일링으로 설계 문제 덮기

- 직렬 병목이면 스케일아웃이 무의미하다
- **앱 오토스케일이 DB 커넥션을 폭증시켜 DB를 죽인다** (매우 흔함)
- 버그로 인한 부하면 돈만 태운다
- 상한 미설정 시 비용 사고

## 복원력 안티패턴

### 10. 타임아웃 없음

**단일 최다 원인.** 외부가 죽는 게 아니라 **느려지기만 해도** 스레드가 고갈되어 전체가 죽는다.

```text
[타임아웃 없음]                       [타임아웃 있음]
외부가 느려짐(죽지도 않음)             외부가 느려짐
   ↓                                   ↓
스레드가 응답을 무한정 기다림           설정 시간에 끊고 실패 반환
   ↓                                   ↓
스레드 풀 고갈 → 전체 다운             스레드 반납 → 다른 요청은 정상
```

> 타임아웃이 없으면 서킷 브레이커도 재시도도 전부 무의미하다.

### 11. 무제한/중복 재시도

- 재시도가 장애를 **증폭**시킨다
- 계층마다 3회씩이면 3계층에서 27배
- 지터 없는 재시도는 파도처럼 몰린다
- **처방**: 한 계층에서만, 지수 백오프 + 지터, 재시도 예산

### 12. 400번대 에러에 재시도

요청 자체가 잘못된 것이라 **몇 번을 해도 같은 결과**다. 자원만 태운다.

### 13. 타임아웃과 재시도의 곱을 계산 안 함

```text
타임아웃 10초 × 재시도 3회 = 최악 30초
   ↓
그런데 사용자 SLA는 3초
   ↓
클라이언트는 이미 떠났는데 서버는 계속 일한다 (유령 작업)
```

### 14. 깊은 헬스체크

헬스체크가 DB를 확인 → DB가 잠깐 느려짐 → **전 인스턴스가 동시에 unhealthy** → 부분 장애가 전체 장애로.

> Liveness는 절대 의존성을 보지 않는다.

### 15. 이중화했는데 용량 계획을 안 함

2대 Active-Active를 각각 70%로 운영 → 한 대 죽으면 남은 한 대가 140% → **같이 죽는다.**

> N대면 각 노드는 (N−1)/N 이하로.

### 16. 폴백이 없어 부분 장애가 전면 장애로

추천 API가 죽었다고 상품 상세 페이지 전체가 500을 반환하는 구조.

> 기능 등급을 미리 나눠 둔다.

## 상태 관리 안티패턴

### 17. 인메모리 스케줄러 + 다중 인스턴스

N대면 **N번 실행된다.** 정산 배치가 3번 돌아 3배 지급되는 식의 사고.

```text
[인메모리 스케줄러 + 3대]            [DB 락 / 리더 선출]
자정 정산 배치                       자정 정산 배치
   ↓                                   ↓
3대가 각자 실행 → 3배 지급 사고        락 잡은 1대만 실행, 나머지 스킵
```

### 18. `synchronized` / 로컬 락으로 동시성 제어

인스턴스가 2대가 되는 순간 **무효**가 된다.\
그런데 단일 인스턴스에서는 잘 동작해서 발견이 늦다.

### 19. 스티키 세션 의존

- 서버 죽으면 그 세션 전부 유실
- 배포할 때마다 문제
- 부하 불균형
- 오토스케일과 상성 최악

### 20. Redis를 진실의 원천(source of truth)으로

- 기본 구성에서 **유실이 정상 동작**이다 (비동기 복제, 주기적 영속화)
- 비즈니스 DB와 **원자성이 성립하지 않는다** (아웃박스를 Redis에 두면 안 되는 이유)
- 캐시·세션·큐로는 좋지만, **잃으면 안 되는 데이터의 유일한 저장소로는 부적합**

> **진실의 원천(source of truth)** — 어떤 데이터의 최종적으로 옳은 값이 사는 유일한 곳.\
> 예: Redis는 기본 구성에서 유실이 정상 동작이라, 잔액처럼 잃으면 안 되는 데이터의 유일한 저장소로 쓰면 안 된다.

### 21. 분산 락을 정확성 보장 수단으로

- TTL 만료, GC 일시정지, 네트워크 지연으로 **두 프로세스가 동시에 락을 가졌다고 믿을 수 있다**
- **분산 락은 최적화(중복 작업 감소) 수단이지 정확성 보장이 아니다**
- 정확성이 필요하면 **DB 제약이나 조건부 업데이트**로

## 운영 안티패턴

### 22. 복원을 테스트하지 않은 백업

**복원해본 적 없는 백업은 백업이 아니다.** 정작 필요할 때 안 되는 경우가 흔하다.

### 23. 복제를 백업으로 착각

`DELETE` 사고는 **모든 복제본에 즉시 전파된다.** 복제는 하드웨어 장애용, 백업은 논리 사고용.

### 24. 실행해본 적 없는 failover

자동 failover를 구성만 하고 한 번도 실행 안 해봤다면, 실제 장애 때 동작하지 않을 확률이 높다.

### 25. 롤백 불가능한 마이그레이션

컬럼을 바로 rename/drop → 구버전 코드가 깨짐 → **배포를 롤백할 수 없다.**

> Expand-Contract로 각 단계가 독립 롤백 가능하게. (→ [`08-deployment-ops.md`](./08-deployment-ops.md))

### 26. Graceful shutdown에 LB 전파 대기가 없음

readiness를 false로 바꾸자마자 프로세스 종료 → LB는 아직 모름 → **502 발생.** "무중단 배포"가 아니게 된다.

### 27. 원인에 거는 알림 / 알림 과다

- "CPU 80%"는 사용자에게 영향이 없을 수도 있다 → **증상(에러율, p99)에 건다**
- 대응할 게 없는 알림은 알림 피로를 만들고, **진짜 알림을 놓치게 한다**

### 28. 완화보다 진단을 먼저

장애 중에 원인을 찾으려다 시간을 다 쓴다.

> **먼저 지혈(롤백·플래그 off·트래픽 차단), 진단은 그 뒤.**

### 29. 비난하는 사후 분석

사람을 탓하면 다음부터 숨기고 보고가 늦어진다. **시스템을 고쳐야 재발이 막힌다.**

## 핵심 문장

- **안티패턴 대부분은 좋은 의도로 도입됐다가 문제를 키운 것 — 이점은 없이 비용만 내는 조합이 최악.**
- **타임아웃 없음이 단일 최다 원인 — 외부가 죽지 않고 느려지기만 해도 전체가 죽는다.**
- **무한 큐는 지표가 초록인 채로 죽는다 — 유한 큐는 느려짐이 보인다.**
- **분산 락은 최적화 수단이지 정확성 보장이 아니다 — 정확성은 DB 제약·조건부 업데이트로.**
- **복제는 백업이 아니고, 테스트 안 한 백업·failover는 없는 것과 같다.**

## 용어 풀이

- **분산 모놀리스(Distributed Monolith)** — 나뉘었지만 함께 배포해야 하는, 결합이 그대로인 서비스.
- **공유 데이터베이스** — 여러 서비스가 같은 테이블을 직접 읽고 쓰는 것. 결합 그대로.
- **동기 호출 체인** — 요청 하나가 여러 서비스를 순차로 거치는 것. 가용성 곱셈 하락.
- **유령 작업** — 바깥이 이미 끊겼는데 안쪽이 계속 하는, 아무도 안 받는 작업.
- **진실의 원천(Source of Truth)** — 데이터의 최종적으로 옳은 값이 사는 유일한 곳.
- **Expand-Contract** — 각 단계가 독립 롤백 가능한 스키마 변경 방식.
