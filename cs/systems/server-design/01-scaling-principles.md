## 1. 확장은 병목을 없애는 게 아니라 옮기는 것이다

**언제 쓰나** — "서버를 늘렸는데 왜 안 빨라지지?"를 만나기 전에 먼저 가져야 할 관점이다.

병목은 없어지지 않고 다음 자리로 넘어간다.

```text
앱 서버 증설      →  병목이 DB 커넥션으로 이동
        ↓
커넥션 풀 확대    →  병목이 DB CPU로 이동
        ↓
읽기 복제본 추가  →  병목이 쓰기(마스터)로 이동
        ↓
샤딩             →  병목이 크로스 샤드 쿼리로 이동
```

> **병목(bottleneck)** — 전체 처리량을 결정짓는 가장 좁은 구간. 여길 넓히면 병목은 다음으로 옮겨간다.\
> 예: 4차선 도로가 요금소에서 1차선으로 줄면, 차선을 아무리 늘려도 요금소가 전체 속도를 정한다.

**따라서 확장성 이해의 척도는 "지금 병목이 어디인지 말할 수 있는가"다.**\
병목이 어딘지 모른 채 서버를 늘리면, 돈만 쓰고 아무것도 안 빨라진다.

### 병목 후보를 훑는 순서

1. **포화된 자원**: CPU / 메모리 / 디스크 IOPS / 네트워크 대역폭
2. **한정된 슬롯**: 스레드 풀, 커넥션 풀, 파일 디스크립터, 포트
3. **직렬 구간**: 락, 단일 리더, 단일 파티션, 전역 카운터
4. **외부 의존**: 서드파티 API의 레이트 리밋

> 병목이 3번(직렬 구간)이면 **장비를 아무리 늘려도 소용없다.**\
> 1·2번은 돈으로 해결되지만 3번은 설계로만 해결된다.

**비용** — 1·2번(자원·슬롯)은 수평 확장으로 O(비용) 선형 개선, 3번(직렬 구간)은 장비를 늘려도 개선 0. 그래서 병목 유형 판별이 먼저다.

## 2. Little's Law — 용량 산정의 기본 공식

```text
L (동시 처리 건수) = λ (도착률, RPS) × W (평균 처리 시간)
```

> **Little's Law** — 대기행렬 이론의 항등식. "동시에 처리 중인 건수 = 도착률 × 평균 체류 시간".\
> 예: 식당에 손님이 초당 2명 들어오고 한 명이 평균 30분 머물면, 항상 60명이 앉아 있다(2 × 30).

### 왜 중요한가

**스레드 풀·커넥션 풀 크기를 감으로 정하지 않게 해준다.**

예시: 목표 1,000 RPS, 평균 응답 200ms

```text
L = 1000 × 0.2 = 200
     ↓
동시에 200건이 처리 중이어야 함
     ↓
워커 스레드가 200개 필요 (또는 비동기로 200건 동시 진행)
```

응답 시간을 100ms로 줄이면 필요 스레드는 100개로 준다.\
**성능 개선은 그대로 용량 확보가 된다.**

### 역방향 활용 — 이게 더 자주 쓴다

큐 대기가 쌓이면: `대기 시간 = 큐 길이 / 처리율`

- 큐에 10,000건, 처리율 100/s → 지금 넣은 건 100초 뒤에 처리됨
- **큐 길이만 보지 말고 "지금 넣으면 언제 나오나"를 지표로 만든다**

**비용** — 공식 자체는 공짜. 얻는 것은 "감으로 넣던 풀 크기"를 근거 있는 숫자로 바꾸는 것.

## 3. Universal Scalability Law — 노드를 늘려도 안 빨라지는 이유

이상적으로는 서버 2배 → 처리량 2배여야 하지만 실제로는:

```text
            N
C(N) = ─────────────────────────
       1 + α(N−1) + βN(N−1)
```

- **α (경합, contention)**: 직렬 구간. 락, 단일 DB — 증가분을 깎는다
- **β (일관성 비용, coherence)**: 노드끼리 상태를 맞추는 비용 — **노드 수의 제곱으로 는다**

> **USL(Universal Scalability Law)** — 노드를 늘릴 때 실제 처리량이 어떻게 되는지 설명하는 모델.\
> 예: 회의 참석자가 늘면(N↑) 서로 말 맞추는 시간(β)이 제곱으로 늘어, 어느 순간 사람이 많을수록 결정이 느려진다.

### 실무적 결론

| | 증상 | 원인 | 처방 |
|---|---|---|---|
| α만 있음 | 늘려도 점점 덜 빨라짐 (수렴) | 직렬 구간 | 락 범위 축소, 샤딩 |
| β가 있음 | **늘리면 오히려 느려짐** | 노드 간 조율 | 조율 자체를 줄임 (파티셔닝, 비동기, 최종적 일관성) |

> **"서버를 늘렸는데 더 느려졌다"는 β 때문이다.**\
> 분산 락, 분산 트랜잭션, 전체 노드 브로드캐스트, 캐시 동기화가 대표적.\
> 그래서 **조율이 필요 없게 데이터를 나누는 것(파티셔닝)이 확장의 본질**이다.

## 4. 상태가 확장을 막는다

### 무상태화 체크리스트

아래가 하나라도 있으면 수평 확장이 막히거나 버그가 난다.

| 상태 | 증상 | 해법 |
|---|---|---|
| **세션을 서버 메모리에** | 다른 서버로 가면 로그아웃 | 외부 세션 저장소 / 토큰 |
| **로컬 파일 업로드** | 다른 서버에서 파일 못 찾음 | 오브젝트 스토리지 |
| **인메모리 캐시** | 인스턴스마다 값이 다름 | 분산 캐시, 또는 짧은 TTL 감수 |
| **인메모리 스케줄러** | **N대면 N번 실행** | 분산 스케줄러, 리더 선출, DB 락 |
| **`synchronized` / 로컬 락** | 인스턴스 간에는 무효 | DB 락, 또는 파티셔닝으로 직렬화 |
| **인메모리 카운터/집계** | 합계가 틀림 | 중앙 집계, 또는 주기적 병합 |
| **로컬 임시 파일 기반 작업** | 재시도가 다른 서버로 가면 실패 | 공유 스토리지 |

> **무상태(stateless)** — 요청 처리에 필요한 상태를 서버 인스턴스 안에 두지 않는 것.\
> 예: 로그인 정보를 서버 메모리가 아니라 외부 Redis/토큰에 두면, 어느 서버가 요청을 받아도 똑같이 처리한다.

### 상태를 "없애는" 게 아니라 "밀어내는" 것

상태는 사라지지 않는다. **앱 계층에서 빼서 전용 저장소로 옮기는 것**이다.\
그래서 앱은 쉽게 늘어나고, 어려운 문제(상태 관리)는 그걸 잘하는 시스템(DB, Redis)에 몰아넣는다.

**→ 그래서 확장의 최종 난이도는 항상 데이터 계층에 있다.** (→ [`03-data-layer.md`](./03-data-layer.md))

### 계층별 확장 난이도

```text
쉬움  앱 서버 (무상태면 그냥 늘림)
  │   캐시 (샤딩 가능, 유실 허용)
  │   DB 읽기 (복제본 추가, 지연 감수)
어려움 DB 쓰기 (샤딩 — 되돌리기 어려움)
```

## 5. 확장하기 전에 먼저 할 것

**"서버를 늘리자"는 대개 세 번째 선택지다.**

### ① 측정

어디가 느린지 모르고 늘리면 병목이 아닌 곳을 늘린다. APM, 프로파일링, DB 실행 계획.

### ② 낭비 제거 (가장 저렴)

| 낭비 | 효과 |
|---|---|
| N+1 쿼리 제거 | 쿼리 수 100분의 1 |
| 인덱스 추가 | 응답 시간 자릿수 개선 |
| 불필요한 데이터 전송 제거 | 네트워크·직렬화 비용 |
| 중복 호출 제거 | 그대로 처리량 |

**낭비 제거는 성능과 확장성을 동시에 개선하면서 복잡도를 늘리지 않는다.** 유일하게 공짜에 가까운 수단.

### ③ 수직 확장

장비 하나로 버틸 수 있으면 그게 훨씬 싸고 단순하다. **수평 확장은 못 버틸 때 지불하는 복잡도**다.

- 현대 서버 1대의 성능은 직관보다 훨씬 높다 (수십 코어, 수백 GB RAM, NVMe)
- 많은 서비스가 "제대로 튜닝한 DB 한 대"로 충분하다

> **수직 확장 vs 수평 확장** — 수직은 장비 하나를 키우는 것(scale-up), 수평은 장비 수를 늘리는 것(scale-out).\
> 예: 트럭 한 대를 더 큰 트럭으로 바꾸면 수직, 트럭을 여러 대로 늘리면 수평(대신 물류 조율이 새 문제).

## 6. 확장성을 말하는 방식

**나쁜 답변**
> "트래픽이 늘어도 괜찮게 설계했습니다."

**좋은 답변의 형태**
> "현재 병목은 X입니다. 지금 구조로 Y까지 버팁니다. 그 이상은 Z를 해야 하고, 아직 안 한 이유는 (복잡도 대비 필요성 / 아직 그 규모가 아님)입니다."

**"안 한 이유를 말할 수 있는 것"이 핵심이다.**\
모든 확장 기법을 다 적용한 시스템은 오버엔지니어링이고, 그 자체가 유지보수 부채다.

## 핵심 문장

- **확장은 병목을 없애는 게 아니라 옮기는 것 — "지금 병목이 어디인가"를 말할 수 있어야 한다.**
- **Little's Law(L = λ × W)로 풀 크기를 감이 아니라 숫자로 정한다.**
- **USL의 β(조율 비용)는 노드 제곱으로 늘어, 늘릴수록 느려지게 만든다 — 조율을 없애는 게 파티셔닝.**
- **상태는 없애는 게 아니라 앱에서 전용 저장소로 밀어내는 것 — 그래서 최종 난이도는 데이터 계층.**
- **서버 증설은 세 번째 선택지 — 측정 → 낭비 제거 → 수직 확장 → 그다음 수평.**

## 용어 풀이

- **병목(Bottleneck)** — 전체 처리량을 결정하는 가장 좁은 구간. 넓히면 다음으로 옮겨간다.
- **Little's Law** — 동시 처리 건수 = 도착률 × 평균 처리 시간(L = λW).
- **USL(Universal Scalability Law)** — 노드 증가 시 실제 처리량 모델. α(경합)·β(일관성 비용)가 이득을 깎는다.
- **경합(Contention, α)** — 직렬 구간을 여럿이 기다리는 비용. 락·단일 리더가 대표.
- **일관성 비용(Coherence, β)** — 노드끼리 상태를 맞추는 비용. 노드 수의 제곱으로 증가.
- **무상태(Stateless)** — 요청 상태를 인스턴스 안에 두지 않는 것. 수평 확장의 전제.
- **수평 확장(Scale-out)** — 장비 수를 늘리는 것. 무상태면 쉽다.
- **수직 확장(Scale-up)** — 장비 하나를 키우는 것. 단순함이 가치.
- **N+1 쿼리** — 목록 1번 + 각 항목마다 1번씩, 총 N+1번 쿼리하는 낭비 패턴.
