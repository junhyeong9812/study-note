# 10. 상황별 플레이북 (증상 → 진단 → 처방)

> 이 문서가 실전용이다. **증상에서 출발해 원인 후보 → 확인 방법 → 처방** 순으로 찾아간다.\
> 개념 문서(01~09)는 "무엇이 있나"를 다루고, 이 문서는 "지금 무엇을 할까"를 다룬다.\
> 출처: `jun-bank/docs/study/notes/server-design/10-playbook-by-symptom.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(세로 도식)만 입힘. 각 항목은 "증상(실패) → 확인 → 처방(방어)"의 대비로 읽는다.

---

## 사용법

```text
1. 증상으로 항목을 찾는다
   ↓
2. "먼저 확인" 항목을 실제로 확인한다  ← 건너뛰지 않는다
   ↓
3. 원인이 확정된 뒤에 처방을 적용한다
```

**모든 항목의 공통 전제**: 추측으로 처방하면 병목이 아닌 곳을 고치게 된다.

## A. 성능 · 지연

### A-1. 평균은 괜찮은데 p99만 나쁘다

**가장 흔하고 가장 중요한 증상.**

| 원인 후보 | 확인 방법 |
|---|---|
| GC 일시 정지 | GC 로그, stop-the-world 시간 |
| 커넥션 풀 대기 | 풀 대기 시간 지표 |
| 락 경합 | DB 락 대기, 스레드 덤프 |
| 콜드 캐시 / 캐시 미스 경로 | 캐시 미스 시 응답 시간 별도 측정 |
| 특정 데이터의 편향 (거대 테넌트) | 요청별 처리량 분포 |
| 재시도 발생 | 재시도 횟수 지표 |
| 네트워크 재전송 | TCP 재전송률 |

**처방**
- 캐시 미스 경로 자체를 빠르게 만든다 (**캐시는 p99를 개선하지 않는다. 오히려 p99가 미스 경로가 된다**)
- 커넥션 풀 크기 재산정 (Little's Law)
- GC 튜닝 또는 힙 축소, 요청당 할당량 감소
- 헤지 요청(hedged request): p95를 넘으면 다른 인스턴스에 중복 요청

> **p99** — 응답 시간을 정렬했을 때 99번째 백분위. 100명 중 가장 느린 1명이 겪는 시간.\
> 예: 평균은 좋아도 p99가 나쁘면 100명 중 1명은 매번 크게 느린 것 — 사용자 체감은 여기서 갈린다.

---

### A-2. 서버를 늘렸는데 안 빨라진다 / 오히려 느려졌다

| 원인 후보 | 확인 방법 |
|---|---|
| **직렬 병목** (단일 DB, 단일 리더, 전역 락) | DB CPU·락 대기가 같이 오르는가 |
| **DB 커넥션 폭증** | 인스턴스 수 × 풀 크기 vs DB 최대 커넥션 |
| **조율 비용 (USL의 β)** | 분산 락, 캐시 동기화, 노드 간 통신량 |
| 부하가 균등하게 분배되지 않음 | 인스턴스별 요청 수 |

**처방**
- 병목이 DB면 **앱 증설을 멈추고** 캐시·읽기 복제본·쿼리 최적화로
- 커넥션 프록시(PgBouncer 등) 도입, 인스턴스당 풀 크기 축소
- 분산 락을 파티셔닝으로 대체 (조율 자체를 없앤다)
- → [`01-scaling-principles.md`](./01-scaling-principles.md)

---

### A-3. DB CPU가 100%다

| 원인 후보 | 확인 방법 |
|---|---|
| 인덱스 없는 쿼리 | 느린 쿼리 로그, `EXPLAIN` |
| N+1 쿼리 | 쿼리 수 / 요청 |
| 통계 정보 낡음 → 잘못된 실행 계획 | `ANALYZE` 후 비교 |
| 갑자기 늘어난 데이터로 계획 변경 | 어느 시점부터 느려졌나 |
| 배치가 동시에 도는 중 | 시간대 상관관계 |

**처방 (순서대로)**
1. 상위 느린 쿼리 5개만 고쳐도 대부분 해결된다 (`pg_stat_statements`)
2. 인덱스 추가 (선택도 높은 컬럼 선두, 커버링 인덱스)
3. 읽기를 복제본으로
4. 캐시
5. 그래도 안 되면 수직 확장 → 샤딩

---

### A-4. 특정 시간대에만 느리다

| 시간대 | 흔한 원인 |
|---|---|
| 매시 정각 / 새벽 | **배치·스케줄러** |
| 특정 요일·시간 | 사용자 트래픽 피크 |
| 주기적 스파이크 | 캐시 동시 만료 (TTL 정렬) |
| 배포 직후 | 콜드 스타트, 캐시 비어 있음 |

**처방**
- 배치를 복제본으로, 청크 분할, 실행 시간 분산
- **TTL 지터** 적용 (→ [`04-caching.md`](./04-caching.md))
- 워밍업 + LB 슬로우 스타트

---

### A-5. 캐시를 넣었는데 더 느려졌다

| 원인 |
|---|
| 히트율이 낮다 (캐시 조회 비용만 추가) |
| 캐시 값이 너무 커서 직렬화·네트워크 비용이 큼 |
| 캐시 서버가 원격이라 왕복 지연이 원본 쿼리보다 큼 |
| 무효화가 잦아 항상 미스 |

**처방**: 히트율부터 측정. 80% 미만이면 캐시 키 설계나 대상 선정이 잘못된 것.\
**캐시를 걷어내고 쿼리를 고치는 게 맞을 수 있다.**

## B. 자원 고갈

### B-1. 커넥션 풀 고갈 (`Connection is not available`)

| 원인 후보 | 확인 |
|---|---|
| **트랜잭션 안에서 외부 API 호출** | 코드 검토. 가장 흔한 원인 |
| 트랜잭션 범위가 너무 넓음 | 트랜잭션 지속 시간 지표 |
| 커넥션 누수 (close 안 함) | 사용 중 커넥션이 계속 증가 |
| 풀 크기가 너무 작음 | Little's Law로 재계산 |
| DB가 느려져서 반납이 늦음 | DB 응답 시간과 상관관계 |

**처방**
- **트랜잭션에서 외부 호출을 빼낸다** (이것만으로 대부분 해결)
- 트랜잭션 범위 최소화 (조회는 밖에서)
- 풀 크기는 **무작정 늘리지 않는다.** DB 쪽 한계와 곱셈 관계
- 커넥션 획득 타임아웃을 짧게 → 빠른 실패

---

### B-2. 메모리가 계속 증가한다 (OOM)

| 원인 후보 | 확인 |
|---|---|
| 무한 캐시 (TTL/크기 제한 없음) | 캐시 엔트리 수 |
| 무한 큐 | 큐 길이 |
| 컬렉션 누수 (static 맵 등) | 힙 덤프 |
| 대용량 응답을 메모리에 통째로 | 요청별 할당량 |
| 스레드 누수 | 스레드 수 추이 |

**처방**: 힙 덤프 분석이 가장 빠르다. 구조적으로는 **모든 캐시와 큐에 상한을 두는 것**.

---

### B-3. 스레드 풀 고갈 / 요청이 쌓인다

| 원인 | 확인 |
|---|---|
| 외부 호출에 타임아웃 없음 | 스레드 덤프에서 대기 지점 |
| 느린 의존성이 스레드를 점유 | 의존성별 응답 시간 |
| 블로킹 I/O를 이벤트 루프에서 실행 | (비동기 프레임워크) |

**처방**: 타임아웃 → 서킷 브레이커 → 벌크헤드 순으로. → [`06-resilience.md`](./06-resilience.md)

## C. 부하 분배

### C-1. 특정 인스턴스에만 부하가 쏠린다

| 원인 후보 | 확인 |
|---|---|
| **HTTP/2 / Keep-Alive 커넥션 고정** | LB 설정, 인스턴스별 커넥션 수 |
| 스티키 세션 | LB 설정 |
| Least-Connections + 재시작 직후 | 방금 뜬 인스턴스에 쏠림 |

**처방**: LB 요청 단위 분배 설정, **슬로우 스타트(ramp-up)**, 커넥션 최대 수명 설정

### C-2. 특정 샤드/파티션만 뜨겁다 (핫스팟)

| 원인 |
|---|
| 샤드 키 편향 (거대 테넌트, 최신 시간 편중) |
| 파티션 키 카디널리티 부족 |
| 인기 항목 집중 (핫키) |

**처방**
- 복합 샤드 키 (`tenant_id + 하위 키`)
- 거대 테넌트 전용 샤드 분리
- 핫키는 로컬 캐시 또는 키 분산(`key:1..N`)
- → [`03-data-layer.md`](./03-data-layer.md), [`04-caching.md`](./04-caching.md)

## D. 장애 · 가용성

### D-1. 외부 API 하나가 죽었는데 서비스 전체가 마비됐다

**전형적인 연쇄 실패.** 실패 경로와 방어를 대비하면:

```text
[방어 없음 — 실제로 벌어진 일]         [방어 있음]
외부 API가 느려짐 (타임아웃 없음)       외부 API가 느려짐
   ↓                                     ↓
공유 스레드풀이 대기로 점유             타임아웃으로 빠르게 실패
   ↓                                     ↓
풀 고갈 → 무관한 요청도 처리 불가        전용 풀(벌크헤드)만 영향
   ↓                                     ↓
서비스 전체 마비                        서킷 열림 + 폴백으로 그 기능만 숨김
```

| 확인 | |
|---|---|
| 해당 호출에 타임아웃이 있었나 | 대개 없다 |
| 스레드 풀이 공유였나 | 대개 그렇다 |
| 서킷 브레이커가 있었나 | 대개 없다 |

**처방 (순서대로)**
1. **타임아웃** 설정 — 가장 먼저
2. **벌크헤드** — 해당 의존성 전용 풀
3. **서킷 브레이커** — 반복 실패 시 즉시 실패
4. **폴백** — 없으면 그 기능만 숨김
- → [`06-resilience.md`](./06-resilience.md)

---

### D-2. 복구했는데 곧바로 다시 죽는다

| 원인 |
|---|
| **재시도 폭풍** — 대기하던 클라이언트가 동시에 몰림 |
| 캐시가 비어 있어 전체 부하가 DB로 |
| 큐에 쌓인 백로그를 한꺼번에 처리 |

**처방**
- **점진적 트래픽 복귀** (LB 슬로우 스타트, 가중치 단계적 상향)
- 클라이언트 재시도에 **지터** 강제
- **캐시 워밍업 후** 트래픽 투입
- 백로그는 **레이트 리밋을 걸고** 소화

---

### D-3. 트래픽 스파이크(이벤트/푸시)에 무너진다

**예측 가능한 스파이크는 설계로 대응한다.**

| 수단 | 설명 |
|---|---|
| **사전 스케일링** | 오토스케일은 반응이 늦다. 이벤트 전에 미리 늘린다 |
| **캐시 사전 워밍** | 이벤트 대상 데이터를 미리 캐시에 |
| **대기열(가상 대기실)** | 유입 자체를 제어 — 티켓팅의 표준 |
| **비동기 전환** | 즉시 처리 대신 큐에 넣고 "접수됨" 응답 |
| **레이트 리밋 + 로드 셰딩** | 일부를 빠르게 거절해 나머지를 살림 |
| **푸시 발송 분산** | 한 번에 전체 발송 금지. 배치로 나눠서 |

> **푸시 알림을 전체 사용자에게 동시 발송하면 스스로에게 DDoS를 한다.**\
> 발송 자체를 분산하는 게 가장 저렴한 해법.

---

### D-4. DB failover 후 앱이 복구되지 않는다

| 원인 |
|---|
| 커넥션 풀이 죽은 커넥션을 계속 들고 있음 |
| DNS 캐시가 옛 엔드포인트를 가리킴 |
| 앱에 재연결 로직이 없음 |

**처방**: 커넥션 유효성 검사(validation query), 커넥션 최대 수명, DNS TTL 조정, JVM DNS 캐시(`networkaddress.cache.ttl`) 설정

---

### D-5. 배포 직후 에러가 급증한다

| 원인 후보 | 확인 |
|---|---|
| graceful shutdown 미비 (502) | 종료 시점의 에러 로그 |
| **신·구 버전 호환성 문제** | 공존 시간에만 발생하는가 |
| DB 마이그레이션 비호환 | 구버전 코드가 새 스키마에서 동작하나 |
| 캐시 포맷 변경 | 역직렬화 오류 |
| 콜드 스타트 | 시간이 지나면 회복되는가 |

**처방**: 즉시 롤백 → 원인 분석. 구조적으로는 Expand-Contract, 카나리 배포, 워밍업. → [`08-deployment-ops.md`](./08-deployment-ops.md)

## E. 데이터 정합성

### E-1. 방금 쓴 데이터가 조회에서 안 보인다

| 원인 |
|---|
| **복제 지연** (읽기가 복제본으로 감) |
| 캐시에 옛 값 |
| 읽기 모델(CQRS) 반영 지연 |

**처방**: 쓰기 직후 일정 시간 Primary 읽기 / 본인 데이터는 Primary / 쓰기 시 캐시 삭제. → [`03-data-layer.md`](./03-data-layer.md)

---

### E-2. 중복 처리가 발생한다 (결제 2번, 알림 2번)

| 원인 |
|---|
| 클라이언트 재시도 (더블 클릭 포함) |
| 메시지 at-least-once 재전달 |
| 오프셋 커밋 전 크래시 |

**처방**: **멱등성 키** (요청 단위) + **인박스 테이블** (메시지 단위) + **DB 유니크 제약** (최종 방어선).\
(메시지 컨슈머 실패·오프셋 커밋 처리는 별도 주제 — 이 컬렉션 밖)

---

### E-3. 재고가 음수가 된다 / 카운터가 안 맞는다

**전형적인 lost update.**

> **lost update** — 두 트랜잭션이 같은 값을 읽고 각자 갱신해, 한쪽 갱신이 덮여 사라지는 것.\
> 예: 재고 1을 둘이 동시에 읽고 각자 −1 하면, 실제로는 2가 빠져야 하는데 하나만 반영돼 재고가 음수가 된다.

**처방**
- 조건부 업데이트: `UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty >= 1` → 영향 행 수 0이면 실패 처리
- 또는 비관적 락 / 낙관적 락(version)
- **DB 제약**: `CHECK (qty >= 0)` — 최후의 방어선
- 극단적 고빈도면 재고를 N개 버킷으로 나눠 경합 분산

---

### E-4. 검색·통계가 실제 데이터와 다르다

| 원인 |
|---|
| 이중 쓰기 실패 (DB는 성공, 색인 실패) |
| 이벤트 유실 |
| 재색인 중 누락 |

**처방**: 아웃박스/CDC로 전환 + **정기 대조 배치**. (이중 쓰기 문제·아웃박스 패턴은 별도 주제 — 이 컬렉션 밖)

## F. 비동기 · 큐

### F-1. 큐가 계속 쌓인다

| 확인 | |
|---|---|
| 유입률 vs 처리율 | 유입 > 처리면 구조적 문제 |
| 컨슈머 수 vs 파티션 수 | 컨슈머가 파티션보다 많으면 놀고 있음 |
| 처리 중 예외로 무한 재시도 | poison pill |
| 특정 파티션만 밀림 | 키 편향 |

**처방**
- 컨슈머 증설 (**파티션 수가 상한**)
- 파티션 증설 (순서 영향 확인 필요)
- 처리 로직 최적화 / 배치 처리
- 영구 실패를 DLQ로 격리
- **유입 자체를 줄인다** (백프레셔)

---

### F-2. 메시지 순서가 뒤바뀐다

| 원인 |
|---|
| 파티션 키가 없거나 잘못됨 |
| 재시도 토픽 사용 (**순서를 깨뜨린다**) |
| 컨슈머 내부 병렬 처리 |
| 파티션 수 변경 |

**처방**: 파티션 키 재설계 / **순서 의존성 자체를 없애기** (버전 필드로 낡은 이벤트 무시). → [`07-async-messaging.md`](./07-async-messaging.md)

---

### F-3. 스케줄 작업이 여러 번 실행된다

**원인**: 인메모리 스케줄러 + 다중 인스턴스.\
**처방**: ShedLock 등 DB 락 / 리더 선출 / 스케줄러는 메시지만 발행하고 처리는 컨슈머가. → [`07-async-messaging.md`](./07-async-messaging.md)

## G. 진단 순서 (증상이 애매할 때)

```text
1. 언제부터?          → 배포·설정 변경·트래픽 변화와의 상관관계
   ↓
2. 어디까지 번졌나?    → 특정 엔드포인트 / 특정 인스턴스 / 전체
   ↓
3. 어느 계층?         → 클라이언트 / LB / 앱 / 캐시 / DB / 외부
   ↓
4. 포화된 자원은?      → CPU / 메모리 / IO / 커넥션 / 스레드
   ↓
5. 지연인가 에러인가?  → 느린 것과 실패하는 것은 원인이 다르다
```

**가장 강력한 단서는 항상 "언제부터"다.** 대부분의 장애는 변경에서 시작된다.

---

## H. 즉시 적용 우선순위 (아무것도 없는 시스템이라면)

효과 대비 비용 순서:

1. **모든 외부 호출에 타임아웃** — 하루면 적용, 효과 최대
2. **느린 쿼리 상위 5개 수정** — 대부분의 성능 문제 해결
3. **골든 시그널 대시보드 + 알림** — 못 보면 못 고친다
4. **graceful shutdown** — 배포 중 502 제거
5. **모든 캐시·큐에 상한과 TTL** — OOM 방지
6. **핵심 의존성에 서킷 브레이커 + 폴백**
7. **롤백 절차 검증 / 피처 플래그**
8. 그 다음에 복제·샤딩·다중 AZ 같은 큰 구조 변경

---

## 핵심 문장

- **추측으로 처방하면 병목이 아닌 곳을 고친다 — "먼저 확인"을 건너뛰지 않는다.**
- **가장 강력한 단서는 항상 "언제부터" — 대부분의 장애는 변경에서 시작된다.**
- **캐시는 p99를 개선하지 않는다 — 오히려 캐시 미스 경로가 p99가 된다.**
- **외부 API 하나로 전체가 마비되면 타임아웃 → 벌크헤드 → 서킷 → 폴백 순.**
- **아무것도 없는 시스템의 1순위는 "모든 외부 호출에 타임아웃" — 하루면 적용, 효과 최대.**

---

## 용어 풀이

- **p99** — 응답 시간의 99번째 백분위. 가장 느린 1%가 겪는 시간.
- **헤지 요청(Hedged Request)** — 느려지면 다른 인스턴스에도 중복 요청해 먼저 오는 걸 쓰는 것.
- **커넥션 풀 고갈** — 사용 가능한 DB 커넥션이 없어 요청이 대기·실패하는 것.
- **lost update** — 동시 갱신에서 한쪽 변경이 덮여 사라지는 것.
- **조건부 업데이트** — `WHERE`로 전제를 걸어 갱신하고 영향 행 수로 성공을 판정하는 것.
- **poison pill** — 처리 때마다 실패해 뒤를 막는 메시지.
- **백로그(Backlog)** — 처리 못 하고 쌓인 미처리분.
