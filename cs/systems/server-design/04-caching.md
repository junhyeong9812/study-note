# 04. 캐시 설계

> 캐시는 가장 효과가 큰 최적화이자, **가장 많은 새 버그를 만드는 수단**이다.\
> "캐시를 어떻게 넣을까"보다 **"언제 무효화할까"**가 설계의 90%다.\
> 출처: `jun-bank/docs/study/notes/server-design/04-caching.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(용어 풀이·세로 도식·실패→방어 대비)만 입힘.

---

## 1. 캐시 계층 — 뒤로 갈수록 비싸다

```text
브라우저 캐시      ← 네트워크 자체가 없음. 가장 저렴
CDN / 엣지         ← 오리진에 안 옴
게이트웨이 캐시     ← 앱에 안 옴
앱 로컬 캐시       ← 네트워크 홉 없음, 대신 인스턴스마다 다름
분산 캐시 (Redis)  ← 일관됨, 대신 네트워크 홉
DB 버퍼 풀         ← 마지막
```

**설계 원칙: 가능한 한 앞 계층에서 끝낸다.**

### 로컬 캐시 vs 분산 캐시

| | 로컬 (Caffeine 등) | 분산 (Redis) |
|---|---|---|
| 속도 | 마이크로초 | 밀리초 |
| 일관성 | **인스턴스마다 다름** | 일관됨 |
| 무효화 | 어려움 (전파 필요) | 쉬움 |
| 적합 | 변경이 드문 참조 데이터, 짧은 TTL | 공유 상태, 세션 |

**다층 캐시(L1 로컬 + L2 Redis)**: Redis 부하와 네트워크 왕복을 줄인다.\
대신 로컬 계층의 무효화 전파(pub/sub)가 필요하고, 짧은 TTL로 타협하는 경우가 많다.

---

## 2. 캐시 패턴

| 패턴 | 흐름 | 특징 |
|---|---|---|
| **Cache-Aside** (Look-aside) | 앱이 캐시 확인 → 없으면 DB → 캐시에 저장 | **가장 널리 쓰임.** 캐시가 죽어도 서비스는 동작 |
| **Read-Through** | 캐시 계층이 알아서 DB 조회 | 앱 코드 단순, 캐시 라이브러리 의존 |
| **Write-Through** | 쓰기를 캐시와 DB에 동시에 | 캐시가 항상 최신, 쓰기 지연 증가 |
| **Write-Behind** | 캐시에 쓰고 나중에 DB 반영 | 쓰기 빠름, **유실 위험** |
| **Refresh-Ahead** | 만료 전에 미리 갱신 | 지연 제거, 불필요한 갱신 가능 |

> **Cache-Aside** — 앱이 직접 캐시를 확인하고, 없으면 DB에서 읽어 캐시에 채우는 방식.\
> 예: 캐시가 통째로 죽어도 앱은 DB로 폴백해 계속 동작한다(그래서 가장 널리 쓰인다).

```java
// Cache-Aside
public User get(Long id) {
    User cached = cache.get(key(id));
    if (cached != null) return cached;
    User user = repo.findById(id);
    cache.set(key(id), user, TTL);
    return user;
}
```

## 3. 무효화 전략

| 전략 | 방식 | 적합 |
|---|---|---|
| **TTL 만료** | 시간 지나면 자동 삭제 | 낡음을 허용할 수 있을 때. **가장 단순하고 안전** |
| **쓰기 시 삭제** | 데이터 변경 시 캐시 키 삭제 | 정합성 중요. 삭제 누락이 버그 |
| **버전/세대 키** | 키에 버전 포함 (`user:v3:123`) | 대량 무효화가 O(1) — 버전만 올리면 됨 |
| **이벤트 기반** | 변경 이벤트 구독해서 무효화 | 다중 인스턴스·다중 서비스 |

> **무효화(invalidation)** — 원본이 바뀌었을 때 캐시의 낡은 값을 지우거나 만료시키는 것.\
> 예: 사용자가 프로필을 바꾸면 `user:123` 키를 삭제해, 다음 조회가 DB에서 최신을 가져오게 한다.

### 갱신 vs 삭제 — 삭제가 안전하다

캐시를 **갱신(update)** 하면 동시 갱신 시 순서가 뒤집혀 낡은 값이 남을 수 있다.\
**삭제(delete)** 하면 다음 조회가 DB에서 최신을 가져온다.

```java
// 권장: 캐시 삭제
@Transactional
public void update(User u) {
    repo.save(u);
    cache.delete(key(u.getId()));   // 갱신이 아니라 삭제
}
```

### 그래도 남는 경쟁 상태

```text
스레드A: DB 조회(옛 값) ─────────────────▶ 캐시에 옛 값 저장
스레드B:        DB 갱신 ─▶ 캐시 삭제
결과: 캐시에 옛 값이 TTL만큼 남음
```

**완전한 해결은 어렵다.** 실무 대응:

- **TTL을 반드시 함께 건다** (최악의 경우에도 TTL 후 자동 복구) ← 가장 중요
- 지연 이중 삭제: 갱신 후 짧은 지연 뒤 한 번 더 삭제
- 정합성이 정말 중요하면 **그 데이터는 캐시하지 않는다**

## 4. 3대 캐시 사고

세 사고 모두 **"캐시 미스가 한꺼번에 DB로 쏟아지는 것"**이 공통 원인이다. 실패→방어로 본다.

### ① 캐시 스탬피드 (Dogpile / Thundering Herd)

**증상**: 인기 키의 TTL이 만료되는 순간, **수천 요청이 동시에 DB로 몰려 DB가 죽는다.**

```text
[방어 없음]                          [싱글플라이트 + 지터]
인기 키 TTL 만료                      인기 키 TTL 만료 (지터로 시점 분산)
   ↓                                   ↓
수천 요청 동시 미스                    하나만 DB 조회, 나머지는 대기
   ↓                                   ↓
전부 DB로 몰림 → DB 다운               한 번 채우면 나머지는 캐시 히트
```

| 해법 | 방식 |
|---|---|
| **뮤텍스 / 싱글플라이트** | 하나만 DB 조회, 나머지는 대기 후 결과 공유 |
| **확률적 조기 갱신** | 만료 임박 시 확률적으로 미리 갱신 (동시 만료 분산) |
| **논블로킹 갱신** | 만료돼도 옛 값을 주고 백그라운드에서 갱신 (`stale-while-revalidate`와 같은 원리) |
| **TTL 지터** | TTL에 랜덤 ±10% → **동시 만료 자체를 막음** |

> **캐시 스탬피드(stampede)** — 인기 키가 만료되는 순간 몰린 요청이 동시에 DB를 때리는 것.\
> 예: TTL이 정확히 같은 인기 키 여럿이 한꺼번에 만료되면, 그 시점에 DB가 평소의 수천 배 부하를 받는다.

> **싱글플라이트(singleflight)** — 같은 키에 대한 동시 미스 중 하나만 실제로 DB를 조회하고 나머지는 그 결과를 공유하는 것.

```java
// 싱글플라이트 개념
if (cached == null) {
    if (lock.tryLock(key)) {
        try { value = loadFromDb(); cache.set(key, value, ttlWithJitter()); }
        finally { lock.unlock(key); }
    } else {
        return staleValue != null ? staleValue : waitAndGet(key);
    }
}
```

### ② 캐시 관통 (Penetration)

**증상**: 존재하지 않는 키를 계속 조회 → 캐시 미스 → 매번 DB 조회. **공격 벡터가 된다.**

- **널(빈 값) 캐싱**: 없다는 사실도 짧은 TTL로 캐시
- **블룸 필터**: 존재하지 않는 키를 캐시 앞에서 차단
- **입력 검증**: 형식에 안 맞는 ID는 DB까지 안 보냄

> **캐시 관통(penetration)** — 캐시에 없는(그리고 DB에도 없는) 키를 반복 조회해 매번 DB로 뚫고 들어가는 것.\
> 예: 없는 상품 ID를 초당 수천 번 조회하면 캐시가 무력화되어 DB가 직격당한다(공격에 악용됨).

### ③ 캐시 눈사태 (Avalanche)

**증상**: 대량의 키가 **동시에** 만료되거나 캐시 서버가 통째로 죽어, DB가 한꺼번에 전체 부하를 받는다.

- **TTL 지터** (①과 동일 — 가장 효과적)
- **캐시 이중화** / 다층 캐시
- **캐시 미스 시 서킷 브레이커·레이트 리밋으로 DB 보호** ← 캐시가 죽어도 DB는 살아야 한다
- 재기동 시 **캐시 워밍업**

> **핵심 원칙: 캐시가 완전히 죽었을 때 시스템이 견디는가?**\
> 캐시 히트율 90%에 의존하는 시스템은, 캐시가 죽으면 DB 부하가 10배가 된다. 이 시나리오를 테스트해봐야 한다.

> **TTL 지터(jitter)** — TTL에 랜덤 편차(±10% 등)를 더해 만료 시점을 흩뿌리는 것. 동시 만료를 막는 가장 싼 방어.

## 5. 핫키 문제

특정 키 하나에 트래픽이 몰려 **Redis 단일 노드/슬롯이 포화**된다. (인기 상품, 이벤트 페이지)

| 해법 | 방식 |
|---|---|
| **로컬 캐시 병행** | 핫키만 앱 로컬에 짧은 TTL로 |
| **키 분산** | `key:1` ~ `key:N`으로 복제 후 랜덤 조회 |
| **읽기 복제본** | Redis 레플리카로 읽기 분산 |
| **핫키 탐지** | `redis-cli --hotkeys`, 클라이언트 측 통계 |

> **핫키(hot key)** — 트래픽이 한 키에 몰려 그 키를 담은 단일 노드/슬롯이 포화되는 것.\
> 예: 이벤트 상품 하나의 조회가 한 Redis 슬롯에 몰리면, 클러스터 전체는 한가한데 그 노드만 터진다.

## 6. 언제 캐시를 쓰면 안 되는가

- **히트율이 낮을 때** — 오버헤드만 늘고 메모리만 쓴다. 히트율 측정이 먼저
- **정합성이 절대적일 때** — 잔액, 재고 확정 수량
- **원본 쿼리를 안 고쳐놓고** — 캐시는 근본 문제를 덮는다. 캐시 미스 시 여전히 느리고, 그게 p99가 된다
- **쓰기가 읽기보다 많을 때** — 무효화만 계속 일어난다

> **먼저 쿼리를 고치고, 그래도 안 되면 캐시.**\
> 순서를 바꾸면 나중에 캐시를 걷어낼 수 없게 된다.

---

## 7. 운영 지표

| 지표 | 의미 |
|---|---|
| **히트율** | 낮으면 캐시가 무의미. 키 설계 재검토 |
| **eviction 수** | 메모리 부족으로 밀려남 → 히트율 저하 원인 |
| **평균/최대 키 크기** | 큰 값은 네트워크·직렬화 비용 |
| **캐시 응답 지연** | Redis가 느려지면 캐시가 병목이 됨 |
| **캐시 미스 시 원본 지연** | **캐시가 죽었을 때의 예상 부하** |

---

## 8. 체크리스트

- [ ] 모든 캐시 키에 TTL이 있는가 (무한 캐시 금지)
- [ ] TTL에 지터가 있는가
- [ ] 인기 키에 스탬피드 방어(싱글플라이트/stale 응답)가 있는가
- [ ] 존재하지 않는 키 조회가 DB까지 가는가
- [ ] **캐시가 전부 죽어도 DB가 버티는가** (레이트 리밋·서킷 브레이커)
- [ ] 캐시 갱신이 아니라 삭제를 쓰는가
- [ ] 히트율을 측정하고 있는가

---

## 핵심 문장

- **설계의 90%는 "언제 무효화할까" — 넣는 법이 아니다.**
- **무효화는 갱신이 아니라 삭제 — 다음 조회가 DB에서 최신을 가져오게 한다. 그리고 TTL을 반드시 함께.**
- **3대 사고(스탬피드·관통·눈사태)의 공통 원인은 캐시 미스가 한꺼번에 DB로 쏟아지는 것.**
- **TTL 지터가 동시 만료(스탬피드·눈사태)를 막는 가장 싼 방어.**
- **캐시가 완전히 죽어도 DB가 견디는지를 테스트해야 한다 — 히트율 90%면 죽는 순간 DB 부하 10배.**

---

## 용어 풀이

- **Cache-Aside** — 앱이 캐시 확인 → 없으면 DB → 캐시 채움. 캐시가 죽어도 동작.
- **무효화(Invalidation)** — 원본 변경 시 낡은 캐시 값을 지우거나 만료시키는 것.
- **TTL 지터(Jitter)** — TTL에 랜덤 편차를 더해 동시 만료를 막는 것.
- **캐시 스탬피드(Stampede)** — 인기 키 만료 순간 요청이 몰려 DB를 때리는 것.
- **싱글플라이트(Singleflight)** — 동시 미스 중 하나만 DB를 조회하고 결과를 공유.
- **캐시 관통(Penetration)** — 존재하지 않는 키 반복 조회로 캐시를 뚫는 것.
- **널 캐싱(Null Caching)** — "없음"이라는 사실도 짧은 TTL로 캐시하는 것.
- **캐시 눈사태(Avalanche)** — 대량 키 동시 만료·캐시 서버 다운으로 DB가 전체 부하를 받는 것.
- **핫키(Hot Key)** — 한 키에 트래픽이 몰려 단일 노드/슬롯이 포화되는 것.
- **eviction** — 메모리 부족으로 캐시 항목이 밀려나는 것.
- **히트율(Hit Ratio)** — 조회 중 캐시에서 해결된 비율. 낮으면 캐시가 무의미.
