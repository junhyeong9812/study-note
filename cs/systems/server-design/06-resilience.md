# 06. 장애 격리와 복원력

> 05번이 "구성 요소를 여러 개 두는 것"이라면, 이 문서는 **"한 곳의 장애가 전체로 번지지 않게 하는 것"**이다.\
> 실제 대형 장애의 대부분은 단일 컴포넌트 고장이 아니라 **전파**에서 나온다.\
> 출처: `jun-bank/docs/study/notes/server-design/06-resilience.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(용어 풀이·세로 도식·실패→방어 대비)만 입힘. 운영 패턴이라 각 장치를 "무엇이 실패하는가 → 어떻게 막는가"로 읽는다.

## 1. 연쇄 실패는 어떻게 일어나는가

### 메커니즘 ① 스레드 고갈

```text
외부 API가 느려짐 (타임아웃 없음)
   ↓
요청 스레드가 응답을 기다리며 점유됨
   ↓
스레드 풀 고갈
   ↓
그 API와 무관한 요청도 처리 불가
   ↓
전체 서비스 다운
```

**외부 의존성 하나가 느려진 것만으로 전체가 죽는다.** 죽지도 않고 그냥 느려진 것만으로.

### 메커니즘 ② 재시도 증폭

```text
DB가 느려짐 → 타임아웃 → 재시도
   ↓
부하 2배 → 더 느려짐 → 더 많은 재시도
   ↓
부하 4배 → ...
```

**재시도가 장애를 증폭시킨다.** 각 계층이 3회씩 재시도하면 3계층에서 27배가 된다.

### 메커니즘 ③ 복구 직후 재사망 (Thundering Herd)

```text
서비스 복구 → 대기하던 모든 클라이언트가 동시에 재시도
   ↓
순간 부하 폭증 → 다시 다운
```

### 메커니즘 ④ GC 죽음의 나선

```text
부하 증가 → 힙 압박 → GC 빈발 → 응답 지연
   ↓
요청 적체 → 메모리 더 사용 → GC 더 빈발 → ...
```

> **공통점: 부하가 스스로를 키우는 양의 되먹임 고리.** 복원력 설계는 전부 이 고리를 끊는 장치다.

> **연쇄 실패(cascading failure)** — 한 곳의 장애가 자원 고갈·재시도·부하 증폭을 통해 무관한 부분까지 번지는 것.\
> 예: 외부 API 하나가 느려져 스레드가 고갈되면, 그 API를 안 쓰는 요청까지 처리 못 해 전체가 죽는다.

## 2. 타임아웃 — 모든 것의 출발점

**타임아웃이 없으면 다른 모든 장치가 무의미하다.** 실패를 감지할 수 없으니까.

### 어디에 걸어야 하나 (전부 다)

- 연결(connect) 타임아웃 / 읽기(read) 타임아웃 — **둘은 다르다**
- HTTP 클라이언트, DB 쿼리, 커넥션 풀 대기, 락 획득, 캐시 조회, 메시지 처리

### 타임아웃 예산 (Timeout Budget)

```text
사용자 요청 SLA 3초
   ├─ 게이트웨이:     2.5초
   │   ├─ 서비스 A:   2.0초
   │   │   ├─ DB:     500ms
   │   │   └─ 외부:   1.0초
```

**안쪽 타임아웃이 바깥쪽보다 짧아야 한다.**\
반대면 바깥이 먼저 끊겨서, 안쪽 작업은 계속 자원을 쓰면서 결과는 아무도 안 받는다(유령 작업).

> **타임아웃 예산(timeout budget)** — 바깥 계층의 제한 시간을 안쪽 계층들이 나눠 갖도록 배분한 것. 안쪽이 항상 더 짧아야 한다.\
> 예: 사용자 SLA가 3초면 게이트웨이 2.5초, 그 안의 DB 호출 0.5초 식으로, 안에서 먼저 끊기게 짠다.

### 값을 정하는 방법

- **p99 응답 시간의 2~3배**로 시작. 감으로 "3초" 넣지 않는다
- 너무 짧으면 정상 요청을 죽이고, 너무 길면 자원을 점유한다
- **재시도를 고려한 총 지연**을 계산한다: 타임아웃 3초 × 재시도 3회 = **최악 9초** → SLA를 넘으면 설정이 잘못된 것

## 3. 재시도 — 위험한 도구

### 전제 조건 (이것 없이 재시도하면 안 됨)

1. **멱등성**: 두 번 실행돼도 안전한가? 결제·주문은 멱등성 키가 먼저
2. **재시도할 가치가 있는 실패인가**

| 실패 | 재시도 |
|---|---|
| 네트워크 오류, 타임아웃, 503, 429 | ✅ |
| 400, 401, 403, 422 (요청 자체가 잘못) | ❌ **재시도해도 똑같이 실패** |
| 500 | ⚠️ 상황에 따라 (서버 버그면 무의미) |

> **멱등성(idempotency)** — 같은 요청을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질.\
> 예: "이체 요청 ID X"를 멱등성 키로 쓰면, 재시도로 같은 요청이 두 번 와도 이체는 한 번만 일어난다.

### 지수 백오프 + 지터 (필수)

```java
delay = min(base * 2^attempt, maxDelay)
delay = random(0, delay)          // Full Jitter
```

**지터가 없으면** 모든 클라이언트가 정확히 같은 시점에 재시도해서 부하가 파도처럼 몰린다.

> **지수 백오프 + 지터** — 재시도 간격을 2배씩 늘리며(백오프), 거기에 랜덤(지터)을 더해 시점을 흩뿌리는 것.\
> 예: 1초·2초·4초 대신 0~1초·0~2초·0~4초의 랜덤을 쓰면, 모든 클라이언트가 같은 순간에 몰리지 않는다.

### 재시도 예산 (Retry Budget)

개별 요청의 재시도 횟수만 제한하면, **전체 재시도 총량은 제한되지 않는다.**

> 규칙: "전체 요청의 N%(예: 10%)를 넘는 재시도는 하지 않는다."\
> 장애 시 재시도가 자동으로 꺼져서 증폭을 막는다.

### 계층 중복 재시도 금지

게이트웨이·클라이언트·SDK가 각각 재시도하면 곱셈이 된다.

> **재시도는 한 계층에서만.** 보통 가장 바깥(클라이언트에 가까운 쪽) 또는 가장 안쪽 한 곳.

## 4. 서킷 브레이커

**죽은 의존성을 계속 때리는 것은 (1) 내 자원 낭비이고 (2) 상대의 복구를 방해한다.**

### 상태 전이

```text
      실패율 임계 초과
CLOSED ──────────────▶ OPEN
  ▲                     │
  │                일정 시간 경과
  │                     ▼
  │  시험 요청 성공   HALF_OPEN
  └─────────────────────┤
                        │ 시험 요청 실패
                        ▼
                      다시 OPEN
```

| 상태 | 동작 |
|---|---|
| **CLOSED** | 정상 통과, 실패율 집계 |
| **OPEN** | **즉시 실패 반환** (호출조차 안 함) → 빠른 실패, 자원 절약 |
| **HALF_OPEN** | 소수 요청만 통과시켜 회복 여부 확인 |

> **서킷 브레이커(circuit breaker)** — 실패율이 임계를 넘으면 회로를 "열어" 호출 자체를 막고 즉시 실패시키는 장치.\
> 예: 죽은 외부 API를 계속 때리는 대신, 열린 동안은 바로 실패를 돌려주어 내 자원을 아끼고 상대가 회복할 틈을 준다.

### 설정 포인트

- **최소 요청 수**: 요청 10건에 2건 실패로 열면 오탐. 통계적 유의성 확보
- **실패율 임계**: 보통 50% 전후
- **OPEN 유지 시간**: 상대의 복구 시간 고려
- **무엇을 실패로 셀 것인가**: 타임아웃과 5xx는 포함, **4xx는 제외** (내 요청이 잘못된 것)
- **의존성별로 분리**: 하나의 브레이커로 여러 의존성을 묶으면 안 됨

### 서킷 브레이커 ≠ 재시도

- 재시도: **일시적** 실패에 대응
- 서킷 브레이커: **지속적** 실패에 대응
- **둘은 함께 쓰되 순서가 있다**: 재시도가 서킷 브레이커 안쪽에 있으면 재시도 실패가 브레이커를 열게 된다(의도한 동작). 바깥쪽이면 열린 브레이커를 계속 때린다.

## 5. 벌크헤드 (격벽)

배의 격벽처럼, **한 구획이 침수돼도 다른 구획은 무사하게.**

```text
[공유 스레드풀 100]           [벌크헤드]
  주문 API  ─┐                  주문   ─▶ 풀 A (60)
  추천 API  ─┼─▶ 100개 공유      추천   ─▶ 풀 B (20)
  통계 API  ─┘                  통계   ─▶ 풀 C (20)

추천 API가 느려지면                 추천이 느려도
→ 100개 전부 점유                  → 풀 B(20)만 고갈
→ 주문도 죽음                      → 주문은 정상
```

> **벌크헤드(bulkhead)** — 자원(스레드·커넥션)을 기능별로 칸막이해, 한 기능이 자원을 다 써도 다른 기능은 무사하게 하는 것.\
> 예: 추천 API 전용 풀을 따로 두면, 추천이 느려져 그 풀이 고갈돼도 주문 API의 풀은 멀쩡하다.

### 적용 대상

- 스레드 풀 / 커넥션 풀 (외부 API별, DB별)
- 세마포어 기반 동시 호출 수 제한 (가벼움)
- 인스턴스 단위 격리 (중요 API 전용 서버군)
- **셀 단위 격리** (→ [`05-ha-topology.md`](./05-ha-topology.md)의 셀 기반 아키텍처)

> **핵심 질문: 부가 기능이 핵심 기능의 자원을 뺏을 수 있는가?**

## 6. 백프레셔와 로드 셰딩

### 백프레셔 — 받아들이는 속도를 제한

처리 능력을 넘는 요청을 **큐에 무한정 쌓는 것은 해결이 아니다.**

```text
큐에 쌓임 → 메모리 증가 → 대기 시간 증가
   ↓
클라이언트는 이미 타임아웃 → 처리해도 아무도 안 받음 (무의미한 작업)
```

| 수단 | 방식 |
|---|---|
| **유한 큐** | 큐가 차면 거부 (무한 큐 금지) |
| **동시 실행 수 제한** | 세마포어 |
| **흐름 제어** | 컨슈머가 요청한 만큼만 (Reactive Streams) |
| **어드미션 컨트롤** | 진입 시점에 판단 |

> **백프레셔(backpressure)** — 처리 능력을 넘는 유입을 받아들이지 않고 밀어내는 것. 큐가 무한히 쌓이는 걸 막는다.\
> 예: 큐 상한을 두고 넘치면 생산자에게 거부를 돌려주어, 메모리가 터지거나 무의미한 지연이 쌓이는 걸 막는다.

### 로드 셰딩 — 일부를 버려 나머지를 살린다

과부하 시 **전부 느리게 실패하는 것보다, 일부를 빠르게 거절하는 게 낫다.**

| 기준 | 방식 |
|---|---|
| 우선순위 | 결제 > 조회 > 추천 |
| 사용자 등급 | 유료 > 무료 |
| 요청 나이 | **이미 오래 기다린 요청은 버린다** (LIFO 처리) — 어차피 클라이언트가 타임아웃함 |
| 비용 | 비싼 쿼리 먼저 거절 |

> **로드 셰딩(load shedding)** — 과부하 시 일부 요청을 의도적으로 빠르게 거절해 나머지를 살리는 것.\
> 예: 다 같이 느려져 전부 타임아웃 나느니, 저우선 요청 20%를 즉시 거절하고 나머지 80%는 정상 처리한다.

> **역직관적이지만 중요한 것**: 과부하 시 **큐를 LIFO로 처리**하는 게 나을 수 있다.\
> FIFO면 오래된(이미 타임아웃된) 요청을 처리하느라 새 요청도 다 죽는다.

## 7. 폴백과 우아한 성능 저하

**미리 기능 등급을 나눠 둔다.** 장애 시점에 나누면 늦다.

| 등급 | 예 | 장애 시 |
|---|---|---|
| **핵심** | 로그인, 결제, 주문 | 반드시 살린다 |
| **주요** | 상품 조회, 검색 | 캐시/축소 응답으로 |
| **부가** | 추천, 리뷰 요약, 배지 | **꺼도 된다** |

### 폴백 전략

| 전략 | 예 |
|---|---|
| **캐시된 옛 데이터** | 실시간 재고 실패 → 최근 값 + "확인 중" 표시 |
| **기본값** | 개인화 추천 실패 → 인기 상품 목록 |
| **기능 숨김** | 리뷰 요약 실패 → 그 영역만 미표시 |
| **비동기 전환** | 즉시 처리 실패 → 큐에 넣고 "처리 중" |

> **폴백(fallback)** — 의존성이 실패했을 때 대신 내놓는 축소된 응답. 부분 장애가 화면 전체 실패로 번지는 걸 막는다.

### 킬 스위치 / 피처 플래그

**배포 없이 기능을 끌 수 있어야 한다.** 장애 대응 시 가장 빠른 수단이 배포라면 이미 늦다.

## 8. 도구별 정리 (무엇이 무엇을 막는가)

| 도구 | 막는 것 | 없으면 |
|---|---|---|
| **타임아웃** | 무한 대기, 스레드 고갈 | 다른 모든 장치가 무의미 |
| **재시도+백오프+지터** | 일시적 실패 | 순간 오류에 사용자 실패 |
| **재시도 예산** | 재시도 증폭 | 장애가 스스로 커짐 |
| **서킷 브레이커** | 죽은 의존성 반복 호출 | 자원 낭비 + 복구 방해 |
| **벌크헤드** | 자원 독점 | 부가 기능이 핵심을 죽임 |
| **백프레셔** | 큐 무한 증가 | OOM, 무의미한 작업 |
| **로드 셰딩** | 전체 동반 사망 | 다 같이 느리게 실패 |
| **폴백** | 부분 장애의 전면화 | 하나 죽으면 화면 전체 실패 |

## 9. 카오스 엔지니어링

> **테스트하지 않은 복원력은 복원력이 아니다.**

- 인스턴스 임의 종료 → 자동 복구되는가
- 의존성에 지연 주입 → 타임아웃·서킷이 동작하는가
- 캐시 전체 다운 → DB가 버티는가
- AZ 하나 차단 → 트래픽이 넘어가는가
- DB failover 실행 → 앱이 재연결하는가

> **카오스 엔지니어링(chaos engineering)** — 프로덕션에 가까운 환경에 의도적으로 장애를 주입해 복원력이 실제로 동작하는지 검증하는 것.

**게임데이**: 계획된 시간에 의도적으로 장애를 일으키고 대응 절차를 검증한다. 프로덕션 이전에 스테이징부터.

## 10. 체크리스트

- [ ] 모든 외부 호출에 연결·읽기 타임아웃이 있는가
- [ ] 타임아웃 예산이 안쪽 < 바깥쪽 순인가
- [ ] 재시도 × 타임아웃의 최악 총 지연이 SLA 안에 있는가
- [ ] 재시도에 지수 백오프 + 지터가 있는가
- [ ] 재시도가 여러 계층에서 중복되지 않는가
- [ ] 의존성별로 서킷 브레이커가 분리되어 있는가
- [ ] 부가 기능이 핵심 기능의 스레드/커넥션을 뺏을 수 있는가
- [ ] 모든 큐가 유한한가
- [ ] 과부하 시 거절 정책이 정의되어 있는가
- [ ] 배포 없이 기능을 끌 수 있는가
- [ ] 위 장치들이 **실제로 동작하는 걸 확인해봤는가**

---

## 핵심 문장

- **대형 장애의 대부분은 단일 고장이 아니라 전파(연쇄 실패)에서 온다.**
- **연쇄 실패는 전부 "부하가 스스로를 키우는 양의 되먹임 고리" — 복원력 장치는 그 고리를 끊는다.**
- **타임아웃이 없으면 서킷도 재시도도 전부 무의미하다 — 출발점.**
- **재시도는 위험한 도구 — 멱등성 전제, 백오프+지터, 예산, 한 계층에서만.**
- **벌크헤드의 질문은 하나 — 부가 기능이 핵심 기능의 자원을 뺏을 수 있는가?**

---

## 용어 풀이

- **연쇄 실패(Cascading Failure)** — 한 장애가 자원 고갈·재시도 증폭으로 전체에 번지는 것.
- **타임아웃 예산(Timeout Budget)** — 바깥 제한 시간을 안쪽이 나눠 갖는 배분. 안쪽이 더 짧아야.
- **유령 작업** — 바깥이 이미 끊겼는데 안쪽이 계속 자원을 쓰며 하는, 아무도 안 받는 작업.
- **멱등성(Idempotency)** — 같은 요청을 여러 번 실행해도 결과가 한 번과 같은 성질.
- **지수 백오프(Exponential Backoff)** — 재시도 간격을 2배씩 늘리는 것.
- **지터(Jitter)** — 재시도 시점에 랜덤을 더해 동시 몰림을 막는 것.
- **재시도 예산(Retry Budget)** — 전체 요청 중 재시도가 차지할 비율 상한.
- **서킷 브레이커(Circuit Breaker)** — 실패율이 임계를 넘으면 호출을 막고 즉시 실패시키는 장치.
- **벌크헤드(Bulkhead)** — 자원을 기능별로 칸막이해 독점을 막는 것.
- **백프레셔(Backpressure)** — 처리 능력을 넘는 유입을 밀어내는 것.
- **로드 셰딩(Load Shedding)** — 과부하 시 일부를 빠르게 거절해 나머지를 살리는 것.
- **폴백(Fallback)** — 실패 시 대신 내놓는 축소 응답.
- **피처 플래그 / 킬 스위치** — 배포 없이 기능을 켜고 끄는 스위치.
- **카오스 엔지니어링(Chaos Engineering)** — 장애를 주입해 복원력을 실제로 검증하는 것.
