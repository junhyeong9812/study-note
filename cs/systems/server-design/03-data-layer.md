# 03. 데이터 계층 확장

> 확장의 최종 난이도는 항상 여기에 있다. 앱은 늘리면 되지만 **데이터는 나눠야 하고, 나누면 되돌리기 어렵다.**\
> 출처: `jun-bank/docs/study/notes/server-design/03-data-layer.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(용어 풀이·세로 도식)만 입힘.

---

## 확장 사다리 (순서대로 올라간다)

```text
1. 쿼리·인덱스 최적화      ← 가장 싸다. 대부분 여기서 해결된다
2. 캐시                    ← 반복 읽기 제거
3. 수직 확장               ← 장비 키우기. 단순함이 가치
4. 읽기 복제본             ← 읽기 분산 (복제 지연 감수)
5. 테이블 파티셔닝         ← 한 DB 안에서 분할 (여전히 단일 노드)
6. 기능별 분할 (수직 분할) ← 도메인별 DB 분리
7. 샤딩 (수평 분할)        ← 마지막. 되돌리기 매우 어려움
```

> **3번을 건너뛰고 7번으로 가는 게 가장 흔한 오버엔지니어링이다.**

---

## 1. 읽기 확장 — 복제

### 구조

```text
쓰기 ──▶ [Primary] ──복제──▶ [Replica 1] ◀── 읽기
                     └──────▶ [Replica 2] ◀── 읽기
```

### 동기 vs 비동기 복제

| | 비동기 | 동기 | 준동기(semi-sync) |
|---|---|---|---|
| 쓰기 지연 | 낮음 | 높음 | 중간 |
| 장애 시 유실 | **가능 (RPO > 0)** | 없음 | 최소 |
| 복제본 장애 영향 | 없음 | **쓰기가 막힘** | 설정에 따라 |

**대부분 비동기를 쓴다.** 그 대가가 아래 문제다.

> **복제(replication)** — 같은 데이터를 여러 노드에 복사해 두는 것. 읽기를 나누고 하드웨어 장애를 견디게 한다.\
> 예: Primary에 쓰면 Replica들이 그 변경을 따라 반영하고, 읽기는 Replica가 나눠 받는다.

### 복제 지연 (replication lag) — 가장 자주 겪는 함정

같은 상황을 실패/방어로 대비하면:

```text
[방어 없음]                              [방어 있음]
글을 씀 (Primary)                        글을 씀 (Primary)
   ↓                                       ↓
바로 목록 조회 (Replica)                  방금 쓴 건 Primary에서 읽음
   ↓                                       ↓
복제가 아직 안 됨 → 방금 쓴 글 없음        내 글이 보인다
   ↓
"내 글이 사라졌다" (read-your-writes 위반)
```

| 해법 | 방식 | 대가 |
|---|---|---|
| **쓰기 후 일정 시간 Primary 읽기** | 쓰기 발생 시 세션에 타임스탬프 기록, N초간 Primary로 | 단순. Primary 부하 일부 증가 |
| **본인 데이터만 Primary** | 내가 수정 가능한 데이터는 항상 Primary | 구현 단순, 효과 큼 |
| **LSN/GTID 기반 대기** | 쓰기 응답에 위치를 받아, 읽기 시 그 위치까지 따라잡은 복제본 선택 | 정확. 구현 복잡 |
| **모노토닉 읽기 보장** | 세션을 같은 복제본에 고정 | 시간이 거꾸로 가는 현상 방지 |

> **복제 지연(replication lag)** — Primary의 변경이 Replica에 반영되기까지의 시차.\
> 예: 비동기 복제에서 방금 쓴 글이 복제본엔 아직 없어, 목록에 안 보이는 read-your-writes 위반이 생긴다.

**필수 운영**: 복제 지연을 **지표로 모니터링하고, 임계치를 넘은 복제본은 LB에서 빼는 것.**\
이게 없으면 지연된 복제본이 계속 낡은 데이터를 서빙한다.

### 복제로 해결되지 않는 것

- **쓰기 부하** — 모든 복제본이 같은 쓰기를 다 수행한다. 복제본을 늘려도 쓰기 용량은 그대로
- **데이터 크기** — 각 복제본이 전체 데이터를 갖는다

## 2. 쓰기·용량 확장 — 파티셔닝과 샤딩

### 용어 정리

| | 범위 | 목적 |
|---|---|---|
| **파티셔닝** | 한 DB 인스턴스 안에서 테이블 분할 | 쿼리 프루닝, **대량 삭제(파티션 드롭)**, 인덱스 크기 축소 |
| **샤딩** | 여러 DB 인스턴스로 분할 | 쓰기·용량 확장 |

> **파티셔닝 vs 샤딩** — 파티셔닝은 한 DB 안에서 테이블을 조각내는 것, 샤딩은 여러 DB 인스턴스로 나누는 것.\
> 예: 로그 테이블을 월별 파티션으로 자르면 파티셔닝(한 노드), 사용자 ID로 서버 4대에 나누면 샤딩(여러 노드).

> **파티셔닝을 먼저 검토한다.**\
> 시계열 데이터의 보관 정책은 파티션 드롭만으로 O(1)이 되고, 이것만으로 해결되는 경우가 많다.\
> (대량 `DELETE`는 락·팽창·복제 지연을 유발하는 최악의 작업 중 하나)

### 샤딩 방식

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **범위 기반** | ID 1~1000 → 샤드1 | 범위 쿼리 가능 | **핫스팟** (최신 데이터가 한 샤드에) |
| **해시 기반** | `hash(key) % N` | 균등 분산 | 범위 쿼리 불가, **N 변경 시 대량 재배치** |
| **디렉터리 기반** | 매핑 테이블 조회 | 유연한 재배치 | 매핑 테이블이 SPOF/병목 |
| **지역 기반** | 국가·테넌트별 | 데이터 주권, 격리 | 불균등 |

### 샤드 키 선택 — 되돌릴 수 없는 결정

3가지를 동시에 만족해야 한다.

1. **높은 카디널리티** — 값 종류가 충분히 많아야 잘게 나뉜다
2. **균등 분포** — 특정 값에 몰리지 않아야 한다 (핫스팟)
3. **쿼리 패턴 일치** — **대부분의 쿼리가 샤드 키를 조건에 포함해야 한다**

3번이 핵심이다.\
샤드 키가 없는 쿼리는 **모든 샤드에 흩뿌려(scatter-gather) 실행**되고, 이건 샤딩의 이점을 전부 상쇄한다.

> **샤드 키(shard key)** — 어느 샤드에 데이터가 들어갈지 정하는 기준 컬럼.\
> 예: 주문을 `user_id`로 샤딩하면 그 사용자 주문은 한 샤드에 모여, `user_id` 조건 쿼리는 한 샤드만 본다.

> **scatter-gather** — 샤드 키가 없는 쿼리를 모든 샤드에 뿌리고(scatter) 결과를 모으는(gather) 것.\
> 예: `WHERE email = ?`가 샤드 키가 아니면 전 샤드를 다 뒤져야 해서, 샤딩으로 얻은 이점이 사라진다.

**흔한 실수**

- **테넌트 ID로 샤딩했는데 거대 테넌트 하나가 한 샤드를 다 먹는 경우** → 복합 키(`tenant_id + 하위 키`)나 그 테넌트만 전용 샤드로
- **타임스탬프로 샤딩** → 항상 최신 샤드에만 쓰기가 몰림

### 리샤딩 (샤드 수 변경)

`hash % N`은 N이 바뀌면 거의 모든 키가 이동한다. 그래서:

| 기법 | 설명 |
|---|---|
| **Consistent Hashing** | 링에 배치. 노드 추가 시 **인접 구간만** 이동 |
| **Virtual Node** | 물리 노드당 가상 노드 여러 개 → 분포 균등화, 이동량 세분화 |
| **사전 분할 (pre-sharding)** | 처음부터 논리 샤드를 많이(예: 1024개) 만들고 물리 노드에 매핑. **노드 추가 = 매핑 변경만.** 실무에서 가장 실용적 |

> **Consistent Hashing** — 키와 노드를 같은 링 위에 놓고, 키를 시계방향 다음 노드에 배정하는 방식.\
> 예: 노드 하나를 추가해도 그 노드가 맡을 인접 구간의 키만 옮겨지고 나머지는 그대로다(대량 재배치 회피).

> **처음 샤딩할 때 사전 분할로 시작하면 나중 리샤딩이 훨씬 쉬워진다.**

### 크로스 샤드 문제와 해법

| 문제 | 해법 |
|---|---|
| **조인 불가** | 자주 조인하는 데이터를 같은 샤드에 배치(공존, colocation) / 참조 데이터는 전 샤드 복제 / 앱에서 조합 |
| **분산 트랜잭션** | 2PC는 피한다 → **Saga 패턴** (보상 트랜잭션) 또는 경계를 다시 그어 한 샤드에 담기 |
| **전역 유니크** | 중앙 시퀀스 / **Snowflake ID** (타임스탬프+노드ID+시퀀스) / UUIDv7 |
| **전역 집계** | 각 샤드 집계 후 병합 / 별도 분석 DB로 복제(CQRS) |
| **페이지네이션** | 모든 샤드에서 N개씩 가져와 병합 — 깊은 페이지는 매우 비쌈 → 커서 기반으로 전환 |

## 3. 읽기 모델 분리 (CQRS)

**쓰기에 최적화된 모델과 읽기에 최적화된 모델은 다르다.**

```text
쓰기 ──▶ [정규화된 OLTP DB]
              │ CDC / 이벤트
              ▼
        [읽기 전용 모델]   비정규화, 검색엔진, 집계 테이블
              ▲
읽기 ─────────┘
```

> **CQRS(Command Query Responsibility Segregation)** — 쓰기(명령) 모델과 읽기(조회) 모델을 분리하는 설계.\
> 예: 쓰기는 정규화된 OLTP DB에, 읽기는 조인을 없앤 비정규화 테이블·검색엔진에 두어 각각 최적화한다.

| 읽기 모델 | 용도 |
|---|---|
| 비정규화 테이블 | 조인 제거 |
| Elasticsearch | 전문 검색, 복합 필터 |
| ClickHouse | 대량 집계·분석 |
| Redis | 랭킹, 카운터 |

**대가: 최종적 일관성.** 읽기 모델은 항상 조금 낡았다.\
그래서 **어떤 화면이 얼마만큼의 지연을 허용하는지** 먼저 정해야 한다.

**동기화 수단**

- **CDC (Debezium 등)**: WAL/binlog를 tail. 앱 코드 변경 없음, 누락 없음
- **애플리케이션 이벤트**: 아웃박스 패턴 필수 (별도 주제: 이중 쓰기 문제·아웃박스 — 이 컬렉션 밖)
- **주기적 배치 재구축**: 정합성 보정용으로 병행

> **CDC(Change Data Capture)** — DB의 변경 로그(WAL/binlog)를 읽어 다른 저장소로 흘려보내는 것.\
> 예: Debezium이 커밋된 변경을 tail 해서 검색엔진 색인을 갱신하면, 앱 코드를 안 고쳐도 누락 없이 반영된다.

## 4. 다중 저장소 정합성

**저장소를 하나 늘릴 때마다 "맞추는 일"이 하나 늘어난다.**

```text
DB 커밋 성공
   ↓
검색엔진 색인 실패
   ↓
검색 결과에 안 나옴  ← 두 저장소가 어긋남
```

| 수단 | 보장 |
|---|---|
| 이중 쓰기 (그냥 둘 다 호출) | ❌ 보장 없음 |
| 트랜잭셔널 아웃박스 | ✅ 유실 없음, 중복 가능 |
| CDC | ✅ 유실 없음, 순서 보장 |
| **대조 배치** | 위 수단의 보완. 정기적으로 원천과 대조해 차이 보정 |

> 어떤 수단을 쓰든 **대조 배치는 있는 게 좋다.**\
> 그게 "우리 시스템이 실제로 맞는지" 확인하는 유일한 방법이다.

## 5. 데이터 수명 관리 (자주 빠뜨림)

데이터가 무한히 쌓이면 **인덱스가 커지고, 백업이 느려지고, 마이그레이션이 불가능해진다.**\
확장성 문제는 트래픽보다 데이터 크기에서 먼저 오는 경우가 많다.

| 수단 | 방식 |
|---|---|
| **파티션 드롭** | 시계열 데이터의 표준. `DELETE` 대신 O(1) |
| **아카이빙** | 오래된 데이터를 저비용 저장소(S3, 콜드 스토리지)로 |
| **TTL** | Redis, ClickHouse, MongoDB 등이 내장 지원 |
| **소프트 삭제 정리** | `deleted_at`만 찍고 방치하면 테이블이 계속 큰다 |

## 6. 체크리스트

- [ ] 샤딩 전에 인덱스·캐시·수직 확장·파티셔닝을 다 해봤는가
- [ ] 샤드 키가 대부분의 쿼리 조건에 포함되는가
- [ ] 복제 지연을 모니터링하고 임계치 초과 시 LB에서 빼는가
- [ ] read-your-writes가 깨지는 화면을 파악하고 있는가
- [ ] 리샤딩 경로가 준비되어 있는가 (사전 분할 여부)
- [ ] 데이터 보관 정책과 삭제 수단이 있는가
- [ ] 다중 저장소 간 대조 수단이 있는가

## 핵심 문장

- **확장 사다리를 순서대로 — 3번(수직 확장)을 건너뛰고 7번(샤딩)으로 가는 게 가장 흔한 오버엔지니어링.**
- **복제는 읽기·하드웨어 장애만 해결한다 — 쓰기 부하와 데이터 크기는 그대로.**
- **샤드 키의 핵심은 "대부분의 쿼리가 샤드 키를 포함하는가" — 아니면 scatter-gather로 이점이 사라진다.**
- **처음부터 사전 분할(pre-sharding)로 시작하면 리샤딩이 쉬워진다.**
- **CQRS의 대가는 최종적 일관성 — 어느 화면이 얼마의 지연을 허용하는지 먼저 정한다.**

---

## 용어 풀이

- **복제(Replication)** — 같은 데이터를 여러 노드에 복사. 읽기 분산·하드웨어 장애 대비.
- **복제 지연(Replication Lag)** — Primary 변경이 Replica에 반영되기까지의 시차.
- **read-your-writes** — 방금 쓴 값을 바로 읽을 수 있어야 한다는 일관성 요구.
- **RPO(Recovery Point Objective)** — 허용하는 데이터 유실량. 비동기 복제면 RPO > 0.
- **파티셔닝(Partitioning)** — 한 DB 안에서 테이블을 조각내는 것.
- **샤딩(Sharding)** — 여러 DB 인스턴스로 데이터를 나누는 것.
- **샤드 키(Shard Key)** — 어느 샤드로 갈지 정하는 기준 컬럼. 되돌리기 어려운 결정.
- **핫스팟(Hotspot)** — 특정 샤드/파티션에 부하가 몰리는 현상.
- **scatter-gather** — 샤드 키 없는 쿼리를 전 샤드에 뿌리고 결과를 모으는 것.
- **Consistent Hashing** — 노드 변동 시 인접 구간만 재배치되는 해싱.
- **사전 분할(Pre-sharding)** — 논리 샤드를 미리 많이 만들어 물리 노드에 매핑하는 것.
- **Saga** — 분산 트랜잭션을 보상 트랜잭션들의 연쇄로 대체하는 패턴.
- **CQRS** — 쓰기 모델과 읽기 모델을 분리하는 설계.
- **CDC(Change Data Capture)** — DB 변경 로그를 tail 해 다른 저장소로 전파.
- **아웃박스(Outbox)** — DB 커밋과 메시지 발행을 한 트랜잭션으로 묶는 패턴.
- **최종적 일관성(Eventual Consistency)** — 지금은 달라도 시간이 지나면 같아지는 상태.
