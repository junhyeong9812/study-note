# 05. 고가용성 토폴로지

> 가용성은 "죽지 않게 만드는 것"이 아니라 **"죽는 걸 전제하고, 죽어도 서비스가 계속되게 만드는 것"**이다.\
> 출처: `jun-bank/docs/study/notes/server-design/05-ha-topology.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(용어 풀이·세로 도식·실패→방어 대비)만 입힘.

---

## 1. 먼저 목표를 숫자로 정한다

| 가용성 | 연간 다운타임 | 월 다운타임 | 대략적 구성 |
|---|---|---|---|
| 99% | 3.65일 | 7.3시간 | 단일 서버 + 백업 |
| 99.9% | 8.8시간 | 43분 | 이중화 + 자동 failover |
| 99.99% | 53분 | 4.3분 | 다중 AZ + 무중단 배포 |
| 99.999% | 5.3분 | 26초 | 다중 리전 액티브-액티브 |

**9가 하나 늘 때마다 비용은 대략 한 자릿수씩 는다.**

### 가용성의 합성 — 직렬이 무섭다

```text
직렬(의존): A와 B가 둘 다 필요  →  A × B
  99.9% × 99.9% = 99.8%       ← 떨어진다

병렬(이중화): 둘 중 하나만 살면 됨 →  1 − (1−A) × (1−B)
  1 − 0.001 × 0.001 = 99.9999% ← 올라간다
```

> **가용성 합성** — 여러 컴포넌트를 묶었을 때 전체 가용성. 직렬(둘 다 필요)이면 곱해서 떨어지고, 병렬(하나만 살면 됨)이면 올라간다.\
> 예: 99.9%짜리 서비스 5개를 순차로 거치면 전체는 99.5%로 떨어진다(곱셈).

**함의: 의존성이 많을수록 가용성은 곱셈으로 떨어진다.**\
마이크로서비스로 쪼개서 요청 하나가 5개 서비스를 거치면, 각각 99.9%여도 전체는 99.5%가 된다.\
→ **그래서 격리(→ [`06-resilience.md`](./06-resilience.md))가 필수다.**

### RTO / RPO

| 지표 | 의미 | 결정하는 것 |
|---|---|---|
| **RTO** (Recovery Time Objective) | 얼마나 빨리 복구해야 하나 | failover 자동화 수준 |
| **RPO** (Recovery Point Objective) | 얼마만큼의 데이터 유실을 허용하나 | 복제 방식(동기/비동기), 백업 주기 |

> **RTO / RPO** — RTO는 "복구까지 걸려도 되는 시간", RPO는 "잃어도 되는 데이터의 양(시간)".\
> 예: RPO 5분이면 마지막 5분치 데이터 유실은 감수, RTO 1분이면 1분 안에 다시 서비스돼야 한다.

> **RPO=0을 원하면 동기 복제가 필요하고, 그러면 쓰기 지연과 가용성을 내준다.** (CAP의 실제 모습)

## 2. 이중화 토폴로지

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **Active-Passive** | 대기 노드는 놀고 있다가 승격 | 단순, 상태 충돌 없음 | 자원 낭비, **failover 시간 필요**, 대기 노드가 실제로 동작하는지 모름 |
| **Active-Active** | 모두 트래픽 처리 | 자원 효율, 즉시 전환 | **상태 동기화 문제**, 용량 계획 주의 |
| **N+1 / N+M** | N개 필요 + 여분 M개 | 비용 균형 | 관리 복잡 |

### Active-Active의 함정 — 용량 계획

같은 2대 구성을 잘못/제대로 대비하면:

```text
[각 70% 부하]                        [각 50% 이하 부하]
2대가 각각 70%                        2대가 각각 50%
   ↓                                   ↓
한 대 죽음                            한 대 죽음
   ↓                                   ↓
남은 한 대가 140% → 같이 죽음          남은 한 대가 100% → 버틴다
```

> **규칙: N대 구성이면 각 노드는 (N−1)/N 이하로 유지한다.** 2대면 50% 이하, 3대면 66% 이하.\
> 이걸 안 지키면 이중화가 오히려 **연쇄 장애 장치**가 된다.

### Active-Passive의 함정 — 검증되지 않은 대기 노드

**"failover를 한 번도 실행해본 적 없는 시스템의 대기 노드는 없는 것과 같다."**\
정기적으로 실제 전환을 수행해야 한다(계획된 failover 훈련).

## 3. 리더-팔로워 Failover

### 자동 승격의 어려움

```text
리더가 응답이 없다.
   ↓
정말 죽은 건가?
   ↓
아니면 네트워크가 끊긴 건가?
   ↓
아니면 GC로 잠깐 멈춘 건가?
```

**구분할 방법이 없다.** 이게 분산 시스템의 근본 문제다.

### Split-Brain

잘못 판단해서 새 리더를 세웠는데 **옛 리더가 살아 있으면 리더가 둘**이 된다.\
→ 양쪽이 각자 쓰기를 받아 **데이터가 갈라진다.** 병합 불가능한 손상.

> **split-brain** — 네트워크 분할 등으로 리더가 둘이 되어 양쪽이 각자 쓰기를 받는 상태.\
> 예: 옛 리더가 살아 있는데 새 리더를 세우면, 두 리더가 서로 모른 채 다른 데이터를 써서 병합 불가능해진다.

| 방어 수단 | 방식 |
|---|---|
| **쿼럼 (과반수)** | 과반 노드의 동의 없이는 리더가 될 수 없음. **3, 5, 7 등 홀수 노드** |
| **Fencing / STONITH** | 옛 리더를 강제로 차단(전원 차단, 스토리지 접근 차단) |
| **Fencing Token** | 단조 증가 번호. 저장소가 낮은 번호의 쓰기를 거부 |
| **임대(Lease)** | 리더십에 만료 시간. 갱신 실패 시 스스로 리더 포기 |

> **쿼럼(quorum)** — 과반수의 동의. 과반을 못 얻으면 리더가 될 수 없어 리더가 둘이 되는 걸 막는다.\
> 예: 5대 중 3대의 동의가 있어야 리더 — 네트워크가 3:2로 갈리면 2대 쪽은 과반이 안 돼 리더가 못 된다.

> **fencing** — 옛 리더가 더 이상 쓰기를 못 하게 강제로 격리하는 것(전원·스토리지 차단, 토큰 거부).

> **노드를 짝수로 두면 안 되는 이유**: 2대에서 네트워크가 갈리면 1:1이라 어느 쪽도 과반이 아니다 → 둘 다 멈추거나, 규칙을 완화하면 split-brain.\
> **홀수 + 외부 조정자(ZooKeeper/etcd/Keeper)** 가 표준.

## 4. 다중 AZ / 다중 리전

### 다중 AZ (같은 리전 내 다른 데이터센터)

- 지연이 낮아(수 ms) **동기 복제 가능**
- 대부분의 서비스에서 **여기까지가 비용 대비 합리적인 지점**
- 필수: 모든 계층(LB, 앱, DB, 캐시)이 다중 AZ여야 한다. 하나라도 단일 AZ면 그게 SPOF

> **AZ(Availability Zone)** — 같은 리전 안의 물리적으로 분리된 데이터센터. 지연이 낮아 동기 복제가 가능하다.\
> 예: 서울 리전의 AZ-a와 AZ-c에 DB를 나눠 두면, 한 데이터센터가 정전돼도 다른 쪽이 이어받는다.

> **SPOF(Single Point of Failure)** — 그것 하나가 죽으면 전체가 죽는 지점. 모든 계층에서 하나씩 짚어 없앤다.

### 다중 리전

| 모델 | RTO | RPO | 비용 |
|---|---|---|---|
| **백업 복원** | 시간~일 | 시간 | 낮음 |
| **Pilot Light** (최소 구성 상시) | 수십 분 | 분 | 중간 |
| **Warm Standby** (축소 구성 상시) | 분 | 초 | 높음 |
| **Active-Active** | 즉시 | ~0 | 매우 높음 |

**다중 리전 Active-Active가 어려운 이유**

- 리전 간 지연(수십~수백 ms)으로 **동기 복제가 비현실적** → 최종적 일관성 감수
- **쓰기 충돌 해결**이 필요 (Last-Write-Wins는 데이터를 잃는다, CRDT는 적용 범위가 제한적)
- 실무 절충: **쓰기는 한 리전, 읽기는 전 리전** / 또는 **사용자·테넌트를 리전에 고정(셀 기반)**

### 셀 기반 아키텍처 (Cell-based / Bulkhead at scale)

사용자를 독립된 셀로 나눠 배치. **한 셀의 장애가 그 셀 사용자에게만 영향.**\
장애 반경(blast radius)을 구조적으로 제한하는 방법. 대규모 서비스의 사실상 표준.

> **셀 기반 아키텍처(cell-based)** — 사용자를 독립된 셀(완결된 스택)로 나눠, 한 셀 장애가 그 셀 사용자에게만 미치게 하는 것.\
> 예: 사용자를 10개 셀로 나누면 한 셀이 죽어도 영향은 10%로 제한된다(장애 반경 축소).

## 5. 상태 없는 것과 있는 것의 HA는 다르다

| | 무상태 (앱 서버) | 상태 저장 (DB, 캐시, 브로커) |
|---|---|---|
| 이중화 | 그냥 여러 대 띄우면 됨 | **복제 + 합의 필요** |
| 노드 교체 | 즉시 | 데이터 이동 필요 |
| failover | LB가 알아서 | 승격·쿼럼·펜싱 필요 |
| 난이도 | 낮음 | 높음 |

> **HA 설계의 어려움은 전부 상태 저장 컴포넌트에 있다.**\
> 그래서 상태를 관리형 서비스(RDS, ElastiCache 등)에 맡기는 선택이 합리적인 경우가 많다.

## 6. 백업 — 복제와 다르다

**복제는 백업이 아니다.**

```text
실수로 DELETE 실행 → 모든 복제본에 즉시 전파됨
스키마 변경 사고    → 모든 복제본에 전파됨
애플리케이션 버그   → 잘못된 데이터가 전 노드에
```

복제는 **하드웨어 장애**를 막고, 백업은 **논리적 사고**를 막는다. 둘 다 필요하다.

> **복제 ≠ 백업** — 복제는 실시간으로 따라 쓰므로 논리 사고(잘못된 DELETE·버그)도 그대로 전파한다. 백업은 특정 시점을 따로 보관한다.\
> 예: 복제만 있으면 `DELETE` 사고가 전 복제본에 퍼져 되돌릴 수 없다 — 시점 백업이 있어야 사고 직전으로 복구한다.

### 백업 체크리스트

- [ ] 백업이 **다른 장애 도메인**(다른 리전/계정)에 있는가
- [ ] **PITR(특정 시점 복구)**가 가능한가 (사고 직전으로 되돌리기)
- [ ] **복원을 실제로 해봤는가** ← 가장 중요. 복원해보지 않은 백업은 백업이 아니다
- [ ] 복원 소요 시간을 아는가 (그게 실제 RTO)
- [ ] 백업이 랜섬웨어/권한 사고로부터 격리되어 있는가 (불변 백업)

## 7. 헬스체크 설계 (다시 강조)

| 종류 | 확인 범위 | 실패 시 |
|---|---|---|
| Liveness | 프로세스 자체 | 재시작 |
| Readiness | 트래픽 수용 준비 | 트래픽 제외 |

**깊은 헬스체크의 연쇄 실패**\
헬스체크가 DB를 확인하면, DB가 잠깐 느려질 때 **전 인스턴스가 동시에 unhealthy** → LB가 보낼 곳이 없어짐 → **부분 장애가 전체 장애가 된다.**

> 원칙:
> - **Liveness는 절대 의존성을 확인하지 않는다**
> - Readiness도 최소한만 확인한다
> - 의존성 상태는 **서킷 브레이커**로 다룬다 (→ [`06-resilience.md`](./06-resilience.md))
> - LB에 "전부 unhealthy면 오히려 전부에게 보낸다"는 fail-open 옵션이 있으면 켠다

## 8. 체크리스트

- [ ] 가용성 목표(몇 9)가 정해져 있고 그에 맞는 투자인가
- [ ] 모든 계층에 SPOF가 없는가 (하나씩 짚으며 "이게 죽으면?")
- [ ] Active-Active 각 노드가 (N−1)/N 이하 부하인가
- [ ] 상태 저장 컴포넌트에 쿼럼·펜싱이 있는가 (홀수 노드)
- [ ] **failover를 실제로 실행해본 적이 있는가**
- [ ] 헬스체크가 연쇄 실패를 유발하지 않는가
- [ ] 백업이 별도 장애 도메인에 있고 **복원을 테스트했는가**
- [ ] 장애 반경이 제한되어 있는가 (셀/샤드 단위 격리)

---

## 핵심 문장

- **가용성은 죽지 않게가 아니라, 죽어도 계속되게 만드는 것.**
- **의존성은 곱셈으로 가용성을 깎는다 — 5개를 직렬로 거치면 99.9%가 99.5%로.**
- **이중화는 (N−1)/N 용량 규칙을 안 지키면 오히려 연쇄 장애 장치가 된다.**
- **split-brain은 쿼럼(홀수 노드)+펜싱으로 막는다 — 짝수 노드는 금물.**
- **복제는 백업이 아니다 — 복원해보지 않은 백업은 백업이 아니다.**

---

## 용어 풀이

- **가용성 합성** — 직렬은 곱해서 떨어지고 병렬(이중화)은 올라가는 전체 가용성 계산.
- **RTO** — 복구까지 허용되는 시간. failover 자동화 수준이 결정.
- **RPO** — 허용하는 데이터 유실량. 복제 방식·백업 주기가 결정.
- **Active-Passive / Active-Active** — 대기 노드가 놀다 승격 / 모두 트래픽 처리.
- **split-brain** — 리더가 둘이 되어 양쪽이 각자 쓰기를 받는 손상 상태.
- **쿼럼(Quorum)** — 과반수 동의. 리더가 둘이 되는 것을 막는다.
- **Fencing / STONITH** — 옛 리더를 강제 차단하는 것.
- **Fencing Token** — 단조 증가 번호로 낡은 리더의 쓰기를 거부하는 것.
- **임대(Lease)** — 만료 시간이 있는 리더십. 갱신 실패 시 스스로 포기.
- **AZ(Availability Zone)** — 같은 리전 내 물리 분리 데이터센터.
- **SPOF** — 그것 하나가 죽으면 전체가 죽는 단일 지점.
- **셀 기반 아키텍처(Cell-based)** — 사용자를 독립 셀로 나눠 장애 반경을 제한.
- **장애 반경(Blast Radius)** — 한 장애가 영향을 미치는 범위.
- **PITR(Point-In-Time Recovery)** — 특정 시점으로 되돌리는 복구.
