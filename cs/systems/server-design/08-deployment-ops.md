# 08. 배포와 운영

> **가용성을 가장 많이 깎는 원인은 하드웨어 고장이 아니라 변경이다.**\
> 장애의 대부분은 배포·설정 변경 직후에 발생한다. 그래서 배포 전략 자체가 가용성 설계다.\
> 출처: `jun-bank/docs/study/notes/server-design/08-deployment-ops.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(용어 풀이·세로 도식)만 입힘.

---

## 1. 무중단 배포 전략

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **Rolling** | 인스턴스를 순차 교체 | 추가 자원 최소 | 롤백 느림, **신·구 버전 공존** |
| **Blue-Green** | 새 환경 전체 구성 후 트래픽 전환 | **즉시 롤백**, 공존 시간 짧음 | 자원 2배, DB는 여전히 공유 |
| **Canary** | 소수(1~5%)에만 신버전 → 점진 확대 | **실제 트래픽으로 검증**, 영향 최소 | 지표 자동 판정 필요, 공존 시간 김 |
| **Shadow** | 실트래픽을 복제해 신버전에 보냄(응답은 버림) | 위험 없이 검증 | 부수효과 격리 필요, 비용 |

> **Blue-Green / Canary** — Blue-Green은 새 환경을 통째로 띄우고 트래픽을 한 번에 넘기는 것(즉시 롤백), Canary는 소수에만 신버전을 흘려 지표를 보며 늘리는 것.\
> 예: Canary로 5% 사용자에게만 신버전을 보내 에러율이 정상이면 25%·50%로 확대하고, 나쁘면 그 5%만 되돌린다.

### 실무 조합

**Canary → 관측 → 자동 롤백** 파이프라인이 가장 안전하다.

- 카나리 판정 지표: 에러율, p99 지연, 핵심 비즈니스 지표(주문 성공률)
- **자동 롤백 기준을 미리 정한다.** 사람 판단을 기다리면 늦다

### 신·구 버전 공존을 항상 전제한다

Rolling·Canary는 **반드시 두 버전이 동시에 도는 시간**이 있다. 그래서:

- **API는 양방향 호환**이어야 한다 (신버전이 구버전 응답을 처리 가능, 반대도)
- **캐시 데이터 포맷**도 공존 가능해야 한다 → 포맷 바꿀 땐 키를 바꾼다
- **메시지 스키마**도 마찬가지 (구버전 컨슈머가 신버전 메시지를 처리 가능해야)

## 2. DB 마이그레이션 — 가장 위험한 변경

**코드는 롤백되지만 데이터는 롤백되지 않는다.**

### Expand–Contract 패턴 (확장 후 축소)

컬럼 이름 변경(`name` → `full_name`)을 예로:

```text
1. Expand   : full_name 컬럼 추가 (nullable). 스키마만 변경, 배포 없음
   ↓
2. Dual Write: 코드가 양쪽에 쓴다. 읽기는 아직 name
   ↓
3. Backfill : 기존 데이터를 full_name으로 채운다 (배치, 청크 단위)
   ↓
4. Switch   : 읽기를 full_name으로 전환
   ↓
5. Contract : 안정화 확인 후 name 컬럼 삭제
```

**각 단계가 독립적으로 롤백 가능해야 한다.** 이게 핵심이다.

> **Expand-Contract** — 스키마를 바로 바꾸지 않고, 새 것을 더한 채 둘 다 유지하다(Expand) 안정되면 옛 것을 지우는(Contract) 방식.\
> 예: 컬럼을 즉시 rename 하면 구버전 코드가 깨지지만, 새 컬럼을 추가·양쪽 쓰기·백필·전환·삭제로 나누면 각 단계를 롤백할 수 있다.

### 절대 하면 안 되는 것

| 위험한 작업 | 이유 | 대안 |
|---|---|---|
| 컬럼 즉시 rename/drop | 구버전 코드가 깨짐 | Expand-Contract |
| `NOT NULL` 컬럼 즉시 추가 | 테이블 전체 락 (DB·버전에 따라) | nullable로 추가 → 백필 → 제약 추가 |
| 대량 `UPDATE`/`DELETE` 단일 트랜잭션 | 락, 복제 지연, 롤백 불가 | 청크 분할 + 사이 휴식 |
| 대형 테이블에 일반 인덱스 생성 | 쓰기 차단 | `CREATE INDEX CONCURRENTLY` (PG) |
| 배포와 마이그레이션 동시 실행 | 순서 보장 안 됨 | 분리 (마이그레이션 먼저, 하위 호환 유지) |

### 원칙

> **스키마 변경은 항상 "구버전 코드가 계속 동작하도록" 한다.**\
> 그래야 배포를 롤백할 수 있다.

## 3. 롤백 가능성 = 가용성

**MTTR(평균 복구 시간)을 줄이는 가장 강력한 수단은 빠른 롤백이다.**

| 수단 | 복구 시간 |
|---|---|
| **피처 플래그 off** | 초 |
| **Blue-Green 전환** | 초~분 |
| **이전 이미지 재배포** | 분 |
| **핫픽스 개발 후 배포** | 수십 분~시간 |
| **DB 복원** | 시간 |

> **MTTR(Mean Time To Recovery)** — 장애 발생부터 복구까지의 평균 시간. 가용성은 "얼마나 안 죽나"보다 "얼마나 빨리 살아나나"에 더 좌우된다.\
> 예: 같은 빈도로 죽어도 롤백이 초 단위면 MTTR이 짧아 가용성 숫자가 훨씬 좋다.

> **모든 위험한 변경은 피처 플래그 뒤에 둔다.**\
> 배포와 릴리스를 분리하면, 문제 시 배포 없이 끌 수 있다.

### 피처 플래그 운영

- 플래그도 부채다. **정리 계획 없이 쌓이면 코드 경로가 폭발한다**
- 플래그 조회 자체가 SPOF가 되지 않게 (기본값 + 로컬 캐시)
- **킬 스위치**: 핵심 의존성별로 "이 기능 끄기" 스위치를 미리 준비

> **피처 플래그(feature flag)** — 코드에 심어 두고 배포 없이 켜고 끌 수 있는 스위치. 배포(코드 반영)와 릴리스(기능 노출)를 분리한다.

## 4. 설정 변경도 배포다

**대형 장애의 상당수는 코드가 아니라 설정 변경에서 나온다.** (잘못된 LB 규칙, 잘못된 레이트 리밋, 잘못된 DNS)

- 설정도 **버전 관리 + 리뷰 + 점진 배포**
- 설정 변경도 **롤백 가능**해야 함
- **전역 설정을 한 번에 전 노드에 적용하지 않는다** (한 번에 전부 죽는 대표 경로)

## 5. 관측 — 골든 시그널

측정하지 않는 것은 개선할 수 없고, **알림이 없으면 사용자가 먼저 안다.**

| 시그널 | 의미 | 예 |
|---|---|---|
| **Latency** | 응답 시간 | p50/p95/p99. **성공/실패 분리해서 측정** |
| **Traffic** | 요청량 | RPS, 동시 접속 |
| **Errors** | 실패율 | 5xx, 타임아웃, 비즈니스 실패 |
| **Saturation** | 자원 포화도 | CPU, 메모리, 스레드풀 사용률, 큐 길이 |

> **골든 시그널(golden signals)** — 서비스 건강을 보는 네 지표: 지연(Latency)·트래픽(Traffic)·에러(Errors)·포화도(Saturation).\
> 예: 이 넷만 대시보드에 두어도 "느린가·많은가·실패하나·자원이 찼나"를 한눈에 판단할 수 있다.

> **실패한 요청의 지연을 성공과 섞으면 안 된다.**\
> 빠르게 실패하는 요청이 많으면 평균 지연이 오히려 좋아 보인다.

### 3축 관측

| 축 | 답하는 질문 |
|---|---|
| **메트릭** | 얼마나 자주, 얼마나 오래 (추세, 알림) |
| **로그** | 무슨 일이 있었나 (**구조화 + trace id 필수**) |
| **트레이스** | 어디서 시간을 썼나 (분산 시스템 필수) |

### 알림 설계

- **증상에 알림을 건다, 원인이 아니라.** "CPU 80%"가 아니라 "에러율 상승" / "p99 초과"
- **행동 가능한 알림만.** 대응할 게 없는 알림은 알림 피로를 만들고, 진짜 알림을 놓치게 한다
- **에러 버짓 소진 속도**에 알림 (SLO 기반 → [`09-capacity-slo.md`](./09-capacity-slo.md))

## 6. 장애 대응 절차

```text
감지 → 완화 → 진단 → 복구 → 사후 분석
```

**가장 흔한 실수: 진단을 먼저 하려는 것.**

> **완화가 진단보다 먼저다.**\
> 원인을 모르더라도 롤백·플래그 off·트래픽 차단으로 먼저 지혈한다. 원인 분석은 서비스가 살아난 뒤에.

### 사후 분석 (Postmortem)

- **비난 없는(blameless) 문화**: 사람이 아니라 시스템을 고친다. 비난하면 다음부터 숨긴다
- 담을 것: 타임라인, 영향 범위, 근본 원인, **감지가 늦은 이유**, 재발 방지 액션(담당자·기한 포함)
- **"조심하겠습니다"는 액션이 아니다.** 자동화·가드레일·알림 추가여야 한다

> **비난 없는 사후 분석(blameless postmortem)** — 사람이 아니라 시스템의 결함을 찾아 고치는 회고. 비난하면 다음부터 사실을 숨겨 재발을 못 막는다.

## 7. 운영 준비 체크리스트 (신규 서비스 출시 전)

**용량**
- [ ] 피크 트래픽 예측과 부하 테스트 결과가 있는가
- [ ] 오토스케일 정책과 상한이 있는가

**복원력**
- [ ] 모든 외부 호출에 타임아웃·재시도·서킷 브레이커가 있는가
- [ ] 의존성이 죽었을 때의 동작이 정의되어 있는가

**배포**
- [ ] 무중단 배포와 **롤백 절차가 검증**되었는가
- [ ] 마이그레이션이 하위 호환인가

**관측**
- [ ] 골든 시그널 대시보드가 있는가
- [ ] 알림이 있고, 담당자에게 실제로 도달하는가 (테스트했는가)
- [ ] trace id가 전 구간에 전파되는가

**복구**
- [ ] 백업이 있고 **복원을 테스트**했는가
- [ ] 런북(장애 상황별 대응 문서)이 있는가
- [ ] 킬 스위치가 있는가

## 핵심 문장

- **가용성을 가장 많이 깎는 건 변경 — 그래서 배포 전략 자체가 가용성 설계다.**
- **Rolling·Canary는 신·구 버전이 공존하는 시간이 반드시 있다 — API·캐시·메시지 스키마가 양방향 호환이어야.**
- **스키마 변경은 "구버전 코드가 계속 동작하도록"(Expand-Contract) — 그래야 배포를 롤백할 수 있다.**
- **롤백 가능성 = 가용성 — MTTR을 줄이는 가장 강력한 수단은 빠른 롤백.**
- **완화가 진단보다 먼저, 사후 분석은 비난 없이.**

---

## 용어 풀이

- **Rolling / Blue-Green / Canary / Shadow** — 순차 교체 / 환경 통째 전환 / 소수 점진 확대 / 복제 트래픽 검증.
- **신·구 버전 공존** — 무중단 배포 중 두 버전이 동시에 도는 시간. 양방향 호환 필요.
- **Expand-Contract** — 새 것을 더한 채 유지하다 안정되면 옛 것을 지우는 마이그레이션.
- **MTTR** — 장애 발생부터 복구까지 평균 시간.
- **피처 플래그(Feature Flag)** — 배포 없이 기능을 켜고 끄는 스위치. 배포와 릴리스 분리.
- **킬 스위치** — 핵심 의존성별로 미리 준비한 기능 끄기 스위치.
- **골든 시그널** — Latency·Traffic·Errors·Saturation 네 지표.
- **3축 관측** — 메트릭·로그·트레이스.
- **에러 버짓** — 허용된 실패량(1 − SLO). 소진 속도에 알림을 건다.
- **비난 없는 사후 분석(Blameless Postmortem)** — 사람이 아닌 시스템을 고치는 회고.
- **런북(Runbook)** — 장애 상황별 대응 절차 문서.
