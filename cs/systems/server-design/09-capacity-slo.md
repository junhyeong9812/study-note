## 1. SLI / SLO / 에러 버짓

| 개념 | 정의 | 예 |
|---|---|---|
| **SLI** | 측정 지표 | 성공 응답 비율, p99 지연 |
| **SLO** | 목표치 | 30일간 성공률 99.9%, p99 < 500ms |
| **SLA** | 고객과의 계약 (위반 시 배상) | SLO보다 느슨하게 잡는다 |
| **에러 버짓** | 허용된 실패량 = 1 − SLO | 99.9%면 30일에 43분 |

> **SLI / SLO / SLA** — SLI는 측정하는 지표, SLO는 그 지표의 내부 목표치, SLA는 고객과 맺은 계약(위반 시 배상).\
> 예: "성공률"이 SLI, "30일 99.9%"가 SLO, "99.5% 밑이면 요금 감면"이 SLA — SLA는 SLO보다 느슨하게 잡는다.

### 에러 버짓의 실질적 쓸모

**"안정성과 개발 속도의 갈등을 숫자로 중재한다."**

```text
버짓이 남아 있음  → 배포·실험을 공격적으로
버짓을 다 씀      → 신규 기능 중단, 안정화 작업에 집중
```

> **에러 버짓(error budget)** — SLO가 100%가 아니기에 생기는 "허용된 실패량"(1 − SLO). 배포·실험에 쓸 수 있는 예산처럼 다룬다.\
> 예: 99.9% SLO면 30일에 43분의 실패가 허용 — 이 예산이 남으면 공격적으로 배포하고, 다 쓰면 안정화에 집중한다.

> **SLO는 100%가 아니어야 한다.**\
> 100%를 목표로 하면 어떤 변경도 못 한다. "적절히 불안정해도 되는 예산"이 있어야 개발이 굴러간다.

### SLI 설계 요령

- **사용자 관점 지표**로 잡는다. "서버 CPU"가 아니라 "주문 성공률"
- **성공/실패를 분리**해서 지연을 측정 (→ [`08-deployment-ops.md`](./08-deployment-ops.md))
- 여러 엔드포인트를 하나로 뭉치면 중요한 실패가 희석된다 → 핵심 경로별로

## 2. 용량 산정 절차

### ① 피크를 기준으로 계산한다

```text
일 요청 1,000만 건
평균 RPS = 10,000,000 / 86,400 ≈ 116

하지만 실제 트래픽은 균등하지 않다.
피크 계수 3~5배 (일반 서비스) → 피크 RPS ≈ 350~580
이벤트/푸시 발송 시 10~50배까지 → 별도 고려
```

**평균으로 사이징하면 매일 피크마다 장애가 난다.**

> **피크 계수** — 평균 대비 피크 시점 트래픽의 배수. 사이징은 평균이 아니라 피크로 해야 한다.\
> 예: 평균 116 RPS라도 점심·저녁에 3\~5배 몰리면 피크는 350\~580 RPS — 여기에 맞춰야 매일 장애를 안 낸다.

### ② Little's Law로 동시성 계산

```text
필요 동시 처리 수 = 피크 RPS × 평균 응답 시간
  = 500 × 0.2초 = 100
     ↓
워커 스레드 100개 (또는 비동기로 100건 동시 진행)
     ↓
인스턴스당 스레드 50개면 최소 2대
```

(Little's Law 자체는 → [`01-scaling-principles.md`](./01-scaling-principles.md))

### ③ 헤드룸을 남긴다

| 목적 | 여유 |
|---|---|
| 노드 장애 대비 | (N−1)/N 이하 부하 (→ [`05-ha-topology.md`](./05-ha-topology.md)) |
| 배포 중 용량 감소 | rolling 시 일부 인스턴스 빠짐 |
| 오토스케일 반응 지연 | 스케일아웃에 1\~5분 걸림 |
| 예측 오차 | 20\~30% |

> 실무 목표: **평상시 CPU 40\~60%**. 80%로 운영하면 스파이크 때 여유가 없다.

> **헤드룸(headroom)** — 평상시 사용률과 한계 사이에 남겨 두는 여유. 장애·배포·스파이크·예측 오차를 흡수한다.

### ④ 데이터 증가도 계산한다

```text
일 1,000만 건 × 행당 1KB = 10GB/일 = 3.65TB/년
+ 인덱스 (보통 원본의 30~100%)
+ 복제본 수만큼 곱하기
```

**트래픽보다 데이터 크기에서 먼저 한계가 오는 경우가 많다.** 보관 정책을 처음부터 정한다.

## 3. 부하 테스트

| 종류 | 목적 | 방법 |
|---|---|---|
| **Load Test** | 목표 부하에서 SLO를 지키나 | 예상 피크로 일정 시간 |
| **Stress Test** | **어디서 무너지나** | 한계까지 올려 붕괴 지점과 붕괴 방식 확인 |
| **Soak Test** | 오래 버티나 | 수 시간\~일. **메모리 누수, 커넥션 누수** 발견 |
| **Spike Test** | 급증에 견디나 | 순간 10배 투입. 오토스케일 반응 검증 |
| **Capacity Test** | 인스턴스당 처리량 | 사이징 근거 확보 |

### 설계 요령

- **프로덕션과 유사한 데이터 크기**로. 빈 DB에서의 테스트는 무의미하다
- **캐시를 워밍하지 않은 상태**도 테스트 (콜드 스타트, 캐시 다운 시나리오)
- **읽기만이 아니라 쓰기 포함** 워크로드
- 병목이 부하 발생기 쪽이 아닌지 확인
- **결과에서 봐야 할 것**: 처리량이 아니라 **처리량이 꺾이는 지점과 그때의 p99**

### 붕괴 방식이 중요하다

같은 한계를 좋은/나쁜 붕괴로 대비하면:

```text
[나쁜 붕괴]                           [좋은 붕괴]
한계 초과                             한계 초과
   ↓                                   ↓
전부 느려지다가 타임아웃               일부를 빠르게 거절 (로드 셰딩)
   ↓                                   ↓
연쇄 실패, 복구도 안 됨                나머지는 정상, 부하 빠지면 회복
```

> 스트레스 테스트의 목적은 "한계 숫자"가 아니라 "**한계를 넘었을 때 어떻게 죽는지**"를 아는 것이다.

## 4. 오토스케일링

### 지표 선택이 핵심

| 지표 | 적합 |
|---|---|
| **CPU 사용률** | CPU 바운드 워크로드. **I/O 바운드에는 부적합** |
| **RPS / 인스턴스당 요청 수** | 웹 서버에 무난 |
| **큐 길이 / 소비 지연** | **비동기 워커에 가장 적합** |
| **동시 요청 수** | 응답 시간 편차가 클 때 |
| **p99 지연** | 사용자 체감에 직결. 반응이 늦을 수 있음 |

> I/O 대기가 많은 서비스는 CPU가 낮은데도 스레드가 고갈된다. **CPU 기준 오토스케일이 전혀 동작하지 않는다.**

### 함정

| 함정 | 설명 | 대응 |
|---|---|---|
| **반응 지연** | 인스턴스 시작\~준비까지 1\~5분 | 예측 스케일링, 여유 확보, 워밍 풀 |
| **콜드 스타트** | 새 인스턴스가 JIT/캐시 미준비로 느림 | 슬로우 스타트(LB ramp-up), 워밍업 |
| **플래핑** | 늘렸다 줄였다 반복 | 쿨다운, 스케일인 임계 낮게(비대칭) |
| **스케일인 위험** | 처리 중 요청이 끊김 | graceful shutdown, 드레이닝 |
| **하위 시스템 압사** | 앱은 늘었는데 **DB 커넥션이 폭증** | **커넥션 풀 총량 상한 = 인스턴스 수 × 풀 크기**를 DB 한계와 비교 |
| **상한 미설정** | 버그로 무한 확장 → 비용 폭발 | max 설정 필수 |

> **플래핑(flapping)** — 오토스케일이 늘렸다 줄였다를 짧게 반복하는 것. 쿨다운과 비대칭 임계로 막는다.

> **가장 자주 보는 사고: 앱 오토스케일이 DB를 죽인다.**\
> 인스턴스 50대 × 커넥션 20 = 1,000 커넥션. DB가 못 버틴다.\
> → 커넥션 풀 프록시(PgBouncer 등) 또는 인스턴스당 풀 크기 축소.

### 스케일링이 답이 아닌 경우

- **직렬 병목**(단일 DB 쓰기)이 원인이면 앱을 늘려도 무의미하고 오히려 악화
- **버그로 인한 부하**(무한 루프, N+1)면 스케일링은 돈만 태운다
- → **스케일링 전에 병목을 확인한다** (→ [`01-scaling-principles.md`](./01-scaling-principles.md))

## 5. 비용 축

확장성 논의에서 자주 빠지지만 실무에서는 중요하다.

| 수단 | 비용 특성 |
|---|---|
| 쿼리 최적화 | 개발 시간만. **가장 저렴** |
| 캐시 | 메모리 비용 < DB 증설 |
| 읽기 복제본 | 인스턴스 수만큼 선형 |
| 다중 AZ | 대략 2배 + AZ 간 전송 비용 |
| 다중 리전 | 2배 이상 + 리전 간 전송 비용(비쌈) |
| 오토스케일 | 피크 기준 상시 구성보다 저렴 |

> 아키텍처 결정에는 "**이 가용성 향상에 월 얼마를 쓸 것인가**"가 포함되어야 한다.\
> 무한 예산이 아니면 이게 실제 제약이다.

## 6. 체크리스트

- [ ] SLO가 사용자 관점 지표로 정의되어 있는가
- [ ] 에러 버짓이 실제 의사결정에 쓰이는가
- [ ] 피크 계수를 반영해 사이징했는가
- [ ] 노드 장애·배포 중 용량 감소를 감안한 헤드룸이 있는가
- [ ] 스트레스 테스트로 **붕괴 지점과 붕괴 방식**을 아는가
- [ ] 오토스케일 지표가 워크로드 성격에 맞는가
- [ ] 오토스케일 상한이 있고, **하위 시스템(DB 커넥션)이 견디는가**
- [ ] 데이터 증가율과 보관 정책이 있는가

---

## 핵심 문장

- **SLO는 100%가 아니어야 한다 — 에러 버짓이 있어야 개발이 굴러간다.**
- **SLI는 사용자 관점 지표로 — "CPU"가 아니라 "주문 성공률".**
- **사이징은 평균이 아니라 피크로 — 피크 계수를 반영하고 헤드룸을 남긴다.**
- **스트레스 테스트의 목적은 한계 숫자가 아니라 "어떻게 죽는가"를 아는 것.**
- **오토스케일 지표는 워크로드에 맞춰야(I/O 바운드에 CPU는 무용) — 그리고 상한과 DB 커넥션을 반드시 확인.**

---

## 용어 풀이

- **SLI** — 측정하는 지표(성공률·p99 등).
- **SLO** — SLI의 내부 목표치.
- **SLA** — 고객과의 계약. SLO보다 느슨.
- **에러 버짓(Error Budget)** — 허용된 실패량(1 − SLO). 안정성과 속도를 중재.
- **피크 계수** — 평균 대비 피크 트래픽 배수. 사이징 기준.
- **헤드룸(Headroom)** — 평상시 사용률과 한계 사이의 여유.
- **Load/Stress/Soak/Spike Test** — 목표 부하 / 붕괴 지점 / 장시간 / 급증 테스트.
- **콜드 스타트(Cold Start)** — 새 인스턴스가 캐시·JIT 미준비로 느린 초기 구간.
- **플래핑(Flapping)** — 스케일 인/아웃을 짧게 반복하는 것.
- **하위 시스템 압사** — 앱을 늘리자 DB 커넥션이 폭증해 DB가 죽는 것.
