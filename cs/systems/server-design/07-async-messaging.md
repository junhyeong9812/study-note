# 07. 비동기 · 메시징 아키텍처

> 비동기는 **결합도를 낮추고 부하를 평탄화**하지만, 대신 **순서·중복·지연·관측**이라는 새 문제를 산다.\
> "비동기로 바꿨습니다"는 그 자체로 개선이 아니라 **교환**이다.\
> 출처: `jun-bank/docs/study/notes/server-design/07-async-messaging.md` · 이관일 2026-09-16.\
> 원고 문체·순서 유지 + cs 형식(용어 풀이·세로 도식)만 입힘.

---

## 1. 언제 비동기로 가는가

| 상황 | 이유 |
|---|---|
| **응답에 결과가 필요 없다** | 알림 발송, 로그 적재, 통계 집계 |
| **처리 시간이 길다** | 영상 인코딩, 리포트 생성, 대량 메일 |
| **피크와 평균의 차이가 크다** | 큐가 완충 역할 → 서버를 피크 기준으로 안 사도 됨 |
| **여러 소비자가 같은 사실을 필요로 한다** | 주문 생성 → 재고·정산·알림·분석 |
| **상대 시스템의 가용성에 내 응답을 묶고 싶지 않다** | 외부 연동 |

### 언제 비동기로 가면 안 되는가

- **사용자가 결과를 즉시 봐야 할 때** (억지로 비동기화하면 폴링 지옥)
- **강한 정합성이 필요할 때**
- **디버깅 난이도를 감당할 팀 여력이 없을 때** ← 현실적으로 가장 중요

## 2. 큐 vs 로그 — 성질이 다르다

| | 메시지 큐 (RabbitMQ, SQS) | 로그 (Kafka, Pulsar) |
|---|---|---|
| 소비 후 | 삭제됨 | **보존됨** (기간/크기 기준) |
| 전달 | 브로커가 push, 메시지별 ack 추적 | 컨슈머가 pull, **오프셋만** 관리 |
| 재처리 | 어려움 (이미 지워짐) | **오프셋 되감기로 자유롭게** |
| 소비자 수 | 경쟁 소비 (한 명이 가져감) | 여러 컨슈머 그룹이 **각자 전체를 읽음** |
| 순서 | 보장 어려움 | 파티션 내 보장 |
| 적합 | 작업 분배(task queue), 지연 큐, 우선순위 | 이벤트 스트림, 다중 소비자, 재처리 |

> **큐 vs 로그** — 큐는 소비하면 메시지가 사라지고(작업 분배), 로그는 소비해도 남아 오프셋만 옮긴다(재처리·다중 소비 가능).\
> 예: 이메일 발송 작업은 한 명이 가져가 처리하면 되니 큐, "주문 생성됨" 이벤트는 재고·정산·알림이 각자 읽어야 하니 로그.

> **오프셋(offset)** — 로그에서 컨슈머가 어디까지 읽었는지 가리키는 위치 번호. 되감으면 재처리가 된다.

> **선택 기준: "나중에 다시 읽어야 하나?"**\
> 재처리·신규 소비자 추가·감사가 필요하면 로그. 단순 작업 분배면 큐가 더 단순하다.

---

## 3. 큐는 해결책이 아니라 완충이다

**가장 흔한 오해**: "큐를 넣었으니 부하를 견딜 수 있다."

```text
유입 100/s, 처리 50/s
   ↓
큐가 초당 50개씩 무한히 쌓임
   ↓
큐는 터지지 않지만 지연이 무한히 증가
   ↓
사용자 입장에서는 "동작하지 않는 것"과 같다
```

**큐는 순간 피크를 흡수할 뿐, 평균 유입 > 평균 처리면 아무것도 해결하지 못한다.**

### 반드시 봐야 할 지표

| 지표 | 의미 |
|---|---|
| **큐 길이** | 절대값만으로는 부족 |
| **소비 지연 (consumer lag)** | Kafka: 최신 오프셋 − 커밋 오프셋 |
| **메시지 나이 (age of oldest message)** | **가장 중요.** "지금 넣으면 언제 처리되나" |
| 처리율 / 유입률 | 둘의 비교가 추세를 알려줌 |

> **소비 지연(consumer lag)** — 로그의 최신 위치와 컨슈머가 처리한 위치의 차이. 컨슈머가 얼마나 뒤처졌는지를 나타낸다.\
> 예: 최신 오프셋이 1000, 커밋된 오프셋이 700이면 lag은 300 — 300건이 아직 처리 안 됐다.

> **알림은 큐 길이가 아니라 "가장 오래된 메시지의 나이"에 건다.**\
> 큐 길이 10,000은 처리율에 따라 1초일 수도 1시간일 수도 있다.

### 백프레셔

큐가 무한히 쌓이게 두지 않는다.

- 큐 크기 상한 → 초과 시 생산자에게 거부 응답
- 생산 측 레이트 리밋
- 오토스케일링을 **소비 지연 기준**으로 (CPU 기준으로 하면 대응이 늦다)

## 4. 순서 보장과 병렬성의 충돌

**근본 트레이드오프: 순서를 지키려면 직렬화해야 하고, 직렬화하면 확장이 안 된다.**

### 해법: 순서가 필요한 범위만 직렬화

```text
파티션 키 = 주문 ID
   ↓
같은 주문의 이벤트는 항상 같은 파티션 → 순서 보장
   ↓
다른 주문끼리는 병렬 처리
```

> **파티션 키(partition key)** — 메시지를 어느 파티션에 넣을지 정하는 값. 같은 키는 같은 파티션 → 그 안에서 순서 보장.\
> 예: 파티션 키를 주문 ID로 잡으면 한 주문의 이벤트는 순서대로, 서로 다른 주문은 병렬로 처리된다.

**설계 포인트**

- 파티션 키는 **순서가 필요한 최소 단위**로 잡는다. 너무 크면(예: 전체를 한 파티션) 확장 불가, 너무 작으면 순서가 깨짐
- **파티션 수는 늘리기는 쉬워도 줄이기 어렵다.** 그리고 파티션 수를 늘리면 기존 키의 배치가 바뀌어 **순서가 일시적으로 깨진다**
- **컨슈머 수 ≤ 파티션 수** (Kafka). 파티션보다 컨슈머가 많으면 노는 컨슈머가 생긴다

### 순서를 포기하는 설계가 더 나을 때

- **이벤트에 버전/타임스탬프를 넣고, 낡은 이벤트는 무시**한다 (`WHERE version < :new`)
- **상태 전이가 아니라 최종 상태를 보낸다** (이벤트가 멱등해짐)

> 순서 의존성을 없애는 게, 순서를 보장하는 것보다 확장성 면에서 훨씬 낫다.

## 5. 전달 보장과 멱등성

| 보장 | 의미 | 현실 |
|---|---|---|
| At-most-once | 중복 없음, **유실 가능** | 거의 안 씀 |
| **At-least-once** | 유실 없음, **중복 가능** | **사실상 표준** |
| Exactly-once | 정확히 한 번 | 외부 시스템이 끼면 사실상 불가 |

> **at-least-once** — 유실은 없지만 중복은 생길 수 있는 전달 보장. 그래서 소비 측이 멱등해야 한다.\
> 예: ack 직전 컨슈머가 죽으면 브로커가 같은 메시지를 다시 보내므로, 같은 메시지가 두 번 처리될 수 있다.

**결론: at-least-once + 멱등 소비.**\
자세한 내용은 별도 주제(컨슈머 실패 처리·오프셋 커밋, 이중 쓰기 문제·아웃박스 — 이 컬렉션 밖) 참고.

### 멱등성 확보 3가지 방법

1. **인박스 테이블**: 처리한 메시지 ID를 유니크 제약으로 기록
2. **멱등한 비즈니스 로직**: `UPDATE ... WHERE status = 'PENDING'`, upsert
3. **버전 체크**: 이벤트 버전이 현재보다 낮으면 무시

> **인박스(inbox) 테이블** — 이미 처리한 메시지 ID를 유니크 제약으로 기록해, 같은 메시지의 재처리를 막는 것.

## 6. 실패 처리 구조

```text
main-topic ─실패─▶ retry-1s ─▶ retry-10s ─▶ retry-1m ─▶ DLQ/DLT
```

**필수 원칙**

- **영구 실패(역직렬화 오류, 검증 실패)는 재시도하지 않고 즉시 DLQ로.** 안 그러면 poison pill이 파티션을 막는다
- **DLQ에 알림을 건다.** 조용히 쌓이는 DLQ는 유실과 같다
- **재처리(replay) 수단을 미리 만든다.** DLQ는 종착지가 아니라 대기소
- **재시도 토픽은 순서를 깨뜨린다.** 순서가 중요하면 못 쓴다

> **DLQ(Dead Letter Queue)** — 정상 처리에 반복 실패한 메시지를 따로 모아 두는 큐. 파티션을 막지 않게 격리하는 곳.\
> 예: 역직렬화가 안 되는 메시지를 계속 재시도하면 그 파티션이 막히므로, 즉시 DLQ로 보내고 나머지를 계속 처리한다.

> **poison pill** — 처리하려 할 때마다 실패해서 뒤 메시지 처리를 막아 버리는 메시지.

## 7. 스케줄러·배치의 HA (자주 빠뜨리는 부분)

**인스턴스를 N대로 늘리면 스케줄러가 N번 실행된다.**

같은 상황을 실패/방어로 대비하면:

```text
[인메모리 스케줄러 + 3대]            [DB 락 / 리더 선출]
매일 자정 정산 배치                   매일 자정 정산 배치
   ↓                                   ↓
3대가 각자 실행                       실행 전 락 획득 시도
   ↓                                   ↓
정산이 3번 → 3배 지급 사고             락 잡은 1대만 실행, 나머지 스킵
```

| 해법 | 방식 | 특징 |
|---|---|---|
| **DB 락 기반** | 실행 전 락 획득 시도, 실패하면 스킵 (ShedLock 등) | 단순, 추가 인프라 불필요 |
| **리더 선출** | ZooKeeper/etcd/Redis로 리더만 실행 | 여러 작업에 재사용 가능 |
| **전용 스케줄러 서비스** | 스케줄러를 별도 배포 단위로 (인스턴스 1대) | 단순하지만 SPOF |
| **분산 스케줄러** | Quartz 클러스터, Temporal, Airflow | 기능 풍부, 운영 비용 |
| **스케줄 → 메시지** | 스케줄러는 메시지만 발행, 처리는 컨슈머가 | **스케줄러는 가볍게, 처리는 확장 가능** ← 권장 |

### 배치가 서비스를 죽이는 문제

새벽 배치가 DB를 점유해서 실시간 요청이 느려지는 것은 매우 흔하다.

- 읽기 전용 배치는 **복제본에서** 실행
- 대량 쓰기는 **청크로 나누고 사이에 쉬는 시간**을 둔다 (한 트랜잭션에 100만 건 금지)
- 배치 전용 커넥션 풀 (벌크헤드)
- 우선순위·리소스 그룹 분리

## 8. 비동기의 관측성 (난이도의 핵심)

동기 호출은 스택 트레이스가 있지만 **비동기는 흐름이 끊긴다.**

- **상관관계 ID(correlation/trace id)를 메시지 헤더에 전파**한다. 이게 없으면 장애 추적이 불가능
- 이벤트 계보 추적: 이 이벤트가 어디서 나와서 어디까지 갔나
- **종단 지연 측정**: 발생 시각을 이벤트에 넣고, 최종 처리 시점과의 차이를 지표로
- 소비 지연, DLQ 유입, 재시도 횟수를 대시보드에

> **상관관계 ID(correlation ID)** — 하나의 요청·흐름에 붙여 모든 로그·메시지에 함께 실어 보내는 식별자. 끊긴 비동기 흐름을 이어 준다.\
> 예: 주문 요청에 ID를 붙여 이벤트 헤더로 계속 전파하면, 재고·정산·알림 로그를 그 ID로 한 줄에 꿸 수 있다.

## 9. 체크리스트

- [ ] 평균 유입 < 평균 처리 능력인가 (큐는 피크만 흡수한다)
- [ ] 알림이 큐 길이가 아니라 **메시지 나이**에 걸려 있는가
- [ ] 모든 큐가 유한하고 백프레셔가 있는가
- [ ] 파티션 키가 순서 필요 범위와 일치하는가
- [ ] 소비가 멱등한가
- [ ] 영구 실패가 즉시 DLQ로 가는가
- [ ] DLQ에 알림과 재처리 수단이 있는가
- [ ] 스케줄러가 다중 인스턴스에서 중복 실행되지 않는가
- [ ] 배치가 실시간 트래픽의 자원을 뺏지 않는가
- [ ] trace id가 메시지를 통해 전파되는가

---

## 핵심 문장

- **비동기는 개선이 아니라 교환 — 결합·부하를 낮추고 순서·중복·지연·관측을 산다.**
- **큐는 완충일 뿐 — 평균 유입 > 평균 처리면 지연만 무한히 는다.**
- **알림은 큐 길이가 아니라 "가장 오래된 메시지의 나이"에 건다.**
- **at-least-once + 멱등 소비가 표준 — Exactly-once는 외부 시스템이 끼면 사실상 불가.**
- **순서를 보장하기보다 순서 의존성을 없애는 게 확장에 낫다(버전 필드로 낡은 이벤트 무시).**

---

## 용어 풀이

- **큐 vs 로그** — 소비하면 사라지는 큐(작업 분배) / 소비해도 남는 로그(재처리·다중 소비).
- **오프셋(Offset)** — 로그에서 컨슈머가 읽은 위치. 되감으면 재처리.
- **소비 지연(Consumer Lag)** — 최신 오프셋과 처리 오프셋의 차이.
- **메시지 나이(Age of Oldest Message)** — 가장 오래된 미처리 메시지의 대기 시간.
- **파티션 키(Partition Key)** — 메시지를 어느 파티션에 넣을지 정하는 값. 순서 보장 단위.
- **at-least-once** — 유실 없음·중복 가능. 소비 측 멱등성 필요.
- **인박스(Inbox)** — 처리한 메시지 ID를 유니크 제약으로 기록해 재처리를 막는 테이블.
- **DLQ(Dead Letter Queue)** — 반복 실패 메시지를 격리하는 큐.
- **poison pill** — 처리 때마다 실패해 뒤를 막는 메시지.
- **상관관계 ID(Correlation ID)** — 흐름을 잇기 위해 모든 로그·메시지에 싣는 식별자.
