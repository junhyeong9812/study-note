# systems/postgres-rls — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: 개인 학습 노트 「PostgreSQL RLS」 · 이관일 2026-09-16.\
> 본문 절들(왜 필요한가·기본 사용법·커넥션 풀 함정·평가 비용·ORM 이중 방어선·검증)은 **원고**를 고쳐 쓴 것이다(문체·순서·SQL/코드 유지).\
> 원고의 예시 테이블·롤 이름은 이미 일반적(orders·tenant_id)이라 그대로 두었다.\
> 「한눈에」의 우편 분류 비유는 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**RLS(Row-Level Security)** = **`WHERE tenant_id = ?`를 빼먹은 쿼리도 DB가 대신 걸러 준다.**\
애플리케이션의 실수를 데이터베이스가 최종 방어하는 구조다.

> **RLS(Row-Level Security)** — 테이블에 정책을 걸어, 세션의 주체 정보를 기준으로 행을 자동으로 걸러 주는 DB 기능.\
> 예: 세션에 `tenant_id=42`를 심어 두면, 개발자가 `SELECT * FROM orders`를 그냥 날려도 DB가 42의 행만 돌려준다.

---

## 한눈에 — 쉽게 말하면

**우편물을 자동으로 걸러 건네는 분류기**를 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
큰 우편함 하나에 전 직원의 편지가 섞여 있다
+-------------------------------------------+
| 내가 "내 편지 줘"라고 하면 → 내 것만 준다      |  ← USING: 이 행이 보이는가
| 내가 실수로 "전부 줘"라고 해도 → 내 것만 준다   |  ← 조건을 빼먹어도 DB가 막는다
| 남의 이름으로 편지를 넣으려 하면 → 거절         |  ← WITH CHECK: 이 행을 써도 되는가
| 단, 우체국장(슈퍼유저)은 분류기를 건너뛴다      |  ← 우회 가능한 주체 존재
+-------------------------------------------+
```

**RLS도 똑같은 구조다.** 한 테이블에 모든 테넌트의 행이 섞여 있어도, DB가 세션의 주체를 보고 자동으로 걸러 준다. 개발자가 `WHERE` 조건을 빼먹어도 막고(USING), 남의 테넌트로 쓰려는 것도 막는다(WITH CHECK). 다만 슈퍼유저 같은 예외 주체는 분류기를 건너뛴다.

쉽게 말하면 이렇다.\
**격리를 "코드의 주의력"에서 "DB의 강제"로 옮기는 장치다.** 코드 리뷰로 모든 쿼리의 `WHERE tenant_id`를 100% 지킬 수는 없으니, 하나가 빠져도 새지 않게 DB에 최종 방어선을 둔다. 대신 그 방어선에는 함정이 둘 있다 — **커넥션 풀에 남는 세션 변수**와 **모든 쿼리에 붙는 정책 평가 비용**.

## 문제 — 이 개념이 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(운영·보안 개념 정리다). 대신 네 개의 질문에 답한다.

```text
1. 왜 필요한가    "코드로만 격리하면 무엇이 잘못되나?"
2. 어떻게 거나     "USING / WITH CHECK — 둘 중 하나만 걸면 어디가 뚫리나?"
3. 무엇이 위험한가  "커넥션 풀에서 세션 변수가 왜 유출을 만드나?"
4. 성능은 어떤가   "정책이 모든 쿼리에 붙으면 무엇을 조심하나?"
```

아래 서머리는 이 네 질문을 하나씩 분석·정리한 것이다.

## 전체 흐름

한 요청이 테넌트를 확정하고, 두 방어선을 통과하는 경로다.

```text
요청 도착
   ↓
인터셉터에서 tenant_id 확정        누구의 요청인지 정한다
   ↓
트랜잭션 시작 + SET LOCAL 주입      세션 변수에 tenant_id 를 심는다 (트랜잭션 범위)
   ↓
   ├─▶ ORM 필터 (성능 + 1차 방어)   인덱스를 타게 조건을 붙여 준다
   └─▶ DB RLS   (최종 방어, 우회 불가) 조건이 빠져도 DB가 행을 거른다
   ↓
트랜잭션 종료 → SET LOCAL 자동 복원   커넥션 반납 시 값이 남지 않는다
```

- 핵심은 마지막 줄이다 — 세션 변수가 트랜잭션 범위여야 커넥션 재사용 시 이전 테넌트 값이 남지 않는다.

## 왜 필요한가

> 출처: 개인 학습 노트 「PostgreSQL RLS」 — §1

**언제 쓰나** — 여러 테넌트를 한 테이블에 담기로(행 단위 격리) 했을 때. 격리를 코드에만 맡길지 판단하는 자리다.

멀티테넌시에서 테넌트 격리를 애플리케이션 코드에만 맡기면, **개발자가 조건 하나를 빠뜨리는 순간 다른 회사 데이터가 노출된다.** 코드 리뷰로 100% 막을 수 없다.

**전/후 대비 — 방어선을 어디에 두나**

```text
애플리케이션 레벨 방어만                DB 레벨 방어(RLS) 추가
+---------------------------+         +---------------------------+
| 조건을 개발자가 매번 넣는다    |         | 쿼리가 어떻게 생겼든         |
| 하나 빠뜨리면 유출           |         |   정책이 강제 적용          |
| 유출 시 전체 테넌트 노출       |         | 조건이 빠져도 DB가 거른다     |
|   (최악의 사고 유형)          |         |                           |
+---------------------------+         +---------------------------+
  → 주의력에 의존              → 구조가 막는다 (단, 함정 둘 아래)
```

**비용** — RLS는 공짜가 아니다. 모든 쿼리에 정책 조건이 붙고(§4), 커넥션 풀에서 세션 변수를 잘못 다루면 오히려 유출을 만든다(§3).

## 기본 사용법 — USING vs WITH CHECK

> 출처: 개인 학습 노트 「PostgreSQL RLS」 — §2

**언제 쓰나** — 정책을 실제로 걸 때. 두 절을 헷갈리면 구멍이 난다.

```sql
-- 1) 테이블에 RLS 켜기 (이것만으로는 정책이 없어 아무것도 안 보임 = deny by default)
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 2) 테이블 소유자에게도 적용 (이걸 빼면 소유자 계정은 정책을 우회한다)
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

-- 3) 정책 생성
CREATE POLICY tenant_isolation ON orders
  USING      (tenant_id = current_setting('app.tenant_id', true)::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::bigint);
```

```text
절            적용 대상                          의미
────────────────────────────────────────────────────────────
USING         SELECT · UPDATE · DELETE의 읽는 행   "이 행이 보이는가"
WITH CHECK    INSERT · UPDATE의 쓰는 결과 행       "이 행을 써도 되는가"
```

> **둘 중 하나만 걸면 구멍이 난다**: `USING`만 있으면 남의 테넌트 ID로 INSERT가 가능하고, UPDATE로 `tenant_id`를 남의 값으로 바꿔 데이터를 넘겨줄 수도 있다.

### 요청마다 세션 변수 주입

```sql
SET LOCAL app.tenant_id = '42';   -- 트랜잭션 범위
```

> **deny by default** — RLS를 켜기만 하고 정책을 안 만들면 아무 행도 안 보이는 기본값.\
> 예: `ENABLE`만 하고 `CREATE POLICY`를 안 하면 그 테이블은 통째로 비어 보인다. 안전하지만 실수하면 서비스가 멈춘다.

**비용** — 두 절을 다 걸어야 읽기·쓰기 양쪽이 막힌다. 하나만 걸면 나머지 방향이 뚫린다.

## 함정 ① 커넥션 풀에서의 세션 변수 관리

> 출처: 개인 학습 노트 「PostgreSQL RLS」 — §3

**언제 쓰나** — 커넥션 풀을 쓸 때(즉 거의 항상). **가장 위험한 부분이다.**

커넥션은 재사용되므로, **직전 요청의 tenant_id가 남아 있으면 그대로 다른 테넌트의 데이터가 보인다.**

```text
방법                                  범위                      안전성
──────────────────────────────────────────────────────────────────────
SET app.tenant_id = ...               세션 전체 — 반납 후에도 남음   위험
SET LOCAL app.tenant_id = ...         트랜잭션 종료 시 자동 복원      권장
set_config('app.tenant_id', v, true)  세 번째 인자 true = local     권장
```

### 반드시 지킬 규칙

- **`SET LOCAL`은 트랜잭션 안에서만 유효하다.**\
  트랜잭션 밖에서 실행하면 조용히 무시되고 경고만 뜬다 → 정책이 빈 값으로 평가되어 **아무것도 안 보이거나(운 좋음), 설정 방식에 따라 잘못 보인다(운 나쁨).**
- **트랜잭션 풀링과 반드시 같이 갈 것.**\
  세션 풀링이 아닌 트랜잭션 풀링에서는 세션 레벨 `SET`이 커넥션 재사용 시 뒤섞인다. `SET LOCAL`만 쓰면 안전하다.
- **커넥션 획득 시점에 자동 주입.**\
  프레임워크의 커넥션 준비 훅·트랜잭션 시작 리스너에서 강제 주입한다. 개발자가 매번 호출하게 하면 결국 빠뜨린다.
- **`current_setting`의 두 번째 인자 `true`(missing_ok).**\
  변수 미설정 시 예외 대신 NULL을 반환한다. NULL과의 비교는 항상 false → 아무 행도 안 보임 = **fail-closed**.\
  이게 안전한 기본값이다. 반대로 `true`를 빼면 예외가 나서 원인을 빨리 찾을 수 있다.\
  **정책상 fail-closed가 낫지만 조용한 빈 결과는 디버깅이 어렵다** — 팀 규칙으로 정할 것.

> **fail-closed(안전하게 닫힘)** — 설정이 없거나 오류가 나면 "다 막힘" 쪽으로 떨어지는 것. 반대는 fail-open(다 열림).\
> 예: tenant_id가 안 심겼을 때 아무 행도 안 보이면 fail-closed(안전), 전체가 보이면 fail-open(유출).

### 우회 가능한 주체 (기억할 것)

- **슈퍼유저**와 `BYPASSRLS` 속성을 가진 롤은 RLS를 무시한다.
- `FORCE ROW LEVEL SECURITY`를 안 걸면 **테이블 소유자**도 무시한다.
- → **애플리케이션은 반드시 소유자가 아닌 전용 롤로 접속해야 한다.** 마이그레이션 계정과 런타임 계정을 분리한다.

**비용** — `SET LOCAL`은 안전하지만 트랜잭션을 반드시 열어야 하고, 자동 주입 훅을 프레임워크에 심는 초기 배선이 필요하다.

## 함정 ② 정책 평가 비용

> 출처: 개인 학습 노트 「PostgreSQL RLS」 — §4

**언제 쓰나** — RLS를 켠 뒤 쿼리가 느려졌을 때. 정책은 **모든 쿼리에 추가되는 조건(qual)**이라 성능에 영향을 준다.

주의점 다섯.

- **정책 표현식은 단순하게.**\
  정책 안에 서브쿼리(`tenant_id IN (SELECT ...)`)를 쓰면 행마다 평가되며 성능이 급락할 수 있다. 세션 변수 비교가 가장 싸다.
- **`current_setting()`은 STABLE 함수**라 쿼리당 한 번 평가된다.\
  타입 캐스팅(`::bigint`)을 명시해야 인덱스를 제대로 탄다 — text와 bigint 비교로 남으면 인덱스를 못 쓸 수 있다.
- **인덱스 설계**: `tenant_id`가 사실상 모든 쿼리의 필수 조건이 되므로, **복합 인덱스의 선두 컬럼**에 `tenant_id`를 넣는다(`(tenant_id, created_at)` 등).
- **leakproof 문제**: RLS 테이블에서는 보안상 정책 조건이 다른 조건보다 먼저 평가되도록 플래너가 제약된다.\
  `LEAKPROOF`가 아닌 함수를 쓴 조건은 뒤로 밀려 예상보다 나쁜 실행 계획이 나올 수 있다 → **RLS 적용 전후로 `EXPLAIN ANALYZE`를 비교하는 습관.**
- **파티셔닝과 상성이 좋다**: `tenant_id`가 정책 조건이자 파티션 키면 프루닝이 같이 먹는다.

> **qual(조건절)** — 쿼리 플래너가 행을 걸러내는 데 쓰는 조건식. RLS 정책은 모든 쿼리에 이 qual을 하나 더 붙인다.\
> 예: `SELECT * FROM orders`가 실제로는 `... WHERE tenant_id = current_setting(...)`로 실행된다.

**비용** — 정책 표현식이 무거우면(서브쿼리·비-leakproof 함수) 모든 쿼리가 그 비용을 문다. 단순 세션 변수 비교 + 선두 인덱스가 표준 답이다.

## 이중 방어선 — ORM 레벨 (Hibernate)

> 출처: 개인 학습 노트 「PostgreSQL RLS」 — §5

**언제 쓰나** — RLS만으로 부족할 때. RLS는 최종 방어선일 뿐, **성능(인덱스 활용)과 계층 방어**를 위해 앱에서도 조건을 넣는다.

### `@TenantId` (Hibernate 6+)

```java
@Entity
public class Order {
    @Id Long id;

    @TenantId
    private Long tenantId;   // 조회 시 자동 필터, 저장 시 자동 주입
}
```

`CurrentTenantIdentifierResolver`가 요청마다 현재 테넌트를 알려주면, Hibernate가 알아서 조건을 붙이고 채워 넣는다.

### `@Filter` (더 범용적, 조건을 직접 정의)

```java
@Entity
@FilterDef(name = "tenantFilter",
           parameters = @ParamDef(name = "tenantId", type = Long.class))
@Filter(name = "tenantFilter", condition = "tenant_id = :tenantId")
public class Order { ... }
```
```java
session.enableFilter("tenantFilter").setParameter("tenantId", ctx.tenantId());
```

> **`@Filter`의 한계 (반드시 알아둘 것)**
> - **`session.get()` / `findById()`에는 적용되지 않는다** (1차 캐시 조회는 필터를 안 탄다).
> - 네이티브 쿼리에도 적용되지 않는다.
> - → 그래서 **RLS가 최종 방어선으로 여전히 필요하다.**

**전/후 대비 — 왜 둘 다 필요한가**

```text
ORM 필터만                           RLS만
+---------------------------+        +---------------------------+
| 인덱스를 타 성능 좋음        |        | 우회 불가 (최종 방어)        |
| findById·네이티브에 안 걸림 |        | 인덱스·계획이 나빠질 수 있음  |
|  → 구멍이 남는다            |        | 조건이 앱에 안 보임          |
+---------------------------+        +---------------------------+
        → 둘을 겹쳐야 성능과 보안을 동시에 얻는다
```

**비용** — 방어선을 둘 유지하는 만큼 배선이 늘지만, `@Filter`가 `findById`에 안 걸리는 구멍을 RLS가 메우므로 하나로는 부족하다.

## 검증 체크리스트

> 출처: 개인 학습 노트 「PostgreSQL RLS」 — §6

```text
[ ] 애플리케이션 롤이 테이블 소유자가 아니고 BYPASSRLS 가 없는가
[ ] FORCE ROW LEVEL SECURITY 가 걸려 있는가
[ ] USING 과 WITH CHECK 가 둘 다 있는가
[ ] SET LOCAL 을 트랜잭션 안에서 쓰는가 (밖에서 쓰면 무시됨)
[ ] 세션 변수 미설정 시 동작이 정의돼 있는가 (fail-closed 확인)
[ ] 테스트: 테넌트 A 컨텍스트로 B의 행 조회/수정/삭제/삽입 4종 모두 실패하는가
[ ] RLS 적용 전후 주요 쿼리의 실행 계획이 나빠지지 않았는가
```

> 검증의 핵심은 마지막 두 줄이다 — **"옆집 테넌트로 4종 연산이 전부 거절되는가"를 전수 시험**하고, 실행 계획 회귀를 함께 본다.

---

## 한 문단 요약 (면접용)

> RLS는 테이블에 정책을 걸어, 애플리케이션이 조건을 빠뜨려도 DB가 행을 걸러 주는 최종 방어선이다. 요청마다 `SET LOCAL`로 세션 변수에 tenant_id를 넣고 정책이 그걸 비교하는 구조인데, 함정이 두 개다. 하나는 커넥션 풀 — 세션 스코프 `SET`을 쓰면 커넥션 재사용 시 이전 테넌트 값이 남아 유출된다. 그래서 트랜잭션 스코프인 `SET LOCAL`을 쓰고, 커넥션 획득 시점에 자동 주입한다. 다른 하나는 성능 — 정책이 모든 쿼리의 조건으로 붙으므로 표현식을 단순하게 유지하고 tenant_id를 복합 인덱스 선두에 둔다. 그리고 RLS만 믿지 않고 Hibernate `@TenantId`/`@Filter`로 ORM 레벨 방어선을 하나 더 둔다. `@Filter`는 `findById`에 안 걸리기 때문에 둘 다 필요하다.

---

## 핵심 문장

- **RLS는 격리를 "코드의 주의력"에서 "DB의 강제"로 옮긴다 — WHERE를 빼먹어도 막는다.**
- **USING(읽는 행)과 WITH CHECK(쓰는 행)는 둘 다 걸어야 한다 — 하나만 걸면 반대 방향이 뚫린다.**
- **최대 함정은 커넥션 풀이다 — `SET LOCAL`(트랜잭션 범위)이 아니면 이전 테넌트 값이 남아 샌다.**
- **`current_setting(..., true)`는 미설정 시 NULL → 아무 행도 안 보임(fail-closed)이 안전한 기본값이다.**
- **RLS는 최종 방어선일 뿐 — ORM 필터가 `findById`에 안 걸리는 구멍을 메우려 둘을 겹친다.**

## 용어 풀이

- **RLS(Row-Level Security)** — 세션 주체 기준으로 행을 자동으로 걸러 주는 DB 기능.
- **정책(policy)** — RLS에서 "어떤 행이 보이고 써도 되는가"를 정하는 규칙. `CREATE POLICY`로 만든다.
- **USING / WITH CHECK** — 각각 "읽는 행이 보이는가" / "쓰는 행을 써도 되는가"를 정하는 정책 절.
- **deny by default** — RLS를 켜고 정책이 없으면 아무 행도 안 보이는 기본값.
- **SET LOCAL** — 트랜잭션 범위로만 유효한 세션 변수 설정. 커넥션 반납 시 자동 복원.
- **트랜잭션 풀링 / 세션 풀링** — 커넥션 풀러가 커넥션을 트랜잭션 단위 / 세션 단위로 재사용하는 방식.
- **fail-closed / fail-open** — 오류·미설정 시 각각 "다 막힘" / "다 열림"으로 떨어지는 것.
- **BYPASSRLS** — RLS를 무시하는 롤 속성. 슈퍼유저·이 속성 롤·(FORCE 없으면)소유자가 우회 주체.
- **qual(조건절)** — 플래너가 행을 거르는 조건식. RLS는 모든 쿼리에 정책 qual을 붙인다.
- **STABLE 함수** — 한 쿼리 안에서 값이 안 변해 쿼리당 한 번만 평가되는 함수(`current_setting` 등).
- **LEAKPROOF** — 조건 평가가 값을 새어 나가게 하지 않음이 보장된 함수. RLS의 조건 평가 순서에 영향.
- **`@TenantId` / `@Filter`** — Hibernate에서 테넌트 조건을 자동으로 붙이는 두 방식. 후자는 `findById`에 안 걸린다.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **RLS는 정책이 여러 개면 OR로 합쳐진다(기본 PERMISSIVE).** 같은 명령에 대해 PERMISSIVE 정책이 둘이면 둘 중 하나만 통과해도 보인다. AND로 좁히려면 `RESTRICTIVE` 정책을 써야 한다 — 정책을 여러 개 얹을 때 "왜 다 보이지"의 흔한 원인이다.
- **`current_setting`의 커스텀 변수는 반드시 점(.)이 있어야 한다.** `app.tenant_id`처럼 `<네임스페이스>.<이름>` 꼴이어야 Postgres가 사용자 정의 파라미터로 받는다. 점 없는 이름은 예약 파라미터로 취급돼 거부된다.
- **RLS는 뷰·함수 경계에서 새기 쉽다.** `SECURITY DEFINER` 함수 안에서 테이블을 읽으면 함수 소유자 권한으로 돌아 정책이 우회될 수 있다. 뷰도 뷰 소유자 기준으로 평가될 수 있어, RLS를 건 테이블 위에 뷰·함수를 올릴 때는 그 소유자와 `security_barrier` 설정을 함께 봐야 한다.
- **애플리케이션 계정 분리는 RLS만의 문제가 아니다.** "런타임 계정은 소유자·슈퍼유저가 아니어야 한다"는 최소권한 원칙 그 자체다. RLS는 이 원칙을 안 지키면 통째로 무력화되므로, 계정 분리가 RLS의 전제 조건이 된다.
