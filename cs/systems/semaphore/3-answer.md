## 정답

<!-- 1-question.md 의 번호와 1:1 대응. 질문 하나 = A 하나. -->

1. 동시에 자원을 쓸 수 있는 개수를 세는 카운터다 — 자리가 남으면 들여보내며 -1, 나갈 때 +1, 0이면 막는다. 카운터가 1이면 "한 번에 한 명"이라 **뮤텍스**(상호배제)와 사실상 같고, N>1이면 **counting semaphore**라 부른다.

> **뮤텍스(mutex)** — 한 번에 하나만 들어가는 자물쇠. 세마포어에서 N=1인 특수 경우.

2. 포화(카운터 0) 시 두 가지다.
   - **줄 세우기(대기)**: 자리가 날 때까지 기다리게 한다. 반드시 처리돼야 하는 작업, 잠깐 기다리면 되는 상황에 맞다(기본 동작).
   - **즉시 거절(503)**: "지금 만석"이라고 바로 돌려보낸다. 기다림이 오히려 손해거나, 실패해도 대안이 있는 경우에 맞다.

3. 자원(GPU·DB 커넥션·외부 API 호출권)은 유한하다. 상한 없이 받으면 요청이 몰릴 때 모든 요청이 자원을 조금씩 나눠 쓰며 **다 같이 느려지다 함께 죽는다**. 세마포어는 "수용량은 N"을 코드로 못 박아, N+1번째부터는 빠르게 실패시키거나 대기시켜 **이미 들어온 것들은 정상 속도를 지키게** 한다.

4. llm 래퍼는 GPU 1장이라 `Semaphore(2)`로 동시 2건까지만 받고, 3번째는 `sem.locked()` 확인 후 **즉시 503**을 던진다(줄을 안 세운다). 근거: **검색은 LLM(rewrite) 없이도 동작한다** — rewrite가 바쁘면 키워드 검색으로 폴백하면 그만이다. 그러니 사용자를 줄 세워 몇 초 기다리게 하는 것보다 "바쁘다"고 7.7ms 만에 알려주고 폴백 경로로 보내는 쪽이 전체 경험이 낫다. **폴백이 있으면 대기보다 빠른 거절**이 옳다.

   > **폴백(fallback)** — 주 경로가 안 되면 품질이 낮아도 동작하는 대체 경로. 여기선 rewrite 없는 순수 키워드 검색.

5. `async with sem:` 은 블록을 빠져나갈 때 — **예외로 빠져나가도** — 카운터를 자동으로 +1 반납한다. 이걸 손으로 하면 예외 경로에서 반납을 빼먹기 쉽고, 그러면 카운터가 영구히 줄어 결국 아무도 못 들어오는 상태(자원 누수)가 된다. 그리고 대기를 허용하기로 했다면 **대기열 길이 자체에도 상한**이 필요하다 — 안 그러면 줄이 무한정 길어져 메모리와 지연이 함께 터진다.
