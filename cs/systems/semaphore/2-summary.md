# cs/semaphore — 세마포어: 동시에 몇 명까지 — 정리 (힌트)

## 해결하는 문제

### 한 줄

**동시에 자원을 쓸 수 있는 개수를 세는 카운터.** 자리가 남으면 들여보내고(카운터 -1), 다 차면 못 들어오게 한다. 나갈 때 카운터 +1.

### 왜 필요한가

자원(GPU, DB 커넥션, 외부 API 호출권)은 무한하지 않다. 제한 없이 받으면
요청이 몰릴 때 전부 느려지다 같이 죽는다. 세마포어는 "우리 가게 수용량은 N"을
코드로 못박는 장치다.

- 카운터가 1이면 = 한 번에 한 명만 = **뮤텍스**(mutex, 상호배제 자물쇠)와 사실상 같다.
- N > 1이면 counting semaphore라 부른다.

## 동작·원리

### 식당 비유

좌석이 2개뿐인 식당. 문지기가 손가락 2개를 펴고 서 있다.

```
손님 A 입장 → 손가락 1개 접음 (남은 자리 1)
손님 B 입장 → 손가락 다 접음 (남은 자리 0 = "포화")
손님 C 도착 → 선택지가 둘:
   (1) 줄 세우기  — 자리가 날 때까지 대기 (기본 동작)
   (2) 돌려보내기 — "지금 만석입니다, 나중에 오세요" (즉시 거절)
손님 A 퇴장 → 손가락 1개 폄 → 다음 손님 입장
```

## 쓰이는 자료구조·알고리즘

<!-- 보충: 노트 본문 요약·참조 (legacy-format-conversion-2) -->
*(Claude 보충 — 노트 본문 요약)*

- **카운터** — 들어올 때 -1, 나갈 때 +1, 0이면 포화다(「해결하는 문제」 한 줄, 「동작·원리」 식당 비유). 카운터가 1이면 뮤텍스와 사실상 같고, N > 1이면 counting semaphore라 부른다(「해결하는 문제」 왜 필요한가).
- **대기열** — 포화 시 줄 세우기를 고르면 생기는 줄. 대기를 허용할 거면 그 길이에도 상한이 필요하다(「장애 시나리오와 대처」 흔한 함정).
- **코드 형태** — `asyncio.Semaphore(2)`, 줄 서지 않고 포화를 확인하는 `sem.locked()`, 입장(-1)과 자동 퇴장(+1)을 묶는 `async with sem:`(「적용 — 풀어나가는 법」 이 프로젝트에서).

## 적용 — 풀어나가는 법

### 이 프로젝트에서

llm 래퍼는 GPU가 1장이라 동시 2건까지만 받는다:

```python
sem = asyncio.Semaphore(2)      # 손가락 2개

if sem.locked():                # 다 접혀 있나? (줄 서지 않고 바로 확인)
    raise Busy()                # → HTTP 503 "만석입니다, 2초 뒤에 오세요"
async with sem:                 # 입장(-1), 블록을 나가면 자동 퇴장(+1)
    ... GPU 추론 ...
```

여기서 중요한 선택: **줄을 세우지 않고 즉시 돌려보낸다.** 검색은 LLM 없이도
동작하므로(그냥 키워드 검색으로 폴백), 사용자를 줄 세워 기다리게 하는 것보다
"바쁘다"고 빨리 알려주는 쪽이 전체 경험이 낫다. 실측: 포화 상태에서 거절까지 7.7ms.

## 장애 시나리오와 대처

### 흔한 함정

- **퇴장을 빼먹는 것** — 예외가 나도 카운터를 돌려놔야 한다. `async with`(파이썬) 같은
  자동 반납 구문을 쓰면 안전하다.
- **줄이 무한정 길어지는 것** — 대기를 허용할 거면 대기열 길이에도 상한이 필요하다.

## 핵심 문장

- 세마포어 = 수용량 카운터. 뮤텍스는 N=1인 특수 경우.
- 포화 시 두 선택: 대기(줄) vs 즉시 거절(503). 우리는 폴백이 있어 즉시 거절이 맞다.
- 반납 누락 = 카운터 영구 감소 → `async with`로 자동화. 대기 허용 시 대기열에도 상한.
