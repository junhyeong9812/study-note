# systems/multi-tenancy — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/09-multi-tenancy/README.md` (프로젝트 학습 노트) · 이관일 2026-09-16.\
> 본문 절들(격리 모델·권한 누수 경로 L1~L8·리소스 편중·스키마 마이그레이션)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지).\
> 원고는 특정 프로젝트(은행 서비스)의 결정에 묶인 절이 많아, 그 고유 식별자(ADR·BR·컨텍스트 번호)는 **일반 개념**과 「현장에서 만나는 상황」으로 승격·재배치했다.\
> 「한눈에」의 아파트 비유와 일부 도식은 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**멀티테넌시(multi-tenancy)** = 한 시스템이 여러 주체의 데이터를 다루면서, 그것들이 **서로 새지 않게** 하는 문제.\
격리 축의 이름은 도메인마다 다르다 — SaaS면 "테넌트", 은행이면 "고객", 병원이면 "환자" — 하지만 **실패 방식은 같다.**

---

## 한눈에 — 쉽게 말하면

**아파트 한 동**을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
아파트 한 동 (여러 세대가 한 건물에 산다)
+-------------------------------------------+
| 301호 열쇠는 301호만 연다      | ← 데이터 격리: 남의 집 못 들어감
| 옆집 열쇠로 우리 집이 열리면 사고 | ← 누수: 조건 하나 빠지면 뚫림
| 관리사무소는 공용부만 관리       | ← 권한 단계: 운영자도 아무거나 못 함
| 큰 세대가 엘리베이터를 독점하면   | ← 리소스 편중: 한 주체가 공용 자원 먹음
|   다른 세대가 못 탄다            |
+-------------------------------------------+
```

**소프트웨어도 똑같은 구조다.** 한 데이터베이스·한 배포에 여러 주체가 함께 살고(공용 건물), 각자는 자기 데이터에만 닿아야 하며(자기 집 열쇠), 운영자라도 조작마다 권한이 갈리고(관리사무소), 한 주체가 커넥션 풀·캐시 같은 공용 자원을 독점하면 나머지가 굶는다(엘리베이터 독점).

쉽게 말하면 이렇다.\
**"주체를 나눠 담는 것"이 절반, "그 경계가 실수로 안 뚫리게 하는 것"이 나머지 절반이다.** 그리고 실무에서 사고가 나는 쪽은 거의 항상 후자다 — 격리를 **코드가 지키게** 두면 조건 하나가 빠져서 샌다.

---

## 문제 — 이 개념이 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(운영·설계 개념 정리다). 대신 네 개의 질문에 답한다.

```text
1. 격리 모델   "주체를 어느 층위에서 가르나? (배포/DB/스키마/행)"
2. 권한 누수   "격리 조건이 어디서 빠져 새는가? 어떻게 막나?"
3. 리소스 편중 "한 주체가 공용 자원을 독점하면 어떻게 격리하나?"
4. 스키마 변경 "격리된 여러 저장소에 스키마를 어떻게 한꺼번에 바꾸나?"
```

아래 서머리는 이 네 질문을 하나씩 분석·정리한 것이다.

> **테넌트(tenant)** — 한 시스템을 공유하는 격리 단위 주체 하나. 회사·고객·조직 등.\
> 예: SaaS에서 가입한 회사 하나가 테넌트, 은행에서 계좌 소유자 한 명이 테넌트에 해당한다.

## 전체 흐름

멀티테넌시는 "격리를 얼마나 강하게 하느냐"라는 **하나의 다이얼**을 중심으로 나머지가 딸려 온다.

```text
격리 모델을 고른다 (행 단위 ← 약 ────── 강 → 인스턴스 분리)
        |
        v
약할수록 → 코드가 격리를 지킨다 → 권한 누수 위험 커짐 (L1~L8)
강할수록 → 구조가 격리를 지킨다 → 마이그레이션·비용이 N배
        |
        v
어느 모델이든 남는 두 문제:
   - 리소스 편중 (공용 자원을 한 주체가 독점)
   - 스키마 변경 (격리된 저장소 전체에 어떻게 적용하나)
        |
        v
판별: "지금 안 하면 나중에 못 하는 것"만 먼저 박는다
   (소유자 컬럼·권한 단계는 나중에 넣기 비쌈 / 격리 등급 승격은 나중에도 가능)
```

## 격리 모델 — 어디서 가르나

> 출처: `jun-bank/docs/study/09-multi-tenancy/README.md` — §1

**언제 쓰나** — 여러 주체를 한 시스템에 담기로 했을 때, 맨 처음 정하는 것. 이 선택이 나머지 전부를 좌우한다.

주체를 가르는 층위는 넷이고, 위로 갈수록 격리가 약하고 싸다.

```text
강함 (구조가 막는다 · 비쌈)
 ^  인스턴스 분리   주체마다 별도 배포·DB       비용·운영이 주체 수만큼
 |  DB 분리        같은 앱, 주체마다 DB         커넥션 풀 폭증 · 마이그레이션 N회
 |  스키마 분리     같은 DB, 주체마다 스키마      마이그레이션 N회 · 스키마 수 한계
 v  행 단위 ★      한 테이블에 전부(소유자 컬럼)  ★ 약 — 코드가 지킨다 · 누수 위험
약함 (코드가 막는다 · 쌈)
```

> **행 단위 격리(row-level / discriminator column)** — 한 테이블에 모든 주체의 데이터를 함께 넣고, `ownerId`(또는 `tenantId`) 컬럼으로 구분하는 방식.\
> 예: 한 `accounts` 테이블에 전 고객의 계좌가 들어 있고, 쿼리마다 `WHERE owner_id = ?`로 걸러낸다.

**전/후 대비 — 격리를 강하게 할 때의 맞교환**

```text
행 단위 (약한 격리)                    인스턴스 분리 (강한 격리)
+---------------------------+         +---------------------------+
| 마이그레이션 1회           |         | 마이그레이션 N회            |
| 주체 간 집계가 쉽다         |         | 주체 간 집계가 어렵다        |
| 소형 주체도 공짜에 가깝다    |         | 소형 주체에 과투자          |
| ❌ 실수로 샐 수 있다         |         | ✅ 구조가 새는 걸 막는다      |
+---------------------------+         +---------------------------+
  → 싸지만 코드가 유일한 방어선          → 비싸지만 실수해도 안 샌다
```

**비용** — 행 단위는 가장 흔하고 가장 위험하다. 비용이 싸서 대부분 여기서 시작하는데, **격리를 코드가 지킨다** — "주의력에 의존하는 규칙은 지켜지지 않는다"가 정면으로 걸리는 자리다.

### 현장에서 만나는 상황

한 도메인 안에서도 격리 축이 여럿 겹친다.

```text
축                     보통 어떤 모델
고객 간(데이터 소유)     행 단위 — 계좌·주문에 소유자가 있다
조직/지점 간            행 단위 + 스코프(부서·지점 범위)
운영자 권한 단계         행 단위 아님 — 조작 자체를 가른다(조회만/정정까지/승인필요)
```

핵심은 **"운영자 권한 단계"는 데이터 격리가 아니라 조작 격리**라는 점이다.\
소유자 컬럼으로는 "이 상담원이 환불을 실행해도 되는가"를 못 막는다. 그건 다음 절(권한 누수)이 아니라 인가(authorization) 모델의 몫이다.

## 권한 누수 — 조건 하나가 빠지는 방식

> 출처: `jun-bank/docs/study/09-multi-tenancy/README.md` — §2

**언제 쓰나** — 행 단위 격리를 골랐을 때(즉 대부분의 경우) 반드시 점검해야 하는 사고 유형. **가장 많이 일어나고, 테스트로는 잘 안 잡힌다** — 정상 경로는 다 통과하기 때문이다.

### 새는 경로 여덟 — L1~L8

한 조건이 어디서 빠지는지를 유형화한 것이다. 저장소만 보면 절반(L6·L8)은 안 보인다.

```text
L1  조회에 조건 누락    WHERE id=? 만 있고 소유자 조건이 없다
L2  식별자 추측(IDOR)   /accounts/12345 를 다른 값으로 바꿔 호출
L3  집계·통계 경로      목록은 막았는데 합계 API가 안 막혔다
L4  조인의 반대편       계좌는 필터했는데 조인한 거래 테이블은 안 했다
L5  배치·리포트         운영 도구가 "전체를 본다"는 전제로 짜였다
L6  캐시 키             캐시 키에 소유자가 빠져 남의 결과가 반환된다
L7  에러 메시지         "계좌 없음" vs "권한 없음" — 존재 여부가 샌다
L8  이벤트·로그         payload에 남의 식별자가 실려 하류로 흘러간다
```

> **IDOR(Insecure Direct Object Reference)** — URL·파라미터의 식별자를 남의 값으로 바꿔 호출해 접근을 우회하는 공격.\
> 예: `/accounts/12345`가 내 계좌면, `12346`으로 바꿔 남의 계좌가 열리는지 시험한다.

### 막는 방법 — 강도 순

```text
약  코드 리뷰·규약        거의 못 막는다
 |  공통 리포지토리        그 리포지토리를 안 쓰면 뚫린다
 |  DB 행 수준 보안(RLS)   ★ 쿼리를 우회할 수 없다
 v  타입으로 강제          소유자 없는 조회를 컴파일이 거부
강  인스턴스/DB 분리       구조가 막는다
```

> **RLS(Row-Level Security)** — DB가 세션의 주체 정보를 기준으로 행을 자동으로 걸러 주는 기능. 애플리케이션이 조건을 빼먹어도 DB가 막는다.\
> 예: 세션에 `owner_id`를 심어두면, `SELECT * FROM accounts`조차 그 주체의 행만 돌려준다.

**전/후 대비 — 조건이 빠질 수 있는 형태 vs 빠질 수 없는 형태**

```text
❌ 빠질 수 있다                        ✅ 빠질 수 없다
findById(accountId)                   findById(accountId, requesterScope)
  → 소유자 조건은 호출자의 주의력에 의존    → 소유자 없이는 호출 자체가 컴파일 안 됨
```

핵심 원리는 *"쓰지 마라"*(규약)가 아니라 **"쓸 수 없게 만든다"**(타입·DB로 강제)이다. *(원고 보강 — 이 프로젝트는 자금 경로를 같은 원리로 단일화했다)*

### 검증은 "정상 경로"가 아니라 "옆집"으로 한다

```text
❌ 내 계좌를 조회하면 보인다              ← 통과해도 아무 보장이 없다
✅ 남의 계좌 식별자로 호출하면 거절된다     ← 이것이 검증이다
✅ 모든 조회 API에 대해 위를 반복한다      ← 하나만 빠져도 뚫린다
```

**비용** — "모든 API에 대해"가 핵심이다. 사람이 세면 빠진다 — **엔드포인트 목록을 생성해서 전수 시험**한다.

### 현장에서 만나는 상황 — 실무에서 흔히 빠지는 인가 구멍

인증(누구인가)만 있고 **인가(무엇을 할 수 있는가)가 비어 있는** 상태를 자주 만난다. 전형적인 공백 넷.

```text
공백                    왜 문제인가
인가 모델 없음           로그인은 되는데, 누가 무엇을 할 수 있는지가 어디에도 없다
운영자 권한 단계 없음     "운영자"라고만 쓰여 있으면 "운영자면 뭐든 할 수 있다"가 된다
조회 경로 소유자 조건     조회 API가 아직 없어 안 드러났을 뿐, 생기면 L1이 된다
감사 로그에 행위자 없음    "얼마가 움직였나"는 남기는데 "누가 했나"는 안 남긴다
```

> ⚠️ **운영자 권한 단계의 부재가 가장 큰 구멍이다.** 운영자 조작(보류·통지·수동 실행·차단 해제 등)이 규칙 여럿에 흩어져 있는데 권한 단계가 없으면, 은행에서 그것은 **내부 통제 부재**다.\
> "운영은 별도 모델이 아니다"라고 판정해 두었더라도, **권한 단계 자체가 하나의 모델**이므로 그 판정은 다시 볼 값어치가 있다. *(원고의 프로젝트 결정을 일반 교훈으로 옮김)*

## 리소스 편중 — 큰 주체 하나가 공용 풀을 먹는다

> 출처: `jun-bank/docs/study/09-multi-tenancy/README.md` — §3

**언제 쓰나** — 격리를 데이터에서 끝냈다고 방심할 때. **자원도 격리해야 한다.**

### 무엇이 편중되나

```text
자원          편중되면
커넥션 풀      큰 주체의 느린 쿼리가 풀을 점유 → 전체 대기
스레드        한 주체의 배치가 워커를 다 먹는다
캐시          큰 주체의 데이터가 캐시를 밀어낸다(eviction)
디스크·인덱스  한 주체가 테이블 대부분을 차지해 통계가 왜곡된다
락            핫 로우가 다른 주체까지 대기시킨다
```

> **eviction(축출)** — 캐시가 꽉 찼을 때 자리를 만들려고 기존 항목을 밀어내는 것.\
> 예: 큰 주체의 데이터가 캐시를 가득 채우면, 작은 주체의 자주 쓰는 데이터가 밀려나 매번 DB를 다시 친다.

### 대응

```text
테넌트별 쿼터   요청 수·동시 실행·데이터량에 상한
풀 분리         큰 주체를 별도 커넥션 풀·워커로
우선순위 큐      배치를 실시간보다 낮게
격리 등급 승격   큰 주체는 DB 분리로 올린다
```

**비용** — 쿼터·풀 분리는 운영 복잡도를 늘리지만, 한 주체의 폭주가 전체를 멈추는 것보다 싸다.

### 현장에서 만나는 상황

편중을 만드는 것은 "큰 고객"보다 **"채널"과 "배치"**인 경우가 많다.\
예: 대사·정산 배치가 실시간 승인 경로의 커넥션·워커를 먹어치우는 것이 전형이다.\
그래서 배치가 실시간 경로를 잠식하면 **되돌리는 조건**(우선순위 강등·풀 분리)을 미리 걸어 둔다. *(원고 보강)*

## 스키마 마이그레이션 — 격리된 저장소 전체에 적용하는 문제

> 출처: `jun-bank/docs/study/09-multi-tenancy/README.md` — §4

**언제 쓰나** — 스키마·DB 분리를 골랐을 때. 저장소가 N개면 스키마 변경도 N번이고, **중간에 하나가 실패하면 부분 적용 상태**가 된다.

```text
행 단위       ✅ 한 번
스키마 분리    ❌ N번 — 하나 실패하면 부분 적용 상태
DB 분리       ❌ N번 + 순서·롤백까지
```

### 부분 적용이 진짜 문제다

```text
주체 1..500   적용 완료
주체 501      실패
주체 502..    미적용
  → 앱은 어느 스키마를 가정해야 하나?
```

**그래서 `expand-contract`가 필수가 된다.**

> **expand-contract(확장-수축) 마이그레이션** — 스키마를 한 번에 바꾸지 않고, 구·신 버전이 공존하는 단계를 거쳐 옮기는 방식.\
> 예: 컬럼 이름을 바꿀 때 새 컬럼을 먼저 "추가"만 하고(둘 다 동작), 데이터를 옮긴 뒤, 마지막에 옛 컬럼을 "제거"한다.

```text
① expand    새 컬럼 추가 (구/신 버전 모두 동작)
      ↓
② 배포      앱이 둘 다 다룰 수 있게
      ↓
③ 이행      데이터 이관
      ↓
④ contract  옛 컬럼 제거
```

**비용** — 각 단계 사이에 **"전 주체 적용 완료"를 기다려야** 한다. 그 대기가 없으면 부분 적용 상태에서 앱이 깨진다. 단계가 늘어나는 대가로 무중단·부분실패 안전을 산다.

---

## 핵심 문장

- **격리 축의 이름은 도메인마다 다르지만(테넌트·고객·환자) 실패 방식은 같다 — 쿼리 조건 하나가 빠져 뚫린다.**
- **격리는 강할수록 구조가 지키고(비쌈), 약할수록 코드가 지킨다(쌈·위험). 행 단위가 가장 흔하고 가장 위험하다.**
- **권한 누수는 정상 경로 테스트로 안 잡힌다 — "옆집 식별자로 거절되는가"를 모든 API에 전수 시험해야 한다.**
- **막는 힘은 "쓰지 마라"(규약)가 아니라 "쓸 수 없게 만든다"(타입·RLS)에서 나온다.**
- **격리는 데이터만이 아니다 — 커넥션·캐시·워커 같은 공용 자원도 편중되면 격리해야 한다.**
- **"멀티테넌시를 안 한다"와 "격리 축이 없다"는 다르다. 테넌트가 하나여도 고객 간 격리와 권한 단계는 필요하다.**

## 용어 풀이

- **멀티테넌시(Multi-tenancy)** — 한 시스템이 여러 주체의 데이터를 격리해 함께 다루는 것.
- **테넌트(Tenant)** — 격리 단위 주체 하나(회사·고객·조직).
- **격리(Isolation)** — 한 주체의 데이터·자원·조작이 다른 주체에게 닿지 않게 막는 것.
- **행 단위 격리(Row-level / Discriminator Column)** — 한 테이블에 전부 넣고 소유자 컬럼으로 구분하는 방식. 싸지만 코드가 지킨다.
- **인스턴스 분리(Silo)** — 주체마다 별도 배포·DB. 가장 강하고 가장 비싸다.
- **인증(Authentication)** — "당신이 누구인가"를 확인하는 것.
- **인가(Authorization)** — "당신이 무엇을 할 수 있는가"를 정하는 것. 인증과 다르다.
- **IDOR(Insecure Direct Object Reference)** — 식별자를 남의 값으로 바꿔 접근을 우회하는 공격.
- **RLS(Row-Level Security)** — DB가 세션 주체 기준으로 행을 자동으로 걸러 주는 기능.
- **eviction(축출)** — 캐시가 꽉 찼을 때 기존 항목을 밀어내는 것.
- **쿼터(Quota)** — 한 주체가 쓸 수 있는 자원(요청·동시성·데이터량)의 상한.
- **expand-contract(확장-수축)** — 구·신 스키마가 공존하는 단계를 거쳐 무중단으로 옮기는 마이그레이션 방식.
- **부분 적용(Partial Migration)** — 여러 저장소에 스키마를 적용하다 일부만 성공한 어긋난 상태.
- **감사 로그(Audit Log)** — "누가 무엇을 언제 했는가"를 남기는 기록. 행위자(주체)가 빠지면 반쪽이다.
- **결과적 일관성(Eventual Consistency)** — 지금은 달라도 시간이 지나면 결국 같아지는 상태.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **"silo vs pool"이라는 업계 용어.** 위 격리 모델 표에서 인스턴스/DB 분리를 **silo(격리된 곳간)**, 행 단위 공유를 **pool(공용 웅덩이)**, 둘을 섞은 것을 **bridge**라고 부른다(AWS SaaS Lens 등에서 정립). 원고의 4단계 표는 이 silo↔pool 스펙트럼을 세분한 것이다.
- **RLS는 Postgres·SQL Server 등이 실제로 제공한다.** 원고에서 "쿼리를 우회할 수 없다"고 한 RLS는 이론이 아니라 DB 기능이다 — `CREATE POLICY`로 정책을 걸면 애플리케이션이 조건을 빼먹어도 DB가 행을 걸러 준다. 단, DB superuser·`BYPASSRLS` 권한은 예외라 운영 계정 관리가 함께 필요하다. *(확인 필요 — DB별 세부 문법)*
- **"noisy neighbor(시끄러운 이웃)".** §3의 리소스 편중을 부르는 표준 용어다. 한 주체가 공용 자원을 독점해 다른 주체의 성능을 떨어뜨리는 현상 전체를 가리키며, 쿼터·풀 분리·우선순위 큐가 그 표준 대응이다.
- **인가 모델의 두 축 — RBAC vs ABAC.** 원고의 "운영자 권한 단계"는 인가 설계 문제인데, 실무 선택지는 보통 둘이다. **RBAC**(Role-Based, 역할에 권한을 묶음: 상담원/관리자/승인자)와 **ABAC**(Attribute-Based, 속성으로 판단: "자기 지점 고객에 한해"). 권한 단계가 "지점·금액 한도"까지 가면 RBAC만으로는 부족해 ABAC가 섞인다.
- **감사 로그와 원장(ledger)은 다르다.** 원고가 지적한 "원장은 자금은 남기지만 행위자를 안 남긴다"는 흔한 혼동이다 — 원장은 *무엇이 얼마나 움직였나*(회계 사실)를 남기고, 감사 로그는 *누가 그 조작을 했나*(행위 책임)를 남긴다. 둘은 목적이 달라 하나로 합칠 수 없다.
