## 한눈에 — 쉽게 말하면

물건을 팔고 **택배를 부치는 가게**를 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
판매 장부(내 DB)          택배 접수(다른 회사)
+------------------+      +------------------+
| 3번 고객, 신발    | ───▶ | 운송장 발급        |
+------------------+      +------------------+
      ①                          ②
```

①은 내 장부, ②는 택배사다. **둘은 서로 다른 시스템이라 한 번에 묶이지 않는다.**\
①만 적히고 ②가 안 되면 → 고객은 산 신발을 못 받는다(유실).\
②만 되고 ①이 취소되면 → 아무도 안 산 신발이 배송된다(유령).

두 가지 대비책이 있다.

```text
아웃박스                         발송 로그
판매 장부 같은 페이지에            먼저 택배를 부치고
"택배 보낼 것"을 함께 적고         "부쳤음"을 나중에 적는다
별도 직원이 그 목록을 처리         → 부치기 직전 죽으면 그 건은
→ 판매가 남으면 지시도 반드시 남음    아무 흔적도 없이 사라진다
```

**코드도 똑같은 구조다.** 판매 장부 = 비즈니스 DB, 택배 = 메시지 브로커(카프카 등).\
아웃박스는 이벤트를 **같은 트랜잭션**에 함께 저장해 "발행 유실" 계열을 닫고, 발송 로그는 보낸 뒤 기록만 남기므로 유실 창(window)이 남는다.

쉽게 말하면 이렇다.\
**저장을 "언제" 하느냐가 전부다.** 비즈니스 변경과 같은 순간에 저장하면 유실이 닫히고, 내보낼 때 저장하면 사후 추적만 된다.

## 문제 — 이 개념이 답하려는 질문

이 주제에는 풀 코드 과제가 없다(개념 정리다). 대신 하나의 곤란한 질문에 답한다.

```text
DB 커밋과 브로커 발행은 서로 다른 시스템이라
한 트랜잭션으로 묶이지 않는다.
   → 그러면 어느 실패를 닫을 것인가?
   → 유실을 닫을 것인가, 사후 추적으로 만족할 것인가?
```

> **이중 쓰기(dual write)** — 한 작업에서 두 개의 다른 저장소/시스템에 각각 써야 하는 상황.\
> 예: DB에 주문을 저장하고 브로커에 "주문 생성됨"을 보내는데, 둘은 원자적으로 묶이지 않는다.

```java
@Transactional
public void createOrder(...) {
    orderRepo.save(order);           // ① DB
    kafkaTemplate.send("orders", e); // ② 브로커  ← 다른 시스템
}
```

| 실패 지점 | 결과 |
|---|---|
| ① 성공, ② 실패 | 주문은 있는데 이벤트가 없음 → **다운스트림 미반영(유실)** |
| ② 성공, ① 롤백 | 이벤트는 나갔는데 주문이 없음 → **유령 이벤트** |

> `@Transactional` 안에서 `send()`를 호출해도 **브로커 전송은 롤백되지 않는다.** 이걸 모르고 짜는 코드가 가장 흔하다.\
> (분산 트랜잭션/2PC는 성능·운영 비용 때문에 사실상 안 쓴다.)

아래 서머리는 이 질문을 두 패턴으로 나눠 분석·정리한 것이다.

## 전체 흐름

두 패턴은 저장 시점 하나로 갈리고, 선택은 "이벤트를 원천에서 다시 만들 수 있는가"로 결정된다.

```text
이중 쓰기 문제 (DB 커밋 ↔ 브로커 발행이 안 묶임)
        ↓
저장을 언제 하나?
   ├─ 비즈니스 TX와 함께  →  트랜잭셔널 아웃박스 (유실 닫음, 중복 남음)
   └─ 내보낼 때          →  발송 로그 (사후 추적, 유실 창 남음)
        ↓
발송 로그를 골랐다면: 유실 창을 어떻게 메우나?
        ↓
이벤트가 원천 상태에서 재도출 가능한가?
   ├─ 아니오 (사건형)  →  아웃박스가 필수
   └─ 예   (상태형)   →  발송 로그 + 대조 배치로 창을 메움
```

## 원인 — 이중 쓰기 문제

> 출처: `jun-bank/docs/study/notes/06-outbox-vs-dispatch-log.md` — 1절

**언제 나오나** — DB 하나와 브로커 하나에 "같은 사건"을 각각 써야 할 때 항상.

①과 ②는 서로 다른 시스템이라 원자적으로 묶이지 않는다.\
그래서 위 표의 두 실패(유실·유령)가 근본적으로 열려 있다.

**비용** — 이 문제를 정면으로 닫으려면 분산 트랜잭션(2PC)이 필요한데, 조율 비용·성능·운영 부담이 커서 현업은 거의 안 쓴다.\
대신 아래 두 패턴처럼 **"어느 한 실패만 확실히 닫는"** 우회를 택한다.

## A. 트랜잭셔널 아웃박스 — 비즈니스 TX와 같이 저장

> 출처: `jun-bank/docs/study/notes/06-outbox-vs-dispatch-log.md` — 2-A절

**언제 쓰나** — 이벤트를 절대 유실하면 안 될 때(사건형 이벤트, 정산·감사 등).

```text
전 (그냥 이중 쓰기)
save(order) ─┐
             ├ 사이에서 죽으면 이벤트만 증발
send(event) ─┘

후 (아웃박스)
+-----------------------------+
| 같은 DB · 같은 트랜잭션        |
|   save(order)               |
|   save(outbox_event)        |  ← 커밋: 둘 다 되거나 둘 다 안 됨
+-----------------------------+
        ↓ (별도 릴레이가 나중에)
   미발행 행 폴링 → 브로커 발행 → ack 후 완료 표시
```

```java
@Transactional
public void createOrder(...) {
    orderRepo.save(order);
    outboxRepo.save(new OutboxEvent(...));   // 같은 DB, 같은 트랜잭션
}   // 커밋: 둘 다 저장되거나 둘 다 안 되거나
```

그림 해설 — 비즈니스 변경이 커밋됐다면 이벤트 행도 **반드시** 함께 존재한다. "발행 유실" 계열이 여기서 닫힌다.

**남는 성질** — 릴레이가 발행 후 완료 표시 전에 죽으면 재발행한다 → **중복 발행이 남는다.**\
그래서 **소비 측 멱등성(인박스 패턴)이 짝으로 필요하다.**

**비용** — 릴레이(폴링) 또는 CDC라는 별도 장치가 필요하다. 보장 등급은 **at-least-once, 유실 없음**.

> **at-least-once** — 메시지가 최소 한 번은 전달되지만 중복될 수 있는 보장.\
> 예: 아웃박스 릴레이가 같은 행을 두 번 발행할 수 있어, 소비 측이 중복을 걸러야 한다.

## B. 발송 로그(dispatch log) — 내보낼 때 저장

> 출처: `jun-bank/docs/study/notes/06-outbox-vs-dispatch-log.md` — 2-B절

**언제 쓰나** — 실시간 지연이 중요하고, 유실을 다른 수단(대조 배치)으로 메울 수 있을 때.

```text
전 상태
send(event) ─┐  먼저 보내고
             │  이 사이에서 죽으면 "보낼 뻔한 것"이 흔적 없이 사라짐
save(log)  ──┘  보낸 기록을 남김

→ 비즈니스는 커밋됐는데 발행 시도 자체가 없었던 구간 = 유실 창
```

```java
public void publish(Event e) {
    kafkaTemplate.send(...);          // 먼저 보내고
    dispatchLogRepo.save(...);        // 보낸 기록을 남김
}
```

그림 해설 — 발송 로그는 **발행을 보장하는 장치가 아니라 사후 추적/대조용**이다.

**남는 실패** — 유실 창이 남는다. **비용** — 구현은 가장 단순하다. 보장 등급은 **best-effort**.

### 비교표

| | 트랜잭셔널 아웃박스 | 발송 로그 |
|---|---|---|
| 저장 시점 | 비즈니스 TX와 **함께** | 발행 **시점에** |
| 원자성 | 있음 (같은 DB 트랜잭션) | 없음 |
| 발행 유실 | 없음 | **가능** |
| 중복 | 있음 (멱등 소비 필요) | 있음 |
| 지연 | 릴레이 폴링 주기만큼 | 거의 없음 |
| 복잡도 | 릴레이/CDC 필요 | 낮음 |
| 순서 | 아웃박스 ID 순으로 보존 가능 | 보장 어려움 |

## 상태형 vs 사건형 — 대조 배치가 성립하는 조건

> 출처: `jun-bank/docs/study/notes/06-outbox-vs-dispatch-log.md` — 3절

**언제 쓰나** — 발송 로그를 골라 놓고, 유실 창을 배치 정합성으로 메우려 할 때.

발송 로그의 유실 창은 **주기적으로 원천 데이터를 통째로 훑어** "나갔어야 하는데 안 나간 이벤트"를 찾아 재발행하는 배치로 메울 수 있다.

```text
실시간 경로: 원천 변경 → 발행 시도 → 발송 로그 기록   (유실 가능)
           ────────────────────────────────────────
보정 경로:  배치 → 원천 전량 스캔 → 발송 로그와 대조 → 누락분 재발행
```

이건 틀린 설계가 아니라 **성립 조건이 붙은 설계**다. 조건은 둘 다 만족해야 한다.

1. **이벤트가 원천 상태에서 재도출 가능해야 한다.**\
   현재 상태를 보고 "이 이벤트가 나갔어야 했다"를 판정할 수 있어야 배치가 누락을 찾는다.
2. **지연을 허용해야 한다.**\
   유실분은 다음 배치 주기까지 반영되지 않는다. 배치 주기 = **최대 복구 지연 시간(RTO)**.

### 성립하지 않는 경우 → 정식 아웃박스 필수

| 이벤트 성격 | 예시 | 재도출 가능? |
|---|---|---|
| **상태형** | "주문 상태 = 배송중", "재고 = 5" | 가능 — 현재 상태를 보면 알 수 있음 |
| **사건형** | "주문이 승인됨", "쿠폰이 사용됨", "잔액이 100 차감됨" | 불가 — **일어났다는 사실 자체가 소실되면 복구 불가** |

**결정적 구분: 중간 상태 전이는 원천에 남지 않는다.**\
`PENDING → APPROVED → SHIPPED`가 짧은 시간에 일어났다면, 배치가 나중에 볼 때는 `SHIPPED`만 보인다.\
`APPROVED` 이벤트가 나갔어야 했다는 사실을 **알 방법이 없다.** 다운스트림이 그 전이에 반응해야 한다면 유실이 확정된다.

또한 **감사(audit)·정산처럼 "발생 순간"이 의미를 갖는 이벤트**도 재도출로 대체할 수 없다.

**비용** — 대조 배치는 원천 전량 스캔이라 데이터가 커질수록 무거워지고, RTO만큼의 지연을 항상 감수한다.

> 정리 문장: **상태를 동기화하는 파이프라인이면 대조 배치로 충분하고, 사건을 전달하는 파이프라인이면 아웃박스가 필수다.**

## 제약 — 아웃박스를 다른 저장소에 두면 안 되는 이유

> 출처: `jun-bank/docs/study/notes/06-outbox-vs-dispatch-log.md` — 4절

**언제 나오나** — "아웃박스를 인메모리 저장소(Redis 등)에 두면 빠르겠지"라는 유혹이 들 때.

아웃박스의 **유일한 존재 이유는 비즈니스 데이터와 같은 트랜잭션에 묶이는 것**이다.

```text
비즈니스 DB(예: PostgreSQL)          별도 저장소(예: Redis)
+------------------------+          +------------------+
| save(order)            |          | opsForList()...  |
+------------------------+          +------------------+
        └── 롤백하면 되돌아옴          └── 롤백해도 안 돌아옴

→ 이중 쓰기 문제를 그대로 한 칸 옮긴 것. 아무것도 해결 못 함.
```

- 인메모리 저장소의 트랜잭션(`MULTI/EXEC` 등)은 그 저장소 내부의 원자성일 뿐, RDBMS와는 무관하다.
- Redis는 기본 구성에서 비동기 복제 + 주기적 영속화라 **장애 시 유실 자체가 정상 동작**이다.

**비용/결론** — **아웃박스는 비즈니스 데이터와 같은 DB, 같은 트랜잭션에 있어야만 아웃박스다.** 다른 저장소에 두면 이름만 아웃박스다.\
(Redis Stream을 **큐**로 쓰는 건 별개 문제이고 가능하다. 문제는 **아웃박스**로 쓰는 것.)

## 릴레이 구현 — 폴링 vs CDC

> 출처: `jun-bank/docs/study/notes/06-outbox-vs-dispatch-log.md` — 5절

**언제 쓰나** — 아웃박스를 골랐다면, 그 행을 브로커로 실어 나르는 릴레이를 어떻게 만들지 정할 때.

| | 폴링 릴레이 | CDC (Debezium 등) |
|---|---|---|
| 방식 | `SELECT ... WHERE published = false` 주기 조회 | WAL/binlog를 tail |
| 지연 | 폴링 주기 | 거의 실시간 |
| DB 부하 | 폴링 쿼리 부하 | 낮음 (로그만 읽음) |
| 인프라 | 없음 | Kafka Connect 등 추가 |
| 다중 인스턴스 | `SELECT ... FOR UPDATE SKIP LOCKED` 필요 | 커넥터가 관리 |

폴링 릴레이 핵심 쿼리:

```sql
SELECT * FROM outbox
WHERE published_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;   -- 여러 릴레이 인스턴스가 같은 행을 잡지 않도록
```

**공통 운영 포인트**

- 발행 후 완료 표시 사이의 크래시 → 재발행 → **소비 측 멱등성으로 흡수.**
- 완료된 아웃박스 행은 주기적으로 정리(파티션 드롭/아카이브). 안 그러면 테이블이 무한 증가.
- 아웃박스 적체량에 알림을 건다(릴레이 정지 감지).

**비용** — CDC는 지연·부하가 유리하지만 커넥터 인프라를 운영해야 하고, 폴링은 인프라가 없는 대신 주기만큼의 지연과 쿼리 부하를 진다.

---

## 현장에서 만나는 상황

발송 로그에 **원천 전량 대조 배치**를 붙인 설계를 실제로 자주 만난다(그리고 직접 짜기도 한다).\
실시간 경로에서는 유실을 막지 못하지만, 배치가 원천을 훑어 누락분을 재발행해 창을 메우는 형태다.

점검 질문은 둘이다.

- **이벤트가 원천 상태에서 재도출 가능한가?** (상태형이면 가능, 사건형이면 불가)
- **배치 주기만큼의 복구 지연(RTO)을 허용하는가?**

둘 다 "예"면 이 설계는 정당하다. 하나라도 "아니오"면 정식 아웃박스로 가야 한다.\
특히 "주문 승인됨"처럼 **중간 상태 전이가 원천에 남지 않는 사건형**이면, 대조 배치로는 그 전이가 있었다는 사실 자체를 알 수 없어 유실이 확정된다.

**이 두 질문의 답이 곧 이 파이프라인의 설계 근거 기록이다.**

---

## 핵심 문장

- **저장 시점이 어떤 실패 계열을 닫는지 결정한다** — 함께 저장하면 유실을, 내보낼 때 저장하면 아무것도 못 닫는다.
- **아웃박스는 유실을 닫고 중복을 남긴다** — 그래서 소비 측 멱등성이 항상 짝으로 필요하다.
- **대조 배치는 상태형에만 성립한다** — 사건형은 중간 전이가 원천에 안 남아 재도출이 불가능하다.
- **아웃박스는 비즈니스 DB 같은 트랜잭션 안에 있어야만 아웃박스다** — 다른 저장소면 이중 쓰기를 한 칸 옮긴 것.

---

## 한 문단 요약

> 이중 쓰기 문제 때문에 DB 커밋과 브로커 발행은 원자적으로 묶이지 않는다. 트랜잭셔널 아웃박스는 이벤트를 비즈니스 트랜잭션과 **같은 트랜잭션**에 저장해 발행 유실 계열을 닫고, 릴레이가 재발행하므로 중복은 남아 소비 측 멱등성이 짝으로 필요하다. 반면 발송 로그는 내보낼 때 기록하는 거라 사후 추적은 되지만 유실 창이 남는다. 발송 로그에 원천 전량 대조 배치를 붙이면 그 창을 메울 수 있는데, 성립 조건이 둘이다 — 이벤트가 원천 상태에서 재도출 가능할 것, 그리고 배치 주기만큼의 복구 지연을 허용할 것. "주문 승인됨" 같은 사건형 이벤트는 중간 상태 전이가 원천에 남지 않아 재도출이 불가능하므로 정식 아웃박스가 필수다. 그리고 아웃박스는 비즈니스 DB 안에 있어야만 의미가 있어서, 다른 저장소에 두면 원자성 자체가 성립하지 않는다.

---

## 관련 자료

- **소비 측 멱등성 / 인박스 패턴** — 아웃박스가 남기는 중복을 소비 측에서 흡수하는 짝 패턴. 아웃박스는 "유실 없음"만 보장하고 "중복 없음"은 소비 측 멱등성에 위임하므로 둘은 항상 함께 설계한다.
- Chris Richardson, *Microservices Patterns* — Transactional Outbox / Polling Publisher / Transaction Log Tailing 패턴의 표준 정리. *(Claude 보강 — 실명 출처 보완)*
- Debezium 공식 문서 — CDC(Change Data Capture)로 아웃박스 테이블을 tail하는 구현(Outbox Event Router). *(Claude 보강)*

## 용어 풀이

- **이중 쓰기(Dual Write)** — 한 작업에서 서로 다른 두 시스템(DB·브로커)에 각각 써야 하는 상황. 원자적으로 안 묶인다.
- **트랜잭셔널 아웃박스(Transactional Outbox)** — 이벤트를 비즈니스 데이터와 같은 DB·같은 트랜잭션에 저장하고, 릴레이가 나중에 브로커로 실어 나르는 패턴.
- **발송 로그(Dispatch Log)** — 브로커로 먼저 보낸 뒤 "보냈다"는 기록만 남기는 패턴. 사후 추적용이며 발행을 보장하지 않는다.
- **릴레이(Relay) / 발행자(Publisher)** — 아웃박스 행을 읽어 브로커로 발행하고 완료 표시하는 별도 프로세스.
- **CDC(Change Data Capture)** — DB의 변경 로그(WAL/binlog)를 tail해 변경을 스트림으로 뽑는 기법. Debezium이 대표.
- **at-least-once** — 최소 한 번 전달을 보장하되 중복은 있을 수 있는 등급.
- **best-effort** — 되도록 전달하지만 유실을 보장하지 않는 등급.
- **멱등성(Idempotency)** — 같은 요청/메시지를 여러 번 처리해도 결과가 한 번 처리한 것과 같은 성질.
- **상태형 이벤트** — 현재 상태를 나타내는 이벤트("재고=5"). 원천 상태에서 재도출 가능.
- **사건형 이벤트** — 일어난 사실을 나타내는 이벤트("승인됨"). 사실이 소실되면 복구 불가.
- **재도출(re-derivation)** — 원천의 현재 상태만 보고 "이 이벤트가 나갔어야 했다"를 다시 판정하는 것.
- **RTO(Recovery Time Objective)** — 유실이 복구되기까지 허용하는 최대 지연. 대조 배치에서는 배치 주기와 같다.
- **SKIP LOCKED** — 다른 트랜잭션이 잠근 행을 건너뛰고 잠긴 것만 집는 조회. 여러 릴레이가 같은 행을 중복 처리하지 않게 한다.
- **2PC(Two-Phase Commit)** — 여러 시스템을 하나의 분산 트랜잭션으로 묶는 프로토콜. 조율 비용·성능 때문에 현업은 거의 안 쓴다.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **왜 2PC를 안 쓰나 — 더 정확히.** 2PC는 코디네이터가 준비(prepare)–커밋(commit) 두 단계로 모든 참여자를 묶는데, 코디네이터가 커밋 직전 죽으면 참여자들이 잠금을 쥔 채 무한 대기(blocking)하는 근본 취약점이 있다. 브로커(카프카)는 애초에 XA 트랜잭션 참여자가 아니어서 이 그림에 끼지 못한다 — 아웃박스가 사실상의 표준이 된 이유다.
- **listen-to-yourself 패턴.** 아웃박스의 변종으로, 서비스가 자기 이벤트를 브로커로 먼저 보내고 그 이벤트를 자기가 다시 소비해 DB에 반영하는 방식. 순서가 뒤집혀 발행이 진실의 원천이 된다 — 트레이드오프가 아웃박스와 정반대다.
- **인박스(inbox) 테이블.** 소비 측 멱등성의 흔한 구현. 처리한 메시지 ID를 인박스 테이블에 기록하고, 이미 있으면 스킵한다. 처리와 ID 기록을 같은 트랜잭션에 묶는 게 핵심 — 아웃박스의 대칭이다.
- **정확히 한 번(exactly-once)은 대체로 환상이다.** 분산 시스템에서 실무가 목표하는 건 "at-least-once 전달 + 멱등 소비 = 실질적 exactly-once 효과"다. 아웃박스+인박스 조합이 바로 이 공식을 구현한 것.
