# software-design/46-quality-attributes-and-tradeoffs — 품질 속성과 맞교환: 무엇을 위해 무엇을 내주나 — 정리 (힌트)

## 해결하는 문제

기능 요구는 "주문을 취소할 수 있다"처럼 된다/안 된다로 갈린다.
품질 요구는 "빨라야 한다", "안 죽어야 한다", "고치기 쉬워야 한다"처럼 정도의 문제다.
그리고 이 정도들은 **서로 당긴다.** 하나를 올리면 다른 것이 내려간다.
이 충돌을 적어 두지 않으면, 누군가 한 속성을 최적화하는 순간 다른 속성이 조용히 무너진다.

```text
 "조회를 빠르게 하자" → 캐시 TTL 1초 → 응답 1μs  (성능 ↑)
                                  → 낡은 가격 98% (정합성 ↓)   ← 아무도 이 줄을 정하지 않았다
```

- *품질 속성(quality attribute)*: 시스템이 기능을 **얼마나 잘** 하는지에 관한 성질. 성능·가용성·보안·유지보수성 등.
- *맞교환(trade-off)*: 하나를 얻으려고 다른 하나를 내주는 것.

쉬운 예: 자동차는 연비·가속·적재량·가격이 서로 당긴다. "다 좋은 차"는 없고, 무엇을 먼저 보는지가 차의 성격을 정한다.\
똑같은 구조다.\
실무 예: 결제 조회 API에 캐시를 넣을지, TTL을 얼마로 할지는 기술 문제가 아니라 "가격이 몇 초 늦게 보여도 되나"라는 사업 판단이다.

기초는 원본 [engineering/engineering-axes](../../engineering/engineering-axes/README.md)에 있다.
원본은 7축(동시성·확장성·가용성·성능·시스템 설계·유지보수성·UX)을 "지키는 것 / 실패하면"으로 나누고, 축 사이 맞교환 표와 "A를 위해 B를 얼마만큼 내줬고 근거는 C" 말하기 틀을 준다.
이 노트는 그 위에 **표준 어휘(ISO/IEC 25010:2023)**, **요구를 시험 가능하게 적는 법(품질 속성 시나리오)**, **우선순위를 정하는 구조(ATAM 효용 트리)**, 그리고 맞교환을 **수치로 보는 실험**을 더한다.

## 동작·원리

### 1. 표준 어휘 — ISO/IEC 25010:2023 제품 품질 모델 9특성

```text
 제품 품질
 ├─ 기능 적합성        완전성·정확성·적절성
 ├─ 성능 효율성        시간 반응·자원 활용·용량
 ├─ 호환성            공존·상호운용
 ├─ 상호작용 능력       인지·학습·조작·사용자 오류 방지·참여·포용성·보조·자기 설명   (옛 "사용성")
 ├─ 신뢰성            무결함(faultlessness)·가용성·결함 허용·복구성
 ├─ 보안              기밀성·무결성·부인 방지·책임 추적·진위성(authenticity)·저항
 ├─ 유지보수성          모듈성·재사용성·분석성·수정성·시험성
 ├─ 유연성            적응성·확장성(scalability)·설치성·교체성                       (옛 "이식성")
 └─ 안전              운영 제약·위험 식별·페일 세이프·위험 경고·안전 통합              (2023 신설)
```

- 출처: iso25000.com의 ISO/IEC 25010 해설 페이지(9특성과 하위 특성 정의). ISO 공식 페이지는 열람이 막혀 표준 본문은 직접 확인하지 못했다.
- 2023판에서 눈여겨볼 것: **확장성은 유연성의 하위 특성**이고, **가용성은 신뢰성의 하위 특성**이다. 안전이 특성으로 들어왔다.
- *하위 특성(sub-characteristic)*: 특성을 더 쪼갠 측정 단위. 예) 유지보수성 → 모듈성: "한 구성 요소의 변경이 다른 구성 요소에 최소한의 영향을 주는 정도".

원본 7축과 맞대면 이렇다.

```text
 원본 7축           ISO/IEC 25010:2023에서의 자리
 ─────────────     ──────────────────────────────────────────
 가용성             신뢰성 > 가용성
 성능               성능 효율성
 확장성             유연성 > 확장성
 유지보수성          유지보수성
 UX                상호작용 능력
 동시성             특성이 아니다 — 기능 정확성·성능 효율성을 해치는 원인(경쟁 조건)의 영역
 시스템 설계         특성이 아니다 — 위 특성들을 맞교환하는 결정 그 자체
```

- 원본의 축 구분은 "실패 방식"을 기준으로 한 실무 분류이고, ISO는 "제품 성질"을 기준으로 한 분류다. 둘은 목적이 달라서 어긋나는 것이 정상이다.

### 2. 요구를 시험 가능하게 — 품질 속성 시나리오 6요소

"빨라야 한다"는 시험할 수 없다. Bass·Clements·Kazman 『Software Architecture in Practice』 2판 4장은 품질 요구를 여섯 부분으로 적는다.

```text
 [자극원] ──자극──> [대상(artifact)] ──> [응답]  ──측정──> [응답 측정치]
  사용자 1만 명       주문 조회 API         결과 반환        p99 ≤ 300ms
                      ↑
                   [환경] 평시 / 피크 / 장애 중
```

- *자극원(source)*: 자극을 만든 주체(사람·다른 시스템).
- *자극(stimulus)*: 시스템에 도착한 조건(요청, 장애, 변경 요청).
- *환경(environment)*: 그때의 상태(평시·과부하·한 노드 장애 중).
- *대상(artifact)*: 자극을 받는 부분(시스템 전체 또는 일부).
- *응답(response)*: 자극 뒤에 시스템이 하는 일.
- *응답 측정치(response measure)*: 요구를 시험할 수 있게 하는 수치.

같은 틀로 유지보수성도 적는다: "개발자 한 명이(자극원) 결제 수단 하나 추가를 요청하면(자극), 평시 개발 중에(환경), 결제 모듈만(대상) 바뀌고(응답), 3일 안에 파일 5개 이하 수정으로 끝난다(측정, 예시)."

### 3. 우선순위 — ATAM 효용 트리

```text
 효용(utility)
 ├─ 성능
 │   └─ 지연 ── (H,M) 피크 시 주문 조회 p99 ≤ 300ms          ← (중요도, 달성 위험)
 ├─ 정합성
 │   └─ 가격 ── (H,L) 가격 변경 후 1초 안에 모든 조회에 반영
 ├─ 가용성
 │   └─ 장애 ── (M,M) 결제사 장애 중에도 주문 접수 계속
 └─ 유지보수성
     └─ 확장 ── (M,L) 결제 수단 추가가 3일 안에
```

- Kazman·Klein·Clements, ATAM 기술 보고서(CMU/SEI-2000-TR-004, 2000-08): 뿌리는 "효용", 그 아래 품질 속성, 잎은 구체 시나리오다. 잎마다 **(시스템 성공에 대한 중요도, 달성 위험)**을 H·M·L로 매긴다. 이해관계자가 H·M·L보다 더 세밀하게는 안정적으로 구분하지 못한다고 적는다.
- (H,H)·(H,M) 잎부터 분석한다. 9단계 중 5단계가 효용 트리 생성이다.
- 같은 보고서의 두 정의:
  - *민감점(sensitivity point)*: 한 품질 속성의 달성에 결정적인 구조 요소의 성질(파라미터).
  - *맞교환점(tradeoff point)*: 한 파라미터가 **여러 민감점을 동시에 가지면서**, 바꾸면 속성들이 서로 다르게 움직이는 곳. 보고서 예: 통신 채널 속도를 올리면 처리량은 오르고 신뢰성은 내려간다 → 채널 속도가 맞교환점이다.

### 실험: 캐시 TTL 하나가 세 속성을 동시에 움직인다

조회 경로에 캐시를 두고 TTL만 바꿨다. 원본 값은 20ms마다 바뀌고, DB 조회는 2ms 걸린다고 흉내 냈다(`Thread.sleep(2)`). 0.2ms 간격으로 3초 동안 읽으며 세 가지를 쟀다.

```java
static long read(long ttlMs) throws InterruptedException {
    if (ttlMs == 0) return dbRead();                  // 캐시 없음
    Entry e = cache;
    if (e != null && System.nanoTime() - e.loadedAtNanos() < ttlMs * 1_000_000L) return e.value();
    long v = dbRead(); cache = new Entry(v, System.nanoTime()); return v;
}
// 읽은 직후 원본과 다르면 "낡은 값"으로 센다
if (v != dbValue.get()) stale++;
```

(실험, JDK 21.0.12 temurin, `--cpus=2`, `scratchpad/sd/45/e46/CacheTradeoff.java`, 2026-10-02 — 3회 실행, 값은 실행마다 조금씩 다르다. 아래는 1회차, 3회 범위는 아래 글에)

```text
TTL(ms)      평균(us)    p99(us)       낡은값%      DB호출/읽기
0            2114.5     2223.1        0.1       1.0000  (읽기 1252건)
10             56.6     2103.1       25.0       0.0264  (읽기 9282건)
100             6.1        2.2       89.7       0.0027  (읽기 11156건)
1000            1.2        2.2       98.4       0.0003  (읽기 11224건)
```

- 관찰 1 — TTL을 0 → 1000ms로 늘리자 평균 응답이 약 2.1ms → 약 1.2μs, DB 호출이 읽기당 1 → 0.0003으로 줄었다(성능 효율성 ↑, 자원 ↓).
- 관찰 2 — 같은 조작으로 낡은 값 비율이 0.1% → 98.4%가 됐다(정합성 ↓). 3회 범위: TTL 10은 24.1~25.0%, TTL 100은 88.7~89.7%, TTL 1000은 98.4~98.5%. 같은 조건 재실행 2회에서는 TTL 10이 24.4~24.9%, TTL 100이 88.4~88.8%, TTL 1000이 98.4~98.5%였다.
- 관찰 3 — TTL 10ms에서는 평균은 56μs로 내려갔지만 p99는 약 2.1ms 그대로다. 만료 때마다 누군가는 DB를 기다린다. **평균과 꼬리가 다른 속성처럼 움직인다.**
- 해석: TTL은 ATAM이 말하는 맞교환점이다. 한 파라미터에 성능·자원·정합성 세 민감점이 걸려 있다. "TTL을 얼마로"는 효용 트리의 (H,L) "1초 안에 반영" 같은 잎이 정해야 하는 값이다. 그 잎이 없으면 성능 쪽 사람이 TTL을 늘려도 막을 근거가 없다.
- 이 실험에서 TTL 0의 0.1%는 "읽은 직후 원본이 바뀐" 경쟁 구간이다(재실행 한 번은 0.0%로 반올림됐다). 캐시가 없어도 낡은 값 0%가 보장되지는 않는다.

### 4. 원본의 맞교환 표에 수치를 붙이는 법

```text
 충돌                         민감 파라미터 (맞교환점)          측정할 것
 ─────────────────────       ─────────────────────────       ─────────────────────────
 성능 ↔ 정합성                캐시 TTL, 복제 방식(동기/비동기)    p99, 낡은 값 비율, 복제 지연
 가용성 ↔ 정합성               쿼럼 크기, 분단 시 거절/수락       분단 중 성공률, 충돌 건수
 성능 ↔ 보안                  토큰 검증 위치(로컬/원격), 암호 강도  인증 지연, 폐기 반영 시간
 확장성 ↔ 유지보수성            샤드 수, 서비스 수                 변경당 배포 단위 수(45 실험 B)
 가용성 ↔ 비용                 복제본 수, 리전 수                 가용성, 월 비용
```

- 원본 README의 표는 충돌의 방향만 적는다. 실무에서는 **어떤 파라미터가 그 충돌을 일으키는지**와 **무엇으로 재는지**까지 적어야 결정을 검증할 수 있다.

## 쓰이는 자료구조·알고리즘

- **트리(효용 트리)** — 뿌리 효용, 중간 품질 속성·세부 속성, 잎 시나리오. 잎에 (중요도, 위험) 두 키를 달아 정렬하면 분석 순서가 된다.
- **다목적 최적화와 파레토 전선** — 속성이 둘 이상이면 "한 속성을 나쁘게 하지 않고는 다른 속성을 좋게 할 수 없는" 설계들의 집합(파레토 전선)이 생긴다. 실험의 TTL 4개 점은 성능·정합성 평면에서 그런 곡선 위의 점들이다.
- **TTL 캐시(만료 시각을 가진 엔트리)** — 실험의 `Entry(value, loadedAt)`. 만료 순간 몰림은 [reliability/29-cache-stampede](../../reliability/29-cache-stampede/2-summary.md).
- **백분위 계산(정렬 후 인덱스)** — 평균과 p99를 따로 본다. [reliability/19-performance-measurement](../../reliability/19-performance-measurement/2-summary.md).

## 적용 — 풀어나가는 법

### 1. 순서

1. **사업 동인에서 속성을 뽑는다.** "가격이 틀리면 법적 문제" → 정합성 H. "피크 때 주문 실패 = 매출 손실" → 가용성 H.
2. **시나리오 6요소로 적는다.** 형용사("빠르게")를 측정치("피크 p99 ≤ 300ms")로 바꾼다.
3. **효용 트리에 달고 (중요도, 위험)을 매긴다.** (H,H)·(H,M)부터 본다.
4. **민감점·맞교환점을 찾는다.** 파라미터 하나를 바꿨을 때 두 속성이 반대로 움직이면 맞교환점이다(실험의 TTL).
5. **결정을 기록한다.** 무엇을 위해 무엇을 얼마만큼 내줬고 근거가 무엇인지([47-architecture-decision-records](../47-architecture-decision-records/2-summary.md)).
6. **측정치를 지속 검사한다.** 시나리오의 측정치를 테스트·대시보드·알림으로 바꾼다.

### 2. 코드 — 시나리오를 테스트로 (Java, JUnit 5)

```java
// 시나리오: 가격 변경 후 1초 안에 모든 조회가 새 가격을 본다 (정합성, H,L)
@Test
void price_change_is_visible_within_one_second() throws Exception {
    priceAdmin.change("SKU-1", 12_000);
    long deadline = System.nanoTime() + Duration.ofSeconds(1).toNanos();
    while (System.nanoTime() < deadline) {
        if (catalog.price("SKU-1") == 12_000) return;     // 통과
        Thread.sleep(50);
    }
    fail("1초 안에 새 가격이 보이지 않음 — 캐시 TTL이 시나리오를 깨뜨린다");
}
```

- 누군가 성능을 위해 TTL을 5초로 바꾸면 이 테스트가 깨진다. 맞교환이 **암묵에서 명시로** 바뀐다.
- 성능 측정치(p99)는 단위 테스트보다 부하 시험·운영 지표로 지킨다([reliability/22-capacity-and-load-testing](../../reliability/22-capacity-and-load-testing/2-summary.md), [reliability/02-slo-sli-error-budget](../../reliability/02-slo-sli-error-budget/2-summary.md)).

### 3. 말하기 틀 (원본 README에서)

> "A를 위해 B를 얼마만큼 내줬고, 그 판단 근거는 C였습니다."

- 실험을 이 틀에 넣으면: "조회 p99를 2.2ms에서 2μs대로 낮추려고(A) TTL을 100ms로 두어 낡은 값 약 89%를 받아들였고(B), 이 화면은 가격이 아니라 조회수라 100ms 지연이 사업상 문제가 없었다(C)."

## 장애 시나리오와 대처

### 1. 충돌을 적지 않은 최적화 — 한 속성이 다른 속성을 무너뜨린다 (⚠ 커리큘럼)

- 현상: 성능 개선 PR(캐시 TTL 연장) 뒤에 "가격이 바뀌었는데 예전 가격으로 결제됐다"는 문의가 온다.
- 보이는 형태: 응답 시간 대시보드는 좋아졌다. 고객 문의·환불 건수, 주문 가격과 현재 가격 불일치 건수가 오른다.
- 원인: 정합성 요구가 측정치로 적혀 있지 않아 TTL을 늘릴 때 막을 근거가 없었다(실험: TTL 1000ms에서 낡은 값 98.4%).
- 대처: 정합성 시나리오를 측정치와 테스트로 적는다. 결제 경로처럼 정합성이 H인 곳은 캐시를 쓰지 않거나 결제 직전에 원본을 다시 읽는다.

### 2. 평균만 본 최적화 — 꼬리는 그대로

- 현상: "캐시로 평균 약 37배 개선"(TTL 10ms: 2114.5μs → 56.6μs) 보고 뒤에도 사용자 불만이 그대로다.
- 보이는 형태: 평균 그래프는 내려갔는데 p99 그래프는 그대로(실험 TTL 10ms: 평균 56μs, p99 약 2.1ms).
- 원인: 만료된 순간의 요청은 여전히 원본을 기다린다. 평균과 꼬리는 다른 측정치다.
- 대처: 시나리오 측정치를 p99로 적고, 만료 전에 미리 갱신하거나 갱신을 비동기로 돌린다.

### 3. 형용사 요구 — 무엇을 지켜야 하는지 아무도 모른다

- 현상: "확장성 있게", "유지보수하기 쉽게"라는 요구로 시작해 끝없는 설계 논쟁이 이어진다.
- 보이는 형태: 리뷰 코멘트가 취향 싸움이 된다. 출시 뒤 "이 정도면 되는 거냐"를 판단할 지표가 없다.
- 원인: 응답 측정치가 없는 요구는 시험할 수 없다.
- 대처: 6요소 시나리오로 다시 적고, 측정치가 합의되지 않은 요구는 효용 트리에 올리지 않는다.

### 4. 모든 속성을 H로 매긴다

- 현상: 성능도 가용성도 보안도 유지보수성도 "최우선"이다. 결국 아무것도 우선이 아니다.
- 보이는 형태: 설계 결정마다 같은 논쟁이 반복되고 일정이 밀린다.
- 원인: 맞교환은 순서를 요구한다. 효용 트리에 순서가 없으면 결정 기준이 없다.
- 대처: (중요도, 위험) 두 키로 잎을 매기게 하고, H가 너무 많으면 사업 동인으로 돌아가 다시 묻는다.

### 5. 가용성을 위한 재시도가 비용과 지연을 키운다

- 현상: 가용성을 올리려고 재시도를 3회로 늘렸더니 하류 장애 때 부하가 커지고 회복이 늦어진다.
- 보이는 형태: 하류 장애 중 요청 수가 평소의 몇 배, 앞단 p99 상승.
- 원인: 재시도 횟수는 가용성과 하류 부하·지연이 함께 걸린 맞교환점이다.
- 대처: 재시도 예산·지터·브레이커로 상한을 둔다([reliability/06-retry-backoff-jitter](../../reliability/06-retry-backoff-jitter/2-summary.md)).

## 핵심 문장

- 품질 속성은 정도의 문제이고 서로 당긴다. 충돌을 적지 않으면 한 속성의 최적화가 다른 속성을 조용히 무너뜨린다.
- ISO/IEC 25010:2023의 제품 품질 특성은 9개다. 확장성은 유연성의, 가용성은 신뢰성의 하위 특성이다.
- 품질 요구는 자극원·자극·환경·대상·응답·응답 측정치 6요소로 적어야 시험할 수 있다.
- ATAM 효용 트리는 잎 시나리오마다 (중요도, 달성 위험)을 매겨 분석 순서를 정한다. 한 파라미터가 여러 속성을 반대로 움직이면 맞교환점이다.
- 실험에서 캐시 TTL을 0 → 1000ms로 늘리자 평균 응답은 약 2.1ms → 약 1.2μs, 낡은 값은 0.1% → 98.4%가 됐다. TTL 10ms에서는 평균이 내려가도 p99는 그대로였다.
