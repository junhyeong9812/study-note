# software-design/26-functional-core-imperative-shell — 질문

## 질문

1. (왜) 할인 규칙이 리포지토리 호출 사이에 끼어 있으면 그 규칙을 시험할 때 무엇이 필요해지나? 25(DI)로 주입만 해서는 왜 부족한가?
2. (그림) 읽기 → 결정 → 쓰기 샌드위치를 그려라. 시계는 어느 층에서 읽고 어떻게 코어에 들어가나?
3. (경계) "결정을 명령 값으로 돌려준다"는 무슨 뜻인가? `sealed` 명령 타입과 패턴 매칭 `switch`를 쓰면 명령 종류를 추가할 때 무엇이 생기나?
4. (예측) VIP 10% 할인 + 1,000원 쿠폰 규칙을 두 구조로 시험했다. 판 1(I/O 사이에 낀 계산)과 판 2(코어)의 테스트에 목이 각각 몇 개 필요했나?
5. (예측) 판 1에서 쿠폰을 고객보다 먼저 읽도록 순서만 바꿨다. 결과 값은 같다. 두 테스트는 각각 어떻게 되나? 판 1 실패 메시지의 핵심은?
6. (연결) Khorikov가 말하는 좋은 테스트의 네 속성 중 실험 A의 판 1 테스트가 낮은 것은? Humble Object 패턴은 이 구조와 어떻게 이어지나?
7. (경계) 이 구조가 손해이거나 그대로 안 되는 경우 셋은? Seemann은 이 리팩터링의 적용 범위를 어떻게 말했나?
8. (장애 진단) API 화면의 할인 금액과 정산 배치 금액이 다르다. 코드 검색에 비슷한 계산이 두 곳 있다. 원인과 대처는?
9. (장애 진단) "어젯밤 11시 59분 주문만 쿠폰이 안 먹었다"가 재현되지 않는다. 구조상 원인과, 코어·셸로 나눴을 때 재현하는 방법은?
