# software-design/26-functional-core-imperative-shell — 정답

## 정답

### 1. 낀 규칙의 비용

- 규칙 두 줄(VIP 할인·쿠폰 차감)을 보려고 주문·고객·쿠폰 저장소, 이벤트 발행, 시계를 모두 흉내 내야 한다.
- DI는 그것들을 **바꿔 끼울 수 있게** 해 줄 뿐, 결정 코드가 여전히 그것들을 부른다. 그래서 테스트는 목과 호출 검증을 피할 수 없다. 이 주제는 결정 코드에서 의존 자체를 없앤다(Seemann의 "dependency rejection").

### 2. 샌드위치

```text
 셸: 읽기 (order, customer, coupon, today = LocalDate.now(clock))
        │ 값
        v
 코어: decide(order, customer, coupon, today) → Decision(total, [명령…])
        │ 값
        v
 셸: 쓰기 (명령 실행: saveTotal, markUsed, publish)
```

- 시계는 셸이 읽고 `LocalDate` **값**으로 코어에 넘긴다. 코어는 시계를 모른다.

### 3. 명령 값

- 코어가 저장·발행을 직접 하지 않고 "이것을 해라"를 값(`MarkUsed("C10")`, `SaveTotal(1, 8000)`, `Publish(...)`)으로 목록에 담아 돌려준다. 실행은 셸이 한다.
- `sealed interface Cmd permits …` + `switch (cmd) { case … }`(JDK 21)이면 명령 종류를 추가했을 때 셸의 `switch`가 모든 경우를 다루지 않아 컴파일 오류가 난다. 빠뜨린 실행 경로를 컴파일러가 잡는다.

### 4. 목 개수

(실험 A, Mockito 5.20.0, JDK 21, 2026-10-02)

```text
  판1 상호작용 테스트                        PASS  (목 4개)
  판2 코어 테스트                          PASS  (목 0개)
```

- 판 1: 주문·고객·쿠폰 저장소와 이벤트 발행, 목 4개(+ 고정 시계). 판 2 코어: 값만, 목 0개.

### 5. 순서만 바꾼 리팩터링

```text
  판1 상호작용 테스트                        FAIL  (목 4개) VerificationInOrderFailure: Verification in order failure / Wanted but not invoked: / couponRepo.find("C10");
  판2 코어 테스트                          PASS  (목 0개)
```

- 판 1은 동작이 같은데 실패했다. 테스트가 `InOrder`로 "고객 조회 다음 쿠폰 조회"라는 구현 순서를 검증했기 때문이다.
- 판 2 코어 테스트는 셸의 읽기 순서와 무관해 그대로 통과했다.

### 6. 리팩터링 내성과 Humble Object

- 네 속성(Khorikov 4장, 7장 서두에서 다시 듦): 회귀 방지, **리팩터링 내성**, 빠른 피드백, 유지보수성. 판 1 테스트는 리팩터링 내성이 낮다 — 동작을 안 바꾼 변경에 깨졌다.
- Humble Object: 시험하기 어려운 부분(I/O)을 로직 없는 얇은 껍질로 남기고 로직을 시험하기 쉬운 객체로 뺀다. 셸이 그 얇은 껍질, 코어가 로직이다.

### 7. 손해·한계

- 결정 중간에 결과에 따라 더 읽어야 할 때 — 샌드위치가 여러 겹이 되거나 미리 넉넉히 읽어야 한다.
- 미리 읽기 비용 — 안 쓸 데이터까지 조회.
- 규칙이 거의 없는 CRUD — 코어가 비어 명령 타입만 늘어난다.
- Seemann("Dependency rejection", 2017): 이런 리팩터링이 놀랄 만큼 자주 되지만, 항상 가능하다고 주장하지는 않는다.

### 8. API와 배치 금액 불일치

- 원인: 계산이 한 건 조회·저장과 엉킨 서비스 메서드에 갇혀, 대량 조회가 필요한 배치가 그것을 못 부르고 복사본을 만들었다. 시간이 지나 한쪽만 고쳐졌다.
- 대처: 계산을 순수 코어로 꺼내 API 셸과 배치 셸이 같은 함수를 부른다. 실험 B에서 배치가 저장소 없이 주문 3건을 같은 규칙으로 계산했다.

### 9. 재현 안 되는 시각 버그

- 원인: 코어가 `LocalDate.now()`·`Math.random()`을 스스로 읽어, 결정에 쓴 입력이 기록되지 않았다.
- 재현: 셸이 시각·난수를 읽어 값으로 넘기고, 결정 입력(주문·고객·쿠폰·today)을 로그에 남긴다. 그 입력으로 코어를 다시 호출하면 같은 결정이 나온다(순수 함수는 같은 입력에 같은 출력).
