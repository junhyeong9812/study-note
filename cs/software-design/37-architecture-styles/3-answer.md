# software-design/37-architecture-styles — 정답

## 정답

### 1. 고르는 기준

- 기능이 아니라 **품질 속성(아키텍처 특성)** 과 **잦은 변경 축**으로 고른다.
- Richards–Ford 1장: 아키텍처 특성("-ilities")은 기능과 직교하는 시스템의 성공 기준이다. 첫 번째 법칙 "Everything in software architecture is a tradeoff." 따름정리: 트레이드오프가 아닌 것을 찾았다면 아직 트레이드오프를 못 찾은 것이다.

### 2. 기술 분할 vs 도메인 분할

```text
 기술 분할:  [표현] [업무] [영속]           ← 계층형
 도메인 분할: [결제] [주문] [정산]           ← 서비스 기반·마이크로서비스
```

- 마이크로커널은 둘 다 가능하다. 코어/플러그인 경계는 기술 분할이고, 플러그인을 업무 종류(결제 수단)로 나누면 도메인 분할이다(Richards–Ford 12장 평가, 독자 노트로 확인 — 책 본문 미열람).

- 자주 오는 변경이 어느 축을 따라오나로 정한다. 기술 층을 따라 바뀌면 기술 분할, 업무 영역·종류를 따라 바뀌면 도메인 분할.

### 3. 새 결제 수단 추가

(실험 A, 2026-10-02)

```text
layered r1-new-method 기존파일수정=2 새파일=0
kernel r1-new-method 기존파일수정=1 새파일=1
```

- 계층형: `PaymentService`의 수수료 `switch`와 `LimitPolicy`의 한도 `switch`에 한 줄씩 — 기존 업무 코드 2곳.
- 마이크로커널: `PointPlugin.java` 새 파일 + 등록 파일(`META-INF/services/core.PaymentPlugin`) 한 줄. Java 기존 코드 수정 0.

### 4. 모든 결제에 통화 추가

```text
layered r2-currency 기존파일수정=4 새파일=0
kernel r2-currency 기존파일수정=5 새파일=0
```

- 계층형: 컨트롤러·서비스·리포지토리·Main, 층마다 한 곳.
- 마이크로커널: 계약·커널·Main + **모든 플러그인**(Card·Kakao).
- 비례 대상: 계층형 R1은 같은 `switch`가 있는 곳의 수, 마이크로커널 R2는 플러그인 수. 플러그인 2개에서만 측정했으므로 비례는 구조에서 나온 추론이다.

### 5. 하류 장애 중 가용성

(실험 B, 결정적 모형)

```text
동기 호출 스타일 : 주문 성공 700/1000 (70.0%)
이벤트 스타일    : 주문 성공 1000/1000 (100.0%), 알림 전달 1000건, 최대 큐 길이 301, 알림 최대 지연 300초
```

- 동기: 다운 시간만큼 주문 실패(30%).
- 이벤트: 주문 전부 수락, 알림은 모두 전달됐지만 최대 300초 지연, 큐 최대 301건.

### 6. 이벤트가 "더 좋은가"

- 말할 수 없다. 가용성(접수율)을 얻고 즉시성·일관성을 내줬다.
- "주문 직후 알림이 반드시 즉시 가야 한다"(예: 결제 인증 알림)가 요구라면 최대 300초 지연은 품질 미달이다. 모형의 수치는 가정(다운 300초, 처리율 5건/초)에서 나온 것이다.

### 7. 마이크로커널의 전제

- 원본 1.3: 코어 계약을 정확히 그을 수 있을 때만 유효하다. 계약을 바꾸면 모든 플러그인이 깨진다.
- 실험 A R2: 공통 속성(통화)이 늘자 계약·커널·플러그인 전부가 바뀌었다. 변동성이 "종류"가 아니라 "공통 속성"에 있으면 이 스타일은 손해다.

### 8. 판단 순서와 변경 축 찾기

1. 품질 속성 상위 몇 개를 고른다.
2. 각 속성을 시험 가능한 시나리오 문장으로 쓴다.
3. 후보 스타일에 시나리오를 대 본다(스파이크·모형).
4. 버리는 속성을 적는다.
5. ADR로 남긴다.

```bash
git log --since=6.months --name-only --pretty=format: | sort | uniq -c | sort -rn | head
```

- 이 명령은 파일별 변경 횟수(빈도)를 센다. 자주 바뀌는 파일들이 같은 커밋에 함께 나오는지(커밋별 `--name-only` 목록)를 보면 변경 축이 드러난다.

### 9. 스타일-요구 불일치

- 의심: 스타일이 품질 우선순위·잦은 변경 축과 맞지 않는다(⚠ 품질 속성 미달).
- 형태: 같은 파일 묶음 반복 수정(실험 A 계층형 R1의 `switch` 2곳), 하류 장애 때 성공률 급락(실험 B 동기 70%).
- 대처: 품질 속성 재정의 → 문제 경로만 다른 스타일로(결제 수단만 플러그인화, 알림만 이벤트 분리). ADR로 기록.

### 10. 이벤트 전환 뒤 알림 지연

- 지표: 소비자 적체(consumer lag)·큐 길이 증가, 주문 시각과 처리 시각 차이 분포가 장애 시간만큼 늘어남(실험 B 최대 300초, 큐 301).
- 대처: 즉시성이 필요한 단계는 동기로 되돌리거나 화면에 "처리 중" 중간 상태를 보인다. 적체 경보를 둔다. 그 경로의 요구가 즉시성이었다는 것을 ADR에 반영한다.
