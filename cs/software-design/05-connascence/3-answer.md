# software-design/05-connascence — 정답

## 정답

### 1. 왜·정의

- 결합도 단계는 "얼마나 나쁜가"를 큰 칸으로 나눌 뿐, 무엇을 어떻게 고칠지 말하지 않는다. 커너선스는 함께 바뀌어야 하는 이유에 종류 이름을 붙여 "더 약한 종류로 바꾸자"는 방향까지 전한다.
- 정의: 하나를 바꾸면 시스템이 올바르려면 다른 하나도 바꿔야 하는 관계. Page-Jones가 도입(CACM 1992).

### 2. 종류

- 정적: 이름·타입·의미·위치·알고리즘.
- 동적: 실행 순서·타이밍·값·동일성.
- 정적이 약하다. 소스만 보고 찾을 수 있기 때문이다. 동적은 실행 시 동작을 알아야 해서 추론하기 어렵다(connascence.io "Strength").

### 3. 세 축

- 강도: 그 종류를 찾고 리팩터링하기가 얼마나 어려운가.
- 지역성: 묶인 요소가 얼마나 가까운가. 강한 것도 한 모듈 안이면 더 받아들일 만하다.
- 정도: 몇 개를 묶나(2개 vs 200개).
- "무조건 나쁘다"는 틀리다. 같은 메서드 안의 짧은 위치 커너선스는 흔하고 무해하다. 멀리 떨어져 있고 정도가 클 때 문제다.

### 4. 인자 뒤바꿈

(실험, JDK 21.0.12, 2026-10-02)

```text
잔액 {alice=1300, bob=700}
```

- 컴파일·실행 모두 통과한다. 의도(alice → bob 300)의 반대로 돈이 갔다. 같은 타입 인자의 위치 커너선스.

### 5. 의미 커너선스

```text
포장 완료 주문(status=3)에 대한 알림: 배송이 시작됐습니다
배송 시작 주문(status=4)에 대한 알림: (알림 없음)
```

- 예외 없이 틀린다. 숫자의 뜻에 대한 합의가 한쪽만 바뀌었다.

### 6. 타입으로 바꾼 뒤

```text
weak/Swapped.java:6: error: incompatible types: To cannot be converted to From
```

- 위치 커너선스가 타입(과 이름) 커너선스로 바뀌었다. 같은 실수가 컴파일 오류가 된다. 대가로 타입 `From`·`To`가 생겼다.

### 7. grep vs javac

- `grep -rnw 3`: 6줄. 실제 배송 상태는 3곳(`Notifier` `status == 3`, `Report` `s == 3`, `Api` `case 3`). 나머지 3줄은 재시도 횟수·페이지 수·문구의 `3`(거짓 양성).
- `send` → `deliver` 이름 변경 후 `javac`: 오류 3건 = 호출 3곳. 거짓 양성 0.
- 이름은 컴파일러가 정확히 찾으니 약하고, 의미는 사람이 판정해야 하니 강하다.

### 8. 사라지지 않는다

- 상수로 바꾸면 의미 → 이름으로 **약해질** 뿐이다. 상수를 둘 곳이 하나 더 생겨 이름 커너선스의 양은 늘어난다(connascence.io "Meaning").
- record로 묶어도 생성자 `new Transfer(from, to, amount)`에 순서가 남는다. 같은 타입 필드 둘이면 위치 커너선스가 생성자로 옮겨갈 뿐이다. 서로 다른 타입(`From`·`To`)이나 이름 붙인 빌더여야 컴파일러가 잡는다.

### 9. init 누락 NPE

- 실행 순서 커너선스(`init()` 다음에 `send()`).
- 생성자에서 초기화를 끝내거나(`new Mailer(config)`), 초기화 전/후를 다른 타입으로 나눠 초기화된 객체만 `send`를 갖게 한다. 실험 B의 생성자 버전은 `sent via smtp:bob`으로 정상 동작하고, 잘못된 순서를 쓸 방법이 없다.
