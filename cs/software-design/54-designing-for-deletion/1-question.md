# software-design/54-designing-for-deletion — 질문

## 질문

1. (왜) tef가 "확장하기 쉬운 코드보다 지우기 쉬운 코드"를 쓰라고 하는 이유는? "생산한 줄"과 "쓴 줄"의 차이로 설명하라.
2. (경계) tef의 "의존을 만들지 않으려고 반복하라, 의존을 관리하려고 반복하지는 마라"는 DRY와 충돌하나? 공유 API가 바꾸기 어려워지는 이유는?
3. (그림) 루트에서의 도달성으로 죽은 코드 후보를 찾는 그림을 그려라. 정적 분석이 놓치는 간선 종류를 셋 이상 대라.
4. (예측) 같은 패키지 클래스들에 `jdeps -verbose:class`를 기본 옵션으로 돌려 도달성을 계산하면 결과는? `-filter:none`을 주면? 실험 출력으로 답하라.
5. (예측) 정적 후보 셋(`LegacyCsvExporter`·`OldPriceCalc`·`RoundingHelper`)을 모두 지우면 컴파일과 실행은 각각 어떻게 되나?
6. (예측) 플래그 분기가 다섯 파일에 흩어진 설계와 팩토리 한 곳에 모인 설계에서 플래그를 지우는 커밋은 각각 몇 파일을 바꾸나? 처음 구조의 비용은 어떻게 달랐나?
7. (장애 진단) 다 쓴 플래그를 설정 저장소에서만 지웠더니 옛 화면이 다시 나온다. 원인과 대처는? 어떤 실사건과 같은 유형인가?
8. (장애 진단) 제거 예정 API의 호출 수가 다시 늘었다. `@Deprecated(forRemoval = true)`만으로 왜 못 막았나? 실험의 종료 코드로 답하라.
9. (경계) 주석 처리한 코드를 남겨 두는 대신 무엇을 쓰나? 지운 코드를 다시 찾는 git 명령은?
10. (연결) Hodgson이 피처 토글의 "carrying cost"를 줄이려고 제시하는 팀 실천 네 가지는? 이것이 50(Strangler Fig의 마지막 단계)과 어떻게 이어지나?
