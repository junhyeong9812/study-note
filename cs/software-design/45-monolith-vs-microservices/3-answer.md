# software-design/45-monolith-vs-microservices — 정답

## 정답

### 1. 두 축 2×2

```text
                 경계 강제 안 함          경계 강제
 배포 단위 1개    큰 진흙 공 모놀리스       모듈러 모놀리스
 배포 단위 N개    분산 모놀리스  ⚠          마이크로서비스
```

- 분산 모놀리스는 "배포 단위 N개 + 경계 강제 안 함" 칸이다.
- 가장 나쁜 이유: 분산의 비용(네트워크 지연·부분 실패·최종적 일관성)은 내면서, 함께 바꾸고 함께 배포해야 하는 결합은 그대로 남는다.

### 2. 정의와 선행 조건

- 정의(Lewis·Fowler 2014): 작은 서비스 여럿이 각자 프로세스로 돌고, 가벼운 통신(흔히 HTTP 리소스 API)을 쓰며, 비즈니스 능력 단위로 만들고, **완전 자동화된 배포 장치로 독립 배포**한다.
- 선행 조건(Fowler 2014 "MicroservicePrerequisites"): 빠른 프로비저닝, 기본 모니터링(기술·비즈니스 지표), 빠른 애플리케이션 배포(배포 파이프라인).
- 이 셋이 없으면 이 방식을 고려하지 말라는 것이 저자의 주장이다.

### 3. 메서드 호출 vs HTTP 3홉

(실험 A, JDK 21.0.12 temurin, `--cpus=2`, nodelay 켬, 3회 실행)

```text
인프로세스 메서드 3단계  평균      2.0us  p50      1.3us  p99      8.7us
localhost HTTP 3홉       평균   3705.6us  p50   3167.0us  p99  19694.9us
```

- 3회에서 메서드 호출 p50은 0.9~1.3μs, HTTP 3홉 p50은 2978~3167μs였다. 같은 조건으로 다시 돌린 2회는 1.2~1.7μs, 3324~3443μs였다(실행마다 다르다). 이 환경에서 수천 배다.
- 진짜 네트워크가 아닌 localhost에서도 이만큼 차이가 난다. 직렬화·소켓·스레드 전환 비용이다. 수치는 `--cpus=2`로 제한한 이 환경의 값이다.

### 4. 기본 설정의 50ms

- `-Dsun.net.httpserver.nodelay=true`(JDK 내장 서버에서 `TCP_NODELAY`를 켜는 속성, 기본 false)를 주자 p50이 약 49ms → 약 3ms로 줄었다.
- 해석: Nagle 알고리즘과 지연 ACK의 상호작용으로 본다.
- 교훈: 분산으로 바꾸면 메서드 호출에는 없던 층(소켓 옵션·커넥션 풀·타임아웃·직렬화)이 생기고, 그 기본값 하나가 지연을 지배할 수 있다. 쪼개는 비용에는 이런 층을 아는 비용도 들어 있다.

### 5. 같은 컬럼 변경의 파급

(실험 B, git 2.43.0)

공유 DB 설계:

```text
### 함께 배포해야 하는 서비스:
billing order shipping 
```

데이터 소유 + 계약 설계:

```text
### 함께 배포해야 하는 서비스:
order 
```

- 공유 DB: 3개 서비스(파일 3개, 5줄 추가·5줄 삭제).
- 데이터 소유: order 1개(파일 2개, 3줄·3줄). `OrderApi.toView`가 내부 행 → 계약 번역에서 변경을 흡수했다.

### 6. 계약 자체가 바뀌는 변경

- 소비자가 새 정보를 원해 계약(`OrderView`)에 필드를 더할 때다. 실험에서는 배송이 `zip`을 따로 원하자 `contracts`·`order`·`shipping` 세 곳이 바뀌었다.
- 안전한 순서: **expand**(생산자가 새 필드를 추가해 먼저 배포, 옛 필드 유지) → **migrate**(소비자가 하나씩 새 필드로 옮김) → **contract**(아무도 안 쓰면 옛 필드 제거).
- 필드 추가만이라면 소비자는 모르는 필드를 무시하게 만들어 두고 각자 일정대로 옮긴다.

### 7. 동기 체인

- 가용성은 곱해져 떨어지고, 지연은 더해진다. 홉이 많을수록 그중 하나가 꼬리 지연에 걸릴 확률이 커진다.
- 0.999^5 ≈ 0.995, 약 99.5%다(reliability/01에서 공식 99.5010%, 시뮬레이션 99.4957%로 확인).
- 실험 A에서 결제 하나를 내리자 주문까지 502가 됐다. 체인의 한 칸이 전체 실패가 된 것이다.

### 8. 분산 모놀리스 진단

- 증거
  - `git log --name-only`로 커밋(또는 티켓)마다 함께 바뀐 서비스를 세면 같은 묶음이 반복된다.
  - 배포 기록에서 같은 시각에 함께 나간 서비스 수가 크다.
  - 배포 직후 역직렬화 실패·누락 필드 400·SQL "column does not exist" 같은 오류가 다른 서비스에서 난다.
  - 공유 DB 테이블, 공유 도메인 모델 라이브러리가 있다.
- 대처
  - 늘 같이 바뀌는 서비스는 합치는 것도 선택지다.
  - 테이블 소유자를 하나로 정하고 계약(DTO·이벤트)으로 읽게 한다.
  - 계약은 expand → migrate → contract로 바꾼다.

### 9. MonolithFirst와 반대 사례

- Fowler(2015)의 이유
  - 첫째, YAGNI. 새 애플리케이션은 쓸모가 있는지부터 빨리 확인해야 하므로 마이크로서비스 비용(premium)은 짐이다.
  - 둘째, 서비스 경계를 처음에 맞히기 어렵고, 서비스 사이 리팩터링은 모놀리스 안보다 훨씬 어렵다.
  - 같은 글에 반론도 소개하고, 조언이 잠정적이라고 밝힌다.
- 반대 사례: Prime Video 모니터링 서비스(2023)
  - Step Functions·Lambda 분산 구성을 한 프로세스로 합쳐 인프라 비용을 90% 넘게 줄였다고 보고했다.
  - 원인은 둘이었다. 상태 전이마다 과금되는 오케스트레이션과, 프레임을 S3에 올려 주고받는 데이터 전달이다.
  - 예상 부하의 약 5%에서 확장 한계에 걸렸다고 적는다.
