# software-design/49-multi-tenancy — 정답

## 정답

### 1. 사일로·풀·브리지

```text
 사일로: 테넌트마다 전용 자원(전용 스택 전체 또는 전용 DB만)
 풀:     테넌트가 자원 공유(컴퓨트·스토리지·메시징의 일부 또는 전부)
 브리지: 서비스마다 섞음(어떤 서비스는 사일로, 어떤 것은 풀)
```

- AWS SaaS Lens: 사일로라도 **신원(identity)·가입(onboarding)·운영 경험은 공유 구조**로 관리한다. 이것이 고객마다 따로 돌리는 관리형 서비스와의 차이다.

### 2. 4단계와 스펙트럼

- 행 단위 = 풀(데이터까지 공유). 스키마 분리는 같은 DB 공유 + 논리 분리로 중간이다. DB 분리·인스턴스 분리 = 사일로 쪽(전용 DB, 전용 스택).
- 원본의 4단계는 스펙트럼을 데이터 층에서 더 잘게 나눈 것이다.
- 브리지에서 사일로 쪽에 두는 서비스: 데이터의 규제 성격이 강한 것, 시끄러운 이웃 특성이 큰 것(AWS SaaS Lens). 민첩성·접근 패턴·비용이 중요한 서비스는 풀 쪽에 둔다.

### 3. 캐시 키 = id

(실험 A, JDK 21.0.12)

```text
== 캐시 키 = id
  요청 테넌트=acme → Invoice[tenant=acme, id=INV-1, amount=990000]
  요청 테넌트=globex → Invoice[tenant=acme, id=INV-1, amount=990000]
  DB 조회 수=1, 캐시 키=[INV-1]
```

- globex가 acme의 청구서(990000)를 받았다.
- DB는 1번만 조회됐다. 두 번째 요청은 tenant 조건이 있는 SQL에 닿지도 않았다.
- 키를 `tenant|id`로 바꾸면 DB 조회가 2번으로 늘고 각자 자기 것을 받았다. 격리의 대가로 캐시 적중이 줄었다.

### 4. RLS로 막을 수 있나

- 막을 수 없다. 캐시가 DB **앞**에 있어서, 적중한 요청은 DB에 가지 않는다. RLS는 DB에 도착한 쿼리에만 술어를 붙인다.
- 캐시·검색 인덱스·메시지 같은 DB 밖 저장소는 각자 키에 tenant를 넣어야 한다.

### 5. 기본 키 생성

- Spring Framework 7.0.9 레퍼런스 "Default Key Generation": 인자가 없으면 `SimpleKey.EMPTY`, **하나면 그 인자 자체**, 여럿이면 모든 인자를 담은 `SimpleKey`.
- tenant를 `ThreadLocal`·보안 컨텍스트로 넘기면 메서드 인자에 tenant가 없다. 그래서 키에도 없다. 실험 A의 `findBad`와 같은 누출이 생긴다.
- 대처: `key = "#tenant.value() + '|' + #id"`처럼 명시하거나, tenant를 메서드 인자로 받는다.

### 6. 시끄러운 이웃

(실험 B, 1회차)

```text
공용 FIFO 풀(워커 4)              B 응답(ms) 최소  920  중앙  968  최대 1011   A 200개 끝난 시각  1026ms
테넌트 쿼터(A 동시 3개)              B 응답(ms) 최소    2  중앙    2  최대    2   A 200개 끝난 시각  1367ms
```

- 공용 풀: B의 2ms 작업이 약 1초 걸렸다(3회 중앙값 967~969ms, 같은 조건 재실행 3회 965~968ms). A 200개 뒤에 줄을 섰기 때문이다.
- 쿼터: B는 2ms(3회 모두). A는 1026ms → 1367ms로 늦어졌다(3회 1366~1367ms, 재실행 3회 1367~1369ms).
- 쿼터는 공정함을 사고 큰 테넌트의 최대 처리량을 낸다.

### 7. Azure의 관점

- 원인과 상관없이 **자원 거버넌스 문제**로 다룬다. 사용 쿼터·스로틀링·거버넌스 통제를 둔다. 스로틀링이 있으면 고객에게 투명하게 알린다.
- 대부분의 테넌트는 의도하지 않고 문제를 일으킨다.
- 각 테넌트가 용량의 작은 부분만 써도 **사용 피크가 겹치면** 합이 용량을 넘어 생긴다.

### 8. tenant_id 파티셔닝

- 얻는 것: 한 테넌트 데이터가 한 파티션에 모인다. 테넌트 안 조회가 한 곳에서 끝나고, 테넌트 단위 이동·삭제·백업이 쉽다.
- 위험: 큰 테넌트 하나가 한 파티션을 포화시킨다(핫 파티션).
- 매핑 테이블(tenant → 샤드)을 두면 큰 테넌트를 전용 샤드·셀로 옮길(사일로 승격) 수 있다. 해시 함수만 쓰면 위치가 함수로 정해져 개별 테넌트를 옮길 수 없다.

### 9. 가끔 보이는 남의 청구서

- 간헐적이라는 점에서 **캐시 키 누락(L6)**을 먼저 의심한다. 캐시가 비어 있을 때는 SQL의 tenant 조건이 작동해 정상이고, 다른 테넌트가 먼저 채운 항목에 적중할 때만 샌다(실험 A).
- 그 밖에 조건 누락 경로(L1·L3·L4)도 점검한다.
- 즉시 조치: 해당 캐시를 비우고 키에 tenant를 넣어 배포한다. 접근 로그로 영향받은 테넌트·기간을 산정하고 통지 의무를 검토한다.
- 재발 방지
  - tenant를 타입 인자로 강제한다.
  - 캐시 정의 전수 점검(`@Cacheable` 중 tenant가 없는 것).
  - DB에는 RLS를 둔다.
  - 모든 조회 경로에 "옆집 식별자" 시험을 둔다.

### 10. 비동기에서 사라지는 tenant

- 원인: tenant를 `ThreadLocal`에 두었는데 스레드 풀·`@Async`로 넘어가며 전파되지 않았다(NULL). 또는 풀 스레드에 이전 작업의 값이 남았다(다른 테넌트).
- 대처
  - tenant를 메서드 인자·메시지 필드로 명시해서 넘긴다.
  - `ThreadLocal`을 쓰면 작업 시작에 설정하고 끝에 finally로 비우는 래퍼(데코레이터)를 둔다.
  - DB 세션 변수도 트랜잭션 범위로만 둔다.
  - `tenant_id NOT NULL` 제약으로 NULL 행은 저장 시점에 막는다.
