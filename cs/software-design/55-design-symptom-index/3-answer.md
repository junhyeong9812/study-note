# software-design/55-design-symptom-index — 정답

## 정답

### 1. "깨졌다"의 모양과 여섯 칸

- 설계 영역에서 깨짐은 대개 크래시가 아니다. **변경 비용 폭증**(PR 크기·충돌·리뷰 시간)과 **조용한 결합**(에러 없는 값 차이)으로 보인다(커리큘럼 §12 머리말).
- 여섯 칸: ① PR·diff·병합 → ② 컴파일·정적 검사 → ③ 기동 → ④ 테스트 → ⑤ 운영 예외 → ⑥ 운영의 조용한 값 오류.
- 늦을수록 비싼 이유
  - 발견까지의 시간이 길다. ⑥은 대사·고객 문의·월말 보고로 며칠 뒤에 드러난다.
  - 그 사이 잘못된 데이터가 쌓인다. 코드를 고쳐도 이미 저장된 불법 행은 고쳐지지 않는다(20-1·23-1).
  - 원인 자리와 증상 자리가 멀어진다. 늦은 실패의 스택 맨 위는 증상 자리다(15-4).
- 그래서 좋은 설계 결정 상당수는 같은 결함을 위 칸으로 끌어올린다. 예: `default` 없는 `switch` 식(⑥ → ②), 생성자 주입(⑤ → ③), 필수 설정에 기본값 없음(⑥ → ③).

### 2. "파일 12개" PR의 두 원인

첫 질문: **바뀐 파일들은 무엇인가?**

| 바뀐 파일이 | 원인 | 처방 | leaf |
|---|---|---|---|
| 같은 지식의 사본(같은 `switch`, 같은 세율, 같은 필드 목록)이 여러 계층에 | 흩어진 결정 — Shotgun Surgery, 처리 단계별 분해 | 결정을 한 인터페이스·한 모듈로 모으는 정리 커밋을 먼저 | 04-1 · 10-1 · 01-1 |
| 위임만 하는 인터페이스·팩토리·매퍼·레지스트리 | 쓰이지 않는 간접 계층(과설계, carry 비용) | 구현 하나짜리 인터페이스·팩토리를 인라인. 둘째 변형이 실제로 오면 다시 추출 | 12-1 · 27-1 · 44-3 · 03-1 |

- 한 번 넓게 바뀐 것보다 **같은 유형의 요구가 매번 같은 묶음을 건드리는가**가 신호다. 같은 유형의 과거 커밋 `--stat`과 비교한다.
- 반대 처방을 잘못 적용하면 악화한다. 간접 계층이 원인인데 레지스트리를 더 얹으면 다음 요구는 파일이 더 늘어난다(장애 시나리오 1).

### 3. 새 상태 누락 — `default` 유무

- (가) `default`가 있는 `switch` 문: 컴파일·실행 모두 성공한다. 새 상태가 기본 분기로 흘러 `label=기타`, 환불 주문이 "대기"로 보인다(28-2 실험 B v1, 24-5). ⑥ 칸 — 고객 문의·대사로 늦게 발견.
- (나) `sealed` + `default` 없는 `switch` 식: 컴파일 오류로 멈춘다. ② 칸.
- javac 메시지(JDK 21.0.12, 이 노트 실행): `error: the switch expression does not cover all possible input values`.
- 대처는 (나)로 바꾸는 것 하나가 아니다. 같은 `switch`가 여러 파일에 있다면 타입별 지식을 한 곳(enum 상수·다형성)으로 모으는 것이 근본이다(28-2 v3, 29-2).

### 4. `because "this.repo" is null` — 생성자 주입했는데

- 의심: 그 메서드가 **final**이다. CGLIB 서브클래스 프록시는 final 메서드를 재정의하지 못한다. 호출이 대상 객체로 위임되지 않고 프록시 인스턴스에서 본문이 실행된다. 프록시 인스턴스의 필드는 초기화되지 않았으므로 `repo`가 null이다(33-2, 33 실험 C3, Spring Framework 6.2.11).
- 확인: 메서드 선언의 `final`, DEBUG 로그의 `cannot get proxied via CGLIB` 줄(33 — `CglibAopProxy` 소스).
- null 검사로 닫으면: 예외(⑤)가 사라지고 결제가 조용히 저장되지 않는 ⑥ 칸 실패로 내려간다. 트랜잭션·캐시 같은 어드바이스도 여전히 그 메서드에 적용되지 않는다.
- 대처: final을 떼거나, 메서드를 인터페이스에 올려 JDK 프록시를 쓴다.

### 5. `because` 뒤 읽기

| `because …` | 먼저 볼 설계 원인 | leaf |
|---|---|---|
| `"<local5>"` (지역 변수) | 반환값이 null — "없음"을 null로 돌려주는 설계. 목록이면 빈 컬렉션으로 | 18-1 |
| `"this.conn"` | 호출 순서 결합 — `init()` 전에 `send()` | 05-3 |
| `"this.clock"` (+ `@PostConstruct` 로그 없음) | 컨테이너 밖에서 `new`로 만든 객체 — 주입·훅 미적용 | 32-3 |

- `<local0>` vs `c`: 같은 소스라도 **컴파일 옵션**이 다르다. JEP 358에 따르면 지역 변수 표가 있으면 변수 이름을, 없으면 `<local i>`를 쓴다. 이 노트 실행(JDK 21.0.12)에서 `javac`는 `<local0>`, `javac -g`는 `"c"`였다. 빌드 설정(디버그 정보 포함 여부)에 따라 메시지가 달라 보일 뿐 같은 결함이다. 필드는 `this.conn`처럼 이름이 나온다.

### 6. "빈 하나 추가했더니 기동이 안 된다"

| 메시지 | 원인 | leaf |
|---|---|---|
| `BeanCurrentlyInCreationException: … Requested bean is currently in creation: Is there an unresolvable circular reference …` (Spring Framework 6.2.11) | A→B→A 순환 주입. 한 클래스가 두 책임 | 25-3 |
| `APPLICATION FAILED TO START` … `required a single bean, but 2 were found` (Spring Boot 3.5.6) | 자동 설정의 `@ConditionalOnMissingBean` 대상이 구현 클래스라 사용자 구현을 못 봄 | 36-2 |
| `Could not generate CGLIB subclass of class …` / `Cannot subclass final class` (Spring Framework 6.2.11) | 애스펙트가 걸리는 빈이 final 클래스 | 33-3 |

- 스위치로 덮으면 안 되는 이유: 기동 실패는 조립 오류를 ③ 칸에서 잡아 준 **좋은 신호**다.
  - 순환 허용은 설계 결함(책임 둘)을 그대로 둔다. Seemann–van Deursen은 프로퍼티 주입으로 순환을 끊는 것을 최후 수단이라 부르고(6.3.5절), 25번은 `allow-circular-references`로 허용하는 것도 같은 부류로 본다(해석, 25-3). 게다가 이 스위치는 세터·필드 순환만 띄우고, 생성자 순환은 켜도 같은 예외로 실패한다(25 실험 E).
  - 덮어쓰기 허용은 이름이 같은 빈에만 듣는다(이름이 다른 `2 were found`는 켜도 그대로). 켜면 같은 이름의 자동 설정 빈이 사용자 정의를 이겨 **오류 없이** 기본 구현이 주입될 수 있다(36 실험 B의 C: `주입된 구현=Default(자동 설정)`). ③이 ⑥으로 내려간다.
- 대처: 공통 부분 추출·이벤트로 순환 끊기, `@ConditionalOnMissingBean(인터페이스.class)`, final 제거 또는 인터페이스 + JDK 프록시.

### 7. `@Audited`가 조용히 꺼짐

- 원인: `@Retention`을 생략하면 기본 정책이 `CLASS`다(`Retention` API 문서). 클래스 파일에는 남지만 런타임 리플렉션(`getAnnotation`)에서는 보이지 않는다. 이 노트 실행: `CLASS(기본) 보존 어노테이션 보임? false`, `RUNTIME … true`.
- 확인: `javap -v <클래스>`에서 `RuntimeVisibleAnnotations`에 그 어노테이션이 있는가(35-2). 회귀 방지로 "스캔 결과 ≥ 1" 테스트.
- 칸: 감사 로그 누락이면 ⑥(조용함)이다. 리플렉션은 "없다"를 오류가 아닌 `null`·빈 목록으로 돌려주고, 컴파일러는 보존 정책과 사용 방식의 불일치를 검사하지 않는다. 같은 실수가 라우팅이면 404로 ⑤ 칸에 보인다(35 실험 A의 직접 만든 스캐너).

### 8. 테스트 증상 둘

| 증상 | 설계 원인 | 첫 진단 | leaf |
|---|---|---|---|
| 테스트를 쓸 수 없다(`ConnectException: Connection refused`, 하네스에서 생성조차 안 됨) | 정책 클래스가 세부 구현을 `new`로 생성(DIP 부재), 숨은 의존이 메서드 안에 | 생성자·메서드 안의 `new`·정적 호출 grep | 22-2 · 51-1 · 38-1 |
| 리팩터링마다 수십 개가 깨지고 동작은 그대로(`VerificationInOrderFailure`, `TooManyActualInvocations`, Mockito 5.20.0) | 계산이 I/O 호출 사이에 끼어 테스트가 결과 대신 호출 순서를 검증 | 실패한 단언이 값인가 상호작용인가 | 26-1 · 25-4 |

- 둘 다 "테스트하기 어려움 = 설계 신호"다. 처방도 이어진다. 의존을 주입하고(25), 계산을 순수 함수로 빼서 값으로 검증한다(26).

### 9. 조용한 값 오류 다섯

| 증상 | 흔한 설계 원인 | leaf |
|---|---|---|
| 고친 곳이 아닌 화면·정산의 1원 차이 | 같은 지식이 다른 모양으로 여러 곳(grep·jdeps에 안 걸리는 암묵 의존) | 01-2 · 11-4 |
| `label=기타` | `default`·마지막 `else`가 새 타입을 삼킴, `switch` 복제 | 28-2 · 22-3 |
| 남의 주문 조회 | `userId`·`orderId`가 둘 다 `Long` — 인자 뒤바뀜이 컴파일을 통과 | 24-1 |
| `PAID`인데 `paidAt=null` | 상태와 필드를 독립 컬럼으로 — 불법 조합이 표현 가능 | 24-3 |
| 예외 뒤에도 앞서 쓴 행이 남음 | `@Transactional` 자기 호출(프록시 우회), checked 예외(기본 롤백 규칙은 unchecked·`Error`만) | 33-1 · 16-1 |

- 공통 대처: 원인 코드를 고치고, 이미 쌓인 데이터를 따로 찾아 보정한다. 한쪽만 하면 재발하거나 과거 데이터가 남는다(장애 시나리오 5).

### 10. 세 오독이 틀리는 조건

- **"추상화하면 좋아진다"**: 추상화는 예측한 축의 변경만 싸게 한다. 축이 틀리면 패턴 판 6파일(진입점 Main 포함)·19줄 추가 대 plain 1파일·10줄 추가(27 실험 A). 1:1 매핑 계층은 필드 하나에 4파일(44 실험 B). 안 쓰는 확장 구조는 할인 하나에 7파일(12 실험 SPEC v2).
- **"복잡도 지표만 낮추면 된다"**: 게이트를 맞추려 쪼개면 메서드별 숫자는 임계 아래로 내려가도 클래스 합계는 오른다(52 실험 c: 순환 14 → 합계 19, 인지 13 → 합 15). 흐름이 여러 파일로 흩어진다. 지표는 어디를 볼지 정하는 데 쓴다.
- **"테스트가 통과하니 리팩터링은 안전하다"**: 테스트는 고른 입력만 지킨다. 반올림 위치를 옮긴 리팩터링이 행복 경로 테스트를 통과하고 정산에서 1원씩 어긋났다(13 실험 A). 새 타입을 모르는 테스트는 `tests: 6 pass, 0 fail`인데 출력은 `label=?`였다(29 실험 A). 리팩터링 전에 넓은 입력으로 현재 동작을 고정한다(골든 마스터·특성 테스트).
