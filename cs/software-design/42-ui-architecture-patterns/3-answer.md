# software-design/42-ui-architecture-patterns — 정답

## 정답

### 1. 섞이면 생기는 일

- 같은 규칙을 다른 화면·API에서 재사용할 수 없어 복사되고 어긋난다.
- 규칙을 화면 없이 테스트할 수 없다.
- Fowler("GUI Architectures", 2006): MVC의 핵심이자 이후 프레임워크에 가장 영향력이 컸던 생각은 **표현 분리(Separated Presentation)** — 도메인 객체와 화면 객체를 나누고 도메인은 화면을 모르게 한다.

### 2. 패턴별 흐름

```text
 Smalltalk MVC  입력→컨트롤러→모델 변경→(이벤트)→뷰가 모델을 읽어 다시 그림
 MVP            입력→위젯→프레젠터→모델 변경/뷰 조작
 MVVM           뷰 ⇄(데이터 바인딩)⇄ 뷰모델 → 모델
 서버 MVC       요청→Front Controller→핸들러→모델→Template View
 Flux           뷰→액션→디스패처(하나)→스토어→뷰
```

### 3. 두 동기화

- 옵서버 동기화: 모델이 이벤트를 내고 구독한 뷰들이 스스로 갱신. 흐름 동기화: 바꾼 쪽 코드가 갱신할 화면을 직접 부른다.
- 옵서버의 단점(Fowler): 코드를 읽어서는 무슨 일이 일어나는지 알 수 없다. 동작이 암묵적이라 디버거와 trace 문으로만 보인다.

### 4. 진동하는 바인딩

(실험, node v22.23.2, 2026-10-02)

```text
입력 8000: 갱신 2회, 최종 subtotal=8000 discount=0 total=8000
입력 12000: 갱신 4회, 최종 subtotal=12000 discount=1200 total=10800
입력 10500: RangeError: Maximum call stack size exceeded — 그 전까지 갱신 2058회
```

- 8,000·12,000은 안정된다. 10,500은 할인을 넣으면 9,450(1만 미만 → 할인 0), 빼면 10,500(1만 이상 → 할인 1,050)이 되어 진동한다.
- 가드는 "값이 같을 때"만 멈춘다. 진동하는 동안 값은 매번 바뀌므로 가드에 걸리지 않는다. 결국 스택이 넘친다(이 환경의 기본 스택에서 매번 2058회. 스택 크기를 바꾸면 횟수도 바뀐다 — `--stack-size=2000`에서 4190회).

### 5. 디스패치 중 디스패치

```text
연쇄 dispatch → Invariant Violation: Dispatch.dispatch(...): Cannot dispatch in the middle of a dispatch.
```

- Flux 디스패처는 디스패치 도중 새 디스패치를 거부해 연쇄 갱신을 구조적으로 막는다.
- 스토어 사이 순서가 필요하면 `waitFor([토큰…])`으로 먼저 처리될 스토어를 선언한다(Flux 문서).

### 6. 같은 규칙이 아니다 — 그게 요점이다

- 아니다. 단방향 버전은 할인 기준을 "소계 1만 원 이상이면 소계의 10%"로 정했다(결과: 10,500 → 할인 1,050, 합계 9,450).
- 파생값을 상태의 함수로 쓰려면 계산 순서가 하나여야 한다. 그래서 "할인 기준은 소계인가 합계인가"라는 명세의 모순을 코드를 쓰는 순간 결정해야 했다. 양방향 바인딩은 그 모순을 받아들였다가 실행 중에 진동했다.

### 7. 서버 쪽 세 패턴

- Front Controller: 웹 사이트의 **모든** 요청을 처리하는 하나의 컨트롤러.
- Page Controller: **특정 페이지·액션**의 요청을 처리하는 객체.
- Template View: HTML 안에 표식을 끼워 정보를 렌더한다(JSP·Thymeleaf류).
- Spring MVC: 중앙 서블릿 `DispatcherServlet`이 front controller다(Spring 문서).

### 8. Massive Controller

- 원인: 할인 등 규칙이 웹 컨트롤러에 있어서 모바일 API가 따로 다시 짰고, 둘이 어긋났다(표현 분리 실패).
- 보이는 형태: 컨트롤러 테스트가 HTTP·세션·DB 없이는 안 돈다. 메서드가 길고 분기가 많다.
- 대처: 규칙을 유스케이스·도메인 함수로 꺼내 두 컨트롤러가 같은 것을 부르게 한다. 규칙 테스트는 HTTP 없이 쓴다.

### 9. 템플릿 속 규칙

- 템플릿들의 조건문(`th:if` 등)을 찾아 비교한다. 같은 판단이 여러 템플릿에 복사되어 조금씩 다를 것이다.
- 판단을 뷰모델·응답 모델의 필드(`isVip`)로 한 곳에서 계산해 넘기고, 템플릿은 그 값만 표시한다.
