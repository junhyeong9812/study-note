# software-design/09-comments-and-conventions — 정답

## 정답

### 1. 주석의 자리

- 필요한 자리: **왜**(결정·제약·외부 사정·버그 번호), **인터페이스 계약**(인자 조건·반환·부작용), **놀라운 동작**(성능 특성·외부 호출), **큰 그림**(이 파일이 무엇과 무엇을 잇나).
- 쓰지 말 것: 코드를 되풀이하는 what, 주석 처리된 코드, 코드와 어긋난 낡은 주석, 나쁜 이름을 변명하는 주석.

### 2. 두 입장

- 동의: 공개 API에는 주석이 필요하다. 구현 코드 안 주석은 코드가 분명하지 않을 때만 필요하다.
- 갈림: Ousterhout는 같은 코드에 5~10배 많은 주석을 쓰고, 빠진 주석이 더 큰 손실이라고 본다. Martin은 주석이 코드로 표현하지 못한 실패의 보상이며, 나쁜 주석의 비용이 더 크다고 본다. 팀 내부 인터페이스 주석에서도 갈린다.
- "obvious"의 기준: 작성자가 아니라 **처음 읽는 사람**. 리뷰어가 분명하지 않다고 하면 분명하지 않은 것이다(APOSD 13.8).

### 3. 포매팅이 섞인 diff

(실험 A, google-java-format 1.37.0, 2026-10-02)

```text
[noisy]       RetryClient.java | 56   (31 insertions, 25 deletions)
[noisy -w]    RetryClient.java | 38   (22 insertions, 16 deletions)
[consistent]  RetryClient.java | 2    (1 insertion, 1 deletion)
```

- 섞이면 56줄. `-w`로도 38줄이 남는다(중괄호 위치·줄 나눔은 공백 변경이 아니다).
- 포매터가 고정된 저장소에서는 바뀐 1줄만 남는다.

### 4. 낡은 주석

(실험 B)

```text
  attempt 4 failed, sleep 800ms
  gave up after 1537ms: downstream 503
```

- 실제: 5회 시도, 대기 100+200+400+800 = 1,500ms, 포기까지 1,513~1,537ms(기록한 5회 실행).
- 주석 기준 기대는 3회·약 300ms. 상위 타임아웃 1초를 주석 기준으로 잡으면, 재시도가 끝나기 전에 상위가 먼저 끊는다. 하위의 4·5번째 시도는 아무도 기다리지 않는 일이 된다.

### 5. doclint의 판정

- 주석 없음: `warning: no comment` 2건.
- 이름 반복("Try acquire. / the key"): 0건.
- 계약 주석: 0건.
- 교훈: 도구는 주석의 **있음**만 본다. 존재만 강제하면 정보 없는 주석이 늘어난다. 내용은 리뷰가 본다.

### 6. 이유 없는 경고 주석

- 찾을 것: `git log -L`·`git blame`·연결된 티켓·장애 기록으로 그 줄을 넣은 이유.
- 남길 것: 이유(무엇이 깨지는지), 근거(장애 번호), 확인 방법(재현 테스트 이름).
- 이유를 못 찾으면 특성화 테스트로 현재 동작을 고정한 뒤 고친다(51). 구조 수준의 결정이면 ADR로(47).

### 7. 주석 속 숫자 = 지식 사본

- **N(비중복)** 위반이다. 같은 지식(재시도 횟수·총 대기)이 코드와 주석 두 곳에 있다. Hunt–Thomas 「Duplication in Documentation」의 예와 같은 구조다.
- 고치기: 주석에서 숫자를 빼고 **이유와 출처**만 남긴다(예: "게이트웨이 SLA 2초 안에 끝나도록 맞춘 값, #1234"). 총 대기 시간이 중요하면 코드로 계산하고 테스트로 고정한다.

### 8. 포매터 도입

1. 포매터 하나를 정한다(Java: google-java-format·Spotless, JS/TS: Prettier).
2. 포매팅만 하는 커밋 하나로 저장소 전체를 맞춘다. 기능 변경과 섞지 않는다.
3. CI에서 검사한다(`--dry-run`이 어긋난 파일 이름을 출력하면 실패).
4. blame: 그 포매팅 커밋 해시를 `.git-blame-ignore-revs`에 넣고 `git config blame.ignoreRevsFile .git-blame-ignore-revs`(또는 `git blame --ignore-rev`).

### 9. Google eng-practices의 스타일 요구

- 스타일 가이드에 없는 개인 취향으로 변경을 막지 않는다. 개선 제안은 "Nit:"를 붙인다.
- 큰 스타일 변경은 기능 변경과 섞지 않고 별도 CL로 보낸다. 섞으면 무엇이 바뀌었는지 보기 어렵고 병합·롤백이 복잡해진다.
