# software-design/38-layered-hexagonal-clean — 질문

## 질문

1. (왜) 업무 규칙이 DB 구현을 직접 알면 무엇이 어려워지나? Cockburn이 헥사고날 아키텍처로 얻으려 한 것은?
2. (그림) 계층형·헥사고날·클린의 의존 그래프를 각각 그려라. Martin의 의존 규칙을 한 문장으로 말하라.
3. (경계) 실행 흐름은 유스케이스 → 저장소 구현으로 가는데, 소스 의존은 어떻게 반대가 되나? 포트는 누가 소유하나? 구현을 고르는 곳은?
4. (예측) `DB_URL` 없이 v1(`OrderService`가 `JdbcOrderRepository`를 직접 생성)과 v2(`PlaceOrder` + 메모리 어댑터)의 업무 규칙 테스트를 돌리면 각각 결과는?
5. (예측) 저장소를 Mongo 구현으로 바꿀 때 v1과 v2는 각각 어떤 파일을 고치나? 실험의 `git diff --stat` 요지는?
6. (경계) 헥사고날이 손해인 경우는? 실험 A에서 같은 기능의 파일·줄 수는 어떻게 달랐나?
7. (예측) v1에 ArchUnit 계층 규칙(Persistence는 Service만 접근)을 걸면 무엇이 몇 건 잡히나? 이것은 커리큘럼 ⚠ 중 무엇인가?
8. (예측) v2에 ArchUnit 1.4.1 `onionArchitecture()`를 예외 없이 걸면 무엇이 잡혔나? 어떻게 통과시켰고, 왜 그 예외가 정당한가?
9. (장애 진단) 유스케이스가 어댑터의 `Db`를 직접 부르는 "급한 수정"이 들어갔다. 컴파일·실행·ArchUnit 중 어디서 드러나나?
10. (연결) `jdeps -verbose:package`로 v1과 v2의 그래프를 비교하라. 업무 쪽 패키지에서 나가는 간선은 각각 무엇인가?
