# software-design/50-legacy-migration-strangler-fig — 정답

## 정답

### 1. 빅뱅 재작성이 잘 실패하는 이유

- Fowler("Strangler Fig", 2024): 이 단순한 계획이 "대부분 실패했다". 이유 셋.
  - 교체가 오래 걸리는데 사용자는 새 기능을 기다리지 못한다(구 시스템이 계속 바뀌어 목표가 움직인다).
  - 기존 동작의 세부를 알아내기 어렵다.
  - 그 동작의 상당수는 실제로 필요 없어서, 재현하는 일이 낭비다.
- "Patterns of Legacy Displacement"(Cartwright·Horn·Lewis): 한 조직의 반복된 실패에서 세 번째 핵심 요인으로 **Feature Parity**(지금 기능을 그대로 재현)를 들고, 그것이 하루짜리 "빅뱅" 전환 계획으로 이어졌다고 적는다. 다른 요인은 조직(리더십·구조·일하는 방식)을 그대로 둔 것, 초기에 합의한 요구사항과 실제 업무 요구의 격차다.
- 위험 관점: 위험이 전환일 하루에 몰리고, 되돌릴 단위가 "전부"다.

### 2. 네 단계와 퍼사드 주의

```text
 ① 클라이언트 → [퍼사드] → 대부분 구, 일부 신
 ② 클라이언트 → [퍼사드] → 신 비율 증가
 ③ 클라이언트 → [퍼사드] → 전부 신 (구 폐기)
 ④ 클라이언트 → 신 (퍼사드 제거)
```

- 주의 1: 퍼사드가 단일 장애 지점이나 성능 병목이 되지 않게 한다.
- 주의 2: 퍼사드가 이전 진행을 따라가게 유지한다(Azure 문서 "Make sure that the façade keeps up with the migration").
- 맞지 않는 경우(같은 문서): 요청을 가로챌 수 없을 때, 시스템이 작아 통째로 바꾸는 편이 쉬울 때, 원 시스템을 빨리 없애야 할 때.

### 3. branch by abstraction vs Strangler Fig

- 같은 점: 두 구현을 한 시스템 안에 공존시키고, 앞단(퍼사드·추상 계층)이 고르게 해서 조금씩 옮긴 뒤 구 구현을 지운다.
- 다른 점: Strangler Fig는 대개 시스템·서비스 경계(HTTP 앞단 등)에서, branch by abstraction은 코드 안의 인터페이스에서 나눈다.
- 긴 브랜치를 대신하는 이유: 추상 계층 뒤에서 바꾸므로 시스템이 매 커밋 빌드·실행된다. 그래서 주 브랜치에 계속 합치며 출시할 수 있다(Fowler "BranchByAbstraction" — Paul Hammant가 트렁크 기반 개발을 옹호하며 붙인 이름. Hammant는 처음 생각해 낸 사람으로 Stacy Curl을 든다).

### 4. 해시 버킷 비율 확대

(실험 A, JDK 21.0.12, 2026-10-02)

```text
  목표 10% → 실제 9.98%
  같은 고객 반복 판정 일치: true
  10%→20% 확대 시 기존 10% 고객이 계속 새 경로: 9980/9980
```

- 원래 10% 고객(버킷 0~9)은 20%(버킷 0~19)에도 포함되므로 계속 새 경로에 있다. 고객이 신·구를 오가지 않는다.
- 같은 고객은 해시가 같아 매 요청 같은 쪽으로 간다.

### 5. 반올림 규칙 차이

```text
== 2) 병행 실행(섀도): 새 구현 v1(HALF_EVEN)
  비교 100000건, 불일치 1289건(1.29%), 후보 예외 0건
   예: amt=57786 pct=25 legacy=14447 new=14446
== 3) 병행 실행(섀도): 새 구현 v2(HALF_UP)
  비교 100000건, 불일치 0건, 후보 예외 0건
```

- 나온다. 금액 × 할인율이 정확히 x.5원이고 정수부 x가 짝수인 입력에서 1원 차이(57786 × 25% = 14446.5 → 구 14447, 신 14446). 정수부가 홀수인 .5(예: 14447.5)는 둘 다 올려 같다. 10만 건 중 1289건(1.29%).
- v2(HALF_UP)로 맞추자 0건. 문서에 없던 구 동작을 비교로 찾은 것이다.

### 6. Scientist의 `run`

- control(`use`)의 값을 돌려준다(README 원문 "will always return whatever the `use` block returns").
- 후보 예외: 삼키고 기록한다(사용자 응답에 영향 없음). 실험 A의 4)도 같은 동작을 흉내 냈다 — 반환 1500, 후보 예외 기록 1.
- 후보가 느림: 막아 주지 않는다. README가 직접 "타임아웃은 보호하지 않는다"고 적고, 낮은 비율로 돌리라고 권한다. 동기 섀도는 요청 지연을 늘린다.

### 7. 화면마다 1원 차이, 에러 없음

- 의심: 신·구 경로가 같은 데이터에 각자 계산해 쓰는 이중 쓰기 + 계산 규칙 차이(반올림·정렬·시간대).
- 실험 A의 5)(`HashMap`으로 흉내 낸 테이블): 같은 행에 두 경로가 쓰자 1289행이 다른 값으로 덮였다. 에러는 0건(마지막 쓰기가 이김).
- 고치기: 기준 저장소를 하나로 정한다. 다른 쪽은 동기화(CDC)하거나 비교만 한다. 병행 실행으로 규칙 차이를 먼저 없앤다. 이미 덮인 행은 대조 배치로 찾아 바로잡는다.

### 8. 데이터 이전 세 단계

- 1단계: 신 서비스가 구 DB를 직접 읽고 쓴다.
- 2단계: 신 도메인 DB를 만들고 ETL로 초기 적재, CDC로 동기화. 두 DB 일치를 검증한다.
- 3단계: 신 DB가 기준이 되고, 구 DB의 해당 테이블·프로시저를 지운다.
- 되돌리기: 2단계와 3단계 시작까지는 구 DB로 되돌릴 수 있다. 구 객체를 지운 뒤에는 복원 + 변경 재생이 필요해 노력과 위험이 크다(Azure 문서). 그래서 제거는 검증 뒤 의도된 마지막 단계.
- expand/contract와의 연결: 같은 구조다. 넓히고(expand) → 채우고(backfill) → 바꾸고(switch) → 줄인다(contract). 줄이는 단계가 되돌리기 어려운 지점이라 맨 끝에 따로 한다([database/26](../../database/26-schema-migration/2-summary.md) §4).

### 9. 구 시스템 영구 병존

- 빠진 것: "구 경로 제거"를 별도 작업으로 계획하지 않았다. 남은 호출자를 모른다.
- 관측: 구 엔드포인트·구 메서드의 호출 카운터와 접근 로그. 호출자 식별(서비스 이름·API 키)을 달아 누가 아직 부르는지 찾는다.
- 판단: 호출이 0인 상태가 일정 기간(정산 주기 등 드문 배치를 덮을 만큼) 이어지면 지운다. 코드·테이블·퍼사드 규칙·배포 파이프라인까지.

### 10. 교차 호출에는 ACL

- 신 ↔ 구 사이에 ACL(Anti-corruption Layer)을 둔다.
- 이유: 구 시스템의 이름·코드값·형식이 신 시스템 모델로 새어 들어오는 것을 막는다. Azure 문서는 ACL이 없으면 교차 의존이 컴포넌트를 깨뜨리거나 신 시스템이 구 관례를 따르게 된다고 적는다.
- ACL도 과도기 아키텍처다. 구 시스템이 사라지면 함께 지운다.
