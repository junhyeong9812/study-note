# software-design/04-decompose-by-change — 정답

## 정답

### 1. 두 기준

- 분해 1: 처리의 주요 단계마다 모듈(흐름도를 그려 자름).
- 분해 2: 정보 은닉. 모듈마다 다른 모듈에게서 숨기는 설계 결정 하나.
- Parnas: 차이는 실행 표현이 아니라 **작업 할당 방식과 모듈 사이 인터페이스**에 있다. 실행 말고 변경·문서화·이해에 쓰는 표현에서 두 시스템은 다르다.

### 2. 그림과 인터페이스

```text
분해 1: Input / Circular Shift / Alphabetizer / Output → 모두 공유 저장 형식(압축 문자, 색인 표)을 읽고 쓴다
분해 2: Line Storage ← Circular Shifter ← Alphabetizer ← Output, Input → Line Storage
```

- 분해 1의 인터페이스: 메모리 안 표 형식·포인터 규약(복잡한 형식).
- 분해 2의 인터페이스: 함수 이름과 인자 수·타입(`CHAR(r,w,c)`, `CSCHAR`, `ITH(i)` 등).

### 3. 다섯 변경

- 같음: 1번 입력 형식 — 두 분해 모두 한 모듈.
- 분해 1에서 모든 모듈: 2번(모든 줄을 메모리에)과 3번(4글자 압축).
- 4번(이동 색인)은 분해 1에서 이동·정렬·출력, 분해 2에서 Circular Shifter만. 5번(한 번에 정렬)은 분해 1에서 어렵고 분해 2에서 Alphabetizer만.

### 4. 저장 형식 변경

(실험, JDK 21.0.12, 2026-10-02)

```text
m1: 5 files changed, 9 insertions(+), 34 deletions(-)
m2: 1 file changed, 6 insertions(+), 14 deletions(-)
```

- 출력은 둘 다 변경 전과 같다.

### 5. 원래 줄 번호

- 분해 1이 싸다: `Output.java` 1파일. 공유 이동 색인 `{줄 번호, 시작}`에 원래 줄이 이미 드러나 있었다.
- 분해 2: `CircularShifter`(인터페이스에 `originalLine(i)` 추가) + `Output` 2파일.
- 숨긴 정보를 새로 꺼내 써야 하는 변경에서는 은닉이 비용이 된다.

### 6. 도달 가능 집합

- 둘 다 5개(`Alphabetizer`, 이동 모듈, `Input`, `Main`, `Output`).
- 실제 변경은 5파일 대 1파일. 도달 가능 집합은 "바뀔 수도 있는" 상한이고, 변경은 인터페이스가 그대로인 첫 모듈에서 멈춘다. 분해 1의 `Core`는 인터페이스가 저장 형식 자체라 멈출 곳이 없었다.

### 7. Parnas의 자기 비판

- Circular Shifter 정의가 이동의 **순서**까지 정해 필요 이상으로 드러냈다. 순서 대신 "모든 이동이 있고, 중복 없고, 원래 줄을 알아내는 함수가 있다"만 정했어야 한다.
- 실험 5에서 분해 2가 `originalLine(i)`를 추가해야 했던 것이 바로 그 "원래 줄을 알아내는 함수"다. 처음부터 인터페이스에 두었다면 변경 ②도 `Output` 1파일이었을 것이다(추정 — 이 변형은 실험하지 않았다).

### 8. 변동성 네 질문

- 무엇이 바뀌나 / 왜 바뀌나 / 얼마나 자주 / 누가 바꾸자고 하나.
- 틀린 예측으로 만든 경계와 확장점은 추측성 일반화(Speculative Generality)가 된다. 변경 이력으로 예측을 고친다.

### 9. 알림만 안 감

- 결제 수단이라는 하나의 변동이 `OrderService`·`PaymentService`·`NotificationService`에 나뉘어 있다(기능 분해가 변동을 나눠 가짐). 알림 쪽 `switch`를 빠뜨렸다.
- 고치기: 결제 수단 결정을 `PaymentMethod` 같은 인터페이스 뒤로 모으고 등록표로 고른다. 당장 못 하면 흩어진 `switch`를 한 곳으로 모으는 것부터.
