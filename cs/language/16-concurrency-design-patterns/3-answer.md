# language/16-concurrency-design-patterns — 정답

## 정답

### 1. 무엇이 무너지고 무엇이 막나

| 무너지는 것 | 막는 패턴 |
|---|---|
| 몰리면 스레드가 끝없이 생겨 메모리·문맥 교환 고갈 | 스레드 풀(Executor) — 스레드 수 상한(설정한 경우 — `maximumPoolSize`를 사실상 무한으로 두면 상한이 없다) + 큐 + 거부 |
| 비동기 결과·예외를 받을 곳이 없음 | Future/Promise — 결과·예외를 담는 손잡이 |
| 예외 경로에서 `unlock` 누락 → 다음 요청 영원히 대기 | Scoped Locking — 잠금 수명 = 블록 수명 |

- 단, 풀의 큐가 무한이면 첫 줄이 "스레드 고갈" 대신 "큐 메모리 고갈"로 바뀔 뿐이다(3번).

### 2. `execute()` 판단 순서

```text
  스레드 < core → 새 스레드
  아니면 큐에 offer → 성공이면 대기
  실패면 스레드 < max → 새 스레드
  아니면 거부 정책
```

- `newFixedThreadPool`의 큐는 용량 `Integer.MAX_VALUE`인 `LinkedBlockingQueue`다. offer가 실패하지 않으므로 "새 스레드" 단계에 도달하지 않는다.
- Java 21 `ThreadPoolExecutor` 문서도 무한 큐에서는 "maximumPoolSize는 아무 효과가 없다"고 적는다.

### 3. 무한 큐 vs Abort vs CallerRuns (실험 1)

| 설정 | 결과 | 시간 |
|---|---|---|
| (a) 무한 큐, `-Xmx64m` | 거부 없이 큐가 자라 3,767~3,822건 대기 중 `OutOfMemoryError: Java heap space`(7회) | 약 0.15초 만에 죽음 |
| (b) 유한 100 + Abort | 1,880~1,886건 `RejectedExecutionException`, 114~120건 완료 | 589~629ms |
| (c) 유한 100 + CallerRuns | 거부 0. 풀 약 1,370건 + 제출 스레드 약 630건 | 6,952~6,963ms |

- (c)의 시간은 약 2,000 × 10ms ÷ 3스레드(워커 2 + 제출 스레드)에 가깝다.
- (b)는 과부하를 호출자에게 즉시 알리고, (c)는 제출을 늦춰 역압을 건다. (a)는 아무것도 알리지 않는다.

### 4. 풀 크기 (실험 2)

- 시작점: 코어 × (1 + W/C) = 2 × (1 + 18/2) = **20**.
- 실험(5회): 20에서 초당 939~964건, 40에서 969~1,061건, 80에서 873~1,018건.
  - 20까지는 스레드에 비례해 늘었다(작업 20ms → 스레드당 초당 50건).
  - 그 뒤는 CPU 2개가 상한이라 거의 안 늘었다(이론 2코어 ÷ 2ms = 초당 1,000).
  - 1,000을 약간 넘은 실행은 CPU 2ms를 벽시계 바쁜 대기로 흉내 냈기 때문이라는 해석이다.
  - 40과 80 중 어느 쪽이 나은지는 실행마다 바뀌었다. 상한 근처에서는 스케줄링 비용이 결과를 흔든다(해석).
- 공식은 출발점이다. W/C를 재서 맞추고, 성격이 다른 작업은 풀을 나눈다.

### 5. 공용 풀 블로킹 (실험 3)

| JVM이 보는 코어 | 공용 풀 병렬도 | 가벼운 작업 대기 | 블로킹 8건 완료 |
|---|---|---|---|
| 4 | 3 | 1,001~1,002ms | 1,506~1,551ms |
| 2 | 1 | 1~2ms | 506~508ms |

- 코어 4: 워커 3개가 500ms씩 막혀 8건이 3번에 나눠 돈다. 가벼운 작업은 앞의 블로킹 작업들 뒤에서 약 1초를 기다린다.
- 코어 2: 병렬도가 1이면 `CompletableFuture`는 공용 풀 대신 **작업마다 새 스레드**를 만든다(Java 21 문서, 소스 `USE_COMMON_POOL = 병렬도 > 1`). 그래서 8건이 동시에 돌았다.
- 교훈: 작은 개발 환경에서 안 보이던 정지가 코어 많은 서버에서 나온다. 블로킹에는 전용 executor를 준다(전용 8개 풀: 506ms, 가벼운 작업 2~3ms).

### 6. 예외가 가는 곳 (실험 4)

| 방식 | 예외 |
|---|---|
| `submit()` | `Future` 안에 담김. `get()` 안 하면 흔적 없음 |
| `execute()` | 워커 스레드 밖으로 나가 기본 처리기가 stderr에 스택 트레이스 |
| `runAsync()` | `CompletableFuture` 안에 담김. 뒤의 `thenRun`도 안 돎. 흔적 없음 |

- 막는 한 줄: `.whenComplete((v, ex) -> { if (ex != null) log.warn("...", ex); })` 또는 `.exceptionally(...)`. 결과가 필요한 일이면 응답 전에 `join()`.
- 실험의 프로세스는 이 실패들에도 exit 0으로 끝났다.

### 7. Active Object vs Monitor Object

| | Active Object | Monitor Object |
|---|---|---|
| 누가 상태를 만지나 | 전용 스케줄러 스레드 하나(기본형 — thread pool 변형은 여럿) | 들어온 호출자 스레드들(한 번에 하나) |
| 보호 수단 | 요청 큐 직렬화 — 상태에 락 불필요 | 객체 락 + 조건 대기 |
| 호출자 | 보통 큐에 넣고 바로 반환, Future로 결과(동기 대기·유한 큐 대기 정책도 있다) | 락을 얻을 때까지 블록 |
| 병목 | 스레드 하나·큐 길이(무한이면 OOM) | 락 경합 |

- Java 실물: Active Object ≈ `newSingleThreadExecutor` + `CompletableFuture` 프록시, 액터·이벤트 루프. Monitor Object ≈ `synchronized` 메서드 + `wait`/`notifyAll`.

### 8. 다른 사용자 ID 누출

- 의심: 스레드 풀 + `ThreadLocal`. 앞 요청이 넣은 값을 지우지 않아, 같은 워커를 재사용한 다음 요청이 본다(실험 6: 익명 요청이 `user_001`을 봄).
- 확인: 로그에 스레드 이름을 같이 찍어, 누출된 요청이 직전 요청과 같은 워커인지 본다. `ThreadLocal.set` 위치를 찾아 짝이 되는 `remove`가 모든 경로(예외 포함)에 있는지 본다.
- 수정: `set`한 필터가 `finally`에서 `remove`. 비동기 경계를 넘길 땐 값을 명시적으로 넘기고 끝에 지운다.
- 가상 스레드: 작업마다 새 스레드라 재사용으로 인한 누출은 사라진다. 그러나 JEP 444는 가상 스레드를 풀링하지 말라고 하고, 스레드 로컬로 비싼 자원을 나누던 관용구는 경계해 다른 캐시 방식으로 바꾸라고 적는다. "옮기면 끝"이 아니라 그 관용구를 같이 고쳐야 한다.

### 9. 두 `volatile` 필드와 DCL

- 볼 수 있다. `volatile`은 각 필드 읽기·쓰기를 보이게 할 뿐, **두 필드를 한 번에** 읽거나 쓰게 하지 않는다.
  - 실험 7: writer가 [0,100] ↔ [1000,1100]을 번갈아 쓰는 동안 reader는 반쪽 상태(`h-l≠100`)를 38,996~3,374,760번, `lo>hi`를 935~96,896번 봤다(7회 — 스케줄에 따라 횟수가 크게 흔들린다).
- DCL의 `volatile`은 다른 문제를 푼다. 참조 하나를 공개할 때, 생성자 안의 쓰기들이 그 공개보다 먼저 보이게(happens-before) 한다. 없으면 참조는 보이는데 필드는 기본값인 "반쯤 만든 객체"를 볼 수 있다.
- 둘 다 피하는 설계: 상태를 **불변 객체**로 만들고 **참조 하나**를 `AtomicReference`/`volatile`로 교체한다. 읽는 쪽은 참조를 한 번 읽어 그 객체만 쓴다. 실험 7의 스냅샷 판은 반쪽 관측 0번이었다. 지연 초기화는 홀더 클래스로 JVM의 클래스 초기화에 맡긴다.
