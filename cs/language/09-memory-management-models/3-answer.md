# language/09-memory-management-models — 정답

## 정답

### 1. 해제 시점을 정하기 어려운 이유와 세 가지 실패

- 객체를 만든 함수가 끝나도 캐시·다른 객체·다른 스레드가 같은 객체를 계속 가리킬 수 있다. 마지막 사용 시점은 실행 경로에 따라 달라진다.
- 실패 세 가지
  - 너무 이르게: **use-after-free** — 해제된 자리를 계속 읽거나 쓴다.
  - 두 번: **double free** — 할당자 자료구조가 깨진다(glibc는 감지 시 `SIGABRT`, [os/11](../../os/11-heap-allocation/2-summary.md)).
  - 안 함: **누수** — 메모리가 계속 오른다.

### 2. 네 모델 표

| 모델 | 해제를 정하는 주체 | 해제 시점 | 틀리면 |
|---|---|---|---|
| 수동 | 프로그래머 | `free` 부른 순간 | 실행 중 UAF·double free·누수 (한참 뒤, 엉뚱한 곳) |
| 참조 카운팅 | 객체별 카운터 | 0이 된 순간 | 순환 누수 (메모리 지표) |
| 추적 GC | 수집기 | 수집기가 돌 때 | 도달 가능한 누수, 일시정지 |
| 소유권 | 컴파일러 규칙 | 소유자가 스코프를 벗어날 때 | 컴파일 거부 (`Rc` 순환은 누수) |

### 3. CPython 순환 누수 예측

- 약 20MB(1000쌍 × 2 × 10KB)가 남는다. 실험(3.12.14): `20.4 MB`.
- 순환 안에서 서로가 카운트 1을 유지해 0이 되지 않는다.
- `gc.collect()`는 순환 수집기를 강제로 돌린다. 실험에서 도달 불가 객체 2,011개를 찾았고 남은 메모리가 `0.0 MB`가 됐다.

### 4. Java의 같은 순환

- `null`을 돌려준다(실험: `System.gc() 후 살아 있나: false`).
- 추적 GC는 카운트가 아니라 "루트에서 닿나"로 판정한다. 지역 변수가 끊기면 순환째 도달 불가가 된다.
- 단 `System.gc()`는 수집을 제안할 뿐이다(Java API 문서 "suggests", "best effort"). 회수는 이 실행에서 관찰된 결과다.

### 5. C use-after-free

- 이 환경(gcc 13.3.0 `-O0`, glibc)에서는 두 번째 `malloc`이 방금 해제한 주소를 그대로 받았다(`same=1`). 옛 포인터로 읽으면 `user_002 balance=999` — **다른 사용자의 데이터**가 크래시 없이 나왔다.
- UB이므로 다른 컴파일러·할당자에서는 다르게 나와도 된다.
- ASan 빌드: 해제 직후 재할당이 다른 주소를 받았고, 읽기 순간 `heap-use-after-free`를 해제·할당 위치 스택과 함께 보고하고 exit 1로 끝났다.

### 6. 두 가지 과장

- GC 언어: GC는 **도달 불가** 객체만 회수한다. static 컬렉션처럼 닿지만 다시 안 쓰는 객체는 영원히 남는다 → 누수([reliability/37](../../reliability/37-memory-leak-and-heap-analysis/2-summary.md)).
- Rust: 소유권은 safe Rust에서 use-after-free·double free를 컴파일 단계에서 막는다(`unsafe` 안은 작성자 책임). 누수는 막지 않는다. Rust 책 15.6: "Preventing memory leaks entirely is not one of Rust's guarantees" — `Rc` 순환이 대표 예다.

### 7. `getrefcount` 4294967295

- 성립하지 않는다. 같은 스크립트에서 호스트 Python 3.12.3은 `4294967295`, `python:3.12-slim`의 3.12.14는 `4`를 냈다. `None`·`True`·`256`은 두 버전 모두 `4294967295`였다.
- 큰 값은 PEP 683 불멸 객체 표시다. 어떤 객체가 불멸인지는 구현 세부이고 패치 사이에서도 달라졌다. Python 3.12.7 체인지로그 gh-113993에서 `sys.intern()` 문자열이 다시 GC 대상이 되고 인터닝 내부가 바뀌었다(3.12.3은 그 전, 3.12.14는 그 뒤). 리터럴이 그 영향이라는 것은 해석이다.
- `sys.getrefcount` 문서(3.12): 반환값을 "0이나 1 말고는" 정확하다고 믿지 말라.

### 8. 그래프로 본 두 방식

- 도달 가능성 = 루트 집합에서 시작하는 그래프 순회(BFS/DFS). 방문 못 한 정점이 쓰레기다.
- 참조 카운팅은 정점마다 **들어오는 간선 수**(진입 차수)만 본다. 사이클 안의 정점은 사이클 안에서 간선을 하나씩 받아 진입 차수가 0이 되지 않는다. 루트에서 닿는지는 보지 않으므로 사이클을 쓰레기로 판정하지 못한다.

### 9. 순환 vs 캐시 누수 가르기

- `gc.isenabled()`·`gc.get_count()`로 수집기 상태를 보고, `gc.collect()` 반환값과 그 뒤 메모리를 본다.
  - 크게 내려가면 순환이 유력하다(단서 — 전체 수집은 내장 타입 free list도 비우므로 참조 관계로 확인) → `weakref`로 역참조를 약하게, 꺼 둔 gc를 안전한 지점에서 돌린다.
  - 안 내려가면 도달 가능한 누수를 의심한다(GC 미지원 확장 타입의 순환일 수도 있다) → `tracemalloc` 스냅샷 상위 줄로 쌓는 곳을 찾아 크기 상한·만료를 둔다.

### 10. `E0382`

- 오류 색인: "A variable was used after its contents have been moved elsewhere". 이동 뒤 원래 변수를 썼다.
- 선택지와 대가
  - 빌림(`&x`): 복사 없음. 대신 수명 규칙 안에서만 쓸 수 있다.
  - `clone()`: 독립 사본. 메모리·복사 비용.
  - `Rc`/`Arc`: 공유 소유. 카운트 갱신 비용, 순환을 만들면 누수(3번과 같은 모양).
