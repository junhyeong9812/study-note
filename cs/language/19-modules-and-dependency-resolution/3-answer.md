# language/19-modules-and-dependency-resolution — 정답

## 정답

### 1. 네 장치와 다이아몬드

| 장치 | 답하는 질문 |
|---|---|
| 모듈·패키지 | 이름이 부딪히지 않게, 무엇을 숨기고 무엇에 기대는지 |
| semver | 판 번호만 보고 호환 여부를 짐작할 수 있게 |
| 버전 해석 | 그래프에서 이름마다 어느 판을 실을지 |
| 락파일 | 그 해석 결과를 다음 빌드에도 똑같이 |

- 다이아몬드: 두 경로가 같은 이름의 다른 판을 요구하는 모양. 문제가 되는 조건은 **실행 환경이 한 이름에 한 판만 올릴 수 있고**, 두 요구를 모두 만족하는 판이 없거나 해석기가 낮은 판을 고를 때다.

### 2. semver 규칙과 범위

- 호환 안 되는 API 변경 → MAJOR, 호환되는 기능 추가 → MINOR, 호환되는 버그 수정 → PATCH. 0.y.z는 초기 개발이라 언제든 바뀔 수 있다(semver.org 2.0.0).
- 범위(npm `node-semver`)
  - `^1.2.3` = `>=1.2.3 <2.0.0-0`
  - `^0.2.5` = `>=0.2.5 <0.3.0-0` — 가장 왼쪽 0 아닌 자리(minor)를 고정
  - `~1.2.3` = `>=1.2.3 <1.3.0-0`
- 검사해 주지 않는다. semver는 작성자의 약속이고, MINOR를 올리며 API를 깨도 해석기는 모른다.

### 3. 클래스패스 순서별 결과 (실험 1)

| 끝부분 | 결과 |
|---|---|
| (a) `libc-1.0.jar` | `A:1000` 출력 뒤 `NoSuchMethodError: 'java.lang.String com.x.Money.fmt(long, java.lang.String)'` |
| (b) `libc-1.0.jar:libc-2.0.jar` | (a)와 같다 — 앞의 1.0이 이김 |
| (c) `libc-2.0.jar:libc-1.0.jar` | `A:1000`, `B:1000 KRW` 정상 |
| (d) 비움 | `NoClassDefFoundError: com/x/Money`, `Caused by: ClassNotFoundException` |

- `-verbose:class`는 `com.x.Money source: file:/w/libc-1.0.jar`를 보여 줬다.
- 기동 직후가 아닌 이유: `libb`의 호출 지점에는 컴파일 때 본 서술자 `fmt:(JLjava/lang/String;)…`가 박제돼 있고(`javap`), HotSpot은 그 호출을 **처음 실행할 때** 메서드를 찾는다. 찾지 못하면 그때 `NoSuchMethodError`(JVMS §5.4.3.3). JVMS §5.4는 조기 해소도 허용하지만, 해소 오류는 그 참조를 쓰는 지점에서 던지도록 정한다. 그래서 A는 먼저 일을 끝냈다.

### 4. D를 고르는 규칙

| 도구 | 선택 | 이유 |
|---|---|---|
| Maven | **D 1.0** | 가장 가까운 선언(E 쪽 깊이 2) — Maven 문서의 바로 그 예 |
| Gradle | D 2.0 | 기본은 요청 중 가장 높은 판 |
| Go MVS | D 2.0 | 요구된 최솟값 {1.0, 2.0} 중 최댓값 |

- Maven 쪽이 위험하다. C가 D 2.0에서 생긴 메서드를 부르면 3번의 (a)처럼 실행 중 `NoSuchMethodError`가 난다. 대처는 A에서 D 판을 직접 선언하거나 `dependencyManagement`로 고정하는 것이다(Maven 문서도 그렇게 권한다).
- 주의: Go에서 major가 다르면(`v2` 이상) 모듈 경로가 다른 별개 모듈이다. 위 표는 같은 major 안의 비교로 읽는다.

### 5. NP-완전의 네 가정과 탈출

- 가정(Cox, "Version SAT" 2016-12-13): ①의존성에 특정 판을 지정할 수 있다 ②설치하려면 의존성을 모두 설치해야 한다 ③판마다 의존성이 다를 수 있다 ④한 패키지의 두 판을 동시에 설치할 수 없다.
- npm은 사실상 ④를 비켜 간다 — 일반 의존성은 중첩 `node_modules`로 두 판을 같이 둔다(실험 2. `peerDependencies` 충돌은 예외). 이것은 해석이다. Cox는 npm도 네 가정이 성립하는 도구로 꼽는다(충돌을 선언할 수단이 있으므로). 또 ④를 깨도 **가장 작은** 조합 찾기는 여전히 NP-완전이다. 대가: 같은 이름 모듈이 두 객체가 돼 싱글턴·`instanceof`가 갈리고, 설치 크기가 는다.
- Go는 ①을 깬다 — 최솟값만 선언하고, 새 판은 옛 판만큼 동작한다(import 호환성 규칙)고 전제한다. 그러면 2-SAT·Horn-SAT 범위라 선형 시간에 풀린다(Cox, "Minimal Version Selection"). 대가: 누군가 요구를 올리기 전까지 고쳐진 새 판을 자동으로 받지 않는다. 호환성을 깨는 판은 새 major(새 모듈 경로)로 내야 한다.

### 7. `NoClassDefFoundError` vs `NoSuchMethodError`

| | `NoClassDefFoundError`(원인 `ClassNotFoundException`) | `NoSuchMethodError` |
|---|---|---|
| 실패 단계 | 클래스 로딩 — 그 이름의 클래스 파일을 못 찾음 | 메서드 해소 — 클래스는 있는데 서술자가 맞는 메서드가 없음 |
| 흔한 원인 | 실행 경로에 jar 없음, `provided`·`compileOnly` 스코프 착오, 패키징 누락 | 컴파일한 판과 실행한 판이 다름(다이아몬드) |

- 확인: 실행 클래스패스(`-verbose:class`, 패키징 결과 `jar tf`)에 그 클래스가 있는지, 빌드 스코프가 실행 시 필요한지.
- 근거: JVMS §5.3.1(부트스트랩 로더가 못 찾으면 `ClassNotFoundException`, 로딩은 `NoClassDefFoundError`로 실패), 실험 1의 (d).

### 8. left-pad

- npm 블로그 원문: 2016-03-22 오후 2:30쯤(태평양 시)부터 분당 수백 건의 실패. 10분 안에 다른 사람이 같은 기능을 **1.0.0**으로 냈지만, `line-numbers`를 거쳐 정확히 **0.0.3**을 요구하는 사슬(babel·atom)이 있어 실패가 이어졌다. npm은 백업에서 원래 0.0.3을 다시 올렸고 중단은 2.5시간이었다.
- 락파일만으로는 못 막는다. 락은 "0.0.3을 받아라"를 고정할 뿐, 그 판이 레지스트리에 남아 있음을 보장하지 않는다.
- 필요한 것: 사내 미러·캐시 프록시, 벤더링, 아티팩트 보관으로 원천이 사라져도 설치되게 한다. 레지스트리 쪽에는 삭제 안전장치가 필요하다. 같은 글에서 npm은 "무제한 삭제가 큰 고통을 낳았다"며 안전장치가 필요하다고 적었다.

### 9. `json.py` 가림 (실험 5)

- `python app.py`면 스크립트 폴더가 `sys.path[0]`에 붙어 **로컬 `json.py`**가 표준 `json`을 가린다. 출력 `json from: /w/json.py`, `not-json`.
- 같은 구조: 클래스패스·`sys.path`·`node_modules` 상향 탐색·`PATH`는 모두 순서 있는 목록에서 **첫 일치**를 쓴다. 같은 이름이 둘이면 앞의 것이 조용히 이긴다(실험 1의 (b)).
- `python -P`(3.11 추가)는 스크립트 폴더를 앞에 붙이지 않아 표준 `json`을 쓴다. `-I`(격리 모드)도 이를 포함한다.
