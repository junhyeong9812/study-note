# language/15-gil-and-runtime-constraints — 정답

## 정답

### 1. GIL은 구현의 성질

- CPython 구현의 성질이다. Python 용어집도 "CPython 인터프리터가 쓰는 장치"로 정의한다. Jython·IronPython에는 GIL이 없다(PEP 703 "Jython and IronPython" 절, 원고 §12).
- 이유: CPython은 모든 객체의 참조 카운트를 새 참조를 만들거나 버릴 때 늘리고 줄인다(빌린 참조·3.12 immortal 객체는 예외).
  - 두 스레드가 동시에 같은 카운트를 2 → 3으로 쓰면 한 갱신이 사라진다. 실제 참조보다 카운트가 작아져 아직 쓰는 객체가 해제될 수 있다.
  - 모든 증감을 원자 연산으로 바꾸면 단일 스레드가 느려진다. 인터프리터 전체를 하나의 락으로 잠그면 객체 모델이 단순하게 안전해진다(용어집). 대가는 멀티코어 병렬성이다.

### 2. GIL 시간축

```text
  (a) 계산   [실행 ......][놓음]      [대기 ....][실행 ......][놓음]     ← 전환 간격마다 넘김
  (b) sleep  [실행][sleep 시작 → GIL 놓음 ─────────────── 깨면 다시 획득]
  (c) sha256 [실행][C 코드가 GIL 놓고 해시 계산 ── 다른 스레드와 동시에 ──][획득]
```

- (b)·(c) 동안에는 다른 스레드가 바이트코드를 실행할 수 있다. (a)끼리는 한 번에 하나다.

### 3. 직렬·스레드·프로세스 (CPython 3.12, 물리 코어 2개)

- 실험 1(`--cpuset-cpus=2,4`, 3회)
  - `cpu` 직렬 ×4: 1.92~2.12초 / 스레드 4: 2.00~2.61초 / 프로세스 4: 1.04~1.30초.
  - `sha256 64MB` 직렬 ×4: 0.52~0.58초 / 스레드 4: 0.27~0.34초.
- 순수 파이썬 계산은 스레드로 안 빨라지고, 프로세스로 코어 수(2)만큼 빨라진다.
- `sha256`은 C 코드가 계산 중 GIL을 놓아 스레드로도 빨라진다.
- 같은 물리 코어의 하이퍼스레드 두 개(`--cpuset-cpus=2,3`)에서는 프로세스 4개도 2.08·2.11초로 빨라지지 않았다.

### 4. GIL 아래의 `g += 1`

- `g += 1`: 3회 모두 5,000,000(재실행 6회도 같음). `abs(0)`를 끼우면 1,797,065~2,884,197(재실행 2,941,076~3,734,654 — 실행마다 다르다).
- CPython 3.12 `bytecodes.c`에서 전환 요청 검사(`CHECK_EVAL_BREAKER()`)는 `JUMP_BACKWARD`·`CALL` 계열에 있다(함수 진입 `RESUME`도 eval breaker를 확인한다).
  - `g += 1`의 `LOAD_GLOBAL … STORE_GLOBAL` 사이에는 그런 명령이 없다. `g`가 정수라 `BINARY_OP`도 파이썬 코드를 부르지 않는다. 그래서 이 구현·이 사례에서는 우연히 중간에 끊기지 않았다(사용자 정의 `__iadd__`를 부르는 객체라면 바이트코드 하나 안에서도 전환될 수 있다).
  - `abs(0)` 호출(CALL)이 읽기와 쓰기 사이에 들어가면 그 뒤에서 전환이 일어나 갱신이 사라진다.
- 언어가 보장한 원자성이 아니다. 공유 상태는 `threading.Lock`으로 지킨다.

### 5. 전환 간격 0.005

- 아니다. Python 3.12 `sys.setswitchinterval` 문서: 이 값은 타임슬라이스의 "이상적인 길이"다.
  - 오래 걸리는 내부 함수·메서드가 있으면 실제 값이 더 길 수 있다.
  - 간격 끝에 어느 스레드가 실행될지는 OS가 정한다. 인터프리터에는 자기 스케줄러가 없다.

### 6. free-threaded 빌드의 참조 카운트

- biased reference counting: 객체 헤더에 주인 스레드 ID·로컬 카운트·공유 카운트를 둔다. 만든 스레드는 원자 연산 없이 로컬 카운트를 바꾸고, 다른 스레드만 원자 연산으로 공유 카운트를 바꾼다(PEP 703).
- immortalization: 상수 같은 일부 객체는 카운트를 아예 바꾸지 않는다.
- 제한적 지연 참조 카운팅, 스레드 안전 할당기 mimalloc(pymalloc 대체)도 쓴다.
- 대가
  - PEP 703 표: 단일 스레드 6%(Skylake)·5%(Zen 3), 다중 스레드 8%·7% 오버헤드.
  - HOWTO(3.14판): 평균 약 1~8%, 메모리 증가.
  - 지원 표시 없는 C 확장을 import하면 GIL이 다시 켜진다.

### 7. 다른 런타임

- Node.js: JS 코드는 이벤트 루프 스레드 하나에서 돈다. CPU 작업 병렬은 `worker_threads`나 별도 프로세스(`cluster`·`child_process`).
  - 실험 4: 계산 두 개를 메인에서 차례로 25.34~26.80초, 워커 2개로 13.27~13.51초(재실행 24.82초 / 12.77초).
- Java(HotSpot): GIL이 없다. 스레드가 코어마다 동시에 바이트코드·JIT 코드를 실행한다. 대신 공유 데이터의 레이스·가시성은 개발자가 락·`volatile`·동시 컬렉션으로 다뤄야 한다.

### 8. 스레드 8개인데 시간이 그대로

- 확인
  - `top`에서 프로세스 CPU가 약 100%(코어 1개분)에 머문다. `top -H`로 보면 스레드들이 번갈아 조금씩 쓴다.
  - 스레드 수를 1·2·8로 바꿔도 시간이 비슷하다.
  - 계산이 순수 파이썬 코드(루프·dict 조작)에 있다.
- 대처 순서
  1. I/O가 섞였는지 본다(그 부분은 스레드 유지).
  2. 계산을 GIL을 놓는 라이브러리(NumPy·hashlib 등)로 옮길 수 있나 본다.
  3. `ProcessPoolExecutor`로 바꾼다. 워커는 물리 코어 수 근처, 인자는 작게.
  4. 핵심을 확장 모듈로 내리거나 free-threaded 빌드를 검토한다.

### 9. 프로세스로 바꾸니 OOM

- 프로세스마다 인터프리터·import한 모듈·데이터를 따로 가진다. 큰 인자·결과는 pickle로 복사된다. 워커 수만큼 메모리가 늘어 컨테이너 한도를 넘는다.
- 대처: 워커 수를 물리 코어·메모리 한도에 맞춘다. 큰 읽기 전용 데이터는 `multiprocessing.shared_memory`·파일 매핑으로 공유한다. 작업 단위로 필요한 조각만 넘긴다.

### 10. 원고 §9 측정의 재현

- 같은 코드를 CPython 3.12.14(`--cpus=2`)로 3회: 멀티스레드 0.035~0.038초, 싱글스레드 0.030~0.032초(사실 점검 재실행 3회: 0.028~0.031초 / 0.026~0.028초).
- 맞는 부분: 순수 파이썬 CPU 연산에는 스레드가 이득이 없고(오히려 약간 느림), 프로세스가 필요하다.
- 다시 볼 부분
  - 약 100배 차이와 60초대 절대값은 재현되지 않았다(원고 측정 환경은 알 수 없다).
  - §10의 `g += 1`이 "매번 다른 값"이라는 서술도 3.12 이 환경에서는 재현되지 않았다. 결론(락이 필요하다)은 그대로 맞다.
