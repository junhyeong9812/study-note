# foundations/security/HMAC — 공유 비밀 하나로 "이 요청이 진짜인가"에 답하기

> 복습은 개념 질문에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/tech/security/hmac.md` · 이관일 2026-09-16.\
> 본문 절들(§1~§7)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지). 특정 프로젝트의 배포 결정(ADR·사내 코드) 참조는 "배포 서명을 쓰는 시스템 일반"의 형태로 일반화했다.\
> 「한눈에」의 비유·그림과 세로 흐름도·전후 대비는 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**HMAC**(Hash-based Message Authentication Code) = 공유 비밀 키 하나와 해시 함수로 "이 메시지를 키를 아는 쪽이 만들었고(진위), 그 뒤로 바뀌지 않았다(무결성)"를 증명하는 **인증 태그**.

---

## 한눈에 — 쉽게 말하면

둘만 아는 **봉인 도장**으로 편지를 봉하는 것을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
보내는 쪽                            받는 쪽
+---------------------------+        +---------------------------+
| 편지 본문 text            |        | 같은 비밀 키 K 를 갖고 있다 |
| + 둘만 아는 비밀 키 K      |        |                           |
|   → 태그 = HMAC(K, text)   |  ───▶ | text 로 태그를 다시 계산    |
|   편지 끝에 태그를 붙여 보냄 |        | 첨부 태그와 같은가? 맞으면   |
+---------------------------+        |  · 키를 아는 쪽이 만들었고   |
                                     |  · 본문이 안 바뀌었다       |
                                     +---------------------------+
```

**약속한 암구호도 똑같은 구조다.** 둘이 미리 정한 규칙으로 "오늘의 암구호"를 계산해 편지 끝에 적으면, 규칙(키)을 모르는 사람은 같은 암구호를 못 만든다.\
실무 예: API 요청 본문을 공유 비밀로 해시해 헤더에 실으면, 받는 서버가 같은 비밀로 다시 계산해 "정말 우리 클라이언트가 보냈나 + 중간에 안 바뀌었나"를 한 번에 판정한다.\
쉽게 말하면 — `ipad`·`opad`·상수시간 비교·재전송 같은 이름들은 각각의 기능이 아니라 **"비밀 키 하나로 진위를 증명한다"는 하나의 결정에서 갈라져 나온 결과**로 읽는 것이 이해가 빠르다.

---

## 문제 — 이 개념이 답하려는 질문

인터넷에서 도달 가능한 API가 요청을 받는다는 것은 **남이 보낸 명령을 우리 서버에서 실행한다는 것**이다. 그러면 받는 쪽이 반드시 답해야 하는 질문이 둘 생긴다.

```text
위조: 이 요청을 정말 우리 쪽이 보냈나, 아무나 엔드포인트에 POST 한 것인가?
변조: 보낸 요청이 맞다 해도, 중간에서 내용이 바뀌지 않았나?

TLS(HTTPS)는 이 둘을 대신 풀어 주지 못한다
  → 전송 구간 도청·변조는 막지만, "이 HTTP 요청의 발신자가 누구인가"를
    애플리케이션에게 증명해 주지는 않는다
  → 엣지/프록시에서 TLS 가 종단되면 그 뒤로는 그냥 평문 요청이다
```

그래서 요청 **자체에** "이건 비밀 키를 아는 쪽이 만들었다"는 증거를 실어야 한다.\
그 증거를 만드는 표준적 방법이 MAC(메시지 인증 코드)이고, 그중 해시 함수로 만드는 것이 HMAC이다.\
아래 서머리는 이 문제를 §1 문제 → §2 아이디어 → §3 왜 그 모양인가 → §4~5 그것이 서려면 무엇을 더 지키나 → §8 그것이 못 푸는 것, 의 순서로 분석한 것이다.

## 전체 흐름

```text
문제: 요청의 발신자·무결성을 증명해야 한다 (TLS 로는 부족) (§1)
        ↓
아이디어: 공유 비밀 K + 해시로 인증 태그 (§2)
   HMAC(K, text) = H( (K⊕opad) ‖ H( (K⊕ipad) ‖ text ) )
        ↓
왜 두 번 해시하나: 단순 H(K‖text) 는 길이 확장 공격에 깨진다 (§3)
        ↓
대칭 키: 검증자가 곧 서명자다 — 닫힌 두 당사자에 적합 (§4)
        ↓
검증의 함정: 태그 비교는 상수시간이어야 한다 (§5)
        ↓
한계: HMAC 은 재전송(freshness)을 막지 못한다 → 시간창·멱등이 별도 축 (§8)
```

## 1. 문제 — API를 여는 것은 원격 코드 실행을 여는 것이다

> 출처: 원고 §1

요청 한 건이 하는 일이 "컨테이너를 갈아 끼운다"거나 "관리 동작을 실행한다"는 것이라면, **그 요청을 받아들이는 것은 남이 보낸 명령을 우리 서버에서 실행하는 것**이다.\
그러면 받는 쪽이 반드시 답해야 할 질문이 둘이다 — **위조**(정말 우리 쪽이 보냈나)와 **변조**(중간에서 대상·본문이 바뀌지 않았나).

TLS(HTTPS)는 이 둘을 대신 풀어 주지 못한다.\
TLS는 전송 구간의 도청·변조를 막고 상대 서버의 신원을 확인해 주지만, **"이 HTTP 요청의 발신자가 누구인가"를 애플리케이션에게 증명해 주지는 않는다**.\
엣지·프록시에서 TLS가 종단되고 나면 그 뒤로 흐르는 것은 그냥 평문 요청이고, 그 구간은 인증하지 않고 전달만 한다.\
그래서 요청 자체에 "이건 비밀 키를 아는 쪽이 만들었다"는 증거를 실어야 한다.

> **MAC(Message Authentication Code)** — 비밀 키로 만들어 메시지에 붙이는 짧은 인증 태그. 키를 아는 쪽만 만들 수 있다.\
> 예: 요청 본문에 대해 계산한 짧은 값을 헤더에 실으면, 같은 키를 가진 서버만 그 값을 재현·검증할 수 있다.

## 2. 아이디어 — 공유 비밀 키와 해시로 인증 태그를 만든다

> 출처: 원고 §2

MAC의 발상은 단순하다.\
보내는 쪽과 받는 쪽만 아는 비밀 키 `K`가 있으면, 메시지 `text`에 대해 `K`가 없으면 계산할 수 없는 짧은 태그를 붙여 함께 보낸다.\
받는 쪽은 같은 `K`로 같은 태그를 다시 계산해 첨부된 값과 맞춰 본다 — 맞으면 **진위와 무결성**이 한꺼번에 증명된다.\
FIPS 198-1은 HMAC을 "암호학적 해시 함수와 공유 비밀 키를 결합해 메시지를 인증하는 메커니즘"으로 규정한다([NIST FIPS 198-1](https://csrc.nist.gov/pubs/fips/198-1/final)).

"해시 함수로 만든다"가 HMAC의 정체다 — SHA-256 같은 잘 검증된 해시를 부품으로 재활용해 MAC을 만들자는 것.\
RFC 2104는 그 조립법을 한 줄로 정의한다([RFC 2104](https://www.rfc-editor.org/rfc/rfc2104)).

```text
HMAC(K, text) = H( (K ⊕ opad) ‖ H( (K ⊕ ipad) ‖ text ) )

  H   = 해시 함수 (예: SHA-256)
  ‖   = 이어 붙이기
  ⊕   = XOR
  ipad = 바이트 0x36 을 블록 크기 B 만큼 반복  (i = inner)
  opad = 바이트 0x5C 을 블록 크기 B 만큼 반복  (o = outer)
  키가 블록 크기보다 길면 먼저 해시해 줄인다
```

눈여겨볼 점은 **해시가 두 번 겹쳐 있다는 것** — 안쪽에서 키를 섞어 메시지를 해시하고, 그 결과를 다시 키를 섞어 한 번 더 해시한다.\
왜 하필 이 모양인지가 다음 절이다.

## 3. 왜 두 번 해시하나 — 단순 `hash(key‖msg)`의 함정

> 출처: 원고 §3

가장 순진한 MAC은 "키와 메시지를 이어 붙여 한 번 해시한다", 즉 `H(K ‖ text)`다. 이건 **깨진다.**

전/후를 나란히 두면 무엇이 뚫리는지 보인다.

```text
순진한 MAC:  H(K ‖ text)                HMAC:  H((K⊕opad) ‖ H((K⊕ipad) ‖ text))
+-----------------------------+        +-----------------------------+
| digest = "여기까지 처리한     |        | 안쪽 해시 결과를 바깥 해시가   |
|  내부 상태" 가 그대로 노출     |        | 한 번 더 감싼다               |
| 공격자가 H(K‖text)+길이만 알면|        | 최종 값은 더 이상 "이어서      |
|  키 없이 뒤에 데이터를 덧붙여   |        | 처리 가능한 내부 상태" 가 아님  |
|  H(K‖text‖x) 태그를 만든다    |        |                             |
+-----------------------------+        +-----------------------------+
  → 길이 확장 공격에 뚫린다              → 바깥 해시가 안쪽 상태를 가려 막는다
```

SHA-256을 포함한 Merkle–Damgård 계열 해시는 메시지를 블록 단위로 순차 처리하며 내부 상태를 이어 가는 구조인데, 이 구조에 **길이 확장 공격(length extension attack)** 약점이 있다.\
해시 출력값 자체가 사실상 "여기까지 처리한 내부 상태"이기 때문에, 공격자가 `H(K ‖ text)` 값과 메시지 길이만 알면 **키를 몰라도** 그 상태에서 이어서 `H(K ‖ text ‖ 임의데이터)`의 유효한 태그를 만들 수 있다([Length extension attack](https://en.wikipedia.org/wiki/Length_extension_attack)).\
유효한 요청 하나를 관찰한 공격자가 뒤에 무언가를 덧붙인 새 요청을 통과시킬 수 있다는 뜻이다.

HMAC의 이중 해시가 정확히 이 구멍을 막는다.\
안쪽 해시의 결과를 바깥 해시가 한 번 더 감싸므로, 최종 값은 더 이상 "이어서 처리 가능한 내부 상태"가 아니다.\
`ipad`와 `opad`가 서로 다른 상수인 것도, 안쪽과 바깥쪽에서 키를 **다른 방식으로** 섞어 두 해시가 서로 다른 키로 동작하는 효과를 내기 위해서다.

## 4. 대칭 키 — 서명자와 검증자가 같은 열쇠를 쥔다

> 출처: 원고 §4

HMAC은 **대칭 키** 방식이다 — 태그를 만드는 쪽과 검증하는 쪽이 **똑같은 비밀 키**를 갖는다.\
이 점이 흔히 "서명"이라 부르는 공개 키 방식(RSA·ECDSA 등)과 갈리는 지점이다.\
공개 키 서명은 개인 키로 서명하고 누구나 아는 공개 키로 검증하므로 **검증자가 서명을 위조할 수 없다** — 검증 능력과 서명 능력이 분리된다.\
HMAC은 그렇지 않다 — 검증할 수 있는 쪽은 곧 태그를 만들 수도 있다. 같은 키를 쥐고 있기 때문이다.

무엇을 언제 쓰나의 판단이 여기서 나온다.

```text
HMAC (대칭)                             공개 키 서명 (비대칭)
+-----------------------------+        +-----------------------------+
| 양쪽이 같은 키를 공유          |        | 개인키로 서명, 공개키로 검증    |
| 검증자 = 서명자가 될 수 있음    |        | 검증자는 서명 위조 불가         |
| 빠르고 단순, 키 관리 = 열쇠 하나|        | 검증자가 여럿이어도 됨          |
| 키가 새면 양쪽 능력이 무너짐    |        | 제3자에게 부인 방지 증명 가능    |
+-----------------------------+        +-----------------------------+
  ← 서로 신뢰하는 "닫힌 두 당사자"       ← 검증자를 못 믿거나 여럿일 때
```

당사자가 **둘뿐**이고 서로 신뢰하며 키를 안전한 시크릿 저장소에 둘 수 있는 경우라면, 검증자가 태그를 만들 수 있다는 성질이 문제가 되지 않는다(양쪽 다 우리 것이므로).\
그래서 무거운 공개 키 기반 없이 대칭 키 하나로 충분하다. *(원고의 「실무 의견」 표기 유지 — 배포 CI↔에이전트가 그 전형이다)*

## 5. 검증의 함정 — 태그 비교는 상수시간이어야 한다

> 출처: 원고 §5

태그를 다시 계산했으면 첨부된 태그와 "같은가"를 봐야 한다.\
그런데 이 비교를 **평범한 바이트 비교(`==`)로 하면 새 구멍이 뚫린다.**

```text
일반 비교 (== , 첫 불일치에서 멈춤)          상수시간 비교 (항상 끝까지)
+-----------------------------+        +-----------------------------+
| 앞쪽이 많이 맞을수록 비교가    |        | 어디서 갈리든 항상 전체를      |
| 미세하게 오래 걸린다          |        | 끝까지 비교                   |
| → 공격자가 응답 시간을 재서    |        | → 걸리는 시간이 입력 내용과    |
|   "앞 몇 바이트 맞았나" 를      |        |   무관 → 시간으로 샐 정보 없음 |
|   시간으로 읽어낸다           |        |                             |
| → 한 바이트씩 맞춰 태그 복원    |        |                             |
+-----------------------------+        +-----------------------------+
  → 타이밍 공격에 인증이 샌다            → 타이밍 부채널을 닫는다
```

보통의 비교 함수는 첫 번째로 다른 바이트를 만나면 즉시 멈추므로, 앞쪽이 많이 맞을수록 미세하게 오래 걸린다.\
공격자는 태그를 바꿔 가며 응답 시간을 재서 "지금 이 후보가 앞 몇 바이트까지 맞았는지"를 시간으로 읽어내고, 앞에서부터 한 바이트씩 맞춰 나가면 결국 유효한 태그를 통째로 복원할 수 있다 — 이것이 **타이밍 공격**이다.

방어는 **상수시간 비교**다 — 두 태그가 어디서 갈리든 항상 전체를 끝까지 비교해 걸리는 시간을 입력 내용과 무관하게 만든다.\
표준 라이브러리가 이를 위한 별도 함수를 제공한다. Go `crypto/hmac`은 문서에 못박는다 — *"Equal은 두 MAC을 타이밍 정보를 흘리지 않고 비교한다"*, 그리고 *"수신자는 타이밍 부채널을 피하기 위해 반드시 Equal로 MAC을 비교해야 한다"*([Go crypto/hmac](https://pkg.go.dev/crypto/hmac)).\
즉 HMAC을 쓴다는 것은 태그 계산뿐 아니라 **태그 비교까지 상수시간으로 한다**는 뜻이며, 둘 중 하나만 빠뜨려도 인증이 새어 나간다.

> **부채널 공격(side-channel attack)** — 알고리즘이 아니라 그 실행의 부수 관찰량(시간·전력·소리)에서 비밀을 캐내는 공격.\
> 예: 태그 비교에 걸린 밀리초 차이를 재서 정답 태그를 한 바이트씩 알아내는 것.

## 6. 표준과 구현 — 라이브러리가 제공하는 것

> 출처: 원고 §6 (Go `crypto/hmac`을 예로 든 것)

HMAC은 RFC 2104가 정의하고 NIST FIPS 198-1이 미국 연방 표준으로 채택한, 20년 넘게 검증된 구성이다.\
그래서 직접 `ipad`/`opad`를 조립할 일은 없다 — 표준 라이브러리를 쓴다.\
공식 문서의 표준 사용 패턴이 그대로 검증 함수다([Go crypto/hmac](https://pkg.go.dev/crypto/hmac)).

```text
// messageMAC 이 message 에 대한 유효한 HMAC 태그인지 검사한다.
func ValidMAC(message, messageMAC, key []byte) bool {
    mac := hmac.New(sha256.New, key)   // 키를 섞은 계산기
    mac.Write(message)
    expectedMAC := mac.Sum(nil)
    return hmac.Equal(messageMAC, expectedMAC)   // == 가 아니라 상수시간 비교 (§5)
}
```

핵심은 두 줄이다 — 해시 생성자와 키로 계산기를 만들고(`hmac.New`), 마지막을 상수시간 비교로 닫는다(`hmac.Equal`).\
여기서 `==`를 쓰면 §5의 타이밍 구멍이 그대로 열린다.

## 7. 적용 예 — 무엇에 서명하고 키는 누가 쥐나

> 출처: 원고 §7 (프로젝트 고유 결정 → 일반 설계 원리로 일반화)

개념을 배포 경로에 얹으면 두 가지 설계 결정이 남는다 — **서명 범위**와 **키 보유**.

- **서명 범위 = 요청의 의미를 결정하는 모든 축.**\
  예: 정규화된 method + path + body digest + 요청 ID + 발급/만료 시각.\
  왜 이들 전부인가는 §1의 "변조" 질문에서 나온다 — 요청의 의미를 정하는 축이 모두 태그 안에 들어가야, 그중 하나라도 바뀌면 검증이 깨진다.\
  method·path는 "무엇을 하는 요청인가", body digest는 "본문 전체"(digest만 서명해도 본문 변조를 잡는다 — [`sha256-and-digest.md`](sha256-and-digest.md) §4), 요청 ID는 요청의 신원, 발급/만료는 유효 시간 창이다.\
  그리고 한 가지 원칙이 따라온다 — **"서명 밖의 값은 판정에 쓰지 않는다."** 태그로 보호되지 않는 필드로 결정을 내리면, 그 필드는 공격자가 자유롭게 바꿀 수 있는 입력이기 때문이다.
- **키는 신뢰 경계 안의 시크릿 저장소가 단독 보유한다.**\
  §4에서 봤듯 HMAC은 대칭 키라 **키를 쥔 쪽이 곧 명령할 수 있는 쪽**이므로, 이 키는 시스템 장악과 같은 강도의 비밀이다.\
  그래서 사람이 만지거나 이미지에 넣지 않고 시크릿에 가두며, 발급·보관·교체를 별도 축이 소유한다.\
  검증에 실패하면 **적용하지 않고 거절을 기록한다 — 예외 없음**(fail-closed).\
  그리고 §1에서 TLS가 인증을 대신하지 못하듯, 전송 계층(SSH 등)은 인증 수단이 아니라 **서명 검증을 통과한 뒤에 열리는 전송**일 뿐이다 — 관문의 순서가 고정이라는 것이 이 구조의 안전 성질이다.

## 8. 한계 — HMAC은 재전송을 막지 못한다

> 출처: 원고 §8

HMAC이 증명하는 것은 딱 두 가지, **진위와 무결성**이다.\
그런데 유효한 요청을 **그대로 복사해 다시 보내면**, 그 복사본도 진짜 키로 만든 진짜 태그를 달고 있으므로 검증을 **당연히 통과한다.**\
HMAC은 "이 태그가 유효한가"에 답할 뿐 "이 요청을 전에 본 적 있는가"에는 답하지 못한다 — 즉 **freshness(신선함)를 보장하지 않는다.**

```text
       원본 유효 요청                          공격자의 복사본
  method+path+digest+태그      ── 그대로 복사 ──▶  똑같은 method+path+digest+태그
  (진짜 키로 만든 진짜 태그)                       (같은 태그이므로 검증 통과!)

  → 지나간 동작이 조용히 재실행된다 (되돌린 버전이 되살아나고, 성공처럼 보인다)
```

배포에서 이건 특히 위험하다 — 지나간 배포를 재실행하면 되돌린 버전이 조용히 되살아날 수 있고, 그 재실행이 성공처럼 보인다.\
프록시·CI의 타임아웃 재시도와 응답 유실도 같은 결과를 만든다.\
그래서 재전송은 **HMAC 밖의 별도 방어선**이 맡는다.

- **시간 창** — 만료 시각이 지났거나 발급 시각이 허용 skew 밖이면 거절·기록한다. 오래된 요청의 재사용 창을 좁힌다.
- **멱등 원장** — 부작용을 내기 전에 요청 ID를 내구적으로 선점하고, **같은 요청 ID + 같은 body digest면 재실행하지 않고 현재 상태를 반환**한다. 같은 요청이 두 번 와도 동작은 한 번만 일어난다.

정리하면 **HMAC은 "누가·무엇을"에 답하고, 요청 ID 멱등은 "몇 번"에 답한다.**\
두 축은 겹치지 않으므로 어느 하나로 다른 하나를 대신할 수 없다 — 서명과 멱등 원장을 함께 두는 이유가 여기 있다.

## 핵심 문장

- **HMAC은 진위(키를 아는 쪽이 만들었다)와 무결성(그 뒤 안 바뀌었다) 둘만 증명한다.**
- **TLS는 전송 구간을 지킬 뿐 "이 HTTP 요청의 발신자가 누구인가"를 애플리케이션에 증명하지 못한다.**
- **이중 해시는 장식이 아니라 단순 `H(K‖msg)`의 길이 확장 공격을 막기 위한 구조다.**
- **HMAC은 대칭 키라 검증자가 곧 서명자다 — 닫힌 두 당사자에 맞고, 키가 새면 양쪽이 무너진다.**
- **태그 비교를 `==`로 하면 타이밍 공격이 열린다 — 반드시 상수시간 비교를 써야 한다.**
- **HMAC은 freshness를 보장하지 않는다 — 재전송은 시간 창과 멱등 원장이라는 별도 축이 막는다.**

## 용어 풀이

- **HMAC(Hash-based MAC)** — 공유 비밀 키와 해시로 만드는 메시지 인증 코드. 이중 해시 구조가 특징.
- **MAC(Message Authentication Code)** — 비밀 키로 만들어 메시지에 붙이는 인증 태그. 진위+무결성을 증명한다.
- **대칭 키(Symmetric Key)** — 서명자와 검증자가 같은 키를 쥐는 방식. 검증자가 곧 서명자가 될 수 있다.
- **비대칭 키/공개 키 서명(Asymmetric)** — 개인키로 서명, 공개키로 검증. 검증 능력과 서명 능력이 분리된다.
- **`ipad`/`opad`** — HMAC에서 키를 안쪽·바깥쪽 해시에 다르게 섞기 위한 두 상수(0x36, 0x5C 반복).
- **길이 확장 공격(Length Extension Attack)** — `H(K‖msg)`에서 키 없이 뒤에 데이터를 덧붙인 유효 태그를 만드는 공격.
- **타이밍 공격(Timing Attack)** — 비교·연산에 걸린 시간 차이로 비밀을 알아내는 부채널 공격.
- **상수시간 비교(Constant-time Comparison)** — 어디서 갈리든 항상 끝까지 비교해 시간이 입력과 무관하게 만드는 비교.
- **부채널 공격(Side-channel Attack)** — 알고리즘이 아니라 실행의 부수 관찰량(시간·전력)에서 비밀을 캐는 공격.
- **freshness(신선함)** — "이 요청을 전에 본 적 있는가"의 성질. HMAC이 보장하지 못하는 것.
- **재전송 공격(Replay Attack)** — 유효한 요청을 그대로 복사해 다시 보내 같은 동작을 재실행시키는 공격.
- **멱등(Idempotency)** — 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질.
- **fail-closed(모르면 닫는다)** — 판정 불가·검증 실패 시 통과가 아니라 거절로 떨어지게 하는 설계.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **HMAC은 밑 해시가 충돌 저항을 잃어도 오래 버틴다.** HMAC의 안전성 증명은 밑 해시의 충돌 저항이 아니라 더 약한 성질(PRF성)에 의존한다. 그래서 HMAC-SHA-1은 SHA-1 충돌이 실증된 뒤에도 MAC 용도로는 즉시 무너지지 않았다(그래도 신규 설계에는 SHA-256을 쓴다). "해시가 깨졌다"와 "그 해시 기반 HMAC이 깨졌다"는 별개의 사건이다.
- **HMAC vs 이제는 CMAC·Poly1305·AEAD.** HMAC은 해시 기반 MAC의 표준이지만, 블록 암호 기반 CMAC이나 스트림 기반 Poly1305도 같은 역할을 한다. 또 요청 본문을 암호화까지 해야 하면 MAC을 따로 붙이는 대신 AES-GCM·ChaCha20-Poly1305 같은 **AEAD**(인증 암호화)를 쓰는 것이 요즘 권장이다 — "암호화 따로, MAC 따로"를 손으로 조합하다 순서를 틀리는 사고(예: MAC-then-encrypt 오용)를 피하기 위해서다.
- **키 회전(rotation)도 HMAC 운영의 일부다.** 대칭 키는 새면 양쪽이 무너지므로, 유출 대비로 주기적 교체가 필요하다. 무중단 교체를 위해 검증 측이 "현재 키 + 직전 키"를 잠시 함께 받아들이는 창을 두는 것이 흔한 패턴이다 — 공개키 회전에서 JWKS가 옛 `kid`·새 `kid`를 잠시 공존시키는 것([`jwks.md`](jwks.md) §3)과 발상이 같다.
