# foundations/security/인가를 켜는 두 단계 — audit에서 enforce로

> 복습은 개념 질문에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/tech/security/audit-enforce-rollout.md` · 이관일 2026-09-16.\
> 본문 절들은 **원고**를 고쳐 쓴 것이다(문체·순서 유지). 마지막 적용 절의 프로젝트 고유 예(게이트웨이 `/internal`)는 "이미 도는 시스템에 인가를 켜는 배포 전략" 일반으로 다시 썼다.\
> 「한눈에」의 비유·그림과 전후 대비는 **Claude가 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**audit / enforce** = 이미 돌고 있는 시스템에 인가("인증 없으면 거절")를 켤 때 쓰는 두 모드.\
**audit**(관측)은 검사하되 없어도 막지 않고, **enforce**(강제)는 판정하고 막는다. 둘로 나누는 유일한 이유는 **무중단 이관**이다.

---

## 한눈에 — 쉽게 말하면

새로 신분증 검사를 도입하는 건물의 **두 단계**를 떠올리면 된다. *(Claude 보강 — 원고의 "문" 비유를 확장)*

```text
1단계 audit: "신분증 확인하되 없어도 들여보내고 기록"
+---------------------------------------------+
| 신분증 있음 → 검증 (틀리면 거절)                |
| 신분증 없음 → 경고 기록하고 통과                 |
| 목적: "다들 신분증을 챙겨 오는가" 를 데이터로 관찰   |
| ⚠ 이 동안 보안 경계는 아직 서 있지 않다           |
+---------------------------------------------+
          ↓  모든 호출이 서명을 붙이는 것이 확인되면
2단계 enforce: "신분증 없으면 입장 불가"
+---------------------------------------------+
| 유효 서명만 통과, 없거나 위조면 전부 거절 (401)   |
| 무서명 경로가 닫히는 이 순간 인가가 완성된다        |
+---------------------------------------------+
```

**보안 기능을 점진적으로 켜는 일반 방법도 똑같은 구조다.** 관측 단계를 먼저 두는 것을 흔히 "dark launch"나 "audit mode"라 부르고, 강제 전 관측으로 "정말 안전하게 닫을 수 있는가"를 데이터로 확인한다.\
실무 예: 클라이언트와 서버가 서로 다른 시점에 배포되므로, 서버가 먼저 enforce로 떠 버리면 아직 서명을 안 붙이는 구버전 클라이언트의 정상 호출이 전부 거절되어 서비스가 끊긴다.\
쉽게 말하면 — 두 모드 모두 서명이 **틀린** 경우는 거절한다. audit가 봐주는 것은 오직 "서명이 아예 없는" 경우뿐이다.

## 문제 — 이 개념이 답하려는 질문

```text
이미 돌고 있는 시스템에 "인증 없으면 거절" 을 새로 켠다
   스위치를 그냥 켜면
        ↓
   아직 인증 정보를 안 붙이는 기존 호출자가 그 순간 전부 거절당한다
        ↓
   그 호출이 배포 파이프라인의 일부라면 → 배포 자체가 끊긴다

질문: 서비스를 끊지 않고 인가를 어떻게 켜나?
```

아래 서머리는 두 모드가 하는 일 → 왜 한 번에 안 켜나(무중단 이관) → audit의 위험 → 적용 순서 → 정리, 로 이 문제를 분석한 것이다.

## 전체 흐름

```text
audit (관측·과도기): 검사하되 없어도 막지 않음 — 보안 경계 아직 안 섬
        ↓  로그에서 "모든 호출이 서명을 붙인다" 확인
enforce (강제): 판정하고 막음 — 무서명 경로가 닫혀 인가 완성
        │
        ├─ 순서 고정: 클라이언트 먼저(서명 붙임) → 서버 audit → 서버 enforce
        ├─ 위험: audit 는 열린 창 — 그 동안 인가는 사실상 꺼진 것
        └─ 안전장치: 기본값 = enforce (모르면 닫는다, fail-closed)
```

## 1. 두 모드가 하는 일

> 출처: 원고

- **audit(관측·과도기) 모드는 인증을 검사하되 없어도 막지 않는다.**\
  서명이 붙어 있으면 정상적으로 검증하고(틀리면 거절), 서명이 아예 없으면 경고 로그만 남기고 통과시킨다.\
  목적은 판정이 아니라 관측이다 — "지금 이 표면을 부르는 호출들이 실제로 서명을 붙이고 있는가"를 로그로 확인하는 단계다.\
  이 모드에서는 무서명 호출이 그대로 통과하므로, **보안 경계는 아직 서 있지 않다.**
- **enforce(강제) 모드는 인증을 판정하고 막는다.**\
  유효한 서명이 붙은 호출만 통과하고, 서명이 없거나 위조된 호출은 전부 거절한다(HTTP 401).\
  무서명 경로가 닫히는 이 순간이 인가가 실제로 완성되는 지점이다.

한 문장 비유로 두면, audit는 "신분증을 확인하되 없어도 들여보내고 기록하는 문", enforce는 "신분증 없으면 입장 불가인 문"이다.\
두 모드 모두 서명이 **틀린** 경우는 거절한다는 점이 중요하다 — audit가 봐주는 것은 오직 "서명이 아예 없는" 경우뿐이고, 잘못된 서명은 어느 모드에서든 막힌다.

---

## 2. 왜 한 번에 켜지 않나 — 무중단 이관

> 출처: 원고

핵심 이유는 배포 절단을 피하는 것이다.\
인증을 붙이는 쪽(클라이언트)과 검사하는 쪽(서버)은 서로 다른 시점에 배포된다.

전/후를 나란히 두면 순서를 왜 고정하는지 보인다.

```text
잘못된 순서: 서버를 enforce 로 먼저             옳은 순서: 클라이언트 먼저
+-----------------------------+          +-----------------------------+
| 아직 서명을 안 붙이는          |          | ① 클라이언트를 먼저 배포        |
| 구버전 클라이언트의 정상 호출이  |          |    → 모든 호출에 서명을 붙임     |
| 전부 401 로 거절              |          | ② 서버를 audit 로 띄워 관측      |
| → 배포 파이프라인이 끊긴다      |          | ③ 무서명 경고가 안 뜨면 enforce  |
+-----------------------------+          +-----------------------------+
  성급한 강제가 서비스를 끊는다             이 시점엔 무서명이 없어 끊길 게 없다
```

그래서 순서를 고정한다 — **클라이언트를 먼저** 서명을 붙이도록 배포하고, 서버는 audit로 띄워 그 서명된 호출을 관측한다.\
로그에서 "모든 호출이 서명을 붙이고 있다"가 확인되면(무서명 경고가 더는 뜨지 않으면), 그때 서버를 enforce로 올린다.\
이 시점에는 무서명 호출이 없으므로 enforce로 올려도 끊기는 것이 없다.\
되돌리기도 싸다 — 문제가 생기면 다시 audit로 내리면 무서명이 다시 통과한다.

이 패턴은 보안 기능을 점진적으로 켜는 일반적 방법이다.\
관측 단계를 먼저 두는 것을 흔히 **"dark launch"**나 **"audit mode"**라 부르고, 강제 전 관측으로 "정말 안전하게 닫을 수 있는가"를 데이터로 확인한다는 발상이 공통이다.

## 3. 위험 — audit는 열린 창이다

> 출처: 원고

audit의 대가를 정직하게 봐야 한다.\
audit로 떠 있는 동안은 **무서명 호출이 그대로 통과**하므로, 그 기간만큼 인가가 실제로는 꺼져 있는 것과 같다.\
그래서 audit는 목적이 분명한 **과도기**여야 하고, 관측이 끝나면 지체 없이 enforce로 넘어가야 한다.\
audit에 오래 머무르면 "인가를 켰다"고 착각하면서 실제로는 열려 있는 상태가 길어진다.

이 때문에 설계에서 기본값을 **enforce로 두는** 선택이 중요하다.\
설정을 깜빡 빠뜨렸을 때 안전한 쪽(닫힘)으로 떨어지게 하려는 것이다.\
audit는 이관 중에만 명시적으로 켜는 예외 상태이고, 아무것도 지정하지 않은 정상값은 enforce다 — **"모르면 닫는다"(fail-closed)**의 한 형태다.

> **fail-closed / fail-open** — 판정 불가·설정 누락 시 어느 쪽으로 떨어지느냐.\
> 예: 기본값을 enforce로 두면(fail-closed) 설정을 빠뜨려도 문이 닫힌 채 안전하고, 기본값을 audit로 두면(fail-open) 빠뜨리는 순간 문이 열린 채 방치된다.

## 4. 적용 순서 — 무중단으로 인가를 켠 실제 절차

> 출처: 원고 (프로젝트 고유 예 → 일반 절차로 일반화)

이 두 모드는 "원래 네트워크 경계에만 의존하던 내부 관리 표면"에 서명 인가를 새로 도입할 때 실제로 쓰인다.\
그런 표면은 흔히 특정 클라이언트(예: 배포 agent)만 불러야 하는데 인증이 없던 자리다. 인가를 켜는 순서는 이랬다.

1. **클라이언트를 먼저 배포**해 모든 내부 호출에 서명(정규화된 요청에 건 HMAC)을 붙이게 했다.
2. **서버를 audit로 띄웠다.**\
   이 상태에서 실제 작업을 한 번 돌려, 클라이언트의 호출이 로그에 "valid-signature 양성"으로 찍히는지 관측했다 — 무서명 경고가 아니라 양성이면 클라이언트가 서명을 붙이고 있다는 증거다.
3. **관측이 확인되면 서버를 enforce로 올려** 무서명 호출을 차단한다.

이 순서 덕분에 파이프라인이 한 번도 끊기지 않고 인가가 켜진다.\
여기에 "모르면 닫는다"를 지키는 장치가 겹쳐 붙는다.

- 기본값을 **enforce로 둔 것.**
- **audit에서도 키가 없으면 아예 기동을 거부**하도록 한 것 — audit가 성공한 척 위장하는 것을 막기 위해서다.
- **잘못된 모드 문자열은 기동을 거부**하는 것.

세 장치 모두 "설정 실수가 조용히 문을 여는" 사고를 막는다.

## 5. 정리 — 언제 무엇을

> 출처: 원고

- **audit는 켜는 중에 잠깐 쓰는 관측 모드다** — 클라이언트가 인증을 붙이는지 데이터로 확인하는 동안만.
- **enforce는 정상 운영 상태이자 안전한 기본값이다** — 인증 없는 호출을 실제로 막는다.
- 둘을 나누는 유일한 이유는 **무중단 이관**이고, audit에 머무는 시간은 짧을수록 좋다(그동안 문이 열려 있으므로).
- 이관이 끝나면 **enforce가 최종 상태**다.

## 핵심 문장

- **audit는 검사하되 없어도 안 막고, enforce는 판정하고 막는다 — 틀린 서명은 두 모드 다 거절한다.**
- **둘로 나누는 유일한 이유는 무중단 이관이다 — 클라이언트와 서버가 다른 시점에 배포되기 때문.**
- **순서는 고정이다 — 클라이언트 먼저(서명 붙임) → 서버 audit(관측) → 서버 enforce(강제).**
- **audit는 열린 창이다 — 그 동안 보안 경계는 서 있지 않으므로 과도기를 짧게 둔다.**
- **기본값은 enforce여야 한다 — 설정을 빠뜨려도 안전한 쪽(닫힘)으로 떨어지게(fail-closed).**
- **audit에서도 키가 없으면 기동을 거부한다 — "성공한 척 위장"을 막는 장치다.**

## 용어 풀이

- **audit(관측) 모드** — 인증을 검사하되 없어도 막지 않고 경고만 기록하는 과도기 모드.
- **enforce(강제) 모드** — 유효 서명만 통과시키고 무서명·위조를 거절하는 정상 운영 모드.
- **무중단 이관(zero-downtime migration)** — 서비스를 끊지 않고 새 동작으로 갈아타는 것.
- **dark launch** — 기능을 사용자에게 강제하기 전에 조용히 띄워 관측하는 배포 기법.
- **fail-closed(모르면 닫는다)** — 설정 누락·판정 불가 시 거절 쪽으로 떨어지는 설계.
- **fail-open** — 반대로 통과 쪽으로 떨어지는 설계. 편하지만 조용히 문을 연다.
- **canonical(정규화)** — 서명 전에 요청을 정해진 형태로 맞추는 것(공백·순서 등). 같은 의미의 요청이 같은 서명을 내게 한다.
- **관측 → 강제 순서(observe-then-enforce)** — 강제 전에 데이터로 안전을 확인하는 롤아웃 원칙.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **같은 "observe-then-enforce"가 보안 밖에도 널려 있다.** Kubernetes의 admission webhook은 `Audit`→`Enforce`로, Content-Security-Policy는 `Content-Security-Policy-Report-Only` 헤더로 먼저 위반을 보고만 받다가 강제로 전환한다. 스키마 검증·rate limit 도입도 같은 순서를 쓴다 — "먼저 관측해 기존 트래픽이 새 규칙을 통과하는지 확인, 그다음 강제." audit/enforce는 이 일반 롤아웃 패턴의 인가판이다.
- **audit 로그가 "관측 완료" 판정의 유일한 근거다.** enforce로 넘어갈 시점을 정하는 것은 감이 아니라 로그다 — "무서명 경고가 0이 된 지 충분한 기간(모든 클라이언트 배포·모든 주기적 잡이 한 바퀴 돈 시간)"을 데이터로 확인해야 한다. 그래서 audit 단계의 로그 필드(무서명인지 valid인지, 어느 호출자인지)를 처음부터 잘 설계해 두는 것이 이 롤아웃의 실질적 성패를 가른다.
- **"audit가 성공한 척 위장"이 왜 특히 위험한가.** §4의 "audit에서도 키가 없으면 기동 거부"는 silent failure 방어다. 키 설정이 빠졌는데 audit가 조용히 뜨면, 로그에는 "무서명 통과"만 잔뜩 찍히고 운영자는 "아직 클라이언트가 서명을 안 붙이나 보다"라고 오해해 enforce 전환을 미룬다 — 실제로는 서버가 검증할 키조차 없는 상태다. 그래서 "관측은 하되 관측할 수단(키)이 없으면 뜨지 않는다"가 audit의 정직성을 지킨다.
