# foundations/security/JWKS — 발급자의 공개키를 어디서 얻고 회전을 어떻게 따라가나

> 복습은 개념 질문에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/tech/security/jwks.md` · 이관일 2026-09-16.\
> 본문 절들(§1~§6)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지). 특정 프로젝트의 게이트·코드 경로 참조는 "JWKS로 서명 검증을 세우는 검증자 일반"으로 일반화했다.\
> 「한눈에」의 비유·그림과 세로 흐름도는 **Claude가 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**JWKS**(JSON Web Key Set) = 토큰 발급자가 자신의 **공개키 집합을 JSON으로 게시하는 표준 엔드포인트**. 검증자가 키를 미리 심어 두지 않고도 발급자에게서 그때그때 가져와 **키 회전을 따라가게** 한다.\
**JWK**(JSON Web Key) = 그 집합 안의 암호 키 하나를 표현한 JSON 객체.

---

## 한눈에 — 쉽게 말하면

위조 방지 도장을 검증하려고 **관공서의 "현재 유효한 도장 목록" 게시판**을 보는 것을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
나쁜 방법: 관공서 도장을 내 서랍에 박아 둔다      좋은 방법: 관공서 게시판을 본다 (JWKS)
+-----------------------------+          +-----------------------------+
| 관공서가 도장을 바꾸는 순간    |          | 관공서가 게시판만 갱신하면      |
| 내 서랍의 옛 도장으로는        |          | 나는 게시판을 다시 볼 뿐        |
| 진짜 문서도 전부 거절          |          | 내 검증 코드는 그대로          |
| → 회전 때마다 내가 재배포       |          | → 회전이 스스로 전파된다        |
+-----------------------------+          +-----------------------------+
```

**공개키 배포도 똑같은 구조다.** 검증자가 쥐는 것은 특정 키가 아니라 "발급자의 키 목록을 어디서 가져오는가"라는 **위치**이고, 키 자체는 그 위치에서 그때그때 온다.\
실무 예: OIDC ID 토큰(RS256)을 검증하려면 발급자의 공개키가 필요한데, 그 키를 코드에 박으면 발급자가 키를 바꾸는 순간 검증이 통째로 깨진다 — JWKS가 그 "어디서·어떻게"를 표준화한다.\
쉽게 말하면 — [`oidc.md`](oidc.md)가 *"서명이 발급자의 공개 키로 검증되지 않으면 payload의 어떤 값도 신뢰할 수 없다"*에서 멈춘 그 자리, 검증자는 그 공개키를 어디서·어떻게 얻는가를 이 글이 잇는다.

## 문제 — 이 개념이 답하려는 질문

```text
비대칭 서명(RS256): 발급자는 개인키로 서명, 검증자는 짝인 공개키로 검증
   공개키는 비밀이 아니라 아무에게나 줘도 안전 (그것으론 위조 못 함)
   → 어려운 문제는 기밀성이 아니라 "전달과 회전"

순진한 답: 검증자 설정에 공개키를 한 번 박아 둔다
   → 발급자가 키를 바꾸는 순간(키 회전) 무너진다

JWKS 가 답하는 질문:
   공개키를 검증자에게 어떻게 넘기고, 발급자가 바꿀 때 어떻게 따라가게 하나?
```

아래 서머리는 §1 왜 필요한가 → §2 JWK/JWKS 구조 → §3 동작(discovery·kid·회전) → §4 실무에서 자주 비어 있는 자리 → §5 보안 고려 → §6 표준, 의 순서로 이 문제를 분석한 것이다.

## 전체 흐름

```text
공개키 하드코딩 → 회전에서 조용히 깨짐 (§1)
        ↓
JWK = 키 하나, JWKS = keys 배열 (여러 키 공존 가능) (§2)
        ↓
동작: 발급자 URL → discovery → jwks_uri → JWK Set (§3)
        ↓
   JWT 헤더의 kid 로 집합에서 키를 고른다
        ↓
   서명 검증 통과 후에야 claim 을 신뢰
        ↓
   회전: 새 kid 추가, 옛 키는 유예로 남김
        "캐시하되 모르는 kid 면 재페치" = 회전 계약의 전부
        ↓
보안: HTTPS 페치 · 알고리즘 서버 고정 · kid 는 경계 밖 힌트 · fail-closed (§5)
```

## 1. 왜 필요한가 — 공개키를 하드코딩하면 회전에서 조용히 깨진다

> 출처: 원고 §1

비대칭 서명의 성질부터 짚어야 이 문제가 보인다.\
RS256에서 발급자는 **개인키로 서명**하고 검증자는 짝인 **공개키로 검증**한다.\
공개키는 이름 그대로 비밀이 아니라서 아무에게나 내줘도 안전하다 — 그것으로는 서명을 위조할 수 없기 때문이다.\
그래서 여기서 어려운 문제는 기밀성이 아니라 **전달과 회전**이다.

가장 순진한 답은 검증자 설정에 발급자의 공개키를 **한 번 박아 두는 것**이고, 이건 발급자가 키를 바꾸는 순간 무너진다.

> **키 회전(key rotation)** — 발급자가 서명키를 주기적으로, 또는 유출이 의심되면 즉시 새 키로 갈아타는 보안 위생.\
> 예: 회전 뒤 발급되는 토큰은 새 개인키로 서명되므로, 박아 둔 옛 공개키로는 하나도 검증되지 않는다.

회전 뒤 발급되는 토큰은 새 개인키로 서명되므로, 박아 둔 옛 공개키로는 **하나도 검증되지 않는다.**\
검증자는 진짜 토큰을 전부 거절하기 시작하고(가용성 사고), 그걸 피하려면 회전 때마다 검증자를 다시 배포해 키를 손으로 맞춰야 한다.

JWKS는 이 결박을 끊는다.\
발급자가 자신의 현재 공개키들을 **정해진 엔드포인트에 게시**하고 검증자가 그것을 가져오면, 회전은 발급자 쪽에서 일어나되 검증자 코드를 건드리지 않고 전파된다.\
검증자가 쥐는 것은 특정 키가 아니라 "발급자의 키 목록을 어디서 가져오는가"라는 **위치**이고, 키 자체는 그 위치에서 그때그때 온다.

## 2. JWK과 JWKS — 공개키 하나, 그리고 그 집합

> 출처: 원고 §2

먼저 낱개 단위인 JWK를 본다.\
**JWK(JSON Web Key)는 암호 키 하나를 표현한 JSON 객체**다(RFC 7517). 판정에 자주 쓰이는 필드 넷은 이렇다.

- **`kty`** — 키 종류(key type). `"RSA"`·`"EC"` 같은 알고리즘 계열.
- **`use`** — 용도. `"sig"`(서명 검증용)냐 `"enc"`(암호화용)냐. 서명 검증에 쓰는 것은 `"sig"`다.
- **`alg`** — 이 키로 쓰도록 의도된 알고리즘(예: `"RS256"`).
- **`kid`** — 키 식별자(key ID). 여러 키 중 하나를 지목하는 이름표이며, 회전 때 옛 키와 새 키를 구분하는 핵심이다(§3).

RSA 공개키의 **실제 키 재료**는 두 수 — 모듈러스 `n`과 지수 `e` — 이고, 이 필드는 RFC 7517이 아니라 그것이 위임하는 RFC 7518(JWA) §6.3.1이 정의한다(둘 다 Base64urlUInt 인코딩, `e`는 흔히 65537 = `"AQAB"`).\
즉 JWK 하나를 받으면 검증자는 `n`·`e`로 RSA 공개키를 복원해 서명 검증에 쓴다.

집합 단위가 **JWKS(JWK Set)**다.\
RFC 7517은 이를 "`keys` 멤버를 가진 JSON 객체이며, `keys`는 JWK들의 배열"로 규정한다.\
발급자가 키를 **여러 개 한꺼번에** 게시할 수 있다는 이 점이 회전을 매끄럽게 만든다 — 옛 키와 새 키가 배열 안에 잠시 공존하기 때문이다(§3).

```text
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "a1b2c3d4...",       // 이 키를 지목하는 이름표
      "n": "0vx7agoebGcQ...",     // 모듈러스 (Base64urlUInt · RFC 7518 §6.3.1)
      "e": "AQAB"                 // 지수 65537
    }
  ]
}
```

## 3. 동작 — discovery로 위치를 찾고, kid로 키를 고른다

> 출처: 원고 §3

검증자가 발급자 URL 하나에서 출발해 검증된 서명에 닿기까지는 네 걸음이고, 순서가 곧 신뢰의 사슬이다.

```text
발급자 URL
   ↓  ① discovery
/.well-known/openid-configuration  (설정 문서)
   ↓  그 안의 jwks_uri 필드 (반드시 https)
JWK Set 문서
   ↓  ② JWT 헤더의 kid 로 같은 kid 를 가진 키를 고른다
고른 JWK (n·e 로 RSA 공개키 복원)
   ↓  ③ 서명 검증
검증 통과 → 이제야 payload claim 을 신뢰 (oidc.md §3)
   ↓  ④ 회전: 발급자가 새 kid 추가, 옛 키는 유예로 남김
"캐시하되 모르는 kid 면 재페치" = 회전 계약의 전부
```

- **① 위치 찾기(discovery)** — OIDC 발급자는 발급자 URL 뒤에 `/.well-known/openid-configuration`을 붙인 자리에 설정 문서를 게시하고(OIDC Discovery 1.0), 그 문서 안의 **`jwks_uri`** 필드가 JWK Set URL을 담는다. 스펙은 이 URL이 반드시 `https`여야 한다고 못박는다(그 이유는 §5).
- **② 키 고르기** — 검증할 JWT 헤더에는 `kid`가 실려 있다(RFC 7515의 JOSE 헤더 파라미터 — "이 서명을 만든 키가 무엇인지 알려 주는 힌트"). 검증자는 그 `kid`를 읽어 JWK Set에서 **같은 `kid`를 가진 키**를 고른다. `kid`가 없으면 집합의 키를 하나씩 다 시도해야 한다.
- **③ 서명 검증** — 고른 JWK의 공개키(`n`·`e`로 복원한 RSA 공개키)로 서명을 확인한다. 이 검증이 통과한 다음에야 payload claim을 신뢰할 수 있다 — JWKS는 이 첫 관문에 넣을 열쇠를 조달하는 일을 한다.
- **④ 회전 따라가기** — 발급자는 JWK Set에 **새 `kid`를 추가**하고 옛 키는 이미 발급된 토큰이 검증되도록 얼마간 유예로 남긴다. 검증자는 매 요청 페치하면 발급자를 두드리게 되므로 JWK Set을 **캐시**하되, **모르는 `kid`를 만나면 다시 페치**한다. "캐시하되 미지 `kid`면 재페치"라는 한 줄이 회전 계약의 전부다.

## 4. 실무에서 자주 비어 있는 자리 — fail-closed 스캐폴드

> 출처: 원고 §4 (프로젝트 고유 게이트·코드 → 일반 패턴으로 일반화)

JWKS 페치는 구현이 밀리기 쉬운 자리다. 그래서 초기에 흔히 이런 모양을 만난다 — **서명 검증 자리에 스캐폴드만 세우고, 페치 함수는 값 대신 오류를 낸다.**

```text
검증자 구조
  · 서명 검증 파트: kid 로 발급자 공개키를 얻어 서명 확인
  · claim 대조 파트: 그 뒤 각 claim 을 본다

문제: "공개키를 얻는" 함수가 아직 "페치 미구현" 오류만 낸다
        ↓
어떤 키도 얻지 못한다
        ↓
fail-closed 설계상 → 토큰을 통과시키는 게 아니라 전부 거절
```

이 구조에서 서명 검증 파트는 `kid`로 발급자 공개키를 얻어 확인하고, claim 대조 파트는 그 뒤 각 claim을 본다.\
JWKS 페치가 사는 곳이 바로 그 "발급자 공개키를 얻는" 지점이다.

페치가 **비어 있으면** 검증자는 어떤 키도 얻지 못하고, **fail-closed 설계상 이는 토큰을 통과시키는 것이 아니라 전부 거절**하는 것으로 귀결된다.\
그래서 그 사이 기계가 보증하는 경계는 앞단(HMAC + 신선도)까지이고, OIDC 서명 검증은 막혀 있다.\
실제 서명 검증이 서려면 발급자의 `jwks_uri`에서 공개키를 페치·캐시하고 회전을 추적하는 조각을 채워야 한다 — 검증된 서명이 신뢰할 수 있는 claim을 내주기 전까지 claim 대조는 대조할 대상이 없기 때문이다.\
(발급자 URL·회전·캐시가 플랫폼에서 실제로 서는 형태는 흔히 `[구현 검증]`으로 이연되는 항목이다.) *(원고의 이연 표기 유지)*

## 5. 보안 고려 — 신뢰의 뿌리가 페치와 알고리즘 고정에 있다

> 출처: 원고 §5

JWKS 검증이 새는 곳은 대개 몇 군데로 정해져 있고, 각각이 하나의 침입 경로를 연다.

- **HTTPS로만 페치한다.** `jwks_uri`가 `https`여야 한다는 규정은 장식이 아니다.\
  평문 HTTP로 키를 가져오면 중간자(MITM)가 응답을 가로채 **가짜 공개키를 주입**할 수 있고, 그러면 공격자가 그 짝 개인키로 서명한 토큰이 버젓이 "검증"된다.\
  페치 채널의 무결성이 이후 모든 서명 검증의 신뢰 뿌리이므로, 여기가 뚫리면 아래가 전부 무의미해진다.
- **알고리즘 혼동 공격(alg confusion)을 막는다.** 고전적 공격은 토큰이 헤더에 `"alg":"none"`(서명 없음)이나 `"alg":"HS256"`(대칭 HMAC)을 선언하는 것이다.

```text
검증자가 토큰 자신의 alg 를 믿으면          방어: 알고리즘을 서버가 고정
+-----------------------------+        +-----------------------------+
| "alg":"none" → 서명 통째 제거  |        | RSA 아닌 방식은 진입에서 거절   |
| "alg":"HS256" → 공개된 발급자  |        | 허용 알고리즘을 RS256 하나로    |
|   공개키를 HMAC 비밀키로 삼아  |        |   못박는다                    |
|   토큰 위조                   |        | → 공개키가 대칭 비밀로 오용될   |
+-----------------------------+        |   여지를 닫는다               |
  → 공개키가 대칭 비밀로 악용됨          +-----------------------------+
```

  방어는 **알고리즘을 토큰이 아니라 서버가 고정**하는 것이다 — 허용 서명 방식을 `RS256` 하나로 못박아, 공개키가 대칭 비밀로 오용될 여지를 닫는다.
- **`kid`는 신뢰 경계 밖의 힌트다.** `kid`는 서명이 검증되기 전의 토큰, 즉 공격자가 만질 수 있는 값이다.\
  그래서 `kid`는 "가져온 JWK Set **안에서** 어느 키를 시도할지"를 좁히는 데만 쓰고, 그 이상을 시켜서는 안 된다 — 예컨대 `kid`가 파일 경로·URL이라고 해서 임의 출처에서 키를 로드하게 두면 안 된다. `kid`는 선택지를 좁힐 뿐 새 출처를 인가하지 않는다.
- **캐시 TTL과 회전 지연은 맞바꿈이다.** 너무 오래 캐시하면 발급자가 **유출로 폐기한 키**가 은퇴 뒤에도 신뢰되고, 너무 짧으면 배포마다 발급자를 두드리다 잠깐의 불통에도 실패한다.\
  새 키는 §3의 "미지 `kid` 재페치"가, 폐기된 키는 유한한 TTL이 각각 맡는 축이다.
- **페치 실패는 fail-closed다.** JWK Set을 못 가져오거나 `kid`에 맞는 키가 없으면 검증자는 통과가 아니라 **거절**해야 한다. §4의 "무조건 오류를 내는 스캐폴드"는 이 규칙의 극단적 형태일 뿐이다.

## 6. 표준과 역사 — JOSE 제품군이 2015년 5월에 한꺼번에 나왔다

> 출처: 원고 §6

JWKS는 홀로 선 규격이 아니라 **JOSE**(JSON Object Signing and Encryption) 제품군의 한 조각이고, 이 계열은 2015년 5월에 함께 표준화됐다.

```text
RFC 7519  JWT   토큰 자체 (header.payload.signature)
RFC 7515  JWS   서명, 어느 키로 서명했는지 가리키는 kid JOSE 헤더 파라미터
RFC 7517  JWK   키 하나(JWK), 키 집합(JWK Set = keys 배열)
RFC 7518  JWA   알고리즘·키 재료, RSA 의 n·e(§6.3.1), RS256
        ↓  그 위에서
OIDC Discovery 1.0   /.well-known/openid-configuration · jwks_uri 로 발급자를 JWK Set 에 묶음
```

이 규격들이 함께 있어 검증자는 발급자 URL 하나에서 출발해 검증된 서명까지 도달한다 — 이 문서가 §3에서 따라간 그 경로다.

---

## 핵심 문장

- **공개키의 어려운 문제는 기밀성이 아니라 전달과 회전이다 — JWKS가 그 "어디서·어떻게"를 표준화한다.**
- **검증자가 쥐는 것은 특정 키가 아니라 "키 목록을 어디서 가져오는가"라는 위치다.**
- **회전 계약의 전부는 한 줄이다 — "캐시하되 모르는 `kid`를 만나면 재페치."**
- **`jwks_uri`가 `https`여야 하는 것은 페치 채널이 모든 서명 검증의 신뢰 뿌리이기 때문이다.**
- **알고리즘은 토큰이 아니라 서버가 고정한다 — 안 그러면 공개키가 HS256 비밀키로 악용되거나 `none`으로 서명이 사라진다.**
- **`kid`는 신뢰 경계 밖의 힌트다 — 선택지를 좁힐 뿐 새 키 출처를 인가하지 않는다.**

## 용어 풀이

- **JWKS(JWK Set)** — 발급자가 공개키들을 `keys` 배열로 게시하는 표준 문서/엔드포인트.
- **JWK(JSON Web Key)** — 키 하나를 담은 JSON 객체. `kty`·`use`·`alg`·`kid`와 키 재료.
- **`kid`(Key ID)** — 여러 키 중 하나를 지목하는 이름표. 회전 시 옛/새 키 구분의 축.
- **`jwks_uri`** — discovery 문서가 가리키는 JWK Set의 URL. 반드시 `https`.
- **discovery** — `/.well-known/openid-configuration`에서 발급자 설정을 찾는 단계.
- **키 회전(Key Rotation)** — 발급자가 서명키를 주기적·유출 시 교체하는 것.
- **`n`·`e`** — RSA 공개키의 모듈러스와 지수. 이 둘로 공개키를 복원한다.
- **알고리즘 혼동 공격(alg confusion)** — 토큰의 `alg`를 믿게 해 `none`·`HS256`으로 서명을 우회하는 공격.
- **중간자 공격(MITM)** — 통신 경로에 끼어들어 응답을 바꿔치기하는 공격. 평문 JWKS 페치의 위협.
- **fail-closed** — 페치 실패·미지 `kid`면 통과가 아니라 거절로 떨어지는 설계.
- **JOSE** — JSON Object Signing and Encryption. JWT/JWS/JWK/JWA를 묶는 제품군.
- **TTL(Time To Live)** — 캐시가 유효한 시간. 회전 지연과 폐기 키 신뢰 사이의 맞바꿈.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **미지 `kid` 재페치에도 한도(throttle)가 필요하다.** "모르는 `kid`면 재페치" 규칙을 그대로 두면, 공격자가 매번 랜덤 `kid`를 단 토큰을 퍼부어 검증자가 발급자 JWKS를 무한히 두드리게 만들 수 있다(발급자 대상 DoS + 자기 DoS). 그래서 실무 구현은 재페치에 쿨다운·rate limit을 걸고, 재페치 후에도 없는 `kid`는 즉시 거절한다.
- **`alg`가 아니라 `kid`+발급자 메타로 알고리즘을 정하는 게 더 안전하다.** §5는 "서버가 알고리즘을 고정"하라고 하는데, 한 발 더 나가면 검증자는 고른 JWK의 `kty`/`alg`(발급자가 게시한 값)를 신뢰의 근거로 삼고 토큰 헤더의 `alg`는 아예 무시할 수 있다. 토큰이 주장하는 알고리즘을 판정에 태우지 않는 것이 alg confusion을 근본에서 없애는 방법이다.
- **JWKS는 폐기(revocation)를 즉시 반영하지 못한다.** 키를 JWK Set에서 빼도 검증자 캐시에 남아 있으면 TTL이 지나기 전까지 그 키로 서명된 토큰이 통과할 수 있다. 그래서 "즉시 무효화"가 필요한 경우엔 JWKS만으로 부족하고, 토큰을 짧게 만료시키거나(단기 토큰) 별도 폐기 목록(introspection·denylist)을 함께 둔다.
