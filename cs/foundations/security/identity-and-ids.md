# foundations/security/식별자와 신원 검증 — 이름은 바뀌고, ID는 남는다

> 복습은 개념 질문에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/tech/security/identity-and-ids.md` · 이관일 2026-09-16.\
> 본문 절들(§1~§5)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지). 특정 저장소 이름·프로젝트 결정 참조는 일반 예(`acme/core` 등)와 일반 원리로 일반화했고, GitHub는 실존 플랫폼 예로 둔다.\
> 「한눈에」의 비유·그림과 표는 **Claude가 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**핵심 주장** — 신원 검증은 사람이 읽는 **이름**이 아니라 불변인 **ID**로 해야 한다. 그리고 그 "ID"는 하나가 아니라 두 축이다 — 플랫폼이 부여한 **신원 ID**(누가)와 내용에서 계산된 **주소**(무엇).

---

## 한눈에 — 쉽게 말하면

회사 출입 통제가 **이름표가 아니라 사번**으로 도는 것을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
이름 (참조)                              불변 ID (신원)
+-----------------------------+        +-----------------------------+
| 개명하면 바뀐다               |        | 사번은 안 바뀐다              |
| 동명이인이 있다               |        | 사번은 겹치지 않는다          |
| 퇴사자 이름이 재사용될 수 있다  |        | 퇴사해도 그 사번은 재발급 안 됨 |
+-----------------------------+        +-----------------------------+
  사람이 읽기 위한 것                    기계가 판정하기 위한 것
```

**저장소 신원도 똑같은 구조다.** `acme/core`라는 이름은 사람을 위한 것이라 개명·삭제 후 재생성·조직 이전으로 바뀌고 재사용된다.\
플랫폼이 부여한 수치 ID(`repository_id`)는 바뀌지 않고 재사용되지도 않는다.\
실무 예: "이 배포 요청이 정말 우리 저장소에서 왔나"를 판정할 때, 이름이 맞아도 수치 ID가 다르면 재생성된 딴 저장소이므로 거절한다.

## 문제 — 이 개념이 답하려는 질문

출발점은 직관이다.

```text
직관: "결국 각 저장소는 깃 자체의 ID 로 분리되니,
       그 ID 로 검증하는 것이 최고의 식별 아닌가?"

이 직관은 방향이 정확히 맞다. 정밀하게 다듬으면 두 개의 서로 다른 ID 축이 나온다:
   ⑴ 플랫폼 수치 ID  — "누가" 의 축
   ⑵ 내용 주소       — "무엇" 의 축

그 두 축이 각각 무엇을 결박하는지가 이 문서의 본론이다.
```

아래 서머리는 §1 이름은 왜 신원이 아닌가 → §2 직관의 정밀화(두 축) → §3 두 축이 서는 자리 → §4 신원 다음의 인가, 의 순서로 분석한 것이다.

---

## 전체 흐름

```text
이름 = 참조 (바뀌고 재사용됨) → 검증 축이 될 수 없다 (§1)
        ↓
"깃의 ID" 를 정밀화하면 두 축 (§2)
   ⑴ 플랫폼 수치 ID (repository_id, owner_id)  = "누가"  신뢰뿌리: 토큰 서명
   ⑵ 내용 주소 (commit SHA, image digest)      = "무엇"  신뢰뿌리: 해시 수학
        ↓
두 축은 대체재가 아니라 상보재 — 서로 다른 대체 공격을 막는다
        ↓
검증 행렬에서 각 값이 어느 축·무엇을 막나 (§3)
        ↓
신원이 서도 권한은 별개 → 인가(allowlist 결박)가 마지막 층 (§4)
```

## 1. 이름은 참조이지 신원이 아니다

> 출처: 원고 §1

`acme/core`라는 이름은 사람을 위한 것이다 — 읽기 좋고, 부르기 좋고, URL에 들어간다.\
그런데 이름에는 신원 검증이 요구하는 성질이 하나 빠져 있다 — **불변성**이다. 이름은 바뀐다.

- **개명(rename)** — 저장소 이름을 바꾸면 옛 이름이 비워진다.
- **삭제 후 재생성** — `acme/core`를 지우고 누군가 같은 이름으로 다시 만들면, **이름은 같지만 완전히 다른 저장소**다.
- **조직 이전(transfer)** — 소유자가 바뀌어도 이름 경로가 재사용될 수 있다.

그래서 "이름이 `acme/core`인 저장소에서 온 요청만 통과"라는 규칙은, 정확히 말하면 *"지금 그 이름을 달고 있는 무언가에서 온 요청만 통과"*다.\
그 무언가가 어제의 그 저장소라는 보장이 없다.

> **이름 재사용 공격(name reuse attack)** — 신뢰받던 이름이 비워진 뒤 공격자가 같은 이름으로 새 대상을 만들어, 이름 기반 검증을 통과하는 공격.\
> 예: 회사가 쓰던 저장소를 지운 뒤 공격자가 같은 이름으로 저장소를 만들면, 이름만 보는 배포 게이트가 그것을 "우리 것"으로 받아들인다.

이것이 이름 재사용 공격의 자리이고, GitHub가 OIDC 보안 강화 문서에서 이름 claim 대신 수치 ID claim(`repository_id`·`repository_owner_id`) 사용을 권고하는 이유다([GitHub Docs — OIDC hardening](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect)).

## 2. 직관의 정밀화 — "깃의 ID"는 사실 두 축이다

> 출처: 원고 §2

*"깃 자체 ID로 검증한다"*는 직관을 뜯어보면, 서로 다른 질문에 답하는 두 종류의 ID가 나온다.

- **⑴ 플랫폼 수치 ID — "누가"의 축.**\
  `repository_id`(예: 1325924362)와 `repository_owner_id`는 플랫폼이 **생성 시점에 부여하는 불변 키**다.\
  이름이 바뀌어도, 조직이 이전돼도 이 숫자는 따라가고, 저장소가 삭제되면 그 숫자는 **영원히 재사용되지 않는다**.\
  엄밀히는 git의 개념이 아니라 호스팅 플랫폼의 데이터베이스 키다 — git 프로토콜 자체에는 "저장소 ID"가 없다.\
  그래서 이 축의 신뢰 뿌리는 git이 아니라 **플랫폼의 OIDC 토큰 서명**이다(토큰 안의 claim이므로, 토큰 서명 검증이 서야 이 값도 선다 — [`jwks.md`](jwks.md)).
- **⑵ 내용 주소 — "무엇"의 축.**\
  commit SHA와 컨테이너 이미지 digest는 **내용에서 계산되는 ID**다(git이 진짜로 소유한 식별 개념은 이쪽이다).\
  같은 내용이면 같은 값, 한 비트만 달라도 다른 값 — 부여받는 것이 아니라 계산되므로 위조하려면 해시를 깨야 한다([`sha256-and-digest.md`](sha256-and-digest.md)).\
  이 축은 "그 저장소가 맞는가"에는 답하지 못하지만 "그 코드·그 산출물이 맞는가"에는 수학적으로 답한다.

두 축은 대체재가 아니라 **상보재**다.

```text
수치 ID 만 있으면                        내용 주소 만 있으면
+-----------------------------+        +-----------------------------+
| 진짜 우리 저장소에서 왔지만    |        | 올바른 형식의 산출물이지만     |
| 엉뚱한 코드를 못 거른다        |        | 남이 만든 것을 못 거른다       |
+-----------------------------+        +-----------------------------+
  신원(누가)과 내용(무엇)은 서로 다른 대체 공격을 막는다 → 둘 다 필요
```

## 3. 두 축이 서는 자리 — 검증 행렬

> 출처: 원고 §3

배포 요청 하나가 통과하는 검증을 축으로 나누면 이렇게 배치된다.

| 검증 값 | 축 | 막는 것 |
|---|---|---|
| `repository` + **`repository_id`** | 신원(플랫폼 ID) | 이름 재사용 — 이름이 맞아도 수치 ID가 다르면 다른 저장소다 |
| **`repository_owner_id`** | 신원(플랫폼 ID) | 조직 이름 재사용 |
| `job_workflow_ref` | 신원(경로 결박) | 같은 저장소의 **다른 워크플로**가 배포 요청을 흉내내는 것 |
| commit SHA (manifest) | 내용 | 어느 코드에서 나온 요청인지의 감사 추적 |
| **image digest**(`sha256:…`) | 내용 | 태그 바꿔치기 — `latest`는 언제든 바뀌지만 digest는 그 빌드 산출물 하나에 고정된다 |

이름과 수치 ID를 **둘 다** 검사하는 이유도 여기서 나온다 — 판정은 불변인 ID가 하고, 이름은 사람이 거절 기록을 읽을 때를 위해 남는다.\
**검증은 기계의 축(불변 ID)으로, 표시와 감사는 사람의 축(이름)으로.**

## 4. 신원 다음의 층 — 신원이 확인돼도 권한은 별개다

> 출처: 원고 §4

수치 ID 검증이 완벽해도 남는 질문이 있다 — *확인된 그 저장소가, 요청한 그 대상을 배포할 자격이 있는가?*\
배포 대상이 여럿(예: 코어·정산·원장·게이트웨이)이 되면 "우리 조직의 등재된 저장소다"까지만 확인하는 것은 부족하다 — 정산 저장소의 워크플로가 코어를 배포하겠다고 요청하면, 신원은 진짜지만 권한이 없다.

그래서 allowlist 확장의 핵심은 목록이 아니라 **결박**이다.

```text
allowlist 항목 = "이 수치 ID 의 저장소  →  이 대상 하나"

신원 검증(§2 ⑴축) 통과
        ↓
그 신원에 묶인 허용 대상  ==  manifest 의 대상  ?
        ↓ 일치해야
배포가 선다
```

인증(authentication — 누구인가)과 인가(authorization — 무엇을 해도 되는가)가 다른 층이라는 일반 원리의 배포판이다.

## 5. 요약 — 한 문장씩

> 출처: 원고 §5

- 이름은 **참조**다 — 사람이 읽으라고 있고, 바뀌고, 재사용된다. 검증의 축이 될 수 없다.
- 플랫폼 수치 ID는 **신원**이다 — 불변·비재사용이라 "누가"를 결박한다. 신뢰 뿌리는 플랫폼의 토큰 서명이다.
- 내용 주소(SHA·digest)는 **내용**이다 — 계산되는 값이라 "무엇"을 결박한다. 신뢰 뿌리는 해시의 수학이다.
- 신원이 서면 그 다음은 **인가**다 — 확인된 신원 ↔ 허용된 대상의 결박(allowlist)이 마지막 층을 닫는다.

처음의 직관 — *최고의 식별은 결국 ID다* — 는 그래서 맞다.\
다만 그 "ID"는 하나가 아니라, 플랫폼이 부여한 신원 ID와 내용에서 계산된 주소라는 **두 개의 불변 축**이고, 검증 행렬은 그 둘을 겹쳐 세운 것이다.

---

## 핵심 문장

- **이름은 참조이지 신원이 아니다 — 개명·재생성·이전으로 바뀌고 재사용되기 때문이다.**
- **"깃의 ID"는 하나가 아니라 두 축이다 — 플랫폼 수치 ID(누가)와 내용 주소(무엇).**
- **수치 ID의 신뢰 뿌리는 토큰 서명, 내용 주소의 신뢰 뿌리는 해시 수학이다.**
- **두 축은 상보재다 — 신원만 보면 엉뚱한 코드를, 내용만 보면 남이 만든 것을 못 거른다.**
- **검증은 불변 ID로, 표시·감사는 사람이 읽는 이름으로 한다.**
- **신원이 확인돼도 권한은 별개다 — 인증 다음에 "그 신원이 이 대상을 배포할 자격이 있나"라는 인가가 온다.**

## 용어 풀이

- **식별자(Identifier)** — 대상을 가리키는 값. 이름(참조)과 ID(신원)로 성격이 갈린다.
- **이름 재사용 공격(Name Reuse Attack)** — 비워진 신뢰받던 이름을 공격자가 차지해 이름 기반 검증을 뚫는 공격.
- **플랫폼 수치 ID** — 호스팅 플랫폼이 생성 시점에 부여하는 불변·비재사용 키(`repository_id` 등).
- **내용 주소(Content Address)** — 내용에서 계산되는 식별자(commit SHA, image digest). 위조하려면 해시를 깨야 한다.
- **commit SHA** — git 커밋 내용의 해시. 어느 코드인지를 내용으로 지목한다.
- **image digest** — 컨테이너 이미지 내용의 해시(`sha256:…`). 가변 태그와 달리 산출물 하나에 고정된다.
- **인증(Authentication)** — "누구인가"의 판정.
- **인가(Authorization)** — "무엇을 해도 되나"의 판정. 인증과 다른 층이다.
- **allowlist 결박(binding)** — "이 신원 → 이 대상 하나"로 허용을 묶는 것. 인가의 마지막 층.
- **신뢰 뿌리(Root of Trust)** — 어떤 검증이 결국 무엇에 기대는가. 수치 ID는 토큰 서명, 내용 주소는 해시 수학.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **이 "이름 vs 불변 ID" 구분은 보안 밖에서도 같은 원리다.** 데이터베이스에서 자연키(사람 이름·이메일) 대신 대리키(surrogate key, 자동증가 ID·UUID)를 쓰는 이유, 파일 시스템이 경로가 아니라 inode 번호로 파일을 식별하는 이유가 모두 같다 — 사람이 읽는 값은 바뀌지만 시스템 판정은 불변 식별자에 걸어야 한다.
- **내용 주소의 극단이 content-addressable storage다.** git·컨테이너 레지스트리·IPFS는 "주소 = 내용의 해시"로 저장한다. 주소를 알면 내용의 무결성이 자동으로 검증되고(주소가 곧 해시니까), 같은 내용은 자동으로 중복 제거된다. §2 ⑵축의 "계산되는 ID"가 저장 시스템 전체의 조직 원리가 된 형태다.
- **수치 ID의 신뢰 뿌리가 토큰 서명이라는 점의 함의.** §2가 "수치 ID는 git이 아니라 플랫폼이 보증한다"고 한 것은 중요한 한계다 — 플랫폼의 서명 검증(JWKS 페치·알고리즘 고정)이 무너지면 수치 ID도 함께 무너진다. 반면 내용 주소는 플랫폼이 아니라 해시 함수 자체에 기대므로, 신뢰의 뿌리가 서로 독립이다. 두 축을 겹쳐 쓰면 한 뿌리가 흔들려도 다른 축이 남는 이유가 이것이다.
