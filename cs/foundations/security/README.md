# cs/foundations/security — 보안 프리미티브 묶음

한 프로젝트의 배포 인증 학습 노트에서 나온 **보안 프리미티브 컬렉션**을, 프로젝트 밖에서도 읽히도록 cs 스타일로 이관한 것.\
원고 문체 유지(오탈자·끊긴 문장만 교정), 프로젝트 고유명사(사내 ADR·게이트·코드 경로)는 "누구나 겪는 형태"로 일반화했다 — 각 파일이 절마다 원고 출처를 명기한다.\
HMAC·JWKS·OIDC·SHA-256·JWT·RFC 번호는 표준이라 그대로 두었다.

- 갈래: **훈련(cs/)** — 나중에 문제로 풀 개념 카드. 다만 컬렉션이라 3파일(질문·서머리·정답) 대신 **개념당 파일 하나**(서머리 톤)로 구조를 보존했다.
- 원고에 없던 지식은 각 파일 맨 끝 `## [Claude 추가]`에만 두어, 복습 시 원고와 섞이지 않게 했다.
- 목표 배치: `cs/foundations/security/`.

## 읽는 순서 (의존 순)

아래로 갈수록 앞 개념을 딛는다. 해시가 모든 것의 바닥이고, 신원·롤아웃이 맨 위다.

|---|---|---|---|---|
| 1 | [sha256-and-digest.md](sha256-and-digest.md) | 해시·digest | 임의 길이를 고정 길이 지문으로 요약 — 세 저항성 위에 무결성·서명·중복 판정이 선다 | FIPS 180-4 · SHAttered |
| 2 | [hmac.md](hmac.md) | 대칭 MAC | 공유 비밀 하나로 진위+무결성 증명 — 이중 해시·상수시간 비교·재전송 한계 | RFC 2104 · FIPS 198-1 |
| 3 | [oidc.md](oidc.md) | 비대칭 신원 토큰 | "키를 아는 자" 너머 "누가 보냈나"를 제3자 발급 ID 토큰으로 — claim 검증은 행렬 | OIDC Core · RFC 7519 |

| 5 | [identity-and-ids.md](identity-and-ids.md) | 식별자 두 축 | 이름은 바뀌고 ID는 남는다 — 플랫폼 수치 ID(누가)와 내용 주소(무엇) | GitHub OIDC hardening |
| 6 | [audit-enforce-rollout.md](audit-enforce-rollout.md) | 인가 롤아웃 전략 | 이미 도는 시스템에 인가를 무중단으로 켜기 — audit(관측) → enforce(강제) | dark launch(일반) |

## 어떻게 엮이나

```text
sha256/digest (해시)  ── 바닥
   │  · body/이미지를 지문으로 고정
   │  · 서명은 본문이 아니라 digest 에 건다
   ▼
hmac (대칭 서명)       "위조되지 않았나 + 안 바뀌었나"
   │  한계: freshness(재전송)를 못 막음
   │  한계: "키를 아는 자" 까지만 (누구인지 모름)
   ▼
oidc (비대칭 신원)     "누가 보냈나" — HMAC 과 AND 로 묶음
   │  검증하려면 발급자 공개키가 필요
   ▼
jwks (공개키 조달)     "그 공개키를 어디서·어떻게 얻나" + 회전
   │  claim 중 저장소 신원을 어떻게 믿나
   ▼
identity-and-ids      "이름이 아니라 불변 ID 로" (플랫폼 ID + 내용 주소)
   ▼
audit → enforce       그 인가를 서비스 안 끊고 켜는 배포 전략
```

## 이관 시 손대지 않은 것 (보존 통찰)

- **각 프리미티브의 "한계" 서술** — HMAC이 재전송을 못 막는다, JWKS가 즉시 폐기를 반영 못 한다, 운영 승인 결박은 플랫폼 요금제 문제로 남는다 등. 원고가 자기 한계를 정직하게 적은 문장은 결론보다 중요해 그대로 옮겼다.
- **`[구현 검증]` 이연 표기** — 문서만으로 판정 불가한 항목(운영 승인 결박 등)에 붙은 태그를 지우지 않고 유지했다.
- **"조용히 샌다"는 서사** — `sub` 문자열 대조·이름 재사용·silent failure가 각 문서의 핵심 서사다.
