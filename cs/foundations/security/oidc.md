# foundations/security/OIDC와 claim·jti — "이 요청이 진짜 그 파이프라인에서 왔나"

> 복습은 개념 질문에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/tech/security/oidc.md` · 이관일 2026-09-16.\
> 본문 절들(§1~§8)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지). 특정 프로젝트의 배포 검증 결정(ADR·사내 코드) 참조는 "OIDC로 발신 파이프라인을 검증하는 시스템 일반"으로 일반화했고, GitHub Actions는 실존하는 발급자 예로 그대로 둔다.\
> 「한눈에」의 비유·그림과 세로 흐름도는 **Claude가 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**OIDC**(OpenID Connect) = OAuth 2.0(인가) 위에 얹은 **인증** 계층. 발급자가 서명한 **ID 토큰**으로 "요청 주체가 누구인가"를 표준화된 형태로 증명한다.\
**claim** = ID 토큰(JWT) payload 안의 키-값 한 쌍(`iss`·`sub`·`aud`·`exp` 등).

## 한눈에 — 쉽게 말하면

입구를 지키는 **두 종류의 문**을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
문 A: "비밀번호 아는 사람만 통과"       문 B: "국가 발급 신분증 확인"
+-----------------------------+      +-----------------------------+
| = HMAC 서명                  |      | = OIDC ID 토큰               |
| 비밀번호(키)를 아는 자면       |      | 제3자(발급기관)가 서명한       |
| 누구든 통과                  |      | 신분증을 제시                 |
| "누가"는 구분 못 함           |      | 이름·생일·발급처가 각각 칸으로  |
|                             |      | 적혀 있어 한 칸씩 대조         |
+-----------------------------+      +-----------------------------+
  → "키를 아는 자"까지만 증명           → "우리 저장소의, 우리 워크플로가,
                                        허용된 브랜치에서"까지 증명
```

**신분증 검사도 똑같은 구조다.** 신분증은 한 값이 아니라 여러 칸(이름·생일·발급기관·유효기간)의 표이고, 위조를 막으려면 한 칸이 아니라 모든 칸을 대조해야 한다.\
실무 예: CI 파이프라인이 배포 API를 부를 때, HMAC은 "위조되지 않았다"를, OIDC ID 토큰은 "정말 우리 저장소의 배포 워크플로가 보냈다"를 각각 증명하고 **둘을 AND로** 묶는다.\
쉽게 말하면 — 서명(HMAC)은 질문의 절반만 답하고, OIDC가 나머지 절반을 답하되, 그 답이 하나의 값이 아니라 **여러 claim의 행렬**로만 성립한다는 것이 이 글의 골자다.

## 문제 — 이 개념이 답하려는 질문

배포 명령을 받는 쪽이 *"이 요청이 정말 그 CI 파이프라인에서 왔나"*를 어떻게 기계적으로 증명하느냐다.

```text
HMAC 서명이 증명하는 것: "이 요청을 만든 자가 비밀 키를 안다"  ← 딱 하나
   문제: "키를 아는 자" 가 알고 싶은 것보다 넓다
     · 여러 워크플로가 키를 공유하면 어느 워크플로인지 구분 못 함
     · 키가 한 번 새면 그 뒤 모든 요청이 형식상 진짜가 됨

실제로 던지고 싶은 질문:
   "우리 저장소의, 우리 배포 워크플로가, 허용된 브랜치에서 실행되고 있는가?"
     → 요청자가 자기 신원을 증명 가능한 형태로 실어 보내야 하고
     → 그 신원을 발급하는 제3자가 있어야 한다   ← 그 제3자가 OIDC 발급자
```

아래 서머리는 §2 OIDC란 무엇인가 → §3 JWT·claim → §4 왜 검증이 "행렬"인가 → §5 `sub` 문자열 대조의 함정 → §6 재전송과 jti → §8 종합, 의 순서로 이 문제를 분석한 것이다.

## 전체 흐름

```text
HMAC = "키를 아는 자" 까지만 증명 (§1)
        ↓  AND 로 묶는다
OIDC = "누가 보냈나" 를 제3자 발급 ID 토큰으로 증명 (§2)
        ↓
ID 토큰의 물리 형식 = JWT (header.payload.signature), claim = payload 의 키-값 (§3)
        ↓
검증 = 먼저 서명 확인 → 그 다음 claim 을 각각 대조 (행렬) (§4)
        ├─ iss · aud · repository(+id) · ref · job_workflow_ref · exp/nbf/iat
        └─ 한 칸이 빠지면 하나의 우회로가 열린다 (전 칸 AND)
        ↓
함정: sub 문자열 통째 대조 = 형식이 바뀌면 조용히 무너진다 (§5)
        ↓
진위를 통과한 토큰도 재전송은 못 막음 → jti 일회성 소비 (§6)
```

## 1. 문제 — 서명은 "키를 아는 자"까지만 증명한다

> 출처: 원고 §1

배포 API가 외부에서 요청을 받을 때 먼저 필요한 것은 진위 확인이고, 흔한 답이 HMAC 서명이다([`hmac.md`](hmac.md)).\
이것이 증명하는 것은 정확히 하나다 — **이 요청을 만든 자가 그 비밀 키를 알고 있다.**\
키가 새지 않는 한 위조는 불가능하다.

문제는 "키를 아는 자"가 우리가 알고 싶은 것보다 넓다는 데 있다.\
같은 키를 여러 워크플로가 공유하면 어느 워크플로가 보냈는지 서명은 구분하지 못하고, 키가 한 번 유출되면 그 뒤 모든 요청이 형식상 진짜가 된다.\
우리가 실제로 던지고 싶은 질문은 *"키를 아는가"*가 아니라 *"우리 저장소의, 우리 배포 워크플로가, 허용된 브랜치에서 실행되고 있는가"*다.

HMAC은 여기에 답할 수 없다 — 답하려면 **요청자가 자기 신원을 증명 가능한 형태로 실어 보내야** 하고, 그 신원을 발급하는 제3자가 있어야 한다. 그 제3자가 OIDC 발급자다.\
그래서 둘을 버리지 않고 **AND로 묶는다** — HMAC은 "위조되지 않았다"를, OIDC는 "누가 보냈다"를 각각 증명하고, 한쪽만으로는 배포를 열지 않는다.

## 2. OIDC — OAuth 2.0(인가) 위에 얹은 인증 계층

> 출처: 원고 §2

OIDC를 이해하려면 그 아래에 깔린 OAuth 2.0부터 갈라 봐야 한다. 둘은 자주 섞여 불리지만 답하는 질문이 다르다.

```text
OAuth 2.0 = 인가(authorization)             OIDC = 인증(authentication)
+-----------------------------+           +-----------------------------+
| 산출물: access token         |           | 산출물: ID 토큰               |
| 답: "이 앱이 무엇을 해도 되나" |           | 답: "요청 주체가 누구인가"      |
| 예: 내 사진에 읽기 접근 위임   |           | 예: 어느 저장소·어느 워크플로   |
| 접근 권한을 위임하는 도구      |           | 신원을 표준 형태로 알려 줌      |
+-----------------------------+           +-----------------------------+
   "무엇을 해도 되나"                        "너는 누구냐"  ← OIDC 가 얹는 것
```

- **OAuth 2.0은 인가의 프레임워크다.** RFC 6749는 자신을 "제3자 애플리케이션이 HTTP 서비스에 제한적으로 접근하게 하는 프레임워크"로 규정한다([RFC 6749](https://www.rfc-editor.org/rfc/rfc6749)). 핵심 산출물은 access token이고, 답하는 것은 *"이 앱이 무엇을 할 수 있는가"*다.
- **OIDC는 그 위에 인증 계층을 얹는다.** OpenID Connect Core 1.0은 스스로를 "OAuth 2.0 위의 단순한 신원 계층(a simple identity layer)"이라 정의한다([OIDC Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)). 추가되는 산출물이 **ID 토큰**이고, 답하는 것은 *"요청 주체가 누구인가"*다.

CI 파이프라인(예: GitHub Actions)은 인가를 위임받으려는 게 아니라 **자기 신원을 증명**하려는 것이다.\
그래서 쓰는 것은 access token이 아니라 OIDC **ID 토큰**이고, 그 안의 claim이 "어느 저장소·어느 워크플로"인지를 말해 준다.\
이 토큰은 발급자(issuer)가 서명해 내주며, 발급자는 GitHub의 경우 `https://token.actions.githubusercontent.com`라는 고정 URL이다(§7).

## 3. JWT — claim은 서명된 payload의 키-값이다

> 출처: 원고 §3

ID 토큰의 물리적 형식은 **JWT**(JSON Web Token)다 — 점(`.`)으로 이어진 세 부분 `header.payload.signature`.\
각 부분은 base64url로 인코딩된 JSON(서명은 바이트열)이고, 겉보기엔 암호문 같지만 **header와 payload는 암호화가 아니라 인코딩일 뿐이라 누구나 디코딩해 읽을 수 있다.**\
JWT가 지키는 것은 기밀성이 아니라 **무결성**이다 — 서명이 "이 내용이 발급 후 바뀌지 않았고 그 발급자가 서명했다"를 보장한다.

```text
[header]    eyJhbGciOiJSUzI1Ni...      = {"alg":"RS256","typ":"JWT"}
[payload]  .eyJpc3MiOiJodHRwcy...       = {"iss":"https://token...","sub":"repo:...", ...}
[sig]      .NHVaYe26MbtOYhSKko...       = payload 를 발급자 키로 서명한 값

  · header/payload = 인코딩일 뿐 → 누구나 읽음 (기밀성 아님)
  · signature      = 발급자 개인키 서명 → 무결성 + 발급자 진위
```

여기서 **claim이란 payload 안의 키-값 한 쌍**이다.\
`iss`(발급자)·`sub`(주체)·`aud`(수신자)·`exp`(만료) 같은 이름은 각각 하나의 claim이고, RFC 7519가 **등록 claim**(registered claim)으로 이름과 의미를 표준화해 둔 것들이다([RFC 7519 §4.1](https://www.rfc-editor.org/rfc/rfc7519#section-4.1)).\
발급자는 여기에 `repository`·`ref` 같은 자기 도메인의 claim을 더 얹는다(§7).

검증의 출발점은 딱 하나다 — **먼저 서명을 확인한다.**\
서명이 발급자의 공개 키로 검증되지 않으면 payload의 어떤 값도 신뢰할 수 없다(그 공개 키를 어디서 얻나는 [`jwks.md`](jwks.md)).\
서명이 통과한 다음에야 payload의 claim들을 하나씩 따져 볼 수 있고, 다음 절이 그 "하나씩"이 왜 여러 칸의 표가 되는지를 다룬다.

## 4. claim 검증이 "행렬"인 이유 — 한 칸이 하나의 침입 경로를 닫는다

> 출처: 원고 §4

서명이 유효한 토큰은 "발급자가 진짜로 발급했다"까지만 말한다.\
그런데 그 발급자(`token.actions.githubusercontent.com`)는 **GitHub의 모든 저장소, 모든 워크플로에** 토큰을 발급한다.\
즉 서명만 보면 *아무 저장소의 아무 워크플로*가 발급받은 토큰도 형식상 유효하다.\
그래서 "우리 것인가"는 서명 하나가 아니라 payload의 여러 claim을 **각각** 대조해야 성립하고, 그 대조가 표(행렬)의 모양을 띤다.

| claim | 무엇을 증명하나 | 빠지면 뚫리는 것 |
|---|---|---|
| **`iss`**(발급자) | 토큰을 서명한 신뢰 도메인 | 다른 신뢰 도메인이 발급한 유효 토큰을 받음 |
| **`aud`**(수신자) | 이 토큰이 향하는 대상 | 다른 목적으로 발급된 토큰이 배포에 재사용됨 |
| **`repository`+`repository_id`** | 어느 저장소가 발급받았나 | 이름 재사용 — 이름만 보면 재생성된 딴 저장소가 통과 |
| **`ref`·`ref_type`** | 어느 브랜치·태그에서 실행됐나 | 임의 브랜치·태그의 워크플로가 배포를 발행 |
| **`job_workflow_ref`** | 어느 워크플로 파일이 정의했나 | 같은 저장소의 다른 워크플로(테스트용 등)가 배포를 엶 |
| **`exp`·`nbf`·`iat`**(시간) | 유효 창·발급 시각 | 오래된 토큰이 계속 유효 (§6 jti와 짝) |

- **`iss`** — OIDC Core는 "`iss`가 반드시 예상 발급자와 일치해야 한다"고 못박는다([OIDC Core §3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)).
- **`aud`** — **배포 API 전용 audience**를 요구하고 플랫폼 기본값을 쓰지 않는 것이 핵심이다. OIDC Core도 "신뢰하지 않는 audience가 있으면 거절해야 한다"고 규정한다(§3.1.3.7).
- **저장소** — 이름만 보면 안 되고 **수치 ID를 함께** 본다. 이름은 이전·삭제 후 재생성으로 재사용되지만 수치 ID는 재사용되지 않기 때문이다(§5·§7, 자세히는 [`identity-and-ids.md`](identity-and-ids.md)).
- **`ref`** — 배포 가능한 ref를 허용목록으로 좁힌다(기본은 기본 브랜치 하나).
- **`job_workflow_ref`** — 배포 워크플로 하나로 고정하지 않으면 이웃 워크플로가 토큰을 받아 배포를 연다.

빠진 칸 하나가 곧 하나의 우회로다 — `aud`를 안 보면 재사용이, `job_workflow_ref`를 안 보면 이웃 워크플로가, `repository_id`를 안 보면 이름 재사용이 뚫린다.\
그래서 검증은 "이 중 몇 개"가 아니라 **전 칸 AND**이고, 한 칸이라도 어긋나면 적용하지 않고 거절을 기록한다.

## 5. sub 문자열 대조가 위험한 이유 — 합성 문자열은 형식이 바뀌면 조용히 무너진다

> 출처: 원고 §5

앞의 claim들을 한 줄로 요약해 담은 것처럼 보이는 값이 `sub`(subject)다. GitHub Actions의 `sub`는 예컨대 이런 모양이다.

```text
sub = "repo:octo-org/octo-repo:environment:prod"        ← 꼬리가 environment
sub = "repo:my-org/my-repo:ref:refs/heads/main"         ← 꼬리가 ref
       └────────┬────────┘└──────┬──────┘
       저장소               무엇을 트리거했느냐에 따라 꼬리가 달라진다
```

한눈에 저장소·ref·environment가 다 들어 있어 보이니 "이 문자열이 우리 것과 같은가"로 검증하고 싶어진다. 이것이 함정이다. 이유는 둘이다.

- **첫째, `sub`는 여러 조각을 이어 붙인 합성 문자열이라 형식이 조용히 바뀐다.**\
  전/후 매칭 방식 모두 조용히 샌다.

```text
정확한 전체 문자열 매칭                 프리픽스 매칭 (repo:my-org/my-repo:*)
+-----------------------------+      +-----------------------------+
| 형식이 바뀌면 우리 것도       |      | 그 저장소의 아무 브랜치·        |
| 조용히 거절                  |      | 아무 environment·PR 까지      |
| → 가용성 사고                |      | 와일드카드에 걸려 통과         |
|                             |      | → 보안 사고                  |
+-----------------------------+      +-----------------------------+
  어느 쪽으로 새든 "조용히" 새는 게 핵심 — 문자열 하나가 여러 축을 뭉쳐 담아서다
```

- **둘째, 발급자가 `sub`의 형식 자체를 바꾸기도 한다.** GitHub 공식 문서에 따르면 **2026년 7월 15일 이후 생성된 저장소는 소유자·저장소의 수치 ID를 포함하는 불변(immutable) 형식**을 쓴다([GitHub OIDC 문서](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect)). 즉 `sub`의 문면은 시간에 따라 움직이는 대상이고, 통째로 대조하는 코드는 그 변화를 만나는 순간 깨진다.

바른 길은 §4의 결론과 같다 — **`sub`를 대조 대상이 아니라 파생값으로 보고, 그 안에 뭉쳐 있는 구성 요소(`repository_id`·`ref`·`job_workflow_ref` 등)를 각각 별도 claim으로 검증한다.**\
각 축을 따로 보면 한 축의 형식이 바뀌어도 판정이 조용히 무너지지 않는다.

## 6. jti — 진위를 통과한 토큰의 재전송을 막는 축

> 출처: 원고 §6

여기까지의 검증을 다 통과한 토큰도 아직 막지 못한 공격이 하나 있다 — **재전송**(replay)이다.\
유효한 토큰을 중간에서 가로채거나 로그에서 주워, 만료 전에 **그대로 다시** 보내는 것이다.\
서명도 claim도 전부 진짜이므로 §4·§5의 어떤 칸도 이걸 잡지 못한다 — 진위 검증과 재전송 방어는 다른 축이다.

그 다른 축을 담당하는 claim이 **`jti`**(JWT ID)다.\
RFC 7519는 이를 "JWT의 고유 식별자"로 정의하며, 값은 **다른 토큰에 우연히 같은 값이 배정될 확률이 무시할 만하도록** 발급되어야 하고, 명시적으로 "`jti` claim은 JWT가 재전송되는 것을 막는 데 쓸 수 있다"고 적는다([RFC 7519 §4.1.7](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.7)).

```text
스펙이 주는 것: 고유한 이름표(jti)까지
받는 쪽이 해야 할 것: 일회성 소비
   부작용을 일으키기 전에 그 jti 를 내구적으로 선점
        ↓
   이미 본 jti 가 다시 오면 → 거절
        ↓
   그래야 비로소 재전송이 막힌다
```

다만 스펙이 주는 것은 *고유한 이름표*까지이고, "한 번만 쓰이게 하는" 것은 받는 쪽의 몫이다.\
이 구조는 흔한 **멱등 규약**과 정확히 같다 — 같은 요청이 두 번 오면 두 번 실행하지 않고 최초 결과를 재반환한다.\
배포 채널은 요청의 요청 ID와 토큰의 `jti`를 **부작용 전에 함께 선점**함으로써 같은 규약을 적용한다.\
*"토큰 재사용 = 재전송"*이라는 한 문장이 시간 claim(`exp`)과 `jti`를 한 묶음으로 묶는 이유다 — `exp`는 창을 좁히고, `jti`는 그 창 안의 중복을 없앤다.

## 7. 발급자가 주는 claim — 이름이 아니라 수치 ID까지 온다

> 출처: 원고 §7 (GitHub Actions OIDC를 실존 예로 든 것)

앞 절들의 claim이 상상이 아니라 실제로 토큰에 온다는 것을 확인해 두면, §8의 검증 행렬이 무엇 위에 서는지가 분명해진다.\
GitHub Actions OIDC ID 토큰의 발급자는 `https://token.actions.githubusercontent.com` 하나이고, payload에는 다음 claim이 실린다([GitHub OIDC 문서](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect)).

- **표준(등록) claim** — `iss`·`sub`·`aud`·`exp`·`nbf`·`iat`·`jti`. 앞 절들이 다룬 그대로.
- **저장소 신원** — `repository`(이름)·`repository_id`(**수치 ID**)·`repository_owner`·`repository_owner_id`·`repository_visibility`. 이름과 수치 ID가 **둘 다** 온다는 점이 §5의 "이름 재사용" 방어를 실제로 가능하게 한다.
- **실행 맥락** — `ref`·`ref_type`·`sha`·`workflow`·`job_workflow_ref`·`event_name`·`head_ref`·`base_ref`·`run_id`·`run_number`·`run_attempt`.
- **행위자·환경** — `actor`·`actor_id`·`environment`·`runner_environment`.

검증에 쓰이는 것은 이 전부가 아니라 §8이 고른 칸들이다 — claim이 많다는 것과 그중 무엇을 신뢰 판정에 태우느냐는 별개다.\
특히 `environment` claim은 존재하지만, 그것이 운영 승인의 증거로 실제로 서는지는 다음 절이 짚는 별도 문제다.

## 8. 종합 — 검증 행렬과 아직 서지 않은 운영 승인 결박

> 출처: 원고 §8 (프로젝트 고유 잔여 항목 → 일반 한계로 일반화)

위 개념을 배포 신원 검증에 그대로 적용하면 **claim 검증 행렬**이 나오고, 형태는 §4~§6이 설명한 그대로다.

```text
iss              → 하나로 고정
aud              → 우리 배포 API 전용
저장소           → repository + repository_id (수치 ID)
ref              → 허용목록
job_workflow_ref → 배포 워크플로 하나
exp·nbf·iat      → 유효 창
jti              → 부작용 전 선점
sub              → 대조하지 않는다 (파생값, §5)

HMAC AND OIDC — 한 칸이라도 불일치면 적용하지 않고 거절을 기록 (무예외)
```

다만 한 칸은 아직 서지 않을 수 있다 — **운영 승인 결박**이다.\
운영 모드 배포를 사람의 승인 뒤에만 열려면 *"승인 뒤에만 발급되는 증거"*(보호된 environment의 secret 또는 그 environment로 발급된 토큰)가 요청에 결박되어 있어야 한다.\
문제는 그 결박이 **플랫폼에서 실제로 서는지를 문서만으로는 판정할 수 없다**는 것이다 — 예컨대 비공개 저장소에서 environment 보호 규칙·승인 게이트가 요금제상 걸리는지가 확인되지 않는 식이다.\
그런 항목은 `[구현 검증]`으로 이연해 대장에 등재하고, **판정 전까지 "운영 승인"은 기계가 보증하는 값이 아니라 「자기 신고」로 읽으며 그 사실을 배포 이력에 남긴다.** *(원고의 이연 표기 유지 — [구현 검증])*

정리하면 검증이 지금 기계적으로 보증하는 경계는 *"우리 저장소의, 우리 배포 워크플로가, 허용된 ref에서, 재전송 없이 보냈는가"*까지다 — 문제 절이 던진 질문의 답이 여기까지 왔다.\
그 위에 "사람이 승인했는가"를 얹는 마지막 칸은 개념이 아니라 플랫폼 요금제의 문제로 남을 수 있고, **그 한계를 감추지 않고 이력에 적어 두는 것이 정직한 상태다.**

## 핵심 문장

- **HMAC은 "키를 아는 자"까지만, OIDC ID 토큰은 "누가 보냈나"를 증명한다 — 둘을 AND로 묶는다.**
- **OAuth 2.0은 인가(무엇을 해도 되나), OIDC는 인증(너는 누구냐)이다.**
- **JWT는 기밀성이 아니라 무결성을 지킨다 — payload는 누구나 읽을 수 있고, 서명이 발급 후 불변임을 보장한다.**
- **claim 검증은 "몇 개"가 아니라 전 칸 AND다 — 빠진 칸 하나가 곧 하나의 우회로다.**
- **`sub` 같은 합성 문자열을 통째로 대조하면 형식 변화에 조용히 무너진다 — 구성 요소를 각각 별도 claim으로 본다.**
- **진위를 통과한 토큰도 재전송은 못 막는다 — `jti` 일회성 소비가 그 별도 축이다.**

## 용어 풀이

- **OIDC(OpenID Connect)** — OAuth 2.0 위에 얹은 인증 계층. ID 토큰으로 "누구인가"를 표준화한다.
- **OAuth 2.0** — 인가 프레임워크. access token으로 "무엇을 해도 되나"를 위임한다.
- **인증(Authentication) / 인가(Authorization)** — "너는 누구냐" vs "무엇을 해도 되나". 다른 층이다.
- **ID 토큰** — OIDC가 발급하는, 주체 신원을 담은 서명된 토큰(JWT 형식).
- **JWT(JSON Web Token)** — `header.payload.signature` 세 부분의 토큰. payload는 인코딩일 뿐(기밀성 아님).
- **claim** — JWT payload 안의 키-값 한 쌍. `iss`·`sub`·`aud`·`exp` 등.
- **등록 claim(Registered Claim)** — RFC 7519가 이름·의미를 표준화한 claim들.
- **`iss`/`aud`/`sub`** — 발급자 / 수신 대상 / 주체.
- **`jti`(JWT ID)** — 토큰 고유 식별자. 일회성 소비로 재전송을 막는 데 쓴다.
- **`job_workflow_ref`** — 이 잡을 정의한 워크플로 파일. 이웃 워크플로 방어의 축.
- **RS256** — RSA 개인키 서명 + SHA-256. 비대칭 서명 알고리즘.
- **audience 고정** — 우리 전용 `aud`를 요구해 다른 목적 토큰의 재사용을 막는 것.
- **[구현 검증] 이연** — 문서만으로 판정 불가한 항목을 태그로 표시해 대장에 등재하고 뒤로 미루는 것.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **OIDC 배포 인증은 "장기 시크릿 없애기(secretless)"의 핵심 수단이다.** 예전엔 클라우드 배포 권한을 CI에 넣으려고 장기 액세스 키를 저장소 시크릿에 박아 두었는데, 그 키가 새면 끝이었다. OIDC ID 토큰은 매 실행마다 발급되고 수 분 내 만료되는 단기 증명이라, 새어도 창이 짧다. AWS/GCP/Azure의 "OIDC federation"이 이 흐름이고, HMAC 공유 키와의 AND 구성은 그 위에 추가 방어선을 하나 더 얹은 것이다.
- **`aud`를 왜 그렇게 강조하나 — confused deputy.** audience를 고정하지 않으면, 다른 서비스용으로 발급된 유효한 토큰을 공격자가 배포 API에 들이미는 "혼동된 대리인(confused deputy)" 공격이 가능하다. `aud`는 "이 토큰은 오직 이 대상에게만 유효"라고 못박아 그 재사용을 끊는다.
- **claim 검증은 "allowlist(전 칸 AND)"이지 "denylist"가 아니다.** 나쁜 값을 하나씩 거르는 방식(denylist)은 새 우회로가 계속 생긴다. 반대로 "이 정확한 저장소·워크플로·ref만 통과"로 좁히면(allowlist), 명시적으로 허용한 것 외에는 전부 자동으로 막힌다. §4의 행렬이 denylist가 아니라 allowlist인 것이 그 안전 성질의 뿌리다.
