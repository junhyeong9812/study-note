# foundations/languages — Rust: 소유권 모델의 동작 방식과 그 보증의 대가 (정리)

> 이 노트는 Rust의 소유권 모델을 개념부터 설명하고, 그 모델이 무엇을 보증하며 그 보증에 얼마를 청구하는지, 그리고 그 청구서가 어디서 회수되는지까지 본다.\
> 원고 출처: `jun-bank/docs/study/tech/languages/rust.md` (따라 친 학습 노트) · 이관일 2026-09-16.\
> 본문 절들은 **원고**를 고쳐 쓴 것이다(문체·순서·인용·컴파일 오류 출력 유지 — 오류는 rustc 1.92.0 재현). 프로젝트 고유명(특정 은행 시스템·내부 결정 문서 번호·전용 도구 이름)은 일반형으로 바꿨다.\
> 「한눈에」·「전체 흐름」 그림은 **Claude가 새로 그린 것**이고, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

Rust의 논리는 하나다 — 차용 검사기·수명·`Send`/`Sync`·제로 코스트 추상은 각각의 기능이 아니라 **"값마다 소유자를 하나만 두고 그 사실을 컴파일러가 추적한다"는 하나의 결정에서 갈라져 나온 결과**로 읽는 것이 이해가 빠르다. 인용은 The Rust Programming Language(현행 판)·Rustonomicon·표준 라이브러리 문서 기준이다.

---

## 한눈에 — 쉽게 말하면

Rust는 **한 물건을 한 사람만 손에 쥐게 하는 규칙**이다. *(Claude 보강 — 원고에 없는 비유)*

```text
GC 언어 (관리인이 치운다)               Rust (물건마다 주인이 하나)
+---------------------------+          +---------------------------+
| 아무나 물건을 참조하고      |          | 값 하나 = 소유자 하나       |
| 관리인이 나중에 치운다      |          | 주인이 방 나가면 그 자리 정리 |
| (언제 치울지는 런타임)      |          | (언제 정리할지 컴파일 확정)  |
+---------------------------+          +---------------------------+
  → 안전을 런타임 자원으로 낸다          → 안전을 사람의 시간(학습·빌드)으로 낸다
```

**언어도 똑같은 구조다.** GC 언어가 안전을 런타임 자원(메모리·CPU·정지)으로 내는 자리에서, Rust는 같은 안전을 사람의 시간 — 소유권·수명을 배우는 학습 곡선과 매 빌드의 컴파일 시간 — 으로 낸다.

쉽게 말하면 이 문서 전체가 하나의 교환이다 — **무엇을 보증하고 그 보증을 어느 통화로 지불하는가.**

## 이 문서가 답하려는 질문

개념 정리다. 논리는 넷으로 흐른다.

```text
무엇이 문제였나          두 해법(수동 관리·GC)을 동시에 거부한다 (§1)
어떤 아이디어로 풀었나     소유권 → 차용 → 수명 → Send/Sync (§2~5)
그 아이디어의 비용은      학습·설계·컴파일 (§6~7)
어디서 회수되나          런타임 못 얹는 곳·공유 상태 병렬화·정지가 위반인 곳 (§8~10)
```

## 전체 흐름 — 하나의 규칙에서 갈라진 보증들

*(Claude 보강 — 원고의 논지를 세로로)*

```text
규칙: "값마다 소유자를 하나만 두고 컴파일러가 추적한다"
        ↓
소유권    이동하면 원래 이름은 죽는다 → double free 불가 (§2)
        ↓
차용      별칭 XOR 변경 (하나의 &mut 또는 다수의 &) (§3)
        ↓
수명      참조는 대상보다 오래 살 수 없다 → dangling 불가 (§4)
        ↓
Send/Sync 위 규칙을 스레드 경계에 적용 → 데이터 레이스가 타입 오류 (§5)
        ↓
청구서:  학습 곡선(줄어듦) · 설계 반복(재발) · 컴파일 시간(매일)
```

## 0. 왜 생겼나 · 무엇을 지향하나

> 출처: 원고 §0

Rust는 2006년 모질라에서 일하던 Graydon Hoare의 개인 프로젝트로 시작했다. 널리 인용되는 계기는 사소하다 — 자기 아파트 엘리베이터가 소프트웨어가 죽어 멈춰 서 있었고, "이런 기반 소프트웨어가 왜 아직도 이렇게 잘 죽는가"가 출발점이었다([MIT Technology Review, 2023](https://www.technologyreview.com/2023/02/14/1067869/rust-worlds-fastest-growing-programming-language/)). 2009년 모질라가 후원을 시작한 이유는 정확히 그 자리에 있었다 — 차세대 브라우저 엔진을 안전하게 짤 언어가 필요했고, **"가비지 컬렉터를 얹지 않고도 안전하게"**가 처음부터 조건이었다. 이정표: 2006 개인 프로젝트 → 2009 모질라 후원 → 2015-05-15 1.0(하위 호환 안정성 시작) → 2016 Servo 공개 → 2018 비렉시컬 수명(NLL) 안정화 → 2021 Rust Foundation 설립.

**지향점 넷** — ① GC 없는 메모리 안전 ② 데이터 레이스를 실행이 아니라 컴파일에서 막는 것 ③ 제로 코스트 추상 ④ 이 셋을 묶은 표어 "**두려움 없는 동시성(Fearless Concurrency)**"([Book ch.16](https://doc.rust-lang.org/book/ch16-00-concurrency.html)) — 동시성 코드를 "돌려 보고 레이스를 디버깅한다"가 아니라 "**컴파일되면 레이스가 없다**"로 바꾸겠다는 목표다.

이 지향은 안전을 한 축이 아니라 **두 축(메모리 안전·데이터 레이스 없음)**으로 본다 — C++는 어느 축도 언어가 보장하지 않고(비안전이 사양), Go·JVM·C#은 GC로 메모리 안전 축만 사되 데이터 레이스 축은 프로그래머에게 열어 두고, Rust는 두 축을 다 컴파일 타임에 잠근다. 공짜는 아니다 — Rust는 같은 안전을 **사람의 시간**(학습 곡선 + 컴파일 시간)으로 낸다.

## 1. 문제 — 두 가지 해법을 동시에 거부한다

> 출처: 원고 §1

메모리 안전 결함은 대규모 C/C++ 코드베이스의 지배적 취약점 계급이다. 7개국 보안 기관 공동 문서가 네 측정을 모았다 — 마이크로소프트 CVE 약 70%, Chromium 취약점 약 70%, 모질라 치명·고위험 34건 중 32건, Project Zero 2021 제로데이 67%([The Case for Memory Safe Roadmaps](http://web.archive.org/web/2024id_/https://media.defense.gov/2023/Dec/06/2003352724/-1/-1/0/THE-CASE-FOR-MEMORY-SAFE-ROADMAPS-TLP-CLEAR.PDF), 2023). 한정어가 중요하다 — 정확한 진술은 "모든 소프트웨어 취약점의 70%"가 아니라 **"메모리 비안전 언어로 쓰인 대규모 코드베이스에서 심각한 취약점의 약 70%"**다. 마이크로소프트가 덧붙인 한 문장이 성격을 말한다 — "이것은 집중적 코드 리뷰·교육·정적 분석을 포함한 완화책들에도 **불구하고** 그렇다"([We need a safer systems programming language](http://web.archive.org/web/2019id_/https://msrc-blog.microsoft.com/2019/07/18/we-need-a-safer-systems-programming-language/), 2019). 규율과 도구를 더 투입해 해결되는 문제가 아니었다.

기존 해법은 하나였다 — 런타임에 GC를 두고 해제 시점을 사람에게서 빼앗는 것(Java·Go·C#). Rust는 이 해법을 거부한다 — 커널·드라이버·임베디드·지연 민감 서비스처럼 런타임을 얹을 수 없거나 얹기 싫은 자리가 남기 때문이다. 그래서 질문이 좁혀진다 — **런타임에 아무것도 두지 않고, 컴파일 타임의 검사만으로 같은 보증을 낼 수 있는가.**

## 2. 소유권 — 값마다 소유자를 하나만 둔다

> 출처: 원고 §2

공식 문서가 세 줄로 규정한다 — "각 값은 소유자를 갖는다. 한 번에 오직 하나의 소유자만 있을 수 있다. 소유자가 스코프를 벗어나면 값은 버려진다(dropped)"([Book ch.4.1](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)). 세 번째 줄이 해제 시점을 결정한다 — 스코프 끝에서 컴파일러가 `drop`을 삽입하므로 해제는 자동이되 **그 시점이 컴파일 타임에 확정된다.** 두 번째 줄이 double free를 막는다 — 대입은 복사가 아니라 **이동(move)**이고, 이동하고 나면 원래 이름은 죽는다.

```rust
let s1 = String::from("hello");
let s2 = s1;            // 이동 — s1은 여기서 무효가 된다
println!("{s1}");       // 컴파일 거부
```

```text
error[E0382]: borrow of moved value: `s1`
  | let s2 = s1;   -- value moved here
  | println!("{s1}"); ^^ value borrowed here after move
```

여기서 이미 성질이 드러난다 — 런타임 검사가 아니라 **타입 검사**다. `s1`이 무효라는 사실은 실행해 봐야 아는 것이 아니라 컴파일러가 소유권 이동을 추적해서 알고, 그래서 비용이 실행 시점에 남지 않는다. 대신 비용은 다른 곳으로 옮겨간다 — 값을 여러 곳에서 쓰고 싶을 때마다 "누가 소유자인가"를 사람이 결정해야 한다.

## 3. 차용 — 별칭과 변경을 동시에 주지 않는다

> 출처: 원고 §3

소유권만으로는 쓸 수 있는 프로그램이 너무 적어서, 소유권을 넘기지 않고 참조만 빌려주는 장치가 차용이다. 규칙 두 줄 — "어느 시점에든 하나의 가변 참조 **또는** 임의 개수의 불변 참조를 가질 수 있다. 참조는 항상 유효해야 한다"([Book ch.4.2](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)). 첫 줄이 중심 규칙이다 — **별칭(aliasing)과 변경(mutation)을 동시에 허용하지 않는다.** 왜 위험한지는 데이터 레이스의 세 조건으로 설명된다 — "둘 이상의 포인터가 같은 데이터에 동시 접근 · 그중 최소 하나가 쓰기 · 동기화 장치 없음." 차용 규칙은 앞의 두 조건을 **단일 스레드에서도** 금지한다.

가변 참조 둘은 E0499, 불변 참조가 산 동안 가변 참조를 만들면 E0502로 거부된다. 초기 Rust가 답답했던 이유는 규칙이 아니라 **범위**였다 — 참조 수명을 렉시컬 스코프로 계산했다. RFC 2094(**비렉시컬 수명, NLL**)가 이것을 제어 흐름 그래프 기반으로 바꿨다 — "참조의 수명은 그 참조가 이후에 사용될 수 있는 함수 구간에만 걸친다"([RFC 2094](https://github.com/rust-lang/rfcs/blob/master/text/2094-nll.md)).

```rust
let mut data = vec!['a', 'b', 'c'];
let slice = &mut data[..];
capitalize(slice);
data.push('d');     // NLL 이전: E0502. 현재: 통과 — slice가 더 이상 쓰이지 않는다
```

다만 RFC의 세 사례가 전부 해결되진 않았다 — 함수 경계를 넘는 조건부 제어 흐름(problem case #3)은 rustc 1.92에서도 E0499로 거부된다(후속 Polonius의 대상, 아직 stable에 없음). **차용 검사기는 "안전한 프로그램을 전부 통과시킨다"가 아니라 "안전하지 않은 프로그램을 전부 막는다"를 보증한다** — 방향이 한쪽이고, 그 비대칭이 §7에서 비용으로 돌아온다.

## 4. 수명 — 참조는 대상보다 오래 살 수 없다

> 출처: 원고 §4

차용 규칙 둘째 줄을 강제하는 장치가 수명이다 — "수명은 … **참조가 우리에게 필요한 기간만큼 유효하도록** 보장한다"([Book ch.10.3](https://doc.rust-lang.org/book/ch10-03-lifetime-syntax.html)). 대부분 추론되고, 관계가 여러 갈래일 때만 사람이 적는다. 이 검사가 잡는 것이 dangling reference다.

```rust
let r;
{ let x = 5; r = &x; }   // x가 여기서 dropped
println!("r: {r}");       // error[E0597]: `x` does not live long enough
```

C에서 이 코드는 컴파일되고 실행되며 대체로 그럴듯한 값을 출력하다가 언젠가 다른 곳에서 터진다. Rust에서는 링크 단계에 가지도 못한다. **use-after-free를 런타임에 탐지하는 것이 아니라 그런 프로그램이 존재할 수 없게 만드는 것** — 이것이 §1의 "런타임에 아무것도 두지 않는다"의 실체다. 헷갈리는 지점은 용어다 — 참조의 **수명(lifetime)**은 "사용되는 기간", 값의 **스코프(scope)**는 "해제되기 전까지의 기간"이고, 검사기는 둘의 포함 관계를 확인한다.

## 5. Send와 Sync — 데이터 레이스가 타입 오류가 되는 원리

> 출처: 원고 §5

여기가 소유권 모델이 가장 크게 값을 내는 자리다 — 앞 세 절의 단일 스레드 규칙이 스레드 경계에 그대로 적용되면 데이터 레이스가 사라진다. 추가 장치는 마커 트레이트 둘뿐이다. `Send`는 "스레드 경계를 넘어 이전될 수 있는 타입", `Sync`는 "스레드 간 참조 공유가 안전한 타입"이고, 둘의 관계는 "**`T`가 `Sync`인 것은 `&T`가 `Send`인 것과 필요충분**"이다([std::marker::Sync](https://doc.rust-lang.org/std/marker/trait.Sync.html)).

핵심은 이것이 **자동 트레이트**라는 점이다 — "어떤 타입이 전부 `Send`/`Sync`인 타입들로만 구성되어 있다면 그 타입도 `Send`/`Sync`다"([Rustonomicon](https://doc.rust-lang.org/nomicon/send-and-sync.html)). 개발자가 선언하는 것이 아니라 **구성 요소로부터 컴파일러가 계산한다.** 안전하지 않은 조각 하나가 들어가면 그것을 담은 구조체 전체가 자동으로 스레드 간 이동 불가가 된다.

거부되는 장면이 원리를 가장 잘 보여 준다 — `Rc<T>`는 참조 카운트를 원자적으로 갱신하지 않으므로 `!Send`(E0277 "`Rc<i32>` cannot be sent between threads safely"), `RefCell<T>`는 동기화 없는 내부 가변성이라 `!Sync`이고 `Arc`로 감싸도 통과 못 한다(E0277 "if you want … use `std::sync::RwLock` instead"). 컴파일러가 대안까지 알려 준다.

주장의 범위는 정확히 봐야 한다 — Book은 "**많은** 동시성 오류가 컴파일 타임 오류가 된다"고 쓴다("모든"이 아니다). 못 막는 것 — "`Mutex<T>`에는 **데드락**을 만들 위험이 따른다." 정리하면 **데이터 레이스·use-after-free·double free·dangling은 컴파일 타임에 막고, 데드락·참조 순환 누수·순서 의존 논리 버그는 막지 못한다.** 경계 하나 — `unsafe`는 검사를 끄지 않는다("`unsafe`가 여는 것은 원시 포인터 역참조 등 다섯 가지뿐이고 나머지 규칙은 그대로"). 정확한 안전성 주장은 "Rust 프로그램은 안전하다"가 아니라 **"Safe Rust만 쓴다면 … 어떤 미정의 동작도 겪지 않는다"**이며, `unsafe` 블록은 그 보증의 책임을 사람이 인수하는 표시다.

## 6. 제로 코스트 추상 — 무엇이 0이고 무엇이 0이 아닌가

> 출처: 원고 §6

앞 절들의 검사가 전부 컴파일 타임이라면, 남는 질문은 "실행 시점에는 정말 아무것도 안 남는가"다. 출처는 Rust가 아니라 C++다 — "쓰지 않는 것에는 비용을 내지 않는다. 그리고 나아가, 쓰는 것은 직접 손으로 짜도 그보다 나을 수 없다"([Book ch.13.4](https://doc.rust-lang.org/book/ch13-04-performance.html)). Book이 측정으로 뒷받침한다 — 같은 검색을 `for` 루프와 반복자 체인으로 벤치마크하니 고수준 추상 쪽이 오히려 근소하게 빨랐다("많은 경우 손으로 쓸 어셈블리와 같은 것으로 컴파일된다").

두 가지를 정확히 읽어야 한다 — ① "많은 경우"는 전부가 아니라는 말이다(경계 검사 제거를 성과로 꼽는다는 것은 뒤집으면 최적화가 못 걷어낸 자리에는 경계 검사가 남는다는 뜻), ② 이 성질을 만드는 기계장치(**단형화, monomorphization** — 제네릭을 타입마다 별도 기계어로 펼침)가 공짜가 아니다. §7의 컴파일 시간 첫 원인이 정확히 이것이다 — "각 제네릭 인스턴스화를 자기 기계어로 번역하는데, 이는 **코드 비대와 컴파일 시간**을 늘린다"([The Rust Compilation Model Calamity](https://www.pingcap.com/blog/rust-compilation-model-calamity/)). **"제로 코스트"는 비용이 사라졌다는 뜻이 아니라 비용이 실행 시점에서 컴파일 시점과 바이너리 크기로 옮겨갔다는 뜻이다.** 0이 아닌 자리도 분명하다 — 트레이트 객체(`dyn Trait`)는 동적 디스패치라 단형화 이점이 사라지고, `async fn`의 상태 기계는 `Pin`이라는 별도 개념을 끌고 들어와 **인지 비용**으로 청구된다.

## 7. 청구서 — 학습 곡선·설계 반복·컴파일 시간

> 출처: 원고 §7

대가는 세 자리에 청구되고 성격이 다르다 — 하나는 시간이 지나면 줄고, 하나는 설계할 때마다 다시 나오며, 하나는 매일 나온다.

- **학습 곡선.** 가장 강한 근거는 대조 실험이다 — 소유권을 GC로 우회하는 `Bronze` 수집기로 학생 428명을 무작위 배정하니, 복잡한 별칭이 필요한 과제에서 GC 집단 약 4시간, Rust 소유권 집단 약 12시간(약 3배)이었다([Garbage Collection Makes Rust Easier to Use, ICSE 2022](https://arxiv.org/abs/2110.01098)). 무엇이 어려운지도 측정됐다 — 컴파일러 에러를 "항상" 이해한 응답이 소유권 위반은 39.6%인데 **수명 위반은 10.0%**([Learning and Programming Challenges of Rust, ICSE 2022](https://songlh.github.io/paper/survey.pdf)). 진짜 벽은 소유권이 아니라 수명이다. 통념 하나는 반박된다 — 안전 규칙 위반의 **91.8%가 safe 코드로 수정된다**("결국 `unsafe`로 도망친다"는 데이터가 지지하지 않는다).
- **설계 반복 비용.** 소유권은 코드 스타일이 아니라 **자료구조 설계를 제약한다.** 연결 리스트 튜토리얼이 `Box` → `Rc` → `Arc` → `unsafe` 순으로 올라가는 것이 그 성질이고([Too Many Linked Lists](https://rust-unofficial.github.io/too-many-lists/)), 그래프처럼 순환이 본질인 구조는 인덱스 기반 표현을 권한다. 이 비용이 특별한 이유는 **되돌리기 어려운 자리에 걸린다**는 점이다 — 소유 구조를 먼저 정해야 컴파일되고, 틀리면 자료구조를 다시 짜야 한다. 자기 참조 구조체가 극단적 사례이고(`Pin` 필요), `async fn`의 `Future`가 바로 그것이라 비동기를 쓰는 순간 누구나 간접적으로 닿는다.
- **컴파일 시간.** Rust 팀 스스로 인정하는 항목이다 — 3,700명 넘는 공식 설문에서 응답자의 **55%가 재빌드에 10초 넘게 기다린다**고 답했고, **"Rust를 더 이상 쓰지 않는다는 응답자의 약 45%가 그만둔 이유 중 하나로 긴 컴파일 시간을 들었다"**([Rust compiler performance survey 2025](https://blog.rust-lang.org/2025/09/10/rust-compiler-performance-survey-2025-results/)). 느린 이유는 구조적이다(단형화·대량 LLVM IR·크레이트 단위 코드 생성·trait coherence). 공동 창시자 Brian Anderson의 요약은 "Rust는 느린 컴파일 시간을 갖도록 설계되었다"이고, 개선은 진행 중이나 "**남아 있는 손쉬운 열매가 없다**"([Faster compilation with the parallel front-end](https://blog.rust-lang.org/2023/11/09/parallel-rustc/)).

**균형을 위한 반대 방향.** 이 청구서가 "쓰지 말라"는 결론은 아니다 — "도입 비용만큼의 값을 했다" 64%(2023), 자기평가 "생산적" 비율이 42%→47%→53%로 오른다. 구글은 "다른 언어 대비 Rust에 생산성 페널티가 있다는 데이터를 보지 못했다"고 보고했고, 안드로이드에서 롤백률이 C++ 대비 약 4배 낮고 리뷰 시간이 약 25% 짧다는 하류 이득까지 실측됐다([Rust in Android](https://blog.google/security/rust-in-android-move-fast-fix-things/)). **정확한 형태는 "Rust는 비싸다"가 아니라, 초기에 크고 줄어드는 비용(학습)·설계마다 재발하는 비용(자료구조)·매일 균일한 비용(컴파일)이 섞여 있고 마지막만 개선 속도가 느리다는 것이다.**

## 8. 회수되는 자리 — 런타임 못 얹는 곳, 공유 상태 병렬화, 정지가 곧 위반인 곳

> 출처: 원고 §8

회수 조건은 셋이고, 셋 다 **"GC 언어를 쓰면 된다"가 답이 되지 않는다**는 공통점이 있다.

- **① 런타임을 얹을 수 없다.** 커널이 대표다 — 리눅스 커널 Rust는 `#![no_std]`가 강제되고 `core`만 쓴다([Linux kernel: Rust](https://docs.kernel.org/rust/general-information.html)). GC는 선택지가 아니고, C를 계속 쓰면 §1의 CVE 계급을 계속 낸다. 이 자리에서 Rust는 "더 나은 선택지"가 아니라 **비어 있던 칸을 채우는 유일한 후보**다. 안전 관리 방식도 참고할 만하다 — `unsafe`를 흩뿌리지 않고 "커널 C API와의 모든 직접 상호작용을 신중히 리뷰된 추상으로 캡슐화"해 한곳에 모으고 드라이버는 그 안전한 추상만 쓴다.
- **② 공유 상태를 병렬화하는 것이 목표다.** §5가 값을 내는 자리다 — 모질라가 Firefox의 CSS 스타일 엔진(Quantum CSS)을 Rust로 다시 쓴 이유가 "**Rust에서는 데이터 레이스가 없다는 것을 정적으로 검증할 수 있다. 컴파일러가 그렇게 하도록 두지 않는다**"였다([Quantum CSS](https://hacks.mozilla.org/2017/08/inside-a-super-fast-css-engine-quantum-css-aka-stylo/)). **핵심은 속도가 아니라 시도 가능성이다** — 공유 가변 상태 위 병렬화는 다른 언어에서도 가능하지만 정확성을 사후 테스트로만 확인할 수 있어 손대기를 포기하게 되는 종류의 작업이다.
- **③ GC 정지가 지연 목표를 직접 깬다.** Discord의 사례가 교과서다 — Go 서비스에서 "대략 **2분마다** 지연·CPU 스파이크"가 났고 원인은 "Go가 최소 2분마다 GC를 강제로 돌리는" 데 있었다. **튜닝으로 해결되지 않았고**("GC 퍼센트를 어떻게 설정해도 아무것도 바뀌지 않았다"), Rust로 옮긴 결과는 "**지연·CPU·메모리 모든 지표에서 Go를 이겼다**"였다([Why Discord is switching from Go to Rust](https://discord.com/blog/why-discord-is-switching-from-go-to-rust)). 단 Discord 자신이 선을 긋는다 — "우리는 그냥 그러고 싶다는 이유로 모든 것을 Rust로 다시 써야 한다고 생각하지 않는다."

세 사례가 공유하는 형태 — 어느 경우에도 대안이 "조금 느린 다른 언어"가 아니었다(커널은 후보 없음, 스타일 엔진은 병렬화 포기가 대안, Discord는 튜닝을 다 돌려 본 뒤). **§7의 청구서는 이렇게 대안이 막힌 자리에서만 상대적으로 싸 보인다.**

뒤집으면 회수되지 않는 조건도 나온다 — 병목이 계산이 아니라 **대기**인 I/O 바운드 서비스, GC 정지가 지연 예산에 비해 무시할 만한 곳, 동시성이 스레드 공유 메모리가 아니라 **DB 트랜잭션과 잠금**에 있는 곳. 회수 실패의 실측 사례 — Prisma는 ORM 쿼리 엔진을 Rust에서 TypeScript로 **되돌렸는데**, 이유가 성능이 아니라 경계 비용이었다(이질 언어 숙련 겸비 부담·OS/OpenSSL별 바이너리·엣지 환경 비호환)([From Rust to TypeScript](https://www.prisma.io/blog/from-rust-to-typescript-a-new-chapter-for-prisma-orm)). 교훈은 "TS가 Rust보다 빠르다"가 아니라 **이질 언어 경계를 하나 세우는 비용이 그 언어의 이점을 삼킬 수 있다**는 것이다.

## 9. 세 계급의 안전성 — 비용이 어디에 놓이는가

> 출처: 원고 §9

흔한 실수가 "안전한가 아닌가"를 한 축으로 보는 것이다. 축은 둘 — **메모리 안전**과 **데이터 레이스 없음**이고, GC는 첫째 축만 준다.

- **C++ — 비안전이 사양이다.** 해제된 포인터 역참조·범위 밖 접근·데이터 레이스가 모두 미정의 동작이다. 안전성 비용은 **전적으로 개발자 규율에 놓인다.** 도구(AddressSanitizer)는 "런타임 라이브러리로 구성되고 일반적 슬로다운 **2배**"라 실행된 경로만 잡는 탐지이지 증명이 아니고 상시 운영에 못 켠다.
- **Go·JVM — GC가 첫째 축을 준다. 둘째 축은 주지 않는다.** 가장 자주 오해된다. Go 메모리 모델은 데이터 레이스 대응을 프로그래머에게 넘기고([The Go Memory Model](https://go.dev/ref/mem)), Java도 "잘못 동기화된 프로그램은 놀라운 동작을 보일 수 있다"고 서술한다([JLS ch.17](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html)) — **컴파일 오류가 아니다.** 다만 C++와 달리 미정의 동작이 아니라 **정의된 범위 안의 이상한 값**이다. 제공하는 것은 런타임 탐지 도구이고 그마저 비용이 크다 — Go race detector는 "메모리 **5~10배**, 실행 **2~20배**" 늘 수 있고 "실행되지 않은 코드 경로의 레이스는 못 찾는다." GC 자체도 구조적 교환이다 — "GOGC를 두 배로 하면 힙 오버헤드가 두 배, GC CPU는 대략 절반"([Go GC Guide](https://go.dev/doc/gc-guide)) — **메모리와 CPU 사이의 상시 교환**이다.
- **Rust — 두 축을 컴파일 타임에 준다.** §2~4가 첫째 축, §5가 둘째 축이다. 비용은 런타임에 없는 대신 §7의 세 항목으로 옮겨가 있다.

**언어 비교 — 아홉 축을 나란히**

| 축 | C++ | Go · JVM | Rust |
|---|---|---|---|
| 메모리 안전 보장 주체 | 없음(개발자 규율) | 런타임 GC | 컴파일러 |
| 해제 시점 결정 | 개발자 | 런타임 | 컴파일 타임 |
| use-after-free | 미정의 동작 | 구조적으로 불가 | 컴파일 거부 |
| 데이터 레이스의 지위 | 미정의 동작 | 정의되나 값이 어긋남 | 컴파일 거부 |
| 데이터 레이스 대응 수단 | 런타임 탐지기 | 런타임 탐지기 | 타입 검사 |
| 탐지기 오버헤드 | 약 2배(ASan) | 실행 2~20배(Go) | 해당 없음 |
| 상시 런타임 비용 | 없음 | 메모리·CPU 교환 | 없음 |
| 주된 비용의 위치 | 운영 중 사고 | 실행 자원 | 학습·설계·빌드 |
| 막지 못하는 것 | 대부분 | 데이터 레이스·데드락 | 데드락·논리 레이스 |

마지막 줄이 요점이다 — **어느 쪽도 데드락과 논리적 순서 버그는 막지 못한다.** 세 언어의 차이는 "안전한가"가 아니라 **같은 안전을 사는 값을 어느 통화로 지불하는가**이며, C++는 운영 사고로, Go·JVM은 실행 자원으로, Rust는 사람의 시간으로 낸다.

## 10. 회수되지 않는 워크로드 — I/O 바운드 릴레이의 경우

> 출처: 원고 §10 (특정 프로젝트의 판정을 일반화)

DB 폴링 → 네트워크 호출 → 상태 전이를 하는 **아웃박스 릴레이**(코어 트랜잭션이 사실 갱신과 같은 커밋으로 넣은 이벤트를 폴링해 수신 측에 전달하고 완료 표시하는 러너)를 예로 들면, §8의 회수 조건 어디에도 걸리지 않는다.

- **첫째, 병목이 Rust가 이기는 축에 없다.** §8의 회수 사례는 전부 CPU·GC 정지·메모리가 병목인 자리였다. 릴레이의 병목은 수신 API 호출과 DB 부하이고, 둘 다 언어를 바꿔서 줄어드는 항목이 아니다 — 계산이 아니라 대기가 비용인 워크로드에서 실행 속도를 몇 배 올려도 총 지연은 거의 그대로다.
- **둘째, 지연 보증이 릴레이에 걸려 있지 않다.** Discord가 옮긴 이유는 GC 정지가 사용자 지연 목표를 직접 깼기 때문인데, p99 초 단위 목표는 대개 동기 승인 경로에 걸리지 릴레이에 걸리지 않는다. 릴레이가 느려지면 결과는 장애가 아니라 적체다(서킷이 열리면 "전달 중단, 아웃박스에 쌓임, 유실 없음") — **밀리초가 아니라 시간 단위의 여유가 있고, 늦어짐이 장애가 아니라 적체로 흡수되는 구조다.**
- **셋째, 이런 시스템의 동시성은 스레드 동시성이 아니다.** §5의 최대 강점은 공유 메모리 위 스레드 경합을 타입으로 잡는 것인데, 은행 원장의 동시성은 전부 DB 층에 있다(버전 필드 낙관적 락, 조건부 UPDATE와 행 잠금). 불변식을 지키는 주체가 컴파일러가 아니라 DB이고, **Rust가 컴파일 타임에 제거해 주는 결함 계급이 이 코드베이스에는 거의 나타나지 않는다.**
- **넷째, 회수해야 할 비용이 측정된 적이 없다.** 측정되지 않은 병목을 근거로 언어를 바꾸는 것은 "미검증 값을 근거로 다른 결정을 하지 않는다"는 원칙의 정반대다.

외부 근거도 있다 — 구글은 C++ 대비로는 "노력이 **2배 넘게 줄었다**"고, 그런데 Go 대비로는 "**같은 규모의 팀이 같은 시간을 들여 만든다**"고 보고했다([Rust Nation UK 2024](https://www.theregister.com/2024/03/31/rust_google_c/)). 생산성 손실도 이득도 없다는 뜻이다. **즉 Rust의 큰 승리는 "C++를 쓸 수밖에 없던 자리"에서 나오고, 이미 메모리 안전한 언어를 쓰는 자리에서는 §8의 좁은 조건에 걸릴 때만 나온다.** 결론은 "Rust가 이 일에 부족하다"가 아니다 — **Rust가 비싸게 사 오는 보증을 이 자리에서는 이미 다른 층이 더 싸게 제공하고 있다**(메모리 안전은 JVM이, 자금 불변식은 DB 제약이, 지연 여유는 설계가). 재판정 신호는 분명하다 — 처리량이 실측되어 CPU·GC 정지가 병목으로 확인되거나 릴레이에 초 단위 아닌 지연 목표가 새로 걸리는 순간이다.

## 핵심 문장

- **차용 검사기·수명·Send/Sync는 별개 기능이 아니라 "값마다 소유자 하나 + 컴파일러 추적"이라는 한 규칙의 결과다.**
- **차용의 중심 규칙은 별칭 XOR 변경이다** — 데이터 레이스 세 조건 중 둘을 단일 스레드에서도 금지한다.
- **차용 검사기는 "안전한 걸 다 통과"가 아니라 "안전하지 않은 걸 다 막는다"를 보증한다** — 방향이 한쪽이라 그 비대칭이 비용이 된다.
- **Send/Sync는 자동 트레이트다** — 개발자가 선언하는 게 아니라 구성 요소로부터 컴파일러가 계산한다.
- **"제로 코스트"는 비용이 사라진 게 아니라 실행 시점에서 컴파일 시간·바이너리 크기로 옮겨간 것이다.**
- **세 언어의 차이는 "안전한가"가 아니라 같은 안전을 어느 통화로 지불하는가다** — 운영 사고 / 실행 자원 / 사람의 시간.
- **Rust의 큰 승리는 "C++를 쓸 수밖에 없던 자리"에서 나온다** — 이미 GC 언어를 쓰는 I/O 바운드 자리에서는 회수되지 않는다.

## 용어 풀이

- **소유권(Ownership)** — 값마다 소유자를 하나만 두고, 소유자가 스코프를 벗어나면 값을 해제하는 규칙. 해제 시점이 컴파일 타임에 확정된다.
- **이동(Move)** — 대입·전달이 복사가 아니라 소유권 이전인 것. 이동 후 원래 이름은 무효(사용하면 컴파일 거부).
- **차용(Borrowing)** — 소유권을 넘기지 않고 참조만 빌려주는 것. 규칙은 "하나의 가변 참조 또는 다수의 불변 참조"(별칭 XOR 변경).
- **수명(Lifetime)** — 참조가 유효해야 하는 기간. 참조가 대상보다 오래 살면(dangling) 컴파일러가 거부한다.
- **NLL(Non-Lexical Lifetimes)** — 참조 수명을 렉시컬 스코프가 아니라 실제 사용 구간으로 계산하는 것. 2018 에디션 기본.
- **Send / Sync** — 스레드 경계를 넘을 수 있는 타입 / 스레드 간 참조 공유가 안전한 타입. 자동 파생 마커 트레이트라 데이터 레이스가 타입 오류가 된다.
- **데이터 레이스(Data Race)** — 동기화 없이 같은 데이터를 동시 접근하며 최소 하나가 쓰기인 상태. Rust는 컴파일에서 막고, Go·JVM은 런타임 탐지에 맡긴다.
- **제로 코스트 추상(Zero-Cost Abstraction)** — 고수준 표현이 런타임 오버헤드를 더하지 않는 것. 비용은 컴파일 시간·바이너리 크기로 옮겨간다.
- **단형화(Monomorphization)** — 제네릭을 타입마다 별도 기계어로 펼치는 것. 런타임 비용을 0으로 만들지만 코드 비대와 컴파일 시간을 늘린다.
- **`unsafe`** — 원시 포인터 역참조 등 다섯 연산을 여는 표시. 차용 검사를 끄지 않으며, 보증 책임을 사람이 인수한다는 뜻.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **RAII와의 관계.** Rust의 `drop`은 C++의 RAII([`c-cpp-csharp.md`](c-cpp-csharp.md) §C++)와 같은 "스코프 끝에서 확정 해제" 아이디어다. 차이는 C++가 "누가 해제하는가"만 자동화한 반면 Rust는 소유권·차용으로 "누가 아직 보고 있는가"(참조 수명)까지 컴파일러가 추적한다는 점 — C++가 못 지운 UAF를 Rust가 지우는 근거다.
- **`Arc`와 `Rc`의 차이가 왜 타입에 드러나나.** `Rc`는 단일 스레드용(참조 카운트 비원자), `Arc`는 멀티 스레드용(원자 카운트)이다. §5에서 `Rc`가 `!Send`인 것은 이 설계의 직접 귀결이고, "필요할 때만 원자 연산 비용을 낸다"는 제로 오버헤드 원칙의 실천이다.
- **`Pin`과 자기 참조.** 값이 이동하면 자기 자신을 가리키던 포인터가 무효가 되는데, Rust는 "값이 이동했다"를 값에게 알려 주지 않으므로 `Pin`으로 이동을 금지한다. `async fn`의 `Future`가 컴파일러 생성 자기 참조 상태 기계라, 비동기를 쓰면 누구나 간접적으로 이 개념에 닿는다 — [`kotlin.md`](kotlin.md)의 코루틴 상태 기계가 같은 문제를 다른 방식(힙의 Continuation)으로 다룬다.
- **Fearless Concurrency의 정확한 범위.** "두려움 없는"은 데이터 레이스·UAF에 대한 것이지 데드락·논리 버그까지는 아니다. 이 한정을 놓치면 "Rust면 동시성이 안전하다"는 과장이 된다 — §5·§9의 "막지 못하는 것" 줄이 그 경계다.
