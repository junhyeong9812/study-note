### 1. 같은 이름이 네 층에 있을 때 — **부른 자리는 한 번도 안 쓰인다** ★★

**출력**

```text
===== node20 js06b-06a-lexical-scope.js (exit=0) =====
[1] 이름은 정의된 자리에서 바깥으로 올라가며 찾는다
  inner() finds it in outer            -> "outer"
  no local at all -> module level      -> "module"
  missing name                         -> ReferenceError: nowhere is not defined

[2] 부른 자리의 지역 변수는 안 보인다 -- 동적 스코프가 아니다
  caller has its own `where`           -> "module"

[3] 정의된 자리가 다르면 같은 소스라도 답이 다르다
  reader defined inside                -> "inside makeReader"
  reader defined outside               -> "module"

[4] 스코프 체인은 몇 겹이든 올라간다 -- 가장 가까운 것이 이긴다
  nearest wins at each level           -> ["L2","L1b","L0"]

[5] 함수 몸통은 자기 스코프를 만들고 블록도 만든다
  block does not leak let              -> "undefined"
  function does not leak var           -> "undefined"
  inner sees outer, not the reverse    -> ["oi","undefined"]
```

**왜 그런가**

- ★★★ **`[2]` 가 `"module"` 이다.** 부른 쪽에 `where = "caller"` 가 있는데도 안 읽혔다.
  **읽는 함수가 정의된 자리**에 `where` 가 없으니 거기서 바깥으로 올라가 **모듈의 것**을 찾은 것이다.
  ★ 이것이 **「렉시컬(정적) 스코프」의 전부**다 — 답이 실행 중에 안 바뀐다. 반대인 **동적 스코프**라면 `"caller"` 가 나왔을 것이다.
- ★★ **`[3]` 의 두 줄은 소스가 거의 같고 정의된 자리만 다르다.** 안에서 만든 것은 `"inside makeReader"`, 밖에서 만든 것은 `"module"` 이다.
  ★★★ **그래서 클로저가 성립한다** — 볼 것이 미리 정해져 있으니 **그 자리를 들고 나가기만 하면** 된다.
- ★★ **`[4]` 는 `["L2","L1b","L0"]`** 다. 규칙 한 문장은 「**가장 가까운 것이 이긴다**」이고, 블록도 스코프를 만들므로 형제 블록끼리는 서로를 못 본다.
- ★ **`[5]` 의 마지막 줄은 `["oi","undefined"]`** 다. 안쪽은 바깥을 보지만 **바깥은 안쪽을 못 본다** — 길이 **한 방향**이다.
- ★ 없는 이름은 `ReferenceError: nowhere is not defined` 다. 「칸이 아예 없다」는 뜻이고,
  「있는데 잠겼다」(`Cannot access ... before initialization`)와 문구가 다르다 — 정본은 [05번](../05-var-let-const-and-tdz/2-summary.md)이다.

### 2. 함수는 셋인데 변수는 몇 개인가 — **`var` 는 1, `for` 헤더의 `let` 은 3** ★★★

**출력**

```text
===== node20 js06b-06b-box-count.js (exit=0) =====
[1] 함수는 늘 셋이다 -- 갈리는 것은 그 셋이 보는 변수의 개수다
  how the loop declares   fns  boxes  which box      read
  ------------------------------------------------------------
  for (var i)             3    1      [0,0,0]        [3,3,3]
  for (let i)             3    3      [0,1,2]        [0,1,2]
  var + IIFE              3    3      [0,1,2]        [0,1,2]
  var + let copy in body  3    3      [0,1,2]        [0,1,2]
  for (let x of ...)      3    3      [0,1,2]        [0,1,2]
  for (const x of ...)    3    n/a    write refused  [0,1,2]
  while + let outside     3    1      [0,0,0]        [3,3,3]
  while + let inside      3    3      [0,1,2]        [0,1,2]
  factory make(i)         3    3      [0,1,2]        [0,1,2]

[2] 탐침이 무엇을 했는지 한 짝만 펼쳐 본다
  for (var i)    before [3,3,3]      after writing through fn0 ["WRITTEN","WRITTEN","WRITTEN"]
  for (let i)    before [0,1,2]      after writing through fn0 ["WRITTEN",1,2]

[3] const 줄은 쓰기 탐침이 부적용이다 -- 그 자리는 for (let x of) 로 잰다
  writing through a `const` handle -> TypeError: Assignment to constant variable., still reads 0
```

**왜 그런가**

- ★★★ **함수 개수는 아홉 줄 전부 3 이다.** 갈리는 것은 **변수 개수**다 — `for (var i)` 가 **1**, `for (let i)` 가 **3**.
  ★★ **`read` 값은 결과이고 `boxes` 가 원인**이다. `[2]` 가 그 인과를 한 장면에 넣는다 —
  `fn0` 으로 한 번 썼더니 `var` 판은 셋 다 `"WRITTEN"` 이 되고 `let` 판은 `["WRITTEN",1,2]` 다.
- ★★★ **`read` 가 같은데 `boxes` 가 다른 줄은 없다** — 이 표에서는 둘이 붙어 다닌다.
  ★★ 그런데 **`boxes` 가 같은데 `read` 가 다른 줄은 있다**: `for (let i)` 와 `factory make(i)` 는 둘 다 3인데 담긴 값의 출처가 다르다(헤더 회차 대 호출 인자).
  **개수가 원인이고 값은 그 위에 얹힌다**는 뜻이다.
- ★★★ **`while + let outside` 가 반례다.** `let` 을 썼는데 **변수 1개**에 `[3,3,3]` 이다.
  ★★ 이 한 줄이 **「`let` 이 고친다」를 반박한다** — 고치는 것은 **`for` 헤더의 선언**이고, 3번 문항이 그 목록을 편다.
- ★★ **`var + IIFE`·`var + let copy in body`·`factory make(i)` 가 전부 3 이다.**
  셋 다 하는 일이 같기 때문이다 — **회차마다 새 이름을 만들어 값을 옮긴다.**
  ★ 「옛날 고침」과 「지금 고침」이 같은 기계라는 것이 이 표의 값어치다.
- ★★ **`for (const x of ...)` 만 `n/a`** 다. `const` 는 재대입이 `TypeError` 라 **탐침이 성립하지 않는다.**
  ★★★ 이것은 **「안 쟀다」가 아니라 「잴 것이 없다」는 뜻**이므로 숫자를 지어내지 않고 그렇게 찍었다.
  `[3]` 이 그 거부를 출력으로 보이고, **같은 자리는 바로 위의 `for (let x of ...)` 줄이 3으로 잰다.**
- ★ **주소를 안 쓰는 것이 요점이다.** 주소는 실행마다 바뀌어 「흔들리는 칸」이지만 **개수와 무리 배치는 안 흔들린다** —
  그래서 이 표가 제출 전 재대조에서 한 글자도 안 움직인다.

### 3. `for` 헤더의 `let` 이 회차마다 하는 일 — **칸은 새것, 값은 이어받는다** ★★★

**출력**

```text
===== node20 js06b-06c-per-iteration.js (exit=0) =====
[1] 칸이 새로 생겼다는 것 -- 한 회차에서 쓴 값이 다른 회차에 안 번진다
  let: write in fn0 leaks to fn1?          -> ["X",1,2]
  var: write in fn0 leaks to fn1?          -> ["X","X","X"]

[2] 그런데 값은 이어진다 -- 새 칸이 앞 회차의 값을 받아 온다
  body sets i = 1 on the first pass        -> [0,2]
  same with var                            -> [0,2]

[3] 회차 안에서 바꾼 값이 그 회차의 클로저에 남는다
  let: change i after pushing the fn       -> [10]
  how many passes did it make              -> 1

[4] 그 일을 하는 것은 let 이 아니라 for 헤더의 let 이다
  for (let i;;) header                     -> [0,1,2]
  while + let declared outside             -> [3,3,3]
  do..while + let outside                  -> [3,3,3]
  for (;;) with let outside header         -> [3,3,3]
  for..of with let                         -> [0,1,2]
  for..in with let                         -> ["a","b"]
  forEach callback param                   -> [0,1,2]

[5] 헤더의 이름과 몸통의 같은 이름은 다른 칸이다
  body shadows the header name             -> ["body","body","body"]
  and the loop still counts                -> 3
```

**왜 그런가**

- ★★★ **`[1]` 과 `[2]` 는 서로 다른 것을 말한다.**
  `[1]` 은 **「칸이 새것이냐」** — `let` 판에서 `fn0` 으로 쓴 값이 `fn1`·`fn2` 에 안 번진다(`["X",1,2]`).
  `[2]` 는 **「값이 이어지느냐」** — 몸통에서 `i = 1` 로 바꾸면 다음 회차가 `2` 로 시작해 `[0,2]` 다.
  ★★ **새 칸을 만들되 앞 회차의 값을 받아 온다**면 둘 다 참이다. `var` 판과 `[2]` 의 글자가 **같은 것**이 그 증거다.
- ★★★ **`[3]` 에서 루프는 한 번만 돈다**(`1`). 몸통의 `i += 10` 이 다음 회차의 시작값을 `11` 로 만들어 조건이 바로 깨지기 때문이다.
  그리고 **그 회차의 함수가 보는 값은 `10`** 이다 — **함수를 넣은 뒤에 바꾼 값이 보인다.**
  ★★ 클로저가 붙든 것이 **값이 아니라 칸**이라는 사실이 여기서도 나온다(4번 문항).
- ★★ **`[4]` 를 두 무리로 가르면**
  - **회차마다 새 칸** — `for (let i;;)` 헤더 · `for..of` · `for..in` · `forEach` 콜백 매개변수 → `[0,1,2]`·`["a","b"]`
  - **칸 하나** — `while` · `do..while` · `for (i = 0; ...)`(헤더 밖에서 선언) → `[3,3,3]`
  ★★★ **갈림의 기준은 「`let` 을 썼나」가 아니라 「선언이 루프 헤더 안에 있나」 쪽**이다.
- ★★ 그래서 **「`let` 을 쓰면 고쳐진다」는 반박된다** — `while + let` 이 `[3,3,3]` 이다.
  ★ 콜백 매개변수가 되는 이유도 같은 사실의 다른 얼굴이다 — **호출마다 새 이름이 생긴다**(4번 문항 `[4]`).
- ★ **`[5]` 에서 몸통의 `let i = "body"` 는 헤더의 `i` 와 다른 칸**이라 루프 제어에 아무 영향이 없다. 그래서 그대로 **세 번** 돈다.

### 4. 만든 뒤에 바꾸면 — **바뀐 것이 나온다** ★★

**출력**

```text
===== node20 js06b-06d-variable-not-value.js (exit=0) =====
[1] 만든 뒤에 바꿔도 따라온다 -- 값이었다면 안 따라온다
  changed after the fn was made          -> ["before","after"]
  the fn was even called in between      -> [0,1,2]

[2] 두 함수가 한 변수를 나눠 쓴다 -- 하나로 쓰면 다른 하나가 본다
  read/write pair                        -> [0,42]
  two calls to make() do not share       -> [42,0]

[3] 그 변수는 함수가 끝난 뒤에도 산다
  counter survives the call that made it -> [1,2,3]
  two counters are independent           -> [1,2,1]

[4] 인자로 받은 것도 같은 성질이다 -- 다만 이름이 회차마다 새로 생긴다
  param is a fresh name per call         -> [99,2]
  object arg: box fresh, contents shared -> 5

[5] 「값을 박아 두고 싶다」는 다른 도구다
  copy into a new name at make time      -> ["before","after"]
  bind freezes the argument              -> ["before","after"]
```

**왜 그런가**

- ★★★ **`[1]` 이 `["before","after"]` 다.** 이것이 배제하는 것은 「**만들 때 값을 복사한다**」는 그림이다.
  ★ 그 사이에 **한 번 불러 봤는데도** 그렇다 — 「처음 부를 때 굳는다」도 배제된다.
- ★★ **`[2]` 의 두 줄이 갈리는 이유는 「방이 언제 생기나」 하나**다.
  한 번의 `make()` 안에서 만든 `read`/`write` 는 같은 방을 보고(`[0,42]`), **`make()` 를 두 번 부르면 방이 둘**이라 안 섞인다(`[42,0]`).
  ★★★ 두 번째 줄이 **2번 문항의 `factory make(i)` 줄과 같은 사실**이다 — 호출이 곧 방이다.
- ★★ **`[4]` 가 「칸」과 「내용물」을 가른다.** 매개변수는 **호출마다 새 칸**이라 `a.write(99)` 가 `b` 에 안 번진다(`[99,2]`).
  그런데 **객체를 넘기면 칸은 새것인데 그 안의 객체는 같은 것**이라 바깥의 변경이 보인다(`5`).
  ★ [05번의 `const`](../05-var-let-const-and-tdz/2-summary.md)가 「이름을 못질하지 값은 아니다」라고 한 것과 **같은 구분**이다.
- ★ **`[5]` 의 두 도구가 공통으로 하는 일** — **그 시점의 값을 새 이름(또는 인자 자리)에 복사해 둔다.**
  그래서 둘 다 `"before"` 로 굳는다. **클로저가 하는 일이 아니라, 클로저를 안 쓰게 만드는 일**이다.

### 5. 밖에서 안 보이는 상태 — **감춰지는 것은 이름이다** ★★

**출력**

```text
===== node20 js06b-06e-module-pattern.js (exit=0) =====
[1] 밖에서는 이름이 아예 안 보인다
  acc.read()                             -> 100
  Object.keys(acc)                       -> ["deposit","read","size"]
  acc.balance                            -> undefined
  "balance" in acc                       -> false
  JSON.stringify(acc)                    -> "{}"
  getOwnPropertyNames                    -> ["deposit","read","size"]

[2] 인스턴스마다 자기 칸이다
  two accounts do not share              -> [10,0]
  methods of one account share           -> [30,2]

[3] 한 번만 만들고 싶으면 IIFE 로 즉시 부른다 -- 같은 기계다
  IIFE module: hit twice                 -> 2
  typeof the IIFE result                 -> "object"

[4] 감춰지는 것은 이름이지 값이 아니다
  a leaked object is still reachable     -> {"k":999}
  a leaked primitive is a copy           -> 1

[5] 같은 일을 하는 다른 도구 -- 클래스의 # 필드
  class #field: deposit then read        -> 7
  Object.keys of the instance            -> []
  reading #balance from outside          -> SyntaxError: Private field '#balance' must be declared in an enclosing class
```

**왜 그런가**

- ★★★ **`[1]` 에서 창 다섯이 전부 실패한다** — `Object.keys`·`getOwnPropertyNames`·점 접근·`in`·`JSON.stringify`.
  ★★ 전부 **프로퍼티를 보는 창**인데 `balance` 는 프로퍼티가 아니라 **스코프의 이름**이기 때문이다.
  ★ 「안 보인다」와 「없다」가 다른 것은 [05번의 전역 `let`](../05-var-let-const-and-tdz/2-summary.md)과 같은 자리다.
- ★★ **`[2]` 는 「인스턴스마다 방」을 보인다.** 계좌 둘이 안 섞이고(`[10,0]`), 한 계좌의 세 메서드는 나눠 쓴다(`[30,2]`).
- ★★ **`[4]` 가 경계를 긋는다.** 안의 **객체를 돌려주면 그 객체는 그대로 만져진다**(`{"k":999}`).
  원시 값을 돌려주면 복사라 안 만져진다(`1`). ★ **감춰지는 것은 이름이지 값이 아니다.**
- ★★ **`[5]` 의 마지막 줄은 `SyntaxError`** 다. 클로저 쪽은 없는 이름을 읽어도 `undefined` 인데,
  `#` 필드는 **파싱 단계에서 거부**된다 — 「그 클래스 안이 아니면 이 문법 자체가 성립하지 않는다」는 뜻이라 **더 이른 시점**에 잡힌다.
  ★ 정본은 [목록의 **16번 주제**](../16-class-syntax/)다.
- ★ **대가** — 메서드가 프로토타입이 아니라 **인스턴스마다 새 함수 객체**로 만들어진다.
  ★★ **얼마나 드는지는 안 쟀다** — 이 노트는 벤치마크를 돌리지 않으므로 「느리다」고 적지 않는다.

### 6. 아무도 안 쓰는 것처럼 보이는데 — **형제가 읽으면 같이 산다** ★

**출력**

```text
===== node20 --expose-gc js06b-06f-retain.js (exit=0) =====
  what the returned closure does  the captured object is
  ------------------------------------------------------
  nobody reads it                 collected     fn() = "small"
  the returned fn reads it        still alive   fn() = "big"
  only a sibling fn reads it      still alive   fn() = "small"
  copy out the one field it needs collected     fn() = "big"

[함수가 끝났는데 그 지역 변수를 아직 읽을 수 있다 -- 그것이 「잡고 있다」의 뜻이다]
  makeReader() returned long ago, r() = 1000
  ten readers made the same way, sum = 10000
```

**왜 그런가**

- ★★★ **첫 줄이 `collected` 여야 이 표에 뜻이 생긴다.** 그것이 **「GC 가 실제로 돌았다」의 증거**이기 때문이다.
  ★★ 네 줄이 전부 `still alive` 였다면 이 표는 **「클로저가 붙든다」가 아니라 「GC 가 안 돌았다」 쪽**을 말하는 것일 수 있다 — 구분이 안 된다.
- ★★★ **셋째 줄이 교재다.** 돌려준 함수는 `() => "small"` 인데, **돌려주지도 않은 형제 함수**가 같은 방에서 그 객체를 읽는다는 이유만으로 살아 남는다.
  ★★ 실무의 「작은 콜백이 큰 응답을 붙든다」가 정확히 이 모양이다.
  ★ 넷째 줄이 **고침**이다 — 큰 것 대신 **필요한 조각 하나만** 새 이름에 복사해 두면 수거된다.
- ★★★ **이 표에 명세 보장 칸은 없다.** ECMA-262 는 **무엇이 언제 수거되는지 약속하지 않는다.**
  「형제까지 산다」는 **V8 이 스코프를 통째로 붙드는 사정**이고, `collected`/`still alive` 라는 판정 자체가 **이 판의 관찰**이다.
  ★ 두 판·6회에서 전부 같았지만 **「같았다」는 보장이 아니다.**
- ★ **아래 두 줄은 GC 없이도 성립한다.** `makeReader()` 는 끝났는데 그 지역 배열이 아직 읽힌다 —
  **「함수가 끝났는데 그 지역 변수를 읽을 수 있다」가 곧 「붙들고 있다」의 뜻**이다. 여기에는 잴 것이 없다.

### 7. 「나중에 읽어서」가 왜 부족한가 — **그 설명은 개수를 안 말한다** ★★★

**왜 그런가**

- ★★★ **설명하지 못하는 것은 「그럼 왜 칸이 하나인가」 하나**다.
  「나중에 읽는다」는 `let` 판에도 그대로 해당한다 — **`let` 판도 루프가 끝난 뒤에 읽는다.** 그런데 답은 `[0,1,2]` 다.
  ★★ 그러니 「나중에 읽어서」는 **두 판을 구분하지 못한다.** 구분하는 것은 개수뿐이다.
- ★★★ **「칸이 셋이었다면 어땠을까」로 되물으면** 답이 드러난다 — **나중에 읽어도 `0 1 2` 가 나왔을 것**이다.
  실제로 **칸을 셋으로 가르면 그렇게 된다**(2번 문항의 IIFE·팩토리 줄).
- ★★ **원인은 개수이고 값은 증상**이다. 05번이 값을 보였고 이 주제가 개수를 센다.
- ★★ **JS 는 잡힌 변수에 손잡이가 없어서** 쓰기 탐침으로 센다 — 한 함수로 쓰고 나머지로 읽어 무리를 짓는다.
  파이썬은 `함수.__closure__[0]` 이라는 **객체**가 있어 `is` 로 세고, Go 는 **`&i` 로 주소**를 찍어 센다.
  ★ **도구가 다른 이유는 언어가 그 칸을 밖으로 얼마나 내보이느냐가 달라서**다. 세는 값은 같다.
- ★ **05번에서 이어받은 것 한 문장** — 「`[3,3,3]` 과 `[0,1,2]` 로 갈린다」를 받아 **「갈리는 원인은 칸의 개수다」로 바꿔 증명했다.**

### 8. 같은 결함, 세 언어의 세 가지 답 — **언어가 고치거나, 판을 바꾸거나, 쓰는 쪽이 고친다** ★★★

**왜 그런가**

- ★★★ **세 답이 이렇게 다르다.**

| 언어 | 무엇이 문제였나 | 누가 고쳤나 | 옛 코드의 의미 |
|---|---|---|---|
| **파이썬**([22번](../../../python/syntax/22-closures-and-late-binding/2-summary.md)) | `for` 가 이름을 새로 안 만든다 | ★ **언어가 안 고쳤다** — 쓰는 쪽이 기본 인자·팩토리·`partial` 로 고친다 | 그대로 |
| **Go**([13번](../../../go/syntax/13-closures-variable-capture-and-loop-variable-change/2-summary.md)) | 루프 변수 하나를 회차가 나눠 쓴다 | ★★★ **언어 판을 바꿨다**(1.22) — 같은 소스의 의미가 뒤집힌다 | ★ **바뀐다** |
| **JS** | `var` 가 함수 스코프라 칸이 하나다 | ★★ **새 선언 형태를 더했다**(`let`, ES2015) — `var` 는 그대로 뒀다 | 그대로 |

- ★★★ **세는 도구도 셋이 다르다.**
  파이썬은 **셀 객체**(`__closure__[0]` 을 `is` 로 비교) · Go 는 **포인터 주소**(모아서 서로 다른 개수) · JS 는 **쓰기 탐침**.
  ★★ **언어가 그 칸을 밖으로 얼마나 내보이느냐가 달라서**다 — JS 는 아무것도 안 내보이므로 **행동으로만** 잰다.
- ★★ **옛 코드의 의미를 바꾼 것은 Go 뿐**이다. 그래서 Go 는 `go.mod` 의 한 줄이 언어 판을 고르게 해 둔다.
  파이썬과 JS 는 **옛 코드가 그대로 돈다.**
- ★★ **JS 가 치른 대가는 「선언이 셋이 된 것」 하나**다. `var`·`let`·`const` 의 규칙을 전부 알아야 남의 코드를 읽을 수 있다(05번이 그 표다).
  ★ 대신 **옛 코드가 한 줄도 안 깨졌다.**
- ★ **파이썬의 고침 셋 중 JS 에 그대로 있는 것은 「팩토리」 하나**다(2번 문항의 `factory make(i)`).
  ★ **기본 인자 트릭은 JS 에 없다** — JS 의 기본값은 **호출마다 평가**되므로 그 기계가 성립하지 않는다. 08번이 그 대비를 편다.

### 9. 보장인가 구현인가 관찰인가 — **이 주제는 관찰 칸이 딱 하나다** ★★★

**왜 그런가**

- ★★★ **명세 보장 다섯** — ① 이름은 **정의된 자리** 기준으로 풀린다 ② 함수는 자기가 태어난 스코프를 붙든다
  ③ 붙드는 것은 **값이 아니라 바인딩**이다 ④ **`for` 헤더의 `let`/`const` 는 회차마다 새 바인딩**을 만들고 `var` 는 함수당 하나다
  ⑤ **호출마다 새 스코프**가 생긴다.
- ★★★ **「형제 클로저가 읽으면 같이 산다」는 V8 의 구현이다.**
  ECMA-262 는 **무엇이 언제 수거되는지 약속하지 않는다.** 그래서 이 문서는 그 줄을 **「관찰」로만** 적고,
  ★★ **거꾸로도 단정하지 않는다** — 「안 쓰는 변수는 안 붙든다」도 보장이 아니다.
- ★★ **예외의 종류는 명세, 문구는 V8 의 것**이다. 이 주제는 문구 위에 결론을 세우지 않았다.
- ★★ **「두 판에서 한 글자도 같았다」는 「이 문서의 출력을 어느 판에서 읽어도 된다」의 근거**는 되지만
  **「어느 엔진에서도 그렇다」의 근거는 못 된다.** 보장은 명세에서 온다.
- ★ **부적용인 창이 둘**이다 — 파이썬식 **속 보기**(JS 에 없다)와 **`const` 칸의 쓰기 탐침**(쓰기가 거부된다).
  ★★ **그 사실 자체가 결론이다** — JS 는 「잡힌 변수」를 **언어 표면에 전혀 안 내보인다.** 그래서 행동으로만 잴 수 있다.

### 10. 경계 — 어디까지가 이 주제인가 ★★

**왜 그런가**

- **정본은 각각 이렇다.**
  **블록 스코프·TDZ** → [05번](../05-var-let-const-and-tdz/2-summary.md) · **`this`** → [목록의 **07번 주제**](../07-this-binding-four-rules/) ·
  **`WeakRef`** → 목록의 **47번 주제** · **`#` 필드** → [목록의 **16번 주제**](../16-class-syntax/) · **엄격 모드** → 목록의 **35번 주제**.
- ★★★ **07번이 뒤집는 것 한 문장** — **`this` 는 정의된 자리가 아니라 호출식이 정한다.**
  이 주제의 규칙(렉시컬)을 `this` 에 적용하는 것이 07번 사고의 뿌리다. ★ 예외가 하나 있다 — **화살표 함수의 `this` 는 렉시컬이다.**
- ★★ **08번이 이어받는 것** — **매개변수도 클로저가 잡는 이름**이라는 것. 그리고 **기본값이 자기 스코프에서 평가된다**는 것.
  「호출마다 새 이름」이 여기서는 4번 문항의 한 줄이고, 거기서는 절 하나다.
- ★ **파이썬에는 블록 스코프가 없다**([`python/syntax/21-scope-legb-global-nonlocal`](../../../python/syntax/21-scope-legb-global-nonlocal/2-summary.md)).
  `if`/`for` 안에서 만든 이름이 함수 전체에 산다 — **JS 의 `var` 쪽**이다.
  **그쪽은 「어느 스코프에서 찾나(LEGB)」까지, 여기는 「그 스코프가 몇 개 생기나」부터다.**
- ★ **이 주제가 끝까지 책임지는 것 셋** — ① 이름을 정의된 자리에서 찾는다는 것 ② **루프 클로저의 원인이 개수라는 것**
  ③ 클로저가 값이 아니라 칸을 붙든다는 것.
