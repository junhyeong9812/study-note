### 1. 화면에 보이는 숫자와 저장된 숫자 — **`toFixed(20)` 이 화면을 걷어 낸다** ★★★

**출력**

```text
===== node20 js01b-03a-float.js (exit=0) =====
[1] 유명한 자리
  0.1 + 0.2            = 0.30000000000000004
  0.1 + 0.2 === 0.3    = false
  0.1 + 0.2 - 0.3      = 5.551115123125783e-17
  Number.EPSILON       = 2.220446049250313e-16
  차이 < EPSILON 인가   = true

[2] 화면에 보이는 것은 '가장 짧은 표기' 이지 저장된 값이 아니다
  0.1                    toFixed(20) = 0.10000000000000000555  toPrecision(17) = 0.10000000000000001
  0.2                    toFixed(20) = 0.20000000000000001110  toPrecision(17) = 0.20000000000000001
  0.3                    toFixed(20) = 0.29999999999999998890  toPrecision(17) = 0.29999999999999999
  0.30000000000000004    toFixed(20) = 0.30000000000000004441  toPrecision(17) = 0.30000000000000004

[3] 그래서 결합 법칙이 깨진다
  (0.1 + 0.2) + 0.3    = 0.6000000000000001
  0.1 + (0.2 + 0.3)    = 0.6
  둘이 같은가           = false
  0.1 * 3              = 0.30000000000000004
  0.1 + 0.1 + 0.1      = 0.30000000000000004

[4] 정확히 표현되는 소수도 있다 — 2 의 거듭제곱 분모면 된다
  0.5      toFixed(20) = 0.50000000000000000000
  0.25     toFixed(20) = 0.25000000000000000000
  0.125    toFixed(20) = 0.12500000000000000000
  0.75     toFixed(20) = 0.75000000000000000000
  1.5      toFixed(20) = 1.50000000000000000000

[5] 돈은 정수로 — 그것이 처방이다
  0.1 + 0.2 를 원 단위로 : 0.3
  10*0.1 + 10*0.2        : 3 (정수 3 이 나온다)
  Number((0.1+0.2).toFixed(2)) : 0.3
```

**왜 그런가**

- ★★★ **세 수가 끌려간 방향이 다르다.**
  `0.1` 은 `0.10000000000000000555`(위로), `0.2` 는 `0.20000000000000001110`(위로),
  `0.3` 은 `0.29999999999999998890`(아래로)이다.
  두 개를 더하면 `0.30000000000000004441` 이 되어 **`0.3` 의 저장값보다 크다** — 그래서 `===` 가 거짓이다.
- ★★★ **`console.log(0.1)` 이 `0.1` 로 보이는 것은 「가장 짧은 표기」 때문**이다.
  그 문자열을 **다시 읽으면 같은 double 이 되는** 가장 짧은 십진 문자열을 보여 준다 —
  ★ **화면이 값을 감추고 있었다.** `toFixed(20)` 이 이 절의 창이다.
- ★★ **`0.1 + 0.2 - 0.3` 은 `5.551115123125783e-17`** 이고 `Number.EPSILON`(`2.220446049250313e-16`)보다 작다.
  그래서 「EPSILON 보다 작으면 같다고 보자」가 실무 처방이 되는데, ★ **큰 수에서는 안 맞는다** — 눈금 간격이 값에 비례해 커지기 때문이다.
- ★★ **결합 법칙이 깨지는 것은 `[3]`** 이 보여 준다. `(0.1+0.2)+0.3` 은 `0.6000000000000001`,
  `0.1+(0.2+0.3)` 은 `0.6` 이다.
  ★ 실무에서는 **합계를 내는 순서를 바꾸면(정렬·병렬 분할) 값이 달라진다** — 재현이 안 되는 합계의 원인이 여기다.
- ★ **정확히 저장되는 소수가 있다** — `0.5`·`0.25`·`0.125`·`0.75`·`1.5`.
  기준은 **분모가 2 의 거듭제곱**인가이다. 「소수는 다 부정확하다」는 틀리다.
- ★ **처방은 정수로 옮기는 것**이다. `10 * 0.1 + 10 * 0.2` 가 정확히 `3` 이다.

### 2. 정수의 한계 — **`2**53` 부터 홀수가 사라진다** ★★★

**출력**

```text
===== node20 js01b-03b-safe-integer.js (exit=0) =====
[1] 한계 상수
  Number.MAX_SAFE_INTEGER = 9007199254740991 (2**53 - 1)
  Number.MIN_SAFE_INTEGER = -9007199254740991
  Number.MAX_VALUE        = 1.7976931348623157e+308
  Number.MAX_VALUE * 2    = Infinity

[2] 경계를 한 걸음 넘으면 두 정수가 한 값이 된다
  M          = 9007199254740991
  M + 1      = 9007199254740992
  M + 2      = 9007199254740992
  M + 1 === M + 2 : true
  M + 3      = 9007199254740994   <- 여기서는 다시 갈린다
  2**53 === 2**53 + 1 : true
  2**53 + 2 === 2**53 : false

[3] 소스에 적은 리터럴부터 이미 바뀐다
  9007199254740993       = 9007199254740992
  9007199254740993n      = 9007199254740993n
  JSON.parse('{"id":9007199254740993}').id = 9007199254740992
  JSON.stringify 로 되돌리면 : {"id":9007199254740992}

[4] isInteger 와 isSafeInteger 는 다른 질문이다
n                       Number.isInteger  Number.isSafeInteger
--------------------------------------------------------------
1                       true              true
1.0                     true              true
1.5                     false             false
2**53 - 1               true              true
2**53                   true              false
1e21                    true              false
Infinity                false             false
NaN                     false             false
"1" (a string)          false             false

[5] 큰 수가 필요하면 BigInt 로 간다
  BigInt(M) + 1n + 1n     = 9007199254740993n
  2n ** 64n               = 18446744073709551616n
  2 ** 64 (Number)        = 18446744073709552000
```

**왜 그런가**

- ★★★ **`M + 1 === M + 2` 가 참**이고 **`M + 3` 에서는 다시 갈린다**(`9007199254740994`).
  `2**53` 부터 **눈금 간격이 2** 라서 **짝수만 눈금 위에 있다** — 홀수는 가장 가까운 짝수로 끌려간다.
  ★ 「`2**53` 부터 전부 부정확하다」가 아니라 「**홀수가 사라진다**」가 정확한 진술이다.
- ★★★ **소스에 `9007199254740993` 을 쳐도 `...992` 가 찍힌다.** 리터럴을 읽는 순간 이미 끌려간다.
- ★★★ **`JSON.parse` 도 같다.** `{"id":9007199254740993}` 이 `...992` 로 들어오고,
  `JSON.stringify` 로 되돌리면 **바뀐 값이 나간다.** ★ **경고도 예외도 없다** — 이 주제에서 가장 조용한 사고다.
- ★★ **`Number.isInteger` 와 `Number.isSafeInteger` 는 `2**53` 과 `1e21` 에서 갈린다.**
  둘 다 정수이지만 안전하지 않다 — **「정수인가」로 큰 수를 방어할 수 없다.**
- ★ **`Number.MAX_VALUE * 2` 는 `Infinity`** 다. 예외가 아니다.
- ★ **실무 답은 문자열로 주고받는 것**이다. `BigInt` 를 쓰더라도 `JSON` 이 모르므로(4번) 경계에서는 문자열이다.

### 3. 숫자인데 숫자가 아닌 값들 — **`-0` 은 두 자리에서만 보인다** ★★★

**출력**

```text
===== node20 js01b-03c-nan-zero.js (exit=0) =====
[1] 나눗셈이 던지지 않는다
  1 / 0      = Infinity
  -1 / 0     = -Infinity
  0 / 0      = NaN
  1 % 0      = NaN
  1n / 0n 은 ? -> RangeError: Division by zero

[2] NaN 은 자기 자신과도 다르다 — 그것이 판별법이다
  typeof NaN            = number
  NaN === NaN           = false
  x !== x 로 판별       = true
  Number.isNaN('abc')   = false
  isNaN('abc')          = true   <- 전역 isNaN 은 먼저 숫자로 바꾼다
  isNaN('')             = false  | Number.isNaN('') = false

[3] -0 은 === 로는 안 보이고 나눗셈과 Object.is 로만 보인다
  -0 === 0              = true
  Object.is(-0, 0)      = false
  String(-0)            = "0"
  (-0).toFixed(2)       = "0.00"
  JSON.stringify(-0)    = 0
  1 / -0                = -Infinity   <- 이것이 실무 판별법
  Math.sign(-0)         = -0 | Object.is(Math.sign(-0), -0) = true
  -0 + 0                = 0 | Object.is(-0 + 0, 0) = true
  -0 * 1                = -0 | Object.is(-0 * 1, -0) = true

[4] -0 을 만드는 흔한 자리
  Math.round(-0.4)     -> 보이는 값 0    | -0 인가: true
  Math.trunc(-0.5)     -> 보이는 값 0    | -0 인가: true
  Math.ceil(-0.5)      -> 보이는 값 0    | -0 인가: true
  parseInt('-0')       -> 보이는 값 0    | -0 인가: true
  Number('-0')         -> 보이는 값 0    | -0 인가: true
  -1 * 0               -> 보이는 값 0    | -0 인가: true
  [-0].sort()[0]       -> 보이는 값 0    | -0 인가: true

[5] 세 동등성이 갈리는 자리는 딱 두 칸이다
  compare    NaN vs NaN    0 vs -0
  ===        false         true
  Object.is  true          false
  includes   true          true
  indexOf    false         true
  Set key    true          true
```

**왜 그런가**

- ★★★ **`1 / 0` 은 `Infinity` 인데 `1n / 0n` 은 `RangeError: Division by zero`** 다.
  `Number` 는 IEEE 754 를 따라 **무한대라는 값**을 갖고 있고, `BigInt` 에는 그런 값이 없어 **터질 수밖에** 없다.
  ★ 같은 연산자가 타입에 따라 「값」과 「예외」로 갈린다.
- ★★★ **`Number.isNaN("abc")` 는 거짓이고 `isNaN("abc")` 는 참**이다.
  전역 `isNaN` 은 **먼저 숫자로 바꾼다** — 「이 값이 `NaN` 인가」를 물었는데 「이 값을 숫자로 바꾸면 `NaN` 인가」가 답으로 온다.
  ★ `isNaN("")` 이 거짓인 것도 같은 이유다(`Number("")` 가 `0`).
- ★★★ **`-0` 이 드러나는 자리는 둘** — `Object.is(-0, 0)` 이 거짓, `1 / -0` 이 `-Infinity`.
  **안 드러나는 자리는 셋** — `-0 === 0` 이 참, `String(-0)` 이 `"0"`, `JSON.stringify(-0)` 이 `0`.
  ★ `(-0).toFixed(2)` 도 `"0.00"` 이다 — **문자열로 나가는 모든 길에서 부호가 사라진다.**
- ★★ **`[4]` 의 일곱 줄이 전부 `-0`** 이다. `Math.round(-0.4)`·`Math.trunc(-0.5)`·`Math.ceil(-0.5)`·
  `parseInt("-0")`·`Number("-0")`·`-1 * 0`·`[-0].sort()[0]`.
  ★ **화면에는 전부 `0` 으로 보인다** — 로그로는 절대 못 찾는다.
- ★★ **`[5]` 에서 갈리는 칸은 둘**이다 — `NaN` 과 `±0`.
  `===` 는 `NaN` 에서 거짓·`±0` 에서 참, `Object.is` 는 정반대다.
  `includes`·`Set` 은 **둘 다 참**(SameValueZero)이고 `indexOf` 만 `===` 를 쓴다.
- ★ **`[NaN].indexOf(NaN)` 이 `-1` 인데 `[NaN].includes(NaN)` 이 참**인 것이 그 결과다.
  같은 배열에 두 메서드가 **다른 답**을 준다 — 02번 주제에서 본 갈림이 여기서 값으로 확인된다.

### 4. `BigInt` 를 섞으면 — **전부 막혔는데 문자열 `+` 하나가 뚫려 있다** ★★★ 본체

**출력**

```text
===== node20 js01b-03d-bigint-mix.js (exit=0) =====
[1] 산술은 섞으면 전부 TypeError 다
  1n + 2n                    -> 3n
  1n + 1                     -> TypeError: Cannot mix BigInt and other types, use explicit conversions
  1 + 1n                     -> TypeError: Cannot mix BigInt and other types, use explicit conversions
  1n - 1                     -> TypeError: Cannot mix BigInt and other types, use explicit conversions
  1n * 2                     -> TypeError: Cannot mix BigInt and other types, use explicit conversions
  1n / 2                     -> TypeError: Cannot mix BigInt and other types, use explicit conversions
  1n ** 2                    -> TypeError: Cannot mix BigInt and other types, use explicit conversions
  -1n                        -> -1n
  +1n                        -> TypeError: Cannot convert a BigInt value to a number
  1n | 0                     -> TypeError: Cannot mix BigInt and other types, use explicit conversions
  1n << 1                    -> TypeError: Cannot mix BigInt and other types, use explicit conversions

[2] 그런데 '+' 가 문자열을 만나면 통과한다 — 유일한 구멍이다
  1n + '1'                   -> "11"
  '1' + 1n                   -> "11"
  `${1n}`                    -> "1"
  String(1n)                 -> "1"
  [1n].join()                -> "1"

[3] 비교는 섞어도 된다 — == 와 관계 연산자만
  1n == 1                    -> true
  1n === 1                   -> false
  1n != 1                    -> false
  1n < 2                     -> true
  2n > 1.5                   -> true
  1n == '1'                  -> true
  0n == false                -> true
  Object.is(1n, 1n)          -> true
  new Set([1n,1]).size       -> 2

[4] 다리를 놓는 두 함수와 그 한계
  Number(9007199254740993n)  -> 9007199254740992
  BigInt(1)                  -> 1n
  BigInt(1.5)                -> RangeError: The number 1.5 cannot be converted to a BigInt because it is not an integer
  BigInt('1.5')              -> SyntaxError: Cannot convert 1.5 to a BigInt
  BigInt('0x10')             -> 16n
  BigInt('')                 -> 0n
  BigInt(null)               -> TypeError: Cannot convert null to a BigInt

[5] 다른 곳에서도 막힌다
  Math.abs(-1n)              -> TypeError: Cannot convert a BigInt value to a number
  Math.max(1n, 2n)           -> TypeError: Cannot convert a BigInt value to a number
  JSON.stringify(1n)         -> TypeError: Do not know how to serialize a BigInt
  parseInt('1n')             -> 1
  (1n).toString(2)           -> "1"
  5n / 2n                    -> 2n
  -5n / 2n                   -> -2n
  5n % 3n                    -> 2n
```

**왜 그런가**

- ★★★ **`[1]` 에서 안 터지는 줄은 `-1n`(단항 마이너스)** 이다.
  단항 `-` 는 **부호를 뒤집는** 연산이라 BigInt 에도 정의돼 있고,
  단항 `+` 는 **언제나 `Number` 를 만드는** 연산으로 규정돼 있어 `TypeError: Cannot convert a BigInt value to a number` 다.
  ★ **부호를 바꾸는 것과 숫자로 바꾸는 것이 다른 일**이라는 뜻이다.
- ★★★ **`[2]` 는 전부 통과한다.** `+` 가 문자열을 만나면 이어붙이기로 가고 **그 경로에는 BigInt 금지가 없다.**
  ★ **「구멍」이라 불러도 된다** — 「섞으면 터진다」는 규칙이 여기서만 안 지켜진다.
  02번의 「`+` 만 문자열로 기운다」가 여기서 다시 나온다.
- ★★★ **`1n == 1` 은 참, `1n === 1` 은 거짓**이다. `==` 는 **수학적 값**으로 견주고 `===` 는 **타입부터** 본다.
  ★ **`new Set([1n, 1]).size` 가 `2`** 다 — `Set` 은 SameValueZero 라 타입을 본다.
  ★★ 그래서 **`Map` 키로 `1n` 과 `1` 이 따로 앉는다** — 02번 격자의 `0n` 행이 `0` 행과 같았던 것과 정반대로 보이지만
  **`==` 격자와 `===` 격자가 다른 줄을 쓰는** 것일 뿐이다.
- ★★ **`BigInt(1.5)` 는 `RangeError`, `BigInt("1.5")` 는 `SyntaxError`** 다.
  숫자로 주면 **값의 범위 문제**(정수가 아니다)이고 문자열로 주면 **읽는 문제**(BigInt 리터럴 문법이 아니다)라 경로가 다르다.
- ★★ **`BigInt("")` 는 `0n`** 이고 **`BigInt(null)` 은 `TypeError`** 다.
  빈 문자열은 `Number("")` 와 같은 규칙으로 `0` 이 되고, `null` 은 BigInt 로 갈 다리가 아예 없다.
- ★★ **`JSON.stringify(1n)` 은 `TypeError: Do not know how to serialize a BigInt`** 다.
  ★ 그래서 **큰 ID 는 문자열로 주고받는다** — `BigInt` 를 쓰더라도 **경계에서는 문자열**이다.
- ★ **`5n / 2n` 은 `2n`, `-5n / 2n` 은 `-2n`** 이다. **0 쪽으로 버린다**(C 계열과 같다).
  파이썬의 `//` 는 아래로 버려 `-3` 이 된다 — 언어마다 다르다.

### 5. 반올림 — **함수가 아니라 값이 그렇다** ★★★

**출력**

```text
===== node20 js01b-03e-rounding.js (exit=0) =====
[1] toFixed 가 '내림' 처럼 보이는 자리
n         toFixed(2)  실제로 저장된 값 (toFixed(20))
----------------------------------------------------
1.005     1.00        1.00499999999999989342
```

**왜 그런가**

- ★★★ **`(1.005).toFixed(2)` 가 `1.00` 인 이유는 옆 칸에 있다** — 저장된 값이 `1.00499999999999989342` 다.
  **`1.005` 보다 작으므로 내림이 맞다.** ★ 「`toFixed` 가 틀렸다」가 아니라 **값이 그렇다.**
  ★★ 그래서 함수를 바꿔도 안 고쳐진다 — **같은 블록에 원인을 같이 찍는 것**이 이 절의 설계다.
- ★★★ **`toFixed(0)` 과 `Math.round` 가 음수에서 갈린다.**
  `(-0.5).toFixed(0)` 은 `-1`, `Math.round(-0.5)` 는 `0`.
  `(-2.5).toFixed(0)` 은 `-3`, `Math.round(-2.5)` 는 `-2`.
  ★ **양수만 보면 넷이 전부 같아서** 「둘이 같은 반올림」이라는 결론을 내게 된다 — 그 자리를 놓치는 설계다.
  **`toFixed` 는 0 에서 먼 쪽, `Math.round` 는 큰 쪽**이다.
- ★★★ **`Math.round(0.49999999999999994)` 는 `0`** 이다.
  같은 블록에서 `0.49999999999999994 + 0.5` 가 **`1`** 이라는 것을 함께 찍었다 —
  **`floor(x + 0.5)` 로 구현했다면 `1` 이 나왔을 자리**다.
  ★★ 명세가 이 자리를 **따로 규정**한다(0.5 보다 작고 0 이상이면 `+0`) — **엔진 재량이 아니다.**
- ★★ **`(1.5).toFixed(2) + 1` 은 `"1.501"`** 이다. `toFixed` 가 **문자열**을 돌려주고 `+` 가 이어붙이기로 간다 —
  02번의 규칙이 여기서 물린다.
- ★ **`(1e21).toFixed(2)` 는 `"1e+21"`** 이다. 큰 수에서는 고정 소수 표기를 포기한다.
  **`toFixed(101)` 은 `RangeError`** 이고 인자 범위는 `0`\~`100` 이다.

### 6. 비트 연산 — **64비트 값에 32비트 자를 대는 것** ★★★

**출력**

```text

  1 << 31     = -2147483648
```

**왜 그런가**

- ★★★ **`1e21 | 0` 이 `-559939584`** 인 것은 세 단계다 —
  ① `1e21` 을 `2**32` 로 나눈 나머지를 구하고 ② 그것을 **부호 있는 32비트**로 읽고 ③ 다시 `Number` 로 돌려준다.
  ★ **아무 관계 없어 보이는 수**가 나오는데 **경고가 없다.**
- ★★★ **`1 << 32` 가 `1`** 인 것은 **시프트 횟수도 32 로 나눈 나머지**를 쓰기 때문이다(`32 % 32 === 0`).
  `1 << 33` 이 `2` 인 것도 같다.
  ★ **`1 << -1` 이 `-2147483648`** 인 것은 `-1` 을 **부호 없는 5비트**로 읽으면 `31` 이기 때문이다.
- ★★ **`-1 >>> 0` 은 `4294967295`, `-1 >> 0` 은 `-1`** 이다.
  `>>>` 만 **부호 없는 32비트**로 읽는다 — 그래서 **부호 없는 정수를 얻는 관용구**가 된다.
- ★★ **`BigInt` 에는 `>>>` 가 없다** — `TypeError: BigInts have no unsigned right shift, use >> instead`.
  ★ **자릿수가 무한한 정수에는 「부호 없는 시프트」라는 개념이 성립하지 않는다** — 최상위 비트가 정해져 있지 않기 때문이다.
  ★ 전용 메시지를 따로 둔 것이 **일부러 뺀 것**이라는 증거다.
- ★★★ **30억(`3000000000`)에 넷을 던지면** `| 0` 과 `~~` 는 **`-1294967296`**(음수!),
  `>>> 0` 은 `3000000000`, `Math.trunc` 도 `3000000000` 이다.
  ★ 「빠른 정수 변환」 관용구가 **32비트를 넘는 순간 부호까지 바뀐다.**
- ★ **안전한 쪽은 `Math.trunc`** 다 — 32비트 한계가 없다. `>>> 0` 은 **양수이고 `2**32` 미만일 때만** 맞다.

  파이썬·자바와 나란히 던져 비교하는 것(형제 문서를 링크만 했다) · `Math` 의 나머지 함수들.
- ★ **못 잰 것** — **`BigInt` 의 비용.**
  「BigInt 는 느리다」는 말이 흔하지만 **이 문서는 재지 않았다** — 벤치마크는 머신·부하·JIT 워밍업에 흔들리고,
  이 주제의 다른 모든 수치가 **안 흔들리는 계산**인 것과 성질이 다르다.
  ★★ 한 블록에 **결정적인 것과 흔들리는 것을 섞지 않기** 위해 아예 뺐고, 본문에도 **성능 주장을 한 줄도 적지 않았다.**

**판이 올랐을 때 다시 돌려야 하는 것**

- ★★ **예외 메시지 문구** — 네 블록에 들어 있다.
- ★★ **`console.log(-0)` 의 표시 규칙** — Node 의 것이라 판마다 바뀔 수 있다.
- ★ **`BigInt` 관련 API 가 늘었는지**(`Math` 대응물·`JSON` 지원 등 — 지금은 없다).
- ★ **TC39 Decimal 이 들어왔는지** — 들어오면 이 주제에 절이 하나 는다.
- **수치와 반올림 규칙은 다시 돌릴 필요가 없다** — IEEE 754 와 명세가 비트까지 정해 놓았다.
