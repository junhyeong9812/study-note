Go의 논리는 하나다 — Go는 언어 연구가 아니라 **구글의 빌드·의존 문제에서 나왔고**, 그 출발점 하나가 런타임(고루틴·GC)·툴체인(단일 바이너리)·언어 표면(작은 문법)의 선택을 전부 같은 방향으로 몰았다. 그리고 그 선택들이 이기는 자리가 "인터넷 입력을 받고 호스트를 조작하는 작은 상주 데몬"이고, 지는 자리가 "돈의 불변식을 타입으로 표현하는 도메인 모델"이다.

인용은 go.dev 공식 문서·설계 문서·Go 팀 강연과 런타임 소스 주석 기준이다.

## 한눈에 — 쉽게 말하면

Go는 **연장통 하나에 든 접이식 멀티툴**이다. *(Claude 보강 — 원고에 없는 비유)*

```text
접이식 멀티툴 (Go)                     정밀 공구 세트 (JVM)
+---------------------------+          +---------------------------+
| 한 덩어리로 접혀 온다        |          | 케이스 + 부품 여러 개       |
| 꺼내자마자 바로 쓴다         |          | 조립·워밍업 후 최고 성능    |
| 기능은 딱 필요한 만큼        |          | 표현력·정밀도가 깊다        |
+---------------------------+          +---------------------------+
  → 현장에 들고 가 즉시 쓰기 좋다        → 공방에 두고 오래 쓰기 좋다
  → 세밀한 조각(타입 방어)은 얕다        → 무겁고 워밍업이 필요하다
```

**언어도 똑같은 구조다.** 정적 단일 바이너리는 배포를 지우고, 밀리초 기동은 짧은 프로세스를 싸게 만들고, 2KB 고루틴은 동시 I/O를 설계 문제에서 빼고, 작은 힙에 맞춘 비압축 GC가 상주 비용을 낮춘다. 같은 "작음"이 도메인 모델링에서는 **컴파일 층 방어의 부재**로 돌아온다.

쉽게 말하면, Go의 모든 장점과 청구서가 **"작은 언어"라는 한 결정의 양면**이다.

## 1. 출발점 — Go는 언어 문제가 아니라 빌드 문제에서 나왔다

> 출처: 원고 §⑴·§1

Go는 2007년 9월 구글에서 Robert Griesemer·Rob Pike·Ken Thompson이 새 언어 목표를 스케치하며 시작됐고, 2009년 11월 공개 오픈소스가 됐다([Go FAQ](https://go.dev/doc/faq#history)). FAQ가 밝힌 출발 동기는 취향이 아니라 고통이었다 — "효율적 컴파일·효율적 실행·프로그래밍의 용이함 중 하나를 골라야 했지 셋 다 갖춘 주류 언어는 없었다"([Go FAQ](https://go.dev/doc/faq#creating_a_new_language)).

그 고통의 숫자가 있다. 2007년 구글 빌드 엔지니어들이 주요 바이너리 하나를 계측했더니 "소스 파일 약 2천 개를 이어 붙이면 4.2메가바이트인데, `#include`가 전개되고 나면 8기가바이트 넘게 컴파일러 입력으로 들어갔다 — C++ 소스 1바이트당 2000바이트의 폭증"이었다. 그 빌드는 45분이 걸렸다([Go at Google](https://go.dev/talks/2012/splash.article)).

이 진단이 언어에 그대로 새겨졌다. Go는 **쓰지 않는 import를 경고가 아니라 컴파일 오류로 만든다** — "이것이 어떤 Go 프로그램의 의존 트리도 정확하며 불필요한 간선이 없음을 구성적으로 보장한다." 같은 글은 이 의존 관리가 "Go 컴파일이 C나 C++보다 빠른 단 하나의 가장 큰 이유"라 못박고, 표준 라이브러리조차 "**의존 위생이 코드 재사용을 이긴다**"는 규칙으로 쓰였다고 밝힌다.

그래서 Go의 자기 규정은 겸손하다 — "이 언어는 대규모 소프트웨어 시스템을 쓰고 읽고 디버깅하고 유지보수하는 사람들에 의해, 그들을 위해 설계되었다 … Go는 프로그래밍 언어 연구보다 소프트웨어 공학에 관한 것이다."

**계보도 있다.** FAQ가 조상을 적는다 — C 계열(기본 문법) + Pascal/Modula/Oberon 계열(선언·패키지) + CSP에서 영감받은 Newsqueak·Limbo(동시성)([Go FAQ](https://go.dev/doc/faq#ancestors)). Wirth의 Oberon 계열은 "언어를 일부러 작게 유지한다"는 사조의 원형이고 Griesemer가 바로 그 전통에서 왔으니, Go의 "작게 유지" 본능에는 이름이 있다.

## 2. 고루틴 — 동시성의 단가를 낮춘 결정

> 출처: 원고 §2

동시성이 쉬워 보이는 이유는 문법이 아니라 **단가**다. Go FAQ가 계산을 직접 말한다 — 고루틴은 "스택을 위한 메모리 말고는 부담이 거의 없어 … 그 스택은 겨우 몇 킬로바이트다 … 같은 주소 공간에 수십만 개의 고루틴을 만드는 것이 현실적이다"([Go FAQ](https://go.dev/doc/faq#goroutines)).

런타임은 세 글자로 요약된다. `runtime/proc.go` 주석이 정의를 준다 — "**G는 고루틴. M은 워커 스레드(machine). P는 프로세서**, Go 코드를 실행하는 데 필요한 자원." P의 개수는 `GOMAXPROCS`이고, 각 P가 실행 큐를 따로 가지며, 자기 큐가 비면 "무작위 희생자(다른 P)의 실행 가능한 고루틴 절반을 훔친다"([Scalable Go Scheduler Design Doc](https://go.dev/s/go11sched), 2012).

싼 스택의 정체는 "작게 시작해서 자란다"이다. 최소값은 소스에 `stackMin = 2048`로 박혀 있고, "스택 한계에 도달하면 더 큰 스택을 새로 할당하고 활성 프레임을 전부 복사한 뒤 포인터들을 갱신한다"([Go 1.4 릴리스 노트](https://go.dev/doc/go1.4)). OS 스레드와의 차이가 여기서 갈린다 — 리눅스 배포판 기본 스레드 스택은 8MB다(`ulimit -s` = 8192 `[측정]`). 2KB에서 자라는 단위와 처음부터 8MB를 예약하는 단위는 같은 밀도로 만들 수 없다.

```go
// 고루틴 10만 개를 띄우고 프로세스 전체 상주 메모리를 잰다
for i := 0; i < 100000; i++ {
    go func() { defer wg.Done(); <-stop }()
}
```

`[측정]` 위 프로그램은 고루틴 100,001개를 동시에 살려 두고 최대 상주 메모리(RSS) **262MB**를 썼다 — 고루틴 하나당 약 2.6KB다. 같은 수의 OS 스레드는 배포판 기본 스택만으로 800GB의 주소 공간을 요구한다.

블로킹 I/O가 스레드를 잡아먹지 않는 것도 런타임 안에 있다. 네트워크 대기는 내장 netpoller(epoll·kqueue 추상화)가 받고, 대기 중 고루틴은 park되어 M을 놓아준다. 계산 루프에 갇힌 고루틴은 Go 1.14부터 **신호 기반 비동기 선점**으로 끊는다([Go 1.14 릴리스 노트](https://go.dev/doc/go1.14)). `GOMAXPROCS`는 Go 1.25부터 **리눅스에서 cgroup CPU 대역폭 제한을 반영**한다([Go 1.25 릴리스 노트](https://go.dev/doc/go1.25)) — 쿠버네티스에서 노드 코어 수만큼 P를 만들어 스로틀링을 자초하던 함정이 런타임 기본값으로 닫혔다.

## 3. GC — 지연을 사고 처리량을 팔았다

> 출처: 원고 §3

Go의 GC는 자기 정체를 소스 주석에 한 문장으로 적는다 — "**쓰기 배리어를 쓰는 동시 마크-스윕이며, 세대별이 아니고 압축하지 않는다**"([runtime/mgc.go](https://github.com/golang/go/blob/master/src/runtime/mgc.go)). 이 한 줄에 이 절이 다 들어 있다.

지연 개선의 궤적은 Go 팀이 공개해 두었다. 정지 시간이 300~400ms(1.5 이전) → 30~40ms(1.5) → 4~5ms(1.6) → **1ms 미만**(1.8)으로 세 자릿수 줄었다([Getting to Go](https://go.dev/blog/ismmkeynote)). 같은 글은 왜 99%ile SLO로 부족한지도 설명한다 — 세션 하나가 요청 100번을 만들면 "GC 사이클의 99%가 10ms 미만"이어도 전체 세션이 일관되게 10ms 미만인 사용자는 37%뿐이다.

압축하지 않기로 한 이유가 언어 성격과 붙어 있다. "Go는 … C 계열 시스템 언어의 전통을 따르는 **값 지향 언어**"라 내부 포인터를 가질 수 있어 객체를 옮기지 않는다. 세대별로 가지 않은 이유는 더 재미있다 — "젊은 객체들이 **스택 위에서 태어나 스택 위에서 죽는다**." 값을 그대로 넘기는 호출 관습 덕분에 이스케이프 분석이 지역적으로 끝나고, 세대별 GC가 잡아 줬을 객체들을 컴파일러가 먼저 스택에 붙여 버린다.

작은 힙에서 사실상 무비용인 이유는 비용 모델에 있다. 공식 가이드는 비용을 "사이클당 고정 비용 + **살아 있는 힙 크기에 비례하는 한계 비용**"으로 모델링한다 — 즉 **비용은 할당량이 아니라 생존 힙에 비례**한다([Go GC Guide](https://go.dev/doc/gc-guide)). 상주 힙이 수 MB인 데몬은 아무리 많이 할당해도 마킹할 대상이 그 수 MB뿐이다.

```text
[측정] 생존 힙 16.5MB · 5초간 인위적 할당 폭주
GC 사이클 296회 · STW 중앙값 93.8µs · 최대 916µs
STW 총합 32.7ms = 벽시계의 0.65%
```

`[측정]` 현실에 없는 할당률(5초 296사이클)의 합성 부하인데도 정지 중앙값이 100마이크로초 아래이고 총 정지가 1%를 넘지 않는다. 정직하게 번역하면 **"정지가 마이크로초 단위이고 총량이 1% 미만이라 배포·SSH 지연 예산에서 잡음"**이다.

**JVM과의 설계 트레이드는 대칭이다.** 세 컬렉터를 같은 축에서 나란히 놓는다.

| 축 | Go GC | ZGC (JDK 21+) | G1 (JVM 기본) |
|---|---|---|---|
| 정지 목표 | 사이클당 500µs | 1ms 미만 | 200ms |
| 객체 이동 | 하지 않음 | 이동(재배치) | 이동(evacuation) |
| 배리어 | 쓰기 배리어, GC 중에만 | 로드·스토어 배리어 상시 | 쓰기 배리어 |
| 세대 구분 | 없음 | 있음(JDK 21부터) | 있음 |
| 정지와 힙 크기 | 생존 힙에 비례해 마킹 증가 | 힙 크기와 무관 | 목표에 맞춰 조절 |

차이를 한 문장으로 줄이면 이렇다 — **ZGC는 객체를 옮기기 위해 모든 참조 읽기에 로드 배리어를 상시 지불하고, Go는 옮기지 않는 대신 GC 중에만 쓰기 배리어를 켠다**([JEP 439](https://openjdk.org/jeps/439); [HotSpot GC Tuning Guide, Java SE 21](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)). 은행 코어처럼 힙이 크고 오래 도는 프로세스에서 ZGC가 이기고, 힙이 수십 MB인 상주 데몬에서 Go가 이기는 것은 어느 쪽이 우수해서가 아니라 **두 컬렉터가 다른 힙을 겨냥해 설계되었기 때문**이다.

## 4. 단일 바이너리 — 링커가 배포 문제를 삼킨다

> 출처: 원고 §4

배포 단순성은 문화가 아니라 링커의 기본값이다. Go FAQ의 한 문장이 이 절을 덮는다 — "`gc` 툴체인의 링커는 **기본적으로 정적 링크된 바이너리를 만든다** … 모든 Go 바이너리는 Go 런타임을 포함한다"([Go FAQ](https://go.dev/doc/faq)).

```text
[측정] fmt.Println("hello") 한 줄 프로그램 (Go 1.24.5, CGO_ENABLED=0)
크기: 2,204,862 바이트 (-ldflags="-s -w" 시 1,429,688)
file: ELF 64-bit ... statically linked
ldd:  동적 실행 파일이 아닙니다
```

`[측정]` 같은 FAQ가 "정적 링크한 C의 hello world가 리눅스에서 약 750kB"라 비교선을 주는데, Go가 세 배쯤 되는 이유가 "런타임을 포함하며"다. 스케줄러·GC·할당자를 매 바이너리가 들고 다니는 것이 정적 배포의 대가다.

**cgo가 켜지면 이 성질이 깨진다**는 것이 실무에서 가장 자주 어긋나는 지점이다. cgo 패키지가 끼면 외부 링킹을 쓰고, 그 산출물은 "동적 실행 파일"이다. `net.LookupHost`를 부르는 프로그램은 `CGO_ENABLED=1`에서 `libc.so.6`에 동적 링크되고 `CGO_ENABLED=0`에서만 정적으로 나온다. 정적 바이너리가 필요하면 `CGO_ENABLED=0`을 명시하는 것이 실무의 정답이고, 다행히 **크로스컴파일할 때는 cgo가 기본적으로 꺼진다**.

```text
[측정] go tool dist list | wc -l          → 48   (Go 1.24.5)
       GOOS=darwin GOARCH=arm64 go build  → Mach-O 64-bit arm64 executable
```

`[측정]` 리눅스 x86-64 한 대에서, 크로스 툴체인을 하나도 설치하지 않고, `go build` 한 줄로 macOS ARM 바이너리가 나온다. "여러 서버 배포 = scp 한 번"이 성립하는 기술적 근거가 이것이다.

컨테이너 쪽 귀결은 Docker 자신의 문서가 보여 준다 — 멀티스테이지 빌드 대표 예제가 **Go로 빌드해 `FROM scratch`에 바이너리 하나만 복사하는 것**이다([Docker 멀티스테이지 빌드](https://docs.docker.com/build/building/multi-stage/)). 최종 이미지에 베이스 OS도 패키지 매니저도 셸도 없으니 공격 표면이 바이너리 하나로 줄어든다. Prometheus 소개 문서가 이 인과를 그대로 적는다 — "대부분의 Prometheus 구성요소는 Go로 작성되어 **정적 바이너리로 빌드하고 배포하기 쉽다**"([Prometheus Overview](https://prometheus.io/docs/introduction/overview/)).

## 5. 기동 — 초기화할 런타임이 거의 없다

> 출처: 원고 §5

기동이 빠른 이유는 최적화가 아니라 **할 일이 적어서**다. Go 명세가 프로그램 시작을 "프로그램을 초기화한 다음 `main`을 호출"로만 규정하고, 초기화도 "**단일 고루틴에서 순차적으로**" 일어난다([Go 명세](https://go.dev/ref/spec#Program_execution)). 클래스 로딩도, 바이트코드 검증도, JIT 워밍업도 없다. 기계어는 이미 파일 안에 있다.

```text
[측정] hello world 프로세스 기동 (각 20회 평균, 캐시 워밍 후)
Go 1.24.5 정적 바이너리 :  4.5 ms
Temurin JDK 21.0.5 java :  78.2 ms
```

`[측정]` 약 17배다. 이 비교는 **JVM에 유리한 조건**이다 — 프레임워크 없는 맨 JVM에 클래스 파일 한 장이고, Spring Boot 애플리케이션 기동은 이보다 한 자릿수 위다.

JVM 쪽이 이것을 문제로 인정하고 있다는 사실이 오히려 좋은 근거다 — Project Leyden의 목표가 "**자바 프로그램의 기동 시간·최고 성능까지의 시간·풋프린트 개선**"이고([Project Leyden](https://openjdk.org/projects/leyden/)), JEP가 비용의 정체를 적는다 — "JVM은 디스크에서 수백 개의 JAR을 스캔하고 수천 개의 클래스 파일을 읽어 파싱한다"([JEP 483](https://openjdk.org/jeps/483)). 정량 상한선은 Quarkus 벤더 수치가 준다 — Thorntail 8,764ms · Quarkus JVM 1,629ms · **Quarkus 네이티브 18ms**([Quarkus Runtime Performance](https://quarkus.io/blog/runtime-performance/), 2019, GraalVM 네이티브 측정이지 Go 측정이 아님).

**같은 수치가 한쪽에서는 결정적이고 다른 쪽에서는 무의미하다.** 호출마다 새로 뜨는 배포 프로세스(SSH 강제 명령 같은)에서는 78ms와 4.5ms의 차이가 호출 수만큼 곱해진다. 반대로 은행 코어는 한 번 떠서 몇 주를 도는 프로세스라 기동이 상각되고 JIT가 뜨거운 경로를 최적화할 시간을 번다 — 이것이 층별로 다른 언어를 쓰는 이유의 정량적 형태다.

## 6. 의도적 단순함 — 제네릭과 에러, 찬반을 그대로

> 출처: 원고 §6

Go의 기능 부재는 대부분 사고가 아니라 결정이다. Pike의 슬라이드가 원칙을 압축한다 — "기능은 복잡도를 더한다. 우리는 단순함을 원한다 … **가독성이 최우선이다**"([Simplicity is Complicated](https://go.dev/talks/2015/simplicity-is-complicated.slide), 2015).

**제네릭은 13년이 걸렸다.** 2009년 공개 후 24시간이 채 지나기 전에 첫 요청이 달렸고 "3년간 설문에서 제네릭 부재는 언제나 상위 세 문제 중 하나"였는데도([Why Generics?](https://go.dev/blog/why-generics), 2019), Ian Lance Taylor의 판정 기준은 "**Go가 여전히 Go처럼 느껴질 때만** 할 가치가 있다"였다. Go 1.18(2022)에서 나왔을 때 릴리스 노트가 이례적 경고를 붙였다 — "그 믿음을 실세계 경험으로 뒷받침할 수 없다 … **프로덕션에 제네릭 코드를 배포할 때는 적절히 주의하시라**"([Go 1.18 릴리스 노트](https://go.dev/doc/go1.18)). 가장 큰 구멍은 **메서드에 타입 파라미터를 달 수 없다**는 영구 제약이다.

**에러는 값으로 반환한다.** 예외를 두지 않은 이유는 설계 문서에 있다 — "예외를 제어 구조에 결합하면 코드가 뒤엉킨다 … 평범한 오류까지 예외적인 것으로 이름 붙이도록 부추긴다"([Go FAQ](https://go.dev/doc/faq#exceptions)). 찬반이 정말로 갈린다는 것은 Go 팀 자신이 인정했다 — 2025년 6월 포스트가 **에러 처리 문법 제안을 전부 닫는다**고 선언한다 — "우리는 문제에 대한 공유된 이해도 갖지 못했고, 애초에 문제가 있다는 데에도 모두가 동의하지 않는다"([On syntactic support for error handling](https://go.dev/blog/error-syntax)). 2024년 설문에서 **에러 처리의 장황함을 최대 난점으로 꼽은 응답이 13%**였다([Go Developer Survey 2024 H1](https://go.dev/blog/survey2024-h1-results)).

그 글의 가장 날카로운 논증은 제네릭과의 비대칭이다 — "오늘날 누구도 제네릭을 쓰도록 강요받지 않는다. 반대로 에러 처리 새 문법이 추가되면 **사실상 모두가 그것을 쓰기 시작해야 한다.**"

정리하면 이 축의 손익은 이렇다 — 얻는 것은 **제어 흐름이 코드에 그대로 보인다**는 것(감사할 표면이 작다), 잃는 것은 분량과 **강제성의 부재**(반환된 에러를 무시해도 컴파일러는 막지 않고, `errcheck` 린터를 CI에 걸어야 강제가 된다).

## 7. 인프라 생태계 — 왜 전부 Go인가

> 출처: 원고 §7

이 관찰은 인상이 아니라 셀 수 있다. Go 팀은 "CNCF 프로젝트의 75% 이상이 Go"라 주장하고([Go for Cloud & Network Services](https://go.dev/solutions/cloud)), 원고 저자가 CNCF graduated 38개를 GitHub API로 전수 조회한 결과 **28개가 Go(73.7%)**로 나와 부합했다 `[측정]`. Docker/Moby·Kubernetes·Prometheus·etcd·Terraform·Consul·Vault·containerd·CoreDNS·Traefik·CockroachDB — 열한 개 전부 주 언어가 Go다 `[측정]`. 리포 생성 시점이 2012~2014에 몰려 있다.

무엇이 이 수렴을 만들었는지는 Go 팀 설문의 관찰 그대로다 — "Go에 내장된 HTTP 서버와 동시성 프리미티브, 손쉬운 크로스컴파일, 단일 바이너리 배포가 이런 애플리케이션에 좋은 선택으로 만든다"([Go Developer Survey 2024 H1](https://go.dev/blog/survey2024-h1-results)). 앞 네 절이 각각 그 항목이다. 2025년 설문에서 응답자의 **96%가 컨테이너 포함 리눅스 시스템에 배포**한다고 답했다([2025 Go Developer Survey](https://go.dev/blog/survey2025)).

**[실무 의견]** 두 가지를 더 얹어야 정직하다 — **시기**(Go 1.0이 2012년, 컨테이너 물결이 2013~2015라 마침 성숙한 선택지가 하나 있었다)와 **네트워크 효과**(쿠버네티스·etcd·Prometheus 클라이언트가 Go 일급이라 새 도구도 Go로 쓰는 편이 마찰이 적다). 성질만으로 설명되는 수렴이 아니라는 뜻이고, 그래서 "인프라니까 Go"는 그 자체로 근거가 아니다.

**[불확실]** 널리 회자되는 두 일화 — Docker가 Go를 고른 이유의 공식 문서, 쿠버네티스가 처음 자바로 시제품을 만들었다는 이야기 — 는 원 출처를 확인하지 못했다. 확인되지 않은 서사이므로 근거로 쓰지 않는다.

## 8. 비용 — 표현력이 얕고, 그 얕음이 도메인에서 비싸다

> 출처: 원고 §8

앞 일곱 절의 장점은 전부 "작은 언어"에서 나왔고, 이 절은 같은 원인의 청구서다. 결론을 먼저 말하면 — **Go에는 "불법 상태를 표현 불가능하게 만드는" 도구가 거의 없다.**

- **합타입(sum type)이 없다.** FAQ가 결정을 기록한다 — "인터페이스와 혼란스럽게 겹치기 때문에 넣지 않기로 했다"([Go FAQ](https://go.dev/doc/faq#variant_types)). 어떤 결제 승인 애그리게이트는 상태 8종에 허용 전이 16건·금지 전이 22건을 갖는데, `sealed` + `when`이 있는 언어에서는 **상태를 추가하면 처리하지 않은 분기가 컴파일 오류**가 된다. Go에서 같은 것을 하려면 완결성을 `default: panic(...)`이나 별도 린터에 맡겨야 한다. "빠뜨린 상태 분기"는 은행 코드에서 조용한 실패의 전형적 입구다.
- **열거형도 없다.** `iota`가 만드는 것은 이름 붙은 정수이고, 범위를 벗어난 값이 그 타입에 대입되는 것을 컴파일러가 막지 않는다([golang/go#19814](https://github.com/golang/go/issues/19814)).
- **불변도 없다.** `const`는 기본 타입에만 걸리고 구조체·슬라이스·맵에는 안 걸린다. 불변 한정자 제안은 2026년 4월 기각됐다([golang/go#27975](https://github.com/golang/go/issues/27975)).
- **제로값이 항상 유효한 값처럼 보인다.** `Money{}`는 컴파일도 실행도 되지만 통화가 빈 문자열인 금액이며, **생성자를 반드시 거치게 강제할 방법이 언어에 없다**. nil 인터페이스 함정까지 있어, `nil` 포인터를 담은 인터페이스 값은 그 자체로는 `nil`이 아니다([Go FAQ](https://go.dev/doc/faq#nil_error)).

사용자들이 정확히 이 지점을 요구하고 있다 — 2024년 설문의 가장 흔한 요청이 "enum, 옵션 타입, 합타입"이었다([Go Developer Survey 2024 H1](https://go.dev/blog/survey2024-h1-results)).

**반대 방향의 정직함이 이 절의 결론이다.** 위 결핍들은 인프라 층에서는 대체로 비용이 아니다 — 배포·감시 도구가 다루는 것은 컨테이너·프로세스·파일·락 행이고, 표현해야 할 도메인 불변식이 없기 때문이다. 그래서 되돌림 신호가 언어가 아니라 경계에 걸린다 — **인프라 도구가 도메인 판정을 담기 시작하면**, 그때 잘못된 것은 언어 선택이 아니라 무엇이 그 도구로 새어 들어갔는가다.

## 9. 정리 — 층별로 다른 것이 맞다

> 출처: 원고 §9

Go를 한 문장으로 줄이면 "대규모 팀의 빌드·의존 문제에서 출발해, 그 답을 런타임과 툴체인에 넣고 언어 표면은 일부러 작게 남긴 언어"다. 그 결과가 서로 보강한다 — 정적 단일 바이너리가 배포를 지우고, 밀리초 기동이 짧은 프로세스를 싸게 만들고, 2KB 고루틴이 동시 I/O를 설계 문제에서 빼고, 작은 힙에 맞춘 비압축 GC가 상주 비용을 낮추고, 작은 문법이 감사할 표면을 줄인다. 같은 "작음"이 도메인 모델링에서는 컴파일 층 방어의 부재로 돌아온다.

그래서 층별 배치는 어느 언어가 우수한가의 결론이 아니다. 돈의 불변식을 타입으로 막아야 하는 층에는 `sealed`·null 안전·값 타입이 있는 언어(Kotlin 등)가 서고, 인터넷 입력을 받고 호스트를 조작하며 가볍게 상주해야 하는 층에는 Go가 선다. **두 판단은 같은 기준의 두 결과다** — 각 층의 실패 모드를 무엇이 막는가.

---

## 핵심 문장

- **Go의 모든 장점과 청구서는 "작은 언어"라는 한 결정의 양면이다.**
- **Go는 언어 문제가 아니라 빌드·의존 문제에서 나왔다** — 쓰지 않는 import가 컴파일 오류인 이유가 그것이다.
- **GC 비용은 할당량이 아니라 생존 힙에 비례한다** — 상주 힙이 수 MB인 데몬에서 GC가 사실상 무비용인 근거.
- **"Go는 정적 바이너리를 만든다"는 조건부 명제다** — cgo가 켜지면 깨진다.
- **같은 기동 수치가 짧은 프로세스에선 결정적이고 오래 도는 코어에선 무의미하다** — 층별로 다른 언어를 쓰는 정량적 이유.
- **인프라 도구가 도메인 판정을 담기 시작하면, 잘못된 것은 언어가 아니라 무엇이 새어 들어갔는가다.**

## 용어 풀이

- **고루틴(Goroutine)** — Go 런타임이 관리하는 경량 실행 단위. 스택이 2KB에서 시작해 필요한 만큼 자란다. OS 스레드보다 두세 자릿수 싸다.
- **G-M-P 모델** — G(고루틴)·M(워커 스레드)·P(프로세서 자원). P 개수는 `GOMAXPROCS`이고, 각 P가 실행 큐를 가지며 비면 다른 P의 절반을 훔친다(work stealing).
- **netpoller** — 네트워크 대기를 받는 런타임 내장 장치(epoll·kqueue 추상화). 블로킹 I/O가 OS 스레드를 잡아먹지 않게 한다.
- **비압축 GC(Non-moving GC)** — 객체를 옮기지 않는 가비지 컬렉터. Go는 값 지향·내부 포인터 때문에 이 방식을 택했다.
- **쓰기 배리어(Write Barrier)** — 동시 GC가 마킹 중 포인터 변경을 추적하려고 쓰기에 끼우는 코드. Go는 GC 중에만 켜고, ZGC의 로드 배리어는 상시 켜져 있다.
- **STW(Stop-The-World)** — GC가 애플리케이션 스레드를 전부 멈추는 구간. Go는 마이크로초 단위다.
- **cgo** — Go에서 C 코드를 호출하는 다리. 켜지면 외부 링킹이 되어 정적 바이너리 성질이 깨진다.
- **크로스컴파일(Cross-compilation)** — 한 기계에서 다른 OS·아키텍처용 바이너리를 만드는 것. `GOOS`·`GOARCH` 두 환경변수로 한다.
- **합타입(Sum Type)** — "이것 또는 저것"을 타입으로 표현하는 것(대수적 타입). Go에는 없어 상태 분기 누락을 컴파일러가 못 잡는다.
- **제로값(Zero Value)** — 초기화하지 않은 변수에 채워지는 기본값(숫자 0, 문자열 "", 포인터 nil). 유효한 값처럼 보이는 것이 함정.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **CSP(Communicating Sequential Processes).** Tony Hoare가 정식화한 동시성 모델로, "메모리를 공유해 통신하지 말고, 통신해서 메모리를 공유하라"가 Go의 표어다. 채널(`chan`)이 그 구현이고, 고루틴 + 채널이 §2의 스케줄러 위에서 돈다.
- **이스케이프 분석(Escape Analysis).** 컴파일러가 "이 값이 함수 밖으로 새는가"를 분석해 새지 않으면 힙 대신 스택에 붙이는 최적화. §3에서 세대별 GC가 필요 없다고 한 근거 — 젊은 객체가 스택에서 나고 죽는 것은 이 분석 덕이다.
- **work stealing(작업 훔치기).** 자기 큐가 빈 P가 다른 P의 큐 절반을 가져오는 부하 분산 방식. 전역 락 하나로 스케줄링을 보호하던 초기 구조가 8코어에서 CPU 70%를 못 넘긴 것이 이 설계의 출발점이었다.
- **Go 1 호환성 약속.** "Go 1용으로 쓴 코드는 그 명세 수명 동안 그대로 컴파일·실행된다"([Go 1 호환성](https://go.dev/doc/go1compat)). §6의 "기능을 안 더하는 쪽에 증명 책임을 지운다"는 태도의 제도적 형태다. 기능을 늦게, 신중히 넣는 이유가 이 약속을 지키기 위해서이기도 하다.
