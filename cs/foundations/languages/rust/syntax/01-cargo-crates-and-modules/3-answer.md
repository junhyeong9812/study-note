# rust/syntax/01 — `cargo` 프로젝트 구조·`main`·크레이트·모듈 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 모든 출력·에러는 **`rustc 1.92.0` · `cargo 1.92.0`(x86_64-unknown-linux-gnu)에서 실제로 돌려 얻은 것**이다.\
> 에러 메시지는 `cargo` 출력을 그대로 옮겼다. **단 하나만 손댔다** — `note:` 줄에 박히는 **절대 경로를 `src/…` 로 줄였다**(그 줄만).\
> 에디션은 이 문서 전체가 **2021**이다(2번·8번의 에디션 실험만 예외로 명시한다).

## 정답

### 1. `cargo new` 직후의 폴더에 무엇이 있는가

**출력**

```text
$ cargo new hello
    Creating binary (application) `hello` package
note: see more `Cargo.toml` keys and their definitions at https://doc.rust-lang.org/cargo/reference/manifest.html

$ find hello -type f -not -path '*/.git/*' | sort
hello/.gitignore
hello/Cargo.toml
hello/src/main.rs

$ cat hello/Cargo.toml
[package]
name = "hello"
version = "0.1.0"
edition = "2024"

[dependencies]

$ cat hello/.gitignore
/target
```

**왜 그런가**

- 만들어진 것은 **`.git/` · `.gitignore` · `Cargo.toml` · `src/main.rs`** 넷이다.\
  `cargo new` 는 git 저장소까지 만든다(`--vcs none` 으로 끌 수 있다).
- **`Cargo.lock` 은 이 시점에 없다.** `target/` 도 없다.

```text
cargo new 직후                  cargo build / cargo run 이후
  Cargo.toml                      Cargo.toml
  .gitignore                      .gitignore
  src/main.rs                     src/main.rs
  .git/                           .git/
                                  Cargo.lock    <- 여기서 생긴다
                                  target/       <- 여기서 생긴다
```

- 실행으로 확인한 `Cargo.lock` 의 내용 — 의존성이 0개인데도 자기 자신이 들어간다.

```text
# This file is automatically @generated by Cargo.
# It is not intended for manual editing.
version = 4

[[package]]
name = "hello"
version = "0.1.0"
```

- `edition` 값은 **`"2024"`** 다. `cargo 1.92.0` 기준이며 **cargo 버전에 달린 값**이다(8번 참조).

> **매니페스트(manifest)** — 사람이 적는 패키지 설명서, 곧 `Cargo.toml`.\
> 예: 이름·버전·에디션·의존성이 여기 적힌다. `Cargo.lock` 은 반대로 **cargo 가 적는** 파일이다.

### 2. `mod greet;` 는 어느 파일을 찾는가

**출력** — `src/greet.rs` 도 `src/greet/mod.rs` 도 없을 때

```text
error[E0583]: file not found for module `greet`
 --> src/main.rs:1:1
  |
1 | mod greet;
  | ^^^^^^^^^^
  |
  = help: to create the module `greet`, create file "src/greet.rs" or "src/greet/mod.rs"
  = note: if there is a `mod greet` elsewhere in the crate already, import it with `use crate::...` instead

For more information about this error, try `rustc --explain E0583`.
```

`rustc --explain E0583` 이 말하는 것(공식 설명 원문):

> Please be sure that a file corresponding to the module exists. If you
> want to use a module named `file_that_doesnt_exist`, you need to have a file
> named `file_that_doesnt_exist.rs` or `file_that_doesnt_exist/mod.rs` in the
> same directory.

**출력** — 둘 다 만들었을 때

```text
error[E0761]: file for module `greet` found at both "src/greet.rs" and "src/greet/mod.rs"
 --> src/main.rs:1:1
  |
1 | mod greet;
  | ^^^^^^^^^^
  |
  = help: delete or rename one of them to remove the ambiguity

For more information about this error, try `rustc --explain E0761`.
```

`rustc --explain E0761` 의 첫 줄:

> Multiple candidate files were found for an out-of-line module.

**왜 그런가**

- 후보는 **정확히 둘**이고, 에러 메시지가 그 둘을 문자 그대로 말해 준다.\
  **외울 필요가 없다 — 던지면 컴파일러가 알려 준다.**
- 하나만 있으면 그 파일이 모듈 본문이 된다. 둘 다 있으면 고르지 않고 **거부**한다(E0761).
- `src/greet.rs` 안의 `pub mod polite;` 는 **`src/greet/polite.rs`** 를 본다.\
  즉 `greet.rs` 파일과 `greet/` 폴더가 **나란히** 있는 배치가 된다.

```text
src/
  main.rs            mod greet;          -> src/greet.rs
  greet.rs           pub mod polite;     -> src/greet/polite.rs
  greet/
    polite.rs
```

> **아웃오브라인 모듈(out-of-line module)** — 본문이 다른 파일에 있는 모듈. `mod greet;` 처럼 세미콜론으로 끝난다.\
> 예: `mod greet { ... }` 는 인라인 모듈이라 파일 탐색이 아예 안 일어난다.

### 3. 이 프로젝트는 빌드에 성공하는가

**출력**

```text
$ ls src
greet  greet.rs  main.rs  orphan.rs

$ cargo build
   Compiling q v0.1.0 (<프로젝트>)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.09s

$ cargo run -q
hi
```

**왜 그런가**

- **성공한다.** 경고조차 **한 줄도 없다.**
- `orphan.rs` 는 문법이 통째로 깨졌지만 컴파일러가 **그 파일을 열어 보지도 않았다.**

```text
컴파일러가 실제로 읽은 것            읽지 않은 것
+--------------------------+       +------------------+
| src/main.rs   (루트)      |       | src/orphan.rs    |
|   mod greet;             |       |                  |
| src/greet.rs             |       | mod 로 아무도     |
|   pub mod polite;        |       | 이름을 부르지     |
| src/greet/polite.rs      |       | 않았다           |
+--------------------------+       +------------------+
```

- 그래서 **Rust 에는 소스 파일 자동 수집이 없다.** 폴더에 넣는 것만으로는 아무 일도 안 일어난다.
- 반대 방향의 사고가 훨씬 흔하다 — **"파일을 만들었는데 왜 안 불리지?"** 는 `mod 파일이름;` 한 줄을 안 쓴 것이다.
- 이 조합이 위험한 이유: **침묵**이다. 에러도 경고도 없어서 「빌드가 됐으니 내 파일도 들어갔겠지」로 읽힌다.\
  들어갔는지 확인하려면 **그 모듈의 것을 실제로 불러 본다.**

### 4. 이 프로그램의 출력을 예측하라

**출력**

```text
greet::hello
  greet::polite::hello
  crate::top
  greet::polite::hello
  crate::top
```

**왜 그런가**

- **다섯 줄**이다. `greet::hello` 안에서 셋이 찍히고, `main` 으로 돌아와 하나가 더 찍힌다.

```text
main
  |
  +-- greet::hello()
  |      +-- println!         -> "greet::hello"
  |      +-- polite::hello()  -> "  greet::polite::hello"
  |      +-- super::top()     -> "  crate::top"
  |      +-- self::polite::hello() -> "  greet::polite::hello"
  |
  +-- crate::top()            -> "  crate::top"
```

- `greet.rs` 안에서 `super::` 는 **크레이트 루트**(`main.rs`)다. `greet` 의 부모가 루트이기 때문이다.
- `self::polite::hello()` 와 `polite::hello()` 는 **같은 것**이다 — 같은 줄이 두 번 찍힌 것이 그 증거다.\
  `self::` 는 "지금 이 모듈 기준"을 명시할 뿐이고, 경로 앞에 아무것도 안 붙이면 어차피 그 기준이다.
- `crate::` 는 **모듈 트리의 루트**를 기준으로 한다. 파일이 어디 있든 상관없다.

```text
crate  (= src/main.rs)
  +-- top()                     crate::top
  +-- greet                     crate::greet
        +-- hello()             crate::greet::hello
        +-- polite
              +-- hello()       crate::greet::polite::hello
```

> **모듈 트리(module tree)** — `mod` 로 만들어진 이름들의 계층. **파일 트리와 닮았지만 같은 것이 아니다.**\
> 예: 인라인 `mod` 를 쓰면 파일은 하나인데 모듈 트리는 여러 층이 된다.

### 5. `fn main` 이 `Result` 를 돌려주면

**출력**

```text
$ ./ex
n = 42
Error: ParseIntError { kind: InvalidDigit }

$ ./ex 2>/dev/null          # 표준 출력만
n = 42

$ ./ex 2>&1 >/dev/null      # 표준 에러만
Error: ParseIntError { kind: InvalidDigit }

$ ./ex; echo $?
...
1
```

**왜 그런가**

- `n = 42` 는 **표준 출력**, `Error: …` 는 **표준 에러**다. 종료 코드는 **1**이다.
- 찍히는 형식은 **`Debug`**(`{:?}`)다.\
  근거는 출력 그 자체다 — `ParseIntError { kind: InvalidDigit }` 는 구조체 필드까지 드러난 `Debug` 형식이고,\
  같은 타입의 `Display` 는 `invalid digit found in string` 이다.
- 그래서 **사용자에게 보여 줄 메시지를 `main` 의 `Err` 로 흘리면 개발자용 형식이 그대로 나간다.**

```text
fn main() -> Result<(), E>

  Ok(())  --> 종료 코드 0, 아무것도 안 찍는다
  Err(e)  --> 표준 에러에 "Error: {e:?}"  +  종료 코드 1
```

`fn main() -> i32 { 7 }` 은 **컴파일되지 않는다.**

```text
error[E0277]: `main` has invalid return type `i32`
 --> ex.rs:1:14
  |
1 | fn main() -> i32 {
  |              ^^^ `main` can only return types that implement `Termination`
  |
  = help: consider using `()`, or a `Result`
```

- 요구되는 트레이트 이름은 **`Termination`** 이다.
- `Box<dyn Error>` 로 받아도 같다 — 실측으로 `Err("일부러 낸 실패".into())` 를 돌려주니\
  `Error: "일부러 낸 실패"` 가 찍히고 종료 코드가 1이었다(따옴표가 붙은 것이 `Debug` 형식의 증거다).

### 6. 크레이트 경계는 어디인가

**출력**

```text
warning: function `thrice` is never used
 --> src/lib.rs:2:15
  |
2 | pub(crate) fn thrice(n: i32) -> i32 { n * 3 }
  |               ^^^^^^
  |
  = note: `#[warn(dead_code)]` (part of `#[warn(unused)]`) on by default

warning: `both` (lib) generated 1 warning
error[E0603]: function `thrice` is private
 --> src/main.rs:3:26
  |
3 |     println!("{}", both::thrice(14));
  |                          ^^^^^^ private function
  |
note: the function `thrice` is defined here
 --> src/lib.rs:2:1
  |
2 | pub(crate) fn thrice(n: i32) -> i32 { n * 3 }
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

For more information about this error, try `rustc --explain E0603`.
```

**왜 그런가**

- 크레이트는 **둘**이다 — 라이브러리 크레이트(`src/lib.rs`)와 바이너리 크레이트(`src/main.rs`).\
  패키지는 하나(`Cargo.toml` 하나)다.

```text
패키지 both (Cargo.toml 하나)
   |
   +-- 라이브러리 크레이트  src/lib.rs   --> libboth.rlib
   |        pub fn twice          밖에서 보인다
   |        pub(crate) fn thrice  이 크레이트 안에서만
   |
   +-- 바이너리 크레이트    src/main.rs  --> both
            both::twice   OK
            both::thrice  E0603  <- 경계를 넘었다
```

- `main.rs` 에서 `crate::` 를 쓰면 **바이너리 크레이트 자신**을 가리킨다. 라이브러리는 남이므로 **패키지 이름**으로 부른다.
- `pub(crate)` 는 **라이브러리 크레이트 안**까지다. 바이너리는 다른 크레이트라 **E0603**이다.
- **경고가 증명하는 것** — `dead_code` 는 "이 함수를 아무도 안 쓴다"는 뜻이다.\
  바이너리 쪽에서 `both::thrice(14)` 를 **쓰고 있는데도** 경고가 떴다.\
  즉 라이브러리를 컴파일하는 동안 컴파일러는 **바이너리 쪽 코드를 전혀 안 보고 있다.**\
  이것이 "크레이트가 컴파일 단위"라는 말의 실물이다.

> **`dead_code` 린트** — 이 크레이트 안에서 도달 불가능한 항목을 알려 주는 기본 경고.\
> 예: `pub` 항목은 밖에서 쓸 수 있으니 안 뜨고, `pub(crate)` 는 안에서 안 쓰이면 뜬다.

### 7. 컴파일 단위는 무엇인가

**출력** (`cargo build -v` — 원래 **한 줄**인 것을 읽기 쉽게 접었고, 긴 절대 경로는 `...` 로 줄였다)

```text
 Running `.../rustc --crate-name modtest --edition=2024 src/main.rs
          --error-format=json --crate-type bin --emit=dep-info,link
          -C embed-bitcode=no -C debuginfo=2 ...`
```

**왜 그런가**

- 명령줄에 적힌 소스 파일은 **`src/main.rs` 하나**다.
- `src/greet.rs` 와 `src/greet/polite.rs` 는 **없다.** `mod` 를 만난 컴파일러가 스스로 찾아 연다.

```text
  cargo 가 하는 일                     rustc 가 하는 일
  +--------------------------+        +-----------------------------+
  | Cargo.toml 을 읽는다      |  --->  | 루트 한 파일을 연다           |
  | --edition 을 붙인다       |        | mod 를 따라 파일을 더 연다    |
  | 의존성을 -L/--extern 로   |        | 전부 합쳐 결과물 하나를 낸다   |
  +--------------------------+        +-----------------------------+
```

- 그래서 **크레이트 안의 한 글자를 고치면 그 크레이트 전체가 다시 컴파일된다.**\
  파일 단위 증분 컴파일이 아니다(증분 캐시는 있지만 단위는 크레이트다).
- 큰 프로젝트를 여러 크레이트로 쪼개는 동기 한 문장:\
  **"다시 컴파일되는 범위를 잘라 두려고."** 워크스페이스 구성은 목록의 **46번 주제**가 정본이다.
- 같은 사실의 다른 증거 — `cargo` 없이 `rustc --edition 2021 src/main.rs` 만으로도 똑같이 빌드된다(실측).\
  `cargo` 는 **플래그를 붙여 주는 사람**이지 컴파일러가 아니다.

### 8. 에디션의 기본값

**출력**

```text
$ cargo new hello && grep edition hello/Cargo.toml
edition = "2024"

$ cat ex.rs
fn main() {
    let dyn = 3;
    println!("{}", dyn);
}

$ rustc ex.rs -o ex && ./ex
3                                     <- 통과한다 = 2015 로 읽었다

$ rustc --edition 2018 ex.rs -o ex
error: expected identifier, found keyword `dyn`
 --> ex.rs:2:9
  |
2 |     let dyn = 3;
  |         ^^^ expected identifier, found keyword
```

**왜 그런가**

- `cargo new` 는 **2024**, `rustc` 기본은 **2015**다. **같은 툴체인 안에서 기본값이 다르다.**
- 증명에 쓴 한 줄은 `let dyn = 3;` 이다 — `dyn` 은 2015 에서 그냥 식별자고 **2018부터 키워드**라\
  통과하면 2015, 거부당하면 2018 이상이다. **통과 자체가 근거**다.
- `Cargo.toml` 한 줄로 깨지는 예 — `gen` 은 **2024 에서만** 예약어다(실측).

```rust
// src/main.rs — 소스는 한 글자도 안 바꾼다
fn main() {
    let gen = 3;
    println!("gen = {gen}");
}
```

```text
$ grep edition Cargo.toml

$ cargo build

  |

  |         ++

 --> src/main.rs:3:22
```

```text
$ grep edition Cargo.toml

$ cargo run -q
```

- 더 위험한 쪽은 **에러 없이 의미만 바뀌는 것**이다. 같은 코드가 에디션에 따라 다른 메서드로 해석된 실측:

```rust
        println!("{} / 타입 크기 {}", x, std::mem::size_of_val(&x));

```

```text
3 / 타입 크기 1
```

- 왼쪽은 `&u8`(참조, 8바이트), 오른쪽은 `u8`(값, 1바이트)이다. **출력의 숫자가 같아 보여도 타입이 다르다.**
- 2018 쪽에는 경고가 붙었다 — **경고가 에디션 마이그레이션의 안전망**이다. 에디션 전환의 정본은 목록의 **47번 주제**.

### 9. `cargo check` 는 무엇을 만드는가

**출력**

```text
$ cargo clean && cargo check -q
$ ls target/debug/
build  deps  examples  incremental          <- 실행 파일 q 가 없다
$ ls target/debug/deps/
libq-597b905aebcb0df0.rmeta
q-597b905aebcb0df0.d

$ cargo build -q
$ ls target/debug/
build  deps  examples  incremental  q  q.d  <- 이제 q 가 있다
```

**왜 그런가**

- **실행 파일은 없다.** 만들어진 것은 **`.rmeta`**(메타데이터)와 `.d`(의존 관계 목록)뿐이다.
- 빠른 이유 한 문장: **코드 생성(LLVM)과 링크를 통째로 건너뛰기 때문이다.**\
  파싱·이름 해석·타입 검사·빌림 검사까지는 다 하고 거기서 멈춘다.
- `cargo check` 로 못 잡는 것:
  - **런타임 동작** — 패닉·오버플로·논리 오류. 안 돌리니 당연하다.
  - 링크 단계의 문제(외부 심볼 누락 등).
  - **최적화에 따라 갈리는 동작** — 예컨대 정수 오버플로의 디버그/릴리스 차이([03번](../03-primitive-types-and-integer-overflow/)).

### 10. 다른 주제와 잇기

**`rustc` 단독으로 돌릴 때 반드시 붙일 플래그**

- **`--edition 2021`**(또는 쓰려는 에디션).\
  안 붙이면 **2015**로 읽는다(8번). 이 노트의 02\~04번 예제는 전부 `rustc --edition 2021` 로 돌렸다.

**`cargo build --release` 가 바꾸는 것 중 03번에서 다루는 것**

- **정수 오버플로의 동작**이다. 디버그 빌드는 패닉하고 릴리스 빌드는 조용히 감싼다.\
  `cargo` 를 안 쓰면 `rustc -O` 와 `rustc -C overflow-checks=off` 로 같은 대조를 만들 수 있다([03번](../03-primitive-types-and-integer-overflow/)).

**가시성을 더 깊이 다루는 주제**

- 목록의 **45번 주제**(모듈 시스템 — `pub(in path)`·`pub use` 재수출·가시성 설계)가 정본이다.\
  여기서는 `pub`·`pub(crate)`·경로 세 종류까지만 다뤘다.

**소유권·빌림은 어디인가**

- **모델의 논증과 대가**는 [`../../언어-특성/README.md`](../../언어-특성/README.md) §2\~§4.
- **코드에서 `&`·`&mut`·`'a` 를 어떻게 쓰는가**는 목록의 [**08**](../08-ownership-and-move/)·[**10**](../10-borrowing-and-aliasing-rules/)·[**12**](../12-lifetime-annotations-and-elision/)번 주제.
- 이 주제(01)에는 소유권이 **한 줄도 나오지 않는다.** 파일 배치와 컴파일 단위만 다룬다.
