## 정답

### 1. (예측) 같은 값, 다른 객체

**출력**

```text
True False
False
```

**왜 그런가**

- `[1, 2, 3]` 이라는 **리터럴을 쓸 때마다** 리스트 객체가 새로 만들어진다.\
  그래서 상자가 둘이다.
- `a == b` 는 상자를 열어 원소를 하나씩 비교한다 → 내용이 같으니 `True`.
- `a is b` 는 상자 자체가 같은지 본다 → 다른 상자니 `False`.
- `id(a) == id(b)` 가 `False` 인 것은 `a is b` 가 `False` 인 것과 **같은 말**이다.\
  언어 레퍼런스가 `is` 를 그렇게 정의한다 — "`x is y` 는 x 와 y 가 같은 객체일 때만 참이며, 객체의 정체는 `id()` 로 정한다".

```text
        +-----------+                +-----------+
   a -> | [1, 2, 3] |           b -> | [1, 2, 3] |
        +-----------+                +-----------+
          상자 #1                       상자 #2
        ==  안을 비교 -> True
        is  상자를 비교 -> False
```

**여기서 틀리는 자리**

- "값이 같으니 `is` 도 참이겠지"가 틀린다.\
  리스트·dict·set·사용자 클래스 인스턴스는 **거의 항상** 새 객체다.
- 반대로 `b = a` 였다면 둘 다 `True` 다. 대입은 복사가 아니라 이름표 추가이기 때문이다.

### 2. (예측) 인터닝 경계

**출력**

```text
True False
True True
```

**왜 그런가**

- 첫 줄 `257`: CPython 이 미리 만들어 둔 정수 캐시 **밖**이라 `int("257")` 을 부를 때마다 새 객체가 생긴다 → `is` 는 `False`.
- 둘째 줄 `100`: 캐시 **안**이라 이미 있는 객체를 돌려준다 → `is` 가 `True`.
- **두 줄 모두 `==` 는 `True`** 다. 값은 언제나 같기 때문이다. 갈리는 것은 `is` 뿐이다.

```text
캐시 안 (-5 ~ 256)                  캐시 밖 (257)
        +-------+                        +-------+   +-------+
   r -> |  100  | <- s              p -> |  257  |   |  257  | <- q
        +-------+                        +-------+   +-------+
   r is s -> True                   p is q -> False
```

경계는 이 머신에서 직접 재어 확인했다.

```python
lo = None
for n in range(-20, 400):
    same = int(str(n)) is int(str(n))
    if same and lo is None:
        lo = n
    if not same and lo is not None:
        print("캐시되는 구간:", lo, "~", n - 1)
        break
```

```text
캐시되는 구간: -5 ~ 256
```

C API 문서도 같은 값을 적는다 — "The **current implementation** keeps an array of integer objects for all integers between `-5` and `256`."

**왜 `int("257")` 로 썼나**

`p = 257; q = 257` 이라고 소스에 직접 쓰면, 같은 코드 객체 안의 동일한 상수를 컴파일러가 **하나로 합쳐** `is` 가 `True` 가 되기도 한다.\
그러면 결과가 정수 캐시 때문인지 컴파일러 최적화 때문인지 구분이 안 된다.\
`int("257")` 은 **실행 중에** 정수를 만들므로 정수 캐시만 시험하게 된다.

**여기서 틀리는 자리**

값 비교에 `is` 를 쓴 코드는 **작은 수로만 시험하면 전부 통과한다.**\
장바구니 개수·나이·점수 같은 작은 수로 짠 테스트는 초록이고, 주문번호·타임스탬프가 들어오는 순간 조용히 무너진다.

### 3. (예측) 문자열 — 만드는 방법이 답을 바꾼다

**출력**

```text
True
True False
```

**왜 그런가 — 그리고 언제 결정되는가**

- `h1 = "hello"` 와 `h2 = "hel" + "lo"` 는 둘 다 **컴파일 시점에** 문자열 상수가 된다.\
  `"hel" + "lo"` 는 상수 접기로 컴파일 때 `"hello"` 로 합쳐지고, 같은 코드 객체의 같은 상수라 **하나의 객체**를 공유한다 → `h1 is h2` 가 `True`.
- `h3 = "".join([...])` 은 **실행 시점에** 새 문자열을 만든다 → 다른 객체 → `h1 is h3` 는 `False`.
- `h1 == h3` 는 당연히 `True`. 글자가 같기 때문이다.

```text
컴파일 시점에 합쳐진 것            실행 시점에 만든 것
        +---------+                     +---------+   +---------+
   h1 ->| "hello" |<- h2           h1 ->| "hello" |   | "hello" |<- h3
        +---------+                     +---------+   +---------+
        is -> True                      is -> False, == -> True
```

같은 글자를 같은 객체로 **강제로** 합치고 싶으면 `sys.intern` 을 쓴다.

```python
import sys
h4 = sys.intern(h3)
print(h1 is h4)      # True
```

`sys.intern` 의 문서상 목적은 dict 조회 최적화다 — 키가 전부 인터닝돼 있으면 해시 이후의 비교를 **문자열 비교 대신 포인터 비교**로 할 수 있다.

**여기서 틀리는 자리**

`if name is "admin":` 같은 코드는 리터럴끼리라 통과하다가, 이름이 파일·네트워크·`input()` 에서 들어오는 순간 `False` 가 된다.\
3.8부터는 이 코드에 `SyntaxWarning` 이 난다(7번 답 참조).

### 4. (왜) `is None` 을 쓰는 이유

**출력**

```text
True
False
```

**왜 그런가**

- `w == None` 은 `w.__eq__(None)` 을 **호출한다.** `Weird.__eq__` 는 무조건 `True` 를 돌려주므로 결과가 `True` 다.\
  `w` 는 `None` 이 아닌데 `True` 가 나왔다 — **거짓말이 통과했다.**
- `w is None` 은 상자 주소만 비교한다. 사용자 코드를 부르지 않으므로 아무도 못 뒤집는다 → `False`(사실).

`==` 와 `is` 의 평가 경로를 나란히 놓으면 이렇다.

```text
w == None 을 평가                    w is None 을 평가
   |                                    |
   +-> w.__eq__(None) 호출  <- 사용자 코드   +-> id(w) 와 id(None) 비교
   |     NotImplemented 면                    끝. 사용자 코드 안 돎
   +-> None.__eq__(w) 호출
   +-> 그래도 안 되면 정체 비교
```

`__eq__` 가 정말 불린다는 것은 이렇게 눈으로 확인된다.

```python
class Loud:
    def __eq__(self, other):
        print("   Loud.__eq__ 호출됨")
        return NotImplemented

x = Loud(); y = Loud()
print(x == y)
print(x is y)
```

```text
   Loud.__eq__ 호출됨
   Loud.__eq__ 호출됨
False
False
```

- `__eq__` 가 **두 번** 찍혔다 — 왼쪽에게 묻고, `NotImplemented` 가 오자 오른쪽에게 다시 물었다.
- 양쪽 다 처리 못 하면 파이썬은 마지막 수단으로 정체 비교를 쓴다. 그래서 `False`.
- `x is y` 에서는 **아무것도 안 찍혔다.** `is` 는 메서드를 부르지 않는다.

**세 가지 실무 이유로 정리하면**

1. **정확하다** — `None` 은 싱글턴이라 `is` 가 언제나 정답이다.
2. **속지 않는다** — 남의 `__eq__`(numpy 배열, ORM 필드, mock 객체)가 이상한 값을 돌려줘도 무관하다.
3. **빠르고 안전하다** — `==` 는 예외를 던질 수도 있고, numpy 배열처럼 **bool 이 아닌 값**을 돌려줘 `if` 에서 터질 수도 있다.

### 5. (예측) nan — 반대 방향의 어긋남

**출력**

```text
False
True
True
False
```

**왜 그런가 — 한 줄씩**

- `nan == nan` → `False`.\
  IEEE 754 에서 nan 은 **자기 자신과도 같지 않다**고 정해져 있다.
- `nan is nan` → `True`.\
  같은 이름이 같은 상자를 가리키니 당연하다. 값이 뭐든 상관없다.
- `nan in [nan]` → `True`.\
  언어 레퍼런스가 규정한다 — 리스트 같은 컨테이너에서 `x in y` 는 `any(x is e or x == e for e in y)` 와 같다.\
  즉 **`is` 를 먼저 보고**, 참이면 `==` 를 물어보지도 않는다.
- `nan in [float("nan")]` → `False`.\
  안에 든 것은 **다른 상자**의 nan 이다. `is` 도 거짓, `==` 도 거짓이라 못 찾는다.

```text
지금까지의 어긋남                    nan 의 어긋남
값 같음 / 정체 다름                   값 다름 / 정체 같음
   a == b  True                       nan == nan  False
   a is b  False                      nan is nan  True

 in 은 is 를 먼저 본다
   nan in [nan]            -> 같은 상자        -> True
   nan in [float("nan")]   -> 다른 상자,
                              == 도 False      -> False
```

**여기서 틀리는 자리**

- 결측치가 섞인 데이터에서 `if value in bad_values:` 가 **어떤 nan 은 찾고 어떤 nan 은 못 찾는다.**\
  nan 판정은 `math.isnan(x)` 로 해야 한다.
- `x == x` 가 거짓이 될 수 있다는 사실 자체가 정렬·중복 제거·dict 키에서 튀는 동작을 만든다.

### 6. (예측) `id()` 재사용과 `True == 1`

**출력**

```text
q02_6.py:4: SyntaxWarning: "is" with 'int' literal. Did you mean "=="?
  print(True == 1, True is 1)
True
False
True False
True
```

**한 줄씩**

- 맨 위 두 줄은 프로그램 출력이 아니라 **컴파일 시점 경고**다. 그래서 다른 출력보다 먼저 찍힌다(3번 답).
  파일 이름(`q02_6.py`)은 내가 돌린 파일 이름이므로 각자 다르게 나온다.
- `id([1, 2, 3]) == id([4, 5, 6])` → **`True`**.\
  첫 리스트는 `id()` 를 계산한 직후 아무도 안 가리키므로 곧바로 회수되고, 그 자리를 둘째 리스트가 **재사용**한다.\
  문서가 그것을 허용한다 — "수명이 겹치지 않는 두 객체는 같은 `id()` 값을 가질 수 있다".
- `id(a) == id(b)` → **`False`**.\
  이번엔 `a`, `b` 가 둘 다 살아 있어 수명이 겹친다. 그래서 주소가 겹칠 수 없다.
- `True == 1, True is 1` → **`True False`**.\
  `bool` 은 `int` 의 하위 타입이라 값으로는 같고, 상자는 다르다.
- `1 in [True]` → **`True`**.\
  `in` 이 `==` 로 떨어지고 `1 == True` 가 참이기 때문이다.

```text
수명이 겹치지 않는다                 수명이 겹친다
 id([1,2,3]) 계산 -> 리스트 회수       a -> [1,2,3]   (살아 있다)
 id([4,5,6]) 계산 -> 같은 자리 재사용   b -> [4,5,6]   (살아 있다)
   같은 id 가 나온다 -> True             다른 자리일 수밖에 -> False
```

**여기서 배울 것**

"두 객체가 같은지"를 확인할 때 **`id()` 를 비교하지 말고 `is` 를 쓴다.**\
`is` 는 두 피연산자가 다 살아 있는 상태에서 비교하므로 이 함정에 안 걸린다.

**`True == 1` 이 실무에서 물리는 자리**

```python
print([1, 2].count(True))   # 1
```

`count`·`in`·`index`·`dict` 키가 전부 `==` 를 쓴다.\
그래서 `{1: "정수", True: "불린"}` 은 키가 **하나**가 된다.

### 7. (경계) `is` 를 써도 되는 값

**써도 되는 것 — 전부 「객체가 하나뿐임이 보장된 것」이다**

| 값 | 왜 되나 |
|---|---|
| `None` | 언어가 보장하는 싱글턴. `if x is None:` 이 표준 관용구다 |
| `True` / `False` | 싱글턴. 다만 **진릿값 판정에는 `if flag:` 를 쓴다** — `is True` 는 1 이나 빈 리스트 아님을 잡아내지 못한다 |
| `Ellipsis` (`...`) | 싱글턴 |
| `NotImplemented` | 싱글턴. `__eq__` 반환값 판정에 쓴다 |
| 내가 만든 센티널 — `MISSING = object()` | 내가 하나만 만들었으므로 내가 보장한다 |
| 클래스·모듈·함수 객체 | 한 번 정의되면 그 객체 하나다 (`type(x) is list` 등) |

**쓰면 안 되는 것** — 숫자·문자열·리스트·dict·튜플·사용자 값 객체, 즉 **값을 묻는 모든 것**.

**왜 테스트가 통과하면서 틀린 상태가 되나**

세 겹으로 겹친다.

1. **인터닝이 작은 값에서 참을 만들어 준다.**\
   테스트에 쓰는 숫자는 대개 0~10, 문자열은 `"a"`·`"test"` 같은 짧은 리터럴이다. 전부 캐시·상수 접기 범위 안이다.
2. **실패가 예외가 아니라 `False` 로 나온다.**\
   `is` 는 타입이 뭐든 조용히 `False` 를 돌려준다. 스택 트레이스가 안 생기므로 로그에 아무것도 안 남는다.
3. **깨지는 조건이 「값의 크기」·「만든 경로」라서 재현이 안 된다.**\
   같은 코드가 리터럴로 부르면 되고 파일에서 읽으면 안 된다.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 결과만 틀린 것.\
> 예: `if code is 200:` 이 로컬 테스트에서는 통과하고, 200 을 문자열 파싱으로 만든 운영에서만 `False` 가 된다.

한 문장으로: **값을 묻고 싶으면 `is` 를 쓰지 않는다. 답이 맞아도 그것은 우연이다.**

### 8. (경계) 구현 세부사항 대 언어 보장

**언어가 보장하는 것** (명세에 적혀 있고, 어떤 구현에서도 성립한다)

| 사실 | 근거 |
|---|---|
| `x is y` 는 x 와 y 가 같은 객체일 때만 참 | 언어 레퍼런스 6.10.3 |
| `==` 의 기본 동작은 정체 기반이고 `__eq__` 로 바꿀 수 있다 | 언어 레퍼런스 6.10.1 |
| 컨테이너의 `x in y` 는 `any(x is e or x == e for e in y)` 와 같다 | 언어 레퍼런스 6.10.2 |
| `id()` 는 객체의 수명 동안 유일하고 변하지 않는다 | 내장 함수 `id()` |
| 수명이 겹치지 않는 두 객체는 같은 `id()` 를 가질 수 있다 | 내장 함수 `id()` |
| `sys.intern()` 을 거친 같은 문자열은 같은 객체다 | `sys.intern()` |
| `None` 은 싱글턴이다 | 내장 상수 |

**CPython 구현 세부사항** (지금 이 구현이 그럴 뿐이다)

| 사실 | 근거 |
|---|---|
| -5 ~ 256 정수가 미리 만들어져 재사용된다 | C API 문서가 "**the current implementation**" 이라고 적는다 |
| `id()` 가 메모리 주소다 | `id()` 문서의 "**CPython implementation detail**" 표시 |
| 소스에 직접 쓴 짧은 문자열이 자동으로 인터닝된다 | 문서는 `sys.intern` 만 규정하고 자동 인터닝의 범위를 규정하지 않는다 |
| `"hel" + "lo"` 가 컴파일 시점에 접힌다 | 상수 접기는 명세에 없는 최적화다 |
| 회수된 객체의 자리를 곧바로 재사용한다 | 참조 카운팅의 결과이지 명세가 아니다 |

**그래서 이렇게 쓰면 틀린다**

- ✗ "파이썬은 -5부터 256까지의 정수를 캐싱한다."\
  ○ "**CPython 3.12 의 현재 구현이** -5~256 정수를 캐싱한다. 다른 구현·버전에서는 다를 수 있다."
- ✗ "같은 문자열은 같은 객체다."\
  ○ "같은 객체가 **되기도 한다.** 만든 경로에 따라 달라지므로 의존하면 안 된다."
- ✗ "`id()` 는 메모리 주소다."\
  ○ "`id()` 는 **정체를 나타내는 정수**다. 그것이 메모리 주소라는 것은 CPython 구현 세부사항이다."

**판정 기준 한 줄**\
어떤 코드가 `is` 의 결과에 기대고 있다면(`None` 류 싱글턴 제외), 그 코드는 **구현 세부사항에 기댄 코드**다.\
같은 프로그램이 PyPy 에서, 또는 다음 CPython 버전에서 다르게 돌 수 있다는 뜻이다.

> **구현 세부사항(implementation detail)** — 언어 명세가 보장하지 않고 특정 구현이 그렇게 만들어 둔 것.\
> 예: 문서에 "CPython implementation detail" 이라 적혀 있거나 "the current implementation" 이라는 말이 붙어 있으면 그것이다.

## 실행 검증

이 파일에 실린 출력은 전부 아래 환경에서 직접 돌려 얻었다.

```text
$ python3 --version
Python 3.12.3
```

- 1·2·3번 — 같은 값/다른 객체, 정수 캐시 경계 탐색, 문자열 세 형태
- 4번 — `Weird.__eq__` 와 `Loud.__eq__` 호출 추적
- 5번 — nan 네 줄
- 6번 — `id()` 재사용, `True == 1`, `SyntaxWarning`
- 7번 — 리터럴에 `is` 를 썼을 때의 `SyntaxWarning` 재현

인터닝과 `id()` 값은 **구현 세부사항**이므로, 다른 파이썬 구현이나 다른 버전에서는 2·3·6번의 결과가 달라질 수 있다.
