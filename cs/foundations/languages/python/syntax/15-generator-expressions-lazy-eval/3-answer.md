## 정답

### 1. 값은 같고 크기는 4만 배 다르다 — 그것이 이 주제의 전부다

**출력**

```text
python 3.12.3 | cpython
list comp  getsizeof : 8448728
gen  expr  getsizeof : 200
배수                 : 42243
합이 같나            : True
```

**왜 그런가**

```text
  [x * 2 for x in range(1_000_000)]        (x * 2 for x in range(1_000_000))
  ┌───────────────────────────────┐        ┌──────────────────┐
  │ 0 2 4 6 ... 1999998           │        │ 만드는 방법       │
  │ 백만 칸이 실제로 있다           │        │ + 어디까지 갔나   │
  └───────────────────────────────┘        └──────────────────┘
        8,448,728 바이트                            200 바이트
```

★ **`합이 같나 : True` 가 이 주제의 문제 설정이다.**
두 형태는 **결과로는 구분이 안 된다.** 그래서 「지연 평가를 확인했다」를 **값으로 적으면 아무것도 확인하지 않은 것**이다.
잴 것은 값이 아니라 **바이트**다.

- 리스트는 **백만 칸 × 포인터 8바이트 + 머리 + 과할당** 이라 `N` 에 비례한다.
- 제너레이터는 「만드는 방법」과 「어디까지 갔나」만 들고 있어 **`N` 과 무관**하다.

★ **다시 돌렸을 때 대조할 것은 `42243` 이라는 숫자가 아니라
「`N` 을 10배로 하면 왼쪽만 10배가 되고 오른쪽은 그대로다」는 성질이다.**
`8448728` 은 과할당 정책의 결과이고, `200` 은 식의 복잡도에 달린 값이라 둘 다 판·빌드에 흔들린다.

### 2. 두 창이 다섯 배 어긋난다 — 그리고 「현재」는 둘 다 0 이다

**출력**

```text
[...]  합=999999000000  현재=       32  최대= 40444616 바이트
(...)  합=999999000000  현재=      182  최대=      646 바이트
```

**왜 그런가**

★★ **`getsizeof` 가 말한 8.4 MB 보다 최대치가 다섯 배 가까이 크다(40 MB).**
어긋난 것이 아니라 **두 창이 다른 것을 재고 있다.**

```text
   getsizeof(리스트)  ──> 리스트 자신만              8,448,728
   tracemalloc 최대치 ──> 리스트 + 그 안의 정수 백만 개  40,444,616
                                 ^^^^^^^^^^^^^^^^^^
                          getsizeof 가 안 세는 부분
```

문서가 범위를 못 박는다 — *"Only the memory consumption directly attributed to the object is accounted for,
**not the memory consumption of objects it refers to**."*\
★ **그러므로 「어느 쪽이 틀렸나」가 아니다.** `getsizeof` 는 **과소평가하도록 정의된** 도구이고,
「실제로 얼마나 잡혔나」를 물으면 `tracemalloc` 이 답한다.

**★ `현재`(cur)를 보면 안 되는 이유**

- 둘 다 **32 바이트·182 바이트**로 거의 0 이다. `sum` 이 끝나면 리스트가 회수되기 때문이다.
- 즉 **다 끝난 뒤에 재면 차이가 통째로 사라진다.**
- ★ **OOM 은 「최대」에서 난다.** 재야 하는 것은 지나간 봉우리이지 지금 수면이 아니다.

★ 이 수치들도 **다시 돌리면 달라진다** — 대조할 것은 숫자가 아니라
「**왼쪽만 `N` 에 비례하고 오른쪽은 안 변한다**」는 성질이다.

### 3. 지금 평가되는 것은 딱 한 조각이다

**출력**

```text
--- 1. 이름을 갈아 끼우면 ---
  list(g) : [1, 2, 3]
--- 2. 같은 객체를 고치면 ---
  list(g2): [1, 2, 3, 4]
--- 3. 첫 for 의 이터러블은 즉시 평가된다 ---
  만드는 자리에서 NameError: name 'nope_first' is not defined
--- 4. 둘째 for 의 이터러블은 늦다 ---
  만들기는 됐다 -> generator
  next 할 때 NameError: name 'nope_second' is not defined
```

**왜 그런가**

```text
   ge = (x        for x in 여기        for y in 저기        if 조건)
         ^^                ^^^^^              ^^^^^           ^^^^
         나중              ★ 지금             나중            나중
```

**1번과 2번이 갈리는 이유 한 문장** — 만들 때 붙잡아 둔 것은 **그때의 객체**이지 **이름**이 아니다.

```text
   판 1                              판 2
   src ──> [1,2,3] <── g 가 붙잡음     src2 ──> [1,2,3] <── g2 가 붙잡음
   src ──> [9,9,9]   (g 는 안 따라감)   src2 의 그 객체에 4 를 붙임
   결과 [1, 2, 3]                     결과 [1, 2, 3, 4]
```

- 판 1 은 **이름을 다른 객체로 옮긴 것**이라 제너레이터가 쥔 객체는 그대로다.
- 판 2 는 **쥐고 있는 그 객체 자체**가 바뀐 것이라 나중에 훑을 때 4가 보인다.
- ★ **두 줄은 코드가 거의 같아 보이는데 결과가 다르다.** 읽는 사람이 이 둘을 구분 못 하는 것이 사고의 씨앗이다.

**3번과 4번이 보이는 것** — **한 식 안에서 평가 시점이 둘로 갈린다.**

| 자리 | 언제 평가되나 | 증거 |
|---|---|---|
| **가장 왼쪽 `for` 의 iterable** | **정의하는 줄** | `g3 = (...)` 대입 줄에서 `NameError` |
| 둘째 이후 `for` 의 iterable | `next()` 때 | `g4` 는 만들어지고 `next` 에서 `NameError` |
| `if` 조건 · 앞쪽 식 | `next()` 때 | 〃 |

문서가 그 한 조각을 콕 집는다 — *"the iterable expression in the leftmost `for` clause is **immediately evaluated**,
so that an error produced by it will be emitted at the point where the generator expression is defined."*\
규칙의 정본은 [14번](../14-comprehensions/2-summary.md)이다. 여기서 더한 것은 **둘째 `for` 를 던져서 반대쪽을 보인 것**이다.

★★ **그래서 「제너레이터 표현식은 아무것도 안 한다」는 틀렸다.** 10번 답에서 그 한 조각이 바이트코드로 보인다.

### 4. 두 번째는 예외가 아니라 `0` 이고, `max` 만 얼굴이 다르다

**출력**

```text
첫 판 sum : 10
둘째 판   : 0
list      : []
max 는?   : 없음
리스트는 몇 번이든 : 10 10 [0, 1, 2, 3, 4]
```

**왜 그런가**

```text
   리스트                       제너레이터 표현식
   ┌───────────────┐            ┌───────────────┐
   │ 0 1 2 3 4     │  sum -> 10 │ 커서 ──────>  │  sum -> 10
   │ 그대로 있다    │  sum -> 10 │ 커서 끝에 있다 │  sum ->  0
   └───────────────┘            └───────────────┘
                                   되감기가 없다
```

★★ **`0` 은 「합이 0 인 경우」와 글자 하나 다르지 않다.** 예외도 경고도 안 나므로 **로그에도 안 남는다.**

**`default=` 를 빼면**

```text
===== 소스: ex.py =====
g = (n for n in range(5))
print("첫 sum :", sum(g))
try:
    max(g)
except ValueError as e:
    print("max(g) -> ValueError:", e)
```

```text
첫 sum : 10
max(g) -> ValueError: max() iterable argument is empty
```

★ **여기서만 터진다.** 같은 원인이 **세 얼굴**로 나온다.

| 두 번째로 부른 것 | 결과 | 눈에 띄나 |
|---|---|---|
| `sum` | `0` | **안 띈다** — 정상 값과 구분 불가 |
| `list`·`tuple`·`set` | `[]` | **안 띈다** — 빈 입력과 구분 불가 |
| `max`·`min`(default 없이) | `ValueError` | **띈다** |

★ **얼굴이 다른 것이 위험한 이유** — `max` 로 터지는 코드만 고치고 `sum` 쪽은 못 찾는다.
버그 리포트가 「**합계가 가끔 0 으로 나옵니다**」로 오고, 재현이 「두 번 호출했을 때만」이라 안 잡힌다.\
왜 되감기가 없는지(프레임이 어떻게 닫히는지)는 [17번](../17-generators-yield/2-summary.md)이 정본이다.

### 5. 이어서 나온다 — 파이프라인이 커서 하나를 공유하기 때문이다

**출력**

```text
처음 다섯 개 : [1, 9, 25, 49, 81]
이어서 세 개 : [121, 169, 225]
```

**왜 그런가**

```text
   naturals()  0 1 2 3 4 5 ...  (끝이 없다)
        │
        ▼  (n * n for n in naturals())
   squares     0 1 4 9 16 25 ...
        │
        ▼  (s for s in squares if s % 2 == 1)
   odd         1 9 25 49 81 | 121 169 225 ...
                 ^^^^^^^^^^   ^^^^^^^^^^^^
                 첫 islice     둘째 islice — 커서가 이어진다
```

- **같은 값이 아니다.** 세 겹을 쌓았어도 **커서는 하나**라 두 번째 `islice` 가 **이어서** 가져간다.
- 4번 답의 소진과 **같은 성질**이다 — 다만 여기서는 **다 안 먹었을 뿐**이라 빈 것이 안 나왔다.
- 앞 5개를 뽑으려고 **계산된 제곱은 딱 그만큼**이다. `naturals()` 는 끝이 없는데도 멈춘다.

**`list(odd)` 를 쓰면 — 예외는 안 난다**

★★ **질문이 「무슨 예외가 나는가」로 물었지만 답은 「예외가 안 난다」다.**
`list()` 는 끝을 기다리고 `naturals()` 에는 끝이 없다. **프로그램이 그냥 안 끝난다.**\
★ **에러로 알려 주지 않는 실패**라서, 실행이 멈춘 줄 모르고 타임아웃만 보게 된다.
그래서 **무한 수열에는 `islice`·`takewhile` 같은 끊는 장치가 문법의 일부처럼 따라붙는다.**

> **`itertools.islice(it, n)`** — 앞 `n` 개만 잘라 주는 지연 도구.\
> 예: 슬라이스와 달리 인덱싱이 없는 것에도 걸리고, **앞에서부터 버리며 세므로** 뒤쪽을 건너뛰는 것은 공짜가 아니다.

### 6. 다섯 줄 중 셋이 지연을 스스로 지운다

**출력**

```text
len(g)       -> TypeError: object of type 'generator' has no len()
g[0]         -> TypeError: 'generator' object is not subscriptable
sorted 는 되나 : [1, 2, 3]  <- 속으로 리스트를 만든다
3 in g2      : True | 남은 것 : [4]  <- in 이 먹었다
개수를 세려면 : 5  <- 그 순간 다 돈다
```

**왜 그런가**

| 줄 | 무엇이 일어나나 | 지연을 지우나 |
|---|---|---|
| `len(g)` | 아직 몇 개인지 모른다. 세려면 꺼내야 하고 꺼내면 소진된다 | — (**아예 막는다**) |
| `g[0]` | 첨자가 없다. 앞으로만 간다 | — (**아예 막는다**) |
| `sorted(...)` | 전부를 봐야 정렬이 되므로 **새 리스트를 만든다** | ★ **지운다** |
| `3 in g2` | 찾을 때까지 꺼낸다 — **0·1·2·3 이 사라졌다** | ★ **지운다**(일부) |
| `sum(1 for _ in ...)` | 세려면 **전부 돈다** | ★ **지운다**(시간을) |

★ **`in` 이 값을 먹는 것**이 가장 눈에 안 띈다. **검사했을 뿐인데 상태가 바뀐다.**
`if 3 in g: ... list(g)` 는 앞쪽을 잃은 채 돈다. [14번](../14-comprehensions/2-summary.md)이 같은 사고를 `3 in g` 두 번으로 보였다.\
★ **`sorted`·`reversed` 는 되지만 「되는 것」이 곧 「이점이 남는 것」은 아니다** — 메모리 이점이 그 줄에서 통째로 사라진다.
`min`·`max`·`sum`·`any`·`all` 은 한 칸으로 되므로 이점이 남는다.

### 7. 「참조하는 것은 안 센다」 — 실측에서 다섯 배 어긋났다

**출력**

```text
getsizeof 는 무엇을 세나
  [0..4] 리스트 자신 : 120
  원소 5개의 합      : 140
  gen expr           : 192
  gen expr (100만)   : 192
  빈 리스트          : 56
```

**왜 그런가**

문서의 낱말이 정확하다 — *"Only the memory consumption directly attributed to the object is accounted for,
**not the memory consumption of objects it refers to**."*

```text
   sys.getsizeof([0,1,2,3,4])  =  120
   ┌──────────────────────────────────┐
   │ 리스트 머리 56 + 포인터 5칸 × 8 …  │   <- 여기까지만 센다
   └──────────────────────────────────┘
        │   │   │   │   │
        v   v   v   v   v
      [28][28][28][28][28]   <- 정수 객체 5개 = 140 바이트. 안 센다
```

- ★ **다섯 개짜리 리스트에서 이미 「안 센 쪽」이 더 크다**(140 > 120).
- 백만 개에서는 **8.4 MB 로 보인 것이 실제로는 40 MB** 였다(2번 답) — **약 4.8배.**
- 그러므로 `getsizeof` 는 「**목록 종이의 무게**」다. 「냉장고 안 물건의 무게」를 물으면 `tracemalloc` 이 답한다.

★ **이 실측이 [14번](../14-comprehensions/2-summary.md)이 남긴 「실제 차이는 더 크다」를 숫자로 닫은 것**이다.

### 8. 원소 수가 아니라 식의 복잡도가 바꾼다

**출력** — 두 실행을 나란히 놓은 것이다.

```text
  gen expr           : 192        <- (x for x in range(5))
  gen expr (100만)   : 192        <- (x for x in range(1_000_000))
```

```text
gen  expr  getsizeof : 200        <- (x * 2 for x in range(1_000_000))
```

**왜 그런가**

- **5개짜리와 100만개짜리가 `192` 로 같다.** 값을 안 들고 있으니 원소 수가 크기에 안 들어간다.
- ★ **그런데 `x` 를 `x * 2` 로 바꾸면 `200` 이 된다.** 8바이트가 늘었다.
- 제너레이터 객체는 **자기 프레임을 안에 품고 있고**, 그 프레임에는 **평가 스택 칸**이 들어 있다.
  식이 복잡해져 스택이 한 칸 더 필요하면 **객체가 그만큼 커진다.**

★ **그러므로 크기를 바꾸는 축은 「몇 개냐」가 아니라 「식이 얼마나 복잡하냐」다.**
둘 다 원소 수와는 무관하다는 점이 요점이고, **그 절대 숫자(`192`·`200`)는 CPython 3.12.3 의 구현 값이다** — 판이 바뀌면 달라진다.

### 9. 세 원인 — 그리고 각각을 무엇으로 잡나

**출력** — 진단에 쓰는 두 창이다.

```text
[...]  합=999999000000  현재=       32  최대= 40444616 바이트
(...)  합=999999000000  현재=      182  최대=      646 바이트
```

**왜 그런가**

| 원인 | 증상 | 진단하는 법 |
|---|---|---|
| **중간에 `list()`·`sorted()` 가 끼었다** | 제너레이터로 바꿨는데 최대치가 그대로 | `tracemalloc` **최대치**를 단계별로 찍는다 |
| **`getsizeof` 로만 확인했다** | 「줄었다」고 적었는데 실제로는 안 줄었다 | `tracemalloc` 으로 다시 잰다 |
| **다 끝난 뒤에 쟀다** | 양쪽 다 0 에 가깝게 나온다 | `현재` 말고 **`최대`** 를 본다 · `reset_peak()` 로 구간을 끊는다 |

★ **셋이 전부 「측정 방법」의 문제**라는 것이 이 주제의 성격이다.
코드가 아니라 **재는 창을 잘못 골라서** 틀린 결론이 난다.\
★ 네 번째 원인은 코드 쪽이다 — **`len`·인덱싱·슬라이싱이 한 줄이라도 있으면** 그 자리는 애초에 리스트여야 한다(6번 답).

### 10. 한눈에 다른 것은 인라인, 안 변한 것은 `GET_ITER` 의 자리

**출력**

```text
===== [x for x in it] =====
  0           0 RESUME                   0
```

★ **나머지는 전부 구현이다.** 명령 이름·오프셋·인라인 여부는 판마다 바뀌고,

### 11. 세 층

**출력** — 층을 가르는 근거로 쓴 것들이다.

```text
python 3.12.3 | cpython
list comp  getsizeof : 8448728
gen  expr  getsizeof : 200
```

**왜 그런가**

**언어 보장**

| 사실 | 근거 |
|---|---|
| 제너레이터 표현식은 **새 제너레이터 객체**를 낸다 | 6.2.8 — *"A generator expression yields a new generator object."* |
| **가장 왼쪽 `for` 의 iterable 은 즉시 평가**되고 그 에러는 **정의된 자리**에서 난다 | 6.2.8 — *"immediately evaluated ... at the point where the generator expression is defined"* |
| 나머지 식은 **지연 평가**된다 | 6.2.8 — *"The other expressions ... are lazily evaluated."* |
| **유일한 인자일 때만 괄호 생략** | 6.2.8 — *"only be omitted on calls with only one argument"* |
| 가장 왼쪽 iterable 을 빼면 **감춰진 중첩 스코프**에서 돈다 | 6.2.4 |
| `getsizeof` 는 **참조하는 것의 메모리를 안 센다** | `sys.getsizeof` |
| 소진된 이터레이터는 **계속 `StopIteration`** 을 낸다 → 두 번째가 빈 결과 | 이터레이터 프로토콜([16번](../16-iterator-protocol/2-summary.md)) |

**CPython 구현 세부사항**

| 사실 | 어떻게 확인했나 |
|---|---|
| 3.12 부터 **컴프리헨션이 인라인**(PEP 709 — list·dict·set) | `dis` — 3.12 와 3.11.15 대조 |
| 제너레이터 표현식은 **인라인 대상이 아니다** | `dis` — 두 판이 같다 |
| 명령 이름(`LOAD_FAST_AND_CLEAR`·`PRECALL`·`CALL_INTRINSIC_1`) | `dis` — 판마다 다르다 |
| 제너레이터 객체가 `192`·`200` 바이트인 것 | `getsizeof` — 프레임·평가 스택 크기의 결과 |
| 리스트가 `8448728` 바이트인 것 | 과할당 정책 |

**이 판(3.12.3)·이 머신의 관찰**

| 관찰 | 어디가 흔들리나 |
|---|---|
| `tracemalloc` 최대치 `40444616` 대 `646` | 할당기 상태. **비례 관계만** 재현된다 |
| `timeit` 비 `1.08`\~`1.45` / `0.01` | 머신·부하. 앞 줄은 **잡음 범위** |
| 코드 객체 주소 `0x740a5cf4eb10` | **매 실행 다르다** |
| 배수 `42243` | `N` 에 달렸다 |
| 예외 **문구** 전부 | 예외 **종류**는 명세, 문구는 아니다 |

★ **판정 기준 한 줄** — 「**무엇이 언제 평가되나**」는 명세에 있고, 「**그것을 어떤 명령으로 몇 바이트에 하나**」는 이 구현에 있다.

### 12. 한 줄은 근거가 되고 한 줄은 안 된다

**출력**

```text
--- 판 1 ---
전부 소비   [..]     28.5 us   (..)     30.8 us   비  1.08
앞 1개만    [..]     23.3 us   (..)      0.3 us   비  0.01
--- 판 2 ---
전부 소비   [..]     28.3 us   (..)     34.0 us   비  1.20
앞 1개만    [..]     23.0 us   (..)      0.2 us   비  0.01
--- 판 3 ---
전부 소비   [..]     29.1 us   (..)     42.1 us   비  1.45
앞 1개만    [..]     31.8 us   (..)      0.2 us   비  0.01
```

**왜 그런가**

| 줄 | 세 판의 비 | 신호 대 잡음 | 주장할 수 있는 것 |
|---|---|---|---|
| **전부 소비** | 1.08 · 1.20 · 1.45 | 판 사이 흔들림이 **30% 넘는다** | 「**전부 소비하면 이점이 없다**」까지 |
| **앞 1개만** | 0.01 · 0.01 · 0.01 | **100배** · 세 판이 같다 | 「**앞쪽만 쓰면 압도적**」 |

★★ **「제너레이터가 느리다」를 못 적는 이유** — 앞 줄의 **신호가 잡음보다 크지 않다.**
세 판의 비가 1.08 에서 1.45 까지 벌어졌으므로, 「1.2배 느리다」는 **다음 판에서 뒤집힐 수 있는 수**다.
★ **재지 않은 성능 주장이 금지인 것과 같은 이유로, 잡음에 묻힌 측정도 주장의 근거가 안 된다.**

★ 앞 줄에는 **3.12 의 인라인**(PEP 709, 10번 답)이 섞여 있다 —
리스트 쪽이 함수 호출 한 번을 아꼈으므로, 이 비교는 **판이 바뀌면 값이 달라지는** 비교다.
**「어느 쪽이 빠르냐」가 아니라 「무엇을 아끼느냐」로 고르는 것**이 이 주제의 판정 기준이다.
