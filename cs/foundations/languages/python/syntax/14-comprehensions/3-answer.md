## 정답

### 1. 계산이 일어나는 줄 (예측)

**출력**

```text
리스트 만들기 시작
   계산: 1
   계산: 2
   계산: 3
리스트 완성: [1, 4, 9]
제너레이터 만들기 시작
제너레이터 완성: <generator object <genexpr> at 0x7c1c79baf9f0>
   계산: 1
첫 개 꺼냄: 1
   계산: 2
   계산: 3
나머지: [4, 9]
```

**어디에 찍혔나**

- 리스트 쪽 — `리스트 만들기 시작` 과 `리스트 완성` **사이에 세 줄이 전부** 들어갔다.
- 제너레이터 쪽 — `제너레이터 완성` **앞까지 한 줄도 없다.**\
  `계산: 1` 은 `첫 개 꺼냄:` **보다 먼저**, `계산: 2`·`계산: 3` 은 `나머지:` **보다 먼저** 찍혔다.

```text
리스트 컴프리헨션                    제너레이터 표현식
── 시간 ─────────>                   ── 시간 ─────────>

[만드는 줄]                          [만드는 줄]
  계산:1 계산:2 계산:3                 (아무것도 안 함)
  -> [1,4,9]                          -> 주문표만

[쓰는 줄]                            [next() 첫 번째]
  이미 다 있다                          계산:1 -> 1
                                     [list() 로 나머지]
                                       계산:2 계산:3 -> [4, 9]
```

**핵심**

**괄호 하나가 계산 시점을 바꾼다.**\
대괄호는 "지금 전부", 소괄호는 "달라고 할 때 하나씩".\
`나머지: [4, 9]` 가 그 증거다 — 이미 하나를 꺼냈으므로 남은 것은 둘뿐이다. **되감기가 없다.**

**왜 이것이 중요한가**

계산 시점이 바뀌면 **부작용의 시점**도, **예외가 나는 줄**도(7번 답), **메모리 사용량**도(2번 답) 같이 바뀐다.\
식은 똑같이 생겼는데 프로그램의 성질이 달라진다.

### 2. 크기 (예측)

**출력**

```text
800984
192
```

- 리스트는 약 **800 KB**, 제너레이터는 **192 바이트**. 자릿수가 넷 이상 차이 난다.

**1000만 개로 늘리면**

```python
import sys
print(sys.getsizeof([n for n in range(10000000)]))
print(sys.getsizeof((n for n in range(10000000))))
```

```text
89095160
192
```

- 리스트는 약 **89 MB** 로 100배 늘었다 — **원소 수에 비례한다.**
- 제너레이터는 **192 바이트 그대로다** — **원소 수와 무관하다.**

```text
        원소 10만        원소 1000만
list    800,984 B  ──>   89,095,160 B     (비례해서 는다)
genexp      192 B  ──>          192 B     (안 는다)
```

**왜 무관한가**

제너레이터는 **값을 들고 있지 않다.** "어떻게 만드는지"와 "어디까지 왔는지"만 들고 있다.\
그래서 무한 수열도 담을 수 있다.

**주의 — `getsizeof` 가 재는 것**

`sys.getsizeof` 는 **그 객체 자체의 크기**만 잰다.\
리스트 800 KB 는 **정수 객체를 가리키는 포인터 10만 개**의 크기이고, 정수 객체들 자체의 크기는 **안 들어 있다.**\
그러니 실제 메모리 차이는 위 숫자보다 **더 크다.**

### 3. 이름이 새는 곳과 안 새는 곳 (예측)

**출력**

```text
A: 2
```

그리고 B 줄에서

```text
NameError: name 'j' is not defined
```

(B 에서 멈추므로 C 는 따로 돌려야 한다.)

```text
C: '원래 값'
```

**한 줄씩**

- **A** — `for` 문은 **바깥 스코프에서 돈다.** 루프가 끝나도 `i` 가 남는다. 마지막 값 `2`.
- **B** — 컴프리헨션의 타깃은 **감춰진 스코프 안에서만** 산다. 바깥에는 `j` 가 없다.
- **C** — 바깥에 같은 이름이 있어도 **덮어쓰지 않는다.** `'원래 값'` 그대로다.

```text
for 문                              컴프리헨션
+--------------------+             +----------------------------+
| for i in range(3): |             | [ j for j in range(3) ]    |
|     ...            |             |   j 는 이 안에서만 산다      |
| i 가 남는다 -> 2     |             +----------------------------+
+--------------------+              바깥의 i 도 안 건드린다
```

문서가 규정한다 — "**가장 왼쪽 `for` 절의 iterable 식을 빼면** 컴프리헨션은 별도의 감춰진 중첩 스코프에서 실행된다. 이것은 타깃 목록에 대입된 이름이 바깥 스코프로 **새지 않게** 보장한다."

**Python 2 와 다른 점**

Python 2 의 리스트 컴프리헨션은 **샜다.** Python 3 에서 바뀐 것이다.\
(3.12 의 인라인화(PEP 709)는 속도를 위해 프레임을 없앴지만 **이름 격리는 유지한다** — B 가 여전히 `NameError` 인 것이 그 확인이다.)

**실무에서 왜 고마운가**

`x`·`i`·`item` 같은 흔한 이름을 컴프리헨션 안에서 마음 놓고 쓸 수 있다.\
바깥의 같은 이름이 조용히 망가질 걱정을 안 해도 된다 — **단 하나만 빼고**(4번 답).

### 4. 왈러스는 샌다 (예측)

**출력**

```text
[0, 2, 4] | y = 4
```

- `y` 는 **살아남는다.** 값은 **마지막 값 4**.

**왜 3번과 다른가**

```text
[ (y := n * 2) for n in range(3) ]

   n  -> 감춰진 스코프에 묶인다   -> 안 샌다  (3번 답)
   y  -> 감싸는 스코프에 묶인다   -> 샌다
```

PEP 572 가 그렇게 정했다 — 컴프리헨션 안의 대입식(`:=`)은 **컴프리헨션을 감싸고 있는 스코프**에 타깃을 바인딩한다.\
`for` 타깃(`n`)과 왈러스 타깃(`y`)은 **같은 대괄호 안에 있어도 운명이 다르다.**

**남는 값이 마지막 하나인 이유**

컴프리헨션이 세 번 도는 동안 `y` 에 0, 2, 4 가 차례로 들어갔다. 마지막 대입이 이긴다.

**언제 쓸모 있나**

필터와 결과에서 같은 계산을 두 번 하지 않게 한다.

```python
[y for n in xs if (y := f(n)) > 0]      # f(n) 을 한 번만 부른다
```

**언제 사고가 되나**

- 이름을 흔한 것(`x`·`i`·`result`)으로 두면 **바깥 변수를 조용히 덮어쓴다.**
- 「컴프리헨션 안의 이름은 안 샌다」는 규칙을 외운 사람이 **이 예외를 모른 채 읽는다.**

### 5. 클래스 몸통에서는 `NameError` (예측)

**출력**

```text
NameError: name 'factor' is not defined
```

**`rows` 는 되고 `factor` 는 안 되는 이유**

두 이름이 **서로 다른 자리에서 평가되기 때문이다.**

```text
    scaled = [ r * factor  for r in rows ]
                   ^^^^^^          ^^^^
                     |               |
                     |               +-- 가장 왼쪽 for 의 iterable
                     |                   -> 바깥 스코프(= 클래스 몸통)에서 평가
                     |                   -> rows 가 보인다
                     |
                     +-- 감춰진 스코프 안에서 평가
                         -> 클래스 몸통은 중첩 스코프의 탐색 경로에 없다
                         -> factor 를 못 찾는다
```

- 문서가 그 갈림을 규정한다 — "**가장 왼쪽 `for` 절의 iterable 식은 바깥 스코프에서 직접 평가되어** 감춰진 중첩 스코프에 인자로 넘어간다."
- 그리고 **클래스 몸통의 이름은 중첩 함수(여기서는 감춰진 스코프)에서 보이지 않는다.** 클래스 스코프는 이름 탐색 사슬(LEGB)에 끼지 않는다(목록의 21번 주제).
- 즉 이것은 컴프리헨션의 버그가 아니라 **두 스코프 규칙이 맞물린 결과**다.

**되는 판**

```python
class TableOK:
    factor = 10
    rows = [1, 2, 3]
    scaled = [r * 10 for r in rows]

print(TableOK.scaled)
```

```text
[10, 20, 30]
```

**고치는 세 가지 길**

1. 값을 직접 쓴다 (`r * 10`).
2. 클래스 밖에서 만들어 대입한다.
3. **가장 왼쪽 `for` 의 iterable 에 실어 보낸다** — 그 자리만 클래스 몸통에서 평가되기 때문이다.

```python
class TableZip:
    factor = 10
    rows = [1, 2, 3]
    scaled = [r * f for r, f in zip(rows, [factor] * len(rows))]

print(TableZip.scaled)
```

```text
[10, 20, 30]
```

**안 되는 우회 하나 — 기본 인자로 밀어 넣기**

```python
class TableLambda:
    factor = 10
    rows = [1, 2, 3]
    scaled = [(lambda r, f=factor: r * f)(r) for r in rows]
```

```text
NameError: name 'factor' is not defined
```

`lambda` 의 **기본값 식도 그 `lambda` 가 놓인 자리에서** 평가된다.\
그 자리가 감춰진 스코프 안이므로 `factor` 를 여전히 못 찾는다 — 함정이 한 겹 더 깊어질 뿐이다.

실무에서는 대개 **클래스 변수 대신 `__init__` 안에서 만든다.**

### 6. 중첩 순서와 중복 (예측)

**출력**

```text
[('x', 1), ('x', 2), ('y', 1), ('y', 2)]
{'a': 3, 'b': 2}
{0, 1, 2}
```

**한 줄씩**

**첫 줄 — 중첩은 쓴 순서 그대로**

```text
[(a, b) for a in "xy" for b in (1, 2)]

   for a in "xy":          <- 왼쪽 for 가 바깥 루프
       for b in (1, 2):    <- 오른쪽 for 가 안쪽 루프
           (a, b) 를 담는다
```

`a='x'` 가 고정된 채 `b` 가 1, 2 를 돌고, 그 다음 `a='y'` 로 넘어간다.\
**`for` 문으로 풀어 쓴 것과 같은 순서**다 — 그것이 외울 필요가 없는 이유다.

**둘째 줄 — 키가 겹치면 뒤엣것이 이긴다**

```text
pairs = [("a", 1), ("b", 2), ("a", 3)]
                ↓                ↓
   'a' -> 1  먼저 들어감     'a' -> 3  덮어씀
   결과: {'a': 3, 'b': 2}
```

- 값은 **3**, 위치는 **처음 넣은 자리**(맨 앞).\
  dict 의 삽입 순서 보장은 3.7+ 언어 보증이다(목록의 12번 주제).
- 원소 3개가 2개가 됐는데 **아무 경고도 없다.** 조용한 데이터 손실이다.
- 중복이 의미 있으면 `collections.defaultdict(list)` 로 모은다(목록의 43번 주제).

**셋째 줄 — set 은 중복을 지운다**

`range(5)` 의 `n % 3` 은 0, 1, 2, 0, 1 → `{0, 1, 2}`.\
set 에는 순서 보장이 없다. 작은 정수라 오름차순으로 보일 뿐이고, **그 순서에 기대면 안 된다**(목록의 13번 주제).

### 7. 예외가 나는 줄 (예측)

**답** — **(a)** 와 **(d)** 두 곳이다.

```text
(a) bad = [10 // n for n in data]    -> 이 줄에서 ZeroDivisionError
(b) lazy = (10 // n for n in data)   -> 조용하다
(c) first = next(lazy)               -> 10 을 돌려준다 (data[0] == 1)
(d) second = next(lazy)              -> 여기서 ZeroDivisionError
```

**실행 확인**

```python
data = [1, 0, 2]
try:
    bad = [10 // n for n in data]
except ZeroDivisionError as e:
    print("리스트: 만드는 중에 터짐 —", e)

lazy = (10 // n for n in data)
print("제너레이터: 만들 때는 조용함 —", lazy)
print("첫 값:", next(lazy))
try:
    next(lazy)
except ZeroDivisionError as e:
    print("꺼낼 때 터짐 —", e)
```

```text
리스트: 만드는 중에 터짐 — integer division or modulo by zero
제너레이터: 만들 때는 조용함 — <generator object <genexpr> at 0x714e6e5af9f0>
첫 값: 10
꺼낼 때 터짐 — integer division or modulo by zero
```

**그림으로**

```text
리스트 컴프리헨션                     제너레이터 표현식
 [만드는 줄]  ← 여기서 터진다          [만드는 줄]  조용
                                     [next 1]    10
                                     [next 2]  ← 여기서 터진다

 try 를 만드는 줄에 두면 잡힌다        try 를 꺼내는 줄에 둬야 잡힌다
```

**실무에서 물리는 두 자리**

1. **예외 처리의 위치가 어긋난다.**\
   제너레이터를 만드는 함수가 `try` 로 감싸고 있어도, 예외는 **호출자 쪽**에서 난다.
2. **자원의 수명이 어긋난다.**

```python
def lines(path):
    with open(path) as f:
        return (line.strip() for line in f)   # 위험
```

`with` 블록은 `return` 과 함께 끝나 파일을 닫는다.\
소비하려 할 때는 이미 닫혀 있어 `ValueError: I/O operation on closed file` 이 난다.\
`yield` 를 쓰거나(17번 주제), 그 자리에서 `list()` 로 물질화해야 한다.

**예외 — 가장 왼쪽 `for` 의 iterable 은 즉시 평가된다**

```python
lazy = (x for x in undefined_name)     # 이 줄에서 바로 NameError
```

문서 표현 — "가장 왼쪽 `for` 절의 iterable 식은 즉시 평가되므로, 그것이 내는 에러는 **제너레이터 표현식이 정의된 자리**에서 나온다."

### 8. 소진 — `in` 도 먹어 치운다 (경계)

**출력**

```text
True
False
[]
```

**왜 그런가**

```text
g = (n for n in range(5))      남은 것: 0 1 2 3 4

3 in g   -> 0,1,2,3 을 꺼내 보고 찾았다     -> True     남은 것: 4
3 in g   -> 4 를 꺼내 보고 못 찾았다         -> False    남은 것: 없음
list(g)  -> 꺼낼 것이 없다                  -> []
```

- `in` 은 **읽기 연산처럼 보이지만 소비한다.** 찾자마자 멈추므로 4는 남았다.
- 둘째 `False` 는 "3이 없다"가 아니라 "**남은 것 중에 없다**"다.
- `list(g)` 의 `[]` 는 **예외가 아니다.** 소진된 이터레이터는 "원소가 0개인 것"과 구별되지 않는다(17번 주제 3번 답).

**리스트로 바꾸면**

```python
g = [n for n in range(5)]
print(3 in g)      # True
print(3 in g)      # True
print(list(g))     # [0, 1, 2, 3, 4]
```

**세 줄이 전부 달라진다.** 리스트는 몇 번 읽어도 줄지 않는다.

```text
제너레이터 표현식                     리스트 컴프리헨션
 True / False / []                   True / True / [0,1,2,3,4]
 읽을 때마다 줄어든다                  몇 번 읽어도 그대로다
```

**판정 기준 — 무엇을 고를 것인가**

| 묻는 것 | 답 |
|---|---|
| 결과를 **두 번 이상** 쓸 것인가 | 그렇다면 **리스트** |
| `len`·인덱싱·정렬이 필요한가 | 그렇다면 **리스트** |
| 원소가 아주 많거나 무한한가 | 그렇다면 **제너레이터** |
| `sum`·`any`·`all`·`max` 에 **바로** 넣는가 | 그렇다면 **제너레이터** (중간 리스트가 필요 없다) |
| 앞쪽 몇 개만 볼 수도 있는가 | 그렇다면 **제너레이터** |
| 부작용(저장·전송·출력)이 목적인가 | **둘 다 아니다 — `for` 문** |

한 문장으로: **「목록이 필요하면 리스트, 흐름이 필요하면 제너레이터, 일을 시키려면 `for` 문.」**

## 실행 검증

이 파일에 실린 출력은 전부 아래 환경에서 직접 돌려 얻었다.

```text
$ python3 --version
Python 3.12.3
```

- 1번 — `mark()` 로 계산 시점 추적(리스트/제너레이터)
- 2번 — `sys.getsizeof` 를 10만·1000만 두 규모로
- 3번 — `for` 뒤의 `i`, 컴프리헨션 뒤의 `j`(NameError), 바깥 `i` 보존
- 4번 — 왈러스 타깃의 유출
- 5번 — 클래스 몸통의 `NameError` 와 되는 판
- 6번 — 중첩 순서, dict 중복 키, set 중복 제거
- 7번 — 리스트/제너레이터의 예외 시점
- 8번 — `in` 두 번과 `list(g)`
- 부록 — `[n if n > 2 for n in range(5)]` 의 `SyntaxError: expected 'else' after 'if' expression`, `timeit` 4종, 3.12 트레이스백 두 형태

스코프 규칙과 평가 시점은 **언어 보장**이다.\
`getsizeof` 가 내놓는 숫자와 `timeit` 수치, PEP 709 의 트레이스백 모양은 **CPython 3.12 의 구현**에 달려 있다.
