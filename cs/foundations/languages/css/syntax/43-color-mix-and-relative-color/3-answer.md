# css/syntax/43 — `color-mix()` 와 상대 색 구문 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 질문 → 서머리 → 여기 순서다.
> 번호는 [1-question.md](1-question.md)와 1:1 이다. **출력을 먼저, 해설은 그 뒤.**
> 모든 계산값은 **Google Chrome 151.0.7922.173** headless 에서 받은 것이고, 모든 RGB 는 **스크린샷 PNG 의 픽셀을 파이썬으로 읽은 값**이다.

### 1. 같은 두 색을 다른 공간에서 섞으면

**출력**

```text
선언                                         계산값                            픽셀
-------------------------------------------  -------------------------------  -----------------
color-mix(in srgb,        #ff0000, #00ffff)  color(srgb 0.5 0.5 0.5)          rgb(128, 128, 128)
color-mix(in srgb-linear, #ff0000, #00ffff)  color(srgb-linear 0.5 0.5 0.5)   rgb(188, 188, 188)
color-mix(in oklab,       #ff0000, #00ffff)  oklab(0.766676 0.0377 0.0432)    rgb(210, 169, 147)
color-mix(in hsl,         #ff0000, #00ffff)  color(srgb 0.5 1 0)              rgb(128, 255,   0)
```

**「보색을 반씩 섞으면 회색」은 `in srgb` 에 대해서만 참이다.** `in srgb-linear` 도 무채색이지만 **더 밝은** 무채색이고, 나머지 둘은 회색이 아니다.

**왜 그런가**

- **`in srgb`** — R·G·B 를 각각 평균한다. `#ff0000` 과 `#00ffff` 는 채널별로 정확히 서로의 보수(`255↔0`)라 셋 다 `0.5` 가 된다. 세 수가 같으면 무채색이다.
- **`in srgb-linear`** — 감마를 푼 「빛의 양」으로 평균한다. 세 수가 여전히 같아 무채색이지만, 다시 감마를 씌우면 `0.5` 가 **`188`** 로 올라온다. **같은 회색이 아니다.**
- **`in oklab`** — 이 좌표계에서 빨강과 청록은 원점 기준 정반대가 **아니다.** 중간점이 무채색 축에 안 떨어져 베이지가 나온다.
- **`in hsl`** — 극좌표 공간이라 **색상 각도를 따라 돈다.** 빨강(0°)에서 청록(180°)으로 가면서 노랑·연두를 거치고, 중간점인 90°가 연두다. **무채색 근처를 아예 안 지난다.**

```text
  직교 공간                          극좌표 공간
  두 점을 직선으로                   각도를 따라 호를 그린다

  빨강 ●───────● 청록                빨강(0°) ●
        ↑ 중간                                 \  ← 노랑(60°)
   무채색 축 위이거나 근처                       \
                                       연두(90°) ● ← 중간점
                                                  \
                                        청록(180°) ●
```

### 2. `in` 을 빼면

**출력**

```text
.a  color-mix(srgb, red, blue)     cssText = ""  [[버려짐]]
.b  color-mix(in srgb, red, blue)  cssText = "background: color-mix(in srgb, red, blue);"

화면 — .a 는 배경 없는 상자로 보인다. 콘솔에 아무 말도 없다.
```

**진단 3창 중 창 1**(`cssRules[j].style.cssText`)로 잡힌다.

**왜 그런가**

- `in <공간>` 은 **선택 사항이 아니라 문법의 일부**다. 빠지면 파서가 함수를 못 읽고 **선언 하나를 통째로** 버린다.
- CSS 는 에러가 없는 언어라 **화면에도 콘솔에도 아무 흔적이 없다.** 창 2(선택자가 안 잡혔다)·창 3(캐스케이드에서 졌다)과 증상이 똑같다.

### 3. `cssText` 에서 사라지는 것

**출력**

```text
적은 것                                   cssText
----------------------------------------  ------------------------------------------
color-mix(in oklab, red, blue)            color-mix(red, blue)                  ★ 달라졌다
color-mix(in srgb, red, blue)             color-mix(in srgb, red, blue)
color-mix(in hsl shorter hue, red, cyan)  color-mix(in hsl, red, cyan)          ★ 달라졌다
color-mix(in hsl longer hue, red, cyan)   color-mix(in hsl longer hue, red, cyan)
```

**달라지는 둘은 `in oklab` 과 `shorter hue` 다.**

**왜 그런가**

- **둘 다 기본값이기 때문이다.** 보간 색 공간의 기본은 `oklab`, 색상 보간법의 기본은 `shorter hue` 다.
- CSSOM 의 직렬화는 **기본값을 생략한다.** 값이 바뀐 게 아니라 **적는 방식**이 바뀐 것이다 — 계산값은 그대로 `oklab(...)` 으로 나온다.
- ★ 그래서 **「`cssText` 에 `in oklab` 이 없으니 안 먹었다」는 오진**이다. 오히려 먹었다는 증거다.

### 4. 비율을 둘 다 적으면

**출력**

```text
선언                                   계산값                          흰 배경 위 픽셀
-------------------------------------  -----------------------------  -----------------
color-mix(in srgb, red, blue)          color(srgb 0.5 0 0.5)          rgb(128,   0, 128)
color-mix(in srgb, red 20%, blue 20%)  color(srgb 0.5 0 0.5 / 0.4)    rgb(204, 153, 204)
color-mix(in srgb, red 150%, blue)     ""  [[버려짐]]                  (배경 없음)
```

**`.b` 가 연한 것은 색이 달라져서가 아니라 알파가 0.4 로 붙었기 때문이다.** 색 성분은 `.a` 와 똑같다.

**왜 그런가**

```text
  적은 비율  red 20% , blue 20%
                └──┬──┘
                합이 40%
                   │
     ┌─────────────┴──────────────┐
     │                            │
  비율은 50:50 으로 정규화        합 40% 가 결과의 알파가 된다
  (색 성분은 red, blue 반반)      (0.4)
```

- 비율 **하나만** 적으면 나머지가 자동으로 채워지므로 이 함정이 아예 없다.
- `150%` 는 `0\~100%` 밖이라 **선언째 버려진다.** 합이 0 인 `red 0%, blue 0%` 도 마찬가지다.

### 5. `longer hue` 가 하는 일

**출력**

```text
선언                                       계산값                픽셀
-----------------------------------------  --------------------  -----------------
color-mix(in hsl shorter hue, red, blue)   color(srgb 1 0 1)     rgb(255,   0, 255)   자홍
color-mix(in hsl longer hue,  red, blue)   color(srgb 0 1 0)     rgb(  0, 255,   0)   초록
```

**빨강과 청록으로 같은 실험을 하면 두 칸이 같아진다** — 실측 결과 둘 다 `color(srgb 0.5 1 0)` 였다.

**왜 그런가**

```text
  빨강(0°) ↔ 파랑(240°)              빨강(0°) ↔ 청록(180°)

        0°(빨강)                            0°(빨강)
      ／    ＼                            ／      ＼
  300°        60°                     270°          90°
   │           │                        │            │
  240°       120°                     180°(청록)   ← 어느 쪽으로 돌든 180°
  (파랑)      ＼／                       ＼        ／
        180°                              긴 쪽과 짧은 쪽이 같다

  shorter : 120° 만 돈다 → 중간 300° = 자홍
  longer  : 240° 를 돈다 → 중간  60° = 초록      보색은 shorter = longer
```

- 각도 차가 정확히 180도면 **어느 쪽으로 돌아도 거리가 같다.** 그래서 두 법이 같은 결과를 낸다.
- `longer hue` 는 **직교 공간(`srgb`·`oklab`·`lab`)에서는 아무 의미가 없다** — 각도라는 축이 없기 때문이다.

### 6. 상대 색 구문에서 조용히 죽는 선언

**출력**

```text
선언                                       cssText
-----------------------------------------  -----------------------------------------------
hsl(from #3b82f6 h s calc(l + 20%))        ""  [[버려짐]]  ★
hsl(from #3b82f6 h s calc(l + 20))         "background: hsl(from rgb(59, 130, 246) h s calc(20 + l));"
oklch(from #3b82f6 calc(l + 0.2) c h)      "background: oklch(from rgb(59, 130, 246) calc(0.2 + l) c h);"
```

**빈 문자열은 첫째다.**

**왜 그런가**

- **상대 색 구문 안에서 축 이름은 `<number>` 로 치환된다.** `hsl()` 의 `l` 은 `50%` 라는 백분율이 아니라 **`50` 이라는 수**다.
- 그래서 `calc(l + 20%)` 는 **수 + 백분율**이 되어 타입이 안 맞고 선언이 통째로 버려진다.

**`20` 과 `0.2` 가 다른 수인 이유**

```text
  같은 글자 l, 다른 스케일

  hsl(from … h s l)     l ∈  0 \~ 100     "20% 밝게" = calc(l + 20)
  oklch(from … l c h)   l ∈  0 \~ 1       "20% 밝게" = calc(l + 0.2)
                             ↑ 여기서 20 을 더하면 1 을 한참 넘겨 흰색이 된다
```

### 7. `from` 뒤에 무엇을 넣을 수 있나

**전부 된다. 공간이 달라도 된다.**

```text
  실측
  oklch(from #3b82f6 l c h)         → oklch(0.623066 0.187997 259.821)   hex 를 받았다
  oklch(from var(--c) l c h)        → oklch(0.623066 0.187997 259.821)   var() 도 받았다
  oklch(from red l c calc(h + 180)) → oklch(0.627966 0.257704 209.235)   이름 있는 색도
  rgb(from red calc(255 - r) g b)   → color(srgb 0 0 0)
```

- `from` 은 **색을 받아 바깥 함수의 축으로 분해**한다. 그래서 `oklch(from #3b82f6 …)` 처럼 **입력 공간과 출력 공간이 달라도 된다.**
- 축 이름은 **바깥 함수**가 정한다 — `oklch()` 안에서는 `l`·`c`·`h`, `rgb()` 안에서는 `r`·`g`·`b`.
- **각도는 360 을 넘기면 한 바퀴 접힌다**(실측): `259.821 + 180 = 439.821` 을 적었는데 계산값은 `79.8207` 이었다.

### 8. `rgb(from red calc(255 - r) g b)` 는 무슨 색인가

**출력**

```text
계산값  color(srgb 0 0 0)      (검정)
```

**계산**

```text
  red 를 rgb 축으로 분해  →  r = 255,  g = 0,  b = 0
  calc(255 - r)           →  255 - 255 = 0
  g, b                    →  그대로 0, 0
  결과                    →  rgb(0 0 0) = 검정
```

**함수 이름이 `rgb(` 가 아닌 이유**

- 상대 색 구문의 결과는 **`color(srgb …)` 형태로 직렬화된다**(실측). 레거시 `rgb()` 형태로 안 접힌다.
- `color(srgb …)` 는 **0\~1 스케일**이라 `rgb()` 의 0\~255 와 숫자 모양이 다르다. 문자열로 대조하면 안 맞는다.

### 9. 흰색과 섞기와 `l` 올리기의 차이

**출력** — `#3b82f6`(oklch 로 `0.623066 0.187997 259.821`)을 두 방법으로 밝혔다.

```text
  방법                                                계산값을 oklch 로 다시 읽은 것       픽셀
  --------------------------------------------------  ---------------------------------  -----------------
  (기준) #3b82f6                                      oklch(0.623066 0.187997 259.821)   rgb( 59, 130, 246)
  color-mix(in oklab, #3b82f6 80%, white)             oklch(0.698451 0.150392 259.824)   rgb(100, 157, 250)
  oklch(from #3b82f6 calc(l + 0.15) c h)              oklch(0.773066 0.187997 259.821)   rgb(105, 179, 255)
  color-mix(in srgb, #3b82f6 80%, white)              oklch(0.692314 0.149802 259.768)   rgb( 98, 155, 248)
```

**흰색과 섞으면 크로마(선명함)를 잃는다.**

```text
  기준         c = 0.187997
  흰색과 섞기  c = 0.150392   ← 20% 쯤 떨어졌다
  l 올리기     c = 0.187997   ← 한 글자도 안 변했다
```

- **흰색과 섞는다 = 무채색 쪽으로 끌어간다.** 밝아지면서 **동시에 흐려진다.**
- **`l` 만 올린다 = 밝기 축만 움직인다.** 선명함과 색상은 그대로다.
- 어느 쪽이 좋은지는 용도에 달렸다 — **연한 배경**을 원하면 흰색과 섞는 쪽이 자연스럽고, **같은 색의 밝은 단계**를 원하면 `l` 쪽이다.

### 10. `color-mix()` 와 `mix-blend-mode` 는 무엇이 다른가

**`color-mix()` 는 「값」을 섞고, `mix-blend-mode` 는 「그려진 픽셀」을 섞는다.**

```text
  ① color-mix()      값 단계에서 두 색 → 한 색
                     결과가 계산값에 보인다.  getComputedStyle 로 읽힌다 ★
                     ↓
  ② 그 색으로 칠한다
                     ↓
  ③ mix-blend-mode   그려진 결과를 아래 레이어와 합성한다
     ([목록의 **48번**](../48-blend-modes-and-isolation/))    계산값에는 아무 흔적이 없다.  픽셀을 읽어야 안다 ★
```

- `color-mix()` 의 피연산자는 **선언에 적힌 두 색**이다. 아래에 무엇이 있는지 모른다.
- 혼합 모드의 피연산자 중 하나는 **아래에 실제로 그려진 것**이다. 같은 선언이 **배경에 따라 다른 결과**를 낸다.
- 그래서 진단 방법이 갈린다 — 전자는 창 3(`getComputedStyle`), 후자는 **스크린샷의 픽셀**.

### 11. 셋을 섞으려면

**중첩한다.**

```css
color-mix(in oklab, color-mix(in oklab, red, blue), lime)
```

**출력**

```text
cssText   background: color-mix(color-mix(red, blue), lime);   ← in oklab 둘 다 생략됐다
계산값     oklab(0.703204 -0.0688157 0.043335)
픽셀       rgb(125, 174, 131)
```

- 인자가 둘뿐인 함수라 **셋 이상은 중첩으로만** 된다.
- **비율에 주의한다** — 위 형태는 `red`·`blue` 가 각각 25%, `lime` 이 50% 다. 셋을 고르게 섞으려면 바깥에서 `33.33%` 를 지정해야 한다.

### 12. 둘 중 무엇을 먼저 쓰나

**출력** (`webstatus.dev` API 조회, 2026-09-23)

```text
기능                   Baseline    low          high         Chrome  Firefox  Safari
---------------------  ----------  -----------  -----------  ------  -------  ------
color-mix()            widely      2023-05-09   2025-11-09   111     113      16.2
Relative colors        newly       2024-09-16   —            125     128      18
```

**지원 폭이 중요하면 `color-mix()` 를 기본으로 삼는다.**

- `widely` 는 「주요 브라우저에 들어간 지 충분히 오래돼 안심하고 쓸 수 있다」는 뜻이고, `newly` 는 「방금 다 들어갔다」는 뜻이다.
- 상대 색 구문이 필요하면 `@supports` 로 갈라 준다([목록의 **41번 주제**](../41-supports-feature-queries/)).

```css
.btn { background: color-mix(in oklab, var(--b) 80%, white); }   /* 어디서나 */
@supports (color: oklch(from red l c h)) {
  .btn { background: oklch(from var(--b) calc(l + 0.15) c h); }  /* 되는 곳에서만 */
}
```

**픽셀을 읽은 방법** — [42번의 같은 절](../42-color-notation-and-spaces/3-answer.md)과 동일하다. 한 줄로: `--screenshot` 으로 PNG 를 뽑고 `PIL.Image.open(f).convert('RGB').getpixel((x,y))` 로 읽는다.

★ **9번의 크로마 비교는 손계산이 아니다.** `oklab(...)` 계산값에서 크로마를 손으로 유도하지 않고, **결과 색을 `oklch(from … l c h)` 로 다시 감싸 브라우저가 계산한 좌표를 읽었다.**

**구현에 달린 항목 — 버전이 오르면 다시 찍을 것**

| 항목 | 왜 |
|---|---|
| 계산값의 소수 자릿수(`0.766676`) | CSSOM 직렬화 정밀도 |
| 기본값(`in oklab`·`shorter hue`)이 직렬화에서 생략되는 것 | 직렬화 규칙 |
| `rgb(from …)` 이 `color(srgb …)` 로 나오는 것 | 직렬화 형태 |
| 픽셀 RGB 의 마지막 1 단위 | 반올림 |
| 상대 색 구문의 Baseline | 아직 `newly` 다. 언젠가 `widely` 가 된다 |
