# css/syntax/17 — 서식 문맥(BFC) — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 **모든 치수는 Google Chrome 151.0.7922.173 headless 에서 실제로 렌더해 `getBoundingClientRect()`·`clientWidth` 로 잰 값**이다. 단위는 px 다.\
> ★ **「잘렸다」처럼 rect 로 잴 수 없는 것은 스크린샷이 근거**이며, 자리마다 어느 쪽인지 밝혔다.\
> 규칙은 [CSS Display Module Level 3](https://drafts.csswg.org/css-display-3/) 과 [CSS Overflow Module Level 3](https://drafts.csswg.org/css-overflow-3/) 으로 접지했다.

## 정답

### 1. BFC 는 무엇을 차단하는가

**한 문장 정의**

- **「안에서 일어난 일이 밖으로 새지 않고, 밖에서 일어난 일이 안으로 들어오지 않는 배치 구역」** 이다.
- 정확히는 **블록 상자들이 위에서 아래로 쌓이는 규칙이 도는 독립된 구역**이고, 문서의 루트 요소가 이미 하나의 BFC 다.

**차단하는 것 셋**

```text
  ① 자식의 마진이 부모 밖으로 새는 것      (마진 상쇄 차단)
  ② 안의 float 가 부모 높이에서 빠지는 것   (높이 붕괴 차단)
  ③ 바깥의 float 가 내 상자로 파고드는 것   (float 침범 차단)
```

- 셋은 **서로 다른 증상이지만 원인이 하나**다 — 그 상자가 독립 구역이 아니라는 것.

**`display: bfc` 가 없는 이유**

- BFC 는 **속성이 아니라 상태**다. 여러 선언의 **부수 효과**로 열린다.
- `overflow: hidden` 은 자르는 것이 목적이고, 자르려면 안쪽이 독립돼야 하니 **덤으로** BFC 가 열린다.

**직접 뜻하는 값 하나**

- **`display: flow-root`** 다. 「이 상자를 흐름의 뿌리로 삼아라」는 뜻이고, **부작용이 없는 유일한 수단**이다.

> **BFC 루트(BFC root)** — 새 BFC 를 연 그 상자. 자신은 **바깥 BFC 의 구성원**이고 안쪽만 새 구역이다.\
> 예: `display: flow-root` 를 준 `<div>` 는 자기 마진이 여전히 형제와 상쇄된다(6번).

### 2. 이 부모의 높이는 몇인가

**실행 결과** (Chrome 151 headless — `.p` 폭 240 · 테두리 2px · float 80×50)

```text
보통 블록        .p 의 rect.height = 4     (위아래 테두리뿐 — 안쪽 높이 0)
display:flow-root .p 의 rect.height = 54   (float 50 + 테두리 4)
```

**`.p` 의 `rect.height`**

- **4.** 위아래 테두리 2px 씩이 전부다. **안쪽 높이가 0 이다.**

**`display: flow-root` 를 주면**

- **54.** float 의 높이 50 이 그대로 들어온다.

**차이가 생기는 이유**

- **float 는 흐름에서 빠져 있어 부모의 높이 계산에 참여하지 않는다.** 그것이 float 의 정의다(정본은 목록의 **20번 주제**).
- **BFC 루트만은 예외로 자기 안의 float 까지 포함해 높이를 잡는다.** 이것이 「감싼다」의 뜻이다.

**바로 뒤 형제는 어디에**

- 보통 블록일 때 — **부모 바로 아래에서 시작한다.** 부모가 4px 뿐이므로 **float(높이 50)가 그 형제 위를 뚫고 내려와** 겹친다.\
  *(실측: 부모 bottom=122, 다음 형제 top=122 — 붙어 있는데 float 는 그 아래까지 내려와 있다.)*
- `flow-root` 일 때 — **float 아래**에 놓인다. *(실측: 부모 bottom=64, 다음 형제 top=64 — float 는 부모 안의 y=4\~64 에 있으므로 겹치지 않는다.)*

### 3. 이 상자는 얼마나 넓은가

**실행 결과** (Chrome 151 headless — `.col` 폭 300 · 테두리 2px · float 100×34)

```text
.t  (그냥 블록)       rect.x = 2     rect.width = 300
.t2 (display:flow-root) rect.x = 102   rect.width = 200
두 상자의 높이는 58.5 로 같다 (글 세 줄)
```

**`.t` 의 폭과 x**

- **x = 2, width = 300.** 즉 **컨테이너 안쪽을 통째로 차지한다.** float 밑까지 깔려 있다.

**`.t2` 의 폭과 x**

- **x = 102, width = 200.** float 의 폭 100 만큼 **상자 자체가 좁아지고 오른쪽으로 밀렸다.**

**무엇이 밀렸고 무엇은 안 밀렸나**

```text
  보통 블록                           BFC 상자
  +--------------------------+       +--------------------------+
  |[float]| 글줄만 밀린다    |       |[float]| 상자째 밀린다     |
  |       | 글줄            |       |       | 글줄            |
  | 상자 배경은 여기까지 깔림 |       |       | 글줄            |
  +--------------------------+       +--------------------------+
   상자: 안 밀림 / 줄: 밀림           상자: 밀림 / 줄: 상자 안에서 흐름
```

- 보통 블록에서 밀린 것은 **줄 상자(line box)뿐**이다. **블록 상자 자체는 float 밑에 그대로 깔려 있다.**
- BFC 상자에서는 **블록 상자 자체가** float 를 피한다.

**눈으로 구분하려면**

- **상자의 배경이 float 아래까지 이어지는지**를 본다. 보통 블록이면 float 가 끝나는 높이부터 배경이 왼쪽 끝까지 넓어진다.
- float 가 상자보다 키가 크면 **화면으로는 구분이 안 된다** — 그때는 `rect.x`·`rect.width` 를 재야 한다.

### 4. `overflow` 네 값 중 BFC 가 아닌 것

**실행 결과** (Chrome 151 headless — 부모 안에 float 만 넣고 부모 높이를 쟀다. 테두리 4 포함)

```text
overflow: hidden   rect.height = 54    감쌈
overflow: auto     rect.height = 54    감쌈
overflow: scroll   rect.height = 69    감쌈 (+15 = 가로 스크롤바)
overflow: clip     rect.height =  4    감싸지 않음

별도의 마진 실험에서도 clip 부모의 높이는 20 — 자식 마진이 밖으로 샜다.
```

**BFC 가 아닌 것**

- **`overflow: clip`** 이다.

**이유**

- `clip` 은 **스크롤 컨테이너를 만들지 않는다** — 정의상 스크롤이 불가능한 값이다.
- `hidden`·`auto`·`scroll` 은 스크롤 컨테이너를 만들고, 스크롤할 내용을 재려면 **안쪽이 독립된 구역이어야** 하므로 BFC 가 딸려 온다.
- `clip` 은 그 필요가 없으므로 **잘라 내기만 하고 안쪽을 독립시키지 않는다.**

**요약이 깨지는 곳**

- 「`overflow` 가 `visible` 이 아니면 BFC」 — **`clip` 에서 깨진다.**

**바르게 고친 한 문장**

- **「`overflow` 가 스크롤 컨테이너를 만드는 값(`hidden`·`auto`·`scroll`)이면 BFC 를 연다.」**

### 5. `flow-root` 대 `overflow: hidden`

**실행 결과** (Chrome 151 headless)

```text
flow-root 부모의 .big        rect 240 x 34   x=2
overflow:hidden 부모의 .big  rect 240 x 34   x=2     ← 완전히 같다
스크린샷: 앞은 테두리 밖까지 붉은 자식이 보이고, 뒤는 테두리에서 잘린다

overflow: auto 로 바꾸면    부모의 clientWidth 가 160 -> 145 (가로 스크롤바 15px)
overflow: scroll 로 바꾸면  부모 높이가 54 -> 69      (가로 스크롤바 15px)
```

**`.big` 의 `rect.width`**

- **둘 다 240.** 한 픽셀도 다르지 않다.

**화면에서는**

- `flow-root` — 자식이 부모 테두리를 **뚫고 나와 240px 전체가 보인다.**
- `overflow: hidden` — 자식이 **부모 테두리에서 딱 잘린다.** 오른쪽 부분이 화면에서 사라진다.

**`getBoundingClientRect()` 로 잴 수 있는가**

- ★ **없다.** 잘린 것은 **레이아웃이 아니라 페인트**이기 때문이다.
- 레이아웃 API 는 「어디에 얼마나 크게 놓였나」만 말한다. **「화면에 그려졌나」는 다른 층의 이야기다.**
- 이 자리의 근거는 **스크린샷**이고, 이 문서는 그것을 근거로 적었다. **「rect 가 같다」를 「같다」로 읽으면 틀린다.**

**`overflow: scroll` 로 바꾸면**

- 부모 높이가 **54 → 69 로 15px 늘어난다.** 가로 스크롤바가 **내용이 안 넘쳐도 늘 자리를 먹기** 때문이다.
- 이 15px 은 **이 플랫폼의 스크롤바 폭**이지 CSS 의 보장이 아니다 — 다른 OS·설정에서는 0 일 수도 있다.

### 6. `flow-root` 를 줬는데 안 막힌다

**실행 결과** (Chrome 151 headless)

```text
앞 형제         rect.bottom = 20   (margin-bottom: 30px)
.root           rect.top    = 50   rect.height = 60   (margin-top: 30px, flow-root)
.child          rect.top    = 90   (margin-top: 40px)

앞 형제와 .root 사이의 간격 = 50 - 20 = 30   (60 이 아니다)
```

**자식의 40px 마진은 새는가**

- **안 샌다.** `.root` 의 높이가 **60**(마진 40 + 자식 20)이고 자식이 `.root` 안쪽 40px 지점(top=90 = root top 50 + 40)에서 시작한다.

**`.root` 자신의 30px 마진은 상쇄되는가**

- **상쇄된다.** 앞 형제 bottom 20 과 `.root` top 50 의 간격이 **30** — 두 마진의 합 60 이 아니다.

**BFC 루트는 누구의 구성원인가**

- **바깥 BFC 의 구성원**이다. 새 BFC 를 「연」 것이지 그 안에 「들어간」 것이 아니다.

```text
   바깥 BFC
  ┌───────────────────────────────┐
  │  [앞 형제]                     │
  │     ↕ 여기서는 상쇄가 일어난다  │
  │  ┌───────────────────────────┐ │  <- .root 는 이 선 바깥 소속
  │  │  새 BFC (.root 안쪽)       │ │
  │  │    ↕ 여기서는 안 일어난다   │ │
  │  │  [자식]                    │ │
  │  └───────────────────────────┘ │
  └───────────────────────────────┘
```

- 그래서 **「`flow-root` 를 줬는데 위 형제와의 간격이 그대로다」는 고장이 아니다.** 막히는 것은 **자식의 마진**이지 자기 마진이 아니다.

### 7. 어느 선언이 BFC 를 여는가

**실행 결과** (Chrome 151 headless — 마진 실험에서 부모 높이 60 이면 갇힘 / 20 이면 샘, float 실험에서 54 면 감쌈 / 4 면 아님)

| 선언 | 마진 | float | BFC |
|---|---|---|---|
| 보통 블록 | 20 | 4 | ✗ |
| `display: flow-root` | 60 | 54 | ✓ |
| `overflow: hidden` / `auto` | 60 | 54 | ✓ |
| `overflow: scroll` | 75 | 69 | ✓ (+ 스크롤바 15px) |
| `overflow: clip` | **20** | **4** | **✗** |
| `float: left` | 60 | 54 | ✓ |
| `position: absolute` | 60 | 54 | ✓ |
| `display: inline-block` | 60 | 54 | ✓ |
| `display: table-cell` | 60 | 54 | ✓ |
| `display: grid` / `flex` | 60 | 54 | ✓ |
| `contain: layout` | 60 | 54 | ✓ |

**`position: absolute`**

- **연다**(실측 60 / 54). 다만 그 상자는 **흐름에서 빠져** 있어 마진 상쇄 이야기가 애초에 성립하지 않는 경우가 많다. 기준을 어디로 잡는가는 목록의 **21번 주제**.

**`display: inline-block`**

- **연다**(60 / 54). `inline-block` = `inline flow-root` 이므로 **안쪽 값이 `flow-root`** 다([16번](../16-display-inner-outer/2-summary.md)). 당연한 결과다.

**`contain: layout`**

- **연다**(60 / 54). 본래 목적은 렌더 비용을 가두는 컨테인먼트이고 BFC 는 덤이다(목록의 **56번 주제**).

**목록이 잡다해 보이는 이유**

- **BFC 가 이 선언들의 목적이 아니라 부수 효과**이기 때문이다. 목적이 제각각이니 목록도 제각각으로 보인다.
- 공통점을 굳이 찾자면 **「안쪽을 독립적으로 재야 하는 사정이 생기는 선언들」** 이다 — 자르려면, 스크롤하려면, 격자를 짜려면 안쪽을 따로 재야 한다.
- ★ **`flex`·`grid` 는 「감쌌다」의 기제가 다르다.** 그 자식은 flex/grid 항목이 되어 **`float` 선언 자체가 무시**되므로 애초에 삐져나갈 float 가 없다. 높이가 살아난 결과만 같다.

### 8. 옛 관용구를 오늘 다시 쓴다면

**`::after { content: ""; display: block; clear: both }` 가 하려던 것**

- **높이 붕괴를 우회하는 것**이다. 마지막에 빈 블록을 하나 만들어 `clear` 를 걸면, 그 빈 블록이 float 아래로 내려가면서 **부모 높이를 float 아래까지 끌어내린다.**
- 감싼 것이 아니라 **바닥에 받침대를 하나 더 놓은** 것에 가깝다.

**오늘 한 줄로**

- **`display: flow-root`.**

**`overflow: hidden` 의 부작용 둘**

- ① **넘치는 것이 잘린다** — 드롭다운·툴팁·포커스 링이 사라진다. 실측에서 240px 자식이 화면에서 부모 테두리에 잘렸다(5번).
- ② **스크롤 컨테이너가 된다** — `position: sticky` 의 기준, 스크롤 앵커링, 키보드 스크롤 대상이 달라진다(목록의 **23번 주제**).
- 그리고 ①은 **`getBoundingClientRect()` 로 관찰되지 않아** 한참 뒤에 발견된다는 점이 특히 나쁘다.

**두 값 `display` 로 풀면**

- **`block flow-root`** 다. 바깥 `block`, 안 `flow-root`([16번](../16-display-inner-outer/2-summary.md)).
- 실측에서 `display: block flow-root` 의 계산값이 `flow-root` 로 돌아왔다.

### 9. 다른 주제와 잇기

**float·`clear` 의 정본**

- 목록의 **20번 주제**(부동과 해제)다.
- ★ **이 문서의 경계선**: 여기는 **「BFC 가 float 를 감싸고 피한다」는 효과**까지이고, **float 자체가 무엇을 밀어내고 `clear` 가 무엇을 하는지는 20번**이다.

**마진 상쇄의 정본**

- [18번 주제](../18-margin-collapsing/2-summary.md)(마진 상쇄 — 인접·부모-자식·빈 상자)다.
- 여기는 **BFC 가 막는 법 중 하나**라는 것까지다.

**BFC 와 쌓임 맥락은 같은가**

- **다르다.** 쌓임 맥락은 **z 방향의 그리기 순서**를 정하고, BFC 는 **평면상의 배치 규칙**을 정한다.
- `opacity`·`transform`·`filter` 는 쌓임 맥락을 만들지만 BFC 와는 무관하다.
- 둘을 섞으면 「`z-index` 가 안 먹는다」와 「마진이 샌다」를 같은 원인으로 오진한다. 쌓임 맥락은 목록의 **22번 주제**.

**flex 항목에 마진 상쇄가 없는 이유**

- **flex 항목은 각각 BFC 를 연다**(실측: flex 부모의 높이가 60 으로 자식 마진을 가뒀다).
- 더 근본적으로는 **flex 서식 문맥에는 마진 상쇄라는 규칙이 아예 없다** — 상쇄는 **블록 서식 문맥의 규칙**이기 때문이다.
- 실측과 demo 는 [18번](../18-margin-collapsing/2-summary.md)에 있고, flex 의 배치 규칙 자체는 [24번](../24-flexbox-axes/2-summary.md)이 정본이다.

## 용어 풀이

- **서식 문맥** — 상자들의 배치 규칙이 도는 독립된 구역.
- **블록 서식 문맥(BFC)** — 블록 상자가 위에서 아래로 쌓이는 규칙이 도는 구역. 루트 요소가 이미 하나다.
- **BFC 루트** — 새 BFC 를 연 상자. **자신은 바깥 BFC 의 구성원**이다.
- **`display: flow-root`** — 「BFC 를 열어라」를 직접 뜻하는 유일한 값. 두 값으로는 `block flow-root`.
- **높이 붕괴** — 안에 float 만 있는 상자의 높이가 0 이 되는 것. float 가 높이 계산에 참여하지 않기 때문이다.
- **clearfix** — 의사 요소와 `clear` 로 높이 붕괴를 우회하던 옛 관용구.
- **줄 상자(line box)** — 한 줄의 글이 차지하는 상자. float 가 미는 것은 블록 상자가 아니라 이것이다.
- **스크롤 컨테이너** — 안쪽을 스크롤할 수 있는 상자. `overflow` 가 `hidden`·`auto`·`scroll` 일 때 생긴다. **`clip` 은 만들지 않는다.**
- **컨테인먼트** — `contain` 으로 렌더 작업을 상자 안에 가두는 최적화. `layout` 값은 덤으로 BFC 를 연다.
- **쌓임 맥락(stacking context)** — z 방향 그리기 순서를 정하는 구역. **BFC 와 무관하다.**
