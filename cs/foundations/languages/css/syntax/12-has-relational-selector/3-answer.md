# css/syntax/12 — `:has()`: 관계 선택자와 그 한계 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 **모든 매치 수 · 모든 `(A, B, C)` 값 · 모든 「담김/버림」 판정은 Google Chrome 151.0.7922.173 headless 에서 실제로 돌려 확인한 것**이다.\
> 근거를 세 층으로 나눠 뽑았다 — `cssRules`(규칙이 담겼나) · `querySelectorAll().length`(무엇이 잡혔나) · `getComputedStyle`(무엇이 이겼나).\
> **명시도 값은 전부 세 번째 층으로만** 확인했다(동점 경쟁자 · 한 칸 낮은 경쟁자 두 판 — 방법은 [02번 주제](../02-specificity/2-summary.md)).\
> 규칙은 [Selectors Level 4 §4.5](https://drafts.csswg.org/selectors-4/#relational) 로 접지했다. **엔진은 Chrome 하나이며, 성능은 재지 않았다.**

## 정답

<!-- 1-question.md 의 번호·문구와 1:1 대응. 질문 하나 = A 하나. -->

### 1. 무엇이 잡히는가

**실행 결과** (Chrome 151 headless, `querySelectorAll().length` 와 잡힌 `id`)

```text
.card:has(img)   ->  2개  [c1, c3]
img              ->  2개  [img, img]      <- 비교용
```

**파란 테두리가 그려지는 요소**

- **`.card` 다.** `img` 에는 아무것도 걸리지 않는다.

```text
   <div class="card" id="c1">      <-- ★ 여기에 테두리가 그려진다
        ├── <h3>
        ├── <img>                  <-- 조건일 뿐. 안 잡힌다
        └── <p>
```

- `:has()` 앞에 쓴 것이 **기준 요소**이고, 그것이 곧 선택 결과다.

**몇 개를 돌려주는가**

- **2개 — `c1` 과 `c3`.**
- `c3` 은 `img` 가 `p` 안에 들어 있지만 **자손이면 되므로** 잡힌다.

**이미지 자체에 테두리를 주려면**

```css
.card:has(img) img { border: 2px solid blue; }
```

- 한 칸 더 내려가야 한다. `:has()` 는 **조건을 얹을 뿐 선택 대상을 옮기지 않는다.**

**조합자의 방향을 뒤집는다고 말해도 되는가**

- **안 된다.** 조합자는 여전히 오른쪽으로만 간다.
- `:has()` 는 **선택 대상을 왼쪽에 그대로 두고, 오른쪽을 「존재 조건」으로만 읽는** 문법이다.
- 결과적으로 「부모를 고를 수 있게」 되지만, 그것은 **방향이 뒤집혀서가 아니라 조건과 선택을 분리해서**다.

### 2. `>` 를 넣으면 무엇이 달라지는가

**실행 결과**

```text
.card:has(img)    ->  2개  [c1, c3]
.card:has(> img)  ->  1개  [c1]
```

**몇 개를 잡는가 · 어느 카드가 갈리는가**

- `.card:has(> img)` 는 **1개(`c1`)** 다.
- 갈리는 것은 **`c3`** 이다 — 그 카드의 `img` 는 `p` 안에 있어 **손자**이고, `> img` 는 직계 자식만 본다.

```text
   c1                         c3
   .card                      .card
    ├ h3                       └ p
    ├ img   <- 직계 자식 ✔        └ img  <- 손자 ✘
    └ p
```

**조합자를 안 쓰면**

- **자손 조합자(공백)가 암묵으로 붙는다.** `:has(img)` = `:has( img)` = 「자손 어디엔가 `img`」.
- 명세가 `:has()` 의 인자를 `<relative-selector-list>`(상대 선택자 목록)로 정하기 때문이다.

**명시도는 다른가**

- **같다.** 둘 다 `p:has(...)` 기준으로 **(0, 0, 2)** 였다.
- 조합자는 어느 자리에도 0 을 보탠다 — [02번 주제](../02-specificity/2-summary.md)의 규칙 그대로다.

### 3. 형제를 조건으로 쓴다

**실행 결과**

```text
.card:has(+ .card)  ->  3개  [c1, c2, c3]
.card:has(~ .card)  ->  3개  [c1, c2, c3]
h3:has(+ img)       ->  1개  [c1 안의 h3]
```

**어느 카드들을 잡는가**

- **`c1`, `c2`, `c3`** — 「뒤에 형제 카드가 있는 카드」다. 마지막 `c4` 만 빠진다.

```text
   c1 → c2 → c3 → c4
   ✔    ✔    ✔    ✘   (c4 뒤에는 형제 카드가 없다)
```

**「마지막 카드」만 고르려면**

```css
.card:not(:has(+ .card)) { }
```

- 조건을 뒤집는다. `:has()` 를 `:not()` **바깥에** 두는 것은 정상이다(실측에서 `cssRules` 에 담겼다).

**앞쪽 형제를 조건으로 쓰는 문법**

- **없다.** `:has()` 의 상대 선택자는 `>`·`+`·`~` 셋뿐이고 전부 오른쪽·아래쪽을 본다.
- 앞쪽 형제를 조건으로 쓰고 싶으면 **관계를 뒤집어** 기준 요소를 바꾼다.\
  「앞에 이미지가 있는 카드」 대신 **「뒤에 카드가 있는 이미지」**(`img:has(+ .card)`)로 세운다.

**`~` 와 `+` 가 같은 결과인 이유**

- 이 문서에서는 네 카드가 **틈 없이 연속**이라, 「바로 뒤」와 「뒤 어딘가」의 답이 같아진다.
- **재현된 것은 「이 문서에서 같다」이지 「둘이 같다」가 아니다.** `<div class="card">` 사이에 다른 요소를 하나 끼우면 갈린다.

### 4. 이 규칙의 명시도는 얼마인가

**실행 결과** (동점·한 칸 낮음 두 판 통과)

```text
p:has(img, #im)       ->  (1, 0, 1)
p:has(img):has(span)  ->  (0, 0, 3)
p:where(:has(#im))    ->  (0, 0, 1)
```

**세 선택자의 `(A, B, C)`**

```text
  p:has(img, #im)
   ├ p                     (0, 0, 1)
   └ :has(img, #im)   껍데기 0
        ├ img   (0,0,1)
        └ #im   (1,0,0)  <- 가장 센 것 하나만 쓴다
                       =  (1, 0, 0)
                  합 =    (1, 0, 1)

  p:has(img):has(span)
   ├ p           (0, 0, 1)
   ├ :has(img)   (0, 0, 1)
   └ :has(span)  (0, 0, 1)
            합 = (0, 0, 3)

  p:where(:has(#im))
   ├ p                     (0, 0, 1)
   └ :where(...)   무조건 0 (0, 0, 0)
                  합 =     (0, 0, 1)
```

**껍데기 자체는 몇을 보태는가**

- **0.** `:has()` 라는 이름 자체는 어느 자리에도 안 보탠다.
- 값은 전부 **바깥의 선택자 + 인자 중 가장 센 것**에서 온다.

**인자를 둘 썼을 때**

- **하나만 쓰인다.** 목록 전체에서 **가장 센 것 하나**로 치환되고 나머지는 버려진다.
- `p:has(span, #im, .ic)` 도 실측에서 `(1, 0, 1)` 이었다 — 순서와 무관하다.

**`:has()` 를 둘 겹치면 왜 달라지는가**

- 「가장 센 것 하나」 규칙은 **한 `:has()` 안에서만** 적용된다.
- 서로 다른 `:has()` 는 **각각 하나의 단순 선택자**로 세어 더해진다 — 그래서 (0,0,3) 이 된다.

### 5. 문서에 없는 ID 가 세기를 올린다

**실행 결과**

```text
p:not(:has(#nope))        ->  (1, 0, 1)      <- #nope 는 문서에 없다
p:has(#im)                ->  (1, 0, 1)      <- #im 은 문서에 있다
.panel:has(#im)           ->  (1, 1, 0)
.panel:has(#legacy-root)  ->  잴 수 없음     <- 아래를 보라
```

**요소가 아예 없을 때의 명시도**

- **(1, 1, 0)** 이다 — `.panel` 이 B 1, `#legacy-root` 가 A 1.
- ★ 다만 **이 줄 자체는 계산값으로 재지 못했다.** 측정 방법이 두 규칙의 승부를 `getComputedStyle` 로 보는 것이라 **선택자가 매치돼야** 값이 나오는데, `#legacy-root` 가 없으면 매치가 없다.
- 그래서 둘로 쪼개 쟀다.
  - **모양** — `.panel:has(#im)` = **(1, 1, 0)**. 클래스 하나 + 인자의 ID 하나.
  - **없는 ID 도 세는가** — `p:not(:has(#nope))` = **(1, 0, 1)**. `#nope` 는 문서에 없고, `:not()` 이 뒤집어 줘서 이 줄은 매치되므로 잴 수 있었다.
- 두 실측을 합치면 「없는 ID 도 A 를 올린다」가 선다. **한 줄로 잰 것이 아니라는 사실을 그대로 남긴다.**

**매칭 결과를 보는가, 모양을 보는가**

- **선택자의 모양만 본다.**
- 명시도는 규칙을 **파싱할 때 한 번** 계산되고, 그때는 아직 문서를 보지도 않았다.

**세기를 올리지 않고 쓰려면**

```css
.panel:where(:has(#legacy-root)) { padding: 8px; }   /* (0, 1, 0) */
```

- 실측에서 `p:where(:has(#im))` 이 `(0, 0, 1)` 이었다 — 안의 ID 가 통째로 사라진다.

**`:is()`·`:not()` 과 같은 규칙인가**

- **같은 규칙이다.** 명세가 셋을 한 조항으로 묶어 「인자 중 가장 센 것으로 치환」이라 정한다.
- 갈리는 것은 명시도가 아니라 **인자 목록의 관용성**이다(6번을 보라).

### 6. 던지면 무엇이 사라지는가

**실행 결과** (`cssRules.length` / 같은 문자열을 `querySelectorAll` 에 준 결과)

```text
.card:has(:has(p))    ->  버림 | SyntaxError
.card:has(::before)   ->  버림 | SyntaxError
.card::before:has(p)  ->  버림 | SyntaxError
.card:has(p, :bogus)  ->  버림 | SyntaxError
```

**몇 줄이 담기는가**

- **0 줄.** 네 줄 전부 버려진다.

**콘솔에 무엇을 출력하는가**

- **아무것도 출력하지 않는다.** CSS 는 에러가 없는 언어라, 못 알아먹는 규칙은 **말없이 버린다.**
- 개발자 도구의 Styles 패널에도 나타나지 않는다 — **존재한 적이 없는 것처럼 보인다.**

**같은 문자열을 `querySelectorAll()` 에 넘기면**

- **`SyntaxError` 를 던진다.** 네 줄 전부 그랬다.
- 그래서 **선택자가 유효한지 확인하는 가장 싼 방법은 `querySelectorAll` 에 한 번 던져 보는 것**이다.

**네 번째 줄이 `:is(p, :bogus)` 와 다른 이유**

```text
  :is(p, :bogus)        관용적 목록  ->  :bogus 만 빼고 :is(p) 로 살아남는다
  :has(p, :bogus)       관용적 아님  ->  목록 전체가 무효 -> 규칙째 버림
```

- 명세가 `<forgiving-selector-list>` 를 **`:is()`·`:where()` 에만** 쓴다고 명시한다.
- 실측 대조: `.card:is(:bogus-xyz, p, .card)` 는 `selectorText` 가 `.card:is(p, .card)` 로 나오고 **1개를 잡았다.**

### 7. 규칙은 살아 있는데 아무 일도 안 일어난다

**실행 결과**

```text
.card:has(:is(:has(p)))
  cssRules.length    ->  1          (담겼다)
  selectorText       ->  ".card:has(:is())"
  querySelectorAll   ->  0개
  getComputedStyle   ->  rgb(0, 0, 0)   (색이 안 바뀌었다)
```

**담기는가**

- **담긴다.** `cssRules.length` 가 1 이다.

**`selectorText` 는**

- **`.card:has(:is())`** — 안이 **비어 있다.**

```text
   내가 쓴 것            .card:has( :is( :has(p) ) )
                                         ^^^^^^^^ :has() 안의 :has() = 무효
   :is() 는 관용적이라 무효한 인자를 조용히 뺀다
   남은 것                .card:has( :is(        ) )
   빈 :is() 는 아무것도 매치하지 않는다
```

**몇 개가 매치되는가**

- **0개.** 빈 `:is()` 는 어떤 요소에도 맞지 않는다.
- 같은 모양을 `.card:has(:where(:has(p)))` 에서도 확인했다 — `selectorText` 가 `.card:has(:where())` 다.

**「규칙이 담겼는지」만 보는 진단이 통과해 버리는 이유**

- 무효한 것은 **인자였고**, 그것을 삼킨 관용적 껍데기는 **자기는 유효**하기 때문이다.
- 규칙도 살고, 선택자도 파싱되고, 에러도 없다 — 그런데 **매치가 0 이다.**
- 그래서 진단의 2단계는 「담겼나」가 아니라 「**`selectorText` 가 내가 쓴 그대로인가**」여야 한다.

### 8. 왜 의사 요소를 금지하는가

**명세가 드는 이유**

- 의사 요소 중 다수가 **조상의 스타일에 따라 조건부로 존재**한다.
- 그런 것을 `:has()` 로 질의하게 하면 **순환(cycle)이 생긴다** — 스타일이 존재를 정하고, 존재가 다시 스타일을 정하게 된다.

```text
   .card:has(::before) { ... }   만약 허용한다면

   ::before 가 있나?  ->  .card 의 스타일을 봐야 안다
   .card 의 스타일은? ->  이 규칙이 맞는지 봐야 안다
   이 규칙이 맞나?    ->  ::before 가 있나?      <-- 되돌아왔다
```

**「조건부로 존재한다」가 무슨 뜻인가**

- `::before` 는 `content` 를 선언해야 생긴다. 선언을 안 하면 **상자가 아예 없다.**
- 곧 **의사 요소의 존재 여부가 CSS 선언의 결과**라는 뜻이다. 정본은 [13번 주제](../13-pseudo-elements-and-generated-content/2-summary.md).

**의사 요소 뒤에 붙이는 것은**

- **안 된다.** `.card::before:has(p)` 도 `::before:has(p)` 도 규칙째 버려졌다.
- 의사 요소는 복합 선택자의 **맨 끝**에만 올 수 있고, 그 뒤에 올 수 있는 것은 명세가 따로 정한 몇 가지뿐이다.

**조건에 따라 `::before` 를 바꾸려면**

```css
.card:has(img)::before { content: "🖼"; }
```

- `:has()` 를 **기준 요소 쪽에** 걸고, 의사 요소는 그 **뒤에** 둔다.
- 실측에서 `.card:has(p) span::before` 도 정상으로 담겼다 — `:has()` 뒤쪽 다른 요소에 의사 요소를 거는 것도 된다.

### 9. 안 먹을 때 무엇부터 보는가

**확인 순서 네 단계**

```text
  ① 규칙이 담겼나        cssRules.length > 0 ?
       0 이면  -> 선택자가 무효다. 여기서 끝
  ② 내가 쓴 그대로인가    selectorText 를 눈으로 읽는다
       다르면  -> 관용적 껍데기가 내용을 삼켰다
  ③ 무엇이 잡혔나        querySelectorAll(sel).length
       0 이면  -> 조건이 문서와 안 맞는다
  ④ 무엇이 이겼나        getComputedStyle(el).<속성>
       기대와 다르면 -> 명시도·캐스케이드 문제 (01·02번)
```

**각각 무엇으로 확인하는가**

| 물음 | 도구 |
|---|---|
| 규칙이 담겼나 | `document.styleSheets[i].cssRules` |
| 내가 쓴 그대로인가 | `cssRules[j].selectorText` |
| 무엇이 잡혔나 | `document.querySelectorAll(sel)` |
| 무엇이 이겼나 | `getComputedStyle(el)` |

**명시도 주장의 근거**

- **네 번째 — `getComputedStyle` 뿐이다.**
- 앞의 셋은 「매치되나」를 말할 뿐 **「이겼나」를 말하지 않는다.**
- 이 주제의 (A, B, C) 값이 전부 네 번째 층으로만 확인된 이유다.

**첫 단계를 건너뛰면**

- **「선택자가 무효라 없는 것」을 「명시도가 낮아 지는 것」으로 오진한다.**
- 그러면 선택자를 더 길게 늘이거나 `!important` 를 붙이게 되는데, **존재하지 않는 규칙은 아무리 세게 만들어도 존재하지 않는다.**

### 10. 성능은 어떤가

**측정했는가**

- **안 쟀다.** 이 주제의 3파일에 `:has()` 의 성능 수치는 하나도 없다.

**명세는 무엇을 요구하는가**

- **아무것도 요구하지 않는다.** Selectors Level 4 의 `:has()` 절에는 성능에 대한 요구도 경고도 없다.
- 문서 초록에 「Selectors 는 성능이 중요한 코드에서 쓸 수 있도록 설계됐다」는 일반 문장이 있을 뿐, `:has()` 에 붙은 말이 아니다.

**Baseline `widely` 가 말해 주는 것**

- **「주요 엔진 전부에서 30개월 이상 쓸 수 있다」뿐이다.** 빠르다는 뜻이 아니다.
- `:has()` 의 Baseline 은 newly 2023-12-19 → widely 2026-06-19 다.

**재려면 무엇을 재야 하는가**

- **정적 매치 시간이 아니라 DOM 이 바뀔 때의 스타일 재계산 시간**이다.
- `:has()` 는 조건이 되는 자손·형제가 바뀌면 **기준 요소 쪽을 다시 계산**해야 하므로, 한 번 매치하는 비용만 재면 의미가 없다.
- 조건에 걸리는 요소가 자주 바뀌는 화면(입력 폼·리스트 추가/삭제)에서 재야 신호가 잡힌다.

### 11. 다른 주제와 잇기

**`:has()` 가 푸는 「08번 주제의 한계」**

- 조합자(`공백` `>` `+` `~`)가 **전부 오른쪽·아래쪽으로만 간다**는 것이다.
- 「부모」·「앞쪽 형제」를 가리키는 조합자가 없어서, 그 방향의 조건은 JS 로 풀 수밖에 없었다.
- `:has()` 는 조합자를 늘리지 않고 **조건과 선택 대상을 분리**해서 같은 일을 하게 한다.

**관용적 목록의 차이**

| | 인자 목록 | 하나가 무효하면 |
|---|---|---|
| `:is()` · `:where()` | 관용적 | 그 항목만 버리고 나머지는 산다 |
| `:has()` | **관용적 아님** | **목록 전체가 무효 → 규칙째 버림** |
| `:not()` | 관용적 아님 | 〃 |

- 이 비대칭이 7번의 「조용한 증발」을 만든다 — 관용적인 것이 관용적이지 않은 것을 **삼킨다.**

**상태 의사 클래스를 넣을 수 있는가**

- **된다.** `.card:has(:hover)` 가 실측에서 정상으로 담겼다.
- 오히려 이것이 `:has()` 의 실무 쓸모 절반이다 — `form:has(:invalid)` · `label:has(input:checked)`.

**클래스를 달 수 있는 상황에서도 쓰는 것이 나은가**

- **아니다.** 클래스 하나로 표현할 수 있으면 그쪽이 더 읽기 쉽고 명시도도 평평하다.
- `:has()` 는 **마크업을 못 바꿀 때** 쓰는 도구다 — 서버가 내려 준 HTML, 남의 컴포넌트, 빌드 타임에 클래스를 못 다는 상황.

**구현 의존 항목** (버전이 오르면 다시 찍을 것)

- `selectorText` 의 **직렬화 형태**(`:has(:is())`) — 표준이 정한 것이 아니라 Chrome 151 이 보여 준 것이다.
- `CSS.supports('selector(...)')` 와 시트 파싱 결과가 **엇갈린 사례**(본문 「더 들어가면」) — 엔진 판정이다.
- `li:nth-child(1 of :has(img))` 가 담기는 것 — **매치 동작은 확인하지 않았다.**

**측정하지 않은 것**

- **성능.** 명세가 요구하는 것이 없고, 이 문서는 재지 않았다. 「`:has()` 는 느리다」는 서술을 넣지 않았다.
- **섀도 DOM 에서의 `:host:has()` 규칙.** 명세에 조항이 있으나 실행 확인하지 않았다.
- **Safari/WebKit.** 이 머신에 없다. Baseline 날짜로만 접지했다.
