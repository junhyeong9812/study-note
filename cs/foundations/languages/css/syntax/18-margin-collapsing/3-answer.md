# css/syntax/18 — 마진 상쇄 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 **모든 간격은 Google Chrome 151.0.7922.173 headless 에서 실제로 렌더해 잰 값**이다.\
> **간격 = 위 상자의 `rect.bottom` 과 아래 상자의 `rect.top` 의 차이.** 단위는 px 다.\
> ★ 측정은 전부 `<!doctype html>` + `html, body { margin: 0; padding: 0 }` 래퍼 안에서 했다 — **`body` 기본 마진 8px 과 쿼크 모드가 이 실험을 오염시키기 때문**이다(8번).\
> 규칙은 [CSS Box Model Level 3](https://drafts.csswg.org/css-box-3/) 과 [CSS Display Module Level 3](https://drafts.csswg.org/css-display-3/) 으로 접지했다.

## 정답

### 1. 두 상자 사이의 간격은 몇 px 인가

**실행 결과** (Chrome 151 headless — 상자 높이 각 30px)

```text
mb 20 + mt 20    A.bottom = 30    B.top = 50     간격 20
mb 40 + mt 20    A.bottom = 30    B.top = 70     간격 40
mb 20 + mt  0    A.bottom = 170   B.top = 190    간격 20
패딩으로 바꿈    A.bottom = 310   B.top = 310    간격  0  (상자 자체가 50px 로 두꺼워짐)
```

**`.a` 와 `.b` 사이의 간격**

- **20px.** `20 + 20 = 40` 이 아니다.

**`margin-bottom` 을 40 으로 바꾸면**

- **40px.** 규칙은 **`max(아래 마진, 위 마진)`** 이므로 큰 쪽이 이긴다.

**`margin-top` 을 0 으로 바꾸면**

- **여전히 20px.** `max(20, 0) = 20`. 한쪽만 줘도 결과가 같다는 뜻이다.
- 그래서 **「한쪽 마진만 주는」 규약**이 널리 쓰인다 — 값이 예측 가능해진다.

**패딩으로 바꾸면**

- **간격 0** 이고 대신 **두 상자 자체가 30 → 50px 로 두꺼워진다.**
- **패딩은 「두께」라서 겹칠 수 없기 때문**이다. 마진은 「거리 요구」라서 겹칠 수 있다.

> **마진 상쇄(margin collapsing)** — 맞닿은 두 세로 마진이 하나로 합쳐져 큰 쪽만 남는 것.\
> 예: 20 과 40 이 맞닿으면 60 이 아니라 **40** 이다.

### 2. 자식의 마진은 어디로 가는가

**실행 결과** (Chrome 151 headless — 기준선(빨간 막대) 바로 아래에 부모를 놓았다)

```text
기준선  rect.bottom =  6
.p      rect.top    = 46    rect.height = 30
.c      rect.top    = 46                        ← 부모와 같은 자리
```

**기준선과 `.p` 사이의 간격**

- **40px.** 자식에게 준 마진이 **부모 위쪽**에 나타났다.

**`.p` 의 `rect.height`**

- **30.** 자식의 높이뿐이다. **마진 40 은 부모 안에 들어 있지 않다.**

**`.c.top` 과 `.p.top`**

- **같다. 둘 다 46.** 부모 상자와 자식 상자가 **완전히 포개져 있다.**

**노란 배경은 마진 자리에 보이는가**

- **안 보인다.** 부모 상자가 그 자리에 없기 때문이다. 마진 자리는 **부모의 조상 배경**(여기서는 흰색)이 보인다.
- 그래서 「카드에 배경을 줬는데 제목 위 여백이 카드 밖에 있다」는 증상이 된다.

```text
   자식의 위 마진 40  +  부모의 위 마진 0
        ↓ 맞닿아 하나로 합쳐진다
   max(40, 0) = 40  ->  이제 이것은 「부모의 마진」이다
        ↓
   부모 자신이 40px 아래로 밀린다
```

- **「샌다」는 비유이고, 정확히는 「부모의 마진이 되었다」** 이다.
- 아래쪽도 같다 — 마지막 자식의 아래 마진이 부모의 아래 마진과 합쳐진다.\
  *(실측: `margin-bottom: 40px` 인 자식만 가진 부모의 높이가 **20**(자식 높이뿐)이고 부모 아래 기준선까지 **40px** 이 비었다.)*

### 3. 빈 상자가 만드는 간격

**실행 결과** (Chrome 151 headless)

```text
빈 상자 그대로       위.bottom = 30    아래.top = 60     간격 30   빈 상자 rect.height = 0
+ height: 1px        위.bottom = 140   빈.top = 170      간격 30
                     빈.bottom = 171   아래.top = 201    간격 30   총 61
+ border-top: 1px    같은 형태로 총 61
+ margin: 50px 0     위.bottom = 591   아래.top = 641    간격 50
```

**「위」와 「아래」 사이의 간격**

- **30px.** 60 도 90 도 아니다.

**`.empty` 의 `rect.height`**

- **0.** 높이·패딩·테두리·내용이 하나도 없으므로 상자가 두께를 갖지 않는다.

**`height: 1px` 을 주면**

- **총 61px.** 위쪽 30 + 선 1 + 아래쪽 30 이다.
- 1px 이 **위 마진과 아래 마진 사이를 가로막아** 자기 상쇄가 깨졌기 때문이다.
- `border-top: 1px` 로도 **똑같이 61** 이었다.

**마진을 `50px 0` 으로 키우면**

- **50px.** 자기 위아래 마진끼리도 **큰 쪽 하나**가 남고, 그 하나가 다시 형제들과 합쳐진다.

```text
   빈 상자 (두께 0)                      빈 상자 (두께 1)
   [ 위 ]                                [ 위 ]
      ↕ 30  ← 위·빈상자위·빈상자아래·아래   ↕ 30
   [ 아래 ]      넷이 한 덩어리로 겹침     [ 선 1 ]
                                            ↕ 30
   총 30                                 [ 아래 ]   총 61
```

### 4. 무엇이 상쇄를 막는가

**실행 결과** (Chrome 151 headless — 2번과 같은 배치. 기준선과 부모의 간격 / 부모 높이)

```text
아무것도 안 줌          간격 40    높이 30    ✗
padding-top: 1px        간격  0    높이 71    ✓
border-top: 1px solid   간격  0    높이 71    ✓
display: flow-root      간격  0    높이 70    ✓
overflow: hidden        간격  0    높이 70    ✓
height: 60px            간격 40    높이 60    ✗ (위쪽은 못 막는다)
min-height: 60px        간격 40    높이 60    ✗
```

**막지 못하는 것**

- **`height` 고정**(과 `min-height`)이다. 실측에서 `height: 60px` 인 부모도 자식의 40px 마진이 **그대로 밖으로 나갔다.**

**그것이 막는 쪽**

- **아래쪽**이다. 자식의 아래 마진과 부모의 아래 경계 사이를 **높이가 가로막기** 때문이다.
- *(실측: `margin-bottom: 40px` 인 자식 + `height: 20px` 인 부모 → 부모 아래 간격 **0**. 같은 부모에 높이를 안 주면 **40**.)*
- **위쪽은 못 막는다** — 부모의 위 경계와 자식의 위 마진 사이에는 높이가 끼어들 자리가 없기 때문이다.

**`padding`/`border` 의 대가**

- **그 1px 이 실제 치수에 더해진다.** 실측에서 부모 높이가 70 이 아니라 **71** 이었다.
- `border` 는 **선이 보인다**(투명하게 하려면 `transparent` 로 해야 하고, 그러면 `box-sizing` 에 따라 치수 계산이 또 흔들린다 — [15번](../15-box-model-and-box-sizing/2-summary.md)).

**대가가 없는 것**

- **`display: flow-root`** 다. 높이가 정확히 **70**(마진 40 + 자식 30)이고, 자르지도 않고 스크롤바도 안 생긴다.
- `overflow: hidden` 도 높이는 70 이지만 **넘치는 것이 잘린다.** 그 대조 실측은 [17번](../17-block-formatting-context/2-summary.md)에 있다.

### 5. 음수 마진이 섞이면

**실행 결과** (Chrome 151 headless — 상자 높이 각 40px 또는 30px)

```text
mb  20 + mt -40   ->  P.bottom = 40    Q.top = 20    간격 -20
mb  20 + mt -10   ->                                 간격  10
mb  20 + mt -25   ->                                 간격  -5
mb -30 + mt -10   ->  R.bottom = 140   S.top = 110   간격 -30
```

**`.p` 와 `.q` 사이의 간격**

- **-20px.** 즉 `.q` 가 `.p` 를 20px 덮는다. `20 + (-40) = -20`.

**`.q` 를 `-10px` 으로 바꾸면**

- **10px.** `20 + (-10) = 10`. **겹치지 않고 벌어진다.**

**`.p` 를 `-30`, `.q` 를 `-10` 으로 하면**

- **-30px.** **합 -40 이 아니다.**
- 양수가 하나도 없으므로 「가장 큰 양수」가 0 이고, 거기에 **가장 작은 음수 -30** 이 더해진 것이다.

**한 문장 규칙**

- **「가장 큰 양수 마진 + 가장 작은 음수 마진」.**
- 양수만 있으면 자동으로 `max` 가 되고, 음수만 있으면 가장 작은 음수 하나가 남는다 — **하나의 규칙이 세 경우를 다 덮는다.**

```text
   양수만        max(20, 20) + 0        =  20
   섞임          max(20)     + (-25)    =  -5
   음수만        0           + (-30)    = -30
```

### 6. 화면만 보고 판정할 수 있는가

**실행 결과** (Chrome 151 headless — 스크린샷과 rect 를 같이 받았다)

```text
mb 20 + mt -25 인 한 쌍    X.bottom = 30    Y.top = 25     간격  -5   묶음 전체 높이 55
margin 0 인 한 쌍          X.bottom = 101   Y.top = 101    간격   0   묶음 전체 높이 60
스크린샷: 두 쌍이 똑같이 「파란 상자 바로 아래 분홍 상자」로 보인다
```

**화면에서 어떻게 보이는가**

- **두 상자가 그냥 맞닿아 보인다.** 5px 이 겹쳤다는 단서가 화면에 없다.

**`margin: 0` 인 두 상자와 구분할 수 있는가**

- ★ **없다.** 스크린샷에서 두 쌍이 같은 모습이었다. 유일한 차이인 **묶음 전체 높이 55 대 60** 은 옆에 자를 대야 보인다.

**올바른 판정 방법**

- **`rect.bottom` 과 다음 상자의 `rect.top` 을 빼서 숫자로 본다.**
- 「붙어 보인다」는 **상쇄의 증거가 아니다** — 상쇄됐을 수도, 마진이 애초에 0 일 수도, 음수로 겹쳤을 수도 있다.
- ★ 이 주제에서 **스크린샷은 보조이고 `getBoundingClientRect()` 가 주력**인 이유다.

### 7. 상쇄가 아예 없는 자리

**실행 결과** (Chrome 151 headless — 같은 마크업, 부모의 `display` 만 바꿨다)

```text
display: flow-root (보통 흐름)   첫.bottom = 30    둘째.top = 50     간격 20
display: flex; column            첫.bottom = 126   둘째.top = 166    간격 40
display: grid                    첫.bottom = 270   둘째.top = 310    간격 40

flex 항목 안에 margin-top: 40px 인 손자를 넣은 경우
  그 항목의 rect.height = 70   손자 top = 항목 top + 40   (마진이 안에 갇혔다)
```

**두 항목 사이의 간격**

- **40px.** `20 + 20` 이 그대로 더해졌다.

**`display: grid` 로 바꾸면**

- **똑같이 40px.**

**이유 — 서식 문맥으로**

- **마진 상쇄는 블록 서식 문맥(BFC)의 규칙**이다. flex 서식 문맥과 grid 서식 문맥에는 **그런 규칙이 아예 없다.**
- 「막혔다」가 아니라 **「애초에 그 규칙이 도는 구역이 아니다」** 가 정확하다.

**flex 항목 안쪽의 부모-자식 상쇄**

- **일어나지 않는다.** flex 항목은 각각 **BFC 를 연다**([17번](../17-block-formatting-context/2-summary.md)).
- 실측에서 항목의 높이가 **70**(마진 40 + 손자 30)으로 마진을 품었다.
- flex 의 배치 규칙 자체는 [24번](../24-flexbox-axes/2-summary.md)이 정본이다.

### 8. 측정 환경이 결과를 바꾼다

**실행 결과** (Chrome 151 headless)

```text
같은 문서를 래퍼 유무로 두 번 띄워 한 판에 다 읽었다.

래퍼 없음   compatMode = BackCompat   body margin-top = 8px
            margin-top: 40px 인 첫 자식의 rect.top = 40
            body 의 rect.height = 445
            width:300 padding:20 border:5 인 상자의 rect.width = 350

래퍼 있음   compatMode = CSS1Compat   body margin-top = 0px
            같은 요소의 rect.top = 40         ← 같다
            body 의 rect.height = 110
            같은 상자의 rect.width = 350      ← 같다
```

**`rect.top` 은 몇인가 — 8px 이 더해지는가**

- **40 이다. 더해지지 않는다.**
- `body` 의 위 마진 8 과 첫 자식의 위 마진 40 이 **서로 상쇄**되어 큰 쪽 40 만 남았기 때문이다. **8 + 40 = 48 이 아니다.**
- ★ 그래서 **`body` 마진은 「좌표를 8 만큼 민다」가 아니라 「측정 대상과 상쇄된다」** 는 형태로 오염시킨다. 더 고약하다.

**`<!doctype html>` 을 빼면**

- **쿼크 모드가 된다.** `document.compatMode` 가 `BackCompat` 이었다.
- 같은 내용의 `body` 높이가 **445 대 110** 으로 갈렸다 — 쿼크 모드에서 `body` 가 뷰포트를 채운다.
- ★ **다만 전설의 「쿼크 모드 = IE 박스 모델」은 재현되지 않았다.** `width: 300px; padding: 20px; border: 5px` 인 상자의 `rect.width` 가 **양쪽 다 350** 이었다. 예상과 달랐던 대목이라 그대로 적는다.

**통제해야 하는 것 둘**

- ① **`<!doctype html>` 을 붙인다**(쿼크 모드 차단).
- ② **`html, body { margin: 0; padding: 0 }`** 을 깐다(`body` 기본 마진 8px 이 실험 대상과 상쇄되는 것을 차단).
- 문서의 `demo` 블록에는 `<!doctype>` 도 `<body>` 도 없으므로, **검증용 사본에는 반드시 래퍼를 붙여야** 문서의 수치와 어긋나지 않는다([`render-rules.md`](../../../../../../reference/render-rules.md)).

### 9. 다른 주제와 잇기

**BFC 의 생성 조건 전체와 다른 효과 둘**

- [17번 주제](../17-block-formatting-context/2-summary.md)(서식 문맥)다.
- 다른 효과 둘은 **② 안의 `float` 를 감싸 높이가 살아난다** · **③ 바깥 `float` 옆으로 파고들지 않는다**.
- ★ **이 문서의 경계선**: 여기는 **BFC 가 마진 상쇄를 막는 쓰임**까지이고, **어떤 선언이 BFC 를 여는가와 나머지 두 효과는 17번**이다.

**`flow` 에서 새고 `flow-root` 에서 안 새는 이유**

- `display: block` 은 **`block flow`** 이고, `flow` 는 **바깥 흐름과 이어진** 흐름이다 — 그래서 부모와 자식의 마진이 **맞닿는다.**
- `flow-root` 는 **자기 안에서 흐름을 새로 시작**하므로 부모의 위 경계와 자식의 위 마진이 **만나지 못한다.**
- `display` 의 두 값 구조는 [16번](../16-display-inner-outer/2-summary.md)이 정본이다.

**마진 자리에 부모 배경이 보이는 이유**

- **마진 칸에는 배경이 칠해지지 않기 때문**이다. 배경은 **`border` 상자까지만** 칠해진다.
- 그래서 마진 자리에는 **그 뒤에 있는 것**(부모나 조상의 배경)이 비친다. 정본은 [15번 주제](../15-box-model-and-box-sizing/2-summary.md)(박스 모델).

**상쇄를 피하고 간격을 주는 수단 둘**

- ① **`gap`** — flex/grid 에서 항목 **사이에만** 넣는 간격. 상쇄도 없고 양 끝에 여백도 안 생긴다(목록의 **26번 주제**).
- ② **부모의 `padding`** — 패딩은 두께라 절대 상쇄되지 않는다(1번 실측).
- (셋째 길) 한쪽 마진만 주는 규약. 상쇄는 여전히 일어나지만 **값이 그 하나로 정해져 예측 가능**해진다.

## 용어 풀이

- **마진 상쇄** — 맞닿은 두 세로 마진이 합쳐져 큰 쪽만 남는 것.
- **맞닿는다(adjoining)** — 두 마진 사이에 테두리·패딩·내용·높이·BFC 경계가 하나도 없는 상태.
- **인접 형제 상쇄** — 위 상자의 아래 마진과 아래 상자의 위 마진이 합쳐지는 것.
- **부모-자식 상쇄** — 자식의 마진이 **부모의 마진이 되어** 부모 자신이 밀리는 것.
- **자기 상쇄(self-collapsing)** — 두께가 0 인 빈 상자의 위아래 마진이 자기 안에서 합쳐지는 것.
- **음수 마진 규칙** — 가장 큰 양수 + 가장 작은 음수. 양수만·음수만인 경우도 이 하나로 덮인다.
- **BFC** — 상쇄가 도는 구역이자 상쇄를 막는 경계. 정본은 [17번](../17-block-formatting-context/2-summary.md).
- **`display: flow-root`** — 치수를 안 바꾸고 BFC 만 여는 값. 상쇄를 막는 **대가 없는** 수단.
- **`gap`** — flex/grid 에서 항목 사이에만 넣는 간격. 상쇄가 개입하지 않는다.
- **쿼크 모드** — `<!doctype html>` 이 없을 때의 호환 모드. `document.compatMode` 가 `BackCompat` 이다.
- **간격(이 문서의 정의)** — 위 상자의 `rect.bottom` 과 아래 상자의 `rect.top` 의 차이. 음수면 겹친 것이다.
