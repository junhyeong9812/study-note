# css/syntax/25 — `flex` 단축의 세 값(`grow`/`shrink`/`basis`)과 크기 해결 — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [CSS Flexible Box Layout Level 1](https://drafts.csswg.org/css-flexbox-1/) (§7 `flex` 단축·§9.7 유연 길이 해결 알고리즘·§4.5 자동 최소 크기) · [CSS Box Sizing Level 3](https://drafts.csswg.org/css-sizing-3/) (`min-width: auto` 가 무엇으로 풀리나). 열어서 확인한 것만 적었다.
> **실행 검증** — 이 문서의 모든 픽셀 값은 **Google Chrome 151.0.7922.173** headless 에 실제로 띄워 `getBoundingClientRect()` 로 잰 값이다. 계산값은 `getComputedStyle` 로 따로 읽었고 **둘을 섞지 않았다**(왜 섞으면 안 되는지는 (9)).\
> **WebKit(Safari)은 이 머신에 없고 Firefox 는 이 환경에서 headless 스크린샷이 산출되지 않는다** — 엔진 차이는 주장하지 않는다.
> **버전** — Flexbox 는 Baseline **widely**(newly 2015-09-30 → widely 2018-03-30). 이 문서가 쓰는 표면은 전부 그 안에 있다(목록 README 의 지원 표).
> **여기서 다루지 않는 것** — 축·정렬(`justify-*`/`align-*`)의 정본은 [24번](../24-flexbox-axes/)이다. 줄바꿈·`gap`·`order` 는 [26번](../26-flex-wrap-gap-order/), 내재적 크기 키워드는 [31번](../31-intrinsic-sizing-and-aspect-ratio/), Grid 의 `fr`·`minmax()` 는 [목록의 **27번 주제**](../27-grid-track-sizing/)다.
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 수치는 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

**flex 컨테이너 = 예산이 정해진 회의. `flex` 세 값은 「기본 배정액 · 남으면 얼마씩 더 · 모자라면 얼마씩 깎아」다.**

비유 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 총예산 | flex 컨테이너의 주축 크기 (`row` 면 폭) |
| 부서별 기본 배정액 | `flex-basis` — 나누기 전에 각 항목이 먼저 받는 크기 |
| 예산이 남았다 | **양의 자유 공간** — `flex-grow` 가 나눈다 |
| 예산이 모자란다 | **음의 자유 공간**(넘침) — `flex-shrink` 가 깎는다 |
| 더 받을 지분 | `flex-grow` 값 |
| 깎일 지분 | `flex-shrink` 값 |
| 「여기까지는 못 깎는다」는 마지노선 | `min-width: auto` — flex 항목의 기본값이고 **`min-content` 로 풀린다** |

- **`flex` 한 줄에는 세 가지 결정이 들어 있다.** 「얼마에서 시작하나(basis)」·「남으면 얼마 받나(grow)」·「모자라면 얼마 깎이나(shrink)」.
- 자유 공간의 **부호가 어느 쪽 값을 쓸지 정한다.** 양수면 `grow` 만, 음수면 `shrink` 만 일한다. 둘이 동시에 일하는 일은 없다.
- 그래서 「`flex: 1`을 줬는데 안 늘어난다」와 「안 줄어든다」는 **완전히 다른 고장**이다. 전자는 자유 공간이 0 인 것이고, 후자는 대개 마지노선(`min-width: auto`)에 걸린 것이다.

```text
총예산 = 컨테이너 주축 크기
+-------------------------------------------------------------+
|  basis 합                          |     자유 공간           |
|  (각 항목이 먼저 받는 크기)          |  (남은 것 — grow 가 나눔) |
+-------------------------------------------------------------+

basis 합이 총예산보다 크면 자유 공간이 음수가 된다
+-------------------------------------------------------------+
|  basis 합                                                    |   넘침
+-------------------------------------------------------------+------+
                                                  shrink 가 깎아 넣는다
```

실무에서 이게 터지는 자리는 **사이드바 + 본문** 2단 레이아웃이다.\
본문에 `flex: 1`을 줬는데 긴 URL 이나 `<pre>` 블록 하나 때문에 **본문이 컨테이너를 뚫고 나가** 가로 스크롤이 생긴다.\
원인은 `flex-shrink` 가 아니라 **마지노선**이다 — (6)이 그 정본이다.

> **flex 항목(flex item)** — flex 컨테이너의 직계 자식 상자. `flex` 단축은 **항목에 주는 것**이고 컨테이너에 주면 아무 일도 하지 않는다.\
> 예: `.container { flex: 1 }` 은 그 컨테이너가 또 다른 flex 의 항목일 때만 의미가 있다.

> **자유 공간(free space)** — 컨테이너의 주축 크기에서 항목들의 **basis 합**(과 `gap`·마진)을 뺀 나머지.\
> 예: 600px 컨테이너에 basis 100·200·300 인 항목 셋이면 자유 공간은 0 이고, 900px 컨테이너면 300px 다.

> **주축(main axis)** — 항목이 줄지어 놓이는 방향. `flex-direction` 이 정한다. 정본은 [24번](../24-flexbox-axes/).\
> 예: `row` 면 주축이 가로라 `flex-basis` 는 **폭**을 뜻하고, `column` 이면 **높이**를 뜻한다.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 세 질문을 둔다.

1. `flex: 1`과 `flex: auto` 는 **무엇이 달라서** 결과가 달라지는가 — 그리고 기본값은 왜 `0 1 auto` 인가.
2. 남는 공간과 모자라는 공간은 **각각 무슨 비율로** 나뉘는가 — `grow` 와 `shrink` 의 계산법이 왜 다른가.
3. 항목이 **더 이상 안 줄어드는 바닥**은 무엇이 정하는가.

## 동작 방식

### (1) 세 값의 자리 — 무엇이 어디에 들어가나

**언제 쓰나** — `flex` 단축을 읽거나 쓸 때마다. 순서를 잘못 외우면 나머지가 전부 어긋난다.

```text
flex:  <flex-grow>   <flex-shrink>   <flex-basis>
         │              │                │
         │              │                └─ 나누기 전에 먼저 받는 크기 (길이·%·auto·content)
         │              └─ 모자랄 때 깎일 지분 (0 이면 안 깎인다)
         └─ 남을 때 더 받을 지분 (0 이면 안 늘어난다)

초기값(아무것도 안 썼을 때)  =  flex: 0 1 auto
                                 │ │ └ 내용 크기(또는 width)에서 시작
                                 │ └── 모자라면 깎인다
                                 └──── 남아도 안 늘어난다
```

그림 해설 (한 단계씩):

- 순서는 **grow → shrink → basis** 다. 「늘어나기 → 줄어들기 → 출발점」.
- 초기값이 `0 1 auto` 라는 것은 **「제 크기로 있다가, 모자랄 때만 양보한다」** 는 뜻이다.
- 그래서 아무 선언 없이 `display: flex` 만 주면 항목들이 **내용 크기로 왼쪽에 모여 있다.**

비용 — 없다. 단축은 파싱 시점에 세 롱핸드로 풀린다.

### (2) 크기 해결 순서 — 한 번에 하나씩

**언제 쓰나** — 「왜 이 폭이 나왔나」를 손으로 따라갈 때. **순서를 건너뛰면 답이 안 맞는다.**

```text
① 각 항목의 flex-basis 를 정한다          길이면 그대로, auto 면 width(없으면 내용 크기)
        ↓
② basis 합을 낸다                         (+ gap + 마진)
        ↓
③ 자유 공간 = 컨테이너 주축 크기 − ②
        ↓
④ 부호로 갈린다
     자유 공간 > 0  ──> flex-grow 로 나눠 더한다   (shrink 는 쉰다)
     자유 공간 < 0  ──> flex-shrink 로 깎는다      (grow 는 쉰다)
     자유 공간 = 0  ──> 아무 일도 안 일어난다
        ↓
⑤ min-*/max-* 로 자른다                    여기서 min-width: auto 가 바닥을 만든다 (6)
        ↓
⑥ 잘린 만큼을 나머지 항목에 다시 나눈다       (반복)
        ↓
⑦ 정해진 크기 위에서 justify-*/align-* 가 배치한다   ← 여기부터가 24번
```

그림 해설 (한 단계씩):

- ③이 이 주제의 중심이다 — **화면에는 자유 공간이 안 보인다.** 그래서 도식이 본체다.
- ④의 배타성이 핵심이다. `flex-shrink: 0`을 줘도 **자유 공간이 양수면 아무 영향이 없다.**
- ⑤는 ④ 뒤에 온다. 그래서 `flex-grow` 를 아무리 크게 줘도 `max-width` 를 못 넘고, `flex-shrink` 를 아무리 크게 줘도 **바닥 아래로는 못 간다.**

비용 — 항목 수에 비례한다. ⑥의 재분배 때문에 최악의 경우 항목 수만큼 반복한다.

### (3) `flex: 1`과 `flex: auto` — 같은 데이터로 대조

**언제 쓰나** — 「칸을 똑같이 나눌까, 내용만큼 주고 남은 것만 나눌까」를 정할 때. **이 주제에서 가장 자주 헷갈리는 자리다.**

내용이 다른 항목 셋(`A` · `BBBB` · `CCCCCCCCCCCC`)을 **600px 컨테이너**에 넣고 네 가지를 각각 걸어 실제로 쟀다.

```text
먼저 각 항목의 내용 크기(= max-content)를 쟀다
  "A"             =   8.02px
  "BBBB"          =  32.02px
  "CCCCCCCCCCCC"  =  96.02px        합 136.06px
```

```text
flex: 1  ( = 1 1 0% )                     flex: auto  ( = 1 1 auto )
basis 가 전부 0 이다                        basis 가 내용 크기다
+---------------------------------+       +---------------------------------+
| basis 합 = 0                    |       | basis 합 = 136.06               |
| 자유 공간 = 600 − 0 = 600        |       | 자유 공간 = 600 − 136.06 = 463.94|
| grow 1:1:1 -> 200 씩            |       | grow 1:1:1 -> 154.65 씩          |
+---------------------------------+       +---------------------------------+
  A=200.00  B=200.00  C=200.00              A= 8.02+154.65 = 162.66
                                            B=32.02+154.65 = 186.67
  -> 내용과 무관하게 똑같이 나뉜다             C=96.02+154.65 = 250.67
                                            -> 내용 차이가 그대로 남는다
```

```html demo
<div class="pair">
  <div class="f one"><i>A</i><i>BBBB</i><i>CCCCCCCCCCCC</i></div>
  <div class="f two"><i>A</i><i>BBBB</i><i>CCCCCCCCCCCC</i></div>
</div>
<style>
  .pair { font: 16px monospace; }
  .f { display: flex; width: 300px; margin-bottom: 6px; background: #eee; }
  .f i { display: block; font-style: normal; background: #bfdbfe; outline: 1px solid #333; }
  .one i { flex: 1; }      /* = 1 1 0%  : 전체를 똑같이 나눈다 */
  .two i { flex: auto; }   /* = 1 1 auto: 내용 크기를 주고 남은 것만 나눈다 */
</style>
```

> **보이는 것** — 위 줄(`flex: 1`)은 칸 셋이 **폭이 똑같고**, 아래 줄(`flex: auto`)은 **`CCCCCCCCCCCC` 칸이 눈에 띄게 넓다**. 두 줄 다 오른쪽 끝까지 꽉 차고, 글자 내용은 같다.\
> **바꿔 볼 것** — `.two` 의 `auto` → `none`(= `0 0 auto`) → 칸이 내용 크기로만 줄고 오른쪽에 빈 공간이 남는다 · `.one` 의 `1` → `2 1 0`(지분이 같으면 결과도 같다 — **비율만 본다**)

*(Chrome 151 headless 실측 — 폭 300px 판: `flex: 1` 은 100.00 / 100.00 / 100.00, `flex: auto` 는 62.66 / 86.67 / 150.67 로 합이 각각 300.00. 위 도식의 600px 판은 `flex: 1` 이 200.00 씩, `flex: auto` 가 162.66 / 186.67 / 250.67 이었다.)*

그림 해설 (한 단계씩):

- 갈리는 원인은 **오직 `basis` 하나**다. `grow`·`shrink` 는 둘 다 `1 1` 로 같다.
- `flex: 1`은 **기본 배정액을 0 으로 만들고** 총예산 전부를 지분대로 나눈다 → 내용과 무관하게 균등.
- `flex: auto` 는 **내용 크기를 먼저 주고** 남은 것만 나눈다 → 내용 차이가 그대로 남는다.
- **「칸을 똑같이」가 목적이면 `flex: 1`이고, 「내용을 존중하되 빈 곳을 채워」가 목적이면 `flex: auto` 다.**

비용 — `flex: auto` 는 항목마다 **내용 크기를 먼저 재야** 하므로 `flex: 1`보다 측정 비용이 크다. 내용이 많은 목록에서 차이가 난다.

### (4) `flex-grow` — 자유 공간을 지분대로 나눈다. basis 로 가중하지 않는다

**언제 쓰나** — 「2:1 로 나누고 싶다」처럼 비율을 지정할 때.

```text
컨테이너 900px, basis 100 / 200 / 300 (합 600), 자유 공간 = 300

grow 가 전부 1 일 때                      grow 가 1 / 2 / 3 일 때
지분 합 = 3                               지분 합 = 6
300 × 1/3 = 100 씩 더한다                  300 × 1/6, 2/6, 3/6 = 50, 100, 150
+---------+---------+---------+           +------+---------+------------+
| 100+100 | 200+100 | 300+100 |           |100+50| 200+100 |  300+150   |
|  = 200  |  = 300  |  = 400  |           | =150 |  = 300  |   = 450    |
+---------+---------+---------+           +------+---------+------------+
```

*(Chrome 151 headless 실측 — 컨테이너 900px: `grow` 전부 1 일 때 200.00 / 300.00 / 400.00, `grow` 1/2/3 일 때 150.00 / 300.00 / 450.00. basis 를 전부 0 으로 두고 `grow` 1/2/3 을 준 판도 150.00 / 300.00 / 450.00 로 **같았다**.)*

- **`grow` 는 `basis` 로 가중하지 않는다.** 지분(`grow` 값)만으로 나눈다.\
  같은 실측에서 `basis: 0` 판과 `basis: 100/200/300` 판의 결과가 **우연히 같아진 것**이 아니라, 앞엣것은 900 을 1:2:3 으로, 뒤엣것은 300 을 1:2:3 으로 나눠 더한 것이 마침 같은 수가 된 것이다.
- 이것이 다음 항의 `shrink` 와 **정확히 반대**다. 두 계산법이 다르다는 것이 이 주제의 두 번째 함정이다.

### (5) `flex-grow` 합이 1 보다 작으면 — 자유 공간이 남는다

**언제 쓰나** — `flex-grow: 0.5` 같은 소수를 쓸 때.

```text
컨테이너 900px, basis 전부 0, grow = 0.2 / 0.3 / 0

지분 합 = 0.5  (1 보다 작다)
-> 자유 공간의 **합만큼만** 나눠 준다. 나머지는 아무도 안 가져간다.

+--------+-----------+--------------------------------------+
| 900×0.2| 900×0.3   |                                      |
| = 180  |   = 270   |   450px 이 빈 채로 남는다              |
+--------+-----------+--------------------------------------+
```

*(Chrome 151 headless 실측: 180.00 / 270.00 / 0.00, 합 450.00 — 컨테이너 900px 중 450px 가 비었다.)*

- 지분 합이 1 이상이면 **자유 공간이 전부 소진**되고, 1 미만이면 **비율만큼만** 쓰인다.
- 그래서 `flex-grow: 0.5` 하나짜리 항목은 **자유 공간의 절반만** 먹는다. 「반만 늘어나게」가 필요할 때 쓰는 표면이다.

### (6) ★ 최대 함정 — `min-width: auto` 가 만드는 바닥

**언제 쓰나** — 「`flex: 1`인데 컨테이너를 뚫고 나간다」·「가로 스크롤이 생긴다」를 만났을 때. **이 주제에서 값어치가 가장 큰 자리다.**

```text
일반 블록 상자의 min-width 기본값       flex 항목의 min-width 기본값
        0                                     auto
        │                                       │
        └ 0 까지 줄어든다                        └ min-content 로 풀린다
                                                   = 「더는 쪼갤 수 없는 조각」의 크기
```

> **`min-content`** — 그 상자가 **내용을 부러뜨리지 않고** 가질 수 있는 가장 작은 크기.\
> 예: 글이면 가장 긴 낱말의 폭, `white-space: pre` 인 `<pre>` 면 **줄바꿈이 없으니 한 줄 전체의 폭**이다. 정본은 [31번](../31-intrinsic-sizing-and-aspect-ratio/).

300px 컨테이너 · 고정 사이드바 100px · 본문 `flex: 1` · 본문 안에 `<pre>` 한 줄. 실제로 쟀다.

```text
고치기 전 (min-width 기본값 auto)          고친 뒤 (min-width: 0)
컨테이너 300                                컨테이너 300
+--------+-----------------------+---+     +--------+--------------------+
| side   | main (280.02)         |   |     | side   | main (200.00)      |
| 100    |                       |   |     | 100    |                    |
+--------+-----------------------+---+     +--------+--------------------+
0       100                   380.02       0       100                 300
                                  ↑                                     ↑
         오른쪽 끝이 380.02 — 80.02px 뚫고 나갔다       정확히 300 에서 끝난다
```

*(Chrome 151 headless 실측 — 같은 문서에서 `.main` 에 `min-width: 0` 만 추가한 판을 나란히 띄웠다. 고치기 전 `main` 폭 280.02px · 오른쪽 끝 x=380.02 · `getComputedStyle(main).minWidth` 는 `auto`. 고친 뒤 `main` 폭 200.00px · 오른쪽 끝 x=300.00 · 계산값 `0px`. 두 판 모두 `pre.scrollWidth` 는 280 으로 같다 — **내용은 그대로이고 상자만 줄었다.** 그 `<pre>` 의 `min-content` 폭과 `max-content` 폭은 둘 다 280.02px 로 **같았다**(줄바꿈이 없으니 쪼갤 수 없다).)*

```html demo
<div class="c"><div class="side">side</div>
  <div class="main"><pre>GET /api/v1/users/12345/preferences</pre></div></div>
<div class="c fix"><div class="side">side</div>
  <div class="main"><pre>GET /api/v1/users/12345/preferences</pre></div></div>
<style>
  .c { display: flex; width: 300px; background: #eee; margin-bottom: 8px;
       font: 16px monospace; outline: 2px solid #c00; }
  .side { flex: 0 0 100px; background: #fca; }
  .main { flex: 1; background: #bfdbfe; }
  .main pre { margin: 0; font: 16px monospace; }
  .fix .main { min-width: 0; }   /* 바닥을 0 으로 내린다 */
</style>
```

> **보이는 것** — 위 상자에서는 파란 본문 **칸 자체가 빨간 테두리 밖으로 튀어나온다**(파란 바탕이 테두리 오른쪽으로 계속 이어진다). 아래 상자(`min-width: 0`)에서는 **파란 바탕이 빨간 테두리에서 정확히 끝나는데, `<pre>` 글자는 여전히 테두리를 넘어 이어진다.** 고쳐진 것은 **상자의 크기**이지 내용의 넘침이 아니다.\
> **바꿔 볼 것** — `.fix .main` 에 `overflow-x: auto` 를 추가 → 넘친 글자가 **본문 칸 안의 가로 스크롤**로 들어간다 · `<pre>` 를 평범한 `<p>` 로 바꾸면 **덜 뚫지만 여전히 뚫는다**(URL 안에 쪼갤 수 없는 긴 조각이 하나 있다 — 아래 실측)

*(Chrome 151 headless 실측 — 컨테이너 왼쪽을 원점으로: 기본 판은 `main` 배경 오른끝 380.02 · 글자 오른끝 380.02. `min-width: 0` 판은 `main` 배경 오른끝 **300.00** · 글자 오른끝은 **그대로 380.02**. 스크린샷으로도 파란 바탕의 끝만 달라지고 글자는 두 판 다 테두리를 넘는 것을 확인했다.)*

*(같은 실측 — 「바꿔 볼 것」의 두 가지도 돌려 봤다.\
`min-width: 0` + `overflow-x: auto` → `main` 폭 **200.00** · 오른끝 **300.00** · `main.scrollWidth` **280**(칸 안에서 스크롤된다) · 높이가 39 로 늘었다(스크롤바 자리).\
★ `<pre>` 를 `<p>` 로 바꾼 판(바닥 그대로) → `main` 폭 **248.00** · 오른끝 **348.00** — **덜 뚫지만 여전히 뚫는다.**\
줄바꿈 기회가 생겨 `min-content` 가 280.02 → 248 로 줄었을 뿐, `/api/v1/users/12345/preferences` 라는 **쪼갤 수 없는 조각 하나**가 남았기 때문이다. 「문단으로 바꾸면 해결된다」는 직관이 이 데이터에서는 틀렸다.)*

그림 해설 (한 단계씩):

- `flex-shrink: 1`은 **일을 하고 있었다.** 280.02 까지 깎았고 거기가 바닥이라 더 못 간 것이다.
- 그래서 `flex-shrink` 를 키워도 **아무 변화가 없다.** 고칠 곳은 `min-width` 다.
- `min-width: 0`은 `flex-shrink` 를 끄는 게 아니라 **바닥을 0 으로 내리는 것**이다.
- `flex-direction: column` 이면 같은 자리가 **`min-height: auto`** 다. 세로로 안 줄어드는 사고의 원인이 똑같다.

비용 — `min-width: 0`을 주면 **내용이 잘리거나 넘친다.** 바닥을 없앤 것이므로 `overflow` 처리를 같이 정해야 한다. 「안 뚫리게」와 「안 잘리게」 중 하나를 고르는 것이지 둘 다는 안 된다.

### (7) `flex-shrink` — basis 에 비례해 가중된다

**언제 쓰나** — 「똑같이 `flex-shrink: 1`인데 왜 어떤 항목만 많이 줄어드나」를 설명할 때.

`grow` 와 달리 `shrink` 는 **지분 × basis** 로 가중한다. 큰 항목이 더 많이 깎이는 것이 자연스럽기 때문이다.

```text
컨테이너 300px, basis 100 / 200 / 300 (합 600), 넘침 = 300, shrink 전부 1

가중치 = shrink × basis = 100, 200, 300   합 600
깎이는 양 = 300 × (가중치 / 600) = 50, 100, 150

        깎기 전                               깎은 뒤
  +------+-----------+---------------+   +---+-----+-------+
  | 100  |    200    |      300      |   | 50| 100 |  150  |
  +------+-----------+---------------+   +---+-----+-------+
     (합 600, 컨테이너 300)                  (합 300, 딱 맞는다)
```

```text
가중이 없었다면 (틀린 계산)          실제 (가중 있음)
300 ÷ 3 = 100 씩 깎는다
  100−100 = 0                      100−50  = 50
  200−100 = 100                    200−100 = 100
  300−100 = 200                    300−150 = 150
  -> 첫 항목이 사라진다              -> 비율이 유지된다
```

*(Chrome 151 headless 실측 — 세 판을 같은 300px 컨테이너에서 쟀다.\
① basis 100/200/300 · shrink 전부 1 → **50.00 / 100.00 / 150.00**\
② basis 전부 200 · shrink 1/2/3 → **150.00 / 100.00 / 50.00**\
③ basis 전부 200 · shrink 0/1/1 → **200.00 / 50.00 / 50.00** — `shrink: 0` 인 항목은 한 톨도 안 깎였다.\
세 판 모두 항목에 `min-width: 0`을 줘서 (6)의 바닥을 치웠다.\
★ **다만 이 demo 에서는 `min-width: 0`을 빼도 결과가 같다** — 실측으로 확인했다(50.00 / 100.00 / 150.00). 칸 안의 글자(`100`·`200`·`300`)가 짧아 `min-content` 가 50 보다 작기 때문이다. **바닥은 늘 있지만 닿아야 보인다.**\
★ 「바꿔 볼 것」 둘도 돌려 봤다 — 첫 항목만 `flex: 0 0 100px` 로 → **100.00 / 80.00 / 120.00**(그 칸만 지키고 나머지가 더 깎인다). 세 항목의 `grow` 를 0 → 1 로 → **50.00 / 100.00 / 150.00** 으로 **한 픽셀도 안 바뀐다**(자유 공간이 음수라 `grow` 가 쉰다 — (2)의 ④).)*

```html demo
<div class="c"><i>100</i><i>200</i><i>300</i></div>
<style>
  .c { display: flex; width: 300px; background: #eee; font: 14px monospace;
       outline: 2px solid #333; }
  .c i { display: block; font-style: normal; min-width: 0; overflow: hidden;
         background: #bfdbfe; outline: 1px solid #333; }
  .c i:nth-child(1) { flex: 0 1 100px; }   /* shrink 는 셋 다 1 */
  .c i:nth-child(2) { flex: 0 1 200px; }
  .c i:nth-child(3) { flex: 0 1 300px; }
</style>
```

> **보이는 것** — basis 합이 600px 인데 컨테이너는 300px 다. 세 칸이 **1 : 2 : 3 비율을 그대로 유지한 채** 절반으로 줄어 딱 맞게 들어간다. 라벨 숫자(`100`·`200`·`300`)는 basis 값이지 실제 폭이 아니다.\
> **바꿔 볼 것** — 첫 항목만 `flex: 0 0 100px`(shrink 0)로 → **그 칸만 100px 를 지키고** 나머지 둘이 더 깎인다 · `flex` 의 첫 값(`0`)을 `1` 로 바꿔도 **아무 일도 일어나지 않는다**(자유 공간이 음수라 `grow` 가 쉰다)

- **`grow` 는 지분만, `shrink` 는 지분 × basis.** 이 비대칭을 한 문장으로 외우는 것이 이 항의 전부다.
- 이유는 목적이 다르기 때문이다 — 남는 공간은 「누가 더 갖고 싶은가」의 문제이고, 모자란 공간은 「누가 더 양보할 여유가 있는가」의 문제다.

### (8) `flex-basis` 와 `width` 가 같이 있으면

**언제 쓰나** — 남의 코드에서 `width` 와 `flex` 가 겹쳐 있을 때.

```text
주축이 가로(row)일 때
  flex-basis: auto   ──> width 를 본다 ──> width 도 auto 면 ──> 내용 크기
  flex-basis: <길이>  ──> width 를 **무시**한다
```

*(Chrome 151 headless 실측 — `width: 100px` 를 셋 다 준 항목에: `flex: 0 0 auto` → 100.00px · `flex: 0 0 50px` → **50.00px**(`width` 가 졌다) · `flex` 선언 없음 → 100.00px. 계산값은 각각 `flex-basis: auto` / `50px` / `auto` 였다.)*

- `flex-basis` 가 길이면 **`width` 는 아무 일도 하지 않는다.** 「`width` 를 줬는데 안 먹는다」의 정체가 이것이다.
- 주축이 세로(`column`)면 같은 관계가 **`height` 와** 성립한다.\
  *(실측: 높이 300px 인 `column` 컨테이너에서 `flex: 1 1 0`과 `flex: 2 1 0`인 두 항목의 높이가 100.00 / 200.00 이었다 — `basis` 가 높이로 읽혔다.)*
- `flex-basis` 가 재는 칸은 **`box-sizing` 을 따른다.** [15번](../15-box-model-and-box-sizing/)과 같은 규칙이다.\
  *(실측: `flex: 0 0 100px; padding: 0 20px` 에서 `content-box` 는 바깥 폭 **140.00px**, `border-box` 는 **100.00px**.)*

### (9) ★ `getComputedStyle` 은 크기를 말해 주지 않는다

**언제 쓰나** — 콘솔에서 「왜 이 폭이 나왔나」를 조사할 때. **틀린 창으로 보면 답이 안 나온다.**

400px 컨테이너에 항목 넷을 넣고 세 창을 **같이** 읽었다.

```text
항목      flex-basis(계산값)   width(계산값)    getBoundingClientRect().width
1        50%                 163.031px       163.03
2        160px               130.438px       130.44
3        auto                100px           100.00
4        min-content         6.53125px         6.53
```

*(Chrome 151 headless 실측. 항목1 은 `flex: 0 1 50%`, 항목2 는 `flex: 0 1 10em`, 항목3 은 `width: 25%; flex: 0 0 auto`, 항목4 는 `flex: 1 1 min-content; min-width: 0`.)*

```text
세 창이 각각 무엇을 보여 주나

  getComputedStyle().flexBasis   ──> 「출발점이 뭐라고 적혀 있나」
                                     %·auto·min-content 가 **그대로 남는다**
                                     em 만 픽셀로 풀린다 (10em -> 160px)

  getComputedStyle().width       ──> 「결국 몇 픽셀이 됐나」 (사용값)

  getBoundingClientRect().width  ──> 「화면에서 실제로 몇 픽셀인가」
                                     transform·소수점까지 반영
```

- **`flex-basis` 의 계산값은 크기가 아니다.** 항목2 는 계산값이 `160px` 인데 실제 폭은 130.44px 다.
- 이 셋을 섞으면 「160px 라고 나오는데 화면은 130px 다」에서 막힌다. **두 값을 나란히 적고 어느 창인지 밝혀라.**
- 값이 단계마다 무엇이 되는지의 정본은 [04번](../04-value-processing-stages/)이다.

### (10) 상한에 걸린 항목이 생기면 — 남은 몫을 다시 나눈다

**언제 쓰나** — `max-width` 나 `flex-basis` 고정 항목이 섞여 있을 때.

```text
컨테이너 600px, 항목 셋 전부 flex: 1 1 0, 첫 항목에만 max-width: 50px

① 일단 200 / 200 / 200 로 나눈다
② 첫 항목이 max-width 50 에 걸려 얼어붙는다(freeze)
③ 남은 550 을 얼지 않은 둘이 1:1 로 다시 나눈다
        ↓
   50 / 275 / 275
```

*(Chrome 151 headless 실측: 50.00 / 275.00 / 275.00, 합 600.00.)*

- **「얼린 다음 다시 나눈다」가 알고리즘의 모양**이다((2)의 ⑤⑥).
- 그래서 `flex: 1`을 준 항목들의 폭이 **똑같지 않을 수 있다.** 누군가 상한·하한에 걸렸는지 먼저 본다.

## 문법 — 형태와 어디서 헷갈리나

CSS 는 문법 표면이 단순하므로 이 절은 **어디서 헷갈리나**로 읽는다.

### 최소 형태

```css
.item {
  flex: 1;                /* 단축 — 세 롱핸드를 한 번에 */

  /* 위 한 줄과 똑같은 것 */
  flex-grow: 1;
  flex-shrink: 1;
  flex-basis: 0%;
}
```

### ★ 단축의 한 값·두 값 축약 — 외우지 말고 물어봐라

`getComputedStyle` 로 각 형태를 **직접 읽어** 확인한 표다. 이 표의 값은 전부 Chrome 151 headless 실측이다.

| 쓴 것 | `flex-grow` | `flex-shrink` | `flex-basis` | 계산된 `flex` |
|---|---|---|---|---|
| (선언 없음) | `0` | `1` | `auto` | `0 1 auto` |
| `flex: initial` | `0` | `1` | `auto` | `0 1 auto` |
| `flex: 1` | `1` | `1` | `0%` | `1 1 0%` |
| `flex: 2` | `2` | `1` | `0%` | `2 1 0%` |
| `flex: auto` | `1` | `1` | `auto` | `1 1 auto` |
| `flex: none` | `0` | `0` | `auto` | `0 0 auto` |
| `flex: 10em` | `1` | `1` | **`160px`** | `1 1 160px` |
| `flex: 0%` | **`1`** | `1` | `0%` | `1 1 0%` |
| `flex: 1 2` | `1` | `2` | `0%` | `1 2 0%` |
| `flex: 1 30px` | `1` | `1` | `30px` | `1 1 30px` |
| `flex: 0 0 50%` | `0` | `0` | `50%` | `0 0 50%` |
| `flex-basis: 50%` 만 | `0` | `1` | `50%` | `0 1 50%` |
| `flex-basis: content` 만 | `0` | `1` | `content` | `0 1 content` |

읽는 법 — **값 하나를 쓸 때 그것이 숫자냐 길이냐로 자리가 갈린다.**

```text
flex: <숫자>          ──> grow 로 읽는다.  나머지는 1 과 0%
   flex: 1   =>  1 1 0%
   flex: 2   =>  2 1 0%

flex: <길이 또는 %>    ──> basis 로 읽는다. 나머지는 1 과 1
   flex: 30px =>  1 1 30px
   flex: 0%   =>  1 1 0%      ← 숫자 0 이 아니라 **길이 0%** 라 grow 가 1 이 된다

flex: <키워드>
   flex: none    =>  0 0 auto
   flex: initial =>  0 1 auto   (= 선언하지 않은 것과 같다)
```

- ★ **단축의 `flex-basis` 생략값은 `0%` 이지 `auto` 가 아니다.** 이것이 `flex: 1` ≠ `flex: auto` 의 유일한 원인이다.
- ★ **롱핸드만 쓰면 생략값이 다르다.** `flex-grow: 1` 한 줄만 쓰면 `flex-basis` 는 **초기값 `auto` 로 남는다** → `1 1 auto` = `flex: auto` 와 같아진다.\
  **`flex: 1`과 `flex-grow: 1`은 같은 뜻이 아니다.**
- `flex: 10em` 의 계산값이 `160px` 인 것은 `em` 이 계산값 단계에서 픽셀이 되기 때문이다([04번](../04-value-processing-stages/)). **`%` 와 `auto` 는 그대로 남는다.**

### 금지에 가까운 형태

```css
/* ① 컨테이너에 준다 — 아무 일도 안 한다 (항목에 주는 속성이다) */
.container { display: flex; flex: 1; }

/* ② flex-basis 에 길이를 쓰고 width 로 덮으려 한다 — width 가 진다 */
.item { flex: 0 0 200px; width: 100px; }   /* 200px 가 된다 */

/* ③ 음수 — 유효하지 않아 선언이 통째로 버려진다 */
.item { flex-grow: -1; }

/* ④ flex-shrink 를 키워 「더 줄이려」 한다 — 바닥은 min-width 가 정한다 */
.item { flex-shrink: 999; }                 /* (6) 을 보라 */
```

*(Chrome 151 headless 실측 — 진단 3창의 첫째 창(`cssRules`)으로 읽은 결과.\
`#n1 { }` ← `flex-grow: -1` · `#n2 { flex-grow: 1; }` ← 정상 · `#n3 { }` ← `flex: 1 1 -10px` · `#n4 { }` ← `flex-shrink: -1`.\
음수를 쓴 셋은 **규칙 상자가 비어 있다** — 선언이 파싱 단계에서 버려졌고 에러도 경고도 없다. 오류 복구의 정본은 [07번](../07-syntax-and-error-recovery/).)*

## 구현 세부사항 대 언어 보장

| 항목 | 누가 보장하나 |
|---|---|
| `flex: 1` = `1 1 0%`·`flex: auto` = `1 1 auto`·`flex: none` = `0 0 auto`·초기값 `0 1 auto` | **명세** — css-flexbox-1 §7 의 단축 정의 |
| 자유 공간이 양수면 `grow` 만, 음수면 `shrink` 만 쓴다 | **명세** — §9.7 유연 길이 해결 알고리즘 |
| `shrink` 는 basis 로 가중하고 `grow` 는 안 한다 | **명세** — §9.7 (「scaled flex shrink factor」) |
| flex 항목의 `min-width`/`min-height` 초기값이 `auto` 이고 자동 최소 크기가 된다 | **명세** — css-flexbox-1 §4.5 + css-sizing-3 |
| `flex-basis` 의 **계산값**에 `%`·`auto`·`content` 가 그대로 남는 것 | **명세** — 계산값 정의가 그렇다. 다만 `getComputedStyle` 이 속성마다 어느 단계를 주는지는 [04번](../04-value-processing-stages/)이 정본 |
| 위 표의 `10em → 160px` 같은 **구체 픽셀값** | **이 머신의 Chrome 151 실측** — 기본 글꼴 크기 16px 에 의존한다 |
| 재분배 반복의 **횟수와 순서** | **구현** — 명세는 결과를 정의하고 엔진이 방법을 고른다. 반올림 잔차가 엔진마다 다를 수 있다 |
| `getBoundingClientRect()` 의 소수 자릿수(163.03 등) | **구현** — 실제값 단계의 격자 맞춤. [04번](../04-value-processing-stages/) §(4) |

## 어디서 틀리나

이 주제의 값어치는 대부분 여기 있다. 여섯 다 **에러 없이 조용히 어긋난다.**

### 1. `flex: 1`과 `flex-grow: 1`을 같은 것으로 쓴다

```css
.a { flex: 1; }         /* = 1 1 0%   -> 칸이 균등해진다 */
.b { flex-grow: 1; }    /* = 1 1 auto -> 내용 차이가 남는다 */
```

단축은 생략된 `flex-basis` 를 **`0%` 로 채우고**, 롱핸드는 초기값 `auto` 를 그대로 둔다.\
「탭 넷이 균등해야 하는데 글자 긴 탭만 넓다」의 원인이 대개 이것이다.

### 2. `flex-shrink` 를 키워 「더 줄이려」 한다

바닥은 `flex-shrink` 가 아니라 **`min-width: auto`** 가 정한다((6)).\
`flex-shrink: 999` 는 **이미 바닥에 닿은 항목에 아무 영향이 없다.** 고칠 곳은 `min-width: 0`이다.

### 3. `flex: 1`을 줬는데 안 늘어난다

```text
자유 공간 = 컨테이너 − basis 합

컨테이너 폭이 내용에 딱 맞으면 자유 공간 = 0
-> grow 가 나눌 것이 없다. grow 값과 무관하다.
```

**컨테이너가 얼마나 넓은지 먼저 재라.** `inline-flex` 컨테이너나 부모가 `fit-content` 인 경우가 흔한 함정이다.

### 4. `width` 를 줬는데 안 먹는다

`flex-basis` 가 길이면 `width` 는 **무시된다**((8)). 남의 컴포넌트를 덮어쓸 때 자주 만난다.\
확인법: `getComputedStyle(el).flexBasis` 가 `auto` 가 아니면 `width` 는 이미 진 것이다.

### 5. `flex: 1`을 여럿에 줬는데 폭이 다르다

`max-width`·`max-height` 에 걸려 **얼어붙은 항목**이 있으면 나머지가 남은 몫을 다시 나눈다((10)).\
또는 (6)의 바닥에 걸린 항목이 있다. **둘 다 계산값으로는 안 보이고 `getBoundingClientRect()` 로만 보인다.**

### 6. 계산값과 실제 크기를 섞어 읽는다

`getComputedStyle().flexBasis` 는 `50%`·`auto`·`min-content` 를 **그대로** 돌려준다((9)).\
크기를 알고 싶으면 `getBoundingClientRect().width` 를 따로 재야 한다. **한 표에 섞어 적지 마라.**

### 7. `flex: 0%` 를 「안 늘어난다」로 읽는다

`0%` 는 **숫자가 아니라 길이**라 `flex-basis` 자리로 읽히고, 생략된 `flex-grow` 가 **1** 이 된다.\
*(실측: `flex: 0%` → `1 1 0%`.)* 「안 늘어나게」를 원했다면 `flex: 0 1 0%` 또는 `flex: none` 이다.

## 언제 쓰고 언제 안 쓰나

| 하고 싶은 것 | 쓸 것 | 왜 |
|---|---|---|
| 칸을 **내용과 무관하게 똑같이** | `flex: 1` | basis 0 이라 전체를 지분대로 나눈다 |
| **내용 크기를 존중하고** 남은 곳만 채우기 | `flex: auto` | basis 가 내용 크기 |
| 절대 안 늘고 안 줄게 (아이콘·아바타) | `flex: none` | `0 0 auto` |
| 고정 폭 사이드바 | `flex: 0 0 240px` | grow·shrink 둘 다 0 |
| 2:1 비율 | `flex: 2` / `flex: 1` | 지분만 비교한다 |
| 긴 텍스트·코드 블록을 담은 칸 | `flex: 1; min-width: 0` | (6)의 바닥을 내린다 |
| 두 축을 동시에 나눠야 한다 | Grid ([목록의 **27번 주제**](../27-grid-track-sizing/)) | `fr` 이 나누는 것도 「남는 공간」이지만 축이 둘이다 |

판단 규칙 두 줄.

- **`flex` 를 쓰기 전에 「자유 공간이 양수인가 음수인가」를 먼저 정하라.** 그 부호가 `grow`/`shrink` 중 무엇을 볼지 정한다.
- **긴 내용을 담는 칸에는 `min-width: 0`을 같이 쓴다.** 나중에 터지는 것이 아니라 **처음부터 같이 다니는 짝**이다.

## 핵심 문장

- `flex` 는 **`grow` · `shrink` · `basis`** 순서이고 초기값은 `0 1 auto` 다.
- **`flex: 1` = `1 1 0%`, `flex: auto` = `1 1 auto`, `flex: none` = `0 0 auto`.** 셋을 가르는 것은 오직 `basis` 다.
- 자유 공간이 **양수면 `grow` 만, 음수면 `shrink` 만** 일한다. 동시에 일하지 않는다.
- **`grow` 는 지분만으로, `shrink` 는 지분 × basis 로** 나눈다. 계산법이 다르다.
- flex 항목의 `min-width` 기본값은 **`auto` 이고 `min-content` 로 풀린다** — 이것이 항목이 컨테이너를 뚫는 유일한 원인급 이유다. `min-width: 0`이 바닥을 내린다.
- **`getComputedStyle().flexBasis` 는 크기가 아니다.** 실제 크기는 `getBoundingClientRect()` 로 따로 잰다.

## 용어 풀이

- **flex 항목(flex item)** — flex 컨테이너의 직계 자식 상자. `flex` 는 항목에 주는 속성이다.
- **`flex-grow`** — 자유 공간이 남을 때 더 받을 지분. 초기값 0. **basis 로 가중하지 않는다.**
- **`flex-shrink`** — 자유 공간이 모자랄 때 깎일 지분. 초기값 1. **basis 로 가중한다.**
- **`flex-basis`** — 나누기 전에 항목이 먼저 받는 주축 크기. 초기값 `auto`.
- **자유 공간(free space)** — 컨테이너 주축 크기 − (basis 합 + `gap` + 마진). 부호가 `grow`/`shrink` 중 무엇이 일할지 정한다.
- **자동 최소 크기(automatic minimum size)** — flex 항목의 `min-width`/`min-height` 가 `auto` 일 때 쓰이는 바닥. 대개 `min-content` 다.
- **`min-content`** — 내용을 부러뜨리지 않고 가질 수 있는 가장 작은 크기. 정본은 [31번](../31-intrinsic-sizing-and-aspect-ratio/).
- **얼어붙음(freeze)** — 해결 중 `min-*`/`max-*` 에 걸린 항목을 고정하고 나머지끼리 다시 나누는 것.
- **단축(shorthand)** — 여러 롱핸드를 한 줄로 쓰는 속성. **생략된 자리에 채워지는 값이 롱핸드 초기값과 다를 수 있다**(여기서는 `flex-basis`).
- **계산값 / 사용값** — 상속에 쓰이는 값 / 레이아웃이 끝난 뒤 확정된 값. 정본은 [04번](../04-value-processing-stages/).
- **주축(main axis)** — 항목이 줄지어 놓이는 방향. `basis` 가 폭인지 높이인지를 이것이 정한다. 정본은 [24번](../24-flexbox-axes/).

## 더 들어가면

- **`flex-basis: content`** — 「`width` 를 무시하고 무조건 내용 크기로」라는 값이다. `auto` 와 달리 `width` 를 보지 않는다.\
  *(실측: 계산값이 `content` 로 그대로 남는다.)* 쓸 일은 드물지만 `flex-basis: auto` 가 `width` 를 본다는 사실을 거울처럼 보여 준다.
- **`flex: 1 1 0` 과 `flex: 1 1 0%` 는 계산값이 다르다** — 앞엣것은 `0px`, 뒤엣것은 `0%` 로 남는다(실측). 결과는 같지만 **`%` 는 부모 크기가 정해져야 풀리므로** 부모 크기가 미정인 상황에서 갈릴 수 있다.
- **`gap` 은 basis 합에 더해져 자유 공간을 미리 줄인다.** 그래서 `flex: 1` 항목 셋에 `gap: 20px` 를 주면 각 칸이 `(폭 − 40) / 3` 이 된다. 정본은 [26번](../26-flex-wrap-gap-order/).
- ★ **`overflow` 를 `visible` 이 아닌 값으로 줘도 (6)의 바닥이 사라진다.** (6)과 같은 문서에서 `.main` 의 `overflow` 만 바꿔 쟀다.\
  *(실측: `overflow: visible` → 폭 280.02 · 오른끝 380.02(뚫는다) / `overflow: hidden` → 200.00 · 300.00 / `overflow: auto` → 200.00 · 300.00.)*\
  ★★ **그런데 세 판 모두 `getComputedStyle(main).minWidth` 는 `auto` 그대로였다.** 계산값만 보면 셋이 구분되지 않는다 —
  「담겼나·잡혔나·이겼나」의 세 창 어디에도 안 잡히고 **`getBoundingClientRect()` 로만 드러나는 자리**다.
  그래서 **`min-width: 0`을 안 썼는데 안 터지는 코드**가 있고, 나중에 누가 `overflow` 를 지우면 그때 터진다.
- **`flex-basis` 에도 내재적 크기 키워드를 쓸 수 있다** — `flex: 1 1 min-content` 처럼. (9)의 항목4 가 그 판이고 계산값이 `min-content` 로 남았다. 키워드의 뜻은 [31번](../31-intrinsic-sizing-and-aspect-ratio/)이 정본이다.
