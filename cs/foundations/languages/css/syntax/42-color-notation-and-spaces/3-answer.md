# css/syntax/42 — 색 표기와 색 공간 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 질문 → 서머리 → 여기 순서다.
> 번호는 [1-question.md](1-question.md)와 1:1 이다. **출력을 먼저, 해설은 그 뒤.**
> 모든 계산값은 **Google Chrome 151.0.7922.173** headless 에서 받은 것이고, 모든 RGB 는 **스크린샷 PNG 의 픽셀을 파이썬으로 읽은 값**이다.

### 1. 다섯 표기는 같은 색인가

**출력**

```text
.a  #f80                →  rgb(255, 136, 0)
.b  rgb(255, 136, 0)    →  rgb(255, 136, 0)
.c  rgb(255 136 0)      →  rgb(255, 136, 0)
.d  hsl(32 100% 50%)    →  rgb(255, 136, 0)
.e  hwb(32 0% 0%)       →  rgb(255, 136, 0)

다섯 문자열이 한 글자도 다르지 않다.
```

**왜 그런가**

- 다섯은 전부 **sRGB 안의 같은 한 점**을 다른 좌표계로 부른 것이다. 「집 한 채를 지번·도로명·방향거리로 부른 것」.
- 계산값 단계에서 **sRGB 계열 표기는 전부 `rgb(r, g, b)` 한 형태로 접힌다.** 그래서 내가 적은 형태의 흔적이 남지 않는다.

```text
  #f80 ┐
  rgb(255,136,0) ┐
  rgb(255 136 0) ├──→ [ sRGB 좌표 (255,136,0) ] ──→ 계산값 "rgb(255, 136, 0)"
  hsl(32 100% 50%) ┤
  hwb(32 0% 0%) ┘
```

- **주의** — `.c` 를 공백 문법으로 적었는데도 돌아온 것은 **쉼표 문법**이다. 문자열로 대조하면 절대 안 맞는다.

### 2. 범위를 넘긴 수와 모르는 함수 — 어느 쪽이 살아남나

**출력**

```text
선언                      cssText                          계산값
------------------------  -------------------------------  -----------------
notacolor(1 2 3)          ""  (빈 문자열)                   rgb(0, 0, 0)
rgb(300 -20 0)            "color: rgb(255, 0, 0);"         rgb(255, 0, 0)
hsl(32 100 50)            "color: rgb(255, 136, 0);"       rgb(255, 136, 0)

선언째 버려진 것은 1번(notacolor) 하나뿐이다.
```

**왜 그런가**

- **`notacolor(...)`** — 파서가 그런 색 함수를 모른다. CSS 의 오류 복구는 **그 선언 하나만** 버린다(07번 주제). 에러도 경고도 없다. 계산값은 `color` 의 초기값인 검정이다.
- **`rgb(300 -20 0)`** — 표기는 **아는 것**이다. 수가 범위를 벗어났을 뿐이라 **버리지 않고 잘라 넣는다.** `300 → 255`, `-20 → 0`.
- **`hsl(32 100 50)`** — `%` 없는 수도 유효하다. 「`%` 를 빠뜨려서 안 먹혔겠지」라는 진단이 틀린다.

```text
  파서가 표기를 아나?
     │
     ├── 모른다 ──→ 선언째 버림.  cssText 가 빈 문자열
     │
     └── 안다 ────→ 수가 범위 밖인가?
                       ├── 예 ──→ 잘라서 넣는다.  cssText 에 잘린 값이 보인다 ★
                       └── 아니오 ──→ 그대로
```

### 3. `getComputedStyle` 이 색을 무엇으로 돌려주나

**출력**

```text
선언                          계산값
----------------------------  ----------------------------------
hsl(32 100% 50%)              rgb(255, 136, 0)
oklch(0.75 0.17 60)           oklch(0.75 0.17 60)
lab(70 40 70)                 lab(70 40 70)
color(display-p3 1 0.5 0)     color(display-p3 1 0.5 0)
rgb(255 136 0 / 1)            rgb(255, 136, 0)
rgba(255, 136, 0, 0.5)        rgba(255, 136, 0, 0.5)
```

**경계 한 줄** — **sRGB 계열 레거시 표기(`#hex`·`rgb()`·`hsl()`·`hwb()`·이름)만 `rgb(...)`/`rgba(...)` 로 접히고, `lab`·`lch`·`oklab`·`oklch`·`color()` 는 적은 공간 그대로 남는다.**

**왜 그런가**

- 04번의 결론이 여기서 한 겹 더 갈린다 — 「계산값이 무엇이냐」가 **속성마다** 다른 게 아니라 **같은 속성 안에서 값의 표기마다** 다르다.
- 현대 표기를 sRGB 로 접으면 **sRGB 밖의 좌표를 표현할 수 없어서** 정보가 사라진다. 그래서 안 접는다.
- **알파가 1 이면 `rgb(...)`, 1 미만이면 `rgba(...)`** 로 갈린다. `/ 1` 을 명시해도 흔적이 사라진다.

```text
  적은 것                         계산값
  ┌────────────────────────┐      ┌──────────────────────────┐
  │ #f80 · rgb() · hsl()   │ ───→ │ rgb(255, 136, 0)         │  접힌다
  │ hwb() · rebeccapurple  │      │ (알파 있으면 rgba(...))   │
  └────────────────────────┘      └──────────────────────────┘
  ┌────────────────────────┐      ┌──────────────────────────┐
  │ oklch() oklab()        │ ───→ │ oklch(0.75 0.17 60)      │  그대로
  │ lab() lch() color()    │      │ (적은 공간 그대로)        │
  └────────────────────────┘      └──────────────────────────┘
```

### 4. 같은 `l` 인데 밝기가 같은가

**출력**

```text
선언                     픽셀                  상대 휘도 Y (픽셀에서 계산)
---------------------    -----------------     -------------------------
hsl( 60 100% 50%) 노랑   rgb(255, 255, 0)      0.9278   ← 가장 밝다
hsl(120 100% 50%) 초록   rgb(  0, 255, 0)      0.7152
hsl(  0 100% 50%) 빨강   rgb(255,   0, 0)      0.2126
hsl(240 100% 50%) 파랑   rgb(  0,   0, 255)    0.0722   ← 가장 어둡다

0.9278 / 0.0722 = 12.9 배
```

**같지 않다.** 눈에도 확연히 다르다 — 노랑은 눈부시고 파랑은 거의 검정처럼 보인다.

**고치는 선언 한 줄**

```css
/* hsl 의 l 대신 oklch 의 l 을 고정한다 */
background: oklch(0.7 0.15 var(--hue));
```

**출력 (고친 뒤)**

```text
선언                     픽셀                   Y
---------------------    -------------------    ------
oklch(0.7 0.15  25)      rgb(237, 117, 110)     0.3185
oklch(0.7 0.15 100)      rgb(181, 159,   0)     0.3462
oklch(0.7 0.15 145)      rgb( 91, 182,  97)     0.3654
oklch(0.7 0.15 260)      rgb(101, 157, 251)     0.3385

0.3654 / 0.3185 = 1.15 배
```

**왜 그런가**

- `hsl` 의 `l` 은 **그 색공간 좌표의 중간값**이지 사람이 느끼는 밝기가 아니다. `l: 50%` 는 「그 색상에서 가장 선명한 자리」에 가깝고, 노랑의 가장 선명한 자리는 밝고 파랑의 그것은 어둡다.
- `oklch` 의 `l` 은 **지각 밝기를 축으로 삼도록 설계된 공간**의 값이다. 그래서 고정하면 실제로 고정된다.

```text
  hsl  l=50% 고정                oklch  l=0.7 고정
  +--------------------------+   +--------------------------+
  | Y 0.0722 \~ 0.9278        |   | Y 0.3185 \~ 0.3654        |
  |        12.9 배            |   |        1.15 배            |
  +--------------------------+   +--------------------------+
```

> **재서술자 주** — 위 표의 `픽셀` 은 스크린샷에서 읽은 **실측**이고, `Y` 는 그 세 수로 WCAG 상대 휘도 식을 돌린 **파생값**이다. 둘을 갈라서 읽는다.

### 5. 넓은 색 영역 색을 sRGB 화면에 칠하면

**출력**

```text
          픽셀                계산값
--------  ------------------  ---------------------------
.p3       rgb(255, 0, 0)      color(display-p3 1 0 0)
.srgb     rgb(255, 0, 0)      rgb(255, 0, 0)

픽셀은 같다. 계산값은 다르다.
```

**왜 갈리나**

- **계산값(③)은 「내가 무엇을 요구했나」** 이고 **픽셀(④)은 「화면이 무엇을 낼 수 있었나」** 다. 서로 다른 칸이다.
- 같은 문서에서 `matchMedia('(color-gamut: p3)').matches` 가 **`false`** 였다 — 이 화면은 sRGB 까지만 낸다. 그래서 P3 의 가장 빨간 색이 **sRGB 의 가장 빨간 색으로 잘려** 나왔다.
- `color(rec2020 0 1 0)` 도 같은 이유로 `rgb(0, 255, 0)` 이었다.

```text
   요구한 색                   화면이 낼 수 있는 범위        실제 픽셀
   color(display-p3 1 0 0) ─┐
                            ├─→ [ sRGB 까지만 ] ──────────→ rgb(255, 0, 0)
   rgb(255 0 0) ────────────┘                                   (둘이 겹쳤다)
```

- ★ **이 환경에서 넓은 색 영역을 「봤다」고 말할 수 없다.** 못 봤다. 다른 화면에서는 다른 픽셀이 나온다.

### 6. `transparent` 의 계산값은 무엇인가

**출력**

```text
color: transparent   →   rgba(0, 0, 0, 0)
```

**왜 그 세 숫자인가**

- **`transparent` 는 「색 없음」이 아니라 「검정 + 알파 0」으로 정의돼 있다.** 그래서 RGB 성분이 `0, 0, 0` 이다.
- 알파가 0 이니 **혼자 칠할 때는 아무 차이가 없다.** 이 검정 성분이 드러나는 자리는 **보간할 때**다 — [45번](../45-gradients-and-interpolation/2-summary.md)에서 픽셀로 잰다.

### 7. 둘 중 어느 쪽이 더 위험한가

**범위를 넘긴 수(`rgb(300 -20 0)`) 쪽이 더 위험하다.**

- `notacolor(...)` 는 **cssText 가 빈 문자열**이라 진단 3창의 **창 1** 에서 바로 잡힌다. 「안 담겼다」가 눈에 보인다.
- `rgb(300 -20 0)` 은 **담긴다.** cssText 에 `color: rgb(255, 0, 0);` 이 있고 계산값도 정상적으로 나온다. **어디에도 「잘렸다」는 흔적이 없다.**
- 그래서 `calc()` 로 만든 채널값이 범위를 넘으면 **조용히 다른 색이 칠해지고**, 진단 3창을 전부 열어 봐도 이상이 안 보인다. **값이 맞는지 직접 계산해 보는 수밖에 없다.**

### 8. `currentColor` 는 상속되는가

**상속된 것은 `color` 다.**

- `border-color` 는 **상속되지 않는 속성**이다. 그런데 **초기값이 `currentColor`** 다.
- `currentColor` 는 「이 요소의 `color` 계산값」을 가리킨다. 그 `color` 가 부모에서 상속돼 내려왔기 때문에 결과적으로 테두리가 따라간 것이다.

```text
  부모 .j { color: #e11d48 }
        │
        │ color 가 상속된다
        v
  자식 <span>  color = rgb(225, 29, 72)
               border-color 를 안 적었다 → 초기값 = currentColor
                                          → currentColor = 이 요소의 color
                                          → rgb(225, 29, 72)

  실측: 자식의 borderTopColor = rgb(225, 29, 72)
```

- **`currentColor` 자체는 상속되는 무엇이 아니다.** 「값을 가리키는 키워드」다. 정본은 [03번](../03-inheritance-and-global-keywords/2-summary.md)이다.

### 9. 「계산값이 `oklch(...)` 다」와 「화면이 그 색이다」는 왜 다른 문장인가

**③(계산값)과 ④(픽셀)이 서로 다른 칸이기 때문이다.**

```text
  ① 적은 것              ② 담겼나          ③ 계산값               ④ 픽셀
  oklch(0.7 0.4 150)  →  담김       →  oklch(0.7 0.4 150)  →  rgb(0, 214, 0)
                                          (요구한 좌표 그대로)      (화면이 낼 수 있는 색)
```

- ③은 **내가 요구한 것**을 그대로 보관한다. 안 접히는 것이 오히려 정보 보존을 위한 설계다.
- ④는 **화면의 색 영역 안으로 옮겨진 결과**다. `oklch(0.7 0.4 150)` 은 어느 화면도 못 내는 좌표라 옮겨졌다.
- 그래서 **계산값만 읽고 「색이 맞다」고 판정하면 틀린다.** 색 주제에서는 **픽셀을 읽어야** 한다.

### 10. 색이 안 나올 때 어느 창부터 여나

**창 1 — `document.styleSheets[i].cssRules[j].style.cssText`.**

- 표기 자체가 안 먹혔으면 **cssText 가 빈 문자열**이다. 규칙은 있는데 선언이 없다.
- CSS 는 에러가 없는 언어라 **콘솔에도 화면에도 아무 말이 없다.** 이 창을 안 열면 「선택자가 안 잡혔나」·「캐스케이드에서 졌나」와 증상이 전부 같다.

```text
  창 1  cssRules[j].style.cssText     ""          → 표기를 몰라 선언째 버렸다
  창 2  querySelectorAll(sel).length  0           → 선택자가 아무것도 못 잡았다
  창 3  getComputedStyle(el).color    남의 값      → 담겼고 잡았는데 졌다
```

- 단 **「잘림」은 이 창으로 안 잡힌다**(7번 참고). cssText 에 정상적인 값이 보인다.

### 11. `oklch` 에서 `C` 를 0 으로 하면

**출력**

```text
oklch(0.7 0 150)   →  회색 (크로마가 0 이므로 색기가 없다)
oklch(0.7 none 150) 픽셀 rgb(158, 158, 158)   ← 실측. none 도 이 자리에서는 0 처럼 칠해졌다
oklch(from red l 0 h) 계산값 oklch(0.627966 0 29.2346)
```

**`#808080` 같은 회색과 무엇이 다른가**

- **밝기를 좌표로 지정한 회색**이다. `oklch(0.7 0 h)` 와 `oklch(0.5 0 h)` 는 **지각 밝기 차가 일정**하다. `#888`·`#666` 을 손으로 고르면 그 간격이 고르지 않다.
- **기준색에서 파생할 수 있다.** `oklch(from var(--brand) l 0 h)` 는 「브랜드 색과 같은 밝기의 회색」이다 — 이 형태는 [43번](../43-color-mix-and-relative-color/2-summary.md)이 정본이다.
- 색상(`h`)은 남아 있지만 크로마가 0 이라 **화면에서는 무채색**이다. 나중에 `C` 만 올리면 원래 색상으로 돌아온다.

### 12. 접근성 대비를 `hsl` 의 `l` 로 맞추면 안 되는 이유

**「`l` 이 같으면 밝기가 같다」가 거짓이기 때문이다.**

- 4번 실측: `l: 50%` 를 고정한 네 색의 상대 휘도가 **0.0722 \~ 0.9278**, **12.9배** 차이였다.
- 대비비는 **두 색의 상대 휘도의 비**로 정해진다. 휘도가 12.9배 벌어지면 **같은 배경 위에서 어떤 색상은 통과하고 어떤 색상은 떨어진다.**
- 특히 **파랑 계열**(`hsl(240 100% 50%)`, Y=0.0722)은 `l: 50%` 인데도 거의 검정에 가깝고, **노랑 계열**(Y=0.9278)은 거의 흰색에 가깝다. 흰 배경 위에서 이 둘의 운명은 정반대다.
- 고치는 법은 둘이다 — ① `oklch` 의 `l` 로 통일한다(1.15배까지 좁혀졌다) ② **휘도를 직접 계산하거나 대비 검사 도구로 잰다.** `oklch` 도 대비비를 보장하지는 않는다 — **지각 밝기와 WCAG 휘도는 다른 척도**다.

**픽셀을 읽은 방법** (다음 주제가 재사용하도록 그대로 적는다)

```text
  1. 색 견본만 담은 최소 HTML 을 쓴다. body{margin:0} 으로 좌표를 예측 가능하게 만든다.
  2. google-chrome --headless --disable-gpu --no-sandbox \
       --screenshot=out.png --window-size=W,H  doc.html
  3. python3 로 PNG 를 열어 좌표의 (r,g,b) 를 읽는다.

       im = Image.open('out.png').convert('RGB')
       print(im.getpixel((x, y)))
  ★ 스크린샷은 세로 스크롤이 생기면 오른쪽 15px 가 스크롤바다 — 그 자리를 읽지 않는다.
  ★ 스크린샷·PNG 는 저장소에 넣지 않는다. 확인용으로 쓰고 버린다.
```

**구현에 달린 항목 — 버전이 오르면 다시 찍을 것**

| 항목 | 왜 |
|---|---|
| `color(display-p3 …)` 의 픽셀 | **화면의 색 영역에 달렸다.** 이 환경은 sRGB 였다 |
| 영역 밖 좌표(`oklch(0.7 0.4 150)`)의 픽셀 | **영역 매핑 알고리즘은 엔진이 고른다** |
| 계산값 문자열의 소수 자릿수 | CSSOM 직렬화 형식 |
| `rgb(none 128 0)` 이 `rgb(0, 128, 0)` 이 되는 것 | 레거시 `rgb()` 의 `none` 처리 |
