# css/syntax/14 — 중첩(nesting): `&` 의 의미와 중첩 명시도 — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [CSS Nesting Module Level 1](https://drafts.csswg.org/css-nesting-1/) (§3 중첩 규칙 · §3.4 선언과 규칙 섞기 · §4 `&` 선택자 · §5 중첩 선언 규칙 · §7 Changes). 열어서 확인한 것만 적었다.
> **실행 검증** — 이 문서의 모든 명시도·직렬화 결과·순서 판정은 **Google Chrome 151.0.7922.173** headless 에서 실제로 돌렸다.\
> 근거를 **두 층**으로 나눠 뽑았다 — ① `cssRules` 를 재귀로 훑어 **브라우저가 무엇으로 파싱했나**(`selectorText`·규칙 종류) ② `getComputedStyle` 로 **무엇이 이겼나**. 명시도 주장은 전부 ② 로만 확인했다.\
> **엔진은 Chrome 하나다.** Firefox 155.0.1 은 이 환경에서 headless 스크린샷이 산출되지 않으므로 **「두 엔진에서 확인했다」고 적지 않았다.** 크로스 브라우저는 Baseline 으로만 접지한다.
> **버전** — CSS 에 언어 버전은 없다. 중첩의 Baseline 은 **widely available**(newly 2023-12-11 → widely 2026-06-11). 2026-09-23 에 `api.webstatus.dev` 를 직접 조회한 값이고, 엔진별 최초 지원은 Firefox 117(2023-08) · Chrome/Edge 120(2023-12) · Safari 17.2(2023-12) 다.
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 숫자는 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

`&` 는 「윗줄이 부른 사람들 **전부**」라는 대명사다. **문자열 복사·붙여넣기가 아니다.**

그리고 결론 하나가 거기서 바로 나온다 — **그 무리에 VIP 가 한 명 끼어 있으면 팀 전체가 VIP 대우를 받는다.**

비유 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 단체 예약 명단 | 부모 규칙의 **선택자 목록**(`.a, #b`) |
| 「윗줄 팀」이라는 대명사 | `&` |
| 명단에 VIP 가 하나 끼어 있다 | 목록에 `#b` 같은 ID 가 하나 있다 |
| 팀 전체가 VIP 등급을 받는다 | ★ **중첩 규칙의 명시도가 `#b` 를 따라 올라간다** |
| 명단을 손으로 베껴 두 줄로 쓴다 | 중첩을 손으로 펼쳐 `#a c, b c` 로 쓰는 것 |
| 베껴 쓰면 각자 제 등급으로 돌아간다 | ★ **손으로 펼치면 결과가 달라진다** |

```text
   중첩 소스                          브라우저가 계산하는 것

   .a, #b {                           :is(.a, #b) .c { color: green; }
     & .c { color: green; }                ^^^^^^^^^^
   }                                       & 가 이것으로 치환된다

   손으로 펼치면 (다른 것이다!)
   .a .c, #b .c { color: green; }
        ^^^^^        각자 제 명시도를 갖는다
```

- `&` 는 「**부모 선택자 목록 전체**」다. 명세가 그 명시도를 「부모 선택자 목록 안의 복잡 선택자들 중 **가장 큰 것**과 같다(`:is()` 와 똑같은 동작)」고 정한다.
- 그래서 **중첩과 손 펼침은 같은 요소를 고르지만 세기가 다르다.** 명세 본문도 이것을 「눈에 띄게, 수동으로 펼쳤을 때와 다른 결과」라고 못 박는다.
- 중첩은 **파일을 짧게 쓰는 문법**이 아니라 **선택자를 조립하는 문법**이다. 조립 결과가 무엇인지 모르면 명시도가 조용히 어긋난다.

실무에서 이게 터지는 자리는 **레거시 ID 하나를 부모 목록에 끼워 넣을 때**다.\
`html, #app { ... }` 같은 줄 아래에 중첩을 쌓으면, 그 아래 **모든 중첩 규칙이 `(1, …)` 짜리**가 된다.

> **중첩(nesting)** — 스타일 규칙 안에 다른 스타일 규칙을 넣어, 안쪽 규칙이 바깥 규칙이 고른 요소를 가리키게 하는 문법.\
> 예: `.card { & .title { … } }` 는 `.card .title { … }` 자리에 온다.

> **중첩 선택자(nesting selector) `&`** — 부모 규칙의 선택자 목록을 가리키는 기호.\
> 예: `.a, #b` 아래의 `&` 는 「`.a` 이거나 `#b` 인 것」을 뜻한다.

> **상대 선택자(relative selector)** — 조합자로 시작할 수 있는 선택자. 중첩 규칙은 이것을 받는다.\
> 예: `.card { > .title { … } }` 의 `> .title`.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 세 질문을 둔다.

1. 중첩을 보고 **펼친 선택자를 손으로 복원**할 수 있는가 — 그리고 그 복원이 **명시도까지 맞는가.**
2. `&` 를 **생략했을 때·뒤에 붙였을 때·두 번 썼을 때** 각각 무엇이 되는가.
3. **선언과 중첩 규칙이 섞였을 때** 어느 것이 이기는가.

## 동작 방식

### (1) 펼치면 무엇이 되나 — 좌우로 놓고 읽는다

**언제 쓰나** — 중첩된 규칙을 읽을 때마다. 이것이 이 주제의 본체다.

브라우저가 실제로 무엇으로 파싱했는지는 `cssRules` 를 재귀로 훑어 `selectorText` 를 읽으면 나온다.\
아래 오른쪽 칸은 **전부 그 실측값**이다(Chrome 151 headless).

```text
   중첩 소스                          Chrome 이 담은 selectorText
   ──────────────────────────────    ──────────────────────────────
   .a, #b {                           바깥: ".a, #b"
     & .c { }                           안쪽: "& .c"
   }

   .a, #b {                           바깥: ".a, #b"
     .c { }        <- & 생략            안쪽: "& .c"   ★ & 가 끼워져 나온다
   }

   .a {                               바깥: ".a"
     div { }       <- 타입으로 시작      안쪽: "& div"  ★ 이것도 끼워진다
   }

   .a {                               바깥: ".a"
     > .q { }      <- 조합자로 시작      안쪽: "& > .q" ★ 절대화된다
   }

   .a {                               바깥: ".a"
     + .bar { }                         안쪽: "& + .bar"
   }

   .c {                               바깥: ".c"
     .x & { }      <- & 를 뒤에          안쪽: ".x &"   (그대로)
   }
```

그림 해설 (한 단계씩):

- **`&` 를 안 쓰면 브라우저가 끼워 넣는다.** 명세가 「중첩 규칙은 `<relative-selector-list>` 를 받고, 상대 선택자는 **암묵의 중첩 선택자**를 기준으로 삼는다」고 정한다.
- **직렬화할 때 절대화된다.** `> .foo` 가 `& > .foo` 로 나오는 것은 CSSOM 조항에 명시돼 있다.
- **`&` 를 뒤에 쓰면 그 자리에 그대로 남는다.** `.x &` 는 「`.x` 안의 (부모)」다 — 부모를 자손 자리로 내린다.
- ★ **여기서 「& 가 문자열로 치환된다」고 읽으면 안 된다.** 치환되는 것은 **`:is(부모 목록)` 이라는 한 덩어리**다. (2)절이 그 증거다.

비용 — 없다. 파싱 시점에 한 번 조립된다.

### (2) `&` 의 명시도 — 부모 목록 중 가장 센 것

**언제 쓰나** — 중첩 규칙이 다른 규칙에 지거나 이길 때. **이 주제에서 사람들이 가장 많이 틀리는 자리다.**

★ **명시도 계산의 정본은 [02번 주제](../02-specificity/2-summary.md)다.** 세 자리 세는 법을 여기서 다시 쓰지 않는다.\
여기서 받아 올 결론은 한 줄이다 — **`&` 의 명시도는 부모 선택자 목록 중 가장 센 것이다.** 규칙이 `:is()` 와 **글자 그대로 같다.**

```text
   .a, #b {  & .c { }  }

   & 의 명시도 = max( .a , #b )
                = max( (0,1,0) , (1,0,0) )
                = (1, 0, 0)          <- #b 를 따라 올라간다

   & .c 전체    = (1,0,0) + (0,1,0)
                = (1, 1, 0)

   ★ .a 에 매치될 때도 (1,1,0) 이다. #b 는 이 문서에 없어도 된다
```

실측표다. `getComputedStyle` 로 **동점 경쟁자 · 한 칸 낮은 경쟁자 두 판**을 돌려 위아래를 고정했다.

| 무엇을 썼나 | (A, B, C) | 같은 값이 나오는 손 펼침 |
|---|---|---|
| `.a, #b { & .c { } }` | **(1, 1, 0)** | `:is(.a, #b) .c` — **같다** |
| `.a, #b { .c { } }`(`&` 생략) | **(1, 1, 0)** | 〃 |
| `.a .c { }`(평평하게) | (0, 2, 0) | — |
| `.a { & .c { } }`(부모가 하나) | (0, 2, 0) | `.a .c` 와 같다 |
| `.a, #b { & { } }` | (1, 0, 0) | `:is(.a, #b)` |
| `.a { & { } }` | (0, 1, 0) | `.a` |
| `.a, #b { && { } }` | **(2, 0, 0)** | `:is(.a,#b):is(.a,#b)` |
| `.a, #b { p { } }` | (1, 0, 1) | `:is(.a, #b) p` |
| `.c { .a & { } }` | (0, 2, 0) | `.a .c` |
| `.c, #b { .a & { } }` | **(1, 1, 0)** | `.a :is(.c, #b)` |
| `.a, #b { & .c { & .d { } } }`(2단) | **(1, 2, 0)** | `:is(:is(.a, #b) .c) .d` — **같다** |
| `.a .c .d { }`(평평하게) | (0, 3, 0) | — |
| `.a { @media (…) { .c { } } }` | (0, 2, 0) | `.a .c` — `@media` 는 명시도에 0 |
| `& p { }`(최상위, 부모 없음) | **(0, 0, 1)** | `p` 와 같다 — ★ `&` 가 **0** |
| `:scope p { }`(최상위) | (0, 1, 1) | ★ `& p` 와 **다르다** |

그림 해설:

- ★ **부모 목록에 ID 가 하나 있으면 `.a` 쪽에 매치될 때도 A 자리가 올라간다.** 매칭 결과가 아니라 **선택자의 모양**을 보기 때문이다.
- ★ **2단 중첩은 (1,2,0)** 이고, 평평하게 쓴 `.a .c .d` 는 (0,3,0) 이다 — **중첩을 한 겹 더 쌓아도 `#b` 가 계속 따라온다.**
- **`&&` 는 `:is(부모):is(부모)`** 다. 명세가 예로 `.foo { && { } }` 가 `.foo.foo` 와 같다고 적어 놓았고, 실측에서 (2,0,0) 이 나왔다.
- ★ **최상위의 `&` 는 0 이다.** 명세가 「부모 선택자 목록이 **없으면 0**」이라고 정한다. `:scope p` 와 **고르는 것은 같은데 명시도가 다르다**(실측 (0,0,1) 대 (0,1,1)).
- **`@media` 는 명시도에 아무것도 안 보탠다.** 중첩됐어도 부모의 값만 따라간다.

비용 — 없다. 대신 **읽는 사람이 파일을 위로 거슬러 올라가야 세기를 알 수 있게 된다.**

#### 명세가 들어 놓은 예를 그대로 돌려 봤다

명세 §4 에 「손으로 펼친 것과 결과가 다르다」는 예가 실려 있다. **그 예를 그대로 던졌다.**

```html
<b class="foo"><c>Blue text</c></b>
```

```text
   판 1 — 중첩으로 쓴다                     판 2 — 손으로 펼쳐 쓴다
   ┌──────────────────────────────┐        ┌──────────────────────────────┐
   │ #a, b { & c { color: blue } }│        │ #a c, b c  { color: blue }   │
   │ .foo c  { color: red }       │        │ .foo c     { color: red }    │
   └──────────────────────────────┘        └──────────────────────────────┘
      & = max(#a, b) = (1,0,0)                #a c  = (1,0,1)   <- <c> 에 안 맞는다
      & c           = (1,0,1)                 b c   = (0,0,2)   <- 이것이 맞는다
      .foo c        = (0,1,1)                 .foo c = (0,1,1)  <- 이쪽이 세다
      -> (1,0,1) 이 이긴다                     -> (0,1,1) 이 이긴다

   실측: rgb(0, 0, 255)  파랑              실측: rgb(255, 0, 0)  빨강
```

- **같은 뜻으로 보이는 두 판이 정반대 결과를 낸다.**
- 이유는 한 줄이다 — **중첩에서는 `#a` 가 매치에 실패해도 명시도에는 남는다.** `:is(#a, b)` 라는 한 덩어리로 계산되기 때문이다.
- 손으로 펼치면 `#a c` 와 `b c` 가 **따로** 계산되고, `<c>` 에 맞는 것은 `b c`(0,0,2) 뿐이라 `.foo c`(0,1,1) 에 진다.
- ★ **이것이 이 주제의 결론이다.** 「중첩은 그냥 짧게 쓰는 것」이라는 모델이 여기서 깨진다.

### (3) `&` 를 생략했을 때와 뒤에 붙였을 때

**언제 쓰나** — 중첩 규칙을 실제로 쓸 때.

```text
   & 를 앞에                  & 를 생략                  & 를 뒤에
   .card {                    .card {                    .title {
     & .title { }               .title { }                 .card & { }
   }                          }                          }
      ↓                           ↓                          ↓
   :is(.card) .title          :is(.card) .title          .card :is(.title)
      (같다)                     (같다)                   ★ 순서가 뒤집힌다
```

- **앞에 쓰나 생략하나 같다.** 브라우저가 `& ` 를 끼워 넣는 것을 `selectorText` 로 확인했다.
- **붙여 쓰는 것은 다르다.**

```css
.card { &.active { } }   /* :is(.card).active — 같은 요소가 .active 이기도 할 때 */
.card { & .active { } }  /* :is(.card) .active — 자손 */
```

- **공백 하나가 「같은 요소」와 「자손」을 가른다.** 중첩에서 가장 자주 나는 오타다.
- **`.x &` 는 부모를 자손 자리로 내린다** — 「`.x` 안에 있을 때의 이 컴포넌트」를 쓰는 형태다.

```css
.theme-dark { }
.card { .theme-dark & { background: #111; } }   /* .theme-dark :is(.card) */
```

### (4) 타입 선택자로 시작하는 중첩 — 표준이 한 번 바뀐 자리

**언제 쓰나** — `.card { div { } }` 처럼 `&` 없이 태그 이름으로 시작하고 싶을 때.

```text
   초기 명세 (2023 초)          지금
   .card { div { } }  ✘         .card { div { } }  ✔
   .card { & div { } } ✔        .card { & div { } } ✔

   ★ 초기 안에서는 중첩 규칙이 식별자로 시작하면 무효였다
     (파서가 「선언인가 선택자인가」를 구분 못 했기 때문)
   ★ 지금은 파서가 무한 예측(infinite lookahead)을 하므로 구분할 수 있다
```

- 명세의 변경 이력에 근거가 남아 있다 — 파서가 무한 예측을 하게 되면서 제약이 풀렸고, 대신 **`&div`(붙여 쓰기)는 다시 무효로 되돌렸다.** 전처리기와 충돌하기 때문이라고 적혀 있다.
- Chrome 151 실측이 그대로다.

| 던진 것 | 안쪽 규칙 | `selectorText` |
|---|---|---|
| `.a { div { } }` | **담김** | `& div` |
| `.a { & div { } }` | **담김** | `& div` |
| `.a { &div { } }` | **버림** | — (바깥 `.a` 는 살아 있다) |
| `.a { &-suffix { } }` | **버림** | — ★ 문자열 이어붙이기는 **안 된다** |
| `.a { &.b { } }` | 담김 | `&.b` |
| `.a { .b& { } }` | 담김 | `.b&` |
| `.a { :where(&) { } }` | 담김 | `:where(&)` |

- ★ **`&-suffix` 가 안 되는 것이 전처리기와 갈리는 가장 큰 자리다.** Sass 의 `&__title` 같은 BEM 이어붙이기는 **CSS 중첩에 없다.**
- 명세도 그 사실을 적어 놓았다 — 전처리기는 선택자를 **문자열로 이어 붙이지만** CSS 중첩은 그렇게 하지 않는다.

#### 무효한 중첩 규칙은 부모를 죽이지 않는다

```text
   .a {                       cssRules
     &div { color: red; }       └ .a          <- 살아 있다
   }                                (자식 규칙 0개)
```

- 명세 조항이 그대로다 — 「무효한 중첩 스타일 규칙은 **그 내용과 함께 무시되지만, 부모 규칙을 무효화하지는 않는다.**」
- 실측에서 바깥 `.a` 규칙은 `cssRules` 에 남았고 자식 규칙만 없었다.
- ★ **그래서 오타가 더 조용해진다** — 부모 규칙이 멀쩡히 살아 있어서 「시트는 정상」으로 보인다.

### (5) 선언과 중첩 규칙이 섞였을 때의 순서

**언제 쓰나** — 중첩 규칙 **뒤에** 선언을 더 쓰게 됐을 때. ★ **직관과 다를 수 있는 자리다.**

```text
   .a {
     color: rgb(1,1,1);        선언
     & { color: rgb(2,2,2); }  중첩 규칙
     color: rgb(3,3,3);        ★ 중첩 규칙 뒤의 선언
   }

   브라우저가 담은 것 (cssRules 재귀 덤프)
   ┌ CSSStyleRule  ".a"   { color: rgb(1,1,1); & {…} color: rgb(3,3,3); }
   │   ├ CSSStyleRule           "&"   { color: rgb(2,2,2); }
   │   └ CSSNestedDeclarations        { color: rgb(3,3,3); }   ★ 별도 규칙으로 감싸진다
   └
```

실측 (Chrome 151 headless, `.a` 의 계산된 `color`).

| 소스 | 이긴 값 | 왜 |
|---|---|---|
| `.a { color:1; & { color:2 } color:3 }` | **3** | 소스 순서 그대로 — 마지막이 이긴다 |
| `.a { color:1; & { color:2 } }` | **2** | `&` 규칙이 마지막 |
| `.a { & { color:2 } color:3 }` | **3** | 선언이 마지막 |
| `.a { color:3; @media (…) { color:2 } }` | **2** | `@media` 가 마지막 |
| `.a { @media (…) { color:2 } color:3 }` | **3** | 선언이 마지막 |
| `.a { color:1; @media (…) { color:2 } color:3 }` | **3** | 〃 |

그림 해설:

- **Chrome 151 에서는 소스 순서가 그대로 지켜진다.** 중첩 규칙 뒤의 선언은 **`CSSNestedDeclarations` 라는 규칙으로 감싸져 그 자리에 남는다.**
- 그래서 `&` 규칙과 선언의 명시도가 동점일 때 **나중에 쓴 쪽이 이긴다.**\
  (`&` 규칙은 `.a { & { } }` = (0,1,0) 이고 `.a` 자신도 (0,1,0) 이라 동점이다.)
- 명세가 이 자리에 **주의를 붙여 놓았다** — 「선언과 중첩 규칙을 자유롭게 섞을 수 있지만 읽기 어렵고 혼란스럽다. **뒤쪽 속성들이 소스에 보이지 않는 중첩 선언 규칙으로 자동으로 감싸지기 때문**이다. 가독성을 위해 속성을 중첩 규칙보다 앞에 모두 쓰기를 권한다.」
- ★ 그리고 이유가 하나 더 적혀 있다 — 「**이쪽이 오래된 사용자 에이전트에서도 조금 더 낫게 동작한다. 파싱·오류 복구의 특성 때문에 중첩 규칙 뒤에 오는 속성은 건너뛰어질 수 있기 때문**이다.」\
  곧 **이 문서의 실측(Chrome 151)이 모든 구현의 답은 아니다.** 순서에 기대지 말고 선언을 앞으로 모으는 것이 안전하다.

비용 — 없다. **읽기 비용만 는다.**

### (6) `@media` 를 중첩한다

**언제 쓰나** — 한 컴포넌트의 반응형 분기를 그 컴포넌트 옆에 두고 싶을 때.

```text
   .card {                            cssRules
     color: blue;                      └ CSSStyleRule ".card"
     @media (min-width: 40em) {            ├ CSSNestedDeclarations { color: blue }  (필요 시)
       color: green;                       └ CSSMediaRule "@media (min-width: 40em)"
     }                                          └ CSSNestedDeclarations { color: green }
   }
```

- 중첩된 `@media` 안의 **선언들도 `CSSNestedDeclarations` 로 감싸진다.** 실측 덤프에서 그대로 나왔다.
- **명시도는 안 바뀐다** — 실측에서 `.a { @media (…) { .c { } } }` 가 (0,2,0) 으로 `.a .c` 와 같았다.
- 순서는 (5)절과 같은 규칙을 따른다 — **`@media` 블록이 놓인 자리가 곧 그 선언들의 자리**다.

비용 — 없다.

## 문법 — 형태와 규칙

CSS 는 문법 표면이 단순하므로 이 절은 「**형태 — 어디서 헷갈리나**」로 읽는다(§2-1 규칙 9).

### 형태

```css
.card {
  padding: 8px;                      /* 선언은 전부 앞에 모은다 */

  & .title   { font-weight: 700; }   /* 자손 */
  &.active   { border-color: blue; } /* 같은 요소 (공백 없음!) */
  &:hover    { background: #eee; }   /* 상태 */
  &::before  { content: ""; }        /* 의사 요소 */
  > .body    { margin: 0; }          /* & 생략 + 조합자 */
  .theme-dark & { background: #111; }/* 부모를 자손 자리로 */

  @media (min-width: 40em) { padding: 16px; }
}
```

### 금지 사례 — 던지면 안쪽 규칙이 사라지는 것

```css
.a { &div      { } }   /* 붙여 쓰기 — 무효 */
.a { &-suffix  { } }   /* 문자열 이어붙이기 — CSS 에는 없다 */
```

- 둘 다 **안쪽 규칙만 사라지고 바깥 `.a` 는 남는다.** 그래서 「시트가 멀쩡해 보이는」 오타가 된다.
- BEM 이어붙이기(`&__title`·`&--active`)를 쓰던 습관이 그대로 넘어오면 여기서 막힌다.

### 세기를 안 올리고 중첩하기

```css
/* 둘 다 (0, 1, 0) — 실측했다 */
:where(.a, #b) { .c { color: green; } }      /* 부모 목록을 눌러 둔다 */
.a, #b { :where(&) .c { color: green; } }    /* & 를 눌러 둔다 */
```

| 무엇을 썼나 | (A, B, C) |
|---|---|
| `.a, #b { & .c { } }`(대조) | (1, 1, 0) |
| `:where(.a, #b) { .c { } }` | **(0, 1, 0)** |
| `.a, #b { :where(&) .c { } }` | **(0, 1, 0)** |

- **두 자리 중 어디를 눌러도 결과가 같다** — 부모 쪽을 누르든 `&` 쪽을 누르든 `(0, 1, 0)` 이다.
- 명세도 같은 기법을 예로 들어 놓았다 — `article { color: blue; :where(&) { color: red } }` 에서 `:where(&)` 가 명시도를 0 으로 눌러 **뒤에 썼는데도 진다.** 그 예 자체는 **재현하지 않았다**(위 두 줄만 쟀다).

## 어디서 틀리나

이 주제의 값어치는 전부 여기 있다. 다섯 다 **에러 없이 조용히 어긋난다.**

### 1. `&` 를 문자열 치환으로 읽는다

```css
.a, #b { & .c { color: green; } }
```

- **`".a .c, #b .c"` 가 아니다.** `:is(.a, #b) .c` 다.
- 그래서 **`.a` 안의 `.c` 에 걸릴 때도 명시도가 `(1, 1, 0)`** 이고, `.a .c { }`(0,2,0)를 **이긴다.**
- 실측에서 명세의 예를 그대로 돌려 결과가 정반대인 것을 확인했다((2)절).
- ★ 전처리기(Sass 등)는 실제로 **문자열로 이어 붙인다.** 같은 소스가 도구에 따라 다른 명시도를 낳는다.

### 2. 부모 목록에 ID 하나를 편의로 끼워 넣는다

```css
html, #app {
  .card { padding: 8px; }    /* (1, 1, 0) — 이 아래 전부가 A 자리로 올라간다 */
}
```

- `#app` 은 **매치되지 않아도** A 자리를 올린다.
- 그리고 **중첩을 더 쌓아도 계속 따라온다** — 실측에서 2단 중첩이 (1, 2, 0) 이었다.
- 세기를 안 올리려면 `:where(html, #app)` 으로 감싸거나 부모 목록을 쪼갠다.

### 3. `&.x` 와 `& .x` 를 헷갈린다

```css
.card { &.active { } }   /* 같은 요소가 .active 이기도 할 때 */
.card { & .active { } }  /* .card 의 자손 중 .active */
```

- **공백 하나 차이**이고 둘 다 유효하다 — 그래서 **에러가 안 난다.**
- ★ 실측에서 **명시도도 같았다** — 부모가 `.card` 하나일 때 `&.active`·`& .active`·`.card.active`·`.card .active` 가 **넷 다 (0, 2, 0)** 이었다.
- **명시도로는 안 갈리고 고르는 요소만 달라진다.** 진단은 `querySelectorAll` 로 한다.
- 「왜 안 먹지」의 원인이 공백인 경우가 잦다.

### 4. BEM 이어붙이기를 가져온다

```css
.card { &__title { } }   /* 안쪽 규칙이 사라진다 */
```

- **CSS 중첩은 문자열을 이어 붙이지 않는다.** `&-suffix` 형태가 전부 무효다.
- 그런데 **바깥 규칙은 살아남으므로** 시트는 정상으로 보인다.
- 실측에서 `.a { &-suffix { } }` 의 바깥 `.a` 는 `cssRules` 에 남았고 자식 규칙만 0개였다.

### 5. 중첩 규칙 뒤에 선언을 더 쓴다

```css
.card {
  color: blue;
  & .title { font-weight: 700; }
  padding: 8px;              /* ★ 여기 */
}
```

- Chrome 151 에서는 **소스 순서대로 동작한다**(자동으로 `CSSNestedDeclarations` 로 감싸진다).
- 그런데 명세가 **오래된 구현에서는 건너뛰어질 수 있다**고 적어 놓았다.
- **선언은 전부 앞으로 모은다.** 명세의 권고이기도 하고, 읽기도 그쪽이 낫다.

## 구현 세부사항 대 언어 보장

| 항목 | 누가 보장하나 | 근거 |
|---|---|---|
| `&` 의 명시도 = 부모 목록 중 가장 센 것 | **명세** | css-nesting-1 §4 — 「identical to the behavior of `:is()`」 |
| 부모 목록이 없으면 `&` 가 **0** | **명세** | 같은 절 — 「or zero if no such selector list exists」 |
| 손 펼침과 결과가 다를 수 있다 | **명세** | 같은 절이 예를 들어 명시한다 |
| `&` 없는 중첩 규칙에 암묵의 `&` 가 붙는다 | **명세** | §3.1 |
| 상대 선택자의 명시도에 암묵의 `&` 가 포함된다 | **명세** | §3.1 — `.foo { > .bar }` 와 `.foo { & > .bar }` 가 같다 |
| `&div` 가 무효 | **명세** | §7 Changes — 「Switched `&div` back to being invalid」 |
| 무효한 중첩 규칙이 부모를 안 죽인다 | **명세** | §3.1 |
| 중첩 규칙 뒤 선언이 중첩 선언 규칙으로 감싸진다 | **명세** | §3.4 · §5 |
| 직렬화 시 `> .foo` → `& > .foo` | **명세** | §6 CSSOM |
| **중첩 규칙 뒤 선언의 실제 순서** | ★ **구현에 달린 부분이 있다** | 명세 주 — 「오래된 UA 에서는 파싱·오류 복구 특성상 **건너뛰어질 수 있다**」. Chrome 151 실측은 소스 순서 그대로였다 |
| `&` 를 최상위에 쓰면 `:scope` 처럼 매치되는 것 | **관찰** | Chrome 151 에서 둘 다 같은 요소를 골랐다. 단 **명시도는 달랐다**((0,0,1) 대 (0,1,1)) |
| `selectorText` 의 정확한 형태 | **관찰** | Chrome 151 이 보여 준 것이다 |

**Baseline** — 중첩은 **widely available**(newly 2023-12-11 → widely 2026-06-11).\
2026-09-23 에 `api.webstatus.dev/v1/features/nesting` 을 직접 조회한 값이다. 엔진별 최초 지원은 Firefox 117(2023-08-29) · Chrome 120(2023-12-05) · Edge 120(2023-12-07) · Safari 17.2(2023-12-11).

★ **여기서 주의할 것 하나** — 중첩은 **표준이 도중에 바뀐 문법**이다(`&div` 허용 → 금지, 식별자 시작 금지 → 허용, `@nest` → 중첩 선언 규칙). Baseline 날짜는 **「어느 판을 구현했나」를 말해 주지 않는다.** 2023년 말에 나온 버전들은 초기 판을 구현했을 수 있다. **이 머신에서 확인한 것은 Chrome 151 하나뿐이다.**

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 컴포넌트 하나의 상태·자식 규칙 모으기 | `.card { &:hover { } & .title { } }` | 파일 여기저기 흩어 쓰기 |
| 부모 목록에 ID 가 섞여야 할 때 | `:where(.a, #b) { … }` | `.a, #b { … }` — 아래 전부가 A 자리로 |
| 반응형 분기 | `@media` 를 컴포넌트 안에 중첩 | 파일 끝에 미디어 쿼리 모으기 |
| 테마 조건 | `.theme-dark & { }` | 부모 규칙을 따로 하나 더 만들기 |
| BEM 이름 조립 | 클래스를 그냥 다 쓴다 | `&__title` — **무효다** |
| 선언과 중첩 규칙 순서 | 선언을 **전부 앞에** | 중첩 뒤에 선언 더 쓰기 |
| 깊이 | 두 단 정도까지 | 세 단 이상 — 명시도가 눈에 안 보이게 쌓인다 |

판단 규칙 두 줄.

- **중첩은 파일을 짧게 쓰는 문법이 아니라 선택자를 조립하는 문법이다.** 조립 결과를 모르면 명시도가 조용히 어긋난다.
- **부모 줄이 곧 아래 전부의 명시도 바닥이다.** 부모를 쓸 때 그 아래 전부를 함께 결정한다는 것을 알고 쓴다.

## 핵심 문장

- `&` 는 「**부모 선택자 목록 전체**」이고, 명시도는 **그 목록 중 가장 센 것**이다 — `:is()` 와 **같은 조항**이다.
- 그래서 **`.a, #b { & .c { } }` 는 `(1, 1, 0)`** 이고, 손으로 펼친 `.a .c, #b .c` 와 **결과가 다르다.** 명세가 이 차이를 직접 예로 든다.
- **`&` 를 생략하면 브라우저가 끼워 넣는다** — `selectorText` 가 `& .c`·`& div`·`& > .q` 로 돌아온다.
- **`&.x`(공백 없음)와 `& .x`(공백)는 다르다.** 둘 다 유효해서 에러가 안 난다.
- **`&-suffix` 는 없다** — CSS 중첩은 문자열을 이어 붙이지 않는다. BEM 이어붙이기가 여기서 막힌다.
- **무효한 중첩 규칙은 부모를 죽이지 않는다** — 안쪽만 사라지고 바깥은 살아남아 시트가 정상으로 보인다.
- 중첩 규칙 **뒤에 쓴 선언**은 `CSSNestedDeclarations` 로 감싸져 **그 자리에 남는다.** Chrome 151 실측은 소스 순서 그대로였지만, **명세는 오래된 구현에서 건너뛸 수 있다고 경고한다** — 선언은 앞으로 모은다.
- **최상위의 `&` 는 0 이다.** `:scope` 와 같은 것을 고르지만 명시도가 다르다.

## 용어 풀이

- **중첩(nesting)** — 스타일 규칙 안에 스타일 규칙을 넣는 문법.
- **중첩 선택자(nesting selector)** — `&`. 부모 규칙의 선택자 목록을 가리킨다.
- **부모 선택자 목록(parent selector list)** — 바깥 규칙의 쉼표 목록. `&` 가 뜻하는 것.
- **상대 선택자(relative selector)** — 조합자로 시작할 수 있는 선택자. `> .q`·`+ .bar`.
- **절대화(absolutize)** — 직렬화할 때 암묵의 `&` 를 실제로 끼워 넣는 것. `> .foo` → `& > .foo`.
- **중첩 선언 규칙(`CSSNestedDeclarations`)** — 중첩 규칙 뒤에 오는 선언들을 자동으로 감싸는 보이지 않는 규칙.
- **명시도(specificity)** — 선택자의 세기. (A, B, C) 세 자리. 정본은 02번.
- **`:is()`** — 인자 목록 중 하나라도 맞으면 매치하고, 명시도는 **가장 센 인자**를 따르는 의사 클래스.
- **`:where()`** — 매칭은 `:is()` 와 같고 명시도 기여만 0 인 의사 클래스.
- **`:scope`** — 스코프의 뿌리를 가리키는 의사 클래스. 시트에서는 문서의 루트 요소.
- **전처리기(preprocessor)** — Sass·Less 처럼 CSS 를 만들어 내는 도구. 중첩을 **문자열 이어 붙이기**로 구현한다.
- **Baseline** — 주요 브라우저 지원 정도 지표. `widely` 는 주요 엔진 전부에서 30개월 이상.

## 더 들어가면

- **전처리기와 CSS 중첩은 같은 문법이 아니다.** Sass 는 선택자를 **문자열로 이어 붙이므로** `.a, #b { & .c { } }` 가 `.a .c, #b .c` 가 되고, 명시도도 그쪽을 따른다.\
  같은 소스를 「Sass 로 빌드한 판」과 「브라우저 중첩으로 넘긴 판」이 **다른 결과를 낸다.** 마이그레이션에서 조용히 터질 자리다.
- **`@scope` 의 `<scope-start>` 는 부모 규칙 노릇을 하지 않는다.** 명세 변경 이력에 그렇게 적혀 있다. 이 문서에서는 **확인하지 않았다**(`@scope` 는 [목록의 **06번 주제**](../06-scope/)).
- **`&` 를 `:has()` 안에 넣는 것**은 Chrome 151 에서 담겼다(`.card:has(&)` 의 `selectorText` 가 그대로 나왔다). **매치 동작은 확인하지 않았다.**
- **중첩은 표준이 도중에 세 번 바뀌었다** — `&div` 허용 → 금지 · 식별자로 시작하는 중첩 금지 → 허용 · `@nest` 규칙 → 중첩 선언 규칙.\
  그래서 **「2023년에 지원 시작」이라는 Baseline 날짜만으로 「내가 쓰는 문법이 거기서 돈다」고 볼 수 없다.** 이 문서가 확인한 것은 Chrome 151 하나다.
- **깊이 제한은 명세에 없다.** 다만 (2)절의 2단 실측이 보여 주듯 **명시도가 한 번 올라가면 아래로 계속 따라간다** — 깊이가 는다는 것은 「이 규칙의 세기를 알려면 위로 몇 줄을 거슬러야 하나」가 는다는 뜻이다.
