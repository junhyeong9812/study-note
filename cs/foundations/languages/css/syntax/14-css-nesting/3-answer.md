# css/syntax/14 — 중첩(nesting): `&` 의 의미와 중첩 명시도 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 **모든 `(A, B, C)` 값 · 모든 `selectorText` · 모든 순서 판정은 Google Chrome 151.0.7922.173 headless 에서 실제로 돌려 확인한 것**이다.\
> 근거를 두 층으로 나눠 뽑았다 — `cssRules` 를 재귀로 훑어 **브라우저가 무엇으로 파싱했나**, `getComputedStyle` 로 **무엇이 이겼나**.\
> **명시도 값은 전부 두 번째 층으로만** 확인했다(동점 경쟁자 · 한 칸 낮은 경쟁자 두 판 — 방법은 [02번 주제](../02-specificity/2-summary.md)).\
> 규칙은 [CSS Nesting Module Level 1](https://drafts.csswg.org/css-nesting-1/) 로 접지했다. **엔진은 Chrome 하나다.**

## 정답

### 1. 이 글자는 무슨 색인가

**실행 결과** (Chrome 151 headless, `getComputedStyle(c).color`)

```text
중첩으로 쓴 판    #a, b { & c { blue } } / .foo c { red }   ->  rgb(0, 0, 255)   파랑
손으로 펼친 판    #a c, b c { blue }     / .foo c { red }   ->  rgb(255, 0, 0)   빨강
```

**무슨 색인가**

- **파랑(blue)** 이다.

```text
  #a, b { & c { color: blue } }

  & = max( #a , b ) = max( (1,0,0) , (0,0,1) ) = (1, 0, 0)
  & c              = (1,0,0) + (0,0,1)         = (1, 0, 1)
  .foo c                                        = (0, 1, 1)

  (1,0,1) > (0,1,1)  ->  파랑이 이긴다
```

**`#a` 가 없는데 영향을 주는가**

- **준다.** 명시도는 **매칭 결과가 아니라 선택자의 모양**만 본다.
- `&` 가 `:is(#a, b)` 라는 **한 덩어리**로 계산되므로, 목록 안에 `#a` 가 있다는 사실만으로 A 자리가 1 이 된다.

**손으로 펼치면**

- **빨강(red)** 이 된다.

```text
  #a c, b c { color: blue }

  #a c  = (1,0,1)   <- <c> 의 조상에 #a 가 없어서 매치 실패
  b   c = (0,0,2)   <- 이것만 매치된다
  .foo c = (0,1,1)

  (0,0,2) < (0,1,1)  ->  빨강이 이긴다
```

**두 판이 갈리는 이유**

- **중첩에서는 매치에 실패한 `#a` 도 명시도에 남고, 손으로 펼치면 각 선택자가 따로 계산돼 `#a` 쪽은 아예 후보에서 빠지기 때문이다.**
- 명세가 이 예를 직접 실어 「**수동으로 펼쳤을 때 얻는 결과와 눈에 띄게 다르다**」고 적어 놓았다.

### 2. `&` 는 무엇으로 치환되는가

**무엇을 뜻하는가**

- **선택자 목록이다.** 문자열이 아니다.
- `.a, #b` 아래의 `&` 는 「`.a` 이거나 `#b` 인 것」이고, 계산상 **`:is(.a, #b)` 와 똑같이 취급된다**.

**명시도를 정하는 규칙**

- **`:is()` 와 같은 조항**이다. 명세 문구가 「부모 스타일 규칙의 선택자 목록 안의 복잡 선택자들 중 **가장 큰 명시도와 같다**(`:is()` 의 동작과 동일)」이다.
- 정본은 [02번 주제](../02-specificity/2-summary.md)의 「안에 선택자를 담는 의사 클래스」 절이다.

**최상위에서 쓰면**

- **0 이다.** 명세가 「그런 선택자 목록이 **없으면 0**」이라고 못 박는다.
- 실측: `& p { }` 의 명시도가 **(0, 0, 1)** 로, `p` 하나와 같았다.

**전처리기의 `&` 와 같은가**

- **아니다.** Sass 같은 전처리기는 선택자를 **문자열로 이어 붙인다.**
- 그래서 같은 소스가 **빌드하면 `.a .c, #b .c`(각자 제 명시도), 브라우저에 그냥 넘기면 `:is(.a, #b) .c`(1,1,0)** 이 된다.
- 마이그레이션에서 조용히 터지는 자리다 — 결과 화면이 달라지는데 **에러는 없다.**

### 3. 네 줄의 명시도를 세어 보라

**실행 결과**

```text
.a, #b { & .c { } }             ->  (1, 1, 0)
.a .c  { }                      ->  (0, 2, 0)
.a, #b { && { } }               ->  (2, 0, 0)
.a, #b { & .c { & .d { } } }    ->  (1, 2, 0)
```

**네 줄의 `(A, B, C)`**

```text
  ① .a, #b { & .c { } }
       & = (1,0,0)   + .c (0,1,0)   =  (1, 1, 0)

  ② .a .c
       .a (0,1,0) + .c (0,1,0)      =  (0, 2, 0)

  ③ .a, #b { && { } }
       & (1,0,0) + & (1,0,0)        =  (2, 0, 0)

  ④ .a, #b { & .c { & .d { } } }
       바깥 & .c = (1,1,0)  <- 이것이 안쪽 & 의 부모 목록이 된다
       안쪽 &   = (1,1,0)
       & .d     = (1,1,0) + (0,1,0) =  (1, 2, 0)
```

**첫째와 둘째가 겨루면**

- **첫째가 이긴다.** `(1,1,0) > (0,2,0)` — A 자리에서 갈린다.
- 「중첩은 그냥 짧게 쓴 것」이라는 모델이 여기서 깨진다.

**`&&` 는 무엇과 같은가**

- **`:is(부모목록):is(부모목록)`** 이다.
- 실측에서 `:is(.a,#b):is(.a,#b)` 가 똑같이 **(2, 0, 0)** 이었다.
- 명세도 예를 들어 놓았다 — `.foo { && { } }` 는 `.foo.foo` 와 같다.
- 명시도만 올리고 매칭은 안 바꾸는 **의도적 승급** 기법이기도 하다.

**한 겹 더 쌓으면 따라오는가**

- **따라온다.** 2단이 (1, 2, 0) 이고, 평평하게 쓴 `.a .c .d` 는 (0, 3, 0) 이다.
- 손으로 펼친 `:is(:is(.a, #b) .c) .d` 도 **(1, 2, 0)** 으로 같았다 — 중첩이 쌓일 때 `:is()` 도 겹겹이 쌓인다.
- 곧 **부모 줄의 ID 하나가 그 블록 전체의 명시도 바닥을 정한다.**

### 4. `&` 를 빼면 무엇이 되는가

**실행 결과** (`cssRules` 재귀 덤프의 `selectorText`)

```text
.card { .title  { } }   ->  안쪽 selectorText = "& .title"
.card { > .body { } }   ->  안쪽 selectorText = "& > .body"
.card { div     { } }   ->  안쪽 selectorText = "& div"
.card { .x &    { } }   ->  안쪽 selectorText = ".x &"
```

**네 줄의 `selectorText`**

- 앞의 셋은 **브라우저가 `&` 를 끼워 넣어 돌려준다.**
- 넷째는 `&` 가 이미 있으므로 **그대로**다.
- 명세의 CSSOM 조항이 이것을 정한다 — 「중첩 스타일 규칙에서 상대 선택자를 직렬화할 때는 **암묵의 중첩 선택자를 끼워 절대화해야 한다.**」

**생략한 것과 앞에 쓴 것의 명시도**

- **같다.** 실측에서 `.a, #b { .c { } }` 와 `.a, #b { & .c { } }` 가 **둘 다 (1, 1, 0)** 이었다.
- 명세도 「상대 선택자를 쓴 중첩 규칙은 **암묵의 중첩 선택자의 명시도를 포함한다**」고 적는다 — `.foo { > .bar }` 와 `.foo { & > .bar }` 가 같은 명시도라는 예까지 들어 놓았다.

**넷째 줄이 가리키는 것**

- **`.x` 안에 있는 `.card`** 다. 부모를 **자손 자리로 내린다.**
- 테마·컨테이너 조건을 컴포넌트 안에서 쓰는 형태다.

```css
.card { .theme-dark & { background: #111; } }   /* .theme-dark :is(.card) */
```

- 실측: `.c, #b { .a & { } }` = **(1, 1, 0)** — `&` 를 뒤에 써도 부모 목록 전체가 따라온다.

**암묵의 `&` 가 명시도에 포함되는가**

- **포함된다.** 위의 「같다」가 그 증거다.

### 5. 공백 하나가 가르는 것

**두 줄이 고르는 것**

```text
  .card { &.active  { } }   ->  :is(.card).active   같은 요소가 .active 이기도 할 때
  .card { & .active { } }   ->  :is(.card) .active  .card 의 자손 중 .active
```

**둘 다 유효한가**

- **유효하다.** 실측에서 `.a { &.b { } }` 가 정상으로 담겼고 `selectorText` 는 `&.b` 였다.

**브라우저가 알려 주는가**

- **안 알려 준다.** 둘 다 문법적으로 맞는 선택자라 **에러도 경고도 없다.**
- 그냥 **다른 요소를 고를 뿐**이고, 그 요소가 문서에 없으면 「안 먹는다」로 보인다.
- 중첩에서 가장 자주 나는 오타이고, **`selectorText` 를 눈으로 읽어야 잡힌다.**

**명시도는 같은가**

**실행 결과** (부모가 `.card` 하나일 때. 각자 자기가 고르는 요소에서 쟀다)

```text
.card { &.active  { } }   ->  (0, 2, 0)    고른 것: div
.card { & .active { } }   ->  (0, 2, 0)    고른 것: span
.card.active   (평평)     ->  (0, 2, 0)
.card .active  (평평)     ->  (0, 2, 0)
```

- **넷 다 (0, 2, 0) 으로 같다.** 조합자는 어느 자리에도 0 을 보태므로([02번 주제](../02-specificity/2-summary.md)) 붙여 쓰든 띄우든 세 자리가 같아진다.
- ★ **그래서 더 위험하다.** 명시도로는 갈리지 않고 **고르는 요소만 조용히 달라진다.**
- 진단은 명시도가 아니라 **`querySelectorAll` 로 무엇이 잡히는지**로 한다.

### 6. 이 셋 중 살아남는 것은

**실행 결과**

```text
.a { &div     { } }   ->  안쪽 DROP.  바깥 ".a" 는 담김 (자식 규칙 0개)
.a { &-suffix { } }   ->  안쪽 DROP.  바깥 ".a" 는 담김 (자식 규칙 0개)
.a { &.b      { } }   ->  안쪽 담김.  selectorText = "&.b"
```

**몇 줄이 담기는가**

- **1줄 — 마지막 줄뿐이다.**

**바깥 `.a` 는 어떻게 되는가**

- **살아남는다.** 명세 조항이 그대로다 — 「무효한 중첩 스타일 규칙은 **그 내용과 함께 무시되지만, 부모 규칙을 무효화하지는 않는다.**」
- ★ **그래서 오타가 더 조용해진다.** 시트도 규칙도 멀쩡해 보이는데 안쪽 것만 없다.

**`&div` 가 처음부터 무효였는가**

- **아니다. 한 번 뒤집혔다.**
- 명세의 변경 이력에 적혀 있다 — 「`&div` 를 **다시 무효로 되돌렸다.** 이제 Syntax 가 무한 예측(infinite lookahead)을 하므로 허용할 필요가 없어졌고, 그렇게 하면 **전처리기와의 충돌도 피할 수 있다.**」
- 같은 변화의 반대쪽이 「**식별자로 시작하는 중첩 규칙 허용**」이다 — 실측에서 `.a { div { } }` 가 `& div` 로 담겼다.

**BEM 을 그대로 옮길 수 있는가**

- **없다.** `&__title`·`&--active` 같은 **문자열 이어붙이기는 CSS 중첩에 없다.**
- 명세가 그 사실을 적어 놓았다 — 일부 전처리 도구는 선택자를 문자열로 이어 붙여 BEM 같은 계층 이름 패턴을 만들지만, CSS 중첩은 그렇게 하지 않는다.
- 옮기려면 클래스 이름을 **그대로 다 쓴다.**

### 7. 어느 선언이 이기는가

**실행 결과**

```text
.a { color:1; & { color:2 } color:3 }              ->  rgb(3, 3, 3)
.b { color:1; & { color:2 } }                      ->  rgb(2, 2, 2)
.c { @media (min-width:1px) { color:2 } color:3 }  ->  rgb(3, 3, 3)
```

(대조로 더 돌린 것)

```text
.a { color:3; @media (…) { color:2 } }             ->  rgb(2, 2, 2)
.a { color:1; @media (…) { color:2 } color:3 }     ->  rgb(3, 3, 3)
```

**세 요소의 계산된 `color`**

- `.a` → **`rgb(3,3,3)`** · `.b` → **`rgb(2,2,2)`** · `.c` → **`rgb(3,3,3)`**.
- 한 줄로 요약하면 **소스 순서 그대로, 마지막에 쓴 것이 이긴다.**

**`cssRules` 에서 어떤 규칙으로 나타나는가**

```text
  CSSStyleRule ".a"
    ├ CSSStyleRule        "&"   { color: rgb(2,2,2) }
    └ CSSNestedDeclarations     { color: rgb(3,3,3) }   ★ 소스에 없는 규칙
```

- **`CSSNestedDeclarations`** 로 감싸진다. 소스에는 안 보이는 규칙이다.
- 중첩된 `@media` 안의 선언들도 같은 방식으로 감싸진다.

**동점일 때 무엇으로 승부가 나는가**

- **등장 순서**다 — 캐스케이드의 마지막 단계([01번 주제](../01-cascade-and-priority/2-summary.md)).
- `.a { & { } }` 의 `&` 는 (0,1,0) 이고 `.a` 자신도 (0,1,0) 이라 **동점**이므로, 순서가 결정한다.

**명세가 붙인 주의**

- 두 가지다.
  1. 「선언과 중첩 규칙을 자유롭게 섞을 수 있지만 **읽기 어렵고 혼란스럽다** — 뒤쪽 속성들이 **소스 텍스트에 나타나지 않는** 중첩 선언 규칙으로 자동으로 감싸지기 때문이다. 가독성을 위해 속성을 중첩 규칙보다 **앞에 모두 쓰기를 권한다.**」
  2. 「이쪽이 **오래된 사용자 에이전트에서도 조금 더 낫게 동작한다** — 파싱·오류 복구의 특성 때문에 **중첩 규칙 뒤에 오는 속성은 건너뛰어질 수 있다.**」
- ★ 그래서 이 문서의 실측(Chrome 151)이 **모든 구현의 답은 아니다.** 순서에 기대지 말고 선언을 앞으로 모은다.

### 8. `@media` 를 중첩하면

**어떻게 담기는가**

```text
  CSSStyleRule ".a"
    └ CSSMediaRule "@media (min-width: 1px)"
         └ CSSNestedDeclarations { color: rgb(2,2,2) }
```

- 중첩된 `@media` 안의 선언들은 **`CSSNestedDeclarations` 로 감싸져** 미디어 규칙 안에 들어간다.

**명시도가 바뀌는가**

- **안 바뀐다.** 실측에서 `.a { @media (…) { .c { } } }` 가 **(0, 2, 0)** 으로, `.a .c` 와 같았다.
- `@media` 는 **조건일 뿐 선택자가 아니다.**

**위치가 순서에 영향을 주는가**

- **준다.** `@media` 블록이 놓인 자리가 곧 그 선언들의 자리다.
  - `.a { color:3; @media (…) { color:2 } }` → **2** 가 이긴다.
  - `.a { @media (…) { color:2 } color:3 }` → **3** 이 이긴다.

**`@layer` 와 중첩은 각각 무엇을 하는가**

| | 무엇을 하나 | 캐스케이드 |
|---|---|---|
| 중첩(`&`) | **명시도를 올린다**(부모 목록 중 가장 센 것) | 5단계에서 겨룬다 |
| `@layer` | 명시도를 **안 건드린다.** 레이어 순서로 먼저 갈라 버린다 | **4단계** — 명시도를 보기 전에 끝난다 |

- 그래서 **중첩이 올려 놓은 세기는 레이어 앞에서 무의미해진다.** 정본은 [01번 주제](../01-cascade-and-priority/2-summary.md)와 [목록의 **05번 주제**](../05-cascade-layers/).

### 9. 세기를 안 올리고 중첩하려면

**실행 결과**

```text
.a, #b { & .c { } }            ->  (1, 1, 0)
:where(.a, #b) { .c { } }      ->  (0, 1, 0)
.a, #b { :where(&) .c { } }    ->  (0, 1, 0)
```

**세 줄의 `(A, B, C)`**

- 위 그대로다. 첫 줄만 A 자리가 1 이다.

**뒤 두 줄이 같은 값을 내는 이유**

```text
  누르는 자리가 다를 뿐 결과가 같다

  :where(.a, #b) { .c { } }        부모 목록 자체를 0 으로 만든다
      -> & = max(:where(...)) = (0,0,0)

  .a, #b { :where(&) .c { } }      & 를 0 으로 감싼다
      -> :where( :is(.a,#b) ) = (0,0,0)

  둘 다 남는 것은 .c (0,1,0) 뿐이다
```

**레거시 ID 가 섞였을 때 무엇부터 하는가**

- **부모 줄을 먼저 본다.** 그 한 줄이 아래 블록 전체의 명시도 바닥이다.
- 고치는 순서는 ① 부모 목록을 쪼갠다 → ② 못 쪼개면 `:where()` 로 감싼다 → ③ 그래도 안 되면 `@layer` 로 아예 다른 층에 둔다.

**`:where()` 는 매칭도 없애는가**

- **아니다. 세기만 0 으로 만든다.** 매칭은 `:is()` 와 똑같이 한다.
- 「이 요소를 고른다」와 「세게 고른다」를 **분리하는 유일한 문법**이다([02번 주제](../02-specificity/2-summary.md)).

### 10. 최상위의 `&`

**실행 결과**

```text
& p { color: … }
  cssRules 담김 = true      selectorText = "& p"
  querySelectorAll("& p").length = 3
  명시도 = (0, 0, 1)

:scope p { color: … }
  cssRules 담김 = true
  명시도 = (0, 1, 1)

p            명시도 = (0, 0, 1)   (비교용)
```

**규칙이 담기는가**

- **담긴다.** `selectorText` 도 `& p` 그대로다.

**무엇을 고르는가**

- 실측에서 문서의 `p` **세 개를 전부** 골랐고, 색도 적용됐다.
- `:scope p` 를 같은 문서에 걸었을 때도 결과가 같았다 — **고르는 것은 같다.**

**`:scope p` 와 같은가**

| | 고르는 것 | 명시도 |
|---|---|---|
| `& p` | 같다 | **(0, 0, 1)** |
| `:scope p` | 같다 | **(0, 1, 1)** |

- ★ **고르는 것은 같고 명시도가 다르다.** `:scope` 는 의사 클래스라 B 자리에 1 을 보태고, 최상위의 `&` 는 **0** 이다.
- 「`&` 는 최상위에서 `:scope` 다」로 외우면 **명시도에서 틀린다.**

**명세는 뭐라고 정하는가**

- 「**그런 선택자 목록이 없으면 0**(or zero if no such selector list exists)」이다.
- 부모가 없으니 「가장 센 것」을 고를 대상 자체가 없고, 그때의 값을 0 으로 정해 둔 것이다.

### 11. 다른 주제와 잇기

**`&` 와 `:has()` 의 명시도 규칙의 관계**

- **같은 조항에서 나온다.** 명세가 `:is()`·`:not()`·`:has()`·`&` 를 전부 「**인자(또는 부모 목록) 중 가장 센 것**」으로 처리한다.
- 차이는 **무엇을 목록으로 삼느냐**뿐이다 — `:has()` 는 괄호 안, `&` 는 부모 규칙의 선택자 목록.
- 그래서 둘 다 「**목록에 강한 것 하나를 편의로 끼워 넣으면 전체가 세진다**」는 같은 사고를 낳는다. 정본은 [02번 주제](../02-specificity/2-summary.md), `:has()` 쪽 실측은 [12번 주제](../12-has-relational-selector/2-summary.md).

**`&::before` 는 어떻게 적용되나**

- 의사 요소 규칙이 **그대로** 적용된다 — `&::before` 는 복합 선택자의 맨 끝이라 유효하고, `&::before .x` 같은 것은 무효다.
- 명시도도 그대로 더해진다 — `&`(부모 목록 중 가장 센 것) + 의사 요소 C 1.
- 정본은 [13번 주제](../13-pseudo-elements-and-generated-content/2-summary.md).

**깊이를 얕게 유지하라는 조언의 근거**

- 명세에 **깊이 제한은 없다.** 근거는 명시도 쪽이다.
- 3번 실측이 보여 준 대로 **한 번 올라간 A 자리는 아래로 계속 따라간다**(2단이 (1,2,0)).
- 곧 **깊이가 는다는 것은 「이 규칙의 세기를 알려면 위로 몇 줄을 거슬러야 하나」가 는다는 뜻**이다. 읽는 비용이 정확히 거기서 는다.

**Baseline 날짜만 보고 판단해도 되는가**

- **안 된다.** 중첩은 **표준이 도중에 바뀐 문법**이다.
- 명세 변경 이력에 남은 것만도 셋이다 — `&div` 허용 → 금지 · 식별자로 시작하는 중첩 금지 → 허용 · `@nest` 규칙 → 중첩 선언 규칙.
- Baseline(newly 2023-12-11 → widely 2026-06-11)은 「**언제부터 이름이 지원됐나**」를 말할 뿐 「**어느 판을 구현했나**」를 말하지 않는다.
- 2023년 말에 나온 버전들은 **초기 판**을 구현했을 수 있다. **이 문서가 확인한 것은 Chrome 151 하나뿐이다.**
