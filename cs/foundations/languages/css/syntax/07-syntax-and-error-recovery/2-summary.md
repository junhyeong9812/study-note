# css/syntax/07 — CSS 구문과 오류 복구: 선언·규칙·at-rule 단위로 버리는 규칙 — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [CSS Syntax Level 3](https://drafts.csswg.org/css-syntax-3/) 의 「Parsing」·「Error Handling」 절과 [CSS Cascading and Inheritance Level 5](https://drafts.csswg.org/css-cascade-5/) 의 「Invalid at computed-value time」 규정. 열어서 확인한 것만 적었다.
> **실행 검증** — 이 문서의 모든 출력은 **Google Chrome 151.0.7922.173** headless 에 실제로 띄워 `document.styleSheets[…].cssRules`·`CSS.supports()`·`getComputedStyle` 로 읽은 것이다. 하네스는 [3-answer.md](3-answer.md) 의 `## 실행 검증` 절에 있다.\
> **엔진은 Chrome 하나다** — Firefox 155.0.1 은 이 환경에서 headless 산출이 조용히 실패하고 WebKit 은 없다. 「두 엔진에서 확인했다」고 적지 않는다.
> **버전** — CSS 에는 언어 버전이 없다. 오류 복구 규칙 자체는 CSS1 부터 있었지만, **중첩(nesting)이 2023 년에 들어오면서 「중괄호를 안 닫았을 때」의 결과가 바뀌었다** — 아래 (5)가 그 이야기다.
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 출력은 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

**★ CSS 는 에러가 없는 언어다. 모르는 것을 만나면 조용히 버리고 다음으로 간다.**

받아쓰기 시험에 비유한다. 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 받아쓰는 사람 | CSS 파서 |
| 못 알아들은 낱말 하나를 빈칸으로 두고 넘어감 | **선언 하나**를 버린다 |
| 문장 하나를 통째로 건너뜀 | **규칙 하나**를 버린다 |
| 문단 하나를 통째로 건너뜀 | **at-rule 하나**를 버린다 |
| 괄호를 못 닫아 나머지를 계속 받아 적음 | **회복 지점을 놓친 경우** |
| 시험지를 안 돌려줌 | **에러·경고가 전혀 없다** |

- **에러가 없다는 것이 장점이자 최대의 함정**이다.\
  장점 — 새 문법을 모르는 구형 브라우저가 페이지를 안 깨뜨린다(**점진적 향상**의 토대).\
  함정 — 오타 하나가 **화면에서만 다르게** 드러나고, 어디가 문제인지 아무도 안 알려 준다.
- **「버려졌다」를 증명하는 방법은 값을 읽어 보는 것**뿐이다. 화면도 콘솔도 말해 주지 않는다.
- **버려지는 단위가 셋**이다. 어느 단위로 버려지느냐에 따라 **한 줄만 죽거나 시트 전체가 죽는다.**

```text
  .c1 { color: redd; background-color: #fde68a }
         ^^^^^^^^^^^
         이 한 줄만 사라진다.  background-color 는 산다
         -> 실측  규칙 .c1 의 속성 목록 = [background-color]

  .s1, ::totally-bogus, .s2 { color: red }
       ^^^^^^^^^^^^^^^^
       선택자 목록에 하나만 이상해도 '규칙 전체'가 사라진다
       -> 실측  시트의 cssRules 에 이 규칙이 아예 없다

  .v3 { color: rgb(1,2,3; }   .v4 { … }   .v5 { … }
                     ^
                     괄호를 안 닫으면 '시트의 나머지 전부'를 삼킨다
       -> 실측  남은 규칙 수 = 1
```

실무에서 이게 터지는 자리는 **새 문법을 시험할 때**다.\
`@scope` 를 썼는데 아무것도 안 먹어서 「문법이 틀렸나」 하고 고치는데, 사실은 **그 브라우저가 `@scope` 를 몰라서 블록을 통째로 버린 것**이다.\
**「선언이 버려졌나 / 규칙이 버려졌나 / 담겼는데 값이 안 먹었나」 셋은 서로 다른 이야기**이고, 진단 도구가 각각 다르다.

> **선언(declaration)** — `속성: 값` 한 쌍. 버려지는 가장 작은 단위.\
> 예: `color: redd` 하나가 사라져도 같은 규칙의 다른 선언은 산다.

> **규칙(qualified rule)** — `선택자 { 선언들 }` 한 덩어리.\
> 예: 선택자 목록에 이상한 것이 하나 있으면 이 덩어리 전체가 사라진다.

> **at-rule** — `@` 로 시작하는 문. `@media`·`@layer`·`@scope`·`@import` 등.\
> 예: 모르는 at-rule 은 블록까지 통째로 사라진다.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 세 질문을 둔다.

1. **모르는 것을 만나면 어디까지 버리는가.** 선언 하나인가, 규칙 하나인가, 그 뒤 전부인가.
2. **「파서가 아예 안 담았다」와 「담았는데 값이 안 먹는다」를 어떻게 가르는가.** 도구가 각각 무엇인가.
3. **어디서 회복하는가.** 한 번 삼키기 시작하면 무엇을 만나야 멈추는가.

## 동작 방식

### (0) 두 질문을 먼저 가른다 — 담겼나 / 먹었나

**언제 쓰나** — 「내 CSS 가 안 먹는다」를 진단하는 모든 자리. **이 절을 먼저 세워야 나머지가 읽힌다.**

```text
질문 ①  파서가 그 선언을 담았나?
   도구:  document.styleSheets[i].cssRules[j].style      속성 목록에 있나
          CSS.supports('속성', '값')                      파싱 가능한가
   답이 '아니오' -> 구문 오류다. 오타·단위 누락·미지원 문법

질문 ②  담겼는데 값이 안 먹나?
   도구:  getComputedStyle(el).속성                       실제 결과
   답이 '그렇다' -> 캐스케이드에서 졌거나(01번)
                   계산 시점에 무효가 됐다(아래 (6) IACVT)
```

실측으로 두 경우를 나란히 놓은 것이다.

```text
  .c1 { color: redd; … }                     .v2 { --x: redd; color: var(--x); … }

  cssRules 의 속성 목록                       cssRules 의 속성 목록
  [background-color]                          [--x, color, background-color]
   ^ color 가 없다                             ^ color 가 있다
  -> 파서가 아예 안 담았다                     -> 담겼는데 값이 안 먹었다
  getComputedStyle -> rgb(0, 0, 0)            getComputedStyle -> rgb(0, 0, 0)
       ★ 화면 결과는 똑같다 — 그래서 값 하나만 보면 두 경우를 못 가른다
```

그림 해설 (한 단계씩):

- **결과가 같아서 진단이 갈린다.** 둘 다 「색이 안 먹었다」로 보이지만 고칠 자리가 다르다.
- ①이면 **문법을 고친다**(오타·단위·지원 여부).
- ②면 **값의 출처를 고친다**(변수 값·캐스케이드·`@property` 등록).
- 그래서 진단은 **언제나 `cssRules` 부터** 본다. 개발자 도구 Styles 패널에서 **아예 안 보이는 선언**이 ①이고, **회색으로 보이는데 안 먹는 것**이 ②다.

비용 — 없음. 다만 `cssRules` 는 **같은 출처의 시트만** 읽을 수 있다 — `file://` 이나 CDN 시트는 예외를 던진다.

### (1) 선언 단위 — 모르는 속성·모르는 값은 그 줄만

**언제 쓰나** — 대부분의 오타. 가장 흔하고 가장 얌전한 경우다.

```text
실측 — 세 규칙의 '담긴 속성 목록'

  .c1 { color: redd; background-color: #fde68a }
        -> [background-color]                       color 만 사라졌다

  .c2 { width: 10; height: 30px }
        -> [height]                                 단위 없는 길이는 무효

  .v1 { color: #b91c1c; -webkit-totally-fake: 1; background-color: #fde68a }
        -> [color, background-color]                모르는 속성 이름도 그 줄만
```

그림 해설 (한 단계씩):

- **모르는 속성 이름**(`colour`·`-webkit-totally-fake`)과 **모르는 값**(`redd`·`10`)이 같은 대우를 받는다 — 그 선언 하나만 사라진다.
- 이것이 **벤더 접두사가 통했던 이유**다. `-webkit-box-shadow` 를 모르는 브라우저는 그 줄만 버리고 다음 줄의 표준 속성을 읽는다.
- 회복 지점은 **다음 `;` 또는 블록을 닫는 `}`** 다.

```css
.btn {
  background: #2563eb;              /* 구형도 아는 것 — 먼저 */
  background: color-mix(in oklch, #2563eb 80%, white);  /* 모르면 이 줄만 버린다 */
}
```

- **같은 속성을 두 번 쓰는 관용구**가 여기서 나온다. 뒤 줄을 모르면 앞 줄이 남고, 알면 뒤 줄이 이긴다(6단계 순서 — [01번 주제](../01-cascade-and-priority/2-summary.md)).

비용 — 없음. **이것이 점진적 향상의 가장 싼 형태**다.

### (2) `!important` 의 표기 — 어디까지 봐주나

**언제 쓰나** — `!important` 가 안 먹는 것 같을 때.

```text
실측 — 각 선언이 담겼는지와 실제 색

  .w1 { color: red ! important }    담김: color: red !important;   -> rgb(255,0,0)  이겼다
  .x1 { color: red! important }     담김: color: red !important;   -> rgb(255,0,0)  이겼다
  .x2 { color: red ! /*c*/ important } 담김: color: red !important;-> rgb(255,0,0)  이겼다
  .w2 { color: red !IMPORTANT }     담김: color: red !important;   -> rgb(255,0,0)  이겼다
  .w4 { color: red!important }      담김: color: red !important;   -> rgb(255,0,0)  이겼다
  .x3 { color: red important }      담김: (빈 블록)                -> 뒤 선언이 이김
  .w3 { color: red; !important }    담김: color: red;              -> red (이 선언만 살았다)
```

그림 해설 (한 단계씩):

- **`!` 와 `important` 사이의 공백·주석은 전부 허용**된다. `red! important` 도 유효하다.
- **대소문자를 안 가린다.** `!IMPORTANT` 도 같다.
- **`!` 가 없으면 무효**다(`red important`) — 그 선언 하나가 버려진다.
- 선언 밖의 `!important`(`.w3`)는 **그 자리만 버려지고** 앞 선언은 산다.
- 직렬화(`cssText`)는 전부 **`red !important`** 한 형태로 정규화된다. 곧 **내가 쓴 형태와 파서가 이해한 형태는 다를 수 있다.**

비용 — 없음.

### (3) 규칙 단위 — 선택자 하나가 목록 전체를 죽인다

**언제 쓰나** — 새 선택자를 쓰거나 선택자 목록을 길게 나열할 때. **가장 아픈 자리다.**

```text
실측 — 시트에 남은 규칙

  .s1, ::totally-bogus, .s2 { color: #b91c1c }
     -> 시트에 이 규칙이 '없다'.   .s1 = rgb(0,0,0)  .s2 = rgb(0,0,0)

  :is(.s3, ::totally-bogus, .s4) { color: #15803d }
     -> 남았다.  cssText = ":is(.s3, .s4) { color: rgb(21, 128, 61); }"
                            ^^^^^^^^^^^^^ 이상한 것만 지워졌다
        .s3 = rgb(21,128,61)   .s4 = rgb(21,128,61)
```

```text
   쉼표로 나열한 목록                      :is() 로 감싼 목록
   +-----------------------------+        +-----------------------------+
   | .s1 , ::bogus , .s2         |        | :is(.s1, ::bogus, .s2)      |
   |   하나가 무효 -> 전부 사망   |        |   하나가 무효 -> 그것만 삭제 |
   +-----------------------------+        +-----------------------------+
     멀쩡한 .s1·.s2 까지 잃는다             나머지는 살아서 동작한다
```

그림 해설 (한 단계씩):

- 쉼표 선택자 목록은 **한 몸**이다. 하나가 무효면 규칙 전체가 버려진다 — **멀쩡한 선택자까지 같이 죽는다.**
- **`:is()`·`:where()` 는** 「**너그러운 선택자 목록**」(forgiving selector list)이라 무효한 것만 빼고 나머지를 쓴다.\
  실측에서 `cssText` 가 **`:is(.s3, .s4)`** 로 직렬화됐다 — 브라우저가 그 자리를 **지워 버린 것**이 눈에 보인다.
- 그래서 **새 선택자를 섞어 쓸 때는 `:is()` 로 감싼다.** `:has()` 를 모르는 브라우저에 `.a, .b:has(x)` 를 주면 `.a` 까지 잃는다.
- 명시도 이야기는 [02번 주제](../02-specificity/2-summary.md)와 [목록의 **11번 주제**](../11-is-where-not/)가 정본이다 — 여기서는 **오류 복구 성질**만 쓴다.

비용 — 없음. 다만 `:is()` 는 명시도를 **가장 센 인자**로 올린다 — 공짜가 아니다.

### (4) at-rule 단위 — 모르는 `@` 는 블록까지 통째로

**언제 쓰나** — 새 at-rule(`@scope`·`@container`·`@starting-style`)을 쓸 때.

```text
실측 — 시트에 남은 규칙과 색

  @totally-unknown { .a1 { color: #b91c1c } }    -> 규칙 자체가 없다.  .a1 = rgb(0,0,0)
  .a2 { color: #b91c1c }                          -> 살았다.           .a2 = rgb(185,28,28)
  @another-unknown some stuff here;               -> 세미콜론까지만 삼킨다
  .a3 { color: #15803d }                          -> 살았다.           .a3 = rgb(21,128,61)
```

```text
  블록이 있는 at-rule       @이름 prelude { ... }
                            회복 지점 = 짝 맞는 '}'  -> 블록까지 버린다

  블록이 없는 at-rule       @이름 prelude ;
                            회복 지점 = ';'          -> 거기서 멈춘다
```

그림 해설 (한 단계씩):

- **모르는 at-rule 은 블록 안의 멀쩡한 규칙까지 같이 버린다.** 구형 브라우저에서 `@scope { … }` 안의 스타일이 통째로 사라지는 이유다.
- 그래서 **기본 모양은 at-rule 밖에 두고, at-rule 안에는 「더 나은 경우」만** 담는다 — 점진적 향상의 배치.
- 회복 지점이 `;` 인지 `}` 인지는 **at-rule 이 블록을 갖느냐**로 갈린다.

비용 — 없음.

### (5) ★ 중괄호를 안 닫으면 — 다음 규칙들이 「중첩 규칙」으로 삼켜진다

**언제 쓰나** — 편집 중 `}` 하나를 빠뜨렸을 때. **2023 년 중첩이 들어오면서 결과가 바뀐 자리다.**

```css
.b1 { color: #b91c1c;
.b2 { color: #15803d; }
.b3 { color: #1d4ed8; }
```

```text
실측
  시트에 남은 규칙 수 = 1
  그 규칙의 cssText =
    .b1 { color: rgb(185, 28, 28); & .b2 { color: rgb(21, 128, 61); }
                                   & .b3 { color: rgb(29, 78, 216); } }
                                   ^^^ 브라우저가 & 를 붙여 '중첩 규칙' 으로 만들었다

  .b1 = rgb(185, 28, 28)                     살았다
  .b2 (문서 아무 데나)  = rgb(0, 0, 0)        안 먹는다
  .b2 (.b1 안에 있을 때) = rgb(21, 128, 61)   ★ 여기서만 먹는다
```

```text
  중첩이 없던 시절                       오늘 (중첩 이후)
  +-----------------------------+       +-----------------------------+
  | .b2·.b3 은 '버려진다'        |       | .b2·.b3 은 '.b1 의 자손에게만'|
  |  -> 아무 데도 안 먹는다      |       |    먹는 규칙이 된다          |
  +-----------------------------+       +-----------------------------+
      어디서도 안 먹으니 금방 눈에 띈다      어떤 곳에서는 먹어서 더 늦게 들킨다
```

그림 해설 (한 단계씩):

- **버려진 게 아니라 자리가 옮겨졌다.** 규칙이 `.b1` 안으로 들어가 **선택자가 `.b1 .b2` 로 바뀐 것과 같아진다.**
- 회복 지점은 **시트 끝**이다 — `}` 를 하나도 안 닫았으므로 EOF 까지 계속 중첩으로 먹는다.
- ★ **이 변화가 진단을 어렵게 만들었다.** 「어디서는 먹고 어디서는 안 먹는다」가 되어, 「전혀 안 먹는다」보다 **원인 추적이 오래 걸린다.**

비용 — 없음(파싱 비용 이야기가 아니다). 사람의 비용만 늘었다.

### (6) ★ 괄호를 안 닫으면 — 시트의 나머지 전부

**언제 쓰나** — 값 안의 함수 괄호를 빠뜨렸을 때. **이 문서에서 가장 파괴적인 경우다.**

```css
.v3 { color: rgb(1,2,3; background-color: #fde68a; }
.v4 { color: #1d4ed8; }
.v5 { color: #15803d; }
```

```text
실측
  시트에 남은 규칙 수 = 1        (.v3 하나뿐)
  .v3 의 속성 목록 = []          background-color 도 없다
  .v3 = rgb(0,0,0)   .v4 = rgb(0,0,0)   .v5 = rgb(0,0,0)
```

```text
   함수 토큰 rgb( 를 열면
        회복 지점은 ';' 도 '}' 도 아니다 — 짝 맞는 ')' 뿐이다
        그런 ')' 가 없으면  ->  시트 끝(EOF)까지 전부 먹는다

   .v3 { color: rgb(1,2,3;  background-color: …; }  .v4 { … }  .v5 { … }
                    ^--------------------- 여기부터 시트 끝까지 한 덩어리 ------^
```

그림 해설 (한 단계씩):

- `;` 와 `}` 는 **함수 괄호 안에서는 회복 지점이 아니다.** 그냥 토큰으로 삼켜진다.
- 그래서 **오타 한 글자가 시트 한 장을 통째로 날릴 수 있다.**
- 같은 성질이 **닫히지 않은 주석**(`/*`)에도 있다 — 실측에서 `/*` 뒤의 규칙이 시트 끝까지 사라졌다.
- **회복 단위가 셋이 아니라 넷**인 셈이다 — 선언 · 규칙 · at-rule · **그리고 「아무 데서도 회복 못 함」.**

비용 — 없음. 대신 **CSS 린터·빌드 검사가 꼭 필요한 이유**가 여기다. 브라우저는 아무 말도 안 한다.

### (7) 최상위 선언 — 다음 규칙까지 같이 죽는다

**언제 쓰나** — 중괄호 밖에 선언을 잘못 남겼을 때.

```css
color: #b91c1c;
.y1 { color: #15803d; }
```

```text
실측
  .y1 = rgb(0, 0, 0)      안 먹는다
```

```text
  최상위에서 파서는 '규칙' 을 기대한다
     prelude 는 '{' 를 만날 때까지다
        prelude = "color: #b91c1c; .y1"      <- 다음 규칙의 선택자까지 빨려 들어갔다
        block   = "{ color: #15803d; }"
     prelude 가 선택자로 무효 -> 규칙 전체 폐기 -> .y1 의 블록도 같이 사라진다
```

- **세미콜론이 안 막아 준다.** 최상위의 `;` 는 선언 구분자가 아니라 그냥 토큰이다.
- 같은 모양이 **세미콜론을 빠뜨린 `@layer` 사전 선언**에서도 났다 — `@layer base, theme`(세미콜론 없음) 뒤의 규칙이 같이 죽었다([05번 주제](../05-cascade-layers/2-summary.md)).

비용 — 없음.

### (8) 파서는 담았는데 값이 안 먹는 경우 — 조건과 IACVT

**언제 쓰나** — `cssRules` 에 멀쩡히 있는데 화면이 안 바뀔 때. **(0)의 질문 ②에 해당하는 자리다.**

```text
경우 A — 조건이 거짓인 at-rule.  파서는 규칙을 '담는다'
  @media (totally-unknown-feature: 1) { .a4 { color: #b91c1c } }
     -> cssRules 에 있다.  matchMedia('(totally-unknown-feature: 1)').matches = false
     -> 안 먹는다

  @supports (color: redd) { .y3 { color: #b91c1c } }
     -> cssRules 에 있다.  조건이 거짓이라 안 먹는다

경우 B — 계산 시점 무효(IACVT).  커스텀 속성이 대표다
  .v2 { --x: redd; color: var(--x); background-color: #fde68a }
     -> 속성 목록 = [--x, color, background-color]   셋 다 담겼다
     -> getComputedStyle(.v2)['--x']  = "redd"       값도 그대로 있다
     -> getComputedStyle(.v2).color   = rgb(0, 0, 0) 색만 안 먹었다
```

그림 해설 (한 단계씩):

- **커스텀 속성은 거의 아무 토큰이나 담는다.** `--x: redd` 는 파서가 무효라고 보지 않는다 — 뜻은 쓰는 쪽이 정하기 때문이다.
- `var(--x)` 로 펼쳤을 때 비로소 `color: redd` 가 되어 무효가 되고, 그때는 **선언을 버리는 게 아니라 `unset` 처럼 취급**된다(명세 용어로 **IACVT**).
- 그래서 **같은 오타가 어디에 있었느냐에 따라 진단 경로가 완전히 다르다.** 자세한 것은 [목록의 **36번 주제**](../36-custom-properties/).
- `@media`·`@supports` 쪽은 **오류가 아니라** 「**조건이 거짓**」이다 — 파서는 아무 문제도 못 느꼈다.

비용 — 없음.

### (9) 어디까지 삼키고 어디서 회복하나 — 한 표로

**언제 쓰나** — 진단의 마지막 단계. 이 표 하나가 이 주제의 요약이다.

```text
  무엇이 잘못됐나                    버려지는 범위            회복 지점        실측 근거
  --------------------------------  ----------------------  ---------------  ---------------
  모르는 속성 이름 (colour)          선언 하나               다음 ';' 또는 '}'  속성 목록에 없음
  모르는 값 (redd · 10)              선언 하나               〃                〃
  전역 키워드 오용 (10px inherit)    선언 하나               〃                속성 목록에 없음
  세미콜론 중복 (;;)                 없음                    —                 정상 동작
  선택자 목록 중 하나가 무효          규칙 하나(선택자 전부)   규칙의 '}'        cssRules 에 없음
  :is() 안의 무효 선택자              그 인자 하나            —                 cssText 가 지워 보여 줌
  모르는 at-rule (블록 있음)          at-rule + 블록          짝 맞는 '}'       cssRules 에 없음
  모르는 at-rule (블록 없음)          at-rule 한 문           ';'               다음 규칙은 살아남음
  '}' 를 안 닫음                      ★ 버리지 않는다         시트 끝           뒤 규칙이 '중첩'이 된다
  ')' 를 안 닫음                      ★ 시트의 나머지 전부     없음(EOF)         남은 규칙 수 = 1
  '*/' 를 안 닫음                     ★ 시트의 나머지 전부     없음(EOF)         뒤 규칙이 사라짐
  최상위에 선언을 둠                  그 선언 + 다음 규칙      다음 '}'          .y1 이 안 먹음
  조건이 거짓인 @media/@supports      ★ 버리지 않는다          —                 cssRules 에 남아 있음
  무효한 var() 치환 결과              그 속성만 unset 처럼     —                 선언은 담겨 있음
```

**세 줄 요약** — 버려지는 것은 **선언 · 규칙 · at-rule** 셋이고, **`)` 와 `/*` 는 회복 지점이 없어 시트를 통째로 날리며**, **`}` 누락은 이제 버려지지 않고 중첩으로 바뀐다.**

## 문법 — 형태와 규칙

CSS 는 문법 표면이 단순하므로 이 절은 「**형태 — 어디서 헷갈리나**」로 읽는다.

### 형태 — 진단 도구 셋

```js
CSS.supports('color', 'redd')            // false — 이 값이 파싱되나
CSS.supports('selector(::totally-bogus)')// false — 이 선택자가 파싱되나
CSS.supports('at-rule(@scope)')          // true  — 이 at-rule 을 아나
sheet.cssRules.length                    // 규칙이 몇 개 담겼나
sheet.cssRules[0].style                  // 그 규칙이 담은 속성 목록
sheet.cssRules[0].cssText                // 파서가 이해한 형태 (정규화된 것)
getComputedStyle(el).color               // 최종 결과
```

### 금지 사례 — 도구가 거짓말하는 자리

```js
CSS.supports('selector(:is(.a, ::totally-bogus))')   // false ← 규칙은 동작하는데도
document.styleSheets[0].cssRules                     // 다른 출처 시트면 예외
```

- **`selector()` 질의는 너그럽지 않다.** `:is()` 안의 무효 선택자를 실제로는 무시해 주는데, 질의는 **`false`** 를 돌려준다(실측).\
  「질의가 false 니까 안 되겠구나」로 읽으면 틀린다.
- **`cssRules` 는 같은 출처 시트만** 읽힌다. `file://` 문서나 CDN 시트에서는 `"Cannot access rules"` 예외가 난다.

### 어디서 헷갈리나

- **「미지원」을 한 낱말로 적지 마라.** ① 파서가 아예 모름(규칙 목록에 없다) ② 파서는 아는데 조건이 거짓(`@media`) ③ 담겼는데 계산 시점에 무효(IACVT) — **셋이 전부 다르다.**
- **`}` 누락과 `)` 누락은 결과가 정반대다.** 앞엣것은 살려서 옮기고, 뒤엣것은 전부 죽인다.
- **개발자 도구의 「줄 그은 선언」은 버려진 게 아니다.** 그것은 캐스케이드에서 진 것이다([01번 주제](../01-cascade-and-priority/2-summary.md)). 버려진 선언은 **아예 안 보인다.**

## 어디서 틀리나

이 주제의 값어치는 전부 여기 있다. 일곱 다 **에러 없이 조용히 어긋난다.**

### 1. 콘솔에 뭔가 찍힐 거라 기대한다

```text
실측 — Chrome 151 을 --enable-logging=stderr 로 돌려 stderr 를 전부 받았다

  .c1 { color: redd; width: 10; background-color: #fde68a }

  CSS 관련 로그 줄 수 = 0
  (같은 실행에서 JS 의 console.log 는 정상적으로 찍혔다)
```

**아무것도 안 찍힌다.** 예외도, 경고도, 개발자 도구 Console 탭의 한 줄도 없다.\
이것이 이 언어에서 「돌려 봤다」가 곧 「값을 읽어 봤다」여야 하는 이유다.

### 2. 새 선택자를 쉼표 목록에 섞어 넣는다

```css
.card, .panel:has(> img) { padding: 16px; }   /* :has() 를 모르면 .card 도 잃는다 */
```

`:is()` 로 감싸면 `.card` 는 산다 — 다만 명시도가 올라간다([목록의 **11번 주제**](../11-is-where-not/)).

### 3. `}` 를 빠뜨렸는데 「일부는 먹으니 괜찮다」고 넘어간다

실측에서 `.b2` 가 **`.b1` 안에서만** 먹었다. 어떤 화면에서는 정상으로 보이고 어떤 화면에서는 안 먹는다.\
**「전혀 안 먹는다」보다 훨씬 늦게 들킨다.**

### 4. `)` 하나로 시트가 통째로 죽는 것을 모른다

실측에서 남은 규칙이 **1개**였다. 그 뒤에 쓴 규칙은 `cssRules` 에 **아예 없다.**\
「맨 아래 규칙만 안 먹네」가 아니라 「**어느 줄 아래로 전부 안 먹네**」면 괄호를 의심한다.

### 5. `@media (unknown)` 를 「버려졌다」고 설명한다

**안 버려졌다.** `cssRules` 에 멀쩡히 있고, 조건이 거짓이라 매치가 안 될 뿐이다(실측 `matchMedia(...).matches = false`).\
버려진 것과 조건이 거짓인 것을 섞어 말하면 **`@supports` 로 고칠 문제를 문법 문제로 오진**한다.

### 6. 커스텀 속성의 오타를 문법 오류로 찾는다

`--x: redd` 는 **문법상 완전히 정상**이다. `cssRules` 에도 있고 `getComputedStyle` 로 읽으면 `"redd"` 가 그대로 나온다.\
무효가 되는 것은 `var(--x)` 를 쓴 **그 속성**이고, 그때도 선언은 버려지지 않고 `unset` 처럼 처리된다(IACVT).

### 7. `CSS.supports('selector(...)')` 의 `false` 를 그대로 믿는다

실측에서 `CSS.supports('selector(:is(.a, ::totally-bogus))')` 가 **`false`** 인데 같은 선택자를 쓴 규칙은 **정상 동작**했다.\
질의는 **너그럽지 않은 파싱**을 쓰기 때문이다. 질의 결과가 아니라 **실제 규칙의 `cssText` 와 값**을 봐야 한다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| 모르는 속성·값이 선언 하나만 버린다 | **명세**(css-syntax-3 「Error Handling」) |
| 선택자 목록 하나가 무효면 규칙 전체가 버려진다 | **명세**(selectors-4) |
| `:is()`·`:where()` 가 너그러운 목록인 것 | **명세**(selectors-4) |
| 모르는 at-rule 이 블록까지 버려지는 것 | **명세** |
| 함수 괄호가 `;`·`}` 로 안 닫히는 것 | **명세**(토큰화 규칙) |
| `}` 누락 시 뒤 규칙이 **중첩 규칙**이 되는 것 | **명세**(css-nesting-1 이 들어온 뒤의 정상 동작) |
| IACVT 가 `unset` 처럼 처리되는 것 | **명세**(css-variables·css-cascade) |
| **콘솔에 아무것도 안 찍히는 것** | **관찰**(Chrome 151). 명세는 로그를 규정하지 않는다 — 다른 브라우저는 경고할 수 있다 |
| `cssText` 가 `:is(.s3, .s4)` 로 직렬화되는 것 | **명세**(CSSOM 직렬화) + 관찰 |
| `CSS.supports('selector(...)')` 가 너그럽지 않은 것 | **명세**(css-conditional) + 관찰 |
| `file://` 에서 `cssRules` 가 막히는 것 | **브라우저 보안 정책.** 언어 규칙이 아니다 |

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 새 색 함수·새 값을 점진적으로 쓴다 | 같은 속성을 두 줄로(구형 먼저) | `@supports`(선언 단위 복구로 충분하다) |
| 새 at-rule 을 쓴다 | 기본은 밖에, 향상은 안에 | at-rule 안에만 전부 담기 |
| 여러 선언이 한 덩어리로 맞물린다 | `@supports` 로 통째로 가르기 | 선언마다 두 줄씩 |
| 새 선택자를 목록에 섞는다 | `:is()` 로 감싸기 | 쉼표로 그냥 나열 |
| 「왜 안 먹지」를 진단한다 | `cssRules` → `getComputedStyle` 순서로 | 화면만 보고 추측 |
| 오타를 미리 잡는다 | 린터·빌드 검사 | 브라우저(아무 말도 안 한다) |

판단 규칙 두 줄.

- **「이 한 줄이 무시돼도 페이지가 성립하는가」를 먼저 묻는다.** 성립하면 오류 복구에 맡기고, 아니면 `@supports` 로 통째로 가른다.
- **진단은 언제나 「담겼나」부터.** 값만 보면 서로 다른 세 원인이 같은 얼굴을 하고 있다.

## 핵심 문장

- **CSS 는 에러를 던지지 않는다.** 실측에서 오타가 든 시트를 로드해도 **CSS 관련 로그가 한 줄도 없었다.**
- 버려지는 단위는 **선언 · 규칙 · at-rule** 셋이고, 어느 단위냐에 따라 **한 줄이 죽거나 시트가 죽는다.**
- **선택자 목록은 한 몸**이다 — 하나가 무효면 전부 잃는다. `:is()` 로 감싸면 **그 인자만** 지워진다(`cssText` 가 그것을 보여 준다).
- **`)` 나 `/*` 를 안 닫으면 회복 지점이 없어 시트 끝까지 삼킨다.** 실측에서 남은 규칙이 **1개**였다.
- **`}` 누락은 이제 「버려짐」이 아니라** 「**중첩으로 옮겨짐**」이다. 중첩이 표준이 되면서 바뀐 자리이고, 그래서 더 늦게 들킨다.
- **「파서가 안 담았다」와 「담겼는데 값이 안 먹는다」는 다른 이야기**다 — 앞은 `cssRules`·`CSS.supports`, 뒤는 `getComputedStyle` 로 가른다.
- **이 관용 규칙이 점진적 향상의 토대**다. 구형 브라우저가 새 문법을 만나도 페이지가 안 깨지는 것은 이 규칙 덕분이다.

## 용어 풀이

- **오류 복구(error recovery)** — 파서가 모르는 것을 만났을 때 어디까지 버리고 어디서 다시 읽기 시작하나.
- **선언(declaration)** — `속성: 값` 한 쌍. 버려지는 가장 작은 단위.
- **규칙(qualified rule)** — `선택자 { 선언들 }` 한 덩어리.
- **at-rule** — `@` 로 시작하는 문. 블록이 있으면 `}` 까지, 없으면 `;` 까지가 한 문이다.
- **프렐류드(prelude)** — at-rule 이름 뒤, `;` 또는 `{` 앞까지. 규칙에서는 선택자 자리.
- **함수 토큰(function token)** — `rgb(` 처럼 `(` 로 시작하는 토큰. 짝 맞는 `)` 까지가 한 덩어리이고 `;`·`}` 로 안 끊긴다.
- **너그러운 선택자 목록(forgiving selector list)** — `:is()`·`:where()` 의 인자 목록. 무효한 인자만 빼고 쓴다.
- **IACVT(invalid at computed-value time)** — 파싱은 됐는데 계산 시점에 무효가 되는 값. `unset` 처럼 처리된다.
- **점진적 향상(progressive enhancement)** — 모르는 문법이 무시돼도 기본 화면이 성립하게 쌓는 방식.
- **`CSS.supports()`** — 속성·값·선택자·at-rule 을 파싱할 수 있는지 묻는 API. **너그럽지 않은 파싱**을 쓴다.
- **`cssRules`** — 시트가 실제로 담은 규칙 목록. 「파서가 담았나」의 정답지. 같은 출처 시트만 읽힌다.

## 더 들어가면

- **벤더 접두사가 통했던 것은 이 규칙 덕분**이다. `-webkit-` 속성을 모르는 브라우저는 그 선언만 버리고 다음 줄을 읽는다. 2026 기준 새로 쓸 문법은 아니지만(목록 README 의 「뺀 것과 이유」), **왜 그 시대에 그게 동작했는가**는 이 주제로 설명된다.
- **CSS 해킹의 정체도 오류 복구다.** `*zoom: 1`·`_height` 같은 옛 해킹은 「어떤 브라우저는 이 선언을 버리고 어떤 브라우저는 안 버린다」를 이용한 것이었다.
- **HTML 과 대비가 선명하다.** HTML 파서는 **복구해서 트리를 만든다**(태그를 닫아 주고 요소를 끼워 넣는다). CSS 파서는 **버린다.** 둘 다 에러를 안 던지지만 방향이 반대다.
- **`@supports` 와 오류 복구는 겹치는 도구**다. 선언 하나면 오류 복구로 충분하고, **여러 선언이 맞물려 한 덩어리로 성립하거나 깨질 때**만 `@supports` 가 필요하다([목록의 **41번 주제**](../41-supports-feature-queries/)).
- **`cssRules` 를 읽는 것 자체가 진단 기법**이다. 빌드 파이프라인에서 시트를 브라우저에 로드해 **`cssRules.length` 가 예상과 같은지** 검사하면, 린터가 못 잡는 「삼켜진 규칙」을 잡을 수 있다.
