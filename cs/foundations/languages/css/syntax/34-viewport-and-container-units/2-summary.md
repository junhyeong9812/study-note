# css/syntax/34 — 뷰포트 단위와 컨테이너 단위: `vh`/`svh`/`lvh`/`dvh`·`cqw`/`cqi` — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [CSS Values and Units Level 4](https://drafts.csswg.org/css-values-4/) 의 「Viewport-percentage Lengths」 절(`vw`/`vh`/`vmin`/`vmax` 와 `sv*`/`lv*`/`dv*`)과 [CSS Containment Level 3](https://drafts.csswg.org/css-contain-3/) 의 「Container Relative Lengths」 절(`cqw`/`cqi`/`cqb`/`cqmin`/`cqmax`). 열어서 확인한 것만 적었다.
> **실행 검증** — 이 문서의 픽셀 값은 **Google Chrome 151.0.7922.173** headless 에 띄워 `getBoundingClientRect()`·`getComputedStyle` 로 읽은 것이다. **뷰포트가 주제이므로 `--window-size` 를 바꿔 가며 세 판을 쟀다**(800×600 · 375×667 · 1200×400). **손으로 계산해 유도한 수치는 없다.**\
> ★ **`svh`/`lvh`/`dvh` 는 headless 에서 세 값이 같게 나왔다** — 주소창이 없기 때문이다. 아래 (4) 에 그대로 적고, **갈리는 상황은 재지 못했음을 명시**했다. 지어내지 않았다.\
> **엔진은 Chrome 하나다** — Firefox 155.0.1 은 이 환경에서 headless 산출이 조용히 실패하고 WebKit 은 이 머신에 없다. 「두 엔진에서 확인했다」고 적지 않는다.
> **버전** — CSS 에 언어 버전은 없다. `vw`/`vh` 는 CSS Values 3, `sv*`/`lv*`/`dv*` 는 Baseline **widely**(newly 2022-12-05 · widely 2025-06-05), 컨테이너 쿼리 단위는 컨테이너 쿼리와 함께 **widely**(newly 2023-02-14 · widely 2025-08-14)다. 근거는 [목록 README](../README.md) 의 지원 표다.
> **여기서 다루지 않는 것** — **`@container` 질의 자체**(`container-type` 의 대가·이름·스타일 쿼리)는 [목록의 **40번 주제**](../40-container-and-style-queries/)가 정본이다. 여기는 **단위까지**다. 미디어 쿼리는 [목록의 **38번 주제**](../38-media-queries/), 단위 일반은 [33번](../33-length-units/2-summary.md)이 정본이다.
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 수치는 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

**뷰포트 단위 = 「창을 100칸으로 나눈 자」, 컨테이너 단위 = 「이 상자를 100칸으로 나눈 자」다.**

같은 「1%」인데 **무엇을 100으로 놓느냐**가 다르다. [33번](../33-length-units/2-summary.md)의 `%` 가 **부모**를 봤다면, 이쪽은 **창** 또는 **지정한 조상 상자**를 본다.

방을 재는 것에 비유한다. 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 「이 건물 로비 폭의 1%」 | **`vw`** — 문서가 몇 겹 안에 있든 창 하나만 본다 |
| 「로비 가로·세로 중 짧은 쪽의 1%」 | **`vmin`** — 가로세로 중 작은 쪽 |
| 「로비 높이 — 접이식 차양 포함/제외/지금」 | **`lvh` / `svh` / `dvh`** — 모바일 주소창이 접히느냐로 갈린다 |
| 「이 방 폭의 1%」 | **`cqi`** — 가장 가까운 **등록된** 컨테이너 상자 |
| 방을 「잴 수 있는 방」으로 등록하는 신고서 | **`container-type`** — 선언해야 컨테이너가 된다 |

```text
  같은 "폭의 100%" 를 세 자로 재면

    +--------- 창(viewport) 800px -----------------+
    |  +------ 문서 content 785px ---------------+ |   <- 세로 스크롤바 15px
    |  |  +--- 카드(container) 300px ---------+  | |
    |  |  |                                  |  | |
    |  |  +----------------------------------+  | |
    |  +---------------------------------------+ |
    +----------------------------------------------+

    100vw  -> 800px   (스크롤바까지 포함한다 — 가로 스크롤이 생긴다)
    100%   -> 785px   (부모 = 문서 content)
    100cqi -> 300px   (카드가 container-type 을 선언했을 때만)
```

*(Chrome 151 실측 — `--window-size=800,600`, 세로 스크롤이 생기는 문서: `100vw` 상자 800px · `100%` 상자 785px.)*

실무에서 이게 터지는 자리는 「**가로로 1px 씩 흔들리는 스크롤바**」다.\
`width: 100vw` 로 전체 폭 배너를 만들면, 세로 스크롤바가 있는 순간 **정확히 스크롤바 폭만큼 가로 스크롤이 생긴다.**

> **뷰포트(viewport)** — 문서가 그려지는 창 안쪽 영역.\
> 예: 위 실측에서 창 800px 중 785px 이 문서 자리였고 나머지 15px 이 세로 스크롤바였다.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 세 질문을 둔다.

1. **`100vw` 와 `100%` 는 왜 다른가** — 어느 쪽이 스크롤바를 포함하고, 그 차이가 무엇을 만드나.
2. **`svh`/`lvh`/`dvh` 셋은 각각 무엇을 재는가** — 왜 하나로 안 되고 셋이 필요했나.
3. **컨테이너 단위는 무엇을 기준으로 삼는가** — `container-type` 을 선언하지 않으면 어떻게 되나.

## 동작 방식

### (1) `vw`·`vh` — 창을 100으로 나눈다. 창 크기가 실험 변수다

**언제 쓰나** — 화면을 꽉 채우는 히어로 영역·전체 폭 배너·모달 높이.

```text
같은 문서를 창 크기만 바꿔 세 판 쟀다 (Chrome 151 headless)

  --window-size      innerWidth  innerHeight  clientWidth  10vw     10vh
  -----------------  ----------  -----------  -----------  -------  -----------
  800,600            800         513          785          80       51.296875
  375,667            ★ 500       580          485          50       58
  1200,400           1200        313          1185         120      31.296875
```

```text
  10vw 가 창 폭을 그대로 따라간다 (같은 축척으로 그렸다)

    창  500 |========================|                10vw =  50
    창  800 |======================================|  10vw =  80
    창 1200 |=========================================================|  10vw = 120

  10vh 는 창 높이를 따라간다 (세로는 크롬 UI 를 뺀 innerHeight 기준이었다)

    창 높이 313 |==========|                10vh = 31.296875
    창 높이 513 |=================|         10vh = 51.296875
    창 높이 580 |===================|        10vh = 58
```

그림 해설 (한 단계씩):

- **`1vw` = 창 폭의 1%** 다. 창을 1200 으로 넓히자 `10vw` 가 120 으로 정확히 따라 늘었다.
- **`1vh` = 창 높이의 1%** 다. 창을 400 으로 줄이자 `10vh` 가 31.3 으로 줄었다.
- ★ **`--window-size=375,667` 을 줬는데 `innerWidth` 가 500 이 나왔다.** Chrome 에는 창 폭 하한이 있어 375 로 안 줄었다.\
  **이 문서의 375 판은 「폭 500 판」으로 읽어야 한다.** 재지 않은 것을 잰 것처럼 적지 않는다.
- `innerHeight` 가 창 높이(600)보다 작은 것은 headless 창에도 **크롬 UI 높이가 잡히기 때문**이다 — 이 역시 관찰이지 명세가 아니다.

비용 — 뷰포트 단위는 **레이아웃 전체를 창 크기에 묶는다.** 창이 바뀔 때마다 그 값을 쓰는 모든 상자가 다시 계산된다.

### (2) ★ `100vw` 는 스크롤바를 포함한다 — `100%` 와 대조

**언제 쓰나** — 「왜 가로로 조금 스크롤되지?」의 범인을 찾을 때. **이 절이 이 주제에서 가장 자주 터지는 자리다.**

```text
세로로 긴 문서(내용 2000px)를 800px 창에 띄웠다 (Chrome 151 실측)

  documentElement.clientWidth = 785      <- 스크롤바를 뺀 문서 폭
  window.innerWidth           = 800      <- 스크롤바를 포함한 창 폭
  스크롤바 폭                  = 15

  width: 100vw 상자 = 800px    ★ 스크롤바 자리까지 덮는다
  width: 100%  상자 = 785px

  documentElement.scrollWidth = 800 > clientWidth 785
    => 가로로 15px 만큼 스크롤된다
```

```text
  100vw 가 만드는 것                    100% 가 만드는 것
  +----------------------------+-+      +----------------------------+-+
  |  빨강 상자 800px           | |      |  파랑 상자 785px           |S|
  |  ...스크롤바 밑으로 15px   |S|      |                            |c|
  |     삐져나간다             |c|      |                            |r|
  +----------------------------+-+      +----------------------------+-+
   => 가로 스크롤바가 하나 더 생긴다      => 딱 맞는다
```

그림 해설 (한 단계씩):

- **`vw` 의 「창」에는 세로 스크롤바 자리가 포함된다.** 명세가 그렇게 정의했다(초기 포함 블록이 아니라 뷰포트).
- `%` 는 **부모의 content 폭**을 보므로 스크롤바가 빠진 785 다.
- 그래서 **세로 스크롤이 생기는 순간** `100vw` 짜리 상자가 15px 넘치고, **그것이 다시 가로 스크롤을 만든다.**
- 15 라는 숫자는 **그 환경의 스크롤바 폭**이다 — 오버레이 스크롤바를 쓰는 환경에서는 0 이 될 수도 있다. 관찰이지 상수가 아니다.

```html demo
<div class="vw">width: 100vw</div>
<div class="pc">width: 100%</div>
<div class="tall"></div>
<style>
  .vw   { width: 100vw; height: 40px; background: #dc2626; color: #fff; }
  .pc   { width: 100%;  height: 40px; background: #2563eb; color: #fff; }
  .tall { height: 2000px; }
</style>
```

> **보이는 것** — 빨간 띠와 파란 띠가 위아래로 붙어 있는데 **빨간 띠만 오른쪽으로 조금 더 길다.** 문서가 2000px 이라 세로 스크롤바가 생겼고, 빨간 띠(`100vw`)는 그 스크롤바 자리까지 덮기 때문이다. 아래쪽에 **가로 스크롤바가 하나 더 생긴다.**\
> **바꿔 볼 것** — `.tall` 의 `height: 2000px` → `100px` 으로 줄이면(세로 스크롤바가 사라진다) → **두 띠의 길이가 같아지고 가로 스크롤도 없어진다**

*(Chrome 151 headless 실측 — 도구 기본 창: 빨강 `780px` · 파랑 `765px` · 차이 15px = 세로 스크롤바 폭. 별도로 `--window-size=800,600` 에서는 800 대 785 로 역시 15px 차이였다.)*

비용 — 고치는 법은 `100vw` 를 **쓰지 않는 것**이다. 전체 폭이 필요하면 `width: 100%` 를 쓰거나, 꼭 `vw` 를 써야 하면 가로 넘침을 부모에서 잘라 낸다.

### (3) `vmin`·`vmax`·`vi`·`vb` — 어느 축을 보느냐가 다르다

**언제 쓰나** — 가로 화면·세로 화면 어느 쪽에서도 화면 안에 들어가야 하는 정사각 요소.

```text
창 크기별 실측 (Chrome 151)

  창 (innerWidth x innerHeight)   10vmin       10vmax     10vi     10vb
  ------------------------------  -----------  ---------  -------  -----------
  800 x 513                       51.296875    80         80       51.296875
  500 x 580                       50           58         50       58
  1200 x 313                      31.296875    120        120      31.296875
```

```text
  1200 x 313 판에서 무슨 일이 일어났나

    가로 1200  ─────────────────────────────────  긴 쪽
    세로  313  ───────                            짧은 쪽

    vmin -> 짧은 쪽(313) 의 1%  = 3.1296875
    vmax -> 긴  쪽(1200) 의 1%  = 12
    vi   -> 인라인 축 = 가로 = 12       (writing-mode 가 가로쓰기일 때)
    vb   -> 블록  축 = 세로 = 3.1296875
```

그림 해설 (한 단계씩):

- **`vmin`/`vmax`** 는 「**물리적으로 짧은/긴 쪽**」이다. 세 판에서 가로세로가 뒤바뀌어도 규칙대로 따라갔다.
- **`vi`/`vb`** 는 「**글이 흐르는 축 / 줄이 쌓이는 축**」이다. 가로쓰기에서는 `vi`=`vw`, `vb`=`vh` 로 일치했다.
- 세로쓰기(`writing-mode: vertical-rl`)면 둘이 뒤집힌다 — 축 규칙의 정본은 [목록의 **32번 주제**](../32-logical-properties-and-writing-mode/)다. **이 문서에서 세로쓰기는 재지 않았다.**
- 「화면에 꼭 들어가는 정사각형」은 `width: 80vmin; height: 80vmin` 이 정답이다. `vw` 로 하면 세로 화면에서 넘친다.

비용 — 없음. 다만 **`vmax` 는 화면 회전에 민감하다** — 긴 쪽이 바뀌면 값이 크게 튄다.

### (4) ★ `svh`/`lvh`/`dvh` — 주소창이 접히는 문제를 셋으로 나눈 것

**언제 쓰나** — 모바일에서 `height: 100vh` 짜리 화면이 **스크롤바 없이 잘리거나 넘칠 때.**

```text
  모바일 브라우저에서 화면 높이는 하나가 아니다

  주소창이 펼쳐진 상태              주소창이 접힌 상태
  +----------------------+          +----------------------+
  | [주소창]             |          |                      |
  +----------------------+          |                      |
  |                      |          |      문서 영역        |
  |     문서 영역         |  <- 작다 |      (더 크다)        |
  |                      |          |                      |
  +----------------------+          +----------------------+
  | [하단 툴바]          |          +----------------------+
  +----------------------+

     small  = svh   가장 작을 때 (UI 가 전부 보일 때)
     large  = lvh   가장 클 때   (UI 가 전부 접혔을 때)
     dynamic= dvh   ★ 지금 이 순간 — 스크롤하는 동안 값이 계속 바뀐다
```

```text
★ headless 실측 — 세 값이 전부 같았다

  창 (innerWidth x innerHeight)   10vh         10svh        10lvh        10dvh
  ------------------------------  -----------  -----------  -----------  -----------
  800 x 513                       51.296875    51.296875    51.296875    51.296875
  500 x 580                       58           58           58           58
  1200 x 313                      31.296875    31.296875    31.296875    31.296875

  가로도 마찬가지였다 (800x600 판)
    100vw = 100svw = 100lvw = 100dvw = 800
```

그림 해설 (한 단계씩):

- **headless 에는 접히는 주소창이 없으므로 세 값이 갈릴 수 없다.** 위 표가 그 결과다.
- 그러니 **이 문서는 셋이 갈리는 것을 재지 못했다.** 「갈린다」는 서술은 전부 명세(css-values-4)에 기댄 것이고, 값이 갈리는 환경은 **모바일 브라우저**다.
- 명세가 정한 성질만 옮기면 — `svh` ≤ `dvh` ≤ `lvh` 이고, **`dvh` 만 스크롤 중에 값이 변한다.**
- `100vh` 는 **`lvh` 와 같게 정의돼 있다**(명세). 그래서 모바일에서 `100vh` 짜리 화면이 주소창에 가려 **아래가 잘리는** 고전 증상이 나온다.
- **`dvh` 가 공짜는 아니다** — 값이 계속 바뀌므로 스크롤 중에 레이아웃이 따라 움직인다. 「잘리지 않는 대신 흔들린다」가 그 대가다.

```text
  셋 중 무엇을 고르나 — 무엇을 받을지 고르는 것이다

    "절대 잘리면 안 된다"           ──> svh    (접히면 아래에 빈 자리)
    "무조건 화면을 꽉 채워야 한다"   ──> lvh    (펼쳐지면 아래가 잘린다)
    "항상 정확히 맞아야 한다"        ──> dvh    (스크롤 중에 움직인다)

  ★ 공짜인 선택지는 없다. 셋 다 무언가를 내준다.
```

비용 — 셋 중 무엇을 고르든 대가가 있다. **`svh` = 항상 들어가지만 접힌 상태에서 빈 자리가 남는다** · **`lvh` = 꽉 차지만 펼친 상태에서 잘린다** · **`dvh` = 항상 맞지만 움직인다.**

> **동적 뷰포트(dynamic viewport)** — 브라우저 UI 가 접히고 펼쳐짐에 따라 지금 이 순간 실제로 보이는 영역.\
> 예: 모바일에서 아래로 스크롤해 주소창이 접히면 `dvh` 값이 그만큼 커진다. (★ 이 문서에서는 **재지 못했다** — headless 에 주소창이 없다.)

### (5) 컨테이너 단위 — 「가장 가까운 등록된 조상」을 100으로 놓는다

**언제 쓰나** — 같은 카드 컴포넌트를 사이드바와 본문에 함께 붙일 때. **창이 아니라 자기가 놓인 칸**에 맞춰야 한다.

```text
카드 셋을 전부 300x150px 로 만들고 container-type 만 바꿔 쟀다
(Chrome 151, 창 800x600 — 뷰포트 800 x 513)

  container-type: inline-size
     50cqw   -> 150      50cqi   -> 150     <- 카드 폭 300 의 50%
     50cqb   -> 256.5    50cqh   -> 256.5   <- ★ 카드가 아니라 뷰포트 높이 513 의 50%
     50cqmin -> 150      50cqmax -> 256.5

  container-type: size
     50cqw   -> 150      50cqb   -> 75      <- 두 축 다 카드(300 x 150)
     50cqmin -> 75       50cqmax -> 150

  container-type 선언 없음
     50cqw   -> 400      50cqi   -> 400     <- ★ 뷰포트 폭 800 의 50%
     50cqb   -> 256.5
     50cqmin -> 256.5    50cqmax -> 400
```

```text
  무엇을 100 으로 놓았나 — 축마다 따로 정해진다

  container-type: inline-size
    인라인 축(가로)  ──> 카드 300      (컨테인먼트가 걸렸다)
    블록  축(세로)  ──> 뷰포트 513    (안 걸렸다 — 위로 새어 나간다)

  container-type: size
    인라인 축(가로)  ──> 카드 300
    블록  축(세로)  ──> 카드 150

  선언 없음
    두 축 모두      ──> 뷰포트 (작은 뷰포트 = svw/svh)
```

그림 해설 (한 단계씩):

- ★ **`container-type` 을 선언하지 않아도 단위가 죽지 않는다.** 조용히 **작은 뷰포트**로 떨어진다(`50cqw` = 400 = 뷰포트 폭 800 의 절반).\
  「아무 일도 안 일어난다」가 아니라 **엉뚱한 기준으로 값이 나온다** — 이 주제에서 가장 잡기 어려운 버그다.
- ★ **`inline-size` 는 한 축만 컨테인먼트한다.** 그래서 `cqb`·`cqh` 는 **카드를 건너뛰고 뷰포트**를 봤다(256.5 = 513의 절반).\
  「컨테이너를 만들었으니 `cqb` 도 되겠지」가 조용히 깨진다.
- **`cqmin`/`cqmax` 는 그 둘을 섞는다** — `inline-size` 판에서 `cqmin` 이 카드(150)를, `cqmax` 가 뷰포트(256.5)를 골랐다.
- **두 축을 다 쓰려면 `container-type: size`** 인데, 그것은 **높이까지 컨테인먼트**한다는 뜻이라 대가가 크다. 그 대가의 정본은 [목록의 **40번 주제**](../40-container-and-style-queries/)다.

비용 — `container-type` 은 컨테인먼트를 켜는 선언이다. **레이아웃 격리가 공짜가 아니라는 점**이 이 주제가 아니라 [목록의 **40번 주제**](../40-container-and-style-queries/)에서 다뤄진다.

```html demo
<div class="card wide"><p class="t">cqi</p></div>
<div class="card slim"><p class="t">cqi</p></div>
<style>
  .card { container-type: inline-size; border: 2px solid #2563eb;
          margin-bottom: 8px; }
  .wide { width: 400px; }
  .slim { width: 150px; }
  .t    { font-size: 10cqi; margin: 0; }
</style>
```

> **보이는 것** — 파란 테두리 상자 두 개에 똑같이 `cqi` 라고 적혀 있는데, **위(400px) 상자의 글자가 아래(150px) 상자의 글자보다 훨씬 크다.** 글꼴 선언은 둘 다 `10cqi` 로 같다 — 각자 자기 카드 폭의 10% 를 잰 것이다.\
> **바꿔 볼 것** — `.t` 의 `font-size: 10cqi` → `10vw` 로 바꾸면 → **두 글자 크기가 같아진다**(창 하나만 보므로 카드 폭과 무관해진다)

*(Chrome 151 headless 실측: `.wide .t` `font-size: 40px` · `.slim .t` `font-size: 15px`.)*

### (6) 두 단위 무리를 한 그림에 놓는다

**언제 쓰나** — 「이 값은 무엇이 바뀌면 따라 바뀌나」를 고를 때.

```text
  무엇이 바뀌면 값이 바뀌나

    %      ──> 부모 상자가 바뀌면          (33번)
    em     ──> 그 요소의 글꼴이 바뀌면     (33번)
    rem    ──> 루트 글꼴이 바뀌면          (33번)
    vw/vh  ──> 창이 바뀌면                 (이 편)
    dvh    ──> 창 + 브라우저 UI 가 움직이면 (이 편)
    cqi    ──> 가장 가까운 등록 컨테이너가 바뀌면 (이 편)
```

```text
  기준을 찾아 올라가는 경로가 다르다

    %                        cqi
    자기                     자기
     ↓ 한 칸                  ↓ 조상들을 훑어 올라가며
    부모  <- 여기서 멈춘다     container-type 이 선언된 첫 상자를 찾는다
                              못 찾으면 -> 작은 뷰포트로 떨어진다
```

그림 해설 (한 단계씩):

- **`%` 는 한 칸만 본다**(부모). 부모가 크기를 안 정했으면 거기서 풀리지 않는다.
- **`cqi` 는 조상을 훑는다.** 그래서 중간에 어떤 상자가 끼어도 컨테이너만 같으면 값이 같다.
- **`vw`/`vh` 는 아무것도 안 훑는다** — 문서가 몇 겹 안에 있든 창 하나다.
- 이 차이가 「같은 컴포넌트를 사이드바에 넣었더니 글자가 안 줄어든다」를 설명한다 — `vw` 로 짰기 때문이다.

## 문법 — 형태와 어디서 헷갈리나

### 최소 형태

```css
.a { width: 100vw;  height: 100vh;  }   /* 창 기준 */
.b { width: 80vmin;                 }   /* 짧은 쪽 기준 */
.c { height: 100dvh;                }   /* 지금 보이는 높이 */
.card { container-type: inline-size; }  /* ★ 먼저 등록해야 한다 */
.card .t { font-size: 10cqi;        }   /* 그 컨테이너의 인라인 크기 10% */
```

### 헷갈리는 자리

| 적은 것 | 실제 | 왜 |
|---|---|---|
| `width: 100vw` | **785 가 아니라 800** | `vw` 는 스크롤바 자리를 포함한다((2)) |
| `container-type` 없이 `10cqi` | **뷰포트의 10%** | 컨테이너를 못 찾으면 작은 뷰포트로 떨어진다((5)) |
| `container-type: inline-size` + `cqb` | **뷰포트 높이 기준** | 블록 축은 컨테인먼트되지 않았다((5)) |
| `height: 100vh` (모바일) | `100lvh` 와 같다 | 명세가 그렇게 정의했다 — 주소창에 가려 잘린다((4)) |
| `@container (min-width: 10cqi)` | 질의 안에서는 다른 규칙 | 질의 문법의 정본은 [목록의 **40번 주제**](../40-container-and-style-queries/) |

### 금지에 가까운 형태

```css
/* 전체 폭 배너를 vw 로 만들기 */
.banner { width: 100vw; }         /* 세로 스크롤이 생기는 순간 가로 스크롤이 따라 생긴다 */

/* 컨테이너 등록 없이 컨테이너 단위 쓰기 */
.card .title { font-size: 5cqi; } /* 조용히 창 기준이 된다 — 에러도 경고도 없다 */

/* 컨테이너 자신에게 컨테이너 단위 쓰기 */
.card { container-type: inline-size; padding: 5cqi; }
/* 자기 크기가 자기 패딩을 정하는 순환이 된다 — 질의의 같은 제약은 40번 주제 */
```

## 구현 세부사항 대 언어 보장

| 무엇 | 어느 쪽 |
|---|---|
| `1vw` = 뷰포트 폭의 1%, **스크롤바 포함** | **명세**(css-values-4) |
| `100vh` 가 `100lvh` 와 같은 것 | **명세**(css-values-4) |
| `svh` ≤ `dvh` ≤ `lvh` 이고 `dvh` 만 변하는 것 | **명세** — ★ 이 문서는 **갈리는 것을 재지 못했다**(headless 에 주소창 없음) |
| 컨테이너를 못 찾을 때 **작은 뷰포트**로 떨어지는 것 | **명세**(css-contain-3) — 실측으로도 확인했다 |
| `inline-size` 에서 `cqb` 가 뷰포트를 보는 것 | **명세**(축별 컨테인먼트) — 실측으로 확인했다 |
| 스크롤바 폭이 **15px** 인 것 | **환경**(이 머신의 Chrome headless). 오버레이 스크롤바면 0 일 수 있다 |
| `innerHeight` 가 창 높이보다 작은 것(600 → 513) | **Chrome headless 구현** — UI 높이가 잡힌다 |
| `--window-size=375` 가 **500 으로 올라간 것** | **Chrome 구현 하한** — 375 판은 재지 못했다 |
| 오버레이 스크롤바에서 `100vw` 가 어떻게 되는가 | **미실행** — 이 환경에서 못 재는 조건이다 |

## 어디서 틀리나

### 1. 전체 폭 배너를 `100vw` 로 만든다

세로 스크롤바가 생기는 순간 **정확히 스크롤바 폭만큼** 가로 스크롤이 생긴다(실측 15px).\
고치는 법 — `width: 100%` 를 쓴다. 꼭 창 폭이 필요하면 부모에서 `overflow-x` 로 잘라 낸다.

### 2. `container-type` 을 안 쓰고 `cqi` 를 쓴다

**에러도 경고도 없이** 창 기준으로 계산된다(실측: `50cqw` 가 400 — 뷰포트 800 의 절반).\
증상이 「값이 이상하다」뿐이라 **진단 3창** 중 `getComputedStyle` 창으로만 잡힌다 — `cssRules` 에는 멀쩡히 담겨 있다([07번](../07-syntax-and-error-recovery/2-summary.md)).

### 3. `container-type: inline-size` 로 `cqb`·`cqh` 를 쓴다

블록 축은 컨테인먼트되지 않아 **뷰포트 높이**를 본다(실측 256.5 = 513의 절반).\
고치는 법 — 두 축이 다 필요하면 `container-type: size` 로 올린다. 그 대가는 [목록의 **40번 주제**](../40-container-and-style-queries/)가 정본이다.

### 4. 모바일에서 `height: 100vh` 로 화면을 채운다

`100vh` = `100lvh` 라 **주소창이 펼쳐진 상태에서 아래가 잘린다.**\
고치는 법 — `100dvh`(항상 맞지만 스크롤 중에 움직인다) 또는 `100svh`(안 잘리지만 빈 자리가 남는다).\
★ 이 문서는 **그 차이를 재지 못했다**((4)).

### 5. `vmax` 로 정사각형을 만든다

`vmax` 는 **긴 쪽**이므로 세로 화면에서 화면을 넘긴다. 「화면에 꼭 들어가는」 쪽은 `vmin` 이다.

### 6. 컨테이너 단위를 컨테이너 자신에게 쓴다

자기 크기가 자기 패딩·글꼴을 정하는 순환이 된다. 값은 **안쪽 요소**에만 쓴다.

## 언제 쓰고 언제 안 쓰나

| 상황 | 고를 단위 | 왜 |
|---|---|---|
| 화면을 채우는 히어로 높이 (모바일 포함) | `dvh` 또는 `svh` | `vh`(=`lvh`)는 주소창에 가려 잘린다 |
| 전체 폭 배너 | **`100%`** | `100vw` 는 스크롤바 때문에 가로 스크롤을 만든다 |
| 화면에 꼭 들어가는 정사각 요소 | `vmin` | 가로·세로 어느 쪽이 짧든 들어간다 |
| 재사용되는 카드 안의 치수 | `cqi` | 창이 아니라 **놓인 칸**을 따라간다 |
| 세로쓰기까지 고려한 축 | `vi`/`vb` | 물리 축이 아니라 논리 축을 본다([목록의 **32번 주제**](../32-logical-properties-and-writing-mode/)) |
| 본문 글꼴 | (여기 아님) | 뷰포트 단위 단독은 사용자 확대를 무력화한다 — [35번](../35-calc-clamp-min-max/2-summary.md)의 `clamp()` 로 감싼다 |
| 부모 하나만 따라가면 되는 칸 | `%` | 가장 싸고 예측이 쉽다([33번](../33-length-units/2-summary.md)) |

## 핵심 문장

- **`vw` 는 스크롤바를 포함하고 `%` 는 포함하지 않는다.** 실측 차이 15px 이 가로 스크롤의 정체다.
- **`100vh` = `100lvh`** 이므로 모바일에서 아래가 잘린다. 셋(`svh`/`lvh`/`dvh`)은 **잘림 / 빈 자리 / 흔들림** 중 무엇을 받을지 고르는 선택지다.
- ★ **이 문서는 셋이 갈리는 것을 재지 못했다** — headless 에는 접히는 주소창이 없어 세 값이 같게 나왔다.
- **컨테이너 단위는 `container-type` 을 선언한 가장 가까운 조상**을 본다. 못 찾으면 **조용히 작은 뷰포트**로 떨어진다.
- **`inline-size` 는 한 축만 컨테인먼트한다** — `cqb`·`cqh` 는 카드를 건너뛰고 뷰포트를 봤다.

## 용어 풀이

- **뷰포트(viewport)** — 문서가 그려지는 창 안쪽 영역. 예: 실측에서 창 800px 중 785px 이 문서 자리, 15px 이 세로 스크롤바였다.
- **`vw` / `vh`** — 뷰포트 폭 / 높이의 1%. **스크롤바 자리를 포함한다.**
- **`vmin` / `vmax`** — 뷰포트의 짧은 쪽 / 긴 쪽의 1%. 예: 1200×313 판에서 `10vmin` 31.3, `10vmax` 120.
- **`vi` / `vb`** — 인라인 축 / 블록 축의 1%. 가로쓰기에서는 각각 `vw`/`vh` 와 같았다.
- **작은 뷰포트(small viewport, `sv*`)** — 브라우저 UI 가 전부 보일 때의 영역. 가장 작다.
- **큰 뷰포트(large viewport, `lv*`)** — UI 가 전부 접혔을 때의 영역. 가장 크다. `100vh` 가 이것과 같다.
- **동적 뷰포트(dynamic viewport, `dv*`)** — 지금 이 순간 실제로 보이는 영역. 스크롤 중에 값이 변한다. ★ 이 문서에서 **재지 못했다**.
- **`container-type`** — 그 요소를 질의·단위의 기준 컨테이너로 등록하는 속성. `inline-size` 는 인라인 축만, `size` 는 두 축을 컨테인먼트한다.
- **`cqw`/`cqh`** — 컨테이너의 폭/높이의 1%. **`cqi`/`cqb`** — 컨테이너의 인라인/블록 크기의 1%. 가로쓰기에서 `cqi`=`cqw`, `cqb`=`cqh` 였다.
- **컨테인먼트(containment)** — 상자 안의 레이아웃 계산을 밖과 끊는 것. 끊겨 있어야 「컨테이너 크기 → 안쪽 크기」가 순환 없이 풀린다.
- **스크롤바 폭** — 세로 스크롤바가 차지하는 가로 길이. 예: 이 환경에서 15px. **환경마다 다르고 0 일 수도 있다.**

## 더 들어가면

- **`svw`/`lvw`/`dvw` 도 있다.** 가로에도 세 종류가 정의돼 있지만, 가로는 브라우저 UI 로 줄어드는 일이 드물어 실무 의미가 작다.\
  실측에서도 `100vw` = `100svw` = `100lvw` = `100dvw` = 800 으로 전부 같았다.
- **`vh` 를 JS 로 대체하던 옛 관용구**가 있다 — `--vh: ${innerHeight * 0.01}px` 를 `resize` 마다 다시 쓰는 방식.\
  `dvh` 가 그것을 CSS 안으로 들여온 것이다. 변수를 JS 로 쓰는 문법 자체는 [36번](../36-custom-properties/2-summary.md)에 있다.
- **`overflow: hidden` 을 `html` 에 걸면 스크롤바가 사라져 `100vw` 문제가 「사라진 것처럼」 보인다.**\
  실제로는 스크롤을 못 하게 만든 것이라 접근성 문제를 새로 만든다. ★ 이 조합은 **이 문서에서 재지 않았다.**
- **컨테이너 단위는 `@container` 질의 없이도 쓸 수 있다.** 질의는 「조건에 따라 규칙을 갈라 쓰는 것」이고 단위는 「길이를 비율로 쓰는 것」이라 서로 독립이다.\
  실무에서는 **단위만 써도 절반은 해결**된다 — 글꼴·패딩이 칸에 따라 부드럽게 따라온다. 질의는 **배치가 통째로 바뀌어야 할 때** 꺼낸다([목록의 **40번 주제**](../40-container-and-style-queries/)).
- **`cqmin`/`cqmax` 가 축을 섞는 것**은 `inline-size` 컨테이너에서만 관찰된다 — 한 축은 컨테이너, 한 축은 뷰포트를 보기 때문이다.\
  `container-type: size` 로 올리면 둘 다 컨테이너 안에서 정해져 직관대로 돈다(실측: `cqmin` 75 · `cqmax` 150).
