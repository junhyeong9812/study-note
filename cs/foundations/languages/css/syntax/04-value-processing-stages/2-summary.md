# css/syntax/04 — 값 처리 단계: 지정값·계산값·사용값·실제값 — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [CSS Cascading and Inheritance Level 5](https://drafts.csswg.org/css-cascade-5/) 의 「Value Processing」(specified / computed / used / actual value) 절과 [CSSOM](https://drafts.csswg.org/cssom/) 의 「resolved values」 절. 열어서 확인한 것만 적었다.
> **실행 검증** — 이 문서의 모든 값은 **Google Chrome 151.0.7922.173** headless 에 실제로 띄워 `getComputedStyle`·`getBoundingClientRect`·`offsetWidth` 로 읽은 것이다. 하네스는 [3-answer.md](3-answer.md) 의 `## 실행 검증` 절에 있다.\
> **엔진은 Chrome 하나다** — Firefox 155.0.1 은 이 환경에서 headless 산출이 조용히 실패하고 WebKit 은 없다. 「두 엔진에서 확인했다」고 적지 않는다.
> **버전** — CSS 에는 언어 버전이 없다. 네 단계 구분은 CSS2 부터 있었고, `getComputedStyle` 이 「해석값」을 돌려준다는 규정은 CSSOM 의 것이다. 1/64px 격자 같은 수치는 **Chrome 151 의 구현 세부**이며 그 자리에 표시해 두었다.
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 값은 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

**값 처리 = 「50%」라고 적은 종이가 네 번 다시 쓰여 마지막에 화면의 점이 되는 과정이다.**

주문서가 공장을 지나는 것에 비유한다. 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 주문서에 적힌 글자 `50%` | **지정값** — 캐스케이드가 뽑은 그 선언의 값 |
| 사무실이 단위를 정리한 판 | **계산값** — `em`·`thin`·`red` 가 절대값으로 바뀐 판 |
| 현장에서 자를 대고 잰 판 | **사용값** — `%`·`auto` 가 실제 레이아웃 치수가 된 판 |
| 기계가 실제로 자른 치수 | **실제값** — 장치 격자에 맞춘 값 |
| 창구에서 보여 주는 서류 | **해석값** — `getComputedStyle` 이 돌려주는 것 |

- 네 단계는 **속성마다 어디까지 가느냐가 다르다.** `color` 는 계산값에서 끝나고, `width` 는 네 단계를 다 간다.
- **자식이 물려받는 것은 계산값이다**(사용값이 아니다). 그래서 부모의 `em` 을 자식이 다시 계산하지 않는다.
- **`getComputedStyle` 은 「계산값」이 아니다.** 이름이 거짓말이다 — 속성마다 계산값을 줄 때도 있고 사용값을 줄 때도 있다. 이것이 이 주제의 결론이다.

```text
  선언 width: 50%
      │
      ├─ ① 지정값   50%          캐스케이드가 뽑은 값 (01번)
      │              ↓  단위·키워드 정리 (em → px, thin → 1px, red → rgb)
      ├─ ② 계산값   50%          ← 상속되는 것은 이 판이다 (03번)
      │              ↓  레이아웃을 돌려 %·auto 를 푼다
      ├─ ③ 사용값   200px        ← 부모 content 폭 400px 이 여기서 들어온다
      │              ↓  장치 격자에 맞춘다
      └─ ④ 실제값   200px

  getComputedStyle 은 ②나 ③ 중 하나를 준다 — 속성이 정한다
```

실무에서 이게 터지는 자리는 **JS 로 값을 읽어 계산할 때**다.\
`getComputedStyle(el).width` 가 `"200px"` 이라 숫자를 뽑아 썼는데, 같은 코드가 다른 요소에서 `"50%"` 나 `"auto"` 를 돌려주고 `parseFloat` 가 `50`·`NaN` 을 낸다.\
**무엇이 조건인지**가 이 주제의 실용 과녁이다.

> **캐스케이드(cascade)** — 한 요소의 한 속성에 걸린 선언 여럿 중 하나를 뽑는 알고리즘. 정본은 [01번 주제](../01-cascade-and-priority/2-summary.md).\
> 예: `color` 에 선언이 다섯 줄 걸려도 지정값은 그중 이긴 하나다.

> **해석값(resolved value)** — `getComputedStyle` 이 실제로 돌려주는 값. CSSOM 이 속성마다 「계산값을 준다 / 사용값을 준다」를 따로 규정한다.\
> 예: `width` 는 사용값 쪽, `color` 는 계산값 쪽이다.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 세 질문을 둔다.

1. `width: 50%` 하나가 **네 단계에서 각각 무엇인가.** `em` 은 어느 단계에서 픽셀이 되는가.
2. **`getComputedStyle` 은 어느 단계를 보여 주는가.** 같은 속성인데 답이 달라지는 조건은 무엇인가.
3. 「**계산값이 상속된다**」는 말이 실제로 무엇을 뜻하는가 — 자식은 왜 부모의 `em` 을 다시 계산하지 않는가.

## 동작 방식

### (1) 네 단계를 한 예제로 관통시킨다 — `width: 50%`

**언제 쓰나** — 치수가 예상과 다를 때. 어느 단계에서 어긋났는지를 먼저 잡아야 고칠 자리가 나온다.

```html
<div id="wrap" style="width:400px">
  <p id="half" style="width:50%">…</p>
</div>
```

```text
① 지정값 specified     50%
      캐스케이드가 뽑은 그 선언의 값 그대로다.
      아무도 선언 안 했으면 여기서 상속·초기값이 채워진다 (03번)
                ↓
② 계산값 computed      50%          <- % 는 아직 % 다
      단위와 키워드만 정리한다. em·rem·ex 는 여기서 px 이 되고
      thin 은 1px, red 는 rgb(255,0,0) 이 된다.
      레이아웃을 아직 안 돌렸으므로 % 는 풀 수 없다
                ↓
③ 사용값 used          200px        <- 부모 content 폭 400px 이 들어왔다
      레이아웃을 돌려야 나오는 값. auto·%·min/max 제약이 여기서 풀린다
                ↓
④ 실제값 actual        200px
      장치 격자·반올림을 적용한 최종값
```

실측으로 확인한 것 — 같은 `#half` 를 **렌더된 채로** 읽으면 `200px`, **`display: none`** 으로 만들어 읽으면 `50%` 가 나온다.

```text
렌더됨       getComputedStyle(#half).width = 200px     <- ③ 사용값을 준다
display:none getComputedStyle(#hidden).width = 50%     <- ③ 이 없으니 ② 계산값을 준다
```

그림 해설 (한 단계씩):

- **②와 ③ 사이에 레이아웃이 있다.** 그래서 상자가 없는 요소(`display: none`)는 ③이 존재하지 않는다.
- 그때 `getComputedStyle` 은 **②로 되돌아가 계산값을 준다.** 이것이 「같은 코드가 다른 값을 돌려주는」 조건이다.
- ④는 대개 ③과 같아 보인다. 갈리는 자리는 아래 (4)에 따로 둔다.

비용 — ③을 읽으면 **레이아웃이 강제로 돌 수 있다**(reflow). 루프 안에서 `getComputedStyle(el).width` 를 읽으면 그때마다 레이아웃이 동기적으로 도는 경로가 생긴다.

> **지정값(specified value)** — 캐스케이드·상속·초기값을 거쳐 그 속성에 배정된 값. 선언에 적은 글자에 가장 가깝다.
> **계산값(computed value)** — 상대 단위와 키워드를 정리한 값. **상속되는 것이 이 판이다.**
> **사용값(used value)** — 레이아웃을 돌려 `%`·`auto` 를 푼 값.
> **실제값(actual value)** — 장치가 실제로 쓸 수 있게 맞춘 값.

### (2) `em` 은 계산값 단계에서 픽셀이 된다

**언제 쓰나** — 중첩된 요소에서 `em` 이 폭주할 때, 또는 자식에서 값이 다시 계산될 줄 알았는데 안 될 때.

```text
같은 부모·자식 판에서 네 속성을 함께 읽었다 (Chrome 151 실측)

  #parent { font-size:20px; text-indent:2em; line-height:1.5; letter-spacing:0.1em }
  #child  { font-size:10px }                       <- 자식은 글꼴만 줄였다

  속성             부모      자식      자식에서 다시 계산됐나
  ---------------  --------  --------  ---------------------
  font-size        20px      10px      (자기 선언)
  text-indent      40px      40px      아니다  <- 2em 이 부모 자리에서 40px 이 됐다
  letter-spacing   2px       2px       아니다  <- 0.1em 이 부모 자리에서 2px 이 됐다
  line-height      30px      15px      ★ 그렇다
```

그림 해설 (한 단계씩):

- **자식은 「2em」이라는 글자를 받지 않는다.** 부모의 계산값 `40px` 을 받는다. 그래서 자식 글꼴이 절반이 돼도 들여쓰기는 그대로다.
- **`line-height` 의 무단위 숫자만 예외**다. 그 값은 **계산값이 「숫자 1.5」 자체**라서 숫자가 내려오고, 자식이 자기 `font-size` 에 곱한다.\
  무단위로 쓰라는 관례가 여기서 나온다 — `1.5em` 으로 쓰면 `30px` 이 내려와 자식 글꼴이 10px 이어도 줄높이가 30px 이 된다.
- 반대로 **`font-size: 1.5em` 은 곱해진다.** 부모의 계산된 px 에 곱하므로 중첩할수록 커진다.

```html demo
<ul class="em">
  <li>1단계
    <ul><li>2단계
      <ul><li>3단계</li></ul>
    </li></ul>
  </li>
</ul>
<style>
  .em, .em ul { font-size: 1.5em; padding-left: 24px; margin: 0; }
</style>
```

> **보이는 것** — 「1단계」·「2단계」·「3단계」 글자가 **안으로 들어갈수록 눈에 띄게 커진다.** 각 단계의 `font-size` 는 `1.5em` 으로 똑같이 적혀 있지만, `em` 이 「부모의 **계산된** 글자 크기」라서 16 → 24 → 36 → 54px 로 곱해진다.\
> **바꿔 볼 것** — `1.5em` → `1.5rem` 으로 바꾸면 → **세 단계가 모두 24px 로 같아진다**(`rem` 은 루트 글꼴만 본다)

*(Chrome 151 headless 실측: 루트 `16px` · 1단계 `24px` · 2단계 `36px` · 3단계 `54px`.)*

```html demo
<div class="outer">
  <span class="big">AAAA</span>
  <span class="small">AAAA</span>
</div>
<style>
  .outer { font-family: monospace; font-size: 20px; letter-spacing: 0.4em; }
  .small { font-size: 10px; }
</style>
```

> **보이는 것** — 오른쪽 작은 `AAAA` 의 **글자 사이 간격이 글자 크기에 비해 지나치게 넓어 보인다.** `letter-spacing: 0.4em` 은 부모(20px) 자리에서 이미 `8px` 로 계산됐고, 자식은 그 `8px` 을 그대로 물려받는다. 자식에서 다시 계산했다면 `4px` 이 나왔을 것이다.\
> **바꿔 볼 것** — `.small` 에 `letter-spacing: 0.4em` 을 **다시 선언하면** → **간격이 절반(4px)으로 줄어 비율이 맞는다**(자식 자리에서 새로 계산되므로)

*(Chrome 151 headless 실측: `.outer` `letter-spacing: 8px` · `.big` `8px` · `.small` `8px`(`font-size: 10px`).)*

비용 — 없음. 다만 **`em` 을 쓴 값이 상속되면 그 뒤로는 고정된 픽셀**이라, 「반응형으로 따라오겠지」라는 기대가 조용히 깨진다.

### (3) `getComputedStyle` 이 무엇을 주나 — 속성이 정한다

**언제 쓰나** — JS 로 CSS 값을 읽는 모든 자리. **이 절이 이 주제의 결론이다.**

CSSOM 은 속성을 두 무리로 나눈다. 실측 표다.

```text
읽은 값 (Chrome 151, 부모 폭 400px)

  선언                      렌더됨일 때        display:none 일 때   어느 단계인가
  ------------------------  -----------------  -------------------  --------------
  width: 50%                200px              50%                  ③ / ②
  width: auto               400px              auto                 ③ / ②
  height: 50% (부모 auto)   24px               —                    ③ (auto 로 풀렸다)
  margin: auto              150px              —                    ③
  margin: 10%               40px               —                    ③ (부모 '폭'의 10%)
  transform: translateX(50%) matrix(1,0,0,1,100,0)  none             ③ / (상자 없음)
  ------------------------  -----------------  -------------------  --------------
  width: 3em (글꼴 20px)    60px               60px                 ② 어느 쪽이든 같다
  letter-spacing: 0.1em     2px                2px                  ②
  color: red                rgb(255, 0, 0)     rgb(255, 0, 0)       ②
  border-width: thin/medium/thick  1px/3px/5px  〃                  ②
  line-height: normal       normal             〃                   ② (절대화 안 한다)
  line-height: 1.5 (글꼴 20px) 30px            30px                 ★ 아래 참고
```

그림 해설 (한 단계씩):

- **위 무리(레이아웃에 걸린 속성)만 사용값을 준다.** `width`·`height`·`margin`·`padding`·`top` 계열과 `transform` 이 여기 속한다.
- 아래 무리는 **언제나 계산값**이다. 그래서 `color` 를 `display:none` 인 요소에서 읽어도 잘 나온다.
- **`margin: 10%` 가 세로도 `40px`** 인 것에 주의한다 — 상하 마진의 `%` 도 **부모의 인라인 크기(가로)** 기준이다. 이것은 ③에서 풀리는 규칙이다.
- **`transform` 은 상자가 없으면 `none`** 이다(실측). 값이 사라진 게 아니라 **사용값을 만들 수 없어서** 그렇다.

**★ `line-height: 1.5` 가 이 표의 함정이다.**

```text
명세가 말하는 계산값        Chrome 151 이 보여 주는 값
+----------------------+   +----------------------+
| 숫자 1.5 그 자체     |   | "30px"               |
+----------------------+   +----------------------+
        ↓                          ↓
자식이 1.5 를 받아         읽는 사람은 "계산값이 30px 이구나"
자기 글꼴에 곱한다          라고 오해한다

증거: 자식(font-size:10px)의 line-height 는 15px 이었다.
      30px 이 상속됐다면 15px 이 나올 수 없다.
```

- 그래서 **`getComputedStyle` 의 출력만으로 「계산값이 무엇인가」를 결론짓지 못한다.** 상속 결과를 같이 봐야 안다.
- `display: none` 으로 만들어도 여전히 `30px` 이었다 — 사용값이 아니라 **CSSOM 이 정한 직렬화 형식**이다.

비용 — `getComputedStyle` 자체는 싸지만 **사용값을 주는 속성을 읽으면 레이아웃이 동기적으로 돈다.** 읽기와 쓰기를 번갈아 하면 그 수만큼 레이아웃이 돈다.

### (4) 실제값 — 격자에 맞춰지는 마지막 단계

**언제 쓰나** — 1px 짜리 선이 사라지거나, 세 칸이 딱 안 맞아 1px 이 남을 때.

```text
같은 요소를 세 창구로 읽었다 (Chrome 151, devicePixelRatio = 1)

  선언                      getComputedStyle  getBoundingClientRect  offsetWidth
  ------------------------  ----------------  ---------------------  -----------
  width: 100.6px (렌더됨)   100.594px         100.59375              101
  width: 100.6px (none)     100.6px           —                      —
  width: 33.333% of 333px   110.984px         110.984375             111
```

그림 해설 (한 단계씩):

- `100.6px` 이 `100.59375px` 이 된 것은 **엔진이 길이를 1/64px 격자에 저장**하기 때문이다(`6438/64 = 100.59375`).\
  **이것은 Chrome 151 의 구현 세부다** — 명세가 정한 수치가 아니다.
- `getComputedStyle` 은 그 격자값을 **소수 셋째 자리로 잘라** `100.594px` 로 보여 준다. 셋은 **같은 값의 다른 표기**다.
- `offsetWidth` 만 **정수로 반올림**한다 — 레이아웃 계산에 쓰면 안 되는 이유가 이것이다.
- `display: none` 이면 격자를 안 탄 `100.6px` 이 그대로 나온다. **③이 없으면 ④도 없다.**

**또 하나의 실제값 — 얇은 테두리**

```text
선언                      border-top-width    상자 높이
------------------------  ------------------  ------------------
border: 0.3px solid       1px                 24 → 26  (위아래 1px 씩)
border: 0.6px solid       1px                 24 → 26
border: 1px solid         1px                 24 → 26
(테두리 없음)             0px                 24
```

- **`0.3px` 을 줬는데 `1px` 이 됐다.** 장치가 0.3픽셀을 칠할 수 없으니 최소 1픽셀로 올린 것이다.
- **Chrome 151 은 이 반올림을 이르게 한다** — `display: none` 으로 만들어도 `1px` 이 나왔다. 명세상 이것은 실제값 단계의 일인데 계산값 자리에서 이미 보인다. **관찰이지 보장이 아니다.**
- 실무 함의는 반대쪽이다 — 고해상도 화면(`devicePixelRatio` 2\~3)에서는 `0.5px` 테두리가 진짜 반 픽셀로 그려질 수 있어 **머신마다 다르게 보인다.** *(이 환경은 `devicePixelRatio = 1` 이라 그 경우는 확인하지 못했다.)*

비용 — 없음. 다만 **정수 픽셀을 가정한 레이아웃 계산은 깨진다.** `width: 33.333%` 셋이 부모를 정확히 채우지 않는 것이 그 결과다.

### (5) 상속되는 것은 ②다 — 03번과 이어지는 자리

**언제 쓰나** — 「부모에 쓴 값이 자식에서 왜 저 값이지」를 설명할 때.

```text
부모                                  자식
+-------------------------------+     +-------------------------------+
| ① 지정값   2em                |     | 바구니가 비었다               |
|      ↓                        |     |      ↓                        |
| ② 계산값   40px  ─────────────────→ | ② 계산값 40px 을 그대로 받는다 |
|      ↓                        |     |      ↓                        |
| ③ 사용값   40px               |     | ③ 자기 레이아웃으로 계산      |
+-------------------------------+     +-------------------------------+
        ↑                                      ↑
  상속이 건너가는 층은 여기다            ①도 ③도 아니다
```

- **①이 상속되지 않는 이유** — 그러면 자식마다 `em` 을 다시 풀게 되어 부모의 글꼴 변경이 자손 전체를 흔든다.
- **③이 상속되지 않는 이유** — 사용값은 그 요소의 상자에 딸린 값이라 다른 상자에 의미가 없다.
- 그래서 [03번 주제](../03-inheritance-and-global-keywords/2-summary.md)의 `inherit` 도 정확히 「부모의 **계산값**」이다.

비용 — 없음. 이 한 칸을 잘못 알면 03번의 모든 예측이 어긋난다.

## 문법 — 형태와 규칙

CSS 는 문법 표면이 단순하므로 이 절은 「**형태 — 어디서 헷갈리나**」로 읽는다.

### 형태 — 값을 읽는 세 창구

```js
getComputedStyle(el).width            // 해석값 — 속성에 따라 ② 또는 ③
el.getBoundingClientRect().width      // 변환(transform)까지 적용된 실제 상자 (소수)
el.offsetWidth                        // 테두리 포함 · 정수로 반올림 · 변환 미적용
```

- 세 창구는 **같은 것을 묻지 않는다.** `transform: scale(2)` 를 걸면 `getBoundingClientRect` 만 두 배가 된다.
- `getComputedStyle(el).width` 가 **어느 상자의 폭인지는 `box-sizing` 이 정한다.**\
  실측(Chrome 151): `width:200px; padding:15px; border:5px` 인 요소에서 두 모드 다 `200px` 이 나왔고,\
  같은 요소의 `clientWidth` 는 `content-box` 에서 `230`, `border-box` 에서 `190` 이었다.\
  곧 **해석값은 「내가 쓴 `width` 가 가리키던 그 상자」의 사용값**이다([목록의 **15번 주제**](../15-box-model-and-box-sizing/)).

### 금지 사례 — 값이 조용히 어긋나는 형태

```js
parseFloat(getComputedStyle(el).width)          // "auto"·"50%" 면 NaN·50 이 나온다
getComputedStyle(hiddenEl).width                // 상자가 없으면 계산값이 나온다
parseFloat(getComputedStyle(el).lineHeight)     // "normal" 이면 NaN
el.offsetWidth / 3                              // 이미 반올림된 정수를 다시 나눈다
```

**에러는 안 난다.** `NaN` 이 그대로 흘러가 레이아웃 계산 끝에서 어긋난 값으로만 드러난다.

### 어디서 헷갈리나 — 이름 넷

- **`getComputedStyle` 은 계산값을 안 준다.** 이름이 CSSOM 초기부터 굳은 것이고, 규정된 이름은 **해석값**이다.
- **「계산값」과 「사용값」의 구분선은 레이아웃**이다. 레이아웃을 돌려야 아는 값이면 사용값이다.
- **「사용값」과 「실제값」의 구분선은 장치**다. 장치가 못 쓰는 정밀도를 깎으면 실제값이다.
- `%` 는 계산값에서 **`%` 그대로 남는다** — 이것이 `width` 가 두 얼굴을 갖는 이유 전부다.

## 어디서 틀리나

이 주제의 값어치는 전부 여기 있다. 여섯 다 **에러 없이 조용히 어긋난다.**

### 1. `getComputedStyle().width` 를 항상 픽셀이라고 믿는다

```text
개발 중 (요소가 보인다)             배포 후 (탭이 닫혀 있다)
+---------------------------+      +---------------------------+
| width = "200px"           |      | width = "50%"             |
| parseFloat → 200          |      | parseFloat → 50           |
+---------------------------+      +---------------------------+
   계산이 맞는다                      너비가 50px 인 줄 안다
```

`display: none` 인 조상 하나면 충분하다. **조건은** 「**그 요소가 상자를 만드는가**」다.

### 2. `line-height` 계산값이 `30px` 인 줄 안다

`getComputedStyle` 이 `30px` 을 주지만 **상속되는 것은 숫자 `1.5`** 다.\
자식에서 `15px` 이 나오는 것이 그 증거다. 출력만 보고 결론을 내면 03번의 예측이 어긋난다.

### 3. 세로 마진의 `%` 를 높이 기준이라고 생각한다

실측에서 `margin: 10%` 의 상·좌 마진이 **둘 다 40px**(부모 폭 400px 의 10%)이었다.\
**상하 마진·패딩의 `%` 도 가로 기준**이다. 세로 기준이면 높이가 마진에 의존하고 마진이 다시 높이에 의존해 순환한다.

### 4. `width: 33.333%` 셋이 부모를 정확히 채울 거라 기대한다

`333px` 에서 한 칸이 `110.984375px` 이었다. 셋을 더해도 `332.953125px` 로 **부모에 못 미친다.**\
`getComputedStyle` 은 `110.984px` 로 잘라 보여 주므로 **손으로 세 배 해도 검산이 안 맞는다.**\
칸을 정확히 나누려면 `%` 가 아니라 flex·grid 의 `fr` 을 쓴다(목록의 **27번 주제**).

### 5. `offsetWidth` 로 레이아웃 계산을 한다

`100.594px` 인 상자의 `offsetWidth` 는 **`101`** 이다. 이미 반올림된 값이다.\
이것을 다시 나누거나 누적하면 오차가 칸 수만큼 쌓인다. 소수가 필요하면 `getBoundingClientRect()` 를 쓴다.

### 6. `transform` 값을 `display: none` 인 요소에서 읽는다

**`none` 이 나온다**(실측). 선언이 사라진 게 아니라 사용값을 만들 수 없어서다.\
애니메이션 시작 전에 요소를 숨겨 두고 현재 변환을 읽는 코드가 여기서 조용히 깨진다.

## 구현 세부사항 대 언어 보장

| 이 문서의 서술 | 누가 보장하나 |
|---|---|
| 네 단계의 존재와 순서 | **명세**(css-cascade-5 「Value Processing」) |
| 상속되는 것이 **계산값**이라는 것 | **명세** |
| `em`·`thin`·`red` 가 계산값에서 절대화된다는 것 | **명세**(속성마다 「Computed value」 칸에 적혀 있다) |
| `width` 의 해석값이 사용값, `color` 의 해석값이 계산값 | **명세**(CSSOM 「resolved values」) |
| 상자가 없으면 해석값이 계산값으로 떨어지는 것 | **명세**(CSSOM 이 그렇게 규정한다) |
| `line-height: 1.5` 의 해석값이 `"30px"` 로 직렬화되는 것 | **관찰**(Chrome 151). 계산값이 숫자라는 것은 명세 |
| **1/64px 격자**(`100.6px` → `100.59375px`) | **Chrome 151 의 구현 세부.** 명세 수치가 아니다 |
| `0.3px` 테두리가 `1px` 이 되고 그것이 **계산값 자리에서 이미 보이는 것** | **관찰.** 명세상 반올림은 실제값 단계의 일이다 |
| `offsetWidth` 가 정수라는 것 | **CSSOM View 명세**(반올림된 정수로 규정) |
| `devicePixelRatio = 1` 에서의 수치 | **이 환경의 값.** 고해상도에서는 다르다 — 확인 못 했다 |

**★ 이 주제에서 명세와 구현이 갈리는 자리는 ④ 하나다.** ①\~③은 명세로 예측할 수 있지만 ④는 반드시 그 머신에서 재 봐야 한다.

## 언제 쓰고 언제 안 쓰나

| 상황 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 요소의 실제 픽셀 폭이 필요하다 | `getBoundingClientRect().width` | `parseFloat(getComputedStyle(...).width)` |
| 숨겨진 요소의 선언 값을 알고 싶다 | `getComputedStyle` (계산값이 나온다) | 요소를 잠깐 보이게 했다가 되돌리기(레이아웃이 돈다) |
| 줄높이를 자손까지 비례로 주고 싶다 | `line-height: 1.5` (무단위) | `line-height: 1.5em`(계산값이 고정돼 내려간다) |
| 컴포넌트 안에서 글꼴 기준 여백을 주고 싶다 | `em` | `rem`(컴포넌트 글꼴을 안 따라온다) |
| 문서 전체 기준 여백을 주고 싶다 | `rem` | `em`(중첩에서 곱해진다) |
| 칸을 정확히 N등분한다 | flex·grid 의 `fr` | `width: 33.333%` |
| 요소의 변환 상태를 읽는다 | 보이는 상태에서 `getComputedStyle().transform` | `display: none` 상태에서 읽기(`none` 이 나온다) |

판단 규칙 두 줄.

- **읽기 전에 「이 속성은 레이아웃에 걸려 있나」를 먼저 묻는다.** 걸려 있으면 답이 상자 유무에 달라진다.
- **`em` 을 쓸 때는 「이 값이 상속될 것인가」를 묻는다.** 상속될 값이면 계산값이 굳어 내려간다.

## 핵심 문장

- 값은 **지정값 → 계산값 → 사용값 → 실제값** 네 판을 지나고, 속성마다 **어디까지 가느냐가 다르다.**
- **②와 ③ 사이에 레이아웃이 있다.** 그래서 `%`·`auto` 는 ②에서 못 풀리고, 상자가 없는 요소에는 ③이 아예 없다.
- **`getComputedStyle` 은 「계산값」이 아니라 「해석값」이다** — `width`·`margin`·`transform` 은 사용값을, `color`·`letter-spacing`·`border-width` 는 계산값을 준다.
- 그 결과 **같은 코드가 요소에 따라 `"200px"` 과 `"50%"` 를 돌려준다.** 조건은 「상자를 만드는가」다.
- **상속되는 것은 ② 계산값이다.** 그래서 `letter-spacing: 0.1em` 은 부모 자리에서 `2px` 이 되어 자식 글꼴이 절반이 돼도 `2px` 로 남는다.
- **`line-height` 의 무단위 숫자만 예외**다 — 계산값이 숫자 자체라 자식이 다시 곱한다. 무단위로 쓰라는 관례가 여기서 나온다.
- ④는 **머신에 달려 있다.** `100.6px` 이 `100.59375px` 이 되는 1/64 격자는 Chrome 의 구현 세부다.

## 용어 풀이

- **지정값(specified value)** — 캐스케이드·상속·초기값을 거쳐 배정된 값. 선언에 적은 글자에 가장 가깝다.
- **계산값(computed value)** — 상대 단위·키워드를 절대화한 값. **상속되는 단위**다.
- **사용값(used value)** — 레이아웃을 돌려 `%`·`auto` 를 푼 값.
- **실제값(actual value)** — 장치 격자·반올림을 적용한 최종값.
- **해석값(resolved value)** — `getComputedStyle` 이 돌려주는 값. 속성마다 계산값 또는 사용값으로 규정돼 있다.
- **레이아웃(layout·reflow)** — 상자의 위치와 치수를 정하는 단계. 계산값과 사용값의 경계선.
- **`em`** — 그 요소의 `font-size` 계산값 기준(단, `font-size` 자신에 쓰면 부모 기준).
- **`rem`** — 루트 요소의 `font-size` 계산값 기준.
- **`devicePixelRatio`** — CSS 픽셀 하나가 장치 픽셀 몇 개인가. 실제값 단계에 영향을 준다.
- **`offsetWidth`** — 테두리를 포함한 정수 반올림 폭. 변환은 반영하지 않는다.
- **`getBoundingClientRect()`** — 변환까지 적용된 실제 상자. 소수를 준다.
- **1/64px 격자** *(Chrome 구현 세부)* — 엔진이 길이를 저장하는 고정소수점 단위.

## 더 들어가면

- **전환·애니메이션은 계산값 사이를 보간한다.** `width: auto` 가 전환되지 않는 이유는 auto 의 계산값이 `auto` 라서 두 끝 사이에 중간값이 정의되지 않기 때문이다([52번 주제](../52-transition/2-summary.md)).
- **커스텀 속성에는 이 네 단계가 다르게 적용된다.** 등록하지 않은 `--x` 는 계산값이 **토큰 나열 그대로**이고, `@property` 로 `syntax` 를 등록해야 타입이 생겨 보간 대상이 된다(목록의 **36번 주제**·**37번 주제**).
- **`getComputedStyle` 의 두 번째 인자**로 의사 요소를 지정하면 `::before` 의 해석값도 읽힌다 — 생성 콘텐츠가 실제로 무엇이 됐는지 확인하는 유일한 방법이다([목록의 **13번 주제**](../13-pseudo-elements-and-generated-content/)).
- **읽기와 쓰기를 번갈아 하면 레이아웃이 그 수만큼 돈다**(layout thrashing). 읽을 것을 먼저 모아 읽고 쓸 것을 나중에 몰아 쓰면 한 번으로 줄어든다. 이 비용의 정체는 「③ 사용값을 만들려면 레이아웃이 최신이어야 한다」는 이 문서의 ②③ 경계 그 자체다.
