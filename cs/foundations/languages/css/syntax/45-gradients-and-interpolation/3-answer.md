# css/syntax/45 — 그라디언트와 보간 색 공간 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 질문 → 서머리 → 여기 순서다.
> 번호는 [1-question.md](1-question.md)와 1:1 이다. **출력을 먼저, 해설은 그 뒤.**
> ★ 이 주제의 모든 색은 **스크린샷 PNG 의 픽셀을 파이썬으로 읽은 값**이다. 계산값으로는 검증이 성립하지 않는다(10번 참고).

### 1. 위치를 안 적으면 어디에 놓이나

**출력** (400px 폭)

```text
x=0    rgb(253,   2,   0)   빨강
x=100  rgb(126, 128,   0)   빨강과 초록의 중간
x=200  rgb(  0, 254,   0)   초록
```

**세 정지점은 `red 0%`, `lime 50%`, `blue 100%` 에 놓였다.**

**왜 그런가**

```text
  규칙 ①  위치를 안 적은 정지점은 앞뒤 사이에 균등 분배된다
  규칙 ②  첫 정지점의 기본 위치는 0%, 끝 정지점은 100%

  red , lime , blue
   ↓     ↓      ↓
   0%   50%   100%      ← 세 개면 가운데가 50%
```

- x=200(50%)이 순수 초록 `rgb(0, 254, 0)` 인 것이 규칙 ①의 증거다.
- x=100(25%)은 빨강과 초록의 정확한 중간이다 — `rgb(126, 128, 0)`.

### 2. 앞선 것보다 작은 위치를 적으면

**출력** (400px 폭, 검정 배경 위)

```text
20%   rgb(192,  64,   0)   빨강 → 초록 가는 중
75%   rgb( 17, 239,   0)   거의 초록
80%   rgb(  1, 255,   0)   초록
90%   rgb(  0,   0, 255)   파랑 ★  ← 80% 에서 딱 끊겼다
```

**`blue 20%` 는 버려지지 않고 앞 정지점 자리(80%)로 옮겨진다.**\
**그 결과 `lime 80%` 와 `blue 80%` 가 같은 자리가 되어 하드 스톱이 된다.**

**계산값에는 `20%` 가 그대로 남아 있다.**

```text
getComputedStyle().backgroundImage
  → linear-gradient(90deg, rgb(255, 0, 0) 0%, rgb(0, 255, 0) 80%, rgb(0, 0, 255) 20%)
                                                                                ↑ 그대로
```

**왜 그런가**

```text
  적은 대로라면                     실제로 그려진 것
  red 0% → lime 80% → blue 20%      red 0% → lime 80% │ blue 80%
             (뒤로 갈 수 없다)                         └ 하드 스톱
```

- 명세는 「앞선 정지점보다 작은 위치는 **앞선 것의 위치로 올린다**」고 정한다. **버리지 않는다.**
- ★ **계산값이 교정 전 값을 보관한다**는 것이 이 주제의 함정이다. 창 3(`getComputedStyle`)으로는 이 사고를 **절대 못 잡는다.**
- 더 센 예: `red 60%, lime 30%, blue 90%` 는 `lime` 이 60% 로 올라가 **0\~60% 가 전부 순수 빨강**이었다(실측: 20%·25%·50%·60% 픽셀이 전부 `rgb(255, 0, 0)`).

### 3. 정지점 둘을 같은 자리에 두면

**출력**

```text
.a  linear-gradient(90deg, red 50%, blue 50%)   — 400px 폭
    x=100 (25%)  rgb(255, 0,   0)
    x=200 (50%)  rgb(  0, 0, 255)
    중간색이 한 픽셀도 없다.

.b  계산값
    linear-gradient(90deg, rgb(255,0,0) 0px, rgb(255,0,0) 25%,
                           rgb(0,255,0) 25%, rgb(0,255,0) 50%,
                           rgb(0,0,255) 50%, rgb(0,0,255) 100%)
    → 정지점 세 개가 여섯 개로 펴졌다.
```

**왜 그런가**

- 정지점 둘이 같은 자리에 있으면 **사이가 0 이라 보간할 구간이 없다.** 그래서 딱 끊긴다.
- **이중 위치(`red 0 25%`)는 그 정지점을 둘로 펴는 문법**이다. 줄무늬를 절반의 글자 수로 적으려고 있다.
- 실측에서 `.b` 의 픽셀은 x=0 `rgb(255, 0, 0)` · 25% `rgb(0, 255, 0)` · 50% `rgb(0, 0, 255)` 로 **중간색이 전혀 없었다.**

### 4. ★ 같은 두 색, 다른 보간 공간

**출력** (400px 폭, 50% 지점 픽셀)

```text
보간 공간                50% 픽셀
--------------------     -----------------
in srgb                  rgb(127,   0, 127)   ← 가장 어둡다
in srgb-linear           rgb(187,   0, 187)   ← 같은 보라인데 밝다
in oklab                 rgb(140,  83, 162)
in hsl                   rgb(254,   0, 255)   ← 가장 밝다
in hsl longer hue        rgb(  0, 255,   1)   ★ 초록
```

**빨강에도 파랑에도 없는 색이 나오는 것은 `in hsl longer hue` 다.**\
**중간이 가장 어두운 것은 `in srgb`, 가장 밝은 것은 `in hsl` 이다.**

**왜 그런가**

```text
  직교 공간 — 두 점을 직선으로            극좌표 공간 — 각도를 따라 호를 그린다

  빨강 ●───────● 파랑                     빨강(0°) ●
        ↑ 중간. R·B 를 평균하면                      ↘ shorter 는 300° 쪽으로
          둘 다 127 → 전체가 어두워진다      자홍(300°) ●
                                                      ↘
                                             파랑(240°) ●
                                           longer 는 반대로 60°(노랑)·120°(초록)를 지난다
```

- **`in srgb`** — R 과 B 를 각각 평균하면 둘 다 127 이 되어 **밝기가 떨어진다.** 「중간이 탁하다」의 정체다.
- **`in srgb-linear`** — 빛의 양으로 평균한 뒤 감마를 다시 씌우니 187 이 됐다. **같은 색조인데 60 만큼 밝다.**
- **`in hsl`** — 채도(S)와 밝기(L)를 그대로 두고 색상 각도만 도니 **끝까지 쨍하다.**
- **`in hsl longer hue`** — 색상환을 **먼 쪽으로** 돌아 노랑·초록을 지난다. 그래서 두 색 어디에도 없는 초록이 한가운데 나온다.
- **`in oklab`** — 지각적으로 고른 보간이라 **중간에서 밝기가 튀지 않는다.** 대신 채도가 조금 떨어져 「탁한 보라」로 보인다.

### 5. 보간 힌트

**출력** (400px 폭)

```text
선언                                       25% 픽셀             50% 픽셀
-----------------------------------------  -----------------   -----------------
linear-gradient(90deg, red, blue)          rgb(191, 0,  64)    rgb(127, 0, 127)
linear-gradient(90deg, red, 20%, blue)     rgb(114, 0, 140)    rgb( 65, 0, 189)
linear-gradient(90deg, red, 80%, blue)     rgb(244, 0,  10)    rgb(225, 0,  30)
```

**힌트는 「50:50 으로 섞인 색이 나오는 자리」를 옮겼다.**

**왜 색을 안 적나**

- 힌트는 **정지점이 아니다.** 「여기가 중간이다」라고 자리만 말하는 표시다.
- 색을 적으면 그 순간 **정지점**이 되어 다른 뜻이 된다 — 그 색으로 고정되므로 **양옆의 색조가 바뀐다.**
- 힌트를 **연달아 둘 적으면 선언째 버려진다**(실측: `linear-gradient(90deg, red, 30%, 60%, blue)` 의 `cssText` 가 빈 문자열이었다). 힌트 사이에는 반드시 정지점이 있어야 한다.

### 6. ★ `transparent` 로 페이드하면 회색이 끼나

**출력** (검정 배경 위, 400px)

```text
끝 정지점                     20%              50%              80%
---------------------------   --------------   --------------   -------------
transparent                   rgb(204, 0, 0)   rgb(128, 0, 0)   rgb(51, 0, 0)
rgb(255 0 0 / 0)  (같은 색)    rgb(204, 0, 0)   rgb(128, 0, 0)   rgb(51, 0, 0)
rgb(0 0 255 / 0)  (다른 색)    rgb(204, 0, 0)   rgb(128, 0, 0)   rgb(51, 0, 0)

셋이 한 글자도 다르지 않다. 회색은 어디에도 없다.
```

**무엇을 증명하나 — 알파가 0 인 색의 색 성분이 결과에 전혀 기여하지 않는다.**

```text
  셋째 줄이 결정적이다.
  rgb(0 0 255 / 0) 은 「파란색」인데, 결과에 파란 기가 한 톨도 없다.
  → 색 성분을 안 읽고 있다 = 미리 곱해진 알파(premultiplied)로 보간한다

  옛 방식 (비premultiplied)              지금 (premultiplied)
  (1,0,0,1) ↔ (0,0,0,0)                  red 에서 알파만 0 으로 간다
  중간 = (0.5, 0, 0, 0.5)                중간 = red 에 알파 0.5
  → 알파를 풀면 어두운 빨강               → 알파를 풀면 그냥 red
  → 회색·검정 끼가 보인다                 → 색기가 안 변한다
```

**「`rgb(R G B / 0)` 으로 고쳐라」는 조언이 이 브라우저에서 바꾸는 것 — 아무것도 없다.**

- 픽셀이 byte 단위로 같다. **화면은 한 톨도 안 달라진다.**
- 남는 값은 **읽는 사람에게 의도가 드러난다**는 것뿐이다.
- ★ 한 걸음 더 — **끝 정지점을 배경색 그대로(알파 없이) 적어도 픽셀이 같다.** `#111` 배경 위에서 `red → transparent` 와 `red → #111` 의 픽셀이 다섯 자리 전부 같았다(실측).
- ★ **재현해 보지 않은 과거 브라우저 동작을 관찰로 적지 않는다.** 위 「옛 방식」 그림은 **이야기의 재구성**이고, 이 환경에서 확인한 것은 오른쪽 칸뿐이다.

### 7. ★ 그런데 회색 띠는 지금도 생긴다

**출력** (배경 `#9ca3af` = `rgb(156, 163, 175)`, 300px)

```text
선언                                                   25%                50%                75%
-----------------------------------------------------  ----------------   ----------------   ----------------
linear-gradient(90deg, #e11d48, transparent, #2563eb)  rgb(191, 96, 123)  rgb(156, 162, 175) ★ rgb(97, 131, 205)
linear-gradient(90deg, #e11d48, #7a2f7a 50%, #2563eb)  rgb(174, 38,  97)  rgb(122,  47, 122)   rgb(80,  73, 178)
linear-gradient(90deg, #e11d48, #2563eb)      (대조)    rgb(178, 46, 113)  rgb(131,  64, 153)   rgb(84,  82, 194)
```

**50% 픽셀 `rgb(156, 162, 175)` 은 배경색 `rgb(156, 163, 175)` 과 사실상 같다.**

**왜 그 값인가 — 그 자리의 그라디언트가 완전히 투명하기 때문이다.**

```text
  가운데 정지점이 transparent = 알파 0
      ↓
  그 자리에서 그라디언트가 아무것도 안 칠한다
      ↓
  뒤에 있는 것(배경)이 그대로 보인다
      ↓
  배경이 회색이면 회색 띠, 흰색이면 흰 띠
```

**6번과 모순되지 않는 이유** — 6번은 **끝** 정지점이 투명한 2정지점 그라디언트이고, 7번은 **가운데** 정지점이 투명한 3정지점 그라디언트다. 6번의 회색은 **보간 방식** 이야기였고 7번의 회색은 **투명해서 뒤가 비치는** 이야기다. **증상이 같고 원인이 다르다.**

**고치는 법**

```css
/* ✗ 가운데를 투명하게 — rgb(R G B / 0) 으로 바꿔도 똑같이 뚫린다 */
linear-gradient(90deg, #e11d48, transparent, #2563eb)

/* ✓ 가운데를 실제 색으로 */
linear-gradient(90deg, #e11d48, #7a2f7a 50%, #2563eb)

/* ✓ 또는 2정지점으로 쪼갠다 */
linear-gradient(90deg, #e11d48, #2563eb)
```

### 8. 그라디언트는 색인가 이미지인가

**출력**

```text
.a  background-color: linear-gradient(red, blue)
    cssText = ""  [[버려짐]]
    계산값 backgroundColor = rgba(0, 0, 0, 0)   ← 초기값
```

**그라디언트는 `<image>` 이지 `<color>` 가 아니라서 `background-color` 에 못 들어간다.**

```text
.b  background-size: 40px 20px 로 40px 그림을 반복
.c  repeating-linear-gradient(90deg, red 0 20px, blue 20px 40px)

  x =        1         10        25         40        50        100       200       300
  .b    (255,0,0) (255,0,0) (0,0,255) (255,0,0) (255,0,0) (0,0,255) (255,0,0) (0,0,255)
  .c    (255,0,0) (255,0,0) (0,0,255) (255,0,0) (255,0,0) (0,0,255) (255,0,0) (0,0,255)

  샘플한 여덟 자리에서 전부 같았다.
```

**왜 그런가**

- **그라디언트는 `background-image` 의 값**이므로 `background-size`·`position`·`repeat`·`origin`/`clip` 이 전부 먹는다([44번](../44-backgrounds-and-object-fit/2-summary.md)).
- 실측: `.b` 에 `background-repeat: no-repeat` 를 더했더니 **40px 까지만 그려지고 그 뒤는 흰색**이었다 — 「이미지 한 장」이라는 증거다.

### 9. `radial-gradient` 의 기본 모양

**출력** (200×100 상자)

```text
선언                                왼쪽(5,50)          위(100,5)
---------------------------------   -----------------   -----------------
radial-gradient(red, blue)          rgb(85, 0, 171)     rgb( 95, 0, 161)   ← 비슷하다
radial-gradient(circle, red, blue)  rgb(40, 0, 216)     rgb(154, 0, 102)   ← 크게 다르다
```

**기본은 `ellipse` 라서 왼쪽과 위의 색이 비슷하다.** `circle` 을 붙이면 크게 갈린다.

**왜 그런가**

```text
  ellipse (기본)                      circle
  상자 비율에 맞춰 늘어난다            정원이다

  ┌───────────────────┐              ┌───────────────────┐
  │  ╭─────────────╮  │              │       ╭───╮       │
  │  │      ●      │  │              │      ╭  ● ╮      │
  │  ╰─────────────╯  │              │       ╰───╯       │
  └───────────────────┘              └───────────────────┘
   가로·세로가 동시에 끝난다           세로(짧은 축)가 먼저 끝난다
   → 가장자리 색이 사방에서 비슷        → 위아래가 먼저 파랑이 된다
```

- 실측에서 `circle` 쪽 위 가장자리가 `rgb(154, 0, 102)` 로 **아직 빨강 쪽**인데 왼쪽은 `rgb(40, 0, 216)` 로 **거의 파랑**이었다.
- 크기 키워드(`closest-side` 등)와 중심(`at x y`)도 지정할 수 있다 — 실측: `circle closest-side at 50px 50px` 은 중심에서 50px 만에 끝나 상자 대부분이 `rgb(0, 0, 255)` 였다.

### 10. 계산값으로 이 주제를 검증할 수 있나

**출력**

```text
적은 것    linear-gradient(in oklab 90deg, red, blue)
계산값     linear-gradient(90deg in oklab, rgb(255, 0, 0), rgb(0, 0, 255))
```

**그 문자열로는 중간색을 알 수 없다. 이 주제의 유일한 근거는 픽셀이다.**

**왜 그런가**

- 계산값은 **내가 적은 것을 색만 정규화해 되돌려 준다.** 무엇이 그려지는지는 말하지 않는다.
- 2번이 더 강한 증거다 — **무효한 `blue 20%` 를 그대로 보관한다.** 교정은 그릴 때 일어난다.
- 그래서 진단 3창의 창 3(`getComputedStyle`)은 이 주제에서 **「담겼나」까지만** 말해 준다.
- ★ **적는 순서와 직렬화 순서가 다른 것도 여기서 보인다** — `in oklab 90deg` 로 적었는데 `90deg in oklab` 으로 돌아왔다. **두 순서 다 유효하고**(실측: 둘 다 `cssText` 에 담겼다) 직렬화 형태만 하나로 고정된 것이다.

```python
# 이 주제를 검증하는 유일한 방법
# 1. --screenshot 으로 PNG
# 2. PIL 로 열어 특정 좌표를 읽는다
from PIL import Image
im = Image.open('out.png').convert('RGB')
print(im.getpixel((200, 10)))       # 400px 띠의 50% 지점

# 3. 하드 스톱은 「한 행을 훑어 색이 바뀐 자리」로 잡는다
prev = None
for x in range(W):
    p = im.getpixel((x, y))
    if prev and p != prev: print('경계', x, prev, '->', p)
    prev = p
```

### 11. 줄무늬를 만드는 두 가지

**`background-size` + 하드 스톱 쪽이 대개 싸다.**

```text
  A  background-size 방식
     작은 그림 한 장(40×20)을 만들고 그것을 타일로 반복한다
     → 그림 한 장만 계산하면 된다

  B  repeating-* 방식
     면 전체를 그라디언트로 본다
     → 상자 전체의 매 픽셀을 계산한다
```

- 다만 **실측으로 성능을 재지는 않았다.** 위는 「무엇을 계산하나」의 구조 차이다 — **이 주제에서 측정한 것은 픽셀이 같다는 것까지**이고, 속도는 **안 재 봤다.**
- `repeating-*` 이 유리한 자리도 있다 — **각도가 있는 줄무늬**(`45deg`)는 타일로 이으면 이음매가 어긋나기 쉽다.

### 12. `in <공간>` 을 못 읽는 브라우저에서는

**출력** (`webstatus.dev` API 조회, 2026-09-23)

```text
기능                     Baseline   low          Chrome  Firefox  Safari
-----------------------  ---------  -----------  ------  -------  ------
Gradients                widely     2015-07-29   26      3.6      7
Conic gradients          widely     2020-11-17   69      83       12.1
Gradient interpolation   newly      2024-06-11   111     127      16.2
```

**그림은 나온다. 색만 다르다.**

- 못 읽는 브라우저는 `in <공간>` 부분을 이해하지 못해 **그 선언을 버린다** — 그러면 배경이 아예 없어진다.
- 그래서 **안전하게 쓰려면 앞 줄에 기본형을 두는 점진적 향상**을 쓴다.

```css
.x { background: linear-gradient(90deg, red, blue); }              /* 어디서나 */
.x { background: linear-gradient(in oklch 90deg, red, blue); }     /* 읽는 곳에서만 덮어쓴다 */
```

- 두 줄을 이 순서로 두면 **뒤 줄을 못 읽는 브라우저는 앞 줄을 쓴다.** 이것이 [07번](../07-syntax-and-error-recovery/2-summary.md)의 오류 복구가 만드는 토대다.

**픽셀을 읽은 방법** — [42번의 같은 절](../42-color-notation-and-spaces/3-answer.md)과 같다. 이 주제에서만 더 쓴 것은 **경계 탐지**다(10번의 코드).

★ **근거로 쓸 칸을 미리 갈랐다.**

| 흔들리는 칸 | 안 흔들리는 칸 |
|---|---|
| 정지점 사이 그라디언트 픽셀의 **마지막 2\~3 단위**(디더링) | 하드 스톱 **칸 안쪽**의 색 |
| 경계에서 ±1px | **경계가 몇 개이고 어디인가** |
| 뷰포트 폭에 따라 달라지는 **좌표** | **비율로 환산한 자리**(25%·50%·75%) |

그래서 본문의 「같다/다르다」 판정은 전부 **평평한 구간**과 **경계의 개수·위치**에서 뽑았고, 마지막 자릿수를 근거로 삼은 곳은 없다.

**구현에 달린 항목 — 버전이 오르면 다시 찍을 것**

| 항목 | 왜 |
|---|---|
| 그라디언트 픽셀의 마지막 2\~3 단위 | 디더링 |

| 화면이 실제로 낼 수 있는 색 영역 | 이 환경은 sRGB 다([42번](../42-color-notation-and-spaces/2-summary.md)) |

| `repeating-*` 과 `background-size` 방식의 **성능 차이** | **안 재 봤다.** 픽셀이 같다는 것까지만 확인했다 |
