# java/syntax/03 — 변수와 대입: 전부 값 전달·`final`·effectively final — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [JLS SE 21 §4.12 Variables](https://docs.oracle.com/javase/specs/jls/se21/html/jls-4.html) · [§8.4.1 Formal Parameters](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html) · [§15.26 Assignment Operators](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html) · [§16 Definite Assignment](https://docs.oracle.com/javase/specs/jls/se21/html/jls-16.html).
> **실행 검증** — 이 문서의 모든 출력·에러·바이트코드는 Temurin **JDK 21.0.5** 에서 실제로 돌려 얻은 것이다.\
> 값 전달 실험(`Ex.java (03-a)`)과 `final` 실험(`03-b`)은 **17.0.13 · 21.0.5 · 25.0.1** 세 곳에서 돌려 **출력이 같았다**.\
> 컴파일 에러 문구(`03-c2`·`03-c3`)도 세 JDK 에서 같았다. 다만 **"세 곳에서 같았다"는 관찰이지 보장이 아니다** — 보장은 JLS 인용으로만 적었다.
> **버전** — 값 전달 규칙과 `final` 은 **Java 1.0**부터. **effectively final** 은 **Java 8**(람다 도입)에 생긴 개념이다.\
> `var` 지역 변수는 10부터이고 이 주제 밖이다([**04번 주제**](../04-var-type-inference/)).
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 JLS 로, 출력은 실행으로 접지했다.

## 한눈에 — 쉽게 말하면

**변수는 "종이쪽지"다. 객체는 그 쪽지에 적힌 주소에 서 있는 "창고"다.**

비유 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 종이쪽지 | 변수 (지역 변수 슬롯·필드·파라미터) |
| 쪽지에 적힌 숫자 | 기본형 값 (`int` 3, `double` 1.5 …) |
| 쪽지에 적힌 주소 | 참조(reference) — 참조 타입 변수가 실제로 들고 있는 것 |
| 주소가 가리키는 창고 | 힙에 놓인 객체 |
| 창고 안의 물건 | 객체의 필드 · 배열의 원소 |
| 쪽지를 **코팅해서** 못 고치게 하는 것 | `final` |
| 쪽지를 **한 번만 쓰고 안 고친 것** | effectively final |

- 메서드를 부르면 자바는 **쪽지를 복사해서** 넘긴다. 창고를 넘기는 게 아니다.
- 그래서 받은 쪽에서 **쪽지를 고쳐 써도**(= 다른 주소를 적어도) 부른 쪽 쪽지는 그대로다.
- 그런데 받은 쪽이 **주소를 따라가 창고 안 물건을 바꾸면** 그건 부른 쪽에도 보인다.\
  창고는 하나뿐이니까.
- `final` 은 **쪽지를 코팅한다.** 창고에 자물쇠를 다는 게 아니다.\
  코팅된 쪽지를 들고 창고에 가서 안을 다 뒤엎을 수 있다.

```text
                  호출 전                              mutateField(p) 안에서

  p(쪽지) [주소 #7] ----+                 p(쪽지)  [주소 #7] ----+
                        |                 이 쪽지는 복사본이다    |
                        v                                        v
                  +-----------+                            +-----------+
                  | 창고 #7   |                            | 창고 #7   |
                  |  x = 1    |                            |  x = 99   |  <- 안을 고쳤다
                  +-----------+                            +-----------+
```

```text
                  호출 전                              reassign(p) 안에서

  p(쪽지) [주소 #7] ----+                 p(쪽지)  [주소 #9] ----+   <- 복사본에 새 주소를 적었다
                        |                                        |
                        v                                        v
                  +-----------+                            +-----------+
                  | 창고 #7   |                            | 창고 #9   |
                  |  x = 1    |  <- 그대로                  |  x = 99   |  <- 새로 지은 창고
                  +-----------+                            +-----------+
```

두 그림의 차이가 이 주제의 전부다.\
**왼쪽은 창고를 고쳤고 오른쪽은 쪽지를 고쳤다** — 밖에서 보이는 것은 앞의 것뿐이다.

**똑같은 구조로** 자바가 동작한다: 쪽지 = 변수, 주소 = 참조, 창고 = 힙 객체.

실무에서 이게 터지는 자리는 **"메서드가 인자를 고쳐 줄 것"이라 믿고 쓴 코드**다.\
`swap(a, b)` 를 만들어 봤자 아무것도 안 바뀌고, `void init(Config c) { c = new Config(); }` 는 조용히 아무 일도 안 한다.

> **참조(reference)** — 객체가 힙의 어디에 있는지 가리키는 값. 변수가 실제로 들고 있는 것은 객체가 아니라 이 값이다.\
> 예: `Point p = new Point(1);` 에서 `p` 가 들고 있는 것은 `Point` 객체 자체가 아니라 그 객체를 가리키는 참조다.

> **값 전달(pass by value)** — 호출할 때 인자의 **값을 복사해** 파라미터에 넣는 것.\
> 예: `f(p)` 는 `p` 가 든 참조를 복사해 넘기므로, `f` 안에서 파라미터에 다른 객체를 대입해도 `p` 는 안 바뀐다.

> **참조 전달(pass by reference)** — 변수 **자체**(쪽지 그 자체)를 넘겨, 받은 쪽이 대입하면 부른 쪽 변수가 바뀌는 방식.\
> 예: C# 의 `ref int x`, C++ 의 `int&`. **자바에는 이 방식이 없다.**

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 세 질문을 둔다.

1. 메서드에 객체를 넘겼을 때 **무엇이 복사되고 무엇이 공유되는가** — 그래서 무엇이 밖에서 보이는가.
2. `final` 은 정확히 **무엇을 막고 무엇을 안 막는가** — 그리고 그것은 런타임 검사인가 컴파일 검사인가.
3. **effectively final** 은 왜 생겼고, 그 제약이 없으면 무엇이 깨지는가.

## 동작 방식

### (1) 대입 — 오른쪽 식의 "값"을 왼쪽 쪽지에 적는다

**언제 쓰나** — `=` 가 나오는 모든 자리. 변수 선언의 초기화, 재대입, 파라미터 전달, `return`.

```text
기본형 대입                              참조 타입 대입

int a = 3;                              Point p = new Point(1);
int b = a;                              Point q = p;

  a [ 3 ]                                 p [주소 #7] ---+
  b [ 3 ]   <- 숫자를 복사                  q [주소 #7] ---+---> +-----------+
                                                                | 창고 #7   |
b = 99 를 해도                            q.x = 99 를 하면        |  x = 99   |
  a [ 3 ]   <- 그대로                                            +-----------+
  b [ 99]                                 p.x 도 99 다 (창고가 하나)
```

그림 해설 (한 단계씩):

- 두 경우 모두 **오른쪽 식을 평가해 나온 값 하나를 왼쪽 쪽지에 적는다** — 규칙은 하나다.
- 다른 것은 **그 값이 무엇이냐**뿐이다. 기본형이면 숫자, 참조 타입이면 주소.
- 그래서 `b = 99` 는 `a` 에 영향이 없고, `q.x = 99` 는 `p.x` 에 영향이 있다.\
  **둘 다 "쪽지 하나를 고쳤다"는 점에서는 같은데**, 뒤의 것은 쪽지를 고친 게 아니라 **주소를 따라가 창고를 고쳤다.**

비용 — 대입 자체는 상수 시간. 복사되는 것은 **한 슬롯**(기본형 값 또는 참조 하나)뿐이고, **객체 전체가 복사되는 일은 절대 없다.**

### (2) 메서드 호출 — 파라미터는 "새 쪽지"다

**언제 쓰나** — 모든 메서드·생성자 호출. 자바에 예외가 없는 규칙이다.

실제로 돌린 프로그램이다(`Ex.java (03-a)`).

```java
static class Point { int x; Point(int x) { this.x = x; } }

static void mutateField(Point p) { p.x = 99; }        // (A) 창고를 고친다
static void reassign(Point p)    { p = new Point(99); } // (B) 쪽지를 고친다
static void changePrimitive(int n) { n = 99; }          // (C) 숫자 쪽지를 고친다
```

**출력** (JDK 21.0.5 — 17·25 에서도 같았다)

```text
(C) int          n = 1
(A) 필드 변경     p1 = Point(99)
(B) 참조 재대입   p2 = Point(1)
```

전/후를 나란히 놓으면 이렇게 된다.

```text
(A) mutateField(p1)  — 창고를 고쳤다            (B) reassign(p2)  — 쪽지를 고쳤다
+----------------------------------+           +----------------------------------+
| 호출 전                          |           | 호출 전                          |
|   p1 [#7] ---> [창고#7 x=1]      |           |   p2 [#7] ---> [창고#7 x=1]      |
| 호출 중                          |           | 호출 중                          |
|   p  [#7] ---> [창고#7 x=99]     |           |   p  [#9] ---> [창고#9 x=99]     |
|   (복사된 쪽지도 #7 을 가리킨다)  |           |   p1 은 여전히 #7 을 본다         |
| 호출 후                          |           | 호출 후                          |
|   p1.x == 99   <- 보인다          |           |   p2.x == 1    <- 안 보인다       |
+----------------------------------+           +----------------------------------+
```

그림 해설 (한 단계씩):

- 두 경우 모두 **쪽지가 복사됐다** — 여기까지는 완전히 같다.
- (A)는 복사된 쪽지의 **주소를 따라가** 창고 안을 고쳤다. 창고는 하나라 밖에서도 보인다.
- (B)는 복사된 쪽지에 **다른 주소를 적었다.** 원본 쪽지는 손도 안 댔으므로 밖에서는 아무 일도 없었다.
- (C)는 숫자를 복사한 것이라 고칠 창고 자체가 없다.

비용 — 호출마다 **인자 개수만큼 슬롯 복사.** 객체가 1MB 든 1GB 든 복사되는 것은 참조 한 칸(64비트 JVM 기준, 압축 참조면 4바이트)뿐이다.

### (3) 한 메서드 안에서 둘이 섞이면 — 순서가 답을 정한다

**언제 쓰나** — 메서드가 인자를 고치면서 중간에 새 객체를 만들 때. 실무 버그가 여기서 난다.

```java
static void both(Point p) {
    p.x = 50;              // (1) 원래 창고를 고쳤다 -> 밖에서 보인다
    p = new Point(77);     // (2) 쪽지를 새 창고로 돌렸다
    p.x = 88;              // (3) 새 창고를 고쳤다 -> 밖에서 안 보인다
}
```

```text
p3 [#7] ---> [창고#7 x=1]
   (1) p.x = 50
p3 [#7] ---> [창고#7 x=50]        p [#7]
   (2) p = new Point(77)
p3 [#7] ---> [창고#7 x=50]        p [#9] ---> [창고#9 x=77]
   (3) p.x = 88
p3 [#7] ---> [창고#7 x=50]        p [#9] ---> [창고#9 x=88]   <- 아무도 안 본다
```

**출력**

```text
(D) 둘 다        p3 = Point(50)
```

그림 해설 (한 단계씩):

- (2) 이전의 변경만 살아남는다 — **재대입이 그 뒤의 모든 변경을 밖에서 안 보이게 만든다.**
- 88 은 어디에도 남지 않는다. (3)이 고친 창고 #9 는 메서드가 끝나면 아무도 안 가리켜 GC 대상이 된다.

비용 — 없다. 판단 규칙이다. **"재대입 이후 줄은 호출자에게 안 보인다"** 한 줄로 외운다.

### (4) 그래서 `swap` 이 불가능하다

**언제 쓰나** — "자바에 참조 전달이 없다"를 증명해야 할 때. 가장 짧은 반증이다.

```java
static void swap(Point a, Point b) { Point t = a; a = b; b = t; }
```

**출력**

```text
(E) swap 후      a = Point(1)  b = Point(2)
```

```text
swap 안에서 무슨 일이 일어났나

  호출자 a [#7]  b [#8]
  파라미터 a [#7]  b [#8]        <- 쪽지 두 장을 복사
  t = a  ->  t [#7]
  a = b  ->  a [#8]              <- 복사본만 바뀐다
  b = t  ->  b [#7]
  메서드 끝 -> 복사본 셋 다 사라짐
  호출자 a [#7]  b [#8]          <- 아무 일도 없었다
```

그림 해설 (한 단계씩):

- `swap` 은 **복사된 쪽지 두 장을 서로 바꿔 놓고 버렸다.**
- 호출자의 쪽지에 손댈 방법이 **언어에 없다** — 이것이 "참조 전달이 없다"의 뜻이다.
- 자바에서 두 값을 바꾸려면 **바뀐 값을 담은 객체를 돌려주거나**(`return new Pair(b, a)`), **가변 컨테이너의 내용을 바꾸는 수밖에** 없다(창고를 고치는 것).

비용 — 없다. 언어의 한계다.

### (5) `final` — 쪽지를 코팅하는 것이지 창고를 잠그는 것이 아니다

**언제 쓰나** — 상수·불변 필드 선언, 다시 대입되면 안 되는 지역 변수.

```java
static final int[]        NUMS  = {1, 2, 3};
static final List<String> NAMES = new ArrayList<>();
static final StringBuilder SB   = new StringBuilder("a");
```

```text
final 이 막는 것                              final 이 안 막는 것
+-------------------------------+            +-------------------------------+
| NUMS = new int[]{9};          |            | NUMS[0] = 99;                 |
|   -> 컴파일 에러               |            |   -> 그냥 된다                 |
|                               |            | NAMES.add("추가됨");           |
| 쪽지를 고치려 했다             |            | SB.append("b");               |
|                               |            |   -> 그냥 된다                 |
|                               |            | 창고 안을 고쳤다               |
+-------------------------------+            +-------------------------------+
```

**출력** (`Ex.java (03-b)`)

```text
final int[]        NUMS[0] = 99
final List         NAMES   = [추가됨]
final StringBuilder SB     = ab
```

그림 해설 (한 단계씩):

- `final` 이 거는 제약은 **"이 쪽지에 값을 한 번만 적을 수 있다"** 뿐이다.
- 쪽지에 적힌 주소를 따라가 **창고 안에서 무슨 짓을 하든 `final` 은 관여하지 않는다.**
- 그래서 `final` 은 **불변(immutable)을 만들지 않는다.** 불변을 만들려면 창고 자체를 고칠 수 없게 설계해야 한다(목록의 **59번 주제**).

비용 — 런타임 비용 0. 지역 변수의 `final` 은 **바이트코드에 흔적도 안 남는다**(아래 (7)).

> **불변(immutable)** — 만들어진 뒤 상태가 절대 바뀌지 않는 객체.\
> 예: `String`·`Integer`·`record` 로 선언한 값 객체. `final List` 는 불변이 아니다 — 쪽지만 고정됐다.

### (6) blank final 과 확정 대입 — 컴파일러가 "한 번만"을 세고 있다

**언제 쓰나** — 선언 자리에서 값을 못 정하는 `final` 변수(분기마다 다른 값).

```java
final int y;
if (args.length == 0) { y = 10; } else { y = 20; }
System.out.println(y);   // 10
```

```text
컴파일러가 세는 것 — 모든 경로에서 "정확히 한 번"

        final int y;            y: 미대입
            |
      +-----+-----+
      |           |
   y = 10      y = 20          두 갈래 각각 한 번씩
      |           |
      +-----+-----+
            |
        println(y)              y: 확정 대입됨 -> 읽어도 된다
```

그림 해설 (한 단계씩):

- **모든 경로에서 한 번 이상** 대입돼야 읽을 수 있다(확정 대입, JLS §16).
- **어느 경로에서도 두 번**은 안 된다(`final` 제약).
- 이 검사는 **흐름을 따라가며** 이뤄진다 — 한쪽 분기에서만 대입하면 컴파일 에러다.

`final` 이 아닌 지역 변수에도 확정 대입 규칙은 그대로 걸린다.

```text
int x;
System.out.println(x);
```

**컴파일 에러** (`javac`, JDK 21.0.5 — `Ex.java (03-c5)`)

```text
Ex.java:4: error: variable x might not have been initialized
        System.out.println(x);
                           ^
1 error
```

비용 — 컴파일 타임 검사. 런타임 비용 없음.

> **확정 대입(definite assignment)** — 어떤 지점에 도달하는 **모든 실행 경로**에서 그 변수에 값이 들어갔음이 컴파일 타임에 증명되는 것(JLS §16).\
> 예: `if (c) x = 1;` 만 쓰고 `x` 를 읽으면, `c` 가 거짓인 경로가 있으므로 에러다.

**필드는 다르다** — 필드는 선언만 해도 기본값(`0`·`false`·`null`)으로 초기화되므로 확정 대입을 요구하지 않는다.\
지역 변수만 이 검사를 받는다. 초기화 순서 자체는 [`../06-initialization-order/`](../06-initialization-order/) 가 정본이다.

### (7) `final` 은 컴파일 타임 장치다 — 바이트코드가 증언한다

**언제 쓰나** — "`final` 이 런타임에 뭘 하나?"를 판단할 때.

`javap -c` 로 찍어 보면 지역 변수의 `final` 은 **명령이 하나도 안 생긴다.** 오히려 사라진다.

```java
static int withFinal()    { final int x = 1; return x + 1; }
static int withoutFinal() { int x = 1; return x + 1; }
```

**`javap -c -p Ex.class` 출력 그대로** (JDK 21.0.5, `Ex.java (03-e)`)

```text
  static int withFinal();
    Code:
       0: iconst_2
       1: ireturn

  static int withoutFinal();
    Code:
       0: iconst_1
       1: istore_0
       2: iload_0
       3: iconst_1
       4: iadd
       5: ireturn
```

그림 해설 (한 단계씩):

- `withFinal` 은 **명령이 둘**이다 — 계산이 통째로 사라지고 `2` 라는 상수만 남았다.
- `withoutFinal` 은 여섯이다 — 저장하고, 읽고, 더한다.
- 이유는 `final int x = 1` 이 **상수 변수**이기 때문이다(JLS §4.12.4).\
  상수 변수는 컴파일 타임에 값이 확정되므로 컴파일러가 `x + 1` 을 `2` 로 접어 버린다.
- **즉 지역 `final` 은 런타임 비용을 만들지 않고, 상수 초기화면 오히려 코드를 줄인다.**

비용 — 0 또는 음수(코드가 줄어든다).

> **상수 변수(constant variable)** — `final` 이고 **컴파일 타임 상수 식**으로 초기화된 기본형 또는 `String` 변수(JLS §4.12.4).\
> 예: `final int x = 1;` 은 상수 변수이고, `final int x = args.length;` 는 아니다.

`final` **필드**는 다르다 — 클래스 파일에 `ACC_FINAL` 플래그로 남는다. `javap -p` 가 그대로 보여 준다.

```text
public class Ex {
  final int f;
  int g;
  ...
}
```

### (8) effectively final — 왜 생겼나

**언제 쓰나** — 람다나 익명 클래스 안에서 바깥 지역 변수를 쓸 때. Java 8 이후 매일 만난다.

이유는 (2)와 똑같다 — **캡처도 값 복사이기 때문이다.**

`javap` 가 증거다(`Ex.java (03-d)`). 익명 클래스로 `int n` 을 캡처하면 이렇게 컴파일된다.

```text
class Ex$1 implements java.lang.Runnable {
  final int val$n;                 <- 캡처한 값이 "필드로 복사"됐다

  Ex$1();
    Code:
       0: aload_0
       1: iload_1
       2: putfield      #1         // Field val$n:I     <- 생성자에서 복사
       ...
  public void run();
    Code:
       ...
       4: getfield      #1         // Field val$n:I     <- 복사본을 읽는다
```

```text
바깥 메서드                              캡처가 만든 것

  n [ 7 ]                                Ex$1 객체
    |  캡처                              +------------------+
    +-------- 값을 복사 ---------------> | final int val$n  |
                                         |        = 7       |
  메서드가 끝나면 n 은 사라진다           +------------------+
  그래도 val$n 은 남아 있다               <- 그래서 람다가 나중에 실행돼도 값을 안다
```

그림 해설 (한 단계씩):

- 캡처는 **바깥 변수를 가리키는 것이 아니라 그 순간의 값을 복사해 필드에 박는 것**이다.
- 그 필드는 `final` 이다 — 복사한 뒤에는 바뀔 길이 없다.
- 그러면 **바깥 변수가 나중에 바뀌면 둘이 어긋난다.**\
  람다는 7 을 보는데 바깥은 1 이 된다. 어느 쪽이 맞는지 아무도 말할 수 없다.
- 그래서 자바는 **애초에 바뀌지 않는 변수만 캡처하게** 막았다. 그 조건이 effectively final 이다.

람다도 같은 성질이다. `invokedynamic` 의 시그니처를 보면 캡처한 값이 **인자로 들어간다.**

```text
  static java.lang.Runnable capture(int);
    Code:
       0: iload_0
       1: invokedynamic #16,  0             // InvokeDynamic #0:run:(I)Ljava/lang/Runnable;
       6: areturn
```

`run:(I)Ljava/lang/Runnable;` 의 `(I)` 가 **캡처한 `int` 하나**다. 캡처가 없으면 `()` 가 된다.

비용 — 캡처 변수 하나당 필드 한 칸(익명 클래스) 또는 `invokedynamic` 인자 한 칸(람다).\
캡처가 **하나도 없는 람다**는 JVM 이 인스턴스를 재사용할 수 있다.

> **캡처(capture)** — 람다·익명 클래스·지역 클래스가 자기 바깥의 지역 변수를 본문에서 쓰는 것.\
> 예: `int n = 7; Runnable r = () -> System.out.println(n);` 에서 `n` 이 캡처된다.

> **effectively final** — `final` 이라고 안 썼지만 **선언 후 한 번도 재대입되지 않아**, `final` 을 붙여도 컴파일이 되는 변수(JLS §4.12.4).\
> 예: `int counter = 7;` 뒤에 `counter` 에 다시 대입하는 줄이 없으면 effectively final 이다.

## 문법 — 형태와 규칙

직접 쓴 최소 예제다. 묻는 것 하나만 남겼다.

### 변수의 네 종류와 기본값

| 종류 | 선언 자리 | 자동 초기화 | 확정 대입 검사 | `final` 가능 |
|---|---|---|---|---|
| 지역 변수 | 메서드 본문 | **안 된다** | **받는다** | 된다 |
| 파라미터 | 시그니처 | 인자로 채워짐 | 해당 없음 | 된다 |
| 인스턴스 필드 | 클래스 본문 | 된다 (`0`/`false`/`null`) | 안 받는다 | 된다(생성자에서 대입) |
| `static` 필드 | 클래스 본문 `static` | 된다 | 안 받는다 | 된다(`static` 블록에서 대입) |

### `final` 을 붙일 수 있는 자리

```java
final int x = 1;                         // 지역 변수
void m(final String s) { }               // 파라미터
class C { final int f; C() { f = 1; } }  // 인스턴스 필드 (blank final)
static final int K = 10;                 // static 필드 = 상수
final class Sealed { }                   // 클래스 — 상속 금지 (다른 의미)
final void hook() { }                    // 메서드 — 오버라이드 금지 (다른 의미)
```

**주의** — 클래스·메서드에 붙은 `final` 은 **변수의 `final` 과 다른 규칙**이다.\
여기서 다루는 것은 앞의 넷(변수)뿐이다. 클래스·메서드 쪽은 [**09번 주제**](../09-inheritance-overriding/)와 [`../15-sealed-classes/`](../15-sealed-classes/) 가 다룬다.

### 대입식은 값을 가진다

```java
int a, b;
a = b = 5;              // b = 5 의 값(5)이 a 에 대입된다 — 오른쪽 결합
System.out.println(a);  // 5
```

- `=` 는 문이 아니라 **식**이다(JLS §15.26). 값은 "대입된 뒤의 왼쪽 값".
- `if (x = true)` 가 컴파일되는 것도 이 때문이다 — `boolean` 이면 조건 자리에 들어간다.\
  `int` 라면 조건 자리에 못 들어가므로 C 에서 흔한 그 버그가 자바에서는 대개 컴파일 에러가 된다.

### effectively final 이 되는 것과 안 되는 것

```java
int a = 1;                       // effectively final — 이후 재대입 없음
int b = 1; b = 2;                // 아니다 — 두 번 대입
int c; if (x) c = 1; else c = 2; // effectively final — 각 경로에서 한 번
for (String s : list) { }        // s 는 매 반복 새 변수 -> effectively final
for (int i = 0; i < 3; i++) { }  // i 는 i++ 로 재대입 -> 아니다
try (Res r = open()) { }         // r 은 암묵적 final (26번 주제)
catch (IOException | SQLException e) { }  // 다중 catch 의 e 는 암묵적 final (25번 주제)
```

## 어디서 틀리나

이 주제의 값어치는 전부 여기 있다. 넷 다 **에러 메시지가 원인을 바로 안 알려 준다.**

### 1. "자바는 객체를 참조로 넘긴다"고 외운다

이 문장은 **틀렸고**, 틀린 채로도 절반은 맞아떨어져서 안 고쳐진다.

```text
"참조로 넘긴다"로 설명되는 것              "참조로 넘긴다"로 설명 안 되는 것
+---------------------------------+      +---------------------------------+
| void f(Point p) { p.x = 99; }   |      | void f(Point p) { p = new ...; }|
|   -> 호출자에게 보인다            |      |   -> 호출자에게 안 보인다        |
| 맞다                             |      | 참조 전달이면 보여야 한다        |
+---------------------------------+      +---------------------------------+
```

정확한 문장은 **"자바는 언제나 값을 넘기고, 참조 타입의 값은 참조다"** 이다.\
이 문장 하나면 두 칸이 다 설명된다.

### 2. `final` 컬렉션을 불변이라고 믿는다

```java
private static final List<String> WHITELIST = new ArrayList<>(List.of("a", "b"));
```

- 다른 클래스가 `WHITELIST.add("해커")` 를 부르면 **그냥 된다.**
- `final` 은 `WHITELIST = ...` 만 막는다.
- 진짜로 막으려면 `List.of(...)` 또는 `Collections.unmodifiableList(...)` 를 써야 한다.\
  둘의 차이("불변" 대 "수정 불가 뷰")는 목록의 **40번 주제**가 정본이다.

같은 함정이 **배열 상수**에서 더 위험하다 — 배열에는 "수정 불가 뷰"가 아예 없다.

```java
public static final int[] PRIMES = {2, 3, 5};   // 누구나 PRIMES[0] = 999 를 할 수 있다
```

방어는 **복사본을 주는 메서드**뿐이다(`PRIMES.clone()`). 자세한 것은 [`../05-arrays/`](../05-arrays/).

### 3. 람다 안에서 카운터를 늘리려다 막힌다

```java
int counter = 0;
Runnable r = () -> System.out.println(counter);
counter = 1;                      // 여기 때문에 위가 에러가 된다
```

**컴파일 에러** (`Ex.java (03-c2)`, 세 JDK 에서 같았다)

```text
Ex.java:4: error: local variables referenced from a lambda expression must be final or effectively final
        Runnable r = () -> System.out.println(counter);
                                              ^
1 error
```

- **에러가 나는 줄이 원인이 아니다.** 원인은 아래의 `counter = 1;` 이다.\
  이 어긋남이 이 에러를 처음 볼 때 제일 헷갈리는 자리다.
- 흔한 우회는 **길이 1짜리 배열**이다 — 쪽지는 고정하고 창고 안을 고치는 것.

```java
int[] box = {0};
Runnable inc = () -> box[0]++;
inc.run(); inc.run(); inc.run();   // box[0] == 3
```

- 이 우회는 **동작하지만 권장되지 않는다.** 여러 스레드가 쓰면 안전하지 않다.\
  누적이 필요하면 `AtomicInteger` 나 스트림의 수집기를 쓴다([**47번 주제**](../47-collectors-basics/)·**55번 주제**).

같은 이유로 **기본 `for` 의 인덱스는 캡처할 수 없다.**

```text
Ex.java:7: error: local variables referenced from a lambda expression must be final or effectively final
            rs.add(() -> System.out.print(i));
                                          ^
```

반면 **향상된 `for`** 의 변수는 반복마다 새로 만들어지므로 캡처된다 — 실행으로 확인했다.

```text
for-each 캡처 = abc
```

### 4. `final` 필드를 다른 메서드에서 고치려 한다

```java
class Ex {
    final int field;
    Ex() { field = 1; }
    void change() { field = 2; }   // 에러
}
```

**컴파일 에러** (`Ex.java (03-c4)`)

```text
Ex.java:4: error: cannot assign a value to final variable field
    void change() { field = 2; }
                    ^
1 error
```

- `final` 필드는 **생성자(또는 인스턴스 초기화 블록)에서만** 대입할 수 있다.
- 그 밖에서는 "대입을 한 번만"이라는 조건을 컴파일러가 증명할 수 없다.

## 구현 세부사항 대 언어 보장

이 절은 **"어디까지 믿어도 되나"**를 가른다.

| 항목 | 누가 보장하나 | 근거 |
|---|---|---|
| 모든 인자는 값으로 전달된다 | **JLS (언어 보장)** | JLS §8.4.1 — 호출 시 인자 값이 파라미터 변수에 대입된다 |
| `final` 변수는 한 번만 대입된다 | **JLS (언어 보장)** | JLS §4.12.4 |
| effectively final 만 캡처 가능 | **JLS (언어 보장)** | JLS §15.27.2 |
| 캡처가 **필드 복사**로 구현된다 | **구현 세부** | 익명 클래스는 `val$n` 필드로 관찰됨(`javap`). 람다는 `invokedynamic` 인자 |
| `final int x = 1` 이 상수로 접힌다 | **JLS + 구현** | 상수 변수라는 사실은 JLS §4.12.4, **접는 것은 javac 의 재량** |
| 참조 한 칸이 4바이트인가 8바이트인가 | **구현 세부** | 압축 참조 여부·힙 크기에 따라 다르다. 이 문서에서 측정하지 않았다 |
| 익명 클래스 필드 이름이 `val$n` | **구현 세부** | javac 의 명명 규칙. 다른 컴파일러는 다를 수 있다 |

**경계 한 줄** — `javap` 로 본 것(`val$n`·`iconst_2`)은 **관찰**이고, `throw` 되는 에러 문구와 캡처 제약은 **명세**다.\
외울 것은 명령 이름이 아니라 **"캡처는 값 복사다"** 라는 성질이다.

## 언제 쓰고 언제 안 쓰나

| 상황 | 판단 |
|---|---|
| 메서드가 인자 객체의 상태를 바꿔야 하나 | 가능하면 **안 바꾼다.** 새 값을 `return` 한다 |
| 그래도 바꿔야 하면 | 메서드 이름에 드러낸다(`fillInto`·`applyTo`) |
| 지역 변수에 `final` 을 다 붙일까 | **팀 규칙을 따른다.** 붙이면 재대입 버그를 컴파일러가 잡아 주고, 안 붙여도 effectively final 이면 캡처는 된다 |
| 필드에 `final` | **기본으로 붙인다.** 안 붙일 이유가 있을 때만 뺀다 |
| `final` 컬렉션·배열 상수 | `final` 만으로는 부족하다 — `List.of` 나 복사본 반환까지 가야 한다 |
| 람다에서 값을 누적해야 할 때 | 배열 우회 대신 `AtomicInteger`·스트림 수집기 |

판단 규칙 두 줄.

- **"이 메서드가 끝난 뒤 밖에서 뭐가 달라지나"를 먼저 답한다** — 달라지는 것은 창고뿐이다.
- **`final` 은 쪽지를 코팅한다.** 창고를 잠그고 싶으면 다른 장치가 필요하다.

## 핵심 문장

- 자바는 **언제나 값을 전달한다.** 참조 타입의 값이 참조일 뿐이고, 참조 전달은 언어에 없다.
- 그래서 메서드 안의 **재대입은 밖에서 안 보이고**, **필드·원소 변경은 보인다.** 이 한 줄이 `swap` 이 불가능한 이유다.
- `final` 은 **변수 하나에 값을 한 번만 적게** 한다. 그 값이 가리키는 대상의 내용은 전혀 막지 않는다.
- **effectively final** 은 캡처가 값 복사이기 때문에 생겼다 — 익명 클래스의 `final int val$n` 필드가 그 증거다.
- 지역 변수의 `final` 은 런타임에 흔적이 없다. 상수 초기화면 `javac` 가 아예 상수로 접는다(`iconst_2`).

## 용어 풀이

- **변수(variable)** — 값을 담는 저장 위치. 지역 변수·파라미터·인스턴스 필드·`static` 필드 넷이 있다.
- **참조(reference)** — 객체가 힙의 어디 있는지 가리키는 값. 참조 타입 변수가 실제로 들고 있는 것.
- **값 전달(pass by value)** — 인자의 값을 복사해 파라미터에 대입하는 호출 방식. 자바의 유일한 방식이다.
- **참조 전달(pass by reference)** — 변수 자체를 넘겨 호출자의 변수를 바꿀 수 있게 하는 방식. **자바에 없다.**
- **`final`** — 변수에 값을 한 번만 대입할 수 있게 하는 제어자. 대상 객체의 내용은 막지 않는다.
- **blank final** — 선언 자리에서 초기화하지 않은 `final` 변수. 나중에 정확히 한 번 대입해야 한다.
- **확정 대입(definite assignment)** — 읽는 지점에 도달하는 모든 경로에서 값이 들어갔음을 컴파일러가 증명하는 규칙(JLS §16).
- **상수 변수(constant variable)** — `final` 이고 컴파일 타임 상수로 초기화된 기본형·`String` 변수. 값이 코드에 접혀 들어간다.
- **effectively final** — `final` 을 안 붙였지만 재대입이 없어 붙여도 되는 변수. 캡처의 조건이다.
- **캡처(capture)** — 람다·익명 클래스·지역 클래스가 바깥 지역 변수를 본문에서 쓰는 것. 값 복사로 구현된다.
- **불변(immutable)** — 생성 후 상태가 바뀌지 않는 객체. `final` 변수와는 다른 개념이다.
- **`invokedynamic`** — 호출 대상을 런타임에 결정하는 JVM 명령. 람다가 이것으로 컴파일되며, 캡처한 값이 인자로 들어간다.

## 더 들어가면

- **`final` 필드에는 메모리 모델상의 보장이 하나 더 있다.**\
  생성자가 끝난 뒤 다른 스레드가 그 객체를 보면 `final` 필드는 반드시 초기화된 값으로 보인다(final field semantics).\
  `final` 이 아닌 필드는 그 보장이 없다. 메모리 모델 자체는 [`../../언어-특성/README.md`](../../언어-특성/README.md) 가 정본이다.
- **상수 변수는 다른 클래스 파일에 복사돼 박힌다.**\
  `static final int K = 10;` 을 다른 클래스에서 쓰면 그 클래스 파일에 `10` 이 직접 들어간다.\
  그래서 라이브러리의 상수 값을 바꾸고 그 라이브러리만 다시 배포하면 **쓰는 쪽이 옛 값을 계속 본다.** 다시 컴파일해야 한다.
- **캡처가 없는 람다는 인스턴스가 재사용될 수 있다.**\
  `() -> System.out.println("x")` 는 캡처가 없어 `invokedynamic` 의 시그니처가 `()` 이고, JVM 이 같은 인스턴스를 돌려줄 수 있다.\
  캡처가 있으면 매번 새 인스턴스가 필요하다 — 값이 다르기 때문이다.
