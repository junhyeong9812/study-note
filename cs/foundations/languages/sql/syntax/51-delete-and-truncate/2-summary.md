# sql/51-DELETE 와 TRUNCATE — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.\
> **이 본문은 Claude 작성이다 — 원고가 아니다.** SQL 은 원고 없이 공식 문서로 접지하는 문법 주제다([작성법 §2-1](../../../../../../reference/study-note-guide.md)).
>
> **기준 소스** — [PostgreSQL 18 · DELETE](https://www.postgresql.org/docs/18/sql-delete.html) · [PostgreSQL 18 · TRUNCATE](https://www.postgresql.org/docs/18/sql-truncate.html) · [MySQL 8.4 · DELETE](https://dev.mysql.com/doc/refman/8.4/en/delete.html) · [MySQL 8.4 · TRUNCATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/truncate-table.html)\
> **실행 검증** — **PostgreSQL 18.6**(도커 `postgres:18`) · **MySQL 8.4.10**(도커 `mysql:8.4`), 2026-09-21.\
> 아래에 실린 출력·에러·수치는 **전부 이 두 서버에 실제로 던져서 받은 것**이다. 지어낸 출력은 없다.\
> ★ **환경 확인** — MySQL `autocommit=1` · `sql_safe_updates=0`(기본) · 스토리지 엔진 **InnoDB**.\
> **엔진이 MyISAM 이면 4번 절의 결론이 통째로 달라지므로** 먼저 밝힌다.\
> ★ **측정 조건** — 6번의 수치는 **JMH 같은 도구가 아니라 클라이언트 타이머**다(PG 는 `psql \timing`, MySQL 은 `SYSDATE(6)` 차). **3판의 원값을 그대로 싣는다.** 재현되는 것은 **절댓값이 아니라 자릿수와 방향**이다.\
> ★ **이 편이 만든 표와 그 뒷정리** — `study` DB 에 `t51_a`·`t51_p`·`t51_c`·`t51_pc`·`t51_cc`·`t51_big`(5만 행) 을 만들었고 **전부 지웠다.** `emp`·`dept` 는 **읽지도 않았다.**\
> ★ **`WHERE` 없는 `DELETE` 와 `TRUNCATE` 가 이 주제다 — 전부 내 표에서만 던졌다.**\
> **선행** — [50 UPDATE](../50-update-with-join-and-subquery/)(`WHERE` 없는 문의 위험·`sql_safe_updates`) · [44 외래키와 참조 동작](../44-foreign-key-referential-actions/).

## 한눈에 — 쉽게 말하면

**둘 다 「표를 비운다」인데, 하는 일이 근본적으로 다르다.**

```text
DELETE   : 행을 하나씩 찾아 "지웠다" 고 표시한다        -> 행 단위 작업 (DML)
TRUNCATE : 표의 내용물 자체를 버리고 새 통을 만든다      -> 표 단위 작업 (DDL 에 가깝다)
```

일상 비유로 바꾸면 **장부에서 줄을 지우는 것 대 장부를 새로 사는 것**이다.

```text
DELETE                                  TRUNCATE
+----------------------------+          +----------------------------+
| 줄마다 찾아가 두 줄 긋는다  |          | 장부를 통째로 버리고        |
| 지운 줄 자리는 남아 있다    |          | 빈 장부를 새로 꺼낸다       |
| 조건을 걸 수 있다           |          | ★ 조건을 못 건다            |
| 되돌릴 수 있다 (연필로 씀)  |          | ★ 엔진에 따라 못 되돌린다   |
+----------------------------+          +----------------------------+
  -> 느리다. 자리가 안 줄어든다             -> 빠르다. 자리가 확 준다
```

"똑같은 구조다" — 그래서 **네 축으로 비교하면 언제 무엇을 쓸지가 정해진다.**

| 축 | `DELETE` | `TRUNCATE` |
|---|---|---|
| 롤백 | 된다 (두 엔진) | ★ **PG 는 된다 · MySQL 은 안 된다** |
| 자동 증가 | 그대로 이어진다 | ★ **MySQL 은 항상 초기화 · PG 는 `RESTART IDENTITY` 를 적어야** |
| FK 자식이 있으면 | **자식 행이 있을 때만** 막힌다 | ★ **제약만 있으면** 막힌다 (행이 없어도) |
| 속도·공간 | 느리고 공간이 안 준다 | 빠르고 공간이 즉시 준다 |

★ **이 편에서 가장 값비싼 두 줄**

1. **MySQL 의 `TRUNCATE` 는 `ROLLBACK` 이 안 먹는다.** 트랜잭션 안에서 던져도 데이터가 사라진다(2번).
2. **`sql_safe_updates` 는 `TRUNCATE` 를 못 막는다.** `DELETE` 는 막으면서(8번).

## 이 주제가 답하려는 질문

1. **`BEGIN … ROLLBACK` 안에서 던지면 둘 다 되돌아오나?** — 엔진에 따라 다른가.
2. **FK 자식이 있는 표에 던지면 무엇이 막나?** — 「자식 행」인가 「자식 제약」인가.
3. **대량 삭제를 왜 나눠 도나?** — 한 트랜잭션이 길면 무엇이 쌓이나. 재어 볼 수 있나.

## 예시 데이터 — 이 편이 만든 표

★ **`emp`·`dept` 는 한 줄도 쓰지 않았다.** `WHERE` 없는 삭제를 실험하기 때문이다.

```text
t51_a (자동 증가 실험)              t51_p / t51_c (FK — 참조 동작 없음)
+----+---+                          t51_p(id PK, name)   : (1,'p1'), (2,'p2')
| id | v |   PG   : IDENTITY        t51_c(id PK, p_id -> t51_p.id) : (11,1),(12,1),(13,2)
+----+---+   MySQL: AUTO_INCREMENT
|  1 | a |                          t51_pc / t51_cc (FK — ON DELETE CASCADE)
|  2 | b |                          t51_pc(id PK, name)  : (1,'p1'), (2,'p2')
|  3 | c |                          t51_cc(id PK, p_id -> t51_pc.id ON DELETE CASCADE)
|  4 | d |                                               : (11,1),(12,1),(13,2)
|  5 | e |
+----+---+                          t51_big (5만 행)
                                    +----+---------+
                                    | id | v       |   id = 1..50000
                                    +----+---------+   v  = 'row-1' ...
```

두 엔진에서 같은 `CREATE TABLE` 로 만들었다(자동 증가 문법만 갈린다 — [45 번](../45-check-not-null-default-generated-columns/)).

```sql
-- PG
CREATE TABLE t51_a (id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, v varchar(10));
-- MySQL
CREATE TABLE t51_a (id int AUTO_INCREMENT PRIMARY KEY, v varchar(10));
-- 공통
CREATE TABLE t51_p (id int PRIMARY KEY, name varchar(10));
CREATE TABLE t51_c (id int PRIMARY KEY, p_id int,
                    CONSTRAINT t51_c_fk FOREIGN KEY (p_id) REFERENCES t51_p(id));
```

★ **MySQL 에서는 표 수준 `FOREIGN KEY` 절을 썼다** — 열 뒤 `REFERENCES` 는 제약을 안 만든다([44 번](../44-foreign-key-referential-actions/)·[49 번 6절](../49-insert-multi-row-and-insert-select/)).

## 동작 방식

### 1. `DELETE` 는 두 엔진에서 똑같이 롤백된다

**언제 쓰나** — 2번의 대조군. **이쪽이 당연한 쪽이다.**

```text
### SQL: BEGIN; DELETE FROM t51_a; SELECT count(*) AS n FROM t51_a; ROLLBACK;
--- PG 18.6 ---
BEGIN
DELETE 5
 n 
---
 0            <- 트랜잭션 안에서는 비어 있다
(1 row)
ROLLBACK
### SQL: SELECT count(*) AS n_after_rollback FROM t51_a;
--- PG 18.6 ---
 n_after_rollback 
------------------
                5            <- ★ 되돌아왔다
(1 row)
```

```text
### SQL: START TRANSACTION; DELETE FROM t51_a; SELECT count(*) AS n FROM t51_a; ROLLBACK; SELECT count(*) AS n_after_rollback FROM t51_a;
--- MySQL 8.4.10 ---
+---+
| n |
+---+
| 0 |               <- 트랜잭션 안에서는 비어 있다
+---+
+------------------+
| n_after_rollback |
+------------------+
|                5 |            <- ★ 되돌아왔다
+------------------+
```

그림 해설 — `DELETE` 는 **DML** 이므로 트랜잭션의 지배를 받는다. 두 엔진이 같다.\
비용 — 되돌릴 수 있다는 것은 **되돌릴 정보를 어딘가에 쌓아 둔다**는 뜻이다. 7번에서 그것을 잰다.

### 2. ★★ `TRUNCATE` — **PG 는 롤백되고 MySQL 은 안 된다**

**언제 쓰나** — 「비우고 다시 채우기」를 트랜잭션으로 감쌀 때. **이 절을 모르면 데이터를 잃는다.**

**같은 구조, 같은 표, 같은 5행.** 문만 `TRUNCATE` 로 바꿨다.

```text
(A) PostgreSQL 18.6                        (B) MySQL 8.4.10
BEGIN;                                     START TRANSACTION;
TRUNCATE t51_a;                            TRUNCATE t51_a;
SELECT count(*) FROM t51_a;                SELECT count(*) FROM t51_a;
ROLLBACK;                                  ROLLBACK;
SELECT count(*) FROM t51_a;                SELECT count(*) FROM t51_a;
--- 실제 출력 ---                          --- 실제 출력 ---
BEGIN                                      +---+
TRUNCATE TABLE                             | n |
 n                                         +---+
---                                        | 0 |
 0                                         +---+
(1 row)                                    +------------------+
ROLLBACK                                   | n_after_rollback |
 n_after_rollback                          +------------------+
------------------                         |                0 |   ★ 0 이다
                5   ★ 되돌아왔다          +------------------+
(1 row)
```

두 그림의 결론 — **`ROLLBACK` 을 똑같이 쳤는데 한쪽은 5행이 돌아오고 한쪽은 0행이다.**\
MySQL 쪽에서 **데이터는 이미 사라졌다.** 에러도 경고도 없었다.

두 문서가 그 이유를 각각 적는다.

> "`TRUNCATE` is transaction-safe with respect to the data in the tables: the truncation will be safely rolled back if the surrounding transaction does not commit."\
> — [PostgreSQL 18 · TRUNCATE](https://www.postgresql.org/docs/18/sql-truncate.html)

> "Although `TRUNCATE TABLE` is similar to `DELETE`, it is classified as a DDL statement rather than a DML statement… **Truncate operations cause an implicit commit, and so cannot be rolled back.**"\
> — [MySQL 8.4 · TRUNCATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/truncate-table.html)

```text
MySQL 에서 실제로 일어난 일

START TRANSACTION;          <- 트랜잭션 시작
TRUNCATE t51_a;             <- ★ 여기서 암묵 커밋이 일어난다
                               (앞의 트랜잭션이 커밋되고, TRUNCATE 는 그 밖에서 돈다)
ROLLBACK;                   <- 되돌릴 것이 남아 있지 않다
```

★ **더 나쁜 것은 「앞의 트랜잭션이 커밋된다」는 부분이다.**\
`TRUNCATE` 앞에서 한 `INSERT`·`UPDATE` 도 **그 자리에서 확정된다.**

대가 — **MySQL 에서 `TRUNCATE` 를 트랜잭션 스크립트에 넣으면 안전망이 통째로 없어진다.**\
비우고 다시 채우는 작업이라면 **`DELETE` 를 쓰거나, 새 표에 채우고 이름을 바꾸는 편**이 안전하다.

> **암묵 커밋(implicit commit)** — 어떤 문을 실행하면 그 전에 열려 있던 트랜잭션이 자동으로 커밋되는 것.\
> 예: MySQL 에서 `TRUNCATE`·`CREATE TABLE` 같은 DDL 이 그렇다.

### 3. 자동 증가 — **네 경우가 다 다르다**

**언제 쓰나** — 표를 비우고 다시 채울 때. **번호가 1부터인지 6부터인지가 여기서 정해진다.**

출발점을 맞췄다 — **두 엔진 다 「다음 번호 6」** 인 상태에서 시작한다.

```text
--- PG 18.6 ---  (ALTER TABLE t51_a ALTER COLUMN id RESTART WITH 6 으로 맞췄다)

BEGIN; DELETE FROM t51_a;                  INSERT ...; SELECT id;   ->  6
BEGIN; TRUNCATE t51_a;                     INSERT ...; SELECT id;   ->  6   ★ 초기화 안 된다
BEGIN; TRUNCATE t51_a RESTART IDENTITY;    INSERT ...; SELECT id;   ->  1
```

```text
### SQL: BEGIN; TRUNCATE t51_a RESTART IDENTITY; INSERT INTO t51_a (v) VALUES ('new'); SELECT id FROM t51_a; ROLLBACK;
--- PG 18.6 ---
BEGIN
TRUNCATE TABLE
INSERT 0 1
 id 
----
  1
(1 row)
ROLLBACK
```

**MySQL 은 `TRUNCATE` 가 항상 초기화한다.**

```text
### SQL: START TRANSACTION; DELETE FROM t51_a; INSERT INTO t51_a (v) VALUES ('new'); SELECT * FROM t51_a; ROLLBACK;
--- MySQL 8.4.10 ---
+----+------+
| id | v    |
+----+------+
|  6 | new  |            <- DELETE 는 이어진다
+----+------+

### SQL: TRUNCATE t51_a; INSERT INTO t51_a (v) VALUES ('new'); SELECT * FROM t51_a;
--- MySQL 8.4.10 ---
+----+------+
| id | v    |
+----+------+
|  1 | new  |            <- ★ TRUNCATE 는 1 로 되돌린다. 적지 않아도
+----+------+
```

**그리고 `RESTART IDENTITY` 문법은 없다.**

```text
### SQL: TRUNCATE t51_a RESTART IDENTITY;
--- MySQL 8.4.10 ---
ERROR 1064 (42000) at line 1: You have an error in your SQL syntax; check the manual that
  corresponds to your MySQL server version for the right syntax to use near 'RESTART IDENTITY' at line 1
```

```text
                        PG 18.6                 MySQL 8.4.10
DELETE                  이어진다 (6)             이어진다 (6)
TRUNCATE                ★ 이어진다 (6)           ★ 초기화 (1)
TRUNCATE RESTART IDENTITY  초기화 (1)            ★ 문법이 없다 (ERROR 1064)
```

MySQL 매뉴얼이 그 동작을 명시한다.

> "Any `AUTO_INCREMENT` value is reset to its start value. This is true even for `MyISAM` and `InnoDB`, which normally do not reuse sequence values."\
> — [MySQL 8.4 · TRUNCATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/truncate-table.html)

★ **덤 — 롤백해도 번호는 안 돌아온다. 두 엔진 다.**

```text
--- PG 18.6 ---
BEGIN; INSERT INTO t51_a (v) VALUES ('x'); ROLLBACK;    -- 번호 6 을 썼다가 버렸다
INSERT INTO t51_a (v) VALUES ('y');
SELECT * FROM t51_a ORDER BY id;
 id | v 
----+---
  1 | a
  2 | b
  3 | c
  4 | d
  5 | e
  7 | y          <- ★ 6 이 비었다
(6 rows)

--- MySQL 8.4.10 ---
START TRANSACTION; INSERT INTO t51_a (v) VALUES ('x'); ROLLBACK;
INSERT INTO t51_a (v) VALUES ('y'); SELECT * FROM t51_a ORDER BY id;
+----+------+
| id | v    |
+----+------+
|  1 | a    |
|  2 | b    |
|  3 | c    |
|  4 | d    |
|  5 | e    |
|  7 | y    |     <- ★ 여기도 6 이 비었다
+----+------+
```

**번호 발급은 트랜잭션 밖에서 일어난다** — 그래서 롤백해도 소비된 번호는 안 돌아온다.\
비용 — **자동 증가 번호에 「연속」을 기대하면 안 된다.** 순서는 보장돼도 빈칸은 생긴다.

### 4. ★ FK 자식이 있으면 — **막는 기준이 다르다**

**언제 쓰나** — 부모 표를 비울 때. **`DELETE` 는 통과하는데 `TRUNCATE` 만 막히는 일이 생긴다.**

**(a) `DELETE` 는 「실제로 참조하는 자식 행」이 있을 때 막는다.**

```text
### SQL: DELETE FROM t51_p WHERE id = 1;       -- t51_c 에 p_id=1 인 행이 둘 있다
--- PG 18.6 ---
ERROR:  update or delete on table "t51_p" violates foreign key constraint "t51_c_fk" on table "t51_c"
DETAIL:  Key (id)=(1) is still referenced from table "t51_c".
--- MySQL 8.4.10 ---
ERROR 1451 (23000) at line 1: Cannot delete or update a parent row: a foreign key constraint fails
  (`study`.`t51_c`, CONSTRAINT `t51_c_fk` FOREIGN KEY (`p_id`) REFERENCES `t51_p` (`id`))
```

**(b) `TRUNCATE` 는 「제약이 있기만 하면」 막는다.**

```text
### SQL: TRUNCATE t51_p;
--- PG 18.6 ---
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "t51_c" references "t51_p".
HINT:  Truncate table "t51_c" at the same time, or use TRUNCATE ... CASCADE.
--- MySQL 8.4.10 ---
ERROR 1701 (42000) at line 1: Cannot truncate a table referenced in a foreign key constraint
  (`study`.`t51_c`, CONSTRAINT `t51_c_fk`)
```

★ **자식 표를 완전히 비운 뒤에도 똑같이 막힌다.**

```text
### SQL: DELETE FROM t51_c;            -- 자식 행이 0개가 됐다
--- PG 18.6 ---            --- MySQL 8.4.10 ---
DELETE 3                   (성공)

### SQL: TRUNCATE t51_p;
--- PG 18.6 ---
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "t51_c" references "t51_p".
HINT:  Truncate table "t51_c" at the same time, or use TRUNCATE ... CASCADE.
--- MySQL 8.4.10 ---
ERROR 1701 (42000) at line 1: Cannot truncate a table referenced in a foreign key constraint
  (`study`.`t51_c`, CONSTRAINT `t51_c_fk`)
```

```text
           무엇을 보나                          자식 행이 0개면
DELETE     실제 참조 행을 행마다 검사한다        통과한다
TRUNCATE   ★ 제약의 존재만 본다 (행을 안 본다)   ★ 여전히 막힌다
```

**왜 그런가** — `TRUNCATE` 는 **행을 하나씩 보지 않는 것이 존재 이유**다.\
행을 안 보니 **참조 검사도 못 한다.** 그래서 **제약이 있다는 사실만으로 거부**한다.

PG 문서가 그 규칙을 적는다.

> "`TRUNCATE` cannot be used on a table that has foreign-key references from other tables, unless all such tables are also truncated in the same command."\
> — [PostgreSQL 18 · TRUNCATE](https://www.postgresql.org/docs/18/sql-truncate.html)

**(c) PG 의 우회는 `CASCADE` 다 — 그리고 되돌아온다.**

```text
### SQL: BEGIN; TRUNCATE t51_p CASCADE; SELECT (SELECT count(*) FROM t51_p) AS p, (SELECT count(*) FROM t51_c) AS c; ROLLBACK;
--- PG 18.6 ---
NOTICE:  truncate cascades to table "t51_c"
BEGIN
TRUNCATE TABLE
 p | c 
---+---
 0 | 0            <- 자식 표도 통째로 비워졌다
(1 row)
ROLLBACK
### SQL: SELECT (SELECT count(*) FROM t51_p) AS p, (SELECT count(*) FROM t51_c) AS c;
--- PG 18.6 ---
 p | c 
---+---
 2 | 3            <- ★ 둘 다 돌아왔다
(1 row)
```

★ **`NOTICE` 로 무엇이 같이 비워지는지 알려 준다.** 「경고도 출력이다」가 여기서도 쓰인다.

★★ **`TRUNCATE … CASCADE` 와 `ON DELETE CASCADE` 는 다른 것이다.**

```text
ON DELETE CASCADE      : 지워진 부모 행을 "참조하던 자식 행" 만 지운다
TRUNCATE ... CASCADE   : ★ 자식 "표 전체" 를 비운다 (참조 여부와 무관)
```

`ON DELETE CASCADE` 가 걸린 `t51_pc`/`t51_cc` 로 두 문을 나란히 던졌다.

```text
### SQL: BEGIN; DELETE FROM t51_pc WHERE id=1; SELECT (SELECT count(*) FROM t51_pc) AS p, (SELECT count(*) FROM t51_cc) AS c; ROLLBACK;
--- PG 18.6 ---
BEGIN
DELETE 1                 <- ★ 1 이다. 자식 2행은 안 센다
 p | c 
---+---
 1 | 1                   <- 부모 1행 · 자식 1행이 남았다 (자식 둘이 따라 지워졌다)
(1 row)
ROLLBACK

--- MySQL 8.4.10 ---
+----------+------+------+
| reported | p    | c    |
+----------+------+------+
|        1 |    1 |    1 |       <- ROW_COUNT() 도 1 이다
+----------+------+------+
```

★ **영향 행 수가 `1` 이다.** 실제로는 **세 행이 사라졌다**(부모 1 + 자식 2).\
**「몇 행이 바뀌었나」를 보고 값으로만 읽으면 안 되는 자리**다 — `SELECT` 로 세어야 안다.

**MySQL 에는 `TRUNCATE … CASCADE` 가 없다.**

```text
### SQL: TRUNCATE t51_p CASCADE;
--- MySQL 8.4.10 ---
ERROR 1064 (42000) at line 1: You have an error in your SQL syntax; check the manual that
  corresponds to your MySQL server version for the right syntax to use near 'CASCADE' at line 1
```

### 5. ★★ MySQL 의 우회가 남기는 것 — **고아 행**

**언제 쓰나** — 인터넷에서 찾은 `SET FOREIGN_KEY_CHECKS=0` 을 쓰기 전에.

```text
### SQL: SET FOREIGN_KEY_CHECKS=0; TRUNCATE t51_p; SET FOREIGN_KEY_CHECKS=1;
        SELECT (SELECT count(*) FROM t51_p) AS p_rows, (SELECT count(*) FROM t51_c) AS c_rows;
--- MySQL 8.4.10 ---
+--------+--------+
| p_rows | c_rows |
+--------+--------+
|      0 |      3 |       <- ★ 부모가 사라졌는데 자식 3행이 남았다
+--------+--------+

### SQL: SELECT * FROM t51_c ORDER BY id;
--- MySQL 8.4.10 ---
+----+------+
| id | p_id |
+----+------+
| 11 |    1 |      <- t51_p 에 id=1 은 이제 없다
| 12 |    1 |
| 13 |    2 |
+----+------+
```

★★ **「통과했는데 안 한 것」이다.** 문은 성공했고, 경고도 없고, **참조 무결성만 깨졌다.**\
제약을 다시 켠(`FOREIGN_KEY_CHECKS=1`) 뒤에도 **엔진은 기존 행을 재검사하지 않는다.**

```text
PG 의 CASCADE                          MySQL 의 FOREIGN_KEY_CHECKS=0
+-----------------------------+        +-----------------------------+
| 자식 표도 같이 비운다        |        | 부모만 비운다                |
| 무결성이 유지된다            |        | ★ 고아 행이 남는다           |
| NOTICE 로 알려 준다          |        | ★ 아무 말도 없다             |
| ROLLBACK 으로 되돌아온다     |        | ★ 되돌아오지 않는다 (2번)    |
+-----------------------------+        +-----------------------------+
```

대가 — **이 우회를 쓰면 「제약이 지켜 주는 불변식」이 그때부터 거짓**이 된다.\
[44 번](../44-foreign-key-referential-actions/)이 참조 동작의 정본이고, 여기서는 **그 보호가 꺼지는 장면**만 보인다.

### 6. 속도와 공간 — **두 축을 나눠 본다**

**언제 쓰나** — 「빠르다」는 말의 크기를 알아야 할 때.

★ **측정 조건** — 5만 행짜리 `t51_big`. 도구는 **JMH 가 아니라 클라이언트 타이머**다.\
PG 는 `psql` 의 `\timing`, MySQL 은 `SYSDATE(6)` 의 차다. **3판의 원값을 그대로 싣는다.**

```text
--- PG 18.6 ---  DELETE FROM t51_big;        --- PG 18.6 ---  TRUNCATE t51_big;
DELETE 50000   Time: 26.033 ms               TRUNCATE TABLE   Time: 4.740 ms
DELETE 50000   Time: 31.312 ms               TRUNCATE TABLE   Time: 4.319 ms
DELETE 50000   Time: 32.893 ms               TRUNCATE TABLE   Time: 4.962 ms

--- MySQL 8.4.10 ---  DELETE                 --- MySQL 8.4.10 ---  TRUNCATE
delete_ms = 123.8520                         truncate_ms = 90.2080
delete_ms = 125.2010                         truncate_ms = 81.8240
delete_ms = 109.4050                         truncate_ms = 84.3030
```

★ **신호 대 잡음을 밝힌다.**

```text
PG    : 26~33 ms  대  4.3~5.0 ms     -> 신호 약 6~7배, 흔들림 폭 약 25%   -> 결론이 선다
MySQL : 109~125 ms 대 82~90 ms       -> 신호 약 1.3배, 흔들림 폭 약 13%   -> ★ 결론이 약하다
```

**두 엔진에서 결론의 강도가 다르다.**\
PG 에서는 `TRUNCATE` 가 확실히 빠르다. **MySQL 에서는 이 데이터 크기로는 「빠르다」를 단정할 수 없다** —\
5만 행에서 차이가 1.3배뿐이고, `TRUNCATE` 가 **테이블스페이스 파일을 지우고 다시 만드는** 비용을 치르기 때문으로 보인다\
(★ **이 원인 설명은 추론이다** — 파일시스템 수준을 직접 재지는 않았다).

**공간은 이야기가 다르다. 두 엔진에서 결론이 같고 강하다.**

```text
--- PG 18.6 ---
SELECT pg_size_pretty(pg_total_relation_size('t51_big'));
 size_before 
-------------
 3304 kB
(1 row)

(DELETE FROM t51_big 실행 후)
 size_after_delete | rows 
-------------------+------
 3304 kB           |    0      <- ★ 0행인데 크기가 그대로다
(1 row)

(다시 채운 뒤 TRUNCATE 실행)
 size_after_truncate | rows 
---------------------+------
 8192 bytes          |    0      <- ★ 즉시 줄었다
(1 row)
```

```text
--- MySQL 8.4.10 ---  (ANALYZE TABLE 뒤 information_schema 조회)
+---------+--------+                 +----------------------+--------+
| size_kb | n_rows |                 | size_kb_after_delete | n_rows |
+---------+--------+                 +----------------------+--------+
|    2576 |  50000 |                 |                 2128 |      0 |   <- 거의 안 줄었다
+---------+--------+                 +----------------------+--------+

+------------------------+--------+
| size_kb_after_truncate | n_rows |
+------------------------+--------+
|                     16 |      0 |   <- ★ 즉시 줄었다
+------------------------+--------+
```

두 그림의 결론 — **`DELETE` 는 행을 없애도 공간을 안 돌려준다.**\
PG 는 `3304 kB` 그대로, MySQL 은 `2576 → 2128 kB` 로 **17% 만** 줄었다.

```text
DELETE 후 표 안에 남는 것
  PG    : 죽은 튜플(dead tuple) — VACUUM 이 회수한다
  MySQL : 비워진 페이지 — 파일은 그대로, 다음 INSERT 가 재사용한다
```

PG 쪽은 카탈로그에 숫자로 남는다.

```text
### SQL: SELECT n_live_tup, n_dead_tup, pg_size_pretty(pg_total_relation_size('t51_big')) AS size FROM pg_stat_user_tables WHERE relname='t51_big';
--- PG 18.6 ---  (DELETE 직후)
 n_live_tup | n_dead_tup |  size   
------------+------------+---------
          0 |      50000 | 3312 kB       <- ★ 죽은 튜플 5만 개
(1 row)

--- PG 18.6 ---  (VACUUM t51_big 뒤)
 n_live_tup | n_dead_tup | size_after_vacuum 
------------+------------+-------------------
          0 |          0 | 1128 kB           <- 회수됐지만 8192 bytes 까지는 안 간다
(1 row)
```

★ **`VACUUM` 을 돌려도 `TRUNCATE` 만큼 작아지지 않았다**(1128 kB 대 8192 bytes).\
비용 — **「비우고 다시 채우기」가 목적이면 `TRUNCATE` 가 공간 면에서 압도적으로 낫다.**\
다만 MySQL 에서는 **되돌릴 수 없다는 대가**를 같이 치른다(2번).

### 7. ★ 대량 삭제를 나눠 도는 이유 — **쌓이는 것을 잰다**

**언제 쓰나** — 수백만 행을 지워야 할 때. 「나눠 돌아라」의 **근거**를 수치로 본다.

MySQL 은 열린 트랜잭션이 들고 있는 것을 조회할 수 있다.

```text
### SQL: START TRANSACTION; DELETE FROM t51_big; SELECT COUNT(*) AS locks_held FROM performance_schema.data_locks; ROLLBACK;
--- MySQL 8.4.10 ---
+------------+
| locks_held |
+------------+
|      50111 |        <- ★ 잠금 5만 개를 한꺼번에 들고 있다
+------------+
+-------------+
| locks_after |
+-------------+
|           0 |
+-------------+

### SQL: START TRANSACTION; DELETE FROM t51_big LIMIT 10000; SELECT COUNT(*) AS locks_held_chunk FROM performance_schema.data_locks; ROLLBACK;
--- MySQL 8.4.10 ---
+------------------+
| locks_held_chunk |
+------------------+
|            10022 |        <- 1만 행씩 나누면 1만 개
+------------------+
```

트랜잭션 자체의 지표도 같은 말을 한다.

```text
### SQL: START TRANSACTION; DELETE FROM t51_big; SELECT trx_rows_modified, trx_rows_locked, trx_lock_structs FROM information_schema.innodb_trx; ROLLBACK;
--- MySQL 8.4.10 ---
+-------------------+-----------------+------------------+
| trx_rows_modified | trx_rows_locked | trx_lock_structs |
+-------------------+-----------------+------------------+
|             50000 |           50110 |              111 |
+-------------------+-----------------+------------------+

### SQL: (같은 문에 LIMIT 10000 을 붙여)
+-------------------+-----------------+------------------+
| trx_rows_modified | trx_rows_locked | trx_lock_structs |
+-------------------+-----------------+------------------+
|             10000 |           10021 |               23 |
+-------------------+-----------------+------------------+
```

```text
한 트랜잭션이 길면 쌓이는 것 — 잰 것과 못 잰 것

★ 잰 것
  MySQL : 행 잠금 수      50,111 개   (1만씩 나누면 10,022 개)
          수정한 행 수    50,000
  PG    : 죽은 튜플       50,000 개   (VACUUM 전까지 남는다 — 6번)

  ※ 되돌리기 정보(undo log)·복제 지연은 이 실험에서 직접 재지 못했다
```

그림 해설 — **잠금은 트랜잭션이 끝날 때까지 안 풀린다.**\
그 사이 같은 행을 건드리는 다른 세션은 **전부 대기**한다.

```text
한 문으로 5만 행                        1만 행씩 다섯 번
+---------------------------+           +---------------------------+
| 잠금 50,111 개            |           | 잠금 10,022 개 x 5 회     |
| 커밋까지 한 번도 안 풀린다 |           | 회마다 커밋하고 풀린다     |
| 실패하면 5만 행을 되돌린다 |           | 실패해도 1만 행만 되돌린다 |
+---------------------------+           +---------------------------+
  -> 다른 세션이 계속 기다린다              -> 틈틈이 지나갈 수 있다
```

**나눠 도는 문법은 방언이 갈린다.**

```text
### SQL: DELETE FROM t51_big LIMIT 10000;
--- PG 18.6 ---
ERROR:  syntax error at or near "LIMIT"
LINE 1: DELETE FROM t51_big LIMIT 10000
                            ^
--- MySQL 8.4.10 ---
+---------+-------+
| deleted | n     |
+---------+-------+
|   10000 | 40000 |
+---------+-------+

### SQL: DELETE FROM t51_big WHERE id IN (SELECT id FROM t51_big ORDER BY id LIMIT 10000);   (PG 관용구)
--- PG 18.6 ---
DELETE 10000
   n   
-------
 40000
(1 row)
```

★ **PG 에는 `DELETE … LIMIT` 이 없다** — 대상을 서브쿼리로 골라야 한다.\
[50 번 13절](../50-update-with-join-and-subquery/)의 `UPDATE` 쪽과 **같은 관용구**다.

비용 — 나눠 돌면 **전체는 느려진다.** 대신 **다른 세션이 멈추지 않고, 실패했을 때 되돌릴 양이 작다.**

### 8. ★★ 안전장치가 `TRUNCATE` 를 못 본다

**언제 쓰나** — [50 번 9절](../50-update-with-join-and-subquery/)에서 켠 `sql_safe_updates` 를 믿고 있을 때.

```text
### SQL: SET sql_safe_updates=1; DELETE FROM t51_c;
--- MySQL 8.4.10 ---
ERROR 1175 (HY000) at line 1: You are using safe update mode and you tried to update a table
  without a WHERE that uses a KEY column.          <- ★ 막았다

### SQL: SET sql_safe_updates=1; START TRANSACTION; DELETE FROM t51_c WHERE id=11; SELECT ROW_COUNT() AS deleted; ROLLBACK;
--- MySQL 8.4.10 ---
+---------+
| deleted |
+---------+
|       1 |                                        <- 기본키를 쓰면 통과
+---------+

### SQL: SET sql_safe_updates=1; TRUNCATE t51_c; SELECT count(*) AS n FROM t51_c;
--- MySQL 8.4.10 ---
+---+
| n |
+---+
| 0 |                                              <- ★★ 그대로 비워졌다
+---+
```

```text
sql_safe_updates = 1 인 상태에서

DELETE FROM t (WHERE 없음)  -> ERROR 1175. 막힌다
TRUNCATE t                  -> ★ 통과한다. 표가 비었다. 게다가 롤백도 안 된다(2번)
```

두 그림의 결론 — **안전 모드는 `UPDATE`/`DELETE` 만 본다.** 매뉴얼의 문장이 그대로다.

> "If this option is enabled, `UPDATE` and `DELETE` statements that do not use a key in the `WHERE` clause or a `LIMIT` clause produce an error."\
> — [MySQL 8.4 · mysql Client Options](https://dev.mysql.com/doc/refman/8.4/en/mysql-command-options.html)

★ **`TRUNCATE` 는 그 목록에 없다.** DDL 이기 때문이다(2번).\
**가장 위험한 문에 가장 약한 방어**가 걸려 있는 셈이다.

대가 — 「안전 모드를 켜 뒀으니 괜찮다」는 감각이 **틀린 자리가 정확히 여기**다.

### 9. 조인을 쓰는 삭제 — 여기도 방언이 갈린다

**언제 쓰나** — 다른 표를 조건으로 삼아 지울 때. [50 번 1절](../50-update-with-join-and-subquery/)의 삭제판이다.

```text
### SQL: BEGIN; DELETE FROM t51_c USING t51_p WHERE t51_p.id = t51_c.p_id AND t51_p.name='p1'; SELECT * FROM t51_c ORDER BY id; ROLLBACK;
--- PG 18.6 ---
BEGIN
DELETE 2
 id | p_id 
----+------
 13 |    2
(1 row)
ROLLBACK

### SQL: DELETE FROM t51_c USING t51_p WHERE t51_p.id = t51_c.p_id AND t51_p.name='p1';
--- MySQL 8.4.10 ---
ERROR 1109 (42S02) at line 1: Unknown table 't51_c' in MULTI DELETE
```

★ **MySQL 에도 `USING` 이 있다.** 다만 **지울 표를 따로 지목**해야 한다 — 그래서 PG 형태를 정확히 거부한다.

```text
### SQL: START TRANSACTION; DELETE c FROM t51_c c JOIN t51_p p ON p.id = c.p_id WHERE p.name='p1'; SELECT ROW_COUNT() AS deleted; SELECT * FROM t51_c ORDER BY id; ROLLBACK;
--- MySQL 8.4.10 ---
+---------+
| deleted |
+---------+
|       2 |
+---------+
+----+------+
| id | p_id |
+----+------+
| 13 |    2 |
+----+------+

### SQL: START TRANSACTION; DELETE FROM c USING t51_c c JOIN t51_p p ON p.id = c.p_id WHERE p.name='p1'; SELECT ROW_COUNT() AS deleted; ROLLBACK;
--- MySQL 8.4.10 ---
+---------+
| deleted |
+---------+
|       2 |
+---------+

### SQL: DELETE c FROM t51_c c JOIN t51_p p ON p.id = c.p_id WHERE p.name='p1';
--- PG 18.6 ---
ERROR:  syntax error at or near "c"
LINE 1: DELETE c FROM t51_c c JOIN t51_p p ON p.id = c.p_id WHERE p....
               ^
```

```text
PG    : DELETE FROM 대상 USING 상대 WHERE 조인조건
                          ^^^^^ 대상은 FROM 뒤에 한 번만
MySQL : DELETE 별칭 FROM 대상 별칭 JOIN 상대 ON ... 
        ^^^^^^ ★ "어느 표를 지울지" 를 앞에 따로 적는다
```

**이식 형태는 서브쿼리다** — 두 엔진에서 같은 글자로 돈다.

```sql
DELETE FROM t51_c WHERE p_id IN (SELECT id FROM t51_p WHERE name = 'p1');
```

## 문법 — 어느 절에서 무엇이 갈리나

```sql
-- 공통
DELETE FROM t WHERE ...;
DELETE FROM t;                              -- 전부 (조건 없음)
DELETE FROM t WHERE k IN (SELECT ...);      -- 이식 가능한 조인 삭제
TRUNCATE t;                                 -- ★ 문법은 같고 의미가 다르다

-- 서로를 거부하는 자리
DELETE FROM t USING s WHERE s.k = t.k;      -- PG.    MySQL 은 ERROR 1109
DELETE c FROM t c JOIN s ON ...;            -- MySQL. PG 는 syntax error
DELETE FROM t LIMIT n;                      -- MySQL. PG 는 syntax error
TRUNCATE t RESTART IDENTITY;                -- PG.    MySQL 은 ERROR 1064
TRUNCATE t CASCADE;                         -- PG.    MySQL 은 ERROR 1064
DELETE FROM t ... RETURNING ...;            -- PG (54번). MySQL 에는 없다
DELETE IGNORE FROM t ...;                   -- MySQL
```

규칙 여덟.

1. **`TRUNCATE` 에는 `WHERE` 가 없다.** 조건이 필요하면 `DELETE` 다.
2. **`DELETE` 는 두 엔진에서 롤백된다.** `TRUNCATE` 는 **PG 만** 롤백된다.
3. **MySQL 의 `TRUNCATE` 는 암묵 커밋이다** — 앞선 트랜잭션까지 확정시킨다.
4. **`TRUNCATE` 는 FK 제약이 있기만 하면 막힌다.** 자식 행이 0개여도.
5. **자동 증가는 `DELETE` 가 안 건드리고, MySQL 의 `TRUNCATE` 는 항상 초기화한다.**\
   PG 는 `RESTART IDENTITY` 를 적어야 한다.
6. **`DELETE` 는 공간을 안 돌려준다.** `TRUNCATE` 는 즉시 돌려준다.
7. **`DELETE … LIMIT` 은 MySQL 만** — PG 는 서브쿼리로 대상을 고른다.
8. **`sql_safe_updates` 는 `TRUNCATE` 를 못 막는다.**

읽을 때 붙잡을 것은 **「되돌릴 수 있나」** 하나다.

```text
 되돌려야 하나 -> 예   : DELETE  (조건도 걸 수 있다. 느리고 공간이 안 준다)
               -> 아니오: TRUNCATE
                          -> PG 면 그래도 되돌아온다
                          -> MySQL 이면 ★ 돌이킬 수 없다. 던지기 전에 한 번 더 본다
```

#### 방언 요약

| | PostgreSQL 18.6 | MySQL 8.4.10 |
|---|---|---|
| `DELETE` 롤백 | 된다 | 된다 |
| ★ `TRUNCATE` 롤백 | **된다**(문서: transaction-safe) | **안 된다**(문서: implicit commit) |
| `TRUNCATE` 와 자동 증가 | 그대로 — `RESTART IDENTITY` 가 필요 | **항상 초기화** |
| `RESTART IDENTITY` 문법 | 있다 | `ERROR 1064` |
| FK 자식이 있는 표에 `TRUNCATE` | `cannot truncate a table referenced…` + `HINT` | `ERROR 1701` |
| `TRUNCATE … CASCADE` | 있다 (+`NOTICE`) | `ERROR 1064` |
| FK 우회 | (없음 — `CASCADE` 를 쓴다) | `SET FOREIGN_KEY_CHECKS=0` — ★ **고아 행이 남는다** |
| 조인 삭제 | `DELETE FROM t USING s WHERE …` | `DELETE c FROM t c JOIN s ON …` |
| `DELETE … LIMIT` | **없다**(구문 오류) | 있다 |
| 안전 모드 | 없다 | `sql_safe_updates` — ★ **`TRUNCATE` 는 못 막는다** |
| `RETURNING` | 있다([54번](../54-returning-and-data-modifying-cte/)) | 없다 |
| `DELETE` 뒤 공간 | 그대로(죽은 튜플) — `VACUUM` 이 회수 | 거의 그대로(빈 페이지) |
| `TRUNCATE` 뒤 공간 | 8192 bytes 까지 즉시 | 16 kB 까지 즉시 |

## 어디서 틀리나

1. ★★ **MySQL 에서 `TRUNCATE` 를 트랜잭션으로 감싸고 안전하다고 믿는다.**\
   **롤백이 안 된다.** 게다가 **앞선 문까지 커밋시킨다**(2번).
2. ★★ **`sql_safe_updates` 가 켜져 있으니 실수로 표를 비울 일은 없다고 생각한다.**\
   `TRUNCATE` 는 **통과한다**(8번).
3. **`TRUNCATE` 가 막히는 이유를 「자식 행이 있어서」로 읽는다.**\
   **제약이 있어서**다. 자식 표를 비워도 여전히 막힌다(4번).
4. **`TRUNCATE … CASCADE` 를 `ON DELETE CASCADE` 와 같은 것으로 안다.**\
   **자식 표 전체를 비운다** — 참조 여부와 무관하다(4번 c).
5. ★ **`SET FOREIGN_KEY_CHECKS=0` 으로 우회한다.**\
   **고아 행이 남고 아무도 안 알려 준다**(5번).
6. **`DELETE` 로 표를 비우면 디스크가 빌 것이라 기대한다.**\
   PG 는 `3304 kB` 그대로, MySQL 은 17% 만 줄었다(6번).
7. **`TRUNCATE` 가 어디서나 극적으로 빠를 것이라 기대한다.**\
   PG 에서는 6~7배였지만 **MySQL 8.4.10 에서는 5만 행에 1.3배뿐**이었다(6번).
8. **자동 증가 번호가 연속일 것이라 기대한다.** 롤백만 해도 번호가 빈다(3번).
9. **`DELETE … LIMIT` 을 PG 에 쓴다.** 구문 오류다(7번).
10. **`ROW_COUNT()`/`DELETE n` 을 실제 사라진 행 수로 읽는다.**\
    `ON DELETE CASCADE` 로 따라 지워진 자식 행은 **안 센다**(4번 c).
11. **대량 삭제를 한 문으로 던진다.** 잠금 5만 개가 커밋까지 안 풀린다(7번).

## 구현 세부사항 대 언어 보장

| | 언어(문서)가 보장하는 것 | 구현이 정하는 것 |
|---|---|---|
| `DELETE` 롤백 | DML 이므로 트랜잭션의 지배를 받는다 | — (두 엔진이 같았다) |
| ★ `TRUNCATE` 롤백 | **PG 문서: transaction-safe** / **MySQL 문서: implicit commit** | — ★ **두 문서가 서로 다른 것을 보장한다** |
| `TRUNCATE` 와 자동 증가 | **MySQL 문서: 항상 초기화** | PG 는 `RESTART IDENTITY` 를 적는 설계 |
| FK 와 `TRUNCATE` | **PG 문서: 같이 truncate 하지 않으면 못 쓴다** | 에러 코드·문구 |
| 속도 | — | ★ **전부**(엔진·저장 구조·파일시스템) |
| 공간 회수 시점 | — | **PG 는 `VACUUM`, MySQL 은 페이지 재사용** |
| 조인 삭제 문법 | — | ★ **전부**(`USING` 대 `DELETE 별칭 FROM`) |
| 잠금 개수 | — | **InnoDB 가 정한다**(`performance_schema` 로 관찰) |

- ★ **6번의 속도 수치는 관찰이다.** 도구가 JMH 가 아니고, 머신·캐시 상태가 섞여 있다.\
  **재현되는 것은 「`TRUNCATE` 가 더 빠르다」는 방향과 자릿수**이지 절댓값이 아니다.\
  그리고 **MySQL 쪽은 신호가 약해 그 방향조차 단정하지 않는다.**
- ★ **7번의 잠금 개수는 InnoDB 의 구현 세부다.** 외울 것은 숫자가 아니라\
  「**한 트랜잭션이 길면 잠금이 그만큼 쌓이고 커밋까지 안 풀린다**」는 성질이다.

## 언제 쓰고 언제 안 쓰나

- **쓴다 — `DELETE`, 조건이 있을 때.** `TRUNCATE` 에는 `WHERE` 가 없다.
- **쓴다 — `DELETE`, 되돌릴 여지를 남겨야 할 때.** 두 엔진 다 롤백된다.
- **쓴다 — `TRUNCATE`, 테스트 픽스처 초기화.** 빠르고 공간을 돌려주고 자동 증가도 정리된다.
- **안 쓴다 — MySQL 에서 트랜잭션 스크립트 안의 `TRUNCATE`.** 안전망이 통째로 없어진다(2번).
- **안 쓴다 — `SET FOREIGN_KEY_CHECKS=0` 우회.** 고아 행이 남는다(5번).
- **안 쓴다 — 수백만 행 `DELETE` 를 한 문으로.** 나눈다(7번).
- **조심한다 — `TRUNCATE` 를 「빠른 `DELETE`」로 이해하는 것.** 하는 일이 다르다. FK·롤백·자동 증가가 전부 다르다.
- **조심한다 — 운영 중 표를 비울 때.** **비우는 것보다 「새 표에 채우고 이름 바꾸기」가 되돌리기 쉽다.**

## 핵심 문장

- ★ **`TRUNCATE` 는 PG 에서 롤백되고 MySQL 에서는 안 된다** — MySQL 은 암묵 커밋이다.
- ★ **`sql_safe_updates` 는 `DELETE` 를 막고 `TRUNCATE` 는 못 막는다** — 가장 위험한 문에 방어가 없다.
- **`TRUNCATE` 는 FK 제약의 존재만으로 막힌다** — 자식 행이 0개여도.
- **`TRUNCATE … CASCADE` 는 자식 표를 통째로 비운다** — `ON DELETE CASCADE` 와 다른 것이다.
- ★ **`SET FOREIGN_KEY_CHECKS=0` 우회는 고아 행을 남기고 아무 말도 안 한다.**
- **`DELETE` 는 공간을 안 돌려준다** — PG 는 죽은 튜플 5만 개, MySQL 은 17% 만 줄었다.
- **자동 증가는 `DELETE` 로 안 돌아가고, MySQL 의 `TRUNCATE` 는 항상 1로 되돌린다.**
- **나눠 도는 이유는 잠금이다** — 5만 행 한 문이 잠금 50,111 개를 커밋까지 들고 있었다.

## 용어 풀이

- **DDL(data definition language)** — 표·인덱스 같은 구조를 정의·변경하는 문. `CREATE`·`ALTER`·`TRUNCATE`.\
  예: MySQL 에서 DDL 은 암묵 커밋을 일으킨다.
- **암묵 커밋(implicit commit)** — 어떤 문을 실행하면 그 전에 열려 있던 트랜잭션이 자동으로 커밋되는 것.\
  예: MySQL 의 `TRUNCATE` 앞에서 한 `INSERT` 도 그 자리에서 확정된다.
- **죽은 튜플(dead tuple)** — PG 에서 `DELETE`·`UPDATE` 로 더는 안 보이지만 파일에는 남아 있는 행.\
  예: 5만 행을 지우면 `n_dead_tup` 이 50000 이 되고 크기는 그대로다.
- **`VACUUM`** — PG 에서 죽은 튜플을 회수해 공간을 재사용 가능하게 만드는 작업.\
  예: 돌려도 `TRUNCATE` 만큼 작아지지는 않았다(1128 kB 대 8192 bytes).
- **`RESTART IDENTITY`** — PG 의 `TRUNCATE` 옵션. 그 표의 시퀀스를 처음 값으로 되돌린다.\
  예: 안 적으면 `TRUNCATE` 뒤에도 번호가 이어진다.
- **`FOREIGN_KEY_CHECKS`** — MySQL 세션 변수. `0` 으로 두면 외래키 검사를 건너뛴다.\
  예: 이것으로 부모를 `TRUNCATE` 하면 자식에 고아 행이 남는다.
- **고아 행(orphan row)** — 참조하는 부모 행이 없는 자식 행.\
  예: `t51_c.p_id = 1` 인데 `t51_p` 에 `id=1` 이 없는 행.
- **행 잠금(row lock)** — 트랜잭션이 특정 행을 다른 트랜잭션으로부터 지키는 표시.\
  예: 5만 행 `DELETE` 가 잠금 50,111 개를 커밋까지 들고 있었다.
- **`performance_schema.data_locks`** — MySQL 에서 현재 걸려 있는 잠금을 보여 주는 표.\
  예: 트랜잭션을 열어 둔 채 세면 그 트랜잭션이 들고 있는 잠금 수가 나온다.
- **`ERROR 1701`** — MySQL 이 「외래키가 참조하는 표는 `TRUNCATE` 할 수 없다」고 거절하는 코드.\
  예: 자식 행이 0개여도 이 에러가 난다.
- **`ERROR 1175`** — MySQL 의 안전 갱신 모드가 `UPDATE`/`DELETE` 를 거절하는 코드.\
  예: `TRUNCATE` 에는 이 에러가 안 난다 — 목록에 없기 때문이다.

## 더 들어가면

- **MySQL 의 스토리지 엔진이 MyISAM 이면 이 편의 결론이 통째로 달라진다.**\
  MyISAM 에는 트랜잭션이 없어 `DELETE` 도 롤백되지 않는다. **이 실험은 전부 InnoDB 에서 했고,\
  다른 엔진은 던져 보지 않았다.**
- **PG 에서 `TRUNCATE` 는 표를 `ACCESS EXCLUSIVE` 로 잠근다** — 읽기조차 막는다.\
  `DELETE` 는 훨씬 약한 잠금을 쓴다. **이 차이는 이 편에서 직접 재지 않았다** — [57 명시적 잠금과 교착](../57-explicit-locking-and-deadlock/) 주제다.
- **되돌리기 정보(undo log)의 크기**는 「한 트랜잭션이 길면 쌓이는 것」의 대표인데,\
  **이 실험에서 직접 재지 못했다.** 대신 `trx_rows_modified`(50,000)와 잠금 수로 대신했다.
- **복제 지연**도 대량 삭제의 비용이지만 **복제를 구성하지 않아 재현하지 못했다.**
- **`DELETE` 를 나눠 돌 때 `ORDER BY` 를 붙이는 이유**는 매번 같은 쪽부터 지워\
  인덱스 스캔이 앞에서부터 진행되게 하려는 것이다. 붙이지 않으면 **매 회차가 표 전체를 훑을 수 있다.**\
  ★ **이 효과는 계획으로 확인하지 않았다** — 계획은 통계에 흔들린다([작성법 §2-1](../../../../../../reference/study-note-guide.md)).
- **PG 18 에는 `DELETE … RETURNING` 에 `OLD`/`NEW` 별칭이 생겼다** — [54 번](../54-returning-and-data-modifying-cte/)이 그것을 다룬다.
