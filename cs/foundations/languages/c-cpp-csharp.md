# foundations/languages — C · C++ · C#: 세 언어는 서로 다른 이유로 빠진다 (정리)

> 이 컬렉션은 은행 원장처럼 정합성이 1순위인 시스템의 언어 선택을 소재로, 각 언어가 "틀렸을 때 어떻게 틀리는가"를 정리한다.\
> 원고 출처: `jun-bank/docs/study/tech/languages/c-cpp-csharp.md` (따라 친 학습 노트) · 이관일 2026-09-16.\
> 본문 절들은 **원고**를 고쳐 쓴 것이다(문체·순서·인용 유지). 프로젝트 고유명(특정 은행 시스템·내부 결정 문서 번호)은 일반형으로 바꿨다.\
> 「한눈에」·「전체 흐름」의 그림은 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다. 실명 표준·서적 인용은 원고 그대로 유지한다.

C·C++·C#은 하나의 축으로 줄 세워지지 않는다.\
**C와 C++는 성능이 모자라서가 아니라 실패 모드가 이 도메인의 최악 실패와 같은 모양이어서 빠지고, C#은 기술적으로 거의 갈리지 않아서 생태계에서 갈린다.**

---

## 한눈에 — 쉽게 말하면

계산기 세 대를 고르는데, 기준이 "얼마나 빨리 더하는가"가 아니라 **"틀렸을 때 어떻게 티가 나는가"**라고 생각하면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
세 계산기의 "틀림" 방식
+-----------------------------------------------+
| C    : 틀린 답을 조용히 화면에 남긴다            |  ← 오류 표시도 없다
| C++  : "해제 잊음"은 못 틀리게 막았지만          |
|        "죽은 값 참조"는 여전히 조용히 틀린다     |
| C#   : 틀리면 그 자리에서 예외로 멈춰 선다        |  ← JVM과 같은 계열
+-----------------------------------------------+
  → 은행 원장에서 최악은 "느림"이 아니라 "조용한 오답"이다
```

**언어 선택도 똑같은 구조다.** 은행 원장의 응답시간을 지배하는 것은 명령어 실행 속도가 아니라 DB 왕복과 잠금 대기이고, "조금 느려도 되지만 숫자가 틀리면 안 된다"가 품질 순위의 근거다. 그러면 언어를 가르는 축은 속도가 아니라 **틀렸을 때 신호가 뜨는가**가 된다.

쉽게 말하면 이렇다.\
**성능은 네 번째 축이 아니라 다른 셋(실패 모드·생태계·운영 비용) 안에 흩어져 들어 있는 부분집합이다** — C의 속도는 "런타임 없이 돈다"는 운영 조건의 결과이고, GC 정지 시간은 성능 수치이기 이전에 응답시간 품질 시나리오의 입력이다.

## 이 문서가 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(개념 정리다). 대신 세 언어를 각각 다른 질문으로 본다.

```text
C 에게    "이 언어로 틀렸을 때 무슨 일이 벌어지는가?"
C++ 에게  "현대적으로 쓰면 그 일이 안 벌어지는가?"
C# 에게   "기술적으로 충분한데 왜 안 쓰는가?"
```

앞의 둘은 실패 모드로 답하고(§C~§C++), 마지막 하나는 실행 모형의 동형성과 생태계로 답한다(§C#).\
그래서 이 문서의 실질적 주제는 세 언어 자체가 아니라 **"언어를 고를 때 무엇을 보는가"**이고, 그 답이 마지막 절이다.

인용한 표준은 C가 ISO C 공개 초안 N1570(C11)과 N3220(C23), C++가 ISO C++ Core Guidelines와 WG21 문서, .NET이 Microsoft 공식 문서와 ECMA 표준 기준이다.

## 전체 흐름 — 성능 순위가 아니라 두 진영

세 언어는 성능 한 줄이 아니라 **두 진영**으로 갈린다. *(Claude 보강 — 원고 §1의 논지를 도식화)*

```text
"네이티브로 돌고 런타임을 안 깐다 · 프로그래머를 믿는다"
   │
   ├─ C     메모리를 그냥 주소로 다룬다
   └─ C++   그 위에 추상화를 얹었다 (C 계보)
   │
   ▼  (실패 신호가 없을 수 있다)

"런타임이 대신 지킨다"
   │
   ├─ C#/.NET   IL → JIT, 추적 GC
   └─ JVM        바이트코드 → JIT, 추적 GC
   │
   ▼  (틀리면 그 지점에서 예외)

→ C#은 C·C++가 아니라 JVM과 같은 진영이다 (§C# 실행 모형 동형)
```

## C — 메모리 관리는 언어 기능이 아니라 프로그래머의 부기다

> 출처: 원고 §2

C는 1972년 무렵 벨 연구소에서 데니스 리치가 Unix를 어셈블리에서 옮겨 쓰기 위해 만든 언어다 — 특정 기계의 어셈블리보다 한 단계 위에 있으면서 기계에는 최대한 가깝게, 그 코드를 다른 기계로 옮길 수 있게 하는 것이 목적이었다([Dennis M. Ritchie, The Development of the C Language, HOPL-II, 1993](https://www.nokia.com/bell-labs/about/dennis-m-ritchie/chist.pdf)). 지향은 그 목적에서 곧장 나온다 — 이식성 있는 저수준 제어, 런타임을 최소로, 그리고 **"프로그래머를 신뢰하라"**는 정신. 검사는 언어가 아니라 프로그래머가 한다는 이 태도가 아래 절 전체의 뿌리다.

B 언어에서 갈라져 나온 C(1972)는 1978년 커니핸·리치의 『The C Programming Language』(K&R)로 사실상의 정의를 얻었고, ANSI C89(1989) → ISO C99·C11·C23으로 개정돼 왔다. 개정은 기능을 더했지만 "프로그래머를 믿고 검사를 언어에 넣지 않는다"는 축은 바꾸지 않았다.

C에서 힙 메모리는 `malloc`으로 얻고 `free`로 돌려준다. 언어가 관리하는 것은 이 두 호출의 문법뿐이고, "이 블록이 아직 살아 있는가", "누가 소유자인가", "몇 바이트짜리인가"는 어디에도 기록되지 않는다. 포인터는 타입이 붙은 주소일 뿐이라 자기가 가리키는 영역의 크기를 모르고, 배열 첨자 `a[i]`는 정의상 `*(a + i)`라는 주소 산술이므로 `i`가 범위 안인지 물어볼 대상 자체가 런타임에 존재하지 않는다.

```c
void credit(long *balances, int idx, long amount) {
    balances[idx] += amount;   // idx가 배열 밖이어도 컴파일도 실행도 막지 않는다
}
```

이것은 구현의 게으름이 아니라 명시된 설계 원칙이다. WG14가 C99 근거 문서에 남긴 **"C의 정신을 지킨다(Keep the spirit of C)"** 절은 그 정신을 다섯 구절로 요약한다 — "프로그래머를 신뢰하라", "프로그래머가 해야 할 일을 못 하게 막지 말라", "언어를 작고 단순하게 유지하라", "한 연산에는 한 가지 방법만 제공하라", "이식성이 보장되지 않더라도 빠르게 만들라"([C99 Rationale, Revision 5.10, 2003-04](https://www.open-std.org/jtc1/sc22/wg14/www/C99RationaleV5.10.pdf) §0). 바로 뒤 해설이 "많은 연산이 일반적인 추상 규칙이 아니라 **대상 기계의 하드웨어가 하는 방식으로** 정의되어 있다"이다.

경계 검사를 넣지 않은 것이 그 귀결이다. 표준은 한 걸음 더 나가 위반을 미정의로 선언한다 — C23 초안 부록 J.2의 미정의 동작 목록 46번은 "**주어진 첨자로 객체에 접근 가능해 보이더라도** 배열 첨자가 범위를 벗어난 경우"를 명시한다. C는 검사를 못 하는 언어가 아니라 **검사하지 않기로 한 언어**다.

## C의 실패 계급 — 즉시 죽는 대신 조용히 오염된 채 진행된다

> 출처: 원고 §3

범위를 벗어난 쓰기가 일어났을 때 무슨 일이 벌어지는지를 표준은 규정하지 않는다. ISO C가 정의하는 **미정의 동작(undefined behavior)**은 "이 국제 표준이 아무런 요구사항도 부과하지 않는" 것이고, 뒤따르는 NOTE가 그 범위를 못박는다 — "상황을 완전히 무시하고 예측 불가능한 결과를 내는 것에서부터 … 번역이나 실행을 진단 메시지와 함께 중단하는 것까지 이른다"([ISO/IEC 9899 위원회 초안 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) §3.4.3 — C23 초안 [N3220](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3220.pdf)에서 §3.5.3으로 번호만 바뀌고 정의는 같다). 여기서 실무적으로 중요한 것은 목록에 "중단한다"가 **선택지 중 하나일 뿐**이라는 점이다. 진단도 중단도 없는 실행이 표준을 어기는 것이 아니다.

컴파일러는 이 자유를 최적화에 쓴다. LLVM 쪽 해설은 직설적이다 — "C의 미정의 동작은 구현에게 하드디스크를 포맷하는 코드나 완전히 예상 밖의 일을 하는 코드를 생성할 재량을 준다"([Chris Lattner, What Every C Programmer Should Know About Undefined Behavior](https://blog.llvm.org/2011/05/what-every-c-programmer-should-know.html), 2011). 같은 글이 흔한 오해를 정정한다 — 널 포인터 역참조는 "트랩하도록 정의되어 있지 않다". 죽어 주는 것은 운영체제가 마침 그 주소를 매핑하지 않았을 때의 우연이지 언어의 보장이 아니다.

메커니즘을 계열로 나누면 왜 신호가 없는지가 분명해진다. Google 보안팀은 공간(spatial)·시간(temporal)·타입(type)·초기화(initialization) 안전성 위반으로 정리한다([Secure by Design: Google's Perspective on Memory Safety](https://research.google/pubs/secure-by-design-googles-perspective-on-memory-safety/), 2024).

**전/후로 보면 신호가 없는 이유가 보인다.** *(Claude 보강 — 원고 서술을 대비 그림으로)*

```text
버퍼 오버플로 (공간)                    해제 후 사용 (시간)
+---------------------------+          +---------------------------+
| 할당 영역 밖을 쓴다         |          | free 이후에도 포인터는 남고 |
| 그 "밖"은 다른 살아있는     |          | 할당자는 그 자리를 재사용   |
|   객체이거나 관리 정보       |          | → 다른 타입 객체가 들어앉음  |
+---------------------------+          +---------------------------+
  → 쓰기는 성공, 프로그램은 계속         → 죽은 포인터로 새 객체 필드를
    나중에 다른 코드가 읽을 때 달라짐        덮어씀 (타입 안전성도 깨짐)
  → 결함 지점과 증상 지점 사이 인과 없음   → 접근 자체는 아무 오류도 안 냄
```

**Heartbleed**가 이 성질의 교과서적 사례다. OpenSSL 권고문의 한 문장이 결함의 전부다 — "TLS heartbeat 확장 처리의 **누락된 경계 검사**로 인해 … 최대 64k의 메모리가 드러날 수 있다"([OpenSSL Security Advisory, 2014-04-07](https://openssl-library.org/news/secadv/20140407.txt), CVE-2014-0160). 서버는 오류를 내지 않았고, 로그도 남기지 않았고, 정상 응답 안에 인접한 힙 메모리를 실어 보냈을 뿐이다. **정상 동작과 최악의 정보 유출이 관측상 구분되지 않는다**는 것이 메모리 안전성 결함의 본질이다.

## 은행에서 이것이 최악인 이유 — 언어 층에서 "조용한 실패"를 기본값으로 받는다

> 출처: 원고 §4

정합성이 1순위인 도메인에서 최악의 실패 유형은 **조용한 실패(silent failure) — 에러 없이 틀린다**이다(부분 실패를 완료로 표시하기, 무음 스킵, 조용한 절단). 어긋났을 때 벌어지는 일이 "초과 승인·이중 출금·돈 증발"인데, 그 어긋남이 예외로 드러나지 않는다는 것이 이 도메인의 어려움이다(참고: [`../../ops-patterns/failure-modes/`](../../ops-patterns/failure-modes/)).

메모리 안전성 결함은 이 실패 유형을 응용 코드가 아니라 **언어 층에서** 제공한다. 차이는 셋이다.

- **응용 층의 방어를 우회한다** — 잔액 불변식을 검사하는 코드가 읽는 그 변수 자체가 다른 코드에 덮어쓰인 값일 수 있으므로, 검사 통과가 정합성의 증거가 되지 못한다.
- **재현되지 않는다** — 같은 입력이 힙 배치·스레드 스케줄에 따라 다르게 깨지므로, 테스트가 잡아 주는 확률이 결함의 심각도와 무관하다.
- **전파 범위가 모듈 경계를 존중하지 않는다** — 승인 모듈의 오프바이원이 원장 모듈의 필드를 바꿀 수 있고, 이 경로는 어떤 아키텍처 다이어그램에도 그려져 있지 않다.

이 계열이 실제로 얼마나 많은지는 공개 통계로 확인된다. MITRE의 2025년 CWE Top 25(공개 CVE 39,080건 대상)에서 상위 25개 중 **일곱이 메모리 계열**이다 — CWE-787 out-of-bounds write(5위), CWE-416 use after free(7위), CWE-125 out-of-bounds read(8위), CWE-120 buffer overflow(11위), CWE-476 NULL deref(13위), CWE-121 stack overflow(14위), CWE-122 heap overflow(16위)([2025 CWE Top 25](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html)). 상위권을 XSS·SQL 인젝션 같은 웹 결함이 차지하는데도 그렇다.

## 그래도 C가 남는 자리 — "빠른 언어"가 아니라 "런타임을 안 깔아도 되는 언어"라서

> 출처: 원고 §5

C가 커널과 임베디드에서 계속 쓰이는 이유는 성능 순위가 아니다. 그 자리들의 공통점은 **의지할 런타임이 아래에 없다**는 것이다. 커널은 자기가 메모리 관리자이므로 힙을 전제하는 언어를 쓸 수 없고, 마이크로컨트롤러는 GC가 돌 여유 메모리가 없으며, 인터럽트 처리 경로는 예측 불가능한 정지를 허용하지 않는다.

Linux 커널이 실제로 그렇게 빌드된다. 최상위 Makefile은 지금도 `-std=gnu11`로 컴파일한다(GNU 확장이 붙은 C11). 동시에 같은 트리에 Rust가 들어와 공식 문서 체계를 갖췄고([The Linux Kernel documentation — Rust](https://docs.kernel.org/rust/)), 새 드라이버를 메모리 안전 언어로 쓰는 경로가 열려 있다. 방향은 분명하다 — **런타임 없는 실행이라는 요구는 남아 있고, 그 요구를 C만 충족한다는 전제가 무너지는 중이다.**

여기서 얻을 교훈이 이 문서 전체에 걸린다. C가 남은 것은 은행 원장 시스템이 필요로 하지 않는 성질 때문이고, 그 시스템이 필요로 하는 성질(정합성 검증, 관측, 빠른 개발) 어디에도 C의 강점이 닿지 않는다. **배제 사유는 "C가 나쁘다"가 아니라 "요구가 겹치지 않는다"이다.**

## C++ — RAII는 해제를 잊는 실패를 지우고, 죽은 것을 가리키는 실패는 못 지운다

> 출처: 원고 §6

1979년 벨 연구소의 비아네 스트롭스트룹이 'C with Classes'로 시작한 것이 뿌리다 — Simula에서 본 추상화(클래스)의 표현력을 C의 성능·제어 위에 얹되, 그 추상화가 **"쓰지 않는 것에는 값을 치르지 않는다(zero-overhead)"**는 규칙을 어기지 않게 하려는 시도였다([Bjarne Stroustrup, A History of C++: 1979–1991](https://www.stroustrup.com/hopl2.pdf); [cppreference — Zero-overhead principle](https://en.cppreference.com/w/cpp/language/Zero-overhead_principle)). §C의 축(네이티브·프로그래머 신뢰)을 그대로 물려받되 그 위에 추상화를 얹은 것이 C++이고, 그 "얹음"이 지우는 실패와 못 지우는 실패를 가르는 것이 주제다. 'C with Classes'(1979)는 1983년 C++로 개명, 1998년 C++98로 표준화됐고 C++11이 스마트 포인터·람다·이동 의미론을 들였다.

C++의 자원 관리 해법은 소멸자와 스코프에 있다. C++ Core Guidelines가 규칙 R.1로 정식화한다 — "자원 핸들과 **RAII**(Resource Acquisition Is Initialization)로 자원을 자동 관리하라 … 생성자에서 획득하고 소멸자에서 해제하라"([C++ Core Guidelines](https://github.com/isocpp/CppCoreGuidelines/blob/master/CppCoreGuidelines.md) R.1). `std::unique_ptr`은 소유권이 하나임을 타입으로 표현하고, `std::shared_ptr`은 참조 계수로 마지막 소유자가 해제하게 한다.

```cpp
{
    auto tx = std::make_unique<Transaction>(id);   // 예외가 나가도 소멸자가 호출된다
    tx->apply();
}   // 스코프를 벗어나는 순간 확정 해제 — free 호출이 코드에 없다
```

이것이 지우는 실패는 실재한다. 이중 해제, 해제 누락, 예외 경로 누수, 조기 반환 누수 — C의 `goto cleanup` 계열이 통째로 사라진다. 하지만 지워지는 것은 **소유권이 명확한 자원의 해제 시점** 문제이지 **참조의 수명** 문제가 아니다. 그리고 UAF(use-after-free)의 본체는 후자다.

RAII와 스마트 포인터가 그대로 두는 것들은 목록으로 셀 수 있다 — 지역 객체에 대한 포인터·참조 반환은 여전히 컴파일된다(규칙 F.43이 "하지 말라"고 금지할 뿐, 언어가 막지 않기에 규칙이 필요하다). `vector`에 원소를 넣으면 재할당으로 기존 반복자·참조가 무효가 되고, 그 무효 참조 사용은 미정의 동작이다. `operator[]`는 경계를 검사하지 않는다. `shared_ptr` 순환 참조는 해제되지 않는다. C API 경계에서는 전부 raw 포인터로 돌아간다. 요약하면 **RAII는 "누가 해제하는가"에 답하지만 "누가 아직 보고 있는가"에는 답하지 않는다.**

가이드라인 자신이 이 부분성을 인정한다 — 경계 안전성은 "**타입 안전성 및 수명 안전성과 결합될 때에만** 완전해지도록 의도되었다." 세 축 중 하나만으로는 보장이 성립하지 않는데, 이 셋을 컴파일러가 강제하는 장치는 아직 표준에 없다(§C++ 실측).

## C++의 실측 — 최고 수준 검증으로도 비율이 안 바뀌고, 바뀐 것은 언어를 바꿨을 때뿐

> 출처: 원고 §7

이 한계가 개인의 숙련도 문제인지 언어의 기본값 문제인지는 통계로 답한다. Chromium 보안팀은 심각도 높음·치명 결함 912건을 분석해 "우리 심각도 높음 보안 결함의 **약 70%가 메모리 비안전성 문제**이고, 그중 절반이 해제 후 사용"이라고 적었다([Chromium — Memory safety](https://www.chromium.org/Home/chromium-security/memory-safety/)). 같은 숫자가 조직을 바꿔도 반복된다 — Chrome 70%, Android 70%, Project Zero가 관측한 실제 공격 제로데이 68%, Microsoft가 CVE를 부여한 취약점 70%([Rebert & Kern, Secure by Design, Google, 2024](https://research.google/pubs/secure-by-design-googles-perspective-on-memory-safety/); Microsoft 수치의 원 발표는 [Matt Miller, BlueHat IL 2019](https://github.com/microsoft/MSRC-Security-Research/tree/master/presentations/2019_02_BlueHatIL)).

각국 보안 기관도 이 통계를 근거로 삼는다 — CISA·NSA·FBI 등 8개 기관 공동 문서([The Case for Memory Safe Roadmaps](https://www.cisa.gov/resources-tools/resources/case-memory-safe-roadmaps), 2023), NSA 정보지([Software Memory Safety](https://media.defense.gov/2022/Nov/10/2003112742/-1/-1/0/CSI_SOFTWARE_MEMORY_SAFETY.PDF), 2022), 미국 국가사이버국장실 보고서([Back to the Building Blocks](https://bidenwhitehouse.archives.gov/wp-content/uploads/2024/02/Final-ONCD-Technical-Report.pdf), 2024)가 "35년 넘게 같은 부류의 결함이 디지털 생태계를 괴롭혀 왔다"고 잇는다(모리스 웜 1988 → 슬래머 2003 → Heartbleed 2014 → BLASTPASS 2023).

이 통계를 읽는 방법이 중요하다. 여기 나오는 코드베이스들은 현대 C++ 관용구, 전담 보안팀, 대규모 퍼징, 새니타이저, 엄격한 코드 리뷰를 전부 갖춘 조직들이고, 그런데도 비율이 바뀌지 않는다. **바뀌는 경우가 하나 있는데 그것이 반증으로서 결정적이다** — Android는 새 네이티브 코드를 메모리 안전 언어로 쓰기 시작하면서 메모리 안전성 결함 비율이 **2019년 76%에서 2024년 24%로** 떨어졌다([Eliminating Memory Safety Vulnerabilities at the Source](https://security.googleblog.com/2024/09/eliminating-memory-safety-vulnerabilities-Android.html), 2024, 2024년 값은 추정치). 비율을 움직인 것은 더 나은 리뷰나 더 많은 퍼징이 아니라 **새 코드를 쓰는 언어**였다.

방향은 확정됐지만 도착은 안 했다. Herb Sutter는 "숙련된 C++ 개발자조차 C++가 **조용히 받아들이는** … '나쁜' 코드를 실수로 작성하기 쉽다"고 쓰고 타입·경계·초기화·수명 네 범주를 지목했으며([C++ safety, in context](https://herbsutter.com/2024/03/11/safety-in-context/), 2024), Stroustrup은 "지침은 큰 코드베이스에서 일관되게 따르는 것이 사실상 불가능하다. 따라서 강제가 필수적이다 … 그 집합을 우리는 **'프로파일'**이라 부른다"고 적었다([21st Century C++](https://www.stroustrup.com/21st-Century-C++.pdf), 2025). 그런데 그 제안은 **C++26에 들어가지 못했고** 목표 릴리스가 C++29다([P4186R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4186r0.html), 2026; [P3970R0](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p3970r0.pdf), 2026).

정리하면 **안전성이 "코딩 규칙과 도구로 보완할 것"에서 "언어가 강제할 것"으로 옮겨 가는 중이며, 그 이동은 빨라야 C++29다.** 새 시스템을 지금 C++로 시작하는 근거는 성능이 아니라 기존 C++ 자산이나 실시간·무런타임 요구 쪽에 가깝다.

## C#/.NET — JVM과 사실상 동형이다: 중간 언어·JIT·세대별 이동 GC

> 출처: 원고 §8

C#은 2000년 마이크로소프트가 .NET 플랫폼과 함께 내놓은 언어로, Turbo Pascal·Delphi를 만든 아네르스 하일스베르그가 설계를 이끌었다. 널리 쓰이는 표현으로 "Java에 대한 마이크로소프트의 답"이고, 첫 버전이 "Java와 많이 닮아" 보였다는 것이 마이크로소프트 자신의 회고다([The history of C#](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-version-history)). 지향(생산성·관리 런타임 위의 안전한 실행·빠른 진화)이 전부 JVM 진영과 겹친다.

C#은 메모리 안전 언어이므로 §C~§C++의 실패 계급이 기본값으로는 발생하지 않는다(`unsafe` 블록과 네이티브 상호운용 제외). 그러면 남는 질문은 "은행 시스템에 기술적으로 충분한가"이고, 답을 얻는 가장 빠른 길은 이미 충분하다고 판정된 JVM과 얼마나 닮았는지 보는 것이다.

실행 모형이 단계까지 같다. Microsoft 문서가 관리 실행을 네 단계로 규정한다 — "① 런타임 대상 컴파일러를 고른다 ② **소스를 공통 중간 언어(CIL)로 번역하고 메타데이터를 생성한다** ③ **실행 시점에 JIT 컴파일러가 CIL을 네이티브 코드로 번역한다** … 타입 안전 검증을 통과해야 한다 ④ 실행한다"([Managed Execution Process](https://learn.microsoft.com/en-us/dotnet/standard/managed-execution-process)). 이 모든 것이 공개 표준 위에 있다 — [ECMA-335 6판(2012)](https://ecma-international.org/publications-and-standards/standards/ecma-335/)(CLI), [ECMA-334 7판(2023)](https://ecma-international.org/publications-and-standards/standards/ecma-334/)(언어).

GC도 같은 계보다. .NET GC는 세대별이며 근거를 명시한다 — "새 객체는 수명이 짧고 오래된 객체는 수명이 길다." 힙을 0·1·2 세대로 나누고, 2세대 수집이 전체 수집(full GC)이며, 85,000바이트 이상은 대형 객체 힙(LOH)으로 간다. 수집은 이동식이다 — "도달 가능한 객체들을 압축한 뒤, 루트가 새 위치를 가리키도록 포인터를 정정한다"([Fundamentals of garbage collection](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/fundamentals)). 처리량용 서버 GC와 지연시간용 백그라운드 GC, 계층형 컴파일(quick JIT + 백그라운드 최적화), OSR까지 대응물이 있다.

**이름만 바꾸면 HotSpot 설명서가 된다.** 그래서 은행 시스템에서 실제로 다투게 되는 축 — GC 정지 시간, 처리량, 메모리 상한, 워밍업, 관측 도구 — 가운데 두 런타임 사이에서 **종류가 다른 것은 없다.** 값이 다를 뿐이고, 그 값은 언어가 아니라 워크로드와 튜닝의 함수다.

## 다른 점 — 값 타입은 C#이 20년 넘게 앞서 있고, AOT는 대가가 명시돼 있다

> 출처: 원고 §9

동형이 아닌 지점이 둘 있다. **하나가 값 타입이다.** C#에서 `struct`는 사용자 정의 값 타입이고, "구조체 타입 변수는 그 데이터를 직접 담는다"([Structure types](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/struct)) — 참조 추적·객체 헤더·할당 압력이 함께 사라진다. `ref struct`는 한 걸음 더 나가 "스택에 할당되며 관리 힙으로 탈출할 수 없다"([ref struct](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/ref-struct)) — `Span<T>`가 바로 이것이다.

JVM 쪽 대응물은 아직 도착하지 않았다. Project Valhalla의 [JEP 401 Value Objects](https://openjdk.org/jeps/401)는 미리보기 단계이고 어떤 정식 JDK에도 아직 없다. 흥미롭게도 이 JEP는 "C와 C#에 있는 것과 같은 struct 기능을 도입하는 것은 목표가 아니다"라고 적는다. C#은 첫 ECMA 표준판(2001)부터 값 타입을 가졌고, JVM은 같은 문제에 20여 년 늦게 다른 설계로 접근하는 중이다.

**다른 하나가 AOT다.** .NET 7의 Native AOT는 "게시 시점에 IL을 네이티브 코드로 컴파일하며, 실행 시 JIT를 쓰지 않는다"([Native AOT deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)). 대가가 문서에 목록으로 박혀 있다는 점이 오히려 중요하다 — **동적 로딩 없음**, **런타임 코드 생성 없음**, 트리밍 필수, 단일 파일 컴파일. 정확한 진술은 "AOT로 켜면 빨라진다"가 아니라 "AOT를 쓰려면 코드와 의존성이 그 제약을 만족해야 한다"이다.

그런데 이 두 차이가 은행 원장 설계의 어떤 결정을 바꾸는가를 물으면 답은 "거의 없다"이다. 값 타입은 할당 압력을 줄이지만 이 시스템의 비용은 DB 왕복과 잠금 대기에 있고, 무결성 방어선은 언어 런타임이 아니라 **컴파일·테스트·DB 세 층**에 둔다. AOT는 배포 형태의 선택지이지 원장 설계의 입력이 아니다.

## 그렇다면 C#은 무엇으로 갈리나 — 기술이 아니라 축적의 분포다 [실무 의견]

> 출처: 원고 §10

전체 사용량으로는 두 언어가 갈리지 않는다. Stack Overflow 2025 설문에서 전문 개발자 기준 C# 29.9%, Java 29.6%로 사실상 동률이다([Developer Survey 2025](https://survey.stackoverflow.co/2025/technology/)).

갈리는 것은 **이 도메인에 축적된 것의 분포**다. 필요한 것은 언어 사용자 수가 아니라 은행 원장·결제·정산을 다뤄 본 코드와 사람과 문서다. 그 축적은 JVM 쪽에 몰려 있다 — 프레임워크(Spring), 국내 금융권 시스템의 다수, 채용 시장, 한국어 자료, 낯선 문제를 검색으로 푸는 확률까지.

**[불확실]** 은행권의 언어 분포를 보여 주는 공개 통계는 확인하지 못했다. Stack Overflow도 JetBrains도 산업×언어 교차 집계를 공개하지 않으므로, 위 문단은 통계가 아니라 관찰이다.

여기서 조심할 것이 하나 있다. "생태계가 크니까 그쪽"은 기술적 판단을 생략해도 된다는 뜻이 아니다. 생태계는 **낯섦을 줄여 stakes를 낮추는 요인**이다. C#으로도 이 시스템을 만들 수 있다는 것과, 이 팀이 이 도메인에서 C#으로 만들었을 때 모르는 것이 더 많아진다는 것은 동시에 참이다.

## 핵심 문장

- **언어는 "얼마나 빠른가"가 아니라 "틀렸을 때 어떻게 틀리는가", "그 도메인의 지식이 어디에 쌓여 있는가", "5년 뒤 이 코드를 누가 고치는가"로 갈린다.**
- **어떤 결함이 "에러 없이 틀린 값을 남긴다"면 그것은 다른 결함보다 한 등급 위다** — 언어 층·동시성·배치 부분 실패 어디서 오든 마찬가지다.
- **C의 배제 사유는 "나쁘다"가 아니라 "요구가 겹치지 않는다"이다** — C는 런타임 없는 실행을 원하는 자리에서 남는다.
- **RAII는 "누가 해제하는가"에 답하지만 "누가 아직 보고 있는가"에는 답하지 않는다** — UAF는 후자다.
- **C#은 C·C++가 아니라 JVM과 같은 진영이다** — 실행 모형이 동형이라 기술이 아니라 생태계에서 갈린다.

## 용어 풀이

- **미정의 동작(Undefined Behavior)** — 표준이 아무 요구사항도 부과하지 않는 동작. 진단·중단은 선택지 중 하나일 뿐이라, 조용히 틀린 채 계속 돌 수 있다.
- **메모리 안전성(Memory Safety)** — 할당 범위·객체 수명·타입·초기화의 규칙을 어긴 접근이 없는 상태. C/C++는 언어가 보장하지 않는다.
- **버퍼 오버플로(Buffer Overflow)** — 할당 영역 밖을 읽거나 쓰는 것(공간 위반). 힙에서 그 "밖"은 대개 다른 살아 있는 객체다.
- **해제 후 사용(Use-After-Free, UAF)** — `free` 이후에도 남은 포인터로 접근하는 것(시간 위반). 그 자리에 다른 타입 객체가 들어앉아 타입 안전성까지 깨진다.
- **RAII(Resource Acquisition Is Initialization)** — 자원을 객체에 캡슐화해 생성자에서 획득, 소멸자에서 해제하는 C++ 관용구. 해제 시점 문제는 지우지만 참조 수명 문제는 못 지운다.
- **스마트 포인터(Smart Pointer)** — 소유권을 타입으로 표현하는 포인터. `unique_ptr`(단일 소유), `shared_ptr`(참조 계수).
- **CIL/IL(Common Intermediate Language)** — .NET이 소스를 먼저 번역해 두는 중간 언어. JVM의 바이트코드에 해당한다.
- **JIT(Just-In-Time Compilation)** — 실행 시점에 중간 코드를 네이티브로 번역하는 것.
- **AOT(Ahead-Of-Time Compilation)** — 배포 전에 미리 네이티브로 컴파일하는 것. 시작이 빠르지만 동적 로딩·리플렉션을 포기한다.
- **값 타입(Value Type)** — 데이터를 참조가 아니라 직접 담는 타입(`struct`). 할당 압력을 줄인다.
- **조용한 실패(Silent Failure)** — 에러 없이 틀린 값을 남기는 실패. 정합성 도메인에서 최악의 유형.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **"메모리 안전 언어(MSL)"라는 용어.** 각국 보안 기관 문서가 쓰는 이 범주는 "언어 차원에서 공간·시간·타입·초기화 안전성을 보장하는 언어"를 뜻한다 — Rust·Go·Java·C#·Python 등이 들어가고 C·C++가 빠진다. 본문의 통계들이 겨냥하는 이분선이 이것이다.
- **오프바이원(off-by-one) 오류.** 반복·인덱싱에서 경계를 하나 넘거나 모자라게 세는 버그. C에서 이 한 칸이 배열 밖 쓰기가 되고, 그것이 곧 §C의 조용한 오염이다. "가장 흔하고 가장 조용한" 결함으로 꼽힌다.
- **제로 오버헤드 원칙의 두 문장.** 스트롭스트룹의 원문은 "쓰지 않는 것에는 비용을 내지 않는다"(첫 문장)와 "쓰는 것은 손으로 짜도 그보다 나을 수 없다"(둘째 문장)로 되어 있다. C++·Rust가 공유하는 이 원칙은 [`rust.md`](rust.md)의 제로 코스트 추상에서 다시 나온다.
- **왜 C#이 아니라 JVM인가는 "동형인데 왜"라는 형태의 질문이다.** 기술이 거의 같을 때 결정은 기술 밖(팀·생태계·기존 자산)으로 넘어간다 — 이것은 언어 선택뿐 아니라 프레임워크·DB 선택에서도 반복되는 판단 형태다.
