# c/syntax/04 — 부동소수점 타입과 변환: 무엇이 보장이고 무엇이 UB 인가 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 이 파일의 모든 출력·경고는 **gcc (Ubuntu 13.3.0-6ubuntu2\~24.04.1) 13.3.0** · x86-64 Linux 에서 실제로 돌려 얻은 것이다.\
> **UB 가 걸린 답(4번)은 `-O0`·`-O2`·sanitizer 셋으로 돌렸다.** `-ffast-math`·`-Ofast` 를 쓴 블록은 그 자리에 밝혔다.\
> 기본 플래그는 `-std=c17 -Wall -Wextra`, 수학 함수를 쓴 프로그램은 `-lm` 을 붙였다.
> ★ **보장이 조건부인 주제다.** 5번의 답은 전부 `__STDC_IEC_559__` 가 정의된 전제 위에 있다.

### 1. `0.1 + 0.2 == 0.3` ★

**출력**

```text
--- double ---
0.1 + 0.2 == 0.3 ? false
0.1       = 0.10000000000000001
0.2       = 0.20000000000000001
0.1 + 0.2 = 0.30000000000000004
0.3       = 0.29999999999999999
차이       = 5.5511151231257827e-17
%g 로 찍으면 : 0.3 vs 0.3
```

```text
--- float / 2진 유한소수 ---
0.1f + 0.2f == 0.3f ? 1              ★
0.1f + 0.2f = 0.300000012   0.3f = 0.300000012
0.5 + 0.25 == 0.75 ? 1
0.1 * 3 == 0.3 ? 0   (0.30000000000000004)
```

**다섯 줄**

- `(0.1 + 0.2) == 0.3` → **`0`(거짓)**
- `%.17g` 세 개 → **`0.10000000000000001` · `0.30000000000000004` · `0.29999999999999999`**
- `%g` 두 개 → **`0.3` · `0.3`** (둘이 같아 보인다)
- `(0.1f + 0.2f) == 0.3f` → **`1`(참)** ★
- `(0.5 + 0.25) == 0.75` → **`1`(참)**

**`float` 쪽이 다른 이유**

```text
  double (유효 비트 53)                 float (유효 비트 24)

  0.1 + 0.2 -> 0.30000000000000004      0.1f + 0.2f -> 0.300000012
  0.3       -> 0.29999999999999999      0.3f        -> 0.300000012
              ^^^^^^^^^^^^^^^^^^^                    ^^^^^^^^^^^
              17자리째에서 갈린다                     ★ 같은 값으로 뭉개졌다
```

- **자릿수가 적어서 오차가 같은 자리로 반올림된 것**이다.
- 그래서 「`0.1 + 0.2 != 0.3` 은 부동소수의 성질」은 **`double` 에 대해서만** 맞다.\
  성질이 아니라 **그 타입·그 값에서의 결과**다.
- 실무 함의: `float` 로 테스트를 짜고 `double` 로 운영하면(또는 반대) **테스트가 못 잡는다.**

**`%g` 와 `%.17g` 가 다른 이유**

- `%g` 의 기본 유효 자릿수는 **6** 이다. `0.30000000000000004` 를 6자리로 반올림하면 `0.3`.
- **진짜 값을 보려면 `%.17g`** 를 써야 한다(`DBL_DECIMAL_DIG` 가 17).
- 화면을 근거로 「같다」고 판단하면 안 되는 이유가 이것이다.

**`0.5 + 0.25 == 0.75` 가 참인 이유**

- 셋 다 **2의 거듭제곱의 합**이라 2진 유한소수다 — `0.5 = 2^-1`, `0.25 = 2^-2`, `0.75 = 2^-1 + 2^-2`.
- **부동소수가 「언제나 부정확」한 게 아니다.** 2진 유한소수가 아닌 값에서만 부정확하다.
- `0.1` 은 2진수로 `0.0001100110011…` 로 끝이 없어서 부정확한 것이다.

### 2. 이 플랫폼의 `long double`

**출력**

```text
sizeof: float=4 double=8 long double=16
FLT_MANT_DIG   = 24   DBL_MANT_DIG = 53   LDBL_MANT_DIG = 64
LDBL_EPSILON   = 1.08420217248550443401e-19
LDBL_MAX       = 1.18973149535723176502e+4932
```

```text
sizeof(long double) = 16, LDBL_MANT_DIG = 64
1.0L 의 바이트: 00 00 00 00 00 00 00 80 ff 3f 00 00 00 00 00 00
  -> 뒤 6바이트는 쓰이지 않는 패딩이다
1.0L + LDBL_EPSILON != 1.0L ? 1
(double)(1.0L + LDBL_EPSILON) == 1.0 ? 1  <- double 로 내리면 사라진다
```

**두 값**

- `sizeof(long double)` = **16** · `LDBL_MANT_DIG` = **64**.

**왜 안 맞나**

```text
  x86-64 의 long double = x87 80비트 확장 형식

  +---------+-------------+--------------------------+
  | 부호 1  |  지수 15    |  유효 비트 64            |  = 80비트 = 10바이트
  +---------+-------------+--------------------------+
  |         ★ 패딩 6바이트 (16바이트 정렬용)          |
  +--------------------------------------------------+

  sizeof 는 16 을 말하고, 정밀도는 64비트뿐이다.
```

- **`sizeof` 는 「차지하는 크기」이지 「정밀도」가 아니다.**
- 실제로 `double`(53비트)보다 유효 비트가 11개 많다 — 위 출력의 마지막 두 줄이 그 증거다.\
  `1.0L + LDBL_EPSILON` 은 `1.0L` 과 다른데, `double` 로 내리면 같아진다.

**바이트 덤프**

```text
00 00 00 00 00 00 00 80 | ff 3f | 00 00 00 00 00 00
^^^^^^^^^^^^^^^^^^^^^^^^   ^^^^^   ^^^^^^^^^^^^^^^^^
 유효 비트 8바이트          지수+부호 2바이트   ★ 패딩 6바이트 (전부 0)
```

- 리틀 엔디언이라 유효 비트가 앞에 온다. `0x8000000000000000` 은 최상위 비트만 1 — x87 의 **명시적 선행 1 비트**다.
- `0x3fff` 는 지수 바이어스 값(1.0 의 지수).
- **뒤 6바이트가 전부 0** 이고 쓰이지 않는다.

**어느 층인가**

- **구현 정의**다. `long double` 은 플랫폼마다 완전히 다르다 —\
  MSVC 는 `double` 과 같은 64비트, ARM 은 128비트 쿼드인 경우가 있다.\
  (이 머신 외의 값은 **확인 못 했다.**)
- 표준이 보장하는 것은 **`float` ≤ `double` ≤ `long double`** 이라는 정밀도 순서뿐이다.

### 3. `(float)16777217`

**출력**

```text
(float)16777216 = 16777216.0
(float)16777217 = 16777216.0   <- 1 이 사라졌다
(float)16777217 == (float)16777216 ? true
(double)9007199254740993 = 9007199254740992.0
1e16 == 1e16 + 1   : 1   (10000000000000000 vs 10000000000000000)
```

**다섯 줄**

- `16777216.0` · **`16777216.0`** · **`true`** · **`9007199254740992.0`** · **`1`(참)**.

**두 수가 무엇의 경계인가**

```text
  16777217 = 2^24 + 1        float 의 유효 비트가 24개
  9007199254740993 = 2^53+1  double 의 유효 비트가 53개

  2^24 까지는 float 가 모든 정수를 정확히 담는다.
  2^24 위부터는 ★ 짝수만 표현된다 (간격이 2)
  2^25 위부터는 4의 배수만 (간격이 4) ...

      ... 16777214  16777215  16777216  [   ]  16777218 ...
                                          ^
                                    16777217 을 담을 자리가 없다
                                    -> 가장 가까운 짝수 16777216 으로 반올림
```

- `1e16 == 1e16 + 1` 도 같은 일이다 — `1e16` 근처에서 `double` 의 눈금 간격이 이미 2다.

**경고**

```text
-- -Wall -Wextra --
(경고 없음)
-- +Wconversion --
ex2.c:4:15: warning: conversion from ‘int’ to ‘float’ changes value from ‘16777217’ to ‘1.6777216e+7f’ [-Wfloat-conversion]
ex2.c:6:16: warning: conversion from ‘long long int’ to ‘double’ may change value [-Wconversion]
```

- **`-Wall -Wextra` 로는 한 건도 안 나온다.**
- `-Wconversion` 을 켜면 나오고, 문구가 **바뀌는 값까지 정확히 말해 준다** — `from ‘16777217’ to ‘1.6777216e+7f’`.
- ★ **그런데 `(float)16777217` 처럼 명시 캐스트를 쓰면 `-Wconversion` 도 조용하다.**\
  위 출력에서 3행(명시 캐스트)에 경고가 안 붙었다. **캐스트가 「알고 한다」는 선언으로 받아들여진다.**\
  즉 캐스트는 값을 안전하게 만드는 게 아니라 **경고를 끈다.**([목록의 **05번 주제**](../05-explicit-casts-and-pointer-conversions/))

**어느 층인가**

- **UB 가 아니다.** 정수 → 부동 변환에서 값이 안 들어가면 **가장 가까운 표현 가능한 값으로 반올림**하는 것이 정의된 동작이다.\
  (어느 쪽으로 반올림하는지는 구현 정의이고, IEEE 754 하에서는 「가장 가까운 쪽, 동점이면 짝수」다 — `FLT_ROUNDS = 1`.)
- 그래서 **sanitizer 도 조용하다.** 4번(반대 방향)과 층이 다르다.
- **가장 조용한 종류의 오류**다 — 에러도 경고도 sanitizer 도 없고 값만 틀린다.

### 4. 부동 → 정수 변환 ★★

**출력**

```text
=== -O0 ===
3 -3 -2147483648 -2147483648 4294967295
(exit 0)
=== -O2 ===
3 -3 2147483647 0 0
(exit 0)
=== ubsan 기본 (-fsanitize=undefined) ===
3 -3 -2147483648 -2147483648 4294967295
        (runtime error 없음 — 아무 말도 안 한다)
=== -fsanitize=undefined,float-cast-overflow ===
ex.c:4:1: runtime error: -1 is outside the range of representable values of type 'unsigned int'
ex.c:3:1: runtime error: nan is outside the range of representable values of type 'int'
3 -3 -2147483648 -2147483648 4294967295
```

**다섯 값과 갈린 개수**

| 식 | `-O0` | `-O2` |
|---|---|---|
| `(int)3.9` | `3` | `3` |
| `(int)-3.9` | `-3` | `-3` |
| `(int)1e10` | **`-2147483648`** | **`2147483647`** |
| `(int)NAN` | **`-2147483648`** | **`0`** |
| `(unsigned)-1.0` | **`4294967295`** | **`0`** |

- **다섯 중 셋이 다르다.**

**종료 코드**

- **둘 다 `0`** 이다. 에러도 경고도 없다.
- 이 갈래의 제1 규칙 — 「안 터졌다」는 「안전하다」가 아니다.

**반올림인가 절단인가**

- **절단**이다. `(int)-3.9` 가 **`-3`** 인 것이 증거다.
- 반올림이면 `-4` 가 나와야 하고, 내림(floor)이어도 `-4` 다.\
  `-3` 이라는 것은 **0 쪽으로 자른다**(truncation toward zero)는 뜻이다.
- 반올림이 필요하면 `<math.h>` 의 `round`·`floor`·`ceil` 을 쓴다.

**`-fsanitize=undefined` 로 돌리면**

- ★ **아무 말도 안 한다.** gcc 13 의 기본 집합에 `float-cast-overflow` 가 **없다.**

**무엇을 더 켜야 하나**

- **`-fsanitize=float-cast-overflow`** 를 명시한다.
- 그런데 켜도 **세 건 중 두 건만 나왔다.** `(int)1e10` 이 빠졌다.\
  이유: `(int)1e10` 과 `(int)NAN` 이 **같은 함수 `to_int` 의 같은 줄**이고,\
  UBSan 은 **같은 소스 위치를 한 번만 보고**한다. (gcc 가 인자를 오른쪽부터 평가해 NAN 쪽이 먼저 걸렸다.)
- ★ **「두 건 나왔다」가 「두 건뿐이다」가 아니다.** 함수를 쪼개야 전수가 보인다.

**막는 법**

```c
if (!(d >= (double)INT_MIN && d <= (double)INT_MAX)) return -1;   /* NaN 도 걸린다 */
int n = (int)d;
```

- `!(...)` 로 쓰는 이유는 5번에서 설명한다 — **NaN 이면 비교가 전부 거짓**이라 `!` 를 씌워야 잡힌다.

### 5. `NaN` 과 무한대

**출력** (기본 `-O2`, `__STDC_IEC_559__` 정의된 상태)

```text
1.0/0.0 = inf  isinf=1
0.0/0.0 = -nan  isnan=1
nan == nan ? false
nan != nan ? true
nan <  1.0 ? false   nan >= 1.0 ? false
inf - inf = -nan
-0.0 == 0.0 ? true
1.0/-0.0 = -inf
```

**각 줄**

- `1.0/0.0` → **`inf`**, `isinf` → **1**
- `0.0/0.0` → **`-nan`**(부호가 붙어 나온다 — 부호는 의미가 없다), `isnan` → **1**
- `nan == nan` → **거짓** · `nan != nan` → **참**
- `nan < 1.0` → **거짓** · `nan >= 1.0` → **거짓**
- `inf - inf` → **`-nan`** · `-0.0 == 0.0` → **참** · `1.0 / -0.0` → **`-inf`**

**둘 다 거짓이면 어떤 추론이 깨지나**

```text
  일반적인 수에서는
      !(x < y)  ==  (x >= y)          <- 언제나 성립

  NaN 에서는
      x <  NaN  ->  거짓
      x >= NaN  ->  ★ 거짓            <- 둘 다 거짓!
      !(x < NaN) -> 참 != (x >= NaN) -> 거짓
```

- **삼분법**(어느 두 수든 `<`·`==`·`>` 중 정확히 하나가 참)이 **깨진다.**
- 실무 함의: 범위 검사를 `if (x < lo || x > hi) reject();` 로 쓰면 **NaN 이 통과한다.**\
  `if (!(x >= lo && x <= hi)) reject();` 로 써야 NaN 이 걸린다.
- 이것이 4번의 `!(...)` 형태가 필요한 이유다.

**`-0.0 == 0.0` 은 참인데 `1.0 / -0.0` 은 `-inf`**

```text
  비교 연산은 ★ 값의 크기만 본다 — +0 과 -0 은 같은 크기다 -> 참

  나눗셈은 ★ 부호 비트를 본다 — 1.0 / (-0) = -inf

  -> 비교로는 구별 못 하는 두 값을 나눗셈은 구별한다.
     (구별하려면 signbit(x) 또는 1.0/x 의 부호를 본다)
```

**어느 조건에서 보장되나**

- **`__STDC_IEC_559__` 가 정의될 때만**이다.

```text
기본        : __STDC_IEC_559__ 정의됨  __FAST_MATH__ 미정의
```

- 이 매크로가 없는 구현에서는 `1.0/0.0` 이 **UB** 이고 `inf` 가 나온다는 보장이 없다.
- 즉 위 여덟 줄은 **전부 조건부 보장**이다. 6번이 그 조건을 깬다.

### 6. `-ffast-math` 를 켜면 ★★

**출력**

```text
##### -O2 -ffast-math #####
1.0/0.0 = inf  isinf=0          ★
0.0/0.0 = 1.000000              ★★
nan == nan ? true               ★
nan != nan ? false              ★
nan <  1.0 ? false   nan >= 1.0 ? true   ★
inf - inf = 0.000000            ★
-0.0 == 0.0 ? true
1.0/-0.0 = -inf
```

**각 답**

- `0.0 / 0.0` → **`1.000000`**. 컴파일러가 `x / x = 1` 로 접었다.
- `isnan(nan_)` → **0** · `isinf(inf)` → **0**. **NaN·Inf 검사 함수가 무력해졌다.**
- `nan == nan` → **참**.
- `inf - inf` → **`0.000000`**.

```text
   같은 소스. -ffast-math 하나 차이.

   기본                              -ffast-math
   +--------------------------+      +--------------------------+
   | 0.0/0.0 = -nan           |      | 0.0/0.0 = 1.000000   ★★  |
   | isnan  = 1               |      | isnan  = 0               |
   | isinf  = 1               |      | isinf  = 0               |
   | nan == nan -> false      |      | nan == nan -> true       |
   | nan >= 1.0 -> false      |      | nan >= 1.0 -> true       |
   | inf - inf = -nan         |      | inf - inf = 0.000000     |
   +--------------------------+      +--------------------------+
```

- 이유: `-ffast-math` 가 포함하는 `-ffinite-math-only` 가 「**이 프로그램에 NaN·Inf 는 없다**」고 컴파일러에게 약속시킨다.\
  그 전제 위에서 `isnan(x)` 는 상수 `0` 으로, `x/x` 는 `1` 로 접힌다.
- **입력 검증을 `isnan` 으로 하던 코드가 통째로 사라진다.** 조용히.

**컴파일러가 알려 주는 방법**

```text
기본        : __STDC_IEC_559__ 정의됨  __FAST_MATH__ 미정의
-ffast-math : __STDC_IEC_559__ 미정의  __FAST_MATH__ 정의됨
```

- **매크로 두 개로 확인된다.**
  - `__STDC_IEC_559__` 가 **사라진다** — IEEE 754 보장을 철회한다는 선언.
  - `__FAST_MATH__` 가 **생긴다** — 이 모드라는 표시.
- 이 갈래에서 드물게 **컴파일러가 정직하게 알려 주는** 자리다.

**`-O3` 와 `-Ofast`**

```text
-O2     : __STDC_IEC_559__ 정의됨  __FAST_MATH__ 미정의
-O3     : __STDC_IEC_559__ 정의됨  __FAST_MATH__ 미정의
-Ofast  : __STDC_IEC_559__ 미정의  __FAST_MATH__ 정의됨   ★
```

- **`-Ofast` 쪽**이다. `-O3` 까지는 안전하다.
- `-Ofast` 는 「`-O3` 보다 조금 더 빠른 것」이 아니라 **언어 보장을 포기하는 모드**다.

### 7. `float` 이 `double` 이 되는 자리

**출력**

```text
printf("%f", float) -> 1.500000   (float 은 double 로 승격되어 전달된다)
가변 인자에 float 를 넘기고 double 로 꺼낸다:
  va_arg(double) = 1.5
  va_arg(double) = 2.5
--- float 연산이 어디서 double 이 되나 ---
float a+b        = 0.300000012
double(a)+double(b) = 0.30000000447034836
a + 0.2 (double 리터럴) = 0.30000000149011613
FLT_EVAL_METHOD = 0
sizeof(a + b) = 4 (float 끼리는 float 로 남는다)
sizeof(a + 0.2) = 8 (double 리터럴이 끼면 double)
```

**두 `sizeof`**

- `sizeof(a + b)` = **4** · `sizeof(a + 0.2)` = **8**.
- **`float` 끼리는 `float` 로 남는다.** 「승격」은 정수에만 있는 규칙이고, 부동소수에는 없다.
- `0.2` 는 **`double` 리터럴**이라 통상 산술 변환이 `a` 를 `double` 로 올린다. `0.2f` 로 써야 `float` 로 남는다.

**세 값이 다른 이유**

```text
  ① float a + float b                       0.300000012
     float 정밀도로 더한다 (유효 비트 24)

  ② (double)a + (double)b                   0.30000000447034836
     ★ float 로 이미 반올림된 두 값을 double 로 올려 더한다
       -> float 의 오차가 그대로 보존되어 보인다

  ③ a + 0.2                                 0.30000000149011613
     a(float 의 0.1) 를 double 로 올리고, 0.2 는 double 의 0.2
       -> 한쪽만 float 오차를 갖는다
```

- **어느 단계에서 올리느냐가 결과를 바꾼다.** 셋 다 「0.3 근사」인데 값이 다르다.
- ②가 ①보다 정확해 보이지만 그렇지 않다 — **이미 잃은 정밀도는 올려도 안 돌아온다.**

**`printf("%f", a)` 가 되는 이유**

- **기본 인자 승격**이다. 프로토타입이 없는 자리(가변 인자의 `...` 부분)에 넘긴 `float` 은 **언제나 `double` 로 승격**된다.
- 그래서 **`%f` 는 `float` 용이 아니라 `double` 용**이다. `float` 전용 지정자는 없다.
- gcc 의 경고 문구가 그것을 말해 준다.

```text
ex2.c:2:57: warning: format ‘%d’ expects argument of type ‘int’, but argument 3 has type ‘double’ [-Wformat=]
```

  소스에는 `float f` 를 줬는데 gcc 가 **`double`** 이라고 한다.

**`va_arg(ap, float)`**

- **틀린 코드다.** `float` 인자는 이미 `double` 로 승격되어 전달됐으므로 `va_arg(ap, double)` 로 꺼내야 한다.
- 위 출력이 그 증거다 — `takes_double(2, f, 2.5f)` 에 `float` 두 개를 넘겼는데 `va_arg(ap, double)` 로 **정확히 `1.5`·`2.5`** 가 나왔다.
- 정본은 목록의 **36번 주제**.

### 8. `FLT_EVAL_METHOD` 가 무엇인가

**출력**

```text
FLT_EVAL_METHOD = 0
```

**이 환경의 값**

- **0** 이다.

**0·1·2 의 뜻**

```text
  0  각 타입을 그 타입의 정밀도로 계산한다        <- 이 환경 (SSE)
  1  float 연산도 double 정밀도로 계산한다
  2  float·double 연산을 전부 long double 정밀도로 계산한다   <- 32비트 x87
 -1  정해지지 않음
```

**2 인 플랫폼에서 달라지는 것**

- `float a, b, c; a = b * c;` 에서 `b * c` 를 **80비트로 계산한 뒤** `float` 로 줄인다.
- 중간 반올림이 한 번 줄어서 **결과가 더 정확해지는데**, 그래서 **`-m64` 와 `-m32` 가 다른 답을 낸다.**
- 고전적인 이식성 사고 지점이다. 이 머신에는 32비트 헤더가 없어 **확인하지 못했다.**

```text
$ gcc -m32 -std=c17 ex.c
/usr/include/stdio.h:28:10: fatal error: bits/libc-header-start.h: 그런 파일이나 디렉터리가 없습니다
```

- **「못 잰 것」이지 「안 돌려 본 것」이 아니다.** `gcc-multilib` 를 설치하면 잴 수 있다.

**어느 층인가**

- **구현 정의**다. 그런데 특이하게 **구현이 값을 매크로로 알려 줄 의무**가 있다 —\
  `<float.h>` 에 `FLT_EVAL_METHOD` 가 있어야 한다.
- 즉 「문서화 의무」가 헤더 매크로로 구체화된 사례다. **물어보면 답해 준다.**

### 9. `__STDC_IEC_559__` 는 무엇을 보장하나

**정의되어 있으면**

- 그 구현의 부동소수 연산이 **IEEE 754 를 따른다**는 보장이다. 구체적으로:
  - `NaN`·`+inf`·`-inf` 가 존재하고 그 성질(`NaN != NaN` 등)이 보장된다.
  - `1.0/0.0` 이 `inf`, `0.0/0.0` 이 `NaN` 이다 — **UB 가 아니다.**
  - 반올림 규칙(가장 가까운 쪽, 동점이면 짝수)이 보장된다.
  - `+0.0` 과 `-0.0` 이 구분되어 저장된다.

**정의되어 있지 않은 구현에서 `1.0/0.0`**

- **UB** 다. 표준의 기본 규칙에서 0 으로 나누기는 정의되지 않았다.
- `inf` 가 나올 수도, 트랩이 걸릴 수도, 아무 일이나 일어날 수도 있다.
- 그래서 UBSan 에 `float-divide-by-zero` 검사가 **있다.** 다만 **기본 집합에는 없다.**

```text
--- -fsanitize=float-divide-by-zero ---
ex2.c:2:44: runtime error: division by zero
inf -nan
--- -fsanitize=undefined 기본 집합 ---
inf -nan                       (아무 말 없음)
```

- ★ **sanitizer 와 이 환경의 보장이 서로 다른 말을 한다.**\
  sanitizer 는 표준의 기본 규칙을 보고 「UB」라 하고, 이 환경은 `__STDC_IEC_559__` 가 있어 「정의됨」이다.
- **「sanitizer 가 말했다」가 곧 「UB 다」가 아니다.** 그래서 이 검사가 기본에서 빠져 있다.

**`-ffast-math` 는**

- **이 매크로를 없앤다.** 보장을 철회한다는 선언이다(6번의 출력).

**이식성 코드에서 쓰는 법**

```c
#ifndef __STDC_IEC_559__
#  error "이 코드는 IEEE 754 부동소수를 요구한다"
#endif
```

- 빌드 시점에 막는다. `-ffast-math`·`-Ofast` 로 빌드하면 **여기서 멈춘다.**
- 이 주제에서 가장 실용적인 방어선이다.

### 10. 어떻게 비교해야 하나

**출력**

```text
== 로 비교        : 0
절대 오차 eps=1e-9 : 1
DBL_EPSILON 로만   : 1
차이 / DBL_EPSILON = 0.250 배
--- 큰 수에서는 절대 오차가 안 통한다 ---
1e16 == 1e16 + 1   : 1   (10000000000000000 vs 10000000000000000)
큰 수에서 eps=1e-9 : 1
상대 오차로         : 1
--- %.17g 는 왕복한다 ---
a -> "0.30000000000000004" -> back == a ? 1
a -> "0.3" -> back == a ? 0  (%.15g 는 왕복 못 한다)
DBL_DIG = 15, 왕복에 필요한 자릿수(DBL_DECIMAL_DIG) = 17
```

**`fabs(a-b) < 1e-9` 가 맞는가**

- **여기서는 맞는다.** 차이가 `5.55e-17` 이라 여유가 크다.
- 하지만 `1e-9` 라는 숫자에 근거가 없다 — **값의 크기에 따라 의미가 달라진다.**

**큰 수에 쓰면**

```text
  1e16 과 1e16 + 1.0 은 ★ 이미 같은 값이다 (눈금 간격이 2)

  fabs(a-b) = 0  ->  어떤 eps 를 줘도 "같다"
  -> 검사가 아무 일도 안 한다
```

- 반대로 `1e16` 과 `1e16 + 4` 처럼 실제로 다른 값이면 차이가 4 라서 `1e-9` 로는 **절대 안 같다고 나온다.**
- **절대 오차는 「1 근처」에서만 의미가 있다.**

**상대 오차**

```c
static int nearly(double a, double b, double eps) { return fabs(a - b) <= eps; }
nearly(big1, big2, DBL_EPSILON * fabs(big1));     /* -> 1 */
```

- `DBL_EPSILON * fabs(a)` 가 「**`a` 근처의 눈금 간격**」이다. 값의 크기에 따라 자동으로 늘어난다.
- 실무에서는 절대·상대를 섞어 쓴다 — `fabs(a-b) <= max(abs_eps, rel_eps * max(|a|,|b|))`.\
  (0 근처에서는 상대 오차가 무의미하기 때문이다.)

**`%.17g` 와 `%.15g`**

- **`%.17g` 가 왕복한다.** `%.15g` 는 못 한다(위 출력).

```text
  DBL_DIG (15)          십진 -> double -> 십진 이 보존되는 자릿수
  DBL_DECIMAL_DIG (17)  double -> 십진 -> double 이 보존되는 자릿수   ★ 이쪽이 크다
```

- **두 매크로가 반대 방향을 말한다.** `DBL_DIG` 를 보고 15자리로 찍으면 값이 상한다.
- 로그·JSON 에 `double` 을 적을 때는 **`%.17g`** 를 쓴다.

### 11. 그래서 무엇을 고르나

**금액에 `double` 을 쓰면 안 되는 이유 — 실측 하나로**

```text
1e16 == 1e16 + 1   : 1
```

- 10경(1e16)에 1을 더해도 **값이 안 변한다.**
- 원 단위로 누적하는 회계 시스템이 이 지점을 넘으면 **입금이 조용히 사라진다.**
- 더 작은 규모에서도 `0.1 + 0.2 != 0.3` 이 그대로 **1원 차이**로 나타난다.
- 결론: **금액은 정수(원·센트 단위)** 로 한다.

**`float` 를 고르는 것이 옳은 상황 둘**

1. **큰 배열·GPU·직렬화** — 메모리와 대역폭이 반이다. 100만 개 배열에서 4MB vs 8MB.
2. **정밀도가 이미 낮은 입력** — 센서 값처럼 원래 유효숫자가 3\~4자리인 데이터.\
  `double` 로 올려도 없는 정밀도가 생기지 않는다.

**부동 → 정수 변환을 안전하게**

```c
#include <math.h>

int safe_to_int(double d, int *out) {
    if (!(d >= (double)INT_MIN && d <= (double)INT_MAX)) return -1;  /* NaN 도 여기서 걸린다 */
    *out = (int)d;
    return 0;
}
```

- **`!(...)` 형태가 핵심**이다. NaN 이면 `>=` 와 `<=` 가 **둘 다 거짓**이라 `&&` 가 거짓이 되고, `!` 로 뒤집으면 참이 되어 걸린다.
- `if (d < INT_MIN || d > INT_MAX) return -1;` 로 쓰면 **NaN 이 통과한다** — 두 비교가 다 거짓이므로.
- 반올림이 필요하면 `lround`·`floor`·`ceil` 을 먼저 쓴다.

**빌드 플래그 한 줄**

```text
개발·운영 빌드
  gcc -std=c17 -O2 -Wall -Wextra -Wconversion -Wfloat-conversion -Werror
  (-Ofast / -ffast-math 는 쓰지 않는다)

테스트 빌드
  gcc -std=c17 -O1 -g -fsanitize=undefined,address,float-cast-overflow \
      -fno-sanitize-recover=all

소스 맨 위
  #ifndef __STDC_IEC_559__
  #  error "이 코드는 IEEE 754 부동소수를 요구한다"
  #endif
```

- `float-cast-overflow` 를 **명시**한다 — 기본 집합에 없다.
- `__STDC_IEC_559__` 검사가 **`-Ofast` 로 빌드하는 것을 막아 준다.**

**구현 의존 항목** — 이 표의 값 중 다음은 **이 환경(x86-64 Linux · gcc 13.3.0 · SSE)에서만** 그렇다.

- `sizeof(long double)`=16 · `LDBL_MANT_DIG`=64 — **플랫폼마다 완전히 다르다.**
- `FLT_EVAL_METHOD`=0 — 32비트 x87 이면 2 이고, 그러면 7번의 세 값이 달라질 수 있다.
- `__STDC_IEC_559__` 가 정의된 것 — 5·9번의 **모든 답이 이 전제 위에 있다.**
- `(int)1e10` 이 `-O0` 에서 `-2147483648`, `-O2` 에서 `2147483647` 인 것 — **UB 라 보장이 아니다.**
- `0.0/0.0` 이 `-nan` 으로 찍히는 것(부호) — NaN 의 부호 비트는 의미가 없다.
- UBSan 기본 집합의 구성 — gcc 의 선택이고 clang 과 다를 수 있다.

**안 돌려 본 것 / 못 잰 것**

- **못 잰 것** — `FLT_EVAL_METHOD` 가 2 인 경우(`-m32`). `bits/libc-header-start.h` 가 없어 컴파일 자체가 안 된다.\
  `gcc-multilib` 를 설치하면 잴 수 있다. **설치 제안만 하고 안 했다.**
- **안 돌려 본 것** — `%a` 서식 · `-ffast-math` 의 개별 하위 플래그(`-ffinite-math-only` 등) 따로 던지기 · `<fenv.h>` 로 반올림 모드 바꾸기.

**버전이 올랐을 때 다시 돌려야 하는 것**

- 4번의 `-O0`/`-O2` 값(UB — 보장이 아니다).
- UBSan 기본 집합에 `float-cast-overflow` 가 들어갔는지(gcc 버전마다 바뀔 수 있다).
- `-Ofast` 가 `__STDC_IEC_559__` 를 없애는지.
