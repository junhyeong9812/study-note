# c/syntax/04 — 부동소수점 타입과 변환: 무엇이 보장이고 무엇이 UB 인가 — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> **기준 소스** — [ISO/IEC 9899 공개 작업 초안 — WG14 프로젝트 문서 목록](https://www.open-std.org/jtc1/sc22/wg14/www/projects) · [cppreference — Floating types (C)](https://en.cppreference.com/w/c/language/arithmetic_types) · [GCC 13 Optimize Options — `-ffast-math`](https://gcc.gnu.org/onlinedocs/gcc-13.3.0/gcc/Optimize-Options.html)
> **실행 검증** — 이 문서의 모든 수치·출력은 **gcc (Ubuntu 13.3.0-6ubuntu2\~24.04.1) 13.3.0** · x86-64 Linux 에서 실제로 돌려 얻은 것이다.\
> **UB 가 걸린 블록(부동→정수 변환)은 `-O0`·`-O2`·sanitizer 셋으로 돌렸다.**\
> `-ffast-math` 를 쓴 블록은 그 자리에 밝혔다. 기본 플래그는 `-std=c17 -Wall -Wextra`.
> **버전** — 부동소수 타입·변환 규칙은 C89 부터 같다. IEEE 754 준수는 **`__STDC_IEC_559__` 가 정의될 때만** 보장된다.
> 이 본문은 Claude 작성이다(원고 없음). 규칙은 위 기준 소스로, 값은 실행으로 접지했다.
> **경계** — 「IEEE 754 의 비트 표현·지수·가수 구조」는 [`../../../../data-representation/`](../../../../data-representation/) 가 정본이다.\
> 여기는 **C 의 타입 선택과 변환 규칙**만 쓴다.

## 한눈에 — 쉽게 말하면

**부동소수점은 「자릿수가 정해진 계산기」다. 자릿수가 모자라면 말없이 반올림한다.**

비유 대응은 문서 끝까지 이것 하나로 고정한다.

| 비유 | 실체 |
|---|---|
| 유효숫자 **7자리**짜리 계산기 | `float` — 유효 비트 24개 ≈ 십진 7자리 |
| 유효숫자 **16자리**짜리 계산기 | `double` — 유효 비트 53개 ≈ 십진 16자리 |
| 유효숫자 **19자리**짜리 계산기 | 이 환경의 `long double` — 유효 비트 64개 |
| 계산기가 **2진수**로 돈다는 것 | `0.1` 을 정확히 못 적는다 — 2진 무한소수다 |
| 큰 수를 넣으면 **끝자리가 안 보인다** | `1e16 + 1 == 1e16` 이 참이 된다 |
| 계산기 화면에 안 나오는 자리 | `%g` 는 반올림해 보여 준다 — `%.17g` 로 봐야 진짜 값이 보인다 |

- 1/3 을 10진수로 적으면 `0.3333…` 로 끝이 없다.\
  **똑같이** 0.1 을 2진수로 적으면 `0.0001100110011…` 로 끝이 없다.
- 그래서 `0.1` 을 담은 `double` 은 0.1 이 아니라 **`0.10000000000000001`** 이다.
- 자릿수가 모자라면 계산기는 **에러를 내지 않고 반올림한다.** 그게 이 주제의 전부다.

```text
   0.1 + 0.2 == 0.3 ?

   0.1       -> 0.10000000000000001    (진짜 값)
   0.2       -> 0.20000000000000001
   0.1 + 0.2 -> 0.30000000000000004    <- 더한 결과
   0.3       -> 0.29999999999999999    <- 0.3 을 담은 값

   -> 다르다. 차이는 5.55e-17
   그런데 %g 로 찍으면 둘 다 "0.3" 이다.
```

실무에서 이게 터지는 자리는 **금액 계산과 누적 합**이다.\
`double` 로 원 단위를 더하면 1원씩 틀리기 시작하고, **테스트는 작은 수로만 돌아서 안 걸린다.**

> **유효 비트(significand / mantissa)** — 부동소수 값에서 「숫자 부분」을 담는 비트 수.\
> 예: `float` 은 24비트라 약 십진 7자리, `double` 은 53비트라 약 16자리를 구분할 수 있다.\
> `<float.h>` 의 `FLT_MANT_DIG`·`DBL_MANT_DIG` 가 이 값을 말해 준다.

> **IEEE 754** — 부동소수 표현·연산을 정한 국제 표준. NaN·무한대·반올림 규칙이 여기서 온다.\
> 예: C 는 IEEE 754 를 **강제하지 않는다.** 구현이 따르면 `__STDC_IEC_559__` 매크로를 정의해 알린다.

## 이 주제가 답하려는 질문

원고가 없는 문법 주제라 「문제」 대신 이 세 질문을 둔다.

1. `float` 과 `double` 을 섞으면 **어느 타입으로 계산되고 어디서 정밀도가 사라지는가.**
2. 정수 ↔ 부동소수 변환에서 **말없이 값이 바뀌는 자리**와 **UB 가 되는 자리**는 각각 어디인가.
3. `NaN`·무한대는 **언어가 보장하는 것인가** — 그리고 그 보장을 깨는 플래그는 무엇인가.

## 동작 방식

### (1) 이 플랫폼의 실제 값 — 찍어서 확인한다

**언제 쓰나** — 정밀도가 걸린 판단을 하기 전에 언제나.

```text
sizeof: float=4 double=8 long double=16
__STDC_IEC_559__ = 1 (IEEE 754 준수 선언)
FLT_RADIX      = 2
FLT_MANT_DIG   = 24   DBL_MANT_DIG = 53   LDBL_MANT_DIG = 64
FLT_DIG        = 6   DBL_DIG      = 15   LDBL_DIG      = 18
FLT_EPSILON    = 1.1920929e-07
DBL_EPSILON    = 2.2204460492503131e-16
LDBL_EPSILON   = 1.08420217248550443401e-19
FLT_MAX        = 3.40282347e+38   FLT_MIN = 1.17549435e-38
DBL_MAX        = 1.7976931348623157e+308  DBL_MIN = 2.2250738585072014e-308
LDBL_MAX       = 1.18973149535723176502e+4932
FLT_EVAL_METHOD = 0
DECIMAL_DIG    = 21  FLT_ROUNDS = 1
```

그림 해설 (한 단계씩):

- **`long double` 이 16바이트인데 유효 비트는 64뿐이다.** `sizeof` 와 정밀도가 따로 논다.

```text
  long double (x86-64) = 16바이트를 차지하지만

  +--------+--------+--------+--------+
  |  유효 비트 64 + 지수 15 + 부호 1   |  = 80비트 (10바이트)
  +--------+--------+--------+--------+
  | ★ 나머지 6바이트는 정렬용 패딩      |
  +--------+--------+--------+--------+
```

  실제 바이트를 찍어 확인했다.

```text
sizeof(long double) = 16, LDBL_MANT_DIG = 64
1.0L 의 바이트: 00 00 00 00 00 00 00 80 ff 3f 00 00 00 00 00 00
  -> 뒤 6바이트는 쓰이지 않는 패딩이다
```

- **`__STDC_IEC_559__` 가 정의되어 있다** — 이 구현이 IEEE 754 를 따른다고 선언한 것이다.\
  이것이 정의되어 있어야 `NaN`·`inf`·「0으로 나누면 inf」가 **보장**이 된다.
- **`FLT_EVAL_METHOD = 0`** — 「각 타입을 그 타입의 정밀도로 계산한다」는 뜻이다.\
  x86-64 는 SSE 를 쓰므로 0 이고, 옛날 32비트 x87 은 2(전부 `long double` 로 계산)였다.\
  (`-m32` 은 이 머신에 헤더가 없어 **확인 못 했다.**)
- `FLT_ROUNDS = 1` — 반올림 모드가 「가장 가까운 쪽으로, 동점이면 짝수로」.

비용 — 없다. 헤더 매크로를 찍는 것뿐이다.

### (2) `0.1 + 0.2 != 0.3` — 그런데 `float` 에서는 참이다

**언제 쓰나** — 부동소수 비교를 판단할 때. **널리 알려진 예제인데 절반만 맞다.**

```text
--- double ---
0.1 + 0.2 == 0.3 ? false
0.1       = 0.10000000000000001
0.2       = 0.20000000000000001
0.1 + 0.2 = 0.30000000000000004
0.3       = 0.29999999999999999
차이       = 5.5511151231257827e-17
%g 로 찍으면 : 0.3 vs 0.3
DBL_EPSILON = 2.2204460492503131e-16
```

```text
--- float ---
0.1f + 0.2f == 0.3f ? 1              ★ 참이다
0.1f + 0.2f = 0.300000012   0.3f = 0.300000012
```

그림 해설 (한 단계씩):

- **`float` 에서는 `0.1f + 0.2f == 0.3f` 가 참이다.**\
  유효 비트가 24개뿐이라 **반올림 오차가 같은 자리로 뭉개진 것**이다.
- 「`0.1 + 0.2 != 0.3` 은 부동소수의 성질」이라는 말은 **`double` 에 대해서만 맞다.**\
  타입을 바꾸면 결과가 바뀐다 — 그러니 **성질이 아니라 그 타입의 결과**다.
- 차이 `5.55e-17` 은 `DBL_EPSILON`(`2.22e-16`)의 **0.25배**다. 실제로 찍었다.

```text
== 로 비교        : 0
절대 오차 eps=1e-9 : 1
DBL_EPSILON 로만   : 1
차이 / DBL_EPSILON = 0.250 배
```

- **`%g` 로 찍으면 둘 다 `0.3`** 이다. 화면만 보면 같아 보인다 —\
  **진짜 값을 보려면 `%.17g`** 를 써야 한다.

비용 — 없다. 값이 다를 뿐이다.

### (3) 큰 수에서는 1을 더해도 안 변한다

**언제 쓰나** — 누적 합·카운터·ID 를 `double` 에 담을 때.

```text
1e16 == 1e16 + 1   : 1   (10000000000000000 vs 10000000000000000)
큰 수에서 eps=1e-9 : 1
상대 오차로         : 1
```

```text
  double 의 유효 비트 53개

  작은 수            1.0 근처        -> 이웃한 값 사이 간격 약 2.2e-16
  큰 수              1e16 근처       -> 이웃한 값 사이 간격 약 2
                                        ★ 1 을 더해도 같은 값으로 반올림된다

  +--------------------------------------------------------+
  |  값이 커질수록 "눈금 간격"이 커진다                        |
  |  0.5 근처:  간격 1.1e-16                                 |
  |  1e16 근처: 간격 2                                       |
  +--------------------------------------------------------+
```

그림 해설 (한 단계씩):

- **`1e16 == 1e16 + 1` 이 참**이다. 더한 1이 통째로 사라졌다.
- 그래서 **절대 오차 비교(`fabs(a-b) < 1e-9`)는 큰 수에서 무의미**하다 — 이미 같은 값이다.
- 큰 수에서 쓸 비교는 **상대 오차**다: `fabs(a-b) <= DBL_EPSILON * fabs(a)`.
- 정수 ID 를 `double` 에 담으면 **2^53 을 넘는 순간 서로 다른 ID 가 같아진다.**\
  (JSON 이 숫자를 `double` 로 읽는 언어들에서 실제로 나는 사고다.)

비용 — 없다. 비교 방식의 문제다.

### (4) 정수 → 부동소수: 말없이 잘린다 / 부동소수 → 정수: UB 가 된다

**언제 쓰나** — 두 세계를 오갈 때마다. **방향에 따라 층이 다르다.**

```text
   정수 -> 부동소수                      부동소수 -> 정수
   ----------------                      ----------------
   값이 안 들어가면                        소수부는 ★ 버린다 (반올림 아님)
     -> ★ 가장 가까운 값으로 반올림          정수부가 목표 타입에 안 들어가면
     -> 정의된 동작 (구현 정의 방향)            -> ★ UB
     -> 에러도 경고도 없다                   NaN/Inf 를 넣어도 -> ★ UB
```

```text
--- 정수 -> 부동 정밀도 ---
(float)16777216 = 16777216.0
(float)16777217 = 16777216.0   <- 1 이 사라졌다
(float)16777217 == (float)16777216 ? true
(double)9007199254740993 = 9007199254740992.0
```

- `16777216` 은 `2^24` 다. `float` 의 유효 비트가 24개라 **그 위부터 짝수만 표현된다.**
- `9007199254740993` 은 `2^53 + 1` 이다. `double` 도 같은 일이 난다.
- **경고 하나 없다.** `-Wconversion` 을 켜면 나온다.

```text
18:15: warning: conversion from ‘long int’ to ‘float’ may change value [-Wconversion]
19:16: warning: conversion from ‘double’ to ‘int’ changes value from ‘3.8999999999999999e+0’ to ‘3’ [-Wfloat-conversion]
```

반대 방향은 UB 다. **세 수준으로 돌렸다.**

```text
##### -O0 #####
(int)3.9   = 3
(int)-3.9  = -3
(int)1e10  = -2147483648      ★
(int)NaN   = -2147483648
(unsigned)-1.0 = 4294967295   ★
##### -O2 #####
(int)3.9   = 3
(int)-3.9  = -3
(int)1e10  = 2147483647       ★ 달라졌다
(int)NaN   = -2147483648
(unsigned)-1.0 = 0            ★ 달라졌다
##### -fsanitize=undefined (기본 집합) #####
(int)1e10  = -2147483648      <- 아무 말도 안 한다 ★
##### -fsanitize=float-cast-overflow #####
ex.c:4:1: runtime error: 1e+10 is outside the range of representable values of type 'int'
ex.c:5:1: runtime error: -nan is outside the range of representable values of type 'int'
ex.c:6:1: runtime error: -1 is outside the range of representable values of type 'unsigned int'
```

그림 해설 (한 단계씩):

- **`(int)1e10` 이 `-O0` 에서 `-2147483648`, `-O2` 에서 `2147483647`** 이다. 다섯 값 중 둘이 갈렸다.
- `(unsigned)-1.0` 도 `4294967295` ↔ `0` 으로 갈린다.
- **둘 다 에러 없이 exit 0** 이다. 「안 터졌다」는 「안전하다」가 아니다.
- ★ **`-fsanitize=undefined` 기본 집합에 `float-cast-overflow` 가 없다.** 따로 켜야 잡힌다.\
  이 주제에서 도구를 믿을 때 가장 조심할 자리다.
- `(int)3.9` 가 `3` 이고 `(int)-3.9` 가 `-3` 인 것은 **절단(0 쪽으로)** 이다. 반올림이 아니다.

비용 — 검사 한 줄이다. `if (d >= INT_MIN && d <= INT_MAX)` 로 막는다.

### (5) `NaN` 과 무한대 — 그리고 `-ffast-math` 가 그것을 깬다

**언제 쓰나** — 0으로 나누거나 정의되지 않은 연산을 할 때. 그리고 **최적화 플래그를 고를 때.**

```text
##### 기본 (-O2) #####
1.0/0.0 = inf  isinf=1
0.0/0.0 = -nan  isnan=1
nan == nan ? false
nan != nan ? true
nan <  1.0 ? false   nan >= 1.0 ? false
inf - inf = -nan
-0.0 == 0.0 ? true
1.0/-0.0 = -inf
```

```text
##### -ffast-math -O2 #####
1.0/0.0 = inf  isinf=0          ★
0.0/0.0 = 1.000000              ★★
nan == nan ? true               ★
nan != nan ? false              ★
nan <  1.0 ? false   nan >= 1.0 ? true   ★
inf - inf = 0.000000            ★
-0.0 == 0.0 ? true
1.0/-0.0 = -inf
```

```text
   같은 소스. -ffast-math 하나 차이.

   기본                              -ffast-math
   +--------------------------+      +--------------------------+
   | 0.0/0.0 = -nan           |      | 0.0/0.0 = 1.000000   ★★  |
   | isnan  = 1               |      | isnan  = 0               |
   | nan == nan -> false      |      | nan == nan -> true       |
   | inf - inf = -nan         |      | inf - inf = 0.000000     |
   | __STDC_IEC_559__ 정의됨   |      | __STDC_IEC_559__ ★ 미정의 |
   +--------------------------+      +--------------------------+
```

그림 해설 (한 단계씩):

- **`0.0 / 0.0` 이 `1.000000`** 이 됐다. 컴파일러가 `x/x = 1` 로 접은 것이다.
- **`isnan`·`isinf` 가 0 을 돌려준다.** NaN 검사 코드가 통째로 무력해진다.
- **`nan == nan` 이 참**이 된다. NaN 의 정의 자체가 사라졌다.
- 그리고 컴파일러가 **정직하게 알려 준다** — `__STDC_IEC_559__` 를 **정의하지 않는다.**

```text
기본        : __STDC_IEC_559__ 정의됨   __FAST_MATH__ 미정의
-ffast-math : __STDC_IEC_559__ 미정의   __FAST_MATH__ 정의됨
```

- **「IEEE 754 를 따른다」는 보장이 플래그 하나로 철회된다.**\
  그래서 `__STDC_IEC_559__` 를 `#if` 로 검사하는 코드가 의미가 있다.
- **NaN 의 성질**(기본 빌드에서):

```text
  NaN 과의 비교는 == != < > <= >= 중 != 만 참이다.

         x == NaN    거짓
         x != NaN    ★ 참
         x <  NaN    거짓
         x >= NaN    거짓        <- !(x < NaN) 이 아니다!

  -> "x < y 가 거짓이면 x >= y" 라는 추론이 NaN 에서 깨진다.
```

  출력에서 `nan < 1.0` 과 `nan >= 1.0` 이 **둘 다 거짓**인 것이 그 증거다.

- `-0.0 == 0.0` 은 **참**이다(부호가 달라도 같다고 비교된다).\
  그런데 `1.0 / -0.0` 은 `-inf` 다 — **비교로는 구별이 안 되는데 나눗셈으로는 구별된다.**

비용 — `-ffast-math` 는 빠르지만 **IEEE 754 계약을 통째로 포기**한다. 금액·과학 계산에는 쓰지 않는다.

> **NaN(Not a Number)** — 정의되지 않은 연산의 결과를 담는 특수한 부동소수 값.\
> 예: `0.0/0.0`, `inf - inf`, `sqrt(-1)`. **자기 자신과도 같지 않다**는 것이 정의다.

### (6) `float` 이 `double` 이 되는 자리

**언제 쓰나** — `float` 을 함수에 넘기거나 `printf` 에 쓸 때.

```text
printf("%f", float) -> 1.500000   (float 은 double 로 승격되어 전달된다)
가변 인자에 float 를 넘기고 double 로 꺼낸다:
  va_arg(double) = 1.5
  va_arg(double) = 2.5
--- float 연산이 어디서 double 이 되나 ---
float a+b        = 0.300000012
double(a)+double(b) = 0.30000000447034836
a + 0.2 (double 리터럴) = 0.30000000149011613
FLT_EVAL_METHOD = 0
sizeof(a + b) = 4 (float 끼리는 float 로 남는다)
sizeof(a + 0.2) = 8 (double 리터럴이 끼면 double)
```

```text
  float 이 double 이 되는 자리 세 곳

  ① 가변 인자 (printf 포함)        ★ 기본 인자 승격 — 언제나
     printf("%f", f)  ->  f 는 double 로 전달된다. %f 가 double 용인 이유.

  ② double 과 섞인 연산            통상 산술 변환
     a + 0.2   ->  0.2 는 double 리터럴이므로 a 가 double 로

  ③ FLT_EVAL_METHOD 가 1 이나 2 인 플랫폼   ★ 이 환경은 0 이라 안 일어난다
     float 연산을 더 넓은 정밀도로 하고 나중에 줄인다
```

그림 해설 (한 단계씩):

- `printf("%f", f)` 에 `float` 을 줘도 되는 이유가 **기본 인자 승격**이다 — 프로토타입이 없는 자리에서는 `float` 이 무조건 `double` 이 된다.\
  그래서 `%f` 는 `float` 용이 아니라 **`double` 용**이고, `va_arg(ap, float)` 는 **틀린 코드**다.
- `sizeof(a + b)` 가 **4** 다 — `float` 끼리는 `float` 로 남는다. 승격은 **정수에만** 있는 규칙이다.
- `a + 0.2` 는 8 이다 — `0.2` 는 `double` 리터럴이다. `0.2f` 로 써야 `float` 로 남는다.
- 세 값이 전부 다르다: `0.300000012`(float 끼리) / `0.30000000447034836`(double 로 올려 더함) / `0.30000000149011613`(한쪽만 double).\
  **어디서 올리느냐가 결과를 바꾼다.**
- gcc 의 경고 문구가 승격을 그대로 말해 준다.

```text
ex2.c:2:57: warning: format ‘%d’ expects argument of type ‘int’, but argument 3 has type ‘double’ [-Wformat=]
```

  소스에는 `float f` 를 줬는데 gcc 가 **`double`** 이라고 말한다.

비용 — `float` 의 메모리 이득은 **배열에서만** 의미가 있다. 계산은 대개 `double` 로 간다.

### (7) 정밀도를 안 잃고 문자열로 왕복하기

**언제 쓰나** — 로그·JSON·설정 파일에 `double` 을 적을 때.

```text
a -> "0.30000000000000004" -> back == a ? 1
a -> "0.3" -> back == a ? 0  (%.15g 는 왕복 못 한다)
DBL_DIG = 15, 왕복에 필요한 자릿수(DBL_DECIMAL_DIG) = 17
```

- **`%.17g` 는 왕복한다**(`double` → 문자열 → `double` 이 비트까지 같다).
- **`%.15g` 는 못 한다.** `DBL_DIG` 가 15 라는 것은 「**십진 15자리를 `double` 에 넣었다 빼면 같다**」는 뜻이지 그 반대가 아니다.
- 두 매크로가 다른 방향을 말한다:

```text
  DBL_DIG (15)          십진 -> double -> 십진 이 보존되는 자릿수
  DBL_DECIMAL_DIG (17)  double -> 십진 -> double 이 보존되는 자릿수   ★ 이쪽이 크다
```

## 문법 — 형태와 규칙

### 형태 — 리터럴과 접미사

```c
float       f = 1.5f;     /* f / F 접미사가 없으면 double 이다 */
double      d = 1.5;      /* 기본 */
long double l = 1.5L;     /* L 접미사 */

float g = 0.1;            /* ★ double 로 계산한 뒤 float 로 줄인다 */
float h = 0.1f;           /* float 로 바로 */
```

`_Generic` 으로 확인한 타입이다.

```text
1.0                    -> double
1.0f                   -> float
1.0L                   -> long double
```

### 금지 사례 — 조용히 틀리는 네 형태

```c
/* (1) == 로 비교 */
if (a + b == c) { }

/* (2) float 을 double 리터럴과 비교 */
float f = 0.3f;
if (f == 0.3) { }               /* 거짓 — 0.3 은 double 이다 */

/* (3) 범위 검사 없이 정수로 변환 */
int n = (int)d;                 /* d 가 범위 밖이면 UB */

/* (4) NaN 을 부등호 하나로 거른다 */
if (!(x < limit)) reject();     /* x 가 NaN 이면 여기로 온다 — 의도인지 확인 */
```

(2)를 돌려 봤다.

```text
float 0.3 을 double 로 보면 0.30000001192092896
f == 0.3 (double 리터럴)? 0   <- float 을 double 리터럴과 비교하지 마라
f == 0.3f ? 1
```

- `float` 을 `double` 로 올리면 **0.3 이 아니라 `0.30000001192092896`** 이다.\
  `float` 의 반올림 오차가 그대로 드러난다.
- 접미사 `f` 하나로 참·거짓이 갈린다.

### 규칙 불릿

- 접미사가 없는 부동소수 리터럴은 **`double`** 이다.
- `float` 끼리의 연산은 **`float` 로 남는다**(이 환경, `FLT_EVAL_METHOD == 0`).
- 가변 인자에 넘긴 `float` 은 **언제나 `double` 로 승격**된다.
- 정수 → 부동: 안 들어가면 **반올림**(정의됨). 부동 → 정수: 소수부 **절단**, 범위 밖이면 **UB**.
- `NaN` 은 **`!=` 만 참**이다. `<` 와 `>=` 가 **둘 다 거짓**일 수 있다.
- `-0.0 == 0.0` 은 **참**이다.
- **`__STDC_IEC_559__` 가 정의될 때만** IEEE 754 동작이 보장된다.
- `%.17g`(`DBL_DECIMAL_DIG`)로 찍어야 왕복한다.

## 어디서 틀리나

### 1. `==` 로 비교한다

```text
== 로 비교        : 0
절대 오차 eps=1e-9 : 1
DBL_EPSILON 로만   : 1
--- 큰 수에서는 절대 오차가 안 통한다 ---
1e16 == 1e16 + 1   : 1
큰 수에서 eps=1e-9 : 1
상대 오차로         : 1
```

- **`==` 를 고치는 정답이 하나가 아니다.**
  - 작은 수 근처 — 절대 오차(`fabs(a-b) < 1e-9`)가 통한다.
  - 큰 수 근처 — 절대 오차가 **무의미**하다(이미 같다). 상대 오차를 써야 한다.
- 진짜 결론: **금액은 부동소수로 안 한다.** 정수 단위(원·센트)로 하거나 십진 타입을 쓴다.

### 2. 「`0.1 + 0.2 != 0.3` 은 부동소수의 성질」이라고 외운다

- **`float` 에서는 참이다**(`0.1f + 0.2f == 0.3f` → `1`).
- 성질이 아니라 **그 타입·그 값에서의 결과**다.
- 그래서 `float` 로 테스트를 짜고 `double` 로 운영하면 **테스트가 못 잡는다.** 반대도 마찬가지다.

### 3. `-ffast-math` 를 「그냥 빠르게」로 읽는다

- `isnan`·`isinf` 가 **0 을 돌려주고**, `0.0/0.0` 이 **`1.000000`** 이 된다.
- NaN 검사로 입력을 거르던 코드가 **통째로 무력해진다.**
- 확인하는 법: **`__STDC_IEC_559__` 가 정의되어 있는지 본다.** `-ffast-math` 는 이것을 없앤다.
- `-Ofast` 가 `-ffast-math` 를 포함한다 — **`-Ofast` 를 무심코 쓰면 같은 일이 난다.** 던져서 확인했다.

```text
-O2     : __STDC_IEC_559__ 정의됨  __FAST_MATH__ 미정의
-O3     : __STDC_IEC_559__ 정의됨  __FAST_MATH__ 미정의
-Ofast  : __STDC_IEC_559__ 미정의  __FAST_MATH__ 정의됨
```

- **`-O3` 까지는 안전하고 `-Ofast` 에서 경계가 넘어간다.** 「`-O3` 보다 조금 더 빠른 것」이 아니다.

### 4. 부동 → 정수 변환에 범위 검사를 안 한다

- `-O0` 과 `-O2` 가 **다른 값**을 낸다(`-2147483648` ↔ `2147483647`).
- **`-fsanitize=undefined` 기본 집합이 안 잡는다.** `float-cast-overflow` 를 따로 켜야 한다.
- 막는 법:

```c
if (!(d >= (double)INT_MIN && d <= (double)INT_MAX)) return -1;  /* NaN 도 걸린다 */
int n = (int)d;
```

- `!(...)` 형태를 쓰는 이유: **NaN 이면 비교가 전부 거짓**이라 `!` 를 씌워야 걸린다.

## 구현 세부사항 대 언어 보장

C 에서는 **「돌아갔다」가 아무것도 증명하지 못한다.** 네 층을 갈라야 한다.\
이 주제는 「**보장이 조건부**」라는 점이 특이하다 — `__STDC_IEC_559__` 가 정의되어야 IEEE 754 동작이 보장된다.

| 층 | 뜻 | 이 주제에서 해당하는 것 | 어떻게 확인했나 |
|---|---|---|---|
| **표준이 정한 것** | 어느 구현에서도 같다 | 리터럴의 기본 타입이 `double` · 접미사 규칙 · 가변 인자에서 `float` → `double` 승격 · 통상 산술 변환의 부동소수 단계 · 부동→정수는 **절단**(반올림 아님) · 범위 밖 변환이 **UB** · `<float.h>` 매크로가 존재한다는 것 | `_Generic` · `sizeof` · `va_arg` 실행 · `-O0/-O2/sanitizer` |
| **표준이 조건부로 정한 것** ★ | `__STDC_IEC_559__` 가 정의되면 IEEE 754 동작이 보장된다 | `NaN != NaN` · `1.0/0.0 == inf` · `-0.0 == 0.0` · 반올림 규칙 · `0.0/0.0` 이 NaN | `__STDC_IEC_559__ = 1` 확인 후 실행 · **`-ffast-math` 로 매크로가 사라지는 것까지** |
| **구현 정의** | 구현마다 다르되 **문서화 의무가 있다** | `sizeof(long double)`=16 · `LDBL_MANT_DIG`=64 · `FLT_EVAL_METHOD`=0 · `FLT_ROUNDS`=1 · `DBL_MAX`·`DBL_EPSILON` 등 모든 `<float.h>` 값 · 정수→부동에서 안 들어갈 때 어느 쪽으로 반올림하나 | `<float.h>` 출력 · `long double` 바이트 덤프 |
| **미명시** | 몇 가지 중 하나, 문서화 의무 없음 | 중간 계산을 더 넓은 정밀도로 할지(플랫폼이 `FLT_EVAL_METHOD` 로 **알려 주므로** 여기서는 구현 정의 쪽에 가깝다) | `FLT_EVAL_METHOD = 0` |
| **UB** | 아무 일이나 일어날 수 있다 | **부동 → 정수 변환에서 정수부가 범위 밖** · **NaN/Inf 를 정수로 변환** · (`__STDC_IEC_559__` 가 **없는** 구현에서의 0 나누기) | `-O0` ↔ `-O2` 가 **다른 값** · `float-cast-overflow` 로 잡음 |

### 조건부 보장을 출력으로 — `__STDC_IEC_559__`

```text
기본        : __STDC_IEC_559__ 정의됨   __FAST_MATH__ 미정의
-ffast-math : __STDC_IEC_559__ 미정의   __FAST_MATH__ 정의됨
```

- **컴파일러가 보장의 유무를 매크로로 알려 준다.** 이 갈래에서 드물게 「물어보면 답하는」 자리다.
- 그래서 이식성이 필요한 코드는 이렇게 쓴다.

```c
#ifndef __STDC_IEC_559__
#  error "이 코드는 IEEE 754 를 요구한다"
#endif
```

- 그리고 `-ffast-math` 로 그 보장이 **실제로 깨진다는 것**을 위 (5)의 출력이 보여 준다.\
  「보장이 사라진다」가 이론이 아니라 **`0.0/0.0 = 1.000000`** 이라는 출력이다.

### UB 를 출력으로

```text
ex.c:4:1: runtime error: 1e+10 is outside the range of representable values of type 'int'
ex.c:5:1: runtime error: -nan is outside the range of representable values of type 'int'
ex.c:6:1: runtime error: -1 is outside the range of representable values of type 'unsigned int'
```

- **세 건 다 `-fsanitize=float-cast-overflow` 를 따로 켜야 나온다.**\
  `-fsanitize=undefined` 만으로는 **한 건도 안 나온다.**
- 그리고 `-O0`/`-O2` 의 값이 다르다 — UB 의 표준적인 증상이다.

```text
  -O0 : (int)1e10 = -2147483648   (unsigned)-1.0 = 4294967295
  -O2 : (int)1e10 =  2147483647   (unsigned)-1.0 = 0
        둘 다 exit 0. 에러 없음.
```

### 부동소수 나누기 0 — 층이 갈리는 자리

```text
--- -fsanitize=float-divide-by-zero ---
ex2.c:2:44: runtime error: division by zero
inf -nan
--- -fsanitize=undefined 기본 집합 ---
inf -nan                       (아무 말 없음)
```

- sanitizer 는 `division by zero` 라고 말하지만, **`__STDC_IEC_559__` 가 정의된 이 환경에서는 `inf` 가 정의된 동작**이다.
- 두 말이 어긋나는 이유: 표준의 **기본 규칙**으로는 UB 인데, IEEE 754 를 따르는 구현에서는 **정의**된다.
- 그래서 `float-divide-by-zero` 는 **기본 집합에 없다** — 켜면 정상 코드에도 붙는다.\
  **「sanitizer 가 말했다」가 곧 「UB 다」가 아니다.**

## 언제 쓰고 언제 안 쓰나

| 상황 | 고를 것 | 안 고를 것 |
|---|---|---|
| 일반 계산 | `double` | `float`(정밀도만 잃는다) |
| 큰 배열·GPU·직렬화 | `float` | `double`(메모리 2배) |
| 더 넓은 중간 정밀도가 필요 | `long double` | — (이식성이 없다 — 플랫폼마다 폭이 다르다) |
| **금액** | **정수(원·센트 단위)** | 부동소수 전부 |
| ID·카운터 | 정수 | `double`(2^53 위에서 충돌) |
| 비교 | `fabs(a-b) <= eps * fabs(a)` (상대) | `a == b` |
| NaN 검사 | `isnan(x)` | `x != x`(맞지만 `-ffast-math` 에서 깨진다) |
| 최적화 | `-O2` | `-Ofast`·`-ffast-math`(IEEE 754 를 포기한다) |

판단 규칙 두 줄.

- **정확해야 하면 부동소수를 쓰지 않는다.** 금액·개수는 정수다.
- **`-ffast-math` 는 「이 코드가 NaN·Inf 를 절대 안 만든다」고 약속하는 것**이다. 약속을 못 지키면 조용히 틀린다.

## 핵심 문장

- `0.1 + 0.2 != 0.3` 은 **`double` 에서만** 참이다 — `float` 에서는 `0.1f + 0.2f == 0.3f` 가 **참**이다.
- `1e16 == 1e16 + 1` 이 참이다 — **큰 수에서는 절대 오차 비교가 무의미**하고 상대 오차를 써야 한다.
- 정수 → 부동은 **말없이 반올림**(정의됨), 부동 → 정수는 **절단**하고 범위 밖이면 **UB** 다.\
  `-O0` 과 `-O2` 가 `(int)1e10` 에 대해 **다른 값**을 냈다.
- **`-fsanitize=undefined` 기본 집합에 `float-cast-overflow` 가 없다.** 따로 켜야 한다.
- IEEE 754 동작은 **`__STDC_IEC_559__` 가 정의될 때만** 보장되고, **`-ffast-math` 가 그 매크로를 없앤다.**\
  그때 `0.0/0.0` 은 `1.000000` 이 되고 `isnan` 은 0 을 돌려준다.
- 가변 인자에 넘긴 `float` 은 **언제나 `double`** 이 된다 — `%f` 가 `double` 용인 이유다.

## 용어 풀이

- **유효 비트(significand)** — 값의 「숫자 부분」을 담는 비트 수. `FLT_MANT_DIG`·`DBL_MANT_DIG` 가 말해 준다.
- **`FLT_DIG` / `DBL_DIG`** — 십진 → 부동 → 십진 왕복이 보존되는 자릿수(이 환경: 6 / 15).
- **`DBL_DECIMAL_DIG`** — 부동 → 십진 → 부동 왕복에 필요한 자릿수(이 환경: 17). **위와 방향이 반대다.**
- **`FLT_EPSILON` / `DBL_EPSILON`** — 1.0 과, 1.0 보다 큰 가장 가까운 값의 차. 「1 근처의 눈금 간격」.
- **`FLT_EVAL_METHOD`** — 중간 계산을 어느 정밀도로 하나. 0=각 타입대로, 1=`float`도 `double`로, 2=전부 `long double`로.
- **`FLT_ROUNDS`** — 반올림 모드. 1 = 가장 가까운 쪽(동점이면 짝수).
- **`__STDC_IEC_559__`** — 이 구현이 IEEE 754 를 따른다고 선언하는 매크로. **없으면 NaN·inf 동작이 보장되지 않는다.**
- **NaN** — 정의되지 않은 연산의 결과. **자기 자신과도 같지 않다.**
- **무한대(inf)** — 표현 범위를 넘은 결과. `1.0/0.0` 이 그 예(IEEE 754 하에서).
- **절단(truncation)** — 소수부를 버리고 0 쪽으로 자르는 것. 부동 → 정수 변환의 규칙(반올림이 아니다).
- **기본 인자 승격(default argument promotion)** — 프로토타입이 없는 자리(가변 인자 포함)에서 `float` → `double`, 좁은 정수 → `int` 로 올리는 규칙.
- **`-ffast-math`** — IEEE 754 계약을 포기하고 부동소수 최적화를 허용하는 플래그. `-Ofast` 에 포함된다.

## 더 들어가면

- **`long double` 은 플랫폼마다 완전히 다르다.** x86-64 리눅스는 80비트 확장(16바이트에 담김),\
  MSVC 는 `double` 과 같은 64비트, ARM 은 128비트 쿼드인 경우가 있다.\
  **`sizeof` 와 `LDBL_MANT_DIG` 를 둘 다 찍어야** 실체를 안다. (이 머신 외의 값은 **확인 못 했다.**)

- `long double` 의 여분 정밀도가 실제로 쓰인다는 것을 확인했다.

```text
1.0L + LDBL_EPSILON != 1.0L ? 1
(double)(1.0L + LDBL_EPSILON) == 1.0 ? 1  <- double 로 내리면 사라진다
```

- **2진수로 딱 떨어지는 값은 정확하다.**

```text
0.5 + 0.25 == 0.75 ? 1
0.1 * 3 == 0.3 ? 0   (0.30000000000000004)
```

  `0.5`·`0.25`·`0.75` 는 2의 거듭제곱 분수라 오차가 없다.\
  **부동소수가 「언제나 부정확」한 게 아니라 「2진 유한소수가 아닌 값에서 부정확」한 것**이다.

- **`FLT_EVAL_METHOD` 가 2 인 플랫폼**(32비트 x87)에서는 `float` 연산도 80비트로 계산한 뒤 줄인다.\
  같은 소스가 `-m32` 과 `-m64` 에서 **다른 답을 내는** 고전적인 자리인데,\
  이 머신에는 32비트 헤더가 없어 **확인하지 못했다**(`fatal error: bits/libc-header-start.h`).\
  **못 잰 것**이지 안 돌려 본 것이 아니다.

- **`-ffast-math` 가 켜는 것들**은 하나가 아니다 — `-fno-math-errno`·`-funsafe-math-optimizations`·`-ffinite-math-only`·`-fno-signed-zeros` 등의 묶음이다.\
  이 문서에서 관찰한 파괴(NaN 검사 무력화)는 주로 `-ffinite-math-only` 의 결과인데,\
  **개별 플래그를 따로 던져 보지는 않았다.**

- `%a` 서식은 부동소수를 **16진 부동소수**로 찍는다. `%.17g` 보다 짧고 정확히 왕복하지만\
  사람이 읽기 어렵다. 이 문서에서는 **안 써 봤다.**
