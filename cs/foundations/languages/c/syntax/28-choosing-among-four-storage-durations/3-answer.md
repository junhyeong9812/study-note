### 1. 여섯 객체의 주소를 `/proc/self/maps` 에 대조하면 — **네 구역으로 갈리고 문자열 리터럴만 `r--p`** ★★★

**출력**

```text
===== gcc -std=c17 -Wall -Wextra -pedantic s28a.c -o x ; ./x (cc exit=0 · run exit=0) =====
저장 기간·무엇   권한 · 구역
자동   a_auto    rw-p [stack]
정적   s_bss     rw-p (실행 파일 이미지)
정적   s_data    rw-p (실행 파일 이미지)
정적   "hello"   r--p (실행 파일 이미지)
스레드 t_tls     rw-p (익명 매핑)
할당   malloc    rw-p [heap]

★ 주소는 흔들려도 차이는 안 흔들린다
(char *)&s_data - (char *)&s_bss = -48 바이트
문자열 리터럴 구역에 w 가 없다 — 그래서 쓰면 죽는다
```

**왜 그런가**

- ★★★ **여섯 줄이 네 구역으로 갈린다.**

  | 객체 | 권한 | 구역 | 저장 기간 |
  |---|---|---|---|
  | `a_auto`(지역 변수) | `rw-p` | `[stack]` | ★ 자동 |
  | `s_bss`(`static int`) | `rw-p` | 실행 파일 이미지 | ★ 정적 |
  | `s_data`(`static int = 42`) | `rw-p` | 실행 파일 이미지 | ★ 정적 |
  | `"hello"` | ★★ **`r--p`** | 실행 파일 이미지 | ★ 정적 |
  | `t_tls`(`_Thread_local`) | `rw-p` | (익명 매핑) | ★ 스레드 |
  | `malloc` 한 것 | `rw-p` | `[heap]` | ★ 할당 |

- ★★★ **문자열 리터럴만 `w` 가 없다.** 그래서 `"abc"[0] = 'X'` 가 죽는다 — [20번 형제](../20-null-terminated-strings-and-string-literals/)의 결론이 **여기서 권한 한 글자로 설명된다.**\
  ★★ **「정적이면 못 고친다」가 아니다** — `s_bss`·`s_data` 도 정적인데 `rw-p` 라 고칠 수 있다. **갈리는 것은 그 구역의 권한**이다.
- ★★ **`_Thread_local` 은 익명 매핑**에 있다. 실행 파일 이미지가 아닌 이유는 **스레드마다 한 벌씩 새로 잡히기** 때문이다 — 실행 파일에 자리를 미리 박아 둘 수 없다(7번이 그것을 확인한다).
- ★★★ **흔들리는 칸은 주소 그 자체뿐**이다(ASLR). **구역 이름·권한·차이는 안 흔들린다.**
- ★ **`(char *)&s_data - (char *)&s_bss` 는 `-48`** 이다. **근거로 써도 된다** — 실행마다 같다.\
  ★ 다만 **「`-48` 이라는 숫자」가 결론은 아니다.** 결론은 「**두 정적 객체가 같은 구역에 이웃해 있다**」는 것이고, 링크 순서가 바뀌면 숫자는 달라진다.

### 2. 같은 함수를 세 번 부르면 — **`a` 는 매번 1 · `s` 는 1 2 3 · `&a` 는 세 번 다 같은 자리** ★★★

**출력**

```text
===== gcc -std=c17 -Wall -Wextra -pedantic s28b.c -o x ; ./x (cc exit=0 · run exit=0) =====
같은 함수를 세 번 부른다
  1번째 호출 : a=1  s=1   &a 가 첫 호출과 같은 자리인가 : 예
  2번째 호출 : a=1  s=2   &a 가 첫 호출과 같은 자리인가 : 예
  3번째 호출 : a=1  s=3   &a 가 첫 호출과 같은 자리인가 : 예

★ 자동 a 는 매번 1 · 정적 s 는 1 2 3 으로 쌓인다
★ 「같은 자리에 다시 태어나는 것」과 「살아 있는 것」은 다르다
```

**왜 그런가**

- ★★★ **`a` 는 매번 `1`** 이다 — 호출마다 **새로 태어나 `0` 으로 초기화**되고 `a++` 가 한 번 돈다.\
  **`s` 는 `1 2 3`** 이다 — **프로그램 시작 전에 한 번** `0` 이 되고 그 뒤로는 계속 산다.
- ★★★ **`&a` 가 세 호출에서 모두 같은 자리**다. 그런데 **살아 있는 것이 아니다.**\
  함수가 끝나면 그 스택 자리는 **비워지고 다음 호출이 같은 자리를 다시 쓴다** — **같은 자리에 다시 태어난 것**이지 이어진 것이 아니다.\
  ★ 증거는 **`a` 가 매번 `1`** 이라는 것이다. 이어져 있었다면 `1 2 3` 이 됐을 것이다.
- ★★★ **이 오해가 5번의 UB 를 「괜찮아 보이게」 만든다.** 죽은 자리를 읽었는데 **아직 아무도 안 덮었으면 옛 값이 그대로 보인다** — 그것이 clang `-O0` 의 `1234` 다.
- ★★ **`static` 은 자리에 따라 다른 일을 한다.**

  | 어디 | 무엇을 바꾸나 |
  |---|---|
  | **함수 안** `static int s;` | ★ **저장 기간**(자동 → 정적). 이름의 가시성은 **안 바뀐다**(여전히 그 함수 안에서만 보인다) |
  | **파일 스코프** `static int g;` | ★ **링크**(외부 → 내부). 저장 기간은 **원래 정적**이라 안 바뀐다 |

  ★ 링크 쪽은 목록의 **29번 주제**가 정본이다.
- ★ **`static` 의 초기화는 프로그램이 시작하기 전에 한 번**이다. 「첫 호출 때」가 아니다 — 그래서 초기자는 **상수식**이어야 한다.

### 3. 초기화를 안 하면 — **정적은 여섯 벌 전부 0 · 자동은 컴파일러로 갈린다** ★★★

**출력**

```text
===== gcc -std=c17 -Wall -Wextra -pedantic s28c.c -o x ; ./x (cc exit=0 · run exit=0) =====
정적 : s_zero=0  s_arr = 0 0 0 0
자동 : a_indet=0  a_arr = 0 0 -1528595728 30953
```

**왜 그런가**

- ★★★ **정적 쪽은 `s_zero=0`·`s_arr = 0 0 0 0`** 이고 **여섯 벌 전부 같다**. 이것은 **표준의 보장**이다.
- ★★★ **자동 쪽은 갈린다.**

  | 벌 | `a_indet` | `a_arr` |
  |---|---|---|
  | gcc `-O0` | **0** | `0 0` + 쓰레기 둘 |
  | gcc `-O1` | **0** | `0 0 0 0` |
  | gcc `-O2` | **0** | `0 0 0 0` |
  | clang `-O0` | 쓰레기 | `0 0` + 쓰레기 둘 |
  | clang `-O1` | 쓰레기 | `0 0` + 쓰레기 + `0` |
  | clang `-O2` | 쓰레기 | `0 0` + 쓰레기 + `0` |

  ★ **어느 칸이 `0` 이고 어느 칸이 쓰레기인지는 3회 재실행에도 같았다.** 바뀌는 것은 **쓰레기 숫자**뿐이다.
- ★★★ **gcc 의 `a_indet=0` 을 근거로 쓰면 틀리는 이유** — 그것은 **여섯 벌 중 셋의 관찰**이고 **clang 은 세 벌 다 쓰레기**를 준다.\
  ★★ **「0 이 나왔다」와 「0 으로 초기화된다」는 다른 문장**이다. 뒤엣것은 **정적 객체에만** 참이다.
- ★★ **경고는 2건**(`a_arr`·`a_indet` 각각)이고 플래그는 **`[-Wuninitialized]`** 다. **`cc exit=0`** 이다.\
  ★ **이 주제에서는 gcc 가 `-O0` 에서도 말해 준다** — [27번 형제](../27-compound-literals/)의 UB 가 `-O0` 에서 1건뿐이었던 것과 갈린다.
- ★★ **대조할 것은 숫자가 아니다** — 「**정적은 여섯 벌 전부 0 이고 자동은 안 그렇다**」와 「**어느 칸이 0 이고 어느 칸이 쓰레기인가**」다.

### 4. 자동 저장 기간에 1 · 4 · 64 MiB 를 잡으면 — **64 MiB 에서 `run exit=139` · 진단 0건** ★★

**출력**

```text
===== ulimit -s 를 보고 1 · 4 · 64 MiB 를 자동 저장 기간에 잡아 본다 (exit=0) =====
ulimit -s = 8192 KiB
자동 저장 기간에 1 MiB 를 잡아 본다
  자동 : 성공 (첫 바이트 1 · 끝 바이트 2)
  할당 : 성공
  run exit=0
자동 저장 기간에 4 MiB 를 잡아 본다
  자동 : 성공 (첫 바이트 1 · 끝 바이트 2)
  할당 : 성공
  run exit=0
자동 저장 기간에 64 MiB 를 잡아 본다
  run exit=139
```

**왜 그런가**

- ★★★ **`ulimit -s` 가 8192 KiB(8 MiB)** 이고, 그래서

  | 크기 | 자동 | 할당 | `run exit` |
  |---|---|---|---|
  | 1 MiB | 성공 | 성공 | 0 |
  | 4 MiB | 성공 | 성공 | 0 |
  | **64 MiB** | ★ **죽는다** | (거기까지 못 간다) | **139**(SIGSEGV) |

- ★★★ **컴파일러 경고는 0건**이다. 크기가 실행 시간에 정해지는 **VLA** 라 컴파일 시간에 알 수 있는 것이 없다([18번 형제](../18-variable-length-arrays-vla/)가 정본).\
  ★★ 이것이 이 주제에서 「**진단이 0건인 자리**」다 — 컴파일도 통과하고 경고도 없고 **실행에서 즉사**한다.
- ★★ **`malloc` 은 64 MiB 도 문제가 없다.** 그리고 **모자라면 `NULL` 을 돌려주므로 검사할 수 있다.**\
  ★★★ **스택은 넘치면 그냥 죽는다** — **검사할 방법이 없다.** 이것이 큰 버퍼를 힙에 두는 가장 큰 이유다.
- ★★ **스택 한도는 구현 정의이자 실행 환경의 설정**이다. `ulimit -s` 로 바뀌므로 **같은 바이너리가 환경에 따라 죽고 산다.**\
  ★ 그래서 「내 머신에서 되던데」가 **가장 약한 근거**가 되는 자리다.
- ★ **64 MiB 벌에서 첫 줄(`자동 저장 기간에 64 MiB 를 잡아 본다`)이 남은 이유** — 소스에 `setvbuf(stdout, NULL, _IONBF, 0)` 가 있어 **버퍼링을 껐기** 때문이다.\
  없었으면 그 줄도 버퍼에 남은 채 죽어 **출력이 통째로 비었을 것**이다.

### 5. 지역 변수의 주소를 돌려주면 — **gcc 셋은 죽고 clang 둘은 `1234` 를 준다** ★★★ 본체

**출력**

```c
/* s28d.c */
#include <stdio.h>

static int *leak_auto(void) {
    int local = 1234;
    return &local;              /* ★ 블록이 끝나면 죽는 자리를 돌려준다 */
}
static int *ok_static(void) {
    static int s = 1234;
    return &s;                  /* 정적이라 살아 있다 */
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    int *p = ok_static();
    printf("정적 : *p = %d\n", *p);
    int *q = leak_auto();
    printf("자동 : *q = %d   <- 이 값을 믿을 수 있나?\n", *q);
    return 0;
}
```

```text
gcc   -O1 : run exit=139 (출력 없음 — 죽었다)
gcc   -O2 : run exit=139 (출력 없음 — 죽었다)
clang -O0 : run exit=0   자동 : *q = 1234   <- 이 값을 믿을 수 있나?

clang -O2 : run exit=0   자동 : *q = -289897232   <- 이 값을 믿을 수 있나?
```

**왜 그런가**

- ★★★ **여섯 벌이 세 갈래**다.

  | gcc `-O0` · `-O1` · `-O2` | **139**(SIGSEGV) | ★ **없다**(죽었다) |

  | clang `-O2` | **0** | 쓰레기 |

- ★★★ **「정답처럼 보이는」 칸은 2개**다 — **clang `-O0` 과 `-O1`.**
- ★★★ 갈린 축은 「**컴파일러**」다.\
  ★★★ **[27번 형제](../27-compound-literals/)와 다르다** — 거기서는 **최적화 수준**으로 갈렸고(같은 컴파일러 안에서 `-O0` 과 `-O2` 가 달랐다) 여기서는 **컴파일러**로 갈린다(같은 컴파일러 안에서는 세 벌이 거의 같다).\
  ★★ **그래서 「무엇으로 갈리는가」를 한 축으로 단정하면 안 된다.** 던져야 할 것은 **격자 두 개가 아니라 여섯 개**다.
- ★★ **경고는 둘 다 1건**이고 **`cc exit=0`** 이다.

  | | 플래그 | 문구 |
  |---|---|---|
  | gcc | `[-Wreturn-local-addr]` | `function returns address of local variable` |
  | clang | `[-Wreturn-stack-address]` | `address of stack memory associated with local variable 'local' returned` |

  ★ **여기서는 clang 도 말해 준다** — [27번 형제](../27-compound-literals/)의 복합 리터럴 UB 에는 **0건**이었던 것과 갈린다. **같은 계열의 UB 인데 진단 범위가 다르다.**
- ★ **정적 쪽(`ok_static`)은 여섯 벌 전부 `1234`** 다 — 비교군이다.
- ★★ **`-pedantic-errors` 로는 못 막는다.** 이것은 **표준 위반 문법이 아니라 실행 시간의 UB** 라 `-pedantic` 계열이 볼 대상이 아니다.\
  ★ 막으려면 `-Werror` 로 저 경고를 에러로 올리거나 **ASan 을 켠 테스트**가 그 경로를 지나가야 한다.

### 6. 왜 gcc 만 죽나 — **`mov eax, 0` 대 `lea rax, [rsp - 4]`** ★★★

**출력**

```text
===== gcc -std=c17 -O1 -S -masm=intel s28d2.c -o - | grep -v '^[[:space:]]*\.' (exit=0) =====
leak_auto:
	endbr64
	mov	eax, 0
	ret
```

```text
===== clang -std=c17 -O1 -S -masm=intel s28d2.c -o - | grep -v '^[[:space:]]*\.' (exit=0) =====
leak_auto:                              # @leak_auto
# %bb.0:
	lea	rax, [rsp - 4]
	ret
                                        # -- End function
```

```text
===== gcc -std=c17 -Wall -Wextra -pedantic -O1 -fsanitize=address s28d.c -o x ; ASAN_OPTIONS=strip_path_prefix=/src/ ./x 2>&1 | sed -n '1,8p' (cc exit=0 · run exit=1) =====
정적 : *p = 1234
AddressSanitizer:DEADLYSIGNAL
=================================================================
==1123512==ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000 (pc 0x621d6fd9f28f bp 0x7ffc5b579e20 sp 0x7ffc5b579d80 T0)
==1123512==The signal is caused by a READ memory access.
==1123512==Hint: address points to the zero page.
    #0 0x621d6fd9f28f in main (x+0x128f) (BuildId: 23905cc8a4b4952b2d88100226f09eb8c69d0917)
    #1 0x798b7b22a1c9 in __libc_start_call_main ../sysdeps/nptl/libc_start_call_main.h:58
```

**왜 그런가**

- ★★★ **gcc 는 `mov eax, 0`** 으로 번역한다 — **널 포인터를 돌려준다.**\
  ★★★ **clang 은 `lea rax, [rsp - 4]`** 로 번역한다 — **스택 포인터보다 아래 주소**를 돌려준다.
- ★★★ **그 두 줄이 5번을 통째로 설명한다.**

  ```text
     gcc   : return &local  ->  mov eax, 0          ->  *q 가 널 역참조
                                                    ->  ★ 반드시 죽는다 (139)
     clang : return &local  ->  lea rax, [rsp - 4]  ->  *q 가 죽은 프레임을 읽는다
                                                    ->  ★ 안 덮였으면 1234 가 나온다
  ```

  ★★ gcc 는 「**어차피 미정의니 널을 돌려주겠다**」를 고른 것이고, clang 은 「**적힌 대로 주소를 돌려주겠다**」를 고른 것이다. **둘 다 적법하다.**
- ★★ **ASan 리포트가 그것을 확인해 준다** — `SEGV on unknown address 0x000000000000` 과 **`Hint: address points to the zero page`**.\
  ★ **「널 포인터였다」를 리포트가 직접 적어 준다** — 역어셈블을 안 봐도 여기까지는 알 수 있다. 다만 「**왜 널이 됐나**」는 역어셈블만 답한다.
- ★★★ **세 창 중 이 질문에 답하는 창이 없다.**

  | 창 | 이 질문에 대해 |
  |---|---|
  | 컴파일 진단 | 「지역 변수 주소를 돌려준다」까지만 — **둘 다 같은 말**을 한다 |
  | 실행 출력 | 「죽었다」·「1234」 — **결과**만 보인다 |
  | sanitizer | 「널을 읽었다」 — **gcc 쪽에서만**, 그리고 **왜 널인지는 모른다** |

  ★★★ 그래서 네 번째 창은 「**역어셈블 네 줄**」이다. `gcc -S -masm=intel` 로 찍으면 끝난다.
- ★ **어느 쪽이 안전한가 — 죽는 쪽**이다. gcc 는 **반드시 죽게** 만들어 개발 중에 드러나고, clang 은 **조용히 지나가게** 둬서 운영에서 터진다.\
  ★ 「값이 나오는 쪽이 더 나은 컴파일러」가 **아니다.**

### 7. 세 스레드가 같은 이름의 변수를 고치면 — **`&tls` 셋이 다르고 `&shared` 셋이 같다** ★★

**출력**

```text
===== gcc -std=c17 -Wall -Wextra -pedantic -pthread s28e.c -o x ; ./x (cc exit=0 · run exit=0) =====
스레드 1 : tls = 101
스레드 2 : tls = 102
스레드 3 : tls = 103
메인     : tls = 100   <- 스레드들이 고친 것이 안 보인다

&tls 가 셋 다 다른가     : 예 — 스레드마다 제 객체다
&shared 가 셋 다 같은가  : 예 — 프로그램에 한 객체다
메인의 &tls 도 스레드들과 다른가 : 예
```

**왜 그런가**

- ★★★ **세 스레드가 `101`·`102`·`103`, 메인은 `100`** 이다. 각자 **제 것**을 고쳤고 서로 안 보인다.
- ★★★ **`&tls` 는 셋 다 다르고 `&shared` 는 셋 다 같다.** **객체가 몇 개인지를 주소로 직접 확인한 것**이다.
- ★★★ **값만 보고는 못 가른다.** `101 102 103` 이라는 출력은\
  「스레드마다 제 객체가 있다」로도 읽히고 「하나를 나눠 쓰는데 경쟁이 운 좋게 안 났다」로도 읽힌다 — **주소를 찍어야** 갈린다.\
  ★★ **1번·2번과 같은 형태의 창**이다: **주소를 값으로 읽지 말고 「같은가 다른가」로 묻는다.**
- ★ **메인의 `&tls` 도 스레드들과 다르다.** 그러므로 이 프로그램에는 **`tls` 라는 이름의 객체가 넷**(메인 + 스레드 3) 있었다.
- ★★ **일부러 안 한 것 — 여러 스레드가 `shared` 를 동시에 고치는 실험.**\
  그것은 **동시성 주제**이지 저장 기간 주제가 아니다([`foundations/process-thread/`](../../../../process-thread/)가 정본).\
  ★ 그리고 그렇게 했으면 **출력이 실행마다 뒤바뀌어** 재현이 안 됐을 것이다 — 이 편은 **결과를 배열에 담았다가 메인이 순서대로 찍어** 결정적으로 만들었다.
- ★ **`-pthread` 가 필요하다.** `_Thread_local` 은 C11 문법이지만 스레드를 만드는 것은 POSIX 다.

### 8. `thread_local` 이라는 철자 — **C11 은 헤더의 매크로 · C23 은 키워드** ★★

**출력**

```text
===== gcc -std=c17 -Wall -Wextra -pedantic s28g.c -o x (cc exit=1) =====
s28g.c:2:13: error: expected ‘;’ before ‘int’
    2 | thread_local int a = 1;             /* C23 키워드 */
      |             ^~~~
      |             ;
```

```text
===== gcc -std=c2x -Wall -Wextra -pedantic s28g.c -o x ; ./x (cc exit=0 · run exit=0) =====
thread_local a = 1
```

```text
===== gcc -std=c17 -Wall -Wextra -pedantic s28g2.c -o x ; ./x (cc exit=0 · run exit=0) =====
thread_local a = 1
```

**왜 그런가**

- ★★★ **세 가지 결과**

  | 명령 | 결과 | `cc exit` |
  |---|---|---|
  | `gcc -std=c17`(헤더 없음) | ★ **에러** `expected ';' before 'int'` | **1** |
  | `gcc -std=c2x`(헤더 없음) | ★ 통과 · `thread_local a = 1` | **0** |
  | `gcc -std=c17` + `<threads.h>` | ★ 통과 · `thread_local a = 1` | **0** |

- ★★★ **`thread_local` 은 「조건부 표준」 칸에 들어간다** — **C11·C17 에서는 `<threads.h>` 가 정의할 때만** 쓸 수 있는 매크로이고, **C23 부터 키워드**다.\
  ★ 이 주제가 **조건부 표준 칸이 비어 있지 않은 드문 편**인 이유가 이것이다.
- ★★★ **에러 메시지만 보고 「지원 안 한다」로 읽으면 틀린다.** `expected ';' before 'int'` 는 **파서가 그 낱말을 모른다**는 뜻일 뿐이고,\
  ★ **헤더가 빠져서 그럴 수도 있고 버전이 낮아서 그럴 수도 있다.** **두 가설을 가르는 것은 헤더를 넣어 다시 던져 보는 것**뿐이다.
- ★ **`_Thread_local` 은 C11 부터 어디서나 키워드**라 헤더가 필요 없다 — **이식성은 그쪽이 낫다.**
- ★ 한편 **`_Thread_local` 이라는 밑줄 대문자 철자가 보기 싫어서** C23 이 키워드를 정리한 것이다. C23 만 쓰는 코드라면 `thread_local` 이 낫다.
- ★★ **철자 이야기가 하나 더 있다** — **`-std=c23` 이라는 플래그 자체가 gcc 13 에 없다**(`unrecognized command-line option` · **`cc exit=1`** · **경고 0건**). clang 18 은 받아 준다.\
  ★ 그래서 이 배치는 **둘 다 받는 `-std=c2x`** 로 고정했다 — 실측은 [27번 형제](../27-compound-literals/)의 (6-나)에 있다.

### 9. 다른 문법들은 어느 저장 기간인가 ★★

**왜 그런가**

| 문법 | 저장 기간 | 정본 |
|---|---|---|
| 함수 안 `int a;` | ★ **자동** | 이 주제 |
| 함수 안 `static int s;` | ★ **정적** | 이 주제(링크는 목록의 **29번 주제**) |
| 파일 스코프 `int g;` · `static int g;` | ★ **정적** | 목록의 **29번 주제** |
| `_Thread_local int t;` | ★ **스레드** | 이 주제 |
| `malloc`/`calloc`/`realloc` | ★ **할당** | 목록의 **37번 주제** |
| `"hello"` | ★ **정적**(권한 `r--p`) | [20번 형제](../20-null-terminated-strings-and-string-literals/) |
| 함수 안 `(struct P){1,2}` | ★ **자동** | [27번 형제](../27-compound-literals/) |
| 파일 스코프 `(struct P){1,2}` | ★ **정적** | [27번 형제](../27-compound-literals/) |
| `(static struct P){1,2}` | ★ **정적**(**C23 부터**) | [27번 형제](../27-compound-literals/) |
| 함수 안 `int vla[n];` | ★ **자동**(스택) | [18번 형제](../18-variable-length-arrays-vla/) |
| opaque struct 의 객체 | ★ **사실상 할당뿐** | [25번 형제](../25-incomplete-types-and-opaque-struct/) |
| FAM 구조체 | ★ **사실상 할당뿐** | [26번 형제](../26-flexible-array-members/) |

- ★★★ **새 저장 기간을 만드는 문법은 없다.** 복합 리터럴도 VLA 도 **자동이거나 정적**이다 — 넷이 전부다.
- ★★★ opaque struct 와 FAM 구조체는 「**고른 것」이 아니라 「떠밀린 것**」이다.
  - **opaque** — 쓰는 쪽이 **크기를 모르므로** 변수로도 배열로도 못 만든다([25번 형제](../25-incomplete-types-and-opaque-struct/)).
  - **FAM** — 자동 저장 기간에서는 **초기자로 꼬리를 못 주므로** 만들 방법이 없다([26번 형제](../26-flexible-array-members/)).

  ★ **이유는 다르고 결과는 같다** — 둘 다 `malloc` 밖에 길이 없다.
- ★★ **`(static struct P){1,2}` 는 정적이고 C23 부터**다. 이 배치에서 **gcc 13 만 받아 줬다**([27번 형제](../27-compound-literals/)).

### 10. 이 값을 어디에 둘까 ★★★

**왜 그런가**

- ★★★ **먼저 묻는 질문 — 「이 값이 이 블록보다 오래 살아야 하나」.**\
  답이 「예」면 **자동은 그 자리에서 탈락**한다. 5번의 UB 가 전부 이 질문을 안 물어서 생긴다.
- ★★ **그다음에 묻는 질문 — 「몇 개 있어야 하나」.**

  | 몇 개 | 답 |
  |---|---|
  | 프로그램에 하나 | **정적** |
  | 스레드마다 하나 | **스레드**(`_Thread_local`) |
  | 호출마다 하나(짧게) | **자동** |
  | 호출마다 하나(길게·크게) | **할당** |

- ★ **함수 밖으로 돌려줄 값은 두 가지 형태**다 — ① **`malloc` 해서 돌려주고 소유권을 넘긴다**(목록의 **38번 주제**) ② **호출자가 준 자리(버퍼 + 길이)에 채운다.**\
  ★ 뒤엣것이 대개 낫다 — **할당을 호출자가 고른다.**
- ★★ **큰 버퍼를 할당에 두는 이유 두 가지** — ① **스택 한도가 있고 넘치면 그냥 죽는다**(4번) ② **`malloc` 은 실패를 `NULL` 로 알려 줘 검사할 수 있다.**
- ★★ 함수 안 `static` 의 대가는 「**재진입 불가·스레드 안전하지 않음**」이다.\
  ★ 피하는 방법은 **`_Thread_local` 로 바꾸거나**(스레드마다 필요할 때) **호출자가 준 자리에 쓰는 것**(호출마다 필요할 때)이다.
- ★ **「이름은 하나인데 객체는 여럿」이 필요한 자리** — `errno` 같은 **스레드별 오류 상태**, 스레드별 캐시·버퍼. 전부 `_Thread_local` 이다.

### 11. 다섯 층과 무게중심 — **조건부 표준 칸이 비어 있지 않은 드문 주제** ★★★

**왜 그런가**

| 층 | 이 주제에서 | 근거 |
|---|---|---|
| ★★★ **표준 (본체)** | **네 저장 기간과 각각의 수명** · **정적은 0 · 자동은 불확정** · **함수 안 `static` 이 호출을 가로질러 사는 것** · **스레드마다 객체가 하나씩인 것**(C11부터) | `s_zero=0`(여섯 벌) · `a=1 s=1/2/3` · `&tls` 셋이 다르고 `&shared` 셋이 같음 |
| ★★ **조건부 표준** | ★★★ **`thread_local` 이라는 철자** — C11·C17 에서는 **`<threads.h>` 가 정의할 때만** 쓸 수 있다 | `-std=c17` 헤더 없음 → **`cc exit=1`** · `<threads.h>` 넣으면 **통과** · `-std=c2x` 는 헤더 없이 **통과** |
| ★ **구현 정의 (얇다)** | **스택 한도**(`ulimit -s` = 8192 KiB) · **각 저장 기간이 어느 구역에 놓이는가** · **문자열 리터럴 구역의 권한**(`r--p`) · 진단 문구와 플래그 이름 · **컴파일러가 UB 를 무엇으로 번역하는가** | `/proc/self/maps` 6행 · 64 MiB 에서 **`run exit=139`** · `[-Wreturn-local-addr]` 대 `[-Wreturn-stack-address]` · `mov eax, 0` 대 `lea rax, [rsp - 4]` |
| ★ **미명시 (얇다)** | **불확정 값으로 무엇이 읽히는가** · 죽은 자동 객체의 자리가 **언제 덮이는가** | 3번 격자 — gcc `a_indet=0`, clang 쓰레기. **숫자는 실행마다 바뀌고 「어느 칸이 0 인가」는 안 바뀐다** |
| ★★ **UB** | ★★★ **죽은 자동 객체를 읽는 것** · ★ **문자열 리터럴을 고치는 것** · ★ **스택 한도를 넘기는 것** | ★★ **여섯 벌 세 갈래** — gcc 셋 `run exit=139` · clang `-O0`/`-O1` **`1234`** · clang `-O2` 쓰레기. 경고는 둘 다 1건 · **`cc exit=0`** |

- ★★★ **비어 있는 칸이 없다.** 다섯 칸에 전부 내용이 있다 —\
  ★ **이것이 이 주제가 다른 편들과 다른 점**이다. [25번 형제](../25-incomplete-types-and-opaque-struct/)·[26번 형제](../26-flexible-array-members/)·[27번 형제](../27-compound-literals/)는 전부 **「조건부 표준」 칸이 비어 있었다.**\
  ★★ 여기서는 **`thread_local` 이라는 철자**가 정확히 그 칸의 정의(「매크로가 정의될 때만」)에 들어맞는다.
- ★★ 가장 두꺼운 칸은 「**표준**」, 두 번째는 「**UB**」다.
- ★★ **도구가 침묵하는 자리**

  | 층 | 침묵하는 자리 |
  |---|---|
  | 표준 | ★★ **「이 객체가 지금 살아 있나」를 말해 주는 도구가 없다.** 컴파일러는 **선언 자리**만 본다 |
  | 조건부 표준 | ★★ **`thread_local` 이 에러 날 때 「헤더가 없어서인지 버전이 낮아서인지」를 진단이 안 가른다** — 둘 다 같은 문구다 |
  | 구현 정의 | ★★★ **스택 한도에 진단이 0건**이다 |
  | 미명시 | ★ **불확정 값이 무엇인지 아무도 안 알려 준다.** gcc 는 **읽었다는 사실**만 잡는다 |
  | UB | ★★★ **`cc exit=0`** 이고 **clang `-O0`/`-O1` 은 `1234` 라는 정답**을 준다. ★★ 세 창 중 **「컴파일러가 이 UB 를 어떻게 번역했나」에 답하는 창이 없다** |

- ★★★ **「진단이 0건인 자리」는 스택 한도**(4번)다. **왜 특히 나쁜가** —\
  ① **컴파일도 통과하고 경고도 없고 실행에서 즉사**한다 ② **`ulimit -s` 라는 환경 설정에 달려 같은 바이너리가 환경에 따라 죽고 산다** ③ **`malloc` 과 달리 실패를 검사할 방법이 없다.**
- ★★ 네 번째 창은 「**역어셈블(`gcc -S -masm=intel`)**」이다.\
  세 창은 **무슨 일이 났는지**는 말해도 **컴파일러가 이 UB 를 무엇으로 바꿨는지**는 말하지 않는다. 네 줄이 그것을 답한다.\
  ★ 그 앞 단계의 창은 **`/proc/self/maps` 대조**(1번)다 — 「이 주소가 어느 구역인가」를 묻는다.

**구현 의존 항목** — 다음은 **이 환경(x86-64 Linux · gcc 13.3.0 · clang 18.1.3 · `ulimit -s` 8192 KiB)에서만** 그렇다.

- ★★★ **5번의 여섯 벌 격자 전부** — **UB** 라 어떤 값도 결론이 아니다.\
  ★ 결론은 「**세 갈래로 갈린다」와 「clang 두 벌이 맞아 보인다」와 「갈린 축이 컴파일러였다**」이지 **어느 숫자가 나오는가**가 아니다.
- ★★★ **역어셈블 두 줄**(`mov eax, 0` · `lea rax, [rsp - 4]`) — **컴파일러의 선택**이다. 버전이 오르면 바뀔 수 있다.
- ★★ **3번의 불확정 값 격자** — **미명시**다. 숫자는 실행마다, 「어느 칸이 0 인가」는 컴파일러·최적화마다 달라질 수 있다.
- ★★ **스택 한도 8 MiB 와 64 MiB 에서 죽는 것** — `ulimit -s` 라는 **환경 설정**에 달렸다.
- ★★ **`/proc/self/maps` 의 구역 이름**(`[stack]`·`[heap]`)과 **권한 문자열** — **리눅스의 형식**이다.
- ★ **`&s_data - &s_bss` = `-48`** — 링크 순서와 정렬에 달렸다. **「같은 구역에 이웃해 있다」만** 결론에 쓴다.
- ★ **진단 문구와 플래그 이름 전부** · **`_Thread_local` 이 익명 매핑에 놓이는 것**.

**네 저장 기간과 각각의 수명 · 정적이 0 으로 초기화되는 것 · 자동이 불확정인 것 · 함수 안 `static` 이 호출을 가로질러 사는 것 · 스레드마다 객체가 하나씩인 것 · `thread_local` 철자의 버전 규칙은 구현 의존이 아니다.**\
어느 C 구현에서도 같다.

**안 돌려 본 것 / 못 잰 것**

- **안 돌려 본 것** — **여러 스레드가 `shared` 를 동시에 고치는 실험**(동시성 주제라 일부러 뺐다) ·\
  `<threads.h>` 의 **스레드 API**(`thrd_create`·`tss_t`·스레드별 소멸자) · **`ulimit -s unlimited`** 에서 4번이 어떻게 되는지 ·\
  **`-fstack-protector`·`-fstack-clash-protection`** 이 4번을 바꾸는지 · **`ASAN_OPTIONS=detect_stack_use_after_return=1`** ·\
  **`objdump` 로 `.bss` 와 `.data` 를 가르는 것**(둘 다 `rw-p` 실행 파일 이미지로만 봤다) ·\
  **`calloc` 의 0 과 정적 초기화의 0 이 같은가**(포인터의 널 표현) · **`-Os`·`-O3`**(3·5번은 `-O0`\~`-O2` 까지만 흔들었다) ·\
  **C++ 의 정적 초기화 순서**(규칙만 적고 던지지 않았다).
- ★ **못 잰 것** — **「죽은 스택 자리가 언제 덮이는가」.**\
  5번에서 clang `-O0`/`-O1` 이 `1234` 를 준 것은 **그 자리가 아직 안 덮였기** 때문인데,\
  **언제 덮이는지를 재려면 그 사이에 무엇을 실행할지를 내가 정해야** 하고 그러면 **내가 정한 조건의 답**이 나온다.\
  프로그램마다 다른 값이라 **이 실험 밖의 일**이다 — 「안 돌려 본 것」이 아니라 「**측정 방법이 전제를 요구해 잴 수 없는 것**」이라 따로 적는다.\
  ★★ **그래서 본문은 「안 덮였으면 옛 값이 보인다」까지만 적고 「얼마나 오래 남는가」는 적지 않았다.**

**버전이 올랐을 때 다시 돌려야 하는 것**

- ★★★ **5번의 여섯 벌 격자와 6번의 역어셈블** — 코드 생성이 바뀌면 그대로 바뀐다. **이 편의 결론이 걸린 자리**다.
- ★★★ **3번의 불확정 값 격자** — 미명시 칸이라 언제든 달라질 수 있다.
- ★★ **clang 이 `thread_local` 이나 C23 기능을 더 받게 됐는지**(8번은 gcc 만 확인했다).
- ★★ **`ulimit -s` 기본값**(배포판·컨테이너마다 다르다) — 4번의 경계가 거기 달렸다.
- ★ **진단 문구와 플래그 이름** · **`/proc/self/maps` 형식**.
- **네 저장 기간의 수명 규칙은 다시 돌릴 필요가 없다** — C89(스레드는 C11) 이후 바뀐 적이 없다.
