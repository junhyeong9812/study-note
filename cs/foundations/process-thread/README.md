## 1. 프로그램과 프로세스

출처: `computer_science/chapter/chapter10/chapter10.py`

프로세스와 스레드는 운영체제를 이해하는 관문이다.
운영체제는 우리가 실행한 프로그램을 프로세스와 스레드 단위로 관리한다.
게다가 CPU 코어 개수가 점점 늘어나는 요즘 멀티스레딩 기법은 거스를 수 없는 대세이다.

프로그램: 하드디스크에 저장된 실행 파일.

프로세스: 프로그램을 실행한 상태.
즉 하드디스크에서 메인 메모리로 코드와 데이터를 가져와 실행 중인 상태.
프로세스는 동시에 여러 개 존재 가능하다.
독립적으로 프로세스가 존재하는데, 여기서의 독립적이란 말은 메모리 공간도 서로 다르다는 것이다.
이러한 프로세스 ID를 통해 각 프로세스 프로그램을 관리한다.

## 2. 프로세스의 상태

출처: `computer_science/chapter/chapter10/chapter10.py`

오늘날의 운영체제는 대부분 멀티프로세스 기반이다.
프로세스 여러 개를 동시에 실행할 수 있다.
프로세스를 실행하려면 독자적인 메모리 공간과 CPU가 필요하다.
이때 메모리는 가상 메모리로 해결했지만, CPU는 한 번에 하나의 프로세스만 할당할 수 있다.
즉 여러 프로세스가 완벽하게 동시에 실행되는 건 불가능하다. 우리 눈에만 그렇게 보일 뿐.
즉 프로세스는 프로그램 구동 순간 프로세스 생성부터 창을 닫을 때까지 계속 실행 상태로 있는 게 아니다.
프로세스는 상황에 따라 변한다.

프로세스 상태를 나타내는 그림을 보면

```
Created -> Waiting <-> Running -> Terminated
            ^               |-> Blocked
            |---------------------|
```

위와 같이 총 5가지 상태가 존재한다.

생성(Created): 프로그램을 더블클릭했을 때 프로세스가 생성되면서 실행 가능한 상태가 된다.
곧바로 실행 상태가 되는 것이 아니라, 우선 실행 가능 상태가 되어 실행 중인 프로세스와 우선순위를 비교한 다음 우선순위가 높으면 실행하고 아니면 실행 가능 상태에서 순서를 기다린다.

실행 가능(Waiting): 실행 가능 상태의 프로세스는 언제든지 실행될 준비가 되어 있다.
운영체제는 인터럽트가 발생했을 때 실행 가능 상태의 프로세스 중 다음으로 CPU를 할당받아 실행될 프로세스를 결정한 후 실행 중인 프로세스와 교체한다.
이때 다음으로 실행할 프로세스에 CPU를 할당하는 것을 디스패치라 한다.
그리고 이때 실행 중이던 프로세스에서 CPU를 해제하는 것을 프리엠션(preemption)이라고 한다.

실행(Running): 프로세스가 운영체제로부터 CPU를 할당받아 실행되고 있는 상태.

보류(Blocked): 프로세스가 I/O(입출력) 작업을 하면 CPU를 해제하고 보류 상태로 변경된다.
이때 실행 가능 상태의 프로세스 중 하나가 CPU를 할당받는다.
보류 상태에 들어간 프로세스는 I/O 작업이 모두 끝나면 실행 가능 상태로 변경된다.
중요한 점은 I/O 작업이 완료된 다음 바로 실행 상태로 변경되는 것이 아니라, 실행 가능 상태가 되어 실행되기를 기다린다는 점이다.
또한 실행 대기 상태(Waiting)와 보류(Blocked) 상태를 구분할 수 있어야 한다.
실행 대기 상태는 언제든지 다시 실행될 수 있는 상태를 말하지만, 보류 상태는 I/O 작업이 끝나기 전에는 실행이 불가능한 상태이다.

소멸(Terminated): 프로세스 실행이 완료되어 메인 메모리에서 사라진다.

## 3. 스케줄링 — 선점형과 비선점형

출처: `computer_science/chapter/chapter10/chapter10.py`

그럼 이때 알아봐야 할 것은, 디스패치(dispatch)와 프리엠션(preemption)이 일어날 때 운영체제는 어떤 프로세스에게 CPU를 할당할까?
이게 스케줄링이다.
즉 스케줄링이란 운영체제가 여러 프로세스의 CPU 할당 순서를 결정하는 것이다.
이 일을 하는 프로그램을 스케줄러라고 한다.
스케줄링은 CPU를 언제 할당하는지에 따라 선점형 스케줄링(preemptive scheduling)과 비선점형 스케줄링(non-preemptive scheduling)이 존재.

선점형 스케줄링에서는 어떤 프로세스가 실행 중에 있어도 스케줄러가 강제로 실행을 중지하고 다른 프로세스에 CPU를 할당할 수 있다.
이에 반해 비선점형 스케줄링에서는 실행 중인 프로세스가 종료되거나 I/O 작업에 들어가거나 명시적으로 CPU를 반환하기 전까지 계속 실행된다.
우선순위가 높은 프로세스가 생성되어도 실행 중인 프로세스가 자발적으로 CPU를 양보하기 전까지 실행 불가능.
윈도우는 멀티태스킹을 위한 선점형 스케줄링을 한다.

## 4. 스케줄링 알고리즘 4가지

출처: `computer_science/chapter/chapter10/chapter10.py`

스케줄링(scheduling)이란 운영체제가 여러 프로세스의 CPU 할당 순서를 결정하는 것이다.
이때 이러한 스케줄링의 알고리즘에는 대표적으로 4가지가 존재한다.

우선순위(Priority) 알고리즘: 프로세스에 우선순위를 매겨 우선순위가 높은 프로세스를 먼저 실행한다.
어떤 프로세스가 CPU를 할당받고 실행되는 도중에 우선순위가 높은 프로세스가 생성되면 스케줄러는 실행 중인 프로세스를 실행 가능 상태로 만들고 우선순위가 높은 프로세스를 구동한다.
이때 우선순위가 낮은 프로세스는 계속 할당받지 못하는데, 이때 해당 프로세스의 상태를 기아(starvation) 상태라 한다.
그리고 이때 일정 시간 할당받지 못하면 우선순위를 높여 처리하는 걸 에이징(aging)이라 한다.

라운드 로빈(Round-Robin) 알고리즘: 실행 가능한 상태에 있는 프로세스들을 순서대로 가져와 일정 시간 동안 CPU를 할당하는 방식이다.
모든 프로세스는 같은 시간이 부여되며,
이때 프로세스에 부여된 일정 시간을 타임 슬라이스(time slice) 혹은 퀀텀(quantum)이라고 한다.
라운드 로빈을 이용하면 모든 프로세스가 동시에 실행되는 것처럼 보인다.
대표적인 선점형 스케줄링이며,
이때 가장 중요한 것은 타임 슬라이스를 어떻게 정하여 컨텍스트 스위칭의 트레이드 오프에 대한 고민이다.

FCFS(First Come First Served): 실행 가능 상태에 먼저 들어온 프로세스를 먼저 실행하는 방법이다. 비선점 스케줄링이다.

SJF(Shortest Job First): 평균 대기 시간을 최소화하기 위해 CPU 할당 시간이 가장 짧은 프로세스를 먼저 실행한다.
우선순위 알고리즘처럼 할당 시간이 긴 프로세스는 계속 실행되지 않아 기아 상태가 되며,
CPU의 실제 할당 시간을 알 수 없어 예측이 불가능하다.

## 5. 컨텍스트 스위칭과 PCB

출처: `computer_science/chapter/chapter10/chapter10.py`

프로세스 두 개가 같은 프로그램에서 만들어졌을 때 두 프로세스의 차이는?
우선 두 프로세스는 독립적인 메모리 공간을 가지게 된다.
실행 중인 인스턴스가 다르기 때문에 인스트럭션이나 스택 프레임이 서로 다르다.
실행 중인 인스트럭션이 다르므로 프로그램 카운터 값도 다르고,
스택 프레임도 다르니 스택 포인터와 프레임 포인터와 범용 레지스터의 값도 모두 다르다.

프로세스가 실행되기 위해서는 다양한 CPU 레지스터 값과 프로세스 상태 정보 등이 필요하며,
프로세스가 실행 상태에서 실행 가능 상태로 변경될 때 이러한 정보를 메모리 어딘가에 저장한다.
즉 프로세스의 CPU 상태와 프로세스의 상태를 저장해 둔 메모리 블록을 프로세스 제어 블록(Process Control Block, PCB)이라 한다.
PCB 데이터는 프로세스가 실행 가능 상태에서 실행 상태로 바뀔 때도 필요하다.
프로그램 카운터를 예로 들면, PCB에 저장된 프로그램 카운터 값을 CPU로 가져와야 이전에 실행한 마지막 인스트럭션의 다음 인스트럭션을 가져와서 실행한다.

즉! 스케줄러가 실행 중인 프로세스에서 CPU를 해제하고 실행 가능 상태의 프로세스에 CPU를 할당할 때,
실행 중인 프로세스의 CPU 상태 정보를 그 프로세스의 PCB에 저장하고
곧 실행될 프로세스의 PCB에서 이전 CPU 상태 정보를 CPU로 가져오는 것을 컨텍스트 스위칭이라 한다.
CPU 상태를 컨텍스트라 부르는데, 말 그대로 현재 CPU의 레지스터 값들을 전환하는 것이다.

즉 여기서 CPU에서 PCB로 데이터를 저장하고 PCB에서 데이터를 가져오는 것은 시스템에 부담을 주며 잦은 컨텍스트 스위칭은 시스템 성능을 떨어트린다.
정답은 없지만 이걸 고려하기 시작하는 걸로 실력 향상에 도움이 된다.

## 6. PC(Program Counter)가 가리키는 것

출처: `computer_science/chapter/chapter10/chapter10.py`

PC는 다음에 실행할 명령어의 메모리 주소를 가리킨다.
이건 스택 프레임의 생성/해제 "중간"일 수도 있고, 일반적인 연산 중간일 수도 있다.

예를 들어 함수 호출 과정에서 컨텍스트 스위칭이 일어났다면
인자를 푸시하는 중이었을 수도 있고,
call 명령어 직전이었을 수도 있다.
함수 내부 로직 실행 중이었을 수도 있다.

PCB에 저장되는 것들
- PC(Program Counter): 다음 실행할 명령어 주소
- SP(Stack Pointer): 현재 스택의 top 위치
- 범용 레지스터들: 연산 중간 결과들
- 상태 레지스터: 플래그들 (carry, zero 등)

## 7. 스레드와 TCB

출처: `computer_science/chapter/chapter10/chapter10.py`

스레드(thread)란 프로세스 안의 실행 흐름의 단위로, 스케줄러에 의해 CPU를 할당받을 수 있는 인스트럭션의 나열이다.
프로세스는 하나 이상의 스레드로 구성된다.
우리가 지금까지 작성한 프로그램은 모두 실행 흐름이 하나인 단일 스레드이다.
프로세스가 PCB를 갖는 것처럼 스레드는 스레드 제어 블록(Thread Control Block, TCB)을 갖고 있다.
TCB에는 스레드 ID, 각종 레지스터 정보, 스레드 상태 정보, 스레드가 속해 있는 프로세스의 PCB 주소 등이 저장되어 있다.
TCB 정보는 PCB와 유사하다.
CPU 레지스터 정보와 스레드의 상태 정보는 정확하게 프로세스와 같다.
즉 이전 설명에서 배운 프로세스 상태나 컨텍스트 스위칭이 스레드에도 똑같이 적용된다.
프로세스와 스레드의 차이를 알기 위해서는 멀티스레드와 멀티프로세스에 대해 알아야 된다.

## 8. 왜 여러 실행 흐름이 필요한가 — 멀티 프로세스 vs 멀티 스레드

출처: `computer_science/chapter/chapter10/chapter10.py`

멀티 프로세스와 멀티 스레드를 이해하기 전, 단일 코어 CPU에서 여러 개의 실행 흐름이 필요하다는 가정을 해보자.

대용량 데이터를 분석하는 프로그램을 만든다. 이때 필요한 흐름은?
네트워크에서 데이터를 전송받는 중에 명령(버튼이나 키보드)을 실행하면 사용자는 프로그램이 멈췄다고 생각할 것이다.
이때 UI를 담당하는 실행 흐름에서는 사용자가 현재까지 읽어들인 데이터를 가지고 분석 및 시각화를 할 수 있도록 명령을 한다.
프로그램 화면에서는 데이터를 얼마나 받았는지 즉각적인 피드백을 준다.

위의 실행 흐름을 분리하면,
1번 실행 흐름에서는 메모리의 힙 영역을 충분히 확보해 놓은 뒤 네트워크에서 데이터를 계속 수신해서 저장한다.
나머지 하나의 실행 흐름(2번)에서는 지금까지 받은 데이터를 이용하여 사용자의 명령을 수행한다.
이때 UI 담당 실행 흐름과 네트워크 수신 흐름에서는 데이터 수신 완료 여부를 나타내는 데이터를 서로 공유해야 즉각적인 반응을 보여줄 수 있다.
왜냐면 네트워크 수신 실행 흐름에서 데이터 수신을 완료했을 때
UI 담당 실행 흐름에서는 프로그램 화면의 데이터 수신 완료 표시등에 표시를 해야 하기 때문이다.
또한 네트워크 수신 실행 흐름과 데이터 분석 실행 흐름에서는 지금까지 받은 데이터(메모리 힙의 데이터)를 공유해야 된다.
그래야 데이터를 사용해 즉각 사용자가 실행 가능하기 때문.
이처럼 실행 흐름 사이에서 데이터를 공유해야 하는 경우는 흔하다.

실행 흐름 하나가 데이터를 변경했을 때 다른 실행 흐름도 변경된 데이터를 업데이트할 수 있어야지.
실행 흐름은 결국 CPU를 점유하고 인스트럭션을 실행하는 것이라 여러 실행을 구현하려면 멀티 프로세스나 멀티 스레드가 필요하다.
이때 멀티 프로세스는 서로 다른 메모리 공간을 가지기 때문에 데이터 공유를 위한 특별한 기법이 필요하다.

하지만 멀티 스레드로 공유하면 스택 레벨의 데이터만 서로 분리하여 쓰기 때문에 데이터 공유가 쉽다.
즉 스레드는 각자 독립적인 스택 세그먼트만 가지고 나머지 코드/데이터/힙은 다른 스레드와 공유한다.
즉 데이터 세그먼트나 힙 세그먼트에 공유 데이터를 두면 모든 스레드가 이용 가능.

메모리 구조만 봐도, 실행 흐름이 동시에 필요하고 공유 데이터가 있으면 멀티스레드가 합리적이다.
이때 여러 실행 흐름이 필요한 프로그래밍을 동시성 프로그래밍이라 하며 멀티 스레딩을 이용한다.

## 9. 파이썬 멀티스레딩 기본과 GIL 실험

출처: `computer_science/chapter/chapter10/chapter10.py`

기본 흐름 — 리스트를 4개 스레드로 나눠 처리하는 코드.

```python
def thread_main(li, i):
    # range() 안의 값이
    # 스레드가 담당할 리스트의 인덱스 범위 결정
    for i in range(offset * i, offset*(i + 1)):
        # 요소에 2를 곱한다.
        li[i] *= 2

if __name__ == "__main__":
    import threading

    num_elem = 1000   # 리스트 요소 개수
    num_thread = 4    # 스레드 개수

    # 오프셋 = 리스트 요소 개수 // 스레드 개수
    # 스레드 함수에서 연산을 담당할 인덱스 범위를 구하는 데 쓰인다.
    offset = num_elem // num_thread

    li = [i+1 for i in range(num_elem)]

    # 스레드를 담을 리스트
    threads = []
    for i in range(num_thread):
        # 스레드 객체 생성
        # target은 실행할 스레드 함수
        # args는 전달할 인자 목록
        th = threading.Thread(target=thread_main, args=(li, i))
        threads.append(th)

    for th in threads:
        # 스레드 실행 시작
        th.start()
    for th in threads:
        # 스레드 실행 완료 대기
        th.join()
```

```
기대한 것:
t1 ████████
t2 ████████
t3 ████████
t4 ████████  (동시에)

실제:
t1 ██      ██      ██
t2   ██      ██      ██
t3     ██      ██      ██
t4       ██      ██       (번갈아가며 순차 실행)
```

리스트 요소에 2를 곱하는 연산은 내부적으로 C로 구현된 리스트 연산이라 짧은 GIL로 오차가 없을 수 있다.
그래서 순수 파이썬 CPU 연산으로 바꿔 측정해 보면:

```python
def thread_main(li, i, offset):
    for idx in range(offset * i, offset * (i + 1)):
        # 순수 파이썬 CPU 연산
        x = li[idx]
        for _ in range(100):
            x = x * 2 + 1 - 1
        li[idx] = x
```

측정 결과:

```
멀티스레드: 62.182초
싱글스레드: 0.643초
```

4개의 스레드가 한 번에 하나씩만 실행 가능한 GIL을 서로 뺏으려고 경쟁한다.
이렇게 CPU 연산에서는 순수 파이썬 연산은 threading은 안 쓰느니만 못하기에 멀티 프로세싱을 써야 한다.

```
멀티스레드:
t1: 실행 → GIL 반납 → 대기 → GIL 획득 → 실행 → ...
t2: 대기 → GIL 획득 → 실행 → GIL 반납 → 대기 → ...
t3: 대기 → 대기 → GIL 획득 → 실행 → GIL 반납 → ...
t4: 대기 → 대기 → 대기 → GIL 획득 → 실행 → ...
```

스레드는 일정한 시간 간격으로 CPU를 할당받아 연산하는데, 이때 일정한 시간 간격을 타임 슬라이스라 한다.
파이썬은 sys 모듈을 사용하면 슬라이스를 알 수 있다.
이때 파이썬 멀티스레딩의 각 스레드 실행 시간인 타임 슬라이스는 0.005초이다.

## 10. 경쟁 조건

출처: `computer_science/chapter/chapter10/chapter10.py`

```python
import threading
# 모든 스레드가 공유할 데이터
g_count = 0

# 스레드가 실행할 함수
def thread_main():
    global g_count
    for i in range(100000):
        g_count += 1

threads = []

if __name__ == "__main__":
    for i in range(50):
        th = threading.Thread(target=thread_main)
        threads.append(th)

    for th in threads:
        th.start()

    for th in threads:
        th.join()

    print('g_count : {:,}'.format(g_count))
```

위의 코드와 같이 50개의 스레드가 동시에 카운트에 접근하여 값을 수정하려고 할 텐데,
이때 여러 스레드가 동시에 접근·수정 가능한 자원을 공유 자원이라 한다.
이때 500만이 나와야 하는데 매번 다른 값이 나오는 이유는,
컨텍스트 스위칭이 일어나면서 값이 교체가 되는데 이때 문제가 생기기 때문이다.
선점형 스케줄링에서는 1번이 끝날 때까지 기다리지 않고
컨텍스트 스위칭이 일어나서 1을 제대로 넣기 전에 2번째 작업이 진행되며, 아직 완료가 안 되어 0이라 1이 들어가고
그 후 1이 들어갈 수도 있다.
그럼 1에 또 스위칭으로 1을 넣어서 2개를 넣었지만 결과적으로는 1만 되는 것.
이처럼 스레드 여러 개가 공유 자원에 동시에 접근하는 것을 경쟁 조건이라 한다.
이처럼 공유 자원에 접근해 변경을 시도하는 코드를 임계 영역이라 한다.

## 11. 상호 배제와 Lock

출처: `computer_science/chapter/chapter10/chapter10.py`

경쟁 조건 문제를 해결하기 위해 상호 배제(mutual exclusion)를 사용한다.

상호 배제의 원리는 매우 간단하다.
스레드 하나가 공유 자원을 이용하는 동안 다른 스레드가 접근하지 못하게 막는 것이다.
파이썬에서는 Lock 객체를 통해 활용한다.

```python
import threading

g_count = 0
# 락 객체 생성
lock = threading.Lock()

def thread_main():
    global g_count
    # Lock을 획득
    # 한 스레드가 획득하면
    # 획득을 시도한 나머지 스레드는 대기
    lock.acquire()
    for i in range(100000):
        g_count += 1

    # lock을 반환
    # 획득했던 스레드가 반환하면
    # 대기하던 스레드 중 하나가 획득
    lock.release()
```

acquire를 통해 락을 획득하면 다른 스레드는 락 객체를 얻지 못하고 대기 상태가 된다.
락을 획득했던 스레드가 임계 영역을 빠져나와 release를 하면
락 객체를 반환하며 대기 중이던 스레드 중 하나가 해당 락을 획득하여 진행한다.

## 12. GIL(전역 인터프리터 락)

출처: `computer_science/chapter/chapter10/chapter10.py`

파이썬의 전역 인터프리터 락(Global Interpreter Lock, GIL)은
상호 배제를 구현하는 한 가지 방법인 뮤텍스(mutex)로, 한 번에 스레드 여러 개가 바이트 코드를 실행하는 것을 막아준다.
멀티 코어에서도 싱글 코어를 사용하는 것과 같은 효과를 내는데,
이는 CPython의 메모리 관리가 스레드에 안전하지 않기 때문이다.
스레드에 안전하다는 의미는 어떤 자원에 여러 스레드가 동시에 접근해도 실행이 잘된다는 의미로,
자바나 아이언파이썬은 GIL이 없어서 멀티코어에서 멀티스레딩 구현이 가능하며
GIL은 Lock 객체 방식과 유사하다.

GIL은 실행 중이던 스레드가 I/O 작업을 시작하면 GIL을 반환하고 다른 스레드가 해당 락을 획득하며,
실행 중인 스레드가 I/O 작업을 하지 않더라도 타임 슬라이스가 지나면 GIL을 반환하고 다른 스레드에게 CPU 할당을 양보한다.
GIL로 인해 멀티코어의 장점을 활용하지 못한다 해도 GIL이 멀티 스레드를 사용하지 않는 이유가 돼서는 안 된다.
GIL에도 불구하고 멀티 스레딩은 여전히 동시 실행에 대한 문제를 해결할 수 있다?

- CPU 바운드: 멀티스레드 의미 없음 → multiprocessing 써야 함
- I/O 바운드: 멀티스레드 효과 있음 → 네트워크, 파일, DB 작업 등
