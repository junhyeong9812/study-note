## 정답

1. 셀을 직렬(string)로 엮어 집적도를 얻은 결정. 직렬이라 셀 하나만 집어 접근할 수 없어 페이지 단위 접근이 되고, program(0)은 페이지 단위지만 복원(1)은 블록 전체를 지워야 하므로 덮어쓰기가 안 되며, 전자를 절연층 너머로 강제 통과시킬 때마다 절연층이 손상되어 수명이 유한하다. 집적도를 얻는 대가로 접근 자유도를 포기한 것이고, NOR(병렬, 바이트 랜덤 접근, 비쌈)와의 차이가 그 증거다.

2. FTL은 SSD 컨트롤러 펌웨어로, 호스트가 보는 "주소 지정 가능한 블록 장치"라는 환상과 NAND 제약 사이를 번역한다 — 주소 변환(LBA → 물리 block/page), GC, 웨어 레벨링, 에러 정정. 핵심 아이디어: "제자리에 못 쓰면 빈 곳에 쓰고 주소표를 고친다." 옛 페이지는 invalid 표시만 하고 새 페이지에 쓴 뒤 매핑을 갱신하므로 SSD 내부는 그 자체가 append-only 로그다(log-structured FTL).

3. GC는 희생 블록의 유효 페이지를 복사한 뒤 지운다. 유효 비율 p면 WAF = 1/(1-p). 순차 쓰기는 블록 안 페이지가 함께 쓰이고 함께 무효화되어 p≈0 → WAF≈1(복사 없이 erase). 랜덤 쓰기는 무효화가 흩뿌려져 어느 블록이든 p≈0.6~0.9 → WAF 3~10. 추가로 4KB 쓰기는 페이지(16KB)보다 작아 RMW로 페이지 전체를 다시 쓴다. HDD의 순차/랜덤 격차가 seek였다면 SSD에서는 WAF가 그 자리를 대신한다. 수명도 비례해 깎인다(1PB 총량이 WAF=5면 호스트 기준 200TB).

4. ① SLC 캐시 고갈 — TLC 일부를 SLC 모드로 써서 쓰기를 빠르게 받다가 캐시가 차면 TLC 본래 속도로 떨어진다(3GB/s → 100MB/s 수준). ② 빈 블록 고갈로 foreground GC — 여유 블록이 바닥나면 GC가 유효 페이지를 복사해 블록을 비울 때까지 호스트 쓰기가 대기한다(3GB/s → 500MB/s). 디스크가 거의 찼으면 둘이 겹친다. 그래서 지속 쓰기 워크로드는 벤치마크 수치가 아니라 캐시 고갈 후 sustained write를 봐야 한다.

5. DRAM은 데이터 캐시가 아니라 주로 FTL 매핑 테이블용이다. page-level 매핑은 1TB·4KB 페이지 → 2.5억 엔트리 × 4B ≈ 1GB(경험칙 1TB당 1GB). DRAM-less는 호스트 RAM 수십 MB를 빌려(HMB) 매핑 일부만 캐싱하므로, 순차 접근은 매핑이 연달아 히트하지만 큰 용량에 랜덤 접근을 흩뿌리면 매핑 캐시 미스가 폭증해 NAND에서 매핑을 읽어오는 추가 지연이 붙는다. "SSD 랜덤 100µs" 안에는 NAND 읽기뿐 아니라 이 매핑 조회 비용이 들어 있다.

6. 2D는 밀도를 위해 셀을 10nm대까지 축소해 전자 수십 개로 1비트를 표현했다(몇 개만 새도 손실). 3D는 밀도를 적층(200~300층)으로 얻으므로 평면 방향은 30~50nm를 유지할 수 있어 셀이 전자를 훨씬 많이 담는다 — 축소에서 적층으로 수단이 바뀌어 셀 크기를 희생하지 않아도 됐다. Floating gate는 도체라 층마다 격리가 필요하고 이웃 셀 간 정전용량 결합(FG-FG coupling) 간섭이 심한데, charge trap은 부도체(질화막)라 전자가 함정에 갇혀 못 움직이므로 원통 하나로 200층을 관통시켜도 층마다 독립 동작한다. 결함이 생겨도 근처 전자만 잃어 내구성도 좋다.

7. append-only → 블록이 순서대로 채워져 GC 시 p=0, WAF=1 / 큰 배치 → 페이지 단위 이상으로 정렬되어 RMW 없음 / 세그먼트 통째 삭제(1GB) → 블록 전체가 한 번에 무효화되어 GC가 사실상 공짜(TRIM과 결합) / 수정 API 없음 → 부분 덮어쓰기가 원천적으로 없음 / offset 순차 읽기 → 매핑 테이블 조회가 연속 히트. SSD 컨트롤러가 랜덤 쓰기를 순차 로그로 바꾸려고 FTL로 고생하는 일을 Kafka는 애초에 시키지 않는다.
