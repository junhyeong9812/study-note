# cs/nand-flash — NAND 플래시와 SSD 내부 (FTL · GC · Write Amplification) — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다.
> 원고는 내가 직접 쓴 `NAND.md`(물리·셀·3D) + `kafka.md`의 SSD 내부 절(FTL·매핑·RMW·GC·WAF)을 한 사슬로 합친 것이다(2026-08-20).

## 전체 흐름

```text
[물리]   NAND 셀은 직렬 배선 → 페이지 단위 읽기/쓰기, 블록 단위 지우기, 덮어쓰기 불가, 수명 유한
   ↓
[펌웨어] 그래서 FTL이 필요 → 매핑 테이블로 주소 변환, "제자리에 못 쓰면 빈 곳에 쓰고 주소표를 고친다"(append)
   ↓
[부작용] 무효 페이지가 쌓임 → GC가 유효 페이지를 복사하고 블록을 지움 → 호스트가 시키지 않은 쓰기 = Write Amplification
   ↓
[성능]   랜덤 쓰기일수록 블록 안에 유효/무효가 섞여 WAF가 커짐 → 느려지고 수명도 깎임
   ↓
[설계]   Kafka(append-only + 큰 배치 + 세그먼트 통째 삭제)는 블록이 통으로 무효화되어 GC가 할 일이 없음 → WAF ≈ 1
```

NAND의 물리 제약이 위로 전파되어 FTL·GC·WAF를 낳고, Kafka의 설계는 그 사슬의 맨 아래 제약을 거스르지 않았기 때문에 SSD 시대에도 맞아떨어진다.

## 1. NAND라는 이름과 구조

NAND는 논리 게이트 이름(NOT AND)이다. 플래시 메모리에 이 이름이 붙은 건 셀들의 배선이 NAND 게이트를 닮았기 때문이다.

```text
NOR 플래시:  ─┬──┬──┬──┬─   셀이 병렬 → 각 셀에 개별 배선 → 아무 셀이나 바로 읽음(바이트 단위 랜덤 접근)
NAND 플래시: ─셀─셀─셀─셀─   셀이 직렬(string) → 배선 적음, 집적도 높음 → 페이지 단위로만 접근
```

직렬로 엮으면 셀당 배선이 적어 조밀하게 만들 수 있지만 특정 셀 하나만 콕 집어 접근하기 어렵다. **"페이지 단위 읽기/쓰기, 블록 단위 지우기"라는 제약은 이 직렬 구조에서 나온다.** 집적도를 얻는 대가로 접근 자유도를 포기한 것이다. NOR는 펌웨어·BIOS(코드를 직접 실행), NAND는 SSD·USB·SD카드(대용량 저장)에 쓴다.

## 2. 셀이 데이터를 저장하는 원리

NAND 셀은 일반 MOSFET에 **floating gate**라는 층이 하나 더 있는 트랜지스터다.

```text
 Control Gate    ← 전압을 거는 곳
 ─── 절연층 ───
 Floating Gate   ← 전자가 갇히는 곳 ★ 사방이 절연체
 ─── 절연층 ───
 Source | Drain
```

- program(쓰기): 고전압으로 전자를 floating gate에 주입 → 문턱 전압(Vth) 상승
- read: 전압을 걸어 전류가 흐르는지 확인 → 전자 유무 판별
- erase: 반대 전압으로 전자를 빼낸다

전원이 꺼져도 전자가 갇힌 채 남는다 — 이게 비휘발성의 정체다.

**수명이 유한한 이유**: 전자를 절연층 너머로 강제 통과시킬 때마다 절연층이 조금씩 손상된다. 수천 번 반복하면 전자가 새기 시작한다 — P/E cycle 한도의 물리적 원인. 갇힌 전자는 시간이 지나면 아주 천천히 빠져나가기도 한다(charge leakage). SSD를 몇 년간 전원 없이 방치하면 데이터가 손상될 수 있고 고온일수록 빠르다.

## 3. 셀당 비트 수 — SLC / MLC / TLC / QLC

전자량을 몇 단계로 구분하느냐가 셀당 비트 수를 정한다. "Level"은 비트 수가 아니라 **구분해야 하는 전압 단계 수**다.

```text
SLC 1bit  2단계   P/E ~100,000   가장 빠름   매우 비쌈
MLC 2bit  4단계   P/E ~3,000
TLC 3bit  8단계   P/E ~1,000     보통        보통
QLC 4bit  16단계  P/E ~300       느림        가장 쌈   오류율 매우 높음
```

문턱 전압 범위는 그대로인데 더 잘게 쪼개는 것이므로 비트를 늘릴수록 단계 사이 여유가 좁아진다. **용량은 선형으로 늘지만 수명은 지수적으로 떨어진다** — TLC→QLC는 용량 +33%, 수명 1/3.

**SLC 캐시 트릭**: TLC 셀 일부를 SLC 모드(1비트)로 써서 들어오는 쓰기를 일단 빠르게 받고 한가할 때 TLC 영역으로 옮긴다. 짧은 쓰기는 매우 빠르지만 캐시가 고갈되면 급락(3GB/s → 100MB/s 수준). 용량이 거의 찬 SSD가 느려지는 이유가 이것이고, GC 문제와 겹쳐 이중으로 느려진다. 지속 대량 쓰기 워크로드(Kafka 같은)는 SLC 캐시를 금방 소진하므로 벤치마크 수치가 아니라 **캐시 고갈 후 sustained write**를 봐야 한다.

## 4. 3D NAND — 축소 대신 적층

평면에서 셀을 계속 작게 만들다 보니 셀 간 간섭이 심해져 미세화가 한계에 부딪혔다. 해법은 위로 쌓는 것이다. 워드라인(게이트)을 200~300층 깔아두고 그걸 관통하는 구멍을 뚫어 채널을 세운다. **수직 채널 기둥 하나가 곧 NAND string 하나** — 2D에서 옆으로 누워 있던 직렬 줄이 3D에서는 서 있는 것이다. 한 겹씩 200번 만드는 게 아니라 절연막과 희생층을 한꺼번에 증착한 뒤 고종횡비 식각(HARC)으로 구멍을 뚫는다. (V-NAND = 삼성, BiCS = 키옥시아/샌디스크, CTF 3D NAND = 일반 명칭)

**Floating Gate → Charge Trap Flash(CTF)**: 3D로 가면서 저장 매체가 도체(polysilicon)에서 부도체(실리콘 질화막)로 바뀌었다. 도체는 셀마다 물리적으로 격리해야 하고 이웃 셀 간 정전용량 결합(FG-FG coupling) 간섭이 심한데, 부도체는 전자가 "함정(trap)"에 걸려 못 움직이므로 질화막을 긴 원통 하나로 뽑아 200층을 관통시켜도 층마다 독립 동작한다. 절연층에 결함이 생겨도 FG는 전하가 전부 새지만 CTF는 그 근처 전자만 잃어 내구성이 구조적으로 좋다.

**"셀이 커졌다"의 의미**: 2D는 밀도를 위해 셀을 10nm대까지 줄여 전자 수십 개로 1비트를 표현했다(몇 개만 새도 손실). 3D는 밀도를 층으로 얻으므로 평면 방향은 30~50nm급을 유지할 수 있어 셀 하나가 전자를 훨씬 많이 담는다. 밀도 수단이 "축소"에서 "적층"으로 바뀐 덕에 셀 크기를 희생하지 않아도 됐고, 3D 초기 세대가 2D 말기보다 수명이 좋아졌다.

## 5. 계층 구조와 병렬성

```text
SSD
└── NAND 패키지 여러 개  ┐
    └── Die (칩)         │ 이 층위들이 병렬로 동작 → SSD 대역폭의 원천
        └── Plane        │
            └── Block  ← ERASE 단위 (수 MB)
                └── Page   ← READ / PROGRAM 단위 (4~16KB)
                    └── Cell ← 비트 저장 (SLC/TLC/QLC)
```

NAND 칩 하나는 느리다(페이지 읽기 ~50µs). SSD가 GB/s를 내는 건 컨트롤러가 수십 개 die에 동시에 요청을 뿌리기 때문이다. 순차 접근은 여러 die에 골고루 퍼져 병렬성을 최대로 쓰고, 작은 랜덤 접근은 한 die에 몰리거나 큐가 얕아져 병렬성을 낭비한다. 큐 깊이(queue depth)가 깊어야 die들이 놀지 않는다 — NVMe가 SATA보다 빠른 이유 중 하나.

## 6. FTL — 제자리에 못 쓰면 빈 곳에 쓰고 주소표를 고친다

### 먼저 알아야 할 것 — NAND의 세 가지 제약

1. **읽기/쓰기 단위(Page 4~16KB)와 지우기 단위(Block = 페이지 수백 개, 수 MB)가 다르다.**
2. **덮어쓰기가 불가능하다.** program(0으로 만들기)은 페이지 단위지만 되돌리기(1로 복원)는 블록 전체를 지워야만 된다.
3. **수명이 유한하다.** 특정 블록만 계속 쓰면 그 부분만 먼저 죽는다.

그런데 OS와 파일시스템은 이걸 모른다. "LBA 12345에 4KB 써"라고 HDD에게 하듯 명령할 뿐이다. 이 간극을 메우는 게 FTL이다.

### 동작

SSD 컨트롤러 안의 펌웨어 계층. 호스트가 보는 "주소 지정 가능한 블록 장치"라는 환상과 NAND 제약 사이를 번역한다 — 주소 변환 + GC + 웨어 레벨링 + 에러 정정.

```text
LBA 12345 수정 요청
  옛 데이터 (Block 5, Page 3) → invalid 표시만 하고 그대로 둠
  새 데이터 (Block 9, Page 0) → 여기에 새로 씀
  매핑 테이블 12345 → (9, 0) 로 갱신
```

**SSD 내부는 그 자체가 append-only 로그 구조다**(log-structured FTL). Kafka가 소프트웨어에서 한 일을 SSD 컨트롤러는 하드웨어에서 이미 하고 있다.

### 매핑 granularity 세 가지

- **Page-level**: 페이지마다 매핑. 랜덤 쓰기 성능 좋음. 테이블이 거대 — 1TB SSD, 4KB 페이지 → 2.5억 엔트리 × 4B ≈ 1GB. **경험칙: 1TB당 DRAM 1GB.** SSD에 DRAM이 붙어 있는 건 데이터 캐시가 아니라 주로 이 테이블 때문이다.
- **Block-level**: 블록 단위만 매핑. 테이블은 수백 분의 1이지만 블록 안 페이지 하나만 고쳐도 블록 전체를 다시 써야 해서 단독으로는 안 쓴다.
- **Hybrid / DFTL**(실무): 대부분 블록 매핑 + 최근 쓰이는 "로그 블록"만 페이지 매핑(Hybrid), 또는 전체 테이블은 NAND에 두고 자주 쓰는 부분만 DRAM 캐싱(DFTL, 미스 시 NAND에서 매핑을 읽어와 추가 지연).

**DRAM-less SSD와 HMB**: 저가형은 DRAM 없이 호스트 RAM 수십 MB를 빌려(HMB) 매핑 캐시로 쓴다. 큰 용량에 랜덤 접근을 흩뿌리면 매핑 캐시 미스가 폭증해 급락한다 — 벤치마크 순차 속도는 멀쩡한데 실사용에서 버벅이는 이유. "SSD 랜덤 접근 ~100µs" 안에는 NAND 읽기뿐 아니라 이 매핑 조회 비용이 들어 있다. 순차는 매핑이 연달아 히트하고 랜덤은 매번 미스날 수 있다.

## 7. Read-Modify-Write (RMW)

쓰기 최소 단위보다 작게 쓰려 할 때 기존 내용을 읽어와 합친 뒤 통째로 다시 쓰는 동작.

```text
페이지 16KB인데 4KB만 쓰면:
  READ 16KB → MODIFY 4KB → WRITE 16KB 전체를 새 페이지에
  → 호스트는 4KB 썼다고 생각하지만 NAND에는 16KB 기록 (4배)
```

SSD 안에만 있는 게 아니다 — 512e 디스크(물리 4KB, 호스트 512B 접근), RAID 5/6(스트라이프 일부만 쓰면 패리티 재계산), 파일시스템(블록보다 작은 쓰기). **정렬(alignment)**도 여기서 나온다: 16KB를 써도 페이지 경계에 안 맞으면 두 페이지 모두 RMW. 파티션을 1MiB 경계에 정렬하라는 권고가 이 때문이다. Kafka는 배치를 모아 큰 단위로 쓰므로 RMW가 거의 없다.

## 8. Garbage Collection — 무효 페이지 공간을 되찾기

FTL은 수정 시 옛 데이터를 invalid로 표시만 하므로 시간이 지나면 블록에 유효/무효가 섞인다. 재사용하려면 통째로 erase해야 하는데 유효 페이지가 살아 있다.

```text
Block 5: [V][I][I][V][I][I][I][V]   유효 3, 무효 5

1. 희생 블록 선정    무효가 가장 많은 블록 (greedy)
2. 유효 페이지 복사  살아있는 3개를 다른 빈 블록으로 이주   ← 공짜가 아니다 ★
3. 매핑 테이블 갱신
4. ERASE            Block 5 통째로 지움 → 빈 블록 확보
```

2번의 복사는 **호스트가 시키지 않은 쓰기**다. 자바 GC와 이름이 같고 "쓰레기를 모아 공간을 되찾는다"는 발상도 같지만 대상이 힙 객체가 아니라 NAND 블록이다.

**문제를 일으키는 지점**: 지연시간 스파이크(평소 100µs가 GC와 겹치면 수 ms — p99 tail latency의 전형적 원인), 대역폭 잠식, 빈 블록 고갈 시 급락(foreground GC — 벤치마크 처음 3GB/s가 계속 쓰면 500MB/s로 주저앉는 현상).

**완화 장치**: Over-provisioning(실제 NAND를 표시 용량보다 많이 — 512GiB 넣고 480GB 판매, 엔터프라이즈는 20~30%), TRIM/UNMAP(파일 삭제 시 OS가 "이 LBA 이제 필요 없다"고 알려줌 — 안 알려주면 삭제된 데이터도 유효한 줄 알고 계속 복사), Idle-time GC, 사용자가 디스크를 꽉 채우지 않기(OP를 늘려주는 효과).

## 9. Write Amplification — 왜 랜덤 쓰기가 SSD를 죽이는가

```text
WAF = 실제 NAND에 기록된 바이트 / 호스트가 요청한 바이트     (1이 이상적, 4면 1GB 쓸 때 4GB 기록)
```

원인: ① GC의 유효 페이지 복사(가장 큼) ② RMW ③ 웨어 레벨링 이주 ④ 매핑 테이블 등 메타데이터.

**핵심 수식** — 희생 블록의 유효 페이지 비율을 p라 하면:

```text
페이지 100개 블록, p=0.8 → 80개 복사 + 20개 기록 = 100개 기록으로 20개분 공간 회수 → WAF = 5
일반화: WAF = 1 / (1 - p)        p=0 → 1,  0.5 → 2,  0.8 → 5,  0.9 → 10
```

p를 결정하는 것은 **접근 패턴**이다.

```text
[순차 쓰기]  블록 안 페이지들이 함께 쓰이고 나중에 함께 무효화 → [I][I][I][I][I][I][I][I] p≈0 → 그냥 erase, WAF≈1
[랜덤 쓰기]  무효화가 여기저기 흩뿌려짐 → [V][I][V][V][I][V][I][V] p≈0.6 → 어느 블록을 골라도 복사할 게 많음, WAF 3~10
```

같은 SSD인데 접근 패턴만 바꿔도 실제 NAND 쓰기량이 5~10배 차이 난다. HDD의 "순차 vs 랜덤 수천 배"는 seek 때문이었지만, **SSD에서는 seek가 없는 대신 WAF가 그 자리를 대신한다.**

수명에 직결된다: 1TB TLC, P/E 1000회 → 총 쓰기 가능량 ≈ 1PB. WAF=1이면 호스트 기준 1PB, WAF=5면 200TB만에 소진. 스펙의 TBW/DWPD는 제조사가 상정한 워크로드 기준이라 랜덤 쓰기가 심하면 스펙보다 빨리 죽는다.

## 10. Kafka로 돌아와서

```text
Kafka의 설계                 SSD 내부에서 벌어지는 일
append-only 로그         →   블록이 순서대로 채워짐 → GC 시 p=0 → WAF=1
큰 배치로 write          →   페이지 단위 이상으로 정렬 → RMW 없음
세그먼트 단위 삭제(1GB)   →   블록 전체가 한 번에 무효화 → GC가 사실상 공짜
수정 API 없음            →   부분 덮어쓰기가 원천적으로 없음
offset 순차 읽기         →   매핑 테이블 조회가 연속 히트
```

SSD 컨트롤러는 랜덤 쓰기를 어떻게든 순차 로그로 바꾸려고 FTL이라는 복잡한 계층을 두고 고생하지만, Kafka는 애초에 순차 로그로 데이터를 만들어 내려보낸다. Kafka가 SSD에서도 빠른 건 "SSD가 빨라서"가 아니라 **SSD가 내부적으로 가장 싫어하는 일(GC 복사·RMW)을 애초에 시키지 않기 때문**이다.

## 핵심 문장

- 페이지 쓰기/블록 지우기/덮어쓰기 불가/유한 수명 — 네 제약은 전부 "셀을 직렬로 엮어 집적도를 얻은" 한 결정에서 나온다.
- FTL의 핵심은 "제자리에 못 쓰면 빈 곳에 쓰고 주소표를 고친다" — SSD 내부는 append-only 로그다.
- GC의 유효 페이지 복사는 호스트가 시키지 않은 쓰기다. WAF = 1/(1-p)이고 p는 접근 패턴이 정한다.
- SSD에는 seek가 없는 대신 WAF가 순차/랜덤 격차의 자리를 대신한다.
- 비트를 늘리면 용량은 선형, 수명은 지수로 떨어진다. 3D는 축소 대신 적층으로 밀도를 얻어 셀 크기를 지켰다.
- Kafka가 SSD에서도 빠른 건 SSD가 싫어하는 일을 시키지 않기 때문이다.
