# reliability/15-logging — 정답

## 정답

### 1. 로그가 답하는 질문

- 지표는 "에러율이 올랐다", "p99가 2초다"처럼 **집계**를 준다. 어떤 주문이, 어느 단계에서, 무슨 값으로 실패했는지는 사건 단위 기록이 있어야 안다.
- 네 가지
  1. 구조화 — 필드로 검색·집계
  2. 상관 ID — 한 요청의 줄을 묶음
  3. 레벨 — 중요도 구분과 비용 조절
  4. 샘플링·비동기 기록 — 로그가 서비스를 느리게 하거나 디스크를 채우지 않게

### 2. 텍스트 vs 구조화

| | 텍스트 | 구조화 |
|---|---|---|
| 주문 1042 찾기 | 정규식, 문구가 바뀌면 깨짐 | `orderId = 1042` 정확히(수집 단계에서 `kvpList` 값을 필드로 뽑아 둔 경우. Logback `JsonEncoder`는 값을 문자열 `"1042"`로 적는다) |
| 집계 | 문장마다 값이 달라 같은 사건끼리 묶기 어려움 | `message`가 고정이라 "order placed" 수를 셈 |
| 트레이스와 연결 | 문장에서 ID를 파싱 | `TraceId`·`SpanId` 칸(OTel 로그 데이터 모델) |

- 메시지에 값을 넣으면 같은 사건이 줄마다 다른 문장이 된다. 사건 종류별 집계가 깨지고, 값 검색은 문자열 검색이 된다.

### 3. MDC와 스레드풀

(실험, JDK 21 + Logback 1.5.18)

```text
..."threadName":"pool-1-thread-1",..."mdc": {},"message":"async step (MDC 복사 안 함)"...
..."threadName":"pool-1-thread-1",..."mdc": {"requestId":"req-AAAA"},"message":"요청 B 처리 — 누구의 ID가 찍히나?"...
```

- 넘긴 작업의 줄: `mdc: {}`. MDC는 ThreadLocal이라 풀 스레드에는 없다.
- 요청 B의 줄: `req-AAAA` — **앞 요청의 ID**가 찍힌다.
- 더 위험한 쪽은 뒤쪽이다. 빈 ID는 "모른다"고 드러나지만, 틀린 ID는 엉뚱한 요청의 기록으로 보여 조사를 잘못 이끈다.

### 4. 동기 vs 비동기

(실험, JDK 21 + Logback 1.5.18, `--cpus=2`, 세 번 실행)

```text
sync              호출 지연 p50=  2.109ms p99=  2.267ms max=  3.199ms ... | 전달 INFO 1800/1800 WARN 200/200
async-default     호출 지연 p50=  0.005ms p99=  0.078ms max=532.936ms ... | 전달 INFO  626/1800 WARN 200/200
async-neverBlock  호출 지연 p50=  0.001ms p99=  0.016ms max=  0.655ms ... | 전달 INFO  372/1800 WARN 107/200
```

- 동기: 호출마다 목적지 지연(약 2ms)이 더해진다. 유실 0.
- 비동기 기본: 호출은 µs 단위. INFO는 남은 칸이 20%(51칸) 미만일 때 버려져 558~743건만 전달됐다(집필·점검 6회). WARN은 다 전달됐지만 가끔 약 530ms 기다렸다.
- neverBlock: 멈춤 없음. WARN도 버린다(실행마다 다르다 — 6회에서 73~141/200).

### 5. 530ms 멈춤

- WARN 이상은 `put`으로 넣으므로 큐(256칸)가 꽉 차면 호출 스레드가 기다린다.
- 워커는 `take()` 후 `drainTo`로 큐를 통째로 가져가 하나씩 쓴다. 256개 × 2ms ≈ 512ms 동안 큐가 다시 찬다.
- 꽉 찬 큐에 자리가 나는 때는 워커가 그 묶음을 다 쓰고 다시 꺼낼 때다. 그래서 멈춤이 약 530ms로 나왔다(해석 — Logback 1.5.18 `AsyncAppenderBase.Worker` 소스와 실험 값의 대조).

### 6. 샘플링 단위

(실험, 요청 1000 × 5줄, 10%)

```text
줄마다 무작위: 남은 줄 452, 5줄 다 남은 요청 0, 일부만 남은 요청 373
요청 ID 해시: 남은 줄 480, 5줄 다 남은 요청 96, 일부만 남은 요청 0
```

- 줄 단위: 남은 줄은 비슷하지만 끝까지 이어지는 요청은 0개(확률상 0.1⁵ = 10만분의 1).
- 요청 ID 해시: 약 10%(96개) 요청이 통째로 남는다.

### 7. stdout과 회전

- 12-factor XI: 앱은 로그 파일을 관리하지 않고, 이벤트 스트림을 **stdout에 버퍼 없이** 쓴다. 모으고 보내는 것은 실행 환경의 몫이다.
- 회전 책임은 실행 환경(컨테이너 런타임·노드 에이전트)으로 간다.
- Docker `json-file` 드라이버의 `max-size` 기본값은 -1(무제한)이다. 데몬 설정이나 `--log-opt max-size=...`로 회전을 걸지 않으면 컨테이너 로그가 디스크를 채울 수 있다.

### 8. 꺼진 DEBUG의 비용

- 레벨 검사는 이벤트를 만들기 전에 하므로 꺼진 로그는 거의 공짜다.
- 단, 호출 **인자**는 그 전에 계산된다. `log.debug("x=" + big.toString())`처럼 문자열을 미리 이어 붙이거나 비싼 메서드를 인자로 부르면 레벨과 상관없이 비용이 든다.
- 문자열 이어 붙이기·`toString()`은 `{}` 자리표시자나 `log.atDebug()`로 피한다(레벨이 꺼지면 형식화하지 않는다).
- 비싼 메서드 호출 자체는 그것으로 못 피한다. 인자는 호출 전에 계산되기 때문이다. `isDebugEnabled()` 검사나 `Supplier`를 받는 `addArgument(() -> …)`·`addKeyValue("x", () -> …)`(SLF4J 2.x)를 쓴다.

### 9. 수집기 지연 → API p99 상승

- 볼 것
  - 스레드 덤프(`jcmd <pid> Thread.print`): 요청 스레드가 appender의 쓰기(`FileOutputStream.write`, 소켓 쓰기)에서 멈춰 있나.
  - p99 상승 시각과 수집기·디스크 지연 상승 시각이 겹치나.
- 원인: 동기 appender라 목적지의 지연이 요청 경로에 들어온다(실험의 sync — 호출마다 목적지 지연만큼 증가).
- 고치기: 비동기 appender로 떼어 내고 유실·멈춤 정책(`queueSize`·`discardingThreshold`·`neverBlock`)을 명시한다. stdout에 쓰고 전송은 수집기에 맡긴다. 로그 양을 줄인다. 버린 수를 지표로 낸다(Logback `AsyncAppender`는 버린 수를 세지 않으니 따로 계측한다).

### 10. 토큰이 로그에 남았을 때

- 남는 경로를 막는다: 헤더·본문 전체 덤프 제거, 민감 필드 마스킹(`Authorization`·비밀번호·세션 ID·카드 정보 — OWASP "Data to exclude"), `toString()`에서 민감 필드 제외, 허용 목록 방식 필드 선택.
- 이미 남은 것: 해당 토큰 폐기(재발급), 로그 저장소의 해당 기간 데이터 처리 절차.
- 밖에서 온 값은 개행·제어 문자를 정리해 로그 주입을 막는다.
