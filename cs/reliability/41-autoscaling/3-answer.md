# reliability/41-autoscaling — 정답

## 정답

### 1. desired 계산

- 105% / 70% = 1.5 → |1.5 − 1| = 0.5 > 0.1 → ceil(4 × 1.5) = **6대**.
- 75% / 70% ≈ 1.07 → 허용 오차 0.1 안 → **그대로 4대**.

### 2. 반응 지연의 구간

```text
 급증 → 지표 수집·평균 → 다음 동기화(≤15초) → 스케줄 → 이미지 pull → 런타임 시작·워밍업 → readiness → 용량
```

- HPA·클러스터 설정으로 줄이는 것: 동기화 주기(`--horizontal-pod-autoscaler-sync-period`), 스케일 업 정책·안정화, 여유 노드(스케줄 대기).
- 애플리케이션·이미지로 줄이는 것: 이미지 크기(pull), 런타임 시작·워밍업, readiness가 정직하게 빨리 통과하도록(42번).

### 3. 4배가 한 번에 안 되는 이유

1. CPU 사용률은 포화되면 더 오르지 못한다. 천장은 CPU limit ÷ request다(사용률이 request 대비 %라서). limit = request이면 천장이 100% 근처라, 목표 70%에서 비율이 약 1.43을 넘지 못한다. 실제 수요가 4배여도 지표는 1.43배만 보여 준다. limit이 request보다 크면 천장이 더 높아(1번의 105%처럼) 이 제약이 느슨해진다.
2. 스케일 업 계산에서 준비 안 된 파드는 0% 사용으로 쳐진다. 새로 만든 파드가 준비될 때까지 추가 확장이 억제된다.
- (덧붙여) 기본 스케일 업 정책은 15초에 +100% 또는 +4개 중 큰 쪽까지다.

### 4. 급증 시뮬레이션

(실험, HPA 식·기본값 결정적 시뮬레이션)

- 모양: 5 → 7 → 10 → 15 → 22 → 25대로 **계단식**. 각 계단은 새 파드 준비(90초)를 기다린 뒤에 온다.
- 따라잡는 시점: t ≈ 360~390초. 급증(t=60~70초) 뒤 약 5분.
- 그동안 대기열이 10초치로 가득 차 타임아웃 121,180건(전체 약 12%).
- 이후 25대(사용률 48%)까지 갔다가 안정화 창 5분 뒤 20 → 18대로 줄었다. 정답은 1,200 / 70 = 17.1 → 18대.

### 5. 준비 시간 단축 vs 여유 용량

| 설정 | 타임아웃 | 파드·분 |
|---|---|---|
| 준비 90초, 목표 70%, 최소 5 | 121,180 | 267 |
| (a) 준비 20초 | 30,180 | 266 |
| (b) 준비 90초, 목표 50%, 최소 8 | 30,300 | 379 |

- 둘 다 타임아웃을 약 1/4로 줄였다. (a)는 비용이 그대로, (b)는 비용이 약 42% 늘었다.
- 준비 시간 단축이 가능하면 더 싸다. 여유 용량은 단축이 어려울 때의 보험이다.

### 6. 기본 behavior와 비대칭

- scaleUp: 안정화 0초, 15초에 +100% 또는 +4개 중 큰 쪽(`selectPolicy: Max`).
- scaleDown: 안정화 300초, 15초에 100%까지.
- 비대칭 이유: 확장 실패는 과부하·유실로 이어지고, 축소 실패는 비용만 든다(SRE Workbook 11장: 스케일 업이 더 중요하고 덜 위험하다). 줄였다가 곧 다시 늘리면 준비 시간 동안 넘친다.
- 안정화 창: 지난 창(기본 300초) 안의 추천값 중 **최댓값**을 써서 줄인다. 문서는 rolling maximum의 근사라고 부른다.

### 7. 출렁임에서의 안정화 창

| 창 | 변경 횟수 | 최대 대기열 | 타임아웃 | 파드·분 |
|---|---|---|---|---|
| 0초 | 58 | 6,000 | 73,127 | 257 |
| 300초 | 5 | 3,591 | 27,569 | 357 |

- 창이 없으면 골마다 줄였다가 마루마다 다시 늘린다. 다시 늘리는 동안(준비 60초) 넘쳐 타임아웃이 더 많다.
- 창 300초는 거의 마루 기준으로 유지해 타임아웃이 줄고, 대신 비용이 약 39% 늘었다.

### 8. maxReplicas

- 역산 대상: 하류 자원 한도. 예: DB 커넥션 총량 = maxReplicas × 인스턴스당 풀 ≤ DB 한도. 외부 API 동시 한도, 클라우드 쿼터도.
- 너무 크게 정하면(`autoscaling/v2`에서 `maxReplicas`는 필수 필드라 생략할 수는 없다)
  1. 앱이 늘수록 DB 커넥션이 폭증해 DB가 죽는다(병목 이동).
  2. 버그(헛도는 CPU)나 하류 장애로 그 상한까지 늘어 쿼터·비용을 다 쓴다(SRE Workbook 11장 Setting Constraints).

### 9. 준비 안 된 파드와 확장 억제

- 이유: CPU 기준 스케일 업 계산에서 준비 안 된 파드는 0% 사용으로 쳐진다. 다시 계산한 비율이 허용 오차 안으로 들어오면 확장하지 않는다. 준비 안 된 파드가 오래 남으면 계속 억제된다.
- 고치는 법: readiness 실패 원인(헬스 체크 경로·의존성 대기·설정 오류)을 고친다. 준비 시간을 줄인다(이미지·워밍업). 로드밸런서가 본 용량 지표로 스케일해 건강하지 않은 인스턴스를 빼는 방법도 있다(SRE Workbook 11장).

### 10. 하류 장애와 폭주 확장

- 일어난 일: 하류가 느려져 요청이 서버에 붙잡혔다. 동시 요청·CPU 지표가 "일이 많다"로 보였고, 오토스케일러가 늘렸다. 늘어난 인스턴스가 하류를 더 눌러 회복을 막는다(SRE Workbook 11장의 사례).
- 막는 법
  - 하류 호출 데드라인과 서킷 브레이커로 막힌 요청을 빨리 끊는다.
  - `maxReplicas`·쿼터로 상한.
  - 오토스케일 킬 스위치와 수동 조정 절차.
