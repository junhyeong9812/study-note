# reliability/24-feature-flag-lifecycle — 정답

## 정답

### 1. 배포와 릴리스의 분리

- 배포 = 코드를 서버에 올림. 릴리스 = 사용자가 기능을 봄.
- 새 코드를 꺼진 플래그 뒤에 두고 배포하면, 공개(켜기)와 되돌림(끄기)이 설정 변경이 된다. 재배포가 필요 없다.
- 대가: 플래그 하나마다 코드 경로가 둘이다. n개면 조합 2^n. 다 쓴 플래그를 안 지우면 죽은 코드가 켤 수 있는 상태로 남는다.

### 2. 네 유형

| 유형 | 수명 | 판정 |
|---|---|---|
| 릴리스 | 1~2주 이내 권장 | 대체로 정적(보통 배포 단위로 같음) |
| 실험 | 시간~주(유의한 결과가 나올 때까지) | 동적, 같은 사용자는 같은 집단 |
| 운영 | 대부분 짧음, 일부 상시 | 운영자가 빨리 바꿔야 함 |
| 권한 | 오래(제품 기능) | 요청마다 |

- 킬 스위치 = 오래 사는 운영 플래그. 부하가 높을 때 덜 중요한 기능을 끈다(Hodgson: 수동 서킷 브레이커).
- 관리 차이: 릴리스 플래그는 빨리 지우는 것이 목표다. 킬 스위치는 지우지 않고, 눌렀을 때 실제로 동작하는지 주기적으로 확인한다.

### 3. 평가 일관성

- 무작위: 화면 10개에서 섞어 볼 확률 = 1 − (0.8^10 + 0.2^10) ≈ 89.3%.
- 해시 버킷: 같은 사용자 → 같은 버킷 값 → 같은 결과 → 0%.

(실험, JDK 21.0.12, 사용자 10,000명)

```text
(1) 요청마다 무작위 20%   → 신·구 섞어 본 사용자  8932명 (89.3%), 항상 신 UI 0명
(1) 사용자 해시 버킷 20%  → 신·구 섞어 본 사용자     0명 (0.0%), 항상 신 UI 2018명
```

### 4. 비율 올리기

```text
(2) 20%→50% (솔트 s1→s1): 전 2018명 켜짐, 후 5035명 켜짐, 켜졌다 꺼진 사용자 0명
(2) 20%→50% (솔트 s1→s2): 전 2018명 켜짐, 후 4987명 켜짐, 켜졌다 꺼진 사용자 1054명
```

- 같은 솔트: 각 사용자의 버킷 값은 그대로이고 기준선만 0.2 → 0.5로 오른다. 0.2 미만이던 사람은 0.5 미만이기도 하다 → 0명.
- 솔트 변경: 버킷 값이 새로 뽑힌다. 처음 켜진 2,018명 중 약 절반(새 기준 50%를 넘는 사람)이 꺼진다 → 1,054명. 받았던 기능을 빼앗긴다.

### 5. 해시에 플래그 키가 없으면

- 솔트 등 나머지 해시 입력도 같으면(이 실험) 플래그끼리 같은 버킷 값을 쓴다. 플래그 A 20%와 플래그 B 20%가 **같은 사람들**이 된다.
- 1,959명: A를 받은 전원(≈ 20%)이 B도 받았다(두 플래그가 같은 버킷 값을 쓰므로 구성상 전원). 두 실험이 같은 집단이라 효과를 구분할 수 없다.
- 407명: 플래그 키를 넣어 독립이 된 경우. 기대값 10,000 × 0.2 × 0.2 = 400명에 가깝다.

### 6. 플래그 서비스 장애와 기본값

- 계약: OpenFeature Requirement 1.4.10 — 평가 메서드는 예외를 던지지 않고, 비정상 실행이면 **호출자가 넘긴 기본값**을 돌려준다.
- 그래서 평가가 기본값으로 떨어지는 장애(받아 둔 설정 없이 플래그 서비스가 안 됨 등)에서는 코드의 기본값이 동작을 정한다. 기본값이 `true`면 노출 10,000/10,000(실험 4).
- 막기
  - 기본값 = 기존 동작(false). Hodgson 관례 "꺼짐 = 기존, 켜짐 = 새".
  - 설정 스냅숏을 로컬에 두고 로컬에서 평가해, 서비스 장애가 평가를 멈추지 않게 한다.
  - reason=ERROR 비율에 경보.

### 7. Knight Capital의 플래그

- 새 RLP 코드는 옛 Power Peg를 켜던 플래그를 재사용했다(SEC 명령 ¶13). Power Peg는 2003년에 쓰지 않게 됐지만 코드는 남아 있었고 호출 가능했다(¶13·¶14).
- 8대 중 1대에 새 코드가 복사되지 않았다(¶15). 플래그가 켜진 주문이 그 서버에 가자 Power Peg가 돌았다(¶16).
- 2005년 이동한 누적 수량 기능 때문에 Power Peg는 체결 수를 세지 않고 자식 주문을 계속 보냈다(¶14·¶16). 약 45분 동안 약 400만 건 체결, 손실 4억 6천만 달러(¶17).
- 맞물림: 죽은 코드(안 지움) + 플래그 재사용(옛 의미가 살아 있는 서버) + 배포 누락(확인 절차 없음). 하나만 없었어도 이 경로는 생기지 않았다.

### 8. 지우는 순서

1. 코드에서 분기를 지우고 배포한다.
2. 전 서버가 그 버전인지 확인한다.
3. 설정에서 플래그를 지운다.

- 거꾸로 하면: 아직 분기를 가진 서버가 "모르는 플래그 → 기본값"으로 평가한다. 기본값이 기존 동작이면 일부 사용자에게 옛 동작이 다시 보이고, reason=ERROR·FLAG_NOT_FOUND 류 평가가 특정 파드에서만 나온다.

### 9. 조합 수와 테스트

- 2^30 = 1,073,741,824개(실험 5).
- Hodgson의 권고: (a) 출시될 운영 설정(현재 운영 + 이번에 켤 플래그 켬) (b) 대비 설정(이번 플래그 끔) (c) 전부 켬. 대부분의 플래그는 서로 상호작용하지 않고, 한 릴리스에서 바뀌는 플래그는 대개 하나다.
- 전제 관례: 꺼짐 = 기존 동작, 켜짐 = 새 동작. 그래야 "전부 켬"이 "미래 상태"를 뜻한다.

### 10. 등록과 방치 방지

- 등록: 이름(재사용 금지), 유형, 담당자, 만료일, 꺼짐·켜짐의 의미, 기본값.
- 장치(Hodgson): 생성 시 제거 작업을 백로그에 함께 넣기, 만료일, 만료가 지나면 테스트를 실패시키는 시한폭탄, 동시 플래그 수 상한(새로 만들려면 하나를 지운다).
- 운영: 코드 참조 vs 등록부 대조, 100% 도달 후 정리 기한.
