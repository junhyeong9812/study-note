# reliability/45-chaos-and-resilience-testing — 정답

## 정답

### 1. 가정을 미리 확인하는 이유

- 가정은 해 보기 전까지 참인지 모른다. 확인하지 않으면 처음 확인하는 날이 진짜 사고 날이다. 그때는 원인 파악·수정이 사고 시간에 더해진다.
- 장애를 작은 범위·근무 시간에 일부러 넣으면, 같은 약점을 대응할 사람이 있을 때 싸게 찾는다.

### 2. 네 단계

```text
 정상 상태 정의 → 가설(두 군 모두 유지) → 실제 사건 주입 → 두 군의 차이 찾기
 (지표·임계)      (반증 가능한 문장)      (범위·중단 조건)    (차이 = 약점 / 없음 = 확신)
```

- 반증: 가설이 틀렸다는 증거(두 군의 정상 상태 차이)를 찾으려 애쓴다. 찾지 못할수록 확신이 쌓이고, 찾으면 고칠 대상이 생긴다.

### 3. 정상 상태 지표

- 사용자 성공률(또는 지연 분위수·업무 지표). Principles: 내부 속성이 아니라 시스템의 **측정 가능한 출력**에 초점을 둔다 — 처리량, 오류율, 지연 분위수.
- Netflix는 초당 재생 시작 수(SPS)를 시스템 건강의 주 지표로 쓴다(Basiri 외 2016). CPU는 오르내려도 사용자가 괜찮을 수 있고, 반대로 CPU는 멀쩡한데 사용자가 실패할 수 있다(위 실험의 naive).

### 4. 실험 예측

(실험, Redis 7.4.9 + JDK 21.0.12)

- naive: 장애 구간부터 실험 끝까지 **0**(`실험군 85 89 89 90 7 0 0 … 0`). 끊긴 소켓을 계속 쓴다.
- resilient: 두 구간만 떨어지고(`15 44`, 다른 실행 `17 43`·`27 31`·`33 24`) 다음 구간부터 대조군과 같다(`89 90 91 …`).
- 대조군: 첫 구간(워밍업, 73~85)을 빼면 구간당 88~92로 평평했다. 두 번째 실행에서는 뒤 절반 합만 기록했는데 721·725로 비슷했다.

### 5. 대조군의 역할

- 실험군이 떨어진 것이 **장애 주입 때문**인지, 같은 시각의 다른 원인(호스트 부하, 네트워크) 때문인지 가를 수 없다. 대조군이 평평하니 "실험군만 떨어졌다"고 말할 수 있다.

### 6. 운영 실험과 폭발 반경

- 범위를 작게(소수 비율 사용자·인스턴스 하나), 자동 중단 조건을 먼저, 대응할 사람이 있을 때 한다. 스테이징 → 운영의 작은 비율 → 넓게.
- Netflix는 Chaos Monkey를 평상 근무 시간에만 돌린다. 인스턴스 종료로 서비스가 실패하면 엔지니어가 바로 대응할 수 있게 하려는 것이다(Basiri 외 2016).

### 7. 결제 서비스 첫 실험 (예)

- 가설: "PG 응답이 2초 지연돼도 결제 API 성공률과 p99는 대조군과 같다(타임아웃·폴백 덕분에)."
- 정상 상태: 결제 API 성공률, p99 지연, 결제 완료 수/분.
- 주입: 실험군 요청의 PG 호출에 2초 지연(서비스 메시 fault 필터 또는 테스트용 프록시).
- 범위: 스테이징 → 운영 내부 사용자 1%.
- 중단 조건(예시): 실험군 성공률이 대조군보다 1%p 이상 낮거나 p99가 3초를 넘으면 자동 원복.

### 8. 게임 데이

- 같은 것: 실제 사건을 흉내 내 주입하고 결과를 관찰한다.
- 더 있는 것: **사람과 절차**의 대응(런북·사고 지휘·공지·에스컬레이션)을 함께 연습한다. 팀이 실제 사건 때와 같은 행동을 해 본다(REL12-BP05).
- 안티패턴(REL12-BP05): 절차를 문서로만 두고 연습하지 않는다. 사업 의사결정자를 빼고 한다.

### 9. 작년엔 됐는데

- 의심: 그 사이 바뀐 것 — 클라이언트 라이브러리·설정, 인프라 이전, DNS·엔드포인트 캐시, 타임아웃 값. 시스템이 바뀌면 지난 실험의 확신은 줄어든다(Basiri 외 2016).
- 막기: 실험을 자동화해 정기적으로 계속 돌린다. 관련 구성 요소를 바꾸는 변경 뒤에는 해당 실험을 다시 돈다. 회복 시간을 지표로 남겨 추세를 본다.
