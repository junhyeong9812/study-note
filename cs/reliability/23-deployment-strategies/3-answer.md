# reliability/23-deployment-strategies — 정답

## 정답

### 1. 배포 전략 = 가용성 설계

- SRE 책 1장 "Change Management": 장애의 약 70%가 운영 중인 시스템의 변경에서 나온다.
- 권하는 세 가지: 점진 배포(progressive rollouts), 빠르고 정확한 문제 탐지, 문제가 생기면 안전한 롤백.
- 이 셋이 "나쁜 변경에 노출되는 사용자·작업의 총량"을 줄인다. 배포 전략은 노출량(몇 %에게)과 복구 시간(얼마나 빨리 되돌리나)을 정하므로 가용성을 직접 좌우한다.

### 2. 네 전략의 시간축

```text
 재생성   v1×4 | 공백 | v2×4                         공존 없음, 대신 서비스 공백
 롤링     v1×4 → v2 v1 v1 v1 → … → v2×4              공존 = 첫 교체부터 마지막 교체까지
 블루그린  [파랑 v1 ← 트래픽] ─전환─> [초록 v2 ← 트래픽]   공존 ≈ 전환 순간뿐(자원 두 배)
 카나리   v1 95% + v2 5% → 25% → 50% → 100%           공존 = 카나리 전 기간(의도된 비교)
```

### 3. 두 요청 흐름이 깨지는 비율

- 두 요청이 서로 다른 버전에 갈 확률 = 2·p·(1−p).
  - 5% → 9.5%, 25% → 37.5%, 50% → 50%.
- 실험 카나리(가중치 76:4 = 5%): 카나리 구간 거절 174 / 흐름 1,798 = 9.7%. 이론값 9.5%와 맞는다.
- 그래서 5% 카나리라도 다단계 흐름의 피해는 5%의 약 두 배다.

### 4. 시나리오별 거절 합계

(실험, nginx 1.31.1 + Node 22.23.2)

```text
rolling        TOTAL {"ok":4437,"badToken":1048,"http5xx":0,"netErr":24}
bluegreen      TOTAL {"ok":4993,"badToken":5,"http5xx":0,"netErr":4}
rolling-compat TOTAL {"ok":4332,"badToken":0,"http5xx":0,"netErr":18}
```

- 롤링: 첫 교체부터 마지막 교체까지 약 6.5초 동안 공존 → 거절 1,048(재실행 1,404 — 건수는 실행마다 다르다). 첫 교체 전, 그리고 마지막 교체를 걸친 0.5초 집계 줄(93건 — 교체 앞뒤를 가를 수 없다) 뒤에는 0.
- 블루그린: 공존이 전환 순간뿐 → 전환 시각에 ①·② 사이에 걸친 흐름만 깨져 5.
- 확장 배포 롤링: `v2read`는 두 형식을 읽고 옛 형식으로 쓴다. v1도 v2read가 쓴 토큰을 읽을 수 있다 → 0.

### 5. Kubernetes 롤링이 해 주는 것·안 해 주는 것

| 항목 | 기본값 | 의미 |
|---|---|---|
| strategy.type | RollingUpdate | 다른 값은 Recreate |
| maxUnavailable | 25%(내림) | 갱신 중 원하는 수의 75% 이상 유지 |
| maxSurge | 25%(올림) | 갱신 중 원하는 수 + ⌈25%⌉개까지(3개면 4개 = 133%) |
| progressDeadlineSeconds | 600 | 넘으면 `ProgressDeadlineExceeded` 조건만 기록 |
| revisionHistoryLimit | 10 | 0이면 `rollout undo` 불가 |

- 해 주는 것: maxSurge·maxUnavailable 범위 안에서, 새 파드가 가용(준비 상태를 `minReadySeconds`(기본 0) 동안 유지)해지는 만큼 다음으로 넘어가고, 가용해지지 않으면 멈춘다. 리비전을 남겨 `kubectl rollout undo`를 가능하게 한다.
- 해 주지 않는 것: 오류율·지연 판정, 멈춘 배포의 자동 롤백(문서: "takes no action … other than to report a status condition"). 이것은 파이프라인이나 Argo Rollouts 같은 상위 도구의 일이다.

### 6. 롤백이 원래대로 못 돌리는 경우

1. 새 버전이 새 형식으로 이미 쓴 데이터(캐시·큐·DB) — 옛 버전이 못 읽는다.
2. 파괴적 스키마 변경(컬럼·테이블 삭제, 의미를 바꾼 UPDATE).
3. 밖으로 나간 부수 효과(결제·메일·주문 체결).

- Knight Capital(SEC 명령 ¶27): 정상 배포된 7대에서 새 RLP 코드를 제거했다. 그 7대에서도 재사용한 플래그가 옛 Power Peg 코드를 켜 문제가 커졌다. 롤백도 변경이고, "옛 버전"이 무엇을 할지 확인하지 않은 롤백은 위험하다.

### 7. 확장 배포 = expand/contract

```text
 배포 1 (확장)  : 새 형식을 읽을 줄 안다, 쓰기는 옛 형식         ← 공존해도 서로 읽는다
 배포 2 (전환)  : 새 형식으로 쓴다 (인스턴스 전부가 이미 읽을 줄 안다)
 배포 3 (축소)  : 옛 형식 읽기 코드를 지운다(옛 형식 데이터가 다 사라진 뒤)
```

- DB에서는 새 컬럼 추가 → 양쪽 쓰기·백필 → 읽기 전환 → 옛 컬럼 삭제다([database/26-schema-migration](../../database/26-schema-migration/2-summary.md)).
- 같은 구조: 어느 순간에도 "돌고 있는 두 버전이 서로가 남긴 상태를 읽을 수 있다"를 지킨다. 그래서 각 단계는 직전 단계로 롤백할 수 있다.
- 최소 두 번(읽기 확장, 쓰기 전환), 정리까지 세 번이다.

### 8. before/after 비교의 위험

- 시간으로 집단을 나누면 시간 자체의 변화(요일·시간대·다른 배포·외부 사건)가 섞인다. Workbook 16장은 이것을 "canary deployment in time-space"라 부르고 위험하다고 적는다.
- 같은 시각에 도는 control(옛 버전 집단)과 비교한다. 카나리와 control이 백엔드를 공유하면 서로 영향을 줄 수 있으니 SLO 같은 고정 기준도 함께 본다.

### 9. 전환 직후 짧은 연결 오류

- 가설: 옛 워커·옛 인스턴스가 keep-alive 연결을 닫는 순간에 클라이언트가 그 연결로 요청을 보냈다. nginx reload는 옛 워커가 옛 클라이언트를 마저 처리하고 끝나는 방식이다(nginx "Controlling nginx").
- 확인: 오류 원인 코드(실험에서는 netErr 전부가 `UND_ERR_SOCKET`), 전환 시각과의 일치, 오류가 HTTP 상태 코드가 아니라 소켓 수준인지.
- 대처: 멱등 요청은 한 번 재시도한다. 옛 인스턴스는 드레이닝 뒤에 내린다([14-graceful-shutdown](../14-graceful-shutdown/2-summary.md)). 비멱등 요청은 멱등 키를 붙여 재시도한다([13-idempotency](../13-idempotency/2-summary.md)).

### 10. 배포 중에만 오류

- 볼 것: 오류를 버전 레이블별로 나눈다. 못 읽는 쪽 버전(양방향 비호환이면 양쪽 모두)이 오류를 내고 오류 내용이 "모르는 형식·필드·스키마"면 공존 비호환이다. 시간축에서 오류 구간이 배포 시작~끝과 겹친다.
- 왜 롤백 중에도 오르나: 롤백도 롤링이라 공존 구간이 또 생긴다.
- 고치기: 변경을 확장 배포(읽기 먼저) → 쓰기 전환으로 쪼갠다. 당장은 블루그린처럼 공존 시간을 줄이는 전환으로 피해를 줄인다(실험: 1,048 → 5).
