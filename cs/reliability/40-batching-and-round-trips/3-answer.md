# reliability/40-batching-and-round-trips — 정답

## 정답

### 1. RTT가 바닥

- 한 건씩 기다리면 한 요청에 최소 RTT 250ms → 초당 최대 4요청(Redis 문서의 예). 서버 처리 능력과 무관하다.
- 파이프라이닝은 서버 쪽 시스템 콜 비용도 줄인다. 명령마다 `read()`·`write()`(사용자 ↔ 커널 전환)를 하던 것을, 여러 명령을 한 번의 `read()`로 읽고 여러 응답을 한 번의 `write()`로 보낸다. 문서는 파이프라인 길이에 따라 처리량이 거의 선형으로 늘다가 파이프라인 없을 때의 약 10배에 이른다고 적는다(문서 그림의 환경 기준).

### 2. 다섯 방식

(실험 1, PostgreSQL 17.11 + pgjdbc 42.7.4, 직결, 두 번째 실행)

| 방식 | 시간 | 행당 |
|---|---|---|
| 자동 커밋 1행씩 | 16567ms | 3.313ms |
| 한 트랜잭션 1행씩 | 812ms | 0.162ms |
| 1000행 배치 | 137ms | 0.027ms |
| 배치 + rewrite | 67ms | 0.013ms |
| COPY | 33ms | 0.007ms |

- 첫 실행도 같은 순위(20029 / 966 / 155 / 68 / 28ms).

### 3. 자동 커밋이 느린 이유

- RTT(SELECT 1 왕복 약 0.6ms)보다 행당 시간(3.3ms)이 훨씬 크다. 차이는 **커밋마다 WAL flush를 기다린 시간**이다.
- 확인: 같은 자동 커밋 1행씩에 `SET synchronous_commit = off`만 주자 15872ms → 939ms(행당 0.188ms)로 한 트랜잭션 묶기(918ms)와 거의 같아졌다. 사실 점검 재실행에서도 0.8~1.5초 vs 0.8~1.1초로 같은 자릿수였다.
- 단 `synchronous_commit = off`는 DB가 죽으면 가장 최근 트랜잭션들을 잃을 수 있다(PostgreSQL 17 문서 28.4). 적재 속도를 위해서는 설정보다 트랜잭션 묶기가 먼저다.

### 4. RTT 약 3ms

- 크게 느려짐: 한 트랜잭션 1행씩 812ms → 14461ms(행당 2.892ms ≈ RTT), 자동 커밋 1행씩 16567 → 29378ms. 둘 다 행마다 왕복하기 때문이다.
- 거의 그대로: 1000행 배치 137 → 197ms, rewrite 67 → 76ms, COPY 33 → 36ms. 왕복이 5번(배치)·1번(COPY)뿐이라 RTT 증가분이 몇 ms~십수 ms에 그친다.

### 5. 배처와 대기 상한

```text
 도착 ──> [버퍼] ──(크기 maxSize 도달 OR 첫 항목이 maxWait 대기)──> 전송
```

- 대기 상한 ≈ min(maxWait, maxSize / 도착률). 실제 상한은 maxWait + 타이머 확인 주기 + 스케줄링 지연(실험 max 20.4~23.3ms)이고, maxSize / 도착률은 고른 도착을 가정한 근사다.
- 50건/s: maxSize / λ = 2초 > maxWait → 상한 20ms. 실험: 평균 배치 2.0건, p99 20.4ms. 이득(왕복 절반) 대비 지연 20ms가 더해졌다.
- 5000건/s: maxSize / λ = 20ms = maxWait. 실험: 크기 트리거 150번, 평균 배치 100건, p99 19.7ms.

### 6. 파이프라인 길이와 지연

- 처리량: 11504.83 → 98425.20 → 222717.16 requests/s(약 8.6배 → 19배).
- p50: 0.055 → 0.119 → 0.367ms로 늘었다.
- 사실 점검 재실행(Redis 컨테이너 안 루프백)도 같은 경향이었다: 처리량 약 9.1배 → 13.9배, p50 0.039 → 0.079 → 0.375ms. 배율은 환경마다 다르다.
- 뜻: 묶을수록 왕복당 처리량은 늘지만, 각 명령은 묶음 전체와 함께 보내지고 응답도 묶음 단위로 오므로 개별 지연이 는다. 배치 크기는 처리량과 지연 사이의 선택이다. 처리량만 보고 정하면 지연 증가를 놓친다.

### 7. 너무 큰 배치의 문제

1. 메시지 크기 한도: MySQL 8.4 서버 `max_allowed_packet` 기본 64MB(mysql 클라이언트 16MB) — 넘으면 `ER_NET_PACKET_TOO_LARGE`를 내고 연결을 닫는다. pgjdbc 확장 쿼리 프로토콜은 한 문장의 바인드 파라미터 65535개 제한.
2. 긴 트랜잭션: 락을 오래 쥐어 다른 요청이 기다리고, 복제 지연·undo/bloat가 커진다(→ database/34).
3. 메모리: Redis는 파이프라인 응답을 서버 메모리에 쌓는다. 문서는 아주 많은 명령을 예컨대 1만 개씩 끊어 보내라고 권한다. 클라이언트 쪽 버퍼도 커진다.

(그리고 모으는 대기가 지연에 더해진다 — 5번.)

### 8. DataLoader 규칙

- 배치 함수는 키 배열과 **같은 길이**의 값 배열을 돌려준다. 각 인덱스의 값은 같은 인덱스의 키에 대응한다(순서 맞추기).
- 키 하나만 없으면 그 자리에 `Error` 인스턴스를 넣는다. 그 키의 `load()`만 실패하고 나머지는 정상 처리된다.
- 기본 `maxBatchSize`는 `Infinity`. 저장소에 크기 한도가 있으면 직접 제한한다.

### 9. 부분 실패

- pgjdbc 42.7.4 + PostgreSQL 17(실험 3): 자동 커밋·명시 커밋·rewrite 모두 `BatchUpdateException`, `updateCounts`가 10개 전부 `-3`(EXECUTE_FAILED), 테이블에 남은 행 0.
  - 이어질 장애: 중복 1건 때문에 나머지 9건도 버려지고, 같은 배치를 재시도하면 계속 실패해 진행이 멈춘다.
- Redis 파이프라인(실험): `SET k1 a`, `SET s hello`, `INCR s`, `SET k2 b` → `+OK`, `+OK`, `-ERR …`, `+OK`. 3번째만 실패하고 나머지는 반영됐다.
  - 이어질 장애: 응답 목록에서 에러 항목을 확인하지 않으면 "파이프라인 성공"으로 처리해 일부 데이터가 빠진다.
- 공통 대처: 그 시스템의 의미를 실험으로 확인하고, 항목별 결과를 검사하며, 실패 항목만 재시도·격리한다.

### 10. 야간 적재 고치기

- 순서
  1. 측정: 행 수, 문장 호출 수(pg_stat_statements `calls`), 행당 시간, RTT.
  2. 트랜잭션 묶기: 자동 커밋을 끄고 청크(예: 수천 행)마다 커밋.
  3. 배치: `addBatch`/`executeBatch` + 드라이버의 다중 VALUES 재작성(pgjdbc `reWriteBatchedInserts=true`).
  4. 대량이면 `COPY`(PostgreSQL 17 문서 14.4: COPY는 PREPARE·한 트랜잭션 묶기를 쓴 INSERT보다도 거의 항상 빠르다).
  5. 한도 확인: 패킷 크기·파라미터 수·트랜잭션 시간이 넘지 않게 청크 크기 조정.
- 확인
  - 적재 후 건수·체크섬 대사(원본 행 수 = 대상 행 수).
  - 실패 처리: 원자적 배치에서 문제 행을 격리하는 경로, 항목별 API라면 실패 건수 지표.
  - 재시작: 청크 진행 지점 기록과 멱등 재실행(→ database/34).
  - 적재 중 다른 쿼리의 지연(락·IO 경합).
