# reliability/08-time-budget-allocation — 정답

## 정답

### 1. 예산표

```text
 총 1000 = 예약(네트워크·직렬화 100) + 예약(폴백 100) + 단계 몫 800
 단계 몫 800 ⊇ 인증 50 → DB 200 → 하류 B(2 × per-try 200 + 대기 50) → 여유 100   (예시)
```

- 먼저 예약: 응답 직렬화·전송, 폴백 실행 몫. 단계가 다 실패해도 이 시간은 남아야 한다.
- 직렬 단계는 더하고, 병렬(팬아웃) 단계는 가장 긴 것 하나만 센다.
- 재시도 단계의 몫 = 시도 수 × per-try + 대기 합.

### 2. AWS의 방법

- 허용할 오탐 타임아웃 비율(예: 0.1%)을 고르고, 하류 지연 분포에서 그에 해당하는 백분위(p99.9)를 출발점으로 삼는다.
- 맞지 않는 경우
  - 인터넷 너머 클라이언트처럼 네트워크 지연이 큰 경우 → 합리적인 최악 네트워크 지연을 더한다.
  - p99.9가 p50에 가까운(분포가 좁은) 서비스 → 여유(padding)를 더해 작은 지연 증가가 대량 타임아웃이 되지 않게 한다.

### 3. per-try 없는 "최대 3회"

(시뮬레이션, 요청 100만 건, 시드 42)

- 시도/요청 **1.000**, 성공 **99.492%** — 단일 시도(99.483%)와 같은 수준이다.
- 이유: 멈춘 시도가 시도 상한 = 전체 1000ms를 다 쓴다. 남은 예산이 0이라 두 번째 시도가 시작되지 않는다. "3회"는 설정에만 있다.
- 대조: per-try = p99(586ms)면 시도/요청 1.010, 성공 99.970%.

### 4. per-try = p50

- 성공 **87.498%**, 시도/요청 **1.750**.
- 식: 시도마다 오탐(정상인데 끊김) 확률이 약 0.5다. 세 번 모두 실패할 확률 ≈ 0.5³ = 12.5% → 성공 87.5%. 평균 시도 수 = 1 + 0.5 + 0.25 = 1.75.
- 하류가 조금만 느려지면 오탐률이 더 올라 부하가 더 커진다.

### 5. Envoy route `timeout`과 `per_try_timeout`

- per-try는 전체보다 작아야 하고, `시도 수 × per-try + 대기 ≤ 전체`가 되게 잡는다. 아니면 마지막 시도가 잘린다. 헤더 `x-envoy-upstream-rq-per-try-timeout-ms`도 전체보다 작지 않으면 무시된다(router 문서).
- per-try는 응답의 일부가 클라이언트 쪽(Envoy 용어 downstream)으로 나가기 **전**까지만 적용된다(보통 상류가 응답 헤더를 보낸 시점까지).
- 전체 timeout 초과로 504가 나면 Envoy는 재시도하지 않는다(router 문서 `5xx` 항목). 재시도를 원하면 per-try를 쓴다.

### 6. 최소치 규칙

- SRE 22장 "Missing deadlines": 여러 단계로 처리하면 각 단계 전에 충분한 시간이 남았는지 확인하라. 끝내지 못할 일은 시작하지 않는다.
- 실험(단계 예산 600ms, per-try p90, 최대 4회): 잘린 시도 0.087 → 0회/100요청, 성공률 99.913 → 99.902%. 효과가 작았다.
- 이유: 이 조건에서 남은 예산이 p50(83ms)보다 작아지는 경우가 드물다(세 번 연속 실패 뒤에만). 예산이 빠듯하고 호출이 깊을수록(남은 예산이 자주 작아질수록) 잘리는 시도가 늘어 효과가 커진다.

### 7. 폴백이 있는데 504

- 원인: 단계들이 전체 예산을 다 쓴 뒤 폴백을 시작한다. 폴백을 실행할 시간이 없거나, 시작하자마자 게이트웨이가 끊는다.
- 대처: 예산표에서 폴백·응답 몫을 먼저 예약하고, 단계 실행기가 `remaining - reserve`만 쓰게 한다.

### 8. 하류 요청량 2배

- 타임아웃이 하류 분포의 한가운데(p50 근처)에 있는 것을 의심한다. 정상 응답의 상당수가 오탐으로 끊기고 재시도된다(실험 p50: 시도/요청 1.75).
- 확인: 하류 쪽 지연 p50·p99·p99.9 vs 클라이언트 per-try 값, 타임아웃 비율, 재시도 비율.
- 대처: 오탐률 기준으로 백분위를 올리고(p99.9), 재시도 예산을 건다.

### 9. 독립 가정이 깨질 때

- 과부하·공유 의존(같은 DB, 같은 네트워크 경로)처럼 **모든 복제본이 함께 느린** 상황에서 깨진다.
- 그때 재시도는 다른 복제본도 느리므로 성공률을 거의 올리지 못하고, 하류 부하만 늘려 회복을 늦춘다. 재시도 예산·서킷 브레이커로 상한을 둔다([06](../06-retry-backoff-jitter/2-summary.md), [10](../10-circuit-breaker/2-summary.md)).
