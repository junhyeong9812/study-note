# reliability/11-rate-limiter — 질문

## 질문

1. (왜) 리미터가 없으면 무너지는 두 가지는? 리미터 설계에서 알고리즘보다 먼저 정할 것은?
2. (그림) 고정 창·슬라이딩 로그·슬라이딩 카운터·토큰 버킷·리키 버킷을 각각 한 줄 그림으로 그리고, 무엇을 저장하는지 써라.
3. (예측) 한도 100건/1초에서 t=999ms에 100건, t=1001ms에 100건이 온다. 고정 창과 토큰 버킷(용량 100, 초당 100)은 각각 몇 건을 통과시키나?
4. (예측) t=900ms부터 1ms마다 10건씩 5초 동안 보낸다. "아무 1000ms 구간의 최대 통과 수"를 네 구현(고정 창·로그·카운터·토큰 버킷)에 대해 예측하라. 토큰 버킷 값이 100이 아닌 이유는?
5. (경계) Resilience4j 2.x `RateLimiter`는 어느 계열인가? 기본값 셋은? 서버 입구에 기본값 그대로 쓰면 어떤 문제가 생기나?
6. (예측) 클라이언트 20개가 Redis 카운터 하나로 "GET → 한도 비교 → INCR"로 한도 100을 지킨다. 각 15건씩 총 300건을 보내면 몇 건이 통과하나? "INCR 먼저, 반환값으로 판정"은?
7. (연결) nginx `limit_req`는 어떤 알고리즘인가? `burst`와 `nodelay`는 무엇을 바꾸나? 기본 거절 상태 코드는?
8. (적용) 429 응답에 무엇을 넣어야 하나? 근거 규격은? 남은 한도를 알리는 헤더의 상태는?
9. (장애 진단) 리미터를 Redis로 옮긴 뒤 Redis 장애 때 모든 API가 실패했다. 무엇을 정하지 않았나? Stripe는 어떻게 했나?
10. (장애 진단) 한 회사 사용자 수백 명이 동시에 429를 받는다. 원인과 대처는?
