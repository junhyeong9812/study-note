# reliability/11-rate-limiter — 정답

## 정답

### 1. 무너지는 두 가지와 먼저 정할 것

- **보호**: 한 사용자의 폭주가 공용 용량을 다 써 다른 사용자가 느려진다.
- **공정성**: 무료 요금제가 유료 몫을 먹는다.
- 먼저 정할 것: **제한 키**(사용자·API 키·테넌트·IP)와 **목적**(보호용 스로틀 vs 계약 쿼터). 키가 틀리면 알고리즘이 성실하게 엉뚱한 것을 막는다.

### 2. 다섯 구현

```text
 고정 창        |-- 창0: count --|-- 창1: count=0 --|        저장: (창 번호, count)
 슬라이딩 로그   [t1 t2 ... tn] 지금-1초 이전 버림           저장: 통과 시각 전부(키당 최대 한도만큼)
 슬라이딩 카운터  이전 count × 남은 비율 + 현재 count         저장: count 2개
 토큰 버킷      [●●●○○] 시간이 채우고 요청이 꺼냄             저장: (토큰 수, 마지막 시각)
 리키 버킷      요청 → [줄] → 초당 r개                       저장: (줄 길이, 마지막 시각)
```

### 3. 경계 2ms

(실험 A, JDK 21, 2026-10-01)

```text
  고정 창                   t=999:100  t=1001:100   2ms 사이 합 200
  토큰 버킷(100, 100/s)      t=999:100  t=1001:  0   2ms 사이 합 100
```

- 고정 창 **200**: 1000ms에서 창이 바뀌며 계수기가 0이 됐다.
- 토큰 버킷 **100**: 2ms 동안 충전은 0.2개뿐이다.

### 4. 아무 1초 구간의 최대

(실험 B, 2026-10-01)

```text
  고정 창                   최대 200건 (구간 10~1009ms)
  슬라이딩 로그                최대 100건 (구간 0~999ms)
  슬라이딩 카운터               최대 189건 (구간 891~1890ms)
  토큰 버킷(100, 100/s)      최대 199건 (구간 892~1891ms)
```

- 토큰 버킷이 199인 이유: t=900에 가득 찬 100개를 다 쓰고, 이어지는 1초 동안 충전된 99개를 쓴다. 상한 = **용량 + 충전 속도 × 구간**.
- 카운터는 "이전 창이 고르게 왔다"는 근사라 몰림이 창 끝에 있으면 한도를 넘긴다.

### 5. Resilience4j RateLimiter

(실험 C, Resilience4j 2.4.0, 2026-10-01)

```text
  limitForPeriod=50 limitRefreshPeriod=PT0.0000005S timeoutDuration=PT5S
  생성 후 t=952ms 100건 시도 → 통과 100
  생성 후 t=1051ms 100건 시도 → 통과 100  (약 100ms 사이에 200건)
```

- **주기 재충전 = 고정 창 계열**. 주기 경계를 끼면 2배가 통과한다.
- 기본: `limitForPeriod=50`, `limitRefreshPeriod=500ns`, `timeoutDuration=5s`.
- 문제: 허가가 없으면 최대 5초 **기다린다**. 요청 스레드가 리미터 앞에서 묶인다. 서버 입구에서는 `timeoutDuration=0`으로 바로 거절한다.

### 6. 분산 카운터 경합

(실험 D, Redis 7.4.9, 클라이언트 20 × 15건, 3회, 2026-10-01)

```text
GET-비교-INCR : 통과 105 (한도 100), 카운터 105
GET-비교-INCR : 통과 108 (한도 100), 카운터 108
GET-비교-INCR : 통과 106 (한도 100), 카운터 106
INCR 먼저     : 통과 100 (한도 100), 카운터 300
```

- GET 후 INCR: **100보다 많이**(집필 3회 105~108, 점검 3회 105~110 — 실행마다 다름). 여러 클라이언트가 같은 값을 읽고 모두 통과시켰다.
- INCR 먼저: **정확히 100**. 원자 연산의 반환값으로 판정했다. 계산이 끼는 알고리즘(토큰 버킷)은 Lua 스크립트로 묶는다.

### 7. nginx limit_req

- **리키 버킷**(nginx 문서: "leaky bucket" method).
- `burst`: 속도를 넘는 요청을 몇 개까지 줄 세울지(기본 0 — 넘으면 바로 거절).
- `nodelay`: 줄 선 요청을 속도에 맞춰 지연시키지 않고 바로 처리한다(줄 자리는 속도대로 비워진다).
- 기본 거절 코드: **503**. 429를 원하면 `limit_req_status 429;`.

### 8. 429 응답

- `Retry-After`(RFC 9110 §10.2.3: HTTP-date 또는 초). RFC 6585 §4는 429에 이것을 넣을 수 있다(MAY)고 적는다.
- 왜: 없으면 클라이언트가 즉시 재시도해 리미터 앞에서 폭풍이 난다(06).
- 남은 한도 헤더 `RateLimit-Policy`/`RateLimit`는 IETF **초안**(draft-ietf-httpapi-ratelimit-headers-11)이다. 표준이 아니다.

### 9. 리미터 자체의 고장

- 정하지 않은 것: 리미터가 고장 났을 때 **통과시킬지(fail open) 막을지(fail closed)**.
- Stripe(2017): 리미터 코드 버그나 Redis 장애가 요청에 영향을 주지 않게 모든 층에서 예외를 잡아 **fail open**했다. 리미터를 끌 수 있는 스위치(기능 플래그)와 경보도 둔다.
- 단, 로그인 시도 제한 같은 보안 한도는 fail closed가 맞을 수 있다. 키 종류별로 정한다.

### 10. 회사 하나가 통째로 429

- 원인: 제한 키가 **IP**다. 회사는 NAT 뒤에서 공인 IP 하나를 나눠 쓴다.
- 보이는 형태: 429가 한 IP에 몰리고 그 뒤에 계정이 수백 개.
- 대처: 인증된 요청은 계정·API 키·테넌트로 센다. IP 한도는 미인증 보호용으로 넉넉하게 따로 둔다.
