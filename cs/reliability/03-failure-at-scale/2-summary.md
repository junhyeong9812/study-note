# reliability/03-failure-at-scale — 규모가 바꾸는 실패의 모양: 부분 실패·재시도 증폭·편중·상태 — 정리 (힌트)

## 해결하는 문제

서버 한 대일 때 장애는 "죽었다/살았다"였다. 수백 대·수십 서비스가 되면 그 그림이 틀린다.

- 어딘가는 늘 반쯤 고장 나 있다. "다운"은 없는데 일부 요청이 계속 실패한다.
- 한 곳이 느려지면 재시도가 그곳에 부하를 더 얹는다. 스파이크가 지나가도 회복하지 못한다.
- 서버를 늘려도 한 키·한 DB에 몰린 부하는 그대로다.

이것을 모르면 소규모의 대응(재시작·증설·재시도)이 대규모에서는 장애를 키운다.

쉬운 예: 고속도로 정체다.
- 차 하나가 급정거하면 뒤차들이 줄줄이 브레이크를 밟는다. 사고 차를 치운 뒤에도 정체는 한참 남는다(되먹임).
- 차선을 늘려도 톨게이트 한 칸으로 몰리는 차는 그대로다(편중).

똑같은 구조다.\
실무 예: DB가 과부하로 요청을 처리하지 못하는 사이 프런트엔드·백엔드·JS 클라이언트가 각각 세 번씩 재시도해, DB에는 사용자 동작 하나당 최대 64번의 시도가 쏟아진다(SRE 22장의 예).

기초(네 양상 — 부분 실패 상시화·재시도 증폭·균등 가정 붕괴·상태의 확장 불가, "내 부하에 걸리는 양상만 센다")는 원본 [ops-patterns/failure-at-scale](../../ops-patterns/failure-at-scale/2-summary.md) 「양상 1~4」·「어느 양상이 실제로 걸리는지 세라」에 있다. 이 노트는 네 양상을 SRE 22장·Tail at Scale·준안정 고장 논문으로 다시 세우고, 각 양상을 작은 시뮬레이션으로 보인다.

## 동작·원리

### 1. 네 양상 한 장

```text
 규모가 커진다
   ├─ ① 부분 실패가 상시화        "다운"이 아니라 "늘 몇 %"   → 분포·비율로 본다
   ├─ ② 재시도가 부하를 곱한다     느림 → 재시도 → 더 느림      → 스파이크가 끝나도 안 돌아온다
   ├─ ③ 균등 가정이 깨진다         한 키·한 테넌트·한 시각에 몰림 → 샤드를 늘려도 안 풀린다
   └─ ④ 상태는 늘려도 안 된다      앱을 늘리면 DB·락이 먼저 죽는다 → 설계 변경이 필요
```

### 2. ① 부분 실패와 꼬리 — 팬아웃이 1%를 63%로 만든다

```text
 사용자 요청 ──┬─> 서버 1  (99%는 10ms, 1%는 1초)
              ├─> 서버 2
              ├─> …         모두 답해야 응답 완료 → 가장 느린 하나를 기다린다
              └─> 서버 100
 P(적어도 하나가 1초) = 1 − 0.99¹⁰⁰ ≈ 63%
```

- Dean·Barroso(2013) "The Tail at Scale"의 예(각 서버가 서로 독립으로 느려진다고 본 이상화된 계산이다. 모두 같은 원인으로 함께 느려지면 이 곱셈이 성립하지 않는다): 서버 하나는 100번 중 1번 1초가 걸린다. 요청이 100대에 퍼지면 사용자 요청의 63%가 1초를 넘는다. 1만 번 중 1번만 느린 서버라도 2,000대에 퍼지면 거의 5번 중 1번이 느리다.
- 같은 논문의 실제 Google 서비스 측정: 하위 요청 하나가 끝나는 시간의 p99는 10ms인데, 전부 끝나기까지의 p99는 140ms다. 95%가 끝나기까지의 p99는 70ms였다 — 가장 느린 5%를 기다리는 데 전체 p99의 절반이 들었다(논문 표 1).
### 실험 C: 팬아웃 꼬리 — 공식과 시뮬레이션

(실험, JDK 21 eclipse-temurin, `--cpus=2`, 요청 20만 번, seed 고정, 2026-10-01 — 코드 `scratchpad/rel/01/e03/Scale.java`)

```text
== C. 서버 하나는 1%가 1초 이상. 요청 하나가 N대에 퍼지면 1초 이상 걸리는 요청 비율
 N=   1  서버당 느릴 확률 1.00%  공식 1-(1-p)^N =   1.0%  시뮬레이션 =   1.0%
 N=  10  서버당 느릴 확률 1.00%  공식 1-(1-p)^N =   9.6%  시뮬레이션 =   9.5%
 N= 100  서버당 느릴 확률 1.00%  공식 1-(1-p)^N =  63.4%  시뮬레이션 =  63.5%
 N=2000  서버당 느릴 확률 0.01%  공식 1-(1-p)^N =  18.1%  시뮬레이션 =  18.1%
```

- 관찰: 논문의 63%·"거의 5분의 1"이 그대로 나온다. 하위 서버 하나의 꼬리 확률이 같아도 팬아웃 수가 사용자 체감을 정한다.

- 그래서 규모가 크면 "어제 3건 실패"를 하나씩 쫓는 대신 실패율·p99를 SLO로 본다([02](../02-slo-sli-error-budget/2-summary.md)). 꼬리를 줄이는 기법(hedged request 등)은 [34-tail-latency-and-stragglers](../34-tail-latency-and-stragglers/2-summary.md).

### 3. ② 재시도 증폭과 준안정 고장

SRE 22장(Addressing Cascading Failures)이 그리는 고리다.

```text
   백엔드 과부하 ──> 응답이 늦거나 실패 ──> 클라이언트가 재시도
        ▲                                        │
        └──────── 재시도가 도착률에 더해진다 <─────┘
   + 과부하 상태에서는 실패할 요청에도 자원(파일 디스크립터·메모리·CPU)을 쓴다 → 쓸모 있는 처리량이 준다
```

- SRE 22장의 예: 백엔드 10,000 QPS 한계에서 100 QPS가 실패해 재시도되면 도착이 10,200 QPS가 되고, 재시도가 100 → 200 → 300 QPS로 불어난다. 첫 시도에 성공하는 요청이 점점 줄어든다.
- 여러 층이 각자 재시도하면 곱이 된다. 세 층이 각각 3회 재시도(시도 4번)면 DB에는 사용자 동작 하나당 최대 4³ = 64번이다(SRE 22장).
- *준안정 고장(metastable failure)*: 계기(trigger)가 사라져도 나쁜 상태가 **유지되는** 고장. 유지시키는 효과(sustaining effect)는 대개 작업 증폭(재시도)이나 효율 저하다. 빠져나오려면 재시작이나 부하를 크게 줄이는 강한 조치가 필요하다(Bronson 외, HotOS 2021).
  - 계기가 사라지면 끝나는 과부하(DoS 공격 등)는 준안정 고장이 아니다(같은 논문).
  - 그래서 사고 원인을 "그 스파이크"로 적기 쉽지만, 진짜 원인은 유지 효과(재시도 정책)다.

### 실험 A: 스파이크 5초, 재시도 정책 셋

- 백엔드 용량 1,000/s. 평시 800/s, 10~14초에만 1,200/s.
- 성공 1건 = 용량 1단위, 과부하로 거절 1건 = 0.3단위(거절에도 비용이 든다 — 예시 가정). 거절된 시도는 다음 초에 재시도.
- SRE 22장 각주 110이 독자에게 권하는 "간단한 시뮬레이터"를 작게 만든 것이다. 실제 시스템의 수치가 아니라 모양을 보는 모델이다.

```java
// 핵심 부분 (전체: scratchpad/rel/01/e03/Scale.java)
// s + 0.3(A − s) ≤ C  →  성공 s = (C − 0.3A) / 0.7  (0 ~ min(A, C))
double s = Math.max(0, Math.min(Math.min(A, C), (C - REJECT_COST * A) / (1 - REJECT_COST)));
if (budget && retries > 0.1 * fresh) scale = 0.1 * fresh / retries;   // 재시도 예산: 신규의 10%까지만
```

- 관찰 1: 재시도가 없으면 스파이크가 끝난 15초에 바로 정상이다.
- 관찰 2: 재시도 3회면 스파이크 동안 도착이 1,200 → 3,233으로 불고, 성공은 914 → 43으로 무너졌다. **스파이크가 끝난 15초 이후에도** 15~17초는 성공 0이고, 그 뒤 도착 약 2,930·성공 약 170 근처로 수렴해 39초까지 돌아오지 않는다. 신규 요청은 800인데 용량 1,000을 못 쓴다. 이 모델에서는 준안정 상태다.
- 관찰 3: 재시도를 신규의 10%로 묶으면 스파이크 동안 성공 863을 유지하고 15초에 회복했다. SRE 22장의 "서버 전체 재시도 예산" 권고와 같은 효과다.
- 한계: 이 모델은 거절 비용(0.3)·재시도 간격(1초)·성공 비율 배분을 단순화했다. 실제 회복 여부는 이 값들에 달려 있다. 모양(재시도 + 거절 비용 → 회복 실패)이 요점이다.

   샤드 4개   [██████][████][████][████]

### 실험 B: Zipf 분포 요청을 해시 샤딩

(실험, 같은 환경, 키 10만·요청 100만, Zipf s=1.1 — 예시 분포)

```text
 샤드수  균등이면  가장바쁜샤드  (Zipf)   가장바쁜샤드 (균등 키)
     4    25.00%      32.80%               25.01%
    16     6.25%      17.51%                6.29%
    64     1.56%      14.29%                1.59%
   256     0.39%      13.65%                0.41%
 가장 인기 있는 키 하나의 몫 = 13.49%
```

- 관찰: 키가 고르면 가장 바쁜 샤드 몫이 1/샤드수로 줄어든다(256개 → 0.41%). Zipf면 256개로 늘려도 13.65%에서 멈춘다. 가장 인기 있는 키 하나(13.49%)가 바닥이다. **샤드를 늘려도 한 키는 한 샤드다.**
- 대처는 키를 바꾸는 것이다(키에 버킷 붙이기, 핫 키 전용 경로, 읽기면 캐시·복제). 샤딩 자체는 [database/33-partitioning-and-sharding](../../database/33-partitioning-and-sharding/2-summary.md).

### 5. ④ 상태는 늘려도 안 된다

```text
 앱 ×2 ──> 커넥션 수 ×2 ──> DB max_connections 초과·락 경합 증가 ──> 더 느려짐
 무상태 앱 CPU : 늘리면 듣는다
 DB 쓰기·행 락·중앙 채번·분산 락 : 늘려도 안 듣는다 → 분할·설계 변경
```

- 커넥션 총량 = 인스턴스 수 × 풀 크기. 풀 크기 정하기는 [database/21-connection-pooling](../../database/21-connection-pooling/2-summary.md).
- SRE 22장도 같은 경고를 한다. 정상 상태를 좋게 하려는 변경(재시도, 불건강한 서버에서 부하 옮기기, 불건강한 서버 죽이기, 캐시 추가)이 대규모 장애 확률을 키울 수 있다. 캐시가 처리하던 몫이 크면 캐시를 잃는 순간 백엔드가 그 부하를 못 받는다(22장 각주 111).

## 쓰이는 자료구조·알고리즘

- **되먹임(피드백) 루프 모델** — 도착 = 신규 + 재시도, 성공 = f(도착). 이산 시간 시뮬레이션으로 안정점·준안정점을 본다.
- **재시도 예산(토큰 버킷)** — 성공·신규 요청마다 토큰을 쌓고 재시도할 때 꺼낸다. 비율로 상한을 건다. [06-retry-backoff-jitter](../06-retry-backoff-jitter/2-summary.md)(원본 [ops-patterns/01-retry-backoff](../../ops-patterns/01-retry-backoff/2-summary.md)).
- **해시 분할과 Zipf 분포** — 인기도 순위 r의 빈도가 1/rˢ에 비례. 상위 몇 개 키가 큰 몫을 가진다. 해시는 키를 고르게 흩지만 한 키 안의 부하는 못 쪼갠다.
- **최댓값 분포(order statistic)** — 팬아웃 응답 시간 = N개 하위 응답의 최댓값. 하위 응답이 독립이고 같은 분포일 때 P(max ≤ t) = P(하나 ≤ t)ᴺ.
- **Little's Law** — 시스템 안 평균 요청 수(대기 중 포함) = 평균 도착률 × 평균 체류 시간. 정상 상태의 평균끼리 관계라 스파이크 중 순간값에는 어림으로만 쓴다. 재시도로 도착률이 늘고 느려져 체류 시간도 늘면 동시 처리 수가 곱으로 는다([21-scaling-principles](../21-scaling-principles/2-summary.md)).

## 적용 — 풀어나가는 법

### 1. 내 시스템에 어느 양상이 걸리나 — 순서

1. 요청 경로의 **팬아웃 수**를 센다. 수십 이상이면 ①(꼬리) 대비가 필요하다. p99를 하위 서비스별로 본다.
2. 경로의 **재시도 지점을 전부** 적는다(클라이언트 SDK·게이트웨이·서비스 메시·애플리케이션·DB 드라이버). 곱을 계산한다. 한 층에서만 재시도하도록 정리한다.
3. 상위 키·테넌트의 **몫**을 잰다(상위 1개·10개 키가 전체의 몇 %인가). 그 몫이 샤드 하나의 용량을 넘으면 ③.
4. 증설 전 **총 커넥션·락 대기**를 계산한다. 앞단을 늘릴 때 뒷단이 받는 양을 먼저 본다(④).
5. 걸리지 않는 양상은 만들지 않는다(원본 「세라」 절). 단 ②·④는 작은 규모에서도 흔히 걸린다.

### 2. 재시도를 안전하게 (Java)

```java
/** 재시도 예산: 최근 요청 대비 재시도 비율 상한(예: 10%). 넘으면 재시도하지 않고 바로 실패. */
final class RetryBudget {
    private final double ratio; private final AtomicLong requests = new AtomicLong(), retries = new AtomicLong();
    RetryBudget(double ratio) { this.ratio = ratio; }
    void onRequest() { requests.incrementAndGet(); }
    boolean tryRetry() {
        long r = retries.get();
        if (r + 1 > ratio * requests.get()) return false;     // 예산 초과 → 재시도 금지
        return retries.compareAndSet(r, r + 1) || tryRetry();
    }
    // 실제로는 슬라이딩 윈도(최근 10초 등)로 두 카운터를 감쇠시킨다
}
```

- 재시도는 **멱등한 요청만**, 지수 백오프 + 지터로, 영구 오류·잘못된 요청과 "재시도하지 말라"는 과부하 신호는 재시도하지 않는다(SRE 22장 권고). 4xx를 계열로 묶어 끊지는 않는다 — 408(요청 시간 초과)·429(Retry-After 대기 후)처럼 재시도할 수 있는 코드가 있다(RFC 9110 §15.5.9, RFC 6585 §4).
- 과부하일 때 "과부하"라는 구체적 상태를 돌려줘 위 계층이 재시도하지 않게 한다(SRE 22장). SRE 21장은 더 나눈다: 일부 태스크만 과부하면 다른 태스크로 바로 재시도하고, 다수가 과부하면 재시도하지 않고 "overloaded; don't retry"로 위로 올린다.

### 3. 진단 지표 (PromQL 예)

```promql
# 재시도 비율: 이 값이 오르면서 성공률이 떨어지면 재시도가 증상이 아니라 원인일 수 있다
sum(rate(client_requests_total{attempt!="1"}[1m])) / sum(rate(client_requests_total[1m]))

# 가장 바쁜 샤드 vs 평균 (편중)
max(rate(db_shard_queries_total[5m])) / avg(rate(db_shard_queries_total[5m]))
```

- 메트릭 이름·라벨은 예시다. 재시도 횟수를 `attempt` 라벨로 남기는 계측이 먼저 있어야 한다.

## 장애 시나리오와 대처

### 1. 재시도가 부하를 N배로 → 복구 불가 (⚠ 커리큘럼)

- 현상: DB가 몇 초 느렸을 뿐인데 이후 수십 분간 서비스가 회복되지 않는다. 트래픽은 평소 수준이다.
- 보이는 형태: 백엔드 도착률이 신규 요청의 몇 배. 재시도 비율 그래프가 치솟아 있다. 성공률은 낮은데 CPU는 꽉 찼다(실험 A: 신규 800인데 도착 2,930, 성공 170).
- 원인: 재시도가 유지 효과가 된 준안정 고장. 층마다 재시도하면 곱으로 커진다(4³ = 64).
- 대처: 당장은 부하를 크게 줄인다(클라이언트 재시도 끄기 배포, 진입 제한·로드 셰딩, 일부 트래픽 차단). SRE 22장: 재시도 동작을 고치거나 부하를 크게 줄이거나 요청을 끊어야 한다. 근본은 재시도 예산·한 층 재시도·지터·서킷 브레이커.

### 2. 팬아웃 서비스의 p99만 계속 나쁘다

- 현상: 하위 서비스 대시보드는 모두 정상인데 상위 API p99가 높다.
- 보이는 형태: 하위 서비스 각각의 p99는 낮다. 상위는 하위 N개의 최댓값을 기다린다.
- 원인: 팬아웃 증폭(1 − (1 − p)ᴺ). 실험 C: 1% 느린 서버 100대 → 63.5%.
- 대처: 하위 p99.9를 관리 목표로, 팬아웃 줄이기, hedged request, 부분 결과 허용(Tail at Scale).

### 3. 샤드를 두 배로 늘렸는데 한 샤드만 계속 뜨겁다

- 현상: 리샤딩 뒤에도 같은 샤드(또는 그 키가 옮겨 간 샤드)만 CPU 100%.
- 보이는 형태: 상위 키 몇 개가 전체 쿼리의 큰 몫. 실험 B: 256샤드에서도 가장 바쁜 샤드 13.65%.
- 원인: 한 키의 부하는 해시로 쪼개지지 않는다.
- 대처: 키에 버킷(`id#0..k`)을 붙여 쓰기를 흩고 읽기는 모은다. 읽기 편중이면 캐시·복제본. 큰 테넌트는 전용 셀로.

### 4. 앱을 늘렸더니 더 느려졌다

- 현상: 지연이 높아 오토스케일 → 인스턴스 2배 → 더 나빠짐.
- 보이는 형태: DB 커넥션 수 급증, `too many connections`, 락 대기 증가. 앱 CPU는 낮다.
- 원인: 병목이 상태 자원(DB·락)이다. 앞단을 늘리면 뒷단 경합이 커진다.
- 대처: 증설 전 총 커넥션을 계산, 커넥션 풀 상한·프록시(PgBouncer 등), 오토스케일 상한, 병목 자원의 분할.

### 5. 캐시가 날아가자 백엔드가 같이 죽었다

- 현상: 캐시 클러스터 재시작 직후 DB가 과부하로 쓰러진다.
- 보이는 형태: 캐시 적중률이 0 근처로 떨어진 시각과 DB 부하 급등이 겹친다.
- 원인: 서비스 용량의 상당 부분이 캐시 위에 있었다. 캐시를 잃으면 백엔드가 받을 수 없는 양이 온다(SRE 22장 각주 111).
- 대처: 캐시 없이 받을 수 있는 양을 알고 그 이상은 셰딩한다. 캐시 워밍·점진 재시작. 스탬피드 방어는 [29-cache-stampede](../29-cache-stampede/2-summary.md).

## 핵심 문장

- 규모가 바꾸는 것은 속도가 아니라 실패의 모양이다. 부분 실패가 상시화되면 개별 건이 아니라 비율과 분포를 본다.
- 팬아웃은 꼬리를 키운다. 1% 느린 서버 100대에 퍼지는 요청의 63%가 느리다.
- 재시도는 과부하에 부하를 더하는 되먹임이다. 거절에도 비용이 들면 스파이크가 지나가도 회복하지 못하는 준안정 상태가 된다(실험: 재시도 3회는 39초까지 성공 약 170, 재시도 예산 10%는 15초에 회복).
- 층마다 재시도하면 곱이 된다. 세 층 × 시도 4번 = 64번.
- 한 키의 부하는 샤드를 늘려도 쪼개지지 않는다(실험: 256샤드에서도 13.65%). 상태 자원은 앞단을 늘릴수록 경합이 커진다.
