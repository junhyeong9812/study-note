# reliability/44-runbooks-and-operational-readiness — 정답

## 정답

### 1. 런북 없는 새벽

```text
 경보 → 대시보드 뒤지기 → 아는 사람 찾기 → 깨우기 → 그 사람이 접속·파악 → 완화
        └──────────────── 이 구간이 통째로 TTM에 더해진다 ────────────────┘
```

- SRE 책 1장: 사람이 개입해야 할 때 모범 사례를 미리 적은 플레이북은 즉흥 대응보다 MTTR을 대략 3배 개선한다. 플레이북을 든 숙련된 온콜이 만능 영웅보다 낫다.

### 2. 연결과 네 절

- 경보 규칙의 `annotations.runbook_url` → (수신 채널의 Alertmanager 템플릿이 표시하도록 설정했을 때) 알림 메시지에 링크 → 런북. 기본 Slack 본문 템플릿은 비어 있으므로 실제 알림에서 링크가 보이는지 확인한다.
- 증상: 사용자에게 무엇이 보이나, 심각도. 확인: 무엇을 실행해 어느 가지로 가나. 완화: 먼저 할 되돌릴 수 있는 조치. 에스컬레이션: 안 되면 누구를, 언제, 어떻게.

### 3. 결정 트리

```text
 복제 지연 > 30초
  ├─ pg_stat_replication에 복제본이 보이나? ─ 아니오 → 연결 끊김 절 → DB 온콜
  ├─ 주 서버에 긴 트랜잭션·대량 쓰기? ─ 예 → 쓰기 배치 중지(플래그)
  └─ 완화: 읽기를 주 서버로 → 15분 내 미감소 시 에스컬레이션
```

- 확인 명령은 읽기 전용이어야 한다. 쓰기·재시작은 확인이 끝난 가지의 완화 절에만 둔다.

### 4. 낡은 SQL

(실험, PostgreSQL 17.11)

- `ERROR:  function pg_current_xlog_location() does not exist`
- `ERROR:  column "replay_location" does not exist`
- PostgreSQL 10에서 "xlog"가 들어간 함수·도구는 "wal"로, WAL 관련 함수·뷰의 "location"은 "lsn"으로 이름이 바뀌었다(릴리스 노트). 지금 이름은 `pg_current_wal_lsn()`, `replay_lsn`.

### 5. 일반형 vs 단계형

- Workbook 8장: 팀마다 갈리는 논쟁이다. 최소한 팀이 플레이북의 **최소 구조(필수 칸)** 에 합의하고, 그 밖의 정보가 쌓이는지 지켜보라고 권한다.
- 경보가 울릴 때마다 온콜이 같은 명령 목록을 그대로 실행하는 결정론적 플레이북이면 자동화하라고 권한다.

### 6. 세 점검

| 점검 | 찾는 것 | 언제 |
|---|---|---|
| 경보마다 `runbook_url` | 런북 없는 페이지 경보(실험: `PostgresTooManyConnections`) | 경보 규칙 PR의 CI |
| 필수 절 | 에스컬레이션 없는 런북(실험: `pg-long-tx.md`) | 런북 PR의 CI |
| 확인 명령 실행 | 지금 인프라와 안 맞는 명령(실험: 구 버전 SQL 2건) | 스테이징에서 주기 작업, DB·플랫폼 업그레이드 PR |

### 7. PRR

- 목표(32장): (1) 서비스가 운영 설정·준비 기준을 만족하고 소유자가 SRE와 일할 준비가 됐는지 확인 (2) 운영 신뢰성을 높이고 예상 사고의 수와 심각도를 줄인다.
- 단계: Engagement(SLO 합의·일정) → Analysis(체크리스트로 결함 찾기) → Improvements and Refactoring(우선순위대로 함께 고침) → Training → Onboarding(책임 단계적 이전) → Continuous Improvement.
- 한계: 이미 출시된 서비스에 늦게 하면 고칠 기회가 적고 비용이 크다. 대안: 설계 단계부터 참여(Early Engagement), 공통 프레임워크로 운영 기준을 기본값으로(Frameworks and SRE Platform).

### 8. 결제 기능 PRR 점검표 (예)

| 질문 | 증거 |
|---|---|
| 결제 성공률·지연 SLO가 있나 | SLO 문서, 대시보드 |
| 사용자에게 보이는 결제 실패가 모두 지표·경보로 잡히나 | 경보 규칙(`runbook_url` 포함) |
| PG 호출에 타임아웃·멱등 키가 있나 | 설정·코드 링크 |
| 롤백·킬 스위치를 실제로 해 봤나 | 리허설 기록 |
| PG가 죽으면 어떻게 되나 | 장애 주입 결과(45) |
| 피크의 N배 부하에서 버티나, 한 대 빠져도 되나 | 부하 시험 결과 |
| 온콜이 정해졌고 테스트 호출이 도착하나 | 호출 테스트 기록 |

### 9. 인수인계 누락

- 원인: 밤 교대의 임시 완화(플래그 끄기)와 그 이유가 인수인계되지 않았다. 아침 교대는 그것을 이상 설정으로 보고 되돌렸다.
- 대처: 인수인계 템플릿에 "진행 중인 완화와 되돌릴 조건"을 필수 칸으로. 임시 완화에는 플래그 설명란·티켓 번호·만료일을 남긴다. Workbook 8장 사례처럼 교대 시작에 이전 교대 인수인계를 읽는 것을 규칙으로 한다.
