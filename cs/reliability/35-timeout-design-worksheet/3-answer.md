# reliability/35-timeout-design-worksheet — 정답

## 정답

### 1. 예산표와 네 검사

```text
 게이트웨이 timeout 3.0 s (재시도 없음)
 └ A 데드라인 2.9 s = 3.0 - 전송 여유 0.1
     예약 0.2 (응답·폴백) → 단계 몫 2.7
     ├ B   0.3 × 2 + 0.05 = 0.65
     ├ DB  0.3
     └ PG  1.5 × 1          합 2.45 ≤ 2.7      (수치는 예시)
```

1. 경로 합 ≤ 상위 몫(직렬은 합, 병렬은 최댓값).
2. 게이트웨이 timeout > 서비스 안 최악 시간(3.0 > 2.75).
3. 단계마다 per-try × 시도 + 대기 ≤ 단계 몫.
4. 결과가 모호한 단계(PG)에 멱등 키·상태 조회·대사 경로가 있다.

### 2. 게이트웨이 1초 < 결제 1.5초

(실험, Envoy 1.39.1)

- 사용자: 1.0초에 HTTP 504.
- 결제: 1.5초에 승인 완료 **1건**. 응답은 게이트웨이가 이미 끊어 `Broken pipe`로 버려졌다.
- 사용자는 실패로 알고, 결제는 됐다. 다시 결제하면 이중 결제다.

### 3. per-try 재시도 / 멱등 키

- 키 없음: Envoy가 1초마다 새 시도를 보냈다. 사용자는 3.03초에 504, 결제는 **3건** 승인. 앞 시도가 아직 처리 중일 때 다음 시도가 도착했다.
- 키 있음: 두 번째 시도가 첫 승인을 기다려 재생했다. 1.51초에 200, 승인 **1건**.

### 4. Envoy 타임아웃 넷

- route `timeout`: 하류 요청을 다 받은 뒤부터 상류의 완전한 응답까지(기본 15초).
- `per_try_timeout`: 재시도 시도 하나. 응답이 하류로 나가기 시작하기 전까지만.
- route `idle_timeout`: 스트림 무활동(HCM `stream_idle_timeout` 덮어쓰기). route 값은 기본 미설정이고, 그때는 HCM `stream_idle_timeout`(기본 5분)이 적용된다.
- cluster `connect_timeout`: 상류 연결 수립, 상류 TLS면 핸드셰이크 포함(기본 5초).
- `x-envoy-expected-rq-timeout-ms`는 설정값에서 온다 — per-try가 있으면 per-try, 없으면 라우트 timeout이고(per-try ≥ 전체이거나 헤징을 켜면 전체 값, `suppress_envoy_headers`면 헤더 없음), 재시도 때만 이 Envoy 안에서 흐른 시간만큼 깎는다(1.39.1 소스. 실험에서는 per-try 값 1000이 실렸다). 게이트웨이까지 오며 쓴 시간은 빼지 않는다. 홉마다 이 값을 남은 예산으로 쓰면 예산이 줄지 않는다.

### 5. 데코레이터 순서

(실험, Resilience4j 2.4.0)

- `Retry(TimeLimiter(call))`: 시도마다 1초로 자르고 재시도. 3번째에 성공, 약 2.35초.
- `TimeLimiter(Retry(call))`: 재시도 묶음 **전체**가 1초. 1.0초에 `TimeoutException`.
- 뒤쪽 순서의 부작용: 호출자가 실패를 받은 뒤, 안쪽 Retry가 인터럽트된 1번째 시도를 실패로 보고 2번째 시도를 1104ms에 시작해 끝까지 돌렸다. 아무도 기다리지 않는 재시도다.

### 6. 서킷 브레이커 위치

- `CB(TL(call))`: 호출자가 받은 `TimeoutException`을 그대로 실패로 센다 — 실패 3, 성공 0.
- `TL(CB(call))`: 서킷 브레이커는 하류가 1.5초 뒤 정상 반환한 것만 본다 — 실패 0, **성공 3**. 호출자는 3번 다 타임아웃이었다.
- 느린 호출: 기본 `slowCallDurationThreshold`가 60초라 1.5초는 느린 호출로도 세지 않았다(느린 호출 0). 타임아웃 근처로 낮춰야 한다.

### 7. Spring Boot 기본 순서

- `Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Function ) ) ) ) )`.
- TimeLimiter가 Retry 안쪽이라 시도마다 잘린다(5번 문제 회피).
- CircuitBreaker가 TimeLimiter 바깥이라 타임아웃을 실패로 센다(6번 문제 회피).
- 함수형으로 직접 엮을 때는 이 순서를 테스트로 고정한다.

### 8. "두 번 결제됐다"

- 맞대어 볼 것: 그 주문의 게이트웨이 액세스 로그(504, 응답 플래그 `UT`)와 클러스터 카운터 `upstream_rq_timeout`, 서비스 A의 PG 호출 시작·끝 로그, PG 승인 기록 시각, 게이트웨이 재시도 지표(`upstream_rq_retry`·`upstream_rq_per_try_timeout`).
- 판정
  - 504 시각 < PG 승인 시각이면 검사 2 위반(게이트웨이가 먼저 끊음).
  - 같은 요청이 1초 간격으로 여러 번 도착했으면 비멱등 라우트의 게이트웨이 재시도.
- 재발 방지: 게이트웨이 timeout > 서비스 최악, 비멱등 라우트의 게이트웨이 재시도 끄기, 결제 요청 멱등 키(재결제가 같은 키면 재생), 504 뒤 "확인 중" 조회 흐름, 대사.

### 9. PG 단계 칸

- per-try: PG 지연 p99.x 근처(예시 1.5초). HTTP 클라이언트에도 같은 값을 건다.
- 시도: 1(자동 재시도 없음). 재시도는 멱등 키가 보장될 때만, 그리고 상태 조회 뒤에.
- 멱등: 멱등 키를 PG에 함께 보낸다.
- 모호할 때: 타임아웃 = "모름"으로 기록 → 키로 상태 조회 → 그래도 모르면 일 단위 대사.
- 게이트웨이에서 재시도하지 않는 이유: 게이트웨이는 결제가 진행 중인지 모른다. per-try가 끝날 때마다 새 시도를 보내 승인 여러 건을 만든다(실험: 3건). 키를 아는 서비스 A가 판단해야 한다.
