# reliability/19-performance-measurement — 정답

## 정답

### 1. 평균이 놓치는 것

- 평균은 "합 ÷ 건수"라 드문 긴 지연이 희석된다. 분포의 꼬리, 즉 가장 느린 1%·0.1%의 사용자가 겪는 시간이 사라진다.
- 실험 A: 평균 1.8ms인데 max는 999ms였다.
- 함께 볼 것: p50·p90·p99·p99.9·max, 처리량, 오류율. 성공과 실패는 나눠서 잰다(빠른 실패가 분포를 좋아 보이게 한다).

### 2. 분위수의 평균

- 분위수는 평균 낼 수 있는 값이 아니다. 255ms는 어느 요청 집합의 99% 지점도 아니다. 실제 전체 p99는 두 서버의 요청 수 비율과 분포 모양에 따라 달라진다.
- 필요한 것: 원 샘플 전체, 또는 **같은 버킷 경계**의 히스토그램 카운트. 합친 뒤 분위수를 다시 계산한다.
- Prometheus라면 summary의 `quantile`은 집계할 수 없고, histogram 버킷을 `sum by (le)`로 합친 뒤 `histogram_quantile`을 쓴다.

### 3. coordinated omission 그림

```text
 계획:  r1 r2 r3 ... (5ms마다)               ... r201 r202
 실제:  r1 ────────── 서버 1초 멈춤 ──────────> 응답, 그다음 r2 r3 ...
 기록:  r1 = 약 1초 (한 건)
 빠짐:  멈춤 동안 보냈어야 할 약 200건 — 각각 0~1초를 기다렸을 요청들
```

- 부하 생성기가 응답을 기다리는 동안 요청을 보내지 않아, 느린 구간의 표본이 거의 남지 않는다.

### 4. 예측과 실험

(실험, Temurin 21.0.12 `--cpus=2`, HdrHistogram 2.2.2)

| 측정 | p50 | p99 | max |
|---|---|---|---|
| A closed, 보낸 시각부터 | 1.2ms | 1.5ms | 999.3ms |
| B closed, 계획 시각부터 | 1.3ms | 939.0ms | 999.3ms |
| C open | 1.3ms | 935.3ms | 997.2ms |

- 수치는 실행마다 조금 다르다(재실행 포함 A p99 1.4~1.8ms, B·C p99 935~942ms). 경향은 같다.
- A에서 1초 멈춤은 max 한 건으로만 보인다. p99 1.5ms는 "멈춤이 없었다"고 말한다.
- B·C에서는 멈춤 동안 계획됐던 요청들의 대기가 들어가 p99가 약 0.94초가 된다.
- p50은 셋이 같다. 꼬리만 달라진다.

### 5. open vs closed

- closed(사용자 수 고정): 응답을 받아야 다음 요청. 서버가 느려지면 **도착률도 떨어진다**. 실험에서 멈춤 1초 동안 보낸 요청이 1건이었다.
- open(도착률 고정): 완료와 무관하게 계획대로 도착한다. 서버가 느려지면 **큐가 쌓인다**. 실험에서 멈춤 1초 동안 200건이 도착했다.
- 맞는 상황: 인터넷 사용자 트래픽처럼 서버 상태와 무관하게 오는 요청은 open. 고정된 수의 워커·연결이 돌아가며 쓰는 내부 소비자처럼 정말 "N명이 순서대로" 쓰는 시스템은 closed.

### 6. 교정 두 가지

1. 계획 시각부터 재기: 처리율 계획(`t0 + i×간격`)을 두고 "보냈어야 할 시각"부터 응답까지 잰다(wrk2).
   - k6 arrival-rate는 다른 길이다. 반복 시작을 계획대로 해 open 모델로 보낸다. 지연은 실제로 보낸 때부터 잰다. VU가 모자라 시작하지 못한 반복은 지연 기록이 아니라 `dropped_iterations`로만 남으므로, 그 값이 0인지 확인한다.
2. 사후 보정: HdrHistogram `recordValueWithExpectedInterval(값, 예상 간격)`. 값이 예상 간격보다 크면, 간격만큼씩 줄어드는 값들을 빠진 표본으로 채운다.

- 사후 보정에는 **예상 간격**(여기선 5ms)을 알아야 한다.
- 1600 → 1798: 999ms짜리 한 건이 기록될 때 999 − 5, 999 − 10, … 처럼 5ms보다 큰 값들이 약 198개 추가됐다. 멈춤 동안 빠졌던 요청 수와 거의 같다.

### 7. 세 가지 근사

| | 방식 | 합치기 |
|---|---|---|
| HdrHistogram | 로그 간격 버킷, 유효 숫자 자릿수로 상대 오차 고정(3자리면 0.1% 이내) | 같은 설정끼리 더함 |
| t-digest | 중심점 묶음, 양 끝에 촘촘 → 꼬리 정확 | 병합 가능 |
| Prometheus classic histogram | 사람이 정한 `le` 경계의 누적 카운트, 버킷 안 선형 보간 | 같은 경계면 `sum by (le)` |

- 합칠 수 있어야 인스턴스 여러 대·시간 창 여러 개를 모아 **서비스 전체 분위수**를 낼 수 있다. 미리 계산한 분위수(summary)는 이것이 안 된다.

### 8. 테스트 p99 2ms, 운영 p99 수백 ms

- 확인할 것
  - 부하 모델이 closed인가(VU 고정)? 지연을 "보낸 시각부터" 쟀나?
  - 테스트 중 처리량 그래프가 GC·멈춤 순간에 떨어졌나? 떨어졌다면 그 순간 요청을 안 보낸 것이다.
  - p99와 max의 차이가 비정상적으로 큰가? 측정 기간이 꼬리를 볼 만큼 길었나?
- 바꿀 것: open 모델(k6 `constant-arrival-rate`, VU를 넉넉히)이나 계획 시각 기준 측정(wrk2 `-R`). 목표 처리율이 실제로 유지됐는지(k6면 `dropped_iterations = 0`) 함께 기록한다. 운영과 같은 GC 설정·힙 크기·데이터 크기로 잰다.

### 9. 배포 전후 비교

- 측정 전에 적을 것: 무엇을 재나(클라이언트 end-to-end / 서버 처리), 부하 모델과 이유, 환경(코어·인스턴스·데이터 크기·캐시 상태·버전), 워밍업 구간, 지표(p50·p99·p99.9·max·처리량·오류율), 기간.
- "빨라졌다" 전에: 같은 조건으로 여러 번 돌려 실행 간 범위를 본다. 차이가 그 범위보다 큰지 확인한다. 한 번에 한 가지만 바꿨는지 확인한다(→ 20). 꼬리 분위수도 같은 방향으로 움직였는지 본다.
