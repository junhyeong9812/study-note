# reliability/39-async-io-gains-and-limits — 정답

## 정답

### 1. 늘려 주는 것과 못 늘려 주는 것

- X = L / W(Little's Law).
- 늘려 주는 것: L(동시에 붙잡을 수 있는 요청 수). 블로킹 + 스레드 풀이면 실행 중인 L ≤ 스레드 수다(큐에서 기다리는 건은 따로). 가상 스레드·논블로킹은 I/O를 기다리는 동안 OS 스레드를 쓰지 않아 L이 스레드 수에 묶이지 않는다. 그래서 처리량 X가 는다.
- 못 늘려 주는 것: W(한 건이 실행되는 서비스 시간)는 그대로다. 하류가 100ms면 100ms다. 큐 대기를 포함한 지연은 대기가 사라지면 줄 수 있고(실험 2의 제출~완료), 경합이 생기면 늘 수 있다(작업 본문). JEP 444: 가상 스레드는 속도(낮은 지연)가 아니라 규모(높은 처리량)를 위한 것이다.
- CPU 바운드면 L을 늘려도 코어 수가 상한이라 X도 늘지 않는다.

### 2. I/O 대기 1만 건 (실험)

(실험, JDK 21 temurin, `--cpus=2`, 집필 3회 + 사실 점검 1회)

| | 처리량 | 작업 본문 p50 | 제출~완료 p50 |
|---|---|---|---|
| 플랫폼 풀 200 | 1,962 건/s | 100ms | 2,515ms |
| 가상 스레드 | 15,944 건/s(4회 13,375~20,878) | 221ms(4회 105~221) | 340ms |

- 처리량 약 8배(4회 범위 약 7~11배). 풀 200의 상한은 200 / 0.1초 = 2,000 건/s다.
- 작업 본문은 줄지 않고 오히려 늘었다. 2코어에서 수천 개 가상 스레드를 만들고 깨우느라 운반 스레드에 다시 올라탈 차례를 기다린 시간이 붙었다(해석).
- 제출~완료가 준 것은 줄 서서 기다린 시간이 사라졌기 때문이다.

### 3. CPU 계산 16건

- 둘 다 약 1.1~1.2초(실험 1.20초 vs 1.16초, 4회 1.05~1.22초).
- 16 × 150ms / 코어 2 ≈ 1.2초. 코어가 상한이라 스레드 종류와 무관하다.

### 4. 하류 풀 10개 (실험)

- 플랫폼 풀 50: 성공 2,000 / 실패 0. 동시성이 50이라 커넥션 대기가 짧다. 대신 나머지 요청이 실행기 큐에서 기다려 p99가 약 4초였다.
- 가상 스레드: 성공 160 / 커넥션 대기 초과 1,840(4회 1,840~1,850). 2,000건이 한꺼번에 커넥션을 기다렸다.
- 대략치: 300ms 동안 커넥션 10개가 20ms 쿼리를 15번씩 → 약 150건만 한도 안에 커넥션을 얻는다.
- 정리: 대기 장소가 실행기 큐에서 DB 풀 앞으로 옮겨 갔다.

### 5. 고정

- 고정: 가상 스레드가 운반 스레드에서 내려오지 못하는 상태. JDK 21에서는 `synchronized` 블록·메서드 안, 그리고 네이티브 메서드·외부 함수 안에서 생긴다.
- 고정된 채 블로킹하면 운반 스레드와 OS 스레드도 막힌다. 스케줄러는 이를 보상하지 **않는다**(병렬도를 늘리지 않음).
- 파일 시스템 연산·`Object.wait()`처럼 OS·JDK 제약으로 운반 스레드를 붙잡는 블로킹은 스케줄러가 병렬도를 **임시로 늘려** 보상한다(JEP 444).

### 6. synchronized vs ReentrantLock

| | JDK 21.0.12 | JDK 25.0.4.1 |
|---|---|---|
| synchronized | 2.51초(trace 실행 2.56초) | 0.11초 |
| ReentrantLock | 0.05초 | 0.06초 |

- JDK 21: 락은 서로 달라 경합이 없다. 차이는 고정뿐이다. 고정된 100개가 운반 스레드 2개를 50ms씩 붙잡아 100 × 50ms / 2 = 2.5초.
- JDK 25: JEP 491(JDK 24)이 `synchronized` 안의 블로킹에서 가상 스레드를 내려놓게 바꿨다.

### 7. 팬아웃 메모리

- 한도 200: 6,000 × 0.2초 / 200 = 6초(실험 6.26초).
- 한도 없음: 실험(`--memory=1g` 컨테이너 → SerialGC)에서 최대 동시 3,706, 힙 최대 315MB(한도 200은 39MB). 메모리 ≈ 동시 수 × 64KB에 아직 회수 안 된 쓰레기가 더해진다.
- 같은 코드를 메모리 제한 없이 돌리면 JVM이 G1을 골라 측정값이 쓰레기에 묻힌다(415 / 309 / 344MB — 경향 없음). 살아 있는 메모리는 GC 직후 힙으로 본다.
- 작업 2만 개·`-Xmx256m`·한도 없음은 100초 안에 끝나지 않아 중단했다(원인은 확인 못 함).

### 8. 동시 접근 제한

- 세마포어(또는 유계 큐)로 제한한다. 가상 스레드는 작업마다 새로 만든다.

```java
private final Semaphore permits = new Semaphore(20);
String call() throws Exception {
    if (!permits.tryAcquire(200, TimeUnit.MILLISECONDS)) throw new RejectedExecutionException("동시 한도 초과");
    try { return downstream.get(); } finally { permits.release(); }
}
```

### 9. WebFlux 전환 후 느려짐

- 덤프에서 볼 것: 이벤트 루프 스레드(예: `reactor-http-nio-*`·`reactor-http-epoll-*`)가 JDBC 소켓 읽기 같은 블로킹 호출에서 멈춰 있는지.
- 원인: 루프 스레드는 몇 개뿐이다(Reactor Netty 기본 max(코어 수, 4)). 블로킹 호출 하나가 루프 하나를 통째로 막는다. 동시성이 스레드 풀 시절보다 작아졌다.
- 고치는 법: 블로킹 호출을 별도 유계 스케줄러(Reactor `boundedElastic`)로 옮기거나, 논블로킹 드라이버(R2DBC)로 바꾸거나, 가상 스레드 + 동기 코드로 돌아간다.

### 10. 가상 스레드 전환 후 커넥션 타임아웃

- 원인: 동시 요청 수가 스레드 풀 크기에서 사실상 무제한으로 커졌다. DB 풀(HikariCP 기본 10)은 그대로라 대기 장소가 풀 앞으로 옮겨 갔다. `connectionTimeout`(기본 30,000ms)을 넘긴 요청이 이 오류를 받는다.
- 대처: 입구에서 하류별 세마포어로 동시성을 제한하고 넘치면 빠르게 거절한다. 요청 타임아웃을 둔다.
- 풀부터 키우지 않는 이유: DB가 그 동시성을 감당하지 못하면 병목이 DB CPU·락으로 다시 옮겨 갈 뿐이다. 인스턴스 수 × 풀 크기가 DB 한도를 넘을 수도 있다.
