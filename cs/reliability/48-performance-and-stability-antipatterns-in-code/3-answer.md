# reliability/48-performance-and-stability-antipatterns-in-code — 정답

## 정답

### 1. 왜 운영에서 터지나

- 코드가 틀려서가 아니라 **규모**가 바뀌어서다. 데이터 양, 동시 요청 수, 인스턴스 수, 통합 지점의 지연이 테스트 환경과 다르다.
- 질문 하나: "이 코드가 100배 데이터·100배 동시성·느려진 의존성에서 어떻게 되나?"

### 2. 클라이언트 재사용 실험

(실험, JDK 21, 집필 2회 + 점검 2회)

| | 클라이언트 쪽 TCP | 스레드 |
|---|---|---|
| (a) 공유 | ESTABLISHED 1 | 15 |
| (b) 요청마다 new, 안 닫음 | ESTABLISHED 160~200 + TIME_WAIT 19~140 | 513~900 |
| (c) 요청마다 new + close | TIME_WAIT 300 | 12 |

- (b)는 버려진 클라이언트의 연결·스레드가 GC 전까지 남는다. 수치는 GC 시점에 따라 다르다.
- (c)는 연결을 먼저 닫은 쪽이 클라이언트라 TIME_WAIT가 클라이언트에 남는다. 300번 닫았으니 300개.
- JDK `HttpClient` 문서: 클라이언트는 대개 자기 풀을 갖고, 풀은 대개 공유하지 않는다. 연산마다 새로 만들면 보통 연결을 재사용하지 못한다.

### 3. `Cannot assign requested address`

- 세어 볼 것: `ss -tan state time-wait | wc -l`, 원격 주소별 연결 수, `ip_local_port_range`, 프로세스 스레드 수 추이.
- 좁히기: TIME_WAIT가 특정 원격 주소에 몰려 있고 수만이면 임시 포트 고갈이다. connect(2): 임시 포트 범위가 모두 사용 중이면 `EADDRNOTAVAIL`. 스레드 수까지 오르면 클라이언트를 요청마다 만든다는 신호다.
- 고치기: 클라이언트를 애플리케이션에 하나(빈·싱글턴)로 두고 연결을 재사용한다. 상대가 keep-alive를 끊는지 확인한다.

### 4. Chatty I/O ↔ Extraneous Fetching

- 경로: 왕복을 줄이려고 "필요할지 모르는 것까지 한 번에" 가져온다. Azure 문서는 Extraneous Fetching을 Chatty I/O의 과잉 보상으로 적는다.
- 균형점: **화면·연산 하나가 실제로 쓰는 데이터**를 한두 번의 왕복으로 가져온다. 필요한 컬럼만, 목록은 페이지로, 연관은 `IN (...)`·배치로 모은다.

### 5. 스레드 4개 + 느린 외부 호출

(실험, JDK 21)

- `plain`: 헬스체크 3번 모두 **타임아웃**(약 1000ms). 스레드 4개가 5초씩 묶였고 `/health`는 큐에서 기다렸다.
- `timeout`(300ms): 첫 헬스체크 **640~765ms**(실행마다 다르다). 주문 8건이 스레드 4개로 300ms씩 두 차례 줄을 섰고, 헬스체크가 그 뒤에 섰다. 첫 연결·클래스 로딩으로 주문 처리 시작이 늦어 단순 계산보다 길다. 다음 두 번은 3~6ms.
- `bulkhead`: 헬스체크 124~155ms(첫 연결), 그다음 5~9ms. 주문과 상관없이 응답했다.

### 6. 타임아웃 vs 격벽

- 타임아웃: 스레드가 묶이는 **시간**을 줄인다. 줄 서기는 없애지 못한다(실험 `timeout`의 640~765ms).
- 격벽: 묶임이 다른 기능으로 **번지는 것**을 막는다. 묶인 쪽(주문)은 여전히 느리고 실패한다(실험 `bulkhead`).
- 그래서 둘을 함께 쓴다. 통합 지점마다 타임아웃 + 동시 호출 상한(세마포어·별도 풀) + 헬스체크 분리.

### 7. 특정 고객만 OOM

- 의심: Unbounded Result Sets. 그 고객만 데이터가 많다.
- 볼 것: 힙 덤프에서 거대한 컬렉션 하나, 직전의 쿼리(`LIMIT` 없음), GC 로그의 연속 Full GC.
- 상한은 **받는 쪽(호출자)** 이 정한다. 상대가 몇 행을 줄지 믿지 않는다. 페이지·`LIMIT`·최대 건수 검사, 대량은 스트리밍·배치 커서로.

### 8. Dogpile vs Self-Denial

- Dogpile: 많은 서버·클라이언트가 같은 순간에 같은 일을 한다(전 서버 크론 00:00, 같은 TTL 캐시 만료, 장애 뒤 동시 재접속). 흩는 법: 시작 시각 지터, 리더 한 대만 실행, TTL 무작위화.
- Self-Denial: 우리 쪽 결정(쿠폰 공지·대량 푸시)이 자기 용량을 넘는 트래픽을 만든다. 흩는 법: 발송을 나눠 보내기(속도 제한), 운영과 일정 공유, 사전 증설, 대기열·우선순위 셰딩.
- 두 항목 모두 Nygard 2판 4장 목록에 있다. 원문 정의 문장은 이 노트에서 확인하지 못했다 `[?]`.
