# reliability/46-disaster-recovery — 정답

## 정답

### 1. HA와 DR

1. 범위: HA는 서버·디스크·AZ 같은 부품 하나의 고장을 버틴다. 리전 전체가 안 되면 부품 이중화로는 못 버틴다.
2. 손상: 복제는 잘못된 `DELETE`·버그 데이터도 그대로 옮긴다. 시점 백업이 있어야 사고 직전으로 돌아간다.

- AWS 백서 "High availability is not disaster recovery": 가용성은 작업의 구성 요소를, DR은 작업 전체의 별도 사본을 다룬다. 계속 복제하는 저장소는 지우거나 망가뜨린 것도 복제하므로 DR에는 시점 백업도 필요하다.

### 2. RPO·RTO 시간축

```text
 ───●(마지막 복구 지점)──────────✕(재해)──────────────────●(서비스 복구)──▶
     |<──── 잃는 데이터 ≤ RPO ───>|<──── 서비스 없음 ≤ RTO ───>|
```

- RPO: 마지막 복구 지점 이후 허용하는 최대 시간(잃어도 되는 데이터). RTO: 중단부터 복구까지 허용하는 최대 지연.
- "목표"라는 뜻: 조직이 정한 허용치다. 실제로 얼마를 잃고 얼마나 걸렸는지는 훈련이나 사고 때 재는 실측이고, 목표와 다를 수 있다.

### 3. 네 전략

| 전략 | RPO/RTO(AWS 그림 6) | 상시 가동 |
|---|---|---|
| 백업·복원 | 시간 | 백업만. 자원은 사고 뒤 생성 |
| 파일럿 라이트 | 수십 분 | 데이터 복제. 앱은 꺼 둠 |
| 웜 스탠바이 | 분 | 작은 규모의 전체 스택 |
| 다중 사이트 액티브/액티브 | 실시간에 가까움 | 전 리전이 트래픽 처리 |

- "near zero"인 이유: 리전 사이 복제가 비동기면 페일오버 순간 아직 건너가지 못한 쓰기는 잃는다. 동기로 하면 리전 간 왕복 지연이 쓰기마다 붙는다.

### 4. 비동기 + 링크 단절

(실험, PostgreSQL 17.11 2대 + JDK 21.0.12)

```text
FINAL acked=1220
pg2 rows=580 max(id)=580 마지막 행 커밋 시각=06:15:22.889(UTC)
```

- 예측: 링크가 끊겨 있던 약 3초 동안 커밋된 전부를 잃는다(RPO ≈ 단절 시간).
- 실측: 성공 1,220건 중 580건만 복제본에 있다 → 640건 손실. 복제본의 마지막 행(22.889)과 클라이언트의 마지막 성공(26.110 직전) 사이 ≈ 3.2초. 반복 실행에서는 1,612·872·921건, 점검 재실행에서는 1,572·985건(처리량 차이 — 건수는 실행마다 다르지만 매번 수백~천여 건).
- 링크가 멀쩡할 때 주만 죽이면: 3회 모두 0건. 같은 호스트에서 지연이 아주 작았기 때문이다. 평소 측정만으로는 RPO 위험이 보이지 않는다.

### 5. 동기 + 링크 단절

```text
06:15:54.154 acked=477 (+21)
06:15:54.655 acked=477 (+0)
06:15:55.155 acked=477 (+0)
06:15:56.658 acked=477 (+0)
FINAL acked=477
pg2 rows=478 max(id)=478
```

- 링크가 끊기자 커밋이 대기 서버 확인을 기다리며 멈췄다(`acked` 정체). 쓰기 가용성을 내준 것이다.
- 성공 응답을 받은 커밋 477건은 복제본에 다 있다 → 잃은 성공 커밋 0.
- PostgreSQL 문서 26.2.8.4: 동기 대기 서버 하나가 죽으면 커밋이 끝나지 않을 수 있다. 그래서 후보를 여럿 둔다.

### 6. 478번 — 결과를 모르는 커밋

- 클라이언트는 478번에 대해 성공을 받지 못하고 연결 오류로 끝났다. 그런데 그 행은 새 주(승격된 복제본)에 있다.
- 뜻: "실패 응답 = 저장 안 됨"이 성립하지 않는다. 연결이 커밋 응답 전에 끊기면 결과는 "모름"이다.
- 매번 생기지는 않는다. 점검 재실행에서는 acked 705 = 복제본 705행이었다. 링크가 끊긴 순간 마지막 커밋의 WAL이 이미 건너갔느냐에 달린 경합이다.
- 대비: 쓰기에 멱등 키를 붙인다. 재시도 전에 키로 존재를 확인하거나, 같은 키의 두 번째 쓰기를 저장소가 무시하게 한다(13-idempotency).

### 7. RTO 1시간 안에 들어가는 것

- 백서 "Detection": 탐지 → 통보 → 에스컬레이션 → 상황 평가 → DR 선언 → 복구. 전환 작업 시간만이 아니다.
- 제어 플레인의 위험: 백서는 페일오버에 데이터 플레인 작업만 쓰라고 한다. 자원 생성·설정 API(제어 플레인)는 가용성 목표가 더 낮아, 재해 때 바로 그것이 안 될 수 있다. 미리 구성한 상태 검사·라우팅 제어(Route 53 ARC)로 전환되는 절차가 안전하다. 레코드 가중치를 API로 바꾸는 것은 제어 플레인 작업이다(AWS "Fault Isolation Boundaries" 부록 B).

### 8. DR 리전 앱이 안 뜸

- 흔한 원인: DR 리전에 없는 이미지·비밀·인증서, 서비스 할당량 부족으로 확장 실패, 앱 설정이 주 리전 DB를 가리킴, 대기 저장소의 용량·능력이 지난 훈련 이후 부족해짐(백서 "Testing disaster recovery").
- 예방: 정기 실전 전환 훈련, DR 리전 설정 드리프트 자동 검사, 복구 경로를 적게 두고 자주 실행(백서: "the only error recovery that works is the path you test frequently").

### 9. 지워진 테이블과 DR 전환

- 해결되지 않는다. 복제본에서도 지워져 있다(복제가 손상을 옮긴다).
- 필요한 것: 다른 장애 도메인의 시점 백업 + WAL 아카이브로 사고 직전 시점까지 복구(PITR).
- database/20 연결: 기준 백업 + WAL 사슬, 사고 지점 찾기(WAL·binlog 읽기), 복원 검증을 정기 작업으로 만드는 것. SRE 26장: 사람들이 원하는 것은 백업이 아니라 복원이다.

### 10. 지연 0 vs 행 없음

- `pg_stat_replication`은 붙어 있는 복제본만 보여 준다. 복제본 연결이 끊긴 것이 감지되면 행이 사라진다(감지 안 된 네트워크 단절은 `wal_sender_timeout` 기본 60초까지 행이 남을 수 있다 — `reply_time`도 본다).
- 지연 지표를 "행마다 최대값"으로만 만들면, 행이 없을 때 값이 비거나 0으로 보여 **가장 위험한 순간(복제본 없음 = 주가 죽으면 마지막 복구 가능 지점(백업 + 아카이브된 WAL) 이후를 잃음)이 가장 안전해 보인다.**
- 그래서 붙어 있는 복제본 수를 따로 세고 0이면 경보한다(정리 노트의 `seen == 0`). 조용한 실패를 막는 장치다.
