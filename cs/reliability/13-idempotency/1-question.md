# reliability/13-idempotency — 질문

## 질문

1. (왜) 클라이언트가 타임아웃 뒤 결제를 재시도했다. 재시도가 중복 결제가 되는 조건과, 멱등 키가 그것을 막는 방식을 그림으로 설명하라.
2. (경계) "HTTP 메서드의 멱등", "API의 멱등 키 약속", "키 저장소 구현"은 각각 무엇을 보장하고 무엇을 보장하지 않나? 멱등 키의 보장이 성립하는 범위(시간·공간) 두 가지는?
3. (예측) 같은 키로 20개 요청을 동시에 보낸다. "SELECT로 키 확인 → 없으면 처리 → 키 INSERT"와 "유일 제약에 `INSERT … ON CONFLICT DO NOTHING`으로 선점"에서 결제 건수는 각각? 실험 수치로 답하라.
4. (경계) 선점을 먼저 커밋하는 방식(claim)과 키·처리·완료를 한 트랜잭션에 넣는 방식(onetx)은 진 쪽 요청에 무엇을 돌려주나? 각각 언제 고르나?
5. (예측) 키를 선점하고 외부 PG를 호출한 뒤, 완료를 기록하기 전에 프로세스가 죽었다. 1초 뒤 재선점 규칙으로 재시도하면 외부 결제는 몇 건이 되나? 외부에도 같은 키를 넘기면?
6. (적용) 같은 키로 금액이 다른 요청이 왔다. 무엇으로 알아채고 무엇을 돌려줘야 하나? 판정 순서(지문과 상태)가 바뀌면 어떤 사고가 나나?
7. (연결) Stripe는 500 응답도 키에 저장해 재생한다. 원본(ops-patterns/06)은 FAILED면 재선점을 허용한다. 두 정책이 각각 지키는 것과 잃는 것은?
8. (장애 진단) 서버 재시작 직후 몇몇 고객이 PG에서 두 번 청구됐는데 우리 DB에는 결제가 한 건뿐이다. 어떤 키 상태를 찾아보고, 무엇으로 막나?
9. (장애 진단) 오프라인 모바일 앱이 하루 뒤 보낸 재시도가 새 주문을 만들었다. 원인과 대처 두 가지는?
