# reliability/13-idempotency — 정답

## 정답

### 1. 재시도가 중복 결제가 되는 조건

```text
 키 없음:  요청 → 실행 ✔ → 응답 유실 → 재시도 → 또 실행 ✔         2건
 키 있음:  요청(K) → 실행 ✔, K=completed + 응답 저장 → 응답 유실
           재시도(K) → K 있음 → 실행 안 함, 저장된 응답 재생        1건
```

- 조건: 첫 요청이 **실제로 실행됐는데** 응답만 사라졌고, 서버가 그 사실을 기억하지 못한다.
- 멱등 키는 클라이언트가 요청 단위로 붙이는 번호다. 서버는 키로 "이미 했다"와 "그때의 응답"을 기억해 재시도에 처리 대신 재생을 준다.

### 2. 세 층과 보장 범위

| 층 | 보장 | 보장하지 않음 |
|---|---|---|
| HTTP 메서드(RFC 9110) | GET·PUT·DELETE 등은 정의상 같은 요청 여러 번 = 한 번의 의도한 효과 | POST는 아님. 구현이 정의를 어기면 깨진다 |
| API 멱등 키 약속 | 같은 키 → 같은 결과 재생(POST에도) | 구현 없이는 말뿐 |
| 키 저장소 구현 | 유일 제약·지문·상태로 실제로 중복을 막음 | 자기 DB 밖(외부 호출)의 중복 |

- 시간 범위: 키가 저장소에 살아 있는 동안(Stripe는 24시간 이상 지나면 지울 수 있다).
- 공간 범위: 같은 범위(사용자·계정) 안에서. 저장소 키는 `(user_id, idem_key)`.

### 3. 동시 20요청

(실험, PostgreSQL 17.11 + JDK 21, 5라운드)

| 방식 | 결제 행 | 라운드당 |
|---|---|---|
| 확인 후 기록(naive) | 17건(5회 실행 범위 9~17건) | 1.8~3.4 |
| 유일 제약 선점(claim) | 5건 | 1.0 |
| 한 트랜잭션(onetx) | 5건 | 1.0 |

- naive는 확인과 기록 사이(처리 20ms)에 들어온 요청이 모두 "처음"이라고 판단한다. 유일 제약은 검사와 기록을 한 연산으로 만든다.

### 4. claim vs onetx의 진 쪽

- claim: 선점이 먼저 커밋되니 진 쪽은 대개 곧바로 기존 행을 본다(선점 INSERT가 아직 커밋 전이면 그 짧은 순간만 유일 인덱스에서 기다린다 — PostgreSQL 17 문서 「Index Uniqueness Checks」). 처리 중이면 `409`(실험: 22건, 실행마다 6~57건), 끝났으면 재생.
- onetx: 진 쪽의 `INSERT`가 유일 인덱스에서 이긴 쪽 커밋을 **기다린다**. 커밋 뒤 0행을 받고 재생한다(실험: 재생 95, 409 0).
- 고르는 기준: 처리가 로컬 DB만 바꾸고 짧으면 onetx(크래시 시 전부 롤백되어 깔끔하다). 외부 호출이 있거나 처리가 길면 claim(진 쪽이 스레드·연결을 잡고 기다리지 않게 즉시 409).

### 5. 외부 호출 뒤 크래시

(실험 E)

- 외부에 키를 안 넘기면 **2건**이다. 키는 in_progress로 남고, 재선점한 재시도가 외부를 다시 불렀다.
- 외부에도 같은 키를 넘기면 **1건**이다. 외부가 두 번째 호출을 중복으로 무시했다.
- 이 틈(외부 호출과 완료 기록 사이)은 PG 승인처럼 2단계 커밋에 참여하지 않는 외부 호출이면 DB 트랜잭션으로 없앨 수 없다. 외부 키 전달, 복구 지점, 재선점 전 외부 조회(대사)로 줄인다.

### 6. 같은 키, 다른 금액

- 지문(금액·통화·대상을 정규화한 해시)을 키와 함께 저장하고, 기존 행의 지문과 비교한다. 다르면 `422`(IETF 초안 권고). 실험: `같은 키, 다른 금액: 422 다른 본문`.
- 순서가 상태 → 지문이면, completed 상태를 먼저 보고 옛 응답을 재생해 버린다. 클라이언트는 새 금액이 결제됐다고 믿고 로그도 남지 않는다.

### 7. 실패를 저장 vs 재선점 허용

| 정책 | 지키는 것 | 잃는 것 |
|---|---|---|
| 실패(500)도 저장해 재생(Stripe) | 부작용이 났을지 모르는 요청을 두 번 실행하지 않는다 | 일시 오류가 그 키의 영구 결과가 된다. 클라이언트는 결과를 "불확정"으로 다뤄야 하고 서버는 대사로 정리한다 |
| FAILED면 재선점 허용(원본) | 일시 오류 뒤 같은 키로 성공할 수 있다 | 실패 전에 외부 부작용이 있었다면 두 번 실행된다 |

- 판단 기준: 실패 전에 부작용이 있었는지를 알 수 있나. 알 수 있으면(로컬 롤백) 재선점이 편하고, 모르면(외부 호출) 저장 + 대사가 안전하다.

### 8. PG 이중 청구, DB는 한 건

- 찾을 것: `status='in_progress'`이면서 `locked_at`이 오래된 키, 그리고 재선점 이력. 재시작 시각 전후로 외부 호출 뒤 완료 기록이 없는 키다.
- 원인: 외부 호출 뒤 완료 기록 전에 죽었고, 재선점한 재시도가 외부를 다시 불렀다(실험 E1과 같은 모양).
- 막는 법: 외부에도 같은 멱등 키 전달(실험 E2), 재선점 경로는 외부 조회 → 이미 승인됐으면 로컬만 기록, 복구 지점 기록, 오래된 in_progress의 주기적 대사.

### 9. TTL보다 늦은 재시도

- 원인: 키 보관 기간이 클라이언트 재시도 기간보다 짧다. 키가 청소된 뒤 같은 키가 와서 새 요청으로 처리됐다(Stripe 문서도 정리된 뒤 재사용된 키는 새 요청으로 처리한다고 적는다).
- 대처 1: TTL을 클라이언트의 최대 재시도 기간보다 길게 잡는다(앱 오프라인 큐 보관 기간을 확인).
- 대처 2: 업무 키(장바구니 ID·주문 번호)에서 키를 파생하고, 업무 테이블에도 유일 제약을 둔다. 키 저장소가 잊어도 업무 데이터가 중복을 막는다.
