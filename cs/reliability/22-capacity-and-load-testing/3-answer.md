# reliability/22-capacity-and-load-testing — 정답

## 정답

### 1. N + 2 계산

- 19,000 / 5,000 = 3.8 → 4개. 두 개가 빠져도 버티려면 + 2 → **6개**(SRE 책 22장 예와 같다).
- 측정이어야 하는 이유: 대당 한계는 데이터 분포·캐시 적중률·쓰기 비율·하류 지연에 따라 몇 배씩 달라진다. 4번 실험에서 같은 코드가 test 분포로는 1,800/s를 넉넉히 처리했고 운영 분포로는 약 1,630/s에서 넘쳤다.

### 2. open vs closed 그림

```text
 closed: VU: [요청──응답][쉼][요청──────응답(느려짐)][쉼]...   → 응답이 늦을수록 다음 요청도 늦다
 open:   시계: │요청 │요청 │요청 │요청 ...                    → 서버와 무관하게 예정대로 온다
```

- closed: 서버가 느려지면 도착률이 **줄어든다**(k6 문서: coordinated omission).
- open: 도착률이 **그대로**다(발생기가 낼 수 있는 한). 처리하지 못한 몫은 서버 대기열에 쌓이거나, 서버가 거절한다. k6 arrival-rate 실행기는 빈 VU가 없으면 반복을 시작하지 못하고 `dropped_iterations`로 센다.

### 3. 모델 선택

- (a) 공개 API: open. 사용자는 서버가 느리다고 덜 오지 않는다.
- (b) 배치 워커 8개: closed. 실제로 8개가 각자 하나 끝내고 다음 것을 꺼낸다.
- (c) 정원 50명 콜센터: closed. 동시 사용자 수가 정원으로 고정이다.

### 4. test vs prod (실험)

(실험, JDK 21 temurin, `--cpus=2`)

| | 적중률 | 처리량 | p99 |
|---|---|---|---|
| test, 1,800/s | 100% | 1,787/s | 3.1ms |
| prod, 1,800/s | 57% | 1,629/s | 433.7ms |

- prod는 처리량이 도착률보다 낮아 4초 동안 대기열이 706까지 자랐다.

### 5. 대당 한계 계산

- 평균 서비스 시간 ≈ 0.57 × 2 + 0.43 × 20 = 1.14 + 8.6 ≈ 9.7ms.
- 한계 ≈ 워커 16 / 9.7ms ≈ 1,650/s. 실험의 1,629/s와 맞는다(실제 sleep이 조금 더 길다 — 해석).
- 캐시가 완전히 비면: 16 / 20ms = 800/s.

### 6. closed 모델 결과

- 실험: 처리 1,559/s, p50 21.8ms, p99 175.7ms, 평균 27.3ms. 한계를 넘지 않는 것처럼 보인다.
- 검산: R = U / X − Z = 200 / 1,559 − 0.1 ≈ 0.0283초 = 28.3ms. 측정 평균 27.3ms와 약 1ms 차이.
- 사용자들이 응답을 기다리느라 요청을 늦게 보내서, 서버는 한계 바로 밑에서 "버틴다". open 1,800/s에서 보인 무한 대기열은 나타나지 않는다.

### 7. 예정 도착 시각부터 재는 이유

- 서버가 막혀 있는 동안 발생기가 요청을 늦게 보냈다면, 그 요청의 "보낸 시각"부터 재면 막혀 있던 시간이 빠진다.
- 실제 사용자는 예정 시각에 왔고 그때부터 기다렸다. 그래서 예정 시각부터 재야 대기 시간이 지연에 들어간다. 이것을 빼먹는 것이 coordinated omission이다.

### 8. 지연 캐시 vs 용량 캐시

- 지연 캐시: 캐시가 비어도 예상 부하를 감당한다. 빠르게만 해 준다.
- 용량 캐시: 캐시가 비면 예상 부하를 감당하지 못한다(SRE 책 22장).
- 실험 서비스: 용량 캐시다. 콜드 캐시 한계 800/s가 운영 피크(예: 1,200/s — 예시)보다 낮다고 가정할 때다. 예상 피크가 800/s 이하면 지연 캐시다.
- 더 넣을 것: 콜드 캐시 상태(재시작 직후·새 클러스터) 부하 테스트, 천천히 트래픽을 올리는 램프업 절차.

### 9. 발생기 병목 의심

- 의심: 부하 발생기 자체(CPU·네트워크·VU 부족), 또는 closed 모델이라 도착률이 서버 지연에 묶였을 가능성.
- 확인
  - 발생기 호스트의 CPU·네트워크 사용률.
  - k6라면 `dropped_iterations`가 0보다 큰지(빈 VU가 없어 시작 못 한 반복).
  - 서버 쪽 지표의 실제 도착률을 발생기 보고와 비교.
- 대처: 발생기를 여러 대로, `maxVUs` 증가, arrival-rate 실행기로 전환.

### 10. 헤드룸 없는 피크

- 이용률 85%면 서비스에 따라 이미 지연이 가파른 구간이다(실험 서비스는 한계의 약 90%에서 p99 2배 — 곡선은 서비스마다 재야 한다). 같은 인스턴스 N대에 균등 분산이라면 한 대가 빠질 때 남은 대수의 이용률은 0.85N/(N−1)이다. N ≤ 6이면 100%를 넘어 대기열이 끝없이 자라고, 10대여도 약 94%다. 느려진 인스턴스가 헬스 체크에 실패해 더 빠지면 연쇄가 된다.
- 부하를 조금 줄여서는 회복되지 않는 경우가 많다. SRE 22장의 예: 10,000 QPS에서 건강하던 서비스가 11,000 QPS에서 무너지기 시작하면 9,000 QPS로 줄여도 멈추지 않는다. 건강한 서버가 일부뿐이기 때문이다.
- 막는 법: N + 1·N + 2 여유 대수, 부하 테스트 곡선에서 정한 목표 이용률, 넘치면 빠르게 거절하는 로드 셰딩.
