# reliability/42-cold-start-and-scale-from-zero — 정답

## 정답

### 1. 콜드 스타트 구간

```text
 환경 확보 → 코드·이미지 가져오기 → 런타임 시작 → 초기화 코드 → 첫 요청의 일회성 비용 → JIT·캐시 워밍업 → 제 속도
                                  └──── Lambda Init 단계 ────┘
```

- Lambda Init 세 작업: 확장 시작(Extension init), 런타임 부트스트랩(Runtime init), 함수의 정적 코드 실행(Function init). SnapStart면 before-checkpoint 훅이 더해진다.

### 2. Init 시간 제한

- 10초. 넘으면 첫 호출 때 함수 타임아웃 설정으로 Init을 다시 시도한다. 실패하면 `INIT_REPORT … Status: timeout`.
- 적용 안 되는 구성: provisioned concurrency, SnapStart, Lambda Managed Instances. 문서는 이때 초기화 코드가 최대 15분까지 돌 수 있다고 적는다.

### 3. JDK 21 첫 요청과 워밍업 (실험)

(실험, JDK 21.0.12, `--cpus=2`, 서버 안 처리 시간 중앙값, 2회)

| 구간 | 1회 | 2회 |
|---|---|---|
| 1번 | 73.6ms | 79.3ms |
| 2~10번 | 3.7ms | 3.1ms |
| 11~100번 | 1.2ms | 1.1ms |
| 1,001~2,000번 | 0.41ms | 0.39ms |

- 첫 요청이 안정 상태보다 약 180~200배 느리다. 사실 점검 재실행 2회는 첫 요청 70·115ms, 1,001번 이후 0.51·0.55ms(약 130~225배)로 폭이 컸다. 모양은 같다.

### 4. `-Xint`로 구분하기

- `-Xint`: 첫 요청 89.6ms(재실행 81.5ms), 2번부터 끝까지 약 13~15ms로 평평하다.
- 첫 요청 비용(약 75ms)은 JIT를 꺼도 그대로다 → 첫 경로의 일회성 비용(클래스 로딩·링크, 람다·`String.format` 부트스트랩 등)이다(해석).
- 이후 3ms → 1.1ms → 0.4ms로 내려가는 계단은 `-Xint`에서 사라진다 → JIT 워밍업이다. C1만 쓰면(`TieredStopAtLevel=1`) 0.69ms에서 멈추므로 마지막 단계가 C2다.

### 5. AppCDS vs AOT 캐시 (실험)

| | 시작→READY | 시작→첫 응답 | 첫 요청 처리 |
|---|---|---|---|
| JDK 21 기본 | 242·295ms | 512·556ms | 74~79ms |
| JDK 21 AppCDS | 205·252ms | 432·449ms | 60~62ms |
| JDK 25 기본 | 302·302ms | 538·575ms | 87~93ms |
| JDK 25 AOT 캐시 | 124·134ms | 307·318ms | 65ms |

- AppCDS는 개선이 작고, AOT 캐시는 READY를 절반 이하로, 첫 응답을 약 40% 줄였다.
- 맞출 것(JEP 483): 같은 JDK 릴리스, 같은 하드웨어 아키텍처·OS, 같은 클래스패스(뒤에 덧붙이기만 허용, JAR만), 같은 모듈 옵션. 어기면 경고 후 캐시를 무시한다.

### 6. 프로브 설계

- readinessProbe: "포트가 열림"이 아니라 "워밍업이 끝남"에서 통과하게 한다. 시작 후 대표 요청으로 경로를 데운 뒤 Ready를 연다.
- startupProbe: 통과할 때까지 liveness·readiness가 돌지 않는다. 최악 시작 시간을 덮게 둔다.
- 300초 허용: `failureThreshold: 30`, `periodSeconds: 10`(30 × 10 = 300초 — Kubernetes 문서의 예).

### 7. provisioned concurrency 계산

- 동시성 = 초당 요청 × 평균 실행 시간 = 200 × 0.25 = **50**.
- 평균 80건으로 계산하면 20이다. 피크에 동시 실행이 20을 넘는 몫(약 30)은 표준 동시성으로 넘어가 콜드 스타트를 낸다.

### 8. SnapStart

- 빠른 이유: 버전 발행 때 Init을 한 번 하고, 초기화된 실행 환경의 메모리·디스크를 스냅숏으로 떠 둔다. 새 환경은 처음부터 초기화하지 않고 스냅숏에서 재개한다.
- 문제 1 — 고유성: 초기화 때 만든 고유 ID·비밀값·난수 시드가 여러 환경에 복제된다. 대처: 핸들러 안이나 after-restore 훅에서 만든다.
- 문제 2 — 커넥션: 초기화 때 연 네트워크 연결의 상태가 재개 뒤 보장되지 않는다. 대처: 복원 뒤 확인하고 다시 연다.

### 9. 확장·배포 때만 p99가 튐

- 볼 것: 파드별 지연(새 파드만 높은지), 새 파드의 Ready 시각과 첫 트래픽 시각, 이미지 pull 이벤트 길이, readiness가 무엇을 확인하는지.
- 원인: 덜 데워진 파드가 트래픽을 받았다(실험의 첫 요청 수십 ms → 수 ms → 1ms 미만 계단). 이미지 pull이 길면 확장 반응도 늦다.
- 고치는 법: 워밍업 후 Ready, LB 슬로 스타트, AOT 캐시·AppCDS, 이미지 축소·pre-pull. 반응 시간 동안은 여유 용량으로 덮는다.

### 10. 첫 요청 게이트웨이 타임아웃

- 볼 것: 그 호출의 `REPORT` 줄 `Init Duration`(수천 ms인지), Init 타임아웃이면 `INIT_REPORT … Status: timeout`.
- 줄이는 순서
  1. 구간 측정: 패키지 다운로드·런타임 시작·정적 초기화 중 무엇이 긴가.
  2. 패키지·의존성 축소, 무거운 초기화 정리(드물게 쓰는 것은 지연 생성).
  3. 런타임 시작 단축: SnapStart(Java·Python·.NET), JVM이면 AOT 캐시.
  4. 지연 민감 경로는 provisioned concurrency.
  5. 호출자 타임아웃이 남은 콜드 스타트를 견디는지 확인.
