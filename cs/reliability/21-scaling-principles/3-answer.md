# reliability/21-scaling-principles — 정답

## 정답

### 1. 병목 이동과 처리량 상한

```text
 앱 증설 → 커넥션 풀이 먼저 참 → 풀 증설 → DB CPU가 참 → 복제본 → 쓰기(주 DB)가 참 → 샤딩 → 샤드 간 쿼리
```

- 병목 하나를 넓히면 그다음으로 좁은 구간이 전체를 정한다.
- 상한: 처리량 X ≤ 1/D. 이용률 U = X × D가 1을 넘을 수 없기 때문이다(한 번에 한 건만 처리하는 자원 기준. 동시에 m건 처리하는 자원이면 X ≤ m/D).
- 실험 contention 모드: 전역 락이 병목이 되어 약 5,000 req/s에서 멈췄다(N=16·32·64, 3회 실행 범위 약 4,850~5,130).

### 2. Little's Law 계산

- L = λ × W = 800 × 0.25 = 200건.
- 여유 25%: 200 × 1.25 = 250, 인스턴스 4대 → 인스턴스당 약 63개(62.5를 올림).
- 틀어지는 조건(하나만 들면 됨)
  - 하류가 느려져 W가 커지면 L도 같은 배수로 커진다(예: W 0.25 → 1초면 L = 800).
  - 피크 λ를 평균으로 잡으면 부족하다.
  - 스레드 말고 하류 자원(DB 커넥션) 총량이 먼저 바닥날 수 있다.

### 3. 성립 조건

- 조건: 장기 평균이 존재하는 안정 상태. 들어온 만큼 나간다.
- 수렴하지 않는 경우: 도착률이 처리율을 넘는 과부하. 큐가 끝없이 자라 L이 계속 커진다.
- 분포: 도착 분포·서비스 시간 분포·처리 순서와 무관하다(Little 1961). 포아송이 아니어도 된다.

### 4. USL 곡선

```text
 C(N) = N / (1 + α(N−1) + βN(N−1))

 X │ α=β=0 ／ (직선)
   │      ／   ___ β=0, α>0: 1/α로 수렴 (Amdahl과 같은 모양)
   │    ／ _--
   │  ／-‾‾‾‾‾--__ β>0: 정점 뒤 감소
   └──────────── N
```

- N_max = √((1−α)/β). β = 0이면 정점이 무한대(감소 없음).

### 5. 실험 예측과 실제

(실험, JDK 21 temurin, `--cpus=2`)

| N | contention 처리량 | coherence 처리량 |
|---|---|---|
| 1 | 441 | 441 |
| 8 | 3,502 | 2,812 |
| 16 | 5,006 | 4,412 (정점) |
| 32 | 5,042 | 3,358 |
| 64 | 5,016 | 1,493 |

- contention: 선형으로 오르다가 약 5,000/s에서 평평하다. 락이 병목 자원이다.
- coherence: N=16 정점 뒤 **줄어든다**. USL 적합 정점 N* ≈ 14(다른 실행 13.0~14.2)와 맞는다.

### 6. 닫힌 루프의 W

- W = L / λ = 64 / 5,016 ≈ 0.01276초 = 12.76ms.
- 측정 W 평균도 12.76ms였다. 표의 λ×W 열도 64.00으로 측정 L(64.00)과 같다.

### 7. 적합값 해석

- contention의 β ≠ 0: 그대로 "조율 비용"으로 읽으면 안 된다. 이 모드는 병목 자원 상한(X ≤ 1/D)에 부딪혀 꺾임 없이 평평해지는 모양이다. USL의 매끄러운 곡선과 모양이 달라 적합이 β에 값을 나눠 준 것이다.
- coherence의 α < 0: 물리적 의미는 없다. 흉내 낸 조율이 USL의 가정과 꼭 같지 않아 생긴 적합 오차다.
- 읽어야 할 것: β가 뚜렷이 양수인지, 정점이 어디인지, 그리고 그것이 측정 곡선과 맞는지. 모형은 원인 후보를 좁히는 도구다.

### 8. 무상태화와 USL

- 이유: 요청 처리에 필요한 상태가 인스턴스 안에 있으면 그 요청은 그 인스턴스로만 가야 한다. 그 인스턴스가 죽으면 상태도 잃는다. LB가 아무 데나 보낼 수 없다.
- 새로 생기는 것
  - 밀어낸 저장소(세션 저장소·DB)가 공유 자원이 된다 → α(경합).
  - 인스턴스끼리 캐시·락을 맞추면 → β(일관성 비용).
- 그래서 확장의 어려움은 데이터 계층으로 모인다.

### 9. 늘렸더니 처리량 감소

- 볼 것: 분산 락 대기 시간, 캐시 무효화·브로드캐스트 메시지 수, 노드 간 RPC 수가 노드 수에 비해 어떻게 늘었나. 처리량을 N = 4, 8, 12, 16에서 재어 USL을 적합해 β > 0인지 본다.
- 원인: β(조율 비용). 인스턴스당 CPU가 낮은 것은 일을 하지 않고 서로를 기다리기 때문이다.
- 대처: 우선 N을 정점 아래로 되돌린다. 근본은 키 파티셔닝으로 조율을 없애고, 전체 방송을 대상 지정으로 바꾸고, 강한 일관성이 필요 없는 곳은 비동기로 돌리는 것이다.

### 10. 하류 지연과 풀 고갈

- λ가 그대로여도 W가 50ms → 500ms가 되면 L은 10배다. 풀 크기는 평소 L에 맞춰져 있어 스레드가 모두 느린 하류를 기다린다.
- 모든 엔드포인트가 같은 풀을 쓰므로 무관한 요청도 줄을 선다.
- 대처
  - 하류 호출 타임아웃으로 하류에 붙잡히는 시간(W를 늘린 몫)의 상한을 만든다. 큐 대기까지 묶으려면 요청 전체 기한을 둔다.
  - 하류별로 풀을 나눈다(벌크헤드).
  - 대기열에 상한을 두고 넘치면 빠르게 거절한다(로드 셰딩).
