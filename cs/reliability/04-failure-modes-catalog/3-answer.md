# reliability/04-failure-modes-catalog — 정답

## 정답

### 1. 네 칸과 판정

- 증상은 원인을 못 알려 주고, 뿌리는 원리를, 현장은 "우리에게도 있나"를 알려 준다. 실제로 사고를 막는지는 마지막 칸이 정한다.
- 이름 붙은 장치: 어기면 **시스템이 거부**한다(유니크 제약, 버전 조건부 UPDATE, fencing token, DLQ, 모듈 경계, 아키텍처 테스트).
- 계약 문장: 사람이 지켜야 한다("순서를 지킨다", "flush를 꼭 한다"). 부하가 걸리는 날 뚫린다.

### 2. "멱등하게 처리한다"

- 문장뿐이면 뚫림으로 판정한다.
- 바뀌는 조건: 처리 기록 테이블에 `event_id` **`NOT NULL` + 유니크 제약**이 실제 스키마(마이그레이션)에 있고, 업무 변경과 **같은 트랜잭션**에서 삽입하며, 제약 위반을 "이미 처리됨"으로 다루는 코드가 있을 때 막힘이다. `pg_constraint` 조회 등으로 확인한다.

### 3. lost update 실험

| 모드 | T1 | T2 | 최종 |
|---|---|---|---|
| RC plain(절대값 저장) | `UPDATE 1` | `UPDATE 1` | 50 — +30이 에러 없이 사라짐 |
| RC optimistic(`AND version = ?`) | `UPDATE 1` | `UPDATE 0` | 30 — T2는 다시 읽고 재시도해야 80 |
| RC atomic(`held = held + ?`) | `UPDATE 1` | `UPDATE 1` | 80 |
| RR plain | `UPDATE 1` | `ERROR: could not serialize access due to concurrent update` | 30 — T2는 트랜잭션 재시도 필요 |

### 4. 상대 UPDATE의 한계

- `held = held + 50`은 최신 값에 더하므로 유실은 없다. 하지만 "가용잔액(잔액 − 홀딩)이 50 이상인가"를 **앱이 읽은 값으로 판단**하면, 판단과 UPDATE 사이에 다른 홀딩이 끼어들어 초과 홀딩(F-22)이 된다.
- 보완: 판단을 같은 문장에 넣는다(`UPDATE ... SET held = held + 50 WHERE id = ? AND balance - held >= 50`, 0행이면 거절), 또는 버전 조건부 UPDATE, 또는 행 락(`SELECT ... FOR UPDATE`).

### 5. RR의 제품 차이

- MySQL InnoDB RR: Jepsen(MySQL 8.0.34, 2023-12)이 lost update를 확인했다(9,048 트랜잭션 중 446개가 198건에 관여). 원본의 "RR은 쓰기에 위험"은 여기에 맞다.
- PostgreSQL 17 RR: 같은 경합에서 두 번째 쓰기를 직렬화 오류(SQLSTATE 40001)로 거부했다(실험). 유실은 없고 대신 재시도가 필요하다.
- 결론: 격리 수준 이름만으로 동작을 판단하지 않는다. 제품·버전의 문서와 실험으로 확인한다.

### 6. 중복 소비 실험

- 조회 후 삽입: 두 소비자 모두 "0건"을 보고 둘 다 넣어 **2행**.
- 유니크 제약: 두 번째 삽입이 `duplicate key value violates unique constraint`로 거부되어 **1행**.
- 조회는 "지금 없다"를 볼 뿐 "앞으로 남이 못 넣는다"를 보장하지 않는다. 확인과 삽입 사이의 틈은 DB가 원자적으로 검사하는 제약만 막는다.

### 7. 고장 모양으로 나누기

- 이 노트의 분류로는 신호 없는 쪽(F-01·04·07·11·12·14·17·18·21·22·23·24·25)이 더 많다.
- 비용이 "건수 × 발견까지 기간"이라 신호 없는 쪽이 더 비싸다. 막는 장치에 **아는 장치**(대조 배치, 불변식·총량 검사, 지표, 그 검사가 실제로 도는지 감시)를 붙인다.

### 8. 정상 동작이 원인

- 예: F-02(DB가 데드락을 탐지해 한쪽을 중단), F-05(MVCC가 열린 스냅샷을 위해 옛 버전을 보존), F-14(GC 멈춤 중 lease 만료), F-15(스케줄러 이중화로 둘 다 실행), F-17(롤링 배포의 두 버전 공존), F-06(DDL 알고리즘의 제약).
- 코드에 "틀린 줄"이 없다. 각 부품이 설계대로 동작한 결과의 조합이라, 버그를 찾는 리뷰로는 안 나오고 동작 원리를 알아야 보인다.

### 9. 배포 중 판정 불일치

- F-17 배포 스큐(구·신 버전 공존).
- Knight Capital(2012-08-01, SEC 34-70694): SMARS 서버 8대 중 1대에 새 코드가 복사되지 않았고, 재사용된 플래그가 그 서버에서 옛 Power Peg 기능을 깨웠다. 약 45분에 4억 6천만 달러 넘게 손실. 이후 새 코드를 다른 7대에서 되돌리자 그 서버들에서도 옛 코드가 돌았다. 겹친 것: 버전 공존 + 플래그 의미 재사용 + 배포 검증(전 서버 버전 일치 확인) 부재.
- 대처: 판단이 바뀌는 변경은 기능 플래그 뒤에, 플래그 이름 재사용 금지, 배포 후 전 인스턴스 버전 확인을 자동화, 스키마는 expand-contract.

### 10. 설계 리뷰 순서

1. 경로를 그린다: 주문 저장 → 포인트 이벤트 발행 → 소비자가 적립 → 외부 알림 호출.
2. 칸마다 번호: 주문·포인트 잔액 갱신 F-01, 이벤트 발행 F-10, 소비 F-11·F-13, 같은 회원 이벤트 순서 F-12, 외부 알림 F-16·F-20(응답 유실 시 중복 알림), 배포 중 이벤트 스키마 F-17.
3. 번호마다 장치 이름: 버전 컬럼, 아웃박스, `event_id` 유니크 제약, DLQ, 회원 ID 파티션 키, 알림 요청 멱등 키.
4. 신호 없는 항목(F-01·F-11·F-12)에 아는 장치(포인트 합계 대조)를 붙이고, 남긴 빈칸은 이유와 함께 기록한다.
