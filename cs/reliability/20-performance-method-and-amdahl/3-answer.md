# reliability/20-performance-method-and-amdahl — 정답

## 정답

### 1. 한 가지만 바꾸는 이유

- 변경과 효과가 1:1로 대응해야 "무엇이 효과였나"를 안다. 회귀가 나도 그 변경 하나만 되돌리면 된다.
- 여러 개를 한꺼번에 바꾸면 잃는 것
  - 원인: 효과가 어느 변경에서 왔는지 모른다. 좋은 변경과 나쁜 변경이 서로 상쇄할 수도 있다.
  - 재현: 회귀를 다른 환경에서 재현하려 해도 어떤 조합인지 모른다.
  - 학습: 다음에 같은 문제를 만나도 쓸 지식이 남지 않는다.
- 같은 조건 재측정은 차이가 실행 간 잡음보다 큰지를 확인하기 위해서다.

### 2. Amdahl 계산

- 5% 구간 2배: 1 / (0.95 + 0.05/2) = 1 / 0.975 ≈ 1.026배. 실행 시간 2.5% 감소.
- 95% 구간 2배: 1 / (0.05 + 0.95/2) = 1 / 0.525 ≈ 1.9배. 실행 시간 47.5% 감소.
- 직렬 10%, 코어 무한대: 상한 1 / 0.1 = 10배.

### 3. 5% 구간 실험

- 예측대로 나오지 않았다. 11회 중앙값으로 세 번 돌린 결과가 −4.8%, +2.4%, +1.3%였다. 5회 중앙값 두 번도 −3.7%, +4.7%였다. 같은 설정의 재실행 2회는 +1.6%, +1.4%였다(예측보다 작거나 반대 방향 — 실행마다 흩어진다).
- 이유: 기대 효과(2.5%)가 이 환경(코어 2개, 부하 높은 공유 호스트)의 실행 간 잡음보다 작다.
- 같은 실험에서 95% 구간 개선은 세 번 모두 45~47%로 예측(47.5%)에 가까웠다.
- 교훈: 작은 구간 최적화는 이득이 작을 뿐 아니라 **측정으로 확인하기도 어렵다.** 효과를 주장하려면 잡음 범위를 먼저 알고, 그보다 큰 차이인지 확인한다. 고칠 곳은 큰 구간부터 고른다.

### 4. USE 체크리스트

```text
 자원         U(사용률)              S(포화)                       E(에러)
 CPU          CPU %                  run queue 길이                 —
 워커 스레드   바쁜 워커 / 전체         (요청 큐 길이)                  거절 수
 DB 풀(4개)    활성 커넥션 / 4          풀 대기 스레드 수, 대기 시간      획득 타임아웃
```

- 실험 3에서 워커 8 이상일 때: DB 풀 U = 4/4(100%), S = 풀 대기 시간 5 → 25 → 65ms로 증가. 이 시스템의 병목은 CPU가 아니라 DB 풀이다. (에러는 실험에 타임아웃을 두지 않아 0이다.)

### 5. 병목 이동 예측과 실험

- 예측: 워커가 적으면 처리량 ≈ W / 15ms(워커가 병목). 최대는 DB 풀 4 / 10ms = 400건/s. 워커 약 6개부터 DB 풀이 병목이 되고, 그 뒤로는 처리량 고정·지연 증가.
- 실험(`--cpus=2`, 워커 수마다 3초): 2 → 131건/s·15.3ms, 4 → 263건/s·15.2ms, 8 → 394건/s·20.4ms, 16 → 396건/s·40.6ms, 32 → 403건/s·80.4ms(그중 풀 대기 65.2ms).
- Little's Law: W = L / λ = 32 / 403 ≈ 79ms. 실측 평균 80.4ms와 맞다.

### 6. Amdahl이 설명 못 하는 것

- Amdahl은 직렬 부분 때문에 이득이 **포화**되는 것만 설명한다. 노드·스레드를 늘릴수록 **오히려 느려지는** 현상은 설명하지 못한다.
- 원인은 참여자 **쌍마다** 생기는 조율 비용이다. 캐시 일관성 트래픽, 노드 간 동기화가 참여자 수의 제곱 꼴로 늘어난다.
- 모델: Gunther의 USL(Universal Scalability Law) — C(N) = N / (1 + α(N−1) + βN(N−1)).
  - 경합(α): 락 앞 줄서기 같은 직렬화. N에 선형이라 Amdahl처럼 **포화**만 만든다(β = 0이면 Amdahl과 같은 꼴).
  - 일관성 비용(β): N(N−1)에 비례. β > 0이면 처리량이 **역행**(감소)한다(perfdynamics.com USL 페이지, → 21-scaling-principles).

### 7. Streetlight·Random Change

- Streetlight: 익숙하거나, 인터넷에서 찾았거나, 아무렇게나 고른 관측 도구를 돌려 눈에 띄는 문제만 본다. 도구가 비추지 않는 자원은 보지 않는다.
- Random Change: 기준선을 재고, 무작위로 고른 설정 하나를 한 방향·반대 방향으로 바꿔 재고, 나으면 유지하고 반복한다.
- 측정을 하는데도 안티 방법론인 이유: 가설이 없다. 왜 좋아졌는지 모르고, 잡음을 효과로 착각할 수 있으며(3번 실험), 설정 간 상호작용을 놓친다. 시간도 오래 걸린다.

### 8. 플래그 다섯 개 회귀

- 찾기: 다섯 개를 하나씩 다시 적용하며 같은 조건으로 재측정한다(또는 기준선에서 반씩 나눠 적용하는 이분 탐색). 재현 환경은 운영과 같은 부하 모델·데이터 크기로 맞춘다.
- 막기: 변경 1개 = 배포·측정 1회 = 기록 1줄. 변경마다 예측과 되돌리는 방법을 적는다. 잡음 범위 안의 효과는 "효과 없음"으로 되돌린다.

### 9. 첫날 순서

1. 문제 정의: 성능 문제라고 보는 근거(p99 수치·기간)? 잘 돌던 때가 있었나? 최근 무엇이 바뀌었나(배포·트래픽·데이터)? 다른 API·사용자도 겪나? 환경·버전은?
2. 측정: open 부하 또는 운영 지표로 p50·p99·max·처리량·오류율 기준선. 실행 간 잡음 범위도 잰다.
3. 병목 특정: 트레이스로 구간별 시간 비율을 본다. 가장 큰 구간에 대해 USE(CPU·풀·디스크·락)를 채운다. 코드 안이면 프로파일러.
4. 순위 매기기: 구간 비율 p와 기대 배율 s로 Amdahl 단축률 1 − ((1 − p) + p/s)를 계산해 큰 것부터. 가설·예측을 적고 변경 하나를 고른다.
