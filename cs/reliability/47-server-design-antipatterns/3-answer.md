# reliability/47-server-design-antipatterns — 정답

## 정답

### 1. 좋은 의도

- 서비스를 나눴다(독립 배포를 원했다) + 같은 DB를 직접 쓴다 → 분산 비용만 내고 결합은 그대로(원본 1·3).
- 큐를 넣었다(피크 완충을 원했다) + 상한이 없다 → 유입 > 처리면 지연·메모리가 무한히 자라 지표가 초록인 채로 OOM(원본 8).
- 공통: 국소 결정이 **숨은 결합**(공유 상태·시간·용량·검증 안 된 가정)을 만든다. 이점은 사라지고 비용만 남는다.

### 2. 네 결합

### 3. 계산

- 0.999^5 ≈ 0.995 → 99.5%(독립 고장 가정).
- 3 × 3 × 3 = 27배(맨 아래 서비스가 받는 최대 요청 배수).
- 1대 장애 → 남은 1대 140% → 포화로 같이 죽는다.
- N대면 평소 사용률 ≤ (N−1)/N(3대 약 67%, 4대 75%).

### 4. 스케줄러 실험

(실험, PostgreSQL 17.11 + JDK 21.0.12, 3회 모두 같은 행 수)

| 모드 | 시각차 0ms | 시각차 150ms |
|---|---|---|
| none | 3 | 3 |
| lock(실행 중에만) | 1 | 3 |
| runkey | 1 | 1 |

### 5. 락이 못 막은 이유

- 정산이 100ms라, 150ms 늦게 깨는 다음 인스턴스가 왔을 때 앞 인스턴스는 이미 끝내고 락을 풀었다. 빈 락을 잡고 다시 실행한다.
- 락(advisory lock)은 "지금 누가 쥐고 있나"만 기억한다. 이력이 없다.
- 유일 키는 "이 회차(`job, run_date`)를 이미 했다"를 영구히 기억한다. 그래서 시각차와 무관하게 한 번이다.

### 6. 기록과 지급의 관계

- 실행 기록 삽입과 지급이 **한 트랜잭션**이어야 한다(실험의 runkey는 `setAutoCommit(false)` → INSERT → 지급 → `commit`).
- 따로 커밋하면: 기록만 남고 지급 전에 죽으면 그 회차는 영영 실행되지 않는다(누락). 지급 먼저 하고 기록 전에 죽으면 다음 인스턴스가 다시 지급한다(중복). 외부 PG 호출처럼 한 트랜잭션에 못 넣는 일은 멱등 키를 따로 쓴다(13).

### 7. 탐지 쿼리

```sql
SELECT job, run_date, count(*) FROM job_history GROUP BY job, run_date HAVING count(*) > 1;
```

```promql
avg(instance_cpu_utilization_ratio{job="api"}) * count(up{job="api"} == 1) / (count(up{job="api"} == 1) - 1) > 0.9
deriv(queue_depth[15m]) > 0
```

- (지표 이름은 예시) 첫 PromQL은 "한 대가 빠지면 남은 쪽 평균 사용률", 둘째는 최근 15분 큐 길이의 추세(선형 회귀 기울기)가 상승인지(단조 증가 보장은 아니다).

### 8. 증설이 DB를 죽인다

- 에러: PostgreSQL `FATAL: sorry, too many clients already`, 앱 쪽 커넥션 풀 획득 타임아웃, DB CPU 포화.
- 원인: 병목이 DB인데 앱을 늘렸다. 인스턴스 수 × 풀 크기(최대) = 그 앱 풀들의 DB 커넥션 상한(원본 5·9 — 다른 클라이언트 연결은 별도).
- 대처: 증설 전 병목 측정. 오토스케일 상한을 DB 커넥션 예산에서 역산. 풀 크기 축소, 커넥션 풀러(PgBouncer)(database/21).

### 9. 깊은 헬스체크

- 원인: 헬스체크가 DB를 확인한다(원본 14). DB 하나의 느림이 모든 인스턴스의 "unhealthy"가 되어 동시에 빠진다.
- 나누기: liveness = 프로세스 자신(멈췄나, 이벤트 루프가 도나). readiness = 트래픽을 받을 준비(기동·종료 중인가). 의존성 장애는 헬스체크가 아니라 요청 경로의 오류·폴백·서킷 브레이커로 다룬다. readiness에 의존성을 넣더라도 전 인스턴스가 함께 빠지지 않게 한다.

### 10. 고정 스레드풀의 무한 큐

- JDK 문서: `newFixedThreadPool`은 "공유 무제한 큐(shared unbounded queue)" 위에서 고정 수 스레드가 일한다. 처리보다 유입이 많으면 큐가 끝없이 자라고, 대기 시간과 메모리가 함께 는다.
- 처방: `new ThreadPoolExecutor(8, 8, 0, SECONDS, new ArrayBlockingQueue<>(200), new CallerRunsPolicy())`처럼 상한 큐 + 거절 정책(호출자 실행으로 역압 — 실행기가 종료되지 않았을 때, 또는 즉시 거절로 로드 셰딩 — 12).
