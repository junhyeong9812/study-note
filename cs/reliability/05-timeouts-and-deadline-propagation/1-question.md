# reliability/05-timeouts-and-deadline-propagation — 질문

## 질문

1. (왜) 타임아웃을 계층마다 "바깥 > 안쪽"으로 정렬했는데도 데드라인 전파가 따로 필요한 이유는? 예를 들어 설명하라.
2. (그림) gRPC Deadlines 가이드의 예(클라이언트 13:00:00에 2초 데드라인, User 서버가 0.5초 일한 뒤 Billing 호출)를 시간축으로 그려라. Billing에게 선로로 가는 값은 무엇이고 왜 그 형태인가?
3. (예측) 클라이언트 → A → B → C, 클라이언트 타임아웃 1초, C는 100ms 단계 30개를 한다. 각 홉이 고정 5초 타임아웃만 쓰면 C는 클라이언트 포기 뒤 대략 몇 단계를 더 하나? 남은 시간을 전파하고 C가 단계마다 확인하면?
4. (예측) 3번에서 절대 만료 시각(epoch)을 헤더로 그대로 전파했는데 C의 시계만 2초 늦다. C의 헛일은 전파 없음과 비교해 어떻게 되나? 왜인가?
5. (경계) gRPC 서버는 데드라인이 지나면 호출을 자동으로 취소한다. 그런데도 서버 코드가 해야 할 일은 무엇인가? SRE 22장은 여러 단계 처리에 대해 무엇을 권하나?
6. (계산) 프런트엔드 스레드 1,000개, 평소 1,000 QPS × 100ms. 요청의 5%가 끝나지 않고 데드라인이 100초다. 처리 가능 비율과 에러율은? 이 계산이 말하는 것은?
7. (연결) 남은 시간 전파에서도 하류가 클라이언트보다 조금 늦게 멈추는 이유는? SRE 22장은 이 틈을 어떻게 다루라고 하나?
8. (장애 진단) 과부하 때 하류 서비스 로그에 응답을 쓰는 순간의 `Broken pipe`가 쏟아지고, 하류 CPU는 요청량에 비해 너무 높다. 무엇을 의심하고 무엇을 확인하나?
9. (적용) Envoy가 상류에 붙이는 `x-envoy-expected-rq-timeout-ms`를 남은 예산으로 그대로 쓰면 무엇이 잘못될 수 있나?
