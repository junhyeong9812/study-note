# reliability/05-timeouts-and-deadline-propagation — 정답

## 정답

### 1. 정렬만으로 부족한 이유

- 고정 타임아웃은 "이 호출을 얼마나 기다리나"만 안다. 요청이 여기 오기까지 **이미 쓴 시간**을 모른다.
- 예: 게이트웨이 3.0s, A 2.5s, B 2.0s로 정렬했다. A가 B를 부르기 전 1.8초를 썼다면, 게이트웨이 기준으로 남은 것은 1.2초 남짓인데 B는 2.0초를 기다린다. 그 차이만큼 바깥이 먼저 떠난 뒤의 헛일이 생긴다.
- 데드라인 전파는 남은 시간을 실어 보내 이 차이를 없앤다. 고정 정렬은 전파가 끊긴 구간의 마지막 방어선으로 남긴다.

### 2. gRPC 예의 시간축

```text
 13:00:00.0 클라이언트 데드라인 13:00:02 ── GetUserProfile ──> User
 13:00:00.5 User: 0.5초 썼다 ── GetTransactionHistory (timeout 1.5s) ──> Billing
            Billing: 받은 순간 + 1.5s = 자기 시계의 데드라인
 13:00:02   시간 끝: 클라이언트 DEADLINE_EXCEEDED, User·Billing 쪽 호출 취소
```

- 선로 값: 절대 시각이 아니라 **이미 흐른 시간을 뺀 타임아웃**(`grpc-timeout: 1500m` 같은 형태 — 값 + 단위).
- 이유: 두 서버의 시계가 맞지 않을 수 있다. 상대 시간을 보내면 받는 쪽이 자기 시계로 다시 만들어 시계 어긋남을 피한다(gRPC Deadlines 가이드).

### 3. 전파 없음 vs 남은 시간 전파

(실험, JDK 21.0.12, 3회 같은 결과)

- 고정 5초(전파 없음): C는 30단계를 모두 했고, 클라이언트 포기(약 1.0초) 뒤에 **22단계**를 더 했다. 응답은 `Broken pipe`로 버려졌다.
- 남은 시간 전파 + 단계별 확인: C는 898ms를 받아 9단계에서 멈췄다. 포기 뒤 **1단계**만 더 했다.
- 차이를 만든 것은 둘이다. (1) 남은 시간을 받았고 (2) C가 단계마다 확인했다.

### 4. 절대 시각 + 시계 어긋남

- C는 "남은 예산 2851ms"를 믿고 29단계까지 했다. 클라이언트 포기 뒤 **21단계** — 전파 없음(22단계)과 거의 같다.
- 이유: 만료 시각은 클라이언트 시계 기준인데, C는 2초 늦은 자기 시계로 비교했다. 예산이 2초 늘어난 셈이다. 시계가 빠르면 반대로 받자마자 만료로 거절한다.

### 5. 서버 코드의 몫

- gRPC는 호출을 `CANCELLED`로 끝낼 뿐, 그 RPC를 위해 시작한 활동을 멈추는 것은 **서버 애플리케이션의 책임**이다. 오래 걸리는 처리는 주기적으로 취소 여부를 확인해야 한다(gRPC Deadlines 가이드).
- SRE 22장 "Missing deadlines": 파싱·하류 요청·처리처럼 여러 단계로 나뉘면 **각 단계 전에** 남은 시간이 충분한지 확인하라. 하류 호출은 전파된 데드라인으로 하고, 취소도 하류로 전파한다.

### 6. 스레드 고갈 계산 (SRE 22장 "Bimodal latency")

- 끝나지 않는 5% = 50 QPS × 100s = 스레드 5,000개가 필요하다. 가진 것은 1,000개.
- 처리 가능 비율 = 1,000 / (5,000 + 95) = **19.6%**, 에러율 **80.4%**.
- 의미: 일부 요청의 멈춤이 공유 자원(스레드)을 다 먹어 정상 요청까지 실패시킨다. 데드라인이 평균의 몇 자릿수 위(이 예는 1,000배)면 타임아웃이 없는 것과 거의 같다. 평균 지연만 보면 원인이 안 보인다.

### 7. 전송 시간의 틈

- 받는 쪽은 "받은 순간"부터 센다. 보내는 쪽이 헤더를 만든 순간과 받는 순간 사이(전송·연결 시간)는 빠지지 않는다.
- 실험: A는 t=72ms에 949ms를 넘겼다(자기가 받은 뒤 쓴 약 51ms만 뺌 — 요청 시작부터 A 도착까지 약 20ms는 빠지지 않음). 그래서 C는 클라이언트보다 약 25ms(재실행 24~29ms) 늦게 멈췄다. 단계 사이에서만 확인하므로 단계 크기(100ms)만큼 더 늦을 수도 있다.
- SRE 22장: 전송 시간과 클라이언트 쪽 후처리를 감안해 나가는 데드라인을 수백 ms쯤 줄이는 것을 고려하라.

### 8. `Broken pipe` 폭주 + 하류 CPU 과다

- 의심: 계층 역전(하류 타임아웃 > 상류) 또는 데드라인 미전파. 상류가 이미 떠난 요청을 하류가 끝까지 처리하고, 응답을 쓰는 순간에야 연결이 닫힌 것을 안다.
- 확인
  - 각 홉의 타임아웃 설정값을 바깥부터 나란히 적는다.
  - 하류 처리 시간 분포 vs 상류 타임아웃.
  - 트레이스에서 상위 스팬이 끝난 뒤에 끝나는 자식 스팬.
  - "데드라인 뒤 완료" 지표.
- 대처: 정렬 + 남은 시간 전파 + 단계별 확인.

### 9. `x-envoy-expected-rq-timeout-ms`

- 이 값은 라우트 timeout(또는 `x-envoy-upstream-rq-timeout-ms`)에서 온다(Envoy router 문서). Envoy 1.39.1 소스로는 per-try가 있으면 per-try 값이고(헤징 `hedge_on_per_try_timeout`이 꺼져 있을 때), 재시도 때만 `전체 timeout - 이 Envoy 안에서 흐른 시간`으로 깎는다. 게이트웨이까지 오는 데 이미 쓴 시간을 뺀 끝에서 끝까지의 "남은" 값이 아니다.
- 35번 실험에서는 per_try_timeout 1s를 둔 라우트에서 `1000`(per-try 값)이 실렸다(Envoy 1.39.1). 이 실험에서는 세 번째 시도 때도 전체 3.5초 중 남은 시간(약 1.5초)이 per-try보다 커서 1000 그대로였다.
- 홉마다 이 값을 "남은 예산"으로 쓰면 예산이 줄지 않고 홉마다 되살아난다. 이름과 달리 "기대 처리 시간"으로 읽고, 남은 시간은 따로 전파한다.
