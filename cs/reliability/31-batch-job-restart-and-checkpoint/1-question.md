# reliability/31-batch-job-restart-and-checkpoint — 질문

## 질문

1. (왜) 청크 쓰기와 체크포인트 갱신을 **같은 트랜잭션**에 커밋해야 하는 이유는? 따로 커밋하면 어떤 두 가지 오류가 생기나?
2. (예측) 1000행(금액 합 4003)을 행마다 자동 커밋으로 옮기다 550번째 행에서 kill -9로 죽였다. 체크포인트 없이 처음부터 다시 돌리면 ledger의 행 수·합·중복 수는? 원천 ID에 유일 제약 + `ON CONFLICT DO NOTHING`을 두면?
3. (예측) 같은 일을 청크 100 + 체크포인트(같은 트랜잭션)로 하면 죽은 직후 ledger에 몇 행이 있고, 재시작은 어디서부터 몇 행을 쓰나?
4. (경계) 체크포인트와 멱등 쓰기는 각각 무엇을 보장하고 무엇을 보장하지 않나? 외부 결제 API를 호출하는 배치라면 무엇이 더 필요한가?
5. (장애 진단) kill -9 뒤 다음 실행이 "이미 실행 중"이라며 시작하지 않는다. 잡 저장소에서 무엇을 보고, 누가 무엇을 결정해야 하나? Spring Batch 6에서 이것을 줄이는 장치는?
6. (예측) 1000행 중 3행이 처리 불가라 스킵했다. 조용한 스킵과 보고하는 스킵의 데이터·상태·종료 코드는 어떻게 다른가? 금액 합계 대사로 누락을 잡을 수 있나?
7. (예측) America/New_York에서 `30 2 * * *`와 `30 1 * * *`를 robfig/cron v3로 계산하면 2026-03-08과 2026-11-01에 각각 몇 번 실행되나? 리눅스 cronie는 어떻게 다르게 처리하나?
8. (설계) 쿠버네티스 CronJob으로 일 정산을 돌린다. `timeZone`·`concurrencyPolicy`·`startingDeadlineSeconds`·`terminationGracePeriodSeconds`를 어떻게 정하고, 각 기본값이면 무엇이 위험한가?
9. (연결) 잡이 한 번 더 실행돼도 정산이 한 번만 반영되게 하려면 "잡의 정체성"을 무엇으로 잡아야 하나? Spring Batch의 JobInstance 규칙과 연결해 설명하라.
