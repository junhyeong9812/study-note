# reliability/31-batch-job-restart-and-checkpoint — 정답

## 정답

### 1. 같은 트랜잭션에 커밋하는 이유

- 둘이 한 단위로 커밋되거나 한 단위로 롤백된다. 죽은 청크는 쓰기도 체크포인트도 남지 않는다.
- 따로 커밋하면:
  - 쓰기 커밋 → 체크포인트 전에 죽음: 재시작이 그 청크를 다시 쓴다(**중복**).
  - 체크포인트 커밋 → 쓰기 전에 죽음: 재시작이 그 청크를 건너뛴다(**누락**).
- 같은 DB여야 한 트랜잭션으로 묶을 수 있다. 쓰는 곳이 다르면 멱등 쓰기로 보완한다.

### 2. 체크포인트 없이 처음부터

(실험, PostgreSQL 17 + JDK 21)

| | 죽은 직후 | 재실행 뒤 |
|---|---|---|
| 비멱등 | 549 / 2193 / 0 | **1549 / 6196 / 549** |
| 유일 제약 + `ON CONFLICT DO NOTHING` | 549 / 2193 / 0 | 1000 / 4003 / 0 |

(행 수 / 합 / 중복 src_id)

- 비멱등: 앞 549행이 두 번 정산됐다. 에러는 없다.
- 멱등: 결과는 맞다. 하지만 앞 549행을 다시 읽고 다시 시도한 비용은 그대로다.

### 3. 청크 + 체크포인트

- 죽은 직후: **500행**(합 1997). 501~549행을 쓰던 청크는 롤백됐다.
- 재시작: `체크포인트에서 재개: last_id = 500` → 500행을 써서 1000행·4003·중복 0.

### 4. 체크포인트 vs 멱등 쓰기

- 체크포인트: 어디서부터 다시 할지(속도). 체크포인트와 같은 트랜잭션 **밖**의 부수효과(외부 API·메일·파일)는 보장하지 않는다.
- 멱등 쓰기: 다시 써도 같음(정확성). 다시 읽고 다시 시도하는 비용은 줄이지 않는다.
- 외부 결제 API: 행마다 **멱등 키**(예: 정산일 + 원천 ID)를 실어 상대가 두 번째 요청을 무시하게 한다. 상대가 지원하지 않으면 "요청함" 기록을 먼저 남기고 결과를 대사하는 경로를 둔다.

### 5. STARTED 고착

- 볼 것: `batch_job_execution.status = 'STARTED'`인데 프로세스가 없다. `last_updated`가 오래됐다.
- 결정: 그 실행을 FAILED(재시작)로 볼지 ABANDONED(포기)로 볼지. Spring Batch 문서는 이것이 비즈니스 결정이며 자동화할 방법이 없다고 적는다. FAILED는 재시작 데이터가 유효하다고 알 때만.
- 실험 3도 같은 모양이었다: `거절: 직전 실행이 STARTED로 남아 있다` → 사람이 FAILED로 판정 → `last_id = 500`부터 재개.
- 줄이는 장치: Spring Batch 6.0+ `JobExecutionShutdownHook`을 JVM 종료 훅에 건다. SIGTERM에 실행을 STOPPED로 기록해 STARTED 고착을 막는다. 청크는 기다리지 않으므로 진행 중 청크는 롤백되고, 재시작이 이어 간다(v6.0.5 소스). kill -9·OOM에는 소용없다. 그때는 `JobOperator.recover` 뒤 `restart`.

### 6. 조용한 스킵 vs 보고하는 스킵

| | 데이터 | 상태 | 종료 코드 |
|---|---|---|---|
| 조용한 스킵 | 997행 | COMPLETED | 0 |
| 보고하는 스킵 | 997행 | COMPLETED WITH SKIPS, 스킵 [137, 444, 901] | 3 |

- 데이터는 같다. 다른 것은 바깥에 드러나느냐다.
- 합계 대사로는 못 잡는다. NULL 금액은 합에서 빠져 원천 합도 3988, ledger 합도 3988이었다. **행 수**(1000 vs 997)나 누락 키 조회로 잡는다.

### 7. DST 전환일

(실험, robfig/cron v3.0.1)

- `30 2 * * *`: 2026-03-07, 2026-03-09만 나온다. **3월 8일 0회**(02:30이 없는 날).
- `30 1 * * *`: 2026-11-01에 01:30 EDT와 01:30 EST, **2회**.
- cronie(man cron(8)): 3시간 미만 변경을 특별 처리한다. 앞으로 갔으면 건너뛴 시간대 잡을 바로 실행하고, 뒤로 갔으면 두 번 실행하지 않는다.
- 같은 크론 문자열이라도 스케줄러마다 결과가 다르다.

### 8. CronJob 설정

- `timeZone`: 명시한다. UTC나 DST 없는 시간대. 지역 시간대면 01~03시를 피한다.
- `concurrencyPolicy`: `Forbid`. 기본 `Allow`면 앞 실행이 안 끝났을 때 다음 회차가 겹친다.
- `startingDeadlineSeconds`: 의미 있는 마감(예: 1시간). 기본(없음)이면 마감이 없다. 문서는 놓친 회차가 100번을 넘으면 시작하지 않는다고 적는다(단, v1.34.0·master 컨트롤러 소스는 `TooManyMissedTimes` 경고만 남기고 가장 최근 회차는 시작할 수 있다). 10초 미만이면 스케줄되지 않을 수 있다(컨트롤러가 10초마다 확인).
- `terminationGracePeriodSeconds`: 청크 경계까지 폴링하며 기다리는 종료 훅을 둘 때, 청크 하나를 끝내고 STOPPED를 기록할 시간보다 길게. 기본 30초면 큰 청크는 중간에 SIGKILL된다. 기본 `JobExecutionShutdownHook`만 쓰면 청크를 기다리지 않으므로 유예를 늘려도 청크가 끝나지 않는다.
- 그래도 쿠버네티스 문서는 잡이 두 번 생기거나 안 생길 수 있다며 잡을 멱등하게 만들라고 적는다.

### 9. 잡의 정체성

- 정체성 = 잡 이름 + **정산일** 같은 식별 파라미터. "실행 시각"이 아니다.
- Spring Batch: JobInstance = Job + 식별 JobParameters. 같은 정산일로 다시 실행하면 새 JobExecution이지만 같은 JobInstance다. 그 JobInstance의 실행이 COMPLETED(또는 ABANDONED)면 런처가 `JobInstanceAlreadyCompleteException`을 던진다(spring-batch main 브랜치 `TaskExecutorJobLauncher.java`).
- 그래서 DST로 두 번 불려도, 사람이 실수로 다시 눌러도, 같은 정산일은 한 번만 완료된다. 쓰기 쪽 유일 키가 마지막 방어선이다.
