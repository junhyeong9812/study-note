# reliability/53-reliability-incidents — 정답

## 정답

### 1. 방아쇠와 길이

| 사건 | 방아쇠 | 길이를 정한 것 |
|---|---|---|
| AWS S3 2017 | 입력 하나가 잘못된 용량 제거 명령 | 수년간 완전히 재시작해 본 적 없는 색인·배치 서브시스템의 재시작과 무결성 점검 |
| Slack 2021 | 연휴 뒤 첫 업무일의 트래픽 급증 + TGW 확장 지연 | 오토스케일·프로비저닝 경로가 같은 나쁜 네트워크와 자원 한도에 막힘, 대시보드 부재 |
| Roblox 2021 | streaming 기능 확대 + 매우 높은 읽기·쓰기 부하 | 네 번 빗나간 진단, 감시의 순환 의존, 무에서 캐시·서비스를 띄우는 절차 |
| CrowdStrike 2024 | 검증기를 통과한 문제 콘텐츠(채널 파일 291) | 전 대상 동시 배포, 원격 되돌림이 닿지 않는 크래시 호스트의 수동 복구 |

- 공통(해석): 방아쇠는 작았고, 길이는 평소에 안 쓰던 복구 경로가 정했다.

### 2. S3 그림과 복구 순서

```text
  09:37 명령(입력 오류) → 의도보다 많은 서버 제거
     ├─ 색인 서브시스템: 리전 모든 객체의 메타데이터·위치, GET·LIST·PUT·DELETE 모두에 필요
     └─ 배치 서브시스템: 새 저장 공간 할당(PUT), 색인이 정상이어야 동작
  둘 다 전체 재시작 → 재시작 동안 S3 요청 처리 불가
  12:26 색인이 GET·LIST·DELETE 처리 시작 → 13:18 색인 완전 복구
  13:54 배치 복구 완료(색인이 동작한 뒤 시작) → S3 정상
```

- PUT은 배치 서브시스템도 필요하고, 배치는 색인이 동작해야 복구를 시작할 수 있었다. 그래서 순서가 색인(읽기·삭제) → 배치(쓰기)였다.
- 계산: 09:37 → 13:54는 4시간 17분.

### 3. 사람이 아니라 도구

- 원문은 "도구가 너무 많은 용량을 너무 빨리 뺄 수 있었다"를 문제로 적었다.
- 안전장치 둘: (1) 용량을 더 천천히 빼게 함, (2) 어떤 서브시스템도 최소 필요 용량 아래로 내려가지 않게 막음. 다른 운영 도구도 같은 점검을 하는지 감사.
- 같은 모양: 49번 Governor의 두 축 — 창당 상한(속도)과 남는 몫 하한([49-5](../49-steady-state-fail-fast-and-supervision/2-summary.md)). 레이트 리미터의 슬라이딩 윈도와 같은 구조다.

### 4. Governor 예측

(실행 확인, OpenJDK 21.0.12 — 출력의 처음 네 줄)

```text
요청    4 → 제거  4, 남은 용량  996  [전부 허용]
요청  400 → 제거 16, 남은 용량  980  [창당 상한(20/10분)]
요청   10 → 제거  0, 남은 용량  980  [창당 상한(20/10분)]
요청   30 → 제거  4, 남은 용량  976  [창당 상한(20/10분)]
```

- 1분의 400은 창에 남은 몫 16(20 − 4)만 허용됐다.
- 11분에는 창이 [1분, 11분]이다. 0분에 뺀 4대는 창 밖으로 나갔고, 1분에 뺀 16대는 아직 창 안이다. 남은 몫은 20 − 16 = 4다.

### 5. Slack의 오토스케일

- 초기: 네트워크 문제로 워커 스레드가 기다리느라 CPU가 떨어졌다 → CPU 신호로 **축소**. 곧 스레드 이용률이 오르자 **확장** — 07:01~07:15 PST에 1,200대 추가 시도. 해석: CPU는 "막혀 있다"를 "한가하다"로 읽었다([41-4](../41-autoscaling/2-summary.md)).
- 확장이 용량이 되지 못한 이유: (1) provision-service가 같은 나쁜 네트워크 위에서 동시 대량 프로비저닝을 하다 리눅스 open files 한도(가장 큰 것)와 AWS 할당량에 걸림, (2) 덜 구성된 인스턴스가 오토스케일 그룹 최대 크기를 채움.
- 서빙을 되살린 것: LB의 panic mode(헬스체크 실패가 많으면 모든 인스턴스에 분산) + 재시도 + 서킷 브레이킹. 09:15 PST쯤 "down이 아니라 degraded".

### 6. Slack은 metastable인가

- Bronson 외의 정의: 방아쇠가 나쁜 상태를 만들고, **방아쇠를 없애도** 지속 효과가 그 상태를 붙잡는 장애([distributed/36](../../distributed/36-distributed-incidents/2-summary.md)).
- 원문 사실: 방아쇠인 TGW 포화는 AWS가 10:40 PST에 용량을 수동으로 늘려 모든 AZ에 반영할 때까지 남아 있었다. 그 전 09:15에 이미 degraded로 서빙했다.
- 판단(해석): 교체·확장이 부하를 키운 되먹임은 있었지만, 방아쇠가 사라진 뒤에도 장애가 남았다는 증거가 원문에 없다. 원문만으로는 metastable로 단정할 수 없다.

### 7. Roblox 진단과 원인

| 시도 | 가설 | 결과 |
|---|---|---|
| 1 | 하드웨어 저하 → 노드 하나 교체 | 효과 없음 |
| 2 | 트래픽 한계 → 전 노드를 128코어·NVMe로 | 여전히 KV 쓰기 p50 약 2초 |
| 3 | 수천 컨테이너의 재연결 폭주 → 비필수 사용 끄기, 서비스 축소, 헬스체크 60초 → 10분 | 부하가 훨씬 적은데도 다시 비정상 |
| 4 | 128코어가 경합 악화 → 64코어로 되돌림 | 효과 없음 |

- 효과가 없던 이유(해석): 장비·부하 크기가 아니라 소프트웨어 안의 경합과 자료 구조가 원인이었다. 측정(perf·플레임 그래프)으로 찾았다([36-1](../36-profiling/2-summary.md)).
- 근본 원인 둘(원문)
  - streaming: 롱 폴링보다 동시성 제어 요소(Go 채널)를 적게 써서, 읽기·쓰기 모두 높은 부하에서 Go 채널 하나에 경합이 몰려 쓰기가 막혔다. 10-30 15:51 streaming 끄기 전파 → KV 쓰기 p50 300ms.
  - BoltDB freelist: 4.2GB 로그 저장소에 실데이터 489MB, 빈 공간 3.8GB. freelist 7.8MB(빈 페이지 ID 거의 100만 개). 16kB 이하를 붙이는 Raft 쓰기마다 7.8MB freelist를 새로 씀. 압축으로 해결, bbolt로 교체 예정.

### 8. Roblox 경과 시간

- 계산(10-28 13:37 기준): 04:00 14.4시간("14시간 넘게" — 맞음), 16:00 26.4시간("24시간 넘게" — 맞음), 10-30 20:00 54.4시간("54시간" — 맞음), 10-31 05:00 63.4시간(원문 "61시간"), 16:45 75.1시간(원문 "73시간").
- 16:35(플레이어 50% 하락) 기준이면 16:45가 72.2시간이다. 원문은 기준 시각을 밝히지 않는다.
- 적는 법: 원문 수치("73시간")는 그대로 인용하고, 원문 시각으로 계산한 값은 "계산"으로 따로 적는다. 어느 쪽이 맞다고 단정하지 않는다.

### 9. CrowdStrike

- 21과 20: IPC Template Type 정의는 입력 필드 21개, 센서 통합 코드가 넘긴 입력은 20개. Content Validator는 21개를 기대하고 검사했다.
- 시험이 못 잡은 이유: 자동 시험(정적 사례 12개)의 채널 파일과 3~4월 운영 Template Instance가 21번째 필드에 와일드카드를 썼다. 와일드카드면 21번째를 읽지 않아 범위 밖 읽기가 드러나지 않았다. 7-19 Instance가 21번째에 와일드카드 아닌 조건을 넣자 21번째를 읽었다 → 범위 밖 읽기 → 크래시.
- 복구가 길었던 이유
  - 원문 사실: 채널 파일은 호스트 디스크에 쓰인다(PIR). 커널 드라이버는 부팅 초기에 올라온다(RCA). Microsoft가 수동 복구 문서·스크립트를 냈다(7-20). CrowdStrike는 7-25에 97% 넘게 온라인이라고 밝히며 자동 복구 기법 개발을 들었다(CEO 게시, TechTarget 보도 인용). 8-06자 RCA는 "7-29 17:00 PT 기준" 업데이트 전 대비 약 99%(평소 주간 변동 약 1%)라고 적는다. 99%에 처음 닿은 시각은 원문에 없다.
  - 해석: 이미 크래시한 호스트는 원격 되돌림이 닿기 전에 디스크의 문제 파일을 다시 읽을 수 있어, 초기에는 호스트마다 수동 조치가 필요했다. 이후 자동 복구 기법이 더해졌다. "롤백 가능"은 롤백 명령이 닿는 대상에서만 성립한다.
- 배포 쪽 조치(원문): Rapid Response Content도 카나리부터 점점 큰 링으로, 링마다 bake 시간과 원격 측정 판정 뒤 다음 링 또는 되돌림. 고객이 어디에·언제 받을지 선택.
