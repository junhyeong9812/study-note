# reliability/12-backpressure-and-load-shedding — 정답

## 정답

### 1. 처리량 vs goodput

```text
 t=0s   대기   0ms → 응답 쓸모 있음
 t=0.5s 대기 250ms → 아슬아슬
 t=1s   대기 500ms → 클라이언트는 300ms에 포기. 서버는 계속 처리(헛일)
 t=3s   대기 1.5s  → 처리하는 것 전부가 헛일
 처리량 ≈ 200/s 유지 · goodput → 0
```

- 처리량: 서버가 끝낸 요청 수. 클라이언트가 이미 떠난 요청도 센다.
- goodput: 클라이언트가 아직 기다리는 동안(데드라인 안에) 끝난 요청 수.
- 도착률이 처리율을 넘는 상태가 이어지면 무한 큐의 대기가 계속 늘어, 어느 시점부터는 처리하는 응답이 전부 데드라인 뒤에 나간다. 실험의 FIFO_UNBOUNDED: `처리 1500`, `초당 goodput: 162 0 0 0 0 0 0 0`.

### 2. 큐 한도 계산

- 처리율 = 16 / 0.05s = 320/s. 큐가 가득 찬 동안 큐에 들어가는 비율 λ도 이 처리율과 같다(나가는 만큼만 들어간다).
- 리틀의 법칙 L = λW → W = L / λ = 160 / 320 = 0.5초. 처리 50ms를 더하면 약 550ms.
  - 조건: 과부하가 이어져 큐가 계속 가득 찬 상태라 평균 L ≈ 160이다. 그래서 0.5초는 **평균** 대기다. 처리 시간이 흔들리거나 작업자가 멈추면 개별 요청은 이보다 오래 기다릴 수 있다.
- 데드라인 500ms보다 길다. 큐가 가득 찬 순간 들어온 요청은 처리해도 헛일이다. 부적절하다.
- 상한은 (500 − 50)ms × 320/s = 144 미만이다. SRE 22장은 꾸준한 트래픽이면 큐를 스레드 수의 50% 이하(여기서는 8 이하, 대기 약 25ms)로 두라고 권한다.

### 3. 무한 FIFO vs 유계 큐

(실험, JDK 21, `--cpus=2`)

| 정책 | 입장 거절 | 처리 | 데드라인 안 성공 | 처리된 요청 p99 |
|---|---|---|---|---|
| FIFO 무한 | 0 | 1500 | 162 (11%) | 2594ms |
| FIFO 유계 40 | 472 | 1028 | 1028 (69%) | 212ms |

- 유계 큐가 6배 이상 많다. 472개를 즉시 거절한 대신 받은 것을 모두 제때 끝냈다.

### 4. "이미 지난 것만" 버리기

- goodput은 거의 오르지 않는다(실험 FIFO_DEADLINE_DROP: 168, 무한 FIFO 162).
- 이유: 큐 대기가 데드라인 경계에 서게 된다. 꺼낼 때는 아직 데드라인 전이지만 처리 10ms를 더하면 넘는다. 처리된 요청 p50이 308ms였다.
- 고친 기준: **남은 예산 < 예상 처리 시간**이면 버린다. 실험 FIFO_BUDGET_DROP의 goodput은 1030이었다.
- 더 근본적으로는 큐를 짧게 두어 대기 자체를 줄인다.

### 5. 역압 vs 셰딩

| | 잃는 것 | 지키는 것 |
|---|---|---|
| 역압 | 생산자의 속도(생산자가 느려지거나 기다린다) | 모든 항목(버리지 않는다) |
| 셰딩 | 일부 요청(거절·폐기) | 나머지 요청의 지연, 서버의 생존 |

- 인터넷 사용자는 서버가 늦추라고 해서 늦춰지지 않는다. 신호를 받아 줄 생산자가 없으니 맨 앞에서는 결국 거절(셰딩)이 필요하다.
- 역압은 신호를 끝까지 전파할 수 있는 내부 파이프라인(큐·스트림·TCP)에서 쓴다. 중간에서 흡수하면 그 자리에 큐가 다시 생긴다.

### 6. CoDel과 적응형 LIFO

- CoDel은 큐 **길이**가 아니라 항목의 **체류 시간**을 본다.
- 체류 시간이 TARGET(기본 5ms)보다 INTERVAL(기본 100ms) 동안 계속 크면 버리기 시작한다. 그 뒤 버리는 간격을 `INTERVAL / sqrt(count)`로 줄인다(RFC 8289 §4.2·§4.3·§5).
- 짧은 버스트는 그대로 두고 오래 서 있는 큐만 줄인다.
- 적응형 LIFO(Maurer 2015)는 큐가 생기면 최신 요청부터 처리한다. CoDel 쪽이 짧은 타임아웃으로 긴 큐를 막고, LIFO가 새 요청을 앞에 두어 그 타임아웃 안에 끝날 확률을 높인다. 실험의 ADAPTIVE_LIFO_CODEL은 처리된 요청 p50 12ms, goodput 984였다.

### 7. 결제를 지키는 입장 판정

```text
 큐 사용률     0% ────── 50% ────── 100%
 추천(SHEDDABLE)  받음 │ 거절
 조회(SHEDDABLE_PLUS) 받음 ───── 75% │ 거절   (예시 임계)
 결제(CRITICAL)   받음 ──────────────── │ 거절
```

- 중요도는 사용자 가까운 곳(HTTP 프런트엔드)에서 정하고 RPC로 하위 호출에 전파한다. 하위 서비스도 같은 등급으로 셰딩해야 결제 경로가 깊은 곳에서 버려지지 않는다(SRE 21장).
- 과부하 태스크는 낮은 등급부터 거절한다. 실험 PRIORITY_SHED: 중요 요청 `302/302` 성공(우선순위 없는 유계 큐는 `206/302`).
- 결제 용량은 CRITICAL 트래픽을 전부 감당하게 미리 확보한다(SRE: CRITICAL·CRITICAL_PLUS는 다 처리할 용량을 둔다).

### 8. 거절이 재시도 폭풍을 부를 때

- 원인: 클라이언트가 거절을 즉시 재시도한다. 거절 응답을 만드는 비용도 공짜가 아니어서, 거절이 많으면 백엔드가 거절만 하다가 과부하된다(SRE 21장).
- 대처 1 — 적응형 스로틀링: 클라이언트가 지난 2분의 `requests`·`accepts`를 세고, 로컬 거절 확률 `max(0, (requests − K × accepts) / (requests + 1))`로 백엔드에 보내기 전에 실패시킨다. K는 보통 2.
- 대처 2 — 재시도 예산(SRE 21장 예: 재시도로 약 3X까지 늘던 요청이 클라이언트당 10% 예산으로 1.1X), 지수 백오프·지터, `Retry-After` 존중.

### 9. 헬스체크까지 셰딩

- 헬스체크 요청이 일반 요청과 같은 큐·같은 입장 판정을 탔다. 과부하 인스턴스가 헬스체크를 거절 → 로드 밸런서가 제외 → 남은 인스턴스 부하 증가 → 같은 일이 반복된다. SRE 22장은 헬스체크 실패가 크래시와 비슷한 효과로 눈덩이를 만든다고 적는다.
- 막는 법: 헬스체크·관리 요청은 별도 경로(별도 포트·스레드, 최고 중요도)로 처리한다. "과부하라 일부 거절 중"과 "죽었다"를 구분해 보고한다. 회복할 때는 트래픽을 용량보다 훨씬 낮게 줄였다가 점진적으로 되돌린다.
