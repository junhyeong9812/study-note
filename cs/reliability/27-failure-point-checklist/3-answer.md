# reliability/27-failure-point-checklist — 정답

## 정답

### 1. 점검 절차가 필요한 이유

- 지식은 있어도 바쁠 때 경로의 한 칸만 보고 답하거나 설계한다. 빠진 칸은 아무도 묻지 않아 알려진 실패가 그대로 들어간다. 회고의 교훈도 절차로 옮기지 않으면 사람 기억에만 남는다.
- SRE 27장: 항공 비행 전 점검표와 수술 점검표를 예로 들며, 점검표는 실패를 줄이고 일관성·완전성을 준다고 적는다.

### 2. 경계 그림

```text
 사용자 ─①─> 게이트웨이 ─②─> 서비스 A ─③─> DB
                               ├─④─> 서비스 B
                               ├─⑤─> 브로커 ─⑥─> 소비자 ─⑦─> 하위 저장소
                               └─⑧─> 외부 PG
```

- 경계는 프로세스·네트워크·트랜잭션이 바뀌는 곳이다. 한쪽의 고장이 다른 쪽의 결함으로 넘어가는 자리라 실패가 여기서 생긴다. 경계를 빠짐없이 세야 질문도 빠지지 않는다.

### 3. 여섯 질문과 카탈로그

| 질문 | 카탈로그 |
|---|---|
| 느림: 얼마나 기다리나, 포기하면 하위도 멈추나 | F-16 타임아웃 계층 역전 |
| 실패: 재시도는 몇 층·상한·예산 | F-09 재시도 폭풍 |
| 모름: 응답 유실 때 상대 처리 여부 | F-20 이중 결제, F-10 |
| 중복·순서 | F-11 중복, F-12 순서 역전 |
| 용량·편중 | F-03 커넥션 풀 고갈, F-19 핫스팟 |
| 알기: 조용히 틀리면 누가 아나 | F-25 조용한 실패, F-21 대사 |

### 4. 칸 1 실험

- 이중 쓰기: 유실 87, 중복 0. 아웃박스: 유실 0, 중복 89(브로커 도착 10,089, 서로 다른 것은 10,000).
- 칸 1을 아웃박스로 닫으면 유실 대신 중복이 생기고, 그 중복은 칸 4(소비 쪽 멱등)가 받아야 한다. 칸 하나의 해법이 다음 칸의 짐을 만든다.

### 5. 칸 4 실험

- 처리 전 커밋: 누락 88, 중복 0. 처리 후 커밋: 누락 0, 중복 88. 처리 후 커밋 + 멱등: 0, 0.
- 커밋 위치는 **유실과 중복**을 맞바꾼다. 중복은 멱등(유니크 제약)으로 흡수할 수 있으니 처리 후 커밋 + 멱등을 고른다.

### 6. 자동 커밋

- 그 자체로 처리 전 커밋은 아니다. Javadoc(4.1): 자동 커밋도 at-least-once가 될 수 있지만, 각 `poll()`이 돌려준 데이터를 다음 `poll()`이나 close 전에 다 소비해야 한다. 그러지 않으면(예: 처리를 다른 스레드로 넘김) 커밋된 오프셋이 소비 위치를 앞질러 레코드를 놓칠 수 있다.

### 7. acks=all인데 유실

- Kafka 4.1 기본 `min.insync.replicas=1`이면, ISR이 리더 하나로 줄어든 상태에서도 `acks=all` 쓰기가 성공한다. 그 메시지가 다른 복제본에도 있다는 보장이 없으므로 그 리더가 영구 고장 나면(디스크 유실 등) 사라질 수 있다(실제 유실 여부는 다른 복제본이 받아 두었는지와 복구 과정에 달렸다. Kafka 설계 문서 "these writes could be lost if the remaining replica also fails"). 기본 `unclean.leader.election.enable=false`에서 리더가 일시 장애면 유실 대신 파티션이 멈춘다.
- 브로커 칸 질문: 복제 수, `min.insync.replicas`(복제 3이면 2 등), `unclean.leader.election.enable`(기본 false), 보존 기간 vs 소비자 최대 지연. 설정 조회 결과를 점검 기록에 붙인다.

### 8. 점검표 운영 규칙(SRE 27장)

1. 질문마다 구체적인 할 일과 방법 링크를 붙인다.
2. 질문의 중요성은 근거로 입증한다 — 이상적으로는 과거 출시 사고로.
3. 길이를 관리한다(한때 새 질문에 부사장 승인, 연 1~2회 전체 재검토로 낡은 항목 삭제).
4. 공용 인프라로 수렴시켜 여러 항목을 한 줄("시스템 X를 써라")로 바꾼다.

- 연결: 사고가 나면 회고 → 카탈로그 항목 → 근거가 붙은 점검 질문 → 할 일 → 공용 장치로 옮긴다. 그러면 다음 출시에서 같은 질문이 자동으로 나와 알려진 실패 모드가 재발하지 않는다.

### 9. 조용한 적립 누락

- 원인: 처리 완료 전에 오프셋이 커밋됐다. 별도 스레드 풀로 처리를 넘기면, 자동 커밋이 다음 `poll()`에서 아직 처리 중인 레코드의 오프셋까지 커밋할 수 있다(Javadoc 조건 위반). 재시작 때 그 레코드는 다시 오지 않는다(실험: 처리 전 커밋 누락 88).
- 대처: 자동 커밋을 끄고 **처리가 끝난 오프셋까지만** 수동 커밋, 처리에 이벤트 ID 유니크 제약(멱등). 이때 이벤트 ID 기록과 적립 반영은 **같은 DB 트랜잭션**으로 커밋하고, 그 뒤에 오프셋을 커밋한다. ID만 먼저 기록하고 적립 전에 죽으면 재전달을 중복으로 보고 건너뛰어 누락이 된다. 외부 PG 같은 다른 시스템의 효과는 그쪽 멱등 키가 따로 필요하다. 누락을 찾는 대조(원천 이벤트 수 vs 적립 수)를 칸 5에 둔다.

### 10. "유실을 어떻게 막았나요?"

- 첫 문장: 범위 되짚기 — "말씀하신 게 발행 전·발행 중·브로커·소비 중·소비 후 중 어느 칸인지, 전 구간인지 확인하고 답하겠습니다"(원본 되짚기 습관).
- 전 구간이면 5칸을 순서대로: 칸 1 아웃박스(→ 중복이 생김), 칸 2 `acks=all`·멱등 프로듀서, 칸 3 복제·`min.insync.replicas`·unclean 선출 금지·보존 기간, 칸 4 처리 후 커밋 + 유니크 제약(적립과 같은 트랜잭션) + DLQ, 칸 5 멱등 upsert·대사. 열어 둔 칸이 있으면 이유를 말한다.
