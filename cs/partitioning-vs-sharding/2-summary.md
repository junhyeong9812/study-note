```text

차이     파티셔닝 = 논리적으로 하나인 테이블을 같은 DB 인스턴스 안에서 물리적으로 쪼갬
         샤딩     = 수평 파티셔닝을 여러 독립 DB 서버에 걸쳐 적용 — 각 샤드는 전체의 일부만 가진 독립 인스턴스
```

## 1. Partitioning(파티셔닝)

파티셔닝은 하나의 큰 테이블이나 데이터베이스를 더 작은 단위(파티션)로 나누는 기법이다.
핵심은 논리적으로 하나의 테이블이지만 물리적으로 분할해서 저장한다는 점이고, 보통 같은 데이터베이스 인스턴스(서버) 안에서 이뤄진다.

파티셔닝 방향성

- 수평 파티셔닝(Horizontal Partitioning):
  - 행(row) 기준으로 나누는 방식이다.
  - 예시) 주문 테이블을 날짜 기준으로 2024년 파티션, 2025년 파티션으로 나누는 방식으로, 스키마는 동일하고 담긴 데이터만 달라진다.
  - 분할 기준에 따라 Range(범위), List(목록), Hash(해시) 파티셔닝으로 세분화된다.
- 수직 파티셔닝(Vertical Partitioning)
  - 열(column) 기준으로 나누는 방식이다.
  - 자주 조회되는 컬럼(이름, 이메일)과 드물게 조회되는 대용량 컬럼(프로필 소개글, 이미지)을 별도 테이블로 분리하는 식이다.
  - 정규화와 비슷해 보이지만, 이미 정규화된 테이블을 성능 목적으로 더 쪼갠다는 점이 다르다.

파티셔닝의 장점

- 쿼리 성능 향상(파티션 프루닝으로 필요한 파티션만 스캔)
- 오래된 데이터의 손쉬운 삭제/아카이빙, 관리 편의성

파티셔닝의 단점

- 파티션 키를 잘못 잡으면 오히려 성능이 나빠진다.
- 조인이나 파티션 간 쿼리가 복잡해질 수 있다는 점이다.

## 2. Sharding(샤딩)

샤딩은 데이터를 여러 개의 독립적인 데이터베이스 서버(샤드)에 분산 저장하는 기법이다.
본질적으로는 수평 파티셔닝을 여러 물리 서버에 걸쳐 적용한 것이라고 볼 수 있다.
각 샤드는 독립적인 DB 인스턴스이고, 전체 데이터의 일부만 가지고 있는다.

예시) 유저 ID가 1~100만인 사용자는 shard A에, 100만~200만은 shard B에 저장하는 식이다.
분산 방식으로는 Hash 기반(샤드 키를 해싱해서 배정), Range 기반(범위별 배정), Directory 기반(별도 매핑 테이블로 관리) 등이 있다.

샤딩의 가장 큰 목적은 **스케일 아웃(수평 확장)**이다.
단일 서버의 저장 용량, CPU, 메모리, 커넥션 한계를 넘어설 수 있고, 부하가 여러 서버로 분산된다.

단점이 생각보다 커서 도입 시 신중해야 된다.

- 샤드 간 조인이 사실상 불가능하거나 매우 비싸다.
- 트랜잭션을 여러 샤드에 걸쳐 보장하기 어렵다.
- 특정 샤드에 데이터가 몰리는 핫스팟 문제
- 샤드 추가 시 리밸런싱(재분배) 비용 등이 대표적이다.

## 핵심 문장

- 파티셔닝은 "한 DB 인스턴스 안에서 물리적으로 쪼갬", 샤딩은 "여러 독립 DB 서버로 쪼갬" — 경계는 인스턴스다.
- 파티셔닝의 이득은 프루닝과 관리이고, 샤딩의 이득은 스케일 아웃이다. 목적이 다르다.
- 샤딩은 샤드 간 조인·트랜잭션이 어려워지는 대가로 확장을 산다. 핫스팟·리밸런싱도 대표 단점이다.
- 수직 파티셔닝은 정규화가 아니라 이미 정규화된 것을 성능 목적으로 더 쪼개는 것이다.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 내용이다. 복습 대상은 1~2절이고, 이 절은 확장 읽을거리다.

### A. 한 표로 비교

```text
                 Partitioning                    Sharding
나누는 곳        같은 DB 인스턴스 안              여러 독립 DB 서버
논리적 모습      하나의 테이블 (DB가 투명하게)     애플리케이션/미들웨어가 어느 샤드인지 알아야 함
주 목적          쿼리 성능·관리                  스케일 아웃
조인·트랜잭션    DB 안에서 그대로 됨              샤드를 넘으면 어렵거나 불가
확장 한계        단일 서버의 한계 그대로           서버 수만큼
```

### B. 연결 — Kafka의 파티션은 어느 쪽인가

Kafka의 "파티션"은 이름은 파티션이지만 동작은 샤딩에 가깝다 — 각 파티션이 다른 브로커에 놓이고, 파티션 간 순서·조인이 없고, `hash(key) % N`으로 배정하며, 파티션 수를 늘리면 기존 key의 배정이 깨진다(리밸런싱 비용). 샤딩의 단점 목록(핫스팟, 리밸런싱)이 그대로 Kafka 파티션 설계 주의사항에 다시 나온다(→ [kafka-why-fast](../kafka-why-fast/) §4).

### C. 파티셔닝 전략별 hot spot 위험

- **Range**: 시간·ID 순 범위. 프루닝과 오래된 파티션 drop에 최적이지만, 최신 범위에 쓰기가 몰린다(시계열의 "마지막 파티션 핫스팟").
- **Hash**: 고르게 퍼지지만 범위 쿼리는 모든 파티션을 훑고, 파티션 수를 바꾸면 전체 재배치.
- **List**: 지역·상태 같은 이산값. 값별 데이터량이 불균형하면 큰 값 하나가 핫스팟.
- **Composite**(예: Range → Hash): 시간으로 자른 뒤 해시로 다시 나눠 범위 프루닝과 쓰기 분산을 함께 노린다.

### D. 샤드 키는 왜 바꾸기 어려운가 — resharding

- 샤드 키는 "대부분의 쿼리가 키 하나로 샤드 1개에 떨어지는가 + 쓰기가 고르게 퍼지는가"로 고른다. 두 조건은 종종 충돌한다(유저 ID는 조회에 좋지만 유명 유저가 핫스팟).
- 키를 바꾸거나 샤드를 추가하면 데이터가 물리적으로 이동해야 하므로, 단순 `hash % N`은 N이 바뀔 때 대부분의 키가 재배치된다. **Consistent hashing**은 이동량을 1/N 수준으로 줄이고, **virtual node**로 노드별 편차를 완화한다.
- Vitess·CockroachDB·TiDB 류는 데이터를 작은 range 단위로 쪼개 두고 크기·부하에 따라 자동 분할·이동시켜 resharding을 운영 작업이 아닌 상시 동작으로 만든다.

### E. 샤딩이 깨뜨리는 것 — 조인·트랜잭션·유니크

- **cross-shard JOIN**: 애플리케이션에서 두 번 조회해 합치거나(scatter-gather), 자주 조인하는 데이터를 같은 샤드에 두도록 키를 설계(co-location)하거나, 작은 테이블을 모든 샤드에 복제한다.
- **cross-shard 트랜잭션**: 2PC는 조정자 장애 시 블로킹되고 느리다. 대안은 saga(보상 트랜잭션)로 결과적 일관성을 받아들이는 것.
- **유니크 제약·auto-increment**: 샤드마다 따로 보장되므로 전역 유니크는 별도 ID 발급(Snowflake 류·UUID·샤드 접두사)이 필요하다.

### F. DB별 용어 차이

- **PostgreSQL**: 선언적 파티셔닝(`PARTITION BY RANGE/LIST/HASH`) — 한 인스턴스 안. 여러 서버로 넘기려면 Citus 같은 확장이 "distributed table"로 샤딩한다.
- **MongoDB**: shard = 서버(레플리카 셋), 그 안의 데이터 조각은 chunk. chunk를 shard 사이로 옮기는 것이 balancer.
- **Kafka**: partition이 곧 분산 단위(B절). "파티션"이라는 이름이지만 서버 간 분산이라 샤딩 성격.
- 용어는 제품마다 다르니 "같은 인스턴스 안인가, 서버를 넘는가"로 번역해서 읽는 것이 안전하다.
