# domain-modeling/02-pojo-and-persistence-ignorance — 정답

## 정답

### 1. 두 종류의 의존

- 컴파일 의존: `@Entity`·`@Id` 같은 어노테이션. `jakarta.persistence` jar가 없으면 컴파일이 안 된다(실험: `symbol: class Entity` 오류). 규칙의 의미는 바뀌지 않는다.
- 실행 의미 의존: 프록시·지연 로딩·더티 체킹. 같은 도메인 메서드가 세션 안/밖에 따라 성공·실패하고(지연 컬렉션 예외), 비교 결과가 달라지고(프록시 equals), 저장 호출 없이 DB가 바뀐다(더티 체킹).
- 후자가 더 깊다. 규칙 테스트를 하려면 저장 기술을 띄워야 하고, 테스트 결과가 저장 기술의 상태에 따라 달라진다.

### 2. POJO의 유래

- Fowler bliki "POJO"(2003-12-08): Rebecca Parsons, Josh MacKenzie, Fowler가 2000년 9월 컨퍼런스 발표를 준비하며 만들었다.
- 맞선 대상: 엔티티 빈(EJB)에 업무 로직을 넣던 방식. 주장은 "평범한 자바 객체에 업무 로직을 담자"였다.
- 그래서 POJO의 기준은 형태(getter·setter)가 아니라 프레임워크에 묶이지 않음이다. getter·setter는 JavaBean 규약이고, 로직 없는 데이터 덩어리는 POJO의 원래 취지와 반대다.

### 3. 엔티티 요구사항 (Hibernate 6.6 가이드 §3.4)

- Jakarta Persistence: public 또는 protected 인자 없는 생성자, 클래스·영속 필드·메서드 final 금지, 필드 접근이면 접근자 불필요(프로퍼티 접근일 때만 접근자가 public·protected), 클라이언트는 필드가 아닌 메서드(접근자 또는 업무 메서드)로 상태를 본다(명세 §2.1·§2.2).
- Hibernate 6.6: 인자 없는 생성자는 필요하지만 public·protected·package 모두 가능(런타임 프록시를 쓰려면 최소 package). final 클래스도 저장은 되지만 지연 로딩용 프록시를 만들 수 없다. getter·setter를 요구하지 않고 필드 직접 접근도 된다.
- 다른 지점: 생성자 가시성, final 허용 여부, 프로퍼티 접근 때 접근자 가시성.

### 4. 프록시 실험 결과

- `getClass()` 이름: `Customer$HibernateProxy`(하위 클래스).
- 필드 `customer.id`: `null`. `customer.getId()`: `1`.
- `getClass()` 비교 equals: `false`. `instanceof` + 필드 접근: `false`. `instanceof` + getter: `true`.
- 이유: 클래스가 다르고, 프록시의 필드는 비어 있다. `Hibernate.initialize` 뒤에도 필드는 `null`이었다(초기화는 별도 실제 객체를 채우고 프록시는 호출을 넘긴다). getter 호출은 프록시가 가로채 식별자를 돌려준다.

### 5. 더티 체킹

- 커밋 뒤 DB `status`는 `APPROVED`.
- 동작: 더티 체킹. 엔티티를 읽을 때 값의 스냅숏을 저장해 두고, flush(커밋 직전) 때 현재 값과 비교해 바뀐 엔티티에 UPDATE를 낸다(기본 설정 기준. 바이트코드 향상의 in-line dirty tracking이면 엔티티가 바뀐 속성을 직접 기록한다).
- 관리 상태 엔티티라면 도메인 메서드나 setter 호출만으로 저장된다.

### 6. 세션 밖 지연 로딩

- 원인: 트랜잭션(세션)이 끝난 뒤 지연 컬렉션·프록시에 처음 접근했다. 이벤트 리스너가 커밋 뒤나 다른 스레드에서 돈다.
- 대처
  - 도메인 메서드 호출을 트랜잭션 경계 안으로 옮긴다.
  - 필요한 연관을 조회 시점에 함께 읽는다(fetch join·엔티티 그래프).
  - 리스너에는 엔티티 대신 필요한 값(id·DTO)을 넘기고, 리스너가 자기 트랜잭션에서 다시 읽는다.

### 7. 세 선택

- 도메인 = JPA 엔티티: 비용은 ORM 규약(생성자·final·프록시)이 설계에 스며드는 것. 대부분의 스프링 서비스, 매핑 코드를 따로 둘 만큼 복잡하지 않을 때.
- `orm.xml` 매핑: 도메인 클래스에 어노테이션이 없다. 비용은 매핑이 코드와 떨어져 함께 고쳐야 하는 것. 도메인 jar를 저장 기술 없이 배포·재사용할 때.
- 모델 분리: 순수 도메인 + 영속 모델 + 매퍼. 비용은 매퍼·중복 필드·변환 테스트. 도메인이 복잡하고 저장 구조가 크게 다를 때.
- 공통 기준: 규칙을 `new`로 만든 객체로, 저장 기술 없이 테스트할 수 있어야 한다.

### 8. final·생성자 제거의 결과

- 인자 없는 생성자가 없으면 조회에서 `org.hibernate.InstantiationException: No default constructor for entity '<이름>'`(실험 4).
- final 클래스면 지연 로딩용 프록시를 만들 수 없다(가이드 §3.4.2). 연관을 매번 즉시 읽게 돼 성능 문제가 생길 수 있다(점검 재실행: `final` 엔티티로 가는 `@ManyToOne(LAZY)`가 조회 직후 이미 초기화된 실제 객체였다).
- 대처: `protected` 인자 없는 생성자를 두고 외부 생성은 검증하는 생성자·팩토리로만 연다. 불변이어야 하는 개념은 엔티티가 아닌 값 객체(`@Embeddable`)로 뺀다.

### 9. 경과 시간 차이와 해석

- 3회 실행: `new` 객체로 0.78~1.44 ms, `SessionFactory` 기동 포함 3808~4117 ms(같은 조건 재실행 3회는 0.72~0.87 ms vs 4294~4656 ms).
- 주의: `--cpus=2` 제한 컨테이너, 첫 실행(JIT 전)·H2 인메모리 값이다. 실행마다 다르다. 다른 환경(스프링 컨텍스트, 실제 DB)에서는 숫자가 달라진다. 차이가 수천 배 자릿수라는 것만 본다.
