# domain-modeling/08-domain-services-and-policies — 정답

## 정답

### 1. 이체는 "물건"이 아니다

- 어색한 점: `A.transferTo(B)`는 A가 B의 상태까지 바꾼다. 이체의 주인이 A인지 B인지 흐려지고, 환율 같은 외부 정보도 계좌가 알아야 한다.
- 『DDD Reference』 Services: 엔티티·값 객체의 자연스러운 책임이 아닌 중요한 과정·변환은 **서비스로 선언한 독립 인터페이스**로 모델에 넣는다.
  - 서비스 계약(상호작용에 대한 단언)을 정의하고, 바운디드 컨텍스트의 유비쿼터스 언어로 적는다.
  - 서비스에 이름을 주고, 그 이름도 유비쿼터스 언어가 된다.

### 2. 세 계층의 서비스

| 계층 | 이체 예에서 하는 일 |
|---|---|
| 애플리케이션 | 요청 해석, 트랜잭션 시작, 리포지토리로 계좌 로드, 도메인 서비스 호출, 알림 요청 |
| 도메인 | `from.withdraw` → `to.deposit` 조율, 환율 적용(도메인 인터페이스로) |
| 인프라 | 환율 API 클라이언트, 이메일 발송 |

- Fowler가 인용한 원칙: 애플리케이션 계층은 **얇게** 유지되고, 업무 규칙이나 지식을 담지 않으며, 작업을 조율해 아래 도메인 객체들에 위임한다.
- 참고: Evans 5장의 서비스 계층 구분 예시 자체는 본문을 열지 못해 `[?]`로 두었다.

### 3. 우회 경로

- 실험 A 출력
  - 비대한 서비스: transfer → 100(막힘), fee → **−50**, admin → **−50**. 음수가 된 경로 2/3.
  - 엔티티 규칙: 세 경로 모두 100. 0/3.
- 이유: 규칙이 한 서비스에만 있으면 같은 엔티티를 고치는 다른 서비스는 그 규칙을 모른다. 엔티티 메서드에 두고 setter를 닫으면, 상태를 바꾸는 경로가 그 메서드를 지나야 한다(리플렉션·직접 SQL 같은 우회는 별도로 막아야 한다).

### 4. 좋은 서비스의 세 특징

1. 연산이 엔티티·값 객체의 자연스러운 일부가 아닌 도메인 개념과 관련된다.
2. 인터페이스가 도메인 모델의 다른 요소로 정의된다.
3. 연산이 상태를 갖지 않는다.

- (Evans 5장, Goodreads 독자 발췌로 확인.)
- 상태를 가지면: 서비스는 보통 싱글턴으로 공유되므로 요청 사이에 상태가 새거나 동시성 문제가 생길 수 있다. 결과가 호출 순서에 기대게 되어 테스트가 어렵다(해석).

### 5. 분기 누락

- if 방식: 컴파일·실행이 통과하고 틀린 안내가 나온다 — `SUB d10 → 수수료 3000 | 안내: 7일 이내 무료 환불, 이후 10%`. 오류 없음.
- 정책 방식: 컴파일 오류 — `SubscriptionRefundPolicy is not abstract and does not override abstract method notice() in RefundPolicy`.
- 추가로, 규칙을 넣기 전의 v1에 `SUB` 주문을 넣으면 if 방식은 `else`로 흘러 `수수료 900`을 조용히 계산했고, 정책 방식은 `정책 없음(등록 누락)`으로 드러났다.

### 6. 반대 측면

- diff는 if 방식이 작았다. 시나리오 1(분기 한 곳): `Main` 포함 +3−1 vs +7−2. 시나리오 2(두 곳): +3 vs +7−1.
- 반례의 뜻: 정책 객체는 파일·간접 계층을 늘린다. 분기가 한 곳뿐이고 잘 안 바뀌면 if/switch가 더 싸다.
- 꺼내는 시점: 같은 분기가 두 곳 이상 흩어지거나, 유형이 자주 늘어 누락 위험이 생길 때. 이득은 줄 수가 아니라 누락을 컴파일러가 잡는 것이다. `sealed` 인터페이스 + default 없는 `switch`로도 같은 효과를 낼 수 있다.

### 7. 정책 등록 누락

- 원인: 새 유형은 추가됐는데 조립 지점(`Map<유형, 정책>`·DI 등록)에 정책을 넣지 않았다. 조회 결과 `null`을 그대로 썼다.
- 대처
  - 조회를 `Optional.ofNullable(map.get(t)).orElseThrow(() -> new IllegalStateException("정책 없음: " + t))`로 바꿔 원인이 메시지에 보이게 한다.
  - 테스트: `for (ProductType t : ProductType.values()) assertNotNull(policies.of(t))`. `EnumMap`을 쓰면 순회가 쉽다.

### 8. 도메인 서비스와 인프라가 섞임

- 섞인 것: 트랜잭션 관리·HTTP 호출(인프라·애플리케이션의 일)이 도메인 서비스 안에 있다.
- 나누는 법
  - 외부 정보는 도메인에 인터페이스(`ExchangeRates`)로 정의하고, 구현(HTTP 클라이언트)은 인프라 모듈에 둔다.
  - `@Transactional`·리포지토리 호출·이벤트 발행은 애플리케이션 서비스로 옮긴다.
  - 도메인 서비스 테스트는 가짜 `ExchangeRates`로 메모리에서 돈다.
  - 의존 방향을 아키텍처 테스트로 검사한다(software-design/41).

### 9. 이체와 "트랜잭션당 애그리거트 하나"

- Vernon(2011)은 잘 설계된 바운디드 컨텍스트가 트랜잭션당 애그리거트 인스턴스 하나만 수정한다고 적는다. 이체는 계좌 두 개를 고친다.
- 기록할 판단
  - 즉시 일관성이 필요한가(출금은 됐는데 입금이 안 된 상태를 보여도 되나). 보통은 안 된다고 본다. 즉시 일관성이 업무상 꼭 필요하면 Vernon의 틀에서는 진짜 불변식이라, 먼저 경계를 다시 본다(예: 이체 자체를 하나의 애그리거트·원장 기록으로 모델링). 그래도 두 계좌를 한 트랜잭션에 묶는다면, Vernon 2부가 든 네 사유(UI 편의·기술 장치 부족·전역 트랜잭션·조회 성능) 중 해당하는 것이나, 그 밖의 팀 판단 이유를 적는다(Vernon은 "these and others"라며 네 가지 밖의 사유도 있을 수 있다고 했다).
  - 결과적 일관성을 택하면: 출금 → 이벤트 → 입금, 실패 시 보상. 중간 상태를 원장(차변·대변)으로 남기는 설계가 따라온다(24 double-entry-ledger).
