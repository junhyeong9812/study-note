# domain-modeling/06-anemic-vs-rich-model — 정답

## 정답

### 1. Fowler의 비판

- 정의: 관계·구조는 진짜 도메인 모델처럼 갖췄지만 행위가 거의 없어 getter·setter 가방인 객체들.
- 근본 문제: 데이터와 처리를 함께 묶는다는 객체 지향 설계의 기본 생각과 정반대다. 결과는 절차적 설계다.
- 같아지는 패턴: Transaction Script. 도메인 모델의 이점을 잃는다.

### 2. Vernon의 진단과 원인

- 질문
  - "domain model"이라 부르는 것에 대부분 public getter·setter만 있고 업무 로직이 거의 없나?
  - 그 모델을 자주 쓰는 컴포넌트에 시스템 업무 로직 대부분이 있나?
- Vernon은 올바른 답이 "둘 다 예" 아니면 "둘 다 아니요"라고 쓴다. 둘 다 "예"면 빈약하다("It's anemic")고 같은 발췌에 적혀 있다.
- 원인: 1990년대 Visual Basic 폼 디자이너의 프로퍼티 시트가 JavaBean 명세·Hibernate 같은 영속 프레임워크에 영향을 줬다. 시장의 프레임워크 대부분이 단순 객체의 public 프로퍼티를 요구해 그 사용을 부추긴다.

### 3. 퍼징 결과 (seed 42)

- 빈약 모델(setter·컬렉션 포함): 9,974 / 10,000.
- 빈약 모델(서비스만 호출): 0.
- 풍부 모델: 0(거절된 호출 126,938).
- 빈약 모델에서 처음 깬 호출은 전부 setter·컬렉션 노출이었다. 가장 많은 것은 `getLines().add`→I2(4,171), `setTotal`→I2(3,871), `setShipped`→I1(1,679).

### 4. 차이의 정체

- 규칙이 지켜지는 근거가 다르다.
  - 빈약 모델: "모두가 서비스를 거친다"는 약속. 약속을 어긴 코드 하나(관리 도구, 배치, 스크립트)가 불법 상태를 만든다.
  - 풍부 모델: 객체에 규칙을 지나지 않는 문이 없다는 구조.
- 거절이 많다는 것: 호출자가 규칙을 어기는 요청을 하면 예외로 돌아온다. 호출 쪽은 거절을 다뤄야 한다(오류 응답·건너뛰기). 이것이 풍부 모델의 비용이다.
- 무작위 호출은 실제 호출 분포가 아니므로 위반 비율 자체가 아니라 "어느 문으로 깨지나"를 읽는다.

### 5. 도달 가능한 상태

- 빈약 모델: 32개 전부(이 실험 정의의 불법 17개 포함). setter로 어떤 칸이든 바꿀 수 있다.
- 풍부 모델: 7개(불법 0).
- 의미: 불법 상태를 만들 수 없으면 "검사를 잊은 경로"도 없다. 테스트해야 할 상태도 7개로 줄고, 각 상태에서 허용·거절되는 연산을 표로 검증할 수 있다.

### 6. 풍부 모델과 JPA

- setter는 필요 없다. Hibernate 6.6은 필드 접근을 지원한다.
- 해야 할 것: `@Id`를 필드에 둬 필드 접근으로 만든다. `protected` 인자 없는 생성자를 둔다. 프록시가 필요하면 클래스·메서드를 final로 하지 않는다.
- 실험 C: setter 0개 엔티티를 저장·복원했고(`status=PAID total=5000`), 복원 뒤에도 `addLine`이 "결제 뒤 변경 불가"로 거절됐다.

### 7. 합계 불일치

- 의심
  - 내부 컬렉션을 그대로 돌려주는 getter에 호출자가 `add`했다(합계 갱신 규칙을 지나지 않음).
  - 합계 setter(`setTotal`)를 따로 불렀다.
- 찾기: `select o.id from orders o join order_line l on l.order_id = o.id group by o.id, o.total having o.total <> sum(l.amount)`.
- 대처: 합계는 줄에서 계산하거나 줄을 바꾸는 메서드 안에서만 갱신한다. 컬렉션은 복사본(`List.copyOf`)이나 읽기 전용 뷰로만 내준다. 기존 불일치 행은 원천 기록으로 판정해 정정한다.

### 8. 빈약한 구조가 맞을 때와 과잉의 신호

- 맞을 때: 지켜야 할 불변식이 없는 데이터 — 설정값 CRUD, 조회 전용 읽기 모델, 경계를 넘는 DTO. Evans 4장은 업무 규칙이 적고 입력·표시가 대부분인 단순 프로젝트에 단순한 접근(Smart UI)이 맞을 수 있다고 쓴다.
- 과잉의 신호: 엔티티 메서드가 setter와 하는 일이 같다(`rename(n) { this.name = n; }`). 필드 하나 추가에 엔티티·매퍼·리포지토리 여러 파일을 고친다. 07번 실험에서 공지 제목 수정이 도메인 모델 구조로 5파일 23줄, 스크립트로 1파일 5줄이었다.

### 9. 외부 의존을 끌어들인 엔티티

- 섞은 것: 자기 상태에 관한 업무 판단과 흐름(외부 조회·알림 발송)을 둘 다 엔티티로 옮겼다.
- 나누기: 엔티티에는 자기 상태에 관한 판단만 둔다. 외부 정보가 필요한 규칙은 값을 인자로 받거나 도메인 서비스로 옮긴다. 메일 발송 여부·순서는 애플리케이션 서비스가 정한다(01번).
