# domain-modeling/28-dm-incidents — 정답

## 정답

### 1. MCO 근본 원인

- 보고서 문장: "the failure to use metric units in the coding of a ground software file, 'Small Forces,' used in trajectory models."
- 틀린 쪽은 **지상** 소프트웨어(SM_FORCES)다. 탑재 AMD 소프트웨어는 미터 단위로 계산해 맞았다(기여 원인 1: "Mismodeling only occurred in the ground software").
- 단위를 요구한 것은 MSOP 프로젝트의 Software Interface Specification(SIS)이다. AMD 파일의 형식과 단위(N·s)를 정의했지만 지켜지지 않았다.

### 2. 작은 오차가 170 km가 된 이유

- AMD 기동이 운영 항법팀 예상보다 **10~14배** 자주 일어났다. 기동마다 4.45배 과소평가된 오차가 들어갔고, 9개월 비행 동안 궤도 추정에 쌓였다.
- 빈도가 높았던 이유: MCO의 태양 전지판이 기체에 비대칭이라 태양 복사압으로 각운동량이 더 많이 쌓였다(대칭인 MGS와 다름).
- 전달되지 않은 결정: 이를 줄이려던 매일 180° 회전("barbecue" 모드)이 시스템 공학 검토 뒤 운영 계획에서 빠졌고, 그 결정과 영향이 운영 항법팀에 전달되지 않았다(기여 원인 4).
- 관측 한계도 겹쳤다. 추력 주 성분이 시선에 수직이라 도플러로 직접 보이지 않았다(기여 원인 1).

### 3. 단위 계산

- 받는 쪽 값 = 10 / 4.4482… ≈ **2.248 N·s**. 실험 출력: `실제 10.000 N·s, 파일 숫자 2.248, 받는 쪽 해석 2.248 N·s, 비율 4.4482`.
- 보고서는 계수를 4.45로 적었다("1 pound force=4.45 Newtons"). 실험은 4.4482216152605를 썼다. 국제 파운드 0.45359237 kg × 표준 중력 가속도 9.80665 m/s²이다(`python3` 실행 결과 `4.4482216152605`).
- 단위를 함께 보낸 `Impulse(2.248, LBF_S).toNs()`는 10.000 N·s로 되돌아왔다.

### 4. 놓친 신호

- 1999년 봄~여름: AMD 이벤트의 기대·관측 도플러 잔차가 **비공식적으로만** 보고됐다. 도플러만 쓴 해는 꾸준히 행성에 더 가까운 진입을 가리켰는데 해소되지 않았다.
- 1999-04: 올바른 형식의 AMD 파일을 쓰기 시작한 지 일주일 안에 과소평가를 가리키는 이상 데이터가 보였다.
- MOI 직전: 첫 근점 고도가 110 km까지 낮게 계산됐다. 비상 기동 TCM-5는 구두로 논의됐지만 준비가 안 돼 실행되지 않았다.
- 연결 leaf(해석): 차이를 사건으로 남기지 않고 방치한 것은 [25-5](../25-reconciliation/2-summary.md)(차이는 먼저 사건으로), 하류가 상류 출력을 검사하지 않은 것은 [18-1](../18-context-mapping/2-summary.md)(계약 테스트)·[19](../19-anti-corruption-layer/2-summary.md)(번역 계층에서 검사).

### 5. Receipts and Payments Mismatch

- 기간 마감 중 차이를 Local Suspense로 옮길지 묻는 화면에서 취소하면 **지점 쪽** 차이가 0이 됐다. POLSAP·Credence(본사 쪽)에는 차이가 남았다. 같은 세션에서 마감을 다시 진행하면 차이 없이 넘어가 두 쪽이 어긋났고, 그 불일치는 다음 기간으로 이월됐다.
- 영향: "circa 40 Branches since migration onto Horizon Online, with an overall cash value of circa £20k loss".
- 경고: 지점은 받지 않았다. 문서는 "the Branch will not get a prompt from the system to say there is Receipts and Payment mismatch, therefore the branch will believe they have balanced correctly"라고 적었다. 오류 코드는 생성돼 Fujitsu만 볼 수 있었다.

### 6. Dalmellington 숫자

- 수령액 £32,000(4 × £8,000), 차이 £24,000(판결 [447]). 몇 주 뒤 TC로 정정됐다.
- 모형 실행: `키 검사 없음: 받은 금액=32000, 보낸 금액=8000, 차이=24000`, `파우치 ID 유일 검사: 받은 금액=8000, 거절=3` — **3건** 거절.
- Fujitsu 조사: 지난 5년간 **88개 지점, 112건**(판결 [448]).

### 7. Issue 2·10·11

- Issue 2: "No, the Horizon system did not alert SPMs". 일부 버그는 수년간 발견되지 않았다([973]).
- Issue 10: Fujitsu는 거래 데이터의 삽입·수정·삭제, 데이터에 영향을 줄 수 있는 수정 배포, 지점 거래 데이터 재구성이 모두 가능했고, SPM이 모르게·동의 없이도 가능했다. 우체국은 Global User로 지점에 있을 때 거래 삽입만 가능했다([1003]·[1005]).
- Issue 11: 권한 통제는 있었지만 역할이 매우 넓고 통제되지 않았으며, 적절한 로그가 없었다([1008]).
- 해석: 24번의 "원장은 추가만, 정정은 역분개, UPDATE·DELETE 금지"와 22번의 "결정 근거를 업무 데이터로 같은 트랜잭션에"는 바로 "누가 언제 무엇을 바꿨나"를 나중에 증명하기 위한 규칙이다.
- 판결 범위 밖: 2019년 현재의 HNG-A 평가([964]: 역사적 분석이라고 명시), 형사 유죄 판결의 재심 등 이후 절차. 기술 부록은 이 노트가 읽은 PDF에 없었다.

### 8. "1년 뒤" 세 API

- `LocalDate.of(2013, 2, 29)` → `DateTimeException: Invalid date 'February 29' as '2013' is not a leap year`.
- lenient `GregorianCalendar(2013, FEB, 29)` → `2013-03-01T00:00:00Z`(조용히 이월).
- `plusYears(1)` → `2013-02-28`(말일로 맞춤).
- 20년 중 실패한 날은 **5일**(윤일). 2012-02-28처럼 윤일이 아닌 날에는 세 방법이 같은 답(`2013-02-28`)을 내므로 평소 날짜로 하는 시험은 갈리지 않는다. 윤일을 고정 `Clock`으로 넣은 시험이 필요하다(13-5).
- Azure 글이 어느 API를 썼는지는 적혀 있지 않다. 실험은 같은 계산이 API에 따라 다르게 실패할 수 있음을 보인 모형이다.

### 9. Azure의 연쇄

- GA는 인증서를 못 만들면 종료했다. HA는 25분 기다린 뒤 VM을 재초기화했다. 깨끗한 VM이 연속 3번 타임아웃하면 HA는 하드웨어 문제로 판단해 서버를 HI로 보고했다. FC는 그 서버의 VM을 다른 서버로 옮겼고, 거기서 같은 버그가 재현돼 HI가 연쇄됐다. HI 임계치를 넘으면 클러스터 전체가 HI와 비슷한 상태가 됐다.
- "75분" = 25분 타임아웃 × 3. 배포 중이던 클러스터에서 4:00PM PST 발동 뒤 5:15PM PST에 임계치 도달.
- 2차 장애: 배포 초기였던 7개 클러스터에 옛 HA를 동시 배포(blast)하면서 새 HA용 네트워킹 플러그인을 함께 묶어 보냈다. 둘이 호환되지 않아 2:47AM PST부터 건강하던 VM까지 네트워크가 끊겼다. 단일 서버 시험이 네트워크 연결을 확인하지 않았다.

### 10. tz 규칙 변경과 저장

- 2022f(2022-10-28)는 Chihuahua가 **2022-10-30**에 연중 -06으로 바뀐다고 실었다 — 이틀 전.
- 2023b(2023-03-23)는 레바논 DST 시작을 3월 25/26일에서 4월 20/21일로 바꿨다 — 원래 전환일 이틀 전. 2023c(2023-03-28)는 그 변경을 되돌렸다.
- 저장: 미래 예약의 원본은 **현지 시각 + tz ID**이고 UTC 순간은 파생값이다. 런타임 tzdata 판을 기록하고 판 갱신 때 재계산한다(13-1).
- tz 규칙은 외부(정부)가 바꾸는 일반 서브도메인이라 자체 구현하지 않는다(17-1). 요율표처럼 규칙에도 판이 있어 "그때 어떤 판으로 계산했나"를 남긴다(23).
