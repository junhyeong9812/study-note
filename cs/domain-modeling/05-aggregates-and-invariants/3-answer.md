# domain-modeling/05-aggregates-and-invariants — 정답

## 정답

### 1. 애그리거트가 푸는 것

- 없을 때: 두 요청이 같은 합(6)을 읽고 각자 "9라서 OK"라고 판단해 둘 다 커밋한다 → 합 12. 검사와 쓰기를 함께 잠그는 지점이 없다.
- 너무 클 때: 업무상 독립적인 수정(서로 다른 항목)이 같은 루트 버전을 다툰다 → 충돌·재시도·응답 지연. Vernon은 성능·확장성 손해도 든다.

### 2. Evans의 Aggregates

```text
  ┌──── 경계 ─────────────────────────┐
  │ Root(전역 id)  ← 불변식 검사 책임   │
  │   ├─ 내부 엔티티(지역 의미)          │
  │   └─ 값 객체                         │
  └───────────────────────────────────┘
      ▲ 바깥은 루트만 참조
  같은 경계 = 트랜잭션·분산 단위
  경계 안: 동기적 일관성 / 경계 사이: 비동기 갱신
```

- 내부 객체 참조는 한 연산 안에서만 쓰도록 넘길 수 있다.
- 경계가 트랜잭션·분산 결정을 잘 이끌지 못하면 모델을 다시 보라고 한다.

### 3. Vernon 4규칙

| 규칙 | 막는 실패 |
|---|---|
| Model True Invariants In Consistency Boundaries | 경계 밖에 놓인 불변식이 동시성에 깨짐 |
| Design Small Aggregates | 상관없는 수정끼리 충돌, 메모리·확장성 손해 |
| Reference Other Aggregates By Identity | 객체 그래프를 따라가 다른 애그리거트를 같은 트랜잭션에서 고치는 것, 큰 로딩 |
| Use Eventual Consistency Outside the Boundary | 여러 애그리거트를 한 트랜잭션에 묶어 실패 범위·경합이 커짐 |

- 불변식: "항상 일관돼야 하는 업무 규칙". 여기서 일관성은 즉시·원자적인 **트랜잭션 일관성**이다(결과적 일관성과 구분).

### 4. 크기와 충돌 수

- 실험 A(PostgreSQL 17.11, 8명 × 50회, 1ms 작업): 거대 애그리거트 충돌 1938~2313회(집필·점검 12측정), 작은 애그리거트 0회. 성공 커밋은 둘 다 400.
- 이유: 버전 단위가 `Product` 하나라, 누가 어떤 항목을 고치든 같은 `version`을 `WHERE version = ?`로 비교한다. 읽은 뒤 1ms 사이에 누군가 커밋하면 실패한다. 작은 쪽은 각자 자기 항목 버전만 비교한다.
- 수치는 사용자 수·작업 시간에 따라 바뀐다. 구조(상관없는 수정이 같은 버전을 다툼)는 남는다.

### 5. 경계 밖 vs 안

- outside(검사만): 8명 모두 성공, 합 **24**. inside(루트 버전): 3명 성공·5명 거절, 합 **9**. 합은 매 측정 같았고, inside의 재시도 수만 14~18로 실행마다 달랐다.
- 깨지는 이유: 8명이 모두 합 0을 읽은 뒤 쓴다(배리어로 강제). 각자 서로 다른 행을 INSERT하므로 행 충돌이 없다. PostgreSQL 기본 READ COMMITTED는 이런 쓰기 왜곡을 막지 않는다.
- inside에서는 모두 같은 `sprint` 행의 버전을 갱신하려 하므로 한 명만 이기고, 진 쪽은 다시 읽어 새 합으로 판단한다.

### 6. Evans vs Vernon

- Evans(『DDD Reference』 2015): 경계를 불변식과 트랜잭션·분산 단위로 정한다. 크기 수치나 "트랜잭션당 하나" 규칙은 『DDD Reference』 항목에 없다.
- Vernon(2011): 작게(루트 + 값 객체가 기본, Hedhman 프로젝트 약 70%가 루트만), 잘 설계된 바운디드 컨텍스트는 트랜잭션당 애그리거트 인스턴스 하나만 수정한다.
- 규칙을 깨도 되는 이유(Vernon 2부): ① 사용자 인터페이스 편의(일괄 생성) ② 기술 장치 부족(메시징·타이머 없음) ③ 전역(2PC) 트랜잭션 정책 ④ 조회 성능(직접 참조). 사용자–애그리거트 친화성이 있으면 더 건전하다.

### 7. mappedBy 자식과 루트 버전

- JPA 3.1 §3.4.2: 버전 검사에는 비관계 필드와 **그 엔티티가 소유한 관계**만 들어간다. 소유한 관계라도 들어가는 것은 연관 자체이고, 자식 엔티티(줄)의 필드는 아니다. 그래서 줄만 고치면 `Order.version`이 오르지 않고, 두 요청이 서로 다른 줄을 고치면 버전 비교가 겹치지 않는다.
- 실험 C(Hibernate 6.6.29): 자식만 고친 뒤 루트 `version = 1` 그대로.
- `mappedBy`를 빼고 루트가 소유한 단방향 `@OneToMany @JoinColumn`으로 바꿔도 줄 필드 수정 뒤 루트 버전은 0 그대로였다. 줄을 추가할 때만 `0 → 1`(실험 C-3). 매핑을 바꾸는 것으로는 막히지 않는다.
- `@ElementCollection`이면: 원소가 루트의 비관계 필드(값)라 원소 추가에 루트 버전이 `0 → 1`로 올랐다(실험 C-2).
- 대처: 줄 변경을 모두 루트 메서드로 모으고, 그 안에서 `LockModeType.OPTIMISTIC_FORCE_INCREMENT`로 루트를 잠근다. 실험 C에서 두 번째 세션이 `StaleObjectStateException`(네이티브 부트스트랩)으로 실패했다.

### 8. 충돌 급증 진단

- 확인
  - 충돌 예외 로그를 엔티티 타입별로 센다. 한 루트 타입에 몰리는가. Hibernate `Statistics.getOptimisticFailureCount()`(가이드 27.1.7).
  - 루트별 자식 수 분포(`GROUP BY parent_id`). 수백~수천이면 거대 애그리거트 후보.
  - 충돌한 요청들이 업무상 같은 것을 고쳤나, 서로 다른 자식을 고쳤나. 후자면 경계 문제다.
  - `pg_stat_statements`로 같은 루트 테이블의 `UPDATE … version` 호출 수.
- 고치는 순서: 진짜 불변식을 문장으로 다시 적는다 → 불변식이 걸치지 않는 자식을 별도 애그리거트로 떼어 ID로 참조한다 → 같은 동시성 시나리오로 충돌 수를 다시 잰다(실험 A처럼).

### 9. 결과적 일관성

- 장치: 도메인 이벤트 + outbox(같은 트랜잭션에 이벤트 행 기록 → 별도 프로세스가 발행) → 다른 애그리거트를 다음 트랜잭션에서 갱신. 실패 시 재시도·보상.
- 쓰면 안 되는 조건: 잠깐이라도 어긋나면 안 되는 규칙(용량 초과 금지, 음수 재고 금지, 좌석 중복 금지)이고, 어긋났을 때 되돌릴(보상할) 방법을 업무가 받아들이지 않을 때. 그런 규칙은 경계 안에 둔다. Vernon의 질문 "이 규칙을 지키는 것이 이 요청을 한 사용자의 일인가?"가 판단 기준이다.
