# 도메인 로직 vs 애플리케이션 로직 — 정답

> 이 파일은 [1-question.md](1-question.md)의 질문에 1:1로 대응하는 정답이다. 근거는 [2-summary.md](2-summary.md)와 개념에서 가져왔다.\
> 근거가 없는 답에는 `(원본에 근거 없음 — 내 추론)`을 붙였다. 복습 때는 질문을 먼저 풀고 막힐 때만 이 파일을 연다.

## 정답

**1. (판단)** 한 문장 기준은 "**이 규칙은 우리가 시스템을 안 만들어도 업무에 존재하는가?**"다.\
있으면 도메인 로직("정산 완료된 거래는 취소할 수 없다"), 시스템이 있어서 생긴 절차면 애플리케이션 로직("취소 요청이 오면 원거래를 조회하고 없으면 404를 반환한다").

**2. (연결)** 도메인 로직은 **"이 상태에서 이 조작이 허용되는가?"**(무엇이 옳은가)에, 애플리케이션 로직은 **"이 유스케이스를 어떤 순서로 처리하는가?"**(무슨 순서로)에 답한다.\
도메인은 불변식을 **판단**하는 일이고, 애플리케이션은 여러 객체·포트를 정해진 순서로 엮는 **조율**(오케스트레이션)이기 때문에 하나는 "무엇이 옳은가", 다른 하나는 "무슨 순서로"라 부른다.

**3. (경계)** 이메일 중복 검사는 도메인 규칙("유일해야 한다")이지만 판단에 저장소 전체를 봐야 해서 인프라가 필요하다. 실무 해법 셋:\
**A** 애플리케이션 서비스에서 `existsByEmail` — 단순함이 장점, TOCTOU가 대가(DB 유니크 제약이 최후 방어선이어야 함).\
**B** 도메인 서비스에 규칙을 두되 조회는 포트로 주입 — 규칙이 도메인 어휘로 표현됨이 장점, 간접 계층 증가가 대가.\
**C** DB 유니크 제약에 맡기고 예외를 도메인 예외로 번역 — 경쟁 조건에 안전함이 장점, 예외 기반 흐름 제어·DB 메시지 파싱 의존이 대가.\
실전 조합은 A + C(평상시 친절한 메시지, 경쟁 상황은 C가 잡는다).

**4. (경계)** "검증"에 섞인 세 가지와 위치:\
**입력 형식 검증**(이메일에 `@`가 있는가) → 프레젠테이션(`@Valid`) — 도메인까지 갈 필요 없는 쓰레기 입력이라서.\
**도메인 불변식**(금액이 음수가 아니다) → 도메인 — 외부 조회가 필요 없는 업무 규칙이라서.\
**컨텍스트 의존 규칙**(이메일이 이미 가입되어 있는가) → 애플리케이션 — 판단에 저장소 조회가 필요하기 때문.

**5. (왜)** 빈약한 도메인 모델은 데이터만 있고 규칙은 서비스에 있어, 같은 판단이 서비스마다 복사·중복되고(하나만 고치면 다른 곳이 남는다) setter로 규칙을 우회할 수 있어 객체가 자기 불변식을 못 지킨다.\
그러나 항상 문제는 아니다 — **지켜야 할 불변식이 없으면**(설정값 CRUD·조회 전용 Read Model·경계를 넘는 DTO) 데이터 가방으로 두는 게 맞다. 판단 기준은 **불변식이 있느냐**다.

**6. (판단)** 목표는 "**읽으면 유스케이스 흐름이 그대로 보이는 것**"이다 — 조건문이 거의 없고(있으면 흐름 분기이지 비즈니스 판단이 아니다), 계산식이 없고, 루프 안에 복잡한 로직이 없다.\
**너무 얇은** 경우는 드물지만, 아무 일도 하지 않고 리포지토리만 호출하는 pass-through 서비스가 많으면 계층이 하나 남는다는 신호일 수 있다.

**7. (왜)** `LocalDateTime.now()`는 **숨은 의존**이라 테스트할 수 없는 코드를 만든다 — "8일 뒤 만료되는가"를 검증하려면 시스템 시계를 조작해야 한다.\
고치는 법은 시간을 **인자로 주입**하는 것(`isExpiredAt(LocalDateTime now)`). 시간·랜덤·현재 로그인 사용자처럼 바깥세상에서 오는 값은 전부 인자로 받는다.

**8. (예측)** 세 신호 — 가용잔액 계산이 서비스에 있음(`balance - hold < amount`), 사용 가능 판단이 서비스에 있음(`card.getStatus() != ACTIVE`), 상태 전이를 서비스가 직접 함(`setStatus(APPROVED)`).\
공통점은 **서비스가 도메인 객체에서 값을 꺼내 스스로 판단**한다는 것이다. clean-code의 **A(단정적/Assertive)** 속성 위반이며, 코드 레벨로는 "묻지 말고 시켜라(Tell, Don't Ask)"의 Ask 형태다.

**9. (경계)** 애그리게이트가 **정합성의 단위**이기 때문이다 — 여러 개를 한 트랜잭션에서 바꾸면 락 범위가 커지고 결국 분산 환경에서 불가능해진다.\
여러 개를 바꿔야 하면 **같은 서비스 안**에서는 도메인 이벤트로 이어붙이거나 정말 필요하면 한 트랜잭션에 의식적으로 묶고, **다른 서비스**에 걸치면 Saga로 조율한다.

**10. (경계)** 조회는 목적이 데이터 표시일 뿐 지켜야 할 불변식이 없어 도메인 모델을 우회해도 되지만(CQRS), 명령은 불변식을 지켜야 하므로 우회하면 **불변식을 건너뛰게 되어** 절대 안 된다.\
조회의 권한 검사 위치는 `(원본에 근거 없음 — 내 추론)` — 조회 서비스(애플리케이션 계층)에서 검사하는 것이 자연스럽다. 조회 경로는 도메인을 우회하므로 권한을 도메인에 맡길 수 없고, 유스케이스 진입점인 애플리케이션 서비스가 조율의 일부로 검사한다.

**11. (연결)** 도메인 이벤트는 **도메인이 만들고**("무슨 일이 일어났는가"는 도메인 사실), **애플리케이션(또는 인프라)이 발행한다**(Kafka·트랜잭션은 인프라 관심사).\
사이의 트랜잭션은 도메인이 이벤트를 객체 안에 담아두고, 저장 후 `pullEvents()`로 꺼내 발행하는 식으로 건다. 그냥 발행하면 위험한 이유는 **DB 커밋과 발행이 원자적이지 않아** 커밋 후 발행이 실패하면 이벤트가 유실되기 때문 — 해법이 Outbox 패턴이다.

**12. (왜)** 도메인 서비스는 **인프라 의존이 없는 순수 객체**여야 하는데, `@Service`(스프링 빈)로 등록하면 "인프라를 주입받아도 되는 곳"으로 오인되기 쉽기 때문이다.\
도메인 서비스는 **한 엔티티에 담으면 어색한 규칙**(전형적으로 여러 애그리게이트에 걸친 규칙, 예: 출금·입금 두 계좌를 다 봐야 하는 이체 판단)일 때만 쓴다.

**13. (판단)** `long amount`로 다니면 원화인지 달러인지, 원 단위인지 전 단위인지 아무도 모른다. `Money`로 감싸면 통화 불일치 같은 실수를 컴파일·실행 시점에 잡고, 값의 유효성·연산이 한곳에 모인다.\
"타입이 곧 문서"란 타입 자체가 의미(통화·단위·불변식)를 담아 별도 주석 없이도 무엇인지 읽힌다는 뜻이다.

**14. (예측)** 둘은 **같은 원인**에서 나왔다 — **분산 트랜잭션(외부 시스템 + 로컬 DB)을 로컬 트랜잭션 하나처럼 다루려 한 것**이다.\
외부 호출은 성공했는데 로컬 커밋이 실패하면(또는 반대) 두 시스템 상태가 어긋나고, 이를 도메인 필드로 수동 롤백하려다 롤백 로직이 도메인에 스몄다. 바른 방향은 외부 호출을 트랜잭션 경계 **밖**으로 빼고 정합성은 Saga·Outbox로 다루는 것 — 그러면 롤백 필드가 사라진다.

**15. (경계)** 의존 방향은 항상 **안쪽**(도메인)을 향한다. `domain/` 패키지의 import에 스프링·JPA가 하나도 없어야 한다.\
가장 쉬운 확인 방법은 **도메인 테스트를 스프링 없이 돌려보는 것**이다 — 순수 자바로 실행되면 순수한 것이다.
