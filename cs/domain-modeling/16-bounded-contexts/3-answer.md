# domain-modeling/16-bounded-contexts — 정답

## 정답

### 1. 공유 모델의 근본 문제

- 한 필드가 **여러 뜻을 동시에** 진다. 예: `status`가 영업에는 "주문 가능", 지원에는 "서비스 제한", 청구에는 "연체 단계"다.
- 그래서 한 팀이 자기 뜻대로 값을 바꾸면, 다른 팀의 해석 코드가 컴파일 오류 없이 조용히 틀린다.
- DDD Reference의 말로는 "서로 다른 모델 위의 코드를 섞으면 버그가 늘고 이해가 어려워진다".

### 2. 정의와 경계 기준

| 용어 | DDD Reference 2015 "Definitions" |
|---|---|
| 모델 | 도메인의 일부 측면을 골라 기술한 추상 체계. 그 도메인의 문제를 푸는 데 쓴다 |
| 컨텍스트 | 단어나 문장의 뜻을 정하는 그것이 나타나는 배경 |
| 바운디드 컨텍스트 | 특정 모델이 정의되고 적용되는 경계(보통 하위 시스템이나 한 팀의 작업) |

- 경계 기준(Bounded Context 처방): **팀 조직**, **애플리케이션 안의 사용 범위**, **물리적 형태(코드베이스·DB 스키마)**.

### 3. 공유 모델에서의 예측

- 연체 45일 고객은 이제 `status = "DELINQUENT"`다.
- 영업 코드는 `"SUSPENDED"`만 막으므로 **주문할 수 있게 된다.** 컴파일 오류는 없다.
- 실험 출력: 청구 파일 1개만 바뀐 상태에서 `FAIL sales | 연체 45일 고객은 주문 불가`, `failures=1`. 바로잡는 데 영업 파일도 고쳐 2파일이 됐다.

### 4. 컨텍스트별 모델에서의 예측

- 영업 쪽 파일은 **0개** 바뀐다. 실험에서는 청구 파일 2개(`BillingAccount.java`, `Dunning.java`)만 바뀌었고 4개 테스트가 모두 통과했다.
- 이유: 영업은 청구 상태값을 모른다. `orderingBlocked`(= 상태가 GOOD이 아님)만 받는다.
- 지원의 45일 티켓이 HIGH로 바뀐 것은 두 설계가 같다. 차이는 결정 위치다.
  - 공유 모델: 지원 코드의 문자열 비교가 우연히 결정했다. 지원팀은 모른다.
  - 컨텍스트별: 청구의 공개 언어 정의 한 줄(`restricted = standing == SUSPENDED`)이 결정한다. 그 줄은 계약으로 검토할 수 있다.

### 5. 나눈 쪽이 비싼 변경

- 모든 컨텍스트가 같은 뜻으로 함께 바꾸는 개념. 실험의 "표시 이름 추가"는 공유 모델에서 1파일, 컨텍스트별 모델에서 3파일이 바뀌었다.
- 이런 변경이 잦다면 경계를 언어가 갈리지 않는 곳에 그었다는 신호다. 컨텍스트를 합치거나 그 부분을 작은 공유 커널로 뺀다(18번).

### 6. 세 개념의 차이

| | 무엇 | 공간 |
|---|---|---|
| 서브도메인 | 회사가 하는 일의 한 부분(주문·청구·지원) | 문제 공간 — **발견**한다 |
| 바운디드 컨텍스트 | 한 모델·언어가 통하는 경계 | 해법 공간 — **설계**한다 |
| 마이크로서비스 | 독립 배포 단위 | 배포·운영 |

- Khononov: 서브도메인은 발견되고, 유비쿼터스 언어를 컨텍스트로 나누는 것은 설계 결정이다.
- 컨텍스트와 서비스는 1:1일 수도 있고, 모놀리스 안의 모듈 경계일 수도 있다.

### 7. 공유 테이블

- 안 맞춘 기준: **물리적 형태(DB 스키마)**. 코드에서는 나뉘었지만 DB 수준에서는 여전히 한 모델이다.
- 증상: 컬럼 변경마다 여러 팀이 함께 배포한다. 마이그레이션 PR에 여러 팀 승인이 붙는다.
- 대처: 테이블 소유자를 정하고, 다른 컨텍스트는 API·이벤트·복제 뷰로 읽는다.

### 8. 컨텍스트 안의 조각남

- 경고: 한 컨텍스트에서 여럿이 일하면 모델이 조각나려는 경향이 강하다. 서너 명으로도 심각해질 수 있다.
- 처방: 코드와 산출물을 자주 합치고 자동 테스트로 조각남을 빨리 드러낸다. 유비쿼터스 언어를 끊임없이 써서 공유된 모델을 맞춘다.
- 반대 경고: 시스템을 계속 더 작은 컨텍스트로 쪼개면 통합성과 일관성을 잃는다.
- 그래서 선택은 둘이다. 언어를 다시 통일하거나, 뜻이 정말 갈린다면 경계를 다시 긋는다.

### 9. 진단

- 공유 클래스의 필드마다, 그 필드를 참조하는 최상위 패키지(컨텍스트)를 `grep`으로 센다.
  - 실험 결과: `status: billing sales support`, 나머지 필드는 한 컨텍스트씩.
- 해석
  - 여러 컨텍스트가 **읽기만** 하는 필드 → 공개 언어(메시지 필드)로 옮기기 쉽다.
  - 한 컨텍스트가 쓰고 다른 컨텍스트가 **해석**하는 필드(`status`) → 뜻 충돌 후보 1순위.
- 커밋마다 함께 바뀐 폴더를 세는 변경 결합 분석도 같은 신호를 준다(software-design/53).
