# domain-modeling/16-bounded-contexts — 질문

## 질문

1. (왜) 영업·지원·청구가 클래스 `Customer` 하나를 함께 쓰면 무엇이 깨지나? "필드가 많아진다"보다 더 근본적인 문제를 한 문장으로 말하라.
2. (정의) DDD Reference(2015)의 정의로 *모델*·*컨텍스트*·*바운디드 컨텍스트*를 각각 한 줄로 말하라. Evans는 경계를 무엇으로 정하라고 하나(세 가지)?
3. (예측) 공유 `Customer`의 `status`를 청구팀이 `"SUSPENDED"` 대신 31~90일 연체에 `"DELINQUENT"`를 넣도록 한 줄 바꿨다. 영업 코드는 `!"SUSPENDED".equals(c.status) && c.creditLimit > 0`이다. 연체 45일 고객은 주문할 수 있나? 컴파일 오류가 나나?
4. (예측) 같은 변경을 컨텍스트별 모델(청구가 `StandingChanged(customerId, orderingBlocked, serviceRestricted)`를 발행)에서 하면 영업 쪽 파일은 몇 개 바뀌나? 이 설계에서도 지원의 연체 45일 티켓 우선순위가 바뀐다면, 공유 모델과 무엇이 다른가?
5. (경계) 컨텍스트를 나눈 쪽이 더 비싼 변경의 예를 들고, 그 신호가 무엇을 뜻하는지 말하라.
6. (경계) 바운디드 컨텍스트, 서브도메인, 마이크로서비스는 각각 무엇이고 어떻게 다른가? Khononov의 "발견 vs 설계" 구분을 써서 답하라.
7. (연결) 코드 패키지는 나눴는데 DB 테이블은 여러 컨텍스트가 같이 쓴다. Reference의 경계 기준 중 무엇을 안 맞춘 것이며, 어떤 증상이 나오나?
8. (장애 진단) 한 컨텍스트 안에서 "그 status는 어느 status냐"는 질문이 회의마다 나온다. Reference "Continuous Integration"은 무엇을 경고하고 무엇을 처방하나? 반대로 너무 쪼갤 때의 경고는?
9. (적용) 공유 클래스가 경계를 흐리고 있는지 코드에서 찾는 간단한 진단 방법을 하나 대고, 결과를 어떻게 해석하나?
