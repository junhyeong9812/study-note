# domain-modeling/22-decision-log-and-provenance — 정답

## 정답

### 1. 결과 + 규칙 ID만으로는 안 되는 이유

- 규칙 ID와 고객 ID는 "지금의 그것"을 가리킨다. 등급·요율이 덮어써지면 다시 계산해도 다른 값이 나온다. 중간 계산(할인율·할인액)은 어디에도 없다.
- 로그는 운영 신호라 샘플링·레벨 조정·보존 기한으로 버려진다. 업무 근거를 로그에 맡기면 필요할 때 이미 없을 수 있다(reliability/18: 레벨 WARN에서 환불 로그 0/100).

### 2. 결정 레코드

| 칸 | 답하는 질문 |
|---|---|
| 대상(order_id) | 무엇에 대한 결정인가 |
| 결정 시각 | 언제 기준으로 계산했나 |
| 입력 스냅샷(또는 불변 참조 + 버전) | 그때 무슨 값을 보고 계산했나 |
| 규칙 ID·버전 | 어떤 규칙의 어느 판으로 |
| 중간 산출 | 어떻게 그 값이 나왔나(검산) |
| 결과 | 무엇으로 결정했나 |
| prev_hash·hash(선택) | 나중에 고쳐지지 않았나 |

### 3. PROV-DM으로

- Entity: 결과(9,270원), 입력 스냅샷(GOLD, 10,300원), 규칙 v1. Activity: 할인 계산 실행. Agent: 계산 서비스(또는 담당자).
- 계산 `used` 입력 스냅샷·규칙 v1, 결과 `wasGeneratedBy` 계산, 결과 `wasDerivedFrom` 입력 스냅샷, 계산 `wasAssociatedWith` 계산 서비스.

### 4. 참조 + 버전의 조건

- 참조 대상이 **추가만 하는 버전 테이블**이어서, 같은 (ID, 버전)이 영원히 같은 값을 돌려줘야 한다. 덮어쓰거나 지우면 참조가 다른 값을 가리키게 된다. 보존 기한도 결정 기록 이상이어야 한다.

### 5. 재계산 불일치

- 참조만: 40/100. 요율이 바뀐 원래 GOLD 33건 + 새로 GOLD가 된 7건.
- 스냅샷 + 규칙 버전: 0/100.
- 실험 출력: `A 참조만 | 40 | 100`, `B 스냅샷+버전 | 0 | 100`(PostgreSQL 17.11).

### 6. 재현 가능성 테스트

- 표본 결정을 읽어, 기록된 규칙 ID·버전으로 규칙을 찾고 기록된 입력으로 다시 계산해 결과를 비교한다. `BigDecimal`은 `compareTo`(AssertJ `isEqualByComparingTo`)로 비교한다 — `equals`는 스케일까지 본다.
- 계산은 순수 함수여야 한다: 같은 입력·같은 규칙 버전 → 같은 결과. 현재 시각·난수·외부 조회를 함수 안에서 부르지 않는다. 시각은 `Clock`에서 받아 입력 스냅샷에 넣는다.
- 옛 규칙 버전의 코드(또는 요율표 버전)를 지우지 않아야 옛 결정을 재현할 수 있다.

### 7. 해시 체인

- 한 행만 고치면 그 행의 저장 해시와 다시 계산한 해시가 어긋난다(실험: seq 40 `hash_ok = f`).
- 그 행부터 끝까지 다시 계산하면 체인 자체 검증은 깨진 행 0이 된다.
- 체인 밖에 따로 보관한 머리 해시(고정점)와 비교해야 드러난다(실험: before ≠ after).

### 8. 변조 없는 전면 실패

- 해시 입력의 텍스트 표현이 세션 설정에 따라 바뀌었는지 의심한다. `timestamptz`의 텍스트 출력은 세션 `TimeZone` 기준이다. 실험에서 `TimeZone`을 UTC → Asia/Seoul로만 바꿔도 100/100이 깨졌다.
- 고치기: 해시 입력을 정규화한다(시각은 UTC ISO 문자열이나 epoch, 숫자는 고정 스케일, JSON은 고정 키 순서). 당장은 검증 세션에 `SET TimeZone = 'UTC'`처럼 생성 때와 같은 설정을 명시한다.

### 9. ADR vs 결정 기록

- ADR: 사람이 내린 **설계·아키텍처** 결정(맥락·선택지·결과)을 남기는 문서. 코드 저장소에 둔다.
- 이 노트의 결정 기록: 시스템이 실행한 **도메인 계산** 결정(입력·규칙 버전·중간 산출·결과)을 남기는 업무 데이터. 거래마다 한 행, 업무 DB에 둔다.

### 10. 결정 기록 누락

- 찾기: 업무 행과 결정 기록을 LEFT JOIN해 기록이 없는 행을 찾는다(`WHERE l.order_id IS NULL`).
- 흔한 원인: 결정 기록을 비동기(로그·메시지)로 쓰거나, 업무 데이터와 다른 트랜잭션에서 썼다.
- 대처: 같은 트랜잭션에 쓴다. 누락 점검 쿼리를 정기 배치로 둔다. 이미 빠진 건은 그때 값을 백업·PITR 범위 안에서 찾아 보충하고, 보충한 사실을 기록에 남긴다.
