# domain-modeling/20-event-storming — 정답

## 정답

### 1. 빠지는 지식

- 예외 경로(재고 없음·취소·환불·부분 배송)와 부서 사이 이해 차이. 이 지식은 현장 업무 담당자 머릿속에 있다.
- 데이터 모델부터: 개발자의 말(명사·필드)로 시작해 업무 흐름의 순서·분기가 안 보인다.
- 이벤트부터: 업무 담당자가 이미 쓰는 말(과거형 사건)로 시작한다. 시간 순서로 늘어놓으면 빠진 단계·중복·충돌이 보인다. Brandolini 2013은 결과 모델이 "완전히 행동 중심이며 구현을 제약하는 밑바탕 데이터 모델이 없다"고 적는다.

### 2. 정의

- 이벤트 스토밍: 복잡한 업무 도메인을 협업으로 탐색하는 유연한 워크숍 형식(eventstorming.com).
- 도메인 이벤트: 도메인에서 일어난 의미 있는 일(Brandolini 2013).
  - 시제: 과거형(용어집: "a verb at the past tense", 예 "Order Placed").
  - 의미: 도메인 전문가에게 의미가 있어야 한다.

### 3. 색

| 포스트잇 | 용어집 색 |
|---|---|
| 도메인 이벤트 | 주황 |
| 명령 | 파랑 |
| 행위자 | 작은 노랑 |
| 외부 시스템 | 넓은 분홍 |
| 정책 | 큰 라일락 |
| 읽기 모델 | 초록 |
| 핫스폿 | 형광 분홍 |
| 제약/애그리거트 | 큰 노랑 |

- 2013년 원글: 이벤트 주황·명령 파랑은 같다. 이벤트의 원인이 외부 시스템이나 시간 경과이면 보라로 적었다(이벤트 자체는 주황). 현재 색표와 다르다.
- 용어집은 큰 노랑을 "제약(Constraint)"으로 부르고, aggregate는 업무 담당자 앞에서 피하려고 레거시 용어로 돌렸다.
- 색은 관례다. 워크숍마다 범례를 벽에 붙여 맞춘다.

### 4. 세 수준과 인원

| 수준 | 목적 |
|---|---|
| Big Picture | 사업 라인 전체의 건강 진단, 공유된 큰 그림 |
| Process Modeling | 한 프로세스의 건강 진단, 병목·분리 기회 찾기 |
| Software Design | 바운디드 컨텍스트 안에서 이벤트 기반 소프트웨어 설계 |

- 인원: 2013년 원글은 "6..8명", 용어집의 Big Picture는 "10~30명+ 한 종이 롤". 형식이 발전하며 규모가 커졌다.

### 5. 문법과 코드

```text
행위자 → 명령 → 애그리거트/시스템 → 이벤트 → 정책 → 명령 → ...
          ↑ 읽기 모델(결정에 필요한 정보)
```

| 포스트잇 | 코드 |
|---|---|
| 명령 | 명령 핸들러·애플리케이션 서비스 메서드 |
| 애그리거트 | 명령을 받아 불변식을 검사하고 이벤트를 내는 엔티티 |
| 이벤트 | 과거형 이름의 도메인 이벤트 클래스 |
| 정책 | 이벤트 구독자(이벤트 → 다음 명령) |
| 읽기 모델 | 조회 전용 모델·화면 |

- 1:1 대응은 관례일 뿐이다.

### 6. 검사기 결과 (실험 첫 보드)

```text
  - 트리거 없는 이벤트: 결제 승인됨
  - 정책이 내리는 명령이 없음: Policy[whenEvent=주문 접수됨, thenCommand=결제 요청]
  - 반응(정책) 없는 이벤트: 결제 승인됨  ← 다음은 누가 하나?
```

- "결제 승인됨"을 내는 명령이 없다. 정책이 가리키는 "결제 요청" 명령이 없다. 결제 승인 뒤 무엇을 하는지가 없다.
- 개발자가 머릿속으로 이어 붙인 곳이 문법상 구멍으로 드러났다.

### 7. "반응 없는 이벤트"의 한계

- 늘 결함은 아니다. 환불 완료는 분기의 끝이라 반응이 없어도 정상일 수 있다.
- 한계: 검사기는 타임라인의 마지막 이벤트만 끝으로 알 뿐, 분기의 끝 이벤트와 빠뜨린 반응을 구분하지 못한다.
- 보완: 보드에 "끝 이벤트" 표시를 두는 규칙을 정한다. 기계 검사는 질문을 만들 뿐이고, 답은 사람이 한다.

### 8. 근거의 종류

- "몇 주가 아니라 몇 시간"은 저자와 실무자의 **경험 주장**이다. 통제된 측정 결과가 아니다.
- 실험이 보이는 것: 문법을 지킨 보드는 검사 가능한 산출물이 되고, 빠진 연결을 기계로 찾을 수 있다.
- 보이지 않는 것: 워크숍이 지식 누락을 실제로 얼마나 줄이는지. 두 보드는 시나리오(예시)다.

### 9. 사진으로만 남은 보드

- 원인: 보드를 검사·추적 가능한 형태(이벤트·명령·정책 목록)로 옮기지 않았다. 용어가 코드로 이어지지 않았다.
- 대처
  - 보드를 목록으로 옮겨 저장소에 둔다. 용어집과 함께 관리한다.
  - 목록과 코드의 이벤트 이름을 대조하는 검사를 둔다. 양쪽에만 있는 이름을 모두 신호로 본다.

### 10. 덮인 핫스폿

- 핫스폿(형광 분홍)을 결정해야 할 질문 목록으로 관리했어야 한다.
- 핫스폿마다 담당자·결정 기한을 붙인다. 결정 전에는 그 기능을 범위에서 빼거나 명시적 기본 동작을 합의한다.
- 실험의 고친 보드에도 이 핫스폿이 남아 있었다. 보드가 질문을 드러내도, 결정으로 이어 주는 것은 관리다.
