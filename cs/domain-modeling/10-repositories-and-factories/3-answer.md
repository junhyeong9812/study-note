# domain-modeling/10-repositories-and-factories — 정답

## 정답

### 1. 리포지토리가 없을 때

- 저장 기술의 복잡함이 클라이언트 코드를 덮고, 개발자가 도메인 계층을 단순화해 모델이 의미를 잃는다(『DDD Reference』 Repositories 항목의 문제 서술).
- 제약 없는 쿼리의 위험
  1. 객체에서 특정 필드만 뽑아 캡슐화를 깬다.
  2. 애그리거트 **내부 객체**를 직접 만들어 루트를 건너뛰고, 루트가 도메인 규칙을 지킬 수 없게 한다.
- 결과: 도메인 로직이 쿼리와 애플리케이션 계층으로 옮겨 가고, 엔티티·값 객체는 데이터 그릇이 된다.

### 2. 리포지토리의 자리

```text
  도메인: interface Orders { byId(id); add(order); satisfying(spec); }
  인프라: JpaOrders / JdbcOrders / InMemoryOrders(테스트) implements Orders
```

- 도메인 전문가에게 의미 있는 기준으로 고르는 메서드, 추가·제거 메서드, 완전히 만들어진 객체(또는 지연 프록시) 반환.
- **직접 접근이 필요한 애그리거트 루트에만** 둔다. Spring Data 문서도 "애그리거트 루트마다 리포지토리 하나"라고 적는다.

### 3. 컬렉션 지향 vs 영속 지향

| | 컬렉션 지향 | 영속 지향 |
|---|---|---|
| 저장 | 처음 `add`, 이후 변경은 자동 반영 | 만들거나 바꿀 때마다 `save` |
| 전제 | 저장 장치가 변경을 추적 | 변경 추적 없음 |
| 예 | JPA/Hibernate 영속성 컨텍스트 | Spring Data JDBC, 키-값·문서 저장소 |

- Spring Data JDBC 문서: "저장하면 저장되고, 안 하면 안 된다. 더티 추적도 세션도 없다."

### 4. 규칙 복제의 결과

- 실험 A(PostgreSQL 17.11, 기준일 2026-10-03, 3회 같은 결과)
  - 메모리 판정: `[7, 9, 17, 19]` (4건)
  - 복제된 쿼리: 14건, **불일치 10건**
  - 명세 객체: `[7, 9, 17, 19]`, 불일치 0건
- 이유: 규칙 변경이 엔티티에만 들어가고 쿼리에는 옛 규칙(유예 0일)이 남았다.

### 5. 명세가 남기는 중복

- 같은 규칙을 Java 식(`isSatisfiedBy`)과 SQL 술어(`sqlWhere`)로 두 번 쓴다. 단일 출처는 "같은 클래스 안"까지다.
- 검증: 모든 행(또는 대표 픽스처)에 대해 메모리 판정 결과와 쿼리 결과가 같은지 비교하는 테스트. 실험 A의 불일치 계산이 그 테스트다.
- Criteria·Querydsl로 술어를 객체로 만들면 문자열 중복은 줄지만, 메모리 판정과의 중복은 남는다.

### 6. 메서드 수 (계산)

- 조건 3개의 비어 있지 않은 조합: 2³ − 1 = **7개**. 조건이 하나 늘 때마다 대략 두 배가 된다.
- 명세: 조건 3개(`status(s)`, `vip()`, `overdue(today)`) + 조회 메서드 1개(`satisfying(spec)`), 조합은 `and`·`or`로.

### 7. 생성 vs 재구성

| | 생성 | 재구성 |
|---|---|---|
| 식별자 | 새로 부여 | 저장된 것 유지 |
| 생성 시점 규칙 | 검사, 위반이면 거절 | 다시 묻지 않음, 구조적 무결성만 |

- Evans 6장(Goodreads 발췌로 확인): ① 재구성용 엔티티 팩토리는 새 추적 ID를 부여하지 않는다 — 부여하면 이전 모습과의 연속성이 끊기므로 식별 속성이 입력에 들어가야 한다. ② 불변식 위반을 다르게 다룬다 — 새 객체 생성에서는 그냥 거절하지만 재구성에서는 더 유연한 대응이 필요할 수 있다.

### 8. 생성 규칙 강화 후 500

- 원인: 행 → 객체 변환이 공개 생성 팩토리(`create`)를 탄다. 1년 전 정상 생성된 행이 새 생성 규칙에 걸린다. 실험 B: `create 경로로 재구성 → 시작일이 과거: 2025-01-01`.
- 대처: 재구성 경로를 분리해 ID를 유지하고 구조만 확인한다(`reconstitute`). 강화된 규칙을 기존 데이터에 어떻게 적용할지(유지·마이그레이션·격리)는 별도 결정으로 다룬다. 과거 데이터 픽스처로 회귀 테스트를 둔다.
- JPA: 공급자가 **무인자 생성자**(public 또는 protected, Jakarta Persistence 3.1 §2.1)와 필드·프로퍼티 접근으로 재구성한다. 그래서 생성 규칙은 공개 생성자·팩토리에 두고 무인자 생성자는 `protected`로 숨기는 경우가 많다.

### 9. save 누락

- JPA(컬렉션 지향)는 영속성 컨텍스트가 변경을 추적해 커밋 때 UPDATE를 낸다. 그래서 기존 코드에 `save` 호출이 없었을 수 있다.
- Spring Data JDBC(영속 지향)는 더티 추적이 없다. `save`를 부르지 않으면 DB에 반영되지 않는다. 오류도 나지 않는다.
- 대처: 쓰기 유스케이스마다 `save`를 부르는 틀을 정하고, 통합 테스트에서 다시 읽어 확인한다.

### 10. 내부 엔티티용 리포지토리

- 루트를 건너뛰므로 루트가 검사하는 불변식(예: 줄 합계 ≤ 한도)이 실행되지 않는다.
- 루트 버전도 오르지 않는다(05 실험 C·C-3: 자식 엔티티의 필드만 고치면 `mappedBy`든 소유 단방향이든 루트 `version` 그대로). 그래서 동시 수정 충돌도 잡히지 않는다.
- 대처: 리포지토리는 루트에만 두고, 줄은 루트 메서드로 고친다. 읽기만 필요하면 프로젝션을 쓴다.
