# domain-modeling/advanced/27-ab-assign — 정리 (힌트)

## 해결하는 문제

"사용자의 절반에게 새 화면"을 동전 던지기로 정하면, 같은 사람이 새로고침마다 다른 화면을 본다.\
배정을 저장해 두면 되지만, 첫 방문마다 쓰기가 생기고 실험 수 × 사용자 수만큼 행이 쌓인다.

```text
  동전 던지기   같은 사람 → 매번 다른 그룹   (자료 오염)
  저장          같은 사람 → 같은 그룹, 대신 쓰기·행 수·설정 어긋남
  해시          같은 열쇠+씨앗 → 늘 같은 칸  (저장 없이 같은 답)
```

쉬운 예: 학생 이름을 규칙으로 1반/2반에 넣으면 명단을 안 적어도 내일 다시 세어 같은 반이 나온다.\
똑같은 구조다: 열쇠(누구)와 씨앗(어느 실험)을 해시해 0~9,999 칸에 넣고, 칸이 비율 경계보다 작으면 B다.\
그런데 이 한 줄에도 정해지지 않은 것이 셋이다 — 무엇으로 나누나(열쇠 수명), 실험이 여럿이면(씨앗), 비율을 올리면(구간 늘리기/다시 섞기).\
실무 예: 기능 플래그 점진 배포, 카나리 배포, 추천·결제 화면 A/B 테스트 — 전부 "누구를 몇 %에 넣나"를 저장 없이 결정적으로 답해야 한다.

### 한눈에 — 쉽게 말하면

**A/B 배정 = 반 나누기.**

- 학교에서 학생을 1반/2반으로 나눈다고 하자. 공평하려면 아무렇게나가 아니라 **규칙으로** 나눠야 하고, 내일 다시 세어도 **같은 반**이 나와야 한다(명단을 안 적어두니까).
- A/B 테스트도 똑같은 구조다: "사용자의 절반에게 새 화면을 보여준다"는 한 줄에 정해지지 않은 것이 셋 숨어 있다 — ① **무엇으로 나누나**(회원 번호? 세션? 기기?) ② **실험이 여럿이면** 같은 씨앗을 쓰나 실험마다 다르게 하나 ③ **비율을 올리면** 기존 구간을 늘리나 다시 섞나.
- 핵심 장치는 해시다: 열쇠(누구)와 씨앗(어느 실험)을 섞어 0~9,999 중 한 칸에 넣고, 칸 번호가 비율보다 작으면 B다. **배정을 저장하지 않고 매번 다시 계산해도 같은 답**이 나온다.
  - *해시(hash)*: 문자열을 큰 숫자로 바꾸는 계산. 같은 입력이면 늘 같은 숫자, 다른 입력이면 고루 퍼진 숫자가 나온다.
  - *씨앗(salt)*: 해시에 섞는 별도 문자열. 씨앗이 다르면 같은 사람도 다른 칸에 떨어진다 — 실험끼리 배정을 가르는 손잡이. 다만 씨앗이 다르다고 저절로 독립이 되지는 않는다: 이 노트처럼 FNV-1a 단독에 끝만 다른 씨앗(`baseSalt|번호`)이면 실험 간 배정이 상관될 수 있다([data-analysis/14](../../../data-analysis/14-ab-testing-design/2-summary.md): 끝 글자만 다른 salt 8쌍 중 7쌍이 2 표준편차 밖, 최대 약 8 표준편차. fmix64 같은 마무리 섞기를 더하면 모두 ±1.4 표준편차 안).

```text
  "u:u1" + 씨앗 ──해시──▶ 칸 3,721   (0 ~ 9,999 만분율)
                              │
        percentB = 50 → 경계 5,000
                              ▼
        칸 < 5,000  →  B      3,721 < 5,000 이므로 B
        칸 ≥ 5,000  →  A
```

실무 예: 새 결제 화면 실험, 추천 알고리즘 실험, 점진적 배포(canary rollout) — 전부 "누구를 몇 %에 넣나"의 문제다.

## 동작·원리

### 전체 흐름

```text
"사용자의 절반에게 새 화면을"   ← 말로 된 요구사항 한 줄
        │  풀어보면 독립된 정책 축이 셋
        ▼
  KeyBy   무엇으로 나누나 — USER / SESSION / DEVICE  (셋의 수명이 다르다)
  Salt    실험마다 씨앗을 다르게 하나 — SHARED / PER_EXPERIMENT
  RampUp  비율을 올릴 때 — EXTEND(구간 늘리기) / RESHUFFLE(다시 섞기)
        │
        ▼
  assign(visitor, experiment, …)
    ① key()     방문자 → 열쇠 문자열 ("u:u1" / "s:s1" / "d:d1")
    ② saltFor() 실험 → 씨앗 (규칙에 따라 실험 번호·비율을 구분자와 함께 섞음)
    ③ bucket()  FNV 해시(씨앗|열쇠) → 0~9,999 칸
    ④ 칸 < percentB × 100  →  B, 아니면 A
        │
        ▼
  moved()    비율 변경 전후 그룹 이동 수 (B→A 가 생기면 사고)
  counts()   그룹별 인원  /  agreeing()  두 실험에서 같은 그룹인 사람 수
```

### 규칙 1 — 무엇으로 나누나 (`KeyBy` + `key`)

**어떤 요구사항인가**: "사용자의 절반"의 *사용자*가 누구인가. 같은 사람을 가리키는 값이 셋인데 **수명이 다르다**.

| 열쇠 | 수명 | 함정 |
|---|---|---|
| 회원 번호(USER) | 로그인해야 있다 | 로그인 안 한 사람은 빈 문자열 → 그냥 나누면 **전부 같은 칸** |
| 세션(SESSION) | 탭 닫으면 바뀜, 하루에 여러 개 | 같은 사람이 새로고침마다 다른 화면 |
| 기기(DEVICE) | 쿠키 지우면 바뀜 | 폰과 PC가 서로 다른 사람 |

요구사항 → 코드 번역: "로그인 안 한 사람을 회원 번호로 나눌 수는 없다" →

```text
key(visitor, USER) = 로그인했으면 "u:" + userId
                     안 했으면    "d:" + deviceId   ← 기기로 폴백
```

- *폴백(fallback)*: 원래 쓰려던 값이 없을 때 대신 쓰는 값.
- 측정 5: 익명 100,000명에서 회원 규칙과 기기 규칙이 A 50,256으로 **같다** — 로그인 전에는 회원 규칙 설정이 아무 일도 안 한다. 그리고 **로그인하는 순간 열쇠가 "d:…"에서 "u:…"로 바뀌어 그룹이 바뀔 수 있다.**
- 측정 4: 기기 하나에 세션 셋일 때, 세 세션이 다 같은 그룹인 기기는 7,975 / 33,334대뿐. 나머지 25,359대는 같은 사람이 새 화면과 옛 화면을 번갈아 본다 — **실험 차이가 작을수록 이 오염이 결론을 뒤집는다.**

### 규칙 2 — 칸 나누기 (`bucket`)

**어떤 요구사항인가**: 고루 퍼지고, **다시 돌려도 같은 값**이 나와야 한다(배정을 저장 안 하니까).

```text
bucket(key, salt):
  hash = FNV-1a( salt + "|" + key )      64비트 해시
  칸   = floorMod(hash, 10_000)           0 ~ 9,999
```

- **`String.hashCode`를 안 쓴다**: 자바 버전이 바뀌면 값이 바뀔 수 있다 → 그날 전원이 그룹을 옮기고 실험 결과가 통째로 못 쓰게 된다. 그래서 알고리즘이 명세로 고정된 FNV-1a를 직접 박는다.
  - *FNV-1a*: 바이트를 하나씩 XOR하고 소수를 곱하는 단순·결정적 해시. 언어·버전과 무관하게 같은 값.
> ⚠ 정정(2026-09-28): `String.hashCode`는 자바 버전이 바뀌어도 값이 바뀌지 않는다 — 계산식 `s[0]·31^(n-1) + … + s[n-1]`이 `java.lang.String` Javadoc에 명세로 고정돼 있다(JDK 1.2~). 실행·버전마다 바뀔 수 있는 것은 `Object.hashCode`(객체 식별 해시)나 enum의 기본 hashCode다. FNV-1a를 직접 박는 실제 이점은 **자바 밖(JS·Python 등 다른 서비스)에서도 같은 식으로 같은 칸을 재현**할 수 있다는 것이다(원본 README·impl 주석의 "버전이 바뀌면 바뀐다"에서 물려받은 오류).
- **`%`가 아니라 `floorMod`**: 해시가 음수면 `%`는 음수 칸을 내놓는다. floorMod는 항상 0~9,999.
- **만분율(10,000칸)인 이유**: 백분율(100칸)이면 1% 단위까지만 나눌 수 있다. 0.01% 점진 배포까지 담으려면 칸이 촘촘해야 한다.
- 측정 1: 100,000명에서 10% 설정 → B 10,103명, 50% → 50,200 : 49,800 — 1% 안쪽으로 맞는다. 비율이 정확해야 하는 이유는 **실험 결과를 나눌 때 분모**로 쓰기 때문.

### 규칙 3 — 씨앗 조립 (`saltFor`)

**어떤 요구사항인가**: 실험 둘을 같이 돌릴 때 그룹이 겹치면 안 된다.

```text
saltFor(experiment, saltRule, rampUp):
  salt = baseSalt
  PER_EXPERIMENT 이면  salt = salt + "|" + 실험번호
  RESHUFFLE 이면       salt = salt + "|" + 비율
```

- 측정 2: **같은 씨앗이면 두 실험이 100,000명 전부 같은 그룹**(100,000/100,000). 실험마다 씨앗이면 49,996/100,000 — 우연 수준. 같은 씨앗으로 실험 둘을 돌리면 두 실험의 B 그룹이 같은 사람들이라 **어느 실험의 효과인지 못 가른다.** 화면에는 실험이 둘로 보이는데 실제로는 하나다.
- **구분자 `|`가 필수다**: 그냥 이어 붙이면 실험 "a"+씨앗 "bc"와 실험 "ab"+씨앗 "c"가 같은 씨앗 "abc"가 된다 — 두 실험이 몰래 같은 그룹을 쓴다. (테스트: `saltsNeedASeparator`)
- **비율 0%·100%에서는 씨앗이 죽는다**: 전원 A거나 전원 B라 어느 씨앗이든 같다. 실험 켜기 전과 전면 적용 뒤에는 그 설정이 안 보이고, 그 사이 구간에서만 살아난다.

### 규칙 4 — 비율 올리기 (`RampUp` + `moved`)

**어떤 요구사항인가**: 10% → 20%로 올릴 때 기존 B 사용자는 어떻게 되나.

```text
칸 수직선 (0 ~ 9,999), 10% → 20% 로 올릴 때

EXTEND(구간 늘리기): 경계만 1,000 → 2,000 으로 민다
  0 ─────1,000─────2,000──────────────9,999
  [ 기존 B ][ 새로 B  ][        A         ]
  기존 B 는 전원 그대로 B      B→A = 0

RESHUFFLE(다시 섞기): 비율이 씨앗에 섞여 전 칸이 재배치
  → 비율을 올렸는데 8,046 명이 B→A (새 화면을 잃음)
```

- 측정 3 (100,000명, 10%→20%): 구간 늘리기 B→A **0** / A→B 9,882. 다시 섞기 B→A **8,046** / A→B 17,997.
- 그 8,046명은 실험 기간에 두 화면을 다 봤으니 **어느 그룹의 자료로도 못 쓴다.** `moved`가 B→A와 A→B를 따로 세는 이유 — 비율을 올렸는데 B→A가 생기면 그것이 사고다.
- **왜 이렇게 모델링했나**: RESHUFFLE은 "비율을 씨앗에 섞는다"는 한 줄로 구현된다 — 정책 차이가 코드 구조 차이가 아니라 **씨앗 조립 규칙 차이**로 표현된다. 그래서 세 축이 서로 독립적으로 조합된다.

## 쓰이는 자료구조·알고리즘

- **FNV-1a 문자열 해시** — `bucket`이 `(salt + "|" + key)`의 바이트를 하나씩 XOR하고 소수를 곱한다. 명세가 고정된 알고리즘이라 어느 언어로 구현해도 같은 값이다. `String.hashCode`도 자바 명세로 고정돼 있지만(JDK 1.2~) 자바 전용 식이라, 다른 언어의 서비스가 같은 칸을 재현하려면 FNV-1a처럼 널리 공개된 식이 편하다 — [algorithm/27-string-hashing](../../../algorithm/27-string-hashing/2-summary.md).
- **모듈러 연산(`Math.floorMod`)** — 64비트 해시를 10,000으로 나눈 나머지가 칸. `%`는 음수 해시에 음수를 내지만 floorMod는 항상 0 이상 — [algorithm/28-number-theory](../../../algorithm/28-number-theory/2-summary.md)의 나머지 정의.
- **해시 버킷 배정** — "열쇠를 해시해 칸에 넣고 칸 번호로 가른다"는 해시맵의 인덱스 계산과 같은 뼈대다 — [data-structure/05-hashmap](../../../data-structure/05-hashmap/2-summary.md). 칸이 10,000개(만분율)라 칸 해상도는 0.01%다. 다만 이 코드의 `percentB`는 정수라 실제로 설정할 수 있는 비율은 1% 단위다(`Assigner.java` 52·141행).
- **일관된 해싱과 같은 관심사** — 비율을 올릴 때 "이미 B인 사람을 안 옮긴다"(EXTEND)는 노드를 늘릴 때 키 이동을 최소화하는 [data-structure/31-consistent-hashing](../../../data-structure/31-consistent-hashing/2-summary.md)과 같은 문제다. RESHUFFLE은 전 칸 재배치라 해시 테이블의 리해싱에 가깝다.
- **구분자로 조립한 문자열 키** — `salt|experiment|percent`처럼 `|`를 끼워야 `"bc"+"a"`와 `"b"+"ca"`가 갈린다. 여러 필드를 문자열 하나로 합칠 때의 모호성을 막는 직렬화 규칙.
  - *직렬화(serialization)*: 여러 값을 한 줄 문자열(또는 바이트)로 바꾸는 것. 되돌릴 수 있어야 모호하지 않다.
- **순수 함수로서의 배정** — `assign`은 입력(방문자·실험·enum 셋·기본 씨앗)만으로 답이 정해지고 상태를 안 든다. 그래서 저장 없이 재현되고, `moved`·`counts`·`agreeing`은 그 함수를 전원에 대해 돌려 세기만 한다.
- **레이트 리밋의 해시 버킷** — 같은 "열쇠 → 칸" 구조가 [ops-patterns/04-rate-limiter](../../../ops-patterns/04-rate-limiter/2-summary.md)의 키별 카운터에도 쓰인다. 열쇠를 무엇으로 잡느냐(회원/세션/기기)의 함정도 그대로 옮겨 간다.

## 적용 — 풀어나가는 법

이런 문제를 받으면 "절반"을 어떻게 정할지보다 **"사용자"가 누구인지(열쇠의 수명)**를 먼저 정한다.\
그 다음 배정을 저장할지 계산할지 고르고, 계산이면 해시·나머지·씨앗 조립을 명세 고정으로 박는다.\
마지막으로 실험 둘·비율 인상·세션 열쇠 같은 조합을 실제 인원으로 돌려 `agreeing`·`moved`를 센다 — 화면의 설정 이름이 아니라 그 수가 오염을 말해준다.\
아래는 원본 챕터가 시킨 과제 목록이다.

### 문제 — 이 챕터가 시키는 것

주어진 말은 한 줄이다(원본 `Assigner` javadoc 그대로).

```text
  "사용자의 절반에게 새 화면을 보여준다"
```

이 한 줄에 **정해지지 않은 것이 셋**이다(원문 그대로).

```text
  무엇으로 나누나     회원 번호인가 세션인가 기기인가
  실험이 여럿이면     같은 씨앗을 쓰나 실험마다 다른 씨앗을 쓰나
  비율을 올리면       기존 구간을 늘리나 다시 섞나
```

README가 먼저 못 박는 장면은 이것이다.

```text
  실험 1 (50 %)   과 실험 2 (50 %)   를 같은 씨앗으로 돌린다

    같은 씨앗       두 실험이 100,000 명 전부 같은 그룹
    실험마다 씨앗   같은 그룹 49,996 명. 우연 수준이다
```

**"두 실험을 같이 돌려놓고 어느 쪽 효과인지를 못 가른다. 그리고 실험 화면에는 실험이 둘로 보인다."**

테스트가 못 박은 계약(`AssignerTest`):

- 익명 방문자는 `KeyBy.USER` 와 `KeyBy.DEVICE` 의 **열쇠가 같다**(세션 열쇠와는 다르다).
- 같은 열쇠·같은 씨앗이면 **늘 같은 칸**, 씨앗이 다르면 다른 칸, 칸은 항상 **0 이상 10,000 미만**.
- 같은 기기의 세션 셋을 `KeyBy.SESSION` 으로 나누면 **갈린다**(서로 다른 그룹이 2가지 나온다).
- 비율 50% 실험 둘 + `Salt.SHARED` → 1,000명 전원이 **같은 그룹**, `PER_EXPERIMENT` 면 600명 미만.
- 씨앗 `"bc"`+실험 `"a"` 와 씨앗 `"b"`+실험 `"ca"` 는 **서로 다른 씨앗**이어야 한다(구분자 필요).
- 비율 0/100 에서는 `SHARED` 와 `PER_EXPERIMENT` 의 결과가 **같다**(씨앗이 죽는다).
- 10%→20% 에서 `EXTEND` 는 **B→A 가 0명**, `RESHUFFLE` 은 0명이 아니다.
- 비율을 안 바꾸면 `RESHUFFLE` 도 **아무도 안 옮긴다**.
- `BUCKETS == 10_000`.
- 비율 0~100 밖·빈 세션/기기 번호·`null` 회원 번호·빈 씨앗은 전부 `IllegalArgumentException`.

## 장애 시나리오와 대처

**1. 배정은 기기 단위인데 지표는 회원 단위로 집계했다**

- 현상: 실험 결과의 차이가 통계적으로 유의하게 나왔는데, 다시 돌리면 재현이 안 된다.
- 보이는 형태: 회원 한 명이 폰(B)과 PC(A)로 양쪽 그룹에 들어가 있다. 회원 단위 지표 표에서 같은 사람이 두 행에 있다.
- 원인: **배정 단위와 분석 단위가 다르다.** `KeyBy.DEVICE`로 나누면 한 회원이 기기 수만큼 독립 표본처럼 세어져, 실제보다 표본이 많아 보이고 분산이 작게 잡힌다(커리큘럼 ⚠ "배정 단위 불일치 → 분산 과소"). 세션 열쇠면 더 심하다(측정 4: 네 기기 중 세 대가 갈린다).
- 대처: 배정 열쇠 = 지표의 집계 단위로 맞춘다. 회원 단위로 볼 실험이면 `KeyBy.USER`, 로그인 전 트래픽이 본체면 기기로 배정하고 기기 단위로 집계한다. 로그인 전후를 잇는 문제는 정답 13번 참고.
  - *분산 과소(variance underestimation)*: 표본이 실제보다 많다고 착각해 결과의 흔들림을 작게 잡는 것. 없는 차이를 "유의하다"고 믿게 된다.

**2. 스테이징에서 확인한 배정이 프로덕션에서 다르게 나온다**

- 현상: QA가 스테이징에서 "u1은 B"를 확인했는데, 프로덕션에서 같은 회원이 A를 본다.
- 보이는 형태: 같은 `experiment`·같은 `percentB`인데 `assign` 결과가 환경마다 다르다. 비율 합계는 두 환경 모두 정상이라 `counts`로는 안 보인다.
- 원인: `Assigner(baseSalt)`의 **기본 씨앗이 환경마다 다르다**(설정 파일·환경 변수 차이). 씨앗은 칸 전체를 재배치하므로 비율은 그대로여도 개인의 그룹은 전부 바뀐다.
- 대처: 기본 씨앗을 환경 설정이 아니라 **실험 정의의 일부(계약)**로 둔다. 배포 전 검사로 옛 씨앗의 `Assigner`와 새 씨앗의 `Assigner`를 각각 만들어, 같은 방문자 목록에 `assign`을 돌려 그룹이 달라진 사람 수를 센다 — 0이 아니면 씨앗이 바뀐 것이다. `moved`는 한 `Assigner`(한 씨앗) 안에서 비율 전후만 비교하므로 이 검사에는 못 쓴다.

**3. 첫 주에 좋던 결과가 셋째 주에 사라진다**

- 현상: B 그룹 전환율이 첫 주 +8%(예시 수치)였다가 주가 갈수록 0에 가까워진다.
- 보이는 형태: 주 단위로 자른 차이 그래프가 우하향한다. 누적으로만 보면 여전히 양수라 "성공"으로 읽힌다.
- 원인: **신규성 효과** — 새 화면이라서 눌러본 것이지 더 좋아서가 아니다(커리큘럼 ⚠). 배정이 결정적이라 같은 사람이 계속 B를 보므로 익숙해지면 효과가 빠진다. 배정 코드의 문제가 아니라 관측 기간의 문제다 [?].
- 대처: 실험 기간을 미리 정하고 주 단위 차이를 따로 본다. 신규 사용자와 기존 사용자를 나눠 집계하면 신규성 효과가 어느 쪽에서 나는지 갈린다. EXTEND로 비율을 올렸을 때 새로 들어온 사람은 노출 기간이 짧으므로 "언제부터 B였나"를 같이 기록한다(정답 13번 참고).

### 경계·모서리 케이스 — 함정 → 올바른 처리

| 함정 | 무슨 일이 나나 | 올바른 처리 |
|---|---|---|
| `String.hashCode` 사용 | 자바 버전 교체일에 전원 그룹 이동 → 그날 실험 폐기 | 명세 고정 해시(FNV-1a) 직접 구현 |
| `%`로 칸 계산 | 해시 음수면 칸도 음수 | `Math.floorMod` |
| 씨앗+열쇠를 그냥 이어 붙임 | "a"+"bc" == "ab"+"c" → 실험이 몰래 겹침 | 구분자 `\|`를 끼워 조립 |
| 익명을 회원 번호로 나눔 | 빈 문자열 → 전부 같은 칸 | 기기 번호로 폴백 |
| 비율 0~100 밖, 빈 실험 번호, null id | 의미 없는 배정 | Experiment·Visitor 생성자에서 IllegalArgumentException |
| 세션 열쇠 선택 | 같은 기기 세 세션이 갈림 → 자료 오염 | 기기/회원 열쇠 선택 + 오염 크기를 측정으로 확인 |

> ⚠ 정정(2026-09-28): 표 첫 행의 "자바 버전 교체일에 전원 그룹 이동"은 `String.hashCode`에는 일어나지 않는다(Javadoc 명세 고정). 위 규칙 2의 정정 참고.

변종 검증: 고칠 것이 없었다 — 변종 14개 전부 잡힘(floorMod→%, 만분율→백분율, 구분자 제거, 익명 폴백 제거가 각각 다른 테스트에 걸렸다).

## 핵심 문장
- "절반에게 새 화면"의 미정 사항은 셋 — 열쇠(KeyBy) × 씨앗(Salt) × 비율 인상(RampUp) — 이고, 각각 enum 한 축으로 분리해야 조합을 측정으로 비교할 수 있다.
- 배정은 저장하지 않고 매번 해시로 다시 계산한다 — 그래서 해시는 언어 버전과 무관하게 결정적이어야 하고(`hashCode` 금지), 칸은 floorMod로 음수를 막는다.
> ⚠ 정정(2026-09-28): `String.hashCode`는 명세로 고정돼 버전마다 바뀌지 않는다. FNV-1a를 쓰는 이유는 언어 밖 재현성이다 — 규칙 2의 정정 참고.
- 씨앗이 실험 독립성의 손잡이다 — 같은 씨앗이면 두 실험이 100% 겹치고, 구분자 없이 이어 붙이면 몰래 겹친다. 씨앗이 달라도 FNV-1a 단독·끝만 다른 씨앗이면 배정이 상관될 수 있어, 마무리 섞기(fmix64 등)와 실험 간 일치율 점검이 필요하다([data-analysis/14](../../../data-analysis/14-ab-testing-design/2-summary.md)).
- 비율을 **올렸는데** 새 화면을 **잃는** 사람(B→A)이 생기면 사고다 — EXTEND는 0명, RESHUFFLE은 8,046명이고 그들의 자료는 양쪽 그룹 어디에도 못 쓴다.
- 열쇠의 수명이 실험 자료의 순도를 정한다 — 세션 열쇠는 같은 사람을 가르고, 익명+회원 열쇠는 로그인 순간 그룹을 바꾼다.

### 용어 풀이

- **A/B 테스트**: 사용자를 두 그룹으로 나눠 화면·기능을 다르게 보여주고 효과를 비교하는 실험.
- **열쇠(key)**: 방문자를 대표하는 문자열. 회원 번호("u:")·세션("s:")·기기("d:") 중 하나 — 수명이 다 다르다.
- **씨앗(salt)**: 해시에 섞는 추가 문자열. 실험 번호·비율을 섞으면 실험끼리·인상 전후끼리 배치가 갈린다(독립에 가까워지려면 해시의 섞임도 충분해야 한다 — FNV-1a 단독에 끝만 다른 씨앗이면 상관될 수 있다, [data-analysis/14](../../../data-analysis/14-ab-testing-design/2-summary.md)).
- **해시(hash)**: 문자열 → 숫자 변환. 같은 입력 = 같은 출력, 고른 분포가 조건.
- **FNV-1a**: 명세로 고정된 단순 해시 알고리즘. 언어·버전이 바뀌어도 같은 값 — `String.hashCode`의 대체.
> ⚠ 정정(2026-09-28): `String.hashCode`도 명세로 고정된 식이라 버전이 바뀌어도 같다. FNV-1a의 차이는 자바 밖에서도 같은 식을 쓸 수 있다는 점이다.
- **칸(bucket)**: 해시를 10,000으로 나눈 나머지(만분율). 칸 번호 < 경계면 B.
- **floorMod**: 음수에도 항상 0 이상 나머지를 주는 나눗셈. `%`는 음수를 낼 수 있다.
- **폴백(fallback)**: 원래 값이 없을 때 대신 쓰는 값. 익명 방문자의 기기 번호.
- **램프업(ramp-up)**: 실험 비율을 점점 올리는 것. EXTEND(구간 늘리기)는 기존 B를 보존, RESHUFFLE(다시 섞기)은 전면 재배치.
- **오염(contamination)**: 한 사람이 두 화면을 다 봐서 어느 그룹 자료로도 못 쓰게 되는 것. 세션 열쇠·RESHUFFLE·로그인 전환이 만든다.
- **결정적(deterministic)**: 같은 입력이면 언제 어디서 돌려도 같은 출력. 배정을 저장 안 하는 설계의 전제.
