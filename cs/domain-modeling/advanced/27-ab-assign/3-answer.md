### A. 과제

#### 0. 말 한 줄이 안 말해주는 것

```text
 안 말해준 것          가능한 읽기
 "사용자"          →  회원(USER) / 세션(SESSION) / 기기(DEVICE)
 (실험이 여럿이면?) →  같은 씨앗(SHARED) / 실험마다 씨앗(PER_EXPERIMENT)
 (비율을 올리면?)   →  구간 늘리기(EXTEND) / 다시 섞기(RESHUFFLE)
```

- "사용자"가 안 정해진 이유: **같은 사람을 가리키는 값이 셋인데 셋의 수명이 다르다.**\
  말하는 사람은 "한 사람"을 떠올리지만 시스템에는 그 한 사람을 가리키는 번호가 셋 있다.
- 수명:

```text
 회원 번호   로그인해야 있다. 로그아웃하면 없다        ← 없을 때가 있다
 세션 번호   탭을 닫으면 바뀐다. 하루에 여러 개 생긴다  ← 제일 짧다
 기기 번호   쿠키를 지우면 바뀐다. 폰과 PC 가 둘이다    ← 사람보다 많다
```

> **수명(lifetime)** — 그 식별자가 같은 값으로 유지되는 기간.\
> 예: 세션 번호는 탭을 닫으면 끝이라 "한 사람"을 하루도 못 붙잡아 준다.

- "서로 간섭한다": **한 축의 값이 다른 축의 효과를 없앤다.**\
  실제 예 셋 —
  - 비율이 0%나 100%면 **씨앗 축이 죽는다**(어느 씨앗을 써도 전원 A/전원 B).
  - `RESHUFFLE` 을 켜면 씨앗 문자열에 비율이 섞여, **비율을 올릴 때마다 실험이 새 실험이 된다.**
  - 로그인 전에는 `USER` 규칙이 기기 폴백을 타서 **`DEVICE` 규칙과 완전히 같아진다.**
- 저장 안 하고 매번 계산하면 필수가 되는 것: **결정성**이다.\
  같은 열쇠·같은 씨앗이면 반년 뒤에 불러도 같은 칸이 나와야 한다.

> **결정적(deterministic)** — 같은 입력을 넣으면 언제 어디서 돌려도 같은 결과가 나오는 성질.\
> 예: 배정을 DB에 안 적어두므로, 함수가 결정적이 아니면 새로고침할 때마다 사용자가 다른 화면을 본다.

#### 2. TODO 2 — bucket

정답 코드:

```java
long hash = 0xcbf29ce484222325L;
for (byte value : (salt + "|" + key).getBytes(StandardCharsets.UTF_8)) {
    hash ^= value & 0xff;
    hash *= 0x100000001b3L;
}
return (int) Math.floorMod(hash, BUCKETS);
```

> **FNV-1a 해시** — 바이트를 하나씩 XOR 하고 정해진 소수를 곱해 나가는 간단한 해시 계산.\
> 예: 자바 버전이나 JVM 구현과 무관하게 **식이 코드 안에 통째로 적혀 있어서**, 몇 년 뒤에 돌려도 같은 값이 나온다.

- `String.hashCode` 를 쓰면 안 되는 이유: **그 값은 언어가 보장해 준 것이 아니라 구현 세부**다.\
  버전이 바뀌면 값이 바뀔 수 있다.
- 바뀌는 날 벌어지는 일: **전원이 그룹을 옮긴다.**\
  배정을 저장하지 않았으므로 옛 배정이 어디에도 없다.\
  그날 이후의 자료는 옛 자료와 이어 붙일 수 없어 **실험 결과가 통째로 못 쓰게 된다.**
- `floorMod` 를 쓰는 이유: **해시가 음수일 수 있고, 자바의 `%` 는 음수를 그대로 음수로 돌려준다.**

```text
 -7 % 10          = -7     ← 부호가 왼쪽 값을 따라간다
 Math.floorMod(-7, 10) = 3  ← 항상 0 이상
```

> **`floorMod`** — 나머지를 구하되 결과를 항상 0 이상으로 만드는 연산.\
> 예: 시계에서 "3시간 전"을 구할 때 1시 − 3시간을 −2시가 아니라 10시로 보는 것과 같다.

- 칸이 음수면: `bucket < percentB * 100` 비교에서 **음수는 어떤 경계보다도 작다.**\
  그래서 **해시가 음수인 사람은 전부 B** 가 된다.\
  해시의 절반쯤이 음수이므로, 50% 실험이 대략 75%(= 50% + 남은 절반의 절반) B 가 된다. (대략 계산 — 내 추론)\
  잡히는 곳은 `bucket >= 0` 단언과 비율 측정 둘 다다.
- 구분자가 필요한 이유: **이어 붙이기만 하면 경계가 사라진다.**

```text
 구분자 없음   씨앗 "bc" + 실험 "a"  = "bca"
               씨앗 "b"  + 실험 "ca" = "bca"   ← 같다! 두 실험이 몰래 같은 그룹
 구분자 있음   "bc|a"  vs  "b|ca"              ← 다르다
```

- 칸을 10,000개로 잡은 이유: **잘게 자를 수 있어야 한다.**\
  칸이 100개면 최소 단위가 1%인데, 실험은 대개 **0.1%부터** 연다.\
  만분율이면 0.01%까지 열 수 있다.

#### 3. TODO 3 — saltFor

정답 코드:

```java
String salt = baseSalt;
if (saltRule == Salt.PER_EXPERIMENT) {
    salt = salt + "|" + experiment.id();
}
if (rampUp == RampUp.RESHUFFLE) {
    salt = salt + "|" + experiment.percentB();

```

- 재료 둘: **실험 번호**(`Salt.PER_EXPERIMENT` 가 켠다)와 **비율**(`RampUp.RESHUFFLE` 이 켠다).

```text
 SHARED   + EXTEND      →  "salt"
 PER_EXP  + EXTEND      →  "salt|exp1"
 SHARED   + RESHUFFLE   →  "salt|50"
 PER_EXP  + RESHUFFLE   →  "salt|exp1|50"
```

- 독립을 만드는 원리: **씨앗이 다르면 같은 사람의 해시 입력이 통째로 달라진다.**\
  해시는 입력이 1비트만 달라도 결과가 전혀 다른 값이 되므로, 두 실험의 칸이 서로 무관해진다.
- `RESHUFFLE` 이 비율을 섞으면: **비율을 건드리는 순간 씨앗이 바뀌어 전원 재계산**된다.\
  10%→20% 로 올리면 사실상 **새 실험**이 되는 셈이다.
- `EXTEND` 는 비율을 **안 섞는다.**\
  그래서 비율을 바꿔도 **칸 번호가 그대로**이고, B 구간이 넓어지기만 한다 — B였던 사람은 계속 B다.
- 비율을 안 바꾸면 `RESHUFFLE` 도 아무도 안 옮기는 이유: **씨앗 문자열이 그대로**이기 때문이다.\
  `RESHUFFLE` 은 "늘 섞는" 규칙이 아니라 "비율이 움직일 때 섞이는" 규칙이다.\
  그리고 비율은 실험 중에 여러 번 올린다 — **올릴 때마다** 섞인다.
- 같은 문자열을 공유하는 설계:
  - 장점 — **손잡이가 하나**다. 씨앗 문자열 하나만 보면 "이 배정이 무엇에 의존하는지"를 다 알 수 있다.
  - 단점 — 두 축이 **은근히 얽힌다.** 구분자를 잘못 쓰면 실험 번호와 비율이 서로의 자리를 침범할 수 있고(예: 실험 번호가 `"exp1|50"` 이면), 씨앗 문자열만 보고는 어느 축이 켜져 있는지 구분이 안 된다. (원본에 답 없음 — 내 추론)

#### 4. TODO 4 — moved

정답 코드:

```java
int lost = 0;
int gained = 0;
for (Visitor visitor : visitors) {
    String was = assign(visitor, before, keyBy, saltRule, rampUp);
    String now = assign(visitor, after, keyBy, saltRule, rampUp);
    if (was.equals(B) && now.equals(A)) {
        lost++;
    } else if (was.equals(A) && now.equals(B)) {
        gained++;
    }
}
return new int[] {lost, gained};
```

- 두 방향을 따로 세는 이유: **의미가 정반대**다.\
  A→B 는 비율을 올렸으니 **당연히 생겨야 하는 이동**이고, B→A 는 **생기면 안 되는 이동**이다.\
  합쳐서 "25,000명이 바뀌었다"고 하면 그 안에 사고가 숨는다.
- 사고는 **B→A**다. 비율을 **올렸는데** 새 화면을 잃는 사람이 생긴 것이다.
- `EXTEND` 에서 B→A 가 0인 이유:

```text
 씨앗이 같으므로 칸 번호는 그대로다.
   10 %  →  경계 1,000    [0 ........ 1000) 이 B
   20 %  →  경계 2,000    [0 .............. 2000) 이 B

   칸 700  : 700 < 1000 → B,  700 < 2000 → B   그대로 B
   칸 1,500: 1500 ≥ 1000 → A, 1500 < 2000 → B  A 에서 B 로  (당연한 이동)
   B 구간이 옛 B 구간을 통째로 포함하므로 B → A 는 있을 수 없다
```

> **포함 관계(superset)** — 새 구간이 옛 구간을 통째로 감싸는 것.\
> 예: 옛날에 뽑힌 번호표가 새 범위 안에 그대로 들어 있으면, 한 번 당첨된 사람은 계속 당첨이다.

- 자료를 못 쓰는 이유: 그 사람은 실험 기간에 **새 화면도 보고 옛 화면도 봤다.**\
  B 그룹의 성과라고 하기에는 A 도 봤고, A 그룹이라고 하기에는 B 도 봤다.\
  어느 쪽 평균에 넣어도 그 사람 때문에 결과가 흐려진다.
- 비율을 **내릴** 때: `EXTEND` 도 **B→A 가 생긴다.**\
  구간이 줄어들면 `[경계새, 경계옛)` 안에 있던 사람들이 B 에서 밀려난다.\
  즉 `EXTEND` 가 보장하는 것은 "아무도 안 잃는다"가 아니라 **"올릴 때는 아무도 안 잃는다"** 뿐이다. (원본에 답 없음 — 내 추론, 배정식에서 바로 나옴)

#### 5. 주어진 `assign` — 배정식

- 경계는 **`<`** 다. `<=` 로 쓰면 칸 하나가 더 B 에 들어가 **10,000명 중 1명꼴**로 많아진다.\
  더 중요한 것은 0% 일 때다 — `<=` 면 경계가 0이어도 칸 0인 사람이 B 가 되어 **"0%인데 B가 있다"** 가 된다.
- 비율 0%: 경계 `0 * 10000 / 100 = 0`.\
  칸은 0 이상이므로 `bucket < 0` 은 절대 참이 아니다 → **전원 A.**
- 비율 100%: 경계 `100 * 10000 / 100 = 10,000`.\
  칸은 9,999 이하이므로 항상 참이다 → **전원 B.**
- 순서를 바꾸면:

```text
 percentB * BUCKETS / 100     50 * 10000 / 100 = 5,000   맞다
 percentB / 100 * BUCKETS     50 / 100 = 0 (정수 나눗셈) → 0 * 10000 = 0
                              → 100 % 를 뺀 모든 비율에서 전원 A
```

> **정수 나눗셈(integer division)** — 소수점을 버리는 나눗셈.\
> 예: 자바에서 `50 / 100` 은 0.5 가 아니라 **0** 이다. 곱셈을 먼저 해야 소수점이 안 버려진다.

### B. 개념

#### 6. 측정 — 발견 하나: 비율은 1퍼센트 안쪽

- 10%: B 가 **10,103명**, 즉 10.103% 다. 설정과 **0.103 퍼센트포인트** 차.
- 정확해야 하는 이유: **실험 결과를 나눌 때 분모**로 쓰기 때문이다.\
  "B 그룹의 구매율"은 `B 그룹 구매 수 / B 그룹 사람 수` 인데, 그 분모가 틀리면 비율이 틀린다.
- 설정값으로 나누면: 10,000명으로 나눠야 할 것을 실제로는 10,103명이 있으므로 **구매율이 1% 과대평가**된다.\
  실험의 효과 크기가 몇 퍼센트인 상황에서 1% 오차는 결론을 바꿀 수 있다.\
  그래서 **배정 수를 실제로 세야** 한다.
- 오차의 근본 이유: **해시가 사람을 칸에 던지는 것은 동전 던지기와 같다.**\
  100,000번 던져 10%를 노리면 평균 10,000, 흔들림(표준편차)은 `√(100,000 × 0.1 × 0.9) ≈ 95` 명이다.\
  측정된 103명 차이는 그 흔들림 범위 안이다 — **버그가 아니라 정상적인 무작위 오차**다. (계산은 내 추론, 측정치는 원본)

> **표준편차(standard deviation)** — 무작위로 흔들리는 값이 평균에서 보통 얼마나 벗어나는지.\
> 예: 동전 100,000번에서 앞면이 정확히 50,000번 나오는 일은 오히려 드물고, 보통 ±158번쯤 어긋난다.

#### 7. 측정 — 발견 둘: 같은 씨앗

- 전부 같은 그룹인 이유: `Salt.SHARED` 면 `saltFor` 가 **실험 번호를 안 섞는다.**\
  두 실험의 씨앗이 `"salt"` 로 똑같고, 열쇠도 같은 사람이니 **해시 입력이 완전히 같다.**\
  같은 입력 → 같은 칸 → 두 실험의 비율까지 같으니(둘 다 50%) 같은 경계 → **같은 그룹.**

```text
 실험 1  bucket("u:u1", "salt") = 3,721  <  5,000  →  B
 실험 2  bucket("u:u1", "salt") = 3,721  <  5,000  →  B      (똑같은 계산)
 100,000 명 전부 이런 식이다 → 일치 100,000 / 100,000
```

- 49,996이 우연 수준인 이유: 두 실험이 독립이면 **같은 그룹일 확률이 50%** 다(BB 25% + AA 25%).\
  100,000 × 0.5 = 50,000 이고, 측정치 49,996은 그 흔들림 안이다.
- 못 하게 되는 것: **어느 실험의 효과인지 분리**다.\
  B 그룹이 같은 사람들이라면 그들은 두 새 기능을 **동시에** 겪었다.\
  구매율이 올랐을 때 새 결제 화면 덕인지 새 추천 덕인지 가를 방법이 없다.

> **교락(confounding)** — 두 원인이 늘 함께 움직여서 어느 쪽 효과인지 못 가르는 상태.\
> 예: 새 화면을 본 사람이 전부 새 추천도 받았다면, 결과의 공을 누구에게 줄지 정할 수 없다.

- 무서운 이유: **화면에는 실험이 둘로 보인다.**\
  실험 목록에 `exp1`, `exp2` 가 따로 있고 각각 50%라고 적혀 있다.\
  겹쳤다는 사실은 어디에도 안 뜬다 — **재보기 전에는 알 수 없다.**

#### 8. 측정 — 발견 셋: 다시 섞기

```text
 10 % → 20 %, 방문자 100,000 명
               B→A       A→B
  구간 늘리기     0      9,882
  다시 섞기   8,046     17,997
```

- 잃는 사람: **8,046명.**
- 못 쓰는 이유: 그 8,046명은 실험 기간에 **B 였다가 A 가 됐다.**\
  두 화면을 다 본 사람이라 어느 그룹의 자료로도 쓸 수 없다.
- `EXTEND` 의 A→B 9,882명: **칸이 [1,000, 2,000) 구간에 있던 사람들**이다.\
  10,000개 칸 중 1,000개니까 기대값 10,000명이고, 측정치 9,882는 그 근처다.
- `RESHUFFLE` 의 A→B 가 더 큰 이유: 씨앗이 바뀌어 **전원이 다시 던져지기** 때문이다.\
  손계산으로 맞춰보면:

```text
 올리기 전  B 10,103 명,  A 89,897 명
 다시 섞으면 각자 독립적으로 20 % 확률로 B 가 된다

   B → A  기대  10,103 × 0.8  ≈  8,082      측정 8,046
   A → B  기대  89,897 × 0.2  ≈ 17,979      측정 17,997

 구간 늘리기의 A → B 는 "새로 늘어난 10 % 칸"에 있던 사람만  ≈ 9,882
```

- 그럼에도 다시 섞고 싶어지는 상황: **앞선 실험의 그림자를 지우고 싶을 때**다.\
  10%였을 때의 B 그룹이 특정 성향으로 치우쳐 있었다면(예: 초기 사용자만 들어왔다면) 그 편향이 20%에도 그대로 남는다.\
  다시 섞으면 편향은 사라지지만 **대신 8,046명의 자료를 잃는다** — 어느 쪽을 잃을지의 교환이다. (원본에 답 없음 — 내 추론)

#### 9. 측정 — 발견 넷: 세션으로 나누기

- 같은 그룹인 기기: **7,975 / 33,334.** 나머지 **25,359대**가 오염된다.
- 우연히 다 같을 확률: 세션 셋이 각각 독립적으로 50%면 **AAA 또는 BBB = 2 × 0.5³ = 25%** 다.\
  33,334 × 0.25 ≈ 8,334 이고 측정치는 7,975 — 대체로 맞는다. (계산은 내 추론, 측정치는 원본)\
  즉 **네 기기 중 세 대**는 화면이 바뀌는 것을 본다.
- 오염된 기기의 자료: **한 사람의 행동이 두 그룹에 반씩 들어간다.**\
  A 그룹 평균에도 그 사람이 있고 B 그룹 평균에도 그 사람이 있다.
- 차이가 작을수록 뒤집히는 이유: 오염은 **두 그룹의 평균을 서로 끌어당긴다.**\
  같은 사람이 양쪽에 들어가면 두 그룹이 점점 닮아져서 **진짜 차이가 작아 보인다.**\
  원래 차이가 크면 희석돼도 남지만, 원래 차이가 1~2%면 희석만으로 사라지거나 부호가 바뀔 수 있다.

#### 10. 측정 — 발견 다섯·여섯

- 같은 답을 내는 이유: 익명이면 `USER` 규칙이 **기기 번호로 폴백**한다.\
  즉 `key(visitor, USER) == key(visitor, DEVICE)` 이므로 같은 칸, 같은 그룹이다(A 둘 다 50,256).\
  세션으로 나눈 것만 다르다(A 49,983).
- "아무 일도 안 한다"의 뜻: 로그인 전 트래픽에서 **`USER` 와 `DEVICE` 를 아무리 바꿔도 결과가 안 변한다.**\
  설정 화면에는 선택지가 두 개로 보이는데 실제로는 하나다.\
  그리고 **로그인하는 순간** 열쇠가 바뀌어 그룹이 바뀔 수 있다 — 설정이 그때 갑자기 살아난다.
- 비율 0/100에서 씨앗이 죽는 이유: 경계가 0이나 10,000 이라 **칸 번호를 아예 안 본다.**\
  칸을 정하는 것이 씨앗인데, 칸을 안 보니 씨앗도 안 본다.

```text
 비율 0   경계 0       bucket < 0      →  칸이 무엇이든 A
 비율 100 경계 10,000  bucket < 10,000 →  칸이 무엇이든 B
 그 사이에서만 칸이 답을 가른다 = 씨앗이 살아 있는 구간
```

- 함정인 이유: **문제가 안 보이는 구간에서 설정을 켜고, 보이는 구간에서 사고가 난다.**\
  0%로 두고 "씨앗 설정 잘 되나" 확인하면 아무 이상이 없다.\
  10%로 여는 순간 잘못된 씨앗이 처음으로 효력을 갖는다.
- 알아채는 법: **두 설정의 결과를 직접 비교하는 테스트**를 쓴다.\
  원본이 한 방식이 그것이다 — 0%와 100%에서 `SHARED` 와 `PER_EXPERIMENT` 의 `counts` 가 같다는 것을 **일부러 단언해** 놓았다.\
  "여기서는 설정이 죽는다"를 계약으로 적어둔 것이다.

#### 11. 함정

- 넷:
  1. **`String.hashCode` 를 쓰는 것** — 버전이 바뀌면 전원이 그룹을 옮기고, 그날 실험 결과가 통째로 못 쓰게 된다.
  2. **`%` 로 칸을 구하는 것** — 해시가 음수면 칸도 음수가 된다.
  3. **씨앗과 열쇠를 그냥 이어 붙이는 것** — 실험 `"a"`+씨앗 `"bc"` 와 `"ab"`+`"c"` 가 같은 씨앗이 된다.
  4. **로그인 안 한 사람을 회원 번호로 나누는 것** — 전부 같은 칸에 들어간다.
- 조용한 것과 요란한 것:

```text
 요란   로그인 안 한 사람 전원 한 칸   →  비율이 0:100 으로 대놓고 틀어진다
 조용   씨앗 구분자 누락               →  두 실험이 몰래 겹친다. 화면은 정상
 조용   hashCode 사용                  →  평소엔 멀쩡하다. 버전 올린 날 한 번에 터진다
 중간   % 로 칸 구하기                 →  비율이 항상 한쪽으로 치우친다(세면 보인다)
```

- `%` 로 구했을 때: 해시가 음수인 사람은 전부 B 가 되므로, 50% 실험에서 **약 75%가 B** 가 된다.\
  다시 말해 **약 25%가 잘못 배정**된다. (대략 계산 — 내 추론)

#### 12. 변종 검증에서 고친 것

- **고칠 것이 없었다. 변종 14개가 전부 잡혔다.**
- `floorMod` → `%`: 칸이 **음수**가 되므로 `bucket >= 0` 단언과 비율 측정에 걸린다.
- 만분율 → 백분율: `BUCKETS` 가 10,000이라는 단언(`assertEquals(10_000, Assigner.BUCKETS)`)과 비율 측정치에 걸린다.
- 씨앗 구분자 제거: `"bc"+"a"` 와 `"b"+"ca"` 가 같아지는 것을 노린 **`saltsNeedASeparator`** 에 걸린다.
- 익명 폴백 제거: 익명 방문자의 `USER` 열쇠와 `DEVICE` 열쇠가 같아야 한다는 **`anonymousVisitorsFallBackToDevice`** 에 걸린다.
- 믿을 수 있는 이유: **"고칠 것이 없었다"가 테스트를 안 돌려본 결과가 아니라, 일부러 14군데를 망가뜨려 보고 전부 잡혔다는 결과**이기 때문이다.\
  26번 박스에서는 같은 방법으로 죽은 코드 하나와 약한 테스트 하나가 나왔다 — **방법이 결과를 가리지 않는다**는 것이 신뢰의 근거다.

#### 13. 생각해볼 것

- 로그인 전후 그룹 변경: 지금 코드는 **로그인 전 열쇠와 로그인 후 열쇠를 이어 붙일 방법이 없다.**\
  실무의 해법은 **아이덴티티 스티칭** — 로그인 시점에 "이 기기 번호는 이 회원의 것"을 기록해 두고, 로그인 후에도 **처음 배정에 쓴 열쇠(기기)** 를 계속 쓰는 것이다.\
  어느 쪽 자료를 쓰느냐는 **로그인 전 행동이 실험 대상이냐**에 달렸다 — 회원가입 전환 실험이면 로그인 전 자료가 본체이고, 결제 화면 실험이면 로그인 후만 본다. (원본에 답 없음 — 내 추론)
- 올린 전후 자료를 같이 보기: `EXTEND` 면 **B 그룹이 옛 B 를 포함**하므로 옛 B 의 자료를 이어서 쓸 수 있다.\
  단, 새로 들어온 9,882명은 노출 기간이 짧아 **관측 기간이 다른 두 집단**이 섞인다 — 기간을 맞춰 자르거나 "언제부터 B였나"를 같이 기록해야 한다.\
  `RESHUFFLE` 이면 전후를 이어 붙일 수 없다 — 8,046명이 양쪽에 걸쳐 있어 **잘라내야 한다.** (원본에 답 없음 — 내 추론)
- 씨앗 재사용: 같은 씨앗을 다시 쓰면 **옛 실험의 B 그룹과 새 실험의 B 그룹이 같은 사람들**이 된다(발견 둘과 같은 사고).\
  옛 실험의 효과가 남아 있다면(학습 효과·습관) 새 실험의 결과에 그대로 묻어 들어온다.\
  그래서 씨앗에는 실험 번호뿐 아니라 **회차·기간**도 섞는 것이 안전하다. (원본에 답 없음 — 내 추론)
- 배정을 저장하면:

```text
 좋아지는 것   해시식을 바꿔도 옛 배정이 남는다 (hashCode 사고를 막는다)
               "이 사람이 언제부터 B였나" 를 정확히 안다
               비율을 내려도 이미 B 인 사람을 지킬 수 있다
 나빠지는 것   사용자 수만큼 행이 쌓인다 (실험마다 × 사용자 수)
               첫 방문 때 쓰기가 필요해 응답이 느려지고 실패 지점이 는다
               로그인 안 한 방문자의 배정까지 저장하면 대부분이 쓰레기다
               저장한 배정과 설정이 어긋날 수 있다 (비율은 20 % 인데 저장은 10 % 시절 것)
```

  이 챕터가 저장 안 하는 쪽을 고른 것은, **결정적 해시만 있으면 저장이 필요 없다**는 점을 드러내기 위해서다. (원본에 답 없음 — 내 추론)

#### 14. 연결

- "같은 입력이면 같은 답": **26-photocard-set 의 `seed`** 와 같은 자리다.\
  거기서는 seed 를 저장해 배분을 재현했고, 여기서는 아예 저장 없이 **식 자체로** 재현한다.

- 실무의 같은 구조: **기능 플래그(feature flag) 점진 배포**, **카나리 배포**, **샤딩(사용자를 서버에 나누기)**, **레이트 리밋의 해시 버킷** — 전부 "열쇠를 해시해 칸에 넣고 칸 번호로 가른다"를 쓴다.\
