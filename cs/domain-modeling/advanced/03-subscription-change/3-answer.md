### A. 과제

#### 0. "일할 계산"이 안 정하는 것

```text
 안 말해준 것              가능한 읽기                        enum
 무엇으로 나누나     →  실제 일수 / 고정 30 일 / 안 함    ProrationBasis
 바꾼 날은 누구 것   →  새 요금제 / 옛 요금제              ChangeDayOwner
 내릴 때 그 돈은     →  지금 환불 / 크레딧 / 다음 주기부터  DowngradeRule
```

- 제일 안 적히는 것: **바꾼 날의 소유(`ChangeDayOwner`).**\
  "31로 나누나 30으로 나누나"는 그래도 논쟁이 되고, "환불이냐 크레딧이냐"는 돈이 오가니 물어본다.\
  그런데 "3월 16일이 누구 날이냐"는 아무도 안 묻는다 — 문제가 있다는 것조차 안 보인다.
- 그런데 무는 범위: **365일 중 365일.** 나눗수는 30일짜리 달 넉 달(120일)을 비켜가지만, 이건 하루도 안 비켜간다.
- 사업 결정인 것: **`DowngradeRule`.** 계산식이 아니라 **현금이 언제 나가느냐**를 정하는 것이고, 측정에서 이번 주기 매출이 56.4% 갈렸다.

#### 1. 주기 — 반열린 구간

- 닫힌 구간으로 잡아도 **일수는 같다**(`[3/1, 3/31]` 도 31일).
- 그런데 반열린 구간이 나은 이유: **다음 주기와 이어 붙일 때 경계가 안 겹친다.**

```text
 반열림  [3/1, 4/1)  다음  [4/1, 5/1)    4/1 은 오직 4 월 주기의 첫날
 닫힘    [3/1, 3/31] 다음  [4/1, 4/30]   3/31 과 4/1 사이에 "빈 자리"가 보이고
                                          경계를 볼 때마다 어느 쪽인지 따져야 한다
```

> **반열린 구간(half-open interval)** — 시작은 포함하고 끝은 제외하는 구간 표기.\
> 예: `[3/1, 4/1)` 은 3월 1일부터 3월 31일까지다. 4월 1일은 안 들어간다.

- 없애는 질문: **"경계일은 어느 주기에 속하나."** 구간 둘을 이어 붙였을 때 겹치는 날도 빠지는 날도 없으므로, 질문 자체가 생기지 않는다.
- `contains`: `!date.isBefore(start) && date.isBefore(endExclusive)` — **시작은 `이상`, 끝은 `미만`.**
- `next()` 가 `endExclusive` 에서 시작하는 것: 이번 주기가 **안 쓴 첫 날**이 정확히 다음 주기의 첫날이다. 하루를 더하거나 빼는 보정이 없다.
- 일수: 2026년 3월 **31일**, 2026년 2월 **28일**, 2028년 2월 **29일**(윤년), 4월 **30일**.
- 규칙 2를 낳는 이유: **같은 요금을 내고 사흘을 더 쓰거나 덜 쓴다.**\
  2월 구독자는 28일치를 29,900원에, 3월 구독자는 31일치를 29,900원에 쓴다 — 하루 단가가 달마다 다르다는 사실이 "그럼 비례배분의 분모는 뭐냐"를 만든다.

#### 2. remainingDays

정답 코드:

```java
int used = (int) ChronoUnit.DAYS.between(cycle.start(), changeOn);
if (owner == ChangeDayOwner.OLD_PLAN) {
    used++;
}
return cycle.days() - used;
```

- 3/16 변경의 남은 날:

```text
 3 월:  1  2  3 ... 15 [16] 17 ... 31
                        ^^^ 바꾼 날

 NEW_PLAN   16 일부터 새 요금제  →  지난 날 15, 남은 날 16
 OLD_PLAN   16 일까지 옛 요금제  →  지난 날 16, 남은 날 15
```

- 하루의 금액:

```text
 NEW_PLAN  29,900×16/31 = 15,432   99,000×16/31 = 51,097   차액 35,665
 OLD_PLAN  29,900×15/31 = 14,468   99,000×15/31 = 47,903   차액 33,435
                                                    하루 = 2,230 원 (요금의 약 3 %)
```

- `effectiveOn`: `NEW_PLAN` 이면 **3/16**, `OLD_PLAN` 이면 **3/17**(`changeOn.plusDays(1)`).
- 하루 다르면 달라지는 것: **기능 사용 권한.**\
  3/16에 프로로 올렸는데 `OLD_PLAN` 이면 그날 하루는 아직 스탠다드다 — 고객은 돈을 냈는데 기능이 안 열린다.
- `Math.max(0, ...)` 를 지운 근거: **음수가 될 수 없다는 것이 증명된다.**\
  변경일이 주기 안이므로 `used ≤ days - 1` 이고, `OLD_PLAN` 으로 1을 더해도 `used ≤ days` 다. 따라서 `days - used ≥ 0`.
- 도달할 수 없는 방어 코드가 나쁜 이유: **"여기 음수가 올 수 있다"는 잘못된 신호**를 준다.\
  읽는 사람은 그 하한을 보고 "어딘가에서 음수가 들어오는구나"라고 믿고 그 가정 위에 코드를 쌓는다. 그리고 그 줄은 테스트로 덮이지 않아 커버리지에도 안 잡힌다.

> **도달 불가 코드(unreachable code)** — 어떤 입력으로도 실행될 수 없는 코드.\
> 예: 이미 0 이상임이 보장된 값에 `Math.max(0, ...)` 를 또 씌우는 것. 안전해 보이지만 거짓 정보를 남긴다.

- 3/31 + `OLD_PLAN`: `used = 30 + 1 = 31`, 남은 날 **0** → 0원짜리 변경이 기록에 남고 `effectiveOn` 은 4/1이다.\
  (`NEW_PLAN` 이면 남은 날 1 → 2,229원.)

#### 3. prorate

정답 코드:

```java
return BigDecimal.valueOf(fullPrice)
        .multiply(BigDecimal.valueOf(remainingDays))
        .divide(BigDecimal.valueOf(basisDays), 0, RoundingMode.HALF_UP)
        .longValueExact();
```

- 나눗셈 먼저 하면 사라지는 것: **나머지.** 나눈 결과를 정수로 만든 뒤 곱하므로, 버려진 소수가 남은 날 수만큼 **곱해져서** 커진다.
- 손계산:

```text
 나눗셈 먼저   29,900 / 31 = 964.516...
                반올림 965 × 16 = 15,440   (8 원 더)
                버림   964 × 16 = 15,424   (8 원 덜)

 곱하기 먼저   29,900 × 16 = 478,400
                478,400 / 31 = 15,432.25...  →  반올림 15,432   ← 올바름
```

  하루 단가에서 생긴 0.48원의 오차가 16일치로 곱해져 8원이 된다. 프로(99,000)면 더 커진다.
> **곱하기 먼저(multiply-then-divide)** — 비례 계산에서 나눗셈을 마지막에 한 번만 하는 순서.\
> 예: `29,900 × 16 ÷ 31` 은 맞지만 `(29,900 ÷ 31) × 16` 은 하루 단가에서 버린 소수가 16배로 커진다.

- `BigDecimal` 인 이유: **나눗셈의 반올림 방식을 내가 고르기 위해서**다.\
  자바의 `long` 나눗셈은 무조건 0 쪽으로 자르므로 "반올림"을 못 쓴다. `double` 은 오차가 있어 0.5 경계에서 어느 쪽으로 갈지 보장이 안 된다.
- 반올림: **HALF_UP(0.5는 올림)** 을 **마지막 나눗셈에서 한 번**만 한다.

#### 4. change

정답 코드 (핵심만):

```java
if (!cycle.contains(changeOn)) { throw ...; }
if (oldPlan.id().equals(newPlan.id())) { throw ...; }

boolean upgrade = newPlan.monthlyPrice() > oldPlan.monthlyPrice();

if (basis == ProrationBasis.NONE) { return new Change(0, 0, 0, cycle.endExclusive(), 0, 0); }
if (!upgrade && downgradeRule == DowngradeRule.NEXT_CYCLE) {
    return new Change(0, 0, 0, cycle.endExclusive(), 0, 0);
}

int remaining = remainingDays(cycle, changeOn, owner);
int basisDays = basis == ProrationBasis.ACTUAL_DAYS ? cycle.days() : 30;
long unusedOld  = prorate(oldPlan.monthlyPrice(), remaining, basisDays);
long newPortion = prorate(newPlan.monthlyPrice(), remaining, basisDays);
long difference = newPortion - unusedOld;

LocalDate effectiveOn = owner == ChangeDayOwner.NEW_PLAN ? changeOn : changeOn.plusDays(1);
if (difference >= 0) { return new Change(difference, 0, 0, effectiveOn, remaining, basisDays); }
long back = -difference;
return downgradeRule == DowngradeRule.REFUND_NOW
        ? new Change(0, back, 0, effectiveOn, remaining, basisDays)
        : new Change(0, 0, back, effectiveOn, remaining, basisDays);
```

- 거부하는 입력 둘: **주기 밖의 변경일**, **같은 id로의 변경**.
- 부등호는 `>` 다 — **요금이 같으면 업그레이드가 아니다.**
- 요금이 똑같은 두 요금제(리브랜딩)에서 가르는 것: **언제부터 새 요금제냐.**

```text
 요금 29,900 → 29,900 (이름만 다른 요금제), 3/16 변경

 upgrade = false (부등호 >)   + NEXT_CYCLE  →  4/1 부터 새 요금제
 upgrade = true  (부등호 >=)                →  3/16 부터 새 요금제
 upgrade = false             + REFUND_NOW  →  3/16 부터 (차액 0 원)
```

- 금액은 갈리는가: **안 갈린다. 어느 쪽이든 0원이다.**\
  그래서 금액만 검증하는 테스트로는 이 부등호를 못 잡는다(변종 검증에서 실제로 안 잡혔다).
- `NONE`: **지금 0원, `effectiveOn` 은 다음 주기 첫날, `remainingDays`·`basisDays` 도 0.**
- 다운그레이드 + `NEXT_CYCLE`: **똑같이 0원·다음 주기 첫날.**
- 두 경우의 `remainingDays`·`basisDays` 가 0인 이유: **비례배분을 아예 안 했기 때문이다.**\
  0은 "0일이 남았다"가 아니라 "이 계산을 안 썼다"는 표시다 — 테스트가 `"비례배분을 아예 안 한다"` 라는 메시지로 못 박았다.
- 차액 ≥ 0 → `chargeNow`, 차액 < 0 → `REFUND_NOW` 면 `refundNow`, 아니면 `credit`.
- `>= 0` 을 `> 0` 으로 바꾼 변종을 못 잡는 이유: **차액이 정확히 0이면 두 갈래가 완전히 같은 `Change` 를 만든다.**

```text
 차액 0 일 때
   >= 0 갈래   new Change(0, 0, 0, effectiveOn, remaining, basisDays)
   <  0 갈래   back = -0 = 0  →  new Change(0, 0, 0, ...)  또는 (0, 0, 0, ...)
                                   어느 쪽이든 세 금액이 다 0 이라 구별이 안 된다
```

> **동치 변종(equivalent mutant)** — 코드를 바꿨는데 동작이 완전히 똑같아서, 어떤 테스트로도 구별할 수 없는 변형.\
> 예: 여기서 `>= 0` 과 `> 0` 은 차액이 0일 때 같은 결과를 내므로 영원히 안 잡힌다. 잡으려 애쓰는 것이 낭비다.

- 반올림 두 번 vs 한 번: **365일 중 44일**에서 1원씩 어긋난다.
- 두 번이 맞는 이유: **고객에게 보이는 두 줄의 차이가 청구액이어야 한다.**\
  명세서에 "안 쓴 옛 요금 15,432원"과 "새 요금 비례분 51,097원"을 찍어놓고 청구액이 35,664원이면, 고객이 뺄셈을 해봤을 때 안 맞는다.

#### 5. unusedAmount

- 같은 식을 쓰는 것이 중요한 이유: **해지는 "새 요금제가 0원인 변경"과 같은 계산**이다.\
  실제로 `change` 의 `unusedOld` 와 `unusedAmount` 가 같은 `prorate` 를 부른다.
- 따로 짜면: **하나를 고칠 때 다른 하나를 잊는다.** 나눗수 규칙을 바꾸면 변경액은 바뀌는데 해지 환불액은 옛 규칙으로 남는다 — 그리고 그 불일치는 두 기능을 같이 쓰는 고객만 발견한다.
- 3/16 기준(`ACTUAL_DAYS`, `NEW_PLAN`):

```text
 unusedAmount(프로)      99,000 × 16 / 31 = 51,097
 unusedAmount(스탠다드)  29,900 × 16 / 31 = 15,432
 차이                                       35,665  =  change(...).chargeNow()
```

- `basis == NONE` 이면 `unusedAmount` 는 **0** 이다(비례배분을 안 하므로 돌려줄 것이 없다).

#### 6. 세 enum — 손계산

- 3/16 스탠다드 → 프로:

```text
 ACTUAL_DAYS (÷31)   29,900×16/31 = 15,432   99,000×16/31 = 51,097   →  35,665
 FIXED_30_DAYS(÷30)  29,900×16/30 = 15,947   99,000×16/30 = 52,800   →  36,853
                                                              차이      1,188 원
```

- 2/16(2월 주기 28일, 남은 날 13)에서는 **뒤집힌다**:

```text
 ACTUAL_DAYS (÷28)   29,900×13/28 = 13,882   99,000×13/28 = 45,964   →  32,082
 FIXED_30_DAYS(÷30)  29,900×13/30 = 12,957   99,000×13/30 = 42,900   →  29,943
                                                   이번엔 고정이 2,139 원 싸다
```

- 뒤집히는 이유: **분모가 작을수록 하루가 비싸다.**\
  3월은 실제 31 > 30이라 실제 일수 쪽이 싸고, 2월은 실제 28 < 30이라 실제 일수 쪽이 비싸다.\
  그래서 **"고정 30일이 회사에 유리하다"는 31일짜리 달에서만 맞는 말**이다.
- 3/1(첫날) 변경: 남은 날 **31 = 주기 전체** → `29,900×31/31 = 29,900`, `99,000×31/31 = 99,000` → 차액 **69,100원**.
- 그 값이 요금 차이와 같은 이유: **비례배분의 비율이 1이 되기 때문이다.** 하나도 안 쓴 상태라 "옛 요금 전액을 빼고 새 요금 전액을 받는" 것과 같다.
- 다운그레이드 세 규칙(3/16 프로 → 스탠다드, 차액 35,665원):

```text
 REFUND_NOW   refundNow 35,665   지금 카드로 돌아간다
 CREDIT       credit    35,665   쌓아뒀다가 다음 청구에서 깎는다 (지금 현금 안 움직임)
 NEXT_CYCLE   전부 0            4/1 부터 스탠다드 (이번 달 프로 요금을 다 받는다)
```

- 올릴 때 세 규칙이 같은 이유: **다운그레이드 규칙은 차액이 음수일 때만 갈라진다.**\
  올릴 때는 차액이 언제나 0 이상이라 `difference >= 0` 갈래로 빠지고, `downgradeRule` 을 보지도 않는다.

### B. 개념

#### 7. 측정 — 365일 전수

- 나눗수로 갈린 날: **245 / 365.**
- 안 갈리는 넉 달: **4·6·9·11월.** 그 달들이 **30일**이라 `ACTUAL_DAYS` 의 분모가 `FIXED_30_DAYS` 와 같아진다(120일).
- 한 건 최대 차이 **4,607원**, 고정 30일 총합 13,216,524 vs 실제 일수 13,025,350 → **+1.47%**.
- 하루 단가 (스탠다드 29,900):

```text
 1 월 (31 일)    964.52 원
 2 월 (28 일)  1,067.86 원   ← 가장 비싸다
 4 월 (30 일)    996.67 원

 (1,067.86 − 964.52) / 964.52 = 10.7 %
```

- "2월에 해지하면 하루당 더 돌려받는다"는 **`ACTUAL_DAYS`(실제 일수) 규칙의 정의**다.\
  2월은 28일에 29,900원을 나누므로 안 쓴 하루의 값이 더 크다 — 버그가 아니라 규칙의 결과다.
- 바꾼 날 소유로 갈린 경우: **365 / 365**, 한 해 **6.80%**(새 요금제 소유 13,025,350 vs 옛 요금제 소유 12,196,150, 차이 829,200원), 한 건 최대 **2,469원**.
- 하루도 안 비켜가는 이유: **나눗수는 달의 길이에 달렸지만 "바꾼 날"은 매번 존재한다.**\
  30일짜리 달에서도 바꾼 날은 있고, 그날이 누구 것이냐는 언제나 하루를 움직인다.
- 다운그레이드 세 규칙에서 회사가 이번 주기에 쥐는 돈:

```text
 환불            23,109,650
 크레딧          23,109,650   ← 이번 주기 기준으로는 환불과 같다
 다음 주기부터   36,135,000   +56.4 %  (= 99,000 × 365, 아무것도 안 돌려준다)
```

> **크레딧(credit)** — 돌려줄 돈을 현금으로 주지 않고 계정에 쌓아뒀다가 다음 청구에서 깎는 것.\
> 예: 35,665원을 카드로 환불하는 대신 "다음 달 요금에서 35,665원 차감"으로 처리하는 것. 금액은 같지만 회사 통장에서 돈이 안 나간다.

- 환불과 크레딧이 같은 금액인데 갈리는 것: **현금이 언제 나가느냐.**\
  크레딧은 이번 달 현금이 안 나가고 다음 청구에서 차감된다 — 회계상 부채로 남고, 고객이 해지하면 그 돈이 어디로 가는지가 또 문제가 된다.
- 반올림 두 번: **44 / 365일**에서 1원씩 어긋난다(전부 1원 차이).
- 4월 + 업그레이드로만 시험하면: **갈림 셋 중 하나만 남는다.**\
  4월은 30일이라 나눗수가 같고(갈림 ①소멸), 업그레이드라 다운그레이드 규칙이 안 걸린다(갈림 ③소멸). 남는 것은 **바꾼 날 소유**뿐이다(4/16 기준 34,550 vs 32,247, 하루 2,303원).
- 예제가 4월·업그레이드인 이유: **4월은 30일이라 계산이 딱 떨어지고**, 업그레이드는 "고객이 더 좋은 걸로 올렸다"는 이야기가 되기 때문이다.\
  즉 예제를 고르는 기준(계산의 편함, 이야기의 자연스러움)이 **갈림이 안 보이는 쪽과 정확히 겹친다.**

#### 8. 변종 검증에서 고친 것

- `Math.max(0, ...)` 를 지운 근거: **변경일이 주기 안이면 `used ≤ days` 가 보장된다**(위 2번의 증명). 도달할 수 없는 하한이었다.
- 업그레이드 부등호를 `>=` 로 바꿔도 통과한 이유: **요금이 같은 두 요금제를 시험한 적이 없었다.**\
  테스트의 모든 변경이 9,900 / 29,900 / 99,000 사이라 `>` 와 `>=` 가 한 번도 갈리지 않았다.
- 잡는 예제: **이름만 다르고 요금이 같은 요금제**(`new Plan("standard-b", "스탠다드 개편", 29_900)`).\
  그리고 검증할 것은 금액이 아니라 **`effectiveOn`**(3/16이냐 4/1이냐)이다.
- `>= 0` → `> 0` 이 동치 변종인 이유: 차액이 정확히 0일 때 **두 갈래가 완전히 같은 값의 `Change` 를 만든다**(위 4번).
- 못 잡는 것이 정상인 이유: **행동이 같으면 테스트로 구별할 방법이 원리적으로 없다.**\
  변종 검증의 점수가 100%가 안 되는 것은 대개 이런 동치 변종 때문이고, 그걸 잡겠다고 테스트를 늘리면 의미 없는 테스트만 는다.

#### 9. 함정 (README)

- 다섯: ① **주기를 닫힌 구간으로 잡는 것** ② **나눗셈을 먼저 하는 것**(나머지가 사라진다 — 곱하기 먼저) ③ **바꾼 날을 안 정하는 것**(하루가 요금의 3%) ④ **해지 환불을 따로 짜는 것**(변경과 해지가 같은 식을 쓴다) ⑤ **요금이 같은 요금제를 "올리는 것"으로 치는 것**(리브랜딩에서 실제로 생긴다).
- ①이 함정인 이유: 일수는 같은데 **다음 주기와의 경계에서 매번 따져야 할 질문이 생긴다.** 그 질문은 코드 여러 곳에서 각각 답을 내고, 한 곳만 틀려도 하루가 어긋난다.
- ④가 함정인 이유: **두 계산이 같은 규칙을 구현하는데 코드가 둘이면 반드시 갈라진다.** 나눗수 규칙을 바꿀 때 한쪽만 고치게 되고, 그 불일치는 "변경했다가 바로 해지한 고객"에게서만 드러난다.

#### 10. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 크레딧이 남은 채로 해지: 이 코드의 `Change.credit` 은 **금액만 돌려주고 그 뒤를 모른다** — 크레딧의 수명은 이 박스 밖의 일이다. 현실의 선택지는 셋이다 — ① 소멸시킨다(약관에 쓰면 합법이지만 고객이 낸 돈이라 분쟁이 잦다) ② 현금 환불한다(그러면 애초에 크레딧으로 준 의미가 없다) ③ 유효기간을 두고 그때까지 재구독하면 살려둔다. 어느 쪽이든 **크레딧은 "돈"이 아니라 "조건부 약속"** 이라는 것을 타입으로 드러내야 한다(만료일 필드 등). (원본에 답 없음 — 내 추론)
- 한 주기에 두 번 변경: 두 번째 계산의 "옛 요금"은 **첫 변경으로 실제로 청구된 금액이 아니라, 지금 적용 중인 요금제의 월 요금**이다. 이 코드는 `oldPlan.monthlyPrice()` 를 그대로 쓰므로 그렇게 동작한다. 문제는 **남은 날의 기준**이다 — 첫 변경의 `effectiveOn` 부터 세야 맞는데, `remainingDays` 는 `cycle.start()` 부터 센다. 즉 이 코드는 **주기당 한 번 변경**을 가정하고 있다. 두 번을 지원하려면 "지금 요금제가 언제부터였나"를 입력으로 받아야 한다. (원본에 답 없음 — 내 추론)
- 결제일 31일의 2월: `Cycle.monthFrom(1/31)` 은 `plusMonths(1)` 이 **2/28로 잘라주므로**(자바 `LocalDate` 의 규칙) `[1/31, 2/28)` 28일이 된다. 그다음 주기는 `[2/28, 3/28)` 이라 **결제일이 28일로 영영 밀린다.** 실무는 보통 "원래 결제일 31일을 기억해뒀다가 가능한 달에는 31일로 되돌린다"인데, 그러면 주기 계산이 `Cycle` 안에 못 들어가고 **구독 정보(원래 결제일)를 알아야** 한다. (원본에 답 없음 — 내 추론)
- 연간 결제: **식은 그대로 된다.** `Cycle` 이 반열린 구간이라 `[2026/3/1, 2027/3/1)` 이면 `days() = 365` 가 나오고, 나머지 계산은 분모만 커진다. 갈라지는 것은 **`FIXED_30_DAYS`** 다 — 365일 주기에 30을 분모로 쓰면 비례분이 12배로 튀어 완전히 틀린다. 즉 `ProrationBasis` 는 "월 주기"를 암묵적으로 가정하고 있고, 연간을 지원하려면 `FIXED_30_DAYS` 를 `FIXED_360_DAYS` 같은 것으로 확장하거나 아예 못 쓰게 막아야 한다. #### 11. 연결

- 01-parking-fee 와 같은 구조: 주차의 **"10분까지"가 10분을 포함하나**와 여기의 **"바꾼 날은 누구 것인가"** 는 둘 다 **경계 하나의 소속**을 묻는다. 그리고 둘 다 문장에 안 적혀 있다.
