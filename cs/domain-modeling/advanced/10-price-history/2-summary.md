# domain-modeling-advanced/10-price-history — 정리 (힌트)

## 해결하는 문제

가격 기록에 시간을 하나만 붙이면 "2월 10일의 가격"에 한 답밖에 못 한다. 그런데 3/15에 "사실 2/1부터 11,000원이었다"는 정정이 들어오는 순간 그 질문은 둘로 갈린다 — 그때 알던 값과 지금 아는 값.\
이 모델이 없으면: 소급 정정이 들어오는 날 **과거 영수증이 스스로 바뀌고**, 이미 낸 보고서를 재현할 수 없으며, 같은 유효일에 기록이 둘이면 조회 쿼리의 순서가 답을 정한다.

```text
시간 하나(유효일)만 들면          시간 둘(유효일 + 기록일)을 들면
  2/1  11,000  ← 3/15 정정이         2/1  11,000  기록 3/15
       1/1 기록을 덮어씀                1/1  10,000  기록 1/1
  "2/10 영수증 재발행" → 11,000        asOf 2/10 → 10,000 (재발행)
  (원래 영수증은 10,000이었는데)        asOf null → 11,000 (재정산)
```

쉬운 예: 일기장에 "오늘 아이스크림 1,000원"이라 썼는데 다음 달 가게가 "사실 1,100원이었다"고 정정했다 — 일기는 그대로 두고 정정 기사를 따로 붙여야 둘 다 남는다.\
똑같은 구조다: 기록 한 줄에 **유효 시각 + 기록 시각**을 붙이고(바이템포럴), 정정은 고치지 않고 줄을 추가하며, `asOf` 커서 하나로 두 질문에 답한다.\
실무 예: 회계 소급 수정, 급여 소급 인상, 세금계산서 수정 발행, DB temporal table.

  - *바이템포럴(bitemporal)*: 사실의 시간축(유효)과 앎의 시간축(기록) 두 개를 함께 기록하는 모델.

### 한눈에 — 쉽게 말하면

**가격 이력 = 일기장과 정정 기사. "그날 무슨 일이 있었나"와 "그날 있었다고 지금 아는 것"은 다르다.**

- 2월 10일 일기에 "오늘 아이스크림이 1,000원이었다"라고 썼다. 3월 15일에 가게가 "사실 2월부터 1,100원이었어요, 전산 오류였습니다"라고 공지했다. 그럼 **2월 10일의 가격**은 얼마인가?
  - 일기(그때 알던 값): 1,000원 — 2월 10일에 낸 돈, 영수증에 찍힌 값.
  - 정정 반영(지금 아는 값): 1,100원 — 정산을 다시 하면 이 값.
  - **둘 다 맞다.** 어느 쪽이 맞느냐가 아니라, 어느 질문에 답하느냐가 다르다.
- 그래서 가격 기록 한 줄에 시간이 **둘** 붙는다: **유효 시각**(이 가격이 언제부터 맞는가)과 **기록 시각**(우리가 그것을 언제 알았는가). 이것이 바이템포럴(bitemporal) 모델이다.
  - *바이템포럴(bitemporal)*: "두 개의 시간"이라는 뜻. 사실의 시간축 + 앎의 시간축.
- 시간을 하나만 들고 있으면 소급 정정이 들어오는 순간 **과거 영수증이 스스로 바뀐다** — 그리고 대개 "지금 아는 값" 쪽만 만든다. 그쪽이 쉬우니까.

```text
  유효일   가격      기록일    성격
  1/1     10,000    1/1      처음
  3/1     12,000    3/1      정시 인상
  2/1     11,000    3/15     소급 정정  ← 3/15 에 "2/1 부터 11,000 이었다" 를 알게 됨

  "2 월 10 일의 가격은?"
    그때 알던 값(asOf 2/10)  10,000   ← 3/15 정정은 아직 없었다
    지금 아는 값(asOf null)   11,000   ← 정정을 반영하면
```

실무 예: 회계 장부의 소급 수정, 급여 소급 인상, 세금계산서 수정 발행, DB의 temporal table / event sourcing.

## 동작·원리

### 전체 흐름

```text
PriceRecord (기록 한 줄 — 계약, 다 주어져 있다)
  sku · effectiveFrom(유효일) · price · recordedAt(기록 시각)
  onTime(sku, on, price)          기록일 = 유효일 (보통의 변경)
  backdated(sku, 유효일, price, 기록일)  소급 정정 (유효일 < 기록일)

PriceHistory (채우는 것)
  생성: 유효일 → 기록 시각 → sku 순으로 정렬해 보관
  priceOn(sku, on, asOf, Tie)
    후보 = sku 일치 · 유효일 ≤ on · (asOf 있으면) 기록시각 ≤ asOf
    답   = 후보 중 유효일이 가장 늦은 것. 없으면 -1
    asOf = null      → "지금 아는 값"
    asOf = 그날 끝   → "그때 알던 값"
  Tie {LATEST_RECORD, FIRST_RECORD}  같은 유효일에 기록 둘이면 누가 이기나
  changedDays(sku, from, to, tie)   그때 값 ≠ 지금 값인 날들 = 다시 뽑으면 달라질 영수증
  backdatedRecords()                소급 정정만 골라내기
```

  - *asOf*: "이 시각까지 알려진 것만 본다"는 커서. 앎의 시간축을 어디서 자르느냐.
  - *sku*: 품목 코드(stock keeping unit). 상품 하나를 가리키는 식별자.

### 규칙 ① 두 시간 — 한 질문에 두 답

**요구사항**: "3월 15일에 '2월 1일부터 11,000원이었다'를 입력하면" → 유효 시각 2/1 + 기록 시각 3/15, **두 필드로 번역**. 기존 기록을 고치지 않고 **줄을 추가**한다(append-only).

손계산 — 위 세 줄 이력에서 "2월 10일의 가격":

```text
지금 아는 값  priceOn("A", 2/10, null, LATEST_RECORD)
  후보: 1/1 기록(유효 1/1 ≤ 2/10 ✓), 2/1 정정(✓), 3/1 인상(유효 3/1 > 2/10 ✗)
  유효일 가장 늦은 것 = 2/1 정정 → 11,000

그때 알던 값  priceOn("A", 2/10, 2/10 23:59:59, ...)
  후보: 1/1 기록만 (2/1 정정은 기록 시각 3/15 > asOf ✗)
  → 10,000

정정 경계: 3/14 에 물으면 10,000, 3/15 에 물으면 11,000
  → 값이 바뀌는 것은 유효일(2/1)이 아니라 "기록된 날(3/15)" 이다
```

- 왜 이렇게 모델링했나: 유효 시각 하나만 있으면 "그때 알던 값" 질문(영수증 재발행, 이미 낸 보고서 재현)에 답할 수 없다. 두 시각을 들면 **asOf 파라미터 하나로 두 질문을 한 코드가 답한다.**
- **없는 가격은 -1이지 0이 아니다.** 0원은 매출 계산에 그대로 들어간다 — "없다"와 "공짜"는 다른 사실이다.

### 규칙 ② 같은 유효일 충돌(Tie) — 정정이 이기나, 원본이 이기나

**요구사항에 없는 결정**: 같은 유효일(2/1)에 기록이 둘이면? 안 정하면 **목록 순서가 정하고, 목록 순서는 조회 쿼리가 정한다** — 결과가 우연이 된다.

```text
Tie.LATEST_RECORD  나중에 기록한 것 → 정정이 이긴다 (보통 원하는 것)
Tie.FIRST_RECORD   먼저 기록한 것  → 정정을 무시한다
```

측정: 소급 30% 이력 200개 중 141개(70%)에서 이 규칙에 따라 답이 갈렸고, 갈린 날이 평균 18일 — 사소한 케이스가 아니다.

### 규칙 ③ changedDays — "다시 뽑으면 달라질 영수증이 몇 장인가"

날마다 `그때 알던 값(asOf 그날 끝)`과 `지금 아는 값(asOf null)`을 비교해 다른 날을 모은다.

```text
1/1 ~ 3/31 에서 바뀐 날 = 2/1 ~ 2/28 정확히 28 일
  2 월만 소급 정정(11,000)에 덮였다. 1 월은 원래 10,000, 3 월은 정시 인상이라 그대로.
```

측정이 보여준 것:

- 소급 정정이 **10%만 있어도 1년의 6.5%(23.9일)** 가 바뀐다 — 기록 하나가 열흘씩 과거를 뒤집는다. 소급이 0%면 **아무 날도 안 바뀐다** — **이 문제는 첫 소급 정정이 들어오는 날 시작된다.**
- 과거 매출을 다시 계산하면(소급 30%): 총액 차이는 +0.83%뿐인데 **이력 200개 전부가 다르다.** "작년 매출이 얼마였나"에 오늘 답한 값과 작년에 답한 값이 다르고, 둘 다 맞다.

## 쓰이는 자료구조·알고리즘

- **바이템포럴 레코드 + append-only 로그** — `PriceRecord(sku, effectiveFrom, price, recordedAt)`. 정정은 UPDATE가 아니라 새 줄이다. → [ops-patterns/16-event-sourcing](../../../ops-patterns/16-event-sourcing/2-summary.md), [data-structure/26-persistent](../../../data-structure/26-persistent/2-summary.md)(옛 버전을 지우지 않는 구조).
- **다중 키 정렬(유효일 → 기록 시각 → sku)** — `records()` 표시용. 정렬이 필요한 곳은 조회가 아니라 목록이었고, 기록 시각 키가 빠져도 **안정 정렬**이 입력 순서를 보존해 우연히 맞았다. → [algorithm/01-elementary-sort](../../../algorithm/01-elementary-sort/2-summary.md)의 안정성.
- **필터 + 최댓값 선택** — `priceOn`은 `sku 일치 ∧ 유효일 ≤ on ∧ (asOf 있으면) 기록시각 ≤ asOf`로 거른 뒤 유효일이 가장 늦은 것을 고른다. [09-policy-version](../09-policy-version/2-summary.md)의 "≤ date 중 가장 늦은 것"에 축 하나가 더 붙은 꼴.
- **동률 해소 규칙(`Tie`)** — 같은 유효일에 기록 둘이면 `LATEST_RECORD`(정정 승) / `FIRST_RECORD`(원본 승). 안 정하면 쿼리 순서가 정한다.
- **두 조회의 차집합(`changedDays`)** — 날마다 `asOf 그날 끝`과 `asOf null`을 비교해 다른 날을 모은다. 일수 × 기록 수의 단순 비교 — "다시 뽑으면 달라질 영수증이 몇 장인가".
- **센티넬 `-1`** — 없는 가격은 0이 아니다. 0원은 매출 계산에 그대로 들어간다.

## 적용 — 풀어나가는 법

풀이 순서는 컬렉션 공통 — 빈 결정 찾기 → enum 올리기 → 갈리는 입력 만들기 → 조합별 측정.\
가격 이력에서 갈리는 입력은 **소급 정정(유효일 < 기록일) 한 건 이상 + 같은 유효일의 기록 둘 + 끝이 실제로 바뀌는 날인 구간 + 품목 둘**이다. 소급이 0%면 200개 이력 전부에서 아무 날도 안 바뀐다 — 이 문제는 첫 소급 정정이 들어오는 날 시작된다.\
질문을 완성하는 습관을 붙인다: "2월 10일의 가격"은 질문이 덜 된 것이다 — **"언제 기준으로(asOf)"** 를 붙여야 답이 하나로 정해진다.

### 문제 — 이 챕터가 시키는 것

주어진 것은 가격 기록 세 줄이 전부다(원본 README 그대로).

```text
  유효일   가격      기록일    성격
  1/1     10,000    1/1      처음
  3/1     12,000    3/1      정시 인상
  2/1     11,000    3/15     소급 정정

  2 월 10 일의 가격은
    그때 알던 값   10,000    (3/15 정정은 아직 없었다)
    지금 아는 값   11,000    (정정을 반영하면)
```

**"둘 다 맞는 값이다. 영수증을 다시 뽑을 때는 앞의 값이고 정산을 다시 할 때는 뒤의 값이다."**

그래서 기록 한 줄에 시간이 **둘**이다(원본 javadoc 그대로).

```text
  유효 시각   이 가격이 언제부터 맞는가       effectiveFrom
  기록 시각   우리가 그것을 언제 알았는가     recordedAt
```

**하나만 만들어두면 다른 질문에 답할 수 없다. 그리고 대개 "지금 아는 값"만 만든다. 그쪽이 쉬우니까.**

과제(원본 README "채울 것"): `src/main/java/com/domain/price/PriceHistory.java` 의 **TODO 1~3**. `PriceRecord` 는 계약이라 다 주어져 있다.

| TODO | 함수 | 시키는 것 |
|---|---|---|
| 1 | `PriceHistory(records)` | **유효일 순, 같으면 기록 시각 순**으로 정렬해 보관 |
| 2 | `priceOn(sku, on, asOf, tie)` | 그 시점에 알던 그날의 가격. 없으면 **-1**(0이 아니다) |
| 3 | `changedDays(sku, from, toInclusive, tie)` | 소급 정정이 바꾼 날들 — **양쪽 끝을 다 센다** |

테스트가 못 박은 계약:

- 2/10의 가격: `asOf=2/10` 이면 **10,000**, `asOf=null` 이면 **11,000**. 기본은 지금 아는 값.
- 정정 하루 전(3/14)과 당일(3/15)이 **10,000 ↔ 11,000** 으로 갈린다.
- 바뀐 날이 **정확히 2월 28일치**(2/1 ~ 2/28). 1월·3월은 안 바뀐다.
- `changedDays(2/1, 2/28)` 은 **28**, `changedDays(2/28, 2/28)` 은 **1** — 끝을 포함한다.
- 같은 유효일이 둘이면 `LATEST_RECORD` → **13,000**, `FIRST_RECORD` → **12,000**.
- 넣은 순서를 뒤집어도 120일 내내 모든 답이 같다. `records()` 는 유효일 순, 같으면 기록 시각 순.
- 첫 기록보다 이른 날·없는 품목·빈 이력은 전부 **-1**.
- 품목이 섞여 있어도 **자기 것만** 본다.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 장애 시나리오와 대처

**1. 재발행한 영수증 금액이 원본과 다르다**

- 현상: 고객이 2/10 영수증을 다시 요청했더니 10,000원이 아니라 11,000원으로 찍힌다.
- 보이는 형태: 원본(종이·PDF)과 재발행본이 다르다는 민원. 세무 증빙 분쟁.
- 원인: 기록 시각이 없거나 있어도 `asOf` 없이 "지금 아는 값"으로 조회했다. 3/15 소급 정정이 2/10을 덮었다.
- 대처: 재발행은 `asOf = 원 발행 시각`으로 조회한다. 발행 시각을 영수증에 저장해 두어야 그 커서를 만들 수 있다.

**2. 지난달 매출 보고서를 다시 뽑으니 지난달에 낸 값과 다르다**

- 현상: 감사가 "3월 보고서의 합계가 왜 바뀌었나"를 묻는다.
- 보이는 형태: 두 보고서의 합계가 조금씩 다르다. 규모 감각은 README 측정 셋이 준다 — 소급 30% 가상 이력 200개를 1년치 다시 계산하면 총액 +0.83%, 이력 200개 전부가 달랐다.
- 원인: 소급 정정이 그 사이 들어왔고, 보고서가 `asOf` 없이 지금 아는 값으로 재계산됐다. 둘 다 맞는 값이라 "어느 쪽이 버그"라고 말할 수 없다.
- 대처: 보고서에 **asOf 스탬프**를 찍고 재현은 그 시각으로 한다. 정정 목록(`backdatedRecords`)과 `changedDays`를 별도 절로 보고해 "무엇이 바뀌었나"를 보이게 한다([15-period-close](../15-period-close/2-summary.md)의 늦은 거래와 같은 문제).

**3. 신규 품목이 0원에 팔렸다**

- 현상: 가격을 아직 안 넣은 품목이 장바구니에 0원으로 담기고 결제까지 된다.
- 보이는 형태: 매출 0원 주문. 예외 없음.
- 원인: 없는 가격을 0으로 돌려주는 구현. "없다"와 "공짜"를 한 값으로 표현했다.
- 대처: 없음은 `-1`(또는 `Optional.empty`)로 구별하고, 호출 쪽은 없음이면 판매를 막는다. 첫 기록보다 이른 날·없는 품목·빈 이력을 테스트에 넣는다.

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 시간을 하나만 든다 | 유효 시각 + 기록 시각 둘 — 하나면 옛 영수증 재현 불가 |
| 없는 가격을 0으로 | -1(없음)과 0원(공짜)을 구별 — 0은 매출에 그대로 들어간다 |
| 같은 유효일 기록 둘을 방치 | Tie 규칙으로 명시 — 안 정하면 쿼리 순서가 정한다 |
| 품목 필터를 빼먹는다 | 유효일 순 정렬 뒤엔 특히 나기 쉽다 — sku 다른 기록이 섞여도 자기 것만 |
| 첫 기록보다 이른 날 / 없는 품목 / 빈 이력 | 전부 -1 |
| 구간 끝을 제외로 잘못 잡는다 | changedDays는 양끝 포함 — **끝이 실제로 바뀌는 날인 구간(2/1~2/28)** 으로 시험해야 잡힌다 |

변종 검증에서 고친 것 셋 — 전부 "테스트가 우연히 통과하는" 유형:

1. changedDays의 **구간 끝을 제외로 바꿔도 통과** — 예제 구간(1/1~3/31)의 끝이 안 바뀌는 날이었다. 끝이 바뀌는 날인 구간으로 교체.
2. **정렬 줄을 지워도 통과** — priceOn이 전체를 훑어서 정렬 없이도 답이 같다. 정렬이 필요한 곳은 `records()` 목록 표시 — 그 순서를 확인하는 테스트 추가.
3. 정렬의 **기록 시각 기준을 빼도 통과** — 자바 정렬이 안정적(stable)이라 넣은 순서가 남아 우연히 맞았다. **나중 기록을 일부러 앞에 넣어** 갈랐다.
  - *안정 정렬(stable sort)*: 비교 기준이 같은 원소들의 원래 순서를 보존하는 정렬. 우연한 통과의 흔한 원인.

## 핵심 문장

- 기록에는 시간이 둘 붙는다 — **"언제부터 맞는가(유효)"와 "언제 알았는가(기록)"** — 하나만 들면 소급 정정이 들어오는 날 과거 영수증이 스스로 바뀐다.
- "2월 10일의 가격"은 질문이 덜 된 것이다 — **"언제 기준으로(asOf)"** 를 붙여야 질문이 완성되고, 그때 알던 값과 지금 아는 값은 **둘 다 맞다.**
- 정정은 고치는 것이 아니라 **줄을 추가하는 것**이다 — 그래야 정정 전의 답도 재현할 수 있다.
- 같은 유효일의 충돌 규칙(Tie)을 코드로 안 정하면 **조회 쿼리의 순서가 대신 정한다** — 결정을 우연에 맡기는 것.
- 이 구조의 필요성은 **첫 소급 정정이 들어오는 날** 드러난다 — 그날까지는 시간 하나짜리 모델도 모든 테스트를 통과한다.

### 용어 풀이

- **유효 시각(effectiveFrom)**: 이 가격이 언제부터 맞는가 — 사실의 시간.
- **기록 시각(recordedAt)**: 우리가 그것을 언제 알았나(입력했나) — 앎의 시간.
- **바이템포럴(bitemporal)**: 위의 두 시간축을 모두 기록하는 모델링. DB에선 temporal table.
- **소급 정정(backdated)**: 나중에 알았는데 예전부터 맞던 값. 유효일 < 기록일이면 소급이다.
- **asOf 조회**: "그 시각까지 알려진 것만 보고" 답하기. asOf = null이면 지금 아는 전부.
- **그때 알던 값 / 지금 아는 값**: 영수증 재발행에 맞는 값 / 재정산에 맞는 값. 둘 다 맞다.
- **append-only**: 고치지 않고 추가만 하는 기록 방식. 정정도 새 줄이다.
- **Tie(동률 규칙)**: 같은 유효일에 기록이 둘일 때 누가 이기나 — LATEST_RECORD(정정 승) / FIRST_RECORD(원본 승).
- **-1 (없음 표시)**: 유효한 기록이 없다는 뜻. 0원과 절대 섞으면 안 된다.
- **안정 정렬(stable sort)**: 같은 키의 원래 순서를 보존하는 정렬. 빠뜨린 정렬 기준을 우연히 덮어 테스트를 통과시키는 원인이 된다.
- **이벤트 소싱(event sourcing)**: 상태 대신 사건을 쌓고 상태는 재계산하는 설계 — 같은 철학의 확장판.
