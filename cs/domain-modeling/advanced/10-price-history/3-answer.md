### A. 과제

#### 0. 한 질문에 답이 둘인 이유

- 답이 둘인 이유: **사실의 시간과 앎의 시간이 다르기 때문**이다.\
  2월 10일에 "그 가격은 10,000원"이었던 것도 사실이고, 3월 15일에 "2월부터 11,000원이었다"를 알게 된 것도 사실이다.

```text
 유효일(사실의 시간)  ─────────────────────────────→
                     1/1        2/1        3/1
                   10,000    (11,000)    12,000
                                ↑
                      3/15 에야 이 사실을 알았다
 기록 시각(앎의 시간) ────────────────────────────→

 2/10 에 서 있으면   1/1 기록만 보인다        →  10,000
 오늘 서 있으면      2/1 기록도 보인다        →  11,000
```

- 어느 쪽이 맞나: **둘 다 맞다.** 맞고 틀림의 문제가 아니라 **어느 질문에 답하느냐**의 문제다.
- 영수증을 다시 뽑을 때: **그때 알던 값(10,000).** 그날 손님이 실제로 낸 돈이다.
- 정산을 다시 할 때: **지금 아는 값(11,000).** 지금 아는 사실대로면 그 돈을 받았어야 했다.
- 시간 둘: **유효 시각(`effectiveFrom`)** — 이 가격이 언제부터 맞는가 / **기록 시각(`recordedAt`)** — 우리가 그것을 언제 알았는가.

> **바이템포럴(bitemporal)** — 한 사실에 "언제부터 참인가"와 "언제 알았는가"라는 두 시간을 붙여 두는 모델.\
> 예: `PriceRecord("A", 2/1, 11_000, 3/15)` 는 "2월 1일부터 11,000원이었다는 것을 3월 15일에 알았다"는 뜻이다.

- 하나만 들고 있으면: **옛 영수증을 재현할 수 없다.**\
  유효 시각만 있으면 "지금 아는 값"만 나오고, 3/10에 발행한 영수증을 3/20에 다시 조회하면 **다른 금액이 찍힌다.**
- 대개 만드는 쪽: **"지금 아는 값".**
- 이유: **그쪽이 쉽다**(원본 javadoc 원문). 기록마다 유효일 하나만 두고 "그날 이하 중 가장 늦은 것"을 고르면 끝이다.\
  "그때 알던 값"을 만들려면 시간 축이 하나 더 필요하고, 조회 함수에 인자가 하나 더 붙는다.

#### 1. TODO 1 — 생성자

정답 코드 (impl/PriceHistory.java):

```java
if (records == null) {
    throw new IllegalArgumentException("기록이 null 이다");
}
List<PriceRecord> sorted = new ArrayList<>(records);
sorted.sort(Comparator
        .comparing(PriceRecord::effectiveFrom)
        .thenComparing(PriceRecord::recordedAt)
        .thenComparing(PriceRecord::sku));
this.records = List.copyOf(sorted);
```

- 정렬 기준: **유효일 → (같으면) 기록 시각 → (같으면) 품목 코드.**
- 기록 시각을 두 번째 기준으로 넣는 이유: **같은 유효일에 기록이 둘일 수 있기** 때문이다.\
  그때 "먼저 기록된 것이 앞"이라는 순서가 목록에 보장돼야 화면이 뒤죽박죽 안 된다.
- 정렬을 지워도 `priceOn` 의 답이 같은 이유: **가격을 찾는 코드가 전체를 훑어 비교하기** 때문이다.\
  `best` 를 들고 하나씩 비교하므로 **순서와 무관하게 같은 것이 뽑힌다.**
- 정렬이 실제로 필요한 곳: **목록을 보여줄 때**(`records()`).\
  그래서 변종 검증에서 "정렬 줄을 지워도 통과"가 나왔고, `records()` 의 순서를 확인하는 테스트를 새로 넣었다.
- 정렬을 안 하면: **목록 순서가 답을 정한다**(찾는 코드를 "앞에서 첫 매치"로 짰다면).\
  그 순서는 다시 **조회 쿼리가 정한다** — `ORDER BY` 없는 쿼리는 순서를 보장하지 않는다.
- 빈 목록: **정상**이다. `records()` 도 `backdatedRecords()` 도 빈 목록이고, `priceOn` 은 **-1** 을 준다.
- `null`: **던진다.** 빈 목록과 `null` 은 다르다 — 빈 목록은 "기록이 없다"는 사실이고, `null` 은 "뭔가 잘못됐다"는 신호다.

#### 2. TODO 2 — priceOn

정답 코드:

```java
PriceRecord best = null;
for (PriceRecord record : records) {
    if (!record.sku().equals(sku)) {
        continue;                                          // ① 품목
    }
    if (record.effectiveFrom().isAfter(on)) {
        continue;                                          // ② 아직 유효하지 않다
    }
    if (asOf != null && record.recordedAt().isAfter(asOf)) {
        continue;                                          // ③ 그때는 아직 몰랐다
    }
    if (best == null) { best = record; continue; }
    if (record.effectiveFrom().isAfter(best.effectiveFrom())) {
        best = record;
    } else if (record.effectiveFrom().equals(best.effectiveFrom())) {
        boolean later = record.recordedAt().isAfter(best.recordedAt());
        if (tie == Tie.LATEST_RECORD ? later : !later) {
            best = record;
        }
    }
}
return best == null ? -1 : best.price();
```

- 거르는 조건 셋: **① 품목이 같은가 ② 유효일이 `on` 이하인가 ③ 기록 시각이 `asOf` 이하인가.**
- 고르는 것: 남은 것 중 **유효일이 가장 늦은 것**(유효일이 같으면 `Tie` 규칙으로 가린다).
- `asOf == null`: **지금 아는 전부** — 기록 시각 필터를 안 건다.
- "그때 알던 값"을 구하려면: `asOf` 에 **그날의 끝**을 넣는다 — `on.atTime(23, 59, 59)`.\
  그날 안에 들어온 기록까지는 알고 있었다고 보는 것이다.

```text
 2/10 의 가격을 묻는다

 asOf = 2/10 23:59:59   1/1 기록(1/1 00:00)  통과   →  10,000
                        2/1 기록(3/15 00:00) 탈락 ③  ← 아직 몰랐다
                        3/1 기록(3/1  00:00) 탈락 ②  ← 아직 유효 전
                                                        답 10,000

 asOf = null            1/1 기록  통과
                        2/1 기록  통과  ← 유효일이 더 늦다
                        3/1 기록  탈락 ②
                                                        답 11,000
```

- -1 을 주는 이유: **없다는 것과 0원인 것은 다르다.**
- 0으로 두면: **매출 계산에 그대로 들어간다.**\
  "아직 등록 안 된 품목"이 "공짜로 판 품목"이 되고, 합계는 조용히 작아진다 — 예외도 경고도 없다.

> **없음을 0으로 표현하기(null-as-zero)** — 값이 없다는 사실을 숫자 0으로 적어 두는 것.\
> 예: 가격이 없는 날을 0원으로 두면 `매출 = 수량 × 가격` 이 0이 되고, 합계에서 그 건이 있었는지조차 안 보인다.

- 품목 필터를 빼먹으면: **다른 품목의 가격이 끼어든다.**\
  B의 99,000원이 A의 가격으로 나온다.
- 유효일 순 정렬에서 특히 나기 쉬운 이유: **정렬이 품목을 섞어 놓기** 때문이다.

```text
 정렬 전(품목별로 모여 있음)          정렬 후(유효일 순)
   A 1/1  10,000                        A 1/1  10,000
   A 3/1  12,000                        B 2/1  99,000   ← A 사이에 B 가 끼었다
   B 2/1  99,000                        A 3/1  12,000

 "가장 늦은 유효일"을 찾다 보면 중간의 B 를 무심코 집는다
```

#### 3. TODO 3 — changedDays

정답 코드:

```java
List<LocalDate> out = new ArrayList<>();
LocalDate at = from;
while (!at.isAfter(toInclusive)) {
    long thenKnown = priceOn(sku, at, at.atTime(23, 59, 59), tie);
    long nowKnown = priceOn(sku, at, null, tie);
    if (thenKnown != nowKnown) {
        out.add(at);
    }
    at = at.plusDays(1);
}
return out;
```

- 비교하는 둘: **그때 알던 값**과 **지금 아는 값**.
- `asOf` 에 넣는 것: **`at.atTime(23, 59, 59)`** — 그날의 끝.
- 바뀌는 날: **정확히 28일**(2/1 ~ 2/28).
- 1월·3월이 안 바뀌는 이유: **정정의 유효일이 2/1 이고 그다음 기록의 유효일이 3/1** 이기 때문이다.

```text
 1/1 ─────── 1/31   10,000  →  10,000     정정이 안 덮는다(2/1 부터라서)
 2/1 ─────── 2/28   10,000  →  11,000     ← 바뀐다
 3/1 ─────── ...    12,000  →  12,000     3/1 기록이 더 늦어서 이긴다
```

- 구간의 끝을 **포함한다**(`!at.isAfter(toInclusive)`).
- 끝을 제외로 바꿔도 통과하는 구간: **끝날이 원래 안 바뀌는 날인 구간.**\
  예제가 `1/1 ~ 3/31` 이었는데 **3/31 은 안 바뀌는 날**이라 하루를 빼도 결과가 같았다.
- 잡으려면: **끝이 실제로 바뀌는 날**인 구간 — `2/1 ~ 2/28` 로 시험하면 28이 27이 되어 잡힌다.

> **경계가 안 드러나는 테스트** — 경계를 지나가긴 하는데, 그 경계에서 결과가 원래 안 바뀌어서 실수가 안 보이는 테스트.\
> 예: `1/1 ~ 3/31` 은 끝을 포함하든 말든 28일이 나온다. 3/31 이 애초에 목록에 없기 때문이다.

- 실무에서 뜻하는 것: **이미 발행한 영수증 중 몇 장이 지금 다시 뽑으면 달라지는가.**\
  즉 "우리가 고객에게 다르게 말하게 될 건수"다.

#### 4. Tie — 같은 유효일에 기록이 둘이면

- "정정"이라는 말은 **나중 것이 이긴다**는 뜻이다(`LATEST_RECORD`).
- 그런데 둘 다 값으로 올린 이유: **"정정을 무시한다"도 실제로 쓰이는 규칙**이기 때문이다.\
  이미 마감한 기간의 값은 안 건드리는 정책이 그렇다.\
  그리고 무엇보다 **두 규칙이 얼마나 갈리는지를 세어 보기 위해서**다 — 측정에서 200개 이력 중 141개(70%)가 갈렸다.
- 안 정하면: **목록 순서가 정한다.** 그 순서는 다시 **조회 쿼리가 정한다.**
- 손계산:

```text
 3/1 부터 12,000  (기록 3/1)
 3/1 부터 13,000  (기록 3/20)    ← 같은 유효일에 들어온 정정

 3/10 의 가격을 물으면
   LATEST_RECORD   나중 기록이 이김   →  13,000
   FIRST_RECORD    먼저 기록이 이김   →  12,000
```

### B. 개념

#### 5. 함정 (README)

- 넷: ① **시간을 하나만 들고 있는 것**(유효 시각만 있으면 옛 영수증을 재현할 수 없다 — 그리고 대개 "지금 아는 값" 쪽만 만든다) ② **없는 가격을 0으로 두는 것**(0원은 매출 계산에 그대로 들어간다) ③ **같은 유효일에 기록이 둘일 때를 안 정하는 것**(목록 순서가 정하고 그 순서는 조회 쿼리가 정한다) ④ **품목 필터를 빼먹는 것**(유효일 순으로 정렬해두면 특히 나기 쉽다).
- "없다 vs 0원": **"아직 값이 정해지지 않았다"와 "값이 정해졌는데 그 값이 0이다"** 는 다른 사실인데, 0 하나로 적으면 둘을 구별할 수 없다.
- ①이 제일 앞인 이유: **다른 셋은 고치면 되지만 이것은 자료를 다시 못 만든다.**\
  기록 시각을 안 저장했으면 **그 정보가 애초에 없어서**, 나중에 코드를 고쳐도 옛 영수증을 재현할 방법이 없다.\
  ②③④는 코드 결함이고 ①은 **모델 결함**이다.

#### 6. 측정 — 답이 갈리는 건수

- 가격 변경 24회·1년·이력 200개, 소급 비율별:

```text
 소급 비율   값이 바뀐 날 평균   최대     소급 기록 평균
     0 %        0.0 / 365         0        0.0 건
    10 %       23.9 / 365        97        2.3 건
    30 %       76.3 / 365       224        7.1 건
    50 %      128.8 / 365       222       12.0 건
```

- 소급 정정이 열에 하나만 있어도 **1년의 6.5 퍼센트**(23.9/365)가 바뀐다.
- 기록 하나가 **열흘씩** 뒤집는 셈이다(23.9일 ÷ 2.3건 ≈ 10).
- 소급 정정이 없으면(0%): **200개 이력 전부에서 아무것도 안 바뀐다.**
- 이 박스가 시작되는 때: **첫 소급 정정이 들어오는 날.**\
  **그날까지는 시간을 하나만 들고 있어도 아무 문제가 없다**(README 원문).
- 과거 매출 재계산(소급 30%, 하루 10개씩 1년):

```text
 그때 알던 값으로   10,487,250,000
 지금 아는 값으로   10,573,950,000     +0.83 %
 총액이 다른 이력      200 / 200       ← 하나도 빠짐없이 다르다
```

- 두 답이 다 맞는 이유: **묻는 질문이 다르다.**\
  작년에 답한 값은 "작년 그 시점의 장부"이고 오늘 답한 값은 "지금 아는 사실로 다시 본 작년"이다.\
  **비율로는 0.83 퍼센트인데 하나도 빠짐없이 다르다** — 작아 보이는데 전수(全數)다.
- 같은 유효일이 겹치는 이력: **141 / 200 (70 %)**, 갈린 날이 평균 **18.0 일.**

> **작은 비율 × 전수** — 차이의 크기는 작은데 영향 범위가 전부인 경우.\
> 예: 총액 차이는 0.83%지만 200개 이력이 **전부** 다르다. "0.83%니까 무시하자"가 "200건 전부 틀렸다"와 같은 말이 된다.

#### 7. 변종 검증에서 고친 것

- 구간 끝을 제외로 바꿔도 통과한 이유: **예제가 `1/1 ~ 3/31` 인데 3/31 은 안 바뀌는 날**이라, 하루를 빼도 결과(28)가 같았다.
- 잡은 구간: **`2/1 ~ 2/28`** — 끝이 실제로 바뀌는 날이라 28이 27이 되어 드러난다.
- 정렬 줄을 지워도 통과한 이유: **가격을 찾는 코드가 전체를 훑어 비교**하므로 순서가 답을 안 바꾼다.\
  정렬이 필요한 곳은 **목록을 보여줄 때**다.
- 넣은 테스트: **`records()` 의 순서를 확인하는 테스트**(`recordsAreSorted`).
- 기록 시각 기준을 빼도 통과한 이유: **자바 정렬이 안정적(stable)** 이라 **넣은 순서가 그대로 남고**, 그 순서가 마침 맞았다.

> **안정 정렬(stable sort)** — 정렬 키가 같은 원소들의 원래 순서를 그대로 유지하는 정렬.\
> 예: 유효일만으로 정렬하면 3/1 짜리 둘의 앞뒤가 입력 순서대로 남는다. 입력이 우연히 기록 시각 순이면 기준을 안 넣어도 맞아 보인다.

- 가른 방법: **나중에 기록된 것을 일부러 앞에 넣었다.**

```text
 입력   [3/1 13,000(기록 3/20),  3/1 12,000(기록 3/1),  2/1 ...,  1/1 ...]
                 ↑ 나중 기록을 앞에

 기록 시각 기준 있음  →  1/1 · 2/1 · 3/1(12,000) · 3/1(13,000)   ✔
 기록 시각 기준 없음  →  1/1 · 2/1 · 3/1(13,000) · 3/1(12,000)   ✘ 입력 순서가 남는다
```

- 이미 발행한 세금계산서: **원본을 고치는 게 아니라 수정 세금계산서를 새로 발행한다.**\
  이 모델과 모양이 같다 — 옛 기록을 지우지 않고 새 기록을 **쌓는다.**\
  즉 발행한 계산서 자체가 "그때 알던 값"의 물리적 증거이고, 정정은 "지금 아는 값"으로 가는 새 줄이다.\
  06-tax 의 "발행 후 배분 규칙을 바꾸면"과 같은 자리로 이어진다. (원본에 근거 없음 — 내 추론)
- "그때 알던 값" 보고서의 재현성: **같아야 한다 — 그리고 이 모델이면 같다.**\
  `priceOn(sku, on, asOf, tie)` 는 `asOf` 를 고정하면 **언제 불러도 같은 답**을 준다(기록을 지우지 않는 한).\
  그것이 이 모델의 요점이다 — "지금 아는 값"만 있으면 같은 보고서를 두 번 뽑을 때 값이 달라진다.\
  단, `tie` 규칙을 나중에 바꾸면 그때는 달라진다 — 그래서 **보고서에 `asOf` 와 `tie` 를 같이 적어 둬야** 완전한 재현이 된다. (원본에 근거 없음 — 내 추론)
- 정정의 정정: **이 모델은 그대로 감당한다.** 같은 유효일에 기록 시각이 더 늦은 줄이 하나 더 쌓일 뿐이고, `LATEST_RECORD` 가 마지막 것을 고른다.\
  "기록 시각이 셋이 된다"는 말은 **시간 축이 셋이 된다는 뜻이 아니라 그 축 위의 점이 셋이라는 뜻**이다 — 축은 여전히 둘이다.\
  진짜 시간 축이 셋이 되는 경우는 "정정을 기록한 시스템 자체를 나중에 고친 경우"인데, 그건 이 박스 범위 밖이다. (원본에 근거 없음 — 내 추론)
- 가격 지우기: **"지움"을 나타내는 표시(tombstone)가 따로 있어야** 한다.\
  지금 모델은 `price` 가 `long` 이라 "없음"을 적을 자리가 없고, 0을 쓰면 **함정 ②** 그대로다.\
  방법은 둘 — **① 유효일부터 판매 중지를 뜻하는 별도 필드**(`deleted` 같은 표시)를 기록에 붙인다 **② 기록을 물리적으로 지운다**(그러면 "그때 알던 값"이 깨지므로 이 모델에서는 안 된다).\
  ①이 맞고, 그러면 `priceOn` 이 "지움 기록이 이겼으면 -1" 을 돌려주게 된다 — 기록 없음과 지움이 같은 -1 로 뭉치는 새 문제가 또 생긴다. (원본에 근거 없음 — 내 추론)

#### 9. 연결

- 09-policy-version 과의 비교:

```text
 09  정책 판에 시행일 하나 + 사건에 날짜 셋  →  "어느 사건 날짜를 볼까"가 결정
 10  기록 한 줄에 시간 둘                    →  "어느 시간 축에서 볼까"가 결정
```

  **같은 것** — 둘 다 "과거를 지금 다시 물으면 답이 달라진다"는 문제다.\
  **다른 것** — 09는 **비교할 날짜를 고르는** 문제(축은 하나)이고, 10은 **축 자체가 둘**인 문제다.\
  10의 모델이 더 강해서, 09의 "소급 정정을 하면 이미 처리한 취소는?"에도 답할 수 있다.

- "목록 순서가 정하고 그 순서는 조회 쿼리가 정한다": **09-policy-version의 "같은 날 시행되는 판이 둘"** 과 **똑같은 문장**이다.\
  둘 다 "동점(tie)을 안 정하면 우연이 정한다"는 같은 교훈이고, 09는 **던져서** 막았고 10은 **값(`Tie`)으로 올려서** 골랐다.
- 실무의 같은 자리: **DB의 temporal table**(SQL 표준의 시스템 버전 테이블), **event sourcing**(사실을 지우지 않고 사건을 쌓는 방식), **회계의 수정 분개**(원장을 안 고치고 반대 분개를 추가).\
  셋 다 "덮어쓰지 않고 쌓는다"는 같은 원칙 위에 있다.
