## 한눈에 — 쉽게 말하면

**정책 버전 = 게임 도중에 규칙이 바뀌면, 어느 시점의 규칙으로 판정하나.**

- 놀이공원 자유이용권이 3월 10일부터 5만 원 → 6만 원으로 올랐다. 3월 7일에 예약하고 3월 12일에 취소하러 갔다면 — **예약할 때 규칙**으로 환불받나, **취소하러 간 날 규칙**으로 받나?
- 환불 정책이 똑같은 구조다. 정책은 시행일이 붙은 **판(version)** 으로 쌓이고, 취소 한 건에는 날짜가 **셋**(주문일·신청일·처리일) 있다. **"3월 10일부터 적용"은 그중 어느 날짜를 보라는 말인지 안 정한다.**
- 고객은 주문할 때 본 약관대로 되기를 바라고, 회사는 이미 바뀐 약관대로 하고 싶다. 둘 다 말이 된다 — 그래서 안 정해두면 갈린다.
- 제일 위험한 건 **처리 시점 기준**: 우리가 늦게 처리할수록 회사에 유리해진다. 그것만으로 기준이 되면 안 된다.

```text
  정책 v1 (3/1 시행, 환불 100%) ──→ v2 (3/10 시행, 환불 80%)

  주문 3/7      신청 3/12     처리 3/15      금액 100,000
    │             │             │
    v1 → 100,000  v2 → 80,000   v2 → 80,000
    (고객이 바라는 것)     (회사가 하고 싶은 것)
```

실무 예: 이용약관 개정("○월 ○일부터 적용"), 환불·취소 규정 변경, 수수료율 개정, 세율 변경 — "언제 것 기준인가"가 항상 따라온다.

## 문제 — 이 챕터가 시키는 것

주어진 것은 날짜 셋과 정책 두 판이 전부다(원본 README 그대로).

```text
  주문 3/7   신청 3/12   처리 3/15
  정책 v1 (3/1 시행, 환불 100 %)  ->  v2 (3/10 시행, 환불 80 %)

    주문 시점   v1   100,000
    신청 시점   v2    80,000
    처리 시점   v2    80,000
```

**"'3 월 10 일부터 적용'은 어느 날짜를 보라는 말인지를 안 정한다.\
고객은 3/7 에 본 약관대로 되기를 바라고, 회사는 3/12 에 이미 바뀐 약관대로 하고 싶다."**

그리고 그 사실이 **코드 어디에도 안 적혀 있고, 대개 "가장 구하기 쉬운 날짜"로 정해진다**(원본 javadoc).

- 넣은 순서가 뒤섞여도 결과가 같다. 같은 날 시행 판 둘이면 **생성이 거부된다.**

- 환불액이 수수료보다 작으면 **0원**이지 음수가 아니다.

## 전체 흐름

```text
PolicyVersion (정책 한 판 — 계약, 다 주어져 있다)
  id · effectiveFrom(시행일) · refundRatePercent(환불%) · cancellationFee(수수료)
  effectiveOn(date): 시행일 "당일부터" 유효  ·  refundOf(amount): 비율 → 수수료 순

CancelRequest (취소 신청 — 계약, 다 주어져 있다)
  orderedOn ≤ requestedOn ≤ processedOn  (생성자가 순서를 강제)

PolicyResolver (채우는 것)
  생성: 판들을 시행일 순으로 정렬해 보관. 같은 날 시행 판 둘이면 거부
  Anchor {ORDERED, REQUESTED, PROCESSED}  ← 어느 날짜로 고르나 (정책!)
  MissingPolicy {FAIL, OLDEST}            ← 그날 유효한 판이 없으면
  versionOn(date): 시행일 ≤ date 인 것 중 "가장 늦은" 판 — 뒤에서부터 첫 매치
  refund(request, anchor, missing) = 고른 판.refundOf(금액)
  anchorsDisagree(request): 세 기준이 다른 판을 고르나 — 갈림을 관측하는 도구
```

  - *판(version)*: 정책의 한 세대. 정책을 고치면 기존 판을 수정하는 게 아니라 새 판을 쌓는다.
  - *시행일(effectiveFrom)*: 그 판이 효력을 갖기 시작하는 날. 만든 날·공표한 날과 다르다 — 날짜가 셋인데 셋이 다 다르다.

## 규칙 ① 판 고르기 — "그날 유효한 판"의 정확한 뜻

**요구사항**: "3월 10일부터 적용" → `effectiveOn(date) = !date.isBefore(effectiveFrom)` — **당일 포함**.

예시 손계산 — v1(3/1)·v2(3/10)·v3(3/20)에서:

```text
날짜:    3/1        3/9   3/10        3/19  3/20
         ├── v1 ────────┤ ├── v2 ─────────┤ ├── v3 ──→
3/9  → v1   (3/10 전날 — 아직 v2 아니다)
3/10 → v2   ("부터" 는 당일 포함)
3/19 → v2
3/20 → v3
```

- **뒤에서부터 찾는다**: "시행일이 그날 이하인 것 중 가장 늦은 것"이 답 — 정렬해 두고 뒤에서 첫 매치. 앞에서부터 찾으면 가장 오래된 판이 걸린다.
- **같은 날 시행되는 판 둘은 생성자에서 거부**: 어느 쪽인지 정할 방법이 없다(목록 순서는 쿼리가 정하는 우연). 애매함은 저장 시점에 막는다.
- **넣은 순서와 무관**: 생성자가 정렬하므로 호출자가 순서를 헷갈려도 결과가 같다.
- **시행 전 날짜(첫 판보다 이른 주문)**: `MissingPolicy.FAIL`이면 던지고, `OLDEST`면 제일 오래된 판을 쓴다. 측정: 과거 자료 5,000건 중 365건(7%)이 여기에 걸렸다 — **과거 데이터를 옮겨올 때 반드시 나오는 자리**라 정책으로 만들었다.

## 규칙 ② 기준 날짜(Anchor) — 이 챕터의 본체

**요구사항에 없는 결정**: 취소의 세 날짜 중 어느 것으로 판을 고르나. 대개 "가장 구하기 쉬운 날짜"로 조용히 정해진다 — 그래서 enum으로 드러냈다.

처리 시점이 위험한 이유 — 손계산(v2 80% → v3 3/20 시행, 50% + 수수료 5,000):

```text
주문 3/18, 신청 3/19, 처리 3/22, 금액 100,000

  신청 시점(3/19) → v2 → 80,000
  처리 시점(3/22) → v3 → 100,000×50% - 5,000 = 45,000
  같은 신청을 3/19 에 바로 처리했다면    → 80,000

  → 처리를 사흘 늦췄더니 회사가 35,000 원 이득.
    환불액이 "우리가 언제 처리하느냐" 에 달리면 안 된다.
```

측정이 보여준 것:

- **판이 하나면 절대 안 갈린다** — 이 문제는 두 번째 판을 만드는 날 시작된다. 그날까지는 뭘 쓰든 테스트가 통과한다.
- 판 수가 늘수록 갈림이 는다: 연 2회 개정이면 5,000건 중 249건(5%), 주마다 개정이면 4,266건(85%). **코드는 그대로인데 정책을 자주 바꾸기 시작하면 갑자기 나타난다.**
- 무작위 정책에선 처리 지연의 손익에 방향이 없다(좋아지기도 나빠지기도). 그러나 **정책이 나빠지는 방향(환불률 100→45)이면 처리 지연 7일에 4.69% 차이** — "늦게 처리하면 이득"은 방향성 있는 자료에서만 보인다.

## 규칙 ③ 금액 계산 — 비율과 수수료의 순서

**요구사항**: "환불 비율을 적용하고 취소 수수료를 뺀다" — 순서가 명시 안 되면 갈린다.

```text
100,000 원 · 환불 50% · 수수료 5,000

  비율 먼저(정답):  100,000 × 50% = 50,000 → - 5,000 = 45,000
  수수료 먼저:     (100,000 - 5,000) × 50%           = 47,500
  → 2,500 원 차이. 어느 쪽인지 약관에 대개 안 적혀 있다.

수수료가 환불액보다 크면:
  1,000 × 50% = 500 - 5,000 = -4,500 → Math.max(0, ·) = 0
  → 음수를 그냥 두면 "취소했는데 고객이 4,500 원을 더 내는" 청구가 된다.
```

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 처리 시점을 기준으로 쓴다 | 늦게 처리할수록 회사 이득 — 인센티브가 뒤틀린다. 기준은 주문 또는 신청 시점 |
| 판을 앞에서부터 찾는다 | "시행일 ≤ 그날" 중 **가장 늦은** 판 — 뒤에서부터 첫 매치 |
| 시행일 당일을 뺀다 | "3월 10일부터"는 3/10 포함 — 경계 날짜 3/9·3/10·3/19·3/20을 테스트에 못 박았다 |
| 같은 날 시행 판을 허용 | 목록 순서(=쿼리 순서)가 결과를 정하는 우연 — 생성자에서 던진다 |
| 수수료를 비율 앞에 뺀다 | 45,000 vs 47,500 — 비율 먼저, 수수료는 뒤에 |
| 환불액이 음수 | `max(0, ·)` — 취소가 청구로 뒤집히면 안 된다 |
| 첫 판 이전 날짜 | FAIL(던짐) / OLDEST(제일 오래된 판) 를 정책으로 — 과거 자료 이관에서 7%가 걸린다 |
| 신청보다 먼저 처리, 주문보다 먼저 취소 | CancelRequest 생성자가 날짜 순서를 강제 |

변종 검증: 변종 10개 전부 잡혔다. 뒤/앞 탐색이 갈리는 자리를 **경계 날짜별 계약 테스트**로 못 박은 것이 주효. PolicyVersion은 계약 클래스라 변종 대신 시행일 경계·수수료 순서·음수 하한을 계약 테스트에서 직접 확인.

## 핵심 문장

- 정책은 수정하는 것이 아니라 **시행일 붙은 판으로 쌓는 것**이고, "그날 유효한 판" = 시행일이 그날 이하인 것 중 **가장 늦은** 판이다(당일 포함).
- "3월 10일부터 적용"은 규칙의 절반이다 — **취소의 세 날짜(주문·신청·처리) 중 어느 것을 보느냐(Anchor)** 를 정해야 규칙이 완성된다.
- **처리 시점은 기준이 되면 안 된다** — 우리가 늦게 처리할수록 우리에게 유리해지는 기준은 그 사실만으로 실격이다.
- 이 문제는 **두 번째 판을 만드는 날 시작되고, 정책을 자주 바꿀수록 커진다** — 판이 하나일 때는 어떤 코드도 테스트를 통과한다.
- 금액 규칙은 순서까지 정해야 한다 — 비율 먼저·수수료 뒤, 그리고 **환불은 음수가 될 수 없다**(0 하한).

## 용어 풀이

- **정책 판(policy version)**: 시행일이 붙은 정책 한 세대. 고치지 않고 새 판을 쌓는다.
- **시행일(effective from)**: 판이 효력을 갖기 시작하는 날, 당일 포함. 만든 날·공표한 날과 별개.
- **기준 날짜(anchor)**: 여러 날짜 중 판을 고르는 데 쓰는 날짜 — ORDERED(주문)·REQUESTED(신청)·PROCESSED(처리).
- **MissingPolicy**: 그날 유효한 판이 없을 때의 행동 — FAIL(던짐) / OLDEST(제일 오래된 판 사용).
- **취소 수수료(cancellation fee)**: 환불에서 빼는 고정액. 비율 적용 **뒤에** 뺀다.
- **소급 적용**: 이미 지난 시점의 일에 새 규칙을 적용하는 것. 처리 시점 기준은 사실상 소급이 된다.
- **계약 클래스**: 다 주어져서 수정하지 않는 클래스(PolicyVersion·CancelRequest). 그 성질은 계약 테스트로 못 박는다.
- **경계 테스트**: 규칙이 뒤집히는 바로 그 날짜(3/9 vs 3/10)를 콕 집어 확인하는 테스트.
- **인센티브 뒤틀림**: 규칙이 규칙 운영자에게 유리한 행동(처리 지연)을 부추기는 구조.
- **이관(migration)**: 과거 데이터를 새 시스템으로 옮기는 일. 첫 판 이전 날짜가 반드시 나온다.
