### A. 과제

#### 0. 규칙 한 줄이 안 말해주는 것

- 안 말해주는 자리 셋(원본 javadoc 표 그대로):

```text
 안 말해준 것        가능한 읽기
 무엇으로 줄 세우나  →  일련번호인가 일어난 시각인가 적힌 시각인가
 중복이 있으면       →  다 반영하나 멱등 키로 거르나
 되돌리기는          →  원본을 지우나 반대 사건을 더하나
```

- 줄 세우기 기준: **말해주지 않는다.** "처음부터"는 어느 시계의 처음인지를 안 정한다.\
  같은 로그에서 세 순서가 나온다.
- 중복: **말해주지 않는다.** `REPLAY_ALL`(다 반영)과 `DEDUP_BY_KEY`(첫 건만) 둘 다 가능하다.
- 되돌리기: **말해주지 않는다.** `REMOVE_ORIGINAL`(원본을 재생에서 뺌)과 `ADD_OPPOSITE`(반대 금액을 더함) 둘 다 가능하다.
- 더하기만 있으면 순서가 답을 안 바꾸는 이유: **덧셈은 교환법칙이 성립한다.**\
  1,000 + 500 + 300 은 어느 순서로 더해도 1,800이다.

> **교환법칙(commutative)** — 순서를 바꿔도 결과가 같은 성질.\
> 예: 용돈을 받은 순서를 뒤섞어 더해도 지갑 총액은 같다.

- 순서 무관함을 깨뜨리는 한 줄: **"잔액이 음수가 되는 변경은 거부한다."**\
  거부는 "지금까지의 잔액"을 보고 판단하므로, 앞에 무엇이 왔는지에 결과가 달라진다.
- enum 세 개로 올리면: **여섯 가지 조합(3×2×2)을 같은 코드로 돌려 답이 갈리는 시행 수를 셀 수 있다.**\
  숨겨두면 "그 구현이 그렇게 돼 있다"는 사실조차 못 찾는다.

#### 1. AuditEvent — 다 주어진 계약

```java
public record AuditEvent(
        long seq, String accountId, Kind kind, long amount,
        Instant occurredAt, Instant recordedAt, Long reverses) { ... }
```

- 시각이 하나면: **순서 갈래가 아예 안 보인다**(README 함정 1번).\
  일어난 순과 적힌 순이 같은 값이 되어, 선택지가 있다는 사실을 눈치챌 수 없다.
- 벌어지는 원인 셋(javadoc 원문): **재시도 · 큐 지연 · 배치 수집.**

> **큐 지연(queue lag)** — 처리할 일이 줄을 서서 밀리는 바람에, 실제로 일어난 시각보다 한참 뒤에 기록되는 것.\
> 예: 오후 2시에 결제가 일어났는데 큐가 밀려 2시 10분에야 로그에 적힌다.

- 생성자가 막는 넷:

```text
 accountId 가 null 이거나 빈칸        →  "계정이 있어야 한다"
 kind 가 null                          →  "종류가 있어야 한다"
 두 시각 중 하나라도 null              →  "시각이 둘 다 있어야 한다"
 recordedAt < occurredAt               →  "일어나기 전에 적힐 수 없다"
 REVERSE 인데 reverses 가 null         →  "되돌릴 대상이 있어야 한다"
 CHANGE 인데 reverses 가 있다          →  "변경은 되돌릴 대상을 안 갖는다"
```

- 예외로 막는 이유: **뒤집힌 시각은 시계가 틀렸다는 신호**다.\
  그것을 조용히 받아들이면 그 사건이 엉뚱한 자리에 줄을 서고, 잔액이 조용히 틀린다.
- `REVERSE` 인데 대상이 없으면 못 만들게 하는 이유: **되돌릴 대상 없는 되돌리기는 뜻이 없다.**\
  `REMOVE_ORIGINAL` 이 `removed.add(event.reverses())` 에서 null 을 담게 되고, 그때 터지면 원인이 한참 멀어진다.
- `dedupKey()` = `accountId + "|" + kind + "|" + amount + "|" + occurredAt`\
  계정 · 종류 · 금액 · **일어난 시각** 네 개를 이어 붙인다(적힌 시각은 안 쓴다 — 재시도는 적힌 시각이 다르기 때문).
- 구별하지 못하는 두 상황(javadoc 원문):\
  ① **재시도로 두 번 적힌 한 건** ② **같은 사람이 같은 금액을 같은 초에 두 번 결제한 진짜 두 건.**\
  키가 똑같이 나와서 둘을 가를 수가 없다.
- "계약이라 다 주어져 있다"의 뜻: **입력의 모양은 고정이고, 학습자가 정할 것은 처리 규칙뿐**이라는 것.\
  입력 모양까지 바꿀 수 있으면 "멱등 키를 고치면 되지" 로 문제를 피해가게 된다.

#### 2. TODO 1 — ordered

정답 코드 (impl/AuditReplay.java):

```java
Comparator<AuditEvent> comparator = switch (ordering) {
    case BY_SEQUENCE -> Comparator.comparingLong(AuditEvent::seq);
    case BY_OCCURRED -> Comparator

            .thenComparingLong(AuditEvent::seq);

List<AuditEvent> sorted = new ArrayList<>(events);
sorted.sort(comparator);

```

- 세 값: `BY_SEQUENCE` = **일련번호**(로그에 적힌 순서 그대로) / `BY_OCCURRED` = **일어난 시각**(진짜 순서) / `BY_RECORDED` = **적힌 시각**(우리가 안 순서).
- `BY_SEQUENCE` 에 타이브레이커가 없는 이유: **일련번호 자체가 중복 없는 값**이라 같은 값이 나올 수 없다.
- 안정 ≠ 결정적:

> **안정 정렬(stable sort)** — 비교해서 같은 값끼리는 원래 있던 순서를 그대로 두는 정렬.\
> 예: `[e3, e1, e2]` 가 전부 같은 시각이면, 안정 정렬 결과도 `[e3, e1, e2]` 다.

> **결정적(deterministic)** — 입력을 어떤 순서로 넣어도 답이 항상 같은 것.\
> 예: 같은 세 사건을 `[e3, e1, e2]` 로 넣든 `[e2, e3, e1]` 로 넣든 결과가 `[e1, e2, e3]` 이어야 한다.

- 타이브레이커를 빼면: 테스트 `tiesBreakBySequence` 가 깨진다.\
  같은 시각의 셋을 **입력 순서만 뒤집어** 두 번 넣는데, 안정 정렬이 입력 순서를 그대로 두므로 한 번은 `[3,1,2]`, 한 번은 `[2,3,1]` 이 나온다. 계약은 둘 다 `[1,2,3]` 이다.
- 입력 리스트를 그 자리에서 정렬하면: **부르는 쪽의 리스트가 몰래 바뀐다.**\
  게다가 `List.of(...)` 는 못 바꾸는 리스트라 예외가 난다. 그래서 `new ArrayList<>(events)` 로 복사한다.

> **방어적 복사(defensive copy)** — 남에게서 받은 자료를 그대로 건드리지 않고, 베껴서 내 사본을 고치는 것.\
> 예: 친구 공책을 빌렸으면 거기 쓰지 말고 복사해서 쓴다.

- 세 줄짜리 로그의 손계산:

```text
  seq  일어난  적힌
   1    +30     +30
   2    +10     +50
   3    +20     +20

 BY_SEQUENCE   1 2 3
 BY_OCCURRED   +10(2) +20(3) +30(1)   ->  2 3 1
 BY_RECORDED   +20(3) +30(1) +50(2)   ->  3 1 2

 같은 로그 한 벌에서 세 순서가 나온다.
```

#### 3. TODO 2 — deduplicate

정답 코드:

```java
if (rule == DuplicateRule.REPLAY_ALL) {
    return List.copyOf(ordered);
}
Set<String> seen = new HashSet<>();
List<AuditEvent> kept = new ArrayList<>();
for (AuditEvent event : ordered) {
    if (seen.add(event.dedupKey())) {
        kept.add(event);
    }
}
return kept;
```

- `REPLAY_ALL` 일 때: **아무것도 안 거르고 그대로 돌려준다**(복사본으로).
- "처음 나온 건만 남긴다"의 한 줄: `if (seen.add(event.dedupKey()))`\
  `Set.add` 는 **처음 넣을 때만 true** 를 준다. 이미 있으면 false 라 안 담긴다.

> **멱등(idempotent)** — 같은 일을 몇 번 해도 결과가 한 번 한 것과 같은 성질.\
> 예: 전등 스위치를 "켜기" 버튼으로 다섯 번 눌러도 전등은 한 번 켜진 상태다.

- 인자 이름이 `ordered` 인 것: **"이미 줄 세운 것을 넘겨라"는 계약을 이름으로 못 박은 것**이다.\
  함수 이름·인자 이름이 호출 순서를 말해준다.
- 거르기를 앞으로 옮기면: **남는 건이 달라진다.**\
  중복 두 줄 중 어느 쪽이 "처음"인지가 입력 순서로 정해지고, 남은 건의 **적힌 시각**이 달라지며, 그 시각이 정렬 위치를 바꿔 잔액이 달라진다.
- 손계산 (테스트 `dedupHappensAfterOrdering`):

```text
  seq  금액     일어난  적힌      (1 과 2 는 멱등 키가 같다: a|CHANGE|+1000|+10)
   1   +1,000    +10     +90
   2   +1,000    +10     +20
   3   -1,000    +50     +50

 적힌 순으로 줄 세우면      2(+20)  3(+50)  1(+90)

 [줄 세우고 거르기 — 정답]
   남는 중복은 2   ->   2(+1,000) 3(-1,000)
   잔액 0 -> 1,000 -> 0            잔액 0, 거부 0 건

 [거르고 줄 세우기 — 틀린 순서]
   남는 중복은 1   ->   3(+50) 1(+90)
   잔액 0 에서 -1,000 은 음수라 거부, 그 뒤 +1,000
                                   잔액 1,000, 거부 1 건
```

- 18개를 다 통과한 이유: 기존 테스트의 중복 쌍은 **적힌 시각이 사실상 같아서**, 어느 쪽을 남겨도 정렬 위치가 안 바뀌었다.\
  둘이 같은 자리에 서면 "어느 하나를 지우느냐"가 결과에 안 나타난다.

> **변종 검증(mutation testing)** — 코드를 일부러 조금 고쳐놓고(변종), 테스트가 그것을 잡아내는지 보는 방법.\
> 예: 거르기와 줄 세우기의 순서를 바꿔놓고도 테스트가 다 통과하면, 그 테스트는 이 순서를 안 지키고 있는 것이다.

- 잡으려면: **적힌 시각만 다른 중복 두 줄**을 넣어야 한다(원본 README: "적힌 시각만 다른 두 줄을 넣으니 잡혔다 — 0 과 1,000").

#### 4. TODO 3 — replay

정답 코드:

```java
List<AuditEvent> sorted = ordered(events, ordering);
List<AuditEvent> kept = deduplicate(sorted, duplicateRule);
int duplicatesDropped = sorted.size() - kept.size();

Set<Long> removed = new LinkedHashSet<>();
if (reversalRule == ReversalRule.REMOVE_ORIGINAL) {
    for (AuditEvent event : kept) {
        if (event.kind() == Kind.REVERSE) {
            removed.add(event.reverses());
            removed.add(event.seq());
        }
    }
}

Map<String, Long> balances = new LinkedHashMap<>();
List<AuditEvent> applied = new ArrayList<>();
List<AuditEvent> rejected = new ArrayList<>();

for (AuditEvent event : kept) {
    if (removed.contains(event.seq())) {
        continue;
    }
    long delta = event.kind() == Kind.REVERSE ? -event.amount() : event.amount();
    long current = balances.getOrDefault(event.accountId(), 0L);
    if (current + delta < 0) {
        rejected.add(event);
        continue;
    }
    balances.put(event.accountId(), current + delta);
    applied.add(event);
}
return new Replay(balances, applied, rejected, duplicatesDropped);
```

- 네 단계: ① **줄 세우기** ② **중복 거르기** ③ **지울 원본 모으기**(REMOVE_ORIGINAL 일 때만) ④ **한 건씩 잔액에 반영하며 거부 판정**.
- `duplicatesDropped` = `sorted.size() - kept.size()` — **줄 세운 뒤 개수에서 거른 뒤 개수를 뺀다.**
- "둘 다 뺀다"의 둘: **되돌림을 당한 원본(`event.reverses()`)** 과 **되돌리기 사건 자신(`event.seq()`)**.
- 미리 모아두는 이유: **되돌리기는 원본보다 뒤에 오는데, 원본은 앞에서 이미 지나간다.**\
  한 번 훑으면서 지우려 하면 "이미 반영해버린 원본"을 되돌릴 수 없다. 그래서 **먼저 전체를 훑어 지울 번호를 모으고**, 그다음 잔액을 만든다.

> **두 번 훑기(two-pass)** — 자료를 한 번 훑어 정보를 모으고, 두 번째 훑을 때 그 정보를 써서 처리하는 방식.\
> 예: 시험지를 한 번 훑어 "빼야 할 문항 번호"를 적어두고, 두 번째에 그 번호를 건너뛰며 채점한다.

- `REVERSE` 의 delta 가 `-amount` 인 이유: `AuditEvent.reverse(...)` 가 **원본과 같은 금액을 그대로 복사해 담기** 때문이다.\
  +1,000 을 되돌리는 사건의 `amount` 도 +1,000 이라, 잔액에 더할 때 부호를 뒤집는다.
- 거부 판정: `if (current + delta < 0)` — **반영 후 잔액이 음수면 거부.**\
  0은 괜찮다(음수만 막는다).
- "뒤 사건의 바닥도 안 올려준다": 거부하면 **`balances.put` 을 아예 안 하고 `continue`** 한다.\
  그래서 `current` 가 그대로 남고, 다음 사건은 올라가지 않은 잔액 위에서 판정된다.
- 원본이 구간 밖일 때(테스트 `reversalWithoutItsOriginal`):

```text
 구간 안: seq 2 (+1,000),  seq 3 (seq 1 을 되돌리기, 금액 1,000)
 구간 밖: seq 1 (+1,000)   ← 이번 재생에 안 들어왔다

 REMOVE_ORIGINAL   removed = {1, 3}. 1 은 원래 없다. 3 만 빠진다.
                   남는 건 2 뿐   ->   잔액 1,000

 ADD_OPPOSITE      2(+1,000) 그다음 3(-1,000)
                                    ->   잔액 0
```

  재생 구간을 어디서 끊었느냐가 잔액을 바꾼다 — 그리고 구간은 대개 성능 때문에 끊는다.

> **재생 구간(replay window)** — 로그 전체가 아니라 "이 날짜부터 저 날짜까지"만 골라 재생하는 것.\
> 예: 3년치 로그를 매번 다 돌리면 느리니까 지난달 것만 돌린다. 그런데 지난달의 되돌리기가 재작년 사건을 가리킬 수 있다.

- `+1,000 → -800 → 되돌리기` (테스트 `removingTheOriginalCascades`):

```text
 ADD_OPPOSITE      0 +1,000 = 1,000   통과
                   1,000 -800 = 200   통과
                   200 -1,000 = -800  음수 -> 거부
                                      잔액 200, 거부 1 건

 REMOVE_ORIGINAL   removed = {1, 3}
                   1 없음. 0 -800 = -800  음수 -> 거부
                                      잔액 0,   거부 1 건 ("-800 이 갈 곳이 없다")
```

  되돌리기 하나가 그 계정의 **그 뒤 전부의 바닥을 내린다.**
- `Replay` 가 넷을 다 내놓는 이유: 잔액만 주면 **무엇이 반영됐고 무엇이 거부됐는지, 몇 건이 걸러졌는지를 부르는 쪽이 알 길이 없다.**\
  대사는 "숫자가 안 맞는다"까지만 알려주고, 원인은 이 세 목록에 있다.
- `rejected` 를 빼면: **거부된 5퍼센트가 조용해진다.**\
  거부된 사건은 잔액에 안 들어가는데 **로그에는 그대로 남아 있어서**, 로그를 눈으로 훑으면 다 반영된 것처럼 보인다.

> **조용한 실패(silent failure)** — 에러도 안 내고 정상처럼 끝나는데 결과만 틀린 것.\
> 예: 2만 건 중 1,088건이 거부됐는데 결과가 잔액 Map 하나뿐이면, 아무도 그 1,088건을 못 본다.

정답 코드:

```java

accounts.addAll(actual.keySet());

Set<String> matched = new LinkedHashSet<>();
Map<String, Long> differences = new LinkedHashMap<>();
for (String account : accounts) {
    long replayed = replay.balances().getOrDefault(account, 0L);
    long real = actual.getOrDefault(account, 0L);
    if (replayed == real) {
        matched.add(account);
    } else {
        differences.put(account, real - replayed);
    }
}
return new Reconciliation(matched, differences);
```

- 도는 목록: **둘의 합집합**이다 — 재생 쪽 계정을 담고 실제 쪽 계정을 `addAll` 로 더한다.
- 재생 쪽만 돌면: **재생에 아예 안 나타난 계정이 통째로 안 보인다.**

```text
 재생   a 1,000     b 없음
 실제   a 1,000     b 500

 재생 쪽만 돈다   ->  a 만 비교 -> "대사 깨끗"   (거짓말)
 합집합을 돈다    ->  b: 500 - 0 = +500 이 드러난다
```

  대사에서 놓치는 것은 대개 **"한쪽에만 있는 것"** 이다.

> **대사(reconciliation)** — 두 벌의 장부를 나란히 놓고 항목마다 같은지 맞춰보는 일.\
> 예: 내 가계부가 계산한 잔액과 은행 앱에 찍힌 잔액을 계좌별로 대보는 것.

- `실제 - 재생` 인 이유: **실제가 기준이고 재생이 맞춰야 할 쪽**이기 때문이다.\
  "실제보다 얼마가 모자라나/남나"로 읽힌다.
- 부호의 뜻(javadoc 원문): **양수 = 로그에 안 남은 입금이 있다**(실제가 더 많다) / **음수 = 로그에만 있는 입금이 있다**(실제가 더 적다).
- `gap()` 만 보면: **방향을 잃는다.** 그리고 방향이 원인을 가리킨다.

```text
 a  실제 1,300  재생 1,000  ->  +300
 b  실제   700  재생 1,000  ->  -300

 gap()  = |+300| + |-300| = 600
 부호 없이 600 만 보면 "어디서 새는지" 를 못 좁힌다.
```

- `clean()` = **`differences` 가 비어 있으면 참.** 하나라도 갈리면 거짓이다.

### B. 개념

#### 6. 측정 하나 — 지연과 세 순서

| 로그 지연 | 갈린 시행 | 총액 최대 차 |
|---|---|---|
| 0 % | **0 / 100** | 0 |
| 5 % | **100 / 100** | 16,200 |
| 20 % | 100 / 100 | 38,000 |
| 50 % | 100 / 100 | 50,700 |

- 지연 0이면 같은 순서를 내는 이유: **`recordedAt` 을 `occurredAt` 과 같은 값으로 넣기** 때문이다.\
  게다가 사건을 만들 때 시각이 안 줄어들게 쌓으므로, 일련번호 순 = 일어난 순 = 적힌 순이 된다.
- 그래서 개발 환경에서 통과하는 것: 개발·테스트 자료에는 **큐 지연이 없다.**\
  세 기준이 같은 답을 내니 어느 것으로 짜뒀든 테스트가 다 통과한다 — **큐가 한 번 밀리는 날 세 답이 나온다.**
- 테스트에 섞어야 하는 것: **지연**이다. 5퍼센트만 섞어도 100번 중 100번이 갈린다.

#### 7. 측정 둘 — 거부가 없으면 순서가 상관없다

- 차감 사건을 아예 안 섞으면(`allowNegative=false`): 지연 0·20·50퍼센트 전부 **갈린 시행 0 / 100**.
- 진짜 원인: **어떤 사건이 거부될 수 있어서**다. 시각이 흔들리는 것 자체는 잔액을 안 바꾼다.
- 나중에 넣으면 위험한 이유: 그때까지 **아무 문제 없던 순서 규칙이 갑자기 답을 바꾼다.**\
  "재고 부족이면 거부", "한도 초과면 거부" 같은 한 줄을 뒤늦게 넣는 일이 실무에서 흔하다.
- 두 측정이 짝으로 증명하는 명제:

```text
 거부 있음 + 지연  5 %   ->  100 / 100 갈림 (최대 차 16,200)
 거부 없음 + 지연 50 %   ->    0 / 100 갈림

 => 순서 규칙이 답이 되는 조건은 "지연" 이 아니라 "거부" 다.
    지연은 갈림을 드러내는 방아쇠일 뿐이다.
```

#### 8. 측정 셋 — 중복 0퍼센트 로그에서 9건

| 재시도 비율 | 다 반영 | 거르기 | 걸러낸 건수 |
|---|---|---|---|
| **0 %** | **135,421,300** | **135,411,600** | **9** |
| 2 % | 138,621,000 | 135,411,600 | 4,054 |
| 10 % | 150,771,900 | 135,411,600 | 20,065 |
| 30 % | 178,575,400 | 135,411,600 | 60,197 |

- 재시도 0퍼센트인데 걸러진 건수: **9건.**
- 그 정체: **진짜 두 건**이다 — 같은 계정에 같은 금액이 같은 초에 두 번 일어난 것.
- 왜 생기나: 자료 생성 코드가 초를 `second += rnd.nextInt(5)` 로 올리는데 **0이 나올 수 있고**, 계정은 50개, 금액은 100원 단위 50가지뿐이라 **우연히 세 값이 다 겹치는** 일이 20만 건 중 9번 일어난다.
- 거르는 쪽 총액이 항상 135,411,600 인 것: **재시도를 아무리 많이 넣어도 멱등 키가 다 걷어낸다**는 뜻이다.\
  거르기가 재시도에 대해서는 제대로 동작한다는 증거이면서, 동시에 **진짜 두 건까지 같은 방식으로 걷어낸다**는 뜻이기도 하다.
- 손계산 — 그 9건이 얼마인가:

```text
 135,421,300  (다 반영)
-135,411,600  (거르기)
------------
       9,700 원   = 9 건이 먹힌 금액
```

- 언제 드러나나: 20만 건 중 9건이라 **대사에서 안 보인다.**\
  보이는 것은 몇 달 뒤 고객이 "결제가 한 번만 잡혔다"고 할 때다.
- 틀리는 방향: **거르는 쪽은 진짜 두 건을 먹어 잔액이 적게** 나오고, **안 거르는 쪽은 재시도를 두 번 반영해 잔액이 많게** 나온다.\
  어느 쪽도 완벽하지 않고, 틀리는 방향이 반대일 뿐이다.

#### 9. 측정 넷 — 되돌리기 두 규칙

| 되돌리기 | 갈린 시행 | 원본 지우기 총액 | 반대 더하기 총액 |
|---|---|---|---|
| 0 % | **0 / 100** | 136,023,800 | 136,023,800 |
| 5 % | **99 / 100** | 129,999,100 | 130,753,200 |
| 20 % | 100 / 100 | 112,310,500 | 115,602,800 |

- 갈린 시행: 0퍼센트 → 0회, 5퍼센트 → **99회**, 20퍼센트 → 100회.
- 총액은 위 표 그대로다.
- 거부는 **줄어든다** — 원본 지우기 10,399 vs 반대 더하기 11,362(되돌리기 20퍼센트 기준, MeasurementTest javadoc).\
  5퍼센트에서는 10,487 vs 10,703이다.
- 줄어드는 이유: **지워진 원본이 차감이면 그 차감이 아예 안 일어난다.**\
  차감이 사라지면 잔액이 덜 내려가고, 덜 내려간 잔액 위에서는 뒤 사건이 덜 거부된다.
- 0퍼센트에서 총액이 같은 것: **되돌리기가 한 건도 없으면 두 규칙이 할 일이 없다.**\
  `removed` 집합이 비어 있어 `REMOVE_ORIGINAL` 이 아무것도 안 지우므로, 두 경로가 글자 그대로 같은 계산이 된다.

#### 10. 측정 다섯 — 조용한 거부

- 지연 20퍼센트 · 되돌리기 5퍼센트 · 100회: **반영 199,283건, 거부 10,885건.**
- 비율: `10,885 × 100 / (199,283 + 10,885) = 5` → **약 5.2퍼센트, 스무 건 중 한 건.**
- "조용하다"의 근거: 거부된 사건은 **잔액에 안 들어가는데 로그에는 그대로 남아 있다.**\
  로그를 눈으로 훑으면 반영된 것과 구별이 안 된다.
- 보이게 만드는 선택: **`Replay` 결과에 `rejected` 목록을 일급 필드로 넣는 것.**\
  잔액 Map만 돌려주는 설계였다면 이 5퍼센트를 볼 방법이 없다.

#### 11. 함정 (원본 README)

- 넷: ① **일어난 시각과 적힌 시각을 안 나누는 것**(시각이 하나면 순서 갈래가 안 보인다) ② **같은 시각의 타이브레이커를 안 두는 것**(정렬이 안정적이기만 하고 결정적이지 않다) ③ **중복을 줄 세우기 전에 거르는 것**(어느 건이 "처음"인지가 안 정해진다) ④ **거부된 사건을 안 내놓는 것**(로그에 남아 있어서 눈으로는 반영된 것처럼 보인다).
- 테스트가 다 통과해도 살아남는 것: **③ 거르기와 줄 세우기의 순서**다.\
  원본 README의 "변종 검증에서 고친 것"이 정확히 이 하나다 — 순서를 바꿔놓아도 18개가 다 통과했다.
- 실무의 모습:

```text
 ① 시각 하나       →  큐가 밀린 날 정산 금액이 서버마다 다르게 나온다
 ② 타이브레이커 없음 →  같은 자료를 다시 돌렸는데 답이 달라진다 (재현 불가 버그)
 ③ 거르기 순서      →  재처리할 때마다 잔액이 미세하게 달라진다
 ④ 거부 미노출      →  "돈이 안 들어왔다" 문의가 오기 전까지 아무도 모른다
```

#### 12. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 거부된 사건을 다시 넣나: **버리면 그 돈이 영원히 사라진다.**\
  `rejected` 목록을 결과에 담아둔 것 자체가 "다시 다룰 여지를 남긴다"는 뜻이다. 다만 **재생은 순수 계산이라 스스로 다시 넣으면 안 된다** — 같은 입력에 같은 답이 나와야 하기 때문이다. 다시 넣는 판단은 바깥(운영)의 일이다. (원본에 근거 없음 — 내 추론)
- 언제 넣나: **잔액이 올라간 뒤**여야 통과한다.\
  그런데 "올라간 뒤"를 기다리면 그 사이에 들어온 다른 차감과 순서가 또 갈린다. 실무에서는 대개 **보류 큐에 넣고 입금 이벤트가 올 때 재시도**하거나, **아예 거부하지 말고 마이너스를 허용**하고 나중에 정산한다. 어느 쪽이든 "거부"라는 규칙 자체를 다시 정하는 일이 된다. (원본에 근거 없음 — 내 추론)
- 멱등 키에 더 넣을 것: **보내는 쪽이 만든 고유 번호**(요청 ID·거래 ID)다.\
  지금 키는 (계정·종류·금액·시각)이라 **우리가 관찰한 값만으로 같음을 추측**한다. 재시도는 원래 요청의 ID를 그대로 들고 오므로, 그 ID가 키에 들어가면 진짜 두 건(ID가 다름)과 재시도(ID가 같음)가 정확히 갈린다. 시각을 쓰는 한 1초 차이 재시도도 못 거른다(테스트 `oneSecondApartEscapesDedup`: 2,000원). (원본에 근거 없음 — 내 추론)
- 재생 구간을 끊으면: **구간 밖 원본을 가리키는 되돌리기가 두 규칙에서 다른 잔액을 낸다**(테스트가 1,000 vs 0으로 못 박았다).\
  막으려면 구간을 끊을 때 **"이 구간의 되돌리기가 가리키는 원본"을 같이 끌어오거나**, 구간 시작점의 잔액을 **스냅샷**으로 들고 시작해야 한다. (원본에 근거 없음 — 내 추론)
- 실제와 재생 중 어느 쪽을 믿나: **돈은 실제가 기준**이다 — 고객 통장에 찍힌 값이 현실이다.\
  `differences` 를 `실제 - 재생` 으로 잡은 것이 그 입장을 코드에 새긴 것이다. 다만 **원인을 찾는 데는 재생이 기준**이다 — 재생은 로그가 말하는 "그랬어야 할 값"이라, 둘의 차가 곧 "로그에 안 남은 일"의 크기다. (원본에 근거 없음 — 내 추론)

#### 13. 연결

- `FeePolicy` 와 같은 일인가: **같다.** 요구사항 문장이 안 정한 자리를 **값으로 올려** 두 해석을 같은 코드로 돌려보게 만든다.\
  다른 점은 개수다 — 주차 요금은 정책 record 하나, 여기는 서로 곱해지는 enum 셋(3×2×2 = 6가지 조합)이다.
- 세는 것의 차이: 알고리즘 트랙은 **비교 횟수**(같은 답으로 가는 비용)를 셌다.\
  여기서는 **답이 갈리는 시행 수**(100번 중 몇 번)와 **총액 차이**를 센다 — 비용이 아니라 **불일치**를 잰다.
- 같은 구조의 다른 자리: **재고 차감**(재고 부족이면 거부) · **좌석 선점**(이미 잡혔으면 거부) · **한도 결제**(한도 초과면 거부).\
  전부 "거부가 있으니 순서가 답이 된다"는 같은 구조다 — 11-stock-reservation · 12-seat-hold 가 그 자리다.
- 실무 이름:

```text
 Ordering        →  이벤트 순서 보장 (event time vs processing time)
                    스트림 처리에서 "이벤트 시각으로 볼래, 처리 시각으로 볼래"
 DuplicateRule   →  멱등 처리 (idempotency key · exactly-once vs at-least-once)
 ReversalRule    →  보정 트랜잭션 (compensating transaction) vs 취소·삭제
```

> **이벤트 시각 / 처리 시각(event time / processing time)** — 일이 실제 일어난 시각 / 우리 시스템이 그것을 다룬 시각.\
> 예: 카프카·플링크 같은 스트림 처리 도구는 둘 중 무엇으로 창을 자를지를 **설정으로** 고르게 한다 — 이 챕터의 `Ordering` 과 같은 자리다.
