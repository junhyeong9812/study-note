# domain-modeling/advanced/16-audit-replay — 정리 (힌트)

## 해결하는 문제

현재 잔액 숫자 하나만 저장해 두면, 그 숫자가 틀렸을 때 **어디서부터 틀렸는지** 알 길이 없다.\
반대로 사건을 전부 적어 두면 처음부터 다시 더해 잔액을 만들 수 있다 — 그런데 "다시 더한다"는 말이 생각보다 안 정해져 있다.

```text
  [사건 로그] --(줄 세우기 ? 중복 ? 되돌리기 ?)--> [잔액]
                    └ 세 물음에 답이 없으면 같은 로그가 다른 잔액을 낸다
```

쉬운 예: 용돈 기입장을 다시 더할 때, 어제 쓴 걸 오늘 적은 줄·두 번 적은 줄·"아까 그건 취소" 줄을 어떻게 다룰지 정해야 지갑 돈과 맞는다.\
똑같은 구조다: 감사 로그에는 일어난 시각·적힌 시각이 따로 있고, 재시도가 중복을 만들고, REVERSE가 섞인다.\
실무 예: 이벤트 소싱의 상태 복원, 회계 원장 재계산, 장애 뒤 큐를 처음부터 다시 읽어 잔액 테이블을 다시 만드는 일 — 이 챕터는 그 "다시 만들기"의 숨은 결정 셋을 enum으로 드러내고, 실제 잔액과 맞춰보는(대사) 데까지 간다.

### 한눈에 — 쉽게 말하면

**감사 로그 재생 = 용돈 기입장을 처음부터 다시 계산해서 "지금 지갑에 있어야 할 돈"을 맞춰보는 일.**

- 용돈 기입장을 처음부터 다시 더해 보면 지갑 속 돈과 같아야 한다. 그런데 기입장에는 함정이 있다: **쓴 날짜와 적은 날짜가 다르고**(어제 쓴 걸 오늘 적음), 같은 줄이 두 번 적혀 있기도 하고(깜빡하고 또 적음), "아까 그건 취소"라는 줄도 있다.
- 은행 감사 로그도 똑같은 구조다. 사건마다 **일어난 시각**과 **로그에 적힌 시각**이 있고, 재시도로 중복이 생기고, 되돌리기(REVERSE)가 섞인다.
- "로그를 처음부터 다시 돌리면 지금 잔액이 나온다"는 말은 당연해 보이지만, 사실 **정해지지 않은 규칙이 3개**나 숨어 있다 — ①무엇으로 줄 세우나 ②중복은 거르나 ③되돌리기는 어떻게 반영하나.
- 그리고 이 3개 규칙이 답을 바꾸게 만드는 방아쇠는 딱 하나: **"잔액 부족이면 거부"라는 한 줄**이다. 더하기만 하면 순서는 아무래도 좋다(덧셈은 순서를 안 탄다). 거부가 생기는 순간 순서가 답이 된다.

```text
  seq  금액     일어난 시각  적힌 시각
   1   -500        +10        +90     ← 차감이 늦게 적혔다
   2   +1,000      +50        +50

  일어난 순: -500 먼저 → 잔액 0이라 거부 → +1,000 = 잔액 1,000
  적힌 순:   +1,000 먼저 → 통과 → -500 도 통과 = 잔액   500

  같은 로그인데 줄 세우는 기준에 따라 잔액이 다르다!
```

실무 예: 이벤트 소싱(event sourcing)의 리플레이, 회계 시스템의 원장 재계산, 카프카 컨슈머가 로그를 처음부터 다시 읽어 상태를 복원하는 것.
  - *이벤트 소싱(event sourcing)*: 현재 상태를 저장하는 대신 "일어난 사건들"을 전부 저장하고, 필요하면 처음부터 재생해서 상태를 만드는 설계.

## 동작·원리

### 전체 흐름

```text
요구사항: "감사 로그를 재생해 계정별 잔액을 복원하고, 실제 잔액과 맞춰본다(대사)"

  [로그: AuditEvent 목록]
        │
        ▼
  ① ordered()      — 무엇으로 줄 세우나 (Ordering 3택)
        │             BY_SEQUENCE(일련번호) / BY_OCCURRED(일어난 순) / BY_RECORDED(적힌 순)
        ▼             + 같은 시각이면 반드시 일련번호로 타이브레이크
  ② deduplicate()  — 중복은? (DuplicateRule 2택)
        │             REPLAY_ALL(다 반영) / DEDUP_BY_KEY(멱등 키로 첫 건만)
        ▼             ※ 반드시 줄 세운 "뒤에" 걸러야 한다
  ③ replay()       — 되돌리기는? (ReversalRule 2택)
        │             REMOVE_ORIGINAL(원본을 지움) / ADD_OPPOSITE(반대 금액을 더함)
        │             + 잔액이 음수가 되는 건은 거부(rejected 목록에)
        ▼
  [Replay: balances + applied + rejected + duplicatesDropped]
        │
        ▼
  ④ reconcile()    — 실제 잔액과 비교 (한쪽에만 있는 계정도 0으로 놓고 비교)
        ▼
  [Reconciliation: matched + differences(실제 - 재생, 부호 있음)]
```

### 규칙 1 — 시각이 둘이다 (AuditEvent의 설계)

**어떤 요구사항인가**: "재시도, 큐 지연, 배치 수집 때문에 일이 일어난 시각과 로그에 적힌 시각은 벌어진다. 그리고 벌어진 만큼 순서가 뒤집힌다."

이 문장이 코드에서는 `AuditEvent` 레코드의 **필드 두 개**로 번역된다:

| 필드 | 뜻 | 검증(생성자에서) |
|---|---|---|
| `occurredAt` | 실제로 일어난 시각 | 둘 다 null 금지 |
| `recordedAt` | 로그에 적힌 시각 | **일어나기 전에 적힐 수 없다** (`recordedAt < occurredAt`이면 예외) |

**예시 입력** (테스트의 실제 값):

```text
  seq  일어난 시각  적힌 시각
   1      +30         +30
   2      +10         +50     ← 제일 먼저 일어났는데 제일 늦게 적혔다
   3      +20         +20

  일련번호 순:  1 2 3
  일어난 순:    2 3 1
  적힌 순:      3 1 2      ← 같은 로그에서 세 가지 순서가 나온다
```

**왜 이렇게 모델링했나**: 시각을 하나만 두면 이 세 갈래가 아예 안 보인다(README의 함정 1번). 지연이 0이면 세 시각이 같은 순서를 내니까 **개발 환경에서는 어느 기준으로 짜두든 테스트가 통과한다** — 큐가 한 번 밀리는 날 세 기준이 세 답을 낸다. 측정: 지연이 **5%만 돼도 100번 중 100번** 세 순서의 잔액이 갈렸다(총액 최대 차 16,200).

### 규칙 2 — 같은 시각이면 일련번호로 가른다 (타이브레이커)

**어떤 요구사항인가**: "정렬이 안정적이기만 하고 결정적이지 않으면 안 된다."

- *안정 정렬(stable sort)*: 같은 값끼리는 입력 순서를 유지하는 정렬. 입력 순서가 바뀌면 결과도 바뀐다.
- *결정적(deterministic)*: 입력을 어떤 순서로 넣어도 답이 항상 같은 것.

코드 번역: 비교자에 `.thenComparingLong(AuditEvent::seq)`를 붙인다. 테스트는 같은 시각의 사건 셋을 **입력 순서만 뒤집어** 두 번 넣고 결과가 똑같이 `1, 2, 3`인지 본다. 타이브레이커가 없으면 안정 정렬이 입력 순서를 그대로 두므로 이 테스트가 깨진다.

### 규칙 3 — 중복: 멱등 키로 거르되, 거르기는 줄 세운 뒤에

**어떤 요구사항인가**: "같은 결제가 재시도로 두 번 적힐 수 있다. 다 반영하면 두 배가 되고, 거르면 진짜 두 건도 한 건이 된다."

멱등 키의 코드 번역 — `dedupKey() = accountId | kind | amount | occurredAt`:
  - *멱등(idempotent)*: 같은 일을 몇 번 해도 결과가 한 번 한 것과 같은 성질. 멱등 키는 "이 두 사건은 같은 사건이다"를 판단하는 이름표.

**손계산** (테스트의 실제 값):

```text
같은 결제 1,000원이 재시도로 두 줄 적힘:
  REPLAY_ALL    → 1,000 + 1,000 = 2,000  (재시도가 두 번 반영)
  DEDUP_BY_KEY  → 1,000                  (한 건 걸러짐)

같은 사람이 진짜로 같은 금액을 같은 초에 두 번 결제:
  DEDUP_BY_KEY  → 5,000  ← 진짜 한 건이 사라졌다!

1초 차이 나는 재시도:
  DEDUP_BY_KEY  → 2,000  ← 키가 다르니 안 걸러진다. 구멍.
```

**어느 쪽도 완벽하지 않다** — 거르면 진짜 두 건을 먹고, 안 거르면 재시도가 두 배로 잡힌다. 틀리는 방향이 반대일 뿐이다. 측정: 재시도를 **한 건도 안 넣은** 20만 건 로그에서도 멱등 키가 **9건**(진짜 두 건들)을 걸러 먹었다. 20만 건 중 9건이라 대사에서 안 보이고, 몇 달 뒤 고객이 "결제가 한 번만 잡혔다"고 할 때 드러난다.

**순서 함정 — 거르기는 줄 세운 뒤에** (변종 검증에서 잡은 버그):

```text
  seq  금액     일어난   적힌
   1   +1,000    +10     +90    원본이 늦게 적혔다
   2   +1,000    +10     +20    재시도가 먼저 적혔다   (1과 2는 멱등 키가 같다)
   3   -1,000    +50     +50

  적힌 순 정렬: 2(+20) → 3(+50) → 1(+90)

  줄 세우고 거르면: 2가 남는다 → +1,000, -1,000 → 잔액 0
  거르고 줄 세우면: 1이 남는다 → -1,000이 먼저라 거부 → 잔액 1,000
```

같은 두 줄에서 하나를 지우는 일인데 **어느 하나를 지우느냐**가 남은 건의 적힌 시각을 정하고, 그것이 잔액을 바꾼다. 줄 세운 뒤에 걸러야 "처음"이 무엇인지가 정해진다.

### 규칙 4 — 되돌리기: 원본을 지우나, 반대를 더하나

**어떤 요구사항인가**: "앞선 사건 하나를 무르는 REVERSE 사건이 있다. 이걸 어떻게 반영하나."

| 규칙 | 뜻 | 결과 |
|---|---|---|
| `REMOVE_ORIGINAL` | 원본과 되돌리기를 재생에서 둘 다 뺀다 | 애초에 없던 일이 된다 |
| `ADD_OPPOSITE` | 원본은 두고 반대 금액을 그 자리에 더한다 | 둘 다 이력에 남는다 |

**손계산 1 — 원본이 구간 안이면 잔액은 같고 이력이 갈린다**:

```text
+1,000 을 되돌리기:
  원본 지우기  → 잔액 0, 반영 0건 (아무 일도 없었다)
  반대 더하기  → 잔액 0, 반영 2건 (+1,000과 -1,000 둘 다 남음)
```

감사 로그의 목적이 이력인데 그 이력이 갈린다.

**손계산 2 — 원본이 재생 구간 밖이면 잔액도 갈린다**:

```text
되돌릴 원본(seq 1, +1,000)이 이번 재생 구간에 없다:
  원본 지우기  → 지울 것이 없다 → 구간 안의 +1,000 그대로 = 1,000
  반대 더하기  → -1,000을 그냥 더한다 = 0
```

재생 구간을 어디서 끊었느냐가 잔액을 바꾼다. 그리고 구간은 대개 성능 때문에 끊는다.

**손계산 3 — 원본을 지우면 그 뒤가 무너진다**:

```text
+1,000 → -800 → (1번 되돌리기)
  반대 더하기: 1,000 - 800 = 200, 거기서 -1,000은 음수라 거부 → 잔액 200
  원본 지우기: 1번이 없으니 -800부터 음수라 거부            → 잔액 0
```

되돌리기 하나가 그 뒤 전부의 바닥을 내린다. 측정: 되돌리기가 **5%만 있어도 두 규칙이 100번 중 99번** 갈렸다. 그리고 원본을 지우면 거부가 오히려 **줄어든다**(10,399 vs 11,362) — 지워진 원본이 차감이면 그 차감이 아예 안 일어나기 때문.

### 규칙 5 — 거부는 조용히 사라지니 목록으로 내놓는다

**어떤 요구사항인가**: "잔액이 음수가 되는 변경은 거부한다. 거부된 건은 반영도 안 되고, 뒤 사건의 바닥도 안 올려준다."

코드 번역: `Replay` 결과 레코드에 `rejected` 목록이 **일급 필드**로 들어 있다. 잔액 Map만 돌려주지 않는다.

왜냐: 거부된 사건은 잔액에 안 들어가는데 **로그에는 그대로 남아 있다**. 로그를 눈으로 훑으면 다 반영된 것처럼 보인다(README 함정 4번). 측정: 지연 20% + 되돌리기 5% 조건에서 반영 199,283건, 거부 **10,885건(5.2%)** — 스무 건 중 한 건이 조용히 거부됐다. 거부 목록을 따로 안 내면 이 5%가 안 보인다.

### 규칙 6 — 대사(reconcile): 한쪽에만 있는 계정도 갈린 것이다

**어떤 요구사항인가**: "재생 잔액과 실제 잔액을 맞춰본다."

**손계산**:

```text
재생:  a 1,000            b 없음
실제:  a 1,000            b 500

b를 안 세면 → "대사 깨끗" (거짓말)
없는 쪽을 0으로 놓고 비교 → b: 실제 500 - 재생 0 = +500 이 드러난다
```

- 차이는 `실제 - 재생`으로 **부호를 남긴다**: 양수면 로그에 안 남은 입금이 있고, 음수면 로그에만 있는 입금이 있다. 절대값 합(gap)만 보면 방향을 잃는데, 방향이 원인을 가리킨다.
- 대사에서 놓치는 것은 대개 "한쪽에만 있는 것"이다 — 그래서 두 쪽 계정의 합집합을 돈다.

## 쓰이는 자료구조·알고리즘

- **비교자 체인 + 안정 정렬** — `Comparator.comparing(occurredAt).thenComparingLong(seq)`. 같은 시각을 일련번호로 가르는 타이브레이커가 "결정적 정렬"을 만든다. Java `List.sort`는 안정 정렬(TimSort)이라 타이브레이커가 없으면 입력 순서가 답이 된다 — [algorithm/02-merge-sort](../../../algorithm/02-merge-sort/2-summary.md)의 안정성 이야기와 같은 자리.
- **해시 집합(`HashSet`)으로 멱등 키 거르기** — `seen.add(dedupKey)`가 false면 중복. 한 건당 O(1)이라 20만 건도 한 번 훑으면 끝난다 — [data-structure/05-hashmap](../../../data-structure/05-hashmap/2-summary.md).
- **삽입 순서를 지키는 맵·집합(`LinkedHashMap`·`LinkedHashSet`)** — 잔액 Map과 대사 결과가 계정을 "처음 본 순서"로 돌려준다. 재현 가능한 출력이 테스트와 디버깅을 쉽게 한다.
- **접기(fold)** — 줄 세운 사건을 앞에서부터 하나씩 잔액에 더해 가는 순차 누적. 덧셈만이면 순서가 무관(교환법칙)하지만 "음수면 거부"가 끼는 순간 순서 의존이 된다.
  - *접기(fold)*: 목록을 앞에서부터 하나씩 상태에 합쳐 최종 상태 하나를 만드는 연산. `reduce`라고도 부른다.
- **집합 합집합** — 대사에서 재생 쪽 계정과 실제 쪽 계정을 합쳐 돌아야 한쪽에만 있는 계정이 잡힌다.
- **이벤트 소싱·멱등 저장소** — 이 챕터의 `Ordering`·`DuplicateRule`이 실무 패턴으로 커진 것이 [ops-patterns/16-event-sourcing](../../../ops-patterns/16-event-sourcing/2-summary.md)·[ops-patterns/06-idempotency-store](../../../ops-patterns/06-idempotency-store/2-summary.md)다.
- **이벤트 시각 vs 처리 시각** — `occurredAt`/`recordedAt`의 분리는 스트림 처리의 event time/processing time과 같은 구분이다. 시각 대신 논리 순서를 쓰는 쪽은 [ops-patterns/14-logical-clock](../../../ops-patterns/14-logical-clock/2-summary.md).

## 적용 — 풀어나가는 법

이런 문제를 받으면 "재생하면 잔액이 나온다"는 한 줄을 그대로 코드로 옮기지 말고, **안 정해진 결정을 먼저 enum으로 꺼내는** 것부터 한다.\
그 다음 각 결정의 갈래를 손계산 예 하나씩으로 확인하고(위 규칙 1~6), 거부·중복 제거 건수를 결과에 일급으로 담아 "조용히 사라지는 것"이 없게 만든다.\
아래는 원본 챕터가 시킨 과제 목록이다 — 순서는 ordered → deduplicate → replay → reconcile, 앞 단계의 출력이 다음 단계의 입력이다.

### 문제 — 이 챕터가 시키는 것

원본 README가 준 규칙은 말 한 줄이 전부다.

```text
  seq  금액     일어난 시각  적힌 시각
   1   -500        +10        +90     차감이 늦게 적혔다
   2   +1,000      +50        +50

  "로그를 처음부터 다시 돌리면 지금 잔액이 나온다"

    일어난 순   -500 이 먼저 -> 잔액 부족으로 거부  ->  1,000
    적힌 순     +1,000 이 먼저 -> 통과            ->    500
```

README의 한 문장: **"더하기만 하면 순서가 상관없다. `잔액 부족이면 거부` 한 줄을 넣는 순간 순서가 답이 된다."**

과제 목록:

- 채울 곳은 `src/main/java/com/domain/audit/AuditReplay.java` 의 **TODO 1~4** 넷이다 — `ordered`(줄 세우기) · `deduplicate`(중복 거르기) · `replay`(재생해 잔액 만들기) · `reconcile`(실제 잔액과 대사).
- `AuditEvent` 는 **계약이라 다 주어져 있다** — 시각 두 개(`occurredAt`/`recordedAt`), 멱등 키(`dedupKey`), 생성자 검증까지 손대지 않는다.
- 안 정해진 자리는 enum 세 개로 드러나 있다 — `Ordering`(3택) · `DuplicateRule`(2택) · `ReversalRule`(2택). 구현은 이 세 스위치를 **전부** 지원해야 한다.
- 테스트가 못 박은 계약: 같은 시각이면 일련번호로 타이브레이크 · 거르기는 줄 세운 **뒤** · 잔액이 음수가 되는 변경은 거부하고 `rejected` 목록에 담기 · 대사는 두 쪽 계정의 합집합을 돌고 차이는 `실제 - 재생` 부호를 남기기.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 장애 시나리오와 대처

**1. 대사 차이가 특정 계정에서만 나고, 부호가 한쪽으로 쏠린다**

- 현상: 재생 잔액과 실제 잔액이 대부분 맞는데 몇 계정만 갈린다.
- 보이는 형태: `Reconciliation.differences`에 `{acct-7: +500, acct-9: +1,200}`처럼 **양수만** 찍힌다. `gap()`은 작지만 `clean()`이 false다.
- 원인: `실제 - 재생`이 양수 = 재생 잔액이 실제보다 적다. 후보는 여럿이다 — 실제에는 있는데 로그에는 없는 입금(트랜잭션은 커밋, 로그 쓰기는 실패), 로그에만 있는 차감(예: 재시도 중복을 `REPLAY_ALL`로 두 번 반영), 재생 구간 시작 전의 잔액을 0으로 놓고 시작한 경우.
- 대처: 부호로 방향을 먼저 읽는다 — 양수면 "재생이 모자람"(입금 누락·차감 과다), 음수면 "재생이 넘침"(로그에만 있는 입금, 로그에서 빠진 차감, 실제로는 반영된 차감을 재생이 거부한 경우). 부호는 방향만 좁혀 줄 뿐 원인을 하나로 정하지는 않으므로 해당 계정의 `applied`·`rejected`를 실제 거래 내역과 건별로 맞춘다. 누락이면 실제를 기준으로 보정 사건을 로그에 **추가**한다(로그는 지우지 않는다). 구간 시작 잔액이 원인이면 스냅샷을 초기 잔액으로 넣고 다시 돌린다(정답 12번 "재생 구간" 참고).
  - *스냅샷(snapshot)*: 어느 시점의 상태(잔액)를 통째로 저장해 둔 것. 그 뒤 사건만 재생하면 된다.

**2. 거부율이 배포 뒤 갑자기 튄다**

- 현상: 평소 재생 결과의 `rejected`가 전체의 약 5%였는데 어느 날부터 훨씬 커진다.
- 보이는 형태: `rejected.size() / (applied + rejected)` 지표가 계단처럼 오른다. 잔액 총합 `total()`이 전날보다 뚝 떨어진다.
- 원인: 재생을 부르는 쪽이 `Ordering`을 바꿨거나(예: `BY_SEQUENCE` → `BY_OCCURRED`), 큐 지연이 커져 차감이 입금보다 앞에 서는 일이 늘었다. 순서가 바뀌면 거부되는 사건이 바뀌고, 거부 하나가 그 뒤 전부의 바닥을 내린다(규칙 5).
- 대처: 거부 건수와 비율을 결과에서 뽑아 **지표로 감시**한다(결과에 `rejected`가 일급으로 있는 이유). 재생 규칙 세 개는 설정이 아니라 **계약**으로 고정하고, 바꿀 때는 옛 규칙과 새 규칙을 같은 로그에 돌려 총액 차이를 먼저 본다(측정 테스트가 하는 일).

**3. 전체 재생이 너무 오래 걸려 구간을 끊었더니 잔액이 갈린다**

- 현상: 로그가 수천만 건이 되자 처음부터 재생하는 데 몇 시간이 걸려, 최근 구간만 재생하도록 바꿨다.
- 보이는 형태: 같은 로그인데 "전체 재생"과 "최근 한 달 재생"의 잔액이 다르다. `REMOVE_ORIGINAL`에서는 지울 원본이 없어 되돌리기가 사라지고, `ADD_OPPOSITE`에서는 반대 금액이 그냥 더해진다(테스트 값 1,000 vs 0).
- 원인: 구간 밖 원본을 가리키는 REVERSE. 되돌리기는 "짝"이 있어야 뜻이 정해지는데, 구간을 끊으면 짝의 절반만 들어온다.
- 대처: 구간을 끊을 때 (a) 구간 시작 시점 스냅샷을 초기 잔액으로 쓰고, (b) 구간 안 REVERSE가 가리키는 원본을 같이 끌어오거나, 원본이 구간 밖이면 스냅샷에 이미 반영된 것으로 보고 `ADD_OPPOSITE`만 허용한다. 어느 쪽이든 **구간 경계 규칙을 계약에 적는다**.

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 시각을 하나만 둔다 | occurredAt / recordedAt 둘로 나눠야 순서 갈래가 보인다 |
| 같은 시각 타이브레이커 없음 | 일련번호로 가른다 — 안정 정렬 ≠ 결정적 정렬 |
| 거르기를 줄 세우기 앞에 한다 | 줄 세운 뒤에 걸러야 "처음"이 정해진다 (변종 검증에서만 잡힌 버그) |
| 거부된 사건을 안 내놓는다 | rejected 목록을 결과에 포함 — 로그에 남아 있어 눈으로는 반영된 것처럼 보인다 |
| 일어나기 전에 적힌 이벤트 | 생성자에서 예외 (`recordedAt < occurredAt` 금지) |
| REVERSE인데 대상 없음 / CHANGE인데 대상 있음 | 생성자에서 예외 — 종류와 reverses 필드의 짝을 강제 |
| 되돌릴 원본이 재생 구간 밖 | REMOVE_ORIGINAL은 지울 게 없어 그대로, ADD_OPPOSITE는 -금액을 그냥 더함 — 잔액이 갈린다 |
| 개발 환경(지연 0%)에서 전부 통과 | 지연 5%부터 100/100 갈림 — 테스트에 지연을 섞어야 한다 |

## 핵심 문장
- "로그를 재생하면 잔액이 나온다"는 한 문장에는 정해지지 않은 규칙이 3개 숨어 있다 — 줄 세우기 기준, 중복 규칙, 되돌리기 규칙. 도메인 모델링은 이 숨은 3택을 enum 3개(Ordering, DuplicateRule, ReversalRule)로 **드러내는** 일이다.
- 더하기만 하면 순서가 상관없다. **"잔액 부족이면 거부" 한 줄을 넣는 순간** 그때까지 멀쩡하던 순서 규칙이 답을 바꾼다 — 순서가 문제인 건 시각이 흔들려서가 아니라 어떤 사건이 거부될 수 있어서다.
- 멱등 키는 재시도와 진짜 두 건을 구별하지 못한다 — 거르는 쪽도 안 거르는 쪽도 틀릴 수 있고, 틀리는 방향이 반대일 뿐이다.
- 거르기는 줄 세운 뒤에 — 같은 중복 쌍에서 **어느 건을 남기느냐**가 남은 건의 시각을 정하고 잔액을 바꾼다.
- 거부된 사건은 로그에 남아 있어서 눈으로는 반영된 것처럼 보인다 — 결과에 거부 목록을 일급으로 내놓지 않으면 5%가 조용히 사라진다.

### 용어 풀이

- **감사 로그(audit log)**: 일어난 일을 시간 순으로 전부 남긴 기록. 지우지 않고 쌓기만 한다.
- **재생(replay)**: 로그를 처음부터 다시 돌려 현재 상태(잔액)를 만들어내는 것.
- **occurredAt / recordedAt**: 일이 실제로 일어난 시각 / 로그에 적힌 시각. 재시도·큐 지연·배치 수집 때문에 벌어진다.
- **타이브레이커(tie-breaker)**: 비교 기준이 같을 때 순서를 가르는 보조 기준. 여기서는 일련번호(seq).
- **안정 정렬(stable sort)**: 같은 값의 입력 순서를 유지하는 정렬. 결정적 정렬과 다르다.
- **멱등 키(dedup key)**: "같은 사건인가"를 판단하는 이름표. 여기서는 계정+종류+금액+일어난 시각.
- **되돌리기(reversal)**: 앞선 사건 하나를 무르는 사건. 원본을 지우는 방식과 반대 금액을 더하는 방식이 있다.
- **거부(rejection)**: 잔액이 음수가 되는 변경을 반영하지 않는 것. 거부된 건도 로그에는 남아 있다.
- **대사(reconciliation)**: 재생 결과와 실제 잔액을 계정별로 맞춰보는 일. 한쪽에만 있는 계정을 놓치기 쉽다.
- **이벤트 소싱(event sourcing)**: 상태 대신 사건을 저장하고 재생으로 상태를 복원하는 설계 방식.
- **재생 구간(replay window)**: 로그 전체가 아니라 일부 구간만 재생하는 것. 구간 밖의 원본을 되돌리는 사건이 문제를 일으킨다.
