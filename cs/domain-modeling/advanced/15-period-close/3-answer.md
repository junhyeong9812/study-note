### A. 과제

#### 0. "3월 매출"이 안 말해주는 것

- 안 말해주는 자리 셋(원본 javadoc 그대로):

```text
 어느 시각으로 달을 정하나   발생일인가 도착일인가            → Basis
 마감 뒤에 온 3 월 거래는    다음 달로 미나 다시 여나 버리나   → LateRule
 마감을 언제 도나            월말 당일인가 며칠 뒤인가        → closeAfterDays
```

- 네 조합의 3월 매출:

```text
 발생일 기준 + 다시 열기   300,000   진짜 3 월에 일어난 것
 발생일 기준 + 다음 달로   100,000   마감한 숫자를 안 건드린다
 도착일 기준               100,000   3 월에 우리가 안 것
 발생일 기준 + 버리기      100,000   그리고 200,000 은 영영 사라진다
```

- "어느 것도 틀리지 않았다"의 뜻: **넷 다 말이 되는 정의**라는 것이다.\
  "3월에 일어난 것"도 "3월에 우리가 안 것"도 "3월 마감에 잡힌 것"도 전부 3월 매출이라 불린다. 고른 뒤에야 하나가 정답이 된다.
- 계산 실수가 아닌 이유: **질문이 모호한 것**이지 답이 틀린 게 아니다.\
  세 값 모두 같은 자료에서 같은 규칙대로 정확히 계산됐다.
- 숨기고 하나만 구현하면: **나중에 다른 기준을 물었을 때 답할 수가 없다.**\
  특히 두 시각을 안 나눠 저장했으면 **자료 자체가 없어서** 코드를 고쳐도 소급이 안 된다(README 첫째 함정).

#### 1. Transaction — 시각이 둘

- 안 나누면: **두 기준 중 하나만 구현할 수 있고, 나중에 다른 쪽을 물어보면 자료가 없다.**\
  이것이 이 박스에서 가장 비싼 실수다 — 코드는 고칠 수 있어도 안 남긴 시각은 못 되살린다.
- `LocalDate` vs `LocalDateTime`:

```text
 occurredOn  LocalDate      발생은 "며칠"이면 충분하다 (달을 정하는 데만 쓴다)
 arrivedAt   LocalDateTime  도착은 마감 시각(06:00)과 견줘야 하므로 시:분이 필요하다
```

  타입이 곧 "이 값을 어느 정밀도로 쓸 것인가"를 못 박는다.
- 도착이 발생보다 빠른 거래를 거부하는 이유: **있을 수 없는 일**이기 때문이다.\
  일어나기 전에 기록이 도착할 수는 없으므로, 그런 자료는 시계 오류나 자료 오염이다. 조용히 받으면 `lateDays()` 가 음수가 되고 마감 판정이 뒤틀린다.
- 음수 금액: **취소나 환불**이다.\
  그래서 늦은 거래가 마감 금액을 **내리기도 한다**(측정 다섯).
- `lateDays()` 는 **발생일과 도착일(날짜만) 사이의 날 수**다. 마감 판정에는 안 쓰이고, 지연을 관찰하는 값이다.

#### 2. TODO 1 — closingTime

정답 코드 (impl/PeriodClose.java):

```java
return month.atEndOfMonth().plusDays(closeAfterDays).atTime(6, 0);
```

- 마감 시각:

```text
 2026-03   3/31 +1일 → 2026-04-01 06:00
 2026-02   2/28 +1일 → 2026-03-01 06:00   (2026 년 2 월은 28 일까지)
 2028-02   2/29 +1일 → 2028-03-01 06:00   (윤년이라 29 일까지)
 2026-04   4/30 +1일 → 2026-05-01 06:00
```

- 하드코딩하면 어긋나는 달: **2월과 30일인 달**이다.\
  `YearMonth.atEndOfMonth()` 는 윤년까지 알아서 맞춰준다 — 달의 길이를 코드가 직접 알 필요가 없다.
- 시각으로 잡아야 하는 이유: **마감은 시각에 돈다**(README 둘째 함정).\
  날짜로만 잡으면 "4월 1일에 마감"인데 4월 1일 05:00 에 온 거래와 07:00 에 온 거래를 구별할 수 없다. **그날 하루의 거래가 마감 앞뒤로 갈린다.**
- `closeAfterDays == 0`: **월말 당일 06:00**(3월이면 2026-03-31 06:00)이다.
- 저울질하는 두 가지: **정확함과 빠름**이다.\
  미루면 늦은 거래가 줄어 숫자가 정확해지지만, 보고가 늦어진다. 그 저울질이 **설정 하나**에 모여 있다.

#### 3. TODO 2 — monthOf

정답 코드:

```java
return basis == Basis.OCCURRED
        ? YearMonth.from(transaction.occurredOn())
        : YearMonth.from(transaction.arrivedAt());
```

- 두 기준: OCCURRED 는 **발생일**에서, ARRIVED 는 **도착 시각**에서 달을 뽑는다.
- 도착일 기준이 늦은 거래를 안 만드는 이유: **도착한 달의 마감은 그 도착보다 뒤에 온다.**\
  4/2 에 도착한 거래는 4월 소속이고 4월 마감은 5/1 06:00 이니, 정의상 절대 늦을 수가 없다. (마감 지연이 0일이어도 4/30 06:00 뒤 도착분은 늦을 수 있다 — 지연 1일 설정에서는 안 생긴다. 원본에 근거 없음 — 내 추론)
- 대신 잃는 것: **"3월에 판 것"이 3월 매출에 안 들어간다.**\
  장사한 달과 숫자가 잡히는 달이 어긋나므로, 월별 실적 비교가 흔들린다.
- 월 중간 거래가 안 갈리는 이유: **사흘 늦어도 여전히 같은 달 안**이다.

```text
 3/15 발생 → 3/18 도착   발생일 3 월, 도착일 3 월   같다
 3/31 발생 → 4/03 도착   발생일 3 월, 도착일 4 월   갈린다
```

- 결과를 정하는 것: **발생일이 월말에서 얼마나 가까운가**다.\
  지연 일수가 같아도 월말 근처에서 발생한 거래만 달을 넘는다.

#### 4. TODO 3 — close

정답 코드:

```java
LocalDateTime closedAt = closingTime(month);
long total = 0;
int count = 0;
long lateTotal = 0;
int lateCount = 0;

for (Transaction transaction : transactions) {
    if (!monthOf(transaction, basis).equals(month)) {
        continue;
    }
    if (transaction.arrivedAt().isAfter(closedAt)) {
        lateTotal += transaction.amount();
        lateCount++;
    } else {
        total += transaction.amount();
        count++;
    }
}
return new Closing(month, closedAt, total, count, lateTotal, lateCount);
```

- 따로 세는 이유: **"마감에 잡힌 숫자"와 "실제로 그달에 일어난 숫자"를 둘 다 알아야** 차이를 설명할 수 있다.\
  버리면 그 차이가 안 보이고, 합치면 마감한 숫자가 바뀐다.
- 정각 도착: **마감에 들어온다.** 테스트가 못 박았다 — 05:59 와 06:00 이 합쳐 300,000, 06:01 만 늦은 거래.
- 부등호: **`arrivedAt.isAfter(closedAt)`** 이면 늦은 것이다(= `arrivedAt > closedAt`).\
  `!isBefore` 로 쓰면 정각 한 건이 늦은 거래로 넘어간다.

```text
 마감 2026-04-01 06:00

 05:59   isAfter = false   →  마감에 포함
 06:00   isAfter = false   →  마감에 포함   ← 여기 한 건이 갈림
 06:01   isAfter = true    →  늦은 거래
```

> **경계 한 점** — 규칙 두 판이 오직 한 값에서만 다른 자리.\
> 예: 마감 06:00 정각에 온 거래. 하루에 한 번 도는 마감이라면 그 한 건이 하루치 배치 전체일 수도 있다.

- `trueTotal()` = `total + lateTotal`, 즉 **늦은 것까지 넣으면 얼마인가**다.\
  나눠 두는 이유는 **"보고한 숫자"와 "진짜 숫자"가 다르다는 사실 자체가 정보**이기 때문이다. 합쳐 두면 언제 얼마가 바뀌었는지 알 수 없다.
- 3일 뒤 마감:

```text
 마감 1일 뒤 (4/01 06:00)   total 100,000   late 200,000 (1 건)
 마감 3일 뒤 (4/03 06:00)   total 300,000   late      0  (2 건이 마감에 들어옴)
```

- 음수가 늦게 오면: **`trueTotal` 이 내려간다.**\
  테스트가 못 박았다 — 마감 때 500,000 이었는데 늦은 −200,000 이 붙어 300,000 이 된다.

#### 5. TODO 4 — closeAll

정답 코드:

```java
Map<YearMonth, Long> totals = new LinkedHashMap<>();
for (YearMonth month = from; !month.isAfter(toInclusive); month = month.plusMonths(1)) {
    totals.put(month, 0L);
}

for (Transaction transaction : transactions) {
    YearMonth month = monthOf(transaction, basis);
    if (month.isBefore(from) || month.isAfter(toInclusive)) {
        continue;
    }
    boolean late = transaction.arrivedAt().isAfter(closingTime(month));
    if (!late) {
        totals.merge(month, transaction.amount(), Long::sum);
        continue;
    }
    switch (lateRule) {
        case NEXT_PERIOD -> {
            YearMonth next = month.plusMonths(1);
            if (!next.isAfter(toInclusive)) {
                totals.merge(next, transaction.amount(), Long::sum);
            }
        }
        case REOPEN -> totals.merge(month, transaction.amount(), Long::sum);
        case DROP -> {
            // 아무 데도 안 넣는다
        }
        default -> throw new IllegalStateException();
    }
}
return totals;
```

- 0으로 먼저 채우는 이유: **거래가 하나도 없는 달도 결과에 나와야** 한다.\
  월별 보고서에서 그 달이 빠지면 "자료가 없음"과 "매출이 0"이 구별되지 않는다. 그리고 결과의 달 목록이 **요청한 범위와 정확히 같아진다.**
- 범위 밖을 안 거르면: **합계는 그대로인데 안 부른 달이 결과에 튀어나온다.**\
  `merge` 가 없는 키를 알아서 만들어 주기 때문이다. 실제로 변종 검증에서 **필터를 통째로 빼도 합계가 그대로라 안 잡혔고**, 2월·5월 거래를 섞고서야 잡혔다.
- 세 규칙에서 t2 의 200,000:

```text
 NEXT_PERIOD   4 월로 간다     3 월 100,000 / 4 월 500,000
 REOPEN        3 월에 들어간다 3 월 300,000 / 4 월 300,000
 DROP          어디에도 안 감  3 월 100,000 / 4 월 300,000   (20 만이 사라진다)
```

- 합계를 지키는 규칙: **REOPEN** 이다.\
  NEXT_PERIOD 는 범위 안에서는 지키지만 **마지막 달에서 새어 나간다.**
- 마지막 달에서 NEXT_PERIOD 는 **DROP 이 된다.**\
  밀 곳(`next`)이 범위 밖이라 그냥 버려진다. 테스트가 못 박았다 — 4월의 늦은 200,000 이 사라져 합이 100,000 이 된다(REOPEN 은 300,000).
- 회계연도의 12월이면: **그해 합계가 틀린다.**\
  12월의 늦은 거래가 다음 해로 나가므로, 연간 보고서의 총액이 실제 거래 합과 안 맞는다.
- REOPEN 의 대가: **이미 보고한 숫자가 바뀐다.**\
  3월 매출을 100,000 으로 발표해 놓고 나중에 300,000 으로 고쳐야 한다 — 합계는 지키지만 **"확정"이라는 말의 의미가 사라진다.**

### B. 개념

#### 6. 측정 — 지연 비율

거래 3,000건, 100회 (README 표 그대로):

| 지연 비율 | 늦게 온 거래 | 달이 갈린 횟수 | 최대 차 |
|---|---|---|---|
| 0 % | 0 | **0 / 1,200** | 0 |
| 5 % | 2,010 | **1,147 / 1,200** | 422,000 |
| 20 % | 7,871 | 1,199 / 1,200 | 939,000 |
| 50 % | 19,775 | 1,200 / 1,200 | 1,342,000 |

- 지연 5 %면 **1,147 / 1,200**, 즉 **열두 달 중 열한 달**이 갈린다.
- 안심할 근거가 못 되는 이유: **"거의 다 당일 도착"이 바로 이 5 %다.**\
  건수로는 작아 보이는 비율이 달 단위 집계에서는 **거의 모든 달을 오염시킨다** — 한 달에 한 건만 늦어도 그 달은 갈리기 때문이다.
- 지연 0 %에서 안 갈리는 것의 뜻: **이 문제 전체가 지연에서 나온다.**\
  그리고 개발용 자료는 대개 지연 0 %라, **이 박스의 세 결정이 전부 같은 답을 낸다.**

#### 7. 측정 — 총액 보존

지연 20 %, 100회:

| | 열두 달 합 | 전체 대비 |
|---|---|---|
| 전체 거래 | 12,120,246,000 | 100 % |
| 다시 열기 | 12,120,246,000 | **100.00 %** |
| 다음 달로 | 12,094,926,000 | 99.79 % |
| 버리기 | 11,802,083,000 | **97.37 %** |

- 다음 달로가 100 %가 아닌 이유: **마지막 달(12월)의 늦은 거래가 밀 곳이 없어서**다.\
  0.21 %가 범위 밖으로 새어 나갔다.
- 버리기에서 사라지는 비율: **2.63 %**(100 − 97.37).
- 총액 검증이 중요한 이유: **"어느 달이 맞나"는 정답이 여럿이지만, "전체 합이 맞나"는 하나**다.\
  달을 어떻게 나누든 합은 전체 거래액과 같아야 한다 — 그래서 총액은 **규칙 선택과 무관한 불변식**이고, 이것이 깨지면 규칙 문제가 아니라 버그다.

> **불변식(invariant)** — 어떤 규칙을 고르든 항상 참이어야 하는 성질.\
> 예: 달을 어떻게 나누든 열두 달의 합은 전체 거래액과 같아야 한다. 이 하나만 검사해도 "돈이 사라지는" 규칙이 바로 드러난다.

#### 8. 측정 — 마감을 미루면

| 마감 지연 | 늦은 거래 | 그 금액 |
|---|---|---|
| 0 일 | 17,757 | 720,243,000 |
| **1 일** | **7,788** | **317,562,000** |
| 3 일 | 4,193 | 170,248,000 |
| 7 일 | 307 | 12,979,000 |

- 하루만 미뤄도: **늦은 거래가 절반 이하**가 된다(17,757 → 7,788, 금액도 7.2억 → 3.2억).
- 계속 미루면 안 되는 이유: **보고가 그만큼 늦어진다.**\
  7일을 미루면 늦은 거래는 307건까지 줄지만, 3월 매출을 4월 8일에야 알 수 있다. 정확함을 사는 값이 속도다 — 그리고 이 저울질은 **코드가 아니라 회사가** 정한다.

#### 9. 측정 — 월말 당일 마감

- 지연 0 %인 자료에서도 **9,884건**이 늦은 거래로 잡힌다.
- 이유: **마감이 3/31 06:00 인데 3/31 의 거래는 그날 하루 종일 들어온다.**

```text
 마감 3/31 06:00

 3/31 05:00 거래   마감에 들어감
 3/31 09:00 거래   "늦은 거래"    ← 당일 도착인데도 늦다
 3/31 23:59 거래   "늦은 거래"
```

- "마감은 월말에 돈다"가 안 정하는 것: **월말 몇 시인가.**\
  날짜만으로는 그날 하루가 어느 쪽인지 안 정해진다.
- 지연을 줄여서는 **안 없어진다.** 지연 0 %에서도 9,884건이 나온다 — **마감 시각을 옮겨야** 없어진다.

#### 10. 측정 — 음수 거래

- 늦게 온 7,871건 중 **789건**(약 열에 하나)이 취소나 환불이다.
- 뜻: **늦은 거래가 마감 금액을 올리기만 하는 것이 아니라 내리기도 한다.**\
  "나중에 더 들어올 거예요"라고만 설명할 수 없다.
- 내려가는 정정이 어려운 이유: **이미 보고한 숫자가 줄어든다.**\
  올라가는 정정은 "좋은 소식이 늦게 왔다"로 넘어가지만, 내려가는 정정은 앞서 발표한 실적이 부풀려져 있었다는 뜻이 된다 — 매출 목표·성과급·외부 공시가 그 숫자에 걸려 있으면 더 그렇다. (뒷부분은 원본에 근거 없음 — 내 추론)

#### 11. 함정 (README)

- 넷: ① **발생일과 도착일을 안 나눈다** ② **마감 시각을 날짜로만 잡는다** ③ **늦게 온 거래를 조용히 그달에 넣는다** ④ **마지막 달의 늦은 거래를 다음 달로 민다**(밀 곳이 없다).
- 안 나누면 못 고치는 이유: **나중에 다른 기준을 물어보면 자료가 없다.**\
  코드는 배포로 고치지만, 안 남긴 시각은 과거 거래에 대해 영원히 복구할 수 없다.
- 날짜로만 잡으면: **그날 하루의 거래가 마감 앞뒤로 갈린다.**\
  마감을 몇 시에 돌았느냐에 따라 같은 날 거래가 이 달이 되기도 다음 달이 되기도 한다.
- 조용히 넣으면: **이미 보고한 숫자가 말없이 바뀐다.**\
  누가 언제 왜 바꿨는지 자취가 안 남아, 나중에 두 보고서를 맞춰보는 사람이 원인을 찾을 수 없다.

#### 12. 변종 검증

- 살아남은 변종 둘의 공통점: **둘 다 경계를 안 밟은 테스트**였다.\
  코드가 아니라 **자료에 그 경계가 없어서** 구현을 망가뜨려도 전부 통과했다.
- 정각 거래가 없을 때: **`isAfter` 를 `!isBefore` 로 바꿔도 18개가 다 통과했다.**\
  둘은 정각 한 점에서만 다른데 자료에 정각이 없었다.
- 잡으려고 세운 세 건: **05:59 / 06:00 / 06:01**.
- 범위 필터를 빼도 합계가 그대로였던 이유: **자료에 범위 밖의 달이 없었다.**\
  거를 대상이 없으면 필터의 유무가 결과에 안 나타난다(12번의 "품목 하나뿐인 테스트"와 같은 구조다). 게다가 이 결함은 **합계를 안 바꾸고 달만 늘리므로**, 합계만 보는 검증으로는 원래 못 잡는다.
- 섞으니 잡힌 것: **2월과 5월 거래.** 결과에 **안 부른 달이 생겼다.**

#### 13. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 보고한 숫자가 바뀌면 알릴 곳: `Closing` 이 **`total` 과 `lateTotal` 을 나눠 들고 있어서** "얼마가 왜 바뀌었나"를 그대로 말해줄 수 있다.\
  알려야 할 곳은 그 숫자를 **이미 쓴 사람들** — 경영 보고, 외부 공시, 성과 정산, 그리고 그 숫자를 받아 간 다른 시스템이다. 코드 쪽의 답은 "마감 결과에 버전을 붙이고, 바뀌면 바뀐 차액을 따로 남기는 것"이다. `lateTotal` 이 그 차액의 원형이다. (원본에 근거 없음 — 내 추론)
- 다시 열기 vs 정정 전표: **정정 전표 쪽이 추적하기 쉽다.**\
  다시 열면 3월 숫자가 그냥 바뀌어 "언제 왜 바뀌었나"가 안 남는다. 정정 전표는 4월에 한 줄이 더 생기므로 **원인이 자료로 남는다.** 대신 3월 숫자는 계속 틀린 채다 — 즉 **정확함(다시 열기)과 추적 가능성(정정 전표)의 맞바꿈**이고, 회계가 후자를 고르는 이유가 여기 있다. 이 코드의 `NEXT_PERIOD` 가 정정 전표에 가깝다. (원본에 근거 없음 — 내 추론)
- 해외 거래의 날짜: 이 모델은 `LocalDate`·`LocalDateTime` 이라 **시간대가 아예 없다** — 그래서 이 질문에 답할 재료가 없다.\
  답하려면 `ZonedDateTime` 이나 UTC 기준 시각 + 기준 시간대가 필요하다. 보통은 **회사(보고 주체)의 시간대**로 통일하는데, 그러면 현지 3/31 23:50 거래가 본사 기준 4/1 이 되어 "가맹점이 보는 달"과 어긋난다. 두 시각을 나눠 저장한 것과 똑같은 이유로, **원본 시간대도 같이 남겨야** 나중에 다른 기준을 고를 수 있다. (원본에 근거 없음 — 내 추론)
- 마감 뒤 도착 비율이 갑자기 늘면: **자료를 보내오는 쪽이 고장났다는 신호**다.\
  가맹점 단말·중계사·배치 전송이 밀렸거나, 우리 쪽 수신 처리가 늦어졌을 수 있다. 이 코드에서는 `lateCount` / `lateTotal` 이 그 감시 지표가 된다 — 평소 비율을 알고 있으면 **숫자가 틀리기 전에** 알아챌 수 있다. (원본에 근거 없음 — 내 추론)

#### 14. 연결

- "마감 시각 정각"과 앞 박스들: **11번의 `Boundary`(만료 정각), 14번의 `ExpiryBoundary`(소멸일 당일)와 같은 자리**다.\
  셋 다 "경계 그 한 점을 어느 쪽에 넣나"이고, 셋 다 부등호 한 글자(`isAfter` vs `!isBefore`)로 갈린다. 그리고 셋 다 **경계를 일부러 밟는 자료를 만들지 않으면 안 잡힌다.**
- 두 시각을 나눠 저장하는 것: **"원본을 버리지 말고 해석은 나중에"** 라는 원칙과 같다.\
  14번이 잔액 대신 사건을 남긴 것(이벤트 소싱)과 같은 생각이다 — 가공한 결과만 남기면 다른 질문에 답할 수 없다.
- "지연 0 %면 두 기준이 같다"의 계보:

```text
 11번  TTL 을 길게 주면        LAZY 와 SWEEP 이 같다
 12번  빈 극장(20 무리까지)    세 Adjacency 가 배정까지 같다
 13번  1 년 계약               SAME_LENGTH 와 ONE_YEAR 가 같다
 14번  전부 1 년 소멸·취소 없음  두 SpendOrder·두 RefundTarget 이 같다
 15번  지연 0 %                두 Basis·세 LateRule 이 같다 (0 / 1,200)
```

  다섯 박스 모두 **개발할 때 자연스럽게 만드는 자료가 곧 갈림을 감추는 자료**다. 갈래를 보려면 그 편한 조건을 일부러 깨야 한다.
