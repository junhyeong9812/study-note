### A. 과제

#### 0. 시작 계산이 안 말해주는 것

```text
 안 말해준 것              가능한 읽기                              올린 자리
 언제 반올림하나     →  항목마다 / 같은 통화끼리 묶어서           SumOrder
 어느 길로 가나      →  고시된 직접 환율 / 언제나 USD 경유        Path
 어떤 반올림인가     →  반올림 / 은행가 반올림 / 버림             RoundingMode 주입
 통화의 소수 자릿수  →  "센트(2 자리)" 가정은 KRW·BHD 에서 틀림   Currency.decimals()
```

- 두 값이 다른 이유: **반올림 횟수가 다르다.**

```text
 항목별   111×9.05 = 1,004.55 → 1,005   반올림 3 번
          222×9.05 = 2,009.10 → 2,009   (오차가 항목 수만큼 쌓인다)
          333×9.05 = 3,013.65 → 3,014
                              합계 6,028

 묶어서   666×9.05 = 6,027.30 → 6,027   반올림 1 번
```

- 더 정확한 쪽: **묶은 값(6,027).** 참값 6,027.3에 더 가깝고, 반올림이 한 번뿐이다.
- 그런데 못 쓰는 이유: **화면에는 항목별 금액이 줄마다 찍힌다.**\
  1,005 + 2,009 + 3,014 를 고객이 더하면 6,028인데 합계가 6,027이면 **세로 합이 안 맞는다.**
- 둘 다 가질 수 있는가: **없다.** 이건 버그가 아니라 **선택**이다 — 정확한 합계를 쓰면 세로 합이 어긋나고, 세로 합을 맞추면 합계가 덜 정확하다.

> **대사(reconciliation)** — 줄별 금액의 합과 합계가 맞는지 검산하는 일.\
> 예: 영수증 항목을 손으로 더해서 맨 아래 합계와 같은지 보는 것. 1원이 안 맞으면 사람은 전체를 의심한다.

#### 1. 금액 표현 — 최소 단위 정수

- `double` 의 문제: **0.1 + 0.2 가 0.3이 아니다.** 2진 소수로 정확히 못 적는 값이 있어서 오차가 쌓인다.
- 소수 자릿수: **KRW 0 · JPY 0 · USD 2 · EUR 2 · BHD 3.**
- "소수 둘째 자리에서 반올림"이 틀리는 통화: **KRW·JPY(0자리)와 BHD(3자리)** — 즉 **달러·유로 빼고 전부**다.
- `Money.of("10.5", KRW)` 가 던지는 이유: **원화에 10.5원은 없다.**\
  통화가 감당 못 하는 자릿수를 **입구에서** 막으면, 그 뒤의 계산 코드는 "이 금액은 유효하다"를 가정할 수 있다.
- `Money.of("10.500", BHD)`: **통과하고 minor 10500 이 된다**(scale 3 ≤ decimals 3).
- `plus` 가 같은 통화끼리만 되는 이유: **"1,000원 + 10달러"는 숫자로는 되지만 뜻이 없다.**
- 타입으로 막아서 얻는 것: **무의미한 값이 아예 안 생긴다.**\
  런타임에 "어라 이 합계가 왜 이러지"를 디버깅하는 대신, 그 코드가 컴파일·실행 시점에 바로 막힌다.

 틀린 계산   1050 × 1350.25 = 1,417,762   ← "1,417,762 원"
 올바른 계산 10.50 × 1350.25 = 14,177.625  →  14,178 원

- 같은 통화면 환율표를 안 보는 이유: **볼 것이 없다.** 1을 곱하는 것과 같고, 반올림도 안 하므로 값이 정확히 보존된다.
- `KRW → KRW` 가 표에 없어도 되는 이유: **이 분기가 표에 닿기 전에 먼저 돌려주기 때문**이다.\
  실제로 `RateTable.put` 은 같은 통화 짝을 넣으려 하면 던진다 — 넣을 수도 없고 넣을 필요도 없다.
- 자릿수가 줄어드는 환산:

```text
 BHD 1.234 × 2.6525 = 3.2731850  →  USD 3.27 (minor 327)
                                       ^^^ 3 자리가 2 자리로, 한 자리가 사라진다
```

  사라진 자리는 되돌릴 수 없다 — 그래서 **환산을 여러 번 거칠수록 정보가 준다**(왕복 손실의 일부가 여기서 온다).
- 반올림 시점: **맨 마지막에 한 번.** 중간 계산은 `MathContext(20, HALF_UP)` 로 20자리를 들고 간다.

#### 3. 환율 — 역수가 아니다

- 역수가 아닌 이유: **은행이 살 때와 팔 때 다른 값을 고시한다.**

```text
 USD → KRW  1350.25       역수 = 0.00074060
 KRW → USD  0.00073       고시값
                          그 차이가 은행의 몫이다
```

- 그 차이의 이름: **스프레드(spread).**

> **스프레드(spread)** — 은행이 살 때 쳐주는 값과 팔 때 받는 값의 차이. 은행의 몫이다.\
> 예: 공항 환전소에서 원화를 달러로 바꿨다가 그대로 다시 원화로 바꾸면 돈이 준다. 준 만큼이 스프레드다.

- 왕복:

```text
 KRW 10,000 → USD   10,000 × 0.00073 = 7.30      (minor 730)
 USD 7.30   → KRW   7.30 × 1350.25 = 9,856.825  →  9,857
                                      143 원이 사라졌다
```

- 버그가 아니라 **정상**이다. 실제 환전소에서도 그렇게 된다.
- 역수로 계산하면 지우는 것: **은행의 몫.** 코드가 현실보다 후한 값을 내고, 정산에서 계속 차이가 난다.
- `RateTable` 이 막는 셋: **같은 통화 짝을 넣는 것**, **0 이하 환율**, **같은 짝 중복 등록**.

> **방향 있는 환율(directed rate)** — `(출발 통화, 도착 통화)` 짝마다 따로 고시되는 값.\
> 예: `USD>KRW` 와 `KRW>USD` 는 이름만 반대일 뿐 서로 독립된 두 값이다. 하나에서 다른 하나를 계산하면 안 된다.

정답 코드:

return rates.require(from, Currency.USD)

- 중간에 반올림하면: **오차가 한 번 더 생긴다.**\
  JPY → USD 로 갈 때 센트 단위로 잘리고, 그 잘린 값에 다시 환율을 곱하므로 오차가 증폭된다.
- JPY 1,000:

```text
 직접    1,000 × 9.05                  = 9,050.0000  →  9,050 원
 경유    1,000 × 0.006702 × 1350.25    = 9,049.3755  →  9,049 원
                                            1 원 차이, 둘 다 맞는 계산
```

- EUR 100: **직접 146,280원 / 경유 146,273원 — 7원 차이.**

```text
 직접  100 × 1462.80              = 146,280
 경유  100 × 1.0833 × 1350.25     = 146,272.58...  →  146,273
```

- 금액이 클수록 **차이가 벌어진다**(오차가 비율로 붙기 때문이다).

> **경유 환산(triangulation)** — 직접 고시 환율이 없을 때 기축통화(보통 USD)를 거쳐 두 환율을 곱하는 것.\
> 예: BHD에서 KRW로 가는 고시는 없지만, BHD→USD와 USD→KRW는 있으므로 둘을 곱해서 간다.

- JPY 100이면 두 길이 **같다**(양쪽 다 905원).
- 함정인 이유: **예제는 대개 작다.** 작은 금액에서는 두 길이 같은 값으로 반올림되므로, 경유 문제가 통째로 안 보인다.
- 출발이나 도착이 USD 이면 같은 이유: **`RateTable.rate(USD, USD)` 가 1을 돌려준다.**

```text
 USD → KRW 를 경유로 가면   rate(USD,USD) × rate(USD,KRW) = 1 × 1350.25 = 1350.25
                             직접 환율과 같은 값이다
```

- 변종 검증에서 지운 것: **"출발이 USD인 경우"와 "도착이 USD인 경우"를 따로 처리하던 두 갈래.**\
  같은 답을 내는 갈래가 셋이었고, 둘을 지워도 테스트가 아무 말도 안 했다.
- 지운 뒤 남긴 것: **`USD → KRW` 와 `JPY → USD` 를 두 길로 계산해 같음을 못 박는 테스트**, 그리고 `rate(USD, USD) == 1` 을 직접 확인하는 assert.\
  **죽은 분기는 지우고, 지워도 되는 이유를 테스트로 남긴다.**

> **죽은 분기(dead branch)** — 있으나 마나 한 조건 분기. 지워도 결과가 같은 코드.\
> 예: 여기서 "출발이 USD면 특별 처리"는 일반 식에 이미 포함돼 있었다. 남겨두면 읽는 사람이 "왜 특별한가"를 고민하게 된다.

- BHD → KRW 직접: **던진다**(`환율이 없다: BHD>KRW`). 고시가 없다.\
  경유로는 `1.234 × 2.6525 × 1350.25 = 4,419.6...` → **4,420원**.
- 환율이 없을 때 0을 돌려주면: **결제가 0원이 된다.** 물건이 공짜로 나가고, 예외도 로그도 없다.

#### 5. TODO 3 — total

정답 코드:

```java
if (order == SumOrder.CONVERT_EACH_THEN_SUM) {
    long sum = 0;
    for (Money money : monies) { sum += convert(money, target, path).minorUnits(); }
    return new Money(sum, target);
}
long sum = 0;
for (Currency currency : Currency.values()) {
    long inCurrency = 0;
    boolean any = false;
    for (Money money : monies) {
        if (money.currency() == currency) { inCurrency += money.minorUnits(); any = true; }
    }
    if (any) { sum += convert(new Money(inCurrency, currency), target, path).minorUnits(); }
}
return new Money(sum, target);
```

- `CONVERT_EACH_THEN_SUM`: **항목 수만큼** 반올림한다.
- `SUM_THEN_CONVERT`: **통화 수만큼** 반올림한다.
- 통화가 셋 섞이면 묶어도 **세 번** 반올림한다.
- 그래서 "한 번만 반올림한다"는 말은 **통화가 하나일 때만** 맞다.
- "합한 뒤 환산"이 "같은 통화끼리 묶기"인 이유: **다른 통화끼리는 애초에 더할 수가 없다**(`Money.plus` 가 거부한다).\
  더하려면 먼저 같은 통화로 만들어야 하는데, 그게 바로 환산이다 — 즉 **순서를 완전히 뒤집는 것은 불가능**하고, 할 수 있는 최선이 "같은 통화끼리 먼저 묶기"다.
- 빈 목록: **0원**(두 순서 다).

#### 7. 반올림 방식

```text
 JPY 111 × 9.05 = 1,004.55        JPY 10 × 9.05 = 90.50 (정확히 0.5)
   HALF_UP(반올림)      1,005       HALF_UP    91
   HALF_EVEN(은행가)    1,005       HALF_EVEN  90   ← 여기서만 갈린다
   DOWN(버림)           1,004                       JPY 50 → 453 vs 452
```

- 은행가 반올림이 갈리는 경우: **소수부가 정확히 0.5일 때만.** 그때 짝수 쪽으로 간다(90.5 → 90, 452.5 → 452).
- 환율에 소수가 많으면 잘 안 생기는 이유: **곱셈 결과의 소수부가 정확히 .5 로 떨어질 확률이 낮다.**\
  9.05 같은 두 자리 환율에서는 가끔 생기지만, 0.006702 같은 환율에서는 거의 안 생긴다.
- "쓰기로 해놓고 안 쓴 것을 아무도 모른다": **HALF_EVEN 을 HALF_UP 으로 바꿔도 테스트가 거의 다 통과한다**(측정에서 5,000개 중 239개만 갈렸다).\
  회계 규정에 "은행가 반올림을 쓴다"고 적어놓고 코드는 다른 걸 쓰고 있어도 몇 년이 지나도록 드러나지 않는다.
- 버림은 **언제나 회사에 유리하다**(고객에게 줄 금액을 항상 깎는 쪽).\
  측정에서 4,483/5,000 바구니가 갈렸고 총액이 13,707원 적었다.
- 주입하는 이유: **반올림 방식이 "구현 세부"가 아니라 회계 정책이기 때문이다.**\
  값으로 밖에 두면 세 방식을 같은 코드로 돌려 총액 차이를 재볼 수 있고, 무엇을 쓰기로 했는지가 호출 지점에 남는다.

### B. 개념

#### 8. 측정 — 어긋남의 크기

- 바구니 5,000개(항목 1~10) 중 세로 합이 안 맞는 것: **1,856 / 5,000 (37%)**.\
  차이 합 **2,095원**, 한 건 최대 **3원**, 총액 차 **63원**.
- 총액으로는 1,332억 중 63원이라 없는 셈인데 문제인 이유: **안 맞는 것을 보는 사람은 영수증 한 장을 본다.**\
  전체 오차율은 회사가 보는 숫자고, 고객은 자기 영수증 한 장의 세로 합만 본다.
- 항목 수별:

```text
 항목   1  →    0 / 1,000   평균 0.00   최대  0    ← 한 번도 안 어긋난다
 항목   5  →  382 / 1,000   평균 0.40   최대  2
 항목  20  →  710 / 1,000   평균 1.10   최대  5
 항목 100  →  882 / 1,000   평균 2.45   최대 10
```

- 항목이 하나면 안 어긋나는 이유: **줄이 하나면 "줄별 환산"과 "묶어서 환산"이 같은 계산**이다. 묶을 상대가 없다.
- 예제에 대해 말해주는 것: **항목 하나짜리 예제로는 이 문제를 절대 못 본다.**\
  그리고 테스트를 처음 쓸 때 사람은 항목 하나로 시작한다. B2B 주문서는 100줄이 예사인데.
- 경유 여부로 갈린 바구니: **4,764 / 5,000 (95%)**, 차이 합 3,725,298원, 한 건 최대 **3,606원**, 총액 차 −0.0028%.
- 비율로 0.0028%인데 못 넘기는 이유: **한 건에 3,606원이면 고객 한 명의 결제 금액**이다.\
  "전체의 0.003%"는 회사의 숫자지만, 그 한 명에게는 100%다.
- 은행가 반올림 **239 / 5,000**(총액 −243원), 버림 **4,483 / 5,000**(총액 −13,707원).
- 원화만 있는 바구니: **아홉 조합이 전부 같은 값.** 환산이 없으니 반올림도 경유도 순서도 안 걸린다.
- "개발 자료는 대개 국내 주문"이 경고인 이유: **개발·테스트 환경의 데이터가 갈림이 0인 쪽에 몰려 있다.**\
  기능은 다 만들었고 테스트도 통과하는데, 해외 주문이 처음 들어오는 날 전부 드러난다.

#### 9. 함정 (README)

- 다섯: ① **"센트"를 가정하는 것**(KRW·JPY는 0자리, BHD는 3자리 — 100배씩 틀린다) ② **최소 단위 정수에 환율을 바로 곱하는 것**(사람이 읽는 금액으로 바꿔 곱해야 한다) ③ **환율이 서로의 역수라고 믿는 것**(그 차이가 은행의 몫이다) ④ **모든 짝의 환율이 있다고 믿는 것**(BHD→KRW 고시는 없다) ⑤ **환율이 없을 때 조용히 0으로 두는 것**(결제가 0원이 된다).
- 100배 틀리는데 예외가 안 나는 것: **②번.** 결과가 그냥 큰 정수라서 타입도 검증도 안 걸린다.
- 결제가 0원이 되는 것: **⑤번.**

#### 10. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 환율의 시점: 이 `RateTable` 은 **시점이 없다** — "지금의 표" 하나뿐이다. 실무에서는 **주문 시점 환율을 주문에 스냅샷으로 저장**하는 것이 보통이다(고객에게 보여준 금액이 곧 약속이므로). 그런데 카드사는 **매입 시점** 환율로 청구하고, 정산은 **정산 시점** 환율로 떨어진다 — 그래서 세 시점의 차이가 그대로 손익이 된다. 이걸 다루려면 `RateTable` 에 유효 시각이 붙어야 하고, 그러면 "그 시각의 표"를 고르는 책임이 밖으로 나간다. (원본에 답 없음 — 내 추론)
- 세로 합이 안 맞는 영수증: 답할 말이 없다. 그래서 현실의 해법은 **설명이 아니라 설계**다 — ① `CONVERT_EACH_THEN_SUM` 을 쓰고 합계의 정확도를 포기한다(가장 흔하다) ② 차액 1원을 **마지막 줄에 몰아주는 배분**을 한다(줄 합과 합계가 둘 다 맞게 된다. 회계 소프트웨어가 쓰는 방법이다) ③ "환율 조정" 같은 별도 줄을 만들어 차액을 드러낸다. **②가 가장 정직하지만 "어느 줄에 몰아줄 것인가"라는 새 결정이 생긴다.** (원본에 답 없음 — 내 추론)
- 부분 환불의 환율: **결제 시점 환율로 돌려주는 것이 맞다** — 고객이 낸 돈을 돌려주는 것이지 지금 값어치를 돌려주는 게 아니기 때문이다. 그러려면 결제 시점의 **환산된 금액을 저장**해 두어야 한다(환율만 저장하면 반올림을 다시 해야 하고, 그 결과가 원래 청구액과 1원 어긋날 수 있다). 그리고 부분 환불에서는 **04-refund 의 비례배분 문제가 여기서 또 나온다** — 환산된 총액을 품목별로 어떻게 쪼개나. (원본에 답 없음 — 내 추론)
- 통화를 하나 더 지원하면: **모든 짝을 고시하려면 `n × (n−1)` 줄**이 필요하다 — 5개면 20줄, 6개면 30줄, 10개면 **90줄**이다. 제곱으로 는다. 그래서 현실의 환율표는 **USD 를 중심으로 `2 × (n−1)` 줄만 들고**(10개면 18줄) 나머지는 경유로 계산한다 — 그게 `Path.VIA_USD` 가 존재하는 이유다. 대신 경유 값은 직접 고시와 다르고, 그 차이가 위 측정의 3,606원이다. (원본에 답 없음 — 내 추론)

#### 11. 연결

- 03-subscription-change 와 같은 구조: 구독은 **"두 줄을 각각 반올림할까 차액을 한 번에 반올림할까"** 로 44/365일이 1원 어긋났고, 여기는 **"항목마다 반올림할까 묶어서 한 번 할까"** 로 37%의 바구니가 어긋난다. 둘 다 결론이 같다 — **고객에게 보이는 줄의 합이 합계여야 하므로, 정확도보다 정합을 택한다.**
- 죽은 분기 이야기: 03의 **`Math.max(0, ...)` 를 지운 것**과 여기의 **`viaUsd` 두 갈래를 지운 것**이 같다. 둘 다 "안전해 보이지만 도달할 수 없거나 같은 답을 내는 코드"였고, 둘 다 **지운 뒤 지워도 되는 이유를 테스트나 주석으로 남겼다.**
- 최소 단위 정수 관행: **실무의 돈 처리 표준**이다(Stripe·PayPal 등 결제 API가 전부 `amount` 를 최소 단위 정수로 받는다). 부동소수점을 아예 안 쓰고, 통화 코드를 금액과 같이 들고 다니는 것이 규칙이다.
