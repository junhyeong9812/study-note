# domain-modeling/advanced/07-installment — 정리 (힌트)

## 해결하는 문제

정수 금액을 회차로 나누면 나머지가 남고, "연 12%"라는 말은 이자를 어디에 매기는지 안 정한다.\
이 모델이 없으면: 상환표의 원금 합이 999,996원이 되어 완납 뒤 4원이 "미납"으로 남고, 무이자 할부에서 원리금 균등 공식이 0으로 나누기로 터지며, 같은 "연 12%"인데 잔액에 이자를 매기느냐(원리금 균등) 원금 전체에 매기느냐(애드온)에 따라 총 이자가 크게 다르다(100만원·12개월 사례에서 애드온이 1.81배 — README 측정 넷).

```text
1,000,000 ÷ 12 = 83,333.33...
  나머지를 안 다루면   83,333 × 12 = 999,996   → 완납인데 잔액 4원
  나머지를 다루면      어느 달에 4원을 얹나 = 정책 (LAST / FIRST / SPREAD)
```

쉬운 예: 사탕 100만 개를 12명에게 남김없이 나누기 — 4개가 남고, 누구에게 주느냐를 정해야 한다.\
똑같은 구조다: 몫은 **내림**으로 구해 나머지를 0 이상으로 만들고, 어느 회차에 얹을지를 `Residue`로, 이자를 잔액에 매기나 원금 전체에 매기나를 `Method`로 드러낸다. 그리고 원금 합·마지막 잔액이라는 **불변식 둘**을 아홉 조합 × 2,000건에서 확인하고, 잔액 단조 감소는 기준 사례 한 건의 아홉 조합에서 확인한다(`MeasurementTest.principalAlwaysReconciles`, `InstallmentPlanTest.balanceNeverGrows`).\
실무 예: 카드 할부 안내문, 대출 상환 계획표, 무이자 할부.

### 한눈에 — 쉽게 말하면

**할부 상환표 = 사탕 100만 개를 12명에게 남김없이 나눠주기 + "빌린 값(이자)을 어떻게 매기나".**

- 사탕 1,000,000개를 12명에게 똑같이 나누면 한 명당 83,333.33...개 — 사탕은 쪼갤 수 없으니 83,333개씩 주면 **4개가 남는다.** 이 4개를 누구에게 주나? 마지막 사람? 첫 사람? 앞에서부터 1개씩?
- 할부가 똑같은 구조다. 1,000,000원을 12개월로 나누면 원 단위로 4원이 남고, **어느 달에 얹느냐(Residue)** 가 규칙이다. 셋 다 합은 정확히 1,000,000원 — 갈리는 건 "어느 달에 몇 원 더 내나"뿐... 인 줄 알았는데 **그 4원이 총 이자까지 바꾼다.**
- 거기에 **이자 방식(Method)** 이 또 셋: 원리금 균등(매달 내는 돈이 같음) / 원금 균등(매달 갚는 원금이 같음) / 애드온(원금 전체 × 기간으로 이자를 한 번에). 같은 "연 12%"인데 애드온은 부담이 **1.81배**다.

```text
  1,000,000 원 ÷ 12 개월 = 83,333.33...  → 원 단위로 끊으면 4 원이 남는다

    마지막에 몰기   83,333 ×11, 83,337
    처음에 몰기     83,337, 83,333 ×11
    나눠서(SPREAD)  83,334 ×4,  83,333 ×8
                    └─ 셋 다 합은 정확히 1,000,000
```

실무 예: 카드 할부 안내문("왜 마지막 달만 금액이 다른가요" 문의가 여기서 나온다), 대출 상환 계획표, 무이자 할부.

## 동작·원리

### 전체 흐름

```text
Loan (할부 조건 — 계약, 다 주어져 있다)
  principal(원금) · annualRatePercent(연 이자율%) · months(개월)
  monthlyRate() = 연이율 / 100 / 12  ← 관행이자 법정 표시 방식 (복리 환산은 안 쓴다)
  interestFree() = 이자율 0 인가

InstallmentPlan.schedule(loan, Method, Residue) → Schedule(상환표)
  ① 원금을 가중치대로 쪼갠다 (split: 내림 + 나머지를 Residue 규칙대로 얹기)
     - 원금 균등·애드온: 가중치 전부 1 (균등)
     - 원리금 균등: 회차별 원금이 점점 느는 가중치 (공식에서 유도)
  ② 이자를 매긴다
     - 원리금·원금 균등: 이자 = 그달의 남은 원금(잔액) × 월이율
     - 애드온: 이자 = 원금 전체 × 월이율 × 개월 수 를 한 번에 → 회차로 균등 분할
  ③ 회차(Installment: 원금·이자·잔액)를 쌓아 Schedule 완성

불변식: 원금의 합 == 원금  ·  마지막 잔액 == 0  ·  잔액은 한 번도 안 는다
```

  - *상환표(schedule)*: 회차마다 "원금 얼마 + 이자 얼마 = 낼 돈 얼마, 남은 빚 얼마"를 적은 표.
  - *잔액(balance)*: 아직 안 갚은 원금. 이자는 여기에 붙는다(애드온만 예외).

### 규칙 ① 나머지 배분 (Residue) — "남는 4원을 어디에 두나"

**요구사항**: "원 단위로 끊고 남은 것을 어디에 두나" → enum `Residue {LAST, FIRST, SPREAD}` 로 번역. 계산 로직이 아니라 **정책이라서 타입으로 드러냈다.**

핵심 구현 규칙 — **몫은 내림(FLOOR)으로 구한다**:

```text
내림으로 구하면:   합 ≤ 총액 → 나머지 ≥ 0 → 어느 회차에 "더해주면" 된다
반올림으로 구하면: 합이 총액을 넘칠 수 있다 → 나머지가 음수
                   → 어느 회차에서 돈을 "빼야" 한다 (원금 0원·잔액 역전 같은 이상한 회차가 생긴다)
```

나머지가 이자를 움직이는가 — 방식에 따라 답이 다르다(테스트가 못 박은 값):

| | 마지막에 몰기 | 처음에 몰기 | 나눠서 |
|---|---|---|---|
| 원리금 균등 총 이자 | 66,186 | **66,185** | 66,186 |
| 원금 균등 총 이자 | 65,000 | 65,000 | 65,000 |

- 원리금 균등: 처음에 4원을 더 갚으면 이후 열한 달의 잔액이 4원씩 작아져 이자가 준다 — **1원 차이지만 방향이 언제나 같다**(측정 5,000건: 처음 몰기가 항상 최소).
- 원금 균등: 4원이 잔액을 움직여도 거기 붙는 월 1%는 0.04원 — 원 단위 반올림에서 사라진다. 그래서 "나머지가 이자를 바꾼다"는 말이 **방식에 따라 맞고 틀리다.**
- 측정: 5,000건 중 3,517건에서 첫 회차 금액이 갈렸다. 안 갈린 30%는 **나누어떨어지는 금액** — 그리고 사람은 예제를 만들 때 나누어떨어지는 금액(1,200,000÷12)을 고른다.

### 규칙 ② 이자 방식 (Method) — 같은 "연 12%"의 세 얼굴

1,000,000원 · 연 12% · 12개월 손계산:

```text
원금 균등     : 매달 원금 83,333~ + 이자(잔액×1%)      총 이자  65,000
               1회 93,333 원 → 12회 84,170 원 (점점 준다, 폭 9,163)
원리금 균등   : 매달 내는 돈 = P·r·(1+r)^n / ((1+r)^n - 1) ≈ 88,850 고정
               1회 원금 78,848 + 이자 10,000 → 갈수록 원금↑ 이자↓  총 이자  66,186 (폭 8원)
애드온        : 이자 = 1,000,000 × 1% × 12 = 120,000 을 한 번에    총 이자 120,000
```

- **원리금 균등의 폭 8원은 반올림 때문**이고 **원금 균등의 폭 9,163원은 규칙 그 자체**다. "매달 얼마 내나요"에 한쪽은 답할 수 있고 한쪽은 못 한다.
- **애드온은 갚아나가는 것을 안 본다.** 이미 갚은 원금에도 이자를 문다 → 1.81배. 기간이 길수록 배수가 커진다(3개월 1.49배 → 24개월 1.85배). **짧은 할부 예제로 시험하면 방식 차이가 작아 보인다.**
- 원리금 균등은 초기 회차의 원금이 작다(1회 78,848) → **초기에 중도 상환하면 남은 원금이 생각보다 많다.**
- 왜 원금을 먼저 나누고 이자를 잔액에서 뽑는 구조인가: "이자는 남은 빚에 붙는다"는 도메인 문장을 그대로 코드 구조(원금 배열 → 잔액 → 이자)로 옮긴 것. 애드온만 이자를 따로 나눈다 — 잔액을 안 보는 방식이라서.

### 규칙 ③ 무이자 — 흔한데 코드가 터지는 자리

**요구사항**: "무이자 할부는 흔하다." 그런데 원리금 균등 공식 `(1+r)^n - 1`은 r=0이면 **0으로 나누기**가 된다.

```text
r = 0  →  분모 (1+0)^12 - 1 = 0  →  나누기 폭발
올바른 처리: interestFree() 면 원금 균등과 같은 균등 가중치로 갈아탄다
결과: 무이자면 세 방식이 통째로 같은 상환표 — 남는 갈림은 나머지 규칙 하나뿐
```

## 쓰이는 자료구조·알고리즘

- **정수 분할(내림 몫 + 나머지 배분)** — `split(total, weights, residue)`. 가중치 비례로 몫을 내림해 합이 총액을 넘지 않게 한 뒤 남은 나머지를 규칙대로 얹는다. 반올림으로 몫을 구하면 나머지가 음수가 되어 어느 회차에서 돈을 빼야 한다. [06-tax](../06-tax/2-summary.md)의 "마지막 몫은 빼기"와 같은 계열.
- **폴드(잔액 갱신)** — 원금 배열을 앞에서부터 훑으며 먼저 `이자 = 상환 전 잔액 × 월이율`을 구하고, 그다음 `잔액 −= 당회 원금`으로 갱신한다(impl `InstallmentPlan.java:199-206`). "이자는 남은 빚에 붙는다"는 도메인 문장이 그대로 순회 구조다. 애드온은 **이자 계산에만** 이 폴드를 안 쓴다 — `balanceAfter`를 만드는 잔액 갱신은 세 방식 모두 한다(`:210-216`).
- **등비수열 공식(원리금 균등 납입액)** — `P·r·(1+r)^n / ((1+r)^n − 1)`. impl은 이 납입액에서 회차별 원금을 뽑아 원금 배분 가중치로 쓴다(`:152-174`). `r = 0`이면 분모 0 — 무이자는 균등 가중치로 갈아탄다. 수식의 정의역을 코드가 지켜야 한다.
- **불변식 검증(속성 기반 테스트)** — 아홉 조합 × 2,000건에서 `원금 합 == 원금`·`마지막 잔액 == 0`을 확인한다(README "변종 검증"). `잔액 단조 감소`는 기준 사례(100만원·12%·12개월)의 아홉 조합에서 따로 확인한다. 개별 값이 아니라 **성질**을 못 박은 것이 변종 15개를 전부 잡는 데 주효했다.
- **enum 3×3 데카르트 곱** — `Method × Residue`. 무이자면 세 방식이 같아져 갈림이 `Residue` 하나로 준다.
- **고정 소수(`BigDecimal`)** — 월이율 `연이율 / 100 / 12`와 이자 계산. 원 단위 반올림은 회차마다.

## 적용 — 풀어나가는 법

풀이 순서는 컬렉션 공통 — 빈 결정 찾기 → enum 올리기 → 갈리는 입력 만들기 → 조합별 측정.\
할부에서 갈리는 입력은 **나누어떨어지지 않는 금액 + 이자 있음 + 긴 기간(12개월 이상)** 이다. 1,200,000÷12·무이자·3개월은 예제로 만들기 제일 쉬운데, 각각 나머지 규칙·방식·배수 차이를 통째로 숨긴다.\
이 노트가 더하는 것: 값을 못 박기 전에 **불변식(원금 합·마지막 잔액, 여기에 잔액 단조 감소)을 먼저 테스트로 적는다.** 그러면 아홉 조합을 하나하나 손계산하지 않아도 틀린 상환표가 걸린다.

### 문제 — 이 챕터가 시키는 것

주어진 규칙은 나눗셈 한 줄과 남는 4원이 전부다(원본 README 그대로).

```text
  1,000,000 원을 12 개월로 나누면 한 달에 83,333.33... 원
  원 단위로 끊으면 12 번 합해도 999,996 원이라 4 원이 남는다

    마지막에 몰기   83,333 x 11,  83,337
    처음에 몰기     83,337,  83,333 x 11
    나눠서          83,334 x 4,   83,333 x 8
```

**"셋 다 합이 정확히 1,000,000 원이다. 갈리는 것은 어느 달에 몇 원을 더 내느냐다.\
그리고 그 4 원이 총 이자까지 바꾼다."**

그리고 "연 12 퍼센트"라는 말에 이자를 **어디에 매기는지**가 안 들어 있다(원본 javadoc 그대로).

```text
  원리금 균등   매달 내는 돈이 같고 이자가 점점 준다
  원금 균등     매달 갚는 원금이 같고 내는 돈이 점점 준다
  애드온        원금 전체에 기간을 곱해 이자를 한 번에 매긴다
```

**같은 "연 12 퍼센트"인데 애드온은 부담이 1.81 배다.**

과제(원본 README "채울 것"): `src/main/java/com/domain/installment/InstallmentPlan.java` 의 **TODO 1~3**. `Loan` 은 계약이라 다 주어져 있다.

| TODO | 함수 | 시키는 것 |
|---|---|---|
| 1 | `split(total, weights, residue)` | 총액을 가중치대로 나누되 합이 정확히 총액. **몫은 내림**, 남은 것은 나머지 규칙대로 |
| 2 | `equalPaymentWeights(loan)` | 원리금 균등의 회차별 원금 비율. **이자율 0이면 0으로 나누기** — 균등으로 갈아탄다 |
| 3 | `schedule(loan, method, residue)` | 상환표. 원금을 먼저 나누고 **이자는 그 원금이 만든 잔액에서** — 애드온만 예외 |

테스트가 못 박은 계약:

- 세 나머지 규칙의 회차별 원금: `83,333×11 + 83,337` / `83,337 + 83,333×11` / `83,334×4 + 83,333×8` — 셋 다 합이 1,000,000.
- 원리금 균등 총 이자: 마지막 몰기 **66,186** / 처음 몰기 **66,185** — 먼저 갚으면 준다.
- 원금 균등 총 이자는 세 규칙 다 **65,000** — 나머지가 이자를 안 바꾼다.
- 세 방식의 총 이자: 65,000 / 66,186 / **120,000**(애드온 = 1.81배).
- 납입액 폭: 원리금 균등 **8원**, 원금 균등 **9,163원**.
- 아홉 조합(방식 3 × 나머지 3) 전부에서 **원금의 합 == 1,000,000**, **마지막 잔액 == 0**, **잔액이 한 번도 안 는다**.
- 무이자면 세 방식이 같은 상환표를 낸다.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 장애 시나리오와 대처

**1. "왜 마지막 달만 금액이 다른가요"가 매달 들어온다**

- 현상: 무이자 12개월(100만원) 할부에서 11회차까지 83,333원이다가 12회차만 83,337원이다.
- 보이는 형태: 반복되는 CS 문의. 금액은 맞다.
- 원인: `Residue.LAST`를 골랐는데 안내문에는 "12개월 균등"이라고만 적혀 있다.
- 대처: 안내문에 "원 단위 나머지는 마지막 회차에 합산"을 명시하거나 `SPREAD`로 바꾼다. 무이자면 규칙을 바꿔도 이자는 0 그대로다. 이자가 있으면 규칙 변경이 총 이자를 움직일 수 있다 — impl로 다시 계산하면 100만원·12%·12개월 원리금 균등에서 LAST 66,186 · SPREAD 66,186 · FIRST 66,185다. 그래서 규칙 변경은 기존 계약에 소급하지 않는다.

**2. 무이자 할부 결제가 서버 오류로 실패한다**

- 현상: 이자율 0%인 할부만 상환표 생성에서 500 오류가 난다.
- 보이는 형태: `ArithmeticException`(이 식은 `r = 0`이면 0÷0이라 `BigDecimal.divide`가 "Division undefined"를 던진다). 이자 있는 할부는 정상.
- 원인: 원리금 균등 납입액 공식의 분모 `(1+r)^n − 1`이 `r = 0`에서 0이다. 개발 예제는 대개 이자가 있어 이 갈래가 안 돌았다.
- 대처: `interestFree()`면 균등 가중치로 분기하고, 무이자 상환표가 세 방식에서 같음을 테스트로 못 박는다.

**3. 3개월 낸 고객이 "남은 원금이 왜 이렇게 많나"고 묻는다**

- 현상: 원리금 균등 12개월 중 3회 납부 후 중도 상환 잔액이 예상보다 크다.
- 보이는 형태: 고객 계산(1,000,000 − 88,848×3 = 733,456)과 우리 잔액(761,082)이 다르다 — 100만원·연 12%·12개월·LAST 기준 impl 재계산. 나머지 규칙에 따라 몇 원 다르다(SPREAD 761,079).
- 원인: 원리금 균등은 초기 회차의 원금이 작다(1회 원금 78,848 + 이자 10,000, LAST 기준) — 낸 돈의 일부가 이자다. 화면이 납입액만 보여주고 잔액을 안 보여줬다.
- 대처: 상환표에 회차별 원금·이자·`balanceAfter`를 함께 보여주고, 중도 상환액은 그 `balanceAfter`를 근거로 계산한다(정답 7번 참고).

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 몫을 반올림으로 구한다 | 합이 총액을 넘쳐 나머지가 음수 → 내림(FLOOR)으로 구해 나머지를 항상 0 이상으로 |
| 이자율 0을 안 챙긴다 | 원리금 균등 공식이 0으로 나누기 — 무이자는 균등 가중치로 분기 |
| 잔액을 안 줄이고 이자를 매긴다 | 다 갚은 원금에도 이자가 붙는다 — 이자는 매 회차 갱신된 잔액에서 |
| 나누어떨어지는 금액으로만 테스트 | 나머지 규칙 셋이 전부 같아져 아무것도 검증 안 된다 (1,200,000÷12) |
| 마지막 잔액 확인 생략 | 잔액이 몇 원 남아도 아무도 안 본다 — "다 갚았는데 빚이 남는" 조용한 결함 |
| 한 달짜리 할부 | 첫 회차 = 마지막 회차라 세 나머지 규칙이 같은 자리를 가리킨다 — 그래도 돌아야 한다 |

> ⚠ 정정(2026-09-28): 표의 "갱신된 잔액"은 **당회 상환 전 잔액**(= 전회까지 갚고 남은 원금)이다. 이자를 먼저 매기고 그다음 당회 원금을 뺀다(impl `InstallmentPlan.java:199-206`, 3-answer의 "맞는 순서" 그림).

변종 검증: 변종 15개 전부 잡혔다. 비결은 나머지 규칙 셋을 **회차별 원금 목록으로 통째로 못 박고**, 아홉 조합(방식 3×나머지 3) 전부에서 `원금 합 == 원금`·`마지막 잔액 == 0`을 2,000건씩 확인한 것. 잔액을 안 줄이는 변종이 세 자리에 있었는데 셋 다 다른 테스트에서 잡혔다.

## 핵심 문장

- 정수 나눗셈의 나머지는 버그가 아니라 **정책이다** — 어느 회차에 얹을지는 enum으로 드러내고, 몫은 내림으로 구해 나머지가 음수가 되지 않게 한다.
- 나머지 몇 원이 "표시 문제"로 끝나지 않는다 — **먼저 갚은 원금은 이후 모든 달의 이자를 줄이므로**, 나머지 규칙이 실제로 돈(총 이자)을 움직인다.
- 같은 "연 12%"라도 **이자를 잔액에 매기느냐(균등 방식) 원금 전체에 매기느냐(애드온)** 로 부담이 1.81배 갈린다 — 애드온은 이미 갚은 원금에도 이자를 문다.
- 무이자·나누어떨어지는 금액·짧은 기간 — **예제로 만들기 쉬운 입력일수록 갈림이 숨는다.** 시험은 일부러 안 나누어떨어지고 이자 있는 긴 할부로.
- 상환표의 불변식은 세 개다: **원금의 합 == 원금, 마지막 잔액 == 0, 잔액은 절대 안 는다** — 방식·나머지의 아홉 조합 전부에서 지켜져야 한다.

### 용어 풀이

- **원리금 균등(EQUAL_PAYMENT)**: 매달 내는 돈(원금+이자)이 같게 맞춘 방식. 초반엔 이자 비중이 크고 갈수록 원금 비중이 는다.
- **원금 균등(EQUAL_PRINCIPAL)**: 매달 갚는 원금이 같은 방식. 내는 돈이 점점 준다(첫 달이 제일 크다).
- **애드온(ADD_ON)**: 원금 전체 × 이율 × 개월로 이자를 한 번에 매기는 방식. 갚아나감을 안 보므로 같은 이율에 부담이 훨씬 크다.
- **나머지(residue)**: 총액을 회차로 나눌 때 원 단위에서 남는 몇 원. 어디 얹을지가 규칙(LAST/FIRST/SPREAD).
- **내림(FLOOR)/반올림(HALF_UP)**: 몫을 내림으로 구하면 합이 총액을 안 넘어 나머지가 항상 0 이상 — 그래서 내림이 안전.
- **월 이자율**: 연 이자율 ÷ 12 (관행·법정 표시 방식). 복리 환산 `(1+연이율)^(1/12)-1` 은 조금 작지만 여기선 안 쓴다.
> ⚠ 정정(2026-09-28): "법정 표시 방식"은 원본 `Loan.java:238` 주석의 표현으로, 어느 나라·어느 법의 규정인지 근거가 없다 [?]. 확실한 것은 "이 모델은 **명목** 연이율을 12로 나눈 월이율을 쓴다"까지다. 실효 연이율에서 월 복리율을 구하면 `(1+연이율)^(1/12)−1`이다.
- **잔액(balanceAfter)**: 그 회차를 갚고 남은 원금. 다음 달 이자의 근거.
- **중도 상환**: 만기 전에 남은 원금을 미리 갚는 것. 원리금 균등은 초기 원금이 적어 초기 중도 상환 시 잔액이 크다.
- **불변식(invariant)**: 어떤 조합에서도 깨지면 안 되는 성질. 여기선 "원금 합 == 원금, 마지막 잔액 == 0, 잔액 단조 감소".
- **폭(spread)**: 제일 많이 내는 달과 제일 적게 내는 달의 차이. 반올림이 만든 폭(8원)과 규칙이 만든 폭(9,163원)은 성격이 다르다.
