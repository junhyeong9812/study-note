### A. 과제

#### 0. 나눗셈 한 줄이 안 말해주는 것

- 안 말해주는 결정 둘: **① 나누고 남은 4원을 어디에 두나(`Residue`) ② 이자를 어디에 매기나(`Method`).**
- 세 규칙의 합이 다 1,000,000인 이유: **남은 것을 버리지 않고 반드시 어딘가에 얹기 때문**이다.

```text
 83,333 × 12 = 999,996     ← 그냥 끊으면 4원이 사라진다
 + 4원을 어딘가에 얹는다   → 1,000,000     ← 어디에 얹든 합은 같다
```

> **나머지(residue)** — 총액을 회차 수로 나눌 때 원 단위에서 남는 몇 원.\
> 예: 1,000,000 ÷ 12 는 83,333 씩이고 4원이 남는다. 이 4원이 어디로 갈지는 나눗셈이 안 정해준다.

- 갈리는 것: **어느 달에 몇 원을 더 내느냐.** 그리고 그것이 안내문에 찍힌다.
- 4원이 총 이자를 바꾸는 이유: **이자는 남은 원금(잔액)에 붙기 때문**이다.\
  처음에 4원을 더 갚으면 **그 뒤 열한 달의 잔액이 4원씩 작아지고**, 그만큼 이자가 조금씩 준다.

```text
 처음에 몰기   1회에 83,337 갚음  →  이후 11달의 잔액이 4원씩 작다  →  총 이자 66,185
 마지막에 몰기 1회에 83,333 갚음  →  이후 11달의 잔액이 4원씩 크다  →  총 이자 66,186
                                                              1원 차이
```

- 마지막 달에 몰면 안내문 문제: **마지막 회차만 금액이 다르다.**\
  "왜 마지막 달만 금액이 다른가요"라는 문의가 거기서 나온다(원본 javadoc 원문).
- "연 12 퍼센트"에 안 들어 있는 것: **그 12퍼센트를 남은 빚에 매기나 원금 전체에 매기나.**\
  원리금 균등·원금 균등은 잔액에 매기고, 애드온은 원금 전체에 매긴다.

#### 1. TODO 1 — split

정답 코드 (impl/InstallmentPlan.java):

```java
long[] parts = new long[weights.length];
long assigned = 0;
for (int i = 0; i < weights.length; i++) {
    parts[i] = BigDecimal.valueOf(total)
            .multiply(weights[i], Loan.CONTEXT)
            .divide(weightSum, 0, RoundingMode.FLOOR)
            .longValueExact();
    assigned += parts[i];
}

long left = total - assigned;
switch (residue) {
    case LAST -> parts[parts.length - 1] += left;
    case FIRST -> parts[0] += left;
    case SPREAD -> {
        for (long i = 0; i < left; i++) {
            parts[(int) (i % parts.length)]++;
        }
    }
}
```

- **내림(FLOOR)** 으로 구한다.
- 나머지가 언제나 0 이상인 이유: 내림은 **각 몫을 실제 값보다 작거나 같게** 만든다.\
  작거나 같은 값을 다 더하면 합도 총액보다 작거나 같다 → `total - assigned >= 0`.

```text
 내림     83,333 × 12 = 999,996  ≤ 1,000,000   나머지 +4  →  "더해준다"
 반올림   83,333 × 12 = 999,996                나머지 +4  (이 예는 같다)
          그런데 83,333.5 처럼 위로 올라가는 자리가 많으면
          합이 1,000,000 을 넘어서 나머지가 음수  →  "빼야 한다"
```

> **내림(FLOOR)** — 소수점을 버리고 항상 작은 쪽 정수로 내리는 것.\
> 예: 83,333.33 도 83,333.99 도 내리면 83,333 이다. 그래서 합이 절대 총액을 안 넘는다.

- 반올림이면: **어느 회차에서 돈을 빼야 한다.**
- 음수 나머지가 깨는 불변식: 빼다 보면 **원금이 0인 회차**가 생기고, 그러면 그달에 잔액이 안 준다.\
  테스트가 못 박은 "**잔액이 한 번도 안 늘어난다**"와 "`principal() > 0`"이 거기서 깨진다.
- SPREAD 에서 남은 금액이 회차 수보다 많으면: `i % parts.length` 가 **한 바퀴 돌아 처음으로 돌아온다.**\
  1회차부터 1원씩 얹다가 마지막을 지나면 다시 1회차로 — 앞쪽이 한 번 더 받는다.
- 원금과 이자에 같은 함수가 쓰이는 이유: 둘 다 **"총액 하나를 회차별 가중치대로 나누되 합을 정확히 맞춘다"** 라는 같은 문제다.\
  원금은 방식별 가중치로, 애드온 이자는 균등 가중치로 부른다.

#### 2. TODO 2 — equalPaymentWeights

정답 코드:

```java
if (loan.interestFree()) {
    return equalWeights(loan.months());
}
BigDecimal rate = loan.monthlyRate();
BigDecimal onePlusR = BigDecimal.ONE.add(rate);
BigDecimal growth = onePlusR.pow(loan.months(), Loan.CONTEXT);

BigDecimal payment = BigDecimal.valueOf(loan.principal())
        .multiply(rate, Loan.CONTEXT)
        .multiply(growth, Loan.CONTEXT)
        .divide(growth.subtract(BigDecimal.ONE), Loan.CONTEXT);

BigDecimal[] weights = new BigDecimal[loan.months()];
BigDecimal balance = BigDecimal.valueOf(loan.principal());
for (int i = 0; i < loan.months(); i++) {
    BigDecimal interest = balance.multiply(rate, Loan.CONTEXT);
    BigDecimal principal = payment.subtract(interest);
    weights[i] = principal;
    balance = balance.subtract(principal);
}
```

- 이자율 0이면 분모가 0인 이유:

```text
 분모 = (1 + r)^n - 1
 r = 0  →  (1 + 0)^12 - 1  =  1 - 1  =  0     ← 0 으로 나누기
```

- 무이자 할부는 **흔하다.** 카드사 "12개월 무이자"가 그것이다 — 드문 예외가 아니라 일상 케이스다.
- 균등으로 갈아타도 되는 이유: 이자가 0이면 **매달 내는 돈이 곧 매달 갚는 원금**이다.\
  "내는 돈이 같다"와 "갚는 원금이 같다"가 같은 말이 된다 → 세 방식이 통째로 같아진다.
- 매달 내는 돈이 같은데 원금이 느는 이유: **내는 돈 = 원금 + 이자**인데, 갚을수록 잔액이 줄어 **이자가 준다.**\
  합계가 고정이므로 이자가 준 만큼 원금이 는다.

```text
 1 회   이자 10,000  원금 78,848   합 88,848
 ...    이자 줄고    원금 늘고     합 그대로
 12 회  이자 900대   원금 88,000대 합 88,856
                                    폭은 8원(반올림 탓)뿐이다
```

- 돌려주는 것은 **가중치(비율)** 다 — 반올림 안 한 `BigDecimal` 금액을 그대로 가중치로 쓴다.
- 가중치로 돌려주면 편한 것: **반올림과 나머지 처리가 `split` 한 곳에 모인다.**\
  여기서 미리 원 단위로 끊으면 반올림이 두 군데로 흩어지고, "합이 정확히 원금" 을 지킬 책임도 둘로 갈린다.
- 1회차 원금 78,848원의 뜻: 원리금 균등은 **초반에 원금을 조금밖에 안 갚는다.**\
  그래서 **초기에 중도 상환하면 남은 원금이 생각보다 많다**(테스트 주석 원문).

#### 3. TODO 3 — schedule

정답 코드:

```java
BigDecimal[] weights = method == Method.EQUAL_PAYMENT
        ? equalPaymentWeights(loan)
        : equalWeights(loan.months());
long[] principals = split(loan.principal(), weights, residue);

long[] interests;
if (method == Method.ADD_ON) {
    BigDecimal total = BigDecimal.valueOf(loan.principal())
            .multiply(loan.monthlyRate(), Loan.CONTEXT)
            .multiply(BigDecimal.valueOf(loan.months()), Loan.CONTEXT);
    interests = split(total.setScale(0, RoundingMode.HALF_UP).longValueExact(),
            equalWeights(loan.months()), residue);
} else {
    interests = new long[loan.months()];
    long balance = loan.principal();
    for (int i = 0; i < loan.months(); i++) {
        interests[i] = BigDecimal.valueOf(balance)
                .multiply(loan.monthlyRate(), Loan.CONTEXT)
                .setScale(0, RoundingMode.HALF_UP)
                .longValueExact();
        balance -= principals[i];
    }
}
```

- 원금이 먼저인 이유: **이자가 원금의 결과**이기 때문이다.\
  "이자는 남은 빚에 붙는다"는 도메인 문장을 그대로 순서로 옮겼다 — 원금을 정해야 잔액이 정해지고, 잔액이 정해져야 이자가 나온다.
- 애드온만 따로 나누는 이유: **애드온은 잔액을 안 본다.**\
  잔액과 무관하니 "잔액 × 이율" 루프를 탈 수가 없다 — 총 이자를 먼저 구하고 회차로 균등 분할한다.
- 애드온 총 이자: **`원금 × 월이율 × 개월 수`**.

```text
 1,000,000 × 0.01 × 12 = 120,000 원

 잔액 방식이면  1달차 10,000 · 2달차 9,200 · ... 처럼 줄어서 66,186
 애드온이면     12달 내내 원금 전체 1,000,000 에 이자를 문다  →  120,000
                                              1.81 배
```

- 잔액을 안 줄이면: **다 갚은 원금에도 이자가 붙는다.**\
  12회차에도 1,000,000원에 대한 이자를 물어 사실상 애드온이 된다.
- 잔액을 빼는 시점이 중요한 이유: **그달 이자를 계산한 뒤에 빼야 한다.**\
  먼저 빼면 1회차부터 이미 한 달치를 갚은 잔액에 이자를 매겨 **이자가 한 회차씩 밀린다.**

```text
 맞는 순서   이자[i] = 잔액 × 이율   →   잔액 -= 원금[i]
 틀린 순서   잔액 -= 원금[i]         →   이자[i] = 잔액 × 이율   ← 첫 달 이자가 10,000 이 아니게 된다
```

- 불변식 셋: **① 원금의 합 == 원금 ② 마지막 회차의 잔액 == 0 ③ 잔액이 한 번도 안 늘어난다**(그리고 회차마다 `principal > 0`).
- 확인해야 하는 조합: **아홉 개**(방식 3 × 나머지 3). 측정 테스트는 거기에 2,000건씩 더해 18,000건을 검산한다.

> **불변식(invariant)** — 어떤 입력·어떤 설정에서도 반드시 참이어야 하는 성질.\
> 예: "마지막 잔액은 0" 은 방식이 무엇이든 나머지를 어디에 두든 깨지면 안 된다. 깨지면 다 갚았는데 빚이 남는다.

### B. 개념

#### 4. 함정 (README)

- 넷: ① **몫을 반올림으로 구하는 것**(합이 넘치면 나머지가 음수가 되어 어느 회차에서 돈을 빼야 한다 — 내림이면 나머지가 언제나 0 이상) ② **이자율 0을 안 챙기는 것**(원리금 균등 식이 0으로 나누기가 되고, 무이자는 흔하다) ③ **애드온을 "이자율이 같으니 비슷하겠지"로 보는 것**(1.8배다) ④ **잔액을 안 줄이고 이자를 매기는 것**(다 갚은 원금에도 이자가 붙는다).
- ③이 함정인 이유: 화면에는 **똑같이 "연 12%"** 라고 적힌다.\
  이율이 같으니 총액도 비슷할 거라고 **이름만 보고 넘기게 된다** — 실제로는 66,186원과 120,000원이다.
- 마지막 잔액이 0이 아닌 상환표가 조용한 이유: **그 잔액은 대개 몇 원**이라 아무도 안 본다(테스트 주석 원문).\
  상환표는 정상적으로 12줄 다 찍히고, 합계도 거의 맞고, 고객은 마지막 달까지 다 냈다 — 그런데 시스템에는 빚이 남아 있다.

#### 5. 측정 — 답이 갈리는 건수

- 할부 5,000건 중 첫 회차 금액이 갈린 건: **3,517 / 5,000.**
- 안 갈린 건: **1,483 / 5,000** — 원금이 개월 수로 **나누어떨어져서** 남는 것이 없다(나머지 0).
- 첫 회차 폭: 평균 **6.14원**, 최대 **32원**.
- 예제에서 안 보이는 이유: **사람은 예제를 만들 때 나누어떨어지는 금액을 고른다.**\
  1,200,000 ÷ 12 = 100,000 처럼 깔끔한 수를 쓰면 세 규칙이 전부 같은 답을 낸다.
- 나머지 규칙 셋의 총 이자(원리금 균등 5,000건):

```text
 처음에 몰기   1,144,524,816
 나눠서        1,144,527,151
 마지막에 몰기 1,144,534,418

 차이  1,144,534,418 - 1,144,524,816 = 9,602 원
```

- 비율로는 11억 중 9,602원 — **약 0.0008 %. 없는 셈이다.**
- 그런데 중요한 이유: **방향이 언제나 같다**(처음 < 나눠서 < 마지막).\
  무작위 오차라면 방향이 섞여야 하는데 안 섞인다 — 즉 나머지 규칙이 **실제로 돈을 한쪽으로 움직인다.**
- 세 방식의 총 이자(5,000건):

```text
 원금 균등     1,087,450,425
 원리금 균등   1,144,534,418
 애드온        2,044,957,850     원리금 균등의 1.79 배
```

- 방식이 갈린 건 **4,836 / 5,000**. 안 갈린 **164건은 이자율이 0인 경우**다 — 이자가 없으면 매기는 방식도 없다.
- 기간별 애드온 배수(1,000,000원 연 12%):

```text
 개월   원리금 균등   원금 균등   애드온    배수
   3        20,067      20,000    30,000   1.49
   6        35,291      35,000    60,000   1.70
  12        66,186      65,000   120,000   1.81
  24       129,765     125,000   240,000   1.85
  36       195,718     185,005   360,000   1.84
```

- 기간이 길수록 배수가 커지는 이유: 애드온 이자는 **기간에 정비례**해서 곧게 늘지만, 잔액 방식은 **잔액이 줄어드는 만큼 덜 는다.**\
  기간이 길수록 "이미 갚은 원금"이 쌓이고, 애드온은 그 전부에 계속 이자를 문다.\
  (36개월에서 1.85 → 1.84 로 살짝 꺾이는 것은 원금 균등 쪽 반올림 탓으로 보인다 — 원본에 설명 없음, 내 추론.)
- 짧은 할부로 시험하면: **방식 차이가 작아 보인다**(3개월 1.49배).\
  그리고 **예제는 대개 3개월이나 6개월이다.**
- 폭 8원과 9,163원의 차이: **8원은 반올림이 만든 것**(고칠 수 있으면 고쳐야 할 잡티)이고 **9,163원은 규칙 그 자체**(원금 균등이 원래 그런 방식).\
  그래서 "매달 얼마 내나요"라는 질문에 **한쪽은 답할 수 있고 한쪽은 못 한다.**
- 무이자가 위험한 이유: 세 방식이 **통째로 같은 상환표**를 낸다.\
  그리고 **무이자 할부는 예제로 만들기 제일 쉽다** — 이자 계산이 없어 손으로 검산하기 편하니까.\
  그 예제로는 이 박스가 다루는 갈림의 대부분이 안 돈다.

> **가려진 갈림(masking)** — 시험 입력이 쉬운 쪽에 쏠려서, 실제로는 갈리는 결정이 안 갈리는 것처럼 보이는 것.\
> 예: 무이자 + 나누어떨어지는 금액 + 3개월로 시험하면 방식 3 × 나머지 3 = 아홉 조합이 거의 한 답으로 뭉친다.

#### 6. 변종 검증

- 비결: **나머지 규칙 셋을 회차별 원금 목록으로 통째로 못 박고**, 아홉 조합 전부에서 `원금의 합 == 원금` 과 `마지막 잔액 == 0` 을 2,000건씩 확인했다.\
  그래서 변종 15개가 전부 잡혀 **고칠 것이 없었다.**
- "통째로 못 박는다"의 뜻: 합계나 첫 회차만 보는 게 아니라 **12개 원금을 목록 그대로** 비교한다는 뜻이다.

```text
 합계만 본다     1,000,000 == 1,000,000  →  나머지를 어디에 뒀는지 안 보인다
 목록을 본다     [83,333 × 11, 83,337]   →  어느 회차에 4원이 갔는지까지 고정된다
```

- 잔액을 안 줄이는 변종이 셋 다 잡힌 이유: 그 결함이 **서로 다른 세 성질을 동시에 깬다.**\
  총 이자가 커지고(방식 비교 테스트), 잔액이 안 줄고(단조 감소 테스트), 마지막 잔액이 0이 아니게 된다(불변식 테스트).\
  성질을 여러 각도로 걸어두면 한 결함이 여러 그물에 걸린다.

#### 7. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 중도 상환의 남은 이자: **잔액 방식(원리금·원금 균등)은 자연스럽다** — 아직 안 지나간 회차의 이자는 애초에 "그때 잔액에 붙을 예정"이었을 뿐 아직 발생하지 않았다. 남은 잔액만 갚으면 그 이자가 통째로 사라진다.\
  **애드온이 문제다** — 이자를 앞에서 한 번에 확정했으니 "이미 다 낸 것"처럼 보인다. 그래서 실제 금융에서는 78분법 같은 별도 규칙으로 되돌려주고, 그 규칙이 또 하나의 결정이 된다.\
  이 코드에는 중도 상환 개념이 아예 없다 — `schedule` 은 끝까지 가는 표만 만든다. (원본에 근거 없음 — 내 추론)
- 연체 이자: 이 코드에는 연체가 없다. 붙이려면 **"연체 원금"을 잔액과 별도로 들고 다녀야** 한다 — 잔액에 합치면 연체 이율(보통 더 높다)을 따로 못 매긴다.\
  즉 `Installment` 에 회차 상태(정상/연체)가 생기고, 상환표가 **미리 다 만드는 표**에서 **매달 갱신되는 표**로 성격이 바뀐다. (원본에 근거 없음 — 내 추론)
- 마지막 회차만 다른 것의 안내: 숨기지 말고 **표에 그대로 적는 쪽**이 맞다 — "1~11회 83,333원, 12회 83,337원".\
  숨기면 마지막 달에 문의가 오고, 그때는 이미 신뢰 문제가 된다.\
  `Residue.SPREAD` 를 고르면 앞 네 달이 1원씩 많아져 "마지막만 다르다"는 없어지지만, 대신 **네 달이 다른** 표가 된다 — 안내가 더 쉬워지는 건 아니다. (원본에 근거 없음 — 내 추론)
- 실질 연이율: **잔액 방식으로 환산해야 한다.** 애드온의 "연 12%"는 실질이 아니다 — 같은 12%로 표기해도 실제 부담이 1.81배다.\
  실질을 구하려면 "이 상환표의 현금 흐름을 같게 만드는 잔액 방식 이율"을 역산해야 하고, 그 값은 이 코드의 `monthlyRate` 와 다르다.\
  `Loan` javadoc 이 "월 이자율을 연 이자율을 12로 나눠 쓴다. 그것이 관행이고 법정 표시 방식"이라고 한 것도 같은 결의 이야기다 — **표시용 이율과 실질 이율은 원래 다르다.** (원본에 근거 없음 — 내 추론)

#### 8. 연결

- "나누어떨어지지 않는 금액을 여럿에 나누기": **06-tax의 할인 배분**과 같은 자리다.\
  거기서는 세 구분에, 여기서는 열두 회차에 나눈다 — 문제 모양이 같다.
- 06-tax 와의 비교: **같은 것** — 합이 총액과 정확히 맞아야 한다는 요구.\
  **다른 것** — 06-tax 는 **마지막 몫을 빼기로 구해** 나머지를 한 곳(영세율)에 자동으로 몰았고, 여기는 **나머지를 어디에 둘지가 정책**이라 enum 으로 올렸다.\
  06-tax 는 어디에 몰아도 부가세가 안 바뀌어서 숨길 수 있었고, 여기는 **총 이자가 바뀌어서** 숨길 수 없다.
- `Residue` 와 `Method` 의 차이: `Residue` 는 **몇 원짜리 배분 규칙**이라 총액을 안 바꾼다 — 총 이자를 1원(5,000건에 9,602원) 움직일 뿐이다.\
  `Method` 는 **계약의 본체**라 총 이자를 1.81배 바꾼다.\
  둘 다 enum 이지만 무게가 다르다 — 06-tax 의 "작은 것(배송비)을 오래 논의하고 큰 것(할인 배분)을 안 정한다"와 같은 교훈이 여기도 있다.
