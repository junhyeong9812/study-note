### A. 과제

#### 0. 규칙 네 줄이 안 말해주는 것

- 안 말해주는 자리 셋:

```text
 안 말해준 것            가능한 읽기
 "가산 50 %" 가 겹치면  →  더하나 / 곱하나 / 큰 것만 주나
 "1 일 8 시간 또는 주 40 시간" → 하루로 재나 / 주로 재나 / 둘 중 하나라도
 자정을 넘는 근무        →  시작한 날인가 끝난 날인가
```

- 연장이면서 야간인 한 시간(시급 10,000원): 답이 **셋**이다.

```text
 더한다   10,000 × (1 + 0.5 + 0.5) = 20,000   ← 근로기준법이 이쪽
 곱한다   10,000 × 1.5 × 1.5       = 22,500
 큰 것만  10,000 × (1 + 0.5)       = 15,000
                    15,000 과 22,500 은 1.5 배 차이
```

- "또는"의 뜻: **합집합이다.** `EITHER` 는 하루를 넘겼거나 주를 넘겼으면 연장으로 본다.\
  그런데 `DAILY` 만·`WEEKLY` 만 보는 읽기도 실제로 쓰인다 — 그래서 3택 enum이다.
- 자정을 넘는 근무: 이 코드는 **시작한 날**로 센다(`Shift.date` = 시작한 날).\
  이 선택이 하루 누적(=연장 판정)과 휴일 여부를 **둘 다** 바꾼다.
- `1.5` 로 적기 vs `0.5` 로 적기: **1.5로 적으면 "겹치면?"이라는 질문 자체가 안 떠오른다.**\
  1.5짜리 배수가 둘이면 손이 자연스럽게 곱하기로 간다. 0.5짜리 가산율이 둘이면 "이걸 더해? 곱해?"가 질문이 된다.

> **가산율(premium rate)** — 기본 시급 위에 **더 얹는 비율**. 배수가 아니다.\
> 예: 야간 가산율 0.5 는 "시급의 50%를 더 준다"는 뜻이고, 배수로 바꾸면 1 + 0.5 = 1.5 다.

- "데이터 표현이 곧 설계다"인 이유: 같은 사실을 **어떤 숫자로 저장하느냐가 그다음 연산을 유도한다.**\
  1.5(배수)는 곱셈을 부르고, 0.5(가산율)는 덧셈을 부른다. 저장 형식이 이미 한쪽 편을 들고 있다.
- enum으로 올리면: **세 해석을 같은 코드로 돌려 답이 갈리는 건수를 셀 수 있다.**\
  그리고 부르는 쪽이 하나를 고르지 않으면 컴파일이 안 되므로, **결정을 미룰 수가 없다.**

#### 1. TODO 1 — calculate

정답 코드 (impl/Payroll.java, 핵심만):

```java
List<Shift> sorted = new ArrayList<>(shifts);
sorted.sort(Comparator.comparing(Shift::startedAt).thenComparing(Shift::endedAt));

for (Shift shift : sorted) {
    LocalDateTime at = shift.startedAt();
    for (int i = 0; i < shift.minutes(); i++, at = at.plusMinutes(1)) {
        int daily = dailyWorked.merge(shift.date(), 1, Integer::sum);
        weeklyWorked++;
        worked++;

        boolean overDaily = daily > rule.dailyRegularMinutes();
        boolean isOvertime = overtime(daily, weeklyWorked, basis);
        boolean isNight = rule.night(at.toLocalTime());

        List<BigDecimal> rates = new ArrayList<>();
        if (shift.holiday()) {
            rates.add(overDaily ? rule.holidayOverRate() : rule.holidayRate());
            holiday++;
        } else if (isOvertime) {
            rates.add(rule.overtimeRate());
        }
        if (isNight) { rates.add(rule.nightRate()); night++; }
        if (isOvertime) { overtime++; }
        if (rates.size() > 1) { stacked++; }

        weightedMinutes = weightedMinutes.add(multiplier(rates, premiumRule));
    }
}
long total = weightedMinutes.multiply(BigDecimal.valueOf(rule.hourlyWage()))
        .divide(BigDecimal.valueOf(60), 0, RoundingMode.HALF_UP).longValueExact();
```

- 1분씩 훑는 이유: **규칙의 경계가 전부 분 단위에 있다.**\
  야간은 22:00에 시작하고, 연장은 481분째에 시작한다 — 둘 다 시간 단위 칸 안에서 갈린다.
- 22:30 시작을 시간 단위로 세면:

```text
 실제      22:30 ~ 23:00  야간 30 분
 내림 처리  22 시 칸을 "낮"으로 봄  →  야간 0 분   (30 분이 사라짐)
 올림 처리  22 시 칸을 통째 야간    →  야간 60 분  (없던 30 분이 생김)
```

- 정렬을 안 하면: **DB 조회 순서가 급여를 바꾼다.**\
  연장 판정이 "지금까지 몇 분 일했나"라는 누적값을 보기 때문에, 어느 근무를 먼저 세느냐가 어느 분이 연장이 되는지를 정한다.

> **누적 판정(cumulative)** — 이 한 건만 봐서는 답이 안 나오고, 앞에 무엇이 있었는지를 알아야 답이 나오는 판정.\
> 예: 똑같은 "화요일 9시 정각의 1분"이 그 주에 이미 40시간을 채웠으면 연장이고, 안 채웠으면 아니다.

- `startedAt` 하나로 부족하다: 시작이 같은 근무가 둘이면 순서가 안 정해져 **결과가 실행마다 달라질 수 있다.**\
  그래서 `.thenComparing(Shift::endedAt)` 로 **전순서(total order)** 를 만든다.

> **안정된 순서(total order)** — 어떤 두 개를 집어도 앞뒤가 반드시 정해지는 정렬 기준.\
> 예: "시작 시각"만 쓰면 9시 시작 근무 둘의 앞뒤가 안 정해지지만, "시작 → 끝" 순으로 보면 정해진다.

- 하루는 `Map`, 주는 `int` 인 이유: **하루 누적은 날짜마다 따로 세야 하고**(한 주에 날이 여럿), 주 누적은 이 계산 전체가 한 주라서 하나면 된다.
- `else if` 가 적어둔 도메인 규칙: **휴일 가산이 연장 가산을 대신한다.**\
  휴일 8시간 초과분은 이미 가산 100%를 받으므로, 거기에 연장 50%를 또 붙이지 않는다.
- 휴일 초과 판정에 `overDaily` 를 쓰는 이유: 규칙 문장이 **"휴일 8시간 초과"** 이기 때문이다.\
  `isOvertime` 은 basis 에 따라 주 40시간으로도 참이 되는데, 그건 "휴일 8시간"이라는 문장과 다른 말이다.
- `stackedMinutes` 는 `rates.size() > 1` 일 때 올라간다 — **한 분에 가산이 2개 이상 붙은 분**의 수다.
- 반올림 vs 버림:

```text
 481 분을 주 기준(WEEKLY)으로 — 주 40 시간을 안 넘겼으니 연장 0
   481 × 10,000 / 60 = 80,166.666...
   HALF_UP  →  80,167
   버림     →  80,166        1 원 차이
```

- 딱 떨어지는 예제만 쓰면 안 잡히는 이유: 480분·540분·600분은 **60으로 나누어떨어져** 소수점이 안 생긴다.\
  버림으로 바꿔도 같은 값이 나오므로 테스트가 전부 통과한다(README "변종 검증" 둘째).

#### 2. TODO 2 — overtime

정답 코드:

```java
boolean overDaily = dailyWorked > rule.dailyRegularMinutes();
boolean overWeekly = weeklyWorked > rule.weeklyRegularMinutes();
return switch (basis) {
    case DAILY -> overDaily;
    case WEEKLY -> overWeekly;
    case EITHER -> overDaily || overWeekly;
};
```

- 부등호는 `>` 다. 인자가 **"이 분을 포함한 누적"** 이기 때문이다.

```text
 480 분째를 세는 순간  daily = 480   480 > 480 ? 거짓  →  아직 소정근로
 481 분째를 세는 순간  daily = 481   481 > 480 ? 참    →  여기부터 연장
```

- `>=` 로 틀리면: 하루 1분씩, 주 5분, **한 달 20분**이 더 붙는다.\
  금액으로는 한 달 20분 × 0.5 가산 × 시급/60 = 약 1,700원 — **명세서에서 아무도 못 알아본다.**
- 세 기준의 식은 위 코드 그대로다. `EITHER` 는 두 조건의 **OR**다.
- 하루 6시간씩 이레 (2,520분):

```text
 DAILY   하루 360 분씩이라 480 을 못 넘김  →  연장   0 분  →  420,000 원
 WEEKLY  2,520 중 2,400 초과분            →  연장 120 분  →  430,000 원
 EITHER  하루는 0, 주는 120 → 합집합      →  연장 120 분  →  430,000 원

 WEEKLY 손계산: 2,400 × 1.0 + 120 × 1.5 = 2,580 분어치
                2,580 × 10,000 / 60 = 430,000
```

- 하루 10시간씩 나흘 (2,400분) — **정반대로 뒤집힌다**:

```text
 DAILY   하루 600 분 중 120 분씩 초과 × 4일  →  연장 480 분  →  440,000 원
 WEEKLY  2,400 을 넘긴 것이 없다             →  연장   0 분  →  400,000 원

 DAILY 손계산: 1,920 × 1.0 + 480 × 1.5 = 2,640 분어치 → 440,000
```

- `EITHER` 가 언제나 가장 큰 이유: **합집합이라 DAILY 로 연장인 분도, WEEKLY 로 연장인 분도 전부 포함**한다.\
  연장으로 세는 분이 늘기만 하므로 총액이 줄어들 수 없다(`MeasurementTest` 가 `either >= daily && either >= weekly` 로 못 박았다).
- "어느 쪽이 유리한가"에 답이 없는 이유: **근무표가 정한다.** 위 두 예가 서로 반대다.\
  짧게 자주 일하면 주 기준이 유리하고, 몰아서 일하면 하루 기준이 유리하다.

#### 3. TODO 3 — multiplier

정답 코드:

```java
if (rates.isEmpty()) {
    return BigDecimal.ONE;
}
return switch (premiumRule) {
    case ADDITIVE -> { /* 1 + r1 + r2 + ... */ }
    case MULTIPLICATIVE -> { /* (1+r1) × (1+r2) × ... */ }
    case HIGHEST_ONLY -> { /* 1 + max(r) */ }
};
```

- 빈 목록에 1을 돌려주는 이유: 이 값은 **배수**이지 가산율이 아니다.\
  가산이 없는 분도 시급의 100%는 받는다 — 0을 주면 그 분이 공짜가 된다.
- 가산율 `[0.5, 0.5]` 손계산:

```text
 ADDITIVE        1 + 0.5 + 0.5      = 2.00
 MULTIPLICATIVE  1.5 × 1.5          = 2.25
 HIGHEST_ONLY    1 + max(0.5, 0.5)  = 1.50

 시급 10,000 · 한 시간이면  20,000 / 22,500 / 15,000
```

- 가산이 하나뿐이면 셋이 같은 이유:

```text
 rates = [0.5]
 ADDITIVE        1 + 0.5   = 1.5
 MULTIPLICATIVE  (1 + 0.5) = 1.5     ← 곱할 상대가 없다
 HIGHEST_ONLY    1 + 0.5   = 1.5     ← 고를 상대가 없다
```

  **그래서 겹치는 분이 없는 근무표에서는 세 규칙이 완전히 같은 답을 낸다.**
- `BigDecimal` 인 이유: `double` 은 0.5 처럼 2의 거듭제곱 분수는 정확해도, **누적 덧셈을 수백만 번 하면 오차가 쌓이고** 원 단위 반올림에서 1원이 튄다.\
  급여는 1원이 안 맞으면 합계와 항목의 합이 어긋난다.

> **BigDecimal** — 소수를 자릿수 그대로 정확히 다루는 자바 타입. 반올림 방식을 직접 고르게 강제한다.\
> 예: `0.1 + 0.2` 가 double 에서는 0.30000000000000004 지만, BigDecimal 에서는 정확히 0.3 이다.

- HIGHEST_ONLY 에서 `1 + max` 인 이유: **max 는 가산율끼리 고르고, 배수로 바꾸는 +1 은 마지막에 한 번**이다.\
  배수끼리 max 를 해도 여기서는 같은 값이 나오지만, 식의 뜻이 "가장 큰 가산 **하나만** 준다"이므로 가산율 단계에서 고르는 것이 맞다.

#### 4. 야간 구간 (`PayRule.night`)

- "22:00 이상 06:00 미만"이 빈 구간인 이유: **22시 이상이면서 동시에 6시 미만인 시각이 하루 안에 없다.**

```text
 00:00 ─────── 06:00 ─────────────── 22:00 ─────── 24:00
   |    야간     |        낮           |    야간      |

 AND 로 쓰면:  t ≥ 22:00  그리고  t < 06:00   →  아무 시각도 해당 없음
 OR 로 써야:   t ≥ 22:00  또는    t < 06:00   →  양쪽 끝이 다 잡힌다
```

- AND가 OR로 바뀌는 이유: 보통 구간은 **하나의 덩어리**지만, 자정을 넘는 구간은 수평선에서 **양 끝으로 잘린 두 덩어리**다.\
  "한 덩어리 안에 있나"는 AND, "두 덩어리 중 하나에 있나"는 OR다.
- 경계 판정 (테스트가 못 박은 값):

```text
 21:59  아니다
 22:00  야간      ← 시작은 포함
 00:00  야간
 05:59  야간
 06:00  아니다    ← 끝은 미포함
 12:00  아니다
```

- `PayRule` 안에 있는 뜻: **야간의 정의는 규칙(정책)에 속하지 계산 절차에 속하지 않는다.**\
  야간 시간대가 23~07시인 회사가 생겨도 `Payroll` 은 안 고친다 — `PayRule` 의 값만 바꾸면 된다.

#### 5. 자정을 넘는 근무 (`Shift`)

- 끝이 시작보다 빠르면 다음 날로 읽는 것이 포기한 것: **24시간을 넘는 근무를 표현할 수 없다.**\
  22:00 시작 30시간 근무는 이 타입으로 못 적는다. 대신 "끝 시각만 적으면 된다"는 간편함을 얻었다.
- 이 처리를 안 하고 그냥 빼면:

```text
 22:00 → 06:00 을 그대로 빼면  6 - 22 = -16 시간 = -960 분
 급여 = -960 × 10,000 / 60 = -160,000 원      ← 예외는 안 난다
```

  **음수 급여가 조용히 나온다.** 합계에서 남의 급여를 깎는 형태로 섞여 들어간다.

> **조용한 실패(silent failure)** — 예외도 에러 로그도 없이, 결과만 틀린 채 정상처럼 끝나는 것.\
> 예: 음수 분이 나와도 자바는 아무 말 안 하고 곱셈·나눗셈을 그대로 해준다.

- "시작한 날"을 택했을 때 22:00~06:00 근무:

```text
 시작한 날로 셈   월요일 누적 480 분  →  딱 8 시간이라 연장 0
                   480 × 1.5(야간) = 720 분어치 → 120,000 원

 끝난 날로 셌다면 화요일에 480 분이 먼저 붙는다
                   → 화요일에 또 일하면 그 분부터 바로 연장이 된다
```

  **어느 날에 넣느냐가 연장 판정과 휴일 가산을 둘 다 바꾼다.**
- 길이 0 근무를 만들 때 막는 이유: 잘못된 값이 **저장된 뒤에는 되돌리기 어렵다.**\
  계산 시점에 막으면 이미 DB에 들어간 뒤이고, 생성 시점에 막으면 애초에 못 들어간다(`Shift` 생성자·`PayRule` 생성자 둘 다 그렇게 한다).

### B. 개념

#### 6. 측정 — 겹침은 13%, 갈림은 89%

- 겹치는 분 (주 2,000개, 일한 분 5,373,180):

```text
 겹치는 분   715,200   13.3 %     ← 여덟 분 중 하나
 야간      1,800,540   33.5 %
 연장      1,405,080   26.1 %
 휴일      1,551,900   28.9 %
```

- 세 규칙이 다른 답을 낸 **주**: **1,781 / 2,000 (89%)**.
- 13%와 89%가 벌어지는 이유: **한 주에 겹치는 분이 단 1분만 있어도 그 주의 총액이 갈린다.**\
  분은 5,373,180개지만 급여는 2,000번 지급된다 — **빈도는 분 단위로 재고 돈은 사람 단위로 나간다.**

> **집계 단위(unit of aggregation)** — 같은 데이터라도 "무엇 하나를 한 건으로 세느냐"에 따라 비율이 완전히 달라진다.\
> 예: 불량률을 나사 하나 단위로 재면 0.01%인데, 자동차 한 대 단위로 재면 "나사 3,000개 중 하나라도 불량"이라 30%가 된다.

- 한 주 최대 차이: **192,500원** (곱한다 − 큰 것만).
- 총액 네 가지:

```text
 가산 없음    895,530,000   1.00
 큰 것만    1,182,595,000   1.32
 더한다     1,242,195,000   1.39
 곱한다     1,275,017,500   1.42

 더한다 기준  곱한다 +2.64 %, 큰 것만 -4.80 %  →  폭 7.44 %
```

- 인건비 12억이면: **약 9천만 원**이 규칙 해석 하나에 달렸다(README 문장 그대로).\
  그리고 그 해석은 대개 코드 리뷰에서 안 나온다 — 코드는 어느 쪽이든 똑같이 "맞게" 생겼기 때문이다.
- 연장 기준으로 갈린 주: **1,738 / 2,000 (87%)**. 총액은 DAILY 1,237,085,000 / WEEKLY 1,201,035,000 / EITHER 1,242,195,000.
- 평일 09:00~17:00 닷새: **세 가산 규칙 × 세 연장 기준 아홉 가지가 전부 400,000원.**\
  겹치는 분 0, 연장 0, 야간 0 — 이 박스의 문제가 통째로 안 보인다.
- 한 날만 09:00~23:00 으로 늘리면:

```text
 더한다   495,000
 곱한다   497,500
 큰 것만  490,000        한 사람 한 주에 7,500 원 차이

 손계산(더한다, DAILY): 평일 4일 1,920 분 × 1.0
                        긴 날 480 분 × 1.0 (09:00~16:59, 소정)
                             300 분 × 1.5 (17:00~21:59, 연장만)
                              60 분 × 2.0 (22:00~22:59, 연장+야간)
                        = 1,920 + 480 + 450 + 120 = 2,970 분어치 → 495,000
```

- "표준 근무 예제"가 경고인 이유: 사람이 예제를 만들 때 **자기가 아는 가장 평범한 케이스**를 고른다.\
  그런데 평범한 케이스는 정의상 규칙이 안 갈리는 곳이다 — **예제가 표준일수록 버그가 숨는다.**

#### 7. 변종 검증에서 고친 것

- 정렬 줄을 지워도 통과한 이유: 순서 테스트(`orderIndependent`)가 **주 40시간을 안 넘기는 근무표**로만 돌고 있었다.\
  주를 안 넘기면 연장 판정이 하루 안에서만 일어나고, 하루 누적은 근무마다 독립이라 순서가 영향을 안 준다.
- ADDITIVE 로만 시험하면 안 보이는 이유:

```text
 월~금 09~17 (2,400 분) + 토 22:00~06:00 (480 분 전부 야간), WEEKLY 기준

 시각 순     토요일 480 분이 연장이면서 야간   (겹침 480)
   ADDITIVE  2,400 × 1.0 + 480 × 2.0 = 3,360 분어치 → 560,000

 토요일 먼저  토요일은 야간만, 금요일 480 분이 연장  (겹침 0)
   ADDITIVE  1,920 × 1.0 + 480 × 1.5 + 480 × 1.5 = 3,360 → 560,000   ← 같다!

 같아지는 이유:  1 × 2.0   =   (1.5) + (1.5) − (1.0)
                한 분에 몰아준 가산과 두 분에 나눠준 가산의 합이 같다
```

- 드러나는 조합: **HIGHEST_ONLY + 주 40시간을 넘기는 근무표.**

```text
 시각 순     2,400 × 1.0 + 480 × 1.5 = 3,120 분어치 → 520,000
 토요일 먼저  1,920 × 1.0 + 480 × 1.5 + 480 × 1.5 = 3,360 → 560,000
                                       40,000 원 차이  ← 여기서 잡힌다
```

  겹친 480분이 가산을 **한 번만** 받기 때문에, 겹치느냐 안 겹치느냐가 총액에 남는다.\
  (520,000 은 테스트가 못 박은 값이고, 560,000 은 그 근무표의 ADDITIVE 값으로 테스트에 있다. 정렬을 뺀 쪽의 560,000 은 위 식으로 손계산한 값이다.)
- 반올림을 버림으로 바꿔도 통과한 이유: **예제 값이 전부 60으로 나누어떨어졌다.**
- 잡은 예제: **481분을 주 기준으로** — `481 × 10,000 / 60 = 80,166.67` → 반올림 80,167, 버림 80,166.
- 자기 말로: **테스트는 "코드가 맞나"가 아니라 "이 입력에서 두 구현이 다른가"만 본다.**\
  두 구현이 같은 답을 내는 입력만 골라 놓으면, 아무리 많이 돌려도 그 차이는 영원히 안 보인다.

> **변종 검증(mutation testing)** — 코드를 일부러 조금 망가뜨린 뒤, 테스트가 그걸 잡아내는지 보는 방법.\
> 예: 정렬 줄을 지워보고도 전부 초록이면, 그 테스트는 정렬을 검증하고 있지 않은 것이다.

#### 8. 함정 (README)

- 다섯: ① **"1.5배"로 적는 것**(0.5로 적어야 겹칠 때 무엇을 할지가 질문이 된다) ② **시간 단위로 세는 것**(22:30 시작의 야간 30분이 사라지거나 한 시간이 된다) ③ **연장 부등호**(480분째는 아직 아니고 481분째부터) ④ **야간 구간이 자정을 넘는 것**("22:00 이상 06:00 미만"은 빈 구간) ⑤ **근무를 목록 순서대로 세는 것**(연장 판정이 누적이라 조회 순서가 급여를 바꾼다).
- 예외 없이 조용히 틀리는 것: **②③⑤ 전부와 자정 넘는 근무의 음수 분.**\
  ④만 "빈 구간"이라 야간 분이 0으로 나와 그나마 눈에 띌 여지가 있다. 나머지는 그럴듯한 금액이 나온다.
- 실무 장애의 모습: 급여 재계산 배치를 다시 돌렸는데 **지난달과 금액이 다르게 나온다.**\
  코드도 데이터도 안 바뀌었는데 `ORDER BY` 없는 조회의 결과 순서만 바뀐 경우다 — 원인을 찾는 데 며칠이 걸린다.

#### 9. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 자정을 넘는 근무의 날: 이 코드는 **시작한 날**을 택했다(`Shift.date`). 바꾸면 **휴일 여부**(금요일 22시 시작이면 토요일 근무인가)와 **연장 판정**(하루 누적이 어느 날에 붙나)이 같이 움직인다. 실무에서 쓰는 셋째 방법은 **자정에서 잘라 두 날로 쪼개는 것**인데, 그러면 "근무 하나"라는 단위가 깨져서 8시간 연속 근무가 두 건으로 보인다 — 어느 쪽도 공짜가 아니다. (원본에 답 없음 — 내 추론)
- 주의 시작 요일: 이 코드는 `weeklyWorked` 를 그냥 0부터 누적하므로 **"넘겨받은 목록 전체가 한 주"** 라고 가정한다 — 주의 경계를 코드가 아니라 **호출자가 정한다.** 월요일 시작이면 토·일이 주의 끝이라 주 40시간 초과가 주말에 몰리고, 일요일 시작이면 토요일 하나만 끝에 남는다. 같은 근무표라도 **경계선을 어디 긋느냐가 어느 분이 연장인지를 바꾼다.** (원본에 답 없음 — 내 추론)
- 지각·조퇴: 소정근로는 **"일하기로 정한 시간"** 이지 "실제 일한 시간"이 아니다. 이 코드는 실제 일한 분만 누적하므로, 지각하면 그날 480분에 늦게 도달해 **연장이 늦게 시작된다.** 반대로 "소정근로를 줄여준다"고 보면 연장이 빨리 시작된다 — 둘 다 말이 되고, 이것도 `PayRule` 로 올려야 할 자리다. (원본에 답 없음 — 내 추론)
- 포괄임금제: **필요 없어지지 않는다.** 포괄임금은 "미리 정해둔 가산을 매달 고정 지급한다"는 것이지 "가산을 안 준다"가 아니다. 실제 계산액이 고정액을 넘으면 차액을 줘야 하므로, **비교하려면 이 계산이 먼저 있어야 한다.** 즉 이 계산은 지급용에서 검증용으로 자리만 옮긴다. (원본에 답 없음 — 내 추론)

#### 10. 연결

- 01-parking-fee 와 같은 자리: 주차는 **"하루"의 기준**(자정 vs 24시간)을 정책 값으로 올렸고, 여기는 **"겹치면"의 처리**를 enum으로 올렸다. 둘 다 **"말이 안 정해준 자리를 값으로 꺼낸다"** 는 같은 수법이다.
- 누적 판정 때문에 순서가 결과를 바꾸는 성질: **02-promotion**(할인 적용 순서), **06-tax**(누진 구간 누적), **14-mileage-expiry**(먼저 쓰는 마일리지가 어느 것인가) — 전부 "무엇을 먼저 세느냐"가 답을 바꾼다.
- 실무 관행과의 대응: enum으로 선택지를 고정하는 것은 **요금/정책 테이블의 코드 값**과 같다. 값으로 있으면 "누가 언제 무엇으로 정했는지"가 남고, 두 값을 나란히 돌려 차액을 재볼 수 있다.
