## 해결하는 문제

급여 규칙은 말로 적힌다 — "연장 50%, 야간 50%". 그런데 한 분(minute)에 두 가산이 동시에 붙을 때 더하나 곱하나 큰 것만 주나는 그 말에 없다.\
이 모델이 없으면: 구현자마다 다른 해석으로 코드를 짜고, 같은 근무표에 다른 급여가 나오며, 어느 쪽이 "버그"인지 판정할 기준조차 없다.

```text
요구사항(말)  "겹치면?"  ──▶  구현자 A: 곱한다    22,500
                              구현자 B: 더한다    20,000
                              둘 다 "50% 가산"을 구현했다 — 코드 리뷰로는 못 가른다
```

쉬운 예: "10% 할인 회원"이 "행사 10% 할인" 상품을 사면 20%인가 19%인가 — 계산대마다 다르면 싸움 난다.\
똑같은 구조다: 결정을 코드 안에 숨기지 않고 `PremiumRule`·`OvertimeBasis` 같은 **이름 붙은 선택지**로 꺼내 두면, 호출자가 하나를 고르지 않고는 계산을 못 하고, 세 해석을 같은 코드로 돌려 차이를 잴 수 있다.\
실무 예: 급여 엔진, 택시·배달 할증 겹침, 통신 요금 결합 할인 — "가산이 겹치면"은 어디에나 있다.

  - *가산율(premium rate)*: 기본 시급 위에 더 얹는 비율. 0.5 = 50% 더.

### 한눈에 — 쉽게 말하면

**급여 계산 = "50% 더 준다"는 말이 겹칠 때 어떻게 되는지 정해 놓기.**

- 편의점에서 "1+1 쿠폰"과 "반값 쿠폰"을 둘 다 들고 갔다고 하자. 둘 다 쓸 수 있나? 더 좋은 것 하나만? 순서대로 겹쳐서? — **가게가 미리 안 정해 놓으면 계산대에서 싸움 난다.**
- 급여도 똑같은 구조다. 연장 근로 50% 가산, 야간 근로 50% 가산 — 그런데 **밤에 하는 연장 근로**는 둘 다 해당된다. 더하나(+0.5+0.5), 곱하나(×1.5×1.5), 큰 것 하나만 주나?
- 같은 한 시간(시급 10,000원)이 규칙 해석에 따라 **15,000원 / 20,000원 / 22,500원**이 된다. 셋 다 "50% 가산"이라는 같은 말에서 나온 답이다. (법은 더하는 쪽이다.)
- 이 챕터의 요점: **말로 된 요구사항("50% 가산")은 그대로 코드가 못 된다** — 겹칠 때의 규칙을 enum으로 이름 붙여 골라야 한다.

```text
야간에 한 연장 근로 1시간, 시급 10,000원

  더한다(ADDITIVE)        10,000 × (1 + 0.5 + 0.5) = 20,000   ← 법이 이쪽
  곱한다(MULTIPLICATIVE)  10,000 × 1.5 × 1.5       = 22,500
  큰 것만(HIGHEST_ONLY)   10,000 × (1 + 0.5)       = 15,000
```

실무 예: 급여 시스템, 택시 심야 할증 + 시외 할증, 배달비 우천 할증 + 심야 할증 — "할증이 겹치면?"은 어디에나 있다.

## 동작·원리

### 전체 흐름

```text
요구사항(말)                          →  코드(타입/메서드)
─────────────────────────────────────────────────────────
"연장·야간·휴일에 50% 가산"           →  PayRule record (가산율을 0.5 라는 숫자로 보관)
"겹치면 어떻게?"  ← 말에는 답이 없다  →  enum PremiumRule { ADDITIVE, MULTIPLICATIVE, HIGHEST_ONLY }
"연장은 하루 8h? 주 40h?" ← 이것도    →  enum OvertimeBasis { DAILY, WEEKLY, EITHER }
"근무 한 번"                          →  Shift record (시작한 날 + 시작·끝 시각 + 휴일 여부)
"급여를 내라"                         →  Payroll.calculate(shifts, premiumRule, basis)

calculate 내부:
  근무를 시각 순 정렬 → 1분씩 훑으며 (연장? 야간? 휴일?) 판정
  → 그 분의 가산율 목록을 만들고 → PremiumRule 로 배수 하나로 합침
  → 가중 분을 전부 더해 시급 × (분/60), 원 단위 반올림
```

  - *가산율(premium rate)*: "기본의 몇 %를 더 주나". 0.5로 적는다. "1.5배"라고 적으면 겹칠 때 곱하는 쪽으로 흘러가는데, 법은 더하는 쪽이다 — **표현 방식이 계산 방식을 유도한다.**
  - *enum*: 선택지에 이름을 붙여 고정한 타입. "겹치면?"이라는 애매한 질문을 코드가 3택 질문으로 바꿔 놓은 것.

### 규칙 1 — 분 단위로 센다 (시간 단위 금지)

**어떤 요구사항인가**: "22:30에 시작한 근무의 야간분을 정확히 세라."

예시: 22:30 시작이면 22:30\~06:00 중 야간은 22:30부터다. 시간 단위로 세면 이 **30분이 통째로 사라지거나 한 시간이 된다.**

그래서 calculate는 근무를 **1분씩** 훑는다: 매 분마다 `daily`(그날 누적), `weeklyWorked`(주 누적)를 1씩 올리고 그 분이 연장/야간/휴일인지 판정한다. 느려 보여도 규칙이 전부 분 단위 경계에서 갈리므로 이게 가장 안 틀리는 모델이다.

### 규칙 2 — 연장은 481분째부터 (부등호 하나)

**어떤 요구사항인가**: "하루 8시간을 넘긴 만큼이 연장이다."

```text
480분째  누적 480 > 480 ? → 거짓. 아직 연장 아님
481분째  누적 481 > 480 ? → 참.   여기부터 연장

09:00~17:01 (481분) 손계산:
  480 × 1.0 + 1 × 1.5 = 481.5 분어치
  481.5 × 10,000 / 60 = 80,250 원
```

- 코드로는 `dailyWorked > rule.dailyRegularMinutes()` — `>=`로 틀리면 하루 1분씩, 한 달 20분이 조용히 어긋난다. 아무도 눈치 못 챈다.
- 연장 기준 자체도 3택이다(OvertimeBasis): 하루 8시간(DAILY) / 주 40시간(WEEKLY) / 둘 중 하나(EITHER).

```text
하루 6시간 × 7일 (2,520분)      하루 10시간 × 4일 (2,400분)
  DAILY:  연장 0   → 420,000      DAILY:  연장 480분 → 440,000
  WEEKLY: 연장 120 → 430,000      WEEKLY: 연장 0     → 400,000
```

**어느 쪽이 근로자에게 유리한지는 근무표가 정한다** — 기준 선택에 정답이 없고, 그래서 enum으로 밖에 내놓았다.

### 규칙 3 — 야간 구간은 자정을 넘는다

**어떤 요구사항인가**: "22시부터 다음 날 6시까지는 야간 가산 50%."

```text
흔한 식: start ≤ t < end   →  "22:00 이상 06:00 미만"은 빈 구간! (22시면서 6시 전인 시각은 없다)

올바른 처리 (PayRule.night):
  start < end 면 (보통 구간):   start ≤ t < end
  start ≥ end 면 (자정 넘김):   t ≥ start  또는  t < end   ← AND 가 OR 로 바뀐다

  21:59 아님 | 22:00 야간 | 00:00 야간 | 05:59 야간 | 06:00 아님
```

Shift도 같은 문제를 가진다: 끝 시각이 시작보다 빠르면(22:00→06:00) **다음 날로 읽는다**. 그냥 빼면 음수 분·음수 급여가 나오는데 예외도 안 난다. 그리고 자정 걸친 근무는 "무슨 날 근무인가"에 답이 둘인데, 여기서는 **시작한 날**로 센다 — 이 선택이 하루 누적(연장 판정)과 휴일 가산을 둘 다 바꾼다.

### 규칙 4 — 근무는 시각 순으로 정렬해서 센다

**어떤 요구사항인가**: 명시된 문장은 없다. 하지만 연장 판정이 **누적**이라 "몇 번째 분인가"가 결과를 정한다 — 목록 순서대로 세면 **DB 조회 순서가 급여를 바꾼다.**

```text
월~금 09~17 (2,400분) + 토 22:00~06:00 (480분 야간), 주 40h 기준

시각 순:      월~금이 소정근로를 다 채우고 → 토요일 480분이 연장+야간 (겹침 480)
토요일 먼저:  토요일은 야간만 → 금요일 480분이 연장 (겹침 0)
```

- 변종 검증에서 잡은 것: **정렬 줄을 지워도 테스트가 전부 통과했다** — 순서 테스트가 주 40시간을 안 넘기는 근무표로만 돌고 있었기 때문.
- 더 미묘한 것: 주 기준 연장을 넣어도 **더하는 규칙에서는 총액이 같다** (`1×2.0`과 `1.5+1.5−1.0`이 같다). 겹친 분에 가산을 한 번만 주는 HIGHEST_ONLY가 있어야 갈린다. — **어느 규칙으로 시험하느냐가 어느 버그를 잡을 수 있느냐를 정한다.**

### 규칙 5 — 휴일 가산은 연장 가산을 대신한다

**어떤 요구사항인가**: "휴일 8시간까지 50%, 8시간 초과 100% 가산."

```text
휴일 09:00~19:00 (600분):
  480분 × 1.5 + 120분 × 2.0 = 960 분어치 → 160,000원
  겹침 0 — 휴일 초과분(100%)이 연장(50%) 자리를 대신하므로 세 규칙이 같은 답

휴일 20:00~24:00 (240분): 22시부터는 휴일+야간이 겹친다
  더한다  120×1.5 + 120×2.0  = 420 → 70,000
  곱한다  120×1.5 + 120×2.25 = 450 → 75,000
  큰 것만 120×1.5 + 120×1.5  = 360 → 60,000
```

코드로는 `if (holiday) { 휴일 가산 } else if (overtime) { 연장 가산 }` — **else if 하나가 "휴일 초과는 연장과 안 겹친다"는 도메인 규칙**이다.

## 쓰이는 자료구조·알고리즘

- **정렬 + 동률을 줄이는 비교자** — 근무를 `startedAt → endedAt` 순으로 정렬해야 누적 판정이 넘겨받은 목록 순서에 덜 휘둘린다(impl `Payroll.java:84`). 시작 시각만 비교하면 같은 시각에 시작한 근무끼리는 Java의 안정 정렬이 **입력 순서**를 그대로 남겨, 조회 순서에 따라 답이 달라질 수 있다. 시작·종료가 모두 같은 근무 둘은 이 비교자로도 여전히 동률이다 — 엄밀한 전순서(total order)가 되려면 id 같은 키가 더 필요하다. → [algorithm/01-elementary-sort](../../../algorithm/01-elementary-sort/2-summary.md)
- **선형 스캔(1분 단위 sweep) + 누적 카운터** — 근무를 분 단위로 훑으며 `daily`·`weeklyWorked`를 올린다. 연장 판정은 "지금까지 몇 분째인가"라는 **누적합**에 대한 임계값(480·2,400) 비교다. → [algorithm/10-prefix-sum](../../../algorithm/10-prefix-sum/2-summary.md)
- **해시맵 `Map<LocalDate, Integer>`** — 날짜별 누적 분. 주 누적은 `int` 하나면 되지만 하루 누적은 날마다 따로 세야 한다. → [data-structure/05-hashmap](../../../data-structure/05-hashmap/2-summary.md)
- **자정을 넘는 구간 판정(원형 구간)** — `22:00~06:00`은 하루라는 원 위에서 두 조각으로 잘린 구간이라 `start ≤ t < end`가 `t ≥ start || t < end`로 바뀐다. 시계·요일·각도처럼 **끝이 처음으로 이어지는 값**에서 같은 처리가 나온다.
- **enum 스위치(전략 선택)** — `PremiumRule`·`OvertimeBasis`. 같은 입력을 세 해석으로 돌려 차이를 세는 측정 도구이기도 하다.
- **고정 소수 산술(`BigDecimal` + `HALF_UP`)** — 가중 분을 1분마다 `BigDecimal`로 더하고, 시급을 곱해 60으로 나눌 때 마지막에 한 번 반올림한다(impl `Payroll.java:125-132`). [05-multi-currency](../05-multi-currency/2-summary.md)에서 같은 원칙이 반복된다.

## 적용 — 풀어나가는 법

이 컬렉션의 풀이 순서는 늘 같다: ① 요구사항 한 줄에서 **안 정해진 결정**을 찾아 적는다 → ② 결정마다 enum을 만들어 호출자가 고르게 한다 → ③ 해석이 **갈리는 입력**(표준 근무가 아닌 것)을 일부러 만든다 → ④ 같은 자료를 모든 조합으로 돌려 **갈린 건수와 금액**을 센다.\
급여에서는 ①이 "겹치면?·연장 기준?·자정 넘는 날?"이고, ③이 "한 날만 09~23시로 늘린 근무표"다. 아래 원본 문제와 측정 절이 그 순서 그대로다.

### 문제 — 이 챕터가 시키는 것

주어진 규칙은 네 줄이다(원본 `PayRule` javadoc 그대로).

```text
  연장            1 일 8 시간 또는 주 40 시간을 넘긴 만큼   가산 50 %
  야간            22 시부터 06 시까지                      가산 50 %
  휴일 8 시간까지                                          가산 50 %
  휴일 8 시간 초과                                         가산 100 %
```

원본 README가 던지는 문장은 이것이다.

**"같은 한 시간에 15,000 과 22,500 이 나온다. 셋 다 '50 퍼센트 가산' 에서 나온 답이다."**

- 야간에 한 연장 근로 한 시간을 **더하나(20,000) 곱하나(22,500) 큰 것만 주나(15,000)?**
- "연장"의 기준은 **하루 8시간인가 주 40시간인가 둘 중 하나인가?**
- 자정을 넘는 근무는 **시작한 날인가 끝난 날인가?**

네 줄이 하나도 안 정해준다.\
그래서 이 박스는 답을 하나로 정하지 않고 `PremiumRule` · `OvertimeBasis` **enum으로 올린다.**

> **enum으로 올린다** — 애매한 선택지에 이름을 붙여 타입으로 고정하는 것.\
> 예: "겹치면 어떡하지?"라는 말을 `ADDITIVE / MULTIPLICATIVE / HIGHEST_ONLY` 세 개로 적어두면, 부르는 쪽이 하나를 **고르지 않고는 계산을 못 한다.**

| 2 | `overtime(dailyWorked, weeklyWorked, basis)` | 이 분이 연장인가. **480분째는 아직 아니고 481분째부터** |

테스트가 못 박은 계약(`PayrollTest`): 8시간→80,000원(세 규칙 동일) · 481분→80,250원(DAILY) · 9시간→95,000원 · 야간 경계 21:59 아님/22:00 야간/05:59 야간/06:00 아님 · 22:00\~06:00→480분 전부 야간 120,000원 · 14:00\~24:00→더한다 120,000 / 곱한다 125,000 / 큰 것만 110,000 · 휴일 09\~19→세 규칙 전부 160,000원(겹침 0) · 휴일 20\~24→70,000 / 75,000 / 60,000 · 하루 6h×7일→DAILY 420,000 vs WEEKLY 430,000 · 하루 10h×4일→DAILY 440,000 vs WEEKLY 400,000 · 목록 순서를 뒤집어도 결과 동일 · 481분 WEEKLY→80,167원(반올림) · 근무 0건→0원 · 길이 0 근무·시급 0은 생성 시점 거부.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

### 측정 — "구석 사례"라는 말의 함정

주 2,000개, 537만 분을 무작위로 만들어 세 규칙을 다 돌렸다 (README 기록):

```text
분 단위:   가산이 겹치는 분은 13.3% 뿐        → "구석 사례네"
주 단위:   세 규칙이 다른 답을 낸 주 1,781/2,000 (89%)
           한 주 최대 차이 192,500원
총액:      큰 것만 1.32 / 더한다 1.39 / 곱한다 1.42 (기본 대비)
           → 인건비 12억이면 약 9천만 원이 해석 하나에 달렸다
```

- **한 주에 겹치는 분이 1분만 있어도 그 주의 급여가 갈린다.** "구석 사례"는 분 단위로 맞고 사람 단위로 틀리다 — 급여는 사람 단위로 지급된다.
- 연장 기준(DAILY/WEEKLY/EITHER)으로도 1,738/2,000 주가 갈렸다.
- **표준 근무(평일 09\~17 닷새)로 시험하면 9가지 조합이 전부 400,000원** — 아무 차이도 안 보인다. 한 날만 09\~23으로 늘리면 그때부터 갈린다. 예제가 "표준"일수록 버그가 숨는다.

## 장애 시나리오와 대처

**1. 명세서 항목 합과 총액이 1원 안 맞는다**

- 현상: 급여 명세서의 "기본급 + 연장 + 야간" 항목 합과 총액이 1원 다르다.
- 보이는 형태: 대사(검산) 배치가 매달 몇 명씩 `합계 불일치`를 찍는다. 값은 항상 ±1원.
- 원인: 항목마다 따로 반올림한 뒤 더했거나, `double`로 누적해 마지막에 반올림했다. 가산율 0.5는 2진수로 정확하지만 `분/60`은 아니다.
- 대처: 가중 분을 `BigDecimal`로 누적하고 **마지막에 한 번** 반올림한다. 항목별 표시가 필요하면 마지막 항목을 `총액 − 나머지`로 구해 합을 맞춘다([06-tax](../06-tax/2-summary.md)의 "마지막 몫은 빼기로").

**2. 야간 시간대를 바꿨더니 지난달 급여가 재계산에서 달라진다**

- 현상: 야간을 22~06시에서 23~07시로 바꾼 뒤, 지난달 급여 재계산 배치가 지급액과 다른 값을 낸다.
- 보이는 형태: 재계산 결과와 실제 지급액의 차액 보고서가 사람 수만큼 쏟아진다.
- 원인: `PayRule`이 **시행일 없는 값 하나**다. 규칙을 바꾸면 과거 근무까지 새 규칙으로 계산된다.
- 대처: 규칙을 시행일 붙은 판으로 쌓고 근무일 기준으로 판을 고른다 — [09-policy-version](../09-policy-version/2-summary.md). 지급 시점의 계산 결과는 스냅샷으로 남긴다.

**3. 같은 근무표인데 조회 범위에 따라 연장 시간이 다르다**

- 현상: 월 단위로 뽑은 급여와 주 단위로 뽑은 급여의 연장 합이 다르다.
- 보이는 형태: 주 40시간 초과분이 어떤 조회에서는 잡히고 어떤 조회에서는 안 잡힌다.
- 원인: `calculate`는 **넘겨받은 목록 전체가 한 주**라고 가정한다. 주의 시작 요일(월/일)과 조회 범위를 호출자가 정하므로, 범위를 잘못 자르면 주 경계가 어긋난다(정답 9번 참고).
- 대처: 주 경계 규칙(시작 요일)을 명시하고, 호출자가 항상 **주 단위로 잘라** 넘기게 한다. 월 급여는 주 계산의 합으로 만든다.

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| "1.5배"로 적음 → 곱하는 쪽으로 흘러감 | 가산율 0.5로 적고, 겹침 규칙을 enum으로 명시 (법은 ADDITIVE) |
| 480분째를 연장으로 셈 (`>=`) | `>` — 481분째부터. 테스트가 17:01 근무로 잡는다 |
| "22:00 이상 06:00 미만" | 자정 넘김이면 AND→OR. 21:59/22:00/05:59/06:00 네 경계 테스트 |
| 자정 넘는 근무를 그냥 빼기 | 끝<시작이면 +1일. 안 하면 음수 급여가 예외 없이 나온다 |
| 목록 순서대로 누적 | 시각 순 정렬 먼저. 단 ADDITIVE만으로는 이 버그가 안 보인다 |
| 원 단위 버림 | 반올림(HALF_UP). 481분 주 기준 = 80,166.67 → 80,167. 딱 떨어지는 예제만 쓰면 버림으로 바꿔도 통과한다 |

## 핵심 문장

- "50% 가산"이라는 같은 말에서 15,000원과 22,500원이 나온다 — **말의 애매함은 코드가 못 없앤다. enum으로 선택지를 드러내고 사람이 골라야 한다.**
- 가산율을 0.5로 적느냐 "1.5배"로 적느냐가 겹침 처리를 유도한다 — **데이터 표현이 곧 설계다.**
- 겹치는 분은 13%지만 갈리는 주는 89% — **빈도는 분 단위로 재고 돈은 사람 단위로 나간다.** 구석 사례라는 말을 믿지 마라.
- 연장 판정이 누적이라 순서가 급여를 바꾼다 — 그리고 그 버그는 특정 규칙(HIGHEST_ONLY)·특정 근무표(주 40h 초과)에서만 보인다.
- 표준 근무 예제로는 아홉 조합이 전부 같은 답을 낸다 — **차이가 나는 입력을 일부러 만들어야 규칙의 차이가 보인다.**

### 용어 풀이

- **가산율(premium rate)**: 기본 시급 위에 더 주는 비율. 0.5 = 50% 더.
- **소정근로**: 가산 없이 일하기로 정한 시간. 하루 480분 / 주 2,400분. 이걸 넘긴 분이 연장이다.
- **연장(overtime) / 야간(night) / 휴일(holiday)**: 가산이 붙는 세 종류. 한 분이 여러 개에 동시에 해당될 수 있다 — 그때가 이 챕터의 주제.
- **겹침(stacking)**: 한 분에 가산이 2개 이상 붙는 것. 더하기/곱하기/큰 것만 — 3가지 해석이 가능하다.
- **ADDITIVE / MULTIPLICATIVE / HIGHEST_ONLY**: 겹침 처리 3택. 법(근로기준법)은 ADDITIVE.
- **OvertimeBasis (DAILY/WEEKLY/EITHER)**: 연장을 하루 8h로 재나 주 40h로 재나. 유불리는 근무표가 정한다.
- **record**: 값 묶음을 담는 자바 타입. 생성 시점에 검증(시급>0 등)을 걸어 잘못된 값이 아예 못 만들어지게 한다.
- **BigDecimal**: 소수를 오차 없이 다루는 타입. 0.5 같은 가산율 계산에 double 대신 쓴다.
- **HALF_UP(반올림)**: 원 단위 처리 방식. 버림과 1원 차이 — 1,000명이면 하루 1,000원이 어디론가 사라진다.
- **누적 판정**: "이 분이 연장인가"가 지금까지 일한 분에 달려 있다는 것. 그래서 세는 순서가 결과를 바꾼다.
