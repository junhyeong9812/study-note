### A. 과제

#### 0. 말 한 줄이 안 말해주는 것

- 안 말해주는 결정 셋(원문 그대로):

```text
 안 말해준 것            가능한 읽기
 "세트를 보장한다"   →  먼저 한 장씩 깔기(SET_FIRST) vs 랜덤 뒤 교체(SWAP_AFTER)
 (같은 종류 두 장?)  →  허용(ALLOW_DUPLICATE) vs 금지(NO_DUPLICATE)
 (나머지는 뭘 주나?) →  무작위(RANDOM) vs 재고 많은 것부터(MOST_STOCK)
```

> **정책 축(policy axis)** — 요구사항 한 줄 안에 숨어 있는, 서로 독립적으로 정해야 하는 선택 하나.\
> 예: "세트 보장"이라는 한 줄 안에 보장 방식·중복 허용·나머지 고르기라는 축 셋이 들어 있다.

- "서로 간섭한다"의 뜻: **한 축의 값이 다른 축의 효과를 통째로 없애거나 뒤집는다.**\
  실제 예 셋 —
  - 중복을 **금지**하면 보장 축이 아무 일도 안 한다(5장 사고 중복 금지면 `SetGuarantee` 셋이 전부 같은 결과).
  - `MOST_STOCK` 만 켜도 보장 없이 세트가 2,702 — 보장 축이 하던 일을 나머지 고르기 축이 대신 한다.
  - 중복을 금지하면 종류보다 많이 산 사람에게 줄 카드가 없어져 **못 준 장수가 3배**가 된다.
- 조합 수: `3 × 2 × 2 = 12` 가지.\
  측정 테스트가 이 열두 개를 기계적으로 전부 돌린다.
- 값으로 안 올리면 잃는 것: **열두 개를 견줄 수 없다.**\
  견주지 못하면 "세트 보장"이라는 이름이 실제로 세트를 제일 많이 만드는지조차 모른 채 출시한다(실제로는 아니었다 — 1,608 vs 2,945).
- "보장은 앞사람 것": **재고가 빠듯할 때** 드러난다.\
  넉넉하면 모두가 세트를 받아서 차이가 안 보인다.
- 5종 1장씩, 5장씩 둘: 둘째 사람은 **0장**이다(`shortage == 5`).

```text
 재고  A1 B1 C1 D1 E1  (총 5 장)
 첫 사람(5장)  A B C D E  ← 세트 완성. 재고 0
 둘째 사람(5장) (없음)     ← 0 장. 보장 규칙을 무엇으로 바꿔도 같다
```

#### 1. TODO 1 — choices

정답 코드 (impl/Distributor.java):

```java
List<String> choices = new ArrayList<>();
for (String kind : stock.available()) {
    if (within == WithinBuyer.ALLOW_DUPLICATE || !already.contains(kind)) {
```

- 두 조건: ① **재고가 1장 이상 남아 있다** ② (중복 금지면) **이 사람이 아직 안 받은 종류다.**
- `Stock.available()` 이 이미 거르는 것: **남은 장수가 0인 종류.**\
  그래서 `choices` 는 거기에 "이미 받았나"만 더 본다.
- 중복 금지에서 빼는 기준: **재고가 아니라 `already`(그 사람이 지금까지 받은 목록)** 다.\
  재고에는 A가 20장 남아 있어도, 그 사람이 이미 A를 받았으면 후보에서 빠진다.
- 비었는데 주면 깨지는 것 둘: **재고가 음수**가 되거나(없는 종류를 빼감) **중복 금지 규칙이 깨진다.**

> **불변식(invariant)** — 프로그램이 도는 동안 언제 확인해도 참이어야 하는 조건.\
> 예: "재고는 절대 음수가 아니다", "중복 금지면 한 사람의 카드에 같은 종류가 두 번 없다."

- 순서가 중요한 이유: `RANDOM` 은 이 목록의 **인덱스를 뽑는다.**\
  목록 순서가 실행마다 달라지면 같은 seed 로도 다른 카드가 나온다.\
  `Stock.available()` 이 `kinds()`(넣은 순서)를 지키는 것이 그래서 계약이다.

#### 2. TODO 2 — giveOne

정답 코드:

```java
List<String> choices = choices(stock, already, within);
if (choices.isEmpty()) {
    return null;
}
String chosen;
if (fillRule == FillRule.MOST_STOCK) {
    List<String> sorted = new ArrayList<>(choices);
    sorted.sort(Comparator
            .comparingInt((String kind) -> stock.left(kind)).reversed()
            .thenComparing(Comparator.naturalOrder()));
    chosen = sorted.get(0);
} else {
    chosen = choices.get(random.nextInt(choices.size()));
}
stock.take(chosen);
return chosen;
```

- `null` 인 이유: **"못 주는 것"이 예외 상황이 아니라 정상적으로 일어나는 결과**이기 때문이다.\
  재고가 마르거나 중복 금지에 걸리는 일은 흔하다.\
  부르는 쪽(`distribute`)은 `null` 을 보고 루프를 멈추고 `shortage` 로 센다.
- 고르는 법: `RANDOM` 은 **후보 중 하나를 무작위로**, `MOST_STOCK` 은 **남은 장수가 제일 많은 종류**를.
- 동률: **종류 이름 사전순**(`thenComparing(naturalOrder())`).
- 타이브레이크를 안 두면: `sort` 가 안정 정렬이라 **원래 목록 순서(= 재고를 만든 `Map` 의 순회 순서)** 가 결과를 정해버린다.\
  그러면 같은 seed 로도 다른 배분이 나온다 — "왜 나만 중복이냐"는 문의에 **다시 돌려 보여줄 수가 없다.**

> **재현 가능성(reproducibility)** — 같은 입력을 다시 넣으면 글자 그대로 같은 결과가 나오는 성질.\
> 예: 주문 목록·재고·seed 만 저장해 두면 반년 뒤에도 그 사람의 배분을 그대로 다시 만들어 보여줄 수 있다.

> **안정 정렬(stable sort)** — 비교해서 같은 값들끼리는 원래 순서를 그대로 두는 정렬.\
> 예: A·B·C 가 다 10장이면, 비교 기준이 "장수"뿐일 때 정렬은 셋의 순서를 안 바꾼다 — 그래서 우연한 입력 순서가 답을 정한다.

- 손계산 (A=10, B=1, C=1, 세 장, `MOST_STOCK`):

```text
 1 장째  후보 A(10) B(1) C(1)  → 제일 많은 A   재고 A9 B1 C1
 2 장째  후보 A(9)  B(1) C(1)  → 여전히 A      재고 A8 B1 C1
 3 장째  후보 A(8)  B(1) C(1)  → 여전히 A      재고 A7 B1 C1
 결과 [A, A, A].  희소한 B·C 가 그대로 남아 뒷사람이 볼 수 있다
```

- `stock.take` 를 빼먹으면: **재고가 안 줄어 무한정 나눠준다.**\
  총량 계약(`shortage`·`total`)이 전부 틀어지고, `MOST_STOCK` 은 같은 종류만 영원히 고른다.
- `MOST_STOCK` 인데 `Random` 을 받는 이유: **부르는 쪽의 시그니처를 규칙마다 바꾸지 않기 위해서다.**\
  `distribute` 는 어느 규칙인지 모르고 늘 같은 방식으로 부른다.\
  그리고 `MOST_STOCK` 은 `random` 을 **안 쓰기 때문에 난수 소비 순서가 달라지지 않는다** — 규칙을 바꿔도 seed 의 의미가 보존된다. (원본에 명시 없음 — 내 추론)

#### 3. TODO 3 — distribute

정답 코드:

```java
Random random = new Random(seed);
Map<String, List<String>> byBuyer = new LinkedHashMap<>();
int shortage = 0;

for (Order order : orders) {
    List<String> given = new ArrayList<>();
    if (guarantee == SetGuarantee.SET_FIRST) {
        for (String kind : stock.kinds()) {
            if (given.size() >= order.quantity()) {
                break;
            }
            if (stock.take(kind)) {
                given.add(kind);
            }
        }
    }
    while (given.size() < order.quantity()) {
        String card = giveOne(stock, given, within, fillRule, random);
        if (card == null) {
            break;
        }
        given.add(card);
    }
    if (guarantee == SetGuarantee.SWAP_AFTER) {
        swapForMissingKinds(stock, given);
    }
    shortage += order.quantity() - given.size();
    byBuyer.put(order.buyerId(), List.copyOf(given));
}
return new Distribution(Map.copyOf(byBuyer), shortage);
```

- `Random` 은 **전체에서 하나**를 `seed` 로 만든다.\
  사람마다 새로 만들면 모든 사람이 같은 난수열을 받아 같은 카드를 뽑는다.
- "살 수 있는 만큼"을 안 지키면: 3장 산 사람에게 5장을 깔게 되어 **주문 수량보다 많이 준다.**\
  그래서 루프 맨 앞에 `given.size() >= quantity` 로 끊는다.
- 재고 없는 종류: `stock.take` 가 `false` 를 주므로 **그냥 건너뛴다.**\
  깐 장수가 종류 수보다 적어지고, 나머지는 아래 `while` 이 채운다.
- 교체는 **후**다. `SWAP_AFTER` 라는 이름 그대로 — **먼저 다 주고 나서** 빠진 종류를 메운다.\
  중복이 생겨야 바꿀 밑천이 생기기 때문이다.
- 교체 성립 조건 둘: ① **`given` 안에 중복된 장이 있다**(`indexOfDuplicate >= 0`) ② **재고에 그 빠진 종류가 남아 있다**(`stock.left(missing) > 0`).\
  하나만 없어도 세트가 안 된다.

```text
 SWAP_AFTER 한 바퀴 (5 종, 받은 카드 A A B C C, 재고에 D·E 있음)

   빠진 종류 D  중복 자리 = index 1(A)  A 를 재고에 반납, D 를 꺼냄
       A A B C C  →  A D B C C
   빠진 종류 E  중복 자리 = index 4(C)  C 를 반납, E 를 꺼냄
       A D B C C  →  A D B C E      세트 완성
```

- `shortage` 는 **주문 수량 − 실제로 준 장수**를 사람마다 더한다.
- 재고가 A만 5장 + `SWAP_AFTER`:

```text
 후보가 A 뿐  →  A A A A A
 교체 시도: B·C·D·E 는 전부 stock.left == 0  →  continue (바꿀 곳이 없다)
 결과 distinctKinds = 1, duplicateCards = 5 − 1 = 4, completeSets = 0
 "세트 보장" 이라고 써 놓고 재고 편성 때문에 안 지켜진다
```

- `List.copyOf` 로 굳히는 이유: `given` 은 루프 안에서 계속 바뀌는 `ArrayList` 다.\
  그대로 넣으면 **다음 교체가 이미 저장한 결과까지 바꿔버린다.**\
  복사해 넣으면 결과가 그 시점에 고정된다.

> **방어적 복사(defensive copy)** — 밖으로 내보내는 값을 복사해서, 안쪽이 나중에 바뀌어도 내보낸 값이 안 바뀌게 하는 것.\
> 예: 장바구니 목록을 그대로 넘겨주면 내가 물건을 더 담을 때 상대가 본 목록도 같이 늘어난다.

```java
int complete = 0;
for (Order order : orders) {
```

- 장수가 아니라 종류 수를 보는 이유: **여덟 장을 받아도 AAAABBBB 면 세트가 아니다.**\
  "세트"는 종류를 다 모았느냐이지 몇 장이냐가 아니다.
- 필터가 죽은 코드인 이유: 3장 산 사람은 **받은 카드도 최대 3장**이라 서로 다른 종류가 3을 못 넘는다.\
  `== 5` 비교에서 저절로 떨어진다.

```text
 quantity = 3  →  given.size() ≤ 3  →  distinctKinds ≤ 3  <  kindCount(5)
 그러므로 "quantity < kindCount 인 사람 제외" 는 결과를 못 바꾼다 = 죽은 코드
```

- `eligibleForSet` 에서는 본체인 이유: 거기서는 **아무도 받지 않은 시점의 주문만 보고** 분모를 센다.\
  받은 카드를 안 보므로 저절로 걸러질 길이 없다 — 직접 `quantity >= kindCount` 를 봐야 한다.
- 보장률 = **`completeSets`(분자) / `eligibleForSet`(분모)**.

#### 5. 측정 — 발견 하나: 이름이 효과를 안 말해준다

원본 MeasurementTest 실측(8종×60장, 100명×100회, 세트 가능자 2,945명):

```text
  보장         중복   나머지       세트    중복 장수  못 준 장수
  먼저 깔기    허용   무작위       1,608   12,853      3,992
  먼저 깔기    허용   재고많은것   1,767   11,408      3,992
  먼저 깔기    금지   아무거나     1,785        0     12,875
  랜덤뒤교체   허용   무작위       2,303   10,439      3,992
  랜덤뒤교체   허용   재고많은것   2,702    9,374      3,992
  랜덤뒤교체   금지   재고많은것   2,945        0     10,247
  보장없음     허용   무작위         216   16,977      3,992
  보장없음     허용   재고많은것   2,702    9,374      3,992
```

- "세트 보장"이라는 이름의 조합(먼저 깔기 + 무작위): **1,608건.**
- `MOST_STOCK` 만 켜면: **216 → 2,702.** 보장 축은 그대로 `NONE` 인데도 그렇다.
- 제일 많은 조합: **랜덤뒤교체 + 금지 + 재고많은것 = 2,945** — 세트 가능자 전원이다.
- 중복 금지: 세트는 1,608 → 1,785 로 늘고 **못 준 장수가 3,992 → 12,875(약 3배)** 가 된다.
- 왜 `SET_FIRST` 가 `SWAP_AFTER` 보다 세트가 적은가: `SET_FIRST` 는 **종류 목록 순서대로** 깔기 때문에, 3장 산 사람에게도 늘 A·B·C 를 준다.\
  구매자의 70%가 1~4장을 사는 자료라서 **앞쪽 종류(A~D)가 먼저 마른다.**\
  그러면 뒤에 오는 큰손이 A·B·C 를 못 받아 세트가 깨진다. (원본에 답 없음 — 내 추론, 코드의 `for (String kind : stock.kinds())` 순서에 근거)
- 위험한 이유: 설정 화면에 "세트 보장 ✔" 을 켜 놓으면 **켠 사람은 그것이 세트를 최대로 만든다고 믿는다.**\
  실제로는 이름이 없는 축(나머지 고르기)이 더 크게 움직인다.\
  이름은 의도를 말할 뿐, **효과는 재봐야 안다.**

#### 6. 측정 — 발견 둘: 뒤 50명

- 뒤 50명의 세트 수: **세 규칙 전부 0.**
- 합계 vs 앞뒤:

```text
 먼저 깔기 기준
   합계로 보면   795 / 2,945  =  27.0 %   ← "27 퍼센트 보장" 으로 보인다
   앞 50 명      795 / 1,488  =  53.4 %
   뒤 50 명        0 / 1,457  =   0.0 %   ← 절벽
```

- 평균이 분포를 가린다: **27%라는 하나의 숫자에는 "절반은 53%, 절반은 0%"라는 절벽이 안 보인다.**\
  27%짜리 복권이 아니라, **줄 앞이냐 뒤냐로 갈리는 절벽**이다.
- 안 나눠 봤다면: "보장률이 27%니 조금만 재고를 늘리면 되겠다"고 판단한다.\
  실제로는 뒤 절반이 **한 명도** 못 받고 있으므로, 고칠 것은 재고 총량이 아니라 **순서·상한 규칙**이다.

> **꼬리 분포(tail)** — 평균 근처가 아니라 끝자락에 몰린 사용자들.\
> 예: 평균 대기 2분이어도 뒤에 선 100명은 20분을 기다린다 — 평균만 보면 그 사람들이 안 보인다.

#### 7. 측정 — 발견 셋: 못 준 장수

```text
 종류당 장수   못 준 장수(세 규칙 전부 동일)   세트(먼저깔기/랜덤뒤교체/보장없음)
  60 장          3,992                         1,608 / 2,303 / 216
  40 장         19,566                         1,051 / 1,564 / 140
  30 장         27,566                           795 / 1,130 / 102
  25 장         31,566                           673 /   940 /  82
```

- "글자 그대로 같다"의 뜻: **보장 규칙은 총 출고량에 아무 영향이 없다.**\
  이유는 중복 허용이기 때문이다 — 재고가 한 장이라도 남아 있으면 누구에게든 줄 수 있으므로, **나간 장수 = min(총 주문, 총 재고)** 가 되어 규칙과 무관해진다. (원본에 답 없음 — 내 추론, `giveOne` 이 재고가 있으면 항상 카드를 준다는 데 근거)
- 보장 규칙이 바꾸는 것: **누가 무엇을 받느냐(분배).**\
  안 바꾸는 것: **몇 장이 나가느냐(총량).**
- "보장을 켜서 재고가 모자란다"가 틀린 이유: 켜든 끄든 못 준 장수가 **똑같이 3,992**다.\
  모자란 것은 **재고**다 — 60장→25장으로 줄이면 3,992 → 31,566 으로 8배가 된다.
- 중복 금지는 왜 다른가: 중복 금지에서는 **재고가 남아 있어도 그 사람에게는 줄 수가 없다.**\
  5종 20장인데 8장 산 사람은 5장만 받고 3장이 부족하다(재고는 90장 넘게 남아 있다).\
  그래서 중복 축은 총량을 바꾸고, 보장 축은 안 바꾼다.

#### 8. 측정 — 발견 넷: 큰손이 없는 자료

```text
 전부 1~4 장만 사는 자료, 8 종
   세트 가능자   열두 조합 전부 0   (아무도 8 장을 안 샀다)
   못 준 장수    열두 조합 전부 0   (재고가 넉넉하다)
   중복 장수     보장없음 + 허용 + 무작위 에서만 2,925, 나머지 열한 조합은 0
```

- 여전히 바꾸는 것: **세트를 못 만드는 사람이 받는 카드의 구성**(중복이 섞이느냐 전부 다른 종류냐).
- 네 장 + `SET_FIRST`: **A B C D** 를 준다(종류 목록 순서대로 한 장씩).
- 중복이 0이 아닌 조합이 하나뿐인 이유: 나머지 열한 조합은 전부 **중복이 생길 길을 막고 있다.**
  - `SET_FIRST`·`SWAP_AFTER` — 서로 다른 종류를 먼저 깔거나 나중에 바꿔준다.
  - `NO_DUPLICATE` — 애초에 같은 종류를 두 번 안 준다.
  - `MOST_STOCK` — 한 장 주면 그 종류 재고가 1 줄어 다음 차례엔 다른 종류가 1등이 된다.\
    8종 60장에서 4장을 사면 A·B·C·D 로 돌아가며 뽑혀 중복이 안 생긴다. (내 추론 — 코드의 정렬 기준에 근거)
  - 남는 것은 **보장없음 + 허용 + 무작위** 하나뿐이고, 거기서만 2,925장의 중복이 나온다.
- "이름만 봐서는 알 수 없다": `SetGuarantee` 라는 이름은 **"세트"** 에 관한 설정처럼 들린다.\
  그런데 세트가 원천적으로 불가능한 사람들에게도 이 설정이 받는 카드를 바꾼다.\
  이름이 **적용 범위를 좁게 말하고 있는** 셈이다.

#### 9. 함정

- 넷:
  1. **재고가 같을 때 순서를 안 가르는 것** — 같은 seed 로도 다른 배분이 나와, "왜 나만 중복이냐"는 문의에 다시 돌려 보여줄 수 없다.
  2. **줄 수 있는 종류가 없는데 주는 것** — 재고가 음수가 되거나 중복 금지가 깨진다.
  3. **바꿀 중복이나 바꿀 재고 없이 교체하는 것** — 둘 중 하나만 없어도 세트가 안 된다.
  4. **종류보다 적게 산 사람을 보장률 분모에 넣는 것** — 보장이 안 지켜지는 것처럼 보인다.
- 못 하게 되는 것: **재현**이다. 고객의 배분을 다시 만들어 보여줄 수 없으니, 설명도 반박도 못 한다.
- 깨지는 불변식 둘: **"재고는 음수가 아니다"** 와 **"중복 금지면 한 사람에게 같은 종류가 두 번 안 간다."**
- 분모에 넣으면: 분모가 커지므로 보장률이 **실제보다 낮게** 나온다.\
  5종에 a=5·b=3·c=5 면 2/2(100%)여야 할 것이 2/3(67%)으로 보인다.

#### 10. 변종 검증에서 고친 것

- 죽은 코드: `completeSets` 의 **수량 필터**(`quantity < kindCount` 면 건너뛰기).\
  지워도 통과한 이유는 4번에서 본 대로 — 적게 산 사람은 받은 종류도 적어 `== kindCount` 에서 저절로 떨어진다.\
  지우고 **왜 없어도 되는지를 주석으로 남겼다.**
- 약한 테스트: **`MOST_STOCK` 의 타이브레이커**.\
  지워도 통과했는데, 테스트가 재고를 `Map.of` 로 만들어서 순회 순서가 **우연히** 맞았기 때문이다.
- 바꾼 것: **넣은 순서를 지키는 재고**(`LinkedHashMap` 으로 C, A, B 순서)로 바꾸니 잡혔다.\
  타이브레이커가 있으면 순서가 C,A,B 여도 **A** 가 나오고, 없으면 **C** 가 나온다.

> **변종 검증(mutation testing)** — 코드의 한 줄을 일부러 망가뜨리거나 지우고, 테스트가 그것을 잡는지 보는 것.\
> 예: 타이브레이커 두 줄을 지웠는데 전부 통과하면, 그 줄은 죽은 코드이거나 테스트가 약한 것이다.

- 두 가지 가능성: ① **그 코드가 정말 필요 없다**(죽은 코드) ② **테스트가 그 동작을 안 보고 있다**(약한 테스트).\
  둘을 가르려면 **그 코드가 없을 때 달라져야 할 입력**을 직접 만들어 봐야 한다 — 여기서는 순서가 뒤섞인 재고가 그 입력이었다.

#### 11. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조·측정치에 근거한 내 추론이다.)*

- 몇 번째까지 보장하나: 지금 코드에는 **그런 개념이 아예 없다.** 재고가 마르면 자동으로 끝난다.\
  넣으려면 `Stock` 위에 "보장 전용 재고"를 따로 떼어 두고(예: 종류마다 N장은 보장용으로 예약), 예약분이 바닥나면 보장을 끄는 식이 된다.\
  공개 여부는 신뢰의 문제다 — 측정치가 말하듯 뒤 절반은 **0%** 이므로, 공개하지 않으면 "보장"이라는 말이 뒤쪽 구매자에게는 사실과 다르다. (원본에 답 없음 — 내 추론)
- 재고 편성을 누가 정하나: 코드상 `Stock` 생성자 인자이므로 **`Distributor` 밖의 누군가**다.\
  그런데 발견 셋이 보여주듯 **못 준 장수는 재고 총량이 정하고**, 발견 둘이 보여주듯 **보장률도 재고가 정한다.**\
  즉 "보장 정책"을 정하는 사람과 "재고 편성"을 정하는 사람이 다르면, **정책 담당자가 자기가 약속한 숫자를 통제하지 못한다.** (원본에 답 없음 — 내 추론)
- 못 준 장수의 처리: 코드는 `shortage` 라는 **숫자만 돌려주고 아무 처리도 안 한다.**\
  즉 이 결정은 의도적으로 도메인 밖에 있다 — 환불이든 다음 회차든 **상위 계층(주문·결제)** 의 일이다.\
  다만 중복 금지에서는 12,875장이라 규모가 커서, "정책을 켜기 전에 이 숫자를 먼저 재보라"는 것이 이 챕터의 함의다. (원본에 답 없음 — 내 추론)
- 뒤에 산 사람에게 같은 확률을 주려면: **순서대로 처리하는 방식 자체를 버려야 한다.**\
  두 방향이 있다 — ① **모든 주문을 모은 뒤 한꺼번에 배분**(추첨식: 재고를 균등하게 쪼개 나눈다) ② **1인당 상한**을 두어 앞사람이 재고를 다 못 가져가게 막는다.\
  지금 구조에서는 ②가 더 작은 변경이다(`distribute` 루프 안에서 `quantity` 를 깎으면 된다). (원본에 답 없음 — 내 추론)

#### 12. 연결

- `seed` 재현 가능성: 실무의 **결정적 재현(deterministic replay)** 과 같다 — 로그에 입력과 seed 만 남기면 사고 당시를 그대로 다시 만든다.\
  A/B 배정(27번 박스)에서 "해시로 배정해 같은 사람은 늘 같은 그룹"과 뿌리가 같다.
- 분모 정의: **19-leaderboard-recount**(누구를 순위에 넣나), **21-throttle**(허용률의 분모가 무엇인가) 과 같은 자리다.\
  분자를 고치는 것보다 **분모를 잘못 정하는 것**이 더 크게 틀린다.
- 조합 전수 측정: **01-parking-fee** 가 `FeePolicy` 값으로 두 해석을 돌려 갈리는 건수를 센 것과 같은 방식이다.\
  거기서는 축이 둘이라 2×2였고, 여기서는 셋이라 3×2×2=12다.
