### A. 과제

#### 0. 규칙 한 줄이 안 말해주는 것

- 안 말해주는 결정 셋: **① 하루를 어떻게 세나(달력일/영업일) ② 면책 기간을 빼나(전부/남 탓만/안 뺌) ③ 상한을 어디에 거나(주문 금액/배송비).**
- 조합 수: **2 × 3 × 2 = 열두 개.**
- 같은 배송인데 배상금이 **0원과 100,000원 사이 어디든** 될 수 있다(측정: 금액 폭 최대 100,000원).
- enum 으로 안 올리면: 세 선택이 코드 안에 숨어 **"어느 규칙으로 계산했는지"를 나중에 못 찾는다.**\
  그리고 두 판을 나란히 못 돌려서 **차이가 몇 배인지(주문 기준의 16.1%)를 숫자로 볼 수 없다.**
- "최대 10 퍼센트"가 무엇의 10퍼센트인지 안 정하는 이유: 규칙 문장이 **앞의 "주문 금액의 0.5 퍼센트"를 그대로 이어받는 것처럼 읽히지만**, 배송 지연 배상에서 "배송비의 몇 배"도 똑같이 흔한 관행이다.\
  **둘 다 한 줄이고 둘 다 그럴듯하다**(README 원문) — 그래서 문장만으로는 못 고른다.

#### 1. TODO 1 — delayedDays

정답 코드 (impl/DelayCompensation.java):

```java
List<LocalDate> days = new ArrayList<>();
LocalDate at = delivery.promisedOn().plusDays(1);
while (!at.isAfter(delivery.deliveredOn())) {
    days.add(at);
    at = at.plusDays(1);
}
return days;
```

- 약속일 당일을 안 세는 이유: **그날은 아직 안 늦었다.** 약속일에 받으면 지연 0이다.
- 도착일을 세는 이유: **그날 받았어도 늦게 받은 것**이다.
- 손계산:

```text
 약속 3/10, 도착 3/10   →  3/11 부터 시작해서 이미 3/10 을 지났다  →  0 일
 약속 3/10, 도착 3/11   →  3/11 하나                              →  1 일
 약속 3/10, 도착 3/25   →  3/11 ~ 3/25                            →  15 일
```

- 양쪽을 다 세면: **하루가 부푼다**(3/10~3/25 가 16일이 된다) — 배상금이 2,500원 는다.
- 양쪽을 다 빼면: **하루가 준다**(14일) — 배상금이 2,500원 줄고, 하루 늦은 배송은 아예 0원이 된다.

> **반열림 구간(half-open interval)** — 시작은 포함하고 끝은 안 포함하는 구간. `[시작, 끝)` 으로 쓴다.\
> 예: "3/11 부터 3/25 까지"를 반열림으로 잡으면 3/25 가 빠져서 14일이 된다. 이 박스는 **양끝 포함**을 골랐다.

- 일찍 도착하면: `promisedOn + 1` 이 이미 `deliveredOn` 보다 뒤라 **루프가 한 바퀴도 안 돈다** → 빈 목록 → 0원.
- 목록을 돌려주는 이유: 뒤에서 **날마다 "주말인가", "면책인가"를 따져야** 하기 때문이다.\
  숫자 15만 있으면 그 15일 중 어느 날이 토요일인지 알 수가 없다.

#### 2. TODO 2 — excused

정답 코드:

```java
Excuse excuse = delivery.excuseOn(date);
if (excuse == null) {
    return false;
}
return switch (policy) {
    case DEDUCT_ALL -> true;
    case DEDUCT_NOT_OURS ->
            excuse.fault() == Fault.BUYER || excuse.fault() == Fault.FORCE_MAJEURE;
    case DEDUCT_NONE -> false;
};
```

- 세 정책: **① 전부 뺀다** — 사유 불문 **② 남 탓만 뺀다** — 구매자(BUYER)와 천재지변(FORCE_MAJEURE)만, 판매자·택배사는 안 뺀다 **③ 안 뺀다** — 늦은 것은 늦은 것이다.
- 택배사 탓: 이 코드는 **우리 쪽으로 본다**(안 뺀다).
- 근거: **"택배사는 남이지만 소비자에게는 우리 쪽이다"**(테스트 주석 원문).\
  소비자가 계약한 상대는 판매자이지 택배사가 아니다.

```text
 표본(면책 5일: 천재지변 3/14~16, 구매자 3/20, 택배사 3/23), 달력일 15일 기준

 전부 뺀다     5일 빠짐  →  세는 날 10  →  25,000 원
 남 탓만 뺀다  4일 빠짐  →  세는 날 11  →  27,500 원   ← 3/23(택배사)만 안 빠진다
 안 뺀다       0일 빠짐  →  세는 날 15  →  37,500 원
```

- 제일 흔한 "남 탓만 뺀다"가 문구로 적기 어려운 이유: **사유를 하나하나 나열해야 한다.**\
  "전부"나 "없음"은 한 단어로 되지만, 중간값은 "천재지변과 구매자 귀책은 제외하고, 판매자와 택배사 귀책은 제외하지 않는다"처럼 목록이 된다.\
  그래서 사유를 `Fault` enum 으로 모델링했다 — 나열해야 하는 것은 타입으로 만든다.
- 양끝 포함으로 잡은 이유: **운영자가 매번 맞게 못 쓴다**(원본 javadoc 원문).\
  반열림이면 "3월 12일 하루"를 적을 때 끝을 3월 **13일**로 써야 한다 — 하루 쓰는데 이틀을 적는 셈이라 실수가 난다.

> **양끝 포함 구간(closed interval)** — 시작일과 종료일이 둘 다 기간 안에 드는 구간.\
> 예: `Excuse(3/14, 3/16)` 은 3/14·3/15·3/16 사흘이다. "3/12 하루"는 `(3/12, 3/12)` 로 적는다.

- 겹치면: **먼저 적힌 것**을 쓴다(`excuseOn` 이 목록을 앞에서부터 훑어 첫 매치를 돌려준다).
- 면책 없는 배송으로 시험하면: **세 정책이 전부 같은 답**을 낸다(15일).\
  그리고 **예제에는 면책이 잘 안 들어간다 — 이야기가 복잡해지니까**(테스트 주석 원문).

#### 3. TODO 3 — cap

정답 코드:

```java
return switch (basis) {
    case ORDER_AMOUNT -> BigDecimal.valueOf(delivery.orderAmount())
            .multiply(orderCapRate)          // 0.10
            .setScale(0, RoundingMode.HALF_UP)
            .longValueExact();
    case SHIPPING_FEE -> delivery.shippingFee() * shippingFeeMultiple;   // × 3
};
```

- 두 식: **주문 금액 × 10%** / **배송비 × 3**.
- 주문 500,000 배송비 3,000일 때: **50,000원** / **9,000원**.
- 주문 기준이 언제나 20일인 이유: **비율끼리 나누므로 금액이 지워진다.**

```text
 상한에 닿는 날 = 상한 ÷ 하루치
               = (주문금액 × 0.10) ÷ (주문금액 × 0.005)
               =            0.10  ÷            0.005        ← 주문금액이 약분돼 사라진다
               = 20 일    (금액이 얼마든 똑같다)
```

- 배송비 기준에서 비쌀수록 빨리 닿는 이유: **상한은 배송비로 고정인데 하루치는 주문 금액에 비례**해서 커진다.

```text
 배송비 3,000 → 상한 9,000 (고정)

 주문   100,000   하루치   500   →  9,000 ÷   500 = 18 일
 주문   500,000   하루치 2,500   →  9,000 ÷ 2,500 =  3.6  →  4 일 (올림)
 주문 1,000,000   하루치 5,000   →  9,000 ÷ 5,000 =  1.8  →  2 일 (올림)

 100만 원짜리를 열흘 늦게 받아도  →  9,000 원   (주문 기준이면 50,000 원)
```

- 무료 배송 + 배송비 기준: **3배도 0이라 배상금이 0원**이 된다.\
  날은 15일을 세는데(`chargeableDays == 15`) 금액만 0이고, `capped` 는 **참**이다.
- 요즘 배송이 대개 무료라는 사실: **"배송비의 세 배"라는 규칙이 대부분의 주문에서 아무것도 안 주게 된다.**\
  즉 예외 케이스가 아니라 **기본 케이스**가 0원이다.

#### 4. TODO 4 — compensate

정답 코드:

```java
List<LocalDate> days = delayedDays(delivery);
int raw = days.size();

int counted = 0;
int chargeable = 0;
for (LocalDate day : days) {
    if (dayCount == DayCount.BUSINESS && weekend(day)) {
        continue;                      // 주말이면 여기서 끝 — 면책 판정에 안 들어간다
    }
    counted++;
    if (!excused(delivery, day, policy)) {
        chargeable++;
    }
}

long cap = cap(delivery, capBasis);
long raw2 = BigDecimal.valueOf(delivery.orderAmount())
        .multiply(dailyRate)
        .multiply(BigDecimal.valueOf(chargeable))
        .setScale(0, RoundingMode.HALF_UP)
        .longValueExact();
long amount = Math.min(raw2, cap);

return new Compensation(raw, counted, chargeable, amount, cap, raw2 > cap);
```

- 상한을 날 수에 걸면: **상한에 닿은 뒤로도 날짜가 늘 때 금액이 계속 같은 것이 안 보인다.**\
  날을 20일로 잘라놓으면 "30일 늦었는데 20일치만 받았다"가 아니라 "20일 늦었다"로 기록돼 **사실이 왜곡된다.**
- 금액에 걸어야 `capped` 가 사실이 되는 이유: `capped` 는 "원래 받을 금액이 상한을 넘어서 잘렸다"는 뜻이다.\
  날에 걸면 잘린 뒤의 금액끼리 비교하게 되어 **언제나 `raw2 == cap` 이 되고 `capped` 를 판정할 수가 없다.**
- 두 번 안 빼려면: **주말이면 `continue` 로 그 날을 아예 건너뛴다.**\
  그러면 면책 판정에 들어가지도 않으므로 **한 날이 한 번만 빠진다.**

```text
 표본, 영업일 + 전부 빼기

 raw        3/11 ~ 3/25                               15 일
  ↓ 주말 제외  (3/14 토, 3/15 일, 3/21 토, 3/22 일)
 counted                                              11 일
  ↓ 면책 제외  (3/16 천재지변 · 3/20 구매자 · 3/23 택배사)
 chargeable                                            8 일  →  20,000 원

 ※ 3/14·3/15 는 천재지변이면서 주말이다 — 주말에서 이미 빠졌으므로 면책에서 또 안 뺀다
```

- 두 번 빼면: 면책 5일을 통째로 또 빼서 **8이어야 할 것이 6이 된다**(11 - 5) → 20,000원이 15,000원이 된다.
- 세 날 수를 다 들고 있는 이유: **"왜 이 금액이냐"를 단계별로 설명할 수 있어야 배상이기 때문**이다.\
  고객에게 "15일 늦었지만 주말 4일을 빼고 11일, 거기서 면책 3일을 빼 8일치입니다"라고 말할 수 있다.\
  최종 금액만 남기면 그 설명을 다시 만들어 내야 한다.

> **중간 결과를 남기기(traceability)** — 최종 답만이 아니라 거기 이르는 단계를 같이 돌려주는 설계.\
> 예: `Compensation` 이 15 → 11 → 8 을 다 담고 있어서, 고객 문의가 오면 어느 단계에서 며칠이 빠졌는지 바로 답할 수 있다.

- 금액은 **`chargeableDays`**(마지막 것)에만 곱한다.
- 순서: **주문금액 × 일할배상률 × 날 수를 다 곱한 뒤 마지막에 한 번 반올림**한다.\
  하루치를 먼저 반올림해서 곱하면 그 오차가 날 수만큼 커진다.

### B. 개념

#### 5. 함정 (README)

- 넷: ① **약속일 당일을 세는 것**(그날은 아직 안 늦었고 도착일은 세야 한다) ② **면책과 주말을 두 번 빼는 것**(영업일로 세면 주말은 이미 빠져 있다) ③ **상한을 날 수에 거는 것**(금액에 걸어야 "상한에 걸렸다"가 사실이 된다) ④ **무료 배송에서 배송비 기준 상한을 쓰는 것**(3배도 0이라 배상금이 0원이 된다).
- ②가 눈에 안 띄는 이유: **두 필터가 각각은 맞다.** 주말을 빼는 것도 맞고 면책을 빼는 것도 맞다.\
  틀리는 것은 **겹치는 날**뿐인데, 겹치려면 "면책 기간에 주말이 껴 있는 배송"을 시험해야 한다 — 짧은 예제에는 그런 날이 안 생긴다.\
  게다가 결과가 예외가 아니라 **그럴듯한 숫자**(8이 아니라 6)라서 보고도 모른다.
- 무료 배송 + 배송비 기준에서 `capped` 는 **참**이다 — 원 배상금 37,500이 상한 0을 넘었으니 잘린 것이 맞다.\
  날은 15일을 세는데 돈이 0원이고, 그 사실이 `capped=true`로 정직하게 기록된다.

#### 6. 측정 — 답이 갈리는 건수

- 배송 5,000건, 열두 조합:

```text
 금액이 갈린 건    4,748 / 5,000   (95 %)
 전부 같은 건        252           (그중 165 건이 지연 0 일)
 금액 폭 평균     28,902 원
 금액 폭 최대    100,000 원
```

- 배송비 기준 총액: **23,995,250 / 148,832,050 = 16.1 %** — **여섯 배가 넘게 차이** 난다.
- 문구로 구별이 안 되는 이유: **둘 다 한 줄이고 둘 다 그럴듯하다.**\
  "주문 금액의 10 퍼센트"도, "배송비의 세 배"도 배상 규정에 실제로 쓰이는 문장이다.
- 배송비 기준 상한 도달일: 10만 **18일** / 50만 **4일** / 100만 **2일**(주문 기준은 셋 다 20일).
- 100만 원짜리를 열흘 늦게: 배송비 기준 **9,000원**, 주문 기준 **50,000원**.
- 영업일 총액: **116,526,650 / 148,832,050 = 78.3 %.**
- 71 퍼센트보다 덜 주는 이유: **상한에 걸린 건이 1,481건(30%)** 이라, 그 건들은 **날을 덜 세도 금액이 같다.**\
  이미 상한에 붙어 있는 배송은 15일이든 11일이든 똑같이 상한 금액을 받는다 — 규칙 둘이 서로 간섭한다.

```text
 지연 30일, 주문 500,000, 주문 기준 상한 50,000

 달력일 30일 → 원 배상 75,000 → 상한 50,000
 영업일 22일 → 원 배상 55,000 → 상한 50,000     ← 날을 8일 덜 셌는데 금액은 같다
```

- 면책 세 정책의 총액:

```text
 전부 뺀다      148,832,050
 남 탓만 뺀다   158,362,650
 안 뺀다        167,548,050

 폭  (167,548,050 - 148,832,050) / 148,832,050 = 12.6 %
```

- 짧고 깔끔한 예제(3/10 화 ~ 3/13 금, 면책 없음, 50만 원): **열두 조합이 전부 7,500원**이다.

```text
 주말이 안 낀다     →  달력일과 영업일이 둘 다 3 일
 면책이 없다        →  세 정책이 전부 3 일
 상한에 안 닿는다   →  두 기준이 전부 7,500 원 그대로

                       3 × 2,500 = 7,500 원   (열두 조합 한 값)
```

- 예제가 대개 그렇게 생긴 것이 문제인 이유: **세 결정 중 하나도 안 드러난다.**\
  테스트가 통과하고 시연이 잘 되고 리뷰도 지나가는데, 정작 **정해야 할 셋을 아무도 안 정한 채** 배포된다.

> **가려진 갈림(masking)** — 시험 입력이 쉬운 쪽에 쏠려서, 실제로는 갈리는 결정이 안 갈리는 것처럼 보이는 것.\
> 예: 사흘짜리 지연·면책 없음·상한 미달이면 열두 조합이 한 값(7,500원)으로 뭉친다.

#### 7. 변종 검증에서 고친 것

- 지운 것: `daysToCap` 의 **`배상률 == 0 || 주문 금액 == 0` 가드.**
- 지워도 되는 이유: 바로 아래에 **`하루치 배상금 == 0`** 검사가 있고, **배상률이 0이든 주문 금액이 0이든 하루치가 0이 된다.**

```text
 하루치 = 주문 금액 × 배상률

 주문 금액 0  →  0 × 0.005 = 0   ← 하루치 0
 배상률   0  →  500,000 × 0 = 0  ← 하루치 0

 그 한 조건(perDay.signum() == 0)이 두 경우를 다 덮는다
```

- "가드가 많은 게 아니라 정확한 게 안전": 겹치는 가드는 **안전을 안 늘리면서 읽는 사람을 헷갈리게 한다.**\
  앞 가드를 보고 "여기가 0 처리 자리구나" 싶은데 실제 판정은 아래에서 또 한다 — 나중에 한쪽만 고치면 둘이 어긋난다.\
  덮는 범위가 넓은 조건 하나로 줄이는 쪽이 **바꿀 자리가 하나**라서 안전하다.

#### 8. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 겹치는 면책: 이 코드는 **먼저 적힌 것**을 쓴다(`excuseOn` 의 첫 매치). 그런데 그것은 **운영자가 입력한 순서**에 결과가 달린다는 뜻이다 — 같은 사실을 다른 순서로 넣으면 배상금이 달라진다.\
  "가장 유리한 것"(= 면책으로 인정되기 쉬운 사유)을 고르는 쪽이 결과가 입력 순서에 안 흔들려 낫지만, **누구에게 유리한지**를 또 정해야 한다.\
  어느 쪽이든 **지금 구현은 "먼저 적힌 것"이라는 선택을 코드에 숨기고 있다** — 이것도 enum 으로 올릴 만한 자리다. (원본에 근거 없음 — 내 추론)
- 두 상한 중 큰 쪽: **배송비 기준이 사실상 무의미해진다.** 배송비 3,000원의 3배(9,000)가 주문 10%보다 큰 것은 주문이 90,000원 미만일 때뿐이다.\
  즉 싼 주문에서만 배송비 기준이 이기고, 나머지는 전부 주문 기준이 된다 — 측정의 16.1%가 100% 가까이로 뛴다.\
  고객에게는 제일 유리하고, 그래서 **규칙이 단순해 보이지만 비용은 제일 크다.** (원본에 근거 없음 — 내 추론)
- 공휴일: **영업일로 보면 안 되는데 이 코드는 주말만 뺀다**(`weekend` 가 토·일만 본다).\
  목록은 코드 밖에 둬야 한다 — 해마다 바뀌고 나라마다 다르니 배포 없이 갱신할 수 있어야 한다.\
  구조적으로는 `DayCount` enum 이 아니라 **"이 날이 영업일인가"를 답하는 달력 객체**를 주입받는 쪽이 맞다 — 그러면 주말·공휴일·회사 휴무를 한 자리에서 판정한다. (원본에 근거 없음 — 내 추론)
- 현금이냐 포인트냐: **포인트면 상한 논의가 느슨해진다.** 포인트는 우리 가게에서만 쓰이고 일부는 안 쓰이고 사라지므로 실제 비용이 액면보다 작다.\
  그래서 "배송비의 3배" 같은 빡빡한 상한을 고집할 이유가 줄고, 주문 기준으로 가기 쉬워진다.\
  대신 소비자분쟁해결기준 같은 법적 기준은 대개 **현금 상당**을 전제하므로, 포인트로 준다는 선택이 **규정 충족 여부**라는 다른 문제를 만든다. (원본에 근거 없음 — 내 추론)

#### 9. 연결

- "구간의 양끝을 세나": **01-parking-fee**("10분까지"가 10분을 포함하나)와 같은 자리다.\
  여기서는 약속일(시작)은 빼고 도착일(끝)은 넣는 **비대칭** 구간이라 한 걸음 더 간다.
- "예제가 쉬워서 갈림이 숨는다" 패턴:

```text
 06-tax          과세 상품만 담은 주문  →  1,955 건 중 부가세 갈림  0 건
 07-installment  무이자·나누어떨어지는 금액·3개월  →  아홉 조합이 한 값
 08-delay        사흘·주말 없음·면책 없음  →  열두 조합이 전부 7,500 원
```

  셋 다 **"쉬워서 고른 예제"가 곧 "갈림이 안 보이는 예제"** 라는 같은 구조다.

- `Compensation` 의 중간 단계 보존: 실무의 **감사 로그(audit trail)** · **계산 근거 스냅샷**과 같다.\
  고객 문의·분쟁·정산 대사에서 "왜 이 금액인가"를 재현해야 하는 곳은 전부 이 모양이 된다 — 16-audit-replay 가 그 주제를 통째로 다룬다.
