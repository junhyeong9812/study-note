### A. 과제

#### 0. 그림 한 장이 말하는 것

- 재고와 다른 점: **좌석은 개수가 아니라 이름과 위치가 있다.**\
  재고 6개는 그냥 6개지만, 좌석 6개는 "어디에 어떻게 흩어져 있는가"에 따라 팔 수 있는 것이 달라진다.
- 못 파는 이유:

```text
    A1 A2 A3 | A4 A5        ■ = 잡힘, · = 빈자리
    B1 B2 B3 | B4 B5        A:  ■ ■ ■ · ·
    C1 C2 C3 | C4 C5        B:  ■ ■ ■ · ·
                            C:  ■ ■ ■ · ·
  빈자리 6개인데 붙은 덩어리는 전부 2짜리 — 최장 연석 = 2
  그래서 3인 일행은 못 받는다
```

- 안 들어 있는 결정 셋(원본 javadoc):

```text
 붙어 있어야 하나   못 붙이면 거절인가 흩어서라도 주나   → Adjacency
 어디를 고르나      앞에서부터인가 딱 맞는 자리인가       → Fit
 만료를 언제 푸나   조회할 때인가 배치가 돌 때인가        → ExpiryCheck
```

- 둘을 따로 재는 이유: **빈자리 수는 "얼마나 남았나"이고 최장 연석은 "무엇을 팔 수 있나"다.**\
  테스트가 같은 상태에서 `freeCount == 6` 과 `longestRun == 2` 를 나란히 못 박았다.
- enum 으로 안 올리면: 세 규칙을 나란히 돌려 **판매량 차이를 잴 수 없다.**\
  측정에서 연석 요구의 비용이 무리 구성에 따라 +1 %에서 +42 %까지 벌어졌다 — 재보기 전에는 그게 큰지 작은지 모른다.

#### 1. TODO 1 — free

정답 코드 (impl/SeatAllocator.java):

```java
Instant until = heldUntil.get(seat);
if (until == null) {
    return true;
}
return check == ExpiryCheck.LAZY && !at.isBefore(until);
```

- 한 번도 안 잡힌 좌석: `heldUntil.get(seat)` 이 **null** 이고, 그때 답은 **true(비었다)**.
- 조건식:

```text
 LAZY    at >= until 이면 비었다      →  !at.isBefore(until)
 SWEEP   무조건 안 비었다             →  false (앞의 && 에서 끊긴다)
```

- 만료 정각: **이미 비어 있다**(`!at.isBefore(until)` 이 `at == until` 에서 true).\
  테스트가 못 박았다 — 1초 전에는 `freeCount == 0`, 정각에는 `freeCount == 3`.
- `Boundary` enum 이 없는 이유: **이 챕터가 그 결정을 하나로 고정했기 때문**이다.\
  11번에서 그 축을 이미 재봤고(11초 중 1초만 갈린다), 여기서 재고 싶은 것은 연석과 fit 이다. 스위치를 셋보다 늘리면 조합이 폭발한다.
- SWEEP 이 만료를 아예 안 보는 뜻: **"만료됐다"는 사실이 이 함수에서는 아무 힘이 없다.**\
  배치가 `heldUntil` 에서 실제로 지워줘야만 비는데, 그러면 위의 `until == null` 로 빠진다. 즉 SWEEP 에서 좌석을 비우는 것은 시간이 아니라 `sweep()` 호출이다.

#### 2. TODO 2 — findRun

정답 코드:

```java
List<String> best = List.of();
int bestSlack = Integer.MAX_VALUE;

for (String row : map.rows()) {
    int runStart = -1;
    for (int n = 1; n <= map.seatsPerRow() + 1; n++) {
        boolean open = n <= map.seatsPerRow() && free(row + n, at, check);
        if (open) {
            if (runStart < 0) {
                runStart = n;
            }
            continue;
        }
        if (runStart < 0) {
            continue;
        }
        int runLength = n - runStart;
        if (runLength >= size) {
            List<String> candidate = new ArrayList<>();
            for (int k = 0; k < size; k++) {
                candidate.add(row + (runStart + k));
            }
            if (fit == Fit.FIRST_FIT) {
                return candidate;
            }
            int slack = runLength - size;
            if (slack < bestSlack) {
                bestSlack = slack;
                best = candidate;
            }
        }
        runStart = -1;
    }
}
return best;
```

- 한 칸 더 도는 이유: **열 끝까지 이어진 연석을 닫아주기 위해서**다.\
  연석은 "막히는 자리"를 만나야 길이가 확정되는데, 마지막 좌석까지 비어 있으면 막히는 자리가 없다. `n = seatsPerRow + 1` 은 `open = false` 가 되는 가상의 벽이다.

> **보초값(sentinel)** — 반복문 끝에서 같은 처리를 한 번 더 시키려고 일부러 두는 가짜 값.\
> 예: 5석짜리 열에서 n=6 은 실제 좌석이 아니지만, "여기서 연석이 끝났다"를 알려주는 벽 노릇을 한다.

- 안 돌면: **열 끝에 붙은 연석이 통째로 안 보인다.**\
  빈 극장(A1~A5 전부 빔)에서 `A1 A2 A3` 를 못 찾고 빈 목록을 돌려준다.
- 연석 길이: `runLength = n - runStart`.\
  예: runStart=1 이고 n=6 에서 끊기면 길이 5다(1,2,3,4,5).
- FIRST_FIT 이 바로 반환할 수 있는 이유: **"처음 맞는 자리"가 곧 답**이라 뒤를 더 볼 필요가 없다.\
  열 순서·번호 순서로 훑으므로 처음 만난 후보가 제일 앞이다.
- `slack` = **연석 길이 − 요청 인원**, 즉 **쓰고 남는 칸 수**다.

```text
 5짜리 덩어리에 3명   slack = 5 - 3 = 2   ← 2칸이 어중간하게 남는다
 3짜리 덩어리에 3명   slack = 3 - 3 = 0   ← 딱 맞는다

 slack 이 작은 자리를 고르면 큰 덩어리가 통째로 보존된다
```

- `slack` 동점이면: **먼저 찾은 쪽이 남는다**(`slack < bestSlack` 이 엄격한 부등호다).\
  열 순서·번호 순서로 훑으므로 앞쪽 자리가 이긴다.
- 열을 넘겨 이어붙이면 안 되는 이유: **A5 와 B1 사이에는 통로가 있다.**\
  번호가 이어진다고 옆자리가 아니다 — 이어붙이면 통로 건너 앉은 일행을 "붙었다"고 팔게 된다.

#### 3. TODO 3 — hold

정답 코드:

```java
if (size <= 0) {
    throw new IllegalArgumentException("인원이 0 이하다: " + size);
}
if (owner.containsValue(groupId)) {
    throw new IllegalArgumentException("이미 잡은 무리다: " + groupId);
}

List<String> seats = findRun(size, at, fit, check);
boolean together = !seats.isEmpty();

if (seats.isEmpty() && adjacency != Adjacency.REQUIRE_TOGETHER) {
    seats = findAny(size, at, check);
}

// 못 찾았으면 아래 반복문이 한 번도 안 돌아 빈 결과가 그대로 나간다.
Instant until = at.plus(ttl);
for (String seat : seats) {
    owner.put(seat, groupId);
    heldUntil.put(seat, until);
}
return new Hold(groupId, seats, together);
```

- 붙은 자리를 먼저 찾는 이유: **찾자마자 흩어 주면 붙을 수 있는 무리까지 떨어뜨린다.**\
  테스트가 세 Adjacency 모두 빈 극장에서 `A1 A2 A3` 를 주는 것으로 못 박았다.
- `together` 는 **`findRun` 직후에 정해진다.**\
  흩어서 받은 좌석이 우연히 붙어 있어도 `together` 는 false 다 — "붙여 달라고 해서 붙여줬다"와 "흩어 받았는데 마침 붙었다"를 구별한다.
- ALLOW_SPLIT 과 PREFER_TOGETHER 는 **이 코드에서 구별되지 않는다.**\
  둘 다 `!= REQUIRE_TOGETHER` 로 같은 갈래를 탄다. enum 이름만 다르고 동작은 같은데, 이름을 둘 다 남긴 것은 **요구사항에서 쓰는 말이 둘이기 때문**이다. (동작이 같다는 사실 자체가 측정 결과 — 판매량이 정확히 같다 — 를 설명한다.)
- 조기 반환을 안 두는 이유: **빈 목록이면 아래 반복문이 한 번도 안 돌아 같은 결과가 그대로 나간다.**\
  따로 `return` 을 두면 **같은 답을 내는 갈래가 둘**이 되고, 나중에 한쪽만 고치는 버그가 생긴다(README 변종 검증 하나).

> **갈래 하나로 모으기** — 결과가 같은 두 경로를 굳이 나누지 않고 한 길로 흐르게 두는 것.\
> 예: "못 찾으면 바로 반환"을 지우면 배정 기록 코드가 한 곳에만 있어서, TTL 계산을 고칠 때 한 군데만 고치면 된다.

- "반쯤 잡아두는 것"이 더 나쁜 이유: **그 좌석이 아무에게도 안 팔린 채 남는다.**\
  손님은 자리를 못 받았는데 좌석은 묶여 있다 — 거절은 적어도 그 자리를 다음 손님에게 준다. 테스트가 못 박았다: 3석짜리 방에서 2인 요청이 거절될 때 `freeCount == 1`, `ownerOf("A3") == null`.
- 같은 무리가 두 번: **`IllegalArgumentException`**(`owner.containsValue(groupId)`).
- 15석에 20명: **세 규칙 모두 거절**이고 `freeCount` 는 15 그대로다.\
  흩어짐을 허락해도 자리 수 자체가 모자라서 `findAny` 도 빈 목록을 준다.

#### 4. TODO 4 — longestRun

정답 코드:

```java
int longest = 0;
for (String row : map.rows()) {
    int run = 0;
    for (int n = 1; n <= map.seatsPerRow(); n++) {
        run = free(row + n, at, check) ? run + 1 : 0;
        longest = Math.max(longest, run);
    }
}
return longest;
```

- 0으로 안 되돌리면: **그냥 빈자리 수를 세게 된다.**\
  `run` 이 계속 누적되므로 "그 열의 빈자리 총합"이 나오고, 붙어 있는지와 무관해진다.
- A2·A4 만 빈 한 열: 정답은 **1**이다(빈자리는 2).

```text
 좌석    A1  A2  A3  A4  A5
 상태     ■   ·   ■   ·   ■
 run      0   1   0   1   0     ← 끊길 때마다 0
 longest  0   1   1   1   1  →  1
 0 으로 안 되돌리면  0 1 1 2 2  →  2 (= 빈자리 수)
```

- 안 잡혔던 이유: **예제의 빈자리가 늘 붙어 있었다.**\
  빈자리가 한 덩어리면 "빈자리 수"와 "최장 연석"이 같은 값이라 둘을 구별할 수 없다. A2·A4 만 비는 경우를 만들어서야 갈렸다(README 변종 검증 셋).
- 단편화를 재는 값인 이유: **빈자리 총량이 같아도 이 값이 작으면 큰 무리를 못 받는다.**\
  이 값 하나로 "지금 받을 수 있는 최대 무리 크기"를 알 수 있다.

#### 5. adjacent

정답 코드(주어짐):

```java
if (seats.size() <= 1) {
    return true;
}
Set<String> rows = new LinkedHashSet<>();
List<Integer> numbers = new ArrayList<>();
for (String seat : seats) {
    rows.add(seat.substring(0, 1));
    numbers.add(Integer.parseInt(seat.substring(1)));
}
if (rows.size() != 1) {
    return false;
}
numbers.sort(Integer::compareTo);
for (int i = 1; i < numbers.size(); i++) {
    if (numbers.get(i) != numbers.get(i - 1) + 1) {
        return false;
    }
}
return true;
```

- 열을 안 보면 틀리는 입력: **번호는 이어지는데 열이 다른 것** — `A1` 과 `B2`.\
  번호가 1,2라 "붙었다"고 답하는데 실제로는 통로 건너 다른 열이다.
- `A5` 와 `B1` 로는 안 잡히는 이유: 번호가 **5와 1**이라 정렬해도 이어지지 않는다.\
  열 검사가 없어도 번호 검사에서 이미 false 가 나온다 — 결함을 덮는 입력이다(README 변종 검증 넷).
- 번호를 정렬하는 이유: **입력 순서를 안 보기 위해서**다.\
  테스트가 `A3, A2, A1` 도 붙은 것으로 못 박았다("순서는 안 본다").
- 0개·1개: **true.** 붙고 말고를 따질 것이 없다 — 혼자 앉은 손님은 언제나 "일행끼리 붙어 앉았다"가 맞다.

### B. 개념

#### 6. 측정 — 연석 요구의 값

10열 x 10석, 300무리 (README 표 그대로):

| 무리 크기 | 붙어야 함 | 흩어져도 됨 | 차이 |
|---|---|---|---|
| 1~2 인 | 261 석 | 264 석 | **+1 %** |
| 1~4 인 | 263 석 | 278 석 | +6 % |
| 3~6 인 | 248 석 | 274 석 | +10 % |
| 5~8 인 | **189 석** | **269 석** | **+42 %** |

- 두 명짜리가 공짜인 이유: **2짜리 연석은 웬만하면 남아 있다.**\
  단편화가 진행돼도 두 칸짜리 틈은 계속 생기므로, 붙여 달라는 요구가 거의 거절을 안 만든다.
- 여덟 명짜리가 섞이면: **42 %를 못 판다**(189 vs 269).
- "손님 구성이 정한다"의 뜻: **같은 코드·같은 정책인데 오는 손님이 달라지면 비용이 달라진다.**\
  정책을 고를 때 보아야 할 것은 정책 자체가 아니라 **우리 손님의 무리 크기 분포**다.
- 영화관과 콘서트장이 다른 이유: 영화관은 1~2인 위주라 연석 보장이 거의 공짜지만, 콘서트·가족 단위 공연은 큰 무리가 섞여 **연석 보장이 판매량을 크게 깎는다.**

#### 7. 측정 — PREFER_TOGETHER

| 무리 크기 | 흩어진 무리 |
|---|---|
| 1~2 인 | 15 |
| 1~4 인 | 23 |
| 3~6 인 | 23 |
| 5~8 인 | 21 |

- 판매량이 ALLOW_SPLIT 과 정확히 같은 것이 중요한 이유: **"붙여 주려는 시도"가 판매량을 전혀 안 깎는다**는 뜻이다.\
  붙은 자리가 있으면 붙여 주고 없으면 흩어 주는데, 어차피 흩어 줄 자리는 그대로 있으므로 잃는 것이 없다.
- "거의 공짜로 둘 다 얻는다"의 근거: **판매량은 최대치(흩어져도 됨)와 같고, 300무리 중 흩어지는 것은 스무 남짓뿐**이다.\
  REQUIRE_TOGETHER 는 판매량을 최대 42 % 깎고, ALLOW_SPLIT 은 붙을 수 있는 무리도 떨어뜨린다 — PREFER_TOGETHER 만 양쪽을 피한다.

#### 8. 측정 — first fit / best fit

| 무리 크기 | 앞에서부터 | 딱 맞는 자리 | 거절 |
|---|---|---|---|
| 1~2 인 | 238 | 241 | 127 (같음) |
| 1~4 인 | 251 | 252 | 180 (같음) |
| 3~6 인 | 238 | 242 | 240 (같음) |
| 5~8 인 | 226 | 226 | 263 (같음) |

- 거절 수는 **아예 같다.** 좌석 수만 1 %쯤 차이가 난다.
- 한 번의 배정:

```text
 A 열 통째로 빔(5), C3 C4 C5 빔(3),  3명이 온다

 FIRST_FIT   A1 A2 A3 을 준다  →  남는 것: A4 A5 / C3 C4 C5   최장 연석 3
 BEST_FIT    C3 C4 C5 를 준다  →  남는 것: A1~A5             최장 연석 5

 다음에 5인 무리가 오면  FIRST_FIT 은 못 받고 BEST_FIT 은 받는다
```

- 한 번은 갈리는데 300번은 안 갈리는 이유: **그 사이에 만료가 계속 일어나 자리가 다시 섞인다.**\
  한 번의 "나쁜 배정"이 남긴 단편화는 몇 분 뒤 홀드가 풀리면서 지워지므로, 300번을 누적하면 서로 상쇄된다.
- 두 말의 차이: 앞의 것은 **한 사례의 최악**이고 뒤의 것은 **분포 전체의 평균**이다.\
  앞의 것만 보고 뒤를 결론 내리면 틀린다 — 여기서는 실제로 틀렸다.
- 교재의 논의를 그대로 가져오면: **없는 문제를 오래 논의하게 된다.**\
  교재의 first fit / best fit 비교는 해제 시점이 임의인 메모리 할당 이야기다. 좌석 예매는 **TTL 때문에 해제 시점이 고르게 흩어져** 단편화가 오래 안 쌓인다.

#### 9. 측정 — 빈 극장

- **무리 20개까지**는 세 규칙이 전부 같다.
- 그 범위에서 거절 **0**, 흩어짐 **0**, 좌석 배정까지 똑같다.
- 문제인 이유: **개발할 때 시험하는 것이 대개 그 범위**다.\
  규칙 선택이 아무 차이도 안 만드는 상태에서 "잘 돌아간다"를 확인하고 배포한 뒤, 매진에 가까운 부하에서 처음 갈린다.

#### 10. 함정 (README)

- 다섯: ① **좌석을 개수로만 본다** ② **A5 와 B1 을 옆자리로 본다** ③ **못 주는데 반쯤 잡아둔다** ④ **빈자리 수와 최장 연석을 같게 본다** ⑤ **배치가 만료 안 된 자리까지 비운다**.
- 개수로만 보면: **붙은 자리가 필요한 무리를 못 판다.**\
  화면에는 "여섯 자리 남음"이 떠 있으니 손님은 왜 거절당하는지 모른다.
- 만료 안 된 자리까지 비우면: **결제 중인 손님의 자리를 빼앗는다.**\
  그 손님은 결제 화면에서 좌석 번호를 보고 있는데 그 자리가 이미 남에게 팔린다.

#### 11. 변종 검증

- 조기 반환을 지운 이유: **빈 목록이면 아래 반복문이 안 돌아 결과가 같다.**\
  갈래가 둘이면 한쪽만 고치는 버그가 생기고, 테스트가 한쪽 갈래만 지나가면 다른 쪽은 검증이 안 된다.
- 배치가 만료 안 된 자리까지 비워도 통과한 이유: **배치를 만료 뒤에만 불러보고 있었다.**\
  자료에 "아직 살아 있는 예약"이 없으면 "살아 있는 것은 안 건드린다"가 검증되지 않는다. 살아 있는 예약을 섞어 갈랐다.
- 0으로 안 되돌려도 통과한 이유: **예제의 빈자리가 늘 붙어 있었다.**\
  그 상태에서는 "빈자리 수"와 "최장 연석"이 같은 값이다.
- 열 검사를 잡아낸 입력: **`A1` 과 `B2`**(번호는 1,2로 이어지고 열이 다르다).
- 공통점: **자료가 결함을 덮고 있었다.**\
  네 가지 모두 코드가 아니라 **테스트 입력의 다양성 부족**이 문제였다 — 만료 안 된 예약, 떨어진 빈자리, 번호가 이어지는 다른 열, 빈 결과 경로가 자료에 없었다.

#### 12. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 흩어 앉게 됨을 언제 알리나: `Hold` 가 **`together` 플래그를 결과에 담아 돌려준다** — 알릴 재료는 배정 직후에 이미 있다.\
  좌석 고를 때 알리면 손님이 다른 회차를 고를 기회가 생기고, 결제 직전에 알리면 이탈이 줄지만 항의가 온다. `together` 를 결과에 넣어둔 설계는 **어느 화면에서든 쓸 수 있게** 해준다. (원본에 근거 없음 — 내 추론)
- 통로 옆자리: 지금 `SeatMap` 은 **열 이름과 열당 좌석 수만** 들고 있어서 통로 위치를 모른다.\
  `findRun` 이 번호가 연속이면 붙었다고 보므로, 한 열 중간에 통로가 있으면 통로 건너를 붙었다고 판다. 고치려면 배치도가 **"끊기는 자리" 목록**을 들고, `free` 옆에 "이 두 번호가 이어지나"를 묻는 자리가 있어야 한다. 좌석 이름 문자열을 자르는 대신 배치도가 그 지식을 갖는 편이 낫다. (원본에 근거 없음 — 내 추론)
- 앞 무리의 결제 화면: 테스트가 **주인이 실제로 바뀌는 것**을 못 박았다(`ownerOf("A1")` 이 g1 → g2).\
  앞 무리는 그 사실을 모르므로, 결제 완료 시점에 **소유권을 다시 확인**해서 실패시켜야 한다. 그러면 11번과 같은 문제가 된다 — 결제는 이미 끝났는데 자리가 없다. (원본에 근거 없음 — 내 추론)
- 여러 열에 걸친 무리: 지금은 `findAny` 가 **앞에서부터 아무 자리나** 모으므로 묶는 기준이 없다.\
  기준을 주려면 "앞뒤 열의 같은 번호대"처럼 **가까움을 재는 값**이 필요하고, 그건 `SeatMap` 이 열 사이의 거리를 알아야 가능하다. 지금 모델은 열 안의 연속만 알고 열 사이는 모른다. (원본에 근거 없음 — 내 추론)

#### 13. 연결

- 11번과 같은 축: **TTL·만료·배치(LAZY/SWEEP)** 다. 달라진 축은 **개수 → 모양**이다.\
  11번은 "몇 개 남았나"만 물으면 됐지만, 여기서는 "어떤 모양으로 남았나"를 물어야 한다.
- `longestRun` 과 운영체제: **메모리 단편화**와 같은 구조다.\
  전체 여유 메모리는 충분한데 연속된 큰 블록이 없어 할당이 실패하는 것과, 빈자리 6개인데 3연석이 없어 거절하는 것이 같은 문제다.
- "부하가 없으면 설계 차이가 안 보인다": **11번의 "결제율 30 %에서는 초과 판매가 0"** 과 같은 이야기다.\
  둘 다 개발 환경의 조건(빈 극장·낮은 결제율)이 설계 결함을 가린다 — 재려면 **부하가 있는 상태를 일부러 만들어야** 한다.
