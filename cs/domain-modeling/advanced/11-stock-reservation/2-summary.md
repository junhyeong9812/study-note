## 한눈에 — 쉽게 말하면

**재고 예약 = "잠깐 이거 맡아주세요" 하고 지갑 가지러 간 손님.**

- 문구점에서 손님이 "이 인형 살게요, 돈 가지고 올게요" 하면 점원은 인형을 계산대 뒤에 **잠깐 치워둔다**. 10분이 지나도 안 오면 다시 진열대에 올린다.
- 온라인 쇼핑·티켓 예매의 "결제 전까지 10분 잡아둔다"가 똑같은 구조다.
- 그런데 그 한 줄 요구사항에는 **세 가지가 안 들어 있다**:
  1. 다른 손님에게 "몇 개 남았어요"라고 말할 때 **맡아둔 것을 빼고 세나?**
  2. 10분이 지난 예약은 **언제 진열대로 돌아가나?** — 누가 물어볼 때마다 확인하나, 아니면 정해진 시간에 한꺼번에 정리하나(배치).
  3. **딱 10분째 그 순간**, 예약은 살아 있나 죽었나.
- 셋을 어떻게 정하느냐에 따라 **초과 판매**(있는 것보다 많이 팖)가 나기도 하고, **재고가 있는데 손님을 돌려보내기도** 한다.
  - *초과 판매(oversell)*: 실물은 10개인데 15명에게 "팔았습니다"라고 확정해버리는 것.
  - *배치(batch)*: 일을 그때그때 하지 않고 모아뒀다가 정해진 주기에 한꺼번에 처리하는 방식.

```text
  10:00:00 예약 (TTL 10분)          TTL = 잡아두는 시간
     │
     │  잡혀 있음 (HELD)
     ▼
  10:10:00  ← 딱 만료 시각. 이 순간은 살았나 죽었나? (규칙 3)
     │
     ▼
  10:10:01  확실히 만료 — 그런데 재고에 언제 돌아오나? (규칙 2)
```

실무 예: 티켓 예매 좌석 홀드, 쇼핑몰 장바구니 재고 점유, 호텔 예약 가결제.

## 전체 흐름

```text
예약 한 건(Reservation)의 상태:

  HELD(잡고 있음) ──confirm(결제 완료)──▶ CONFIRMED(확정 — 실물이 나감)
      │
      └────만료 후 sweep(배치)──────────▶ RELEASED(풀림 — 진열대로 복귀)

"재고 몇 개 남았나"(available)를 정하는 세 개의 스위치:

  AvailabilityRule  SUBTRACT_HELD  잡아둔 것을 뺀다   ← 안전, 대신 덜 팖
                    PHYSICAL_ONLY  물리 재고만 본다   ← 많이 팖, 대신 초과 판매
  ExpiryCheck       LAZY   조회할 때마다 만료를 반영
                    SWEEP  배치가 돌기 전까지는 만료돼도 잡힌 것으로 침
  Boundary          EXPIRED_AT_DEADLINE  만료 시각이 되면 이미 죽었다
                    ALIVE_AT_DEADLINE    만료 시각을 넘겨야 죽는다

확정(CONFIRMED)된 수량은 어느 스위치에서도 항상 뺀다 — 실물이 나갔으니까.
```

## 규칙 1 — 잡아둔 것을 빼나 (AvailabilityRule)

**어떤 요구사항인가**: "몇 개 남았어요?"라는 질문에 예약(HELD)을 어떻게 취급할지 정해야 한다. 요구사항 문서에는 보통 안 적혀 있다.

**예시 입력**: 재고 10개, 예약 7건(아직 확정 없음).

```text
                    SUBTRACT_HELD        PHYSICAL_ONLY
  물리 재고             10                    10
  잡아둔 것(HELD)      - 7                   안 뺌
  ─────────────────────────────────────────────────
  가용 재고              3                    10
```

**결과**: 물리 재고만 보면 열 명이 더 예약할 수 있고, 그 열 명이 다 결제하면 17개를 팔아야 한다 — 실물은 10개뿐인데.

**왜 이렇게 모델링했나**: 정답을 하나 고르는 대신 **enum 스위치로 두 규칙을 다 구현하고 결과를 측정**했다. 어느 쪽이 옳은지는 코드가 아니라 도메인(장사 방침)이 정하기 때문이다. 단, 확정된 것은 두 규칙 모두에서 뺀다 — 확정을 안 빼면 재고가 영원히 안 준다(README의 첫 번째 함정).

- *enum*: 고를 수 있는 값을 몇 개로 못 박아둔 타입. 여기서는 "규칙 스위치"로 쓴다.

또 하나, `available`은 **품목(sku)이 같은 예약만** 센다. B 품목의 예약이 A 품목의 재고를 깎으면 안 된다 — 그리고 이 실수는 **품목이 하나뿐인 테스트로는 절대 안 잡힌다**.

- *sku*: 품목 코드. "A 인형", "B 인형"처럼 상품 종류 하나를 가리키는 이름표.

## 규칙 2 — 만료를 언제 반영하나 (ExpiryCheck)

**어떤 요구사항인가**: 10분이 지난 예약은 재고로 돌아와야 한다. 그런데 "돌아오는 순간"이 조회 시점인지 배치 시점인지 정해야 한다.

**예시 입력**: 재고 10, 예약 10건이 전부 만료된 뒤(만료 1초 후) 가용 재고를 물으면 —

```text
  LAZY  (조회 시 만료)   "만료됐네, 빼고 세자"        → 가용 10
  SWEEP (배치 만료)      "배치가 아직 안 풀었잖아"     → 가용 0
                          └─ sweep(배치) 실행 후      → 가용 10
```

**결과**: 배치가 안 돌면 **재고가 있는데 손님을 돌려보낸다**. 측정(재고 100, 손님 300, 결제율 30%)에서 조회 시 만료는 확정 61·거절 103인데, 배치를 안 돌리면 확정 33·거절 **200**이었다. 초과 판매의 정반대인데, **아무 오류도 안 나서 알아채기가 더 어렵다**.

**왜 이렇게 모델링했나**: `sweep()`은 만료된 HELD만 RELEASED로 바꾼다. 확정된 것과 아직 안 만료된 것을 건드리면 **결제한 손님의 물건을 빼앗는** 사고가 된다. 그래서 "전부 푸는 배치"가 함정으로 명시돼 있다.

## 규칙 3 — 만료 시각 그 순간 (Boundary)

**어떤 요구사항인가**: 10:00:00에 TTL 10분으로 예약했다. 10:10:00 정각에 이 예약은 살아 있나?

**예시 입력**: 재고 1, 예약 1건. 만료 시각(DEADLINE) 근처를 1초씩 훑으면 —

```text
  시각          EXPIRED_AT_DEADLINE     ALIVE_AT_DEADLINE
  10:09:59      잡고 있음 → 가용 0       잡고 있음 → 가용 0
  10:10:00      이미 죽음 → 가용 1       아직 삶  → 가용 0    ← 여기만 갈린다
  10:10:01      죽음     → 가용 1       죽음     → 가용 1
```

**결과**: 11초를 훑어도 두 규칙이 갈리는 것은 **딱 1초**다. 시각을 아무렇게나 흩뿌린 테스트 자료로는 거의 안 잡히고, TTL이 정확히 떨어지는 시각을 **일부러 만들어야** 보인다.

**왜 이렇게 모델링했나**: 코드에서는 부등호 하나 차이다 — `!at.isBefore(deadline)`(이상이면 죽음) vs `at.isAfter(deadline)`(초과해야 죽음). 이 한 글자가 손님 한 명의 예약 성패를 가르므로 enum으로 끌어올려 **이름 붙은 결정**으로 만들었다.

## 확정(confirm) — 막는 것만으로 안 끝나는 이유

**어떤 요구사항인가**: 결제가 끝나면 예약을 확정한다. 만료된 예약은 확정하면 안 된다.

**규칙 적용 단계**:

```text
confirm(id, at, boundary)
  [1] 예약이 없거나 HELD가 아니면        → false (두 번 확정도 여기서 막힌다)
  [2] 그 시각에 만료됐으면               → false
  [3] 물리 재고 < 이미 확정된 수량 + 이번 수량 이면 → oversold에 그 수량을 더해 기록
  [4] 상태를 CONFIRMED로 바꾸고 true
```

**결과**: 만료된 예약의 확정은 거부된다(false). 그런데 **결제는 이미 끝나 있다** — 거부만으로는 문제가 안 끝나고, 그 돈을 어떻게 할지(환불? 재예약?)는 별개의 도메인 결정으로 남는다. README가 "생각해볼 것"으로 남긴 지점이다.

**왜 이렇게 모델링했나**: 초과 판매를 예외로 터뜨리지 않고 `oversold` 카운터에 **기록**한다. 초과 판매는 예약 단계가 아니라 확정 단계에서 드러나고, 그 크기를 재봐야 규칙끼리 비교할 수 있기 때문이다. 이 카운터도 **품목별로** 센다 — A 8개·B 5개를 각각 확정하면 둘 다 자기 재고 안이라 초과 판매 0이어야 하는데, 품목을 안 나누면 13개로 합쳐 세서 틀린다.

## 측정이 알려준 것 (README 수치 그대로)

**하나 — 결제율이 높을수록 초과 판매가 드러난다** (재고 100, 손님 300):

| 결제율 | 물리 재고만 (확정/거절/초과) | 잡은 것 뺌 (확정/거절/초과) |
|---|---|---|
| 10 % | 35 / 0 / **0** | 30 / 66 / 0 |
| 30 % | 96 / 0 / **0** | 63 / 108 / 0 |
| 60 % | 125 / 90 / 25 | 92 / 152 / 0 |
| 100 % | 150 / 150 / **50** | 100 / 200 / 0 |

- 결제율 30%까지는 물리 재고만 봐도 초과 판매가 0이다 — **개발 중에는 안 보인다**.
- 한정 판매·티켓 오픈은 결제율이 100%에 가깝다. 그때 100개짜리가 **150개 확정**된다.
- 잡은 것을 빼면 확정이 재고를 절대 안 넘는다. 대신 결제율 10%에서 30개만 판다(물리만 보면 35개). **안 팔린 5개 vs 초과 판매 50개** — 어느 쪽이 나쁜지는 도메인이 정하지만, 저울질하려면 둘 다 재봐야 한다.

**둘 — 배치를 자주 돌려도 조회 시 만료에 수렴하지 않는다** (잡은 것 뺌 + 배치 만료):

| 배치 주기 | 확정 | 거절 |
|---|---|---|
| 안 돎 | 33 | 200 |
| 60 초 | **65** | 111 |
| 300 초 | 54 | 132 |
| 600 초 | 55 | 139 |

조회 시 만료는 확정 61·거절 103인데, **60초 배치가 확정 65로 오히려 더 판다**. 배치가 한꺼번에 여러 건을 풀어 그 순간 자리가 몰려 나기 때문이다. 두 방식은 크기만 다른 게 아니라 **자리가 나는 모양이 다르다**.

**셋 — 아무도 만료 안 되면 두 만료 방식이 같다.** TTL을 하루로 넉넉히 주면 LAZY와 SWEEP이 같은 답을 낸다. 개발할 때는 보통 TTL을 길게 두므로 **이 함정의 절반이 개발 환경에서 사라진다**.

## 경계·모서리 케이스 — 함정 → 올바른 처리

| 함정 | 올바른 처리 |
|---|---|
| 확정된 것을 물리 재고 계산에서 안 뺌 | 확정 수량은 **어느 규칙에서도** 뺀다 — 안 빼면 재고가 영원히 안 준다 |
| 품목 필터 누락 (available·oversold 둘 다) | sku가 같은 예약만 센다. 테스트에 **품목을 2개** 넣어야 잡힌다 — 실제로 필터를 지워도 전부 통과했고, A+B 테스트를 넣고서야 잡혔다(변종 검증) |
| 만료된 예약을 확정해줌 | confirm에서 만료 검사 — 단, 결제된 돈 처리는 별개 문제로 남는다 |
| 배치가 만료 안 된 것까지 풂 | sweep은 "만료된 HELD"만 RELEASED로 — 확정·신선한 예약은 안 건드린다 |
| TTL 0 (설정 실수로 실제 들어옴) | EXPIRED_AT_DEADLINE이면 만드는 순간 이미 만료(확정 불가), ALIVE_AT_DEADLINE이면 그 순간까지는 산다(확정 가능) |
| 예약 번호 중복 | IllegalArgumentException — 조용히 덮어쓰지 않는다 |
| 없는 예약·없는 품목 | confirm은 false, 재고·가용은 0 — 예외가 아니라 "없음"으로 답한다 |
| (측정 코드의 함정) 결제를 전부 뒤로 몰아 처리 | 시각 순으로 섞어 처리 — 몰아서 하면 안전한 규칙에서도 초과 판매가 나는 것처럼 **측정 자체가 거짓말**을 한다 |

## 핵심 문장

- "10분 잡아둔다"는 한 줄에는 **세 가지 결정이 빠져 있다** — 잡은 것을 빼고 세나, 만료를 언제 반영하나, 만료 순간은 살았나 죽었나. 모델링은 이 숨은 결정을 enum으로 끌어내 이름을 붙이는 일이다.
- 잡은 것을 빼면 초과 판매가 0이 되는 대신 덜 팔고, 물리 재고만 보면 더 파는 대신 결제율이 높을 때 초과 판매가 터진다 — **어느 쪽이 옳은지는 코드가 아니라 도메인이 정하고, 정하려면 둘 다 재봐야 한다**.
- 배치 만료의 실패는 초과 판매의 반대(재고가 있는데 거절)라서 **아무 오류도 안 나고**, 그래서 더 위험하다.
- 품목 필터·만료 경계 같은 결함은 **품목 1개·아무 시각 테스트로는 안 잡힌다** — 품목 2개, TTL이 딱 떨어지는 시각을 일부러 만들어야 보인다.
- 만료된 예약의 확정을 막아도 **결제는 이미 끝나 있다** — 코드가 거절한 뒤의 뒷수습이 진짜 도메인 문제다.

## 용어 풀이

- **TTL(time to live)**: 잡아두는 시간. 예약 시각 + TTL = 만료 시각.
- **HELD / CONFIRMED / RELEASED**: 잡고 있음 / 확정(실물이 나감) / 풀림(취소·만료). 예약 한 건의 세 가지 상태.
- **가용 재고(available)**: "지금 몇 개 팔 수 있나". 물리 재고에서 확정을 빼고, 규칙에 따라 잡아둔 것도 뺀 값.
- **물리 재고(physical)**: 창고에 실제로 있는 개수.
- **초과 판매(oversell)**: 물리 재고보다 많이 확정된 수량. 예약 단계가 아니라 확정 단계에서 드러난다.
- **sku**: 품목 코드. 상품 종류 하나의 이름표.
- **배치/스윕(sweep)**: 만료된 예약을 주기적으로 한꺼번에 푸는 작업.
- **LAZY / SWEEP**: 만료를 조회할 때마다 반영 / 배치가 돌 때만 반영.
- **Boundary(만료 경계)**: 만료 시각 정각의 생사 규칙. 부등호 하나(`isBefore` vs `isAfter`) 차이.
- **enum 스위치**: 정답이 도메인마다 다른 규칙을 코드에 이름 붙은 선택지로 남겨두는 기법.
- **변종 검증(mutation testing류)**: 구현을 일부러 망가뜨려(품목 필터 삭제 등) 테스트가 잡는지 확인하는 것. 안 잡히면 테스트 구멍이다.
