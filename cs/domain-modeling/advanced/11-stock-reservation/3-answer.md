### A. 과제

#### 0. 한 줄 요구사항이 안 말해주는 것

- 안 말해주는 자리 셋(README 그대로):

```text
 안 말해준 것             가능한 읽기
 "잡아둔다"        →  남은 개수를 셀 때 잡아둔 것을 빼나 마나
 "10 분"           →  10 분이 지난 예약을 언제 풀어주나 (조회 때 / 배치 때)
 "10 분까지"       →  딱 10 분 되는 순간은 살아 있나 죽었나
```

- 빼는 판이 잃는 것: **덜 판다.**\
  결제율 10 %일 때 30개만 판다(물리 재고만 보면 35개 — README 측정).
- 안 빼는 판이 잃는 것: **초과 판매가 난다.**\
  결제율 100 %일 때 100개짜리가 150개 확정된다(초과 50).
- 조회 시 만료(LAZY)와 배치 만료(SWEEP)의 차이: LAZY 는 **묻는 순간 계산**하고, SWEEP 은 **배치가 실제로 풀어줄 때까지 잡힌 것으로 센다.**\
  그래서 SWEEP 에서 배치가 안 돌면 재고가 있어도 0개다.

> **조회 시 만료(lazy expiry)** — 저장된 상태는 그대로 두고, 읽는 시점에 "지금 기준으로 만료됐나"를 계산해 반영하는 방식.\
> 예: 예약 상태는 여전히 HELD 지만 10분이 지났으면 가용 재고를 셀 때만 빼고 센다.

> **배치 만료(sweep)** — 주기적으로 도는 작업이 만료된 것을 실제로 RELEASED 로 바꿔줘야 비로소 풀리는 방식.\
> 예: 1분마다 도는 배치가 아직 안 돌았으면, 20분 전에 만료된 예약도 여전히 재고를 잡고 있다.

- 만료 정각: **정한 대로다.** 테스트가 둘 다 못 박았다 — `EXPIRED_AT_DEADLINE` 이면 DEADLINE 에 가용 1(이미 죽음), `ALIVE_AT_DEADLINE` 이면 가용 0(아직 삶).
- enum 으로 안 올리면: **두 판을 같은 코드로 돌려 답이 갈리는 건수를 셀 수 없다.**\
  세어보기 전에는 "구석 사례"인지 "계약의 본체"인지 모른다 — 측정에서는 결제율 100 %에서 초과 50개가 나왔다.
- 확정이 항상 빠지는 이유: **확정은 실물이 나간 것**이다.\
  안 빼면 재고가 영원히 안 준다(README 첫 번째 함정). 규칙 셋은 "아직 안 나간 것"을 어떻게 볼지에 대한 것이고, 확정은 이미 나갔다.

#### 1. TODO 1 — expired

정답 코드 (impl/InventoryLedger.java):

```java
if (!reservation.held()) {
    return false;
}
Instant deadline = reservation.expiresAt();
return boundary == Boundary.EXPIRED_AT_DEADLINE
        ? !at.isBefore(deadline)
        : at.isAfter(deadline);
```

- HELD 가 아니면: **false.** 확정되거나 이미 풀린 예약은 만료를 따질 것이 없다.
- 확정된 예약에 true 를 주면: `sweep` 이 **확정을 RELEASED 로 되돌린다** — 결제한 손님의 물건을 빼앗는다.
- 부등호:

```text
 EXPIRED_AT_DEADLINE   at >= deadline   →  !at.isBefore(deadline)
 ALIVE_AT_DEADLINE     at >  deadline   →   at.isAfter(deadline)
```

- 갈리는 시각은 **`at == deadline` 하나뿐**이다.\
  그 앞은 둘 다 false(살아 있음), 그 뒤는 둘 다 true(죽음).

```text
 시각        10:09:59   10:10:00   10:10:01
 EXPIRED_AT   살아있음   죽음       죽음
 ALIVE_AT     살아있음   살아있음   죽음
                         ↑ 여기 1초만 갈린다
```

- 만료 시각은 **계산된다** — `Reservation.expiresAt()` 이 `reservedAt.plus(ttl)` 을 돌려준다.\
  필드로 저장하지 않으므로 TTL 을 바꾸면 만료 시각도 같이 따라온다.

#### 2. TODO 2 — holding

정답 코드:

```java
if (!reservation.held()) {
    return false;
}
return check == ExpiryCheck.SWEEP || !expired(reservation, at, boundary);
```

- SWEEP 에서 만료된 예약이 여전히 잡힌 것으로 세지는 이유: **배치가 돌아야 실제로 풀리기 때문**이다.\
  "만료됐다"와 "풀렸다"는 다른 사건이고, SWEEP 은 그 둘 사이에 시간 간격이 있다는 것을 인정하는 모델이다.
- `check == SWEEP` 를 먼저 보면 **`expired` 는 LAZY 일 때만 호출된다**(자바의 `||` 는 앞이 true 면 뒤를 안 본다).

> **단축 평가(short-circuit)** — `||` 앞이 true 면 뒤를 아예 실행하지 않는 것.\
> 예: `SWEEP || !expired(...)` 에서 SWEEP 이면 `expired` 를 부르지 않으므로 Boundary 는 이 경로에서 무의미해진다.

- 두 결정의 분리: `expired` 는 **만료 경계(Boundary)** 만 판단하고, `holding` 은 **그 만료를 지금 반영하나(ExpiryCheck)** 만 판단한다.\
  결정 두 개를 함수 두 개로 나눠 놓으면 조합(2×2=4가지)을 그대로 돌려볼 수 있다.
- SWEEP 인데 배치를 안 돌리면: **영원히** 잡힌 것으로 센다.\
  측정에서 "배치 안 돎"이 확정 33·거절 200이 된 이유가 이것이다.

#### 3. TODO 3 — available

정답 코드:

```java
int left = physical(sku);
for (Reservation reservation : reservations.values()) {
    if (!reservation.sku().equals(sku)) {
        continue;
    }
    if (reservation.state() == State.CONFIRMED) {
        left -= reservation.quantity();
    } else if (rule == AvailabilityRule.SUBTRACT_HELD
            && holding(reservation, at, check, boundary)) {
        left -= reservation.quantity();
    }
}
return left;
```

- `else if` 여야 하는 이유: 한 예약이 **두 번 빠지면 안 된다.**\
  CONFIRMED 는 `held()` 가 false 라 `holding` 도 false 를 주지만, 순서를 `if`/`if` 로 늘어놓으면 나중에 상태가 늘어날 때 이중 차감이 생긴다. 상태 하나당 차감 한 번이 계약이다.
- 품목 필터를 빼먹으면: **다른 품목의 예약이 이 품목의 재고를 깎는다.**

```text
 A 재고 10, B 재고 5,  B 를 5개 예약(HELD)

 필터 있음   A 의 가용 = 10 - 0 = 10   ← 맞다
 필터 없음   A 의 가용 = 10 - 5 =  5   ← B 예약이 A 를 깎았다
```

- 품목 하나뿐인 테스트로 안 잡히는 이유: 품목이 하나면 **필터가 있으나 없으나 전부 같은 품목**이라 `continue` 가 한 번도 안 걸린다.\
  실제로 원본에서 필터를 지워도 테스트가 전부 통과했고, A·B 를 같이 넣는 테스트를 넣고서야 잡혔다(README 변종 검증).
- 음수가 나올 수 있다 — 테스트가 못 박았다(`-10`).\
  뜻은 **"이미 재고보다 많이 확정했다"**, 즉 초과 판매가 그만큼 있다는 뜻이다.
- 없는 품목: **0**(`physical.getOrDefault(sku, 0)`).\
  예외가 아니라 "없음"으로 답한다 — 조회는 실패가 아니라 0이 자연스러운 답이고, 진짜 사고는 예약·확정 단계에서 막는다.

#### 4. TODO 4 — confirm

정답 코드:

```java
Reservation reservation = reservations.get(id);
if (reservation == null || !reservation.held()) {
    return false;
}
if (expired(reservation, at, boundary)) {
    return false;
}
if (physical(reservation.sku()) < confirmedQuantity(reservation.sku())
        + reservation.quantity()) {
    oversold += reservation.quantity();
}
reservations.put(id, reservation.as(State.CONFIRMED));
return true;
```

- 네 단계: ① 없거나 HELD 가 아니면 false ② 만료됐으면 false ③ 재고를 넘기면 `oversold` 에 기록 ④ CONFIRMED 로 바꾸고 true.
- 두 번 확정: **①에서 막힌다.** 첫 확정으로 상태가 CONFIRMED 가 됐으니 `held()` 가 false 다.\
  테스트가 `"두 번 확정은 안 된다"` 로 못 박았다.
- 예외 대신 카운터에 기록하는 이유: **초과 판매의 크기를 재야 규칙끼리 비교할 수 있다.**\
  예외로 터뜨리면 "몇 개나 났나"를 못 세고, 애초에 예약을 받은 쪽(물리 재고만 보는 규칙)의 책임이 확정 시점에 떠넘겨진다.
- 품목을 안 나누면:

```text
 A 재고 10 · B 재고 5,   B 5개 확정 → A 8개 확정

 품목별로 셈   A 의 확정 8  <= 10   → 초과 0   ← 맞다
 합쳐서 셈     확정 합 13   >  10   → 초과 8   ← 틀렸다
```

  이 자리는 품목 둘을 넣는 테스트를 넣고도 안 잡혔고, "각각은 재고 안인데 합치면 넘치는" 사례를 일부러 만들어서야 잡혔다(README 변종 검증 둘).
- 막는 것만으로 안 끝나는 이유: **결제는 이미 끝났다.**\
  `confirm` 이 false 를 줘도 손님 돈은 빠져나가 있다. 환불인지 재예약인지는 이 함수 밖의 도메인 결정이다.
- `rule` 을 안 받는 뜻: **확정은 가용 재고 규칙과 무관하다.**\
  가용 재고 규칙은 "예약을 받아줄까"를 정할 때만 쓰고, 확정에서는 물리 재고와 이미 확정된 수량이라는 **사실**만 본다. 계약 표면이 그만큼 작아진다.

#### 5. TODO 5 — sweep

정답 코드:

```java
int released = 0;
for (Map.Entry<String, Reservation> entry : new ArrayList<>(reservations.entrySet())) {
    if (expired(entry.getValue(), at, boundary)) {
        reservations.put(entry.getKey(), entry.getValue().as(State.RELEASED));
        released++;
    }
}
return released;
```

- 건드릴 것: **만료된 HELD 만.** 안 건드릴 것: 확정된 것, 아직 안 만료된 HELD, 이미 풀린 것.\
  (`expired` 가 `held()` 검사를 이미 하므로 여기서는 `expired` 하나만 보면 된다.)
- 만료 안 된 것까지 푸는 배치: **결제한 손님의 물건을 빼앗는다**(README 넷째 함정).\
  손님 화면에는 "예약됨"이 떠 있는데 재고는 남에게 팔린다.
- 두 번 부르면 두 번째는 **0**이다.\
  첫 번째에서 전부 RELEASED 가 됐고, `expired` 는 HELD 가 아니면 false 를 주기 때문이다. 테스트가 못 박았다(`assertEquals(0, ledger.sweep(...))`).

> **멱등(idempotent)** — 같은 조작을 여러 번 해도 결과가 한 번 한 것과 같은 성질.\
> 예: 같은 시각으로 배치를 두 번 돌려도 두 번째는 푼 게 0건이다. 배치가 재시도돼도 안전하다는 뜻이다.

- 복사하는 이유: **반복 중에 map 을 고치면 `ConcurrentModificationException` 이 난다.**\
  `put` 은 키가 이미 있으면 값만 바꾸는 것이라 구조 변경은 아니지만, 복사해두면 그 판단에 안 기대도 된다.

### B. 개념

#### 6. 측정 — 배치를 안 돌리면

재고 100, 손님 300, 결제율 30 % (README 표 그대로):

| 규칙 | 확정 | 거절 | 초과 판매 |
|---|---|---|---|
| 잡은 것 뺌 / 조회 시 만료 | 61 | 103 | 0 |
| 잡은 것 뺌 / 배치 만료 | **33** | **200** | 0 |
| 물리 재고만 / 조회 시 만료 | 95 | 0 | 0 |
| 물리 재고만 / 배치 만료 | 95 | 0 | 0 |

- 배치를 안 돌리면 **200명**을 돌려보낸다 — 재고가 있는데도.
- 더 알아채기 어려운 이유: **아무 오류도 안 난다.**\
  초과 판매는 나중에 "물건이 없다"는 사고로 터지지만, 이쪽은 손님이 조용히 "품절"만 보고 떠난다. 로그에도 예외에도 안 남는다.
- 물리 재고만 보는 두 줄이 같은 이유: **잡은 것을 아예 안 세기 때문**이다.\
  안 세는 값의 만료 시점을 언제 반영하든 결과가 같다 — `available` 의 SUBTRACT_HELD 분기 안에서만 `holding` 을 부른다.

#### 7. 측정 — 결제율

| 결제율 | 물리 재고만 (확정/거절/초과) | 잡은 것 뺌 (확정/거절/초과) |
|---|---|---|
| 10 % | 35 / 0 / **0** | 30 / 66 / 0 |
| 30 % | 96 / 0 / **0** | 63 / 108 / 0 |
| 60 % | 125 / 90 / 25 | 92 / 152 / 0 |
| 100 % | 150 / 150 / **50** | 100 / 200 / 0 |

- 결제율 30 %에서 초과 0이 위험한 이유: **개발·테스트 중에는 안 보인다.**\
  버그가 없는 게 아니라 조건이 안 맞아 안 드러난 것이고, 한정 판매·티켓 오픈은 결제율이 100 %에 가깝다.
- 결제율 100 %: 100개짜리가 **150개 확정**된다(초과 50).
- 잡은 것을 빼는 판이 결제율 10 %에서 잃는 것: **5개**(35 → 30).
- 누가 정하나: **도메인(장사 방침)** 이 정한다.\
  다만 "안 팔린 5개 vs 초과 판매 50개"를 저울질하려면 **두 값을 다 재봐야 한다** — 그게 이 박스가 enum 두 개를 다 구현한 이유다.

#### 8. 측정 — 배치 주기

| 배치 주기 | 확정 | 거절 |
|---|---|---|
| 안 돎 | 33 | 200 |
| 60 초 | **65** | 111 |
| 300 초 | 54 | 132 |
| 600 초 | 55 | 139 |

- 수렴하지 **않는다.** 조회 시 만료는 확정 61·거절 103인데 60초 배치는 확정 **65**로 더 많이 판다.
- 더 파는 이유: 배치가 **한꺼번에 여러 건을 풀어 그 순간 자리가 몰려 난다.**\
  마침 그때 온 손님들이 한꺼번에 예약에 성공한다.
- "모양이 다르다"의 뜻: 조회 시 만료는 자리가 **한 건씩 고르게** 나고, 배치는 **주기마다 뭉텅이로** 난다.\
  총량이 비슷해도 누가 성공하느냐가 달라지므로, "배치 주기만 줄이면 LAZY 와 같아진다"는 직관이 틀린다.

#### 9. 측정 — 만료 경계와 TTL

- 만료 경계: 11초 중 **딱 1초**에서만 갈린다(만료 정각).\
  1초 전에는 두 규칙 다 0, 1초 뒤에는 두 규칙 다 1이다.
- 흩뿌린 자료로 안 잡히는 이유: 갈리는 자리가 **`at == deadline` 정확히 한 점**이라, 무작위 시각이 그 점에 맞을 확률이 거의 없다.\
  TTL 이 딱 떨어지는 시각을 **일부러 만들어야** 보인다.
- TTL 이 넉넉하면 같아지는 이유: **아무도 만료가 안 되니 LAZY 와 SWEEP 이 볼 만료된 예약 자체가 없다.**\
  `holding` 의 두 갈래가 같은 답을 준다.
- 개발 환경에서 사라지는 이유: 개발할 때는 보통 **TTL 을 길게 두거나 아예 안 만료시킨다.**\
  그래서 만료 관련 결함이 운영에 가서야 처음 드러난다.

#### 10. 함정 (README)

- 넷: ① **확정된 것을 물리 재고에서 안 뺀다** ② **품목 필터를 빼먹는다**(품목 하나짜리 예제로는 절대 안 잡힌다) ③ **만료된 예약을 확정해준다**(막는 것만으로 안 끝난다 — 결제는 이미 됐다) ④ **배치가 만료 안 된 것까지 푼다**(결제한 손님의 물건을 빼앗는다).
- 확정을 안 빼면: **가용 재고가 영원히 안 준다.**\
  실물은 계속 나가는데 화면에는 늘 재고가 있어서, 창고가 빌 때까지 계속 판다.
- 만료된 예약을 확정해주면: **만료가 의미를 잃는다.**\
  그 자리는 이미 다른 손님에게 팔렸을 수 있으므로 초과 판매로 이어진다.

#### 11. 변종 검증

- 필터를 지워도 통과한 이유: 테스트가 **품목을 하나만** 쓰고 있었다.\
  필터가 걸러낼 대상이 자료에 없으면 필터의 유무가 결과에 안 나타난다.
- 여전히 안 잡힌 자리: **초과 판매를 셀 때의 품목 필터**(`confirmedQuantity`).\
  `available` 쪽만 A·B 로 갈라놨기 때문이다.
- A 8개·B 5개가 갈림을 드러내는 이유: **각각은 자기 재고 안(8≤10, 5≤5)인데 합치면 13 > 10** 이라, 품목을 안 나누는 구현에서만 초과 판매가 잡힌다.
- 결제를 뒤로 몰면: **측정 자체가 거짓말을 한다.**\
  예약 시점의 가용 재고가 아직 확정을 못 봐서, 안전한 규칙(잡은 것 뺌)에서도 초과 판매가 나는 것처럼 보인다. 시각 순으로 섞어 처리하도록 고쳤다.

> **시뮬레이션 편향** — 측정 코드가 현실과 다른 순서로 사건을 처리해, 규칙이 아니라 측정 방식이 결과를 만드는 것.\
> 예: 예약을 다 받은 뒤에 결제를 몰아서 처리하면, 결제 결과가 뒤따르는 예약의 판단에 반영되지 않는다.

#### 12. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 만료된 예약의 결제 대금: `confirm` 이 false 를 주는 것까지가 이 코드의 책임이다.\
  뒷수습은 셋 중 하나 — **자동 환불**(손님 신뢰·정산 복잡) / **재고가 남아 있으면 확정으로 구제**(만료의 의미가 흐려짐) / **보류 후 사람이 판단**(느림). 어느 쪽이든 `confirm` 의 false 를 **"결제 취소 이벤트"로 밖에 알려야** 한다 — 지금은 반환값이 그냥 버려질 수 있다. (원본에 근거 없음 — 내 추론)
- 서버가 여럿일 때 LAZY: 이 코드는 `at` 을 **인자로 받으므로** 판정 시각이 호출자에게 달려 있다.\
  서버마다 시계가 다르면 같은 예약이 어떤 서버에서는 살아 있고 어떤 서버에서는 죽는다. 실무에서는 **DB 의 시각 하나를 기준으로 삼거나**(만료 조건을 쿼리에 넣는다) 판정을 한 곳에 모은다. `at` 을 인자로 뽑아둔 설계가 이 문제를 **테스트 가능하게** 만든 동시에 드러내 준다. (원본에 근거 없음 — 내 추론)
- TTL 연장: `Reservation` 은 record 라 `ttl` 을 못 바꾼다 — 바꾸려면 `as(state)` 처럼 **새 사본을 만들어 넣어야** 한다.\
  무한정 연장하면 잡아둔 재고가 영원히 안 풀려 "배치 안 돎"과 같은 상태가 된다(확정 33·거절 200). 그래서 보통 **연장 횟수나 총 상한**을 둔다. (원본에 근거 없음 — 내 추론)
- "품절"로 보이는 것: SUBTRACT_HELD 에서는 **잡힌 재고와 팔린 재고가 화면에서 구별이 안 된다.**\
  구별하려면 "n분 뒤 다시 확인하세요" 같은 **잡힘 상태를 노출**하거나 대기열을 둬야 하는데, 그러면 잡아둔 물건의 개수가 남에게 새어 나간다. 이 코드는 `available` 하나만 공개하므로 그 구별이 아직 계약에 없다. (원본에 근거 없음 — 내 추론)

#### 13. 연결

- `Boundary` 와 01-parking-fee: **"경계를 포함하나"** 로 같은 자리다.\
  주차는 "10분까지 무료"의 10분이 포함인지, 여기는 만료 정각이 살았는지 — 둘 다 부등호 한 글자가 답을 가른다.
- `oversold` 처럼 세어두는 방식: **막을 수 없는 자리에서 규모를 재야 할 때** 쓴다.\
  여기서는 예약을 받아준 뒤(물리 재고만 보는 규칙) 확정 시점에야 드러나므로 막을 수가 없다. 예외로 던지면 손님 결제가 실패하고, 세어두면 나중에 뒷수습할 목록이 남는다.
- LAZY / SWEEP 의 실무 대응: **읽을 때 계산하나, 미리 써두나**(캐시 무효화 방식, TTL 만료 vs 명시적 삭제).\
  읽을 때 계산은 항상 최신이지만 매번 비용이 들고, 배치는 싸지만 **배치와 배치 사이의 틈이 그대로 오차**가 된다.
