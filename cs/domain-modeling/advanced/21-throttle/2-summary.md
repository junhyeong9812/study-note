## 한눈에 — 쉽게 말하면

**스로틀링 = 놀이기구 줄 관리.** "1시간에 60명까지 태워요"라는 안내문 하나로는 규칙이 안 정해진다.

- 1시간을 **어떻게** 세나 — 정각~정각인가, 지금부터 거슬러 1시간인가, 자리가 조금씩 다시 나는 방식인가.
- **누구를** 세나 — 사람마다 세나, 단체(같은 버스로 온 팀)로 세나.
- **못 탄 사람도** 세나 — 줄 섰다가 돌아간 사람도 "탄 것"으로 치나.
- 원본의 한 줄 요약: **"1초에 60번"이라는 한 줄에 세 가지가 안 들어 있다** — 1초를 어떻게 세나, 무엇을 세나, 막힌 요청도 세나. 이 셋을 각각 enum으로 만들어 3×3×2 = 18 조합을 전부 돌려보는 것이 이 챕터다.
  - *스로틀링(throttling)*: 일정 시간 안에 처리할 요청 수에 한도를 두고, 넘치면 막는 것. API 서버가 과부하·남용을 막는 기본 장치.

```text
한도 5, 창 1초일 때 "시계 창(FIXED_WINDOW)"의 함정:

시각(ms)   0 ──────────── 999 │ 1000 ──────────── 1999
                     ●●●●● │ ●●●●●
                999ms에 5번  │  1000ms에 5번 — 창이 바뀌어 자리가 되살아남
                     └── 2밀리초 사이에 10번 통과. 한도는 "1초에 5번"인데.
```

실무 예: API rate limit(GitHub API의 "시간당 5,000회"), 로그인 시도 제한, 문자 발송 한도.

## 전체 흐름

```text
Request(id, userId, ip, atMillis)     ← 누가·어디서·언제. 사용자와 주소는 일대일이 아니다
        │
        ▼
key(request, keyBy)                   ← 이 요청이 어느 "통"에 들어가나
   USER        → "u:" + userId          (접두사 + 구분자가 함정 방어)
   IP          → "i:" + ip
   USER_AND_IP → "u:" + userId + "|i:" + ip
        │
        ▼
allow(bucket, atMillis, algorithm, countRejected)   ← 통과? 통 상태도 함께 바뀜
   FIXED_WINDOW   시계의 창. 창이 바뀌면 세던 것을 통째로 버림
   SLIDING_LOG    지금부터 거슬러 창 하나. 지나간 기록만 버림
   TOKEN_BUCKET   채워지는 통. 시간이 지나면 조금씩 다시 참
        │
        ▼
run(requests, ...)                    ← 키마다 통 하나. 도착 순서 그대로 처리
        │
        ▼
Result(allowed, rejected, allowedByUser) + maxInAnyWindow(allowed)
                                      ← "어느 한 창 안에 최대 몇 건 지나갔나"를 재는 자
```

## 규칙 1 — 창을 어떻게 세나 (Algorithm)

**요구사항 문장**: "1초에 5번까지." 이 문장이 코드에서는 enum `Algorithm`의 세 값으로 갈라진다.

예시 입력 — 한도 5, 창 1초. 같은 사용자가 999ms에 5번 + 1000ms에 5번:

| 알고리즘 | 통과 수 | maxInAnyWindow | 왜 |
|---|---|---|---|
| FIXED_WINDOW (시계 창) | **10** | **10** | 1000ms에 창이 바뀌며 5자리가 한꺼번에 되살아남 |
| SLIDING_LOG (훑는 기록) | 5 | 5 | 거슬러 1초 안의 기록을 세니 경계가 없음 |
| TOKEN_BUCKET (채워지는 통) | 5 | 5 | 통이 비어 있고 1ms로는 거의 안 참 |

각 알고리즘의 동작(정답 `impl/Throttle.java`의 allow):

```text
FIXED_WINDOW: start = atMillis / windowMillis * windowMillis
              창이 바뀌면 windowCount = 0 부터 다시. count ≥ limit 이면 거절
SLIDING_LOG:  log(Deque)에서 atMillis - windowMillis 이하인 옛 기록을 앞에서 뽑아 버림
              남은 크기 ≥ limit 이면 거절, 아니면 지금 시각을 기록
TOKEN_BUCKET: capacity = limit × windowMillis (토큰을 "밀리" 단위 정수로!)
              지난 시간 × limit 만큼 다시 채움(상한 capacity)
              토큰 < windowMillis(1개분)이면 거절, 아니면 1개분 차감
```

- 훑는 기록의 창은 `(t-1000, t]`다 — 0ms의 기록은 **정확히 1000ms에** 빠진다(테스트: 999ms엔 막히고 1000ms엔 통과). 경계를 닫으면 그 한 건이 1ms 더 기다리고, 재시도 간격과 맞물리면 계속 어긋난다.
- 채워지는 통은 한도 5·창 1초면 **200ms마다 한 자리씩** 다시 연다(테스트: 100ms엔 막히고 200ms엔 통과). 같은 한도인데 훑는 기록은 1000ms까지 한 자리도 안 연다 — **기다리는 모양이 다르다.**
- 토큰을 소수(0.005개)로 안 세고 "토큰 1개 = windowMillis 밀리토큰" 정수로 세는 이유: **소수를 안 쓰면 자리 잃는 일이 없다**(부동소수점 오차 방어 — README 함정 셋째).

**왜 이렇게 모델링했나**: 세 알고리즘을 if 분기가 아니라 enum + switch로 둔 것은, "1초를 어떻게 세나"가 구현 세부가 아니라 **업무 규칙의 선택지**이기 때문이다. 어느 것이 정답이 아니라 트레이드오프다 — 시계 창은 싸지만 경계에서 2배, 훑는 기록은 정확하지만 기록(메모리)을 들고 다녀야 하고, 채워지는 통은 몰아 쓰기를 허용한다.

## 규칙 2 — 무엇을 세나 (KeyBy) + 키 만들기의 함정 둘

**요구사항 문장**: "사용자당 한도" vs "회선(IP)당 한도" vs "사용자·회선 짝당 한도". `Request`가 userId와 ip를 둘 다 갖고, **둘은 일대일이 아니다** — 같은 사람이 집·회사·휴대폰 세 주소를 쓰고, 회사 공유 회선·통신사 NAT에는 한 주소에 여러 사람이 있다.
  - *NAT*: 여러 기기가 바깥에서는 하나의 주소로 보이게 하는 방식. 통신사·회사망에서 흔하다.

예시 입력 — 한도 5, 회사 공유 회선에서 a·b·c 세 사람이 3번씩(총 9번):

```text
USER 로 세면 : 9번 다 통과 (각자 3/5)
IP   로 세면 : 5번만 통과 — 막힌 4번은 전부 맨 뒤에 온 c의 요청.
               c는 자기가 처음 눌렀는데 막혔다. 남이 내 몫을 먹었다.
```

반대 방향 — 같은 사람이 집·회사·휴대폰에서 5번씩(총 15번): USER로 세면 5번, USER_AND_IP로 세면 15번. **짝으로 세면 주소만 바꿔도 한도가 3배**가 된다. 그리고 주소를 바꾸는 것은 쉽다(우회 통로).

키 문자열의 함정 둘 (README 함정 첫·둘째):

| 함정 | 예 | 방어 |
|---|---|---|
| 구분자 없이 이어 붙임 | 사용자 "ab"+주소 "c" 와 "a"+"bc" → 둘 다 "abc" | `"u:" + userId + "\|i:" + ip` 처럼 구분자 |
| 사용자 통·주소 통 안 나눔 | 익명 사용자를 주소로 식별 → 사용자 "10.0.0.1"과 주소 "10.0.0.1"이 같은 통 | `u:` `i:` 접두사로 이름공간 분리 |

- 구분자 충돌은 사용자 번호가 숫자면 안 보이고, 이메일·자유 문자열이 되는 날 나타난다. 접두사 충돌은 **익명 사용자를 다루기 시작한 날** 생긴다 — 지금 안 터진다고 없는 버그가 아니다.

## 규칙 3 — 막힌 요청도 세나 (CountRejected)

**요구사항 문장**: "막혔어도 한 번 부른 것으로 친다"(악의적 재시도에 벌 주기). 코드에서는 거절 분기 안에서 **막힌 요청이 자국을 남기는가**로 번역된다 — 훑는 기록에는 시각이 하나 더 쌓이고, 채워지는 통은 음수로 내려간다(빚).

예시 입력 — 한도 5, 창 1초, 100ms마다 20번 두드림(훑는 기록):

```text
안 세면(NO)  : 10번 통과 — 1000ms부터 창이 조금씩 열림
세면(YES)    : 5번뿐 — 막힌 요청이 기록에 쌓여 창이 계속 가득. 두드릴수록 더 막힘
```

- 두드리는 쪽에서는 둘이 구별이 안 된다. 그런데 하나는 1초 뒤에 열리고 하나는 안 열린다. 그리고 두드리는 쪽은 대개 **버그가 난 우리 앱**이다.
- 채워지는 통의 빚에는 **상한이 필요하다**(`Math.max(-capacity, ...)`) — 상한이 없으면 100번 두드린 사람이 20초를 기다린다. 상한을 통 크기만큼 두면 아무리 두드려도 1초 뒤엔 회복한다(테스트: 100번 폭주 후 3000ms의 요청은 통과). **벌은 주되 벌의 크기를 정해둔다.**
- **시계 창에서는 이 스위치가 죽는다.** 이미 한도를 넘은 상태에서 하나 더 세도 여전히 넘은 상태이고, 창이 바뀌면 세던 것을 통째로 버려 쌓이지도 않는다. 변종 검증에서 이 분기가 **죽은 코드**임을 확인하고 지운 뒤 이유를 주석으로 남겼다 — "설정 화면에 스위치를 두고 시계 창을 고르면 스위치가 죽는다. 그리고 아무 표시도 안 난다."

## 측정 — 18 조합이 실제로 얼마나 갈리나

전제: 한도 1초 60번, 사용자 20명이 10초간 1인당 1,200건(초당 120건 — **한도의 2배**), 10회 반복.

**하나. 셋 중 훑는 기록만 한도를 지킨다** (한 창 상한 = 60×20 = 1,200):

| 경계 몰림 | 시계 창 | 훑는 기록 | 채워지는 통 |
|---|---|---|---|
| 0 % | 1,311 | **1,200** | 2,328 |
| 30 % | 1,689 | **1,200** | 2,334 |
| 80 % | **2,278** | **1,200** | 1,781 |

- 시계 창은 경계에 몰릴수록 나빠진다(앞 창 잔여 + 뒤 창 새 자리가 몇 ms 사이에 붙음). 채워지는 통은 몰림 0%여도 **1.94배** — 가득 찬 채로 시작해 한 창 분을 한 번에 쓰고 그 창 안에서 또 채워지기 때문. **버그가 아니라 그 알고리즘의 뜻이다. 몰아 쓰기를 허용한다.**

**둘. 주소로 세면 몇 명이 나눠 쓰든 통과량이 같다**: 공유 2명이든 20명이든 6,000(= 60×10초×10회). **회선 하나가 곧 한도다.** 공유 20명이면 한 사람 몫이 단독 사용자의 1/20 — 그리고 그 사람은 자기가 왜 막히는지 알 방법이 없다.

**셋. 막힌 요청까지 세면 정상 사용자도 10분의 1로 막힌다**: 정상 17명 + 폭주 3명에서 훑는 기록·세면 → 폭주 18,000→1,800, 정상 102,000→**10,200**. 정상(이라지만 한도 2배) 사용자의 막힌 절반이 기록에 쌓여 **첫 1초 뒤로는 영영 안 열린다.** 벌은 악의적 재시도를 겨냥했는데, 한도를 조금 넘는 모두에게 같은 벌이 간다.

**넷. 시계 창에서는 그 설정이 죽는다** — 세든 말든 120,000으로 같다.

**다섯. 한도 아래(1인당 300건 = 한도의 절반)로만 오면 18 조합이 통째로 같다** — 170번 비교에서 어긋남 0. **개발 환경의 트래픽이 이렇다. 갈래는 한도를 넘는 날 처음 나타난다. 그날은 오픈 날이다.**

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 창 경계 999ms/1000ms에 5+5 | 시계 창은 10 통과(그게 이 알고리즘의 성질) — 정확해야 하면 SLIDING_LOG |
| 정확히 창 길이만큼 지난 요청 | 창은 `(t-창, t]` — 0ms 기록은 1000ms에 빠져 통과. 경계를 닫으면 1ms씩 어긋남 |
| 키 이어붙이기 "ab"+"c" vs "a"+"bc" | 구분자 `\|` 로 다른 키 보장 (assertNotEquals) |
| 사용자 번호 == 주소 문자열 (익명) | `u:` `i:` 접두사로 다른 통 — 접두사 지운 변종은 원래 테스트를 통과했다(약한 테스트를 보강) |
| 토큰 빚의 바닥 | `-capacity`에서 자름 — 없으면 두드린 만큼 기다림이 무한정 늘어남 |
| 잘못된 입력 | 한도<1·창<1ms·빈 사용자/주소·음수 시각 → IllegalArgumentException. 빈 목록의 maxInAnyWindow = 0 |

## 핵심 문장

- "1초에 60번"이라는 한 줄에는 **세 가지 결정이 안 들어 있다** — 창을 어떻게 세나, 무엇을 세나, 막힌 요청도 세나. 이 결정들을 enum으로 드러내는 것이 모델링이다.
- 시계 창은 경계에서 2배가 지나가고, 채워지는 통은 몰아 쓰기로 1.94배가 지나간다 — **한도를 정확히 지키는 것은 훑는 기록뿐**이고, 대신 기록을 들고 다니는 값을 치른다.
- 키는 반드시 **접두사 + 구분자** — "ab"+"c"와 "a"+"bc", 그리고 사용자 번호와 주소 문자열이 같아지는 익명 사용자의 날을 방어한다.
- 막힌 요청까지 세는 벌은 악의적 재시도만이 아니라 **한도를 조금 넘는 모두**에게 가고, 시계 창에서는 아예 죽은 스위치다 — 설정 하나가 알고리즘 선택과 간섭한다.
- 한도 아래 트래픽에서는 18 조합이 전부 같다 — **개발 환경에서는 어느 조합을 골라도 테스트가 통과하고, 갈래는 오픈 날 처음 나타난다.**

## 용어 풀이

- **스로틀링(throttling) / rate limit**: 일정 시간 안의 요청 수에 한도를 두고 넘치면 막는 것.
- **고정 창(FIXED_WINDOW, 시계 창)**: 0~1초, 1~2초처럼 시계 기준으로 자른 창. 창이 바뀌면 카운트를 버린다 — 경계에서 2배 통과.
- **슬라이딩 로그(SLIDING_LOG, 훑는 기록)**: 지금부터 거슬러 창 하나 안의 요청 시각을 전부 기록해 두고 센다. 정확하지만 기록 비용.
- **토큰 버킷(TOKEN_BUCKET, 채워지는 통)**: 통에 든 토큰을 쓰고, 시간이 지나면 일정 속도로 다시 찬다. 몰아 쓰기(burst) 허용.
- **버스트(burst, 몰아 쓰기)**: 짧은 순간에 요청이 몰리는 것. 토큰 버킷은 가득 찬 통만큼 한 번에 허용한다.
- **키(key) / 통(bucket)**: 요청을 분류하는 문자열과, 키마다 하나씩 두는 카운터 상태. 같은 키끼리만 서로를 밀어낸다.
- **NAT / 공유 회선**: 여러 사람이 바깥에서 하나의 주소로 보이는 망. IP로 세면 남이 내 몫을 먹는 원인.
- **빚(debt)**: 막힌 요청까지 셀 때 토큰 버킷이 음수로 내려가는 것. 상한(-capacity)이 없으면 기다림이 무한정 늘어난다.
- **죽은 코드(dead code)**: 지워도 넣어도 결과가 안 바뀌는 코드. 시계 창의 "막힌 요청 세기" 분기가 그랬다.
- **천분율(per mille)**: 1000분의 몇 — 통과율을 소수 없이 정수로 내는 표기(passPerMille).
