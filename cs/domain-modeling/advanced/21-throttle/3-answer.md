### A. 과제

#### 0. 규칙 한 줄이 안 말해주는 것

- 안 말해주는 자리 셋(원본 javadoc 표 그대로):

```text
 안 말해준 것        가능한 읽기
 "1 초를 어떻게"  →  시계의 1 초인가  지금부터 거슬러 1 초인가  채워지는 통인가
 "무엇을 세나"    →  사용자인가  접속 주소인가  둘 다인가
 "막힌 요청도?"   →  막혔어도 한 번으로 세나  안 세나
```

- "1초"를 세는 방법 셋:

```text
 FIXED_WINDOW  시계 창    0~1초, 1~2초 로 잘라 센다. 창이 바뀌면 세던 것을 통째로 버린다
 SLIDING_LOG   훑는 기록  지금부터 거슬러 1초 안의 요청 시각을 다 들고 있다가 센다
 TOKEN_BUCKET  채워지는 통 통에 든 토큰을 쓰고, 시간이 지나면 일정 속도로 다시 찬다
```

> **고정 창(fixed window)** — 시계를 기준으로 자른 칸에 몇 건이 들어왔나만 세는 방식.\
> 예: 0.999초에 5건, 1.000초에 5건이면 "다른 칸"이라 둘 다 통과한다 — 2밀리초 사이에 10건.

> **슬라이딩 로그(sliding log, 훑는 기록)** — 지금 시각에서 창 길이만큼 거슬러 올라간 구간의 요청 시각을 전부 기록해 두고 세는 방식.\
> 예: 지금이 1500ms면 500ms 이후의 기록만 남기고 앞의 것은 버린 뒤, 남은 개수를 한도와 비교한다.

> **토큰 버킷(token bucket, 채워지는 통)** — 통에 든 토큰 하나를 써서 요청을 통과시키고, 시간이 지나면 정해진 속도로 토큰이 다시 차는 방식.\
> 예: 한도 5·창 1초면 200ms마다 토큰 하나가 찬다 — 0ms에 5건 쓰고 200ms에 한 건 더 통과.

- "무엇을 세나" 선택지 셋: **USER**(사용자) · **IP**(접속 주소) · **USER_AND_IP**(둘의 짝).
- "막힌 요청도 세나"가 결정 사항인 이유: 막힌 요청이 **자국을 남기느냐**가 갈린다.\
  남기면 계속 두드리는 쪽이 영영 못 들어오고, 안 남기면 1초 뒤에 열린다.\
  안 정하면 구현자가 아무거나 고르고, 그 선택이 사용자 눈에는 "가끔 안 열림"으로만 보인다.
- 조합 수: 3 × 3 × 2 = **18가지**.
- 서로 간섭하는가: **간섭한다.** "막힌 요청도 세나"는 시계 창에서는 아무 일도 안 한다(죽은 스위치).\
  즉 설정 하나의 효력이 다른 설정의 값에 달려 있다.
- enum으로 올리면 할 수 있는 것: **18 조합을 같은 코드로 돌려 답이 몇 건이나 갈리는지 셀 수 있다.**\
  세어보기 전에는 "구석 사례"인지 "계약의 본체"인지 알 방법이 없다.

#### 1. TODO 1 — key

정답 코드 (impl/Throttle.java):

```java
public String key(Request request, KeyBy keyBy) {
    return switch (keyBy) {
        case USER -> "u:" + request.userId();
        case IP -> "i:" + request.ip();
        case USER_AND_IP -> "u:" + request.userId() + "|i:" + request.ip();
    };
}
```

- 세 키의 모양: `u:a` · `i:회사` · `u:a|i:회사`.
- 구분자를 안 넣으면:

```text
 사용자 "ab" + 주소 "c"   →  구분자 없으면  "abc"
 사용자 "a"  + 주소 "bc"  →  구분자 없으면  "abc"   ← 같은 통!
 구분자 넣으면            →  "u:ab|i:c"  vs  "u:a|i:bc"   ← 다른 통
```

  둘은 남남인데 서로의 한도를 갉아먹는다.\
  테스트가 `assertNotEquals` 로 못 박았다.

> **키 충돌(key collision)** — 서로 다른 두 대상이 같은 키 문자열로 계산되어, 한 칸을 같이 쓰게 되는 것.\
> 예: "ab"+"c"와 "a"+"bc"가 둘 다 "abc"가 되면, 한 사람이 한도를 다 쓸 때 남이 막힌다.

- 숫자면 안 보이는 이유: 사용자 번호가 `1`, `2`, `1234` 처럼 **길이가 고정되지 않은 숫자**라도 주소 쪽이 숫자가 아니면 겹칠 일이 드물다.\
  겹침은 **사용자 번호가 이메일·자유 문자열이 되는 날** 처음 나타난다(테스트 javadoc 원문).
- `u:` `i:` 접두사가 막는 것: **사용자 통과 주소 통이 같아지는 것.**\
  접두사가 없으면 사용자 `10.0.0.1` 과 주소 `10.0.0.1` 이 한 통이 된다.

> **이름공간(namespace)** — 같은 글자라도 어느 종류의 이름인지를 앞에 붙여 구분하는 것.\
> 예: `u:10.0.0.1` 과 `i:10.0.0.1` 은 글자는 같아도 접두사가 달라 다른 통이다.

- 접두사 충돌이 처음 생기는 시점: **익명 사용자를 다루기 시작한 날.**\
  로그인 안 한 사람을 주소로 식별하면 사용자 번호가 곧 주소 문자열이 된다.
- 테스트(`userKeysAndAddressKeysNeverCollide`): 사용자 `10.0.0.1` 이 5번 + 주소 `10.0.0.1` 로 5번 → **10건 다 통과**해야 한다(각각 5건씩이라 한도 5를 안 넘는다). 접두사를 지우면 한 통이 되어 5건이 막힌다.
- 키 하나 = **통(bucket) 하나**. 키가 다르면 서로 밀어내지 않는다.

#### 2. TODO 2 — allow

정답 코드 — 시계 창:

```java
long start = atMillis / windowMillis * windowMillis;
if (start != bucket.windowStart) {
    bucket.windowStart = start;
    bucket.windowCount = 0;
}
if (bucket.windowCount >= limit) {
    // 막힌 요청을 세는 규칙이어도 여기서는 아무 일도 안 한다.
    // 이미 한도를 넘은 상태라 하나 더 세도 여전히 넘은 상태이고,
    // 창이 바뀌면 세던 것을 통째로 버려서 쌓이지도 않는다.
    yield false;
}
bucket.windowCount++;
yield true;
```

- "지금 어느 창인가": `atMillis / windowMillis * windowMillis` — 정수 나눗셈으로 몫만 남기고 다시 곱해 **창의 시작 시각**을 얻는다.\
  999 / 1000 × 1000 = 0, 1000 / 1000 × 1000 = 1000.
- 창이 바뀐 것을 아는 법: 그 시작 시각이 `bucket.windowStart` 와 **다르면** 바뀐 것이다.\
  바뀌면 `windowCount = 0` 으로 **통째로 버린다.**
- 999ms에 5번 + 1000ms에 5번 → 시계 창은 **10건 다 통과**(테스트 `assertEquals(10, ...)`), `maxInAnyWindow` 도 **10**:

```text
 창 [0, 1000)          창 [1000, 2000)
 ├──────────●●●●●─────┼●●●●●────────────┤
        999ms 5건      1000ms 5건
        └─ 여기서 windowCount=5 (가득)
                       └─ start 가 0 → 1000 으로 바뀌어 windowCount=0 리셋

 실제로 지나간 시간: 1밀리초. 지나간 건수: 10건. 한도: 1초에 5건.
```

정답 코드 — 훑는 기록:

```java
while (!bucket.log.isEmpty()
        && bucket.log.peekFirst() <= atMillis - windowMillis) {
    bucket.log.pollFirst();
}
if (bucket.log.size() >= limit) {
    if (mark) {
        bucket.log.addLast(atMillis);
    }
    yield false;
}
bucket.log.addLast(atMillis);
yield true;
```

- 자료구조: **덱(Deque)** — 앞에서 버리고 뒤에 넣는다.\
  기록은 시각 순으로 들어오므로 오래된 것이 항상 맨 앞에 있어, 앞에서만 버리면 된다.

> **덱(deque, double-ended queue)** — 양쪽 끝에서 넣고 뺄 수 있는 줄.\
> 예: 오래된 기록은 `pollFirst` 로 앞에서 버리고, 새 기록은 `addLast` 로 뒤에 붙인다.

- 버리는 조건이 `<=` 인 이유: 창을 **`(t-창, t]`** 로 잡았기 때문이다.\
  `t - windowMillis` **와 같은** 시각의 기록은 창 밖이라 버린다.
- 0ms 기록이 빠지는 시각: **정확히 1000ms.**\
  테스트가 999ms면 막히고(5건) 1000ms면 통과(6건)로 못 박았다.

```text
 0ms 에 5건 기록.  ●●●●●
                   │
  at = 999ms  →  버릴 조건 0 <= 999-1000 = -1  →  거짓. 안 버린다
                 log.size()=5 >= 5  →  막힘   (통과 5건)

  at = 1000ms →  버릴 조건 0 <= 1000-1000 = 0  →  참.  5건을 다 버린다
                 log.size()=0 < 5   →  통과   (통과 6건)
```

- 경계를 `[t-1000, t]` 로 닫으면: 그 한 건이 **1밀리초 더 기다린다.**\
  그리고 그 1밀리초가 재시도 간격과 맞물리면 계속 어긋난다(테스트 javadoc 원문).

정답 코드 — 채워지는 통:

```java
long capacity = (long) limit * windowMillis;
if (bucket.tokensMilli == Long.MIN_VALUE) {
    bucket.tokensMilli = capacity;
    bucket.lastRefill = atMillis;
}
bucket.tokensMilli = Math.min(
        capacity,
        bucket.tokensMilli + (atMillis - bucket.lastRefill) * limit);
bucket.lastRefill = atMillis;
if (bucket.tokensMilli < windowMillis) {
    if (mark) {
        bucket.tokensMilli = Math.max(
                -capacity, bucket.tokensMilli - windowMillis);
    }
    yield false;
}
bucket.tokensMilli -= windowMillis;
yield true;
```

- 용량이 `limit × windowMillis` 인 이유: **토큰 1개를 `windowMillis` 밀리토큰으로 센다.**\
  토큰 `limit` 개가 곧 `limit × windowMillis` 밀리토큰이다.
- 소수를 안 쓰는 이유: 소수(0.005개씩 더하기)로 세면 **부동소수점 오차로 자리가 조금씩 사라지거나 늘어난다.**\
  정수로 세면 그런 일이 없다(README 함정 셋째).

> **부동소수점 오차(floating point error)** — 컴퓨터가 소수를 이진수로 근사해서 생기는 아주 작은 오차.\
> 예: `0.1 + 0.2` 가 `0.30000000000000004` 가 되는 것 — 이런 덧셈을 수만 번 하면 토큰 개수가 어긋난다.

- 채우는 속도: 1밀리초에 `limit` 밀리토큰. 그래서 `windowMillis` 밀리초가 지나면 정확히 `limit` 개가 찬다.
- 처음 쓰일 때: **가득 차 있다**(`tokensMilli = capacity`).\
  그래서 첫 순간에 한 창 분을 통째로 쓸 수 있다 — 몰아 쓰기가 허용된다.
- 한 자리가 열리는 간격 (한도 5 · 창 1000ms):

```text
 capacity = 5 × 1000 = 5,000 밀리토큰
 토큰 1개 = 1,000 밀리토큰
 채우는 속도 = 1 ms 당 5 밀리토큰

 0 ms    5,000 에서 5번 소비 →   0 밀리토큰
 100 ms  0 + 100×5 =   500  <  1,000  →  막힘   (테스트: 통과 5건)
 200 ms  0 + 200×5 = 1,000  >= 1,000  →  통과   (테스트: 통과 6건)
                                          1,000 / 5 = 200ms 마다 한 자리
```

- 기다리는 모양의 차이: 채워지는 통은 **200ms마다 한 자리씩 조금씩** 연다.\
  훑는 기록은 1000ms까지 **한 자리도 안 열다가** 한꺼번에 5자리를 연다.\
  같은 "1초에 5번"인데 사용자가 겪는 모양이 다르다(테스트가 200ms 시점에 훑는 기록은 5건임을 못 박았다).
- 막힌 요청을 셀 때 남는 자국:

```text
 훑는 기록    막혀도 log 에 시각을 하나 더 넣는다  →  창이 계속 가득
 채워지는 통  막혀도 토큰을 한 개분 더 뺀다        →  음수(빚)로 내려간다
 시계 창      아무것도 안 한다                     →  죽은 스위치
```

> **빚(debt)** — 토큰이 0 아래로 내려간 상태. 0으로 올라올 때까지는 아무것도 통과하지 못한다.\
> 예: 100번 두드려 -95개가 되면, 다시 0이 될 때까지 기다린 뒤에야 첫 요청이 통과한다.

- 빚에 상한이 없으면: 100번 두드린 사람이 **20초를 기다린다**(README 함정 넷째).\
  상한을 `-capacity` 로 두면 아무리 두드려도 **1초 뒤에는 회복한다.**\
  테스트(`debtNeedsACeiling`): 10ms마다 100번 폭주 후 3000ms의 한 건 → 총 **6건 통과**(5 + 뒤의 1건), 마지막 통과의 id는 `"after"`.
- 시계 창에서 분기가 죽는 이유: 막히는 자리는 **이미 `windowCount >= limit` 인 상태**다.\
  거기서 하나 더 세도 여전히 넘은 상태이고, 창이 바뀌면 통째로 버려 **쌓이지도 않는다.**

```text
 a0 a1 a2  b0 b1 b2  c0 c1 c2   (0~8ms, 전부 "회사" 회선, 한도 5)

 USER 로 세면  u:a 3건  u:b 3건  u:c 3건   →  9건 다 통과. c 도 3건
 IP   로 세면  i:회사 한 통에 9건이 몰림  →  앞의 5건만 통과
                                             a0 a1 a2 b0 b1  ✓
                                             b2 c0 c1 c2     ✗
                                             c 의 통과 건수 = 0
```

- 맨 뒤 사람이 전부 막히는 이유: 통이 **도착 순서대로** 채워지기 때문이다.\

  c 입장에서는 자기가 뭘 잘못했는지 알 방법이 없다.
- `List.copyOf` 로 감싸는 것: **밖에서 결과를 고치는 것**을 막는다(불변 목록).

> **불변 컬렉션(immutable collection)** — 한 번 만들면 원소를 더하거나 뺄 수 없는 목록/맵.\
> 예: `Result` 를 받은 쪽이 `allowed.add(...)` 를 부르면 예외가 난다 — 측정 결과가 조용히 바뀌는 일이 없다.

#### 4. TODO 4 — maxInAnyWindow

정답 코드:

```java
int max = 0;
int from = 0;
for (int to = 0; to < allowed.size(); to++) {
    long end = allowed.get(to).atMillis();
    while (allowed.get(from).atMillis() <= end - windowMillis) {
        from++;
    }
    max = Math.max(max, to - from + 1);
}
return max;
```

- 기법: **두 포인터(슬라이딩 윈도우)** — 오른쪽 끝 `to` 를 한 칸씩 밀면서, 창 밖으로 나간 왼쪽 끝 `from` 을 앞으로 민다.\
  `from` 은 뒤로 안 돌아가므로 전체가 O(n)이다.

> **두 포인터(two pointers)** — 목록 위에서 시작 위치와 끝 위치를 각각 하나씩 두고, 둘 다 앞으로만 밀며 훑는 방법.\
> 예: 여기서는 `from`·`to` 가 각각 최대 n번만 움직여서, 매번 처음부터 다시 세는 O(n²)이 O(n)이 된다.

- 조건이 `<= end - windowMillis` 인 이유: `allow` 의 창 판정과 **같은 경계 규칙**을 쓰기 위해서다.\
  `end - windowMillis` 와 같은 시각은 창 밖이다.
- 방향이 반대인 것처럼 보이는 이유: javadoc은 창을 `[t, t + windowMillis)` 로 쓴다.\
  같은 구간을 오른쪽 끝에서 보면 `(t - windowMillis, t]` 다 — **같은 창을 어느 끝에서 이름 붙였느냐의 차이**일 뿐 규칙은 하나다.

```text
 같은 창을 두 가지 이름으로 부른 것

  [ t ────────────── t+창 )      왼쪽 끝 기준:  시작은 포함, 끝은 제외
  ( end-창 ────────── end ]      오른쪽 끝 기준: 시작은 제외, 끝은 포함
```

- 빈 목록: **0**(테스트 `assertEquals(0, small().maxInAnyWindow(List.of()))`). 루프가 한 바퀴도 안 돌아 `max` 가 초기값 그대로 나온다.
- 이 함수가 없으면: "통과 건수"만으로는 한도가 지켜졌는지 모른다.\
  10초 동안 600건 통과가 고르게 흘러간 것인지, 1초에 몰린 것인지 구별이 안 된다.\
  **한도는 "총합"이 아니라 "어느 한 창 안"의 약속**이므로 창 단위로 재야 한다.
- 이 값이 한도와 같으면 항상 좋은가: **아니다.** 훑는 기록은 1,200을 정확히 지키지만 **기록을 전부 들고 다니는 메모리 값**을 치른다.\
  그리고 "정확함"이 곧 "좋은 사용자 경험"도 아니다 — 훑는 기록은 1초 동안 한 자리도 안 열어준다.

### B. 개념

#### 5. 함정 (README)

- 넷: ① **키를 그냥 이어 붙이는 것** ② **사용자 통과 주소 통을 안 나누는 것** ③ **통을 소수로 세는 것** ④ **빚에 상한을 안 두는 것**.
- ① 한 문장: 사용자 "ab"+주소 "c" 와 "a"+"bc" 가 **같은 통이 되어 남의 한도를 쓴다.**
- ② 터지는 곳: **익명(로그인 안 한) 사용자를 주소로 식별하는 서비스.**\
  사용자 번호 자리에 주소 문자열이 들어가 두 통이 겹친다.
- ③ 위험한 이유: 소수 덧셈을 수만 번 반복하면 **부동소수점 오차로 토큰이 조용히 늘거나 준다.**\
  한도가 60인데 실제로는 59.9997이 되는 식이고, 아무 에러도 안 난다.
- ④ 숫자로: **100번 두드린 사람이 20초를 기다린다**(README 원문). 상한을 `-capacity` 로 두면 1초다.

#### 6. 측정 — 18 조합이 얼마나 갈리나

전제(MeasurementTest): 사용자 20명 × 10초 × 1인당 1,200건 = 초당 120건(한도의 2배), 10회 반복. `burstPercent` 는 그 확률로 요청이 **초 경계 앞뒤 50ms 안**에 떨어진다는 뜻이다.

- 한 창 상한 1,200을 지킨 알고리즘: **훑는 기록(SLIDING_LOG)뿐**이다.

```text
 한 창 최대 통과 수 (상한 = 60 × 20명 = 1,200)

 몰림     시계 창    훑는 기록   채워지는 통
  0 %      1,311      1,200       2,328
 30 %      1,689      1,200       2,334
 80 %      2,278      1,200       1,781
```

- 시계 창이 몰릴수록 나빠지는 이유: **앞 창의 마지막 자리와 뒤 창의 첫 자리가 몇 밀리초 사이에 붙는다**(측정 javadoc 원문).\
  그래서 몰림을 경계 **앞뒤로** 걸쳐야 이 현상이 보인다 — 앞쪽으로만 몰면 두 배 통과가 안 나타난다.
- 채워지는 통이 몰림 0%에서도 2,328인 이유: **통이 가득 찬 채로 시작해 한 창 분을 한 번에 쓰고, 그 창 안에서 또 채워지기 때문**(원문).\
  2,328 ÷ 1,200 = **1.94배**.
- 몰림 80%에서 1,781로 **줄어드는** 것: 요청이 경계 ±50ms의 좁은 구간에 뭉치면, 그 앞의 조용한 900ms 동안 통이 가득 차고 뭉친 구간에서 거의 다 쓰인다.\
  뭉침이 1초 간격이라 **한 창 안에 뭉침 하나만 들어와** 한 창 최대 통과 수가 오히려 내려간다. (원본에 근거 없음 — 내 추론)
- 버그인가 뜻인가: **그 알고리즘의 뜻이다. 몰아 쓰기(burst)를 허용한다**(README 원문).

> **몰아 쓰기(burst)** — 짧은 순간에 요청을 한꺼번에 보내는 것. 토큰 버킷은 통이 가득 찬 만큼을 한 번에 허용한다.\
> 예: 평소 안 쓰다가 한 번에 5건을 몰아 보내면, 토큰 버킷은 다 통과시키고 슬라이딩 로그도 다 통과시키지만 이후 회복 방식이 다르다.

- 주소로 셀 때 통과량이 항상 6,000인 이유: **통이 회선 하나에 하나뿐**이기 때문이다.\
  몇 명이 나눠 쓰든 그 통의 한도는 그대로다 — **회선 하나가 곧 한도다.**

```text
 공유 인원   사용자로 세면   주소로 세면
  0 명       (공유 사용자 통과 0)      —
  2 명           11,993           6,000
  5 명           29,993           6,000
 20 명          119,993           6,000
```

- 6,000의 출처: **60(한도) × 10초 × 10회 = 6,000.**
- 공유 20명이면 한 사람 몫은 **300건** — 단독 사용자의 **20분의 1**이다.\
  그리고 그 사람은 자기가 왜 막히는지 알 방법이 없다(원문).
- 막힌 요청까지 셀 때(정상 17명 + 폭주 3명, 10회):

```text
                          폭주 사용자   정상 사용자
 시계 창    세든 말든        18,000      102,000
 훑는 기록  안 세면          18,000      102,000
 훑는 기록  세면              1,800       10,200   ← 정상도 10분의 1
 채워지는 통 안 세면          19,770      111,898
 채워지는 통 세면              2,458       19,928
```

- 절반이 아니라 10분의 1이 되는 이유: 여기서 "정상 사용자"도 한도의 2배로 부르므로 **절반이 막히는 것까지는 맞다.**\
  그런데 **막힌 절반이 기록에 쌓여 창이 계속 가득 차서, 첫 1초 뒤로는 영영 안 열린다**(원문).
- 의도와 결과의 어긋남: 이 설정은 **"악의적 재시도에 벌을 준다"**는 뜻으로 켠다.\
  그리고 **한도를 조금 넘는 모두에게 같은 벌이 간다**(원문).
- 시계 창에서 120,000으로 같다는 것: **그 설정이 아무 일도 안 한다**는 뜻이다 — 죽은 스위치.\
  설정 화면에 스위치가 보이는데 효력이 없고, **아무 표시도 안 난다.**
- 한도 아래(1인당 300건 = 초당 30건 = 한도의 절반)에서 갈린 횟수: **0**(10회 × 17비교).
- 무서운 이유: **개발 환경의 트래픽이 딱 그렇다.**\
  어느 조합을 골라도 테스트가 통과하니 결정이 미뤄지고, **갈래는 한도를 넘는 날 처음 나타난다. 그날은 오픈 날이다.**

#### 7. 변종 검증에서 고친 것

- 약한 테스트: 키의 `u:` `i:` 접두사를 **지워도 테스트가 통과했다.**\
  **사용자 번호와 주소 문자열이 같은 경우를 안 만들었기 때문**이다.\
  그래서 `userKeysAndAddressKeysNeverCollide` 를 보강했다.

> **변종 검증(mutation testing)** — 코드를 일부러 조금 망가뜨린 뒤 테스트가 그 망가짐을 잡아내는지 보는 방법.\
> 예: 키에서 접두사를 지운 "변종"을 만들었는데 테스트가 다 통과하면, 그 테스트는 접두사를 실제로 검증하고 있지 않았던 것이다.

- 죽은 코드: **시계 창에서 막힌 요청을 세는 분기.**\
  이미 한도를 넘은 상태라 하나 더 세도 여전히 넘은 상태이고, 창이 바뀌면 세던 것을 통째로 버려 쌓이지도 않는다.
- 지우고 주석을 남긴 이유: 지우기만 하면 **다음 사람이 "빠뜨린 것"으로 보고 다시 넣는다.**\
  "왜 없는지"가 코드에 남아야 같은 자리를 두 번 안 돈다.

> **죽은 코드(dead code)** — 넣어도 빼도 결과가 달라지지 않는 코드.\
> 예: 시계 창의 거절 분기에서 카운트를 더해도, 이미 한도를 넘었으니 판정도 그대로고 창이 바뀌면 버려진다.

- 사용자에게 보이는 모습: **아무것도 안 보인다.**\
  스위치는 켜져 있고, 설명도 붙어 있고, 효력만 없다.

#### 8. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- **언제 다시 오라고 알려주나**: 알고리즘마다 그 답이 실제로 다르다.

```text
 시계 창     다음 창 시작까지  →  창 경계에 전원이 한꺼번에 몰려온다(재몰림)
 훑는 기록   log 의 맨 앞 기록 + 창 길이  →  사람마다 다른 시각. 잘 흩어진다
 채워지는 통 토큰이 1개분 찰 때까지 →  한도 5·창 1초면 200ms. 가장 촘촘하다
```

  즉 `Retry-After` 헤더를 정확히 채우려면 **알고리즘마다 다른 식**이 필요하다.\
  그리고 시계 창에서 정직하게 알려주면 **모두 같은 시각을 받아 다시 몰린다** — 약간의 흔들림(jitter)을 섞어야 한다. (원본에 근거 없음 — 내 추론)
- **회선을 같이 쓰는 사람에게 무엇을 보여주나**: 지금 코드는 `allowedByUser` 로 **누가 몫을 못 받았는지**까지는 안다.\
  그런데 "당신 회사 회선의 다른 분들이 한도를 썼습니다"는 **남의 사용 정보를 흘리는 말**이다.\
  실무의 타협은 보통 "이 회선에서 요청이 많습니다 — 로그인하시면 개인 한도가 적용됩니다"처럼, **원인은 알려주되 누구인지는 안 알려주는** 문구다. (원본에 근거 없음 — 내 추론)
- **한도를 넘는 앱이 우리 앱이면**: 테스트 javadoc이 "**두드리는 쪽은 대개 버그가 난 우리 앱이다**"라고 못 박았다.\
  벌(`CountRejected.YES`)은 악의를 가정하는데, 실제 다수는 재시도 로직이 잘못된 **우리 클라이언트**다.\
  그러면 벌은 공격을 막는 대신 **우리 앱의 복구를 늦춘다** — 고치는 방향은 서버의 벌이 아니라 클라이언트의 지수 백오프(backoff)다. (원본에 근거 없음 — 내 추론)

> **지수 백오프(exponential backoff)** — 실패할 때마다 다시 시도하는 간격을 두 배씩 늘리는 방법.\
> 예: 막히면 1초, 또 막히면 2초, 4초… 이렇게 늘리면 훑는 기록의 창이 비워질 틈이 생긴다.

- **몰아 쓰기를 허용할 것인가**: 허용하면(채워지는 통) **한 사람이 통을 비운 동안 뒤 사람이 기다린다.**\
  측정의 2,328이 바로 그 값이다 — 한도의 1.94배가 한 창 안에 몰린다.\
  허용 안 하면(훑는 기록) 정확하지만, 정상적으로 몰아 쓰는 사용자(첫 화면 로딩에 API 10개 호출)까지 막힌다.\
  실무에서는 "평소 속도는 낮게, 통 크기는 조금 크게" 두 값을 따로 주는 식으로 절충한다. (원본에 근거 없음 — 내 추론)

#### 9. 연결

- 세는 것의 차이: 알고리즘 트랙은 **비교 횟수**(같은 답으로 가는 비용)를 셌다.\
  여기서 세는 것은 **18 조합 중 답이 갈리는 건수** — 답 자체가 여럿이라 비용이 아니라 **불일치**를 잰다.
- 훑는 기록의 "앞에서 버리기"는 알고리즘 트랙의 **슬라이딩 윈도우 / 단조 덱**과 같은 자리다.\
  `maxInAnyWindow` 의 두 포인터도 정확히 같은 기법이다.
- 경계 포함/미포함(`(t-창, t]`)은 **01-parking-fee의 "10분까지는 무료인가"**, 그리고 구간 겹침을 다루는 박스들과 같은 문제다 — 한쪽 끝을 포함하느냐가 답을 가른다.
- 조합을 전부 돌려보는 방식은 실무의 **기능 플래그(feature flag) + A/B 비교**와 같다.\
  값으로 올려 두면 "누가 언제 무엇으로 정했는지"가 남고, 두 판을 나란히 돌려볼 수 있다.
- 스로틀링과 스탬피드(stampede)의 관계: 둘 다 **"같은 순간에 몰리는 것"** 이 문제다.\
  다른 점은 스탬피드가 **캐시가 비는 순간** 뒤로 몰리는 것이고, 스로틀링은 **창이 바뀌는 순간** 앞으로 몰리는 것이다.\
  해법의 모양도 닮았다 — 시각을 흩뜨리는 흔들림(jitter)을 섞는다. (원본에 근거 없음 — 내 추론)
