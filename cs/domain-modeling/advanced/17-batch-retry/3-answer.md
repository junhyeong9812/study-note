### A. 과제

#### 0. 요구사항 한 줄이 안 말해주는 것

- 안 정해준 갈래는 **셋**이다(원본 javadoc 그대로):

```text
  실패를 만나면      거기서 멈추나 건너뛰나 통째로 되돌리나     3 택
  재시도 범위는      실패한 건만인가 그 뒤 전부인가 배치 전체인가 3 택
  결과를 모르면      실패로 보나 성공으로 보나                   2 택
```

- 조합 수: **3 × 3 × 2 = 18개**.\
  README 제목이 "열여덟 조합"인 것이 이 곱이다.
- 같이 쓰면 구멍 나는 예: **멈추기(STOP) + 실패한 건만 재시도(FAILED_ONLY)**.\
  멈추면 뒤가 "안 돌린 것"으로 남는데, 재시도는 "실패한 것"만 다시 돈다.\
  그래서 안 돌린 것은 **영영 아무도 안 돌린다.**
- 평소에 안 보이는 이유: **그 구멍은 실패가 나야 열린다.**\
  측정 여섯: 문제 0%면 18조합 × 100회 = 1,800번이 통째로 같다(어긋남 0).\
  개발할 때 도는 배치는 대개 문제가 없어서, 아무 조합이나 골라도 테스트가 통과한다.
- 그냥 버그가 아닌 이유: 두 규칙 **각각은 요구사항대로 정확히 동작한다.**\
  틀린 것은 코드가 아니라 "실패하면 재시도한다"는 **한 줄이 조합을 안 정해줬다는 것**이다.\
  코드를 고쳐서 없앨 수 없고, 규칙을 정해야 없어진다.
- 채점표: **`Ledger` 의 건별 반영 횟수(`applications(id)`)이고 정답은 1회다.**\
  "에러 없이 끝났다"는 아무것도 말해주지 않는다 — 구멍은 전부 **예외 없이** 열린다.

> **조용한 실패(silent failure)** — 프로그램이 에러를 안 내고 정상처럼 끝나는데 결과만 틀린 것.\
> 예: 4번과 5번이 한 번도 안 돌았는데 배치가 "성공"으로 보고되고, 다음 날 아무도 안 본다.

#### 1. 계약 — BatchJob

- 거부하는 입력 셋: **빈 작업 번호**, **빈 주문 번호**, **0 이하 금액**.\
  전부 `IllegalArgumentException` 이다(테스트 `rejectsBadInput`).
- 금액 0을 막는 이유: 금액 0짜리는 **반영해도 장부 잔액이 안 움직여서**, 반영됐는지 안 됐는지를 잔액으로 구별할 수 없다.\
  채점표가 안 통하는 데이터를 애초에 못 들어오게 막는 것이다.
- `id` 와 `orderId` 를 따로 두면: **재시도로 같은 주문을 다시 처리하는 상황**을 표현할 수 있다.\
  한 주문에 대해 작업 번호가 여러 개일 수 있고, 멱등 키를 붙인다면 붙일 자리가 `orderId` 쪽이다.\
  (이 박스의 코드는 멱등 키를 안 쓴다 — 자리만 있다.)

#### 2. 계약 — Ledger (채점표)

- 뭉개지는 자리:

```text
  실제로 일어난 일(Scripted)        호출한 쪽이 보는 것(Outcome)
    DONE             되고 응답 옴      →  DONE
    FAILED           안 되고 응답 옴    →  FAILED
    UNKNOWN_APPLIED  됐는데 응답 없음   ┐
    UNKNOWN_LOST     안 됐고 응답 없음  ┴→  UNKNOWN   ← 넷이 셋으로 줄어든다
```

- 구별할 방법: **없다.** 원본 javadoc이 못 박은 문장 — "호출한 쪽에서는 둘 다 그냥 UNKNOWN 이다. 구별할 방법이 없다."
- 이 구별 불가가 만드는 어려움: 어느 쪽으로 놓든 **반대 실체에서는 틀린다.**\
  실패로 놓으면 이미 반영된 건이 두 번 나가고, 성공으로 놓으면 안 나간 돈이 영영 안 나간다.\
  그래서 **정답이 있는 문제가 아니라 방향을 고르는 문제**가 된다.

> **정보 손실(information loss)** — 바깥에서 볼 수 있는 상태가 실제 상태보다 가짓수가 적은 것.\
> 예: 실제로는 4가지 일이 일어나는데 호출한 쪽은 3가지 결과만 본다 — 남은 1가지는 영영 못 알아낸다.

- `applications(id)` 를 채점표로 삼는 이유: **잔액은 초과와 누락이 서로를 지운다.**\
  측정 둘 — 초과 2,183,000 · 누락 6,581,000 인데 총액 차이는 4,398,000 하나로만 보이고,\
  그 안에 숨은 **이중 처리 5,157건**은 잔액으로 절대 안 보인다.
- `undo()` 가 "언제나 성공한다고 본다"인 것: **문제를 하나로 좁히기 위한 단순화**다.\
  실제로는 되돌리기도 네트워크 호출이라 실패하고 UNKNOWN 도 난다 — 그러면 "되돌리기의 되돌리기"라는 갈래가 또 생긴다.\
  README "생각해볼 것"이 그것을 질문으로 남겨뒀다.
- 대본이 떨어지면 성공으로 주는 이유: 원본 주석 — **"재시도는 대개 결국 성공하기 때문이다."**\
  첫 회차만 흔들리고 다음 회차에 붙는 실제 배치의 모습을 흉내 낸 것이다.

> **대본(scripted fake)** — 테스트에서 "몇 번째 호출에 무슨 일이 일어날지"를 미리 정해두는 가짜 부품.\
> 예: `new Ledger().schedule("3", Scripted.FAILED)` 는 3번 작업의 첫 호출만 실패시키고 그 뒤는 성공시킨다.

#### 3. TODO 1 — succeeded

정답 코드 (impl/BatchRunner.java):

```java
return switch (outcome) {
    case DONE -> true;
    case FAILED -> false;
    case UNKNOWN -> unknownRule == UnknownRule.TREAT_AS_DONE;
};
```

- `DONE` → true, `FAILED` → false, `UNKNOWN` → **규칙이 정한다**(TREAT_AS_DONE 이면 true).
- `TREAT_AS_FAILED` 의 사고: 다시 돈다 → **이미 반영된 건이 두 번 반영된다**(이중 처리).\
  테스트: 3번이 `UNKNOWN_APPLIED` 일 때 장부 6,000(정답 5,000), `applications("3") == 2`.
- `TREAT_AS_DONE` 의 사고: 안 돈다 → **안 된 건이 영영 안 된다**(누락).\
  테스트: 3번이 `UNKNOWN_LOST` 일 때 장부 4,000인데 `run.complete()` 는 **true** 다 — 다 끝났다고 보고한다.
- "한 줄"의 정확한 위치: `case UNKNOWN -> unknownRule == UnknownRule.TREAT_AS_DONE;` **이 한 줄**이다.\
  18조합 중 2배를 만드는 갈래가 전부 여기서 갈린다.
- enum 으로 밖에 올린 것의 차이: **두 판을 같은 코드로 나란히 돌려 얼마나 갈리는지 잴 수 있다.**\
  코드 안에 하나 박으면 그 선택이 숨어서, 나중에 "왜 두 번 나갔냐"는 문의가 와도 어디가 갈림인지 못 찾는다.

> **정책 외부화(policy as a value)** — 답이 갈리는 자리를 코드에 박지 않고 값(enum·설정)으로 끌어올리는 것.\
> 예: `UnknownRule` 이 값이라 같은 자료에 두 규칙을 돌려 "초과 628,000 vs 누락 693,000"을 잴 수 있었다.

#### 4. TODO 2 — runOnce

정답 코드:

```java
for (int i = 0; i < jobs.size(); i++) {
    BatchJob job = jobs.get(i);
    if (!failed.isEmpty() && failureRule == FailureRule.STOP) {
        untouched.add(job);
        continue;
    }
    Outcome outcome = ledger.apply(job);
    if (outcome == Outcome.UNKNOWN) {
        unknownSeen++;
    }
    if (succeeded(outcome, unknownRule)) {
        done.add(job);
    } else {
        failed.add(job);
    }
}

boolean rolledBack = failureRule == FailureRule.ROLLBACK && !failed.isEmpty();
if (rolledBack) {
    for (BatchJob job : done) {
        ledger.undo(job);
    }
}
```

- **`continue` 다.** `break` 로 끊으면 루프를 빠져나가서 **남은 건을 `untouched` 에 못 담는다.**\
  "손을 뗀다"는 것은 `ledger.apply` 를 안 부른다는 뜻이지 목록 만들기를 그만둔다는 뜻이 아니다.\
  안 돌린 것을 못 담으면 `FROM_FAILED_ON` 재시도가 아예 불가능해진다.
- 멈춘 뒤의 건: **`untouched`** 다. 실패한 게 아니라 시도조차 안 한 것이다.
- 되돌리기를 루프 끝에서 하는 이유: **끝까지 돌아본 뒤 실패가 하나라도 있으면** 되돌리는 규칙이라서다.\
  도중에 되돌리면 "뒤에 실패가 또 있나"를 아직 모른다.
- 되돌리는 대상: **이번 회차의 `done` 만.**\
  `jobs` 전부를 되돌리면 안 반영된 건까지 빼서 잔액이 마이너스로 내려간다.
- `SKIP` 에서 `untouched` 가 늘 빈 이유: `untouched.add` 는 `failureRule == STOP` 조건 안에만 있다.\
  건너뛰기는 실패해도 계속 가므로 안 돌린 건이 생길 수 없다.
- `unknownSeen`: `ledger.apply` 가 `UNKNOWN` 을 돌려줄 때마다 올라간다.\
  이 값이 알려주는 것은 **"이번 결과를 얼마나 못 믿을 수 있는가"** 다 — 0이면 규칙 선택이 결과를 안 바꾼다.
- 다섯 칸인 이유: **대응이 다른 상태를 한 통에 안 넣으려고.**\
  `done`(끝) / `failed`(원인을 봐야 함) / `untouched`(다시 돌리면 됨) / `unknownSeen`(못 믿을 정도) / `rolledBack`(이 회차 성공을 성공으로 세면 안 됨).

> **부분 실패(partial failure)** — 여럿을 처리하다가 일부만 실패해서, 전부 성공도 전부 실패도 아닌 상태.\
> 예: 5건 중 3번만 실패해서 장부에 2,000원이 남아 있는 상태 — 처음부터 다시 돌릴 수도, 그냥 끝낼 수도 없다.

#### 5. Attempt.clean()

- `untouched.isEmpty()` 를 같이 안 보는 이유: **같은 것을 두 번 보는 것**이기 때문이다.\
  안 돌린 것은 `failed` 가 비어 있지 않을 때만 생긴다(위 코드의 `!failed.isEmpty() &&` 조건).\
  그러니 `failed.isEmpty()` 가 참이면 `untouched` 도 반드시 비어 있다.
- 불변식 한 문장: **"안 돌린 것은 실패한 것이 하나라도 있을 때만, 그리고 실패한 것 뒤에서만 생긴다."**
- 불변식이 깨지는 변경이 들어오면: `clean()` 이 **안 돌린 것이 남았는데도 "깨끗하다"고 답한다.**\
  그 회차가 그대로 종료되고, 안 돌린 건은 `settled` 에도 못 들어가지만 루프가 이미 끝나서 재시도되지 않는다.
- 지운 대가: **방어선이 사라졌으니 불변식이 깨지면 조용히 틀린다.**\
  대신 얻은 것은 "이 조건이 무슨 일을 하는지 아무도 모르는 코드"가 안 남는 것이다.\
  README는 대가를 알고 **주석에 불변식을 적는 것**으로 맞바꿨다.

> **죽은 방어선(dead guard)** — 실제로는 한 번도 참이 될 수 없어 아무 일도 안 하는 방어 코드.\
> 예: 이미 `failed.isEmpty()` 로 걸러진 뒤에 `untouched.isEmpty()` 를 또 확인하는 것 — 항상 참이라 아무것도 못 막는다.

#### 6. TODO 3 — retryJobs

정답 코드:

```java
if (retryScope == RetryScope.WHOLE_BATCH || attempt.rolledBack()) {
    return List.copyOf(jobs);
}
List<BatchJob> retry = new ArrayList<>(attempt.failed());
if (retryScope == RetryScope.FROM_FAILED_ON) {
    retry.addAll(attempt.untouched());
}
return List.copyOf(retry);
```

- 담는 것: `FAILED_ONLY` = **실패한 것만** / `FROM_FAILED_ON` = **실패한 것 + 안 돌린 것** / `WHOLE_BATCH` = **이번 회차에 돌린 목록 전부**.
- `rolledBack` 이면 범위를 안 보는 이유: **되돌린 것도 다시 돌려야 하기 때문**이다.\
  되돌리기는 "이번 회차 것을 다 물리는" 것이라 성공했던 1·2·4·5도 장부에서 빠졌다.\
  그것들을 다시 안 돌리면 그 회차는 그냥 **삭제**가 된다 — 돈이 반영됐다가 사라진 채 끝난다.
- "그냥 삭제가 된다": 반영 → 취소 → **끝**. 잔액이 0인데 아무도 다시 안 돌린다는 뜻이다.
- 순서가 계약인 이유: 같은 배치가 회차마다 다른 순서로 돌면 **재현이 안 된다.**\
  장애를 재현해서 원인을 찾는 일이 불가능해지고, 순서에 의존하는 작업(잔액 검사 같은 것)은 결과까지 달라진다.
- 저절로 원래 순서가 되는 까닭:

```text
  원래 목록      1   2   3   4   5
  STOP 규칙            ↑ 여기서 실패
  failed                   [3]
  untouched                    [4 5]   ← 실패 뒤에서만 생긴다

  failed 뒤에 untouched 를 붙이면   [3][4 5] = 3 4 5   ← 이게 원래 순서
```

- 이 성질에 기대는 것이 안전한가: **지금 구현에서는 안전하다.**\
  `runOnce` 가 `for (i = 0 .. size)` 로 원래 순서를 훑고, 두 목록 모두 그 순서로만 담기기 때문이다.\
  다만 이것도 **불변식에 기댄 것**이라, `runOnce` 를 병렬로 돌리는 등 순회 방식을 바꾸면 같이 깨진다(위 5번과 같은 종류의 대가다).

> **재현성(determinism)** — 같은 입력을 주면 언제 돌려도 같은 결과·같은 순서가 나오는 성질.\
> 예: 측정 테스트가 `new Random(3)` 으로 씨앗을 고정하는 것도 같은 이유다 — 안 그러면 628,000 같은 숫자를 못 박을 수 없다.

#### 7. TODO 4 — run

정답 코드:

```java
while (attempts < maxAttempts && !pending.isEmpty()) {
    attempts++;
    Attempt attempt = runOnce(pending, ledger, failureRule, unknownRule);
    unknownSeen += attempt.unknownSeen();
    if (!attempt.rolledBack()) {
        for (BatchJob job : attempt.done()) {
            settled.add(job.id());
        }
    }
    if (attempt.clean()) {
        pending = List.of();
        break;
    }
    pending = retryJobs(pending, attempt, retryScope);
}

for (BatchJob job : jobs) {
    if (!settled.contains(job.id())) {
        unresolved.add(job.id());
    }
}
```

- 멈추는 조건 둘: **회차를 다 썼거나**(`attempts < maxAttempts` 가 거짓) **돌릴 게 없거나**(`pending` 이 빔).\
  여기에 "깨끗하게 끝나면 `break`" 가 하나 더 있다.
- `!attempt.rolledBack()` 이 필요한 이유: **되돌린 회차의 "됐다"는 됐던 게 아니다.**\
  그 건들은 곧바로 `undo` 돼서 장부에서 빠졌다.\
  세면 **장부 잔액 0인데 배치는 성공**이라는 보고가 나온다(테스트 `rollbackOnTheLastAttemptSettlesNothing`).
- `unresolved` 를 전체에서 빼서 만드는 이유: **안 돌린 건은 어느 회차의 `failed` 에도 안 들어간다.**\
  STOP + FAILED_ONLY 에서 4·5는 2회차 `pending` 에서 아예 빠지므로, 마지막 `Attempt` 만 보면 **흔적도 없이 사라진다.**\
  "원래 목록에 있었는데 settled 에 없는 것"으로 세야만 잡힌다.

```text
  원래 목록      1 2 3 4 5
  1 회차 done    1 2          failed 3    untouched 4 5
  2 회차 pending [3]          → done 3 → clean → 끝
  settled        {1,2,3}
  마지막 failed  (비어 있음)   ← 이것만 보면 "실패 0건 = 성공"
  전체 - settled {4,5}         ← 이렇게 세야 구멍이 보인다
```

- `Set<String>` 인 이유: `WHOLE_BATCH` 재시도에서는 **같은 작업이 여러 회차에 done 으로 나온다.**\
  `List` 면 같은 번호가 두 번 쌓여 "끝난 작업 수"가 부풀고, `Set` 이면 한 번만 남는다.\
  `LinkedHashSet` 이라 원래 순서도 유지된다(테스트가 `unresolved` 순서를 `[1,2,3,4,5]` 로 못 박았다).
- 회차를 다 썼는데 안 끝났으면 `complete()` 는 **false** 다 — `unresolved` 가 안 비었기 때문.\
  테스트 `exhaustingAttemptsIsNotSuccess`: attempts 3 · complete false · unresolved `[3]` · 장부 4,000.
- `attempts` 를 담는 이유: **몇 번 흔들렸는지가 운영 신호**다.\
  1회차에 끝난 배치와 3회차 만에 끝난 배치는 장부가 같아도 상태가 다르다(후자는 이중 처리 위험을 이미 지나왔다).

#### 8. 테스트가 못 박은 숫자

- 0과 4,000이 남는 게 증거인 이유: **입력도 같고 실패도 같은데 결과가 다르다.**\
  결과를 가른 것은 코드의 버그가 아니라 **아직 안 정한 규칙**뿐이다.
- STOP + FAILED_ONLY(끝까지): 장부 **3,000**(5,000이어야 함) · `unresolved = [4, 5]` · `applications("4") == 0` · `complete() == false`.
- STOP + FROM_FAILED_ON: 장부 **5,000** · 이중 처리 0 · `complete() == true`. **멈추기의 짝은 이쪽이다.**
- SKIP + WHOLE_BATCH: 장부 **9,000**(5,000이어야 함) · 이중 처리 **4건** · `applications("1") == 2`.

```text
  SKIP + WHOLE_BATCH 손계산
   1 회차   1 2 4 5 반영(+4,000)   3 실패
   2 회차   전체 다시 → 1 2 3 4 5 반영(+5,000)
   장부      4,000 + 5,000 = 9,000      정답은 5,000
   두 번 반영된 것  1 2 4 5 → 4 건
```

- ROLLBACK + WHOLE_BATCH(상한 3): 1번은 **반영 → 취소 → 반영으로 세 번 건드려지고 최종 반영 횟수는 1**이다.\
  attempts 2 · 장부 5,000 · `doubleApplied() == 0`.\
  되돌리기가 깨끗해 보이는 것은 **잔액만 볼 때**고, 이력에는 세 줄이 남는다.
- 회차 상한을 1로 두면: 되돌린 뒤 다음 회차가 없어서 **덮어쓸 기회가 사라진다.**\
  그래서 "장부 0인데 배치 성공"이라는 버그가 드러난다 — 장부 0 · settled 비어 있음 · unresolved 5건 전부 · complete false.
- 3번이 `UNKNOWN_APPLIED`(SKIP + FAILED_ONLY):

```text
  실패로 보기   3 을 다시 돈다 → 두 번 반영   장부 6,000   applications("3") = 2
  성공으로 보기 3 을 안 돈다   → 한 번 반영   장부 5,000 ✓ applications("3") = 1
```

- 3번이 `UNKNOWN_LOST`(같은 조합):

```text
  실패로 보기   3 을 다시 돈다 → 한 번 반영   장부 5,000 ✓
  성공으로 보기 3 을 안 돈다   → 안 반영      장부 4,000   그런데 complete() = true
                                              unknownSeen = 1 만 남는다
```

  **위 둘은 호출한 쪽에서 구별이 안 되는 같은 상황이다** — 어느 규칙을 골라도 한쪽에서 틀린다.
- 3번이 세 번 다 실패(상한 3, SKIP + FAILED_ONLY): `attempts = 3` · `complete() = false` · `unresolved = [3]` · 장부 **4,000**.

### B. 개념

#### 9. 측정 — 열여덟 조합

- 정확히 맞는 조합: **0개.** 작업 200 · 문제 10% · 100회에서 18조합 전부가 초과 아니면 누락을 낸다.
- 있어야 할 잔액: **20,000,000** (`SIZE 200 × 1,000 × 100회`).
- STOP + FAILED_ONLY + 실패로 보기: 초과 0 · 누락 **18,992,000** · 이중 28.\
  있어야 할 20,000,000 중 19,000,000 가까이가 안 나갔다 — **95% 가까이 누락**이다.
- SKIP + WHOLE_BATCH: 초과 **18,636,000** · 누락 0 · 이중 **18,636건**.\
  초과 금액 ÷ 1,000 = 이중 건수로 딱 맞는다(작업 한 건이 1,000원이니까).
- 고를 수 있는 것: **어느 방향으로 틀릴 것인가 뿐이다.**\
  결과를 모르는 호출이 하나라도 있으면 맞는 조합이 없다.

> **오라클(채점표, oracle)** — "정답이 무엇인가"를 따로 알고 있는 기준.\
> 예: 여기서는 `applications(id) == 1` 과 잔액 20,000,000 이 오라클이다 — 이게 없으면 18조합 중 무엇이 틀렸는지도 말할 수 없다.

#### 10. 측정 — 초과와 누락이 서로를 가린다

- 멈추기 + 배치 전체 + 성공으로 보기: 초과 **2,183,000** · 누락 **6,581,000** · 이중 **5,157건**.
- 총액만 보면:

```text
  누락  6,581,000
  초과 -2,183,000
  ----------------
  차이  4,398,000   "4,398,000 모자라네" 로만 보인다
```

- 통째로 숨는 것: **이중 처리 5,157건.**\
  누군가의 돈이 두 번 나갔는데 총액에서는 흔적이 없다.
- 건별 검증이 규칙이 되는 이유: 잔액은 **한 숫자로 뭉쳐진 값**이라 두 종류의 틀림이 서로를 지운다.\
  "총액이 맞으니 괜찮다"는 확인이 **이중 처리와 누락이 정확히 상쇄된 최악의 경우**를 통과시킨다.

> **상쇄로 가려짐(masking)** — 서로 반대 방향의 오류가 합산에서 서로를 지워, 겉보기에는 정상으로 보이는 것.\
> 예: 2,183,000원이 더 나가고 6,581,000원이 덜 나갔는데 보고서에는 "4,398,000 부족" 한 줄만 찍힌다.

#### 11. 측정 — 문제 1%여도 절반이 안 돈다

| 문제 비율 | 미처리 (20,000건 중) | 모자란 금액 |
|---|---|---|
| 1 % | **11,762** | 11,732,000 |
| 5 % | 18,024 | 17,986,000 |
| 10 % | 19,020 | 18,992,000 |
| 30 % | 19,656 | 19,616,000 |

- 문제 1%: **11,762건 미처리** — 20,000건의 **약 59%** 다(원본 javadoc: "1 퍼센트에서 이미 59 퍼센트가 안 돌았다").
- 문제 10%는 19,020건, 30%는 19,656건.
- 30배 낮췄는데 절반밖에 안 줄어드는 이유: **미처리 건수를 정하는 것은 문제 비율이 아니라 "첫 실패가 어디서 났나"** 다.\
  첫 실패 뒤는 전부 안 돈다 — 실패가 1건이든 60건이든 뒤가 날아가는 건 같다.
- 첫 실패가 한복판에서 나는 이유: 각 건이 독립적으로 1% 확률로 흔들리면, 첫 흔들림이 나는 위치가 **목록 전체에 골고루 퍼진다.**\
  200건 중 어디서든 균등하게 나므로 평균적으로 **한복판**이고, 그 뒤 평균 절반이 안 돈다.

```text
  200 건, 첫 실패가 100 번째에서 났다고 하면

  [1 ..... 99] 됨   [100] 실패   [101 ..... 200] 안 돌림
   99 건 반영                      100 건이 통째로 안 돈다
   재시도는 [100] 한 건만 → 성공 → "실패 0 건 = 깨끗하게 끝"
```

- 그래도 성공으로 보고되는 이유: `clean()` 은 `failed.isEmpty()` 만 본다.\
  2회차 pending 이 `[100]` 뿐이고 그게 성공하면 `failed` 가 비어서 **깨끗하게 끝났다**고 나온다.\
  이 구멍을 잡아주는 건 `run` 마지막의 "전체 − settled" 계산뿐이다.

#### 12. 측정 — 안전한 쪽이 없다

| 문제 비율 | 실패로 보기 초과 | 성공으로 보기 누락 |
|---|---|---|
| 1 % | 54,000 | 75,000 |
| 5 % | 309,000 | 344,000 |
| 10 % | **628,000** | **693,000** |
| 30 % | 1,962,000 | 1,993,000 |

- 문제 10%: 실패로 보기 초과 **628,000** · 성공으로 보기 누락 **693,000**.
- 비슷한 이유: `UNKNOWN_APPLIED` 와 `UNKNOWN_LOST` 가 **대략 반반씩 생기기 때문**이다.\
  측정 코드가 문제를 `FAILED / UNKNOWN_APPLIED / UNKNOWN_LOST` 셋 중 하나로 고르게 굴린다(`rnd.nextInt(3)`).\
  그래서 "이중 처리로 틀릴 몫"과 "누락으로 틀릴 몫"의 크기가 거의 같다.
- "안전한 쪽으로 놓자"가 방향을 못 주는 이유: **지침이 방향을 주려면 한쪽이 확실히 작아야 하는데 여기는 안 기울어 있다.**\
  628,000과 693,000 사이에는 고를 근거가 없다.
- 누가 결정하나: **도메인(사업)이다.**\
  "돈이 두 번 나가는 것과 안 나가는 것 중 무엇이 나은가"는 기술 결정이 아니다.\
  환불이 쉬운 업이면 초과 쪽, 이중 출금이 치명적인 업이면 누락 쪽을 고른다.
- 초과 금액과 이중 건수의 관계: 측정 테스트가 `assertEquals(over / 1_000, doubles)` 로 못 박았다.\
  작업 하나가 1,000원이므로 **이중 처리 1건 = 초과 1,000원**이 정확히 맞물린다.

> **이중 처리(double apply)** — 같은 작업이 두 번 반영되는 것. 돈이 두 번 나간다.\
> 예: 반영은 됐는데 응답만 안 온 건을 실패로 보고 다시 돌릴 때 생긴다(장부 6,000 / 정답 5,000).

> **누락(missing)** — 반영됐어야 하는데 안 된 것. 돈이 안 나간다.\
> 예: 반영이 안 된 건을 성공으로 보고 안 돌릴 때 생긴다(장부 4,000 / 정답 5,000).

#### 13. 측정 — 되돌리기가 설정을 죽인다

- 세 범위의 결과가 **똑같아진다.**

```text
  FAILED_ONLY     초과 628,000   누락 693,000
  FROM_FAILED_ON  초과 628,000   누락 693,000
  WHOLE_BATCH     초과 628,000   누락 693,000
```

- "설정 화면에 셋을 두고 되돌리기를 켜면" — **그 설정이 아무 일도 안 한다. 그리고 아무도 모른다.**\
  운영자는 범위를 바꿔가며 조정하고 있다고 믿는데 실제로는 전부 배치 전체 재시도다.
- 정확한 한 줄:

```java
if (retryScope == RetryScope.WHOLE_BATCH || attempt.rolledBack()) {
    return List.copyOf(jobs);
}
```

  `attempt.rolledBack()` 이 참이면 `retryScope` 를 아예 안 본다 — **세 값이 같은 가지로 흡수된다.**

#### 14. 측정 — 문제가 없으면 다 같다

- 어긋난 것: **0번** (18조합 × 100회 = 1,800번).\
  전부 한 회차에 끝나고, 장부가 딱 맞고, 안 끝난 것이 없다.
- 교훈: **개발·테스트 환경의 배치는 대개 문제가 없어서, 여섯 갈래를 아무렇게나 골라도 통과한다.**\
  "테스트가 다 통과한다"가 "규칙을 제대로 골랐다"를 전혀 뜻하지 않는다.
- 테스트 전략 한 줄: **실패·UNKNOWN 을 일부러 주입한 테스트가 없으면 이 박스의 계약은 하나도 검증되지 않는다.**\
  그래서 `Ledger.schedule(...)` 로 대본을 깔고, 회차 상한까지 1로 낮춰본다.

#### 15. 함정 넷 (README)

- 넷: ① **안 돌린 것을 실패로 세는 것** ② **결과를 모르는 것을 실패나 성공 한쪽으로 뭉개는 것** ③ **되돌린 회차의 성공을 성공으로 세는 것** ④ **회차를 다 쓴 것을 완료로 보고하는 것**.
- "실패 3건"이 틀린 보고인 이유: 실제로는 **실패 1건 + 안 돌린 것 2건**이다.\
  숫자만 맞추면 3이지만 **무엇을 해야 하는지가 다른 세 건을 한 통에 넣은 것**이다.
- 대응의 차이: **안 돌린 것은 다시 돌리면 되고, 실패한 것은 원인을 봐야 한다.**\
  안 돌린 것을 원인 조사 대기열에 넣으면 아무 원인도 안 나오고, 실패한 것을 그냥 다시 돌리면 같은 이유로 또 실패한다.
- 되돌린 회차의 성공을 성공으로 세면: **"장부 잔액은 0인데 배치는 성공했다"** 가 성립한다.
- 회차를 다 쓴 것을 완료로 보고하면: **그 한 건은 다음 날 아무도 안 본다.**\
  완료 보고가 곧 "볼 필요 없음" 신호라서, 미처리 건이 어느 목록에도 안 남는다.

#### 16. 변종 검증에서 고친 것 (README)

- 약한 테스트: **되돌린 회차의 성공을 끝난 것으로 세도 18개 테스트가 전부 통과했다.**\
  드러낸 방법은 **회차 상한을 1로 두는 것** — 그러니 "장부 0인데 배치 성공"이 바로 나왔다.
- 회차가 남아 있으면 안 보이는 이유: **다음 회차가 같은 건을 다시 돌려서 덮어쓴다.**\
  잘못 센 settled 가 결국 진짜 settled 로 바뀌므로 최종 결과가 같아진다 — **마지막 회차에서 되돌아갈 때만 드러난다.**
- 죽은 방어선 둘: ① `clean()` 이 `untouched` 를 따로 본 것 ② `retryJobs` 가 원래 순서로 다시 훑어 정렬한 것.
- 근거가 된 불변식: **"안 돌린 것은 실패가 있을 때만 생기고, 실패한 것 뒤에서만 생긴다."**\
  앞부분이 ①을 죽이고, 뒷부분이 ②를 죽인다.
- 대신 남긴 것: **주석에 불변식을 적었다.**\
  코드가 아무 일도 안 하면서 자리만 차지하는 대신, "왜 안 해도 되는지"를 글로 남긴 선택이다.

#### 17. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- **나중에 조회해서 확인하면 갈래가 없어지나**: 줄어들지만 안 없어진다.\
  조회로 `UNKNOWN_APPLIED` 와 `UNKNOWN_LOST` 를 구별할 수 있으면 `UnknownRule` 이라는 2택 자체는 사라진다.\
  하지만 **조회도 실패하고 조회 자체가 UNKNOWN 을 낸다.** 갈래가 한 단계 뒤로 밀릴 뿐이다.\
  그리고 조회가 되려면 작업에 조회 가능한 키가 있어야 한다 — `BatchJob.orderId` 가 그 자리다. (원본에 근거 없음 — 내 추론)
- **멱등 키를 주면 재시도 범위를 안 따져도 되나**: **초과는 없어지고 누락은 안 없어진다.**\
  멱등이면 SKIP + WHOLE_BATCH 의 이중 4건(장부 9,000)이 사라지고, `TREAT_AS_FAILED` 의 이중 처리도 사라진다.\
  그러나 STOP + FAILED_ONLY 의 구멍(측정 셋의 11,762건)은 **아예 안 돌린 것**이라 멱등과 무관하다.\
  멱등 키는 "두 번 돌아도 괜찮게" 만들 뿐 "안 돈 것을 돌게" 하지는 못한다. (원본에 근거 없음 — 내 추론)

> **멱등 키(idempotency key)** — 같은 작업 요청에 붙이는 고유 번호. 받는 쪽이 이미 본 번호면 두 번째부터는 아무 일도 안 한다.\
> 예: 3번 작업에 `o-3` 을 키로 주면, 응답이 안 와서 다시 보내도 장부에는 한 번만 반영된다.

- **되돌리기가 실패하면**: 이 코드는 `undo()` 가 항상 성공한다고 보므로 그 갈래가 없다.\
  실제로는 **되돌리기도 DONE/FAILED/UNKNOWN 셋을 낸다.**\
  되돌리기가 UNKNOWN 이면 "반영도 취소도 확실치 않은" 상태가 되어 어느 회차 결과도 못 믿는다.\
  현실적인 대응은 그 건을 **자동 처리에서 빼고 사람 확인 대기열로 보내는 것**이다. (원본에 근거 없음 — 내 추론)
- **미처리 건을 누가 언제 보나**: 코드에는 `Run.unresolved` 라는 **목록만 있고 약속이 없다.**\
  이 박스의 진짜 지적이 그것이다 — 함정 넷이 전부 "그 한 건은 다음 날 아무도 안 본다"로 끝난다.\
  약속이 되려면 `unresolved` 가 비지 않았을 때 **누가·언제까지 처리하는지**가 운영 규칙으로 붙어야 한다. (원본에 근거 없음 — 내 추론)

#### 18. 연결

- 실무의 같은 자리: **결제/송금의 타임아웃**이다.\
  카드 승인 요청을 보냈는데 응답이 안 오면 승인됐는지 모른다 — 다시 보내면 이중 결제, 안 보내면 미결제.\
  실무의 답도 이 박스와 같다: 멱등 키 + 나중 조회(정산 대사) + "어느 방향으로 틀릴지"의 사업 결정.
- 앞 박스들과의 차이: 앞 박스(주차요금 등)는 **답이 여러 개인데 각각은 맞는 답**이라 "몇 건이나 갈리나"를 셌다.\
  여기는 **18개 전부가 틀린다** — 셀 것이 "갈리는 건수"가 아니라 **"어느 방향으로 얼마나 틀리나"** 다.
- ops-patterns 와의 다리: **재시도·백오프·멱등·서킷 브레이커**가 전부 이 자리의 이웃이다.\
  특히 "재시도가 상황을 더 나쁘게 만들 수 있다"는 점이 공통이다(SKIP + WHOLE_BATCH 의 이중 18,636건).
- 장애 주입과의 연결: **구멍은 실패가 나야 열린다**는 것이 곧 **평시 트래픽으로는 못 찾는다**는 뜻이다.\
  그래서 일부러 실패와 타임아웃을 주입해서 돌려봐야 한다 — `Ledger.schedule(...)` 이 그 주입을 테스트 안에서 한 것이다.

> **계약(contract)** — 함수가 "이런 입력에는 이렇게 답한다"고 밖에 약속한 내용.\
> 예: "회차를 다 써도 안 끝났으면 `complete()` 는 false" 는 계약이라, 구현을 어떻게 바꿔도 지켜져야 한다.

> **회차(attempt)** — 배치 목록을 한 바퀴 도는 것. 상한(`maxAttempts`, 기본 3)까지 반복한다.\
> 예: 상한이 3인데 3번 작업이 세 번 다 실패하면 `attempts = 3` 에 `unresolved = [3]` 으로 끝난다.
