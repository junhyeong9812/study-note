## 한눈에 — 쉽게 말하면

**배치 부분 실패 = 반 아이들 30명에게 급식을 나눠주다가 15번째에서 식판이 떨어졌을 때, "누구까지 받았고 누구를 다시 줘야 하나"를 정하는 문제.**

- 식판이 떨어졌을 때 선택지가 있다: 거기서 멈추나(뒤 아이들은 못 받음), 그 아이만 건너뛰고 계속 주나, 아니면 이미 준 것까지 다 걷고 처음부터 다시 하나.
- 다시 줄 때도 선택지가 있다: 못 받은 아이만 주나, 그 아이부터 뒤 전부 주나, 처음부터 전부 다시 주나 — **처음부터 다시 주면 이미 받은 아이가 두 번 받는다.**
- 배치 작업도 똑같은 구조다. "실패하면 재시도한다"는 한 줄에 **정해지지 않은 규칙이 3개** 숨어 있고, 각각은 말이 되는 규칙들이 **같이 쓰면 구멍**을 낸다.
- 최악의 함정: "멈추기 + 실패한 건만 재시도"는 각각 그럴듯한데, 합치면 **안 돌린 뒷건들이 영영 안 돌면서 배치는 성공으로 보고된다.**

```text
  작업 5건, 3번이 실패:  멈추기 + 실패한 건만 재시도

  1회차:  [1 됨] [2 됨] [3 실패] [4 안 돌림] [5 안 돌림]
  2회차:  [3만 다시] → 성공 → "실패 없음 = 깨끗하게 끝"

  4와 5는 한 번도 안 돌았다. 그런데 배치는 성공이다.
```

실무 예: 야간 정산 배치, 대량 송금 배치, 메시지 일괄 발송 — "밤에 돌다 중간에 죽은 배치를 아침에 어떻게 다시 돌리나"가 바로 이 문제다.

## 문제 — 이 챕터가 시키는 것

원본 README가 주는 요구사항은 딱 이만큼이다.

```text
  작업 다섯 건 중 3 번이 실패한다. "실패하면 재시도한다"

    멈추기 + 실패한 건만 재시도
      1 회차  1 2 됨, 3 실패, 4 5 안 돌림
      2 회차  3 만 다시 돈다 -> 성공 -> 깨끗하게 끝났다고 본다

      4 와 5 는 한 번도 안 돌았다. 그런데 배치는 성공이다.
```

> 두 규칙이 각각은 말이 된다. **같이 쓰면 구멍이 난다.**\
> 그리고 그 구멍은 실패가 나야 열린다.

**과제 목록**

- `src/main/java/com/domain/batch/BatchRunner.java` 의 **TODO 1~4** 를 채운다.\
  TODO 1 `succeeded` — 모르는 결과를 규칙대로 성공이나 실패로 놓는다.\

  TODO 3 `retryJobs` — 다음 회차에 돌릴 작업 목록을 만든다.\
  TODO 4 `run` — 다 될 때까지, 또는 회차가 다 될 때까지 돈다.
- `BatchJob` 과 `Ledger` 는 **계약이라 다 주어져 있다** — 고치지 않는다.
- `Ledger` 는 실제로 몇 번 반영됐는지를 센다. **그것이 이 박스의 채점표다**(건별 정답은 1회).

**테스트가 못 박은 계약**(`BatchRunnerTest`)

- 5건 중 3번 실패 → 멈추기 장부 2,000 / 건너뛰기 4,000 / 되돌리기 0.
- 멈추기에서 4,5는 `failed` 가 아니라 `untouched` 다 — 따로 센다.
- 되돌린 회차의 done 은 `settled` 가 아니다(회차 상한 1에서 장부 0 · 미해결 5건).
- STOP + FAILED_ONLY → 장부 3,000 · 미해결 `[4, 5]` · `complete() == false`.
- SKIP + WHOLE_BATCH → 장부 9,000 · 이중 4건.
- 회차를 다 써도 안 끝나면 `complete() == false`.

## 전체 흐름

```text
요구사항: "작업 목록을 돌리고, 실패하면 재시도한다" — 숨은 3택 × 3택 × 2택 = 18조합

  ① 실패를 만나면 (FailureRule)
       STOP      거기서 멈춘다. 뒤는 안 건드린다
       SKIP      그 건만 두고 계속 간다
       ROLLBACK  이번 회차에 반영한 것을 다 되돌린다

  ② 다음 회차에 무엇을 다시 도나 (RetryScope)
       FAILED_ONLY     실패한 건만
       FROM_FAILED_ON  실패한 건 + 그 뒤로 안 돈 건 전부
       WHOLE_BATCH     배치 전체

  ③ 결과를 모르면 (UnknownRule)
       TREAT_AS_FAILED  실패로 보고 다시 돈다 → 이미 됐으면 두 번 된다
       TREAT_AS_DONE    성공으로 보고 안 돈다 → 안 됐으면 영영 안 된다

  runOnce() 한 회차 → Attempt(done/failed/untouched/unknownSeen/rolledBack)
  retryJobs() 다음 회차 목록
  run() 회차 상한까지 반복 → Run(settled/unresolved/…)

  채점표 = Ledger: 작업마다 "실제로 몇 번 반영됐나"를 센다. 정답은 1.
```

## 규칙 1 — 실패를 만나면: 같은 실패인데 장부에 0과 4,000이 남는다

**어떤 요구사항인가**: "실패하면 어떻게 하나" — STOP / SKIP / ROLLBACK 3택.

**예시 입력**: 1,000원짜리 작업 5건, 3번만 실패.

**손계산** (테스트의 실제 값):

```text
             된 것        안 돌린 것    장부 잔액
  멈추기     1 2          4 5           2,000
  건너뛰기   1 2 4 5      없음          4,000
  되돌리기   (다 물림)    없음              0
```

같은 배치, 같은 실패인데 규칙에 따라 장부에 0원과 4,000원이 남는다. "실패하면 재시도"라는 말은 이 셋 중 무엇도 정하지 않았다.

## 규칙 2 — 안 돌린 것 ≠ 실패한 것

**어떤 요구사항인가**: README 함정 1번 — "안 돌린 것을 실패로 세지 마라."

코드 번역: `Attempt` 레코드에 `failed`와 `untouched`가 **별도 필드**다. 멈추기에서 4, 5는 실패한 게 아니라 아예 안 돌린 것이다.

- 한 통에 넣으면 "실패 3건"이라는 보고가 나온다. 실제로는 **실패 1건 + 안 돌린 것 2건**.
- 왜 나누나: **대응이 다르다.** 안 돌린 것은 다시 돌리면 되고, 실패한 것은 원인을 봐야 한다.
- `clean()`은 `failed.isEmpty()`만 본다 — 안 돌린 것은 실패가 있을 때만, 실패한 것 뒤에서만 생기므로 둘 다 보면 같은 것을 두 번 보는 것이다(변종 검증에서 지운 죽은 방어선).

## 규칙 3 — 짝이 맞아야 한다: STOP은 FROM_FAILED_ON과 짝

**손계산** — 같은 자료(5건, 3번 실패)에 재시도 범위만 바꾸면:

| 조합 | 무슨 일이 | 장부 |
|---|---|---|
| STOP + FAILED_ONLY | 3만 다시 돌고 4, 5는 영영 안 돈다 — 그런데 complete | **3,000** (5,000이어야 함) |
| STOP + FROM_FAILED_ON | 3 4 5를 다시 돈다 — 구멍 없음 | **5,000** ✓ |
| SKIP + WHOLE_BATCH | 이미 된 1 2 4 5가 또 반영 (이중 4건) | **9,000** (5,000이어야 함) |

- 규칙 하나하나는 말이 되는데 **조합이 틀린다.** 그리고 그 구멍은 실패가 나야 열린다 — 측정: 문제 0%면 18조합 1,800번이 통째로 같다.
- 재시도가 멱등하지 않으면 범위가 넓을수록 더 망가진다.
- 측정: 문제가 **1%여도** STOP + FAILED_ONLY는 20,000건 중 **11,762건**을 안 돈다 — 첫 실패가 대개 배치 한복판에서 나기 때문. 문제 비율을 낮춰도 이 구멍은 안 작아진다.

**재시도 목록은 원래 순서를 지킨다**: 실패한 것(2, 4) 뒤에 안 돌린 것을 붙이면 그것이 원래 순서다 — runOnce가 원래 순서로 훑기 때문. 같은 배치가 회차마다 다른 순서로 돌면 재현이 안 된다.

## 규칙 4 — 결과를 모르면: 안전한 쪽이 없다

**어떤 요구사항인가**: `Ledger`가 모델링한 핵심 — 결과를 모르는 경우가 실제로는 **두 가지**다:

```text
  UNKNOWN_APPLIED  반영은 됐는데 응답이 안 왔다
  UNKNOWN_LOST     반영도 안 됐고 응답도 안 왔다

  호출한 쪽에서는 둘 다 그냥 UNKNOWN. 구별할 방법이 없다.
```

**손계산** — 3번이 UNKNOWN일 때 (5건 × 1,000원, 정답은 5,000):

| 실제 상황 | 실패로 보기 | 성공으로 보기 |
|---|---|---|
| 반영됐는데 응답만 안 옴 | 다시 돈다 → 두 번 반영 → **6,000** | 안 돈다 → **5,000** ✓ |
| 반영도 안 됨 | 다시 돈다 → **5,000** ✓ | 안 돈다 → **4,000** (영영 안 됨, 그런데 complete) |

같은 UNKNOWN인데 **어느 규칙을 골라도 한쪽에서 틀린다.** 측정: 실패로 보기 초과 628,000 vs 성공으로 보기 누락 693,000 — 두 쪽 크기가 거의 같아서 "안전한 쪽으로 놓자"는 말에 안전한 쪽이 없다. **돈이 두 번 나가는 것과 안 나가는 것 중 무엇이 나은가는 기술 결정이 아니다** — 도메인(비즈니스)이 정할 일이다.

## 규칙 5 — 되돌린 회차의 성공은 성공이 아니다

**어떤 요구사항인가**: README 함정 3번. ROLLBACK 회차에서 "됐다"고 나온 건들은 곧바로 되돌려졌다.

**손계산** — 회차 상한 1, ROLLBACK, 3번 실패:

```text
1회차: 1 2 됨 → 3 실패 → 4 5 됨 → 전부 되돌림
  장부 잔액   0
  끝난 것     없음        ← 1 2 4 5를 settled로 세면?
  안 끝난 것  5건 전부       "장부 0인데 배치 성공"이 된다
```

코드 번역: `run()`에서 `if (!attempt.rolledBack())` 일 때만 done을 settled에 넣는다.

- 변종 검증에서 잡은 약한 테스트: 회차가 남아 있으면 다음 회차가 덮어써서 이 버그가 안 보인다. **회차 상한을 1로 두니** 드러났다.
- 정상 케이스(상한 3): 반영 → 취소 → 반영으로 같은 건이 세 번 건드려지지만 최종 반영 횟수는 1 — 되돌리기가 깨끗해 보이는 것은 잔액만 볼 때고, 장부 이력에는 세 줄이 남는다.
- 되돌리기를 켜면 되돌린 것도 다시 돌려야 해서 재시도 범위가 전부 WHOLE_BATCH가 된다 — 측정: 세 범위의 결과가 똑같아져서 **설정 화면의 범위 설정이 아무 일도 안 한다.**

## 규칙 6 — 회차를 다 써도 안 끝나면 안 끝났다고 낸다

**어떤 요구사항인가**: README 함정 4번 — "회차를 다 쓴 것을 완료로 보고하지 마라."

손계산: 3번이 세 번 다 실패, 상한 3 → `complete() = false`, `unresolved = [3]`, 장부 4,000. 끝까지 안 된 것을 안 세면 배치가 성공했다고 보고되고, **그 한 건은 다음 날 아무도 안 본다.**

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 안 돌린 것을 실패로 센다 | failed / untouched 별도 필드 — 대응이 다르다 |
| UNKNOWN을 한쪽으로 뭉갠다 | 어느 쪽도 안전하지 않음을 드러내고(enum 2택) 방향 선택은 도메인에 넘긴다 |
| 되돌린 회차의 done을 settled로 센다 | rolledBack이면 안 센다 — 장부 0인데 배치 성공이 된다 |
| 회차 소진을 완료로 보고 | unresolved가 비어야만 complete |
| STOP + FAILED_ONLY 조합 | 뒷건이 영영 안 돈다 — STOP은 FROM_FAILED_ON과 짝 |
| SKIP + WHOLE_BATCH 조합 | 이미 된 건이 두 번 반영 — 멱등 키 없이는 범위가 넓을수록 망가진다 |
| 문제 0%에서 테스트 통과로 안심 | 18조합이 통째로 같다 — 구멍은 실패가 나야 열린다 |
| 회차 금액 0 / 상한 0 | 생성자에서 예외 (amount > 0, maxAttempts ≥ 1) |
| 총액만 보고 검증 | 초과 2,183,000과 누락 6,581,000이 상쇄돼 "4,398,000 모자람"으로 보인다 — 건별(applications) 검증 필수 |

## 핵심 문장

- "실패하면 재시도한다"는 한 줄에는 3택(실패 규칙) × 3택(재시도 범위) × 2택(모르는 결과) = 18조합이 숨어 있고, **결과를 모르는 호출이 하나라도 있으면 맞는 조합이 없다** — 고를 수 있는 것은 어느 방향으로 틀릴 것인가뿐이다.
- 각각 말이 되는 규칙도 같이 쓰면 구멍이 난다(STOP + FAILED_ONLY) — 그리고 그 구멍은 실패가 나야 열려서, 문제 0%인 개발 환경에서는 18조합이 다 통과한다.
- 안 돌린 것과 실패한 것은 다른 상태다 — 다시 돌리면 되는 것과 원인을 봐야 하는 것을 한 통에 넣으면 보고도 대응도 틀린다.
- UNKNOWN의 두 실체(반영됨/유실됨)는 호출한 쪽에서 구별이 안 된다 — 이중 처리와 누락 중 무엇이 나은가는 기술이 아니라 도메인이 정한다.
- 채점표는 잔액이 아니라 **건별 반영 횟수**다 — 초과와 누락은 총액에서 서로를 가리고, 이중 처리 5,157건이 통째로 숨는다.

## 용어 풀이

- **배치(batch)**: 작업 여러 건을 한 번에 몰아서 돌리는 처리 방식. 야간 정산·일괄 송금 등.
- **부분 실패(partial failure)**: 배치 중 일부만 실패한 상태. "전부 성공 아니면 전부 실패"가 아니라서 어렵다.
- **회차(attempt)**: 배치를 한 바퀴 도는 것. 상한(maxAttempts)까지 반복한다.
- **되돌리기(rollback)**: 이번 회차에 반영한 것을 전부 물리는 것. 잔액은 깨끗해지지만 이력에는 반영·취소가 다 남는다.
- **멱등(idempotent)**: 같은 작업을 몇 번 반영해도 결과가 한 번과 같은 성질. 멱등하지 않으면 재시도 범위가 넓을수록 이중 반영이 는다.
- **UNKNOWN(모르는 결과)**: 응답이 안 와서 됐는지 안 됐는지 모르는 상태. 실체는 "반영됨(UNKNOWN_APPLIED)"과 "유실됨(UNKNOWN_LOST)" 둘인데 호출한 쪽에서는 구별 불가.
- **이중 처리(double apply)**: 같은 작업이 두 번 반영된 것. 돈이 두 번 나간다.
- **누락(missing)**: 반영됐어야 하는데 안 된 것. 돈이 안 나간다.
- **untouched(안 돌린 것)**: 실패 때문에 시도조차 안 한 작업. 실패와 다르다 — 다시 돌리면 된다.
- **settled / unresolved**: 배치 전체 기준으로 끝난 작업 / 끝까지 안 끝난 작업. unresolved가 비어야 완료다.
- **장부(ledger)**: 실제 반영 횟수를 세는 채점표. 건별 정답은 1회.
