## 한눈에 — 쉽게 말하면

**응모 추첨 = 학교 축제 경품 뽑기.** "응모권 많을수록 당첨 확률이 오르고 중복 당첨은 안 됩니다"라는 안내문으로는 뽑기 규칙이 안 정해진다.

- **누구를 한 사람으로 보나** — 회원 번호? 이름+전화? 주문? ("1인당"의 1인이 누구인가)
- **중복 당첨은 어디까지 막나** — 이벤트 전체에서 한 번? 상품마다 한 번? 안 막나?
- **어떻게 뽑나** — 응모권(쪽지)을 뽑나, 사람을 뽑나?
- 원본의 한 줄 요약: **"1인당"이라는 말에 세 답이 있다.** 응모권은 한 장도 안 늘고 안 준다 — 나뉘는 방식만 바뀐다.

```text
같은 이름·전화로 계정 둘을 만들어 각각 두 번 주문. 건마다 응모권 1장:

  회원 번호로(MEMBER)   → 두 사람, 각각 2장
  이름+전화로(IDENTITY) → 한 사람, 4장
  주문으로(ORDER)       → 네 사람, 각각 1장
                          응모권 총합은 언제나 4장.
```

실무 예: 구매 이벤트 추첨, 래플(한정판 신발 추첨), 경품 당첨자 선정 — 그리고 "조작 아니냐"는 문의에 답할 수 있어야 하는 모든 추첨.

## 전체 흐름

```text
Entry(id, memberId, name, phone, orderId, tickets)   ← 같은 사람을 가리키는 값이 셋
        │
        ▼
key(entry, sumKey)          ← "m:" / "n:이름|p:전화" / "o:" — 접두사 + 구분자
        │
        ▼
aggregate(entries, sumKey)  ← 같은 키끼리 응모권 합산 → 키 순 정렬(★재현성)
        │
        ▼
draw(applicants, prizes, duplicateRule, pick, seed)
   상품(1등→2등→3등…)을 차례로, 인원수만큼 pickOne 반복
   후보 = 중복 규칙에 안 막힌 응모자
     PER_EVENT: 어디서든 당첨된 사람 제외   PER_PRIZE: 이 상품 당첨자만 제외   NONE: 제외 없음
   pickOne: BY_TICKET(응모권 비례) / BY_PERSON(균등)
   후보 없으면 null → 그 상품은 거기서 끝 (채운 척 금지)
        │
        ▼
List<Winner(prizeId, key)> + winsByKey(누가 몇 번 됐나)
```

## 규칙 1 — 무엇으로 합산하나 (SumKey)

**요구사항 문장**: "1인당 응모권 합산" — 그런데 1인이 누구인가. Entry 주석이 답의 부재를 보여준다:

| 키 | 뜻 | 부작용 |
|---|---|---|
| MEMBER (회원 번호) | 계정 기준 | 계정을 여러 개 만들면 여러 사람이 된다 |
| IDENTITY (이름+전화) | 사람 기준 | 계정이 달라도 한 사람. 개명하면 두 사람이 된다 |
| ORDER (주문 번호) | 주문 기준 | 한 사람이 열 번 주문하면 열 사람이다 |

키 문자열 함정 (README 함정 첫째, 21장과 같은 무늬): 구분자 없이 붙이면 이름 "김하"+전화 "1234"와 이름 "김"+전화 "하1234"가 둘 다 "김하1234" — **남남이 한 사람이 되고, 그 둘 중 하나만 당첨된다.** 그래서 `"n:" + name + "|p:" + phone` 처럼 접두사+구분자.

**합산 결과는 키 순으로 세운다** (README 함정 둘째): 안 세우면 입력 순서(조회 쿼리)가 후보 목록 순서가 되어 **같은 seed로도 다른 당첨자가 나온다.** 추첨은 다시 돌려서 같은 답이 나와야 한다 — 이의가 들어오면 그때 다시 돌려 보여준다.
  - *seed(시드)*: 난수 생성기의 시작값. 같은 seed면 같은 난수열이 나와 추첨을 재현할 수 있다.

## 규칙 2 — 어떻게 뽑나 (Pick)

**요구사항 문장**: "응모권 많을수록 확률이 오릅니다" — 이 문장이 진실이려면 BY_TICKET이어야 한다.

손계산 — a 90장, b 10장, 1,000번 뽑기:

```text
BY_TICKET: 총 100장 중 하나를 뽑아 주인을 낸다 → a가 약 900번 (테스트: >850)
BY_PERSON: 후보 둘 중 하나를 균등하게       → a가 약 500번 (테스트: 400~600)
사람을 뽑으면 응모권을 더 산 이유가 없어진다. 그리고 아무도 모른다.
```

- BY_TICKET 구현: 응모권 총합에서 번호 하나를 뽑고(`floorMod(nextLong, total)`), 응모자를 앞에서부터 훑으며 누적 차감 — 음수가 되는 지점의 주인이 당첨.
- **후보가 없으면 null** (README 함정 셋째) — 빈 목록에서 무엇이든 내면 없는 당첨자가 생기고, **그 당첨자에게 상품을 보내려다 알게 된다.**

## 규칙 3 — 중복 당첨은 (DuplicateRule)

**요구사항 문장**: "중복 당첨은 안 됩니다" — 어디까지? 손계산, a 100장·b 1장·c 1장, 1등 1명 + 2등 1명, BY_TICKET:

```text
PER_EVENT: a가 1등(확률 ~98%) → 남은 99장이 통째로 죽는다. 2등은 b나 c
PER_PRIZE: a가 1등, 2등도 a가 될 수 있다
NONE     : 같은 상품 안에서도 a가 또 될 수 있다 ("1등 3명"의 당첨자가 한 사람)
```

- PER_EVENT + BY_TICKET의 간섭: **많이 산 사람이 한 번 당첨되는 순간 남은 응모권이 전부 죽는다.** 응모권을 많이 산 사람일수록 버려지는 응모권이 많다.
- PER_PRIZE를 응모자가 a 하나뿐인 상황에 적용하면: 1등도 2등도 a — **"중복 당첨 불가"를 상품별로 읽으면 한 사람이 다 가져간다.**
- **후보가 모자라면 인원을 못 채운다** (README 함정 넷째): 응모자 둘에 1등 3명이면 두 명만 뽑고 끝. 채운 척하면 없는 당첨자가 생긴다 — **응모가 적은 이벤트에서 늘 생기는 상황**이다.
- draw 안의 불변식(변종 검증에서 확인): 후보는 줄기만 하므로 한 번 비면 그 상품에서는 다시 안 찬다 — `break`와 `continue`가 동작이 같은 이유. 주석 한 줄로 기록해 뒀다.

## 측정 — 갈래가 실제로 얼마나 갈리나

전제: 사람 1,000명(큰손 10%, 다계정 20%), 100회, 상품 1등 1·2등 5·3등 50. 전부 실측.

**하나. 합산 키를 바꿔도 응모권 총합은 안 바뀐다** — 셋 다 640,656장:

| 합산 키 | 응모자 | 최다 보유 |
|---|---|---|
| 회원 번호 | 102,000 | 9,970 |
| 이름+전화 | 100,000 | 10,186 |
| 주문 | 140,184 | **4,997** |

주문 기준에서 최다 보유가 절반이 되는 것은 **큰손의 응모권이 여러 주문으로 흩어지기 때문** — 같은 사람인데 여러 명이 된다. 회원 기준과 이름+전화 기준의 응모자 차이 2,000 = 계정 하나를 더 만든 사람들.

**둘. 응모권을 뽑으면 큰손 당첨이 5.7배** — 당첨 건수는 둘 다 5,600으로 같고, 20장 이상 보유자의 당첨이 3,019 vs 531. **누가 되느냐만 바뀐다** — 그리고 안내문("응모권 많을수록…")과 코드가 어긋나도 아무도 모른다.

**셋. PER_EVENT는 당첨자 응모권의 96%를 죽인다** — 버려진 응모권 136,809장(당첨자 응모권 합 142,409 중). 50장 산 사람이 3등에 당첨되면 49장이 1등 추첨에서 빠진다 — **상품을 낮은 등수부터 뽑을지 높은 등수부터 뽑을지가 여기서 돈이 된다.**

**넷. NONE이면 서로 다른 당첨자가 574명 줄어든다** — 5,600 / 5,469 / 5,026. 당첨 건수는 늘 5,600 — 명단에 **같은 이름이 몇 번 나오는가**만 바뀐다. 당첨자 발표 화면에 이름이 두 번 나오는 순간 "조작 아니냐"는 문의가 들어온다.

**다섯. 상품이 하나면 중복 규칙 갈래만 사라진다** — 6조합 비교 900/1,500 어긋남 vs 중복 규칙 3개만 비교 0/200. 두 번째 당첨이 없으니 중복 규칙이 할 일이 없다. **대부분의 이벤트가 상품 하나다 — 중복 당첨 규칙은 등수를 나누는 날 처음 필요해지고, 그날 새로 정하면 이미 돌린 추첨과 기준이 달라진다.**

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 키를 그냥 이어 붙임 | 접두사 + 구분자(`n:…\|p:…`) — "김하"+"1234" vs "김"+"하1234" 분리 |
| 합산 결과를 안 세움 | 키 순 정렬 — 같은 seed면 같은 당첨자(재현성). 입력 순서를 안 탄다 |
| 후보가 없는데 뽑음 | pickOne이 null — 없는 당첨자 방지 |
| 인원을 못 채웠는데 채운 척 | 그 상품은 break로 끝 — 뽑힌 만큼만 명단에 |
| 같은 seed 재실행 | 당첨자 명단이 글자 그대로 같아야 한다 (테스트가 draw 두 번 돌려 비교) |
| 잘못된 입력 | 응모권<1, 상품 인원<1, 빈 이름/전화/회원번호 → IllegalArgumentException |

변종 검증: 15개 중 14개 잡힘. 살아남은 하나는 **동작이 같은 변종**(break↔continue) — 결함이 아니라 불변식의 증거였고, 주석으로 기록했다.

## 핵심 문장

- "응모권 많을수록 확률이 오르고 중복 당첨은 안 됩니다"라는 한 줄에는 **세 결정이 안 들어 있다** — 1인이 누구인가, 중복을 어디까지 막나, 무엇을 뽑나.
- 합산 키는 응모권을 늘리지도 줄이지도 않는다 — **같은 총합이 다르게 나뉠 뿐이고, 그 나뉨이 누가 당첨되는지를 정한다.**
- 추첨의 제1 계약은 **재현성**이다 — 키 순 정렬 + seed. 같은 입력·같은 seed면 글자 그대로 같은 명단이 나와야 이의에 답할 수 있다.
- BY_PERSON을 고르는 순간 "응모권 많을수록"이라는 안내문이 거짓이 된다 — **문장과 코드의 어긋남은 겉으로 안 보인다**(당첨 건수는 똑같이 5,600이다).
- PER_EVENT + BY_TICKET은 많이 산 사람의 남은 응모권을 통째로 죽인다 — **뽑는 순서(등수)까지가 규칙이고, 약관에 적혀 있어야 한다.**
- 중복 규칙은 상품이 하나인 동안 안 보인다 — **갈래는 등수를 나누는 날 처음 나타난다.**

## 용어 풀이

- **응모권(ticket)**: 추첨함에 들어가는 쪽지 한 장. 많을수록 BY_TICKET에서 잘 뽑힌다.
- **합산 키(sum key)**: 응모들을 "한 사람"으로 묶는 기준. MEMBER / IDENTITY / ORDER — "1인당"의 1인을 정한다.
- **가중 추첨(BY_TICKET)**: 응모권 수에 비례해 뽑힐 확률이 오르는 뽑기. 균등 추첨(BY_PERSON)의 반대.
- **중복 당첨 규칙(duplicate rule)**: 이미 당첨된 사람을 이후 추첨에서 빼는 범위. 이벤트 전체 / 상품별 / 안 뺌.
- **seed(시드)**: 난수 생성기의 시작값. 같으면 같은 난수열 — 추첨 재현의 열쇠.
- **재현성(reproducibility)**: 같은 입력으로 다시 돌리면 같은 결과가 나오는 성질. 정렬 + seed가 만든다. 감사(이의 제기) 대응의 근거.
- **죽은 응모권**: PER_EVENT에서 당첨자의 남은 응모권 — 이후 추첨에 못 쓰인다. 실측 96%.
- **다계정**: 한 사람이 계정을 여러 개 만드는 것. MEMBER 키에서는 여러 사람, IDENTITY 키에서는 한 사람.
- **불변식(invariant)**: 실행 중 늘 참인 성질. "후보는 줄기만 한다 — 한 번 비면 다시 안 찬다" 같은 것.
- **floorMod**: 음수가 안 나오는 나머지 연산. `nextLong()`이 음수여도 0~총합-1 범위를 보장한다.
