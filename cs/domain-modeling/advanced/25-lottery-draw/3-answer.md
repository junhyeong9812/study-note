### A. 과제

#### 0. 안내문 한 줄이 안 말해주는 것

- 안 말해주는 자리 셋(원본 `Draw` javadoc 그대로):

```text
 안 말해준 것        가능한 읽기
 "1 인당"       →   회원 번호인가  이름과 전화인가  주문인가      (SumKey)
 "중복 당첨 불가" →   이벤트 전체인가  상품별인가  안 막나         (DuplicateRule)
 "확률이 오른다"  →   응모권을 뽑나  사람을 뽑나                  (Pick)
```

- "1 인당"의 1인: **정책이 정한다.**\
  `MEMBER` 면 계정이 한 사람, `IDENTITY` 면 이름+전화가 한 사람, `ORDER` 면 주문 하나가 한 사람이다.
- 합산 키를 바꾸면 총합이 늘거나 주는가: **안 바뀐다.**\
  측정에서 세 키 모두 응모권 총합이 **640,656** 장으로 똑같았다.

> **합산 키(sum key)** — 여러 응모를 "한 사람"으로 묶는 기준.\
> 예: 같은 이름·전화로 만든 계정 둘이 각각 두 번 주문했을 때, 회원 번호로 묶으면 두 사람이고 이름+전화로 묶으면 한 사람이다.

- 그럼 무엇이 바뀌는가: **나뉘는 방식**이다.\
  응모자 수가 102,000 / 100,000 / 140,184 로 달라지고, 최다 보유가 9,970 / 10,186 / 4,997 로 달라진다.\
  같은 응모권 더미를 몇 덩어리로 쪼개느냐만 바뀌고, 그 덩어리 모양이 누가 당첨되는지를 정한다.
- "안 됩니다"의 범위: **이벤트 전체 / 상품마다 / 안 막음** 셋 다 그 문장으로 읽힌다.
- 사람을 뽑으면 거짓이 되는 것: **"응모권 많을수록 확률이 오릅니다"라는 안내문 자체.**\
  `BY_PERSON` 은 응모권 수를 아예 안 본다 — 90장 가진 사람과 1장 가진 사람이 똑같다.
- 상품 순서: **안내문에 없다.** 코드에서도 `draw` 가 받은 `prizes` 리스트 순서대로 돌 뿐이라, 순서를 정하는 책임이 부르는 쪽에 있다.
- 인원을 못 채우면: **안내문이 아무 말도 안 한다.** 이 코드는 뽑힌 만큼만 명단에 넣는다.
- enum 값으로 올리면 할 수 있게 되는 것: **여섯 조합(3 × 2)을 같은 코드로 돌려 답이 갈리는 건수를 셀 수 있다.**\
  측정 다섯 번째가 정확히 그걸 했다 — 상품 하나일 때 여섯 조합 중 어긋난 것 900 / 1,500.
- "서로 간섭한다": **한 갈래의 선택이 다른 갈래의 결과를 바꾼다.**\
  응모권을 뽑으면서(`BY_TICKET`) 이벤트 전체 중복을 막으면(`PER_EVENT`), 많이 산 사람이 한 번 당첨되는 순간 남은 응모권이 전부 죽는다 — 어느 한쪽만 보면 안 보이는 결과다.

> **간섭(interaction)** — 두 설정이 각각은 말이 되는데 함께 켜면 뜻밖의 결과가 나오는 것.\
> 예: "응모권 많을수록 유리"와 "중복 당첨 금지"는 각각 공정해 보이지만, 함께 쓰면 응모권을 많이 산 사람이 가장 많은 응모권을 버리게 된다.

#### 1. TODO 1 — key

정답 코드 (impl/Draw.java):

```java
public String key(Entry entry, SumKey sumKey) {
    return switch (sumKey) {
        case MEMBER -> "m:" + entry.memberId();
        case IDENTITY -> "n:" + entry.name() + "|p:" + entry.phone();
        case ORDER -> "o:" + entry.orderId();
    };
}
```

- 세 키의 모양:

```text
 MEMBER    "m:" + 회원번호                 →  "m:m1"
 IDENTITY  "n:" + 이름 + "|p:" + 전화      →  "n:김하|p:1234"
 ORDER     "o:" + 주문번호                 →  "o:o1"
```

- 구분자 없이 붙이면:

```text
 이름 "김하" + 전화 "1234"   →  "김하1234"
 이름 "김"   + 전화 "하1234" →  "김하1234"    ← 같다. 남남이 한 사람이 된다

 구분자를 넣으면
 "n:김하|p:1234"  vs  "n:김|p:하1234"        ← 다르다
```

> **구분자(delimiter)** — 이어 붙인 값들의 경계를 표시하는 글자.\
> 예: 이름과 전화 사이에 `|p:` 를 끼우면 "김하"+"1234"와 "김"+"하1234"가 서로 다른 글자열이 된다.

- 두 사람이 한 사람이 되면: **응모권이 합쳐지고, 그 둘 중 하나만 당첨된다.**\
  당첨자 명단에 이름이 하나만 뜨는데, 상품을 보낼 사람이 누구인지 코드가 모른다.
- 접두사(`m:`·`n:`·`o:`)를 붙이는 이유: **키 공간을 갈래마다 분리한다.**\
  회원번호 "1"과 주문번호 "1"이 서로 다른 갈래인데 같은 문자열 "1"이 되는 일을 막는다. 갈래를 섞어 한 맵에 담아도 안전하다. (원본에 근거 없음 — 내 추론)
- 전화번호에 `|` 가 있으면: **여전히 부딪힐 수 있다.**\
  이름 "A" + 전화 "B|p:C" 와 이름 "A|p:B" + 전화 "C" 는 둘 다 `"n:A|p:B|p:C"` 다.\
  완전히 막으려면 값 안의 구분자를 이스케이프하거나, 길이를 앞에 적는 방식이 필요하다. (원본에 근거 없음 — 내 추론)

> **키 충돌(key collision)** — 서로 달라야 할 두 값이 같은 키가 되어 한 덩어리로 묶이는 것.\
> 예: 이어 붙인 문자열이 우연히 같아져서 남남 두 사람이 한 응모자로 합산되는 일.

- MEMBER 가 못 막는 것: **다계정.**\
  같은 사람이 계정을 둘 만들면 응모자 두 명이 된다 — 측정에서 회원 기준 102,000 vs 이름+전화 기준 100,000, 그 차이 2,000이 계정을 하나 더 만든 사람들이다.
- IDENTITY 가 두 사람으로 만드는 정상 사용자: **개명한 사람**(`Entry` javadoc 원문: "개명하면 두 사람이 된다"). 전화번호를 바꾼 사람도 같다.
- ORDER 를 쓰면 큰손의 응모권은: **여러 주문으로 흩어진다.**\
  같은 사람인데 여러 명이 되어 최다 보유가 절반(9,970 → 4,997)으로 떨어진다.

> **merge** — 맵에 값을 넣되, 이미 있으면 주어진 방법으로 합치는 연산.\
> 예: `merge("m:m1", 2, Integer::sum)` 은 "m:m1"이 없으면 2를 넣고, 이미 3이 있으면 5로 만든다.

  그 순서가 `pickOne` 의 누적 차감 순서이자 `BY_PERSON` 의 인덱스라, 같은 seed 라도 다른 사람이 뽑힌다.
- 입력 순서를 정하는 것: **조회 쿼리다.** DB 에서 `ORDER BY` 없이 읽으면 순서가 보장되지 않고, 인덱스·병렬 실행·데이터 이동에 따라 조용히 바뀐다. (원본에 근거 없음 — 내 추론)
- 같은 seed 인데 당첨자가 달라지면: **이의가 들어와도 다시 못 돌린다**(README 함정 둘째 원문).\
  "그때 이렇게 나왔다"를 증명할 수 없다.

> **재현성(reproducibility)** — 같은 입력으로 다시 돌리면 글자 그대로 같은 결과가 나오는 성질.\
> 예: 당첨자 명단에 이의가 들어왔을 때, 같은 자료와 같은 seed 로 다시 돌려 같은 명단을 보여줄 수 있는 것.

- seed 만 고정하면 안 되는 이유: **seed 는 난수열만 고정한다.**\
  같은 난수 3번이 나와도 후보 목록의 3번째가 다른 사람이면 당첨자가 달라진다 — 난수열과 목록 순서가 **둘 다** 고정돼야 결과가 고정된다.

> **seed(시드)** — 난수 생성기의 시작값. 같은 시드는 같은 난수 순서를 낸다.\
> 예: `new Random(42)` 를 두 번 만들면 두 번 다 똑같은 수열이 나온다. 테스트가 seed 42 두 번은 같고 43은 다르다고 못 박았다.

- 정렬 기준이 키 하나로 충분한 이유: **키가 맵의 키라서 결과에 유일하게 한 번씩만 있다.**\
  같은 키를 가진 응모자가 둘 생길 수 없으므로 키만으로 순서가 하나로 정해진다.

> **전순서(total order)** — 어떤 두 원소를 집어도 앞뒤가 하나로 정해지는 정렬 기준.\
> 예: 키가 중복되지 않으면 키 비교만으로 목록 순서가 딱 하나로 결정된다. 중복이 있으면 두 번째 기준이 더 필요하다.

- `List.copyOf` 가 막는 것: **밖에서 목록을 고치는 일.** 불변 리스트를 돌려주므로 호출자가 응모자를 추가·삭제해 추첨 입력을 몰래 바꿀 수 없다.
- 테스트의 확인 방법: 같은 세 응모를 **순서만 바꿔 넣고 두 결과가 같은지 비교**한다.

#### 3. TODO 3 — pickOne

정답 코드:

```java
if (candidates.isEmpty()) {
    return null;
}
if (pick == Pick.BY_PERSON) {
    return candidates.get(random.nextInt(candidates.size()));
}
long total = 0;
for (Applicant candidate : candidates) {
    total += candidate.tickets();
}
long drawn = Math.floorMod(random.nextLong(), total);
for (Applicant candidate : candidates) {
    drawn -= candidate.tickets();
    if (drawn < 0) {
        return candidate;
    }
}
return candidates.get(candidates.size() - 1);
```

- 후보가 비면: **`null`** 을 돌려준다.
- 빈 목록에서 아무나 내면: **없는 당첨자가 생기고, 그 당첨자에게 상품을 보내려다 알게 된다**(테스트 주석 원문).
- `BY_PERSON`: `candidates.get(random.nextInt(candidates.size()))` — 후보 수 중에서 하나를 균등하게 고른다.
- `BY_TICKET` 의 절차:

```text
 [1] 후보들의 응모권을 다 더해 total 을 만든다
 [2] 0 ~ total-1 중에서 번호 하나(drawn)를 뽑는다
 [3] 앞에서부터 응모권 수만큼 빼 나가다가, 음수가 되는 그 자리의 주인이 당첨
```

손계산 — a 90장, b 10장 (total = 100):

```text
 drawn = 0   → 0-90 = -90  < 0  → a
 drawn = 89  → 89-90 = -1  < 0  → a        ← a 는 0~89 (90개)
 drawn = 90  → 90-90 =  0  안됨 → 다음
               0-10 = -10  < 0  → b        ← b 는 90~99 (10개)

 90/100 = 90%   ↔   테스트: 1,000번에 a 가 850회 초과
 BY_PERSON 이면 둘 중 하나 = 50%  ↔  테스트: 400~600회
```

```text
 응모권 상자를 그림으로

 |←─────────── a 의 응모권 90 ──────────→|←─ b 의 10 ─→|
 0                                      89 90         99
 ↑ 이 101칸 아닌 100칸 중 한 칸을 뽑고, 그 칸이 든 구간의 주인이 당첨
```

> **가중 추첨(weighted draw)** — 뽑힐 확률이 가진 몫에 비례하는 뽑기.\
> 예: 응모권 90장인 사람이 10장인 사람보다 딱 9배 잘 뽑힌다.

- `total` 을 `long` 으로 세는 이유: **응모자가 많으면 `int` 합이 넘칠 수 있다.**\
  `Applicant.tickets()` 는 `int` 지만 그 합은 커질 수 있어서, 더하는 그릇을 넓게 잡는다. (원본에 근거 없음 — 내 추론)
- `Math.floorMod` 를 쓰는 이유: **`random.nextLong()` 은 음수도 낸다.**\
  음수를 그냥 쓰면 `drawn` 이 처음부터 음수라 **맨 앞 후보가 무조건 당첨**된다.

> **floorMod** — 나머지를 구하되 결과가 항상 0 이상이 되게 하는 연산.\
> 예: `-7 % 3` 은 자바에서 -1 이지만, `Math.floorMod(-7, 3)` 은 2 다.

- `%` 만 쓰면 깨지는 것: 자바의 `%` 는 **피제수의 부호를 따라간다.**\
  `nextLong()` 이 음수면 `drawn` 도 음수가 되어 0~total-1 범위를 벗어난다 — 첫 후보에게 확률이 몰린다.
- `drawn < 0` 이어야 하는 이유: 후보 i 는 누적합 구간 `[C(i-1), C(i)-1]` 을 가져야 한다.

```text
 a 90, b 10 일 때

 drawn < 0  로 판정   a: 0~89 (90칸)   b: 90~99 (10칸)   ← 정확히 90:10
 drawn <= 0 로 판정   a: 0~90 (91칸)   b: 91~99  (9칸)   ← 첫 후보가 한 칸 더,
                                                            마지막 후보가 한 칸 덜
```

- 루프가 끝까지 도는 경우: **정상 입력에서는 안 생긴다.**\
  `drawn` 이 `total` 보다 작으므로 응모권을 다 빼면 반드시 어딘가에서 음수가 된다.\
  마지막 줄의 `return candidates.get(size-1)` 은 컴파일러를 만족시키는 **방어선**이다. (원본에 근거 없음 — 내 추론)
- 1,000번 뽑기 결과: `BY_TICKET` 은 a 가 **850회 초과**, `BY_PERSON` 은 a 가 **400~600회** (테스트 assert 그대로).
- `Random` 을 인자로 받는 것과 안에서 만드는 것의 차이: **밖에서 받으면 재현할 수 있다.**\
  `draw` 는 `new Random(seed)` 를 **한 번만** 만들어 상품·인원 전체에 같은 난수열을 흘려보낸다.\
  `pickOne` 이 안에서 난수를 새로 만들면 매 호출이 같은 수로 시작해 같은 사람만 계속 뽑힌다. (원본에 근거 없음 — 내 추론)

```java
Random random = new Random(seed);
List<Winner> winners = new ArrayList<>();
Set<String> wonAnywhere = new LinkedHashSet<>();

for (Prize prize : prizes) {
    Set<String> wonHere = new LinkedHashSet<>();
    for (int i = 0; i < prize.count(); i++) {

        if (picked == null) {
            // 후보는 줄기만 한다. 한 번 비면 이 상품에서는 다시 안 찬다.
            break;
        }
        winners.add(new Winner(prize.id(), picked.key()));
        wonHere.add(picked.key());
        wonAnywhere.add(picked.key());
    }
}
return List.copyOf(winners);
```

- 루프는 **세 겹**이다.

```text
 for 상품                       1등 → 2등 → 3등 (받은 순서대로)
   for 인원 (prize.count())     그 상품에서 뽑을 사람 수만큼
     for 응모자                 중복 규칙에 안 막힌 사람만 후보로 모은다
       → pickOne(후보, pick, random)
```

- `Random` 은 **함수 맨 앞에서 seed 로 한 번만** 만든다.\
  상품마다 새로 만들면 1등과 2등이 **같은 난수열**을 다시 쓰게 되어, 후보가 같은 경우(NONE 규칙 등) 같은 사람이 또 뽑힌다. (원본에 근거 없음 — 내 추론)
- 세 규칙이 보는 집합:

```text
 PER_EVENT  → wonAnywhere  (이벤트 전체에서 한 번이라도 당첨된 사람)
 PER_PRIZE  → wonHere      (이 상품에서 당첨된 사람)
 NONE       → 아무것도 안 본다 (blocked = false)
```

- 비워지는 시점: `wonAnywhere` 는 **한 번 만들고 끝까지 안 비운다.** `wonHere` 는 **상품이 바뀔 때마다 새로 만든다**(상품 루프 안에서 선언).
- NONE 도 코드가 필요한 이유: **switch 가 세 갈래를 다 덮어야 한다.** `false` 를 내는 것 자체가 "아무도 안 막는다"는 선언이고, enum 에 갈래가 추가되면 컴파일러가 빠진 자리를 잡아준다. (원본에 근거 없음 — 내 추론)
- 후보 목록은 **한 명 뽑을 때마다 새로 만든다.** 직전에 뽑힌 사람이 즉시 빠져야 하기 때문이다.
- `pickOne` 이 null 이면: **`break`** — 그 상품의 인원을 못 채운 채 다음 상품으로 넘어간다.
- `continue` 로 써도 같은 이유: **후보는 줄기만 하기 때문**이다.\
  한 바퀴 돌 때마다 당첨자가 하나씩 차단 집합에 들어갈 뿐, 빠졌던 사람이 다시 후보로 돌아오는 경로가 없다.\
  그래서 한 번 비면 남은 반복에서도 계속 비어 있고, `continue` 로 헛바퀴만 더 돌 뿐 결과가 같다.
- 불변식 한 문장: **"한 상품 안에서 후보 집합은 단조 감소한다 — 한 번 비면 그 상품에서는 다시 안 찬다."**

> **불변식(invariant)** — 코드가 도는 내내 항상 참인 성질.\
> 예: "후보는 줄기만 한다"가 참이라서, 후보가 빈 순간 그 상품의 추첨을 끝내도 안전하다.

- 응모자 2명 · 1등 3명 (PER_EVENT): **당첨 2건.** 세 번째 뽑기에서 후보가 비어 `break` 한다 — 테스트가 당첨자를 정렬하면 `[a, b]` 라고 못 박았다.

```text
 뽑기 1   후보 [a, b]  → a 당첨   wonAnywhere = {a}
 뽑기 2   후보 [b]     → b 당첨   wonAnywhere = {a, b}
 뽑기 3   후보 []      → null    → break
                                   당첨 2건 (3명 자리 중 2명)
```

- 응모자 a 하나 · 1등 1명 + 2등 1명:

```text
 PER_EVENT   1등 a, 2등은 후보가 비어 있음   →  당첨 1건
 PER_PRIZE   1등 a, 2등 a (상품이 바뀌며 wonHere 가 비워짐)  →  당첨 2건
 NONE        1등 a, 2등 a                   →  당첨 2건
```

- 응모자 a 하나 · 1등 3명: **PER_PRIZE 1건, NONE 3건.**\
  NONE 은 `winsByKey("a")` 가 **3** 이다 — "1등 3명"인데 당첨자가 한 사람이다.
- 상품 순서가 나타나는 자리: **`prizes` 리스트의 순서 그대로.**\
  `draw` 는 순서를 정하지 않고 받은 대로 돈다 — 1등부터냐 3등부터냐는 **부르는 쪽의 결정**이고, 코드에는 그 결정이 안 적혀 있다.

### B. 개념

#### 5. 함정 (README)

- 넷이 각각 망가뜨리는 것:

| 함정 | 조용히 망가지는 것 |
|---|---|
| 키를 그냥 이어 붙임 | 남남 둘이 한 응모자로 합쳐지고 **그 둘 중 하나만 당첨**된다 |
| 합산 결과를 안 세움 | 같은 seed 로도 다른 당첨자 — **다시 못 돌린다** |
| 후보가 없는데 뽑음 | **없는 당첨자**가 명단에 오른다 |
| 인원을 못 채웠는데 채운 척 | 뽑히지 않은 자리가 채워진 것처럼 보인다 |

- 둘 중 하나만 당첨되는 이유: 합쳐진 키는 **하나의 응모자**라서, 당첨돼도 `Winner` 의 `key` 가 하나다.\
  그 키 뒤에 사람이 둘 있다는 사실을 추첨 결과가 기억하지 못한다.
- "이의가 들어와도 다시 못 돌린다": 재현이 안 되면 **"그때 정말 이렇게 나왔다"를 증명할 방법이 없다.**\
  같은 자료·같은 seed 를 넣었는데 명단이 다르면, 조작이 없었어도 조작을 부인할 근거가 없다.
- "없는 당첨자"의 실무 장면: **상품을 보내려다 안다**(테스트 주석 원문).\
  발표가 나가고 배송 단계에서 받는 사람이 비어 있는 건이 나온다 — 그때는 이미 명단이 공개된 뒤다.
- 인원 미달이 늘 생기는 곳: **응모가 적은 이벤트**(README 원문). 응모자보다 상품 인원이 많으면 매번 생긴다.
- 예외 없이 틀린 값이 나오는 것: **조용한 실패(silent failure)** 다.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 결과만 틀린 실패.\
> 예: 후보가 없는데도 아무나 하나 내면 프로그램은 성공했다고 하고, 잘못은 배송 단계에서 처음 보인다.

#### 6. 측정 — 갈래가 얼마나 갈리나

전제: 사람 1,000명(큰손 10%, 다계정 20%), 100회, 상품 1등 1명·2등 5명·3등 50명.

- 합산 키별 응모자 수: **회원 102,000 / 이름+전화 100,000 / 주문 140,184.**
- 응모권 총합: **셋 다 640,656.**
- 총합이 같은데 최다 보유가 바뀌는 이유: **같은 더미를 다르게 쪼개기 때문**이다.\
  한 사람의 응모권이 한 덩어리로 뭉치면 최다 보유가 커지고, 여러 덩어리로 흩어지면 작아진다.
- 주문 기준 최다 보유가 절반(**4,997**)인 이유: **큰손의 응모권이 여러 주문으로 흩어진다**(README 원문).\
  큰손은 3~7번 주문하므로, 주문 기준에서는 같은 사람이 여러 명이 된다.
- 차이 2,000 의 정체: **계정을 하나 더 만든 사람들**이다(테스트 주석 원문).\
  102,000 − 100,000 = 2,000 — 회원 기준에서 한 사람이 두 명으로 세어진 만큼이다.
- 당첨 건수: **둘 다 5,600.**
- 응모권 20장 이상인 사람의 당첨: **응모권 뽑기 3,019 / 사람 뽑기 531** — 약 **5.7배**.
- "누가 되느냐만 바뀐다"가 무서운 이유: **겉으로 안 보인다.**\
  당첨 건수도, 명단 길이도 똑같다 — 안내문과 코드가 어긋나 있어도 결과 화면만 봐서는 알 수 없다.

> **가려진 차이(masking)** — 총계가 같아서 내부의 큰 차이가 결과 지표에 안 나타나는 것.\
> 예: 당첨 건수는 5,600 으로 그대로인데 큰손 당첨만 3,019 에서 531 로 바뀐다.

- 세 중복 규칙의 응모권 수치:

| 규칙 | 당첨자 응모권 합 | 버려진 응모권 |
|---|---|---|
| PER_EVENT | 142,409 | **136,809** |
| PER_PRIZE | 145,687 | 0 |
| NONE | 157,113 | 0 |

- 버려진 비율: **136,809 / 142,409 ≈ 96%** (README "96 퍼센트").
- 50장을 산 사람이 3등에 당첨되면: **49장이 1등 추첨에서 빠진다**(README 원문).
- 순서가 돈이 되는 이유: 낮은 등수를 먼저 뽑으면 **큰손이 작은 상품에 먼저 걸려 큰 상품 추첨에서 빠진다.**\
  높은 등수를 먼저 뽑으면 반대다 — 같은 규칙·같은 seed 라도 상품 순서만으로 누가 1등이 되는지가 바뀐다.
- 서로 다른 당첨자 수: **PER_EVENT 5,600 / PER_PRIZE 5,469 / NONE 5,026** (당첨 건수는 늘 5,600).\
  5,600 − 5,026 = **574명**이 줄어든다.
- 명단이 보이는 모양: **같은 이름이 여러 번 나온다.**\
  그리고 당첨자 발표 화면에 이름이 두 번 나오는 순간 "조작 아니냐"는 문의가 들어온다(테스트 주석 원문).
- 상품이 1등 1명뿐일 때 여섯 조합: 어긋난 것 **900 / 1,500.**
- 그때 중복 규칙 셋만 견주면: 어긋난 것 **0 / 200.**
- 상품이 하나면 중복 규칙이 안 보이는 이유: **두 번째 당첨이 없기 때문**이다.\
  차단 집합에 사람이 들어가도 그 뒤에 뽑을 자리가 없어서, 세 규칙이 전부 같은 답을 낸다.
- 처음 필요해지는 날: **등수를 나누는 날**(README 원문). 대부분의 이벤트가 상품 하나라서 그때까지는 갈래가 숨어 있다.
- 그날 새로 정하면 어긋나는 것: **이미 돌린 추첨과 기준이 달라진다**(테스트 주석 원문).\
  전에 한 추첨을 지금 규칙으로 다시 돌리면 다른 명단이 나오므로, 과거 결과를 재현하려면 그때의 규칙까지 같이 남겨야 한다.

#### 7. 변종 검증에서 고친 것

- 살아남은 변종: **후보가 없을 때 `break` 대신 `continue` 로 바꾼 것.**
- 테스트의 결함인가: **아니다.** 동작이 같으니 결과로 구별할 방법이 없다 — 결함이 아니라 **불변식의 증거**다.
- 남긴 것: **주석 한 줄**.

```java
// 후보는 줄기만 한다. 한 번 비면 이 상품에서는 다시 안 찬다.
break;
```

- 잡으려고 테스트를 더 쓰면 나빠지는 것: **구현 세부를 고정하게 된다.**\
  결과가 같은 두 코드를 구별하려면 "어떻게 도는가"를 검사해야 하고, 그러면 나중에 안전한 리팩토링까지 테스트가 막는다. (원본에 근거 없음 — 내 추론)

> **동치 변종(equivalent mutant)** — 코드를 바꿨는데 동작이 완전히 같아서 어떤 테스트로도 못 잡는 변종.\
> 예: 후보가 빌 때의 `break` 를 `continue` 로 바꾼 것 — 후보가 다시 안 차므로 결과가 같다.

#### 8. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 다계정을 어떻게 하나: **합산 키를 바꾸는 것이 코드가 주는 답의 전부다.**\
  `IDENTITY` 로 묶으면 계정이 달라도 한 사람이 되어 측정의 2,000건이 사라진다.\
  다만 이름+전화도 바꿀 수 있고 개명하면 오히려 한 사람이 둘이 되므로, 이건 "막는" 게 아니라 **어느 오류를 감수할지 고르는 일**이다.\
  진짜로 막으려면 본인 확인(실명·본인인증) 같은 `Draw` 바깥의 장치가 필요하고, 그건 응모를 **받는 단계**의 일이지 추첨의 일이 아니다. (원본에 답 없음 — 내 추론)
- 상품 순서를 약관에 적었나: **코드는 순서를 정하지 않는다** — `draw` 가 `prizes` 를 받은 그대로 돌기 때문이다.\
  그래서 순서는 어딘가에 문서로 남아야만 결정된 것이 된다. 측정 셋째(136,809장이 죽는다)가 그 순서에 달려 있으므로, **약관에 없으면 이의가 들어왔을 때 근거가 없다.** (원본에 답 없음 — 내 추론)
- 응모권이 죽는 것을 응모자가 아나: **명단만 봐서는 못 안다.**\
  버려진 응모권은 어떤 화면에도 안 나온다 — 당첨 건수도, 당첨자 수도 그대로다.\
  알게 되면 `PER_EVENT` 에서는 **많이 사는 것의 값어치가 줄어든다** — 한 번 당첨되면 나머지가 다 죽으니, 기대값을 계산할 줄 아는 사람은 덜 산다. (원본에 답 없음 — 내 추론)
- 이의가 들어오면 무엇을 보여주나: **입력(합산된 응모자 목록) + seed + 규칙 셋(SumKey·DuplicateRule·Pick) + 상품 순서.**\
  이 다섯이 있으면 누구든 같은 명단을 다시 만들 수 있다 — 그게 `aggregate` 의 정렬과 `new Random(seed)` 가 있는 이유다.\
  seed 공개는 양날이다: 미리 공개하면 결과를 먼저 계산할 수 있고, 추첨 뒤에 공개하면 "그 seed 를 골라서 쓴 거 아니냐"는 의심이 남는다.\
  실무에서는 **추첨 전에 seed 를 봉인(해시 공개)하고 추첨 후에 원본을 공개**하는 방식이 이 둘을 동시에 푼다. (원본에 답 없음 — 내 추론)

> **감사 가능성(auditability)** — 나중에 제3자가 결과를 다시 확인할 수 있는 성질.\
> 예: 입력·seed·규칙을 남겨 두면, 이의를 제기한 사람이 직접 돌려 같은 명단을 확인할 수 있다.

#### 9. 연결

- 세는 것의 차이: 알고리즘 트랙은 **비교 횟수**(같은 답으로 가는 비용)를 셌다.\
  여기서 세는 것은 **갈래가 갈리는 건수** — 답 자체가 여럿이라 비용이 아니라 **불일치**를 잰다(900/1,500, 0/200 처럼).
- 구분자 문제와 같은 무늬의 박스: **21-throttle** — 그쪽도 "누구를 한 단위로 보나"를 키 문자열로 만든다(서머리가 짚은 대응).\
  넓게 보면 **27-ab-assign**(배정 키)도 같은 자리다 — 키를 어떻게 만드느냐가 누가 같은 그룹이 되는지를 정한다. (원본에 근거 없음 — 내 추론)
- "같은 seed 면 같은 결과"와 같은 실무 관행: **결정적 재실행(deterministic replay)** 이다.\
  배치 재처리, 감사 로그 재생(**16-audit-replay**), 금융 정산 재계산이 전부 "같은 입력으로 다시 돌려 같은 답"에 기대고 있다. (원본에 근거 없음 — 내 추론)
- `FeePolicy` 와 같은 점·다른 점:

```text
 같은 점   말이 안 정해준 자리를 코드에 숨기지 않고 "값"으로 올렸다
           그래서 여러 해석을 같은 코드로 돌려 갈림을 셀 수 있다

 다른 점   FeePolicy   숫자(10분·1,000원) 중심 — 값을 바꿔도 뜻은 하나다
           세 enum     갈래(누구를/어디까지/무엇을) 중심 — 서로 간섭한다
                       그래서 조합의 수(3 × 2 = 6)가 측정의 단위가 된다
```

- 문장과 코드의 어긋남을 막는 테스트: **안내문이 주장하는 성질 자체를 검사해야 한다.**\
