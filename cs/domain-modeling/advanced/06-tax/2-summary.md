# domain-modeling-advanced/06-tax — 정리 (힌트)

## 해결하는 문제

과세·면세·영세율이 섞인 주문에 할인 하나가 붙으면 "부가세 10%"로는 세금계산서를 못 만든다. 할인을 어느 구분에서 빼나, 표시가가 세금 포함인가, 배송비는 과세인가가 비어 있다.\
이 모델이 없으면: 주문 시스템과 회계 시스템이 **각자** 할인을 배분해 같은 주문의 공급가액이 둘이 되고, 고객 화면·QA·결제 대사는 총액만 보므로 아무도 못 잡다가 **세무 신고에서만** 드러난다.

```text
같은 주문 1,083,000원 (포함가)
  주문 시스템  할인 비례 배분     부가세 91,798
  회계 시스템  과세 먼저 배분     부가세 ~?      ← 총액은 같으니 대사는 통과
                                               신고서의 공급가액만 다르다
```

쉬운 예: 친구 셋의 피자값에서 쿠폰 한 장을 누구 몫에서 빼든 가게에 내는 돈은 같다 — 하지만 각자 부담은 달라진다. 여기서는 "나라 몫"이 그 각자 부담이다.\
똑같은 구조다: `DiscountAllocation`·`PriceBasis`·`ShippingTax` 세 enum이 그 빈칸이고, 배분은 **곱하기 먼저·마지막 몫은 빼기·넘치면 흘려보내기**로 합을 지킨다.\
실무 예: 쇼핑몰 세금계산서, 부가세 신고서, 마트 영수증의 "과세물품/면세물품" 줄.

### 한눈에 — 쉽게 말하면

**부가세 계산 = 피자값 나눠 내기에서 "할인 쿠폰을 누구 몫에서 빼줄까" 문제.**

- 친구 셋이 피자를 시켰는데 할인 쿠폰이 한 장 나왔다. 쿠폰을 A 몫에서 빼든 B 몫에서 빼든 **가게에 내는 총액은 같다.** 하지만 각자의 부담은 달라진다.
- 주문도 똑같은 구조다. 과세 상품(노트북)·면세 상품(책)·영세율 상품(수출품)이 섞인 주문에 할인 하나가 붙으면, **할인을 어느 구분에서 빼느냐로 나라에 갈 부가세가 달라진다.** 고객이 낼 총액은 그대로인데.
  - *과세(TAXABLE)*: 부가세 10%가 붙는 상품. 노트북, 옷 등 대부분.
  - *면세(EXEMPT)*: 부가세가 아예 없는 상품. 책, 농산물 등.
  - *영세율(ZERO_RATED)*: 과세 대상인데 세율이 0%인 상품. 수출품이 대표.
- "부가세는 10%" 라는 말에 안 들어 있는 결정이 셋이다: ① 할인을 어디서 빼나 ② 표시가가 세금 포함인가 별도인가 ③ 배송비는 과세인가. **셋 다 나라에 내는 돈을 바꾼다.**
- 이 챕터의 무서운 점: 포함가에서는 **고객 화면·QA·결제 대사 어디서도 이 차이가 안 보인다.** 세무 신고에서만 드러난다.

```text
  노트북 1,100,000(과세) + 책 30,000(면세) + 수출품 50,000(영세율)
  할인 100,000 · 배송비 3,000

  할인을 어디서 빼나       과세 몫      면세 몫     영세율 몫
    금액 비례              93,220      2,542       4,238
    과세 먼저             100,000          0           0
    면세 먼저              70,000     30,000           0
                          └─ 어느 쪽이든 고객이 낼 돈은 1,083,000 으로 같다.
                             갈리는 것은 그 안의 "나라 몫(부가세)" 뿐이다.
```

실무 예: 쇼핑몰 세금계산서 발행, 부가세 신고서 작성, 마트 영수증의 "과세물품/면세물품" 줄.

## 동작·원리

### 전체 흐름

```text
TaxOrder (주문 계약 — 다 주어져 있다)
  lines(품목: 금액+세금구분) · discount(주문 전체 할인) · shippingFee(배송비)
  생성자 검증: 품목 없음 X · 음수 X · 할인 > 상품합 X

VatCalculator.invoice(order, 결정 셋) → Invoice(세금계산서 한 장)
  결정 ① DiscountAllocation : BY_AMOUNT(비례) / TAXABLE_FIRST / EXEMPT_FIRST
  결정 ② PriceBasis         : VAT_INCLUDED(포함가→역산) / VAT_EXCLUDED(별도가→더한다)
  결정 ③ ShippingTax        : ALWAYS_TAXABLE / PRORATED(비례) / TAXABLE_IF_ANY_TAXABLE

  단계: 할인을 구분별로 배분 → 배송비의 과세분 결정
        → 구분별 금액 확정 → (포함가면) 공급가액 역산 → Invoice
```

  - *공급가액*: 세금을 붙이기 전의 "물건값". 세금계산서에서 부가세와 나란히 적히는 줄.
  - *역산*: 세금이 이미 들어 있는 총액에서 거꾸로 물건값을 구하는 것.

### 결정 ① 할인 배분 — "할인 100,000원을 누가 뒤집어쓰나"

**요구사항**: "주문 전체에 할인이 붙는다" — 그런데 과세·면세·영세율 중 어디서 뺄지는 요구사항 문장에 없다. 코드로는 `for` 문 하나 차이지만 **세무 판단**이다.

예시 손계산 — 할인 100,000, 상품합 1,180,000:

```text
금액 비례:  과세 몫 = 100,000 × 1,100,000 / 1,180,000 = 93,220
            면세 몫 = 100,000 ×    30,000 / 1,180,000 =  2,542
            영세율 몫 = 100,000 - 93,220 - 2,542      =  4,238  ← 빼기로 구한다
과세 먼저:  과세에서 100,000 전부 (과세분 1,100,000 안에 다 들어간다)
면세 먼저:  면세 30,000 을 다 쓰고 → 남은 70,000 이 과세로 흘러넘친다
```

모델링 포인트:

- **마지막 몫은 빼기로 구한다.** 셋을 각각 반올림하면 합이 100,000에서 1원 어긋날 수 있다. `할인 - 앞의 둘`로 구하면 합이 언제나 정확하다 — 대신 마지막 하나가 반올림 나머지를 뒤집어쓴다.
- **넘치면 흘려보낸다(cascade).** 할인 1,150,000이면 과세 1,100,000 → 면세 30,000 → 영세율 20,000 순으로 채운다. 안 흘려보내면 할인 일부가 사라져서 **고객이 낼 돈이 늘어난다.**
- **곱하기가 먼저다.** `100,000 / 1,180,000` 을 정수로 먼저 하면 0이 되어 할인이 통째로 사라진다. `100,000 × 1,100,000` 을 먼저 하고 마지막에 한 번만 나눈다(원본 `share()` 주석 그대로).
- 왜 enum 세 개로 모델링했나: "어디서 빼나"는 계산 로직이 아니라 **정책 선택**이라서, 호출자가 명시적으로 고르게 했다. 기본값을 숨겨두면 세무 판단이 코드 어딘가에 암묵적으로 들어간다.

측정(주문 5,000개): 과세 먼저로 몰면 부가세 총합이 **2.695% (약 610만 원) 준다.** 고객이 낸 돈은 셋 다 같다.

### 결정 ② 포함가 vs 별도가 — "1,100,000원은 세금 포함인가"

**요구사항**: "표시가가 세금 포함(VAT_INCLUDED)이면 역산, 별도(VAT_EXCLUDED)면 더한다."

포함가 역산 손계산 — 과세 총액 1,009,780(비례 배분 + 배송비 전액 과세 후):

```text
공급가액 = 1,009,780 × 10 / 11 = 917,981.8... → 917,982   (10 곱하고 11 로 나눈다)
부가세   = 1,009,780 - 917,982 = 91,798                    (빼기로 구한다!)
검산     : 917,982 + 91,798 = 1,009,780  ← 언제나 정확히 맞는다
```

- **부가세를 `공급가액 × 0.1` 로 구하면 안 되나?** 이 예에서는 91,798.2 → 반올림 91,798로 우연히 같다. 그러나 합이 1원 안 맞는 경우가 생긴다. **빼기로 구해야 세금계산서의 두 줄(공급가액+부가세=총액)이 언제나 맞는다.**
- **11로 먼저 나누면 안 되나?** 나누기를 먼저 하면 나머지가 사라진다. 곱하기 먼저 — 할인 배분과 같은 원칙.
- 면세·영세율은 세금이 0이라 역산할 것이 없다. 포함이든 별도든 금액 그대로가 공급가액.

측정: **포함가면 아홉 조합(배분 3 × 배송 3) 전부 총액 1,083,000으로 같고**, 부가세만 91,163~93,909로 갈린다(폭 2,746원). **별도가로 바꾸면 총액이 1,183,280~1,186,300으로 3,020원 갈린다 — 이번엔 고객이 낸다.** 그래서 포함/별도를 먼저 정해야 나머지 두 결정의 무게(국세청 문제냐 고객 항의 문제냐)가 정해진다.

### 결정 ③ 배송비 — "배송비 3,000원은 과세인가"

**요구사항**: 세 규칙 — 언제나 과세 / 과세 상품 비율만큼 과세(비례) / 과세 상품이 하나라도 있으면 전액 과세.

```text
과세 상품이 전체의 93% 인 주문, 배송비 3,000:
  전액 과세   부가세 91,798
  비례        부가세 91,780   차이 18 원 — 작다. 그런데 백만 건이면 1,800만 원.

책 30,000(면세)만 사고 배송비 3,000:
  전액 과세     배송비에 부가세 273 원
  비례/있으면   과세 상품이 없으니 0 원
  → "배송은 용역이니 과세" 도 맞고 "면세 상품의 배송은 면세" 도 맞는다. 판단이 필요하다.
```

- 측정: 배송비 규칙의 영향(-0.123%)은 할인 배분(-2.695%)의 **약 20분의 1**. "작은 것을 오래 논의하고 큰 것을 안 정하는 일이 흔하다."
- 영세율 함정: `hasTaxable()`은 **영세율을 과세로 안 센다**(세율 0이라 배송비에 세금 붙일 근거가 약함). 수출품만 산 주문은 "있으면 전액" 규칙에서 배송비 부가세 0원.

## 쓰이는 자료구조·알고리즘

- **비례배분 `share(amount, part, whole)`** — 곱하기 먼저, 분모 0 보호. [04-refund](../04-refund/2-summary.md)·[07-installment](../07-installment/2-summary.md)와 같은 함수 모양이다.
- **마지막 몫은 빼기(잔여 흡수)** — 셋을 각각 반올림하면 합이 1원 어긋날 수 있으므로 마지막 구분을 `할인 − 앞의 둘`로 구한다. 합을 강제로 지키는 대신 마지막 하나(impl에서는 영세율 몫, `VatCalculator.java:119-120`)가 반올림 나머지를 뒤집어쓴다 — 나머지를 소수부가 큰 순으로 나누는 최대 잔여(largest remainder) 배분보다 단순하게, 한 곳에 몰아주는 방식이다.
- **순차 채우기(cascade)** — `TAXABLE_FIRST`·`EXEMPT_FIRST`는 구분을 정해진 순서로 돌며 그 구분의 금액만큼 채우고 남는 것을 다음으로 넘긴다. 탐욕적으로 앞부터 채우는 한 패스 알고리즘. → [algorithm/23-greedy](../../../algorithm/23-greedy/2-summary.md)
- **역산(과세분 포함가 × 10 / 11)** — 포함가일 때 **과세분**(할인 뺀 과세 상품 + 과세 배송비)에서 공급가액을 구하는 산술(`:171-177`). 면세·영세율은 세금이 0이라 역산하지 않는다. 부가세는 `총액 − 공급가액`으로 구해 두 줄의 합이 언제나 총액이 되게 한다.
- **enum 3개의 데카르트 곱(3×2×3 = 18)** — 측정은 규칙 조합(측정마다 여섯 또는 아홉)을 돌려 `TreeSet`에 부가세·총액을 모으고 크기가 1보다 큰지로 "갈렸나"를 센다(`MeasurementTest.java:90-108`)([09-policy-version](../09-policy-version/2-summary.md) 정답 10번의 비교표 참고).
- **분기 키의 3치 구분(과세/면세/영세율)** — 세율 0인 둘을 한 값으로 합치면 신고서 줄을 못 만든다. 겉값이 같아도 타입을 나눠 끝까지 따로 센다.

## 적용 — 풀어나가는 법

풀이 순서는 컬렉션 공통 — 빈 결정 찾기 → enum 올리기 → 갈리는 입력 만들기 → 조합별 측정.\
부가세에서 갈리는 입력은 **면세 상품이 섞인 주문 + 할인 + 배송비**, 그리고 **포함가와 별도가 둘 다**다. 과세 상품만 담은 주문은 1,955건 중 부가세가 갈린 것이 0건이라 아무것도 검증하지 못한다.\
결정에는 **무게 순서**가 있다: 포함가/별도가를 먼저 정해야 나머지 둘이 "국세청 문제"인지 "고객 항의 문제"인지 정해지고, 할인 배분(−2.695%)이 배송비 규칙(−0.123%)보다 20배 크다 — 큰 것부터 정한다.

### 문제 — 이 챕터가 시키는 것

주어진 규칙은 주문 한 건과 할인 한 줄이 전부다(원본 README 그대로).

```text
  노트북 1,100,000 과세 / 책 30,000 면세 / 수출품 50,000 영세율, 할인 100,000

  할인을 어디서 빼나
    금액 비례   과세 93,220   면세 2,542    영세율 4,238
    과세 먼저   과세 100,000  면세 0        영세율 0
    면세 먼저   과세 70,000   면세 30,000   영세율 0
```

**"고객이 낼 돈은 셋 다 1,083,000 원으로 같다. 갈리는 것은 부가세뿐이다."**

"부가세 10 퍼센트"라는 말에 안 들어 있는 결정이 셋이다(원본 javadoc 그대로).

```text
  할인을 어디서 빼나     과세분인가 면세분인가 비례인가
  표시가가 세금 포함인가  포함이면 역산하고 별도면 더한다
  배송비는 과세인가      과세 상품이 있으면 전액인가 비례인가
```

**셋 다 나라에 내는 돈을 바꾼다.**\
그런데 코드에는 `for` 문 하나로 들어간다.

과제(원본 README "채울 것"): `src/main/java/com/domain/tax/VatCalculator.java` 의 **TODO 1~4**. `TaxOrder` 는 계약이라 다 주어져 있다.

| TODO | 함수 | 시키는 것 |
|---|---|---|
| 1 | `share(amount, part, whole)` | 비례배분 한 조각. **곱하기 먼저**, 분모 0 보호 |
| 2 | `allocate(order, allocation)` | 할인을 과세·면세·영세율로 나눈다. 한 구분을 넘으면 **다음 구분으로 흘려보낸다** |
| 3 | `taxableShipping(order, shippingTax)` | 배송비 중 과세인 부분 — 전액/비례/있으면 전액 |
| 4 | `invoice(order, 결정 셋)` | 세금계산서 한 장. 포함가면 **10 곱하고 11 로 나눠** 역산, 부가세는 **빼기로** |

테스트가 못 박은 계약:

- 세 배분의 몫: `{93,220 · 2,542 · 4,238}` / `{100,000 · 0 · 0}` / `{70,000 · 30,000 · 0}` — 셋 다 합이 정확히 100,000.
- 포함가 아홉 조합의 총액은 **하나뿐**(1,083,000), 부가세는 91,163~93,909(폭 2,746).
- 별도가 아홉 조합의 총액은 1,183,280~1,186,300 — **3,020원 갈린다.**
- 공급가액 + 부가세 = 포함가 총액이 **언제나** 맞는다(917,982 + 91,798 = 1,009,780).
- 상품 금액 0원 주문에서도 비례배분이 예외 없이 돌아간다.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 장애 시나리오와 대처

**1. 부가세 신고액과 세금계산서 합이 안 맞는다**

- 현상: 분기 신고 직전, 회계 시스템의 구분별 공급가액 합과 발행된 세금계산서의 합이 다르다.
- 보이는 형태: 고객 총액은 전부 일치한다. 신고서의 "과세 공급가액"만 몇백만 원 어긋난다.
- 원인: 주문 시스템과 회계 시스템이 **각자** 할인을 배분했고 규칙이 다르다(비례 vs 과세 먼저). 포함가에서는 총액이 같아 화면·QA·결제 대사가 전부 통과한다.
- 대처: 배분 결과(`Invoice`)를 주문 시점에 한 번 계산해 저장하고 회계는 그 값을 읽는다. 신고 전 대사에 "구분별 공급가액 합"을 추가해 총액 말고 **구분**을 맞춘다.

**2. 부분 취소 뒤 수정 세금계산서 금액이 원본과 안 맞는다**

- 현상: 품목 하나를 취소하고 수정 발행했더니 남은 품목의 공급가액이 원 발행분과 다르다.
- 보이는 형태: 원 계산서 − 수정 계산서 ≠ 취소 품목 금액. 회계 담당이 손으로 맞춘다.
- 원인: 취소 시 할인 배분을 **처음부터 다시** 계산했다. 처음 배분을 저장해 두지 않아 남은 품목의 몫이 달라진다(정답 8번 참고).
- 대처: 처음 배분(구분별 할인 몫)을 스냅샷으로 저장하고, 취소는 그 배분을 비례로 되돌린다. 재계산은 새 주문에만 쓴다.

**3. 별도가로 표기 방식을 바꾸자 "총액이 달라졌다"는 항의가 늘었다**

- 현상: 포함가 → 별도가 전환 후 같은 장바구니의 결제 금액이 고객마다 다르게 보인다.
- 보이는 형태: 문의가 3,020원 안팎의 차이로 몰린다.
- 원인: 포함가에서는 아홉 조합의 총액이 하나였지만, 별도가에서는 배분·배송비 규칙 차이가 **고객이 내는 총액**에 드러난다(2,715/5,000).
- 대처: 표기 전환은 배분·배송비 규칙을 같이 고정하고 공지한 뒤에 한다. 전환 전에 두 표기로 총액 폭을 측정해 항의 규모를 미리 안다.

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 나눗셈을 먼저 한다 | 할인 1원을 999,999:1로 나누면 정수 나눗셈 먼저 시 전부 0. **곱하기 먼저** → `{1, 0, 0}` |
| 부가세 = 공급가액 × 0.1 | 합이 1원 안 맞는 경우가 생긴다. **부가세 = 총액 - 공급가액** (빼기) |
| 할인이 한 구분보다 크다 | 다음 구분으로 흘려보낸다. 안 흘리면 할인이 사라져 고객이 더 낸다 |
| 영세율과 면세를 합친다 | 세금계산서의 줄이 다르다. 합치면 신고서를 못 만든다 — `exemptSupply`와 `zeroRatedSupply`를 따로 |
| 상품 금액 0원 주문(사은품+배송비) | 비례배분 분모가 0 — `share()`가 `whole == 0`이면 0 반환. 예외 나면 주문이 안 끝난다 |
| 과세 상품만으로 테스트 | 과세만 있으면 부가세가 한 번도 안 갈린다(1,955주문 중 0). **면세를 넣어야 문제가 시작된다** |

변종 검증에서 드러난 것: 분모 0 보호를 지워도 테스트가 통과했다(0원 주문을 시험한 적이 없었다) → 테스트 추가. 중간 자릿수 10자리는 지워도 안 깨졌다(곱하기 먼저라 필요 없었다) → 두 번 반올림을 한 번으로. **순서(곱하기 먼저)가 load-bearing이고 자릿수는 아니었다.**

## 핵심 문장

- 과세·면세가 섞인 주문의 부가세는 "10%" 로 안 끝난다 — **할인 배분·포함/별도·배송비**라는 세 결정이 더 필요하고, 셋 다 나라에 내는 돈을 바꾼다.
- 포함가에서는 어떤 조합을 골라도 고객이 낼 돈이 같다 — 그래서 **이 결정의 오류는 화면·QA·결제 대사로 못 잡고 세무 신고에서만 드러난다.**
- 금액을 나눌 때는 **곱하기 먼저, 마지막 몫은 빼기로** — 나누기를 먼저 하면 나머지가 사라지고, 각각 반올림하면 합이 안 맞는다.
- 할인이 한 구분을 넘으면 다음 구분으로 흘려보내야 한다 — 흘리지 않으면 할인이 증발해 고객이 더 낸다.
- 영세율은 "세금이 0" 이라는 점에서 면세와 같아 보이지만 **과세 대상 여부가 다르다** — 세금계산서 줄이 다르므로 타입(enum)으로 구분해 끝까지 따로 센다.

### 용어 풀이

- **부가세(VAT)**: 물건값에 붙어 나라에 가는 세금. 한국은 10%.
- **과세/면세/영세율**: 10% 붙음 / 과세 대상 아님 / 과세 대상인데 세율 0%(수출). 영세율≠면세 — 신고서 줄이 다르다.
- **공급가액(supply)**: 세금 붙이기 전 물건값. 공급가액 + 부가세 = 총액.
- **포함가/별도가(VAT_INCLUDED/EXCLUDED)**: 표시 가격에 세금이 들어 있나. 포함이면 역산, 별도면 더한다.
- **역산**: 세금 포함 총액 × 10 / 11 = 공급가액, 부가세는 빼기로. 11로 먼저 나누면 나머지가 사라진다.
- **비례배분(proration)**: 금액 비율대로 나누기. 곱하기 먼저 + 마지막 몫은 빼기.
- **흘려보내기(cascade)**: 할인이 한 구분의 금액을 넘으면 남는 만큼을 다음 구분에서 빼는 것.
- **세금계산서(invoice)**: 공급가액·부가세·면세·영세율·총액이 적힌 문서. 신고의 근거.
- **결제 대사**: 우리 장부의 금액과 결제사(PG) 금액이 맞는지 맞춰보는 일. 총액이 같으면 여기서 안 걸린다.
- **load-bearing**: 건물의 하중을 받치는 벽처럼, 지우면 실제로 무너지는(테스트가 깨지는) 코드 조각.
