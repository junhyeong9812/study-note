### A. 과제

#### 0. 주문 한 건이 안 말해주는 것

- 안 말해주는 결정 셋(원본 javadoc 그대로):

```text
 할인을 어디서 빼나     과세분인가 면세분인가 비례인가
 표시가가 세금 포함인가  포함이면 역산하고 별도면 더한다
 배송비는 과세인가      과세 상품이 있으면 전액인가 비례인가
```

- 총액이 같은 이유: 고객이 낼 돈은 언제나 **`상품 - 할인 + 배송비`** 다.\
  손계산: `1,180,000 - 100,000 + 3,000 = 1,083,000`.\
  할인을 어느 구분에서 빼든 **빼는 금액의 합이 100,000으로 같으므로** 총액이 안 움직인다.
- 갈리는 것: **그 1,083,000 안에서 나라에 가는 몫(부가세)** 이다.\
  포함가 아홉 조합에서 부가세는 91,163 \~ 93,909 로 갈린다(폭 2,746원).

> **부가세(VAT, 부가가치세)** — 물건값에 얹혀서 나라에 가는 세금. 한국은 10%.\
> 예: 11,000원짜리 포함가 상품이면 물건값 10,000 + 부가세 1,000 이다.

- 안 갈리는 것이 위험한 이유: **확인할 방법이 화면에 없다.**\
  고객 화면에도, QA 체크리스트에도, 결제사와 맞춰보는 대사에도 총액만 나온다.\
  전부 1,083,000으로 똑같으니 어느 규칙을 골랐든 "정상"으로 보인다.
- 드러나는 단계: **세무 신고.**\
  그때는 이미 세금계산서가 나갔고 몇 달치가 쌓여 있다.

> **결제 대사(reconciliation)** — 우리 장부의 금액과 결제사(PG) 가 받은 금액이 같은지 맞춰보는 일.\
> 예: "오늘 주문 합계 1억 830만원 / PG 입금 1억 830만원 → 일치"로 끝난다. 그 안의 부가세는 안 본다.

- "면세 먼저"가 면세 상품이 작을 때: **사실상 "거의 과세 먼저"** 다.\
  손계산: 면세분이 30,000뿐이라 할인 100,000 중 30,000만 쓰고 **남은 70,000이 과세로 흘러넘친다.**\
  이름은 정반대인데 결과의 70%가 같은 쪽으로 간다.
- enum 으로 올리는 것과 `for` 문에 박는 것: 박아 넣으면 **세무 판단이 코드 안에 숨는다.**\
  값으로 올리면 세 판을 같은 코드로 돌려 **부가세 총합 차이(6,105,982원)를 숫자로 볼 수 있다.**\
  숫자를 봐야 "이건 개발자가 정할 일이 아니다"가 보인다.

#### 1. TODO 1 — share

정답 코드 (impl/VatCalculator.java):

```java
if (whole == 0) {
    return 0;
}
// 곱하기를 먼저 한다. 나누기를 먼저 하면 나머지가 통째로 사라진다.
// 곱한 뒤에 나누면 한 번만 반올림하면 되므로 중간 자릿수를 안 남겨도 된다.
return BigDecimal.valueOf(amount)
        .multiply(BigDecimal.valueOf(part))
        .divide(BigDecimal.valueOf(whole), 0, rounding)
        .longValueExact();
```

- **곱하기가 먼저다.** `amount × part` 를 먼저 하고 그 결과를 `whole` 로 나눈다.
- 나누기를 먼저 하면 (할인 1원, 999,999 대 1):

```text
 나누기 먼저   1 / 1,000,000 = 0      →  0 × 999,999 = 0     나눌 것이 통째로 사라진다
               1 / 1,000,000 = 0      →  0 × 1       = 0
                                          합계 0원  ← 할인 1원이 증발

 곱하기 먼저   1 × 999,999 / 1,000,000 = 0.999999  →  반올림 1
               1 × 1       / 1,000,000 = 0.000001  →  반올림 0
                                          합계 1원  ← 테스트가 못 박은 {1, 0, 0}
```

> **정수 나눗셈(integer division)** — 소수점을 버리고 정수만 남기는 나눗셈.\
> 예: `1 / 1,000,000` 은 0.000001이 아니라 **0** 이다. 작은 비율이 전부 0으로 뭉개진다.

- `whole == 0` 을 안 막으면: **0원짜리 사은품만 받고 배송비만 내는 주문**에서 `3,000 × 0 / 0` 이 되어 터진다.
- 그 자리가 문제인 이유: 예외가 **세금계산서를 만드는 자리**에서 난다.\
  거기서 터지면 주문이 안 끝난다 — 고객은 결제했는데 주문이 실패한다.
- 중간 자릿수를 안 남겨도 되는 이유: **곱하기를 먼저 하면 큰 정수가 되어 정밀도가 안 날아간다.**\
  `1 × 999,999 = 999,999` 는 이미 온전한 수이고, 나누는 순간 딱 한 번 반올림하면 끝이다.
- 반올림 두 번 vs 한 번: 두 번 하면 **첫 반올림의 오차가 두 번째에 또 굴러간다.**\
  원본은 "중간 10자리로 나눈 뒤 다시 반올림"하던 것을 한 번으로 줄였다.

> **반올림 누적 오차(double rounding)** — 반올림한 값을 다시 반올림하면 한 번에 반올림한 값과 달라질 수 있는 현상.\
> 예: 2.46 → (소수 1자리) 2.5 → (정수) 3. 한 번에 정수로 반올림하면 2다.

#### 2. TODO 2 — allocate

정답 코드:

```java
if (allocation == DiscountAllocation.BY_AMOUNT) {
    long total = taxable + exempt + zero;

long[] order3 = allocation == DiscountAllocation.TAXABLE_FIRST
        ? new long[] {taxable, exempt, zero}
        : new long[] {exempt, taxable, zero};
long[] taken = new long[3];

```

- 각각 반올림하면 합이 어긋나는 이유: 세 몫의 소수 부분이 **각자 올라가거나 내려가서** 합이 원래 금액과 안 맞는다.

```text
 정직하게 셋 다 반올림하면
   과세    100,000 × 1,100,000 / 1,180,000 = 93,220.33  →  93,220
   면세    100,000 ×    30,000 / 1,180,000 =  2,542.37  →   2,542
   영세율  100,000 ×    50,000 / 1,180,000 =  4,237.29  →   4,237
                                              합계        99,999  ← 1원 모자라다

 마지막을 빼기로 구하면
   영세율  100,000 - 93,220 - 2,542                     =   4,238
                                              합계       100,000  ← 언제나 맞는다
```

- 빼기로 구하면: **합이 언제나 정확하다.** 대신 **마지막 하나가 반올림 나머지를 다 뒤집어쓴다**(4,237이 아니라 4,238).
- "마지막"은 **영세율**이다.\
  영세율은 세율이 0이라 **거기서 1원이 왔다갔다 해도 부가세가 안 바뀐다** — 오차를 제일 안 아픈 곳에 몰았다.\
  (원본 코드는 순서만 정하고 근거를 안 적었다 — 근거 부분은 내 추론이다.)

> **나머지 몰아주기(remainder absorption)** — 나눠떨어지지 않는 금액을 한 몫에 몰아서 합을 맞추는 방법.\
> 예: 1,000원을 셋이 나누면 333·333·334 다. 마지막 사람이 1원을 더 가져간다.

- cascade 를 안 하면: 채우지 못한 할인이 **아무 데서도 안 빠진다.**\
  총액은 `상품 - (실제로 뺀 할인) + 배송비` 라서 **뺀 할인이 줄면 고객이 낼 돈이 는다.**
- 할인 1,150,000원에서 두 규칙이 같아지는 이유:

```text
 과세 먼저   과세 1,100,000 다 씀 → 면세 30,000 다 씀 → 영세율 20,000
 면세 먼저   면세    30,000 다 씀 → 과세 1,100,000 다 씀 → 영세율 20,000
                        결과는 둘 다 {과세 1,100,000, 면세 30,000, 영세율 20,000}
```

  **할인이 커서 앞의 두 통을 다 채우면 순서가 의미를 잃는다.** 남는 자리가 영세율 하나뿐이라서다.

- 할인이 0원이면: 셋 다 `{0, 0, 0}` 이라 **세 규칙의 차이가 아예 안 보인다.**\
  "할인 없는 깔끔한 예제"로 시험하면 이 박스의 절반이 안 보인다.
- 생성자가 `discount > total` 을 막는데도 cascade 가 필요한 이유: 생성자가 막는 것은 **주문 전체 합**을 넘는 경우뿐이다.\
  할인 1,150,000은 상품합 1,180,000보다 작아서 통과하지만 **과세분 1,100,000 하나는 넘는다.**\
  "전체는 안 넘는데 한 구분은 넘는" 구간이 그대로 남는다.

#### 4. TODO 4 — invoice

정답 코드:

```java
long[] discounts = allocate(order, allocation);

long taxableGross = order.amountOf(Category.TAXABLE) - discounts[0]
        + taxableShipping(order, shippingTax);
long exemptSupply = order.amountOf(Category.EXEMPT) - discounts[1]
        + (order.shippingFee() - taxableShipping(order, shippingTax));
long zeroRatedSupply = order.amountOf(Category.ZERO_RATED) - discounts[2];

if (basis == PriceBasis.VAT_INCLUDED) {
    // 10 을 곱한 뒤 11 로 나눈다. 11 로 먼저 나누면 나머지가 사라진다.
    taxableSupply = BigDecimal.valueOf(taxableGross)
            .multiply(BigDecimal.TEN)
            .divide(BigDecimal.valueOf(11), 0, rounding)
            .longValueExact();
    vat = taxableGross - taxableSupply;
} else {
    taxableSupply = taxableGross;
    vat = round(BigDecimal.valueOf(taxableGross).multiply(RATE));
}
long total = taxableSupply + vat + exemptSupply + zeroRatedSupply;
```

- 11로 먼저 나누면 **나머지가 사라진다** — `share` 와 똑같은 함정이다.\
  `1,009,780 / 11` 을 정수로 하면 91,798 이 되고 거기에 10을 곱하면 917,980 — **2원이 증발**한다.
- 손계산 (포함가·비례배분·배송비 전액 과세):

```text
 과세 총액  1,100,000 - 93,220 + 3,000 = 1,009,780
 공급가액   1,009,780 × 10 / 11 = 917,981.81...  →  917,982
 부가세     1,009,780 - 917,982               =    91,798   ← 빼기로
 검산       917,982 + 91,798 = 1,009,780  ✔ 언제나 맞는다
```

- `공급가액 × 0.1` 로 구하면 안 되는 이유: **합이 안 맞는 경우가 생긴다.**\
  이 예에서는 `917,982 × 0.1 = 91,798.2 → 91,798` 로 우연히 같지만, 반올림이 위로 가면 `공급가액 + 부가세 > 총액` 이 되어 세금계산서가 스스로 안 맞는다.
- 빼기로 구하면 맞는 등식: **`공급가액 + 부가세 = 포함가 총액`** 이 정의상 성립한다(빼기로 만든 값이라서).
- 면세·영세율이 역산할 것 없는 이유: **세금이 0이다.**\
  세금이 0이면 "세금 포함 금액"과 "물건값"이 같은 수다. 포함가든 별도든 금액 그대로가 공급가액.
- 별도가에서는 `공급가액 × 0.1` 을 반올림해 부가세를 구한다.\
  여기서는 빼기를 못 쓴다 — **총액이 아직 없기 때문**이다. 총액은 공급가액과 부가세를 더해야 나온다.

```text
 포함가  총액이 먼저 있다  →  공급가액을 역산  →  부가세 = 총액 - 공급가액
 별도가  공급가액이 먼저 있다  →  부가세를 곱셈으로  →  총액 = 공급가액 + 부가세
                                              방향이 반대다
```

- 과세 총액의 세 조각: **① 과세 상품 금액 ② 빼기: 과세분에 배분된 할인 ③ 더하기: 과세로 본 배송비.**
- 영세율과 면세를 합치면: **신고서를 못 만든다.**\
  면세는 과세 대상이 아니고 영세율은 **과세 대상인데 세율이 0** 이다 — 세금계산서에서 줄이 다르다.

> **영세율(zero-rated)** — 부가세를 매기는 대상이긴 한데 세율이 0%인 것. 수출품이 대표.\
> 예: 수출품 50,000원은 부가세가 0원이지만 신고서의 "영세율" 칸에 적어야 하고, 면세 칸에 적으면 틀린 신고다.

### B. 개념

#### 5. 함정 (README)

- 다섯: ① **나눗셈을 먼저 하는 것**(할인 1원을 999,999 대 1로 나누면 나눌 것이 통째로 사라진다) ② **부가세를 공급가액에 0.1을 곱해 구하는 것**(합이 1원 안 맞는 경우가 생긴다 — **빼기로** 구해야 두 줄이 언제나 맞는다) ③ **할인이 한 구분을 넘칠 때 안 흘려보내는 것**(할인이 사라지고 낼 돈이 는다) ④ **영세율과 면세를 합치는 것**(세금계산서 줄이 달라 신고서를 못 만든다) ⑤ **상품 금액이 0인 주문**(배송비 비례배분의 분모가 0이 된다).
- 나눗셈 순서가 제일 앞인 이유: 이 함정만 **금액이 조용히 0이 된다.**\
  나머지 넷은 1원\~수만 원이 어긋나지만, 이건 **나눌 것 전체가 없어진다.**\
  실제로 변종 검증에서 "나눗셈을 먼저 하는 변종은 잡힌다 — **순서가 load-bearing**"으로 확인됐다.
- 상품 금액 0원 주문의 정체: **0원짜리 사은품만 받고 배송비만 내는 주문.**\
  실제로 있는 주문인데 개발 중에는 거의 안 만든다.

#### 6. 측정 — 답이 갈리는 건수

- 주문 5,000개, 여섯 규칙 조합:

```text
 과세·면세가 섞인 주문     2,569 / 5,000
 부가세가 갈린 주문        2,661 / 5,000
 총액이 갈린 주문              0 / 5,000   ← 고객은 한 번도 못 느낀다
```

- 부가세 폭: 평균 **1,405.5원**, 최대 **9,091원**.
- 세 배분의 부가세 총합(포함가·배송비 전액 과세):

```text
 면세 먼저   226,589,475
 금액 비례   223,912,515
 과세 먼저   220,483,493     면세 먼저 대비  -2.695 %

 차이  226,589,475 - 220,483,493 = 6,105,982 원
```

- 금액으로 **6,105,982원**(약 610만 원). 그리고 **고객이 낸 돈은 셋 다 같다.**
- 배송비 규칙의 영향: **약 20분의 1.**

```text
 전액 과세    223,912,515
 있으면 전액  223,827,885
 비례         223,637,401      전액 과세 대비  -0.123 %

 할인 배분 -2.695 %  vs  배송비 -0.123 %   →  약 22 배 차이
```

- 교훈: **"작은 것을 오래 논의하고 큰 것을 안 정하는 일이 흔하다."**\
  배송비 규칙은 눈에 보여서 회의에 오르고, 할인 배분은 `for` 문 한 줄이라 아무도 안 본다.
- 별도가로 바꾸면 총액이 갈리는 주문: **0 → 2,715 / 5,000**(아홉 조합 기준).\
  총합도 3,650,598,000 → 3,901,586,424 로 바뀐다.
- 포함/별도를 먼저 정해야 하는 이유: 그 하나로 **"고객이 못 느끼는 문제"가 "고객이 항의하는 문제"로 바뀐다.**\
  즉 나머지 두 결정의 **무게**(국세청 문제냐 고객 문제냐)가 여기서 정해진다.
- 과세만 담긴 주문 **1,955개 중 부가세가 갈린 것은 0개**다.\
  나눌 면세분이 없고 배송비도 어차피 전액 과세라서다.
- 위험한 이유: **개발할 때 만드는 주문은 대개 과세 상품만 담는다.**\
  그 주문으로는 여섯 규칙이 전부 같은 답을 내서 "잘 돌아간다"로 보인다.\
  **면세를 넣어야 시작된다.**

> **가려진 갈림(masking)** — 시험 데이터가 한쪽에 쏠려 있어서, 실제로는 갈리는 결정이 안 갈리는 것처럼 보이는 것.\
> 예: 과세 상품만 담은 테스트 주문 1,955건에서는 세 배분 규칙이 전부 같은 부가세를 낸다.

#### 7. 변종 검증에서 고친 것

- 분모 0 보호를 지워도 통과한 이유: **0원짜리 사은품만 받고 배송비만 내는 주문을 시험한 적이 없었다.**\
  테스트에 없는 입력은 보호 코드가 있든 없든 결과가 같다.
- 중간 자릿수 10자리를 0으로 바꿔도 안 깨진 이유: **곱하기를 먼저 하므로 중간 자릿수가 필요 없었다.**\
  큰 정수를 한 번에 나누면 중간에 소수를 남길 일이 애초에 없다.
- "순서가 load-bearing 이고 자릿수는 아니었다": **곱하기 먼저**라는 순서를 바꾸면 테스트가 깨지지만, **자릿수 10자리**는 지워도 안 깨진다.\
  즉 안전을 실제로 떠받치던 것은 순서였고, 자릿수는 "안전해 보이는 장식"이었다.

> **변종 검증(mutation testing)** — 코드를 일부러 조금 망가뜨려 보고 테스트가 잡아내는지 확인하는 방법.\
> 예: `whole == 0` 보호를 지웠는데 테스트가 다 통과하면, 그 보호를 지키는 테스트가 없다는 뜻이다.

> **load-bearing** — 건물의 하중을 받치는 벽처럼, 지우면 실제로 무너지는(테스트가 깨지는) 코드 조각.\
> 예: `multiply` 를 `divide` 앞으로 둔 순서는 load-bearing 이고, 중간 자릿수 10은 아니었다.

- 지워도 안 깨지는 코드를 발견했을 때의 선택 둘: **① 그 코드를 지킬 테스트를 추가한다**(분모 0 보호 — 실제로 필요한 보호였다) **② 그 코드를 지운다**(중간 자릿수 — 실제로 필요 없었다).\
  어느 쪽인지는 "그 입력이 실제로 오는가"로 가른다.

#### 8. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 부분 취소: **처음 배분을 저장해둬야 한다.**\
  이 코드의 `allocate` 는 주문 전체 금액 비율로 나눈다 — 한 품목을 빼고 다시 부르면 **남은 품목들의 비율이 바뀌어 배분이 통째로 달라진다.**\
  이미 세금계산서가 나갔다면 그건 "취소"가 아니라 "다시 계산"이라 신고와 안 맞는다.\
  그래서 `discountSplit` 의 결과를 주문에 **못 박아 저장**하고, 취소는 그 저장된 몫에서 빼는 쪽이 맞다. (원본에 근거 없음 — 내 추론)
- 발행 후 규칙 변경: **이미 낸 신고는 못 바꾼다 — 바꾸려면 수정 세금계산서다.**\
  그래서 규칙은 **발행 시점의 것으로 고정**돼야 하고, `invoice` 가 규칙을 인자로 받는 구조가 여기에 유리하다(어느 규칙으로 발행했는지를 주문에 같이 저장할 수 있다).\
  규칙을 코드에 박아뒀다면 배포 시각이 곧 규칙 변경 시각이 되어 **언제부터 달라졌는지 추적이 안 된다.**\
  이 주제는 09-policy-version 이 통째로 다룬다. (원본에 근거 없음 — 내 추론)
- 세트 상품의 구분: `Line` 이 `category` 를 하나만 갖는 구조라 **세트를 한 줄로 두면 구분을 못 정한다.**\
  방법은 둘 — **① 세트를 과세/면세 두 줄로 쪼개고 금액을 나눈다**(그럼 "얼마씩 나누나"가 또 결정이다) **② 세트 전체를 한 구분으로 본다**(간단하지만 실제 세법과 어긋날 수 있다).\
  ①을 고르면 이 박스의 배분 문제가 **품목 안에서 한 번 더 반복**된다. (원본에 근거 없음 — 내 추론)
- 영세율을 과세로 세나: 이 코드는 **안 센다**(`hasTaxable()` 이 `TAXABLE` 만 본다). 테스트가 근거를 적어뒀다 — "세율이 0이라 배송비에 세금을 붙일 근거가 약하다."
- 바뀌는 것: 수출품만 산 주문(50,000 + 배송비 3,000)에서 "있으면 전액" 규칙의 배송비 부가세가 **0원 ↔ 273원**으로 갈린다(테스트가 두 값을 다 못 박았다).

#### 9. 연결

- "고객 화면에 안 보이는 결정": **01-parking-fee의 자정 분할**과 같은 자리다.\
  거기서는 "손님에게 유리하게"라는 지침으로 못 정했고, 여기서는 "총액이 같으니 상관없다"로 안 정해진다.\
  둘 다 **흔한 검증 수단(화면·QA·지침)이 결정을 대신 못 해주는** 자리다.
- "곱하기 먼저, 마지막 몫은 빼기": **05-multi-currency(환율 변환)**, **07-installment(할부 원금 쪼개기)**, **22-parcel-split(분할)** — 나누어떨어지지 않는 금액을 여럿에 나누는 곳마다 같은 규칙이 나온다.
- `FeePolicy` 와의 비교: **같은 것** — 요구사항 문장에 없는 결정을 코드 밖으로 올려 두 판을 나란히 돌려볼 수 있게 했다.\
  **다른 것** — `FeePolicy` 는 값(숫자) 위주의 record 라 "10분이냐 15분이냐"를 바꾸지만, 여기는 **enum 세 개**라 "어느 방식이냐"를 바꾼다. 방식은 값과 달리 **중간이 없어서** 반드시 하나를 골라야 한다.
