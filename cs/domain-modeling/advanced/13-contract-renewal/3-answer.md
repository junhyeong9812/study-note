### A. 과제

#### 0. 한 줄 요구사항이 안 말해주는 것

- 안 말해주는 자리 셋(원본 javadoc 그대로):

```text
 30 일 전을 어디서 세나   종료일부터인가 마지막 날부터인가   → NoticeAnchor
 유예 기간 중에는         계약이 살아 있나 죽었나            → GraceState
 갱신 기간은              같은 길이인가 딱 1 년인가          → RenewalTerm
```

- 12월 2일 통지자:

```text
 종료일 기준    기한 2026-12-02   →  기한 당일이니 해지    (daysOfNotice = 0)
 마지막 날 기준 기한 2026-12-01   →  하루 넘겼으니 갱신    (daysOfNotice = -1)

 같은 통지서 한 장이 해지와 1 년 연장으로 갈린다
```

- "30일 전까지"의 당일: **포함이다.** 그날까지 통지하면 해지된다(README 둘째 함정, 테스트 `deadlineIsInclusive`).
- 그 하루에 달린 금액: **1년치 요금**이다. 월 10만 원이면 120만 원이 통지서 한 장의 날짜에 달린다.
- 셋 다 돈이 오가는 날을 바꾸는 이유: **통지 기한**은 해지냐 연장이냐를, **유예 상태**는 15일치 서비스가 공짜냐를, **갱신 기간**은 다음 청구가 언제 얼마나 도느냐를 바꾼다.

#### 1. Contract — 반열림 구간

- 닫힌 구간으로 잡으면: **"12월 31일까지"와 "1월 1일부터" 사이에 하루가 겹치는지 비는지를 매번 따져야 한다.**\
  반열림이면 한 계약의 종료일이 곧 다음 계약의 시작일이라 그 질문이 아예 안 생긴다.
- `activeOn`:

```java
return !date.isBefore(startedOn) && date.isBefore(endsOn);
```

  시작일은 **이상**(`!isBefore`), 종료일은 **미만**(`isBefore`).

```text
 [2026-01-01, 2027-01-01)

 2025-12-31   밖       시작 전
 2026-01-01   안       시작일은 포함
 2026-12-31   안       마지막 날
 2027-01-01   밖       종료일은 제외 — 다음 계약의 첫날
```

- `lastDay()` 는 **종료일 하루 전**(2026-12-31), `endsOn()` 은 **계약이 이미 끝난 날**(2027-01-01)이다.\
  사람이 말하는 "12월 31일까지"가 `lastDay` 고, 코드가 계산에 쓰는 경계가 `endsOn` 이다.
- 저절로 맞아떨어지는 것: **갱신된 계약이 앞 계약과 틈도 겹침도 없이 이어진다.**\
  새 계약의 시작일 = 앞 계약의 `endsOn` 이면 끝이다. 테스트가 못 박았다 — `next().activeOn(contract.lastDay())` 는 false, `next().activeOn(contract.endsOn())` 는 true.
- 종료일 == 시작일을 거부하는 이유: 반열림에서 그것은 **길이 0인 기간**이다.\
  하루짜리 계약을 만들려면 `[1/1, 1/2)` 로 써야 하고, `[1/1, 1/1)` 은 아무 날도 안 포함한다 — 실수일 가능성이 높으므로 예외로 막는다.

#### 2. TODO 1 — noticeDeadline

정답 코드 (impl/RenewalPolicy.java):

```java
LocalDate anchorDate = anchor == NoticeAnchor.FROM_END_DATE
        ? contract.endsOn()
        : contract.lastDay();
return anchorDate.minusDays(noticeDays);
```

- 두 기준:

```text
 FROM_END_DATE   2027-01-01 - 30 = 2026-12-02
 FROM_LAST_DAY   2026-12-31 - 30 = 2026-12-01
                                   ─────┬─────
                          하루 차이. 그 하루가 갈림이다
```

- 이르고 늦은 이유: **기준일이 하루 차이나기 때문**이다.\
  `lastDay` 가 `endsOn` 보다 하루 앞이니, 거기서 같은 30일을 빼면 기한도 하루 앞이다 — 즉 **마지막 날 기준이 고객에게 더 빡빡하다**(하루 일찍 통지해야 한다).
- 자동 갱신이 아닌 계약에도 기한을 알려주는 이유: **고객이 "언제까지 통지해야 하나요"라고 물으면 답해야 한다**(테스트 주석 원문).\
  갱신 여부와 기한 계산은 별개의 질문이고, `Renewal` 이 둘 다 담는다.
- `noticeDays == 0`: 기한이 **기준일 그 자체**가 된다(종료일 기준이면 2027-01-01).\
  "끝나는 날까지 통지하면 된다"는 뜻이다.

#### 3. TODO 2 — renew

정답 코드:

```java
LocalDate deadline = noticeDeadline(contract, anchor);
long daysOfNotice = noticedOn == null
        ? Long.MIN_VALUE
        : ChronoUnit.DAYS.between(noticedOn, deadline);

boolean cancelled = noticedOn != null && !noticedOn.isAfter(deadline);
if (!contract.autoRenew() || cancelled) {
    return new Renewal(false, null, deadline, daysOfNotice);
}

LocalDate nextEnd = term == RenewalTerm.ONE_YEAR
        ? contract.endsOn().plusYears(1)
        : contract.endsOn().plusDays(
                ChronoUnit.DAYS.between(contract.startedOn(), contract.endsOn()));
return new Renewal(
        true, contract.spanning(contract.endsOn(), nextEnd), deadline, daysOfNotice);
```

- "기한 안에 통지" = **`!noticedOn.isAfter(deadline)`**, 즉 `noticedOn <= deadline`.\
  당일은 **해지 쪽**에 포함된다. `isBefore` 로 쓰면 기한 당일 통지가 갱신이 되어 계약서와 어긋난다.
- `daysOfNotice` 는 **통지가 기한보다 며칠 이른가**다. **양수면 이르고, 0이면 당일, 음수면 늦었다.**

```text
 12/01 통지, 기한 12/02   between(12/01, 12/02) = +1   하루 일찍
 12/02 통지, 기한 12/02   between(12/02, 12/02) =  0   당일 → 해지
 12/02 통지, 기한 12/01   between(12/02, 12/01) = -1   하루 늦음 → 갱신
```

- `Long.MIN_VALUE` 의 뜻: **통지가 아예 없었다**는 표시다.\
  0을 쓰면 "기한 당일 통지"와 구별이 안 되고, 음수 아무 값이나 쓰면 "며칠 늦었다"로 오해된다. 있을 수 없을 만큼 작은 값을 두어 **"이 값은 날 수가 아니다"** 를 드러낸다. (다만 `null` 을 담을 수 있는 타입을 쓰는 편이 더 정직하다 — 원본은 `long` 을 골랐다.)

> **초병값(magic value)** — "없음"을 나타내려고 정상 범위 밖의 특별한 값을 쓰는 것.\
> 예: 통지가 없을 때 `Long.MIN_VALUE` 를 담는다. 편하지만, 그 뜻을 모르는 코드가 그냥 숫자로 계산하면 조용히 틀린다.

- 안 갱신에도 기한을 담는 이유: **거절 사유를 스스로 설명하기 위해서**다.\
  "왜 해지됐나"에 답하려면 기한이 며칠이었는지와 며칠 차이였는지가 함께 있어야 한다.
- 새 계약의 시작일: **앞 계약의 `endsOn`** 이다(마지막 날 다음이 아니라).\
  반열림이라 그 둘이 같은 날이다 — `lastDay + 1일 == endsOn`.
- 같은 길이: `endsOn + (endsOn - startedOn)` **날 수**다.\
  달이 아니라 날로 더한다.
- 1개월 계약이 3월 4일이 되는 이유:

```text
 [2026-01-01, 2026-02-01)    길이 = 31 일 (1월이 31일)

 같은 길이   2026-02-01 + 31 일
             2월은 28 일 →  2026-02-01 +28 = 2026-03-01,  +3 = 2026-03-04
 달로 더하면  2026-02-01 +1개월 = 2026-03-01

 3 일 차이. 날 수로 더하면 "짧은 달 뒤에 긴 기간"을 받는다
```

- 약관이 적어두는 쪽: **대개 안 적혀 있다**(테스트 주석 원문 — "어느 쪽이 맞는지는 약관이 정한다. 그리고 대개 안 적혀 있다").\
  그래서 이 챕터가 그 자리를 enum 으로 올려 둘 다 돌려본다.

#### 4. TODO 3 — servesOn

정답 코드:

```java
if (contract.activeOn(date)) {
    return true;
}
if (date.isBefore(contract.endsOn()) || !date.isBefore(graceEndsOn(contract))) {
    return false;
}
return graceState == GraceState.ACTIVE;
```

- 세 구간:

```text
 [2026-01-01, 2026-02-01) 계약, 유예 15 일 → 유예 [2026-02-01, 2026-02-16)

 구간               예                    답
 계약 전            2025-12-31            false
 계약 안            2026-01-15            true  (유예 규칙 무관)
 유예 안            2026-02-08            GraceState 가 정한다
 유예 뒤            2026-03-01            false
```

- 계약 시작 전: **두 번째 `if` 의 `date.isBefore(endsOn())`** 으로 빠진다.\
  시작 전 날짜는 당연히 종료일보다도 앞이므로 여기서 false 가 된다 — 조건 하나가 "계약 전"과 "계약 안인데 activeOn 이 이미 true 로 걸러간 나머지"를 함께 처리한다.
- 계약 안에서 상관없는 이유: **첫 줄에서 이미 true 로 돌아간다.**\
  유예는 계약이 끝난 **뒤**의 규칙이라, 계약 안에서는 물어볼 일이 없다. 그래서 유예를 안 겪는 자료로 시험하면 이 갈래가 통째로 안 돈다.
- 누가 손해인가:

```text
 ACTIVE    서비스가 계속 나간다   →  못 받은 요금만큼 회사가 손해
 EXPIRED   서비스가 끊긴다        →  결제하면 되살린다. 고객이 불편
```

  "유예 기간"이라는 말 자체는 이 둘 중 무엇인지를 안 정한다. 그리고 **그 15일치 서비스가 공짜인지 아닌지가 거기서 갈린다.**
- 유예 0일: **두 규칙이 같아진다.**\
  `graceEndsOn == endsOn` 이라 유예 구간이 빈 구간이 되고, 종료일에 바로 끊긴다. 테스트가 못 박았다.

#### 5. TODO 4 — inGrace

정답 코드:

```java
return !date.isBefore(contract.endsOn()) && date.isBefore(graceEndsOn(contract));
```

- 구간 모양: **`[endsOn, endsOn + graceDays)`** — 계약과 똑같이 반열림이다.
- 네 날:

```text
 2026-01-31   계약 안 (마지막 날)        inGrace = false
 2026-02-01   유예 첫날 (= endsOn)       inGrace = true
 2026-02-15   유예 마지막 날             inGrace = true
 2026-02-16   유예도 끝 (= graceEndsOn)  inGrace = false
```

- 안 겹치게 하는 부등호: **`!date.isBefore(endsOn)`** 이다.\
  계약은 `endsOn` 미만이고 유예는 `endsOn` 이상이라, 같은 부등호 한 쌍이 두 구간을 딱 붙여 놓는다 — 겹치는 날도 비는 날도 없다.
- `graceEndsOn` 이 "마지막 날 다음"인 이유: **계약의 `endsOn` 과 같은 규칙을 쓰기 위해서**다.\
  구간의 끝을 항상 "제외되는 첫날"로 두면, 구간을 이어 붙이거나 비교할 때 ±1일을 따질 필요가 없다.

### B. 개념

#### 6. 측정 — 기준 하나로 갈리는 건수

통지 기한 앞뒤 60일에 무작위로 통지한 10,000건 (README 표 그대로):

| | |
|---|---|
| 기준이 갈린 건 | **97 / 10,000** |
| 해지 (종료일 기준) | 5,014 |
| 해지 (마지막 날 기준) | 4,917 |

- 전부 분쟁이 되는 이유: **갈린 97건은 전부 "고객은 해지했다고 믿고 회사는 갱신했다고 믿는" 건**이다.\
  나머지 9,903건은 어느 기준이든 답이 같아서 아무 일도 안 생긴다 — 갈린 것만 100 % 문제가 된다.
- "중간이 없다"의 뜻: **결과가 이분법**이라는 것이다.\
  요금이 조금 더 나오는 게 아니라 **0원이냐 1년치냐**로 갈린다. 반올림 오차처럼 "조금 틀린 값"이 없어서 협상할 여지도 없다.

#### 7. 측정 — 통지가 기한 근처에 몰리면

| 흩어진 폭 | 갈린 건 / 10,000 |
|---|---|
| 60 일 | 97 |
| 30 일 | 170 |
| 10 일 | 508 |
| 3 일 | **1,429** |

- 몇 배인가: **약 15배**(97 → 1,429).
- 몰리는 이유: **실제 통지는 기한을 의식해서 들어온다.**\
  고객은 "30일 전까지"를 보고 그 무렵에 통지하지, 아무 날에나 무작위로 통지하지 않는다.
- 고르게 흩뿌린 자료로 재면: **이 문제를 15배 작게 본다.**\
  "1 %도 안 되는 구석 사례"라고 판단하고 넘어가는데, 실제 분포에서는 **14 %가 갈린다.**

> **분포 가정** — 측정 자료를 만들 때 "값이 어떻게 흩어져 있는가"에 대해 몰래 들어가는 가정.\
> 예: 통지일을 60일에 고르게 뿌리면 97건이 갈리지만, 현실처럼 기한 근처 3일에 몰아 뿌리면 1,429건이 갈린다. 코드는 그대로인데 결론이 뒤집힌다.

#### 8. 측정 — 계약 길이별 갱신 기간

| 계약 길이 | 같은 길이 | 1 년 |
|---|---|---|
| 1 개월 | 31 일 | 365 일 |
| 6 개월 | 181 일 | 365 일 |
| 12 개월 | **365 일** | **365 일** |
| 24 개월 | 730 일 | 366 일 |

- 방향이 반대인 이유: **1년 규칙은 모든 계약을 1년으로 "끌어당긴다".**\
  1년보다 짧으면 늘리고(1개월 → 12배), 길면 줄인다(24개월 → 절반).
- 1년 계약에서만 같은 것이 함정인 이유: **예제는 대개 1년 계약이다.**\
  1년짜리로만 시험하면 두 규칙이 항상 같은 답을 내므로 **이 갈래가 아예 안 보인다**. 테스트가 그 사실 자체를 `yearlyContractsLookTheSame` 으로 못 박아 뒀다.
- 2년 계약을 1년으로 줄이면: **고객은 2년을 기대했는데 1년 뒤에 다시 정해야 한다.**\
  가격 인상·조건 변경의 기회가 1년 앞당겨 오고, 장기 계약의 이점이 사라진다.

#### 9. 측정 — 윤년 밀림

- 1년 계약을 다섯 번 갱신한 개시일:

| | 개시일 |
|---|---|
| 같은 길이 | **2030-12-31** |
| 1 년 | 2031-01-01 |

- 손계산:

```text
 회차   같은 길이 (365 일 더하기)          1 년 (plusYears)
  0     2026-01-01
  1     2027-01-01                        2027-01-01
  2     2028-01-01                        2028-01-01
  3     2028-12-31  ← 2028 은 윤년(366)   2029-01-01
  4     2029-12-31                        2030-01-01
  5     2030-12-31                        2031-01-01
```

- 12월 31일에 떨어지는 이유: **2028년이 윤년이라 1년이 366일인데 365일만 더했다.**\
  하루 모자란 만큼 앞당겨진다.
- 되돌아오지 않는 이유: **다음 갱신도 그 앞당겨진 날에서 다시 365를 더하기 때문**이다.\
  기준이 원래 날짜가 아니라 **직전 결과**라서, 한 번 밀린 오차가 계속 쌓인다.

> **누적 오차(drift)** — 매번의 계산을 직전 결과 위에 쌓아서, 작은 오차가 안 사라지고 누적되는 것.\
> 예: "365일 더하기"를 반복하면 윤년마다 하루씩 앞당겨지고, 원래 날짜로 돌아오는 힘이 어디에도 없다.

- 4년에 하루씩이 더 위험한 이유: **오래 안 보인다.**\
  배포 직후 몇 년은 멀쩡해 보이다가, 청구 주기·정산 마감과 어긋나기 시작할 때는 이미 수많은 계약에 퍼져 있다.

#### 10. 측정 — 10년 누적과 유예

- 갱신 횟수(1~24개월짜리 1,000건, 10년): **19,614회 vs 9,432회**(같은 길이 쪽이 두 배).
- 갱신 횟수가 뜻하는 것: **시스템 부하이자 고객 접점 수**다.\
  갱신마다 안내 메일이 나가고 결제가 잡히고 정산이 돈다 — 규칙 하나가 이 모든 일의 양을 두 배로 만든다.
- 유예에 들어간 날이 0일인 이유: **갱신된 계약이 앞 계약의 종료일부터 바로 이어지기 때문**이다.\
  틈이 없으니 "계약이 끝났는데 아직 안 이어진 날"이 아예 안 생긴다.
- 유예 규칙이 도는 계약: **갱신에 실패하는 계약**(자동 갱신이 꺼졌거나 기한 안에 해지 통지가 들어온 것)뿐이다.
- 검증하기 어려운 이유: **개발 자료는 대개 갱신이 잘 된다.**\
  성공 경로만 있는 자료로는 유예 코드가 한 줄도 안 실행된다 — 12번의 "빈 극장", 11번의 "TTL 을 길게 둠"과 같은 구조다.

#### 11. 함정 (README)

- 넷: ① **기간을 닫힌 구간으로 잡는다** ② **"30일 전까지"의 당일을 뺀다**(그날은 포함이다) ③ **같은 길이를 날 수로 더한다**(윤년마다 하루씩 밀리고 안 되돌아온다) ④ **유예 기간 중의 상태를 안 정한다**(서비스가 나가느냐 마느냐가 돈이다).
- 닫힌 구간이면 매번 다시 물어야 하는 것: **"12월 31일까지"와 "1월 1일부터" 사이에 하루가 겹치나 비나.**\
  계약을 이어 붙일 때마다, 두 기간을 비교할 때마다 그 질문이 되살아난다.
- 안 되돌아오는 것: **윤년 때문에 앞당겨진 하루**다. 4년에 하루씩 쌓인다.
- 유예 상태를 안 정하면: **그 15일치 서비스가 공짜인지 아닌지**가 안 정해진다.\
  ACTIVE 면 회사가 받지도 못한 요금의 서비스를 내주고, EXPIRED 면 고객이 끊긴 채로 결제를 기다린다.

#### 12. 변종 검증

- 고칠 것이 없었던 이유: **변종 13개가 전부 잡혔다.**\
  경계를 미리 날짜로 못 박아 둔 테스트가 변종을 남김없이 걸러냈다.
- 주효했던 것: ① **통지 기한을 두 기준으로 각각 날짜까지 못 박고**(12/01 과 12/02) **그 하루에 통지한 경우를 따로 시험**한 것, ② **유예 기간의 앞뒤 경계 네 날**(1/31·2/1·2/15·2/16)을 전부 확인한 것.
- 앞 챕터와 다른 점: 11·12번은 **자료가 결함을 덮고 있어서**(품목 하나, 붙어 있는 빈자리) 테스트를 고쳐야 했다.\
  여기서는 **갈리는 자리를 미리 알고 그 날짜를 직접 써뒀다** — 경계가 날짜라서 "일부러 만들기"가 쉬웠던 것도 크다.

> **경계값 테스트(boundary test)** — 답이 바뀌는 지점의 바로 앞·그 자리·바로 뒤를 각각 확인하는 것.\
> 예: 기한 12/02 라면 12/01·12/02·12/03 셋을 다 넣어 본다. 한가운데 값만 넣으면 부등호 실수가 안 잡힌다.

#### 13. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 기한 하루 뒤에 통지한 고객: 코드는 `daysOfNotice = -1` 과 `noticeDeadline` 을 **결과에 담아 돌려준다** — 답할 재료가 이미 있다.\
  근거는 **약관의 기준(NoticeAnchor)** 에 있어야 하는데, 그게 약관에 안 적혀 있으면 회사가 나중에 고른 기준이 된다. 그래서 진짜 답은 **"기준을 미리 약관에 적어두는 것"** 이고, 코드의 enum 은 그 자리가 비어 있다는 사실을 드러내는 장치다. (원본에 근거 없음 — 내 추론)
- 갱신 안내 메일: **통지 기한보다 앞이어야** 고객이 선택할 수 있다.\
  기한 뒤에 보내면 "알려주기 전에 이미 갱신됐다"가 되어 분쟁이 된다. 다만 너무 일찍 보내면 잊어버린다 — 실무에서는 보통 기한 전 여러 번 보낸다. 코드에는 이 시점이 없다: `noticeDeadline` 은 있는데 "언제 알릴까"는 아직 모델 밖이다. (원본에 근거 없음 — 내 추론)
- 요금 인상 후 자동 갱신: `Contract.spanning` 은 **`monthlyFee` 를 그대로 물려준다** — 지금 모델에는 인상 자체가 없다.\
  인상을 넣으려면 갱신 시점에 새 요금을 받아야 하고, 그러면 **"인상을 통지 기한 전에 알렸나"** 가 새 계약 조건이 된다. 안 알리고 올리면 통지 기한의 의미가 사라진다 — 고객은 얼마가 될지 모르고 해지 여부를 정해야 하기 때문이다. (원본에 근거 없음 — 내 추론)
- 유예 중 결제: 두 선택지가 있다 — **앞 계약의 종료일부터**(기간이 안 밀리고 청구 주기가 유지되지만 이미 지난 며칠 값을 받는다) 또는 **결제일부터**(고객에게 유리하지만 청구 주기가 계속 밀린다).\
  `GraceState` 가 ACTIVE 면 그 며칠도 서비스가 나갔으니 **종료일부터**가 일관되고, EXPIRED 면 안 나갔으니 **결제일부터**가 일관된다. 즉 이 답은 유예 상태 결정에 딸려 온다. (원본에 근거 없음 — 내 추론)

#### 14. 연결

- 01-parking-fee 와의 같은 자리: **"하루"의 기준**이다.\
  주차는 자정 기준이냐 입차 후 24시간이냐로 갈렸고, 여기는 종료일 기준이냐 마지막 날 기준이냐로 갈린다 — 둘 다 **어디서부터 세는가**가 안 적혀 있다.
- 반열림과 11·12번의 만료 경계: **같은 질문의 날짜판**이다.\
  11번의 `Boundary`(만료 정각은 살았나)와 여기의 "종료일 당일은 계약 안인가"는 똑같이 **구간의 끝을 포함하나**를 묻는다. 차이는 11번이 그것을 enum 으로 남긴 반면, 여기서는 **반열림 하나로 고정**했다는 것이다.
- "예제는 대개 1년 계약이다"와 12번: **12번의 "빈 극장에서는 세 규칙이 전부 같다"** 와 같은 구조다.\
  둘 다 **개발·예제 조건에서 규칙 차이가 0으로 보인다** — 그 조건을 벗어난 자료(2년 계약, 매진에 가까운 부하)를 일부러 만들어야 갈린다.
