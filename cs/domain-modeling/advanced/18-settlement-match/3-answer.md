### A. 과제

#### 0. 한 줄 요구사항이 안 말해주는 것

- 안 말해주는 자리 셋(원본 클래스 주석 그대로):

```text
  무엇으로 짝을 찾나   참조값인가 금액과 날짜인가        → MatchKey
  어느 금액과 맞추나   총액인가 수수료를 뗀 금액인가      → AmountRule
  여러 건을 묶어       한 번에 보낸 것을 허용하나        → Grouping
```

> **대사(reconciliation)** — 두 장부를 줄 단위로 맞춰보고 차이를 찾는 일.\
> 예: 우리 장부의 "3/10 에 100,000원 팔았다" 한 줄과, 은행 입금 내역의 "3/10 에 97,000원 들어왔다" 한 줄을 짝지어 보는 것.

- "서로 간섭한다"는 뜻: **한 자리의 선택이 다른 자리의 위험을 키운다.**\
  금액으로 찾기(①)만 해도 위험한데, 거기에 묶기(③)를 열면 **합이 우연히 맞는 아무 조합이나** 짝이 된다.\
  거기에 총액(②)까지 고르면 아예 한 줄도 안 맞아서 대사가 통째로 죽는다(측정 넷).
- 완벽해 보이는 이유: 금액으로 찾으면 **금액은 언제나 맞는다.**\
  맞는 것을 골랐으니 `difference == 0` 이고, 모든 줄이 짝을 찾았으니 미대사도 0 이다.\
  대사표가 보는 두 지표가 둘 다 0 이 되므로 `looksClean() == true` 가 된다 — 그런데 짝은 전부 엉뚱할 수 있다.
- 세 enum 으로 올리면: **여덟 가지(2×2×2) 조합을 같은 코드로 돌려 오짝과 미대사를 각각 셀 수 있다.**\
  그래야 "이건 구석 사례야"가 아니라 "2,893 / 6,000 이야"라고 말할 수 있다.
- 하나라도 안 정하면 제일 먼저 망가지는 것: **수수료(②).**\
  안 정하면 모든 줄에 차이가 찍히고, 차이가 늘 있으면 **진짜 차이가 안 보인다**(README 함정 1번).

#### 1. 계약 — OurRecord / BankLine

- 우리 장부는 참조값이 필수, 입금 줄은 선택인 이유: **참조값을 만드는 쪽이 우리이기 때문이다.**\
  주문 번호는 우리가 찍어서 파트너에게 넘긴다 — 우리 쪽에 없을 수가 없다.\
  돌아오는 길(은행·파트너)에서는 흔히 빠지거나 바뀐다 — `BankLine.anonymous` 가 그 경우를 위한 생성자다.

> **참조값(reference)** — 두 장부를 잇는 열쇠. 여기서는 주문 번호다.\
> 예: 우리가 `o-1` 을 붙여 넘겼는데 입금 내역에는 참조값 칸이 비어 오거나 `o-2` 로 바뀌어 온다.

- 빈 문자열은 되고 `null` 은 안 되는 이유: **"값이 없다"와 "칸 자체가 없다"를 섞지 않기 위해서다.**\
  빈 문자열이면 `record.reference().equals(line.reference())` 가 조용히 false 가 되어 안전하게 흘러간다.\
  `null` 이면 그 비교에서 터지거나 더 나쁘게는 `null == null` 로 **엉뚱한 줄끼리 맞다고 나온다.**
- `gross` 와 `fee` 를 따로 갖는 이유: **`net` 만 있으면 AmountRule 이라는 선택지 자체가 사라진다.**\
  총액으로 맞춰볼 수도, 수수료 합을 검산할 수도, 수수료율이 바뀐 날을 찾을 수도 없다.

> **총액(gross) / 실수령(net)** — 우리가 판 금액 전체 / 수수료를 뗀 뒤 실제로 들어오는 금액. `net = gross - fee`.\
> 예: 100,000원을 팔고 수수료 3,000원을 떼면 파트너가 보내는 돈은 97,000원이다.

- `fee > gross` 를 생성자에서 막으면: `net()` 이 **절대 음수가 안 된다.**\
  그래서 `expected()` 도, `search` 의 `target - expected(...)` 도 음수 금액을 걱정 안 해도 된다.
- 경계: **바깥과 주고받는 자료의 모양은 계약(주어짐), 그 자료로 무엇을 할지가 과제(TODO).**\
  `search`(조합 탐색)도 주어졌다 — 이 챕터가 묻는 것은 알고리즘이 아니라 **선택**이기 때문이다.

> **상시 차이(constant noise)** — 늘 있어서 아무도 안 보게 된 경보.\
> 예: 모든 줄에 차이가 찍히는 대사표는 "차이 있음" 필터가 무의미해져서, 진짜 사고 한 줄을 못 건진다.

  즉 짝짓기용이 아니라 **검산용** 이다. (원본에 명시 없음 — 내 추론)

- 거르는 기준은 **날짜 창 하나**다. 금액은 안 본다 — 금액을 볼지 말지는 `pick` 의 `MatchKey` 가 정할 일이라서, 후보 만들기 단계에서 미리 자르면 참조값 방식이 망가진다.
- 정렬 키가 두 단계인 이유: **날짜만으로는 동점이 생긴다.**\
  같은 날 줄이 여럿이면 `sort` 가 안정 정렬이라 **입력 순서가 그대로 남는다** — 그게 곧 "입력 순서를 탄다"이다.\
  번호를 두 번째 키로 붙여야 동점이 완전히 사라진다.
- 번호를 안 붙이면: 같은 자료를 다른 순서로 넣었을 때 짝이 달라진다.\
  테스트가 그것을 못 박았다 — `List.of(r3, r1, r2)` 와 `List.of(r1, r2, r3)` 둘 다 후보 순서가 `["r2","r1","r3"]` 이어야 한다(r2 는 하루 전 날짜라 맨 앞).

> **결정성(determinism)** — 같은 입력이면 언제 몇 번을 돌려도 같은 답이 나오는 성질.\
> 예: 어제 대사와 오늘 대사가 같은 자료에서 다른 짝을 지으면, 차이가 3건 늘었는지 원래 3건이었는지 말할 수 없다.

- 매일 도는 일과의 연결: 대사의 값어치는 **어제와의 차이**에 있다.\
  답이 흔들리면 "미대사가 12줄 늘었다"가 사고 신호인지 정렬 운인지 구별이 안 된다 — 지표가 통째로 죽는다.
- `Math.abs` 를 쓰는 이유: **입금이 우리 장부보다 앞선 날 들어올 수 있다**(선입금).

> **선입금** — 우리 장부에 매출이 찍히기 전에 돈이 먼저 들어온 것.\
> 예: 장부는 3/10 인데 입금은 3/9 다. 날짜 차를 절대값으로 안 보면 이쪽만 조용히 막힌다.

- 창 0일이면: **같은 날짜의 우리 줄만** 후보다(`|차| <= 0`).
- 창 음수를 막는 이유: 음수면 `withinWindow` 가 **어떤 날짜에도 false** 라 후보가 언제나 비고, 대사가 "전부 미대사"로 조용히 성공한다.\
  터뜨려야 알아챈다 — `new Reconciler(-1)` 이 `IllegalArgumentException` 임을 테스트가 못 박았다.

#### 4. TODO 3 — pick

정답 코드:

```java
if (matchKey == MatchKey.BY_REFERENCE) {
    List<OurRecord> same = new ArrayList<>();
    for (OurRecord record : candidates) {
        if (record.reference().equals(line.reference())) {
            same.add(record);
            if (grouping == Grouping.ONE_TO_ONE) {
                break;
            }
        }
    }
    return List.copyOf(same);
}

int limit = grouping == Grouping.ONE_TO_ONE ? 1 : MAX_GROUP;
for (int size = 1; size <= limit; size++) {
    List<OurRecord> found = search(candidates, line.amount(), amountRule, size, 0);
    if (found != null) {
        return List.copyOf(found);
    }
}
return List.of();
```

- 갈라지는 방식: 참조값 방식은 **문자열 비교 한 번으로 훑고 끝**, 금액 방식은 **조합 탐색(`search`)** 으로 들어간다.\
  참조값 방식은 금액을 아예 안 본다 — 그래서 금액이 달라도 짝을 짓고 차이만 남긴다.
- ONE_TO_ONE 에서 `break`: **"한 줄에 한 건"이 규칙**이므로 첫 줄을 찾으면 더 볼 이유가 없다.\
  후보가 날짜·번호 순으로 서 있으니 "첫 줄"이 매번 같은 줄이다(결정성).
- 참조값 + ALLOW_MANY_TO_ONE 은 **`MAX_GROUP`(3) 제한을 안 받는다.**\
  `break` 가 없으니 같은 참조값을 가진 후보를 **전부** 담는다 — 같은 참조값 5줄이면 5줄이 다 붙는다.\
  묶음 한도는 금액 탐색(`limit`)에만 걸려 있다. 근거가 같은 참조값이므로 무한정 묶어도 오짝이 안 생긴다는 판단으로 보인다. (원본에 명시 없음 — 내 추론)
- 크기 1 → 2 → 3 순으로 훑는 이유: **작은 설명이 큰 설명보다 그럴듯하다는 가정**이다.\
  한 건으로 설명되면 굳이 두 건 조합을 찾지 않는다.
- "첫 조합이지 제일 그럴듯한 조합이 아니다" 손계산 (ReconcilerTest 의 실제 값):

```text
 우리 장부  r1 (o-1) 10,000   r2 (o-2) 20,000   r3 (o-3) 30,000   수수료 0
 입금       b1 참조값 o-1, 금액 30,000

 30,000 을 만드는 방법
   크기 1:  r3            = 30,000   ← 먼저 걸린다
   크기 2:  r1 + r2 = 10,000+20,000 = 30,000   ← 이게 진짜 짝일 수도

 결과   ours = [r3],  difference = 0,  referenceAgrees = false
        차이 0 으로 붙었는데 참조값은 o-1, r3 은 o-3 — 다른 주문의 돈이다
        wrongPairs() = 1
```

- 참조값 빈 입금 줄이 저절로 못 찾는 이유: **우리 장부 쪽 참조값은 빌 수 없다**(`OurRecord` 생성자가 막는다).\
  그래서 `"".equals(record.reference())` 가 어떤 줄에서도 참이 될 수 없다 — 따로 막는 코드가 필요 없다.\
  impl 은 이 자리를 **주석 한 줄**로만 남겼다(죽은 방어선 제거, §15 참고).
- `null` 이 아니라 빈 목록을 주는 이유: **부르는 쪽이 `isEmpty()` 하나로 판단하게 하려고.**\
  `reconcile` 이 `picked.isEmpty()` 로 미대사를 가르므로 `null` 이면 그 자리에서 터진다.\
  (안쪽 `search` 는 반대로 `null` 을 쓴다 — 거기서는 "빈 목록"이 다른 뜻이기 때문이다. §5 참고.)

#### 5. search — 주어진 조합 탐색

- `size == 0` 에서 빈 목록과 `null` 을 구별하는 이유: **빈 목록은 "크기 0 짜리 조합을 찾았다"는 성공 신호**다.\
  즉 남은 목표 금액이 0 이라 더 고를 것이 없다는 뜻 — 재귀의 바닥에서 "여기까지 합이 딱 맞았다"를 알린다.\
  `null` 은 "못 찾았다"는 실패 신호다.

> **센티널(sentinel)** — "없음"이나 "실패"를 나타내려고 따로 정해 둔 특별한 값.\
> 예: 여기서는 `null` 이 실패, 빈 목록이 성공(더 고를 것 없음)이다. 둘을 같은 값으로 쓰면 구별이 사라진다.

- 안 구별하면: 합이 안 맞는데도 빈 조합을 "찾았다"로 돌려주어 **`ours` 가 빈 Match** 가 만들어진다.\
  그러면 `sum = 0` 이라 `difference = -line.amount()` — 아무 줄도 안 붙은 짝이 차이만 잔뜩 안고 생긴다.
- 반복 조건 `i <= candidates.size() - size` 인 이유: **뒤에 최소 `size` 개가 남아 있어야** 크기 `size` 조합을 만들 수 있다.\
  예: 후보 5개에서 크기 3을 고르면 시작 위치는 최대 2번(0,1,2)까지다(5-3=2).
- `i + 1` 을 넘기면: **같은 줄을 두 번 안 고른다**, 그리고 고른 줄들이 **후보 순서대로**만 나온다(중복 조합이 안 생긴다).
- `tail.add(0, record)` 로 앞에 꽂는 이유: 재귀가 뒤에서부터 돌아오므로, 앞에 꽂아야 **후보 순서대로** 정렬된 목록이 된다.

> **백트래킹(backtracking)** — 후보를 하나 골라보고, 나머지로 답이 안 되면 되돌아와 다음 후보를 고르는 탐색.\
> 예: r1 을 넣어보고 남은 20,000 을 못 만들면 r1 을 빼고 r2 부터 다시 시도한다.

- 조합 수: 후보 n개, 묶음 최대 3이면

```text
 크기 1   n
 크기 2   n(n-1)/2
 크기 3   n(n-1)(n-2)/6
 합계 ≈ n^3 / 6

 n = 60 이면  60 + 1,770 + 34,220 = 36,050 가지
 (최악의 경우. 합이 맞는 첫 조합에서 멈추므로 보통은 훨씬 적다)
```

- `private` 이고 "주어진 코드"인 이유: **계약 표면이 아니다.**\
  밖에서 부르지 않으니 나중에 탐색 방식을 갈아엎어도 안 깨진다.\
  그리고 이 챕터가 묻는 것은 탐색 알고리즘이 아니라 **"금액으로 찾겠다는 선택이 무엇을 부르는가"** 라서 미리 줬다.

> **계약 표면(public API)** — 바깥 코드가 직접 부를 수 있는 것들의 집합.\
> 예: `reconcile` 은 public 이라 결과 모양을 함부로 못 바꾸지만, private 인 `search` 는 언제든 갈아엎어도 된다.

- `looksClean` 이라는 이름: **"깨끗하다"가 아니라 "깨끗해 보인다"** 는 뜻이다.\
  이 함수가 보는 것은 남은 줄 수와 금액 차이뿐이고, **짝이 제 짝인지는 안 본다.**\
  이름이 `isClean` 이면 부르는 쪽이 "검증됐다"로 읽는다 — 이름 하나로 그 오독을 막았다.

> **대리 지표(proxy metric)** — 진짜 알고 싶은 것을 직접 못 재서 대신 재는 숫자.\
> 예: 알고 싶은 것은 "짝이 맞나"인데 재는 것은 "남은 줄이 없나"다. 둘이 어긋나면 지표가 사람을 속인다.

- `gap()` 이 잃는 정보: **방향**이다.\
  +5,000(독촉)과 -5,000(반환)이 절대값에서는 같은 크기로 보이지만 해야 할 일이 정반대다.\
  그리고 **합으로 뭉개면 서로를 지운다** — 한 줄이 5,000 덜 들어오고 다른 줄이 5,000 더 들어오면 단순 합은 0 이 된다.
- `looksClean() == true` 인데 전부 틀린 짝일 수 있는가: **있다.**\
  테스트가 그것만 따로 못 박았다 — 같은 날 같은 금액 두 건에 참조값이 바뀌어 들어온 자료에서 `looksClean()` 이 true 이고 `wrongPairs()` 가 2 다.
- `wrongPairs()` vs `trulyWrong()`:

```text
 wrongPairs()   참조값이 안 맞는 짝의 수      ← 운영에서 볼 수 있는 값
 trulyWrong()   자료를 만들 때의 진실과      ← 측정 테스트에서만 볼 수 있는 값
                다른 짝의 수
```

- 진실과 견주는 이유: **참조값으로 세면 참조값 없는 줄이 전부 오짝으로 잡혀 숫자가 부풀려진다.**\
  참조값이 빈 입금 줄은 `referenceAgrees` 가 저절로 false 라서, 제 짝을 정확히 찾았어도 `wrongPairs()` 에 들어간다.\
  그래서 측정 테스트는 자료를 만들 때 `truth` 맵(입금 줄 번호 → 실제로 묶인 우리 줄 번호들)을 같이 만들어 둔다.

#### 8. 측정 하나 — 완벽한 자료에서도 절반이 엉뚱하게 붙는다

- 하루 60건·100일, 무참조 0%·묶음 0%·지연 0%, 금액+실수령+한 건씩:

```text
 미대사        0 / 0
 차이(gap)     0
 깨끗해 보인 날   100 / 100
 짝             6,000
 실제로 엉뚱하게 붙은 짝   2,893 / 6,000     ← 48 %
```

- 엉뚱하게 붙은 짝: **2,893 / 6,000.**
- 완벽한 자료인데 왜 갈리나 — 금액 가짓수와 하루 건수를 견주면 답이 나온다:

```text
 자료 만드는 규칙 (MeasurementTest.day)
   gross = 1,000 × (10 + 0..39)      →  10,000 ~ 49,000   가짓수 40
   fee   = gross × 3 / 100
   net   = gross - fee               →  가짓수도 40

 하루 60 건을 40 개 칸에 넣는다
   ┌────────────────────────────────────────┐
   │ 60 개 구슬  →  40 개 상자               │
   │ 최소 20 개는 반드시 남과 같은 상자에 들어간다 │
   └────────────────────────────────────────┘

 같은 상자(같은 금액)에 둘 이상이면 어느 것을 골라도 숫자는 맞는다
 → 금액 매칭은 "맞는 답"이 아니라 "맞아 보이는 답"을 고른다
```

> **비둘기집 원리(pigeonhole principle)** — 물건이 상자보다 많으면 한 상자에 둘 이상이 반드시 들어간다.\
> 예: 60건의 매출을 40가지 금액으로 만들면 같은 금액짜리가 최소 20건은 겹친다.

- "대사가 통과했다"가 보장하는 것: **총액이 맞는다.**\
  보장하지 않는 것: **각 줄이 제 짝을 찾았다.** 이 챕터의 제목 문장이 그것이다.

#### 9. 측정 둘 — 금액 매칭은 참조값을 아예 안 본다

- 묶음 20%·지연 20%·창 1일, 금액+실수령+묶기:

```text
 무참조   0 %   오짝 2,675 / 짝 4,171
 무참조   5 %   오짝 2,675 / 짝 4,171
 무참조  20 %   오짝 2,675 / 짝 4,171
 무참조  50 %   오짝 2,675 / 짝 4,171
 무참조 100 %   오짝 2,675 / 짝 4,171
                  ↑ 다섯 값이 완전히 같다
```

- 무엇을 증명하나: **그 규칙의 코드 경로에 `reference` 가 한 번도 안 나온다는 것.**\
  입력의 한 칸을 0%에서 100%까지 바꿨는데 출력이 한 자리도 안 변하면, 그 칸은 계산에 안 쓰인 것이다.\
  추측이 아니라 **실험으로 증명한 무관계**다.
- 참조값을 받아내면 품질이 오르나: **안 오른다.**\
  `pick` 의 금액 분기는 `line.amount()` 만 본다 — 참조값이 다 붙어 있어도 안 읽는다.
- 조직에 주는 함의: **"파트너에게 참조값을 받아내자"는 개선안이 이 대사에서는 0원짜리다.**\
  자료 품질을 올리기 전에 **그 자료를 쓰는 규칙으로 바꾸는 것**이 먼저다.\
  반대로 규칙을 참조값 방식으로 바꾸면, 그때부터 자료 품질 개선이 그대로 효과로 돌아온다(측정 셋의 901 → 더 줄어드는 방향).

#### 10. 측정 셋 — 참조값 매칭은 오짝이 0이다

- 묶음 20%·지연 20%·창 1일, 참조값+실수령+묶기:

| 무참조 비율 | 오짝 | 미대사 입금 |
|---|---|---|
| 0 % | **0** | 901 |
| 5 % | **0** | 1,109 |
| 20 % | **0** | 1,644 |
| 50 % | **0** | 2,800 |

- 참조값이 다 붙어 있는데도 901줄이 남는 이유: **묶어 보낸 줄에는 참조값이 안 붙기 때문이다.**\
  자료 생성기가 `size > 1` 이면 무조건 `anonymous = true` 로 만든다 — 여러 주문을 합쳐 보내면 어느 주문 번호를 적어야 할지 정할 수 없어서다.\
  즉 무참조 0% 는 "한 건짜리 줄에는 참조값이 다 있다"는 뜻이지 "모든 입금 줄에 있다"가 아니다.
- 두 규칙의 실패 성격:

```text
 참조값으로   틀린 답을 안 낸다.  답을 못 내는 줄이 남는다
 금액으로     늘 답을 낸다.      그 답의 절반이 틀렸다
```

> **미대사(unmatched)** — 짝을 못 찾고 남은 줄. 대사표에 그대로 남는다.\
> 예: 참조값 없는 입금 줄 901개가 "확인 필요" 목록에 올라오고, 사람이 하나씩 본다.

> **오짝(wrong pair)** — 짝은 지어졌는데 엉뚱한 것끼리 붙은 것. 대사표에 안 남는다.\
> 예: 2,893건이 잘못 붙었는데 미대사 0·차이 0 이라 아무도 볼 이유가 없다.

- 규칙 선택 기준: **실패가 보이는 쪽을 고른다.**\
  남은 줄은 비용(사람 시간)이지만 **알 수 있는 비용**이다.\
  틀린 짝은 비용이 언제 얼마로 터질지 모르는 **숨은 부채**다.

#### 11. 측정 넷 — 총액으로 맞추면 두 규칙이 각각 다르게 망가진다

- 무참조 0%·묶음 0%·지연 0%, 총액 기준:

| | 결과 |
|---|---|
| 참조값 + 총액 | 짝은 **다 짓고**(미대사 0) 차이 **5,282,190** 이 남는다 |
| 금액 + 총액 | **6,000줄 전부 미대사.** 짝 **0**. 한 줄도 못 찾는다 |

- 한 줄도 못 찾는 이유를 숫자로:

```text
 gross = 1,000 k        (k = 10 ~ 49)
 fee   = 1,000 k × 3 / 100 = 30 k
 net   = 1,000 k - 30 k    = 970 k       ← 입금 줄에 찍히는 금액

 총액 기준이면 우리가 기대하는 값은 gross = 1,000 j

 970 k = 1,000 j  가 되려면   97 k = 100 j
 97 과 100 은 서로소  →  k 가 100 의 배수여야 한다
 그런데 k 는 10 ~ 49 다  →  절대 안 맞는다

 예: k=10  net 9,700  ↔ gross 는 10,000/11,000/... 어느 것과도 다르다
     k=20  net 19,400 ↔ 마찬가지
 → 크기 1 조합이 하나도 없다 → 미대사 6,000
```

- 두 고장의 모양은 다른데 원인은 하나: **`expected()` 가 돌려주는 값이 입금 금액과 체계가 다르다.**\
  참조값 방식은 금액을 **짝짓기에 안 쓰므로** 짝은 지어지고 차이만 남고,\
  금액 방식은 금액이 **짝짓기의 유일한 근거이므로** 통째로 죽는다.
- 5,282,190 검산:

```text
 5,282,190 ÷ 6,000 줄 = 880.365 원   ← 줄당 평균 수수료
 평균 수수료가 총액의 3 % 이므로  평균 총액 ≈ 880.365 ÷ 0.03 ≈ 29,345 원
 자료는 10,000 ~ 49,000 균등이므로 이론 평균은 29,500 원
 → 29,345 ≈ 29,500,  "차이 = 수수료 합" 이 맞는다
```

#### 13. 측정 여섯 — 묶기

- 금액+실수령, 무참조 20%·묶음 20%·지연 0%·창 1일:

 한 건씩       2,180         847      1,899
 묶어서          524         522      2,670

 우리 줄 미대사  2,180 → 524    약 4 분의 1 로 줄었다

 오짝           1,899 → 2,670   771 늘었다 = 약 40 % 증가

- 묶기가 **필요한** 예 (ReconcilerTest 실제 값):

```text

             50,000(수수료 1,500) → net 48,500
             25,000(수수료   750) → net 24,250

```

- 묶기가 **위험한** 예: §4 의 30,000원 예 — r3 하나로도, r1+r2 로도 30,000 이 되어 **참조값과 다른 쪽이 걸린다.**
- 참조값 방식에서 묶기가 필요한 이유: **부분 정산**이다.

> **부분 정산** — 한 주문의 돈이 여러 번에 나눠 들어오거나, 우리 장부에 같은 참조값 줄이 여럿인 것.\
> 예: `o-1` 짜리 50,000원 줄이 둘인데 입금은 `o-1` 100,000원 한 줄이다.

```text
 한 건씩   첫 줄만 붙는다   차이 50,000,  미대사 우리 1
 묶어서    둘 다 붙는다     차이      0,  referenceAgrees = true
```

  참조값이 같으므로 몇 개를 묶어도 오짝이 안 생긴다 — **묶기의 위험은 묶기 자체가 아니라 "금액으로 찾으면서 묶는 것"** 에 있다.

#### 14. 함정 (원본 README)

- 넷: ① **수수료를 안 정하고 시작하는 것** ② **"미대사 0"을 "다 맞았다"로 읽는 것** ③ **짝지은 줄을 남은 것에서 안 빼는 것** ④ **후보를 안 세우는 것**.
- ①이 첫 번째인 이유: **차이가 늘 있으면 진짜 차이가 안 보인다.**\
  나머지 셋은 특정 상황에서 터지지만, 이것은 **모든 줄에 매일** 영향을 준다.
- ②가 놓치는 것: 짝이 지어졌다는 사실과 금액이 맞다는 사실은 **별개**다.\
  참조값 같고 92,000만 들어온 테스트에서 미대사는 0인데 `gap()` 은 5,000 이다.
- ③의 결과: **같은 매출이 두 번 정산된다.** 회계상 매출이 부풀고, 파트너에게 이중 청구가 나간다.
- ④가 함정인 이유: **대사의 값어치가 "어제와의 비교"에 있기 때문이다.**\
  답이 매번 흔들리면 차이가 늘었는지 줄었는지 자체를 말할 수 없어, 지표로서 쓸모가 사라진다.

#### 15. 변종 검증에서 고친 것

- 약한 테스트 둘:
  - **날짜 창을 절대값으로 안 봐도 통과했다.** 자료를 늘 한 방향(입금이 장부보다 늦게)으로만 만들어서 **선입금을 한 번도 안 밟았다.**
  - **차이의 부호를 뒤집어도 통과했다.** `gap()` 이 절대값이라 부호가 안 보였다.
- 한 방향 자료의 문제: **코드의 절반이 한 번도 안 실행된다.**\
  `Math.abs` 를 빼도 테스트가 다 통과하므로 "테스트가 지키고 있다"는 착각만 남는다.\
  고친 방법: 창 1일에 **닷새 앞선 입금**(못 찾아야 한다)과 **하루 앞선 입금**(찾아야 한다)을 같이 넣었다.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 결과만 틀린 것.\
> 예: 선입금이 전부 미대사로 남아도 "미대사가 좀 있네" 로만 보이지, 코드가 한쪽 방향만 본다는 사실은 안 드러난다.

- 부호 테스트 고침: **덜 들어온 줄(+5,000)과 더 들어온 줄(-3,000)을 한 테스트에 같이 넣었다.**\
  그러면 `difference` 를 개별로 확인하게 되어 부호가 계약이 된다 — assert 가 `+5,000`, `-3,000`, `gap 8,000` 셋이다.
- 죽은 방어선 셋:
  - 참조 없는 입금 줄을 따로 막는 코드 → **`OurRecord` 가 빈 참조값을 막으므로 저절로 못 찾는다.**
  - `referenceAgrees` 를 따로 false 로 만드는 코드 → **저절로 false 가 된다**(빈 문자열은 어떤 참조값과도 안 같다).
  - `unmatchedOurs` 를 다시 정렬하는 코드 → **풀을 복사한 뒤 빼기만 하므로 원래 순서다.**

> **죽은 방어선(dead defense)** — 이미 다른 곳에서 보장되는 것을 또 지키는 코드.\
> 예: 생성자가 빈 참조값을 막는데 사용하는 쪽에서 또 `if (reference.isBlank())` 를 쓰는 것.

- 지우고 주석으로 바꾼 근거: **그 코드는 절대 안 타는 분기**라 테스트가 못 덮는다.\
  안 타는 코드는 읽는 사람에게 "여기 위험이 있다"는 틀린 신호를 준다 — 대신 **왜 안 타는지**를 한 줄로 남기는 것이 정보량이 크다.\
  impl 에 실제로 남은 주석: `// 참조값이 빈 입금 줄은 저절로 아무것도 못 찾는다.` / `// pool 은 처음에 ours 를 그대로 복사한 뒤 빼기만 한다. 그래서 원래 순서다.`

#### 17. 연결

- 세는 것의 같고 다름: 앞 챕터들(예: 01-parking-fee)은 **"같은 자료에서 두 해석의 답이 갈리는 건수"** 를 셌다.\
  여기서도 세 갈래의 갈림을 세지만, 다른 점은 **정답이 존재한다**는 것이다 — 자료를 만들 때의 `truth` 가 있다.\
  그래서 "갈린다"가 아니라 **"틀렸다"** 를 셀 수 있고, 그 결과가 2,893 / 6,000 이다.
- "보이는 실패 / 안 보이는 실패" 구도: 01-parking-fee 의 **뒤집힌 시각을 거부하느냐 0원으로 뭉개느냐**와 같은 자리다.\
  거부하면 시끄럽고 알 수 있다, 뭉개면 조용하고 모른다 — 이 챕터는 그 구도를 **지표 수준**으로 확대한 것이다.
- 알고리즘 트랙과 닿는 곳: `candidates`(정렬) + `pick`(앞에서부터 합 맞는 첫 조합) + `pool.removeAll` 은 **그리디 매칭**이다.\
  최적 짝짓기를 원하면 이분 매칭(비용 최소 매칭)으로 가야 하는데, 이 챕터는 일부러 안 간다 — **최적화해도 근거가 금액인 한 오짝은 안 줄기 때문이다.**

> **그리디 매칭(greedy matching)** — 앞에서부터 그때그때 맞는 것을 짝지어 버리고 되돌아보지 않는 방식.\
> 예: b1 이 r1 을 가져가면 b2 는 r1 을 못 쓴다. 나중에 b2 에게 r1 이 더 맞았어도 되돌리지 않는다.

- 실무 관행과 같은 함정: `looksClean()` 은 **초록불 대시보드**와 같다.\
  테스트가 다 통과했다고 계약이 검증된 것이 아니듯, 미대사 0 이라고 짝이 맞는 것이 아니다.\
  둘 다 **"재고 있는 것"과 "알고 싶은 것"이 다르다**는 같은 문제다.
