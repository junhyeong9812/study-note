### A. 과제

#### 0. 시작 문장이 안 말해주는 것

- 정액은 순서를 안 타고 정률은 타는 이유: **정률이 "지금 남은 금액"을 읽기 때문이다.**

```text
 10,000 원에 10 % 와 1,000 원

 퍼센트 먼저   10,000 → (10 % = 1,000 깎음) → 9,000 → (1,000 깎음) → 8,000
 정액 먼저     10,000 → (1,000 깎음)        → 9,000 → (9,000 의 10 % = 900) → 8,100
                                                                         100 원 차이
```

> **상태를 읽는 연산** — 앞에서 무슨 일이 있었는지에 따라 결과가 달라지는 계산.\
> 예: "1,000원 깎기"는 언제 해도 1,000원이지만, "10% 깎기"는 남은 금액이 얼마냐에 따라 1,000원도 되고 900원도 된다.

- 안 말해주는 자리 넷:

```text
 안 말해준 것                      가능한 읽기
 "여러 장을 같이 쓴다"    →  어떤 순서로? (정률 먼저 / 정액 먼저 / 우선순위 순)
 "다른 것과 중복 불가"    →  배타를 쓰나 나머지 묶음을 쓰나 (3택)
 "제일 많이 깎이는 것"    →  할인 금액 기준인가 낼 돈 기준인가
 "8,000 원 이상 사용 가능" →  할인 전 금액인가 할인 후 금액인가
```

- 정률 두 장: **순서가 답을 바꾼다.** 10% → 5% 와 5% → 10% 는 결과가 같지만(곱셈은 교환법칙), 상한(`maxDiscount`)이나 잔액 한계가 끼면 갈린다. 측정에서 정률 2개 이상인 시행의 33%가 갈렸다.
- 고객에게 유리한 순서: **정률 먼저(PERCENT_FIRST).** 큰 금액에 %를 걸면 더 많이 깎인다.
- 고객이 알 수 있는가: **없다.** 장바구니에는 최종 금액만 뜬다. 그래서 이 선택은 사실상 조용한 가격 정책이다.
- "배타"에서 나오는 규칙: **셋**(더 깎이는 쪽 / 무조건 배타 / 우선순위 1등).
- enum으로 올리면: **세 해석을 같은 코드로 돌려 매출 차이를 재볼 수 있다.** 측정 결과 배타 규칙 하나로 매출이 4.98% 갈렸다.

#### 1. TODO 1 — ordered

정답 코드 (impl/PromotionEngine.java):

```java
List<Promotion> sorted = new ArrayList<>(promotions);
Comparator<Promotion> byId = Comparator.comparing(Promotion::id);
sorted.sort(switch (order) {
    case PERCENT_FIRST -> Comparator
            .comparingInt((Promotion p) -> p.kind() == Kind.PERCENT ? 0 : 1)
            .thenComparingInt(Promotion::priority).thenComparing(byId);
    case FIXED_FIRST -> Comparator
            .comparingInt((Promotion p) -> p.kind() == Kind.FIXED ? 0 : 1)
            .thenComparingInt(Promotion::priority).thenComparing(byId);
    case BY_PRIORITY -> Comparator
            .comparingInt(Promotion::priority).thenComparing(byId);
});
```

- `PERCENT_FIRST` 의 1차 키: **"정률인가 아닌가"를 0/1로 바꾼 값.** 0이 앞이라 정률이 먼저 온다.
- 무료배송은 `PERCENT_FIRST` 에서 **1그룹(뒤쪽)** 으로 간다 — 정률이 아니기 때문이다.\
  무료배송은 주문 금액을 안 건드리므로 어디에 있든 결과가 같다.
- 2차 키는 `priority`(작을수록 먼저), 3차 키는 `id`(문자열 순).
- 식별자 뒷기준이 없으면: **목록 순서, 즉 DB 조회 순서가 답을 정한다.**\
  `ORDER BY` 없는 쿼리의 결과 순서는 보장되지 않으므로, 같은 주문을 두 번 계산하면 금액이 다를 수 있다.

> **안정된 순서(total order)** — 어떤 둘을 집어도 앞뒤가 반드시 정해지는 정렬 기준.\
> 예: 우선순위가 똑같이 1인 쿠폰 둘은 "id 순"이라는 뒷기준이 있어야 앞뒤가 정해진다.

- 테스트의 강제 방법: 같은 프로모션 목록을 **20번 셔플해서** 전부 같은 `Result` 가 나오는지 본다(`inputOrderIndependent`).
- 우선순위는 **작을수록 먼저**다(`comparingInt` 오름차순).
- 그 숫자를 넣는 사람: **대개 운영자**다. 테스트 주석 그대로 — "숫자 하나로 100원이 움직인다. 그 숫자는 대개 운영자가 넣는다."\
  코드 리뷰를 안 거치는 값이 금액을 바꾼다는 뜻이다.

#### 2. TODO 2 — discountOf

정답 코드:

```java
long raw = switch (promotion.kind()) {
    case FIXED -> promotion.amount();
    case PERCENT -> remaining * promotion.amount() / 100;
    case FREE_SHIPPING -> 0;
};
if (promotion.maxDiscount() > 0) {
    raw = Math.min(raw, promotion.maxDiscount());
}
return Math.min(raw, remaining);
```

- 세 종류의 raw: 정액은 **적힌 금액 그대로**, 정률은 **남은 금액 × % / 100**, 무료배송은 **0**.
- 무료배송이 0인데 배송비는 누가 0으로 만드나: **`applyAll` 이 따로 처리한다.**\
  무료배송은 주문 금액이 아니라 배송비라는 **다른 주머니**를 건드리기 때문에, 할인액 계산 함수 안에 들어가지 않는다.
- 상한과 잔액 중 어느 걸 먼저 자르나: **순서가 결과를 안 바꾼다.** 둘 다 `min` 이고, `min(min(a,b),c) = min(a,b,c)` 이기 때문이다.
- `maxDiscount == 0` = **상한 없음**(`> 0` 일 때만 min 을 건다).
- 그 약속의 위험: **"상한 0원"(= 한 푼도 못 깎음)과 구분이 안 된다.**\
  방어는 **테스트에 약속을 못 박아 두는 것**이다(`maxDiscount` 테스트가 "0 은 상한 없음"을 검증한다). 더 나은 방법은 `Optional<Long>` 이나 `-1` 같은 별도 표식인데, 여기서는 단순함을 택하고 테스트로 덮었다.

> **센티넬 값(sentinel value)** — "값 없음"을 특별한 숫자 하나로 대신 표현하는 것.\
> 예: 상한 없음을 0으로 적는 것. 언젠가 진짜 0이 필요해지는 순간 무너진다.

- 남은 금액보다 많이 깎으면:

```text
 10,000 원 주문에 20,000 원 할인
   막지 않으면  finalAmount = -10,000   →  음수 금액이 배송비까지 먹는다
   막으면       finalAmount = 0, 배송비 3,000 은 그대로 낸다 (payable 3,000)
```

- 정률 나눗셈은 **0 쪽으로 잘린다**(remaining 이 양수라 사실상 버림).\
  `9,999 × 10 / 100 = 999.9 → 999` — 고객이 0.9원 손해다. 항상 같은 방향으로 기울어 있으므로 대량이면 누적된다.

#### 3. TODO 3 — applyAll

정답 코드:

```java
long remaining = orderAmount;
long shipping = shippingFee;
List<String> applied = new ArrayList<>();

for (Promotion promotion : ordered(promotions, order)) {
    if (promotion.kind() == Kind.FREE_SHIPPING) {
        if (shipping == 0) { continue; }
        shipping = 0;
        applied.add(promotion.id());
        continue;
    }
    long discount = discountOf(promotion, remaining);
    if (discount == 0) { continue; }
    remaining -= discount;
    applied.add(promotion.id());
}
return new Result(remaining, shipping, orderAmount - remaining, applied);
```

- 0원이면 안 넣는 이유: **`appliedIds` 는 "쿠폰을 썼다"는 기록**이고, 1회용 쿠폰은 그 기록으로 소진된다.
- 그 줄이 없으면:

```text
 20,000 원 할인(잔액 0) → 1,000 원 할인 → 10 % 할인

 없을 때  appliedIds = [big, small, pct]   금액 0 원 (맞음)
                                            small 과 pct 쿠폰이 0 원을 받고 사라진다
 있을 때  appliedIds = [big]                금액 0 원 (같음)
```

  **금액은 두 쪽 다 맞는다.** 틀리는 것은 쿠폰 사용 기록뿐이라 예외도 안 나고 검산도 통과한다.

> **조용한 실패(silent failure)** — 예외도 금액 오류도 없이 결과만 틀리는 실패.\
> 예: 합계는 정확한데 고객의 1회용 쿠폰 두 장이 0원을 받고 소진된다. 고객센터 문의가 들어와야 안다.

- 배송비가 이미 0인데 무료배송: **`continue` 로 건너뛰고 적용 목록에 안 넣는다.** 같은 이유다 — 아무것도 안 바꿨으면 안 쓴 것이다.
- `finalAmount` 와 `shippingPaid` 를 따로 두는 이유: **둘이 다른 주머니**이기 때문이다.\
  무료배송은 주문 금액을 하나도 안 깎지만 고객이 내는 돈은 3,000원 줄인다 — 한 숫자로 합쳐두면 이 사실이 사라진다.
- `discount` 는 **배송비 절약분을 포함하지 않는다**(`orderAmount - remaining` 이다).\
  테스트가 무료배송 단독 적용에서 `discount() == 0` 이고 `shippingPaid() == 0` 임을 못 박았다.
- `payable()` = `finalAmount + shippingPaid` — **고객이 실제로 내는 돈.**

> **비교 단위(unit of comparison)** — "무엇이 더 좋은가"를 잴 때 쓰는 자.\
> 예: 같은 프로모션 둘을 "할인 금액"으로 재면 무료배송이 0원이라 지고, "고객이 낼 돈"으로 재면 이긴다. 자를 바꾸면 승자가 바뀐다.

정답 코드 (핵심만):

```java
if (orderAmount < 0 || shippingFee < 0) { throw new IllegalArgumentException("금액이 음수다"); }
List<Promotion> usable = eligible(orderAmount, promotions);   // 할인 전 금액으로 자격 판정

// 배타 / 비배타로 나눈다
if (exclusives.isEmpty()) { return applyAll(orderAmount, shippingFee, shared, order); }

candidates.sort(Comparator.comparingInt(Promotion::priority).thenComparing(Promotion::id));
return switch (exclusiveRule) {
    case EXCLUSIVE_WINS -> applyAll(..., List.of(candidates.get(0)), order);
    case HIGHEST_PRIORITY_WINS -> { /* 배타 1등과 비배타들의 순위를 견줘 이긴 쪽 */ }
    case BEST_DISCOUNT_WINS -> { /* 비배타 묶음과 배타 하나짜리들을 payable() 로 견줌 */ }
};
```

- 자격은 **할인 전 금액**(`orderAmount`)으로 판정한다.
- 할인 후로 보면 무너지는 것: **적용 순서가 금액뿐 아니라 자격까지 바꾼다.**

```text
 10,000 원 주문 + 5,000 원 할인(a) + "8,000 원 이상" 1,000 원 쿠폰(b)

 할인 전 기준  10,000 ≥ 8,000 → b 도 자격 있음 → 둘 다 적용 → 4,000 원
 할인 후 기준  a 를 먼저 쓰면 잔액 5,000 < 8,000 → b 자격 상실 → 5,000 원
               b 를 먼저 쓰면 둘 다 적용 → 4,000 원
                                          같은 쿠폰인데 순서만으로 자격이 생겼다 없어졌다 한다
```

- 설명 가능한가: **못 한다.** "왜 이 쿠폰이 안 되나요"의 답이 "다른 쿠폰을 먼저 써서"가 되고, 그 순서는 고객이 못 본다.
- 배타가 없으면: **비배타 전부를 순서대로 적용하고 끝.**
- 배타가 둘 이상이면: **배타끼리도 같이 못 쓰므로 하나만 고른다.**
- `EXCLUSIVE_WINS` 가 고르는 것: **우선순위 정렬 후 첫째**(`candidates.get(0)`) — 순위가 같으면 id 순.
- `HIGHEST_PRIORITY_WINS` 가 견주는 것: **배타 중 1등의 순위 vs 비배타들의 순위.**\
  비배타 쪽에 더 높은 순위(작은 숫자)가 있으면 **비배타 묶음 전체**를 쓴다.
- `BEST_DISCOUNT_WINS` 의 기준: **`payable()` — 고객이 낼 돈이 가장 적은 쪽.**
- 할인 금액으로 견주면:

```text
 배타 무료배송(할인 0 원, 배송비 3,000 절약)  vs  비배타 1,000 원 할인

 할인 금액 기준   0 < 1,000        →  비배타 승   ← 무료배송은 언제나 진다
 낼 돈 기준      10,000 < 12,000  →  배타 승     ← 올바름
```

- 배타가 다섯이면: **다섯 번 + 비배타 묶음 한 번 = 여섯 번** 계산한다(배타 하나짜리 묶음을 각각 돌려본다).\
  선형이라 아직 괜찮지만, "배타 둘을 같이 쓸 수 있게 해달라"가 들어오면 **조합의 수가 폭발한다.**

#### 5. 손계산

주문 10,000원 · 배송비 3,000원 · 배타 500원(순위1) + 비배타 1,000원(순위2) + 1,500원(순위3), BY_PRIORITY:

```text
 비배타 묶음  10,000 − 1,000 − 1,500 = 7,500   payable 10,500
 배타 하나    10,000 −   500         = 9,500   payable 12,500

 BEST_DISCOUNT_WINS     7,500   (10,500 < 12,500 이라 비배타 묶음)
 EXCLUSIVE_WINS         9,500   (배타가 있으면 무조건 배타)
 HIGHEST_PRIORITY_WINS  9,500   (배타의 순위 1 이 비배타의 2·3 보다 높다)
                        ^^^^^ 2,000 원 차이
```

- 배타 순위만 9로 바꾸면:

```text
 BEST_DISCOUNT_WINS     7,500   (그대로 — 금액만 보므로)
 EXCLUSIVE_WINS         9,500   (그대로 — 배타라는 사실만 보므로)
 HIGHEST_PRIORITY_WINS  7,500   ← 뒤집힌다. 비배타 a 의 순위 2 가 9 보다 높다
```

  (테스트는 배타 500원 순위9 + 비배타 1,000원 순위2 두 장 판으로 9,000 / 9,500 / 9,000 을 못 박았다. 위 세 장짜리는 같은 구조를 내가 손계산한 값이다.)
- 배타를 30%로 바꾸면: **세 규칙 전부 7,000원**(배타 3,000원 할인 > 비배타 2,500원 할인, 그리고 배타의 순위도 1등).
- "배타가 크면 셋이 같다"가 함정인 이유: **예제를 만드는 사람은 배타를 '큰 혜택'으로 상상한다.**\
  그런데 실제 운영에서는 작은 배타 쿠폰(배송비 500원 할인 등)이 훨씬 많고, 거기서만 규칙이 갈린다.

#### 6. 측정 — 갈림의 크기

- 적용 순서로 갈린 시행: **1,136 / 5,000 (23%)**, 한 건 최대 차이 **3,000원**.

```text
 낼 돈 총합
   퍼센트 먼저   226,601,250
   정액 먼저     227,232,856      ← 정액 먼저가 0.279 % 더 비싸다
   우선순위      226,934,108
```

- 정률이 둘 이상인 시행만: **591 / 1,801 (약 33%)** 이 갈린다.
- 정률이 하나뿐이면 순서를 안 타는 이유: **정률이 보는 "남은 금액"은 정액들을 다 뺀 값으로 똑같고, 정률 하나가 앞이든 뒤든 전체 할인 합계가 같아지는 구간이 대부분**이기 때문이다.\
  정확히는 정률 하나 + 정액들은 **정률이 먼저냐 나중이냐만 갈리고**, 정률끼리 서로의 결과를 보는 일이 없어 갈림이 한 자리로 제한된다. 정률이 둘이면 서로가 서로의 입력이 되어 갈림이 커진다.
- 배타 규칙으로 갈린 시행: **1,685 / 5,000 (34%)**, 한 건 최대 **49,980원**.

```text
 낼 돈 총합
   더 깎이는 쪽    226,934,108   기준
   우선순위 우선   233,569,994   +2.92 %
   배타 우선       238,225,832   +4.98 %
```

- `EXCLUSIVE_WINS` 로 두면 매출 **+4.98%**.
- 그 5퍼센트는 **고객이 더 싼 조합을 못 쓴 결과**다(README 문장 그대로). 매출이 는 게 아니라 고객 혜택이 준 것이다.
- 다섯 조합이 전부 같은 시행: **2,614 / 5,000 (52%)**.
- 그런 시행의 모양: **프로모션이 하나뿐이거나, 정액만 있거나, 배타가 없는 경우.**
- 정액 셋 + 배타 없음 (주문 50,000 · 배송비 3,000): **아홉 조합이 전부 주문 45,500원 / 낼 돈 48,500원.**
- 경고인 이유: 사람이 예제를 만들 때 **계산이 쉬운 정액**을 고르고, **하나만** 넣어보고, **배타를 안 붙인다.**\
  즉 예제가 자연히 "규칙이 안 갈리는 52% 쪽"으로 몰린다 — **차이가 나는 입력을 일부러 만들어야 한다.**

#### 7. 변종 검증에서 고친 것

- 0원 할인을 빼는 줄을 지워도 통과한 이유: **테스트에 0원을 깎는 경우가 하나도 없었다.**\
  모든 예제에서 모든 쿠폰이 실제로 돈을 깎았으므로, `if (discount == 0) continue;` 가 한 번도 실행되지 않았다.
- 잡은 예제 둘: ① **20,000원 할인으로 잔액이 0이 된 뒤 1,000원 할인이 붙는 경우** ② **금액이 0인 쿠폰이 섞인 경우**(운영자가 금액을 안 넣은 실수).
- "금액은 어느 쪽이든 맞는다"가 무서운 이유: **검산이 통과한다.** 총 매출, 총 할인액, 정산 대사가 전부 맞는다.\
  틀린 것은 쿠폰 잔여 수량뿐인데, 그건 며칠 뒤 고객 문의로만 드러난다.
- 알아채는 법: **금액 말고 "상태 변화"를 검증한다.** 여기서는 `appliedIds` 를 assert 하는 것이다 — 돈이 아니라 **기록**을 본다.

> **변종 검증(mutation testing)** — 코드를 일부러 망가뜨려 보고 테스트가 잡는지 확인하는 방법.\
> 예: `if (discount == 0) continue;` 를 지우고 돌려서 전부 초록이면, 그 규칙은 검증되고 있지 않은 것이다.

#### 8. 함정 (README)

- 다섯: ① **최소 주문 금액을 할인 후 금액으로 보는 것**(앞의 할인이 뒤의 자격을 없앤다) ② **0원 깎은 프로모션을 "적용됨"으로 기록하는 것**(1회용 쿠폰이 0원을 받고 사라진다) ③ **할인 금액으로 배타를 견주는 것**(무료 배송은 언제나 진다) ④ **같은 우선순위의 순서를 안 정하는 것**(목록 순서가 답을 정한다) ⑤ **남은 금액보다 많이 깎는 것**(금액이 음수가 되고 배송비까지 먹는다).
- 예외도 안 나고 금액도 맞는 것: **②번.** 나머지는 금액이 틀리거나(①③⑤) 재현이 안 되거나(④) 하므로 언젠가는 드러난다.
- "무료 배송은 언제나 진다"가 생기는 이유: 무료배송의 **할인 금액이 정의상 0**이기 때문이다.\
  비교 기준을 할인액으로 잡는 순간, 배송비라는 다른 주머니의 절약분이 비교에서 통째로 빠진다.

#### 9. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 정률 먼저가 유리하다는 사실을 알리나: **알리는 순간 순서가 계약이 된다.** 안 알리면 운영자가 언제든 `ApplyOrder` 를 바꿔 조용히 매출을 0.279% 올릴 수 있고, 알리면 그게 약관이 되어 못 바꾼다. 실무에서 "가장 유리한 순서로 자동 적용"이라고 쓰는 쇼핑몰이 있는데, 그건 **모든 순서를 다 계산해 최소 payable 을 고르겠다는 선언**이라 계산량이 순열만큼 는다. (원본에 답 없음 — 내 추론)
- 배타 셋, 다섯, 열: 지금 구조는 **배타 하나씩만 견주므로 n번**이면 된다(선형). 문제는 "배타 둘을 같이 쓰게 해달라"가 들어올 때다 — 그때는 **부분집합 전부**를 봐야 해서 2ⁿ 이 된다. 열이면 1,024번, 스물이면 100만 번이다. 현실적 타협은 **탐색을 상위 k개로 자르거나**, 배타에 그룹을 붙여 "같은 그룹끼리만 배타"로 좁히는 것이다. (원본에 답 없음 — 내 추론)
- 규칙이 바뀐 뒤의 옛 주문: 이 엔진은 **입력을 받아 계산만 하는 순수 함수**라 과거를 기억하지 못한다. 그래서 `Result`(금액 + `appliedIds`)를 **주문에 스냅샷으로 저장해야** 한다. 저장을 안 하고 "필요할 때 다시 계산"하면 규칙이 바뀐 뒤 같은 주문의 금액이 달라져서 **환불액과 결제액이 안 맞는다.** 이건 09-policy-version 이 다루는 주제다. (원본에 답 없음 — 내 추론)
- 부분 취소: **할인을 어떻게 쪼개느냐가 또 3택이다.** ① 금액 비례로 나눈다(가장 흔하다) ② 취소하는 품목에 붙은 할인만 뺀다(품목별 할인이 있어야 가능) ③ 남은 주문으로 다시 계산한다(그러면 최소 주문 금액 미달로 쿠폰 자격이 사라질 수 있다 — 이미 쓴 쿠폰을 어떻게 되돌리나). 정률과 정액이 섞이면 ③이 특히 위험하다 — **순서가 바뀌면서 남은 금액도 달라진다.** (원본에 답 없음 — 내 추론)

#### 10. 연결

- 01-payroll 과 같은 구조: 급여는 **누적 분** 때문에 순서가 답을 바꿨고, 여기는 **남은 금액** 때문에 순서가 답을 바꾼다. 둘 다 "앞의 결과를 읽는 연산이 끼면 순서가 계약이 된다"는 같은 이야기다.
- 정률이 "지금 남은 금액"을 보는 성질: **비가환(non-commutative)** 이라고 부른다. 덧셈은 순서를 바꿔도 같지만(가환), 곱셈과 덧셈이 섞이면 순서가 결과를 바꾼다.
- 비교 단위를 도메인이 정하는 자리: **05-multi-currency**(어느 통화로 견주나), **04-refund**(환불액인가 고객이 돌려받는 돈인가), **18-settlement-match**(무엇을 "같은 건"으로 보나) — 전부 "무엇을 기준으로 견주나"가 답을 가른다.
