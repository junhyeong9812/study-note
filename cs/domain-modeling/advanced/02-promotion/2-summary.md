# domain-modeling/advanced/02-promotion — 정리 (힌트)

## 해결하는 문제

"쿠폰 여러 장을 같이 쓸 수 있다"는 한 줄로는 계산이 안 된다. 어떤 순서로 적용하나, 배타 쿠폰이 섞이면 무엇을 고르나, "제일 좋은"의 단위는 무엇인가가 비어 있다.\
이 엔진이 없으면: 장바구니 화면·주문 API·환불 계산이 각자 다른 순서로 깎아 **같은 주문에 세 금액**이 생기고, 고객 문의("왜 이 쿠폰이 안 되나요")에 답할 근거가 없다.

```text
같은 장바구니 10,000원 + "10%" + "1,000원"
  화면 계산    퍼센트 먼저  8,000
  주문 API    정액 먼저    8,100   ← 100원이 어디서 왔는지 아무도 모른다
```

쉬운 예: 학교 급식 줄에서 "친구 먼저"와 "선착순"이 동시에 규칙이면 줄이 매번 다르게 선다.\
똑같은 구조다: 순서(`ApplyOrder`)와 배타(`ExclusiveRule`)를 enum으로 박아 두면 모든 호출자가 같은 규칙으로 같은 금액을 낸다.\
실무 예: 쇼핑몰 쿠폰 중복, 통신사 결합 할인, 카드사 청구 할인.

### 한눈에 — 쉽게 말하면

**프로모션 엔진 = 쿠폰 여러 장을 낼 때 "어떤 순서로, 어떤 조합으로 계산할지" 정하는 기계.**

- 마트 계산대에 "10% 할인권"과 "1,000원 할인권"을 같이 냈다. 뭘 먼저 찍느냐에 따라 낼 돈이 달라진다 — **10%는 "지금 남은 금액"을 보고, 1,000원은 안 보기 때문이다.**
- 게다가 어떤 쿠폰에는 "다른 쿠폰과 같이 못 씀(배타)"이라고 적혀 있다. 그럼 배타 한 장을 쓸까, 나머지 묶음을 쓸까? — "배타"라는 한 낱말에서 답이 셋 나온다.
- 이 챕터의 요점: **순서 규칙(ApplyOrder)과 배타 규칙(ExclusiveRule)을 각각 enum으로 박아서, 애매한 말을 코드의 3택으로 바꾼다.**

```text
10,000원 주문 + "10%" + "1,000원"

  퍼센트 먼저   10,000 → 9,000 → 8,000   (10% = 1,000 깎음)
  정액 먼저     10,000 → 9,000 → 8,100   (10% = 900 깎음 — 남은 9,000의 10%)
                                  ^^^^^ 100원 차이
정액은 앞의 결과를 안 보고, 정률은 본다 — 이 차이가 이 박스의 절반이다.
```

실무 예: 쇼핑몰 쿠폰 중복 적용, 통신사 결합 할인, 카드사 청구 할인 — "할인 두 개를 같이 쓰면?"은 어디에나 있다.

## 동작·원리

### 전체 흐름

```text
요구사항(말)                       →  코드(타입/메서드)
──────────────────────────────────────────────────────
"프로모션 한 장"                   →  Promotion record (id·종류·금액·우선순위·배타·최소주문·상한)
"정액/정률/무료배송"               →  enum Kind { FIXED, PERCENT, FREE_SHIPPING }
"어떤 순서로 적용?"  ← 말엔 답 없음 →  enum ApplyOrder { PERCENT_FIRST, FIXED_FIRST, BY_PRIORITY }
"배타면 뭘 고르나?"  ← 이것도      →  enum ExclusiveRule { BEST_DISCOUNT_WINS, EXCLUSIVE_WINS,
                                                          HIGHEST_PRIORITY_WINS }

apply(주문금액, 배송비, 프로모션들, order, exclusiveRule):
  ① eligible  — 최소 주문 금액(할인 전 금액 기준)으로 자격 거르기
  ② 배타/비배타로 나누기 — 배타가 없으면 비배타 전부를 순서대로 적용하고 끝
  ③ 배타가 있으면 ExclusiveRule로 "배타 하나짜리 묶음 vs 비배타 묶음"을 고름
  ④ applyAll — 고른 묶음을 ordered()로 정렬해 하나씩 적용
     · 정률은 "지금 남은 금액"의 %  · 남은 금액보다 많이 못 깎음
     · 0원 깎았으면 적용 목록에 안 넣음
```

  - *정액(FIXED)*: 무조건 그 금액을 깎음. 순서를 안 탄다.
  - *정률(PERCENT)*: 지금 남은 금액의 %를 깎음. **앞의 결과를 보므로 순서를 탄다.**
  - *배타(exclusive)*: 다른 프로모션과 같이 못 쓰는 성질.

### 규칙 1 — 순서가 답을 바꾼다 (정률이 있을 때만)

**어떤 요구사항인가**: "쿠폰 여러 장을 같이 쓸 수 있다." — 순서는 아무도 말 안 해준다.

- 정액만 있으면 순서가 상관없다: 1,000 + 1,500은 어느 쪽이 먼저든 2,500. **그래서 정액 예제로만 시험하면 순서 문제가 통째로 안 보인다** (그리고 예제는 계산 쉬운 정액으로 만들게 된다).
- 정률이 끼는 순간 갈린다. 측정(시행 5,000): 순서로 갈린 시행 1,136/5,000 (23%), 한 건 최대 3,000원. 정률이 2개 이상인 시행만 보면 591/1,801 (33%)이 갈린다.
- 고객에게는 **정률 먼저(PERCENT_FIRST)가 유리**하다 — 큰 금액에 %가 걸리니까. 그걸 아는 고객은 없다.
- 같은 우선순위끼리는 **식별자(id) 순**으로 가른다. 이 기준이 없으면 목록 순서(=DB 조회 순서)가 답을 정한다 — 테스트가 20번 셔플해서 같은 결과를 강제한다.

### 규칙 2 — 배타: "같이 못 쓴다"에서 규칙이 셋 나온다

**어떤 요구사항인가**: "이 프로모션은 다른 것과 중복 불가."— 그럼 배타를 쓸까 말까는 누가 정하나?

예시: 주문 10,000원, 배타 정액 500원(우선순위 1) + 비배타 1,000 + 1,500.

```text
                     고르는 것        낼 주문금액
  BEST_DISCOUNT_WINS  더 싼 쪽       → 비배타 묶음  7,500
  EXCLUSIVE_WINS      무조건 배타     → 배타 하나    9,500
  HIGHEST_PRIORITY    순위 1등이 배타 → 배타 하나    9,500
                                       ^^^^^ 2,000원 차이
```

- 배타가 크면(30% 등) 셋이 같은 답을 낸다 — **예제가 그렇게 생겨서 차이가 안 보인다.**
- 배타의 우선순위를 9로 낮추면 HIGHEST_PRIORITY_WINS는 비배타를 고른다 — 숫자 하나로 규칙의 답이 뒤집힌다.
- 배타가 둘이면 배타끼리도 같이 못 쓴다 — 하나만 고른다.
- 측정: 배타 규칙으로 갈린 시행 1,685/5,000 (34%), 한 건 최대 49,980원. **배타를 무조건 쓰게 하면(EXCLUSIVE_WINS) 매출이 +4.98%** — 그 5%는 고객이 더 싼 조합을 못 쓴 결과다.

### 규칙 3 — 비교는 "할인 금액"이 아니라 "낼 돈"으로

**어떤 요구사항인가**: "제일 많이 깎이는 것을 골라라." — "깎이는"이 무슨 뜻인지 정해야 한다.

```text
배타 무료배송 (할인 0원, 배송비 3,000 절약)  vs  비배타 1,000원 할인

  할인 금액으로 견주면:  0 < 1,000  → 비배타 승  (무료배송은 언제나 진다!)
  낼 돈(payable)으로:    10,000 < 12,000 → 배타 승  ← 올바름
```

- 무료배송은 주문 금액을 안 건드리고 배송비만 0으로 만든다. 그래서 Result에 `finalAmount`(주문금액)와 `shippingPaid`(낼 배송비)를 따로 두고, `payable() = finalAmount + shippingPaid`로 견준다.
- **"제일 좋은"의 단위를 도메인이 정한다** — 할인 합계가 아니라 고객이 실제로 내는 돈.

### 규칙 4 — 자격(최소 주문 금액)은 할인 전 금액으로

**어떤 요구사항인가**: "8,000원 이상 주문 시 사용 가능."

- 할인 **후** 금액으로 보면: 5,000원 할인이 먼저 붙어 잔액 5,000 → "8,000원 이상" 쿠폰이 자격 상실. **적용 순서가 금액뿐 아니라 자격까지 바꾼다** — 그 순간 "이 쿠폰이 왜 안 되나요"를 설명할 수 없게 된다.
- 그래서 eligible()은 **원래 주문 금액(orderAmount)** 하나로 전부 거른다. 테스트: 10,000원 주문에 5,000원 할인 + 최소주문 8,000원 쿠폰 → 둘 다 적용, 4,000원.

### 규칙 5 — 0원 깎았으면 "쓴 것"이 아니다

**어떤 요구사항인가**: 명시된 문장이 없다 — 변종 검증이 찾아낸 규칙이다.

```text
20,000원 할인(잔액 0이 됨) → 그다음 1,000원 할인은 깎을 게 없음

  판정 없이 기록하면: 예외 없음, 금액도 맞음 — 그런데 1회용 쿠폰이
  "0원을 받고 사라진다."  ← 조용한 버그
```

- impl의 `if (discount == 0) continue;` 한 줄이 이 규칙이다. **이 줄을 지워도 원래 테스트는 전부 통과했다** — 0원을 깎는 경우가 테스트에 없었기 때문. 잔액 0 뒤의 쿠폰, 금액 0인 쿠폰(운영자가 금액을 안 넣은 실수) 두 예제를 넣으니 잡혔다.
- 배송비가 이미 0이면 무료배송도 "안 쓴 것"으로 센다 — 같은 이유.
- **금액은 어느 쪽이든 맞는다. 틀리는 것은 쿠폰 사용 기록뿐이다** — 돈이 맞는다고 도메인이 맞는 게 아니다.

### 그 밖의 안전선

- 남은 금액보다 많이 못 깎는다: `Math.min(raw, remaining)` — 없으면 금액이 음수가 되고 배송비까지 먹는다. (20,000원 할인 → 잔액 0, 배송비 3,000은 그대로 낸다.)
- 할인 상한 `maxDiscount`: 30%가 3,000이어도 상한 2,000이면 2,000. **0 = "상한 없음"** 이라는 약속 — "상한 0원"과 헷갈리니 테스트에 기록해놨다.
- 생성 시점 검증: 퍼센트 > 100, 음수 금액, 빈 id, 음수 주문금액은 record 생성자/apply 입구에서 예외.

## 쓰이는 자료구조·알고리즘

- **다중 키 정렬(비교자 합성)** — `ordered()`는 `PERCENT_FIRST`·`FIXED_FIRST`면 `(종류 그룹, priority, id)` 세 키, `BY_PRIORITY`면 `(priority, id)` 두 키를 `thenComparing`으로 이어 붙인다(impl `PromotionEngine.java:86-103`). 마지막 키 `id`가 동률을 끊어 목록(DB 조회) 순서가 답에 새지 않게 한다 — id가 유일할 때 전순서가 된다(`Promotion`이 id 유일성을 강제하지는 않는다). → [algorithm/01-elementary-sort](../../../algorithm/01-elementary-sort/2-summary.md)
- **폴드(fold, 누적 적용)** — `applyAll`은 `remaining`을 들고 프로모션 목록을 한 번 훑으며 갱신한다. 정률이 "지금 남은 금액"을 읽으므로 이 폴드는 **비가환**이다 — 순서가 곧 결과다.
- **후보 열거 + 최소값 선택** — `BEST_DISCOUNT_WINS`는 "배타 하나짜리 묶음 n개 + 비배타 묶음 1개"를 전부 계산해 `payable()` 최소를 고른다. 배타 n개면 n+1번 — 선형이다. "배타 둘을 같이"가 되면 부분집합 2ⁿ으로 폭발한다(정답 9번 참고). → [algorithm/13-backtracking](../../../algorithm/13-backtracking/2-summary.md)
- **자격 필터 → 분할(partition)** — `eligible`(할인 전 금액으로 거르기) → 배타/비배타 두 목록으로 나누기. 필터를 파이프라인 앞에 두어 뒤의 순서가 자격을 못 건드리게 한다.
- **하한·상한 클램프** — `min(raw, maxDiscount)`·`min(raw, remaining)`. `min`끼리는 순서가 무관하다는 성질이 안전선을 단순하게 만든다.
- **센티넬 값** — `maxDiscount == 0` = 상한 없음. "값 없음"을 숫자 하나로 표현하는 관행과 그 위험(정답 2번 참고).

## 적용 — 풀어나가는 법

풀이 순서는 01-payroll과 같다 — 빈 결정 찾기 → enum 올리기 → 갈리는 입력 만들기 → 조합별 측정.\
프로모션에서 갈리는 입력은 "정률 2개 이상 + 작은 배타 쿠폰 + 최소 주문 금액 조건"이다. 정액 하나짜리 예제는 다섯 조합이 전부 같은 답을 내서 아무것도 검증하지 못한다 — 측정에서도 다섯 조합이 전부 같은 시행이 52%(2,614/5,000)였다.\
한 가지가 더 붙는다: **금액이 아니라 상태 변화(`appliedIds`)를 검증하라** — 0원 쿠폰 소진처럼 금액이 맞아도 도메인이 틀리는 결함은 기록을 봐야 잡힌다.

### 문제 — 이 챕터가 시키는 것

원본 README가 던지는 문장은 이것이다.

```text
  10,000 원 주문에 "10 퍼센트" 와 "1,000 원" 을 같이 쓰면

    퍼센트 먼저   10,000 -> 9,000 -> 8,000
    정액 먼저     10,000 -> 9,000 -> 8,100
```

**"정액은 앞의 결과를 안 보고 정률은 본다. 그 차이가 이 박스의 절반이다. 나머지 절반은 배타 프로모션이다."**

- 쿠폰 여러 장을 **어떤 순서로** 적용하는가? — 아무도 말 안 해준다.
- "다른 쿠폰과 같이 못 씀(배타)"이면 **배타를 쓰나 나머지 묶음을 쓰나?**
- "제일 많이 깎이는 것"의 **"깎이는"은 할인 금액인가 고객이 낼 돈인가?**
- "8,000원 이상 주문 시" 자격은 **할인 전 금액인가 할인 후 금액인가?**

넷 다 말이 된다.\
그래서 이 박스는 답을 하나로 정하지 않고 `ApplyOrder` · `ExclusiveRule` **enum으로 올린다.**

> **배타(exclusive)** — "이 쿠폰은 다른 쿠폰과 같이 못 쓴다"는 성질.\
> 예: "첫 구매 30% 쿠폰(타 쿠폰과 중복 불가)"을 내면 손에 든 1,000원 쿠폰은 못 쓴다 — 그럼 어느 쪽을 쓸지 누가 정하나.

| 3 | `applyAll(...)` | 묶음을 순서대로 적용. **0원 깎았으면 적용 목록에 안 넣음** |
| 4 | `apply(...)` | 자격 거르기 → 배타/비배타 분리 → `ExclusiveRule` 로 묶음 선택 |

테스트가 못 박은 계약(`PromotionEngineTest`, 주문 10,000원·배송비 3,000원): 10%+1,000원 → 퍼센트 먼저 8,000 / 정액 먼저 8,100 · 정액 1,000+1,500 → 세 순서 전부 7,500 · 20번 셔플해도 결과 동일 · 배타 30% vs 비배타 2,500 → 세 규칙 전부 7,000 · 배타 500원(순위1) vs 비배타 2,500 → 7,500 / 9,500 / 9,500 · 배타 순위를 9로 낮추면 9,000 / 9,500 / 9,000 으로 뒤집힘 · 배타 둘이면 하나만 · 무료배송은 할인 0원인데 낼 돈 10,000원 · 상한 2,000이면 30%도 2,000까지 · 최소주문 8,000 쿠폰은 5,000원 할인 뒤에도 적용(4,000원) · 20,000원 할인은 0원까지만, 배송비는 그대로 · 0원 깎은 프로모션은 `appliedIds` 에 안 들어감.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

### 측정 — 예제가 숨기는 것

```text
시행 5,000 (README 기록):
  순서로 갈림           1,136 (23%)     정액 먼저가 총액 +0.279%
  배타 규칙으로 갈림    1,685 (34%)     EXCLUSIVE_WINS 가 +4.98%
  다섯 조합 전부 같음   2,614 (52%)     ← 프로모션 1개·정액만·배타 없음
정액 셋 + 배타 없음 → 아홉 조합 전부 48,500원 (아무것도 안 갈린다)
```

**절반의 입력에서는 어느 규칙을 골라도 같다** — 그리고 예제를 만들 때 그런 조합이 먼저 떠오른다. 규칙의 차이는 "정률 2개 이상 + 배타 섞임" 같은 입력을 일부러 만들어야 보인다.

## 장애 시나리오와 대처

**1. 장바구니 금액과 결제 금액이 100원 다르다**

- 현상: 장바구니 화면에는 8,000원, 결제창에는 8,100원이 뜬다.
- 보이는 형태: PG 결제 요청 금액과 주문 금액 불일치로 결제가 거절되거나, 고객이 "화면과 다르다"고 문의한다.
- 원인: 프론트와 백엔드가 **각자 계산**하며 `ApplyOrder`가 다르다(퍼센트 먼저 vs 정액 먼저). 정률이 끼면 순서가 100원을 움직인다.
- 대처: 계산은 한 곳(엔진)에서만 하고 화면은 결과를 표시만 한다. 주문에 `Result`(금액 + `appliedIds`)를 스냅샷으로 저장해 결제·환불이 같은 값을 쓴다.

**2. 1회용 쿠폰이 0원을 받고 사라졌다는 문의**

- 현상: 잔액이 이미 0인 주문에 붙은 쿠폰이 "사용됨"으로 소진됐다.
- 보이는 형태: 매출·할인 합계·정산은 전부 맞는다. 며칠 뒤 고객센터에 "쿠폰이 없어졌다"가 들어온다.
- 원인: 0원 깎은 프로모션을 `appliedIds`에 넣었다. 예외도 금액 오류도 없는 **조용한 실패**다.
- 대처: `discount == 0`이면 적용 목록에 넣지 않는다(무료배송도 배송비가 이미 0이면 같다). 테스트는 금액이 아니라 `appliedIds`를 assert 한다. 이미 소진된 쿠폰은 사용 기록을 뒤져 복구한다.

**3. 같은 주문을 두 번 계산했더니 금액이 다르다**

- 현상: 재계산 배치나 재시도에서 같은 주문의 할인 금액이 달라진다.
- 보이는 형태: 우선순위가 같은 쿠폰 둘이 있을 때만, 그리고 간헐적으로만 생긴다.
- 원인: 정렬의 마지막 키(`id`)가 빠져 있어 `ORDER BY` 없는 조회 순서가 답을 정한다. 정률이 끼면 순서가 금액을 바꾼다.
- 대처: 비교자에 전순서 키를 붙이고, 테스트는 입력을 여러 번 셔플해 같은 결과를 강제한다(`inputOrderIndependent`).

**4. "왜 이 쿠폰이 안 되나요"에 답을 못 한다**

- 현상: 최소 주문 금액 8,000원 쿠폰이 10,000원 주문에서 거절된다.
- 보이는 형태: 고객이 다른 쿠폰을 빼면 그 쿠폰이 갑자기 된다.
- 원인: 자격을 **할인 후 금액**으로 판정해 앞의 5,000원 할인이 뒤의 자격을 없앴다. 순서가 금액뿐 아니라 자격까지 바꾼다.
- 대처: `eligible()`은 원래 주문 금액(`orderAmount`) 하나로만 거른다. 거절 사유를 값으로 돌려줘 화면이 이유를 보여준다.

## 핵심 문장

- 정액은 앞의 결과를 안 보고 정률은 본다 — **상태를 읽는 연산이 끼는 순간 순서가 계약이 된다.**
- "배타"라는 한 낱말에서 규칙 셋(더 싼 쪽/무조건 배타/우선순위)이 나오고, 34%의 주문에서 답이 갈린다 — enum으로 선택지를 드러내고 사람이 골라야 한다.
- "제일 좋은 프로모션"의 비교 단위는 할인 금액이 아니라 **고객이 낼 돈** — 아니면 무료배송이 언제나 진다.
- 자격 판정은 할인 전 금액으로 — 아니면 순서가 자격까지 바꾸고, 설명 불가능한 시스템이 된다.
- 0원 깎은 쿠폰을 "적용됨"으로 기록하면 예외도 금액 오류도 없이 **쿠폰만 사라진다** — 금액이 맞아도 도메인은 틀릴 수 있다.

### 용어 풀이

- **정액 할인(FIXED)**: "1,000원 깎음". 앞의 결과와 무관 — 순서를 안 탄다.
- **정률 할인(PERCENT)**: "남은 금액의 10% 깎음". 앞의 결과를 본다 — 순서를 탄다.
- **무료 배송(FREE_SHIPPING)**: 배송비를 0으로. 주문 금액(할인 합계)에는 안 잡힌다.
- **배타(exclusive)**: 다른 프로모션과 같이 못 쓰는 성질. 배타끼리도 같이 못 쓴다.
- **ApplyOrder**: 적용 순서 3택 — 정률 먼저 / 정액 먼저 / 우선순위 숫자 순.
- **ExclusiveRule**: 배타가 섞였을 때 3택 — 더 싼 쪽 / 무조건 배타 / 우선순위 1등.
- **우선순위(priority)**: 작을수록 먼저. 같으면 id 순 — 이 뒷기준이 없으면 목록 순서가 답을 정한다.
- **payable(낼 돈)**: 최종 주문 금액 + 낼 배송비. 프로모션 조합을 견주는 올바른 단위.
- **최소 주문 금액(minOrderAmount)**: 쿠폰 자격 조건. 할인 **전** 금액으로 판정한다.
- **할인 상한(maxDiscount)**: 정률 할인이 깎을 수 있는 최대 금액. 0이면 상한 없음(약속).
- **적용 목록(appliedIds)**: 실제로 돈을 움직인 프로모션의 기록. 1회용 쿠폰 소진과 직결된다.
