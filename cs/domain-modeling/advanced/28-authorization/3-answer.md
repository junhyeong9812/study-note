### A. 과제

#### 0. 두 줄에서 세 답

```text
 안 말해준 것            가능한 읽기
 (겹치면 누가 이기나?)  →  거부 우선 / 허용 우선 / 구체성 우선
 (안 맞으면?)           →  기본 거부 / 기본 허용
 (물려받을 때?)         →  둘 다 물려받기 / 허용만 물려받기
```

- 어디에도 안 적혀 있다. **두 줄은 "무엇을 허용/거부한다"만 말하고, "겹쳤을 때 누가 이기나"는 말하지 않는다.**\
  그 결정은 규칙 목록 바깥의 **엔진 설정**에 있다.
- 구체성 우선이 허용으로 가는 이유:

```text
 (order, *,      ALLOW)   대상 있음(2) + 행위 별표(0)  =  2
 (*,     delete, DENY)    대상 별표(0) + 행위 있음(1)  =  1
 2 > 1 이므로 허용 줄이 이긴다
```

- "서로 간섭한다": **한 축의 값이 다른 축을 무력화한다.**\
  실제 예 셋 —
  - 허용만 물려받으면 **부모의 거부가 사라져** "거부 우선"이 아무 일도 안 한다(481 → 3,102).
  - 거부가 하나도 없으면 **상속 축이 통째로 죽는다**(7,186 = 7,186).
  - 규칙이 스무 줄만 돼도 거의 다 맞아서 **기본값 축이 7,200건 중 14건에만** 걸린다.
- 흩어져 있는 곳: 충돌 규칙과 상속 규칙은 **권한 설정 화면의 다른 탭**에 있다(README).\
  그래서 한 화면만 보고는 두 설정이 서로를 무력화한다는 것을 알 수 없다.

#### 1. TODO 1 — matches

정답 코드 (impl/Authorizer.java):

```java
boolean resourceOk = rule.anyResource() || rule.resource().equals(resource);
boolean actionOk = rule.anyAction() || rule.action().equals(action);
return resourceOk && actionOk;
```

- 맞는 두 경우: ① **별표다**(`*`) ② **글자 그대로 같다**(`equals`).
- 하나만 맞으면: **안 맞는다.** 둘 다(`&&`) 맞아야 한다.
- `startsWith` 로 맞추면: **앞글자가 같기만 하면 열린다.**

```text
 규칙 (order, read, ALLOW)  ← "주문을 읽을 수 있다"
   요청 (order, readAll)     startsWith → 맞는다(!)  → 전체 내려받기가 열린다
   요청 (orderItem, read)    startsWith → 맞는다(!)  → 다른 대상이 열린다
 equals 면 둘 다 안 맞는다
```

- 큰 사고인 이유: **`readAll` 은 대개 전체 내려받기**다.\
  "한 건 조회" 권한만 준 사람이 **전 고객 명단을 통째로 받아간다.**\
  그리고 판정은 정상적으로 "허용"이라 로그에도 이상이 안 남는다.

> **권한 상승(privilege escalation)** — 준 적 없는 더 큰 권한이 실수로 열리는 것.\
> 예: 주문 한 건 조회 권한이 전체 주문 내려받기까지 열어 주면, 문법상 버그가 아니라 보안 사고다.

- 접두사 짝 셋: **`read`/`readAll`**, **`export`/`exportAll`**, **`approve`/`approveAll`**.
- 대상 쪽의 같은 사고: **`order` 규칙이 `orders`·`orderItem` 요청에 맞는 것.**
- `equalsIgnoreCase` 로 하면: `Order` 규칙이 `order` 요청에 맞는다.\
  편해 보이지만 **대상 이름을 정하는 규칙이 두 군데(저장할 때·비교할 때)로 갈린다.**\
  원본은 **글자 그대로**를 골랐다 — 판정이 문자열 정규화 규칙에 안 끌려가게 한 것이다. (원본에 답 없음 — 내 추론)

#### 2. TODO 2 — specificity

정답 코드:

```java
return (rule.anyResource() ? 0 : 2) + (rule.anyAction() ? 0 : 1);
```

- 네 조합:

```text
 (order, delete)  2 + 1 = 3   제일 구체적
 (order, *)       2 + 0 = 2
 (*,     delete)  0 + 1 = 1
 (*,     *)       0 + 0 = 0   제일 약하다
```

- 대상에 2점을 준 이유: **"주문에 대해서는"이 "삭제에 대해서는"보다 좁다고 본 것**이다.\
  대상 하나에 행위가 여럿 붙으므로, 대상을 고정하는 쪽이 더 많이 좁힌다.\
  이 판단 자체가 **정답이 있는 문제가 아니라 정한 것**이다.
- 반대로 잡으면(대상 1, 행위 2):

```text
 (order, *)       1 + 0 = 1
 (*,     delete)  0 + 2 = 2   ← 이쪽이 이긴다
 0 번의 예가 "허용" 에서 "거부" 로 뒤집힌다
```

- 규칙 목록 어디에도 안 적혀 있다. **가중치는 엔진 코드 안에만 있다.**\
  그래서 규칙 두 줄을 아무리 들여다봐도 왜 그 답이 나왔는지 알 수 없다(README "생각해볼 것"의 첫 질문이 이것이다).
- 0~3의 정수라는 것: **값이 넷뿐**이라는 뜻이다.\
  규칙이 스무 줄이면 **비둘기집 원리로 같은 값이 반드시 겹친다** — 동률이 예외가 아니라 기본이다.\
  그래서 "구체성이 같을 때 누가 이기나"를 반드시 정해둬야 한다.

> **동률(tie)** — 비교 기준으로 우열을 못 가리는 상태.\
> 예: `(order,delete,ALLOW)` 와 `(order,delete,DENY)` 는 둘 다 구체성 3이라 구체성으로는 못 가른다.

#### 3. TODO 3 — applicable

정답 코드:

```java
List<String> chain = chain(roleId);
List<Rule> applicable = new ArrayList<>();
for (String role : chain) {
    boolean inherited = !role.equals(roleId);
    for (Rule rule : rules) {
        if (!rule.roleId().equals(role) || !matches(rule, resource, action)) {
            continue;
        }
        if (inherited && inheritance == Inheritance.ALLOW_ONLY
                && rule.effect() == Effect.DENY) {
            continue;
        }
        applicable.add(rule);
    }
}
return List.copyOf(applicable);
```

- 가까운 것부터 훑는 이유: **동률일 때 목록 앞쪽이 뽑히기 때문**이다.\
  구체성이 같고 효과도 같은 줄이 여럿이면 `candidates.get(0)` 이 답이 된다.\
  그 자리에 **자기 역할의 규칙이 먼저 오게** 해서, 가까운 규칙이 먼 규칙을 이기게 한 것이다.
- `ALLOW_ONLY` 가 버리는 것: **자기 역할이 아닌 역할(= 물려받은 역할)의 거부 규칙**뿐이다.

```text
 사원 → 운영자 → 관리자

  관리자의 DENY   물려받은 것   ALLOW_ONLY 에서 버린다
  운영자의 DENY   물려받은 것   버린다
  사원  의 DENY   자기 것       남긴다
  모든 ALLOW      어디 것이든   남긴다
```

- 자기 것까지 버리면: **거부를 아예 쓸 수 없다.**\
  `ALLOW_ONLY` 를 켠 순간 시스템 전체에서 거부가 사라져, 규칙 화면에 적은 거부가 전부 장식이 된다.
- 한 줄 설명: **"내가 스스로 건 금지"와 "위에서 내려온 금지"는 다른 것이다.**\
  상속을 제한하는 설정은 앞엣것까지 지울 이유가 없다.
- `chain` 이 멈추는 이유: **같은 역할을 두 번 보면 무한 반복**이기 때문이다.

```java
while (current != null && seen.add(current)) {   // 이미 본 역할이면 add 가 false
    chain.add(current);
    current = parents.get(current);
}
```

- 안 막으면: `a → b → a → b → …` 로 **영원히 돈다.**\
  권한 판정은 모든 요청마다 부르므로, 요청 하나가 스레드 하나를 영원히 잡는다.
- 화면에서 안 보이는 이유: 권한 화면은 **역할마다 "부모가 누구"만 보여준다.**\
  `a`의 부모가 `b`, `b`의 부모가 `a` 는 각각 한 줄씩으로는 전혀 이상하지 않다.\
  고리는 **두 줄을 이어 봐야** 보인다.

> **고리(cycle)** — 따라가다 보면 출발점으로 돌아오는 관계.\
> 예: 부장이 차장을 물려받고 차장이 부장을 물려받으면, 위로 올라가는 길이 끝나지 않는다.

#### 4. TODO 4 — decide

정답 코드:

```java
List<Rule> matched = applicable(roleId, resource, action, rules, inheritance);
if (matched.isEmpty()) {
    return new Decision(fallback == Fallback.ALLOW, null, matched);
}

List<Rule> candidates = matched;
if (conflict == Conflict.MOST_SPECIFIC) {
    int best = 0;
    for (Rule rule : matched) {
        best = Math.max(best, specificity(rule));
    }
    List<Rule> narrowed = new ArrayList<>();
    for (Rule rule : matched) {
        if (specificity(rule) == best) {
            narrowed.add(rule);
        }
    }
    candidates = narrowed;
}

boolean allowWins = conflict == Conflict.ALLOW_WINS;
Effect winner = allowWins ? Effect.ALLOW : Effect.DENY;
for (Rule rule : candidates) {
    if (rule.effect() == winner) {
        return new Decision(winner == Effect.ALLOW, rule, matched);
    }
}
Rule first = candidates.get(0);
return new Decision(first.effect() == Effect.ALLOW, first, matched);
```

- 순서:

```text
 ① 맞는 줄 모으기(applicable)
 ② 하나도 없으면 → 기본값, decidedBy = null
 ③ 구체성 우선이면 → 최고 구체성인 줄만 남긴다
 ④ 후보 중에 "이기는 효과" 가 있으면 그 줄이 답
       허용 우선 → ALLOW 를 찾는다
       거부 우선·구체성 우선 → DENY 를 찾는다
 ⑤ 없으면 후보의 첫 줄이 답
```

- `MOST_SPECIFIC` 의 좁히기: **맞은 줄들의 구체성 최댓값을 구하고, 그 값과 같은 줄만 남긴다.**
- 좁힌 뒤 남는 여러 줄: **거부가 이긴다**(`winner = DENY`).\
  `MOST_SPECIFIC` 은 "구체성으로 가르고, 못 가르면 거부"라는 **두 단 규칙**이다.
- 목록 순서의 정체: **규칙을 DB에서 읽어온 순서**다.\
  즉 **조회 쿼리의 `ORDER BY`** 가 판정을 정하게 된다.
- 정렬을 바꾸는 날: 규칙을 한 줄도 안 고쳤는데 **권한이 바뀐다.**\
  "성능 때문에 인덱스를 바꿨다" 같은 변경이 권한 사고가 된다.\
  그래서 테스트가 **목록을 뒤집어도 같은 답**임을 못 박는다(`tiesGoToDeny`).
- `decidedBy` 를 돌려주는 이유: **"왜 막혔는지"를 사람에게 보여주려고.**\
  스무 줄 중 어느 줄이 이겼는지 모르면 규칙을 고칠 수가 없다.
- `byDefault()` 로만 알 수 있는 것: **기본값 때문에 그렇게 됐는지, 규칙 때문인지.**\
  둘 다 "거부"라는 같은 결과로 보이지만 고치는 법이 정반대다 — 전자는 규칙을 추가해야 하고, 후자는 규칙을 고쳐야 한다.
- `matched` 에 들어가는 것: **좁히기 전 목록 전부**다.\
  "이 요청에 몇 줄이 맞았나(겹침)"를 세려면 좁히기 전 목록이 있어야 한다.\
  측정 테스트가 `matched().size() > 1` 로 겹침을 세는 것이 그 쓰임이다.

### B. 개념

#### 5. 측정 — 발견 하나: 별표가 갈림을 키운다

- 별표 80%: 거부 우선 **37 / 7,200 = 0.5%**, 허용 우선 **7,200 / 7,200 = 100%**.\
  **같은 규칙 스무 줄로 0.5%와 100%가 나온다.**
- 별표 0%인데 겹치는 이유: **같은 대상·같은 행위에 허용과 거부를 둘 다 적어놨기** 때문이다.\
  규칙을 무작위로 스무 줄 만들면 대상 6 × 행위 4 = 24칸에 스무 줄이 떨어지므로 같은 칸에 둘 이상이 흔하다.
- 표로 설명:

```text
 별표  0 %   겹친 요청 1,460   ← 별표가 없어도 겹친다 (생기는 원인은 별표가 아니다)
 별표 20 %   겹친 요청 5,593
 별표 40 %   겹친 요청 7,096
 별표 80 %   겹친 요청 7,200   ← 모든 요청이 겹친다 (별표가 키운다)
```

- 0%에서 거부 우선 = 구체성 우선인 이유: **별표가 없으면 모든 규칙의 구체성이 3이다.**\
  최고 구체성이 3이고 맞은 줄이 전부 3이므로 **좁히기가 아무것도 안 걸러낸다.**\
  그다음 단계가 "거부를 찾는다"이므로 거부 우선과 글자 그대로 같은 계산이 된다.
- 구체성 우선이 80%에서 오히려 줄어드는 이유(3,402 → 2,946): 별표가 늘면 **맞는 줄이 많아지고 동률 묶음도 커진다.**\
  묶음이 커질수록 그 안에 거부가 하나라도 낄 확률이 올라가고, **동률이면 거부가 이긴다.**\
  즉 별표가 늘면 "구체성으로 가르기"가 실패하고 **사실상 거부 우선으로 미끄러진다.** (원본에 답 없음 — 내 추론, `decide` 의 동률 규칙에 근거)

#### 6. 측정 — 발견 둘: 기본값은 거의 안 걸린다

- 기본값이 걸린 건수: **14 / 7,200**(0.19%).
- 차이가 딱 14인 이유: **기본값이 걸린 요청에서만 두 설정이 갈리기** 때문이다.

```text
 맞는 줄이 있는 7,186 건  →  기본값을 안 본다 → 두 설정이 같은 답
 맞는 줄이 없는    14 건  →  기본 거부면 거부, 기본 허용이면 허용
 그러므로 허용 건수 차이 = 정확히 14   (481 + 14 = 495)
```

- 거의 다 맞는 이유: **별표가 40%나 있다.** `(*, *)` 한 줄이면 24가지 요청 **전부**에 맞는다.\
  스무 줄 중 그런 줄이 몇 개만 있어도 안 맞는 요청이 거의 남지 않는다.
- 위험한 관찰인 이유: **회의 시간과 실제 효과가 정반대로 배분돼 있다.**\
  기본값은 오래 논쟁하고 14건에 걸리는데, 상속 설정은 논쟁 없이 탭 하나를 바꿔 **2,621건**(481→3,102)을 움직인다.\
  **어디를 봐야 하는지를 직관이 못 알려준다**는 것이 이 챕터의 핵심 교훈이다.
- `ALLOW_ONLY` 에서 71건으로 느는 이유: **부모의 거부를 버리면서 맞는 줄이 사라지는 요청이 생긴다.**\
  원래는 "부모의 거부 한 줄"만 맞던 요청이, 그 줄을 버리자 **아무 줄도 안 맞는 요청**이 된다 → 기본값으로 넘어간다.
- 그래도 중요한 이유: **14건이 무엇이냐가 문제**다.\
  아무 규칙도 안 걸린 요청은 대개 **방금 배포한 새 기능**이다.\
  건수는 적지만 그 건들이 정확히 "아직 아무도 권한을 정하지 않은 자리"다.

#### 7. 측정 — 발견 셋: 허용만 물려받기

- **481 → 3,102, 약 6.4배.**
- 거부가 후보에 없는 과정:

```text
 규칙   관리자에게 (order, *,      ALLOW)
        관리자에게 (order, delete, DENY)
 사원이 order/delete 를 요청한다

  둘 다 물려받기   후보 [ALLOW, DENY]  →  거부 우선 → 거부
  허용만 물려받기  후보 [ALLOW]        →  거부 우선이지만 거부가 없다 → 허용
```

  "거부 우선"은 **후보 안에 거부가 있을 때만** 일한다.\
  상속 설정이 후보를 만들기 전에 거부를 걸러버리므로, 충돌 설정은 이미 끝난 싸움을 심판한다.
- 다른 탭에 있는 것이 문제인 이유: **두 설정을 한 화면에서 같이 볼 수 없다.**\
  "거부 우선"을 켠 사람은 자기가 안전하게 설정했다고 믿는다.\
  다른 탭의 "허용만 물려받기"가 그것을 무력화한다는 사실은 **어느 화면에도 안 뜬다.**
- 미리 알아채는 법: **조합을 전부 돌려보고 건수를 세는 것.**\
  이 챕터가 한 방법이 그것이다 — 3(충돌) × 2(기본값) × 2(상속) = 12 조합을 7,200건에 대해 돌려본다.\
  설정 화면을 읽어서는 절대 안 나오고, **재봐야 나온다.**

#### 8. 측정 — 발견 넷·다섯

```text
 거부  0 %   둘 다 7,186   허용만 7,186   차이 0
 거부 20 %   둘 다 5,073   허용만 6,298   차이 1,225
 거부 40 %   둘 다 3,402   허용만 5,238   차이 1,836
 거부 80 %   둘 다 1,034   허용만 2,268   차이 1,234
```

- 거부 0%면 사라지는 이유: `ALLOW_ONLY` 가 하는 일은 **거부를 버리는 것**뿐이다.\
  버릴 거부가 없으면 두 설정이 **글자 그대로 같은 후보 목록**을 만든다.
- 한 줄 설명: **제한하는 설정은 제한할 대상이 있어야 일한다.**\
  (참고: 7,186 = 7,200 − 14 로, 발견 둘의 "안 맞는 14건"과 같은 수다. 맞는 줄이 있으면 전부 ALLOW 이니 허용, 안 맞는 14건만 기본 거부로 막힌다.)
- 초기에 안 보이는 이유: **권한 설계를 처음 할 때는 허용만 적는다.**\
  "누가 무엇을 할 수 있다"를 나열하는 것이 자연스럽고, 거부는 아직 쓸 일이 없다.\
  그 상태에서는 세 설정 중 둘이 죽어 있어서 **아무 값으로 둬도 결과가 같다.**
- 거부를 처음 붙이는 날: **잠자던 설정이 한꺼번에 살아난다.**\
  거부는 대개 **사고가 나서** 붙인다 — 급하게 "이건 막아"를 넣는 날이다.\
  그날 그 거부가 실제로 먹히는지는 몇 달 전 아무 생각 없이 정해둔 상속 설정이 정한다.
- 별표만 없애도 갈리는 이유: **거부가 남아 있기** 때문이다(3,300 비교 중 **2,884**, 약 87%).\
  겹침을 만드는 원인이 별표 하나가 아니라 **별표 + 거부** 둘이고, 하나만 없애서는 안 사라진다.
- 경고: **"우리 설정으로는 지금 아무 문제 없다"가 안전을 뜻하지 않는다.**\
  지금 문제가 없는 이유는 설정이 좋아서가 아니라 **아직 거부를 안 썼거나 별표를 안 썼기** 때문일 수 있다.\
  그 조건이 깨지는 날 잠복해 있던 설정이 전부 효력을 갖는다.

> **잠복한 설정(dormant configuration)** — 지금 조건에서는 결과를 안 바꾸지만, 조건이 바뀌면 갑자기 효력을 갖는 설정.\
> 예: 거부 규칙이 하나도 없는 동안에는 "허용만 물려받기"를 켜든 끄든 완전히 같다.

#### 9. 함정

- 넷:
  1. **접두사 일치로 맞추는 것** — `read` 권한이 `readAll`(전체 내려받기)을 연다.
  2. **구체성이 같을 때를 안 정하는 것** — 목록 순서가 판정을 정하고, 그 순서는 조회 쿼리의 정렬이다.
  3. **허용만 물려받는 규칙에서 자기 역할의 거부까지 버리는 것** — 거부를 아예 못 쓴다.
  4. **역할 고리를 안 막는 것** — 설정 실수 하나가 무한 반복이 된다.
- 여는 쪽과 막는 쪽:

```text
 조용히 연다   ① 접두사 일치        → 안 준 권한이 열린다 (보안 사고)
 조용히 연다   ③ 자기 거부까지 버림 → 막으려던 것이 안 막힌다
 갈린다        ② 동률 미정의        → 정렬에 따라 열렸다 막혔다 한다
 요란하다      ④ 역할 고리          → 응답이 영원히 안 온다 (장애)
```

- ②가 특히 무서운 이유: **권한 코드도 규칙 데이터도 안 바뀌었는데 판정이 바뀐다.**\
  변경 이력을 아무리 뒤져도 "권한을 바꾼 사람"이 안 나온다.\
  바꾼 사람은 쿼리 정렬을 손본 사람이고, 본인은 권한을 건드린 줄도 모른다.

#### 10. 변종 검증에서 고친 것

- 약한 테스트: **행위를 `startsWith` 로 맞춰도 통과했다.**
- 생긴 이유: **대상 쪽만 봤다.** `order` / `orders` 로는 확인했는데 **행위 쪽 접두사 짝을 안 만들었다.**\
  같은 함수 안에 축이 둘(대상·행위) 있는데 **한 축만 테스트한 것**이다.
- 잡힌 방법: **`read` 와 `readAll` 을 넣으니** 잡혔다.\
  그리고 그 짝은 `export`/`exportAll`, `approve`/`approveAll` 처럼 실제로 흔하다.
- 일반적으로 막는 법: **축마다 같은 종류의 경계 케이스를 대칭으로 만든다.**\
  "대상에 접두사 짝을 넣었으면 행위에도 넣는다"를 체크리스트로 두는 것이다.\
  그리고 확실한 방법은 **변종 검증** — 한 축의 비교를 일부러 느슨하게 바꿔보고 테스트가 잡는지 본다. (원본에 답 없음 — 내 추론)

#### 11. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조·측정치에 근거한 내 추론이다.)*

- 구체성이 규칙 어딘가에 적혀 있나: **안 적혀 있다.** `specificity` 의 `2`와 `1`은 엔진 코드 안에만 있다.\
  그래서 규칙을 쓰는 사람은 **자기가 쓴 두 줄 중 어느 쪽이 이길지 모른다.**\
  적으려면 규칙 줄마다 `priority` 를 사람이 직접 쓰게 하거나(AWS IAM 의 명시적 Deny 처럼 **규칙에 우선순위를 넣거나**), 최소한 화면에 "이 줄의 구체성: 2"를 보여줘야 한다. (원본에 답 없음 — 내 추론)
- 겹친 두 줄을 보여주나: 코드는 **보여줄 재료를 갖고 있다** — `Decision` 이 `matched`(맞은 줄 전부)와 `decidedBy`(이긴 줄)를 함께 낸다.\
  판정(`allowed`)만 화면에 쓰면 그 재료가 버려진다.\
  겹침이 7,200건 중 7,096건인 상황(별표 40%)에서 **"막혔습니다"만 보여주는 화면은 고칠 수가 없다.** (원본에 답 없음 — 내 추론)
- 배포일과 규칙 입력일 사이: **기본값이 그 구간을 정한다.**

```text
 기본 거부   새 대상 refund 가 배포됨 → 규칙을 넣을 때까지 아무도 못 쓴다
             (기능이 죽어 보이지만 안전하다)
 기본 허용   배포된 순간부터 규칙을 넣기 전까지 전원이 쓴다
             (권한 화면에는 아무 줄도 없는데 실제로는 다 열려 있다)
```

  그리고 발견 둘이 말하듯 그 구간에 걸리는 건수는 적다(14건) — **적지만 전부 새 기능이다.** (원본에 답 없음 — 내 추론)
- 역할을 지우면: `parents` 맵에서 그 역할이 빠지면 **`chain` 이 그 자리에서 끊긴다.**\
  `parents.get(current)` 가 `null` 을 주므로 루프가 멈추고, **그 위의 조상 규칙들이 통째로 사라진다.**\
  즉 중간 역할 하나를 지우면 자식 역할이 **조용히 권한을 잃는다**(또는 조상의 거부가 사라져 **조용히 권한을 얻는다**).\
  막으려면 지우기 전에 "이 역할을 부모로 삼은 역할이 있나"를 확인해야 한다. (원본에 답 없음 — 내 추론)

#### 12. 연결

- 실무의 같은 구조: **AWS IAM**(명시적 Deny 우선 + 정책 평가 순서), **파일 시스템 ACL**, **방화벽 규칙**(첫 매치 우선), **Kubernetes RBAC**(거부가 아예 없는 설계) — 전부 "겹친 규칙을 어떻게 심판하나"다.\
  IAM 이 "명시적 Deny 는 무조건 이긴다"로 못 박은 것은, 여기서 본 **동률·상속 상호작용을 아예 없애려는** 선택이다.
- "설정 A가 설정 B를 무력화": **26-photocard-set 의 "중복 금지가 보장 설정을 무력화"**, **27-ab-assign 의 "비율 0/100이 씨앗을 죽인다"** 와 같은 자리다.\
  세 박스가 공통으로 말하는 것 — **축을 독립적으로 이해하면 안 된다. 조합을 재야 한다.**
- 알고리즘 트랙과의 차이: 알고리즘은 **같은 답으로 가는 비용**을 셌다.\
  여기서는 **답 자체가 갈리는 건수**를 센다 — 7,200건 중 37과 7,200이 둘 다 "정답"이다.\
  비용이 아니라 **불일치**를 재는 것이 도메인 모델링 트랙의 측정이다.
