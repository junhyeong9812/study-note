# domain-modeling-advanced/28-authorization — 정리 (힌트)

## 해결하는 문제

권한 규칙을 한 줄씩 적으면 언젠가 두 줄이 같은 요청에 **둘 다 맞는다** — 그리고 답이 서로 다르다.\
어느 줄을 따를지는 그 두 줄 어디에도 안 적혀 있으므로, 규칙 밖의 **메타 규칙**이 없으면 판정이 목록 순서나 조회 정렬에 매달린다.

```text
  요청 (운영자, order, delete)
      ├ (order, *,      ALLOW)  맞음
      └ (*,     delete, DENY)   맞음     → 누가 이기나?  규칙에 없다
```

쉬운 예: "체육관은 누구나 사용 가능"과 "방과 후 전부 출입 금지"가 붙어 있을 때 방과 후 체육관 — 두 규칙이 둘 다 맞고 답이 다르다.\
똑같은 구조다: 겹치면 누가 이기나(Conflict) × 아무 줄도 안 맞으면(Fallback) × 역할을 물려받을 때 거부도 오나(Inheritance)를 enum 세 축으로 꺼내야 같은 규칙 스무 줄이 허용률 0.5%와 100% 사이 어디로 가는지 잴 수 있다.\
실무 예: AWS IAM의 명시적 Deny 우선, 파일 시스템 ACL, 관리자 화면 메뉴 권한 — 그리고 "왜 나는 안 되나요"에 판정 근거(어느 줄이 이겼나)를 값으로 돌려줘야 하는 모든 권한 서비스.

### 한눈에 — 쉽게 말하면

**권한 판정 = 학교 규칙 겹칠 때 어느 규칙을 따르나.**

- "체육관은 누구나 사용 가능"이라는 규칙과 "방과 후에는 전부 출입 금지"라는 규칙이 붙어 있다. 방과 후에 체육관에 가면? — 두 규칙이 **둘 다 맞고, 답이 서로 다르다.** 어느 쪽을 따를지는 두 규칙 어디에도 안 적혀 있다.
- 권한 시스템이 똑같은 구조다. "운영자는 주문을 볼 수 있고 삭제는 못 한다"는 말에 정해지지 않은 것이 셋: ① **겹치면** 거부가 이기나, 허용이 이기나, 더 구체적인 줄이 이기나(Conflict) ② **아무 줄도 안 맞으면** 기본이 거부인가 허용인가(Fallback) ③ **역할을 물려받을 때** 거부도 물려받나 허용만 물려받나(Inheritance).
- 원본 README의 핵심 예:

```text
  운영자에게 주문 전부 허용   (order, *,      ALLOW)   구체성 2
  운영자에게 전부 삭제 거부   (*,     delete, DENY)    구체성 1

  운영자가 주문을 삭제하려 하면

    거부 우선     → 거부
    허용 우선     → 허용
    구체성 우선   → 허용 (order 쪽이 더 구체적)

  같은 두 줄에서 세 답이 나온다.
```

실무 예: AWS IAM(명시적 Deny 우선), 파일 시스템 ACL, 관리자 페이지 메뉴 권한 — 전부 "겹친 규칙을 어떻게 심판하나"의 문제다.

## 동작·원리

### 전체 흐름

```text
규칙 한 줄 Rule = (역할, 대상, 행위, ALLOW/DENY)   별표(*) = 전부
        │
        ▼
  decide(역할, 대상, 행위, 규칙들, Conflict, Fallback, Inheritance)
    ① chain()       역할 → 부모까지의 사슬 (가까운 것부터, 고리는 끊는다)
    ② applicable()  사슬을 훑으며 맞는 규칙 수집
                    (ALLOW_ONLY 면 물려받은 역할의 DENY 는 버림 — 자기 것은 남김)
    ③ 맞는 줄 0개  → Fallback 값으로 판정 (decidedBy = null)
    ④ MOST_SPECIFIC → 구체성 최고점 줄들만 남김
    ⑤ 우선 효과(거부 우선=DENY / 허용 우선=ALLOW)가 후보에 있으면 그 줄로 판정
        │
        ▼
  Decision(허용 여부, 판정 낸 규칙, 맞은 규칙 전부)
```

- 판정 결과가 boolean 하나가 아니라 **Decision 레코드**다 — "왜 그렇게 판정됐나"(decidedBy)와 "무엇이 겹쳤나"(matched)를 함께 남긴다. 권한 문의("왜 나는 안 되나요")에 답하려면 판정의 근거가 값이어야 한다.

### 규칙 1 — 매칭: 별표 아니면 글자 그대로 (`matches`)

**어떤 요구사항인가**: 규칙 한 줄이 이 요청에 맞는가.

예시 입력: 규칙 `(order, read, ALLOW)`, 요청 (order, readAll).

```text
별표(*)          → 무엇에나 맞는다
별표가 아니면    → equals — 글자 그대로 같아야 맞는다

(order, read)  vs 요청 (order, readAll)  → 안 맞는다  ← equals
(order, read)  vs 요청 (orders, read)    → 안 맞는다
```

- **접두사 일치(startsWith)로 맞추면**: read 권한이 readAll을 연다 — readAll은 **전체 내려받기**다. 조회 권한을 준 사람에게 전체 유출 권한이 딸려 간다.
- 변종 검증의 발견: 행위를 `startsWith`로 바꿔도 테스트가 통과했다(약한 테스트). 대상 쪽은 `order`/`orders` 짝으로 확인했는데 행위 쪽을 안 봤다. `read`/`readAll`을 넣으니 잡혔다 — 그리고 그 짝은 `export`/`exportAll`, `approve`/`approveAll`처럼 실제로 흔하다.

### 규칙 2 — 충돌 심판 (`Conflict` + `specificity`)

**어떤 요구사항인가**: 허용과 거부가 같은 요청에 둘 다 맞으면.

```text
구체성 점수: 대상이 별표 아니면 +2, 행위가 별표 아니면 +1  →  0~3

  (order, delete)  = 3     (order, *) = 2     (*, delete) = 1     (*, *) = 0

  대상이 행위보다 무겁다 — "주문 전부"(2) 와 "전부 삭제"(1) 가 겹치면 주문 쪽.
```

- **왜 대상 > 행위인가**: "주문에 관한 규칙"이 "삭제에 관한 규칙"보다 그 도메인에 가깝다고 본 설계 결정이다. 점수 2+1 체계라 (별표 조합이 다른) 두 줄의 점수가 같아질 일이 없게 대상·행위에 다른 가중치를 준다.
- **구체성이 같으면?** 거부가 이긴다 — 정해두지 않으면 **목록 순서가 판정을 정하고, 목록 순서는 조회 쿼리의 정렬**이다. DB 정렬이 바뀌는 날 권한 판정이 바뀐다.
- MOST_SPECIFIC은 최고점 줄들만 남긴 뒤 그 안에서 거부 우선으로 다시 심판한다 — 타이브레이크까지 명세에 적는 것이 이 챕터의 요점.

### 규칙 3 — 기본값 (`Fallback`)

**어떤 요구사항인가**: 아무 줄도 안 맞으면 열까 닫을까.

- DENY: 새 기능이 기본으로 막힌다(규칙을 넣어야 열림). ALLOW: 새 기능이 기본으로 열린다.
- 측정 2: 24요청 × 300회 = 7,200건에서 기본 거부 481 vs 기본 허용 495 — **차이가 딱 14건.** 규칙이 스무 줄만 있어도 거의 모든 요청이 어떤 줄엔가 맞기 때문이다. "기본은 거부냐 허용이냐"는 회의에서 제일 오래 얘기하고 **제일 적게 걸린다.**
- 대신 그 14건이 언제 생기나가 중요하다: **새 기능을 배포한 날과 규칙을 넣는 날 사이** — 그 틈에 무엇이 열려 있는지를 기본값이 정한다.

### 규칙 4 — 역할 상속 (`chain` + `Inheritance`)

**어떤 요구사항인가**: 사원 ← 운영자 ← 관리자처럼 역할이 역할을 물려받는다.

```text
chain("사원") = [사원, 운영자, 관리자]   ← 가까운 것부터

고리 방어: a 의 부모 b, b 의 부모 a 여도
  chain("a") = [a, b]  ← 이미 본 역할에서 멈춘다(seen 집합)
  안 막으면 설정 실수 하나가 무한 반복이 된다
```

- **ALLOW_ONLY의 함정**: 허용만 물려받는 규칙에서 **자기 역할의 거부까지 버리면** 거부를 아예 못 쓴다. 원본은 `inherited && ALLOW_ONLY && DENY`일 때만 버린다 — 물려받은 역할의 거부만 버리고 자기 것은 남긴다.
- 측정 3: 거부 우선 + 둘 다 물려받기 허용 **481** vs 거부 우선 + 허용만 물려받기 **3,102** (6.4배). "거부 우선"을 켜 놓고도 **거부가 후보에 아예 없어서** 아무 일도 안 한다 — 그리고 이 두 설정은 권한 화면의 **다른 탭**에 있다. 설정 둘이 다른 화면에서 서로를 무력화한다.
- 측정 4: 거부 규칙이 0%면 상속 갈래 두 값이 7,186으로 **같다.** 권한 설계 초기에는 허용만 적으니 이 설정이 죽어 있다가, 사고가 나서 거부를 붙이는 날 살아난다.

## 쓰이는 자료구조·알고리즘

- **부모 포인터 맵 + 방문 집합으로 상향 탐색** — `parents: Map<역할, 부모>`를 따라 `chain`이 가까운 역할부터 올라가고, `seen: LinkedHashSet`이 이미 본 역할에서 멈춰 고리(a↔b)를 끊는다. 그래프에서 방문 표시로 무한 반복을 막는 [algorithm/12-dfs](../../../algorithm/12-dfs/2-summary.md)의 같은 장치. 역할 계층이 단일 부모라 사슬(경로)이지만, 다중 상속이면 [data-structure/08-graph](../../../data-structure/08-graph/2-summary.md)의 탐색이 된다.
- **선형 필터** — `applicable`은 사슬의 역할마다 규칙 전체를 훑어 `roleId`가 같고 `matches`인 줄을 모은다. 비용은 규칙 수 × 사슬 길이. 규칙이 수만 줄이면 (역할, 대상)별로 미리 묶은 해시 인덱스가 필요하다 — [data-structure/05-hashmap](../../../data-structure/05-hashmap/2-summary.md).
- **와일드카드 매칭 = 별표 아니면 `equals`** — 접두사·정규식이 아니다. 대상을 `order/123`처럼 계층으로 넓히려면 접두사 매칭이 필요해지는데, 그때는 "어디까지 접두사인가"를 [data-structure/09-trie](../../../data-structure/09-trie/2-summary.md)처럼 경계(`/`) 단위로 정해야 `read`/`readAll` 사고를 피한다.
- **가중 점수 + 최댓값 좁히기** — `specificity` = 대상 비별표 2 + 행위 비별표 1. `decide`는 맞은 줄을 한 번 훑어 최고점을 구하고 다시 훑어 그 점수만 남긴다(두 패스). 가중치가 2·1이라 별표 조합이 다른 두 줄은 점수가 겹치지 않는다.
- **우선 효과 첫 매치 탐색** — 후보에서 이기는 효과(DENY 또는 ALLOW)를 가진 첫 줄을 찾아 `decidedBy`로 돌려준다. 동률에 거부가 하나라도 있으면 거부 — 방화벽의 첫 매치 규칙과 닮았지만 여기서는 순서가 아니라 효과가 기준이다.
- **근거를 담는 결과 레코드** — `Decision(allowed, decidedBy, matched)`. boolean 하나가 아니라 이긴 줄과 맞은 줄 전부를 값으로 남겨 "왜"에 답한다.
- **접근 제어 모델** — 이 챕터는 역할 기반(RBAC)에 역할 계층·거부 규칙을 얹은 형태다. 대상 인스턴스의 소유 관계까지 보는 ReBAC(관계 그래프 탐색 — Zanzibar류)는 [security/15-access-control-models](../../../security/15-access-control-models/2-summary.md)의 자리.
  - *RBAC / ReBAC*: 역할 기반 접근 제어 / 관계 기반 접근 제어. 전자는 "역할이 무엇을 할 수 있나", 후자는 "이 사용자와 이 객체가 어떤 관계인가"로 판정한다.

## 적용 — 풀어나가는 법

이런 문제를 받으면 규칙 문법(별표·역할)을 정하기 전에 **겹칠 때·안 맞을 때·물려받을 때의 메타 규칙 셋**을 먼저 값으로 꺼낸다.\
그 다음 매칭을 `equals`로 못 박고, 동률·고리 같은 타이브레이크를 명세에 적는다 — 안 적으면 조회 정렬이 대신 정한다.\
마지막으로 12조합을 같은 규칙·같은 요청으로 돌려 허용 건수를 센다. 설정 화면의 탭이 아니라 그 표가 "거부 우선이 실제로 일하는가"를 말해준다.\
아래는 원본 챕터가 시킨 과제 목록과, 실제로 돌린 측정이다.

### 문제 — 이 챕터가 시키는 것

주어진 말은 한 줄이다(원본 `Authorizer` javadoc 그대로).

```text
  "운영자는 주문을 볼 수 있고 삭제는 못 한다"
```

이 한 줄에 **정해지지 않은 것이 셋**이다(원문 그대로).

```text
  허용과 거부가 겹치면   거부가 이기나 허용이 이기나 더 구체적인 줄이 이기나
  아무 줄도 안 맞으면    거부인가 허용인가
  역할을 물려받을 때     거부도 물려받나 허용만 물려받나
```

README가 먼저 못 박는 장면은 이것이다.

```text
  운영자에게 주문 전부 허용   (order, *,      ALLOW)   구체성 2
  운영자에게 전부 삭제 거부   (*,     delete, DENY)    구체성 1

  운영자가 주문을 삭제하려 하면

    거부 우선     거부
    허용 우선     허용
    구체성 우선   허용
```

**"같은 두 줄에서 세 답이 나온다. 그리고 어느 답을 쓸지는 그 두 줄에 안 적혀 있다."**

과제(원본 README "채울 것"): `src/main/java/com/domain/authz/Authorizer.java` 의 **TODO 1~4**. `Rule` 은 계약이라 다 주어져 있다.

| TODO | 함수 | 시키는 것 |
|---|---|---|
| 1 | `matches(rule, resource, action)` | 그 규칙이 이 요청에 맞나. **별표는 무엇에나, 아니면 글자 그대로 같아야** |
| 2 | `specificity(rule)` | 얼마나 구체적인가(0~3). **대상이 행위보다 무겁다** |
| 3 | `applicable(roleId, resource, action, rules, inheritance)` | 맞는 규칙들. 허용만 물려받으면 **남의 역할의 거부만** 버린다 |
| 4 | `decide(…, conflict, fallback, inheritance)` | 허용인가 거부인가. 안 맞으면 기본값, **구체성 동률이면 거부** |

`chain` · `role` · `allowedCount` 는 이미 주어져 있다 — `chain` 은 가까운 역할부터 내고 **이미 본 역할에서 멈춘다**(고리 방지).

테스트가 못 박은 계약(`AuthorizerTest`):

- 같은 두 줄에서 **거부 우선=거부 / 허용 우선=허용 / 구체성 우선=허용**.
- 구체성 값: `(order, delete)` **3**, `(order, *)` **2**, `(*, delete)` **1**, `(*, *)` **0**.
- 구체성이 같으면 **거부가 이긴다** — 목록 순서를 뒤집어도 결과가 같다.
- `(order, *)` 규칙은 `orders` 요청에 **안 맞는다**. `read` 규칙은 `readAll` 을 **안 연다**.
- 아무 줄도 안 맞으면 기본값이고 이때 `byDefault()` 가 참, `decidedBy` 는 `null`.
- 맞는 줄이 하나라도 있으면 **기본값은 안 쓰인다**(기본 허용인데 거부 한 줄이 맞으면 거부).
- 허용만 물려받기면 **부모의 거부가 사라져** "거부 우선"이 아무 일도 안 한다.
- 그래도 **자기 역할의 거부는 남는다**(`applicable` 크기가 둘 다 2).
- `chain("사원") == [사원, 운영자, 관리자]`, 역할 고리(a↔b)가 있어도 **안 멈추지 않는다**(`[a, b]`).
- 자기 자신이 부모·빈 역할/대상/행위·`null` 효과는 전부 `IllegalArgumentException`.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

### 측정 — 별표가 갈림을 키운다

대상 6 × 행위 4 = 24요청, 300회(7,200건), 규칙 20줄:

| 별표 비율 | 거부 우선 | 허용 우선 | 구체성 우선 | 두 줄 이상 맞은 요청 |
|---|---|---|---|---|
| 0% | 2,070 | 2,864 | 2,070 | **1,460** |
| 20% | 1,806 | 5,781 | 3,538 | 5,593 |
| 80% | **37** | **7,200** | 2,946 | 7,200 |

- 별표가 많아지면 허용률이 0.5%(37/7,200)와 100%로 갈린다 — 같은 규칙, 다른 심판.
- 별표가 하나도 없어도 겹침이 1,460건 — 같은 대상·행위에 허용과 거부를 둘 다 적어놓은 것. **겹침은 별표 때문에 생기는 것이 아니라 별표가 키우는 것이다.**
- 측정 5: 별표도 거부도 없으면 여섯 조합이 통째로 같다(1,500번 비교에서 차이 0). 별표만 없애면 여전히 갈린다(3,300번 중 2,884) — 거부가 남아 있기 때문. **갈림의 뿌리는 거부 규칙이고, 별표는 확성기다.**

## 장애 시나리오와 대처

**1. 권한 판정은 통과했는데 남의 주문이 보인다 (IDOR/BOLA)**

- 현상: 운영자가 아닌 일반 회원이 `/orders/123`의 123을 124로 바꿔 다른 회원의 주문을 열람한다.
- 보이는 형태: 접근 로그에 같은 회원이 연속된 주문 번호를 훑은 흔적. 권한 로그에는 전부 `Decision(allowed=true, decidedBy=(order, read, ALLOW))`로 정상 판정이다.
- 원인: 이 모델의 `resource`는 **"order"라는 종류**이지 "order#124"라는 인스턴스가 아니다. `(회원, order, read, ALLOW)` 한 줄은 모든 주문에 맞는다. 종류 수준 판정만으로는 "내 것인가"를 못 본다(커리큘럼 ⚠ IDOR/BOLA — OWASP A01).
  - *IDOR/BOLA*: 식별자만 바꾸면 남의 객체에 닿는 취약점. 인증은 됐고 역할 권한도 맞는데 **객체 소유 검사**가 빠진 상태.
- 대처: 역할 판정 뒤에 **객체 수준 검사**를 두 번째 게이트로 둔다(주문의 소유자 = 요청자, 또는 관계 그래프 조회). 규칙 문법에 인스턴스를 넣으려 하면 줄 수가 폭발하므로, 종류 판정(이 챕터)과 소유 판정(ReBAC)을 계층으로 나눈다.

**2. 역할 하나를 등록했더니 사원이 관리자 권한을 전부 얻는다 (수직 권한 상승)**

- 현상: 새 역할을 추가한 배포 뒤 사원 계정으로 삭제·승인이 된다.
- 보이는 형태: `allowedCount("사원", …)`이 배포 전후로 관리자 수준까지 뛴다. `chain("사원")`을 찍어 보면 사슬 끝에 관리자가 있다.
- 원인: `role(roleId, parentId)`는 "누구의 규칙을 물려받나"를 인자 순서 하나로 정한다. 부모를 반대로 등록하거나 중간 역할의 부모를 잘못 잡으면 사슬이 위로 뻗어 상위 역할의 ALLOW가 전부 내려온다. 규칙은 한 줄도 안 바뀌었으므로 규칙 변경 이력에는 안 남는다.
- 대처: 역할 등록을 규칙 변경과 같은 등급의 **검토 대상**으로 둔다. 배포 전 검사로 역할마다 `chain`과 `allowedCount`를 스냅샷과 비교해 늘어난 역할을 표시한다. 역할 삭제의 반대 방향(자식이 조용히 권한을 잃거나 얻는 것)은 정답 11번 참고.

**3. 규칙이 수만 줄이 되자 요청마다 판정이 느려진다**

- 현상: 권한 판정이 API 응답 시간의 대부분을 차지한다.
- 보이는 형태: 프로파일에 `applicable`의 루프가 찍히고, 규칙 수와 사슬 길이에 비례해 지연이 는다. 규칙 20줄에서는 안 보이던 문제다.
- 원인: `applicable`이 사슬의 역할마다 **규칙 목록 전체**를 훑는다(규칙 수 × 사슬 길이). 목록을 그대로 넘기는 설계는 측정을 위한 것이지 운영 규모를 위한 것이 아니다.
- 대처: 규칙을 `(역할, 대상)` 또는 역할별로 미리 묶은 맵을 두고 사슬의 역할만 조회한다. 판정 결과는 입력(역할·대상·행위·규칙 버전)만으로 정해지므로 규칙 버전을 키에 넣어 캐시할 수 있다 — 규칙이 바뀌면 버전이 바뀌어 캐시가 자연히 무효가 된다.

### 경계·모서리 케이스 — 함정 → 올바른 처리

| 함정 | 무슨 일이 나나 | 올바른 처리 |
|---|---|---|
| 접두사 일치 | read가 readAll(전체 내려받기)을 연다 | 별표 아니면 equals — 글자 그대로 |
| 구체성 동률을 안 정함 | 목록 순서 = 조회 정렬이 판정을 정함 | 동률이면 거부가 이긴다고 명세에 박음 |
| ALLOW_ONLY가 자기 거부까지 버림 | 거부를 아예 못 쓴다 | 물려받은(inherited) 역할의 거부만 버림 |
| 역할 고리(a↔b)를 안 막음 | 설정 실수 하나가 무한 반복 | seen 집합 — 이미 본 역할에서 멈춤 |
| 자기 자신을 부모로 등록 | 의미 없는 사슬 | role()에서 IllegalArgumentException |
| 빈 역할·대상·행위·효과 null | 의미 없는 규칙 | Rule 생성자에서 전부 거부 |
| 아무 줄도 안 맞는데 decidedBy를 채움 | 기본값 판정과 규칙 판정을 구분 못 함 | decidedBy = null, byDefault()로 노출 |

## 핵심 문장
- 규칙 두 줄이 겹치면 답은 규칙에 없다 — 심판(Conflict) × 기본값(Fallback) × 상속(Inheritance)이라는 메타 규칙 세 축을 따로 정해야 하고, 그 조합이 판정을 0.5%에서 100%까지 가른다.
- 매칭은 별표 아니면 equals다 — 접두사 일치는 read 권한에 readAll(전체 유출)을 끼워 주고, 그 짝(export/exportAll)은 실무에 흔하다.
- 타이브레이크 없는 규칙은 조회 정렬이 판정한다 — 구체성 동률은 거부 우선, 구체성은 대상(2) > 행위(1)로 점수까지 명세에 적는다.
- 허용만 물려받기는 "거부 우선"을 조용히 무력화한다 — 거부가 후보에 없으면 어떤 심판도 거부를 못 고르고, 그 두 설정은 다른 화면 탭에 있다.
- 기본값은 제일 오래 회의하고 제일 적게 걸린다(7,200건 중 14건) — 진짜 쟁점은 새 기능 배포일과 규칙 등록일 사이의 틈이다.

### 용어 풀이

- **권한 판정(authorization)**: "이 역할이 이 대상에 이 행위를 해도 되나"를 규칙으로 정하는 것. 인증(authentication, 누구인지 확인)과 다르다.
- **규칙(Rule)**: (역할, 대상, 행위, 허용/거부) 한 줄. 별표(*)는 "전부".
- **Conflict(충돌 규칙)**: 허용·거부가 겹칠 때의 심판 — DENY_WINS / ALLOW_WINS / MOST_SPECIFIC.
- **Fallback(기본값)**: 아무 줄도 안 맞을 때의 답 — 기본 거부(안전) / 기본 허용(개방).
- **Inheritance(상속 범위)**: 부모 역할 규칙을 어디까지 물려받나 — ALL / ALLOW_ONLY(허용만).
- **구체성(specificity)**: 규칙이 얼마나 좁은가. 대상 비별표 +2, 행위 비별표 +1 → 0~3점.
- **타이브레이크(tie-break)**: 동률일 때의 결정 규칙. 안 정하면 목록 순서(=조회 정렬)가 대신 정한다.
- **역할 사슬(role chain)**: 역할 → 부모 → 부모의 부모. 가까운 것부터. 고리는 seen 집합으로 끊는다.
- **역할 고리(cycle)**: a의 부모가 b, b의 부모가 a인 설정 실수. 안 막으면 무한 반복.
- **Decision**: 판정 결과 레코드 — 허용 여부 + 판정 낸 규칙(decidedBy) + 맞은 규칙 전부(matched). "왜"에 답하는 값.
- **접두사 일치(startsWith)**: 앞글자만 같으면 맞다고 치는 것. read ⊃ readAll 사고의 원인 — 권한 매칭에서 금지.
