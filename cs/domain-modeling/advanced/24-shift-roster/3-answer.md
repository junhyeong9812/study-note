### A. 과제

#### 0. 규칙 한 줄이 안 말해주는 것

- 안 말해주는 자리 셋(원본 `Roster` javadoc 그대로):

```text
 안 말해준 것        가능한 읽기
 "주"          →  월요일부터인가 일요일부터인가
 야간 근무      →  시작일인가 종료일인가 나눠서인가
 "연속"        →  달력 날짜인가 실제로 쉰 시간인가
```

- "주": **정해야 한다.** `WeekStart.MONDAY`(근로기준법의 주) 또는 `WeekStart.SUNDAY`(달력의 주).
- 야간 근무: **정해야 한다.** `START_DAY`(근무표에 적힌 날) / `END_DAY`(퇴근한 날) / `SPLIT`(자정에서 잘라 나눔).
- "연속": **정해야 한다.** `BY_DATE`(근무가 걸친 달력 날짜) / `BY_GAP`(24시간 이상 쉬면 끊김).
- 자정 정각 종료: **그날 것이다.** `Shift.endDate()` 가 00:00 이면 하루를 뺀다.\
  테스트가 `evening.endDate() == MONDAY` 로 못 박았다(18:00~다음날 00:00 근무).
- 딱 24시간 휴식: **끊긴 쪽이다.** 규칙이 "24시간 **이상**"(`>= 24`)이라 BY_GAP 이 2일을 낸다.

> **경계값(boundary value)** — 규칙의 답이 바뀌는 바로 그 지점의 값.\
> 예: 여기서는 "자정 정각"과 "정확히 24시간"이 경계값이다. 1분만 달라도 답이 안 갈린다.

- 세 결정은 **독립이 아니다 — 서로 간섭한다.**\
  야간 근무를 종료일로 세면 그 8시간이 **주 경계를 넘어가** 초과근무가 다음 주로 옮겨간다.\
  달력으로 연속을 세면 밤에 끝난 근무 때문에 **하루가 더 붙는다.**
- enum 으로 올리면: **여섯 조합(주 시작 2 × 귀속 3)을 같은 근무표에 돌려 초과근무가 얼마나 벌어지는지 잴 수 있다.** 실측으로 137,040분(2,284시간) 벌어졌다.
- 하나 골라 구현하면: 그 선택이 코드에 숨어버린다.\
  그런데 이건 요금 계산이 아니라 **월급**이라, 나중에 바꾸면 "이미 지급한 수당"을 어떻게 할지가 남는다.

#### 1. TODO 1 — weekOf

정답 코드 (impl/Roster.java):

```java
if (weekStart == WeekStart.MONDAY) {
    return date.minusDays(date.getDayOfWeek().getValue() - 1L);
}
return date.minusDays(date.getDayOfWeek().getValue() % 7);
```

- `DayOfWeek.getValue()` 는 **월요일 1 … 일요일 7** 이다(ISO 순서).

> **ISO 요일 번호(DayOfWeek.getValue)** — 자바가 요일에 매긴 번호. 월요일이 1, 일요일이 7이다.\
> 예: `LocalDate.of(2026,3,29)` 는 일요일이라 7, `2026-03-30` 은 월요일이라 1.

- 월요일 시작: **요일번호에서 1을 빼고 그만큼 되돌린다.**\
  월요일이면 `1-1=0` 일 되돌림(자기 자신), 일요일이면 `7-1=6` 일 되돌림.
- 일요일 시작에서 `% 7` 이 하는 일: **일요일(7)을 0으로 만든다.**\
  7 % 7 = 0 이라 되돌리지 않고 자기 자신이 주의 첫날이 된다. 월요일(1)은 1일, 토요일(6)은 6일 되돌린다.
- 손계산:

```text
 날짜         요일  값   MONDAY: date-(값-1)      SUNDAY: date-(값%7)
 2026-03-29   일    7    29 - 6  = 03-23          29 - 0 = 03-29  ← 자기 자신
 2026-03-30   월    1    30 - 0  = 03-30          30 - 1 = 03-29
 2026-03-28   토    6    28 - 5  = 03-23          28 - 6 = 03-22
```

- 일요일을 앞주로 보내면: **일요일 근무가 매번 앞주 초과근무가 된다.**\
  앞주는 이미 월~토로 차 있으니, 일요일 9시간이 통째로 상한을 넘는 쪽에 얹힌다.
- 2026-03-29(일): 월요일 기준 **3/23**, 일요일 기준 **3/29 자신**(테스트 `sundayBelongsToTwoWeeks`).
- 2026-03-30(월): 월요일 기준 **3/30**, 일요일 기준 **3/29**.
- 같은 하루가 다른 주에 속하는 것이 치명적인 이유: **초과근무는 "주 단위 합계 − 상한"이라 주가 바뀌면 합계가 바뀐다.**\
  근무 시간의 총합은 그대로인데 **초과근무만 갈린다** — 그리고 초과근무에만 가산 수당이 붙는다.
- `dayOfWeek(date)` 와의 차이: 그건 **그냥 그 날짜의 요일**이다.\
  "3/29는 일요일"이라는 사실은 주를 월요일부터 끊든 일요일부터 끊든 안 변한다 — 달력의 사실이지 정책이 아니다.

```text

 END_DAY     {3/30: 480}                     퇴근한 날
```


- 0분짜리 근무일이 망가뜨리는 것: **연속 근무 일수.**\

> **0분짜리 근무일(phantom workday)** — 실제로는 일하지 않았는데 계산 실수로 생겨난 근무일.\
> 예: 18:00~24:00 근무의 종료일을 다음 날로 보면, 다음 날에 0분이 기록되고 그 날도 "일한 날"로 세어진다.

  `max(0, ...)` 이 없으면 상한 미달인 주가 **음수 초과근무**를 내고, 합산에서 다른 주의 초과를 깎는다.

> 예: 3/16 주를 먼저 넣고 3/2 주를 나중에 넣어도, 꺼낼 때는 3/2 → 3/16 순서로 나온다.

> **merge(병합)** — 키가 없으면 값을 넣고, 이미 있으면 두 값을 합치는 규칙으로 갱신하는 맵 연산.\
> 예: `byWeek.merge(3/23주, 480, Long::sum)` 은 3/23 주에 이미 2,700분이 있으면 3,180분으로 만든다.

- 손계산 — 월~금 45시간 + 3/29(일) 밤 근무 8시간, 월요일 시작, 상한 40시간:

```text
 START_DAY      45 + 8 = 53h → 13h      (없음)           13시간
 END_DAY        45     = 45h →  5h      8h →  0h          5시간
 SPLIT          45 + 2 = 47h →  7h      6h →  0h          7시간

 같은 8시간짜리 근무 하나가 초과근무를 13 / 5 / 7 시간으로 가른다.
```

```text
   3/23 주 ───────────────────────────┤├─────── 3/30 주

                       END_DAY  : 8h 전부 오른쪽
```

- 초과근무만 갈리고 총 근무 시간은 안 갈리는 이유: **귀속은 같은 시간을 옮겨 담을 뿐 늘리거나 줄이지 않는다.**\

> **초과근무(overtime)** — 한 주에 잡힌 근무 시간이 상한을 넘은 부분.\
> 예: 상한 40시간에 53시간이면 13시간이 초과근무다. 40시간 미만이면 음수가 아니라 0이다.

- 근무가 없으면: **빈 목록.** 테스트 `weeks(List.of(), MONDAY, SPLIT).isEmpty()`.

#### 4. TODO 4 — longestRun

정답 코드 (앞부분 — 빈 목록과 정렬):

```java
if (shifts.isEmpty()) {
    return 0;
}
List<Shift> sorted = new ArrayList<>(shifts);
sorted.sort(Comparator.comparing(Shift::startsAt).thenComparing(Shift::id));
```

BY_DATE:

```java
Set<LocalDate> worked = new LinkedHashSet<>();
for (Shift shift : sorted) {
    for (LocalDate date = shift.startDate();
            !date.isAfter(shift.endDate());
            date = date.plusDays(1)) {
        worked.add(date);
    }
}
List<LocalDate> days = new ArrayList<>(worked);
days.sort(Comparator.naturalOrder());
int best = 1;
int run = 1;
for (int i = 1; i < days.size(); i++) {
    run = ChronoUnit.DAYS.between(days.get(i - 1), days.get(i)) == 1 ? run + 1 : 1;
    best = Math.max(best, run);
}
return best;
```

BY_GAP:

```java
int best = 0;
LocalDate groupStart = sorted.get(0).startDate();
LocalDate groupEnd = sorted.get(0).endDate();
LocalDateTime lastEnd = sorted.get(0).endsAt();
for (int i = 1; i < sorted.size(); i++) {
    Shift shift = sorted.get(i);
    if (Duration.between(lastEnd, shift.startsAt()).toHours() >= 24) {
        best = Math.max(best, spanDays(groupStart, groupEnd));
        groupStart = shift.startDate();
        groupEnd = shift.endDate();
    } else if (shift.endDate().isAfter(groupEnd)) {
        groupEnd = shift.endDate();
    }
    if (shift.endsAt().isAfter(lastEnd)) {
        lastEnd = shift.endsAt();
    }
}
return Math.max(best, spanDays(groupStart, groupEnd));
```

- BY_DATE 가 하는 일: **근무가 걸친 달력 날짜를 전부 집합에 모으고**, 정렬한 뒤 **하루씩 붙어 있는 구간의 최대 길이**를 잰다.\
  근무 사이에 얼마나 쉬었는지는 아예 안 본다.
- BY_GAP 이 하는 일: **직전까지의 끝에서 다음 근무 시작까지가 24시간 이상이면 묶음을 끊고**, 끊기지 않은 묶음이 **걸친 날 수**(`spanDays`)를 잰다.

> **휴식 간격(gap)** — 한 근무가 끝난 시각부터 다음 근무가 시작하는 시각까지의 길이.\
> 예: 월 18:00 퇴근, 화 20:00 출근이면 gap 은 26시간이다.

> **스팬 일수(span)** — 묶음의 첫날부터 마지막 날까지를 **양끝 포함**으로 센 날 수.\
> 예: 화요일에 시작해 수요일에 끝난 묶음은 `수 - 화 + 1 = 2` 일이다.

- 정렬이 필요한 이유: **BY_GAP 이 "앞 근무 → 뒤 근무" 순서로 간격을 재기 때문**이다.\
  목록이 뒤죽박죽이면 간격이 음수가 되어 끊김 판정이 무너진다.
- 시작 시각 하나로 모자란 이유: **같은 시각에 시작한 근무가 둘이면 순서가 안 정해진다.**\
  그러면 같은 입력에 실행마다 다른 답이 나올 수 있다. `thenComparing(Shift::id)` 가 그 동률을 깬다.

> **동률 깨기(tie-break)** — 정렬 기준이 같을 때 순서를 확정하기 위해 쓰는 두 번째 기준.\
> 예: 시작 시각이 똑같은 근무 두 건은 근무 번호(id) 순으로 세운다. 그래야 결과가 항상 같다.

- "제일 늦은 끝"(`lastEnd`)을 들고 다녀야 하는 이유: **근무가 겹치거나 포함될 수 있기 때문**이다.\
  긴 근무 뒤에 그 안에 들어가는 짧은 근무가 오면, "직전 근무의 끝"으로 재면 간격이 실제보다 커져서 없는 끊김이 생긴다.\
  (원본에 근거 없음 — 내 추론: 테스트에는 겹치는 근무 케이스가 없다. 코드가 `Math.max` 로 `lastEnd` 를 갱신하는 것이 근거다.)
- 손계산 — 월 09:00~18:00 + 화 20:00~수 04:00:

```text
 BY_DATE  걸친 날 = {월} ∪ {화, 수} = 월 화 수  → 붙어 있다 → 3일
 BY_GAP   gap = 월 18:00 → 화 20:00 = 26시간 ≥ 24 → 끊김
          묶음1 = 월~월 = 1일   묶음2 = 화~수 = 2일   → 최장 2일

        월                      화              수
   09 ▓▓▓▓ 18 ┄┄┄┄┄ 26시간 휴식 ┄┄┄┄ 20 ▓▓▓▓▓▓▓▓▓▓ 04
        ↑ 하루 일함              ↑ 실제로는 26시간 쉬었다
   달력으로는 월·화·수가 다 차서 "사흘 연속"으로 보인다
```

- 실제로 쉰 시간: **26시간**.
- 밤 근무 3연속(월·화·수 22:00~06:00)에서 같아지는 이유: **쉬는 시간이 16시간씩이라 안 끊기고**(06:00→22:00), **달력으로도 월·화·수·목이 다 차 있다.**\
  둘 다 **4일**. "야간 근무만 하는 사람에게는 이 갈래가 안 보인다."
- 하루를 통째로 쉬면 같아지는 이유: **달력도 안 붙고(월·수) 간격도 47시간이라 둘 다 끊긴다.**\
  둘 다 **1일**.
- 두 규칙이 갈리는 경우: **"쉬긴 쉬었는데 달력이 붙어 있는 경우"뿐이다**(테스트 주석 원문).\
  즉 밤을 넘긴 근무가 다음 날 새벽까지 이어져 달력을 채우는 모양.
- 손계산 — 딱 24시간 휴식(월 09:00~18:00, 화 18:00~수 02:00):

```text
 gap = 월 18:00 → 화 18:00 = 정확히 24시간
 조건이 >= 24 이므로 끊긴다

 BY_GAP   묶음1 = 월~월 1일   묶음2 = 화~수 2일   → 2일
 BY_DATE  {월} ∪ {화, 수} = 월 화 수 붙어 있음    → 3일
```

- 근무가 없으면 0: **1을 내면 "아무도 안 일한 주"가 연속 1일로 잡힌다**(테스트 주석 원문).\
  `best` 초기값이 1이라 빈 목록을 앞에서 따로 막지 않으면 1이 새어 나온다.

### B. 개념

#### 5. 함정 (README)

- 넷: ① **자정 정각에 끝난 근무를 다음 날 것으로 보는 것** ② **일요일 시작에서 일요일을 앞주로 보내는 것** ③ **근무가 없는 주를 0으로 채우는 것** ④ **딱 24시간 쉰 사람을 어느 쪽으로 놓을지 안 정하는 것**.
- 자정 정각을 다음 날로 보면: **0분짜리 근무일이 생기고, 그 하루가 연속 근무 일수를 하나 늘린다.**
- 일요일을 앞주로 보내면: **일요일 근무가 매번 앞주 초과근무가 된다.**\
  한 번의 실수가 아니라 **매주 반복되는 계통 오차**다.
- 근무 없는 주를 0으로 채우면: **"몇 주를 일했나"가 안 맞는다.**
- 딱 24시간을 안 정하는 것이 특히 위험한 이유: **근무표를 짜는 쪽은 정확히 24시간을 노린다**(README 원문).\
  법정 휴식을 딱 맞춰 짜므로, 실무 데이터가 그 경계에 몰린다 — 드문 케이스가 아니라 **가장 흔한 케이스**다.
- 예외 없이 조용히 틀린 값이 나오는 것: **넷 다.**\
  모두 `IllegalArgumentException` 을 안 던지고 **숫자만 틀리게 나온다** — 연속 일수가 1 늘고, 초과근무가 옮겨가고, 주 수가 늘고, 연속 일수가 안 끊긴다.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 결과만 틀린 실패.\
> 예: 연속 근무가 6일인 사람이 7일로 잡혀 경고가 뜨는데, 코드는 아무 예외도 안 낸다.

#### 6. 측정 하나 — 주 4일인데 달력으로 세면 6일 연속을 넘긴다

- 주 4일 + 달력으로: **182 / 300명**이 6일 연속을 넘긴다.
- 같은 사람들을 쉰 시간으로: **6 / 300명**.
- 벌어지는 이유: **야간 근무 하나가 이틀을 채우기 때문**이다.\
  화 20:00~수 04:00 은 화요일과 수요일을 **둘 다** 근무일로 만든다.
- 실제로 쉰 시간: **26시간일 수 있다**(하루 일하고 26시간 휴식).
- 주당 근무일이 늘수록 가까워지는 이유: **근무가 빽빽해지면 24시간 이상 쉴 틈 자체가 사라진다.**\
  주 7일이면 달력 300/300, 쉰 시간으로도 299/300 이라 거의 같아진다.

```text
 주당 근무일   달력으로   쉰 시간으로   최장 연속 합계(달력 / 쉰 시간)
    4 일       182/300      6/300        2,151 /  1,239
    5 일       293/300     49/300        3,181 /  1,647
    6 일       300/300    215/300        5,912 /  2,187
    7 일       300/300    299/300       25,289 /  3,437
```

- 그대로 두면 생기는 일: **주 4일 근무자의 3분의 2가 "6일 연속 초과"로 잡힌다.**\
  실제로 법을 어긴 사람은 거의 없는데 경고가 쏟아진다 — 그러면 **경고를 아무도 안 보게 된다.** (원본에 근거 없음 — 내 추론: README 는 182/300 이라는 수치까지만 말한다.)

#### 7. 측정 둘 — 야간 근무가 없으면 세 귀속 규칙이 완전히 같다

- 야간 0%에서 같은 이유: **귀속 규칙은 `crossesMidnight()` 이 참일 때만 갈라진다.**\
  09:00~18:00 근무는 시작일 = 종료일이라 세 규칙이 같은 한 칸을 낸다.
- 개발할 때 만드는 근무표: **대개 09:00~18:00 이다**(README 원문).\
  그래서 세 규칙 중 아무거나 골라 구현해도 테스트가 다 통과한다 — **갈래가 눈에 안 보인다.**
- 야간 비율이 오를수록 초과근무가 주는 이유: **야간 근무가 8시간이고 주간이 9시간이기 때문**이다(테스트 주석 원문).\
  **착시가 아니라 실제**다 — 야간이 늘면 총 근무 시간 자체가 준다.
- 야간 100%: **1,728,000 / 1,602,720 / 1,634,040분**(시작일 / 종료일 / 나눠서).
- 이 표가 말하는 것: **테스트 데이터에 야간 근무를 반드시 섞어야 한다.**\
  주간 근무만으로 만든 데이터는 귀속 갈래를 **한 건도** 드러내지 못한다.

#### 8. 측정 셋 — 야간이 없어도 주 시작 갈래는 그대로 남는다

- 야간 0%인데 900건이 어긋나는 이유: **비교 대상이 여섯 조합이고, 그 여섯에는 주 시작 2가지가 들어 있다.**\
  야간 규칙 셋은 같은 값을 내지만 **주 시작이 다르면 주말 근무가 다른 주로 간다.**
- 같은 데이터에서 야간 규칙 셋만 비교하면 0건: **야간 근무가 없으니 세 규칙이 완전히 같은 값**이다(#7).
- "다른 조건에서 나타난다": **각 갈래가 보이려면 필요한 데이터 조건이 서로 다르다**는 뜻.
- 야간 귀속 갈래가 보이려면: **야간 근무(밤을 넘긴 근무)가 있어야 한다.**
- 주 시작 갈래가 보이려면: **주말에 일하기만 하면 된다.**
- 절반만 덮이는 이유: **야간 근무를 넣는 것은 귀속 갈래만 켠다.**\
  주말 근무가 없으면 주 시작 갈래는 여전히 0건이다 — 두 조건을 **따로** 챙겨야 한다.

> **갈래(divergence)** — 같은 입력에 대해 규칙 선택이 다른 답을 내는 자리.\
> 예: 여기서는 "주 시작"과 "야간 귀속"이 두 개의 갈래고, 각각을 드러내는 데이터 조건이 다르다.

- 근무 요일을 무작위로 뽑는 이유: **요일을 고정하면 주 경계에 닿는 근무가 안 생긴다**(테스트 주석 원문).\
  예를 들어 월~금만 고정하면 주말 근무가 없어 **주 시작 갈래도 야간 귀속 갈래도 안 보인다.**

#### 9. 측정 넷 — 여섯 조합의 초과근무가 2,284시간 벌어진다

- 여섯 조합: **주 시작 2가지 × 야간 귀속 3가지 = 6.**

```text
 조합                     초과근무(분)   초과한 주
 월요일 + 시작일로         2,638,380      3,600   ← 제일 많다
 월요일 + 종료일로         2,602,860      3,599
 월요일 + 나눠서           2,611,740      3,600
 일요일 + 시작일로         2,501,880      3,600
 일요일 + 종료일로         2,509,980      3,438   ← 초과한 주 제일 적다
 일요일 + 나눠서           2,501,340      3,442   ← 초과근무 제일 적다
```

- 최다 = **월요일 + 시작일로(2,638,380분)**, 최소 = **일요일 + 나눠서(2,501,340분)**.\
  차이 = **137,040분** = 2,284시간.
- 한 사람당: **7.6시간**(137,040분 ÷ 300명 ÷ 60).
- "초과한 주"의 차이: **3,600 − 3,438 = 162주.**
- 둘을 따로 봐야 하는 이유: **분(分)은 수당의 양이고, 주 수는 수당이 붙은 사건의 수**다.\
  "초과근무 총량은 비슷한데 초과한 주 수가 162주 다르다"는 건, 어떤 조합에서는 **자잘하게 여러 주에 걸쳐** 초과가 잡힌다는 뜻이다. 수당 계산식이 주 단위 가산이면 결과가 또 달라진다. (원본에 근거 없음 — 내 추론: README 는 두 수치를 나란히 보여줄 뿐 해석을 안 준다.)
- 개발자가 골라도 되는가: **안 된다.**\
  이건 성능 튜닝이 아니라 **월급 계산 규칙**이고, 300명 기준 한 사람당 7.6시간의 수당이 걸려 있다.\
  근로계약서·취업규칙에 적혀 있어야 하고, 없으면 **코드 기본값이 아니라 회사가 정할 일**이다.

#### 10. 변종 검증에서 고친 것

- 원시 종료 날짜를 보면: **18:00~24:00 근무가 "두 날에 걸친 것"으로 잡힌다.**\
  원시 종료 시각은 다음 날 00:00 이라 `endsAt.toLocalDate()` 가 다음 날을 낸다.
- "0분이 앞날 값을 덮어썼다"의 정체: **`Map.put` 은 같은 키면 덮어쓴다.**

```text
 잘못된 판정에서 SPLIT 이 하는 일 (18:00 ~ 다음날 00:00, 360분)

 midnight = 다음 날 00:00
 put(시작일,   18:00 → 00:00 = 360분)      맵: {월: 360}
 put(종료일,   00:00 → 00:00 =   0분)      ← 보정 전 종료일이 "다음 날"

 그런데 endDate() 는 보정돼서 "그날"을 낸다
 → 같은 키(월)에 0 을 put → 맵: {월: 0}     ★ 앞날 360분이 사라진다
```

> **덮어쓰기(put)** — 맵에 같은 키로 값을 넣으면 이전 값이 지워지고 새 값이 들어가는 것.\
> 예: `{월: 360}` 에 `put(월, 0)` 하면 `{월: 0}` 이 된다. 더해지지 않는다.

- 고친 방법: **`crossesMidnight()` 이 보정한 `endDate()` 를 보도록 했다.**

```java
public boolean crossesMidnight() {
    return !startDate().equals(endDate());   // 보정된 endDate 를 본다
}
```

  그러면 18:00~24:00 은 `startDate == endDate` 라 **안 걸친 것**이 되고, SPLIT 도 `{그날: 360}` 한 칸을 낸다.
- 경계 테스트가 없으면 `>= 24` 를 `> 24` 로 바꿔도 통과하는 이유: **딱 24시간인 입력이 하나도 없었기 때문**이다.\
  25시간이나 26시간 휴식만 있으면 두 부등호가 같은 답을 낸다.

> **경계 테스트(boundary test)** — 규칙의 답이 바뀌는 바로 그 값을 입력으로 넣어보는 테스트.\
> 예: "24시간 이상 쉬면 끊긴다"면 23시간·**24시간**·25시간을 다 넣어봐야 한다. 24시간이 빠지면 부등호 실수를 못 잡는다.

- "그 경계가 이 규칙의 전부": **`>=` 냐 `>` 냐가 이 규칙이 결정하는 유일한 것**이라는 뜻.\
  나머지 구간(23시간, 26시간)에서는 두 판이 같은 답을 내므로, **경계를 안 보면 규칙을 아예 안 본 것**이다.
- 두 사건의 교훈: **테스트는 "정상 케이스"가 아니라 "답이 갈리는 자리"에 걸어야 한다.**\
  자정 정각·정확히 24시간처럼 **실무 데이터가 몰리는 경계**가 그 자리다.

#### 11. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 근로계약서에 적혀 있나: 대개 **안 적혀 있다.** 계약서는 "주 40시간"까지만 말하고, 야간 근무를 어느 날로 세는지는 안 적는다.\
  그러면 그 결정이 **급여 시스템 코드의 기본값**으로 내려간다 — 그게 이 박스가 경고하는 상황이다.\
  코드가 `NightAttribution` 을 **인자로 받게** 설계된 것은 "이 결정의 주인은 여기가 아니다"라고 표시한 것이다. (원본에 근거 없음 — 내 추론)
- 주 시작 요일을 바꾸면 이미 지급한 수당: 소급하면 **어떤 주는 수당이 늘고 어떤 주는 준다.**\
  측정의 3,600 vs 3,438 주가 그 규모다 — 162주에서 수당 유무가 뒤집힌다.\
  실무적으로는 **소급하지 않고 변경 시점 이후부터 적용**하고, 그러려면 주 시작 규칙에 **유효기간**이 필요하다. 지금 코드는 규칙을 호출할 때마다 받으므로 "언제부터 이 규칙"을 담을 자리가 없다. (원본에 근거 없음 — 내 추론)
- 두 화면이 같이 있으면: **같은 사람이 한 화면에서는 3일 연속, 다른 화면에서는 2일 연속으로 보인다.**\
  측정 하나가 그 규모다 — 주 4일 근무자 300명 중 **182명 vs 6명**이 "6일 초과"로 잡힌다.\
  이건 버그 신고가 되고, 어느 쪽이 맞는지 아무도 답을 못 한다. **화면을 두 개 두려면 규칙 이름을 화면에 같이 띄워야 한다**("달력 기준" / "휴식 기준"). (원본에 근거 없음 — 내 추론)
- 시차가 있는 지역의 자정: 이 코드는 `LocalDateTime`(시간대 없는 벽시계 시각)이라 **문제가 안 드러난다.**\
  실제로는 **근무지의 자정**인지 **본사의 자정**인지를 정해야 하고, 서머타임이 있으면 "하루"가 23시간이나 25시간이 되어 SPLIT 의 조각 길이가 달라진다.\
  근무 기록은 보통 **근무지 기준**이 맞다 — 그러려면 `ZonedDateTime` 이 필요하다. (원본에 근거 없음 — 내 추론)

> **LocalDateTime** — 시간대 없이 "날짜 + 벽시계 시각"만 담는 자바 타입.\
> 예: `2026-03-29T22:00` 은 서울의 22시인지 뉴욕의 22시인지 스스로는 모른다.

#### 12. 연결

- 01-parking-fee 와 같은 것: 둘 다 **"말로 된 규칙이 안 정해준 자리"를 값으로 올리고, 두 해석의 답이 얼마나 갈리는지 잰다.**\
  다른 것: 주차 요금은 **건수**(1,000건 중 444건이 갈림)를 셌고, 여기는 **금액의 벌어짐**(137,040분)과 **사건 수**(162주)를 잰다.\
  그리고 여기는 갈래가 **세 개고 서로 간섭한다** — 조합이 6가지로 늘어난다.
- "하루의 기준"과 "주의 기준": **같은 종류다.**\
  둘 다 "달력의 경계로 자르나, 시작 시각에서 재나"라는 같은 모양이다 — 주차는 자정 vs 입차 후 24시간, 여기는 월요일 vs 일요일(그리고 BY_DATE vs BY_GAP).
- enum vs record 정책값: **enum 은 "이름 붙은 몇 가지 중 하나"**, **record 는 "여러 값의 묶음"** 이다.\
  주차 요금은 숫자(무료 분·단위 요금)가 많아 record 가 맞고, 여기는 선택지가 유한한 이름들이라 enum 이 맞다.\
  enum 은 **전부 돌려보기(`values()` 순회)** 가 쉬워서 측정 코드가 여섯 조합을 그대로 돈다.
- 자정 정각 경계와 같은 자리: **04-hotel-booking**(체크아웃 날이 포함인가), **08-meeting-slot**(구간이 맞닿는 것과 겹치는 것) — 전부 "끝이 포함인가"가 답을 가른다. (원본에 근거 없음 — 내 추론)
- 실무 관행과의 대응: **조합 테스트(pairwise/matrix testing)** 와 **실데이터를 닮은 테스트 데이터**.\
  갈래마다 켜지는 조건이 다르므로, "야간 근무 하나 넣어봤다" 같은 단일 샘플이 아니라 **주말 근무·야간 근무·딱 24시간 휴식을 각각 포함한 데이터 세트**가 필요하다.
