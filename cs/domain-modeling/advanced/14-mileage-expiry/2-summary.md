## 한눈에 — 쉽게 말하면

**마일리지 소멸 = 유통기한이 제각각인 우유들.**

- 냉장고에 우유가 두 팩 있다. 하나는 유통기한이 내일, 하나는 다음 주. **어느 팩부터 마시나?** 당연히 내일 것부터 — 안 그러면 내일 것이 상해서 버려진다.
- 항공 마일리지·포인트가 똑같은 구조다. 적립할 때마다 **적립분(lot)마다 소멸일이 따로** 붙는다. 나중에 쌓인 것이 먼저 소멸할 수도 있다(이벤트 포인트는 3개월, 일반 적립은 1년처럼).
- 핵심 반전: **오늘 잔액은 어느 규칙이든 똑같다.** 1,500 포인트를 어느 적립분에서 뺐든 남은 합계는 같으니까. 갈리는 것은 **그 잔액이 언제 사라지느냐**다. 그래서 "잔액만 맞추는" 구현은 오늘 맞고 **내년에 틀린다**.
  - *적립분(lot)*: 한 번의 적립으로 생긴 덩어리. 금액 + 소멸일을 함께 들고 있다.

```text
  e1  1/1 적립 1,000  소멸 2027-01-01
  e2  6/1 적립 2,000  소멸 2026-09-01   ← 나중에 쌓였는데 먼저 소멸
  s1  7/1 사용 1,500

    먼저 쌓인 것부터 빼면    e1에서 1,000 + e2에서 500  →  e1: 0,     e2: 1,500
    먼저 소멸할 것부터 빼면  e2에서 1,500               →  e1: 1,000, e2: 500

  잔액은 둘 다 1,500. 그런데 9/1에 e2가 소멸하면 → 1,500 vs 500이 사라진다
```

실무 예: 항공 마일리지, 카드 포인트, 쇼핑몰 적립금, 상품권 잔액.

## 전체 흐름

```text
사건(MileageEvent) 세 종류가 한 줄기로 흐른다:
  EARN(적립, 소멸일 붙음) / SPEND(사용) / REFUND(사용 취소, 원래 사용을 가리킴)

MileageLedger = 사건 목록 (생성 시 날짜 순, 같은 날이면 번호 순으로 정렬
                — 안 하면 사용이 적립보다 먼저 처리돼 잔액이 음수가 된다)

lotsOn(날짜, 스위치 3개) — 그 날까지 사건을 재생(replay)해 남은 적립분들을 계산
  EARN   → 새 lot 추가
  SPEND  → 규칙 순서대로 살아 있는 lot에서 뺀다 + "어느 lot에서 얼마 뺐는지" 기록
  REFUND → 규칙이 정한 곳으로 되돌린다

세 개의 스위치:
  SpendOrder      OLDEST_FIRST(먼저 쌓인 것부터) / EXPIRING_FIRST(먼저 소멸할 것부터)
  RefundTarget    ORIGINAL_LOT(원래 뺀 곳으로) / NEW_LOT(취소한 날 새로 쌓음, 소멸 +1년)
  ExpiryBoundary  EXPIRED_ON_DATE(소멸일에 이미 없다) / ALIVE_ON_DATE(당일까지 쓸 수 있다)
```

- *재생(replay)*: 현재 상태를 저장해두지 않고, 사건 기록을 처음부터 다시 흘려보내 상태를 계산하는 방식. 이벤트 소싱의 기본 발상이다.

## 규칙 1 — 쓸 때 어느 적립분에서 빼나 (SpendOrder)

**어떤 요구사항인가**: "1,500 포인트 사용"이라는 요청은 **어느 적립분에서 뺄지**를 말하지 않는다.

**예시 손계산**: 위 그림 그대로. 잔액은 똑같이 1,500인데 적립분 모양이 다르고, 9/1에 e2가 소멸하는 순간 —

```text
  OLDEST_FIRST    e2에 1,500 남아 있었음  →  1,500 소멸, 잔액 0
  EXPIRING_FIRST  e2에   500 남아 있었음  →    500 소멸, 잔액 1,000
```

**측정 결과** (무작위 장부 200개, 소멸 기간 90~729일):

| 취소 비율 | 먼저 쌓인 것부터 | 먼저 소멸할 것부터 |
|---|---|---|
| 0 % | **2,784,300** | **234,500** |
| 10 % | 3,800,400 | 946,400 |
| 25 % | 5,557,300 | 3,663,400 |

- 취소가 없을 때 **12배 차이**. 먼저 쌓인 것부터 쓰면 곧 사라질 적립분을 안 건드리고 놔둬서 그대로 소멸한다.
- **"선입선출(FIFO)"은 재고에서는 맞는 말인데, 소멸이 있는 자산에서는 반대다** — 고객에게 유리한 것은 "먼저 소멸할 것부터"다.
- 잔액은 200개 중 199개에서 갈렸는데 **적립분 모양은 200개 전부** 갈렸다 — 합계를 맞춰놓고 소멸일이 틀리는 것이 이 문제의 요점이다.

**왜 이렇게 모델링했나**: 그래서 상태를 "잔액 하나"가 아니라 **적립분 목록(Lot: 남은 금액 + 소멸일)** 으로 들고 있어야 한다. 잔액 하나로 뭉개면 "언제 사라지나"라는 질문에 답할 수 없다.

## 규칙 2 — 취소하면 어디로 되돌리나 (RefundTarget)

**어떤 요구사항인가**: 7/1의 사용 1,500을 8/1에 취소하면, 그 1,500은 **어느 소멸일을 가진 포인트로** 돌아오나.

**예시 손계산** (OLDEST_FIRST로 e1에서 1,000, e2에서 500을 뺐던 상태):

```text
  ORIGINAL_LOT  e1 +1,000(소멸 2027-01-01), e2 +500(소멸 2026-09-01)
  NEW_LOT       r1 1,500 (취소일 + 1년 = 소멸 2027-08-01)

  8/1 잔액: 둘 다 3,000  ← 또 같다!
  9/1 (e2 소멸 후): 1,000 vs 1,500  ← 되돌아간 500이 e2와 함께 사라졌는가
```

**측정 결과**: 취소가 없는 장부 200개에서 두 규칙이 **한 번도 안 갈리고**, 취소 25%를 넣으면 **200개 전부** 갈린다. **이 갈래는 취소가 들어오는 날 시작된다** — 그날까지는 어느 쪽으로 짜두든 테스트가 다 통과한다. 그리고 예제에는 취소가 잘 안 들어간다. 이야기가 길어지니까.

**왜 이렇게 모델링했나**: ORIGINAL_LOT으로 되돌리려면 **사용할 때 "어느 lot에서 얼마 뺐는지"를 적어둬야** 한다(takenBySpend 기록). 안 적어두면 취소할 때 되돌릴 곳을 모른다 — README 함정 세 번째.

## 규칙 3 — 소멸일 당일은 (ExpiryBoundary)

**예시**: 1/1 적립, 7/1 소멸이면 —

```text
  날짜      EXPIRED_ON_DATE   ALIVE_ON_DATE
  6/30         1,000             1,000
  7/1              0             1,000     ← 딱 하루만 갈린다
  7/2              0                 0
```

"7월 1일에 소멸합니다"라는 안내문은 **그날 쓸 수 있는지를 안 알려준다**. 그리고 소멸 처리는 대개 밤에 배치로 도는데, **그 배치가 몇 시에 도느냐가 이 하루를 어느 쪽으로 만드는지를 정한다**.

## 경계·모서리 케이스 — 함정 → 올바른 처리

| 함정 | 올바른 처리 |
|---|---|
| 잔액 하나만 관리 | 적립분(lot) 목록으로 — 오늘 잔액은 맞고 내년 소멸액이 틀린다 |
| 소멸한 적립분에서 뺌 | 사용 시점에 살아 있는 lot만 후보로 — 9/2에 500을 쓰면 소멸한 e2가 아니라 e1에서 빠져야 한다. 이 오류는 **소멸일이 지난 뒤에만** 난다 |
| 사용 내역(어느 lot에서 뺐나)을 안 기록 | takenBySpend에 기록 — 취소할 때 되돌릴 곳의 근거다 |
| 사건을 날짜 순으로 안 정렬 | 생성자에서 날짜 순·번호 순 정렬 — 사용이 적립보다 먼저 처리되면 잔액이 음수가 된다 |
| 잔액보다 많이 쓰는 사건 | 있는 만큼만 뺀다(음수 금지) — 막는 것은 이 장부의 일이 아니고, 흘려보내되 망가지지 않는 것이 일이다 |
| 소멸 기간이 다 같은 테스트 자료 | 전부 1년이면 "먼저 쌓인 것"="먼저 소멸할 것"이라 두 규칙이 200개 장부에서 **한 번도 안 갈린다** — 기간을 흩뜨려야 갈래가 보인다 |
| 취소 없는 테스트 자료 | RefundTarget 갈래가 통째로 안 돈다 (0/200 → 25% 취소 시 200/200) |
| 적립에 소멸일 없음, 소멸일 ≤ 적립일, 금액 ≤ 0, 취소가 원 사용을 안 가리킴 | 생성 시 IllegalArgumentException |

**측정 코드 자체의 함정 둘** (변종 검증에서 — 구현이 아니라 측정을 고쳤다):
1. `expiredBetween`이 시작일에 살아 있던 적립분만 훑었다 → 시작일엔 아직 아무것도 안 쌓여 소멸 합이 늘 0. **적립 사건을 훑어 각 소멸일 하루 전의 잔액**을 보도록 고쳤다.
2. 무작위 장부의 소멸 기간이 전부 1년이라 갈린 시행이 0 → 90~729일로 흩뿌리니 12배 차이가 드러났다.

구현 변종 15개는 전부 잡혔다 — 고칠 것이 없었다.

## 핵심 문장

- "1년 뒤에 소멸"이라는 한 줄에는 **빼는 순서·되돌리는 곳·당일의 생사** 세 결정이 빠져 있고, 셋 다 잔액이 아니라 **소멸일**을 가른다.
- **오늘 잔액이 같다고 상태가 같은 게 아니다** — 적립분 모양(금액+소멸일)이 진짜 상태이고, 잔액은 그 요약일 뿐이다. 요약만 맞추면 내년에 틀린다.
- 선입선출은 재고의 정답이지만 **소멸 자산에서는 정반대** — 먼저 소멸할 것부터 쓰면 고객의 소멸액이 12분의 1이 된다.
- 취소 규칙은 **취소가 들어오는 날 처음 실행된다** — 그날까지는 어떤 구현이든 테스트를 통과한다. 갈래를 깨우는 자료(취소·흩어진 소멸 기간)를 일부러 넣어야 한다.
- 사용할 때 "어느 적립분에서 뺐는지"를 기록하지 않으면 **취소를 옳게 되돌릴 방법 자체가 없다** — 미래의 요구사항이 현재의 기록 의무를 만든다.
- 소멸일 경계는 딱 하루 — 그 하루를 정하는 것은 코드가 아니라 **밤 배치가 도는 시각**일 수 있다.

## 용어 풀이

- **적립분(lot)**: 한 번의 적립으로 생긴 덩어리. 남은 금액과 소멸일을 함께 들고 있는 것이 이 도메인의 핵심 자료구조.
- **소멸(expiry)**: 소멸일이 지나 포인트가 사라지는 것. 적립분마다 소멸일이 다를 수 있다.
- **EARN / SPEND / REFUND**: 적립 / 사용 / 사용 취소. 장부를 이루는 세 가지 사건.
- **SpendOrder**: 사용할 때 빼는 순서 — OLDEST_FIRST(먼저 쌓인 것부터, FIFO) / EXPIRING_FIRST(먼저 소멸할 것부터).
- **FIFO(선입선출)**: 먼저 들어온 것부터 내보내는 규칙. 재고에서는 정답, 소멸 자산에서는 소멸을 키우는 함정.
- **RefundTarget**: 취소분이 돌아가는 곳 — ORIGINAL_LOT(원래 뺀 lot, 소멸일 부활) / NEW_LOT(취소일 기준 새 lot, 소멸일 연장).
- **ExpiryBoundary**: 소멸일 당일의 생사 — EXPIRED_ON_DATE(당일 이미 없음) / ALIVE_ON_DATE(당일까지 사용 가능).
- **재생(replay)**: 사건 기록을 처음부터 다시 흘려보내 상태를 계산하는 방식. 상태 캐시가 없어 규칙 스위치를 바꿔 끼우기 좋다.
- **takenBySpend**: 사용 사건마다 "어느 lot에서 얼마 뺐나"의 기록. 취소를 원래 자리로 되돌리는 근거.
- **expiredBetween**: 구간 안에 소멸한 총액. 각 적립분의 소멸일 하루 전 잔액을 합산한다.
