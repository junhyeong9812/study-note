### A. 과제

#### 0. 장부 세 줄이 말하는 것

- 안 말해주는 자리 셋(원본 javadoc 그대로):

```text
 쓸 때 어느 적립분에서 빼나   먼저 쌓인 것인가 먼저 소멸할 것인가   → SpendOrder
 취소하면 어디로 되돌리나     원래 뺀 곳인가 지금 새로 쌓나          → RefundTarget
 소멸일 당일에는              살아 있나 죽었나                       → ExpiryBoundary
```

- 7월 1일 잔액: **둘 다 1,500**이다.
- 갈리는 것: **그 1,500 이 언제 사라지느냐**다.

```text
 7/1 잔액          적립분 모양                9/1 에 e2 가 소멸하면
 1,500 (같음)      e1 0     / e2 1,500   →   1,500 이 사라진다 → 잔액 0
 1,500 (같음)      e1 1,000 / e2   500   →     500 이 사라진다 → 잔액 1,000
```

- 나중에 쌓인 것이 먼저 소멸하는 이유: **적립분마다 소멸 기간이 다르다.**\
  이벤트 포인트는 3개월, 일반 적립은 1년처럼 종류별로 기간이 다르면 순서가 뒤집힌다.
- 잔액만 맞추는 구현은: **오늘 잔액을 맞춰놓고 내년에 틀린다**(README 첫째 함정).\
  소멸일이 오기 전까지는 어떤 테스트도 이 결함을 못 잡는다.

#### 1. MileageEvent — 사건 하나

- 음수 금액 대신 종류로 나눈 차이: **사건마다 딸린 정보가 다르다.**\
  적립에는 소멸일이 붙고, 취소에는 "어느 사용을 되돌리나"가 붙는다. 금액 부호 하나로는 그 정보를 담을 자리가 없다. 그리고 `amount <= 0` 을 전부 거부할 수 있어 부호 실수가 조용히 지나가지 않는다.
- `refersTo` 가 필요한 이유: **되돌릴 곳을 알아야 하기 때문**이다.\
  `ORIGINAL_LOT` 규칙은 "그 사용이 어느 적립분에서 얼마씩 뺐는지"를 찾아 그대로 되돌린다 — 가리키는 사용이 없으면 그 계산 자체가 불가능하다.
- 적립에만 소멸일이 붙는 이유: **소멸하는 것은 적립분뿐**이다.\
  사용과 취소는 적립분을 깎거나 되돌릴 뿐 자기 수명이 없다.
- 소멸일 == 적립일을 거부하는 이유: 그 적립은 **쌓이는 순간 이미 죽어 있다**(EXPIRED_ON_DATE 기준).\
  쓸 수 없는 포인트를 쌓는 것은 설정 실수일 가능성이 높으므로 예외로 막는다.
- 정렬을 안 하면: **사용이 적립보다 먼저 처리되어 잔액이 음수가 된다.**\
  같은 날 사건끼리도 번호 순으로 가른다 — 테스트가 넣은 순서를 뒤섞어도 `e1, e2, s1` 이 되는 것으로 못 박았다.

#### 2. TODO 1 — expired

- 부등호:

```text
 EXPIRED_ON_DATE   at >= expiresOn   →  !at.isBefore(expiresOn)
 ALIVE_ON_DATE     at >  expiresOn   →   at.isAfter(expiresOn)
```

- 갈리는 날은 **소멸일 그 하루뿐**이다.

```text
 1/1 적립 1,000, 7/1 소멸

 날짜        EXPIRED_ON_DATE   ALIVE_ON_DATE
 6/30            1,000            1,000
 7/1                 0            1,000     ← 여기만 갈린다
 7/2                 0                0
```

- 안내가 안 알려주는 것: **"7월 1일에 소멸합니다"가 그날 쓸 수 있는지를 안 말한다.**\
  "7월 1일에"가 그날 아침에 사라진다는 뜻인지, 그날 밤까지는 쓸 수 있다는 뜻인지가 문장에 없다.
- 배치 시각이 정하는 이유: **소멸 처리는 대개 밤에 배치로 돈다.**\
  7월 1일 0시에 돌면 그날은 못 쓰고, 7월 1일 밤 11시에 돌면 그날 하루는 쓸 수 있다. 즉 **운영 일정이 계약을 정해버린다** — 그래서 이 결정을 코드 밖으로 미루면 안 된다.
- 11번의 `Boundary` 와 같은 문제인가: **같다.** 둘 다 "구간의 끝을 포함하나"를 묻는다.\
  차이는 단위뿐이다 — 11번은 초 단위 시각, 여기는 날짜다. 그래서 11번의 "11초 중 1초"가 여기서는 "딱 하루"가 된다.

#### 3. TODO 2 — lotsOn

정답 코드:

```java
Map<String, Lot> lots = new LinkedHashMap<>();
Map<String, Map<String, Long>> takenBySpend = new LinkedHashMap<>();

for (MileageEvent event : events) {
    if (event.on().isAfter(at)) {
        break;
    }
    switch (event.kind()) {
        case EARN -> lots.put(
                event.id(), new Lot(event.id(), event.amount(), event.expiresOn()));
        case SPEND -> {
            Map<String, Long> taken = new LinkedHashMap<>();
            long left = event.amount();
            for (Lot lot : ordered(lots, event.on(), spendOrder, boundary)) {
                if (left == 0) {
                    break;
                }
                long use = Math.min(left, lot.remaining());
                if (use == 0) {
                    continue;
                }
                lots.put(
                        lot.earnId(),
                        new Lot(lot.earnId(), lot.remaining() - use, lot.expiresOn()));
                taken.merge(lot.earnId(), use, Long::sum);
                left -= use;
            }
            takenBySpend.put(event.id(), taken);
        }
        case REFUND -> {
            if (refundTarget == RefundTarget.NEW_LOT) {
                lots.put(
                        event.id(),
                        new Lot(event.id(), event.amount(), event.on().plusYears(1)));
                break;
            }
            long left = event.amount();
            Map<String, Long> taken = takenBySpend.getOrDefault(event.refersTo(), Map.of());
            for (Map.Entry<String, Long> entry : taken.entrySet()) {
                if (left == 0) {
                    break;
                }
                long back = Math.min(left, entry.getValue());
                Lot lot = lots.get(entry.getKey());
                lots.put(
                        lot.earnId(),
                        new Lot(lot.earnId(), lot.remaining() + back, lot.expiresOn()));
                left -= back;
            }
        }
        default -> throw new IllegalStateException();
    }
}

List<Lot> alive = new ArrayList<>();
for (Lot lot : lots.values()) {
    if (lot.remaining() > 0 && !expired(lot.expiresOn(), at, boundary)) {
        alive.add(lot);
    }
}
return alive;
```

- 세 종류:

```text
 EARN    새 적립분을 만든다 (금액 + 소멸일)
 SPEND   쓸 수 있는 적립분에서 규칙 순서대로 깎고, 어디서 얼마 뺐는지를 적어둔다
 REFUND  ORIGINAL_LOT 이면 적어둔 곳으로 되돌리고, NEW_LOT 이면 새 적립분을 만든다
```

- `break` 인 이유: **사건이 날짜 순으로 정렬돼 있기 때문**이다.\
  한 번 `at` 을 넘어가면 그 뒤는 전부 `at` 보다 뒤다 — 더 볼 필요가 없다. 정렬이 안 돼 있으면 이 `break` 가 뒤쪽 사건을 조용히 빠뜨린다.
- 잔액보다 많이 쓰면: **있는 만큼만 빠지고 0에서 멈춘다.**\
  `Math.min(left, lot.remaining())` 이 각 적립분에서 남은 만큼만 가져가고, 다 돌아도 `left` 가 남으면 그냥 버려진다. 막는 것은 이 장부의 일이 아니다(테스트 주석) — 여기서는 사건을 흘려보내기만 하고, **음수가 안 되는 것**만 보장한다.
- 어디서 얼마 뺐는지를 적어두는 이유: **취소할 때 되돌릴 곳을 알아야 한다**(README 셋째 함정).\
  안 적어두면 `ORIGINAL_LOT` 규칙을 아예 구현할 수 없다.
- 그 기록이 읽히는 때: **`ORIGINAL_LOT` 취소를 처리할 때** 딱 한 번, `takenBySpend.get(event.refersTo())` 로 읽는다.
- 두 규칙의 차이:

```text
 7/1 사용 1,500 (OLDEST_FIRST) → e1 에서 1,000, e2 에서 500

 ORIGINAL_LOT   e1 +1,000 (소멸 2027-01-01),  e2 +500 (소멸 2026-09-01)
 NEW_LOT        r1 1,500  (소멸 2027-08-01)   — e1·e2 는 깎인 채로 둔다
```

- `NEW_LOT` 의 소멸일: **취소한 날 + 1년**(`event.on().plusYears(1)`)이다.\
  원래 적립분의 기간과 무관하게 1년으로 못 박혀 있다 — 적립분마다 기간이 다른 이 도메인에서는 그 자체가 또 하나의 숨은 결정이다.
- 마지막에 보는 두 조건: **잔액이 0보다 크다** + **그 날 아직 안 소멸했다**.
- 소멸한 것에서 빼면: **잔액이 음수가 되거나 없는 돈을 쓴다.** 그리고 **그 오류는 소멸일이 지난 뒤에만 난다**(README 둘째 함정).\
  테스트가 못 박았다 — 9/2 의 사용 500은 이미 소멸한 e2 가 아니라 **살아 있는 e1** 에서 빠져서 `e1` 이 500 이 된다.

정답 코드:

```java
List<Lot> usable = new ArrayList<>();
for (Lot lot : lots.values()) {

```

- `OLDEST_FIRST` 에 정렬이 필요 없는 이유: **`lots` 가 `LinkedHashMap` 이라 넣은 순서를 지킨다.**\
  적립분은 적립 사건 순서로 들어가고, 사건은 이미 날짜 순으로 정렬돼 있다 — 그래서 맵을 훑는 순서가 곧 적립 순서다.

> **LinkedHashMap** — 키를 넣은 순서를 기억하는 맵.\
> 예: e1 을 먼저 넣고 e2 를 나중에 넣으면, 값을 훑을 때도 e1 → e2 순으로 나온다. 일반 `HashMap` 은 이 순서를 보장하지 않는다.

- `EXPIRING_FIRST` 는 **소멸일 오름차순**으로 정렬하고, 같은 날이면 **적립 번호**로 가른다.
- 같은 날 순서를 못 박는 이유: **결과를 재현 가능하게 만들기 위해서**다.\
  안 정하면 같은 입력에 실행할 때마다 다른 적립분이 깎일 수 있고, 잔액은 같은데 **적립분 모양이 달라져** 나중의 소멸액이 달라진다 — 이 박스가 재는 바로 그 값이 흔들린다.
- 여기서 미리 걸러두면: **부르는 쪽이 "쓸 수 있나"를 다시 안 봐도 된다.**\
  `lotsOn` 의 SPEND 갈래는 그냥 순서대로 훑으며 `Math.min` 만 하면 되고, 소멸 판정이 한 곳(`ordered`)에만 있게 된다.

#### 5. TODO 4 — expiredBetween

정답 코드:

```java
long sum = 0;
for (MileageEvent event : events) {
    if (event.kind() != Kind.EARN) {
        continue;
    }
    LocalDate expiresOn = event.expiresOn();
    if (expiresOn.isBefore(from) || expiresOn.isAfter(toInclusive)) {
        continue;
    }
    Lot atEnd = find(
            lotsOn(expiresOn.minusDays(1), spendOrder, refundTarget, boundary),

    if (atEnd != null) {
        sum += atEnd.remaining();
    }
}
return sum;
```

- 하루 전을 보는 이유: **소멸일 당일에는 이미 그 적립분이 목록에서 빠져 있다.**\
  사라지는 금액을 알려면 **사라지기 직전의 잔액**을 봐야 한다.

```text
 e2  6/1 적립 2,000, 소멸 2026-09-01

 8/31 의 e2 잔액        9/1 에 사라지는 금액
 OLDEST_FIRST   1,500   →   1,500
 EXPIRING_FIRST   500   →     500      세 배 차이
```

- 훑는 것은 **적립 사건**이다.\
  적립분 목록이 아니라 사건을 훑어야 **"구간 안에서 쌓였다가 구간 안에서 소멸한" 적립분**까지 잡힌다.
- 시작일에 살아 있던 것만 훑으면: **구간 안에서 새로 쌓인 적립분을 통째로 놓친다.**\
  실제로 측정 코드가 그렇게 돼 있어서 **소멸 합이 늘 0** 이었다(README 변종 검증 하나) — 시작일에는 아직 아무것도 안 쌓여 있었기 때문이다.
- 구간 밖 걸러내기: `expiresOn < from` 이거나 `expiresOn > toInclusive` 면 건너뛴다.\
  이름 그대로 **끝은 포함**(`toInclusive`)이다 — 여기만 반열림이 아니라 닫힌 구간이다.
- 비용: **적립 사건 하나마다 `lotsOn` 을 통째로 한 번 더 부른다.**\
  적립이 n건이면 사건 전체를 n번 다시 흘려보내므로 O(n × 사건 수)다. 정확하지만 느린 방식이고, 이 박스에서는 **정확함을 골랐다.** (원본에 근거 없음 — 내 추론)

### B. 개념

#### 6. 측정 — 사용 순서가 소멸에 미치는 영향

장부 200개 (README 표 그대로):

| 취소 비율 | 먼저 쌓인 것부터 | 먼저 소멸할 것부터 |
|---|---|---|
| 0 % | **2,784,300** | **234,500** |
| 10 % | 3,800,400 | 946,400 |
| 25 % | 5,557,300 | 3,663,400 |

- 취소가 없을 때: **약 12배**(2,784,300 ÷ 234,500 ≈ 11.9).
- 소멸이 늘어나는 이유: **먼저 쌓인 것부터 쓰면 곧 사라질 적립분을 안 건드리고 놔둔다.**\
  그 적립분이 그대로 소멸한다 — 냉장고에서 유통기한 먼 우유부터 마시는 것과 같다.
- "선입선출이 반대"인 이유: **재고에는 소멸일이 없다.**\
  재고의 선입선출은 "오래된 것이 상하기 전에 내보낸다"는 목적인데, 마일리지는 **오래된 것이 먼저 상하지 않는다**(나중에 쌓인 것이 먼저 소멸할 수 있다). 목적이 "소멸을 줄이는 것"이라면 기준은 적립 순서가 아니라 **소멸 순서**여야 한다.
- 취소가 늘면 차이가 줄어드는 이유: **취소가 적립분을 되살려 순서를 흐트러뜨린다.** 그리고 양쪽 다 소멸액이 늘어난다(2,784,300 → 5,557,300 / 234,500 → 3,663,400) — 되돌아온 마일리지가 짧은 소멸일을 달고 돌아오기 때문이다. (뒷부분은 원본에 근거 없음 — 내 추론)

#### 7. 측정 — 잔액과 적립분 모양

- 잔액이 갈린 건수 **199 / 200**, 적립분 모양이 갈린 건수 **200 / 200**.
- 잔액이 안 갈린 한 건에서도 적립분이 갈린 것이 요점인 이유: **잔액만 보는 검증은 그 한 건을 "이상 없음"으로 통과시킨다.**\
  그런데 그 장부도 소멸일이 오면 틀린 금액을 낸다 — **오늘의 검증이 미래의 오류를 못 잡는다**는 사실이 한 건으로 증명된다.
- 한 문장: **합계는 같은데 그 합계가 어느 소멸일에 묶여 있는지가 다르다.**

#### 8. 측정 — 갈래가 안 보이는 조건

- 소멸 기간이 다 같으면: **두 사용 규칙이 통째로 같아진다.**\
  전부 1년이면 먼저 쌓인 것이 곧 먼저 소멸할 것이기 때문이다.
- 장부 200개에서 **한 번도 안 갈렸다**(잔액도 적립분 모양도).
- 문제인 이유: **개발할 때 만드는 적립은 대개 다 같은 기간이다.**\
  `MileageEvent.earn(...)` 같은 편한 헬퍼가 1년을 기본으로 주므로, 일부러 `earnUntil` 로 기간을 흩뜨리지 않으면 이 갈래가 아예 안 돈다.
- 되돌림 규칙이 갈린 장부:

| | 두 되돌림 규칙이 갈린 장부 |
|---|---|
| 취소 없음 | **0 / 200** |
| 취소 25 % | **200 / 200** |

- "취소가 들어오는 날 시작된다"의 뜻: **취소가 없으면 되돌릴 것이 없어 두 규칙이 구별조차 안 된다.**\
  그날까지는 어느 쪽으로 짜두든 테스트가 다 통과하고, 첫 취소가 들어오는 순간 **전부** 갈린다(0/200 → 200/200). 0 아니면 전부인 갈림이다.

#### 9. 측정 — 되돌린 마일리지의 소멸일

- 8/1 잔액: **둘 다 3,000**이다.
- 9/1 에 e2 가 소멸하면:

```text
 8/1 취소 직후                       9/1 (e2 소멸 후)
 ORIGINAL_LOT  e1 1,000 + e2 2,000   →   e1 1,000            = 1,000
 NEW_LOT       e1 0 + e2 1,500
               + r1 1,500(소멸 2027-08-01)  →  r1 1,500       = 1,500
                                                   차이 500
```

- 그 500은: **e2 로 되돌아갔다가 한 달 뒤에 e2 와 함께 사라진 몫**이다.
- 새로 쌓는 규칙이 고객에게 유리한 이유: **되돌아온 마일리지가 1년을 더 산다.**\
  원래 적립분의 소멸일을 물려받지 않기 때문이다.
- 원래 뺀 곳이 더 정직한 이유: **취소는 "없던 일로 하는 것"** 이다.\
  사용을 없던 일로 했으면 적립분도 사용 전 상태로 돌아가야 하고, 소멸일도 원래대로여야 한다. 새로 쌓는 규칙은 **취소를 새 적립으로 바꿔** 수명을 늘려주는데, 그건 되돌리기가 아니라 선물에 가깝다.

#### 10. 측정 — 소멸일 경계

- 갈리는 날은 **딱 하루**(소멸일 당일)다.
- 하루 전에는 **두 규칙 다 살아 있고**, 하루 뒤에는 **두 규칙 다 죽었다**.
- 배치 시각이 정하는 이유: **소멸 처리가 밤에 배치로 돌기 때문**이다.\
  배치가 소멸일 0시에 돌면 그날은 못 쓰고(EXPIRED_ON_DATE 와 같아진다), 그날 밤늦게 돌면 하루를 더 쓸 수 있다(ALIVE_ON_DATE 와 같아진다). **운영 일정이 계약 조항을 정해버린다** — 그래서 이 결정은 코드와 약관에 먼저 있어야 한다.

#### 11. 함정 (README)

- 넷: ① **잔액만 맞춘다**(오늘 맞고 내년에 틀린다) ② **소멸한 적립분에서 뺀다**(잔액이 음수가 되거나 없는 돈을 쓴다) ③ **사용을 어느 적립분에서 뺐는지 안 적어둔다**(취소할 때 되돌릴 곳을 모른다) ④ **사건을 날짜 순으로 안 흘려보낸다**(사용이 적립보다 먼저 처리된다).
- 소멸한 것에서 빼면: **잔액이 음수가 되거나 없는 돈을 쓴다.**\
  그리고 **그 오류는 소멸일이 지난 뒤에만 난다** — 배포하고 몇 달 뒤에 처음 드러난다.
- 안 적어두면: **`ORIGINAL_LOT` 취소를 구현할 수 없다.**\
  "1,500을 되돌린다"까지는 알아도 "e1 에 1,000, e2 에 500"을 모르면 소멸일을 살릴 수가 없다.
- 정렬 안 하면: **사용이 적립보다 먼저 처리된다.**\
  그러면 쓸 적립분이 아직 없어서 잔액이 음수가 되거나, 있는 돈을 못 쓰고 버려진다.

#### 12. 변종 검증

- 구현은 변종 15개가 전부 잡혔고, 대신 **측정 코드를 두 번 고쳤다.**
- `expiredBetween` 이 늘 0 이던 이유: **시작일에 살아 있던 적립분만 훑고 있었다.**\
  시작일에는 아직 아무것도 안 쌓여 있어서 훑을 대상이 없었다. 적립 사건을 훑어 **각 소멸일 하루 전의 잔액**을 보도록 고쳤다.
- 기간이 전부 1년이라: **두 사용 규칙이 같은 순서가 되어 갈린 시행이 0** 으로 나왔다.
- 90~729일로 흩뿌리자: **12배 차이가 드러났다**(2,784,300 vs 234,500).
- 공통점: **구현이 아니라 측정이 틀렸다.**\
  둘 다 "차이가 없다"는 잘못된 결론을 내고 있었고, 그 결론은 코드가 아니라 **자료를 만든 방식**에서 나왔다. 측정 결과가 "0"이나 "차이 없음"으로 나올 때 먼저 의심할 것은 측정 자체다.

> **거짓 음성(false negative)** — 문제가 실제로 있는데 검사에서 "없음"으로 나오는 것.\
> 예: 소멸 기간을 전부 1년으로 만든 측정은 두 규칙의 12배 차이를 "차이 0"으로 보고했다.

#### 13. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 소멸 예정 안내: `expiredBetween(from, to, ...)` 이 **"이 구간에 얼마가 사라지나"를 그대로 답해준다** — 안내에 쓸 값은 이미 계산 가능하다.\
  문제는 그 값이 **규칙마다 다르다**는 것이다(1,500 vs 500). 안내를 보낸 뒤에 규칙을 바꾸면 안내와 실제가 어긋나므로, **안내 시점의 규칙을 기록해 두거나** 규칙을 못 박은 뒤에 안내를 시작해야 한다. (원본에 근거 없음 — 내 추론)
- 부분 취소가 여러 번: `takenBySpend` 는 **사용 한 건당 하나의 기록**만 들고, 취소는 그 기록을 앞에서부터 `Math.min` 으로 깎아 간다.\
  같은 사용에 취소가 두 번 들어오면 **두 번째 취소도 같은 기록을 처음부터 다시 읽어** 이미 되돌린 몫을 또 되돌릴 수 있다. 제대로 하려면 **되돌린 양을 기록에서 차감해 나가야** 한다 — 지금 모델은 취소 한 번을 가정한다. (원본에 근거 없음 — 내 추론)
- 배치 전후의 잔액 차이: 이 코드는 **`at` 을 받아 그때의 잔액을 계산**하므로 배치가 있든 없든 답이 같다 — 즉 **LAZY 방식**이다.\
  실무처럼 배치로 상태를 갱신하면 11번의 LAZY/SWEEP 문제가 그대로 생긴다: 배치 전에 조회한 잔액과 배치 후 잔액이 다르다. 답은 둘 중 하나다 — **조회도 소멸을 계산해서 보여주거나**(화면과 DB가 어긋남), **배치를 소멸일 0시에 확실히 돌리거나**(배치 지연이 곧 오류). (원본에 근거 없음 — 내 추론)
- 적립분마다 다른 소멸일 보여주기: `lotsOn` 이 **적립분 목록을 그대로 돌려주므로** 화면에 "1,000점은 1/1 소멸, 500점은 9/1 소멸"처럼 나눠 보여줄 수 있다.\
  합계 하나만 보여주면 고객은 "내 3,000점"이라고 생각하는데 실제로는 며칠 뒤 500점이 사라진다. 다만 적립분이 수백 개면 목록이 쓸모없어지므로, 보통 **가까운 소멸일 몇 개만 묶어** 보여준다. (원본에 근거 없음 — 내 추론)

#### 14. 연결

- `ExpiryBoundary` 와 11번: **완전히 같은 자리**다 — 만료/소멸 시각 정각의 생사.\
  11번은 초 단위라 "11초 중 1초"였고, 여기는 날짜라 "딱 하루"다. 둘 다 부등호 한 글자(`isBefore` vs `isAfter`)가 답을 가른다.
- 사건을 다시 흘려보내는 방식: **이벤트 소싱(event sourcing)** 과 같다.\
  현재 상태를 저장하지 않고 사건 목록만 남긴 뒤, 필요할 때 처음부터 재생해서 상태를 만든다.

> **이벤트 소싱(event sourcing)** — 지금의 잔액을 저장하는 대신, 일어난 일의 목록을 저장하고 그것을 다시 흘려보내 상태를 계산하는 방식.\
> 예: 이 장부는 "잔액 1,500"을 저장하지 않는다. 적립·사용·취소 사건만 남겨두고, 규칙을 바꿔가며 같은 사건을 다시 흘려보내 답이 어떻게 갈리는지 볼 수 있다.

- "개발 자료에서는 갈래가 안 돈다"의 모습:

```text
 11번  TTL 을 길게 두면        LAZY 와 SWEEP 이 같은 답을 낸다
 12번  빈 극장(무리 20개까지)  세 Adjacency 규칙이 좌석 배정까지 똑같다
 13번  1 년 계약               SAME_LENGTH 와 ONE_YEAR 가 같은 답을 낸다
 14번  전부 1 년 소멸 / 취소 없음  두 SpendOrder·두 RefundTarget 이 같은 답을 낸다
```

  넷 다 **개발·예제에서 자연스럽게 고르는 조건이 바로 갈림을 감추는 조건**이다. 갈래를 보려면 그 조건을 일부러 깨야 한다.
