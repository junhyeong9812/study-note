### A. 과제

#### 0. 상황 다섯 줄

- "어느 것도 틀리지 않았다"의 뜻: **두 계산 다 자기 입력에 대해서는 정확하다.**\
  a 를 1 등으로 낸 계산은 4/01 00:00 시점의 자료를 정확히 더했다.\
  b 를 1 등으로 낸 계산은 4/05 시점의 자료를 정확히 더했다.\
  버그가 아니라 **입력이 달라진 것**이다.
- 다른 것: **기준 시점**이다.\
  같은 함수에 같은 참여 목록을 줘도, "언제의 상태로 볼 것인가"를 바꾸면 답이 바뀐다.

> **기준 시점(snapshot)** — 계산할 때 "몇 시 몇 분의 세상"을 볼지 정한 한 점.\
> 예: 4/01 00:00 시점으로 보면 a 의 취소는 아직 안 일어난 일이라 a 가 1 등이고, 4/05 시점으로 보면 이미 일어난 일이라 b 가 1 등이다.

- 안 말해주는 결정 셋(원본 javadoc 그대로):

```text
  언제 기준으로 세나   종료 시점의 상태인가 지금 상태인가      Snapshot
  동점을 어떻게 가르나  먼저 도달한 사람인가 나중인가 안 가르나  TieBreak
  등수를 어떻게 매기나  1 2 2 4 인가 1 2 2 3 인가              RankStyle
```

- 서로 간섭한다는 뜻: **한 갈래의 선택이 다른 갈래를 살리기도 하고 죽이기도 한다.**\
  동점을 가르면(`EARLIEST`/`LATEST`) 동점 자체가 사라져서 **등수 방식이 아무 일도 안 한다.**\
  동점을 안 가르고(`NONE`) 조밀 등수를 겹치면 초과 인원이 곱해져서 수상자가 305 명이 된다.
- enum 으로 올리면: **열두 조합을 같은 코드로 돌려 "답이 갈리는 회차"를 셀 수 있다.**\
  그래야 어느 갈래가 큰지 재보고 안다 — 재보니 시점 하나가 동점 규칙 둘보다 16 배 컸다.
- 01-parking-fee 와 같은 자리인 이유: 둘 다 **"말은 한 줄인데 읽는 법이 여럿"** 이다.\
  주차장은 "하루"가 자정인지 24 시간인지 안 정했고, 여기는 "상위 3 명"이 언제 기준인지 안 정했다.\
  그리고 둘 다 **안 정한 자리를 코드 안에 숨기지 않고 값(정책 record / enum)으로 올려서** 갈리는 건수를 센다.

#### 1. TODO 1 — counts

정답 코드 (impl/Leaderboard.java):

```java
public boolean counts(Contribution contribution, LocalDateTime endsAt, Snapshot snapshot) {
    if (!contribution.at().isBefore(endsAt)) {
        return false;
    }
    if (!contribution.cancelled()) {
        return true;
    }
    return snapshot == Snapshot.AS_OF_END
            && !contribution.cancelledAt().isBefore(endsAt);
}
```

- 판정 순서 세 단계: ① **이벤트 밖인가**(참여 시각이 종료 시각 이후면 무조건 제외) ② **안 취소됐나**(그럼 무조건 포함) ③ **취소됐는데 그 취소가 기준 시점에 보이나**.
- 참여 시각 == 종료 시각: **안 센다.** 종료 시각은 **제외 경계**다.
- 그 한 줄: `if (!contribution.at().isBefore(endsAt)) return false;`\
  "종료 시각보다 **앞**이어야 센다"이므로 정각은 떨어진다.

> **제외 경계(exclusive boundary)** — 구간의 끝점을 구간에 넣지 않는 것. 수학 기호로 `[시작, 끝)`.\
> 예: 종료가 04/01 00:00 이면 03/31 23:59:59 는 세고 04/01 00:00:00 은 안 센다. 테스트가 이 두 건으로 못 박았다.

- "4 월 1 일까지" vs "4 월 1 일 0 시까지": 앞은 **4 월 1 일 하루를 통째로 포함**하고, 뒤는 **3 월 31 일까지만**이다.\
  같은 한국말인데 24 시간이 통째로 다르다.
- 정각 포함이 크게 터지는 이유: **이벤트 마감 직전 1 초에 참여가 몰린다**(README 함정 1).\
  경계가 제일 붐비는 자리라서, 한 건 차이가 아니라 수백 건 차이가 난다.
- 안 취소된 참여: **두 기준에서 같다.** 두 번째 `if` 에서 스냅샷을 보기도 전에 `true` 로 빠진다.
- `AS_OF_NOW` 에서 취소된 참여: **절대 안 센다.** 마지막 줄의 `snapshot == AS_OF_END` 가 먼저 거짓이 된다.\
  "지금 상태"에서 취소된 건 그냥 취소된 것이다.
- `AS_OF_END` 가 취소된 참여를 세는 때: **취소 시각이 종료 시각보다 앞이 아닐 때** — 즉 종료 시각 이후에 들어온 취소.\
  종료 시점에는 아직 없던 일이니까 그 사진에는 안 찍혀 있다.
- 취소 시각 == 종료 시각: **센다.** `!cancelledAt.isBefore(endsAt)` 가 참이다.\
  참여 경계와 방향이 같다 — 종료 시각 정각에 일어난 일은 "종료 시점의 세상"에 아직 안 들어와 있다.
- 갈리는 구간: **종료 시각 이상 ~ 지금 사이에 들어온 취소**뿐이다.

```text
 종료 시각 endsAt = 2026-04-01 00:00

 참여 시각        취소 시각         AS_OF_END  AS_OF_NOW
 03/31 23:59:59  (없음)              센다       센다     같다
 04/01 00:00:00  (없음)            안 센다    안 센다    같다   ← 정각은 이벤트 밖
 03/31 19:00     03/31 20:00       안 센다    안 센다    같다   ← 종료 전 취소
 03/31 23:00     04/01 00:00         센다     안 센다   갈린다  ← 정각 취소
 03/31 23:00     04/03 10:00         센다     안 센다   갈린다  ← README 의 그 건
```

- 그 구간이 개발 자료에 잘 안 생기는 이유: 테스트 자료를 손으로 만들면 보통 **취소를 아예 안 넣거나, 넣어도 이벤트 중에 넣는다.**\
  "끝난 뒤에 들어오는 취소"는 일부러 상상해야 나오는 모양이다.\
  측정 다섯이 그걸 수로 보여준다 — 취소도 동점도 없으면 열두 조합이 통째로 같다.
- `Leaderboard` 안에 있는 이유: `counts` 는 **참여 혼자서는 못 대답하는 질문**이다.\
  `endsAt`(이벤트 규칙)과 `snapshot`(계산 규칙)이 있어야 답이 나온다.\
  `Contribution` 은 **사실**만 안다(언제 얼마를 냈고 언제 취소됐나). **판단**은 순위표 쪽 일이다.

> **사실과 판단의 분리** — 데이터는 "일어난 일"만 갖고, "그것을 셀지 말지"는 규칙을 쥔 쪽이 정하는 설계.\
> 예: `Contribution.cancelled()` 는 "취소된 적 있나"만 답하고, "이번 계산에서 셀 것인가"는 `Leaderboard.counts` 가 답한다.

#### 2. TODO 2 — standings

정답 코드:

```java
List<Contribution> sorted = new ArrayList<>(contributions);
sorted.sort(Comparator.comparing(Contribution::at));

Map<String, Long> totals = new LinkedHashMap<>();
Map<String, LocalDateTime> reached = new LinkedHashMap<>();
for (Contribution contribution : sorted) {
    if (!counts(contribution, endsAt, snapshot)) {
        continue;
    }
    totals.merge(contribution.userId(), contribution.amount(), Long::sum);
    reached.put(contribution.userId(), contribution.at());
}

List<Standing> standings = new ArrayList<>();
for (Map.Entry<String, Long> entry : totals.entrySet()) {
    standings.add(new Standing(entry.getKey(), entry.getValue(), reached.get(entry.getKey())));
}
return standings;
```

- `Standing` 세 칸: `userId`(누구) · `total`(유효한 참여 금액 합) · `reachedAt`(그 금액에 도달한 시각).
- `reachedAt` 정의: **마지막 유효 참여 시각**이다(javadoc 원문).\
  "그 합계에 도달한 순간"이니까 마지막 한 건이 들어온 시각이 맞다.\
  `reached.put(...)` 이 덮어쓰기라서, 시각 순으로 훑으면 자연히 마지막 값이 남는다.
- 시각 순으로 안 훑으면: `reached` 에 **입력 목록의 마지막 건**이 남는다.\
  DB 가 정렬을 안 보장하면 같은 자료가 조회할 때마다 다른 `reachedAt` 을 낸다.\
  그러면 `EARLIEST`/`LATEST` 동점 규칙의 답이 새로고침마다 바뀐다.

```text
 a 의 참여  10:00(3,000)  ·  09:00(5,000)   (목록에 이 순서로 들어옴)

 안 정렬하고 훑으면   reached = 09:00  ← 목록 마지막 건
 시각 순으로 훑으면   reached = 10:00  ← 진짜 마지막 참여
 total 은 8,000 으로 같다 — 합만 보면 안 틀린 것처럼 보인다
```

- 입력 같은데 결과가 달라지면 버그인 이유: **순위표는 화면에 줄로 나온다.**\
  같은 이벤트를 두 번 열었는데 순서가 다르면, 쓰는 사람은 "누가 조작했나"로 읽는다.\
  그리고 버그를 재현할 수도 없다 — 어떤 순서로 읽혔는지가 안 남는다.

> **결정성(determinism)** — 같은 입력이면 몇 번을 돌려도 같은 출력이 나오는 성질.\
> 예: 동점인 세 사람의 목록 순서가 새로고침마다 바뀌면 결정적이지 않은 것이고, 테스트도 가끔만 깨져서 잡기 어렵다.

- 같은 시각의 두 참여를 안 가르는 이유: **가를 게 없다.**\
  합은 사람별로 더하니 순서와 무관하고, 도달 시각은 어느 쪽을 나중에 놓아도 그 시각 그대로다.\
  README "변종 검증에서 고친 것"이 정확히 이 얘기다 — 거기 있던 번호 타이브레이커는 죽은 코드였다.
- `Map` 두 개인 이유: **더하는 값과 덮어쓰는 값이라 합치는 법이 다르다.**\
  `total` 은 `Long::sum` 으로 누적하고, `reachedAt` 은 마지막 것으로 교체한다.\
  (한 개의 `Map<String, Standing>` 으로도 되지만 그러면 record 를 매번 새로 만들어야 한다 — 원본에 근거 없음, 내 추론)
- `totals.merge(userId, amount, Long::sum)`: **키가 없으면 `amount` 를 넣고, 있으면 기존 값과 `amount` 를 더해 넣는다.**\
  `get` → null 검사 → `put` 세 줄을 한 줄로 줄인 것이다.
- 전부 취소한 사람을 남기면: 순위표 맨 아래에 **0 원짜리 줄**이 생기고, **그 줄이 등수를 하나 차지한다**(README 함정 3).\
  `winners(ranked, 3)` 가 0 원짜리를 3 등으로 뽑아 경품을 줄 수도 있다.
- `total == 0` 필터가 없어도 되는 이유: **`Contribution` 생성자가 `amount <= 0` 을 막기 때문**이다.\
  그래서 `totals` 에 키가 올라갔다는 것은 **유효 참여가 최소 한 건, 금액이 최소 1** 이라는 뜻이다.\
  전부 취소된 사람은 `counts` 가 전부 `false` 라 `merge` 가 한 번도 안 불리고, **키 자체가 안 생긴다.**\
  테스트 `fullyCancelledUsersDisappear` 가 `standings.size() == 1` 로 확인한다.

```text
 a  10,000 (종료 뒤 취소)      AS_OF_NOW 에서 counts = false  → merge 0 회 → totals 에 "a" 없음
 b   8,000                     counts = true                  → totals = { b: 8000 }
                                                 standings = [ b ]   크기 1
```

> **불변식을 입구에서 막기** — 나쁜 값이 아예 못 들어오게 생성자에서 거부해두면, 안쪽 코드가 그 검사를 다시 안 해도 되는 방식.\
> 예: `amount > 0` 을 `Contribution` 이 보장하니 `standings` 는 "합이 0 인가"를 검사할 필요가 없다.

- `LinkedHashMap` 인 이유: **넣은 순서를 기억하는 Map** 이라서 `standings` 의 목록 순서가 결정적이 된다.\
  `HashMap` 이면 순서가 해시값에 따라 정해져 자바 판이 바뀌면 달라질 수 있다.\
  여기서는 시각 순으로 훑으니까 **"첫 유효 참여가 빠른 사람"** 순으로 나온다.
- 금액 순 정렬 여부: **아니다.** `standings` 는 집계만 하고 정렬은 `rank` 가 한다.\
  한 함수에 한 가지 일만 시킨 것이다.

#### 3. TODO 3 — rank

정답 코드:

```java
Comparator<Standing> comparator = Comparator
        .comparingLong(Standing::total).reversed();
comparator = switch (tieBreak) {
    case EARLIEST -> comparator.thenComparing(Standing::reachedAt);
    case LATEST -> comparator.thenComparing(
            Comparator.comparing(Standing::reachedAt).reversed());
    case NONE -> comparator;
};
comparator = comparator.thenComparing(Standing::userId);

List<Standing> sorted = new ArrayList<>(standings);
sorted.sort(comparator);

List<Row> rows = new ArrayList<>();
int rank = 0;
Standing previous = null;
for (int i = 0; i < sorted.size(); i++) {
    Standing standing = sorted.get(i);
    boolean tied = previous != null
            && tieBreak == TieBreak.NONE
            && standing.total() == previous.total();
    if (!tied) {
        rank = rankStyle == RankStyle.DENSE ? rank + 1 : i + 1;
    }
    rows.add(new Row(rank, standing));
    previous = standing;
}
return List.copyOf(rows);
```

- 정렬 키 순서: ① **금액 내림차순** ② **동점 규칙**(`EARLIEST` 면 도달 시각 오름, `LATEST` 면 내림, `NONE` 이면 없음) ③ **사용자 번호 오름차순**.
- `.reversed()` 인 이유: 기본 비교는 **작은 것이 앞**인데 순위표는 **큰 금액이 1 등**이다.
- `EARLIEST` / `LATEST`:

```text
 EARLIEST  thenComparing(Standing::reachedAt)                       시각이 이른 사람이 앞
 LATEST    thenComparing(comparing(reachedAt).reversed())           시각이 늦은 사람이 앞
```

- `NONE` 인데도 번호로 세우는 이유: **등수가 같아도 화면의 위아래는 정해야 하기 때문**이다.\
  `sort` 자체는 안정 정렬이라 입력 순서를 그대로 유지하는데, **그 입력 순서가 DB 조회 순서라서 못 믿는다.**\
  번호로 한 번 더 세우면 같은 자료가 항상 같은 줄 순서를 낸다.
- 번호 정렬을 빼면: 테스트 `listOrderIsDeterministicEvenWhenTied` 가 깨진다.\
  그 테스트는 동점 셋을 `[c, a, b]` 로도 넣고 `[b, c, a]` 로도 넣어서 **둘 다 `[a, b, c]`** 가 나오는지 본다.\
  화면 쪽 증상은 "새로고침할 때마다 동점자들의 위아래가 바뀐다"이다.
- `tied` 조건 셋: ① 앞사람이 있다(`previous != null`) ② **동점 규칙이 `NONE` 이다** ③ 앞사람과 금액이 같다.
- `tieBreak == NONE` 을 빼면: `EARLIEST` 에서도 금액만 같으면 동점 처리가 되어 **등수가 1 2 3 4 가 아니라 1 1 3 4** 로 나온다.\
  그러면 "가른 동점은 더 이상 동점이 아니다"라는 계약이 깨지고, 테스트 `threeTieRulesThreeLeaderboards` 의 `ranks(earliest) == [1,2,3]` 이 실패한다.
- `COMPETITION`: `rank = i + 1` — **지금까지 지나온 사람 수 + 1.** 동점 묶음만큼 다음 등수가 건너뛴다.
- `DENSE`: `rank = rank + 1` — **직전 등수 + 1.** 절대 안 건너뛴다.

> **표준 경쟁 등수(competition ranking)** — 동점이 k 명이면 다음 사람은 k 칸 건너뛴 등수를 받는 방식. 1 1 3 4.\
> 예: 올림픽에서 공동 1 위가 둘이면 다음이 3 위다. 2 위는 없다.

> **조밀 등수(dense ranking)** — 동점이 몇 명이든 다음 등수는 바로 다음 번호인 방식. 1 1 2 3.\
> 예: "금액 등급"처럼 등수 번호 자체가 계단인 화면에서 쓴다. 대신 "3 등까지"의 범위가 훨씬 넓어진다.

- a 10,000 · b 10,000 · c 5,000 · d 3,000 의 네 조합 (테스트 `breakingTiesMakesRankStyleIrrelevant`):

```text
 정렬 후            a       b       c      d
 total          10,000  10,000   5,000  3,000
 i                  0       1       2      3

 NONE      tied?    -      예     아니오  아니오
   COMPETITION   i+1=1   유지 1   i+1=3  i+1=4   →  1 1 3 4
   DENSE         0+1=1   유지 1   1+1=2  2+1=3   →  1 1 2 3

 EARLIEST  tied? 항상 아니오 (조건에 NONE 이 들어있다)
   COMPETITION   1 2 3 4
   DENSE         1 2 3 4   ← 같다
```

- 동점을 가르면 두 방식이 같아지는 이유: `tied` 가 **한 번도 참이 안 되므로** 매 줄에서 `if (!tied)` 가 실행된다.\
  그러면 `COMPETITION` 은 `i+1`, `DENSE` 는 `rank+1` 인데, 매번 1 씩 오르니 **둘 다 1, 2, 3, 4 …** 로 같은 수열이 된다.\
  테스트가 두 결과를 `assertEquals` 로 통째로 비교한다.
- 설정 화면 관점: **켜면 아무 일도 안 하는 설정이 생긴다.**\
  "동점 가르기 = 먼저 도달"을 켠 순간 "등수 방식" 드롭다운은 죽은 설정이다.\
  쓰는 사람은 그걸 모르고 바꿔보고는 "적용이 안 되네"라고 문의한다.

> **죽은 설정(no-op flag)** — 화면에는 있는데 다른 설정 때문에 결과에 아무 영향을 못 주는 설정.\
> 예: 동점을 가르도록 켜두면 표준 경쟁/조밀 선택이 결과를 하나도 안 바꾼다.

- `List.copyOf(rows)` 인 이유: **못 고치는 목록**으로 돌려줘서 부르는 쪽이 순위표를 몰래 손대지 못하게 한다.\
  (`standings` 는 그냥 `ArrayList` 를 돌려주므로 두 함수의 방침이 일치하지는 않는다 — 원본에 근거 없음, 내 관찰)

#### 5. Contribution — 주어진 계약

- `LocalDateTime cancelledAt` 인 이유: **"취소됐나"만으로는 이 챕터의 질문에 답할 수 없다.**\
  `AS_OF_END` 는 "취소가 **언제** 들어왔나"를 봐야 세는지 마는지 정한다.
- `boolean` 이었다면: **`Snapshot` 갈래 자체가 못 만들어진다.**\
  종료 전 취소와 종료 후 취소를 구분할 방법이 없으니 계산은 항상 "지금 상태" 하나뿐이고, 발표한 순위가 조용히 바뀌는 것을 막을 수단이 없다.
- `amount <= 0` 을 막아서 필요 없어진 코드: `standings` 의 **`total == 0` 필터**(2 번 답 참고).\
  javadoc 에는 "합이 0 인 사람은 안 낸다"라고 적혀 있는데, 구현에는 그 `if` 가 없다 — 입구에서 이미 막았기 때문이다.
- `cancelledAt < at` 금지: **시간 순서 불변식**이다. 취소는 참여보다 나중일 수밖에 없다.\
  이걸 안 막으면 "참여 전에 취소된 건"이 자료에 섞이고, `counts` 는 그걸 그냥 취소로 세서 **잘못된 자료가 조용히 반영된다.**

> **불변식(invariant)** — 그 자료가 살아 있는 동안 언제나 참이어야 하는 조건.\
> 예: "취소 시각은 참여 시각보다 앞일 수 없다" · "금액은 0 보다 크다". 깨지면 만들 때 바로 예외를 던진다.

- `cancelled()` javadoc 의 "지금 기준으로": **이 메서드는 시점을 모른다**는 선언이다.\
  `cancelledAt != null` 만 보므로 언제나 "현재 상태"의 답이다.\
  그래서 `AS_OF_END` 판정은 이 메서드로는 못 하고, `counts` 가 `cancelledAt` 을 직접 꺼내 `endsAt` 과 견준다.

#### 6. 측정 하나 — 취소 비율

사용자 50, 참여 300, 100 회. 종료 시점 기준과 지금 기준의 상위 3 명을 견줬다.

```text
 취소 비율                 상위 3 명 바뀜   1 등 바뀜
 0 %                         0 / 100          0
 5 %  (절반이 늦은 것)      33 / 100         11
 20 % (절반이 늦은 것)      82 / 100         34
 20 % (전부 늦은 것)        89 / 100         42
```

- 0 %: **0 / 100 과 0.**
- 5 %(절반 늦음): **33 / 100 과 11.** 상위 3 명이 세 번 중 한 번 바뀌고, 1 등은 열 번에 한 번 바뀐다.
- 20 %(전부 늦음): **89 / 100 과 42.**
- 취소 0 % 면 항상 같은 이유: `counts` 에서 스냅샷을 보는 줄은 **취소된 참여에만** 닿는다.\
  취소가 하나도 없으면 모든 참여가 두 번째 `if` 에서 `true` 로 빠져, 두 기준이 **같은 집합**을 센다.
- "개발 환경이 그렇다"가 무서운 이유: **어느 기준으로 짜두든 테스트가 통과한다.**\
  즉 이 선택이 틀렸다는 신호를 개발 중에는 한 번도 못 받는다.\
  신호는 운영에서, 경품이 나간 뒤에 온다.

#### 7. 측정 둘 — 금액 단위

```text
 금액 단위    넘친 회차   초과 인원   동점 쌍
 1 원          0 / 100        0           0
 10,000 원     3 / 100        3         260
 100,000 원   10 / 100       13       1,888
 500,000 원   52 / 100       97       3,909
```

- 1 원 단위: **0 / 100 · 0 명 · 0 쌍.**
- 500,000 원 단위: **52 / 100 · 97 명 · 3,909 쌍.**
- 굵게 만드는 법: **깎는다.** `amount = Math.max(roundTo, raw / roundTo * roundTo)` — 정수 나눗셈으로 잘라내고 다시 곱한다.
- 곱하면 안 되는 이유(측정 테스트 javadoc 원문): **전부 같은 비율로 커져서 동점 빈도가 안 바뀐다.**\
  1,234 와 5,678 에 1,000 을 곱하면 1,234,000 과 5,678,000 — 여전히 다른 값이다.\
  깎아야 **값의 가짓수가 줄어서** 동점이 는다.

> **양자화(quantization)** — 연속적인 값을 정해진 단위의 계단으로 내리는 것. 값의 가짓수가 줄어든다.\
> 예: 10,000 원 단위로 깎으면 123,456 원과 129,999 원이 둘 다 120,000 원이 되어 동점이 된다.

- 500,000 원 단위에서 나올 수 있는 금액: **한 가지(500,000 원)뿐이다.**

```text
 raw 는 10,000 ~ 999,999 중 하나
 amount = max(500,000, raw / 500,000 * 500,000)

   raw < 500,000   →  raw/500000 = 0  →  0        →  max = 500,000
   raw >= 500,000  →  raw/500000 = 1  →  500,000  →  max = 500,000

 값의 가짓수
   단위       1  →  약 99 만 가지   동점 쌍     0
   단위  10,000  →       99 가지    동점 쌍   260
   단위 100,000  →        9 가지    동점 쌍 1,888
   단위 500,000  →        1 가지    동점 쌍 3,909
```

- 합계가 같아지는 조건: 단위가 500,000 이면 모두 같은 금액이므로 **참여 건수만 같으면 동점**이다.\
  50 명이 300 건을 나눠 가지면 평균 6 건이라 건수가 겹치는 사람이 쏟아진다.\
  (인접 동점 쌍의 최대치는 100 회 × 49 = 4,900 쌍인데 실제가 3,909 쌍이니 약 80 % 가 동점이다 — 원본에 근거 없음, 내 계산)
- "1 원 단위면 안 정해도 된다"가 함정인 이유: **동점 규칙이 필요 없는 게 아니라, 지금 자료에 동점이 안 나올 뿐**이다.\
  규칙의 빈자리는 그대로 있고, 자료가 바뀌는 날 그 빈자리가 드러난다.
- 터지는 날: **포인트·응모권처럼 값이 굵은 이벤트로 옮기는 날**(README 원문).\
  그날 절반(52 / 100)의 회차에서 상위 3 명이 세 명이 아니게 된다. 그리고 그날은 예고가 없다.

#### 8. 측정 셋 — 시점 vs 동점 규칙

- 열두 조합 = **Snapshot 2 × TieBreak 3 × RankStyle 2 = 12.**
- 같은 시점 안(`AS_OF_END` 여섯 조합): **최대 5 / 100.**
- 시점을 바꾼 쪽(`AS_OF_NOW` 여섯 조합): **최소 82 / 100.**

측정 테스트 javadoc 의 전체 표 (취소 20 %, 절반이 늦은 것, 단위 10,000, 100 회):

```text
 시점       동점    등수   인원   기준과 다른 회차
 종료 시점  먼저    표준   300     0   ← 기준 그 자체
 종료 시점  먼저    조밀   300     0
 종료 시점  나중    표준   300     5
 종료 시점  나중    조밀   300     5
 종료 시점  안가름  표준   301     4
 종료 시점  안가름  조밀   305     5      같은 시점 안에서 최대 5
 지금       먼저    표준   300    84
 지금       먼저    조밀   300    84
 지금       나중    표준   300    82   ← 시점을 바꾼 것 중 최소 82
 지금       나중    조밀   300    82
 지금       안가름  표준   303    84
 지금       안가름  조밀   305    84
```

- "열여섯 배": **82 ÷ 5 = 16.4** — 시점 쪽 최소값을 동점 쪽 최대값으로 나눈 것이다.\
  제일 불리하게 잡아도 16 배라는 뜻이다.
- 교훈 한 문장: **"규칙의 크기는 이야기한 시간이 아니라 답을 바꾼 횟수로 잰다."**
- 어긋나는 이유: 동점 규칙은 **눈에 보이고 말로 설명하기 쉬워서** 회의에서 다들 의견이 있다.\
  재계산 시점은 **평소에는 아예 안 드러난다** — 취소가 없으면 두 기준이 같은 답을 내니 아무도 질문을 떠올리지 못한다.\
  그래서 논쟁의 크기와 영향의 크기가 반대로 붙는다.

#### 9. 측정 넷 — 수상자 305 명

- 정원: **100 회 × 3 명 = 300 명.**
- 가르면 **300 명**(정확히 정원), 안 가름 + 표준 경쟁 **301 명**, 안 가름 + 조밀 **305 명**.
- "곱해진다"의 뜻: **두 갈래가 각각 정원을 넓히고, 겹치면 넓힘이 더 커진다.**

```text
 가름   + 아무 등수 방식   300      초과 0
 안가름 + 표준 경쟁        301      초과 1
 안가름 + 조밀             305      초과 5   ← 1 의 다섯 배
```

  안 가름이 동점자를 같은 등수로 묶어 정원을 넘기고, 조밀이 "3 등까지"의 범위를 더 넓힌다.

> **정원 초과(overfill)** — "상위 N 명"을 뽑았는데 N 명보다 많이 나오는 것.\
> 예: 셋이 다 같은 금액이면 `NONE` 에서 셋 다 1 등이라 "상위 2 명"이 세 명이 된다.

- 5 명 초과가 무시 못 할 수인 이유: 경품은 **개수로 산다.**\
  100 회에 5 개면 이벤트 한 번에 0.05 개씩 초과인데, 경품 단가가 비싸면 그 자체로 예산 초과이고, 안 주면 "등수는 같은데 왜 나는 못 받나"라는 항의가 된다.\
  (예산·항의 얘기는 원본에 근거 없음 — 내 추론)

#### 10. 측정 다섯 — 열두 조합이 통째로 같아지는 자료

- 조건: **단위 1 원(동점 없음) + 취소 0 %(늦은 취소 없음).**
- 비교 횟수 **1,100 번**, 어긋난 횟수 **0**.
- 1,100 의 출처: **100 회 × 11 번.**\
  한 회차에서 열두 조합을 돌리고, 첫 조합을 기준으로 삼아 나머지 **11 개**와 견준다.\
  `assertEquals(0, differed)` 가 그 0 을 못 박는다.
- 개발 자료가 그 모양인 이유(README 원문): **금액을 손으로 다르게 적고 취소를 안 넣는다.**\
  손으로 적으면 자연히 1,000 · 2,000 · 3,000 처럼 다 다르게 쓰고, 취소는 "나중에 테스트하지" 하고 미룬다.
- 테스트 자료 규칙으로 바꾸면: **"갈래를 만드는 조건을 자료에 일부러 심어라."**\
  이 챕터에서는 ① 종료 시각 뒤에 들어오는 취소 ② 합계가 같아지는 사람 ③ 종료 정각에 걸친 한 건 — 셋을 반드시 넣는다.
- `new Random(31)` 로 씨앗을 고정한 이유: **측정 수를 테스트 assert 로 박으려면 값이 재현돼야 한다.**\
  씨앗이 같으면 같은 난수열이 나와서 33 · 82 · 305 같은 수가 매번 똑같이 나온다.\
  그래서 구현을 바꾸면 이 수가 깨지고, 측정 테스트의 javadoc 말대로 **"그때 깨지는 것이 이 파일의 일"** 이 된다.

> **씨앗 고정(seeded random)** — 난수 생성기에 시작값을 정해줘서 매번 같은 난수열이 나오게 하는 것.\
> 예: `new Random(31)` 로 만든 자료는 몇 번을 돌려도 똑같아서, 측정값을 테스트로 못 박을 수 있다.

#### 11. 함정 (README)

- 넷:\
  ① **종료 시각을 포함으로 잡는 것** — 마감 직전 1 초에 참여가 몰린다.\
  ② **취소를 지금 상태로만 보는 것** — 발표한 값이 말없이 바뀐다.\
  ③ **전부 취소한 사람을 순위표에 남기는 것** — 0 원짜리 줄이 등수를 차지한다.\
  ④ **동점 규칙을 안 정하는 것** — 상위 3 명이 세 명이 아니게 된다.
- "말없이 바뀐다"가 붙은 것: **②번(취소를 지금 상태로만 보는 것).**
- 0 원짜리 줄의 화면: 순위표 맨 아래에 이름은 있는데 금액 칸이 `0` 인 줄이 생긴다.\
  정렬은 금액 내림차순이라 맨 밑이고, `winners(ranked, 3)` 은 **등수만 보므로** 참여자가 적은 이벤트에서는 그 줄이 3 등 안에 들어온다.
- 정원 초과가 버그로 안 보이는 이유: **예외도 안 나고 값도 다 맞다.**\
  "상위 3 명" 목록이 네 줄인 것뿐이라, 화면만 보면 그냥 동점이 많았나 보다 싶다.\
  숫자가 어긋나는 곳은 코드가 아니라 **경품 창고**다.

#### 12. 변종 검증에서 고친 것

- 고친 것: **`standings` 의 번호 타이브레이커**를 지웠다. 죽은 코드였다.
- 죽은 코드였던 이유 한 문장: **같은 시각의 두 참여는 어느 쪽을 나중에 놓아도 합계와 도달 시각이 똑같이 나오므로, 순서를 정해봐야 결과에 안 보인다.**\
  합은 사람별로 더하니 순서와 무관하고, 도달 시각은 그 시각 그대로다.

> **죽은 코드(dead code)** — 실행은 되는데 결과에 아무 영향을 못 주는 코드.\
> 예: 같은 시각끼리 참여 번호로 한 번 더 정렬해도 집계 결과가 한 글자도 안 바뀐다.

- 시각 정렬을 지우면 안 되는 이유: **지우면 도달 시각이 입력 순서를 탄다**(README 원문).\
  같은 시각끼리의 순서는 안 중요하지만, **다른 시각끼리의 순서는 `reachedAt` 을 결정한다.**\
  `reached.put` 이 덮어쓰기라서 마지막에 훑은 건이 남기 때문이다.
- 주석을 남기는 것이 나은 이유: 그냥 지우면 **다음 사람이 "동점 처리가 빠졌네" 하고 도로 넣는다.**\
  "왜 없는지"가 코드에 없으면 없는 이유가 사라지고, 같은 죽은 코드가 다시 태어난다.
- 이 챕터의 "죽은 것" 둘: ① **죽은 코드** — `standings` 의 번호 타이브레이커 ② **죽은 설정** — 동점을 가를 때의 `RankStyle`.\
  둘 다 원인이 같다: **다른 규칙이 먼저 그 차이를 없애버려서** 뒤 규칙이 일할 거리가 없다.

#### 13. 생각해볼 것

*(원본 README 는 질문만 던지고 답을 안 준다 — 아래는 코드·측정에 근거한 내 추론이다.)*

- 순위를 고칠 때 알리는 대상: **바뀐 사람 전원**이다.\
  ① 내려간 사람(경품 회수·사과) ② 올라온 사람(뒤늦은 수여) ③ 안 바뀌었지만 등수 숫자가 달라진 사람 ④ 내부 정산·회계.\
  알릴 내용은 "무엇이 왜 바뀌었나" — **취소가 언제 들어왔는지**를 같이 줘야 "조작"으로 안 읽힌다.\
  코드 쪽 대비는 **두 스냅샷을 다 계산해 두는 것**이다. `AS_OF_END` 로 발표하고 `AS_OF_NOW` 도 같이 뽑아두면 차이를 바로 보여줄 수 있다.\
  (원본에 답 없음 — 내 추론)
- 종료 뒤 취소를 막으면 없어지나: **문제 자체는 없어진다.** 취소가 종료 전에만 들어오면 `counts` 의 마지막 줄이 항상 같은 답을 내서 두 스냅샷이 일치한다(테스트 `cancellationsBeforeTheEndAgree` 가 그 증거다).\
  하지만 **막을 수 있는 종류의 취소가 아니다.**
- 청약철회: 결제 뒤 일정 기간 안에 취소할 수 있는 **법으로 보장된 권리**라, 이벤트 규칙으로 막을 수 없다.\
  그래서 현실적인 답은 "취소를 막는다"가 아니라 **"발표는 `AS_OF_END` 로 고정하고, 늦은 취소는 별도 정산 절차로 다룬다"** 쪽이다.\
  즉 순위 계산에서 밀어내고 **환불·정산 도메인**으로 옮긴다.\
  (원본에 답 없음 — 내 추론)
- 경품 하나 더 vs 추첨: **경품 단가와 초과 인원 수로 갈린다.**\
  측정에서 초과는 100 회에 1~5 명(안 가름 + 조밀이면 5 명)이니, 굿즈처럼 싼 경품이면 **하나 더 주는 쪽이 싸다** — 추첨은 공지·이의제기·운영 비용이 따로 든다.\
  자동차처럼 비싼 단일 경품이면 추첨이 유일한 답이다.\
  다만 추첨을 쓰면 **결정성이 깨지므로**(같은 자료가 다른 답을 낸다) 추첨 씨앗과 결과를 기록해 재현 가능하게 만들어야 한다 — 25-lottery-draw 가 그 자리다.\
  (원본에 답 없음 — 내 추론)
- 도달 시각을 처음 참여로 잡으면: **`EARLIEST` 와 `LATEST` 의 의미가 통째로 바뀐다.**

```text
 a  09:00 에 3,000  ·  23:00 에 7,000   합 10,000
 b  10:00 에 9,000  ·  11:00 에 1,000   합 10,000

 마지막 참여 기준(지금 구현)  a 23:00 · b 11:00  →  EARLIEST 면 b 가 1 등
 처음 참여 기준               a 09:00 · b 10:00  →  EARLIEST 면 a 가 1 등
```

  "먼저 그 **금액에 도달**한 사람"이라는 javadoc 의 말과 맞는 것은 **마지막 참여**다.\
  처음 참여로 잡으면 그건 "먼저 **시작**한 사람"이라는 다른 규칙이고, 늦게 시작해 몰아넣은 사람이 항상 불리해진다.\
  그리고 처음 참여 기준은 **늦은 취소에 덜 흔들린다**(맨 앞 건이 취소돼야만 바뀐다) — 안정성과 의미가 서로 반대로 붙는 자리다.\
  (원본에 답 없음 — 내 추론)

#### 14. 연결

- 세는 것의 차이: 알고리즘 트랙은 **비용**(비교 횟수·시간)을 셌다. 같은 답으로 가는 길이 얼마나 비싼가였다.\
  여기서 세는 것은 **답이 갈리는 회차 수** — 답 자체가 여럿이라서 비용이 아니라 **불일치**를 잰다.\
  그래서 "빠르게 만들었다"가 아니라 **"어느 결정이 큰가"** 가 결론이 된다.
- `Snapshot` 2 택과 같은 자리: 데이터베이스의 **시점 조회(as-of query)** 와 **이력 테이블(temporal table)** 이다.\
  "지금 값"과 "그때 값"을 둘 다 답할 수 있게 **행에 유효 기간을 붙여 두는** 설계가 같은 문제를 푼다.\
  이 노트 안에서는 **09-policy-version**(어느 시점의 정책으로 계산하나)과 **16-audit-replay**(그때 상태를 다시 만들어 보기)가 같은 자리다.\
  (챕터 대응은 제목에서 짐작한 것 — 원본에 근거 없음, 내 추론)

> **시점 조회(as-of query)** — "지금 값" 말고 "그 시각의 값"을 묻는 조회.\
> 예: "4 월 1 일 0 시 기준으로 a 의 유효 참여 합은 얼마였나" — 그 답은 오늘 조회해도 안 변해야 한다.

- "규칙을 켜면 다른 규칙이 죽는다" 패턴: **17-batch-retry** 의 "되돌리기를 켜면 재시도 범위가 죽는다"가 같은 모양이다(2-summary 가 이미 짚어둔 대응이다).\
  설정 두 개를 나란히 놓았는데 실제로는 **하나가 다른 하나를 무효로 만드는** 구조다.
- 종료 정각 경계와 같은 자리: **01-parking-fee** 의 "10 분까지는 무료인가"가 정확히 같다.\
  그 밖에 **04-hotel-booking**(체크아웃 날이 숙박에 들어가나) · **08-meeting-slot**(끝나는 시각과 시작 시각이 맞닿으면 겹침인가) · **15-period-close**(마감 시각 정각의 거래는 이번 달인가) 가 전부 경계 포함/제외 문제다.\
  (앞 두 챕터는 01-parking-fee 정답 노트가 짚어둔 대응이고, 15 번은 제목에서 짐작한 내 추론이다)
- 코드 리뷰 체크리스트 한 줄: **"이 계산은 '언제 기준'인가 — 그 답이 코드 주석이 아니라 인자에 적혀 있나?"**\
  기준 시점이 인자로 안 올라와 있으면, 그 코드는 **"지금"을 몰래 고른 것**이다.
