# domain-modeling/advanced/19-leaderboard-recount — 정리 (힌트)

## 해결하는 문제

"참여 금액 순으로 상위 3명"은 한 문장인데, 그대로 코드로 옮기면 **발표한 순위가 며칠 뒤 말없이 바뀌거나, 상위 3명이 네 명이 되는** 일이 생긴다.\
참여는 이벤트 중에 들어오지만 취소는 나중에(종료 뒤에도) 들어오고, 금액이 굵으면 동점이 생기기 때문이다.

```text
  [참여·취소 목록] --(언제 기준? 동점은? 등수 방식은?)--> [상위 N]
                        └ 셋을 안 정하면 같은 자료가 다른 순위표를 낸다
```

쉬운 예: 운동회 메달을 나눠준 뒤 한 선수의 기록이 취소되면 "그럼 금메달은 누구 거냐" — 발표 시점 답과 지금 답이 다르고 둘 다 틀리지 않았다.\
똑같은 구조다: 이벤트 종료 후 청약철회가 들어오면 종료 시점 기준 순위와 지금 기준 순위가 갈리는데, 경품은 이미 나갔다.\
실무 예: 이벤트 경품 순위·게임 시즌 랭킹 정산·펀딩 후원 순위 — 이 챕터는 숨은 결정 셋(기준 시점·동점·등수 방식)을 enum으로 드러내고, 어느 결정이 실제로 답을 크게 바꾸는지를 잰다.

### 한눈에 — 쉽게 말하면

**순위 재계산 = 운동회가 끝나고 메달까지 나눠줬는데, 며칠 뒤 한 선수의 기록이 취소됐을 때 "그럼 금메달은 누구 거냐"는 문제.**

- 발표 순간의 기록으로 보면 a가 1등이고, 지금 기록으로 보면 b가 1등이다. **두 답 중 어느 것도 틀리지 않았다 — 기준 시점이 다를 뿐이다.** 그리고 메달(경품)은 이미 나갔다.
- 이벤트 순위표도 똑같은 구조다. 참여는 이벤트 중에 하지만 **취소는 나중에**, 심지어 이벤트가 끝난 뒤에 들어온다(청약철회 등).
- 여기에 동점 문제가 겹친다: 동점을 안 가르면 "상위 3명"이 네 명이 될 수 있는데 경품은 세 개뿐이다.
- "참여 금액 순으로 상위 3명"이라는 한 문장에 **정해지지 않은 규칙이 3개** 숨어 있다.

```text
  3/31 23:00  a 가 10,000 참여
  3/31 22:00  b 가  8,000 참여
  4/01 00:00  이벤트 종료, 순위 발표          → 1등 a
  4/03 10:00  a 의 참여가 취소됨
  4/05        다시 계산하면                   → 1등 b

  발표할 때 1등이던 사람이 며칠 뒤 순위표에서 사라진다.
```

실무 예: 이벤트 경품 순위, 게임 시즌 랭킹 정산, 크라우드펀딩 후원 순위 — "발표 후 환불/취소"가 있는 모든 순위.

## 동작·원리

### 전체 흐름

```text
요구사항: "참여 금액 순으로 상위 3명" — 숨은 3택

  ① 언제 기준으로 세나 (Snapshot)
       AS_OF_END  종료 시점의 상태 — 그 뒤 취소는 안 본다. 발표한 값이 안 바뀐다
       AS_OF_NOW  지금 상태 — 늦은 취소도 반영. 발표한 값이 바뀐다

  ② 동점을 어떻게 가르나 (TieBreak)
       EARLIEST  먼저 그 금액에 도달한 사람이 위
       LATEST    나중에 도달한 사람이 위
       NONE      안 가른다 — 같은 등수

  ③ 등수를 어떻게 매기나 (RankStyle)
       COMPETITION  표준 경쟁: 1 2 2 4 (동점 다음이 건너뛴다)
       DENSE        조밀:      1 2 2 3 (안 건너뛴다)

  counts()    그 참여를 세나 (종료 정각 제외 + 스냅샷 규칙)
  standings() 사람별 합계 + 도달 시각 (합 0인 사람 제외)
  rank()      정렬 + 등수 부여
  winners()   rank ≤ topN 전부 — 동점을 안 가르면 정원이 넘칠 수 있다
```

### 규칙 1 — 기준 시점: 종료 시점인가 지금인가

**어떤 요구사항인가**: "취소는 나중에 들어온다. 그리고 그 나중이 이벤트 종료 뒤일 수 있다."

코드 번역 — `counts()`의 판정:

```text
참여가 종료 시각 이후            → 어느 규칙에서도 안 센다 (이벤트 밖)
안 취소된 참여                   → 센다
취소된 참여:
  AS_OF_NOW                     → 안 센다 (지금은 취소 상태니까)
  AS_OF_END + 취소가 종료 후     → 센다 (종료 시점엔 아직 없던 일)
  AS_OF_END + 취소가 종료 전     → 안 센다 (종료 시점에 이미 취소)
```

**갈리는 것은 "종료 시각과 지금 사이에 들어온 취소"뿐이다** — 종료 전 취소는 두 기준이 같은 답을 낸다. 그리고 그 구간은 개발할 때 만드는 자료에 잘 안 생긴다. 측정: 취소 0%면 두 기준이 100번 다 같고, 취소가 **5%만 되면 상위 3명이 33/100 회 바뀌고 1등이 11번 바뀐다.**

측정의 결정타: 재계산 시점 하나가 동점 규칙 둘보다 **16배** 크다 — 같은 시점 안에서 동점 규칙만 바꾸면 최대 5/100 갈리는데, 시점을 바꾸면 최소 82/100 갈린다. **동점 규칙은 회의에서 오래 얘기하고, 재계산 시점은 아무도 안 묻는다.**

### 규칙 2 — 종료 시각 정각은 이벤트 밖

**어떤 요구사항인가**: README 함정 1번 — "종료 시각을 포함으로 잡지 마라."

**손계산**: 종료 2026-04-01 00:00일 때 —

```text
  03/31 23:59:59 참여  → 센다
  04/01 00:00:00 참여  → 안 센다     (!at.isBefore(endsAt) → 제외)
```

"4월 1일까지"와 "4월 1일 0시까지"가 이 한 건을 가른다. 그리고 **이벤트 마감 직전 1초에 참여가 몰린다** — 경계값이 제일 붐비는 자리다.

### 규칙 3 — 합이 0인 사람은 순위표에서 뺀다

**어떤 요구사항인가**: README 함정 3번 — 전부 취소한 사람을 남기면 순위표 맨 아래 0원짜리 줄이 생기고, **그 줄이 등수를 하나 차지한다.** `standings()`는 totals에 올랐어도 합 0이면 안 낸다(구현상 취소된 참여는 애초에 안 더해지고, 유효 합이 있는 사람만 나온다).

**도달 시각(reachedAt)**: 그 금액에 도달한 시각 = **마지막 유효 참여 시각**. 참여를 시각 순으로 훑어야 한다 — 안 훑으면 도달 시각이 입력 순서를 탄다. 같은 시각끼리는 안 가른다(변종 검증: 번호 타이브레이커는 죽은 코드였다 — 어느 쪽을 나중으로 놓아도 도달 시각이 같으니까. 지우고 이유를 주석에 적었다).

### 규칙 4 — 동점: 같은 자료에서 1등이 셋으로 갈린다

**예시 입력**: a 10,000(종료 5시간 전 도달), b 10,000(1시간 전 도달), c 5,000.

```text
  EARLIEST(먼저 도달이 위)   a b c   등수 1 2 3
  LATEST(나중 도달이 위)     b a c   등수 1 2 3
  NONE(안 가름)              a b c   등수 1 1 3

  1등이 a도 되고 b도 되고 둘 다도 된다.
```

**안 가르면 정원이 넘친다**: a b c 셋 다 10,000이면 NONE에서 셋 다 1등 → **상위 2명이 세 명.** 경품은 두 개뿐이다(README 함정 4번). `winners()`는 rank ≤ topN을 전부 넣기 때문이다.

측정 — **동점은 금액 단위가 만든다**: 1원 단위면 동점이 아예 안 나서(0/100) 동점 규칙 없이도 돌아간다. 그런데 포인트·응모권처럼 값이 굵은 이벤트(500,000원 단위)로 옮기는 날 **52/100 회차에서 정원이 넘친다.**

**결정성**: 안 가르는 규칙에서도 목록 순서는 사용자 번호로 세운다 — 순위표는 화면에 줄로 나오고, 등수가 같아도 위아래가 새로고침마다 바뀌면 안 된다.

### 규칙 5 — 등수 방식은 "안 가를 때만" 일을 한다

**예시 입력**: a 10,000, b 10,000, c 5,000, d 3,000.

| 조합 | 등수 |
|---|---|
| 안 가름 + 표준 경쟁(COMPETITION) | 1 1 3 4 (동점 다음이 건너뛴다) |
| 안 가름 + 조밀(DENSE) | 1 1 2 3 |
| 가름 + 표준 경쟁 | 1 2 3 4 |
| 가름 + 조밀 | 1 2 3 4 — **같다** |

동점을 가르면 더 이상 동점이 없으므로 두 등수 방식이 통째로 같아진다 — **설정 화면에 둘을 두고 동점 가르기를 켜면 그 설정이 아무 일도 안 한다** (17장의 "되돌리기를 켜면 재시도 범위가 죽는다"와 같은 패턴: 규칙끼리의 간섭).

**조밀 등수의 함정**: a b 동점, c d 동점, e 다섯 명에서 "3등까지" 뽑으면 —

```text
  표준 경쟁  1 1 3 3 5  → 4명
  조밀       1 1 2 2 3  → 다섯 명 전부
```

조밀 등수는 번호가 촘촘해서 "3등까지"가 훨씬 넓다. 측정: 100회 × 상위 3명 = 정원 300에서, 가르면 정확히 300, 안 가름+표준 경쟁 301, 안 가름+조밀 **305**.

## 쓰이는 자료구조·알고리즘

- **다중 키 비교자 정렬** — `comparingLong(total).reversed()` 뒤에 동점 규칙(`reachedAt` 정/역순)과 최종 `userId`를 체인으로 붙인다. 동점을 안 가르는 규칙에서도 마지막 키가 있어야 같은 자료가 같은 순서를 낸다 — [algorithm/02-merge-sort](../../../algorithm/02-merge-sort/2-summary.md)(안정 정렬과 타이브레이커).
- **삽입 순서 맵으로 집계(`LinkedHashMap` + `merge`)** — 사람별 합계는 `merge(userId, amount, Long::sum)`, 도달 시각은 `put`으로 **덮어써** 마지막 유효 참여 시각을 남긴다. 그래서 집계 전에 시각 순 정렬이 필요하다 — [data-structure/05-hashmap](../../../data-structure/05-hashmap/2-summary.md).
- **등수 부여(competition / dense)** — 정렬된 목록을 한 번 훑으며 "앞사람과 동점인가"만 보고 등수를 정한다. SQL 윈도우 함수 `RANK()`(1 2 2 4)와 `DENSE_RANK()`(1 2 2 3)가 같은 두 방식이다.
  - *윈도우 함수(window function)*: 행마다 "주변 행들"을 보고 값을 계산하는 SQL 기능. 등수·누적합이 대표.
- **시점 조회(as-of)** — `Snapshot`은 "그때 상태 vs 지금 상태"를 고르는 스위치다. 데이터베이스의 이력 테이블·시점 조회, 이 노트의 [09-policy-version](../09-policy-version/2-summary.md)·[16-audit-replay](../16-audit-replay/2-summary.md)와 같은 자리(정답 14번 참고).
- **경계 판정(반열린 구간)** — `at.isBefore(endsAt)`만 센다 = `[시작, 종료)`. 마감 정각을 어느 쪽에 넣을지가 한 건을 가른다.
- **양자화가 만드는 동점** — 금액을 단위로 깎으면 값의 가짓수가 줄어 동점이 폭증한다(1원 단위 0쌍 → 500,000원 단위 3,909쌍). 동점 규칙의 필요성은 코드가 아니라 자료의 굵기가 정한다(정답 7번 참고).
- **실시간 순위표 자료구조(실무 확장)** — 이 코드는 매번 전체를 정렬하지만, 참여가 계속 들어오는 순위표는 정렬 상태를 유지하는 구조(예: Redis Sorted Set — 원소가 많으면 스킵 리스트 + 해시, 적으면 압축 목록(listpack) 인코딩)를 쓴다 — [data-structure/12-skip-list](../../../data-structure/12-skip-list/2-summary.md) · [basic/24-leaderboard](../../basic/24-leaderboard/2-summary.md). 상위 N만 필요하면 힙으로 부분 정렬한다 — [data-structure/07-heap](../../../data-structure/07-heap/2-summary.md).
- **씨앗 고정 난수 시뮬레이션** — 측정 테스트가 `new Random(31)`로 취소 비율·금액 단위를 바꿔가며 100회 돌려 "답이 갈리는 회차 수"를 센다. 동점자 추첨으로 넘어가면 [25-lottery-draw](../25-lottery-draw/2-summary.md)의 재현 가능한 난수 문제가 된다.

## 적용 — 풀어나가는 법

이런 문제를 받으면 "상위 N명"을 정렬 한 줄로 옮기기 전에 **언제 기준인가·동점은·등수 방식은**을 인자(enum)로 끌어올린다 — 인자에 없으면 코드가 "지금"을 몰래 고른 것이다.\
그 다음 갈래가 드러나는 자료를 일부러 만든다: 종료 뒤 취소, 합계가 같은 사람, 종료 정각에 걸친 한 건. 취소도 동점도 없는 자료에서는 12조합이 통째로 같아 아무것도 검증되지 않는다.\
아래는 원본 챕터가 시킨 과제 목록이다 — 순서는 counts → standings → rank → winners.

| 2 | `standings(contributions, endsAt, snapshot)` | 사람마다 합계 + 도달 시각 — **시각 순으로 훑는다.** 합이 0 인 사람은 안 낸다 |
| 3 | `rank(standings, tieBreak, rankStyle)` | 금액 큰 순 정렬 + 등수 부여 — 안 가르는 규칙에서도 **목록 순서는 사용자 번호로** 정한다 |
| 4 | `winners(ranked, topN)` | 등수가 `topN` 이하인 사람 전부 — **네 명이 나올 수 있다.** `topN < 1` 은 거부 |

테스트가 못 박은 계약(`LeaderboardTest`): 03/31 23:59:59 참여는 세고 04/01 00:00:00 참여는 안 센다 · 종료 뒤 취소는 `AS_OF_END`=[a,b] / `AS_OF_NOW`=[b] 로 갈린다 · 종료 전 취소는 두 기준이 `assertEquals` 로 같다 · 전부 취소한 사람은 순위표에서 사라진다 · 동점 셋 + `NONE` 은 등수가 1 1 1 이고 상위 2 명이 **세 명** · `NONE+COMPETITION` 은 1 1 3 4, `NONE+DENSE` 는 1 1 2 3 · `EARLIEST` 면 두 등수 방식의 결과가 **통째로 같다** · 다섯 명 예제에서 "3 등까지"가 표준 4 명 vs 조밀 **5 명** · 입력 순서를 섞어도 목록 순서가 같다 · `winners(…, 0)` · 참여 전 취소 · 금액 0 · 빈 사용자 번호는 전부 예외.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 장애 시나리오와 대처

**1. 실시간 순위표가 발표 뒤에도 계속 움직인다**

- 현상: 종료 시점에 발표한 1등이 며칠 뒤 화면에서 2등으로 내려가 있고, 고객센터에 "순위가 조작됐다"는 문의가 온다.
- 보이는 형태: 발표 화면과 현재 화면의 순위가 다르다. 취소 이벤트가 들어올 때마다 순위표의 합계가 깎이고(실시간 캐시에 음수 증가분 반영), 발표 값은 어디에도 저장돼 있지 않다.
- 원인: 실시간 순위표 하나로 발표까지 대신했다 — 그 구조는 `AS_OF_NOW`만 안다. 종료 시점의 상태를 따로 고정해 두지 않으면 늦은 취소가 발표 값을 덮어쓴다.
- 대처: 종료 시각에 `AS_OF_END` 결과를 **불변 스냅샷**으로 저장하고 발표·경품은 그 스냅샷만 본다. 실시간판은 별도 화면으로 두고 "발표 기준"과 "현재" 라벨을 붙인다. 늦은 취소는 순위가 아니라 환불·정산 절차로 넘긴다(정답 13번 참고).

**2. 마감이 9시간 일찍 닫혔다 — 타임존**

- 현상: "4월 1일 0시 마감"인데 3월 31일 오후 3시 이후 참여가 전부 순위에서 빠졌다.
- 보이는 형태: `counts`가 마감 직전 참여를 `false`로 판정한다. 로그의 참여 시각은 KST, `endsAt`는 서버(UTC)에서 만든 값이라 9시간 차이가 난다.
- 원인: 이 코드의 시각은 `LocalDateTime`이라 타임존 정보가 없다. 참여 시각과 종료 시각을 서로 다른 시간대에서 만들면 같은 "0시"가 다른 순간을 가리킨다. 경계 정각 규칙(규칙 2)이 정확해도 경계 자체가 어긋난다.
- 대처: 종료 시각과 참여 시각을 같은 기준(`Instant` 또는 시간대가 붙은 시각)으로 계약에 박고, 마감 경계 테스트에 시간대가 다른 입력을 넣는다. 화면 표기용 시간대와 판정용 시각을 분리한다.

**3. 참여가 몰리자 순위 조회가 느려진다**

- 현상: 이벤트 마지막 날 참여가 몰리면서 순위표 화면 응답이 수 초로 늘고, 새로고침마다 더 느려진다.
- 보이는 형태: 조회 한 번마다 `standings`(전체 정렬 + 집계)와 `rank`(다시 정렬)가 통째로 돈다. 조회 한 번에 참여 건수 n에 대해 O(n log n)이 든다.
- 원인: 이 코드는 "계약을 보여주는" 구현이라 매 호출마다 전체를 다시 계산한다. 조회가 잦은 실시간 순위표에 그대로 쓰면 읽기마다 재계산이다.
- 대처: 합계를 정렬 상태로 유지하는 구조(정렬 집합·스킵 리스트)에 참여·취소를 증분 반영하고, 상위 N만 뽑는다. 단 그 구조는 `AS_OF_NOW`만 알므로 발표용 `AS_OF_END`는 종료 시각에 이 코드 같은 재계산으로 한 번 만들어 고정한다(시나리오 1).

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 종료 시각 정각 포함 | `at.isBefore(endsAt)`만 센다 — 마감 직전 1초에 참여가 몰린다 |
| 취소를 지금 상태로만 봄 | Snapshot 2택을 드러낸다 — 발표한 값이 말없이 바뀐다 |
| 종료 전 취소 vs 종료 후 취소 | 종료 전 취소는 두 기준이 같다 — 갈리는 건 종료~지금 사이의 취소뿐 |
| 전부 취소한 사람이 순위표에 남음 | 합 0인 사람 제외 — 0원 줄이 등수를 차지한다 |
| 참여하기 전에 취소 | 생성자에서 예외 (`cancelledAt < at` 금지), 금액 ≤ 0도 예외 |
| 동점 규칙 없음 | 상위 N명이 N명이 아니게 된다 — 경품 수와 어긋남 |
| 동점 목록 순서가 입력 순서를 탐 | userId 최종 타이브레이크로 결정성 보장 |
| 도달 시각이 입력 순서를 탐 | 시각 순 정렬 후 집계 |
| 개발 자료로 검증 | 취소도 동점도 없으면 12조합이 통째로 같다(1,100번 비교 0 갈림) — 갈래를 보려면 취소·동점을 일부러 넣어야 한다 |

## 핵심 문장
- 발표 순위와 재계산 순위가 다를 때 **어느 쪽도 틀리지 않았다 — 기준 시점이 다를 뿐이다.** 그래서 기준 시점(Snapshot)은 코드가 몰래 정할 게 아니라 도메인이 명시할 규칙이다.
- 재계산 시점 하나가 동점 규칙 둘보다 16배 크게 답을 바꾼다 — 회의에서 오래 얘기하는 것과 실제로 답을 바꾸는 것은 다르다.
- 동점을 안 가르면 "상위 3명"이 3명이 아니게 된다 — 그리고 동점은 규칙이 아니라 **금액 단위의 굵기**가 만든다(1원 단위 0건 → 500,000원 단위 52/100).
- 동점을 가르면 등수 방식(표준/조밀)이 죽는다 — 규칙 셋은 독립이 아니라 서로 간섭한다.
- 취소도 동점도 없는 개발 자료에서는 12조합이 전부 같은 답을 낸다 — 갈래는 저절로 안 보이고, 일부러 넣어야 보인다.

### 용어 풀이

- **스냅샷(snapshot)**: 어느 시점의 상태를 사진 찍듯 고정해서 보는 것. AS_OF_END는 종료 시점 사진, AS_OF_NOW는 지금 사진.
- **재계산(recount)**: 이미 발표한 순위를 나중에 다시 계산하는 것. 늦은 취소가 있으면 답이 달라진다.
- **타이브레이크(tie-break)**: 동점을 가르는 보조 규칙. 먼저 도달/나중 도달/안 가름.
- **도달 시각(reachedAt)**: 그 사람이 최종 합계 금액에 도달한 시각 — 마지막 유효 참여의 시각.
- **표준 경쟁 등수(competition ranking)**: 1 2 2 4 — 동점 다음 등수가 인원수만큼 건너뛴다.
- **조밀 등수(dense ranking)**: 1 2 2 3 — 안 건너뛴다. "3등까지"의 범위가 훨씬 넓어진다.
- **경계값(boundary)**: 규칙이 갈리는 정확한 지점. 여기서는 종료 시각 정각 — 포함이냐 제외냐가 한 건을 가른다.
- **결정성(determinism)**: 같은 자료면 입력 순서와 무관하게 같은 순위표. 화면의 위아래가 새로고침마다 바뀌면 안 된다.
- **청약철회**: 결제 후 일정 기간 안에 취소할 소비자의 법적 권리. "종료 뒤 취소를 막으면 되지 않나"가 안 되는 이유.
- **죽은 코드/죽은 설정**: 다른 규칙 때문에 실행돼도 아무 효과가 없는 코드나 설정. 동점을 가르면 등수 방식이 그렇게 된다.
