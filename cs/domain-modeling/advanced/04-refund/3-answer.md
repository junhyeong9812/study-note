### A. 과제

#### 0. 안내문 한 줄이 안 말해주는 것

```text
 안 말해준 것                    가능한 읽기                        enum
 "7 일 이내" 의 첫날      →  받은 날이 1 일차 / 다음 날이 1 일차   DayCount
 부분 반품에서 할인은     →  비례 회수 / 안 회수 / 전액 회수       DiscountAllocation
 반품 배송비는 누가       →  전액 소비자 / 비례 / 안 뭄            ReturnShippingRule
 기간이 지났을 때         →  예외를 던지나 / 값으로 알려주나        (설계 선택)
```

- 3월 8일 신청:

```text
 3/1 수령, 단순 변심 7 일

 날짜    3/1   3/2  3/3 ... 3/7  3/8  3/9
 산입    1일차 2일차 ...   7일차  8일차  X      →  3/7 까지
 불산입  0일차 1일차 ...   6일차  7일차 8일차   →  3/8 까지 (하루 더 여유)

 3/8 신청  산입 → 8 일차, 기간 밖, 0 원
           불산입 → 7 일차, 기간 안, 24,000 원
```

- "그 사이가 없다"인 이유: **금액이 조금 갈리는 게 아니라 전부냐 0이냐**다.\
  나눗수가 갈리면 1,188원 차이지만, 여기는 24,000원과 0원이다 — 그래서 **갈린 건은 전부 분쟁이 된다.**
- 법이 적은 것: **"대금을 환급한다"** 그뿐이다. 나누는 방법도, 첫날을 세는지도 안 적혀 있다.

> **청약철회** — 소비자가 정해진 기간 안에 계약을 무를 수 있는 법적 권리.\
> 예: 인터넷으로 산 옷이 마음에 안 들면 7일 안에 반품할 수 있다. "이유를 대지 않아도 된다"는 것이 핵심이다.

- enum으로 올리면: **아홉 조합을 같은 코드로 돌려 폭(22,000~30,000)을 재볼 수 있다.**\
  그래야 "이 결정이 얼마짜리인가"를 사업 쪽에 보여줄 수 있다.

#### 1. TODO 1 — daysElapsed

정답 코드 (impl/RefundPolicy.java):

```java
long between = ChronoUnit.DAYS.between(order.deliveredOn(), request.requestedOn());
return (int) (dayCount == DayCount.INCLUSIVE_FIRST_DAY ? between + 1 : between);
```

- 두 방식의 식: 산입은 **`두 날짜의 차 + 1`**, 불산입은 **`두 날짜의 차` 그대로**.
- 수령 당일(3/1) 신청: 차가 0이므로 **산입 1일차 / 불산입 0일차.**
- 당일 신청은 **양쪽 다 통과한다**(1 ≤ 7, 0 ≤ 7).
- 경계 앞뒤:

```text
 산입    3/7 된다 (7 일차)    3/8 안 된다 (8 일차)
 불산입  3/8 된다 (7 일차)    3/9 안 된다 (8 일차)
```

- 부등호는 **`<=`** 다(`elapsed <= window`). "7일 이내"의 7일차는 포함이다.
- 둘 다 두는 이유: **민법 원칙은 불산입이지만 쇼핑몰 안내문은 산입으로 쓰인 곳이 많다.**\
  어느 쪽이 "맞다"가 아니라, 그 회사가 어느 쪽을 쓰는지를 **밖에서 고를 수 있게** 해야 두 해석의 차이를 재볼 수 있다.

#### 2. TODO 2 — returnedAmount

정답 코드:

```java
long amount = 0;
for (Map.Entry<String, Integer> entry : request.quantities().entrySet()) {
    OrderLine line = order.line(entry.getKey());
    if (entry.getValue() > line.quantity()) {
        throw new IllegalArgumentException("주문 수량보다 많이 반품한다: " + entry.getKey());
    }
    amount += line.unitPrice() * entry.getValue();
}
return amount;
```

- 주문 수량 초과: **던진다.**
- 없는 품목: **던진다**(`order.line(sku)` 안에서).
- 던지는 것과 안 던지는 것의 차이: **말이 되는 신청인가 아닌가.**

```text
 기간이 지난 신청     말은 된다. 답이 "0 원"인 정상 결과다     →  값으로 돌려준다
 없는 품목 반품       말이 안 된다. 입력 자체가 틀렸다         →  던진다
 수량 초과 반품       말이 안 된다. 있지도 않은 물건이다       →  던진다
```

> **도메인 오류 vs 입력 오류** — 전자는 규칙에 따른 정상적인 "거절", 후자는 애초에 성립하지 않는 입력.\
> 예: "7일 지나서 환불 불가"는 고객에게 설명할 답이 있는 거절이고, "주문에 없는 상품을 반품"은 설명할 답이 없는 잘못된 요청이다.

- 이 금액은 **할인 전 금액**(`unitPrice × quantity`)이다. 할인은 그다음 단계에서 따로 뺀다.

#### 3. TODO 3 — share

정답 코드:

```java
if (whole == 0) {
    return 0;
}
return BigDecimal.valueOf(amount)
        .multiply(BigDecimal.valueOf(part))
        .divide(BigDecimal.valueOf(whole), 0, RoundingMode.HALF_UP)
        .longValueExact();
```

- 나눗셈 먼저 하면 사라지는 것: **나머지.** 비율을 정수로 먼저 만들면 소수가 통째로 버려진다.
- 손계산:

```text
 곱하기 먼저   5,000 × 30,000 = 150,000,000
                150,000,000 / 50,000 = 3,000          ← 올바름

 나눗셈 먼저   5,000 / 50,000 = 0.1  →  정수로 0
                0 × 30,000 = 0                        ← 할인이 통째로 사라진다
```

  이 예는 극단적으로 0이 되지만, 값이 조금만 달라도 오차가 수량만큼 곱해진다.

> **비례배분(proration)** — 하나로 묶인 금액을 어떤 비율에 따라 쪼개는 것.\
> 예: 할인 5,000원을 A(30,000원)와 B(20,000원)에 금액 비율로 나누면 3,000원과 2,000원이 된다.

- `whole == 0` 보호가 없으면: **`ArithmeticException`(0으로 나눔)** 이 터진다.
- 그런 주문: **사은품만 받고 배송비만 낸 주문.** 품목 단가가 0이라 `itemsTotal()` 이 0이다.
- 깨지는 것: **금액이 틀리는 게 아니라 환불 화면이 죽는다.**\
  고객은 "환불 금액이 이상하다"가 아니라 "페이지가 안 열린다"를 겪고, 로그에는 도메인과 무관해 보이는 산술 예외만 남는다.
- 변종 검증: **안 잡혔다.** 상품 금액이 0인 주문을 시험한 적이 없었기 때문이다.

#### 4. TODO 4 — refund

정답 코드:

```java
int elapsed = daysElapsed(request, order, dayCount);
int window = request.reason() == Reason.DEFECT ? defectDays : changeOfMindDays;
boolean within = elapsed <= window;

long returned = returnedAmount(order, request);
if (!within) {
    return new Refund(0, 0, 0, 0, false, elapsed, window);
}

long clawback = switch (allocation) {
    case BY_VALUE -> share(order.discount(), returned, order.itemsTotal());
    case NONE -> 0;
    case ALL -> Math.min(order.discount(), returned);
};
long shipping = request.reason() == Reason.DEFECT ? 0 : switch (shippingRule) {
    case FULL_FROM_BUYER -> order.shippingFee();
    case PRORATED -> share(order.shippingFee(), returned, order.itemsTotal());
    case WAIVED -> 0;
};
long total = returned - clawback - shipping;
return new Refund(returned, clawback, shipping, total, true, elapsed, window);
```

- 기간이 지났을 때 담는 것: **금액은 전부 0, 그리고 `withinWindow=false`·`daysElapsed`·`windowDays`.**\
  테스트가 61일 뒤 신청에 대해 `daysElapsed=61`, `windowDays=7` 을 못 박았다.
- 던지면: **화면에 "오류"만 뜬다.** "며칠 지났고 며칠까지였다"를 못 보여주므로 고객은 왜 안 되는지 모르고, 상담원도 모른다.
- 세 필드를 따로 담는 이유: **거절 화면이 그 값들로 만들어지기 때문이다.**\
  "7일 이내인데 61일째라 불가합니다"라는 문장을 만들려면 셋이 다 필요하다 — **거절도 도메인의 정상 결과**라는 뜻이다.
- 사유가 바꾸는 것 둘: **기간(7일 vs 30일)** 과 **배송비 부담(소비자 vs 판매자).**
- 하자면 배송비: **규칙 셋을 보지도 않고 0** 이다(`WAIVED` 와 같은 값이지만, 규칙 선택보다 사유가 먼저다).
- `DiscountAllocation` 세 식:

```text
 BY_VALUE  할인 × 반품금액 / 상품총액     (반품 비율만큼 회수)
 NONE      0                              (남은 주문이 할인을 다 가진다)
 ALL       min(할인, 반품금액)            (남은 주문이 정가가 된다)
```

- `ALL` 에 `min` 이 붙은 이유: **회수액이 돌려줄 상품 금액보다 크면 안 되기 때문이다.**\
  없으면 싼 품목 하나(5,000원)를 반품했는데 할인 20,000원을 회수해 **환불이 −15,000원**이 된다.

> **할인 회수(clawback)** — 이미 준 할인을 부분 반품 때 도로 가져가는 것.\
> 예: 5만 원 이상 사면 5,000원 깎아주는 쿠폰을 쓴 뒤 절반을 반품하면, 그 5,000원 중 얼마를 다시 받을지가 문제가 된다.

- `ReturnShippingRule` 세 식: **전액(`shippingFee`) / 비례(`배송비 × 반품금액 / 상품총액`) / 0.**
- 최종 총액: **`반품 상품 금액 − 할인 회수 − 배송비 부담`.**
- 음수가 되는 경우: **상품 금액 0인 주문(사은품)을 반품하면서 배송비를 전액 무는 경우** — 총액 **−3,000원**.\
  돌려받는 게 아니라 **내야 한다.** 이걸 청구할지 0으로 뭉갤지는 "생각해볼 것"으로 남아 있다.

#### 5. 손계산 — 아홉 조합

주문: A 30,000 + B 20,000 = 50,000 · 할인 5,000 · 배송비 3,000. **A만 반품(반품 비율 60%)**:

```text
 할인 회수    BY_VALUE 5,000×30,000/50,000 = 3,000   NONE 0   ALL min(5,000,30,000) = 5,000
 배송비 부담  FULL 3,000   PRORATED 3,000×30,000/50,000 = 1,800   WAIVED 0

                │ 배송비 전액   배송비 비례   배송비 안 뭄
 ───────────────┼──────────────────────────────────────
 할인 비례      │   24,000       25,200       27,000
 할인 안 회수   │   27,000       28,200       30,000   ← 제일 후함
 할인 전액 회수 │   22,000       23,200       25,000   ← 제일 박함
```

- 제일 후한 값 **30,000**, 제일 박한 값 **22,000**, 폭 **8,000원**.
- 상품값의 **약 27%**(8,000 / 30,000).
- 할인 비례 + 배송비 비례의 내역:

```text
 itemRefund        30,000
 discountClawback   3,000
 shippingCharge     1,800
 total             25,200
```

- 개수 기준으로 하면: A·B가 각각 1개씩이라 **반반** → 할인 **2,500**, 배송비 **1,500**.\
  금액 기준(3,000·1,800)과 다르고, **개수 기준도 말이 된다** — 그래서 기준을 명시해야 한다.
- 싼 B만 반품 + 할인 전액 회수: `20,000 − 5,000 − 3,000 = ` **12,000원**\
  (할인 비례면 `20,000 − 2,000 − 3,000 = ` **15,000원** — 3,000원 차이, 반품 금액의 15%.)
- 남은 A: **정가 30,000원짜리 주문이 된다.** 할인 5,000원이 통째로 사라졌다.

### B. 개념

#### 6. 측정 — 갈림의 크기

- A만 반품 아홉 조합: 폭 **8,000원**, 상품값의 **27%**.
- 무작위 5,000건: 폭 평균 **5,631원**, 최대 **13,000원**.
- 아홉이 전부 같은 시행: **533 / 5,000**(약 10.7%).
- 제일 박한 규칙 / 제일 후한 규칙:

```text
 할인 전액회수 / 배송비 전액   239,393,000   89.5 %
 할인 비례     / 배송비 전액   248,420,104   92.9 %
 할인 안회수   / 배송비 면제   267,547,000  100.0 %
                                    차이 10.5 %
```

- 그런데 아홉 다 합법인 이유: **법은 "대금을 환급한다"고만 적혀 있다.**\
  무엇이 "대금"인지, 할인을 어떻게 나누는지, 반품 배송비를 누가 무는지를 법이 안 정한다.
- 초일 하나로 갈린 시행: **431 / 5,000 (8.6%)**. 기간 안인 시행은 **산입 2,918 / 불산입 3,349**.
- 8.6%가 전부 분쟁이 되는 이유: **금액이 절반으로 주는 게 아니라 전부냐 0이냐**이기 때문이다.\
  1,000원 차이는 그냥 넘어가지만, "0원"은 반드시 항의가 들어온다.

> **절벽(cliff)** — 입력이 한 칸만 움직여도 결과가 조금이 아니라 통째로 바뀌는 자리.\
> 예: 3/7 신청은 24,000원, 3/8 신청은 0원. 중간값이 없으므로 "거의 맞았다"가 성립하지 않는다.

- 사유(0~39일차 균등 신청):

```text
                 단순 변심      하자
 거부된 시행       3,971       1,126
 환불 총액     51,829,420   200,246,856     →  약 3.9 배
```

  기간이 7일과 30일로 다르고, 하자면 배송비도 안 문다.\
  **"하자입니다"라는 한 줄이 금액을 네 배로 만든다.**
- 전부 반품이면 아홉이 **네 값**(42,000 / 45,000 / 47,000 / 50,000)으로 준다. 측정에서 **728건 전부** 그랬다.
- 그렇게 되는 이유: **반품 금액 = 주문 금액이라 비율이 1**이 된다.

```text
 할인 비례  5,000 × 50,000/50,000 = 5,000  =  할인 전액회수 min(5,000, 50,000)
 배송비 비례 3,000 × 50,000/50,000 = 3,000  =  배송비 전액
                       3 × 3 조합이 2 × 2 로 접힌다
```

- 할인도 배송비도 없는 주문이면 아홉이 **하나**가 된다(회수할 것도 물 것도 없다).
- "본질이 아니니까 빼기 쉽다"가 경고인 이유: **예제에서 지워지는 바로 그 두 줄이 갈림의 원천**이다.\
  할인과 배송비는 "곁가지"처럼 보이지만, 아홉 갈래는 정확히 그 둘에서 나온다.

#### 7. 함정 (README)

- 다섯: ① **기간이 지났을 때 던지는 것**(며칠 지났는지를 보여줘야 한다) ② **부분 반품에서 할인을 나눌 방법을 안 정하는 것**(주문서의 한 줄이 셋으로 갈린다) ③ **나눗셈을 먼저 하는 것**(나머지가 사라진다) ④ **상품 금액이 0인 주문**(비례배분의 분모가 0) ⑤ **전부 반품으로만 시험하는 것**(아홉 조합이 네 값으로 준다).
- 금액이 아니라 화면이 죽는 것: **④번.** 나머지는 금액이 틀리거나 안 보이는 형태다.
- ⑤가 함정인 이유: **전부 반품은 비율이 1이라 세 규칙 중 둘이 같아진다.**\
  "가장 단순한 케이스"로 시험한다는 좋은 습관이 여기서는 정확히 갈림을 지운다.

- 음수 환불: 이 코드는 **음수를 그대로 돌려준다**(`total = -3,000`). 실무의 선택지는 셋이다 — ① 0으로 막는다(판매자가 손해를 떠안는다. 가장 흔하다) ② 정말 청구한다(결제 수단에 추가 승인을 걸어야 해서 기술적으로 어렵고 분쟁이 크다) ③ 반품 자체를 거절한다("이 반품은 배송비가 상품값보다 큽니다"). **음수를 값으로 드러낸 것 자체가 설계**다 — 0으로 뭉갰으면 이 결정을 해야 한다는 사실조차 안 보인다. (원본에 답 없음 — 내 추론)
- 하자 판정: 이 코드는 **`request.reason()` 을 그냥 믿는다** — 신청자가 고른 값이다. 현실에서는 상품을 받아본 뒤 판매자가 판정하므로, **신청 시점과 확정 시점의 금액이 다르다.** 그래서 신청 화면에서는 **두 사유를 다 계산해 "변심이면 0원, 하자로 인정되면 30,000원"을 같이 보여주는 것**이 맞다. `RefundPolicy` 가 순수 계산이라 두 번 부르면 되고, 그게 `ReturnRequest` javadoc 이 "두 사유를 다 계산해봐야 한다"고 적은 이유다. (원본에 답 없음 — 내 추론)
- 남은 주문의 할인 후 금액: 이 코드는 **남은 주문을 계산하지 않는다** — 환불액만 낸다. 그런데 `DiscountAllocation` 을 고른 순간 남은 주문의 값도 정해진다(`ALL` 이면 남은 A가 정가 30,000원). 문제는 **그 값을 어디에 저장하느냐**다. 다시 계산하면 규칙이 바뀌었을 때 과거가 흔들리므로, **반품 시점에 남은 주문의 금액을 스냅샷으로 기록**해야 한다. 안 그러면 2차 반품의 기준 금액이 달라진다. (원본에 답 없음 — 내 추론)
- 무료배송 조건: **논리적으로는 청구하는 것이 맞지만 거의 아무도 안 한다.** 청구하면 "왜 이미 받은 배송비를 또 내느냐"는 항의가 확실하고, 금액은 3,000원이라 방어 비용이 더 크다. 다만 **이것을 악용한 반품**(5만 원어치 사서 무료배송 받고 대부분 반품)은 실제로 있어서, 보통은 계산이 아니라 **반복 반품 계정 제재**로 막는다 — 즉 요금 계산의 문제가 아니라 **남용 탐지**의 문제로 옮긴다. (원본에 답 없음 — 내 추론)

#### 9. 연결

- 01-parking-fee 와 같은 구조: 주차의 **"10분까지"가 10분을 포함하나**와 여기의 **"7일 이내"의 첫날을 세나**는 둘 다 **경계 하나의 포함 여부**다. 다만 주차는 500원이 갈리고 여기는 **전액이냐 0이냐**가 갈린다 — 같은 종류의 모호함이라도 **결과의 폭이 다르면 위험도가 다르다.**
- 02-promotion 과 같은 이야기: 프로모션의 **"할인 5,000원 한 줄을 어느 순서로 적용하나"** 와 여기의 **"할인 5,000원 한 줄을 품목에 어떻게 나누나"** 는 둘 다 **집계된 한 줄을 다시 쪼개는 규칙**이 요구사항에 없다는 문제다.
- 거절을 값으로 돌려주는 설계 — 얻는 것: **거절의 이유와 정도를 화면에 보여줄 수 있고, 여러 해석을 나란히 계산해 비교할 수 있다.** 잃는 것: **호출자가 `withinWindow` 를 확인하는 것을 잊을 수 있다.** 예외는 무시하면 프로그램이 멈추지만, 0원은 그냥 0원으로 흘러간다 — 그래서 `total` 만 보고 쓰는 코드가 생기면 거절이 "무료 환불"처럼 지나갈 위험이 있다.
