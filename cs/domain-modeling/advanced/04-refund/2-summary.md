## 한눈에 — 쉽게 말하면

**환불 계산 = "7일 이내 환불 가능"이라는 안내문 한 줄을 진짜 금액으로 바꾸는 문제.**

- "7일 이내"라고 하면 다들 같은 뜻인 줄 안다. 그런데 **받은 날을 1일차로 세나, 다음 날을 1일차로 세나?** 3/1에 받았으면 3/7까지거나 3/8까지다 — 그 하루에 신청한 사람은 **전액 환불이거나 0원**이다. 그 사이가 없다.
- 두 개 산 것 중 하나만 반품하면? 주문서에는 "할인 5,000원", "배송비 3,000원" 두 줄뿐인데, 그 두 줄을 나누는 방법이 **3×3 = 아홉 가지**다. 같은 반품이 22,000원에서 30,000원까지 간다.
- 이 챕터의 요점: **안내문에 안 적힌 결정들**(초일 산입 / 할인 회수 / 배송비 부담)을 enum 3개로 드러내고, 기간이 지나도 예외 대신 **"며칠 지났는지"를 담은 값**을 돌려준다.

```text
3/1 수령, "7일 이내 청약철회"

  초일 산입     3/1이 1일차  →  3/7까지
  초일 불산입   3/2가 1일차  →  3/8까지

  3/8 신청자: 한쪽은 24,000원, 한쪽은 0원.
```

실무 예: 쇼핑몰 반품/환불, 전자상거래법 청약철회, 부분 반품 시 쿠폰 회수.

## 문제 — 이 챕터가 시키는 것

원본 README가 던지는 문장은 이것이다.

```text
  3 월 1 일 수령, "7 일 이내 청약철회"

    초일 산입     3/1 이 1 일차   ->  3/7 까지
    초일 불산입   3/2 가 1 일차   ->  3/8 까지
```

**"3 월 8 일에 신청한 사람은 한쪽에서는 되고 한쪽에서는 안 된다. 전액 환불과 0 원이다. 그 사이가 없다."**

- "7일 이내"의 **첫날을 세나 안 세나?**
- 부분 반품에서 **주문서의 "할인 5,000원" 한 줄**을 품목에 어떻게 나누나?
- 반품 배송비는 **누가 무나?**
- 기간이 지났을 때 **던지나 값으로 알려주나?**

법은 "대금을 환급한다"고만 적혀 있다.\
그래서 이 박스는 답을 하나로 정하지 않고 `DayCount` · `DiscountAllocation` · `ReturnShippingRule` **enum 셋으로 올린다.**

> **초일 산입 / 불산입** — 기간을 셀 때 첫날을 1일차로 세느냐(산입), 다음 날부터 세느냐(불산입).\
> 예: 3/1에 물건을 받았을 때 산입이면 3/1이 1일차라 3/7까지, 불산입이면 3/2가 1일차라 3/8까지다. (민법 원칙은 불산입이다.)

과제(원본 README "채울 것"): `src/main/java/com/domain/refund/RefundPolicy.java` 의 **TODO 1~4**. `Order` 와 `ReturnRequest` 는 계약이라 다 주어져 있다.

테스트가 못 박은 계약(`RefundPolicyTest`, 주문 A 30,000 + B 20,000 · 할인 5,000 · 배송비 3,000 · 3/1 수령): 3/8 신청 → 산입 8일차 거절 0원 / 불산입 7일차 24,000원 · 당일 신청은 양쪽 다 통과 · 같은 날 신청이 사유로 0원과 30,000원 · 61일 지나도 `daysElapsed=61` 을 값으로 반환 · A만 반품 시 **아홉 조합이 22,000~30,000** · 비례배분은 금액 기준(할인 3,000·배송비 1,800·총 25,200) · B만 반품 + 할인 전액 회수 → 12,000(비례면 15,000) · 전부 반품 → 아홉이 네 값(42,000/45,000/47,000/50,000)으로 축소 · 할인 없는 주문이면 세 배분 규칙이 같음 · 상품 0원 주문에서 `0/0` 을 안 함 · 그때 배송비 전액 부담이면 총액 **−3,000원**.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
요구사항(말)                     →  코드(타입/메서드)
─────────────────────────────────────────────────────
"주문"                           →  Order record (품목들 + 배송비 + 주문 전체 할인 + 받은 날)
"반품 신청"                      →  ReturnRequest record (신청일 + 품목별 수량 + 사유)
"단순 변심 7일 / 하자 30일"      →  Reason enum이 기간·배송비를 둘 다 바꾼다
"7일을 어디부터 세나?" ← 안 적힘 →  enum DayCount { INCLUSIVE_FIRST_DAY, EXCLUSIVE_FIRST_DAY }
"할인은 어떻게 회수?"  ← 안 적힘 →  enum DiscountAllocation { BY_VALUE, NONE, ALL }
"반품 배송비는 누가?"  ← 안 적힘 →  enum ReturnShippingRule { FULL_FROM_BUYER, PRORATED, WAIVED }

refund(order, request, dayCount, allocation, shippingRule):
  경과일 계산 → 사유별 기간과 비교
  기간 밖 → 던지지 않고 Refund(0원, withinWindow=false, 며칠째인지) 반환
  기간 안 → 반품 상품 금액 − 할인 회수분 − 배송비 부담분 = 돌려줄 돈
  (하자면 배송비는 무조건 0)
```

  - *청약철회*: 소비자가 일정 기간 안에 계약을 무르는 권리. 법은 "대금을 환급한다"고만 적혀 있다.
  - *초일 불산입*: 첫날은 안 세고 다음 날부터 1일차로 세는 민법의 원칙.

## 규칙 1 — 기간: 하루가 전부냐 0이냐를 가른다 (DayCount)

**어떤 요구사항인가**: "수령일로부터 7일 이내." — 수령일이 1일차인지가 안 적혀 있다.

```text
3/1 수령, 변심 7일:
  날짜    3/1  3/2 ... 3/7  3/8  3/9
  산입    1일차 ......  7일차  X    X      → 3/7까지
  불산입  0일차 1일차 .. 6일차 7일차  X     → 3/8까지 (하루 더 여유)

3/8 신청: 산입이면 8일차(0원) / 불산입이면 7일차(24,000원)
```

- 측정(0~11일차 균등 신청 5,000건): 초일 하나로 갈린 건 **431/5,000 (8.6%)** — 금액이 반씩 갈리는 게 아니라 **전부냐 0이냐**라서 전부 분쟁이 된다.
- 당일(3/1) 신청은 양쪽 다 된다 — 1일차이거나 0일차.
- **기간이 지나도 던지지 않는다**: `Refund(0, …, withinWindow=false, daysElapsed=61, windowDays=7)`처럼 **얼마나 늦었는지를 값으로** 돌려준다. 던지면 화면에 "오류"만 뜨고 며칠 지났는지 못 보여준다 — **거절도 도메인의 정상 결과다.**

## 규칙 2 — 사유 한 줄이 기간과 배송비를 둘 다 바꾼다 (Reason)

**어떤 요구사항인가**: "단순 변심은 7일·배송비 소비자 부담, 하자는 30일·판매자 부담."

```text
3/20 신청 (수령 3/1), A 30,000원:
  단순 변심   기간 7일  → 지남 → 0원
  하자        기간 30일 → 안 지남 → 30,000원 전액 (배송비도 안 문다)
```

- 측정(0~39일차 균등): 변심 거부 3,971건 vs 하자 거부 1,126건, 환불 총액 5,183만 vs 2억 24만 — **"하자입니다" 한 줄이 금액을 3.9배로 만든다.**
- 사유는 소비자가 고르고 판매자가 다툰다 — 그래서 **두 사유를 다 계산해서 다툼의 값을 보여줄 수 있어야 한다.**

## 규칙 3 — 부분 반품: 두 줄이 아홉 가지로 갈린다

**어떤 요구사항인가**: 주문서에는 "할인 5,000원", "배송비 3,000원" 한 줄씩뿐이다. 품목별로 어떻게 흩어지는지는 아무 데도 안 적혀 있다.

주문: A 30,000 + B 20,000 = 50,000, 할인 −5,000, 배송비 3,000 (낸 돈 48,000). **A만 변심 반품:**

```text
             │ 배송비 전액  배송비 비례  배송비 안 뭄
  ───────────┼────────────────────────────────────
  할인 비례  │   24,000      25,200      27,000
  할인 안회수│   27,000      28,200      30,000  ← 제일 후함
  할인 전액  │   22,000      23,200      25,000
             └ 폭 8,000원 = 상품값의 27%
```

손계산 (할인 비례 + 배송비 비례): A는 전체의 60%(30,000/50,000) → 할인 회수 5,000×0.6=3,000, 배송비 3,000×0.6=1,800 → 30,000−3,000−1,800 = **25,200**.

- 비례배분은 **금액 기준**이다. 개수 기준(A·B 각 반)이면 2,500과 1,500 — 그것도 말이 된다. 어느 쪽인지 **정해야** 한다.
- 싼 B(20,000)만 반품 + 할인 전액 회수: 20,000−5,000−3,000 = 12,000 — 그리고 남은 A는 정가가 된다(할인이 사라졌다).
- 측정(무작위 5,000건): 아홉 조합의 폭 평균 5,631원, 최대 13,000원. 제일 박한 규칙이 제일 후한 규칙의 **89.5%** — 10.5% 차이인데 **아홉 규칙 어느 것도 법을 어기지 않는다.**

## 규칙 4 — 계산의 안전선

- **곱하기 먼저**: `share()`는 `금액 × 부분`을 먼저 하고 마지막에 나눈다(BigDecimal, HALF_UP). 나눗셈 먼저면 나머지가 사라진다.
- **분모 0 보호**: `whole == 0 → 0`. 사은품만 받고 배송비만 낸 주문(상품 0원)이 실제로 있고, 그걸 반품하면 `3,000 × 0 / 0`이 된다. **금액이 틀리는 게 아니라 환불 화면이 죽는다.** 변종 검증: 이 보호를 지워도 전부 통과했다 — 상품 0원 주문을 시험한 적이 없어서.
- **음수 환불이 존재한다**: 사은품 반품 + 배송비 전액 부담이면 total = −3,000 — 돌려받는 게 아니라 내야 한다. 이걸 어떻게 할지는 "생각해볼 것"으로 남아 있다.
- 생성 시점 검증: 수량 0 이하·음수 단가·품목 없음·sku 중복·할인 > 주문 금액·주문 수량 초과 반품·없는 품목은 전부 예외.

## 경계·모서리 케이스 — 예제가 숨기는 것

| 함정 | 왜 안 보이나 |
|---|---|
| 전부 반품으로만 시험 | 반품 금액 = 주문 금액이라 할인 비례=전액, 배송비 비례=전액 → 아홉 조합이 **네 값**(42,000/45,000/47,000/50,000)으로 준다. 측정: 728건 전부 |
| 할인 없는 주문으로만 시험 | 회수할 게 없어 배분 규칙 셋이 같은 27,000원 — 규칙이 통째로 안 보인다 |
| 할인도 배송비도 없는 주문 | 아홉이 **하나**가 된다 — "본질이 아니니까" 빼기 쉬운 게 바로 갈림의 원천 |
| 기간 지남을 예외로 처리 | 화면에 "오류"만 — 며칠 지났는지·며칠까지였는지를 값으로 돌려줘야 한다 |
| 상품 0원 주문 | 분모 0 — 예제에 없는 주문 형태가 실제로 존재한다 |

## 핵심 문장

- "7일 이내"의 하루는 경계가 아니라 **전부냐 0이냐의 절벽**이다 — 초일 산입 여부를 명시하지 않으면 8.6%의 신청이 분쟁이 된다.
- 주문서의 "할인 5,000원" 한 줄이 부분 반품에서 셋으로 갈린다 — **집계된 한 줄을 품목으로 나누는 규칙은 항상 별도의 결정**이고, 아홉 조합 전부 합법이다.
- 기간 지남은 예외가 아니라 값이다 — **거절 사유와 정도를 보여주는 것까지가 도메인 계산**이다.
- 사유(변심/하자)는 기간과 배송비를 동시에 바꾸는 분기다 — 소비자가 고르고 판매자가 다투므로 양쪽 다 계산 가능해야 한다.
- 전부 반품·할인 없음·배송비 없음 — 편한 예제 세 개가 아홉 갈래를 하나로 접어 버린다. **갈림이 보이는 입력을 일부러 만들어라.**

## 용어 풀이

- **청약철회**: 소비자가 기간 안에 계약을 무르는 법적 권리. 단순 변심 7일, 하자 30일이 관행적 기준.
- **초일 산입/불산입**: 첫날(수령일)을 1일차로 세나(산입) 다음 날부터 세나(불산입). 불산입이 민법 원칙이고 하루 더 여유.
- **DayCount / DiscountAllocation / ReturnShippingRule**: 안내문에 안 적힌 세 결정을 드러낸 enum — 기간 기산 2택 × 할인 회수 3택 × 배송비 3택.
- **할인 회수(clawback)**: 부분 반품 시 이미 준 할인을 도로 가져가는 것. 비례/안 회수/전액의 3택.
- **비례배분(proration)**: 반품 금액 비율(금액 기준)로 할인·배송비를 나누는 것. 개수 기준도 말이 되므로 기준 명시가 필수.
- **withinWindow / daysElapsed / windowDays**: 기간 판정의 결과 3종 — 됐나, 며칠째인가, 며칠까지였나. 거절 화면이 이 값으로 만들어진다.
- **사유(Reason)**: CHANGE_OF_MIND(변심) / DEFECT(하자). 기간과 배송비 부담을 동시에 바꾼다.
- **분모 0 보호**: 비율 계산에서 전체가 0이면 0을 돌려주는 방어. 상품 0원 주문(사은품+배송비)에서 화면이 죽는 것을 막는다.
- **record 생성자 검증**: 잘못된 주문·신청이 아예 못 만들어지게 입구에서 막는 것. 계산 코드가 깨끗해진다.
