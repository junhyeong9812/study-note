### A. 과제

#### 0. 규칙 한 줄이 안 말해주는 것

- 안 말해주는 자리 셋(원본 `Packer` 클래스 주석 그대로):

```text
 안 말해준 것            가능한 읽기
 "5 킬로그램까지"    →  무게로 나누나 부피로 나누나 둘 다 보나
 (넘는 물건 얘기 없음) →  혼자 한 상자로 보내나 아예 못 보낸다고 하나
 (순서 얘기 없음)     →  들어온 순서인가 큰 것부터인가 작은 것부터인가
 "까지"              →  딱 5,000 g 은 들어가나 안 들어가나
```

- 딱 5,000g: **들어간다.**\
  테스트가 `exceeds(4_000, 0, new Item("x", 1_000, 1), Limit.WEIGHT) == false` 로 못 박았다.\
  1,001g 이면 true 다 — 부등호가 `>` 라서 경계값 자체는 통과한다.
- 무게냐 부피냐를 안 정하면: **같은 주문이 규칙에 따라 다른 상자 수가 된다.**\
  앨범 11장은 무게로만 보면 1상자, 부피를 보면 2상자다 — 그리고 요금은 상자 수로 매긴다.
- 넘는 물건: **요구사항은 아무 말도 안 한다.**\
  이 챕터는 그 자리를 `Oversize` enum(`OWN_BOX` / `REJECT`)으로 올렸다.
- 순서: **문장에서는 절대 알 수 없다.**\
  "5kg까지"만 읽으면 순서가 결과를 바꾼다는 생각 자체가 안 떠오른다 — 그런데 3000/2500/2000/2500g 넷은 순서에 따라 2상자와 3상자로 갈린다.
- "서로 간섭한다": **결정 하나의 좋고 나쁨이 다른 결정을 무엇으로 정했느냐에 따라 뒤집힌다.**\
  부피로만 나누기는 요금만 보면 최선인데(4,816,500 vs 5,871,500), 그 결과 5kg 넘는 상자가 483개 생긴다.

> **간섭(interaction)** — 두 결정을 따로따로 고르면 좋은데, 합쳐 놓으면 나빠지는 관계.\
> 예: "부피로만 나누기"와 "상한을 지키기"는 각각은 말이 되는데, 같이 쓰면 6kg짜리 상자가 나온다.

- 요금이 상자 수에 붙으니: **세 결정이 전부 돈 문제가 된다.**\
  상자 하나 = 기본료 3,000원이고, 측정에서 규칙 하나 바꾸는 것만으로 500개 주문의 요금이 100만 원 넘게 움직였다.
- enum 으로 인자를 받는 이유: **세 갈래를 같은 코드로 전부 돌려보고 숫자를 비교하기 위해서다.**\
  하나를 코드 안에 박아버리면 "우리 규칙이 얼마짜리인가"를 잴 방법이 없어진다.

> **결정을 값으로 올린다(externalize a decision)** — 코드 안에 숨긴 선택을 밖에서 바꿀 수 있는 값(enum·설정)으로 꺼내는 것.\
> 예: `Limit.WEIGHT` / `VOLUME` / `BOTH` 를 인자로 받으면 세 판을 같은 입력에 돌려 상자 수 1,392 / 861 / 1,408 을 나란히 볼 수 있다.

#### 1. TODO 1 — exceeds

정답 코드 (impl/Packer.java):

```java
public boolean exceeds(long grams, long volume, Item item, Limit limit) {
    boolean overWeight = grams + item.grams() > maxGrams;
    boolean overVolume = volume + item.volume() > maxVolume;
    return switch (limit) {
        case WEIGHT -> overWeight;
        case VOLUME -> overVolume;
        case BOTH -> overWeight || overVolume;
    };
}
```

- 부등호는 **`>`** 다. `>=` 가 아니다.\
  "5,000g 까지"의 5,000 을 포함한다 — 딱 맞는 것은 안 넘는 것이다.

> **경계 포함(inclusive boundary)** — 한계값 자체가 허용 범위 안에 들어가는 것.\
> 예: "5kg까지"에서 정확히 5kg이 통과하면 포함, 튕기면 미포함. 부등호 한 글자가 이걸 정한다.

- 손계산 — 테스트가 박아둔 네 자리:

```text
 담긴 것        더 넣을 것     합      상한     exceeds
 4,000 g        1,000 g     5,000    5,000     false   ← 딱 맞으면 들어간다
 4,000 g        1,001 g     5,001    5,000     true
 29,000 cm3     1,000 cm3   30,000   30,000    false
 29,000 cm3     1,001 cm3   30,001   30,000    true
```

- 뒤집으면: **상한에 정확히 맞는 주문마다 상자가 하나씩 더 생긴다.**\
  상자 하나 = 기본료 3,000원이므로, 부등호 한 글자가 그런 주문 전부의 3,000원이다.\
  (정확히 몇 건이 그렇게 되는지는 원본에 측정치가 없다 — 내 추론)
- `BOTH` 는 **`||`** 다 — 어느 하나만 넘어도 새 상자다.\
  `&&` 로 쓰면 "무게도 넘고 부피도 넘어야" 새 상자가 되어, 앨범 11장(무게는 여유, 부피 초과)이 33,000cm³짜리 한 상자가 된다.
- `long` 두 개로 받는 이유: **"지금 상자에 담긴 총합"은 `Item` 이 아니다.**\
  `Item` 으로 받으려면 가짜 물건을 만들어야 하고, `grams > 0` 검증 때문에 빈 상자(0, 0)를 표현할 수도 없다.\
  실제로 `oversize` 는 이 덕분에 `exceeds(0, 0, item, limit)` 한 줄로 끝난다.
- 앨범 11장(장당 300g / 3,000cm³):

```text
 무게  300 x 11 = 3,300 g      <= 5,000     여유 있다
 부피 3,000 x 11 = 33,000 cm3  >  30,000    넘는다

   WEIGHT  1 상자
   VOLUME  2 상자   (앞 상자에 열 장 = 딱 30,000, 열한 번째가 새 상자)
   BOTH    2 상자
```

- 머그컵 5개(개당 1,200g / 800cm³):

```text
 무게 1,200 x 5 = 6,000 g     >  5,000     넘는다
 부피   800 x 5 = 4,000 cm3   <= 30,000    여유 있다

   WEIGHT  2 상자   (네 개 = 4,800 g, 다섯째가 새 상자)
   VOLUME  1 상자   ← 그 상자가 6,000 g
   BOTH    2 상자
```

- 그 6,000g 상자가 문제인 이유: **상한을 1kg 넘긴 상자인데, 코드는 아무 경고도 안 한다.**\
  요금표에도 안 나온다 — 대가는 택배 기사가 든다.

#### 2. TODO 2 — sorted

정답 코드:

```java
public List<Item> sorted(List<Item> items, FillOrder fillOrder) {
    List<Item> copy = new ArrayList<>(items);
    if (fillOrder == FillOrder.AS_IS) {
        return copy;
    }
    Comparator<Item> bySize = Comparator.comparingLong(this::score);
    if (fillOrder == FillOrder.LARGEST_FIRST) {
        bySize = bySize.reversed();
    }
    copy.sort(bySize.thenComparing(Item::id));
    return copy;
}

/** 상한 대비 크기. 만분율로 낸다. */
public long score(Item item) {
    return item.grams() * 10_000 / maxGrams + item.volume() * 10_000 / maxVolume;
}
```

- 상한으로 나누는 이유: **그램과 세제곱센티미터는 서로 다른 자다.**\
  그냥 더하면 숫자가 큰 쪽(부피)이 순서를 독차지한다.

> **정규화(normalization)** — 단위가 다른 값들을 각자의 기준으로 나눠 같은 자로 비교할 수 있게 만드는 것.\
> 예: 300g과 3,000cm³를 그냥 더하지 않고, 각각 상한 5,000g·30,000cm³로 나눈 뒤 더한다.

- 손계산 — 그냥 더할 때 vs 상한 대비(상한 5,000g / 30,000cm³):

```text
                 그램   세제곱cm   그냥 더하면    상한 대비 만분율
 머그컵 heavy   1,200      800       2,000        1,200x10000/5000  = 2,400
                                                    800x10000/30000 =   266
                                                                 합 = 2,666
 앨범   light     300    3,000       3,300          300x10000/5000  =   600
                                                  3,000x10000/30000 = 1,000
                                                                 합 = 1,600

 그냥 더하면  앨범(3,300) > 머그컵(2,000)     ← 부피 숫자가 커서 뒤집힌 순서
 상한 대비로  머그컵(2,666) > 앨범(1,600)     ← 테스트가 박아둔 값
```

- **상자를 더 잡아먹는 것은 머그컵이다.**\
  머그컵은 상한의 24%를 무게로 쓴다 — 네 개면 상자가 찬다.\
  앨범은 상한의 10%를 부피로 쓴다 — 열 장이 들어간다.\
  그러니 "큰 것부터"에서 먼저 자리를 잡아야 하는 쪽은 머그컵이다.
- 만분율인 이유: **정수 나눗셈이라 자릿수가 곧 해상도다.**\
  백분율로 재면 `800 × 100 / 30_000 = 2`(2.66이 잘린다)처럼 소수가 통째로 날아가, 서로 다른 크기가 같은 점수로 뭉개진다.\
  뭉개진 만큼 동점이 늘고, 동점이 늘면 순서를 id 가 정해버려 크기 기준이 무력해진다. (원본에 근거 없음 — 내 추론)

> **만분율(basis point 식 표기)** — 10,000분의 몇으로 비율을 적는 것. 소수점 없이 정수만으로 네 자리 정밀도를 쓴다.\
> 예: 상한 5,000g 중 1,200g은 24% = 2,400 만분율.

- 동점을 안 가르면: **같은 주문이 매번 다른 순서로 담긴다.**\
  자바의 `List.sort` 는 안정 정렬이라 같은 입력이면 같은 결과지만, **입력 순서가 조금만 달라져도**(장바구니 담은 순서, DB 조회 순서) 동점끼리의 순서가 따라 바뀐다.\
  `.thenComparing(Item::id)` 를 붙이면 입력 순서와 무관하게 늘 `a, b, c` 다 — 테스트가 `sorted(List.of(c, a, b), LARGEST_FIRST)` 와 `sorted(List.of(b, c, a), SMALLEST_FIRST)` 를 둘 다 `[a, b, c]` 로 못 박았다.

> **타이브레이크(tie-break)** — 1순위 기준이 같을 때 순서를 가르는 2순위 기준.\
> 예: 크기가 같으면 물건 번호(id) 순으로 — 이게 없으면 같은 주문의 송장이 매번 달라진다.

> **결정성(determinism)** — 같은 입력이면 언제 돌려도 같은 결과가 나오는 성질.\
> 예: 같은 장바구니를 두 번 결제하면 상자 구성도 송장도 똑같아야 고객센터가 "어제 것과 다르다"를 설명할 수 있다.

- 상자 수는 같은데 송장이 달라지는 게 문제인 이유: **고객·물류센터·CS 가 보는 문서가 바뀐다.**\
  "1번 상자에 앨범"이라고 안내해 놓고 실제로는 머그컵이 들어 있으면, 상자 수가 맞아도 클레임이다.
- 복사본을 만드는 이유(`AS_IS` 포함): **입력 리스트를 안 건드리겠다는 약속이다.**\
  `List.of(...)` 같은 불변 리스트가 들어오면 정렬이 예외가 나고, 가변 리스트가 들어오면 부르는 쪽의 리스트가 몰래 재배열된다.\
  `AS_IS` 도 복사본을 돌려줘야 세 갈래가 **같은 종류의 값**(마음대로 써도 되는 새 리스트)을 반환한다.

> **방어적 복사(defensive copy)** — 받은 컬렉션을 그대로 쓰지 않고 복사본을 만들어 다루는 것.\
> 예: `new ArrayList<>(items)` — 이걸 안 하면 `sorted` 를 부른 쪽의 장바구니 순서가 바뀌어 있다.

- `reversed()` 와 동점: **`bySize.reversed().thenComparing(Item::id)` 는 크기만 뒤집고 id 는 안 뒤집는다.**\
  `reversed()` 를 `thenComparing` **뒤에** 붙였다면 id 까지 뒤집혀 `LARGEST_FIRST` 의 동점이 `c, b, a` 가 됐을 것이다.\
  테스트가 `LARGEST_FIRST` 에서도 `[a, b, c]` 를 요구하므로 이 순서가 계약이다.

```text
 (bySize.reversed()).thenComparing(id)   →  크기 내림차순, 동점은 id 오름차순   ← 정답
 (bySize.thenComparing(id)).reversed()   →  크기 내림차순, 동점은 id 내림차순   ← 테스트가 거부
```

#### 3. TODO 3 — pack

정답 코드:

```java
List<Item> queue = sorted(items, fillOrder);
...
for (Item item : queue) {
    if (oversize(item, limit)) {
        if (oversizeRule == Oversize.REJECT) {
            rejected.add(item);
        } else {
            boxes.add(new Box(
                    List.of(item), item.grams(), item.volume(), true));
        }
        continue;
    }
    boolean placed = false;
    for (int i = 0; i < open.size(); i++) {
        long[] load = loads.get(i);
        if (!exceeds(load[0], load[1], item, limit)) {
            open.get(i).add(item);
            load[0] += item.grams();
            load[1] += item.volume();
            placed = true;
            break;
        }
    }
    if (!placed) {
        List<Item> fresh = new ArrayList<>();
        fresh.add(item);
        open.add(fresh);
        loads.add(new long[] {item.grams(), item.volume()});
    }
}
```

- 전략 이름: **first-fit(처음 맞는 곳에 넣기).**\
  큰 것부터 정렬해서 first-fit 을 돌리면 **first-fit decreasing**(FFD) 이다.

> **first-fit** — 열린 상자를 앞에서부터 훑어, 들어가는 첫 상자에 넣는 담기 전략. 안 들어가면 새 상자를 연다.\
> 예: [3,000g] [2,500g] 두 상자가 열려 있고 2,000g을 넣으면, 첫 상자가 5,000g으로 딱 차므로 거기 들어간다.

- **상자 수를 가장 적게 만들지는 않는다.**\
  테스트의 3000/2500/2000/2500g 넷은 합이 10,000g 이라 이론상 2상자가 최선인데, `SMALLEST_FIRST` 로 돌리면 3상자가 나온다.
- 그런데도 고른 이유: **단순하고 예측 가능하다.**\
  최적으로 담으려면 모든 조합을 따져야 하는데(빈 패킹은 정확히 풀기 어려운 문제다), 물류는 "왜 이렇게 담겼나"를 사람이 설명할 수 있어야 한다.\
  `pack` 결과는 앞 상자부터 훑은 결과라 손으로 재현된다. (원본에 명시 없음 — 내 추론)

> **빈 패킹(bin packing)** — 상한이 있는 통 여러 개에 물건을 나눠 담아 통 수를 최소로 만드는 문제. 정확한 최적해를 구하는 것이 매우 비싸서 보통 근사 전략을 쓴다.\
> 예: 이삿짐을 상자에 나눠 담기, 서버에 컨테이너 배치하기, 디스크에 파일 채우기.

- 손계산 — 상한 5,000g, 물건 a=3,000 / b=2,500 / c=2,000 / d=2,500:

```text
 들어온 순서 (a b c d)
   a → 새 상자1 [3,000]
   b → 상자1 3,000+2,500=5,500 > 5,000  안 들어감 → 새 상자2 [2,500]
   c → 상자1 3,000+2,000=5,000 <= 5,000 들어감    상자1 [5,000]
   d → 상자1 꽉 참, 상자2 2,500+2,500=5,000 들어감 상자2 [5,000]
                                                      두 상자

 큰 것부터 (a b d c — b,d 동점은 id 로 b 먼저)
   같은 방식으로 상자1 [a+c], 상자2 [b+d]           두 상자

 작은 것부터 (c b d a)
   c → 상자1 [2,000]
   b → 상자1 [4,500]
   d → 상자1 4,500+2,500=7,000 안 됨 → 상자2 [2,500]
   a → 상자1 7,500 안 됨, 상자2 5,500 안 됨 → 상자3 [3,000]
                                                      세 상자!

   작은 것들이 앞 상자를 어중간하게 채워, 큰 것이 못 들어갈 자리만 남긴다.
```

- `oversize` 를 `exceeds(0, 0, ...)` 로 파생시킨 이유: **두 규칙이 어긋날 수 없게 하려고.**\
  "빈 상자에 넣어도 넘나"가 곧 "혼자서도 넘나"다.\
  따로 구현하면 한쪽만 `>=` 로 고쳐도 아무 테스트가 안 깨지면서 두 판정이 갈라진다.

> **파생 정의(derived definition)** — 새 규칙을 새로 쓰지 않고 이미 있는 규칙의 특수한 경우로 표현하는 것.\
> 예: "혼자서도 상한을 넘는 물건" = "빈 상자(0, 0)에 넣어도 `exceeds` 인 물건".

- "넘는 물건"의 정의가 `Limit` 에 달려 있다: **같은 물건이 규칙에 따라 보낼 수 있기도 없기도 하다.**

```text
 40,000 cm3 짜리 가벼운 물건 (500 g / 40,000 cm3)

   Limit.WEIGHT   500 g <= 5,000       oversize 아님 → 그냥 담긴다, 거부 0건
   Limit.VOLUME   40,000 > 30,000      oversize     → REJECT 면 거부 1건
```

- 섞으면 나빠지는 것: **상한을 넘는 상자가 더 커진다.**\
  8kg 짜리에 앨범 둘(각 300g)을 섞으면 8,600g 상자가 된다 — 이미 규칙을 어긴 상자를 더 무겁게 만드는 것이다.\
  게다가 요금은 무게 초과분에 kg당 500원이 붙으므로 **비용도 는다.**
- 거부된 물건이 가는 곳: `Packing.rejected()` 목록.\
  `boxes` 에는 안 들어가므로 `boxCount()` 에도, `fee` 에도 안 잡힌다.
- 거부하면 요금: **0원이다** — 테스트가 `fee(rejecting) == 0` 으로 못 박았다.\
  그리고 고객은 주문을 못 한다.
- oversize 상자의 위치: **일반 상자 다음, 목록의 맨 뒤다.**\
  `packed.addAll(boxes)` 로 나중에 붙인다.\
  테스트가 `ownBox.boxes().get(1).oversize()` 와 `ids(...get(1)) == ["큰것"]` 로 확인하므로 — 입력에서는 "큰것"이 **첫 번째**였는데 결과에서는 **두 번째**다.
- 계약인가 구현 세부인가: **테스트가 인덱스로 박아뒀으므로 계약이다.**\
  다만 이 순서가 송장에 그대로 나가면 "화면 순서대로 담긴다"는 `AS_IS` 의 약속과 어긋난다 — 상한 넘는 물건은 어차피 예외 취급이라 뒤로 밀어둔 것으로 읽힌다. (원본에 명시 없음 — 내 추론)
- 상자마다 무게·부피를 들고 다니는 이유(`loads` 배열): **매번 상자 안 물건을 다시 더하면 같은 덧셈을 반복한다.**\
  물건 n개를 담을 때 상자를 앞에서부터 훑는 것만으로도 비교가 쌓이는데, 상자마다 내용을 매번 합산하면 그 위에 한 겹이 더 붙는다.\
  `long[] {grams, volume}` 하나를 갱신하면 더하기 두 번으로 끝난다.

- 올림 나눗셈: `(over + 999) / 1_000`\
  나누는 수보다 1 작은 값을 먼저 더하고 정수 나눗셈(버림)을 하면 결과가 올림이 된다.

> **올림 나눗셈(ceiling division)** — 나머지가 조금이라도 있으면 몫을 한 칸 올리는 나눗셈.\
> 예: 1g만 초과해도 1kg치 요금(500원)을 받는다 — `(1 + 999) / 1000 = 1`.

- 손계산:

```text
 상자 무게   초과분(=무게-2,000)   올림 킬로그램          요금
   1,500 g        -500  (<=0)          없음        3,000
   2,000 g           0  (<=0)          없음        3,000
   2,001 g           1     (1+999)/1000 = 1        3,000 +   500 = 3,500
   3,000 g       1,000  (1000+999)/1000 = 1        3,000 +   500 = 3,500
   8,000 g       6,000  (6000+999)/1000 = 6        3,000 + 3,000 = 6,000
                                        + oversize 5,000 = 11,000
```

- 초과분이 음수인데 올림 식을 그냥 태우면: **요금이 조용히 깎인다.**\
  자바의 `/` 는 0 쪽으로 자르기 때문에 대부분의 무게에서는 우연히 0이 나와 살아난다.\
  그런데 딱 한 구간에서 음수가 샌다:

```text
 상자 무게    over    over+999    (over+999)/1000    붙는 요금
     1 g    -1,999     -1,000          -1              -500   ← 기본료가 깎인다
   500 g    -1,500       -501           0                 0
 1,000 g    -1,000         -1           0                 0
 1,500 g      -500        499           0                 0

 1 g 짜리 상자의 요금이 3,000 원이 아니라 2,500 원이 된다.
 Item 은 grams > 0 만 요구하므로 1 g 짜리 물건은 만들 수 있다.
```

  그래서 `if (over > 0)` 로 **먼저 끊는다** — 음수를 올림 식에 절대 안 태운다.\
  이 버그는 예외를 안 내고 금액만 틀리므로, 1g짜리 물건을 안 파는 동안은 영영 안 보인다.

> **0 쪽으로 자르기(truncate toward zero)** — 자바 정수 나눗셈이 소수를 버리는 방향. 항상 0에 가까워진다.\
> 예: `-1.9` 를 내림하면 `-2` 지만 자바의 `-19 / 10` 은 `-1` 이다. 음수가 끼면 "버림"이 기대와 달라진다.

- 요금이 거부된 물건에 안 붙는다: **`fee` 는 `packing.boxes()` 만 돈다.**\
  `rejected` 는 요금 계산에 아예 안 들어간다 — 배송비 0원이고, 매출도 0원이다.
- 앨범 10장 요금:

```text
 한 상자 (3,000 g)     3,000 + (1000+999)/1000 x 500 = 3,000 + 500 = 3,500
 두 상자 (1,500 g x 2) 3,000 x 2                     = 6,000   (초과분 없음)
                                                  차이  2,500 원
```

  상자를 나눴더니 **총 무게는 같은데 요금이 71% 올랐다.**
- 상자를 하나 더 만들면: **최소 기본료 3,000원이 오른다.**\
  나눈 두 상자가 각각 2kg 이하면 초과요금이 사라지므로 딱 3,000원만 오르고, 그렇지 않으면 더 오른다.
- 8kg 혼자 보내기 = **11,000원** (테스트가 박아둔 값):

```text
 기본료           3,000
 초과 6 kg x 500  3,000
 oversize 추가    5,000
                 11,000
```

  상자 하나만 받으면 "거부된 물건은 요금 0"이라는 결정을 부르는 쪽이 매번 다시 해야 한다. (원본에 명시 없음 — 내 추론)

#### 6. 측정 — 하나: 부피로만 나누기

```text
 기준        상자     요금        5 kg 넘는 상자
 무게로만   1,392   5,820,000          0
 부피로만     861   4,816,500        483
 둘 다      1,408   5,871,500          0
```

- **상자 40% 감소, 요금 18% 감소** (원본 측정 주석 문구 그대로).
- 대가: **5kg 넘는 상자 483개.** 주문 500개 중 483개에 그런 상자가 들어 있다.
- 요금표에 안 나오는 이유: **요금은 상자 수와 무게로만 계산되고, "상한 위반"은 요금 항목이 아니다.**\
  6kg 상자도 요금 계산상으로는 그냥 "조금 비싼 상자"다.
- 최적화가 이 답을 고르는 이유: **목적함수에 없는 것은 제약이 아니다.**\
  "요금 최소화"만 시키면, 상한은 최적화기가 지켜야 할 이유가 없다.

> **지표 최적화의 함정(metric gaming / Goodhart)** — 지표를 목표로 삼는 순간, 지표에 안 잡히는 비용을 깎아서 지표를 좋게 만드는 답이 선택되는 것.\
> 예: 배송비를 지표로 걸면 "부피로만 나누기"가 1등이 되고, 그 대가인 6kg 상자는 지표 어디에도 안 나온다.

- 끌어올리는 법: **상한 위반을 세는 열을 대시보드에 나란히 둔다.**\
  측정 테스트가 실제로 그렇게 한다 — `box.grams() > packer.maxGrams()` 인 상자를 세서 483이라는 수를 만든다.\
  또는 위반을 요금으로 환산해(예: 위반 상자마다 벌점) 목적함수 안으로 넣는다. (원본에 없음 — 내 추론)

#### 7. 측정 — 둘: 한 종류만 팔면 안 보인다

```text
 가볍고 큰 것 비율   무게로만   부피로만                 둘 다
        0 %          2,174     500 (전부 무게 초과)     2,174
       50 %          1,392     861                     1,408
      100 %            528 (500 개 부피 초과)  1,291    1,291
```

- 무겁고 작은 것만(0%): **무게로만 = 둘 다** (2,174로 같다).\
  부피가 절대 상한에 안 닿으니 부피 조건이 한 번도 발동하지 않는다.
- 가볍고 큰 것만(100%): **부피로만 = 둘 다** (1,291로 같다).\
  무게가 절대 상한에 안 닿으니 무게 조건이 한 번도 발동하지 않는다.
- 버그가 나타나는 시점: **다른 종류를 하나 붙이는 날.**\
  코드는 그대로인데 **상품 구성이 바뀌는 날** 상자가 터진다.
- 코드를 안 고쳤는데 버그가 나타난다: **버그는 코드 안에 처음부터 있었고, 입력이 그 자리를 안 밟고 있었을 뿐이다.**\
  테스트가 초록인 이유가 "코드가 맞아서"가 아니라 "그 경로를 안 밟아서"일 수 있다.

> **잠복 결함(latent defect)** — 코드에 이미 있지만 특정 입력이 오기 전까지는 증상이 없는 결함.\
> 예: 부피 상한을 안 보는 코드는 무겁고 작은 물건만 파는 동안 아무 문제도 안 일으킨다.

- 배포 전에 잡는 법: **테스트 데이터를 상품 구성 비율로 쪼개서 돌린다.**\
  0% / 30% / 50% / 100% 네 지점을 다 돌리는 것이 정확히 그 방법이다 — 50%만 봤으면 무게로만(1,392)과 둘 다(1,408)가 달라서 "둘 다 필요하구나"를 알지만, 0%만 봤으면 둘이 같아서 모른다.

#### 8. 측정 — 셋: 주문이 작으면 순서가 안 보인다

```text
 주문 크기   들어온 순서   큰 것부터   작은 것부터
   4 건          596        596         596
   8 건        1,054      1,048       1,085
  12 건        1,408      1,397       1,470
  20 건        2,175      2,149       2,319
```

- 4건에서 같은 이유: **물건이 넷이면 대개 한두 상자라 순서가 끼어들 자리가 없다.**\
  상자가 하나면 무엇을 먼저 넣든 다 같은 상자에 들어간다.
- 20건 차이: **작은 것부터가 큰 것부터보다 170개 더** (2,319 − 2,149 = 170).
- 요금으로: 기본료만 세면 **170 × 3,000 = 510,000원.**\
  (초과요금은 상자 구성에 따라 달라서 원본에 별도 수치가 없다 — 기본료만 센 내 계산이다.)
- "개발할 때 만드는 주문이 대개 두세 건이다"가 경고인 이유: **개발자가 손으로 만드는 데이터가 정확히 버그를 안 밟는 크기다.**\
  테스트를 아무리 돌려도 초록인데, 실제 고객 주문에서만 갈린다.
- 손으로 만든 주문으로 테스트하면: **담는 순서 결정의 효과를 통째로 못 본다.**\
  "순서는 아무래도 상관없네"라는 잘못된 결론까지 얻는다.

#### 9. 측정 — 넷: 거부가 요금을 네 배로 가른다

```text
 초과 비율   혼자 보내기              못 보내기
    0 %      5,871,500 / 거부 0      5,871,500 / 거부     0
    5 %      8,882,500 / 거부 0      5,557,000 / 거부   297
   20 %     18,271,500 / 거부 0      4,783,000 / 거부 1,200
```

- 0%에서 같은 이유: **oversize 물건이 하나도 없으면 두 규칙의 분기 자체가 실행되지 않는다.**\
  `oversize(item, limit)` 가 항상 false 라 `OWN_BOX` 도 `REJECT` 도 도달하지 않는다.
- 20%의 차이: **18,271,500 vs 4,783,000 — 약 네 배.**
- 싼 쪽이 싼 진짜 이유: **1,200건을 안 판 결과다.**\
  배송비를 줄인 게 아니라 매출을 없앤 것이다.
- 꼬집는 것: **비용 지표 하나만 보면 "아무것도 안 하기"가 늘 1등이라는 것.**\
  비용은 매출과 같이 봐야 의미가 있다.
- 경영진에게 같이 보여야 하는 열: **거부 건수(그리고 그 건수가 곧 잃은 매출이라는 환산).**\
  요금 열만 있는 표는 "못 보내기가 싸다"는 잘못된 결론으로 곧장 간다.

#### 10. 측정 — 다섯: 한 상자면 전부 같다

  18개 조합 중 첫 번째를 기준(reference)으로 잡고 나머지 17개와 견주므로 주문 하나당 17회다.
- 초록색을 못 믿게 하는 이유: **테스트가 통과했다는 것이 "코드가 맞다"가 아니라 "그 입력이 차이를 못 만든다"일 수 있다.**\
  두 건짜리 주문으로 짠 테스트 스위트는 18가지 규칙 조합을 전부 돌려도 아무 차이를 못 잡는다.

> **가려짐(masking)** — 입력이 작거나 한쪽에 치우쳐서, 실제로 존재하는 차이가 결과에 안 나타나는 것.\
> 예: 두 건짜리 주문에서는 `WEIGHT` 와 `VOLUME` 이 같은 답을 주지만, 12건이면 1,392와 861로 갈린다.

#### 11. 변종 검증에서 고친 것

- **변종(mutation) 검증**: 정답 코드에 일부러 작은 오류를 심은 판을 여러 개 만들고, 기존 테스트가 그 판들을 **전부 실패시키는지** 확인하는 방법.

> **변종 테스트(mutation testing)** — 코드를 일부러 조금 틀리게 바꾼 뒤, 테스트가 그 변화를 잡아내는지로 테스트의 품질을 재는 기법.\
> 예: `>` 를 `>=` 로 바꾼 판을 돌려보고, 테스트가 빨간불이 되면 "그 경계는 테스트가 지키고 있다"는 뜻이다.

- 17개가 전부 잡혔다 = **테스트가 이 코드의 중요한 결정들을 빠짐없이 덮고 있다.**\
  "고칠 것이 없었다"는 구현 자랑이 아니라 **테스트망이 촘촘하다는 증거**다.
- 각각 다른 테스트에 걸린 게 좋은 신호인 이유: **테스트 하나가 실패하면 어느 결정이 깨졌는지 바로 알 수 있다.**\
  다섯 자리가 전부 같은 테스트 하나에 걸려 있으면, 빨간불을 봐도 어디가 원인인지 모른다.
- 변종이 안 잡히면: **테스트를 고쳐야 한다.**\
  코드는 (변종을 심기 전에는) 맞는 상태였고, 못 잡는 것은 테스트의 결함이다.

#### 12. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- **상자 수 vs 상한 준수 — 무엇이 계약인가**: 코드가 답을 반쯤 보여준다.\
  `Limit.VOLUME` 은 상한을 어긴 상자를 만들 수 있는데(6,000g 상자), 코드는 그걸 막지도 표시하지도 않는다 — `Box.oversize` 는 **혼자서 넘는 물건**에만 true 다.\
  즉 현재 모델에서 계약인 것은 **상자 수(= 요금)** 고, 상한은 `Limit` 를 뭘로 고르냐에 딸린 부수 효과다.\
  상한을 진짜 계약으로 만들려면 `pack` 이 상한 넘는 상자를 만들었을 때 **거부하거나 최소한 표시**해야 한다. 지금은 측정 테스트만 그걸 세고 있다.
- **송장 순서 vs 상자 수 — 무엇을 포기하나**: 이 코드는 둘을 `FillOrder` 로 양자택일시킨다.\
  `AS_IS` 는 송장 순서를 지키고 상자 수를 포기하고, `LARGEST_FIRST` 는 반대다(12건에서 1,408 vs 1,397, 20건에서 2,175 vs 2,149).\
  차이가 크지 않은 구간(작은 주문)에서는 `AS_IS` 가 낫고, 주문이 커질수록 `LARGEST_FIRST` 의 이득이 커진다.\
  셋째 길도 있다 — **담기는 크기 순으로 하되 송장은 원래 순서로 출력**하기. 상자 안 내용물 순서만 다시 정렬하면 되고, 상자 수는 그대로다.
- **거부하면 고객에게 무엇을 보여주나**: 지금 모델은 `rejected` 라는 **물건 목록**만 준다 — 이유가 없다.\
  고객에게 쓸모 있으려면 최소한 "왜"(무게 초과인지 부피 초과인지)와 "얼마나"(상한 대비 얼마를 넘었는지)가 필요하다.\
  `exceeds` 가 `boolean` 대신 어느 축을 넘었는지를 돌려주면 그 메시지를 만들 수 있다 — 지금은 `overWeight` / `overVolume` 을 계산해 놓고 버린다.\
  덧붙여, 거부는 **장바구니 단계**에서 나와야 한다. 결제 후에 나오면 그건 환불이다.
- **한 상자만 반품되면 배송비를 어떻게 나누나**: 코드는 주문 전체의 요금만 계산하고, **상자별 요금**은 안 남긴다.\
  `fee` 의 루프 안에서 상자마다 금액이 이미 계산되니 그걸 `Box` 에 붙여 두는 것이 자연스러운 확장이다.\
  나누는 방식은 셋 — 상자별 실제 요금대로(계산이 이미 있으니 제일 정확하다) / 상자 수로 균등 분할(설명이 쉽다) / 무게 비율로 분할(요금 구조와 어긋난다: 기본료는 무게와 무관하다).\
  어느 쪽이든 **상자 단위로 돈을 기억해야** 가능한 일이다 — 지금 모델은 합계만 돌려주므로 반품 계산을 아예 못 한다.

#### 13. 연결

- 01-parking-fee 와 같은 자리: **"까지"의 경계 포함 여부.**\
  저기서는 "10분까지 무료"의 10분이 무료인가(`minutes <= freeMinutes`), 여기서는 "5kg까지"의 5,000g이 들어가는가(`> maxGrams`)다.\
  둘 다 부등호 한 글자가 모든 경계 주문의 금액을 바꾼다.
- 재는 것의 차이: 알고리즘 트랙은 **비교 횟수**(같은 답으로 가는 비용)를 셌다.\
  여기서 세는 것은 **규칙을 다르게 골랐을 때의 결과 차이** — 상자 수·요금·상한 넘는 상자 수·거부 건수다.\
  답이 하나가 아니라 여럿이라서, 비용이 아니라 **선택의 값**을 잰다.
- 순서가 답을 바꾸는 성질: **탐욕 알고리즘(greedy)의 순서 의존성**과 같은 자리다.\
  first-fit 은 앞에서부터 되는 대로 넣는 탐욕 전략이라, 입력 순서가 결과를 바꾼다 — 그래서 "큰 것부터"(FFD)가 대체로 낫다.

> **탐욕 알고리즘(greedy)** — 매 단계에서 그 순간 제일 좋아 보이는 선택을 하고 되돌아보지 않는 전략.\
> 예: 앞 상자부터 훑어 들어가는 첫 상자에 넣는 것 — 나중에 큰 물건이 올 것을 고려하지 않는다.

- 동점을 id 로 가르는 것: **정렬 결과의 안정성·커서 페이지네이션의 관행과 같다.**\
  정렬 키가 동점이면 페이지 경계에서 같은 행이 두 번 나오거나 아예 빠진다 — 그래서 실무에서 정렬 키 끝에 항상 고유 키(id)를 붙인다.
- 지표에 안 잡히는 비용이 밟히는 현상: **SLO·비용 최적화 사고와 같은 모양이다.**\
  응답시간만 지표로 걸면 캐시가 오래된 데이터를 주고, 비용만 지표로 걸면 이중화가 사라진다.\
  여기서는 요금만 지표로 걸었더니 택배 기사가 6kg 상자를 든다.
