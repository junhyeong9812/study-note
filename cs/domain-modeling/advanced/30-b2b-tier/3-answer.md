### A. 과제

#### 0. 말 한 줄이 안 말해주는 것

```text
 안 말해준 것        가능한 읽기
 "연"             →  최근 12 개월(ROLLING_12M) / 지난해(LAST_YEAR) / 누적(LIFETIME)
 (내려갈 때?)     →  바로(IMMEDIATE) / 한 등급씩(ONE_STEP) / 한 달 봐주기(GRACE)
 (언제 세나?)     →  돈이 들어온 날(PAID_ONLY) / 주문한 날(ORDERED)
```

- "연"에 세 읽기가 있는 이유: **"1년치"는 길이만 말하고 시작점을 안 말한다.**\
  어제부터 거꾸로 1년인지, 달력의 작년 한 해인지, 아예 처음부터인지가 다 다르다.
- 2026-01이 셋으로 갈리는 과정 (2025-01에 2억, 그 뒤 매입 없음, 최근 12개월):

```text
 2025-12  창 = 2025-01 ~ 2025-12  → 2 억      raw 플래티넘   applied 플래티넘
 2026-01  창 = 2025-02 ~ 2026-01  → 0 원      raw 브론즈     applied 는 규칙마다 다르다

   바로 내리기    applied = raw                      →  브론즈
   한 등급씩      applied = applied.down()           →  골드   (플래티넘의 한 칸 아래)
   한 달 봐주기   지난달 raw 도 낮았나? 아니다(플래티넘) →  플래티넘 유지
```

- "서로 간섭한다": **한 축의 값이 다른 축을 아예 죽인다.**\
  실제 예 셋 —
  - **지난해** 창을 고르면 한 해 내내 금액이 고정이라 **하락 규칙도 매출 기준도 아무 일을 안 한다**(변경 0회).
  - **누적** 창을 고르면 매출이 줄지 않아 **하락 규칙 셋이 통째로 같다**(600번 비교에서 0).
  - **미수도 지연도 없으면** 두 매출 기준이 통째로 같다(900번 비교에서 0).
- 최근 12개월 + 바로 내리기: **매달 등급이 오르내린다.**\
  한 달 매입이 비기만 해도 창에서 큰 건이 빠지면서 바로 떨어진다.
- 누적: **한 번 올라간 등급이 안 내려온다.** 3,600개 짝에서 브론즈인 달이 **0개**다.
- 주문 기준: **미수금이 등급을 올린다.** 돈을 안 낸 거래처가 골드 할인을 받는다.

#### 1. TODO 1 — countable

정답 코드 (impl/TierPolicy.java):

```java
LocalDate when = revenue == Revenue.PAID_ONLY
        ? purchase.paidOn()
        : purchase.orderedOn();
if (when == null) {
    return false;
}
YearMonth month = YearMonth.from(when);
return switch (window) {
    case ROLLING_12M -> !month.isAfter(asOf) && !month.isBefore(asOf.minusMonths(11));
    case LAST_YEAR -> month.getYear() == asOf.getYear() - 1;
    case LIFETIME -> !month.isAfter(asOf);
};
```

- 어느 날짜를 보는지는 **`Revenue`(매출 기준)** 가 정한다 — 결제 기준이면 `paidOn`, 주문 기준이면 `orderedOn`.
- 미수가 어느 창에도 안 들어가는 이유: **`paidOn` 이 `null`** 이라 **비교할 날짜 자체가 없다.**\
  창이 아무리 넓어도(누적이어도) 들어갈 수 없다 — 미수는 **영영 0원**이다.

> **미수(未收, arrears)** — 주문은 됐는데 돈이 아직 안 들어온 건.\
> 예: 3/31에 5,000만 원어치를 주문하고 입금이 없으면, 결제 기준으로는 그 거래처의 매출이 0원이다.

- 2026-03의 최근 12개월: **2025-04 ~ 2026-03**(산정 달 포함, 12개월).

```text
 asOf = 2026-03
   asOf.minusMonths(11) = 2025-04
   2025-03  이전이라 제외      2025-04  포함(경계)      2026-03  포함(산정 달)
   2026-04  미래라 제외
```

- 산정 달을 빼면: **이번 달 매입이 다음 달에야 반영된다.**
- 월말에 크게 사는 거래처: 3/31에 사면 **4월이 돼야 등급이 오른다.**\
  매달 월말에 사는 습관이면 **매달 한 달씩 손해**를 본다 — 같은 금액을 사도 남보다 늘 늦게 승급한다.
- 지난해 창: **`month.getYear() == asOf.getYear() - 1`** — 달이 아니라 **연도만** 본다.
- 누적에도 상한이 있다: **`!month.isAfter(asOf)`** — 산정 달까지만 센다.\
  "누적"이라도 **미래는 안 센다**는 것이 계약이다.
- 미래를 안 막으면: **다음 달 예정 주문이 이번 달 등급을 올린다.**\
  그리고 **그 주문은 취소될 수 있다** — 이미 준 할인은 못 돌려받는다.

#### 2. TODO 2 — tierFor

정답 코드:

```java
Tier tier = Tier.BRONZE;
for (Tier candidate : Tier.values()) {
    if (amountCents >= candidate.threshold()) {
        tier = candidate;
    }
}
return tier;
```

- **5,000만 원 정확히는 골드다**(`>=`). 4,999만 9,999원이면 실버다.
- "넘어야"(`>`)로 잡으면: **딱 맞춘 거래처가 한 등급 아래**가 된다.
- 중요한 이유: **거래처는 딱 맞춰 산다.**\
  "5,000만 원부터 골드"라고 공지하면 연말에 4,900만 원인 거래처가 **정확히 100만 원**을 더 산다.\
  즉 경계는 드문 자리가 아니라 **거래가 몰리는 자리**다 — 거기서 한 글자를 틀리면 가장 많은 거래처가 한꺼번에 틀린다.
- 위/아래에서 훑기:

```text
 아래에서부터 (이 구현)   조건을 만족하는 마지막 등급을 남긴다
   0 >= 0(브론즈) ✓ → 브론즈 / 5000만 >= 1000만 ✓ → 실버 / >= 5000만 ✓ → 골드 / >= 2억 ✗
   결과 골드                         enum 선언 순서가 오름차순이라는 것에 기댄다

 위에서부터               만족하는 첫 등급에서 멈춘다(early return)
   같은 답을 내지만, 선언 순서가 내림차순이어야 한다
```

  어느 쪽이든 **enum 선언 순서에 결과가 달려 있다** — 등급을 새로 끼워 넣을 때 순서를 지켜야 한다. (비교는 내 추론)
- `Tier.BRONZE.down() == BRONZE`(자기 자신).\
  제일 아래에서 더 내려갈 곳이 없기 때문이다 — **`down()` 을 아무 데서나 불러도 안전하게** 만든 것이다(배열 범위를 벗어나지 않는다).

#### 3. TODO 3 — revenueOf

정답 코드:

```java
long sum = 0;
for (Purchase purchase : purchases) {
    if (purchase.buyerId().equals(buyerId)
            && countable(purchase, asOf, window, revenue)) {
        sum += purchase.amountCents();
    }
}
return sum;
```

- 거르는 두 조건: ① **거래처 번호가 같다** ② **`countable` 이 참이다**(창·매출 기준).
- 안 거르면: **전체 매출로 등급을 매긴다.**
- 제일 큰 거래처가 있으면: **그 한 곳의 매출이 모든 거래처를 플래티넘으로 만든다.**\
  테스트가 이것을 못 박는다 — 거래처 `b` 가 1,000만 원인데 `other` 가 5억이어도 `b` 의 매출은 **1,000만 원**이어야 한다.
- 테스트에서 안 잡히기 쉬운 이유: **거래처가 하나뿐인 자료로 테스트하면 절대 안 드러난다.**\
  한 곳만 넣으면 걸러도 안 걸러도 합계가 같다.\
  잡으려면 **다른 거래처의 큰 건을 일부러 섞어 놓아야** 한다 — 원본 테스트가 그렇게 만들었다.

> **오염 테스트(contamination case)** — 정답에 섞이면 안 되는 자료를 일부러 넣어 두고, 결과가 안 변하는지 보는 테스트.\
> 예: 다른 거래처의 5억짜리 매입을 같은 목록에 넣고, 이 거래처의 매출이 그대로 1,000만 원인지 확인한다.

#### 4. TODO 4 — monthly

정답 코드:

```java
List<Grade> grades = new ArrayList<>();
Tier applied = Tier.BRONZE;
Tier previousRaw = Tier.BRONZE;

for (YearMonth month = from; !month.isAfter(toInclusive);
        month = month.plusMonths(1)) {
    long amount = revenueOf(purchases, buyerId, month, window, revenue);
    Tier raw = tierFor(amount);

    if (raw.ordinal() >= applied.ordinal()) {
        applied = raw;
    } else {
        applied = switch (demotion) {
            case IMMEDIATE -> raw;
            // 이 가지에 오면 raw 가 applied 보다 낮다. 그래서 한 등급 내린
            // 값이 raw 보다 더 내려가는 일은 없다. 따로 안 막아도 된다.
            case ONE_STEP -> applied.down();
            case GRACE -> previousRaw.ordinal() < applied.ordinal()
                    ? raw
                    : applied;
        };
    }
    grades.add(new Grade(month, amount, raw, applied));
    previousRaw = raw;
}
return List.copyOf(grades);
```

- 올라갈 때 같은 이유: **`raw >= applied` 가지에서는 `demotion` 을 아예 안 본다.**\
  그래서 성장하는 거래처만 보면 **세 규칙이 완전히 같아 보인다** — 갈리는 것은 매입이 주는 날부터다.
- 가르는 조건문: **`raw.ordinal() >= applied.ordinal()`**(같거나 높으면 상승 처리).
- `ONE_STEP` 이 내리는 것은 **`applied`** 다(`applied.down()`).\
  `raw` 를 내리면 한 번에 바닥까지 떨어져 `IMMEDIATE` 와 같아진다.
- `GRACE` 의 판단 기준: **지난달의 `raw`**(`previousRaw`)가 지금의 `applied` 보다 낮았나.\
  낮았으면 "두 달 연속 낮다"이므로 내리고, 아니면 이번 달은 봐준다.
- `GRACE` 가 내릴 때는 **`raw` 까지 한 번에** 내린다(한 등급씩이 아니다).
- `previousRaw` 를 따로 드는 이유: **`applied` 만으로는 "지난달이 실제로 낮았는지"를 알 수 없다.**\
  지난달에 봐줘서 `applied` 가 높게 유지됐다면, `applied` 를 봐서는 그 달이 낮았다는 사실이 지워져 있다.\
  그래서 **규칙이 손대지 않은 원본 등급**을 따로 기억해야 한다.
- `Grade` 가 둘을 드는 이유:

```text
 raw      매출만 보고 매긴 등급     ← "실제 실적은 이렇다"
 applied  하락 규칙을 거친 등급     ← "이번 달 실제로 준 등급"
 둘이 다른 달 = 규칙이 떠받친 달(propped)
```

  하나만 남기면 **"왜 브론즈인데 플래티넘 할인을 받았나"** 를 설명할 수 없다.
- `propped()`: **실제 등급이 매출 등급보다 높은 것** — `applied.ordinal() > raw.ordinal()`.\
  `GRACE` 와 `ONE_STEP` 에서만 생긴다. `IMMEDIATE` 는 항상 `applied == raw` 라 절대 안 생긴다.\
  (측정에서 `ONE_STEP` 의 부양된 달이 0인 것은, 그 자료에서 한 번에 두 등급 떨어지는 일이 없어 `ONE_STEP` 이 `IMMEDIATE` 와 같게 움직였기 때문이다.)
- 브론즈에서 시작하는 것이 안전한 이유: **브론즈는 제일 낮은 등급**이라 첫 달의 `raw` 가 무엇이든 `raw >= applied` 가 참이 된다.\
  그래서 **첫 달은 반드시 상승 가지로 들어가** 매출 그대로의 등급을 받는다 — 하락 규칙이 첫 달에 오작동할 여지가 없다.

#### 5. 측정 — 발견 하나: 지난해 기준은 한 해가 고정

- 변경 0인 이유: 2026년 열두 달 내내 **창이 2025년 한 해로 똑같다.**\
  매달 같은 금액 → 같은 `raw` → 첫 달에 정해진 `applied` 가 열두 달 그대로다.

```text
 asOf 2026-01 → 창 2025 년       금액 X
 asOf 2026-02 → 창 2025 년       금액 X   (같다)
 ...
 asOf 2026-12 → 창 2025 년       금액 X   (같다)
 변경이 일어날 계기가 없다
```

- 다른 두 축: **둘 다 죽는다.**\
  등급이 안 변하니 하락 규칙이 발동할 일이 없고, 매출 기준(결제/주문)도 한 해가 다 지나간 뒤라 미수·지연이 이미 결판나 있다.\
  README의 표현대로 **"하락 규칙도 매출 기준도 아무 일을 안 한다."**
- `IMMEDIATE` 와 `ONE_STEP` 이 똑같이 98인 이유: **이 자료에서 한 번에 두 등급이 떨어지는 일이 없었다.**\
  한 등급씩 떨어지는 경우에는 `applied.down()` 과 `raw` 가 같은 값이다.\
  즉 두 규칙의 차이는 **두 등급 이상 급락할 때만** 드러난다.
- 45로 줄어든 대신 생긴 것: **부양된 달 51개.**\
  변경 횟수(등급 안내 메일)를 53건 줄이는 대신, **매출은 낮은데 높은 등급 할인을 준 달이 51개** 생겼다.
- 부양된 달 51: **회사가 51개월치 할인을 실적 없이 내줬다**는 뜻이다.\
  거래처 입장에서는 "한 달 쉬어도 등급이 안 떨어지는" 안정성이고, 회사 입장에서는 비용이다 — **같은 숫자가 두 얼굴**이다.

#### 6. 측정 — 발견 둘: 미수가 흔들어 놓는 것

```text
  미수   결제 기준           주문 기준
   0 %   실버이상 3,574  변경  26     3,574  변경 24
   5 %   실버이상 3,547  변경  44     3,578  변경 17
  15 %   실버이상 3,441  변경  98     3,562  변경 20
  40 %   실버이상 2,840  변경 282     3,568  변경 24
```

- 결제 기준의 변경: **26 → 282, 약 11배.**
- 주문 기준이 20대에 머무는 이유: **주문 기준은 미수를 그냥 센다.**\
  돈이 들어왔는지 여부가 계산에 아예 안 들어가므로, 미수 비율을 올려도 매출 곡선이 거의 안 변한다(실버 이상도 3,574 → 3,568로 사실상 그대로다).
- "나쁘다"고 말할 수 없는 이유: **요동친다는 것은 등급이 실제 상황을 따라가고 있다는 뜻**이다.\
  미수가 40%인 거래처는 실제로 위태로운 거래처이고, 결제 기준은 그 사실을 **등급에 반영하고 있다.**\
  주문 기준의 "안정적인 24회"는 **위험을 안 보고 있는 안정성**이다.
- 현실에서의 282: **등급 안내 메일 282통**이다.\
  거래처 300곳에 한 해 동안 282번의 "등급이 변경되었습니다"가 나간다 — 거의 곳마다 한 번씩이다.
- 미수 40%의 실버 이상: 결제 기준 **2,840 / 3,600**, 주문 기준 **3,568 / 3,600**.\
  차이 728개월치가 **"돈은 안 들어왔는데 할인은 나간 달"** 이다.

#### 7. 측정 — 발견 셋: 누적 창

- 206번의 방향: **전부 상승**이다.\
  누적 매출은 **줄지 않는다**(과거 매입이 창 밖으로 빠지지 않으므로). 그래서 `raw` 가 절대 안 내려가고 `raw >= applied` 가지만 탄다.
- 브론즈인 달이 0인 이유: 2026년 첫 달에 이미 **2024~2025년 매입이 전부 누적**되어 최소 실버 이상이 된다.\
  그리고 한 번 올라간 등급은 안 내려온다.
- 문제: **등급이 "지금 얼마나 거래하는가"가 아니라 "과거에 얼마나 샀는가"를 나타내게 된다.**\
  3년 전에 크게 사고 지금은 거래가 없는 곳이 계속 골드 할인을 받는다 — 할인의 대가로 받아야 할 **현재의 거래가 없다.**
- 159 vs 108: 창이 다르므로 **브론즈로 떨어지는 조건이 다르다.**\
  최근 12개월은 **매달** 창이 움직여서 큰 건이 빠지는 달마다 브론즈로 내려앉을 수 있다(159개월).\
  지난해 창은 1년치가 통으로 고정이라, 브론즈인 거래처는 **열두 달 내내 브론즈**이고 아닌 곳은 한 번도 안 떨어진다 — 108은 곧 **9곳이 한 해 내내 브론즈**였다는 뜻이다(108 = 9 × 12). (계산은 내 추론)

#### 8. 측정 — 발견 넷·다섯

- 누적 창에서 하락 규칙이 죽는 이유: **누적 매출은 줄지 않으니 내려갈 일이 없다.**\
  `else` 가지(하락 처리)에 **한 번도 안 들어간다** — 그 안에 무엇을 써 놓아도 결과가 같다(300곳 × 2비교 = 600번에서 어긋남 0).
- 설정 화면에 셋을 두고 누적을 고르면: **그 설정이 죽는다.**\
  화면에는 라디오 버튼 셋이 멀쩡히 보이는데 **무엇을 골라도 결과가 같다.**\
  고른 사람은 자기가 정책을 정했다고 믿는다.
- 두 매출 기준이 같아지는 이유: 미수도 지연도 없으면 **`paidOn == orderedOn`** 이다.\
  `countable` 이 보는 날짜가 같은 값이니 두 기준이 **글자 그대로 같은 계산**이 된다(300곳 × 3창 = 900번에서 어긋남 0).
- 위험한 이유: **개발할 때 만드는 매입이 대개 그 모양**이다 — 주문일과 입금일을 같은 값으로 넣는다.\
  그 자료로는 **매출 기준을 아무거나 골라도 테스트가 통과**한다.
- 그날: **그 거래처가 어려워진 날**이다.\
  즉 이 갈래는 **평온할 때는 안 보이다가 사고가 난 날 처음 나타난다** — 가장 나쁜 타이밍이다.
- 공통 교훈: **"설정이 결과를 안 바꾼다"는 것이 "설정이 안전하다"는 뜻이 아니다.**\
  안 바뀌는 이유가 **자료의 성질** 때문이면, 그 성질이 깨지는 날 설정이 한꺼번에 효력을 갖는다.\
  그래서 축을 검증할 때는 **그 축이 실제로 갈리는 자료**를 일부러 만들어야 한다.

> **잠재 갈래(latent branch)** — 지금 자료에서는 결과가 같아 보이지만, 조건이 바뀌면 갈라지는 설정.\
> 예: 주문일과 입금일이 같은 자료에서는 결제 기준과 주문 기준이 완전히 같은 답을 낸다.

#### 9. 함정

- 넷:
  1. **문턱을 "넘어야"로 잡는 것** — 딱 맞춘 거래처가 한 등급 아래다. 그리고 거래처는 딱 맞춰 산다.
  2. **최근 12개월에서 산정 달을 빼는 것** — 이번 달 매입이 다음 달에야 반영된다.
  3. **미래의 매입을 세는 것** — 다음 달 예정 주문이 이번 달 등급을 올린다.
  4. **거래처 번호로 안 거르는 것** — 제일 큰 거래처 하나가 모두를 플래티넘으로 만든다.
- 방향:

```text
 조용히 올린다   ③ 미래 매입을 셈      → 취소될 주문으로 할인을 준다
 조용히 올린다   ④ 거래처 미필터       → 전원이 최고 등급이 된다
 조용히 내린다   ① "넘어야" 로 잡음    → 경계에 몰린 거래처가 한 칸 아래
 조용히 내린다   ② 산정 달 제외        → 모두가 늘 한 달씩 늦게 승급한다
```

- 한 달 늦게 반영되면: **월말에 사는 거래처**가 손해다.\
  월초에 사는 거래처는 같은 달 안에 반영되는 반면, 월말에 사면 다음 달까지 기다린다 — **같은 금액인데 대우가 다르다.**
- 미래 주문의 문제: **취소될 수 있다.**\
  주문을 넣어 등급을 올리고 할인을 받은 다음 주문을 취소하면, **할인만 챙기고 매입은 없는 것**이 된다.

#### 10. 변종 검증에서 고친 것

- 죽은 코드: **`ONE_STEP` 의 하한 검사** — "한 등급 내린 값이 `raw` 보다 더 내려가지 않게 막는" 코드.
- 그 가지의 조건: **`raw.ordinal() < applied.ordinal()`**(else 가지로 들어왔다는 것 자체가 그 뜻이다).

```text
 raw < applied 이므로  raw.ordinal() ≤ applied.ordinal() - 1 = applied.down().ordinal()
 즉 applied.down() 은 항상 raw 이상이다 → "raw 보다 더 내려가는 일" 이 불가능
```

- 지우고 **그 이유를 주석으로 남겼다.**\
  주석이 없으면 다음 사람이 "여기 하한 검사가 빠졌다"며 다시 넣는다.
- 29번과 다른 이유: **불가능의 종류가 다르다.**

```text
 29-customs (남김)   지금은 LocalDate 의 글자 모양이 고정이라 안 겹칠 뿐이다
                     날짜 표현을 바꾸는 날 겹칠 수 있다  →  미래에 가능하다  →  남긴다

 30-b2b-tier (지움)  else 가지의 조건 자체가 "raw < applied" 다
                     이 조건이 유지되는 한 논리적으로 불가능하다  →  지운다
```

  판단 기준은 **"막는 사고가 미래에 가능한가"** 이고, 어느 쪽이든 **판단 근거를 글로 남기는 것**이 짝이다.

- 영업과 재무: 주문 기준은 **영업에 좋다** — 큰 주문을 받은 즉시 등급이 올라 다음 상담에 쓸 수 있다.\
  재무에는 **나쁘다** — 미수 40%에서 "돈은 안 들어왔는데 할인은 나간 달"이 728개월치다(발견 둘).\
  그리고 할인은 **다음 주문의 단가를 깎으므로**, 미수가 쌓일수록 회수할 금액 자체가 줄어든다.\
  즉 이 축은 기술 결정이 아니라 **영업과 재무의 이해 충돌**이고, 코드는 그 충돌을 `Revenue` 라는 값 하나로 드러낸 것이다. (원본에 답 없음 — 내 추론)
- 소급: 이 코드는 **달마다 등급만 내고 할인은 안 다룬다.**\
  소급하면 1월 주문의 청구서를 다시 계산해야 하는데, 결제 기준을 쓰면 **그 재계산이 다시 등급을 바꿀 수 있다**(할인으로 금액이 줄면 매출이 줄고, 매출이 줄면 등급이 내려간다).\
  그 되먹임을 피하려면 **"등급은 그달의 확정 매출로 정하고 소급하지 않는다"** 를 계약으로 못 박는 것이 안전하다 — `Grade` 가 달마다 `amountCents` 를 기록으로 남기는 것이 그 준비다. (원본에 답 없음 — 내 추론)

#### 12. 연결

- "문턱에 딱 맞으면": **29-customs-clearance 의 "150 달러 정확히는 면세"**, **01-parking-fee 의 "10분까지 무료"** 와 같은 자리다.\
  셋 다 **경계에 사람이 몰려 있다**는 점이 공통이다.
- "조건이 안 맞으면 설정이 죽는다"가 반복되는 이유: **정책 축이 여럿이면 축끼리 곱해지고, 곱셈에서는 한 축이 0이면 전체가 0이 되기 때문**이다.\
  28-authorization(거부가 없으면 상속 축이 죽는다), 29-customs(운임이 0이면 CIF 축이 죽는다), 27-ab-assign(비율 0/100이면 씨앗이 죽는다) — 전부 같은 모양이다.
- 최근 12개월 창: 다른 트랙의 **슬라이딩 윈도(sliding window)** 와 같은 모양이다.\
  레이트 리밋의 "최근 1분간 요청 수", 모니터링의 "최근 5분 에러율"이 전부 같은 구조이고, **고정 창(fixed window)과 슬라이딩 창의 차이**가 여기 "지난해 vs 최근 12개월"과 정확히 같다.
- 26~30 다섯 박스의 공통:

```text
 ① 말로 된 요구사항 한 줄 안에 독립된 정책 축이 둘~셋 숨어 있다
 ② 축을 enum(값)으로 올려야 조합을 전부 돌려볼 수 있다
 ③ 조합을 돌려보면 "이름이 말해주는 효과" 와 "실제 효과" 가 다르다
 ④ 어떤 축은 특정 조건에서 죽고, 그 조건이 깨지는 날 한꺼번에 살아난다
 ⑤ 그래서 답이 갈리는 건수를 세는 것이 이 트랙의 측정이다
```
