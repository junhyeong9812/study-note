## 해결하는 문제

"팀장, 본부장, 대표 순으로 결재받는다"를 그대로 코드로 옮기면, **순서를 어긴 클릭·한 단계에 여러 명·승인 도중 금액 변경**이 들어오는 순간 결재가 통과인지 대기인지가 코드마다 다르게 나온다.\
그리고 무효가 된 클릭을 세지 않으면, 누른 사람의 화면(결재 완료)과 서버의 상태(대기)가 어긋난 채 아무도 모른다.

```text
  [결재함 사건: 상신 → 클릭 → 클릭 → 금액 변경 → 클릭 …]
        └ 순서를 지키나?  몇 명이?  금액이 바뀌면 이미 받은 승인은?
        └ 안 정하면 같은 결재함이 통과이기도 대기이기도 하다
```

쉬운 예: 현장학습 신청서에 담임 → 교감 → 교장 도장을 받는데, 교장이 먼저 찍어도 되나·교감이 셋이면 몇 명이 찍나·도중에 금액을 고치면 찍힌 도장은 유효한가.\
똑같은 구조다: 전자결재에서 대표가 먼저 눌렀다가 무효가 되면 대표는 다시 눌러야 하는데, 대표 화면엔 이미 결재했다고 나와 있었다.\
실무 예: 그룹웨어 전자결재, 지출 품의, PR 리뷰 승인 규칙(코드 오너 + 승인 수 + 새 커밋 시 승인 무효), 배포 승인 체인 — 이 챕터는 숨은 결정 셋을 enum으로 드러내고, 버린 클릭을 결과의 일급 필드로 센다.

### 한눈에 — 쉽게 말하면

**다단계 결재 = 현장학습 신청서에 담임 → 교감 → 교장 도장을 차례로 받는 일.**

- 그런데 규칙이 은근히 안 정해져 있다: 교장이 먼저 도장을 찍어도 되나? 교감이 세 명이면 몇 명이 찍어야 하나? 도장을 받는 도중에 신청서의 금액을 고치면, 이미 찍힌 도장은 유효한가?
- 회사 결재도 똑같은 구조다. "팀장, 본부장, 대표 순으로 결재받는다"는 한 문장에 **정해지지 않은 규칙이 3개** 숨어 있다.
- 제일 아픈 지점: 순서 규칙에서 버려진 클릭 — 대표가 먼저 눌렀다가 무효가 되면 대표는 **다시 눌러야** 하는데, **대표 화면에는 이미 결재했다고 나와 있었다.** 버린 클릭을 안 세면 이 어긋남이 안 보인다.

```text
  결재선   1 팀장   2 본부장 A B C   3 대표

  대표 → 본부장A → 팀장 순으로 눌렀다 (거꾸로)

    병렬(아무나 먼저)   셋 다 유효          → 통과
    순차(순서대로)      대표·본부장 클릭 버려짐 → 팀장만 유효 (대기)
```

실무 예: 전자결재(그룹웨어), 지출 품의, PR 리뷰 승인 규칙(코드 오너 + 승인 수), 배포 승인 체인.

## 동작·원리

### 전체 흐름

```text
요구사항: "팀장, 본부장, 대표 순으로 결재받는다" — 숨은 3택

  ① 순서를 지키나 (Order)
       SEQUENTIAL  아래 단계가 끝나야 위가 유효 — 어긴 승인은 버린다
       PARALLEL    아무 단계나 먼저 눌러도 된다

  ② 한 단계에 몇 명이 (Quorum)
       ALL       전원
       MAJORITY  과반 = 절반보다 큰 수 (n/2 + 1)
       ANY       한 명

  ③ 금액이 바뀌면 이미 받은 승인은 (AmendRule)
       RESET_ALL        전부 무효 — 처음부터 다시
       KEEP             그대로 — 승인자가 못 본 금액이 통과한다
       RESET_IF_HIGHER  올라갈 때만 무효

  입력 = 결재함의 사건 흐름(ApprovalEvent: SUBMIT/APPROVE/REJECT/AMEND, seq 순)
  run(): 사건을 차례로 흘려보냄
    accepts()가 4가지 검사: 그 단계 승인자인가 / 이미 눌렀나 / 상신자 본인인가 / 순서 규칙에 맞나
    → Progress(status, amount, approvals, ignored(버린 클릭!), resets(뒤집힌 횟수))
  waitingOn(): 아직 정족수를 못 채운 사람들 — 독촉 알림 보낼 대상
```

### 규칙 1 — 정족수: 과반은 "절반보다 큰 수"다

**어떤 요구사항인가**: README 함정 1번 — "과반을 절반으로 잡지 마라."

코드 번역: `required = approvers.size() / 2 + 1`.

| 승인자 수 | 전원(ALL) | 과반(MAJORITY) | 한 명(ANY) |
|---|---|---|---|
| 1명 | 1 | 1 | 1 |
| **2명** | 2 | **2** | 1 |
| 3명 | 3 | 2 | 1 |
| 4명 | 4 | 3 | 1 |

둘짜리 단계에서 과반을 "절반"으로 잡으면 **한 명이 통과시킨다** — 그리고 둘짜리 단계는 대개 "둘 다 봐야 한다"는 뜻으로 만든다.

**같은 결재함이 통과이기도 대기이기도 하다**: 팀장·대표는 눌렀고 본부장 셋 중 한 명만 눌렀을 때 — ANY면 통과, MAJORITY면 대기(둘 필요), ALL이면 대기(셋 필요).

### 규칙 2 — 클릭 하나를 받는 4가지 검사 (accepts)

**어떤 요구사항인가**: 승인/반려 클릭 하나를 받아들이기 전에 넷을 본다. 각각이 README의 함정과 짝이다.

| 검사 | 안 하면 |
|---|---|
| 그 단계의 승인자인가 | **결재선이 그냥 목록이 된다** — 본부장이 대표 단계(3)나 아무도 없는 9단계를 눌러 통과시킨다 |
| 이미 누른 사람인가 | 새로고침 두 번 클릭으로 **과반 정족수가 한 사람으로 채워진다** |
| 상신자 본인인가 | 팀장이 자기 건을 올리면 1단계가 저절로 통과 — **결재선을 사람 이름으로 짜면 늘 생긴다** |
| 순서 규칙에 맞나 (SEQUENTIAL만) | 아래 단계가 안 끝났는데 위가 유효해진다 |

여기에 더해: **두 번째 SUBMIT은 안 받는다** — 받아주면 상신자와 금액이 말없이 바뀌고, 이미 받은 승인이 아무도 안 본 금액에 붙는다. 재상신은 새 결재함이어야 한다. **반려 하나면 그 뒤 클릭은 다 버려진다** — 반려된 건은 다시 상신해야 한다.

변종 검증의 교훈: 이 넷을 잡는 테스트가 다 약했다 — **넷 다 화면에서는 못 만드는 클릭**이라(화면은 자기 단계만 보여준다) 일부러 안 만들었는데, **넷 다 API 직접 호출·재상신·사유 수정 같은 실제 경로로 나온다.**

### 규칙 3 — 순서: 갈리는 것은 "순서를 어긴 클릭"이 들어올 때뿐

**손계산** — 대표 → 본부장A → 팀장 순(거꾸로)으로 눌렀을 때 (ANY 정족수):

```text
  PARALLEL:    셋 다 유효 → APPROVED, 버린 클릭 0
  SEQUENTIAL:  대표 클릭(1단계 미완) 버림, 본부장 클릭(1단계 미완) 버림,
               팀장만 유효 → PENDING, 버린 클릭 2
               → 대표와 본부장은 다시 눌러야 한다. 화면엔 이미 결재했다고 나왔었는데.
```

- 순서대로 눌렀으면 두 규칙이 완전히 같다 — 갈리는 것은 순서를 어긴 클릭이 실제로 들어올 때뿐. 결재함 화면은 대개 다음 차례만 보여줘서 **개발할 때는 그 클릭이 안 만들어진다.** 측정: 아무 일도 안 일어나면(순서대로 + 금액 안 고침) 18조합이 17,000번 비교에서 전부 같다.
- 측정: 순서를 10%만 섞어도 순차 결재 1,000건 중 **913건만 통과**(나머지는 도중에 멈춤), 버린 클릭 237. 100% 섞으면 통과 47. **병렬은 아무리 섞어도 한 건도 안 버린다.**
- 버린 클릭(`ignored`)을 결과에 일급으로 내는 이유(README 함정 4번): **누른 사람은 자기가 결재했다고 알고 있다.** 측정: ANY 정족수의 병렬 결재에서도 본부장 셋 중 둘의 클릭은 늘 버려진다(정족수가 찬 뒤의 클릭은 갈 곳이 없다) — 버려도 결과는 같지만, **그 두 사람은 결재를 한 것인가 안 한 것인가.**

### 규칙 4 — 대기 목록(waitingOn): 정족수만 보고 순서는 안 본다

**어떤 요구사항인가**: "누구를 기다리는지 화면에 띄울 값."

- 순차 결재에서 팀장만 눌렀으면 다음 차례는 본부장뿐인데, `waitingOn`은 정족수 미달 단계의 안 누른 사람을 **전부** 모은다 → 본부장 A B C와 **대표까지** 뜬다. 화면에 그대로 쓰면 아직 차례도 아닌 대표에게 알림이 간다 — 이 함수의 한계를 알고 써야 한다.
- 반대로 **정족수를 채운 단계의 나머지는 목록에서 빠진다**: ANY에서 본부장A가 눌렀으면 B·C는 기다릴 필요가 없다 — 남겨두면 그 둘에게 독촉 알림이 간다. (ALL이면 여전히 둘을 기다린다.)

### 규칙 5 — 금액 변경(AMEND): 이미 받은 승인을 어떻게 하나

**어떤 요구사항인가**: "금액 변경이 승인 중간에 들어온다. 그리고 그것이 이 박스의 골칫거리다." 상신자만 고칠 수 있다 — 본부장이 금액을 고칠 수 있으면 결재가 아니라 편집이다.

**손계산 1 — 올리면 세 규칙이 세 결과**: 100만 원에 팀장·본부장A 승인 후 상신자가 300만 원으로:

```text
  RESET_ALL         승인 0건, 되돌림 1회
  KEEP              승인 2건, 되돌림 0회  ← 팀장이 못 본 300만 원이 팀장 승인을 달고 대표에게 간다
  RESET_IF_HIGHER   승인 0건, 되돌림 1회
```

**손계산 2 — 내리면 두 규칙이 같아진다**: 300만 → 100만이면 RESET_IF_HIGHER는 KEEP과 같다. **금액을 내리는 자료로만 테스트하면 둘이 같아 보인다.** 측정: 인하만 있는 자료에서 "올라갈 때만"의 통과 수는 "그대로"와 동일(1,000), 인상만 있는 자료에서는 "전부 다시"와 동일(189) — **세 규칙인데 자료가 어느 둘로 접을지를 정한다.** 어느 쪽으로 접혔는지는 테스트 결과만 봐서는 안 보인다.

**손계산 3 — 올렸다 내리면 같은 금액인데 승인이 다르다**: 100만 → 300만 → 100만:

```text
  KEEP              되돌림 0회, 팀장 승인 살아 있음
  RESET_IF_HIGHER   되돌림 1회, 팀장 승인 사라짐
  최종 금액은 둘 다 100만 원으로 같다.
  → 금액 "이력"을 안 보고는 지금 상태를 설명할 수 없다.
```

**손계산 4 — 같은 금액으로 다시 올리면 인상이 아니다**: 첨부·사유만 고쳐 다시 올려도 AMEND 사건이 들어온다. 인상 판정은 `event.amount() > amount`(초과, 이상 아님) — "같으면 올라간 것"으로 잡으면 사유만 고쳐도 결재가 처음으로 돌아가고, 사유를 고칠 때마다 또 돌아간다.

## 쓰이는 자료구조·알고리즘

- **상태 기계 + 사건 흐름** — `Status`(PENDING → APPROVED / REJECTED)가 상태이고, `ApprovalEvent`(SUBMIT/APPROVE/REJECT/AMEND)가 전이를 일으킨다. 종료 상태에 들어가면 뒤 사건은 전부 버린다 — [basic/09-order-state](../../basic/09-order-state/2-summary.md).
- **이벤트 소싱** — `run(events, …)`은 현재 상태를 저장하지 않고 사건 목록을 처음부터 흘려 `Progress`를 만든다. 같은 사건 목록을 규칙만 바꿔 18가지 답을 내는 측정이 이 구조 덕분에 가능하다 — [ops-patterns/16-event-sourcing](../../../ops-patterns/16-event-sourcing/2-summary.md) · [16-audit-replay](../16-audit-replay/2-summary.md).
- **단계 → 승인자 목록 맵(`LinkedHashMap<Integer, List<String>>`)** — `approvals`가 단계별로 누른 사람을 담는다. 중복 클릭 검사는 그 목록의 `contains`(단계당 사람이 몇 명이라 선형 검색으로 충분) — [data-structure/05-hashmap](../../../data-structure/05-hashmap/2-summary.md).
- **정족수 계산(과반 = n/2 + 1)** — 정수 나눗셈 한 줄이지만 "절반"과 "절반보다 큰 수"를 가른다. 분산 합의에서 노드 과반을 세는 것과 같은 산수 — [ops-patterns/12-leader-election](../../../ops-patterns/12-leader-election/2-summary.md).
- **선행 단계 완료 검사(prefix check)** — `SEQUENTIAL`은 클릭한 단계보다 낮은 단계를 앞에서부터 훑어 하나라도 정족수 미달이면 버린다. "앞이 끝나야 뒤가 유효"라는 의존 순서를 가장 단순하게 검사한 것 — 일반화하면 [data-structure/34-dependency-resolver](../../../data-structure/34-dependency-resolver/2-summary.md)의 위상 정렬.
- **결재선 검증(정렬 + 연속성)** — `ApprovalChain` 생성자가 `Step`을 level로 정렬한 뒤 1부터 빈틈없이 이어지는지 확인한다. 같은 단계에 같은 승인자가 두 번 있으면 거부하는 검사는 `Step` 생성자(`distinct` 개수 비교)가 한다.
- **삽입 순서 집합(`LinkedHashSet`)으로 대기 목록** — `waitingOn`이 정족수 미달 단계의 안 누른 사람을 모은다. 정족수를 채운 단계는 통째로 건너뛰어 독촉 대상에서 뺀다.
- **권한 검사의 축소판** — `Step.canApprove(actorId)`가 "이 사람이 이 단계를 누를 수 있나"를 본다. 역할·자원별 허용 규칙으로 키운 것이 [28-authorization](../28-authorization/2-summary.md)이다.

## 적용 — 풀어나가는 법

이런 문제를 받으면 결재선을 "사람 목록"으로 저장하기 전에 **순서·정족수·금액 변경 시 처리**를 enum으로 꺼내고, 클릭 하나를 받는 검사 넷(단계 승인자·중복·상신자 본인·순서)을 도메인 코드에 둔다 — 화면이 막는 것은 제안이고 도메인이 막는 것만 보장이다.\
그 다음 결과에 `ignored`(버린 클릭)와 `resets`(뒤집힌 횟수)를 일급으로 담아, 결과가 같아도 사람의 인식과 어긋나는 건수를 센다.\
마지막으로 순서를 어긴 클릭·금액 인상·인하·같은 금액 재상신을 일부러 섞은 자료로 18조합을 돌려 본다. 아래는 원본 챕터가 시킨 과제 목록이다.

## 장애 시나리오와 대처

**1. 같은 사람의 더블 클릭이 둘 다 승인으로 저장된다**

- 현상: 과반 정족수인 단계가 한 사람의 클릭으로 통과됐다. 승인 목록에 같은 이름이 두 줄이다.
- 보이는 형태: `approvals`의 한 단계에 같은 `actorId`가 두 번 들어 있고, 그 단계가 `complete`로 판정돼 결재가 `APPROVED`가 됐다. 로그에는 같은 사용자의 승인 요청이 밀리초 차이로 둘 찍혀 있다.
- 원인: `accepts`의 중복 검사는 한 사건 흐름 안에서는 맞지만, 실제 서비스에서는 두 요청이 **동시에** 옛 상태를 읽고 각자 "아직 안 눌렀다"로 판정한 뒤 둘 다 저장한다(읽고-쓰기 경합). 이 코드의 `run`은 사건 목록의 순서를 그대로 믿고(`seq`로 다시 정렬하지 않는다) 한 번에 하나씩 흘리므로, 그 순서와 직렬성은 저장소가 보장해 줘야 성립한다.
  - *경합(race)*: 두 요청이 같은 상태를 동시에 읽고 각자 갱신해 한쪽 결과가 덮이거나 둘 다 반영되는 현상.
- 대처: 사건에 단조 증가하는 `seq`를 저장소가 부여하게 하고(한 결재함의 사건은 한 줄로 직렬화), 승인 저장에 `(결재함, 단계, 사용자)` 유일 제약이나 요청 멱등 키를 둔다. 상태는 사건 목록에서 다시 만들므로, 저장이 유일하면 `run`의 중복 검사가 두 번째 방어선이 된다.

**2. 승인자가 퇴사해 결재함이 영원히 대기다**

- 현상: 몇 주째 `PENDING`인 결재함이 쌓인다. `waitingOn`에 계속 같은 이름이 뜨는데 그 사람은 회사에 없다.
- 보이는 형태: `Quorum.ALL`인 단계에서 `required`가 승인자 수 그대로인데, 그중 한 명이 영영 누르지 않는다. 독촉 알림이 없는 계정으로 매일 나간다.
- 원인: `Step.approvers`가 사람 이름(ID)으로 박혀 있고, 진행 중인 결재함은 결재선을 만들 때의 목록을 그대로 쓴다. 인사이동·퇴사가 결재선에 반영되지 않으면 정족수 분모는 그대로고 분자는 채울 수 없다.
- 대처: 결재선의 자리를 직책·역할로 두고 사람은 그 자리에 매핑한다(자기결재 문제는 그래도 남는다 — 정답 13번 참고). 진행 중 결재함에는 대결(위임)·재배정 사건을 정의해 `approvers`를 바꾸되, 대결자를 승인자 목록에 **추가**하면 과반 분모가 늘어나므로 "원래 사람 자리를 대신한다"로 기록한다.

**3. 금액 변경 규칙을 바꿨더니 옛 결재함의 상태가 달라진다**

- 현상: `KEEP`에서 `RESET_IF_HIGHER`로 규칙을 바꿔 배포한 뒤, 이미 승인이 붙어 있던 결재함들이 다시 열어 보니 승인 0건으로 돌아가 있다.
- 보이는 형태: 같은 사건 목록인데 `resets`가 0에서 1로, `approvals`가 비어 있다. 승인했던 사람들은 아무것도 안 했는데 "재결재 요청" 알림을 받는다.
- 원인: 이벤트 소싱은 상태를 저장하지 않고 **사건 + 규칙**으로 매번 다시 만든다. 규칙이 바뀌면 옛 사건 목록이 새 규칙으로 재해석된다 — 이 챕터가 18조합을 한 자료로 돌릴 수 있는 바로 그 성질이 운영에서는 소급 적용이 된다.
- 대처: 규칙(`Order`·`Quorum`·`AmendRule`)을 결재함 생성 시점에 **결재함에 고정**해 저장하거나, 규칙 자체를 날짜 버전으로 관리해 상신일 기준으로 고른다([09-policy-version](../09-policy-version/2-summary.md)). 규칙 변경은 새 결재함부터만 적용하고, 변경 전후 결과 차이를 측정 테스트처럼 먼저 센다.

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 과반 = 절반 | n/2 + 1 — 둘짜리 단계는 둘 다 |
| 단계 승인자 검사 생략 | 아무나 아무 단계를 눌러 통과 — 화면에선 안 나와도 API로 나온다 |
| 같은 사람 두 번 클릭 | 한 번만 센다 — 안 그러면 과반이 한 사람으로 채워진다 |
| 상신자 자기결재 | 순서 규칙과 무관하게 거부 — 사람 이름 결재선에서 늘 생긴다 |
| 두 번째 상신 수용 | 무시 — 상신자·금액이 말없이 바뀌고 기존 승인이 오염된다 |
| 반려 뒤의 클릭 | 다 버리되 ignored에 센다 — 대표는 자기가 결재한 줄 안다 |
| 버린 클릭을 안 셈 | ignored를 결과의 일급 필드로 — 누른 사람의 화면과 실제가 어긋난다 |
| waitingOn을 알림에 그대로 사용 | 순서를 안 보는 함수다 — 차례 아닌 사람에게 독촉이 간다 |
| 같은 금액 AMEND를 인상으로 판정 | 초과(>)만 인상 — 사유 수정마다 결재가 리셋되는 참사 방지 |
| 결재선 검증 | 1단계부터 연속, 한 단계에 같은 승인자 중복 금지, 승인/반려는 단계 필수·상신/변경은 단계 0 |
| 개발 자료로 검증 | 순서대로 + 금액 안 고침이면 18조합이 통째로 같다 — 어긋난 클릭과 금액 변경을 일부러 넣어야 갈래가 보인다 |

## 핵심 문장
- "팀장, 본부장, 대표 순으로 결재받는다"에는 순서(2택) × 정족수(3택) × 금액 변경(3택) = 18조합이 숨어 있고, **아무 일도 안 일어나는 개발 결재함에서는 18조합이 전부 같은 답을 낸다.**
- 클릭 하나를 받는 데 4가지 검사가 필요하고, 그 검사들이 막는 입력은 **전부 화면에서는 못 만들지만 실제 시스템에서는 나온다** — 화면이 막아주는 것과 도메인이 막는 것은 다르다.
- 버린 클릭은 세어야 한다 — 버려도 결과는 같지만, 누른 사람은 자기가 결재했다고 알고 있다. 상태(Progress)에 ignored가 일급인 이유다.
- "올라갈 때만 다시"는 자료에 따라 "그대로" 또는 "전부 다시"로 접혀 보인다 — 한 방향 자료로만 테스트하면 세 규칙이 두 규칙으로 보인다(18장의 한 방향 날짜 자료와 같은 패턴).
- 올렸다 내린 결재함은 최종 금액이 같아도 승인이 다르다 — **이력을 안 보고는 지금 상태를 설명할 수 없다.** 이벤트(사건 흐름)로 모델링하는 이유가 여기 있다.

### 용어 풀이

- **상신(submit)**: 결재를 올리는 것. 올린 사람이 상신자(requester)다.
- **결재선(approval chain)**: 어느 단계에 누가 승인할 수 있는지를 정한 순서 목록. 1단계부터 이어져야 한다.
- **정족수(quorum)**: 한 단계가 통과하는 데 필요한 승인자 수. 전원/과반/한 명.
- **과반(majority)**: 절반보다 **큰** 수. n/2 + 1. 절반과 다르다 — 2명의 과반은 2다.
- **순차/병렬(sequential/parallel)**: 아래 단계가 끝나야 위가 유효한가 / 아무 단계나 먼저 눌러도 되는가.
- **반려(reject)**: 결재를 거부하는 것. 하나 들어오면 그 결재함은 끝나고 뒤 클릭은 다 버려진다.
- **금액 변경(amend)**: 상신자가 승인 중간에 금액을 고치는 것. 이미 받은 승인의 처리 규칙(AmendRule)이 따로 필요하다.
- **버린 클릭(ignored)**: 규칙에 안 맞아 무효 처리된 사건. 버려도 결과는 같지만 누른 사람의 인식과 어긋난다.
- **되돌림(reset)**: 금액 변경으로 기존 승인을 무효로 만든 것. 그 횟수가 "결재가 몇 번 뒤집혔나"다.
- **대기 목록(waitingOn)**: 아직 정족수를 못 채운 단계의 안 누른 사람들. 정족수만 보고 순서는 안 본다.
- **자기결재(self-approval)**: 상신자가 자기 건을 승인하는 것. 결재선을 사람 이름으로 짜면 늘 생기는 충돌.
- **대결(위임)**: 자리를 비운 결재자 대신 다른 사람이 결재하는 것. 정족수 계산을 복잡하게 만든다(생각해볼 것).
