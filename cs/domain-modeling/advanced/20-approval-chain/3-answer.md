### A. 과제

#### 0. 요구사항 한 줄이 안 말해주는 것

- 안 말해주는 자리 셋(클래스 javadoc 그대로):

```text
 안 말해준 것        가능한 읽기
 "순으로"      →  위 단계가 끝나야 아래가 눌리나 아무나 먼저 눌러도 되나
 "결재받는다"  →  한 단계에 전원인가 과반인가 한 명인가
 (안 나온 말)  →  금액이 바뀌면 전부 다시인가 그대로인가 올라갈 때만 다시인가
```

- 조합 수: **18가지**다.\
  순서 2택 × 정족수 3택 × 금액 변경 3택 = 2 × 3 × 3 = 18.

> **갈래(branch)** — 요구사항 한 문장을 코드로 옮길 때 서로 다른 답을 내는 선택지.\
> 예: "순으로 결재받는다"는 순서를 강제하는 코드로도, 그냥 목록으로도 옮길 수 있다. 그 둘이 한 갈래다.

- "순으로": **둘 다 읽힌다.** 그래서 `Order` 라는 값으로 올려 두 판을 다 돌려본다.\
  `SEQUENTIAL` 은 아래 단계가 끝나야 위가 유효하고, `PARALLEL` 은 아무 단계나 먼저 눌러도 된다.
- 화면과 실제의 어긋남: 대표와 본부장은 **버튼을 눌렀고 화면에는 "결재함"으로 나왔다.**\
  그런데 서버는 그 클릭을 버렸다. 그 둘은 **다시 눌러야** 하는데 다시 누를 이유를 모른다.
- "서로 간섭한다": 한 갈래의 선택이 다른 갈래의 결과를 바꾼다.\
  예를 들어 순서를 안 지키는 판(PARALLEL)에서는 대표가 팀장보다 먼저 눌러도 통과다.\
  금액이 오르내리면 **같은 최종 금액인데 결재 이력이 달라진다**(javadoc 원문).
- 값으로 올리면: **같은 결재함을 18조합으로 돌려 답이 갈리는 건수를 셀 수 있다.**\
  세어보기 전에는 그 갈림이 "구석 사례"인지 "계약의 본체"인지 모른다.

#### 1. TODO 1 — required

정답 코드 (impl/ApprovalChain.java):

```java
return switch (quorum) {
    case ALL -> step.approvers().size();
    case MAJORITY -> step.approvers().size() / 2 + 1;
    case ANY -> 1;
};
```

- 과반 식: `size() / 2 + 1`.\
  자바의 `/` 가 소수점을 버리므로 3/2 = 1, 거기에 1을 더해 2가 된다.

> **과반(majority)** — 절반보다 **큰** 수. 절반(50 %)이 아니라 50 %를 넘는 수다.\
> 예: 2명의 과반은 1명이 아니라 2명이다. 1명은 절반이지 과반이 아니다.

- 손계산:

```text
 승인자 수   전원   과반(n/2+1)      한 명
    1        1     1/2+1 = 0+1 = 1    1
    2        2     2/2+1 = 1+1 = 2    1
    3        3     3/2+1 = 1+1 = 2    1
    4        4     4/2+1 = 2+1 = 3    1
```

- `size()/2` 로 잡으면: 둘짜리 단계가 `2/2 = 1` 이 되어 **한 명이 통과시킨다.**
- 둘짜리 단계가 제일 위험한 이유: **둘짜리 단계는 대개 "둘 다 봐야 한다"는 뜻으로 만든다**(테스트 주석 원문).\
  셋짜리는 과반이 2라 절반(1.5)과 비교해도 어차피 2로 올라가지만, 둘짜리는 1과 2로 완전히 갈린다.
- `Step` 이 정족수를 안 갖는 이유: `Step` javadoc이 못 박았다 — "그 중 몇 명이 눌러야 통과인지는 이 단계가 안 갖는다. 정족수 규칙이 따로 정한다."\
  같은 결재선을 세 정족수로 각각 돌려볼 수 있어야 하기 때문이다.
- 4명 과반 = 3 의 계약: `assertEquals(3, chain.required(four, Quorum.MAJORITY))` — 4명짜리 `Step` 을 만들어 직접 못 박았다.\
  `assertEquals(4, ..., Quorum.ALL)` 과 `assertEquals(1, ..., Quorum.ANY)` 도 같이 있다.

- 네 검사와 순서:

```text
 ① 그 단계가 있고, 그 사람이 그 단계 승인자인가   (없는 단계 · 남의 단계 차단)
 ② 상신자 본인인가                                 (자기결재 차단)
 ③ 이미 그 단계에서 누른 사람인가                   (중복 클릭 차단)
 ④ 순서 규칙에 맞나 — SEQUENTIAL 일 때만           (어긴 순서 차단)
```

- ①을 안 보면: **결재선이 그냥 목록이 된다**(README 함정 원문).\
  누구든 아무 단계나 눌러 통과시킬 수 있다 — 테스트는 본부장A가 3단계(대표)를 누르는 장면으로 못 박았다(`countAt(3) == 0`).
- 9단계 클릭: `stepAt(9)` 가 **null 을 돌려주고** 첫 줄에서 false 가 된다.\
  테스트는 3단계 오클릭과 9단계 오클릭을 합쳐 `ignored().size() == 2` 로 못 박았다.
- ③을 안 보면: 새로고침 후 두 번 누른 한 사람이 **과반 정족수를 혼자 채운다.**\
  테스트: 본부장A가 2단계를 두 번 눌렀을 때 `countAt(2) == 1`, `ignored().size() == 1`, 상태는 `PENDING`.
- ②가 ④보다 앞에 있어야 하는 이유: javadoc이 "상신자는 자기 건을 못 누른다. **순서를 지키든 안 지키든** 그렇다"라고 못 박았다.\
  뒤에 두면 PARALLEL 판에서 `return true` 에 먼저 걸려 자기결재가 통과한다.

> **자기결재(self-approval)** — 결재를 올린 사람이 그 건의 승인자로도 들어가 있어서 스스로 통과시키는 것.\
> 예: 팀장이 자기 출장비를 올렸는데 결재선 1단계가 "팀장"이면, 막지 않는 한 1단계가 저절로 통과한다.

- ②가 `Order` 와 무관: 두 판 모두에서 똑같이 거부한다.\
  테스트는 `Order.PARALLEL` 로 돌려 `countAt(1) == 0`, `ignored().size() == 1` 을 확인한다.
- 순차 확인법: **내 단계보다 낮은 모든 단계가 정족수를 채웠는지** 하나씩 본다(`complete(approvals, earlier, quorum)`).
- `break` 하는 이유: 생성자에서 `steps` 를 **단계 번호 오름차순으로 정렬**해 두었다.\
  그래서 내 단계에 도달하면 그 뒤는 전부 나보다 위 단계라 볼 필요가 없다 — 위 단계는 내 순서를 막지 않는다.
- PARALLEL 이 바로 true 인 이유: 그 규칙의 정의가 "아무 단계나 먼저 눌러도 된다"이기 때문이다.\
  볼 게 없으니 ①②③만 통과하면 끝이다.
- `accepts` 가 `quorum` 을 받는 이유: **"아래 단계가 끝났나"를 판정하려면 정족수를 알아야 한다.**\
  같은 승인 2건이 ANY면 끝난 것이고 ALL이면 아직이다 — 순서 판정이 정족수에 얹혀 있다.
- public 인 뜻: 클릭 하나를 **미리 물어볼 수 있는 표면**이 된다.\
  화면이 버튼을 회색으로 만들지 결정할 때 `run` 을 통째로 돌리지 않고 이 함수만 부르면 된다. (원본에 근거 없음 — 내 추론)

#### 3. TODO 3 — run

정답 코드(뼈대):

```java
Map<Integer, List<String>> approvals = new LinkedHashMap<>();
List<ApprovalEvent> ignored = new ArrayList<>();
Status status = Status.PENDING;
String requesterId = null;
long amount = 0;
int resets = 0;

for (ApprovalEvent event : events) {
    if (status != Status.PENDING) {
        ignored.add(event);
        continue;
    }
    switch (event.kind()) {
        case SUBMIT -> { ... }
        case AMEND -> { ... }
        case APPROVE, REJECT -> { ... }
    }
}
```

- 들고 다니는 상태 여섯: `approvals`(단계별 누른 사람) · `ignored`(버린 사건) · `status` · `requesterId` · `amount` · `resets`.
- PENDING 이 아니게 되면: **그 뒤 사건은 전부 `ignored` 로 간다.**\
  테스트: 본부장A 반려 뒤의 대표 승인이 버려져 `ignored().size() == 1`, 상태는 `REJECTED`.
- 두 번째 SUBMIT 을 안 받는 이유:

```java
case SUBMIT -> {
    if (requesterId != null) {
        ignored.add(event);
        break;
    }
    requesterId = event.actorId();
    amount = event.amount();
}
```

  받아주면 **상신자와 금액이 말없이 바뀐다**(테스트 주석 원문).\
  그리고 이미 받은 승인은 그대로 남아서 **아무도 안 본 금액이 승인을 달고 있게 된다.**
- 말없이 바뀌는 것 둘: `requesterId` 와 `amount`.\
  테스트는 사원 100만 원 건에 팀장 승인이 붙은 뒤 "다른사원"이 900만 원으로 재상신하는 장면으로 못 박았다 — `amount()` 는 여전히 `1_000_000`, `countAt(1) == 1`, `ignored().size() == 1`.\
  재상신은 **새 결재함**이어야 한다.
- AMEND 를 상신자만: 안 막으면 "결재가 아니라 **편집**"이 된다(테스트 주석 원문).\
  테스트: 본부장A가 900만 원으로 고치려 하면 `amount() == 1_000_000`, `resets() == 0`, `ignored().size() == 1`.
- 상신 전 APPROVE: `requesterId == null` 이면 `accepts` 를 부르지도 않고 버린다.\
  상신자를 모르면 자기결재인지 판정할 수 없기 때문이다.
- `>` 와 `>=` 의 차이:

```java
boolean higher = event.amount() > amount;
```

  `>=` 로 잡으면 **같은 금액으로 다시 올린 것도 "인상"이 된다.**\
  첨부나 사유만 고쳐 다시 올리는 일은 흔한데, 그때마다 결재가 처음으로 돌아간다.\
  테스트: 100만 → 100만 AMEND 에서 `RESET_IF_HIGHER` 는 `countAt(1) == 1`(팀장 승인 살아 있음), `resets() == 0`.
- 비교와 대입의 순서: **비교가 먼저다.**\
  `higher` 를 구한 다음에 `amount = event.amount()` 로 덮는다. 순서를 바꾸면 `higher` 가 늘 false 가 된다(자기 자신과 비교하게 되므로).
- REJECT 사건 자체: **`ignored` 에 안 들어간다.**\
  `accepts` 를 통과한 반려는 상태를 `REJECTED` 로 바꾸고 끝난다 — 버려진 게 아니라 **받아들여진** 사건이다.\
  통과 못 한 반려(남의 단계 등)는 `ignored` 로 간다.
- 승인이 붙을 때마다: `allComplete(approvals, quorum)` 를 다시 본다 — **모든 단계가 정족수를 채웠으면 그 자리에서 `APPROVED`.**
- 얼려서 돌려주는 이유: `Progress` 안의 리스트를 밖에서 고치면 **이미 끝난 결재 이력이 나중에 바뀐다.**\
  그리고 테스트가 `Progress` 두 개를 통째로 `assertEquals` 로 비교한다(순서대로 누르면 PARALLEL·SEQUENTIAL 결과가 같다) — 값 객체로 다루려면 안쪽도 불변이어야 한다.

> **불변 값(immutable value)** — 만든 뒤에는 내용이 안 바뀌는 객체.\
> 예: `List.copyOf(...)` 로 만든 리스트는 `add` 를 부르면 예외가 난다. 그래서 남에게 건네도 안심이다.

- `ignored` 와 `resets` 가 일급 필드인 이유: **버려도 결과는 같지만 누른 사람은 자기가 결재했다고 알고 있다**(README 함정 4).\
  `resets` 는 "결재가 몇 번 뒤집혔나"다(javadoc 원문) — 최종 상태만 보면 안 보이는 숫자다.

> **일급 필드(first-class field)** — 로그나 부수효과가 아니라 결과 값 자체에 들어 있는 항목.\
> 예: 버린 클릭을 `System.out` 에 찍으면 아무도 안 보지만, `Progress.ignored()` 로 돌려주면 화면이 "당신의 클릭은 무효였습니다"를 띄울 수 있다.

- 지금 상태만 저장하는 설계와의 차이: 100만 → 300만 → 100만으로 갔다 온 결재함은 **최종 금액이 같은데 승인이 다르다.**\
  `KEEP` 이면 팀장 승인이 살아 있고 `RESET_IF_HIGHER` 면 사라진다 — **금액 이력을 안 보고는 지금 상태를 설명할 수 없다**(테스트 주석 원문).

#### 4. TODO 4 — waitingOn

정답 코드:

```java
Set<String> waiting = new LinkedHashSet<>();
if (progress.status() != Status.PENDING) {
    return waiting;
}
for (Step step : steps) {
    if (complete(progress.approvals(), step, quorum)) {
        continue;
    }
    for (String approver : step.approvers()) {
        if (!progress.approvals()
                .getOrDefault(step.level(), List.of())
                .contains(approver)) {
            waiting.add(approver);
        }
    }
}
return waiting;
```

- 제일 먼저: **상태가 PENDING 인지** 본다.
- 끝난 결재함의 대기 목록: **빈 목록**이다.\
  테스트: 반려된 결재함에서 `chain.waitingOn(progress, Quorum.ANY).isEmpty()`.
- 정족수를 채운 단계의 나머지: **뺀다**(`continue`).
- "안 누른 사람" ≠ "기다리는 사람": ANY 정족수에서 본부장A가 눌렀으면 2단계는 끝났다.\
  본부장B·C는 안 눌렀지만 **기다릴 필요가 없다** — 목록에 남기면 그 둘에게 **독촉 알림이 간다**(테스트 주석 원문).
- 순차에서 팀장만 눌렀을 때 (ANY 정족수):

```text
 1 단계  팀장       채움(1 >= 1)     →  건너뜀
 2 단계  본부장 A B C  0 명, 미달      →  A, B, C 추가
 3 단계  대표       0 명, 미달        →  대표 추가

 결과  [본부장A, 본부장B, 본부장C, 대표]
       순차 규칙이면 다음 차례는 본부장뿐인데 대표까지 들어 있다
```

  테스트가 이 순서 그대로 `assertEquals(List.of("본부장A","본부장B","본부장C","대표"), ...)` 로 못 박았다.
- 그대로 알림에 쓰면: **아직 차례도 아닌 대표에게 독촉이 간다.**
- `LinkedHashSet` 인 이유: **넣은 순서를 지키기 위해서**다.\
  단계 오름차순 → 그 단계의 승인자 나열 순서가 그대로 화면 순서가 된다. 테스트도 `List.copyOf(...)` 로 순서까지 비교한다.\
  `Set` 인 것은 한 사람이 여러 단계에 있어도 한 번만 뜨게 하기 위해서다. (`Set` 선택 이유는 원본에 근거 없음 — 내 추론)

> **삽입 순서 유지 집합(LinkedHashSet)** — 중복은 없애면서 넣은 차례는 그대로 기억하는 자료구조.\
> 예: 그냥 `HashSet` 을 쓰면 `[대표, 본부장B, 본부장A, 본부장C]` 처럼 뒤죽박죽 나올 수 있어 화면에 쓰기 어렵다.

- 순서를 안 보는 것은 **정해진 계약**이다.\
  테스트 이름 자체가 "대기 목록은 순서를 안 본다"이고, 주석이 "대기 목록은 **정족수만 보고 순서는 안 본다**"고 못 박았다.\
  버그가 아니라 **알고 써야 하는 한계**다 — 알림을 보내려면 호출하는 쪽이 순서를 한 번 더 걸러야 한다.

#### 5. 계약 — Step · ApprovalEvent

- 생성자가 보는 둘: ① 결재선이 **비었나** ② 단계가 **1부터 빈틈없이 이어지나**.

```java
List<Step> sorted = new ArrayList<>(steps);
sorted.sort((a, b) -> Integer.compare(a.level(), b.level()));
for (int i = 0; i < sorted.size(); i++) {
    if (sorted.get(i).level() != i + 1) {
        throw new IllegalArgumentException("단계가 1 부터 이어져야 한다");
    }
}
```

- 2부터 시작하면 거부: **1단계가 비었다는 뜻**이고, 그러면 `accepts` 의 순차 검사가 "아래 단계"를 못 찾는다.\
  테스트: `new ApprovalChain(List.of(Step.single(2, "a")))` 는 `IllegalArgumentException`.
- 같은 승인자 중복: 정족수가 **한 사람으로 채워진다.**\
  승인자 목록이 `["a","a"]` 면 ALL 정족수가 2인데 a 혼자는 한 번만 셀 수 있으니 영원히 안 차거나(중복 클릭 차단 때문), 중복 클릭을 허용하면 a 혼자 통과시킨다.\
  그래서 `Step` 생성자가 아예 막는다 — `new Step(1, List.of("a","a"))` 는 예외.
- 단계 번호 규칙:

```java
boolean atLevel = kind == Kind.APPROVE || kind == Kind.REJECT;
if (atLevel && level < 1) { throw ... }
if (!atLevel && level != 0) { throw ... }
```

  승인·반려는 **어느 단계에 대한 행동인지**가 있어야 판정이 된다.\
  상신·금액 변경은 단계에 속한 행동이 아니라 **결재함 전체**에 대한 행동이라 단계를 가지면 안 된다 — 0이 "단계 없음"의 표시다.

> **차원이 다른 사건** — 같은 목록에 섞여 있지만 가리키는 대상이 다른 사건.\
> 예: "2단계 승인"은 한 단계를 가리키고, "금액을 300만으로"는 결재함 전체를 가리킨다. 단계 번호를 0으로 못 박아 둘을 구분한다.

- 금액 0 이하 차단: `if ((kind == SUBMIT || kind == AMEND) && amount <= 0) throw ...`.\
  0원 결재나 마이너스 결재는 뜻이 없고, 무엇보다 `higher` 판정이 이상해진다.
- `seq` 의 쓸모: `run` 은 리스트 순서대로만 돈다 — `seq` 를 안 본다.\
  실제로 쓰이는 곳은 **예외 메시지**다(`"행위자가 있어야 한다: " + seq`, `"승인과 반려는 단계가 있어야 한다: " + seq`) — 어느 사건이 잘못됐는지 짚어준다.\
  그 밖에 저장소에서 꺼낸 사건을 다시 정렬하거나 감사 자료에서 순서를 재현할 때 쓴다. (그 밖의 쓸모는 원본에 근거 없음 — 내 추론)

### B. 개념

#### 6. 측정 — 아무 일도 안 일어나면

- 열여덟 조합 **전부** 1,000 / 1,000 통과다.
- 버린 클릭 **0**, 되돌림 **0**.
- **17,000번** 비교에서 어긋난 것 **0**.

```text
 조합 수  Order 2 x Quorum 3 x AmendRule 3 = 18
 비교 수  결재함 1,000 개 x (18 - 1) = 17,000
          (첫 조합을 기준으로 삼고 나머지 17개와 비교한다)
 어긋남   0
```

> **기준(reference)** — 여러 판을 비교할 때 "이것과 같은가"를 재는 기준이 되는 한 판.\
> 예: 18조합 중 첫 조합의 결과를 기준으로 잡고 나머지 17개가 같은지만 센다. 그래서 1,000 × 17 = 17,000 비교다.

- "개발할 때 만드는 결재함이 이렇다"가 무서운 이유: **개발용 자료가 세 갈래를 전부 가린다.**\
  순서대로 누르고 금액을 안 고치면, 어떤 규칙을 골랐든 답이 같아서 **고르지 않았다는 사실 자체를 모른다.**
- 이어지는 사고: 아무거나 골라 배포한 뒤 **실제 결재함에서 갈림이 터진다.**\
  그때는 "왜 대표 결재가 무효가 됐냐"는 문의로 들어오고, 코드 어디가 갈림인지 아무도 모른다.

> **가려진 갈림(masking)** — 자료가 한쪽으로 치우쳐서, 규칙이 갈리는 자리가 결과에 안 나타나는 것.\
> 예: 순서를 한 번도 안 어긴 자료에서는 순차와 병렬이 완전히 같은 답을 낸다.

#### 7. 측정 — 순서를 섞으면

- 표(MeasurementTest 의 assert 값 그대로):

```text
 섞임      순차 통과   병렬 통과   순차가 버린 클릭   병렬이 버린 클릭
   0 %      1,000      1,000              0                0
  10 %        913      1,000            237                0
  30 %        711      1,000            730                0
 100 %         47      1,000          2,482                0
```

- 병렬 통과는 어느 섞임에서나 **1,000**(`assertEquals(1_000, parallelApproved, "병렬은 늘 통과한다")`).
- 섞임 10 %의 버린 클릭: **237개**.
- 섞임 100 %의 버린 클릭: **2,482개**.
- "한 건도 안 버린다"는 **정족수가 전원(ALL)일 때의 이야기**다.\
  이 측정은 `Quorum.ALL` 로 돌렸다. 정족수가 과반이나 한 명이면 병렬도 버린다(아래 10번: 185, 284).
- 10 %만 섞었는데 87건이 줄어드는 이유: 한 결재함에 클릭이 **다섯 개**다.\
  섞이는 판정은 결재함 단위라 10 %면 100개쯤이 섞이는데, 섞인 결재함은 다섯 클릭 중 하나만 어긋나도 그 뒤가 줄줄이 무효가 된다.\
  1,000 − 913 = **87건**이 그렇게 멈췄다.

```text
 순차 + 전원 정족수에서 어긋난 클릭 하나의 값
   팀장 -> 본부장A -> [대표] -> 본부장B -> 본부장C
                       ^ 2 단계가 아직 1/3 이라 버려짐
   대표는 다시 눌러야 하는데, 그의 화면에는 이미 결재로 나와 있었다
```

#### 8. 측정 — "올라갈 때만 다시"가 접히는 자리

- 표(README + MeasurementTest assert):

```text
 인상 비율   전부 다시   그대로   올라갈 때만   올라갈 때만의 되돌림
    0 %         189     1,000      1,000              0
   50 %         189     1,000        592            408
  100 %         189     1,000        189            811
                        (전부 다시의 되돌림은 언제나 811)
```

- "전부 다시"는 인상 비율을 **안 탄다** — 올리든 내리든 무조건 지우니까 189로 고정이다.\
  `assertEquals(189, resetAllApproved, "전부 다시는 인상 비율을 안 탄다")`.
- "그대로"는 **1,000** — 아무것도 안 지우니 늘 통과한다.
- 인하만 있는 자료: "올라갈 때만"이 **"그대로"와 같아 보인다**(둘 다 1,000, 되돌림 0).
- 인상만 있는 자료: **"전부 다시"와 같아 보인다**(둘 다 189, 되돌림 811).
- 자기 말로: **규칙은 셋인데, 자료가 한쪽으로 치우쳐 있으면 둘로 보인다.**\
  내가 고른 규칙이 무엇인지가 아니라, 내가 쓴 자료가 무엇인지가 테스트 결과를 정한다.
- 안 보이는 이유: **접힌 두 규칙이 같은 숫자를 내기 때문**이다.\
  189를 보고 "전부 다시를 골랐구나"라고 할 수 없고 "올라갈 때만인데 자료가 전부 인상이었구나"일 수도 있다.\
  숫자가 같으면 어느 쪽으로 접혔는지 **결과만으로는 판별이 안 된다.**

> **접힘(collapse)** — 서로 다른 두 규칙이 특정 자료에서 똑같은 결과를 내어 구분이 안 되는 것.\
> 예: 금액을 내리기만 하는 자료에서는 "올라갈 때만 다시"와 "그대로"가 한 글자도 다르지 않은 결과를 낸다.

- 189가 나오는 까닭(코드 근거): `inbox()` javadoc이 "변경 위치는 1~5 를 뽑는데 5 면 마지막 클릭 뒤라 아무 일도 안 한다. 그래서 변경 100 % 여도 실제로 끼는 것은 **다섯 중 넷**이다"라고 적어놨다.\
  금액 변경이 안 낀 다섯 중 하나(≈200건)만 전원 승인을 다 모을 수 있고, 실제 측정값이 **189**다.

#### 9. 측정 — 같은 결재함, 498 vs 1,000

- 가장 빡빡한 조합: **순차 + 전원 + 전부 다시** → 통과 **498**.
- 가장 헐거운 조합: **병렬 + 아무나 + 그대로** → 통과 **1,000**.
- 빡빡한 쪽이 버린 클릭: **1,328개**.

```text
 같은 입력 (섞임 30 %, 금액 변경 40 %, 그 중 절반이 인상) 결재함 1,000 개

  순차 + 전원 + 전부 다시   통과   498   버린 클릭 1,328
  병렬 + 아무나 + 그대로    통과 1,000   (측정 안 함)

  차이  502 건 — 절반이 통과하느냐 전부 통과하느냐
```

- 이 사실이 말해주는 것: **"팀장, 본부장, 대표 순으로 결재받는다"는 문장이 통과율을 안 정한다.**\
  같은 문장, 같은 결재함인데 고른 조합에 따라 절반이 막히거나 전부 통과한다 — 요구사항 한 문장으로는 시스템이 안 정해진다.
- 1,328명의 인식: **자기가 결재했다고 알고 있다.**\
  화면에서 버튼을 누르고 "결재 완료"를 봤는데 서버는 그 클릭을 버렸다.

#### 10. 측정 — 정족수가 차면 그 뒤 클릭은

- 병렬 결재, 섞임 30 %에서:

```text
 정족수    버린 클릭
  전원          0
  과반        185
  한 명       284
 (셋 다 통과는 1,000 으로 같다)
```

- 전원일 때 0인 이유: **전원 정족수는 다섯 클릭을 다 써야 채워진다.**\
  남는 클릭이 없으니 버릴 것도 없다.
- 한 명 정족수에서 본부장의 클릭이 버려지는 이유: **결재함 전체가 먼저 끝나 버리기 때문**이다.\
  `run` 은 승인이 붙을 때마다 `allComplete` 를 보고, 세 단계가 다 차면 그 자리에서 `APPROVED` 로 바꾼다.\
  그 뒤의 사건은 `status != PENDING` 에 걸려 전부 `ignored` 로 간다.

```text
 한 명 정족수, 순서가 섞여 대표가 먼저 눌린 결재함

  팀장    ->  1 단계 1/1
  본부장A ->  2 단계 1/1
  대표    ->  3 단계 1/1  ->  세 단계 다 참  ->  APPROVED
  본부장B ->  이미 끝남   ->  ignored
  본부장C ->  이미 끝남   ->  ignored

 결과는 통과로 같다. 그런데 B 와 C 는 무엇을 한 것인가
```

  ⚠️ README 는 "한 명 정족수에서는 본부장 셋 중 둘의 클릭이 **늘** 버려진다"고 적었지만, impl 코드를 그대로 따라가면 **순서가 결재선대로면(대표가 마지막이면) 안 버려진다** — B·C 는 그냥 `approvals` 에 쌓인다.\
  실제 측정도 1,000개 결재함에서 284개로, "늘"이라면 나올 수 없는 수다(섞임 30 %라 섞인 결재함이 300개쯤이다).\
  README 문장은 "대표가 먼저 눌린 경우"를 줄여 쓴 것으로 읽는 편이 코드와 맞는다. (이 대조는 원본에 근거 없음 — 내 추론)

- 통과 건수: **셋 다 1,000 으로 같다**(`assertEquals(1_000, approved, "셋 다 통과는 한다")`).
- 코드가 아니라 제품의 질문인 이유: **버려도 결과는 같다.**\
  숫자로는 아무 문제가 없다. 문제는 **그 두 사람의 결재 이력에 무엇을 적을 것인가**이고, 그건 감사·인사·책임의 문제라 코드가 혼자 못 정한다.

> **감사 자료(audit trail)** — 누가 언제 무엇을 했는지 나중에 되짚을 수 있게 남기는 기록.\
> 예: "본부장B가 승인 버튼을 눌렀으나 이미 정족수가 차서 반영되지 않음"까지 남겨야 나중에 "B는 왜 결재를 안 했냐"는 질문에 답할 수 있다.

#### 11. 함정 (README)

- 넷(README 원문 그대로):

```text
 ① 과반을 절반으로 잡는 것          둘짜리 단계에서 한 명이 통과시킨다
 ② 그 단계의 승인자인지 안 보는 것   결재선이 그냥 목록이 된다
 ③ 상신자가 자기 건을 누르게 두는 것 결재선을 사람 이름으로 짜면 늘 생긴다
 ④ 버린 클릭을 안 세는 것            누른 사람은 자기가 결재했다고 알고 있다
```

- ②가 "목록"이 되는 이유: 단계 번호가 **검증에 안 쓰이면** 그냥 화면에 예쁘게 그리는 장식이 된다.\
  아무나 아무 단계를 눌러 통과시킬 수 있으니 "결재선"이라는 말이 뜻을 잃는다.
- ③이 사람 이름 결재선에서 늘 생기는 이유: **결재선을 짤 때는 그 사람이 상신자가 될 줄 모른다.**\
  "1단계 팀장"으로 짜두면, 팀장이 자기 출장비를 올리는 날 1단계가 저절로 통과한다 — 예외가 아니라 정기적으로 온다.
- ④의 피해자: **버려진 클릭을 누른 사람.**\
  결재함 주인(상신자)은 "아직 대기"로 보여서 알 수 있지만, 누른 사람은 자기 화면의 "결재 완료"만 믿고 있다.

- 남의 단계 클릭의 경로: **API 직접 호출.**\
  화면은 자기 단계만 보여주므로 화면으로는 못 만든다(테스트 주석 원문).
- 두 번째 상신의 경로: **재상신을 같은 흐름에 이어 붙였을 때.**\
  반려된 건을 고쳐 다시 올리면서 새 결재함을 안 만들면 같은 사건 목록에 SUBMIT 이 두 번 들어온다.
- 같은 금액 변경의 경로: **사유나 첨부만 고쳐 다시 올렸을 때.**\
  사람 눈에는 "금액을 안 고쳤다"인데 시스템에는 AMEND 사건이 들어온다.
- 정족수 찬 단계 사람을 안 빼면: **독촉 알림이 나간다.**\
  기다릴 필요가 없는 사람에게 "결재해 주세요"가 계속 가면, 알림 자체를 아무도 안 보게 된다.
- 화면과 도메인의 차이: **화면은 "만들기 어렵게" 하고, 도메인은 "안 되게" 한다.**\
  화면이 막는 것은 제안이고, 도메인이 막는 것만 보장이다 — API·배치·재처리·연동은 화면을 안 거친다.

> **화면 검증과 도메인 검증** — 앞단(UI)에서 거르는 것과 뒤단(규칙 코드)에서 거르는 것.\
> 예: 버튼을 회색으로 만들어도 `curl` 로 같은 요청을 보내면 통과한다. 그래서 같은 규칙을 도메인에도 둔다.

#### 13. 생각해볼 것

- 버린 클릭을 누른 사람에게: 최소한 **"반영되지 않았다 + 왜 + 다시 눌러야 하는가"** 셋이 필요하다.\

  지금은 "왜 버렸는지"가 코드 안에만 있고 결과에는 안 남는다. (원본에 근거 없음 — 내 추론)
- 직책으로 결재선을 짜면: **자기결재 문제가 없어지지 않는다.**\
  결재선이 "1단계 = 팀장 직책"이어도 그 자리에 앉은 사람이 상신자면 같은 충돌이다 — 직책을 사람으로 바꾸는 순간 다시 이름이 된다.\
  달라지는 것은 **인사이동에 결재선이 안 깨진다**는 점이고, 자기결재는 여전히 "상신자 == 그 자리의 사람"으로 따로 막아야 한다. (원본에 근거 없음 — 내 추론)
- 금액이 오르내린 결재함의 감사 자료: **금액 이력 전체 + 각 승인이 어느 금액에 붙은 것인지**를 남겨야 한다.\

#### 14. 연결

- 세는 것의 차이: 알고리즘 트랙은 **비용**(비교 횟수 같은, 같은 답으로 가는 값)을 셌다.\
  여기서 세는 것은 **답이 갈리는 건수**다 — 답 자체가 여럿이라서 비용이 아니라 **불일치**를 잰다.\
  이 박스는 거기에 하나를 더 센다: **버린 클릭**, 즉 "결과는 같은데 사람의 인식과 어긋난 건수".
- 사건 목록 → 상태: 실무의 **이벤트 소싱(event sourcing)** 과 같은 모양이다.\
  지금 상태(`Progress`)를 저장하는 게 아니라 사건을 저장하고 **다시 흘려서** 상태를 만든다.

> **이벤트 소싱(event sourcing)** — 지금 상태 대신 "무슨 일이 있었나"의 목록을 저장하고, 필요할 때 처음부터 다시 흘려 상태를 만드는 방식.\
> 예: 이 박스의 `run(events, order, quorum, amendRule)` 은 같은 사건 목록을 규칙만 바꿔 다시 흘려 18가지 답을 낸다 — 상태만 저장했다면 못 하는 일이다.

- "버린 클릭"과 같은 자리: 앞 박스들의 **"조용히 버려진 입력"** 과 같은 자리다 — 결과에는 안 나타나지만 사람은 했다고 믿는 값.\
  01-parking-fee 의 "음수 시간을 0으로 뭉개기"가 같은 종류다(에러 없이 정상처럼 끝나는데 사실은 틀린 것). (다른 박스와의 대응은 원본에 근거 없음 — 내 추론)
- PR 리뷰 규칙의 번역:

```text
 PR 규칙                        이 박스의 값
 "코드 오너 목록"          →   Step.approvers()
 "승인 N 개 필요"          →   Quorum (ALL / MAJORITY / ANY)
 "누구든 먼저 승인 가능"   →   Order.PARALLEL
 "자기 PR 은 자기가 승인 못 함"  →  상신자 검사
 "새 커밋이 오면 승인 무효" →   AmendRule.RESET_ALL
 "문서만 고친 커밋은 유지"  →   AmendRule.RESET_IF_HIGHER 같은 조건부 규칙
```

  GitHub 의 "dismiss stale approvals when new commits are pushed" 옵션이 정확히 `AmendRule` 갈래다. (대응 관계는 원본에 근거 없음 — 내 추론)
- 접힘과 같은 패턴: **한 방향으로만 치우친 자료로 테스트하면 규칙 수가 줄어 보인다**는 현상 자체가 패턴이다.\
  이 박스에서는 "인하만 있는 자료"가 세 규칙을 둘로 접었고, 같은 일이 "순서를 한 번도 안 어긴 자료"에서도 일어난다(18조합이 통째로 같아진다).\
  자료를 만들 때 **일부러 반대 방향을 섞어야** 갈래가 보인다.
