# domain-modeling/23-versioned-rules-and-effective-dating — 정답

## 정답

### 1. 덮어쓰기가 잃는 것

- "그 주문을 계산할 때 요율이 얼마였나"에 답할 수 없다. 과거 주문을 다시 계산하면 지금 요율로 계산된다.
- 판을 쌓아도 남는 결정
  - **적용 기준 시각**: 주문·결제·처리 중 어느 시각으로 판을 고르나.
  - **발효 시각의 표현**: 데이터(`effective` 시작)로 둘 것인가, 배포로 둘 것인가. 그리고 그 시각은 어느 시간대의 자정인가.

### 2. 반열린 구간

```text
  1/1            7/1                 11/1
  ├──── v1 ──────┤├──── v2 ───────────┤├──── v3 ─────▶
  [             )[                   )[
  6/30 23:59:59.999999 → v1      7/1 00:00:00 → v2
```

- 실험 출력: `2026-06-30 23:59:59.999999+09 | {1}`, `2026-07-01 00:00:00+09 | {2}`.
- 반열린이면 맞닿은 두 판이 경계 시각을 나눠 갖지 않는다. 닫힌 구간이면 경계 시각에 두 판이 모두 맞거나, "끝 = 다음 시작 − 1초" 같은 계산이 필요하고 그 사이 빈틈이 생긴다.

### 3. 재계산 비교 (PG 17.11 실험)

| 방법 | 불일치 건수 |
|---|---|
| 덮어쓴 요율(0.0350) | 599건(v1 시기 전부), 합 155,998원 차이 |
| 주문 시각으로 판 재조회 | 0건 |
| 저장된 판 스탬프 | 0건 |

### 4. 경계 주문 1001

- 주문 시각 기준: v1(3.00%) → 3,000원. 결제 시각 기준: v2(3.50%) → 3,500원.
- 어느 쪽인지는 약관·법·계약이 정한다. 코드는 그 결정을 `Anchor` 같은 이름으로 드러내고, 결과 행에 기준 시각과 판을 남긴다. 처리 시각 기준의 위험은 [advanced/09-policy-version](../advanced/09-policy-version/2-summary.md) 규칙 ②.

### 5. `EXCLUDE`가 막는 것과 못 막는 것

- 막는 것: 같은 `rule_id`에서 유효 구간이 겹치는 판. 실험에서 6/15~8/1 판이 `conflicting key value violates exclusion constraint`로 거절됐다.
- 못 막는 것
  - **빈틈**: 판 사이가 비어도 거절하지 않는다. `lead(lower(effective))`로 이웃과 맞닿는지 점검한다.
  - **판 없음**: 첫 판 이전 주문(1003). `LEFT JOIN … WHERE v.version IS NULL`로 찾는다. 내부 조인 집계에서는 조용히 빠진다.
  - 판 행의 UPDATE(값 변경): 권한·트리거로 따로 막는다.

### 6. 미래 발효와 배포 지연

- 10/31 23:59:59 → v2 0.0350, 11/1 00:00:00 → v3 0.0400. 같은 쿼리, 조회 시각만 다르다.
- 코드 상수 + 03:00 배포 가정: 00:00~02:59 주문 **36건**이 구 요율로 계산됐고 9,226원을 덜 받았다.

### 7. 버전 스탬프의 효과

- 스탬프가 있으면 재계산은 `(rule_id, rule_version)`으로 판을 바로 조인해 "다시 계산한 값 = 저장값"인지 보는 비교다. 기준 시각으로 판을 다시 찾지 않으니 기준 시각 논쟁·빈틈과 무관하게 점검된다.
- 22번(결정 기록)은 판 외에 **입력 스냅숏·중간 산출·결정 시각**까지 한 레코드로 남겨, 입력 데이터가 바뀐 뒤에도 같은 결과를 재현하게 한다([22-decision-log-and-provenance](../22-decision-log-and-provenance/2-summary.md)).

### 8. `floorEntry`와 빈틈

- `floorEntry(t)`는 시작 시각 ≤ t 인 판 중 가장 늦은 것을 돌려줄 뿐, 그 판의 **끝**을 보지 않는다.
- 빈틈 안의 t에서도 직전 판을 돌려줘서, 이미 끝난 판으로 계산하게 된다.
- 보완: 고른 판의 `contains(t)`(`t < to`)를 확인하고 아니면 예외를 낸다(노트의 `FeeSchedule.at`). Extra 실험에서 첫 판 이전 시각은 `null`이 나왔다 — 이것도 "판 없음"으로 처리한다.

### 9. 스탬프 재현성 불일치 급증

- 의심: 판 테이블의 행이 UPDATE됐다(같은 판 번호의 `rate`가 바뀜). "같은 판 번호 = 같은 규칙" 전제가 깨졌다.
- 확인: 판 테이블의 변경 이력(감사 로그·트리거 이력)과 불일치 행의 `rule_version` 분포.
- 재발 방지: 판 행 UPDATE·DELETE 권한을 막거나 트리거로 거절한다. 정정은 새 판으로 하고, 잘못된 판으로 이미 계산된 결과의 처리(유지·재계산·조정)를 따로 결정한다.

### 10. 계산 공식이 바뀌는 경우

- 공식은 데이터만으로 바꿀 수 없으니 새 로직을 **미리 배포**한다.
- 판 데이터에 "어느 계산기를 쓰는가"(예: `calculator = 'v2-tiered'`)와 발효 구간을 두고, 판을 고른 뒤 그 계산기로 분기한다.
- 그러면 발효 시각은 여전히 데이터가 정하고, 배포 시각과 분리된다. 결과 행에는 판과 함께 계산기 식별자가 남는다.
