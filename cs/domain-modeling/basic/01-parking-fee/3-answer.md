### A. 과제

#### 0. 규칙 세 줄이 안 말해주는 것

- 안 말해주는 자리 넷(README 표 그대로):

```text
 안 말해준 것      가능한 읽기
 "10 분까지"   →  10 분 정확히는 무료인가 유료인가
 "10 분마다"   →  초과 1 분을 한 단위로 세나 버리나
 "하루"        →  자정 기준 날짜인가 입차 후 24 시간인가
 초 단위        →  1 분 1 초는 1 분인가 2 분인가
```

- 10분 정확히: **무료다.** 테스트가 `chargeFor(10) == 0`, `chargeFor(11) == 1000` 으로 못 박았다 — "10분 무료"의 10을 포함한다(`minutes <= freeMinutes`).
- 초과 1분: **정책이 정한다.** `partialUnitCharged=true` 면 1단위(31분 → 1,500원), false 면 0단위(31분 → 1,000원).
- "하루": **정책이 정한다.** `capPerCalendarDay=true` 면 자정 기준, false 면 입차 시각부터 24시간.
- 1분 1초: **2분이다.** `minutesParked` 가 초를 올린다.
- 정책 값으로 올리면: **두 해석을 같은 코드로 돌려 답이 갈리는 건수를 셀 수 있다.** 그래야 "구석 사례"인지 "계약의 본체"인지 재보고 안다.
- 그냥 하나 골라 구현하면: 그 선택이 코드 안에 숨어버려 **나중에 "왜 이렇게 나오냐"는 문의가 들어와도 어디가 갈림인지 못 찾는다.** 세어보기 전에는 그 갈림이 몇 건인지도 모른다.

#### 1. TODO 1 — minutesParked

정답 코드 (impl/ParkingFee.java):

```java
if (exit.isBefore(entry)) {
    throw new IllegalArgumentException("출차가 입차보다 빠르다: " + entry + " -> " + exit);
}
long seconds = Duration.between(entry, exit).toSeconds();
return (seconds + 59) / 60;
```

- 올림 나눗셈: `(seconds + 59) / 60`\
  나누는 수보다 1 작은 값을 먼저 더하고 내림하면, 결과가 올림이 된다.

> **올림 나눗셈** — 나머지가 조금이라도 있으면 몫을 한 칸 올리는 나눗셈.\
> 예: 61초를 분으로 바꿀 때 그냥 나누면 1분(버림)이지만, 올림 나눗셈은 2분이 된다.

- 손계산:

```text
 초    0    1    60   61
 식  (0+59)/60 (1+59)/60 (60+59)/60 (61+59)/60
     = 59/60   = 60/60   = 119/60   = 120/60
 분    0        1         1          2
```

- 뒤집힌 시각을 거부하는 이유: **음수 시간을 0으로 뭉개면 잘못된 데이터가 조용히 0원이 된다.**\
  기기 시계가 어긋난 경우가 실제로 있고, 그때 알아야 한다(테스트 주석 원문).
- 조용해지는 사고: 시계 어긋난 기기가 **모든 차를 공짜로 내보낸다.**\
  0원 영수증은 정상 영수증과 똑같이 생겨서 아무도 안 본다.

> **조용한 실패(silent failure)** — 프로그램이 에러를 내지 않고 정상처럼 끝나는데, 결과만 틀린 것.\
> 예: 출차가 입차보다 빠른 기록에서 예외를 던지면 바로 알지만, 0원을 돌려주면 "무료 주차였나 보다" 하고 넘어간다.

#### 2. TODO 2 — feeForMinutes

정답 코드:

```java
if (minutes <= policy.freeMinutes()) {
    return 0;
}
if (minutes <= policy.baseMinutes()) {
    return policy.baseFee();
}
long over = minutes - policy.baseMinutes();
long units = policy.partialUnitCharged()
        ? (over + policy.unitMinutes() - 1) / policy.unitMinutes()
        : over / policy.unitMinutes();
return policy.baseFee() + units * policy.unitFee();
```

- 순서 = 계약: ① **무료 시간 이내면 0** ② **기본 시간 이내면 기본 요금** ③ 남은 초과분(over)을 단위로 나눠 더한다.\
  이 순서가 바뀌면 경계값이 전부 어긋난다.
- 먼저 안 끊으면: minutes=11 일 때 `over = 11 - 30 = -19` 가 된다.\
  올림식이 `(-19 + 9) / 10 = -10/10 = -1` 이므로 **요금은 `1000 + (-1)×500 = 500원`** 으로 조용히 깎인다.
- 자바의 `/` 는 **0 쪽으로 자른다** — `-9 / 10 == 0`, `-19 / 10 == -1`.\
  내림(floor)이 아니라서 음수에서 값이 커지는 쪽으로 잘린다.

> **0 쪽으로 자르기(truncate toward zero)** — 나눗셈 결과의 소수점을 버릴 때, 항상 0에 가까워지는 방향으로 버리는 것.\
> 예: `-1.9` 를 내림하면 `-2` 지만, 0 쪽으로 자르면 `-1` 이다. 그래서 음수 요금이 생각보다 덜 깎인다.

- 경계값 30분만 보면 안 잡히는 이유: 그 자리는 `over == 0` 이라 **단위가 0개**다.\
  끊으나 안 끊으나 `baseFee` 로 같아서, 버그는 **경계 밑(11~29분)** 에서만 보인다.
- 31분 요금:

```text
 over = 31 - 30 = 1
 partialUnitCharged=true   (1 + 9)/10 = 1 단위  →  1000 + 500 = 1,500 원
 partialUnitCharged=false   1/10      = 0 단위  →  1000 +   0 = 1,000 원
                                                    500 원 차이
 딱 떨어지는 40분(over=10)이면 둘 다 1 단위 → 1,500 원으로 같다
```

#### 3. TODO 3 — charge

정답 코드:

```java
if (exit.isBefore(entry)) {
    throw new IllegalArgumentException("출차가 입차보다 빠르다: " + entry + " -> " + exit);
}
long total = 0;
LocalDateTime cursor = entry;
while (cursor.isBefore(exit)) {
    LocalDateTime windowEnd = nextWindowEnd(cursor, policy);
    LocalDateTime segmentEnd = windowEnd.isBefore(exit) ? windowEnd : exit;
    long minutes = minutesParked(cursor, segmentEnd);
    long fee = feeForMinutes(minutes, policy);
    total += policy.dailyCap() > 0 ? Math.min(fee, policy.dailyCap()) : fee;
    cursor = segmentEnd;
}
return total;
```

- 루프 조건이 `isBefore` 인 이유: **0분 주차(입차 즉시 출차)면 한 바퀴도 안 돌아야 0원**이다.\
  `<=` 로 쓰면 cursor==exit 에서 한 바퀴 더 돌아 요금이 붙는다.
- 상한은 **조각마다** 건다(`Math.min(fee, dailyCap)` 을 루프 안에서).\
  마지막에 한 번만 걸면 3일 주차도 20,000원이 되어 "하루 최대"가 "전체 최대"로 바뀐다.
- `dailyCap == 0` = **상한 없음**(`dailyCap() > 0` 일 때만 min 을 적용).
- 조각마다 새로 붙는 것: 무료 시간도 기본 요금도 **날마다 새로 붙는다.**\
  그래서 나누는 쪽이 항상 싸지 않다.
- `charge` 도 거부해야 하는 이유: 안 거부하면 `while (cursor.isBefore(exit))` 가 **한 번도 안 돌아 조용히 0원**이 나온다.\
  `minutesParked` 는 거부하는데 `charge` 는 0을 주면, 부르는 쪽이 어느 쪽을 믿을지 모른다.

> **계약(contract)** — 함수가 "이런 입력에는 이렇게 답한다"고 밖에 약속한 내용.\
> 예: "뒤집힌 시각은 거부한다"가 계약이면, 같은 입력에 한 함수만 예외를 던지고 다른 함수는 0을 주면 안 된다.
- 손계산 (23:00 입차, 다음날 01:00 출차, 자정 기준):

```text
 조각 1  23:00 ~ 24:00   60분  over=30  units=3  → 1000 + 1500 = 2,500
 조각 2  00:00 ~ 01:00   60분  over=30  units=3  → 1000 + 1500 = 2,500
                                               합계  5,000 원
 안 나누면  120분 통째  over=90  units=9  → 1000 + 4500 = 5,500 원
```

- 다음 자정: `cursor.toLocalDate().plusDays(1).atStartOfDay()` — 날짜만 떼서 하루 더하고 0시로.

  계약은 `charge` 의 결과 금액뿐이다.

> **계약 표면(public API)** — 바깥 코드가 직접 부를 수 있는 함수들의 집합.\
> 예: `charge` 는 public 이라 한 번 공개하면 이름도 결과도 함부로 못 바꾸지만, private 인 `nextWindowEnd` 는 언제든 갈아엎어도 된다.

### B. 개념

#### 6. 측정 — 답이 갈리는 건수

- 올림/버림: 무작위 1,000건 중 **444건**이 갈리고 최대 차이 **1,000원**.
- 짧은 주차(2시간 이내)만: **695/1,000**. 더 많이 갈리는 이유는 **긴 주차는 상한(20,000원)에 걸려 두 판이 똑같아지기 때문** — 상한이 갈림을 덮는다.
- "하루"의 기준: **571/1,000**.
- 3/1 8:00 입차, 정확히 3일:

```text
 자정 기준     3/1(16h)  3/2(24h)  3/3(24h)  3/4(8h)    네 조각
               20,000  + 20,000  + 20,000  + 20,000  =  80,000 원
               (조각마다 상한에 걸린다. 예: 3/1 은 960분 → 47,500 → 20,000)

 24시간 기준   [8:00~8:00] × 3                         세 조각
               20,000  + 20,000  + 20,000            =  60,000 원

                                            차이       20,000 원
```

- 자정을 아예 안 나누면: **720/1,000** 이 갈린다. 방향이 일정하지 않은 이유 — 나누면 **무료 시간·기본 요금·상한이 날마다 새로 붙어** 짧은 밤샘 주차는 싸지고(23:00~01:00: 5,000 vs 5,500) 긴 주차는 비싸진다(3일: 80,000 vs 20,000).
- 상한을 없애면: 444 → **943/1,000**.\
  상한에 걸리면 두 판이 똑같이 20,000이 되어 갈림이 안 보였을 뿐이다.
- "상한이 있으니 대충"이 위험한 이유: **상한 아래에 있는 대부분의 실제 주차에서는 그 세부가 그대로 금액이 된다.**\
  갈림이 사라진 게 아니라 측정에서 가려진 것이다.

> **가려진 갈림(masking)** — 나중에 덮어쓰는 규칙 때문에, 앞 단계의 차이가 결과에서 안 보이게 되는 것.\
> 예: 올림이면 29,500원, 버림이면 29,000원이라도 상한 20,000원에 걸리면 둘 다 20,000원이 되어 "차이 없음"으로 보인다.

- "손님에게 유리하게"로 못 정하는 이유: 자정 분할은 **한쪽이 항상 싸지 않다.**\
  지침이 방향을 주려면 한 방향으로 기울어 있어야 하는데, 여기는 안 기울어 있다.

#### 7. 함정 (README)

- 넷: ① 기본 시간 이내를 **먼저 끊어야 한다**(안 끊으면 음수 나눗셈으로 요금이 깎인다) ② 자정을 넘기면 **날마다 무료 시간과 기본 요금이 새로 붙는다**(그래서 나누는 쪽이 항상 싸지 않다) ③ `charge` 와 `minutesParked` 가 **뒤집힌 시각을 다르게 처리하면 안 된다** ④ **정기권을 계산 앞에 볼지 뒤에 볼지**가 잘못된 입력에서 갈린다.
- 조용히 0이 되는 것: `charge` 의 **총액**. 루프 조건이 `isBefore` 라 한 바퀴도 안 돌고 `total` 이 0으로 반환된다.
- 방향이 일정하지 않은 두 예: `23:00~01:00` → 나누면 5,000 / 안 나누면 5,500 (**나누는 쪽이 싸다**). `8:00부터 3일` → 나누면 80,000 / 안 나누면 20,000 (**안 나누는 쪽이 싸다**).

#### 8. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 정책 변경 중 입차 중인 차: 이 코드는 `charge(entry, exit, policy)` 로 **정책을 인자로 받으므로 "어느 정책"을 고르는 책임이 밖에 있다.** 정하는 법은 셋 — 입차 시각의 정책(손님 기대에 맞음) / 출차 시각의 정책(구현이 제일 쉬움) / 구간별로 그때의 정책(제일 정확하지만 `charge` 의 조각 루프를 정책 변경 시각으로도 쪼개야 한다). 어느 쪽이든 **정책에 유효기간을 붙여야** 고를 수 있다. (원본에 답 없음 — 내 추론)
- 서머타임: `LocalDateTime` 은 시간대가 없어서 이 코드에서는 문제가 안 드러난다. 실제로는 **"하루"가 23시간이나 25시간이 되는 날**이 생긴다 — `cursor.plusDays(1)`(달력 기준 하루)과 `cursor.plusHours(24)`(물리 24시간)가 그날 달라진다. 요금 계산의 기준은 보통 **달력 기준**(손님이 보는 날짜)이 맞고, 이때는 `ZonedDateTime` 이 필요하다. (원본에 답 없음 — 내 추론)
- 10분마다 재입차: 이 코드는 **주차 1회(entry~exit)만 본다.** 막으려면 "같은 차량의 직전 출차로부터 N분 이내 재입차는 이어진 한 건으로 본다" 같은 규칙이 필요한데, 그건 `ParkingFee` 가 아니라 **입출차 기록을 가진 상위 계층(세션 병합)** 의 일이다. 요금 함수를 순수하게 두는 대가로 이 규칙이 밖으로 나간다. (원본에 답 없음 — 내 추론)
- 상한을 "연속 주차 1회"로: **조각 루프가 사라진다.** `charge` 는 전체 분수를 한 번에 요금으로 바꾸고 상한을 한 번만 걸면 된다 — 즉 지금의 `chargeIgnoringMidnight` 에 가까워진다. 3일 주차가 20,000원이 되므로 **장기 주차 수익이 사라진다**(측정의 80,000 vs 20,000이 그 차이다). (원본에 답 없음 — 내 추론)

#### 9. 연결

- 세는 것의 차이: 알고리즘 트랙은 **비교 횟수**(같은 답으로 가는 비용)를 셌다. 여기서 세는 것은 **답이 갈리는 케이스 수** — 답 자체가 여럿이라서 비용이 아니라 **불일치**를 잰다.
- 실무 관행과의 대응: 모호한 자리를 record 값으로 올리는 것은 **정책/설정 외부화(feature flag · 요금 정책 테이블)** 와 같다. 값으로 있으면 "누가 언제 무엇으로 정했는지"가 남고, 두 값을 나란히 돌려볼 수 있다.
- 같은 자리의 뒤 박스: **04-hotel-booking**(체크인/체크아웃 날의 겹침 — 구간 끝이 포함인가), **08-meeting-slot**(경계 맞닿음), **19-tax**(누진 구간 경계) — 전부 "경계를 포함하나"가 답을 가른다.
