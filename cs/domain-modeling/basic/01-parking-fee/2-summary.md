# domain-modeling/basic/01-parking-fee — 정리 (힌트)

## 해결하는 문제

"10분까지 무료, 30분까지 1,000원, 이후 10분마다 500원, 하루 최대 20,000원." 이 세 줄만 주면 개발자마다 다른 요금표가 나온다.\
문장이 안 정해준 자리("10분까지"의 10분, 초과 1분, "하루"의 기준)를 각자 머릿속에서 채우기 때문이다.

```text
같은 세 줄  →  A의 코드: 31분 = 1,000원 (버림)     B의 코드: 31분 = 1,500원 (올림)
           →  A의 코드: 3일 = 60,000원 (24시간)   B의 코드: 3일 = 80,000원 (자정)
                          둘 다 "규칙대로" 만들었고, 둘 다 테스트가 통과한다
```

이 방식이 없으면 그 차이가 코드 안의 `if` 한 줄에 숨고, 정산이 끝난 뒤에야 "왜 금액이 다르냐"로 드러난다.\
쉬운 예: "1시간 무료 주차" 표지판 — 61분이면 얼마인지, 표지판은 말해주지 않는다.\
똑같은 구조다: 빈칸을 코드에 숨기지 않고 **정책 값(`FeePolicy`)**으로 올리면, 두 해석을 같은 코드로 돌려 **답이 갈리는 건수**를 셀 수 있다.\
실무 예: 통신요금 일할, 렌터카 "1일" 요금, 클라우드 시간당 과금 — 전부 "단위에 못 미치는 나머지"와 "하루의 기준"이 금액을 가른다.

### 한눈에 — 쉽게 말하면

**주차 요금 = "말로는 세 줄, 해석은 여러 갈래"인 규칙을 코드로 못박는 연습.**

- "우유 사 와"라는 심부름과 같다. 어떤 우유? 몇 개? 없으면? — **말이 안 정해준 자리는 듣는 사람마다 다르게 채운다.** 요구사항도 똑같은 구조다.
- 주차장 규칙은 세 줄이다: "10분까지 무료, 30분까지 1,000원, 이후 10분마다 500원, 하루 최대 20,000원." 그런데 "10분 정확히는 무료인가", "초과 1분은 한 단위인가", **"하루는 자정 기준인가 입차 후 24시간인가"** — 세 줄이 하나도 안 정해준다.
- 이 챕터의 방식: 애매한 자리를 코드 안에 숨기지 않고 **정책 값(`FeePolicy`)으로 올린다.** 그러면 두 해석을 같은 코드로 돌려서 **답이 몇 건이나 갈리는지 셀 수 있다.**
- 세어 보니 넷 다 1,000건 중 절반 넘게 갈렸다 — 구석 사례가 아니라 **계약의 본체**였다.

```text
요구사항 문장            →  코드에서의 자리
"10분까지 무료"          →  FeePolicy.freeMinutes = 10
"30분까지 1,000원"       →  baseMinutes = 30, baseFee = 1000
"10분마다 500원"         →  unitMinutes = 10, unitFee = 500
"(초과 1분도 한 단위?)"  →  partialUnitCharged = true/false  ← 문장에 없어서 값으로 올림
"하루 최대 20,000원"     →  dailyCap = 20000
"(하루의 기준은?)"       →  capPerCalendarDay = true/false   ← 문장에 없어서 값으로 올림
```

실무 예: 통신요금 일할 계산, 렌터카 "1일" 요금, 클라우드 시간당 과금 — 전부 "단위에 못 미치는 나머지"와 "하루의 기준"이 돈을 가른다.

## 동작·원리

### 전체 흐름

```text
minutesParked(입차, 출차)          몇 분 주차했나 (초는 올림, 뒤집힌 시각은 거부)
        ↓
feeForMinutes(분, 정책)            그 분수의 요금 (무료 → 기본 → 단위 순서, 상한 없음)
        ↓
charge(입차, 출차, 정책)           자정(또는 24시간)으로 조각내고, 조각마다 요금+상한, 합산
        ↓
chargeFor(..., 정기권 여부)        정기권이면 계산 자체를 안 하고 0원

대조용: chargeIgnoringMidnight     자정을 안 나누는 판 — 측정에서 비교 상대
측정:   두 해석을 같은 입력 1,000건에 돌려 "답이 갈리는 건수"를 센다
```

### 규칙 1 — 주차 시간: 초는 올린다 (`minutesParked`)

**어떤 요구사항인가**: "몇 분 주차했나"부터 정해야 한다. 1분 1초는 1분인가 2분인가 — 규칙 세 줄에 없다.

예시 입력과 결과:

```text
9:00:00 → 9:00:00   0분
9:00:00 → 9:00:01   1분   ← 1초도 1분으로 올림
9:00:00 → 9:01:00   1분
9:00:00 → 9:01:01   2분   ← 61초 = 2분

계산: (초 + 59) / 60   — 정수 나눗셈으로 올림하는 관용구
```

**왜 이렇게 모델링했나**: 내리면 손님에게 유리하고 올리면 주차장에 유리하다. 어느 쪽이 맞다가 아니라 **어느 쪽이든 정해야 한다** — 안 정하면 구현마다 달라진다. 여기서는 올림으로 정했다.

- 출차가 입차보다 빠르면(기기 시계가 어긋난 경우가 실제로 있다) 0으로 뭉개지 않고 **예외로 거부한다.** 잘못된 데이터가 조용히 0원이 되면 아무도 모른다.

### 규칙 2 — 요금 계산: 순서가 계약이다 (`feeForMinutes`)

**어떤 요구사항인가**: "10분 무료, 30분까지 1,000원, 이후 10분마다 500원."

예시 손계산 — **130분 주차** (표준 정책, 올림 판):

```text
[1] 130분 > 무료 10분        → 무료 아님
[2] 130분 > 기본 30분        → 기본 요금만으로 안 끝남
[3] 초과 = 130 - 30 = 100분
[4] 단위 = 100 / 10 = 10개   (딱 떨어짐)
[5] 요금 = 1,000 + 10 × 500 = 6,000원
```

경계값 표 (테스트가 실제로 박아둔 값):

```text
분    0   10   11   30   31   40   41
원    0    0 1000 1000 1500 1500 2000
     └─무료 경계─┘    └─기본 경계─┘
10분은 무료, 11분부터 1,000원 — "10분까지"의 10을 포함한다
30분은 1,000원, 31분부터 1,500원 — 초과 1분이 한 단위로 올라간다
```

**왜 이렇게 모델링했나 (함정 포함)**:

- **무료·기본 이내를 먼저 끊어야 한다.** 안 끊으면 초과분(over)이 음수가 되고, 자바 나눗셈은 0 쪽으로 자르므로 요금이 **조용히 깎인다** — 예외도 안 난다.
  - *0 쪽으로 자름(truncation)*: 자바에서 `-7 / 10`은 -1이 아니라 0. 음수가 끼면 "버림"이 기대와 달라진다.
- 초과 1분을 한 단위로 세는가(`partialUnitCharged`)는 정책 값이다. 31분 주차: 올림이면 1,500원, 버림이면 1,000원 — **500원 차이**.
- 경계값(딱 30분)은 끊으나 안 끊으나 같다 — over가 0이라서. **경계 하나만 테스트하면 이 버그를 못 잡는다.**

### 규칙 3 — "하루"의 기준: 조각내기 (`charge`)

**어떤 요구사항인가**: "하루 최대 20,000원." 그런데 "하루"가 뭔가 — 자정 기준 날짜인가, 입차 후 24시간인가.

**모델링**: 주차 전체를 창(window)으로 조각내고, **조각마다** 요금을 계산해 상한을 걸고 합산한다. 창의 끝이 정책에 따라 다르다:

```text
capPerCalendarDay = true  → 다음 자정         (달력 날짜 기준)
capPerCalendarDay = false → 지금부터 24시간 뒤 (입차 시각 기준)
```

예시 손계산 — 3월 1일 8:00 입차, 정확히 3일 주차:

```text
자정 기준:    |--3/1--|----3/2----|----3/3----|-3/4-|
               16시간    24시간      24시간     8시간   → 네 조각
              조각마다 상한 20,000 → 20,000 × 4 = 80,000원

24시간 기준:  |--8:00~8:00--|--8:00~8:00--|--8:00~8:00--|
                                                          → 세 조각
              20,000 × 3 = 60,000원
```

**2만 원 차이다.** "하루 최대 2만 원"이라는 문장은 "하루"를 정하지 않으면 아무것도 정하지 않은 것이다.

- 조각을 나누면 **날마다 무료 시간과 기본 요금이 새로 붙는다.** 그래서 나누는 쪽이 항상 비싸지도, 항상 싸지도 않다:

```text
23:00 ~ 다음날 01:00 (2시간)
  나눔:   [23:00~24:00] 2,500 + [00:00~01:00] 2,500 = 5,000원  ← 나누는 쪽이 쌈
  안 나눔: 120분 통째로 = 5,500원
8:00부터 3일
  나눔: 80,000원   안 나눔: 20,000원(상한 1번)                  ← 안 나누는 쪽이 쌈
```

**왜 중요한가**: 방향이 일정하지 않으니 **"손님에게 유리하게"라는 지침으로는 이 결정을 못 한다.** 비즈니스가 정해줘야 하는 결정이다.

### 규칙 4 — 정기권: 계산 앞에서 본다 (`chargeFor`)

**어떤 요구사항인가**: "정기권 차량은 0원."

**모델링**: subscriber면 **다른 계산을 아예 안 하고** 0을 돌려준다. "계산하고 0을 곱한다"와 다르다.

```text
정기권 먼저 확인  → 뒤집힌 시각(시계 오류)이어도 0원 통과
계산을 먼저 하면  → 뒤집힌 시각에서 예외가 터짐
```

**왜 이렇게 정했나**: 정기권 차량의 기기가 시계 오류를 냈을 때 — 요금이 어차피 0이면 통과시키는 게 맞다고 보고 순서를 그렇게 정했다. **검사 순서도 잘못된 입력에서 드러나는 설계 결정이다.**

## 쓰이는 자료구조·알고리즘

- **정책 레코드(값 객체)** — `FeePolicy` record 하나에 값 8개(시간·요금 6개 + 해석 플래그 2개)를 모으고 생성자에서 말이 안 되는 조합(무료 > 기본, 단위 0분)을 거부한다. 06번 `ProrationPolicy`·07번 `QuietHours`가 같은 자리.
- **정수 올림 관용구 `(초 + 59) / 60`** — 자바 나눗셈이 0쪽으로 자르는 성질을 역이용한 올림. 단, 피제수가 음수가 되면 뜻이 뒤집힌다(규칙 2의 함정 — 그래서 무료·기본을 먼저 끊는다).
- **창(window) 단위 조각내기 루프** — 커서를 `nextWindowEnd`로 옮기며 조각마다 계산·상한·합산. [05-attendance](../05-attendance/2-summary.md)의 자정 분할, [08-meeting-slot](../08-meeting-slot/2-summary.md)의 커서와 같은 모양이다.
- **상한 = `min(요금, dailyCap)`을 조각마다** — 조각을 어떻게 자르느냐(자정/24시간)가 곧 상한의 뜻이 된다.
- **대조군 구현 + 갈린 건수 세기** — `chargeIgnoringMidnight`처럼 틀린 판을 일부러 남기고 무작위 1,000건에서 답이 다른 건수를 센다. 알고리즘 트랙이 비교 횟수를 세던 자를 도메인으로 옮긴 것.
- **`java.time`** — `LocalDateTime`·`Duration`으로 시각 차이와 다음 자정을 계산한다. 시간대·서머타임은 이 챕터 범위 밖이다(README "생각해볼 것").

## 적용 — 풀어나가는 법

실제 요금 규칙 문장을 받았을 때의 순서: ① 문장에서 "안 정해진 자리"를 표로 뽑는다 ② 자리마다 정책 값을 만들고 생성자에서 말이 안 되는 조합을 막는다 ③ 계산 순서(무료 → 기본 → 단위 → 조각 → 상한)를 고정한다 ④ 두 해석을 같은 입력에 돌려 갈린 건수를 센 뒤, 결정을 비즈니스에 넘긴다.\
아래 「문제」 절이 ①의 재료이고, 「측정」 절이 ④의 결과다.

### 문제 — 이 챕터가 시키는 것

주어진 규칙은 딱 세 줄이다(원본 README 그대로).

```text
  10 분까지 무료
  30 분까지 1,000 원
  이후 10 분마다 500 원, 하루 최대 20,000 원
```

**"어려운 것은 이 세 줄이 안 말해주는 자리다."**

- "10분까지"의 10분은 무료인가 유료인가?
- "10분마다"에서 초과 1분을 한 단위로 세나 버리나?
- "하루"가 자정 기준 날짜인가 입차 후 24시간인가?
- 1분 1초는 1분인가 2분인가?

**셋 다 말이 된다.**\
그래서 이 박스는 답을 하나로 정하지 않고 `FeePolicy` 값으로 올린다.\
그러면 두 해석을 같은 코드로 돌려 **답이 갈리는 건수를 셀 수 있다.**

> **정책 값으로 올린다** — 코드 안에 조건문으로 숨긴 선택을, 밖에서 바꿀 수 있는 설정값으로 꺼내는 것.\
> 예: `if (초과분 > 0) 올림한다` 를 `partialUnitCharged` 라는 값으로 빼면, 같은 코드로 올림 판과 버림 판을 둘 다 돌려볼 수 있다.

과제(원본 README "채울 것"): `src/main/java/com/domain/parking/ParkingFee.java` 의 **TODO 1~5**. `FeePolicy` 는 계약이라 다 주어져 있다.

| TODO | 함수 | 시키는 것 |
|---|---|---|
| 1 | `minutesParked(entry, exit)` | 주차 시간(분). **초 단위는 올린다.** 뒤집힌 시각은 거부 |
| 2 | `feeForMinutes(minutes, policy)` | 상한 없는 요금. **순서가 계약** — 무료 → 기본 → 나머지를 단위로 |
| 3 | `charge(entry, exit, policy)` | 상한까지 적용. 자정(또는 24시간)으로 쪼개서 조각마다 상한을 걸고 합산 |

### 측정 — 갈림은 구석이 아니라 본체였다

알고리즘 트랙은 비교 횟수를 셌다. 여기서 세는 것은 **"두 해석의 답이 다른 케이스 수"** — 무작위 주차 1,000건 기준:

| 갈림의 원인 | 갈린 건수 | 비고 |
|---|---|---|
| 초과 단위 올림 vs 버림 | 444 / 1,000 | 짧은 주차(2시간 이내)만 보면 **695** |
| "하루" = 자정 vs 24시간 | 571 / 1,000 | 대표 사례 2만 원 차이 |
| 자정을 나눔 vs 안 나눔 | 720 / 1,000 | **방향이 일정하지 않다** |
| 올림/버림 — 상한 없이 재면 | **943** / 1,000 | 상한이 갈림을 덮고 있었다 |

- **상한이 갈림을 덮는다**: 상한에 걸리면 두 판 다 20,000원으로 같아진다. "상한이 있으니 세부 규칙은 대충 해도 된다"가 위험한 이유 — 상한 아래에 있는 대부분의 실제 주차에서는 그 세부가 그대로 금액이 된다.
- 갈린 수가 작으면 구석 사례고 크면 계약의 본체다. **재보기 전에는 어느 쪽인지 알 수 없다.** 여기서는 넷 다 절반이 넘었다.

## 장애 시나리오와 대처

**1. 화면 요금과 정산 금액이 건당 500원씩 무작위로 어긋난다**

- 현상: 같은 주차 건인데 앱에 보인 요금과 나중에 청구된 금액이 다르다.
- 보이는 형태: 고객 문의 "31분인데 왜 1,500원?" · 회계 대사에서 500원·1,000원 차이가 건마다 들쭉날쭉(측정으로 치면 444/1,000 규모).
  - *대사(reconciliation)*: 두 장부를 나란히 놓고 건별로 맞춰 보는 일.
- 원인: 앱과 정산 서버가 `partialUnitCharged`(초과 1분을 한 단위로 세나)를 각자 코드 안 `if`로 다르게 정했다.
- 대처: 정책 값을 한 곳에서 만들어 두 시스템이 **같은 `FeePolicy`**를 쓰게 한다. "갈린 건수 = 0"을 회귀 테스트로 둔다.

**2. "하루 최대 2만 원"이라더니 3일에 8만 원**

- 현상: 장기 주차 손님 요금이 안내문으로 계산한 것보다 많다.
- 보이는 형태: 민원 "하루 2만 원이면 3일에 6만 원 아니냐" · 3일 주차 건에서 20,000원 차이가 반복된다.
- 원인: 안내문의 "하루"는 24시간으로 읽히는데 코드는 `capPerCalendarDay = true`(자정 기준)로 조각냈다 — 조각이 넷이 되어 상한이 네 번 붙는다.
- 대처: 안내문 문구와 정책 값을 **함께** 정한다. "3/1 8:00 입차 3일 주차 = 얼마"를 계약 테스트로 못 박는다(정답 6번 참고).

**3. 요금 정책을 바꾼 날, 이미 들어와 있던 차**

- 현상: 정책 배포 직후 출차 차량들의 요금이 같은 시간 주차인데도 다르다.
- 보이는 형태: 배포 시각 전후로 같은 120분 주차가 옛 정책 금액과 새 정책 금액으로 갈린다(표준 정책이면 120분 = 5,500원).
- 원인: 정책이 전역 값 하나라 "입차 시각 기준 정책"을 고를 수 없다 — README "생각해볼 것"이 던진 질문 그대로다.
- 대처: 정책에 발효 시각(버전)을 두고 입차 시각으로 고른다. 어느 시각을 기준으로 할지(입차·출차)도 정책이다(정답 8번 참고).

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 초과분이 음수인데 나눗셈 (무료 이내를 안 끊음) | 무료 → 기본 → 단위 **순서로 먼저 끊는다** — 안 끊으면 요금이 조용히 깎임 |
| 출차 < 입차를 `charge`가 조용히 0원 처리 | 루프 조건 `isBefore`라 한 바퀴도 안 돌고 0이 나온다 — `minutesParked`와 **같은 예외로 거부** (함수마다 다르게 처리하면 부르는 쪽이 어느 쪽을 믿을지 모른다) |
| 0분 주차(입차 즉시 출차) | 0원 — 루프가 한 번도 안 돌아야 한다. 조건을 `<=`로 쓰면 한 바퀴 더 돈다 |
| 딱 10분 / 딱 30분 | 10분은 무료, 30분은 1,000원 — "까지"는 포함 |
| 딱 떨어지는 초과분(40분) | 올림 판과 버림 판이 같은 값 — 이 경계만 테스트하면 갈림을 못 본다 |
| 말이 안 되는 정책(무료 > 기본, 단위 0분, 음수 요금) | `FeePolicy` 생성자에서 거부 — **계산할 때가 아니라 만들 때** 막는다 (잘못된 정책으로 계산된 값이 저장되면 되돌리기 어렵다) |

## 핵심 문장

- 요구사항의 어려움은 문장에 있는 규칙이 아니라 **문장이 안 말해주는 자리**에 있다 — 그 자리를 코드에 숨기지 말고 정책 값으로 올려라.
- 두 해석을 같은 코드로 돌려 **갈리는 건수를 재라** — 재보기 전에는 구석 사례인지 계약의 본체인지 알 수 없다 (여기서는 넷 다 절반 초과).
- "하루 최대 2만 원"은 "하루"를 정하지 않으면 아무것도 정하지 않은 문장이다 — 자정 기준과 24시간 기준이 같은 3일 주차에서 2만 원 갈린다.
- 자정 나누기는 방향이 일정하지 않아 "손님에게 유리하게"로는 결정할 수 없다 — 비즈니스 결정으로 올려야 한다.
- 상한은 갈림을 덮는다(444 → 943) — "상한이 있으니 세부는 대충"이 위험한 이유다.
- 무료·기본 구간을 **먼저** 끊지 않으면 음수 나눗셈이 요금을 조용히 깎는다 — 계산 순서 자체가 계약이다.

### 용어 풀이

- **도메인 모델링(domain modeling)**: 말로 된 업무 규칙을 타입·메서드·검증 같은 코드 구조로 번역하는 일.
- **정책(policy) 객체**: 애매하거나 바뀔 수 있는 결정을 값으로 올려 담은 객체. 여기서는 `FeePolicy` 레코드.
- **계약(contract)**: 함수·타입이 지키기로 약속한 규칙. "무료 → 기본 → 단위 순서", "뒤집힌 시각은 거부" 같은 것.
- **경계값(boundary value)**: 규칙이 바뀌는 지점의 값(딱 10분, 딱 30분). 한 칸 밀리면 전부 어긋난다.
- **상한(cap)**: 요금의 최대치. 조각(하루)마다 거는가 전체에 한 번 거는가로 답이 달라진다.
- **올림/버림(ceil/floor)**: 단위에 못 미치는 나머지를 한 단위로 세는가(올림) 버리는가(버림). `(x + n - 1) / n`이 정수 올림 관용구.
- **0 쪽으로 자름(truncation)**: 자바 정수 나눗셈의 규칙. 음수에서 "버림"과 달라져서 순서를 안 지키면 요금이 깎인다.
- **silent failure(조용한 실패)**: 예외 없이 틀린 값이 나오는 실패. 뒤집힌 시각이 0원이 되는 것, 음수 나눗셈으로 요금이 깎이는 것.
- **레코드(record)**: 자바의 값 묶음 타입. 생성자에서 검증을 걸어 "말이 안 되는 정책"을 만들 때부터 막는다.
