### A. 과제 (MeetingFinder.java 의 TODO 1~4)

#### 0. 요구사항

- 안 정해준 결정 넷: **① 이동 시간(buffer)을 둘 것인가·얼마나** **② 근무 시간의 범위** **③ 회의 시작 시각의 관례(step)** **④ 구간 경계 규약**(끝이 포함인가 미포함인가).
- 이동 시간의 효과: 있다고 보면 회의 사이의 짧은 틈이 전부 사라져 **빈 시간이 확 준다**(측정: -41%). 없다고 보면 회의가 끝나자마자 다음 회의를 넣을 수 있어 **하루가 회의로 꽉 찬다.**
- 일정에 안 적히는데 넣어야 하는 이유: **실제로 그 시간에는 다른 회의를 못 한다.** 캘린더에는 안 보이지만 현실에서는 소모되는 시간이다 — 회의 3건이면 하루에 **1.5시간**이고, 그 1.5시간은 아무 일정에도 안 나타난다.
- 근무 시간: 요구사항 문장에 **없다.** 예시 그림의 "빈 곳 09-10 … 15-18"에서만 암시된다 — 즉 **밖에서 주는 값**(`workingHours` 인자)이다.
- "빈 시간을 찾는다" ≠ "회의를 넣을 수 있다". 조각나 있으면 총합이 커도 못 넣는다. 이 챕터가 제일 강조하는 구분이다.

#### 1. TODO 1 — mergeBusy

```java
if (busy.isEmpty()) {
    return new ArrayList<>();
}
List<TimeSlot> padded = new ArrayList<>();
for (TimeSlot slot : busy) {
    padded.add(slot.padded(buffer));            // ① 여유를 먼저 붙이고
}
padded.sort(Comparator.comparing(TimeSlot::start).thenComparing(TimeSlot::end));  // ② 정렬

List<TimeSlot> merged = new ArrayList<>();
LocalDateTime start = padded.get(0).start();
LocalDateTime end = padded.get(0).end();
for (int i = 1; i < padded.size(); i++) {
    TimeSlot next = padded.get(i);
    if (!next.start().isAfter(end)) {           // 맞닿은 것(==)도 합친다
        if (next.end().isAfter(end)) {          // 끝은 max 로만 늘린다
            end = next.end();
        }
    } else {
        merged.add(new TimeSlot(start, end));
        start = next.start();
        end = next.end();
    }
}
merged.add(new TimeSlot(start, end));           // 마지막 구간을 빠뜨리지 않는다
return merged;
```

- 맞닿은 구간을 안 합치면: 사이에 **길이 0짜리 빈 구간**([12:00, 12:00))이 생긴다.
- 조용히 안 넘어가는 이유: `TimeSlot` 생성자가 **`끝이 시작보다 늦어야 한다`로 거부**해서 그 자리에서 예외가 난다. 계약을 타입에 심어두면 잘못된 값이 흘러다니지 못한다.
- [10-15] + [11-12] 에서 끝을 덮어쓰면: **[10-12]** 가 된다 — 안에 들어간 짧은 회의가 큰 회의의 끝을 **줄여버린다.**
- 그래서: `if (next.end().isAfter(end)) end = next.end();` — **max 로만 늘린다**(절대 줄이지 않는다).
- 정렬이 먼저인 이유: 참석자별 일정을 그냥 이어붙이면 순서가 뒤죽박죽이다. **정렬해야 한 번 훑기(one pass)로 합칠 수 있다.**
- 정렬 키: 시작만으로도 합치기는 되지만, **같은 시작끼리의 순서가 불안정**해진다. `.thenComparing(end)` 를 붙이면 결과가 입력 순서와 완전히 무관해진다(테스트 `orderIndependent`).
- 여유를 **먼저** 붙이고 합친다. 합친 뒤 붙이면 이미 하나가 된 덩어리에만 여유가 붙어, 원래 회의 사이에 있던 틈을 못 없앤다.
- [10-11] + [11:15-12] · 15분 여유:

```text
  여유 없음        [10:00-11:00)  [11:15-12:00)        두 구간
  여유 15분 붙임   [09:45-11:15)  [11:00-12:15)        겹친다!
  합치면           [09:45-12:15)                        한 구간
```

  → **사이 15분 틈이 사라진다.** 그것이 이동 시간의 뜻이다.

- 빈 목록: **빈 목록**(새 `ArrayList`)을 반환한다. `padded.get(0)` 을 하기 전에 걸러야 터지지 않는다.

#### 2. TODO 2 — freeSlots

```java
List<TimeSlot> merged = mergeBusy(busy, buffer);
List<TimeSlot> free = new ArrayList<>();
LocalDateTime cursor = workingHours.start();

for (TimeSlot slot : merged) {
    if (!slot.end().isAfter(cursor)) {
        continue;                                   // ① 커서보다 앞에서 끝난 회의는 건너뛴다
    }
    if (!slot.start().isBefore(workingHours.end())) {
        break;                                      // ② 근무 종료 후에 시작한 회의에서 멈춘다
    }
    if (slot.start().isAfter(cursor)) {
        free.add(new TimeSlot(cursor, slot.start()));   // 사이가 비었으면 줍는다
    }
    cursor = slot.end();
}
if (cursor.isBefore(workingHours.end())) {
    free.add(new TimeSlot(cursor, workingHours.end()));  // ③ 마지막 꼬리
}
return free;
```

- 커서 절차: **커서를 근무 시작에 둔다 → 합쳐진 바쁜 구간을 순서대로 본다 → 커서와 그 구간 시작 사이가 비었으면 빈 구간으로 줍는다 → 커서를 그 구간의 끝으로 옮긴다 → 다 돌면 커서~근무 종료를 마지막 빈 구간으로 줍는다.**
- 07-08 회의를 안 건너뛰면: 커서가 09:00 에서 **08:00 으로 뒤로 간다** → 결과가 **[8-18]** 이 되어 근무 시작 전 시간이 빈 시간으로 보고된다.
- 19-20 회의에서 안 멈추면: 커서가 18:00 을 지나 **[18-19] 라는 근무 시간 밖 빈 구간**이 생긴다.
- 가장 조용한 이유: 근무 시간 밖에 **완전히** 있는 회의는 "관계없는 데이터"처럼 보여 테스트 데이터에 잘 안 들어간다. 그런데 실제로는 아침 운동·저녁 약속 등으로 흔하다 — **흔한데 시험에는 없는** 입력이다.
- 걸쳐 있는 회의(08-10, 17-20)만으로는 안 드러나는 이유: 08-10 은 끝(10:00)이 커서(09:00)보다 **뒤**라 ① 조건에 안 걸리고, 17-20 은 시작(17:00)이 근무 종료(18:00)보다 **앞**이라 ② 조건에 안 걸린다. 두 방어 어느 쪽도 실행되지 않으므로 지워도 통과한다.
- 마지막 꼬리: `cursor.isBefore(workingHours.end())` 일 때만 넣는다 — 같으면 길이 0이라 `TimeSlot` 이 거부하고, 지나쳤으면(클립 안 한 경우) 역구간이 된다.
- 바쁜 일정 없음 → **[9-18] 하나**(merged 가 비어서 루프를 안 돌고 꼬리만 나온다).
- 통째로 참(09-18) → **빈 목록**(커서가 18:00 이 되어 꼬리 조건이 거짓).

List<LocalDateTime> starts = new ArrayList<>();

- [9-10] · 30분 · step 15분:

```text
  09:00 ~ 09:30   된다
  09:15 ~ 09:45   된다
  09:30 ~ 10:00   된다   ← 끝이 딱 맞는다. 포함이다
  09:45 ~ 10:15   구간을 넘는다. 안 된다

  후보 3개: 09:00, 09:15, 09:30
```

- 09:45 가 빠지는 이유: 회의 끝(10:15)이 **빈 구간의 끝(10:00)을 넘는다.**
- 종료 조건을 `!isAfter` 로 쓰는 이유: 끝이 **정확히 같은 경우(09:30~10:00)는 들어가야** 하기 때문이다. `isBefore` 로 쓰면 딱 맞는 마지막 후보를 잃는다 — 경계 하나가 후보 하나를 먹는다.
- 길이 0·음수: `IllegalArgumentException`. 안 막으면 `while` 조건이 항상 참이라 **무한 루프**가 된다.
- 45분인데 30분을 못 넣는 이유: 45분이 **15분씩 세 조각**이기 때문이다. 합계는 조각의 길이를 말해주지 않는다.
- `step` 을 5분으로 줄여도 **"넣을 수 있나"는 안 바뀐다.** 넣을 수 있는 구간은 빈 구간의 길이가 정하지 step 이 정하지 않는다.
- `step` 이 정하는 것: **회의 시작 시각의 관례.** 5분 단위로 시작하는 회의를 만들 것인지의 문제다 — 정밀도가 아니라 문화다.

### B. 개념

#### 5. 측정이 알려준 것

- 참석자 3명·각 3건·500일:

| | 빈 시간 합계 | 1시간 회의 후보 |
|---|---|---|
| 여유 없음 | 142,110분 | 3,731 |
| 여유 15분 | **84,285분** | **2,091** |

  → 빈 시간 **-41%**, 후보 **-44%**.

- **500/500** 에서 값이 갈린다 — 한 번도 같지 않다.
- 회의 3건 × 앞뒤 15분 = **하루 1.5시간.**
- 무서운 이유: **그 1.5시간은 아무 일정에도 안 나타난다.** 캘린더는 비어 보이는데 실제로는 못 쓴다 — 보이지 않는 소모라 아무도 예산에 안 잡는다.
- 참석자 수:

| 참석자 | 평균 빈 시간 | 1시간 회의 후보 | 후보 없는 날 |
|---|---|---|---|
| 1 | 438분 | 20 | 0 / 200 |
| 2 | 355분 | 12 | 0 / 200 |
| 3 | 292분 | 7 | 0 / 200 |
| 5 | 194분 | 2 | 38 / 200 |
| 8 | 107분 | **0** | **125 / 200** |
| 12 | 49분 | 0 | 189 / 200 |

- 절벽이 되는 이유: 빈 시간은 438 → 49 로 **대략 선형**인데 후보는 20 → 12 → 7 → 2 → 0 → 0. **참석자가 늘면 빈 시간이 줄기만 하는 게 아니라 쪼개진다.** 회의를 넣으려면 "연속된 60분"이 필요한데, 쪼개짐은 총량보다 훨씬 빨리 그것을 파괴한다.
- 8명: 하루 107분이 남지만 조각나 있어 **62%(125/200)의 날에** 1시간 회의를 못 잡는다.
- 그림:

```text
  09:00     09:15 ...... 10:00     10:15 ...... 11:00     11:15 ...... 12:00
  [ 15분 )  [## 45분 ##)  [ 15분 )  [## 45분 ##)  [ 15분 )  [## 45분 ##)
   비었음      바쁨        비었음      바쁨        비었음      바쁨

  총 빈 시간   45 분  (15 + 15 + 15)
  30 분 회의    0 개  (가장 긴 조각이 15분)
  15 분 회의    3 개
```

- `step` 표 (빈 구간 [9-10] · 30분 회의): step 30분 → **2개**, 15분 → **3개**, 5분 → **7개.** "넣을 수 있나"는 셋 다 예 — 바뀌는 것은 후보 개수뿐이다.

#### 6. 변종 검증에서 고친 것

- 겹치는 방어 둘: **①앞선(이미 끝난) 구간을 건너뛰는 것** 과 **②커서가 뒤로 안 가게 막는 것**(`cursor = max(cursor, slot.end())` 류).
- 하나만 지워도 안 깨진 이유: **서로를 덮고 있었다.** ①이 있으면 커서가 뒤로 갈 일이 없고, ②가 있으면 ①을 지워도 결과가 같다. 어느 쪽을 지워도 다른 쪽이 메운다 — 06번의 `Math.max(0, days)` 와 **똑같은 구조.**
- **뒤의 것(②)을 지우고 앞의 것(①)을 남겼다.** 그리고 impl 주석에 "위에서 이미 끝난 구간을 건너뛰었으므로 여기서는 커서가 반드시 앞으로 간다"고 근거를 남겼다.
- 더한 테스트: **근무 시간 밖에 완전히 있는 회의**(07-08, 19-20)를 넣는 테스트. 이제 ①을 지우면 잡힌다.
- 06번과 같은 교훈: **같은 불변식을 두 곳에서 지키면 한쪽이 죽어도 안 드러난다.** 방어는 도달 가능한 곳에 한 번만 두고, 그 하나를 테스트가 실제로 때리게 만든다.

> 원본 README가 답을 주지 않고 던진 질문 — (원본에 근거 없음 — 내 추론) 표시.

- 근무 시간이 다르면: (내 추론) 공통 근무 시간 = **모든 참석자 근무 시간의 교집합.** 시차가 크면 교집합이 아예 비어 후보가 0이 된다 — 그때 "공통 근무 시간"이라는 개념 자체를 포기하고 "몇 명이 무리하나"를 세는 쪽으로 문제를 바꿔야 한다. 구현상으로는 `workingHours` 를 하나가 아니라 목록으로 받아 교집합을 먼저 구하는 단계가 앞에 붙는다.
- 필수/선택 참석자: (내 추론) **필수만으로 freeSlots 를 구하고, 후보마다 선택 참석자 중 몇 명이 되는지를 점수로 매긴다.** 답이 "된다/안 된다"에서 "몇 점짜리 후보"로 바뀌는 것 — 반환 타입이 `List<LocalDateTime>` 에서 `List<후보+점수>` 가 된다.
- 후보가 없을 때: (내 추론) 세 갈래 — ① 가장 적게 겹치는 시간(누구 몇 명이 빠지는지 명시) ② 다음날 ③ 회의 길이를 줄인 후보(60분이 없으면 30분). 측정이 말해주는 것은 8명 이상이면 이 상황이 **기본값**이라는 것이므로, "후보 없음"은 예외가 아니라 정상 응답으로 설계해야 한다.
- 회의실: (내 추론) **거의 같다** — 회의실의 예약 일정을 참석자 하나의 busy 목록처럼 넣으면 그대로 동작한다. 다른 점은 회의실은 **대체 가능**(A방이 안 되면 B방)이라는 것 — 참석자는 대체가 안 된다. 그래서 회의실은 "AND 하나 더"가 아니라 "OR 여러 개"라, 방마다 따로 후보를 구해 합집합을 취해야 한다.

#### 8. 연결

- **시작 포함·끝 미포함**: 04번 숙박의 **체크아웃 날**, 06번 정기권의 **해지일**과 같은 규약이다. 10:00~11:00 회의는 11:00 에 방을 안 쓰므로 11:00~12:00 회의와 안 겹친다. 도메인이 달라도 **같은 결정이 반복된다.**
- 안에 들어간 구간이 끝을 줄이는 실수: **10번 누적 합**, **30번 스위핑**에서 본 것과 같다(테스트 주석 근거). 구간을 합치는 모든 곳에 있는 함정.
- **07번 알림과의 비교**: 07은 **단계의 순서**(중복 제거 → 조용 시간)가 결과를 바꿨고, 08은 **한 함수 안의 순서**(여유 붙이기 → 정렬 → 합치기)가 결과를 바꾼다. 같은 점은 "앞 단계가 뒤 단계의 판정 기준(시각·경계)을 바꾼다"는 것이고, 다른 점은 07은 **건수가 줄어드는** 사고고 08은 **구간이 잘못 합쳐지는** 사고라는 것이다.
