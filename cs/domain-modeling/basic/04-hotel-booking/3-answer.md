### A. 과제

#### 0. 그림 한 장이 안 말해주는 것

- 답이 둘인 이유: **청소가 끝나야 들어올 수 있으면 겹치는 것**이고, **오전 퇴실 오후 입실이면 안 겹치는 것**이다.\
  둘 다 말이 된다.
- 올라간 자리: **`sameDayTurnover` 라는 boolean 파라미터** — 모든 함수가 이 값을 받아서 두 해석을 같은 코드로 돌린다.
- 3/1 ~ 3/3: **날짜는 셋(3/1, 3/2, 3/3), 숙박은 2박.**
- 다른 이유: **체크아웃 날은 방을 안 쓰는 날**이기 때문이다.\
  자는 밤을 세면 3/1밤·3/2밤 둘이다.

```text
  3/1  3/2  3/3
  [-----------)
   1박  2박   나간다
```

- 체크아웃 날: **안 쓴다**(반열린 구간의 닫힌 끝).
- 0박·뒤집힌 날짜: **`Stay` 생성자에서 막는다** — 만들 때 거부하지 계산할 때 거부하지 않는다.

#### 1. Stay 의 계약

- `nights()` 가 epochDay 차인 이유: **박 수 = 끝 − 시작** 이 정의 그대로다.\
  날짜를 세어서 1을 빼는 방식은 "몇 개를 셌는지"를 한 번 더 거치므로 **오프바이원이 끼어들 자리**가 생긴다.

> **오프바이원(off-by-one)** — 경계를 한 칸 잘못 세서 생기는 흔한 실수.\
> 예: 3/1~3/3 숙박을 "날짜 세 개"로 세고 1을 빼는 대신 그냥 세 개로 두면 2박이 3박이 된다.

- `occupies` 의 두 부등호:

```text
 !date.isBefore(checkIn)   →  date >= checkIn   체크인 날은 포함 (닫힌 시작)
 date.isBefore(checkOut)   →  date <  checkOut  체크아웃 날은 제외 (열린 끝)
```

- 반열린 구간 `[checkIn, checkOut)`: **시작은 포함하고 끝은 포함하지 않는 구간.**\
  이렇게 하면 이어 붙는 구간(`[1,3)` 과 `[3,5)`)이 **겹치지 않고 정확히 맞닿는다.**\
  경계가 두 번 세어지지 않는다.

> **반열린 구간(half-open interval)** — 한쪽 끝은 포함하고 반대쪽 끝은 빼는 구간. 보통 `[시작, 끝)` 으로 쓴다.\
> 예: 3/1~3/3 숙박은 3/1·3/2 는 방을 쓰고 3/3 은 안 쓴다. 그래서 3/3 부터 시작하는 다음 예약과 딱 맞닿기만 한다.

- 0박 허용하면: **아무 데도 안 겹치는데 목록에는 있는 유령 예약**이 생긴다.\
  객실을 차지하지도 않으면서 예약 건수에는 잡힌다.
- `Stay` 에 둔 이유: **잘못된 예약을 애초에 만들 수 없게** 하기 위해서다.\
  `Bookings` 에서 막으면, 검사를 안 거치는 다른 경로로 유령 예약이 들어온다.\
  (README의 변종 검증에서 이 계약 클래스의 검증을 손으로 확인해야 했던 이유이기도 하다.)

> **불변식(invariant)** — 그 값이 존재하는 한 항상 참이어야 하는 조건.\
> 예: "숙박은 1박 이상이다"는 `Stay` 의 불변식이라, 0박짜리 `Stay` 는 아예 만들어지지 않게 생성자에서 막는다.

#### 2. TODO 1 — overlaps

정답 코드 (impl/Bookings.java):

```java
if (sameDayTurnover) {
    return a.checkIn().isBefore(b.checkOut()) && b.checkIn().isBefore(a.checkOut());
}
// 하루를 비워야 하면 경계를 하루씩 넓혀서 본다.
return !a.checkIn().isAfter(b.checkOut()) && !b.checkIn().isAfter(a.checkOut());
```

- true 일 때의 식: **`a.in < b.out && b.in < a.out`**.
- 표준 공식인 이유: 반열린 구간 둘이 겹치려면 **각자의 시작이 상대의 끝보다 앞**이어야 한다.\
  한쪽이라도 상대의 끝 이후에 시작하면 안 겹친다.
- false 일 때: 부등호를 **`<` 에서 `<=` 로** 바꾼다(`!isAfter` = `<=`).
- "경계를 하루씩 넓힌다"의 실현: `<=` 로 바꾸면 **끝 날짜까지 포함하는 닫힌 구간 `[in, out]`** 으로 보는 것과 같다 — 3/3에 끝나는 예약이 3/3에 시작하는 예약과 맞닿기만 해도 겹침이 된다.
- 대칭: **같은 판정이 a,b 순서를 바꿔도 나와야 한다.**\
  두 식 모두 `A조건 && B조건` 이 서로 대칭 짝이라 순서를 바꿔도 항이 자리만 바꾼다 — 대칭이다.

> **대칭(symmetry)** — 두 인자의 자리를 바꿔 넣어도 결과가 같아야 한다는 성질.\
> 예: "A가 B와 겹치나"와 "B가 A와 겹치나"는 같은 질문이므로, 답이 다르게 나오면 그 자체가 결함이다.

- A(3/1~3/5) 기준 손계산:

```text
 B 3/2~3/3   안에 들어감   겹친다   (두 규칙 모두)
 B 3/4~3/7   뒤로 걸침     겹친다   (두 규칙 모두)
 B 3/7~3/9   완전히 뒤     안 겹친다 (b.in 3/7 > a.out 3/5)
 B 2/24~2/27 완전히 앞     안 겹친다
 B 3/5~3/7   맞닿음        같은 날 교체: 안 겹친다 / 하루 비우기: 겹친다   ← 여기가 갈림
```

#### 4. TODO 3 — peakOccupancy

정답 코드:

```java
if (stays.isEmpty()) {
    return 0;
}
List<long[]> events = new ArrayList<>();
for (Stay stay : stays) {
    events.add(new long[] {stay.checkIn().toEpochDay(), +1});
    events.add(new long[] {stay.checkOut().toEpochDay(), -1});
}
events.sort((x, y) -> {
    if (x[0] != y[0]) {
        return Long.compare(x[0], y[0]);
    }
    // 퇴실 먼저면 그날 방이 비워지고, 입실 먼저면 하루를 비우는 셈이 된다.
    return sameDayTurnover ? Long.compare(x[1], y[1]) : Long.compare(y[1], x[1]);
});

int active = 0;
int peak = 0;
for (long[] event : events) {
    active += (int) event[1];
    peak = Math.max(peak, active);
}
return peak;
```

- 이벤트 둘: **체크인 = +1**, **체크아웃 = −1**.

> **스위핑(sweeping, 훑기)** — 구간 전체를 보지 않고, 값이 바뀌는 **경계에만** 표시를 남겨 한 번 훑는 방법.\
> 예: 1년짜리 숙박도 "시작 +1, 끝 −1" 두 점이면 끝난다. 365칸을 다 돌 필요가 없다.

> **최대 동시 사용(peak occupancy)** — 전 기간을 통틀어 "한순간에 동시에 쓰이는 방의 수"가 가장 컸을 때의 값.\
> 예: 예약이 스무 건이어도 겹치는 순간이 최대 셋이면 객실 3개로 전부 받을 수 있다.

- 같은 날짜: **체크아웃(−1)을 먼저** 처리해야 그날 퇴실한 방을 다시 팔 수 있다 = 같은 날 교체 허용.
- 입실을 먼저 처리하면: 그 순간 두 예약이 동시에 세어져 **하루를 비우는 셈**이 된다.\
  필요한 객실이 하나 더 나온다.
- 비교자 표현: 변화량으로 정렬하는데 **−1 < +1** 이므로

```text
 sameDayTurnover = true   Long.compare(x[1], y[1])   오름차순 → -1 먼저 (퇴실 먼저)
 sameDayTurnover = false  Long.compare(y[1], x[1])   내림차순 → +1 먼저 (입실 먼저)
```

- 빈 목록: **0**.
- 비용: **예약 수 × log(예약 수)**(정렬) — 기간 길이와 무관하다.
- 1년 장기 숙박 한 건:

```text
 날짜별  365 칸을 돈다 (지도 크기도 365)
 이벤트    2 칸 (체크인 +1, 체크아웃 -1) → peak = 1
```

> 예: "받을 수 있나"만 물었는데 그 함수가 내 예약 목록에 후보를 끼워 넣어 두면, 묻기만 했는데 자료가 바뀐다.

- 객실 1개, A(3/1~3/3), B(3/3~3/5):

```text

 하루 비우기         3/3 에 입실을 먼저 처리 → peak = 2 > 1   못 받는다

 객실이 2개면 하루 비우기에서도 받는다.
```

#### 6. overlappingPairs — 대조용

- 차이: `overlappingPairs` 는 **서로 겹치는 예약 쌍의 개수**를 세고, `peakOccupancy` 는 **어느 한 순간에 동시에 쓰이는 객실 수**를 센다.\

- 손계산:

```text
 서로 겹치는 3 건   쌍 = AB, AC, BC        = 3     필요한 객실 = 3

```

- 증가 속도: 쌍은 **n(n−1)/2 — 대략 제곱**으로, 필요한 객실은 **n — 선형**으로 는다.

### B. 개념

#### 7. 측정 — 교체 규칙의 값

- 12건씩 1,000회·20일 범위: 최대 동시 사용이 다른 경우 **658/1,000**.
- 합계: **같은 날 교체 허용 3,725 / 하루 비우기 4,474** — **20퍼센트** 차이.
- 현실에서의 뜻: **객실을 20퍼센트 더 지어야 한다**는 뜻이다.\
  **"청소 때문에 그날은 못 받습니다" 한 마디가 그만큼**이다.
- 예약 수락 여부(객실 4개): **355/1,000** 이 갈린다 — 세 건 중 한 건.
- "방향이 한쪽뿐": **하루를 비우는 쪽이 거절하는 건은 같은 날 교체를 허용하는 쪽이 전부 받는다. 반대는 한 건도 없다**(355건 전부 그 방향).\
  그럴 수밖에 없는 이유는 **하루 비우기 판정이 같은 날 교체 판정보다 항상 크거나 같기** 때문이다 — 경계를 넓혔으니 겹침이 줄어들 수는 없다.

> **한 방향으로만 갈린다(단방향 차이)** — 두 규칙의 결과가 다를 때, 늘 정해진 한쪽만 더 엄격한 관계.\
> 예: 하루를 비우는 규칙은 같은 날 교체 규칙이 받는 예약을 거절할 수는 있어도, 그쪽이 거절한 예약을 받아줄 수는 없다.

#### 8. 측정 — 쌍의 수 vs 객실 수

- 1,000회 중 같았던 적: **0번**(1,000/1,000 이 다르다).
- 쓸모없는 보고인 이유: **"겹치는 예약이 6건 있습니다"는 객실이 몇 개 필요한지 안 말해준다.**\
  6쌍은 서로 겹치는 4건일 수도 있고, 다른 배치일 수도 있다.\
  쌍의 수에서 객실 수를 되돌릴 수 없다.
- 그런데도 자주 만드는 이유: **쌍을 세는 것이 훨씬 쓰기 쉽다**(이중 루프 한 번이면 끝난다).\
  쉬운 쪽이 답을 주지 않는데도, 쉬워서 만들어진다.

> **대리 지표(proxy metric)** — 진짜 알고 싶은 값 대신, 재기 쉬워서 쓰는 다른 값.\
> 예: "겹치는 예약 쌍 수"는 세기 쉽지만, 정작 궁금한 "객실이 몇 개 필요한가"에는 답하지 못한다.

#### 9. 측정 — 두 세는 방법

- 500회에서 어긋난 적: **0회**.
- 둘 다 만든 이유: **원리가 다른 두 방법이 같은 답을 내는지 대조**하기 위해서다.\
  한쪽이 틀렸으면 여기서 드러난다(서로가 서로의 검산이다).

> **교차 검산(cross-check)** — 원리가 다른 두 방법으로 같은 값을 구해, 답이 맞는지 서로 대조하는 것.\
> 예: 날짜를 하나씩 세는 방법과 경계만 훑는 방법이 500회 내내 같은 답을 내면, 둘 다 틀렸을 가능성은 크게 줄어든다.

- 비용: 날짜별 = **예약 수 × 숙박 일수**, 이벤트 = **예약 수 × log(예약 수)**.
- 같은 구조의 주제: **30번 스위핑** — **볼 곳이 값의 범위가 아니라 경계의 개수**다.

#### 10. 변종 검증에서 배운 것

- 둘이 있던 곳: `impl/` 이 아니라 **주어진 계약 클래스 `Stay`** 였다(0박 검증, `occupies` 의 경계) — 그래서 손으로 확인해야 했다.
- 건너뛰면: **주어진 코드라고 검증을 건너뛰면 그 부분만 안 지켜진다.**\
  "계약이라 다 준다"는 말이 "그 부분은 틀릴 수 없다"는 뜻이 아니다.

> **변종 검증(mutation testing)** — 코드의 한 줄을 일부러 망가뜨리거나 지우고, 테스트가 그것을 잡는지 보는 것.\
> 예: `Stay` 의 0박 금지 검사를 지웠는데도 전부 통과한다면, 그 검사는 어느 테스트도 보고 있지 않다는 뜻이다.

#### 11. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 방 등급: 지금 `peakOccupancy` 는 **방을 구별하지 않고 개수만 센다.**\
  등급이 생기면 최소한 **등급별로 따로 세야** 하고, "상위 등급으로 대체 가능(업그레이드)"까지 허용하면 단순 카운트로는 안 되고 **매칭 문제**가 된다(어느 예약을 어느 등급에 넣느냐가 답을 바꾼다).\
  즉 등급 대체를 허용하는 순간 이 챕터의 스위핑이 안 통한다. (원본에 답 없음 — 내 추론)
- 취소 후 즉시 재판매: 02번 좌석과 **완전히 같은 질문**이다.\
  결제 취소가 진행 중이면 되돌아올 수 있으므로 "해제됨"과 "판매 가능" 사이에 중간 상태가 필요하다.\
  지금 모델에는 상태가 아예 없고 **목록에서 빼는 것이 곧 취소**다. (원본에 답 없음 — 내 추론)
- 최소 숙박일: **`Stay` 가 아니라 `Bookings`(또는 그 위)** 가 맞다.\
  `Stay` 의 불변식은 "숙박 한 건이 말이 되나"(0박 금지)이고, "성수기 2박 이상"은 **날짜에 따라 바뀌는 정책**이라 같은 `Stay` 가 성수기엔 거부되고 비수기엔 허용된다 — 값 자체의 불변식이 아니다.\
  불변식과 정책을 같은 자리에 두면 정책이 바뀔 때 과거 데이터가 만들어질 수 없게 된다. (원본에 답 없음 — 내 추론)
- 시각까지 다루면: 세는 단위가 **"하루"에서 "시점(instant)"으로** 바뀐다.\
  이벤트 방식은 거의 그대로다 — epochDay 대신 시각으로 정렬하면 된다(경계의 개수는 그대로 2n).\
  반면 **날짜별 세기는 못 쓴다**(칸이 무한히 잘게 쪼개진다).\
  그리고 `sameDayTurnover` 라는 boolean 은 **"청소에 몇 시간"이라는 기간 값**으로 바뀐다 — 참/거짓이 아니라 숫자가 된다. (원본에 답 없음 — 내 추론)

#### 12. 연결

- 01번과 같은 자리: **"경계를 포함하나"** 가 답을 가른다.\
  01번은 "10분까지"의 10분, 04번은 체크아웃 날 — 둘 다 **끝점 하나가 금액·객실 수를 정한다.**
- 02번의 `Preference` 에 해당하는 값: **`sameDayTurnover`.**\
  어느 쪽으로 정해도 코드가 돌고 에러도 안 나는데, 그 선택이 **필요한 객실 20퍼센트**를 정한다.
- "무엇을 세느냐"의 이어짐: 02번은 **남은 좌석 수 vs 고아 좌석 수**, 04번은 **겹치는 쌍 수 vs 필요한 객실 수** — 둘 다 **세기 쉬운 값이 묻고 싶은 질문에 답하지 않는다.**
