### A. 과제 (Coupon.java 의 TODO 1~4)

#### 0. 요구사항 — 진짜 어려운 것은 따로 있다

- 조건 다섯: **① 최소 금액**(minAmount), **② 허용 카테고리**(allowedCategories), **③ 사용 기간**(startsOn~endsOn), **④ 최소 등급**(minGrade), **⑤ 중복 사용 가능 여부**(stackable).
- 진짜 문제: **"못 쓴다"를 어떻게 알려주느냐.**\
  판정은 `if` 다섯 줄이면 끝난다.\
  그 결과를 손님에게 어떻게 전달하느냐가 이 도메인의 전부다.
- `boolean` 이면 안 되는 이유: **화면이 "왜 안 되는지"를 말할 수 없다.**\
  false 하나로는 "3만원을 더 담으면 되는지"와 "기간이 끝나 아무것도 못 하는지"를 구별할 방법이 없다.

> **검증(validation)** — 조건을 확인해 통과/실패와 그 이유를 내는 일.\
> 예: 쿠폰의 조건 다섯을 확인해 "쓸 수 있음" 또는 "금액 미달·카테고리 불일치"를 돌려준다.

> **사유(Reason)** — 못 쓰는 이유마다 붙인 이름. 여기서는 enum 6종이다.\
> 예: `MIN_AMOUNT`, `CATEGORY`, `EXPIRED` 처럼 이름이 있으면 화면 문구도, 고칠 수 있음 여부도 그 이름에 매달 수 있다.

- enum 이름을 붙이면: **표시 문구·고칠 수 있음 여부·정렬 우선순위를 그 이름에 매달 수 있다.**\
  실제로 `Reason.isFixableByCustomer()` 가 그렇게 붙어 있다.
- 두 방식의 거래:

```text
 첫 사유만   싸다(조건 하나만 평가해도 된다)   손님이 고치면 다음 사유가 나온다 → 두더지 잡기
 전부        한 번에 다 고칠 수 있다           조건을 전부 평가해야 한다
```

- 안 들어 있는 결정 셋: **① 사유를 하나 줄 것인가 전부 줄 것인가**, **② 전부 준다면 어떤 순서로 줄 것인가**, **③ 손님이 못 고치는 사유가 섞였을 때 고칠 수 있는 것도 보여줄 것인가.**

#### 1. TODO 1 — reasonsAgainst

```java
public List<Reason> reasonsAgainst(Order order) {
    List<Reason> reasons = new ArrayList<>();
    if (order.orderedOn().isBefore(startsOn)) {           // ① 기간 — 못 고침
        reasons.add(Reason.NOT_STARTED);
    }
    if (!order.orderedOn().isBefore(endsOn)) {            // ② 기간 — 못 고침
        reasons.add(Reason.EXPIRED);
    }
    if (order.memberGrade() < minGrade) {                 // ③ 등급 — 당장은 못 고침
        reasons.add(Reason.GRADE);
    }
    if (order.amount() < minAmount) {                     // ④ 금액 — 고칠 수 있음
        reasons.add(Reason.MIN_AMOUNT);
    }
    if (!allowedCategories.isEmpty()                      // ⑤ 카테고리 — 고칠 수 있음
            && order.categories().stream().noneMatch(allowedCategories::contains)) {
        reasons.add(Reason.CATEGORY);
    }
    if (order.alreadyUsedCoupon() && !stackable) {        // ⑥ 중복 — 고칠 수 있음
        reasons.add(Reason.ALREADY_USED);
    }
    return reasons;
}
```

- 순서: **NOT_STARTED → EXPIRED → GRADE → MIN_AMOUNT → CATEGORY → ALREADY_USED.**\
  앞의 셋이 못 고치는 것, 뒤의 셋이 고칠 수 있는 것이다.
- 근거 측정값: **못 쓰는 주문 9,461건 중 7,735건이 아예 고칠 수 없다**(README 82%, 테스트 정수 81).\
  열에 여덟은 장바구니를 아무리 손봐도 안 된다.\
  그런데 고칠 수 있는 사유를 먼저 보여주면 그 여덟은 헛수고를 한다.
- "순서가 계약"이 가리키는 곳: **`reasons.add(...)` 를 쓴 코드의 줄 순서** 그 자체다.\
  이 줄들을 재배열하면 화면에 먼저 뜨는 문구가 바뀐다.\
  리팩토링으로 줄을 옮기는 것이 UX 변경이 된다.

> **계약(contract)** — 함수가 바깥에 약속한 동작. 지키지 않으면 부르는 쪽이 깨진다.\
> 예: "사유 목록의 첫 항목이 가장 먼저 보여줄 것"이 계약이면, 줄 순서를 바꾸는 순간 그 약속이 깨진다.

- 기간이 둘로 갈린 이유: **손님에게 하는 말이 다르다.**\
  "아직 시작 전입니다(3월 1일부터)"는 **기다리면 되는 것**이다.\
  "기간이 끝났습니다"는 **영영 안 되는 것**이다.\
  하나로 뭉쳐 `PERIOD` 라고 하면 그 차이가 사라진다.
- 최소 금액: **`order.amount() < minAmount` 일 때만 사유.**\
  즉 **"이상"(≥)이라 경계 포함** — 딱 30,000원은 통과한다.\
  초과로 쓰면 **딱 3만원인 손님이 못 쓰는데, 그 손님이 가장 많다**(3만원에 맞춰 담기 때문).

```text
 minAmount = 30,000

    29,999  →  [MIN_AMOUNT]
    30,000  →  통과          ← 여기 사람이 제일 많이 몰린다
```

> **경계 포함(inclusive bound)** — 구간의 끝 값을 구간 안에 넣는 것. "이상(≥)"이 여기 해당한다.\
> 예: "3만원 이상"에서 정확히 30,000원은 통과한다. "초과(>)"로 읽으면 30,000원이 탈락한다.

- 종료일: **`!orderedOn.isBefore(endsOn)` 이면 EXPIRED** — 즉 `orderedOn >= endsOn` 이면 끝이다.\
  endsOn 그 날에는 이미 못 쓴다.

```text
 3/1 ~ 4/1 쿠폰

    2/28  NOT_STARTED   시작일 전
    3/ 1  통과          시작일 포함
    3/31  통과
    4/ 1  EXPIRED       종료일 미포함
```

> **미포함 경계(exclusive bound)** — 구간의 끝 값을 구간 밖으로 두는 것.\
> 예: 종료일이 4/1 이면 3/31 까지 쓸 수 있고 4/1 에는 못 쓴다. "4월 1일까지"라고 안내하려면 endsOn 을 4/2 로 넣어야 한다.

- `isEmpty()` 를 먼저 보는 이유: **빈 집합은 "제한 없음"** 이기 때문이다.\
  비어 있으면 카테고리 검사 자체를 건너뛴다.

> **빈 집합 = 제한 없음** — 허용 목록이 비어 있으면 "아무것도 허용 안 함"이 아니라 "전부 허용"으로 읽는 관습.\
> 예: 전 상품 쿠폰은 허용 카테고리를 굳이 다 적지 않고 빈 집합으로 둔다. 반대로 읽으면 이 쿠폰이 아무 데도 안 먹는다.

- 빈 집합을 "아무것도 안 됨"으로 읽으면: **전 상품 쿠폰이 아무 데도 못 쓰인다.**\
  그리고 **그 쿠폰이 가장 많이 발행된다** — 즉 가장 많은 쿠폰이 전부 죽는다.
- 카테고리는 **`noneMatch` 일 때만 사유** = **하나만 걸리면 통과**다.\
  `allMatch` 로 읽으면 **장바구니에 대상 아닌 상품이 하나만 섞여도 못 쓴다.**

```text
 허용 {food, drink}

    [food]         통과
    [food, book]   통과      ← any-match. all-match 로 읽으면 여기서 막힌다
    [book]         CATEGORY
```

> **하나만 걸리면 됨(any-match)** — 여러 항목 중 하나라도 조건에 맞으면 통과로 보는 규칙.\
> 예: 장바구니에 food 와 book 이 있고 허용이 {food, drink} 면 통과한다. 전부 해당(all-match)으로 읽으면 book 때문에 탈락한다.

- 중복 사유 조건: **이미 다른 쿠폰을 썼고(`alreadyUsedCoupon`) 이 쿠폰이 중복 불가(`!stackable`)** — 둘 다여야 한다.

> **stackable(중복 사용 가능)** — 다른 쿠폰과 같이 쓸 수 있는가를 가리키는 성질.\
> 예: 배송비 쿠폰은 보통 stackable 이라 할인 쿠폰과 함께 쓰이지만, 대형 할인 쿠폰은 대개 불가다.

- 바로 return 하지 않는 이유: **전부 모으는 것이 이 함수의 목적**이다.\
  첫 사유에서 멈추면 "한 번에 다 고칠 수 있다"는 이점이 사라진다.\
  그리고 `actionableReasons` 도 못 고치는 사유가 뒤에 숨어 있는지 알 수 없다.

#### 3. TODO 3 — firstReason

```java
public Reason firstReason(Order order) {
    List<Reason> reasons = reasonsAgainst(order);
    return reasons.isEmpty() ? null : reasons.get(0);
}
```

- 두 방식의 차이: **"전부 평가하고 첫 것만 주기"는 조건 여섯을 다 돌린 뒤 목록의 0번을 꺼낸다.**\
  **"첫 것을 만나면 멈추기"는 사유를 발견하는 순간 return 한다.**
- 돌려주는 값은 **같다.**\
  순서가 같으니 첫 사유도 같다.
- 그런데 중요한 이유: **비용과 부수 효과가 다르다.**\
  조건 평가가 외부 조회(등급 서버, 재고 API)라면 전자는 매번 여섯 번 호출하고 후자는 평균 한두 번이다.\
  값이 같다고 같은 코드가 아니다 — **테스트로는 구별이 안 되는 차이**라서 더 위험하다.

> **단축 평가(short-circuit)** — 답이 확정되는 순간 나머지 조건을 아예 평가하지 않고 멈추는 것.\
> 예: 자바의 `a && b` 는 a 가 false 면 b 를 계산조차 안 한다. b 가 외부 API 호출이면 호출 자체가 안 일어난다.

- 전부 평가하기로 한 근거: **조건이 싸다.**\
  전부 메모리 안의 비교 연산이라 여섯 번을 다 돌려도 공짜에 가깝다.\
  대신 `reasonsAgainst` 하나만 만들면 나머지 셋이 다 여기서 파생된다.
- 비싸지면: **순서가 비용 순으로 재편된다** — 싼 조건부터 평가하고 걸리면 멈춘다.\
  그런데 그러면 **"못 고치는 것을 앞에"라는 UX 순서와 충돌**한다.\
  해법은 (내 추론) **평가 순서와 표시 순서를 분리**하는 것이다 — 평가는 싼 것부터, 표시는 `Reason` 에 우선순위를 매겨 정렬.
- 사유가 없으면: **`null`.**\
  테스트 `allConditionsMet` — `assertEquals(null, coupon().firstReason(goodOrder()))`.

#### 4. TODO 4 — actionableReasons

```java
public List<Reason> actionableReasons(Order order) {
    List<Reason> reasons = reasonsAgainst(order);
    for (Reason reason : reasons) {
        if (!reason.isFixableByCustomer()) {
            return List.of();          // 하나라도 못 고치면 통째로 빈 목록
        }
    }
    return reasons;
}
```

| Reason | 고칠 수 있나 | 손님이 할 일 |
|---|---|---|
| NOT_STARTED | ✗ | 기다리는 것 말고 없다 |
| EXPIRED | ✗ | 아무것도 못 한다 |
| GRADE | ✗ | 등급을 올려야 한다 — 지금은 못 한다 |
| MIN_AMOUNT | ✓ | 더 담으면 된다 |
| CATEGORY | ✓ | 다른 상품을 담으면 된다 |
| ALREADY_USED | ✓ | 다른 쿠폰을 빼면 된다 |

> **고칠 수 있는 사유(fixable)** — 손님이 지금 이 결제 화면에서 스스로 해결할 수 있는 사유.\
> 예: "3만원 이상"은 상품을 더 담으면 해결되지만, "기간 만료"는 손님이 할 수 있는 일이 없다.

- GRADE 가 "못 고친다"인 이유: **지금 장바구니에서 해결할 수 없다.**\
  등급은 누적 구매액 같은 장기 지표라 오늘 당장 바꿀 수 없다.\
  기준은 "언젠가 가능한가"가 아니라 **"이 결제 화면에서 할 수 있나"** 다.
- 걸러내기 vs 빈 목록: **걸러내면** "기간 끝남 + 금액 미달" 주문에 `[MIN_AMOUNT]` 를 보여준다.\
  → 손님이 3만원을 채우고 다시 시도했다가 "기간이 끝났습니다"를 본다.\
  **빈 목록이면** 고치라고 안 한다.
- 후자를 고른 이유: **못 고치는 사유가 하나라도 있으면 고칠 수 있는 것을 알려줘봐야 소용없다.**\
  헛수고를 시키느니 아무 안내도 안 하는 편이 낫다.\
  측정: 못 쓰는 주문의 **82%(7,735/9,461)** 가 이 경우다.
- 기간 지났는데 금액 안내를 보여주면: **손님은 담는다.**\
  그리고 담은 뒤에 "기간이 끝났습니다"를 본다.\
  테스트 `orderDecidesWastedEffort` 가 이 주문의 `attemptsWithFirstOnly` 를 **-1**(고쳐도 소용없음)로 못 박는다.

> **두더지 잡기(whack-a-mole)** — 하나를 고치면 다음 문제가 나타나고, 그걸 고치면 또 다음이 나오는 상황.\
> 예: "3만원 이상 담아주세요" → 담음 → "이 상품은 대상이 아닙니다" → 바꿈 → "기간이 끝났습니다". 측정에서 41%가 이 경험을 한다.

- `reasonsAgainst` 를 안 쓰고 따로 구현하면: **판정 로직이 또 갈라진다**(2번과 같은 문제).\
  게다가 **순서가 어긋난다.**\
  이 함수는 `reasonsAgainst` 의 순서를 그대로 물려받는 것이 계약이다 — 테스트가 `[MIN_AMOUNT, CATEGORY]` 라는 **순서까지** 못 박고 있다.

  그래서 **"첫 사유를 무엇으로 고를지"가 예외 상황이 아니라 매번 일어나는 결정**이 된다.\
  평균 2.13개면 첫 사유만 주는 설계는 손님이 봐야 할 정보의 절반 이상을 버리는 것이다.
- 첫 사유만 알려줄 때, 고칠 수 있는 주문 1,726건의 시도 횟수:

| 시도 | 건수 |
|---|---|
| 1번 | 1,015 (59%) |
| 2번 | 604 |
| 3번 | 107 |

- 두 번 이상: **41%**(`(604+107)*100/1726`), 평균 **1.47번**.
- 전부 알려주면: **전부 한 번.**\
  사유가 한꺼번에 나오니 한 번에 다 고친다.
- 못 쓰는 주문 **9,461건** → 고칠 수 있는 것 **1,726건(18%)**, **고칠 수 없는 것 7,735건**.\
  README 는 82%로 적었고, 테스트 assert 는 정수 나눗셈으로 **81** 이다 — `"정수로 81, 실제 81.8 퍼센트"`.
- 순서 결정에 쓰이는 방식: **다수를 먼저 챙긴다.**\
  열에 여덟이 못 고치는 사람인데 "3만원 더 담으세요"를 기본 문구로 두면, 그 여덟이 전부 헛장바구니를 채운다.\
  그래서 못 고치는 사유를 목록 앞에 둔다.
- 조건 하나뿐인 쿠폰의 사유 개수 최댓값: **1**.\
  테스트 `singleConditionHidesEverything` — `assertEquals(1, maxReasons, "사유가 절대 둘이 안 된다")`.
- 안 보이는 것: **"첫 사유"와 "전부"가 같은 말이 된다.**\
  → `firstReason`·`reasonsAgainst`·`actionableReasons` 셋의 차이가 전부 사라진다.\
  **이 박스의 문제가 통째로 안 보인다.**\
  실제 쿠폰은 대개 조건 셋 이상이다.

> **가려진 갈림(masking)** — 테스트 데이터가 우연히 특수해서 설계 선택의 차이가 결과에 안 나타나는 것.\
> 예: 조건이 하나뿐인 쿠폰으로만 시험하면 사유가 절대 둘이 안 되므로, "첫 사유만 줄까 전부 줄까"라는 결정 자체가 존재하지 않는 것처럼 보인다.

- 기간 지남 + 금액 미달 주문의 `attemptsWithFirstOnly`: **-1**.\
  첫 사유(EXPIRED)가 고칠 수 없는 것이라 시도 자체가 무의미하다는 뜻이다.

#### 6. 생각해볼 것

> 원본 README가 답을 주지 않고 던진 질문 — (원본에 근거 없음 — 내 추론) 표시.

- **조건이 외부에 드러나는 문제**: (내 추론) 있다.\
  ① **타깃 쿠폰** — "등급 3 이상만"을 알리면 등급 체계와 그 사람의 등급이 노출된다(개인정보에 가깝다).\
  ② **테스트용·보상용 쿠폰** — 조건을 보여주면 어뷰징 경로가 드러난다("A상품만 대상"을 알면 그 상품만 담았다 취소하는 패턴).\
  ③ **A/B 실험 중인 조건** — 두 집단에 다른 조건을 주고 있다는 게 드러난다.\
  해법은 사유를 **공개 등급으로 나누는 것**이다 — 손님에게 보여줄 사유(MIN_AMOUNT, CATEGORY)와 내부 로그에만 남길 사유(GRADE)를 분리하고, 후자는 "이 쿠폰은 사용할 수 없습니다"로 뭉뚱그린다.\
  다만 **뭉뚱그리면 82%가 왜 안 되는지 모르게 되므로** 어뷰징 위험과 헛수고를 저울질해야 한다.
- **조건 평가가 비싸면**: 원본 javadoc 이 방향을 준다.\
  *"조건 평가가 싸면 전부 알리는 것이 낫다. 비싸면 그렇지 않다. 그런데 이 판단은 조건의 비용을 알아야 할 수 있다."*\
  (내 추론) 구체적으로는 **싼 조건부터 평가하고 걸리면 멈추는 단축 평가**로 바뀐다.\
  그러면 표시 순서와 평가 순서가 충돌하므로 **둘을 분리**한다.\
  ① 싼 로컬 조건(금액·기간·카테고리)을 먼저 전부 평가한다.\
  ② 거기서 못 고치는 사유가 나오면 비싼 조회(등급 서버)를 **아예 건너뛴다.**\
  ③ 표시할 때만 `Reason` 의 우선순위로 정렬한다.\
  비싼 조건이 하필 못 고치는 쪽(등급)이라는 게 이 챕터의 얄궂은 점이다.
- **얼마가 모자란지 알려주기**: (내 추론) 알려주는 편이 낫다.\
  "3만원 이상"보다 **"5,200원만 더 담으면 됩니다"** 가 행동으로 이어진다.\
  대가는 **Reason 이 enum 으로는 부족해진다**는 것이다 — 값(모자란 금액)을 실어야 하니 `record ReasonDetail(Reason kind, int shortfall)` 같은 것이 된다.\
  그러면 `isFixableByCustomer()` 같은 단순한 매달기가 복잡해진다.\
  게다가 사유마다 실어야 할 값이 다르다(카테고리는 "어떤 카테고리", 등급은 "몇 등급").\
  **enum 의 단순함을 언제 포기할 것인가**가 진짜 질문이다.
- **조건을 데이터로 두면**: (내 추론) 사유 순서를 **코드 줄 순서로 정할 수 없게 된다.**\
  지금은 `reasons.add(...)` 줄 순서가 곧 순서지만, 조건이 DB 행이면 행 순서는 의미가 없다.\
  그래서 순서는 **`Reason` enum 자체에 우선순위를 매달거나**(`displayOrder` 필드) **별도의 정렬 정책 테이블**에 둬야 한다.\
  좋은 점은 **순서가 명시적 데이터가 되어 리팩토링으로 우연히 바뀌지 않는다**는 것이다.\
  나쁜 점은 **한 곳에 있던 규칙이 두 곳(조건 데이터 + 순서 데이터)으로 나뉜다**는 것이다.

#### 7. 연결

- **09번 주문 상태**: 09는 "결과를 boolean 하나로 뭉개면 IGNORED 와 REJECTED 가 섞인다".\
  15는 "판정을 boolean 하나로 뭉개면 왜 안 되는지가 사라진다".\
  둘 다 **참/거짓으로 압축하면 사라지는 정보가 바로 그 도메인의 본체**라는 이야기다.\
  09는 결과를 셋으로 늘렸고, 15는 목록으로 늘렸다.
- **14번 포인트**: "유효기간이 균일하면 FIFO와 만료 임박 순이 한 번도 안 갈린다" ↔ "조건이 하나면 첫 사유와 전부가 같은 말이 된다".\
  **결정이 실제로 갈리는 입력을 안 쓰면 그 결정이 존재하지 않는 것처럼 보인다.**\
  둘 다 테스트 데이터가 설계 결정을 숨긴 사례다.
- **반복되는 종료일 미포함**: 04(호텔 체크아웃)·06(구독)·08(회의)·12(버프)·14(포인트 만료)·15(쿠폰 기간)에서 같은 결정이 나온다.\
  뜻하는 바는 **기간 경계가 도메인이 달라도 같은 모양의 결정**이라는 것이다.\
  팀이 규칙을 한 번 정해 전부에 똑같이 쓰는 편이 낫다.\
  챕터마다 다르게 정하면 코드베이스 안에서 `<` 와 `<=` 가 섞이고, 그건 읽어서는 구별이 안 된다.
- **폼 검증·API 에러로 옮기면**: 폼은 **필드별 오류를 한꺼번에** 보여줘야 한다(첫 오류만 보여주는 폼이 두더지 잡기가 되는 것이 정확히 같다).\
  API 는 **`{"errors": [...]}` 배열 + 코드(enum) + 고칠 수 있음 표시**가 된다.\
  HTTP 400 의 본문이 문자열 하나인 API 는 `boolean` 만 돌려주는 `isUsableBy` 와 같다.\
  대출 심사 거절 사유, 결제 실패 코드도 같은 자리다.
- **줄 순서로 순서를 정하는 위험**: **읽는 사람이 그게 계약인지 모른다.**\
  IDE 의 자동 정렬, "조건을 그룹으로 묶자"는 리팩토링, 조건 하나 추가할 때 "끝에 붙이면 되겠지" — 전부 UX를 바꾼다.\
  javadoc 에 **"순서가 계약이다"** 라고 적은 것이 최소한의 방어다.\
  더 단단하게 하려면 **순서를 테스트가 못 박아야 한다** — 실제로 `unfixableFirst` 가 `reasons.get(0)`·`get(1)` 로 못 박고 있다.
