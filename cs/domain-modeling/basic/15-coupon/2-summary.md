## 한눈에 — 쉽게 말하면

**쿠폰 검증 = 놀이기구 탑승 조건 안내판.**

- 놀이기구 앞 안내판: "키 120cm 이상, 보호자 동반, 우천 시 운휴". 못 타는 아이에게 **"키가 모자라요"만 말해주면**, 아이는 내년에 다시 왔다가 그제서야 "보호자가 필요해요"를 듣는다. **한 번에 다 알려줘야** 헛걸음이 없다.
- 쿠폰도 똑같다. 조건은 다섯 개(최소 금액·카테고리·기간·등급·중복 사용)고 전부 만족해야 쓴다. **판정 자체는 어렵지 않다. 어려운 것은 "못 쓴다"를 어떻게 알려주느냐다.**
- 그리고 사유마다 **손님이 고칠 수 있느냐**가 다르다 — "3만원 더 담으세요"는 고칠 수 있지만 "기간이 지났어요"는 아무것도 못 한다. 못 고치는 사유가 있는데 고칠 수 있는 것부터 보여주면 손님은 헛수고를 한다.

```text
  첫 사유만 알린다   구현이 쉽다. 손님이 고치면 다음 사유가 나온다 (두더지 잡기)
  전부 알린다        한 번에 다 고칠 수 있다. 대신 조건을 전부 평가해야 한다
```

실무 예: 쿠폰/프로모션 적용 조건, 폼 입력 검증(오류를 하나씩 vs 한꺼번에), 대출 심사 결과 안내 — "거절 사유를 어떻게 전달하나"가 있는 모든 검증.

## 문제 — 이 챕터가 시키는 것

원본 README가 말로 못 박은 요구사항 전부.

> "조건은 다섯 개고 전부 만족해야 쓸 수 있다. **판정 자체는 어렵지 않다.**"
> "어려운 것은 **못 쓴다는 것을 어떻게 알려주느냐**다."
> ```
>   첫 사유만 알린다   구현이 쉽다. 손님이 고치면 다음 사유가 나온다
>   전부 알린다        한 번에 다 고칠 수 있다. 대신 조건을 전부 평가해야 한다
> ```
> "`src/main/java/com/domain/coupon/Coupon.java` 의 TODO 1~4. `Order`, `Reason` 은 계약이라 다 주어져 있다."

과제 목록 — 채울 TODO 4개:

| TODO | 메서드 | 말로 된 요구 |
|---|---|---|
| 1 | `reasonsAgainst(order)` | 못 쓰는 사유를 **전부** 모은다. **순서가 계약** — 못 고치는 것(기간·등급)을 앞에 |
| 2 | `isUsableBy(order)` | 쓸 수 있나 (= 사유 목록이 비었나) |
| 3 | `firstReason(order)` | 첫 사유만. 없으면 null. **전부 평가한 뒤** 첫 것을 준다 |
| 4 | `actionableReasons(order)` | 손님이 지금 고칠 수 있는 것만. 못 고치는 게 하나라도 있으면 **빈 목록** |

테스트가 못 박은 계약:

- 최소 30,000원이면 29,999는 `[MIN_AMOUNT]`, 30,000은 통과 — **"이상"은 경계 포함**.
- 3/1~4/1 쿠폰에서 2/28은 `[NOT_STARTED]`, 3/1 통과, 3/31 통과, **4/1은 `[EXPIRED]`** — 시작일 포함·종료일 미포함.
- 허용 {food, drink}에서 `[food, book]`은 **통과**(하나만 걸리면 된다), `[book]`은 `[CATEGORY]`.
- **빈 카테고리 집합은 "제한 없음"** — `Set.of()` 쿠폰은 book 주문에도 쓸 수 있다.
- stackable=false + 이미 쿠폰 사용 → `[ALREADY_USED]`, stackable=true면 통과.
- 금액·카테고리·등급이 다 걸린 주문 → 사유 **3개**가 한꺼번에 나온다.
- 기간 지남 + 금액 미달 → `reasons.get(0) == EXPIRED`, `get(1) == MIN_AMOUNT` — **못 고치는 것이 앞**.
- 고칠 수 있는 것만 걸린 주문 → `actionableReasons == [MIN_AMOUNT, CATEGORY]`, 기간이 지난 주문 → **빈 목록**.
- **빈 목록이 두 가지를 뜻한다** — "쓸 수 있다"와 "안내할 것이 없다". 그래서 `isUsableBy`를 따로 둔다.
- 빈 쿠폰 코드·종료일 ≤ 시작일·음수 주문 금액은 생성자에서 예외.

README가 미리 알려준 함정: ①빈 카테고리 집합은 제한 없음(**가장 많이 발행되는 쿠폰이 여기 걸린다**) ②카테고리는 하나만 걸리면 된다 ③"3만원 이상"은 이상(초과로 쓰면 **딱 3만원인 손님이 가장 많은데** 못 쓴다) ④종료일 미포함(04·06·08·12·14번과 같은 자리) ⑤**사유 목록의 순서가 곧 "무엇을 먼저 보여줄까"의 기본값**이다.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
말로 된 요구사항                          →  코드 구조
────────────────────────────────────────────────────────────
"조건 다섯: 금액·카테고리·기간·등급·중복" →  Coupon 필드 (minAmount, allowedCategories,
                                             startsOn/endsOn, minGrade, stackable)
"검증에 필요한 주문 정보만"               →  record Order(amount, categories, orderedOn,
                                             memberGrade, alreadyUsedCoupon)
"못 쓰는 이유에 이름을 붙인다"            →  enum Reason 6종
"사유마다 고칠 수 있나가 다르다"           →  Reason.isFixableByCustomer()
"전부 알린다"                             →  reasonsAgainst(order) → List<Reason>
"쓸 수 있나"                              →  isUsableBy = reasonsAgainst가 빈 목록
"첫 사유만"                               →  firstReason (전부 평가 후 첫 것)
"지금 고칠 수 있는 것만"                  →  actionableReasons (못 고치는 게 있으면 빈 목록)
```

## 규칙 1 — 조건 다섯 개와 사유 6종

**예시 손계산** — 쿠폰: 3만원 이상·패션 카테고리·3/1~4/1·등급 2 이상·중복 불가. 주문: 25,000원·식품만·3/15·등급 1·다른 쿠폰 사용 중.

```text
  NOT_STARTED? 3/15 ≥ 3/1     통과
  EXPIRED?     3/15 < 4/1     통과
  GRADE?       1 < 2          걸림
  MIN_AMOUNT?  25,000 < 30,000 걸림
  CATEGORY?    식품 ∉ {패션}    걸림
  ALREADY_USED? 사용 중 & 중복불가 걸림

  → reasonsAgainst = [GRADE, MIN_AMOUNT, CATEGORY, ALREADY_USED]  (4개!)
```

측정: 무작위 주문 10,000건에서 쓸 수 있는 것은 539건(5.4%), 사유는 총 21,392개 — **한 주문에 평균 2.13개**. 사유가 하나만 걸리는 경우가 오히려 드물다.

**왜 boolean이 아니라 List<Reason>인가**: isUsableBy만 있으면 "왜 안 되는지"를 화면이 말할 수 없다. 사유에 enum으로 이름을 붙이고, 표시 문구·고칠 수 있음 여부를 그 이름에 매단다.

## 규칙 2 — 사유 목록의 순서가 곧 UX다

**reasonsAgainst의 추가 순서가 계약이다**: 기간(NOT_STARTED, EXPIRED) → 등급 → 금액 → 카테고리 → 중복. **못 고치는 것을 앞에 둔다.**

**왜**: 측정에서 못 쓰는 주문 9,461건 중 **82%(7,735건)는 고칠 수 없다**(기간·등급). 그런데 "3만원 이상 담아주세요"를 먼저 보여주면 손님은 담는다 — 담은 뒤에 "기간이 지났습니다"를 본다. 못 고치는 사유를 먼저 알려주는 편이 헛수고를 줄인다.

| Reason | 뜻 | 손님이 고칠 수 있나 |
|---|---|---|
| NOT_STARTED | 아직 시작 전 | 못 고친다 |
| EXPIRED | 기간 지남 | 못 고친다 |
| GRADE | 등급 미달 | 당장은 못 고친다 |
| MIN_AMOUNT | 금액 미달 | 더 담으면 된다 |
| CATEGORY | 대상 상품 없음 | 다른 상품 담으면 된다 |
| ALREADY_USED | 다른 쿠폰 사용 중(중복 불가) | 다른 쿠폰 빼면 된다 |

**actionableReasons의 규칙**: 못 고치는 사유가 **하나라도** 있으면 빈 목록 — 고칠 수 있는 것을 알려줘봐야 소용없기 때문이다.

**첫 사유만 알리면 (측정)**: 고칠 수 있는 주문 1,726건에서 41%가 두 번 이상 시도(평균 1.47번). "3만원 이상 담아주세요"를 보고 담은 뒤 "이 상품은 대상이 아닙니다"를 보는 손님이 41%다. 전부 알려주면 전부 한 번이다.

**firstReason의 미묘함**: "전부 평가하고 첫 것만 주기"와 "첫 것을 만나면 멈추기"는 다르다. 여기서는 전부 평가한다 — 조건이 싸기 때문. 조건 평가가 비싸면(외부 조회) 이 선택이 달라진다.

## 경계·모서리 케이스

- **함정: 빈 카테고리 집합 = "아무것도 안 됨"으로 읽기** → 빈 집합은 **"제한 없음"** 이다. 반대로 읽으면 전 상품 쿠폰이 아무 데도 못 쓰인다 — **그리고 그 쿠폰이 가장 많이 발행된다.** (코드: `!allowedCategories.isEmpty() && ...` — 비어 있으면 검사 자체를 건너뛴다.)
- **함정: 카테고리를 "전부 해당"으로 읽기** → **하나만 걸리면 된다**(noneMatch일 때만 사유 추가). "전부 해당"으로 읽으면 대상 아닌 상품이 하나만 섞여도 못 쓴다.
- **함정: "3만원 이상"을 초과로 구현** → 딱 3만원인 손님이 못 쓴다 — 그 손님이 가장 많다. `amount < minAmount`일 때만 사유(이상 = 경계 포함).
- **함정: 종료일 포함** → 종료일은 **미포함**이다 (`!orderedOn.isBefore(endsOn)`이면 EXPIRED). 04(호텔)·06(구독)·08·12·14번과 같은 자리 — 이 시리즈의 일관 규칙이다.
- **함정: 조건 하나짜리 쿠폰으로 시험** → 사유가 언제나 0개 아니면 1개라 "첫 사유"와 "전부"가 같은 말이 된다. **이 박스의 문제가 통째로 안 보인다.** 실제 쿠폰은 대개 셋 이상.
- 잘못된 객체는 못 만든다: 빈 쿠폰 코드, 종료일 ≤ 시작일, 음수 주문 금액 전부 생성자에서 거부.

## 핵심 문장

- 판정(쓸 수 있나)은 쉽다 — 이 도메인의 실제 문제는 **"못 쓴다"를 어떻게 알려주느냐**고, 그것이 boolean이 아니라 `List<Reason>`을 반환 타입으로 만든다.
- 사유 목록의 순서가 곧 화면의 기본값이다 — 못 고치는 사유(기간·등급)를 앞에 두는 이유는 못 쓰는 주문의 82%가 어차피 못 고치는 것이라서다.
- 첫 사유만 알리면 두더지 잡기가 된다 — 41%의 손님이 고치고 나서 또 다른 사유를 만난다.
- 빈 집합은 "제한 없음"이다 — 가장 많이 발행되는 전 상품 쿠폰이 이 해석 하나에 걸려 있다.
- "이상"은 경계 포함, 종료일은 미포함 — 경계의 손님(딱 3만원)이 가장 많으니 경계 해석이 곧 매출이다.
- 조건 하나짜리 테스트는 이 문제를 통째로 숨긴다 — 사유가 여러 개 걸리는 입력을 일부러 만들어야 한다.

## 용어 풀이

- **검증(validation)**: 조건을 전부 확인해 통과/실패와 그 이유를 내는 일. 여기서는 조건 5개 전부 만족해야 통과.
- **사유(Reason)**: 못 쓰는 이유에 붙인 이름(enum 6종). boolean 대신 이유의 목록을 돌려주는 것이 이 설계의 축.
- **고칠 수 있는 사유(fixable)**: 손님이 지금 장바구니에서 해결 가능한 사유 — MIN_AMOUNT, CATEGORY, ALREADY_USED.
- **actionable**: "지금 행동으로 옮길 수 있는". 못 고치는 사유가 하나라도 있으면 고칠 수 있는 목록도 무의미하다.
- **빈 집합 = 제한 없음**: 허용 카테고리가 비어 있으면 모든 카테고리 허용. "아무것도 안 됨"의 반대.
- **하나만 걸리면 됨(any-match)**: 주문의 카테고리 중 하나라도 허용 목록에 있으면 통과. "전부 해당(all-match)"과 대비.
- **이상(≥)**: 경계값 포함. "3만원 이상"에서 딱 3만원은 통과.
- **종료일 미포함**: endsOn 그 날에는 이미 못 쓴다. 시리즈(04·06·08·12·14) 공통의 기간 경계 규칙.
- **stackable(중복 사용 가능)**: 다른 쿠폰과 같이 쓸 수 있는가. 불가인데 이미 다른 쿠폰을 썼으면 ALREADY_USED.
- **첫 사유 vs 전부**: 실패 안내 전략 둘. 전부 평가가 가능한 것은 조건이 싸기 때문 — 비싸지면(외부 조회) 트레이드오프가 바뀐다.
