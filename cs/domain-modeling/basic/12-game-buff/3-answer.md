### A. 과제 (BuffBoard 의 TODO 1~4)

#### 0. 챕터 지문 — 요구사항 전문

- Q: 기획서 한 줄에 안 들어 있는 결정은?
  A: 최소 여섯 개다.
  ① 같은 버프를 또 걸면 어떻게 되나(중첩/갱신/무시) ② 효과를 어떻게 합치나(더하기/곱하기) ③ 몇 개까지 쌓이나(상한) ④ 상한에 걸리면 무엇을 버리나 ⑤ 만료 시각은 포함인가 미포함인가 ⑥ 못 걸렸을 때 부르는 쪽에 어떻게 알리나.
  기획서는 "20 퍼센트, 10 분"이라는 **두 숫자만** 준다. 나머지 여섯 개를 안 정하면 코드가 안 돌아간다.

- Q: 셋을 다 구현한 이유는?
  A: **셋 다 실제 게임에서 쓰이고, 같은 게임 안에서도 버프마다 다르기 때문**이다(README 원문).
  즉 셋 중 하나가 정답이 아니라, 버프마다 골라 쓸 수 있는 **설정값**이 정답이다.
  그리고 셋을 나란히 두면 "같은 이벤트열에서 효과가 3배 갈린다"는 사실을 측정할 수 있다.

- Q: 어느 필드가 되는가?
  A: `BuffBoard` 생성자가 받는 `StackRule stackRule` 과 `int maxStacks` 다.
  ```java
  public BuffBoard(StackRule stackRule, int maxStacks) { ... }
  ```
  버프 종류마다 판을 따로 만들어 다른 규칙을 줄 수 있다 — 규칙이 코드가 아니라 **데이터**가 된 것이다.
  (다만 `CombineRule` 은 필드가 아니라 `totalPercent` 의 인자다 — 같은 판을 두 방식으로 재볼 수 있게 열어둔 것.)

- Q: 규칙은 몇 개의 축인가?
  A: **두 축**이다. 중첩 축(STACK/REFRESH/IGNORE)과 합치기 축(ADDITIVE/MULTIPLICATIVE).
  둘은 직교한다 — 3 × 2 = 6가지 조합이 전부 말이 된다. 거기에 상한(maxStacks)과 버릴 대상 규칙이 STACK 축에 딸려 붙는다.

#### 1. TODO 1 — apply

- Q: 만료 정리를 규칙 적용 뒤에 하면?
  A: IGNORE 에서 **새 버프가 영영 안 걸린다.**
  ```text
  09:00  20% 60초 버프를 건다        → 목록 [끝난것 아님]
  09:02  또 건다 (앞의 것은 09:01에 이미 끝남)

    정리 먼저 → 목록이 비어 있다 → 걸린다      ✔
    정리 나중 → 목록에 09:01 끝난 것이 보인다
                → "이미 있네" → false          ✘ 영원히 못 건다
  ```
  BuffTest `expiredBuffDoesNotBlock` 이 이 한 줄 순서를 못 박아 둔 테스트다.

- Q: "시간이 지나야만 나타난다"는?
  A: 버프를 **연달아 거는 테스트로는 절대 안 나온다**는 뜻이다.
  같은 `now` 로 두 번 부르면 앞 버프가 아직 살아 있어서 IGNORE 가 false 를 주는 게 맞고, 그건 정상 동작이다.
  `now` 를 만료 이후로 옮겨야만 갈린다. 즉 **시계를 움직이는 테스트를 쓰지 않으면 이 버그는 통과한다.**

- Q: boolean 을 돌려주는 이유는?
  A: 세 규칙 중 둘(IGNORE, 상한에 걸린 STACK)이 **"안 걸었다"는 결과를 낼 수 있기 때문**이다.
  안 걸었는데 void 면 부르는 쪽이 그 사실을 알 길이 없다.

- Q: false 를 안 보면?
  A: 화면에 **"버프 적용!"이 뜨는데 실제 능력치는 그대로**다.
  README 함정 2번 원문: "무시 규칙은 `false` 를 돌려주는 것이 계약이다. 안 보면 '걸었다' 고 알리고 실제로는 안 걸린다."
  아이템을 소모했다면 아이템만 사라진다 — 유저 문의가 들어오는 종류의 사고다.

- Q: 같은 종류의 기준은?
  A: `Buff.kind()` 문자열이 같은가 — `activeOf(buff.kind(), now)` 로 **살아 있는 같은 종류**만 모은다.
  주의: 여기서 모으는 것은 전체 목록이 아니라 살아 있는 것뿐이다. 그래서 만료 정리를 먼저 하는 것과 겹쳐 두 겹으로 막는다.

- Q: 종류를 안 나누면?
  A: **아무 버프나 서로를 막는다**(테스트 javadoc 원문).
  IGNORE 판에서 공격력 버프가 걸려 있으면 방어력 버프가 안 걸린다.
  BuffTest `differentKinds` 가 atk + def 둘 다 걸리는 것을 못 박았다.

- Q: REFRESH 에 더 낮은 버프가 오면?
  A: **그대로 갈아치운다.** 30 % 가 걸려 있는데 10 % 를 걸면 남는 것은 10 % 다.
  ```java
  case REFRESH -> { buffs.removeAll(sameKind); buffs.add(buff); yield true; }
  ```
  효과 비교가 없으므로 손해가 날 수 있다. "더 센 것만 갱신"이 필요하면 그건 **네 번째 규칙**이다(README 측정 2 원문: "규칙이 셋이 아니라 넷이 된다").

#### 2. TODO 1 딸림 — 상한과 버릴 대상

- Q: 무엇을 버리는가?
  A: **남은 시간이 가장 짧은 것**(`min(comparing(remainingAt(now)))`).

- Q: "무엇을 버릴지도 규칙이다"는?
  A: "최대 3개"라는 요구사항은 **넘쳤을 때 누가 나가는지**를 안 정해준다는 뜻이다.
  후보가 최소 셋이다 — 남은 시간 최단 / 가장 오래된 것 / 효과가 가장 약한 것. 어느 것을 골라도 "3개"는 지켜지지만 게임의 느낌은 달라진다.
  **정하지 않으면 구현 순서가 규칙이 된다** — 그게 최악이다.

- Q: "가장 오래된 것을 버린다"면?
  A: 테스트 javadoc 원문: "그러면 방금 건 긴 버프가 밀려난다."
  방금 큰 비용을 치르고 건 10분짜리가, 먼저 걸려 있던 1분짜리를 못 밀어내고 오히려 자기가 밀려날 수 있다.
  남은 시간 기준은 "판 위의 총 버프 시간을 최대로"라는 방향이고, 오래된 것 기준은 "최근 것 우선"이라는 방향이다.

- Q: 새 버프가 더 짧으면?
  A: **새 버프를 버린다**(`false`).
  ```java
  if (weakest.remainingAt(now).compareTo(buff.remainingAt(now)) >= 0) yield false;
  ```
  `>=` 이므로 **같을 때도 새것을 버린다** — 기존 것을 흔들지 않는 쪽으로 동점을 깬다.
  테스트: 상한 3에 720·780·840초가 차 있을 때 60초짜리를 걸면 `false`.

- Q: false 와 "넣고 바로 밀어내기"의 차이는?
  A: 결과 목록은 같지만 **부르는 쪽이 받는 답이 다르다.**
  넣고 밀어내면 `true` 를 주게 되고, 아무 효과도 못 얻은 유저에게 "걸렸다"고 알리게 된다 — IGNORE 에서 false 를 계약으로 삼은 것과 같은 이유로 틀렸다.

- Q: 왜 "효과 크기"가 아닌가?
  A: (원본에 명시 없음 — 내 추론) 이 판은 종류별 버프를 다루고, **같은 종류는 효과가 대개 같기 때문**이다. 같은 20 % 가 여러 개 쌓이는 그림이라 효과로는 동점이 나서 못 가른다.
  효과가 제각각인 버프를 쌓는 게임이라면 "약한 것부터 버린다"가 더 맞는 규칙이 된다 — **규칙은 데이터 모양에 따라 달라진다.**

- Q: maxStacks ≤ 0 을 왜 생성자에서 막는가?
  A: 0이면 어떤 버프도 못 걸리는 판이고, 음수면 `sameKind.size() >= maxStacks` 가 언제나 참이라 첫 버프부터 이상하게 돈다.
  **말이 안 되는 객체를 아예 못 만들게** 하는 것이 값 검증의 자리다 — 생성 이후에 나타나는 이상 동작을 전부 없앤다.

#### 3. TODO 2 — expire 와 stored

- Q: 지웠는데 테스트가 안 깨진 이유는?
  A: **합계와 목록이 어차피 살아 있는 것만 보기 때문**이다.
  `active(now)` 가 `isActiveAt` 으로 거르고, `totalPercent` 는 `active(now)` 를 쓴다. 만료된 것이 리스트에 남아 있어도 **답에는 안 나온다.**
  README 원문: "답이 안 바뀌는 일이라 결과 테스트로는 잡을 수 없었다."

- Q: 그럼 왜 필요한가?
  A: **목록이 무한히 자라는 것을 막으려고.**
  README 원문: "오래 도는 캐릭터 하나가 서버 메모리를 먹는 경로가 여기다."
  버그의 증상이 오답이 아니라 **메모리**다 — 서버가 며칠 돌아야 보인다.

- Q: 200번 걸면 stored 는?
  A: 걷어내는 쪽 **1**, 안 걷어내는 쪽 **200**.
  ```text
  1분짜리 버프를 5분 간격으로 200번
    → 걸 때마다 앞의 것은 이미 4분 전에 끝나 있다
    → 정리하면 언제나 살아 있는 1개만 보유
    → 정리 안 하면 죽은 199개가 그대로 쌓인다
  ```
  BuffTest `expiredBuffsDoNotAccumulate` 가 `active(now)==1` **과** `stored()==1` 을 둘 다 단언한다. 앞의 것만 있으면 버그가 통과한다.

- Q: active 와 stored 의 차이는?
  A: `active(now)` = 지금 살아 있는 것(도메인 답). `stored()` = 리스트가 실제로 들고 있는 개수, **만료 포함**(구현 내부 사정).
  전자는 게임 규칙이고 후자는 **자원 관측용 창**이다.

- Q: 답이 안 바뀌는 결함을 테스트로 잡으려면?
  A: **결과 말고 내부 상태를 볼 수 있게 밖으로 열어야 한다.**
  여기서는 `stored()` 를 public 으로 열어 "결과는 같지만 보유 개수가 다르다"를 단언 가능하게 만들었다.
  일반화하면 — 관측할 수 없는 것은 테스트할 수 없고, 관측 지점을 만드는 것 자체가 설계 작업이다.

- Q: 관측용 public 의 대가는?
  A: **구현 세부가 공개 계약이 된다.** 나중에 리스트를 맵이나 다른 구조로 바꿔도 `stored()` 의 의미를 유지해야 한다.
  대가를 치를 가치가 있는지는 "이걸 안 열면 이 결함을 못 잡는다"로 판단한다 — 여기서는 열 가치가 있었다.

#### 4. TODO 4 — totalPercent

- Q: 곱하기 초기값이 1인 이유는?
  A: 곱셈의 **항등원**이 1이기 때문이다. 아무것도 안 곱한 상태 = 1배 = 원래 능력치.
  ```java
  BigDecimal factor = BigDecimal.ONE;
  for (Buff b : live) factor = factor.multiply(ONE.add(valueOf(b.percent(), 2)));
  ```

- Q: 0으로 두면?
  A: **결과가 항상 0**이다. 0에 무엇을 곱해도 0이므로 버프를 아무리 쌓아도 배율이 0 → 능력치가 0이 된다.
  README 함정 3번이 이걸 따로 적어둔 이유는, 더하기 쪽 초기값이 0이라 복사해 쓰다 실수하기 딱 좋기 때문이다.

- Q: 버프 0개일 때 0이 나오는 과정은?
  A: 손으로 따라가면.
  ```text
  factor = 1                (반복문을 한 번도 안 돈다)
  factor - 1 = 0
  0 × 100 = 0
  setScale(2) → 0.00        ← 테스트가 요구하는 값
  ```
  "빈 곱은 1이고 거기서 1을 빼면 0"이 정확히 이 흐름이다.

- Q: 1을 빼고 100을 곱하는 이유는?
  A: `factor` 는 **배율**(1.44)이고 함수가 돌려주는 것은 **증가율 퍼센트**(44)이기 때문이다.
  ```text
  배율 1.44  ─(-1)→  증가분 0.44  ─(×100)→  44 퍼센트
  ```
  안 빼면 "144 퍼센트 증가"가 되어 더하기 쪽(40)과 단위가 안 맞는다.

- Q: long 과 BigDecimal 을 나눈 이유는?
  A: 더하기는 **정수 덧셈**이라 오차가 없다(20+20=40). 곱하기는 1.2 같은 소수를 거듭 곱하므로 `double` 로 하면 오차가 누적되어 44.00 대신 44.000000000000006 류가 나온다.
  BigDecimal 은 십진수를 정확히 다루고 **반올림 자리를 내가 정하게** 강제한다.

- Q: 반올림은?
  A: `setScale(2, RoundingMode.HALF_UP)` — **소수 둘째 자리, 반올림**.
  그래서 테스트가 `new BigDecimal("44.00")` 로 **스케일까지** 비교한다(BigDecimal 의 `equals` 는 스케일이 다르면 false다 — 44 와 44.00 은 다른 값으로 본다).

- Q: 20 % 세 개의 72.80 을 손계산하면?
  A:
  ```text
  1.20 × 1.20 = 1.4400
  1.4400 × 1.20 = 1.728000
  1.728000 - 1 = 0.728000
  × 100 = 72.800000
  setScale(2, HALF_UP) → 72.80
  ```
  더하기로는 60이다. 세 개만 쌓여도 12.8 %p 가 벌어진다.

- Q: active(now) 와 buffs 를 그대로 쓰는 것의 차이는?
  A: `buffs` 를 그대로 더하면 **끝난 버프가 계속 효과를 낸다.**
  BuffTest `expiredBuffsDoNotCount`: 20 %(60초) + 30 %(600초) 를 걸고 100초 뒤에 재면 **30** 이어야 한다. 그대로 더하면 50이 나온다.
  이건 expire 와 달리 **답이 바뀌는** 결함이라 결과 테스트로 잡힌다.

#### 5. 계약으로 주어진 Buff

- Q: 만료 미포함(반열린 구간)의 이유는?
  A: 구간을 `[시작, 끝)` 으로 잡으면 **이어 붙일 때 겹치거나 비지 않는다.** 09:00~09:01 버프와 09:01~09:02 버프가 09:01에 동시에 살아 있지 않다.
  테스트 javadoc 원문: "04, 06, 08 번에서 본 것과 같은 규약이다."

- Q: 끝을 포함하면 1초짜리는?
  A: **2초를 산다.** 0초에 걸고 1초에 만료인데 1초에도 살아 있으면 0초와 1초 두 시점에 유효하다.
  1초씩 재는 시스템에서 모든 버프가 1초씩 길어지는 셈이다.

- Q: 시작은 포함, 끝은 미포함인 비대칭이 왜 맞나?
  A: 그래야 **길이가 정확히 `expiresAt - appliedAt`** 이 되기 때문이다. 양쪽 다 포함하면 길이가 하나 더 길고, 양쪽 다 미포함이면 하나 더 짧다.
  "10분간"이라는 기획서 문구와 실제 지속이 어긋나지 않게 하는 쪽이 이 비대칭이다.

- Q: 만료 뒤 남은 시간을 0으로 주는 이유는?
  A: 테스트 javadoc 원문: "음수를 돌려주면 정렬이나 비교에서 이상하게 동작한다."
  `remainingAt` 은 실제로 상한 로직의 **정렬 키**로 쓰인다.

- Q: 음수면 어디가 망가지는가?
  A: STACK 상한 로직이다.
  ```java
  Buff weakest = sameKind.stream().min(comparing(b -> b.remainingAt(now)))...
  ```
  음수를 주면 "가장 많이 만료된 것"이 최솟값이 되어, 만료 정도에 따라 버릴 대상이 뒤바뀐다.
  (실제로는 `activeOf` 가 살아 있는 것만 모으므로 지금은 안 터진다 — 그래도 계약으로 0을 못 박아 두면 그 의존이 깨져도 안전하다.)

- Q: 효과 0 / 지속 0 / 빈 종류를 막는 이유는?
  A: 테스트 javadoc 원문 그대로.
  ```text
  효과 0 이하  → 아무 일도 안 하는 버프가 목록을 채운다
  지속 0 이하  → 걸자마자 없는 버프
  종류 없음    → 중첩 규칙을 적용할 대상이 없다
  ```
  셋 다 "만들 수는 있는데 쓸모가 없고, 그 무쓸모가 조용히 판을 어지럽히는" 값이다. 그래서 생성 시점에 막는다.

### B. 개념

#### 6. 더하기와 곱하기의 벌어짐

- Q: 개수별 값은?
  A: README 측정표(20 % 버프).
  | 개수 | 더하기 | 곱하기 |
  |---|---|---|
  | 1 | 20 | 20.00 |
  | 2 | 40 | 44.00 |
  | 3 | 60 | 72.80 |
  | 5 | 100 | 148.83 |
  | 10 | 200 | **519.17** |

- Q: 10개면 몇 배인가?
  A: **약 2.6배**(519.17 / 200 ≈ 2.60).

- Q: 두 개일 때 아무도 신경 안 쓰는 이유는?
  A: 40 vs 44 — **4 퍼센트포인트 차이**라 체감이 없고, 기획 문서에서도 다툴 이유가 없다.
  그래서 결정이 미뤄지고, 미뤄진 채로 코드가 굳어진다. 문제가 드러날 때는 이미 게임 밸런스 전체가 그 위에 얹혀 있다.

- Q: 1,000회 합계는?
  A: 더하기 **77,849**, 곱하기 **103,080** — **32 퍼센트** 차이.

- Q: 왜 1,000/1,000 전부 갈리는가?
  A: **버프가 둘 이상이면 반드시 다르기 때문**이다(README 원문).
  a + b 와 (1+a)(1+b) − 1 = a + b + ab 의 차이가 `ab` 인데, 효과가 양수인 한 `ab > 0` 이라 절대 같아질 수 없다.
  버프가 0개나 1개일 때만 같다.

- Q: "총합을 내는 한 줄에 숨어 있다"는?
  A: 이 결정은 게임의 성격을 바꾸는 **설계 축**인데, 코드에서는 `sum += percent` 냐 `factor *= (1+percent)` 냐 하는 **한 줄 차이**로 나타난다는 뜻이다.
  코드 리뷰에서 눈에 안 띄고, 이름도 안 붙고, 문서에도 안 남는다. 그래서 enum 으로 **이름을 붙여 밖으로 꺼낸 것** 자체가 이 챕터의 모델링 답이다.

#### 7. 중첩 규칙으로 갈리는 효과

- Q: 세 규칙의 합계는?
  A: 중첩 **58,913**, 갱신 **19,442**, 무시 **19,561**(같은 이벤트열 1,000회).
  중첩이 나머지의 약 3배다.

- Q: 중첩과 갱신은 몇 번 갈렸는가?
  A: **938 / 1,000.**

- Q: 갱신과 무시가 다른 이유는?
  A: **누가 남느냐가 반대**이기 때문이다.
  ```text
  갱신(REFRESH) : 나중 것이 남는다  → 나중 것이 약하면 손해
  무시(IGNORE)  : 먼저 것이 남는다  → 나중 것이 세도 못 받는다
  ```
  효과가 다 같으면 둘은 지속 시간만 다르지만, 효과가 제각각이면 합계가 갈린다.
  측정에서는 무시가 **조금 더 높았다**(19,561 vs 19,442).

- Q: 30 % 뒤에 10 % 면?
  A: 갱신은 **10 이 남고**, 무시는 **30 이 남는다.**
  README 원문: "30 퍼센트를 걸고 10 퍼센트를 또 걸면 갱신은 10 이 남는다. 갈아치우기 때문이다."
  즉 갱신은 **효과를 깎아먹을 수 있는** 규칙이다 — 이름만 보면 좋아 보이는데 그렇지 않다.

- Q: "더 센 것만 갱신"이 네 번째 규칙인 이유는?
  A: 셋 중 어느 것으로도 표현이 안 되기 때문이다.
  갱신이지만 조건이 붙고(효과 비교), 무시지만 조건이 붙는다(더 세면 통과). 즉 기존 셋의 조합이 아니라 **새 축(효과 비교)** 이 들어온다.
  README 원문: "규칙이 셋이 아니라 넷이 된다." — 요구가 하나 늘면 enum 이 하나 느는 게 정직한 모델이다.

#### 8. 곱하기와 상한은 하나의 결정

- Q: 20 %를 20번, 상한별 값은?
  A: README 측정표.
  | 상한 | 더하기 | 곱하기 |
  |---|---|---|
  | 20 | 400 | **3,733.76** |
  | 5 | 100 | 148.83 |
  | 3 | 60 | 72.80 |
  더하기는 상한에 **비례**해서 늘고(20배 → 400), 곱하기는 **지수로** 늘어난다(1.2²⁰ ≈ 38.34배).

- Q: "하나의 결정"이란?
  A: 곱하기를 고르는 순간 상한이 **선택이 아니라 필수**가 된다는 뜻이다.
  곱하기의 결과는 개수에 지수로 반응하므로, 상한을 안 두면 값이 얼마까지 갈지 설계자가 모른다.
  그래서 "곱하기로 하자"와 "상한은 몇으로 하자"는 따로 정할 수 있는 두 결정이 아니라 **같이 정해야 하는 한 결정**이다.

- Q: 더하기면 상한이 없어도 되나?
  A: 안전 면에서는 훨씬 낫다 — 20개면 400, 200개면 4,000으로 **예측 가능하게** 커진다.
  그래도 상한은 필요하다. 이유가 밸런스에서 **메모리·성능**으로 바뀔 뿐이다(만료 정리와 같은 이유).

- Q: 상한 없는 곱하기의 사고 모양은?
  A: (원본에 사례 없음 — 내 추론) 유저가 버프 쌓기 경로를 찾아내 능력치가 수천 %가 되는 그림이다. 보스가 한 방에 죽고 랭킹이 무너진다.
  특징은 **평소에는 전혀 안 보인다**는 것이다 — 2~3개까지는 정상이고, 쌓는 방법을 찾아낸 소수만이 절벽 너머로 간다.

#### 9. 변종 검증이 열어둔 것

- Q: 만료 정리를 지워도 안 깨진 근본 이유는?
  A: **정답 경로가 만료된 버프를 이미 거르고 있어서** 리스트에 뭐가 남아 있든 답이 같기 때문이다.
  결함이 **결과가 아니라 자원**에만 나타난다. 결과를 보는 테스트는 원리적으로 못 잡는다.

- Q: 무엇을 열었는가?
  A: `stored()` — 만료 포함 실제 보유 개수.

- Q: 이런 결함을 뭐라 부르나?
  A: 메모리 누수(memory leak) 류 — 더 넓게는 **답은 맞는데 자원이 새는 결함**이다.
  같은 성격으로 불필요한 재계산·커넥션 누수·캐시 무한 증식이 있다. 공통점은 **오답이 아니라 시간이 지나야 죽는다**는 것.

- Q: 테스트는 무엇을 단언해야 하나?
  A: 결과 대신 **자원 지표**다. 여기서는 `assertEquals(1, board.stored())`.
  그리고 **시간이 흐르는 시나리오**여야 한다 — 200번을 5분 간격으로 돌린 것은 결함이 축적되는 조건을 일부러 만든 것이다.

#### 10. 생각해볼 것

- Q: 디버프(효과 음수)를 같이 다루려면?
  A: (원본은 질문만 던진다 — 이하 내 추론)
  ① `Buff` 생성자의 `percent <= 0` 거부가 깨진다 — 0만 막고 음수는 허용하도록 바꿔야 한다.
  ② 곱하기 합성이 **유효한 구간을 벗어날 수 있다** — −100 % 짜리가 들어오면 배율이 0이 되고, 그 아래면 음수 배율이라 의미가 없다. 하한 처리가 필요하다.
  ③ 상한 규칙이 갈린다 — 버프 개수 제한과 디버프 개수 제한을 같은 판에서 셀 수는 없다.
  ④ "가장 약한 것을 버린다"의 방향이 뒤집힌다.
  즉 "음수 하나 허용"이 아니라 **판을 둘로 나누는 게 맞는지**부터 다시 묻게 되는 변경이다.

- Q: 체감(감소 수익) 규칙은 어디에 두나?
  A: (내 추론) `CombineRule` 옆의 **세 번째 합치기 방식**으로 두는 것이 이 코드의 결에 맞는다 — 예: n번째 버프는 효과의 1/n 만 반영.
  `apply` 쪽에 두면 안 된다. 거는 시점에 효과를 깎아 저장하면 **버프가 하나 사라질 때 나머지를 다시 계산할 수 없다.**
  일반 규칙: 합성 결과는 **읽을 때 계산**하고, 저장은 원본 그대로.

- Q: 건 사람이 나가면 유지되나?
  A: (내 추론) 지금 모델에는 **건 사람이 없다** — `Buff` 는 kind·percent·시각만 갖는다. 그래서 이 질문에 답하려면 필드가 하나 늘어야 한다(`casterId`).
  정책은 게임마다 다르다(유지 / 즉시 해제 / 남은 시간 단축). 중요한 건 **모델에 없는 정보는 정책을 만들 수도 없다**는 것 — 요구가 오면 모델부터 바뀐다.

- Q: 서버 재시작 뒤 만료된 버프는?
  A: (내 추론) 저장소에서 불러올 때 `expire(now)` 를 한 번 돌리면 그만이다 — 이 모델은 **만료를 시각 비교로 판정**하므로 꺼져 있던 동안의 시간도 자동으로 반영된다.
  타이머로 만료를 구현했다면 이야기가 달라진다 — 꺼져 있는 동안 타이머가 안 돌아서 되살아난 버프가 영원히 산다.
  **시각을 저장하고 비교하는 설계가 재시작에 강한 이유가 여기다.**

#### 11. 연결

- Q: 세 규칙은 어디와 같은 자리인가?
  A: **쿠폰 중복 적용 정책**이다 — 같은 쿠폰을 두 장 쓸 수 있나(중첩), 새 쿠폰이 기존 것을 대체하나(갱신), 하나만 되나(무시).
  15-coupon·17-cart-discount 에서 같은 질문이 돈 모양으로 다시 나온다.

- Q: 더하기 vs 곱하기는?
  A: **단리 vs 복리**다. 20 %를 세 번 더하면 60, 세 번 곱하면 72.8 — 이자 계산과 같은 식이다.
  할인에서도 같다: 10 % + 10 % 를 40,000원에 적용할 때 "20 % 할인"과 "10 % 하고 또 10 %"는 8,000원과 7,600원으로 다르다.

- Q: 만료 미포함 규약은?
  A: 04(호텔 예약)·06(구독)·08(회의 슬롯) 과 같은 규약이다 — 테스트 javadoc 이 직접 짚어 놓았다.
  **구간은 `[시작, 끝)`** 이라는 한 가지 규약을 문제집 전체가 공유한다. 챕터마다 다르면 그 경계에서 사고가 난다.

- Q: `now` 를 인자로 받는 설계는?
  A: 시계를 **호출자가 주입**하므로 과거·미래 어느 시점이든 테스트할 수 있다. 200번 5분 간격 테스트가 실제로 1,000분을 기다리지 않는 이유다.
  내부에서 `Instant.now()` 를 읽으면 그 순간 테스트가 실제 시간에 묶인다 — 만료 관련 계약을 **검증할 방법 자체가 사라진다.**
