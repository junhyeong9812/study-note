## 한눈에 — 쉽게 말하면

**버프 중첩 = 같은 쿠폰을 또 내밀었을 때 가게가 어떻게 하느냐.**

- "공격력 20% 증가, 10분간" 버프가 이미 걸려 있는데 **같은 버프를 또 걸면** 어떻게 되나?\
  게임마다, 심지어 같은 게임 안에서도 버프마다 답이 다르다.

> **버프(buff)** — 게임에서 캐릭터를 일시적으로 강하게 해주는 효과.\
> 예: "공격력 20 % 증가, 10분간" 같은 것이고, 반대로 약하게 만드는 것은 디버프다.
- 답이 셋이다: **중첩**(둘 다 살아서 효과가 합쳐짐) / **갱신**(하나만 남고 시간이 다시 참) / **무시**(먼저 걸린 게 끝날 때까지 새것은 버려짐).
- 그리고 효과를 **합치는 방법**도 둘이다: 더하기(20+20=40%) vs 곱하기(1.2×1.2=1.44 → 44%).
- 두 개일 때는 40 vs 44로 4%p 차이라 아무도 신경 안 쓰지만, **열 개가 쌓이면 200 vs 519로 2.6배**다.

```text
  같은 버프가 또 들어오면?          효과는 어떻게 합치나?

  중첩(STACK)  : [20%][20%] 둘 다   더하기: 20+20      = 40%
  갱신(REFRESH): [20%] 시간 리필    곱하기: 1.2 × 1.2  = 44%
  무시(IGNORE) : [20%] 새것 버림              ↑ 쌓일수록 벌어진다
```

실무 예: 게임 버프/디버프 시스템, 할인 쿠폰 중복 적용 정책, 이자 계산(단리 vs 복리 — 더하기/곱하기와 똑같은 구조다).

## 문제 — 이 챕터가 시키는 것

원본 README가 말로 못 박은 요구사항 전부.

> "'공격력 20 퍼센트 증가, 10 분간.' **같은 버프를 또 걸면 어떻게 되나.**"
> "중첩 — 두 개가 다 살아 있다. 효과가 더해진다 / 갱신 — 하나만 남고 지속 시간이 다시 찬다 / 무시 — 먼저 걸린 것이 끝날 때까지 아무 일도 안 일어난다"
> "셋 다 실제 게임에서 쓰인다. **그리고 같은 게임 안에서도 버프마다 다르다.**"
> "`src/main/java/com/domain/buff/BuffBoard.java` 의 TODO 1~4. `Buff` 는 계약이라 다 주어져 있다."

과제 목록 — 채울 TODO 4개:

| TODO | 메서드 | 말로 된 요구 |
|---|---|---|
| 1 | `apply(buff, now)` | 버프를 건다. 실제로 걸렸으면 `true`. **만료 정리를 먼저** 하고 규칙을 적용(순서가 계약) |
| 2 | `expire(now)` | 만료된 버프를 걷어낸다 — 답은 안 바뀌고 메모리만 바뀐다 |
| 3 | `active(now)` | 지금 살아 있는 버프들 |
| 4 | `totalPercent(now, rule)` | 합쳐진 효과(퍼센트). 더하기 / 곱하기 |

테스트가 못 박은 계약:

- 만료 시각은 **미포함** — 09:00 적용 60초면 09:00:59 살아 있고 09:01:00 없다.\
  걸리기 전(09:00 이전)도 없다.
- 만료 뒤 `remainingAt` 은 **0**, 음수가 아니다.
- 잘못된 버프는 못 만든다: 효과 0 이하 · 지속 0 이하 · 종류 공백.
- STACK: 20 % 세 번 → 살아 있는 3개, 더하기 60. 60초 뒤에는 2개.
- REFRESH: 60초짜리 뒤에 300초짜리 → 1개, 더하기 20, 100초 뒤에도 1개.
- IGNORE: 30 % 뒤에 10 % → 두 번째가 **`false`**, 남은 것은 30 %, 60초 뒤엔 0개(시간도 안 늘었다).
- 종류가 다르면(atk/def) IGNORE 여도 둘 다 걸린다.
- 이미 만료된 버프는 IGNORE 에서 새것을 **안 막는다**.
- maxStacks 3 에 5번 걸면 3개, 남는 것은 **남은 시간이 긴 것들**. 새것이 가장 짧으면 새것이 `false`.
- maxStacks 0 이하는 생성자에서 거부.
- 20 % 두 개 → 더하기 `40`, 곱하기 `44.00`.
- 버프 0개 → 더하기 `0`, 곱하기 `0.00`(빈 곱 = 1, 1 빼서 0).
- 1분짜리를 5분마다 200번 → 살아 있는 1개이면서 `stored()` 도 **1**.

README가 미리 알려준 함정: ①만료를 먼저 걷어내고 규칙 적용(반대면 새 버프가 영영 안 걸리고, 그 버그는 시간이 지나야만 나타난다) ②무시 규칙은 `false` 반환이 계약 ③곱하기 초기값은 1(0이면 결과가 항상 0) ④상한에 걸렸을 때 **무엇을 버릴지도 규칙**(여기서는 남은 시간 최단).

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
말로 된 요구사항                          →  코드 구조
────────────────────────────────────────────────────────────
"버프 한 개 = 종류·효과·기간"             →  record Buff(kind, percent, appliedAt, expiresAt)
"잘못된 버프는 아예 못 만든다"             →  record 생성자 검증 (빈 종류·0 이하 효과·뒤집힌 기간 거부)
"같은 종류가 또 오면?"                    →  enum StackRule {STACK, REFRESH, IGNORE}
"효과를 어떻게 합치나?"                   →  enum CombineRule {ADDITIVE, MULTIPLICATIVE}
"무한정 쌓이면 안 된다"                   →  maxStacks 상한 + 버릴 대상 규칙(남은 시간 최단)
"만료된 버프가 새것을 막으면 안 된다"      →  apply()가 expire(now)를 먼저 호출 (순서가 계약)
"메모리가 새는지 밖에서 봐야 한다"         →  stored() (만료 포함 실제 보유 수)
```

## 규칙 1 — 중첩 규칙 3종 (StackRule)

**어떤 요구사항인가**: 같은 종류의 버프가 또 들어왔을 때 무엇이 남는가.
**종류(kind)가 다르면 서로 안 막는다** — 규칙은 같은 종류끼리만 적용된다.

**예시 입력**: 공격버프 30%가 걸려 있는데 공격버프 10%를 또 건다.

| 규칙 | 결과 | apply() 반환 |
|---|---|---|
| STACK | 30%와 10% 둘 다 산다 | true |
| REFRESH | 10%만 남는다 (갈아치움 — 30%가 사라진다!) | true |
| IGNORE | 30%만 남는다 (새것 버림) | **false** |

- **무시 규칙은 false를 돌려주는 것이 계약이다.**\
  반환값을 안 보면 화면에는 "버프 걸림!"이라고 알리고 실제로는 안 걸린 상태가 된다.
- **갱신 vs 무시의 함정**: 둘 다 "하나만 남는다"인데 결과가 다르다.\
  30% 위에 10%를 걸면 갱신은 **10이 남는다** — 갈아치우기 때문이다.\
  측정에서도 무시의 효과 합계(19,561)가 갱신(19,442)보다 오히려 조금 높았다.\
  "더 센 것만 갱신"이 필요하면 그것은 **네 번째 규칙**이다 — 규칙이 셋이 아니라 넷이 된다.
- 측정: 같은 이벤트열 1,000회에서 효과 합계가 중첩 58,913 vs 갱신 19,442 — **3배** 갈린다.\
  중첩/갱신은 938/1,000 회 다른 답.

**왜 이렇게 모델링했나**: 세 규칙을 if 분기로 흩뿌리지 않고 enum 하나로 이름 붙였다.
"이 버프는 무슨 규칙인가"가 생성자 인자 한 곳에 보이고, 새 규칙(넷째)이 와도 enum 값 추가로 자리가 정해진다.

## 규칙 2 — 효과 합치기 (CombineRule)

**어떤 요구사항인가**: 살아 있는 버프들의 총 효과는 몇 퍼센트인가.

**예시 입력**: 20% 버프 3개.
손계산:

```text
  더하기: 20 + 20 + 20            = 60%
  곱하기: 1.2 × 1.2 × 1.2 = 1.728 → 72.80%
```

| 개수 | 더하기 | 곱하기 |
|---|---|---|
| 1 | 20 | 20.00 |
| 2 | 40 | 44.00 |
| 5 | 100 | 148.83 |
| 10 | 200 | **519.17** |

- **곱하기의 초기값은 1이다.**\
  0으로 두면 무엇을 곱해도 0이다 (더하기의 초기값이 0인 것과 대비).
- 측정: 더하기와 곱하기는 **1,000/1,000 갈린다** — 버프가 둘 이상이면 반드시 다르기 때문.\
  합계 77,849 vs 103,080 (32% 차이). **구석 사례가 아니라 게임 설계의 축인데, 코드에서는 총합 내는 한 줄에 숨어 있다.**
- 구현은 BigDecimal로 계산하고 소수 둘째 자리 반올림 — 부동소수점 오차를 피한다.

> **BigDecimal** — 십진수를 오차 없이 다루는 자바 타입.\
> 예: 0.1 같은 값을 이진 소수(double)로 들면 미세한 오차가 생기는데, 그것을 피하고 반올림 자리를 직접 정하게 한다.

## 규칙 3 — 상한(maxStacks)과 버리기

**어떤 요구사항인가**: 곱하기 20%를 20번 걸면 3,733%가 된다 — 무한 중첩은 게임을 부순다.
그래서 상한이 필요한데, **상한에 걸렸을 때 무엇을 버릴지도 규칙이다.**

| 상한 | 더하기 | 곱하기 |
|---|---|---|
| 20 | 400 | **3,733.76** |
| 5 | 100 | 148.83 |
| 3 | 60 | 72.80 |

**곱하기와 상한은 하나의 결정이지 두 개가 아니다** — 곱하기를 고르는 순간 상한 없이는 못 산다.

**버리기 규칙 (impl)**: 상한에 걸리면 **남은 시간이 가장 짧은 것**을 버린다.
단, 새 버프의 남은 시간이 그것보다 길 때만 — 새것이 더 짧으면 새것을 버린다(false).

```text
  상한 2, 이미 [남은 5분][남은 3분] 상태에서 남은 10분짜리가 오면
    → 3분짜리를 버리고 10분짜리를 넣는다 (true)
  남은 1분짜리가 오면
    → 1분 < 3분 이므로 새것을 버린다 (false)
```

## 규칙 4 — 만료 정리 (expire)와 stored()

**어떤 요구사항인가**: 끝난 버프는 치워야 한다.
그런데 **언제** 치우느냐가 계약이다.

**apply()의 순서가 계약이다**: ① 만료된 것을 걷어낸다 → ② 중첩 규칙을 적용한다.
**반대로 하면 이미 끝난 버프 때문에 새 버프가 영영 안 걸린다** (IGNORE 규칙에서 만료된 버프가 sameKind로 잡혀서 false). 그리고 이 버그는 **시간이 지나야만 나타난다** — 버프 지속 시간 안에 도는 테스트는 절대 못 잡는다.

**변종 검증이 열어둔 것**: 만료 정리를 아예 지워도 **아무 테스트가 안 깨졌다.**
합계(totalPercent)와 목록(active)이 어차피 살아 있는 것만 걸러 보기 때문 — 답이 안 바뀌는 일이라 결과 테스트로는 못 잡는다.
그래서 `stored()`(만료 포함 실제 보유 개수)를 밖으로 열었다.

```text
  1분짜리 버프를 5분마다 200번 걸면 (매번 이전 것은 이미 만료)

    걷어내는 구현:   stored() = 1     ← 정상
    안 걷어내는 구현: stored() = 200   ← 오래 도는 캐릭터 하나가
                                        서버 메모리를 먹는 경로
```

## 경계·모서리 케이스

- **함정: 만료 "시각"에 아직 살아 있다고 보기** → 만료 시각에는 **이미 없다**. `isActiveAt`은 `now < expiresAt` (미포함 경계). 10:00에 만료면 10:00에는 죽어 있다.
- **함정: 곱하기 누적 초기값 0** → 결과가 항상 0. 초기값은 1(ONE)이다.
- **함정: apply 반환값 무시** → IGNORE 규칙에서 "걸었다"고 알리고 실제로는 안 걸린다.
- **함정: 잘못된 버프를 만들 수 있게 두기** → record 생성자가 거부한다: 빈 종류, 효과 ≤ 0, 만료가 적용보다 안 늦음.\
  상한 ≤ 0인 보드도 못 만든다.
- **함정: 만료된 버프가 새것을 막거나 상한 개수에 끼기** → expire 먼저, 그리고 상한 판정은 activeOf(살아 있는 같은 종류)로만 센다.

## 핵심 문장

- "같은 버프를 또 걸면?"의 답은 하나가 아니라 **셋이고(중첩·갱신·무시), 그것은 버그가 아니라 각각 이름 붙여야 할 규칙**이다 — enum 두 개(StackRule, CombineRule)가 이 도메인의 전부다.
- 더하기와 곱하기는 두 개일 때 4%p 차이지만 열 개면 2.6배다 — **쌓일수록 벌어지는 규칙은 총합 한 줄에 숨어 있어도 게임 설계의 축**이다.
- 곱하기를 고르는 순간 상한은 선택이 아니다 — **곱하기와 상한은 하나의 결정**이고, 상한에서 무엇을 버릴지도 규칙이다.
- "만료 걷어내기 → 규칙 적용" 순서가 계약이다 — 뒤집으면 죽은 버프가 새 버프를 막고, 그 버그는 시간이 지나야만 보인다.
- 답이 안 바뀌는 일(만료 정리)은 결과 테스트로 못 잡는다 — **관측 창(stored())을 따로 열어야** 메모리 누수를 검증할 수 있다.

## 용어 풀이

- **버프(buff)**: 캐릭터를 일시적으로 강화하는 효과.\
  종류(kind)·효과(percent)·기간(appliedAt~expiresAt)으로 표현.
- **중첩(STACK)**: 같은 종류를 또 걸면 둘 다 산다.\
  효과가 합쳐진다.
- **갱신(REFRESH)**: 하나만 남기고 새것으로 갈아친다.\
  지속 시간이 다시 차지만, 약한 새것이 센 옛것을 지울 수 있다.
- **무시(IGNORE)**: 이미 있으면 새것을 버린다.\
  apply가 false를 돌려주는 것이 계약.
- **더하기 합산(ADDITIVE)**: 퍼센트를 그냥 더한다.\
  20+20=40. 초기값 0.
- **곱하기 합산(MULTIPLICATIVE)**: 배율(1.2)끼리 곱한다.\
  1.2×1.2=1.44→44%. 초기값 1. 복리와 같은 구조.
- **상한(maxStacks)**: 같은 종류가 쌓일 수 있는 최대 개수.\
  곱하기와는 한 몸의 결정.
- **만료 미포함 경계**: 만료 시각 정각에는 이미 죽어 있다 (`now < expiresAt`).
- **stored()**: 만료된 것까지 포함해 실제로 들고 있는 개수.\
  메모리 누수 관측 창.
- **BigDecimal**: 십진수를 오차 없이 계산하는 타입.\
  퍼센트 곱셈의 반올림을 통제한다.
- **record 생성자 검증**: 잘못된 값(빈 종류, 0 이하 효과, 뒤집힌 기간)으로는 객체 자체를 못 만들게 하는 방식.
