### A. 과제 (Cart 의 TODO 1~3)

#### 1. 챕터 지문

- 침묵하는 결정 셋:

```text
"쿠폰을 여러 장 쓸 수 있다"  ← 요구사항은 여기까지만 말한다

  1. 순서       어느 할인을 먼저 적용하나          → Order  (AS_GIVEN|PERCENT_FIRST|AMOUNT_FIRST)
  2. 정률 기준   "10%" 는 무엇의 10% 인가          → Base   (ORIGINAL|RUNNING)
  3. 반올림 시점 매 단계 버리나 마지막에 한 번 하나 → boolean roundEachStep
```

- 안 정한 채 코드를 쓰면: **안 정한 게 되는 게 아니라 "모르고 정한" 게 된다.** 루프를 짜는 순간 순서가 생기고, `total` 이나 `remaining` 중 하나를 타이핑하는 순간 기준이 정해진다. 나중에 "우리 정책이 뭐였지"를 물으면 답이 문서가 아니라 코드 한 줄에만 있다.
- 이 챕터는 셋을 전부 **`apply` 의 매개변수(enum·boolean)로 끌어올렸다.** 호출자가 고르게 만든 것 — 그래야 정책이 눈에 보이는 값이 된다.
- 요구사항이 침묵하는 것이 더 있다:
  - 할인 합이 금액을 넘으면? → 0에서 멈춘다(음수 금지).
  - 정률에 상한이 있나? → `cap`. 실제 쿠폰엔 거의 항상 있다.
  - 정률끼리의 상대 순서가 화면 내역에 보이나? → 보인다(안정 정렬 필요).
  - 반올림 방식은 버림인가 반올림인가? → impl은 `RoundingMode.DOWN`(버림).

#### 2. TODO 1 — apply

정답 코드 (impl/Cart.java):

```java
List<Discount> sorted = new ArrayList<>(discounts);
if (order == Order.PERCENT_FIRST) {
    sorted.sort(Comparator.comparingInt(d -> d.kind() == Discount.Kind.PERCENT ? 0 : 1));
} else if (order == Order.AMOUNT_FIRST) {
    sorted.sort(Comparator.comparingInt(d -> d.kind() == Discount.Kind.AMOUNT ? 0 : 1));
}

List<Applied> applied = new ArrayList<>();
BigDecimal remaining = total;
for (Discount discount : sorted) {
    BigDecimal against = base == Base.ORIGINAL ? total : remaining;   // ★ 기준 결정이 이 한 줄
    BigDecimal deduction = discount.deductionFrom(against, remaining);
    if (roundEachStep) {
        deduction = deduction.setScale(0, RoundingMode.DOWN);
    }
    applied.add(new Applied(discount.name(), deduction));
    remaining = remaining.subtract(deduction);
}
return applied;
```

- 돌려주는 것은 **내역(`List<Applied>`)** 이다. 금액만 돌려주면 화면에 "10% 쿠폰 −1,000원 / 1,000원 쿠폰 −1,000원"처럼 줄줄이 보여줄 수가 없다. **총액은 내역에서 만들 수 있지만 내역은 총액에서 못 만든다.**
- 복사하는 이유: `sort` 는 리스트를 **제자리에서 바꾼다.** 호출자가 넘긴 리스트를 뒤집어버리면 계산 함수가 남의 데이터를 망가뜨리는 것이고, 불변 리스트(`List.of`)면 예외가 난다.
- `comparingInt(정률이면 0 아니면 1)` 이 안정 정렬이 되는 이유: **자바의 `List.sort` 자체가 안정 정렬(TimSort)** 이고, 비교 키가 0/1 두 값뿐이라 **같은 종류끼리는 전부 "같음"으로 판정되어 원래 순서가 그대로 유지**된다. 종류로만 가르고 그 안은 건드리지 않는 설계다.
- 안정 정렬이 아니면: 정률 A·정액 C·정률 B 를 PERCENT_FIRST 로 정렬했을 때 A·B 가 뒤집혀 **내역이 B, A, C 로 찍힌다.** 결제 금액은 같은데(정률끼리는 곱셈이라 교환법칙) 손님이 보는 화면만 매번 달라진다 — 재현 안 되는 CS 문의가 된다. 테스트 `stableWithinKind` 가 A, B, C 를 단언한다.
- `against`(기준)와 `remaining`(잔액)의 역할:

```text
against   = 정률을 "몇 %" 적용할 대상 금액.  ORIGINAL 이면 total, RUNNING 이면 remaining
remaining = 지금 남은 낼 금액.               깎을 금액을 여기까지만 자른다(음수 방지)

→ ORIGINAL 일 때 둘이 서로 다른 값이 된다. 그게 "원가 기준"의 정체다.
```

- 버림은 **깎을 금액(deduction)에** 한다. 잔액에 하지 않는다 — 그래야 내역의 각 줄이 정수가 되고 화면에 그대로 찍힌다.
- `RoundingMode.DOWN`(버림)을 **깎는 금액에** 적용하면 할인이 줄어드니 **회사에 유리**하다. 테스트 수치가 그것을 보여준다 — 10,001원에 10% 두 장이면 매 단계 버림 **8,101원**, 마지막 한 번 **8,100원**. 손님이 1원 더 낸다.
  - ⚠️ 원본 테스트 javadoc은 "매 단계 버리면 손님에게 유리하고 회사는 그만큼 덜 받는다"라고 쓰는데, **같은 테스트의 단언값과 방향이 반대다.** 수치(8,101 > 8,100)를 믿는다. (원본 주석의 오기로 보임 — 내 판단)
- 잔액 갱신을 버림 **전에** 하면: 내역에는 버림한 정수(1,000)가 찍히는데 잔액은 소수(1,000.1)를 뺀 값이 되어, **내역의 합과 "원가 − 낼 금액"이 어긋난다.** 테스트 `lineItemsSumToTotal` 이 깨진다. 코드가 `applied.add` 뒤에 `remaining.subtract(deduction)` 를 두고 **같은 값**을 쓰는 것이 핵심이다.

#### 3. TODO 2·3 — payable 과 totalDeduction

정답 코드:

```java
public static BigDecimal payable(...) {
    BigDecimal remaining = total;
    for (Applied applied : apply(total, discounts, order, base, roundEachStep)) {
        remaining = remaining.subtract(applied.deduction());
    }
    return remaining.setScale(0, RoundingMode.DOWN);
}

public static BigDecimal totalDeduction(...) {
    BigDecimal sum = BigDecimal.ZERO;
    for (Applied applied : apply(total, discounts, order, base, roundEachStep)) {
        sum = sum.add(applied.deduction());
    }
    return sum.setScale(0, RoundingMode.DOWN);
}
```

- 둘 다 **`apply` 를 다시 부른다.** 계산 논리를 한 곳(`apply`)에만 두는 게 맞다 — 따로 계산하면 두 벌의 규칙이 생기고 언젠가 갈라진다. (대가는 중복 계산인데, 이 정도 크기에선 싸다.)
- 마지막 `setScale(0, DOWN)`: `roundEachStep=false` 면 깎는 금액에 소수가 남는다. **손님에게 청구하는 숫자는 결국 정수여야** 하므로 출구에서 한 번 자른다. 이게 "마지막에 한 번 반올림"의 실체다.
- `payable + totalDeduction == total` 은 **언제나 성립하지 않는다.**

```text
10,001 원, 10% 두 장(RUNNING), roundEachStep = false

  깎을 금액  1,000.1 + 900.09 = 1,900.19
  payable        = (10,001 - 1,900.19) = 8,100.81 → 버림 → 8,100
  totalDeduction = 1,900.19            → 버림 → 1,900
                                          합 = 10,000  ≠ 10,001   ← 1원이 사라진다

roundEachStep = true 면 각 줄이 정수라 8,101 + 1,900 = 10,001  ← 언제나 맞는다
```

이것이 README가 말한 "반올림은 정해도 내역과 합계가 안 맞는다"의 정확한 모습이다.

- 음수를 막는 곳은 이 둘이 **아니다.** `Discount.deductionFrom` 의 `raw.min(remaining)` 한 줄이다. 방어선을 값이 만들어지는 자리에 두었다.

#### 4. 계약으로 주어진 Discount

- 자르는 순서(상한 먼저 / 잔액 나중)를 **뒤바꿔도 결과는 같다.** 둘 다 "더 작은 쪽을 고르는(min)" 연산이고, min 은 순서를 바꿔도 같기 때문이다 — `min(min(raw, cap), remaining) == min(min(raw, remaining), cap)`.
- `cap == 0` 이 "상한 없음": **0이라는 정상값을 특별한 뜻으로 쓰는 것**이 위험이다. "상한 0원(= 한 푼도 안 깎음)" 쿠폰을 표현할 방법이 사라진다. 제대로 하려면 `Optional<Integer>` 나 `Integer cap` (null = 없음), 또는 별도 플래그다. (원본에 근거 없음 — 내 추론)
- `raw.min(remaining)` 이 막는 사고: **결제 금액이 음수가 되어 손님에게 돈을 주는 것.** 그리고 그 음수는 정산까지 흘러가면 어디서 생겼는지 못 찾는다(README 함정 1).
- 잘못된 값은 **`Discount` 의 compact 생성자**에서 막힌다 — 빈 이름 / `value <= 0` / PERCENT인데 `value > 100` / `cap < 0` 전부 `IllegalArgumentException`. 테스트 `invalidDiscount` 가 네 가지를 전부 단언한다. **잘못된 객체가 애초에 태어나지 못하게** 하는 것 — 16번에서 체크섬을 "만드는 자리에서 막는" 것과 같은 자세다.
- `BigDecimal` 인 이유: `double` 은 이진 소수라 `0.1` 조차 정확히 못 담는다. 돈은 십진 단위로 딱 떨어져야 하고, 무엇보다 **`BigDecimal` 은 나눗셈·반올림에서 `RoundingMode` 를 명시하도록 강제**한다 — 즉 "반올림 시점"이라는 이 챕터의 결정 3을 언어가 대놓고 묻게 만든다.

### B. 개념

#### 5. 측정 하나 — 적용 순서

| | 1,000건 합계 |
|---|---|
| 정률 먼저 | 37,294,681 원 |
| 정액 먼저 | **38,012,592 원** |

- **706/1,000 이 갈리고**, 합계 차이 **717,911원**(약 72만), 최대 차이 **4,300원**, 건당 평균 **718원**.
- 손님에게 유리한 쪽은 **정률 먼저**(8,000 < 8,100). 이유: 정액을 먼저 빼면 정률이 **이미 작아진 금액에** 붙어서 깎이는 액수가 준다.
- `AS_GIVEN` 이 위험한 기본값인 이유: **정한 것처럼 보이지만 정하지 않은 것**이다. 실제 순서는 목록을 만든 코드 — 보통 **DB 조회 순서** — 가 정한다. 인덱스가 바뀌거나 정렬 절이 추가되면 **정책이 아무도 모르게 바뀐다.**

#### 6. 측정 둘 — 정률의 기준

| | 1,000건 합계 |
|---|---|
| 원가 기준(ORIGINAL) | 35,921,980 원 |
| 누적 기준(RUNNING) | **37,659,474 원** |

- 차이 **1,737,494원**(약 174만) — **순서 결정(72만)의 두 배가 넘는다.**
- "더 조용하다": 순서는 화면에서 "어느 쿠폰을 먼저 쓸까요"라고 **물어보기라도 한다.** 기준은 아무도 안 묻는다 — 기획서에도, 화면에도, 회의에도 안 나온다.
- 코드에서의 차이는 단어 하나:

```java
BigDecimal against = base == Base.ORIGINAL ? total : remaining;
//                                           ^^^^^   ^^^^^^^^^
//                                    이 한 단어가 174만 원을 가른다
```

- 수식:

```text
ORIGINAL (더하기)   total × (1 - a - b)      할인끼리 독립. 10%+10% = 20% 할인
RUNNING  (곱하기)   total × (1-a) × (1-b)    뒤 할인이 작아짐. 0.9 × 0.9 = 0.81 → 19% 할인

10,000 원 · 10% 두 장
  ORIGINAL   1,000 + 1,000 = 2,000  →  8,000
  RUNNING    1,000 +   900 = 1,900  →  8,100
```

- 12번 게임 버프의 **가산(additive) vs 승산(multiplicative) 중첩**이 도메인만 바꿔 그대로 나온 것이다.
- 원가 기준에 60% 두 장 = 120%:

```text
ORIGINAL  6,000 깎고 잔액 4,000 → 다음도 6,000 을 깎으려는데 잔액이 4,000
          → min(6,000, 4,000) = 4,000 만 깎는다  →  결제 0 원 (공짜)
RUNNING   6,000 깎고 잔액 4,000 → 4,000 의 60% = 2,400  →  결제 1,600 원
```

원가 기준은 **합이 100%를 넘을 수 있고**, 그때 `min(remaining)` 이 일해서 0에서 멈춘다.

#### 7. 측정 셋 — 반올림 시점

- **351/1,000 이 갈리는데 총액 차이는 391원**, 건당 **1.1원**. 앞의 두 결정에 비하면 돈으로는 아무것도 아니다.
- 그런데 회계에서 문제가 되는 것은 이쪽이다. **순서와 기준은 정하면 끝**이다 — 어느 쪽을 골라도 계산은 일관되게 맞는다. **반올림은 정해도 내역과 합계가 안 맞는다**(위 §3의 10,000 ≠ 10,001).
- 안 맞는 것: **화면에 줄마다 찍힌 할인액의 합**과 **아래에 찍힌 총 할인액**(또는 원가 − 결제액). 손님이 계산기를 두드리면 바로 보인다.
- 매 단계 버림을 고르면 **각 줄이 정수 → 줄들의 합 = 총 할인액이 언제나 성립**한다(테스트 `lineItemsSumToTotal`).
- 우선순위 교훈: **금액이 큰 결정(기준 174만 > 순서 72만)과 시끄러운 결정(반올림 391원)이 다르다.** 돈 크기로만 우선순위를 매기면 반올림을 끝까지 안 정하고, 그러다 회계팀 항의로 되돌아온다. 두 축(금액·소음)을 따로 봐야 한다.

#### 8. 측정 넷 — 할인이 하나면 세 결정이 전부 사라진다

| 결정 | 할인이 하나일 때 |
|---|---|
| 순서 | 적용할 것이 하나라 의미가 없다 |
| 기준 | 원가와 잔액이 같다(`total == remaining`) |
| 반올림 | 한 번뿐이라 시점이라는 게 없다 |

- 1,000건 **전부에서 여섯 가지 조합이 같은 답**을 낸다.
- 테스트 설계 교훈: **경계는 "둘 이상"에서만 드러난다.** 할인 하나짜리 테스트를 아무리 많이 써도 이 챕터의 문제는 통째로 안 보인다 — 초록불이 아무것도 보장하지 않는 대표 사례다.
- 15번 쿠폰의 "조건 하나"와 같은 자리: 거기서도 조건이 하나면 **조건들 사이의 상호작용**(순서·우선순위)이 사라져서 진짜 버그가 안 잡힌다. 구조가 같다.

#### 9. 측정 다섯 — 정률끼리는 합계가 같고 내역이 다르다

```text
10,000 원에 10% 와 20% (누적 기준)

  0.9 × 0.8 = 0.72        어느 순서든 7,200 원   ← 곱셈의 교환법칙
  10% 먼저   내역 1,000 원과 1,800 원
  20% 먼저   내역 2,000 원과   800 원
```

- 결제 금액이 같은 이유: 누적 기준의 정률은 **곱셈**이고 곱셈은 순서를 바꿔도 결과가 같다.
- 반쪽만 맞은 이유: **손님이 보는 화면이 달라진다.** "10% 쿠폰으로 1,000원 아꼈다"와 "10% 쿠폰으로 1,800원 아꼈다"는 다른 이야기고, 부분 취소·환불 때 줄 단위 금액이 그대로 쓰이면 **돈 문제가 된다.**

#### 10. 생각해볼 것 (원본 README 이관 — 답은 원본에 없다, 아래는 내 추론)

- 무료 배송은 **세 번째 종류**다. 상품 금액을 깎는 게 아니라 **다른 항목(배송비)을 0으로 만드는 것**이라, `total` 에 대한 정액/정률 어느 쪽으로도 깔끔하게 안 들어간다. 게다가 18번(배송비)에서 보듯 배송비는 "할인 후 금액"으로 무료 기준을 판정하므로 **순환이 생긴다** — 할인이 배송비를 정하고 배송비가 할인 대상이 되는 구조. 그래서 별도 축으로 모델링하는 게 맞다.
- 상품별 배분: **22번(정산)과 같은 문제다.** 장바구니 전체에 붙은 1,000원 할인을 상품 3개에 나눌 때 나머지 1원이 남고, 그 1원을 누구에게 줄지 규칙(최대 잔여법·첫 줄 몰아주기 등)이 필요하다. 부분 취소 때 "이 상품에 붙었던 할인"을 되돌려야 하므로 **배분 결과를 저장해 둬야** 한다 — 재계산하면 값이 달라진다.
- 손님에게 가장 유리한 순서 자동 선택: 계산은 쉽다(조합이 몇 개 안 된다). 문제는 **설명이다.** 같은 쿠폰 두 장을 쓴 두 주문의 적용 순서가 달라 보이고, "왜 저 사람은 저 순서로 됐냐"에 답해야 한다. 또 **쿠폰 정책을 바꾸면 과거 주문의 최적 순서가 달라져** 재현이 안 된다. 그래서 실무에선 보통 고정 순서를 쓰고 그 순서를 공개한다.
- 기준을 쿠폰마다 다르게 두면: **순서가 훨씬 더 중요해진다.** 모든 쿠폰이 RUNNING 이면 정률끼리는 순서 무관(교환법칙)인데, 한 장은 ORIGINAL 이고 한 장은 RUNNING 이면 그 교환법칙이 깨져서 **정률끼리도 순서로 금액이 갈린다.** 결정 둘이 서로 곱해져 경우의 수가 폭발한다.

#### 11. 연결

- 16번과 같은 것: **"지문 한 줄에 안 들어 있는 결정"이 진짜 과제다.** 16번은 그게 null 처리·자리 번호 시작점·검사 순서였고, 17번은 순서·기준·반올림이다. 둘 다 "코드를 쓰는 순간 정해진다"는 점이 같다.
- 18번으로 흘러드는 것: **할인 후 결제 금액**이 배송비의 무료 기준(예: 30,000원 이상 무료) 판정 입력이 된다. 그래서 여기서 어느 기준을 골랐느냐가 **배송비가 붙느냐 마느냐**까지 바꾼다 — 100원 차이가 3,000원 배송비를 가르는 자리가 생긴다.
- 22번에서의 재등장: 여기의 "내역과 합계가 안 맞는다"가 정산에서는 **"가맹점별 분배액의 합이 총 정산액과 안 맞는다"** 로 나타난다. 같은 반올림 잔돈 문제이고, 해법도 같다 — 어느 한 줄에 잔돈을 몰아주고 그 규칙을 명시하는 것.
