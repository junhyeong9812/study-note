# domain-modeling/basic/17-cart-discount — 정리 (힌트)

## 해결하는 문제

"10% 쿠폰과 1,000원 쿠폰을 둘 다 쓸 수 있다" — 요구사항은 여기서 끝난다.\
그런데 코드를 한 줄이라도 쓰는 순간 순서·정률의 기준·반올림 시점이 **어느 쪽으로든 정해진다.**

```text
요구사항이 말한 것          코드가 정해야 하는 것            갈리는 돈(1,000건)
+-----------------+       +---------------------------+
| 10% 쿠폰        |  -->  | 순서:  정률 먼저? 정액 먼저?  |   72만 원
| 1,000원 쿠폰    |       | 기준:  원가? 깎인 잔액?       |  174만 원
| 둘 다 쓸 수 있다 |       | 반올림: 매 단계? 마지막 한 번? |   391원 (회계 항의)
+-----------------+       +---------------------------+
```

이 결정들을 그대로 두면 **DB 조회 순서나 변수 이름 하나(`total` vs `remaining`)가 정책이 된다.**\
아무도 모르는 사이에 정해진 정책은 인덱스가 바뀌는 날 함께 바뀐다.\
쉬운 예: 세일 스티커 두 장을 어느 순서로 붙이느냐로 값이 달라진다.\
똑같은 구조다: 숨은 결정을 `Order`·`Base`·`roundEachStep` 매개변수로 끌어올려 호출자가 고르게 한다.\
실무 예: 쇼핑몰 쿠폰 중복 적용, 카드 청구할인 + 상품 할인, 통신비 결합 할인 — 모두 "여러 할인의 합성 규칙"을 어딘가에 명시해야 한다.

### 한눈에 — 쉽게 말하면

**장바구니 할인 = 세일 스티커 두 장을 어느 순서로 붙이느냐 문제.**

- 만 원짜리 물건에 "10% 할인" 스티커와 "1,000원 할인" 스티커를 둘 다 붙인다고 하자.\
  **어느 걸 먼저 계산하느냐에 따라 값이 달라진다** — 10%를 먼저 하면 8,000원, 1,000원을 먼저 빼면 8,100원.
- 100원 차이인데, **그 100원이 어느 쪽인지는 어떤 문서에도 안 적혀 있다.**\
  요구사항은 "10% 쿠폰과 1,000원 쿠폰을 둘 다 쓸 수 있다"까지만 말한다.
- 이 챕터가 보여주는 것: 요구사항이 침묵하는 결정이 **셋**(순서·기준·반올림) 있고, 셋 다 최종 금액을 바꾸며, 코드를 쓰는 순간 **어느 한쪽으로든 정해진다.**\
  안 정한 게 아니라 모르고 정한 게 된다.

```text
10,000 원 + [10% 쿠폰] + [1,000원 쿠폰]

  정률 먼저   10,000 ─10%→ 9,000 ─1,000→ 8,000
  정액 먼저   10,000 ─1,000→ 9,000 ─10%→ 8,100   ← 100 원 차이
```

> **정률 할인(percent)** — "10%"처럼 비율로 깎는 할인. 몇 %를 어디에 곱할지 기준 금액이 있어야 한다.\
> 예: 10,000원에 붙으면 1,000원이 깎이지만, 이미 9,000원으로 줄어든 금액에 붙으면 900원만 깎인다.

> **정액 할인(amount)** — "1,000원 할인"처럼 고정 금액으로 깎는 할인. 기준 금액이 필요 없다.\
> 예: 장바구니가 10,000원이든 50,000원이든 1,000원 쿠폰은 1,000원을 깎는다.

실무 예: 쇼핑몰 쿠폰 중복 적용, 카드사 청구할인+상품 할인, 게임의 버프 중첩(12번과 같은 구조).

## 동작·원리

### 전체 흐름

```text
요구사항에 안 적히는 결정 셋 → 전부 enum/boolean 매개변수로 끌어올렸다

  Order  (순서)      AS_GIVEN | PERCENT_FIRST | AMOUNT_FIRST
  Base   (정률 기준)  ORIGINAL(원가) | RUNNING(그때까지 깎인 금액)
  roundEachStep      true(매 단계 버림) | false(마지막에 한 번)

Discount (계약, 전부 주어짐)  name / kind(PERCENT|AMOUNT) / value / cap(정률 상한, 0=없음)
  deductionFrom(base, remaining) = 계산 → cap 으로 자르고 → remaining 으로 자른다(음수 방지)

Cart.apply(total, discounts, order, base, roundEachStep)
  [1] 순서 규칙대로 정렬 (★안정 정렬)
  [2] 할인마다: 기준 금액 정하기(원가? 잔액?) → 깎을 금액 → (옵션) 버림 → 잔액 갱신
  → 적용 내역 List<Applied> (화면에 줄줄이 보여줄 것)
```

**설계의 핵심**: 숨은 결정을 코드 깊숙이 묻지 않고 **호출자가 고르는 값**으로 올렸다.\
그래야 "우리 정책이 뭐냐"가 코드 한 줄이 아니라 눈에 보이는 설정이 된다.

### 결정 1 — 적용 순서: 100원이 갈린다

**요구사항 문장**: "쿠폰을 여러 장 쓸 수 있다." (순서는 말 안 해준다)

손계산 — 10,000원, 10% + 1,000원 (누적 기준):

```text
PERCENT_FIRST   10,000 → -1,000(10%) → 9,000 → -1,000 → 8,000   손님에게 유리
AMOUNT_FIRST    10,000 → -1,000      → 9,000 → -900(10%) → 8,100  회사에 유리
```

- 정액을 먼저 빼면 정률이 **작아진 금액에** 붙어서 할인이 준다.\
  그래서 정률 먼저가 손님 유리.
- `AS_GIVEN`은 "정하지 않은 것"이다 — 목록을 만든 코드(보통 DB 조회 순서)가 순서를 정하게 된다.\
  가장 위험한 기본값.
- 정렬은 **안정 정렬**이어야 한다.\
  정률 A, 정액 C, 정률 B를 "정률 먼저"로 정렬하면 A,B,C — A와 B의 순서가 안 뒤집혀야 한다.\
  정률끼리는 곱셈이라 결과는 같지만(교환법칙) **화면에 찍히는 내역 순서가 바뀐다.**

> **안정 정렬(stable sort)** — 정렬 키가 같은 원소들의 원래 앞뒤 순서가 그대로 유지되는 정렬.\
> 예: 정률 A·정액 C·정률 B 를 "정률 먼저"로 정렬하면 A·B 가 뒤집히지 않고 A, B, C 가 된다.

측정(원본 README): 1,000건에서 706건이 갈리고, 합계 차이 **717,911원**(37,294,681 vs 38,012,592), 최대 4,300원, 건당 평균 718원.

### 결정 2 — 정률의 기준: 순서보다 두 배 크고, 더 조용하다

**요구사항 문장**: "10% 할인." (무엇의 10%인지 말 안 해준다)

손계산 — 10,000원에 10% 두 장:

```text
ORIGINAL(원가 기준)   1,000 + 1,000 = 2,000 할인  → 8,000   할인끼리 독립 = 더하기
RUNNING (누적 기준)   1,000 +   900 = 1,900 할인  → 8,100   뒤 할인이 작아짐 = 곱하기(0.9×0.9)
```

- 12번 게임 버프의 "가산 vs 승산"이 여기서 다시 나온다 — 같은 수학 구조.

> **가산 중첩 / 승산 중첩** — 효과 여럿을 더해서 겹치느냐(가산), 곱해서 겹치느냐(승산).\
> 예: 10% 두 장이 가산이면 20% 할인(8,000원)이고, 승산이면 0.9×0.9 = 19% 할인(8,100원)이다.

- 원가 기준은 합이 100%를 넘을 수 있다: 60% 두 장 = 120% → 6,000+6,000을 깎으려는데 잔액이 4,000뿐.\
  **잔액을 넘지 않게 자르는 규칙**(`min(remaining)`)이 여기서 일해서 0원에서 멈춘다.\
  누적 기준은 6,000+2,400=8,400 할인 → 1,600원. 공짜가 되느냐 마느냐가 갈린다.
- 측정: 1,000건 합계 차이 **1,737,494원**(35,921,980 vs 37,659,474) — **순서 결정의 두 배가 넘는다.**\
  그런데 순서는 "어느 쿠폰 먼저?"라고 묻기라도 하지, 기준은 아무도 안 묻는다.\
  **코드에서 `total`을 쓰느냐 `remaining`을 쓰느냐 한 단어 차이다.**

### 결정 3 — 반올림 시점: 금액은 작고 소리는 크다

**요구사항 문장**: (아예 없음 — 소수점이 생긴다는 것 자체를 요구사항은 모른다)

손계산 — 10,001원에 10% 두 장(누적 기준):

```text
매 단계 버림    1,000.1→1,000 깎고 9,001 / 900.1→900 깎고 → 8,101
마지막에 한 번  1,000.1 깎고 9,000.9 / 900.09 깎고 8,100.81 → 버림 → 8,100
```

- 1원 차이.\
  측정: 1,000건 중 351건이 갈리는데 총액 차이는 **391원**(건당 1.1원).\
  앞의 두 결정에 비하면 돈으로는 아무것도 아니다.

> **버림(RoundingMode.DOWN)** — 소수점 아래를 반올림하지 않고 그냥 잘라내는 것.\
> 예: 1,000.1원 깎을 차례에 버림하면 1,000원만 깎는다.

- **그런데 회계에서 시끄러운 건 이쪽이다.**\
  매 단계 버리면 내역의 각 줄이 정수라서 "줄들의 합 = 총 할인액"이 언제나 성립하고 화면에 그대로 보여줄 수 있다.\
  마지막에 한 번 하면 내역과 합계가 안 맞을 수 있다 — 손님이 계산기를 두드리는 순간이다.
- **금액이 큰 결정(기준·순서)과 시끄러운 결정(반올림)이 다르다** — 우선순위를 금액만으로 매기면 틀린다.

## 쓰이는 자료구조·알고리즘

- **안정 정렬(stable sort)** — `Order`가 `PERCENT_FIRST`면 종류로만 정렬하고 같은 종류끼리는 준 순서를 지켜야 한다. Java `List.sort`·`Collections.sort`는 병합 정렬 계열(TimSort)이라 안정이다 — [algorithm/02-merge-sort](../../../algorithm/02-merge-sort/2-summary.md). 일반적인 제자리 퀵 정렬·힙 정렬은 안정이 아니다.
  - *안정 정렬*: 정렬 키가 같은 원소의 원래 앞뒤 순서가 유지되는 정렬.
- **접기(fold, 누적 순회)** — 할인 목록을 앞에서부터 하나씩 적용하며 `remaining`을 갱신한다. 리스트 한 번 순회 O(n). 순서가 결과를 바꾸므로 병렬로 나눌 수 없다.
- **십진 소수(`BigDecimal`)와 반올림 모드** — 정률 계산은 소수가 생긴다. `double`은 이진 소수라 0.1을 정확히 못 담는다. `BigDecimal`은 십진 값을 그대로 들고 있다가, 원본처럼 `setScale(0, RoundingMode.DOWN)`을 **적은 자리에서만** 반올림한다(나누어떨어지지 않는 `divide`는 반올림 모드를 안 주면 예외를 던진다).
- **클램프(clamp, 상·하한 자르기)** — `deductionFrom`의 `min(cap)`·`min(remaining)`. 두 줄이 "정률 폭발"과 "음수 결제"를 막는 불변식이다.
- **가산 vs 승산 중첩** — `ORIGINAL`은 `total × (1 − a − b)`(더하기), `RUNNING`은 `total × (1−a)(1−b)`(곱하기). [12-game-buff](../12-game-buff/2-summary.md)의 버프 중첩과 같은 수학이다.
- **적용 내역(`List<Applied>`) = 감사 로그** — 결과 금액만이 아니라 줄 단위 기록을 남긴다. 부분 취소·환불이 이 줄을 다시 읽는다.

## 적용 — 풀어나가는 법

할인이 둘 이상 겹치는 도메인(쿠폰·청구할인·결합 할인)을 받으면 이 챕터의 세 결정을 **먼저 표로 적고** 코드를 쓴다.\
① 요구사항에서 침묵하는 결정을 찾는다(순서·기준·반올림) → ② 각 결정을 enum/boolean 매개변수로 올려 정책이 눈에 보이게 한다 → ③ 결정마다 손계산 한 줄(10,000원 + 10% + 1,000원)을 테스트로 못 박는다 → ④ 할인 **둘 이상**으로만 경계를 시험한다 → ⑤ 갈리는 금액(측정)과 시끄러움(회계)을 따로 보고 우선순위를 정한다.\
아래 문제 절이 이 순서를 TODO 1~3으로 시킨 것이다.

### 문제 — 이 챕터가 시키는 것

원본 README가 시키는 것은 이 말 몇 줄이 전부다.

> 10,000 원에 **"10 퍼센트"** 와 **"1,000 원 할인"** 을 적용하면 얼마인가.
> 정률 먼저 `10,000 → 9,000 → 8,000` / 정액 먼저 `10,000 → 9,000 → 8,100`.
> **100 원 차이다. 그리고 그 100 원이 어느 쪽인지는 아무 문서에도 없다.**
> 정할 것이 셋이다. **순서**, **정률의 기준**, **반올림 시점**. 셋 다 요구사항에 안 적힌다.

과제 목록:

- `src/main/java/com/domain/cart/Cart.java` 의 **TODO 1~3** 을 채운다.
  - TODO 1 `apply(total, discounts, order, base, roundEachStep)` — 할인을 순서대로 적용해 **적용 내역(`List<Applied>`)** 을 낸다.\
    javadoc: "순서 규칙이 AS_GIVEN 이면 준 순서 그대로 쓴다. 정렬할 때는 **안정 정렬**이어야 같은 종류끼리의 순서가 유지된다."
  - TODO 2 `payable(...)` — 적용 후 낼 금액.
  - TODO 3 `totalDeduction(...)` — 총 할인액.
- `Discount`(정률/정액·값·상한 cap)와 `Order`·`Base` enum 은 **계약이라 전부 주어져 있다**.\
  깎는 금액을 `cap` 과 `remaining` 으로 자르는 `deductionFrom` 도 이미 있다.

> **계약(contract)** — 함수·타입이 "이런 입력에는 이렇게 답한다"고 밖에 약속해 둔 내용. 구현하는 쪽이 마음대로 못 바꾼다.\
> 예: `Discount`·`Order`·`Base` 는 이미 다 주어져 있고, 내가 채우는 것은 그 약속을 쓰는 `Cart` 의 TODO 세 개뿐이다.

- 테스트가 못 박은 계약: 10,000원+10%+1,000원 → **PERCENT_FIRST 8,000 / AMOUNT_FIRST 8,100** · 10,000원+10%×2 → **ORIGINAL 8,000 / RUNNING 8,100** · 60%×2 → **ORIGINAL 0원 / RUNNING 1,600원** · 10,001원+10%×2 → **매 단계 버림 8,101 / 마지막 한 번 8,100** · 8,000+5,000 쿠폰이어도 **낼 금액 0원(음수 금지), 총 할인액도 10,000 초과 금지** · 50,000원에 "20%, 상한 1,000" → 49,000 · 정률A·정액C·정률B를 PERCENT_FIRST 로 정렬하면 내역 순서 **A, B, C**(안정 정렬) · 매 단계 버림이면 **내역의 합 == 총 할인액**.

## 장애 시나리오와 대처

**1. 인덱스 하나 바꿨는데 결제 금액이 달라진다 — `AS_GIVEN`의 정체**

- 현상: 배포도 정책 변경도 없었는데 어느 날부터 같은 쿠폰 조합의 결제 금액이 100원씩 달라진다.
- 보이는 형태: 주문 금액 검증 테스트가 간헐적으로 깨진다. 같은 쿠폰 두 장을 쓴 두 주문의 적용 내역 순서가 다르다. DB 실행 계획이 바뀐 시점과 일치한다.
- 원인: `Order.AS_GIVEN`으로 두고 쿠폰 목록을 `ORDER BY` 없이 읽었다. 순서를 정한 주체가 코드가 아니라 **DB 조회 순서**였다(정답 5번 참고).
- 대처: `AS_GIVEN`을 기본값에서 제거하고 정책 enum을 명시적으로 넘긴다. 목록을 읽는 쿼리에도 결정적 정렬(발급 순·쿠폰 ID)을 건다. 회귀 테스트는 정렬 없는 목록을 섞어 넣어 결과가 같은지 본다.

**2. 정률 상한이 없는 쿠폰이 대형 주문에서 폭발**

- 현상: 프로모션 첫날 고가 주문 몇 건에서 할인액이 상품 가격의 대부분을 먹는다.
- 보이는 형태: 정산 리포트에서 특정 쿠폰의 할인 총액이 예산의 수십 배. 개별 주문 내역에 "20% → 200,000원 할인" 같은 줄이 찍힌다.
- 원인: `Discount.cap = 0`(상한 없음)으로 발급했다. 정률은 장바구니가 비쌀수록 절대액이 커진다.
- 대처: 쿠폰 발급 화면에서 정률에는 상한을 **필수**로 받는다(생성자에서 검증). 이미 발급된 것은 정책 테이블에 상한을 소급 적용할지 사용자 합의 후 결정한다.

**3. 부분 취소 때 줄 단위 할인액이 재계산돼 환불액이 달라진다**

- 현상: 상품 하나만 취소했더니 환불 금액이 원래 그 상품에 붙었던 할인액과 다르다.
- 보이는 형태: 결제 당시 내역은 "10% 쿠폰 1,000원 + 20% 쿠폰 1,800원"인데, 환불 계산은 "2,000원 + 800원"으로 나온다(정률끼리 순서가 뒤집혀 합계는 같고 내역만 다름).
- 원인: 환불 시점에 할인을 **다시 계산**했다. 정책(`Order`·`Base`)이 같아도 입력 목록의 순서가 다르면 내역은 달라질 수 있고, 정책이 그 사이 바뀌면 합계도 달라진다.
- 대처: 결제 시점의 `List<Applied>`를 **저장**하고, 환불은 저장된 줄을 읽어 되돌린다. 상품별 배분 규칙은 [22-settlement](../22-settlement/2-summary.md)의 잔돈 규칙과 같은 문제다.

### 경계·모서리 케이스 — 원본 테스트가 잡는 함정

- **함정: 할인 합이 금액을 넘어 음수 결제** → 10,000원에 8,000+5,000 쿠폰: 두 번째는 잔액 2,000까지만 깎고 **0에서 멈춘다.**\
  음수를 허용하면 손님에게 돈을 주는 것이고, 그 음수가 정산으로 흘러가면 출처를 못 찾는다.\
  `deductionFrom`의 `min(remaining)`이 이 방어선.

> **불변식(invariant)** — 어떤 입력이 들어와도 깨지면 안 되는 조건.\
> 예: "낼 금액은 0원 밑으로 안 내려간다" — 10,000원 장바구니에 8,000원·5,000원 쿠폰을 겹쳐도 결제는 0원에서 멈춘다.

- **함정: 상한 없는 정률** → 50,000원에 "20%, 최대 1,000원": 상한 없으면 10,000원이 깎인다.\
  정률은 장바구니가 비쌀수록 폭발하므로 실제 쿠폰에는 거의 항상 상한(cap)이 붙는다.

> **상한(cap)** — 정률 할인이 깎을 수 있는 최대 금액을 따로 정해 둔 값.\
> 예: "20%, 최대 1,000원" 쿠폰은 50,000원 장바구니에서도 10,000원이 아니라 1,000원만 깎는다.

- **함정: 할인 하나로만 테스트** → 할인이 하나면 순서(적용할 게 하나)·기준(원가=잔액)·반올림(한 번뿐) **세 결정이 전부 사라져서** 여섯 조합이 같은 답을 낸다(측정: 1,000건 전부).\
  "10% 쿠폰 하나 테스트 통과"로는 이 챕터의 문제가 통째로 안 보인다.
- **함정: "정률끼리는 순서 무관"** → 합계는 같다(0.9×0.8=0.72, 어느 순서든 7,200원).\
  그런데 내역이 다르다 — 10% 먼저면 1,000원+1,800원, 20% 먼저면 2,000원+800원.\
  **결과가 같다는 말은 반쪽만 맞다. 손님이 보는 화면이 달라진다.**
- **함정: 잘못된 할인 생성** → 0% / 101% / 빈 이름 / 음수 상한은 생성자에서 예외 — 잘못된 값은 만들어지는 순간 막는다.

## 핵심 문장

- 요구사항이 침묵하는 결정이 셋 있다 — 순서·정률의 기준·반올림 시점.\
  코드를 쓰는 순간 셋 다 정해지므로, **모르고 정하지 말고 매개변수로 끌어올려 보이게 하라.**
- 갈리는 돈의 크기: 기준(174만) > 순서(72만) >> 반올림(391원/1,000건) — 그런데 회계 항의는 제일 작은 반올림에서 온다.\
  **금액이 큰 결정과 시끄러운 결정은 다르다.**
- 원가 기준은 더하기(할인 독립, 100% 초과 가능), 누적 기준은 곱하기(뒤 할인이 작아짐) — 12번 버프의 가산/승산이 도메인만 바꿔 다시 나온 것.
- 어떤 조합에서도 결제 금액은 음수가 되지 않는다 — 잔액으로 자르는 한 줄이 정산 사고를 막는 불변식이다.
- 할인 하나로 시험하면 세 결정이 전부 안 보인다 — 경계는 "둘 이상"에서만 드러난다.

### 용어 풀이

- **정률 할인(percent discount)**: 비율로 깎는 할인. 기준 금액이 필요해서 "무엇의 몇 %냐"는 질문이 따라온다.
- **정액 할인(amount discount)**: 고정 금액으로 깎는 할인. 기준이 필요 없다.
- **상한(cap)**: 정률 할인이 깎을 수 있는 최대 금액. 비싼 장바구니에서의 폭발을 막는다.
- **원가 기준(ORIGINAL)**: 정률을 항상 처음 금액에 적용. 할인끼리 독립(더하기 구조).
- **누적 기준(RUNNING)**: 정률을 그때까지 깎인 잔액에 적용. 뒤 할인이 작아짐(곱하기 구조).
- **안정 정렬(stable sort)**: 정렬 기준이 같은 원소끼리 원래 순서를 유지하는 정렬. 적용 내역의 표시 순서를 지킨다.
- **교환법칙**: 곱셈은 순서를 바꿔도 결과가 같다(0.9×0.8=0.8×0.9). 정률끼리 합계가 순서 무관인 이유 — 단, 내역은 다르다.
- **버림(RoundingMode.DOWN)**: 소수점을 잘라내는 것. 매 단계 버리면 손님에게 유리하고 내역이 정수로 맞아떨어진다.
- **BigDecimal**: 돈 계산용 십진 소수 타입. 이진 소수(double)의 오차 없이 반올림 시점을 명시적으로 정하게 강제한다.
- **불변식(invariant)**: 어떤 경우에도 깨지면 안 되는 조건. 예: "낼 금액 ≥ 0", "내역의 합 = 총 할인액(매 단계 버림일 때)".
