## 한눈에 — 쉽게 말하면

**카테고리 트리 = 쇼핑몰의 "가전 > 노트북 > 게이밍" 같은 분류 폴더.**

- 집 주소를 생각해 보자. "서울시 강남구 역삼동 12번지"라는 주소를 얻는 방법이 둘이다: ① 동사무소에 가서 "12번지의 상위 동네가 뭐예요?"를 **매번 물어 올라가기**(계산), ② 집집마다 **문패에 전체 주소를 미리 새겨 두기**(저장).
- 카테고리 경로도 똑같은 구조다. **계산 방식**은 조회할 때마다 부모를 타고 올라가고, **저장 방식**은 칸마다 자기 경로 문자열을 들고 있다.
- 둘 다 맞는 경로를 준다 — **결과만 보면 구별할 수 없다**. 갈리는 것은 비용이다: 계산은 조회가 비싸고(깊이만큼 읽기), 저장은 이동이 비싸다(이사 가면 온 동네 문패를 다시 새긴다).
- 실무 예: 쇼핑몰 카테고리, 게시판 분류, 파일 탐색기의 breadcrumb("홈 > 문서 > 사진").
  - *breadcrumb(빵부스러기)*: 화면 위에 "가전 > 노트북 > 게이밍"처럼 현재 위치까지의 경로를 보여주는 UI.

```text
  c1 가전                     경로
   +-- c11 노트북              "가전 > 노트북"
   |    +-- c111 게이밍        "가전 > 노트북 > 게이밍"
   +-- c12 액세서리            "가전 > 액세서리"
  c2 의류
   +-- c21 액세서리            "의류 > 액세서리"   ← 이름은 겹쳐도 경로는 다르다
```

## 전체 흐름

```text
요구사항: "카테고리마다 '가전 > 노트북 > 게이밍' 경로를 보여줘라"

만들 때 (of)               경로 조회 (path)          이동 (move)
  식별자 중복 거부            COMPUTED: 부모 타고        자기 밑으로 가는 것 거부
  없는 부모 거부                올라가며 조립             새 부모 밑 이름 충돌 거부
  순환 거부 (walkUp)         STORED: 저장된 문자열      STORED 면 자기+밑 전부
  형제 이름 중복 거부           한 번에 꺼냄               경로 다시 쓰기
  STORED 면 전 칸 경로 저장

reads/writes 카운터가 두 방식의 비용 차이를 숫자로 남긴다 — 결과는 같으니까
```

## 요구사항 → 코드: 어디에 번역됐나

| 말로 된 요구사항 | 코드 |
|---|---|
| "이름에 `>`가 들어가면 경로와 헷갈린다" | `Category` 생성자 — `name.contains(">")` 이면 예외 |
| "같은 부모 밑에 같은 이름 금지" | `of()`의 `pairs.add(parentId + " " + name)` 중복 검사 |
| "경로를 보여줘라" | `path(id)` — 모드에 따라 계산 또는 저장값 |
| "자기 밑으로 이동 금지(순환)" | `move()` — `descendants(id).contains(newParentId)` 거부 |
| "이동해도 경로가 맞아야 한다" | STORED 모드 `move()` — 자기 + `descendants` 전부 재계산 |

## 규칙 1 — 형제 이름 중복을 막는 이유: 경로가 식별자 노릇을 한다

**어떤 요구사항인가**: "가전 > 액세서리"라는 경로로 카테고리를 찾을 수 있어야 한다(`findByPath`).

**예시 입력**: 가전(c1) 밑에 "노트북"이 **둘** 있다면?

```text
  가전
   +-- 노트북 (c11)    경로 = "가전 > 노트북"
   +-- 노트북 (c12)    경로 = "가전 > 노트북"   ← 똑같다!
```

**결과**: 식별자(c11, c12)는 다르니 자료로는 멀쩡하다. 그런데 경로로 찾으면 먼저 나온 것을 준다 — **예외도 안 나고, 가끔 엉뚱한 카테고리가 나올 뿐이다.** 그래서 만들 때(`of`)부터 형제 이름 중복을 던진다.

**함정 둘**:
- **최상위끼리도 형제다.** 부모가 둘 다 null이면 같은 부모다. null을 특별 취급하다가 여기를 빠뜨린다 — 테스트 `topLevelNamesMustDiffer`가 잡는다.
- **이름에 구분자(`>`)가 들어가는 것.** 이름이 "가전 > 노트북"인 칸 하나와, "가전" 밑의 "노트북" — 경로 문자열로는 똑같다. 이스케이프하는 방법도 있지만, 그러면 경로를 만드는 곳과 읽는 곳이 같은 규칙을 알아야 한다. **처음부터 막는 편이 싸다.**
  - *이스케이프(escape)*: 특수문자를 `\>`처럼 표시를 붙여 "이건 구분자가 아니라 글자다"라고 알리는 방법.

부모가 다르면 이름이 겹쳐도 된다: "가전 > 액세서리"와 "의류 > 액세서리"는 다른 경로다. 실제 카탈로그가 정확히 이렇게 생겼다.

## 규칙 2 — 경로를 얻는 두 방식 (COMPUTED vs STORED)

**어떤 요구사항인가**: 같은 `path(id)` 계약을 두 가지 구현으로.

**예시 입력**: c111(게이밍)의 경로 한 번 조회.

```text
COMPUTED (계산)                         STORED (저장)
  c111 읽기 → "게이밍"                    storedPath.get(c111) 읽기 1번
  c11  읽기 → "노트북"                    → "가전 > 노트북 > 게이밍" 끝
  c1   읽기 → "가전"
  → 조립: "가전 > 노트북 > 게이밍"
  읽기 3번 (깊이만큼)                      읽기 1번 (깊이 무관)
```

**측정이 알려준 것** (README, 무작위 칸 경로 1,000번 읽기):

| 깊이 | 칸 수 | 계산 읽기 | 저장 읽기 | 배수 |
|---|---|---|---|---|
| 2 | 20 | 1,810 | 1,000 | 1.8 |
| 3 | 84 | 2,691 | 1,000 | 2.7 |
| 4 | 340 | 3,687 | 1,000 | 3.7 |
| 5 | 1,364 | 4,700 | 1,000 | **4.7** |

- 저장 방식은 **언제나 1,000**이다. 계산 방식은 깊이에 정비례 — 카탈로그가 2단에서 5단이 되면 **아무 코드도 안 바꿨는데** 조회 비용이 2.6배가 된다.
- 대신 저장 방식은 만들 때 이미 칸마다 한 번씩 쓴다(`rebuildStoredPaths`) — 그 비용도 `writes()`에 남는다.

## 규칙 3 — 이동(move): 저장 방식의 청구서

**어떤 요구사항인가**: 관리자가 "노트북" 카테고리를 "의류" 밑으로 드래그해서 옮긴다.

**예시 입력**: `move("c11", "c2")` — 노트북을 가전에서 의류 밑으로.

```text
  이동 전                              이동 후
  노트북   "가전 > 노트북"              → "의류 > 노트북"
  게이밍   "가전 > 노트북 > 게이밍"      → "의류 > 노트북 > 게이밍"

  부모를 가리키는 줄은 c11 하나만 바뀌었다.
  COMPUTED: 다시 쓸 것 없음 (writes 0)
  STORED:   자기 것 + 밑의 것 전부 다시 쓴다 (writes 2 — 노트북, 게이밍)
```

**함정 — 옮긴 칸 자신을 빠뜨리는 것**: "밑을 전부 다시 쓴다"라고 생각하면 자기는 "밑"이 아니라서 빠진다. 원본도 변종 검증에서 이걸 겪었다 — 밑의 칸만 확인하고 있어서 **자기 경로를 안 고쳐도 테스트가 다 통과했다.** 옮긴 칸 자신을 확인하는 단언을 넣어 고쳤다.

**측정**: 이동 한 번이 깊이 5에서 **최대 93줄**을 다시 쓴다. 화면에서는 카테고리 하나를 끌어다 놓은 것뿐인데.

**이동이 막아야 하는 것 둘**:
1. **자기 밑으로 가는 것**(순환): "가전"을 "게이밍" 밑으로 → 부모 사슬이 뱅글뱅글 돈다.
2. **새 부모 밑 이름 충돌**: "의류 > 액세서리"를 "가전" 밑으로 옮기는데 "가전 > 액세서리"가 이미 있다. **만들 때는 아무 문제 없던 자료인데 이동이 문제를 만든다** — 카탈로그 정리는 전부 이동으로 이뤄진다.

## 어느 쪽을 고르나 — 손익분기 2.4회

**측정에서**: 깊이 4에서 조회 한 번이 아끼는 읽기 = 3.687 − 1 = 2.687, 이동 한 번이 무는 쓰기 = 637 / 100 = 6.37. 나누면 **손익분기 = 조회 2.4회** — 이동 한 번당 조회가 2.4회를 넘으면 저장 방식이 이긴다.

- 쇼핑몰 카탈로그는 이동 한 번당 조회가 수만 회다 — 그래서 이 결정은 사실 정해져 있다.
- 그런데 근거는 "**우리 서비스의 조회 대 이동 비율이 2.4를 넘는다**"여야 한다. 관리자 화면만 있는 시스템이면 반대다.
- **모델링 교훈**: 두 설계가 같은 답을 줄 때, 고르는 근거는 취향이 아니라 **워크로드 숫자**다.
  - *워크로드(workload)*: 시스템에 실제로 들어오는 일의 종류와 비율. 여기서는 "조회 몇 번, 이동 몇 번".

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 형제 이름 중복을 안 막음 | 같은 경로가 둘 생겨 `findByPath`가 엉뚱한 것을 줌 → `of`에서 던진다 |
| 최상위(부모 null)끼리는 검사 누락 | null 부모도 "같은 부모"다 → 함께 검사 |
| 이동 후 옮긴 칸 자신의 경로 누락 | 자기 + descendants 전부 재계산, 테스트도 자기를 단언 |
| 이름에 `>` 포함 | `Category` 생성자에서 즉시 거부 |
| 자기 밑으로 이동(순환) | `descendants(id).contains(newParentId)`면 거부 |
| 이동으로 생기는 이름 충돌 | `move`에서 새 부모의 형제 이름 검사 후 거부 |
| 이름으로 검색이 유일하다고 믿음 | 340칸 카탈로그에서 "가전"이란 이름이 85칸 — `findByName`은 List를 준다 |

**측정 넷**: 무작위 이동 1,000번 중 순환은 10번, 이름 충돌은 **233번** — 이름 충돌이 순환보다 **23배 흔하다.** 순환은 무한 루프가 무서워 누구나 막는데, 이름 충돌은 23배 흔한데 아무도 안 막는다.

**변종 검증 둘째**: `of`가 끝에서 카운터를 0으로 돌려서 **만들 때 드는 비용이 아무 데도 안 남았다** — 계산 방식이 몰래 경로를 저장하는 변종이 안 잡혔다. 0으로 안 돌리게 바꾸고(지우고 싶은 쪽이 `resetCounters()`를 직접 부른다) 만드는 비용을 재는 측정을 넣었다.

## 핵심 문장

- 계산과 저장은 **같은 답을 주므로 결과로는 구별할 수 없다** — 고르는 근거는 조회 대 이동 비율(손익분기 2.4회)이라는 워크로드 숫자다.
- 경로가 식별자 노릇을 하는 순간, **형제 이름 중복은 "같은 경로가 둘"이라는 조용한 결함**이 된다 — 예외 없이 가끔 엉뚱한 카테고리가 나온다.
- 이름 충돌은 순환보다 23배 흔한데, 무서운 쪽(순환)만 다들 막는다 — **막을 것의 우선순위는 공포가 아니라 빈도로 정한다.**
- 저장 방식의 이동은 "자기 + 밑 전부 다시 쓰기"다 — 자기를 빠뜨리는 변종은 밑만 검사하는 테스트를 통과한다.
- 비용을 지우는 코드(`of` 끝의 카운터 리셋)는 측정 자체를 눈멀게 한다 — **지우고 싶은 쪽이 직접 지우게 하라.**

## 용어 풀이

- **카테고리 트리(category tree)**: 분류가 부모-자식으로 이어진 구조. 각 칸은 id·이름·부모 id를 가진다.
- **경로(path)**: 최상위부터 그 칸까지 이름을 " > "로 이은 문자열. 화면의 breadcrumb이 이것이다.
- **COMPUTED(계산 방식)**: 조회 때마다 부모를 타고 올라가 경로를 조립. 조회 비용 = 깊이, 이동 비용 = 0.
- **STORED(저장 방식)**: 칸마다 경로 문자열을 미리 저장. 조회 비용 = 1, 이동 비용 = 자기 + 밑 전부.
- **형제(sibling)**: 같은 부모를 가진 칸들. 최상위(부모 null)끼리도 형제다.
- **순환(cycle)**: 부모 사슬이 자기 자신으로 되돌아오는 것. 경로 계산이 무한 루프가 된다.
- **descendants(밑의 모든 칸)**: 자식, 자식의 자식… 전부. 자기 자신은 안 들어간다.
- **손익분기(break-even)**: 두 방식의 총비용이 같아지는 지점. 여기서는 이동 1회당 조회 2.4회.
- **구분자(separator)**: 경로에서 칸 이름 사이를 가르는 " > ". 이름에 들어가면 경로와 구별이 안 된다.
- **워크로드(workload)**: 실제 들어오는 요청의 종류·비율. 설계 선택의 최종 근거.
