### A. 과제 (Shipping 의 TODO 1~4)

#### 1. 챕터 지문

```text
"5 만원      이상        무료      배송"
  ↑           ↑           ↑         ↑
  무엇의      경계가      무엇까지   누구 단위로
  5만원?      이상? 초과?  무료?     세는 배송?

  · 할인 전인가 후인가        → thresholdOnDiscountedAmount
  · 49,999 는? 50,000 은?     → 코드의 >= 한 글자 (테스트가 "이상"으로 못 박음)
  · 도서산간 추가비도 무료?    → freeAppliesToSurcharge
  · 판매자 여럿이면 각각?      → perSeller
```

- 넷 말고 침묵하는 것:
  - **전부 취소된 주문**은 얼마인가? → 0원. 안 그러면 아무것도 안 샀는데 3,000원을 낸다.
  - **무료 기준이 아예 없는 정책**은 어떻게 표현하나? → `freeThreshold == 0` 을 "무료 없음"으로 읽는다.
  - **부분 취소로 기준이 깨지면** 다시 받나? → 계산은 `feeDeltaAfterCancel` 이 하고, **받을지는 정책이 정한다.**
- 침묵을 모아 둔 곳: **`ShippingPolicy` record 의 필드 6개.** 17번에서 결정을 `apply` 의 매개변수로 올린 것과 같은 수법인데, 여기선 아예 **정책 객체 한 덩이**로 묶었다.
- 짝짓기:

| 필드 | 뜻 | 결정 |
|---|---|---|
| `baseFee` | 기본 배송비(표준 3,000) | — |
| `freeThreshold` | 무료 기준. **0 = 무료 없음** | (경계) |
| `remoteSurcharge` | 도서산간 추가비(표준 3,000) | — |
| `freeAppliesToSurcharge` | 무료가 추가비까지 없애나 | **결정 2** |
| `thresholdOnDiscountedAmount` | 기준을 할인 후로 보나 | **결정 1** |
| `perSeller` | 판매자별로 따로 계산하나 | **결정 3** |

(결정 4는 필드가 아니라 `feeDeltaAfterCancel` 이라는 **계산 수단**으로만 제공된다 — 정책 판단은 바깥에 남겼다.)

#### 2. TODO 1 — thresholdAmount

정답 코드 (impl/Shipping.java):

```java
int sum = 0;
for (OrderLine line : lines) {
    if (line.cancelled()) {
        continue;                       // ★ 취소된 줄은 안 센다
    }
    sum += policy.thresholdOnDiscountedAmount() ? line.payable() : line.listPrice();
}
return sum;
```

- 보는 필드는 **`thresholdOnDiscountedAmount` 하나**다.
- 할인 후 기준이면 `line.payable()`(= `listPrice - discount`), 할인 전 기준이면 `line.listPrice()` 를 더한다.
- 정가 60,000 · 할인 15,000:

```text
할인 후 기준   45,000  <  50,000  →  배송비 3,000
할인 전 기준   60,000  >= 50,000  →  무료

손님은 "6만원어치 담았는데 배송비가 붙었다" 고 느낀다 — 손님이 본 숫자는 정가이기 때문이다.
```

- 취소된 줄을 그대로 세면: **5만원어치 담아 무료 배송을 받고 절반을 취소하는 길**이 열린다. 배송은 이미 나갔는데 기준 금액만 그대로다.
- 달라도 된다. **판정용 금액과 결제 금액은 다른 개념**이고, 어느 쪽을 판정에 쓸지가 바로 결정 1이다. 이 함수를 따로 뽑아 이름을 붙인 것 자체가 "이건 결제액이 아니다"라는 선언이다.

#### 3. TODO 3 — feeForGroup

정답 코드:

```java
boolean allCancelled = true;
for (OrderLine line : lines) {
    if (!line.cancelled()) { allCancelled = false; break; }
}
if (lines.isEmpty() || allCancelled) {
    return 0;                                     // [1] 보낼 것이 없으면 0
}

boolean free = policy.freeThreshold() > 0         // [2] 0 = 무료 없음
        && thresholdAmount(lines, policy) >= policy.freeThreshold();   // 이상(>=)

int fee = free ? 0 : policy.baseFee();            // [3] 무료 여부가 먼저
if (remote && !(free && policy.freeAppliesToSurcharge())) {
    fee += policy.remoteSurcharge();              // [4] 도서산간은 그 다음
}
return fee;
```

- 가장 먼저 거를 둘: **빈 목록**과 **전부 취소**.
- 안 걸러내면: 기준 금액이 0 → "기준 미달"로 판정되어 **아무것도 안 샀는데 3,000원**(도서산간이면 6,000원)이 붙는다. 테스트 `allCancelled` 가 세 경우(전부취소·전부취소+도서산간·빈 목록) 전부 0을 단언한다.
- `freeThreshold() > 0` 을 앞에 둔 이유: **0을 금액이 아니라 "무료 제도 없음"이라는 신호로 읽기 위해서**다.
- 0을 "0원 이상이면 무료"로 읽으면: `thresholdAmount >= 0` 은 **언제나 참**이라 **전 주문이 무료 배송**이 된다. 그리고 0은 흔한 기본값이라 아무도 설정 안 한 환경에서 조용히 그렇게 된다(테스트 `zeroThresholdMeansNoFreeShipping`).
- 비교는 **`>=`(이상)** 이다. `>`(초과)로 쓰면 **딱 5만원인 손님이 배송비를 낸다** — 그리고 그 손님이 가장 많다. 무료 배송을 받으려고 **5만원에 맞춰 담기** 때문이다.
- 도서산간 조건: **`remote && !(free && freeAppliesToSurcharge)`** — "도서산간이고, (무료이면서 무료가 추가비까지 덮는 경우)가 아니면 붙인다."
- 순서를 뒤집으면: 추가비를 먼저 더하고 무료면 전체를 0으로 만들게 되어 **"무료 배송인데 도서산간 3,000원만 남는" 상태를 표현할 방법이 없다.** 그런데 그게 현실에서 제일 흔한 정책이다.

```text
무료 먼저 → 추가비 나중        추가비 먼저 → 무료 나중
  fee = 0                        fee = 3,000 + 3,000 = 6,000
  + 3,000(추가비)                무료니까 → 0
  = 3,000  ✔ 표현 가능           = 0       ✘ 3,000 을 못 만든다
```

- STANDARD 정책 + 6만원 + 도서산간 = **3,000원.** 무료 판정으로 기본 3,000은 0이 되고, `freeAppliesToSurcharge = false` 라 추가비 3,000이 남는다(테스트 `freeAndSurcharge`).

#### 4. TODO 2 — feeFor

정답 코드:

```java
if (!policy.perSeller()) {
    return feeForGroup(lines, policy, remote);        // 주문 전체가 한 묶음
}
Map<String, List<OrderLine>> bySeller = new LinkedHashMap<>();
for (OrderLine line : lines) {
    bySeller.computeIfAbsent(line.seller(), key -> new ArrayList<>()).add(line);
}
int total = 0;
for (List<OrderLine> group : bySeller.values()) {
    total += feeForGroup(group, policy, remote);      // 묶음마다 따로 판정
}
return total;
```

- `perSeller` 가 거짓이면 **주문 전체를 한 묶음으로 보고 `feeForGroup` 한 번**을 부른다.
- 참이면 **`seller` 로 묶고(`computeIfAbsent`), 묶음마다 `feeForGroup` 을 불러 더한다.**
- `LinkedHashMap` 인 이유: **입력 순서대로 묶음을 돌게 해서 결과를 결정적으로** 만든다. 합계만 보면 순서가 상관없지만, 나중에 판매자별 내역을 화면에 찍거나 로그를 비교할 때 순서가 매번 바뀌면 재현이 안 된다. (17번의 안정 정렬과 같은 동기 — 금액은 같아도 **보이는 순서**를 지킨다.)
- 판정은 **묶음마다 따로** 한다. 전체를 보고 한 번에 정하지 않는다.
- S1 60,000 + S2 10,000 판매자별:

```text
S1 묶음   60,000 >= 50,000  →  무료      0 원
S2 묶음   10,000 <  50,000  →  기본   3,000 원
                                합계  3,000 원
```

- 도서산간 추가비는 **묶음 수만큼 붙는다.** `feeForGroup` 안에서 더하기 때문이다. 판매자가 각자 따로 부치니 각자 도서산간 비용을 치른다 — 계산상은 맞다. 다만 손님 화면엔 "도서산간 추가비 6,000원"으로만 보여서 오해를 산다(원본에 근거 없음 — 내 추론).

#### 5. TODO 4 · feeDeltaAfterCancel

정답 코드:

```java
public static boolean isFree(List<OrderLine> lines, ShippingPolicy policy) {
    return policy.freeThreshold() > 0
            && thresholdAmount(lines, policy) >= policy.freeThreshold();
}
```

- `isFree` 는 **`feeFor == 0` 과 같지 않다.** 두 방향으로 어긋난다:

```text
isFree = true 인데 fee ≠ 0    6만원 + 도서산간 + STANDARD  →  fee 3,000  (추가비가 남는다)
isFree = false 인데 fee = 0   전부 취소된 주문             →  fee 0      (기준 금액이 0이라 미달 판정)
```

  `isFree` 는 **"무료 기준을 넘겼나"** 라는 질문이고, `feeFor` 는 **"얼마를 받나"** 라는 질문이다. 화면에 "무료 배송!" 배지를 띄우는 건 앞의 것, 청구하는 건 뒤의 것 — 이 둘을 같은 것으로 쓰면 배지와 금액이 어긋난다.
- `feeDeltaAfterCancel` 이 양수 = **취소 뒤 배송비가 늘었다 = 더 받아야 한다.** 취소로 무료 기준에서 떨어졌다는 뜻이다(테스트: 30,000×2 중 하나 취소 → **+3,000**).
- 청구 여부는 **이 함수가 정하지 않는다.** 숫자만 낸다. 받을지 말지는 정책·법무·CS가 정할 일이다.
- 지침: **"계산도 안 하면 정할 수가 없다."** 정책이 안 정해졌다고 계산까지 미루면 회의 테이블에 올릴 근거가 없다. 먼저 **얼마인지 세는 코드**를 만들고, 수치를 들고 정책을 정한다. 이 챕터의 측정 넷(404건·1,212,000원)이 바로 그렇게 나온 숫자다.

#### 6. 계약으로 주어진 OrderLine·ShippingPolicy

- `cancel()` 이 새 객체를 돌려주는 이점: **취소 전 상태가 그대로 살아 있다.** `feeDeltaAfterCancel(before, after, ...)` 이 before 와 after 를 **동시에** 들고 비교할 수 있는 이유가 이것이다. 필드를 바꿔버리면 before 가 사라져 차액을 계산할 수 없다.
- `discount > listPrice` 를 생성자에서 막으면: **`payable()` 이 절대 음수가 아니다** → `thresholdAmount` 도 음수가 안 된다 → "할인 때문에 기준 금액이 줄어드는" 이상한 일이 안 생긴다. 17번의 `min(remaining)` 과 같은 자리의 방어선이다.
- `standard()` = `(3_000, 50_000, 3_000, false, true, false)`:

```text
기본 배송비 3,000원 · 5만원 이상 무료 · 도서산간 3,000원 추가
· 무료여도 도서산간 추가비는 받는다 (false)
· 무료 기준은 할인 후 금액으로 본다  (true)
· 주문 전체를 한 묶음으로 본다       (false)
```

- `freeAppliesToSurcharge = false` 는 **"무료 배송이라도 도서산간 3,000원은 받는다"** 는 뜻이다. 그러면 화면에 **"무료 배송(도서산간 제외)"** 이라고 써야 한다. 안 쓰면 "무료라더니 3,000원을 받는다"는 항의가 온다 — 측정 셋이 정확히 그 얘기다.

### B. 개념

#### 7. 측정 하나 — 기준 금액

| | 무료 배송 건수 | 배송비 합계 |
|---|---|---|
| 할인 후 기준 | 634 | 4,695,000 원 |
| 할인 전 기준 | **865** | 4,002,000 원 |

- 할인 후로 보면 무료 배송이 865 → 634 로 **약 27% 준다.** 배송비 합계는 693,000원 늘어난다.
- 갈리는 건은 **231/2,000 뿐**이다. **할인이 붙은 주문에서만** 두 기준의 값이 달라지기 때문이다.
- 그 231건은 전부 **"5만원 넘게 담았는데 배송비가 붙은"** 손님이다. 손님은 정가를 보고 담았는데 계산대에서 할인이 붙어 기준 아래로 내려간 것 — **손님 입장에선 이유를 알 수 없는 배송비**다.
- 교훈: **갈리는 비율이 낮은 것과 문제가 작은 것은 다르다.** 11.5%(231/2,000)라는 숫자만 보면 작아 보이지만, 그 11.5%가 **전부 화난 손님**이다. 비율이 아니라 **갈린 쪽이 누구인지**를 봐야 한다.

#### 8. 측정 둘 — 판매자별

| | 배송비 합계 |
|---|---|
| 주문 전체 기준 | 4,695,000 원 |
| 판매자별 기준 | **11,289,000 원** |

- **2.4배.** 1,248/2,000 이 갈린다 — **네 결정 중 금액이 가장 크다.**
- 손님이 가장 이해하기 어려운 이유: 판매자가 각자 보내니 각자 배송비가 드는 것은 **맞는 말**인데, **화면에는 그 사정이 안 보인다.** 손님에게는 "장바구니 하나, 결제 한 번"이라 "6만원어치 샀는데 배송비가 6,000원"으로만 보인다. 옳은 계산인데 설명이 화면에 없는 것 — 코드 문제가 아니라 표시 문제다.

#### 9. 측정 셋 — 도서산간

| | 배송비 합계 |
|---|---|
| 추가비는 그대로 | 4,695,000 원 |
| 추가비도 무료 | 4,497,000 원 |

- 차이 **198,000원**, **66건**이 갈리고 건당 **3,000원**.
- 금액은 작고 항의는 큰 이유: 그 66건의 손님은 **"무료 배송"이라고 쓰인 화면을 보고 3,000원을 낸다.** 배신감은 금액에 비례하지 않는다. 게다가 도서산간 손님은 이미 배송에서 손해를 보고 있다고 느끼는 집단이다.
- 그래서 화면에는 **"무료 배송(도서산간 제외)"** 이라고 써야 한다. 코드는 그대로 두고 문구 하나로 항의를 없애는 자리다.

#### 10. 측정 넷 — 부분 취소

| | |
|---|---|
| 두 줄 이상인 주문 | 1,495 건 |
| 무료에서 떨어진 건 | **404 건 (27 %)** |
| 추가로 생긴 배송비 | 1,212,000 원 |

- 안 받으면: **5만원어치 담고 무료 배송을 받은 뒤 절반을 취소하는 길**이 남는다(= 악용 경로).
- 받으면: **환불 금액이 예상과 다르다**는 항의가 온다. "3만원 취소했는데 27,000원만 들어왔다."
- 이 챕터는 어느 쪽이 맞다고 말하지 않는다. **"어느 쪽이든 계산은 할 수 있어야 한다"** 만 요구한다 — 그래서 `feeDeltaAfterCancel` 이 정책 플래그가 아니라 **계산 함수**로 주어졌다.

#### 11. 측정 다섯 — 할인이 없으면 결정 하나가 사라진다

- 모든 줄의 할인이 0이면 **`listPrice == payable`** 이라 `thresholdOnDiscountedAmount` 를 어느 쪽으로 켜도 같은 값이 나온다. **2,000건 전부 같은 답.**
- 경고: **"개발할 때 만드는 주문은 대개 할인이 없다."** 개발·QA 데이터는 보통 `discount = 0` 이라, 결정 1의 버그가 **테스트에서 절대 안 잡히고 운영에서만 터진다.** 테스트 픽스처에 할인 0이 아닌 줄을 반드시 섞어야 한다.
- 17번과 **같은 구조다.** 17번은 "할인이 하나면 세 결정이 전부 사라진다", 18번은 "할인이 0이면 기준 결정이 사라진다" — 둘 다 **가장 단순한 데이터가 문제를 통째로 감춘다**는 같은 이야기다.

#### 12. 생각해볼 것 (원본 README 이관 — 답은 원본에 없다, 아래는 내 추론)

- **한 줄로 이어져 있다.** 17번에서 고른 순서·기준·반올림이 각 줄의 `discount` 를 정하고, 그 `discount` 가 여기 `payable()` 을 정하고, 그게 무료 배송 판정을 가른다. 17번에서 100원 차이가 나면 49,900 vs 50,000 경계에서 **3,000원 배송비가 붙느냐 마느냐**로 증폭된다. 두 박스는 별개가 아니라 **한 계산 파이프라인의 앞뒤**다.
- 판매자별 화면 표시: **묶음마다 한 줄씩** 보여주는 게 맞다 — "S1 배송비 3,000원 / S2 배송비 무료"처럼. 합계만 보이면 측정 둘에서 말한 "사정이 안 보이는" 상태가 된다. 다만 묶음이 많아지면 화면이 길어지니, 접었다 펴는 형태가 현실적이다.
- 반품 배송비: **별도로 보는 게 맞다.** 여기 계산은 "이 주문을 보내는 데 드는 돈"이고, 반품비는 "되돌리는 데 드는 돈"이라 귀책(손님 변심 vs 상품 하자)에 따라 부담 주체가 달라진다. 같은 숫자에 섞으면 정산에서 못 가른다. 다만 `feeDeltaAfterCancel` 과는 붙어 있다 — 부분 취소 때 손님이 실제로 내는 돈은 "배송비 차액 + 반품비"이기 때문이다.
- 기준 넘기려고 담은 것만 취소: **측정 넷의 404건이 바로 그 후보군**이다. 전부가 악의는 아니라서 일률 차단은 안 된다. 현실적 대응은 (1) 차액을 청구하되 화면에 미리 고지, (2) 반복 패턴인 계정만 표시해 두는 것. **계산이 있어야 어느 쪽이든 할 수 있다**는 점이 여기서도 같다.

#### 13. 연결

- 15번 쿠폰의 최소 금액과 같은 자리인 이유: 둘 다 **"금액 기준선 하나가 혜택의 유무를 가른다"** 는 같은 모양이고, 둘 다 **이상/초과 한 글자**로 결과가 갈린다. 그리고 두 경우 모두 **손님이 기준선에 딱 맞춰 담기 때문에** 경계값에 사람이 몰린다 — 경계 버그의 피해가 최대가 되는 분포다.
- 16·17·18 공통 한 문장: **"요구사항 한 줄이 침묵하는 결정을 찾아내, 코드 깊숙이 묻지 말고 값(enum·정책 필드)으로 끌어올려 보이게 하라."** 16은 정규화·순서, 17은 순서·기준·반올림, 18은 정책 필드 6개. 그리고 셋 다 **가장 단순한 데이터로 시험하면 그 결정이 통째로 안 보인다**는 경고가 붙는다.
- 무료 배송을 17번의 할인 종류로 모델링하면 꼬이는 것: **순환이 생긴다.** 배송비 판정은 할인 후 금액을 입력으로 받는데, 무료 배송이 할인의 하나가 되면 할인 계산이 배송비를 입력으로 받아야 한다. 게다가 무료 배송은 상품 금액을 깎는 게 아니라 **다른 항목을 0으로 만드는 것**이라 `total` 에 대한 정액/정률 어느 쪽에도 안 맞는다. 별도 축으로 두는 게 맞다.
