### A. 과제 (Insurance.java 의 TODO 1~3)

#### 0. 챕터 지문 — 표는 쉽고 분류가 어렵다

- 안 말해주는 결정: **"나이"가 어느 나이인가.**\
  그리고 그에 딸린 것들 — **경계를 이상으로 볼까 초과로 볼까**, **표 밖 나이는 어떻게 할까**, **천분율 나눗셈의 반올림은 어디서 할까**, **기준일이 계약일인가 개시일인가.**
- 세 나이가 오르는 날:

```text
 만 나이     ──── 생일에 +1
 연 나이     ──── 1월 1일에 +1
 보험 나이   ──── 생일 + 6개월 되는 날에 +1   (상령일)
```

> **만 나이(exact age)** — 태어난 날로부터 꽉 찬 해를 센 나이. 우리가 법에서 쓰는 나이다.\
> 예: 1986/6/15생은 2026/6/14 에 39살, 6/15 에 40살이 된다.

> **연 나이(calendar-year age)** — 올해 연도에서 태어난 연도를 뺀 나이. 생일을 안 본다.\
> 예: 1986/12/25생은 2026/1/1 부터 이미 40살이다. 만 나이로는 12/25 까지 39살인데도 그렇다.

> **보험 나이(insurance age)** — 만 나이를 6개월 기준으로 반올림한 나이.\
> 예: 마지막 생일에서 6개월이 지났으면 만 나이에 1을 더한다. 1986/6/15생은 2026/12/15 부터 41살로 친다.

> **상령일** — 보험 나이가 한 살 오르는 날. 생일 + 6개월이다.\
> 예: 6/15 생의 상령일은 12/15 다. 이날을 넘기면 요율 구간이 바뀔 수 있어 "그 전에 가입하세요"라는 안내가 나온다.

- 셋 중 맞는 나이: **셋 다 맞다.**\
  틀린 것을 고르는 문제가 아니라, **어느 정의를 쓸지 정하는 문제**다.
- 약관이 안 정하면: **코드가 정한다.**\
  개발자가 `ChronoUnit.YEARS.between` 을 아무 생각 없이 쓰면 그 순간 "만 나이"로 확정되고, 그 결정은 어디에도 안 적힌다.
- 19번에 새로 붙은 축: **입력 자체가 여러 정의를 갖는다.**\
  19번은 "소득"이 하나뿐이었고 구간 경계만 정하면 됐다.\
  여기서는 **구간에 넣을 값 자체가 셋**이라, 표를 다 맞춰도 입력이 틀리면 답이 틀린다.
- 실제 예: **술·담배는 연 나이**(태어난 해 기준), **병역·선거는 만 나이**, **보험은 보험 나이.**\
  같은 사람이 같은 날 법마다 다른 나이를 갖는다.

#### 1. TODO 1 — ageOn

```java
public static int ageOn(LocalDate birthDate, LocalDate on, AgeBasis basis) {
    if (on.isBefore(birthDate)) {
        throw new IllegalArgumentException("기준일이 생일보다 빠르다");
    }
    int exact = (int) ChronoUnit.YEARS.between(birthDate, on);
    return switch (basis) {
        case EXACT -> exact;
        case CALENDAR_YEAR -> on.getYear() - birthDate.getYear();
        case INSURANCE -> {
            LocalDate lastBirthday = birthDate.plusYears(exact);
            long months = ChronoUnit.MONTHS.between(lastBirthday, on);
            yield months >= 6 ? exact + 1 : exact;
        }
    };
}
```

- 만 나이: **`ChronoUnit.YEARS.between(birthDate, on)`** 한 줄.\
  꽉 찬 해만 세므로 생일 전날까지는 한 살 적다.
- 연 나이: **`on.getYear() - birthDate.getYear()`** — 연도끼리만 뺀다.\
  월·일을 아예 안 본다.
- 보험 나이의 절차:\
  ① 먼저 **만 나이**를 구한다.\
  ② **마지막 생일**을 구한다 — `birthDate.plusYears(exact)`.\
  ③ 마지막 생일에서 기준일까지 **꽉 찬 달 수**를 센다.\
  ④ **6 이상이면** 만 나이 + 1, 아니면 만 나이 그대로.
- 6개월을 태어난 날에서 세면: **나이가 터무니없이 커진다.**\
  1986년생이면 태어난 날부터 지금까지가 480개월이라 `>= 6` 이 늘 참이 되고, **누구나 항상 만 나이 + 1** 이 된다.\
  6개월은 **올해 치**를 세는 것이지 인생 전체를 세는 것이 아니다.
- `ChronoUnit.MONTHS` 가 꽉 찬 달만 센다: **6개월 하고 하루는 6이고, 5개월 29일도 5다.**\
  즉 이 값은 **"몇 달이 완전히 지났나"** 이지 "몇 달쯤 됐나"가 아니다.

> **ChronoUnit.MONTHS** — 두 날짜 사이의 **완전히 지난 달 수**를 세는 자바 기능.\
> 예: 6/15 에서 12/14 까지는 5(6개월이 아직 안 찼다), 12/15 까지는 정확히 6이다.

- `>= 6` 이냐 `> 6` 이냐가 결정인 이유: **"정확히 6개월"인 날을 어느 쪽에 넣을지**가 갈리기 때문이다.\
  `>= 6` 이면 12/15 에 한 살 오르고, `> 6` 이면 1/15 까지 기다린다.\
  한 달이 통째로 밀린다.
- 반올림에 맞는 쪽: **`>= 6`(이상)** 이다.\
  반올림은 "절반이면 올린다"이고, 1년의 절반이 6개월이다.\
  javadoc 이 *"정확히 6 개월이면 올린다. 반올림이라 그렇다"* 라고 못 박았다.
- 1986/6/15생을 2026/6/14에 보면 (테스트 `threeAges`):

```text
 만 나이    YEARS.between(1986-06-15, 2026-06-14) = 39   생일 하루 전
 연 나이    2026 - 1986                          = 40   생일 무관
 보험 나이  마지막 생일 2025-06-15 → 2026-06-14 = 11개월
            11 >= 6 이므로  39 + 1              = 40

 같은 사람, 같은 날, 39 / 40 / 40
```

- 보험 나이 41이 되는 첫 날: **2026/12/15** (테스트 `insuranceAge`).\
  12/14 에는 만 40·보험 40, 12/15 에는 만 40·보험 **41** 이다.\
  그날 만 나이는 그대로 40이라는 게 요점 — **두 나이가 서로 다른 날에 오른다.**
- 태어난 날: **셋 다 0살** (테스트 `bornToday`).\
  (한국식으로 "태어나면 1살"을 세는 방식은 또 다른 정의이고, 이 모델에는 없다.)
- 기준일이 생일보다 빠르면: **예외를 던진다.**\
  0으로 뭉개면 **음수 나이가 조용히 0살이 되어** 첫 구간(요율 0.8)이 적용된다.\
  데이터 입력 실수(생년월일 오타)가 **"가장 싼 보험료"** 로 둔갑해 아무도 못 알아챈다.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 결과만 틀린 것.\
> 예: 생년월일을 2086년으로 잘못 입력해도 나이를 0으로 뭉개면 보험이 그냥 가입된다. 예외를 던지면 그 자리에서 잡힌다.

#### 2. TODO 2 — premium

```java
public static BigDecimal premium(
        long insuredAmount, LocalDate birthDate, LocalDate on, AgeBasis basis, RateTable table) {
    if (insuredAmount <= 0) {
        throw new IllegalArgumentException("가입 금액이 0 보다 커야 한다: " + insuredAmount);
    }
    int age = ageOn(birthDate, on, basis);          // ① 나이
    int rate = table.ratePermilleFor(age);          // ② 요율
    return BigDecimal.valueOf(insuredAmount)        // ③ 금액 × 요율 / 1,000
            .multiply(BigDecimal.valueOf(rate))
            .divide(BigDecimal.valueOf(1_000), 0, RoundingMode.HALF_UP);
}
```

- 세 단계: **① 나이를 센다 → ② 표에서 요율을 찾는다 → ③ 가입 금액 × 요율 ÷ 1,000.**\
  어려운 것은 ①뿐이고 ②③은 기계적이다.
- 요율을 정수 천분율로 든 이유: **표에 소수점 오차가 안 생긴다.**\
  0.8·1.0·1.5·2.5 를 실수로 들면 표기·비교·직렬화에서 오차가 끼어든다.\
  800·1,000·1,500·2,500 은 정수라 정확하고, 나눗셈은 **계산할 때 딱 한 번**만 한다.

> **천분율(permille, ‰)** — 1,000을 기준으로 쓰는 비율. 퍼센트가 100 기준인 것과 같은 방식이다.\
> 예: 요율 1,500‰ 은 요율 1.5 를 뜻한다. 가입 금액 1억이면 보험료는 1억 × 1,500 ÷ 1,000 = 1.5억이다.

- 나눗셈이 생기는 순간: **반올림 규칙과 자릿수를 정해야 한다.**\
  안 정하면 `BigDecimal.divide` 가 나누어떨어지지 않을 때 **예외를 던진다** — 자바가 "네가 정하라"고 요구하는 셈이다.
- 고른 방식: **`RoundingMode.HALF_UP`, 0자리**(원 단위).\
  0.5 이상이면 올린다.\
  19번 누진세가 `DOWN`(버림)을 고른 것과 **다르다** — 도메인마다 따로 정하는 결정이라는 뜻이다.

> **HALF_UP** — 소수점 아래 첫 자리가 5 이상이면 올리고 아니면 버리는, 우리가 학교에서 배운 반올림.\
> 예: 1,234.5 → 1,235, 1,234.4 → 1,234.

- 가입 금액이 0 이하면: **예외** (테스트 `invalidAmount`).\
  0원짜리 보험은 계약으로 성립하지 않는다.
- 1986/6/15생·1억 손계산 (테스트 `birthdayCliff`):

```text
 2026/6/14   만 39  →  구간 20~39  요율 1,000  →  1억 × 1,000 / 1,000 = 100,000,000
 2026/6/15   만 40  →  구간 40~59  요율 1,500  →  1억 × 1,500 / 1,000 = 150,000,000
                                                        하루 차이   50,000,000
```

- 만 30세·1억: **100,000,000원** (테스트 `basicPremium` — 1996/1/1생을 2026/1/1에 보면 만 30세, 요율 1,000).

#### 3. TODO 3 — jumpIfDelayedOneDay

```java
public static BigDecimal jumpIfDelayedOneDay(
        long insuredAmount, LocalDate birthDate, LocalDate on, AgeBasis basis, RateTable table) {
    BigDecimal today = premium(insuredAmount, birthDate, on, basis, table);
    BigDecimal tomorrow = premium(insuredAmount, birthDate, on.plusDays(1), basis, table);
    return tomorrow.subtract(today);
}
```

- **내일의 보험료에서 오늘의 보험료를 뺀다.**\
  계산을 새로 하지 않고 `premium` 을 두 번 부른다 — 그래서 요율표나 나이 규칙이 바뀌어도 자동으로 따라간다.
- 0이면: **그 날은 구간 경계가 아닌 평평한 날**이다.\
  0이 아니면 **바로 그 다음 날이 구간이 바뀌는 날**이다.
- 1986/6/15생·1억:

```text
 jumpIfDelayedOneDay(..., 2026/6/14) = 150,000,000 - 100,000,000 = 50,000,000
 jumpIfDelayedOneDay(..., 2026/6/15) = 150,000,000 - 150,000,000 =          0
                                       ↑ 경계를 지나면 다시 평평하다
```

- 절벽이 반드시 생기는 이유: **구간표는 계단 함수**이기 때문이다.\
  나이가 한 살 오르는 순간 요율이 통째로 바뀌고, 나이는 **하루 만에** 오른다.\
  경계 사이를 매끄럽게 잇는 규칙(선형 보간 같은 것)이 없는 한 계단은 없어지지 않는다.

> **절벽(cliff)** — 입력이 아주 조금 변했는데 출력이 계단처럼 크게 뛰는 지점.\
> 예: 가입일을 하루 미뤘더니 보험료가 5,000만원 오른다. 구간표를 쓰는 도메인의 필연이다.

> **계단 함수(step function)** — 구간 안에서는 값이 일정하다가 경계에서 한 번에 뛰는 함수.\
> 예: 20~39세는 전부 요율 1.0, 40세부터 갑자기 1.5. 39.9세라는 중간값이 없다.

- 도구로 따로 둔 의도: **경계를 사람이 눈으로 찾지 않아도 되게 하려고**다.\
  요율표를 읽으며 "39/40 사이가 경계구나"를 머리로 계산하는 대신, **아무 날짜나 넣고 0인지 보면 된다.**\
  측정 코드가 20,000건을 훑어 절벽을 3건 찾아낸 것이 바로 이 쓰임이다.\
  01번 주차요금이 두 정책을 값으로 올려 갈림을 센 것과 같은 수법 — **결정을 재는 도구를 코드 안에 둔다.**
- "생일 전에 가입하세요" 안내: **`jumpIfDelayedOneDay` 가 0이 아닌 날**에서 나온다.\
  그 값이 곧 "오늘 가입하면 아끼는 금액"이다.

#### 4. 계약으로 주어진 RateTable

- 표준 요율표:

| 구간 | 천분율 | 요율 |
|---|---|---|
| 0 ~ 19 | 800 | 0.8 |
| 20 ~ 39 | 1,000 | 1.0 |
| 40 ~ 59 | 1,500 | 1.5 |
| 60 ~ 200 | 2,500 | 2.5 |

- 나이별 요율 (테스트 `bracketBounds`): **19 → 800, 20 → 1,000, 39 → 1,000, 40 → 1,500, 60 → 2,500.**\
  구간은 **이상 ~ 이하**다.
- 이어짐 검사가 `+1` 인 이유: **나이가 정수**이기 때문이다.\
  19 다음 정수는 20이므로 "빈틈 없음"은 `앞 toAge + 1 == 뒤 fromAge` 가 된다.\
  19번 누진세는 **금액이 연속값**이라 `앞 upperBound == 뒤 lowerBound` 로 맞붙였다(경계값은 "초과~이하"로 한쪽에만 들어간다).\
  **같은 의도(빈틈 없음)인데 값의 종류가 달라 식이 다르다.**

```text
 19번 누진세(금액, 연속)     0 ~ 14,000,000 | 14,000,000 ~ 50,000,000
                              앞 upper == 뒤 lower  (경계값은 "초과" 규칙이 가른다)

 20번 보험(나이, 정수)       0 ~ 19 | 20 ~ 39
                              앞 to + 1 == 뒤 from  (19 다음은 20)
```

- 0~19 다음이 21부터면: **20살인 사람만** 피해를 본다.\
  `ratePermilleFor(20)` 이 어느 줄에도 안 걸려 **예외**가 나므로 가입이 막힌다.\
  (예외가 없었다면 조용히 잘못된 요율이 나왔을 것이다 — 그래서 이어짐 검사와 표 밖 예외가 **세트**다.)
- 표 밖에 예외를 안 던지고 마지막 구간을 쓰면: **표에 없는 사람이 가입된다.**\
  201세라는 입력은 대개 **생년월일 오타**인데, 그럴듯한 답(2,500‰)이 나오니 아무도 모른다.\
  원칙은 **"없는 입력에 그럴듯한 답을 주지 않는다"** 다.
- `Row` 생성자가 막는 것 둘: **① `fromAge < 0` 또는 `toAge < fromAge`**(뒤집힌 구간), **② `ratePermille <= 0`**(0이거나 음수인 요율).
- 생성 시점에 검사하는 이유: **잘못된 표는 아예 존재할 수 없게** 하기 위해서다.\
  계산 시점에 검사하면 **잘못된 표가 이미 메모리에 있고**, 운 나쁜 나이가 들어올 때까지 아무 일도 안 일어난다.\
  생성 시점에 막으면 배포 직후 첫 로딩에서 터진다 — **빨리 터지는 쪽이 싸다.**

> **생성 시점 검증(construct-time validation)** — 객체를 만들 때 규칙을 확인해, 잘못된 상태의 객체 자체를 못 만들게 하는 것.\
> 예: 구간이 안 이어지는 요율표는 `new RateTable(...)` 에서 바로 예외가 난다. 그 표로 보험료를 계산할 기회가 아예 없다.

| | 나이가 다른 경우 | 보험료가 다른 경우 |
|---|---|---|
| 만 vs 연 나이 | **9,978 (50%)** | **440 (2.2%)** |
| 만 vs 보험 나이 | 9,945 (50%) | 441 (2.2%) |

- 대개 같은 이유: **구간 폭이 20년**이기 때문이다.\
  한 살 달라져도 대부분 **같은 구간 안**에 있다.\
  갈리는 것은 딱 **구간 경계에 걸친 사람**뿐이다 — 20년에 한 살이니 약 5%, 실제로는 2.2%.

```text
 나이     18 19 | 20 21 ... 38 39 | 40 41
 요율    800 800| 1000 ............ 1000 |1500

 만 39 / 연 40  →  같은 구간, 보험료 같다   (대부분)
 만 39 / 연 40  →  39와 40 사이가 경계!     (여기서만 갈린다)
```

- 잘 안 드러나는 이유: **50번 중 49번은 틀려도 결과가 같다.**\
  테스트를 몇 건 돌려보고 "맞네" 하기 딱 좋은 비율이다.\
  틀린 코드가 **97.8%의 입력에서 정답을 낸다.**
- 화면에 나이를 안 보여주면: **2.2%의 사람만** 보험료가 이상하다고 느낀다.\
  나머지는 나이가 틀린 줄도 모르고 지나간다.

> **조용한 결함(silent defect)** — 코드가 틀렸는데 대부분의 입력에서 결과가 같아 오래 안 드러나는 결함.\
> 예: 나이 계산이 20,000건 중 9,978건에서 틀리는데 보험료는 440건만 다르다. 사용자도 테스트도 대부분 못 잡는다.

#### 6. 측정 둘 — 빈도와 합계는 다른 질문

- 세 방식의 보험료 합계 (`totalsDifferLessThanOnePercent`):

| | 합계 |
|---|---|
| 만 나이 | 2,926,180,000,000 |
| 연 나이 | 2,951,930,000,000 |
| 보험 나이 | 2,951,790,000,000 |

- 만 나이 vs 연 나이: **약 0.88%** 차이.\
  테스트가 `천분율로 8` 로 못 박았다(정수 퍼센트로는 0).
- 연 나이 vs 보험 나이: **나이는 9,945건이나 갈리는데 합계는 거의 같다**(약 0.005%).\
  둘은 서로 다른 날 오르지만 **1년 전체로 보면 비슷한 분포**가 되기 때문이다.
- 따로 물어야 하는 이유: **두 질문이 서로 다른 것을 재기 때문**이다.\
  "자주 갈리나"는 **개별 손님의 경험**(내 보험료가 맞나)을 재고, "합계가 다르나"는 **회사의 손익**을 잰다.\
  9,945건이 갈려도 회사 장부는 0.005%만 움직인다 — 회사는 멀쩡한데 만 명의 손님 각자는 틀린 값을 받는다.
- 안 나누면 생기는 잘못된 판단: **"합계가 0.005%밖에 안 다르니 어느 나이를 쓰든 상관없다"** 는 결론이다.\
  반대로 **"절반이 갈리니 큰 문제다"** 도 틀렸다 — 회사 손익으로는 작다.\
  **두 숫자를 다 봐야 "누구에게 얼마나 문제인가"를 말할 수 있다.**

#### 7. 측정 셋 — 하루 절벽

- 20,000건 중 하루 차이로 뛰는 경우: **3건**, 최대 **50,000,000원** (`theCliffIsRareButHuge`).
- 확률: **0.015%.**
- 경고하는 것: **평균·빈도로만 위험을 재면 안 된다.**\
  0.015%는 "무시해도 되는 숫자"처럼 보이지만, **그 3명에게는 5,000만원**이다.\
  기댓값(0.015% × 5,000만 = 7,500원)으로 뭉개면 문제가 사라진 것처럼 보인다.

```text
 빈도로 보면      3 / 20,000  =  0.015 %      "없는 거나 마찬가지"
 당사자로 보면    50,000,000 원                "인생이 걸린 금액"

 같은 사실을 두 가지로 읽을 수 있다. 둘 다 봐야 한다.
```

- 그냥 두면: **하필 그 날에 가입한 사람**이 "하루 차이로 5,000만원"을 알게 되고, **불공정하다고 느낀다.**\
  민원과 분쟁으로 돌아오고, 3건이라는 빈도 때문에 **재현도 어렵다.**\
  그래서 안내(상령일 고지)나 완화(구간 사이 보간)를 **미리** 정해야 한다.

#### 8. 측정 넷 — 생월이 전부를 정한다

- 만 나이와 연 나이가 다른 날 수 (2026년 365일, `birthMonthDecidesEverything`):

| 생일 | 갈리는 날 |
|---|---|
| 12월 25일 | **358 / 365** |
| 1월 1일 | **0 / 365** |

- 생월에 따라 다르게 틀리는 이유: **연 나이는 1/1에 오르고 만 나이는 생일에 오른다.**\
  둘 사이의 **간격이 곧 갈리는 기간**이다.\
  1월 1일생은 두 날이 같은 날이라 간격이 0이고, 12월 25일생은 거의 1년이다.

```text
 1/1 생     1/1 둘 다 +1 ─────────────────────────────  갈리는 날 0
 12/25 생   1/1 연 나이만 +1 ──────────── 12/25 만 나이 +1
            └──────── 358일 동안 갈린다 ────────┘
```

- 1월생 데이터로 시험하면: **이 결함이 절대 안 보인다.**\
  같은 코드가 **태어난 달에 따라 100% 틀리거나 0% 틀린다** — 코드는 그대로인데 테스트 데이터만 바뀌어도 통과/실패가 뒤집힌다.
- 19번과 같은 교훈: **"첫 구간 안 소득으로만 시험하면 0건 갈리고, 경계 하나만 넘기면 10,000건 전부 갈린다."**\
  둘 다 **테스트 데이터가 결함을 통째로 숨긴 사례**다.\
  14번(유효기간을 다 같게), 15번(조건 하나짜리 쿠폰)까지 같은 모양이 네 번 반복된다.

> **가려진 결함(masked bug)** — 코드에 있는데 테스트 데이터가 우연히 특수해서 드러나지 않는 결함.\
> 예: 1월 1일생만으로 시험하면 만 나이와 연 나이가 365일 내내 같아서, 둘을 혼동한 코드도 완벽해 보인다.

#### 9. 측정 다섯 — 구간을 좁히면 나이가 중요해진다

- 구간 폭별 갈림 (`narrowerBracketsMakeAgeMatterMore`, 20,000건):

| 구간 폭 | 보험료가 갈리는 경우 |
|---|---|
| 20년 | 440 |
| 10년 | 978 |
| 5년 | **2,011** |

- 느는 이유: **경계가 많아지기 때문**이다.\
  나이 한 살 차이가 문제가 되는 것은 **그 사이에 경계가 있을 때**뿐이다.\
  구간이 좁아지면 경계 밀도가 올라가고, 같은 "한 살 차이"가 경계에 걸릴 확률이 커진다.

```text
 구간 폭 20년   경계가 200살까지 약 10개    한 살 차이가 경계에 걸릴 확률 낮음
 구간 폭  5년   경계가 약 40개              확률이 4배 ─→ 갈림도 대략 4~5배
```

- "요율을 더 정교하게"가 "나이를 더 정확하게"를 부르는 이유: **정교한 요율표는 경계가 많고, 경계가 많으면 입력의 오차가 그대로 금액 오차가 된다.**\
  구간이 넓을 때는 나이가 한 살 틀려도 대개 묻혔는데, 좁아지면 안 묻힌다.
- 설계에 주는 교훈: **따로 있어 보이는 두 결정이 붙어 있다.**\
  "요율표를 세분화하자"는 상품 기획의 결정이고 "나이를 어떻게 세나"는 구현의 결정인데, 앞의 결정이 **뒤의 결정의 비용을 올린다.**\
  그래서 요율표를 촘촘하게 바꾸는 변경은 **나이 계산 코드를 다시 검토하라는 신호**로 읽어야 한다.

#### 10. 생각해볼 것

> 원본 README가 답을 주지 않고 던진 질문 — (원본에 근거 없음 — 내 추론) 표시.

- **계약일 기준인가 개시일 기준인가**: (내 추론) 지금 코드는 **`on` 이라는 날짜 하나만 받는다.**\
  즉 **누가 그 날짜를 정하는지가 코드 밖에 있다** — 이것 자체가 미정 상태다.\
  실무적으로는 **개시일(보장이 시작되는 날)** 이 자연스럽다. 위험을 떠안기 시작하는 날의 나이가 요율의 근거이기 때문이다.\
  그런데 그 사이에 생일이 있으면 **계약할 때 안내한 보험료와 실제 보험료가 달라진다** — 손님 입장에서는 "말이 바뀌었다"가 된다.\
  그래서 **계약일 기준으로 안내하고 개시일로 확정**하는 구조라면, 그 사이에 생일·상령일이 있는지 **계약 시점에 미리 경고**해야 한다.\
  `jumpIfDelayedOneDay` 를 계약일부터 개시일까지 훑으면 그 경고를 자동으로 만들 수 있다.
- **갱신 시 나이 재계산**: (내 추론) 둘 다 실제로 쓰이는 방식이라 **약관이 정할 문제**다.\
  **재계산**하면 요율이 나이에 맞게 오르지만, 갱신 때마다 보험료가 뛰어 손님이 이탈한다 — 특히 60세 경계를 넘을 때 800 → 2,500 으로 한 번에 뛴다.\
  **처음 나이를 고정**하면 손님은 안정적이지만 **회사가 위험을 덜 반영**하게 된다(나이가 들수록 실제 위험은 커지므로).\
  코드 관점에서 중요한 것은 **어느 쪽이든 그 결정이 데이터로 남아야 한다**는 것이다 — 계약에 `요율산정일` 같은 필드가 있어야 나중에 "왜 이 요율인가"를 답할 수 있다.\
  지금 `premium` 이 `on` 을 인자로 받는 구조는 두 방식 다 표현할 수 있다(고정하려면 계약 시점의 날짜를 계속 넘기면 된다).
- **2월 29일생의 평년 생일**: (내 추론) 자바가 이미 답을 정해뒀다 — **`plusYears` 는 2월 28일로 당긴다.**\
  `LocalDate.of(2000,2,29).plusYears(1)` 은 2001-02-28 이다.\
  그래서 이 코드에서 2/29생의 만 나이는 **평년 2월 28일에 오른다**(법도 대체로 그렇게 본다).\
  주의할 곳은 **보험 나이**다 — `lastBirthday` 가 2/28 로 당겨진 뒤 6개월을 세므로 **상령일이 8/28** 이 된다(윤년에는 8/29).\
  즉 **윤년이냐에 따라 상령일이 하루 움직인다.** 드물지만 실제로 존재하는 갈림이고, 테스트에 2/29생이 없으면 안 보인다.
- **경계 직전 가입 안내**: (내 추론) **해야 한다고 본다.**\
  안 하면 손님은 나중에 알게 되고, 그때는 **회사가 숨겼다고 느낀다** — 5,000만원짜리 정보를 안 알려준 셈이 된다.\
  다만 안내가 **"오늘 안 하면 손해"라는 압박 판매**로 변질될 수 있어, 표현을 사실 위주로 두어야 한다("귀하의 상령일은 12/15 입니다").\
  기술적으로는 이미 도구가 있다 — `jumpIfDelayedOneDay` 가 0이 아닌 날을 찾아 그 금액을 그대로 보여주면 된다.\
  더 근본적인 해법은 **절벽 자체를 없애는 것**(구간 사이를 매끄럽게 잇는 요율)인데, 그러면 요율표가 "표"가 아니게 되어 설명과 심사가 어려워진다.

#### 11. 연결

- **19번 누진세와의 결정적 차이**: **경계의 값이 다르다.**\
  19번은 경계에서 **걸친 금액이 0이라 어느 구간에 넣어도 같은 답**이 나왔다 — 경계가 공짜였다.\
  20번은 경계에서 **요율이 통째로 바뀌어 5,000만원이 뛴다** — 경계가 비싸다.\
  같은 "구간표"인데 **누진세는 연속 함수, 보험료는 계단 함수**이기 때문이다.\
  구간표를 봤다고 "경계는 안 중요하다"고 넘기면 안 되는 이유가 여기 있다.
- **"첫 구간 안 테스트" ↔ "1월생 테스트"**: 둘 다 **테스트 데이터의 특수성이 결함을 0으로 만든 사례**다.\
  19번은 소득 범위가, 20번은 생월이 그 역할을 했다.\
  교훈: **"통과했다"는 "코드가 맞다"가 아니라 "이 데이터로는 안 틀렸다"이다.**
- **14·15번과 같은 모양**: 14번은 유효기간을 균일하게 두면 두 차감 규칙이 안 갈렸고, 15번은 조건이 하나면 두 안내 전략이 안 갈렸다.\
  20번은 1월생이면 두 나이가 안 갈린다.\
  **결정이 갈리는 입력을 일부러 만들지 않으면, 그 결정이 존재하지 않는 것처럼 보인다** — 네 챕터가 같은 말을 한다.
- **"입력 자체가 여러 정의를 갖는다"의 다른 예**: **"매출"**(인식 시점이 주문·배송·정산 중 언제인가), **"활성 사용자"**(일·주·월 기준, 로그인인가 행동인가), **"근무일"**(달력일·영업일·실근무일), **"재고"**(물리 재고·가용 재고·예약분 제외), **"체류 시간"**(탭 포커스인가 페이지 오픈인가).\
  전부 **표(계산 규칙)는 단순한데 입력의 정의가 여럿**인 경우다.\
  공통 처방도 같다 — **정의를 값(enum)으로 올려 두 해석을 나란히 재본다.**
- **반올림 시점**: 17번(장바구니 할인)에서 "항목마다 반올림할까 합계에서 한 번 할까"로 처음 나왔고, 19번에서 지방소득세로 다시 나왔다.\
  여기서는 **천분율 나눗셈**이 같은 자리다.\
  반복되는 규칙: **나눗셈이 있는 곳에는 반드시 반올림 결정이 있고, 그것은 계산이 아니라 계약이다.**\
  19번은 `DOWN`, 20번은 `HALF_UP` 을 골랐다 — **도메인마다 다르게 정해도 되지만, 정하지 않으면 안 된다.**
