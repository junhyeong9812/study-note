# domain-modeling-basic/29-transfer-fare — 정리 (힌트)

## 해결하는 문제

"환승 30분, 최대 4회"를 그대로 구현하면 두 사람이 서로 다른 요금을 내는 코드를 짜고, 둘 다 자기가 규칙대로라고 믿는다.

```text
  요금표: "10km 1,250원, 5km마다 100원"     ← 본문 (누구나 같게 구현)
  각주:   "환승 30분, 최대 4회"              ← 여기에 미정 결정이 셋

    기준점   하차부터? 승차부터?      → 총 매출 47.6% 차이 (1.5배)
    경계값   정확히 30분은?           → 여정 4.7%가 갈림 (하루 천만 명이면 47만 명)
    한도     5번째 환승은?            → 거부면 요금을 못 내는 사람이 생김
```

셋을 정하지 않으면: 오래 탄 사람일수록 할인을 못 받거나(승차 기준), 경계에 몰린 열차 시각표에서 대량으로 갈리거나, 5번째 환승을 한 사람이 개찰구를 못 나간다.\
쉬운 예: 통화 요금의 "무료 통화 묶음" — 끊고 몇 분 안에 다시 걸면 한 통화로 치는지, 정확히 그 분은 포함인지.\
똑같은 구조다: 탄 것들을 시각 순으로 훑어 `connects`면 같은 여정에 붙이고 아니면 새 여정을 열어(`split`), 여정 단위로 거리 합에 요금을 한 번 매긴다.\
실무 예: 교통카드 정산, 게임 콤보 판정 시간, 세션 타임아웃(마지막 요청 기준인가 첫 요청 기준인가).

### 한눈에 — 쉽게 말하면

**환승 요금 = 지하철 여러 번 탄 것을 "한 번 탄 것처럼" 묶어서 계산하기.**

- 1호선을 타고 내려서 2호선으로 갈아탔다. 카드값이 두 번 나가면 억울하다 — 그래서 "30분 안에 갈아타면 이어서 탄 것으로 친다"가 환승 규칙이다.
- 그런데 **"환승 30분"이라는 한 줄이 어디서부터 30분인지를 안 정했다**:

```text
  1호선   09:00 승차   09:20 하차
  2호선                             09:45 승차

    하차 기준   09:20 → 09:45 = 25분   환승이다
    승차 기준   09:00 → 09:45 = 45분   환승이 아니다

  같은 한 사람의 같은 이동인데 답이 다르다.
```

- 이런 "안 정해진 자리"가 셋이다: **기준점**(어디서부터 재나) · **경계값**(정확히 30분이면?) · **한도**(5번째 환승은 거부인가 새 여정인가). 셋 다 "환승 30분, 최대 4회"라는 한 줄에서 안 읽힌다.
- 실무 예: 교통카드 정산, 통화 요금의 무료 통화 묶음, 게임의 콤보 판정 시간.

## 동작·원리

### 전체 흐름

```text
Ride (한 번 타고 내림 — 승차·하차 시각, 거리, night() 판정)
        │ 시각 순 목록
        ▼
split(rides)  ── connects(앞, 뒤)? ──┬─ 이어짐 + 한도 남음 → 같은 Journey에 붙임
  여정으로 묶기                        └─ 아니면 → 새 Journey 시작 (거부 아님!)
        │
        ▼
Journey (묶인 한 여정: 거리 합, 환승 횟수 = 탄 횟수 - 1)
        │
        ▼
fareOf(journey) = FareRule.fareFor(거리 합)   ← 기본 10km 1,250원 + 5km마다 100원(올림)
totalFare = 여정별 요금의 합
```

### 규칙 1 — 기준점(WindowBase): 매출이 1.5배 갈리는 한 단어

**어떤 요구사항인가**: "앞 구간이 끝나고 30분 안에 타면 환승."— 그런데 "끝나고"가 하차인가 승차인가?

**예시 손계산** (위 그림): 하차 기준 25분 → 환승(요금 한 번), 승차 기준 45분 → 환승 아님(요금 두 번).

- **승차 기준의 숨은 부작용**: 오래 탄 사람일수록 앞 구간 승차가 옛날이라 창이 먼저 닫힌다 — **오래 탄 사람일수록 환승을 못 받는다.** 할인이 필요한 쪽이 못 받는다.
- **측정** (여정 2,000건, 승차 8,009회): 요금이 갈린 여정 **1,470/2,000(73.5%)**, 하차 기준 총액 5,616,750원 vs 승차 기준 8,290,150원 — **차이 2,673,400원(47.6%)**, 한 건 최대 4,600원. **같은 규칙을 두 사람이 구현하면 총 매출이 1.5배 갈리고, 둘 다 자기 코드가 규칙대로라고 생각한다.**
- 참고로 환승 할인 자체가 총액의 45.6%다(환승 안 치면 10,320,950원 → 치면 5,616,750원) — **매출의 절반이 이 규칙 하나에 달렸는데** 요금표에는 거리·금액만 있고 "환승 30분"은 각주 한 줄이다.

### 규칙 2 — 경계값(BoundaryRule): 정확히 30분이면?

**예시**: 대기 정확히 30분. INCLUSIVE면 `minutes <= 30` → 환승, EXCLUSIVE면 `minutes < 30` → 환승 아님.

- **측정**: 경계값으로 갈리는 여정은 93/2,000(4.7%) — 기준점(73.5%)에 비해 작아서 "사소한 것"으로 분류되고 안 정해진다. **하루 천만 명이면 47만 명이다.**
- 경계를 정확히 밟는 짝은 6,053개 중 86개(1.4%)뿐인데, 이것은 **분 단위로 무작위인 자료**에서다. 실제 환승은 열차 시각표에 맞춰 특정 간격에 몰린다 — **몰리는 자리가 하필 경계면 1.4%가 아니다.**

### 규칙 3 — 한도(maxTransfers): "거부"가 아니라 "새 여정"

**어떤 요구사항인가**: "환승은 최대 4회."

**예시**: 5번째 환승을 시도한 사람 — 거부로 만들면 그 사람은 **요금을 아예 못 낸다.** 그런 사람은 실제로 있고, 그 사람도 개찰구를 나가야 한다.

```text
  탄 것:  R1 → R2 → R3 → R4 → R5 → R6   (전부 30분 안에 이어짐, 한도 4회)

  거부 방식:   R6에서 예외 → 정산 불가         ← 함정
  새 여정:    [R1 R2 R3 R4 R5] [R6 ...]      ← 한도가 차면 거기서 여정을 끊는다
```

코드: `split`에서 `roomLeft = current.size() - 1 < maxTransfers` — 자리가 없으면 현재 여정을 닫고 새 여정을 연다. **측정**: 묶인 여정 3,837개 중 한도 4회를 다 쓴 것이 346개(9%) — 한도가 실제로 작동하는 자리가 9%이고, 거기서 "거부"와 "새 여정"이 갈린다.

**모델링 교훈**: 한도·제한을 만나면 "넘으면 어떻게 되나"까지 정해야 한다 — 예외는 도메인에서 갈 곳 없는 사람을 만든다.

### 규칙 4 — 심야: 어느 구간으로, 어느 시각으로 판정하나

- **심야 = 21시~다음 날 7시, 환승 인정 60분.** 두 번의 결정이 숨어 있다:
  1. **어느 구간이 심야인가** — `connects`는 **앞 구간**의 `night()`를 본다. 환승 시간은 앞 구간이 끝난 뒤의 대기 시간이고, **그 대기가 심야였느냐**를 묻는 것이기 때문.
  2. **한 구간의 심야는 어느 시각인가** — `night()`는 **승차 시각**으로 판정한다. 하차로 하면 20:50에 타서 21:10에 내린 사람이 심야가 된다. 둘 다 말이 되고, 그래서 정해두지 않으면 갈린다.
- **측정**: 고르게 흩어진 자료에서는 심야 승차가 3,461/7,978(43%) — 21~7시가 하루의 10시간(41.7%)이니 거의 그대로. **실제 승차는 출퇴근에 몰려 심야 비율이 훨씬 낮다** — 그러면 심야 규칙을 틀려도 잘 안 드러난다. 28번의 차단 방향과 같은 자리다(결함은 있는데 노출 빈도가 낮아 문의로만 잡히는 자리).

### 규칙 5 — 거리 요금: 올림이다

**예시 손계산** (서울 규칙: 기본 10km 1,250원, 5km마다 100원):

```text
   9,999 m → 1,250     기본 거리 안
  10,000 m → 1,250     기본 거리는 포함
  10,001 m → 1,350     1m라도 넘기면 한 단위 (올림)
  15,000 m → 1,350
  15,001 m → 1,450
```

- 내림으로 하면 14,999m인 사람이 100원을 덜 낸다. 올림 나눗셈은 `(over + extraMeters - 1) / extraMeters`.
- 여정 요금은 **구간별 요금의 합이 아니라 거리 합으로 한 번** 계산한다(`fareOf`) — 이게 환승 할인의 실체다.

## 쓰이는 자료구조·알고리즘

- **시각 순 선형 스캔으로 구간 묶기(`split`)** — 정렬된 탑승을 한 번 훑으며 앞 구간과 이어지면 같은 묶음, 아니면 새 묶음을 연다. 겹치는 구간을 합치는 [sweeping](../../../algorithm/30-sweeping/2-summary.md)과 같은 한 방향 스캔이고 O(n)이다. **입력이 시각 순이라는 전제** 위에서만 맞다.
  - *스윕(sweep)*: 정렬된 축(여기서는 시각)을 따라 한 번 지나가며 상태(현재 여정)만 갱신하는 방식.
- **시간 산술(`java.time`)** — `Duration.between(from, next.boardedAt()).toMinutes()`로 대기 시간을 잰다. `toMinutes()`는 초를 **버리므로** 30분 59초는 30분이다. `LocalDateTime`은 시간대가 없다.
- **경계 비교 한 글자(`<=` vs `<`)** — `BoundaryRule`이 비교 연산자 하나를 고른다. [01-parking-fee](../01-parking-fee/2-summary.md)의 "10분까지 무료"와 같은 자리.
- **올림 나눗셈(정수 산술)** — `(over + extraMeters - 1) / extraMeters`. 부동소수 없이 "1m라도 넘기면 한 단위"를 만든다.
- **전략을 값으로(enum 파라미터)** — `WindowBase`·`BoundaryRule`은 생성자로 받는 값이라 같은 입력을 두 규칙으로 나란히 돌려 차이를 잴 수 있다(측정 테스트의 방법).
- **규칙 숫자를 record로 분리(`FareRule`)** — 기본 거리·단가·환승 분·한도를 한 값 객체에 모아 요금 개정 = 숫자 교체가 된다. 유효기간을 붙이면 [advanced/09-policy-version](../../advanced/09-policy-version/2-summary.md)의 버전 규칙이 된다.

## 적용 — 풀어나가는 법

"N분 안에 이어지면 하나로 친다"는 규칙(환승·콤보·세션·통화 묶음)을 만나면 이 순서로 결정을 내린다.\
① 기준점 — 앞 것의 **끝**부터인가 **시작**부터인가를 적고, 누가 손해 보는지(오래 탄 사람) 확인한다 → ② 경계값 — 정확히 N분의 포함 여부를 `<=`/`<`로 적는다 → ③ 한도 — 넘으면 **거부가 아니라 새 묶음**으로 정한다 → ④ 조건부 창(심야 60분)은 **어느 구간의 어느 시각**으로 판정하는지 적는다 → ⑤ 두 해석을 나란히 돌려 차이를 **금액으로** 재고, 29분·30분·31분처럼 경계 양옆을 테스트에 박는다.\
아래 문제 절이 이 순서를 TODO 1~3으로 시킨 것이다.

## 장애 시나리오와 대처

**1. 단말기 지연 업로드로 탑승 기록이 시각 순이 아니다**

- 현상: 오프라인이던 버스 단말기가 나중에 기록을 올려, 앞 구간이 뒤 구간보다 **늦게** 도착한다.
- 보이는 형태: 같은 사람의 여정이 둘로 쪼개져 요금이 두 번 매겨진다. `split`은 예외 없이 돌고, 하차 기준에서는 "시간이 거꾸로 간" 짝을 `connects`가 false로 처리해 새 여정을 연다. 민원 "환승이 안 됐다"가 특정 노선·시간대에 몰린다.
- 원인: `split`은 "시각 순으로 들어온다고 본다" — 정렬은 호출자의 책임인데 도착 순서를 그대로 넣었다. 뒤 승차가 기준점보다 이르면 `connects`가 false를 돌려주는 방어(경계 절 마지막 행)는 **음수 시간**을 막을 뿐 순서를 고쳐 주지 않는다.
- 대처: `split` 앞에서 `boardedAt`으로 정렬하고, 정산은 실시간 확정이 아니라 마감 후 재계산으로 최종 확정한다. 시간 역행 짝의 개수를 지표로 내보내 지연 업로드를 관측한다.

**2. 승차 단말과 하차 단말의 시계가 다르다**

- 현상: 정확히 경계 근처(29~31분)의 환승 판정이 단말기 조합에 따라 흔들린다.
- 보이는 형태: 같은 역·같은 간격의 환승인데 어떤 날은 1여정, 어떤 날은 2여정이다. 단말 시계 오차에 분 단위 절삭(`toMinutes()` — 초를 버린다)까지 겹쳐, 경계 근처 판정이 오차만큼 흔들린다.
- 원인: 시각을 각 단말의 로컬 시계로 찍었고 `LocalDateTime`에는 시간대·동기 정보가 없다. 규칙은 분 단위인데 시계 오차가 분 단위면 경계 짝(6,053개 중 86개, 시각표에 몰리면 더 많다)이 전부 흔들린다.
- 대처: 단말 시계를 NTP 등으로 동기하고 기록에는 서버 수신 시각도 함께 남긴다. 경계 ±1분 안의 판정 건수를 지표로 두어 시계 문제를 조기에 본다. 시간대가 둘 이상인 서비스라면 `LocalDateTime` 대신 시간대 있는 시각을 쓴다.

**3. 요금표를 덮어쓰고 과거 여정을 재정산했더니 금액이 달라진다**

- 현상: 요금 인상 뒤 이의 제기로 지난달 여정을 다시 계산하니 청구액과 다르다.
- 보이는 형태: 재계산 결과가 원 청구보다 요금 인상폭만큼 높다. 개정일 전 여정 전부에서 난다.
- 원인: `FareRule`은 숫자를 분리했지만 **유효기간이 없다**. `seoul()`을 새 숫자로 바꿔 배포하면 과거 여정도 새 요금표로 계산된다(정답 12번 참고 — 어느 요금표를 고르는 책임은 호출자에 있다).
- 대처: 요금표에 발효일을 붙여 여정의 첫 승차 시각으로 요금표를 고르고, 청구 기록에 적용한 요금표 버전을 남긴다. 규칙 버전 관리는 [advanced/09-policy-version](../../advanced/09-policy-version/2-summary.md).

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 기준점 미정 | WindowBase로 명시 — 승차 기준은 오래 탄 사람이 할인을 못 받는다 |
| 정확히 30분 미정 | BoundaryRule로 명시 — `<=` vs `<` |
| 한도 초과를 거부로 | 새 여정 시작 — 요금 못 내는 사람이 생기면 안 된다 |
| 심야를 뒤 구간으로 판정 | 앞 구간의 night() — 대기가 심야였느냐를 묻는 것 |
| 심야를 하차 시각으로 판정 | 승차 시각 — 20:50 승차가 심야가 되면 안 된다 |
| 거리 요금 내림 | 올림 — 14,999m가 100원 덜 내는 것을 막는다 |
| 하차가 승차보다 빠른 자료 | `Ride` 생성자에서 즉시 거부 |
| 뒤 승차가 기준점보다 이른 경우 | `connects`가 false — 음수 시간 방지 |

**변종 검증**: 고칠 것이 없었다 — 변종 14개 전부 잡혔다. 기준점 둘·경계값 둘·심야·한도를 계약 테스트에서 **두 규칙을 나란히 놓고** 확인하기 때문. 특히 "**29분과 31분에서는 두 규칙이 같다**"는 테스트가 있어야 **경계에서만 갈린다는 사실 자체**가 문서로 남는다.

## 핵심 문장

- "환승 30분, 최대 4회" 한 줄에는 **기준점·경계값·한도 처리라는 세 개의 미정 결정**이 숨어 있다 — 도메인 모델링은 그 미정을 enum과 규칙으로 드러내 적는 일이다.
- 기준점 한 단어(하차/승차)로 **총 매출이 47.6% 갈린다** — 그리고 두 구현 다 자기가 규칙대로라고 생각한다.
- 경계값은 4.7%에서만 갈려서 "사소한 것"이 되지만, 하루 천만 명이면 47만 명이고, 실제 트래픽은 경계에 몰릴 수 있다.
- **한도는 거부가 아니라 새 여정이다** — 5번째 환승을 한 사람도 개찰구를 나가야 한다.
- 심야처럼 **실제 분포에서 드물게 밟히는 규칙은 틀려도 안 드러난다** — 테스트가 그 자리를 명시적으로 박아야 한다(29분/30분/31분 나란히).

### 용어 풀이

- **환승(transfer)**: 내렸다가 정해진 시간 안에 다시 타서 한 여정으로 이어지는 것.
- **여정(Journey)**: 환승으로 이어진 탑승들의 묶음. 요금은 여정 단위로 거리 합에 한 번 매긴다.
- **기준점(WindowBase)**: 환승 시간을 재기 시작하는 시각 — 앞 구간의 하차(FROM_ALIGHT) 또는 승차(FROM_BOARD).
- **경계값(BoundaryRule)**: 정확히 30분일 때의 판정 — 포함(INCLUSIVE, `<=`) / 제외(EXCLUSIVE, `<`).
- **한도(maxTransfers)**: 여정 하나에 인정하는 환승 횟수. 넘으면 새 여정이 시작된다.
- **심야(night)**: 21시~다음 날 7시. 승차 시각으로 판정하고, 환승 인정이 60분으로 늘어난다.
- **올림 나눗셈(ceiling division)**: `(over + unit - 1) / unit` — 1m라도 넘기면 한 단위로 세는 계산.
- **FareRule**: 요금의 숫자들(기본가·단위·환승 시간·한도)을 코드에서 분리해 모은 record. 요금 개정 = 숫자만 교체.
- **경계 케이스(boundary case)**: 규칙의 딱 끝값(정확히 30분, 정확히 10,000m). 구현이 갈리는 단골 자리.
- **각주 규칙**: 요금표 본문이 아니라 각주 한 줄로 적힌 규칙 — 그런데 매출의 절반을 정한다.
