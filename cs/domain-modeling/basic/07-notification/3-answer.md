### A. 과제 (Scheduler.java 의 TODO 1~4)

#### 0. 요구사항 한 줄

- 안 들어 있는 결정 다섯: **① "밤"의 범위**(몇 시~몇 시) **② 끝 시각 포함 여부** **③ 걸린 알림을 어떻게 하나**(버림/미룸/흩음) **④ 미룬 것을 흩는 간격** **⑤ 중복 제거 창과 그 키.**

> **조용 시간(quiet hours)** — 알림을 보내지 않기로 정한 하루 중의 시간대.\
> 예: `22:00~08:00` 으로 두면 밤 10시부터 아침 8시 전까지는 알림이 안 나간다.

- "밤"의 범위가 코드 모양을 바꾸는 이유: `22:00~08:00` 처럼 **자정을 걸치면** 판정식이 `and` 에서 `or` 로 뒤집힌다.\
  `09:00~18:00` 처럼 안 걸치면 그대로다.\
  설정으로 받는 값이라 어느 쪽이 올지 모르므로 **한 코드가 두 경우를 다 다뤄야 한다.**

> **자정을 걸치는 구간(wrap-around)** — 시작 시각이 끝 시각보다 뒤라서, 날짜를 넘어가며 이어지는 구간.\
> 예: 22시~8시는 시계 위에서 22 → 23 → 0 → … → 7 로 한 바퀴 돌아가므로, "22 이상이면서 8 미만"인 시각은 하나도 없다.

- 걸린 알림 처리: 이 문장은 **전혀 말해주지 않는다.**\
  "안 보낸다"는 버린다는 뜻일 수도, 나중에 보낸다는 뜻일 수도 있다.
- 아무도 반대 안 하는데 문제가 나오는 이유: 규칙 자체는 옳지만 **그 규칙이 만드는 부작용이 규칙 문장 밖에 있다.**\
  알림의 41%가 걸리고(양), 미룬 것이 한 시각에 몰린다(분포).
- 재는 법: **걸린 건수**(양)와 **peakBurst = 같은 시각 최대 발송 건수**(분포).\
  발송 총량만 세면 몰림이 안 보인다.

#### 1. TODO 1 — nextAllowed

```java
if (!quiet.contains(at.toLocalTime())) {
    return at;
}
LocalDateTime end = at.toLocalDate().atTime(quiet.to());
return end.isAfter(at) ? end : end.plusDays(1);
```

- `시작 <= t < 끝` 으로 쓰면: `22 <= t && t < 8` 은 **어떤 시각도 만족하지 않는다** → 조용 시간이 **통째로 사라진다.**
- 위험한 이유: 예외도 안 나고 로그도 안 남는다.\
  알림이 밤새 그냥 나간다 — **아무도 모른다.**\
  사용자 민원으로만 발견된다.

> **조용한 실패(silent failure)** — 프로그램이 에러를 내지 않고 정상처럼 끝나는데, 결과만 틀린 것.\
> 예: 조용 시간 판정식이 늘 거짓이면 예외 하나 없이 잘 돌아가고, 다만 밤새 알림이 나갈 뿐이다.

- 올바른 판정식 (`QuietHours.contains`):

```java
if (crossesMidnight()) {
    return !time.isBefore(from) || time.isBefore(to);   // or
}
return !time.isBefore(from) && time.isBefore(to);       // and
```

- 안 걸치는 경우도 다뤄야 하는 이유: 조용 시간은 **설정값**이다.\
  "업무 시간에 조용"(09:00~18:00) 같은 설정이 들어올 수 있고, 어느 쪽이 올지는 컴파일 시점에 모른다.
- 22:00 은 **포함**(시작 시각 포함), 08:00 은 **미포함**(끝 시각 미포함).\
  06번의 "끝은 미포함"과 같은 관례.

> **반열린 구간(half-open interval)** — 한쪽 끝은 포함하고 반대쪽 끝은 빼는 구간.\
> 예: 조용 시간 22:00~08:00 에서 22:00 정각은 조용 시간이고 08:00 정각은 이미 아니다 — 그래서 8시에 바로 보낼 수 있다.

- 발송 시각:

```text
  조용 시간 22:00 ~ 08:00

  3/1 23:00  ──►  3/2 08:00     그날 8시는 이미 지났다 → 다음날
  3/2 02:00  ──►  3/2 08:00     그날 8시가 아직 안 왔다 → 같은 날
  3/2 12:00  ──►  3/2 12:00     조용 시간이 아니다 → 그대로
```

- 날짜 갈림의 판정: **그날 날짜의 `quiet.to()` 를 만들어 보고, 그것이 지금보다 뒤면 그대로·아니면 +1일.** `end.isAfter(at) ? end : end.plusDays(1)`.
- `22:00 ~ 22:00` 을 막는 이유: **하루 종일 조용인지 한 순간도 아닌지 둘 다 말이 된다.**\
  애매한 값을 만들 수 있게 두면 두 해석이 코드 곳곳에서 갈린다 — 그래서 **생성 시점에 거부**하고, "하루 종일 조용"이 필요하면 그걸 표현하는 다른 수단을 둔다.

> **만들 때 막기(생성 시점 검증)** — 말이 안 되는 값을 계산할 때가 아니라 객체를 만드는 순간에 거부하는 것.\
> 예: 시작과 끝이 같은 조용 시간은 아예 만들어지지 않게 하면, 그 값을 읽는 모든 코드가 애매함을 안 만난다.

#### 2. TODO 2 — plan

```java
List<Notification> deduped = dedupe(requested, dedupeWindow);   // ① 먼저

List<Notification> planned = new ArrayList<>();
Map<LocalDateTime, Integer> deferredAt = new HashMap<>();
for (Notification n : deduped) {
    if (!quiet.contains(n.at().toLocalTime())) {   // 조용 시간이 아니면 손 안 댄다
        planned.add(n);
        continue;
    }
    if (policy == QuietPolicy.DROP) {
        continue;                                   // 버린다
    }
    LocalDateTime target = nextAllowed(n.at(), quiet);
    if (policy == QuietPolicy.DEFER_AND_SPREAD && spread != null && !spread.isZero()) {
        int index = deferredAt.merge(target, 1, Integer::sum) - 1;   // 같은 목표 시각의 몇 번째인가
        target = target.plus(spread.multipliedBy(index));
    }
    planned.add(new Notification(n.userId(), n.kind(), target));
}
```

- 순서를 반대로 하면: 미루기가 먼저 돌면 **밤에 걸린 알림이 전부 `08:00` 이 된다.**\
  그 다음 중복 제거를 돌리면 같은 사람·같은 종류의 **23:00 알림과 02:00 알림이 같은 시각(08:00)이 되어** 1시간 창 안의 중복으로 판정돼 하나가 버려진다.
- 한 문장: **서로 다른 알림이 미루기 때문에 같아 보이게 되고, 그래서 서로를 지운다.**\
  그래서 순서가 계약이다 — 측정에서도 순서를 지키면 `plan` 결과 건수가 `dedupe` 결과와 정확히 같다(3,479건).

> **파이프라인 순서(pipeline order)** — 변환을 여러 단계로 이어 붙일 때, 앞 단계가 뒤 단계의 판단 재료를 바꿔버려 순서 자체가 결과를 정하는 것.\
> 예: 미루기가 시각을 바꾸는데 중복 제거도 시각으로 판정하므로, 미루기를 먼저 돌리면 원래 다른 알림들이 서로를 지운다.

- 조용 시간이 아닌 알림: **정책과 무관하게 그대로 둔다**(DROP·DEFER·SPREAD 모두).
- 빼먹으면: 낮 12시 알림도 8시로 옮겨져 **어제 낮 알림이 오늘 아침에 도착한다.**
- 세 정책의 거래:

| 정책 | 사는 것 | 파는 것 |
|---|---|---|
| DROP | 몰림 없음(최대 7) | 걸린 알림 41%를 **잃는다** |
| DEFER | 한 건도 안 잃는다 | 08:00에 **724건 스파이크**(103배) |
| DEFER_AND_SPREAD | 스파이크 해소(7) | **지연** — 마지막 사람이 늦게 받는다 |

- `index`: **같은 목표 시각으로 미뤄진 것이 지금까지 몇 개였나.**\
  `deferredAt.merge(target, 1, Integer::sum) - 1` 로 0부터 센다.
- 첫 번째가 08:00:00 이어야 하는 이유: index 가 **0**이라 `spread × 0 = 0` 이 더해진다.\
  1부터 세면 첫 알림부터 불필요하게 밀린다.
- `spread` 가 null·0이면: 흩기를 건너뛰고 **DEFER 와 똑같이** 동작한다(전부 08:00).

#### 3. TODO 3 — dedupe

```java
if (window == null || window.isZero()) {
    return new ArrayList<>(requested);
}
List<Notification> sorted = new ArrayList<>(requested);
sorted.sort((a, b) -> a.at().compareTo(b.at()));

Map<String, LocalDateTime> lastSent = new HashMap<>();
List<Notification> kept = new ArrayList<>();
for (Notification n : sorted) {
    LocalDateTime last = lastSent.get(n.dedupeKey());
    if (last != null && Duration.between(last, n.at()).compareTo(window) < 0) {
        continue;                       // 창 안이다 → 버린다 (lastSent 는 갱신 안 한다)
    }
    lastSent.put(n.dedupeKey(), n.at());   // 보낸 것만 기록한다
    kept.add(n);
}
return kept;
```

- 키: `userId + "/" + kind` — **같은 사람에게 같은 종류**면 같은 알림으로 본다.

> **중복 제거 키(dedupe key)** — "어디까지 같으면 같은 알림으로 볼 것인가"를 정하는 값의 조합.\
> 예: 키를 `사용자` 로만 잡으면 주문 알림이 광고 알림을 지우고, `사용자+종류` 로 잡으면 종류가 다른 둘은 따로 나간다.

- 사람만으로 잡으면: **주문 알림이 광고 알림을 막는다**(u1/order 가 u1/promo 를 지운다).\
  종류가 다르면 다른 알림이어야 한다.
- 기준점: **마지막으로 보낸 시각**(`lastSent`).\
  버린 건은 기록하지 않는다.
- 요청 시각 기준이면: 30분마다 오는 알림이 **매번 "직전 요청에서 30분"** 이라 1시간 창을 영원히 못 넘는다 → **영원히 안 나간다.**\
  기준점 하나로 기능이 죽는다.
- 09:00·09:30·15:00 · 1시간 창:

```text
  09:00   lastSent 없음        ──►  보낸다     (lastSent = 09:00)
  09:30   09:00 에서 30분 < 1h ──►  버린다     (lastSent 그대로 09:00)
  15:00   09:00 에서 6시간 ≥ 1h ──►  보낸다     (lastSent = 15:00)

  결과 2건: 09:00, 15:00
```

- 정렬부터 하는 이유: "**첫 것**을 남긴다"는 말이 **시각 순**을 전제한다.\
  정렬해야 가장 이른 것이 기준점이 된다.
- 정렬을 빼먹으면: **목록에 먼저 있는 것**을 남긴다 — 그게 15:00 이고 09:00 이 뒤에 있으면 늦은 것을 남기고 이른 것을 버린다.\
  입력 순서에 따라 결과가 달라진다(테스트 `orderIndependent`).

> **입력 순서 비의존(order independence)** — 같은 자료가 어떤 순서로 들어와도 결과가 같아야 한다는 성질.\
> 예: 알림 목록이 뒤섞여 들어와도 먼저 정렬하면 늘 09:00 짜리가 남고, 정렬을 빼면 목록 순서가 결과를 정해버린다.

- 창이 null·0: **전부 그대로** 반환한다(중복 제거를 안 하는 알림도 있다).
- 복사본을 만드는 이유: `List.of(...)` 같은 불변 리스트가 들어오면 정렬이 터지고, 가변 리스트면 **호출자의 목록을 몰래 뒤섞는다.**\
  입력을 건드리지 않는 것이 함수의 계약이다.

> **방어적 복사(defensive copy)** — 남에게 받은 값을 그대로 건드리지 않고 복사본을 만들어 쓰는 것.\
> 예: 넘겨받은 알림 목록을 직접 정렬하면, 부르기만 했는데 호출자 쪽 목록의 순서가 바뀌어 있다.

#### 4. TODO 4 — peakBurst

```java
Map<LocalDateTime, Integer> counts = new HashMap<>();
int peak = 0;
for (Notification n : planned) {
    peak = Math.max(peak, counts.merge(n.at(), 1, Integer::sum));
}
return peak;
```

- 이 챕터의 자인 이유: 터지는 것은 **총량이 아니라 순간 부하**다.\
  "밤에는 안 보낸다"의 대가가 바로 이 수로 나타난다(7 → 724).

> **순간 부하(peak burst)** — 어느 한 시점에 한꺼번에 몰리는 처리량. 총량이 같아도 이 값이 크면 시스템이 터진다.\
> 예: 하루 5,000건을 고르게 보내면 아무 일도 없지만, 그중 724건이 8시 정각 한 점에 몰리면 그 순간만 감당이 안 된다.

- 발송 건수만 세면: DEFER 와 DEFER_AND_SPREAD 는 **건수가 완전히 같다**(흩기는 시각만 옮긴다) — 구별이 안 된다.
- 묶는 키: **발송 시각(`at`)** 하나.\
  같은 `LocalDateTime` 값마다 세고 그 최대치를 취한다.

### B. 개념

#### 5. 측정이 알려준 것

- `22:00~08:00` = 하루 10시간 = **41.7%.**\
  5,000건 중 **2,074건**이 걸린다(DROP 하면 2,926건만 남는다).
- 같은 말: **"밤에는 안 보낸다" = "알림의 40%를 버린다".**\
  규칙 문장에는 그 말이 한 글자도 없다.
- 몰림:

| | 같은 시각 최대 건수 |
|---|---|
| 버리기 | 7 |
| 미루기 | **724** |
| 흩기 (1초) | 7 |

  → **103배.** 미룬 알림이 전부 `08:00:00` 한 점으로 간다.

- 랜덤 장애보다 나쁜 점: **정확히 하루 한 번, 같은 시각에** 온다 — 예측 가능하게 반복되는 스파이크라 매일 터진다.\
  "밤에는 안 보낸다"를 넣은 대가로 **아침 8시 부하를 산 것.**

> **스파이크(spike)** — 평소 수준에서 갑자기 치솟았다가 내려오는 부하의 뾰족한 봉우리.\
> 예: 하루 내내 최대 7건이던 것이 아침 8시 정각에만 724건이 되는 모양이 스파이크다.

- 간격을 바꾸면:

| 간격 | 최대 몰림 | 마지막 발송 |
|---|---|---|
| 1초 | 7 | 08:02:33 |
| 5초 | 7 | 08:12:45 |
| 10초 | **8** | 08:25:30 |
| 60초 | 8 | **10:33** |

- 7 → 8 로 느는 이유: 10초·60초 간격은 **분 단위로 떨어지는 낮 알림과 자주 겹친다.**\
  간격이 커질수록 흩은 알림이 "정각·정분" 자리에 더 자주 착지한다.\
  **"간격을 늘리면 부하가 준다"는 짐작이 여기서 틀린다** — 간격이 정하는 것은 부하가 아니라 **마지막 사람의 지연**이다(60초면 10:33까지 밀린다).

> **꼬리 지연(tail latency)** — 평균이 아니라 제일 늦게 처리되는 쪽이 얼마나 기다리는가.\
> 예: 60초 간격으로 흩으면 대부분은 8시대에 받지만 마지막 사람은 10시 33분에 받는다 — 평균만 보면 이 사람이 안 보인다.

- 몰림이 1이 안 되는 이유: 흩기는 **미룬 것끼리만** 안 겹치게 만든다.\
  원래 그 시각에 있던 **낮 알림**과는 여전히 겹친다 — 흩기는 전체를 고르게 만들지 않는다.
- 중복 제거 창:

| 창 | 발송 건수 |
|---|---|
| 없음 | 5,000 |
| 1시간 | 4,615 |
| 6시간 | 3,479 |
| 24시간 | **1,949** |

  → **-61%.** 비용도 그만큼 준다.

- 무조건 좋은 게 아닌 이유: 버려진 3,051건 안에 **정말 필요한 알림**이 섞여 있을 수 있다.\
  무엇을 "같은 종류"로 묶느냐(키 설계)가 그것을 정한다 — 키를 넓게 잡을수록 많이 버린다.

#### 8. 연결

- **06번 정기권**: 둘 다 요구사항 한 줄에 **안 정해진 빈칸**이 여럿 있고, 그 빈칸이 전부 결과(금액/발송)를 바꾼다.\

- "순서가 계약": **변환을 여러 단계로 쌓을 때, 앞 단계가 뒤 단계의 판정 기준을 바꿔버리면 순서가 결과를 바꾼다.**\
