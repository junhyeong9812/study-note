## 해결하는 문제

"밤에는 알림을 보내지 않는다." 반대할 사람이 없는 규칙이라 그냥 넣게 된다.\
그런데 재보면 이 한 줄은 두 가지 결정을 숨기고 있고, 구현 자체에도 조용한 함정이 있다.

```text
"밤(22~08시)에는 안 보낸다"
    │
    ├─ 얼마나 걸리나?     하루의 10시간 = 알림의 41%      ← 구석 사례가 아니다
    ├─ 걸린 건 어쩌나?    버린다 / 미룬다 / 미루고 흩는다   ← 정해야 한다
    └─ 구현 함정          22 <= t < 8 인 시각은 없다        ← 조용 시간이 통째로 사라진다
```

이 챕터가 없으면 셋 중 하나가 난다: 알림의 40%를 잃거나, 아침 8시 정각에 724건이 한 점에 몰리거나, 판정식이 늘 거짓이라 밤에도 알림이 나가는데 아무도 모른다.\
쉬운 예: 우체부 — 밤에 온 편지를 버릴지 아침까지 들고 있을지, 들고 있다가 8시에 한꺼번에 배달하면 우체통이 터진다.\
똑같은 구조다: 처리 정책을 enum으로 이름 붙이고, 중복 제거와 조용 시간의 **순서**를 계약으로 고정한다.\
실무 예: 푸시 알림 서버, 마케팅 문자 발송(야간 발송 제한), 야간 방해 금지(DND) 모드, 배치 잡의 유지보수 창.

### 한눈에 — 쉽게 말하면

**알림 예약 = "밤에 전화하지 마" 규칙을 지키는 우체부.**

- "밤에는 알림을 보내지 않는다" — **아무도 반대하지 않는 규칙**이다.\
  그런데 우체부 입장에서 생각하면 바로 두 가지 문제가 생긴다.
- 첫째, 밤에 온 편지를 **버릴 건가, 아침까지 들고 있을 건가?**\
  버리면 중요한 편지를 놓치고, 들고 있으면 아침에 한꺼번에 배달해야 한다.

> **조용 시간(quiet hours)** — 알림을 보내지 않기로 정한 하루 중의 시간대.\
> 예: `22:00~08:00` 으로 두면 밤 10시부터 아침 8시 전까지는 알림이 안 나간다.

- 둘째, 들고 있다가 아침 8시에 한꺼번에 배달하면 **8시 정각에 우체통이 터진다** — 실측으로 724건이 같은 초에 몰린다.
- 게다가 "같은 편지가 여러 번 오면 한 번만"(중복 제거)까지 얹으면, **어느 것을 먼저 처리하느냐**에 따라 서로 다른 편지가 하나로 합쳐지는 사고가 난다.
- 실무 예: 푸시 알림 서버, 마케팅 문자 발송, 야간 방해 금지(DND) 모드.

```text
"밤에는 안 보낸다" 한 줄이 낳는 결정들

  밤에 걸린 알림 41% ──┬── 버린다(DROP)            → 알림의 40%를 잃는다
                       ├── 미룬다(DEFER)           → 아침 8시에 724건 스파이크
                       └── 미루고 흩는다(SPREAD)    → 스파이크 해소, 대신 지연
```

## 동작·원리

### 전체 흐름

```text
요구사항 문장                            코드로의 번역
──────────────────────────────────────────────────────────────
"밤(22~08시)"                →  QuietHours 레코드 (자정 걸침 처리 포함)
"걸리면 어떻게 하나"          →  QuietPolicy enum {DROP, DEFER, DEFER_AND_SPREAD}
"같은 알림은 한 번만"         →  dedupe(요청 목록, 창) — 키 = userId/kind
"발송 계획을 만든다"          →  plan(...) = ① dedupe 먼저 → ② 조용 시간 처리
"얼마나 몰리나"               →  peakBurst(계획) — 같은 시각 최대 건수

순서가 계약이다: 중복 제거 → 조용 시간.  (반대로 하면 사고 — 아래 참조)
```

  - *enum(열거형)*: 선택지가 정해진 값의 목록. "버린다/미룬다/흩는다" 세 갈래를 이름 붙인 것.
  - *중복 제거(dedupe)*: 같은 알림이 짧은 시간에 여러 번 오면 한 번만 보내는 것.

### 규칙 1 — 조용 시간은 자정을 걸친다 (이 챕터 최대의 함정)

**어떤 요구사항인가**: "밤 = 22:00 ~ 08:00". 끝 시각이 시작 시각보다 **앞선다** — 자정을 걸치기 때문.

**함정**: 구간 판정의 상식 `시작 <= t < 끝`을 그대로 쓰면 `22 <= t < 8`인 시각은 **하나도 없다.**\
조용 시간이 통째로 사라진다.\
그리고 아무도 모른다 — 예외도 안 나고 그냥 밤에도 알림이 나간다.

> **자정을 걸치는 구간(wrap-around)** — 시작 시각이 끝 시각보다 뒤라서, 날짜를 넘어가며 이어지는 구간.\
> 예: 22시~8시는 시계 위에서 22 → 23 → 0 → … → 7 로 한 바퀴 돌아가므로, "22 이상이면서 8 미만"인 시각은 하나도 없다.

> **조용한 실패(silent failure)** — 프로그램이 에러를 내지 않고 정상처럼 끝나는데, 결과만 틀린 것.\
> 예: 조용 시간 판정식이 늘 거짓이면 예외 하나 없이 잘 돌아가고, 다만 밤새 알림이 나갈 뿐이다.

```text
  0시     6시  8시        12시      18시    22시    24시
  ████████████│                             │████████
  조용        조용 끝                       조용 시작

  안 걸침 (09:00~18:00):  시작 <= t  그리고  t < 끝    (AND)
  걸침   (22:00~08:00):  t >= 시작  이거나  t < 끝    (OR)  ← 조건이 뒤집힌다
```

**결과** (`QuietHours.contains`): 22:00 포함, 23:59 포함, 00:00 포함, 07:59 포함, **08:00 미포함**(끝 시각은 열린 경계), 12:00 미포함.

**왜 이렇게 모델링했나**:
- `crossesMidnight()`(= `to < from`)로 걸침을 판정해 AND/OR을 가른다.\
  설정으로 받는 값이라 어느 쪽이 올지 모르니 같은 코드가 둘 다 다뤄야 한다.
- 변종 검증: 걸침 조건을 or 대신 and로 바꾸면 테스트 10개가 깨진다 — 이 조건이 진짜로 지켜지고 있다는 증거.
- **시작 == 끝은 생성자에서 거부한다** — 22:00~22:00이 "하루 종일"인지 "한 순간도 아님"인지 둘 다 말이 되므로, 모호한 값은 아예 못 만들게 한다.

> **만들 때 막기(생성 시점 검증)** — 말이 안 되는 값을 계산할 때가 아니라 객체를 만드는 순간에 거부하는 것.\
> 예: 시작과 끝이 같은 조용 시간은 아예 만들어지지 않게 하면, 그 값을 읽는 모든 코드가 애매함을 안 만난다.

### 규칙 2 — 미루면 날짜가 갈린다

**어떤 요구사항인가**: 조용 시간에 걸린 알림을 "조용 시간이 끝나는 시각"으로 미룬다.

**예시 입력** (`nextAllowed`):

```text
  3/1 23:00 알림  →  3/2 08:00   다음날로 넘어간다
  3/2 02:00 알림  →  3/2 08:00   같은 날이다
  3/2 12:00 알림  →  3/2 12:00   조용 시간 아님 — 그대로
```

**계산 방법**: 그 알림 날짜의 08:00(`at.toLocalDate().atTime(quiet.to())`)을 만들고, 그것이 알림 시각보다 **뒤면 그대로, 앞이면 +1일**. 같은 "8시"인데 하루가 다르다 — 이게 핵심이다.

**왜 이렇게 모델링했나**: 조용 시간이 아니면 정책과 무관하게 안 건드린다. 무조건 적용하면 낮 알림도 8시로 가서 "어제 낮 알림이 오늘 아침에 오는" 사고가 난다.

### 규칙 3 — 순서가 계약이다: 중복 제거 먼저, 조용 시간 나중

**함정**: 순서를 반대로 하면(조용 시간 먼저), 23시 알림과 2시 알림이 **둘 다 8:00으로 미뤄진 뒤** 중복 판정에 들어간다.\
서로 다른 알림인데 같은 시각이 되어 **하나가 다른 하나를 지운다.**

> **파이프라인 순서(pipeline order)** — 변환을 여러 단계로 이어 붙일 때, 앞 단계가 뒤 단계의 판단 재료를 바꿔버려 순서 자체가 결과를 정하는 것.\
> 예: 미루기가 시각을 바꾸는데 중복 제거도 시각으로 판정하므로, 미루기를 먼저 돌리면 원래 다른 알림들이 서로를 지운다.

```text
  올바른 순서:  [23:00 A, 02:00 B] → dedupe(원래 시각으로 판정: 다르다, 둘 다 생존)
                                   → 조용 시간 처리 → 둘 다 8:00으로
  틀린 순서:    [23:00 A, 02:00 B] → 둘 다 8:00으로 → dedupe → 하나 삭제!
```

**중복 판정의 세부** (`dedupe`):
- 키 = `userId + "/" + kind`.\
  사람만으로 잡으면 주문 알림이 광고 알림을 막는다.
- 기준은 **"마지막으로 보낸(남긴) 시각"** 이지 "마지막으로 요청한 시각"이 아니다.\
  요청 기준이면 30분마다 오는 알림은 창이 계속 리셋되어 **영원히 안 나간다.**
- 시각 순으로 정렬 후 판정 — 입력 순서에 의존하면 목록에 먼저 있는(그러나 나중 시각인) 것을 남길 수 있다.

> **중복 제거 키(dedupe key)** — "어디까지 같으면 같은 알림으로 볼 것인가"를 정하는 값의 조합.\
> 예: 키를 `사용자` 로만 잡으면 주문 알림이 광고 알림을 지우고, `사용자+종류` 로 잡으면 종류가 다른 둘은 따로 나간다.

- 창이 null/0이면 제거 안 함(중복 제거를 안 하는 알림도 있다).

**예시**: u1/order가 09:00, 09:30, 15:00 — 창 1시간이면 09:00 발송, 09:30은 창 안이라 버림, 15:00은 (09:00 기준 6시간 뒤라) 발송. 결과 2건.

### 규칙 4 — 흩기(spread): 스파이크의 대가는 지연이다

**어떤 요구사항인가**: 미룬 알림이 전부 08:00:00에 몰리니, 같은 목적지끼리 1초 간격으로 흩는다.

**예시**: 23시에 온 알림 3건 → DEFER면 셋 다 8:00:00(peakBurst=3), DEFER_AND_SPREAD(1초)면 08:00:00, 08:00:01, 08:00:02(peakBurst=1).

**측정이 알려준 것** (5,000건 표본, 사용자 300명, 종류 3가지, 사흘치):

| 정책 | 같은 시각 최대 건수 |
|---|---|
| 버리기 | 7 |
| 미루기 | **724** (103배) |
| 흩기(1초) | 7 |

간격을 바꿔 보면:

| 간격 | 최대 몰림 | 마지막 발송 |
|---|---|---|
| 1초 | 7 | 08:02:33 |
| 5초 | 7 | 08:12:45 |
| 10초 | **8** | 08:25:30 |
| 60초 | 8 | **10:33** |

**왜 이렇게 읽나** — 짐작이 틀리는 지점 둘:
- **몰림이 1이 안 된다.**\
  미룬 것끼리는 안 겹치지만, 원래 그 시각에 있던 낮 알림과 겹친다.
- **간격을 늘리면 몰림이 오히려 는다**(7→8).\
  분 단위로 떨어지는 낮 알림과 더 자주 겹치기 때문.\
  "간격을 늘리면 부하가 준다"는 짐작이 틀린다.\
  간격이 정하는 것은 부하가 아니라 **지연**이다 — 60초 간격이면 마지막 사람은 10시 반에 받는다.

> **꼬리 지연(tail latency)** — 평균이 아니라 제일 늦게 처리되는 쪽이 얼마나 기다리는가.\
> 예: 60초 간격으로 흩으면 대부분은 8시대에 받지만 마지막 사람은 10시 33분에 받는다 — 평균만 보면 이 사람이 안 보인다.

## 쓰이는 자료구조·알고리즘

- **자정을 걸치는 구간 판정** — 안 걸치면 `from <= t && t < to`(AND), 걸치면 `t >= from || t < to`(OR). `crossesMidnight() = to < from`으로 가른다. 끝 시각은 열린 경계.
- **정렬 + 마지막 발송 시각 맵(dedupe)** — 시각순 정렬 후 `HashMap<키, lastSent>`. 키 = `userId/kind`, 기준은 마지막 **보낸** 시각. [11-delivery-tracking](../11-delivery-tracking/2-summary.md)의 중복 키, [ops-patterns/06-idempotency-store](../../../ops-patterns/06-idempotency-store/2-summary.md)의 키 저장소와 같은 자리.
- **파이프라인 순서 고정** — `plan` = ① dedupe → ② 조용 시간 처리. 미루기가 중복 제거의 판단 재료(시각)를 바꾸므로 순서가 결과를 정한다 — 미루기를 먼저 하면 서로 다른 시각의 알림이 같은 8시가 되어 서로를 지운다. [09-order-state](../09-order-state/2-summary.md)·[10-payment](../10-payment/2-summary.md)의 "판정 순서가 계약"과 같은 교훈.
- **시각별 카운터로 흩기(spread)** — `HashMap<시각, 건수>`(`deferredAt`)로 같은 목표 시각(`target`, 사용자 구분 없음)에 몇 건이 몰렸는지 세고 그 수 × 간격만큼 뒤로 민다. 부하를 지연으로 바꾸는 평탄화 — [ops-patterns/05-backpressure](../../../ops-patterns/05-backpressure/2-summary.md)의 이웃.
- **히스토그램 최댓값 = `peakBurst`** — 같은 시각에 나가는 건수의 최대치. 총량이 아니라 **순간 부하**를 재는 자.
- **enum 정책 `QuietPolicy {DROP, DEFER, DEFER_AND_SPREAD}`** — 세 처리를 이름으로. 조건문 분기 대신 값이라 측정에서 나란히 돌릴 수 있다.
- **생성 시점 검증** — `QuietHours(22:00, 22:00)`처럼 모호한 값은 만들 때 거부. [12-game-buff](../12-game-buff/2-summary.md)의 record 검증과 같은 자세.

## 적용 — 풀어나가는 법

발송 제한 규칙(조용 시간·발송 한도·중복 억제)을 넣을 때의 순서: ① "아무도 반대하지 않는 규칙"일수록 얼마나 걸리는지부터 잰다 ② 걸린 건의 처리를 enum으로 이름 붙여 세 판을 같은 코드로 돌린다 ③ 시각을 바꾸는 단계(미루기)와 시각으로 판정하는 단계(중복 제거)의 순서를 계약으로 적는다 ④ 총량이 아니라 `peakBurst` 같은 순간 부하 지표로 대가를 본다.\
아래 「문제」 절이 ②~③의 재료이고, 「측정」 절이 ①·④의 결과다.

### 측정이 알려준 것 (나머지)

- **알림의 41%가 조용 시간에 걸린다.**\
  22~08시는 하루의 10시간 = 41.7%.\
  5,000건 중 2,074건.\
  "밤에는 안 보낸다" = "알림의 40%를 버린다"와 같은 말이다.\
  구석 사례가 아니라 하루의 절반 가까이다.
- **중복 제거 창 하나로 발송량이 3분의 1이 된다**: 창 없음 5,000 → 1시간 4,615 → 6시간 3,479 → 24시간 **1,949** (-61%).\
  비용도 그만큼 준다.\
  그런데 그 사이에 정말 필요한 알림이 섞여 있을 수 있다 — "같은 종류"를 어떻게 묶느냐(dedupeKey)가 그것을 정한다.

> **순간 부하(peak burst)** — 어느 한 시점에 한꺼번에 몰리는 처리량. 총량이 같아도 이 값이 크면 시스템이 터진다.\
> 예: 하루 5,000건을 고르게 보내면 아무 일도 없지만, 그중 724건이 8시 정각 한 점에 몰리면 그 순간만 감당이 안 된다.

## 장애 시나리오와 대처

**1. 매일 아침 8시 정각에 발송 서버가 넘어진다**

- 현상: 하루 한 번, 같은 시각에 발송 큐가 밀리고 타임아웃이 난다.
- 보이는 형태: 08:00:00에 724건이 한 점에 몰린다(버리기 7건의 103배). 총 발송량은 어제와 같다.
- 원인: DEFER 정책이 밤에 걸린 알림 전부를 `nextAllowed` = 08:00:00 한 시각으로 보낸다. 총량 지표만 보면 안 보인다.
- 대처: DEFER_AND_SPREAD로 같은 시각으로 미뤄진 것끼리 간격을 두고 흩는다. 대가는 지연이므로 간격은 "마지막 사람이 언제 받나"(60초면 10:33)로 정한다(정답 5번 참고).

**2. 중복 제거 창을 늘렸더니 주문 확인 알림이 사라진다**

- 현상: 발송량을 줄이려 창을 24시간으로 늘린 뒤 "주문했는데 알림이 안 왔다"는 문의가 는다.
- 보이는 형태: 발송량은 5,000 → 1,949로 61% 줄었다. 사라진 것 중에 광고가 아니라 주문·배송 알림이 섞여 있다.
- 원인: 창이 "같은 종류"를 어떻게 묶느냐(`dedupeKey`)와 함께 정해져야 하는데 창만 키웠다. 키가 `userId/kind`라도 kind가 거칠면(예: "order" 하나) 서로 다른 주문의 알림이 같은 키로 지워진다.
- 대처: 키를 "무엇이 같으면 같은 알림인가"로 다시 정한다 — 주문 알림이면 주문 번호까지 키에 넣는다. 종류별로 창을 다르게 둔다(광고 24시간, 거래 알림 0). 창을 바꿀 때는 발송량뿐 아니라 **무엇이 사라졌는지**를 종류별로 센다.

**3. 해외 사용자에게 한낮에 조용 시간이 걸린다**

- 현상: 특정 사용자군만 낮 알림이 밤으로 미뤄지거나, 반대로 새벽에 알림이 온다.
- 보이는 형태: 미뤄진 알림의 사용자 시간대가 서버와 다르다. 서버 22시 = 사용자 현지 낮.
- 원인: 조용 시간을 서버 시각(`LocalDateTime`)으로 판정했다 — README "생각해볼 것"의 "사용자마다 시간대가 다르면 '밤'이 언제인가". 이 챕터의 `QuietHours`는 시간대 개념이 없다.
- 대처: 판정 전에 알림 시각을 사용자 시간대의 현지 시각으로 바꾼 뒤 `contains`를 부른다. 사용자별 시간대를 데이터로 갖고, "밤"의 정의가 사용자마다 다름을 정책에 명시한다(정답 7번 참고).

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 22:00~08:00을 `시작 <= t < 끝`으로 판정 | 아무 시각도 안 들어 조용 시간이 소멸. 걸침이면 OR로 뒤집는다 |
| 끝 시각(08:00) 포함 여부 | 미포함 — 08:00은 이미 발송 가능 시각이다 |
| 시작 == 끝인 QuietHours | 생성자 거부 — 하루 종일인지 한 순간도 아닌지 모호 |
| 조용 시간 먼저, dedupe 나중 | 미뤄진 서로 다른 알림이 같은 시각이 되어 서로를 지운다 |
| dedupe 기준을 "마지막 요청 시각"으로 | 30분마다 오는 알림이 영원히 안 나간다 |
| 낮(12:00) 알림에도 정책 적용 | 안 건드린다 — 무조건 미루면 어제 낮 알림이 오늘 아침에 온다 |
| userId·kind가 빈 문자열 | Notification 생성자에서 거부 |

## 핵심 문장

- **아무도 반대하지 않는 규칙일수록 재봐야 한다** — "밤에는 안 보낸다"는 실측하면 "알림의 41%를 어떻게든 처리해야 한다"와 같은 말이고, 미루기의 대가는 아침 8시 724건 스파이크다.
- 자정을 걸치는 시간 구간은 판정 조건이 AND에서 OR로 **뒤집힌다** — 상식대로 쓰면 조용 시간이 소리 없이 사라진다.
- **처리 순서 자체가 계약이다** — 중복 제거를 조용 시간보다 먼저 해야 서로 다른 알림이 미뤄져 합쳐지는 사고를 막는다.
- 흩는 간격이 정하는 것은 부하가 아니라 지연이다 — 간격을 늘려도 낮 알림과의 겹침 때문에 몰림은 안 줄고, 마지막 발송만 늦어진다.
- 모호한 값(시작==끝인 조용 시간, 빈 userId)은 **만들 때 거부한다** — 쓰는 곳마다 해석하게 두지 않는다.

### 용어 풀이

- **조용 시간(quiet hours)**: 알림을 보내지 않는 시간대. 22:00~08:00처럼 자정을 걸치는 것이 보통이다.
- **자정 걸침(crossing midnight)**: 구간의 끝이 시작보다 앞선 시각인 경우. 판정 조건이 AND에서 OR로 뒤집힌다.
- **DROP / DEFER / DEFER_AND_SPREAD**: 조용 시간에 걸린 알림의 세 가지 처리 — 버리기 / 끝나는 순간으로 미루기 / 미룬 뒤 간격을 두고 흩기.
- **중복 제거(dedupe)**: 같은 키의 알림이 창(window) 안에 여러 번 오면 첫 것만 남기는 것.
- **중복 판정 키(dedupeKey)**: "같은 알림"의 정의. 여기서는 사람+종류(`userId/kind`).
- **창(window)**: 중복으로 볼 시간 범위. 창이 클수록 발송량이 준다(24시간 창이면 -61%).
- **스파이크(spike)**: 한순간에 요청이 몰리는 것. 미루기는 매일 아침 8시 정각에 724건짜리 스파이크를 만든다.
- **흩기(spread)**: 같은 시각으로 몰린 발송을 일정 간격으로 벌려 놓는 것. 부하 대신 지연을 산다.
- **peakBurst**: 같은 시각에 나가는 건수의 최대치. 몰림의 측정값.
- **record(레코드)**: 자바의 값 묶음 선언. Notification(누구에게, 무슨 종류, 언제)과 QuietHours(부터, 까지)가 레코드다.
