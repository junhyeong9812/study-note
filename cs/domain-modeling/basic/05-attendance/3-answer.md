### A. 과제

#### 0. 요구사항 한 줄이 안 말해주는 것

- "규칙보다 데이터가 문제": 계산식 자체는 뺄셈 한 번인데, **입력이 짝이 안 맞는다.**\
  코드의 대부분이 계산이 아니라 **지저분한 기록을 어떻게 다룰지**에 들어간다.
- 안 말해주는 결정들:

```text
 안 말해준 것              코드에서의 자리
 "출근이 두 번이면"      →  pair 의 pending.put 이 덮어쓰기 (뒤의 IN)
 "퇴근이 없으면"         →  pair 가 버림 + unpairedCount 로 셈
 "자정을 넘기면"         →  NightShiftRule (BY_CHECK_IN_DATE / SPLIT_AT_MIDNIGHT)
 "휴게는 어떻게 빼나"    →  breakThreshold·breakLength 를 하루 단위로 1회 적용
```

- 출근 중복: **앞을 쓰면 근무가 길어지고(사원에게 유리), 뒤를 쓰면 짧아진다(회사에 유리).**\
  이 박스는 **뒤를 쓴다** — 기기 앞에서 두 번 찍은 것으로 본다.
- 자정 넘김: **정해져 있지 않다.**\
  그래서 `NightShiftRule` 로 올려 두 해석을 돌린다.
- 퇴근 누락: **버린다.**\
  다만 "자정까지 일한 것으로 친다"도 가능한 규칙이었고, 버리는 쪽을 고르되 **몇 건을 버렸는지 셀 수 있게** 남겼다.
- 휴게 한 줄이 안 정하는 것: **근무마다 뺄지 하루 단위로 뺄지**, 그리고 **기준 경계가 이상인지 초과인지**, **기준을 넘을 때마다 뺄지 한 번만 뺄지**.

> **짝짓기(pairing)** — 따로따로 들어온 시작 기록과 끝 기록을 같은 한 건으로 묶는 일.\
> 예: 출근 기록과 퇴근 기록을 사원별로 이어 붙여야 "근무 한 건"이 되는데, 둘 중 하나가 없으면 묶을 수가 없다.

#### 1. TODO 1 — pair

정답 코드 (impl/Attendance.java):

```java
List<Punch> sorted = new ArrayList<>(punches);
sorted.sort(null);

Map<String, LocalDateTime> pending = new HashMap<>();
List<Shift> shifts = new ArrayList<>();
for (Punch punch : sorted) {
    if (punch.kind() == Punch.Kind.IN) {
        pending.put(punch.employee(), punch.at());
    } else {
        LocalDateTime in = pending.remove(punch.employee());
        if (in != null) {
            shifts.add(new Shift(punch.employee(), in, punch.at()));
        }
    }
}
return shifts;
```

- 정렬을 먼저 하는 이유: **기기 로그는 순서를 보장하지 않는다.**\
  네트워크로 모으면 더 그렇다.
- 입력 순서에 의존하면: **같은 데이터가 배치마다 다른 결과를 낸다.**\
  재현이 안 되는 결함이 된다.

> **결정적(deterministic)** — 같은 입력을 넣으면 언제 몇 번을 돌려도 같은 결과가 나오는 성질.\
> 예: 로그 순서가 섞여 들어와도 먼저 정렬하면 결과가 늘 같다. 정렬을 빼면 어제 돌린 배치와 오늘 돌린 배치의 근무 시간이 달라진다.

- 사원별 분리: **사원 번호를 키로 하는 `Map<String, LocalDateTime> pending`.**\
  사람마다 자기 칸을 따로 갖는다.
- 시각 순으로만 훑으면: **남의 퇴근과 짝지어진다.**

```text
 e1 IN 09:00   e2 IN 10:00   e2 OUT 14:00   e1 OUT 18:00

  맞게 짝지으면    e1  9 시간,  e2  4 시간
  섞어서 짝지으면  e1  5 시간,  e2  8 시간
  합계는 13 시간으로 같다 → 합계만 보면 안 걸린다
```

- 근무 시간이 같은 두 사람으로 시험하면: **섞여도 값이 똑같이 나온다.**\
  테스트 데이터가 결함을 가려버리는 전형적인 경우다.
- "뒤의 IN 을 쓴다"를 실현하는 한 줄: **`pending.put(punch.employee(), punch.at())`** — 이미 있는 키를 **덮어쓰기** 때문에 앞의 IN 이 자동으로 버려진다.

> **보류 칸(pending)** — 짝이 올 때까지 시작 기록을 임시로 담아두는 자리. 사람마다 한 칸씩 둔다.\
> 예: e1 의 출근이 들어오면 e1 칸에 넣어두고, e1 의 퇴근이 오면 그 칸을 비우면서 근무 한 건을 만든다.

- 짝 없는 OUT: `pending.remove` 가 **null 을 돌려주고**, `if (in != null)` 이 막는다.
- 짝 없는 IN: 루프가 끝날 때까지 **`pending` 에 남아 있다가 그대로 사라진다**(shifts 에 안 들어간다).
- `remove` 를 쓰는 이유: 꺼내면서 **자리를 비워야** 같은 IN 이 두 번 짝지어지지 않는다.\
  `get` 만 하면 다음 OUT 이 같은 IN 을 또 쓴다.
- 복사본을 정렬하는 이유: **부르는 쪽의 목록을 바꾸지 않기 위해서**다(그리고 `List.of(...)` 같은 불변 목록은 정렬하면 예외가 난다).
- 정렬 기준(`Punch.compareTo`): **시각 순, 같으면 IN 을 먼저**(`Kind.IN` 이 enum 앞이라 `kind.compareTo` 가 IN 을 앞에 둔다).\
  같은 시각에 OUT 이 먼저 오면 **짝이 어긋나기** 때문이다.

#### 2. unpairedCount

```java
return punches.size() - pair(punches).size() * 2;
```

- 성립하는 이유: **짝이 맞은 근무 하나는 기록 두 줄(IN + OUT)을 소비한다.**\
  전체 줄 수에서 소비된 줄 수를 빼면, 남은 게 버려진 줄이다.
- `* 2` 인 이유: 위와 같다 — Shift 하나당 기록 **두 줄**.
- 안 세고 조용히 버리면: **근무 시간이 왜 적은지 아무도 모른다.**\
  데이터가 얼마나 지저분한지도 알 수 없어서, 사고가 숫자에 안 나타난다.

> **무음 스킵(silent skip)** — 처리하지 못한 데이터를 아무 기록 없이 그냥 건너뛰는 것.\
> 예: 퇴근 기록이 없는 줄을 세지 않고 버리면, 근무 시간이 10퍼센트 모자라게 나와도 "원래 그런가 보다" 하고 넘어간다.

#### 3. TODO 2 — byDate

정답 코드:

```java
Map<LocalDate, Duration> result = new TreeMap<>();
if (rule == NightShiftRule.BY_CHECK_IN_DATE) {
    result.put(shift.in().toLocalDate(), shift.worked());
    return result;
}
LocalDateTime cursor = shift.in();
while (cursor.isBefore(shift.out())) {
    LocalDateTime midnight = cursor.toLocalDate().plusDays(1).atStartOfDay();
    LocalDateTime end = midnight.isBefore(shift.out()) ? midnight : shift.out();
    result.merge(cursor.toLocalDate(), Duration.between(cursor, end), Duration::plus);
    cursor = end;
}
return result;
```

- `BY_CHECK_IN_DATE`: **한 칸**(출근한 날짜에 전체 근무 시간).
- 자정 분할 루프의 종료 조건: **`cursor.isBefore(shift.out())`**.
- 안 지키면(하루만 처리하면): **이틀 이상을 넘기는 근무에서 틀린다**(중간 날이 통째로 빠진다).

> **귀속(attribution)** — 한 덩어리의 값을 "어느 칸의 것으로 볼 것인가"를 정하는 일.\
> 예: 밤 10시부터 다음날 6시까지 일한 8시간을 전부 출근한 날에 붙일지, 2시간·6시간으로 쪼개 이틀에 나눠 붙일지의 선택이다.

- 3/1 22:00 \~ 3/3 06:00 손계산:

```text
 cursor 3/1 22:00 → 자정 3/2 00:00 (< out) → 3/1 에  120 분
 cursor 3/2 00:00 → 자정 3/3 00:00 (< out) → 3/2 에 1440 분
 cursor 3/3 00:00 → 자정 3/4 00:00 (> out) → 3/3 에  360 분 (out 까지)
 cursor = out → 루프 끝                        합계 1,920 분 = 32 시간
```

- 3/2 칸이 생기면 안 되는 이유: **"3/2 에 0분 근무"라는 줄이 보고서에 나온다.**\
  일하지 않은 날이 근무일로 잡힌다.
- 보장하는 조건: **`while (cursor.isBefore(shift.out()))`** — cursor 가 3/2 00:00 이 되는 순간 out 과 같아져서 루프가 한 바퀴도 더 안 돈다.
- `TreeMap` 인 이유: **날짜 순으로 정렬되어 나온다** — 보고서에 그대로 쓸 수 있고, 테스트에서 크기·순서를 보기도 쉽다.

#### 4. TODO 3 — dailyTotals

정답 코드:

```java
Map<LocalDate, Duration> totals = new TreeMap<>();
for (Shift shift : pair(punches)) {
    for (Map.Entry<LocalDate, Duration> entry : byDate(shift, rule).entrySet()) {
        totals.merge(entry.getKey(), entry.getValue(), Duration::plus);
    }
}
if (breakThreshold == null || breakThreshold.isZero()) {
    return totals;
}
Map<LocalDate, Duration> deducted = new TreeMap<>();
for (Map.Entry<LocalDate, Duration> entry : totals.entrySet()) {
    Duration worked = entry.getValue();
    if (worked.compareTo(breakThreshold) >= 0) {
        worked = worked.minus(breakLength);
    }
    deducted.put(entry.getKey(), worked.isNegative() ? Duration.ZERO : worked);
}
return deducted;
```

- 공제 전에 끝내야 하는 것: **날짜별 합산.**\
  그날 전체가 모인 뒤에 한 번 빼야 "하루 단위 공제"가 된다.
- 09\~12 + 13\~16 손계산:

```text
 근무마다 공제   각각 180 분 < 240 분(기준) → 공제 없음 → 360 분
 하루로 공제     합계 360 분 ≥ 240 분       → 30 분 공제 → 330 분
                                              차이 30 분
```

- 그 차이가 생기는 사람: **하루에 두 번 이상 출근하는 사람**(시간제·분할 근무).\
  전일 근무자만 보면 두 구현이 똑같이 통과한다.
- 기준 경계: **이상(`>=`)** — 정확히 4시간이면 공제한다(`compareTo(breakThreshold) >= 0`).
- 9시간 근무: **540 − 30 = 510분.**
- "4시간마다 30분"으로 읽으면: 540 / 240 = 2번 → **540 − 60 = 480분.**
- 갈리는 지점: **8시간을 넘겨야** 두 해석이 달라진다(기준의 2배).\
  짧은 근무만 시험하면 둘이 같은 답을 낸다.
- 공제 후 음수: **0으로 막는다**(`worked.isNegative() ? Duration.ZERO : worked`).
- 음수를 두면: **마이너스 급여**가 된다 — 음수 근무 시간이 급여 계산으로 넘어간다.
- `breakThreshold` 가 null 또는 0: **공제 없이 그대로 돌려준다.**\
  휴게 규정이 없는 사업장도 있다.

return !shift.in().toLocalDate().equals(shift.out().toLocalDate())

- 조건 둘: ① **출근 날짜와 퇴근 날짜가 다르다** ② **퇴근 시각이 자정이 아니다.**
- 날짜만 보면: **자정에 딱 끝나는 근무**(3/1 18:00 \~ 3/2 00:00)를 "자정을 넘겼다"고 잘못 센다 — 실제로 다음날 일한 시간은 0분이다.

> **경계에 딱 걸린 값(경계 케이스)** — 규칙이 바뀌는 지점에 정확히 놓여서, 어느 쪽으로 세느냐가 갈리는 입력.\
> 예: 퇴근 시각이 정확히 자정이면 날짜는 바뀌었지만 다음날 일한 시간은 0분이라, "날짜가 다르다"만 보면 틀린다.

- 판정:

```text
 3/1 18:00 ~ 3/2 00:00   날짜 다름 O, 퇴근이 자정 O  →  false
 3/1 22:00 ~ 3/2 06:00   날짜 다름 O, 퇴근이 자정 X  →  true
```

### B. 개념

#### 6. 측정 — 자정 규칙

- 10일치 기록 500벌: 날짜별 근무 시간이 다른 경우 **438/500**.
- 하루 기준 최대 차이: **713분**(약 12시간).
- 22시 출근·다음날 6시 퇴근:

```text
              3/1      3/2
 출근일 귀속   480 분    0 분
 자정 분할     120 분  360 분
 합계          480 분  480 분   ← 같다
```

- 합계: **언제나 같다.**\
  어느 날의 근무인지만 다르다(측정 테스트가 매 시행마다 이걸 단언한다).
- 그래도 중요한 이유: **월 합계만 보는 보고서에서는 아무 차이도 안 만든다.**\
  대신 **일일 상한 · 야간 수당 · 주 52시간 판정**에서 갈린다.
- "어차피 합계는 같으니까"로 넘어가면: **그 셋에서 틀린다.**

#### 7. 측정 — 휴게 공제

- 기준 4시간·공제 30분: **500/500** 전부 값이 달라진다.
- 한 줄이 안 정하는 것: **근무마다 뺄지 하루 단위로 뺄지**(그리고 경계·횟수).
- 한 번만 출근하는 사람이 같은 이유: 그날의 근무가 **하나뿐**이라 "근무 단위 = 하루 단위"다 — 두 방식이 같은 값을 낸다.
- 전일 근무자 데이터로만 시험하면: **두 구현이 똑같이 통과한다.**\
  **시간제 근무자가 들어오는 날 갈린다.**

#### 8. 측정 — 데이터의 지저분함

- **기록 9,723줄 중 1,109줄**이 짝이 안 맞았다 — **11퍼센트**(11.4%).
- 일부러 넣은 비율: **퇴근 누락 10퍼센트, 출근 중복 5퍼센트.**\
  실제 기기 로그도 이 정도는 나온다.
- 짝이 맞는다를 전제로 짠 코드: **실데이터에서 바로 깨진다**(null 참조·짝 어긋남·근무 시간 폭주).
- 버리기로 정했으면: **몇 건을 버렸는지 셀 수 있어야 한다.**\
  조용히 버리면 근무 시간이 왜 적은지 아무도 모른다.

#### 9. 변종 검증에서 고친 것

- 지운 줄: **퇴근이 출근보다 빠른지 확인하던 줄.**\
  **도달할 수 없는 코드**였다.
- 불변식을 지켜주는 것: **시각 순 정렬.**\
  정렬해서 보므로 `pending` 에 든 IN 은 **항상 지금 OUT 보다 앞**이다.

> **불변식(invariant)** — 프로그램이 도는 동안 언제 확인해도 참이어야 하는 조건.\
> 예: "보류 칸에 든 출근 시각은 지금 보고 있는 퇴근 시각보다 항상 앞이다" — 정렬이 이 조건을 만들어 준다.

> **도달 불가 코드(unreachable code)** — 어떤 입력을 넣어도 절대 실행되지 않는 코드.\
> 예: 정렬을 먼저 했으면 "퇴근이 출근보다 빠른" 경우가 만들어질 수 없으므로, 그걸 검사하는 `if` 는 한 번도 참이 되지 않는다.

- 두 곳에서 안 막는 이유: **정렬을 빼는 것 자체를 테스트가 잡는다**("입력 순서에 의존하지 않는다" 테스트).\
  이미 잡히는 것을 한 번 더 막으면 **죽은 코드**가 되고, 읽는 사람은 그 검사가 실제로 무언가를 막는다고 오해한다.
- 판단 기준: **"이 방어가 없으면 무엇이 통과하나"를 물어서, 답이 '아무것도 없다'면 지운다.**\
  단, 그 불변식을 세우는 쪽(여기서는 정렬)이 테스트로 지켜지고 있어야 한다.

- "자정까지 일한 것"으로 치면: 버려지던 IN 이 근무로 살아나 **근무 시간이 늘고, 그 늘어난 시간이 진짜인지 아무도 모른다.**\
  퇴근을 안 찍는 사람이 **매일 자정까지 일한 것**이 되어 급여·주52시간 판정이 전부 부풀려진다(테스트 주석도 이 점을 지적한다).\
  버리는 쪽은 **적게 나오는 오류**, 살리는 쪽은 **많이 나오는 오류** — 어느 쪽 오류가 더 나쁜지가 결정 기준이다. (원본에 답 없음 — 내 추론)
- 규정에 쓰는 법: 뒤의 IN 을 쓰는 것은 **사원에게 불리한 쪽**이므로, "같은 사원의 출근 기록이 연속되면 **마지막 기록을 출근 시각으로 본다**"처럼 **규정 문서에 명시**하고 이의 제기 절차를 붙여야 한다.\
  코드가 조용히 정하면 그건 규정 없이 불이익을 주는 것이다. (원본에 답 없음 — 내 추론)
- 급여를 계산하려면: **시급·연장/야간/휴일 가산율 · 일일·주간 상한 · 소정근로시간 · 반올림 단위**가 더 필요하다.\
  그리고 이때부터 **자정 규칙이 금액을 바꾼다** — 야간 수당은 시간대별로 붙으므로 "몇 분"이 아니라 **"몇 시에 일한 몇 분"** 을 들고 있어야 한다.\
  지금 `Map<LocalDate, Duration>` 은 그 정보를 이미 버렸다. (원본에 답 없음 — 내 추론)
- 기기 시계가 5분 어긋나면: **기록 자체로는 못 알아챈다.**\
  모든 줄이 똑같이 5분 밀려서 짝도 맞고 근무 시간도 정상으로 보이기 때문이다.\
  알아채려면 **기기 밖의 기준**이 필요하다 — 서버 수신 시각과의 차이를 같이 저장하거나, 같은 사람이 여러 기기를 쓸 때 기기 간 차이를 보거나, 주기적으로 시각 동기 신호를 남긴다.\
  **"조용한 오차"는 그 데이터 안에서는 절대 안 보인다**는 것이 요점이다. (원본에 답 없음 — 내 추론)

> **기준점(reference)** — 어떤 값이 맞는지 판단하려고 밖에서 가져오는 비교 대상.\
> 예: 기기 시계가 맞는지는 그 기기 안에서 알 수 없다. 서버 시각처럼 기기 밖의 시계와 대봐야 5분 차이가 드러난다.

#### 11. 연결

- 01번의 자정 분할과의 비교: **자정마다 커서를 옮기는 루프 구조가 똑같다**(`cursor` → 다음 자정 → min(자정, 끝)).\
  다른 점은 01번은 조각마다 **요금과 상한**을 걸고, 05번은 조각마다 **시간을 날짜 칸에 더한다** — 그리고 01번은 합계가 달라지지만 **05번은 합계가 항상 같다**(귀속만 바뀐다).
- 04번과 같은 자리: **경계에서 빈 칸을 만들지 않는 것.**\
  04번은 체크아웃 날을 안 세고, 05번은 자정에 끝나면 다음날 칸을 안 만든다 — 둘 다 **끝점을 포함하면 0짜리 줄이 보고서에 나온다.**
- 05번이 더 세라고 하는 것: **버린 데이터의 양(`unpairedCount`).**\
  02·04번은 "무엇을 세느냐"가 보이는 것을 정한다고 했고, 05번은 거기에 **"처리하지 못한 것도 세라"** 를 더한다.
- 실무의 같은 구조: **세션 로그 처리** — 접속/종료 이벤트 짝짓기, 출입 게이트, IoT 센서.\
  전부 **순서 보장 없음 · 누락 · 중복**이 기본이고, 그래서 정렬 → 주체별 pending → 짝짓기 → 버린 것 세기가 같은 모양으로 반복된다.
