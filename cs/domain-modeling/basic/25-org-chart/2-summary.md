## 한눈에 — 쉽게 말하면

**조직도 = "내 상사는 누구" 한 줄씩만 적은 명단. 함정은 그 줄들이 뱅글뱅글 도는 것.**

- 직원마다 "내 상사는 ○○"라고 한 줄씩 적는다. 각 줄은 완벽하게 정상이다. 그런데 a의 상사가 b, b의 상사가 c, c의 상사가 a라면? **셋을 모아야 보이는 문제** — 상사를 따라 올라가는 코드가 영원히 안 멈춘다.
- 술래잡기에서 "나 잡아봐라"를 서로 가리키며 도는 것과 같다. 한 명 한 명은 그냥 손가락으로 누군가를 가리킬 뿐이다.
- 더 무서운 건, 순환이 생겨도 **예외가 안 난다는 것.** 그 고리가 조직도에서 통째로 떨어져 나와, 위에서부터 훑는 화면에서 사람이 그냥 안 보일 뿐이다.
- 그리고 순환은 만들 때 한 번 막으면 끝이 아니다 — **조직 개편은 "옮기는" 일이고, 옮기다 보면 자기 부하 밑으로 들어간다.** 옮길 때마다 다시 봐야 한다.

```text
  정상 (숲 — 뿌리가 여럿이어도 된다)          순환 (각 줄은 정상인데 모으면 고리)

  c0(대표)      x0(소속미정 신입)               a → b → c → a → b → ...
   ├ f0(재무)
   └ t0(기술)                                  a의 상사 b   ← 이 줄만 보면 OK
      ├ d1                                     b의 상사 c   ← 이 줄만 보면 OK
      └ d2                                     c의 상사 a   ← 이 줄만 보면 OK
         └ i1
```

실무 예: 사내 조직도·결재선, 카테고리 트리(26번), 파일 시스템, 댓글 대댓글 — "부모 포인터 하나로 만든 계층"은 어디에나 있고, 전부 같은 함정을 갖는다.

> "a 의 상사가 b / b 의 상사가 c / c 의 상사가 a — `a -> b -> c -> a -> b -> ...`
> **각 줄은 완벽하게 정상이다.** 셋을 모아야 보인다.
> 그리고 이 상태에서 상사를 따라 올라가는 코드는 영원히 안 멈춘다."

- 주어진 계약: `Employee(id, name, managerId)` — 자기 자신이 상사인 것만 막는다. TODO 없이 전부 주어진다.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
OrgChart.of(직원 목록)   ← 만들 때: 사번 중복 / 없는 상사 / 순환 검사. 사번 순(TreeMap) 저장
        │
  읽기:  roots()               위가 없는 사람들 (여러 명 가능 — 숲)
         directReports(id)     바로 밑 (사번 순)
         allReports(id)        밑 전부 (가까운 단부터 BFS, 같은 단은 사번 순)
         chainOfCommand(id)    위로 가는 사슬 (바로 위 → 맨 위)
         depth(id)             단 (맨 위 = 0), maxDepth(), subtreeSize(id)
        │
  변경 (불변 — 항상 새 OrgChart 반환):
         moveUnder(id, 새상사)  ← 옮길 때마다 순환 재검사: 자기 밑(allReports)으로는 못 간다
         remove(id, RemoveRule) ← 밑을 어떻게 하나: REPARENT / REJECT / CASCADE
```

  - *BFS(너비 우선 탐색)*: 가까운 단부터 한 단씩 훑는 순회. 큐(줄서기)로 구현한다.
  - *숲(forest)*: 뿌리가 여러 개인 트리들의 모음. 합병 중인 조직 + 소속 미정 신입이 자연스럽게 숲이다.

## 요구사항 → 코드 구조: 무엇이 무엇으로 변했나

| 말로 된 요구사항 | 코드에서의 모습 |
|---|---|
| "직원은 상사 사번 하나만 안다" | `record Employee(id, name, managerId)` — managerId가 null이면 위가 없음 |
| "자기가 자기 상사일 수는 없다" | `Employee` 생성자에서 거부 — **한 줄만 보고도 알 수 있는 것**은 record가 막는다 |
| "둘 이상이 도는 순환은 전체를 봐야 보인다" | `OrgChart.of()` / `walkUp()` — **전체가 있어야 보이는 것**은 OrgChart가 막는다 |
| "옮기다 보면 자기 부하 밑으로 들어간다" | `moveUnder()`가 `allReports(id).contains(newManagerId)`로 매번 재검사 |
| "뺄 때 밑을 어떻게 하나 — 정할 문제다" | `enum RemoveRule` 3값 — REPARENT / REJECT_IF_HAS_SUBORDINATES / CASCADE |
| "같은 조직도는 항상 같은 목록을 준다" | TreeMap(사번 순) 저장 + 모든 목록에 순서 명시 — 맵 순회 순서에 안 기댐 |
| "변경해도 원본은 그대로" | moveUnder/remove가 새 OrgChart를 반환 (불변 객체) |

## 규칙 — 순환 탐지: 걸음 수가 아니라 "본 사번"으로

**어떤 요구사항인가**: 상사를 따라 끝까지 올라가되, 같은 사번을 두 번 만나면 순환이다.

예시 — a→b→c→a에서 a부터 올라가기:

```text
  seen = {a}
  [1] a의 상사 b: 처음 봄 → seen = {a, b}
  [2] b의 상사 c: 처음 봄 → seen = {a, b, c}
  [3] c의 상사 a: 이미 봤다! → "순환이 있다" 예외
```

**왜 이 방법뿐인가**: "100걸음 넘으면 순환"처럼 걸음 수로 판정하면, 조직이 깊어질 때 **멀쩡한 조직도가 거부된다**(측정에서 최대 단 74가 실제로 나온다). 본 사번을 Set에 모아두는 것이 유일한 방법이다.

검증 분담이 설계다: 자기 자신을 상사로 두는 것(한 줄로 판정 가능)은 `Employee`가, 둘 이상의 순환(전체 필요)은 `OrgChart`가 막는다. a↔b처럼 서로 가리키는 경우 Employee는 통과시키고 OrgChart가 잡는다.

## 규칙 — 옮길 때마다 순환을 다시 본다 (moveUnder)

**어떤 요구사항인가**: 상사를 바꿀 수 있다. 단, **자기 밑으로는 못 간다.**

예시 — t0(밑에 d1, d2, i1)를 자기 부하 d2 밑으로 옮기면:

```text
  t0 → d2 → t0 → d2 → ...   고리가 생기고, 이 고리는 c0와 끊어진다
  → 위에서부터 훑는 화면에서 t0, d1, d2, i1이 통째로 안 보인다
  → 예외가 안 나고 사람이 사라진다. 그게 더 나쁘다.
```

그래서 `moveUnder`는 새 상사가 `allReports(id)`(자기 밑 전체)에 있으면 거부한다. 상사를 null로 바꾸는 것은 허용 — 그 사람과 밑이 통째로 떨어져 나와 새 뿌리가 된다(회사 분할이 실제로 이렇다).

**측정 — 이것이 드문 일이 아니다**: 100명 조직에서 무작위로 둘을 골라 옮기면 깊은 조직에서 **1,000번 중 313번(31%)이 순환**이 된다. 넓은 조직도 54번. 그리고 한 명을 옮기면 부모 포인터는 하나만 바뀌는데 **밑의 전원(깊은 조직 평균 34.6명, 최대 100명)의 소속 사슬이 바뀐다** — "한 명 옮겼습니다"라는 감사 로그 한 줄에 34명의 소속 변경이 숨는다.

## 규칙 — 삭제 3규칙: 같은 버튼이 5명과 2명을 만든다

**어떤 요구사항인가**: 사람을 뺄 때 그 밑을 어떻게 하나.

예시 — 6명 조직에서 t0(밑에 d1, d2, i1)를 빼면:

| 규칙 | 결과 | 남는 인원 | 어울리는 상황 |
|---|---|---|---|
| REPARENT | d1, d2가 t0의 상사(c0) 밑으로 | 5명 (한 단 얕아짐) | 퇴사 — 부하는 남는다 |
| REJECT_IF_HAS_SUBORDINATES | 예외 — 못 뺀다 | 6명 그대로 | 실수 방지 |
| CASCADE | t0, d1, d2, i1 전부 삭제 | 2명 | 부서 폐지 |

**어느 것이 맞는지는 코드가 아니라 도메인이 정한다.** 그래서 enum이다.

**측정 — CASCADE의 이빨**: 밑이 있는 사람 하나를 뺐을 때 REPARENT는 언제나 정확히 99명을 남기지만(예측 가능), CASCADE는 깊은 조직에서 평균 54.9명 — **절반을 지운다.** 최소는 0명: 맨 위를 CASCADE로 빼면 전원이 사라진다. 같은 버튼, 같은 코드, 누구를 골랐느냐만 다르다.

경계의 재미: 뿌리를 REPARENT로 빼면 "상사의 상사에게 붙인다"가 "뿌리가 된다"로 자연스럽게 변한다(c0의 상사가 null이라). 분기 없이 그렇게 되는데, **그 결과가 업무상 맞는지는 별개다** — 대표가 없어졌는데 부문장 둘이 각자 대표가 되는 게 맞나?

## 경계·모서리 케이스

- **함정: 말단 삭제만 테스트** → 밑이 없는 사람은 세 삭제 규칙이 완전히 같은 결과를 낸다. 측정: 넓은 조직은 **49%가 말단** — 무작위 삭제 테스트의 절반이 규칙을 안 건드린다. 그리고 말단은 지우기 만만해서 예제로 자주 뽑힌다.
- **함정: 뿌리 하나 강제** → 합병 중인 조직, 소속 미정 신입이 다 뿌리다. 숲이지 나무가 아니다. "대표는 한 명"은 이 자료구조가 정할 일이 아니다 — 순환만 막는다.
- **함정: 목록 순서 미지정** → 맵의 순회 순서에 기대면 같은 조직도가 부를 때마다 다른 목록을 준다. 사번 순(TreeMap) + "가까운 단부터, 같은 단은 사번 순"으로 못 박았다. (24번 순위표의 결정성과 같은 자리.)
- **깊이의 직관 배반** → 1단 중간 관리자를 12명 빼도 최대 단은 21→18로 3밖에 안 준다. **깊이는 가장 깊은 한 줄이 정한다** — 그 줄을 안 건드리면 평균만 좋아지고 최악은 그대로다.
- **빈 조직도** → roots는 빈 목록, maxDepth 0. 없는 사번 조회는 전부 예외.
- **방어선은 한 곳에(원본 변종 검증)**: `moveUnder`의 자기 자신 검사(`id.equals(newManagerId)`)를 **지웠다** — `Employee.under()`의 record 생성자가 이미 막는다. 두 군데서 막으면 어느 쪽이 진짜 방어선인지 모르고, 그 상태에선 한쪽을 지워도 테스트가 다 통과한다. 또 REJECT 규칙의 `direct.isEmpty()`를 `allReports(id).isEmpty()`로 바꾼 변종은 안 잡히는데 — 직속이 없으면 그 밑도 없으니 **같은 말**이다. 버그가 아니므로 싼 쪽(직속만 확인)을 골랐다.

## 핵심 문장

- 부모 포인터만 있으면 트리가 된다고 생각하기 쉽다 — 안 된다. **각 줄은 완벽하게 정상이어도 모으면 순환**일 수 있고, 그 검증은 전체를 가진 OrgChart만 할 수 있다(한 줄 검증은 Employee, 전체 검증은 OrgChart — 검증의 분담이 곧 설계다).
- 순환 방지는 만들 때 한 번이 아니라 **옮길 때마다**다 — 조직 개편은 옮기는 일이고, 깊은 조직에서 무작위 이동의 31%가 순환이 되며, 안 막으면 예외 대신 "사람이 화면에서 사라지는" 조용한 사고가 난다.
- 순환 판정은 걸음 수 제한이 아니라 **본 사번 집합**으로 — 걸음 수는 깊은 멀쩡한 조직을 거부한다.
- 삭제는 하나의 연산이 아니라 세 규칙(REPARENT/REJECT/CASCADE)이다 — 같은 버튼이 5명도 2명도 0명도 남길 수 있고, 어느 것이 맞는지는 도메인이 정한다. 말단만 테스트하면 이 규칙이 통째로 안 검증된다.
- 부모 포인터 하나의 변경이 밑 전원의 소속을 바꾼다 — "한 명 옮겼습니다" 로그 한 줄에 34명의 변화가 숨고, 깊이는 인원이 아니라 가장 깊은 한 줄이 정한다.

## 용어 풀이

- **조직도(org chart)**: 누가 누구 밑인지를 나타낸 계층 구조. 여기선 직원마다 상사 사번 하나를 드는 방식.
- **부모 포인터(parent pointer)**: 자식이 부모를 가리키는 참조 하나로 계층을 표현하는 방식. 만들긴 쉽지만 순환을 스스로 못 막는다.
- **순환(cycle)**: 상사를 따라 올라가면 제자리로 돌아오는 상태. 무한 루프의 원인이고, 만들 때와 옮길 때 모두 막아야 한다.
- **트리(tree) / 숲(forest)**: 순환 없이 뿌리에서 가지 치는 구조가 트리, 뿌리가 여럿이면 숲. 조직도는 숲이다.
- **뿌리(root)**: 위(상사)가 없는 사람. 대표일 수도, 소속 미정 신입일 수도 — 그 구분은 이 자료가 안 한다.
- **말단(leaf)**: 밑에 아무도 없는 사람. 삭제 규칙 셋이 같아지는 지점 — 테스트 함정.
- **단(depth)**: 맨 위에서 몇 번 내려왔나. 맨 위가 0. 위로 가는 사슬의 길이와 같다.
- **직속(direct reports) / 밑 전부(all reports)**: 바로 아래 한 단 / 그 아래 전부(자기 자신 제외).
- **BFS(너비 우선 탐색)**: 가까운 단부터 한 단씩 훑는 순회. allReports의 "가까운 단부터" 순서를 만든다.
- **REPARENT / CASCADE**: 삭제 시 밑을 상사에게 붙이기 / 밑을 통째로 같이 지우기. 퇴사 vs 부서 폐지.
- **불변 객체(immutable)**: 변경 연산이 원본을 고치지 않고 새 객체를 돌려주는 방식. 옮긴 뒤에도 원본 조직도는 그대로다.
- **TreeMap**: 키(사번) 순으로 정렬 저장되는 Map. 입력 순서가 결과에 안 남게 한다.
- **방어선(defense line)**: 같은 잘못을 막는 검증 위치. 두 군데서 막으면 어느 쪽이 진짜인지 모른다 — 한 곳에만 둔다.
