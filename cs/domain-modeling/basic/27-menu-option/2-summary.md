> 이미 따라 치며 만든 정리본이 따로 있으면(organize류) 이 파일은 핵심 문장 압축 + 링크만 담는다.

## 한눈에 — 쉽게 말하면

**메뉴 옵션 = 카페 키오스크에서 사이즈·얼음·토핑 고르기.**

- "얼음 빼기"를 고른 상태에서 "얼음 많이"를 누르면 어떻게 될까? 키오스크마다 다르다:
  - **거부**: 두 번째 누름이 안 먹는다 → 남는 것은 "얼음 빼기"
  - **교체**: 두 번째가 이긴다 → 남는 것은 "얼음 많이"
  - **확정**: 둘 다 담기고, 결제 직전에 통째로 거부된다
- **셋 다 실제 서비스에 있고, 셋 다 명세에는 "조합 금지"라고만 적힌다.**\
  어느 쪽인지는 대개 구현자가 정한다 — 그런데 셋의 결과가 일치하는 것은 40%뿐이다.
- 도메인 모델링 관점의 핵심: "이 둘은 같이 못 고릅니다"라는 **한 줄짜리 규칙에 읽는 법이 셋**이다.\
  규칙 자체가 아니라 **언제·어떻게 집행하느냐**가 결과를 가른다.

> **집행 시점(enforcement point)** — 규칙을 어겼는지 언제 확인하느냐, 즉 검사를 거는 자리.\
> 예: 같은 "얼음 빼기와 얼음 많이는 같이 못 고름" 규칙이라도 누를 때 보면 거부·교체가 되고, 결제할 때 보면 확정이 된다.

```text
  "얼음 빼기" 고름 → "얼음 많이" 누름

  거부(REJECT_LATER)      교체(REPLACE_EARLIER)    확정(ON_CONFIRM)
  [얼음 빼기]              [얼음 많이]               [빼기, 많이] 둘 다 담김
  누름을 조용히 무시         먼저 것을 밀어냄           결제 버튼에서 예외
```

실무 예: 스타벅스 사이렌오더의 옵션 선택, 배달앱의 "필수 옵션을 선택해 주세요", 게임 캐릭터 장비 슬롯.

## 문제 — 이 챕터가 시키는 것

원본 README가 시키는 것은 이 한 줄이다.

> "얼음 빼기"를 고른 상태에서 "얼음 많이"를 누르면
> **거부** — 두 번째 누름이 안 먹는다. 남는 것은 얼음 빼기.
> **교체** — 두 번째가 이긴다. 남는 것은 얼음 많이.
> **확정** — 둘 다 담기고 결제 직전에 통째로 거부된다.
> **셋 다 실제 서비스에 있고, 셋 다 "조합 금지"라고 불린다.**

**채울 것**: `OptionSelection.java`의 TODO 1~4. (`Menu`는 계약이라 다 주어져 있다.)

| TODO | 메서드 | 시키는 일 |
|---|---|---|
| 1 | `select(itemId)` | 옵션 하나 고르기 — 이미 고른 것은 조용히 무시, 방식(거부/교체/확정)대로 충돌·최대 초과를 처리하고 `rejected`/`replaced`를 센다 |
| 2 | `countIn(group)` | 지금 고른 것 중 그 그룹에 속한 개수 |
| 3 | `violations()` | 지금 어긴 규칙 **전부** — 최소 미달·최대 초과·충돌 짝 |
| 4 | `confirm(quantity)` | 위반이면 던지고, `(기본가 + 옵션가 합) × 수량` |

**테스트가 못 박은 계약**(`OptionSelectionTest`, 4,500원 아메리카노 / size min1max1 · ice min0max1 · top min0max2 / 충돌 (noIce,moreIce)·(normal,whip)):

- `noIce → moreIce` 두 번 누름: 거부 `[noIce]`·`rejected 1`, 교체 `[moreIce]`·`replaced 1`, 확정 `[noIce, moreIce]`·`violations 3개`.
- 순서를 뒤집으면 거부·교체의 결과도 뒤집힌다.
- 같은 버튼 3번 = `rejected 0` — **꽉 찬 그룹에서도 0**(자기 자신에게 밀려나지 않는다).
- 그룹을 넘는 충돌: `normal → whip`이면 `[normal]`, `large → whip`이면 `[large, whip]`.
- 교체로 `shot → syrup → whip`이면 `[syrup, whip]`·`replaced 1`.
- 사이즈를 안 고르면 **세 방식 모두** `violations` 1건 + `confirm` 예외.
- 값: `4,500 + 500 + 500 + 700 = 6,200`, `×2 = 12,400`. 수량 0 이하는 던진다.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
Menu (계약 — 다 주어짐)                 OptionSelection (구현 — TODO)
  OptionGroup: min/max 개수              select(itemId)  : 규칙 방식대로 담기
    사이즈  min1 max1 (반드시 하나)       deselect(itemId): 빼기
    얼음    min0 max1                    violations()    : 지금 어긴 규칙 전부
    토핑    min0 max2                    confirm(qty)    : 검사 → (기본가+옵션가)×수량
  Conflict: 같이 못 고르는 짝
    (얼음빼기, 얼음많이)                  rejected() / replaced() 카운터
    (보통, 휘핑) ← 그룹을 넘는 충돌
```

## 요구사항 → 코드: 어디에 번역됐나

| 말로 된 요구사항 | 코드 |
|---|---|
| "사이즈는 필수, 토핑은 최대 2개" | `OptionGroup(min, max)` — "필수/선택" 낱말이 아니라 개수 |
| "얼음 빼기와 얼음 많이는 같이 못 고름" | `Conflict(left, right)` — 방향 없는 짝, `matches`가 순서 무시 |
| "조합 금지를 언제 집행하나" | `ConflictRule` enum 3종 (REJECT_LATER/REPLACE_EARLIER/ON_CONFIRM) |
| "필수인데 안 골랐으면 결제 불가" | `violations()`의 min 검사 — **확정 때만 잡을 수 있다** |
| "값 = (기본가 + 옵션가 합) × 수량" | `confirm(quantity)` — 더한 뒤에 곱한다 |

> **무방향 짝(undirected pair)** — 두 값의 앞뒤 순서가 의미를 갖지 않는 짝.\
> 예: `Conflict(noIce, moreIce)` 하나만 적어도 얼음 빼기를 먼저 골랐든 얼음 많이를 먼저 골랐든 똑같이 걸린다.

## 규칙 1 — "필수/선택" 두 낱말을 버리고 개수(min/max)로 적는다

**어떤 요구사항인가**: 사이즈는 반드시 하나, 토핑은 안 골라도 되고 둘까지, 2종 세트는 정확히 둘.

```text
  최소 1 최대 1   반드시 하나만          (사이즈)
  최소 0 최대 3   안 골라도 되고 셋까지   (토핑)
  최소 2 최대 2   정확히 둘             (2종 세트)
```

- "필수"와 "선택" 두 낱말로는 "최소 2, 최대 3" 같은 그룹을 **못 적는다.** 그래서 개수로 적는다.
- "필수"는 별도 개념이 아니라 **min ≥ 1이라는 뜻일 뿐**이다 — 코드에서도 `required()`는 `min >= 1` 한 줄이다.
- **모델링 교훈**: 요구사항의 낱말(필수/선택)을 그대로 타입으로 만들면 표현력이 모자란다.\
  낱말 뒤의 **실제 규칙(개수 범위)** 을 타입으로 만든다.

> **옵션 그룹의 min/max** — 그 그룹에서 골라야 하는 개수의 아래위 한계.\
> 예: 사이즈는 min 1 max 1(반드시 하나), 토핑은 min 0 max 2(안 골라도 되고 둘까지) — "필수"는 min ≥ 1의 별명일 뿐이다.

`OptionGroup` 생성자가 어긋난 조합을 즉시 거부한다: min < 0, max < min, 옵션 없는 그룹, max > 옵션 수.

## 규칙 2 — 충돌 처리 세 방식 (같은 "조합 금지", 세 가지 집행)

**예시 입력**: "얼음 빼기" 선택 → "얼음 많이" 누름. 충돌 짝 `(noIce, moreIce)`.

| 방식 | 동작 | 남는 것 | 사용자 경험 |
|---|---|---|---|
| REJECT_LATER (거부) | 나중 누름을 무시, `rejected++` | 얼음 빼기 | 버튼을 눌렀는데 아무 일도 없다 |
| REPLACE_EARLIER (교체) | 부딪힌 것을 빼고 넣음, `replaced += 빠진 수` | 얼음 많이 | 먼저 고른 게 슬쩍 사라진다 |
| ON_CONFIRM (확정) | 고르는 동안 안 봄, `confirm()`에서 예외 | 둘 다 담김 | 다 고르고 나서야 안 된다는 걸 안다 |

**측정이 알려준 것**:

- **순서만 바꿔도 1/3이 다른 결과**: 같은 옵션들을 순서만 바꿔 누르면 거부는 337/1,000, 교체는 374/1,000 건이 다른 결과가 된다.\
  **확정만 0/1,000** — 고르는 동안 아무것도 안 지우기 때문.\
  그리고 그 순서는 화면을 위에서 훑느냐 아래에서 훑느냐로 정해진다 — **같은 것을 주문하려던 두 사람이 다른 것을 받는다.**

> **순서 민감(order-sensitive)** — 같은 것들을 눌러도 누른 순서에 따라 결과가 달라지는 성질.\
> 예: 거부·교체는 "보통→휘핑→라지→샷"과 그 역순이 다른 주문이 되지만, 확정은 같은 주문이 된다(0/1,000).

- **세 방식이 일치하는 것은 397/1,000** — 나머지 603건은 어느 방식을 골랐느냐로 결과가 달라지는데, 이 선택은 대개 명세에 안 적힌다.
- **값이 최대 1,200원 갈린다**: 둘 다 통과한 622건에서 값 차이 평균 288원, 최대 1,200원 — 4,500원 커피의 27%.\
  **이 차이는 오류가 아니다.** 두 구현 다 자기 규칙대로 맞고 영수증도 이상이 없다.

## 규칙 3 — 그룹 최대를 넘으면 "가장 먼저 고른 것"이 비켜난다

**예시 입력**: 토핑 그룹(max 2)에 샷·시럽을 고른 상태에서 휘핑을 누름(교체 방식).

```text
  chosen = [shot, syrup]  ← 토핑 2개, 꽉 참
  select(whip)
    → blocking = { oldestIn(top) = shot }   가장 먼저 고른 샷이 비켜남
    → chosen = [syrup, whip]
```

- `LinkedHashSet`이 고른 순서를 기억하니 `oldestIn`은 그 그룹에서 처음 만나는 것을 준다.

> **`LinkedHashSet`** — 중복은 막으면서 넣은 순서는 기억하는 집합.\
> 예: `[shot, syrup]` 순으로 담겼다는 기록이 남아 있어야 `oldestIn(top)` 이 shot 을 "가장 먼저 고른 것"으로 집어낼 수 있다.

- **교체 한 번이 둘을 밀어낼 수 있다**: 충돌 상대 하나 + 그룹 최대로 밀려나는 하나.\
  그래서 옵션 7개를 무작위 순서로 전부 누르면 거부는 평균 **3.00회** 무시되는데 교체는 평균 **3.37개**가 빠진다 — **"몇 번 충돌했나"와 "몇 개가 빠졌나"는 다른 수다.**\
  하나만 세면 다른 하나를 못 본다.

## 규칙 4 — 확정(confirm)은 세 방식 모두 다시 검사한다

**어떤 요구사항인가**: "필수 옵션을 안 골랐으면 결제 불가."

- **안 고른 것에는 누름이 없다.** 고를 때(select) 보는 방식으로는 "사이즈를 아예 안 골랐다"를 **절대 못 잡는다** — 검사할 사건 자체가 발생하지 않으니까.\
  최소 개수는 `violations()`(확정 시점)에서만 볼 수 있다.
- 고를 때 다 검사했다고 확정을 통과시키면: ① 최소 개수가 통째로 빠지고 ② 규칙이 바뀐 뒤에 담아둔 장바구니도 못 잡는다.\
  그래서 `confirm`은 방식과 무관하게 `violations()`를 다시 부른다.
- **측정**: 확정 시점에 규칙을 어긴 상태 — 거부 방식 300/1,000, 확정 방식 751/1,000.\
  즉시 검사가 절반 이상을 미리 걸러내지만, 거르는 방법이 "누름을 조용히 무시"이고, 그래도 300건(사이즈 미선택류)은 남는다.

> **조용한 무시(silent ignore)** — 버튼을 눌렀는데 예외도 안내도 없이 아무 일도 안 일어나는 처리.\
> 예: 거부 방식이 위반을 751건에서 300건으로 줄이는 방법이 바로 이것이다 — 줄인 대가가 침묵이다.

**값 계산**: `(기본가 + 고른 옵션 extraPrice 합) × 수량` — 더한 뒤에 곱한다. 수량 0 이하는 던진다.

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 같은 버튼 두 번 누름을 충돌로 셈 | `chosen.contains(itemId)`면 즉시 return — 충돌 카운트 부풀림 방지 |
| 꽉 찬 그룹에서 이미 고른 것을 또 누름 | 위와 같은 이유로 조용히 무시 — 안 하면 **자기 자신이 비켜야 할 대상**이 된다 |
| 충돌을 그룹 안에서만 봄 | 실제 조합 금지는 대부분 그룹을 넘는다 — "보통 사이즈엔 휘핑 불가" `Conflict(normal, whip)` |
| 밀어낼 것을 List에 담음 | 충돌과 최대 개수에 **동시에** 걸린 옵션이 두 번 들어가 "하나 뺐는데 둘 뺐다"고 센다 → **Set**으로 |
| 최소 개수를 select에서 잡으려 함 | 안 고른 것에는 누름이 없다 — violations/confirm에서만 |
| 안 고른 것을 deselect | 아무 일도 안 일어남 (예외 아님) |
| 자기 자신과의 충돌, 없는 옵션의 충돌 | Menu 생성자에서 거부 |

**변종 검증에서 고친 것 둘**:

1. blocking을 목록으로 담아 이중 카운트 — 집합으로 교체.
2. "이미 고른 것을 또 누르면 무시" 줄을 **지워도 테스트가 다 통과했다** — 테스트가 최대에 안 찬 그룹으로만 확인하고 있었기 때문.\
   **꽉 찬 그룹**에서 같은 것을 또 누르는 케이스를 넣으니 잡혔다.

> **변종 검증(mutation testing)** — 코드의 한 줄을 일부러 지우거나 망가뜨리고, 테스트가 그것을 잡는지 보는 것.\
> 예: "이미 고른 것을 또 누르면 무시" 줄을 지웠는데 전부 통과했다면, 그 동작을 아무 테스트도 안 보고 있다는 뜻이다.

## 핵심 문장

- "조합 금지" 한 줄에 집행 방식이 셋(거부·교체·확정) 있고, **셋이 같은 답을 내는 것은 40%뿐**인데 이 선택은 명세에 안 적힌다 — 모델링은 규칙만이 아니라 **집행 시점과 방식**까지 적는 일이다.
- 거부·교체는 결과가 **누른 순서**에 달렸고(1/3이 갈림), 확정만 순서 무관이다 — 대신 확정은 사용자가 다 고른 뒤에야 안 된다는 것을 알려준다.
- "필수/선택"이라는 낱말 대신 **min/max 개수**로 적어야 "정확히 둘" 같은 그룹을 표현할 수 있다 — 필수는 min ≥ 1의 별명일 뿐이다.
- **안 고른 것에는 누름이 없다** — 최소 개수 위반은 select에서 절대 못 잡고 confirm에서만 잡힌다. 그래서 세 방식 모두 확정 때 전체 재검사한다.
- "몇 번 충돌했나(rejected)"와 "몇 개가 빠졌나(replaced)"는 다른 수다 — 교체 한 번이 충돌 상대와 최대 초과분, 둘을 동시에 밀어낼 수 있다.

## 용어 풀이

- **옵션 그룹(OptionGroup)**: 사이즈·얼음·토핑처럼 옵션을 묶은 단위. min/max 개수로 규칙을 적는다.
- **min/max(최소/최대 개수)**: 그 그룹에서 골라야 하는 개수의 범위. "필수" = min ≥ 1.
- **충돌(Conflict)**: 같이 못 고르는 옵션 짝. 방향이 없다 — 어느 쪽을 먼저 골랐든 같이 못 간다.
- **REJECT_LATER(거부)**: 나중 누름이 안 먹는 방식. 먼저 고른 것이 남는다.
- **REPLACE_EARLIER(교체)**: 나중 누름이 이기는 방식. 부딪힌 것(충돌 상대 + 최대 초과분)을 빼고 넣는다.
- **ON_CONFIRM(확정)**: 고르는 동안 안 보고 결제 직전에 통째로 검사하는 방식. 유일하게 순서 무관.
- **violations()**: 지금 고른 것들이 어긴 규칙 전부(최소 미달·최대 초과·충돌)를 돌려주는 검사.
- **순서 민감(order-sensitive)**: 같은 것들을 눌러도 누른 순서에 따라 결과가 달라지는 성질.
- **조용한 무시(silent ignore)**: 버튼을 눌렀는데 예외도 없이 아무 일도 안 일어나는 처리. 거부 방식의 대가.
- **LinkedHashSet**: 중복을 막으면서 넣은 순서를 기억하는 집합. "가장 먼저 고른 것"을 찾는 근거.
