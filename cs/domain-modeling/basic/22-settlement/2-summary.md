# domain-modeling-basic/22-settlement — 정리 (힌트)

## 해결하는 문제

돈을 비율로 나누면 거의 항상 소수가 나오고, 원 단위로 끊으면 총액과 몫의 합이 안 맞는다.\
그 차이(잔돈)를 어떻게 할지 정하지 않으면 두 가지가 동시에 생긴다.

```text
  10,000원 ÷ 3명               규칙 없음                       규칙 있음 (예: 최대 잔여법)
  3,333 / 3,333 / 3,333        1원이 어디로도 안 간다          3,334 / 3,333 / 3,333
  합 9,999                     → 장부 합 ≠ 지급 합 (회계 안 닫힘)   합 10,000 = 총액
                               또는 늘 A가 가짐 → 매일이면 1년에 365원 쏠림
```

첫째, 합계가 안 맞는다 — 지급한 돈을 다 더해도 총액이 아니라서 장부를 못 닫는다.\
둘째, 아무렇게나 정하면 한쪽으로 쌓인다 — 한 번 1원이지만, 매일 10,000원을 셋이 나누면 1년에 365원이 A에게 간다. 매일 총액이 다른 원본 측정(10만~100만 원 무작위, 365일)에서는 A가 B보다 399원을 더 받았다. 참여자가 100명이면 한 번에 최대 99원까지 남는다.\
쉬운 예: 피자값 만 원을 셋이 더치페이 — 남는 1원을 누가 내나.\
똑같은 구조다: 총액 × 비중 ÷ 비중 합 → 내림 → 남는 잔돈을 **이름 붙은 규칙**으로 준다.\
실무 예: 오픈마켓 판매자 정산·광고 수익 배분·장바구니 할인 배분(17번) — "총액을 정수로 쪼개는" 모든 곳.

### 한눈에 — 쉽게 말하면

**정산 배분 = 피자값 만 원을 셋이 나눌 때 "남는 1원" 문제.**

- 10,000원을 셋이 똑같이 나누면 한 사람 몫은 3,333.33...원.\
  원 단위로 끊으면 3,333 x 3 = 9,999원 — **1원이 남는다.**
- "겨우 1원?"이라고 생각하기 쉽다.\
  하지만 아무도 안 가지면 합계가 총액과 안 맞아 **회계가 안 닫히고**, 매번 같은 사람이 가지면 1년 뒤에는 눈에 보이는 차이가 쌓인다.
- 그래서 이 도메인의 설계는 나눗셈이 아니라 **"남는 잔돈을 누가 갖나"라는 규칙을 이름 붙여 고르는 것**이다.

> **잔돈(remainder)** — 정수로 끊은 몫을 다 더하고 총액에서 뺀 나머지 금액. 항상 참여자 수보다 작다.\
> 예: 10,000원을 셋이 나누면 3,333 × 3 = 9,999 라서 잔돈은 1원이다.

- 더 무서운 함정: **딱 떨어지는 예제(9,000÷3)로는 어떤 규칙을 골라도 답이 같다.**\
  그래서 규칙을 안 정해도 예제가 다 통과하고, 문제는 운영에서 터진다.

```text
  10,000원 ÷ 3명 (똑같이)

   A      B      C         합계
  3,333  3,333  3,333  =  9,999   ← 1원이 떠 있다. 누가 갖나?
```

실무 예: 오픈마켓 판매자 정산, 공동구매 더치페이 앱, 광고 수익 배분, 17번 장바구니 할인 배분 — "총액을 비율로 나눠 정수로 끊는" 모든 곳에서 똑같이 생긴다.

## 동작·원리

### 전체 흐름

```text
distribute(총액, 비중 목록, 잔돈 규칙)

  [1] 각자의 정확한 몫 = 총액 x 자기 비중 ÷ 비중 합     (합이 얼마든 상관없다)
  [2] 내림(floor)으로 정수 몫 확정 + 버려진 소수를 기억
  [3] 잔돈 = 총액 - 내림 몫의 합                        (항상 0 ≤ 잔돈 < 참여자 수)
  [4] 잔돈을 규칙(RemainderRule)대로 배분
        DROP               아무도 안 갖는다 → 합이 안 맞는다
        FIRST              목록 첫 번째가 전부
        LARGEST            비중이 가장 큰 쪽이 전부
        LARGEST_REMAINDER  버려진 소수가 큰 순서로 1원씩 (최대 잔여법)
```

> **내림(floor)** — 소수점 아래를 무조건 버리는 것.\
> 예: 3,333.9 도 3,333 이 된다.

> **최대 잔여법(largest remainder method)** — 내림하며 버린 소수가 큰 사람부터 1원씩 돌려주는 방식. 선거 의석 배분에도 쓰이는 고전 규칙이다.\
> 예: 100원을 1:2:4 로 나누면 버려진 소수가 .2857 / .5714 / .1428 이라 제일 큰 B 가 1원을 받는다.

### 규칙 — 먼저 내림, 그 다음 잔돈 (반올림이 아니라 내림인 이유)

**어떤 요구사항인가**: 각자의 몫을 정할 때 내림을 쓴다.

예시 입력 — 100원을 1:2:4 (비중 합 7)로:

```text
  정확한 몫    A 14.2857   B 28.5714   C 57.1428
  내림         A 14        B 28        C 57       합 99 → 잔돈 1원
  버려진 소수    .2857       .5714       .1428
```

**왜 내림인가**: 내림하면 각자 "1원 미만"을 버리므로 몫의 합이 총액을 **절대 넘지 않는다** — 잔돈은 항상 0 이상이고, 참여자 수보다 작다(각자 1원 미만씩 버리니까).\
반올림을 쓰면 몫의 합이 총액을 넘을 수 있어 잔돈이 **음수**가 되고, 그러면 누군가에게서 돈을 **빼야** 한다.\
"나눠주기"가 "뺏기"로 변하는 설계는 피한다.

### 규칙 — 잔돈 규칙 4종: 같은 1원, 다른 주인

**어떤 요구사항인가**: 남은 잔돈을 규칙대로 준다. 위의 100원 ÷ 1:2:4 예시(잔돈 1원)로:

| 규칙 | 결과 (A/B/C) | 성격 |
|---|---|---|
| DROP | 14 / 28 / 57 (합 99) | 1원이 사라진다 — 회계가 안 닫힌다 |
| FIRST | **15** / 28 / 57 | 구현이 가장 쉽다. 매번 목록 첫 번째가 가진다 |
| LARGEST | 14 / 28 / **58** | 비중 최대(C)가 가진다. 비중이 고정이면 FIRST와 다를 게 없다 |
| LARGEST_REMAINDER | 14 / **29** / 57 | 버려진 소수가 가장 큰 B(.5714)가 가진다 — 비례에 가장 가깝다 |

잔돈이 여럿이면(예: 10,001원 ÷ 3, 잔돈 2원) FIRST는 한 명이 2원을 다 갖고(3,335/3,333/3,333), 최대 잔여법은 두 명이 1원씩 나눈다(3,334/3,334/3,333).

**왜 이렇게 모델링했나**: 어느 규칙도 "정답"이 아니다 — 쉬움(FIRST), 비례(LARGEST_REMAINDER), 그리고 "합이 맞아야 한다"는 불변식 사이의 트레이드오프다.\
그래서 코드에 숨기지 않고 enum으로 이름 붙여 호출자가 고르게 했다.

> **합계 보존(sum preservation)** — 나눠 준 금액을 전부 더하면 원래 총액과 정확히 같아야 한다는 조건.\
> 예: DROP 을 쓰면 10,000원이 9,999원으로 배분되어 이 조건을 어긴다 — 회계가 안 닫힌다.

### 규칙 — 1원짜리 문제가 아니다: 측정이 알려준 것

**하나 — 잔돈은 예외가 아니라 일상이다.** 무작위 정산 10,000건 중 **7,743건(77%)** 에서 잔돈이 남는다(버려진 합 21,289원).\
딱 떨어지는 게 23%뿐인데, 예제는 대개 딱 떨어지게 만든다.

**둘 — 매일 쌓이면 보인다.** 똑같이 나누는 셋에게 365일 정산:

```text
              A            B            C
  FIRST      66,135,650   66,135,251   66,135,251   ← A가 B보다 399원 더
  최대잔여법  66,135,519   66,135,382   66,135,251
```

한 번에 1원이라 아무도 신경 안 쓰지만 1년이면 399원, 참여자가 100명이면 그 수가 100배가 된다.

**셋 — "가장 공평한 규칙"도 동점 처리를 안 정하면 편향이 남는다.** 365일 누적 편차(이상적 몫과의 차이): FIRST는 A +266 / B -133 / C -133, 최대 잔여법은 A **+135** / B -2 / C -133.\
절반으로 줄었지만 0이 아니다 — 똑같이 나누면 버려진 소수가 셋 다 같고, 동점을 인덱스 순으로 끊으니 앞쪽이 계속 유리하다.\
완전히 없애려면 회차마다 순서를 돌려야 한다.

> **편향(bias / drift)** — 이상적인 몫과의 차이가 한쪽 방향으로만 계속 쌓이는 것.\
> 예: 한 번은 1원이라 안 보이지만, FIRST 규칙으로 365일 돌리면 A 가 B 보다 399원을 더 받는다.

**넷 — 참여자가 많을수록 잔돈이 크다.** 잔돈 < 참여자 수이므로 100명이면 한 번에 99원까지.\
2,000건 측정에서 참여자 2명일 때 잔돈 합 1,085원, 100명일 때 **97,474원**.\
이것을 한 명에게 몰아주는 규칙이면 그 한 명이 매번 99원까지 더 받는다.

## 쓰이는 자료구조·알고리즘

- **고정 소수 산술(`BigDecimal`, 스케일 10, `RoundingMode.DOWN`)** — 몫과 버려진 소수를 십진 소수 10자리까지 끊어 비교하려고 `double` 대신 쓴다. 이진 오차는 없지만 10자리 아래는 버리므로, 완전히 정확한 비교는 아래 정수 방식이다. 같은 계산을 정수만으로도 할 수 있다: 몫 = `총액×비중 / 비중합`(정수 나눗셈), 소수 비교는 나머지 `총액×비중 % 비중합`로.
  - *스케일(scale)*: 소수점 아래 자릿수. 10이면 소수 10자리까지 유지한다.
- **최대 잔여법(largest remainder) = 정렬 + 앞에서부터 1원씩** — 버려진 소수로 내림차순 정렬(`Comparator.reversed().thenComparingInt`)한 뒤 잔돈만큼 앞에서 준다. 동점은 `thenComparingInt(i -> i)`로 인덱스 순을 **명시**한다 — 원본 주석대로 자바 정렬이 안정적이라 이 줄이 없어도 지금은 같은 결과지만, 정렬 구현([algorithm/01-elementary-sort](../../../algorithm/01-elementary-sort/2-summary.md)의 안정성)에 기대지 않으려는 것이다. 잔돈 k개만 필요하면 정렬 대신 [힙](../../../data-structure/07-heap/2-summary.md)으로 상위 k만 뽑아도 된다.
- **폴드(접기)로 합계 보존 검증** — `sumOf(distribution)`는 배분 결과를 하나의 합으로 접어 `== total`을 확인한다. 회계가 닫히는지를 코드가 스스로 재는 불변식 검사다.
- **`LinkedHashMap`으로 입력 순서 유지** — 결과 맵을 입력(`shares`) 순서대로 보여 주려고 넣은 순서를 지킨다. FIRST 규칙(`shares.get(0)`)과 동점 처리(인덱스)는 맵이 아니라 `shares` 목록의 순서를 본다.
- **라운드로빈(회차별 순서 회전)** — 편향을 0으로 만들려면 `순서 = (인덱스 + 회차) % n`처럼 회차 밖 상태나 결정적 시드가 필요하다(정답 10번 참고).

## 적용 — 풀어나가는 법

"총액을 정수로 쪼개는" 문제를 만나면 나눗셈보다 먼저 아래 순서로 결정한다.\
① 몫은 **내림**으로 확정한다(잔돈이 음수가 되지 않게) → ② 잔돈 = 총액 − 몫의 합을 계산하고 `0 ≤ 잔돈 < 참여자 수`를 확인한다 → ③ 잔돈의 주인을 이름 붙은 규칙(enum)으로 고르고 동점 처리까지 적는다 → ④ `sumOf == total`을 경계에서 검증한다 → ⑤ 딱 안 떨어지는 총액(9,001)과 다른 비중(1:2:4)으로 테스트한다.\

## 장애 시나리오와 대처

**1. `double`로 몫을 계산해 잔돈이 1원 어긋나거나 최대 잔여법 순서가 뒤바뀜**

- 현상: 어떤 총액·비중 조합에서만 합계 보존 테스트가 간헐적으로 깨지거나, 소수가 같아야 할 참여자의 순서가 실행마다 다르다.
- 보이는 형태: `sumOf(결과) == total`이 1원 차이로 실패한다. 로그의 버려진 소수가 `0.30000000000000004`처럼 찍힌다.
- 원인: 이진 부동소수는 0.1 같은 십진 소수를 정확히 못 담는다. 내림 직전 값이 `2.9999999`가 되면 몫이 1원 줄고, "같은 소수"가 미세하게 달라 정렬 순서가 흔들린다.
- 대처: 기준 소스처럼 `BigDecimal`(스케일 고정, `DOWN`)을 쓰거나, 정수만으로 계산한다 — 몫은 `총액×비중 / 비중합`, 소수 비교는 나머지 `총액×비중 % 비중합`.

**2. 합계 검증 없이 DROP이 운영에 들어가 잔돈이 매일 증발**

- 현상: 월말에 지급 총액이 매출 정산 총액보다 조금 적다. 차이가 매달 다르다.
- 보이는 형태: 대사(원장 vs 지급 내역)에서 수천~수만 원 차이가 나는데 어느 건에서 났는지 모른다. 건별로는 1~99원이라 아무 알람도 없다.
- 원인: 잔돈 규칙이 DROP이거나 규칙이 아예 없어 잔돈이 어디로도 안 갔다. 건별 합계 보존을 검사하는 지점이 없어 조용히 쌓였다(측정 넷: 100명이면 2,000건에 97,474원).
- 대처: 배분 함수의 출구에서 `sumOf == total`을 검사해 어기면 **예외**로 올린다. DROP은 측정·비교용으로만 두고 운영 경로에서 못 고르게 한다. 회사가 갖는 정책이라면 그것을 수익으로 회계 처리한다(정답 10번 참고).

**3. 재계산하면 결과가 달라진다 — 라운드로빈 상태 유실**

- 현상: 편향을 없애려고 회차마다 순서를 돌렸는데, 장애 후 같은 회차를 다시 돌리니 다른 사람이 잔돈을 받는다.
- 보이는 형태: 재실행 전후 지급표가 1원씩 다르다. 감사에서 "같은 입력인데 왜 결과가 다른가"에 답을 못 한다.
- 원인: "다음 차례가 누구인가"가 정산 회차 밖의 가변 상태였고, 재실행이 그 상태를 한 번 더 전진시켰다.
- 대처: 순서를 회차 번호에서 결정적으로 계산하거나(`(인덱스 + 회차) % n`), 결과 행에 적용 규칙·회차·순서를 스탬프로 남겨 같은 입력이면 같은 출력이 나오게 한다.

### 경계·모서리 케이스

- **함정: 딱 떨어지는 예제만으로 시험** → 9,000÷3, 10,000÷4, 12,000÷6에서는 네 규칙이 전부 같은 답을 낸다.\
  잔돈 규칙 코드가 한 줄도 안 갈린다. 9,001로 1원만 바꾸면 바로 갈린다.
- **함정: 균등 비중만으로 시험** → 1:1:1이면 버려진 소수가 전부 같아서 최대 잔여법의 "소수 큰 순서 정렬"이 아무 일도 안 한다.\
  정렬을 뒤집는 버그도 못 잡는다.\
  1:2:4처럼 비중을 다르게 해야 소수가 .2857/.5714/.1428로 갈려 정렬이 검증된다. (원본이 변종 검증에서 실제로 보강한 테스트다.)
- **경계값**: 총액 0원 → 전부 0, 잔돈도 0. 음수 총액·빈 목록·비중 0 이하·빈 이름은 예외로 거부.
- **불변식**: DROP을 뺀 세 규칙은 어떤 입력에서도 `sumOf(결과) == 총액`(합계 보존), DROP의 잔돈은 항상 `0 ≤ 잔돈 < 참여자 수`.
- **동점 처리 명시**: 소수가 같으면 앞 인덱스 먼저 — 자바의 정렬이 안정적(stable)이라 안 써도 지금은 같은 결과지만, 정렬 구현에 기대지 않으려고 `thenComparingInt(i -> i)`로 명시해 뒀다.

> **안정 정렬(stable sort)** — 비교 기준이 같은 원소들의 원래 순서를 그대로 유지하는 정렬.\
> 예: 버려진 소수가 셋 다 같으면 정렬해도 A·B·C 순서가 안 바뀌어서, 결과적으로 앞쪽 A 가 먼저 받는다.

## 핵심 문장

- 정수로 끊는 비례 배분에는 **반드시 잔돈이 남는다**(77%가 일상) — 설계할 것은 나눗셈이 아니라 "그 잔돈을 누가 갖나"라는 이름 붙은 규칙이다.
- **내림이 계약이다** — 합이 총액을 절대 안 넘게 해서 잔돈이 음수(누군가에게서 뺏기)가 되는 것을 원천 차단하고, 잔돈 < 참여자 수라는 불변식을 만든다.
- 딱 떨어지는 예제와 균등 비중으로는 **네 규칙이 전부 같은 답**을 낸다 — 규칙을 안 정해도 테스트가 다 통과하는 것이 이 도메인 최대의 함정이다.
- 한 번의 1원은 안 보이지만 누적은 보인다 — FIRST 규칙은 1년에 399원이 한쪽으로 쏠리고, 최대 잔여법조차 동점 처리를 안 정하면 편향이 절반만 줄지 0이 되지 않는다.
- 합계 보존(`sumOf == total`)은 회계가 닫히는 조건이다 — 어기면 그 차이가 매일 쌓여 나중에 원인을 못 찾는다.

### 용어 풀이

- **정산(settlement)**: 거래로 생긴 돈을 참여자들에게 나눠 지급하는 일.
- **비중(weight)**: 각자가 받을 몫의 비율. 합이 얼마든 상관없다 — 합으로 나누니까.
- **잔돈(remainder)**: 정수로 내림한 몫의 합과 총액의 차이. 항상 참여자 수 미만.
- **내림(floor / RoundingMode.DOWN)**: 소수점 아래를 무조건 버리는 것. 합이 총액을 못 넘게 하는 장치.
- **최대 잔여법(largest remainder method)**: 버려진 소수가 큰 순서로 잔돈을 1원씩 주는 규칙. 비례에 가장 가깝지만 동점 처리를 정해야 한다.
- **합계 보존**: 배분 결과의 합 = 총액. 회계가 닫히기 위한 불변식.
- **불변식(invariant)**: 어떤 입력에서도 항상 참이어야 하는 조건. 예: 잔돈 < 참여자 수.
- **편향(bias/drift)**: 이상적인 몫과의 차이가 한쪽으로 계속 쌓이는 것. 한 번은 1원, 1년이면 수백 원.
- **동점 처리(tie-breaking)**: 비교 기준이 같을 때 순서를 정하는 규칙. 안 정하면 "가장 공평한 규칙"에도 편향이 남는다.
- **안정 정렬(stable sort)**: 같은 값끼리 원래 순서를 유지하는 정렬. 자바 List.sort가 그렇다 — 하지만 그것에 기대지 말고 명시하라.
- **enum(열거형)**: 가능한 값을 전부 나열한 타입. 잔돈 규칙 4가지를 이름 붙여 "선택지"임을 드러낸다.
- **record**: 값 묶음의 불변 타입. `Share`처럼 생성자 검증으로 잘못된 값을 차단한다.
- **BigDecimal**: 소수 계산을 오차 없이 하는 자바 타입. 버려진 소수를 정확히 비교해야 해서 double 대신 쓴다.
