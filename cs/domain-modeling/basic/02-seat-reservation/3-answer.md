### A. 과제

#### 0. 한 문장이 안 말해주는 셋

```text
 "통로를 건너도 붙은 것인가"      →  respectAisle (boolean 파라미터)
 "어느 자리를 먼저 줄 것인가"      →  Preference enum (FRONT_LEFT / CENTER)
 "못 붙이면 흩어서라도 줄 것인가"  →  안 준다 (계약 — 전부 아니면 전무)
```

- 특히 조용한 것: **2번(우선 규칙).**\
  조용한 이유는 **어느 규칙을 골라도 답이 나오기 때문**이다.\
  1번은 "통로 건너 앉은 손님"이 항의해서 드러나고, 3번은 빈 목록이 나와서 드러난다.\
  2번만 아무 신호도 안 낸다.
- 안 정하면 대신 정해지는 것: **뒤에 오는 손님이 앉을 자리.**\
  그리고 못 팔게 된 좌석 수(고아 좌석) — 측정에서 10배 갈렸다.

> **고아 좌석(orphan seat)** — 비어 있는데 양옆이 다 막혀서, 둘 이상이 붙어 앉을 수 없는 자리.\
> 예: `X . X` 에서 가운데 한 칸은 혼자 온 손님만 앉을 수 있고, 2명 일행에게는 영영 못 판다.

- 3번의 결정: **안 준다.**\
  `reserveBlock` 은 붙은 블록을 못 찾으면 빈 목록을 주고 좌석을 하나도 안 잡는다(부분 배정 금지).

> **연석(連席, block)** — 같은 줄에서 사이에 통로 없이 이어진 좌석 묶음.\
> 예: 3연석은 `2,3,4` 처럼 한 줄 안에서 열 번호가 1씩 올라가며 붙어 있는 세 자리다.

> **부분 배정(partial allocation)** — 요청한 수량 중 일부만 확보하고 나머지는 못 채운 채 끝내는 것.\
> 예: 3연석을 달라고 했는데 2자리만 잡아두면 손님은 못 앉는데 좌석은 팔린 상태가 된다.

#### 1. TODO 1 — findBlock

정답 코드 (impl/SeatAllocator.java):

```java
if (count <= 0) {
    throw new IllegalArgumentException("인원이 1 명 이상이어야 한다: " + count);
}
List<int[]> best = new ArrayList<>();
int bestScore = Integer.MAX_VALUE;

for (int r = 0; r < map.rows(); r++) {
    for (int c = 0; c + count <= map.cols(); c++) {
        if (!isBlockFree(map, r, c, count, respectAisle)) {
            continue;
        }
        int score = score(map, r, c, count, preference);
        if (score < bestScore) {
            bestScore = score;
            best = block(r, c, count);
        }
    }
}
return best;
```

- 나눈 이유: **미리 보기(preview).**\
  손님에게 "이 자리 드릴까요?"를 먼저 보여주려면, 찾기만 하고 안 잡을 수 있어야 한다.
- 나눈 대가: **부르는 쪽이 잡는 것을 잊을 수 있다.**\
  그러면 `findBlock` 만 두 번 불러 **두 손님에게 같은 자리**를 준다.
- 루프 상한이 `c + count <= map.cols()` 인 이유: 시작 열 c 에서 count 칸을 세면 마지막 칸이 `c+count-1` 이다.\
  그게 마지막 열(cols-1) 이하여야 하므로 `c + count <= cols` 가 된다.\
  `c < cols` 로 두면 블록이 벽 밖으로 삐져나가 범위 예외가 난다.

> **오프바이원(off-by-one)** — 경계를 한 칸 잘못 세서 생기는 흔한 실수.\
> 예: 6칸짜리 줄에서 3연석을 찾을 때 시작 열을 0\~5로 두면 마지막 후보가 벽을 넘어간다. 0\~3까지만 봐야 한다.

- 고르는 방법: 모든 후보를 다 훑으면서 **점수가 제일 작은 것**을 남긴다(완전 탐색 + 최소 점수).

> **완전 탐색(brute force)** — 가능한 후보를 빠짐없이 전부 만들어 보고 그중에서 고르는 방법.\
> 예: 10행 12열 극장에서 3연석 후보는 행마다 10자리씩 100개뿐이라, 다 훑어도 비용이 문제되지 않는다.

- 점수가 같으면: 비교가 `score < bestScore` 로 **엄격 부등호**라 **먼저 만난 후보가 이긴다**.\
  루프 순서상 앞줄·왼쪽이 먼저다.

> **엄격 부등호로 가르기(tie-break)** — 점수가 같은 후보가 여럿일 때 누가 이길지를 정하는 규칙.\
> 예: `<` 로 비교하면 나중 후보가 같은 점수여도 교체를 못 해서 먼저 만난 쪽이 남고, `<=` 로 쓰면 반대로 마지막 후보가 남는다.

- `count <= 0`: **예외(`IllegalArgumentException`).**\
  "0명을 앉힌다"는 말 자체가 성립하지 않는 입력이라, 빈 목록("못 찾았다")과 구별해야 한다.

#### 2. TODO 2 — isBlockFree

정답 코드:

```java
for (int i = 0; i < count; i++) {
    if (map.isTaken(row, col + i)) {
        return false;
    }
    // 마지막 칸 뒤의 통로는 상관없다. 사이에 있는 것만 본다.
    if (respectAisle && i < count - 1 && map.aisleAfter(col + i)) {
        return false;
    }
}
return true;
```

- 담당하는 조건: **`i < count - 1`.**\
  마지막 칸(i == count-1)에서는 통로 검사를 건너뛴다.
- 빼먹으면: 통로 바로 앞에서 끝나는 블록까지 거부한다 → **통로 앞자리를 영영 못 판다.**

> **통로(aisle)** — 열과 열 사이에 난 길. 배열에서는 이웃인 두 좌석을 실제로는 이웃이 아니게 만든다.\
> 예: `aisleAfter(1)` 이 참이면 1열과 2열은 번호가 붙어 있어도 통로를 사이에 두고 떨어져 있다.

- 1행 6열, 1열 뒤 통로, 3연석:

```text
  열   0  1 | 2  3  4  5
            ^ 통로

  통로 존중  c=0 → 0,1,2 : 1 뒤에 통로(사이) → 거부
             c=1 → 1,2,3 : 1 뒤에 통로(사이) → 거부
             c=2 → 2,3,4 : 사이에 통로 없음  → 채택   시작 열 2
  통로 무시  c=0 → 0,1,2 채택                          시작 열 0
```

- 1행 4열·1열 뒤 통로에서 2연석이 0열부터인 이유: 블록이 `0,1` 이고 통로는 **1 뒤**, 즉 **블록의 마지막 칸 뒤**다.\
  사이가 아니므로 통로 규칙에 안 걸린다.

#### 3. TODO 3 — score

정답 코드:

```java
if (preference == Preference.FRONT_LEFT) {
    return row * map.cols() + col;
}
// 블록의 가운데가 줄의 가운데에서 얼마나 떨어져 있나. 같으면 앞줄 우선.
int blockCenter = col * 2 + count - 1;
int rowCenter = map.cols() - 1;
return Math.abs(blockCenter - rowCenter) * map.rows() + row;
```

- FRONT_LEFT 식: `row * cols + col` — 좌석을 **읽는 순서대로 0,1,2,…** 로 번호 매긴 것과 같다.\
  앞줄이 작고, 같은 줄에서는 왼쪽이 작다.
- CENTER 가 재는 것: **블록의 가운데와 줄의 가운데 사이 거리.**
- 2배로 쓰는 이유: 블록의 가운데는 `col + (count-1)/2` 인데 count 가 짝수면 **가운데가 두 칸 사이(x.5)** 다.\
  소수점을 피하려고 **양쪽을 2배**로 재는 것 — `blockCenter = 2col + count - 1`, `rowCenter = 2 × (cols-1)/2 = cols - 1`.

> **2배로 재기(정수로 소수점 피하기)** — 반쪽 칸이 생기는 계산에서 모든 값을 2배로 키워 소수 없이 비교하는 방법.\
> 예: 2연석의 가운데는 `2.5` 번 자리처럼 칸 사이에 오는데, 2배로 재면 `5` 라는 정수가 되어 나눗셈 오차 없이 견줄 수 있다.

- 거리가 같으면: `* map.rows() + row` 가 **앞줄 우선**으로 가른다(거리 차이 1이 rows 만큼 벌어지므로 거리가 먼저, 그 안에서 row 가 나중).\
  같은 줄 같은 거리면 `score <` 의 엄격 부등호로 **왼쪽(먼저 만난 쪽)** 이 이긴다.
- 1행 7열, 3연석 손계산:

```text
  cols=7 → rowCenter = 6,  count=3

   col   blockCenter = 2col+2   |center - 6|   score(rows=1, row=0)
    0          2                     4              4
    1          4                     2              2
    2          6                     0              0   ← CENTER 가 고른다
    3          8                     2              2
    4         10                     4              4

  FRONT_LEFT: score = 0*7 + col = col → col 0 이 최소  ← 0열부터
```

#### 4. TODO 4 — reserveBlock

정답 코드:

```java
List<int[]> found = findBlock(map, count, respectAisle, preference);
for (int[] seat : found) {
    map.take(seat[0], seat[1]);
}
return found;
```

- 자동으로 지켜지는 이유: **먼저 전부 찾고(findBlock) 그다음에 잡는다.**\
  못 찾으면 `found` 가 비어 있어 루프가 한 번도 안 돌고, 아무것도 안 잡힌다.\
  "전부 아니면 전무"가 구조에서 저절로 나온다.
- 한 칸씩 찾아가며 잡았다면: 세 자리 중 두 자리를 잡은 뒤 세 번째에서 막히면 **잡은 두 자리가 그대로 남는다.**\
  손님은 못 앉는데 좌석은 팔린 상태가 되고, 되돌리려면 보상 로직(취소)이 따로 필요해진다.

> **전부 아니면 전무(all-or-nothing)** — 여러 단계를 묶어서, 다 되거나 하나도 안 되거나 둘 중 하나만 허용하는 것.\
> 예: 3연석을 요청했는데 2자리만 잡히면 손님은 못 앉는다. 그래서 3자리가 다 확보될 때만 잡는다.

- 1행 3열에 4연석 요청: 빈 목록 + `available() == 3` (하나도 안 잡힘).

#### 5. SeatMap 의 계약

- `false` 인 이유: **예외로 하면 재시도가 어렵다.**\
  같은 요청이 두 번 와도(네트워크 재전송) 두 번째가 조용히 false 면 부르는 쪽이 판단할 수 있다.

> **반환값 계약(return value as contract)** — 실패를 예외로 알리는 대신 돌려주는 값으로 알리기로 한 약속.\
> 예: `take` 가 false 를 주면 "이미 팔린 자리"라는 뜻인데, 그 값을 안 보고 넘어가면 안 판 좌석을 팔았다고 답하게 된다.

- 안 지키면: 반환값을 안 보고 넘어가서 **안 판 좌석을 팔았다고 답한다** — 그래서 "돌려주는 값이 계약"이다.
- 없다고 정한 것: **"취소 후 재판매 대기" 상태.**\
  `release` 한 자리는 즉시 팔린다.\
  결제 취소 중 같은 중간 상태가 필요하면 그건 다른 상태이고 이 박스엔 없다.
- 고아 좌석: **양옆이 다 막힌 빈자리.**\
  `leftOpen` 은 왼쪽이 벽도 통로도 아니고 비어 있을 때, `rightOpen` 은 오른쪽이 그럴 때 — 둘 다 아니면 고아다.\
  **벽과 통로도 "막힌 것"으로 센다.**\
  혼자 오는 손님은 앉을 수 있지만 둘 이상은 절대 못 앉는다.
- 1행 2열, 0열 뒤 통로:

```text
   . | .     왼쪽 칸: 왼쪽은 벽, 오른쪽은 통로  → 고아
             오른쪽 칸: 왼쪽은 통로, 오른쪽은 벽 → 고아
                                           고아 2 개
```

### B. 개념

#### 6. 측정 — 통로 규칙

- 500회 중 **348회**가 갈린다(앉힌 팀 수 또는 고아 좌석 수가 다름).
- 통로를 무시해서 더 앉힌 팀: 500회를 통틀어 **36팀** = 회당 **0.07팀**.
- 결론이 틀린 이유: **"통로를 건너 붙어 앉았다"는 실제로는 안 붙어 앉은 것**이다.\
  이 비용은 어느 카운터에도 안 잡힌다 — **손님이 도착해야 안다.**\
  숫자가 안 움직인다고 비용이 없는 게 아니다.

> **측정에 안 잡히는 비용** — 프로그램이 세고 있는 지표 어디에도 나타나지 않는 손해.\
> 예: 통로를 무시하고 붙여 앉히면 "앉힌 팀 수"는 그대로 늘지만, 떨어져 앉은 불만은 극장에 도착한 손님만 안다.

#### 7. 측정 — 가운데 우선의 대가

- 500회 동안 생긴 고아 좌석: **FRONT_LEFT 577 / CENTER 5,903** — **10.2배**. (그리고 500회 중 **500회 전부** 결과가 갈린다 — 한 번도 같지 않다.)
- 쪼개지는 그림:

```text
  가운데 우선
    . . . [X X X] . . .    가운데 3 자리를 주면 양쪽에 3 자리씩 남는다
                           4 명 일행은 6 자리가 남았는데도 못 앉는다

  앞줄 왼쪽 우선
    [X X X] . . . . . .    남는 자리가 한쪽에 몰려 큰 덩어리로 남는다
```

- 1행 9열에 3명씩 세 팀이 같은 이유: **딱 맞아떨어진다.**\
  두 규칙 다 세 팀을 앉히고 고아 0개.\
  **자리가 안 맞는 길이(10열)에서 갈린다** — 남은 1칸이 어디 남느냐가 달라진다.
- 200회 배정 후:

```text
              남은 좌석   그 중 고아   고아 비율
 앞줄 왼쪽      11,533        205       1.7 %
 가운데         14,389      2,360      16.4 %

  남은 좌석은 24 퍼센트 차이인데, 못 파는 비율은 9 배가 넘는다.
```

- 못 보는 것: **"남은 좌석 70석"이 "그 중 12석은 2명 이상 못 앉는 자리"일 수 있다는 사실.**\
  좌석 수만 세는 대시보드는 팔 수 있는 좌석과 못 파는 좌석을 구별하지 못한다.
- "실제 극장은 가운데부터 준다"가 맞는데도 중요한 이유: 그것은 **좌석을 버리는 선택**이다.\
  버리는 대신 손님 만족을 사는 것이고, **그 거래를 알고 해야 한다.**\
  재보기 전에는 얼마를 버리는지 모른다.

#### 8. 측정 — 도착 순서

- 500회 합계: **작은 팀부터 8,744팀 / 큰 팀부터 9,281팀** — 약 **6퍼센트** 더.
- 큰 팀부터가 이기는 이유:

```text
  [1] . . . . . . . . .    1 명이 왼쪽 끝을 먹으면
                           남은 9 칸에 5 명 두 팀이 안 들어간다
  작은 팀이 큰 덩어리를 먼저 쪼갠다.
```

- 갈린 횟수 **389/500**, 그 중 큰 팀부터가 이긴 횟수 **357** (작은 팀부터가 이긴 경우도 32회 있다 — 항상 이기는 건 아니다).
- 이 6퍼센트의 정체: **순서를 고를 수 있는 것과 없는 것의 차이.**\
  실제 예매는 오는 대로 처리해야 하므로, 이 6퍼센트는 **가질 수 없는 이득**이다.
- 같은 구조의 주제: **23번 그리디** — 지금 최선(오는 팀을 바로 앉히는 것)이 전체 최선이 아니다.

> **그리디(greedy, 탐욕법)** — 매 순간 그때 가장 좋아 보이는 선택을 하는 방법.\
> 예: 오는 팀을 족족 앉히면 그 순간은 최선이지만, 1명이 큰 덩어리를 먼저 쪼개서 뒤의 5명 두 팀을 못 받게 된다.

#### 9. 생각해볼 것

*(원본 README는 질문만 던지고 답을 안 준다 — 아래는 코드 구조에 근거한 내 추론이다.)*

- 동시 요청: **부족하다.**\
  `findBlock` 과 `take` 사이에 틈이 있어서, 두 스레드가 같은 블록을 찾고 각자 `take` 를 부르면 한쪽만 true 를 받는다 — 그러면 **한쪽은 부분 배정 상태**가 된다(`reserveBlock` 이 `take` 의 반환값을 안 본다).\
  실제로는 찾기+잡기를 한 원자 연산으로 묶거나(락·조건부 UPDATE), 실패 시 잡은 자리를 되돌려야 한다.\
  `false` 는 "중복 감지" 신호일 뿐 경쟁을 막는 장치가 아니다. (원본에 답 없음 — 내 추론)

> **경쟁 상태(race condition)** — 두 요청이 거의 같은 순간에 같은 자원을 건드려서, 누가 먼저냐에 따라 결과가 달라지는 상태.\
> 예: 두 손님이 동시에 같은 3연석을 조회하면 둘 다 "빈자리"로 보고, 잡는 순간에야 한쪽이 밀린다.

> **원자 연산(atomic operation)** — 중간에 다른 요청이 끼어들 수 없게, 여러 단계를 쪼개지지 않는 한 덩어리로 실행하는 것.\
> 예: "빈지 확인"과 "잡기"를 한 덩어리로 묶으면 두 손님이 같은 자리를 동시에 확인하는 틈 자체가 없어진다.

- 취소한 자리 즉시 재판매: **결제 취소가 진행 중이면 위험하다.**\
  취소가 실패해 되돌아오면 같은 자리에 두 명이 된다.\
  필요한 것은 "해제" 와 "판매 가능" 사이의 **중간 상태**(취소 확정 대기) — 이 박스는 그 상태가 **없다고 정했다**(테스트 주석에 명시). (원본에 답 없음 — 내 추론)
- 고아 좌석을 안 만들려면: 점수에 **"이 블록을 주면 남는 조각이 얼마나 쓸모 있나"** 를 넣는다(예: 줄 끝에 붙여 주기, 남는 조각이 1칸이 되는 배치에 벌점).\
  대가는 **손님 만족**(가운데 자리를 못 준다)과 **계산 비용**(후보마다 남을 조각을 따져야 한다). (원본에 답 없음 — 내 추론)
- 커플석·휠체어석: `SeatMap` 이 `boolean[][] taken` 만으로는 부족해지고 **좌석마다 종류(type)** 가 붙는다.\
  그러면 `isBlockFree` 가 "비었나" 외에 "이 손님이 앉을 수 있는 종류인가"를 함께 봐야 하고, 요청도 인원수만이 아니라 **필요한 종류**를 실어야 한다.\
  통로처럼 **"이어 앉을 수 없는 경계"** 가 종류 경계로도 생긴다. (원본에 답 없음 — 내 추론)

#### 10. 연결

- 01번과 같은 방식: 모호한 자리를 코드 안에 숨기지 않고 **파라미터·enum 으로 올렸다**(`respectAisle`, `Preference`).\
  그래야 두 해석을 같은 코드로 돌려 갈림을 셀 수 있다.
