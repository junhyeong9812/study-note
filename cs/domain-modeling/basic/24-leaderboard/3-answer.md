### A. 과제 (Leaderboard.java 의 TODO 1~4)

#### 0. 한 줄 요구사항 — 안 들어 있는 결정

```text
  적혀 있는 것                    적혀 있지 않은 것 (= 내가 정해야 하는 것)
  ─────────────────────────────   ──────────────────────────────────────
  동점 등수 규칙 셋의 정의         같은 점수인 둘 중 누가 위인가? (줄 세우기)
  "한 질문에 답이 셋이다"          동점 판정에 시각·이름까지 보나?
                                  상위 N 의 경계 동점을 자르나 넣나?
                                  없는 참가자에게 무엇을 돌려주나?
                                  두 번 조회하면 같은 답이 나와야 하나?
```

- **누가 위인가**: 요구사항엔 없다. impl은 점수 내림차순 → **달성 시각 빠른 순** → **이름 순**. 시각이 데이터에 들어 있는 이유가 이것이다.
- **서수의 3등/4등**: 동점을 안 인정하니 결국 **정렬 순서**가 등수를 정한다 — 즉 정렬 2·3차 기준이 그대로 등수가 된다. 정렬 기준을 안 정하면 서수 등수가 매번 달라진다.
- **동점 판정 범위**: 요구사항에 없다. impl은 **점수만** 본다. 시각까지 넣으면 동점이 거의 안 생겨서 세 규칙이 전부 서수와 같아지고, 규칙을 고른 의미가 사라진다.
- **상위 N 경계**: 없다. 그래서 `enum CutRule` 둘(EXACTLY_N / INCLUDE_TIES)을 따로 만들었다.
- **없는 참가자**: 없다. impl은 **−1**. 0으로 하면 1등과 헷갈린다.
- **재현성**: 없다. 하지만 3차 기준까지 넣어야 얻어지고, 이게 이 챕터의 함정 첫 줄이다.

#### 1. TODO 1 — sorted

```java
List<Entry> sorted = new ArrayList<>(entries);
sorted.sort(Comparator
        .comparingLong(Entry::score).reversed()   // 1차: 점수 내림차순
        .thenComparing(Entry::achievedAt)         // 2차: 먼저 달성한 쪽이 위
        .thenComparing(Entry::player));           // 3차: 이름 순 (최후의 기준)
return sorted;
```

- 기준 셋: **점수 ↓ → 달성 시각 ↑ → 이름 ↑**.
- 점수만 비교하면: 자바 정렬이 **안정적(stable)**이라 같은 점수끼리는 **넣은 순서가 그대로 남는다.** 그래서 같은 데이터라도 입력 순서가 다르면 결과가 다르다.
- "안정적" ≠ "결정적": 안정적은 "같은 값끼리 **입력 순서를 보존**한다"는 뜻이고, 결정적은 "**입력 순서와 무관하게** 같은 답"이라는 뜻이다. 안정 정렬은 오히려 입력 순서를 **결과에 남긴다** — 그래서 2·3차 기준이 없으면 결정적이지 않다.
- 이름 기준을 빼면: **점수도 같고 시각도 같은** 둘이 있을 때만 드러난다. 그 경우가 없으면 테스트가 전부 통과한다.
- 시각 기준을 지워도 통과했던 이유: 테스트 데이터의 **이름 순서와 시각 순서가 같았다.** A@100, B@200, C@300처럼 만들면 이름으로 정렬해도 같은 답이 나온다.
- 잡는 데이터: **일부러 어긋나게** — `Z@100`(먼저 달성)과 `A@200`. 시각 기준이 있으면 Z가 위, 이름만 보면 A가 위다.
- 복사하는 이유: `List.of(...)`로 만든 **불변 리스트**를 받으면 `sort()`가 예외를 던지고, 가변 리스트라도 **호출자의 리스트를 몰래 바꾸는 것**은 부작용이다.

#### 2. TODO 2 — rank

```java
List<Entry> sorted = sorted(entries);
List<Ranked> ranked = new ArrayList<>();

int currentRank = 0;
for (int i = 0; i < sorted.size(); i++) {
    Entry entry = sorted.get(i);
    boolean tied = i > 0 && entry.score() == sorted.get(i - 1).score();   // 점수만 본다

    if (rule == TieRule.ORDINAL) {
        currentRank = i + 1;                       // 무조건 줄 번호
    } else if (!tied) {
        currentRank = rule == TieRule.STANDARD_COMPETITION
                ? i + 1                            // 표준: 줄 번호로 점프
                : currentRank + 1;                 // 조밀: 하나씩만 증가
    }
    ranked.add(new Ranked(entry, currentRank));
}
return ranked;
```

- 동점 판정은 **점수만** 본다.
- 시각까지 넣으면: 같은 시각인 경우가 거의 없어 **동점이 아예 안 생기고**, 세 규칙이 전부 서수(1,2,3,4)와 같아진다 — 규칙을 고른 의미가 사라진다.
- 표준 경쟁의 등수 = **자기 줄 번호(i+1)**. 곧 "나보다 위에 있는 사람 수 + 1"이다.
- 조밀의 등수 = **직전 등수 + 1** — 건너뛰지 않으므로 "몇 번째 점수대인가"가 된다.
- 서수의 등수 = **무조건 줄 번호(i+1)** — 동점이라도 앞줄이 더 높은 등수다.
- 첫 줄 문제: `i = 0`이면 "앞 사람"이 없다. `i > 0 &&`으로 끊지 않으면 `sorted.get(-1)`에서 예외가 나거나, 초깃값과 비교해 **첫 줄이 동점으로 판정**된다.
- 두 방식의 차이(변종 검증 하나): `previousScore` 변수를 따로 두고 초깃값을 `Long.MIN_VALUE`로 잡으면, `i > 0`을 지워도 **첫 줄이 어차피 동점이 안 되어** 테스트가 다 통과한다 — **두 겹의 방어 중 하나가 놀고 있는 것**이다. `sorted.get(i - 1).score()`로 바꾸면 `i > 0`이 없을 때 진짜로 터지므로, 그 조건이 **실제로 필요한 조건**이 된다.

손계산 — 100, 90, 90, 90, 80:

```text
  줄 번호 i+1 │  1    2    3    4    5
  점수        │ 100  90   90   90   80
  동점?       │  -    x    o    o    x
  ────────────┼──────────────────────────
  표준(i+1)   │  1    2    2    2    5    ← 3등·4등이 없다
  조밀(직전+1)│  1    2    2    2    3
  서수(i+1)   │  1    2    3    4    5
```

#### 3. TODO 3 — top

```java
if (n <= 0) {
    throw new IllegalArgumentException("인원이 1 명 이상이어야 한다: " + n);
}
List<Ranked> ranked = rank(entries, rule);
if (ranked.size() <= n) {
    return ranked;                                   // 적으면 전부. 예외가 아니다
}
if (cutRule == CutRule.EXACTLY_N) {
    return new ArrayList<>(ranked.subList(0, n));     // 칼같이 자른다
}
long boundaryScore = ranked.get(n - 1).entry().score();   // 경계 = n 번째의 점수
List<Ranked> result = new ArrayList<>(ranked.subList(0, n));
int i = n;
while (i < ranked.size() && ranked.get(i).entry().score() == boundaryScore) {
    result.add(ranked.get(i));                       // 같은 점수면 계속 넣는다
    i++;
}
return result;
```

- n ≤ 0이면 **예외**(`IllegalArgumentException`).
- 참가자가 n명 이하면 **있는 만큼 전부** 돌려준다 — 예외가 아니다(3명에게 상위 10을 물으면 3명이 답이다).
- EXACTLY_N은 **n번째에서 칼같이 자른다** — 경계의 동점자 중 뒤쪽이 잘린다.
- INCLUDE_TIES는 **경계 점수와 같은 점수**를 계속 넣는다.
- 경계 점수는 **n번째 줄**(`ranked.get(n-1)`)에서 읽는다.
- 더 들어온 동점자의 등수는 **그대로**다 — 100,90,90,80에서 상위 2에 C가 들어와도 C는 여전히 **2등**이다(테스트가 못 박음).

```text
  100(A), 90(B), 90(C), 80(D) 에서 상위 2 명

    EXACTLY_N      A(1등), B(2등)             ← C 가 잘린다. B 와 동점인데
    INCLUDE_TIES   A(1등), B(2등), C(2등)     ← 3 명이 된다
```

- `break`를 지워도 결과가 같았던 이유(변종 검증 둘): 목록이 **점수 내림차순**이라 경계 점수 아래로 한 번 내려가면 **다시 올라올 일이 없다.** 그래서 break 없이 끝까지 돌아도 추가로 들어오는 줄이 없다 — **없어도 되는 줄**이었다. 원본은 그 조건을 `while` 조건으로 옮겨 **종료 조건을 하나로** 만들었다.

### B. 개념

#### 5. 동점은 점수 설계가 정한다 (측정 하나)

```text
  참가자 100 명, 1,000 회 시행
  점수 범위 │ 동점이 있는 시행 │ 표준/조밀 최대 등수차
  ──────────┼─────────────────┼──────────────────────
      10    │  1,000 / 1,000  │  89
     100    │  1,000 / 1,000  │  46
   1,000    │    995 / 1,000  │  14
  100,000   │     50 / 1,000  │   2
```

- 점수 범위 10·100은 **1,000번 전부** 동점이 생기고, 100,000이면 **50번(5%)**만 생긴다.
- 최대 등수차는 **89 / 46 / 14 / 2**.
- "몇 점 만점으로 할까"가 규칙 선택이었던 이유: 점수 종류가 적으면 동점이 **언제나** 생겨서 세 규칙이 크게 갈리고, 점수가 촘촘하면 동점이 거의 없어서 **어느 규칙을 골라도 거의 같다.** 즉 동점 규칙이 얼마나 중요한지를 **점수 설계가 미리 정해 버린다.**

#### 6. 상위 10명이 30명이 된다 (측정 둘)

```text
  동점을 다 넣는 규칙으로 100 명 중 상위 10 명
  점수 범위 │ 10 명을 넘긴 시행 │ 최대 인원
  ──────────┼──────────────────┼──────────
      10    │   850 / 1,000    │   30
     100    │   362 / 1,000    │   14
   1,000    │    31 / 1,000    │   11
```

- 상품이 10개인데 30명이 받으면: **상품이 모자란다.** 예산이 3배가 되거나, 약속을 못 지킨다.
- 정확히 자르면: **같은 점수인데 누구는 받고 누구는 못 받는다** — 무엇으로 갈랐는지(시각? 이름?) 설명해야 하고, 그 기준이 곧 분쟁이 된다.
- 진짜 해결: 규칙 선택이 아니라 **점수를 더 잘게 만드는 것**이다. 동점이 안 생기면 두 문제가 다 사라진다.

#### 7. 2차 기준이 없으면 (측정 셋)

- 점수만 비교하는 정렬로 같은 데이터를 섞어 넣으면 **1,000번 중 1,000번** 결과가 달라진다 — 한 번도 같지 않다.
- DB에서 읽어오는 순서는 **인덱스 하나만 추가해도** 바뀐다.
- 재현 불가능한 버그가 되는 과정: 로컬에서는 항상 같은 순서로 읽혀 순위표가 안정적이다 → 운영 DB에 인덱스가 추가되거나 실행 계획이 바뀐다 → 순위표 순서가 달라진다 → "같은 점수인데 어제는 내가 위였다"는 문의가 온다 → 코드를 봐도 **바뀐 게 없어서** 원인을 못 찾는다. 원인은 코드가 아니라 **읽는 순서**였다.

#### 8. 점수가 다 다르면 세 규칙이 같다 (측정 넷)

- 100명에게 서로 다른 점수를 주면 **세 규칙의 등수가 전부 일치**한다.
- 상위 10은 **언제나 정확히 10명** — CutRule도 의미가 없어진다.
- 위험한 이유: 손으로 예제를 만들 때는 자연스럽게 100, 90, 80, 70처럼 **다 다르게** 준다. 그러면 TieRule·CutRule 코드가 **한 번도 안 갈려서** 문제가 통째로 안 보인다.
- 같은 자리: **14번(취소 없는 데이터), 23번(취소율 0)**.

#### 9. 조밀과 표준은 다른 질문이다 (측정 다섯)

- 점수가 10가지이고 참가자가 100명이면 **조밀 최대 등수는 10**, **서수 최대 등수는 100**.
- 조밀은 **"몇 번째 점수대인가"** — 그래서 최댓값이 참가자 수가 아니라 **점수 종류 수**다.
- 표준은 **"나보다 잘한 사람이 몇 명인가"** — 그래서 최댓값이 참가자 수에 가깝다.
- 같은 "등수"라는 말이 **다른 질문**을 가리킨다는 것이 이 측정의 요점이다.
- SQL 짝: `RANK()` = 표준 경쟁, `DENSE_RANK()` = 조밀, `ROW_NUMBER()` = 서수. (README에는 없고 서머리에 적힌 대응 — 표준 SQL 정의 기준.)

#### 10. 생각해볼 것 (원본 README — 답이 적혀 있지 않다. 아래는 내 추론)

- **API에 규칙을 적나**: 적어야 한다. 응답에 `"tieRule": "STANDARD_COMPETITION"` 같은 필드가 없으면 클라이언트는 **1,2,2,4를 보고 3등이 누락됐다고 판단**하거나 자기 나름대로 다시 매긴다. 등수 숫자만으로는 어느 규칙인지 알 수 없고, 동점이 없는 동안에는 셋이 똑같아서 한참 뒤에 어긋난다.
- **100만 명**: 매번 전부 정렬할 수는 없다. 흔한 방법은 정렬된 자료구조(예: Redis Sorted Set)에 점수를 유지해 "나보다 점수가 높은 사람 수"를 바로 세거나, 점수 구간별 개수를 미리 집계해 두고 근사 등수를 내는 것이다. "내 등수만"은 **전체 정렬 없이 셀 수 있는 질문**이라는 점이 열쇠다(표준 경쟁 등수 = 나보다 높은 사람 수 + 1).
- **실시간 변동**: 등수는 **조회 시점의 스냅샷**이라고 화면에 명시하고 조회 시각을 함께 보여주는 것이 정직하다. 23번의 `asOf`와 같은 문제다 — 시점 없는 수치는 재현할 수 없다.
- **동점 30명**: 셋 중 하나를 미리 공지해야 한다. ①추첨(공정하지만 운) ②상품 분할(30명이 1/3씩) ③보조 기준으로 자르기(먼저 달성한 순) — ③은 정렬 2차 기준을 **상품 규칙으로 승격**시키는 것이라, 그렇게 쓸 거면 처음부터 공지해야 한다.
