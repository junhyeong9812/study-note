## 해결하는 문제

점수를 정렬하는 것은 한 줄이다. 그런데 동점이 생기는 순간 "몇 등"에 답이 셋이 되고, 정렬 결과조차 넣은 순서에 따라 달라진다.

```text
  점수 100, 90, 90, 80                규칙 없음                            규칙 있음 (TieRule·CutRule)
  "B는 몇 등?"                        구현을 열어봐야 안다 (2? 2? 3?)       표준 2 / 조밀 2 / 서수 2 또는 3 — 이름으로 답한다
  "상위 2명"                          누구는 받고 누구는 못 받음 (조용히)    EXACTLY_N: 2명 / INCLUDE_TIES: 3명 — 정한 대로
  같은 데이터를 다른 순서로 넣으면      순위표가 바뀐다 (1,000/1,000)         점수→시각→이름 3차 기준으로 항상 같다
```

규칙이 없으면 같은 점수인 두 사람이 다른 등수를 받거나, 클라이언트가 1,2,2,4를 보고 "3등이 빠졌다"고 신고한다.\
2차 기준이 없으면 DB 인덱스 하나 추가로 순위표가 바뀌는 "재현 안 되는 버그"가 된다.\
쉬운 예: 운동회 시상 — 공동 2등이 둘이면 다음은 3등인가 4등인가, 메달이 2개뿐이면 누가 받나.\
똑같은 구조다: 정렬(줄 세우기)과 등수(가르기)를 분리하고, 동점 규칙과 경계 규칙을 이름 붙여 호출자가 고른다.\
실무 예: 게임 랭킹, 시험 석차, SQL `RANK()`/`DENSE_RANK()`/`ROW_NUMBER()` — 세 함수가 정확히 세 규칙이다.

### 한눈에 — 쉽게 말하면

**순위표 = 운동회 시상식에서 "공동 2등이 두 명이면 다음은 몇 등?" 문제.**

- 점수를 정렬하는 건 쉽다.\
  어려운 건 **동점**이다.

> **동점(tie)** — 점수가 같아서 등수를 가를 수 없는 상태.\
> 예: 100, 90, 90, 80 에서 90점인 두 사람이 동점이고, 이 박스의 모든 문제가 여기서 나온다.

- 올림픽에서 은메달이 둘이면 동메달이 없다(1, 2, 2, **4**등).\
  반면 "몇 번째 점수대인가"로 세면 다음은 3등이다(1, 2, 2, **3**).\
  상품을 정확히 나눠줘야 하면 동점을 아예 안 인정하고 1, 2, 3, 4로 줄 세운다.
- **"몇 등이에요?"라는 한 질문에 답이 셋이다.**\
  셋 다 실제로 쓰이고, 어느 것인지는 코드를 열어봐야만 안다 — 그래서 이름 붙은 규칙(enum)으로 드러낸다.

> **enum(열거형)** — 고를 수 있는 선택지를 전부 이름으로 나열해 둔 타입.\
> 예: `TieRule` 에 표준 경쟁·조밀·서수 셋을 나열해 두면, "어느 규칙이냐"가 코드 표면에 드러나서 열어보지 않아도 알 수 있다.

```text
  점수  100, 90, 90, 80

    표준 경쟁   1, 2, 2, 4    동점 수만큼 건너뛴다 (올림픽)
    조밀       1, 2, 2, 3    안 건너뛴다 ("몇 번째 점수대")
    서수       1, 2, 3, 4    동점을 안 인정한다 (상품 배분)
```

실무 예: 게임 랭킹, 올림픽 메달 순위, 시험 석차, SQL의 `RANK()` / `DENSE_RANK()` / `ROW_NUMBER()` — 세 함수가 정확히 이 세 규칙이다.

## 동작·원리

### 전체 흐름

```text
sorted(entries)          점수 내림차순 → 같으면 달성 시각 빠른 순 → 그래도 같으면 이름 순
                         (3차 기준까지 있어야 "같은 데이터 = 같은 순위표"가 보장된다)
        │
rank(entries, TieRule)   정렬 후 등수 붙이기 — 동점 판정은 "점수만" 본다
                           STANDARD_COMPETITION  1,2,2,4
                           DENSE                 1,2,2,3
                           ORDINAL               1,2,3,4
        │
top(entries, n, TieRule, CutRule)   상위 N — 경계에 동점이 걸리면?
                           EXACTLY_N     정확히 N명 (동점자 일부가 잘린다)
                           INCLUDE_TIES  경계 동점자 전부 (N을 넘을 수 있다)

rankOf(entries, player, rule)   특정 참가자의 등수. 없으면 -1 (0이면 1등과 헷갈린다)
```

### 규칙 — 정렬은 3차 기준까지: 점수 → 시각 → 이름

**어떤 요구사항인가**: 점수 내림차순, 같으면 달성 시각 오름차순, 그래도 같으면 이름 순.

예시 입력과 단계:

```text
  넣은 순서: C(90점, t=300), A(100점, t=100), B(90점, t=200)

  [1] 점수 내림차순     → A(100) 이 맨 위
  [2] 90점 동점 둘      → 시각 비교: B(t=200) 가 C(t=300) 보다 먼저 달성 → B 위
  [3] 시각까지 같으면   → 이름 순 (최후의 기준)

  결과: A, B, C   — 어떤 순서로 넣어도 항상 이 순서
```

**왜 3차까지 필요한가**: 점수만 비교하면 자바 정렬이 안정적(stable)이라 **넣은 순서가 그대로 남는다.**\
측정: 점수만 비교하는 정렬로 같은 데이터를 섞어 넣으면 1,000번 중 **1,000번** 결과가 다르다.\
DB에서 읽어오는 순서는 인덱스 하나 추가하면 바뀐다 — 그때 순위표도 바뀐다.\
**"정렬이 안정적이다"가 "결과가 결정적이다"를 뜻하지 않는다.** (14번 포인트의 동점 처리와 같은 함정.)

> **안정 정렬(stable sort)** — 값이 같은 원소들의 입력 순서를 보존하는 정렬.\
> 예: 90점인 B·C 를 점수만으로 정렬하면 둘의 앞뒤가 안 바뀌어서, 넣은 순서가 그대로 순위표에 남는다.

> **결정적(deterministic)** — 같은 데이터면 항상 같은 결과가 나오는 성질.\
> 예: 안정 정렬은 "입력 순서"라는 숨은 입력에 의존하므로, 점수만 비교해서는 이것을 보장하지 않는다.

### 규칙 — 동점 판정은 "점수만" 본다 (시각은 줄 세우는 기준일 뿐)

**어떤 요구사항인가**: 등수를 가르는 것은 점수뿐이다. 시각·이름은 표시 순서만 정한다.

```text
  A(90점, t=100), B(90점, t=999)  → 표시는 A가 위지만, 등수는 둘 다 1등 [1, 1]
```

**왜 이렇게 모델링했나**: 동점 판정에 시각까지 넣으면 동점이 아예 안 생기고, 그러면 세 규칙이 전부 서수와 같아진다 — 규칙을 고른 의미가 사라진다.\
"누가 위에 표시되나"와 "몇 등인가"는 다른 질문이다.

> **동점 처리 기준(tie-breaker)** — 동점일 때 누구를 위에 놓을지 정하는 2차·3차 기준.\
> 예: 여기서는 달성 시각과 이름이 그 기준인데, 표시 순서만 정할 뿐 등수를 가르지는 않는다.

### 규칙 — 세 가지 동점 등수 (rank의 한 줄 차이)

예시 입력 — 100, 90, 90, 90, 80 (동점 셋):

```text
  표준 경쟁   1, 2, 2, 2, 5    ← 3등과 4등이 없다. "나보다 잘한 사람 수 + 1"
  조밀       1, 2, 2, 2, 3    ← "몇 번째 점수대인가"
  서수       1, 2, 3, 4, 5    ← 자리 번호 그대로
```

구현의 갈림 한 곳: 동점이 아닐 때 표준 경쟁은 `currentRank = i + 1`(자리 번호로 점프), 조밀은 `currentRank + 1`(하나만 증가).\
서수는 무조건 `i + 1`.

측정 — 조밀 등수의 최댓값은 **참가자 수가 아니라 점수 종류 수**다: 점수가 10가지면 100명이어도 조밀 최대 등수는 10, 서수는 100.\
같은 "등수"라는 말이 다른 질문("몇 번째 점수대" vs "나보다 잘한 사람 몇 명")을 가리킨다.

### 규칙 — 상위 N: 경계 동점을 자르나, 다 넣나

**어떤 요구사항인가**: 100, 90, 90, 80에서 "상위 2명"을 뽑으면 B와 C가 같은 90점인데 경계가 그 사이를 지난다.

```text
  EXACTLY_N     → A, B        (2명. 동점인 C가 잘린다 — 같은 점수인데 누구는 받고 누구는 못 받는다)
  INCLUDE_TIES  → A, B, C     (3명. C의 등수도 그대로 2등 — 상품이 2개면 곤란하다)
```

**왜 둘 다 두나**: 상품이 N개면 정확히 N명이어야 하고, 명예의 전당이면 다 넣는 편이 낫다.\
어느 쪽이든 **정해야 한다 — 안 정하면 구현이 정한다.**

> **경계 동점(boundary tie)** — 상위 N 을 자르는 자리의 점수와 같은 점수가 그 뒤에도 더 있는 상태.\
> 예: 100, 90, 90, 80 에서 상위 2명을 뽑으면 2번째(90점)와 3번째(90점)가 같아서 경계가 동점자 사이를 지난다.

**측정 — 상위 10명이 30명이 된다**: 점수 범위 10, 참가자 100명, INCLUDE_TIES로 1,000회 → 850회에서 10명을 넘고 최대 **30명**.\
상품이 10개인데 30명이 받는다.\
그렇다고 정확히 자르면 동점자 차별이다.\
**진짜 해결은 규칙 선택이 아니라 점수를 더 잘게 만드는 것이다.**

## 쓰이는 자료구조·알고리즘

- **다중 키 비교 정렬(`Comparator.comparing(...).reversed().thenComparing(...)`)** — 점수 내림차순 → 시각 → 이름의 3차 비교자로 `List.sort`. Java의 `List.sort`는 안정 정렬(TimSort — 병합 정렬 계열)이라 기준이 모자라면 입력 순서가 새어 나온다. 안정성의 원리는 [algorithm/02-merge-sort](../../../algorithm/02-merge-sort/2-summary.md).
  - *비교자(Comparator)*: 두 원소 중 누가 앞인지 답하는 함수. 여러 개를 이으면 앞 기준이 같을 때만 다음 기준을 본다.
- **한 번 훑기(선형 스캔)로 등수 붙이기** — 정렬된 목록을 앞에서부터 돌며 "앞 사람과 점수가 같은가"만 본다. 표준은 `i + 1`로 점프, 조밀은 `+1`, 서수는 항상 `i + 1`. O(n).
- **표준 경쟁 등수 = "나보다 높은 사람 수 + 1"** — 이 정의 덕에 전체 정렬 없이도 내 등수를 셀 수 있다. 정렬된 배열이면 [이진 탐색](../../../algorithm/06-binary-search/2-summary.md)으로 O(log n), 대규모면 정렬 집합(Redis Sorted Set — 원소가 많으면 [스킵 리스트](../../../data-structure/12-skip-list/2-summary.md) + 해시 테이블, 적으면 listpack 인코딩)이 순위 조회(`ZRANK`, O(log n))를 제공한다.
- **상위 N = 정렬 후 `subList(0, n)` + 경계 확장** — INCLUDE_TIES는 경계 점수와 같은 동안 `while`로 더 담는다. n이 작으면 전체 정렬 대신 [힙](../../../data-structure/07-heap/2-summary.md)으로 상위 n만 뽑을 수 있다.
- **SQL 윈도 함수** — `RANK()` = 표준 경쟁, `DENSE_RANK()` = 조밀, `ROW_NUMBER()` = 서수. 같은 세 규칙이 DB 안에 이름으로 들어 있다.

## 적용 — 풀어나가는 법

"순위를 매겨라"는 요구를 받으면 정렬 코드보다 먼저 아래를 정한다.\
① 줄 세우는 기준을 결정적이 되도록 끝까지 적는다(점수 → 시각 → 이름) → ② 등수를 가르는 기준은 **점수만**으로 두고 동점 규칙(표준/조밀/서수)을 고른다 → ③ 상위 N의 경계 동점을 자를지 넣을지(CutRule) 정한다 → ④ 점수 범위를 보고 동점이 얼마나 자주 나는지 재서, 잦으면 점수를 더 잘게 설계한다 → ⑤ 동점이 든 표본(100·90·90·80)과 뒤집어 넣은 입력으로 검증한다.\
아래 문제 절의 TODO 1~4가 이 순서 그대로다.

- 테스트가 못 박은 계약(`LeaderboardTest`): 정렬은 점수↓ → 시각↑ → 이름↑이고 **시각이 이름보다 먼저**(90점 Z@100 vs A@200이면 Z가 위) / 같은 데이터를 뒤집어 넣어도 같은 결과 / 100·90·90·80은 표준 `1,2,2,4`·조밀 `1,2,2,3`·서수 `1,2,3,4` / 동점 판정은 **점수만**(90@100과 90@999도 둘 다 1등) / 100·90·90·90·80은 표준 `1,2,2,2,5`·조밀 `1,2,2,2,3` / 빈 목록은 빈 결과, 한 명은 1등 / 없는 참가자는 **−1** / 상위 2명은 EXACTLY_N이면 2명(C가 잘림), INCLUDE_TIES면 3명이고 **C의 등수는 그대로 2** / 경계에 동점이 없으면 두 CutRule이 같다 / 참가자가 n보다 적으면 전부, n ≤ 0은 예외 / 빈 이름·음수 점수는 예외.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

### 요구사항 → 코드 구조: 무엇이 무엇으로 변했나

| 말로 된 요구사항 | 코드에서의 모습 |
|---|---|
| "같은 점수면 먼저 달성한 사람이 위" | `record Entry(player, score, achievedAt)` — 시각을 데이터에 포함 |
| "동점 등수 규칙이 셋이다" | `enum TieRule` 3값 |
| "상위 N의 경계 동점을 자르나 넣나" | `enum CutRule` 2값 — 안 정하면 구현이 정해버린다 |
| "등수가 붙은 한 줄" | `record Ranked(entry, rank)` — 원본과 등수를 분리 |
| "점수는 음수 불가, 참가자 필수" | `Entry` 생성자 검증 |

## 장애 시나리오와 대처

**1. 인덱스 하나 추가했더니 순위표가 바뀜**

- 현상: 코드도 데이터도 안 바꿨는데 배포 후 동점자들의 표시 순서가 뒤집혔다. 테스트는 그대로 통과한다.
- 보이는 형태: 어떤 환경에서는 A가 위, 다른 환경에서는 B가 위. 재현하려고 같은 데이터를 넣으면 또 다르다. 사용자 신고는 "내가 먼저 달성했는데 아래에 있다".
- 원인: 정렬에 점수만 비교했다. 안정 정렬이라 DB에서 읽어온 순서가 그대로 남았고, 그 순서를 인덱스 변경이 바꿨다(측정 셋: 1,000/1,000 다름).
- 대처: 비교자를 결정적이 될 때까지 잇는다(점수 → 달성 시각 → 이름). 테스트는 같은 데이터를 **뒤집어 넣은** 입력으로 결과가 같은지 단언한다.

**2. 클라이언트가 등수를 다시 매김 — "3등이 사라졌어요"**

- 현상: API가 1,2,2,4를 돌려주자 앱이 3등 자리가 비었다고 표시하거나 자기 나름대로 1,2,3,4로 다시 붙인다. 서버 화면과 앱 화면의 등수가 다르다.
- 보이는 형태: 동점이 없는 동안은 아무 문제 없다가 첫 동점에서 두 화면이 갈린다. 상금 지급 목록과 앱 표시가 어긋난다.
- 원인: 응답에 등수 숫자만 있고 **어느 규칙**인지가 없다. 셋 중 무엇인지는 코드를 열어봐야만 알 수 있다는 이 챕터의 출발점이 API 경계에서 그대로 재현된 것이다.
- 대처: 응답에 `tieRule`·`cutRule`을 함께 싣고 클라이언트는 등수를 재계산하지 않는다. 등수 규칙은 계약 문서에 적는다(정답 10번 참고).

**3. 100만 명 순위표를 요청마다 전부 정렬**

- 현상: "내 등수" 조회 API의 응답이 수 초로 늘고 CPU가 튄다.
- 보이는 형태: 프로파일에 `List.sort`가 요청마다 찍힌다. 점수가 들어올 때마다 캐시가 무효화되어 다시 정렬한다.
- 원인: 전체 순위표를 만든 뒤 한 명을 찾는 구조. "내 등수"는 정렬 없이 셀 수 있는 질문(나보다 높은 사람 수 + 1)인데 전체 정렬에 묶었다.
- 대처: 정렬 집합(Redis Sorted Set 등)에 점수를 유지해 순위 질의를 O(log n)으로 하거나, 점수 구간별 개수를 미리 집계해 근사 등수를 낸다. 조회 시각을 함께 보여 스냅샷임을 명시한다.

### 경계·모서리 케이스

- **함정: 점수가 다 다른 예제** → 세 TieRule의 등수가 전부 같고, 상위 10도 언제나 정확히 10명 — CutRule도 안 갈린다.\
  손으로 만드는 예제는 대개 점수를 다르게 준다.\
  그러면 이 박스의 문제가 통째로 안 보인다(14번 취소 없는 데이터, 23번 취소율 0과 같은 자리).
- **동점 발생률은 점수 설계가 정한다** → 참가자 100명, 1,000회: 점수 범위 10이면 동점이 1,000/1,000(항상), 100,000이면 50/1,000(5%).\
  표준/조밀 최대 등수차는 범위 10에서 89까지 벌어진다.\
  **"몇 점 만점으로 할까"가 사실은 동점 규칙의 중요도를 정하는 결정이었다.**
- **빈 목록 / 한 명** → 빈 결과 / 1등.\
  첫 줄에서 "앞 사람과 같은 점수인가"를 물으면 앞 사람이 없다 — 그 경우를 안 끊으면 첫 줄이 동점으로 판정된다.
- **없는 참가자의 등수는 -1** → 0으로 하면 1등과 헷갈린다.
- **참가자가 N명 이하면 전부 반환** — 예외가 아니다.\
  N ≤ 0은 거부.
- **테스트 설계 함정(원본 변종 검증)**: ① `tied` 판정의 `i > 0`이 `previousScore` 초깃값(Long.MIN_VALUE) 방어와 겹쳐 한쪽이 놀고 있었다 — `sorted.get(i - 1).score()` 비교로 바꿔 조건을 실제 필요하게 만듦.\
  ② 상위 N 루프의 `break`는 내림차순이라 없어도 되는 줄 — while 조건으로 옮겨 종료 조건을 하나로.\
  ③ 정렬 테스트에서 이름 순서와 시각 순서가 같아 시각 기준을 지워도 통과했다 — "이름은 Z인데 먼저 달성"(Z, t=100 vs A, t=200 → Z가 위) 케이스를 넣어 가름.

> **변종 검증(mutation testing)** — 코드의 한 줄을 일부러 지우거나 망가뜨리고, 테스트가 그것을 잡아내는지 보는 것.\
> 예: 정렬의 시각 기준을 지웠는데 테스트가 전부 통과하면, 그 줄이 필요 없거나 테스트 데이터가 약한 것이다.

## 핵심 문장

- "몇 등이에요?"라는 한 질문에 답이 셋이다(표준 1,2,2,4 / 조밀 1,2,2,3 / 서수 1,2,3,4) — 어느 것인지 코드를 열어봐야 안다면 모델링이 덜 된 것이고, 그래서 TieRule이라는 이름 붙은 규칙으로 드러낸다.
- **동점 판정은 점수만, 줄 세우기는 점수→시각→이름 3차까지** — 판정에 시각을 넣으면 동점이 사라져 규칙이 무의미해지고, 정렬에 3차 기준이 없으면 입력 순서가 순위표에 새어 나온다.
- "정렬이 안정적이다"는 "결과가 결정적이다"가 아니다 — 점수만 비교하면 1,000번 중 1,000번 입력 순서에 따라 순위표가 달라진다.
- 상위 N은 N명이 아닐 수 있다(10명이 30명까지) — 경계 동점을 자르나 넣나(CutRule)는 안 정하면 구현이 정하고, 진짜 해결은 점수를 더 잘게 설계하는 것이다.
- 동점 규칙의 중요도는 점수 설계가 정한다 — 점수가 10가지면 동점이 100%, 100,000가지면 5%.\
  "몇 점 만점"이 곧 규칙 선택이다.

### 용어 풀이

- **순위표(leaderboard)**: 점수 순으로 참가자를 줄 세운 표.
- **동점(tie)**: 점수가 같은 것. 이 박스의 모든 문제가 여기서 나온다.
- **표준 경쟁 순위(standard competition ranking)**: 1,2,2,4 — 동점 다음 등수가 동점 수만큼 건너뛴다. "나보다 잘한 사람 수 + 1". SQL `RANK()`.
- **조밀 순위(dense ranking)**: 1,2,2,3 — 안 건너뛴다. "몇 번째 점수대인가". SQL `DENSE_RANK()`.
- **서수 순위(ordinal ranking)**: 1,2,3,4 — 동점을 안 인정하고 자리 번호를 준다. SQL `ROW_NUMBER()`.
- **동점 처리 기준(tie-breaker)**: 동점일 때 표시 순서를 정하는 2차·3차 기준(시각, 이름). 등수를 가르는 기준이 아니다.
- **안정 정렬(stable sort)**: 같은 값끼리 입력 순서를 보존하는 정렬. 자바 List.sort가 그렇다.
- **결정적(deterministic)**: 같은 데이터면 항상 같은 결과. 안정 정렬만으로는 보장 안 된다 — 입력 순서가 숨은 입력이 되기 때문.
- **상위 N(top N)**: 등수 순으로 앞에서 N명. 경계에 동점이 걸리면 N명이 아닐 수 있다.
- **경계(boundary)**: 상위 N을 자르는 지점. 그 자리 점수와 같은 점수가 뒤에 더 있으면 "경계 동점".
- **enum(열거형)**: 선택지를 전부 나열한 타입. TieRule 3값·CutRule 2값 — "정할 문제"를 코드 표면으로 올린다.
- **record**: 값 묶음의 불변 타입. `Entry`는 생성자 검증으로 빈 이름·음수 점수를 차단한다.
- **Instant**: 자바의 시각 타입(UTC 기준 한 시점). 달성 시각 비교에 쓴다.
