### A. 과제 (Dispatch.java 의 TODO 1~3)

#### 0. 한 줄 요구사항 — "가장 가까운 기사를 준다"

- 이 규칙이 답이 안 되는 이유: **남이 먼저 가져가기** 때문이다.\
  주문마다 "가장 가까운 기사"가 정해져 있어도, 그 기사를 두 주문이 동시에 원하면 한 명만 받는다.\
  그러면 **누가 먼저 고르느냐**가 남은 사람의 답을 바꾼다.

```text
 주문 A 와 B, 기사 1 과 2

   A-1 거리 1   A-2 거리 9
   B-1 거리 2   B-2 거리 9

 B 를 먼저 처리   B 가 1 을 가져간다 → A 는 9   합 11
 A 를 먼저 처리   A 가 1 을 가져간다 → B 는 9   합 10

 두 사람 다 "가장 가까운 기사"를 받았다. 그런데 합이 다르다.
```

- 이 규칙이 답이 되려면 **"기사 하나는 하나만 맡는다"는 제약이 없어야** 한다.\
  제약이 없으면 모든 주문에 각자 가장 가까운 기사를 주면 끝난다.\
  `Driver` javadoc이 직접 그렇게 적었다 — **"그 제약이 이 문제를 어렵게 만든다."**

> **배타적 자원(exclusive resource)** — 동시에 한 사람만 쓸 수 있는 자원.\
> 예: 기사 한 명, 회의실 하나, 좌석 하나. 나눠 쓸 수 있으면 배분 문제가 아니라 계산 문제가 된다.

- 처리 순서가 코드에 안 적혀 있으면 실제로 그 순서를 정하는 것은 **주문 목록을 가져온 쿼리**다.\
  `SELECT ... FROM orders`에 `ORDER BY`가 없으면 데이터베이스가 편한 순서로 준다.
- 그 순서는 **인덱스 하나로 바뀐다.**\
  성능을 위해 인덱스를 추가했을 뿐인데 **배차 결과가 통째로 달라진다.**\
  코드는 한 줄도 안 바뀌었고, 테스트도 다 통과한다.
- 안 들어 있는 결정 셋(+둘): **① 누구를 중심으로 도나**(`Strategy` 3종) **② 주문을 어떤 순서로 보나**(`OrderPriority` 2종) **③ 같은 거리인 후보 중 누구를 고르나**(동점 규칙).\
  더하면 **④ 너무 먼 짝은 어떻게 하나**(거리 제한) **⑤ 무엇을 지표로 재나**(합계만? 최악도?).

#### 1. 계약 — Order 와 Driver

```java
public int distanceTo(Driver driver) {
    return Math.abs(x - driver.x()) + Math.abs(y - driver.y());
}
```

- 격자 거리: **가로 차이의 절댓값 + 세로 차이의 절댓값.**\
  대각선 지름길이 없다 — 도시 블록을 따라 도는 거리다.

> **격자 거리(맨해튼 거리, Manhattan distance)** — 가로와 세로로만 움직여 잰 거리.\
> 예: (0,0)에서 (3,4)까지 직선으로는 5지만, 블록을 따라가면 3+4=7이다.

- 손계산:

```text
 주문 A = (3, 4)

   → (0, 0)   |3-0| + |4-0| = 3 + 4 = 7
   → (6, 8)   |3-6| + |4-8| = 3 + 4 = 7     음수 차이도 같다
   → (3, 5)   |3-3| + |4-5| = 0 + 1 = 1
   → (3, 4)   0                              같은 자리면 0
```

- 좌표 차가 음수여도 같은 값이 나오는 이유: **`Math.abs`가 부호를 지우기** 때문이다.\
  거리는 방향이 없는 값이라 **A에서 B나 B에서 A나 같아야** 한다.\
  부호를 안 지우면 왼쪽 위의 기사가 "거리 −7"이 되어 **누구보다도 가까운 사람**이 된다.
- 위도·경도를 격자 좌표로 두어도 되는 이유: **거리 계산의 성질이 같기** 때문이다(`Order` javadoc).\
  가까운 것과 먼 것이 있고, 삼각부등식이 성립한다.\
  이 챕터가 묻는 것은 **"거리를 정확히 재는 법"이 아니라 "누구에게 줄 것인가"** 라서, 좌표를 단순하게 두면 그 질문만 남는다.
- 생성자가 막는 것: `Order`는 **빈 주문 번호**와 **음수 대기 시간**, `Driver`는 **빈 기사 번호**.\
  전부 **그 한 줄만 보고 판정할 수 있는 잘못**이다.
- `waitedSeconds`는 **공정함의 축**이다.\
  `LONGEST_WAIT`가 이 값으로 주문을 정렬하고, `worstWaitLeftBehind`가 이 값으로 "가장 오래 버려진 사람"을 잰다.\
  거리 계산에는 전혀 안 쓰인다.

#### 2. TODO 1 — orderFirst

```java
List<Order> sorted = new ArrayList<>(orders);
if (priority == OrderPriority.LONGEST_WAIT) {
    sorted.sort(Comparator
            .comparingInt(Order::waitedSeconds).reversed()
            .thenComparing(Order::id));                      // 대기가 같으면 번호로
} else {
    sorted.sort(Comparator.comparing(Order::id));
}

Set<String> taken = new LinkedHashSet<>();
List<Assignment> out = new ArrayList<>();
for (Order order : sorted) {
    Driver best = null;
    int bestDistance = Integer.MAX_VALUE;
    for (Driver driver : drivers) {
        if (taken.contains(driver.id())) {
            continue;                                        // 이미 나간 기사
        }
        int distance = order.distanceTo(driver);
        if (best == null
                || distance < bestDistance
                || (distance == bestDistance && driver.id().compareTo(best.id()) < 0)) {
            best = driver;                                   // 같은 거리면 번호가 앞선 쪽
            bestDistance = distance;
        }
    }
    if (best != null && !tooFar(bestDistance)) {
        taken.add(best.id());
        out.add(new Assignment(order.id(), best.id(), bestDistance));
    }
}
```

- 주문 정렬: `LONGEST_WAIT`는 **대기 시간 내림차순 → 주문 번호 오름차순**, `BY_ID`는 **주문 번호 오름차순**.
- `LONGEST_WAIT`에 번호 비교를 붙이는 이유: **대기 시간이 같은 주문이 실제로 있기** 때문이다.\
  붙이지 않으면 대기가 같은 주문들끼리는 **정렬이 아무것도 안 가른다.**\
  자바의 정렬은 안정적이라 **넣은 순서가 그대로 남고**, 그 순서는 쿼리가 정한다.

> **안정 정렬(stable sort)** — 정렬 기준으로 안 갈리는 항목끼리는 원래 순서를 유지하는 정렬.\
> 예: 대기 시간이 전부 100초면 정렬해도 입력 순서 그대로다. 예외도 안 나고 결과도 그럴듯한데, 답이 입력에 달려 있다.

> **동점 규칙(tie-break)** — 1차 기준으로 순서가 안 갈릴 때 쓰는 2차·3차 기준.\
> 예: 대기 시간이 같으면 주문 번호로, 거리가 같으면 기사 번호로 가린다. 번호는 중복이 없어 반드시 갈린다.

- 그것을 빼면 **대기 시간이 전부 같은 자료에서만** 결함이 드러난다.\
  원본이 실제로 그 줄을 지워봤는데 테스트가 다 통과했다 — 입력 순서를 흔드는 테스트가 `BY_ID`로만 돌고 있었기 때문이다.\
  **대기 시간이 전부 같은 자료**로 흔드는 테스트를 넣으니 잡혔다.
- 이미 배차된 기사는 **`taken` 집합**으로 걸러낸다.\
  기사 번호를 넣어두고 `taken.contains(...)`이면 건너뛴다.\
  이 한 줄이 "기사 하나는 하나만"이라는 제약의 전부다.
- 같은 거리인 기사가 둘이면 **번호가 앞선 쪽**을 고른다(`driver.id().compareTo(best.id()) < 0`).
- 그 기준이 없으면 **`drivers` 목록을 읽는 순서**가 답을 정한다.\
  그리고 그 순서는 데이터베이스 인덱스 하나로 바뀐다.

> **결정성(determinism)** — 같은 입력에 언제나 같은 결과가 나오는 성질.\
> 예: 같은 주문·기사를 20번 섞어 넣어도 같은 배차가 나와야 한다. 안 그러면 버그를 재현할 수조차 없다.
- 거리 제한에 걸린 주문은 **그냥 배차를 못 받는다.**\
  다음으로 가까운 기사를 다시 찾지 **않는다** — 가장 가까운 기사도 멀다면 나머지는 더 머니까 볼 것이 없다.\
  그 주문은 `unassigned`에 남는다.

```text
 거리:  A-d1 2   A-d2 10   B-d1 1   B-d2 7

 기사 순   d1 이 먼저 고른다 → 남은 주문 중 가장 가까운 것은 B(1) → B-d1

                                        합 11, 최악 10
```

#### 4. TODO 3 — globalNearest

```java
while (true) {
    Order bestOrder = null;
    Driver bestDriver = null;
    int bestDistance = Integer.MAX_VALUE;

    for (Order order : orders) {
        if (takenOrders.contains(order.id())) { continue; }
        for (Driver driver : drivers) {
            if (takenDrivers.contains(driver.id())) { continue; }
            int distance = order.distanceTo(driver);
            if (bestOrder == null
                    || distance < bestDistance
                    || (distance == bestDistance
                            && compare(order, driver, bestOrder, bestDriver) < 0)) {
                bestOrder = order;
                bestDriver = driver;
                bestDistance = distance;
            }
        }
    }
    if (bestOrder == null || tooFar(bestDistance)) {
        break;
    }
    takenOrders.add(bestOrder.id());
    takenDrivers.add(bestDriver.id());
    out.add(new Assignment(bestOrder.id(), bestDriver.id(), bestDistance));
}
```

- 한 바퀴가 하는 일: **남은 주문 × 남은 기사를 전부 훑어 가장 짧은 짝 하나를 찾아 붙인다.**\
  그리고 그 둘을 빼고 다시 처음부터 훑는다.
- 같은 거리인 짝이 여럿이면 **주문 번호를 먼저 보고, 같으면 기사 번호**를 본다(`compare`).
- 루프가 끝나는 조건 둘: **① 붙일 짝이 더 없을 때**(`bestOrder == null` — 주문이나 기사가 바닥났다) **② 남은 최단 짝이 거리 제한을 넘을 때.**
- 최단 짝이 제한을 넘으면 그 자리에서 멈춰도 되는 이유: **남은 짝은 전부 그보다 멀기** 때문이다.\
  가장 짧은 것이 안 되면 나머지는 볼 것도 없다.\
  이 성질이 없으면 남은 짝을 전부 훑어야 한다.
- 전체 최적을 안 쓰는 이유: **계산이 훨씬 비싸고 배차는 초 단위로 돌아야 하기** 때문이다.\
  탐욕은 매 바퀴 최선을 고를 뿐 전체를 안 본다.

> **탐욕(greedy)** — 매 순간 지금 가장 좋아 보이는 것을 고르는 방식.\
> 예: 남은 짝 중 최단 거리부터 붙인다. 빠르지만 전체 최적을 보장하지 않는다.

> **전체 최적(global optimum)** — 가능한 모든 짝짓기 조합 중 진짜 최선.\
> 예: 주문 20·기사 20이면 조합이 천문학적이다. 전용 알고리즘이 있어도 탐욕보다 훨씬 비싸다.

- 네 칸짜리 예제에서 탐욕이 지는 과정:

```text
 거리표      d1    d2
        A     2    10
        B     1     7

 [1바퀴] 남은 짝 중 최단 = B-d1 (1)  → 붙인다
 [2바퀴] 남은 것은 A 와 d2 뿐        → A-d2 (10)
                                        합 11, 최악 10

 주문 번호 순은?
        A 가 먼저 고른다 → d1 (2)
        B 는 남은 d2     → 7
                                        합  9, 최악  7

 B-d1 의 1 을 먼저 챙기느라 A 가 10 을 가게 됐다.
```

- 탐욕에 대해 말하는 것: **한 걸음의 최선이 전체의 최선이 아니다.**\
  게다가 **제일 똑똑해 보이는 방식**이라 검증 없이 채택되기 쉽다.\
  측정에서도 200회 중 **47회는 총 거리조차 졌다.**

#### 5. 지표 — 무엇을 재는가

- 네 지표:

| 지표 | 무엇을 보나 |
|---|---|
| `totalDistance` | 배차된 거리의 합 — 효율 |
| `worstDistance` | 배차된 것 중 가장 먼 거리 — 가장 나쁜 배차 하나 |
| `unassigned` | 짝을 못 받은 주문 번호 — 지표에서 빠진 사람들 |
| `worstWaitLeftBehind` | 미배차 중 가장 오래 기다린 시간 — 가장 오래 버려진 한 명 |

- 합계·평균이 감추는 것: **한 명의 극단값**이다.\
  javadoc 그대로 — **"한 명이 두 시간을 기다려도 평균은 다른 999명이 눌러준다."**\
  합계와 평균은 **많은 쪽의 목소리**이고, 서비스가 욕을 먹는 것은 **한 명의 두 시간** 때문이다.

> **최악 지표(worst-case metric)** — 평균·합계가 아니라 가장 나쁜 한 건을 보는 값.\
> 예: `worstDistance`와 `worstWaitLeftBehind`. 성능에서 평균 응답시간 대신 p99를 보는 것과 같다.

> **미배차(unassigned)** — 짝을 못 받은 주문.\
> 예: 기사가 모자라거나 거리 제한에 걸려 아무도 못 받은 사람. 배차 통계의 분모에서 빠지기 쉽다.

- `worstWaitLeftBehind`가 **미배차**를 보는 이유: **배차된 사람은 이미 문제가 끝났기** 때문이다.\
  아직 아무것도 못 받은 사람이 지금도 기다리고 있고, 그 사람이 **다음 라운드에서도 밀리면** 대기가 계속 늘어난다.\
  배차된 건만 세는 지표는 **이 사람을 아예 안 본다.**
- 기사 하나에 주문 셋:

```text
 A(0,0) 10초   B(0,1) 100초   C(0,2) 300초    기사 d1(0,1)

 번호 순   A 가 먼저 고른다 → d1        남는 것 B, C   최장 대기 300 초
 대기 순   C 가 먼저 고른다 → d1        남는 것 A, B   최장 대기 100 초

 같은 자료, 같은 기사 한 명. 전략 하나로 "제일 오래 기다린 사람"이 3 배 갈린다.
```

#### 6. 거리 제한 (maxDistance)

```java
private boolean tooFar(int distance) {
    return maxDistance > 0 && distance > maxDistance;
}
```

- 제한이 **0 이하면 제한 없음**이다.
- "제한 없음"을 0으로 적으면 **"0을 넘으면 안 붙인다"(= 같은 자리에 있는 기사만 허용)** 와 헷갈린다.\
  그래서 코드가 `maxDistance > 0`을 먼저 보고, **테스트가 그 약속을 박아둔다**(`new Dispatch(0)`과 `new Dispatch(-1)` 둘 다 2건).\
  **애매한 값의 뜻은 주석이 아니라 테스트에 적어야 남는다.**
- 제한 8에서:

```text
 번호 순   A-d1 (2)  B-d2 (7)   둘 다 8 이하 → 2 건, 미배차 없음
 대기 순   B-d1 (1)  A-d2 (10)  A 가 10 이라 제한 초과 → 1 건, 미배차 [A]
```

- 공정하게 주려다 한 명을 버리는 과정: **공정함이 B에게 가까운 기사를 주고, 그래서 A에게 먼 기사만 남고, 그 먼 기사가 제한에 걸린다.**\
  공정함과 제한이 각각은 멀쩡한 규칙인데 **합쳐지면 사람을 버린다.**
- 그 버려진 한 명은 **다음 번에 제일 오래 기다린 사람**이 된다.\
  그러면 다음 라운드에서 우선권을 받고, 또 먼 기사만 남으면 또 버려진다.\
  **버려진 사람이 계속 버려지는 고리**가 생길 수 있다.

> **거리 제한(maxDistance)** — 이 거리를 넘는 짝은 아예 안 붙이는 규칙.\
> 예: 제한 20이면 20을 넘는 짝은 배차되지 않고 그 주문은 미배차로 남는다.

### B. 개념

#### 7. 측정 — 총 거리를 줄이면 최악이 나빠진다

```text
 주문 20, 기사 20, 200 회
 전략             총 거리    최악 거리 평균
 ───────────────  ─────────  ──────────────
 주문 번호 순     120,667        95.5
 대기 순          121,649        94.5
 기사 순          122,067        98.0
 짧은 짝부터      112,705       113.3
```

- 짧은 짝부터는 총 거리가 **7% 낫고** 최악 거리가 **19% 나쁘다.**
- 가까운 짝을 먼저 챙기면 **마지막에 남는 짝이 아주 멀어진다.**\
  좋은 짝을 앞에서 다 써버렸기 때문이다.
- 그 마지막 한 명이 **오늘 제일 오래 기다리는 사람**이다.\
  평균은 그 사람을 못 보여준다.
- 보고서에는 **"평균 배차 거리 7% 개선"** 이 올라간다.\
  같은 변경으로 **최악이 19% 나빠졌다는 말은 안 올라간다.**\
  안 재는 지표는 안 나빠진 것처럼 보인다.
- 총 거리조차 지는 경우는 **200회 중 47회**다.\
  탐욕은 전체를 안 본다 — **더 나은 쪽이라고 믿고 골랐는데 네 번에 한 번은 그냥 진다.**

#### 8. 측정 — 네 방식이 같은 배차를 낸 적이 한 번도 없다

```text
 200 회 중 네 방식이 전부 일치한 횟수   0
 둘씩 짝지어도                          0
```

- 전략을 안 정하고 짜면 **코드가 알아서 하나를 고른다.**\
  루프를 주문부터 돌지 기사부터 돌지는 아무 생각 없이 정해지는 것이고, 그게 곧 전략이다.
- 그 선택은 **200번 중 200번** 눈에 보이는 차이를 만든다.
- "전략은 구현 세부"라는 생각에 대한 반박: **일치율이 0%다.**\
  구현 세부라면 대부분 같은 답이 나오고 가끔 다르기를 기대한다.\
  **한 번도 같지 않다면 그것은 세부가 아니라 결과 그 자체다.**

#### 9. 측정 — 사람이 많으면 공정함이 거의 공짜다

```text
 주문 20, 기사 8 (기사가 모자란 상황)
                        번호 순    대기 순
 ─────────────────────  ─────────  ─────────
 남은 주문의 최장 대기   1,660 초   1,013 초
 총 거리                 65,385     65,391
```

- 최장 대기가 **39% 줄고**(1,660 → 1,013) 총 거리는 **6만큼**(0.01%) 는다.\
  사실상 공짜다.
- 계약 테스트의 두 명짜리 예제에서는 공정함이 총 거리를 **22% 올렸다**(9 → 11).
- 두 수가 이렇게 다른 이유: **후보가 많으면 대체재가 있기** 때문이다.\
  두 명뿐이면 좋은 기사 하나를 양보하는 것이 곧 나쁜 기사 하나를 받는 것이다.\
  스무 명이면 "두 번째로 가까운 기사"가 거의 비슷하게 가깝다.\
  **규모가 트레이드오프의 크기를 바꾼다.**
- 자기 말로: **작은 예제는 극단만 보여준다.**\
  두 명짜리 예제에서 잰 22%를 "공정함의 가격"으로 보고하면, 실제 규모에서의 0.01%와 천 배 넘게 틀린다.\
  **예제로는 규칙을 이해하고, 값은 실제 규모에서 재라.**

#### 10. 측정 — 제한을 걸면 지표가 좋아지고 42퍼센트가 버려진다

```text
 거리 제한   미배차          총 거리    배차 건당 거리
 ──────────  ─────────────  ─────────  ──────────────
 없음        0 / 4,000       112,256        28.1
 60            494            65,161
 40            809            49,470
 20          1,672 (42 %)     25,029        10.8
```

- 제한 20에서 총 거리가 **4.5배 줄고 42%가 아무도 못 받는다.**
- 배차된 건만 세면 건당 거리가 **28.1에서 10.8로 2.6배 좋아진다.**\
  **아무 일도 안 하고.**
- 그 "개선"의 실체: **그냥 먼 사람을 안 태웠을 뿐이다.**\
  알고리즘도, 기사 배치도, 아무것도 안 좋아졌다.
- "지표에서 빠진 것이 지표를 좋게 만든다": 건당 평균 거리의 **분모는 "배차된 건"** 이다.\
  먼 짝을 미배차로 밀어내면 **분자(먼 거리)도 빠지고 분모(그 건수)도 빠지는데, 분자가 훨씬 크게 빠진다.**\
  그래서 평균이 내려간다.\
  **나쁜 건을 고치지 않고 집계에서 빼면 집계가 좋아진다.**

> **선택 편향(selection bias)** — 재는 대상을 고르는 방식 때문에 결과가 실제와 달라지는 것.\
> 예: 배차된 건만 세는 평균 거리. 못 태운 42%를 안 세니 평균이 저절로 좋아진다.

- 반드시 같이 재야 하는 지표: **`unassigned`(몇 명이 빠졌나)와 `worstWaitLeftBehind`(빠진 사람 중 제일 오래 기다린 사람).**\
  합계와 평균만으로는 이 둘이 절대 안 보인다.

#### 11. 변종 검증 — 지워도 통과한 줄이 있었다

- 지워도 통과한 코드: **대기 순 정렬의 마지막 주문 번호 기준**(`.thenComparing(Order::id)`).
- 안 잡힌 이유: **입력 순서를 흔드는 테스트가 `BY_ID`로만 돌고 있었기** 때문이다.\
  `BY_ID`는 주문 번호로 정렬하니 동점이 아예 안 생긴다.\
  즉 **동점 규칙을 검증한다면서 동점이 없는 자료로 돌린 것**이다.
- 잡은 방법: **대기 시간이 전부 같은 자료**로 입력 순서를 흔드는 테스트를 넣었다.\
  8개 주문의 대기 시간을 전부 100초로 두고 20번 섞어도 같은 답이 나와야 한다.
- 이 자리는 **14번 포인트, 24번 순위표와 같은 자리**다.\
  셋 다 "값이 같을 때 무엇으로 가리나"이고, 셋 다 **안정 정렬이 결함을 조용히 덮는다.**
- 자기 말로: **동점 규칙은 동점인 자료로만 검증된다.**\
  규칙이 작동하는 조건을 안 만들어놓고 테스트하면, 그 테스트는 규칙이 있든 없든 통과한다.\
  **"지워도 통과하는 테스트"는 검증이 아니라 장식이다.**

> **변종 검증(mutation testing)** — 코드를 일부러 조금 망가뜨려 보고 테스트가 잡아내는지 확인하는 방법.\
> 예: `.thenComparing(Order::id)`를 지웠는데 전부 통과했다 → 그 줄은 아무 테스트도 지키고 있지 않았다.

#### 12. 생각해볼 것 (원본 README)

> 원본 README는 질문만 던지고 답을 안 준다 — 아래는 **(원본에 근거 없음 — 내 추론)** 이다.

- **배차를 미루면 더 좋은 짝이 올 수도 있다**: 이 구현은 **한 순간의 목록을 한 번에 배분**한다(배치).\
  미루기를 넣으면 축이 하나 더 생긴다 — **"얼마나 모아서 한 번에 돌리나"(배치 창)** 다.\
  창을 늘리면 후보가 많아져 총 거리가 줄지만 **모두의 대기가 그만큼 늘어난다.**\
  그리고 이 챕터의 교훈이 그대로 반복된다 — **평균 거리는 좋아지고 최악 대기는 나빠진다.**\
  그러니 배치 창을 넣는다면 `worstWaitLeftBehind`를 **반드시 같이 보고**해야 한다.
- **기사가 거절하면**: 지금 모델에는 거절이 없다 — `Driver`는 상태가 없고 `taken` 집합에 들어가면 끝이다.\
  넣는다면 ① 거절된 짝을 **금지 목록**에 넣고 그 주문만 다시 배차하거나 ② 그 라운드 전체를 다시 돌린다.\
  같은 기사에게 다시 주면 **무한 반복**이 되므로, 최소한 **(주문, 기사) 짝 단위의 거절 기록**이 필요하다.\
  그리고 거절이 잦은 기사는 **후보에서 뒤로 미루는 규칙**이 붙게 되는데, 그것 또한 새 축이다.
- **최악을 재는 지표도 무언가를 감춘다**: 최악 하나만 보면 **분포가 사라진다.**\
  최악 대기가 1,013초라는 사실은 "1,013초짜리가 한 명"인지 "900초대가 200명"인지를 구별해주지 않는다.\
  최악을 좋게 만드느라 **중간 대부분이 조금씩 나빠지는 변경**도 최악 지표만으로는 안 보인다.\
  결국 답은 **하나의 숫자가 아니라 분포**다 — 합계·평균·최악을 같이 보고, 가능하면 p50/p90/p99로 본다.\
  **이 챕터의 진짜 교훈은 "최악을 봐라"가 아니라 "지표 하나로는 항상 뭔가 감춰진다"이다.**
- **기사마다 속도가 다르면**: 거리 대신 **도착 시간**으로 재야 한다.\
  바뀌는 곳은 **`distanceTo` 한 곳뿐**이 아니다 — ① 비교의 축이 거리에서 시간으로 바뀌고 ② `maxDistance`가 `maxEta`가 되고 ③ **`worstDistance`도 의미가 바뀐다**(먼 기사가 빠를 수 있다).\
  더 중요한 것은 **삼각부등식이 흔들린다**는 점이다 — 거리에서는 성립하던 "가까운 것이 빠르다"가 깨지고, 그러면 `globalNearest`의 "최단 짝이 제한을 넘으면 멈춘다"는 최적화도 다시 따져봐야 한다.\
  **`Order.distanceTo(Driver)`가 계약이라는 것이 이 확장을 한 자리로 모아준다.**

#### 13. 연결

- **24번 순위표·14번 포인트와 같은 점**: 셋 다 **"같은 값일 때 무엇으로 가리나"** 이고, 셋 다 **안정 정렬이 결함을 덮는다.**\
  예외도 안 나고 결과도 그럴듯한데 **답이 입력 순서에 달려 있다.**\
  해법도 같다 — **중복이 없는 마지막 기준(식별자)까지 붙인다.**
- **25번 조직도와 비교**: 같은 점은 **"순서를 안 정하면 부를 때마다 다르다"** 이다.\
  다른 점은 **결과의 무게**다 — 25번은 목록의 순서가 흔들려 화면이 이상해지지만, 30번은 **누가 택시를 받고 누가 못 받는지**가 바뀐다.\
  25번은 `TreeMap`으로 자료구조가 순서를 보장하게 만들었고, 30번은 **비교자에 기준을 명시**했다.
- **27번 `ConflictRule`·28번 `BlockRule`·29번 `WindowBase`와 같은 구도**: 넷 다 **명세가 뭉뚱그린 갈림을 enum으로 끌어올려 부르는 쪽이 고르게** 했다.\
  그리고 넷 다 **어느 쪽도 틀리지 않았다.**\
  30번이 다른 점은 **갈림이 가장 크다**는 것이다 — 27번은 결과가 40% 일치하고, 28번은 명단이 93% 다르고, 30번은 **일치율이 0%다.**
- 한 문장: **자원이 배타적이면(기사 하나 = 주문 하나) "가장 가까운 것"이라는 규칙만으로 답이 안 정해진다 — 처리 순서가 답의 일부이고, 그 순서를 안 적으면 쿼리가 대신 정한다.**
- **도메인 모델링 30개의 마지막 챕터가 남기는 것**: 앞의 29개가 **"명세에 안 적힌 결정을 찾아내 드러내라"** 였다면, 30번은 거기에 하나를 더 얹는다 — **"그 결정을 무엇으로 평가할 것인가"** 도 명세에 없다.\
  전략을 enum으로 올려도, **평균만 재면 잘못된 전략을 고르게 된다.**\
  그래서 이 챕터는 결정을 드러내는 것(`Strategy`·`OrderPriority`)과 **결정을 재는 자(`worstDistance`·`unassigned`·`worstWaitLeftBehind`)를 같이 만든다.**\
  **드러내지 않은 결정은 코드가 정하고, 재지 않은 결과는 없는 것이 된다.**
