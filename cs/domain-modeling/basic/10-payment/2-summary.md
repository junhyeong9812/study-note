## 해결하는 문제

결제 취소는 되돌릴 수 없고, 취소 요청은 재시도된다. 이 둘이 만나면 "값이 다르다"가 아니라 **돈이 없어진다.**\
같은 "3,000원 취소해 주세요"가 두 번 왔을 때, 재전송인지 진짜 두 번째 요청인지를 금액만으로는 알 수 없다.

```text
10,000원 승인, 3,000원 취소 요청이 두 번 도착

  재전송이라면      3,000 한 번만       남은 7,000
  다른 상품이라면   3,000 두 번         남은 4,000
                     ↑ 금액은 같다 — 구별할 수 있는 것은 요청에 붙인 번호표(멱등키)뿐
```

이 방식이 없으면 재시도 10%에서 247만 원이 더 빠지고, 더 조용하게는 **중복이 잔액을 먹어 정당한 취소가 거절된다**(230건, 111만 원) — 손님은 성공 응답을 두 번 받았는데 6,000원만 환불된다.\
쉬운 예: 문화상품권 환불 창구 — 3,000원 돌려주고 "7,000원 남았습니다"를 장부에 적는데, 같은 사람이 같은 영수증을 또 내밀면 장부의 영수증 번호로 알아본다.\
똑같은 구조다: 요청마다 **멱등키**를 붙이고, 키를 금액보다 먼저 보며, 상태는 저장하지 않고 **금액에서 파생**시킨다.\
실무 예: PG사 결제 취소 API, 계좌 환불, 포인트 차감, 재고 차감 — 돈이나 수량이 움직이는 모든 API.

### 한눈에 — 쉽게 말하면

**결제 부분 취소 = 문화상품권 환불 창구.**

- 10,000원짜리 상품권으로 결제했는데 3,000원어치만 환불받고 싶다.\
  창구 직원은 "3,000원 돌려드렸고 7,000원 남았습니다"라고 장부에 적는다.\
  나중에 7,000원을 마저 환불받으면 전액 취소다.
- 무서운 점: **환불은 되돌릴 수 없다.**\
  이 챕터에서 재는 것은 "값이 다르다"가 아니라 **"돈이 없어진다"** 다.
- 그리고 환불 요청은 **재시도되는 대표적인 요청**이다 — 응답을 못 받으면 다시 보낸다.\
  같은 "3,000원 환불해 주세요"가 두 번 오면? 재전송인가, 진짜 두 번째 요청인가?\
  이것을 구별하는 도구가 **멱등키**(요청마다 붙이는 고유 번호표)다.
- 실무 예: PG사 결제 취소 API, 계좌 환불, 포인트 차감 — 돈이 움직이는 모든 API.

```text
  10,000원 승인
    → 3,000원 취소   남은 7,000   PARTIALLY_CANCELLED
    → 7,000원 취소   남은     0   CANCELLED

  같은 요청이 두 번 오면?  멱등키 "a" 를 보고 → DUPLICATE (아무 일도 안 함)
```

## 동작·원리

### 전체 흐름

```text
요구사항 문장                          코드로의 번역
─────────────────────────────────────────────────────────────
"돈"                          →  Money 레코드 — 원 단위 정수, 음수 생성 불가
"결제 한 건"                  →  Payment(승인액, 멱등 여부)
"취소 요청 한 건"             →  Cancellation(멱등키, 금액) — 키 없으면 생성 거부
"취소 결과"                   →  Outcome enum {CANCELLED, DUPLICATE, INSUFFICIENT}
"현재 상태"                   →  status() — 필드가 아니라 금액에서 파생
"남은 금액"                   →  remaining() = 승인액 - 취소 합계

cancel()의 판정 순서(계약): ① 멱등키 봤던 키인가 → DUPLICATE
                            ② 금액이 잔액을 넘나 → INSUFFICIENT
                            ③ 반영 → CANCELLED
```

> **멱등키(idempotency key)** — 요청마다 붙이는 고유 번호표.\
> 예: 같은 키가 다시 오면 "아까 그 요청의 재전송"으로 보고 한 번만 반영한다.

> **파생(derive)** — 따로 저장하지 않고 다른 값에서 계산해 내는 것.\
> 예: 상태를 필드로 두지 않고 승인액·취소액에서 매번 계산하면 둘이 어긋날 자리가 없다.

### 규칙 1 — 음수 금액은 만들 수 없다 (Money 타입)

**어떤 요구사항인가**: 명시된 적 없다. 그러나 돈을 다루는 모든 코드의 바닥 규칙이다.

```text
  Money.won(10_000).minus(Money.won(3_000))  →  7,000원   된다
  Money.won(3_000).minus(Money.won(10_000))  →  예외!      "금액이 모자란다"
  new Money(-1)                              →  예외!      생성 자체가 불가
```

**왜 이렇게 모델링했나**: 음수 금액을 허용하면 그것이 흘러다니다가 어딘가에서 합계를 깎고, **그때가 되면 어디서 생겼는지 못 찾는다.**\
만드는 자리에서 막는 것이 유일하게 값싼 방법이다.

세부 규약 하나 더: BigDecimal의 `equals`는 소수 자리수(scale)까지 봐서 0과 0.00이 다르다 — 그래서 금액 비교는 `compareTo`로 한다.

### 규칙 2 — 상태를 따로 들고 있지 않는다: 금액에서 파생시킨다

**흔한(틀린) 구현**:

```text
  if (취소액 == 승인액) 상태 = CANCELLED
  else                  상태 = PARTIALLY_CANCELLED
```

10,000원을 3,000 + 7,000으로 **나눠** 취소하면: 마지막 요청의 취소액(7,000) ≠ 승인액(10,000)이라 잔액은 0인데 상태는 PARTIALLY_CANCELLED.\
측정: 전액 취소로 끝난 909건 중 **612건이 어긋난다.**\
한 번에 전액 취소할 때만 우연히 맞는다.

**올바른 구현** (`status()`):

```text
  취소 합계가 0        →  APPROVED
  잔액이 0             →  CANCELLED
  그 외                →  PARTIALLY_CANCELLED
```

**왜 이렇게 모델링했나**: 상태 필드를 따로 두면 금액과 어긋날 수 있고, 파생시키면 **어긋날 수가 없다.**\
**필드 하나를 없애는 것이 검사 하나를 넣는 것보다 낫다.** (09번의 "끝났다는 표가 말한다"와 같은 원리.)

### 규칙 3 — 멱등키를 금액보다 먼저 본다 (순서가 계약)

**예시**: 10,000원 승인, 키 "a"로 10,000원 취소 완료. 잔액 0. 같은 요청이 재전송되면:

```text
  키를 먼저 본다     →  DUPLICATE      "이미 처리했습니다"
  금액을 먼저 본다   →  INSUFFICIENT   "잔액이 모자랍니다"  ← 틀린 답
```

**왜 순서가 중요한가**: 재시도하는 쪽에서 INSUFFICIENT는 **진짜 실패로 읽힌다.**\
사람이 확인하러 들어오고, 확인해 보면 이미 취소돼 있다.\
최종 잔액은 같아 보여도 **운영 비용이 다르다.** (07번 "dedupe 먼저", 09번 "같은 상태 먼저"와 같은 교훈 — 판정 순서 자체가 계약이다.)

### 규칙 4 — 금액은 멱등키가 아니다

**예시**: 5,000원짜리 취소가 두 번 온다.

```text
  같은 요청의 재전송인가?    → 한 번만 반영해야 한다
  서로 다른 상품의 취소인가? → 두 번 다 반영해야 한다

  금액만 보면 이 둘을 구별할 수 없다. 키가 다르면 다른 요청이다 — 금액이 같아도.
```

키 "a"/5,000 + 키 "b"/5,000 → 둘 다 CANCELLED, 잔액 0, 상태 CANCELLED.\
측정: 멱등키를 금액으로 대신하면 **1,000/1,000이 어긋나고** 누락 총액 23,905,000원 — 금액 종류가 몇 가지 안 되면 반드시 겹치기 때문이다.

### 규칙 5 — 잔액을 넘는 취소는 전부 아니면 전무

**예시**: 10,000원 승인, 7,000원 취소 후 잔액 3,000. 거기에 5,000원 취소 요청:

```text
  INSUFFICIENT — 아무것도 안 바뀐다. 잔액은 그대로 3,000.
  (3,000원만 부분 반영하지 않는다 — 그러면 요청자가 얼마가 취소됐는지 모른다)
```

이후 3,000원 취소 요청은 정상 처리 → CANCELLED.

## 쓰이는 자료구조·알고리즘

- **멱등키 저장소 = 삽입 순서 집합 + 맵** — 봤던 키인지는 `LinkedHashSet<키>`(`seenKeys`)로 판정해 DUPLICATE를 돌려준다. 반영된 취소는 `LinkedHashMap<키, Money>`(`applied`)에 삽입 순서대로 남아 이력 조회(`appliedCancellations`)에 쓰인다. 둘 다 CANCELLED일 때만 기록된다 — [ops-patterns/06-idempotency-store](../../../ops-patterns/06-idempotency-store/2-summary.md)의 축소판.
- **값 타입 `Money`** — 음수 금액 생성과, 결과가 음수가 되는 뺄셈(작은 − 큰)을 타입에서 막는다. `BigDecimal.equals`는 0과 0.00을 다르게 보지만, `Money` 생성자가 소수 자릿수를 0으로 정규화하므로(원 미만이 남으면 예외) `Money`끼리는 그 문제가 없다. 대소 비교는 `compareTo`. [06-subscription](../06-subscription/2-summary.md)의 `BigDecimal` 규칙과 같은 바닥.
- **파생 상태** — `status()` = 취소 합계 0 → APPROVED / 잔액 0 → CANCELLED / 그 외 → PARTIALLY_CANCELLED. 필드가 없으니 어긋날 수 없다. [09-order-state](../09-order-state/2-summary.md)의 `isTerminalIn`(표에서 파생)과 같은 원리.
- **판정 순서 = 계약** — ① 키 → ② 잔액 → ③ 반영. 순서를 바꾸면 재전송이 INSUFFICIENT(진짜 실패)로 읽힌다. [13-inventory](../13-inventory/2-summary.md)의 "중복을 재고보다 먼저"와 같은 자리.
- **3갈래 결과 enum** — `Outcome {CANCELLED, DUPLICATE, INSUFFICIENT}`. 세 결과가 다 자주 나온다(3,140 / 5,423 / 1,437). [09-order-state](../09-order-state/2-summary.md)의 APPLIED/IGNORED/REJECTED와 같은 자리.
- **전부 아니면 전무** — 잔액을 넘는 취소는 부분 반영 없이 통째로 거부. [02-seat-reservation](../02-seat-reservation/2-summary.md)·[14-points](../14-points/2-summary.md)와 같은 계약.
- **대조군 + 양방향 측정** — 멱등을 끈 판을 남겨 "더 빠진 돈"뿐 아니라 "덜 빠진 돈"까지 센다.

## 적용 — 풀어나가는 법

돈이나 수량이 빠져나가는 API(취소·환불·차감)를 만들 때의 순서: ① 요청에 고유 번호표(멱등키)를 붙이게 하고 없는 요청은 만들 수 없게 한다 ② 판정 순서를 키 → 잔액 → 반영으로 고정한다 ③ 상태 필드를 두지 말고 금액에서 파생시킨다 ④ 결과를 boolean이 아니라 셋(됨/이미 됨/모자람)으로 돌려준다 ⑤ 멱등을 끈 대조군으로 재시도 비율별 손실을 양방향으로 잰다.\
아래 「문제」 절이 ①~④의 재료이고, 「측정」 절이 ⑤의 결과다.

### 문제 — 이 챕터가 시키는 것

원본 README가 준 것은 예시 셋과 두 문장이다.

```text
  10,000 원 승인
    -> 3,000 원 취소   남은 7,000   PARTIALLY_CANCELLED
    -> 7,000 원 취소   남은     0   CANCELLED
```

> **결제 취소는 되돌릴 수 없다.** 그래서 이 박스에서 재는 것은 값이 다른 것이 아니라 **돈이 없어지는 것**이다.
>
> 그리고 결제 취소는 **재시도되는 대표적인 요청**이다. 응답을 못 받으면 다시 보낸다.

채울 것: `src/main/java/com/domain/payment/Payment.java` 의 TODO 1~3.\
`Money`(음수 금지 금액 타입)와 `PaymentStatus`(3개 상태 enum)는 계약이라 다 주어져 있다.

| TODO | 메서드 | 시키는 일 |
|---|---|---|
| 1 | `remaining()` | 남은 금액 = 승인액 − 취소액 |
| 2 | `status()` | 상태를 **필드로 들고 있지 말고 금액에서 파생**시킨다 |
| 3 | `cancel(request)` | 취소 시도. **순서가 계약** — 멱등키를 **금액보다 먼저** 본다. 결과는 CANCELLED / DUPLICATE / INSUFFICIENT 셋 |

원본이 못 박은 함정 넷: ① 상태를 따로 들고 있지 않는다(따로 두면 어긋날 수 있고 파생시키면 어긋날 수가 없다) ② 멱등키를 금액보다 먼저 본다 ③ **금액은 멱등키가 아니다** ④ 음수 금액을 만들 수 없게 막는다.

테스트가 못 박은 계약(`PaymentTest`):

- 10,000−3,000 = 7,000이고 3,000−10,000은 예외.
- 10,000을 3,000+7,000으로 나눠 취소하면 APPROVED → PARTIALLY_CANCELLED → CANCELLED.
- 잔액 3,000에 5,000 취소는 INSUFFICIENT이고 **아무것도 안 바꾼다.**
- 0원 결제·0원 취소·빈 멱등키는 생성 거부.
- 같은 키를 세 번 보내면 CANCELLED·DUPLICATE·DUPLICATE, 반영된 취소는 1건.
- 금액이 같아도(5,000+5,000) 키가 다르면 둘 다 적용.
- **잔액이 0이어도 같은 키는 INSUFFICIENT가 아니라 DUPLICATE.**
- 멱등을 끄면 같은 요청이 두 번 빠져 잔액 4,000.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

### 측정이 알려준 것

**하나. 재시도 10%에 247만 원이 더 빠진다** (10만 원 결제 500건, 각 1만 원씩 5번 취소, 멱등 없이):

| 재시도 비율 | 초과 취소 |
|---|---|
| 0% | 0원 |
| 10% | **2,470,000원** |
| 30% | 7,560,000원 |
| 50% | 12,510,000원 |

재시도 10%는 흔한 값이다 — 타임아웃 한 번이면 재전송한다.

**둘. 그런데 방향이 양쪽이다** — 더 빠진 건 420건 2,800,995원, **덜 빠진 건 230건 1,115,370원**:

```text
  10,000 승인, k0=3,000 (재전송됨), k1=7,000

    멱등     3,000 + 7,000 = 10,000   전액 취소 ✓
    비멱등   3,000 + 3,000 = 6,000    k1은 잔액 4,000이라 거부!
```

**중복이 잔액을 먹어서 정당한 취소를 막는다.**\
손님은 전액 환불을 요청했고 성공 응답을 두 번 받았는데 실제로는 6,000원만 환불됐다.\
"중복 요청 = 돈이 더 나간다"만 생각하면 이 방향을 놓친다.\
**그리고 이쪽이 더 나쁘다 — 더 빠진 것은 눈에 띄고 덜 빠진 것은 안 띈다.**

**셋. 세 결과가 다 자주 나온다**: 취소 3,140 / 중복 5,423 / 부족 1,437.\
불리언 하나로 만들면 이 중 둘이 같은 값으로 뭉개진다 — 09번의 APPLIED/IGNORED/REJECTED와 같은 자리다.

## 장애 시나리오와 대처

**1. 전액 환불했다는데 손님 계좌에는 6,000원만 들어왔다**

- 현상: 손님은 성공 응답을 두 번 받았고 전액 환불로 알고 있는데 실제 환불액이 모자란다.
- 보이는 형태: 3,000원 취소가 두 번 반영되고(재전송), 7,000원 취소가 잔액 4,000이라 INSUFFICIENT. 초과 취소 지표에는 안 잡힌다.
- 원인: 멱등 처리가 없어 중복 취소가 잔액을 먹었다 — 피해가 "더 빠지는" 방향이 아니라 "덜 빠지는" 방향이라 눈에 안 띈다(230건, 1,115,370원).
- 대처: 멱등키로 재전송을 DUPLICATE로 걸러 잔액을 지킨다. 지표는 초과 취소만이 아니라 "요청 합계 vs 반영 합계"의 차이를 양방향으로 센다(정답 4번 참고).

**2. 잘못 취소한 3,000원을 되돌릴 방법이 없다**

- 현상: 운영자가 실수로 취소한 건을 "취소의 취소"로 되돌리려는데 모델에 그 경로가 없다.
- 보이는 형태: `Payment`에는 `cancel`만 있고 취소를 지우는 메서드가 없다. `applied` 맵·`seenKeys` 집합에서 키를 빼면 이력이 사라지고 감사가 깨진다.
- 원인: 결제 취소는 되돌릴 수 없다는 전제 위에 모델을 세웠다 — README "생각해볼 것"의 "부분 취소를 취소하려면 무엇이 필요한가". 잔액을 계산으로 파생시키므로 이력을 고치면 상태가 통째로 바뀐다.
- 대처: 취소를 지우지 말고 **반대 방향의 거래**(재승인·보정)를 새 키로 추가해 잔액이 파생되게 한다. 그러면 이력이 남고 멱등키 규칙도 그대로다 — 원장 방식이며 [advanced/04-refund](../../advanced/04-refund/2-summary.md)로 이어진다(정답 5번 참고).

**3. 멱등키를 무한정 들고 있다가 메모리·저장소가 찬다**

- 현상: 오래 돌수록 `applied` 맵(또는 그에 해당하는 테이블)이 커진다.
- 보이는 형태: 결제 한 건의 취소 이력이 영구히 남는다. 이 챕터의 `Payment`는 키를 지우는 경로가 없다 — README "생각해볼 것"의 "멱등키를 언제까지 들고 있나".
- 원인: 재전송은 보통 몇 분 안에 오지만, 키를 영원히 보관하면 저장 비용이 무한히 는다. 반대로 너무 빨리 지우면 늦은 재전송이 새 요청으로 반영된다.
- 대처: 키에 보관 기간(재시도 창보다 충분히 긴 값)을 두고 만료시킨다. 만료 뒤 같은 키가 오면 어떻게 볼지(거부·새 요청)도 정책이다 — [ops-patterns/06-idempotency-store](../../../ops-patterns/06-idempotency-store/2-summary.md)(정답 5번 참고).

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 0원 결제 | 생성 거부 — 처음부터 APPROVED인지 CANCELLED인지 모호하다 |
| 0원 취소 | 생성 거부 — 아무 일도 안 하는데 이력에는 남는다 |
| 빈 멱등키 | Cancellation 생성 거부 |
| 음수 금액 | Money 생성·뺄셈에서 거부 |
| 잔액 0에서 같은 키 재전송 | INSUFFICIENT가 아니라 **DUPLICATE** — 키를 먼저 보니까 |
| 잔액 초과 취소 | 부분 반영 없이 통째로 거부(전부 아니면 전무) |
| 한 번에 전액 취소 | 바로 CANCELLED — 손 갱신 구현은 여기서만 맞고 나눠 취소에서 틀린다 |
| 멱등 끔(비교용 구현) | 같은 요청 2번 = 6,000원 빠짐. 측정 대조용 — 실전에서는 절대 금지 |

## 핵심 문장

- 결제 취소는 되돌릴 수 없고 재시도는 반드시 온다 — 그래서 **멱등키는 선택이 아니라 돈을 지키는 장치**다(재시도 10%면 247만 원).
- 중복 취소의 피해는 양방향이다 — 돈이 더 빠지기도 하고, **중복이 잔액을 먹어 정당한 취소를 막기도 한다.**\
  안 보이는 후자가 더 나쁘다.
- **상태는 저장하지 말고 금액에서 파생시켜라** — 필드 하나를 없애는 것이 검사 하나를 넣는 것보다 낫다(손 갱신은 612/909 어긋남).
- 멱등키를 금액보다 먼저 봐야 재전송이 "이미 처리했음"으로 읽힌다 — 순서를 바꾸면 중복이 실패로 보고되어 사람이 출동한다.
- 금액은 멱등키가 아니다 — 같은 5,000원이 재전송인지 다른 상품인지 금액만으로는 구별 불가.
- 음수 금액·0원 결제·빈 키 같은 모호한 값은 **만드는 자리에서 막는 것이 유일하게 값싼 방법**이다.

### 용어 풀이

- **부분 취소(partial cancellation)**: 결제 금액의 일부만 취소하는 것. 여러 번 나눠 올 수 있다.
- **멱등(idempotent)**: 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질.
- **멱등키(idempotency key)**: 요청의 고유 번호표. "같은 요청"의 판정 기준 — 금액이 아니라 키다.
- **재시도(retry)**: 응답을 못 받은 쪽이 같은 요청을 다시 보내는 것. 타임아웃 한 번이면 발생한다.
- **CANCELLED / DUPLICATE / INSUFFICIENT**: 취소됨 / 이미 처리한 키(아무 일 안 함) / 잔액 부족. 취소 결과의 3갈래.
- **파생 상태(derived state)**: 저장하지 않고 계산해 내는 상태. 금액과 어긋날 수가 없다.
- **Money(값 타입)**: 금액을 감싼 레코드. 음수 생성·음수 뺄셈을 타입 차원에서 막는다.
- **BigDecimal compareTo vs equals**: equals는 0과 0.00을 다르다고 본다 — 금액 비교는 compareTo.
- **전부 아니면 전무(all-or-nothing)**: 요청을 일부만 반영하지 않는 원칙. 부분 반영하면 요청자가 결과를 모른다.
- **초과 취소(over-cancellation)**: 중복 반영으로 승인액보다 많이(또는 의도보다 많이) 빠져나간 돈. 되돌릴 수 없다.
