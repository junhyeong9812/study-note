### A. 과제 (Payment.java 의 TODO 1~3)

#### 0. 요구사항 — 예시 셋

- 안 정해준 결정 넷: **① 같은 요청을 어떻게 식별하나**(멱등키) **② 잔액을 넘는 취소를 어떻게 하나**(전부 아니면 전무 vs 일부만) **③ 상태를 어디에 두나**(필드 vs 파생) **④ 결과를 몇 가지로 표현하나**(불리언 vs 셋).

> **멱등키(idempotency key)** — 같은 요청인지 다른 요청인지를 가르려고 요청마다 붙이는 고유 이름표.\
> 예: 같은 이름표를 단 취소 요청이 두 번 오면 두 번째는 재전송으로 보고 아무 일도 안 한다.

- "되돌릴 수 없다"의 효과: 다른 챕터처럼 "값이 갈린다"로 끝나지 않는다.\
  **틀리면 돈이 실제로 사라지고 복구할 방법이 없다.**\
  그래서 이 챕터의 측정 단위는 "갈린 건수"가 아니라 **원(元)** 이다.
- 재는 것: **돈이 없어지는 것**(초과 취소액·누락 총액).
- 두 번 오는 일이 드물지 않은 이유: **응답을 못 받으면 다시 보내는 것이 정상 동작**이기 때문이다.\
  타임아웃 한 번이면 재전송이고, 측정에서 쓰는 재시도 10%도 흔한 값이다.

> **재전송(retry)** — 응답을 못 받은 쪽이 같은 요청을 한 번 더 보내는 것.\
> 예: 취소는 실제로 처리됐는데 응답만 유실되면, 보낸 쪽은 실패로 알고 똑같은 취소를 다시 보낸다.

- 식별하는 것: **멱등키**(`idempotencyKey`).\
  금액은 식별자가 아니다.

#### 1. TODO 1 — remaining

```java
return approved.minus(cancelled);
```

```java
// Money.minus — 계약 쪽 코드
BigDecimal result = amount.subtract(other.amount);
if (result.signum() < 0) {
    throw new IllegalArgumentException("금액이 모자란다: " + amount + " - " + other.amount);
}
return new Money(result);
```

- 음수를 거부하는 이유: **음수 금액이라는 것은 이 도메인에 존재하지 않는 값**이다.\
  만들 수 없게 막으면 잘못된 계산이 **발생한 그 자리에서** 터진다.
- 나중에 못 찾는 이유: 음수 `Money` 하나가 만들어지면 그 뒤로 여러 번 더해지고 합계에 섞인다.\
  며칠 뒤 정산 총액이 안 맞는 것으로 발견되는데, 그때는 **어디서 생긴 음수인지 추적할 단서가 없다.**\
  터지는 자리와 원인이 멀어진다.

> **조용한 실패(silent failure)** — 에러 없이 정상처럼 끝나는데 결과만 틀린 것.\
> 예: 음수 금액을 그 자리에서 거부하지 않으면, 며칠 뒤 정산 총액이 안 맞을 때에야 드러난다.

- `double` 로 다루면: 이진 근사 오차가 쌓여 **부분 취소를 여러 번 한 뒤 잔액이 정확히 0이 안 된다** → 전액 취소인데 `CANCELLED` 로 안 넘어간다(`Money` javadoc 근거).

> **이진 근사 오차(floating-point error)** — 0.1 같은 십진 소수를 2진수로는 정확히 못 적어서 생기는 아주 작은 차이.\
> 예: 부분 취소를 여러 번 더한 값이 10,000 이 아니라 9,999.9999999 가 되어 "잔액 0"이 영원히 안 된다.

- record + 생성자 검사의 이득: **불변**이라 공유해도 안전하고, **생성자를 통과한 모든 `Money` 는 이미 0 이상·정수 원**이다.\
  검사를 쓰는 쪽마다 반복할 필요가 없다 — 06번의 "방어는 한 곳에만"과 같은 얘기다.

> **불변 객체(immutable)** — 만들어진 뒤 내용이 절대 안 바뀌는 값.\
> 예: `Money` 를 여러 곳에서 같이 들고 있어도, 한쪽이 몰래 금액을 바꿔놓을 수가 없다.

#### 2. TODO 2 — status

```java
if (cancelled.isZero()) {
    return PaymentStatus.APPROVED;
}
return remaining().isZero() ? PaymentStatus.CANCELLED : PaymentStatus.PARTIALLY_CANCELLED;
```

- 판정 순서: **① 취소액이 0이면 APPROVED ② 남은 금액이 0이면 CANCELLED ③ 아니면 PARTIALLY_CANCELLED.**
- 취소액이 0인지를 먼저 봐야 하는 이유: 아무것도 안 한 결제는 취소액 0·잔액 = 승인액이다.\
  잔액부터 보면 APPROVED 를 구별할 자리가 없다 — **"아직 아무것도 취소 안 됨"과 "일부 취소됨"은 다른 상태**다.
- 흔한 구현이 틀리는 입력: **취소를 여러 번 나눠서 한 경우.**\
  `취소액 == 승인액` 을 **한 요청의 금액**과 비교하기 때문이다.

```text
  10,000 승인
    ① 3,000 취소 → 3,000 != 10,000 → PARTIALLY_CANCELLED   (맞다)
    ② 7,000 취소 → 7,000 != 10,000 → PARTIALLY_CANCELLED   (틀렸다!)

    실제 잔액 0인데 상태는 PARTIALLY_CANCELLED
```

- 그 구현의 상태: **PARTIALLY_CANCELLED** — 잔액은 0인데.
- 자기 말로: **어긋날 수 있는 것을 두 개 들고 있지 말고, 하나에서 계산해 내라.**\
  검사는 어긋남을 "발견"할 뿐이고 파생은 어긋남을 "불가능"하게 만든다.

> **파생값(derived value)** — 따로 저장하지 않고, 필요할 때마다 다른 값에서 계산해 내는 값.\
> 예: 상태를 필드로 두지 않고 승인액·취소액에서 매번 계산하면, 상태가 금액과 어긋날 자리 자체가 없다.

- 필드 + 검사 방식의 문제: 검사를 **모든 갱신 경로에** 넣어야 하고, 하나라도 빠뜨리면 조용히 어긋난다.\
  게다가 검사 자체가 죽어 있어도 아무도 모른다(06·08·09번과 같은 구조).
- 09번과 같은 점: 09는 **"끝났다"를 필드가 아니라 표가 말하게** 했고(`isTerminalIn(machine)`), 10은 **상태를 필드가 아니라 금액이 말하게** 했다.\
  둘 다 **단일 출처** — 파생 가능한 것을 저장하지 않는다.

> **단일 출처(single source of truth)** — 같은 사실을 두 곳에 적어두지 않고 한 곳에서만 관리하는 것.\
> 예: "전액 취소됐나"의 출처를 금액 하나로 두면, 상태 필드를 갱신하다 빠뜨릴 일이 없다.

#### 3. TODO 3 — cancel

```java
if (idempotent && seenKeys.contains(request.idempotencyKey())) {
    return Outcome.DUPLICATE;              // ① 키를 먼저 본다
}
if (request.amount().compareTo(remaining()) > 0) {
    return Outcome.INSUFFICIENT;           // ② 그 다음 금액. 아무것도 안 바꾼다
}
seenKeys.add(request.idempotencyKey());
applied.put(request.idempotencyKey(), request.amount());
cancelled = cancelled.plus(request.amount());
return Outcome.CANCELLED;
```

- 세 결과: **CANCELLED** 취소했다 / **DUPLICATE** 같은 멱등키로 이미 처리했다, 아무 일도 안 했다 / **INSUFFICIENT** 남은 금액이 모자란다.
- 불리언으로 뭉개면: **DUPLICATE 와 INSUFFICIENT** 가 "실패" 하나로 합쳐진다(또는 DUPLICATE 가 "성공"으로 합쳐져 중복 처리가 된다).\
  **09번과 정확히 같은 자리.**
- 순서를 뒤집으면: 잔액이 0인데 같은 키가 오면 **INSUFFICIENT**("잔액이 모자란다")가 나간다.
- 재시도 쪽의 오해: 그 응답을 **진짜 실패**로 읽는다 → 경보가 울리고 사람이 확인하러 들어온다 → 확인해보면 **이미 취소돼 있다.**\
  결과 상태는 같지만 **운영 비용이 다르다.**
- 전부 아니면 전무인 이유: 결제 취소는 되돌릴 수 없다.\
  "3,000만 취소해드렸습니다"는 **요청한 적 없는 취소**를 실행한 것이고, 부르는 쪽은 나머지를 다시 요청해야 할지 판단할 근거가 없다.\
  안 하고 거절하면 부르는 쪽이 **다시 판단**할 수 있다(테스트: 잔액 3,000에 5,000 취소 → INSUFFICIENT, 잔액은 여전히 3,000, 상태도 그대로).

> **전부 아니면 전무(all-or-nothing)** — 요청을 통째로 처리하거나 아예 손도 안 대거나, 둘 중 하나만 하는 규칙.\
> 예: 잔액 3,000 에 5,000 취소가 오면 3,000 만 몰래 처리하지 않고 통째로 거절한다.

- 금액으로는 구별 **불가능**하다:

```text
  5,000 원 취소가 두 번 왔다

    같은 요청의 재전송인가      → 한 번만 반영해야 한다
    서로 다른 상품의 취소인가    → 두 번 다 반영해야 한다

  금액만 보면 이 둘이 완전히 똑같아 보인다.
  키가 다르면 다른 요청이다. 금액이 같아도 그렇다.
```

- 키가 같고 금액이 다르면: **DUPLICATE** 다 — 키를 먼저 보고 금액은 아예 안 본다. (`seenKeys` 만으로 판정)
- 반영된 취소를 따로 기록하는 이유(`applied`): **무엇이 실제로 빠졌는지**를 순서대로 남기기 위해서다.\
  DUPLICATE·INSUFFICIENT 는 아무것도 안 넣으므로, 이 목록이 곧 "실제로 일어난 일"의 원장이다 — 테스트가 `List.of(Money.won(3_000))` 처럼 이것을 직접 검증한다.

> **원장(ledger)** — 일어난 사건을 지우지 않고 순서대로 쌓아두는 기록.\
> 예: 잔액만 보면 "지금 얼마 남았나"만 알지만, 원장을 보면 "3,000 이 언제 어떤 요청으로 빠졌나"까지 답할 수 있다.

- 멱등을 끄면: 10,000 승인에 3,000 취소를 두 번 보내면 **둘 다 CANCELLED** 가 되어 6,000이 빠지고 **잔액 4,000.**\
  (이 구현은 측정 대조용으로만 남겨둔 것이다.)

### B. 개념

#### 4. 측정이 알려준 것

- 10만원 결제 500건·각 1만원씩 5번 취소:

| 재시도 비율 | 초과 취소 |
|---|---|
| 0% | 0원 |
| 10% | **2,470,000원** |
| 30% | 7,560,000원 |
| 50% | 12,510,000원 |

- 10%가 흔한 이유: **타임아웃 한 번이면 재전송한다.**\
  네트워크가 있는 한 재시도는 예외가 아니라 기본값이다.
- "더 빠지는 것"만 보면 안 되는 이유: **방향이 양쪽**이다.

| | 건수 | 합계 |
|---|---|---|
| 더 빠진 건 | 420 | 2,800,995원 |
| **덜 빠진 건** | **230** | **1,115,370원** |

- 덜 빠진 건: **230건 / 1,115,370원.**
- 중복이 정당한 취소를 막는 시나리오:

```text
  10,000 승인,  k0 = 3,000 (재전송됨),  k1 = 7,000

  멱등    k0 3,000 → 적용
          k0 3,000 → DUPLICATE (아무 일 없음)
          k1 7,000 → 적용        합계 10,000   전액 취소 ✓

  비멱등  k0 3,000 → 적용
          k0 3,000 → 적용        (잔액 4,000)
          k1 7,000 → 잔액 4,000 이라 거부 ✗
                                합계  6,000   PARTIALLY_CANCELLED
```

  → **중복이 잔액을 먹어서 정당한 취소를 막는다.**

- 손님 입장: **전액 환불을 요청했고 성공 응답을 두 번 받았는데 실제로는 6,000원만 환불됐다.**
- 어느 쪽이 나쁜가: **덜 빠진 쪽이 더 나쁘다.**\
  더 빠진 것은 회사 회계에 구멍으로 **눈에 띄고**, 덜 빠진 것은 손님이 통장을 확인하기 전까지 **아무 데도 안 띈다.**\
  "중복 요청은 돈이 더 나간다"만 생각하면 이 방향을 통째로 놓친다.
- 상태를 손으로 갱신: 전액 취소로 끝난 **909건 중 612건**이 어긋난다.
- 멱등키를 금액으로 대신하면: **1,000/1,000** 이 어긋나고 누락 총액 **23,905,000원.**
- 근본 이유: **금액이 몇 가지 안 되면 반드시 겹친다.**\
  서로 다른 취소가 같은 금액을 갖는 일이 흔하고, 그때마다 뒤엣것이 "중복"으로 버려진다 — 그래서 **누락(덜 빠짐)** 방향으로 어긋난다.
- 세 결과의 건수:

| | 건수 |
|---|---|
| 취소 | 3,140 |
| 중복 | 5,423 |
| 부족 | 1,437 |

  → 셋 다 자주 나온다. 불리언 하나로 만들면 이 중 둘이 같은 값으로 뭉개진다.

- 취소 수수료: (내 추론) 잔액 계산이 **두 축으로 갈린다** — "손님에게 돌려줄 금액"과 "결제에서 차감할 금액"이 달라진다.\
  3,000원 취소에 수수료 500원이면 손님은 2,500을 받지만 결제의 취소액은 3,000일 수도 2,500일 수도 있고, 그 선택이 잔액과 상태를 바꾼다.\
  06번의 "두 번 반올림하지 마라"와 같은 자리 — **합이 맞는 쪽을 뺄셈으로 만들어야 한다.**
- 부분 취소의 취소: (내 추론) 되돌리기가 아니라 **새 승인**이어야 한다.\
  취소를 지우면 원장에서 사건이 사라져 "무엇이 실제로 일어났나"를 못 답한다.\
  필요한 것은 ① 취소 건마다 식별자(지금 `applied` 의 키가 그것) ② 반대 방향 사건을 추가하는 연산 ③ 잔액을 늘리는 것이 허용되는지에 대한 규칙.
- 승인/매입 분리: (내 추론) 상태가 **3개에서 최소 5~6개로** 늘어난다 — AUTHORIZED(승인만) / CAPTURED(매입) / VOIDED(매입 전 취소) / REFUNDED(매입 후 환불) / PARTIALLY_* 들.\
  핵심은 **매입 전 취소와 매입 후 환불이 다른 사건**이라는 것이고, 그러면 금액 축도 승인액·매입액·환불액 셋이 된다.\
  09번의 "표로 그려라"가 바로 필요해지는 지점이다.

> **승인·매입(authorization / capture)** — 카드로 금액을 잡아두는 것(승인)과 실제로 돈을 가져가는 것(매입)을 나눈 두 단계.\
> 예: 주문 시 승인만 걸어두고 출고할 때 매입하면, 출고 전 취소는 "매입 전 취소"라 환불과는 다른 사건이 된다.

#### 6. 연결

- **09번과 같은 점**: 둘 다 결과가 **셋**이고, 둘 다 "불리언 하나로는 표현할 수 없다"가 핵심이다.\
  09의 IGNORED ↔ 10의 DUPLICATE, 09의 REJECTED ↔ 10의 INSUFFICIENT 가 대응한다.\
  **다른 점**: 09의 셋은 `changed()`·`isError()` 두 질문의 조합이고, 10의 셋은 **어디서 걸렸나**(키 / 금액 / 통과)를 말한다.\
  또 09는 상태만 틀리지만 10은 **돈이 사라진다.**
- **07번 중복 제거 키와 같은 문제**: 07의 `userId/kind` 도, 10의 멱등키도 **"무엇을 같은 것으로 볼 것인가"** 를 정하는 일이다.\
  07은 키를 넓게 잡으면 필요한 알림이 사라지고, 10은 키를 금액으로 대신하면 정당한 취소가 사라진다 — **키 설계를 틀리면 조용히 누락된다**는 결말이 같다.
- **06번 `BigDecimal` 과 공유하는 것**: 돈을 **근사값으로 다루지 않는다**는 원칙.\
  06은 `BigDecimal` + 명시적 `RoundingMode` 로, 10은 `Money` 레코드(정수 원·음수 금지)로 같은 원칙을 타입에 심었다.\
  둘 다 **잘못된 값을 만들 수 없게** 막는 쪽을 골랐다.
- 한 문장: **되돌릴 수 없는 요청은 반드시 재시도되므로, "같은 요청인가"를 금액이 아닌 키로 판정하고 그 판정을 금액 검사보다 먼저 두어야 한다 — 그리고 상태는 저장하지 말고 금액에서 파생시킨다.**
