## 한눈에 — 쉽게 말하면

**친구 추천 = "알 수도 있는 사람" 목록 만들기.**

- 규칙 자체는 한 줄이다: **친구의 친구 중에서, 공통 친구가 많은 순.** 반 친구의 반 친구를 소개받는 것과 같다 — 겹치는 친구가 많을수록 아는 사이일 확률이 높다.
- 어려운 것은 세는 쪽이 아니라 **빼는 쪽**이다:

```text
  친구의 친구 중 공통 친구가 많은 순

    나 자신            당연히 뺀다  ┐
    이미 친구           당연히 뺀다  ├ 아무도 안 빠뜨린다
    내가 차단한 사람     당연히 뺀다  ┘
    나를 차단한 사람     ...        ┐
    추천에서 지운 사람   ...        ┘ 여기가 갈린다
```

- 그리고 "공통 친구가 많은 순"의 나머지 — **동점일 때** 누가 위인가 — 는 명세에 아예 안 적히는데, 실제로는 후보의 80%가 동점이다.
- 실무 예: 페이스북 "알 수도 있는 사람", 링크드인 "함께 아는 1촌", 인스타그램 추천 팔로우.

## 문제 — 이 챕터가 시키는 것

원본 README가 시키는 것은 이 한 줄이다.

> 친구의 친구 중 공통 친구가 많은 순.

> **나를 차단한 사람 — …  추천에서 지운 사람 — …**
> **위의 셋은 아무도 안 빠뜨린다. 아래의 둘이 갈린다.**

**채울 것**: `FriendSuggestion.java`의 TODO 1~5. (`Social`은 계약이라 다 주어져 있다.)

| TODO | 메서드 | 시키는 일 |

| 2 | `suggest(me, limit, blockRule, tieRule)` | 제외 → 정렬(공통 수 내림차순 → 동점 규칙 → 항상 식별자) → limit 자르기 |
| 3 | `tieKey(personId, rule)` | 동점일 때 비교할 값 — 가입순/역가입순/식별자 |
| 4 | `excluded(me, candidate, blockRule)` | 이미 친구 / 내가 차단 / (규칙이면) 나를 차단 / 거절 |
| 5 | `excludedCounts(me, blockRule)` | 왜 빠졌나 집계 — **한 사람은 먼저 걸린 한 이유로만** 센다 |

**테스트가 못 박은 계약**(`FriendSuggestionTest`, 9명 관계망 / 차단 me→d·e→me / 거절 me→g):
- 후보는 **두 단까지만** — `candidateIds("me") == {a,b,c,d,e,g,h}`. f(세 단)는 안 들어간다.
- `c`는 a와 b 둘을 통해 닿으므로 공통 친구 2, 나머지는 1.
- 차단 방향 하나로 목록이 갈린다: `I_BLOCKED → [c,e,h]`, `EITHER_BLOCKED → [c,h]`.
- 제외 집계: `I_BLOCKED → Excluded(2,1,1)`, `EITHER_BLOCKED → Excluded(2,2,1)`.
- 친구이면서 차단·거절에도 걸린 사람은 **친구 하나로만** 센다 — `Excluded(2,0,0)`.
- 동점 규칙: `EARLIEST_JOIN → [c,e,h]`, `LATEST_JOIN → [c,h,e]`, `BY_ID → [c,e,h]`.
- 가입 순서가 같으면 **식별자**로 가린다 — 두 규칙 모두 `[y,z]`.
- 없는 사람·`limit ≤ 0`은 `IllegalArgumentException`.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
Social (계약 — 관계 3종, 성질이 다 다르다)
  친구   방향 없음   a-b 친구면 b-a 도 친구
  차단   방향 있음   a가 b를 차단해도 b는 모른다     ← blocked(a,b)는 반대 방향을 안 본다
  거절   방향 있음   추천에서 "이 사람 아니에요"

FriendSuggestion (구현)
  candidates(me)  : 친구의 친구 전부 + 공통 친구 수 세기 (나 자신만 뺌)
  excluded(...)   : 이미 친구 / 차단(BlockRule) / 거절 검사
  suggest(...)    : 걸러내기 → 정렬(공통 수 ↓, 동점은 TieRule, 마지막은 항상 id) → limit 자르기
  excludedCounts  : 왜 빠졌나 집계 — 한 사람은 한 이유로만 센다
```

## 요구사항 → 코드: 어디에 번역됐나

| 말로 된 요구사항 | 코드 |
|---|---|
| "친구는 서로, 차단은 일방" | `Friendship(a,b)` 무방향 / `Block(from,to)` 방향 — `blocked(a,b)`는 반대 방향을 안 본다 |
| "차단을 어느 방향까지 보나" (명세에 없던 결정) | `BlockRule` enum — I_BLOCKED / EITHER_BLOCKED |
| "공통 친구가 많은 순" | `candidates`의 `mutual.merge(candidate, 1, sum)` + 내림차순 정렬 |
| "동점이면?" (명세에 없던 결정) | `TieRule` enum — EARLIEST_JOIN / LATEST_JOIN / BY_ID |
| "왜 빠졌는지 보여달라" | `Excluded(alreadyFriend, blocked, dismissed)` — 한 사람 한 이유 |

## 규칙 1 — 차단은 방향이 있다: BlockRule

**어떤 요구사항인가**: "차단한 사람은 추천에 안 뜬다." — 그런데 **누가 누구를** 차단한 경우인가?

**예시 입력**: b가 나(a)를 차단했다. 나는 그 사실을 모른다.

```text
  I_BLOCKED (내가 차단한 사람만 뺌)
    b는 내 후보에 그대로 남는다 → 내 화면에 b가 뜬다
    b의 화면에는 내가 안 뜨는데, 내 화면에는 b가 뜬다
    → 차단이 반쪽만 작동. 그리고 그것을 겪는 쪽은 "차단한 b"다

  EITHER_BLOCKED (어느 쪽이 차단했든 뺌)
    blocked(me, candidate) 또는 blocked(candidate, me) → 제외
```

**왜 이 결함이 무서운가 — 측정**:
- 차단 방향을 틀려도 **상위 10에서는 거의 안 드러난다**: 200명 관계망에서 차단 50건이면 1/200, 800건이어도 30/200명에서만 상위 10이 갈린다.
- 그런데 **전체 목록으로 비교하면 148/200(74%)이 갈린다.** 같은 결함인데 어디를 보느냐만 다르다 — 결함은 74%에게 있는데 화면(상위 10)에 보이는 것은 15%다. "재현이 잘 안 되네요"가 여기서 나온다.
- 이 결함은 테스트로도 QA로도 안 잡힌다. 잡히는 곳은 **"저 사람이 왜 제 추천에 떠요"라는 문의**뿐이다.

**모델링 교훈**: 방향 있는 관계(차단·거절)를 방향 없는 것(친구)처럼 다루면 **조용히 새어 나간다** — 예외가 아니라 누락으로.

## 규칙 2 — 동점 규칙(TieRule)이 사실상 명단을 정한다

**어떤 요구사항인가**: "공통 친구가 많은 순으로 정렬."

**측정 — 공통 친구 수 분포** (후보 13,638건):

| 공통 친구 | 건수 | 비율 |
|---|---|---|
| 1명 | 10,962 | **80%** |
| 2명 | 2,389 | 17% |
| 3명 | 267 | 1% |
| 4명 이상 | 20 | 0% |

- "많은 순"이라는 규칙이 실제로 정하는 것은 **맨 위 몇 줄뿐**이다. 나머지 80%는 전부 동점 — 그 순서는 동점 규칙이 정하는데, **명세에는 그 말이 없다.**
- 동점 규칙이 없으면? 후보를 모으는 순서 = **친구 목록을 읽는 순서**가 그대로 답이 된다. 규칙이 코드에 없는 게 아니라 **정렬의 부작용으로 존재**하게 된다.
- **측정 — 동점 규칙을 바꾸면**: 순서가 다른 사람 200/200, **뽑힌 사람 자체가 다른 사람 186/200(93%)**. limit로 자르니까 순서가 곧 당락이다 — 추천에 뜨느냐 마느냐가 동점 규칙 하나로 정해진다.

**코드의 처리**: 정렬 사슬 `mutual 내림차순 → tieKey(TieRule) → personId`. 마지막 id 비교는 규칙과 무관하게 **늘 붙는다** — 어떤 규칙이든 최종 순서가 결정적(deterministic)이도록.
  - *결정적(deterministic)*: 같은 입력이면 언제 돌려도 같은 출력. 반대는 "돌릴 때마다 다를 수 있음".

## 규칙 3 — 제외 집계: 한 사람은 한 이유로만 센다

**어떤 요구사항인가**: "후보 중 몇 명이 어떤 이유로 빠졌는지 보여달라."

**함정**: 한 사람이 여러 이유에 걸릴 수 있다(이미 친구인데 거절도 눌렀다). 이유마다 따로 세면 **합계가 후보 수를 넘어서 비율을 못 낸다.**

**처리**: `excludedCounts`는 if / else if 사슬 — 이미 친구 → 차단 → 거절 순서로 **먼저 걸린 이유 하나**로만 센다.

**측정**: 후보 14,498명 중 이미 친구 644, 차단 146, 거절 70 — 남는 것 13,638(94%). **제외 규칙을 다 켜도 6%만 걸러낸다.** 그래서 규칙 하나를 빼먹어도 목록이 멀쩡해 보인다 — 눈으로는 결함을 못 찾는다는 뜻이다.

## 규칙 4 — "몇 단까지"는 알고리즘 세부가 아니라 제품 결정이다

**측정**: 200명 관계망에서 친구의 친구(2단)는 평균 **72.5명**, 3단은 평균 **195.6명** — 사실상 전원이다.

- 후보 범위를 한 칸 늘리면 "추천"이 "서비스 전원 명단"이 된다. 좁은 세상 효과 때문에 단수는 민감한 손잡이다.
  - *좁은 세상(small world)*: 몇 다리만 건너면 누구와도 이어지는 관계망의 성질.
- 그래서 `candidates`는 딱 2단(친구의 친구)만 본다 — 이것은 성능 최적화가 아니라 **제품의 의미**다.

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 차단을 무방향으로 다룸 | `blocked(a,b)`는 한 방향만 — 반대 방향은 EITHER_BLOCKED일 때 별도 호출 |
| 나를 차단한 사람이 내 추천에 뜸 | EITHER_BLOCKED — 안 그러면 차단이 반쪽 작동, 겪는 쪽은 차단한 사람 |
| 동점 규칙 없음 | 친구 목록 읽는 순서가 답이 됨 → TieRule + 최종 id 비교로 결정적으로 |
| 여러 이유에 걸린 사람 중복 카운트 | else if 사슬 — 먼저 걸린 이유 하나로만 |
| 후보에 나 자신 포함 | `candidate.equals(me)`면 continue |
| limit ≤ 0 | 즉시 예외 |
| 없는 사람 id | `social.person(me)`가 던짐 |

**변종 검증**: 고칠 것이 없었다 — 변종 16개 전부 잡혔다. 제외 규칙 넷과 동점 규칙 셋을 계약 테스트에서 **하나씩 따로** 확인하고, 측정 테스트가 무작위 관계망 200명으로 다시 밟기 때문. (규칙 하나 = 테스트 하나의 힘.)

## 핵심 문장

- 추천의 본체는 "세는 규칙"이 아니라 **"빼는 규칙"** 이다 — 그리고 갈리는 자리는 나를 차단한 사람·거절한 사람, 즉 명세가 침묵하는 둘이다.
- **차단은 방향이 있다.** 방향을 틀려도 상위 10에서는 15%만 드러나 테스트·QA를 다 통과하고, "저 사람이 왜 제 추천에 떠요"라는 문의로만 잡힌다.
- 후보의 80%가 공통 친구 1명 동점이라 **"많은 순" 규칙은 맨 위 몇 줄만 정한다** — 나머지는 동점 규칙이 정하는데, 그 규칙은 대개 정렬의 부작용으로만 존재한다.
- 동점 규칙을 바꾸면 93%는 **명단 자체**가 바뀐다 — limit로 자르는 목록에서 순서는 곧 당락이다.
- 제외 규칙을 다 켜도 6%만 걸러내므로 **규칙 하나를 빼먹어도 목록은 멀쩡해 보인다** — 규칙 하나마다 테스트 하나가 있어야 하는 이유.

## 용어 풀이

- **친구의 친구(2단, friend-of-friend)**: 내 친구 목록의 각 사람의 친구. 추천 후보의 정의.
- **공통 친구(mutual friends)**: 나와 후보가 둘 다 친구인 사람들. 그 수가 추천 순서의 유일한 점수.
- **방향 있는 관계(directed)**: a→b와 b→a가 별개인 관계. 차단·거절이 이것이다. 친구는 무방향.
- **BlockRule**: 차단을 어느 방향까지 보나 — I_BLOCKED(내가 차단한 것만) / EITHER_BLOCKED(양방향).
- **TieRule**: 공통 친구 수가 같을 때의 순서 — EARLIEST_JOIN / LATEST_JOIN / BY_ID.
- **동점(tie)**: 정렬 점수가 같은 상태. 여기서는 후보의 80%가 공통 친구 1명으로 동점.
- **결정적(deterministic)**: 같은 입력이면 항상 같은 출력. 최종 id 비교를 늘 붙여서 보장한다.
- **거절(dismissal)**: 추천 화면에서 "이 사람 아니에요"를 누른 기록. 방향이 있다.
- **limit**: 추천 몇 명까지 보여줄지. 이것 때문에 "순서 차이"가 "명단 차이"가 된다.
- **반쪽 작동**: 차단이 한쪽 화면에서만 적용된 상태. 예외 없이 조용히 일어나는 누락 결함.
