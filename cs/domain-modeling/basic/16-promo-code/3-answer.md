### A. 과제 (PromoCode 의 TODO 1~3)

#### 1. 챕터 지문

- 두 층: **정규화 = 이미 일어난 다양성을 흡수**(검출/구제), **글자 빼기 = 다양성 자체를 없앰**(예방). 뒤가 더 아래층이고 더 근본적이다.
- 지문에 **안 들어 있는 결정** — 이게 이 챕터의 진짜 과제다.

```text
지문이 말한 것            지문이 안 말한 것 (내가 정해야 함)
────────────────────     ─────────────────────────────────────────
"하이픈·공백을 뺀다"  →   밑줄 _ 은? 점은? 탭은?  (impl: _ 도 뺀다)
"정규화한다"          →   대문자로 올리나 소문자로 내리나?
"null 이 오면"        →   (아예 말 안 함) 예외인가 빈 문자열인가
"체크섬을 붙인다"     →   자리 번호를 0부터 세나 1부터 세나
"검증한다"            →   길이·문자·체크섬의 검사 순서는?
"코드 길이"           →   체크섬 글자는 길이에 포함인가 (impl: 포함, 8 중 1)
```

- 지울 글자 목록: **요구사항이 아니라 구현자가 정한다.** impl은 `-`, ` `, `_` 셋. 근거는 "손님이 실제로 치는 모양"이고, 늘리면 더 관대해지지만 서로 다른 코드가 같아질 위험도 커진다.
- 대문자로 올리는 이유: 문자 집합(`Alphabet`)이 대문자 기준이라서다. 집합이 소문자였다면 반대였을 것 — **정규화의 방향은 비교 대상의 모양이 정한다.**

#### 2. TODO 1 — normalize

정답 코드 (impl/PromoCode.java):

```java
public static String normalize(String raw) {
    if (raw == null) {
        return "";
    }
    StringBuilder out = new StringBuilder();
    for (char c : raw.toCharArray()) {
        if (c == '-' || c == ' ' || c == '_') {
            continue;
        }
        out.append(Character.toUpperCase(c));
    }
    return out.toString();
}
```

- `null` → **빈 문자열**. 예외가 아니다. 근거: 정규화는 "정리"지 "검증"이 아니다(테스트 `nullInput` 이 못 박음).
- 예외를 던지면: 부르는 쪽이 **null 검사를 또 한다** — 책임이 두 군데로 흩어지고, 검사를 빼먹은 호출처 하나가 그대로 장애가 된다.
- `"---"` → `""`. 안전한 이유: 빈 문자열은 다음 단계인 **길이 검사에서 자연스럽게 거부**된다. 정규화가 판정하지 않고 판정 단계로 넘긴다.
- 한쪽만 정규화하면:

```text
저장:  "PROMO1234"  (정규화 O)
조회:  "promo-1234" (정규화 X)  →  DB 에서 영영 못 찾는다
       → 손님 화면: "없는 코드입니다"   실제: 있다
```

- 다른 모양은 버그가 아니라 **정상**이다. 보여줄 때는 읽기 좋게 하이픈을 넣고(`PROM-O123`), 받을 때는 뺀다. 표시 형식과 저장 형식은 다른 관심사다.
- 밑줄 `_` 은 README 지문에 **없다.** impl 코드에만 있다 — 지문에 없는 결정을 구현자가 채운 대표 사례.

#### 3. TODO 2 — checksum

정답 코드:

```java
public static char checksum(String body, Alphabet alphabet) {
    int sum = 0;
    for (int i = 0; i < body.length(); i++) {
        int value = alphabet.indexOf(body.charAt(i));
        if (value < 0) {
            throw new IllegalArgumentException("문자 집합에 없는 글자다: " + body.charAt(i));
        }
        sum += value * (i + 1);
    }
    return alphabet.at(sum % alphabet.size());
}
```

- 한 줄 계산식: **`체크섬 글자 = alphabet[ (Σ 글자값 × 자리번호) mod 글자수 ]`**
- 자리 번호는 **1부터**(`i + 1`). 0부터 세면 첫 글자의 가중치가 0이라 **첫 글자를 아무거나 바꿔도 체크섬이 안 변한다** — 첫 자리 오타를 통째로 못 잡는다.
- 손계산 `checksum("AAAAAAA", UNAMBIGUOUS)`:

```text
UNAMBIGUOUS = "23456789ABCDEFGHJKMNPQRSTUVWXYZ"  (31 글자)
                0123456789...
A 의 값(index) = 8

자리      1   2   3   4   5   6   7
값        8   8   8   8   8   8   8
곱        8  16  24  32  40  48  56

합 = 8 × (1+2+3+4+5+6+7) = 8 × 28 = 224
224 mod 31 = 224 - 217 = 7
alphabet.at(7) = '9'          →  체크섬 = '9'
```

(테스트 `unknownCharacter` 가 이 값을 그대로 단언한다.)

- 집합 밖 글자 → **`IllegalArgumentException`**. 조용히 넘기지 않는다.
- `indexOf` 가 -1 을 조용히 돌려주면: 음수 가중치가 섞여 **이상한 체크섬이 붙은 코드가 발급**되고, 그 코드는 `isValid` 를 영영 통과 못 한다. 손님 손에 "발급되자마자 못 쓰는 코드"가 쥐여진다.
- 만드는 자리에서 막는 이유: 쓰는 자리에서 걸리면 **이미 코드가 나간 뒤**다. 회수할 방법이 없다. 잘못된 값이 태어나지 못하게 하는 게 싸다.
- `issue` 와 `isValid` 가 어긋나면: 손님은 정확히 받은 대로 쳤는데 "코드가 틀렸다"를 본다 — 고객센터가 재현도 못 하는 문의가 쌓인다. 그래서 테스트가 **두 알파벳 × 500회 무작위로 "issue한 코드는 반드시 isValid"** 를 계약으로 박아 놓았다.

#### 4. TODO 3 — isValid

정답 코드:

```java
public static boolean isValid(String raw, Alphabet alphabet, int length, boolean useChecksum) {
    String code = normalize(raw);                       // [1] 정규화
    if (code.length() != length) return false;          // [2] 길이
    for (char c : code.toCharArray()) {
        if (!alphabet.contains(c)) return false;        // [3] 문자 집합
    }
    if (!useChecksum) return true;
    String body = code.substring(0, length - 1);        // [4] 체크섬
    return code.charAt(length - 1) == checksum(body, alphabet);
}
```

- 순서: **정규화 → 길이 → 문자 집합 → 체크섬.** 주석이 "순서가 계약이다"라고 못 박은 그 순서다.
- 길이를 정규화 전에 재면:

```text
입력 "ABCD-EFGH"   원래 길이 9  ≠ 8  →  거부
     정규화 후     "ABCDEFGH"  길이 8 →  통과

→ 하이픈을 넣어 보여준 코드를 그대로 복사해 붙인 손님이 전부 거부된다
  (소문자 입력도 같은 이유로 [1] 이 먼저여야 한다)
```

- 문자 집합 검사를 체크섬보다 먼저 두는 이유: **체크섬이 집합 밖 글자에 예외를 던지기** 때문이다. 순서를 바꾸면 `isValid` 가 false 를 돌려줘야 할 자리에서 `IllegalArgumentException` 을 던진다 — 반환값 계약이 깨진다.
- `useChecksum=false` 면 `"ABCDEFGH"` 는 **통과한다**(테스트 `withoutChecksum`). 같은 문자열을 `useChecksum=true` 로 부르면 거부된다.
- 그 차이가 **"유효한 코드"(형식이 맞다) vs "존재하는 코드"(우리가 발급했다)** 다. 체크섬이 없으면 이 둘을 구분할 방법이 DB 조회밖에 없다.
- 본문(body) = `code.substring(0, length - 1)` — **마지막 한 글자를 뺀 앞부분 전부.** 체크섬 글자는 길이 8에 포함된다(본문 7 + 체크섬 1).

### B. 개념

#### 5. 측정 하나 — 정규화가 입력의 75%를 살린다

- **7,491 / 10,000** 이 정규화 덕에 통과한다(원본 README).
- 입력 모양을 넷(그대로·소문자·하이픈·공백)으로 나눴으니, 정규화가 없으면 **넷 중 셋이 거부**된다. 그 손님 화면은 "코드가 틀렸다"인데 **코드는 맞았다.**
- 진짜 버그의 위치: 손님도 코드도 아니고 **비교 직전의 처리 단계**다. 데이터는 옳은데 비교 방식이 틀린 것 — 그래서 로그에는 "잘못된 코드 입력"으로만 찍히고 아무도 이상하게 안 여긴다.

#### 6. 측정 둘 — 글자 수가 소수면 체크섬이 전부 잡는다

| 문자 집합 | 글자 수 | 한 글자 치환 | 이웃 자리바꿈 |
|---|---|---|---|
| `0-9 A-Z` | 36 | 18,695 / 19,447 | 19,211 / 19,427 |
| 헷갈림 제외 | **31** | **19,370 / 19,370** | **19,382 / 19,382** |

- 36은 약 **4%를 놓치고**, 31은 **하나도 안 놓친다**.
- 놓치는 이유: 체크섬은 `(Σ 값×자리) mod 글자수` 다. 오타로 생긴 차이가 **글자수의 배수**면 나머지가 그대로라 안 잡힌다.

```text
36 = 4 × 9   →  자리 2, 3, 4, 6 과 약수를 공유
                예) 자리 4에서 값이 9 만큼 바뀌면 차이 = 9×4 = 36 ≡ 0 (mod 36) → 안 잡힘
31 = 소수    →  어떤 자리 번호(1..7)와도 약수를 공유하지 않는다
                자리×차이 가 31의 배수가 되려면 차이가 31의 배수여야 하는데
                값의 범위가 0..30 이라 불가능 → 전부 잡힌다
```

- **우연이다.** 헷갈리는 글자 `0 O 1 I L` 다섯을 뺐더니 36-5=31이 나왔을 뿐이고, README도 "헷갈리는 글자를 뺀 것이 우연히 소수가 된 것인데, 그 덕에 체크섬까지 좋아졌다"라고 쓴다. (설계 교훈: 이 행운을 기대하지 말고, 글자 수를 소수로 **맞추는 것**이 맞다 — 원본에 근거 없음, 내 추론)

#### 7. 측정 셋·넷 — 체크섬 없으면 0, 전체 집합이면 70%

| | 잡은 오타 |
|---|---|
| 체크섬 있음 | 9,473 / 10,000 |
| 체크섬 없음 | **0 / 10,000** |

- **0건이다.** 길이와 문자만 보면 오타 난 코드도 형식은 여전히 맞기 때문이다.
- 그러면 "틀렸는지"를 알려면 **데이터베이스를 조회해야** 한다 — 손님의 오타 하나가 DB 왕복 하나가 된다.

| | 헷갈리는 글자가 든 코드 |
|---|---|
| 전체 집합 (36) | 7,024 / 10,000 |
| 헷갈림 제외 (31) | **0** |

- 전체 집합이면 **70%** 의 코드에 `0 O 1 I L` 중 하나가 든다.
- 체크섬이 잡아주는데도 부족한 이유: **잡아주면 손님은 다시 치고, 또 같은 실수를 한다.** 같은 코드를 다시 봐도 `O`는 여전히 `0`처럼 보이기 때문이다. 검출은 루프를 끊지 못한다.
- 대가: 8글자 기준 **36⁸ ≈ 2.8조 → 31⁸ ≈ 8,529억, 3.3배 감소.** 그래도 충분하다고 본 근거는 발급량이 수십억에 한참 못 미치기 때문이다 — **트레이드오프를 수치로 확인하고 받아들인 것**이 핵심이다.

#### 8. 생각해볼 것 (원본 README 이관 — 답은 원본에 없다, 아래는 내 추론)

- 하이픈 간격: 4글자마다가 흔하다(카드번호·`XXXX-XXXX`). 정답은 없고, **짧은 기억 덩어리로 끊는 것**이 목적이다. 중요한 건 표시용 하이픈이 저장·비교에 절대 들어가지 않는 것.
- 체크섬 두 글자: 검출 실패 확률이 대략 `1/31` → `1/31²`(약 3% → 0.1%)로 준다. 대신 같은 길이면 본문이 한 글자 줄어 **코드 공간이 31배 준다.** 발급량이 적고 오타 비용이 큰 곳(기프트카드)이면 살 만한 거래다.
- 발급 수량 제한: **13번(inventory)과 같은 문제다.** "남은 수량 하나를 동시에 둘이 집는다"는 동일한 공유 자원 경쟁이고, 해법도 같다 — 수를 줄이는 연산을 원자적으로(조건부 UPDATE) 하는 것. 이 챕터의 정규화·체크섬은 그 문제를 전혀 건드리지 않는다.
- 무작위 충돌: 생일 문제다. 코드 공간 N에서 발급 수 k가 `√N` 근처가 되면 충돌이 흔해진다. 31⁸ ≈ 8.5×10¹¹ 이니 `√N ≈ 92만` — **수십만 장까지는 재시도 한 번으로 충분**하고, 그 이상이면 유니크 제약 + 재생성 루프가 필요하다.

#### 9. 연결

- 정규화 후 비교 패턴이 같은 곳: 이메일(대소문자·점), 전화번호(하이픈·국가번호), 주소, 파일 경로(canonical path), 유니코드 정규화(NFC). **공통 규칙 — 저장할 때와 조회할 때 같은 함수를 통과시킨다.**
- 15번(coupon)·17번(cart-discount)과의 다리: 세 챕터 모두 "규칙을 나중에 검사할 것인가, 애초에 성립 불가능하게 만들 것인가"를 묻는다. 16은 **글자 집합으로 오타를 불가능하게** 만들고, 17은 **적용 순서를 계약으로 못 박아** 이상한 할인이 나올 수 없게 만든다.
- 체크섬의 정체: **둘 다지만 1차 목적은 DB 조회를 줄이는 것**이다. 오타 자체를 줄이는 것은 문자 집합이 하고, 체크섬은 이미 난 오타를 **DB에 가기 전에** 걸러낸다. 그래서 측정 셋의 결론이 "체크섬이 없으면 DB를 조회해야 한다"였다.
