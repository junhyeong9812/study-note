# domain-modeling/basic/03-waiting-queue — 정리 (힌트)

## 해결하는 문제

"우대 손님을 먼저 부른다"를 코드로 그대로 옮기면 두 가지가 조용히 깨진다.\
하나는 요구사항의 반례고, 하나는 라이브러리의 성질이다.

```text
[1] 굶주림          우대 우대 우대 우대 ...        [2] 순서 뒤집힘
                     일반 → 영영 대기                 같은 일반 손님 a, b, c 순으로 발권
                                                       PriorityQueue.poll → a, c, b
    "먼저 부른다"의 반례를 안 다뤘다                   2명 테스트는 통과, 3명부터 깨질 수 있다
```

이 챕터가 없으면 [1]은 "가끔 오래 기다린 손님이 있다"는 민원으로, [2]는 "가끔 순서가 이상하다"는 신고로 들어온다. 무작위가 아니다 — 같은 입력(같은 우선순위 a, b, c)이면 매번 똑같이 뒤집히지만, 어떤 입력에서 나는지 모르면 찾기 어렵다.\
쉬운 예: 놀이공원 패스트트랙 — 패스트트랙 줄이 끊이지 않으면 일반 줄은 한 명도 못 탄다. 그래서 "일반 줄에서 N명마다 한 명"처럼 섞는 규칙이 붙는다.\
똑같은 구조다: 우선순위 하나만으로는 안 되고, **밀린 만큼 올려주는 규칙(노화)**과 **같은 등급끼리의 순서(발권 순서)**가 따로 있어야 한다.\
실무 예: 콜센터 라우팅, OS 스케줄러, 메시지 큐 우선순위, 병원 접수 — 우선순위 큐를 쓰는 모든 곳에 같은 두 함정이 있다.

### 한눈에 — 쉽게 말하면

**대기 순번 = "VIP 먼저"라는 규칙을 그대로 코드로 옮기면 일반 손님이 영영 안 불리는 문제.**

- 은행 창구를 생각하자.\
  "우대 손님을 먼저 부른다"를 문자 그대로 지키면, 우대 손님이 끊이지 않는 한 **먼저 온 일반 손님이 영영 안 불린다.**\
  이것이 굶주림(starvation)이다.

```text
우대 우대 우대 우대 ...
일반  →  영영 대기
```

- 막는 방법이 **노화(aging)**: 밀린 만큼 우선순위를 조금씩 올려준다.\
  "최대 몇 번까지 밀리나"를 정하는 값이라 성능 상수가 아니라 **서비스 약속**이다.
- 조용한 함정 하나 더: **자바 `PriorityQueue`는 같은 우선순위끼리의 순서를 보장하지 않는다.**\
  비교자에 발권 순서를 안 넣으면 "먼저 온 순서"가 조용히 뒤집힌다 — 2명 테스트는 통과하고 3명부터 깨진다.

실무 예: 콜센터 라우팅, OS 스케줄러(같은 굶주림·노화 개념), 메시지 큐 우선순위, 병원 접수.

## 동작·원리

### 전체 흐름

```text
Ticket (계약 — 주어짐)
  number    대기 번호 — 사람에게 보이는 값, 뽑은 순서
  priority  우선순위 — 작을수록 먼저 (우대 0, 일반 1)
  sequence  발권 순서 — 같은 우선순위끼리의 순서를 정하는 근거

WaitingQueue (내가 채움)
  issue(priority)      발권 — 번호는 1부터 뽑은 순서대로
  call()               다음 손님 호출 — 빈 큐면 null
                       부를 때 "추월당한" 사람들의 overtaken을 올린다
  effectivePriority    실효 우선순위 = max(0, priority - overtaken/기준)
  cancel / drain / waiting

두 축의 순서:  번호 = 뽑은 순서  /  호출 = 실효 우선순위 → 발권 순서
측정: 역전 쌍 수 (안정성) + 일반 손님이 몇 번째에 불리나 (노화)
```

### 규칙 1 — 번호와 호출 순서는 다른 것이다 (`issue`)

**어떤 요구사항인가**: 대기표 번호는 1부터 순서대로. 우선순위가 높아도 번호는 뽑은 순서다.

```text
일반 발권 → 1번        우대 발권 → 2번
호출:  2번(우대) 먼저, 그다음 1번
```

**왜 이렇게 모델링했나**: 번호는 사람에게 보이는 값이고 호출은 우선순위 순서다 — **둘을 같게 만들면** 이미 1번을 들고 있는 사람이 있는데 나중에 온 우대가 1번을 받는 모순이 생긴다.\
그래서 `Ticket`이 번호(number)·우선순위(priority)·발권 순서(sequence) **셋을 따로** 들고 있다.

### 규칙 2 — 같은 우선순위는 먼저 온 순서 (안정성)

**어떤 요구사항인가**: "일반 1, 2, 3이 차례로 오면 1, 2, 3 순서로 부른다."\
당연해 보이는데 **자바 `PriorityQueue`는 이것을 보장하지 않는다.**

> **힙(heap)** — "제일 작은 것 하나"만 빨리 꺼내도록 만든 자료구조. 전체를 줄 세우지는 않는다.\
> 예: `[1, 5, 3, 9]` 에서 1을 꺼내는 건 빠르지만, 5와 3 중 누가 앞인지는 애초에 정해두지 않는다.

힙에서 왜 뒤집히나 — 같은 우선순위 [a, b, c]:

```text
poll → a를 꺼내고 마지막 c를 뿌리로 올린다  [c, b]
       c와 b가 같으므로 안 내린다
poll → c,  poll → b
결과: a, c, b   ← b와 c가 뒤집혔다
```

**올바른 처리**: 비교자를 "실효 우선순위 → 같으면 발권 순서(sequence)" 2단으로 만든다.

측정 (40명씩 200회, 우대 10%):

| | 역전 쌍 | 발생한 시행 |
|---|---|---|
| 발권 순서 없음 | 104,175 | **200/200** |
| 발권 순서 넣음 | 0 | 0 |

인원수별로는:

```text
n=2 → 0/200   n=3 → 177/200   n=4 → 196/200   n=8 이상 → 200/200
```

> **역전 쌍(inversion)** — 같은 우선순위인데 늦게 온 사람이 먼저 불린, 순서가 뒤집힌 두 사람의 묶음.\
> 예: 3번과 5번이 같은 일반 손님인데 5번이 먼저 불렸다면 그 둘이 역전 한 쌍이고, 이 쌍의 개수가 안정성이 깨진 정도다.

**두 명일 때만 옮길 원소가 없어서 순서가 유지된다.**\
손으로 쓴 2명짜리 테스트는 통과하고 3명부터 깨진다 — "테스트가 통과했다"와 "맞다" 사이의 거리가 한 명이다.\
"가끔 순서가 이상하다"는 신고로 들어오는, 재현 안 되는 종류의 결함이고, 재현하려면 이 측정처럼 **세어야** 한다.
> ⚠ 정정(2026-09-28): "재현 안 되는"은 과장이다 — `PriorityQueue`는 결정적이라 같은 우선순위 [a, b, c]를 같은 순서로 넣으면 매번 a, c, b로 재현된다(README 힙 그림). 또 3명이라고 항상 뒤집히지는 않는다(200회 중 177회). 세는 것은 재현이 아니라 발생 범위를 재기 위해서다.

### 규칙 3 — 노화: 밀린 만큼 올려준다 (`effectivePriority`, `call`)

**어떤 요구사항인가**: 우대만 계속 오면 일반이 굶는다. 그래서 **추월당한 횟수(overtaken)가 기준(agingThreshold)에 찰 때마다 우선순위를 한 단계 올린다.**

```text
실효 우선순위 = max(0, priority - overtaken / 기준)     (작을수록 먼저)
```

예시 손계산 — 노화 기준 10, 일반(priority 1)이 5번 밀린 상태:

```text
실효 = max(0, 1 - 5/10) = 1   ← 아직 안 올랐다 (정수 나눗셈)
새로 온 우대 = 0               → 우대가 먼저
10번 밀리면: max(0, 1 - 10/10) = 0  → 우대와 같아짐 → 발권 순서가 이겨서 일반이 먼저
```

측정 — 일반 1명 앞에 우대 50명이 계속 들어올 때 일반이 불리는 순번:

| 노화 기준 | 불린 순번 |
|---|---|
| 없음(0) | 51번째 |
| 3 | 4번째 |
| 5 | 6번째 |
| 10 | 11번째 |

**정확히 기준 + 1이다.** 그래서 이 값은 성능 튜닝 상수가 아니라 **"최대 N명까지만 밀립니다"라는 서비스 약속을 코드로 쓴 것**이다.

- 우대 비율 측정: 10%에서 이미 최대 245걸음, 30%에서 316, 50%에서 355 — **대기가 우대 비율에 비례하지 않는다.**\
  조금만 우대해도 오래 밀린다.

### 규칙 4 — "밀렸다"의 정의: 시간이 아니라 추월

**핵심 함정**: 부를 때마다 **남은 사람 전부**의 나이를 올리면 안 된다.

```text
노화 기준 1:  일반 A(1번), 일반 B(2번) 발권
call → A     ← 먼저 온 사람이 먼저 간 것. B는 추월당한 게 아니다
우대 P(3번) 발권
call → P     ← 우대가 먼저 (B의 나이를 안 올렸으니까)

만약 "부를 때마다 전원 +1"이었다면: B가 한 번 만에 우대와 같아져 P보다 먼저 불린다
→ 줄이 도는 것만으로 우선순위가 사라진다
```

**올바른 정의**: `call()`에서 꺼낸 사람보다 **먼저 발권한(sequence가 작은) 남은 사람만** overtaken을 올린다 — "밀렸다"는 **나중에 온 사람에게 추월당했다**는 뜻이지 시간이 지났다는 뜻이 아니다.\
요구사항 단어 하나("밀리다")의 정의가 구현의 if 조건 하나(`e.ticket.sequence() < next.ticket.sequence()`)로 번역된 자리다.

### 규칙 5 — 빈 큐는 null, 하한 max(0, …)은 미래를 위해

- **빈 큐에서 `call()` → null** (예외 아님).\
  예외로 하면 "있나 확인"과 "부르기"가 두 단계가 되고 **그 사이에 다른 창구가 부르면** 예외가 난다.\
  null이면 한 번의 호출로 판단한다.

> **확인하고 행동하기(check-then-act)** — "있는지 본다"와 "가져간다"를 두 번에 나눠서 하는 것.\
> 예: `if (대기자 있나) 부른다` 는 두 줄 사이에 다른 창구가 끼어들 수 있다. 한 번에 꺼내고 결과가 null 인지 보면 그 틈이 없다.

- **cancel은 true/false**: 이미 불린 사람 취소는 false(큐에 없다).\
  "취소했다"와 "원래 없었다"를 구별하려면 다른 상태가 필요한데, 여기서는 구별하지 않기로 **정했다**.
- **하한 `max(0, ...)`을 지워도 지금은 모든 테스트가 통과한다** — 추월 횟수가 발권 순서에 대해 단조라서.\
  그래도 남겨뒀다: 노화를 "추월 횟수"에서 "기다린 시간"으로 바꾸면 그 단조성이 깨지고, 그때 이 한 줄이 **이번엔 우대가 굶는 것**을 막는다.\
  (지금 결함이 아닌 코드도 규칙 변경에 대한 방어선일 수 있다.)

> **단조(monotone)** — 한 값이 커질 때 다른 값이 절대 반대로 움직이지 않는 관계.\
> 예: 여기서는 "먼저 온 사람일수록 추월당한 횟수가 항상 크거나 같다". 이 관계가 깨지지 않는 한, 값을 똑같이 깎아도 순위는 안 뒤집힌다.

## 쓰이는 자료구조·알고리즘

- **우선순위 큐 = 이진 힙** — `java.util.PriorityQueue`. "가장 작은 것 하나"만 빨리 꺼내고 전체 순서는 유지하지 않는다. 그래서 같은 값끼리의 순서가 poll마다 섞인다 — [data-structure/07-heap](../../../data-structure/07-heap/2-summary.md).
- **2단 비교자** — `comparingInt(실효 우선순위).thenComparingLong(sequence)`. 힙에 안정성이 없으니 **발권 순서를 키에 넣어** 안정성을 산다. [11-delivery-tracking](../11-delivery-tracking/2-summary.md)의 `thenComparing(ordinal)`, [14-points](../14-points/2-summary.md)의 `thenComparing(id)`와 같은 자리.
- **단조 증가 시퀀스 번호** — `sequence++`로 "먼저 왔다"를 숫자로 만든다. 시각 대신 카운터를 쓰는 이유는 같은 밀리초에 두 명이 올 수 있어서다.
- **노화(aging)** — OS 스케줄러가 굶주림을 막는 그 기법. 여기서는 `max(0, priority - overtaken / 기준)` — 정수 나눗셈이라 기준의 배수마다 한 단계씩 오른다.
- **추월 횟수 세기** — `call()`에서 꺼낸 사람보다 `sequence`가 작은 남은 사람만 `overtaken++`. 힙 안 원소의 키를 바꾸면 힙 순서가 저절로 고쳐지지 않으므로, impl은 남은 원소를 목록으로 옮기고 `clear()`한 뒤 하나씩 다시 `add`한다 — 호출당 O(n log n)이다(노화 기준 0이면 이 단계를 건너뛴다).
- **역전 쌍(inversion) 세기** — 안정성이 깨진 정도의 측정 단위. 정렬 알고리즘에서 "얼마나 안 정렬됐나"를 재는 그 수다 — [algorithm/02-merge-sort](../../../algorithm/02-merge-sort/2-summary.md).
- **빈 큐 = null** — 확인/호출 두 단계를 한 호출로 합쳐 check-then-act 틈을 없앤다.

## 적용 — 풀어나가는 법

우선순위가 있는 대기열(접수·티켓·작업 큐)을 만들 때의 순서: ① 우선순위 외에 "같은 등급끼리의 순서"를 무엇으로 정할지 비교자 2차 키로 못 박는다 ② 낮은 우선순위의 반례("언제 불리나")를 요구사항에 되묻고 노화 기준을 서비스 약속으로 정한다 ③ "밀렸다"의 정의(추월 vs 시간)를 if 조건 하나로 번역한다 ④ 3명 이상 + 역전 쌍 세기로 안정성을 검증한다 — 2명 테스트는 이 결함을 못 본다.\
아래 「문제」 절이 ①~③의 재료다.

### 문제 — 이 챕터가 시키는 것

요구사항은 한 문장이다(원본 README 그대로).

```text
  "우대 손님을 먼저 부른다."
```

**"그대로 옮기면 일반 손님이 영영 안 불릴 수 있다. 그것을 굶주림이라고 한다."**\
막는 방법이 **노화** — 기다린 만큼 우선순위를 올려준다.

> **굶주림(starvation)** — 우선순위가 낮은 쪽이 영영 차례를 못 받는 상태.\
> 예: 우대 손님이 계속 들어오면, 제일 먼저 온 일반 손님이 끝까지 안 불린다.
>
> **노화(aging)** — 기다린(밀린) 만큼 우선순위를 조금씩 올려줘서 굶주림을 막는 방법.\
> 예: 세 번 추월당하면 일반 손님도 우대와 같은 등급이 되고, 같아지면 먼저 온 쪽이 이긴다.

**"그리고 조용한 함정이 하나 더 있다."**\
**자바의 `PriorityQueue` 는 같은 우선순위끼리의 순서를 보장하지 않는다.**

## 장애 시나리오와 대처

**1. 창구를 둘로 늘리자 같은 손님이 두 번 불리거나 번호가 건너뛴다**

- 현상: 창구 하나일 때는 멀쩡하던 순번이 창구 둘부터 꼬인다.
- 보이는 형태: 전광판에 같은 번호가 두 창구에 뜨거나, 한 번호가 아예 안 뜬다. 바쁜 시간에만 난다.
- 원인: 두 창구가 한 큐를 같이 쓰는데 `call()`이 "꺼내기 + 남은 사람 추월 횟수 올리기"를 여러 단계로 하므로 중간에 다른 창구가 끼어든다. `issue`의 번호 증가(`nextNumber++`)와 `cancel`도 같은 상태를 바꾸는데, `PriorityQueue`는 동기화되지 않는다 — README "생각해볼 것"이 던진 질문 그대로다. 빈 큐를 null로 만든 이유(확인/호출 두 단계 사이의 틈)가 창구가 여럿이면 `call()` 안에서도 되풀이된다.
- 대처: 발권·호출·취소 등 큐 상태를 건드리는 연산 전부를 같은 락으로 묶는다(`call()`만 묶으면 부족하다). 한 프로세스 안이면 보통의 락으로 충분하고, 분산 락이 필요한지는 창구 서버 배치에 달렸다. 이 챕터 범위 밖이라 [ops-patterns/11-distributed-lock](../../../ops-patterns/11-distributed-lock/2-summary.md)으로 넘긴다(정답 9번 참고).

**2. 우대 손님이 10%뿐인데 일반 손님이 수백 걸음 밀린다**

- 현상: 우대 비율은 낮은데 일반 손님 최대 대기가 비정상적으로 길다.
- 보이는 형태: 우대 10%에서 최대 245걸음, 30%에서 316, 50%에서 355 — 비율에 비례하지 않는다.
- 원인: 이 수치는 노화가 꺼진 조건(기준 0 = 노화 없음, 300명을 받으며 두 명당 한 명씩 호출)에서 잰 것이다 — 노화가 없으면 굶주림을 막는 장치가 없다. 기준이 지나치게 큰 경우도 비슷하리라 짐작되지만 측정은 없다 [?]. "조금만 우대해도 오래 밀린다"는 직관과 반대다.
- 대처: 노화 기준 = "최대 N명까지만 밀립니다"라는 약속으로 정한다 — 측정 조건(일반 1명 뒤로 우대가 계속 옴)에서는 기준 N이면 N번 추월당한 뒤 N+1번째로 불린다. 우선순위 차이가 더 크거나 조건이 다르면 상한도 달라진다. 값을 정하는 주체는 개발자가 아니라 서비스다(정답 6번 참고).

**3. 불렀는데 안 온 손님이 줄 전체를 세운다**

- 현상: 호출된 손님이 자리에 없으면 창구가 기다리고 다음 사람이 안 불린다.
- 보이는 형태: `call()`로 꺼낸 순간 그 손님은 큐에서 사라진다 — 다시 넣는 API가 없다. `cancel`은 대기 중인 표를 버릴 뿐이라 이미 불린 표에는 `false`다. 줄에 다시 서려면 `issue`로 새 번호를 받아야 한다.
- 원인: 이 큐에는 "불렸으나 미도착"이라는 상태가 없다. 대기 → 호출 두 단계뿐이라 재호출 횟수·복귀 번호 규칙이 정해져 있지 않다.
- 대처: 호출 상태를 따로 두고 "몇 번까지 재호출하나, 돌아오면 원래 번호인가 새 번호인가"를 규칙으로 정한다. 상태가 셋 이상이 되면 [09-order-state](../09-order-state/2-summary.md)의 전이 표가 필요해진다(정답 9번 참고).

### 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 비교자가 우선순위만 봄 | **발권 순서를 2차 키로** — 안 넣으면 3명부터 뒤집히고 40명이면 200/200 |
| 2명짜리 수동 테스트로 안정성 확인 | 2명은 유일하게 안 걸리는 크기 — **3명 이상 + 역전 쌍 세기**로 검증 |
| 부를 때마다 전원 나이 올림 | **추월당한 사람만**(sequence가 더 작은 남은 사람) — 아니면 줄이 도는 것만으로 우선순위 소멸 |
| 노화가 즉시 뒤집는다고 착각 | 정수 나눗셈이라 기준의 배수마다 한 단계씩 — 기준 10에 5번 밀렸으면 아직 우대가 먼저 |
| 빈 큐에서 예외 | null 반환 — 확인/호출 두 단계 사이의 틈을 없앤다 |
| 음수 우선순위·0 이하 번호·음수 노화 기준 | 생성 시 거부 — 음수 우선순위를 허용하면 노화가 아무리 붙어도 못 따라잡는 손님이 생긴다 |
| 하한 없는 실효 우선순위 | max(0, …) — 오래 기다린 일반이 우대보다 영구히 앞서면 이번엔 우대가 굶는다 |

> ⚠ 정정(2026-09-28): 위 표의 세 줄을 바로잡는다. ① "2명은 유일하게 안 걸리는 크기" — 0·1명도 역전이 없고, 3명이라고 항상 뒤집히지도 않는다(177/200). "2명 이하로는 드러나지 않는다"가 맞다. ② 음수 우선순위 거부는 `Ticket` 생성자 계약이 맞다(Ticket.java:19). 그러나 이유가 성립하지 않는다 — 노화가 켜져 있으면 `max(0, …)` 때문에 음수 우선순위도 실효값 0으로 올라가 따라잡힌다(WaitingQueue.java `effectivePriority`). 거부 이유는 원본에 없다 [?]. ③ 지금의 추월 횟수 모델에서는 하한을 지워도 호출 순서가 같다(README 「변종 검증」). "우대가 굶는다"는 노화를 '기다린 시간' 기준으로 바꿨을 때의 위험이다.

## 핵심 문장

- "우대를 먼저 부른다"를 그대로 옮기면 굶주림이 생긴다 — 요구사항 문장 하나에는 그 반례(일반 손님은 언제 불리나)까지가 설계 대상이다.
- 노화 기준은 성능 상수가 아니라 서비스 약속이다 — 기준 + 1이 정확히 최대 밀림 횟수다.
> ⚠ 정정(2026-09-28): 기준 + 1은 **불린 순번**이다. 밀림(추월당한) 횟수는 기준과 같다 — 기준 3이면 3번 추월당하고 4번째로 불린다(README 표). 그리고 이 값은 측정 조건(일반 1명 뒤로 우대가 계속 옴, 우선순위 차이 1)에서의 값이다. README의 "기준 + 1이 최대 밀림 횟수" 표현도 같은 혼동이다.
- 자바 `PriorityQueue`는 같은 우선순위의 순서를 보장하지 않는다 — 발권 순서를 비교자 2차 키로 넣어야 하고, 이 결함은 2명 테스트로는 절대 안 잡힌다.
- "밀렸다" = 나중에 온 사람에게 추월당했다 — 시간 경과로 정의하면 줄이 도는 것만으로 우선순위가 사라진다.\
  단어의 정의가 곧 if 조건이다.
- 번호는 뽑은 순서, 호출은 우선순위 순서 — 사람에게 보이는 값과 처리 순서를 한 값으로 합치면 모순이 생긴다.
- 지금 결함이 아닌 `max(0, …)` 한 줄을 남긴 이유: 규칙이 "횟수"에서 "시간"으로 바뀌는 순간의 방어선이다.

### 용어 풀이

- **굶주림(starvation)**: 우선순위가 낮은 쪽이 영영 처리되지 않는 현상. "우대 먼저"의 부작용.
- **노화(aging)**: 밀린 만큼 우선순위를 조금씩 올려 굶주림을 막는 기법. 여기서는 추월 횟수 기반.
- **추월(overtake)**: 나보다 늦게 발권한 사람이 먼저 불리는 것. "밀렸다"의 정확한 정의.
- **실효 우선순위(effective priority)**: 원래 우선순위에서 노화 보정을 뺀 값. `max(0, priority - overtaken/기준)`.
- **안정성(stability)**: 같은 우선순위끼리 들어온 순서가 유지되는 성질. 자바 `PriorityQueue`에는 없다.
- **역전 쌍(inversion)**: 같은 우선순위인데 늦게 온 사람이 먼저 불린 두 사람의 쌍. 안정성 깨짐의 측정 단위.
- **힙(heap)**: `PriorityQueue`의 내부 구조. 꺼낼 때 마지막 원소를 뿌리로 올리는 과정에서 같은 값끼리의 순서가 섞인다.
- **비교자(comparator)**: 누가 먼저인지 정하는 함수. "실효 우선순위 → 발권 순서" 2단이 계약이다.
- **단조(monotonic)**: 순서가 한 방향으로만 가는 성질. 추월 횟수가 발권 순서에 단조라서 하한 없이도 지금은 결과가 같다.
- **멱등 없는 확인-후-행동 틈(check-then-act)**: "있나 확인" 후 "부르기" 사이에 상태가 바뀌는 문제. 빈 큐를 null로 처리해 한 호출로 합친 이유.
