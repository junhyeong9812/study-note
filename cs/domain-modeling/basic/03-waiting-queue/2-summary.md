## 한눈에 — 쉽게 말하면

**대기 순번 = "VIP 먼저"라는 규칙을 그대로 코드로 옮기면 일반 손님이 영영 안 불리는 문제.**

- 은행 창구를 생각하자. "우대 손님을 먼저 부른다"를 문자 그대로 지키면, 우대 손님이 끊이지 않는 한 **먼저 온 일반 손님이 영영 안 불린다.** 이것이 굶주림(starvation)이다.

```text
우대 우대 우대 우대 ...
일반  →  영영 대기
```

- 막는 방법이 **노화(aging)**: 밀린 만큼 우선순위를 조금씩 올려준다. "최대 몇 번까지 밀리나"를 정하는 값이라 성능 상수가 아니라 **서비스 약속**이다.
- 조용한 함정 하나 더: **자바 `PriorityQueue`는 같은 우선순위끼리의 순서를 보장하지 않는다.** 비교자에 발권 순서를 안 넣으면 "먼저 온 순서"가 조용히 뒤집힌다 — 2명 테스트는 통과하고 3명부터 깨진다.

실무 예: 콜센터 라우팅, OS 스케줄러(같은 굶주림·노화 개념), 메시지 큐 우선순위, 병원 접수.

## 문제 — 이 챕터가 시키는 것

요구사항은 한 문장이다(원본 README 그대로).

```text
  "우대 손님을 먼저 부른다."
```

**"그대로 옮기면 일반 손님이 영영 안 불릴 수 있다. 그것을 굶주림이라고 한다."**\
막는 방법이 **노화** — 기다린 만큼 우선순위를 올려준다.

> **굶주림(starvation)** — 우선순위가 낮은 쪽이 영영 차례를 못 받는 상태.\
> 예: 우대 손님이 계속 들어오면, 제일 먼저 온 일반 손님이 끝까지 안 불린다.
>
> **노화(aging)** — 기다린(밀린) 만큼 우선순위를 조금씩 올려줘서 굶주림을 막는 방법.\
> 예: 세 번 추월당하면 일반 손님도 우대와 같은 등급이 되고, 같아지면 먼저 온 쪽이 이긴다.

**"그리고 조용한 함정이 하나 더 있다."**\
**자바의 `PriorityQueue` 는 같은 우선순위끼리의 순서를 보장하지 않는다.**

## 전체 흐름

```text
Ticket (계약 — 주어짐)
  number    대기 번호 — 사람에게 보이는 값, 뽑은 순서
  priority  우선순위 — 작을수록 먼저 (우대 0, 일반 1)
  sequence  발권 순서 — 같은 우선순위끼리의 순서를 정하는 근거

WaitingQueue (내가 채움)
  issue(priority)      발권 — 번호는 1부터 뽑은 순서대로
  call()               다음 손님 호출 — 빈 큐면 null
                       부를 때 "추월당한" 사람들의 overtaken을 올린다
  effectivePriority    실효 우선순위 = max(0, priority - overtaken/기준)
  cancel / drain / waiting

두 축의 순서:  번호 = 뽑은 순서  /  호출 = 실효 우선순위 → 발권 순서
측정: 역전 쌍 수 (안정성) + 일반 손님이 몇 번째에 불리나 (노화)
```

## 규칙 1 — 번호와 호출 순서는 다른 것이다 (`issue`)

**어떤 요구사항인가**: 대기표 번호는 1부터 순서대로. 우선순위가 높아도 번호는 뽑은 순서다.

```text
일반 발권 → 1번        우대 발권 → 2번
호출:  2번(우대) 먼저, 그다음 1번
```

**왜 이렇게 모델링했나**: 번호는 사람에게 보이는 값이고 호출은 우선순위 순서다 — **둘을 같게 만들면** 이미 1번을 들고 있는 사람이 있는데 나중에 온 우대가 1번을 받는 모순이 생긴다. 그래서 `Ticket`이 번호(number)·우선순위(priority)·발권 순서(sequence) **셋을 따로** 들고 있다.

## 규칙 2 — 같은 우선순위는 먼저 온 순서 (안정성)

**어떤 요구사항인가**: "일반 1, 2, 3이 차례로 오면 1, 2, 3 순서로 부른다." 당연해 보이는데 **자바 `PriorityQueue`는 이것을 보장하지 않는다.**

힙에서 왜 뒤집히나 — 같은 우선순위 [a, b, c]:

```text
poll → a를 꺼내고 마지막 c를 뿌리로 올린다  [c, b]
       c와 b가 같으므로 안 내린다
poll → c,  poll → b
결과: a, c, b   ← b와 c가 뒤집혔다
```

**올바른 처리**: 비교자를 "실효 우선순위 → 같으면 발권 순서(sequence)" 2단으로 만든다.

측정 (40명씩 200회, 우대 10%):

| | 역전 쌍 | 발생한 시행 |
|---|---|---|
| 발권 순서 없음 | 104,175 | **200/200** |
| 발권 순서 넣음 | 0 | 0 |

인원수별로는:

```text
n=2 → 0/200   n=3 → 177/200   n=4 → 196/200   n=8 이상 → 200/200
```

**두 명일 때만 옮길 원소가 없어서 순서가 유지된다.** 손으로 쓴 2명짜리 테스트는 통과하고 3명부터 깨진다 — "테스트가 통과했다"와 "맞다" 사이의 거리가 한 명이다. "가끔 순서가 이상하다"는 신고로 들어오는, 재현 안 되는 종류의 결함이고, 재현하려면 이 측정처럼 **세어야** 한다.

## 규칙 3 — 노화: 밀린 만큼 올려준다 (`effectivePriority`, `call`)

**어떤 요구사항인가**: 우대만 계속 오면 일반이 굶는다. 그래서 **추월당한 횟수(overtaken)가 기준(agingThreshold)에 찰 때마다 우선순위를 한 단계 올린다.**

```text
실효 우선순위 = max(0, priority - overtaken / 기준)     (작을수록 먼저)
```

예시 손계산 — 노화 기준 10, 일반(priority 1)이 5번 밀린 상태:

```text
실효 = max(0, 1 - 5/10) = 1   ← 아직 안 올랐다 (정수 나눗셈)
새로 온 우대 = 0               → 우대가 먼저
10번 밀리면: max(0, 1 - 10/10) = 0  → 우대와 같아짐 → 발권 순서가 이겨서 일반이 먼저
```

측정 — 일반 1명 앞에 우대 50명이 계속 들어올 때 일반이 불리는 순번:

| 노화 기준 | 불린 순번 |
|---|---|
| 없음(0) | 51번째 |
| 3 | 4번째 |
| 5 | 6번째 |
| 10 | 11번째 |

**정확히 기준 + 1이다.** 그래서 이 값은 성능 튜닝 상수가 아니라 **"최대 N명까지만 밀립니다"라는 서비스 약속을 코드로 쓴 것**이다.

- 우대 비율 측정: 10%에서 이미 최대 245걸음, 30%에서 316, 50%에서 355 — **대기가 우대 비율에 비례하지 않는다.** 조금만 우대해도 오래 밀린다.

## 규칙 4 — "밀렸다"의 정의: 시간이 아니라 추월

**핵심 함정**: 부를 때마다 **남은 사람 전부**의 나이를 올리면 안 된다.

```text
노화 기준 1:  일반 A(1번), 일반 B(2번) 발권
call → A     ← 먼저 온 사람이 먼저 간 것. B는 추월당한 게 아니다
우대 P(3번) 발권
call → P     ← 우대가 먼저 (B의 나이를 안 올렸으니까)

만약 "부를 때마다 전원 +1"이었다면: B가 한 번 만에 우대와 같아져 P보다 먼저 불린다
→ 줄이 도는 것만으로 우선순위가 사라진다
```

**올바른 정의**: `call()`에서 꺼낸 사람보다 **먼저 발권한(sequence가 작은) 남은 사람만** overtaken을 올린다 — "밀렸다"는 **나중에 온 사람에게 추월당했다**는 뜻이지 시간이 지났다는 뜻이 아니다. 요구사항 단어 하나("밀리다")의 정의가 구현의 if 조건 하나(`e.ticket.sequence() < next.ticket.sequence()`)로 번역된 자리다.

## 규칙 5 — 빈 큐는 null, 하한 max(0, …)은 미래를 위해

- **빈 큐에서 `call()` → null** (예외 아님). 예외로 하면 "있나 확인"과 "부르기"가 두 단계가 되고 **그 사이에 다른 창구가 부르면** 예외가 난다. null이면 한 번의 호출로 판단한다.
- **cancel은 true/false**: 이미 불린 사람 취소는 false(큐에 없다). "취소했다"와 "원래 없었다"를 구별하려면 다른 상태가 필요한데, 여기서는 구별하지 않기로 **정했다**.
- **하한 `max(0, ...)`을 지워도 지금은 모든 테스트가 통과한다** — 추월 횟수가 발권 순서에 대해 단조라서. 그래도 남겨뒀다: 노화를 "추월 횟수"에서 "기다린 시간"으로 바꾸면 그 단조성이 깨지고, 그때 이 한 줄이 **이번엔 우대가 굶는 것**을 막는다. (지금 결함이 아닌 코드도 규칙 변경에 대한 방어선일 수 있다.)

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 비교자가 우선순위만 봄 | **발권 순서를 2차 키로** — 안 넣으면 3명부터 뒤집히고 40명이면 200/200 |
| 2명짜리 수동 테스트로 안정성 확인 | 2명은 유일하게 안 걸리는 크기 — **3명 이상 + 역전 쌍 세기**로 검증 |
| 부를 때마다 전원 나이 올림 | **추월당한 사람만**(sequence가 더 작은 남은 사람) — 아니면 줄이 도는 것만으로 우선순위 소멸 |
| 노화가 즉시 뒤집는다고 착각 | 정수 나눗셈이라 기준의 배수마다 한 단계씩 — 기준 10에 5번 밀렸으면 아직 우대가 먼저 |
| 빈 큐에서 예외 | null 반환 — 확인/호출 두 단계 사이의 틈을 없앤다 |
| 음수 우선순위·0 이하 번호·음수 노화 기준 | 생성 시 거부 — 음수 우선순위를 허용하면 노화가 아무리 붙어도 못 따라잡는 손님이 생긴다 |
| 하한 없는 실효 우선순위 | max(0, …) — 오래 기다린 일반이 우대보다 영구히 앞서면 이번엔 우대가 굶는다 |

## 핵심 문장

- "우대를 먼저 부른다"를 그대로 옮기면 굶주림이 생긴다 — 요구사항 문장 하나에는 그 반례(일반 손님은 언제 불리나)까지가 설계 대상이다.
- 노화 기준은 성능 상수가 아니라 서비스 약속이다 — 기준 + 1이 정확히 최대 밀림 횟수다.
- 자바 `PriorityQueue`는 같은 우선순위의 순서를 보장하지 않는다 — 발권 순서를 비교자 2차 키로 넣어야 하고, 이 결함은 2명 테스트로는 절대 안 잡힌다.
- "밀렸다" = 나중에 온 사람에게 추월당했다 — 시간 경과로 정의하면 줄이 도는 것만으로 우선순위가 사라진다. 단어의 정의가 곧 if 조건이다.
- 번호는 뽑은 순서, 호출은 우선순위 순서 — 사람에게 보이는 값과 처리 순서를 한 값으로 합치면 모순이 생긴다.
- 지금 결함이 아닌 `max(0, …)` 한 줄을 남긴 이유: 규칙이 "횟수"에서 "시간"으로 바뀌는 순간의 방어선이다.

## 용어 풀이

- **굶주림(starvation)**: 우선순위가 낮은 쪽이 영영 처리되지 않는 현상. "우대 먼저"의 부작용.
- **노화(aging)**: 밀린 만큼 우선순위를 조금씩 올려 굶주림을 막는 기법. 여기서는 추월 횟수 기반.
- **추월(overtake)**: 나보다 늦게 발권한 사람이 먼저 불리는 것. "밀렸다"의 정확한 정의.
- **실효 우선순위(effective priority)**: 원래 우선순위에서 노화 보정을 뺀 값. `max(0, priority - overtaken/기준)`.
- **안정성(stability)**: 같은 우선순위끼리 들어온 순서가 유지되는 성질. 자바 `PriorityQueue`에는 없다.
- **역전 쌍(inversion)**: 같은 우선순위인데 늦게 온 사람이 먼저 불린 두 사람의 쌍. 안정성 깨짐의 측정 단위.
- **힙(heap)**: `PriorityQueue`의 내부 구조. 꺼낼 때 마지막 원소를 뿌리로 올리는 과정에서 같은 값끼리의 순서가 섞인다.
- **비교자(comparator)**: 누가 먼저인지 정하는 함수. "실효 우선순위 → 발권 순서" 2단이 계약이다.
- **단조(monotonic)**: 순서가 한 방향으로만 가는 성질. 추월 횟수가 발권 순서에 단조라서 하한 없이도 지금은 결과가 같다.
- **멱등 없는 확인-후-행동 틈(check-then-act)**: "있나 확인" 후 "부르기" 사이에 상태가 바뀌는 문제. 빈 큐를 null로 처리해 한 호출로 합친 이유.
