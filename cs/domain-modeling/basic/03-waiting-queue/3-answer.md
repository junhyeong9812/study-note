### A. 과제

#### 0. 한 문장이 안 말해주는 것

```text
 안 말해준 것                    코드에서의 자리
 "얼마나 밀려도 되는가"        →  agingThreshold (노화 기준)
 "같은 등급끼리는 누가 먼저"    →  stableOrder (비교자의 2차 기준 = 발권 순서)
 "번호와 부르는 순서는 같은가"  →  Ticket.number (뽑은 순서) vs 호출 순서 (우선순위)
 "아무도 없을 때 무엇을 주나"   →  null (예외가 아니라)
```

- 굶주림(starvation): **우선순위가 낮은 쪽이 영영 차례가 안 오는 것.** 우대가 끊이지 않으면 먼저 온 일반 손님이 영영 안 불린다.
- 같은 우선순위끼리의 순서: **안 정해준다.** 그리고 자바 `PriorityQueue` 도 안 정해준다 — 안 정하면 구현이 마음대로 정한다.
- "얼마나 밀려도 되는가": **문장 어디에도 없다.** 그래서 `agingThreshold` 라는 값으로 올렸고, 그 값이 곧 "최대 몇 번까지 밀립니다"라는 서비스 약속이 된다.
- 막는 방법: **노화(aging)** — **남에게 추월당한 횟수만큼 우선순위를 조금씩 올려준다.**

#### 1. TODO 1 — effectivePriority

정답 코드 (impl/WaitingQueue.java):

```java
int effectivePriority(int threshold) {
    if (threshold <= 0) {
        return ticket.priority();
    }
    return Math.max(0, ticket.priority() - overtaken / threshold);
}
```

- 식: **`max(0, 우선순위 - 추월횟수 / 기준)`** (작을수록 먼저).
- `threshold <= 0`: **노화 없음** — 원래 우선순위를 그대로 돌려준다(0으로 나누기도 피한다).
- 언제 오르나: **정수 나눗셈이라 기준의 배수마다 한 단계씩** 오른다. 기준이 3이면 추월 3회째에 1단계, 6회째에 2단계.
- 기준 10, 5번 밀림:

```text
 max(0, 1 - 5/10) = max(0, 1 - 0) = 1     아직 안 올랐다
 새로 온 우대     = 0                      → 우대가 먼저
```

- 하한이 없으면: 오래 기다린 일반의 실효 우선순위가 **음수**로 내려가 우대(0)보다 **영구히 앞선다** → 이번엔 **우대가 굶는다.**
- 지워도 테스트가 통과하는데 남겨둔 이유: 지금 규칙에서는 **추월 횟수가 발권 순서에 대해 단조**라 같은 등급 안에서 하한이 없어도 결과 순서가 같다(변종 검증에서 확인). 그래도 남긴 것은 **노화 규칙을 "기다린 시간"으로 바꾸면 그 단조성이 깨지고, 그때 이 한 줄이 우대가 굶는 것을 막기 때문**이다.

#### 2. TODO 2 — 생성자

정답 코드:

```java
if (agingThreshold < 0) {
    throw new IllegalArgumentException("노화 기준은 0 이상이다: " + agingThreshold);
}
this.agingThreshold = agingThreshold;
this.stableOrder = stableOrder;
Comparator<Entry> byPriority =
        Comparator.comparingInt(e -> e.effectivePriority(agingThreshold));
this.queue = new PriorityQueue<>(
        stableOrder
                ? byPriority.thenComparingLong(e -> e.ticket.sequence())
                : byPriority);
```

- 1차 기준: **실효 우선순위**(노화 반영).\
  2차 기준: **발권 순서(sequence)**.
- `stableOrder == false`: 2차 기준이 **없다.**\
  같은 실효 우선순위끼리의 순서를 힙 내부 구조가 마음대로 정한다.
- 우선순위만 비교하면 안 되는 이유: **자바 `PriorityQueue` 는 같은 값끼리의 순서를 보장하지 않는다**(문서에 명시, 힙의 성질상 그렇다).\
  그러면 나중에 온 사람이 먼저 불린다.

> **힙(heap)** — "제일 작은 것 하나"만 빨리 꺼내도록 만든 자료구조. 전체를 줄 세우지는 않는다.\
> 예: `[1, 5, 3, 9]` 에서 1을 꺼내는 건 빠르지만, 5와 3 중 누가 앞인지는 애초에 정해두지 않는다.
>
> **안정성(stability)** — 값이 같은 것들끼리 원래 들어온 순서가 유지되는 성질.\
> 예: 같은 일반 손님 셋이면 1번·2번·3번 순으로 나와야 한다. 힙은 이걸 보장하지 않아서 발권 순서를 직접 넣어줘야 한다.

- 노화 기준 음수: **예외**(`IllegalArgumentException`).
- 큐에 들어간 뒤 값이 바뀌면: `PriorityQueue` 는 **넣을 때의 비교 결과로 힙 위치를 잡는다.**\
  `overtaken` 을 그냥 올리면 힙이 이미 어긋난 상태가 되어 순서가 틀어진다.\
  그래서 `call()` 이 **전부 꺼내서 다시 넣는다**(TODO 4 참조).

#### 3. TODO 3 — issue

정답 코드:

```java
Ticket ticket = new Ticket(nextNumber++, priority, sequence++);
queue.add(new Entry(ticket));
return ticket;
```

- `Ticket` 의 세 값: **number**(사람에게 보이는 대기 번호) · **priority**(작을수록 먼저, `PRIORITY=0` / `NORMAL=1`) · **sequence**(전체를 통틀어 증가하는 발권 순서).
- 따로 있는 이유: **번호는 뽑은 순서(사람이 보는 값)고, sequence 는 순서를 가르는 내부 기준**이다. 취소·재발권 같은 일이 생겨도 sequence 는 흔들리지 않는다.
- 우선순위대로 번호를 매기면: **이미 1번을 들고 있는 사람이 있는데 나중에 온 우대가 1번을 받는다.**
- 우대가 나중에 와도: 번호는 **뽑은 순서 그대로 2번**이다. 다만 **부를 때는 2번이 먼저** 불린다(테스트가 그렇게 못 박았다).

#### 4. TODO 4 — call

정답 코드:

```java
Entry next = queue.poll();
if (next == null) {
    return null;
}
if (agingThreshold > 0) {
    List<Entry> rest = new ArrayList<>(queue);
    queue.clear();
    for (Entry e : rest) {
        if (e.ticket.sequence() < next.ticket.sequence()) {
            e.overtaken++;
        }
        queue.add(e);
    }
}
return next.ticket;
```

- null 인 이유: 예외로 하면 **"지금 손님이 있나"와 "부르기"가 두 단계**가 되고 그 사이가 벌어진다.\
  그 틈에 다른 창구가 부르면 예외가 난다.\
  null 이면 **한 번의 호출로 판단**할 수 있다.

> **확인하고 행동하기(check-then-act)** — "있는지 본다"와 "가져간다"를 두 번에 나눠서 하는 것.\
> 예: `if (대기자 있나) 부른다` 는 두 줄 사이에 다른 창구가 끼어들 수 있다. 한 번에 꺼내고 결과가 null 인지 보면 그 틈이 없다.

- 올리는 대상: **`e.sequence < 불린 사람의 sequence`**\
  즉 **불린 사람보다 먼저 온 사람만** 추월당한 것이다.
- 전부 올리면: **줄이 도는 것만으로 우선순위가 사라진다.**\
  아래 예에서 B는 추월당한 적이 없는데, 한 번 만에 우대와 같아져 우대보다 먼저 불린다.

```text
 노화 기준 1
   일반 A(1번), 일반 B(2번) 발권
   call → A        A 는 B 보다 먼저 왔다 → B 는 추월당한 게 아니다
   우대 P(3번) 발권
   call → P        맞는 답

 만약 남은 사람 전부의 나이를 올렸다면
   call → A 때 B 의 overtaken = 1 → eff = max(0, 1-1/1) = 0
   call → B (P 보다 sequence 가 작다)    ← 우대가 밀린다
```

- "밀렸다"의 정의: **나중에 온 사람에게 추월당했다**는 뜻이지, **그냥 시간이 지났다**는 뜻이 아니다.
- 비우고 다시 넣는 이유: `PriorityQueue` 의 힙 위치는 **넣을 때의 비교 결과**로 잡힌다. `overtaken` 을 바꾸면 비교 결과가 바뀌는데 힙은 그걸 모른다 — **전부 꺼내서 다시 넣어야 힙이 새 값으로 다시 정렬된다.**
- 필드만 바꾸면: 힙이 옛 순서를 유지한 채로 남아 **노화가 반영 안 되거나 엉뚱한 순서로 나온다**(조용한 결함 — 예외가 안 난다).
- `agingThreshold == 0` 이면 건너뛰어도 되는 이유: `effectivePriority` 가 **`overtaken` 을 아예 안 본다.** 세어봤자 순서에 영향이 없으므로 O(n) 재삽입을 낭비할 필요가 없다.

### B. 개념

#### 5. 측정 — PriorityQueue 는 안정적이지 않다

- 40명씩 200회, 발권 순서 없음: **역전 104,175쌍**, **200/200 회**에서 발생.
- 발권 순서를 넣으면: **0쌍**.
- 크기별 역전 발생 시행(각 200회):

```text
  n= 2     0 / 200
  n= 3   177 / 200
  n= 4   196 / 200
  n= 5   199 / 200
  n= 8   200 / 200
  n=40   200 / 200
```

- 두 명일 때만 안 걸리는 이유 — 힙의 poll:

```text
 같은 우선순위 [a, b, c]
   poll → a 를 꺼내고 마지막 c 를 뿌리로 올린다   [c, b]
          c 와 b 를 비교하면 같으므로 안 내린다
   poll → c
   poll → b
   결과  a, c, b        b 와 c 가 뒤집혔다

 두 명 [a, b]
   poll → a 를 꺼내고 마지막 b 를 뿌리로     [b]
          옮길 것이 없다 → 순서 유지
```

- 무서운 이유: **"테스트가 통과했다"와 "맞다" 사이의 거리가 한 명이다.** 손으로 쓰는 테스트는 두 명짜리가 되기 쉽고, 그건 이 결함이 절대 안 걸리는 유일한 크기다.
- 현장에서의 모습: **"가끔 순서가 이상하다"** 는 신고. 재현이 안 되니 못 고치고, 재현하려면 이 측정처럼 **세어야** 한다.

#### 6. 측정 — 노화 기준은 서비스 약속

```text
 노화 기준   일반 손님이 불린 순번
   없음           51 번째    (우대 50 명이 다 지나간 뒤)
    3              4 번째
    5              6 번째
   10             11 번째
                  정확히 기준 + 1
```

- 기준 + 1 이 나오는 이유: 한 번 불릴 때마다 추월 1회가 쌓이므로 **t번 추월당하면 `1 - t/t = 0`** 이 되어 우대와 같아진다. 같아지면 **발권 순서가 이기고**, 일반이 제일 먼저 왔으므로 **그다음 호출(t+1번째)에 불린다.**
- "서비스 약속"의 뜻: 이 값은 속도를 조절하는 튜닝 상수가 아니라 **"최대 10명까지만 밀립니다"를 코드로 쓴 것**이다. 값을 바꾸면 손님에게 한 약속이 바뀐다.

#### 7. 측정 — 우대 비율

```text
 우대 비율   일반 손님 최대 대기 걸음 (300명 접수, 두 명당 한 명 호출)
   10 %            245
   30 %            316
   50 %            355
```

- 비례하지 않는다는 뜻: 우대를 10%에서 50%로 **5배** 늘렸는데 최대 대기는 245 → 355 로 **1.4배**밖에 안 는다. 거꾸로 말하면 **10퍼센트만 우대해도 이미 245걸음**이다 — "조금만 우대하니까 영향도 조금"이 아니다.
- 우대가 절반이면: 절반이 "먼저"인데 그건 **먼저가 아니다** — "우대"라는 말이 변별력을 잃는다. 그런데도 최대 대기는 계속 는다.

#### 8. 변종 검증에서 남은 것

- 하한을 지워도 통과하는 이유: **추월 횟수가 발권 순서에 대해 단조**이기 때문이다.\
  하한을 안 걸어도 같은 등급 안의 상대 순서가 안 바뀐다(음수로 같이 내려가도 순위는 그대로다).

> **단조(monotone)** — 한 값이 커질 때 다른 값이 절대 반대로 움직이지 않는 관계.\
> 예: 여기서는 "먼저 온 사람일수록 추월당한 횟수가 항상 크거나 같다". 이 관계가 깨지지 않는 한, 값을 똑같이 깎아도 순위는 안 뒤집힌다.

- "기다린 시간"으로 바꾸면: 추월과 무관하게 시간만 흘러도 값이 내려간다.\
  그러면 **먼저 온 사람이 반드시 더 많이 내려가는 관계가 깨진다.**\
  그때는 하한이 없으면 오래 기다린 일반이 우대를 영구히 앞질러 **우대가 굶는다.**
- 테스트가 안 잡는 코드를 남기는 판단이 옳은 경우: **곧 바뀔 것이 예상되는 규칙의 안전장치**이고, **왜 남기는지가 문서로 남아 있을 때.** 이 코드는 javadoc과 README에 "지금은 결함이 아니다 / 그래도 남겨뒀다"를 명시했다 — 근거 없이 남은 죽은 코드와 다른 점이 그것이다.

- 노화 기준 공개: 알리면 **약속이 되어 지켜야 한다**(그리고 손님이 "10번 밀렸는데 왜 아직이냐"를 셀 수 있게 된다). 안 알리면 운영이 자유롭지만, 밀린 손님은 **언제 불릴지 모르는 상태**를 견뎌야 한다 — 대기 시간 안내가 불만을 줄이는 것과 같은 거래다. (원본에 답 없음 — 내 추론)

#### 10. 연결

- 말이 안 정해준 자리: 01번은 `FeePolicy` record, 02번은 `respectAisle`·`Preference`, 03번은 **`agingThreshold`·`stableOrder`** — 셋 다 **생성자/파라미터로 올려서 두 해석을 같은 코드로 돌린다.**
- OS 개념과의 대응: **굶주림과 노화는 프로세스 스케줄러의 그것과 같은 것**이다. 우선순위 스케줄링이 낮은 우선순위 프로세스를 굶기는 문제를, 대기 시간에 비례해 우선순위를 올리는 aging 으로 막는다.
- 안정 정렬과의 공통점: **같은 키를 가진 원소들의 원래 순서를 보존하느냐**가 똑같은 쟁점이다. 여기서는 "같은 우선순위끼리 발권 순서 유지" — 비교자에 2차 키(발권 순서)를 넣는 것이 곧 **정렬을 안정적으로 만드는 표준 수법**이다.
