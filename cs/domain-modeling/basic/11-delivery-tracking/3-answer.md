### A. 과제 (Tracking 의 TODO 1~5)

#### 0. 챕터 지문 — 요구사항 전문

- Q: 지문에 "정답 규칙"이 안 적혀 있는데 무엇을 근거로 스캔 순서를 고르는가?\
  A: **손님이 보는 사실**이 근거다.\
  지문의 마지막 줄 — "손님은 이미 물건을 받았는데 화면에는 집화라고 나온다" — 이 한 문장이 판정 기준이다.\
  물건이 도착했다는 것은 현장에서 실제로 일어난 사건이고, 그 사건의 시각은 **스캔 시각**에 적혀 있다.\
  수신 시각은 우리 파이프라인 사정이지 물건의 사정이 아니다.\
  그래서 상태는 스캔 시각으로 판정한다.

- Q: "시각이 둘이다"라는 한 줄에 안 들어 있는 결정은?\
  A: 최소 여섯 개다.\
  ① 중복 키에 어느 시각을 넣는가 ② "현재"를 어느 시각 기준으로 고르는가 ③ 스캔 시각이 **같을 때** 누가 이기는가 ④ 이력 화면은 어느 순서인가 ⑤ 되돌아감을 버릴 것인가 셀 것인가 ⑥ 빠진 단계와 아직 안 온 단계의 경계선은 어디인가.\
  요구사항 한 줄은 문제를 가리킬 뿐이고, 코드는 이 여섯 개를 전부 정해야만 돌아간다.\
  **모델링은 안 적힌 결정을 찾아내는 일이다.**

- Q: 이 사고가 개발 환경에서 안 보이는 이유는?\
  A: **지연이 0이면 세 규칙이 완전히 같은 답을 내기 때문**이다(README 측정 1·5).\
  개발 환경에서는 이벤트를 순서대로 넣고, 넣자마자 받는다 → 스캔 순서 = 수신 순서.\
  측정표에서 지연 0 %일 때 갈림은 **0 / 1,000**. 즉 틀린 규칙과 맞는 규칙이 1,000번 다 같은 답을 낸다.\
  운영에서 터미널 하나가 늦게 올려주기 시작하는 순간 갈리기 시작하는데, **우리 코드는 바뀐 게 없어서** 원인을 찾기 어렵다.

#### 1. TODO 1 — dedupe

- Q: "같은 이벤트"의 키는?\
  A: **단계 + 스캔 시각**. impl 은 문자열로 이어 붙인다.
  ```java
  if (seen.add(event.stage() + "@" + event.scannedAt())) { kept.add(event); }
  ```
  `LinkedHashSet.add` 가 false 를 주면 이미 본 키 → 버린다.\
  수신 시각은 키에 **없다**.

> **중복 제거 키(dedupe key)** — "무엇이 같으면 같은 것으로 볼까"를 정하는 값들의 조합.\
> 예: 단계+스캔 시각을 키로 잡으면 같은 스캔이 두 번 올라와도 한 건으로 세고, 수신 시각까지 넣으면 전부 다른 건이 된다.

> **재전송(retransmission)** — 보낸 쪽이 응답을 못 받아 같은 내용을 다시 올리는 것.\
> 예: 스캔 시각은 그대로인데 수신 시각만 다른 이벤트가 두 건 들어온다.

- Q: 키에 수신 시각을 넣으면 재전송은?\
  A: **전부 다른 이벤트가 된다.**\
  재전송의 정의가 "스캔 시각은 같고 수신 시각만 다르다"이기 때문이다.
  ```text
  집화 스캔10 수신12  ┐ 키 = PICKED_UP@10        → 1건 (정답)
  집화 스캔10 수신30  ┘ 키 = PICKED_UP@10+12 / +30 → 2건 (틀림)
  ```
  중복 제거 함수가 아무것도 안 거르는 함수가 된다.\
  그리고 **에러 없이 조용히** 그렇게 된다.

- Q: 제거 결과 수가 왜 2,000 이 안 되는가?\
  A: 원본 이벤트가 2,000건인 데이터에 중복을 섞은 것이므로, 키가 맞으면 제거 후는 반드시 2,000이다.\
  수신 시각을 키에 넣으면 재전송분이 안 지워지므로 제거 후가 2,364(20 % 섞음)·2,997(50 % 섞음) 쪽에 가깝게 남는다 — 즉 **전체 건수와 같아진다**.

- Q: 같은 단계가 다른 시각에 두 번이면?\
  A: **다른 이벤트다.**\
  README 함정 2번: "재분류로 간선 상차가 두 번 찍힌다."\
  실제로 두 번 일어난 사건이므로 지우면 이력에서 사실이 사라진다.\
  테스트: 간선상차(스캔60) + 간선상차(스캔120) → dedupe 후 **2건**.

- Q: 중복 중 어느 것을 남기는가?\
  A: **먼저 온 것**(목록에서 앞에 있는 것)을 남긴다 — `seen.add` 가 처음 성공한 그 건만 `kept` 에 담기기 때문이다.\
  영향: 남는 건의 **수신 시각**이 달라진다.\
  스캔 시각과 단계는 어차피 같으므로 current·history 결과는 안 변하고, 수신 시각을 쓰는 쪽(진단·지연 계산)만 영향을 받는다.

- Q: 남긴 목록의 순서는?\
  A: **입력 순서 그대로**다(`LinkedHashSet` + `ArrayList` 로 삽입 순서 보존).\
  이게 중요한 이유: 입력이 수신 순서로 들어온다는 전제 아래, TODO 2 의 `LAST_RECEIVED`(마지막 원소)와 TODO 4 의 `backwardSteps`(이웃 비교)가 **이 순서를 그대로 믿고 쓴다.**\
  정렬해버리면 그 둘의 의미가 통째로 바뀐다.

> **삽입 순서 보존(insertion order)** — 넣은 순서를 그대로 기억하는 자료구조의 성질.\
> 예: `LinkedHashSet` 은 중복은 걸러내면서도 "먼저 들어온 것이 먼저"라는 순서를 지켜준다.

#### 2. TODO 2 — current

- Q: 세 규칙은 각각 무엇의 최대값인가?\
  A:
  ```java
  case LAST_RECEIVED  -> deduped.get(deduped.size() - 1);          // 목록의 마지막
  case LATEST_SCAN    -> deduped.stream().max(byScanThenStage());  // 스캔 시각 최대
  case FURTHEST_STAGE -> deduped.stream().max(byStageThenScan());  // 단계 ordinal 최대
  ```

- Q: 배달완료(스캔120·수신125) + 집화(스캔30·수신180) 의 답은?\
  A: 손계산.
  ```text
  입력 목록(수신 순서): [배달완료(스캔120), 집화(스캔30)]

  LAST_RECEIVED  : 목록 마지막         = 집화      ← 틀린 화면
  LATEST_SCAN    : max(120, 30) = 120  = 배달완료
  FURTHEST_STAGE : max(ordinal 3, 0)=3 = 배달완료
  ```
  이것이 TrackingTest 의 `lateArrivalBreaksReceiveOrder` 가 못 박은 계약이다.

- Q: 틀린 규칙을 왜 안 지웠는가?\
  A: **재려고 남겼다.**\
  셋을 같은 데이터에 돌려야 "언제 갈리는가"를 측정할 수 있다.\
  지우면 "지연 0 %에서는 셋이 똑같다"는 사실 자체를 관측할 방법이 없어진다.\
  틀린 규칙을 삭제하는 대신 **나란히 놓고 비교하는 것**이 이 챕터의 학습 장치다.

- Q: LAST_RECEIVED 는 무엇을 고르는가?\
  A: 정렬 없이 **목록의 마지막 원소**다.\
  즉 "입력 목록이 이미 수신 순서로 정렬돼 있다"는 **말 안 한 전제**에 기대고 있다.\
  전제가 깨지면(예: DB 가 임의 순서로 돌려주면) 이 규칙은 틀린 것도 아니고 무의미한 것이 된다.\
  (원본에 명시 없음 — impl 코드에서 읽어낸 것)

- Q: 0건일 때 Optional.empty() 인 이유는?\
  A: **아직 아무 스캔도 안 된 송장은 흔하기 때문**이다(javadoc 원문: "예외가 아니다").\
  흔히 일어나는 정상 상태를 예외로 만들면 호출하는 쪽이 try-catch 로 정상 흐름을 처리하게 된다.\
  Optional 은 "값이 없을 수 있다"를 **타입으로** 알려서 호출자가 빈 경우를 강제로 생각하게 한다.

> **Optional(값이 없을 수 있는 상자)** — 값이 있을 수도 없을 수도 있다는 사실을 타입에 적어두는 자바 도구.\
> 예: 아직 스캔이 하나도 없는 송장은 예외가 아니라 "빈 상자"를 돌려주고, 받는 쪽이 빈 경우를 반드시 처리하게 만든다.

- Q: dedupe 를 먼저 안 부르면?\
  A: `LAST_RECEIVED` 가 달라진다 — 재전송된 늦은 사본이 목록 맨 뒤에 붙어 있으면 그게 "현재"가 된다.\
  `LATEST_SCAN` · `FURTHEST_STAGE` 는 최대값이라 중복이 있어도 답은 같다(단계·스캔이 같은 건이니까).\
  그리고 `backwardSteps` 는 중복이 이웃 비교를 늘려 **수가 부풀어 오른다.**

#### 3. TODO 2 딸림 — 스캔 시각 동점

- Q: 같은 스캔 시각이 실제로 생기는 이유는?\
  A: **기기가 분 단위로만 기록하기 때문**이다(테스트 javadoc 원문). 배달출발과 배달완료가 같은 분에 찍히는 일이 실제로 있다.

- Q: 동점 순서를 안 정하면?\
  A: **결과가 목록 순서에 달라진다** → 같은 데이터를 두 번 조회했을 때 다른 답이 나온다.
  ```text
  목록 [배달출발(100), 배달완료(100)] → max 가 뒤엣것? 앞엣것? → 구현 나름
  목록 [배달완료(100), 배달출발(100)] → 답이 뒤집힐 수 있다
  ```
  테스트는 목록을 뒤집어 두 번 호출하고 **둘 다 배달완료**를 요구한다(`tieBrokenByStage`).\
  이게 결정론의 계약이다.

> **결정론(determinism)** — 같은 입력이면 몇 번을 돌려도 똑같은 답이 나오는 성질.\
> 예: 목록 순서가 뒤바뀌어도 같은 답이 나와야, 같은 송장을 두 번 조회한 손님이 다른 화면을 보지 않는다.

- Q: "뒤 단계가 이긴다"의 근거는?\
  A: 같은 시각에 두 단계가 찍혔다면 그 사이에 **실제로 진행이 일어난 것**이고, 나중 일이 곧 뒤 단계다.\
  배달출발과 배달완료가 같은 분에 찍혔다면 손님은 물건을 받았다 — 화면에 "배달출발"을 띄우면 안 된다.\
  앞 단계를 이기게 하면 지연 화면 사고(이 챕터의 원죄)를 동점 구간에서 다시 만드는 셈이다.

- Q: byStageThenScan 이 반대로 뒤집힌 이유는?\
  A: 규칙이 다르기 때문이다.\
  FURTHEST_STAGE 는 **단계가 1차 기준**이고 스캔 시각은 동점 처리용 2차 기준이다.
  ```java
  byScanThenStage : 스캔시각 → (동점) 단계 ordinal    // LATEST_SCAN·history 용
  byStageThenScan : 단계 ordinal → (동점) 스캔시각    // FURTHEST_STAGE 용
  ```
  1·2차를 뒤집으면 규칙 자체가 바뀐다 — 두 비교자는 "정렬 취향"이 아니라 **두 개의 서로 다른 도메인 규칙**이다.

> **1차·2차 정렬 기준(primary / secondary key)** — 먼저 비교하는 기준과, 그게 같을 때만 보는 기준.\
> 예: "스캔 시각 먼저, 같으면 단계"와 "단계 먼저, 같으면 스캔 시각"은 글자만 바뀐 게 아니라 아예 다른 규칙이다.

- Q: ordinal 로 단계 순서를 쓰면 무엇이 깨지기 쉬운가?\
  A: **enum 선언 순서를 바꾸면 도메인 규칙이 조용히 바뀐다.**\
  테스트 javadoc 원문: "enum 의 선언 순서가 곧 도메인 순서다.\
  그래서 선언 순서를 바꾸면 규칙이 바뀐다.\
  그 사실을 알고 있어야 한다."\
  중간에 새 단계(예: 반송)를 알파벳 순으로 끼워 넣거나 정렬하면 컴파일은 되고 테스트는 조용히 틀린다.

> **ordinal(선언 순서 번호)** — enum 을 적은 순서대로 0, 1, 2 … 로 자동으로 붙는 번호.\
> 예: 집화 0 · 간선상차 1 · 배달출발 2 · 배달완료 3 이라서 "번호가 크면 뒤 단계"가 성립하고, 선언 순서를 건드리면 그 규칙이 통째로 바뀐다.

#### 4. TODO 3 — history

- Q: 수신 순서로 보여주면?\
  A: 화면에 **"배달 완료" 다음에 "집화"** 가 나온다.\
  손님이 보기에 말이 안 되는 화면이다.

- Q: history 와 current(LATEST_SCAN) 를 왜 따로 두는가?\
  A: 쓰임이 다르다.\
  current 는 **하나**(최대값)를 뽑고 history 는 **전부**를 순서대로 준다.\
  같은 비교자를 공유하는 것은 오히려 계약이다 — 화면의 마지막 줄과 "현재 상태"가 **반드시 일치**하게 만든다.\
  비교자가 갈라지면 "이력 마지막은 배달완료인데 현재 상태는 다른 것"인 화면이 나온다.

- Q: 정렬 전 복사하는 이유는?\
  A: `List.of(...)` 같은 **불변 목록이 들어오면 sort 가 예외를 던지고**, 가변 목록이면 **호출자의 목록을 몰래 뒤집어 놓기** 때문이다.
  ```java
  List<ScanEvent> sorted = new ArrayList<>(dedupe(events));  // 새 목록에 담고
  sorted.sort(byScanThenStage());                            // 그걸 정렬
  ```
  조회 함수가 입력을 바꾸면 안 된다.

#### 5. TODO 4 — backwardSteps

- Q: 왜 수신 순서로 세는가?\
  A: 재려는 대상이 **"우리 파이프라인이 얼마나 어긋나 있나"**이기 때문이다.\
  스캔 순서로 세면(반송이 없는 한) 언제나 0이 나온다 — 스캔 순서는 정의상 진행 순서니까.\
  즉 아무것도 재지 않는 지표가 된다.\
  되돌아감은 **도착이 어긋났을 때만** 보이는 현상이고, 그래서 도착 순서로 세야 한다.

- Q: 배달완료(수125) → 집화(수180) → 간선상차(수190) 은?\
  A: **1회**다.\
  이웃끼리만 센다.
  ```text
  쌍1: 배달완료(3) → 집화(0)      앞이 뒤 단계 → 되돌아감 1
  쌍2: 집화(0)     → 간선상차(1)  앞이 앞 단계 → 0
                                       합계 1
  ```
  2회가 아닌 이유: 최고 단계와의 비교가 아니라 `deduped.get(i-1).isLaterStageThan(deduped.get(i))` 인 **연속 쌍 비교**이기 때문이다.\
  집화→간선상차는 정상 전진이므로 안 센다.\
  (TrackingTest `backwardSteps` 가 이 값을 1로 못 박아 뒀다.)

- Q: 그럼 잘못은 무엇인가?\
  A: **되돌아감을 그대로 상태로 쓰는 것**이다(javadoc 원문).\
  이벤트가 늦게 오는 것은 물류의 사실이고 막을 수 없다.\
  막을 수 있는 것은 그 도착 순서를 "현재 상태"로 삼는 우리 코드다.

- Q: 이 수가 올라가면?\
  A: 이벤트 파이프라인의 **지연이 커지고 있다**는 신호다.\
  README 측정: 지연 0 %→238회(10 %)→576회(30 %)→794회(50 %) 로 지연 비율과 같이 올라간다.\
  그래서 이 수는 알람용 지표로 쓸 수 있다 — 상태 판정에는 못 쓰지만 버리면 안 되는 수.

> **되돌아감(backward step)** — 도착 순서로 늘어놓았을 때 앞 이벤트가 뒤 이벤트보다 더 진행된 단계인 자리.\
> 예: 배달완료가 먼저 도착하고 집화가 나중에 도착하면, 그 이웃 한 쌍이 되돌아감 1회로 세어진다.

### B. 개념

#### 7. 두 시각과 지연

- Q: 지연 0 %에서 0/1,000 이 뜻하는 것은?\
  A: **틀린 규칙과 맞는 규칙이 구별 불가능하다**는 뜻이다.\
  지연이 없으면 스캔 순서 = 수신 순서이므로 두 규칙이 정의상 같아진다.\
  그래서 "테스트 다 통과"가 이 버그에 대해 아무 보증도 못 한다.

- Q: 지연별 갈린 건수는?\
  A: README 측정표 그대로.

  | 지연 비율 | 수신순/스캔순 갈림 | 되돌아간 횟수 |
  |---|---|---|
  | 0 % | 0 / 1,000 | 0 |
  | 10 % | 150 / 1,000 | 238 |
  | 30 % | 320 / 1,000 | 576 |
  | 50 % | 395 / 1,000 | 794 |
  지연 10 %만 돼도 **1,000건 중 150건**이 다른 답을 낸다.

- Q: "아직 안 왔다"로 보인 완료 송장은?\
  A: **338건 / 1,000건 = 33.8 %.** 1,000건 전부 네 단계를 다 거쳐 배달 완료된 데이터인데도 그렇다.

- Q: "데이터는 멀쩡하다"의 뜻은?\
  A: 이벤트는 전부 도착했고 내용도 정확하다.\
  틀린 것은 **저장된 것을 읽어 상태로 바꾸는 규칙** 하나다.\
  그래서 고치는 곳도 파이프라인이나 택배사가 아니라 우리 조회 코드 한 군데다.

- Q: 코드가 안 바뀌었는데 사고가 나는 이유는?\
  A: 입력의 성질(지연 비율)이 바뀌었기 때문이다.\
  지방 터미널 하나가 늦게 올려주기 시작하면 그날부터 갈리기 시작한다.\
  배포 이력을 뒤져도 원인이 안 나오는 종류의 사고다 — README 원문: "우리 코드가 바뀐 것이 아니라서 원인을 찾기 어렵다."

#### 8. 안 갈렸다고 같은 규칙은 아니다

- Q: 스캔 순서와 최선 단계는 몇 번 갈렸는가?\
  A: **한 번도 안 갈렸다**(1,000건 중 0건).

- Q: 그런데도 다른 규칙인 근거는?\
  A: **갈리는 입력을 만들 수 있기 때문**이다.\
  README 원문: "갈리는 입력을 만들 수 있으면 다른 규칙이다.\
  1,000 번 같았던 것은 데이터가 얌전해서다."\
  같은 답을 낸 횟수는 규칙의 동일성에 대한 증거가 아니라 **데이터 분포에 대한 증거**일 뿐이다.

- Q: 갈리는 입력 하나는?\
  A: 반송.
  ```text
  배달완료 100분 스캔
  간선상차 200분 스캔   (반송으로 다시 트럭에 실림)

    스캔 순서(LATEST_SCAN)  → 간선상차   (시각이 늦으니까)
    최선 단계(FURTHEST)     → 배달완료   (단계가 앞이니까)
  ```
  TrackingTest `furthestStageNeverGoesBack` 이 바로 이 입력으로 두 규칙을 갈라 놓았다.

- Q: 지연 0 데이터로만 만든 테스트는 무엇을 지키는가?\
  A: **아무것도 안 지킨다.**\
  세 규칙이 다 통과하므로 규칙을 잘못 골라도 초록불이다.\
  README 원문: "테스트도 대개 이벤트를 순서대로 넣어 만든다.\
  … 그 조건을 안 만들면 통과하는 테스트는 아무것도 안 지킨다."

- Q: "언제 갈라지나"를 먼저 물어야 하는 이유는?\
  A: 테스트는 **갈라지는 지점에서만** 정보를 준다.\
  안 갈라지는 입력에서의 통과는 구현을 구별하지 못한다.\
  그래서 테스트 설계의 첫 질문은 "무엇을 넣지"가 아니라 **"무엇을 넣어야 틀린 구현이 빨개지나"**다.

#### 9. 중복 키가 맞다는 증거

- Q: 중복 비율별 수는?\
  A:

  | 중복 비율 | 전체 | 제거 후 |
  |---|---|---|
  | 0 % | 2,000 | 2,000 |
  | 20 % | 2,364 | **2,000** |
  | 50 % | 2,997 | **2,000** |

- Q: 왜 증거가 되는가?\
  A: 원본 이벤트가 2,000건이라는 것을 알고 있으므로, **섞은 양과 무관하게 항상 2,000으로 복원된다**는 것은 키가 재전송분만 정확히 지운다는 뜻이다.\
  더 지웠으면 2,000 미만, 덜 지웠으면 2,000 초과가 나온다.\
  2,000 은 양쪽 오류를 동시에 배제한다.

- Q: 키가 틀렸다면 어느 칸이 어긋나는가?\
  A: 오른쪽 "제거 후" 칸.

  - 수신 시각을 **넣으면**(과소 제거): 2,364·2,997 쪽으로 커진다.
  - 스캔 시각을 **빼고 단계만** 쓰면(과다 제거): 단계 4종뿐이므로 송장당 4건까지 줄어든다 — 재분류로 두 번 찍힌 간선상차가 사라진다.

#### 10. 생각해볼 것

- Q: 반송을 다루려면?\
  A: **되돌아감을 표현하는 단계(또는 이벤트 종류)가 따로 필요하다.**\
  테스트 javadoc 원문: "반송을 다루려면 되돌아감을 표현하는 다른 단계가 필요하다."\
  지금 모델은 단계가 4개의 일렬 진행이고, 그 안에는 "뒤로 갔다"를 담을 자리가 없다.

- Q: 반송이 있으면 최선 단계 규칙을 왜 못 쓰나?\
  A: 최선 단계는 정의상 **절대 내려가지 않기** 때문이다.\
  반송으로 물건이 창고로 돌아가도 화면은 영원히 "배달완료"다.\
  "되돌아가지 않는다"는 이 챕터에서 **규칙이지 사실이 아니다**(테스트 javadoc 원문) — 반송이 들어오는 순간 규칙이 사실과 어긋난다.

- Q: 스캔 시각이 미래로 찍혀 오면?\
  A: (원본 README는 질문만 던지고 답을 안 준다 — 이하 내 추론)\
  현재 계약은 `receivedAt < scannedAt` 만 거부하므로, 스캔·수신이 **둘 다** 미래면 통과한다.\
  그리고 그 이벤트는 스캔 시각 최대값이라 영원히 "현재 상태"를 점령한다.\
  대응 선택지: ①수신 시각 기준 허용 오차(예: +5분) 밖이면 거부 ②받되 의심 표시를 달고 상태 판정에서 제외 ③기기 시계 오차를 추정해 보정.\
  핵심은 **하나를 정하는 것**이다 — 안 정하면 시계 어긋난 기기 하나가 그 구역 전체 화면을 망친다.

- Q: 되돌아간 횟수를 어디에 알리나?\
  A: (원본에 답 없음 — 내 추론) 손님 화면에는 안 보낸다.\
  손님에게는 이미 정리된 스캔 순서 이력만 보여주면 된다.\
  보낼 곳은 **내부 모니터링**이다 — 집계해서 대시보드·알람으로.

- Q: 우리 지표인가 택배사 지표인가?\
  A: **둘 다인데 뜻이 다르다.**\
  우리 쪽: 우리가 이벤트를 받아 처리하는 파이프라인이 어긋난 정도.\
  택배사 쪽: 특정 터미널이 스캔을 늦게 올리는 정도.\
  그래서 유용하게 쓰려면 송장 단위 총합이 아니라 **터미널·구역별로 쪼개서** 봐야 한다 — 그래야 "어느 터미널이 범인인가"가 나온다.

- Q: 이벤트가 영영 안 오면?\
  A: (원본에 답 없음 — 내 추론) **없는 이벤트는 스스로 알리지 않는다.**\
  지금 모델은 도착한 이벤트만 보므로 침묵을 감지할 수 없다.\
  감지하려면 시간을 보는 쪽이 필요하다 — "마지막 스캔 이후 경과 시간"을 주기적으로 재는 것.

- Q: "언제까지 안 오면 이상하다"를 무엇으로 정하나?\
  A: (내 추론) 고정 상수보다 **단계별 실측 분포**가 낫다.\
  집화→간선상차는 보통 몇 시간, 배달출발→배달완료는 보통 몇 십 분처럼 단계마다 정상 간격이 다르다.\
  그래서 기준도 단계별로, 예컨대 그 단계 소요 시간의 상위 백분위(p99)를 넘으면 이상으로 본다.\
  주의: 이 기준선은 `missingStages` 와 다른 질문에 답한다 — missingStages 는 "지나간 단계 중 빈 것", 이쪽은 "다음 단계가 안 오는 것"이다.

#### 11. 연결

- Q: 시각이 둘인 구조는 어디와 같은 자리인가?\
  A: 로그·스트림 처리의 **event time vs processing time** 과 정확히 같다.\
  스캔 시각 = 사건이 일어난 시각(event time), 수신 시각 = 우리가 처리한 시각(processing time).\
  거기서도 결론이 같다 — 집계는 event time 으로 하고, processing time 은 지연 진단에 쓴다.

> **event time / processing time** — 사건이 실제로 일어난 시각과, 우리 시스템이 그걸 받아 처리한 시각.\
> 예: 스캔은 10시에 찍혔는데 서버에는 12시에 들어왔다면 event time 은 10시, processing time 은 12시다.

- Q: ScanEvent 생성자 검증은 누구 책임인가?\
  A: **도메인 모델(값 객체) 자신**이다.\
  record 생성자에서 막으면 "수신이 스캔보다 빠른 ScanEvent 는 이 프로그램 안에 존재할 수 없다"가 보장된다.\
  이걸 서비스 계층 if 문으로 옮기면 검증을 안 거친 생성 경로가 반드시 하나 생긴다.\
  **불변식은 만들어지는 자리에서 막는 것이 가장 싸다.**

> **값 객체(value object)** — 식별자 없이 값 자체로 의미가 정해지는 작은 타입.\
> 예: `ScanEvent` 생성자에서 "수신이 스캔보다 빠를 수 없다"를 막으면, 프로그램 안에 그런 이벤트가 아예 존재할 수 없게 된다.

- Q: 09-order-state 의 상태 전이와 FURTHEST_STAGE 는?\
  A: 같은 점 — 둘 다 "뒤로 못 간다"는 단조 진행 규칙이다.\
  다른 점 — 주문 상태는 우리가 **직접 전이를 실행**하므로 순서를 강제할 수 있지만, 배송 단계는 남이 찍은 이벤트를 **사후에 해석**할 뿐이라 강제할 수 없다.\
  그래서 여기서는 "뒤로 못 간다"가 검증이 아니라 **해석 규칙**이고, 반송처럼 사실이 규칙을 배반하면 규칙 쪽이 진다.

> **단조 진행(monotonic)** — 한 방향으로만 가고 절대 되돌아오지 않는 성질.\
> 예: 최선 단계 규칙은 단조라서 한 번 배달완료가 되면 반송이 와도 화면이 영원히 배달완료로 남는다.
