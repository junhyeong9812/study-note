**배송 추적 = 친구들이 보낸 카톡이 뒤죽박죽 도착하는 문제.**

- 손님은 이미 물건을 받았는데 화면에는 "집화"라고 나오는 사고가 바로 이것이다.

> **집화** — 택배 기사가 물건을 처음 걷어가는 단계.\
> 예: 배송의 출발점이라, 화면에 집화가 떠 있으면 손님은 "아직 안 왔구나"로 읽는다.

```text
  집화     09:30 스캔 ──(터미널이 늦게 올림)──> 12:00 수신
  배달완료 11:00 스캔 ──(바로 올림)──────────> 11:05 수신

  수신 순서로 보면: 배달완료 → 집화   → 현재 상태 "집화" (틀림!)
  스캔 순서로 보면: 집화 → 배달완료   → 현재 상태 "배달완료" (맞음)
```

실무 예: 택배 조회 화면, 물류 이벤트 파이프라인, 로그 수집 시스템 — "일어난 시각"과 "도착한 시각"이 다른 모든 곳.

## 문제 — 이 챕터가 시키는 것

원본 README가 말로 못 박은 요구사항은 이것뿐이다.

> "시각이 둘이다. **스캔한 시각**과 **우리가 받은 시각**."
> "손님은 이미 물건을 받았는데 화면에는 집화라고 나온다."
> "`src/main/java/com/domain/delivery/Tracking.java` 의 TODO 1~5. `ScanEvent` 는 계약이라 다 주어져 있다."

과제 목록 — 채울 TODO 5개:

| TODO | 메서드 | 말로 된 요구 |
|---|---|---|
| 1 | `dedupe(events)` | 같은 단계 + 같은 스캔 시각이면 같은 이벤트로 본다 |
| 2 | `current(events, rule)` | 규칙(수신순/스캔순/최선단계)별 현재 상태. 없으면 `Optional.empty()` |
| 3 | `history(events)` | 손님에게 보여줄 이력 — 스캔 순서로 정렬 |
| 4 | `backwardSteps(events)` | 수신 순서로 볼 때 단계가 뒤로 간 횟수 |
| 5 | `missingStages(events)` | 건너뛴 단계 — 최선 단계보다 앞의 것만 |

테스트가 못 박은 계약:

- 수신 < 스캔인 `ScanEvent` 는 생성 자체가 거부된다(같은 시각은 허용).
- 집화(스캔10·수신12) + 집화(스캔10·수신30) + 간선상차(스캔60) → dedupe 후 **2건**.
- 배달완료(스캔120·수신125) + 집화(스캔30·수신180) → 수신순 "집화", 스캔순 "배달완료", 최선단계 "배달완료".
- 스캔 시각이 같으면(배달출발 100 / 배달완료 100) 목록 순서를 뒤집어도 답이 같아야 한다 — 둘 다 "배달완료".
- 집화 + 배달완료만 있으면 빠진 단계 = `[간선상차, 배달출발]`. 집화만 있으면 빠진 단계 **없음**.
- 빈 목록: dedupe 빈 목록 · current 빈 Optional · history 빈 목록 · backwardSteps 0.

README가 미리 알려준 함정 5가지: ①중복 판정에 수신 시각을 넣지 말 것 ②같은 단계라도 시각이 다르면 다른 이벤트 ③스캔 시각 동점의 순서를 반드시 정할 것 ④이력은 스캔 순서 ⑤건너뛴 단계는 최선 단계보다 앞의 것만.

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 규칙 1 — "현재 상태"의 세 가지 기준 (Rule)

**어떤 요구사항인가**: "가장 최근 이벤트가 현재 상태다"는 맞는 말인데, **"최근"이 무엇인지**가 문제다.
세 가지 답이 가능하다.

| Rule | 뜻 | 위 예시(집화 늦게 도착)의 답 |
|---|---|---|
| LAST_RECEIVED | 마지막으로 받은 이벤트 | 집화 (틀린 화면) |
| LATEST_SCAN | 스캔 시각이 가장 늦은 이벤트 | 배달완료 |
| FURTHEST_STAGE | 가장 앞선 단계 (되돌아가지 않음) | 배달완료 |

**예시 입력**: 배달완료(스캔 120분, 수신 125분) + 집화(스캔 30분, 수신 180분).

**규칙 적용**:

```text
LAST_RECEIVED : 목록 마지막 = 수신 180분인 집화        → "집화"
LATEST_SCAN   : max(스캔시각) = 120분인 배달완료       → "배달완료"
FURTHEST_STAGE: max(단계) = 배달완료                   → "배달완료"
```

**왜 이렇게 모델링했나**: 틀린 규칙(LAST_RECEIVED)도 enum에 남겨뒀다 — 셋을 같은 데이터에 돌려서 **언제 갈리는지 측정**하기 위해서다.
규칙을 지우는 대신 나란히 놓고 비교하는 것이 이 챕터의 학습 장치다.

**LATEST_SCAN과 FURTHEST_STAGE는 언제 갈리나**: 반송처럼 단계가 실제로 뒤로 가는 이벤트가 있을 때.

```text
  배달완료 100분 스캔
  간선상차 200분 스캔 (반송으로 다시 트럭에 실림)

  스캔 순서 → 간선상차 (시각이 더 늦으니까)
  최선 단계 → 배달완료 (단계가 더 앞이니까)
```

측정 데이터 1,000건에서는 한 번도 안 갈렸지만, **갈리는 입력을 만들 수 있으면 다른 규칙이다.**
1,000번 같았던 것은 데이터가 얌전해서다.
이 문제에서는 반송을 안 다루기로 했으므로 "되돌아가지 않는다"는 규칙이지 사실이 아니다.

## 규칙 2 — 중복 제거 (dedupe)

**어떤 요구사항인가**: 네트워크 재전송으로 같은 이벤트가 두 번 올 수 있다.
무엇을 "같은 이벤트"로 볼 것인가?

**예시 입력**:

```text
  집화     스캔 10분, 수신 12분   ┐ 스캔 시각이 같다
  집화     스캔 10분, 수신 30분   ┘ = 재전송 (수신 시각만 다름)
  간선상차 스캔 60분, 수신 61분
```

**규칙 적용**: 중복 키 = **단계 + 스캔 시각** (수신 시각은 제외). 위 3건 → 2건.

- **수신 시각을 키에 넣으면 안 되는 이유**: 재전송은 스캔 시각이 같고 **수신 시각만 다르다**. 수신 시각까지 보면 재전송이 전부 "다른 이벤트"가 되어 중복 제거가 아무것도 못 거른다.
- **같은 단계라도 시각이 다르면 다른 이벤트다**: 재분류로 간선 상차가 두 번(60분, 120분) 찍히면 실제로 두 번 일어난 것이다.

**측정이 준 증거**: 원래 이벤트 2,000건에 중복을 섞어도 제거 후는 **언제나 2,000건**.

| 중복 비율 | 전체 | 제거 후 |
|---|---|---|
| 0% | 2,000 | 2,000 |
| 20% | 2,364 | **2,000** |
| 50% | 2,997 | **2,000** |

제거 후가 항상 원래 수와 같다는 것이 **중복 키가 맞다는 증거**다.
수신 시각을 키에 넣으면 이 수가 안 맞는다.

## 규칙 3 — 동점 처리 (스캔 시각이 같을 때)

**어떤 요구사항인가**: 기기가 분 단위로만 기록하면 배달출발과 배달완료가 **같은 시각**에 찍힌다.
순서를 안 정하면?

**예시 입력**: 배달출발(스캔 100분) + 배달완료(스캔 100분) — 목록에 넣는 순서만 바꿔서 두 번 조회.

**규칙 적용**: 스캔 시각이 같으면 **뒤 단계를 나중(이긴 것)으로** 본다.
두 조회 모두 "배달완료".

**왜**: 순서를 안 정하면 결과가 **목록 순서**에 달라진다 — 같은 데이터를 두 번 조회했는데 다른 답이 나오는 시스템이 된다.
Comparator에 `thenComparing(stage.ordinal())`을 붙이는 한 줄이 이 결정론을 산다.

> **Comparator(비교자)** — "누가 앞이고 누가 뒤인가"를 정하는 규칙 객체.\
> 예: 1차 기준이 같을 때 쓸 2차 기준을 thenComparing 으로 잇는다.

> **결정론(deterministic)** — 같은 입력이면 언제나 같은 답이 나오는 성질.\
> 예: 목록에 넣은 순서가 달라도 같은 송장은 늘 같은 현재 상태를 보여준다.

## 규칙 4 — 이력(history)과 진단(backwardSteps, missingStages)

**이력은 스캔 순서로 보여준다**: 수신 순서로 보여주면 "배달 완료" 다음에 "집화"가 나온다 — 손님이 보기에 말이 안 되는 화면이다.

**backwardSteps — 되돌아간 횟수 (수신 순서 기준)**:

```text
  수신 순서: 배달완료 → 집화 → 간선상차
                      ↑ 여기서 단계가 뒤로 갔다 (배달완료 다음 집화) → 1회
```

- 되돌아간 것 자체는 잘못이 아니다 — 이벤트가 늦게 온 것뿐이다.\
  **잘못은 그것을 그대로 상태로 쓰는 것이다.**
- 이 수를 세두면 "우리 파이프라인이 얼마나 어긋나 있나"를 알 수 있다 — 상태 판정용이 아니라 **진단 지표**다.

**missingStages — 건너뛴 단계**:

```text
  집화 → (간선상차?) → (배달출발?) → 배달완료
          ^^^^^^^^^^^^^^^^^^^^^^ 이 둘이 비었다 = 스캔 누락 의심

  단, 집화만 찍힌 진행 중 송장 → 빠진 것 없음
  (최선 단계보다 뒤의 것은 "아직 안 온 것"이지 "빠진 것"이 아니다)
```

## 경계·모서리 케이스

- **함정: 수신이 스캔보다 빠른 데이터** — 기기 시계가 어긋나면 실제로 온다.\
  → ScanEvent 생성자가 예외로 거부한다(같은 시각은 허용). 막지 않으면 그 데이터가 그대로 이력에 남는다.
- **함정: 이벤트 0건인 송장에 예외 던지기** — 아직 아무 스캔도 안 된 송장은 흔하다.\
  → current는 `Optional.empty()`를 준다.\
  예외가 아니다.

> **Optional** — "값이 없을 수도 있음"을 타입으로 표현하는 상자.\
> 예: 아직 스캔이 없는 송장에 예외 대신 빈 상자를 주면, 호출하는 쪽이 빈 경우를 강제로 생각하게 된다.
- **함정: 개발 환경에서 테스트가 다 통과했으니 안심** — 지연이 0이면 세 규칙이 1,000/1,000 같은 답을 낸다.\
  측정: 지연 10%면 수신순/스캔순이 150/1,000 갈리고, 50%면 395/1,000 갈린다.\
  배달 완료된 송장의 **33.8%(338/1,000)** 가 수신순 판정으로는 "아직 안 왔다"로 보였다.\
  데이터는 멀쩡하다 — **읽는 방법이 틀린 것이다.**\
  "어떤 조건에서 이 코드가 갈라지나"를 먼저 물어야 한다.
- **함정: enum 선언 순서를 무심코 바꾸기** — Stage의 선언 순서(집화→간선상차→배달출발→배달완료)가 곧 도메인 순서다(ordinal 사용). 순서를 바꾸면 규칙이 바뀐다.

## 핵심 문장

- 이벤트에는 시각이 둘이다 — **일어난 시각(스캔)과 안 시각(수신)**. 상태 판정은 일어난 시각으로 해야 한다.
- 중복 키는 "그 사건의 정체성"만 담는다 — 재전송으로 변하는 값(수신 시각)을 키에 넣으면 중복 제거가 죽는다.
- 지연이 0이면 틀린 규칙과 맞는 규칙이 같은 답을 낸다 — 그래서 개발 환경에서는 이 버그가 절대 안 보이고, 운영에서 터미널 하나가 늦어지는 순간 나타난다.
- 1,000번 같은 답을 냈어도 갈리는 입력을 만들 수 있으면 다른 규칙이다.
- 되돌아감(backwardSteps)은 버리지 말고 세라 — 상태로는 쓰면 안 되지만, 파이프라인이 어긋난 정도를 알려주는 진단 지표다.

## 용어 풀이

- **스캔 시각(scannedAt)**: 현장 기기가 바코드를 찍은 시각.\
  사건이 실제로 일어난 시각.
- **수신 시각(receivedAt)**: 우리 서버가 그 이벤트를 전달받은 시각.\
  지연 때문에 스캔보다 늦을 수 있다(빠를 수는 없다 — 계약).
- **집화 / 간선상차 / 배달출발 / 배달완료**: 배송 4단계.\
  enum Stage의 선언 순서가 곧 진행 순서다.
- **중복 제거(dedupe)**: 재전송으로 겹친 이벤트를 하나로 합치기.\
  키 = 단계 + 스캔 시각.
- **재전송(retransmission)**: 네트워크 문제로 같은 이벤트를 다시 보내는 것.\
  스캔 시각은 같고 수신 시각만 다르다.
- **record**: 값 묶음을 표현하는 자바 문법.\
  생성자에서 검증하면 "잘못된 값은 아예 못 만든다"가 보장된다.
- **Optional**: 값이 없을 수 있음을 타입으로 알리는 상자.\
  빈 송장 처리를 예외 대신 이것으로.
- **Comparator(비교자)**: 정렬·최대값 계산에 쓰는 순서 규칙.\
  thenComparing으로 동점 처리 기준을 잇는다.
- **ordinal**: enum 상수의 선언 순번(0부터). 여기서는 도메인의 단계 순서로 쓴다.
- **진단 지표**: 상태 판정에는 안 쓰지만 시스템이 얼마나 어긋났는지 알려주는 수.\
  backwardSteps가 그 예.
