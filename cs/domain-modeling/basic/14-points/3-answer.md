### A. 과제 (PointWallet.java 의 TODO 1\~4)

#### 0. 요구사항 — 한 줄이 안 말해주는 것

- 숨은 결정 둘: **① 어느 적립분부터 빼나**(FIFO / 만료 임박 순), **② 사용을 취소하면 어디로 되돌리나**(원래 덩어리 / 새 덩어리).
- 이해가 갈리는 이유: 두 결정 모두 **"손님이 만료로 얼마를 잃나"** 를 정하기 때문이다.

```text
 ① 차감 순서
    FIFO         → 만료 임박분이 남아 사라진다        회사에 유리(포인트가 덜 나간다)
    만료 임박 순  → 버려질 것부터 소진한다             손님에 유리

 ② 되돌리는 곳
    원래 덩어리   → 만료일 그대로                     회사에 유리
    새 덩어리     → 만료일이 취소 시점부터 다시 시작   손님에 유리(유효기간 선물)
```

- 총액만 들면 안 되는 이유: 만료는 **덩어리마다 날짜가 다르다.**\
  숫자 하나에는 "이 1,000점 중 어느 300점이 1/31에 죽는가"가 안 들어 있다.\
  만료를 처리하려면 **죽는 단위**를 알아야 한다.

> **덩어리(lot)** — 적립 한 건을 가리키는 단위. 적립 번호·적립일·만료일·남은 점수를 함께 들고 다닌다.\
> 예: "가입 축하 1,000점(1/1 적립, 1/31 만료)"과 "구매 적립 500점(1/2 적립, 12/31 만료)"은 합쳐서 1,500점이 아니라 **덩어리 두 개**다.

- 잔액은 **덩어리 목록의 파생값**이다.\
  `balanceOn(date)` 는 그때그때 살아 있는 덩어리를 세서 만든 값이지, 따로 들고 있는 필드가 아니다.

> **파생값(derived value)** — 원본 데이터에서 그때그때 계산해 내는 값. 따로 저장하지 않는다.\
> 예: 잔액을 필드로 저장하면 덩어리 목록과 어긋날 수 있지만, 매번 세서 만들면 어긋날 자리가 없다.

- 덩어리가 아는 값 넷: `record PointLot(String id, LocalDate earnedOn, LocalDate expiresOn, int remaining)`\
  → **적립 번호·적립일·만료일·남은 포인트.**
- "규칙"이라는 말: **둘 다 틀리지 않았다.**\
  자연법칙이 아니라 회사가 고르는 것이고, 고른 쪽이 **누구의 돈을 아끼는지**가 다를 뿐이다.\
  그래서 코드가 `SpendOrder` enum 과 `restoreToOriginalLot` 플래그로 **둘 다 표현할 수 있게** 만들어져 있다.

#### 1. TODO 1 — balanceOn

```java
public int balanceOn(LocalDate date) {
    int sum = 0;
    for (PointLot lot : lots.values()) {
        if (lot.isUsableOn(date)) {
            sum += lot.remaining();
        }
    }
    return sum;
}
```

- "1/31까지 유효" → `expiresOn = 2/1`.\
  만료일은 **"이미 없는 첫날"** 이다.
- 1/31 로 쓰면: 판정이 `date < expiresOn` 이라 1/31 에 이미 0이 된다.\
  **하루가 통째로 사라진다.**\
  손님은 "31일까지라며?"라고 문의하고, 개발자는 재현이 안 된다(하루만 어긋나므로).

> **미포함 경계(exclusive bound)** — 구간의 끝 값을 구간 안에 넣지 않는 것. `date < expiresOn` 처럼 쓴다.\
> 예: 만료일이 2/1 이면 1/31 까지는 쓸 수 있고 2/1 부터 못 쓴다. 2/1 은 "마지막 날"이 아니라 "없어진 첫날"이다.

```text
 expiresOn = 2/1 일 때

    1/30  쓸 수 있다  ──┐
    1/31  쓸 수 있다  ──┴─ date < expiresOn
    2/ 1  이미 없다
```

- `isUsableOn` 의 조건 셋: `!date.isBefore(earnedOn)`(적립일 이후) **그리고** `date.isBefore(expiresOn)`(만료 전) **그리고** `remaining > 0`(남아 있음).
- `earnedOn` 도 봐야 하는 이유: **미래 적립분을 미리 넣어두는 경우가 있다**(생일 포인트).\
  테스트 `notUsableBeforeEarned` — day(10) 적립분은 day(0)에 **0**, day(10)에 1,000.
- 만료가 절벽인 그림:

```text
 잔액
 1,000 ├──────────────────────┐
       │                      │
     0 └──────────────────────┴──────────
       1/1                  1/30 │ 1/31

 서서히 주는 것이 아니라 하루에 통째로 0 이 된다.
```

> **절벽 만료(cliff expiry)** — 잔액이 조금씩 줄지 않고 어느 날 한 번에 0이 되는 만료 방식.\
> 예: 1/30 에 1,000점이던 잔액이 1/31 에 0점이 된다. 전날까지는 아무 신호가 없다.

- 절벽이면 필요한 것: **"곧 만료될 포인트" 사전 알림.**\
  그리고 **그 기준일을 며칠 전으로 잡느냐가 또 하나의 결정이다**(7일 전? 30일 전?).\
  그것도 요구사항에 안 적혀 있다.
- `balanceOn` 은 **지금 쓸 수 있는 합**이다.\
  `expiredBy` 는 **그 날까지 만료로 사라진 합**이다(`!date.isBefore(lot.expiresOn())` 인 덩어리의 remaining).\
  둘은 겹치지 않는다 — 한 덩어리는 살아 있거나 죽었거나 둘 중 하나다.

#### 2. TODO 2 — spend

```java
public boolean spend(String spendId, LocalDate date, int amount) {
    if (amount <= 0) {
        throw new IllegalArgumentException("사용은 1 이상이다: " + amount);
    }
    if (spends.containsKey(spendId)) {      // ① 중복
        return false;
    }
    if (amount > balanceOn(date)) {         // ② 모자람 — 여기서 끝내야 상태가 안 바뀐다
        return false;
    }

    Map<String, Integer> taken = new LinkedHashMap<>();
    int left = amount;
    for (PointLot lot : usableLots(date)) { // ③ 규칙대로 정렬된 덩어리에서 차례로
        if (left == 0) break;
        int take = Math.min(left, lot.remaining());
        lots.put(lot.id(), lot.minus(take));
        taken.put(lot.id(), take);          //    어디서 얼마 뺐는지 기록
        left -= take;
    }
    spends.put(spendId, new Spend(spendId, taken));
    return true;
}
```

- 순서: **① 금액 검증 → ② 중복 spendId → ③ 잔액 검사 → ④ 차감 + 기록.**\
  핵심은 **③이 ④보다 앞**이라는 것이다.\
  빼다가 중간에 모자란 걸 알면 이미 상태가 망가진 뒤다.
- 1,000점에 3,000점 사용: **`false`, 잔액 1,000 그대로.**\
  테스트 `allOrNothing` — `assertEquals(1_000, wallet.balanceOn(day(1)), "하나도 안 빠졌다")`.

> **전부 아니면 전무(all-or-nothing)** — 요청한 양을 다 채우지 못하면 아예 하나도 건드리지 않는 규칙.\
> 예: 3,000점 사용 요청에 1,000점밖에 없으면, 1,000점만 빼고 "성공"이라 하지 않고 하나도 안 빼고 실패로 답한다.

- 부분 사용 허용 시 사고: **"3,000점 쓰기"가 1,000점만 쓰이고 성공으로 보고된다.**\
  주문은 3,000점 할인으로 처리되고 지갑에서는 1,000점만 빠져 **결제 금액이 안 맞는다.**\
  차액 2,000점은 아무도 못 찾는 손실이다.
- 중복 spendId: **`false`.**\
  테스트 `duplicateSpend` — 두 번째는 false, 잔액 700 유지.\
  예외가 아닌 이유는 **중복이 네트워크 재시도라는 정상적인 사건**이기 때문이다.

> **멱등(idempotent)** — 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질.\
> 예: 같은 `spendId` 로 사용 요청이 세 번 와도 포인트는 한 번만 빠진다. 응답이 유실돼 앱이 재시도해도 안전하다.

- 잔액 판정 ≠ 차감 판정이면: 사용자에게 **"잔액은 1,000점이라고 떠 있는데 쓰면 실패"** 가 보인다.\
  잔액 검사는 통과했는데 차감 루프가 그 덩어리를 대상에서 빼면, `left` 가 0이 안 된 채로 커밋된다.
- 확실한 방법: **같은 함수를 쓴다.**\
  `balanceOn` 도 `usableLots` 도 똑같이 `lot.isUsableOn(date)` 로 판정한다.\
  기준이 한 곳에만 있으면 어긋날 수가 없다.

> **단일 출처(single source of truth)** — 같은 판단을 내리는 코드를 딱 한 군데만 두는 것.\
> 예: "쓸 수 있는 덩어리인가"를 `isUsableOn` 하나에만 두면, 잔액 계산과 차감이 절대 서로 다른 답을 낼 수 없다.

- 남기는 기록: **`Spend(spendId, byLot)`** — 덩어리별로 얼마 뺐는지의 장부.\
  총액("800점 썼다")만 남기면 취소 때 **어느 덩어리에 얼마를 돌려줄지 모른다.**\
  만료일이 다르므로 아무 데나 넣으면 만료일이 뒤바뀐다.

> **장부(ledger)** — "무엇이 어디로 얼마 움직였는지"를 건별로 남긴 기록.\
> 예: `{"L1": 600, "L2": 400}` 이 있어야 취소할 때 L1 에 600, L2 에 400 을 정확히 되돌릴 수 있다.

- `amount <= 0`: **예외.**\
  중복과 다르게 다루는 이유는 **0점 사용이 부르는 쪽의 프로그래밍 오류**이지 정상적인 사건이 아니기 때문이다.\
  중복 재시도는 세상에서 일어나는 일이고, 음수 사용은 코드 버그다.

#### 3. TODO 3 — usableLots

```java
private List<PointLot> usableLots(LocalDate date) {
    List<PointLot> usable = new ArrayList<>();
    for (PointLot lot : lots.values()) {
        if (lot.isUsableOn(date)) {      // 잔액과 같은 판정
            usable.add(lot);
        }
    }
    Comparator<PointLot> order = spendOrder == SpendOrder.OLDEST_FIRST
            ? Comparator.comparing(PointLot::earnedOn).thenComparing(PointLot::id)
            : Comparator.comparing(PointLot::expiresOn).thenComparing(PointLot::id);
    usable.sort(order);
    return usable;
}
```

- 비교 기준: **OLDEST_FIRST → `earnedOn`**, **EXPIRING_FIRST → `expiresOn`.**\
  둘 다 동점은 `id` 로 끊는다.

> **FIFO(First In First Out, 선입선출)** — 먼저 들어온 것부터 꺼내 쓰는 순서.\
> 예: 1/1 에 쌓인 포인트를 1/2 에 쌓인 것보다 먼저 쓴다. 만료일이 언제든 상관하지 않는다.

> **만료 임박 순(expiring first)** — 곧 죽을 것부터 꺼내 쓰는 순서.\
> 예: 만료일이 1/31 인 덩어리를 12/31 인 덩어리보다 먼저 쓴다. 버려지는 포인트가 줄어 손님에게 유리하다.

- 손계산 (테스트 `spendOrder`):

```text
 L1  1/1 적립, 12/31 만료(day 364), 1,000 점
 L2  1/2 적립,  1/31 만료(day  30), 1,000 점
 1/3 에 1,500 점 사용

 FIFO           L1 에서 1,000, L2 에서 500   →  L1 = 0,   L2 = 500
 만료 임박 순    L2 에서 1,000, L1 에서 500   →  L1 = 500, L2 = 0

 1/31(day 30) 이 지나면 — L2 는 죽는다
 FIFO           남은 500 이 하필 L2 라 사라진다   expiredBy = 500,  balance = 0
 만료 임박 순    남은 500 이 L1 이라 산다        expiredBy = 0,    balance = 500
```

- 갈리는 이유: **같은 1,500점을 썼어도 "무엇을 남겼는지"가 다르다.**\
  남은 500점이 곧 죽을 덩어리냐 오래 사는 덩어리냐 — 그게 잔액 0과 500을 가른다.
- 같은 날 적립분: **`thenComparing(PointLot::id)`** 로 번호가 순서를 정한다.

> **동점 깨기(tie-break)** — 정렬 기준이 같을 때 순서를 확정하기 위해 쓰는 보조 기준.\
> 예: 적립일이 둘 다 1/1 이면 번호 "L1"이 "L2"보다 앞에 온다. 이 규칙이 없으면 순서가 그때그때 달라진다.

- 안정 정렬만으로 부족한 이유: 안정 정렬은 **입력 순서를 보존**할 뿐이다.\
  입력 순서 자체가 안 정해져 있으면 **그 비결정성이 그대로 결과로 흘러든다.**

> **안정 정렬(stable sort)** — 정렬 기준이 같은 값들끼리는 원래 있던 순서를 그대로 유지하는 정렬.\
> 예: [L2, L1] 을 적립일로 정렬하면 둘 다 1/1 이라 [L2, L1] 그대로 나온다. 순서를 만들어주는 것이 아니라 **보존**할 뿐이다.

> **결정적(deterministic)** — 같은 입력이면 언제나 같은 답이 나오는 성질.\
> 예: L1·L2 를 어떤 순서로 넣었든 사용 후 잔액이 늘 같아야 결정적이다.

- 두 말의 차이: **안정 정렬 = "같은 것끼리는 넣은 순서 유지"**, **결정적 결과 = "같은 데이터면 언제나 같은 답".**\
  전자는 후자를 보장하지 않는다.\
  넣은 순서가 매번 다르면 답도 매번 다르다.
- DB에서 다시 읽으면: **행이 나오는 순서가 바뀔 수 있다**(ORDER BY 없는 조회, 인덱스 변경, 샤드 순서).\
  테스트 `tieBreakMakesItDeterministic` 이 정확히 이것을 잡는다.\
  L1·L2 를 **넣는 순서만 앞뒤로 바꾼 두 지갑**의 day(30) 잔액이 같아야 한다(둘 다 1,000).
- `private` 인 의미: **차감 순서는 지갑 내부의 결정**이지 바깥이 고를 것이 아니다.\
  밖에서 고르게 하면 같은 지갑이 호출마다 다른 규칙으로 빠진다.\
  규칙은 지갑을 만들 때(`new PointWallet(order, ...)`) **한 번** 정한다.

```java
public boolean cancelSpend(String spendId, LocalDate date, int extendedDays) {
    Spend spend = spends.remove(spendId);    // 꺼내면서 동시에 지운다
    if (spend == null) {
        return false;
    }
    for (Map.Entry<String, Integer> entry : spend.byLot().entrySet()) {
        if (restoreToOriginalLot) {
            PointLot lot = lots.get(entry.getKey());
            lots.put(lot.id(), lot.plus(entry.getValue()));      // 만료일 그대로
        } else {
            String id = "restore-" + (++restoreCounter);
            lots.put(id, new PointLot(id, date, date.plusDays(extendedDays), entry.getValue()));
        }
    }
    return true;
}
```

- 손계산 (테스트 `restoreTarget` — 1/1 적립 day(30) 만료, 1/5 사용, 1/10 취소 +30일):

```text
 원래 덩어리로   L1 에 도로 1,000      만료 = day(30)   → day(30) 잔액 0
 새 덩어리로     restore-1 을 새로 생성  만료 = day(10)+30 = day(40)
                                                     → day(30) 잔액 1,000
                                                     → day(40) 잔액 0
```

  게다가 원래 덩어리와의 연결이 끊겨 **이력을 못 따라간다.**\
  구현이 쉬운 쪽이 **비용을 두 군데로 나눠 내는 셈이다.**
- 취소 5번 뒤 (테스트 `restoringCreatesLots`): **원래 덩어리 `lotCount()==1`, 새 덩어리 `==6`.**\
  그런데 **잔액은 둘 다 1,000으로 같다.**\
  겉으로 보이는 숫자가 같아서 차이를 눈치채기 어렵다.
- 두 번 취소: **`false`**(테스트 `cancelOnce`).\
  허용하면 **포인트가 두 배로 돌아온다** — 500점 쓰고 두 번 취소하면 1,500점이 된다.\
  없는 번호의 취소도 `false`.
- 합계만 기억하면: **만료일이 뒤바뀐다.**\
  테스트 `restoresPerLot` — L1(day0\~day30) 600 + L2(day1\~day90) 400 을 되돌릴 때 덩어리마다 그만큼 넣어야 day(30)에 400 이 남는다.\
  합계 1,000을 L2 에만 넣으면 day(30) 잔액이 1,000이 되어 **손님이 600점을 공짜로 더 갖는다.**\
  반대로 L1 에만 넣으면 400점을 잃는다.
- `spends.remove` 를 쓰면: **꺼내기와 지우기가 한 번에** 끝난다.\
  null 이면 "없거나 이미 취소된 것"이므로 **두 번 취소 방지가 저절로 된다.**\
  따로 "취소됨" 플래그를 둘 필요가 없다 — 플래그를 두면 그 플래그와 spends 맵이 어긋날 자리가 생긴다.

#### 5. 측정이 알려준 것

- 유효기간 30\~365일 제각각, 200일 × 500회 (`spendOrderDecidesHowMuchExpires`):

| | 만료로 사라진 포인트 |
|---|---|
| FIFO | **1,732,900** |
| 만료 임박 순 | 25,600 |

- 배수: README 제목은 **68배**다.\
  테스트 assert 는 정수 나눗셈으로 **67**이다 — `assertEquals(67, expiredFifo / expiredExpiring, "정수로 67, 실제 67.7 배")`.\
  500회 중 **493회**에서 값이 갈린다.
- 유효기간 전부 60일이면: **0회.**\
  `assertEquals(0, differ, "한 번도 안 갈린다")`.
- 이유: **적립 순서가 곧 만료 순서**이기 때문이다.\
  기간이 같으면 먼저 적립된 것이 반드시 먼저 만료되므로 두 규칙이 **같은 덩어리를 고른다.**

```text
 기간이 같다(60일)        기간이 제각각이다
 L1 1/1 적립 → 3/1 만료   L1 1/1 적립 → 12/31 만료
 L2 1/2 적립 → 3/2 만료   L2 1/2 적립 →  1/31 만료

 적립 순 = 만료 순         적립 순 ≠ 만료 순
 두 규칙이 같은 답          두 규칙이 갈린다
```

- "적립은 다 1년"으로 시험하면: **차이가 0으로 보인다.**\
  두 규칙 중 아무거나 골라도 테스트가 통과하고, 그래서 **어느 쪽을 골랐는지조차 잊는다.**\
  운영에 나가서 기간이 섞이는 순간 68배가 튀어나온다.

> **가려진 갈림(masking)** — 테스트 데이터가 우연히 특수해서, 두 설계의 차이가 결과에 안 나타나는 것.\
> 예: 유효기간을 전부 60일로 맞춘 데이터에서는 FIFO와 만료 임박 순이 500번 중 한 번도 안 갈린다. 차이가 없는 게 아니라 **안 보이는** 것이다.

- 실제 서비스가 제각각인 근거: README — **가입 축하 30일, 구매 적립 1년, 이벤트 7일**이 섞인다.
- 취소 20% 상황 (`restoreTargetChangesBothMoneyAndSize`, 500회):

| | 만료 소멸 | 덩어리 수 |
|---|---|---|
| 원래 덩어리로 | 16,730,000 | 33,308 |
| 새 덩어리로 | **14,992,000** | **44,117** |

- 퍼센트: 만료 소멸 **−10%**, 덩어리 수 **+32%**.\
  테스트가 그 계산을 직접 assert 한다.
- 취소를 한 번도 안 하면: **완전히 같다** — 만료 소멸도 덩어리 수도 잔액도(`withoutCancellationBothAreIdentical`).\
  **되돌리는 코드가 아예 안 돌기 때문이다.**
- 테스트에 주는 경고: **취소 경로는 정상 흐름이 아니라 테스트에서 자주 빠진다.**\
  그런데 **이 박스에서 갈리는 것은 전부 그 경로에 있다.**\
  취소를 안 넣은 시나리오는 두 방식의 차이를 0으로 만들어, "아무거나 골라도 된다"는 잘못된 확신을 준다.\
  **차감 순서의 "기간 균일" 함정과 정확히 같은 모양이다** — 갈리는 입력을 일부러 만들지 않으면 결정이 안 보인다.
- 1/30은 **1,000점**, 1/31은 **0점**(`expiryIsACliff`).

#### 6. 생각해볼 것

> 원본 README가 답을 주지 않고 던진 질문 — (원본에 근거 없음 — 내 추론) 표시.

- **FIFO를 쓰는 이유**: (내 추론)\
  ① **회사 비용이 덜 든다** — 만료로 사라지는 포인트가 곧 안 나간 돈이다.\
  ② **장부 관행이 선입선출**이다 — 재고·원가 회계가 FIFO라 포인트도 같은 규칙으로 맞추면 정산이 단순하다.\
  ③ **설명하기 쉽다** — "먼저 쌓인 것부터 씁니다"는 손님도 이해하고, "임박한 것부터"는 왜 그런지 설명이 한 단계 더 든다.\
  ④ 기간이 균일한 서비스에서는 **어차피 같은 답**이라 굳이 바꿀 이유가 없다.
- **만료된 포인트를 쓴 주문의 취소**: 코드가 답을 준다 — **되돌리기 방식에 따라 갈린다.**
  - 원래 덩어리 방식: `lots.get(id).plus(amount)` 로 **죽은 덩어리에 도로 넣는다.**\
    `isUsableOn` 은 `date < expiresOn` 이 false 라 잔액에 안 잡히고, `expiredBy` 는 그 remaining 을 **만료분으로 센다.**\
    → 사실상 **안 살아난다**(넣자마자 사라진 것과 같다).
  - 새 덩어리 방식: 취소 시점 + extendedDays 로 **새 덩어리가 생겨 살아난다.**
  - (내 추론) 손님은 "썼던 포인트가 돌아온다"고 기대한다.\
    원래 덩어리 방식을 쓴다면 **만료된 덩어리로의 복원을 어떻게 알릴지**가 따로 정해야 할 규칙이다.
- **적립 취소(구매 취소로 적립분 회수)**: (내 추론) 지금 코드에는 **없는 기능**이다(`earn` 의 반대가 없다).\
  넣는다면 **적립 번호로 그 덩어리를 찾아 빼는 것**이 맞다 — 차감 순서를 쓰면 안 된다.\
  적립 취소는 "어느 덩어리든 그만큼"이 아니라 **"그 적립 건"** 을 없애는 것이기 때문이다.\
  어려운 점은 **이미 그 덩어리에서 쓴 경우**다 — remaining 이 부족하면 음수가 되어 `PointLot` 생성자가 거부한다.\
  그래서 "쓴 만큼은 회수 못 함"인지 "다른 덩어리에서 빼서 채움"인지 **또 하나의 결정**이 생긴다.
- **덩어리 수십만 개의 잔액 조회**: (내 추론) 지금은 `balanceOn` 이 전 덩어리를 매번 순회한다(O(n)).\
  ① **만료된 덩어리를 배치로 걷어낸다**(remaining 을 만료 장부로 옮긴 뒤 삭제) — 살아 있는 것만 남긴다.\
  ② **캐시된 잔액 필드**를 두고 적립·사용·만료 때 갱신한다 — 다만 **덩어리 목록과 캐시가 어긋날 자리**가 생기므로 정기 대사가 필요하다.\
  ③ **만료일 인덱스**로 "오늘 살아 있는 것"만 범위 조회한다.\
  ④ 새 덩어리 복원 방식이 덩어리를 32% 늘린다는 측정값이 있으니, **되돌리기 방식 선택 자체가 이 문제의 크기를 정한다.**

#### 7. 연결

- **09번 주문 상태**: 09는 "그림의 화살표 9개 밖에 있는 55칸", 14는 "'포인트를 쓴다' 한 줄 밖에 있는 결정 둘".\
  둘 다 **요구사항이 말한 것보다 말 안 한 것이 훨씬 많고, 그 안 말한 칸이 실제 동작을 정한다.**\
  차이는 09는 빈칸이 "금지냐 누락이냐"이고, 14는 **어느 쪽을 골라도 맞는데 누구 돈인지가 다르다**는 것이다.
- **같은 spendId 두 번 막기**: 09번 주문 상태의 `IGNORED`(같은 상태 재요청), 10번 결제·13번 재고의 멱등키와 **같은 자리**다.\
  재시도는 사고가 아니라 정상 사건이므로 **예외가 아니라 값으로 거부**한다.
- **"두 규칙이 같아지는 입력만으로 시험"**: 09번의 **"표준 표에는 자기 전이가 없어서 apply 의 판정 순서가 무의미해 보인다"** 와 정확히 같은 모양이다.\
  교훈은 하나 — **결정이 갈리는 입력을 테스트가 반드시 들고 있어야 한다.**\
  14에서는 그게 **기간이 제각각인 데이터**와 **취소가 들어간 시나리오** 둘이다.
- **다른 도메인으로**: **"총액이 아니라 건별 목록, 잔액은 파생값"**.\
  재고(입고 로트별 유통기한·원가), 휴가 일수(부여 연도별 소멸 시한), 기프트카드·선불 충전금, 쿠폰 보유분, 탄소배출권.\
  **단위마다 죽는 날이 다른 것은 전부 합쳐서 들고 있으면 안 된다.**
- **만료 경계**: `date < expiresOn` 은 **끝을 포함하지 않는 반열림 구간**이다.\
  08번 회의 시간 겹침(`start < otherEnd && otherStart < end`), 예약 구간, 페이지네이션의 `[offset, offset+limit)` 과 같은 관습이다.\
  **끝을 포함하느냐가 늘 하루(또는 한 건)를 만들거나 없앤다.**

> **반열림 구간(half-open interval)** — 시작은 포함하고 끝은 포함하지 않는 구간. `[시작, 끝)` 으로 쓴다.\
> 예: 포인트의 `[earnedOn, expiresOn)`, 회의의 `[start, end)`. 이렇게 잡으면 연속한 두 구간이 겹치지도 비지도 않는다.
