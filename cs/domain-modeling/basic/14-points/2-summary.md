## 한눈에 — 쉽게 말하면

**포인트 관리 = 냉장고 우유 관리.**

- 냉장고에 우유가 세 팩 있다. "우유 있어?"라는 질문에는 "1.5리터"라고 총량으로 답해도 되지만, **마실 때는 어느 팩부터 딸지 골라야 한다** — 팩마다 유통기한이 다르니까.
- 먼저 산 것부터 딸 수도 있고(FIFO), **유통기한이 임박한 것부터** 딸 수도 있다. 임박한 것부터 마셔야 버리는 우유가 준다.
- 포인트도 똑같다. **총액만 들고 있으면 만료를 처리할 수 없다.** 그래서 적립 한 건 한 건을 **덩어리(lot)** 로 관리한다 — 언제 적립됐고 언제 만료되는지를 덩어리마다 안다.
- "포인트를 쓴다"는 한 줄이 안 말해주는 결정이 둘이다: ① 어느 적립분부터 빼나 ② 사용을 취소하면 어디로 되돌리나. **둘 다 손님에게 유리한 쪽과 회사에 유리한 쪽이 갈린다.**

```text
  덩어리:  [가입축하 1,000점, ~1/31]  [구매적립 500점, ~12/31]  [이벤트 300점, ~1/10]

  800점을 쓴다면?
    FIFO(적립 순)     → 가입축하에서 800
    만료 임박 순      → 이벤트 300 + 가입축하 500   ← 버려질 것부터 소진
```

실무 예: 멤버십 포인트, 마일리지, 기프트 카드 잔액, 선불 충전금 — 유효기간이 제각각인 돈 비슷한 것 전부.

## 문제 — 이 챕터가 시키는 것

원본 README가 말로 못 박은 요구사항 전부.

> "'포인트를 쓴다' 는 한 줄이 안 말해주는 것이 둘이다."
> ```
>   1. 어느 적립분부터 빼나
>        먼저 적립된 것부터   (FIFO)
>        먼저 만료될 것부터   (만료 임박 순)
>
>   2. 사용을 취소하면 어디로 되돌리나
>        원래 뺀 덩어리로     만료일이 그대로다
>        새 덩어리로          만료일이 늘어난다
> ```
> "**둘 다 손님에게 유리한 쪽과 회사에 유리한 쪽이 갈린다.**"
> "총액만 들고 있으면 만료를 처리할 수 없다. 그래서 덩어리(lot) 로 관리한다."

테스트가 못 박은 계약:

- 1/1 적립 + 30일 만료면 day(29)까지 1,000, **day(30)에는 0**이고 `expiredBy(day(30))==1,000`.
- 미래 적립(day(10) 적립)은 day(0)에 **0**, day(10)에 1,000.
- 적립 0 이하 · 중복 적립 번호 · 만료일 ≤ 적립일은 예외.
- L1(1/1 적립, 364일) + L2(1/2 적립, 30일)에서 1,500 사용 → **FIFO 는 500 을 잃고**(잔액 0), 만료 임박 순은 **안 잃는다**(잔액 500).
- 같은 날 적립된 L1·L2 를 **넣는 순서만 바꿔도** 결과가 같아야 한다(둘 다 day(30) 잔액 1,000).
- 1,000점 있는데 3,000점 쓰기 → `false`, **하나도 안 빠진다**.
- 같은 사용 번호 두 번째는 `false`, 잔액은 안 바뀐다.
- 만료된 덩어리는 잔액에도 안 잡히고 차감 대상도 아니다.
- 1/1 적립 1/31 만료 → 1/5 사용 → 1/10 취소(+30일): **원래 덩어리**는 day(30)에 0, **새 덩어리**는 day(30)에 1,000이고 day(40)에 0.
- 취소 5번: 원래 덩어리 방식 `lotCount()==1`, 새 덩어리 방식 `==6`. **잔액은 같다.**
- 두 번 취소는 `false`(포인트가 두 배로 안 돌아온다).
- 여러 덩어리에서 뺀 사용(L1 600 + L2 400)은 **덩어리마다 그만큼** 되돌린다.

README가 미리 알려준 함정: ①만료일에는 이미 없다("1월 31일까지 유효"를 만료일 1/31로 쓰면 하루가 사라진다) ②**잔액 판정과 차감 판정이 같아야 한다**(다르면 "잔액은 있는데 못 쓴다") ③모자라면 아무것도 안 쓴다 ④같은 날 적립분의 순서를 정해야 한다 — **"안정 정렬"과 "결정적 결과"는 다른 말이다**.

## 전체 흐름

```text
말로 된 요구사항                          →  코드 구조
────────────────────────────────────────────────────────────
"총액만으론 만료를 못 다룬다"             →  record PointLot(id, earnedOn, expiresOn, remaining)
"1/31까지 유효 = 만료일에는 이미 없다"     →  isUsableOn: date < expiresOn (미포함)
"어느 적립분부터 빼나"                    →  enum SpendOrder {OLDEST_FIRST, EXPIRING_FIRST}
"모자라면 아무것도 안 쓴다"               →  spend: 잔액 검사 통과 못 하면 false, 상태 불변
"취소하려면 어디서 뺐는지 알아야 한다"     →  record Spend(spendId, byLot) — 덩어리별 차감 기록
"취소하면 어디로 되돌리나"                →  restoreToOriginalLot (원래 덩어리 vs 새 덩어리)
"되돌리기가 덩어리를 만드나 관측"          →  lotCount()
```

## 규칙 1 — 덩어리(lot)와 만료 경계

**어떤 요구사항인가**: "1월 31일까지 유효"인 포인트는 2월 1일부터 못 쓴다 — 그런데 코드의 만료일(expiresOn)은 **"이 날에는 이미 없다"** 는 뜻으로 정했다.

**예시**: "1/31까지 유효" → expiresOn = **2/1** 로 저장해야 한다. 만료일을 1/31로 쓰면 1/31 하루가 사라진다.

```text
  isUsableOn(date) = earnedOn ≤ date < expiresOn  그리고 remaining > 0

  expiresOn = 2/1 일 때:   1/30 쓸 수 있음 | 1/31 쓸 수 있음 | 2/1 이미 없음
```

- 만료는 **하루에 통째로 일어난다** — 1/30에 1,000점, 1/31에 0점. 서서히 줄지 않는다. 그래서 "곧 만료" 알림이 필요하고, 그 기준일을 며칠 전으로 잡느냐가 또 하나의 결정이다.
- 잘못된 덩어리는 못 만든다: 빈 id, 음수 잔액, 만료일 ≤ 적립일 전부 생성자에서 거부.

## 규칙 2 — 차감 순서 (SpendOrder)

**어떤 요구사항인가**: 여러 덩어리에서 어느 것부터 빼나.

| 순서 | 뜻 | 누구에게 유리 |
|---|---|---|
| OLDEST_FIRST (FIFO) | 먼저 적립된 것부터 | 회사 (임박분이 만료로 사라짐) |
| EXPIRING_FIRST | 먼저 만료될 것부터 | 손님 (버려지는 포인트 최소) |

**측정: 차감 순서로 만료 소멸이 68배 갈린다** — 200일 동안 적립·사용 500회, 유효기간 30~365일 섞임:

| | 만료로 사라진 포인트 |
|---|---|
| FIFO | **1,732,900** |
| 만료 임박 순 | 25,600 |

**그런데 유효기간이 다 같으면(전부 60일) 500회 중 한 번도 안 갈린다** — 적립 순서가 곧 만료 순서이기 때문. **개발할 때 "적립은 다 1년"으로 시험하면 이 차이가 안 보인다.** 실제 서비스는 가입 축하 30일, 구매 적립 1년, 이벤트 7일이 섞인다.

**동점 처리도 규칙이다**: 같은 날 적립(또는 같은 만료일)이면 `thenComparing(id)`로 순서를 고정한다. 정렬이 안정적(stable)이어도 **입력 순서 자체가 안 정해져 있으면 그대로 흘러든다** — "안정 정렬"과 "결정적 결과"는 다른 말이다.
  - *안정 정렬(stable sort)*: 정렬 기준이 같은 원소끼리는 원래 순서를 유지하는 정렬. 원래 순서가 매번 다르면 결과도 매번 다르다.

## 규칙 3 — 전부 아니면 전무 (spend)

**어떤 요구사항인가**: 3,000점을 쓰려는데 1,000점밖에 없으면?

**규칙**: **아무것도 안 쓰고 false.** 부분 사용을 허용하면 "3,000점 쓰기"가 1,000점만 쓰이고 성공으로 보고되어 **결제 금액이 안 맞는다.**

```text
  spend(id, date, 3000)의 순서:
  ① 이미 있는 spendId?      → false (중복)
  ② 3000 > balanceOn(date)? → false (모자람 — 상태 그대로)
  ③ 정렬된 덩어리들에서 차례로 뺀다. 어디서 얼마 뺐는지 Spend에 기록.
```

**함정: 잔액 판정과 차감 판정이 같아야 한다.** balanceOn은 `isUsableOn`으로 세고, 차감 대상(usableLots)도 같은 `isUsableOn`으로 거른다 — 기준이 다르면 "잔액은 있는데 못 쓴다"가 된다.

## 규칙 4 — 취소 되돌리기 (cancelSpend)

**어떤 요구사항인가**: 쓴 포인트의 주문이 취소되면 포인트를 돌려줘야 한다. **어디로?**

| 방식 | 만료일 | 구현 |
|---|---|---|
| 원래 덩어리로 (restoreToOriginalLot=true) | 그대로 | Spend 기록의 byLot을 보고 각 덩어리에 plus |
| 새 덩어리로 (false) | 취소 시점부터 다시 시작 (연장!) | "restore-N" 덩어리를 새로 만든다 |

**측정: 사용의 20%가 취소되는 상황에서**:

| | 만료 소멸 | 덩어리 수 |
|---|---|---|
| 원래 덩어리로 | 16,730,000 | 33,308 |
| 새 덩어리로 | **14,992,000** (−10%) | **44,117** (+32%) |

- 새 덩어리 방식은 취소할 때마다 유효기간을 새로 준다 — 손님은 10% 덜 잃고 **회사는 그만큼 더 준다.**
- 덩어리가 32% 늘어 잔액 계산이 느려지고, 원래 덩어리와의 연결이 끊긴다.
- **구현이 쉬운 쪽(새 덩어리 — 원래 덩어리를 안 찾아도 된다)이 비용을 두 군데(회사 돈 + 성능)로 나눠 내는 셈이다.**

**되돌리려면 기록이 필요하다**: spend가 "총 800점 썼다"만 남기면 취소 때 어디로 돌려줄지 모른다. 그래서 `Spend(spendId, byLot)` — **덩어리별로 얼마 뺐는지** — 를 남긴다. 원래-덩어리 방식은 이 기록 없이는 불가능하다.

## 경계·모서리 케이스

- **함정: "1/31까지 유효"를 expiresOn=1/31로 저장** → 1/31 하루가 사라진다. 만료일은 "이미 없는 첫날"이다.
- **함정: 부분 사용 허용** → 성공 보고와 실제 차감이 어긋나 결제 금액이 안 맞는다. 모자라면 상태를 안 건드리고 false.
- **함정: 같은 날 적립 덩어리의 순서 미정** → 같은 데이터에 다른 답. id로 동점을 깬다.
- **함정: 취소 경로를 테스트에서 빼먹기** → 측정에서 취소가 0이면 두 되돌리기 방식이 **완전히 같다**(되돌리는 코드가 아예 안 돈다). **이 박스에서 갈리는 것은 전부 취소 경로에 있는데, 취소는 정상 흐름이 아니라 테스트에서 자주 빠진다.**
- **함정: 유효기간을 다 같게 만든 테스트 데이터** → FIFO와 만료 임박 순이 한 번도 안 갈린다. 갈리는 입력(제각각 기간)을 일부러 만들어야 한다.
- 중복 spendId는 false(멱등하게 거부), 없는 사용의 취소도 false.

## 핵심 문장

- 총액만 들고 있으면 만료를 처리할 수 없다 — 포인트는 **만료일이 제각각인 덩어리(lot)의 목록**이고, 잔액은 그 파생값일 뿐이다.
- "포인트를 쓴다" 한 줄에는 결정이 둘 숨어 있다 — **어느 덩어리부터 빼나, 취소하면 어디로 되돌리나** — 그리고 둘 다 손님과 회사의 이해가 갈리는 사업 결정이다.
- 만료일에는 이미 없다 — "까지 유효"와 만료일 표기 사이의 하루가 경계 버그의 단골이다.
- 모자라면 아무것도 안 쓴다 — 부분 성공은 성공이 아니라 금액이 안 맞는 사고다.
- 갈리는 것은 전부 취소 경로에 있는데 취소는 정상 흐름이 아니라 테스트에서 빠진다 — 유효기간이 균일한 데이터, 취소 없는 시나리오는 두 규칙의 차이를 0으로 만든다.

## 용어 풀이

- **덩어리(lot)**: 적립 한 건. 적립 번호·적립일·만료일·남은 포인트를 가진 불변 record. 차감은 minus로 새 객체를 만든다.
- **FIFO(First In First Out, 선입선출)**: 먼저 적립된 것부터 쓰는 순서. OLDEST_FIRST.
- **만료 임박 순(EXPIRING_FIRST)**: 먼저 만료될 것부터 쓰는 순서. 만료 소멸을 최소화 — 손님에게 유리.
- **만료 미포함 경계**: expiresOn 그 날에는 이미 못 쓴다 (`date < expiresOn`). "까지 유효"의 다음 날이 만료일.
- **전부 아니면 전무(all-or-nothing)**: 요청 수량을 다 채우지 못하면 아무것도 차감하지 않는 규칙.
- **Spend 기록(byLot)**: 사용 한 건이 어느 덩어리에서 얼마씩 뺐는지의 장부. 원래 덩어리로 되돌리기의 전제.
- **원래 덩어리 복원**: 취소분을 뺐던 덩어리에 도로 넣기 — 만료일 유지.
- **새 덩어리 복원**: 취소분을 새 덩어리로 만들기 — 유효기간이 연장되고(회사 부담) 덩어리 수가 는다(성능 부담).
- **안정 정렬(stable sort)**: 기준이 같은 원소의 원래 순서를 지키는 정렬. 입력 순서가 비결정적이면 결과도 비결정적 — 그래서 동점 규칙(id)이 따로 필요하다.
- **결정적(deterministic)**: 같은 입력이면 언제나 같은 답. 동점 처리까지 정해야 얻는다.
- **멱등(idempotent)**: 같은 spendId의 재요청이 두 번 차감되지 않는 성질.
