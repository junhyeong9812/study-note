## 한눈에 — 쉽게 말하면

**정기권 일할 계산 = 한 달 치 급식비를 중간에 전학 갈 때 돌려받는 문제.**

- "한 달 30,000원, 중도 해지하면 남은 날만큼 돌려드립니다" — 이 한 문장으로 충분해 보이지만, **이 문장이 안 정해준 것이 넷이고, 넷 다 돈 액수를 바꾼다.**
- 급식비로 바꿔 말하면: "남은 날만큼 돌려준다"고 할 때 ① 한 달을 며칠로 볼 건지(2월은 28일인데?) ② 전학 가는 날 급식을 먹었으면 그날은 쓴 날인지 ③ 1원 미만 우수리는 어쩔 건지 ④ "낸 돈 - 돌려줄 돈"이 딱 맞아떨어지는지.
- 도메인 모델링의 일은 바로 이것이다: **말 속에 숨어 있는 빈칸을 찾아내서, 각각을 코드의 값(정책)으로 올리는 것.**
- 실무 예: 넷플릭스·통신사 요금제 중도 해지, 헬스장 환불, 보험료 일할 계산.

```text
"남은 날만큼 돌려드립니다" 가 안 정해준 4가지
                                          ┌─ 그 달 실제 일수(28~31)?
  ① 분모: 한 달 = 며칠? ──────────────────┤
                                          └─ 30일 고정?
  ② 시작일: 시작한 날은 쓴 날인가?
  ③ 해지일: 해지한 날은 쓴 날인가?
  ④ 반올림: 원 미만은 버리나 올리나?
```

## 전체 흐름

```text
요구사항 문장                              코드로의 번역
─────────────────────────────────────────────────────────────────
"안 정해진 4가지"          →  ProrationPolicy 레코드 (4개 필드)
                              actualDaysInMonth / countStartDay /
                              countEndDay / rounding
"쓴 날이 며칠인가"         →  usedDays(start, end, policy)
"한 달을 며칠로 보나"      →  daysInPeriod(month, policy)
"그 달에 받을 돈"          →  chargeFor(...) = 요금 × 쓴날/분모
"돌려줄 돈"                →  refundFor(...) = 월요금 - chargeFor   ← 뺄셈!
"여러 달에 걸치면"         →  monthlyCharges(...) 달마다 따로 일할
```

  - *일할 계산(proration)*: 한 달 요금을 날수 비율로 쪼개서 계산하는 것. "일(日) 단위로 나눈다(割)"는 뜻.
  - *정책(policy)*: 요구사항이 안 정해준 선택지를 코드의 값으로 올린 것. 여기서는 `ProrationPolicy` 레코드 하나에 4개가 다 모여 있다.

## 규칙 1 — 쓴 날 수: 경계를 세는 방식이 날수를 정한다

**어떤 요구사항인가**: "남은 날만큼"이라고만 쓰면, 해지한 날이 "남은 날"인지 "쓴 날"인지 안 정해진다. 시작한 날도 마찬가지다.

**예시 입력**: 3/1 시작, 3/10 해지.

```text
  3/1  3/2  3/3  3/4  3/5  3/6  3/7  3/8  3/9  3/10
   ●────────────────────────────────────────○
  시작                                     해지

  시작 포함 + 해지 미포함 (standard)  →  3/1~3/9   =  9일
  시작 포함 + 해지 포함              →  3/1~3/10  = 10일
  시작 미포함 + 해지 포함            →  3/2~3/10  =  9일
```

**계산 방법** (impl의 `usedDays`): `end.toEpochDay() - start.toEpochDay()`로 날짜 차이를 구하고, 시작일을 세면 +1, 해지일을 안 세면 -1.

**왜 이렇게 모델링했나**:
- 04번 숙박의 체크아웃 날과 정확히 같은 구조다. "해지한 날 서비스를 쓸 수 있나"가 이 값을 정한다.
- 측정: 해지일을 세느냐로 **1,000건 중 1,000건이 갈린다** — 하루가 통째로 붙거나 빠지니 언제나 다르다. 그런데 이것이 요구사항에 안 적히는 대표 항목이다.
- **둘 다 안 세는 정책은 만들 때부터 막는다**(생성자에서 예외) — 하루 쓰고 해지한 사람이 0일이 되어 공짜가 되기 때문.

## 규칙 2 — 분모: 실제 일수냐 30일 고정이냐

**어떤 요구사항인가**: "한 달 30,000원"의 "한 달"이 며칠인지가 안 정해져 있다.

**예시 입력**: 월 30,000원, 1일부터 15일까지(쓴 날 14일).

| | 2월 (28일) | 1월 (31일) |
|---|---|---|
| 실제 일수 | 30,000×14/28 = **15,000** | 30,000×14/31 = 13,548 |
| 30일 고정 | 30,000×14/30 = 14,000 | 30,000×14/30 = **14,000** |

**결과**: 2월에는 실제 일수가 비싸고, 31일 달에는 30일 고정이 비싸다. **방향이 달마다 반대다.**

**왜 이렇게 모델링했나**:
- 측정: 분모 규칙으로 1,000건 중 **637건**이 갈리고 최대 차이 **1,714원**.
- 방향이 반대로 갈리니 **"손님에게 유리한 쪽으로"라는 지침으로는 이 결정을 못 한다.** 01번 주차 요금과 같은 모양 — 사업이 정해야 하는 결정이지 개발자가 추측할 결정이 아니다.
- 그래서 boolean 하나(`actualDaysInMonth`)로 정책에 올려, 결정을 바꿔도 코드 한 줄 안 바꾸게 했다.

## 규칙 3 — 전액 상한: 분모를 넘으면 전액으로 막는다

**어떤 요구사항인가**: 요구사항에는 아예 없다. 30일 고정 분모를 골랐을 때만 생기는 파생 문제다.

**예시 입력**: 30일 고정 분모, 1월(31일)을 통째로 사용.

```text
  31일 사용 / 분모 30  =  103%   →  30,000 × 31/30 = 31,000원?!

  chargeFor: used >= denominator 이면 월 요금 전액으로 자른다 → 30,000원
```

**왜 이렇게 모델링했나**: 안 막으면 월 요금보다 많이 청구한다. 변종 검증에서 확인한 세부: 경계(쓴 날 == 분모)에서는 상한을 끊으나 안 끊으나 같다 — 나눗셈이 정확히 1이라서. 상한이 실제로 일하는 곳은 **초과일 때뿐**이다.

## 규칙 4 — 반올림: 건당 1원, 쌓이면 돈이 된다

**어떤 요구사항인가**: 30,000×14/31 = 13,548.38...원. 원 미만을 어쩔 것인가.

```text
  30,000 × 14/31 = 13,548.38...
    버림(DOWN)     13,548
    반올림(HALF_UP) 13,548
    올림(UP)       13,549
```

**측정 결과**: 1,000건에서 버림 합계 9,441,637원 vs 반올림 합계 9,441,945원 — 차이 **308원 = 갈린 건수(308건)와 정확히 같다.** 건당 1원. 한 건만 보면 없는 것과 같고, 10만 건이면 3만 원이다.

**왜 이렇게 모델링했나**: 돈은 `BigDecimal`로 다룬다 — `double`은 0.1을 세 번 더해도 0.3이 아니다. 반올림 방식(`RoundingMode`)도 정책 필드다. null이면 생성자에서 거부한다("반올림 방식을 정해야 한다").

  - *BigDecimal*: 자바에서 돈처럼 정확해야 하는 소수를 다루는 타입. 2진수 근사 없이 10진수 그대로 계산한다.
  - *RoundingMode*: 반올림 방식의 이름표. DOWN(버림)·UP(올림)·HALF_UP(반올림) 등.

## 규칙 5 — 환불은 뺄셈으로 만든다 (이 챕터의 백미)

**어떤 요구사항인가**: "남은 날만큼 돌려드립니다" — 청구와 환불의 합이 월 요금이어야 한다는 불변식이 숨어 있다.

**함정 — 따로 계산하면**:

```text
  1월, 1일~15일, 버림 정책

  청구 = 30,000 × 14/31 = 13,548.38 → 버림 → 13,548
  환불 = 30,000 × 17/31 = 16,451.61 → 버림 → 16,451
  합계                               29,999   ← 1원이 사라졌다!
```

**올바른 처리 — 뺄셈으로 만들면**:

```text
  청구 = 13,548 (한 번만 반올림)
  환불 = 30,000 - 13,548 = 16,452 (뺄셈 — 반올림 없음)
  합계 = 30,000  ✓ 언제나 맞는다
```

**측정 결과**: 따로 계산하면 1,000건 중 **635건**에서 1원이 사라진다. 절반이 넘고, **항상 한 방향이다** — 버림이라 언제나 모자라고 남는 경우는 없다.

**왜 이렇게 모델링했나**: **합이 안 맞는 것은 반올림이 나쁜 게 아니라 두 번 반올림한 것이 나쁜 것이다.** 한 번만 반올림하고 나머지를 뺄셈으로 만들면 오차가 환불 쪽에 몰린다(사라지지 않는다). 오차를 어느 쪽에 몰지는 정책이지만, 사라지게 두는 것만은 안 된다. 대조용으로 `refundByUnusedDays`(직접 계산 판)를 남겨서 둘이 다르면 반올림이 돈을 만들거나 없앤 것임을 보이게 했다.

## 규칙 6 — 여러 달에 걸치면 달마다 따로 일할한다

**예시 입력**: 1/20 ~ 3/10, 월 30,000원, standard 정책.

```text
  1월  1/20 ~ 1/31   11일 / 31   30,000×11/31 = 10,645
  2월  2/1  ~ 2/28   27일 / 28   30,000×27/28 = 28,928
  3월  3/1  ~ 3/10    9일 / 31   30,000× 9/31 =  8,709
                                              ────────
                                                48,282
```

**왜 이렇게 모델링했나**: 기간 전체를 한 번에 일수로 나누면 달마다 일수가 다른 것(특히 2월)이 반영되지 않는다. `monthlyCharges`는 달을 하나씩 돌며 그 달과 기간의 교집합만 잘라 `chargeFor`에 넘긴다. 한 달 안에서 끝나면 한 칸 — 두 칸을 만들면 두 번 청구된다.

## 경계·모서리 케이스

| 함정 | 올바른 처리 |
|---|---|
| 말일(1/31)에 해지하면 전액? | 아니다. 해지일 미포함이면 30/31 = 29,032원. **전액이 되려면 해지일이 다음달 1일**이어야 한다 (04번 체크아웃과 동일) |
| 같은 날 시작·해지 | standard(해지일 미포함)면 0일. 해지일 포함이면 1일 |
| 시작일도 해지일도 안 세는 정책 | 생성자에서 거부 — 하루짜리가 항상 0일(공짜)이 된다 |
| 해지가 시작보다 빠름 | `usedDays`가 IllegalArgumentException |
| 30일 고정 분모 × 31일 달 전체 사용 | 103%가 나온다 → 전액 상한으로 자른다 |
| `usedDays`에 `Math.max(0, days)` 방어 추가 | **지웠다.** 정책 생성자가 이미 막아 도달 불가. 같은 것을 두 곳에서 지키면 정책 쪽 검사를 지워도 이쪽이 덮어버려 안 드러난다. 지우니 변종이 테스트 3개에 잡힌다 |

  - *변종 검증(mutation testing)*: 코드를 일부러 조금 망가뜨려(변종) 테스트가 잡아내는지 보는 검증. 못 잡으면 그 코드는 테스트가 안 지키고 있다는 뜻.

## 핵심 문장

- 요구사항 한 줄("남은 날만큼 돌려드립니다")이 안 정해준 것이 넷(분모·시작일·해지일·반올림)이고 넷 다 금액을 바꾼다 — **그 빈칸을 찾아 정책 값으로 올리는 것이 도메인 모델링이다.**
- 분모 규칙은 달마다 유불리 방향이 반대라서 "손님에게 유리하게"로는 결정할 수 없다 — 사업이 정할 결정을 코드가 추측하면 안 된다.
- **환불은 계산하지 말고 뺄셈으로 만들어라** — 두 번 반올림하면 절반이 넘는 건에서 1원이 사라지고, 항상 모자라는 방향이다.
- 반올림은 건당 1원이라 한 건만 보면 없는 것 같지만 10만 건이면 3만 원이다 — 그래서 돈은 BigDecimal, 반올림은 명시적 정책이다.
- 같은 불변식을 두 곳에서 지키면 한쪽 검사가 죽어도 안 드러난다 — 방어 코드는 도달 가능한 곳에 한 번만.

## 용어 풀이

- **일할 계산(proration)**: 한 달 요금을 쓴 날수 비율로 쪼개는 계산. 요금 × 쓴날/분모.
- **분모(denominator)**: 나눗셈의 아래쪽 수. 여기서는 "한 달 = 며칠"의 답 — 실제 일수(28~31) 또는 30 고정.
- **정책(policy)**: 요구사항이 안 정해준 선택지를 코드의 값으로 올린 것. 바꿔도 계산 코드는 그대로다.
- **record(레코드)**: 자바에서 값 묶음을 선언하는 문법. `ProrationPolicy`는 4개 선택지를 담은 레코드다.
- **BigDecimal**: 정확한 10진 소수 타입. 돈 계산의 기본. `double`은 0.1+0.1+0.1 ≠ 0.3.
- **RoundingMode**: 반올림 방식 — DOWN(버림), UP(올림), HALF_UP(반올림).
- **불변식(invariant)**: 언제나 참이어야 하는 조건. 여기서는 "청구 + 환불 = 월 요금".
- **경계 포함/미포함(inclusive/exclusive)**: 기간의 끝 날을 세느냐 마느냐. 끝을 포함으로 받으면 "한 달을 다 썼다"를 표현할 수 없다.
- **변종 검증(mutation testing)**: 코드를 일부러 망가뜨려 테스트가 잡는지 확인하는 기법. 죽은 방어 코드를 찾아냈다.
- **전액 상한(cap)**: 계산 결과가 월 요금을 넘지 못하게 자르는 규칙. 30일 고정 분모의 103% 문제를 막는다.
