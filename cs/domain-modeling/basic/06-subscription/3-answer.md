### A. 과제 (Subscription.java 의 TODO 1~5)

#### 0. 요구사항 한 줄

- 안 말해주는 것 넷: **① 분모**(그 달 실제 일수 28~31 vs 30일 고정) **② 시작일**(시작한 날을 쓴 날로 세나) **③ 해지일**(해지한 날을 쓴 날로 세나) **④ 반올림**(원 미만을 버리나 올리나).

> **일할 계산(proration)** — 한 달 요금을 실제로 쓴 날수만큼만 나눠서 받는 것.\
> 예: 월 30,000원짜리를 14일만 썼으면 30,000 × 14 ÷ (그 달 일수) 를 받는다.

- 전부 금액을 바꾸는 이유: 분모는 나눗셈의 아래쪽 수, 시작·해지일은 위쪽 수(쓴 날), 반올림은 마지막 1원 — 넷이 각각 계산식의 다른 자리를 건드린다.\
  말투가 아니라 **산수가 달라진다.**
- 올릴 자리: **정책 객체**(`ProrationPolicy` 레코드 4필드).\
  계산 코드(`chargeFor` 등)는 정책을 받아 쓰기만 하므로, 사업이 결정을 바꿔도 계산 코드는 한 줄도 안 바뀐다.

> **정책 객체(policy object)** — 요구사항이 안 정해준 선택들을 한데 모아 값으로 들고 다니는 객체.\
> 예: `ProrationPolicy(분모, 시작일 셈, 해지일 셈, 반올림)` 하나만 바꿔 끼우면 같은 계산 코드가 다른 회사 규정대로 돈다.

- "남은 날만큼"은 **환불 기준** 표현이다.\
  그런데 impl은 청구를 먼저 계산하고 환불을 뺄셈으로 만든다 — 말과 구현의 기준점이 반대라는 것이 규칙 5의 출발점이다.

#### 1. TODO 1 — usedDays

정답 코드 (impl/Subscription.java):

```java
if (end.isBefore(start)) {
    throw new IllegalArgumentException("해지가 시작보다 빠르다: " + start + " -> " + end);
}
long days = end.toEpochDay() - start.toEpochDay();
if (policy.countStartDay()) {
    days++;
}
if (!policy.countEndDay()) {
    days--;
}
return days;
```

- 3/1~3/10, standard(시작 포함·해지 미포함) → **9일.**

```text
  3/1  3/2  3/3  3/4  3/5  3/6  3/7  3/8  3/9  3/10
   ●────────────────────────────────────────○
  시작(셈)                               해지(안 셈)

  차이 = 10 - 1 = 9 → 시작 포함 +1 = 10 → 해지 미포함 -1 = 9
```

- 해지일 포함 정책이면 **10일** (−1을 안 한다).
- 계산 순서: `end - start` 로 날짜 차이를 먼저 구하고 → `countStartDay` 면 +1 → `countEndDay` 가 아니면 −1.\
  두 boolean이 독립적으로 ±1 을 얹는다.
- 둘 다 안 세는 정책을 막는 이유: 하루 쓰고 해지한 사람(3/1~3/1)이 차이 0 → +0 → −1 = **−1일**, 잘 봐줘도 0일이 되어 **공짜**가 된다.\
  그래서 `ProrationPolicy` 생성자에서 `IllegalArgumentException`.
- `Math.max(0, days)` 를 여기 넣으면: 정책 생성자의 검사를 지우는 변종이 **여기서 덮여서 안 드러난다.**\
  같은 불변식을 두 곳에서 지키면 한쪽이 죽어도 티가 안 난다 — 그래서 원본은 이 방어를 **지웠다.**

> **이중 방어(double guard)** — 같은 조건을 두 곳에서 각각 막는 것. 안전해 보이지만 한쪽이 죽어도 티가 안 난다.\
> 예: 정책 생성자와 계산 함수가 둘 다 "0일 이하"를 막으면, 생성자 쪽 검사를 지워도 계산 쪽이 덮어버려 테스트가 통과한다.

- 해지 < 시작: `IllegalArgumentException` 을 던진다(테스트 `reversedDates`).

#### 2. TODO 2 — daysInPeriod

#### 3. TODO 3 — chargeFor

```java
long used = usedDays(start, end, policy);
int denominator = daysInPeriod(month, policy);
if (used >= denominator) {
    return monthlyFee.setScale(0, policy.rounding());     // 전액 상한
}
return monthlyFee
        .multiply(BigDecimal.valueOf(used))
        .divide(BigDecimal.valueOf(denominator), 0, policy.rounding());
```

- 상한이 없으면: 31일 사용 / 분모 30 = **103%** → 30,000 × 31/30 = 31,000원.\
  월 요금보다 많이 청구한다.
- `>` vs `>=` 가 같은 이유: 경계(쓴 날 == 분모)에서는 나눗셈이 **정확히 1** 이라 어차피 월 요금 전액이 나온다.\
  상한을 타든 나눗셈을 타든 결과가 같다.
- 그래도 `>=` 로 쓰는 게 손해가 아닌 이유: 결과가 같으니 **틀릴 수가 없고**, "분모 이상은 전액"이라는 규칙을 코드가 그대로 읽히게 쓴 것이다.\
  실제로 일하는 구간은 초과(>)일 때뿐 — 변종 검증이 그 사실을 확인해줬다.
- 1/1~1/31 standard 가 전액이 아닌 이유: 해지일 미포함이라 쓴 날이 **30일**이다 → 30,000 × 30/31 = **29,032원.**
- 전액이 되려면 해지일이 **2월 1일**이어야 한다.
- 04번 숙박의 **체크아웃 날**과 같다 — 기간의 끝을 포함으로 받으면 "한 달을 다 썼다"를 표현할 방법이 없다.\
  그래서 API 이름에 끝이 포함인지 미포함인지를 드러내야 한다.

> **반열린 구간(half-open interval)** — 한쪽 끝은 포함하고 반대쪽 끝은 빼는 구간.\
> 예: 1/1 시작 1/31 해지는 1/31 을 안 쓴 것으로 봐서 30일이다. 한 달을 다 쓰려면 해지일이 2/1 이어야 한다.

- `double` 을 쓰면: 2진 근사 때문에 0.1을 세 번 더한 값이 0.3이 아니다 — 돈은 `BigDecimal` 로 다루고, 나눗셈에는 반올림 방식을 **명시적으로** 준다(`divide(..., 0, rounding)`).

> **부동소수점(floating point)** — 컴퓨터가 소수를 2진수 근삿값으로 저장하는 방식. 십진 소수를 정확히 담지 못한다.\
> 예: `0.1 + 0.1 + 0.1` 이 `0.3` 이 아니라 `0.30000000000000004` 가 되므로, 돈 계산에는 쓰지 않는다.

#### 4. TODO 4 — refundFor

```java
return monthlyFee.setScale(0, policy.rounding())
        .subtract(chargeFor(monthlyFee, month, start, end, policy));
```

- 불변식: **청구 + 환불 = 월 요금.**\
  언제나.

> **불변식(invariant)** — 프로그램이 도는 동안 언제 확인해도 참이어야 하는 조건.\
> 예: "청구액 + 환불액은 항상 월 요금과 같다" — 이 조건이 깨지면 어딘가에서 돈이 사라졌거나 생긴 것이다.

- 따로 계산하면 (1월 1~15일, 버림):

```text
  청구 = 30,000 × 14/31 = 13,548.38… → 버림 → 13,548
  환불 = 30,000 × 17/31 = 16,451.61… → 버림 → 16,451
                                       ─────────────
  합계                                   29,999    ← 1원이 없어졌다
```

- 그 1원은 **두 번의 버림에 각각 0.38 과 0.61 이 잘려나가** 합계 0.99…가 사라진 것이다.\
  버림은 언제나 아래로만 깎으므로 **남는 방향은 존재할 수 없다** — 항상 모자란다(측정: 1,000건 중 635건).

> **반올림 오차(rounding error)** — 소수점을 잘라내면서 생기는 아주 작은 차이. 여러 번 자르면 그 차이가 쌓인다.\
> 예: 13,548.38 과 16,451.61 을 각각 버리면 0.99 원이 없어져, 둘을 더해도 30,000원이 안 되고 29,999원이 된다.

- 자기 말로: 반올림 자체는 필요하다.\
  문제는 **하나의 총액을 두 조각으로 나누면서 조각마다 반올림한 것.**\
  한 조각만 반올림하고 나머지는 총액에서 빼면 합은 무조건 맞는다.
- 뺄셈으로 만들면 오차는 **환불 쪽**에 몰린다(16,451 → 16,452).\
  어느 쪽에 몰지는 정책이지만, **사라지게 두는 것만은 안 된다.**
- `refundByUnusedDays` 를 남긴 이유: 두 계산이 다르면 **반올림이 돈을 만들거나 없앴다는 신호**다.\
  대조용 자(ruler)를 코드 안에 남겨 불일치를 테스트로 못 박았다(13,548 + 16,451 = 29,999).

> **교차 검산(cross-check)** — 원리가 다른 두 방법으로 같은 값을 구해, 답이 맞는지 서로 대조하는 것.\
> 예: 환불을 "안 쓴 날 × 일요금"으로도 구해 놓고 뺄셈 결과와 비교하면, 1원이 사라지는 순간을 테스트가 바로 잡는다.

#### 6. 측정이 알려준 것

- 분모 규칙: **637/1,000** 이 갈리고 최대 차이 **1,714원.**\
  방향이 달마다 반대.
- 해지일: **1,000/1,000.**\
  하루가 통째로 붙거나 빠지므로 **언제나** 다르다 — 그런데 이것이 요구사항에 안 적히는 대표 항목이다.
- 반올림: 버림 합계 **9,441,637** vs 반올림 합계 **9,441,945**, 차이 **308원** = 갈린 건수 **308건**과 정확히 같다.\
  갈리는 건은 **건당 딱 1원**씩만 차이 나기 때문이다(원 단위 반올림이라 차이는 0 또는 1).\
  10만 건이면 3만 원.
- 환불 따로 계산: **635/1,000** 에서 1원 증발.\
  절반이 넘고, 버림이라 **항상 모자라는 한 방향.**

#### 7. 변종 검증에서 고친 것

- `usedDays` 의 `Math.max(0, days)` 를 **지웠다.**\
  정책 생성자가 이미 그 경우(둘 다 안 셈)를 막고 있어 **도달할 수 없는 코드**였다.

> **변종 검증(mutation testing)** — 코드의 한 줄을 일부러 망가뜨리거나 지우고, 테스트가 그것을 잡는지 보는 것.\
> 예: 정책 생성자의 검사를 지웠는데도 전부 통과하면, 그 검사는 어느 테스트도 보고 있지 않다는 뜻이다.

- 숨는 결함: 같은 것을 두 곳에서 지키면, **정책 쪽 검사를 지운 변종**을 `usedDays` 의 방어가 덮어버려 테스트가 통과한다 — 검사가 죽었는데 조용하다.
- 지우고 나니 그 변종이 **테스트 3개**에 잡힌다.
- 전액 상한의 경계: `쓴 날 == 분모` 에서 나눗셈이 정확히 1 이라 **끊으나 안 끊으나 같은 값** — 그 경계만 바꾸는 변종은 결과를 못 바꾸므로 "동등 변종"이다.\
  상한이 실제로 필요한 것은 **초과일 때뿐.**

> **동등 변종(equivalent mutant)** — 코드를 바꿨는데도 결과가 어떤 입력에서도 달라지지 않는 변종. 테스트가 못 잡는 게 정상이다.\
> 예: `>=` 를 `>` 로 바꿔도 경계에서 나눗셈이 정확히 1이라 값이 같으니, 잡히지 않는다고 테스트가 약한 게 아니다.

- 오차를 청구 쪽에 몰면: (내 추론) 환불이 "안 쓴 날 × 일요금"의 깔끔한 값이 되고 청구가 우수리를 먹는다 → **오차가 회사 쪽으로 간다**(버림 기준이면 청구가 1원 줄어든다).\
  고객 설명은 쉬워지고 매출은 건당 1원씩 준다.\
  중요한 건 방향 선택이지, 어느 쪽이 옳다가 아니다.
- 연 단위 분모: (내 추론) 후보가 셋이다 — 365(또는 윤년 366) / 12개월 × 30 = 360 / "남은 개월 수".\
  여기서도 **분모 결정은 그대로 살아 있고**, 게다가 윤년이라는 새 갈림이 추가된다.\
  이 챕터의 교훈이 그대로 재사용된다.

#### 9. 연결

- **01번 주차 요금**: 요구사항 한 줄이 여러 갈래로 읽히고, **"손님에게 유리하게"라는 지침으로는 결정이 안 되는** 모양이 같다.\
  둘 다 "사업이 결정할 자리"를 코드가 추측하면 안 된다는 교훈.
- **04번 숙박 체크아웃**: 기간의 끝 날을 세느냐 — 체크아웃 날에 안 자듯이 해지일에 안 쓴다(standard).\
  끝을 포함으로 받으면 "다 썼다"를 표현할 수 없다는 구조가 동일하다.
- 도메인 모델링 한 문장: **말로 된 규칙에서 안 정해진 빈칸을 전부 찾아내고, 그 빈칸을 코드의 값(정책)으로 올려서 결정을 사업에 돌려주는 일.**
