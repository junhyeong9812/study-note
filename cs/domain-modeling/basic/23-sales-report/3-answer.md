### A. 과제 (SalesReport.java 의 TODO 1~4)

#### 0. 한 줄 요구사항 — 안 들어 있는 결정

```text
  적혀 있는 것                      적혀 있지 않은 것 (= 내가 정해야 하는 것)
  ───────────────────────────────   ──────────────────────────────────────
  소급 반영 / 당일 반영 둘 다 필요    "언제 기준으로 보는가"(기준일)를 어디서 받나?
  3/1 주문, 3/5 취소의 결과          취소일 당일은 취소인가 아닌가?
                                    취소를 아예 안 빼는 규칙도 필요한가?
                                    주는 무슨 요일에 시작하나?
                                    "매출 0"과 "행이 없음"은 같은가?
```

- **기준일**: 요구사항에 한 글자도 없다.\
  그런데 이게 빠지면 `daily()`가 내부에서 `LocalDate.now()`를 쓰게 되고, **같은 입력에 매번 다른 답**이 나온다 — 테스트도 못 쓰고 과거 재현도 못 한다.\
  impl은 `asOf`를 **인자로 받는 것이 계약**이라고 못 박았다.

> **기준일(asOf)** — "이 날까지 일어난 일만 보고 계산하라"고 밖에서 넘겨주는 시점.\
> 예: 같은 주문 목록이라도 `asOf = 3/4` 면 3/5 취소가 아직 안 보이고, `asOf = 3/6` 이면 보인다.

- **취소일 당일**: 요구사항이 안 말해준다.\
  impl의 `isCancelledAsOf`는 `!cancelledOn.isAfter(asOf)` — **당일 포함**이다.\
  미포함으로 하면 취소한 날 하루 동안 매출이 남고, 그 하루가 마감일이면 마감 수치가 틀린다.

> **경계 포함(inclusive boundary)** — 구간의 끝 값을 그 구간 안으로 셀지 밖으로 뺄지의 선택.\
> 예: 취소일이 3/5일 때 "3/5 기준 조회"에서 이미 취소로 보면 포함, 아직 매출로 남기면 미포함이다.

- **제3의 규칙(IGNORE)**: 요구사항엔 없다.\
  하지만 "총 주문액"은 다른 질문의 답이라 실제로 필요하다 — `enum CancellationRule`이 셋인 이유다.
- **주 시작 요일**: 없다.\
  그래서 `weekly()`가 `DayOfWeek weekStart`를 인자로 **강제**한다.
- **0 vs 행 없음**: impl의 RETROACTIVE는 취소된 주문을 **아예 안 넣는다** — 그래서 그 날짜에 다른 주문이 없으면 키 자체가 없다.\
  테스트도 그걸 인정한다(`retro.isEmpty() || retro.getOrDefault(day(0), 0L) == 0`).\
  즉 "0"과 "없음"을 둘 다 허용하는 계약이다.

> **계약(contract)** — 함수가 "이런 입력에는 이렇게 답한다"고 밖에 약속한 내용.\
> 예: "기준일을 인자로 받는다", "취소일 당일은 이미 취소다" 같은 것 — 테스트가 이 약속을 못 박는다.

- **재현 가능성**: 요구사항에 없다.\
  하지만 `asOf`를 받는 순간 얻어지는 성질이고, 그것을 재는 도구가 `changedPastDays`다.

> **재현 가능성(reproducibility)** — 같은 입력을 다시 넣으면 글자 그대로 같은 결과가 나오는 성질.\
> 예: "3월 3일에 뽑았던 보고서"를 오늘 다시 만들려면 `asOf = 3/3` 으로 부르기만 하면 된다.

#### 1. TODO 1 — daily

```java
Map<LocalDate, Long> result = new TreeMap<>();
for (SalesOrder order : orders) {
    if (order.orderedOn().isAfter(asOf)) {
        continue;                                  // 기준일 이후의 주문은 아직 없는 일
    }
    boolean cancelled = order.isCancelledAsOf(asOf);

    switch (rule) {
        case IGNORE -> result.merge(order.orderedOn(), order.amount(), Long::sum);
        case RETROACTIVE -> {
            if (!cancelled) {                      // 취소면 아예 안 넣는다
                result.merge(order.orderedOn(), order.amount(), Long::sum);
            }
        }
        case ON_CANCEL_DATE -> {
            result.merge(order.orderedOn(), order.amount(), Long::sum);       // 주문일에 +
            if (cancelled) {
                result.merge(order.cancelledOn(), -order.amount(), Long::sum); // 취소일에 -
            }
        }
        default -> throw new IllegalStateException();
    }
}
return result;
```

- 주문일이 기준일보다 뒤면 **건너뛴다**(`continue`) — 그 시점엔 아직 일어나지 않은 일이다.
- 취소 판정은 `order.isCancelledAsOf(asOf)`.\
  기준일을 받는 이유는 **취소가 절대적 사실이 아니라 시점의 함수**이기 때문이다 — 3/5 취소된 주문도 3/4 기준으로는 취소 전이다.

> **시점의 함수(time-dependent value)** — 값이 그 자체로 정해져 있지 않고, "언제 기준으로 보느냐"에 따라 달라지는 것.\
> 예: "이 주문은 취소됐나"는 예/아니오가 아니라 `asOf` 를 넣어야 답이 나오는 질문이다.

- RETROACTIVE는 취소된 주문을 **맵에 넣지 않는다**(주문일에서 뺀 것과 같은 효과).
- ON_CANCEL_DATE는 한 주문을 **최대 두 번** 넣는다 — 주문일에 +금액, 취소일에 −금액.
- IGNORE가 무시하는 것은 **취소 사실 자체**다.\
  그래서 이 값은 "매출"이 아니라 "총 주문액"이다.
- `TreeMap`인 이유: 날짜 순으로 **정렬된 채로** 나와야 일별 그래프·주별 버킷팅이 자연스럽다.\
  `HashMap`이면 순서가 뒤죽박죽이다.

> **TreeMap(정렬된 맵)** — 키를 넣은 순서가 아니라 키 자체의 순서대로 정렬해 보관하는 Map.\
> 예: 날짜를 키로 넣으면 3/1, 3/2, 3/5 순으로 꺼내져서 일별 그래프를 그대로 그릴 수 있다.

- `merge(키, 값, Long::sum)`인 이유: **같은 날 여러 주문**이 있을 수 있고, ON_CANCEL_DATE에서는 같은 날에 +와 −가 함께 떨어질 수도 있다.\
  "없으면 넣고 있으면 더한다"를 한 줄로 쓰는 것이다.

손계산 — 3/1 주문 10,000원, 3/5 취소:

```text
  asOf = 3/11 (이미 취소됨)
    RETROACTIVE      { }  또는 { 3/1: 0 }        ← 3/1 이 사라진다
    ON_CANCEL_DATE   { 3/1: 10,000, 3/5: -10,000 }
    IGNORE           { 3/1: 10,000 }

  asOf = 3/4 (아직 취소 전)
    RETROACTIVE      { 3/1: 10,000 }             ← 같은 날짜, 다른 답!
    ON_CANCEL_DATE   { 3/1: 10,000 }
    IGNORE           { 3/1: 10,000 }
```

#### 2. TODO 2 — weekly

```java
Map<LocalDate, Long> result = new TreeMap<>();
for (Map.Entry<LocalDate, Long> entry : daily(orders, asOf, rule).entrySet()) {
    LocalDate weekOf = entry.getKey().with(TemporalAdjusters.previousOrSame(weekStart));
    result.merge(weekOf, entry.getValue(), Long::sum);
}
return result;
```

- **`daily()`의 결과를 재사용**한다.\
  취소 규칙·기준일 처리를 두 곳에 복사하지 않으려는 것이다 — 한쪽만 고치는 사고를 원천 차단한다.
- 주의 첫날은 `TemporalAdjusters.previousOrSame(weekStart)` — "그 요일이거나, 아니면 그 전에 있는 가장 가까운 그 요일".

> **버킷(bucket)** — 집계할 때 값을 몰아 담는 칸, 그리고 그 칸에 붙은 이름.\
> 예: 주별 집계의 버킷 이름은 그 주의 첫날 날짜여서, 월요일 시작이면 2/23, 일요일 시작이면 3/1 이 된다.

- `previous`를 쓰면: 날짜가 **마침 그 요일일 때 한 주 앞으로 밀린다.**\
  3월 1일(일요일)을 일요일 시작으로 묶으면 2/22 주에 들어가 버린다 — 주 첫날이 자기 주에서 빠지는 셈이다.
- 2026-03-01은 **일요일**이다:

```text
  월요일 시작  3/1 → previousOrSame(MONDAY) = 2/23   (2/23 주 버킷)
  일요일 시작  3/1 → previousOrSame(SUNDAY) = 3/1    (3/1 주 버킷)
```

- 주별 합이 일별 합과 다르면: **어떤 날이 어느 버킷에도 안 들어갔거나 두 번 들어간** 것이다.\
  그래서 테스트가 모든 요일×규칙 조합에서 `weeklySum == total`을 확인한다.

> **불변식(invariant)** — 언제 확인해도 참이어야 하는 조건. 깨지면 어딘가가 틀렸다는 신호다.\
> 예: "주별 합 = 일별 합" — 날짜를 어떤 칸에 담아도 총합은 안 변해야 한다.

- 요일을 상수로 고정하면: **다른 기준을 쓰는 보고서를 못 만든다.**\
  그리고 더 나쁜 것은, 고정한 사실이 안 보여서 두 보고서를 나란히 놓고 "숫자가 왜 안 맞지"를 한참 찾게 된다.

#### 3. TODO 3 — total

```java
long sum = 0;
for (long amount : daily(orders, asOf, rule).values()) {
    sum += amount;
}
return sum;
```

- **`daily()`의 값들**을 더하면 된다.\
  주문 목록을 다시 도는 게 아니라, 규칙 해석은 한 곳(`daily`)에만 둔다.
- RETROACTIVE와 ON_CANCEL_DATE의 total이 항상 같은 이유: 소급은 취소분을 **아예 안 더하고**, 당일은 **+금액과 −금액을 둘 다 더한다** — 후자의 합이 0이다.\
  결국 두 규칙 다 "취소된 주문의 기여 = 0"이다.

> **상쇄(offset)** — 같은 크기의 +와 −가 한 합계 안에서 만나 0이 되는 것.\
> 예: 당일 반영이 3/1에 +10,000, 3/5에 −10,000을 적어도 전체 합계에는 아무것도 안 남는다.

```text
  3/1 주문 10,000(3/5 취소) + 3/2 주문 20,000
    RETROACTIVE     0 + 20,000 = 20,000
    ON_CANCEL_DATE  10,000 - 10,000 + 20,000 = 20,000   ← 같다
    IGNORE          10,000 + 20,000 = 30,000            ← 혼자 다르다
```

- IGNORE만 다른 이유: **음수를 안 넣고 취소분을 그대로 남기기** 때문이다.\
  그래서 이 값은 매출이 아니라 총 주문액이다.

#### 4. TODO 4 — changedPastDays

```java
Map<LocalDate, Long> before = daily(orders, earlier, rule);
Map<LocalDate, Long> after = daily(orders, later, rule);

// daily(earlier) 는 earlier 이후의 날짜를 만들지 않는다.
int changed = 0;
for (LocalDate date : before.keySet()) {
    if (!before.get(date).equals(after.getOrDefault(date, 0L))) {
        changed++;
    }
}
return changed;
```

- 비교 대상: **이른 기준일로 뽑은 보고서**와 **늦은 기준일로 뽑은 같은 날짜의 보고서**.
- `before`의 키를 기준으로 돈다.\
  우리가 묻는 것이 "**전에 보였던 수치**가 바뀌었나"이기 때문이다 — `after`에만 새로 생긴 날짜(그 사이에 일어난 일)는 "과거가 바뀐 것"이 아니라 "새 자료"다.
- `after`에 없으면 **0과 비교**한다(`getOrDefault(date, 0L)`) — RETROACTIVE에서 취소 때문에 키가 통째로 사라지는 경우가 바로 이것이다.
- 미래 날짜를 걸러낼 필요가 없는 이유: `daily(earlier)`가 **애초에 `earlier` 이후의 키를 안 만든다.**\
  주문일은 `isAfter(asOf)`로 걸러지고, 취소일은 `isCancelledAsOf(asOf)`가 참일 때만 들어가는데 그건 취소일 ≤ 기준일이라는 뜻이다.\
  그래서 **도달할 수 없는 코드**라 원본이 지웠다(README "변종 검증에서 고친 것").

> **도달할 수 없는 코드(dead code)** — 어떤 입력을 넣어도 실행되지 않거나, 실행돼도 결과를 못 바꾸는 코드.\
> 예: `daily(earlier)` 가 earlier 이후의 키를 아예 안 만드니, 그 키를 걸러내는 줄은 영원히 아무것도 안 거른다.

> **변종 검증(mutation testing)** — 코드의 한 줄을 일부러 지우거나 망가뜨리고, 테스트가 그것을 잡는지 보는 것.\
> 예: 미래 날짜 필터를 지웠는데 테스트가 전부 통과하면, 그 줄은 죽은 코드이거나 테스트가 약한 것이다.

- ON_CANCEL_DATE에서 항상 0인 이유: 이 규칙은 **과거 날짜의 값을 절대 안 건드린다.**\
  3/1의 10,000은 영원히 10,000이고, 취소는 3/5에 새 행으로 찍힌다.
- 0이 아닌 것은 **버그가 아니라 규칙**이다.\
  소급 반영은 정의상 과거를 고친다.\
  다만 그 사실을 모르면 버그로 보인다 — 그게 이 챕터의 요점이다.

### B. 개념

#### 5. 합계는 같고 날짜별은 전부 다르다 (측정 하나)

```text
  주문 5,000 건, 취소 20 %
  일별 값이 다른 날 │ 90 / 90
  하루 최대 차이    │ 777,000 원
  합계 (소급)       │ 205,154,000
  합계 (당일)       │ 205,154,000   ← 완전히 같다
```

- 일별 값이 다른 날: **90일 전부**. 하루 최대 차이 **777,000원**.
- 합계는 소급·당일 **둘 다 205,154,000원**.
- 총합이 같아지는 이유: 당일 반영의 **+와 −가 상쇄**되어, 결국 두 규칙 다 취소된 주문의 기여가 0이다.
- 실무 위험: 검수를 "합계가 맞나"로만 하면 **규칙이 잘못 구현돼 있어도 통과한다.**\
  일별 그래프를 그리는 순간 전부 다른데, 그때는 이미 배포된 뒤다.

#### 6. 과거가 바뀐다 (측정 둘)

```text
  다시 본 시점 │ 바뀐 날 (소급) │ 바뀐 날 (당일)
  ─────────────┼───────────────┼──────────────
  하루 뒤      │       6       │      0
  일주일 뒤    │      25       │      0
  한 달 뒤     │      25       │      0
```

- 소급: 하루 뒤 **6일**, 일주일 뒤 **25일**, 한 달 뒤 **25일**. 당일: 전부 **0**.
- 61일 중 25일이면 **41퍼센트**.
- "왜 지난달 매출이 바뀌었나요"는 **소급 반영**에서 나온다.
- 일주일 뒤와 한 달 뒤가 같은 이유: 취소가 주문 후 대체로 짧은 기간 안에 일어나서, 일주일이 지나면 **바뀔 것이 이미 다 바뀌었기** 때문이다. (README가 이유를 적어 두진 않았다 — 내 추론.)

#### 7. 취소가 없으면 세 규칙이 같다 (측정 셋)

- 취소율 0%면 **세 규칙의 일별 결과가 전부 같다.**
- 안 도는 코드: **취소 처리 분기 전부** — RETROACTIVE의 `if (!cancelled)`, ON_CANCEL_DATE의 음수 넣기.
- 같은 자리: **14번 사용 취소, 21번 결측 자료**.
- 교훈: **정상 데이터로만 시험하면 규칙 선택이 통째로 안 보인다.**\
  테스트 데이터를 만들 때 "예외 경로가 실제로 도는가"를 먼저 확인해야 하고, 그러려면 취소·결측·환불 같은 비정상 케이스를 **일부러** 섞어야 한다.

> **예외 경로(exception path)** — 정상 흐름이 아니라 취소·결측·실패처럼 가끔만 일어나는 일이 지나가는 코드 길.\
> 예: 취소율 0%짜리 데이터로 시험하면 취소 처리 분기가 한 번도 안 돌아, 규칙이 틀려도 결과가 멀쩡해 보인다.

#### 8. 취소를 안 빼면 부풀려진다 (측정 넷)

```text
  취소율 │    실매출     │    총주문
  ───────┼──────────────┼──────────────
   5 %   │ 240,379,000  │ 252,700,000
  20 %   │ 200,024,000  │ 252,809,000
  50 %   │ 123,870,000  │ 250,119,000
```

- 취소율 50%에서 차이는 **250,119,000 − 123,870,000 = 126,249,000원** — 실매출의 두 배 가까운 수를 매출이라고 보고하게 된다.
- 같은 표에 놓으면 안 보이는 이유: 두 수가 **같은 단위(원)로 나란히** 놓여 있고 이름도 비슷해서, 어느 쪽이 취소를 뺀 값인지 표만 봐서는 구별이 안 된다.\
  총주문은 취소율이 올라가도 거의 안 변해서(252,700,000 → 250,119,000) "안정적인 지표"처럼도 보인다.
- 가르는 한 문장: **"주문은 취소돼도 주문이고, 매출은 아니다."**

#### 9. 주 시작 요일 (측정 다섯)

```text
            │ 버킷 수 │ 최대 주매출
  ──────────┼────────┼─────────────
  월요일 시작│   14   │ 17,255,000
  일요일 시작│   14   │ 17,090,000
```

- 버킷 수는 **둘 다 14**, 최대 주매출은 **17,255,000 vs 17,090,000** — 차이 **165,000원**.
- 버킷 수가 같은 것이 더 위험한 이유: 표의 **줄 수가 같아서 나란히 놓인다.**\
  형태가 같으니 같은 것으로 착각하고 비교하는데, 안의 값이 다르다.\
  줄 수가 달랐다면 즉시 이상하다고 알아챘을 것이다.
- **총합은 같다** — 날짜를 다른 칸에 담았을 뿐 잃어버린 날은 없기 때문이다.

#### 10. 생각해볼 것 (원본 README — 답이 적혀 있지 않다. 아래는 내 추론)

- **어느 것을 기본으로**: 대시보드의 "현재 매출"에는 소급(지금 시점의 진짜 매출), 일별 그래프·운영 리포트에는 당일(과거가 안 바뀜)이 맞다.\
  중요한 것은 화면에 **어느 규칙인지 이름을 적어 두는 것** — 이름이 없으면 보는 사람마다 다르게 해석한다.
- **마감**: 마감은 "이 날짜 이후로는 그 달의 수치를 안 바꾼다"는 선언이다.\
  즉 **마감일을 기준일로 고정해 스냅샷을 저장**해 두고, 마감 후의 취소는 당일 반영으로(다음 달에 음수로) 넣는 방식이 흔하다.\
  소급만 쓰면 마감 자체를 표현할 수 없다.

> **마감(closing)** — 어느 시점의 수치를 확정하고, 그 뒤로는 안 바꾸기로 하는 선언.\
> 예: 3월을 마감했는데 소급 반영을 쓰면 4월에 들어온 취소가 3월 숫자를 다시 고쳐버린다.

> **스냅샷(snapshot)** — 어느 시점의 계산 결과를 그대로 떠서 저장해 둔 것.\
> 예: 마감일을 `asOf` 로 고정해 뽑은 보고서를 저장해 두면, 나중에 취소가 들어와도 그 표는 안 바뀐다.

- **타임존**: `LocalDate`에는 타임존이 없다.\
  어느 나라 자정을 기준으로 날짜를 자를지 정해야 하고(보통 회사의 회계 타임존 하나로 통일), 정하지 않으면 같은 주문이 날짜 경계에서 하루씩 밀린다.

> **타임존(time zone)** — 같은 순간을 나라마다 다른 시각으로 부르는 규칙. 그래서 "날짜"의 경계도 나라마다 다르다.\
> 예: 한국 자정 직후의 주문이 다른 나라 기준으로는 아직 어제라서, 어느 자정으로 자르냐에 따라 하루가 밀린다.

- **부분 취소**: 지금 모델은 `cancelledOn` 하나뿐이라 전체 취소만 표현된다.\
  부분 취소를 세려면 금액이 한 값이 아니라 **취소 이력의 목록**이 되어야 한다(날짜 + 취소 금액).\
  그러면 ON_CANCEL_DATE는 자연스럽게 확장되지만, RETROACTIVE는 "주문일의 금액"을 매번 다시 계산해야 한다.\
  10번의 부분 취소가 여기로 흘러온다.

#### 11. 연결

- **14번·21번과 공유하는 함정**: 예외 경로(사용 취소 / 결측 자료 / 주문 취소)가 없는 데이터로 시험하면 **그 분기가 한 번도 안 돌아서** 설계 결정이 통째로 안 보인다.
- **10번 부분 취소**: 10번 답 참조 — 취소가 "있다/없다"에서 "얼마가, 언제"로 바뀌면 모델이 한 단계 커진다.
- **기준일을 받는 설계**: "그 시점에 이미 일어난 일만 본다"는 시간 의존 계산 전부에 그대로 쓰인다 — 잔액 조회, 포인트 만료, 구독 상태.\
  `now()`를 안에서 부르는 순간 테스트도 재현도 잃는다. (구체적으로 어느 챕터인지는 원본에 명시 없음 — 내 추론.)
