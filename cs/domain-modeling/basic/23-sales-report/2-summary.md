## 한눈에 — 쉽게 말하면

**매출 집계 = 용돈 기입장에서 "환불받은 돈"을 어느 날에 적을까 문제.**

- 3월 1일에 만 원짜리를 샀는데 3월 5일에 환불받았다. 용돈 기입장에 어떻게 적나?
  - **과거를 고친다**: 3월 1일 칸으로 돌아가 지출을 지운다 → "지금 시점의 진짜 지출"이 보인다.\
    대신 어제 본 기입장과 오늘 본 기입장이 다르다.
  - **오늘 적는다**: 3월 1일은 그대로 두고 3월 5일에 +10,000(환불)을 적는다 → "그날 무슨 일이 있었나"가 보인다.\
    과거는 절대 안 바뀐다.
- 매출 집계의 취소도 똑같다.\
  **소급 반영**과 **당일 반영** — 둘 다 필요한 값이고, 어느 쪽도 틀리지 않았다.\
  위험한 건 하나만 만들어놓고 다른 질문에 답하는 것이다.
- 그리고 총합은 두 규칙이 **완전히 같다**(+와 -가 상쇄).\
  그래서 합계만 보면 차이가 안 보이고, 일별 그래프를 그리는 순간 전부 다르다.

```text
  3/1 주문 10,000원, 3/5 취소

            3/1        3/5        합계
  소급        0          -          0     ← 과거가 바뀐다
  당일     10,000    -10,000       0     ← 과거는 그대로, 합계는 같다
  무시     10,000       -       10,000   ← 총주문액 (매출 아님)
```

> **상쇄(offset)** — 같은 크기의 +와 −가 한 합계 안에서 만나 0이 되는 것.\
> 예: 당일 반영이 3/1에 +10,000, 3/5에 −10,000을 적어도 전체 합계에는 아무것도 안 남는다.

실무 예: 이커머스 매출 대시보드, 회계 마감, "왜 지난달 매출이 바뀌었나요?"라는 CS 문의 — 전부 이 규칙 선택에서 나온다.

> 소급은 **"지금 시점의 진짜 매출"**이고 당일은 **"그날 무슨 일이 있었나"**다.
> 둘 다 필요한 값이다. **하나만 만들어놓고 다른 질문에 답하면 어긋난다.**"

## 전체 흐름

```text
daily(주문 목록, 기준일 asOf, 취소 규칙)
  [1] 주문일이 기준일보다 뒤면 건너뜀           ← 기준일까지 일어난 일만
  [2] 취소 여부 = "기준일 시점에 이미 취소됐나" (isCancelledAsOf — 당일 포함)
  [3] 규칙별 반영
        RETROACTIVE     취소면 아예 안 넣음 (주문일에서 뺀 효과)
        ON_CANCEL_DATE  주문일에 +금액, 취소일에 -금액
        IGNORE          취소 무시하고 전부 +금액

weekly = daily 결과를 "주의 시작 요일" 기준으로 버킷에 다시 담기
total  = daily 값들의 합
changedPastDays(earlier, later) = 두 기준일로 각각 뽑았을 때 값이 달라진 날의 수
                                  (0이 아니면 "어제 보고서 ≠ 오늘 보고서")
```

> **기준일(asOf)** — "이 날까지 일어난 일만 보고 계산하라"는 시점. 과거 재현의 열쇠다.\
> 예: `asOf = 3/3` 이면 3/5 취소가 아직 안 보이고, `asOf = 3/6` 이면 보인다 — 같은 주문인데 답이 갈린다.

> **버킷(bucket)** — 집계할 때 값을 담는 칸.\
> 예: 일별 집계는 날짜가 칸이고, 주별 집계는 그 주의 첫날이 칸이다.

## 요구사항 → 코드 구조: 무엇이 무엇으로 변했나

| 말로 된 요구사항 | 코드에서의 모습 |
|---|---|
| "취소를 어느 날에 반영하나 — 정할 문제다" | `enum CancellationRule` 3값 — RETROACTIVE / ON_CANCEL_DATE / IGNORE |
| "날짜가 둘이다: 주문한 날과 취소한 날" | `record SalesOrder(id, orderedOn, cancelledOn, amount)` — cancelledOn은 null 가능 |
| "그 시점엔 아직 취소 전이었다" | `isCancelledAsOf(asOf)` — 취소 여부가 절대값이 아니라 **시점의 함수** |
| "과거를 재현할 수 있어야 한다" | `daily(..., LocalDate asOf, ...)` — 기준일을 인자로 받는 것이 계약 |
| "주별은 시작 요일에 따라 다르다" | `weekly(..., DayOfWeek weekStart)` — 요일을 인자로 강제 |
| "취소가 주문보다 빠를 수 없다" | 생성자 검증 — 잘못된 주문은 만들 수 없다 |

## 규칙 — 기준일(asOf)을 인자로 받는다: "지금"은 계약이 아니다

**어떤 요구사항인가**: 집계는 "기준일까지 일어난 일"만 본다.

예시 입력 — 3/1 주문 10,000원, 3/5 취소 (소급 규칙):

```text
  asOf = 3/3 으로 조회 → 3/5 취소는 아직 미래 → 3/1 매출 10,000  (아직 안 취소됨)
  asOf = 3/6 으로 조회 → 취소 반영             → 3/1 매출 0
  asOf = 주문 전(2/28) → 아무것도 없다          → 합계 0
```

**왜 이렇게 모델링했나**: 기준일을 안 받고 함수 안에서 "지금(now)"을 쓰면 같은 함수가 부를 때마다 다른 답을 낸다 — 테스트를 못 쓰고, "3월 3일에 뽑았던 보고서"를 재현할 수도 없다.\
시간을 인자로 끌어올리면 함수가 순수해진다(같은 입력 = 같은 출력).

> **순수 함수(pure function)** — 같은 입력을 넣으면 언제 불러도 같은 출력이 나오는 함수.\
> 예: 안에서 `now()` 를 부르면 어제와 오늘의 답이 달라져 순수하지 않고, `asOf` 를 인자로 받으면 순수해진다.

## 규칙 — 소급 vs 당일: 총합은 같고 날짜별은 전부 다르다

**어떤 요구사항인가**: 취소된 매출을 주문일에서 뺄 것인가(소급), 취소일에 음수로 적을 것인가(당일).

측정 (주문 5,000건, 취소 20%, 90일치):

```text
  일별 값이 다른 날    90 / 90  (전부!)      하루 최대 차이  777,000원
  합계: 소급 205,154,000 = 당일 205,154,000  (완전히 같다 — +와 -가 상쇄)
```

두 규칙의 성격 대비:

| | 소급 반영 (RETROACTIVE) | 당일 반영 (ON_CANCEL_DATE) |
|---|---|---|
| 답하는 질문 | "지금 시점의 진짜 매출은?" | "그날 무슨 일이 있었나?" |
| 과거 수치 | **바뀐다** — 어제 보고서 ≠ 오늘 보고서 | 안 바뀐다 — 다시 뽑아도 같다 |
| 측정(61일치, 일주일 뒤 재조회) | 25일이 바뀜 (41%) | 0일 |
| 대가 | "왜 지난달 매출이 바뀌었나요" 문의 | "3/1의 진짜 매출"은 뒤의 음수까지 봐야 안다 |

**왜 이렇게 모델링했나**: 소급 반영에서 과거가 바뀌는 것은 **버그가 아니라 규칙이다.**\
그런데 그 사실을 모르면 버그로 보인다.\
둘 다 정당한 답이므로 enum으로 이름 붙여 "어느 질문에 답하는 집계인가"를 호출자가 고르게 했다.

## 규칙 — 취소일 당일에는 이미 취소된 것이다 (경계 포함)

**어떤 요구사항인가**: 3/5에 취소했으면 3/5 기준 조회에서 이미 취소 상태다.

```text
  isCancelledAsOf(3/3) = false    isCancelledAsOf(3/4=취소일) = true    isCancelledAsOf(3/5) = true
  구현: cancelledOn != null && !cancelledOn.isAfter(asOf)   ← "이하"(당일 포함)
```

**왜 중요한가**: 미포함(`isBefore`)으로 하면 취소한 날 하루 동안 매출이 남아 있다.\
그 하루가 하필 **마감일**이면 마감 수치가 틀린다.

> **경계 포함(inclusive boundary)** — 구간의 끝 값을 그 구간 안으로 셀지 밖으로 뺄지의 선택.\
> 예: 취소일 3/5를 "3/5 기준 조회"에서 이미 취소로 보면 포함, 아직 매출로 남기면 미포함이다.

## 규칙 — 주별 집계는 "주의 시작 요일"을 받아야 한다

**어떤 요구사항인가**: 같은 데이터도 월요일 시작 주와 일요일 시작 주에서 다른 버킷에 들어간다.

예시 입력 — 2026년 3월 1일(일요일)의 주문 10,000원:

```text
  월요일 시작:  3/1은 [2/23(월)~3/1(일)] 주의 마지막 날 → 2/23 버킷
  일요일 시작:  3/1은 [3/1(일)~3/7(토)] 주의 첫날      → 3/1 버킷
```

측정: 같은 데이터로 월요일/일요일 시작 주별 집계 → 버킷 수는 14개로 **같은데** 최대 주매출이 17,255,000 vs 17,090,000 — **165,000원 갈린다**(총합은 같다).\
버킷 수가 같으니 표가 나란히 놓이고, 안의 값이 다른 이유는 찾기 어렵다.\
"이번 주 최고 매출" 같은 지표는 요일 규칙 하나로 답이 바뀐다.

불변식: **주별 합 = 일별 합** — 버킷을 어떻게 묶어도 총합은 안 변해야 한다.\
안 맞으면 어떤 날이 어느 버킷에도 안 들어간 것이다.

> **불변식(invariant)** — 언제 확인해도 참이어야 하는 조건. 깨지면 어딘가가 틀렸다는 신호다.\
> 예: "주별 합 = 일별 합" — 날짜를 다른 칸에 담았을 뿐이니 총합은 안 변해야 한다.

## 경계·모서리 케이스

- **함정: 취소 없는 테스트 데이터** → 취소율 0%면 세 규칙의 일별 결과가 **전부 같다.**\
  취소 처리 코드가 한 번도 안 돈다.\
  개발할 때 만드는 데이터에는 예외 경로가 없다 — 21번의 결측 자료, 14번의 사용 취소와 같은 자리다.

> **예외 경로(exception path)** — 정상 흐름이 아니라 취소·결측·실패처럼 가끔만 일어나는 일이 지나가는 코드 길.\
> 예: 취소율 0%짜리 데이터로 시험하면 취소 처리 분기가 한 번도 안 돌아, 규칙이 틀려도 결과가 멀쩡해 보인다.

- **함정: 취소를 안 빼면(IGNORE) 취소율만큼 부풀려진다** → 취소율 50%면 실매출 123,870,000 vs 총주문 250,119,000.\
  "주문 건수"와 "매출"을 같은 표에 놓으면 이 차이가 안 보인다 — 주문은 취소돼도 주문이고, 매출은 아니다.
- **함정: 합계만 보는 검증** → 소급과 당일은 총합이 항상 같아서 합계 비교로는 구현 차이를 못 잡는다.\
  일별 값을 비교해야 한다.
- **생성자 검증**: 빈 주문번호, 금액 ≤ 0, 취소일 < 주문일은 만들 수 없다.
- **죽은 코드 정리(원본 변종 검증)**: `changedPastDays`에서 미래 날짜를 걸러내던 줄을 지웠다 — `daily(earlier)`가 애초에 earlier 이후의 키를 안 만들기 때문에(주문일은 걸러지고, 취소일도 기준일 이하일 때만 들어감) 도달할 수 없는 코드였다.

## 핵심 문장

- 취소 반영은 "빼느냐 마느냐"가 아니라 **"어느 날에서 빼느냐"** 다 — 소급은 "지금의 진짜 매출", 당일은 "그날 일어난 일"이라는 서로 다른 질문에 답한다.
- **총합은 같고 날짜별은 전부 다르다** — 합계만 보는 보고서에서는 두 규칙이 구분이 안 되고, 일별 그래프를 그리는 순간 90일 전부가 갈린다.
- 소급 반영에서 과거 수치가 바뀌는 것(일주일 뒤 41%의 날이 변함)은 버그가 아니라 규칙이다 — 모르고 쓰면 "왜 지난달 매출이 바뀌었나요"가 버그 신고로 들어온다.
- 기준일(asOf)을 인자로 받는 것이 계약이다 — "지금"을 쓰는 함수는 부를 때마다 답이 달라 테스트도 과거 재현도 불가능하다.
- 취소일 당일은 이미 취소이고(경계 포함), 주별 집계는 시작 요일이 계약이다 — 경계 하나가 마감 수치와 "최고 매출" 지표를 바꾼다.

## 용어 풀이

- **집계(aggregation)**: 낱개 기록(주문)을 날짜·주 단위로 묶어 합치는 것.
- **소급 반영(retroactive)**: 취소를 주문한 날로 거슬러 올라가 빼는 것. 과거 수치가 바뀐다.
- **당일 반영(on cancel date)**: 취소를 취소한 날에 음수로 새로 적는 것. 과거 수치가 안 바뀐다.
- **기준일(asOf)**: "이 날까지 일어난 일만 보라"는 시점 인자. 같은 질문을 다른 시점 기준으로 다시 물을 수 있게 한다.
- **과거 재현(reproducibility)**: 예전에 뽑았던 보고서와 똑같은 결과를 다시 만들 수 있는 성질. asOf가 있어야 가능하다.
- **버킷(bucket)**: 집계값을 담는 칸. 주별 집계의 버킷 이름은 그 주의 첫날 날짜다.
- **주의 시작 요일(week start)**: 한 주를 어느 요일부터 세는가. 월요일 시작과 일요일 시작은 같은 주문을 다른 주에 넣는다.
- **상쇄(offset)**: +10,000과 -10,000이 합에서 0이 되는 것. 당일 반영의 총합이 소급과 같아지는 이유.
- **마감(closing)**: 어느 시점의 수치를 확정해 더 이상 안 바꾸기로 하는 것. 소급 반영과 정면으로 충돌하는 개념.
- **enum(열거형)**: 가능한 선택지를 전부 나열한 타입. 취소 규칙 3가지가 "정할 문제"임을 코드로 드러낸다.
- **record**: 값 묶음의 불변 타입. 생성자 검증으로 "취소가 주문보다 빠른" 주문을 차단한다.
- **LocalDate / DayOfWeek**: 자바의 날짜·요일 타입. 시간대 없이 "달력 날짜"만 다룬다.
- **TreeMap**: 키(날짜) 순서로 정렬돼 저장되는 Map. 날짜별 보고서가 순서대로 나온다.
