## 한눈에 — 쉽게 말하면

**재고 차감 = 영화관 좌석 "선택 중" 표시.**

- 영화표를 살 때 좌석을 고르면 결제가 끝나기 전인데도 그 좌석이 **"선택 중"** 으로 잠긴다.\
  결제 중에 남이 같은 좌석을 사가면 안 되니까.
- 재고도 똑같다.\
  결제가 끝나야 재고를 빼는데, 결제 중에 남이 사가면 안 된다.\
  그래서 **예약(잡아둠)** 과 **확정(실제로 나감)** 을 나눈다.
- 안 나누면 둘 중 하나다: 결제 **전에** 빼면 결제 실패한 재고가 사라지고, 결제 **후에** 빼면 초과 판매가 난다.
- 그래서 수량이 **셋**이 된다: 총 재고 / 물리 재고(창고에 실제 있는 것) / 가용 재고(지금 팔 수 있는 것).

```text
  총 재고 100
    예약 10  →  물리 100, 가용 90    창고에서 안 나갔는데 팔 수는 없다
    확정 10  →  물리  90, 가용 90    실제로 나갔다
```

실무 예: 쇼핑몰 재고, 좌석/숙소 예약, 티켓팅 — "확인하고 빼기" 사이에 남이 끼어들 수 있는 모든 판매 시스템.

## 문제 — 이 챕터가 시키는 것

원본 README가 말로 못 박은 요구사항 전부.

> ```
>   총 재고 100
>     예약 10   ->  물리 100, 가용 90     창고에서 안 나갔는데 팔 수는 없다
>     확정 10   ->  물리  90, 가용 90     실제로 나갔다
> ```
> "**수량이 셋이다.** 화면에 무엇을 보여줄지는 또 다른 결정이다."
> "예약과 확정을 나누는 이유는, **결제가 끝나야 재고를 빼는데 결제 중에 남이 사가면 안 되기** 때문이다. 안 나누면 결제 전에 빼서 실패한 재고가 사라지거나, 결제 후에 빼서 초과 판매가 난다."
> "`src/main/java/com/domain/inventory/Inventory.java` 의 TODO 1~4. `StockResult` 는 계약이라 다 주어져 있다."

과제 목록 — 채울 TODO 4개:

| TODO | 메서드 | 말로 된 요구 |
|---|---|---|
| 1 | `available()` | 팔 수 있는 수량 — **예약도 빼야 한다** |
| 2 | `reserve(orderId, qty)` | 예약. 같은 주문 번호면 중복. **중복을 재고보다 먼저** 본다(순서가 계약) |
| 3 | `release(orderId)` | 예약 되돌리기. 없는 예약이면 `UNKNOWN` |
| 4 | `commit(orderId, qty)` | 확정. 예약 단계를 쓰면 예약이 있어야 하고, 안 쓰면 여기서 재고를 본다 |

테스트가 못 박은 계약:

- 재고 100에 10 예약 → 물리 **100**, 가용 **90**. 확정하면 물리 **90**, 가용 90, 예약 **0**.
- 재고 10 전량 예약 → 물리 10, 가용 **0**, 다른 주문의 1개 예약은 `SHORT`.
- 총 재고 음수 · 수량 0 이하는 `IllegalArgumentException`.
- 같은 주문의 두 번째 예약은 `DUPLICATE`, 예약 합계는 안 늘어난다.
- 재고를 다 잡은 뒤 같은 주문이 재전송되면 `SHORT` 가 아니라 `DUPLICATE`(`SHORT.shouldRetry()==true`, `DUPLICATE.shouldRetry()==false`).
- 취소하면 가용이 되돌아오고, 같은 취소를 또 하면 `UNKNOWN`(예외 아님).
- 예약 없이 확정 = `UNKNOWN`, 물리는 안 줄어든다.
- 3개 예약에 5개/1개 확정 = 둘 다 `SHORT`, 예약은 **그대로 남는다**. 3개 확정만 `OK`.
- `reserveBeforeCommit=false` 판: 재고 5에 3 확정 OK → 3 확정 `SHORT` → 2 확정 OK → 물리 0, 초과 판매 0.
- 확정도 두 번째는 `DUPLICATE`, 물리는 안 더 줄어든다.
- `commitTrusting` 으로 재고 3에 5개 빼면 물리 **−2**, 초과 판매 **2**(음수를 막지 않는다).

README가 미리 알려준 함정: ①가용에서 예약도 빼기(안 빼면 같은 재고를 여러 사람에게 팔고, 결제가 다 끝난 뒤에야 드러난다) ②중복을 재고보다 먼저 보기(`SHORT` 는 재시도하라는 뜻이라 무한 재시도가 된다) ③예약 수량과 다른 수량으로 확정 불가(조용히 허용하면 재고가 생기거나 영영 잠긴다) ④물리 재고 음수를 **막지 않는다**(막으면 이미 판 것을 취소해야 한다 — 대신 얼마나 넘겼는지 센다).

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
말로 된 요구사항                          →  코드 구조
────────────────────────────────────────────────────────────
"수량이 셋이다"                           →  physical()=총-확정, reserved()=예약합,
                                             available()=물리-예약
"결제 중에 남이 못 사게 잡아둔다"          →  reserve(orderId, qty) — 주문 번호별 Map
"결제 실패하면 되돌린다"                  →  release(orderId)
"결제 성공하면 실제로 뺀다"               →  commit(orderId, qty) — 예약을 확정으로 전환
"결과가 왜 실패인지 구별해야 한다"         →  enum StockResult {OK, DUPLICATE, SHORT, UNKNOWN}
"재시도 여부는 결과가 알려준다"            →  shouldRetry() = SHORT만 true
"틀린 방식과 비교해 본다"                 →  commitTrusting() (확인 없이 빼는 대조군)
"사고 났으면 크기를 잰다"                 →  oversold() = max(0, 확정-총)
```

## 규칙 1 — 수량 셋: 총 / 물리 / 가용

**어떤 요구사항인가**: "재고가 몇 개냐"는 질문에 답이 셋이다.
화면에 무엇을 보여줄지는 또 다른 결정이다.

**예시 손계산** — 총 100에서 예약 10, 확정 10이 있으면:

| 수량 | 계산 | 값 | 뜻 |
|---|---|---|---|
| 총(total) | 고정 | 100 | 처음 들어온 양 |
| 물리(physical) | 총 − 확정 | 90 | 창고에 실제 있는 양 |
| 가용(available) | 물리 − 예약 | 80 | 지금 팔 수 있는 양 |

**함정: 가용에서 예약을 안 빼면** 같은 재고를 여러 사람에게 판다 — 그리고 그 차이는 **결제가 다 끝난 뒤에야** 드러난다.

> **예약(reservation)** — 아직 창고에서 안 뺐지만 남이 못 사게 잡아두는 중간 상태.\
> 예: 결제 화면에 들어간 손님의 10개는 창고에 그대로 있어서 물리 재고는 안 줄지만, 가용 재고에서는 빠진다.

## 규칙 2 — 예약 → 확정/취소의 생애

```text
              reserve OK                commit OK
  (없음) ────────────────→ 예약됨 ────────────────→ 확정됨
                              │
                              │ release OK
                              ↓
                           (없음)                  ← 재고가 가용으로 돌아온다
```

**reserve의 검사 순서가 계약이다** (impl 기준):

```text
  ① 수량 ≤ 0        → 예외 (잘못된 호출)
  ② 같은 주문 번호?  → DUPLICATE (아무 일도 안 함)   ← 재고보다 먼저!
  ③ 수량 > 가용?     → SHORT
  ④ 통과            → 예약 기록, OK
```

**왜 중복을 재고보다 먼저 보나**: SHORT는 "다시 시도하라"는 뜻이다(shouldRetry). 네트워크가 끊겨 같은 주문이 재전송됐을 때, 이미 잡힌 예약 때문에 재고가 모자라 SHORT를 주면 부르는 쪽은 **무한히 재시도**한다.
DUPLICATE는 "이미 됐다, 다시 하지 마라"다.

**commit의 규칙**:
- 예약 수량과 **다른 수량으로 확정할 수 없다** (10개 예약, 7개 확정 → SHORT). 조용히 허용하면 재고가 허공에서 생기거나 영영 잠긴다.
- 예약이 없으면 UNKNOWN. 이미 확정했으면 DUPLICATE(확정도 한 번만).

**왜 결과를 enum 4종으로 나눴나**: 부르는 쪽의 행동이 다 다르기 때문이다 — OK(진행) / DUPLICATE(이미 됨, 재시도 금지) / SHORT(재시도 또는 품절 안내) / UNKNOWN(버그 또는 잘못된 호출). boolean 하나면 이 구별이 사라진다.

## 규칙 3 — 신뢰 방식(commitTrusting)과의 대조

**어떤 구조인가**: "부르기 전에 available을 확인했으니 여기서는 빼기만 하면 된다" — 실무에서 아주 흔하다.
확인하는 곳과 빼는 곳이 **다른 계층**에 있기 때문이다.

**측정: 동시 주문이 둘만 돼도 초과 판매가 난다** (재고 20, "동시" = 전부 같은 가용 재고를 읽고 그 다음 차례로 차감):

| 동시 주문 수 | 신뢰 방식 초과 판매 | 예약 방식 |
|---|---|---|
| 1 | **0** | 0 |
| 2 | 318 | 0 |
| 5 | 1,324 | 0 |
| 10 | 2,709 | 0 |

> **동시(concurrent)** — 여러 요청이 같은 가용 재고를 읽고 나서 차례로 차감하는 상황.\
> 예: 진짜 병렬이 아니어도, 읽고 나서 쓰기까지 시간이 걸리면 그 사이에 남이 같은 값을 읽어 간다.

- **동시가 1이면 문제가 없다 — 그래서 단위 테스트에서는 절대 안 보인다.**
- 재고가 넉넉해도 안 보인다: 재고 100·동시 3이면 초과 판매 0, 재고 1·동시 10이면 9. **품절 직전에만 나는 결함이고, 품절 직전이 가장 바쁜 때다.**
- 물리 재고가 음수가 되는 것을 코드가 **막지 않는다** — 막으면 이미 판 것을 취소해야 한다.\
  대신 `oversold()`로 얼마나 넘겼는지 세서 알린다.

## 규칙 4 — 예약 취소를 빠뜨리면 (잠긴 재고)

**측정: 재고 100, 주문 200건, 결제 성공률 50%에서**:

| 취소율 | 판매 합계 | 잠긴 재고 |
|---|---|---|
| 100% | 50,000 | 0 |
| 50% | 33,259 | 16,741 |
| 0% | **24,812** | **25,188** |

결제 실패한 예약을 release 안 하면 **화면에는 "품절", 창고에는 물건이 있는** 상태가 된다.
판매가 절반으로 준다.

**잠긴 재고는 초과 판매보다 조용하다**:

| | 누가 알려주나 |
|---|---|
| 초과 판매 | 고객이 주문했는데 물건이 없다 → **고객이 알려준다** |
| 잠긴 재고 | 창고에 있는데 품절로 나온다 → **아무도 안 알려준다** |

같은 조건에서 잠긴 재고 16,741개, 초과 판매 0개 — **지표를 초과 판매만 보면 이 시스템은 완벽해 보인다.**

## 경계·모서리 케이스

- **함정: 재시도를 SHORT로 거부** → 무한 재시도.\
  중복 검사가 재고 검사보다 먼저다.
- **함정: 예약 수량 ≠ 확정 수량을 조용히 허용** → 재고가 생기거나 영영 잠긴다.\
  SHORT로 거부.
- **함정: 없는 예약의 release/commit** → UNKNOWN (OK도 SHORT도 아니다 — 호출 쪽 버그 신호).
- **함정: 음수 재고·0 이하 수량** → 생성자와 reserve/commit이 예외로 거부.\
  단, **초과 판매로 인한 물리 음수는 예외가 아니라 oversold()로 측정** — 이미 판 것을 취소할 수는 없으니까.
- **함정: "우리 재고는 넉넉하다"** → 결함이 안 드러날 뿐 없는 게 아니다.\
  갈리는 조건(품절 직전 + 동시)을 테스트가 직접 만들어야 한다.

## 핵심 문장

- 재고 수량은 하나가 아니라 셋이다 — 총·물리·가용.\
  **가용 = 물리 − 예약**이고, 예약을 안 빼는 순간 같은 물건을 두 번 판다.
- 예약과 확정을 나누는 이유는 "결제가 끝나야 빼는데 결제 중에 남이 사가면 안 되기" 때문 — 안 나누면 재고 증발(선차감)이냐 초과 판매(후차감)냐 중 하나를 고르게 된다.
- 중복 검사는 재고 검사보다 먼저다 — SHORT는 재시도 신호라서, 재시도를 SHORT로 답하면 무한 루프가 된다.
- 확인과 차감이 떨어져 있으면 그 사이가 벌어진다 — 동시 2건이면 이미 초과 판매가 나고, 동시 1건인 단위 테스트는 그것을 절대 못 본다.
- 초과 판매는 고객이 알려주지만 잠긴 재고는 아무도 안 알려준다 — 조용한 실패일수록 지표를 따로 세야 한다.

## 용어 풀이

- **총 재고(total)**: 처음 들어온 전체 수량.\
  확정으로만 줄어드는 기준값.
- **물리 재고(physical)**: 창고에 실제로 있는 수량 = 총 − 확정.
- **가용 재고(available)**: 지금 팔 수 있는 수량 = 물리 − 예약.\
  화면·판매 판단의 기준.
- **예약(reserve)**: 결제 동안 재고를 잡아두는 것.\
  물리는 안 줄고 가용만 준다.
- **확정(commit)**: 실제로 재고가 나가는 것.\
  예약을 소비하며 물리가 준다.
- **취소(release)**: 예약을 되돌려 가용을 복구하는 것.\
  빠뜨리면 재고가 "잠긴다".
- **초과 판매(oversold)**: 창고에 없는 것을 판 수량 = max(0, 확정 − 총). 고객이 알아채는 사고.
- **잠긴 재고**: 실패한 결제의 예약이 안 풀려 팔 수 없게 된 재고.\
  아무도 안 알려주는 사고.
- **StockResult**: 재고 조작 결과 4종 — OK(됨) / DUPLICATE(이미 됨, 재시도 금지) / SHORT(모자람, 재시도 가능) / UNKNOWN(그런 예약 없음).
- **멱등(idempotent)**: 같은 요청을 여러 번 보내도 한 번만 처리되는 성질.\
  주문 번호로 중복을 걸러서 얻는다.
- **check-then-act 틈**: "확인하고 나서 행동"하는 사이에 남이 끼어드는 문제.\
  신뢰 방식(commitTrusting)이 이 틈을 그대로 가진다.
