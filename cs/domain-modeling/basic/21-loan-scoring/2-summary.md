## 한눈에 — 쉽게 말하면

**대출 심사 = 과목별 가중치가 있는 성적표. 어려운 건 계산이 아니라 "빈칸"이다.**

- 학교 성적표를 생각하자.\
  국어 40%, 수학 30%, 영어 20%, 체육 10%처럼 과목마다 중요도(가중치)가 다르고, 점수에 가중치를 곱해 더하면 총점이 나온다.\
  대출 심사도 똑같은 구조다 — 신용 40, 소득 30, 재직 20, 자산 10.

> **가중치(weight)** — 항목마다 "얼마나 중요하게 볼지"를 정한 숫자. 점수에 곱해서 더한다.\
> 예: 신용 40·소득 30·재직 20·자산 10 이면 신용이 자산보다 네 배 무겁게 총점에 들어간다.

- 곱해서 더하는 건 틀릴 것이 없다.\
  진짜 문제는 **시험을 아예 안 본 과목**이다.\
  전학 온 학생(신용 이력이 없는 신파일러, 이직 직후라 소득 증빙이 없는 사람, 국내 기록이 없는 외국인)은 빈칸이 있다.

> **결측(missing) · 빈칸** — 있어야 할 자료가 아예 없는 것. "값이 0"이 아니라 "값 자체가 없음"이다.\
> 예: 신파일러의 credit 칸은 0점이 아니라 빈칸이고, 그 둘을 같게 다루면 신용 90짜리 사람이 36점으로 계산된다.

- **빈칸을 0점으로 볼까, 다른 과목 평균으로 채울까, "채점 불가"로 돌려보낼까** — 이 선택 하나로 승인률이 몇 배씩 갈린다.\
  그리고 "없음"과 "0점"은 다른데, 코드에서는 같아지기 쉽다.

```text
  신청자 성적표          credit  income  employment  assets
  (가중치)               x40     x30     x20         x10
  자료가 다 있는 사람     80      60      50          40    → 계산하면 끝
  신파일러               90      (빈칸)  (빈칸)      (빈칸) → 빈칸을 어떻게 보나?
```

실무 예: 은행·카드사의 신용평가(CSS), 입사 지원 서류 스코어링, 추천 시스템의 결측값 처리 — "데이터가 없는 사용자"를 어떻게 다루느냐는 어디에나 있는 문제다.

## 전체 흐름

```text
decide(신청자) — 순서가 계약이다
  [1] 연체 기록 있나?          → 있으면 INELIGIBLE (결격 — 점수와 무관하게 안 됨)
  [2] 점수를 낼 수 있나?       → 못 내면 UNSCORABLE (심사 불가 — 자료를 더 내면 됨)
        └ 빈칸 정책(MissingPolicy)이 여기서 갈린다
            AS_ZERO     빈칸을 0점으로
            AS_AVERAGE  있는 항목들의 평균으로 (하나도 없으면 UNSCORABLE)
            UNSCORABLE  하나라도 비면 심사 불가
  [3] 점수 ≥ 컷오프(60)?       → 이상이면 APPROVED, 미만이면 REJECTED

점수 = Σ(항목 점수 x 가중치) ÷ 가중치 합   ← 나눠서 항상 0~100으로 정규화
```

> **정규화(normalize)** — 계산 결과를 늘 정해진 범위(여기서는 0\~100)에 들어오게 맞추는 것.\
> 예: 가중치 합이 100이든 4든 그 합으로 나누면 총점은 항상 0\~100이라서, 컷오프 60의 뜻이 안 변한다.

## 요구사항 → 코드 구조: 무엇이 무엇으로 변했나

| 말로 된 요구사항 | 코드에서의 모습 |
|---|---|
| "항목마다 점수가 있는데, 없을 수도 있다" | `Applicant.scoreOf(factor)`가 `Optional<Integer>` 반환 — null이나 0이 아니라 "없음"을 타입으로 |
| "빈칸을 어떻게 볼지는 정책이다" | `enum MissingPolicy` — AS_ZERO / AS_AVERAGE / UNSCORABLE |
| "심사할 수 없으면 점수가 없다" | `scoreOf()`가 `Optional<BigDecimal>` — 심사 불가는 예외도 -1도 아닌 "빈 값" |
| "거절에도 종류가 있다" | `enum Decision` 4값 — APPROVED / REJECTED / INELIGIBLE / UNSCORABLE |
| "자료를 더 내면 달라질 수 있나" | `Decision.canImproveWithMoreData()` — UNSCORABLE만 true |
| "가중치는 0보다 커야 한다" | `record Factor`의 컴팩트 생성자가 `weight <= 0`이면 예외 — 잘못된 값은 애초에 못 만든다 |

## 규칙 — 점수는 가중 평균이다 (가중치 합으로 나눈다)

**어떤 요구사항인가**: 항목 점수에 가중치를 곱해 더하고, **가중치 합으로 나눈다**.

예시 입력 — 표준 설정(credit 40, income 30, employment 20, assets 10 — 합 100), 점수 80/60/50/40:

```text
  80x40 + 60x30 + 50x20 + 40x10 = 3200 + 1800 + 1000 + 400 = 6400
  6400 ÷ 100 (가중치 합) = 64점
```

**왜 나누나**: 안 나누면 총점의 만점이 "가중치 합 x 100"이 되어, 항목을 하나 더할 때마다 컷오프를 손으로 고쳐야 한다.\
고치는 걸 잊으면 아무도 승인이 안 되거나 전부 승인된다.\
나누면 가중치 합이 100이 아니어도 점수는 항상 0\~100이다:

```text
  가중치 a=3, b=1 (합 4),  a=80점, b=40점
  (80x3 + 40x1) ÷ 4 = 280 ÷ 4 = 70점   ← 합이 4여도 0~100 범위 유지
```

반올림은 `RoundingMode.HALF_UP`(반올림)으로 소수점 없이.\
아래 "컷오프에 몰린 사람들"에서 이 반올림 방식이 왜 중요한지 나온다.

## 규칙 — 빈칸 정책 셋: 어느 것도 "안전한 기본값"이 아니다

**어떤 요구사항인가**: 점수가 없는 항목을 만나면 정책에 따라 다르게 처리한다.

예시 입력 — credit만 90점, 나머지 셋은 빈칸:

| 정책 | 계산 | 결과 |
|---|---|---|
| AS_ZERO | (90x40 + 0x30 + 0x20 + 0x10) ÷ 100 | **36점 → 거절** (신용 90인데!) |
| AS_AVERAGE | 있는 항목 평균 = 90 → 빈칸 셋을 90으로 채움 | **90점 → 승인** (자료 하나뿐인데!) |
| UNSCORABLE | 하나라도 비면 점수를 안 냄 | **심사 불가 → "자료를 더 내주세요"** |

- 0점 정책: "정보 없음"을 "최악"으로 본다 → 자료가 원래 없는 신규 고객이 전부 거절된다.
- 평균 정책: "정보 없음"을 "나머지와 비슷하겠지"로 본다 → 자료 하나가 우연히 높으면 그 값이 셋을 채운다.\
  **"중간으로 보자"가 "좋게 보자"로 변한다.**
- 둘 다 틀렸는데 **방향이 정반대다.**\
  그래서 이건 코드 문제가 아니라 업무 결정이고, enum으로 이름 붙여 밖으로 드러낸 것이다.

**측정이 보여준 것** (10,000건 난수 신청자, 원본 MeasurementTest):

```text
  결측 개수별 승인 건수
    결측    AS_ZERO    AS_AVERAGE   UNSCORABLE
     0       4,702       4,702        4,702     ← 자료가 다 있으면 세 정책이 완전히 같다!
     1         938       4,730            0
     2          18       4,674            0
     3           0       4,824            0     ← 평균 정책은 자료가 없을수록 오히려 는다
```

- 결측 0개에서 세 정책이 똑같다는 것이 함정이다 — **테스트 데이터는 대개 다 채워져 있어서, 이 결정이 통째로 안 보인다.**
- 0점 정책은 하나 비면 승인이 1/5(4,702→938), 둘 비면 사실상 전멸(18).
- 평균 정책은 셋이 비어도(자료 하나뿐) 4,824건 승인 — 자료가 다 있을 때보다 **많다**.

## 규칙 — 자료가 하나도 없으면 평균도 못 낸다

**어떤 요구사항인가**: AS_AVERAGE 정책이어도 채울 평균이 없으면 심사 불가다.

예시 입력 — 점수가 하나도 없는 신청자(`Map.of()`), AS_AVERAGE:

```text
  있는 항목 수 = 0  →  평균 = ? (0으로 나누기!)
  원본 구현: averageOfPresent()가 count == 0 이면 null → scoreOf()가 Optional.empty() → UNSCORABLE
  (AS_ZERO 정책은 이때도 0점을 낸다 — 0÷100 = 0점 → 거절)
```

> **0으로 나누기(division by zero)** — 나누는 수가 0이면 답이 정의되지 않아, 자바 정수 나눗셈은 그 자리에서 예외를 던진다.\
> 예: 값이 있는 항목이 하나도 없으면 `sum / count` 의 count 가 0이라 계산이 터진다 — 그래서 미리 null 로 끊는다.

**왜 중요한가**: 0으로 나누는 걸 안 막으면 여기서 터지는데, **그 사람은 우리 시스템을 처음 쓰는 사람이다.**\
첫 고객에게 에러 화면을 보여주게 된다.

## 규칙 — 판정 순서가 계약이다: 결격 → 심사 불가 → 점수

**어떤 요구사항인가**: 연체 기록(결격)을 점수보다 먼저, 그리고 심사 불가보다도 먼저 본다.

> **결격(INELIGIBLE)** — 점수와 상관없이 자격 자체가 안 되는 것. 자료를 더 내도 안 바뀐다.\
> 예: 연체 기록이 있으면 총점이 만점(100점)이어도 결격이다.

> **심사 불가(UNSCORABLE)** — 자료가 모자라 점수를 못 내는 것. 거절이 아니라 "아직 못 잰다"이다.\
> 예: UNSCORABLE 정책에서 항목 하나가 비면 점수를 안 내고 "자료를 더 내주세요"로 안내한다.

예시 1 — 만점인데 연체 기록이 있는 사람:

```text
  점수: (100x40+100x30+100x20+100x10)÷100 = 100점 (만점)
  하지만 hasDefaultRecord = true  →  INELIGIBLE
  순서를 바꾸면? "점수를 더 올리세요"라고 안내하게 된다 — 올려도 안 되는데.
```

예시 2 — 자료도 없고 연체 기록도 있는 사람 (UNSCORABLE 정책):

```text
  결격을 먼저 보므로 → INELIGIBLE
  심사 불가를 먼저 보면? "자료를 더 내주세요"라고 안내하게 된다 — 내도 안 되는데.
```

**왜 이 순서인가**: 각 판정은 신청자에게 "다음에 뭘 하면 되는지"를 안내한다.\
못 고치는 사유(결격)를 고칠 수 있는 사유(자료 부족, 점수 부족)보다 앞에 둬야 안내가 거짓말이 안 된다.\
15번 쿠폰에서 못 고치는 거절 사유를 앞에 둔 것과 같은 판단이다.

## 규칙 — 심사 불가는 거절이 아니다 (결과 4값을 2값으로 뭉개면 안 된다)

**어떤 요구사항인가**: 결과는 승인/거절 2값이 아니라 4값이다.

```text
  APPROVED    승인
  REJECTED    점수가 컷오프 미만        → "점수가 모자랍니다"
  INELIGIBLE  결격 — 점수와 무관        → "신청 자격이 안 됩니다"
  UNSCORABLE  점수를 낼 수 없음         → "자료를 더 내주세요"  ← canImproveWithMoreData() = true
```

**측정**: 결측 1개, UNSCORABLE 정책, 10,000건 → 결격 501 / 심사 불가 9,499 / 승인 0 / 거절 0.\
심사 불가를 거절로 뭉개면 **9,499명이 "점수가 모자랍니다"를 본다** — 실제로는 자료만 더 내면 되는 사람들이다.\
09번(주문 상태), 10번(결제)에서 본 것과 같다: 값을 하나 줄이면 안내가 틀린다.

## 경계·모서리 케이스

- **함정: 컷오프 경계** → 컷오프는 "이상"이다. 59점 거절, 60점 승인.\
  `marginFromCutoff`로 재면 59점은 -1, 60점은 0.

> **컷오프(cutoff)** — 승인과 거절을 가르는 기준 점수.\
> 예: 여기서는 60점이고 "이상"이라서 59점은 거절, 60점은 승인이다.

- **함정: "없음"과 "0점"을 같게 취급** → `Applicant.scoreOf()`가 `Optional`을 반환해서 구별을 강제한다.\
  Map에서 `getOrDefault(k, 0)`으로 꺼냈다면 그 순간 모든 신청자가 조용히 AS_ZERO가 된다.

> **조용한 실패(silent failure)** — 예외도 에러 메시지도 없이 정상처럼 끝나는데 결과만 틀린 것.\
> 예: `getOrDefault(k, 0)` 한 줄이면 정책 설정이 무엇이든 전원 AS_ZERO로 심사되는데, 아무 에러도 안 난다.

- **함정: 점수 범위 밖 값** → `Applicant` 생성자가 0\~100 밖 점수, 빈 id를 거부.\
  `Factor`는 가중치 ≤ 0을, `Scoring`은 빈 항목 리스트를 거부 — 잘못된 값은 만들 수조차 없다.
- **함정: 컷오프에 몰린 사람들** → 측정: 자료가 다 있는 94,904명 중 컷오프 ±1점에 11,103명(11.7%), ±3점에 25,749명(27%).\
  **반올림 방식 하나, 가중치 소수점 하나만 달라져도 1만 명 넘는 사람의 결과가 바뀔 수 있다.**\
  그래서 이 도메인에서는 "어디서 반올림하느냐"가 사소하지 않다.

## 핵심 문장

- 곱해서 더하는 총점 계산은 틀릴 것이 없다 — 이 도메인의 진짜 설계는 **"점수가 없는 항목"을 어떻게 볼 것인가**다.
- "없음"과 "0점"은 다르다 — 그래서 점수는 `Optional<Integer>`이고, 빈칸 처리 방식은 `MissingPolicy`라는 이름 붙은 정책이다.
- 0점 정책과 평균 정책은 둘 다 틀렸는데 **방향이 정반대**다(승인 전멸 vs 자료 없을수록 승인 증가) — "안전한 기본값" 같은 것은 없고, 자료가 다 채워진 테스트 데이터에서는 이 차이가 아예 안 보인다.
- 판정 순서(결격 → 심사 불가 → 점수)가 계약이다 — 못 고치는 사유를 먼저 봐야 신청자에게 거짓 안내를 하지 않는다.
- 가중치 합으로 나눠 정규화하면 항목을 더해도 컷오프를 안 고쳐도 된다 — 그리고 컷오프 ±1점에 12%가 몰려 있으니 반올림 하나가 1만 명을 움직인다.

## 용어 풀이

- **가중치(weight)**: 항목마다 "얼마나 중요한지"를 정한 숫자. 점수에 곱해서 더한다.
- **가중 평균(weighted average)**: (점수x가중치의 합) ÷ (가중치의 합). 가중치 합이 얼마든 결과가 0\~100에 머문다.
- **정규화(normalize)**: 값을 정해진 범위(0\~100)로 맞추는 것. 여기서는 가중치 합으로 나누는 것.
- **결측(missing)**: 있어야 할 자료가 없는 것. "0점"이 아니라 "값 자체가 없음".
- **신파일러(thin filer)**: 신용 이력이 얇은(거의 없는) 사람. 금융 거래 기록이 없어 점수를 매길 자료가 없다.
- **컷오프(cutoff)**: 승인과 거절을 가르는 기준 점수. 여기서는 60점 "이상" 승인.
- **결격(INELIGIBLE)**: 점수와 무관하게 자격이 안 되는 것. 자료를 더 내도 안 된다.
- **심사 불가(UNSCORABLE)**: 자료가 모자라 점수를 낼 수 없는 것. 자료를 더 내면 달라질 수 있다 — 거절이 아니다.
- **Optional**: "값이 있을 수도, 없을 수도 있다"를 타입으로 표현하는 자바 도구. null 대신 써서 "없음" 처리를 강제한다.
- **enum(열거형)**: 가능한 값을 전부 나열해 이름 붙인 타입. `Decision` 4값, `MissingPolicy` 3값처럼 "이것 말고는 없다"를 코드로 못 박는다.
- **record**: 값 묶음을 표현하는 자바의 불변 타입. 생성자에서 검증하면 잘못된 값은 아예 못 만든다.
- **BigDecimal**: 소수점 계산을 오차 없이 하는 자바 타입. 돈·점수처럼 반올림 방식이 중요한 곳에 쓴다.
- **HALF_UP(반올림)**: 5부터 올리는 흔한 반올림. 반올림 방식이 컷오프 근처 1만 명을 움직일 수 있어 명시한다.
