### A. 과제 (Scoring.java 의 TODO 1~4)

#### 0. 한 줄 요구사항 — 안 들어 있는 결정

한 줄 요구사항은 "곱해서 더한다"까지만 말한다.\
나머지는 **전부 내가 정해야 하는 결정**이다.

```text
  적혀 있는 것                적혀 있지 않은 것 (= 내가 정해야 하는 것)
  ─────────────────────────   ──────────────────────────────────────
  항목마다 가중치가 있다       가중치 합으로 나누나? (정규화)
  점수를 곱해 더한다           소수점은 어디서 어떻게 반올림하나?
  점수가 없는 항목이 어렵다     빈칸을 0으로? 평균으로? 심사 불가로?
  "없음"과 "0점"은 다르다       결과는 승인/거절 둘인가, 더 필요한가?
                              연체 기록은 점수 전에 보나 후에 보나?
```

- **나눌지 말지**: 안 나누면 총점의 만점이 "가중치 합 × 100"이 된다.\
  가중치 합이 100이면 만점 10,000, 합이 4면 만점 400이다.\
  컷오프 60은 그때마다 다른 뜻이 된다 — 그래서 나누는 것은 취향이 아니라 결정이다.

> **정규화(normalize)** — 계산 결과를 늘 같은 범위(여기서는 0~100)에 들어오게 맞추는 것.\
> 예: 가중치 합이 100이든 4든 그 합으로 나누면 총점은 언제나 0~100 사이에 있어서, 컷오프 60의 뜻이 안 변한다.

> **컷오프(cutoff)** — 승인과 거절을 가르는 기준 점수.\
> 예: 여기서는 60점이고 "이상"이라서 59점은 거절, 60점은 승인이다.

- **소수점**: 요구사항에 한 글자도 없다.\
  impl은 `divide(총가중치, 0, RoundingMode.HALF_UP)` — 소수 0자리·반올림이다.\
  이 선택이 측정 다섯(컷오프 ±1에 11,103명)과 직결된다.

> **HALF_UP(반올림)** — 버릴 자리가 5 이상이면 올리고 아니면 버리는, 우리가 보통 "반올림"이라 부르는 방식.\
> 예: 59.5점은 60점이 되어 승인으로 넘어가고, 59.4점은 59점이 되어 거절로 남는다.

- **빈칸 처리**: 요구사항은 "어렵다"고만 하지 답을 안 준다.\
  답이 셋(AS_ZERO / AS_AVERAGE / UNSCORABLE)이고 셋 다 실무에서 쓰인다 — 그래서 코드에 `enum MissingPolicy`로 **이름 붙여 밖으로 드러냈다.**

> **결측(missing)** — 있어야 할 자료가 아예 없는 상태. "값이 0"이 아니라 "값 자체가 없음"이다.\
> 예: 신용 이력이 없는 신파일러의 credit 항목은 0점이 아니라 빈칸이다.

> **enum(열거형)** — 가능한 값을 전부 나열해 이름을 붙여 둔 타입.\
> 예: `MissingPolicy` 를 enum 으로 두면 빈칸 처리 방식이 AS_ZERO·AS_AVERAGE·UNSCORABLE 셋뿐임이 코드에 못 박힌다.

- **결과 값 개수**: 요구사항에 없다.\
  승인/거절 둘로는 "왜 안 되나"에 답을 못 해서 넷이 됐다(APPROVED / REJECTED / INELIGIBLE / UNSCORABLE).
- **연체 기록 보는 시점**: 요구사항에 없다.\
  impl은 `decide()` 맨 앞 — 이 순서가 안내 문구의 진실성을 결정한다.
- **"없음"이 "0점"이 되는 한 줄**: `scores.getOrDefault("credit", 0)` 또는 `int s = scores.get(k) == null ? 0 : ...`.\
  이 한 줄을 쓰는 순간 정책 설정이 무엇이든 전원 AS_ZERO다.

#### 1. TODO 1 — totalWeight

```java
public int totalWeight() {
    int sum = 0;
    for (Factor factor : factors) {
        sum += factor.weight();
    }
    return sum;
}
```

- "100 이 아닐 수도 있다"를 적어 둔 이유: 가중치를 **비율**이 아니라 **상대 무게**로 쓸 수 있게 하려는 것.\
  3:1처럼 적어도 되고, 항목을 더해도 가중치를 다시 100에 맞출 필요가 없다.

> **가중치(weight)** — 항목마다 "얼마나 중요하게 볼지"를 정해 둔 숫자. 점수에 곱해서 더한다.\
> 예: credit 40·income 30·employment 20·assets 10 이면 신용이 자산보다 네 배 무겁다.

- 100으로 하드코딩하면: `weightsNeedNotSumTo100` 테스트가 깨진다 — 가중치 3·1(합 4), 점수 80·40일 때 `(80×3+40×1)/4 = 70`이어야 하는데 `280/100 = 3`(반올림)이 나온다.

#### 2. TODO 2 — scoreOf

```java
Integer average = averageOfPresent(applicant);
BigDecimal weighted = BigDecimal.ZERO;

for (Factor factor : factors) {
    Optional<Integer> value = applicant.scoreOf(factor.name());
    int score;
    if (value.isPresent()) {
        score = value.get();
    } else {
        switch (missingPolicy) {
            case AS_ZERO -> score = 0;
            case AS_AVERAGE -> {
                if (average == null) {
                    return Optional.empty();       // 채울 평균이 없다
                }
                score = average;
            }
            default -> {
                return Optional.empty();           // UNSCORABLE
            }
        }
    }
    weighted = weighted.add(BigDecimal.valueOf((long) score * factor.weight()));
}
return Optional.of(
        weighted.divide(BigDecimal.valueOf(totalWeight()), 0, RoundingMode.HALF_UP));
```

- `Optional<BigDecimal>`이 강제하는 것: **"점수가 없다"를 호출하는 쪽이 반드시 다루게** 한다.\
  꺼내려면 `isEmpty()`를 지나야 하므로 심사 불가 경로를 잊을 수 없다.

> **Optional** — "값이 있을 수도, 없을 수도 있다"를 타입으로 적어 두는 자바 도구.\
> 예: `Optional<BigDecimal>` 을 받은 쪽은 값을 꺼내기 전에 비었는지 먼저 확인해야 해서, 심사 불가 경로를 건너뛸 수가 없다.

- 예외로 던지면: 정상 흐름(자료가 모자란 신규 고객)이 오류가 된다 — 예외는 "예외적인 일"에 쓰는 것이고 이건 예외적이지 않다.\
  -1로 돌려주면: -1이 진짜 점수인 척 계산에 섞여 들어가고, 누군가 `score >= cutoff` 앞에서 -1 검사를 잊는다.

> **매직 넘버(sentinel value)** — "없음"이나 "오류"를 뜻하려고 정상 값 자리에 끼워 넣은 특별한 숫자.\
> 예: 심사 불가를 -1로 돌려주면 그 -1 이 진짜 점수처럼 계산에 섞여 들어간다.

- 안 나누면: 항목을 하나 더할 때마다 만점이 커져서 **컷오프를 손으로 고쳐야** 한다.\
  고치는 걸 잊으면 (만점이 커졌으니) 아무도 승인이 안 되거나, 반대 방향이면 전부 승인된다.
- 손계산:

```text
  전부 70점:  70×40 + 70×30 + 70×20 + 70×10 = 2800+2100+1400+700 = 7000
              7000 ÷ 100 = 70점

  80/60/50/40: 80×40 + 60×30 + 50×20 + 40×10 = 3200+1800+1000+400 = 6400
              6400 ÷ 100 = 64점

  가중치 3:1, 80·40:  80×3 + 40×1 = 240+40 = 280
              280 ÷ 4 = 70점          ← 합이 4여도 0~100 유지
```

- AS_AVERAGE인데 점수가 하나도 없으면: `average == null`이므로 **`Optional.empty()`** — 즉 UNSCORABLE.\
  (AS_ZERO였다면 0÷100 = **0점**이 나오고 거절이다. 같은 입력인데 결과가 "심사 불가"와 "0점 거절"로 갈린다.)
- 반올림은 `divide(..., 0, RoundingMode.HALF_UP)` — 소수 0자리, 5부터 올림.\
  이 한 줄이 컷오프 근처 사람들의 운명을 정한다.

#### 3. TODO 3 — averageOfPresent

```java
int sum = 0;
int count = 0;
for (Factor factor : factors) {
    Optional<Integer> value = applicant.scoreOf(factor.name());
    if (value.isPresent()) {
        sum += value.get();
        count++;
    }
}
return count == 0 ? null : sum / count;
```

- `Integer`인 이유: **"평균이 없다"를 표현해야** 하기 때문.\
  `int`면 없음을 0으로 쓸 수밖에 없고, 그러면 "자료 없음"이 다시 "0점"이 된다 — 이 챕터가 막으려는 바로 그 사고다.
- null을 안 지키면: `sum / count`에서 `count == 0` → **ArithmeticException(0으로 나누기)**.\
  그리고 그 사람은 점수가 하나도 없는 사람, 즉 **우리 시스템을 처음 쓰는 사람**이다.\
  첫 고객에게 에러 화면을 보여주게 된다.

> **0으로 나누기(division by zero)** — 나누는 수가 0이면 답이 정의되지 않아 자바 정수 나눗셈은 그 자리에서 예외를 던진다.\
> 예: 값이 있는 항목이 하나도 없으면 `sum / count` 의 count 가 0이라 `ArithmeticException` 이 터진다.

- 분모는 **값이 있는 항목 수**(count)다.\
  전체 항목 수로 나누면 그것 자체가 "빈칸을 0으로 본 평균"이 된다.
- 가중치는 **곱하지 않는다**.\
  여기서 구하는 것은 "빈칸에 꽂아 넣을 대표 점수"라서 단순 평균이다.\
  가중치는 바깥 `scoreOf()`에서 한 번만 곱한다 — 여기서도 곱하면 두 번 곱해진다.
- `sum / count`는 정수 나눗셈이라 **소수점이 버려진다**(90과 61의 평균 75.5 → 75).\
  빈칸을 채우는 값이 그만큼 아래로 깎인다 — 원본 구현이 그렇게 되어 있고, 명시된 요구사항은 아니다.

> **정수 나눗셈(integer division)** — 정수끼리 나누면 소수점 아래가 그냥 버려지는 자바의 계산 규칙.\
> 예: `(90 + 61) / 2` 는 75.5 가 아니라 75 다 — 빈칸을 채우는 값이 0.5점만큼 아래로 깎인다.

if (applicant.hasDefaultRecord()) {

}
Optional<BigDecimal> score = scoreOf(applicant);

```text
  결격?  ──예──▶ INELIGIBLE   "신청 자격이 안 됩니다"        (자료 더 내도 안 됨)
    │아니오
  점수 낼 수 있나? ──아니오──▶ UNSCORABLE  "자료를 더 내주세요"  (더 내면 됨)
    │예
  점수 ≥ 60? ──예──▶ APPROVED / ──아니오──▶ REJECTED  "점수가 모자랍니다"
```

- 봐야 하는 셋: **결격 → 심사 불가 → 점수**.

> **결격(INELIGIBLE)** — 점수와 상관없이 애초에 자격이 안 되는 것. 자료를 더 내도 안 바뀐다.\
> 예: 연체 기록이 있으면 총점이 만점이어도 결격이다.

> **심사 불가(UNSCORABLE)** — 자료가 모자라 점수를 낼 수 없는 것. 거절이 아니라 "아직 못 잰다"이다.\
> 예: UNSCORABLE 정책에서 항목 하나가 비면 점수를 안 내고 "자료를 더 내주세요"로 안내한다.

- 결격을 뒤에 보면: 만점(100점)인 연체자에게 "점수를 더 올리세요"라고 안내한다 — 올려도 안 되는데.\
  (`ineligibleBeatsScore` 테스트: 점수는 100인데 결과는 INELIGIBLE.)
- 결격을 심사 불가보다 뒤에 보면: 자료도 없고 연체도 있는 사람에게 "자료를 더 내주세요"라고 안내한다 — 내도 안 되는데.\
  (`ineligibleBeatsUnscorable` 테스트.)
- 컷오프가 "이상"임은 `cutoffIsInclusive` 테스트가 못 박는다: 59점 REJECTED, 60점 APPROVED — 즉 `>= cutoff`.
- `marginFromCutoff`: 59점 → **-1**, 60점 → **0**. (음수면 모자란 것.)

### B. 개념

#### 5. "없음"과 "0점"

- `getOrDefault(factor, 0)`: 빈칸이 값 0으로 둔갑해 `Optional.isPresent()`가 항상 참이 된다 → `MissingPolicy` 분기가 **한 번도 안 돈다** → 설정이 AS_AVERAGE든 UNSCORABLE이든 전원 AS_ZERO로 심사된다.\
  그리고 이 사고는 에러를 안 낸다.

> **조용한 실패(silent failure)** — 예외도 에러 메시지도 없이 정상처럼 끝나는데 결과만 틀린 것.\
> 예: `getOrDefault(factor, 0)` 한 줄이면 정책 설정이 무엇이든 전원 AS_ZERO로 심사되는데, 아무 에러도 안 난다.

- `Optional<Integer>`가 막는 방식: 값을 꺼내려면 `isPresent()`/`orElse()`를 **반드시 지나야** 한다 — "없음을 어떻게 할지"를 그 자리에서 정하도록 컴파일러가 강제한다.
- DB에서 구별: 점수 컬럼을 `NOT NULL DEFAULT 0`으로 두면 그 순간 구별이 사라진다.\
  **NULL 허용**으로 두거나, 별도의 "자료 있음" 플래그/증빙 레코드를 함께 둬야 한다. (원본에 답이 적혀 있지 않은 "생각해볼 것" — 내 추론.)

#### 6. 결측 정책 셋의 방향 (원본 측정 하나·둘·셋)

```text
  10,000 건 중 승인 건수
  결측 │ AS_ZERO │ AS_AVERAGE │ UNSCORABLE
  ─────┼─────────┼────────────┼───────────
    0  │  4,702  │   4,702    │   4,702     ← 세 정책이 완전히 같다
    1  │    938  │   4,730    │       0
    2  │     18  │   4,674    │       0
    3  │      0  │   4,824    │       0
```

- 결측 0개에서 셋이 같은 것이 함정인 이유: **테스트 데이터는 대개 다 채워져 있다.**\
  그래서 결측 처리 코드가 한 번도 안 돌고, 이 결정이 통째로 안 보인 채 배포된다.\
  (결측 0개에서는 세 정책 전부 승인 4,702 / 거절 4,767 / 결격 531로 동일.)
- 결측 1개에서 AS_ZERO 승인: 4,702 → **938** (약 1/5).
- 결측 2개 **18건**, 3개 **0건** — 사실상 전멸.
- AS_AVERAGE가 결측 3개(자료 하나뿐)에서 4,824건으로 **오히려 느는** 이유: 남은 자료 하나가 우연히 높으면 **나머지 셋이 전부 그 높은 값으로 채워진다.**\
  낮으면 떨어지지만, 높은 쪽이 컷오프를 넘기는 효과가 더 커서 전체 승인 수가 는다.
- "중간으로 보자"가 "좋게 보자"로: 채우는 값이 **모집단 평균이 아니라 그 사람의 남은 항목 평균**이기 때문이다.\
  자료가 적을수록 그 한 값이 총점 전체를 지배한다.
- "안전한 기본값이 없다": 두 정책이 **정반대 방향으로** 틀린다(승인 전멸 vs 승인 증가).\
  어느 쪽도 "일단 이걸로 두면 무난"이 아니고, 그래서 코드가 아니라 **업무 결정**이다.

#### 7. 결과를 넷에서 둘로 뭉개면 (원본 측정 넷)

- 결측 1개·UNSCORABLE·10,000건: 결격 **501** / 심사 불가 **9,499** / 승인 **0** / 거절 **0**.
- 뭉개면: **9,499명**이 "점수가 모자랍니다"를 본다 — 실제로는 자료만 더 내면 되는 사람들이다.
- `canImproveWithMoreData()`가 true인 것은 **UNSCORABLE 하나뿐**. REJECTED는 false다.
- 같은 자리: **09번 주문 상태, 10번 결제** — 상태/결과 값을 줄이면 "지금 무엇을 하면 되는지"를 말할 수 없게 된다.

#### 8. 컷오프 경계 (원본 측정 다섯)

```text
  자료가 다 있는 94,904 명
  컷오프 ±1 점 │ 11,103 명 (11.7 %)
  컷오프 ±3 점 │ 25,749 명 (27 %)
```

- ±1점 **11,103명(11.7%)**, ±3점 **25,749명(27%)**.
- 1점 차이로 1만 명이 바뀌는 이유: 점수 분포가 컷오프 근처에 두껍게 몰려 있다.\
  (원본 README는 "점수를 60에 맞추도록 상담하기 때문"이라고 경계 집중의 이유를 적어 뒀다.)

> **경계 집중** — 사람들의 값이 기준선 바로 근처에 몰려 쌓이는 현상.\
> 예: 컷오프를 60으로 두고 거기에 맞춰 상담하면, 점수가 59~61에 두껍게 몰린다(±1점에 11,103명).

- 반올림이 사소하지 않은 이유: 0자리 HALF_UP 대신 버림(FLOOR)을 쓰면 59.5~59.9인 사람들이 통째로 거절로 넘어간다 — 규칙 한 줄이 1만 명 규모의 결과를 옮긴다.

#### 9. 생각해볼 것 (원본 README — 답이 적혀 있지 않다. 아래는 내 추론)

- **항목마다 다른 결측 정책**(신용은 심사 불가, 자산은 0점): 장점은 "없으면 심사 못 하는 항목"과 "없어도 그냥 낮게 보면 되는 항목"을 구별할 수 있다는 것.\
  어려워지는 것은 정책이 `MissingPolicy` 한 개가 아니라 `Factor`마다 붙어야 하고(`record Factor(name, weight, missingPolicy)`), 조합 수가 늘어 측정·설명이 복잡해진다.
- **DB 구별**: 5번 답 참조 — NULL 허용 또는 "자료 수집 여부"를 별도 사실로 기록.
- **컷오프 12퍼센트**: 경계 밴드(±1점)를 자동 판정에서 빼고 사람이 다시 보는 "보류(manual review)" 값을 하나 더 두는 방법이 있다.\
  결과 enum이 다섯이 되는 셈이고, 이 챕터의 "뭉개지 말라"와 방향이 같다.
- **점수 공개**: 알려주면 신청자가 컷오프에 맞춰 행동을 조정한다(상담·서류 보강).\
  좋은 면은 "무엇을 하면 되는지"가 분명해지는 것, 나쁜 면은 점수를 올리기 위한 역이용과, 공개한 점수가 곧 규칙이 되어 가중치를 바꾸기 어려워지는 것.

#### 10. 연결

- **15번 쿠폰**: 못 고치는 거절 사유를 고칠 수 있는 사유보다 앞에 두는 것 — 여기 판정 순서(결격 먼저)와 정확히 같은 판단이다.
- **09번 주문 상태·10번 결제**: 값을 줄이면(상태를 뭉개면) 안내가 틀린다 — 여기서는 UNSCORABLE을 REJECTED로 뭉개는 것으로 다시 나타난다.
- **정책을 enum으로 드러내기**: 이 저장소에서 "선택지가 여럿이고 어느 것도 기본값이 아닐 때 이름을 붙여 밖으로 꺼낸다"는 같은 수법이다. (구체적으로 어느 챕터인지는 원본에 명시 없음 — 내 추론.)
