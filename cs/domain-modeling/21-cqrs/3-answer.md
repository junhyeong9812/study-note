# domain-modeling/21-cqrs — 정답

## 정답

### 1. 한 모델의 충돌, CQRS vs CQS

- 쓰기 모델은 작고 엄격해야 한다(애그리거트 경계·불변식·정규화). 조회는 넓고 비정규화돼야 편하다(조인·검색·정렬). 한쪽에 맞추면 다른 쪽이 나빠진다 — 조회마다 조인이 늘거나, 엔티티에 화면용 필드가 붙는다.
- CQS(Meyer): **메서드**를 명령(상태 변경)과 조회(값 반환)로 나눈다. CQRS: 갱신 모델과 조회 모델을 따로 둔다(Fowler 2011). 이름(Command·Query)은 CQS 어휘를 따랐다고 Fowler가 적는다. "CQS를 **모델** 단위로 키운 것"은 흔한 해석이다.

### 2. 구조

```text
  명령 → 핸들러 → [쓰기 모델 + events]  (한 트랜잭션)
                        │ seq
                        ▼
                 프로젝터 ── [order_view + checkpoint]  (한 트랜잭션)
                                   ▲
  조회 → 핸들러 ────────────────────┘
```

- 체크포인트는 뷰 갱신과 같은 트랜잭션에 둔다. 따로 두면 뷰와 위치가 어긋나 이벤트를 두 번 반영하거나 건너뛴다.

### 3. 폴드의 두 능력과 전제

- 재구축: 빈 뷰에서 처음부터 다시 접으면 같은 뷰가 나온다 → 뷰는 버려도 되는 파생본.
- 대조: 라이브 뷰와 재구축 뷰(또는 쓰기 모델)를 `EXCEPT`로 비교해 차이를 행 단위로 찾는다.
- 전제: `apply`가 결정적(현재 시각·외부 조회 없음)이고, 이벤트가 빠짐없이 순서대로 들어온다.

### 4. 시퀀스 구멍

- 생긴다. 실험에서 1,000건 중 25건이 영영 없었다(집필 3회 + 재실행 3회에서 14~25건). 프로젝터를 더 돌려도 회복되지 않았다.
- 이유: seq는 할당 순서이지 커밋 순서가 아니다. seq 41을 받은 트랜잭션이 42보다 늦게 커밋하면, 프로젝터는 42만 보고 checkpoint를 42로 옮긴다. 이후 41은 `seq > 42`에 걸리지 않는다. PostgreSQL 17 문서도 시퀀스 값에 구멍이 생길 수 있다고 적는다.
- advisory lock으로 붙이기를 커밋까지 직렬화하면 0건. 대가는 쓰기 처리량 상한.

### 5. 쓰기 직후 조회

- 그냥 읽기: 100/100 없음.
- 토큰 대기: 0/100 없음, 대기 p50 46ms·max 56ms(폴링 주기 근처).
- 대가: 조회가 느려진다. 프로젝터가 멈추면 상한까지 기다리므로 "반영 중" 표시나 쓰기 모델 대체 경로가 필요하다.

### 6. 프로젝터 버그 찾기·고치기

- 찾기: 고친 프로젝터로 새 뷰를 처음부터 재구축하고 라이브 뷰와 양방향 `EXCEPT`. 실험에서 양방향 30행 = 취소 30건. 또는 뷰 vs 쓰기 모델 대조.
- 고치기: 새 뷰를 끝까지 재구축 → 쓰기 모델과 대조 0 확인 → 조회를 새 뷰로 전환 → 옛 뷰 삭제. 제자리 수정은 하지 않는다.

### 7. Fowler의 경고

- "대부분의 시스템에서 CQRS는 위험한 복잡도를 더한다." 그리고 시스템 전체가 아니라 특정 부분(Bounded Context)에만 쓰라.
- 필드 하나 추가: CRUD는 테이블·조회 쿼리. CQRS는 쓰기 테이블, 이벤트 페이로드, 프로젝터 `apply`, 뷰 테이블, 조회 쿼리, 그리고 기존 뷰 재구축(이 노트 예시 코드 기준).

### 8. 두 종류의 "목록에 없음"

- 새로고침하면 보임: 지연. `max(events.seq) - checkpoint`(지연 이벤트 수)가 0보다 크고 시간이 지나면 0으로 돌아온다.
- 영영 안 보임: 누락. 체크포인트보다 작은 seq인데 뷰에 없는 주문을 찾는 쿼리, 또는 뷰 vs 쓰기 모델 `EXCEPT`에 행이 남는다. 시퀀스 구멍이나 프로젝터 버그를 의심한다.

### 9. CDC가 유실·순서를 보장하지 못하는 조건

- 논리 복제 슬롯이 삭제되거나, `max_slot_wal_keep_size`보다 뒤처져 필요한 WAL이 지워지면 그 사이 변경을 받지 못한다.
- 순서는 DB 커밋 순서까지다. 브로커에 들어간 뒤에는 파티션 단위로만 순서가 유지된다.

### 10. 도입 전에 정할 것

- 조회가 쓰기와 정말 다른 모양인가(아니면 하지 않는다).
- 화면별 허용 지연, 특히 지연 0이 필요한 화면(토큰·대체 경로).
- 변경 흐름(outbox 또는 CDC)과 순서 보장 방법, 그리고 재구축·대조 절차.
