# domain-modeling/25-reconciliation — 정답

## 정답

### 1. 균형이 맞아도 대사가 필요한 이유

- 차대 균형은 **우리 장부 안**의 일관성이다. 바깥 세계(실제 돈의 이동)와 일치하는지는 말해주지 않는다.
  - PG는 승인했는데 우리 쪽에 전표가 없으면, 우리 원장은 균형이 맞은 채로 틀렸다.
- 타임아웃은 실패가 아니라 "모름"이다. 우리 쪽 정보만으로는 확정할 수 없다.
- 대사는 외부 장부 전체를 보고 그 모름을 확정한다. 커리큘럼의 표현대로 "결과를 모르는 요청의 최종 확정 경로"다.

### 2. 흐름과 금지 사항

```text
  적재 ─► 키 맞추기 ─► 분류 ─► 사건 기록 ─► 처리
```

| 단계 | 하지 말 것 |
|---|---|
| 적재 | 외부 파일을 고쳐서 넣기(원본·줄 번호를 남긴다) |
| 키 맞추기 | 금액·시각을 키로 쓰기, 양쪽 날짜 경계를 다르게 자르기 |
| 분류 | "다름" 하나로 뭉치기(누락·중복·금액·상태를 나눈다) |
| 사건 기록 | 기록 없이 바로 고치기 |
| 처리 | 원장 전표를 UPDATE로 고치기(조정 분개로 한다), 모든 분류를 자동 보정하기 |

### 3. 키와 비교 값

- 키: 두 장부의 줄을 짝짓는 식별자 — 주문 ID(우리가 PG에 보낸 것), PG 거래 ID(PG가 돌려준 것).
- 비교 값: 짝지은 뒤 같은지 보는 값 — 금액, 상태, 승인 시각.
- 타임아웃이면 거래 ID를 못 받는다. 그래서 주문 ID를 요청에 싣는 것이 중요하다.
- 키가 없으면 금액·시각으로 붙이게 된다. 같은 금액 후보가 여럿이면 합은 맞고 짝은 틀린다.
  - [advanced/18-settlement-match](../advanced/18-settlement-match/2-summary.md)의 측정: 금액 매칭이 6,000줄 중 2,893줄을 엉뚱하게 붙였다.

### 4. 세 방식의 차이 (PostgreSQL 17.11 실험)

| 방식 | 찾는 것 | 놓치는 것 |
|---|---|---|
| ① 총액 비교 | "다르다"(5,581,182 vs 5,598,055) | 어느 줄인지, 서로 상쇄된 차이(⑦ O606·O607: 16,057 = 16,057) |
| ② `EXCEPT` | 같은 (주문, 금액)이 없는 줄 | 이중 승인(O303), 차이의 종류 |
| ③ 분류 FULL OUTER JOIN | 주입한 7가지 전부(8줄), 종류별 분류 | (접는 단계를 빼면 중복을 놓친다) |

- O303이 `EXCEPT`에 없었던 이유: `EXCEPT`는 `ALL` 없이 쓰면 중복을 지운다(PostgreSQL 17 문서 7.4). 외부의 (O303, 2651) 두 줄이 하나가 되어 내부 한 줄과 상쇄됐다.
- `EXCEPT ALL`이면 O303 한 줄이 남는다(실험). 그래도 "중복"이라는 분류는 알려주지 않는다.

### 5. 중복을 먼저 보는 이유

- O303: 내부 금액 2,651, 외부를 주문 단위로 접은 합 5,302.
- 금액 비교를 먼저 하면 AMOUNT_MISMATCH로 분류된다. 담당자는 반올림·할인을 의심한다.
- 실제 원인은 승인 두 번(T303, T303-dup)이다. 처리도 "중복분 PG 취소 + 고객 안내"로 다르다.
- 그래서 `count(*) > 1`을 금액 비교보다 앞에 둔다.

### 6. 날짜 경계 실험

- KST vs UTC로 다르게 자르면: 내부 1,000건, 외부 625건, 내부에만 376건, 외부에만 1건.
  - 9시간(KST 00:00~09:00 = UTC 전날 15:00~24:00)치가 외부 파일의 UTC 10-02에 들어가지 않았다.
  - 376건 중 1건(O202)은 진짜 누락이다. 가짜 차이는 375건이고, 진짜 차이가 그 속에 묻힌다.
- 같은 기준(`[10-01 15:00Z, 10-02 15:00Z)`)으로 자르면: 1,000 vs 1,000, 차이는 주입한 2건(O202 누락, X001)뿐.

### 7. 타임아웃 확정의 두 단계

| 단계 | 방법 | 장점 | 단점 |
|---|---|---|---|
| 1단계(분 단위) | PG 조회 API(예: 토스페이먼츠 `GET /v1/payments/orders/{orderId}`) | 빠르다, 건별 | 조회도 타임아웃날 수 있다, 건마다 호출 |
| 2단계(일 단위) | 대사(외부 파일 전체와 맞춤) | 외부 장부 전체를 본다, 조회로 못 정한 것까지 | 늦다(다음 날), 파일 형식·경계에 의존 |

- 멱등키 재시도는 같은 키로 저장된 결과를 받는 길이다. 하지만 키 보존 기간이 유한하다.
  - Stripe 문서: 키는 최소 24시간 뒤 정리될 수 있고, 정리된 뒤 같은 키를 쓰면 새 요청으로 처리된다.
- 그 기간을 넘긴 재시도, 키를 지원하지 않는 외부 시스템, 재시도 자체가 실패하는 경우는 조회·대사로 확정한다.

### 8. 차이 0건인데 설명 없는 조정

- 무엇이 잘못됐나: 차이를 발견 즉시 내부를 외부에 맞춰 덮어썼다. 지표는 깨끗했지만 원인(우리 반올림 버그, PG 오류)이 지워졌다.
- 자동 처리 범위: 원인이 정해진 분류만. 실험에서는 RESOLVE_UNKNOWN(외부 승인 + 금액 일치)만 자동 확정했다.
- 나머지는 사건(recon_break)으로 OPEN 상태로 남기고, 사람이 원인을 보고 근거 문장이 붙은 조정 분개로 처리한다.
- 같은 원인이 반복되면 원인 수정 작업으로 올린다.

### 9. 매일 상쇄되는 차이

- 첫 의심: 날짜 경계(시간대 또는 기준 날짜 — 매출일 vs 지급일)가 양쪽에서 다르다.
- 확인:
  - 차이 줄의 시각 분포를 본다. 특정 시간대(예: KST 00~09시)에 몰리면 경계 문제다.
  - 외부 문서로 날짜 기준을 확인한다. Stripe 보고서는 시간대를 지정하지 않으면 UTC다. 토스페이먼츠 정산 조회는 `dateType`으로 `soldDate`·`paidOutDate`를 고른다.
- 대처: 내부 추출을 외부와 같은 `timestamptz` 반열린 구간으로 자른다. 경계 근처는 하루 겹쳐 가져와 키로 맞춘 뒤 기간 귀속을 따로 판단한다.

### 10. 원장 반영과 감시

- 원장 반영: 원 전표를 고치지 않는다. 조정 분개(필요하면 역분개 + 재분개)를 넣고, 대사 사건을 근거로 가리킨다. 차대 합 0도 그대로 지킨다.
- 감시 이유: 외부 파일이 안 오거나 배치가 실패하면 "차이 0건"처럼 보인다. 대사가 안 돈 것과 차이가 없는 것은 결과가 같아 보인다.
  - reliability/04 카탈로그 F-21의 대처가 "대사 + 대사가 도는지 감시"다.
  - 그래서 처리 건수(MATCHED 수 포함)와 실행 여부를 지표로 낸다.
