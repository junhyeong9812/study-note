# POJO — 정답

## 정답

**1. (연결)** POJO는 **반대 개념(EJB)에서 태어난 말**이라 "무엇인가"보다 "무엇이 아닌가"가 핵심이다.\
반대 개념은 EJB(Enterprise JavaBeans)로, ① 프레임워크 인터페이스를 구현해야 해서 컨테이너 없이는 실행도 테스트도 불가능하고 ② 비즈니스 로직이 프레임워크 코드에 파묻히며 ③ 프레임워크를 바꾸면 전부 다시 써야 하는 것이 문제였다.

**2. (판단)** 판정 질문 하나는 "**이 클래스를 `main()`에서 `new`로 만들어 (컨테이너·서버·프레임워크 없이) 테스트할 수 있는가?**"다.\
이 하나로 충분한 이유는 POJO의 본질이 getter/setter 유무 같은 **형태 규칙이 아니라 "무엇에도 종속되지 않는다"는 종속성 기준**이기 때문이다 — `new`로 돌아가면 종속이 없는 것이다.

**3. (경계)** POJO는 **종속성 기준**(프레임워크에 안 묶임, 형태 규칙 없음), JavaBean은 **형태 기준**(기본 생성자 + private 필드 + getter/setter + `Serializable`을 갖춘, 도구가 리플렉션으로 다루기 위한 규격)이다.\
둘은 서로를 함의하지 않는다 — JavaBean이면서 POJO인 경우가 대부분이지만, getter/setter가 하나도 없어도 POJO이고(오히려 불변 객체가 더 좋은 POJO), 형태를 갖췄다고 종속이 없는 것도 아니다.

**4. (경계)** "로직 없는 데이터 덩어리"는 오해다. POJO의 원래 취지는 정반대인 "**평범한 객체에 비즈니스 로직을 담자**"였다.\
그 오해를 실제로 구현하면 — 로직을 다 빼고 getter/setter만 남기면 — **빈약한 도메인 모델**(Anemic Domain Model)이라는 안티패턴이 된다.

**5. (왜)** 가장 큰 이득은 **테스트 용이성**이다.\
프레임워크 컨텍스트 로딩(수 초~수십 초)이 필요 없이 `new`로 만들어 즉시 검증하니 테스트가 밀리초 단위로 끝나고, **테스트가 그렇게 빨라야 개발자가 실제로 돌리기** 때문이다.

**6. (연결)** 모순이 아니다 — **스프링의 존재 이유 자체가 "POJO에 엔터프라이즈 기능을 주는 것**"이었다.\
스프링은 IoC(제어의 역전)와 AOP(프록시)로, 객체는 평범한 상태로 두고 트랜잭션·보안 같은 부가 기능을 **바깥에서 감싼다**. 그래서 코드 어디에도 스프링 API 호출이 없이 POJO가 유지된다.

**7. (예측)** `@Transactional`은 원본 객체를 감싼 **프록시**로 동작하는데, 같은 클래스 내부에서 `this.method()`를 부르면 프록시를 우회해 원본을 직접 호출하므로 트랜잭션이 안 걸린다(self-invocation).\
이 함정은 POJO를 유지하는 방식과 직결된다 — 객체를 침투 없이 두기 위해 부가 기능을 프록시로 얹은 **대가**로 생긴 대표적 함정이다.

**8. (판단)** `@Entity`가 POJO인지는 **의견이 갈린다**(상속·구현이 없고 `new`로 테스트 가능하니 POJO다 vs `jakarta.persistence`에 대한 컴파일 타임 의존이 생기니 아니다).\
이분법 대신 **침투 정도(invasiveness)의 스펙트럼**으로 보는 게 유용하다. 최종 판단 기준은 **"테스트할 수 있는가"** — 애노테이션이 붙어도 `new`로 만들어 로직을 테스트할 수 있으면 POJO의 실질적 이득은 유지된다.

**9. (경계)** record는 **불변이고 기본 생성자가 없기** 때문에 JPA 엔티티로 못 쓴다.\
JPA는 프록시·더티 체킹을 위해 **기본 생성자와 가변 필드**가 필요한데 record는 둘 다 없다 — 그래서 record는 경계 바깥(DTO·VO)에 두고 영속화 엔티티는 별도 클래스로 두는 분리가 자연스럽다.

**10. (예측)** 모든 필드에 setter를 열면 객체가 **아무 상태로나 바뀔 수 있어 불변식이 무너진다**.\
`setStatus`가 어디서든 호출 가능하면 상태 전이 규칙을 누구나 우회할 수 있고, 그 규칙이 여러 서비스에 흩어져 중복되며, 객체가 자기 불변식을 못 지켜 동시성·정합성 문제의 온상이 된다. 상태 변경은 `approve()` 같은 의미 있는 메서드 안에서만 일어나야 한다.

**11. (판단)** 항상 나쁘지는 않다. **단순 CRUD 위주이거나 지켜야 할 불변식이 없으면** 빈약한 모델이 오히려 합리적이다.\
**진짜 문제**가 되는 경우는 복잡한 규칙이 있는데도 그것을 객체 밖 서비스에 흩뿌리는 경우다 — 같은 규칙이 중복되고 누구나 우회할 수 있게 된다.

**12. (연결)** `transfer(Long from, Long to, BigDecimal amount)`를 `transfer(AccountId from, AccountId to, Money amount)`로 바꾸면 **인자 순서를 바꿔 넣는 실수**(from/to를 뒤섞거나 금액 자리에 계좌 ID를 넣는 것)가 컴파일 타임에 막힌다.\
이는 도메인 모델링에서 "요구사항 문장의 개념을 어느 타입으로 세우는가"의 실천이다 — 원시 타입 집착(Primitive Obsession)을 벗고 개념을 값 객체로 세우는 것.
