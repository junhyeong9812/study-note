# domain-modeling/14-money-arithmetic-rounding-allocation — 정답

## 정답

### 1. 정확한 타입이어도 돈이 새는 이유

- 덧셈·뺄셈은 정확하다. 곱셈·나눗셈 결과를 통화 자릿수로 **자르는 순간**(반올림) 차이가 생긴다.
- Fowler의 구분(PoEAA Money 초안)
  - 비례 요금(세금·수수료처럼 금액 × 비율): 곱셈 + 반올림이 맞다.
  - 배분(정해진 총액을 여러 곳에 나눔): 곱셈으로 하면 합이 원금과 달라진다. "an allocator works better for the latter".

### 2. 배분 실험 (실험 A)

| 경우 | 각자 반올림(또는 자르기) | 최대 잔여 |
|---|---|---|
| 10,000원 ÷ 3 | 3333 × 3 = 9,999(1원 소실) | `[3334, 3333, 3333]` 합 10,000 |
| 100원 1:1:1, HALF_UP | `[33, 33, 33]` 합 99 | `[34, 33, 33]` 합 100 |
| 5원 1:1, HALF_UP | `[3, 3]` 합 6(1원 생김) | `[3, 2]` 합 5 |

- 각자 반올림은 사라지기도 생기기도 한다. 배분기는 합 = 원금을 보장한다.

### 3. 7원을 2:3:5

- 정확값: 1.4, 2.1, 3.5. 내림: 1, 2, 3(합 6). 남은 몫 1원.
- Fowler(앞 칸부터): `[2, 2, 3]`.
- 최대 잔여(버린 소수 0.4·0.1·0.5 중 가장 큰 셋째 칸): `[1, 2, 4]`.
- 정확값과의 차이: Fowler 0.6·0.1·0.5, 최대 잔여 0.4·0.1·0.5. 최대 잔여 쪽이 더 가깝다.
- 실험 A 출력: `7 비율 [2, 3, 5]: Fowler(앞 칸부터) [2, 2, 3] / 최대 잔여 [1, 2, 4]`.

### 4. 반올림 모드 (실험 D, PG 재현)

| 값 | HALF_UP | HALF_EVEN | DOWN | FLOOR |
|---|---|---|---|---|
| 2.5 | 3 | 2 | 2 | 2 |
| 3.5 | 4 | 4 | 3 | 3 |
| -2.5 | -3 | -2 | -2 | -3 |

- 모드 없이 `setScale(0)`: `ArithmeticException: Rounding necessary`. `10000.divide(3)`도 `Non-terminating decimal expansion`.
- 단, 모드를 안 받는 경로는 조용히 줄인다: `new MathContext(1)`(기본 HALF_UP) → `2.5` 반올림 `3`, `longValue()` → `2`(자르기), PostgreSQL `numeric(19,4)` 열에 `1.23455` 저장 → `1.2346`(17.11 재현).
- PostgreSQL 17.11: `round(2.5::numeric)` = 3, `round(2.5::float8)` = 2. 문서: `numeric`은 동률을 0에서 먼 쪽으로, `double precision`은 플랫폼 의존(대개 짝수 쪽).

### 5. 줄별 vs 합계 세액 (실험 B)

- 줄별: 10.5 → 11 세 번, 합 33원. 합계: 315 × 0.1 = 31.5 → 32원.
- 무작위 1만 건(줄 1~10, seed 42): 4,309건(43%)에서 갈렸고 최대 4원.

### 6. 할인·세금 순서 (실험 C)

- 정확히 계산하면 정률끼리는 곱셈이라 순서와 무관하다.
- 단계마다 원 단위로 반올림하면 1~100,000원 중 33,000개 가격(33%)에서 갈렸다. 예: 10,005원 → 할인→세금 9,354 / 세금→할인 9,355. (9,999원은 둘 다 9,349로 같았다.)
- 정액 할인 100원(가격 1,000): 할인→세금 990, 세금→할인 1,000. 반올림과 무관하게 순서가 결과를 바꾼다. 어느 쪽인지는 세법·약관이 정한다.

### 7. 통화 자릿수

| 통화 | ISO 4217 minor unit | JDK 21.0.12 |
|---|---|---|
| KRW·JPY | 0 | 0 |
| USD | 2 | 2 |
| KWD·BHD | 3 | 3 |
| CLF | 4 | 4 |

- ISO 목록은 SIX가 배포하는 2026-09-17 공표판으로 확인했다. 실험 E에서 JDK 값이 같았다.
- 결제사 연동은 그 결제사의 통화 표가 기준이다. 결제사가 특정 통화를 ISO와 다르게 처리하는 예외가 있을 수 있다.

### 8. 중복 청구 검사 실패

- 원인: `BigDecimal.equals`는 값과 **스케일**을 함께 비교한다. DB 경로는 `numeric(19,4)`라 `1.0000`(PG 17 재현), JSON 경로는 `1.0`처럼 스케일이 달랐다. 실험 F: `equals false / compareTo 0`, `HashSet size 2 / TreeSet size 1`.
- 대처: 금액을 `Money` 값 객체로 감싼다. `BigDecimal`로 든다면 생성자에서 통화 자릿수로 `setScale`하고(12번 노트의 `Money`), 최소 단위 `long`으로 든다면 스케일 문제가 없다. 맨 `BigDecimal` 비교는 `compareTo`로 한다.
- PostgreSQL은 다르다: `numeric '1.0' = numeric '1.00'`은 참이고 `DISTINCT`도 하나로 셌다. 앱과 DB의 판정이 갈릴 수 있다.

### 9. 결제사 "금액 불일치"

- 의심 순서
  1. 주문 서비스와 결제 요청이 금액을 **각자 다시 계산**하는가(반올림 위치·할인 순서가 다를 수 있다 — 실험 B·C).
  2. 통화 자릿수 가정(JPY·KWD).
  3. 직렬화에서 정밀도·스케일 손실.
- 고치기: 세금·할인 계산을 하나의 정책 객체로 모은다. 결제 요청에는 주문에 저장된 **확정 금액**을 그대로 보낸다. 줄별 표시가 필요하면 합계 세액을 줄에 배분해 세로 합을 맞춘다.

### 10. JSON 직렬화

- JS `Number`는 IEEE 754 double이다. 2^53을 넘는 정수(`9007199254740993` → `9007199254740992`)와 대부분의 소수(`0.1 + 0.2`)가 정확하지 않다(Node v18.19.1 실험).
- `1.005`는 double로 1.00499…에 가까운 값이라 `toFixed(2)`가 `1.00`을 낸다.
- 권장 형식
  - 문자열 금액 + 통화: `{"amount": "12.30", "currency": "USD"}`
  - 안전 범위 안의 최소 단위 정수 + 통화: `{"amountMinor": 1230, "currency": "USD"}`
- Java에서 문자열로 낼 때는 `toPlainString()`을 쓴다. `new BigDecimal("100").stripTrailingZeros().toString()`은 `1E+2`다.
