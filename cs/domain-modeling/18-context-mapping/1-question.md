# domain-modeling/18-context-mapping — 질문

## 질문

1. (왜) 컨텍스트를 나눈 뒤에도 "상류가 필드 이름을 바꾸면 누가 알아야 하나"에 답이 없으면 무슨 일이 생기나? 왜 REST·Kafka 같은 기술 선택으로는 답이 안 나오나?
2. (정의) DDD Reference의 *상류-하류*, *상호 의존*, *자유*를 각각 한 줄로 정의하라. 강을 낀 두 도시 예는 무엇을 보이나?
3. (분류) 관계 패턴 9가지를 팀 관계(상호 의존 / 상류-하류 / 자유 / 경계 없음)로 묶어라.
4. (비교) 순응자(Conformist)와 ACL은 둘 다 상류가 협조하지 않을 때 쓴다. 각각 무엇을 사고 무엇을 내주나? 하류가 핵심 서브도메인이면 어느 쪽을 경계하나?
5. (예측) 컨텍스트 그래프에서 Catalog → Ordering(ACL), Catalog → Search(순응), Ordering → Shipping·Invoicing(공개 언어), Shipping → Tracking(공유 커널)이다. "순응·공유 커널만 모델 변경을 넘긴다"는 규칙이면 Catalog 변경은 어디까지 번지나? 모든 선이 순응이면?
6. (예측) 하류가 `resp.getOrDefault("price", 0) * 3`으로 합계를 낸다. 상류가 `price`를 `unitPrice`로 바꾸면 하류는 무엇을 출력하나? 에러가 나나? 하류 계약(`sku`, `price`)을 상류 CI에서 돌리면 결과는?
7. (경계) Open-host Service와 Published Language는 각각 무엇이고 왜 자주 함께 쓰나? OHS에 한 팀만의 특이 요구가 오면 Reference는 어떻게 하라고 하나?
8. (장애 진단) "작은 공통 모듈"이던 공유 커널의 PR이 늘 두 팀 승인을 기다린다. Reference의 어떤 처방을 어겼고, 어떻게 되돌리나?
9. (장애 진단) 두 팀이 서로의 기능이 있어야 출시할 수 있는데 통합 직전마다 인터페이스가 안 맞는다. 어떤 관계로 다뤄야 했고, Reference는 무엇을 하라고 하나?
10. (적용) 컨텍스트 맵을 처음 그릴 때 Reference가 강조하는 순서상의 원칙 한 가지는? 맵에 없는 숨은 순응 관계를 코드에서 찾는 방법은?
