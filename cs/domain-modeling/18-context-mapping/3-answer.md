# domain-modeling/18-context-mapping — 정답

## 정답

### 1. 관계가 없으면

- 상류 변경이 하류를 예고 없이 깨뜨린다. 하류는 사실상 순응자인데 상류는 그것을 모른다.
- 기술은 "어떻게 보내나"만 정한다. "누가 누구에게 맞추나, 깨지면 누가 고치나"는 팀 사이 힘 관계와 번역 방식의 문제다.

### 2. 세 정의

| 용어 | 정의(Reference IV부) |
|---|---|
| 상류-하류 | 상류의 행동은 하류 성패에 영향을 주지만, 하류의 행동은 상류에 큰 영향이 없다. 상류는 하류와 무관하게 성공할 수 있다 |
| 상호 의존 | 두 컨텍스트 프로젝트가 둘 다 전달돼야 어느 쪽이든 성공으로 친다 |
| 자유 | 다른 컨텍스트의 방향·성패가 이쪽 전달에 거의 영향이 없다 |

- 강 예: 위쪽 도시의 오염은 주로 아래쪽 도시에 영향을 준다. 영향이 한 방향이라는 것이 상류-하류의 핵심이다.

### 3. 9가지 묶기

| 팀 관계 | 패턴 |
|---|---|
| 상호 의존 | Partnership, Shared Kernel |
| 상류-하류 | Customer/Supplier, Conformist, Anticorruption Layer, Open-host Service, Published Language |
| 자유 | Separate Ways |
| 경계 없음 | Big Ball of Mud |

- 이 묶음은 Reference의 세 관계 정의에 패턴을 배치한 정리다. Reference 자체는 패턴을 관계별로 묶지 않는다.
- Khononov는 협력(Partnership·Shared Kernel)·고객-공급자(Conformist·ACL·OHS)·Separate Ways로 묶는다(2차 정리로 확인).

### 4. 순응자 vs ACL

| | 얻는 것 | 내주는 것 |
|---|---|---|
| 순응자 | 번역 복잡도 0, 상류와 같은 언어 | 하류 설계가 상류에 묶인다. 상류 변경이 그대로 번진다 |
| ACL | 하류 모델을 지킨다. 변경이 번역기에서 멈춘다 | 번역 계층을 만들고 유지하는 비용 |

- 하류가 핵심이면 **순응자**를 경계한다. 상류 모델이 핵심 모델을 결정하게 된다. Reference도 레거시 상류 모델은 대개 약해서 순응이 비현실적이라고 적는다.

### 5. 영향 범위 (실험 [1])

- 관계를 고른 맵: `{Ordering=번역 계층만 수정(ACL), Search=모델 변경(CONFORMIST)}` — 2곳에서 멈춘다. Ordering은 ACL이라 그 뒤(Shipping·Invoicing·Tracking)로 안 간다.
- 모두 순응: Ordering·Search·Shipping·Invoicing·Tracking **5곳 전부**.
- 주의: 이 결과는 실험에서 가정한 파급 규칙 위의 계산이다. "ACL이면 번역기만 바뀐다"는 19번 실험에서 실제 diff로 보인다.

### 6. 필드 이름 변경 (실험 [2])

- 하류 출력: `하류 주문 합계(수량 3) = 0`. **에러가 없다.** `getOrDefault`가 없는 필드를 0으로 덮었다.
- 상류 CI 계약 테스트: v1 `PASS`, v2 `FAIL missing=[price]`. 릴리스 전에 상류가 안다.
- 교훈: 하류는 없는 필드를 기본값으로 덮지 말고 예외로 드러낸다. 고객/공급자라면 계약 테스트를 상류 CI에 넣는다(Reference "Customer/Supplier"의 함께 만든 자동 인수 테스트).

### 7. OHS와 PL

- OHS: 많은 하류와 통합해야 하는 상류가 하위 시스템을 서비스 집합으로 여는 프로토콜을 정의·공개한다. 하류마다 번역기를 따로 만드는 비용을 없앤다.
- PL: 필요한 도메인 정보를 표현하는, 잘 문서화된 공유 교환 언어. 기존 내부 모델을 교환 언어로 쓰면 그 모델이 얼어붙기 때문에 따로 둔다.
- 함께 쓰는 이유: OHS는 "열린 접점", PL은 "그 접점에서 쓰는 언어"다. Reference도 PL이 OHS와 자주 결합된다고 적는다.
- 특이 요구: 공용 프로토콜에 넣지 않고 그 팀용 **일회용 번역기**로 보강해 프로토콜을 단순하게 유지한다.

### 8. 커진 공유 커널

- 어긴 처방: "Keep this kernel small." 공유 커널은 매우 밀접한 의존이라 커지면 공유 모델 문제(16번)로 돌아간다.
- 되돌리기: 두 팀이 정말 같은 뜻으로 쓰는 것만 남기고, 한쪽만 쓰는 것은 각자 컨텍스트로 돌려보낸다. 커널 변경은 상대 팀과 상의 후에만 한다.

### 9. 상호 의존

- **Partnership**으로 다뤄야 했다. 상호 의존을 상류-하류처럼 따로 계획했다.
- Reference 처방: 계획을 함께 세우고 통합을 함께 관리한다. 서로 의존하는 기능은 같은 릴리스에 맞춘다. 인터페이스가 클라이언트 기대를 만족하는지 보는 테스트를 서버 쪽 CI에서 돌린다.

### 10. 맵 그리기

- 원칙: **지금 지형을 먼저 그리고, 바꾸는 것은 나중에 한다**("Map the existing terrain. Take up transformations later."). 비객체지향 하위 시스템의 암묵적 모델도 포함한다.
- 숨은 순응 찾기: 우리 컨텍스트 코드가 다른 컨텍스트의 내부 패키지를 import하는지 `grep`으로 찾는다. 있으면 사실상 순응이다. 맵에 그 선이 있는지, 의도한 관계인지 확인한다.
