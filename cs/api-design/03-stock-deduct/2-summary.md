# api-design/03-stock-deduct — 정리 (힌트)

## 해결하는 문제

"주문 상품들의 재고를 깎고, 취소하면 되돌려라" — 상품이 하나면 01번과 같은 문제다. 한 주문이 상품 20개를 한꺼번에 잠그는 순간 새 문제가 생긴다.

```text
없으면 안 되는 것 네 가지

  (1) 단일 차감   읽고-빼고-쓰기 → 오버셀 (01번과 같다)
  (2) 여러 상품   주문1: A 잠금 → B 대기 / 주문2: B 잠금 → A 대기 → 데드락
                  15번째에서 부족 → 앞의 14개는? (전체 실패여야 한다)
  (3) 복원        취소 재시도가 두 번 → 재고 +2배 → 없는 재고를 판다
  (4) 예약        결제 전에 잡아둔 재고에 만료가 없음 → 이탈한 장바구니가 재고를 영원히 잠근다
```

쉬운 예: 도서관에서 책 20권을 한 번에 빌리기 — 사서는 늘 같은 순서(청구기호순)로 서가를 돌고, 한 권이라도 없으면 대출을 통째로 취소하며, 반납은 "대출 기록이 있는 책만" 받는다.\
똑같은 구조다: `product_id` 정렬 잠금(같은 순서) · 한 트랜잭션 전체 롤백(통째로 취소) · 차감 이력을 상쇄하는 복원(기록이 있는 것만) · 만료 있는 예약.\
실무 예: 커머스 주문·취소, 좌석 선점(만료 있는 hold), 호텔 객실 예약 — "여러 자원을 한 번에 잡고 나중에 되돌리는" 모든 곳.

### 한눈에 — 쉽게 말하면

**재고 차감 = 창고에서 물건 빼기. 이 문제의 새 축은 "한 주문이 창고 칸 20개를 동시에 잠근다"는 것이다.**

- 단일 상품 차감은 01번(포인트)과 같다 — 읽고-계산해서-쓰면 지고, 조건부 UPDATE로 이긴다.
- 새로 들어오는 축 둘:
  - **여러 상품**: 20개 중 15번째에서 부족하면 전체 실패해야 하고, 두 주문이 서로 반대 순서로 상품을 잠그면 **데드락**이 난다.

    > **데드락(deadlock)** — 내가 A를 잡고 B를 기다리는데, 상대는 B를 잡고 A를 기다림 — 둘 다 영원히 멈춘다.\
    > 예: 주문1은 상품A를 잡고 상품B를, 주문2는 상품B를 잡고 상품A를 기다린다.

  - **복원**: 취소 시 재고를 되돌린다.\
    **복원이 차감보다 위험하다** — 복원이 중복되면 없는 재고를 판다.
- 지문의 배경 문단("결제하려니 품절" 문의 → 확보 시점을 앞당기는 검토)이 **예약**이라는 숨은 주제를 유도한다.
- 실무 예: 커머스 주문/취소, 좌석 선점, 호텔 예약.

```text
[데드락 — 순서를 통제하지 않으면]

  주문1: 상품A 잠금 ──> 상품B 기다림 ─┐
  주문2: 상품B 잠금 ──> 상품A 기다림 ─┴─ 서로 영원히 기다린다

[막는 법 — 항상 같은 순서로]
  두 주문 모두: product_id 오름차순 정렬 → A 먼저, B 다음  → 순환이 안 생긴다
```

## 동작·원리

### 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 상품별 재고 수량 (한 요청이 최대 20행)
  Q2. 동시에 두 번 오면?  → 오버셀 / 이중 복원 / 데드락
  Q3. 중간에 끊기면?      → 차감됐는데 주문 실패 → 재고가 허공에 잠긴다

숨은 요구: A 차감 방식 · B 여러 상품 원자성+잠금 순서(이 문제 고유) ·
           C 복원 멱등(차감보다 위험) · D 예약과 만료(배경 문단이 유도)
```

### 설계 — 차감: 01번과 같은 무기 (A)

```sql
-- 좋음: 조건부 UPDATE + affected rows 판정
UPDATE products
   SET qty = qty - 2
 WHERE product_id = 501 AND qty >= 2;
-- affected rows 0 → 재고 부족
```

- 재고가 음수가 될 수 없음을 보장하는 것은 앱 검증이 아니라 **이 WHERE 조건(또는 DB CHECK 제약)** 이다.

> **조건부 UPDATE / affected rows** — 검사와 갱신을 DB 한 문장에 넣고, 바뀐 행 수 0으로 부족을 판정하는 기법.\
> 예: affected rows 0 이면 재고 부족이다.

- `SELECT ... FOR UPDATE`를 쓴다면 근거를 말할 수 있어야 한다(복합 검증 가능 vs 잠금 관리 부담).

### 설계 — 여러 상품의 원자성과 잠금 순서 (B, 이 문제의 고유 변별점)

**언제 문제가 되나**: "부족한 상품이 하나라도 있으면 전체 실패" — 그래서 한 트랜잭션으로 묶는데, 묶는 순간 잠금 순서가 운명을 가른다.

> **잠금 순서(lock ordering)** — 여러 자원을 잠글 때 모두가 따르는 고정 순서(예: id 오름차순).\
> 예: 순환 대기를 구조적으로 없앤다 — 두 주문 모두 product_id 오름차순으로 잠근다.

나쁜 계약 → 좋은 계약:

```text
나쁨: items를 요청에 온 순서대로 차감
  주문1: [501, 733] / 주문2: [733, 501] → 서로 반대 순서로 잠금 → 데드락

좋음: BEGIN
        items를 product_id로 정렬          ← 모든 주문이 같은 순서로 잠근다
        같은 상품 중복은 합산(또는 에러)     ← 정책을 정해둔다
        각 상품 조건부 UPDATE, 하나라도 affected rows 0이면 전체 ROLLBACK
      COMMIT
```

- 15번째에서 부족하면 앞의 14개는 **롤백이 되돌린다** — 트랜잭션으로 묶었기 때문에 가능.

> **트랜잭션 / 롤백** — 여러 작업을 전부-아니면-전무로 묶는 단위 / 중간 실패 시 전부 되돌리기.\
> 예: 하나라도 부족하면 전체 ROLLBACK 이라 앞의 14개도 되돌아간다.

- Mercari 사례가 정확히 이 구조: 두 user 행을 순서 통제 없이 갱신 → 데드락 → "id 절대값으로 정렬"이 해법.
- 응답에는 **어느 상품이 부족한지** 담아야 한다 — 프론트가 표시해야 하니까(G).

**비용/트레이드오프**: 정렬은 공짜에 가깝고 데드락을 구조적으로 없앤다.\
대신 잠금을 오래 들면(상품 20개 × 인기 상품) 경합이 커진다 — 트랜잭션은 짧게.

### 설계 — 복원: 차감보다 위험하다 (C)

**언제 문제가 되나**: 취소 요청이 재시도로 두 번 오면?\
차감한 적 없는 주문에 복원 요청이 오면?

```text
나쁨: DELETE 요청마다  UPDATE products SET qty = qty + ?
  → 복원이 두 번 실행되면 재고가 두 배로 늘어난다 → 없는 재고를 판다(오버셀)

좋음: 차감 이력을 남기고, 복원은 "그 이력을 상쇄"하는 연산으로
  차감 시: INSERT 차감 이력(order_id UNIQUE, items…)   ← order_id가 자연 멱등 키
  복원 시: 이력이 '차감됨' 상태일 때만 상태 전이 + qty 복원 (조건부, 한 번만 성립)
  차감 이력이 없으면 → 복원 거부
```

- **차감 실패는 "사용자가 못 사는 것"으로 끝나지만, 복원 중복은 "없는 재고를 파는 것"이다** — 이 비대칭을 설명할 수 있는지가 숨은 변별점.

> **오버셀(oversell) / 언더셀(undersell)** — 실제 재고보다 많이 파는 사고 / 있는데 품절이라 답하는 사고 — 이것도 장애다.\
> 예: 복원 중복은 없는 재고를 파는 것이다.

- 재고 숫자만 고치고 이력을 안 남기면 멱등 판정 근거 자체가 없다.

> **멱등성(idempotency)** — 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.\
> 예: 복원에서 특히 중요하다 — 두 번 와도 재고는 한 번만 늘어야 한다.

### 설계 — 예약 vs 차감 (D, 배경 문단이 유도)

**언제 문제가 되나**: "결제 전에 재고를 확보"하면 그건 차감이 아니라 **예약**이다 — 그리고 예약에는 반드시 **만료**가 있어야 한다.

> **예약(reservation)** — 차감 전에 재고를 임시로 잡아두는 것.\
> 예: 반드시 만료가 있어야 한다 — 없으면 이탈한 예약이 재고를 영원히 잠근다.

```text
차감만 있을 때: 결제 화면에서 이탈 → 재고가 영원히 잠긴다 ✗

예약 모델:
  담기/결제 진입 → 예약(만료 시각 부여) → 결제 완료 → 예약을 확정(차감)으로 전환
                                        └ 이탈/만료 → 회수(배치 or 조회 시 lazy 정리)
```

- 만료된 예약을 **누가** 회수하는가(배치?\
  조회 시점 정리?)와, 예약 수량과 실재고의 정합성을 누가 보장하는가까지 정해야 예약 모델이 완성된다.

> **만료 회수(sweeper / lazy)** — 만료된 예약을 배치가 주기적으로, 또는 조회 시점에 정리하는 방식.\
> 예: 배치로 주기적으로 회수하거나 조회 시점에 정리한다.

- Shopify의 답: 예약과 원장을 **같은 DB(MySQL)** 에 넣어 reserve와 claim을 하나의 ACID 트랜잭션으로.\
  "판매 단위당 1행" 모델 + `SKIP LOCKED`, 일관된 잠금 순서로 데드락을 설계로 회피.

### 설계 — 저장소 선택: 두 곳에 두면 원자성이 없다 (E)

```text
재고를 Redis(빠름) + DB(정본) 두 곳에 두면:
  두 쓰기를 하나의 원자 단위로 묶을 수 없다
  → Redis 먼저 성공 + DB 실패 = 언더셀 (있는데 품절이라 답함)
  → DB 먼저 성공 + Redis 실패 = 오버셀 (없는데 팔림)
  순서에 따라 방향만 바뀔 뿐, 사고는 난다
```

- Shopify 원문: "그 두 연산은 하나의 원자 단계로 묶을 수 없었다."\
  해법은 저장소를 하나로 합치는 것이었다.
- **무엇이 정본인지** 못 정하면 불일치가 났을 때 어느 쪽을 고칠지도 모른다.

> **정본(source of truth)** — 값이 갈릴 때 믿는 쪽.\
> 예: 캐시-DB 이원화 시 반드시 정해야 한다.

## 쓰이는 자료구조·알고리즘

- **조건부 UPDATE** (`SET qty = qty - ? WHERE qty >= ?`) — 행 단위 원자 CAS. 커리큘럼이 이 사례의 🔧로 꼽는 장치 → [01-order-point](../01-order-point/2-summary.md)와 같은 무기.
- **잠금 순서 고정 = 자원 ID 정렬(전순서)** — 모든 트랜잭션이 같은 순서로 잠그면 "누가 누구를 기다리나" 그래프에 순환이 생길 수 없다. 데드락 탐지는 이 대기 그래프의 사이클 탐지다 → [data-structure/08-graph](../../data-structure/08-graph/2-summary.md) · [algorithm/12-dfs](../../algorithm/12-dfs/2-summary.md).
  - *대기 그래프(wait-for graph)*: 트랜잭션을 점, "A가 B의 잠금을 기다림"을 화살표로 그린 그래프. 순환 = 데드락.
- **행 잠금 · `SKIP LOCKED`** — `SKIP LOCKED`는 잠긴 행을 기다리지 않고 건너뛰어 다음 행을 잡는 옵션(MySQL 8.0 · PostgreSQL 9.5 이상). Shopify가 "판매 단위당 1행" 모델에서 경합을 줄이는 데 썼다.
- **차감 이력 + 상태 전이(차감됨 → 복원됨)** — 복원을 "숫자 +"가 아니라 이력의 상태 전이로 정의하면 한 번만 성립한다. 상태 기계 → [domain-modeling/basic/09-order-state](../../domain-modeling/basic/09-order-state/2-summary.md).
- **`order_id` 자연 멱등 키** — 차감/복원 각 1회를 이력 테이블의 UNIQUE가 판정 → [ops-patterns/06-idempotency-store](../../ops-patterns/06-idempotency-store/2-summary.md).
- **만료 회수 sweeper** — 만료 시각 순으로 예약을 훑는 배치. 만료 시각 인덱스(B-tree 계열 인덱스의 범위 스캔) 또는 최소 힙 → [data-structure/07-heap](../../data-structure/07-heap/2-summary.md) · [ops-patterns/10-scheduler](../../ops-patterns/10-scheduler/2-summary.md).
- **대사 = 폴드** — 재고 = 입고 − 판매(차감) 이력 합 + 복원 이력 합. 숫자 컬럼과 이력 합을 맞춰보는 것이 오버셀 조기 탐지다.

## 적용 — 풀어나가는 법

재고 문제는 "조건부 UPDATE"를 아는 데서 시작하지만, 변별은 **여러 행을 한 번에 잠그는 순간**에 난다.\
순서: ① 공유 자원 = 상품별 재고 행, 한 요청이 최대 20행 → ② 한 트랜잭션 + `product_id` 정렬로 "전체 실패"와 "데드락 없음"을 동시에 얻는다 → ③ 복원은 차감 이력을 상쇄하는 연산으로 정의한다(숫자만 +하지 않는다) → ④ 배경 문단의 "확보 시점 앞당기기"를 예약 모델(만료 · 회수 주체 · 정합성 보장자)로 번역한다.\
아래 과제 목록이 그 훈련의 실제 절차다.

### 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 커머스 주문팀의 평범한 요구사항 문서다: `POST/DELETE /orders/{order_id}/stock` 으로 주문의 각 상품 재고를 차감하고, 취소 시 되돌려라.\
"부족한 상품이 하나라도 있으면 주문 전체가 실패", "실제 수량보다 많이 팔리는 일이 없어야" 하고, 한 주문 최대 20개 상품·인기 상품 초당 수백 건이 참고로 적혀 있다.\
배경 문단의 "재고 확보 시점을 앞당기는 방향도 검토"가 예약이라는 숨은 주제를 유도한다 — 그냥 넘기면 놓친다.

### 나머지 축 — 짧게

- **부분 실패(F)**: 차감은 됐는데 주문 생성이 실패하면?\
  복원 직전에 죽으면?\
  — 이력(흔적)이 남아야 나중에 찾아서 회수할 수 있다.
- **응답/에러(G)**: 부족은 4xx(재시도 무의미).\
  **품절이 아닌데 품절이라고 답하는 것도 장애**라는 인식 — 수량이 새는 것만 사고가 아니다.
- **관측(H)**: 재고 숫자와 판매 이력의 합이 맞는지 대사.\
  오버셀을 **고객 문의 전에** 알 수 있는가.

> **대사(reconciliation)** — 재고 숫자와 판매 이력의 합을 맞춰보고 불일치를 찾는 작업.\
> 예: 오버셀을 고객 문의 전에 발견할 수 있게 해준다.

- **되묻기(I)**: 예약 만료 시간, 부분 주문 허용 여부, 동일 상품 중복 담기 정책.

## 장애 시나리오와 대처

아래는 우리 시스템 안에서 마주치는 모양이다. 회사 사례는 「실패 사례」 절에 따로 있다.

**1. 인기 상품 재고가 -3이다**

- 현상: 오픈 후 `qty`가 음수인 상품이 나온다. 배송 단계에서 "보낼 물건이 없다"가 터진다.
- 보이는 형태: 예외 0건. 대사 배치에서 판매 이력 합 > 입고량. 초과분이 초당 수백 건이 몰린 몇 초에 집중된다.
- 원인: `SELECT qty` → 앱에서 비교 → 조건 없는 `UPDATE qty = qty - ?`. 동시 주문이 같은 값으로 검사를 통과해 차감이 모두 반영되며 음수가 됐다. 계산값을 덮어쓰는 `UPDATE qty = <계산값>`이었다면 음수 대신 qty가 실제보다 크게 남는(한쪽 차감이 사라지는) lost update 모양으로 나타난다(정답 2번 참고).
- 대처: 조건부 UPDATE(`WHERE qty >= ?`) + affected rows 판정, DB `CHECK (qty >= 0)`. 초과 판매분은 이력을 근거로 취소·보상 처리한다.

**2. 피크에만 데드락 에러가 간헐적으로 난다**

- 현상: 오픈 직후 몇 분 동안만 주문 실패가 튀고, 재시도하면 성공한다.
- 보이는 형태: MySQL `Deadlock found when trying to get lock; try restarting transaction` / PostgreSQL `ERROR: deadlock detected`. 실패한 주문 쌍은 같은 상품들을 서로 반대 순서로 담고 있다.
- 원인: items를 요청에 온 순서대로 차감해 잠금 순서가 주문마다 다르다. 또는 bulk upsert/INSERT에 넘기는 행 순서가 실행마다 달라진다(Go map처럼 순회 순서가 무작위인 자료구조로 행 목록을 만든 경우 — 원본 REFERENCE의 incident.io 사례)(정답 3번 참고).
- 대처: `product_id`로 정렬한 뒤 처리하고, 같은 상품 중복은 합산(또는 거부)해 한 행을 두 번 잠그지 않는다. 트랜잭션을 짧게(외부 호출 밖으로) 유지하고, 데드락 에러는 재시도 가능한 실패로 분류해 자동 재시도 1회를 둔다.

**3. 취소했더니 품절 상품 재고가 두 배로 늘었다**

- 현상: 품절이던 상품이 갑자기 "재고 있음"으로 바뀌고, 곧 없는 물건이 팔린다.
- 보이는 형태: 같은 `order_id`의 복원 요청 로그 2건(타임아웃 재시도), 판매 이력 대비 재고 초과.
- 원인: 복원이 조건 없이 `UPDATE qty = qty + ?`를 실행한다. 차감 이력이 없어 "이미 복원했는지"를 판정할 근거 자체가 없다(정답 4번 참고).
- 대처: 차감 시 이력(`order_id` UNIQUE, 상태 '차감됨')을 남기고, 복원은 '차감됨' → '복원됨' 상태 전이가 성립할 때만 수량을 더한다(조건부, 한 번만). 이력이 없는 주문의 복원은 거부한다.

**4. 팔리지도 않았는데 품절로 표시된다**

- 현상: 재고가 있는 상품이 품절로 보이고 매출이 줄어든다. 고객 문의는 오지 않는다 — 못 사는 고객은 조용히 떠난다.
- 보이는 형태: 예약 테이블에 만료 시각이 없는 오래된 hold가 쌓여 있거나, Redis 재고와 DB 재고가 다르다.
- 원인: 예약에 만료·회수가 없어 이탈한 장바구니가 재고를 영원히 잠갔거나, Redis-DB 이원화에서 Redis 차감은 성공하고 DB가 실패했다(언더셀 방향).
- 대처: 예약에 만료 시각을 붙이고 sweeper(또는 조회 시점 정리)로 회수한다. 정본을 하나(DB)로 정하고 캐시는 게이트로만 쓴다. "품절 표시 vs 실재고" 대사를 두어 언더셀도 장애로 계측한다 — 수량이 새는 것만 사고가 아니다.

### 실패 사례 — 이 항목들이 나온 실제 사고

- **Shopify 재고 예약(정본 사례)**: Redis 예약 + MySQL 원장 이원화로 claim이 원자로 안 묶임 → 오버셀·언더셀 모두 발생.\
  MySQL 단일화 + 단위당 1행 + SKIP LOCKED + 일관된 잠금 순서로 해결.
- **Mercari 데드락**: 잠금 순서 미통제로 상호 대기.\
  해법 = id로 정렬.\
  케이스 2: 없는 행에 UPDATE → 인덱스 갭 전체에 잠금 → 무관한 INSERT까지 막힘(UPSERT로 재고 행을 만드는 설계라면 주의).

> **gap lock** — 행 사이의 빈 구간까지 잠그는 DB 잠금.\
> 예: 없는 행 UPDATE·unique 충돌 시 무관한 INSERT를 막을 수 있다.

- **Shopify 데드락 완화**: 논리적으로 안 겹치는 계정들의 ETL이 데드락 — 물리 저장 순서와 gap lock 때문.\
  PK를 (account, id) 복합키로 바꿔 잠금을 파티션 안에 가둠.
- **incident.io**: 같은 코드·같은 행인데 간헐 데드락 — Go map 순회 순서가 랜덤이라 bulk upsert 행 순서가 매번 달랐다.\
  DB는 문장 시작 시 한꺼번에가 아니라 **행 단위로 순차 잠금**한다.
- **Netflix 분산 카운터**: increment/decrement는 본질적으로 멱등하지 않다 — 변경마다 멱등키를 단 이벤트로 기록해야 재시도가 안전하다.

## 핵심 문장

- 단일 상품은 01번과 같지만, **여러 상품을 한 주문에서 다루는 순간 데드락이 새 축으로 들어온다** — 답은 잠금 순서 고정(product_id 정렬).
- "하나라도 부족하면 전체 실패"는 트랜잭션이 지키고, "모든 주문이 같은 순서로 잠근다"는 정렬이 지킨다.
- **복원이 차감보다 위험하다** — 차감 실패는 못 파는 것, 복원 중복은 없는 것을 파는 것.
- "결제 전 확보"는 차감이 아니라 예약이고, **만료 없는 예약은 재고를 영원히 잠근다.**
- 불변식이 두 저장소에 걸치면 어떤 트랜잭션으로도 강제할 수 없다 — 오버셀과 언더셀은 방향만 다른 같은 버그다.

### 용어 풀이

- **데드락(deadlock)**: 두 트랜잭션이 서로가 잡은 잠금을 기다리며 영원히 멈추는 상태.\
  잠금 순서 고정으로 예방.
- **잠금 순서(lock ordering)**: 여러 자원을 잠글 때 모두가 따르는 고정 순서(예: id 오름차순).\
  순환 대기를 구조적으로 없앤다.
- **조건부 UPDATE / affected rows**: 검사와 갱신을 DB 한 문장에 넣고, 바뀐 행 수 0으로 부족을 판정하는 기법.
- **트랜잭션 / 롤백**: 여러 작업을 전부-아니면-전무로 묶는 단위 / 중간 실패 시 전부 되돌리기.
- **오버셀(oversell)**: 실제 재고보다 많이 파는 사고.\
  **언더셀(undersell)**: 있는데 품절이라 답하는 사고 — 이것도 장애다.
- **예약(reservation)**: 차감 전에 재고를 임시로 잡아두는 것.\
  반드시 만료가 있어야 한다.
- **만료 회수(sweeper/lazy)**: 만료된 예약을 배치가 주기적으로, 또는 조회 시점에 정리하는 방식.
- **멱등성(idempotency)**: 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.\
  복원에서 특히 중요.
- **자연 멱등 키**: 도메인 규칙이 이미 주는 유일 키 — 여기서는 `order_id`(주문당 차감/복원 1회).
- **정본(source of truth)**: 값이 갈릴 때 믿는 쪽.\
  캐시-DB 이원화 시 반드시 정해야 한다.
- **gap lock**: 행 사이의 빈 구간까지 잠그는 DB 잠금.\
  없는 행 UPDATE·unique 충돌 시 무관한 INSERT를 막을 수 있다.
- **SKIP LOCKED**: 잠긴 행을 기다리지 않고 건너뛰고 다음 행을 잡는 SQL 옵션.\
  경합을 줄인다.
- **UPSERT**: 없으면 INSERT, 있으면 UPDATE를 한 번에 하는 연산.
- **대사(reconciliation)**: 재고 숫자와 판매 이력의 합을 맞춰보고 불일치를 찾는 작업.
