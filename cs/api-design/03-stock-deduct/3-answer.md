### A. 문제 (REQUIREMENTS.md — 재고 차감 / 복원 API)

#### 1. 지문 읽기 — 숨은 요구

- Q: 새로 들어오는 축 둘은?\
  A: ① **여러 상품의 원자성 + 잠금 순서**(B) — 한 주문이 최대 20행을 잠그는 순간 데드락이 새 축으로 들어온다.\
  ② **복원**(C) — 취소 시 되돌리는 연산이 생기고, 복원 중복은 차감 실패보다 위험하다.\
  단일 상품 차감(A)은 01번 잔액 차감과 같은 구조(조건부 UPDATE)다.\
  CHECKLIST 원문: "단일 상품 재고 차감은 01번과 같지만, 여러 상품을 한 주문에서 다루는 순간 데드락이 새 축으로 들어옵니다."

> **데드락(deadlock)** — 두 트랜잭션이 서로가 잡은 잠금을 기다리며 영원히 멈추는 상태.\
> 예: 주문1은 501을 잡고 733을 기다리고, 주문2는 733을 잡고 501을 기다린다.

- Q: 배경 문단이 유도하는 숨은 주제는?\
  A: **예약(reservation)과 만료**(D)다.\
  "결제 전에 재고를 확보"하면 그것은 차감이 아니라 예약이고, 예약에는 반드시 만료가 있어야 한다.\
  CHECKLIST 원문: "지문의 '재고 확보 시점을 앞당기는 방향도 검토'가 이 항목을 유도합니다.\
  배경 문단을 그냥 넘겼다면 놓쳤을 겁니다."\
  자가 채점에서 A+B+D면 "지문의 배경 문단까지 읽어냈다는 뜻 — 상위권"이다.

> **예약(reservation)** — 차감 전에 재고를 임시로 잡아두는 것.\
> 예: 결제가 완료되면 확정(차감)으로 전환되고 이탈하면 풀려야 한다.

- Q: 공통 질문 3개를 돌리면?\
  A: Q1 공유 자원 → **상품별 재고 수량**, 한 요청이 최대 20행을 건드린다.\
  Q2 동시에 두 번 → 오버셀(lost update) / 이중 복원 / 그리고 이 문제 고유의 **데드락**.\
  Q3 중간에 끊기면 → 차감됐는데 주문 생성 실패 → 재고가 허공에 잠긴다(F).\
  20행이라는 복수성이 Q2의 답에 데드락을 추가시키는 것이 이 문제의 모양이다.

> **오버셀(oversell) / 언더셀(undersell)** — 실제 재고보다 많이 파는 사고 / 있는데 품절이라 답하는 사고 — 이것도 장애다.\
> 예: 복원이 중복되면 없는 재고를 팔게 된다.

#### 2. 차감 방식 (A)

- Q: 조건부 UPDATE와 부족 판정은?\
  A: 검사와 차감을 한 문장에 넣는다.
  ```sql
  UPDATE products
     SET qty = qty - 2
   WHERE product_id = 501 AND qty >= 2;
  ```
  affected rows가 0이면 재고 부족 — 별도 SELECT 없이 판정된다.\
  읽고-계산해서-쓰면 01번과 똑같이 lost update로 오버셀이 난다.

> **lost update** — 읽고 계산해서 다시 쓰는 사이에 끼어든 요청의 차감이 사라지는 것.\
> 예: 읽고-계산해서-쓰면 01번과 똑같이 오버셀이 난다.

> **조건부 UPDATE / affected rows** — 검사와 갱신을 DB 한 문장에 넣고, 바뀐 행 수 0으로 부족을 판정하는 기법.\
> 예: `WHERE product_id = 501 AND qty >= 2` 가 0행이면 재고 부족이다.

- Q: 음수 방지를 보장하는 것은?\
  A: 앱 검증이 아니라 **WHERE 조건(또는 DB CHECK 제약)** 이다.\
  앱의 사전 검사는 검사와 갱신 사이 틈으로 동시 요청이 지나간다.\
  `SELECT ... FOR UPDATE`를 쓴다면 근거를 말할 수 있어야 한다 — 복합 검증이 가능하지만 잠금 범위·시간 관리 부담을 진다.\
  기대 동작 4번("실제 수량보다 많이 팔리는 일이 없어야")의 보장 주체를 묻는 항목이다.

#### 3. 여러 상품의 원자성과 잠금 순서 (B — 고유 변별점)

- Q: 15번째에서 부족하면 앞의 14개는?\
  A: **전부 되돌아가야 한다** — 기대 동작 2번 "하나라도 부족하면 주문 전체 실패".\
  가능하게 하는 것은 **트랜잭션**: 전체를 한 트랜잭션으로 묶고, 하나라도 affected rows 0이면 전체 ROLLBACK.\
  묶지 않으면 14개 상품의 재고가 깎인 채로 남아 수동 복구 대상이 된다.\
  "전체 실패"는 지문에 적혀 있지만 "그래서 트랜잭션"은 적혀 있지 않다 — 읽어내야 한다.

> **트랜잭션 / 롤백** — 여러 작업을 전부-아니면-전무로 묶는 단위 / 중간 실패 시 전부 되돌리기.\
> 예: 하나라도 affected rows 0이면 전체 ROLLBACK 이라 앞의 14개도 되돌아간다.

- Q: 반대 순서로 잠그면?\
  A: **데드락**이 난다.\
  주문1이 [501, 733] 순서, 주문2가 [733, 501] 순서로 잠그면 — 주문1은 501을 잡고 733을 기다리고, 주문2는 733을 잡고 501을 기다린다.\
  서로가 서로를 영원히 기다린다(한쪽이 DB의 데드락 감지로 강제 종료될 때까지).\
  Mercari 실사고: 판매자·구매자 두 user 행을 순서 통제 없이 갱신 → A가 B에게서 사는 동시에 B가 A에게서 사면 데드락.

- Q: 구조적으로 없애는 방법은?\
  A: **잠금 순서 고정** — items를 `product_id`로 정렬한 뒤 처리한다.\
  모든 주문이 같은 순서로 잠그면 순환 대기가 만들어질 수 없다.\
  Mercari 해법 원문: "id 같은 절대값으로 정렬해 쓰기 순서를 맞춘다."\
  Shopify도 reserve 후 DELETE → INSERT라는 일관된 락 순서로 데드락을 설계로 회피했다.

> **잠금 순서(lock ordering)** — 여러 자원을 잠글 때 모두가 따르는 고정 순서(예: id 오름차순).\
> 예: 모든 주문이 product_id 순으로 잠그면 순환 대기가 만들어질 수 없다.

- Q: 같은 상품이 두 번 들어오면?\
  A: **합산할지 에러로 거절할지 정책을 정해둔다** — 어느 쪽이든 정하지 않으면 사고다.\
  합산하지 않고 그대로 돌리면 같은 행을 한 트랜잭션이 두 번 갱신해 수량 판정이 꼬인다.\
  정렬 단계에서 중복을 발견할 수 있으므로 정렬과 함께 처리하는 것이 자연스럽다.\
  되묻기(I) 항목이기도 하다 — 동일 상품 중복 담기를 물었는가.

- Q: 잠금 순서 고정의 비용은?\
  A: 정렬 자체는 공짜에 가깝다(20개 정렬).\
  진짜 비용은 잠금을 드는 시간 — 상품 20개 × 인기 상품(초당 수백 건)이면 트랜잭션이 긴 만큼 경합이 커진다.\
  그래서 트랜잭션은 짧게: 잠금 구간에서 외부 호출·불필요한 작업을 하지 않는다.\
  데드락은 없앴어도 잠금 대기(경합)는 남는다 — 별개의 축이다.

#### 4. 복원 멱등성 (C — 숨은 변별점)

- Q: 복원이 두 번 실행되면?\
  A: `qty = qty + ?`가 두 번 실행되어 재고가 두 배로 늘어난다.\
  늘어난 재고는 실물이 없으므로 그만큼 **없는 재고를 판다** — 오버셀.\
  취소 재시도·중복 클릭·복구 배치의 재실행 등으로 복원 요청은 반드시 중복될 수 있다.\
  increment/decrement는 본질적으로 멱등하지 않다(Netflix) — 그냥 더하기로 구현하면 진다.

> **멱등성(idempotency)** — 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.\
> 예: 복원이 두 번 실행돼도 재고는 한 번만 늘어야 한다.

- Q: 복원이 차감보다 위험한 이유 한 문장은?\
  A: **차감 실패는 사용자가 못 사는 것으로 끝나지만, 복원이 중복되면 없는 재고를 팔게 된다.**\
  차감 쪽 오류는 언더셀(매출 손실)로, 복원 쪽 오류는 오버셀(배송 불가·보상)로 간다 — 손실 비대칭.\
  CHECKLIST 자가 채점: 이 비대칭을 설명할 수 있는지가 숨은 변별점 — "이걸 말하면 이 문제로는 더 잴 게 없다."

- Q: 이력 없이 숫자만 고치면 잃는 것은?\
  A: **멱등 판정의 근거**를 잃는다.\
  "이 주문의 복원이 이미 실행됐는가"를 물을 데이터가 없으니 중복 복원을 막을 수 없다.\
  "이 주문이 차감한 적이 있는가"도 알 수 없어 차감 안 한 주문의 복원 요청을 거부할 수 없다.\
  01번의 원장과 같은 자리 — 숫자는 파생값이고 이력이 정본이다.

- Q: 차감한 적 없는 주문에 복원 요청이 오면?\
  A: **거부해야 한다.**\
  차감 이력이 없으면 복원할 근거가 없다 — 받아주면 무근거로 재고가 늘어난다(오버셀 입구).\
  좋은 구현: 차감 시 이력을 남기고(order_id UNIQUE), 복원은 이력이 '차감됨' 상태일 때만 상태 전이 + 복원(조건부, 한 번만 성립).\
  상태 전이 조건이 곧 멱등 장치다 — 두 번째 복원은 조건 불충족으로 no-op.

- Q: 자연 멱등 키는?\
  A: **`order_id`** — 주문당 차감 1회·복원 1회가 도메인 규칙이다.\
  차감 이력 테이블의 order_id UNIQUE가 차감 중복을, '차감됨→복원됨' 상태 전이가 복원 중복을 막는다.\
  01번(주문당 포인트 적용 1회)과 같은 패턴 — 별도 Idempotency-Key가 필요 없다.

> **자연 멱등 키** — 도메인 규칙이 이미 주는 유일 키 — 여기서는 `order_id`(주문당 차감/복원 1회).\
> 예: 별도 Idempotency-Key 없이 order_id UNIQUE 가 차감 중복을 막는다.

#### 5. 예약 vs 차감 (D — 배경 문단이 유도)

- Q: 확보는 차감인가 예약인가?\
  A: **예약**이다 — 아직 팔린 게 아니라 "잡아둔" 것.\
  차감은 판매 확정의 기록이고, 예약은 결제가 완료되면 확정(차감)으로 전환되고 이탈하면 풀려야 하는 임시 상태다.\
  이 구분을 안 하면 결제 화면 이탈자가 잡아둔 재고의 처리를 설계할 수 없다.\
  흐름: 담기/결제 진입 → 예약(만료 시각 부여) → 결제 완료 → 확정 전환 / 이탈·만료 → 회수.

- Q: 만료가 없으면?\
  A: 결제 중 이탈한 예약이 **재고를 영원히 잡는다.**\
  이탈률이 높다는 것이 지문의 배경("결제 화면에서 이탈하는 사용자가 많아")이므로 이 경로는 상시 발생한다.\
  잡힌 재고는 실물이 있는데 못 파는 언더셀 — "품절이 아닌데 품절이라고 답하는" 장애.\
  만료 없는 예약은 예약이 아니라 느린 차감이다.

- Q: 만료 회수의 주체 선택지는?\
  A: ① **배치(sweeper)** — 주기적으로 만료 예약을 찾아 회수.\
  단순하지만 만료~회수 사이 지연이 있다.\
  ② **조회 시점 lazy 정리** — 재고 조회/차감 때 만료분을 정리.\
  지연은 없지만 조회 경로가 무거워진다.\
  어느 쪽이든 "누가 회수하는가"를 정하지 않으면 만료는 장식이다.\
  예약 수량과 실재고의 정합성을 누가 보장하는가까지 정해야 예약 모델이 완성된다.

> **만료 회수(sweeper / lazy)** — 만료된 예약을 배치가 주기적으로, 또는 조회 시점에 정리하는 방식.\
> 예: 누가 회수하는가를 정하지 않으면 만료는 장식이다.

- Q: Shopify의 배치는?\
  A: 예약을 Redis에서 **MySQL로 옮겨 원장과 같은 DB에** 넣었다 — reserve와 claim이 하나의 ACID 트랜잭션에 들어간다.\
  모델도 바꿨다: "수량 컬럼 1행"이 아니라 **"판매 단위당 1행" + `SKIP LOCKED`** (bounded pool 1,000행 + inline replenishment).\
  데드락은 일관된 락 순서(DELETE → INSERT)로 설계로 회피, gap lock이 보충 INSERT를 막지 않게 격리수준은 READ COMMITTED.\
  교훈: 원자성이 필요한 두 쓰기는 같은 저장소에 있어야 한다.

> **SKIP LOCKED** — 잠긴 행을 기다리지 않고 건너뛰고 다음 행을 잡는 SQL 옵션.\
> 예: "판매 단위당 1행" 모델에서 경합을 줄인다.

> **gap lock** — 행 사이의 빈 구간까지 잠그는 DB 잠금.\
> 예: 격리수준을 READ COMMITTED 로 낮춰 보충 INSERT 를 막지 않게 했다.

#### 6. 저장소 선택·부분 실패·응답 (E, F, G, H)

- Q: 두 곳에 두면 왜 사고이고, 방향은?\
  A: **두 쓰기를 하나의 원자 단위로 묶을 수 없기 때문**이다(Shopify 원문 그대로).\
  Redis 먼저 성공 + DB 실패 = **언더셀**(있는데 품절이라 답함) / DB 먼저 성공 + Redis 실패 = **오버셀**(없는데 팔림).\
  순서를 바꿔도 사고의 방향만 바뀔 뿐 사고는 난다.\
  정본을 정하고(보통 DB), 정합성이 필요한 쓰기는 정본 하나에서 원자적으로 한다.

> **정본(source of truth)** — 값이 갈릴 때 믿는 쪽.\
> 예: 캐시-DB 이원화 시 반드시 정해야 한다.

- Q: 차감 후 주문 생성 실패 시 재고는?\
  A: 차감된 채로 허공에 잠긴다 — 주문이 없으니 취소(복원) 경로도 못 탄다.\
  복원 호출 직전에 프로세스가 죽어도 같은 상태다.\
  회수하려면 **흔적(차감 이력)** 이 남아 있어야 한다 — "주문 없는 차감 이력"을 대사 배치가 찾아 회수한다.\
  흔적이 없으면 그 상태는 존재 자체를 알 수 없다 — 부분 실패는 "탐지 가능한가"가 요구사항.

- Q: 부족 응답에 담을 것과 상태 코드는?\
  A: **어느 상품이 부족한지**를 담는다 — 프론트가 사용자에게 표시해야 하기 때문(G).\
  "전체 실패"만 주면 사용자는 무엇을 빼야 할지 모른다.\
  재고 부족은 4xx — 같은 요청 재시도로 해결되지 않는 실패다.\
  단, 품절이 아닌데 품절이라고 답하는 것도 장애라는 인식이 있어야 한다 — 거짓 4xx는 매출 손실이다.

- Q: 오버셀을 고객 문의 전에 알려면?\
  A: **대사(reconciliation)** — 재고 숫자와 판매 이력의 합이 맞는지 주기적으로 맞춰본다.\
  이력이 있어야 대사가 가능하다(숫자만 있으면 맞춰볼 상대가 없다).\
  불일치 발견 시 알림 → 고객 문의 전에 발견·보정.\
  Slack의 scan/detect/repair(01번 REFERENCE)와 같은 사상 — 어긋남 탐지를 1급 운영 도구로.

> **대사(reconciliation)** — 재고 숫자와 판매 이력의 합을 맞춰보고 불일치를 찾는 작업.\
> 예: 불일치를 발견하면 고객 문의 전에 보정할 수 있다.

### B. 개념

#### 7. 문제를 여는 질문 세 개 (원본 README 이관)

- Q: Q1. 여기서 바뀌는 공유 자원이 무엇인가?\
  A: 상품별 재고 수량 — 그리고 한 요청이 **최대 20행**을 동시에 건드린다.\
  공유 자원이 복수라는 점이 01·02번과 다른 이 문제의 정체성이다.\
  복수 자원 + 동시 갱신 = 잠금 순서 문제의 등장 조건.

- Q: Q2. 이게 정확히 동시에 두 번 오면?\
  A: 차감끼리 겹치면 lost update(오버셀), 복원끼리 겹치면 이중 복원(역시 오버셀).\
  서로 다른 주문이 겹치면 잠금 순서에 따라 데드락.\
  답: 조건부 UPDATE + order_id 멱등 + product_id 정렬.

- Q: Q3. 중간에 끊기면 어디까지 남는가?\
  A: 트랜잭션 안이면 전부 롤백 — "하나라도 부족하면 전체 실패"가 공짜로 따라온다.\
  트랜잭션 밖(차감 성공 후 주문 생성 실패, 복원 직전 사망)이면 재고가 허공에 잠긴다.\
  흔적(이력)이 남아야 sweeper·대사가 회수할 수 있다.

#### 8. 파생 — 왜 / 예측 / 경계 / 연결

- Q: "두 스토어에 걸친 불변식은 강제할 수 없다"가 참인 이유는?\
  A: 트랜잭션(ACID)은 한 저장소 안의 보장이기 때문이다.\
  Redis 쓰기와 MySQL 쓰기 사이에는 커밋을 함께 묶어줄 장치가 없다 — 한쪽만 성공한 순간이 반드시 존재한다.\
  분산 트랜잭션(2PC)은 비용·가용성 문제로 실무 기본값이 아니다.\
  그래서 실무 해법은 "불변식이 걸친 데이터를 한 저장소로 모으는 것"(Shopify) 또는 어긋남을 전제로 대사하는 것이다.

- Q: incident.io 간헐 데드락의 원인은?\
  A: **Go map 순회 순서가 랜덤**이라 bulk upsert의 행 순서가 실행마다 달랐다.\
  같은 코드·같은 행 집합이어도 잠그는 순서가 다르면 데드락 조건이 성립한다.\
  근거 원문: "Postgres는 bulk insert에서 영향받는 행을 문장 시작 시 한꺼번에가 아니라 **행 단위로 순차** 잠근다."\
  교훈: 잠금 순서는 언어 런타임의 우연에 맡기지 말고 명시적으로 정렬하라.

- Q: 논리적으로 안 겹치는 ETL이 충돌한 원인과 해법은?\
  A: 원인은 **물리 저장 순서와 gap lock** — 순차 대리키라 서로 다른 계정의 행들이 물리적으로 이웃해 있었고, unique 충돌 시 잡히는 gap lock이 겹쳤다.\
  해법: PK를 `(account, id)` 복합키로 바꿔 계정별로 물리 클러스터링 — gap lock이 파티션 안에 갇힌다.\
  "논리적 분리 ≠ 물리적 분리"라는 고급 교훈.\
  행 잠금만 생각하면 안 보이는 충돌이다.

- Q: 없는 행에 UPDATE를 치면(Mercari 케이스 2)?\
  A: 매칭되는 행이 없으면 **인덱스 갭 전체에 잠금**이 걸릴 수 있다(MySQL gap lock).\
  그 갭에 들어올 무관한 INSERT들이 줄줄이 막힌다.\
  UPSERT로 재고 행을 처음 만드는 설계라면 이 경로를 주의해야 한다.\
  "UPDATE는 있는 행만 잠근다"는 직관이 깨지는 지점이다.

> **UPSERT** — 없으면 INSERT, 있으면 UPDATE를 한 번에 하는 연산.\
> 예: 재고 행을 처음 만드는 설계라면 갭 잠금 경로를 주의해야 한다.

- Q: 오버셀과 언더셀이 같은 버그인 이유는?\
  A: 둘 다 **"실제 재고와 시스템이 아는 재고의 불일치"** 라는 하나의 버그이고, 불일치의 부호만 다르다.\
  오버셀 = 시스템이 실제보다 많다고 앎, 언더셀 = 실제보다 적다고 앎.\
  같은 원인(두 저장소 비원자 쓰기, 복원 누락/중복)이 순서에 따라 어느 쪽으로든 나타난다.\
  "수량이 새는 것만 사고"라는 인식이면 언더셀을 장애로 세지 않게 된다 — Shopify: "merchant loses a sale."

- Q: 01번의 원장 개념이 다시 나타나는 곳은?\
  A: **차감 이력**(C)이다.\
  재고 숫자는 파생값, 이력이 정본 — 멱등 판정(중복 차감·복원 방지), 복원 근거, 대사(H)가 전부 이력에서 나온다.\
  Netflix 카운터도 같은 사상: 값 대신 멱등키를 단 이벤트를 쌓고 집계는 한 번만.\
  "숫자만 고치는 설계"가 왜 지는지의 공통 답이다.

- Q: debugging 박스 짝은?\
  A: A 차감 방식 → `debugging/01-lost-update`.\
  B 잠금 순서 → `debugging/04-lock-ordering`.\
  C 멱등성 → `debugging/02-toctou-idempotency` + `debugging/06-retry-duplication`.\
  F 부분 실패 → `debugging/03-partial-failure`.
