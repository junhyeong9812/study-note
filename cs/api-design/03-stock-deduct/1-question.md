### A. 문제 (REQUIREMENTS.md — 재고 차감 / 복원 API)

```text
POST   /orders/{order_id}/stock      재고 차감
DELETE /orders/{order_id}/stock      재고 복원

{ "items": [ { "product_id": 501, "quantity": 2 },
             { "product_id": 733, "quantity": 1 } ] }

배경
  현재는 결제 완료 시점에 재고를 차감하고 있는데, "장바구니에 담을 때는
  있었는데 결제하려니 품절" 문의가 늘고 있습니다.
  재고 확보 시점을 앞당기는 방향도 함께 검토하고 있습니다.

기대 동작
  1. 주문에 포함된 각 상품의 재고를 요청 수량만큼 차감합니다.
  2. 재고가 부족한 상품이 하나라도 있으면 주문 전체가 실패해야 합니다.
  3. 주문이 취소되면 차감했던 재고를 되돌립니다.
  4. 재고가 실제 수량보다 많이 팔리는 일이 없어야 합니다.

참고
  - 인기 상품은 오픈 직후 초당 수백 건의 주문이 몰립니다.
  - 한 주문에 최대 20개 상품까지 담을 수 있습니다.
```

#### 1. 지문 읽기 — 숨은 요구

- 단일 상품 차감은 01번과 같다면, 이 문제에 새로 들어오는 축 둘은 무엇인가?
- 배경 문단("결제하려니 품절" → 확보 시점 앞당기기 검토)은 어떤 숨은 주제를 유도하는가?
- 공통 질문 3개를 이 지문에 돌리면 각각 무엇이 나오는가?

#### 2. 차감 방식 (A)

- 재고 차감의 조건부 UPDATE는 어떻게 생겼고, 부족은 무엇으로 판정하는가?
- 재고가 음수가 될 수 없음을 보장하는 것은 무엇인가?

#### 3. 여러 상품의 원자성과 잠금 순서 (B — 이 문제의 고유 변별점)

- 20개 상품 중 15번째에서 재고가 부족하면 앞의 14개는 어떻게 되어야 하고, 무엇이 그걸 가능하게 하는가?
- 두 주문이 서로 반대 순서로 상품을 잠그면 무슨 일이 일어나는가?
- 데드락을 구조적으로 없애는 방법은 무엇인가?
- 같은 상품이 items에 두 번 들어오면 어떻게 처리해야 하는가?
- 잠금 순서 고정의 비용(트레이드오프)은 무엇인가?

#### 4. 복원 멱등성 (C — 숨은 변별점)

- 복원 요청이 두 번 실행되면 무슨 일이 생기는가?
- 복원이 차감보다 위험한 이유를 한 문장으로 설명할 수 있는가?
- 차감 이력 없이 재고 숫자만 고치면 무엇을 잃는가?
- 차감한 적 없는 주문에 복원 요청이 오면 어떻게 해야 하는가?
- 이 API의 자연 멱등 키는 무엇인가?

#### 5. 예약 vs 차감 (D — 배경 문단이 유도)

- "결제 전에 재고를 확보한다"는 것은 차감인가 예약인가 — 둘의 차이는 무엇인가?
- 예약에 만료가 없으면 무슨 일이 벌어지는가?
- 만료된 예약은 누가 회수하는가(선택지 둘)?
- Shopify는 예약과 원장을 어떻게 배치해서 원자성을 얻었는가?

#### 6. 저장소 선택·부분 실패·응답 (E, F, G, H)

- 재고를 Redis와 DB 두 곳에 두면 왜 사고가 나는가 — 순서에 따라 어느 방향 사고가 나는가?
- 차감은 됐는데 주문 생성이 실패하면 재고는 어떻게 되고, 무엇이 있어야 회수할 수 있는가?
- 재고 부족 응답에 무엇을 담아야 하고, 4xx인가 5xx인가?
- 오버셀이 발생했다는 것을 고객 문의 전에 알 수 있으려면 무엇이 필요한가?
