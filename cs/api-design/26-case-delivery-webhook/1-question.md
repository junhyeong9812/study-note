### A. 문제 (REQUIREMENTS.md — 배송 상태 웹훅 수신 API)

```text
POST /webhooks/delivery
X-Carrier-Signature: sha256=...
{ "event_id": "evt_9f8a7b", "tracking_number": "1234567890",
  "status": "IN_TRANSIT", "occurred_at": "2026-08-13T09:12:00Z" }

상태 값: ACCEPTED, IN_TRANSIT, OUT_FOR_DELIVERY, DELIVERED, RETURNED

기대 동작
  1. 웹훅을 받아 해당 배송의 상태를 갱신합니다.
  2. 배송 완료(DELIVERED) 시 주문을 배송완료로 바꾸고 구매확정 타이머를 시작합니다.
  3. 택배사에 2초 이내로 응답해야 합니다. 그렇지 않으면 택배사가 실패로 간주합니다.
  4. 우리 시스템 장애로 웹훅을 놓치면 안 됩니다.

참고
  - 하루 웹훅 수신량은 평균 50만 건, 피크 시간대에 집중됩니다.
  - 택배사는 여러 곳이고, 각 택배사마다 페이로드 형식이 조금씩 다릅니다.
  - 택배사 문서에 "응답이 없으면 최대 24시간 동안 재전송한다"고 적혀 있습니다.
```

1. 지문 읽기 — 숨은 요구

- "응답이 없으면 최대 24시간 동안 재전송" 한 줄은 무엇의 선언이고, 무엇을 수신자 책임으로 만드는가?
- 이 문제의 숨은 요구 축들은 무엇이고, 그중 "자주 놓치는" 고유 변별점은 무엇인가?
- 공통 질문 3개를 이 지문에 돌리면 각각 무엇이 나오는가?

2. 중복 수신 (A — 중요)

- 웹훅에서 중복이 "정상 동작"인 이유는 무엇인가?
- "event_id 조회해서 없으면 처리"는 왜 방어가 아닌가?
- 중복이 서로 다른 서버 인스턴스에 동시에 도착하면 무엇으로 막는가?
- dedup 기록과 실제 처리를 같은 트랜잭션에 묶어야 하는 이유는 — 따로 커밋하면 무슨 일이 나는가?
- dedup 기록 보관 기간은 무엇보다 길어야 하고, 짧으면 어떻게 되는가?

3. 순서 뒤바뀜 (B — 고유 변별점)

- 이벤트는 왜 발생 순서대로 도착하지 않는가?
- DELIVERED 다음에 IN_TRANSIT이 도착했을 때 그냥 UPDATE 하면 무슨 사고가 나는가?
- 오래된 이벤트가 새 상태를 덮지 못하게 하는 방법 두 가지는 무엇이고, 어느 쪽이 더 견고한가?
- `occurred_at`을 그대로 믿으면 안 되는 이유 두 가지는?
- 순서를 애초에 보존하는 파티셔닝 키는 무엇으로 잡는가?

4. 응답 시간과 200의 의미 (C)

- 2초 제한에서 무거운 처리를 동기로 하면 어떻게 되고, 표준 구조는 무엇인가?
- 수신과 처리를 분리하는 순간 생기는 새 구간은 무엇인가?
- 200을 주는 시점이 보장해야 하는 것은 무엇인가?
- 큐 적재가 실패했을 때 200을 주면 안 되는 이유는?

5. 유실 (D — 지문 4번)

- 우리가 5xx를 주는 것이 왜 "안전망을 켜는 것"인가?
- 웹훅만 믿으면 안 되는 이유는 — 발신 측에서 무슨 일이 일어날 수 있는가?
- 지문의 "폴링을 걷어낸다"가 함정인 이유는?

6. 인증·처리량·부수효과·관측 (E, F, G, H, I)

- 서명 검증은 왜 본문 파싱 전에 해야 하고, 검증 실패에는 어떤 응답을 주는가?
- head-of-line blocking과 poison pill은 각각 무엇이고 어떻게 막는가?
- 다중 택배사에서 event_id를 그대로 멱등 키로 쓰면 어떤 위험이 있는가?
- DELIVERED가 켜는 구매확정 타이머가 두 번 실행되면 — 부수효과에는 무엇이 필요한가?
- 웹훅이 "안 오는 것"은 왜 로그에 안 남고, 어떻게 감지하는가?
