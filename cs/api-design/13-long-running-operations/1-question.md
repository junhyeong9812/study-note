# api-design/13-long-running-operations — 질문

## 질문

1. (왜) 90초 걸리는 리포트를 동기 `POST`로 처리하는데 LB 읽기 타임아웃이 60초다. 클라이언트와 서버에서 각각 무슨 일이 생기나? 클라이언트가 받은 `504`는 무엇을 뜻하고 무엇을 뜻하지 않나?
2. (그림) `202 Accepted` + 작업 자원 + 폴링 시퀀스를 그려라. 각 응답에 들어가는 헤더와 작업 자원 본문의 핵심 필드를 적어라.
3. (예측) 실험에서 nginx `proxy_read_timeout 3s` 뒤에 6초 작업을 동기로 두 번 요청하면 클라이언트가 받는 상태 코드와 서버가 만든 리포트 수는? 같은 `Idempotency-Key`로 `POST /reports`를 두 번 보낸 뒤 폴링하면?
4. (경계) RFC 9110의 `202`는 무엇을 약속하고 무엇을 약속하지 않나? HTTP가 비동기 작업의 결과 상태 코드를 전달하지 못하는 이유와, 그래서 결과를 어디에 두나?
5. (연결) Google AIP-151의 `Operation`과 Azure 가이드의 status monitor를 비교하라. AIP가 말하는 "오래 걸린다"의 경험칙과 완료 작업 만료의 경험칙은?
6. (그림) 작업 상태 기계를 그리고, 상태 전이를 원자적으로 만드는 SQL 한 줄을 써라. 취소와 완료가 동시에 일어나면 어떻게 되나?
7. (경계) AIP `CancelOperation`과 `WaitOperation`은 각각 무엇을 보장하지 않나? 클라이언트는 그 대신 무엇을 확인해야 하나?
8. (장애 진단) 작업 조회 API가 전체 트래픽의 대부분을 차지한다. 작업당 GET이 수백 건이다. 원인과 서버·클라이언트 양쪽 대처는?
9. (장애 진단) 진행률이 몇 시간째 40%에서 멈춘 작업이 여럿 있다. 어떤 쿼리로 찾고, 왜 생기며, 어떻게 막나?
10. (경계) 작업 자원 URL이 `/operations/1001`처럼 순번이다. 무엇이 위험하고 어떻게 고치나?
