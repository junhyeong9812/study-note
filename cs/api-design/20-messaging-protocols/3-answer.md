# api-design/20-messaging-protocols — 정답

## 정답

### 1. 브로커의 이득과 대가

- 이득: 생산자와 소비자를 **시간**(동시에 살아 있을 필요 없음)과 **공간**(서로 주소를 몰라도 됨)으로 분리한다. 받는 쪽이 죽어도 메시지가 브로커에 쌓였다가 나중에 처리된다. 팬아웃·흐름 제어(소비자가 속도 결정)도 브로커가 맡는다.
- 대가: 호출자가 결과를 바로 모른다. **"언제 전달이 끝났나"(ack 위치)**를 정해야 하고, 그에 따라 유실이나 중복이 생긴다. 순서·재처리·DLQ도 설계해야 한다.

### 2. 세 프로토콜의 흐름

```text
  AMQP  생산자 ─> exchange ─binding─> queue ─push─> 소비자 ─basic.ack─> 큐에서 삭제
  MQTT  발행자 ─PUBLISH─> broker ─PUBLISH─> 구독자       (구간마다 QoS)
  Kafka 생산자 ─Produce─> partition 로그 <─Fetch─ 소비자 ─ 오프셋 커밋(위치만)
```

- AMQP: 구독이면 push(권장), `basic.get`은 pull(문서가 매우 비효율적이라 함). ack되면 큐에서 지운다.
- MQTT: 브로커가 구독자에게 push한다.
- Kafka: 소비자가 pull한다. 브로커는 소비했다고 지우지 않는다 — 그룹별 오프셋만 저장하고 로그는 보존 정책으로 지운다.

### 3. MQTT QoS

```text
  QoS 0  PUBLISH ──>                                   0번 또는 1번 (응답·재전송 없음)
  QoS 1  PUBLISH ──>  <── PUBACK                       1번 이상 (PUBACK 전까지 재전송, 중복 가능)
  QoS 2  PUBLISH ──>  <── PUBREC  PUBREL ──>  <── PUBCOMP   정확히 1번 (그 구간)
```

- QoS는 발행자→브로커, 브로커→구독자 구간마다 따로다.
- 구독자 구간 QoS = min(발행 QoS, 브로커가 허락한 최대 QoS)(MQTT-3.8.4-8). 질문의 경우 구독 쪽이 최대 0만 허락받았다면 **QoS 0** — 그 구간에서 유실될 수 있다. 명세는 이 경우 서버가 중복 사본을 보내는 것도 허용한다.

### 4. 커밋 여부와 재실행 결과

- 실험 출력(apache/kafka 4.1.0)
  - 그룹 A(`g-manual`): 1회차 m1~m3, 2회차도 **m1~m3**. 커밋한 오프셋이 없어 처음부터 다시 받는다.
  - 그룹 B(`g-auto`): 1회차 m1~m3, 2회차 **m4~m6**. `--describe`에서 `CURRENT-OFFSET 6`, `LAG 4`.
- A = 처리는 했는데 커밋 전에 죽음 → **중복**(at-least-once).
- B = 이 실행에서는 m1~m3를 출력(처리)한 뒤 종료하면서 커밋했다 → 처리 후 커밋이라 정상 경로다. 같은 위치 이동이 **처리 전에** 일어나고(자동 커밋이 처리 완료보다 앞섬) 처리 중 죽으면, 처리 못 한 메시지가 이 그룹에서 다시 오지 않는다 → **유실**(at-most-once). 실험은 처리 실패를 만들지 않았으므로 유실은 위치 이동에서 끌어낸 해석이다(개수 실험은 distributed/17).

### 5. AMQP 자동 ack vs 수동 ack

- 자동 ack: 브로커가 메시지를 **보낸 직후** 전달 성공으로 친다(RabbitMQ 문서 "fire-and-forget"). 소비자가 처리 전에 죽으면 유실.
- 수동 ack: 소비자가 `basic.ack`를 보낼 때 끝난다. ack 전에 채널·연결이 닫히면 ack 안 된 전달은 **자동으로 재큐잉**되고 `redeliver` 플래그가 켜진 채 다시 전달된다 — 그래서 중복 처리 대비가 필요하다.

### 6. Kafka 4.1 기본값

| 쪽 | 설정 | 기본값 |
|---|---|---|
| 생산자 | `acks` | `all`(모든 ISR이 받아야 성공) |
| 생산자 | `enable.idempotence` | `true` |
| 소비자 | `enable.auto.commit` | `true` |
| 소비자 | `auto.commit.interval.ms` | 5000 |

- 자동 커밋은 처리 완료와 무관하게 **주기적으로**(그리고 종료 시) 현재 위치를 커밋한다. 처리 도중 죽으면 커밋 시점에 따라 처리 못 한 메시지를 건너뛰거나(유실) 처리한 메시지를 다시 받는다(중복).

### 7. 끊김 감지

- TCP만으로는 상대가 전원 장애로 사라진 것을 늦게 안다(RabbitMQ 문서: 리눅스 기본 설정에서 약 11분). 그동안 죽은 소비자가 unacked 메시지·파티션을 붙잡는다.
- MQTT 5.0: Keep Alive × **1.5** 안에 패킷이 없으면 서버가 연결을 닫는다(MQTT-3.1.2-22). 비정상 종료면 Will 메시지를 발행한다.
- RabbitMQ: heartbeat 타임아웃의 서버 제안 기본값 **60초**(문서는 대부분 환경에 5~20초가 최적이라 한다), 그 절반 간격으로 보내고 **2번** 놓치면 연결을 닫는다.
- Kafka(classic 그룹 프로토콜): `session.timeout.ms` 기본 **45초**, `heartbeat.interval.ms` 기본 3초. 넘기면 그룹에서 빠지고 리밸런스.
- 너무 짧게 잡으면 GC 정지·순간 지연에도 끊겨 재연결·리밸런스가 잦아진다.

### 8. lag 0인데 처리 안 된 주문

- 원인: 처리 전 ack — AMQP 자동 ack, Kafka 처리 전 커밋·자동 커밋. 브로커는 이미 전달 끝으로 쳤다.
- 대처: 수동 ack·`enable.auto.commit=false` + 처리 **후** 커밋.
- 새 문제: ack 전에 죽으면 다시 전달된다 → 중복.
- 해결: 멱등 소비 — 메시지 ID(또는 업무 키)를 인박스 테이블·유일 제약으로 기록하고 이미 처리한 것은 건너뛴다. 외부 부작용에는 멱등 키를 함께 보낸다.

### 9. 소비자 힙 포화

- 확인: 큐의 `unacked` 수가 소비자 처리 능력보다 훨씬 큰지, 채널에 prefetch(`basic.qos`)가 설정됐는지.
- 원인: prefetch가 없으면 브로커가 ack 안 된 메시지를 제한 없이 밀어 넣어 소비자 메모리에 쌓인다.
- 대처: prefetch를 건다(RabbitMQ 문서: 보통 100~300 범위가 처리량이 좋다). 처리 시간이 긴 작업이면 더 작게. Kafka라면 pull이라 `max.poll.records` 등으로 한 번에 가져오는 양을 조절한다.
