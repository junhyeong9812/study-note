# api-design/05-idempotency-keys — 정답

## 정답

### 1. 타임아웃 뒤의 세 가지 경우

```text
 (가) 요청 유실           C ──X                      서버는 모른다
 (나) 처리 후 응답 유실    C ──▶ S [완료] ──X
 (다) 처리 중             C ──▶ S [처리 중....]
```

- 클라이언트는 셋을 구분하지 못한다. 셋 다 "타임아웃"으로 보인다.
- 서버가 `(계정, 키)`를 기억하면
  - (가) 처음 보는 키 → 처리한다. 결과는 1번.
  - (나) 완료된 키 → 저장한 첫 응답을 재생한다. 두 번째 실행이 없다.
  - (다) 처리 중인 키 → 409를 준다. 클라이언트는 잠시 뒤 같은 키로 다시 와서 재생을 받는다.

### 2. 두 "멱등"

- RFC 9110 §9.2.2: 같은 요청을 여러 번 보냈을 때 서버에 대한 **의도한 효과**가 한 번과 같은 **메서드의 성질**이다. PUT·DELETE·안전 메서드가 해당한다.
  - 응답은 달라도 된다. 첫 `DELETE`가 지웠으니 두 번째는 404를 받아도, "그 자원이 없다"는 효과는 같다.
- Stripe `Idempotency-Key`: 비멱등 메서드(POST)에 대해 **서버가 키 단위로 하는 약속**이다. 같은 키면 한 번만 실행하고, 첫 응답(상태 코드·본문)을 **재생**한다. 즉 응답까지 같게 해 준다(Stripe v1 기준).
- 앞의 것은 메서드 의미론, 뒤의 것은 API 계약 + 서버 구현이다.

### 3. JDK 21 HttpClient 자동 재전송

실험 A(JDK 21.0.12) 결과:

| 메서드 | 기본 | `enableAllMethodRetry=true` |
|---|---|---|
| GET | 서버 2회 수신, 클라이언트는 200 | 2회, 200 |
| POST | 1회, 클라이언트 `IOException` | 2회, 200 |
| PUT | 1회, `IOException` | 2회, 200 |
| DELETE | 1회, `IOException` | 2회, 200 |

- OpenJDK jdk21u `MultiExchange.isIdempotentRequest`가 `GET`·`HEAD`만 참으로 본다. 그래서 RFC상 멱등인 PUT·DELETE도 기본으로는 다시 보내지 않는다.
- 재전송 조건은 재사용 연결이 응답 전에 닫힌 경우(`ConnectionExpiredException`), 연결 실패(`ConnectException`), HTTP/2에서 상대가 처리하지 않았다고 알린 요청(`isUnprocessedByPeer`)이고, 한 번만 한다. GET·HEAD 제한은 첫 번째 경우에만 걸린다. 나머지 둘은 서버가 처리하지 않은 요청이니 메서드와 무관하게 다시 보낸다.
- 교훈: 프로토콜의 멱등 목록과 라이브러리의 재시도 목록은 다르다. 속성 하나로 POST도 다시 갈 수 있으니, 서버는 재시도를 전제로 설계한다.

### 4. 재시도와 결제 행 수

실험 B 결과(3회 실행에서 같음):

- (a) 키 없음: 4번 다 타임아웃, **결제 4건**. 클라이언트는 실패만 봤지만 서버는 매번 처리를 끝냈다.
- (b) 같은 키: 시도1 타임아웃 → 시도2(350ms 무렵)에서 `201 replayed {"id":5}`. **결제 1건**.
- (c) 시도마다 새 키: 4번 다 타임아웃, **결제 4건**. 서버가 키를 지원해도 매번 처음 보는 키라 소용이 없다.
- 키는 시도가 아니라 사용자 의도(논리 작업) 하나에 하나다. 재시도 루프 밖에서 만든다.

### 5. 같은 키, 다른 요청

실험 B S4:

```text
  1차(1000): 201 {"id":10}
  2차(5000): 422 {"title":"Idempotency-Key is already used"}
  3차(1000): 201 replayed {"id":10}
  다른 계정 같은 키(1000): 201 {"id":11}
```

- (1) 금액만 바꿈 → 지문이 다르다 → **422**(초안 §2.7). 재생하면 엉뚱한 결과를, 새로 처리하면 키의 의미를 깬다.
- (2) 같은 요청 → 첫 응답 재생.
- (3) 다른 계정 → 별개 요청이다. 저장소 키가 `(계정, 키)`이기 때문이다(초안 §5의 복합 키 권고).
- 초안 -07 권고: 키 누락 400, 다른 본문 422, 처리 중 409. 400·422 뒤에는 요청을 고쳐야 하고, 409는 고칠 필요 없이 다시 보내면 된다.

### 6. 동시 같은 키

- 실험 B S6: `{201=1, 409=9}`, 결제 1건.
- 원자성은 `(account, idem_key)` 기본 키의 **유일 제약**이 준다. `INSERT … ON CONFLICT DO NOTHING`에서 1행을 넣은 쪽만 처리하러 간다. "SELECT로 확인 후 INSERT"로 나누면 그 틈에 여럿이 통과한다([reliability/13](../../reliability/13-idempotency/2-summary.md) 실험 naive).
- 409를 받은 클라이언트는 백오프 후 **같은 키로** 다시 보낸다. 처리가 끝났으면 재생을 받는다.

### 7. 출처별 규칙

| | 실패한 첫 요청 | 보관 기간 |
|---|---|---|
| IETF 초안 -07 | 완료된 결과는 성공이든 에러든 재생(SHOULD) | 서버가 정해 문서에 공개(SHOULD) |
| Stripe v1 | 실행이 시작된 뒤의 결과는 성공·실패 무관 저장, 500도 재생. 검증 실패·동시 충돌은 저장 안 함 | 24시간 이상 지나면 지울 수 있음 |
| Stripe v2 | 실패(부분 실패 포함)한 요청은 부작용 없이 **다시 실행**해 새 응답 | 같은 API·같은 계정에서 30일 |
| AIP-155 | 이전 **성공** 응답을 돌려준다(should) | "합리적 기간" |

- 초안 지위: draft-ietf-httpapi-idempotency-key-header-07(2025-10-15 게시, 2026-04-18 만료)은 만료된 Internet-Draft다. RFC가 아니다. 값 형식은 Structured Field String(따옴표)으로 정의한다.

### 8. 키 없이 재시도 안전성 얻기

- (a) **클라이언트가 ID를 정하는 PUT**: `PUT /payments/pay_7f3e…`. PUT은 본래 멱등이라 두 번 보내도 자원 하나다. "없을 때만 생성"은 `If-None-Match: *`(이미 있으면 412).
- (b) **업무 키 유일 제약**: 주문당 결제 1건처럼 업무상 한 번뿐인 동작은 `order_id`에 유일 제약을 건다. 보관 기간이 없어 오래 뒤 재시도에도 막힌다(사례 22).
- 키 방식이 맞는 경우: 같은 내용을 정상적으로 여러 번 할 수 있는 동작(같은 금액 송금 두 번)이라 업무 키로 "이번 시도"를 구분할 수 없을 때.

### 9. 남의 응답이 재생된다

- 의심 원인
  - 저장소를 키 문자열 하나로 조회했다. 계정 범위가 없다.
  - SDK 버그로 키가 짧거나 순차적이어서 다른 사용자 키와 겹쳤다. 초안 §5는 저엔트로피 키로 남의 저장 응답을 꺼내는 "Data leaks"를 경고한다.
- 대처
  - 저장소 키를 `(계정, 클라이언트 키)`로 바꾼다.
  - 키 형식을 UUID로 검증하고 아니면 400.
  - 재생 응답의 계정과 요청 계정이 다르면 거절하는 방어 검사, 영향 범위 조사.

### 10. 하루 뒤 재시도

- 키가 같아도 저장소가 그 키를 이미 지웠다. Stripe v1은 24시간 이상 지난 키를 정리할 수 있고, 정리된 뒤 같은 키는 새 요청이 된다.
- 막는 법
  - 보관 기간을 문서에 쓰고, SDK의 재시도 기간을 그보다 짧게 한다. 넘으면 재시도 대신 "상태 조회"로 바꾼다.
  - 주문처럼 한 번뿐인 동작은 업무 키 유일 제약을 함께 둔다(8번 (b)).
