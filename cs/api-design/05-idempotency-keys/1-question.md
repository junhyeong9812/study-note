# api-design/05-idempotency-keys — 질문

## 질문

1. (왜) 클라이언트가 결제 요청에서 타임아웃을 받았다. 서버 쪽에서 일어났을 수 있는 일 세 가지를 그리고, 멱등 키가 각 경우를 어떻게 안전하게 만드는지 설명하라.
2. (경계) RFC 9110의 "멱등"과 Stripe `Idempotency-Key`의 "멱등"은 무엇이 다른가? 두 번째 `DELETE`가 404를 받아도 멱등인 이유는?
3. (예측) JDK 21 HttpClient로 keep-alive 연결을 재사용한 요청을 보냈는데, 서버가 요청을 다 읽고 응답 없이 연결을 닫았다. GET·POST·PUT·DELETE 각각에서 서버는 그 요청을 몇 번 받나? `jdk.httpclient.enableAllMethodRetry=true`를 켜면?
4. (예측) 서버 처리 300ms, 클라이언트 타임아웃 150ms, 최대 4회 재시도다. (a) 멱등 키가 없을 때 (b) 같은 키로 재시도할 때 (c) 시도마다 새 키를 만들 때, 결제 행은 각각 몇 개 생기나?
5. (경계) 같은 키로 (1) 금액만 바꾼 요청 (2) 원래와 같은 요청 (3) 다른 계정이 같은 키 문자열로 보낸 요청이 오면 서버는 각각 무엇을 돌려줘야 하나? IETF 초안이 권하는 상태 코드는?
6. (연결) 같은 키로 동시에 10개 요청이 오면 몇 개가 처리되고 나머지는 무엇을 받나? 그 원자성은 무엇이 주나? 409를 받은 클라이언트는 어떻게 해야 하나?
7. (경계) IETF 초안 -07, Stripe v1, Stripe v2, Google AIP-155는 "실패한 첫 요청"과 "보관 기간"을 각각 어떻게 다루나? 초안의 지위는?
8. (설계) 멱등 키 저장소 없이 재시도 안전성을 얻는 설계 두 가지를 대고, 키 방식이 더 맞는 경우를 말하라.
9. (장애 진단) 결제 서비스에서 "고객 B의 결제 응답에 고객 A의 카드 정보가 보였다"는 신고가 들어왔다. 멱등 계층에서 의심할 원인과 대처는?
10. (장애 진단) 앱이 오프라인에서 쌓아 둔 주문 요청을 다음 날 보냈더니 주문이 두 건 생겼다. 키는 같았다. 왜 막히지 않았고, 어떻게 막나?
