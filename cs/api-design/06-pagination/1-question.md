# api-design/06-pagination — 질문

## 질문

1. (왜) 목록 API에 페이지네이션이 필요한 이유는? offset 방식과 커서(keyset) 방식이 "다음 쪽"을 가리키는 방법의 차이를 책 비유로 설명하라.
2. (예측) 100만 행 테이블에 `(created_at DESC, id DESC)` 인덱스가 있다. `LIMIT 20 OFFSET 999980`과 같은 깊이의 keyset 쿼리를 `EXPLAIN ANALYZE`하면 자식 노드의 `actual rows`는 각각 얼마이고, 실행 시간은 어느 자릿수인가?
3. (예측) 50개씩 넘기는 동안 페이지마다 (a) 새 글 3개가 맨 앞에 들어오고 본 글 1개가 지워질 때 (b) 새 글 1개가 들어오고 본 글 3개가 지워질 때, offset과 커서의 중복·누락은 어떻게 되나?
4. (경계) 커서 방식이 막지 못하는 중복·누락 또는 "안 보임"은 무엇인가? 한 시점의 일관된 목록이 필요하면 어떤 방식이 있나?
5. (경계) `ORDER BY created_at`만으로 페이지를 넘기면 데이터가 바뀌지 않아도 어떤 문제가 생기나? 고치는 법은?
6. (연결) AIP-158은 `page_size`의 생략·상한 초과·음수, 토큰의 성질, 다른 인자 변경을 각각 어떻게 다루라고 하나?
7. (설계) 페이지 토큰을 `?after_created=…&after_id=…`처럼 읽을 수 있게 노출하면 어떤 일이 생기나? base64 인코딩과 HMAC 서명은 각각 무엇을 막고 무엇을 못 막나?
8. (경계) 응답마다 `total_size`(전체 건수)를 주는 것의 비용은? 실험 테이블에서 `count(*)`는 얼마였나?
9. (장애 진단) 평소 빠른 목록 API가 특정 시간대에 느려지고 DB CPU가 오른다. 무엇을 확인하고 어떻게 대처하나?
10. (장애 진단) offset 클라이언트가 "빈 페이지가 나오면 끝"으로 순회했더니, 쓰기가 많은 시간에 순회가 끝나지 않았다. 왜인가? 어떤 응답 계약이 이를 막나?
