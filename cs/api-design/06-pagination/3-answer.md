# api-design/06-pagination — 정답

## 정답

### 1. 왜 자르나, 무엇으로 가리키나

- 결과 전체를 한 응답에 담으면 서버 메모리·응답 시간·클라이언트가 버티지 못한다. 그래서 잘라 준다.
- offset = "앞에서 300쪽 넘겨라". 앞쪽에 쪽이 끼면 읽은 쪽을 또 읽고, 빠지면 못 읽은 쪽이 생긴다. 매번 300쪽을 넘기니 느리다.
- 커서(keyset) = 책갈피. "마지막으로 본 행의 정렬 키 다음부터". 앞쪽 변화와 무관하고, 인덱스로 바로 그 자리로 간다.

### 2. 깊은 offset vs keyset

실험 A(PostgreSQL 17.11, 100만 행, 각 3회):

| | 자식 노드 `actual rows` | 실행 시간 |
|---|---|---|
| `OFFSET 999980` | 1,000,000 | 379.114 ~ 454.388 ms |
| keyset(같은 깊이, 같은 20행) | 20 | 0.111 ~ 0.123 ms |

- offset은 건너뛸 행을 실제로 읽고 버린다. 깊이에 비례해 늘었다(offset 10만: 39.313~42.831ms, 50만: 206.104~233.113ms).
- keyset은 B+Tree로 경계(앞 페이지의 마지막 행)까지 내려가 필요한 20행만 읽었다. 두 쿼리가 돌려준 `id` 목록은 같았다.
- 수치는 2 CPU 제한·캐시 적중 환경의 값이다. 자릿수 차이를 읽는다.

### 3. 순회 중 쓰기

실험 B(1000행, 50개씩, 2회 실행 같은 결과):

```text
쓰기(페이지마다 삽입 3·삭제 1) offset 중복 40, 누락 0
쓰기(페이지마다 삽입 3·삭제 1) cursor 중복 0,  누락 0
쓰기(페이지마다 삽입 1·삭제 3) offset 중복 0,  누락 33
쓰기(페이지마다 삽입 1·삭제 3) cursor 중복 0,  누락 0
```

- (a) 앞쪽이 페이지마다 순증 2 → offset은 2칸씩 밀려 이미 본 행을 또 받는다(20번 × 2 = 40).
- (b) 앞쪽이 줄어든다 → offset이 당겨져 못 본 행을 건너뛴다(33개, 그 행들은 순회 내내 DB에 있었다).
- 커서는 "이 값 다음"이라 두 경우 모두 원래 1000행을 정확히 한 번씩 받았다.

### 4. 커서의 한계와 스냅샷

- 커서보다 앞쪽에 새로 들어온 행은 이번 순회에서 안 보인다(실험 B의 새 글들).
- 정렬 키 자체가 바뀌는 행(예: `updated_at` 정렬에서 순회 중 수정)은 커서 앞뒤로 옮겨져 중복·누락될 수 있다.
- 한 시점의 일관된 목록이 필요하면 스냅샷 방식: Kubernetes 목록 API는 `continue` 토큰에 resourceVersion과 위치를 담아 같은 시점의 스냅샷을 보여 준다. 토큰은 기본 5분 뒤 만료되고 `410 Gone`을 준다. 그러면 처음부터 다시 한다.

### 5. 동률 정렬

- 같은 `created_at` 값의 행들은 순서가 정해지지 않는다. 실행마다 순서가 달라질 수 있어 페이지 경계에서 하나가 두 번, 하나는 안 나온다. 데이터 변경이 없어도 그렇다.
- 정렬 끝에 유일 키를 붙인다: `ORDER BY created_at DESC, id DESC`. 커서에도 `(created_at, id)`를 함께 넣는다(Winand: "Paging requires a deterministic sort order").

### 6. AIP-158 규칙

- `page_size`: 필수 아님. 생략·0 → API 기본값(에러 아님). 상한보다 크면 상한으로 깎는다(should). 음수 → `INVALID_ARGUMENT`(must).
- 토큰: 불투명하고 URL 안전, 사용자가 해석할 수 없어야 한다. 위치 표시 외에 쓰지 않고, 권한 부여 수단이 되면 안 된다. 만료시킬 수 있다.
- 다음 요청에서 `page_size`는 바꿀 수 있고 서버는 따라야 한다. 다른 인자가 바뀌면 `INVALID_ARGUMENT`(should).
- 끝이면 `next_page_token`은 비어 있어야 하고, 끝이 아니면 있어야 한다.
- 실험 B에서 필터를 바꾼 토큰 → 400, `page_size=1000` → 100개, `-1` → 400.

### 7. 읽을 수 있는 토큰의 문제

- 클라이언트가 형식을 해석하거나 직접 만든다. 서버가 정렬 키를 바꾸면 그 클라이언트가 깨진다(Hyrum의 법칙). 범위 밖 값을 넣어 이상한 쿼리를 만들 수도 있다.
- base64(url): 문자열을 URL 안전하게 만들 뿐이다. 숨기지 못한다. 실험 토큰 앞부분을 디코드하면 `2026-01-01 01:39:00+00|998|status=open`이 보인다.
- HMAC 서명: 조작을 막는다(실험: 조작 토큰 → 400). 내용은 여전히 보인다.
- 내용까지 숨기려면 암호화한다.

### 8. total_size의 비용

- 전체 건수는 조건에 맞는 행을 다 세야 한다. 실험 테이블(100만 행)에서 `SELECT count(*)`는 104~139ms(3회, Parallel Seq Scan)였다(사실 점검 재실행 62~96ms — 실행마다 다르다). 첫 페이지 조회(0.1~0.3ms)의 수백~천 배다.
- 그래서 AIP-158은 `total_size`를 선택(may)으로 둔다. 필요하면 근사치·캐시·별도 요청으로 준다.

### 9. 특정 시간대에 느린 목록

- 확인
  - 느린 쿼리 로그·접근 로그에서 `offset`·`page` 값 분포. 수십만 값이 있으면 깊은 offset이다.
  - 그 쿼리의 `EXPLAIN (ANALYZE)`에서 자식 노드 `actual rows`가 `offset + limit`인지.
  - 요청 주체(크롤러·동기화 배치·특정 파트너).
- 대처
  - 커서로 전환. offset은 최대 깊이를 제한하고 그 너머는 필터·검색으로 좁히게.
  - 대량 내보내기는 별도 배치 API·파일로.

### 10. 끝나지 않는 offset 순회

- 실험 B 첫 작성에서 실제로 겪었다. 페이지마다 행이 2개 늘고, 끝 페이지가 2행이라 offset이 따라가도 끝이 계속 밀렸다. 빈 페이지가 나오지 않았다.
- 서버가 `LIMIT size + 1`로 다음 존재 여부를 판단해 `next_page_token`(또는 `has_more`)을 주고, 클라이언트는 그것이 비면 끝내는 계약이 이를 막는다. AIP-158도 "끝이면 `next_page_token`은 비어야 한다"를 규칙으로 두고, 그것이 끝을 알리는 유일한 방법이라고 적는다. 반대로 API는 끝이 아니어도 요청보다 적은(0개 포함) 결과를 돌려줄 수 있다 — "빈 페이지 = 끝"은 AIP-158 계약에서도 틀린 종료 조건이다.
- 커서 방식이면 새 행은 커서 앞에 들어가므로 이 문제가 생기지 않는다.
