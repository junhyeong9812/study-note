# api-design/09-async-apis-and-webhooks — 정답

## 정답

### 1. 폴링 vs 웹훅, 새로 생기는 책임

- 좋아지는 것: 헛걸음 조회가 없어지고, 바뀐 순간 알 수 있다(폴링은 간격만큼 늦다).
- 보내는 쪽(제공자)의 새 책임
  - 남의 서버를 부르는 HTTP 클라이언트가 된다 → 타임아웃·재전송 일정·실패 목록·수동 재전송.
  - 서명으로 자기가 보냈음을 증명한다.
  - 고객이 등록한 URL을 부르므로 SSRF를 막아야 한다.
- 받는 쪽의 새 책임
  - 인터넷에 열린 엔드포인트 → 서명·타임스탬프 검사.
  - 중복·순서 역전·유실을 견디는 처리(사례 26).
  - 빨리 2xx를 돌려주고 무거운 처리는 큐 뒤로.

### 2. 전달 한 번

```text
  보내는 쪽 ── POST /hooks ──────────────────────────> 받는 쪽
              webhook-id: msg_…          (재전송해도 같음)   ① 타임스탬프 창
              webhook-timestamp: 1674087231 (이번 시도 시각)  ② 서명(원문, 상수 시간 비교)
              webhook-signature: v1,…    (서명 목록)         ③ id 중복
              본문                                           ④ 저장
            <────────────────────────────── 2xx ────────── ⑤ 응답
```

- 성공 = 2xx만. 3xx는 실패, `410`은 엔드포인트 끄기, `429`·`502`·`504`는 속도 줄이기, `retry-after`가 있으면 반영(Standard Webhooks 「Delivery success and failure」).
- `webhook-timestamp`는 **이번 시도**의 시각이라 재전송마다 바뀐다. 본문 `timestamp`는 **사건이 일어난** 시각이라 그대로다(명세 「Webhook metadata」).

### 3. id·타임스탬프까지 서명하는 이유

- 본문만 서명하면, 캡처한 요청의 타임스탬프 헤더만 새 값으로 바꿔 다시 보내도 서명이 맞는다. 타임스탬프 창 검사가 무력해진다.
- 서명 대상이 `id.timestamp.body`면 헤더를 바꾸는 순간 서명이 깨진다.
- 서명이 맞아도 거부할 것
  - 타임스탬프가 허용 창(예: 5분) 밖인 요청 — 재전송 공격.
  - 이미 처리한 webhook-id — 거부라기보다 "이미 받음"으로 2xx를 주고 처리하지 않는다.

### 4. 실험 B 판정

| 요청 | 판정(실험 출력) | 이유 |
|---|---|---|
| ① 30초 뒤 같은 요청 | `DUPLICATE(이미 처리한 webhook-id)` | 창 안, 서명 맞음, id가 이미 있음 |
| ② 금액 1000→1 | `REJECT(signature)` | 본문이 바뀌어 HMAC 불일치 |
| ③ 공백만 다른 본문 | `REJECT(signature)` | 서명은 바이트 단위다 |
| ④ 10분 전 캡처 | `REJECT(timestamp 600s 차이)` | 창 300초 밖 |
| ⑤ 옛+새 서명 | `ACCEPT` | 목록 중 하나라도 맞으면 통과(키 회전) |

### 5. 순서 역전 + 중복

- 도착 순서대로 덮어쓰기: 마지막 도착이 `PAID`라서 최종 `PAID`(실험 C 출력 "그냥 덮어쓰기 최종 = PAID"). 배송된 주문이 되돌아갔다.
- id 중복 제거만: 두 번째 `PAID`는 걸러지지만 `CREATED`·`PAID`가 `SHIPPED`를 덮는 것은 못 막는다. 최종 `PAID`.
- id 중복 제거 + seq 비교: 최종 `SHIPPED`(적용 1, 중복 1, 오래됨 2).
- 교훈: id 중복 제거는 **같은** 이벤트만 거른다. **다른** 이벤트 사이의 순서는 버전 비교나 상태 전이 규칙이 맡는다.

### 6. thin vs full

- full: 바뀐 객체 전체를 싣는다. 추가 조회가 없다.
- thin: ID와 바뀐 사실만 싣는다. 받는 쪽이 API로 최신을 읽는다.
- 순서 관점의 장점(해석): 매번 최신을 조회하니 늦게 온 알림이 옛 상태를 덮지 않는다. 대가는 조회 호출이 늘고 조회 API의 가용성·속도 제한에 기대게 된다는 것.
- 명세가 꼽는 다른 장점: 데이터가 적고, 나중에 full로 바꾸기 쉽고, 데이터 접근을 조회 API의 권한·감사로 통제할 수 있다.
- Stripe(「Event ordering」): 생성 순서를 보장하지 않는다. snapshot 이벤트의 `created`는 초 단위라 겹칠 수 있으니 순서·중복 판정에 쓰지 말고 **이벤트 ID**로 중복을 가려라. 빠진 객체는 API로 조회하라.

### 7. 재전송은 언제 멈추나

- 2xx를 받거나, `410`을 받거나, 일정이 끝나면 멈춘다. 오래 계속 실패하면 명세는 다른 경로로 알리고 엔드포인트를 끄라고 권한다.
- 명세 예시: 즉시, 5초, 5분, 30분, 2시간, 5시간, 10시간, 14시간, 20시간, 24시간 → 누적 75:35:05(약 3.1일).
- Stripe 라이브 모드: 최대 3일, 지수 백오프(샌드박스는 몇 시간 동안 3회).
- 복구: 보내는 쪽 실패 목록에서 수동 재전송(Stripe 대시보드 15일, CLI 30일까지), 받는 쪽 정기 대사(조회 API로 실제 상태 맞추기).

### 8. 서명 실패율 100%

- 원인 후보
  - 미들웨어가 본문을 JSON으로 파싱한 뒤 다시 직렬화한 문자열로 검증했다(실험 B4와 같은 모양).
  - 문자셋 변환, 줄바꿈 정규화, 본문 압축 해제 순서 변경.
  - 비밀을 base64 디코딩하지 않고 문자열 그대로 키로 썼다(`whsec_` 뒤는 base64).
- 고치는 법: 웹훅 경로는 원문 바이트를 그대로 받아 그 바이트로 검증하고, 검증 뒤에 파싱한다.
- 유실 여부: 실패를 4xx로 돌려줬다면 보내는 쪽은 실패로 보고 재전송한다. 재전송 기간(예: 3일) 안에 고치면 유실은 없다. 기간을 넘겼다면 수동 재전송·대사로 메운다.

### 9. `169.254.169.254`로 나간 요청

- SSRF다. 고객이 등록한 웹훅 URL이 클라우드 메타데이터 주소·내부 서비스를 가리켜, 보내는 쪽 워커가 대신 요청했다.
- 등록 시 검사만으로 부족한 이유(해석): 도메인의 DNS 응답은 등록 뒤에 내부 IP로 바뀔 수 있고, 리다이렉트로 내부 주소에 닿을 수도 있다.
- 명세 대책: 내부 IP를 거르는 송신 전용 프록시(예: smokescreen)를 거치고, 워커·프록시를 내부 서비스에 닿지 않는 서브넷에 둔다. 3xx는 따르지 않고 실패로 처리한다.
