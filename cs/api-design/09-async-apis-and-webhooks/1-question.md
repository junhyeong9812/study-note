# api-design/09-async-apis-and-webhooks — 질문

## 질문

1. (왜) 폴링 대신 웹훅을 쓰면 무엇이 좋아지나? 웹훅을 여는 순간 보내는 쪽과 받는 쪽에 각각 새로 생기는 책임은 무엇인가?
2. (그림) Standard Webhooks 방식의 전달 한 번을 그려라. 헤더 세 개의 이름과 뜻, 받는 쪽 검사 순서, 보내는 쪽이 성공으로 보는 응답을 적어라. `webhook-timestamp`와 본문의 `timestamp`는 무엇이 다른가?
3. (경계) 서명 대상에 본문만 넣지 않고 id와 타임스탬프를 함께 넣는 이유는? 서명이 맞는데도 거부해야 하는 요청은 어떤 것인가?
4. (예측) 실험 B에서 다음 요청은 각각 어떤 판정을 받나? ① 같은 요청을 30초 뒤 다시 보냄 ② 금액만 1000→1로 바꾼 본문 ③ 내용은 같고 공백만 다른 본문 ④ 10분 전에 캡처한 정상 요청 ⑤ 옛 키·새 키 서명이 함께 실린 요청
5. (예측) 같은 주문의 이벤트가 `SHIPPED(seq 3)`, `CREATED(seq 1)`, `PAID(seq 2)`, `PAID(seq 2, 같은 id)` 순서로 도착했다. 도착 순서대로 덮어쓰면 최종 상태는? id 중복 제거만 하면? id 중복 제거 + seq 비교를 하면?
6. (연결) thin payload와 full payload는 무엇이 다른가? 순서 역전 관점에서 thin이 갖는 장점과 대가는? Stripe 문서는 순서·중복 판정에 무엇을 쓰지 말고 무엇을 쓰라고 하나?
7. (경계) 보내는 쪽 재전송은 언제 멈추나? Standard Webhooks 예시 일정과 Stripe 라이브 모드의 재시도 기간은? 그 기간을 넘긴 이벤트는 어떻게 복구하나?
8. (장애 진단) 프레임워크 업그레이드 뒤 웹훅 서명 실패율이 100%가 됐다. 같은 요청을 손으로 다시 계산하면 서명이 맞는다. 원인 후보와 고치는 법은? 고치는 동안 이벤트가 유실되나?
9. (장애 진단) 보안팀이 웹훅 워커에서 `169.254.169.254`로 나간 요청을 찾았다. 무슨 공격이고, 등록 시 URL 검사만으로 부족한 이유와 명세가 권하는 대책은?
