# api-design/01-order-point — 정리 (힌트)

## 해결하는 문제

"보유 포인트에서 3,000원을 빼서 주문에 붙여라" — 한 줄짜리 요구지만, 같은 통장을 여러 요청이 동시에 건드리는 순간 평범한 코드가 틀린다.

```text
없으면 안 되는 것 세 가지                              잔액 5000, 3000 사용 요청이 둘

  (1) 동시 차감    요청A: 읽기 5000 → 계산 2000 → 쓰기 2000
                   요청B:   읽기 5000 → 계산 2000 → 쓰기 2000   → 6000 쓰고 잔액 2000
  (2) 재시도       타임아웃 → 버튼 한 번 더 → 같은 주문에 두 번 차감
  (3) 중간 끊김    잔액은 깎였는데 주문 기록 전에 죽음 → "왜 빠졌냐"에 답할 데이터가 없다
```

쉬운 예: 한 통장에서 두 사람이 동시에 ATM 출금 — 은행은 "잔액 확인과 출금"을 한 동작으로 처리하고, 거래 내역(원장)을 반드시 남긴다.\
똑같은 구조다: 조건부 UPDATE(확인 + 차감이 한 문장) · `order_id` UNIQUE(주문당 1회) · 원장 INSERT(근거)가 각각 (1)(2)(3)을 막는다.\
실무 예: 포인트·마일리지·상품권·예치금처럼 "잔액이 있는 모든 것"에 이 세 문제가 그대로 따라온다.

  - *원장(ledger)*: "언제 얼마가 왜 움직였나"를 한 줄씩 쌓는 기록. 잔액은 여기서 파생된다.

### 한눈에 — 쉽게 말하면

**주문에 포인트 적용 = 통장에서 돈 빼서 봉투에 넣어두기. 문제는 "두 명이 동시에 같은 통장에서 빼면?"이다.**

- 지문은 평범하다: "주문에 포인트를 적용하고, 보유 포인트에서 차감하라."\
  함정은 마지막 한 줄 — "여러 번 호출되거나 동시에 호출되어도 잘못 차감되지 않아야 한다."
- 이 한 줄이 난이도를 혼자 결정한다.\
  잔액을 **읽고, 계산해서, 쓰는** 코드는 그 사이에 남이 끼어들면 틀린다(lost update).

  > **lost update(갱신 유실)** — 두 요청이 같은 값을 읽고 각자 계산해서 쓰면, 나중에 쓴 쪽이 먼저 쓴 쪽을 덮어써서 한쪽 차감이 사라지는 버그.\
  > 예: 잔액 5000 에 3000 사용 두 건이 겹치면 6000을 썼는데 잔액이 2000 으로 남는다.

- 그리고 버튼을 두 번 누르면(재시도 포함) 두 번 차감되면 안 된다 — 멱등성.

  > **멱등성(idempotency)** — 같은 요청이 몇 번 와도 결과가 한 번 온 것과 같아야 한다는 성질.\
  > 예: 같은 주문에 포인트 적용이 두 번 와도 차감은 한 번만 일어나야 한다.

- 실무 예: 결제 앞 단계의 포인트/마일리지 적용, 상품권 사용.\
  이 문제는 실제 면접 문제(2026-08-13)였다.

```text
[동시에 두 번 오면?]                         잔액 5000, 요청은 둘 다 3000 사용

  요청A: 읽기(5000) → 계산(2000) → 쓰기(2000)
  요청B:    읽기(5000) → 계산(2000) → 쓰기(2000)   ← A의 차감이 사라졌다
                                                      6000을 쓰고 잔액은 2000
```

## 동작·원리

### 전체 흐름

```text
이 문제집의 푸는 순서 (전 문제 공통):
  지문(REQUIREMENTS)만 읽는다 → 15분 타이머로 "확정해야 할 것"을 나열(NOTES 1번 칸)
  → 결정을 내리고 그 결정을 검증받는 프롬프트로 설계 → 마지막에 CHECKLIST 대조

지문을 열기 전 기계적으로 돌리는 질문 3개:
  Q1. 바뀌는 공유 자원이 무엇인가?   → 포인트 잔액 (있으면 Q2, Q3 자동 발동)
  Q2. 정확히 동시에 두 번 오면?      → lost update, TOCTOU
  Q3. 중간에 끊기면 어디까지 남는가? → 부분 실패, 복구 가능성

이 문제의 숨은 요구 3축: D 잔액 차감(lost update) · E 멱등성 · G 부분 실패
```

  > **TOCTOU(Time-of-check to time-of-use)** — "확인한 시점"과 "사용한 시점" 사이에 상황이 바뀌어 확인이 무효가 되는 문제.\
  > 예: 요청 A와 B가 둘 다 "없음"을 확인하고 둘 다 삽입까지 통과한다.

### 설계 — 잔액 차감: 읽고-계산해서-쓰지 마라 (D)

**언제 문제가 되나**: 공유 자원(잔액)을 여러 요청이 동시에 깎을 때.\
코드는 돌아가고 테스트도 통과하는데, 동시에만 틀린다.

나쁜 계약 → 좋은 계약:

```sql
-- 나쁨: 앱이 계산한다 (읽기와 쓰기 사이에 남이 끼어든다)
SELECT balance FROM users WHERE id = 7;      -- 5000
-- 앱에서 5000 - 3000 = 2000 계산
UPDATE users SET balance = 2000 WHERE id = 7;

-- 좋음: DB가 계산하고 조건이 지킨다 (조건부 UPDATE)
UPDATE users
   SET balance = balance - 3000
 WHERE id = 7 AND balance >= 3000;
-- affected rows = 1 → 성공 / 0 → 잔액 부족
```

- 좋은 쪽은 "빼기"와 "부족 검사"가 **한 문장 안**에서 원자적으로 일어난다.\
  끼어들 틈이 없다.

  > **원자적(atomic)** — 중간에 끼어들거나 반만 실행될 수 없는, 쪼개지지 않는 한 덩어리 연산.\
  > 예: "빼기"와 "부족 검사"가 한 문장 안에서 같이 일어나 끼어들 틈이 없다.

> **조건부 UPDATE** — `SET balance = balance - ? WHERE balance >= ?`처럼 계산과 검사를 DB 한 문장에 넣는 갱신.\
> 예: 잔액 5000 에서 3000 을 뺄 때 부족하면 아무 행도 안 바뀐다.

- affected rows(영향받은 행 수)가 0이면 잔액 부족 — 별도 SELECT 없이 판정된다.

> **affected rows** — UPDATE가 실제로 바꾼 행 수.\
> 예: 0이면 조건 불충족(잔액 부족)으로 판정한다 — 별도 SELECT 가 필요 없다.

- 잔액이 음수가 될 수 없음을 보장하는 것은 앱 코드가 아니라 **이 WHERE 조건(또는 DB 제약)** 이다.
- 대안은 `SELECT ... FOR UPDATE`(행 잠금) — 유연하지만 잠금 범위를 넓게 잡으면 데드락·성능 저하로 번진다(토스 사례: 잔액 행만 최소로 잠금).

**트레이드오프**: 조건부 UPDATE는 단순·안전하지만 "차감 전 값"을 응답에 담으려면 한 번 더 읽어야 한다.\
FOR UPDATE는 읽고 검증하고 쓰는 복합 로직이 가능하지만 잠금 순서·범위를 설계해야 한다.

### 설계 — 멱등성: order_id가 이미 열쇠다 (E)

**언제 문제가 되나**: 타임아웃 후 재시도, 더블 클릭, 네트워크 끊김.\
"성공했는지 실패했는지 모르는" 요청이 반드시 다시 온다.

- 이 API는 별도 `Idempotency-Key` 헤더가 필요 없다 — **"주문당 포인트 적용 1회"가 도메인 규칙이라 `order_id`가 자연 멱등 키**다.

> **자연 멱등 키** — 별도 키를 만들지 않아도 도메인 규칙("주문당 1회")이 이미 주는 유일 키.\
> 예: 여기서는 `order_id` 가 그 키라서 `Idempotency-Key` 헤더가 필요 없다.

- 판정의 최종 방어선은 사전 조회가 아니라 **DB UNIQUE 제약**이다.\
  "조회해서 없으면 넣기"는 조회와 삽입 사이에 다른 요청이 통과한다(TOCTOU).\
  **사전 조회는 방어가 아니라 최적화다.**

> **UNIQUE 제약** — 같은 값이 두 번 들어갈 수 없게 DB가 강제하는 규칙. 멱등 판정의 최종 방어선.\
> 예: 같은 order_id 의 두 번째 삽입을 어떤 타이밍에도 DB가 거절한다.

나쁜 계약 → 좋은 계약 (응답 관점):

```text
나쁨: 두 번째 요청에 그냥 500 이나 "이미 처리됨" 모호한 에러
  → 프론트는 성공인지 실패인지 모른다. 사용자는 또 누른다.

좋음: 응답의 의미를 계약으로 정한다. 예:
  같은 주문 + 같은 금액 재요청 → 200 (첫 응답과 동등한 내용 재생) 또는 409
  같은 주문 + 다른 금액       → 409/422 (충돌임을 명시)
  프론트와의 약속: "타임아웃 후 재시도해서 409를 받으면 그것은 성공이다"
```

- 실제 회사들의 선택은 갈린다: Stripe는 첫 응답을(500이어도) 그대로 재생, GoCardless는 재생 없이 409 + 충돌 자원 ID, 토스페이먼츠는 body 다르면 422/진행 중이면 409, AWS는 "의미적으로 동등한 응답".\
  **정답이 하나가 아니고, 그 선택이 프론트엔드 복잡도를 결정한다.**
- Airbnb의 결정적 조항: 멱등성 데이터는 **오직 master DB에서만** 읽고 쓴다 — 복제 지연 몇 초가 완료된 결제를 "미실행"으로 보이게 해 재실행시킨다.

### 설계 — 부분 실패와 원장 (G)

**언제 문제가 되나**: 프로세스가 어느 줄에서든 죽을 수 있다.\
"잔액 UPDATE는 됐는데 주문 기록 전에 죽으면?"에 답이 있어야 한다.

> **부분 실패(partial failure)** — 여러 단계 중 일부만 성공하고 끊긴 상태. "중간에 죽으면 뭐가 남나"의 답.\
> 예: 원장만 남고 잔액이 안 깎인 상태가 가능하다.

```text
나쁨: 잔액만 고치고 끝                          좋음: 원장 + 잔액을 한 트랜잭션으로
  users.balance: 5000 → 2000                     BEGIN
  (근거 없음 — CS가 "왜 빠졌나" 물으면            INSERT 포인트 사용 원장(order_id UNIQUE,
   답할 데이터가 없다)                                   금액, 시각)   ← 멱등 판정도 겸한다
                                                  UPDATE 잔액 조건부 차감
                                                  UPDATE 주문에 사용 포인트 기록
                                                 COMMIT  ← 전부 남거나 전부 안 남거나
```

> **원장(ledger)** — "언제 얼마가 왜 움직였나"를 한 줄씩 쌓는 기록.\
> **잔액은 원장에서 파생되는 값**이고, 불일치가 나면 원장이 이긴다(정본).\
> 예: "이 사용자 포인트가 왜 빠졌냐"는 CS 문의에 답할 근거가 여기서 나온다.

- 한 트랜잭션으로 묶으면 단순하다(중간에 죽어도 전부 롤백).\
  나누면 부분 복구가 가능하지만 "반만 된 상태"를 찾아 고치는 sweeper(청소 배치)가 필요해진다.

> **트랜잭션(transaction)** — 여러 DB 작업을 "전부 성공 아니면 전부 취소"로 묶는 단위.\
> 예: INSERT 원장 → UPDATE 잔액 → UPDATE 주문 → COMMIT 을 한 덩어리로 묶는다.

- 복구 재시도가 두 번 차감하지 않음을 보장하는 것도 결국 원장의 UNIQUE 제약이다.

## 쓰이는 자료구조·알고리즘

- **조건부 UPDATE** (`SET balance = balance - ? WHERE balance >= ?`) — DB 행 하나에 대한 원자적 read-modify-write. "기대 조건이 맞을 때만 쓴다"는 점에서 compare-and-set(CAS)과 같은 모양이다.
  - *CAS(compare-and-set)*: "값이 아직 X면 Y로 바꿔라"를 한 번에 하는 연산. 끼어들 틈이 없다.
- **UNIQUE 제약 = 유니크 인덱스** — 두 번째 `order_id` 삽입을 인덱스가 키 충돌로 거절한다. MySQL InnoDB · PostgreSQL에서 유니크 인덱스는 B-tree 계열이라 판정 비용은 O(log n) 탐색 한 번 → [data-structure/15-b-tree](../../data-structure/15-b-tree/2-summary.md).
- **멱등 키 저장소** — 키(`order_id`) → 결과(첫 응답)를 담는 맵. 재생 정책(Stripe식)을 택하면 이 맵이 응답 본문까지 보관한다 → [ops-patterns/06-idempotency-store](../../ops-patterns/06-idempotency-store/2-summary.md).
- **append-only 로그 + 폴드** — 원장은 지우지 않는 로그, 잔액은 그 로그를 처음부터 합산(폴드)한 값. 불일치 시 로그로 다시 만들 수 있다 → [ops-patterns/16-event-sourcing](../../ops-patterns/16-event-sourcing/2-summary.md).
  - *폴드(fold)*: 목록을 앞에서부터 누적해 값 하나로 줄이는 연산. 여기서는 원장 합 = 잔액.
- **행 잠금(`SELECT ... FOR UPDATE`)** — 읽는 순간 행에 쓰기 잠금을 걸고 트랜잭션 끝까지 쥐는 비관적 잠금. 여러 행을 잠글 때는 순서 고정이 필요하다 → [03-stock-deduct](../24-case-stock-deduct/2-summary.md)의 잠금 순서.
- **트랜잭션(ACID)** — 원장 INSERT · 잔액 UPDATE · 주문 UPDATE 세 쓰기를 전부-아니면-전무로 묶는 단위.
- **대사(reconciliation)** — 두 기록(원장 vs 잔액, 우리 vs PG)을 키로 정렬해 맞춰보는 병합 비교 → [algorithm/02-merge-sort](../../algorithm/02-merge-sort/2-summary.md)의 병합 단계와 같은 모양.

## 적용 — 풀어나가는 법

이 문제집은 코드가 아니라 "확정해야 할 것"을 뽑는 훈련이다.\
순서는 항상 같다: ① 지문에서 **바뀌는 공유 자원**을 찾는다(잔액) → ② "정확히 동시에 두 번 오면"과 "중간에 끊기면"을 그 자원에 들이댄다 → ③ 나온 위험마다 **DB가 판정하는 장치**(조건부 UPDATE · UNIQUE · 트랜잭션)를 하나씩 붙이고, 그 선택을 "A 대신 B, 왜냐하면 C"로 적는다.\
아래 과제 목록이 그 훈련의 실제 절차다.

### 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 평범한 요구사항 문서다: 결제와 분리된 단계로 `POST /orders/{order_id}/point` 를 만들어, 주문에 포인트를 적용하고 보유 포인트를 차감하라.\
함정 표시는 없지만 "동일한 주문에 여러 번 호출되거나, 동시에 호출되는 상황에서도 포인트가 잘못 차감되지 않아야 한다" 한 줄이 난이도를 결정한다.\
코드를 짜는 문제가 아니라 **지문에 안 적혀 있는 요구를 읽어내는** 문제이고, 실제 면접 문제(2026-08-13)였다.

과제 목록 (원본 "이 문제를 푸는 방법" · NOTES.md 기준):

### 나머지 축 — 짧게

- **권한(B)**: 요청 바디로 `user_id`를 받지 마라.\
  **주문에 이미 소유자가 있다.**\
  바디로 받으면 클라이언트가 조작할 수 있는 값이 하나 늘 뿐이다.\
  요청자 ≠ 주문 소유자면 거부.
- **주문 상태(C)**: 포인트 적용은 결제 수단 구성이지 결제가 아니다 — 여기서 주문 상태를 전이시키면 결제 승인/취소 로직이 얽힌다.\
  어떤 상태에서만 허용할지는 확정 질문 대상.
- **입력 검증(A)**: 0 이하, 주문 총액 초과, 사용 단위(10원/100원), 최소 사용액, 총액 대비 % 상한 — 못 짚어도 큰 감점은 아니다(물어보면 나온다).
- **응답/에러(H)**: 4xx와 5xx를 가르는 기준 = "클라이언트가 재시도해도 되는 실패인가".
- **관측(I)**: "이 사용자 포인트가 왜 빠졌냐"에 답할 데이터(원장), 부분 실패 적체 알림, dead letter.
- **되묻기(J)**: 지문에 "명시되지 않은 정책은 질문하며 진행"이 **적혀 있다**.\
  실제로 질문했는가가 평가 항목이다.

## 장애 시나리오와 대처

아래는 우리 시스템 안에서 실제로 마주치는 모양이다. 회사 사례는 「실패 사례」 절에 따로 있다.

**1. 에러는 없는데 원장 합이 잔액과 안 맞는다**

- 현상: 정산 대사에서 특정 사용자의 포인트 사용 원장 합이 최초 잔액보다 크다.
- 보이는 형태: 예외 0건, 테스트 전부 통과. 불일치는 트래픽이 몰린 시간대의 사용자에게만 몰려 있다.
- 원인: `SELECT balance` → 앱에서 빼기 → `UPDATE balance = 2000`. 읽기와 쓰기 사이에 다른 요청이 끼어든 lost update(정답 2번 참고).
- 대처: 조건부 UPDATE로 바꾸고 affected rows로 판정한다. `CHECK (balance >= 0)` 제약을 DB에 걸어 앱 코드가 틀려도 음수는 못 들어가게 한다(MySQL은 8.0.16부터 CHECK를 실제로 강제한다 — 그 전 버전은 문법만 받고 무시). 동시 요청을 실제로 겹치게 쏘는 테스트를 하나 둔다.

**2. 포인트는 빠졌는데 화면에는 "실패"라고 떴다**

- 현상: 사용자 문의 — "적용 실패라고 나왔는데 포인트가 줄었다."
- 보이는 형태: 서버 로그에는 같은 주문의 첫 요청 200, 3초 뒤 두 번째 요청 409. 프론트는 409를 에러 토스트로 그렸다.
- 원인: 첫 응답이 타임아웃으로 유실 → 프론트 재시도 → UNIQUE가 두 번째를 거절(정확한 동작) → 그런데 "재시도 후 409 = 성공"이라는 계약을 프론트와 맺지 않았다(정답 3번 참고).
- 대처: 멱등 응답의 의미를 문서로 정한다 — 같은 금액 재요청은 첫 응답 재생(200) 또는 409를 "이미 적용됨"으로 렌더링. 프론트는 409를 받으면 주문을 재조회해 적용 여부를 표시한다.

**3. 잔액은 줄었는데 주문에는 사용 포인트가 0이다**

- 현상: 결제 화면의 최종 금액이 포인트를 반영하지 않는다.
- 보이는 형태: `users.balance`는 3,000 감소, `orders.used_point`는 0. 배포 재시작 시각과 요청 시각이 겹친다.
- 원인: 잔액 UPDATE와 주문 UPDATE가 서로 다른 트랜잭션(또는 auto-commit) — 그 사이에 프로세스가 죽었다. 부분 실패.
- 대처: 원장 INSERT · 잔액 UPDATE · 주문 UPDATE를 한 트랜잭션으로 묶는다. 나누는 설계라면 원장을 정본으로 "원장은 있는데 주문 기록이 없는 건"을 찾아 마저 처리하는 sweeper를 두고, 그 적체를 알람으로 본다.
  - *sweeper(청소 배치)*: 반만 된 상태를 주기적으로 찾아 이어서 처리하는 작업.

**4. 피크 시간대에만 데드락 에러가 튄다**

- 현상: 같은 주문에 대한 포인트 적용이 거의 동시에 두 번 들어오면(더블클릭 · 재시도) 가끔 한쪽이 실패한다.
- 보이는 형태: MySQL `Deadlock found when trying to get lock; try restarting transaction` / PostgreSQL `ERROR: deadlock detected`. 재시도하면 성공한다.
- 원인: 한 트랜잭션 안에서 같은 `users` 행과 같은 `orders` 행을 잠그는 순서가 요청마다 다르다(주문을 먼저 잠그는 경로와 사용자를 먼저 잠그는 경로가 공존) — 서로 상대가 쥔 행을 기다리는 순환 대기. 주문이 서로 다르면 겹치는 행이 `users` 하나뿐이라 이런 순환은 생기지 않는다.
- 대처: 잠금 순서를 고정한다(예: 항상 `users` → `orders`). 조건부 UPDATE도 행 잠금은 트랜잭션 끝까지 쥔다 — 다만 `FOR UPDATE` → 앱 계산 → UPDATE처럼 읽기와 쓰기 사이에 앱 왕복이 끼지 않아 잠금 보유 시간이 짧아지기 쉽다. 데드락 에러는 재시도 가능한 실패로 분류하고 트랜잭션은 짧게 유지한다.

### 실패 사례 — 이 항목들이 나온 실제 사고

- **올리브영 선착순 쿠폰(2025)**: Redis GET과 INCR을 따로 실행해 원자성이 깨짐 → 미발급률 0.014%. Lua 스크립트는 정확도 100%였지만 성능 21% 저하로 기각 — **정확성과 성능은 교환 관계이고, 어디까지 포기할지가 요구사항이다.**
- **Airbnb 이중 결제 방지**: 타임아웃 시 성공/실패 구분 불가 → 요청당 멱등키 + 3단계(의도 기록/외부 호출/결과 기록) 원자 트랜잭션.
- **Twilio 과금 사고(2013)**: 잔액 저장소가 깨져 잔액이 0으로 보이자 자동충전이 카드를 반복 청구.\
  추가한 안전장치 — "잔액을 읽거나 쓸 수 없으면 청구하지도, 정지하지도 않는다."
- **우아한형제들 결제 장애 대응**: PG는 승인됐는데 시스템엔 기록 없는 "고아 승인" → 실시간 대사로 1시간 내 자동 취소.\
  **부분 실패는 "탐지 가능한가"가 요구사항이다.**

> **PG(Payment Gateway)** — 카드사·은행과 결제를 중계하는 외부 결제 대행사.\
> 예: PG 쪽에는 승인 기록이 있는데 내 시스템에는 없는 상태를 "고아 승인"이라 한다.

> **대사(reconciliation)** — 두 시스템(예: 우리 DB와 PG)의 기록을 맞춰보고 불일치를 찾는 작업.\
> 예: 고아 승인을 실시간 대사로 1시간 내에 찾아 자동 취소한다.

- **Mercari 데드락**: 두 user 행을 잠그는 순서를 통제하지 않아 서로 기다림 → id 순 정렬로 해결.

> **데드락(deadlock)** — 두 트랜잭션이 서로가 잡은 잠금을 기다리며 영원히 멈추는 상태.\
> 예: 잠그는 순서를 id 순으로 고정하면 예방된다.

## 핵심 문장

- 이 문제집이 기르는 것은 **적혀 있지 않은 요구를 읽어내는 힘**이다 — "동시에 호출되어도 잘못 차감되지 않아야 한다" 한 줄이 전체 난이도를 결정한다.
- 잔액은 **읽고-계산해서-쓰면 진다.**\
  DB가 한 문장 안에서 빼고 검사하게 하라(조건부 UPDATE + affected rows).
- `order_id`는 자연 멱등 키다 — 판정은 UNIQUE 제약이 하고, **사전 조회는 방어가 아니라 최적화다.**
- 잔액만 고치면 안 된다 — **원장이 정본이고 잔액은 파생값이다.**\
  CS·정산·복구의 근거가 전부 원장에서 나온다.
- 재시도 후 받은 409는 실패가 아니라 성공일 수 있다 — **멱등 응답의 의미는 프론트와의 계약이다.**

### 용어 풀이

- **lost update(갱신 유실)**: 두 요청이 같은 값을 읽고 각자 계산해 쓰면 한쪽 갱신이 덮여 사라지는 버그.
- **TOCTOU**: 확인(check)과 사용(use) 사이에 상황이 바뀌어 확인이 무효가 되는 문제.\
  "조회해서 없으면 넣기"의 함정.
- **멱등성(idempotency)**: 같은 요청이 몇 번 와도 한 번 온 것과 결과가 같은 성질.\
  재시도를 안전하게 만든다.
- **자연 멱등 키**: 별도 키를 만들지 않아도 도메인 규칙("주문당 1회")이 이미 주는 유일 키.\
  여기서는 `order_id`.
- **조건부 UPDATE**: `SET balance = balance - ? WHERE balance >= ?`처럼 계산과 검사를 DB 한 문장에 넣는 갱신.
- **affected rows**: UPDATE가 실제로 바꾼 행 수.\
  0이면 조건 불충족(잔액 부족)으로 판정한다.
- **원자적(atomic)**: 쪼개지거나 중간에 끼어들 수 없는 한 덩어리 연산.
- **트랜잭션(transaction)**: 여러 DB 작업을 "전부 성공 아니면 전부 취소"로 묶는 단위.
- **원장(ledger)**: 변동을 한 줄씩 쌓는 기록.\
  정본이며, 잔액은 여기서 파생된다.
- **UNIQUE 제약**: 같은 값이 두 번 들어갈 수 없게 DB가 강제하는 규칙.\
  멱등 판정의 최종 방어선.
- **부분 실패(partial failure)**: 여러 단계 중 일부만 성공하고 끊긴 상태.\
  "중간에 죽으면 뭐가 남나"의 답.
- **고아 승인**: 외부(PG)에서는 승인됐는데 내 시스템에는 기록이 없는 상태.
- **대사(reconciliation)**: 두 시스템(예: 우리 DB와 PG)의 기록을 맞춰보고 불일치를 찾는 작업.
- **dead letter**: 재시도해도 계속 실패하는 요청을 따로 모아두는 곳.\
  버리지 않고 사람이 본다.
- **데드락(deadlock)**: 두 트랜잭션이 서로가 잡은 잠금을 기다리며 영원히 멈추는 상태.\
  잠금 순서 고정으로 예방.
- **PG(Payment Gateway)**: 카드사·은행과 결제를 중계하는 외부 결제 대행사.
