# api-design/04-settlement-report — 정리 (힌트)

> 이미 따라 치며 만든 정리본이 따로 있으면(organize류) 이 파일은 핵심 문장 압축 + 링크만 담는다.

## 한눈에 — 쉽게 말하면

**정산 리포트 = 가게 주인에게 보여주는 월말 장부. 쓰기가 하나도 없는데도 사고가 난다 — 이 감각을 깨는 것이 이 문제의 목적이다.**

- "조회 API인데 뭐가 위험하냐"라고 생각했다면 그 자체가 이 문제의 답이다. **읽기만 해도 틀린 숫자를 보여주면 돈 문제다.**
- 사고 나는 자리 네 곳: ① 합계와 상세가 서로 다른 시점을 읽음 ② OFFSET 페이지네이션의 중복/누락 ③ read replica의 복제 지연(어제 데이터를 보여줌) ④ "왜 이 숫자인지" 되짚을 근거가 없음(추적 가능성).
- 지문의 배경 한 줄 — "판매자 문의 중 가장 많은 것이 '정산 금액이 왜 이 숫자인지 모르겠다'" — 이것을 요구사항으로 읽어내는 것이 진짜 주제다.
- 실무 예: 오픈마켓 판매자 정산, 광고비 리포트, 급여 명세.

```text
[합계 따로, 상세 따로 읽으면]

  쿼리1: SUM(전체 기간)  ──┐ 이 사이에 새벽 배치가
  쿼리2: 이번 페이지 50건 ──┘ 한 건을 더 넣으면?
  → 합계에는 있는데 상세 어디에도 없는 돈 → "왜 이 숫자예요?" 문의
```

## 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 정산팀의 평범한 요구사항 문서다: `GET /merchants/{merchant_id}/settlements` 로 기간 내 정산 내역을 합계(summary)+건별(items)+페이지네이션으로 제공하라. 판매자는 자기 정산만 보고, 엑셀 다운로드도 곧 붙는다. 함정 표시는 없지만 배경 문단의 "판매자 문의 중 가장 많은 것이 '정산 금액이 왜 이 숫자인지 모르겠다'" 한 줄과 참고의 "read replica 검토 중"·"판매자는 국내와 해외 모두"가 진짜 요구(추적 가능성·복제 지연·타임존/통화)를 심어놓은 자리다. **쓰기가 하나도 없는 조회 API인데도 사고가 난다** — 그 감각을 깨는 문제다.

과제 목록 (원본 "이 문제를 푸는 방법" · NOTES.md 기준):

- REQUIREMENTS.md 지문만 읽고, NOTES.md 1번 칸에 **타이머 15분**으로 "확정해야 할 것"을 질문 형태로 나열한다 (답이 아니라 질문을 적는다)
- NOTES.md 2번 칸: 결정을 **"A 대신 B, 왜냐하면 C"** 형태로 적는다
- Claude에게 "어떻게 해야 해?"가 아니라 **본인이 내린 결정을 검증받는** 프롬프트로 설계를 진행하고, 보낸 프롬프트 원문을 3번 칸에 남긴다
- **마지막에** solution/CHECKLIST.md 를 열어 대조하고 나머지 칸(대조 결과 / 가장 아팠던 놓침 / 30초 설명)을 채운다 — 먼저 보면 효과가 없다

## 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 없다? 아니 — "읽는 동안 배치가 쓰는" 같은 데이터
  Q2. 동시에(읽는 중에 쓰이면)? → 합계≠상세, 페이지 경계 흔들림
  Q3. 중간에 끊기면?      → (쓰기가 없으니) 대신: "이 숫자의 근거를 되짚을 수 있나"

숨은 요구: A 합계-상세 일치 · B 페이지네이션 · C read replica(지문이 언급) ·
           D 추적 가능성(진짜 주제) · E 금액·타임존 · F 권한
```

## 설계 — 합계와 상세의 일치 (A)

**언제 문제가 되나**: `summary`와 `items`를 별도 쿼리로 만들 때 — 두 쿼리 사이에 데이터가 바뀔 수 있다.

나쁜 계약 → 좋은 계약:

```text
나쁨: 합계 쿼리와 상세 쿼리를 각각 실행 (서로 다른 시점을 읽음)
      + "합계 = 페이지 합"이라고 은연중 약속 (페이지네이션이라 애초에 불가능)

좋음: ① 두 쿼리를 같은 스냅샷에서 읽는다 (한 트랜잭션, 또는 "확정분까지"로 상한 고정)
      ② 합계는 전체 기간, items는 현재 페이지 — 다른 것이 정상임을 응답에 문서화
```

- *스냅샷(snapshot)*: 특정 시점의 데이터 모습. 같은 스냅샷을 읽으면 읽는 도중의 변경이 안 보인다.
- 또 하나의 함정: JOIN 조건이나 WHERE 필터가 하나 빠지면 **조용히 중복 행을 세서 합계가 두 배**가 된다 — 에러가 안 나서 못 알아챈다. 산출물을 검증 없이 내보내면 안 된다(Cloudflare 사고).

## 설계 — 페이지네이션: OFFSET의 함정 (B)

**언제 문제가 되나**: 읽는 동안 앞쪽 데이터가 늘거나 줄 때, 그리고 정렬 키가 유일하지 않을 때.

```text
나쁨: ORDER BY settled_at LIMIT 50 OFFSET 100
  ① 읽는 동안 앞쪽에 한 건 삽입 → 2페이지 첫 행 = 1페이지 마지막 행 (중복)
     앞쪽에서 한 건 삭제 → 한 건 건너뜀 (누락)
  ② settled_at이 같은 행이 여럿이면 경계가 실행마다 흔들린다 (정렬 키 비유일)
  ③ OFFSET 100000은 10만 행을 세고 버린다 (성능)

좋음: 커서(keyset) 방식 + 유일한 정렬 키
  ORDER BY settled_at, settlement_id      ← 동률을 id가 깨준다 (유일해짐)
  WHERE (settled_at, settlement_id) > (마지막으로 본 값)   ← "그 다음부터 50건"
  LIMIT 50
```

- *커서(cursor/keyset) 페이지네이션*: "몇 번째부터"가 아니라 "이 값 다음부터"로 페이지를 넘기는 방식. 앞쪽 변동에 흔들리지 않고, 깊은 페이지도 빠르다.
- `total_count`를 매 페이지 다시 세면 값이 페이지마다 달라질 수 있다 — 허용할지 정해야 한다.
- 엑셀 다운로드(지문 5번)는 전체를 훑는다 — 같은 문제가 훨씬 크게 터진다. 행 수 상한도 물어야 한다.

## 설계 — read replica: 어제 장부를 보여주는 문제 (C)

**언제 문제가 되나**: 새벽 배치가 primary에 쓰고, 조회는 replica에서 할 때 — 복제 지연 동안 판매자는 어제 데이터를 본다.

```text
  배치 ──쓰기──> primary ══복제(지연 δ)══> replica <──조회── 판매자
                                 └ δ 동안: "오늘 정산이 왜 없죠?"

  더 나쁨: 합계는 primary, 상세는 replica처럼 섞어 읽기 → 둘이 서로 다른 세상을 본다
```

- 좋은 계약: "배치 완료 후 조회 가능" 시점을 명시적으로 맞춘다 — 배치가 완료 표시를 남기고, API는 완료된 정산 회차만 노출.
- 복제 지연은 감지 수단이 필요하다 — incident.io는 쓰기 시점의 LSN을 기록하고 replica가 따라왔는지 비교해 못 따라왔으면 기다렸다(replica는 "건강"했고 그냥 뒤처져 있어서 알람에도 안 걸렸다).
  - *LSN(log sequence number)*: DB 변경 로그의 일련번호. primary의 번호와 replica의 번호를 비교하면 얼마나 뒤처졌는지 안다.

## 설계 — 추적 가능성: "왜 이 숫자인가"에 답하기 (D, 진짜 주제)

**언제 문제가 되나**: 집계만 저장하고 상세를 안 남기면, 총액이 틀렸을 때 **어느 건이 틀렸는지 추적이 불가능**하다.

```text
나쁨: 하나의 거대한 쿼리 → 최종 집계 숫자만 저장
  "거래 A, B, C 중 어떤 건에서 오류가 났는지 추적 불가" (토스페이먼츠 레거시)

좋음: 단계별 분해 + 중간 산출물 보존
  건별 원천 → 건별 수수료 계산(요율·기준 금액·반올림 기록) → 회차 집계
  어느 단계든 되짚을 수 있다 = "왜 이 숫자냐"에 답할 수 있다

수정이 필요하면: UPDATE ✗ → 상쇄 엔트리 추가 ○
  90001번 정산 -1,500원 조정 = "-1,500원짜리 새 줄"을 추가한다
  (토스페이먼츠: 취소를 UPDATE에서 INSERT-only로 바꿔 불변성 보장 + 데드락 방지)
```

- **총액이 맞는 것과 근거를 되짚을 수 있는 것은 다르다.** 지문의 "가장 많은 문의"가 바로 이것이다.

## 설계 — 금액과 시간 (E)

- 금액은 부동소수(float) 금지 — 0.1 + 0.2 ≠ 0.3인 세계에 돈을 두면 안 된다. 정수(원 단위)나 decimal로.
- 반올림: **건별 반올림의 합 ≠ 합계의 반올림.** 어느 쪽이 정본인지 규칙을 정해야 한다.
- `from`/`to`가 어느 타임존 기준인가, `to`는 포함인가 미포함인가 — 판매자가 해외면(지문 참고) 하루가 통째로 어긋날 수 있다.
- 다통화면 합계를 어떤 환율로, **어느 시점의** 환율로 환산하는가.

## 나머지 축 — 짧게

- **권한(F)**: `merchant_id`가 경로에 있다 — **다른 판매자 ID를 넣으면?** 인증 주체와 경로 ID를 반드시 대조. 운영자의 열람 권한은 별도 정책.
- **성능 한계(G)**: `size=1000000`, `from=2000-01-01` 같은 입력에 상한이 있는가. 큰 기간 합계는 매번 계산인가 사전 집계인가.
- **되묻기(H)**: 타임존 기준, 정산 확정 시점, 수정 정산 표시 방법, 엑셀 행 수 상한.

## 실패 사례 — 이 항목들이 나온 실제 사고

- **토스페이먼츠 정산 개편(D의 정본)**: 거대 단일 쿼리 + 집계만 저장 → 오류 건 추적 불가, 재활용 불가. 단계별 분해 + 중간 산출물 보존으로 재설계. 같은 시리즈: INSERT-only 원장, 복제 지연을 고려한 5분 간격 정합성 검증 배치.
- **Cloudflare(2025-11-18)**: DB 이름 필터가 빠진 메타데이터 쿼리가 중복 행 반환 → 피처 파일이 약 60개에서 200개 초과로 두 배 → 하드코딩 한계 초과 → 전 세계 5xx 약 6시간. 필터 하나 빠진 집계가 조용히 두 배가 되는 실증.
- **incident.io read replica**: 워커가 복제보다 빨라 0.1~0.5% NotFoundError — replica는 건강했고 그냥 뒤처져 있었다. LSN 비교로 해결.
- **GitHub(2018)**: 43초 네트워크 분단 후 24시간 11분간 stale 데이터 노출. "무결성을 가용성보다 우선했다" — 정산에서는 특히 맞는 선택.
- **Monzo**: 예외를 안 던지는 실패(0.1% 미스케줄)는 에러 리포팅에 안 잡힌다 — 규칙 기반 정합성 검사가 따로 필요.
- 참고: 페이지네이션 중복/누락 자체를 다룬 회사 공식 회고는 원본 리서치에서 못 찾았다(원본에 정직하게 기록됨) — Cloudflare·GitHub이 인접 근거다.

## 핵심 문장

- **쓰기가 없어도 사고가 난다** — 틀린 숫자를 보여주는 조회 API는 돈 문제다.
- 합계와 상세를 따로 읽으면 서로 다른 시점을 본다 — 같은 스냅샷을 읽거나, 다를 수 있음을 계약으로 문서화하라.
- OFFSET은 앞쪽이 변하면 중복/누락이 나고 깊을수록 느리다 — **유일한 정렬 키 + 커서**가 답이다.
- 배경 문단의 "가장 많은 문의"가 진짜 요구사항이다 — **총액이 맞는 것과 근거를 되짚을 수 있는 것은 다르다.**
- 금액 수정은 UPDATE가 아니라 상쇄 엔트리 추가다 — 그래야 감사가 된다.

## 용어 풀이

- **정산(settlement)**: 판매 대금에서 수수료를 빼고 판매자에게 지급할 금액을 확정하는 일.
- **스냅샷(snapshot)**: 특정 시점의 데이터 모습. 같은 스냅샷을 읽으면 도중의 변경이 안 보인다.
- **OFFSET 페이지네이션**: "앞에서 N개 건너뛰고 50개". 앞쪽이 변하면 중복/누락, 깊으면 느림.
- **커서/keyset 페이지네이션**: "마지막으로 본 값 다음부터 50개". 변동에 강하고 깊어도 빠르다.
- **유일한 정렬 키**: 동률이 없는 정렬 기준(예: settled_at + settlement_id). 페이지 경계를 고정한다.
- **read replica**: 조회 부하를 분산하려고 두는 읽기 전용 복제본. 원본(primary)보다 늦다.
- **복제 지연(replication lag)**: primary의 쓰기가 replica에 도달하기까지의 시간차.
- **LSN(log sequence number)**: DB 변경 로그의 일련번호. replica가 얼마나 뒤처졌는지 비교하는 기준.
- **추적 가능성(traceability)**: 최종 숫자에서 근거(건별 계산·요율·반올림)까지 되짚을 수 있는 성질.
- **상쇄 엔트리**: 기존 줄을 고치는 대신 반대 방향 금액의 새 줄을 추가하는 수정 방식. 이력이 보존된다.
- **INSERT-only(불변 원장)**: 한 번 쓴 줄은 절대 고치지 않는 원칙. 감사 가능 + 데드락 감소.
- **부동소수(float)**: 근사값으로 저장되는 소수 표현. 돈에 쓰면 1원이 샌다 — 정수/decimal을 쓴다.
- **대사(reconciliation)**: 두 기록(내부-외부, 집계-건별)을 맞춰보고 불일치를 찾는 작업.
- **정합성 검증 배치**: 예외 없이 조용히 틀어진 데이터를 규칙으로 훑어 잡아내는 주기 작업.
