### A. 문제 (REQUIREMENTS.md — 정산 리포트 조회 API)

```text
GET /merchants/{merchant_id}/settlements?from=2026-08-01&to=2026-08-31&page=1&size=50

응답: { "summary": { total_sales, total_fee, total_payout },
        "items": [ { settlement_id, order_id, sales_amount, fee, payout, settled_at } ],
        "page": 1, "size": 50, "total_count": 1043 }

배경
  판매자 문의 중 가장 많은 것이 "정산 금액이 왜 이 숫자인지 모르겠다"입니다.

기대 동작
  1. 기간 내 정산 내역을 조회합니다.
  2. 상단에 합계를, 하단에 건별 내역을 페이지 단위로 제공합니다.
  3. 판매자는 자기 정산만 볼 수 있습니다.
  4. 건수가 많을 수 있으므로 페이지네이션합니다.
  5. 엑셀 다운로드 기능도 곧 붙일 예정입니다.

참고
  - 정산 데이터는 매일 새벽 배치가 생성합니다.
  - 조회 트래픽이 많아 read replica 를 붙이는 것을 검토 중입니다.
  - 판매자는 국내와 해외 모두 있습니다.
```

#### 1. 지문 읽기 — 숨은 요구

- 쓰기가 하나도 없는 이 API에서 사고가 나는 자리 네 곳은 어디인가?
- 배경 문단의 "가장 많은 문의" 한 줄은 어떤 요구사항으로 번역되는가?
- 참고의 "read replica 검토 중"과 "판매자는 국내와 해외 모두"는 각각 어떤 항목을 유도하는가?

#### 2. 합계와 상세의 일치 (A — 중요)

- summary와 items를 별도 쿼리로 만들면 무슨 일이 생길 수 있는가?
- 합계가 items의 합과 다른 것이 "정상"인 경우는 무엇이고, 어떻게 처리해야 하는가?
- 두 쿼리를 같은 시점으로 맞추는 방법은 무엇인가?
- JOIN 조건이나 WHERE 필터가 하나 빠지면 어떤 사고가 나는가 — 왜 못 알아채는가?

#### 3. 페이지네이션 (B — 중요)

- OFFSET 방식은 읽는 동안 앞쪽이 변하면 어떻게 되는가(두 방향)?
- `settled_at`만으로 정렬하면 무엇이 흔들리는가?
- 커서(keyset) 방식은 어떻게 생겼고, 무엇을 해결하는가?
- `OFFSET 100000`의 성능 문제는 무엇인가?
- 엑셀 다운로드(지문 5번)에서는 왜 같은 문제가 더 크게 터지는가?

#### 4. read replica (C — 지문이 명시적으로 언급)

- 새벽 배치가 primary에 쓰고 조회가 replica를 보면 판매자는 무엇을 보는가?
- 배치 완료와 조회 가능 시점은 어떻게 맞추는가?
- 합계는 primary, 상세는 replica처럼 섞어 읽으면 어떻게 되는가?
- 복제 지연은 어떻게 감지하는가?

#### 5. 추적 가능성 (D — 이 문제의 진짜 주제)

- 집계만 저장하고 상세를 안 남기면 무엇이 불가능해지는가?
- "총액이 맞는 것"과 "근거를 되짚을 수 있는 것"의 차이는 무엇인가?
- 수수료 계산을 되짚으려면 무엇을 기록해야 하는가?
- 정산 금액을 수정해야 할 때 UPDATE 대신 무엇을 해야 하고, 왜인가?

#### 6. 금액·시간·권한·한계 (E, F, G)

- 금액을 부동소수로 다루면 안 되는 이유는?
- "건별 반올림의 합"과 "합계의 반올림"은 왜 다르고, 무엇을 정해야 하는가?
- `from`/`to`의 타임존과 포함/미포함이 흐리면 무슨 일이 생기는가?
- 경로의 `merchant_id`에 다른 판매자 ID를 넣으면 어떻게 되어야 하는가?
- `size=1000000`이나 `from=2000-01-01` 같은 입력에는 무엇이 필요한가?
