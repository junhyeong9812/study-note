# api-design/10-notification-delivery-pipeline — 질문

## 질문

1. (왜) `orderRepository.save(order); smsClient.send(...)` 한 줄짜리 발송이 만드는 사고 다섯 가지를 들어라. 각각을 막는 장치는 무엇인가?
2. (그림) outbox → 릴레이 → 큐 → 발송 워커 → 공급자 흐름을 그리고, 워커가 보내기 **전**에 확인하는 것 세 가지와 보낸 **뒤** 응답을 나누는 세 갈래를 적어라.
3. (예측) 실험 A에서 트랜잭션 안에서 바로 발송한 뒤 롤백하면 `orders` 행 수와 도착한 알림은? outbox로 바꾸면?
4. (예측) 공급자가 처리는 하고 응답만 두 번 잃는다. 클라이언트는 성공할 때까지 재시도한다. 멱등 키가 없을 때와 있을 때 도착 통수는 각각 몇인가?
5. (경계) outbox의 `UNIQUE(notification_key)`가 막는 중복과 못 막는 중복은 각각 무엇인가? 못 막는 구간은 무엇이 닫나? 그것을 공급자가 지원하지 않으면?
6. (경계) FCM `UNREGISTERED`(404), FCM `UNAVAILABLE`(503), FCM `INVALID_ARGUMENT`(400), APNs `410 Unregistered`, SMTP `550 5.1.1`, SMTP `4yz`를 재시도·억제(삭제)·알람 중 어디로 보내나? `INVALID_ARGUMENT`를 바로 토큰 문제로 보면 안 되는 이유는?
7. (계산) 정보통신망법 제50조 ③의 야간 창을 적용하면 광고성 메시지를 KST 20:59, 22:30, 07:59, 08:00에 보내려 할 때 각각 언제 보내나? 서버가 UTC로 예약 시각을 계산했을 때 생기는 사고는?
8. (연결) 푸시 토큰을 언제 저장·갱신·삭제하나? FCM 문서가 말하는 비활성 기준과 Android 만료 기준은?
9. (장애 진단) 몇 주 사이 정상 고객의 비밀번호 재설정 메일까지 스팸함으로 간다. 어떤 지표·로그를 보고, 원인과 대처는 무엇인가?
