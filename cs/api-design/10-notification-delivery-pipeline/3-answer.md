# api-design/10-notification-delivery-pipeline — 정답

## 정답

### 1. 한 줄 발송의 다섯 사고

| 사고 | 막는 장치 |
|---|---|
| 응답 유실 후 재시도 → 중복 발송 | 사건에서 만든 멱등 발송 키 + 공급자 멱등 키 |
| 롤백됐는데 발송됨(유령 알림) | outbox — 발송 의도를 업무와 같은 트랜잭션에 기록 |
| 하드 바운스 주소에 계속 발송 → 평판 하락 | 실패 분류 + 억제 목록 |
| 죽은 푸시 토큰에 계속 발송 → 실패율 상승 | 404·410이면 토큰 삭제, 오래된 토큰 정리 |
| 야간 광고 → 법 위반 | 광고성 구분 + 수신자 시간 기준 야간 창 검사 + 야간 별도 동의 |

### 2. 흐름과 분기

```text
  [업무 + outbox 한 커밋] ─> 릴레이 ─> 큐 ─> 워커 ─> 공급자
```

- 보내기 전(워커, 발송 직전): ⓪ 이미 SENT인가 ① 억제 목록 ② 사용자 선호(채널·종류) ③ 광고성이면 야간 창·야간 동의.
- 보낸 뒤: 성공(기록) / 일시 실패(백오프 재시도, 기한 넘으면 DLQ) / 영구 실패(수신처 문제는 억제·토큰 삭제, 우리 문제는 알람).

### 3. 실험 A

- 직접 발송 + 롤백: `orders=0`, 도착한 알림 `[user1:주문 o1 완료]` — 주문은 없는데 알림은 나갔다.
- outbox + 롤백: `outbox=0` — 보낼 것이 남지 않는다.
- 이유: DB 롤백은 DB 안만 되돌린다. 외부로 나간 요청은 되돌리지 못한다.

### 4. 실험 B

- 멱등 키 없음: 시도 3회, 도착 3통.
- 멱등 키 있음: 시도 3회, 도착 1통.
- 응답 유실은 "실패"가 아니라 "결과 불명"이다. 결과 불명을 실패로 보고 재시도하면 중복이 된다.

### 5. UNIQUE가 막는 것과 못 막는 것

- 막는 것: 같은 사건을 코드가 두 번 적재하는 것. 실험 C에서 두 번째 INSERT가 `23505 duplicate key … "outbox_notification_key_key"`로 거절됐다.
- 못 막는 것: 릴레이·워커가 **보낸 뒤 기록하기 전에** 죽어 같은 행을 다시 집는 것. 실험 C "공급자 멱등 키 없음: 도착 2통".
- 닫는 것: 공급자 멱등 키(실험 C "있음: 1통").
- 공급자가 지원하지 않으면: 재시도 전 공급자 조회 API로 상태 확인, 재시도 횟수·간격 축소로 확률만 줄인다. 완전히 없애지는 못한다.

### 6. 응답 분류

| 응답 | 갈래 |
|---|---|
| FCM `UNREGISTERED`(404) | 영구(수신처) → 토큰 삭제 |
| FCM `UNAVAILABLE`(503) | 일시 → `Retry-After` 준수 + 지수 백오프(+지터) |
| FCM `INVALID_ARGUMENT`(400) | 영구 — 토큰 문제일 수도, 페이로드 문제일 수도 |
| APNs `410 Unregistered` | 영구(수신처) → 토큰 삭제 |
| SMTP `550 5.1.1` | 영구(수신처, 하드 바운스) → 억제 목록 |
| SMTP `4yz` | 일시 → 백오프 재시도, 기한 넘으면 실패 |

- `INVALID_ARGUMENT`는 페이로드 초과(4096바이트, 토픽 2048), 잘못된 데이터 키, TTL 범위 등 우리 쪽 문제로도 난다(FCM ErrorCode 문서). FCM 토큰 관리 문서는 메시지가 유효하다고 확인된 경우에만 토큰 문제로 보라고 한다. 바로 토큰을 지우면 우리 버그 하나로 멀쩡한 토큰을 대량 삭제한다.

### 7. 야간 창 계산

- 20:59 → 바로 보냄.
- 22:30 → 다음 날 08:00.
- 07:59 → 그날 08:00.
- 08:00 → 바로 보냄(창은 21:00 이상 또는 08:00 미만).
- (실험 E 출력과 같다.)
- UTC 사고: 예약 시각 14:00을 UTC로 계산하면 KST 23:00에 나간다. 야간 판정은 수신자 시간대(`Asia/Seoul`)로 한다.
- 이 조항은 영리목적 광고성 정보에 적용된다. 단서의 예외 매체는 시행령 제61조 ②에 따라 전자우편이다 — 광고 메일은 야간 창 밖이고, 문자·푸시가 대상이다(국가법령정보센터 조문).

### 8. 푸시 토큰 수명

- 저장·갱신: 앱이 업로드할 때마다 `(user, token, updated_at)`을 저장하고 타임스탬프를 갱신한다. 토큰이 바뀌면 교체한다(추가만 하지 않는다).
- 삭제: 발송 결과 FCM `UNREGISTERED`, APNs `410`이면 즉시. 주기 작업으로 오래된 토큰 정리.
- FCM 문서 기준: FCM에 한 달 넘게 연결하지 않은 기기의 등록을 stale로 본다(그래서 서버도 한 달 정도를 정리 기준으로 쓴다). Android에서 270일 비활성이면 FCM이 만료로 보고 보내기를 거부한다.

### 9. 재설정 메일까지 스팸함

- 볼 것: 바운스율(하드 바운스 비율), 수신 측 평판 지표(Gmail Postmaster Tools의 스팸률·도메인 평판), 수신 서버 응답 중 `5.7.x` 정책 거절 증가, 같은 도메인에서 나간 광고 캠페인 일정.
- 원인 후보: 하드 바운스(`5.1.1`)를 일시 실패로 재시도했거나 억제 목록에 넣지 않았다. 오래된 목록에 대량 광고를 보내 스팸 신고가 늘었다. 거래성과 광고 메일이 같은 도메인을 써서 광고가 깎은 평판이 재설정 메일까지 끌어내렸다.
- 대처: 하드 바운스·수신 거부·스팸 신고를 즉시 억제한다. 바운스 웹훅을 반영한다. 거래성·광고 발송 도메인(서브도메인)을 나눈다. 인증(SPF·DKIM·DMARC)과 원클릭 수신 거부 요건을 점검한다(network/51).
