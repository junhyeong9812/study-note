# api-design/06-refund — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> 작성 방식: 내가 먼저 기억으로 흐름을 서술하고, Claude는 빠지거나 틀린 곳을 짚는다. 대신 써주지 않는다.
> 이미 따라 치며 만든 정리본이 따로 있으면(organize류) 이 파일은 핵심 문장 압축 + 링크만 담는다.
> 2026-09-14: 쉽게 풀어쓴 서머리(Claude 작성) — 원본 myway/api-design 문서 기준.
> 2026-09-28: 통일 골격 양식으로 재배치 + 새 절 추가(Claude 작성 — 기존 본문은 이동만).

## 해결하는 문제

"환불 요청을 받아 PG 취소 · 포인트 · 쿠폰 · 재고를 되돌리고 알림을 보내라" — 여섯 단계 중 하나(PG 취소)는 되돌릴 수 없고, 하나(알림)는 주워 담을 수 없다. 앞의 다섯 문제가 여기 다 모인다.

```text
없으면 안 되는 것 네 가지

  (1) 멱등       "다시 눌렀더니 두 번 나갔다" — 그런데 부분 환불이라 order_id 는 키가 못 된다
  (2) 누적 상한  두 상담원이 동시에 부분 환불 → 같은 합계로 검사해 결제액을 넘는다 (조회-판단-쓰기 경쟁)
  (3) 순서       BEGIN → 복원 → PG 호출(5초) → COMMIT 실패 → 돈은 나갔는데 기록이 없다
  (4) 안분       5만원 주문 · 포인트 3천원 · 2만원 상품만 환불 → 포인트 1,200원? 남는 1원은?
```

쉬운 예: 여행 패키지 취소 — 항공권(외부, 취소 불가) · 호텔 · 바우처를 각각 되돌리는데, 항공사에 먼저 전화하면 그 뒤의 실패를 되돌릴 수 없으니 **우리 쪽 기록을 먼저 확정하고 외부는 나중에** 부른다.\
똑같은 구조다: 재시도 밖에서 한 번 만든 멱등 키 · 조건부 UPDATE로 누적 상한 · 의도 기록 → PG 호출(트랜잭션 밖) → 결과 기록의 3단 · 정수 안분 + 잔여 1원 규칙 · 알림은 맨 끝.\
실무 예: 커머스 환불 · 부분 취소, 구독 해지 정산, 예약 취소 수수료 — "외부 불가역 + 내부 여러 자원"이 있는 모든 되감기.

### 한눈에 — 쉽게 말하면

**환불 = 거래를 거꾸로 되감기. 6개 중 가장 어렵다 — 앞의 다섯 문제가 전부 모이고, 여기에 "되돌릴 수 없음"이 더해진다.**

- 되감을 것이 네 가지다: PG 결제 취소(외부, 불가역) + 포인트 복원 + 쿠폰 복원 + 재고 복원.\
  **전부 성공하거나, 반만 된 상태를 찾아낼 수 있어야 한다.**

> **불가역(irreversible)** — 한 번 실행하면 되돌릴 수 없는 것 — PG 취소, 알림 발송.\
> 예: 순서를 뒤로 미루고 확인 절차를 붙인다.

- 지문이 대놓고 유도하는 것: "버튼을 다시 눌렀더니 두 번 나갔다"(작년 사고 2회) = 멱등성.\
  그런데 **부분 환불이라 `order_id`만으로는 멱등 키가 안 된다** — 같은 주문에 환불이 여러 번 "정상적으로" 일어난다.

> **멱등성(idempotency)** — 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.\
> 예: 버튼을 다시 눌러도 환불은 한 번만 나가야 한다.

- 멱등을 잡고 나면 남는 함정: **누적 상한**(부분 환불 합계가 원 결제액을 못 넘게) — 이것은 01번 lost update와 정확히 같은 구조다.

> **누적 상한** — 부분 환불 합계 ≤ 원 결제액이라는 불변식.\
> 예: 조건부 UPDATE로 지킨다.

> **lost update** — 두 요청이 같은 값을 읽고 각자 계산해 써서 한쪽이 사라지는 버그.\
> 예: 조회-합산-판단의 함정이다.

- 실무 예: 커머스 환불, 구독 해지 환불, 여행 취소.

```text
[앞의 다섯이 모이는 지도]

  01 포인트 → 복원 + 안분        04 정산 → 원장·추적 가능성
  02 쿠폰   → 복원               05 웹훅 → PG 취소 결과 통지·재시도
  03 재고   → 복원 + 잠금 순서   +  이 문제 고유: 불가역(PG 취소·알림)
```

## 동작·원리

### 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 환불 가능 잔액(누적 상한) + 포인트·쿠폰·재고
  Q2. 동시에 두 번 오면?  → 이중 환불 / 상한 초과 (두 상담원이 같은 주문을)
  Q3. 중간에 끊기면?      → PG는 취소됐는데 우리 DB는 결제완료 (찾아낼 수 있나?)

권장 순서 (되돌릴 수 없는 것은 뒤로):
  검증(권한·상태·기간) → 멱등 기록+누적 상한 차감(내부 트랜잭션, 여기서 자리 확보)
  → PG 취소 호출(트랜잭션 밖! 800ms~5초) → 결과 기록+포인트·쿠폰·재고 복원 → 알림(맨 끝)

숨은 요구: A 멱등(order_id로는 부족) · B 누적 상한 · C 여러 자원 복원+불가역 순서 ·
           D 안분과 반올림 · E 비동기 상태 · H 알림 시점 · I 대사
```

> ⚠ 정정(2026-09-28): 이 노트 곳곳의 "800ms~5초"는 범위가 아니다 — 지문 원문은 "평균 800ms, 간혹 5초 이상"이다(REQUIREMENTS.md:51). 800ms는 최솟값이 아니고 5초는 최댓값이 아니다. 원본 CHECKLIST.md:106 의 줄임 표기를 옮긴 것.

### 설계 — 멱등성: 이번엔 키를 만들어야 한다 (A)

**언제 문제가 되나**: "다시 눌렀더니 두 번 나갔다."\
그런데 부분 환불이 가능하므로 "주문당 1회"가 성립하지 않는다.

나쁜 계약 → 좋은 계약:

```text
나쁨: order_id를 멱등 키로 → 두 번째 '정상' 부분 환불까지 막는다
나쁨: 서버가 재시도 루프 안에서 멱등키 생성 → 재시도마다 새 키 = 멱등이 무의미 (Grab 사고)

좋음: 키의 출처를 정한다
  ① 클라이언트가 Idempotency-Key 헤더를 생성해 보낸다 (재시도에도 같은 키 유지), 또는
  ② 결정적 entity 키: "이 결제의 환불은 하나"면 payment-1234-refund 같은 자연 키 (Airbnb)
  + 멱등 기록과 환불 기록은 하나의 ACID 단위 (AWS 조항)
  + 같은 키 + 다른 금액 → 409/422로 거부 / 진행 중 + 같은 키 → 409
  + 키 보관 기간 > 재시도가 올 수 있는 기간
```

- 응답 계약은 회사마다 정반대다: Stripe는 첫 응답을(500이어도) 재생, GoCardless는 409 + 충돌 자원 ID, 토스페이먼츠는 body 다르면 422/진행 중 409, AWS는 의미적으로 동등한 응답.\
  **선택이 프론트 복잡도를 결정한다.**
- Airbnb: 멱등 데이터는 **master DB에서만** 읽고 쓴다(복제 지연이 완료 건을 미실행으로 보이게 함).

### 설계 — 누적 상한: 다시 lost update (B)

**언제 문제가 되나**: 두 상담원이 동시에 같은 주문을 부분 환불할 때.\
"지금까지 환불액을 조회해서 더해보고 판단"은 두 요청이 같은 값을 읽는다.

```sql
-- 나쁨: SELECT SUM(환불액) → 앱에서 합산 비교 → INSERT   (그 사이에 남이 끼어든다)

-- 좋음: 조건부 UPDATE가 상한을 지킨다 (01번과 같은 무기)
UPDATE orders
   SET refunded_amount = refunded_amount + :이번 환불액
 WHERE order_id = :id
   AND refunded_amount + :이번 환불액 <= paid_amount;
-- affected rows 0 → 상한 초과 거부
```

> ⚠ 정정(2026-09-28): "나쁨" 예(`SELECT SUM` → INSERT)는 두 환불 행이 모두 INSERT되므로 한쪽 갱신이 덮여 사라지는 lost update와는 모양이 다르다 — 같은 집계값으로 검사해 누적 상한을 위반하는 동시성 이상(격리 수준에 따라 write skew)이다. lost update는 누적값을 읽어 계산해 덮어쓸 때의 이름이다. 막는 방법(조건부 UPDATE)은 같다. 근거: DDIA 7장(lost update · write skew 구분).

- 같은 `order_item_id`의 환불 수량 합이 주문 수량을 넘지 않는 것도 같은 방식으로.

> **조건부 UPDATE / affected rows** — 검사와 갱신을 DB 한 문장에 넣고 바뀐 행 수로 판정하는 기법.\
> 예: affected rows 0 이면 상한 초과로 거부한다.

### 설계 — 여러 자원 복원과 불가역의 순서 (C)

**언제 문제가 되나**: PG 취소는 되돌릴 수 없고, 800ms~5초 걸리는 외부 호출이다.

나쁜 계약 → 좋은 계약:

```text
나쁨: BEGIN → 포인트·쿠폰·재고 복원 → PG 호출(5초!) → COMMIT
  ① 외부 호출을 DB 트랜잭션 안에 → 잠금을 5초 들고 있어 전체가 막힌다
  ② PG 성공 후 COMMIT 실패 → 돈은 나갔는데 기록이 없다 (그리고 PG 취소는 못 되돌린다)

좋음: 내부 먼저, 불가역은 나중에, 기록 못 하면 부르지도 않는다
  1) 내부 트랜잭션: 환불 의도 기록(멱등키) + 누적 상한 차감  → COMMIT
  2) PG 취소 호출 (트랜잭션 밖)
  3) 내부 트랜잭션: 결과 기록 + 포인트·쿠폰·재고 복원(잠금은 고정 순서로)
     3)이 실패하면 → "PG 취소됨 + 내부 미복원" 흔적이 1)·2) 기록으로 남아 있다
     → 복구 배치가 이어서 처리 (복원 각각이 멱등해야 여러 번 돌아도 안전)
```

> ⚠ 정정(2026-09-28): 2) PG 호출은 우리 DB에 아무것도 남기지 않는다 — 3)이 실패하면 확실히 남는 것은 1)의 의도 기록뿐이고, "PG 취소됨"은 PG 조회로 확인해야 안다. 그래서 복구 배치는 오래 머문 의도 기록 건을 PG에 조회해 이어 처리하며, PG 호출에는 영속화한 환불 요청 ID를 멱등 키로 넘겨 재호출이 이중 취소가 되지 않게 한다. 또 1)의 "누적 상한 차감"은 완료액이 아니라 예약액이다 — PG 확정 실패면 해제, 결과 불명이면 유지한다.

- Airbnb Orpheus의 3단 구조가 이것: Pre-RPC(의도 기록) / RPC(DB 작업 금지) / Post-RPC(결과 기록), 각각 원자 트랜잭션.
- Twilio의 fail-safe를 환불로 번역하면: **"복원을 기록할 수 없으면 PG 취소를 부르지 않는다."**
- 포인트·쿠폰·재고를 잠글 때 순서 고정(03번의 데드락 축이 여기서 재등장).

### 설계 — 안분과 반올림 (D, 지문에 한 줄로만 암시)

**언제 문제가 되나**: 5만원 주문에 포인트 3천원을 썼고 그중 한 상품(2만원)만 환불하면, 포인트는 얼마를 돌려주나?

> **안분(pro-rata)** — 할인·포인트를 상품 금액 비율로 나눠 배분하는 계산.\
> 예: 반올림 1원 처리 규칙까지가 안분이다.

```text
안분: 할인·포인트를 상품 금액 비율로 나눠 붙이는 것
  2만원/5만원 = 40% → 포인트 3,000 × 0.4 = 1,200원 복원, 현금 18,800원 환불

함정: 반올림 — 3,333원을 3상품에 안분하면 1,111 + 1,111 + 1,111 = 3,333? 1원이 남거나 모자란다
  → 남는 1원을 어디에 붙일지(첫/마지막 상품) 규칙을 정하고,
  → 마지막 상품 환불 때 "지금까지 환불한 금액의 잔여"로 정산해 총합을 맞춘다
  → 금액은 부동소수 금지 (돈은 정수/decimal)
```

> ⚠ 정정(2026-09-28): 예시 숫자가 맞지 않는다 — 3,333 ÷ 3 = 1,111로 나누어떨어져 합이 정확히 3,333이다. 1원이 어긋나는 예는 3,334원(1,111.33… → 버림 1,111 × 3 = 3,333, 1원 부족)이나 3,332원(반올림 1,111 × 3 = 3,333, 1원 초과)이다. 정답 5번의 설명(3,334)이 맞다.

- 배송비는 환불되는가, 부분 환불이면?\
  — 전부 확정 질문 대상.\
  **실무 CS 문의가 가장 많은 지점이 D다.**

## 쓰이는 자료구조·알고리즘

- **멱등 키 저장소** — 키(클라이언트 생성 `Idempotency-Key` 또는 entity 키) → 상태(진행 중 / 완료) + 결과. 환불 기록과 같은 ACID 단위에 쓴다 → [ops-patterns/06-idempotency-store](../../ops-patterns/06-idempotency-store/2-summary.md).
- **조건부 UPDATE로 누적 상한** — `refunded_amount + :x <= paid_amount`를 한 문장에 넣는 원자 CAS. 01번의 잔액 차감과 같은 무기 → [01-order-point](../01-order-point/2-summary.md).
- **사가(saga) / 3단 처리** — 의도 기록(내부 트랜잭션) → 외부 호출(불가역, 트랜잭션 밖) → 결과 기록 + 복원(내부 트랜잭션). 단계마다 별도 트랜잭션이고 셋 전체가 하나의 원자 트랜잭션은 아니다. 보상할 수 없는 단계를 뒤로 미루고, 실패 시 복구 배치가 이어서 처리한다 → [ops-patterns/08-saga](../../ops-patterns/08-saga/2-summary.md).
- **상태 기계** — 커리큘럼 🔧: 주문 상태(`PAID → PARTIALLY_REFUNDED → REFUNDED` — `PARTIALLY_REFUNDED`는 원본 CHECKLIST G의 제안)와 환불 건별 진행 기록(설계 예시: `REQUESTED → PG_CANCELLED → RESTORED → NOTIFIED` — 원본에 없는 이름). 주문 상태 하나로는 여러 환불 건의 진행을 표현하기 어렵다 — 환불별 식별자와 영속적인 진행·결과 기록이 있어야 "반만 된 환불"을 찾기 쉽다(PG 대사로도 찾을 수 있다) → [domain-modeling/basic/09-order-state](../../domain-modeling/basic/09-order-state/2-summary.md) · [domain-modeling/advanced/04-refund](../../domain-modeling/advanced/04-refund/2-summary.md).
- **정수 안분** — 비율 배분을 정수 나눗셈으로 하고 나머지를 규칙(첫/마지막 항목)으로 배정한다. 마지막 환불은 "원 사용액 − 지금까지 복원액"으로 총합을 맞춘다 → [domain-modeling/basic/17-cart-discount](../../domain-modeling/basic/17-cart-discount/2-summary.md).
- **잠금 순서 정렬** — 포인트 · 쿠폰 · 재고 행을 고정 순서로 잠근다 → [03-stock-deduct](../03-stock-deduct/2-summary.md).
- **상쇄 엔트리 원장** — 환불은 원 결제를 지우지 않고 조정(반대 방향) 엔트리를 더한다. 복식부기는 이와 별개로 거래 하나마다 차변·대변이 균형을 이루게 적는 장부법이다(Uber는 둘을 함께 쓴다 — 원본 REFERENCE). 전액 환불이면 원 거래의 효과가 상쇄되지만, 부분 환불이면 원 결제와 환불 합이 0이 아니다 → [ops-patterns/16-event-sourcing](../../ops-patterns/16-event-sourcing/2-summary.md).
- **대사 + 재시도 분류** — 우리 기록과 PG 기록의 병합 비교로 드리프트를 찾고, 에러를 retryable / non-retryable로 나눈다 → [ops-patterns/01-retry-backoff](../../ops-patterns/01-retry-backoff/2-summary.md).

## 적용 — 풀어나가는 법

환불은 앞의 다섯 문제를 순서대로 다시 푸는 것이다 — 단, **되돌릴 수 없는 단계가 끼어 있다**는 조건이 모든 순서를 바꾼다.\
순서: ① 지문의 사고 문장을 멱등 요구로, 참고 네 줄을 누적 상한 · 안분 · 비동기 · 불가역으로 번역한다 → ② 키의 출처(클라이언트 헤더 / entity 키)와 응답 계약을 정한다 → ③ "내부 의도 기록 → 외부 불가역 호출 → 내부 결과 기록"으로 트랜잭션 경계를 그린다(외부 호출은 밖) → ④ 안분 · 반올림 · 배송비 규칙을 되묻고, 알림은 맨 끝에 둔다 → ⑤ 반만 된 상태를 찾는 대사와 복구 배치를 붙인다.\
아래 과제 목록이 그 훈련의 실제 절차다.

### 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 CS 플랫폼팀의 평범한 요구사항 문서다: 지금은 상담원이 어드민에서 환불 버튼을 눌러 처리하는데, 고객이 앱에서 직접 신청할 수 있게 `POST /orders/{order_id}/refunds` 를 만들라.\
기대 동작에 **환불 금액 계산 → PG 결제 취소 → 포인트·쿠폰 되돌리기 → 재고 복원 → 주문 상태 갱신 → 고객 알림** 여섯 단계가 나열돼 있고, 배경에 **"환불 버튼을 눌렀는데 응답이 없어서 다시 눌렀더니 두 번 나갔다"는 사고가 작년에 두 번** 있었다고 적혀 있다(= 멱등성 유도).\
참고에는 **부분 환불 가능 · 포인트와 쿠폰이 함께 적용되었을 수 있음 · PG는 평균 800ms, 간혹 5초 이상 · 환불은 되돌릴 수 없음** 네 줄이 있고, 이 네 줄이 각각 누적 상한·안분·비동기·불가역 축을 심어놓았다.\
**6개 중 가장 어렵고, 앞의 다섯 문제 요소가 전부 여기 모인다** — 마지막에 푸는 것을 권한다.

> **PG(Payment Gateway)** — 카드사·은행과 결제·취소를 중계하는 외부 대행사.\
> 예: 느리고(800ms~5초), 취소는 불가역이다.

과제 목록 (원본 "이 문제를 푸는 방법" · NOTES.md 기준):

- REQUIREMENTS.md 지문만 읽고, NOTES.md 1번 칸에 **타이머 15분**으로 "확정해야 할 것"을 질문 형태로 나열한다 (답이 아니라 질문을 적는다)
- NOTES.md 2번 칸: 결정을 **"A 대신 B, 왜냐하면 C"** 형태로 적는다 (유보형 금지)
- Claude에게 "어떻게 해야 해?"가 아니라 **본인이 내린 결정을 지시·검증받는** 프롬프트로 설계를 진행하고, 보낸 프롬프트 원문을 3번 칸에 남긴다
- 실제 DB가 없더라도 **있다고 가정했을 때의 트랜잭션 경계를 코드나 주석으로 표현**한다 (구현 조건)
- **마지막에** solution/CHECKLIST.md 를 열어 대조하고 나머지 칸(대조 결과 / 가장 아팠던 놓침 / 30초 설명)을 채운다 — 먼저 보면 효과가 없다

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

### 나머지 축 — 짧게

- **비동기 상태(E)**: PG가 5초 걸리면 동기 대기 불가 → "접수됨"과 "환불됨"이 다른 상태가 된다.\
  그 차이를 사용자에게 보여주고, 접수 후 실패를 알릴 경로를 정한다.
- **권한·검증(F)**: 요청자 = 주문 소유자?\
  환불 가능한 상태·기간(청약철회)?\
  이미 전액 환불?
- **상태 전이(G)**: 부분 환불 후 상태(`PARTIALLY_REFUNDED`?), 전액 판정 시점, 진행 중 또 오는 환불 요청.
- **알림(H)**: 알림은 되돌릴 수 없다 — **확정 후 맨 끝에.**\
  알림 실패가 환불을 롤백시키면 안 된다.
- **대사·에러 분류(I)**: "PG는 취소됐는데 우리는 결제완료"를 상시 탐지(Shopify의 드리프트 탐지).\
  에러를 retryable/non-retryable로 분류 — **분류를 틀리면 영구 실패 또는 중복 환불이다.**

> **대사(reconciliation)** — 우리 기록과 PG 기록을 맞춰보고 드리프트를 찾는 작업.\
> 예: 에러를 retryable / non-retryable 로 분류하는 것도 같은 축이다.

- **되묻기(J)**: 안분 규칙, 배송비, 환불 가능 기간, 부분 환불 시 쿠폰 처리, 그리고 "되돌릴 수 없다"를 보고 **확인 절차**를 물었는가.

## 장애 시나리오와 대처

아래는 우리 시스템 안에서 마주치는 모양이다. 회사 사례는 「실패 사례」 절에 따로 있다.

**1. 같은 상품이 두 번 환불됐는데 멱등 키는 서로 다르다**

- 현상: 고객 계좌에 두 번 입금, PG 정산에 같은 결제의 취소 2건.
- 보이는 형태: 같은 `order_id` · 같은 `order_item_id` 환불 레코드 2개, 요청 간격 3초(타임아웃 재시도), `Idempotency-Key`가 서로 다르다.
- 원인: 키를 재시도 루프 안에서 만들었다 — 서버가 재시도마다 새 키를 생성했거나, 클라이언트가 재시도할 때 키를 새로 뽑았다. 멱등 키가 있어도 재시도마다 바뀌면 없는 것과 같다(정답 2번 참고).
- 대처: 논리적 환불 요청마다 고유한 요청 ID(클라이언트 생성 `Idempotency-Key` 등)를 요청 시작 시 한 번 만들고, 그 요청의 재시도에서만 같은 값을 재사용한다. 항목 기반 결정적 키(`payment-1234-refund-<항목>`)는 "항목당 환불은 정확히 한 번"이라는 정책이 있을 때만 쓴다 — 같은 항목의 수량을 나눠 환불할 수 있으면 정상적인 두 번째 환불까지 막는다. 멱등 기록과 환불 기록을 같은 트랜잭션에 쓰고, 진행 중인 같은 키에는 409를 준다(응답 코드는 선택한 계약 — 원본 REFERENCE 토스페이먼츠 예).

**2. 5만원 결제에 6만원이 환불됐다**

- 현상: 두 상담원이 같은 주문을 각각 3만원씩 부분 환불했고 둘 다 성공했다.
- 보이는 형태: 두 요청이 1초 안에 도착, 둘 다 200. 환불 합계가 결제액을 초과.
- 원인: `SELECT SUM(환불액)` → 앱에서 더해 비교 → INSERT. 두 요청이 같은 합계로 검사해 둘 다 통과했다 — 두 INSERT가 모두 남으므로 엄밀히는 덮어쓰기(lost update)가 아니라 집계 조건에 대한 동시성 이상(격리 수준에 따라 write skew로 분류)이다. 원본 CHECKLIST B는 이를 lost update라 부르며 01번과 같은 구조로 본다(정답 3번 참고).
- 대처: `UPDATE orders SET refunded_amount = refunded_amount + :x WHERE id = :id AND refunded_amount + :x <= paid_amount`로 상한 검사와 누적을 한 문장에 넣고 affected rows 0이면 거부한다. `CHECK (refunded_amount <= paid_amount)`를 건다. 상품별 환불 수량 합도 같은 방식으로.\
  이 차감은 PG 호출 **전**이라 완료 환불액이 아니라 **예약액**이다 — "완료액 + 진행 중 예약액 ≤ 결제액"을 지키고, PG 성공이면 예약을 완료액으로 전환, 확정 실패면 해제, 결과 불명이면 확인될 때까지 유지한다.

**3. PG는 취소됐는데 앱은 "환불 처리 중"에서 멈췄다**

- 현상: 고객 — "카드사에서 취소 문자가 왔는데 앱은 아직 처리 중이고 포인트도 안 돌아왔다."
- 보이는 형태: PG 취소 성공 로그 직후 DB 커넥션 예외 또는 배포 재시작. 3단계(결과 기록 + 복원)가 한 트랜잭션이라 결과도 저장되지 않았다 — 환불 건은 1단계의 `REQUESTED`(의도만 기록)에 오래 머물러 있고 포인트 · 쿠폰 · 재고 복원 기록이 없다.
- 원인: 3단계(결과 기록 + 복원)가 실패했는데 이어서 처리할 주체가 없다. 반만 된 환불(정답 4번 참고).
- 대처: 확실히 남는 것은 1단계 의도 기록뿐이다 — 복구 배치가 오래된 `REQUESTED` · 처리 중 · 결과 불명 건을 훑어 PG 조회 API로 결과를 확인한 뒤 복원을 마저 한다(`PG_CANCELLED`만 찾으면 이 장애를 놓친다). 영속화한 환불 요청 ID를 PG 멱등 키로 재사용하고 PG의 멱등·조회 계약을 확인한다 — 결과 불명 건을 무조건 재호출하면 이중 취소가 될 수 있다. 복원 각각이 멱등해야 배치가 여러 번 돌아도 안전하다. PG 대사 배치로 "PG 취소 · 내부 미완료"를 상시 탐지하고, 재시도해도 안 되는 건은 dead letter로 보내 사람이 본다.

**4. 전액 환불이 끝났는데 포인트가 1원 모자란다**

- 현상: 부분 환불 세 번 뒤 마지막 상품까지 환불했는데 포인트 잔액이 원래보다 1원 적다(또는 많다).
- 보이는 형태: 환불 3건의 포인트 복원액이 각각 반올림돼 있고, 합이 원 사용 포인트와 1원 차이. CS 문의는 "1원"이지만 신뢰 문제로 커진다.
- 원인: 건별 안분을 각각 반올림해 더했다 — 건별 반올림의 합 ≠ 원값. 잔여를 처리할 규칙이 없다(정답 5번 참고).
- 대처: 안분은 정수 연산으로, 남는 1원의 귀속 규칙(첫/마지막 상품)을 정해 문서화한다. 마지막 환불은 비율 계산이 아니라 "원 사용액 − 지금까지 복원한 액"으로 정산해 총합을 맞춘다. 금액은 정수/decimal, 부동소수 금지.

### 실패 사례 — 이 항목들이 나온 실제 사고

- **Grab(A의 정본)**: 멱등키를 쓰는데도 이중 지급 — 핸들러 전체가 재큐잉되며 **1단계부터 다시 시작해 새 멱등키를 생성**했다.\
  해법: 단계(activity) 단위 재시도 + 키를 durable state에 보관.
- **Airbnb**: request-level 키와 entity-level 키 구분, 3단 원자 트랜잭션, master-only 멱등 데이터, 5XX/4XX 재시도 분류.

> ⚠ 정정(2026-09-28): "3단 원자 트랜잭션"은 세 단계 전체가 하나의 원자 트랜잭션이라는 뜻이 아니다 — Orpheus는 Pre-RPC / RPC / Post-RPC의 3단계이고, Pre·Post가 **각각** 원자 트랜잭션이며 RPC(외부 호출) 단계에서는 DB 작업을 하지 않는다. 근거: 원본 REFERENCE.md:219-220, Airbnb 원문.
- **우아한형제들**: PG 승인됐는데 기록 없는 "고아 승인" — 실시간 조회로 1시간 내 자동 취소.\
  **환불은 방향이 반대다**: PG는 취소됐는데 DB는 결제완료인 상태를 탐지해야 한다.

> **고아 승인 / 고아 취소** — 외부(PG)에는 있는데 내 시스템에는 기록이 없는 상태.\
> 예: 대사로 탐지한다.

- **Twilio(2013)**: 외부 부수효과는 성공, 내부 기록은 실패하는 조합 → "잔액을 읽거나 쓸 수 없으면 청구하지 않는다"는 fail-safe.
- **올리브영**: read-modify-write 구조의 실사고 — 누적 상한 검사가 정확히 같은 형태다.
- **토스페이먼츠 / Uber**: 취소를 UPDATE가 아닌 INSERT-only 상쇄 엔트리로 — **환불은 원 결제를 지우는 게 아니라 반대 방향 엔트리를 더하는 것.**\
  Uber는 합이 0인 복식부기.

> **상쇄 엔트리 / INSERT-only 원장** — 수정 대신 반대 방향 금액의 새 줄을 추가하는 기록 방식.\
> 예: 불변이라 감사 가능하다.

- **Atlassian(2022)**: "permanently delete" 스크립트를 잘못된 ID 목록에 실행 → 23분 만에 883개 사이트 삭제, 복구 최대 14일.\
  "되돌릴 수 없다" 한 줄이 요구하는 것 = 확인 절차, dry-run, soft 처리, 복구 경로.

> **dry-run** — 실제로 실행하지 않고 무엇이 일어날지만 미리 보여주는 모드.\
> 예: 불가역 작업의 확인 절차다.

## 핵심 문장

- 앞의 다섯 문제가 전부 모인다 — 멱등(01·05) + 누적 상한(01의 lost update) + 여러 자원 잠금 순서(03) + 원장·추적(04) + 외부 통지(05), 그리고 **불가역**이 얹힌다.
- **`order_id`는 이번엔 멱등 키가 못 된다** — 부분 환불이 여러 번 정상이므로, 키는 클라이언트 생성 또는 결정적 entity 키로, **재시도 루프 밖에서 한 번만** 만든다.
- 멱등을 잡아도 끝이 아니다 — **부분 환불의 누적 상한은 별도 문제**고, 조회-합산-판단은 lost update다.
- 외부 호출은 트랜잭션 밖으로, 불가역은 뒤로 — **기록할 수 없으면 PG를 부르지도 마라.**
- 환불은 지우기가 아니라 **반대 방향 엔트리 추가**다 — 그래야 감사와 대사가 된다.

### 용어 풀이

- **불가역(irreversible)**: 한 번 실행하면 되돌릴 수 없는 것 — PG 취소, 알림 발송.\
  순서를 뒤로 미루고 확인 절차를 붙인다.
- **멱등성(idempotency)**: 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.
- **Idempotency-Key**: 클라이언트가 요청마다 만들어 보내는 멱등 키 헤더.\
  재시도에도 같은 키를 유지해야 의미가 있다.
- **entity-level 키**: "이 결제의 환불은 하나" 같은 도메인 규칙에서 결정적으로 만드는 키(예: payment-1234-refund).
- **누적 상한**: 부분 환불 합계 ≤ 원 결제액이라는 불변식.\
  조건부 UPDATE로 지킨다.
- **lost update**: 두 요청이 같은 값을 읽고 각자 계산해 써서 한쪽이 사라지는 버그.\
  조회-합산-판단의 함정.
- **조건부 UPDATE / affected rows**: 검사와 갱신을 DB 한 문장에 넣고 바뀐 행 수로 판정하는 기법.
- **ACID 단위**: 전부 성공 아니면 전부 취소로 묶이는 트랜잭션 덩어리.\
  멱등 기록과 실제 변경은 한 단위여야 한다.
- **PG(Payment Gateway)**: 카드사·은행과 결제·취소를 중계하는 외부 대행사.\
  느리고(800ms~5초), 취소는 불가역.
- **안분(pro-rata)**: 할인·포인트를 상품 금액 비율로 나눠 배분하는 계산.\
  반올림 1원 처리 규칙까지가 안분이다.
- **retryable / non-retryable**: 재시도하면 될 수 있는 실패(5xx류) / 재시도해도 소용없는 실패(4xx류).\
  분류를 틀리면 영구 실패 또는 중복 환불.

> ⚠ 정정(2026-09-28): 상태 코드 계열만으로는 분류할 수 없다 — 429(요청 과다)·408 같은 4xx는 재시도 대상일 수 있고, 5xx·타임아웃은 PG 쪽 작업이 이미 성공한 뒤에도 날 수 있다(결과 불명). PG의 오류 코드·재시도 계약·멱등성 보장을 기준으로 분류하고, 결과 불명은 조회로 확인한다. 5XX/4XX 구분은 원본 REFERENCE.md:223 의 Airbnb 요약을 옮긴 출발점이다.
- **고아 승인/취소**: 외부(PG)에는 있는데 내 시스템에는 기록이 없는 상태.\
  대사로 탐지한다.
- **대사(reconciliation)**: 우리 기록과 PG 기록을 맞춰보고 드리프트를 찾는 작업.
- **상쇄 엔트리 / INSERT-only 원장**: 수정 대신 반대 방향 금액의 새 줄을 추가하는 기록 방식.\
  불변이라 감사 가능.
- **복식부기(double-entry)**: 모든 돈 움직임을 두 방향 엔트리로 적어 합이 0이 되게 하는 장부법.
- **sweeper(복구 배치)**: 반만 된 환불("PG 취소됨 + 내부 미복원")의 흔적을 찾아 이어서 처리하는 주기 작업.\
  복원이 멱등해야 안전하다.
- **dry-run**: 실제로 실행하지 않고 무엇이 일어날지만 미리 보여주는 모드.\
  불가역 작업의 확인 절차.
