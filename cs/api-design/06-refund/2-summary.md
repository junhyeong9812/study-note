# api-design/06-refund — 정리 (힌트)

> 복습 시 이 파일은 **질문에 막혔을 때만** 연다. 먼저 읽고 답하면 인출이 아니라 받아쓰기다.
> 작성 방식: 내가 먼저 기억으로 흐름을 서술하고, Claude는 빠지거나 틀린 곳을 짚는다. 대신 써주지 않는다.
> 이미 따라 치며 만든 정리본이 따로 있으면(organize류) 이 파일은 핵심 문장 압축 + 링크만 담는다.
> 2026-09-14: 쉽게 풀어쓴 서머리(Claude 작성) — 원본 myway/api-design 문서 기준.

## 한눈에 — 쉽게 말하면

**환불 = 거래를 거꾸로 되감기. 6개 중 가장 어렵다 — 앞의 다섯 문제가 전부 모이고, 여기에 "되돌릴 수 없음"이 더해진다.**

- 되감을 것이 네 가지다: PG 결제 취소(외부, 불가역) + 포인트 복원 + 쿠폰 복원 + 재고 복원.\
  **전부 성공하거나, 반만 된 상태를 찾아낼 수 있어야 한다.**

> **불가역(irreversible)** — 한 번 실행하면 되돌릴 수 없는 것 — PG 취소, 알림 발송.\
> 예: 순서를 뒤로 미루고 확인 절차를 붙인다.

- 지문이 대놓고 유도하는 것: "버튼을 다시 눌렀더니 두 번 나갔다"(작년 사고 2회) = 멱등성.\
  그런데 **부분 환불이라 `order_id`만으로는 멱등 키가 안 된다** — 같은 주문에 환불이 여러 번 "정상적으로" 일어난다.

> **멱등성(idempotency)** — 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.\
> 예: 버튼을 다시 눌러도 환불은 한 번만 나가야 한다.

- 멱등을 잡고 나면 남는 함정: **누적 상한**(부분 환불 합계가 원 결제액을 못 넘게) — 이것은 01번 lost update와 정확히 같은 구조다.

> **누적 상한** — 부분 환불 합계 ≤ 원 결제액이라는 불변식.\
> 예: 조건부 UPDATE로 지킨다.

> **lost update** — 두 요청이 같은 값을 읽고 각자 계산해 써서 한쪽이 사라지는 버그.\
> 예: 조회-합산-판단의 함정이다.

- 실무 예: 커머스 환불, 구독 해지 환불, 여행 취소.

```text
[앞의 다섯이 모이는 지도]

  01 포인트 → 복원 + 안분        04 정산 → 원장·추적 가능성
  02 쿠폰   → 복원               05 웹훅 → PG 취소 결과 통지·재시도
  03 재고   → 복원 + 잠금 순서   +  이 문제 고유: 불가역(PG 취소·알림)
```

## 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 CS 플랫폼팀의 평범한 요구사항 문서다: 지금은 상담원이 어드민에서 환불 버튼을 눌러 처리하는데, 고객이 앱에서 직접 신청할 수 있게 `POST /orders/{order_id}/refunds` 를 만들라.\
기대 동작에 **환불 금액 계산 → PG 결제 취소 → 포인트·쿠폰 되돌리기 → 재고 복원 → 주문 상태 갱신 → 고객 알림** 여섯 단계가 나열돼 있고, 배경에 **"환불 버튼을 눌렀는데 응답이 없어서 다시 눌렀더니 두 번 나갔다"는 사고가 작년에 두 번** 있었다고 적혀 있다(= 멱등성 유도).\
참고에는 **부분 환불 가능 · 포인트와 쿠폰이 함께 적용되었을 수 있음 · PG는 평균 800ms, 간혹 5초 이상 · 환불은 되돌릴 수 없음** 네 줄이 있고, 이 네 줄이 각각 누적 상한·안분·비동기·불가역 축을 심어놓았다.\
**6개 중 가장 어렵고, 앞의 다섯 문제 요소가 전부 여기 모인다** — 마지막에 푸는 것을 권한다.

> **PG(Payment Gateway)** — 카드사·은행과 결제·취소를 중계하는 외부 대행사.\
> 예: 느리고(800ms~5초), 취소는 불가역이다.

과제 목록 (원본 "이 문제를 푸는 방법" · NOTES.md 기준):

- REQUIREMENTS.md 지문만 읽고, NOTES.md 1번 칸에 **타이머 15분**으로 "확정해야 할 것"을 질문 형태로 나열한다 (답이 아니라 질문을 적는다)
- NOTES.md 2번 칸: 결정을 **"A 대신 B, 왜냐하면 C"** 형태로 적는다 (유보형 금지)
- Claude에게 "어떻게 해야 해?"가 아니라 **본인이 내린 결정을 지시·검증받는** 프롬프트로 설계를 진행하고, 보낸 프롬프트 원문을 3번 칸에 남긴다
- 실제 DB가 없더라도 **있다고 가정했을 때의 트랜잭션 경계를 코드나 주석으로 표현**한다 (구현 조건)
- **마지막에** solution/CHECKLIST.md 를 열어 대조하고 나머지 칸(대조 결과 / 가장 아팠던 놓침 / 30초 설명)을 채운다 — 먼저 보면 효과가 없다

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

## 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 환불 가능 잔액(누적 상한) + 포인트·쿠폰·재고
  Q2. 동시에 두 번 오면?  → 이중 환불 / 상한 초과 (두 상담원이 같은 주문을)
  Q3. 중간에 끊기면?      → PG는 취소됐는데 우리 DB는 결제완료 (찾아낼 수 있나?)

권장 순서 (되돌릴 수 없는 것은 뒤로):
  검증(권한·상태·기간) → 멱등 기록+누적 상한 차감(내부 트랜잭션, 여기서 자리 확보)
  → PG 취소 호출(트랜잭션 밖! 800ms~5초) → 결과 기록+포인트·쿠폰·재고 복원 → 알림(맨 끝)

숨은 요구: A 멱등(order_id로는 부족) · B 누적 상한 · C 여러 자원 복원+불가역 순서 ·
           D 안분과 반올림 · E 비동기 상태 · H 알림 시점 · I 대사
```

## 설계 — 멱등성: 이번엔 키를 만들어야 한다 (A)

**언제 문제가 되나**: "다시 눌렀더니 두 번 나갔다."\
그런데 부분 환불이 가능하므로 "주문당 1회"가 성립하지 않는다.

나쁜 계약 → 좋은 계약:

```text
나쁨: order_id를 멱등 키로 → 두 번째 '정상' 부분 환불까지 막는다
나쁨: 서버가 재시도 루프 안에서 멱등키 생성 → 재시도마다 새 키 = 멱등이 무의미 (Grab 사고)

좋음: 키의 출처를 정한다
  ① 클라이언트가 Idempotency-Key 헤더를 생성해 보낸다 (재시도에도 같은 키 유지), 또는
  ② 결정적 entity 키: "이 결제의 환불은 하나"면 payment-1234-refund 같은 자연 키 (Airbnb)
  + 멱등 기록과 환불 기록은 하나의 ACID 단위 (AWS 조항)
  + 같은 키 + 다른 금액 → 409/422로 거부 / 진행 중 + 같은 키 → 409
  + 키 보관 기간 > 재시도가 올 수 있는 기간
```

- 응답 계약은 회사마다 정반대다: Stripe는 첫 응답을(500이어도) 재생, GoCardless는 409 + 충돌 자원 ID, 토스페이먼츠는 body 다르면 422/진행 중 409, AWS는 의미적으로 동등한 응답.\
  **선택이 프론트 복잡도를 결정한다.**
- Airbnb: 멱등 데이터는 **master DB에서만** 읽고 쓴다(복제 지연이 완료 건을 미실행으로 보이게 함).

## 설계 — 누적 상한: 다시 lost update (B)

**언제 문제가 되나**: 두 상담원이 동시에 같은 주문을 부분 환불할 때.\
"지금까지 환불액을 조회해서 더해보고 판단"은 두 요청이 같은 값을 읽는다.

```sql
-- 나쁨: SELECT SUM(환불액) → 앱에서 합산 비교 → INSERT   (그 사이에 남이 끼어든다)

-- 좋음: 조건부 UPDATE가 상한을 지킨다 (01번과 같은 무기)
UPDATE orders
   SET refunded_amount = refunded_amount + :이번 환불액
 WHERE order_id = :id
   AND refunded_amount + :이번 환불액 <= paid_amount;
-- affected rows 0 → 상한 초과 거부
```

- 같은 `order_item_id`의 환불 수량 합이 주문 수량을 넘지 않는 것도 같은 방식으로.

> **조건부 UPDATE / affected rows** — 검사와 갱신을 DB 한 문장에 넣고 바뀐 행 수로 판정하는 기법.\
> 예: affected rows 0 이면 상한 초과로 거부한다.

## 설계 — 여러 자원 복원과 불가역의 순서 (C)

**언제 문제가 되나**: PG 취소는 되돌릴 수 없고, 800ms~5초 걸리는 외부 호출이다.

나쁜 계약 → 좋은 계약:

```text
나쁨: BEGIN → 포인트·쿠폰·재고 복원 → PG 호출(5초!) → COMMIT
  ① 외부 호출을 DB 트랜잭션 안에 → 잠금을 5초 들고 있어 전체가 막힌다
  ② PG 성공 후 COMMIT 실패 → 돈은 나갔는데 기록이 없다 (그리고 PG 취소는 못 되돌린다)

좋음: 내부 먼저, 불가역은 나중에, 기록 못 하면 부르지도 않는다
  1) 내부 트랜잭션: 환불 의도 기록(멱등키) + 누적 상한 차감  → COMMIT
  2) PG 취소 호출 (트랜잭션 밖)
  3) 내부 트랜잭션: 결과 기록 + 포인트·쿠폰·재고 복원(잠금은 고정 순서로)
     3)이 실패하면 → "PG 취소됨 + 내부 미복원" 흔적이 1)·2) 기록으로 남아 있다
     → 복구 배치가 이어서 처리 (복원 각각이 멱등해야 여러 번 돌아도 안전)
```

- Airbnb Orpheus의 3단 구조가 이것: Pre-RPC(의도 기록) / RPC(DB 작업 금지) / Post-RPC(결과 기록), 각각 원자 트랜잭션.
- Twilio의 fail-safe를 환불로 번역하면: **"복원을 기록할 수 없으면 PG 취소를 부르지 않는다."**
- 포인트·쿠폰·재고를 잠글 때 순서 고정(03번의 데드락 축이 여기서 재등장).

## 설계 — 안분과 반올림 (D, 지문에 한 줄로만 암시)

**언제 문제가 되나**: 5만원 주문에 포인트 3천원을 썼고 그중 한 상품(2만원)만 환불하면, 포인트는 얼마를 돌려주나?

> **안분(pro-rata)** — 할인·포인트를 상품 금액 비율로 나눠 배분하는 계산.\
> 예: 반올림 1원 처리 규칙까지가 안분이다.

```text
안분: 할인·포인트를 상품 금액 비율로 나눠 붙이는 것
  2만원/5만원 = 40% → 포인트 3,000 × 0.4 = 1,200원 복원, 현금 18,800원 환불

함정: 반올림 — 3,333원을 3상품에 안분하면 1,111 + 1,111 + 1,111 = 3,333? 1원이 남거나 모자란다
  → 남는 1원을 어디에 붙일지(첫/마지막 상품) 규칙을 정하고,
  → 마지막 상품 환불 때 "지금까지 환불한 금액의 잔여"로 정산해 총합을 맞춘다
  → 금액은 부동소수 금지 (돈은 정수/decimal)
```

- 배송비는 환불되는가, 부분 환불이면?\
  — 전부 확정 질문 대상.\
  **실무 CS 문의가 가장 많은 지점이 D다.**

## 나머지 축 — 짧게

- **비동기 상태(E)**: PG가 5초 걸리면 동기 대기 불가 → "접수됨"과 "환불됨"이 다른 상태가 된다.\
  그 차이를 사용자에게 보여주고, 접수 후 실패를 알릴 경로를 정한다.
- **권한·검증(F)**: 요청자 = 주문 소유자?\
  환불 가능한 상태·기간(청약철회)?\
  이미 전액 환불?
- **상태 전이(G)**: 부분 환불 후 상태(`PARTIALLY_REFUNDED`?), 전액 판정 시점, 진행 중 또 오는 환불 요청.
- **알림(H)**: 알림은 되돌릴 수 없다 — **확정 후 맨 끝에.**\
  알림 실패가 환불을 롤백시키면 안 된다.
- **대사·에러 분류(I)**: "PG는 취소됐는데 우리는 결제완료"를 상시 탐지(Shopify의 드리프트 탐지).\
  에러를 retryable/non-retryable로 분류 — **분류를 틀리면 영구 실패 또는 중복 환불이다.**

> **대사(reconciliation)** — 우리 기록과 PG 기록을 맞춰보고 드리프트를 찾는 작업.\
> 예: 에러를 retryable / non-retryable 로 분류하는 것도 같은 축이다.

- **되묻기(J)**: 안분 규칙, 배송비, 환불 가능 기간, 부분 환불 시 쿠폰 처리, 그리고 "되돌릴 수 없다"를 보고 **확인 절차**를 물었는가.

## 실패 사례 — 이 항목들이 나온 실제 사고

- **Grab(A의 정본)**: 멱등키를 쓰는데도 이중 지급 — 핸들러 전체가 재큐잉되며 **1단계부터 다시 시작해 새 멱등키를 생성**했다.\
  해법: 단계(activity) 단위 재시도 + 키를 durable state에 보관.
- **Airbnb**: request-level 키와 entity-level 키 구분, 3단 원자 트랜잭션, master-only 멱등 데이터, 5XX/4XX 재시도 분류.
- **우아한형제들**: PG 승인됐는데 기록 없는 "고아 승인" — 실시간 조회로 1시간 내 자동 취소.\
  **환불은 방향이 반대다**: PG는 취소됐는데 DB는 결제완료인 상태를 탐지해야 한다.

> **고아 승인 / 고아 취소** — 외부(PG)에는 있는데 내 시스템에는 기록이 없는 상태.\
> 예: 대사로 탐지한다.

- **Twilio(2013)**: 외부 부수효과는 성공, 내부 기록은 실패하는 조합 → "잔액을 읽거나 쓸 수 없으면 청구하지 않는다"는 fail-safe.
- **올리브영**: read-modify-write 구조의 실사고 — 누적 상한 검사가 정확히 같은 형태다.
- **토스페이먼츠 / Uber**: 취소를 UPDATE가 아닌 INSERT-only 상쇄 엔트리로 — **환불은 원 결제를 지우는 게 아니라 반대 방향 엔트리를 더하는 것.**\
  Uber는 합이 0인 복식부기.

> **상쇄 엔트리 / INSERT-only 원장** — 수정 대신 반대 방향 금액의 새 줄을 추가하는 기록 방식.\
> 예: 불변이라 감사 가능하다.

- **Atlassian(2022)**: "permanently delete" 스크립트를 잘못된 ID 목록에 실행 → 23분 만에 883개 사이트 삭제, 복구 최대 14일.\
  "되돌릴 수 없다" 한 줄이 요구하는 것 = 확인 절차, dry-run, soft 처리, 복구 경로.

> **dry-run** — 실제로 실행하지 않고 무엇이 일어날지만 미리 보여주는 모드.\
> 예: 불가역 작업의 확인 절차다.

## 핵심 문장

- 앞의 다섯 문제가 전부 모인다 — 멱등(01·05) + 누적 상한(01의 lost update) + 여러 자원 잠금 순서(03) + 원장·추적(04) + 외부 통지(05), 그리고 **불가역**이 얹힌다.
- **`order_id`는 이번엔 멱등 키가 못 된다** — 부분 환불이 여러 번 정상이므로, 키는 클라이언트 생성 또는 결정적 entity 키로, **재시도 루프 밖에서 한 번만** 만든다.
- 멱등을 잡아도 끝이 아니다 — **부분 환불의 누적 상한은 별도 문제**고, 조회-합산-판단은 lost update다.
- 외부 호출은 트랜잭션 밖으로, 불가역은 뒤로 — **기록할 수 없으면 PG를 부르지도 마라.**
- 환불은 지우기가 아니라 **반대 방향 엔트리 추가**다 — 그래야 감사와 대사가 된다.

## 용어 풀이

- **불가역(irreversible)**: 한 번 실행하면 되돌릴 수 없는 것 — PG 취소, 알림 발송.\
  순서를 뒤로 미루고 확인 절차를 붙인다.
- **멱등성(idempotency)**: 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.
- **Idempotency-Key**: 클라이언트가 요청마다 만들어 보내는 멱등 키 헤더.\
  재시도에도 같은 키를 유지해야 의미가 있다.
- **entity-level 키**: "이 결제의 환불은 하나" 같은 도메인 규칙에서 결정적으로 만드는 키(예: payment-1234-refund).
- **누적 상한**: 부분 환불 합계 ≤ 원 결제액이라는 불변식.\
  조건부 UPDATE로 지킨다.
- **lost update**: 두 요청이 같은 값을 읽고 각자 계산해 써서 한쪽이 사라지는 버그.\
  조회-합산-판단의 함정.
- **조건부 UPDATE / affected rows**: 검사와 갱신을 DB 한 문장에 넣고 바뀐 행 수로 판정하는 기법.
- **ACID 단위**: 전부 성공 아니면 전부 취소로 묶이는 트랜잭션 덩어리.\
  멱등 기록과 실제 변경은 한 단위여야 한다.
- **PG(Payment Gateway)**: 카드사·은행과 결제·취소를 중계하는 외부 대행사.\
  느리고(800ms~5초), 취소는 불가역.
- **안분(pro-rata)**: 할인·포인트를 상품 금액 비율로 나눠 배분하는 계산.\
  반올림 1원 처리 규칙까지가 안분이다.
- **retryable / non-retryable**: 재시도하면 될 수 있는 실패(5xx류) / 재시도해도 소용없는 실패(4xx류).\
  분류를 틀리면 영구 실패 또는 중복 환불.
- **고아 승인/취소**: 외부(PG)에는 있는데 내 시스템에는 기록이 없는 상태.\
  대사로 탐지한다.
- **대사(reconciliation)**: 우리 기록과 PG 기록을 맞춰보고 드리프트를 찾는 작업.
- **상쇄 엔트리 / INSERT-only 원장**: 수정 대신 반대 방향 금액의 새 줄을 추가하는 기록 방식.\
  불변이라 감사 가능.
- **복식부기(double-entry)**: 모든 돈 움직임을 두 방향 엔트리로 적어 합이 0이 되게 하는 장부법.
- **sweeper(복구 배치)**: 반만 된 환불("PG 취소됨 + 내부 미복원")의 흔적을 찾아 이어서 처리하는 주기 작업.\
  복원이 멱등해야 안전하다.
- **dry-run**: 실제로 실행하지 않고 무엇이 일어날지만 미리 보여주는 모드.\
  불가역 작업의 확인 절차.
