### A. 문제 (REQUIREMENTS.md — 환불 처리 API)

#### 1. 지문 읽기 — 숨은 요구

- Q: "다시 눌렀더니 두 번 나갔다"는 무엇의 선언인가?
  A: **멱등성 요구**다 — 지문이 대놓고 유도하는 축(A).
  응답이 늦거나 유실되면 사람이든 클라이언트든 **반드시 다시 누른다**. 그것이 작년에 두 번 실사고가 된 회사다.
  CHECKLIST A 첫 항목: "지문의 '다시 눌렀더니 두 번 나갔다'를 요구사항으로 읽어냈는가."
  참고로 PG 가 간혹 5초 이상 걸린다는 줄이 이 재요청을 **상시 발생**시킨다 — 둘은 같은 이야기다.

- Q: 참고 네 줄이 심어놓은 축은?
  A: **"부분 환불이 가능합니다"** → B 누적 상한(그리고 A 의 "order_id 로는 부족" 문제).
  **"포인트와 쿠폰이 함께 적용되었을 수 있습니다"** → D 안분과 반올림.
  **"평균 800ms, 간혹 5초 이상"** → C 트랜잭션 경계 + E 비동기 상태.
  **"환불은 되돌릴 수 없습니다"** → C 불가역 순서 + J 확인 절차(dry-run·soft·복구 경로).
  네 줄이 전부 요구사항이지 배경 설명이 아니다.

- Q: 가장 어려운 이유는?
  A: **앞의 다섯 문제 요소가 전부 모이고, 여기에 불가역성이 더해지기 때문**이다(CHECKLIST 서두 원문).
  다른 문제는 실수하면 되돌릴 수 있지만 여기서는 **PG 취소와 알림 발송이 되돌아가지 않는다** — 설계 실수가 곧 확정 손실이다.
  그래서 6개 중 **마지막에 푸는 것을 권한다**고 지문이 적어뒀다.

- Q: 앞의 다섯이 들어오는 자리는?
  A: **01 포인트** → 포인트 복원 + 안분, 그리고 누적 상한의 lost update 구조.
  **02 쿠폰** → 쿠폰 복원(그리고 "성공 응답의 의미").
  **03 재고** → 재고 복원 + **여러 자원 잠금 순서**(데드락).
  **04 정산** → 원장·추적 가능성(대사).
  **05 웹훅** → PG 취소 결과 통지·재시도·멱등 응답 계약.
  + 이 문제 고유: **불가역**(PG 취소·알림).

- Q: 공통 질문 3개를 돌리면?
  A: Q1 공유 자원 → **환불 가능 잔액(누적 상한)** + 포인트·쿠폰·재고.
  Q2 동시에 두 번 → **이중 환불**(같은 요청 재전송) / **상한 초과**(두 상담원이 서로 다른 부분 환불을 동시에).
  Q3 중간에 끊기면 → **PG 는 취소됐는데 우리 DB 는 결제완료** — 돈은 나갔는데 기록이 없다. 찾아낼 수 있는가가 요구사항이다.

#### 2. 멱등성 (A — 중요, 지문이 대놓고 유도)

- Q: order_id 만으로 안 되는 이유는?
  A: **부분 환불이라 같은 주문에 환불이 여러 번 정상적으로 일어나기** 때문이다.
  order_id 를 키로 삼으면 **두 번째 정상 부분 환불까지 막힌다** — 멱등이 아니라 기능 고장이다.
  03번(주문당 차감 1회)에서는 order_id 가 자연 멱등 키였는데 여기서는 아니다 — **도메인 규칙이 키를 정한다**는 것이 요점이다.

- Q: 키의 출처 선택지 둘은?
  A: ① **클라이언트가 `Idempotency-Key` 헤더를 생성해 보낸다** — 재시도에도 같은 키를 유지해야 의미가 있다.
  ② **결정적 entity-level 키** — "이 결제에 대한 환불은 하나"인 경우 `payment-1234-refund` 같은 키(Airbnb).
  Airbnb 는 request-level 키와 entity-level 키를 구분하고, 환불 같은 경우엔 **결정적 entity 키가 랜덤 UUID 보다 나을 수 있다**고 본다.
  자연 키를 만든다면 `order_item_id` + 수량, 혹은 환불 요청 ID 가 후보다(CHECKLIST A).

- Q: 재시도 루프 안에서 키를 만들면?
  A: **재시도마다 새 키가 되어 멱등이 무의미**해진다.
  Grab 이 정확히 이 사고다: 핸들러가 (1) 멱등키 생성 (2) 혜택1 (3) 혜택2 를 한 덩어리로 처리했는데 3에서 실패하면 핸들러 전체가 SQS 로 재큐잉되어 **1단계부터 다시 돌며 새 멱등키를 생성**했다 → 혜택1 이중 지급.
  원문: "This generates a new idempotency key, meaning the Reward system wouldn't recognize the retry and will award Benefits1 twice."
  규칙: **멱등키는 재시도 바깥에서 한 번만** 만들어지고 durable state 에 보관된다.

- Q: 같은 키 + 다른 금액이면?
  A: **거부한다** — 같은 키는 같은 요청이어야 한다는 계약이기 때문이다.
  토스페이먼츠는 **422**(body 가 다르면), GoCardless 는 **409 + conflicting_resource_id**, AWS 는 validation error 로 답한다.
  Stripe 는 파라미터가 검증에 실패하거나 동시 실행 중인 요청과 충돌하면 **멱등 결과를 저장하지 않는다** — 그래서 재시도가 가능하다.
  어느 쪽이든 **말없이 첫 요청을 재실행하거나 새 금액으로 처리하면 안 된다.**

- Q: 진행 중인 같은 키는?
  A: **409**(진행 중)로 답하는 것이 일반적이다(토스페이먼츠).
  동시에 두 번 실행되지 않게 **row-level lease 락**으로 막는다(Airbnb Orpheus).
  "기다렸다가 같은 응답을 준다"는 선택도 있지만 PG 가 5초까지 걸리는 이 도메인에서는 클라이언트 타임아웃을 부른다. (원본에 근거 없음 — 내 추론)

- Q: 실패 응답 재생인가 재시도인가?
  A: **회사마다 정반대다.** Stripe 는 첫 응답을 **500 포함 그대로 재생**하고(24시간 후 pruning), GoCardless 는 재생하지 않고 **409 + conflicting_resource_id** 를 준다.
  AWS 는 **의미적으로 동등한 응답**을 요구한다.
  중요한 것은 **어느 쪽을 고르든 문서로 고정하는 것** — "어느 쪽을 고르느냐가 프론트엔드의 복잡도를 결정한다."
  단, 동시 충돌로 저장하지 않은 건은 재시도가 가능해야 한다(Stripe 조항).

- Q: 하나의 ACID 단위여야 하는 이유는?
  A: 따로 커밋하면 **"키만 기록되고 환불은 실패"** 한 상태가 생기고, 그러면 **재시도가 와도 '이미 처리됨'으로 걸러져 영구 미처리**가 된다.
  반대로 환불만 되고 키 기록이 실패하면 **재시도가 두 번째 환불**을 만든다.
  AWS 조항 원문: 토큰 기록과 자원 생성이 **반드시 하나의 ACID 단위**여야 한다.

- Q: 보관 기간이 지난 뒤 늦은 재시도는?
  A: **새 요청으로 처리되어 중복 환불이 된다** — 그래서 보관 기간을 **재시도가 올 수 있는 기간보다 길게** 잡아야 한다.
  AWS 의 기준: **자원 수명 + 유예기간** — 자원이 삭제된 뒤 늦게 온 재시도까지 계약을 지키려면 그만큼 필요하다.
  토스페이먼츠는 반대로 "기간이 지나면 새 요청"이라고 명시한다 — 즉 **기간 자체가 계약의 일부**다.

- Q: replica 에서 읽으면?
  A: **복제 지연(replica lag) 때문에 이미 완료된 건이 미실행으로 보여 재실행을 유발한다.**
  그래서 Airbnb 는 **멱등성 데이터는 오직 master DB 에서만** 읽고 쓴다.
  읽기 부하를 줄이려 replica 를 쓰는 습관이 그대로 이중 환불이 되는 자리다.

#### 3. 부분 환불의 누적 상한 (B — 중요, 놓치기 쉽다)

- Q: 총 환불액 ≤ 원 결제액을 누가 보장하는가?
  A: 앱의 사전 검사가 아니라 **DB 의 조건부 UPDATE(또는 제약)** 다.
  불변식을 **쓰기와 같은 문장 안**에 넣어야 동시 요청 사이로 빠져나가지 못한다.
  01번에서 쓴 무기가 그대로 재등장한다.

- Q: 조회-합산-판단이 왜 틀렸고 이름은?
  A: **lost update** 다 — 두 요청이 **같은 값을 읽고** 각자 더해 쓰면 한쪽이 사라지고 상한을 넘는다.
  올리브영 선착순 쿠폰 사고가 정확히 이 **read-modify-write** 구조이고, "누적 상한 검사가 정확히 같은 형태"다.
  CHECKLIST B 원문: "'지금까지 환불한 금액을 조회해서 더해보고 판단'하면 lost update 다."

- Q: 조건부 UPDATE 문장과 판정은?
  A:
  ```sql
  UPDATE orders
     SET refunded_amount = refunded_amount + :이번_환불액
   WHERE order_id = :id
     AND refunded_amount + :이번_환불액 <= paid_amount;
  ```
  **affected rows 가 0 이면 상한 초과**로 거부한다 — 별도 SELECT 없이 검사와 갱신이 한 문장이다.

- Q: order_item_id 의 수량 합은?
  A: 같은 방식이다 — 아이템별 `refunded_quantity + :수량 <= ordered_quantity` 를 WHERE 에 넣는다.
  금액 상한만 막고 수량 상한을 안 막으면 **같은 상품을 주문 수량보다 많이 환불**할 수 있다.

- Q: 두 상담원이 동시에 부분 환불하면?
  A: 둘 다 "아직 여유가 있다"고 읽고 각자 처리해 **합이 결제액을 넘는다**(과다 환불).
  조건부 UPDATE 면 **한쪽만 성립하고 다른 쪽은 affected rows 0 으로 거부**된다.
  멱등성으로는 이걸 못 막는다 — **서로 다른 정상 요청**이기 때문이다.

- Q: 멱등성을 잡았는데도 남는 이유는?
  A: 멱등성은 **같은 요청의 중복**을 막고, 누적 상한은 **서로 다른 정상 요청들의 합**을 막는다 — 다른 문제다.
  CHECKLIST 자가 채점 원문: "멱등성(A)을 잡고 나면 다 됐다고 느끼는데, **부분 환불이 여러 번 정상적으로 일어나는 도메인에서는 누적 상한이 별도 문제로 남습니다.** 그리고 그건 01번의 lost update 와 정확히 같은 구조입니다."
  그래서 **B 를 놓치기 쉽다** — A+C 는 "좋습니다", A+B+C 가 "상위권"이다.

#### 4. 여러 자원의 동시 복원과 불가역의 순서 (C — 중요)

- Q: 넷이 "모두 성공하거나 모두 실패"할 수 있는가?
  A: **없다.** PG 는 외부 시스템이라 우리 DB 트랜잭션에 들어오지 않고, **PG 취소는 되돌릴 수도 없다.**
  그러므로 목표를 바꿔야 한다: 원자성 대신 **"반만 된 상태를 반드시 탐지·복구할 수 있게"** 만드는 것.
  부분 실패는 "탐지 가능한가"가 요구사항이다(Slack scan/detect/repair).

- Q: PG 를 먼저인가 나중인가?
  A: **내부 기록을 먼저, PG 를 나중에.**
  근거는 **되돌릴 수 없는 것을 뒤로 미룬다** 는 원칙과, Twilio 의 fail-safe다.
  PG 를 먼저 부르면 내부 기록에 실패했을 때 **돈은 나갔는데 아무 흔적이 없다** — 되돌릴 방법이 없다.
  반대로 내부 의도 기록이 먼저면 최악의 경우도 "기록은 있는데 PG 를 못 불렀다"이고, 이건 재시도로 수렴한다.

- Q: 외부 호출을 트랜잭션 안에 넣으면?
  A: **잠금을 800ms~5초 동안 들고 있게 된다** — 같은 주문·상품·포인트 행을 기다리는 다른 요청이 전부 막히고, 커넥션 풀이 마른다.
  더 나쁜 경우: **PG 성공 후 COMMIT 실패** — 돈은 나갔는데 기록이 없고, PG 취소는 되돌릴 수 없다.
  규칙: **RPC 구간에서는 DB 작업을 하지 않는다**(Airbnb Orpheus 의 RPC 단계 규칙).

- Q: PG 성공 + 포인트 복원 실패면?
  A: **"고객 돈은 돌려줬는데 포인트는 안 돌아온"** 상태가 남는다 — 고객이 손해를 본 채 조용히 방치된다.
  찾아내려면 **1단계(의도)와 2단계(PG 결과) 기록이 남아 있어야** 한다 — 그 흔적으로 복구 배치(sweeper)가 이어서 처리한다.
  흔적이 없으면 그 상태는 존재 자체를 알 수 없다.
  우아한형제들의 고아 승인과 같은 자리인데 **방향이 반대**다: 여기서는 **PG 는 취소됐는데 우리 DB 는 아직 결제완료**인 것을 탐지해야 한다.

- Q: 권장 흐름 3단계는?
  A:
  ```text
  1) 내부 트랜잭션: 환불 의도 기록(멱등키) + 누적 상한 차감      → COMMIT
  2) PG 취소 호출                                                (트랜잭션 밖)
  3) 내부 트랜잭션: PG 결과 기록 + 포인트·쿠폰·재고 복원(잠금 고정 순서) → COMMIT
     3)이 실패해도 1)·2)의 기록이 남아 복구 배치가 이어받는다
  ```
  Airbnb Orpheus 의 3단 구조 그대로다: **Pre-RPC(의도 기록) / RPC(DB 작업 금지) / Post-RPC(결과 기록)**, 각각 원자 트랜잭션.

- Q: 잠글 때 정해야 할 것과 안 정하면?
  A: **잠금 순서**다 — 안 정하면 **데드락**이 난다(두 요청이 포인트·재고를 서로 반대 순서로 잡으면 순환 대기).
  Mercari 해법: **"id 같은 절대값으로 sort"** 해서 모든 경로가 같은 순서로 잡게 한다.
  03번의 데드락 축이 여기서 자원 종류를 바꿔 재등장한다.

- Q: 복원이 멱등해야 하는 이유는?
  A: **복구 배치가 여러 번 돌기 때문**이다 — 실패 지점이 불확실하므로 sweeper 는 같은 건을 재시도할 수밖에 없다.
  포인트 복원이 멱등하지 않으면 재시도마다 포인트가 늘어난다(03번 복원 중복과 같은 구조).
  방법: 복원도 환불 건 id 를 키로 "이미 복원됨" 상태 전이로 만든다.

- Q: Twilio 의 fail-safe 를 환불로 번역하면?
  A: **"포인트/재고 복원을 기록할 수 없으면 PG 취소를 부르지 않는다."**
  Twilio 원문은 "잔액을 읽거나 쓸 수 없으면 카드를 청구하지도, 계정을 정지하지도 않는다" — 외부 부수효과는 성공하는데 내부 상태 쓰기가 실패하는 조합을 막는 규칙이다.
  한 줄 요약: **기록할 수 없으면 되돌릴 수 없는 일을 시작하지 마라.**

#### 5. 금액 계산 — 안분과 반올림 (D)

- Q: 5만원에 포인트 3천원, 2만원짜리 하나만 환불하면?
  A: 상품 금액 비율로 안분한다 — 2만/5만 = **40%** → 포인트 **3,000 × 0.4 = 1,200원** 복원, 현금 환불은 **18,800원**.
  포인트를 안 빼고 2만원을 다 현금으로 주면 **고객이 포인트만큼 이득**을 보고 그 차액은 회사 손실이다.
  반대로 포인트를 안 돌려주면 고객이 손해다 — 어느 쪽이든 CS 문의가 된다.

- Q: 반올림으로 1원이 남거나 모자라면?
  A: **어디로 갈지 규칙을 정해둬야 한다**(첫 상품에 몰아주기 / 마지막 상품에 몰아주기 / 큰 금액부터 등).
  예: 3,333원을 3상품에 안분하면 1,111 × 3 = 3,333 이지만 3,334 였다면 1원이 떠돈다.
  규칙이 없으면 구현자마다 달라지고 합계가 안 맞는다 — 되묻기(J) 대상이다.

- Q: 마지막 상품 환불 때 앞서 버린 1원들은?
  A: **"지금까지 환불한 금액의 잔여"로 정산**해 총합을 맞춘다 — 마지막 건은 비율 계산이 아니라 **남은 전부**를 준다.
  그래야 전액 환불했을 때 합계가 원 결제액과 정확히 일치한다.
  CHECKLIST D 원문: "마지막 상품을 환불할 때 앞서 버린 1원들이 정산되는가."

- Q: 배송비는?
  A: **정책 질문이다** — 지문에 없다. 보통 전액 환불이면 배송비까지, 부분 환불이면 배송비는 유지(또는 반품 사유에 따라 다름)지만 **회사 정책으로 확정받아야 한다.**
  (원본에 근거 없음 — 내 추론. CHECKLIST 는 "배송비는 환불되는가. 부분 환불이면?"이라고 묻기만 한다.)

- Q: 부동소수를 쓰면 안 되는 이유는?
  A: **0.1 같은 값이 이진 부동소수로 정확히 표현되지 않아** 더할수록 오차가 쌓이고, 안분·합계가 1원씩 어긋난다.
  돈은 **정수(최소 단위)나 decimal** 로 다룬다.
  대사(I)에서 "왜 1원이 안 맞나"를 쫓게 되는 원인이 대개 이것이다. (원본은 "금액을 부동소수로 다루지 않는가" 항목만 둔다 — 이유 설명은 내 보충)

- Q: 이 축이 실무에서 중요한 이유는?
  A: **CS 문의가 가장 많이 나오는 지점**이기 때문이다(CHECKLIST D 주석).
  그런데 지문에는 **"포인트와 쿠폰이 함께 적용되었을 수 있습니다" 한 줄로만 암시**돼 있다 — 읽어내지 못하면 통째로 빠진다.
  자가 채점에서 A+B+C **+ D 의 안분**이면 "실무 경험이 있다는 뜻, 이 문제로는 더 잴 게 없다".

#### 6. 응답 시간·권한·상태 전이·알림·대사 (E, F, G, H, I)

- Q: 동기로 기다리면, 비동기로 바꾸면?
  A: 동기면 PG 가 5초 걸릴 때 **클라이언트 타임아웃**이 난다 — 그리고 그 타임아웃이 재요청을 부른다(A 로 되돌아온다).
  비동기로 바꾸면 **"접수했다"와 "환불됐다"가 서로 다른 상태**가 된다 — 상태 모델과 UI 가 그 차이를 표현해야 한다.
  사용자에게는 "환불 접수됨 → 처리 중 → 환불 완료"로 보여주고, 완료 시점을 알림/조회로 확인하게 한다.

- Q: 접수만 하고 실패하면 누가 알려주는가?
  A: **우리가 알려야 한다** — 접수 응답을 준 순간 책임이 우리에게 넘어왔기 때문이다.
  경로를 정해둬야 한다: 실패 상태로 전이 + 고객 알림 + 재시도/수동 처리 큐(CS 어드민).
  정하지 않으면 "접수됐다"는 화면만 남고 아무 일도 안 일어난다.

- Q: 검증해야 할 것 넷은?
  A: ① **요청자가 주문 소유자인가**(고객이 직접 신청하게 되므로 새로 생긴 축) ② **환불 가능한 주문 상태인가**(배송 완료 전/후? 구매확정 후?) ③ **청약철회 기간을 넘었는가** ④ **이미 전액 환불된 주문인가**.

- Q: 부분 환불 후 상태와 전액 판정은?
  A: **`PARTIALLY_REFUNDED` 같은 상태가 필요한가**를 정해야 한다 — 없으면 "환불됨/안 됨" 이분법이라 부분 환불을 표현하지 못한다.
  전액 판정은 **누적 환불액 == 결제액**(또는 모든 아이템의 환불 수량 == 주문 수량)으로 — B 의 누적 컬럼이 그대로 판정 근거가 된다.
  그리고 **환불 진행 중에 다른 환불 요청이 오면** 어떻게 할지(거부/대기/허용)도 정해야 한다.

- Q: 알림은 언제, 실패하면?
  A: **되돌릴 수 없으므로 확정 후 가장 마지막**에 보낸다 — 환불이 실패했는데 알림이 먼저 나가면 회수할 방법이 없다.
  **알림 발송 실패가 환불 전체를 롤백시켜서는 안 된다** — 돈은 이미 돌아갔고 PG 취소는 못 되돌린다. 알림은 재시도 대상이지 롤백 사유가 아니다.
  구조적으로는 07번 아웃박스처럼 **이벤트를 기록해두고 따로 발송**하는 것이 맞다. (마지막 문장은 내 추론 — 원본 CHECKLIST 는 "어디에 두는가"까지만 묻는다)

- Q: "PG 는 취소됐는데 DB 는 결제완료"를 어떻게 탐지하나?
  A: **대사(reconciliation)** — PG 기록과 우리 기록을 주기적으로 맞춰보고 드리프트를 찾는다.
  Shopify 의 `MismatchCaptureStatusAnomaly` 가 그것 — **로컬 상태가 파트너 상태와 드리프트하는 것을 상시 탐지**한다.
  Slack 은 이것을 **scan/detect/repair** 프레임워크로 일반화했다 — 부분 실패는 "탐지 가능한가"가 요구사항이다.

- Q: 에러 분류를 틀리면?
  A: **retryable 을 non-retryable 로 분류하면 영구 실패**(고칠 수 있었던 건을 버린다), **non-retryable 을 retryable 로 분류하면 중복 환불**(같은 취소를 계속 재시도한다).
  Airbnb 의 규칙: **5XX = retryable, 4XX = non-retryable** 로 분류한다.
  CHECKLIST I 원문: "분류를 틀리면 영구 실패 또는 중복 환불이다."

- Q: 재시도해도 안 되는 건은?
  A: **사람이 보는 곳으로 보낸다** — DLQ/수동 처리 큐 + 알림.
  조용히 버리면 고객 돈이 묶인 채 사라지고, 무한 재시도하면 PG 를 때린다.

#### 7. 되묻기 (J)

- Q: 무엇을 되물어야 하는가?
  A: ① **안분 규칙**(포인트·쿠폰을 어떻게 나누고 1원은 어디로) ② **배송비 정책**(전액/부분) ③ **환불 가능 기간**(청약철회·구매확정 후) ④ **부분 환불 시 쿠폰 처리**(쪼갤 수 있나, 되살릴 수 있나).
  지문 구현 조건에 **"명시되지 않은 정책은 질문하며 진행해 주세요"** 라고 적혀 있다 — 되묻기는 선택이 아니라 지시다.

- Q: "되돌릴 수 없습니다"를 보고 물어야 할 것은?
  A: **확인 절차**다 — CHECKLIST J 원문: "'환불은 되돌릴 수 없습니다'를 보고 확인 절차를 물었는가."
  Atlassian 2022 사고가 그 값을 보여준다: "permanently delete" 모드를 잘못된 ID 목록에 실행해 **23분 만에 883개 사이트(고객 775곳) 삭제, 복구에 최대 14일.**
  요구되는 것: **확인 절차 · dry-run · soft 처리 · 복구 경로**(그리고 Atlassian 의 해법은 전면 soft delete + 다층 보호였다).

### B. 개념

#### 8. 문제를 여는 질문 세 개 (원본 README 이관)

- Q: Q1. 여기서 바뀌는 공유 자원이 무엇인가?
  A: **환불 가능 잔액**(= 결제액 − 누적 환불액)이 1차 자원이고, 거기에 **포인트 잔액·쿠폰·재고**가 따라온다.
  자원이 **여럿이고 그중 하나(PG)는 우리 DB 밖**이라는 것이 이 문제의 정체성이다 — 그래서 트랜잭션 하나로 안 묶인다.

- Q: Q2. 이게 정확히 동시에 두 번 오면?
  A: **같은 요청이 두 번** → 이중 환불(A: 멱등키 + 하나의 ACID 단위).
  **다른 부분 환불이 두 번** → 상한 초과(B: 조건부 UPDATE).
  **여러 자원을 서로 반대 순서로 잠그면** → 데드락(C: 잠금 순서 고정).
  세 가지가 전부 "동시에 두 번"에서 나온다.

- Q: Q3. 중간에 끊기면 어디까지 남는가?
  A: 1)만 커밋 → **의도 기록만 있고 PG 미호출** — 재시도로 수렴(안전한 실패).
  2)까지 → **PG 취소됨 + 내부 미복원** — 기록이 있으니 sweeper 가 이어받는다.
  아무 기록 없이 PG 만 성공 → **탐지 불가**. 그래서 **의도를 먼저 기록**하는 순서가 전부다.

#### 9. 파생 — 왜 / 예측 / 경계 / 연결

- Q: Grab 은 왜 이중 지급이 났고 해법은?
  A: 원인은 **재시도 단위가 "핸들러 전체"** 였던 것 — 3단계 실패 시 핸들러가 통째로 재큐잉되며 1단계(멱등키 생성)부터 다시 돌아 **새 키를 만들었다.**
  해법: **Temporal 워크플로로 전환해 activity(단계) 단위로 재시도**하고 멱등키를 **durable state** 에 보관.
  원문: "If the 'AssignBenefits2' step fails ... it will restart directly from that step, thus preventing the double awarding."
  환불처럼 **여러 외부 호출이 이어지는 흐름에서 특히 위험하다** — 이 문제의 정본 사례다.

- Q: request-level 키와 entity-level 키의 차이, 환불에는?
  A: **request-level** = 요청마다 클라이언트가 만드는 키(보통 랜덤 UUID) — 재시도에 같은 키를 유지해야 의미가 있다.
  **entity-level** = 도메인 사실에서 결정적으로 유도하는 키(`payment-1234-refund`).
  환불처럼 **"이 결제에 대한 환불은 하나"** 인 경우에는 **결정적 entity 키가 랜덤 UUID 보다 나을 수 있다**(Airbnb) — 클라이언트가 키를 잃어버려도 같은 키가 재생되기 때문이다.
  단 이 문제는 **부분 환불**이라 entity 키의 단위를 결제 단위가 아니라 "환불 건" 단위로 잡아야 한다.

- Q: Orpheus 3단 구조는?
  A: **Pre-RPC** — 의도를 기록한다(멱등키·요청 내용). **RPC** — 외부 호출만 한다, **DB 작업 금지**. **Post-RPC** — 결과를 기록한다.
  **각각이 원자 트랜잭션**이고, 동시 중복은 **row-level lease 락**으로 막으며, 멱등성 데이터는 **master DB 에서만** 읽고 쓴다.
  이 구조의 효능: 어느 단계에서 끊겨도 **다음 시도가 어디서부터 이어야 할지 기록으로 알 수 있다.**

- Q: Stripe 와 GoCardless 가 정반대인 이유와 그 선택이 결정하는 것은?
  A: Stripe 는 **첫 응답을 500 포함 그대로 재생**한다 — 클라이언트는 재시도해도 "처음 본 그 답"을 받으므로 분기가 단순하다.
  GoCardless 는 재생하지 않고 **409 + conflicting_resource_id** 를 준다 — 클라이언트가 그 id 로 조회해 상태를 확인해야 한다.
  **어느 쪽을 고르느냐가 프론트엔드의 복잡도를 결정한다** — 정답이 있는 게 아니라 **고르고 문서화하는 것**이 설계다.

- Q: 우아한형제들의 고아 승인과 방향 차이는?
  A: 우아한형제들: **PG 에서는 승인이 났는데 시스템에는 기록이 없는** 상태 — "실제로 돈이 출금되는 경우도 발생합니다". 해법은 실시간 조회로 **1시간 이내 자동 취소**.
  환불: **방향이 반대다** — **PG 는 취소됐는데 우리 DB 는 아직 결제완료**인 상태를 탐지해야 한다.
  공통점은 "외부와 내부가 어긋난 채 조용히 남는다"이고, 답도 같다 — **상시 대사.**

- Q: 토스페이먼츠·Uber 의 원장 교훈을 한 문장으로?
  A: **환불은 원 결제를 지우는 게 아니라 반대 방향 엔트리를 더하는 것이다.**
  토스페이먼츠는 취소를 UPDATE 로 처리하던 것을 **INSERT-only 원칙으로 변경**해 불변성을 보장하고 데드락도 방지했다.
  Uber 는 **immutable Money Order** 와 **모든 엔트리 합이 0인 복식부기**.
  **금액 수정은 UPDATE 가 아니라 상쇄 엔트리 추가여야 감사가 된다** — 01번·04번의 원장이 여기서 완성된다.

- Q: Atlassian 사고가 요구하는 것 넷은?
  A: **확인 절차 · dry-run · soft 처리 · 복구 경로.**
  사고: 유지보수 스크립트를 "permanently delete" 모드로 잘못된 ID 목록에 실행 → **23분 만에 883개 사이트(고객 775곳) 삭제, 복구 최대 14일.** 삭제 API 가 site ID 와 app ID 를 **구분 없이 받았고 검증이 없었다.**
