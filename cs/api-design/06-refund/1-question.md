### A. 문제 (REQUIREMENTS.md — 환불 처리 API)

```text
POST /orders/{order_id}/refunds

{ "items": [ { "order_item_id": 5001, "quantity": 1 } ],
  "reason": "CHANGE_OF_MIND" }

배경
  지금은 CS 상담원이 어드민에서 환불 버튼을 눌러 처리합니다.
  고객이 앱에서 직접 환불을 신청할 수 있게 API 를 만듭니다.
  상담원 어드민에서 "환불 버튼을 눌렀는데 응답이 없어서 다시 눌렀더니 두 번 나갔다"는
  사고가 작년에 두 번 있었습니다.

기대 동작
  1. 요청한 상품에 대해 환불 금액을 계산합니다.
  2. PG 사에 결제 취소를 요청합니다.
  3. 사용했던 포인트와 쿠폰을 되돌립니다.
  4. 재고를 복원합니다.
  5. 주문 상태를 갱신합니다.
  6. 고객에게 환불 완료 알림을 보냅니다.

참고
  - 부분 환불이 가능합니다. 한 주문의 일부 상품만 환불할 수 있습니다.
  - 주문에 포인트와 쿠폰이 함께 적용되었을 수 있습니다.
  - PG 사 API 는 평균 800ms, 간혹 5초 이상 걸립니다.
  - 환불은 되돌릴 수 없습니다.

구현 조건
  - 실제 DB 가 없더라도, 있다고 가정했을 때의 트랜잭션 경계를 코드나 주석으로 표현해 주세요.
  - 명시되지 않은 정책은 질문하며 진행해 주세요.
```

#### 1. 지문 읽기 — 숨은 요구

- 배경의 "다시 눌렀더니 두 번 나갔다"는 무엇을 요구사항으로 선언한 것인가?
- 참고 네 줄(부분 환불 / 포인트·쿠폰 / PG 800ms~5초 / 되돌릴 수 없음)은 각각 어떤 축을 심어놓았는가?
- 이 문제가 "6개 중 가장 어렵다"고 하는 이유는 무엇인가?
- 앞의 다섯 문제가 각각 이 문제의 어디로 들어오는가?
- 공통 질문 3개를 이 지문에 돌리면 각각 무엇이 나오는가?

#### 2. 멱등성 (A — 중요, 지문이 대놓고 유도)

- `order_id` 만으로 멱등 키를 삼으면 안 되는 이유는 무엇인가?
- 그럼 키의 출처로 가능한 선택지 둘은 무엇인가?
- 멱등키를 재시도 루프 안에서 만들면 무슨 일이 벌어지는가?
- 같은 키에 다른 금액이 오면 어떻게 응답하는가?
- 진행 중인 요청과 같은 키가 또 오면?
- 재시도가 원래 실패 응답을 그대로 받아야 하는가, 새로 시도해야 하는가?
- 멱등 기록과 실제 환불이 하나의 ACID 단위여야 하는 이유는 무엇인가?
- 멱등키 보관 기간이 지난 뒤 늦게 온 재시도는 어떻게 되는가?
- 멱등 데이터를 replica 에서 읽으면 무슨 일이 생기는가?

#### 3. 부분 환불의 누적 상한 (B — 중요, 놓치기 쉽다)

- 총 환불액이 원 결제액을 넘지 않음을 누가 보장하는가?
- "지금까지 환불한 금액을 조회해서 더해보고 판단"은 왜 틀렸고, 그 버그의 이름은 무엇인가?
- 조건부 UPDATE 로 쓰면 어떤 문장이 되고, 무엇으로 거부를 판정하는가?
- 같은 `order_item_id` 의 수량 합은 무엇으로 막는가?
- 두 상담원이 동시에 같은 주문을 부분 환불하면 무슨 일이 일어나는가?
- 멱등성(A)을 잡았는데도 이 문제가 별도로 남는 이유는 무엇인가?

#### 4. 여러 자원의 동시 복원과 불가역의 순서 (C — 중요)

- PG 취소·포인트·쿠폰·재고 복원이 "모두 성공하거나 모두 실패"할 수 있는가?
- PG 를 먼저 부를 것인가 나중에 부를 것인가 — 그 근거는?
- 외부 호출(800ms~5초)을 DB 트랜잭션 안에 넣으면 무슨 일이 벌어지는가?
- PG 취소는 성공했는데 포인트 복원이 실패하면 무엇이 남고, 그것을 찾아낼 수 있는가?
- 권장 흐름을 3단계로 나눠 쓰면 어떻게 되는가?
- 포인트·쿠폰·재고를 잠글 때 무엇을 정해야 하고, 안 정하면 무엇이 나는가?
- 복원 각각이 멱등해야 하는 이유는 무엇인가?
- Twilio 의 fail-safe 를 환불 문장으로 번역하면 무엇인가?

#### 5. 금액 계산 — 안분과 반올림 (D — 지문에 한 줄로만 암시)

- 5만원 주문에 포인트 3천원을 썼고 2만원짜리 한 상품만 환불하면 포인트는 얼마인가?
- 안분 결과의 반올림으로 1원이 남거나 모자라면 어디로 가는가?
- 마지막 상품을 환불할 때 앞서 버린 1원들은 어떻게 정산되는가?
- 배송비는 환불되는가, 부분 환불이면?
- 금액을 부동소수로 다루면 안 되는 이유는 무엇인가?
- 이 축이 실무에서 중요한 이유는 무엇인가?

#### 6. 응답 시간·권한·상태 전이·알림·대사 (E, F, G, H, I)

- PG 가 5초 걸리는데 동기로 기다리면 무엇이 나고, 비동기로 바꾸면 무엇이 새로 생기는가?
- 접수만 하고 실패하면 누가 알려주는가?
- 환불 요청에서 검증해야 할 것 넷은 무엇인가?
- 부분 환불 후 주문 상태는 무엇이 되고, 전액 시점은 어떻게 판정하는가?
- 알림은 어느 시점에 보내야 하고, 알림 실패가 환불을 롤백시켜야 하는가?
- "PG 는 취소됐는데 우리 DB 는 아직 결제완료"인 상태를 어떻게 탐지하는가?
- 에러를 retryable / non-retryable 로 분류하는데, 분류를 틀리면 각각 무엇이 되는가?
- 재시도해도 안 되는 건은 어디로 가는가?
