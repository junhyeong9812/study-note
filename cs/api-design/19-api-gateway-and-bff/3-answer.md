# api-design/19-api-gateway-and-bff — 정답

## 정답

### 1. 직접 호출의 문제와 게이트웨이의 일

- 문제
  - 클라이언트가 서비스 주소·분할 구조를 안다. 서비스를 쪼개거나 합치면 앱을 다시 배포해야 한다.
  - 지연이 큰 망에서 왕복이 여러 번이다.
  - 인증·TLS 인증서·속도 제한을 서비스마다 중복 구현한다.
- 게이트웨이의 일: **라우팅**(알맞은 서비스로), **집계**(여러 서비스 결과를 하나로), **오프로딩**(TLS 종료·인증·속도 제한·로깅).

### 2. 다섯 패턴

```text
  클라 ─TLS─> [ 오프로딩 | 라우팅 | 집계 ] ─> 서비스들
  공개 파사드(게이트키퍼: 검증·정제만, 자격 증명 없음) ─> 신뢰 호스트 ─> 저장소
  클라 ─(발렛 키 토큰)─────────────────────────────> 저장소 직접
```

| 패턴 | 해결하는 것 |
|---|---|
| Routing | 엔드포인트 하나로 여러 서비스·버전에 L7 라우팅, 클라는 분할 구조를 모름 |
| Aggregation | 요청 하나를 여러 백엔드로 나눠 모아 왕복 감소 |
| Offloading | TLS·인증·스로틀링 같은 공통 관심사 중복 제거 |
| Gatekeeper | 공개 쪽을 낮은 권한의 검증 전용으로 분리, 뚫려도 데이터·자격 증명에 못 닿음 |
| Valet Key | 범위·기간 제한 토큰으로 클라가 저장소에 직접 전송, 앱 서버 중계 제거 |

- Azure 카탈로그에서 "Gateway" 패턴은 위 셋이고, Gatekeeper·Valet Key는 보안 쪽 별개 패턴이다(함께 보는 이웃 패턴).

### 3. 최장 접두사

- `/api/orders/3`은 두 접두사에 다 일치하지만 더 긴 `/api/orders/`가 선택된다. 실험에서도 `/api/orders/*`는 백엔드 `/orders/`로 갔다.
- nginx는 접두사 location 중 **가장 긴 일치**를 고르므로 설정 순서를 바꿔도 결과는 같다(사실 점검에서 두 `location`의 순서를 바꿔 다시 돌려도 출력이 같았다). 순서가 의미 있는 것은 정규식 location이다(설정에 나온 순서대로 검사, 첫 일치에서 멈춤).

### 4. `limit_req` 결과

- 실험 출력: `200 200 200 429 429 429`. 초당 1건의 기본 몫 1건 + `burst=2`를 `nodelay`로 즉시 처리해 3건 통과, 나머지 3건은 `limit_req_status`로 정한 429. 거절된 요청은 백엔드에 닿지 않았다.
- nginx 문서: **키 값이 빈 요청은 세지 않는다**. 키 헤더가 없는 요청은 제한을 받지 않고 통과한다 — 그래서 실험에서는 `if`로 키 없는 요청을 401로 먼저 끊었다. 기본 거절 상태는 503이다.

### 5. 집계 응답 시간

```text
A 순차, 타임아웃 없음     :  3159 ms
B 병렬, 타임아웃 없음     :  3053 ms
C 병렬, 호출별 300ms 예산 :   307 ms  {profile=..., orders=..., recommendations=null} missing=[recommendations]
```

- 순차 ≈ 합(3.1초), 병렬 ≈ 가장 느린 것(3.0초), 예산을 걸면 ≈ 예산(0.3초). 네 번 실행 범위: A 3156~3163ms, B 3051~3053ms, C 306~307ms.
- C의 응답은 받은 것만 채우고 빠진 필드를 **명시**해야 한다(`missing`). 그 필드가 선택 필드인지(부분 응답 허용) 필수인지(전체 실패)는 화면 기준으로 미리 정한다.
- JDK 21 `HttpRequest.Builder.timeout()`을 안 걸면 무한 대기와 같다(Javadoc "block forever") — A·B가 3초를 다 기다렸다.

### 6. 게이트웨이에 두면 안 되는 것

- **업무 규칙**(가격 계산, 주문 가능 여부, 등급별 분기). Azure "Gateway Offloading": "Never offload business logic to the gateway."
- 이유: 서비스 변경마다 게이트웨이도 바꿔야 해 배포가 묶이고(분산 모놀리스), 게이트웨이 팀이 병목이 된다. Azure 문서는 서비스 전용 로직·라우팅 규칙이 게이트웨이를 서비스 변경에 결합시키면 이 패턴이 맞지 않는다고 적는다.
- 집계도 복잡해지면 게이트웨이 안이 아니라 **뒤**의 별도 집계 서비스로 두는 것을 고려하라고 한다(Gateway Aggregation).

### 7. BFF 적합성

- 맞는 경우
  - 범용 백엔드가 여러 인터페이스의 상충 요구로 유지 부담이 크다.
  - 특정 클라이언트(모바일)의 요구에 맞춰 최적화하고 싶다.
- 맞지 않는 경우(Azure 문서)
  - 인터페이스들이 같거나 비슷한 요청을 보낸다.
  - 인터페이스가 하나뿐이다.
  - (추가) 프론트엔드별 리졸버를 둔 GraphQL을 쓰면 BFF가 가치를 더하지 않을 수 있다.
- 소유자: 그 **프론트엔드 팀**(Azure 문서, Newman 2015의 주장).

### 8. 발렛 키

- 앱은 짧게 유효한 토큰만 발급하고 클라이언트가 저장소에 직접 올린다(Azure SAS 예).
- 토큰 제한: 특정 컨테이너·파일 경로, 허용 동작(생성만, 읽기 불가), 짧은 유효 기간(예제는 약 3분), HTTPS만.
- 남는 위험
  - 새어 나가면 유효 기간 동안 누구나 쓸 수 있다.
  - 업로드 크기·횟수는 키로 제한하기 어렵다 → 사후 검사 필요.
  - 올라온 데이터는 쓰기 전에 검증해야 한다. URL에 담긴 키가 로그에 남을 수 있다.

### 9. 홈 API p99가 추천 지연을 따라간다

- 확인: 집계 엔드포인트에서 하위 호출별 지연과 전체 지연을 비교한다. 전체 ≈ 가장 느린 하위 호출이면 타임아웃·부분 응답이 없는 것이다. 하위 호출 코드에 `timeout()`이 있는지 본다.
- 대처: 호출별 예산(남은 데드라인 기준) + 선택 필드 부분 응답(실험 C처럼 3053ms → 307ms). 반복되면 서킷 브레이커로 즉시 실패하고 캐시 값을 대체로 쓴다. 느린 하위 서비스 전용 연결 풀(벌크헤드)로 다른 호출을 보호한다.

### 10. 게이트웨이 우회

- 원인: 백엔드 서비스가 게이트웨이 경로 밖(내부망 직접 주소·공개 IP)에서도 요청을 받는다. 또는 서비스가 `X-User-Id` 같은 전달 헤더를 검증 없이 신원으로 믿는다.
- 대처(Azure "Gateway Offloading"): 백엔드는 게이트웨이 경로로만 받게 네트워크로 막는다. 게이트웨이가 백엔드에 따로 인증하고(mTLS·서비스 토큰), 검증 안 된 전달 헤더를 신원 증명으로 쓰지 않는다. 서비스 접근 로그에서 게이트웨이가 아닌 출처를 탐지한다.
