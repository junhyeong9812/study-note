## 한눈에 — 쉽게 말하면

**선착순 쿠폰 = 한정판 빵 1,000개 판매. 3만 명이 동시에 문을 밀고 들어온다.**

- 지켜야 할 것 세 가지: ① 1,000장을 넘게 찍지 않는다(수량 원자성) ② 한 사람 한 장(인당 제한) ③ 문이 부서지지 않는다(트래픽).
- 그런데 이 문제의 진짜 변별점은 넷째다 — **"발급 성공"이라는 응답이 정확히 무엇을 보장하는가?** 빠르게 응답하려고 뒤에서 비동기로 처리하면, "받았다는 손님"과 "실제 발급"이 어긋날 수 있다.
  - *비동기(asynchronous)*: 요청을 접수만 하고 실제 처리는 뒤의 작업자(워커)가 나중에 하는 방식. 응답은 빨라지지만 "응답 = 처리 완료"가 아니게 된다.
- 실무 예: 올영세일·블랙프라이데이 선착순 쿠폰, 콘서트 예매, 한정판 드롭.

```text
[사고 나는 지점]

  사용자 ──발급 요청──> 게이트웨이 ──큐──> 워커 ──> DB(쿠폰함)
             <──"성공!"──┘                  X 실패
                                            └─> 고객은 받았다고 아는데 쿠폰함에 없다
```

## 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 프로모션팀의 평범한 요구사항 문서다: `POST /promotions/{promotion_id}/coupons` 로 선착순 1,000명에게 쿠폰을 발급하라. 한 사용자는 한 장, 소진되면 실패 응답, 쿠폰함에서 조회 가능해야 하고, "오픈 직후 트래픽이 몰려도 서비스가 죽지 않아야" 한다(예상 동시 접속 3만 명, 작년에 오픈 직후 5분간 전체가 느려진 이력이 배경 문단에 심어져 있다). 코드를 짜는 문제가 아니라 **지문에 안 적혀 있는 요구(수량 원자성·인당 제한·응답 시점)를 읽어내는** 문제다.

과제 목록 (원본 "이 문제를 푸는 방법" · NOTES.md 기준):

- REQUIREMENTS.md 지문만 읽고, NOTES.md 1번 칸에 **타이머 15분**으로 "확정해야 할 것"을 질문 형태로 나열한다 (답이 아니라 질문을 적는다)

- Claude에게 "어떻게 해야 해?"가 아니라 **본인이 내린 결정을 검증받는** 프롬프트로 설계를 진행하고, 보낸 프롬프트 원문을 3번 칸에 남긴다
- **마지막에** solution/CHECKLIST.md 를 열어 대조하고 나머지 칸(대조 결과 / 가장 아팠던 놓침 / 30초 설명)을 채운다 — 먼저 보면 효과가 없다

## 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 남은 수량 (한 행에 3만 명이 몰린다)
  Q2. 동시에 두 번 오면?  → 수량 초과 발급 / 한 사람 두 장
  Q3. 중간에 끊기면?      → 성공 응답 후 워커 실패 = 미발급

숨은 요구 3축: A 수량 원자성 · B 인당 1매 · C 응답 시점(자주 놓침)
+ D 트래픽(지문이 명시적으로 요구: "작년에 오픈 직후 5분간 전체가 느려졌다")
```

## 설계 — 수량 차감: 확인과 차감을 쪼개지 마라 (A)

**언제 문제가 되나**: 남은 수량을 읽고, 앱에서 빼고, 다시 쓰면 — 읽기와 쓰기 사이에 수백 요청이 끼어든다.

나쁜 계약 → 좋은 계약:

```text
나쁨 (Redis): GET remaining        ← 500 읽음
              앱에서 500-1 계산
              SET remaining 499    ← 그 사이 끼어든 요청들의 차감이 사라진다
      ※ GET 후 INCR/DECR 도 마찬가지 — 두 명령 사이가 원자가 아니다

좋음 (Redis): DECR remaining       ← 읽기+빼기가 한 명령. 결과가 음수면 소진
좋음 (DB):    UPDATE promotions
                 SET remaining = remaining - 1
               WHERE id = ? AND remaining > 0    ← affected rows 0 = 소진
```

- "1,000장 정확히"인가, 999장/1,001장 오차 허용인가 — **어느 쪽 오차가 더 싼지가 요구사항이다.** (초과 발급 = 비용, 미달 발급 = 고객 불만)
- 발급이 뒤에서 실패하면 차감한 수량을 **복원**해야 한다 — 복원도 원자적으로.

## 설계 — 인당 1매: DB가 판정하게 하라 (B)

**언제 문제가 되나**: 같은 사용자가 두 기기에서 동시에 누른다. "발급 이력 조회해서 없으면 발급"은 조회와 삽입 사이로 둘 다 통과한다(TOCTOU).
  - *TOCTOU*: 확인한 시점과 사용한 시점 사이에 상황이 바뀌어 확인이 무효가 되는 문제.

```sql
-- 나쁨: 앱이 판정
SELECT * FROM coupons WHERE promotion_id=? AND user_id=?;  -- 없네?
INSERT INTO coupons ...;                                   -- 동시 요청도 똑같이 통과

-- 좋음: DB 제약이 판정
UNIQUE (promotion_id, user_id)   -- 두 번째 INSERT는 DB가 거부한다
INSERT ... → 충돌 잡히면 "이미 발급됨"으로 응답
```

- incident.io도 같은 구조 — unique index를 걸어 **애플리케이션이 아니라 DB가 충돌을 판정**하게 했다.
- 인당 제한 검사와 수량 차감의 **순서**도 결정 사항이다 — 인당 제한을 먼저 걸어야 중복 요청이 수량을 갉아먹지 않는다(실패 시 복원 경로도 단순해진다). 어느 쪽이든 "왜"를 말할 수 있어야 한다.

## 설계 — 응답 시점: "성공"의 의미를 정의하라 (C, 이 문제의 변별점)

**언제 문제가 되나**: 3만 명을 동기 처리로 받을 수 없어 큐+워커를 쓰는 순간, "성공 응답"과 "실제 발급" 사이에 틈이 생긴다.

나쁜 계약 → 좋은 계약:

```text
나쁨: 큐에 넣고 "발급 완료!" 응답
  → 워커가 실패하면 고객은 받았다고 아는데 쿠폰함에 없다 (올리브영 미발급 0.014%)

좋음: 응답이 보장하는 것을 정의하고 그 계약을 지킨다. 선택지:
  ① "발급 확정" 응답 = 자리 확보(원자 차감 + 인당 제한 통과)까지 끝났다.
     워커는 쿠폰함 기록만 한다. 워커 실패는 재시도로 반드시 수렴시킨다.
  ② "접수됨" 응답 = 처리 중임을 정직하게 알리고, 결과는 쿠폰함/알림으로.
  어느 쪽이든: 성공 응답 후 실패가 "탐지"되는가 — 이중 카운터·대사로 미발급을 셀 수 있어야 한다
```

- 게이트웨이 1차 검증과 워커 2차 검증이 있어도 **그 사이 간극**으로 수백 요청이 동시에 들어온다(올리브영 원인 중 하나).
- 발급 직후 쿠폰함 조회가 replica(복제본)를 보면 복제 지연 동안 "없음"으로 보인다 → 사용자는 또 누른다(F).

## 설계 — 트래픽: 소진 후를 싸게 거절하라 (D)

**언제 문제가 되나**: 3만 명이 DB 한 행(남은 수량)을 두드릴 때, 그리고 캐시가 죽었을 때.

```text
캐시(Redis)로 앞에서 받는다               캐시가 죽으면?
  Redis DECR로 1차 판정                     → 3만 명이 DB로 쏟아진다
  소진 후 요청은 Redis에서 즉시 거절        → DB가 바빠서 캐시를 다시 못 채운다
  (DB까지 안 간다)                          → metastable: 장애가 스스로 유지된다
```

- *metastable overload*: 원인이 사라져도 재시도 폭풍 때문에 과부하가 스스로 유지되는 상태. Slack 2-22-22 장애 — "전체가 과부하일 때 재시도는 부하를 늘리고 복구를 막는다."
- 캐시와 DB 중 **무엇이 정본인가**를 정해야 한다(보통 DB가 정본, Redis는 빠른 게이트).
- 클라이언트 재시도가 부하를 키운다 — 지수 백오프만으로 부족하고 retry budget(재시도 총량 제한)이 필요. AWS 측정: 경합 시 총 작업량이 N²로 늘고, full jitter가 100 클라이언트 경합에서 작업량을 50% 이상 절감.
  - *지수 백오프(exponential backoff)*: 재시도 간격을 1초→2초→4초처럼 늘리는 것. *jitter*: 거기에 무작위성을 섞어 재시도가 한꺼번에 몰리지 않게 하는 것.

## 나머지 축 — 짧게

- **취소·복원(E)**: 사용자가 쿠폰을 삭제하면 수량 복원? 복원이 두 번 실행되면? — 복원에도 멱등성이 필요하다.
- **응답/에러(G)**: 소진 / 이미 발급 / 기간 아님을 구분해서 응답. 소진은 4xx — **재시도해도 소용없으므로 클라이언트가 재시도하면 안 된다**는 신호다.
- **관측(H)**: 실제 발급 수와 카운터가 맞는지 대사. "성공 응답 후 실패"(미발급)를 어떻게 알아채는가 — 올리브영은 실발급 키와 요청 키를 분리한 이중 카운터로 잡았다.
- **되묻기(I)**: "선착순 1,000명"의 기준 시각(요청 도착? 처리 완료?), 이벤트 시작/종료, 등급 제한.

## 실패 사례 — 이 항목들이 나온 실제 사고

- **올리브영(2025, 이 문제의 정본)**: 성공 응답 후 워커 실패로 미발급률 0.014%(1만 건당 1.4건). 원인 = GET/INCR 비원자 + 게이트웨이-워커 검증 간극. Lua 스크립트(정확도 100%)는 성능 21% 저하로 기각하고, 프론트 선차감 + 롤백 + 이중 카운터로 미발급 0% 달성 — **"정확한 방법"을 알고도 안 쓰는 판단이 실무다.**
- **Slack 2-22-22**: 캐시 25%가 빈 채로 교체 → 캐시 미스가 DB scatter 쿼리로 폴백 → DB가 바빠 캐시를 못 채우는 metastable 상태. 재시도가 복구를 막았다.
- **Shopify 재고 예약**: 예약(Redis)과 원장(MySQL) 두 저장소에 걸친 갱신은 원자로 묶을 수 없다 → 오버셀/언더셀. "**품절이 아닌데 품절이라고 답하는 것도 장애다.**"
- **Netflix 분산 카운터**: increment는 본질적으로 멱등하지 않다 — 각 증가에 멱등키를 달아 이벤트로 기록하고 집계는 한 번만 반영.

## 핵심 문장

- 수량은 **확인과 차감이 한 연산**이어야 한다 — Redis GET 후 INCR은 원자가 아니다.
- 인당 1매의 판정자는 앱이 아니라 **DB UNIQUE 제약**이다 — 조회-후-삽입은 동시 요청을 둘 다 통과시킨다.
- 이 문제의 진짜 변별점은 **"성공 응답이 무엇을 보장하는가"** 다 — 대부분 원자 차감까지는 가는데, 응답 시점은 잘 안 나온다. 실제 사고(올리브영)가 난 곳이 바로 거기다.
- 과부하에서 **재시도는 복구를 막는다** — 소진 후 요청을 얼마나 싸게 거절하는가가 생존을 가른다.
- 정확성과 성능은 교환 관계다 — 1,000장 "정확히"인지, 어느 방향 오차가 더 싼지는 **기술이 아니라 요구사항**이다.

## 용어 풀이

- **원자성(atomicity)**: 연산이 쪼개지지 않고 한 덩어리로 실행되는 성질. 확인과 차감 사이에 끼어들 수 없어야 한다.
- **TOCTOU**: 확인 시점과 사용 시점 사이에 상황이 바뀌어 확인이 무효가 되는 문제.
- **UNIQUE 제약**: 같은 조합(promotion_id, user_id)이 두 번 들어갈 수 없게 DB가 강제하는 규칙.
- **비동기 워커(worker)**: 요청을 큐에서 꺼내 뒤에서 처리하는 프로세스. 응답과 처리를 분리한다.
- **큐(queue)**: 요청을 줄 세워두는 대기열. 순간 폭주를 완충한다.
- **멱등성(idempotency)**: 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질. 복원·재시도에 필요.
- **복제 지연(replication lag)**: primary에 쓴 내용이 replica(읽기 복제본)에 도달하기까지의 시간차. 발급 직후 조회가 "없음"으로 보이는 원인.
- **정본(source of truth)**: 값이 갈릴 때 믿는 쪽. 캐시와 DB에 같은 값이 있으면 어느 쪽이 정본인지 정해야 한다.
- **metastable overload**: 원인이 사라져도 재시도 폭풍으로 과부하가 스스로 유지되는 상태.
- **scatter 쿼리**: 캐시 미스 시 조회가 모든 샤드로 흩어지는 비싼 폴백 경로.
- **지수 백오프 / jitter**: 재시도 간격을 배수로 늘리기 / 거기에 무작위성을 섞어 몰림을 방지하기.
- **retry budget**: 클라이언트가 쓸 수 있는 재시도 총량의 상한. 백오프만으로 부족할 때의 방어선.
- **이중 카운터**: 요청 수와 실발급 수를 분리해 세는 것. 둘의 차이가 곧 미발급이다.
- **대사(reconciliation)**: 카운터와 실제 발급 이력을 맞춰보고 불일치를 찾는 작업.
- **오버셀/언더셀**: 실제보다 많이 파는 것 / 있는데 품절이라고 답하는 것. 방향만 다른 같은 버그.
