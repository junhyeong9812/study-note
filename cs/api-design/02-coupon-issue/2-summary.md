# api-design/02-coupon-issue — 정리 (힌트)

## 해결하는 문제

"선착순 1,000명에게 한 장씩" — 사람이 창구에서 나눠주면 저절로 지켜지는 규칙이, 3만 명이 같은 밀리초에 버튼을 누르면 전부 깨진다.

```text
없으면 안 되는 것 네 가지

  (1) 수량      남은 수량 1 을 500 요청이 동시에 읽음 → 500장 발급 (초과)
  (2) 인당 1매  같은 사람이 두 기기에서 동시에 → "이력 없음" 둘 다 통과 → 2장
  (3) 응답      큐에 넣고 "발급 완료" → 뒤에서 워커 실패 → 받았다는데 쿠폰함이 비었다
  (4) 트래픽    3만 명이 DB 한 행에 → 전체 서비스가 느려진다 (작년 사고)
```

쉬운 예: 콘서트 티켓 1,000장을 창구 30개에서 동시에 파는 매표소 — 남은 표는 한 곳에서만 세고, 신분증당 한 장은 명부가 판정하고, "판매 완료"는 표를 실제로 건넨 뒤에만 말한다.\
똑같은 구조다: Redis `DECR` 또는 조건부 UPDATE(한 곳에서 세기) · `UNIQUE (promotion_id, user_id)`(명부) · "성공 응답이 보장하는 것"의 정의(건넨 뒤에 완료) · 소진 뒤 요청은 앞단에서 싸게 거절.\
실무 예: 선착순 쿠폰, 타임세일 수량 한정, 예매 오픈, 한정판 드롭 — 네 문제가 그대로 따라온다.

### 한눈에 — 쉽게 말하면

**선착순 쿠폰 = 한정판 빵 1,000개 판매. 3만 명이 동시에 문을 밀고 들어온다.**

- 지켜야 할 것 세 가지: ① 1,000장을 넘게 찍지 않는다(수량 원자성) ② 한 사람 한 장(인당 제한) ③ 문이 부서지지 않는다(트래픽).

> **원자성(atomicity)** — 연산이 쪼개지지 않고 한 덩어리로 실행되는 성질.\
> 예: 확인과 차감 사이에 끼어들 수 없어야 한다.

- 그런데 이 문제의 진짜 변별점은 넷째다 — **"발급 성공"이라는 응답이 정확히 무엇을 보장하는가?**\
  빠르게 응답하려고 뒤에서 비동기로 처리하면, "받았다는 손님"과 "실제 발급"이 어긋날 수 있다.

  > **비동기(asynchronous)** — 요청을 접수만 하고 실제 처리는 뒤의 작업자(워커)가 나중에 하는 방식.\
  > 응답은 빨라지지만 "응답 = 처리 완료"가 아니게 된다.\
  > 예: 큐에 넣고 "발급 완료!"를 응답하면 그 시점에 발급은 아직 안 일어났다.

- 실무 예: 올영세일·블랙프라이데이 선착순 쿠폰, 콘서트 예매, 한정판 드롭.

```text
[사고 나는 지점]

  사용자 ──발급 요청──> 게이트웨이 ──큐──> 워커 ──> DB(쿠폰함)
             <──"성공!"──┘                  X 실패
                                            └─> 고객은 받았다고 아는데 쿠폰함에 없다
```

## 동작·원리

### 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 남은 수량 (한 행에 3만 명이 몰린다)
  Q2. 동시에 두 번 오면?  → 수량 초과 발급 / 한 사람 두 장
  Q3. 중간에 끊기면?      → 성공 응답 후 워커 실패 = 미발급

숨은 요구 3축: A 수량 원자성 · B 인당 1매 · C 응답 시점(자주 놓침)
+ D 트래픽(지문이 명시적으로 요구: "작년에 오픈 직후 5분간 전체가 느려졌다")
```

### 설계 — 수량 차감: 확인과 차감을 쪼개지 마라 (A)

**언제 문제가 되나**: 남은 수량을 읽고, 앱에서 빼고, 다시 쓰면 — 읽기와 쓰기 사이에 수백 요청이 끼어든다.

나쁜 계약 → 좋은 계약:

```text
나쁨 (Redis): GET remaining        ← 500 읽음
              앱에서 500-1 계산
              SET remaining 499    ← 그 사이 끼어든 요청들의 차감이 사라진다
      ※ GET 후 INCR/DECR 도 마찬가지 — 두 명령 사이가 원자가 아니다

좋음 (Redis): DECR remaining       ← 읽기+빼기가 한 명령. 결과가 음수면 소진
좋음 (DB):    UPDATE promotions
                 SET remaining = remaining - 1
               WHERE id = ? AND remaining > 0    ← affected rows 0 = 소진
```

- "1,000장 정확히"인가, 999장/1,001장 오차 허용인가 — **어느 쪽 오차가 더 싼지가 요구사항이다.**\
  (초과 발급 = 비용, 미달 발급 = 고객 불만)
- 발급이 뒤에서 실패하면 차감한 수량을 **복원**해야 한다 — 복원도 원자적으로.

### 설계 — 인당 1매: DB가 판정하게 하라 (B)

**언제 문제가 되나**: 같은 사용자가 두 기기에서 동시에 누른다.\
"발급 이력 조회해서 없으면 발급"은 조회와 삽입 사이로 둘 다 통과한다(TOCTOU).

  > **TOCTOU** — 확인한 시점과 사용한 시점 사이에 상황이 바뀌어 확인이 무효가 되는 문제.\
  > 예: "조회해서 없으면 발급"은 조회와 삽입 사이로 동시 요청 둘 다를 통과시킨다.

```sql
-- 나쁨: 앱이 판정
SELECT * FROM coupons WHERE promotion_id=? AND user_id=?;  -- 없네?
INSERT INTO coupons ...;                                   -- 동시 요청도 똑같이 통과

-- 좋음: DB 제약이 판정
UNIQUE (promotion_id, user_id)   -- 두 번째 INSERT는 DB가 거부한다
INSERT ... → 충돌 잡히면 "이미 발급됨"으로 응답
```

- incident.io도 같은 구조 — unique index를 걸어 **애플리케이션이 아니라 DB가 충돌을 판정**하게 했다.

> **UNIQUE 제약** — 같은 조합(promotion_id, user_id)이 두 번 들어갈 수 없게 DB가 강제하는 규칙.\
> 예: 두 번째 INSERT는 DB가 거부한다.

- 인당 제한 검사와 수량 차감의 **순서**도 결정 사항이다 — 인당 제한을 먼저 걸어야 중복 요청이 수량을 갉아먹지 않는다(실패 시 복원 경로도 단순해진다).\
  어느 쪽이든 "왜"를 말할 수 있어야 한다.

### 설계 — 응답 시점: "성공"의 의미를 정의하라 (C, 이 문제의 변별점)

**언제 문제가 되나**: 3만 명을 동기 처리로 받을 수 없어 큐+워커를 쓰는 순간, "성공 응답"과 "실제 발급" 사이에 틈이 생긴다.

> **큐(queue)** — 요청을 줄 세워두는 대기열.\
> 예: 순간 폭주를 완충한다 — 3만 명을 동기 처리로 받을 수 없을 때 쓴다.

나쁜 계약 → 좋은 계약:

```text
나쁨: 큐에 넣고 "발급 완료!" 응답
  → 워커가 실패하면 고객은 받았다고 아는데 쿠폰함에 없다 (올리브영 미발급 0.014%)

좋음: 응답이 보장하는 것을 정의하고 그 계약을 지킨다. 선택지:
  ① "발급 확정" 응답 = 자리 확보(원자 차감 + 인당 제한 통과)까지 끝났다.
     워커는 쿠폰함 기록만 한다. 워커 실패는 재시도로 반드시 수렴시킨다.
  ② "접수됨" 응답 = 처리 중임을 정직하게 알리고, 결과는 쿠폰함/알림으로.
  어느 쪽이든: 성공 응답 후 실패가 "탐지"되는가 — 이중 카운터·대사로 미발급을 셀 수 있어야 한다
```

- 게이트웨이 1차 검증과 워커 2차 검증이 있어도 **그 사이 간극**으로 수백 요청이 동시에 들어온다(올리브영 원인 중 하나).
- 발급 직후 쿠폰함 조회가 replica(복제본)를 보면 복제 지연 동안 "없음"으로 보인다 → 사용자는 또 누른다(F).

> **복제 지연(replication lag)** — primary에 쓴 내용이 replica(읽기 복제본)에 도달하기까지의 시간차.\
> 예: 발급 직후 조회가 "없음"으로 보이는 원인이다.

### 설계 — 트래픽: 소진 후를 싸게 거절하라 (D)

**언제 문제가 되나**: 3만 명이 DB 한 행(남은 수량)을 두드릴 때, 그리고 캐시가 죽었을 때.

```text
캐시(Redis)로 앞에서 받는다               캐시가 죽으면?
  Redis DECR로 1차 판정                     → 3만 명이 DB로 쏟아진다
  소진 후 요청은 Redis에서 즉시 거절        → DB가 바빠서 캐시를 다시 못 채운다
  (DB까지 안 간다)                          → metastable: 장애가 스스로 유지된다
```

> **metastable overload** — 원인이 사라져도 재시도 폭풍 때문에 과부하가 스스로 유지되는 상태.\
> Slack 2-22-22 장애 — "전체가 과부하일 때 재시도는 부하를 늘리고 복구를 막는다."\
> 예: 3만 명이 DB로 쏟아지면 DB가 바빠서 캐시를 다시 못 채운다.

- 캐시와 DB 중 **무엇이 정본인가**를 정해야 한다(보통 DB가 정본, Redis는 빠른 게이트).

> **정본(source of truth)** — 값이 갈릴 때 믿는 쪽.\
> 예: 캐시와 DB에 같은 값이 있으면 어느 쪽이 정본인지 정해야 한다.

- 클라이언트 재시도가 부하를 키운다 — 지수 백오프만으로 부족하고 retry budget(재시도 총량 제한)이 필요.\
  AWS 측정: 경합 시 총 작업량이 N²로 늘고, full jitter가 100 클라이언트 경합에서 작업량을 50% 이상 절감.

> **retry budget** — 클라이언트가 쓸 수 있는 재시도 총량의 상한.\
> 예: 백오프만으로 부족할 때의 방어선이다.

  > **지수 백오프(exponential backoff)** — 재시도 간격을 1초→2초→4초처럼 늘리는 것.\
  > *jitter*: 거기에 무작위성을 섞어 재시도가 한꺼번에 몰리지 않게 하는 것.\
  > 예: full jitter가 100 클라이언트 경합에서 작업량을 50% 이상 줄였다.

## 쓰이는 자료구조·알고리즘

- **원자 카운터** — Redis `DECR remaining` 또는 `UPDATE ... SET remaining = remaining - 1 WHERE remaining > 0`. 읽기와 빼기가 한 연산이고, 소진 판정은 결과값(음수 / affected rows 0)으로 끝난다. `GET` 후 `INCR`/`DECR`처럼 두 명령으로 쪼개면 그 사이가 원자가 아니다(원본 CHECKLIST A · 올리브영 사례는 `GET` 후 `INCR`).
- **UNIQUE 복합 인덱스** `(promotion_id, user_id)` — 인당 1매의 판정자. 유니크 인덱스(MySQL InnoDB · PostgreSQL에서는 B-tree 계열)가 두 번째 INSERT를 키 충돌로 거절한다 → [data-structure/15-b-tree](../../data-structure/15-b-tree/2-summary.md).
- **큐 + 워커** — 순간 폭주를 줄 세워 완충하는 FIFO. 응답과 처리가 분리되는 대가로 "성공 응답의 의미"를 정의해야 한다 → [data-structure/04-queue-deque](../../data-structure/04-queue-deque/2-summary.md) · [ops-patterns/05-backpressure](../../ops-patterns/05-backpressure/2-summary.md).
- **지수 백오프 + jitter + retry budget** — 클라이언트 재시도가 과부하를 유지시키지 않게 하는 장치 → [ops-patterns/01-retry-backoff](../../ops-patterns/01-retry-backoff/2-summary.md).
- **캐시 붕괴 → 스탬피드** — 캐시가 죽으면 3만 요청이 DB로 쏟아지고 DB가 바빠 캐시를 못 채우는 자기 유지 과부하 → [ops-patterns/09-stampede](../../ops-patterns/09-stampede/2-summary.md).
- **이중 카운터 = 집합 차이** — 요청 키 집합과 실발급 키 집합을 따로 두고 차집합을 세면 그것이 미발급이다. 해시 집합 연산 → [data-structure/05-hashmap](../../data-structure/05-hashmap/2-summary.md).
- **멱등 복원** — 취소 시 수량 복원이 두 번 실행돼도 한 번만 반영되게 하는 키 기록 → [ops-patterns/06-idempotency-store](../../ops-patterns/06-idempotency-store/2-summary.md).

## 적용 — 풀어나가는 법

쿠폰 문제는 "수량을 원자적으로 깎는다"까지는 누구나 가고, 그 다음 두 질문에서 갈린다 — **성공 응답이 무엇을 보장하는가**, **소진 뒤의 3만 명을 어디서 얼마나 싸게 돌려보내는가**.\
순서: ① 공유 자원(남은 수량 · 인당 이력)에 공통 질문 3개를 돌린다 → ② 원자 차감 · UNIQUE로 수량과 인당 1매를 DB가 판정하게 한다 → ③ 큐를 쓰기로 했다면 응답 계약(확정 vs 접수)을 문장으로 정한다 → ④ 캐시가 죽는 순간까지 그려서 거절 경로와 재시도 예산을 정한다.\
아래 과제 목록이 그 훈련의 실제 절차다.

### 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 프로모션팀의 평범한 요구사항 문서다: `POST /promotions/{promotion_id}/coupons` 로 선착순 1,000명에게 쿠폰을 발급하라.\
한 사용자는 한 장, 소진되면 실패 응답, 쿠폰함에서 조회 가능해야 하고, "오픈 직후 트래픽이 몰려도 서비스가 죽지 않아야" 한다(예상 동시 접속 3만 명, 작년에 오픈 직후 5분간 전체가 느려진 이력이 배경 문단에 심어져 있다).\
코드를 짜는 문제가 아니라 **지문에 안 적혀 있는 요구(수량 원자성·인당 제한·응답 시점)를 읽어내는** 문제다.

과제 목록 (원본 "이 문제를 푸는 방법" · NOTES.md 기준):

- REQUIREMENTS.md 지문만 읽고, NOTES.md 1번 칸에 **타이머 15분**으로 "확정해야 할 것"을 질문 형태로 나열한다 (답이 아니라 질문을 적는다)
- NOTES.md 2번 칸: 결정을 **"A 대신 B, 왜냐하면 C"** 형태로 적는다
- Claude에게 "어떻게 해야 해?"가 아니라 **본인이 내린 결정을 검증받는** 프롬프트로 설계를 진행하고, 보낸 프롬프트 원문을 3번 칸에 남긴다
- **마지막에** solution/CHECKLIST.md 를 열어 대조하고 나머지 칸(대조 결과 / 가장 아팠던 놓침 / 30초 설명)을 채운다 — 먼저 보면 효과가 없다

아래 서머리는 이 문제(README)를 분석·정리한 것이다.

### 나머지 축 — 짧게

- **취소·복원(E)**: 사용자가 쿠폰을 삭제하면 수량 복원?\
  복원이 두 번 실행되면?\
  — 복원에도 멱등성이 필요하다.

> **멱등성(idempotency)** — 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.\
> 예: 복원·재시도에 필요하다 — 복원이 두 번 실행돼도 수량은 한 번만 는다.

- **응답/에러(G)**: 소진 / 이미 발급 / 기간 아님을 구분해서 응답.\
  소진은 4xx — **재시도해도 소용없으므로 클라이언트가 재시도하면 안 된다**는 신호다.
- **관측(H)**: 실제 발급 수와 카운터가 맞는지 대사.\
  "성공 응답 후 실패"(미발급)를 어떻게 알아채는가 — 올리브영은 실발급 키와 요청 키를 분리한 이중 카운터로 잡았다.

> **대사(reconciliation)** — 카운터와 실제 발급 이력을 맞춰보고 불일치를 찾는 작업.\
> 예: 실제 발급 수와 카운터가 맞는지 맞춰본다.

> **이중 카운터** — 요청 수와 실발급 수를 분리해 세는 것.\
> 예: 둘의 차이가 곧 미발급이다.

- **되묻기(I)**: "선착순 1,000명"의 기준 시각(요청 도착?\
  처리 완료?), 이벤트 시작/종료, 등급 제한.

## 장애 시나리오와 대처

아래는 우리 시스템 안에서 마주치는 모양이다. 회사 사례는 「실패 사례」 절에 따로 있다.

**1. 1,000장인데 발급 이력이 1,007건이다**

- 현상: 이벤트 종료 후 발급 이력 COUNT가 총 수량을 넘는다.
- 보이는 형태: 예외 0건. `remaining` 컬럼은 -7 또는 0. 초과분은 오픈 직후 1초 안에 몰려 있다.
- 원인: 남은 수량을 읽고 앱에서 빼서 쓰거나, Redis `GET` 후 `DECR`처럼 두 명령으로 쪼갰다 — 그 사이로 수백 요청이 같은 값을 읽었다(정답 2번 참고).
- 대처: `DECR` 한 명령의 반환값으로 판정하거나 조건부 UPDATE(`WHERE remaining > 0`)로 바꾼다. DB에 `CHECK (remaining >= 0)`을 건다. 초과 발급분은 원장을 근거로 사후 처리(무효화 또는 비용 인정)한다 — 어느 쪽이 싼지가 요구사항이다.

**2. "받았다고 떴는데 쿠폰함이 비었다"**

- 현상: 오픈 5분 뒤 CS 문의가 한꺼번에 들어온다.
- 보이는 형태: 요청 카운터 1,000 / 실발급 이력 986. 워커의 dead letter에 14건, 원인은 쿠폰함 INSERT 실패.
- 원인: 성공 응답을 큐 적재 시점에 줬다. 워커 실패는 응답에 반영될 수 없고, 재시도도 수렴하지 않았다(정답 4번 참고).
- 대처: 응답 계약을 다시 정한다 — "발급 확정" = 원자 차감 + 인당 제한 통과까지 끝난 뒤, 워커는 쿠폰함 기록만 하고 실패는 재시도로 반드시 수렴시킨다. 요청 키 / 실발급 키 이중 카운터의 차이를 대사해 미발급을 알람으로 본다.
  - *dead letter*: 재시도해도 계속 실패하는 작업을 버리지 않고 따로 모아두는 곳.

**3. Redis 노드가 재시작되자 쿠폰과 무관한 API까지 느려졌다**

- 현상: 오픈 2분 뒤 캐시 노드 재시작 → 서비스 전체 p99가 튄다.
- 보이는 형태: DB CPU 100%, 커넥션 풀 고갈(HikariCP라면 `Connection is not available, request timed out after …ms`), 캐시 히트율이 0 근처에 머문다. 재시작이 끝났는데도 회복이 안 된다.
- 원인: 캐시 미스가 전부 DB로 폴백하고, DB가 바빠서 캐시를 다시 채우지 못하고, 클라이언트 재시도가 그 부하를 유지시킨다(metastable). 쿠폰 트래픽이 공용 DB 커넥션 풀을 다 먹어 다른 API가 같이 죽는다.
- 대처: 소진 플래그를 게이트웨이/로컬 캐시에 두어 소진 뒤 요청은 DB 근처에도 못 가게 한다. 429 + `Retry-After`와 retry budget으로 재시도 총량을 제한하고, 과부하 시 요청을 버리는 load shedding을 둔다. 쿠폰 경로는 별도 커넥션 풀/인스턴스로 격리한다. 캐시 워밍 전에는 트래픽을 열지 않는다.
  - *load shedding(부하 차단)*: 감당 못 할 요청을 처리하다 죽는 대신 앞에서 빨리 거절하는 것.

**4. 같은 사용자에게 두 장이 나갔다**

- 현상: 대사 배치가 `(promotion_id, user_id)` 중복 그룹을 찾는다.
- 보이는 형태: 같은 `user_id`로 200ms 간격 2건, 서로 다른 서버 인스턴스가 처리했다.
- 원인: "발급 이력 조회 → 없으면 INSERT"의 TOCTOU. 인스턴스 안의 `synchronized`는 다른 인스턴스를 모른다.
- 대처: `UNIQUE (promotion_id, user_id)`를 걸고 INSERT를 먼저 던져 충돌을 "이미 발급됨" 응답으로 바꾼다. 인당 검사를 수량 차감보다 앞에 두어 중복 요청이 수량을 갉아먹지 않게 한다 — 둘이 같은 DB 트랜잭션이면 뒤 단계 실패 시 함께 롤백되고, Redis 차감처럼 저장소가 다르면 실패 시 복원 경로가 따로 필요하다(순서 선택 자체가 원본 CHECKLIST B의 확정 질문이다).

### 실패 사례 — 이 항목들이 나온 실제 사고

- **올리브영(2025, 이 문제의 정본)**: 성공 응답 후 워커 실패로 미발급률 0.014%(1만 건당 1.4건).\
  원인 = GET/INCR 비원자 + 게이트웨이-워커 검증 간극.\
  Lua 스크립트(정확도 100%)는 성능 21% 저하로 기각하고, 프론트 선차감 + 롤백 + 이중 카운터로 미발급 0% 달성 — **"정확한 방법"을 알고도 안 쓰는 판단이 실무다.**
- **Slack 2-22-22**: 캐시 25%가 빈 채로 교체 → 캐시 미스가 DB scatter 쿼리로 폴백 → DB가 바빠 캐시를 못 채우는 metastable 상태.\
  재시도가 복구를 막았다.
- **Shopify 재고 예약**: 예약(Redis)과 원장(MySQL) 두 저장소에 걸친 갱신은 원자로 묶을 수 없다 → 오버셀/언더셀.\
  "**품절이 아닌데 품절이라고 답하는 것도 장애다.**"
- **Netflix 분산 카운터**: increment는 본질적으로 멱등하지 않다 — 각 증가에 멱등키를 달아 이벤트로 기록하고 집계는 한 번만 반영.

## 핵심 문장

- 수량은 **확인과 차감이 한 연산**이어야 한다 — Redis GET 후 INCR은 원자가 아니다.
- 인당 1매의 판정자는 앱이 아니라 **DB UNIQUE 제약**이다 — 조회-후-삽입은 동시 요청을 둘 다 통과시킨다.
- 이 문제의 진짜 변별점은 **"성공 응답이 무엇을 보장하는가"** 다 — 대부분 원자 차감까지는 가는데, 응답 시점은 잘 안 나온다.\
  실제 사고(올리브영)가 난 곳이 바로 거기다.
- 과부하에서 **재시도는 복구를 막는다** — 소진 후 요청을 얼마나 싸게 거절하는가가 생존을 가른다.
- 정확성과 성능은 교환 관계다 — 1,000장 "정확히"인지, 어느 방향 오차가 더 싼지는 **기술이 아니라 요구사항**이다.

### 용어 풀이

- **원자성(atomicity)**: 연산이 쪼개지지 않고 한 덩어리로 실행되는 성질.\
  확인과 차감 사이에 끼어들 수 없어야 한다.
- **TOCTOU**: 확인 시점과 사용 시점 사이에 상황이 바뀌어 확인이 무효가 되는 문제.
- **UNIQUE 제약**: 같은 조합(promotion_id, user_id)이 두 번 들어갈 수 없게 DB가 강제하는 규칙.
- **비동기 워커(worker)**: 요청을 큐에서 꺼내 뒤에서 처리하는 프로세스.\
  응답과 처리를 분리한다.
- **큐(queue)**: 요청을 줄 세워두는 대기열.\
  순간 폭주를 완충한다.
- **멱등성(idempotency)**: 같은 요청이 몇 번 와도 결과가 한 번과 같은 성질.\
  복원·재시도에 필요.
- **복제 지연(replication lag)**: primary에 쓴 내용이 replica(읽기 복제본)에 도달하기까지의 시간차.\
  발급 직후 조회가 "없음"으로 보이는 원인.
- **정본(source of truth)**: 값이 갈릴 때 믿는 쪽.\
  캐시와 DB에 같은 값이 있으면 어느 쪽이 정본인지 정해야 한다.
- **metastable overload**: 원인이 사라져도 재시도 폭풍으로 과부하가 스스로 유지되는 상태.
- **scatter 쿼리**: 캐시 미스 시 조회가 모든 샤드로 흩어지는 비싼 폴백 경로.
- **지수 백오프 / jitter**: 재시도 간격을 배수로 늘리기 / 거기에 무작위성을 섞어 몰림을 방지하기.
- **retry budget**: 클라이언트가 쓸 수 있는 재시도 총량의 상한.\
  백오프만으로 부족할 때의 방어선.
- **이중 카운터**: 요청 수와 실발급 수를 분리해 세는 것.\
  둘의 차이가 곧 미발급이다.
- **대사(reconciliation)**: 카운터와 실제 발급 이력을 맞춰보고 불일치를 찾는 작업.
- **오버셀/언더셀**: 실제보다 많이 파는 것 / 있는데 품절이라고 답하는 것.\
  방향만 다른 같은 버그.
