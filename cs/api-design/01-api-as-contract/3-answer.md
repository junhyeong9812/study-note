# api-design/01-api-as-contract — 정답

## 정답

### 1. 네트워크 API 계약이 더 깨지기 쉬운 이유

- 같은 프로세스의 메서드 계약은 호출자와 구현이 같은 빌드에 있다. 타입 검사·테스트가 함께 돈다.
- API 소비자는 다른 저장소·다른 팀·다른 회사에 있고, 따로 배포한다. 업데이트를 강제할 수 없는 소비자(설치된 앱, 외부 고객)도 있다.
- 그래서 서버 변경이 소비자를 깨도 서버 빌드는 초록색이다. 깨짐은 운영에서, 대개 소비자 쪽 증상으로 먼저 보인다.
- 대처의 방향: 계약을 기계가 읽게 적고(스키마·`code`), 약속하지 않는 것을 명시하고, 소비자 기대를 서버 빌드에서 검사한다(계약 테스트, testing/13).

### 2. 세 겹

```text
  구현             LinkedHashMap 저장소, Jackson 레코드 직렬화
  관찰 가능한 동작   목록이 생성 순서로 나옴, JSON 필드가 id → name 순, 404 문구 "user ... not found"
  명시 계약         응답 필드 id·name·createdAt의 의미, 없으면 404 + code=USER_NOT_FOUND
```

- 가운데 겹(관찰 가능한 동작)은 문서에 없지만 응답에서 보인다. Hyrum Wright는 이것을 암묵 인터페이스라고 부른다.

### 3. Hyrum의 법칙

- "API 사용자가 충분히 많으면 계약에 무엇을 약속했는지는 상관없다. 시스템의 관찰 가능한 동작마다 누군가는 기댄다."
- **경험적 관찰**이다. Hyrum Wright가 Google에서 저수준 인프라 이전을 하며 얻은 관찰이고, Titus Winters가 이름을 붙였다(hyrumslaw.com).
- 출처: hyrumslaw.com, *Software Engineering at Google* 1장(해시 순회 순서 예시).

### 4. 실험 결과 예측

(실험, JDK 21.0.12 + Jackson 2.19.2, 사용자 12명)

| 클라이언트 | v1 | v2 |
|---|---|---|
| A 계약만 사용 | 맞음 | 맞음 |
| B 목록 끝 원소 = 최근 가입 | `oh` (맞음) | `jang` (틀림) |
| C 원문 정규식 | 12/12 | 0/12 |
| D 문구 파싱 | 없는 사용자 판정 true | false (오분류) |

- 예외가 난 클라이언트는 **0개**다. B·C·D 셋 다 예외 없이 틀린 값을 냈다(조용한 실패).
- B의 첫 원소(가장 오래된 사용자)는 v2에서도 `kim`이라 맞았다. 반만 깨진 것이라 더 늦게 발견된다.

### 5. 사용자 5명일 때

- B는 깨지지 않았다. v2(ConcurrentHashMap)에서도 순서가 `u-1001,…,u-1005`로 삽입 순서와 같았다. C(필드 순서 정규식)는 5명에서도 0/5로 깨졌다.
- 이유: 키를 하나씩 넣어 보면 11명까지는 순서가 삽입 순서와 같았다. 12번째 삽입에서 기본 테이블 16칸이 임계값 12에 닿아 32칸으로 커졌다. 그때 확산 함수(`h ^ (h >>> 16)`)로 정해지는 버킷 위치가 달라져 `u-1012`는 `u-1001`과 같은 0번 버킷에, `u-1009`는 24번(맨 끝) 버킷으로 갔다. 5명일 때 순서가 맞은 것은 이 키들에서 나온 우연이다.
- 교훈: 숨은 의존은 데이터가 바뀌어야 드러난다. 적은 데이터로 돌린 테스트 통과는 "계약"의 증거가 아니다.

### 6. `Map.of` 순회 순서

- JDK 21 `java.util.Map` Javadoc은 불변 맵의 순회 순서를 "정해지지 않았고 바뀔 수 있다"고 적는다.
- 구현(`ImmutableCollections`)은 JVM 시작 때 `System.nanoTime()`으로 `SALT32L`을 정하고, 그 값으로 순회 시작 위치·방향을 섞는다.
- 실험: 같은 코드를 JVM 10번 새로 띄워 `[code, message]` 6번, `[message, code]` 4번. 비율은 실행마다 다르다(재실행에서는 8:2).
- 함의: 순서에 기대는 코드가 생기지 못하게 하는 장치다(Hyrum의 법칙에 대한 방어). 서버가 `Map.of`로 응답 JSON을 만들면 키 순서가 재시작마다 바뀔 수 있다. 소비자는 키 순서에 기대면 안 되고, 서버는 순서가 계약이 아님을 적어 둔다.

### 7. 호환의 종류와 출처별 기준

- AIP-180
  - 소스 호환: 이전 버전 기준 코드가 새 클라이언트 라이브러리로 컴파일·실행된다.
  - 와이어 호환: 이전 버전 기준 코드가 새 서버와 올바르게 통신한다(직렬화·역직렬화 기대가 맞음).
  - 의미 호환: 이전 코드가 합리적인 개발자가 기대할 결과를 계속 받는다.
  - "기본값이면 생략 → 항상 포함"은 AIP-180이 같은 주 버전 안의 비호환 변경으로 명시한다("Serializing defaults"). 소비자가 필드 존재 여부에 의미를 둘 수 있기 때문이다. 의미 호환 쪽 문제다.
- Stripe 블로그(2017): 있던 필드는 계속 있고 이름·타입을 유지한다. 새 엔드포인트·새 필드 추가는 안전하다고 본다.
- RFC 9457: 사람용 `detail`을 파싱하지 않아야 한다(SHOULD NOT). 모르는 확장 멤버는 무시해야 한다(MUST). 기계용 정보는 `type`과 확장 멤버로 준다.

### 8. 404 반복 재시도 진단

- 가설: 클라이언트가 에러 `message` 문구로 "없는 사용자"를 판정했다. 문구가 바뀌자 일시 오류로 분류해 재시도한다.
- 확인: 배포 시각과 반복 요청 시작 시각 비교, 클라이언트 코드에서 `message`에 대한 `startsWith`·`contains`·`equals` 검색.
- 서버 대처: 기계용 식별자(`code` 또는 RFC 9457 `type`)를 주고 문서화한다. 당장은 이전 문구를 되돌리는 것도 선택지다.
- 클라이언트 대처: 상태 코드 + `code`로 분기, 문구는 표시만.
- AIP-193: RPC가 늘 `ErrorInfo`(기계용 reason·domain·metadata)를 줬다면 `Status.message`를 바꿔도 된다. 그렇지 않았던 기존 API는 같은 오류에 같은 문구를 유지해야 하고, 개선 문구는 `LocalizedMessage`로 더한다.

### 9. 필드 추가와 엄격한 소비자

- Jackson 2.x 기본값 `FAIL_ON_UNKNOWN_PROPERTIES=true`라 `UnrecognizedPropertyException`으로 실패한다(실험, Jackson 2.19.2). Jackson 3.x는 이 기본값이 `false`라 같은 응답을 실패 없이 읽는다(jackson-databind 3.0 소스).
- 소비자 대처: 관대한 리더 — `FAIL_ON_UNKNOWN_PROPERTIES`를 끄거나 `@JsonIgnoreProperties(ignoreUnknown = true)`. Fowler "TolerantReader"(2011)가 권하는 방식이다(저자 주장).
- 한계: 모르는 필드를 무시하는 것은 쉽지만, 모르는 enum 값처럼 "값의 의미"가 새로 생기는 경우는 무시만으로 안 된다. 소비자가 "알 수 없음" 처리를 정해야 한다(07에서 다룸).
- 정리: 호환 여부는 제공자 규칙만으로 정해지지 않는다. 소비자 쪽 읽기 규칙도 계약의 일부다.
