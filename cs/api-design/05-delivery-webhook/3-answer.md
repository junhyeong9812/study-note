### A. 문제 (REQUIREMENTS.md — 배송 상태 웹훅 수신 API)

#### 1. 지문 읽기 — 숨은 요구

- Q: "응답이 없으면 최대 24시간 동안 재전송" 한 줄은 무엇의 선언인가?\
  A: **at-least-once(최소 한 번 전달) 선언**이다 — 뒤집으면 "같은 이벤트가 여러 번 올 수 있다".\
  그러므로 **중복은 버그가 아니라 스펙**이고, 중복을 거르는 일이 **수신자(우리) 책임**이 된다.\
  CHECKLIST A 원문: "웹훅은 **at-least-once 다.**\
  같은 이벤트가 두 번 이상 오는 것이 정상 동작임을 아는가 / 지문의 '응답이 없으면 최대 24시간 동안 재전송'이 그 뜻임을 읽어냈는가."\
  덤으로 이 한 줄은 **dedup 기록의 보관 기간**(24시간보다 길게)까지 지정해준다.

> **at-least-once** — "최소 한 번은 전달" 보장 — 뒤집으면 "여러 번 올 수 있다".\
> 예: 중복 처리(멱등)가 수신자 책임이 된다.

- Q: 숨은 요구 축들과 고유 변별점은?\
  A: 축은 **A 중복 수신 · B 순서 뒤바뀜 · C 응답 시간(200의 의미) · D 유실 · E 인증 · F 처리량 · G 다중 택배사 · H 부수효과 · I 관측 · J 되묻기**.\
  고유 변별점은 **B 순서 뒤바뀜**이다 — 멱등성(A)은 대부분 떠올리지만 "순서가 뒤바뀐다"는 잘 안 나온다.\
  배송 상태에서는 이게 직접 사고가 된다: **`DELIVERED` 가 `IN_TRANSIT` 으로 되돌아가면 구매확정 타이머가 리셋된다.**\
  자가 채점: A만 = 흔한 수준 / A+C = 실무 경험 / **A+B = 상위권** / A+B+C+D = "이 문제로는 더 잴 게 없다".

> **멱등성(idempotency)** — 같은 이벤트를 몇 번 처리해도 결과가 한 번과 같은 성질.\
> 예: "중복이 오면 안 된다"가 아니라 "중복이 와도 결과가 같아야 한다".

- Q: 공통 질문 3개를 돌리면?\
  A: Q1 공유 자원 → **배송 상태 행**(+ DELIVERED 가 켜는 **구매확정 타이머**).\
  Q2 동시에 두 번 → 같은 `event_id` 가 **서로 다른 서버 인스턴스에 동시 도착** — 메모리 검사로는 못 막는다.\
  Q3 중간에 끊기면 → **200 을 줬는데 처리에 실패한 구간** = 재전송이 안 오므로 **영구 유실**.

#### 2. 중복 수신 (A — 중요)

- Q: 중복이 "정상 동작"인 이유는?\
  A: 발신 측이 **응답을 못 받으면 재전송**하도록 설계돼 있기 때문이다(24시간).\
  우리가 잘 처리하고 200 을 보냈는데 그 응답이 유실돼도 택배사는 다시 보낸다 — 발신자 입장에서는 구별할 방법이 없다.\
  그래서 "중복이 오면 안 된다"가 아니라 "중복이 와도 결과가 같아야 한다"가 요구사항이다.\
  incident.io 도 같은 성질: Pub/Sub 이 **같은 메시지를 두 컨슈머에 동시 전달**해 같은 workflow run 이 동시에 실행됐다.

- Q: "event_id 조회해서 없으면 처리"가 방어가 아닌 이유는?\
  A: **TOCTOU** — 조회와 삽입 사이의 간극으로 **둘 다 통과**한다.\
  "존재하는지 조회 → 없으면 생성" 패턴은 동시 도착 앞에서 무력하다(incident.io 원문 그대로).\
  판정 주체를 애플리케이션이 아니라 **DB** 로 옮겨야 한다.

> **TOCTOU** — 확인과 사용 사이에 상황이 바뀌어 확인이 무효가 되는 문제.\
> 예: "조회 후 처리"의 함정 — 동시 도착이 둘 다 통과한다.

- Q: 다른 서버 인스턴스에 동시 도착하면?\
  A: **`event_id` 에 UNIQUE 인덱스**를 걸어 **DB(Postgres)가 충돌을 판정**하게 한다.\
  incident.io 해법이 정확히 이것 — `once_for` 컬럼에 unique index.\
  인스턴스 로컬 캐시·메모리 집합은 인스턴스 간에 공유되지 않으므로 방어가 안 된다.

- Q: dedup 기록과 처리를 같은 트랜잭션에 묶어야 하는 이유는?\
  A: 따로 커밋하면 **"기록만 남고 처리는 실패"** 한 상태가 생긴다.\
  그러면 택배사가 재전송해줘도 우리는 **"이미 봤다"며 버린다** — 안전망이 있는데도 유실된다.\
  반대로 처리만 되고 기록이 실패하면 재전송이 중복 처리된다.\
  AWS 의 정리: 토큰 기록과 자원 생성이 **하나의 ACID 단위**여야 한다.
  ```sql
  BEGIN;
    INSERT INTO processed_events(event_id, ...);  -- UNIQUE 위반이면 중복
    -- 상태 갱신 + 부수효과 기록
  COMMIT;
  ```

- Q: dedup 보관 기간은?\
  A: **재전송 기간(24시간)보다 길게.**\
  짧으면 늦게 온 재전송을 **새 이벤트로 처리**해서 중복이 그대로 통과한다.\
  Segment 는 여기서 한 발 더 나가 **4주 창**을 두되 **시간이 아니라 크기 기준**(600억 키, 1.5TB RocksDB)으로 잡았다.

> **dedup(중복 제거)** — 이미 처리한 event_id를 기록해두고 재도착을 걸러내는 것.\
> 예: 판정은 DB UNIQUE 가 한다.

#### 3. 순서 뒤바뀜 (B — 고유 변별점)

- Q: 왜 발생 순서대로 도착하지 않는가?\
  A: **재전송**(실패한 앞 이벤트가 나중에 다시 온다), **다중 경로·다중 워커**, **택배사 내부 지연** 때문이다.\
  네트워크는 순서를 보장하지 않고, 큐도 파티션이 나뉘면 보장하지 않는다.\
  "이벤트가 발생 순서대로 도착하지 않는다는 것을 고려했는가"가 CHECKLIST B 의 첫 항목이다.

- Q: DELIVERED 다음 IN_TRANSIT 을 그냥 UPDATE 하면?\
  A: 상태가 **DELIVERED → IN_TRANSIT 으로 되돌아간다.**\
  그러면 **구매확정 타이머가 리셋**되고, 고객에게는 이미 받은 물건이 "이동중"으로 보인다.\
  CHECKLIST 의 주석: "DELIVERED 가 IN_TRANSIT 으로 되돌아가면 구매확정 타이머가 리셋됩니다."\
  AWS DynamoDB 장애(2025-10-19)가 같은 구조의 대형 실증 — **지연됐던 Enactor 가 뒤늦게 자기 옛 계획으로 최신을 덮어썼고**, 이어진 정리 작업이 그것을 "너무 오래됐다"며 삭제해 리전 엔드포인트의 모든 IP 가 사라졌다.

- Q: 막는 방법 두 가지와 더 견고한 쪽은?\
  A: ① **상태 전이 규칙(state machine)**: `ACCEPTED → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED / RETURNED` 를 정의하고 **허용되지 않는 전이는 무시**한다.\
  "DELIVERED → IN_TRANSIT"은 규칙에 없다.\
  ② **시각/순번 비교**: `UPDATE ... WHERE occurred_at < :새 이벤트 시각` 같은 조건부 UPDATE.\
  **①이 더 견고하다** — 남의 시계에 기대지 않기 때문이다.\
  둘을 병용할 수 있다.\
  Uber 는 ②의 강화판: 사용자별 **순차 버전 번호를 가진 entity change log** 로 순서를 강제하고 빈 곳을 자동으로 메웠다 — "이벤트에 순번을 붙여야 한다는 요구는 지문에 절대 안 나온다."

> **상태 전이 규칙(state machine)** — 어떤 상태에서 어떤 상태로 갈 수 있는지의 규칙.\
> 예: "DELIVERED → IN_TRANSIT"은 규칙에 없으므로 무시된다.

- Q: occurred_at 을 그대로 믿으면 안 되는 이유 둘은?\
  A: ① **택배사 시계다** — 우리가 통제하지 못하고 오차·역행이 있을 수 있다(여러 택배사면 제각각).\
  ② **같은 값이 두 개 올 수 있다** — 동률일 때 어느 쪽이 최신인지 판정할 근거가 없다.\
  그래서 되묻기(J) 항목에 "`occurred_at` 의 신뢰도"가 들어 있다.\
  쓰더라도 전이 규칙과 함께 쓴다.

- Q: 순서를 애초에 보존하는 파티셔닝 키는?\
  A: **`tracking_number`** — 같은 배송의 이벤트가 항상 같은 파티션·같은 워커로 가서 **키 단위 순서가 보장**된다(F).\
  Segment 도 같은 사상으로 Kafka 를 **`messageId` 로 파티셔닝**해 같은 ID 가 항상 같은 워커로 가게 했다.\
  단 파티셔닝은 순서를 **보존**할 뿐, 재전송으로 인한 역행까지 없애주지는 않는다 — 전이 규칙은 여전히 필요하다.

> **파티셔닝(partitioning)** — 키(예: tracking_number) 기준으로 큐를 나눠 같은 키는 같은 워커로 보내는 것.\
> 예: 키 단위 순서가 보장된다.

#### 4. 응답 시간과 200의 의미 (C)

- Q: 무거운 처리를 동기로 하면, 표준 구조는?\
  A: **2초를 넘겨 택배사가 실패로 간주**하고 재전송한다 — 처리는 되는데 계속 중복이 쌓이는 최악의 조합이다.\
  표준 구조는 **수신과 처리의 분리**: 받아서 **큐에 넣고 바로 200**, 실제 처리는 워커가 비동기로.\
  하루 50만 건이 피크에 몰린다는 참고가 이 구조를 요구한다(F).

- Q: 분리하면 생기는 새 구간은?\
  A: **"200 을 줬는데 처리에 실패"** 하는 구간.\
  택배사는 전달 성공으로 알고 재전송하지 않으므로, 이 구간의 실패는 **우리 책임으로 수렴**시켜야 한다 — 워커 재시도 + DLQ.\
  분리는 공짜가 아니라 **책임의 이전**이다.

- Q: 200 이 보장해야 하는 것은?\
  A: **"잃지 않을 곳에 넣었다"** 는 보장 — 큐/DB 에 내구성 있게 적재됐다는 뜻으로 정의한다.\
  "처리를 마쳤다"로 정의하면 2초를 못 지키고, "받았다"로만 정의하면 유실이 은폐된다.\
  200 의 의미를 **명시적으로 정의했는가**가 CHECKLIST C 의 마지막 항목이다.

- Q: 큐 적재 실패에 200 을 주면 안 되는 이유는?\
  A: 택배사가 **"전달 완료"로 알고 재전송하지 않는다 = 영구 유실.**\
  이때는 **5xx** 를 줘야 한다 — 그래야 재전송이라는 안전망이 켜진다.\
  지문 기대 동작 4번("우리 시스템 장애로 웹훅을 놓치면 안 됩니다")이 정확히 이 항목이다.

#### 5. 유실 (D — 지문 4번)

- Q: 5xx 가 왜 "안전망을 켜는 것"인가?\
  A: 우리가 5xx 를 주면 **택배사가 재전송한다** — 실패를 숨기지 않는 것이 곧 복구 경로를 여는 것이다.\
  반대로 200 을 주고 처리에 실패하면 재전송이 오지 않는다(영구 유실).\
  즉 **상태 코드가 곧 재시도 계약**이다 — 성공을 과장하면 안전망이 꺼진다.

- Q: 웹훅만 믿으면 안 되는 이유는?\
  A: **발신 측이 TTL 로 이벤트를 버리기 때문**이다.\
  GitHub 2018 장애: 복구 과정에서 웹훅 이벤트 **500만 건 이상이 적체**되고 **TTL 이 지난 페이로드 약 20만 건이 폐기**됐다.\
  우리가 아무리 잘 받아도 **애초에 오지 않는 이벤트**는 막을 수 없다 — 웹훅은 **best-effort** 다.

> **TTL(time to live)** — 보관/재시도 유효 기간.\
> 예: 지나면 폐기된다 — GitHub 2018 에서 약 20만 건이 버려졌다.

> **best-effort** — 최선은 다하지만 보장은 없다는 뜻.\
> 예: 발신 측 TTL 초과 시 이벤트는 버려진다.

- Q: "폴링을 걷어낸다"가 함정인 이유는?\
  A: 웹훅이 best-effort 인 이상 **정합성을 보증할 경로가 사라지기** 때문이다.\
  폴링을 완전히 없애지 말고 **저빈도로 남겨 대사(reconciliation) 경로**로 쓴다 — 빠진 배송을 주기적으로 찾아 메운다.\
  지문은 폴링 제거를 목적처럼 써놨지만, 그것을 그대로 받아들이는지가 이 항목의 시험대다.

> **폴링(polling)** — 우리가 주기적으로 "바뀐 것 있어?"라고 물어보는 방식.\
> 예: 웹훅의 보정 수단으로도 쓴다.

> **대사(reconciliation)** — 웹훅으로 만든 상태와 택배사 원본을 맞춰보고 빠진 것을 찾는 작업.\
> 예: 빠진 배송을 주기적으로 찾아 메운다.

#### 6. 인증·처리량·부수효과·관측 (E, F, G, H, I)

- Q: 서명 검증은 왜 파싱 전이고, 실패에는 무엇을 주는가?\
  A: **파싱 자체가 공격면**이기 때문이다 — 검증 안 된 본문을 역직렬화하면 그 단계에서 당한다(자원 소모·파서 취약점).\
  검증 실패에는 **재전송을 유도하지 않는 4xx**(401/403)를 준다 — 5xx 를 주면 공격자/오설정 발신자가 24시간 동안 계속 때린다.

> **서명 검증(signature)** — 페이로드가 진짜 발신자의 것인지 공유 비밀로 확인하는 절차.\
> 예: 파싱 전에 한다 — 검증 안 된 본문을 역직렬화하면 그 단계에서 당한다.

- Q: head-of-line blocking 과 poison pill 은?\
  A: **head-of-line blocking** = 줄 맨 앞의 느린 처리가 뒤 전체를 막는 것 — 느린 택배사 하나가 다른 택배사 이벤트를 막는다.\
  **poison pill** = 처리가 영원히 실패하는 메시지가 파티션 전체를 막는 것(예: 파싱 불가 페이로드).\
  해법은 **DLQ(dead letter queue) + 비동기 처리**, 그리고 택배사/키별 파티셔닝으로 영향 범위를 가두는 것.\
  Uber 의 Kafka Consumer Proxy 가 정확히 이 둘(느린 Visa 가 Mastercard 를 막는 문제)을 다룬다.

> **dead letter queue(DLQ)** — 재시도해도 실패하는 메시지를 따로 모아두는 곳.\
> 예: 버리지 않고 사람이 본다.

- Q: 다중 택배사에서 event_id 를 그대로 멱등 키로 쓰면?\
  A: **택배사 간 id 가 충돌하면 남의 이벤트를 버린다** — dedup 이 정상 이벤트를 삼키는 유실로 바뀐다.\
  `event_id` 의 유일성 범위가 **택배사 내인지 전역인지**를 물어(J) 확인하고, 불확실하면 **`(carrier, event_id)`** 복합 키로 잡는다.\
  덧붙여 페이로드 형식이 다르므로 **정규화 지점**(수신 직후 어댑터)을 정해야 새 택배사 추가가 국소 변경으로 끝난다.

- Q: 타이머가 두 번 실행되면 — 부수효과에는 무엇이 필요한가?\
  A: 구매확정이 두 번 잡히거나 시점이 리셋된다 — **부수효과도 멱등해야 한다**(타이머 키를 배송/주문 단위로 잡아 "이미 있으면 no-op").\
  상태 갱신은 됐는데 타이머 시작이 실패하는 경우까지 보려면 **같은 트랜잭션에 넣거나 복구 경로**(아웃박스·대사)가 있어야 한다.\
  알림처럼 **되돌릴 수 없는 부수효과는 확정된 뒤 가장 마지막**에 둔다.\
  Grab 이 이 자리에서 졌다: 핸들러가 (1) 멱등키 생성 (2) 혜택1 (3) 혜택2 를 한 덩어리로 처리했는데 3에서 실패하면 **핸들러 전체가 재큐잉되어 1부터 다시 돌며 새 멱등키를 만들었다** → 혜택1 이 두 번 지급.\
  **재시도는 단계 단위여야 하고 멱등키는 재시도 바깥에서 한 번만.**

- Q: 웹훅이 "안 오는 것"은 왜 로그에 안 남고 어떻게 감지하는가?\
  A: **일어나지 않은 일에는 이벤트가 없기 때문**이다 — 오류도 예외도 없고 그래프도 조용하다.\
  감지하려면 **부재를 지표로 만든다**: "마지막 수신으로부터 N시간", 택배사별 수신량의 급감 알림, 폴링 대사에서 발견되는 누락 건수.\
  함께 볼 지표: **중복 비율**과 **dead letter 적체**(CHECKLIST I).

### B. 개념

#### 7. 문제를 여는 질문 세 개 (원본 README 이관)

- Q: Q1. 여기서 바뀌는 공유 자원이 무엇인가?\
  A: **배송 상태 행**(tracking_number 단위) — 그리고 그것이 트리거하는 **주문 상태**와 **구매확정 타이머**.\
  공유 자원이 "숫자"가 아니라 **상태 기계**라는 점이 01·03번과 다르다 — 그래서 lost update 가 아니라 **역행 갱신**이 주 사고 형태다.

- Q: Q2. 이게 정확히 동시에 두 번 오면?\
  A: 같은 `event_id` 가 **서로 다른 인스턴스에** 동시 도착해 둘 다 처리된다(TOCTOU).\
  답: **UNIQUE 인덱스로 DB 가 판정** + dedup 기록과 처리를 **한 트랜잭션**으로.\
  다른 event_id 두 개가 겹치는 경우는 순서 문제로 넘어간다 — 전이 규칙이 받는다.

- Q: Q3. 중간에 끊기면 어디까지 남는가?\
  A: **200 을 준 뒤 처리에 실패**하면 택배사 쪽에는 성공으로 남고 우리 쪽에는 아무것도 없다 — **영구 유실**.\
  그래서 200 의 의미를 "잃지 않을 곳에 넣었다"로 정의하고, 그 뒤 실패는 **재시도·DLQ**로 수렴시킨다.\
  dedup 기록만 커밋되고 처리가 실패한 경우가 제일 나쁘다 — 재전송이 와도 걸러진다.

#### 8. 파생 — 왜 / 예측 / 경계 / 연결

- Q: Grab 은 멱등키를 쓰고 있었는데 왜 중복 지급이 났는가?\
  A: **재시도 단위가 "핸들러 전체"** 였기 때문이다.\
  3단계에서 실패하면 핸들러가 통째로 재큐잉되며 1단계(멱등키 생성)부터 다시 돌아 **새 키를 만들었다** — 보상 시스템이 그것을 재시도로 인식하지 못했다.\
  원문: "This generates a new idempotency key, meaning the Reward system wouldn't recognize the retry and will award Benefits1 twice."\
  교훈: 멱등키는 **재시도 바깥에서 한 번만** 만들어지고, 재시도는 **단계 단위**여야 한다.

- Q: CircleCI 사고의 교훈 — 어디를 고쳐야 하는가?\
  A: **컨슈머다.**\
  답은 명시돼 있다 — "컨슈머는 언제나 멱등해야 합니다."\
  배포가 workflow status 계산에 race 를 넣어 **중복 완료 이벤트**가 발행됐고, 비멱등 auto-rerun 컨슈머가 중복마다 새 워크플로를 만들어 **중복 33,135건**, job 3,500건 지연, 8,000건 canceling 정지가 났다.\
  생산자의 사소한 race 가 비멱등 컨슈머를 만나면 규모가 폭발한다 — 생산자를 고쳐도 컨슈머 멱등성은 면제되지 않는다.

- Q: AWS DynamoDB 장애는 어느 축과 같은 구조인가?\
  A: **B 순서 뒤바뀜**이다.\
  지연됐던 DNS Enactor 가 뒤늦게 **자기 옛 계획으로 최신 계획을 덮어썼고**, 정리 작업이 그 옛 계획을 "너무 오래됐다"며 삭제해 리전 엔드포인트의 **모든 IP 가 사라졌다.**\
  `DELIVERED` 뒤에 `IN_TRANSIT` 이 도착하는 것과 **같은 구조**이며, 그 사고가 얼마나 크게 터질 수 있는지의 실증이다.

- Q: Segment 의 dedup 창이 크기 기반인 것의 이점은?\
  A: **트래픽 스파이크 때 우아하게 degrade 한다** — 시간 기준이면 스파이크에 메모리·디스크가 예측 불가로 부푸는데, 크기 기준이면 자원 상한이 고정된다.\
  대신 스파이크 때 창의 "시간 폭"이 줄어 아주 늦은 중복을 놓칠 수 있다 — 그 트레이드오프를 아는 것이 고급 선택이다.\
  규모: 4주 창, 600억 키, 1.5TB RocksDB(워커 로컬), `messageId` 파티셔닝과 짝.

- Q: 02번의 "성공 응답의 의미"와 여기 "200의 의미"는?\
  A: 같은 점: 둘 다 **응답이 무엇을 보장하는지를 계약으로 못 박아야** 하고, 과장된 성공은 재시도 안전망을 꺼버린다.\
  다른 점: 02번은 **클라이언트가 재시도하는 API** 라 "같은 키 재요청에 무엇을 돌려줄지"(첫 응답 재생/409/422)가 쟁점이다 — Stripe 는 첫 응답을 **500 포함** 그대로 재생하고 24시간 후 pruning, 토스는 body 가 다르면 422·진행 중이면 409, GoCardless 는 재생 없이 409 + conflicting_resource_id.\
  웹훅 수신은 **발신자가 기계**라 응답 본문에 기대가 없다 — **보통 200 하나면 되고**, 대신 "200 = 내구성 있게 적재됨"이라는 의미 정의가 쟁점이다.

- Q: 웹훅 수신 API 와 클라이언트 재시도 API 의 멱등 응답 계약 차이는?\
  A: 웹훅 수신: 중복에 **200 을 주고 조용히 버린다**(발신자는 "전달됐다"만 알면 된다).\
  4xx/5xx 는 각각 "다시 보내지 마라 / 다시 보내라"의 신호로만 쓴다.\
  클라이언트 재시도 API: 사람이 결과를 봐야 하므로 **첫 응답 재생 / 충돌 판정 / 진행 중 구분**이 필요하다 — 회사마다 다르고(위 네 곳), 그래서 **문서로 고정**해야 한다.\
  공통: 기록과 처리가 **한 ACID 단위**(AWS)라는 점은 양쪽 다 같다.
