## 한눈에 — 쉽게 말하면

**웹훅 수신 = 택배사가 우리 집 우편함에 소식을 넣어주는 것. 문제는 같은 소식이 두 번 오고, 순서가 뒤바뀌어 오고, 아예 안 오기도 한다는 것.**

- *웹훅(webhook)*: 우리가 물어보는(폴링) 대신, 상대가 사건이 생길 때 우리 URL로 POST를 쏴주는 방식.
- 지문의 "응답이 없으면 최대 24시간 재전송" 한 줄이 곧 **at-least-once**(최소 한 번 = 중복 가능) 선언이다. 중복은 비정상이 아니라 **정상 동작**이다.
- 대부분 중복(멱등)까지는 떠올린다. 이 문제의 고유 변별점은 **순서 뒤바뀜** — `DELIVERED`(배송완료) 다음에 늦게 온 `IN_TRANSIT`(이동중)이 도착하면? 막지 않으면 완료가 이동중으로 되돌아가고 구매확정 타이머가 리셋된다.
- 그리고 "2초 안에 응답" — 무거운 처리를 동기로 하면 타임아웃. 받아서 큐에 넣고 바로 200. 단, **200의 의미를 정의해야 한다.**
- 실무 예: 택배 추적, PG 결제 통지, GitHub 이벤트 등 모든 웹훅 수신.

```text
[순서 뒤바뀜 — 막지 않으면]

  실제 발생:  IN_TRANSIT ──> DELIVERED
  도착 순서:  DELIVERED 먼저, IN_TRANSIT 나중 (재전송·경로 차이로 흔함)

  그냥 UPDATE 하면:  상태 = DELIVERED → IN_TRANSIT ✗  (완료가 되돌아감, 타이머 리셋)
  전이 규칙을 두면:  DELIVERED에서 IN_TRANSIT으로는 못 간다 → 늦은 이벤트 무시 ○
```

## 문제 — 이 챕터가 시키는 것

원본 REQUIREMENTS.md는 물류팀의 평범한 요구사항 문서다: 5분 폴링을 걷어내고 `POST /webhooks/delivery` 로 택배사 웹훅을 받아 배송 상태를 갱신하라. DELIVERED면 주문을 배송완료로 바꾸고 구매확정 타이머를 시작하고, "택배사에 2초 이내로 응답", "우리 시스템 장애로 웹훅을 놓치면 안 됩니다"가 기대 동작에 있다. 참고의 "응답이 없으면 최대 24시간 동안 재전송" 한 줄이 at-least-once(중복 가능) 선언이고, 하루 50만 건 피크 집중·다중 택배사·페이로드 상이가 처리량·정규화 요구를 심어놓았다. 이 방향(외부→우리)의 수신 API 설계 문제다.

과제 목록 (원본 "이 문제를 푸는 방법" · NOTES.md 기준):

- REQUIREMENTS.md 지문만 읽고, NOTES.md 1번 칸에 **타이머 15분**으로 "확정해야 할 것"을 질문 형태로 나열한다 (답이 아니라 질문을 적는다)
- NOTES.md 2번 칸: 결정을 **"A 대신 B, 왜냐하면 C"** 형태로 적는다
- Claude에게 "어떻게 해야 해?"가 아니라 **본인이 내린 결정을 검증받는** 프롬프트로 설계를 진행하고, 보낸 프롬프트 원문을 3번 칸에 남긴다
- **마지막에** solution/CHECKLIST.md 를 열어 대조하고 나머지 칸(대조 결과 / 가장 아팠던 놓침 / 30초 설명)을 채운다 — 먼저 보면 효과가 없다

## 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 배송 상태 행 (+ DELIVERED가 켜는 구매확정 타이머)
  Q2. 동시에 두 번 오면?  → 같은 event_id가 다른 서버 인스턴스에 동시 도착
  Q3. 중간에 끊기면?      → 200 줬는데 처리 실패 = 영구 유실 (재전송 안 옴)

수신 파이프라인:
  택배사 → [서명 검증(파싱 전!)] → [큐에 적재] → 200 응답 (2초 내)
                                       ↓
           [워커] 정규화 → dedup(event_id) → 상태 전이 규칙 검사 → 갱신 + 부수효과

숨은 요구: A 중복(at-least-once) · B 순서 뒤바뀜(고유 변별점) · C 200의 의미 · D 유실(폴링 보정)
```

## 설계 — 중복 수신: event_id로 dedup (A)

**언제 문제가 되나**: 재전송은 스펙이다. 게다가 중복이 **서로 다른 서버 인스턴스에 동시에** 도착할 수 있다 — 메모리 검사로는 못 막는다.

나쁜 계약 → 좋은 계약:

```text
나쁨: "event_id 조회해서 없으면 처리" (조회와 기록 사이로 동시 중복이 둘 다 통과 — TOCTOU)
나쁨: dedup 기록과 실제 처리가 따로 커밋 (기록만 남고 처리 실패 → 재전송이 와도 "이미 봤다"며 버림)

좋음: BEGIN
        INSERT INTO processed_events(event_id UNIQUE, ...)  ← DB가 중복을 판정
        상태 갱신 + 부수효과 기록
      COMMIT          ← dedup 기록과 처리가 한 덩어리
```

- dedup 기록 보관 기간은 **재전송 기간(24시간)보다 길게** — 짧으면 늦은 재전송을 새 이벤트로 처리한다.
- 택배사가 여러 곳이다(G): `event_id`가 **택배사마다 유일**이라면 그대로 키로 쓰면 충돌 시 남의 이벤트를 버린다 → `(carrier, event_id)`처럼 범위를 물어서 확정해야 한다.

## 설계 — 순서 뒤바뀜: 오래된 이벤트가 새 상태를 덮지 못하게 (B, 고유 변별점)

**언제 문제가 되나**: 이벤트는 발생 순서대로 도착하지 않는다 — 재전송, 다중 경로, 택배사 내부 지연.

```text
막는 방법 두 가지 (병용 가능):
  ① 상태 전이 규칙: ACCEPTED → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED / RETURNED
     허용된 전이가 아니면 무시. "DELIVERED → IN_TRANSIT"은 규칙에 없다.
  ② 시각/순번 비교: UPDATE ... WHERE occurred_at < :새 이벤트 시각  (조건부 UPDATE)
     단, occurred_at은 "택배사 시계"다 — 신뢰할 수 있나? 같은 값 두 개가 오면?
```

- ①이 더 견고하다 — 남의 시계에 기대지 않는다. ②만 쓰면 시계 오차·동률 처리를 정해야 한다.
- 순서를 애초에 보존하는 수단도 있다: 큐를 `tracking_number`로 파티셔닝하면 **같은 배송의 이벤트는 같은 워커로 순서대로** 간다(F).
- AWS DynamoDB 장애(2025-10-19)가 정확히 이 구조 — 지연됐던 프로세스가 뒤늦게 **옛 계획으로 최신을 덮어써서** 리전 엔드포인트 IP가 전부 사라졌다. "오래된 것이 새것을 덮는" 사고는 이만큼 크게 터진다.

## 설계 — 200의 의미: 응답 시간과 유실 (C, D)

**언제 문제가 되나**: 2초 안에 응답해야 하니 수신과 처리를 분리하는데, 그 순간 "200을 줬는데 처리 실패" 구간이 생긴다.

나쁜 계약 → 좋은 계약:

```text
나쁨: 무조건 빨리 200 (큐 적재가 실패해도 200)
  → 택배사는 "전달 완료"로 알고 재전송하지 않는다 = 영구 유실

좋음: 200 = "잃지 않을 곳(큐/DB)에 넣었다"는 보장으로 정의
  큐 적재 성공 → 200   (이후 처리는 우리 책임 — 재시도·DLQ로 수렴)
  큐 적재 실패 → 5xx   (택배사의 재전송이 우리의 안전망이 된다)
```

- 우리가 5xx를 주면 재전송이 온다 — **실패를 숨기지 않는 것이 안전망을 켜는 것**이다.
- 그런데 재전송도 영원하지 않다: **발신 측이 TTL로 이벤트를 버린다.** GitHub 2018 장애에서 TTL 초과 웹훅 약 20만 건이 폐기됐다. 웹훅은 best-effort — 정합성이 중요하면 **폴링을 완전히 걷어내면 안 되고** 저빈도 폴링/대사 경로를 남겨야 한다. 지문의 "폴링을 걷어낸다"가 함정인 이유.

## 설계 — 인증·처리량·부수효과 (E, F, H)

- **서명 검증(E)**: `X-Carrier-Signature`를 **본문 파싱 전에** 검증(파싱 자체가 공격면). 검증 실패는 재전송을 유도하지 않는 4xx로.
- **처리량(F)**: 하루 50만 건이 피크에 몰린다. 느린 택배사 하나가 다른 택배사 이벤트를 막지 않게(head-of-line blocking), 파싱 불가 이벤트 하나가 큐를 막지 않게(poison pill → dead letter). Uber는 DLQ + 비동기 처리로 풀었다.
- **부수효과(H)**: DELIVERED가 구매확정 타이머를 켠다 — 중복 이벤트로 **두 번 켜지면?** 타이머 시작도 멱등해야 한다. 상태 갱신은 됐는데 타이머 시작이 실패하면? — 같은 트랜잭션이거나 복구 경로가 있어야 한다. 알림처럼 되돌릴 수 없는 부수효과는 확정 후 가장 마지막에.
- **관측(I)**: **웹훅이 안 오는 것은 로그에 안 남는다** — "마지막 수신으로부터 N시간" 같은 부재 감지가 필요. 중복 비율·dead letter 적체도 지표다.
- **되묻기(J)**: event_id 유일성 범위, occurred_at 신뢰도, 재전송 정책, 상태 전이 규칙.

## 실패 사례 — 이 항목들이 나온 실제 사고

- **incident.io**: Pub/Sub이 같은 메시지를 두 컨슈머에 동시 전달 → unique index로 DB가 판정하게 해서 해결. "조회 후 생성"은 방어가 아니다.
- **Segment**: 4주 창에서 이벤트의 0.6%가 중복(모바일 재전송) — 전자상거래 고객에겐 수백만 달러 차이. messageId로 파티셔닝 + 크기 기반 dedup 창(600억 키)으로 해결.
- **CircleCI(2025-12-02)**: 생산자의 사소한 race로 중복 완료 이벤트 → 비멱등 컨슈머가 중복마다 워크플로 생성 → 중복 33,135건. **컨슈머는 언제나 멱등해야 한다.**
- **Grab**: 멱등키를 쓰는데도 중복 지급 — 재시도 단위가 "핸들러 전체"라 재시도마다 **새 멱등키를 생성**했다. 재시도는 단계 단위여야 하고 키는 재시도 바깥에서 한 번만.
- **AWS DynamoDB(2025-10-19)**: 지연된 프로세스가 옛 상태로 최신을 덮어씀 — 순서 뒤바뀜의 대형 실증.
- **GitHub(2018)**: 복구 중 웹훅 500만 건 적체, TTL 초과 약 20만 건 폐기 — 발신 측이 버린다.

## 핵심 문장

- "24시간 재전송" 한 줄 = at-least-once 선언 — **중복은 버그가 아니라 스펙이고, dedup은 처리와 같은 트랜잭션이어야 한다.**
- 이 문제의 고유 변별점은 순서다 — **오래된 이벤트가 새 상태를 덮지 못하게** 상태 전이 규칙(또는 순번 비교)으로 막아라.
- 200의 의미를 정의하라 — **큐 적재 실패에 200을 주는 순간 영구 유실이다.** 5xx는 재전송이라는 안전망을 켠다.
- 웹훅은 best-effort다 — 발신 측 TTL이 이벤트를 버리므로 **폴링 보정/대사 경로를 완전히 걷어내면 안 된다.**
- 웹훅이 안 오는 것은 로그에 안 남는다 — 부재를 감지하는 관측이 따로 필요하다.

## 용어 풀이

- **웹훅(webhook)**: 사건 발생 시 상대가 우리 URL로 POST를 보내주는 통지 방식. 폴링의 반대.
- **폴링(polling)**: 우리가 주기적으로 "바뀐 것 있어?"라고 물어보는 방식. 웹훅의 보정 수단으로도 쓴다.
- **at-least-once**: "최소 한 번은 전달" 보장 — 뒤집으면 "여러 번 올 수 있다". 중복 처리(멱등)가 수신자 책임이 된다.
- **멱등성(idempotency)**: 같은 이벤트를 몇 번 처리해도 결과가 한 번과 같은 성질.
- **dedup(중복 제거)**: 이미 처리한 event_id를 기록해두고 재도착을 걸러내는 것. 판정은 DB UNIQUE가 한다.
- **TOCTOU**: 확인과 사용 사이에 상황이 바뀌어 확인이 무효가 되는 문제. "조회 후 처리"의 함정.
- **상태 전이 규칙(state machine)**: 어떤 상태에서 어떤 상태로 갈 수 있는지의 규칙. 역행 이벤트를 걸러낸다.
- **best-effort**: 최선은 다하지만 보장은 없다는 뜻. 발신 측 TTL 초과 시 이벤트는 버려진다.
- **TTL(time to live)**: 보관/재시도 유효 기간. 지나면 폐기된다.
- **파티셔닝(partitioning)**: 키(예: tracking_number) 기준으로 큐를 나눠 같은 키는 같은 워커로 보내는 것. 키 단위 순서가 보장된다.
- **head-of-line blocking**: 줄 맨 앞의 느린 작업이 뒤 전체를 막는 현상.
- **poison pill**: 처리가 영원히 실패하는 메시지. 치우지 않으면 큐 전체를 막는다.
- **dead letter queue(DLQ)**: 재시도해도 실패하는 메시지를 따로 모아두는 곳. 버리지 않고 사람이 본다.
- **서명 검증(signature)**: 페이로드가 진짜 발신자의 것인지 공유 비밀로 확인하는 절차. 파싱 전에 한다.
- **대사(reconciliation)**: 웹훅으로 만든 상태와 택배사 원본을 맞춰보고 빠진 것을 찾는 작업.
