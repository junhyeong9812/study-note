## 해결하는 문제

"택배사가 보내주는 상태를 받아 갱신하라" — 받기만 하면 될 것 같지만, 웹훅은 우편함이다: 같은 편지가 두 번 오고, 늦게 부친 편지가 먼저 도착하고, 우체국이 편지를 버리기도 한다.

```text
없으면 안 되는 것 네 가지

  (1) 중복      "응답 없으면 24시간 재전송" = 같은 event_id 가 여러 번 → 구매확정 타이머가 두 번 켜진다
  (2) 순서      DELIVERED 도착 뒤 늦은 IN_TRANSIT → 완료가 이동중으로 되돌아감 → 타이머 리셋
  (3) 200의 뜻  큐 적재 실패에도 200 → 택배사는 "전달 완료" → 재전송 없음 = 영구 유실
  (4) 안 옴     택배사 TTL 초과·장애로 이벤트 폐기 → 우리 로그에는 아무것도 남지 않는다
```

쉬운 예: 친구가 보낸 문자 여러 통 — "출발했어", "도착했어"가 순서 바뀌어 오거나 같은 문자가 두 번 와도, 우리는 "도착" 뒤에 온 "출발"을 무시할 줄 안다. 그 판단 규칙을 코드에 넣는 것이다.\
똑같은 구조다: `(carrier_id, event_id)` UNIQUE dedup(처리와 같은 트랜잭션 — `event_id`가 전역 유일로 확인되면 단독 키도 가능) · 상태 전이 규칙 · "200 = 잃지 않을 곳에 넣었다"는 정의 · 저빈도 폴링 보정.\
실무 예: PG 결제 통지, 문자·카카오 발송 결과 콜백, GitHub·Stripe 이벤트, IoT 센서 상태 — 외부가 밀어 넣는 모든 이벤트 수신.

### 한눈에 — 쉽게 말하면

**웹훅 수신 = 택배사가 우리 집 우편함에 소식을 넣어주는 것. 문제는 같은 소식이 두 번 오고, 순서가 뒤바뀌어 오고, 아예 안 오기도 한다는 것.**

> **웹훅(webhook)** — 우리가 물어보는(폴링) 대신, 상대가 사건이 생길 때 우리 URL로 POST를 쏴주는 방식.\
> 예: 택배 추적, PG 결제 통지, GitHub 이벤트가 전부 웹훅이다.

- 지문의 "응답이 없으면 최대 24시간 재전송" 한 줄이 곧 **at-least-once**(최소 한 번 = 중복 가능) 선언이다.\
  중복은 비정상이 아니라 **정상 동작**이다.

> **at-least-once** — "최소 한 번은 전달" 보장 — 뒤집으면 "여러 번 올 수 있다".\
> 예: 중복 처리(멱등)가 수신자 책임이 된다.

- 대부분 중복(멱등)까지는 떠올린다.\
  이 문제의 고유 변별점은 **순서 뒤바뀜** — `DELIVERED`(배송완료) 다음에 늦게 온 `IN_TRANSIT`(이동중)이 도착하면?\
  막지 않으면 완료가 이동중으로 되돌아가고 구매확정 타이머가 리셋된다.

> **멱등성(idempotency)** — 같은 이벤트를 몇 번 처리해도 결과가 한 번과 같은 성질.\
> 예: 같은 이벤트가 두 번 와도 상태는 한 번 갱신된 것과 같아야 한다.

- 그리고 "2초 안에 응답" — 무거운 처리를 동기로 하면 타임아웃.\
  받아서 큐에 넣고 바로 200. 단, **200의 의미를 정의해야 한다.**
- 실무 예: 택배 추적, PG 결제 통지, GitHub 이벤트 등 모든 웹훅 수신.

```text
[순서 뒤바뀜 — 막지 않으면]

  실제 발생:  IN_TRANSIT ──> DELIVERED
  도착 순서:  DELIVERED 먼저, IN_TRANSIT 나중 (재전송·경로 차이로 흔함)

  그냥 UPDATE 하면:  상태 = DELIVERED → IN_TRANSIT ✗  (완료가 되돌아감, 타이머 리셋)
  전이 규칙을 두면:  DELIVERED에서 IN_TRANSIT으로는 못 간다 → 늦은 이벤트 무시 ○
```

## 동작·원리

### 전체 흐름

```text
공통 질문 3개를 이 문제에 돌리면:
  Q1. 공유 자원?          → 배송 상태 행 (+ DELIVERED가 켜는 구매확정 타이머)
  Q2. 동시에 두 번 오면?  → 같은 event_id가 다른 서버 인스턴스에 동시 도착
  Q3. 중간에 끊기면?      → 200 줬는데 처리 실패 = 영구 유실 (재전송 안 옴)

수신 파이프라인:
  택배사 → [서명 검증(파싱 전!)] → [큐에 적재] → 200 응답 (2초 내)
                                       ↓
           [워커] 정규화 → dedup(event_id) → 상태 전이 규칙 검사 → 갱신 + 부수효과

숨은 요구: A 중복(at-least-once) · B 순서 뒤바뀜(고유 변별점) · C 200의 의미 · D 유실(폴링 보정)
```

### 설계 — 중복 수신: event_id로 dedup (A)

**언제 문제가 되나**: 재전송은 스펙이다.\
게다가 중복이 **서로 다른 서버 인스턴스에 동시에** 도착할 수 있다 — 메모리 검사로는 못 막는다.

나쁜 계약 → 좋은 계약:

```text
나쁨: "event_id 조회해서 없으면 처리" (조회와 기록 사이로 동시 중복이 둘 다 통과 — TOCTOU)
나쁨: dedup 기록과 실제 처리가 따로 커밋 (기록만 남고 처리 실패 → 재전송이 와도 "이미 봤다"며 버림)

좋음: BEGIN
        INSERT INTO processed_events(event_id UNIQUE, ...)  ← DB가 중복을 판정
        상태 갱신 + 부수효과 기록
      COMMIT          ← dedup 기록과 처리가 한 덩어리
```

- dedup 기록 보관 기간은 **재전송 기간(24시간)보다 길게** — 짧으면 늦은 재전송을 새 이벤트로 처리한다.

> **dedup(중복 제거)** — 이미 처리한 event_id를 기록해두고 재도착을 걸러내는 것.\
> 예: 판정은 DB UNIQUE가 한다.

- 택배사가 여러 곳이다(G): `event_id`가 **택배사마다 유일**이라면 그대로 키로 쓰면 충돌 시 남의 이벤트를 버린다 → `(carrier, event_id)`처럼 범위를 물어서 확정해야 한다.

### 설계 — 순서 뒤바뀜: 오래된 이벤트가 새 상태를 덮지 못하게 (B, 고유 변별점)

**언제 문제가 되나**: 이벤트는 발생 순서대로 도착하지 않는다 — 재전송, 다중 경로, 택배사 내부 지연.

```text
막는 방법 두 가지 (병용 가능):
  ① 상태 전이 규칙: ACCEPTED → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED / RETURNED
     허용된 전이가 아니면 무시. "DELIVERED → IN_TRANSIT"은 규칙에 없다.
  ② 시각/순번 비교: UPDATE ... WHERE occurred_at < :새 이벤트 시각  (조건부 UPDATE)
     단, occurred_at은 "택배사 시계"다 — 신뢰할 수 있나? 같은 값 두 개가 오면?
```

- ①이 더 견고하다 — 남의 시계에 기대지 않는다.\
  ②만 쓰면 시계 오차·동률 처리를 정해야 한다.

> **상태 전이 규칙(state machine)** — 어떤 상태에서 어떤 상태로 갈 수 있는지의 규칙.\
> 예: 역행 이벤트를 걸러낸다.

- 순서를 애초에 보존하는 수단도 있다: 큐를 `tracking_number`로 파티셔닝하면 **같은 배송의 이벤트는 같은 워커로 순서대로** 간다(F).

> **파티셔닝(partitioning)** — 키(예: tracking_number) 기준으로 큐를 나눠 같은 키는 같은 워커로 보내는 것.\
> 예: 키 단위 순서가 보장된다.

> ⚠ 정정(2026-09-28): 파티셔닝만으로 순서가 "애초에 보존"되지는 않는다. 같은 키가 같은 파티션에 모이는 것일 뿐이고, 파티션이 FIFO이며 한 소비자가 직렬 처리하고 재시도도 순서를 지켜야 **큐에 들어온 순서**가 보존된다. 택배사에서 이미 발생 순서가 뒤바뀌어 도착한 이벤트는 되돌리지 못하므로 ①의 전이 규칙 검사는 여전히 필요하다(근거: 원본 CHECKLIST.md:85·124 — 도착 순서와 파티션 배정은 별개 항목).

- AWS DynamoDB 장애(2025-10-19)가 정확히 이 구조 — 지연됐던 프로세스가 뒤늦게 **옛 계획으로 최신을 덮어써서** 리전 엔드포인트 IP가 전부 사라졌다.\
  "오래된 것이 새것을 덮는" 사고는 이만큼 크게 터진다.

### 설계 — 200의 의미: 응답 시간과 유실 (C, D)

**언제 문제가 되나**: 2초 안에 응답해야 하니 수신과 처리를 분리하는데, 그 순간 "200을 줬는데 처리 실패" 구간이 생긴다.

나쁜 계약 → 좋은 계약:

```text
나쁨: 무조건 빨리 200 (큐 적재가 실패해도 200)
  → 택배사는 "전달 완료"로 알고 재전송하지 않는다 = 영구 유실

좋음: 200 = "잃지 않을 곳(큐/DB)에 넣었다"는 보장으로 정의
  큐 적재 성공 → 200   (이후 처리는 우리 책임 — 재시도·DLQ로 수렴)
  큐 적재 실패 → 5xx   (택배사의 재전송이 우리의 안전망이 된다)
```

- 우리가 5xx를 주면 재전송이 온다 — **실패를 숨기지 않는 것이 안전망을 켜는 것**이다.
- 그런데 재전송도 영원하지 않다: **발신 측이 TTL로 이벤트를 버린다.**\
  GitHub 2018 장애에서 TTL 초과 웹훅 약 20만 건이 폐기됐다.\
  웹훅은 best-effort — 정합성이 중요하면 **폴링을 완전히 걷어내면 안 되고** 저빈도 폴링/대사 경로를 남겨야 한다.\
  지문의 "폴링을 걷어낸다"가 함정인 이유.

> **best-effort** — 최선은 다하지만 보장은 없다는 뜻.\
> 예: 발신 측 TTL 초과 시 이벤트는 버려진다.

### 설계 — 인증·처리량·부수효과 (E, F, H)

- **서명 검증(E)**: `X-Carrier-Signature`를 **본문 파싱 전에** 검증(파싱 자체가 공격면).\
  검증 실패는 재전송을 유도하지 않는 4xx로.

> **서명 검증(signature)** — 페이로드가 진짜 발신자의 것인지 공유 비밀로 확인하는 절차.\
> 예: 파싱 전에 한다.

- **처리량(F)**: 하루 50만 건이 피크에 몰린다.\
  느린 택배사 하나가 다른 택배사 이벤트를 막지 않게(head-of-line blocking), 파싱 불가 이벤트 하나가 큐를 막지 않게(poison pill → dead letter).\
  Uber는 DLQ + 비동기 처리로 풀었다.
- **부수효과(H)**: DELIVERED가 구매확정 타이머를 켠다 — 중복 이벤트로 **두 번 켜지면?**\
  타이머 시작도 멱등해야 한다.\
  상태 갱신은 됐는데 타이머 시작이 실패하면?\
  — 같은 트랜잭션이거나 복구 경로가 있어야 한다.\
  알림처럼 되돌릴 수 없는 부수효과는 확정 후 가장 마지막에.
- **관측(I)**: **웹훅이 안 오는 것은 로그에 안 남는다** — "마지막 수신으로부터 N시간" 같은 부재 감지가 필요.\
  중복 비율·dead letter 적체도 지표다.
- **되묻기(J)**: event_id 유일성 범위, occurred_at 신뢰도, 재전송 정책, 상태 전이 규칙.

## 쓰이는 자료구조·알고리즘

- **dedup 집합** — `processed_events`에 `UNIQUE(carrier_id, event_id)`. `event_id`의 전역 유일성이 확인되지 않았으므로 택배사까지 키에 넣는다(원본 CHECKLIST G — 충돌하면 남의 이벤트를 버린다). 유니크 인덱스가 "이미 봤다"를 판정하고, 보관 창은 재전송 기간(24시간)보다 길어야 한다 → [ops-patterns/06-idempotency-store](../../ops-patterns/06-idempotency-store/2-summary.md) · [data-structure/05-hashmap](../../data-structure/05-hashmap/2-summary.md).
- **상태 기계(전이 표)** — 설계 예시: `ACCEPTED → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED / RETURNED`. 원본 지문은 상태 값 다섯 개만 주고 전이 관계는 정하지 않았다 — 중간 상태 생략·반품 경로는 되물어 확정한다(CHECKLIST J). 확정한 허용 전이 집합을 조회해 역행 이벤트를 걸러낸다 → [domain-modeling/basic/11-delivery-tracking](../../domain-modeling/basic/11-delivery-tracking/2-summary.md) · [domain-modeling/basic/09-order-state](../../domain-modeling/basic/09-order-state/2-summary.md).
- **큐 + 키 기반 파티셔닝** — `tracking_number`를 해시해 파티션을 고르면 같은 배송의 이벤트는 같은 파티션에 모인다. 파티션이 FIFO이고 한 소비자가 직렬 처리하며 재시도도 순서를 지키면, **큐에 들어온 순서**가 처리 순서로 보존된다. 발생 순서가 이미 뒤바뀌어 도착한 것은 되돌리지 못하므로 전이 검사는 따로 필요하다 → [data-structure/04-queue-deque](../../data-structure/04-queue-deque/2-summary.md).
- **재시도 큐 + dead letter** — 커리큘럼 🔧: 처리 실패는 백오프 재시도, 상한을 넘으면 DLQ로 격리해 poison pill이 큐를 막지 못하게 한다 → [ops-patterns/01-retry-backoff](../../ops-patterns/01-retry-backoff/2-summary.md).
- **HMAC 서명 검증** — `X-Carrier-Signature: sha256=…`는 흔히 공유 비밀로 만든 HMAC-SHA256 값이다. 다만 헤더 모양만으로 알고리즘·서명 대상(본문만인지, 타임스탬프 등 다른 필드도 포함하는지)을 확정할 수 없으니 택배사 명세를 따른다. 원문 바이트로 파싱 전에 검증하고, 실행 시간 차이를 이용한 공격(타이밍 공격)에 안전한 상수 시간 비교를 쓴다(Java `MessageDigest.isEqual`) — Standard Webhooks 명세도 같은 권고.
  - *HMAC*: 비밀 키와 메시지를 함께 해시해 "비밀을 아는 쪽이 보냈다"를 증명하는 방식.
- **타이머 스케줄** — 구매확정 타이머는 "N일 뒤 실행"의 만료 시각 순 큐(최소 힙 / 만료 시각 인덱스)이며, 잡 키 `(order_id, DELIVERED)`로 중복 등록을 막고, 실행 쪽 부수효과도 멱등해야 한다 → [data-structure/07-heap](../../data-structure/07-heap/2-summary.md) · [ops-patterns/10-scheduler](../../ops-patterns/10-scheduler/2-summary.md).
- **부재 감지 워터마크** — 택배사별 "마지막 수신 시각"을 기록해 "N시간 동안 0건"을 알람으로 만든다. 안 오는 것은 로그에 안 남으므로 시각 비교로 본다. 단 이것은 택배사 **전체**의 무수신만 잡는다 — 다른 이벤트가 계속 오는 중에 일부 배송만 빠진 것은 배송별 갱신 지연 검사("N시간 이상 갱신 없는 배송")·대사로 잡는다.

## 적용 — 풀어나가는 법

수신 API는 방향이 반대다 — 클라이언트가 아니라 **외부가 우리를 재시도**한다. 그래서 설계의 첫 문장은 "재전송 정책이 무엇인가"(at-least-once · TTL)가 된다.\
순서: ① 지문의 재전송 문장에서 중복 · 순서 · 유실 세 축을 뽑는다 → ② 수신(서명 검증 → 큐 적재 → 200)과 처리(dedup → 전이 검사 → 갱신 + 부수효과)를 분리하고 200의 의미를 정한다 → ③ 상태 전이 표를 먼저 쓴다 → ④ "안 오는 것"과 "택배사가 버리는 것"을 잡을 보정 경로(저빈도 폴링 · 대사)를 남긴다.\
아래 과제 목록이 그 훈련의 실제 절차다.

### 문제 — 이 챕터가 시키는 것

## 장애 시나리오와 대처

아래는 우리 시스템 안에서 마주치는 모양이다. 회사 사례는 「실패 사례」 절에 따로 있다.

**1. 구매확정 알림이 두 번 갔다**

- 현상: 고객 한 명에게 구매확정 알림이 2통, 정산에 같은 주문이 두 번 잡힌다.
- 보이는 형태: 같은 `event_id`의 처리 로그 2건 — 서로 다른 인스턴스, 200ms 간격. 타이머 잡이 2개 등록돼 있다.
- 원인: "event_id 조회 → 없으면 처리"의 TOCTOU로 두 인스턴스가 동시에 통과했거나, dedup 기록과 처리를 따로 커밋했다 — 처리는 커밋됐는데 dedup 기록이 실패하면 재전송이 다시 처리된다(중복). 반대로 dedup만 커밋되고 처리가 실패하면 재전송이 막혀 처리 누락이 된다(정답 2번 참고).
- 대처: `INSERT INTO processed_events` UNIQUE와 상태 갱신, 그리고 같은 DB의 타이머 작업 행(또는 outbox 행)을 한 트랜잭션에 묶는다. 외부 스케줄러 등록은 DB 트랜잭션에 들어가지 않으므로 커밋 뒤 outbox로 넘긴다. 타이머 잡 키를 `(order_id, DELIVERED)`로 두어 두 번 등록돼도 하나만 남게 하고, 실행 시 부수효과(확정 처리·알림)도 멱등하게 만든다(정답 6번 참고). 알림은 확정 뒤 맨 마지막에 보낸다.

**2. 배송완료였던 주문이 다시 배송중이 됐다**

- 현상: 구매확정 D-day가 미뤄지고 판매자 정산이 늦어진다는 CS.
- 보이는 형태: 상태 이력 — `DELIVERED`(occurred_at 09:12, 수신 09:13) 다음에 `IN_TRANSIT`(occurred_at 09:05, 수신 09:40).
- 원인: 도착 순서대로 UPDATE했다. 전이 규칙이 없어 완료 상태가 이동중으로 되돌아갔다(정답 3번 참고).
- 대처: 전이 표 검사(`DELIVERED`에서 `IN_TRANSIT`으로는 못 간다)와 조건부 UPDATE로 역행을 막는다. 무시한 이벤트는 버리지 말고 "역행으로 무시됨"으로 기록한다 — 나중에 택배사 데이터 문제를 추적할 근거가 된다.

**3. 특정 택배사 배송 200건이 영원히 배송중이다**

- 현상: 한 시간대에 들어온 배송들이 영영 `IN_TRANSIT`에 멈춰 있다.
- 보이는 형태: 그 시간대 우리 5xx는 0건, 전부 200. 큐 브로커 장애 시간과 정확히 겹친다. 택배사 로그는 "전달 성공".
- 원인: 큐 적재 실패를 삼키고 200을 줬다. 택배사는 전달 완료로 알고 재전송하지 않았다 — 영구 유실(정답 4번 · 5번 참고).
- 대처: 적재 실패는 5xx로 정직하게 돌려 재전송이라는 안전망을 켠다. 적재 실패율을 알람한다. 그래도 발신 측 TTL이 버린 이벤트는 못 받으므로 "N시간 이상 갱신 없는 배송"을 저빈도 폴링으로 보정한다.

**4. 한 택배사의 이상한 메시지 하나가 전체를 30분 막았다**

- 현상: 피크에 모든 택배사의 상태 갱신이 지연된다.
- 보이는 형태: 큐 적체 그래프가 한 방향으로만 자란다. 워커 로그에 같은 메시지의 파싱 예외가 무한 반복.
- 원인: 전체를 직렬로 소비하는 단일 큐 + 실패 메시지를 옆으로 빼지 못하는 재시도 구조(상한 없음) + 포맷이 다른 페이로드(poison pill). 이 조합에서 한 메시지가 큐 맨 앞을 붙잡아 뒤 전체를 막는다(head-of-line blocking). 단일 큐라도 소비자가 여럿이거나 실패 메시지를 분리하면 전체가 막히지는 않는다.
- 대처: 택배사별 큐 또는 파티션으로 격리하고, 재시도 상한을 넘긴 메시지는 DLQ로 보낸다. 정규화 계층에서 스키마 검증에 실패한 페이로드는 즉시 DLQ로 보내고 사람이 본다(정답 6번 참고).

### 실패 사례 — 이 항목들이 나온 실제 사고

- **incident.io**: Pub/Sub이 같은 메시지를 두 컨슈머에 동시 전달 → unique index로 DB가 판정하게 해서 해결.\
  "조회 후 생성"은 방어가 아니다.

> **TOCTOU** — 확인과 사용 사이에 상황이 바뀌어 확인이 무효가 되는 문제.\
> 예: "조회 후 처리"의 함정이다.

- **Segment**: 4주 창에서 이벤트의 0.6%가 중복(모바일 재전송) — 전자상거래 고객에겐 수백만 달러 차이.\
  messageId로 파티셔닝 + 크기 기반 dedup 창(600억 키)으로 해결.
- **CircleCI(2025-12-02)**: 생산자의 사소한 race로 중복 완료 이벤트 → 비멱등 컨슈머가 중복마다 워크플로 생성 → 중복 33,135건.\
  **컨슈머는 언제나 멱등해야 한다.**
- **Grab**: 멱등키를 쓰는데도 중복 지급 — 재시도 단위가 "핸들러 전체"라 재시도마다 **새 멱등키를 생성**했다.\
  재시도는 단계 단위여야 하고 키는 재시도 바깥에서 한 번만.
- **AWS DynamoDB(2025-10-19)**: 지연된 프로세스가 옛 상태로 최신을 덮어씀 — 순서 뒤바뀜의 대형 실증.
- **GitHub(2018)**: 복구 중 웹훅 500만 건 적체, TTL 초과 약 20만 건 폐기 — 발신 측이 버린다.

## 핵심 문장

- "24시간 재전송" 한 줄 = at-least-once 선언 — **중복은 버그가 아니라 스펙이고, dedup은 처리와 같은 트랜잭션이어야 한다.**
- 이 문제의 고유 변별점은 순서다 — **오래된 이벤트가 새 상태를 덮지 못하게** 상태 전이 규칙(또는 순번 비교)으로 막아라.
- 200의 의미를 정의하라 — **큐 적재 실패에 200을 주는 순간 영구 유실이다.**\
  5xx는 재전송이라는 안전망을 켠다.
- 웹훅은 best-effort다 — 발신 측 TTL이 이벤트를 버리므로 **폴링 보정/대사 경로를 완전히 걷어내면 안 된다.**
- 웹훅이 안 오는 것은 로그에 안 남는다 — 부재를 감지하는 관측이 따로 필요하다.

> ⚠ 정정(2026-09-28): 첫 문장의 "at-least-once 선언"은 "중복 가능 선언"으로 읽는다 — 재전송 기간이 24시간으로 유한하므로 전달 자체를 보장하지는 않는다(기간을 넘기면 유실). 근거: 원본 REQUIREMENTS.md:51, CHECKLIST.md:107.

### 용어 풀이

- **웹훅(webhook)**: 사건 발생 시 상대가 우리 URL로 POST를 보내주는 통지 방식. 폴링의 반대.
- **폴링(polling)**: 우리가 주기적으로 "바뀐 것 있어?"라고 물어보는 방식.\
  웹훅의 보정 수단으로도 쓴다.
- **at-least-once**: "최소 한 번은 전달" 보장 — 뒤집으면 "여러 번 올 수 있다".\
  중복 처리(멱등)가 수신자 책임이 된다.
- **멱등성(idempotency)**: 같은 이벤트를 몇 번 처리해도 결과가 한 번과 같은 성질.
- **dedup(중복 제거)**: 이미 처리한 event_id를 기록해두고 재도착을 걸러내는 것.\
  판정은 DB UNIQUE가 한다.
- **TOCTOU**: 확인과 사용 사이에 상황이 바뀌어 확인이 무효가 되는 문제.\
  "조회 후 처리"의 함정.
- **상태 전이 규칙(state machine)**: 어떤 상태에서 어떤 상태로 갈 수 있는지의 규칙.\
  역행 이벤트를 걸러낸다.
- **best-effort**: 최선은 다하지만 보장은 없다는 뜻.\
  발신 측 TTL 초과 시 이벤트는 버려진다.
- **TTL(time to live)**: 보관/재시도 유효 기간.\
  지나면 폐기된다.
- **파티셔닝(partitioning)**: 키(예: tracking_number) 기준으로 큐를 나눠 같은 키는 같은 워커로 보내는 것.\
  키 단위 순서가 보장된다.
- **head-of-line blocking**: 줄 맨 앞의 느린 작업이 뒤 전체를 막는 현상.
- **poison pill**: 처리가 영원히 실패하는 메시지.\
  치우지 않으면 큐 전체를 막는다.
- **dead letter queue(DLQ)**: 재시도해도 실패하는 메시지를 따로 모아두는 곳.\
  버리지 않고 사람이 본다.
- **서명 검증(signature)**: 페이로드가 진짜 발신자의 것인지 공유 비밀로 확인하는 절차.\
  파싱 전에 한다.
- **대사(reconciliation)**: 웹훅으로 만든 상태와 택배사 원본을 맞춰보고 빠진 것을 찾는 작업.
