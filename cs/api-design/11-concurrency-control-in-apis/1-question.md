# api-design/11-concurrency-control-in-apis — 질문

## 질문

1. (왜) 두 클라이언트가 같은 문서를 GET → 수정 → PUT 할 때 생기는 lost update를 시퀀스로 그려라. DB 트랜잭션으로는 왜 이 구간을 못 지키나?
2. (그림) `ETag`·`If-Match`로 이 경합을 막는 흐름을 그려라. 늦게 쓴 쪽은 무엇을 받고, 그다음 무엇을 해야 두 변경이 모두 남나?
3. (경계) 412와 428은 각각 무엇을 뜻하나? 각각 어느 문서가 정의하나?
4. (예측) 현재 ETag가 `"3"`인 자원에 `If-Match: W/"3"`으로 PUT하면 어떻게 되나? `If-None-Match: W/"3"`으로 GET하면? 근거 규칙은?
5. (설계) `If-Match: *`와 `If-None-Match: *`는 각각 언제 참인가? 클라이언트가 ID를 정하는 `PUT /docs/{id}` 생성에서 어느 쪽을 쓰나?
6. (예측) 같은 `If-Match: "1"`을 든 PUT 20개가 동시에 온다. 서버가 (a) 버전을 SELECT로 읽어 비교한 뒤 UPDATE할 때 (b) `UPDATE … WHERE id=? AND version=?` 한 문장으로 할 때, 200은 각각 몇 개 나오나?
7. (연결) RFC 9110, Google AIP-154, Kubernetes는 판 불일치에 각각 어떤 응답을 주나? 클라이언트가 할 일은 어떻게 같은가?
8. (설계) ETag를 버전 카운터로 만들 때와 내용 해시로 만들 때의 장단점은? `Last-Modified`/`If-Unmodified-Since`가 쓰기 경합에 약한 이유는?
9. (장애 진단) 조건부 쓰기를 도입한 뒤 모바일 앱이 같은 PUT을 초당 여러 번 보내며 412를 계속 받는다. 원인과 대처는?
10. (장애 진단) 조건부 쓰기를 붙였더니 PUT이 전부 412다. GET 응답 헤더에서 무엇을 확인하나? 앞단 nginx가 관련될 수 있는 이유는?
