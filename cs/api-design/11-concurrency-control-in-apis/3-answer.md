# api-design/11-concurrency-control-in-apis — 정답

## 정답

### 1. lost update와 DB 트랜잭션의 범위

```text
 Alice  GET {title:초안, tags:a}            Bob  GET {title:초안, tags:a}
 Alice  PUT {title:새 제목, tags:a}  → 200
                                           Bob  PUT {title:초안, tags:a,b} → 200
 최종 {title:초안, tags:a,b}   ← Alice 변경 소실, 에러 없음 (실험 L1)
```

- 각 요청은 짧은 DB 트랜잭션 하나로 끝난다. GET과 PUT 사이(사람이 화면을 보며 고치는 몇 분)에는 열린 트랜잭션이 없다.
- 그 구간에 DB 락을 쥐고 있으면 연결·락을 오래 붙잡아 다른 요청을 막는다. 그래서 요청 사이의 경합은 HTTP 계약(판 표시 + 조건부 쓰기)으로 지킨다.

### 2. ETag + If-Match 흐름

```text
 Alice GET → ETag "1"          Bob GET → ETag "1"
 Alice PUT If-Match "1" → 200, ETag "2"
 Bob   PUT If-Match "1" → 412 (현재 "2")
 Bob   GET → ETag "2", 최신 본문 {title:새 제목, tags:a}
 Bob   자기 변경(tags에 b)을 최신 본문 위에 얹어 PUT If-Match "2" → 200
 최종 {title:새 제목, tags:a,b}   (실험 L2)
```

- 늦은 쪽은 412를 받는다. 같은 ETag로 다시 보내면 계속 412다. 다시 GET해서 최신 판 위에 자기 변경을 얹어야 한다.
- 같은 필드를 둘이 다르게 고쳤다면 자동으로 얹을 수 없다. 사용자에게 충돌을 보여 준다.

### 3. 412 vs 428

- 412 Precondition Failed: 요청이 보낸 조건(`If-Match` 등)이 서버에서 거짓이었다. RFC 9110 §15.5.13.
- 428 Precondition Required: 서버가 이 요청은 조건부여야 한다고 요구한다(조건을 안 보냈다). RFC 6585 §3. lost update를 막으려고 조건 없는 쓰기를 거절할 때 쓰고, 다시 보내는 법을 설명하라고 권한다.
- 실험 L2: 낡은 ETag → 412, If-Match 없음 → 428.

### 4. 약한 ETag

- `If-Match: W/"3"` → **412**(실험 L3). If-Match는 강한 비교를 써야 하고(RFC 9110 §13.1.1 MUST), 강한 비교에서 약한 태그는 무엇과도 일치하지 않는다(§8.8.3.2 표 3: `W/"1"` vs `"1"` 불일치).
- `If-None-Match: W/"3"`으로 GET → 약한 비교라(§13.1.2 MUST) 현재 `"3"`과 일치 → 조건 거짓 → **304 Not Modified**.
- 그래서 약한 ETag는 캐시 검증에는 쓰이지만 조건부 쓰기에는 못 쓴다.

### 5. 별표 조건

- `If-Match: *` — 현재 표현이 있으면 참. "있는 것만 고쳐라". 없을 때 412가 나오는 것은 조건 없이 보냈다면 생성됐을 PUT이다. 원래 404가 될 요청(DELETE·PATCH 등)은 조건을 무시하고 404다(RFC 9110 §13.2.1).
- `If-None-Match: *` — 현재 표현이 없으면 참. "없을 때만 만들어라". 있으면 412.
- 클라이언트가 ID를 정하는 PUT 생성에는 `If-None-Match: *`를 쓴다. 실험 L5: 1차 201, 2차 412. 둘이 동시에 만들어도 하나만 생긴다(서버는 `INSERT … ON CONFLICT DO NOTHING`처럼 원자적으로 해야 한다).

### 6. 검사 방식에 따른 결과

- (a) 검사와 쓰기가 따로(check-then-write, 사이 처리 300ms): 7회 실행에서 200이 **1~14개**(사실 점검 재실행 4회: 1·4·15·3개 — 실행마다 다르다). 같은 판을 든 요청 여럿이 비교를 통과한 뒤 차례로 덮어썼다. 처리 시간 50ms 설정에서는 3회 중 1~2개였다.
- (b) 조건부 UPDATE 한 문장(atomic): 7회 모두 **정확히 1개**, 나머지 19개 412.
- 조건 검사와 쓰기를 한 원자적 연산(CAS)으로 묶어야 HTTP 계약이 서버 안에서도 지켜진다.

### 7. 출처별 불일치 응답

| 출처 | 판 표시 | 불일치 |
|---|---|---|
| RFC 9110 | `ETag` 헤더 / `If-Match` | 412 |
| AIP-154 | 본문 `etag` 필드 | gRPC `ABORTED`(HTTP 대응 409). etag를 안 보내면 허용(should), 필수로 하면 `INVALID_ARGUMENT`(may) |
| Kubernetes | `metadata.resourceVersion` | 409 Conflict |

- 클라이언트 할 일은 같다: 다시 읽고, 최신 판 위에 변경을 다시 적용하고, 새 판으로 다시 쓴다. `google.rpc.Code` 주석도 ABORTED를 "read-modify-write 시퀀스를 처음부터 다시 하라"는 신호로 설명한다.

### 8. ETag 만들기

- 버전 카운터: 쓰기마다 +1. 싸고 인스턴스 간에 같다(DB 값). 같은 내용으로 되돌려도 번호는 오른다(불필요한 412가 생길 수 있음).
- 내용 해시: 같은 내용이면 같은 값. 대신 표현 전체를 해시해야 하고, 압축·필드 순서·인스턴스별 값에 따라 해시가 달라지면 쓸데없는 412가 난다.
- `Last-Modified`는 HTTP 날짜 형식이라 초 단위다. 1초 안의 두 변경을 구분하지 못해 경합을 놓칠 수 있다. 쓰기 경합에는 ETag가 맞다.

### 9. 412 무한 재시도

- 원인: 앱이 412를 받고 다시 GET 하지 않은 채 **같은 ETag**로 재시도한다. 서버의 판은 이미 바뀌었으니 영원히 412다.
- 대처
  - 클라이언트: 412 → 다시 GET → 재적용 또는 충돌 화면. 재시도 상한.
  - 서버: 412 본문(problem+json)에 "다시 GET하라"를 쓴다. 같은 자원·같은 ETag의 연속 412를 지표로 본다.

### 10. 전부 412

- GET 응답의 `ETag`가 `W/"…"`인지 본다. 약한 ETag면 If-Match 강한 비교에서 일치할 수 없다(실험 L3).
- 앞단 nginx가 응답을 압축(gzip)하면 강한 ETag를 약한 것으로 바꾼다(nginx 1.7.3부터, CHANGES). 원 서버는 강한 ETag를 줘도 클라이언트는 약한 것을 받는다.
- 원 서버 응답과 앞단 응답의 ETag를 `curl -i`로 비교한다. 쓰기 대상 자원은 압축 대상에서 빼거나, 조건부 쓰기용 판 표시를 본문 필드(AIP-154 방식)로 준다.
- 인스턴스마다 ETag가 다른지도 본다(GET을 여러 번 해 값이 바뀌는지).
