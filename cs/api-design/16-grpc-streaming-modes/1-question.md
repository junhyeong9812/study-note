# api-design/16-grpc-streaming-modes — 질문

## 질문

1. (그림) 단항·서버 스트리밍·클라이언트 스트리밍·양방향을 화살표로 그리고 `.proto` 선언을 적어라. gRPC가 보장하는 메시지 순서의 범위는?
2. (예측) 서버가 메시지 5개를 보낸 뒤 `onError(UNAVAILABLE)`로 끝낸다. 블로킹 반복자를 `try { ... } catch (StatusRuntimeException ignored) {}`로 감싼 클라이언트는 무엇을 기록하나? 올바른 완료 판정 기준은?
3. (예측) 서버가 100ms마다 1개씩 30개를 보내는 서버 스트리밍에 클라이언트가 데드라인 1초를 건다. 클라이언트는 몇 개를 받고 어떤 상태로 끝나나? 데드라인은 메시지마다인가 호출 전체인가?
4. (경계) 3번에서 서버가 취소를 확인하지 않으면 무슨 일이 생기나? grpc-java 1.72.0에서 취소된 호출에 `onNext`하면 무엇이 나오고, 어떻게 확인·정리하나?
5. (원리) HTTP/2 흐름 제어는 누가 무엇의 크기를 정하나? 어떤 프레임만 창을 소비하고, 초기 창 크기는(RFC 9113)? grpc-java Netty 전송의 기본 창은?
6. (예측) 클라이언트가 10ms마다 1개씩만 요청한다. 서버가 (a) `isReady()`를 무시하고 20,000개×10KB를 `onNext`, (b) `setOnReadyHandler` + `isReady()` 루프로 보낸다. 4초 뒤 클라이언트가 취소할 때 각각 서버가 보낸 수와 메모리는 어떻게 다른가?
7. (경계) 클라이언트 측 `round_robin`을 쓰면 오래 사는 구독 스트림도 서버들에 고르게 퍼지나? 서버 하나를 배포로 내릴 때 무슨 일이 생기고, 무엇으로 대비하나?
8. (장애 진단) 실시간 시세 구독이 일정 간격마다 끊기고 다시 붙는다. 서버 로그에는 `DEADLINE_EXCEEDED`·`CANCELLED`가 같은 간격으로 찍힌다. 원인과 대처는?
9. (적용) 주문 10만 건 내보내기를 설계한다. 단항 + 페이지네이션과 서버 스트리밍 중 무엇을 고르겠나? 서버 스트리밍을 고른다면 서버·클라이언트 코드에 꼭 넣을 것 세 가지는?
