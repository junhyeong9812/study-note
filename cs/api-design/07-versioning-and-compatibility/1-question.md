# api-design/07-versioning-and-compatibility — 질문

## 질문

1. (왜) 서버 배포는 우리가 정하는데, 왜 API 변경 하나하나가 "구 클라이언트와 아직 맞나"라는 질문이 되나? 서버 응답을 바꿀 때 클라이언트 쪽에 필요한 것은 backward 호환인가 forward 호환인가?
2. (분류) 다음 변경을 응답/요청으로 나눠 안전·조건부·파괴로 분류하라 — 응답에 필드 추가, 응답 enum에 값 추가, 응답 필드 삭제, 요청에 필수 필드 추가, 요청 문자열 최대 길이 축소, 금액 필드의 단위를 원에서 전으로 변경.
3. (예측) v1 클라이언트 DTO가 `id`·`amount(long)`·`status{PAID}`이다. 서버가 (a) `memo` 필드 추가, (b) `status="REFUNDED"`, (c) `amount` 삭제를 했다. Jackson 2.19.2 기본 `ObjectMapper`와 Jackson 3.0.0 기본 `ObjectMapper`에서 각각 어떻게 되나?
4. (경계) 클라이언트를 "관대하게" 설정하면 3번의 세 경우가 모두 해결되나? 해결되지 않는 것은 무엇이고 어떻게 막나?
5. (비교) 경로 메이저 버전(`/v1`, AIP-185)과 Stripe의 날짜 버전은 버전을 어디에 두고, 내부 구현을 어떻게 유지하나? 각각 비용은 어디서 생기나?
6. (경계) `Deprecation`과 `Sunset` 헤더는 각각 어느 RFC이고 값 형식은 무엇인가? `Deprecation`이 붙은 응답의 동작은 달라지나? 두 시각 사이의 제약은?
7. (적용) 응답 필드 `amount`를 `{value, currency}` 객체로 바꿔야 한다. 구 클라이언트를 깨지 않는 순서를 단계별로 대라.
8. (장애 진단) v1을 Sunset 날짜에 제거했더니 한 파트너의 배치가 전부 실패했다. 무엇을 빠뜨렸고, 다음에는 무엇을 근거로 제거 시점을 정하나?
9. (연결) Jackson 2 → 3 업그레이드 후 "알 수 없는 필드가 오면 400을 내야 한다"는 요청 검증 테스트가 깨졌다. 무엇이 바뀌었고, 요청 검증과 응답 읽기의 엄격성은 어떻게 따로 정하나?
