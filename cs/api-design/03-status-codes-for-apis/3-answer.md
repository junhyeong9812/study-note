# api-design/03-status-codes-for-apis — 정답

## 정답

### 1. 상태 코드가 따로 중요한 이유

- 본문을 읽지 않는 소프트웨어가 많다. 그들은 상태 코드만으로 행동을 정한다.
  - 재시도 계층(SDK·게이트웨이): 5xx·429·408이면 다시 보낼지.
  - 모니터링: 5xx 비율을 에러율로 셈, 경보.
  - 로드 밸런서·헬스체크: 5xx가 계속되면 대상에서 뺌.
  - 캐시: 404·405·410·501 등은 휴리스틱 캐시 가능(RFC 9110).
  - 클라이언트 SDK: 어떤 예외 타입으로 던질지.
- 상태 코드가 틀리면 이 계층들이 동시에 틀린다. 본문의 에러 상세는 사람과 앱 로직용이다(04).

### 2. RFC 9110의 요구

- 모든 코드를 알 필요는 없지만 첫 자리 분류는 이해해야 한다(MUST). 모르는 코드는 그 분류의 x00으로 다룬다(§15).
- 471 → 400처럼 처리한다. 요청 쪽 잘못으로 보고 같은 요청을 그대로 재시도하지 않는다.
- 100..599 밖의 값은 무효다. 받은 클라이언트는 5xx처럼 처리해야 한다(SHOULD, §15).

### 3. 결정 흐름과 순서

```text
  형식 오류 400 → 인증 401(+WWW-Authenticate) → 권한 403 → 존재 404/410 → 메서드 405(+Allow)
  → 미디어 타입 415 → 의미 검증 422/400 → 전제 조건 412 → 상태 충돌 409 → 속도 제한 429
  → 처리: 200/201/202/204 | 500 | 503
```

- 존재 확인을 권한보다 먼저 하면, 권한 없는 사용자가 403(있음)과 404(없음)의 차이로 자원 존재를 알아낸다.
- AIP-193(회사 지침): 권한을 먼저 검사하고, 권한이 없으면 자원이 있든 없든 403.
- RFC 9110 §15.5.4: 존재를 숨기려는 서버는 403 대신 404를 줄 수 있다(MAY).
- 둘 다 같은 목표(존재 비노출)의 다른 선택이다. 팀이 하나를 골라 일관되게 쓴다.

### 4. 400 vs 422, 충돌

| 상황 | RFC 9110 | Google | Stripe |
|---|---|---|---|
| 수량 -1(문법 OK, 의미 틀림) | 422 | INVALID_ARGUMENT → 400 | 400 |
| 이미 취소된 주문 취소 | 409(현재 상태와 충돌) | FAILED_PRECONDITION → 400 | — |

- 422는 WebDAV(RFC 4918)에서 RFC 9110으로 옮겨 온 코드다. 문법은 맞는데 처리할 수 없는 내용.
- Google은 "상태를 고치기 전에 재시도하지 말라"는 뜻으로 FAILED_PRECONDITION(400)을 쓴다. Stripe는 "매개변수는 유효하지만 요청 실패"에 402를 쓴다(RFC 9110에선 402가 "향후 사용 예약").
- 팀이 할 일: 하나를 골라 매핑 표로 문서화하고 API 전체에서 일관되게 쓴다. 놓치면 안 되는 경계는 4xx/5xx 구분과 재시도 의미다.

### 5. 세 스타일 예측

(실험, JDK 21.0.12)

```text
== CORRECT             서버 도착=13  서버 집계={2xx=8, 4xx=2, 5xx=3}
== OK_WITH_ERROR_BODY  서버 도착=10  서버 집계={2xx=10}
== ALL_500             서버 도착=19  서버 집계={2xx=8, 5xx=11}
```

- (a) 10 + 일시 장애 재시도 3 = 13. 입력 오류는 재시도 없음. 5xx 3건으로 DB 문제가 보인다.
- (b) 10. 재시도 0. 대시보드 2xx 100%인데 실제 실패 5건(HTTP 계층은 성공 10으로 판정). 회복 가능했던 3건도 실패로 끝남.
- (c) 10 + 3 + 입력 오류 2건 × 재시도 3 = 19. 5xx 11건. 입력 오류 2건은 "재시도 소진"으로 끝나 클라이언트가 입력을 고치라는 신호를 못 받는다.

### 6. Google 코드의 재시도 의미

| 코드 | 뜻(`code.proto` 지침) | HTTP |
|---|---|---|
| UNAVAILABLE | 그 호출만 다시 하면 된다(백오프와 함께). 비멱등 연산 재시도는 안전하지 않을 수 있다 | 503 |
| ABORTED | 더 높은 단계부터 다시(예: test-and-set 실패 → 읽기-수정-쓰기 전체 재시작) | 409 |
| FAILED_PRECONDITION | 시스템 상태를 명시적으로 고치기 전엔 재시도하지 말 것(예: 비어 있지 않은 디렉터리 rmdir) | 400 |

### 7. 429와 503

- 429(RFC 6585 §4): 이 클라이언트가 너무 많이 보냄. 설명을 담아야 함(SHOULD), `Retry-After`는 줄 수 있음(MAY). 429 응답은 캐시에 저장하면 안 된다(MUST NOT). 사용자 식별·카운트 방식은 RFC가 정하지 않는다.
- 503(RFC 9110 §15.6.4): 서버가 일시 과부하·점검. `Retry-After` 줄 수 있음(MAY). 과부하라도 503 대신 연결을 거부하는 서버가 있을 수 있다고 RFC가 적는다.
- `Retry-After` 값: HTTP 날짜 또는 0 이상의 초 정수(§10.2.3).

### 8. "입력값을 확인하세요" + 경보 없음

- 잘못된 매핑: 인프라 일시 장애(커넥션 획득 타임아웃)가 catch-all에 걸려 400으로 나갔다.
- 결과: 재시도 계층은 4xx라 재시도 안 함, 5xx 경보 안 울림, 사용자는 잘못된 안내를 받음.
- 수정: catch-all은 500. 커넥션 획득 실패·타임아웃 같은 일시적 예외는 503(+`Retry-After`)으로 따로 매핑. Spring에서 커넥션 획득 실패(`CannotGetJdbcConnectionException`)는 NonTransient 계열이라 `TransientDataAccessException`과 별도로 넣어야 한다. 400 계열은 입력 검증 예외에만.

### 9. 클라이언트 배포 뒤 5xx 급증

- 볼 것
  - 같은 경로·같은 클라이언트의 요청이 짧은 간격으로 3~4번 반복되는가(재시도 흔적).
  - 5xx 로그의 예외 타입이 검증 예외(`MethodArgumentNotValidException`, 도메인 검증 예외)인가.
  - 5xx가 특정 클라이언트 버전(User-Agent)에 몰리는가.
- 원인 가설: 새 클라이언트가 잘못된 입력을 보내고, 서버가 검증 실패를 500으로 응답, 재시도 계층이 이를 반복(실험 c).
- 대처: 검증 예외를 400/422로 매핑. 재시도 예산으로 증폭 상한을 둔다. 클라이언트 쪽 입력 오류를 고친다.
