# api-design/03-status-codes-for-apis — 질문

## 질문

1. (왜) 응답 본문에 에러 상세를 다 적는데도 상태 코드를 제대로 골라야 하는 이유는? 상태 코드만 보고 판단하는 계층을 셋 이상 들어라.
2. (경계) RFC 9110이 클라이언트에게 요구하는 상태 코드 이해 수준은? 모르는 코드 471을 받은 클라이언트는 어떻게 처리해야 하나? 600~999 같은 범위 밖 값은?
3. (그림) "형식 오류 → 인증 → 권한 → 존재 → 메서드 → 의미 검증 → 충돌 → 속도 제한 → 처리" 결정 흐름을 그리고 각 단계의 코드를 붙여라. 권한과 존재 확인의 순서는 왜 중요한가? AIP-193과 RFC 9110 §15.5.4는 각각 어떻게 다루나?
4. (경계) "주문 수량 -1"은 400인가 422인가? "이미 취소된 주문을 취소"는? RFC 9110, Google(`google.rpc.Code` 매핑), Stripe의 선택을 비교하고, 팀은 무엇을 해야 하나?
5. (예측) 요청 10건(입력 오류 2건, 첫 시도만 실패하는 일시 장애 3건)을 "5xx·429면 최대 3번 더 시도" 클라이언트로 보낸다. 서버가 (a) 422/503/201, (b) 전부 200 + 본문 `ok:false`, (c) 입력 오류·일시 장애 모두 500일 때 서버 도착 수와 상태 분류 집계를 예측하라.
6. (연결) `google.rpc.Code`의 UNAVAILABLE·ABORTED·FAILED_PRECONDITION은 각각 어떤 재시도를 뜻하고 HTTP로는 무엇에 대응하나?
7. (경계) 429와 503은 무엇이 다른가? `Retry-After`의 형식과 각 코드에서의 의무 수준(MUST/SHOULD/MAY)은? 429 응답을 캐시해도 되나?
8. (장애 진단) DB 커넥션 풀 고갈 동안 사용자 화면에 "입력값을 확인하세요"가 떴고 서버 경보는 울리지 않았다. 무엇이 잘못 매핑됐나? 어떻게 고치나?
9. (장애 진단) 클라이언트 배포 뒤 서버 5xx가 급증했는데 서버에는 문제가 없다. 접근 로그에서 무엇을 보면 원인을 좁힐 수 있나? 대처는?
