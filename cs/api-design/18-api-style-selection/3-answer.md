# api-design/18-api-style-selection — 정답

## 정답

### 1. 제약으로 고르는 이유

- 스타일은 한번 클라이언트가 붙으면 바꾸기 어렵다. 유행이나 성능 수치로 고르면 "브라우저가 못 부른다", "캐시가 안 먹는다" 같은 제약 위반이 나중에 드러난다.
- 이 노트의 질문
  1. 호출자가 결과를 기다려야 하나? (아니면 메시지 큐·이벤트)
  2. 서버가 먼저 보내야 하나? (SSE·WebSocket)
  3. 누가 부르나? (브라우저·제3자 → REST, 자사 여러 화면 → GraphQL·BFF, 내부 → gRPC)
  4. 공개 조회 캐시가 중요한가? (GET + 캐시 헤더)

### 2. 다섯 모양과 대가

| 스타일 | 모양 | 얻는 것 | 대가 |
|---|---|---|---|
| REST | `GET /orders/1` | 표준 의미·캐시·중간자 | 화면마다 여러 번 왕복, 표준 형태라 비효율 |
| gRPC | `Service.Method(msg)` over HTTP/2 | 강타입·코드 생성·스트리밍 | 브라우저 직접 불가, HTTP 캐시 없음 |
| GraphQL | `POST /graphql {query}` | 클라가 모양 지정, 왕복 1번 | POST면 캐시 불가, N+1·쿼리 비용 관리 |
| WS / SSE | 연결 유지, 서버가 먼저 보냄 | 실시간 푸시 | 열린 연결 관리·재접속 |
| 메시지 큐 | 생산자 → 브로커 → 소비자 | 시간 분리·재처리·팬아웃 | 즉시 결과 없음, 중복·순서 처리 |

- Fielding 2000 5.1.5: 균일 인터페이스는 정보가 앱에 맞춘 형태가 아니라 **표준 형태로 오가므로 효율을 떨어뜨린다**. 대신 큰 단위 하이퍼미디어 전송이라는 웹의 흔한 경우에 최적화했다.

### 3. 캐시 실험 결과

```text
REST  GET  /items/1          MISS HIT HIT HIT HIT
GQL   POST /graphql          - - - - -
GQL   GET  /graphql?query=   MISS HIT HIT HIT HIT
백엔드 도달 횟수: {"GET /items/1":1,"POST /graphql":5,"GET /graphql":1}
```

- REST GET 1번, GraphQL POST 5번, GraphQL GET 1번(nginx 1.31.6).
- 같은 캐시 헤더라도 nginx `proxy_cache_methods` 기본값이 `GET HEAD`라 POST는 캐시 대상이 아니다.

### 4. RFC 9110과 POST 캐시

- 9.2.3: 이 명세는 GET·HEAD·**POST**의 캐시 의미를 정의한다. 다만 **대부분의 캐시 구현은 GET·HEAD만** 지원한다.
- 9.3.3: POST 응답은 **명시적 신선도** + 요청 URI와 같은 값의 **`Content-Location`**이 있을 때만 캐시 가능하다.
  - 그 캐시된 POST 응답은 이후 **GET·HEAD**를 채우는 데만 쓸 수 있다.
  - POST 요청을 캐시된 POST 응답으로 채울 수는 없다 — POST는 안전하지 않을 수 있기 때문이다.
- 그래서 "POST로 조회하고 캐시도 받자"는 실무에서 기대할 수 없다.

### 5. 브라우저와 gRPC

- 직접은 못 부른다. gRPC `doc/PROTOCOL-WEB.md`: 브라우저 제약 때문에 gRPC-Web은 네이티브 gRPC와 다른 프로토콜을 쓰고, 프록시가 변환하는 배치를 전제로 한다.
- grpc-web README 기준
  - 가능: 단항 RPC, 서버 스트리밍(`grpcwebtext` 모드일 때만).
  - 불가: 클라이언트 스트리밍, 양방향 스트리밍.
  - 브라우저 클라이언트는 특별한 프록시(기본 Envoy)를 거친다.

### 6. 폴링 비용 계산(예시)

- 초당 요청 = 10,000 × 1 = 10,000 req/s.
- 평균 감지 지연 ≈ 간격의 절반 = 0.5초 + 처리 시간.
- 간격을 10초로 늘리면 1,000 req/s지만 평균 지연은 5초로 는다 — 부하와 지연을 맞바꿀 뿐이다.
- SSE: 변화가 있을 때만 이벤트를 보내므로 요청 수 비용이 사라지고, 대신 **열린 연결 10,000개**(메모리·파일 디스크립터·프록시 타임아웃·재접속 폭주)를 관리한다.

### 7. 경계별 선택

| 경계 | 흔한 선택 | 근거 |
|---|---|---|
| 외부 공개 API | REST + OpenAPI | 어떤 클라이언트든 부르고, HTTP 캐시·문서 도구를 그대로 쓴다 |
| 자사 앱 → 백엔드 | REST, 화면 조합이 많으면 BFF·GraphQL | 화면마다 필요한 모양이 다르다 |
| 내부 동기 호출 | gRPC(또는 REST) | 강타입 계약·코드 생성·데드라인·스트리밍 |
| 결과를 안 기다리는 후속 작업 | 메시지 큐·이벤트 | 시간 분리·재처리·팬아웃 |

- 표는 "흔한 선택"이다. 팀 역량·기존 도구에 따라 내부도 REST로 통일하는 경우가 있다.

### 8. CDN 적중률 0

- 원인: 공개 조회가 POST라 공용 캐시가 저장하지 않는다(RFC 9110 9.2.3, nginx 기본 `GET HEAD`). nginx 기본 캐시 키(`$scheme$proxy_host$request_uri`)에는 요청 본문이 없어서, POST 캐시를 켜더라도 키를 바꾸지 않으면 본문만 다른 POST를 구분하지 못한다. 키에 본문을 넣는 설정도 가능하지만, RFC 9110 9.3.3은 POST 요청을 캐시된 POST 응답으로 채우지 않는다고 적는다 — 그건 HTTP 캐시가 아니라 프록시 고유 동작이다.
- 대처
  1. 공개 조회는 REST GET 엔드포인트로 따로 연다.
  2. GraphQL을 유지하려면 GET + persisted query(쿼리 해시)로 보낸다 — 실험에서 GraphQL GET은 백엔드 1번이었다.
  - 개인화 데이터는 `Cache-Control: private`로 공용 캐시에서 뺀다.

### 9. 동기 사슬 끊기

- 결제 응답에 결과가 필요 없는 알림·포인트·추천은 **이벤트로 분리**한다. 결제 트랜잭션과 함께 outbox에 쓰고, 브로커로 내보내 각 소비자가 따로 처리한다.
- 대가
  - 결과가 즉시 오지 않는다 — 실패를 호출자가 바로 모른다.
  - 전달 보장(at-least-once면 중복), 순서, 재처리·DLQ를 설계해야 한다([20](../20-messaging-protocols/2-summary.md), distributed 17·18).
