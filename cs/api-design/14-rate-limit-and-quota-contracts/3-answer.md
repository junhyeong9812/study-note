# api-design/14-rate-limit-and-quota-contracts — 정답

## 정답

### 1. 계약 없는 리미터, 쿼터 vs 스로틀

- 계약이 없으면: 클라이언트가 429를 즉시 재시도해 거절 처리 부하가 늘고, 누구 몫으로 세는지 몰라 NAT 뒤 사용자들이 같이 막히며, 언제 다시 보내야 할지 모른다.

| | 요금제 쿼터 | 보호용 스로틀 |
|---|---|---|
| 목적 | 쓸 권리(사업) | 시스템 보호 |
| 창 | 일·월 | 초·분·동시 실행 수 |
| 넘으면 | 다음 주기까지 막힘, 업그레이드 안내 | 짧은 `Retry-After` 뒤 다시 가능 |
| 예 | Stripe 읽기 할당(거래당 500, 30일) | Stripe 초당 100건, 동시 실행 한도 |

### 2. RFC 6585 §4

- 정하는 것: 429 = 주어진 시간에 너무 많이 보냈다. 응답에 상황 설명을 담아야 한다(SHOULD). `Retry-After`를 담을 수 있다(MAY). 429 응답은 캐시에 저장하면 안 된다(MUST NOT).
- 정하지 않는 것: 서버가 사용자를 어떻게 식별하고 어떻게 세는지.
- `Retry-After`는 필수가 아니다. 그래서 계약에서 넣는 것을 기본으로 정해 둬야 한다.
- 429 = 이 클라이언트가 많이 보냈다. 503 = 서버가 지금 처리할 수 없다(과부하·점검, RFC 9110 §15.6.4). nginx `limit_req`의 기본 거절 코드는 503이라 클라이언트별 제한이면 429로 바꾼다.

### 3. 실험 A

- 무시: 3.0초(여러 실행에서 3.0~3.1초), 서버가 받은 요청 84(실행에 따라 85), 그중 429 64(65).
- 준수: 3.2초, 받은 요청 23, 그중 429 3.
- 이유: 성공 속도는 토큰 충전 속도(초당 5)가 정한다. 일찍 다시 보내도 토큰이 없으면 거절될 뿐이다. 무시는 시간을 거의 줄이지 못하고 요청만 약 3.7배로 늘렸다.

### 4. 실험 B

- IP 키: 앞의 100건(약 33명분)만 통과해 267명이 한 번 이상 429를 받는다.
- API 키: 사람마다 3건이라 0명.
- 그래서 인증된 요청은 API 키·사용자·테넌트로 센다.

### 5. RateLimit 헤더

- `RateLimit-Policy: "burst";q=100;w=60` = 정책 이름 burst, 60초 창에 100 단위 할당.
- `RateLimit: "burst";r=50;t=30` = burst 정책에서 지금 50 남았고, 30초 안에 그 이상 쓰지 말라.
- 정의 문서: IETF `draft-ietf-httpapi-ratelimit-headers-11`(2026-05, 초안). RFC가 아니다.
- 하면 안 되는 가정: 양수 `r`이면 다음 요청이 성공한다(보장 아님). 다음 응답에도 이 헤더가 온다(MUST NOT 가정). 형식이 틀린 헤더는 무시해야 한다.
- `Retry-After`가 함께 오면 `Retry-After`가 우선한다(MUST).

### 6. reset 시각 vs 남은 초

- GitHub `x-ratelimit-reset`: 창이 리셋되는 **시각**(UTC 유닉스 초). 실측 값 `1791058648`.
- 초안 `t`: 남은 **초 수**.
- 초안의 이유(4.1.2): 클라이언트·서버 시계 동기화에 기대지 않고, 같은 시각에 너무 많은 클라이언트가 몰리는 것(thundering herd)을 줄인다.

### 7. 헤더 없는 Stripe 429, GitHub 상태 코드

- Stripe 문서: 속도 제한 429에는 `Stripe-Rate-Limited-Reason`이 붙는다. 없으면 속도 제한이 아니다. 객체 잠금 타임아웃(`lock_timeout`)을 의심한다.
- 대처: 같은 객체에 대한 변경을 직렬화하거나 속도를 낮추고, 지수 백오프로 재시도한다. Stripe는 이 실패 요청을 처리하지 않았다고 적는다.
- GitHub: 1차·2차 한도 초과에 403 또는 429를 쓴다(1차는 `x-ratelimit-reset`까지, 2차는 `retry-after` → reset → 최소 1분 순으로 기다리라고 한다). 그래서 GitHub 클라이언트는 403도 한도 헤더와 함께 확인해야 한다.

### 8. 로그인 장애

- 원인: `/login` 전체에 한도 하나를 걸어, 공격 트래픽이 정상 사용자의 몫까지 다 먹었다.
- OWASP: 실패 카운터는 IP가 아니라 **계정**에 붙인다(여러 IP로 나눠 공격하는 것 대비). 잠금 정책은 임계 횟수·관찰 창·잠금 기간을 함께 정한다. 고정 기간 대신 짧게 시작해 실패마다 두 배로 늘리는 지수 잠금도 소개한다("일부 애플리케이션이 쓰는" 방식). 잠금이 남의 계정을 잠그는 서비스 거부 수단이 되지 않게 주의하라고 하고, 예로 잠긴 계정도 비밀번호 찾기로는 들어올 수 있게 하는 방법을 든다.
- 더하기: IP별 한도, 봇 판별, 계정별·IP별 정책을 나눠 응답에 어떤 정책인지 남긴다.

### 9. 테넌트 공정성

- 공유 100건: A 99건, B 1/10 성공(실험 C).
- 테넌트별 50건: A 50건, B 10/10.
- 알아보는 법: 전역 한도 429를 테넌트별로 쪼개 보면, 여러 테넌트가 429를 받는데 사용량 상위 1개가 대부분을 쓰고 있다.
- 대처: 테넌트별 한도 + 전역은 최후 보호선, 대량 작업은 별도 큐·낮은 우선순위(벌크헤드).

### 10. 쿼터 소진을 과부하처럼 응답

- 잘못: 쿼터 초과와 스로틀을 같은 429 + `Retry-After: 1`로 줬다. 클라이언트는 "곧 풀린다"로 읽고 계속 재시도한다.
- 고치기: 쿼터 초과는 다음 주기 시작까지의 `Retry-After`(초 또는 HTTP-date), `quota-exceeded` 문제 유형과 넘은 정책 이름, 업그레이드 안내를 준다. SDK는 정책 종류에 따라 재시도를 멈춘다.
