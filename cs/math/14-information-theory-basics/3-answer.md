# math/14-information-theory-basics — 정답

## 정답

### 1. 엔트로피와 접두 부호

- `H = 0.5×1 + 0.25×2 + 0.125×3 + 0.125×3 = 1.75` 비트/기호.
- 부호: `0`, `10`, `110`, `111`. 평균 길이 = 0.5×1 + 0.25×2 + 0.125×3×2 = 1.75. 확률이 모두 2의 거듭제곱이라 정확히 H와 같다.
- 크래프트: `2⁻¹ + 2⁻² + 2⁻³ + 2⁻³ = 1 ≤ 1`. 접두 부호가 존재한다.

### 2. 원천 부호화 정리의 전제

- 전제(한 기호 엔트로피 H를 한계로 쓰는 기본형): 기호가 **독립·동일 분포**로 나오고, 부호를 그 **분포에 맞춰** 만든다. 그때 복호 가능한 부호의 기호당 평균 길이는 H 이상이고, 여러 기호를 묶어 부호화하면 H에 얼마든지 가까워진다(Shannon 1948).
- 이 전제가 정리의 유일한 형태는 아니다. 기억 있는 원천은 엔트로피율이 한계이고(Shannon 1948 정리 9), 분포를 몰라도 보편 부호(LZ77)가 그 한계에 다가간다(Ziv·Lempel 1977).
- 깨지는 방식
  - 기억이 있다: 텍스트는 앞 글자가 다음 글자를 예측하게 한다. 진짜 한계는 엔트로피율이고 H₀보다 작다.
  - 분포를 모른다: 압축기는 데이터를 보며 분포를 추정한다(보편 부호). 짧은 데이터에서는 추정 비용(부호표·헤더)이 크다.

### 3. H₀ 하한 vs gzip

- 텍스트: gzip이 **더 작다.** 10,458 B로 H₀ 하한(20,411 B)의 0.51배다. LZ77이 반복 문자열(문맥)을 쓰기 때문이다. H₀는 텍스트의 한계가 아니다.
- 무기억 4기호: gzip이 **더 크다.** 263,115 B로 H₀ 하한(218,609 B)의 1.20배다. 이 원천에서는 H₀가 진짜 한계이고 DEFLATE가 거기 못 미친다. 매치를 끈 허프만만으로도 234,539 B라, 초과분은 블록 끝 기호가 낀 정수 비트 부호(약 7%)와 쓸모없는 짧은 매치(약 12%)에서 온다(해석).
- 출력은 `entropy.py` 실험(Python 3.12.3)과 같다.

### 4. 모든 입력을 줄일 수는 없다

- n비트 입력은 2ⁿ개, n비트보다 짧은 출력은 2⁰ + … + 2ⁿ⁻¹ = 2ⁿ − 1개다. 무손실이면 서로 다른 입력이 서로 다른 출력으로 가야 하므로, 적어도 하나는 줄지 않는다(비둘기집).
- 더 나아가 k비트 이상 줄어드는 입력은 2^(1−k) 비율 미만이다. 무작위 입력은 거의 줄지 않는다.
- 실험: 1,000,000 B `os.urandom` → gzip 1,000,328 B. **328바이트 커졌다.** `.gz`를 다시 gzip해도 10,458 → 10,481 B로 23바이트 커졌다.

### 5. 최소 거리와 능력

- 검출 d_min − 1개, 정정 ⌊(d_min − 1)/2⌋개.
- 패리티 1비트: d_min = 2 → 1비트 검출, 정정 0.
- 해밍(7,4): d_min = 3 → 1비트 정정 **또는** 2비트 검출(둘을 동시에는 못 한다).
- 확장 해밍(8,4) SECDED: d_min = 4 → 1비트 정정 **그리고** 2비트 검출.
- 실험(`Codes.java`)에서 최소 거리를 전수로 세면 3과 4가 나왔다.

### 6. 해밍(7,4)의 2비트 오류

- 신드롬은 두 오류 위치 번호의 XOR가 되어 0이 아니다. 복호기는 그 값을 "1비트 오류 위치"로 믿고 **세 번째 비트를 뒤집는다.**
- 결과는 원래와 다른 부호어다. 실험: 336가지 중 **0개** 올바르게 복원, 336개 전부 잘못 고침.
- 오류 표시 없이 틀린 데이터가 나간다. 그래서 2비트 검출이 필요한 곳은 SECDED를 쓴다(실험: 448가지 전부 "정정 불가"로 검출).

### 7. CRC의 보장과 어림

- 보장(Peterson & Brown 1961): 생성 다항식이 차수 r이고 상수항이 있으면, 길이 r 이하의 버스트 오류를 **모두** 검출한다.
- 무작위로 크게 망가진 메시지의 미검출 확률 ≈ 2^(−r). 오류 패턴이 고르게 무작위(신드롬이 거의 균등)라는 가정 아래의 근사다. 길이가 정확히 r+1인 버스트는 2^(−(r−1))이다.
- CRC-8로 100만 번이면 약 100만/256 ≈ 3,906건을 놓친다고 어림한다. 실험은 3,773건(0.377%)이었다. 조금 낮은 것은 표본 잡음이다. 시드만 바꾸면 3,825~3,984건으로 3,906의 위아래에 흩어진다(표준편차 약 62건).
- CRC-32 실험(64바이트 메시지)은 1비트·2비트 오류 전부, 길이 ≤ 32 버스트 20만 건 전부를 검출했다.

### 8. 재압축으로 커진 응답

- 원인: 이미지(JPEG·PNG)·동영상·압축 파일은 반복·치우침이 거의 남지 않았다(H₀도 8비트/바이트에 붙어 있다 — 다만 H₀ = 8만으로는 압축 불가를 판단하지 못한다). 무손실 압축은 이런 입력을 대개 줄이지 못하고(4번), gzip 헤더·꼬리와 블록 비용만 더한다. 압축 CPU만 쓴다.
- 대처: 콘텐츠 타입 제외 목록을 둔다. 작은 응답은 문턱 이하이면 압축하지 않는다. 판단은 H₀가 아니라 실제 표본 압축 비율로 한다.

### 9. 체크섬 비트 수와 위조

- 계산: 기대 미검출 수 ≈ (손상된 블록 수) × 2^(−r). 예: 손상 블록 10¹⁰개면 CRC-32로 약 2.3개(예시 계산). 이것이 감당 못 할 수준이면 r을 늘리거나(CRC-64·암호학적 해시) 종단 다이제스트를 더한다.
- 손상 블록 수는 "전체 블록 수 × 손상률"이다. 규모가 커질수록 작은 확률이 실제 건수가 된다.
- 위조 가능성이 있으면 CRC는 쓸모없다. CRC는 선형이고 키가 없어 공격자가 맞출 수 있다. HMAC이나 서명을 쓴다([algorithm/12](../../algorithm/12-hash-functions/2-summary.md), [security/05](../../security/05-mac-and-hmac/2-summary.md)).
