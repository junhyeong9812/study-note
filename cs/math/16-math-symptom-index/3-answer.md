### 2. 합계 차이의 네 모양

- 마지막 한 건 값
  - 원인: off-by-one — 루프 경계 `i < n - 1`, 불변식이 종료 시 전체를 말하지 않음([02-1](../02-induction-and-invariants/2-summary.md)).
  - 확인: 길이 0·1·2 입력으로 합 비교.
- 작은 소수(예: 1.969×10⁻⁴)
  - 원인: 큰 누적값에 작은 항을 더할 때의 반올림 누적([15-1](../15-numerical-stability/2-summary.md)).
  - 확인: 같은 데이터를 `BigDecimal`이나 `long` 최소 단위로 다시 합해 비교.
- 병렬도·파티션 수마다 마지막 자리가 다름
  - 원인: 부동소수 덧셈은 결합법칙이 없다 — 덧셈 나무가 바뀜([15-2](../15-numerical-stability/2-summary.md)).
  - 확인: 병렬도 1과 여러 값에서 결과 비교(leaf 실험: 1·3·7·15에서 네 가지 값).
- 차이 = 조건 열이 NULL인 행 수
  - 원인: SQL 3치 논리 — `P`와 `NOT P`가 둘 다 UNKNOWN([01-4](../01-propositional-logic/2-summary.md)).
  - 확인: `count(*) FILTER (WHERE col IS NULL)`과 차이 비교.

### 3. 77,163행의 생일 어림

- 균일 가정에서 P ≈ 1 − exp(−k(k−1)/2N), N = 2^32 → 약 0.5(실행 출력 `32bit k=77,163: 0.500`, [05](../05-counting-and-birthday-bound/2-summary.md)의 정확값 0.5000).
- 행 수 두 배: 충돌 쌍의 기대 수 k(k−1)/2N은 k²에 비례하므로 약 4배.
- 관측이 차수 이상 잦으면 비트 수보다 **생성기**를 먼저 의심한다. 같은 시드(상수·시작 시각)면 인스턴스들이 같은 수열을 되풀이하고, 엔트로피가 부족하면 서로 다른 수열이 시드 수만큼뿐이다([05-3](../05-counting-and-birthday-bound/2-summary.md), [12-1](../12-randomness-and-prng/2-summary.md), Debian 2008은 [17](../17-math-incidents/2-summary.md) 사건 1).

### 4. `Math.abs(h) % n`의 남은 구멍

- 2의 보수 `int`에서 −MIN_VALUE는 표현할 수 없어 `Math.abs(Integer.MIN_VALUE)`가 −2147483648 그대로다. 나머지가 음수로 남아 `Index -8 out of bounds for length 10` 같은 예외가 난다([11-3](../11-modular-arithmetic/2-summary.md)).
- 균일 해시라면 해시값 2^32개 중 1개(`Integer.MIN_VALUE`)에서만 나므로 아주 드물다.
- `floorMod`로 바꿀 때: `& 0x7fffffff`나 `abs` 방식과 결과가 다른 키가 있다. 이미 그 규칙으로 저장된 데이터의 재배치를 함께 계획한다.

### 5. ρ/(1−ρ)

- Wq = ρ/(1−ρ) · E[S]: ρ 0.8 → 4, 0.9 → 9(실행 출력 `4.0 -> 9.0`, leaf 시뮬레이션 3.98~4.05 → 8.83~9.17). 0.6 → 1.5, 0.95 → 19.
- 전제: 포아송 도착, 지수 서비스 시간(서로 독립·동일 분포, 도착과 독립), 정상 상태(ρ < 1, 장기 평균).
- 쓸모 있는 이유: P-K 식 Wq = λ·E[S²] / (2(1 − ρ))(포아송 도착, E[S²] 유한)처럼 다른 서비스 분포에서도 분모에 1 − ρ가 있어, ρ가 1에 다가가면 대기가 급격히 커지는 모양이 유지된다. 수치는 어림이고 확정은 부하 테스트로 한다([10](../10-queueing-and-littles-law/2-summary.md)).

### 6. 지연 악화의 네 갈래

- 큐잉(10-1): 트래픽이 10~20%만 늘었는데 이용률이 80~90%대이고 지연이 몇 배.
- 서비스 시간 분산(10-3): 평균 처리 시간은 그대로인데 같은 풀의 짧은 요청 p99가 오르고, 느린 작업 시간대와 겹친다.
- 버스트 도착(09-1): 분당 지표는 평온하고 초 단위에서 스파이크, 초 단위 카운트의 분산/평균이 1보다 훨씬 크다.
- 평균만 본 꼬리(08-1): 평균은 SLO 안인데 p99가 수백 ms — 히스토그램 백분위로 본다.

### 7. `useLegacyMergeSort`가 남긴 것

- 비교자의 추이성 위반이 그대로 남는다. 예외는 위반을 우연히 만났을 때의 증상이었고, 예외 없이 끝난 실행도 역전 쌍이 있는 틀린 순서였다([03-2](../03-sets-relations-orders/2-summary.md)의 `Near.java`).
- 구현 경계: OpenJDK TimSort는 길이 32 미만이면 병합 없이 이진 삽입 정렬로 끝내 계약 위반 예외를 던질 기회가 없다(`MIN_MERGE = 32`, [algorithm/09](../../algorithm/09-sorting-in-practice/2-summary.md)). 31개 이하 테스트로는 예외가 0회였다.

### 8. 공통 원인과 전제 표기

- 공통 원인의 예: 정각 cron·배포·한 AZ 장애. 같은 순간에 요청이 몰리고(포아송 붕괴), 같은 AZ 복제본이 함께 내려가고(독립 붕괴), 같은 시각에 뜬 인스턴스가 같은 시드를 쓴다(균일 붕괴).
- 괄호에 전제를 적는 이유: 식은 전제 안에서만 값을 준다. 전제를 같은 줄에 두면, 어림과 관측이 차수 단위로 어긋날 때 "식이 틀렸다"가 아니라 "어느 전제가 깨졌나"로 바로 넘어갈 수 있다(7절, 장애 5).
