# math/17-math-incidents — 실사건: Debian OpenSSL PRNG(2008) · Java 7 TimSort 계약 위반 예외 · TimSort 자체 버그의 형식 검증 발견(de Gouw 외 2015) — 수학 관점 — 정리 (힌트)

## 해결하는 문제

세 사건은 모두 **수학 전제 하나가 코드 속에서 조용히 깨진** 경우다.

```text
  Debian 2008       "키는 큰 공간에서 균일하게 뽑힌다"   ── 엔트로피 입력 줄이 주석 처리됨 ──▶ 시드 = PID 뿐 → 아키텍처당 난수 흐름 32,767개
  Java 7 TimSort    "비교자는 전전순서다"               ── 정렬 구현이 바뀌어 위반을 검사 ──▶ 오래된 비교자들이 IllegalArgumentException
  de Gouw 외 2015   "run 스택 불변식이 늘 성립한다"      ── 위 3개만 검사해 아래가 깨짐 ──────▶ 특정 입력에서 ArrayIndexOutOfBoundsException
```

쉬운 예: 자물쇠 번호 다이얼이 4자리(1만 가지)라고 믿었는데, 공장 실수로 앞 3자리가 늘 0으로 고정돼 있었다.\
자물쇠는 잘 잠기고 잘 열린다. 겉으로는 아무 문제가 없다. 다만 도둑이 10번만 돌려 보면 열린다.

똑같은 구조다.\
Debian의 키 생성기는 키를 잘 만들었다. 서명도 검증도 됐다. 다만 만들 수 있는 키의 **개수**가 무너져 있었다.\
Java의 옛 정렬은 잘못된 비교자로도 조용히 무언가를 돌려줬다. 새 정렬은 그 위반을 발견하면 예외로 알렸다.\
TimSort는 수년간 수십억 기기에서 정렬을 했다(블로그: "well into the billions"). 증명을 시도하자 "늘 성립한다"던 불변식이 깨지는 입력이 나왔다.

실무 예:
- 난수·ID·토큰을 만드는 코드는 결과만 봐서는 품질을 알 수 없다. 값이 "무작위처럼 보이는" 것과 공간이 큰 것은 다르다([12-randomness-and-prng](../12-randomness-and-prng/2-summary.md)).
- `compare`·`equals`처럼 수학 공리를 요구하는 계약은 라이브러리가 바뀌면 그동안 숨어 있던 위반이 드러난다([03-sets-relations-orders](../03-sets-relations-orders/2-summary.md)).

  - *1차 출처*: 당사자가 직접 쓴 문서 — Debian 보안 공지, NVD, Debian 위키, Oracle 호환성 노트, OpenJDK 버그 DB, 논문·저자 블로그. 이 노트는 날짜·수치를 원문 그대로 옮기고, 원문에 없는 연결은 "해석"이라고 표시한다.
  - *키 공간*: 생성기가 만들 수 있는 서로 다른 키의 개수. 키 길이(예: 2048비트)와 다르다. 길이가 길어도 시드가 작으면 공간은 시드 개수 이하다([05-counting-and-birthday-bound](../05-counting-and-birthday-bound/2-summary.md)).

## 동작·원리

### 사건 1 — Debian OpenSSL 예측 가능한 난수 (도입 2006-09-17 · 공지 2008-05-13)

출처
- Debian Security Advisory DSA-1571-1 "openssl — predictable random number generator", 2008-05-13 <https://lists.debian.org/debian-security-announce/2008/msg00152.html>(2026-10-07 열람).
- NVD CVE-2008-0166, 게시 2008-05-13 <https://nvd.nist.gov/vuln/detail/CVE-2008-0166>(NVD API로 열람).
- Debian 위키 "SSLkeys" <https://wiki.debian.org/SSLkeys>(2026-10-07 열람 — 위키라 누구나 고칠 수 있는 문서다. 이 노트의 32,767은 이 페이지에서 옮겼다).

#### 사실 (원문)

- DSA-1571: "Luciano Bello discovered that the random number generator in Debian's openssl package is predictable. This is caused by an incorrect Debian-specific change to the openssl package (CVE-2008-0166). As a result, cryptographic key material may be guessable."
- 첫 취약 판: "The first vulnerable version, 0.9.8c-1, was uploaded to the unstable distribution on 2006-09-17, and has since propagated to the testing and current stable (etch) distributions." 고친 판은 etch 0.9.8c-4etch3, sid·lenny 0.9.8g-9.
- 권고: "all cryptographic key material which has been generated by OpenSSL versions starting with 0.9.8c-1 on Debian systems is recreated from scratch." 그리고 "all DSA keys ever used on affected Debian systems for signing or authentication purposes should be considered compromised".
- 영향 키: SSH·OpenVPN·DNSSEC 키, X.509 인증서용 키, SSL/TLS 세션 키. GnuPG·GNUTLS로 만든 키는 영향 없음.
- NVD 설명: "OpenSSL 0.9.8c-1 up to versions before 0.9.8g-9 on Debian-based operating systems uses a random number generator that generates predictable numbers, which makes it easier for remote attackers to conduct brute force guessing attacks against cryptographic keys."
- Debian 위키: "The broken version of OpenSSL was being seeded only by process ID." 출력은 아키텍처(리틀 엔디언 32비트·리틀 엔디언 64비트·빅 엔디언 32비트)마다 달랐고, "PID 0 is the kernel and PID_MAX (32768) is not reached when wrapping, so there were 32767 possible random number streams per architecture. This is (2^15-1)*3 or 98301."
- 위키가 적은 원인: `md_rand.c`의 같은 줄 두 개 `MD_Update(&m, buf, j);`가 valgrind 경고를 없애려고 2006년에 주석 처리됐다. 그중 `ssleay_rand_bytes`의 줄은 지워도 큰 영향이 없었지만, `ssleay_rand_add`의 줄은 엔트로피를 풀에 넣는 입력 경로였다 — "Failing to call MD_Update there means that the pool will never actually get the entropy intended for it."

#### 원리 — 세기: 키 길이가 아니라 시드 개수가 공간이다

```text
  정상:   /dev/urandom ─┐
          PID ─────────┼─▶ [엔트로피 풀] ─▶ PRNG ─▶ 2048비트 RSA 키      공간: 시드 엔트로피가 정함(충분히 큼)
                       │
  Debian 패치 뒤:  PID ─┴─▶ [엔트로피 풀] ─▶ PRNG ─▶ 2048비트 RSA 키      공간 ≤ PID 개수 = 32,767
                    (ssleay_rand_add의 MD_Update 줄이 꺼져                 (아키텍처·키 종류·길이별로)
                     urandom 엔트로피가 풀에 안 들어감)                    (~/.rnd 유무 같은 입력 상태별로도)

  32,767 = 2^15 − 1  →  약 15비트          2^128 과 비교하면 32,767 / 2^128 ≈ 9.6 × 10^-35
```

- 곱 법칙·함수의 상(像): 결정적 함수 f(시드)가 만드는 키의 개수는 시드 개수를 넘지 못한다([05](../05-counting-and-birthday-bound/2-summary.md) 1절, [03](../03-sets-relations-orders/2-summary.md) 1절). 키를 2048비트로 늘려도 공간은 그대로다.
  - *시드*: PRNG의 초기 상태를 정하는 입력. 같은 시드면 같은 수열이 나온다([12](../12-randomness-and-prng/2-summary.md) 4절).
- 결과 두 가지(해석)
  - **열거 공격**: 공격자는 32,767개(아키텍처별) 키를 미리 다 만들어 둔다. 남의 공개키·지문을 보고 표에서 찾으면 개인키가 나온다. Debian이 약한 키 검출기(`dowkd.pl`)를 낸 것도 같은 원리다 — 가능한 키를 다 알기 때문에 목록과 대조할 수 있다.
  - **생일 충돌**: 서로 다른 서버가 같은 키를 갖는다. 서버 k대가 N = 32,767칸에 떨어지면 같은 키 쌍의 기대 수는 C(k, 2)/N이다(PID가 균일하다는 가정에서 — 실제 PID는 부팅 직후 작은 값에 몰려 더 자주 겹친다고 볼 수 있다. 해석).
- DSA 서명 쪽은 키 생성이 아니라 **서명마다** 쓰는 비밀 난수가 약해져 키가 샌다. DSA-1571이 "ever used ... for signing"까지 손상으로 본 이유다. 수식은 [security/06-public-key-and-signatures](../../security/06-public-key-and-signatures/2-summary.md) §5.

#### 실험 A: PID만으로 시드된 생성기 — 열거와 충돌 (`PidKeys.java`)

**모형**이다. OpenSSL 코드가 아니라, "시드가 PID(1~32,767)뿐인 PRNG가 128비트 키를 만든다"를 `java.util.Random(pid)`로 흉내 냈다. 지문은 키의 SHA-256 앞 8바이트.

```java
static byte[] keyFromPid(int pid) { Random r = new Random(pid); byte[] k = new byte[16]; r.nextBytes(k); return k; }
// A. 공격자: 지문 하나를 보고 pid = 1..32767 을 전부 시도
for (int pid = 1; pid < 32768; pid++) if (fp(keyFromPid(pid)).equals(target)) { found = pid; break; }
// B. 서버 k대가 PID 를 1..32767 에서 균등하게 골라 키 생성 → 같은 키 쌍 수, 서로 다른 키 수 (200회 평균)
```

(실험, eclipse-temurin:21-jdk = OpenJDK 21.0.12, docker `--network none --cpus=2`, `java PidKeys.java`, 2026-10-07 — 세 번 실행, A의 시간은 실행마다 다르다)

```text
A. 지문 하나 → PID 23456 복원, 시도 23,456회, 315 ms
   가능한 키 전부의 지문 표: 32,767개, 139 ms (서로 다른 지문 32,767개)
B. 서버    100대: 같은 키 쌍 평균       0.1 (이론 C(k,2)/N =       0.2), 서로 다른 키 평균     99.9 (이론     99.8), 충돌≥1 근사 0.1402
B. 서버  1,000대: 같은 키 쌍 평균      15.5 (이론 C(k,2)/N =      15.2), 서로 다른 키 평균    984.7 (이론    984.9), 충돌≥1 근사 1.0000
B. 서버 10,000대: 같은 키 쌍 평균    1525.9 (이론 C(k,2)/N =    1525.8), 서로 다른 키 평균   8619.3 (이론   8618.3), 충돌≥1 근사 1.0000
C. 키 공간 비율: 32,767 / 2^128 = 9.629e-35, log2(32,767) = 15.00비트
```

다른 두 실행의 A: 복원 266·295 ms, 표 148·129 ms(B·C는 시드 고정이라 같은 값). 사실 점검 재실행(같은 명령, 다른 컨테이너와 동시에 돈 호스트): 복원 366 ms, 표 259 ms, B·C는 위와 같은 값.

- 관찰
  - A: 가능한 키 32,767개 전부의 지문 표를 만드는 데 129~259 ms, 지문 하나에서 PID를 찾는 데 266~366 ms(첫 시도라 JIT 예열 포함)였다(이 제한 환경, 집필 세 번 + 사실 점검 한 번 — 호스트 부하에 따라 흔들림). 128비트 키 길이는 방어가 되지 않았다. 공간이 15비트이기 때문이다.
  - B: 시뮬레이션(200회 평균, 시드 고정)이 이론 C(k,2)/N과 서로 다른 키 수 N(1 − (1 − 1/N)^k)에 맞았다. 서버 1,000대면 같은 키 쌍이 15개쯤, 1만 대면 1,500개쯤 생긴다.
  - "충돌≥1 근사" 1 − exp(−k(k−1)/2N)은 k = 1,000에서 이미 1.0000(소수 넷째 자리 반올림)이다. 32비트 공간에서 7.7만 개에 50%였던 것([05](../05-counting-and-birthday-bound/2-summary.md))이 15비트 공간에서는 약 213개에 50%가 된다(√(2 ln 2 · 32,767) ≈ 213, 계산).
- 한계: 실제 OpenSSL 키 생성은 아키텍처·키 종류·길이별로 따로 공간이 생기고(같은 PID라도 `~/.rnd` 파일 유무에 따라 다른 키가 나왔다는 당시 보고 — debian-security 2008-05 <https://lists.debian.org/debian-security/2008/05/msg00271.html>), 실제 PID 분포는 균등하지 않다. 이 실험은 "시드 공간 = 키 공간"이라는 세기의 결론만 보인다.

### 사건 2 — Java 7의 TimSort가 계약을 어긴 비교자를 드러냄 (JDK 7 GA 2011-07-28)

출처
- Oracle, "Java SE 7 and JDK 7 Compatibility" — 「Incompatibilities between JDK 7 and JDK 6」 절의 정렬 항목 <https://www.oracle.com/java/technologies/compatibility.html>(2026-10-07 열람).
- JDK-6804124 "(coll) Replace "modified mergesort" in java.util.Arrays.sort with timsort" — Enhancement, Fix Version 7(b70), 등록 2009-02-11, 해결 2009-08-14.
- JDK-7075600 "IllegalArgumentException throws when running apps" — Affects 7, 등록 2011-08-05.
- JDK-8048887 "SortingFocusTraversalPolicy throws IllegalArgumentException from the sort method" — Affects 7·8·9, Fix Version 9(b24), 등록 2014-07-01, 해결 2014-07-04. 백포트 8u40·8u45·7u72·7u76·7u79·7u80 등.
- JDK 7 GA 날짜: OpenJDK JDK 7 프로젝트 페이지 "JDK 7 reached General Availability on 28 July 2011." <https://openjdk.org/projects/jdk7/>
- OpenJDK 버그 페이지(`bugs.openjdk.org`)는 2026-10-07에 오류 페이지를 내서 Internet Archive 사본으로 읽었다.

#### 사실 (원문)

- Oracle 호환성 노트(Area: API: Utilities): "Synopsis: Updated sort behavior for Arrays and Collections may throw an IllegalArgumentException". "The sorting algorithm used by java.util.Arrays.sort and (indirectly) by java.util.Collections.sort has been replaced. The new sort implementation may throw an IllegalArgumentException if it detects a Comparable that violates the Comparable contract. The previous implementation silently ignored such a situation. If the previous behavior is desired, you can use the new system property, java.util.Arrays.useLegacyMergeSort, to restore previous mergesort behavior." Nature of Incompatibility: behavioral, RFE: 6804124.
- JDK-6804124 설명: 옛 알고리즘은 1997년 Joshua Bloch가 쓴 "modified mergesort"였다. Python이 2003년부터 쓰는 Tim Peters의 timsort를 Bloch가 Java로 옮겼다. "On highly ordered data, this code can run up to 25 times as fast as the current implementation (on the HotSpot server VM)."
- JDK-7075600(2011-08-05, JDK 7 GA 8일 뒤 등록): "Get the follow reproduible exception with Java 7 on Windows when running attached designer.zip apps: Exception in thread "AWT-EventQueue-0" java.lang.IllegalArgumentException: Comparison method violates its general contract! at java.util.TimSort.mergeHi(TimSort.java:868) ... at javax.swing.SortingFocusTraversalPolicy.enumerateAndSortCycle(...)" — 예외가 난 비교자는 사용자 코드가 아니라 **JDK 자신의 Swing** 코드였다.
- JDK-8048887의 원인 설명: "SortingFocusTraversalPolicy uses ROW_TOLERANCE conception to alter a disposition of components in a focus cycle for the sake of visually more appropriate traversal order. This however breaks the transitivity rule, which in case of using the default tim-sort algo leads to an exception".
- 규모: 커리큘럼은 "대량 발생"이라 적었지만, 영향받은 애플리케이션 수를 센 1차 자료는 찾지 못했다 [?]. 확인한 것은 JDK 버그 DB에 같은 예외의 보고가 여러 건이고(JDK-7075600은 JDK-8013775·JDK-8048887·JDK-8040632·JDK-8013550과 "duplicates" 링크), JDK 7·8의 여러 업데이트에 백포트됐다는 것이다.

#### 원리 — "허용 오차 안이면 같은 행"은 추이적이지 않다

```text
  ROW_TOLERANCE 꼴 비교자 (모형, TOL = 10):  |dy| <= 10 이면 x 로 비교, 아니면 y 로 비교

        y
        0 ┤                    c (20, 0)       a·b: |16−8| = 8 ≤ 10 → x 비교 → a(0) < b(10)
        8 ┤          b (10, 8)                 b·c: |8−0|  = 8 ≤ 10 → x 비교 → b(10) < c(20)
       16 ┤ a (0, 16)                          a·c: |16−0| = 16 > 10 → y 비교 → c(0) < a(16)
          └───────────────────── x
                                               a < b < c < a  — 순환. 전순서가 없다.
```

- 그림·실험 B는 단순화한 모형이다. 실제 Swing `LayoutComparator`(jdk8u 소스)는 `ROW_TOLERANCE = 10`이고 조건이 `Math.abs(ay - by) < ROW_TOLERANCE`(미만)다. 위 세 점(차이 8·16)은 어느 쪽이든 같은 결과다.
- 추이성: a < b이고 b < c면 a < c여야 한다([03](../03-sets-relations-orders/2-summary.md) 4절). "가까우면 같은 행"이라는 관계는 반사·대칭이지만 추이적이지 않아 동치관계가 아니다. 그 위에 세운 순서도 추이성이 깨진다.
- 옛 병합 정렬은 위반을 만나도 검사 없이 무언가를 돌려줬다. TimSort는 병합 중 불가능한 상태를 만나면 예외를 던진다(`mergeLo`·`mergeHi`). 둘 다 **올바른 순서가 정의되지 않는** 입력에 대한 반응일 뿐이다(해석).
- JDK 7은 비교자를 바꾸지 않았다. 바뀐 것은 위반을 **보이게 하는** 정렬 구현이다. 그래서 JDK 업그레이드 직후 "코드를 안 고쳤는데 예외가 난다"는 보고가 생겼다(해석).

#### 실험 B: ROW_TOLERANCE 꼴 비교자 (`RowTol.java`)

```java
record P(int x, int y) {}
static final int TOL = 10;
static final Comparator<P> ROW = (a, b) -> Math.abs(a.y() - b.y()) <= TOL
        ? Integer.compare(a.x(), b.x()) : Integer.compare(a.y(), b.y());
// 점 n개: x ∈ [0, 1000), y ∈ [0, 2n), 시드 0..199 로 200회. 정렬 후 i<j 인데 ROW(xs[i], xs[j]) > 0 인 쌍이 있으면 "뒤집힌 쌍"
```

(실험, 같은 환경, `java RowTol.java`와 `java -Djava.util.Arrays.useLegacyMergeSort=true RowTol.java`, 2026-10-07)

```text
useLegacyMergeSort=null
세 점: a<b? -1  b<c? -1  a<c? 1  (a=(0,16) b=(10,8) c=(20,0))
n=   31: 200회 중 예외   0회, 예외 없이 뒤집힌 쌍이 남은 결과 200회
```

- 관찰
  - 세 점 출력이 위 그림의 순환이다(a < b, b < c, 그런데 a > c).
  - 기본 TimSort에서 예외는 800회 중 2회뿐이었다. 나머지는 예외 없이 끝났고, 끝난 결과에는 모두 비교자 자신의 기준으로도 뒤집힌 쌍이 있었다.

### 사건 3 — TimSort 자체의 불변식 버그를 형식 검증이 찾음 (de Gouw 외, 블로그 2015-02-24 · CAV 2015)

출처
- Stijn de Gouw, Jurriaan Rot, Frank S. de Boer, Richard Bubel, Reiner Hähnle, "OpenJDK's Java.utils.Collection.sort() Is Broken: The Good, the Bad and the Worst Case", *Computer Aided Verification*(CAV 2015), LNCS, pp. 273–289 <https://link.springer.com/chapter/10.1007/978-3-319-21690-4_16>(서지는 Crossref 메타데이터로 확인, 본문은 열지 못함 [?]).
- Stijn de Gouw, "Proving that Android's, Java's and Python's sorting algorithm is broken (and showing how to fix it)", Envisage 프로젝트 블로그, 2015-02-24 <http://envisage-project.eu/proving-android-java-and-python-sorting-algorithm-is-broken-and-how-to-fix-it/>(Internet Archive 사본으로 열람).
- JDK-8072909 "TimSort fails with ArrayIndexOutOfBoundsException on worst case long arrays" — Affects 7u76·8·9, Fix Version 9(b51), 등록 2015-02-06, 해결 2015-02-12. 백포트 8u60·8u65·7u85 등.
- JDK-8203864 "Execution error in Java's Timsort" — Fix Version 11(b20), 등록 2018-05-27, 해결 2018-06-25. 백포트 11.0.1·12.
- OpenJDK 21 소스 `src/java.base/share/classes/java/util/TimSort.java`(jdk21u) <https://github.com/openjdk/jdk21u>.

#### 사실 (원문)

- 블로그: KeY(순차 Java용 연역적 검증 도구)로 Counting·Radix sort를 검증한 뒤 TimSort에 도전했다. "Unfortunately, we weren't able to prove its correctness. A closer analysis showed that this was, quite simply, because TimSort was broken".
- 의도된 불변식(블로그): `mergeCollapse`는 마지막 3개 run이 `runLen[n-2] > runLen[n-1] + runLen[n]`과 `runLen[n-1] > runLen[n]`을 만족할 때까지 병합한다. "The intention is that checking this invariant on the top 3 runs in runLen in fact guarantees that all runs satisfy it."
- 반례(블로그): `mergeCollapse` 진입 시 `120, 80, 25, 20, 30` → 25와 20을 병합해 `120, 80, 45, 30` → 위 3개는 80 > 45 + 30, 45 > 30이라 종료. "But mergeCollapse has not fully restored the invariant: it is broken by 120, since 120 < 80 + 45."
- 결과(블로그): 불변식이 깨지면 run 길이가 기대보다 느리게 커져 "more than runLen.length runs are needed to cover the entire input array, resulting in an ArrayOutOfBoundsException on runLen". 재현: `java TestTimSort 67108864` → `java.lang.ArrayIndexOutOfBoundsException: 40 at java.util.TimSort.pushRun(...)`.
- 제안한 수정(블로그): "check that the invariant holds for the last 4 runs in runLen, instead of only the last 3." 수정본은 KeY로 증명했다고 적는다.
- Python(블로그): 같은 버그가 CPython에도 있으나 `runLen`에 85칸을 잡아 "arrays with less than 2^49 elements"에는 충분해 현재 기계에서는 터뜨릴 수 없다.
- JDK-8072909 보고: 앞서 JDK-8011944에서 스택 길이를 늘려 "fixed"로 표시됐지만, "the declared length 40 of runLen which is chosen if the length of the input array is >= 119151, does not suffice." 보고자가 제시한 우회책은 두 가지 — 스택 길이 40 → 49, 또는 `mergeCollapse` 수정.
- OpenJDK의 대응: 블로그 원문 "instead of using our fixed (and verified!) version of mergeCollapse(), they opted to increase the allocated runLen "sufficiently"." 3년 뒤 JDK-8203864(Carine Pivoteau의 분석 전달)는 "the correction implemented in the Java source code (changing Timsort stack size) is wrong and that it is still possible to make it break"라고 적고, 알고리즘 수정을 권했다.
- 현재 소스(OpenJDK 21, jdk21u): `stackLen`은 길이 119,151 이상에서 49이고, `mergeCollapse`는 `n > 1 && runLen[n-2] <= runLen[n] + runLen[n-1]` 조건을 포함해 위 4개를 검사한다. 이 조건은 jdk10u 소스에는 없고 jdk11u 소스부터 있다(JDK-8203864의 Fix Version 11과 맞다). jdk7u 공개 소스의 `stackLen`은 아직 40이고, jdk8u는 49다.

#### 원리 — 불변식은 "끝에서 성립"이 아니라 "전부에서 성립"해야 한다

```text
  run 스택 (아래가 오래된 run)        불변식 I:  모든 i 에 대해 runLen[i] > runLen[i+1] + runLen[i+2]  그리고  runLen[i] > runLen[i+1]

  진입:  [120, 80, 25, 20, 30]         위 3개 (25, 20, 30): 25 <= 20 + 30 → 25·20 병합
  1회:   [120, 80, 45, 30]             위 3개 (80, 45, 30): 80 > 75, 45 > 30 → "성립" → 종료  (옛 판)
                                        그런데 아래쪽 (120, 80, 45): 120 <= 125 → I 깨짐
  새 판:  위 4개까지 보므로 120 <= 80 + 45 를 발견 → 계속 병합 → [275]
```

- 루프 불변식의 세 단계(초기화·유지·종료, [02-induction-and-invariants](../02-induction-and-invariants/2-summary.md))에서 **유지** 단계가 틀렸다. "위 3개만 고치면 전체가 유지된다"는 귀납 단계에 빈틈이 있었다. 병합으로 새로 생긴 run(45)이 그 아래(120, 80)와의 관계를 바꾸는데, 그 관계를 다시 확인하지 않았다.
- 스택 크기가 왜 문제인가 — 점화식: I가 전부 성립하면 run 길이는 위에서 아래로 r_k > r_{k−1} + r_{k−2}로, 피보나치보다 빨리 커진다([06-recurrences-and-asymptotics](../06-recurrences-and-asymptotics/2-summary.md)). 그래서 run 개수는 배열 길이의 로그에 비례하고, 작은 고정 크기 스택(40)으로 충분하다고 계산했다. I가 깨지면 이 점화식이 성립하지 않아 run이 더 많이 쌓인다.
- 형식 검증이 찾은 이유(해석): 테스트는 "실제로 나오는 입력"을 본다. 이 버그를 터뜨린 입력은 특정 run 길이 수열을 일부러 만든 것(블로그의 테스트 생성기)이고, 재현 길이는 67,108,864였다. 무작위 테스트로 만나기 어렵다. 증명은 입력 전체에 대해 불변식 유지를 요구하므로 빈틈을 바로 드러냈다.

#### 실험 C: run 길이 스택만 흉내 내기 (`RunStack.java`)

원소 없이 run 길이 스택만 두고, 옛 `mergeCollapse`(위 3개)와 OpenJDK 21의 `mergeCollapse`(위 4개)를 그대로 옮겨 블로그의 예를 넣었다. 마지막 줄은 I가 전부 성립할 때 필요한 run 수의 어림이다(맨 위 run ≥ 16, r_k = r_{k−1} + r_{k−2} + 1로 최소 증가를 가정해 합이 2^31 − 1을 넘기 전까지 센 값).

```java
static void collapseOld() {             // JDK 7·8 초기판: 위 3개만 검사
    while (st.size() > 1) {
        int n = st.size() - 2;
        if (n > 0 && L(n - 1) <= L(n) + L(n + 1)) { if (L(n - 1) < L(n + 1)) n--; mergeAt(n); }
        else if (L(n) <= L(n + 1)) mergeAt(n);
        else break;
    }
}
static void collapseNew() {             // OpenJDK 21 TimSort.mergeCollapse: 위 4개 검사
    while (st.size() > 1) {
        int n = st.size() - 2;
        if (n > 0 && L(n - 1) <= L(n) + L(n + 1) || n > 1 && L(n - 2) <= L(n) + L(n - 1)) { if (L(n - 1) < L(n + 1)) n--; }
        else if (n < 0 || L(n) > L(n + 1)) break;
        mergeAt(n);
    }
}
```

(실험, 같은 환경, `java RunStack.java`, 2026-10-07 — 결정적)

```text
old(위 3개)    시작 [120, 80, 25, 20, 30] → [120, 80, 45, 30], 깨진 불변식: 120 <= 80 + 45
new(위 4개)    시작 [120, 80, 25, 20, 30] → [275], 깨진 불변식: 없음
불변식이 전부 지켜질 때 int 길이(2^31-1) 배열에 필요한 run 수 상한 ≈ 38 (OpenJDK 7·8 스택 40, 21은 49)
```

- 관찰: 옛 판은 블로그와 같은 `[120, 80, 45, 30]`에서 멈췄고, 스택 아래쪽에 깨진 불변식이 남았다. 새 판은 끝까지 병합했다.
- 마지막 줄의 38은 이 노트의 어림 계산이다(최소 run 길이 16 가정). 스택 40이 "I가 지켜지면" 충분했다는 설계 계산과 같은 차수다. I가 깨지는 입력에서는 이 어림이 성립하지 않는다는 것이 사건의 요지다. 출력의 "7·8 스택 40"은 JDK-8072909 이전 판이다(jdk8u 현재 소스는 49).
- OpenJDK 21 소스 주석은 49가 "the worst case stack size increasing scenario"에서도 길이 Integer.MAX_VALUE−4까지 충분하다고 적고, 설명을 de Gouw 외 논문 4절로 돌린다. 원래 40을 정한 계산 과정은 확인하지 않았다 [?].
- 실제 6,700만 원소 재현(`TestTimSort 67108864`)은 이 환경의 메모리 상한(1GB)을 넘어 돌리지 않았다. 원 보고의 출력으로 대신한다.

## 쓰이는 자료구조·알고리즘

- **PRNG·CSPRNG**: 시드 → 상태 → 출력. 시드 공간이 출력 공간의 상한이다([12-randomness-and-prng](../12-randomness-and-prng/2-summary.md), [security/09-randomness-and-key-management](../../security/09-randomness-and-key-management/2-summary.md)).
- **TimSort**: run 탐지 + 이진 삽입 + run 스택 + 갤럽 병합. `MIN_MERGE = 32`, `mergeLo`·`mergeHi`의 계약 위반 예외([algorithm/09-sorting-in-practice](../../algorithm/09-sorting-in-practice/2-summary.md) §3).
- **루프 불변식·형식 검증**: KeY + JML(`loop_invariant`, `decreases`). 불변식·종료 척도의 수학은 [02-induction-and-invariants](../02-induction-and-invariants/2-summary.md).
- **생일 한계**: 약한 키의 서버 간 충돌 어림([05](../05-counting-and-birthday-bound/2-summary.md)).

### 2. 코드 — Java 21

```java
import java.security.SecureRandom;
import java.util.*;

final class Guards {
    // 사건 1: 키·토큰은 OS CSPRNG 기반. 시드를 직접 넣지 않는다.
    static final SecureRandom RNG = new SecureRandom();
    static byte[] token(int bytes) { byte[] b = new byte[bytes]; RNG.nextBytes(b); return b; }

    // 사건 1: 생성기 점검 — 표본의 중복 수를 생일 어림과 비교 (128비트 10만 개면 기대 쌍 수 ≈ 1.5e-29, 사실상 0)
    static long duplicates(int samples) {
        Set<String> seen = new HashSet<>(); long dup = 0;
        for (int i = 0; i < samples; i++) if (!seen.add(HexFormat.of().formatHex(token(16)))) dup++;
        return dup;
    }

    // 사건 2: 비교자 계약 속성 테스트 — 무작위 세 원소로 부호 반대칭·추이성·0의 일관성(Comparator 명세의 세 조건)
    static <T> void checkComparator(Comparator<T> c, List<T> pool, int trials, Random r) {
        for (int t = 0; t < trials; t++) {
            T a = pool.get(r.nextInt(pool.size())), b = pool.get(r.nextInt(pool.size())), d = pool.get(r.nextInt(pool.size()));
            if (Integer.signum(c.compare(a, b)) != -Integer.signum(c.compare(b, a)))
                throw new AssertionError("부호 반대칭 위반: " + a + ", " + b);
            if (c.compare(a, b) < 0 && c.compare(b, d) < 0 && c.compare(a, d) >= 0)
                throw new AssertionError("추이성 위반: " + a + " < " + b + " < " + d + " 인데 a >= d");
            if (c.compare(a, b) == 0 && Integer.signum(c.compare(a, d)) != Integer.signum(c.compare(b, d)))
                throw new AssertionError("0의 일관성 위반: " + a + " ~ " + b + " 인데 " + d + "와의 비교 부호가 다름");
        }
    }

    // 사건 3: 불변식은 스택 전체에 대해 검사 (테스트·디버그 빌드에서)
    static void checkRunStack(int[] runLen, int size) {
        for (int i = 0; i + 2 < size; i++)
            if (runLen[i] <= runLen[i + 1] + runLen[i + 2]) throw new IllegalStateException("I 위반 at " + i);
    }
}
```

- `checkComparator`의 풀은 실제 데이터 분포(값이 빽빽한 구간 포함)에서 뽑는다. 실험 B의 세 점처럼 순환은 경계 근처에서 생긴다.
- 사건 2의 처방은 비교자를 바꾸는 것이다. 허용 오차 대신 양자화한 키(예: `y / TOL`로 행 번호를 먼저 정하고 그 안에서 x)로 비교하면 행 번호가 동치관계가 되어 추이성이 선다([03](../03-sets-relations-orders/2-summary.md) 장애 2·4). 화면 배치 결과가 달라질 수 있으므로 요구사항을 확인한다(해석).

## 장애 시나리오와 대처

### 1. 상류 코드의 "경고 없애기" 수정이 엔트로피를 지움 — Debian형

- **현상**: 정적·동적 분석 도구 경고를 없애려고 난수 관련 코드 몇 줄을 지웠다. 기능 테스트는 다 통과했다.
- **보이는 형태**: 당장은 없다. 나중에 다른 서버에서 같은 키 지문, 약한 키 목록과 일치, 공격자가 토큰을 맞힘.
- **원인**: 엔트로피 입력 경로가 끊겨 실제 공간이 시드(PID) 개수로 줄었다. 출력은 여전히 무작위처럼 보인다(사건 1).
- **대처**: 암호 코드의 상류 수정은 상류 저자와 확인한다. 생성기에 "다른 시드 → 다른 출력" 회귀 테스트와 대량 표본 중복 검사를 둔다. 의심되면 그 기간에 만든 키·토큰을 전부 재발급한다([security/09](../../security/09-randomness-and-key-management/2-summary.md) 장애 3).

### 2. JDK 업그레이드 직후 정렬 예외 — 비교자 위반이 드러남

- **현상**: 코드 변경 없이 JDK만 올렸는데 일부 화면·배치에서 정렬 예외가 난다.
- **보이는 형태**: `java.lang.IllegalArgumentException: Comparison method violates its general contract!`, 트레이스에 `TimSort.mergeHi`/`mergeLo`. 특정 데이터에서만.
- **원인**: 비교자가 원래 추이성을 어겼다. 옛 구현은 조용히 넘겼고 새 구현은 발견하면 알린다(사건 2).
- **대처**: 비교자를 고친다. `useLegacyMergeSort`는 이행 기간의 임시 조치로만 쓰고 종료 날짜를 정한다 — 이 옵션 아래에서도 결과는 틀린 순서다(실험 B). 비교자 공리 속성 테스트를 CI에 둔다.

### 3. 예외가 드물어서 "운이 나쁜 데이터"로 치부함

- **현상**: 정렬 예외가 한 달에 몇 번 나서 재시도로 처리했다. 화면 순서가 가끔 이상하다는 문의는 별건으로 처리됐다.
- **보이는 형태**: 예외 로그는 드물고, 순서 이상 문의는 꾸준하다. 둘이 같은 화면이다.
- **원인**: 예외는 위반을 우연히 만났을 때만 난다. 실험 B에서 예외는 800회 중 2회였고, 나머지 실행 결과에는 모두 뒤집힌 쌍이 있었다.
- **대처**: 예외 한 건을 비교자 결함의 증거로 본다. 정렬 결과를 올바른 기준으로 재검사하는 테스트를 둔다([16-math-symptom-index](../16-math-symptom-index/2-summary.md) 1절).

### 4. "수십억 번 돌았으니 맞다" — 검증되지 않은 불변식

- **현상**: 오래 쓰인 라이브러리·사내 공용 코드의 경계 입력에서 배열 범위 예외가 난다.
- **보이는 형태**: 아주 큰 입력이나 특수한 모양의 입력에서만 `ArrayIndexOutOfBoundsException`. 재현 입력이 인위적이다.
- **원인**: 불변식을 일부(스택 위쪽)만 검사했다. 대부분의 입력에서는 나머지가 우연히 성립했다(사건 3).
- **대처**: 고정 크기 자료구조의 크기 계산이 기대는 불변식을 문서로 적고, 테스트·디버그 빌드에서 전체를 검사한다. 핵심 루틴에는 적대적 입력 생성기나 형식 검증을 고려한다. 근본 수정(불변식 복구)과 증상 완화(스택 확대)를 구분한다 — OpenJDK는 2015년에 스택을 늘렸고, 2018년에 그것이 충분하지 않다는 분석을 받고서 `mergeCollapse`를 고쳤다(JDK-8203864).

## 핵심 문장

- Debian 2008은 **세기**의 사건이다. 키 길이와 상관없이 키 공간은 시드 공간(아키텍처당 32,767개 난수 흐름) 이하였다. 모형 실험 A에서는 32,767개 지문 표를 1초 안에 만들었다(실제 RSA 키 생성은 키당 훨씬 오래 걸리지만 32,767번이면 끝나는 유한한 일이다 — 해석).
- Java 7 TimSort 예외는 **관계**의 사건이다. "허용 오차 안이면 같다"는 추이적이지 않아 정렬에 올바른 답이 없을 수 있다. 바뀐 것은 비교자가 아니라 위반을 드러내는 구현이었다.
- de Gouw 외 2015는 **귀납**의 사건이다. 불변식을 끝부분만 다시 세우면 전체 유지가 보장되지 않는다. 증명을 시도하자 그 빈틈이 드러났다.
- 세 경우 모두 결과는 그럴듯했다. 전제 위반은 출력이 아니라 전제를 직접 따져야 보인다.
- 예외를 숨기는 처방(`useLegacyMergeSort`, 스택만 늘리기)은 위반을 남긴다.
