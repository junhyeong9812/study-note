# math/10-queueing-and-littles-law — L=λW, M/M/1, 이용률과 대기시간의 비선형 관계 — 정리 (힌트)

## 해결하는 문제

"CPU 80%면 아직 20% 여유가 있다"는 직관이 틀리는 이유를 숫자로 보여 주는 도구다.\
이용률이 1에 가까워질수록 **대기 시간은 비례가 아니라 1/(1−ρ)로** 폭증한다.

쉬운 예: 바리스타 한 명인 카페.

```text
  손님 도착 간격도 들쭉날쭉, 음료 만드는 시간도 들쭉날쭉

  바리스타가 50% 바쁨  → 가게 안(줄 + 만드는 중)에 평균 1명, 기다림 짧음
  바리스타가 80% 바쁨  → 기다림이 50%일 때의 4배
  바리스타가 90% 바쁨  → 9배
  바리스타가 99% 바쁨  → 99배      ← 90%에서 9%포인트 더 바빠졌을 뿐인데
```

- 바리스타가 놀고 있는 순간에 온 손님은 바로 받지만, 몰려온 손님은 줄을 선다. 노는 시간은 저축할 수 없다.
- 이용률이 높을수록 "몰려온 순간"을 흡수할 여유가 줄어 줄이 길어진다.

똑같은 구조다.\
실무 예:
- 부하 테스트에서 도착률을 한계의 약 90%까지 올리자 p99 지연이 600/s일 때의 2배, 한계를 넘기자 약 20배가 됐다([reliability/22-capacity-and-load-testing](../../reliability/22-capacity-and-load-testing/2-summary.md) 실험).
- Little 법칙으로 "평균 200건이 동시에 처리 중"이라 계산하고 스레드·커넥션 풀을 정확히 200으로 잡았더니 대기가 끝없이 길어졌다.

Little 법칙의 기초(식당 예, 풀 크기 계산, 대기 시간 역산)는 원고 [server-design/01-scaling-principles](../../systems/server-design/01-scaling-principles.md) §2에 있다. 성립 조건과 닫힌 루프 실험은 [reliability/21-scaling-principles](../../reliability/21-scaling-principles/2-summary.md) §2·§4에 있다. 여기서는 그 위의 **대기행렬 수학**(M/M/1, 분산의 효과, 서버 여러 대, 풀 크기의 여유)을 다룬다.

참고: 원고 §2 식당 예의 "초당 2명 × 30분 = 60명"은 단위가 어긋났다. 분당 2명 × 30분이면 평균 60명이고, 초당 2명이면 2 × 1,800초 = 평균 3,600명이다. 또 "항상 60명"이 아니라 **평균** 60명이다(L은 시간 평균).

## 동작·원리

### 1. Little 법칙 다시 보기 — 어느 상자에든 쓴다

```text
              ┌─────────────── 시스템 (L, W) ───────────────┐
   도착 λ ──> │  ┌──── 대기열 (Lq, Wq) ────┐   ┌─ 서버 ─┐   │ ──> 떠남 λ
              │  │  ▢ ▢ ▢ ▢                │──>│  ●     │   │
              │  └─────────────────────────┘   └────────┘   │
              └──────────────────────────────────────────────┘

   시스템 전체:   L  = λ · W
   대기열만:      Lq = λ · Wq
   서버만:        (서버에서 일하는 평균 건수) = λ · E[S] = ρ     ← 이용률 법칙
```

- *Little 법칙*: 장기 평균에서 `L = λW`. L은 상자 안 평균 건수, λ는 평균 도착률, W는 한 건이 상자 안에 머무는 평균 시간이다.
  - Little(1961)의 증명 조건: 세 평균이 유한하고, 과정이 정상(stationary)이며 도착 과정이 에르고딕(metrically transitive)하다. 도착·서비스 분포와 처리 순서는 가정하지 않는다.
  - 이후의 표본 경로(sample path) 증명(Stidham 1974)은 정상성도 요구하지 않는다. 한 관측 경로에서 λ와 W의 장기 극한이 존재·유한하면 L도 그렇고 `L = λW`다(Little 2011, OR 59(3) §3).
  - 큐가 끝없이 자라는 과부하(ρ ≥ 1)에서는 평균이 수렴하지 않아 쓸 수 없다.
- 같은 법칙을 **상자를 어떻게 그리느냐**에 따라 세 번 쓴다. 대기열만 그리면 `Lq = λWq`, 서버만 그리면 이용률 `ρ = λ·E[S]`(서버 1대)다.
  - *이용률(ρ, utilization)*: 서버가 일하는 시간의 비율. 서버 c대면 `ρ = λ·E[S] / c`.
  - *E[S]*: 한 건의 평균 서비스 시간. 처리율 μ = 1/E[S].

### 2. M/M/1 — 대기가 ρ/(1−ρ)로 폭증한다

```text
  켄들 표기  A / S / c
             │   │   └ 서버 수
             │   └──── 서비스 시간 분포 (M = 지수, D = 고정, G = 일반)
             └──────── 도착 간격 분포   (M = 지수 = 포아송 도착)

  M/M/1 상태 그림 (시스템 안 건수 n) — 출생·사망 사슬
      λ        λ        λ        λ
   (0) ──> (1) ──> (2) ──> (3) ──> …
      <──      <──      <──      <──
      μ        μ        μ        μ

  정상 상태 확률  P(n) = (1 − ρ)·ρⁿ     (기하 분포, ρ = λ/μ < 1)
```

- *M/M/1*: 포아송 도착, 지수 서비스 시간, 서버 1대, 줄 길이 제한 없음, 먼저 온 순서(FIFO).
  - 서비스 시간끼리 독립·동일 분포이고, 도착 과정과도 독립이라는 전제가 함께 들어 있다(MIT 6.263 L5).
- 증명 아이디어: 정상 상태에서는 n → n+1로 가는 흐름(λ·P(n))과 n+1 → n으로 오는 흐름(μ·P(n+1))이 같다. 그래서 `P(n+1) = ρ·P(n)`, 합이 1이 되게 하면 `P(n) = (1−ρ)ρⁿ`(Harchol-Balter 4부, Kleinrock 1권 — 장 번호 `[?]`).
- 결과(정확식, M/M/1 전제에서)

| 양 | 식 | ρ=0.5 | 0.8 | 0.9 | 0.95 | 0.99 |
|---|---|---|---|---|---|---|
| 시스템 안 평균 건수 L | ρ/(1−ρ) | 1 | 4 | 9 | 19 | 99 |
| 평균 대기 Wq (E[S] 단위) | ρ/(1−ρ) · E[S] | 1 | 4 | 9 | 19 | 99 |
| 평균 체류 W (E[S] 단위) | E[S]/(1−ρ) | 2 | 5 | 10 | 20 | 100 |
| 대기열 평균 Lq | ρ²/(1−ρ) | 0.5 | 3.2 | 8.1 | 18.05 | 98.01 |

- 기호
  - *Wq*: 줄에서 기다린 시간(서비스 전). *W = Wq + E[S]*: 도착부터 떠날 때까지.
  - E[S] = 1일 때 L과 Wq는 같은 숫자다(Little: `L = λW = ρ·W`, `W = 1/(1−ρ)`).
- 기울기: `dW/dρ = E[S]/(1−ρ)²`. ρ가 0.8 → 0.9로 0.1 오르면 W가 5 → 10으로 두 배가 된다. 0.5 → 0.6은 2 → 2.5뿐이다.
- 이것이 커리큘럼 ⚠ 칸의 "이용률 80% 넘자 지연 급등"이다. 80%라는 숫자 자체에 특별한 의미는 없다. 곡선의 기울기가 그 근처부터 커질 뿐이다.

```text
  평균 대기 Wq / E[S]  (M/M/1)
  100 │                                      ●  ρ=0.99
      │
   20 │                               ● 0.95
   10 │                         ● 0.9
    4 │                 ● 0.8
    1 │        ●  0.5
      └──────────────────────────────────────── ρ
        0     0.5      0.8   0.9 0.95   1
```

#### 실험: M/M/1 이산 사건 시뮬레이션

- 고객 200만 명(앞 20만 명은 초기 상태 영향을 빼려고 버림), E[S] = 1(시간 단위 = 평균 서비스 시간), 시드 1·2·3.
- 대기는 FIFO 서버 c대의 "가장 먼저 비는 서버" 규칙으로 계산했다(c = 1이면 린들리 점화식 `Wq(n+1) = max(0, Wq(n) + S(n) − A(n+1))`과 같다).
- L은 Little을 쓰지 않고 도착·이탈 시각을 시간순으로 훑어 N(t)를 적분한 **시간 평균**으로 직접 쟀다. 그래야 `λ×W`와 비교하는 의미가 있다.
- 코드 핵심(`Queue.java`):

```java
for (int i = 0; i < n; i++) {
    t += exp(r, 1 / lambda);                      // 포아송 도착 = 지수 간격
    double f = free.poll();                        // 가장 먼저 비는 서버 (PriorityQueue)
    double start = Math.max(t, f), end = start + svc.next(r);
    free.add(end);
    if (i >= warm) { sumWq += start - t; sumW += end - t; ... }
}
// 시간 평균 L: 도착·이탈 시각을 합쳐 훑으며 area += (현재 인원) × (구간 길이)
```

(시뮬레이션, OpenJDK 21.0.12 temurin, Docker `--cpus=2`, 2026-10-07 — 시드 1·2·3, 고객 200만/시드)

```text
   ρ   이론 Wq=ρ/(1−ρ)  시뮬 Wq(최소~최대)      이론 L=ρ/(1−ρ)  시뮬 L(시간평균)   λ×W(시뮬)
 0.50        1.00          1.00 ~     1.01            1.00      1.00 ~   1.01   (시드1)   1.00 vs L   1.00
 0.70        2.33          2.32 ~     2.36            2.33      2.33 ~   2.35   (시드1)   2.33 vs L   2.33
 0.80        4.00          3.98 ~     4.05            4.00      3.99 ~   4.05   (시드1)   3.99 vs L   3.99
 0.90        9.00          8.83 ~     9.17            9.00      8.85 ~   9.16   (시드1)   8.85 vs L   8.85
 0.95       19.00         18.90 ~    20.14           19.00     18.91 ~  20.11   (시드1)  18.91 vs L  18.91
 0.99       99.00         98.32 ~   150.86           99.00     98.34 ~ 150.47   (시드1)  98.38 vs L  98.34
```

- 관찰 1: ρ = 0.5~0.95에서 시뮬레이션 평균 대기가 이론값 ρ/(1−ρ)의 −2%~+6% 안에 있다(가장 큰 벗어남은 ρ = 0.95 시드 하나의 20.14).
- 관찰 2: ρ = 0.99에서는 시드에 따라 98~151로 크게 흔들렸다. 1에 가까울수록 대기열이 한 번 길어지면 오래 빠지지 않아, 같은 정확도에 훨씬 긴 관측이 필요하다(해석). 운영 지표도 마찬가지로 고이용률에서는 짧은 창의 평균이 크게 흔들린다.
- 관찰 3: 직접 잰 시간 평균 L과 `λ×W`가 소수 둘째 자리까지 같다(ρ = 0.99만 98.38 vs 98.34). Little 법칙이 이 시뮬레이션에서 맞는다는 확인이다. "분포 가정 없이"의 근거는 증명(Little 1961)이고, M/M/1 한 가지 시뮬레이션은 그 한 예일 뿐이다.

### 3. 평균이 같아도 분산이 대기를 만든다

```text
  M/G/1 — 서비스 시간 분포가 일반(G)일 때, 포아송 도착 (폴라체크–힌친 공식)

      Wq = λ·E[S²] / (2(1 − ρ))  =  ρ/(1−ρ) · (1 + Cs²)/2 · E[S]

      Cs² = Var(S) / E[S]²    (서비스 시간의 변동 계수 제곱)

  같은 ρ = 0.8, 같은 E[S] = 1
    고정 시간(D)   Cs² = 0    → Wq = 4 × 0.5  = 2
    지수(M)        Cs² = 1    → Wq = 4 × 1    = 4
    가끔 아주 긴 것 Cs² = 5.5 → Wq = 4 × 3.25 = 13
```

- *폴라체크–힌친(P-K) 공식*: M/G/1의 평균 대기. 정확식이다(포아송 도착·서비스 시간 독립·동일 분포이고 도착과 독립·FIFO·ρ < 1 전제, E[S²]가 유한해야 평균 대기도 유한)(Harchol-Balter·Kleinrock 1권 — 실린 장 미확인 `[?]`).
- 대기는 평균 서비스 시간뿐 아니라 **두 번째 모멘트 E[S²]**에 비례한다. 가끔 아주 긴 작업(배치 쿼리, 큰 페이로드)이 섞이면 평균이 같아도 모두가 더 기다린다.
- 도착 쪽 버스트도 같은 방향으로 작용한다(포아송보다 몰려오면 대기가 는다). 분포 자체는 [math/09-common-distributions](../09-common-distributions/2-summary.md), 꼬리 지연은 [reliability/34-tail-latency-and-stragglers](../../reliability/34-tail-latency-and-stragglers/2-summary.md).

#### 실험: 서비스 시간 분산만 바꾸기

- 평균 1은 같고 분포만 다르다: 고정 1(M/D/1), 지수(M/M/1), 초지수 H2(확률 0.1로 평균 5.5, 0.9로 평균 0.5 — E[S²] = 6.5, Cs² = 5.5).

```java
Svc h2 = r -> r.nextDouble() < 0.1 ? exp(r, 5.5) : exp(r, 0.5);   // 평균 1, Cs² = 5.5
```

(시뮬레이션, 같은 환경 — ρ = 0.8, 시드 1, 고객 200만)

```text
  M/D/1 (Cs²=0)      이론 Wq   2.00   시뮬 Wq   2.01
  M/M/1 (Cs²=1)      이론 Wq   4.00   시뮬 Wq   3.98
  M/H2/1 (Cs²=5.5)   이론 Wq  13.00   시뮬 Wq  12.74
```

- 관찰: 이용률·평균 서비스 시간이 같아도 평균 대기가 2 → 4 → 약 13으로 6배 넘게 차이 난다. P-K 공식과 2% 안으로 맞다.

### 4. 서버 여러 대 — 공유 큐와 Erlang C

```text
  공유 큐 하나 (M/M/c)                     서버마다 따로 줄 (M/M/1 × c)
   ▢▢▢ ──┬──> ● 서버1                       ▢▢ ──> ● 서버1
         ├──> ● 서버2                       ▢▢▢▢ ──> ● 서버2   ← 이 줄이 긴데 옆 서버는 놀 수 있다
         └──> ● 서버3                       ▢ ──> ● 서버3
   비는 서버가 하나라도 있으면 기다리지 않는다
```

- *M/M/c*: 포아송 도착, 지수 서비스(독립·동일 분포, 도착과 독립), 서버 c대, 공유 FIFO 큐.
- *제공 부하(offered load) a*: `a = λ·E[S]`(단위 Erlang). 평균 동시 처리 건수다 — Little을 서버 묶음에 쓴 값.
- *Erlang C 공식*: M/M/c에서 도착한 요청이 기다려야 할 확률 `C(c, a)`. 평균 대기는 `Wq = C(c, a) / (c·μ − λ)`.
  - 계산은 Erlang B 점화식으로 한다: `B(0) = 1`, `B(k) = a·B(k−1) / (k + a·B(k−1))`, 그리고 `C = c·B / (c − a(1 − B))`(a < c 전제).
- 서버 c대의 이용률은 `ρ = a / c`. **c = a이면 ρ = 1이라 대기가 발산한다.**

#### 실험: 공유 큐 vs 따로 줄, 그리고 풀 크기

(시뮬레이션·계산, 같은 환경 — 시드 1, 고객 200만)

```text
== 3. 서버 10개: 공유 큐 하나(M/M/10) vs 따로 줄 선 10개(M/M/1 ×10), 서버당 ρ=0.8, E[S]=1
  공유 큐: 시뮬 Wq 0.203, 대기 비율 0.411 (Erlang C 이론 0.409 → Wq = C/(cμ−λ) = 0.205)
  따로 줄: 시뮬 Wq 3.982 (이론 ρ/(1−ρ) = 4.000)
== 4. 풀 크기: λ=1000/s, 평균 점유 0.2s (제공 부하 a = 200), 서비스 지수 분포 가정
  c=200  이용률 1.000  대기 확률 1.000  평균 대기 발산
  c=201  이용률 0.995  대기 확률 0.916  평균 대기 183.15 ms
  c=205  이용률 0.976  대기 확률 0.631  평균 대기 25.22 ms
  c=210  이용률 0.952  대기 확률 0.376  평균 대기 7.51 ms
  c=220  이용률 0.909  대기 확률 0.109  평균 대기 1.09 ms
  c=230  이용률 0.870  대기 확률 0.024  평균 대기 0.16 ms
  c=250  이용률 0.800  대기 확률 0.000  평균 대기 0.00 ms
```

- 관찰 1: 서버당 이용률이 같은 0.8인데, 공유 큐의 평균 대기(0.203)가 따로 줄(3.98)의 약 20분의 1이다. 시뮬레이션이 Erlang C 이론(대기 확률 0.409, Wq 0.205)과 맞다.
- 관찰 2: 서버가 많을수록 같은 이용률에서 대기가 짧다(풀링 효과). 큰 풀은 높은 이용률을 견딘다. 작은 풀(c = 1)은 0.8에서 이미 대기가 서비스 시간의 4배다.
- 관찰 3: a = 200에서 c = 200이면 발산, c = 210(이용률 95%)이면 평균 대기 7.5 ms, c = 220이면 1.1 ms다. **평균 동시 처리 수(Little) = 필요한 풀 크기가 아니다.** 여유분이 필요하고, 그 크기는 Erlang C로 어림한다(c = 250의 0.000은 소수 셋째 자리 미만).
- 참고: 원고 §2의 "L = 1000 × 0.2 = 200 → 워커 스레드가 200개 필요"는 **평균 동시 처리 수**다. 정확히 200개로 잡으면 이용률 100%라 대기가 발산한다(위 c = 200 행). 원고의 "또는 비동기로 200건 동시 진행"도 같은 여유가 필요하다.

### 5. 모형이 깨지는 곳

| 가정 | 깨지는 운영 상황 | 효과 |
|---|---|---|
| 포아송 도착(독립) | 버스트·재시도 폭풍·크론 정각 몰림 | 대기 증가(Ca² > 1) |
| 지수 서비스 | 긴 꼬리 서비스 시간(GC 정지·느린 쿼리) | P-K: Cs²만큼 증가 |
| 무한 대기열 | 유계 큐·타임아웃 | 대기 대신 거절·타임아웃으로 나타남 |
| 열린 시스템(도착이 응답과 무관) | 사용자가 응답을 받아야 다음 요청(닫힌 시스템) | 지연이 늘면 도착이 줄어 스스로 제한됨 |
| 정상 상태 | 트래픽 급증 직후·배포 직후 | M/M/1 정상 상태 공식이 아직 맞지 않음. Little은 측정 창 경계에 걸친 건을 처리해야 맞음 |

- 닫힌 시스템과 대화형 응답 시간 법칙은 [reliability/22](../../reliability/22-capacity-and-load-testing/2-summary.md), 재시도가 도착률을 키우는 되먹임은 [reliability/06-retry-backoff-jitter](../../reliability/06-retry-backoff-jitter/2-summary.md)에 있다.
- 모형은 "어디서 꺾이는지"와 "무엇을 바꾸면 얼마나 나아지는지"를 어림하는 도구다. 실제 한계는 부하 테스트로 잰다.

## 쓰이는 자료구조·알고리즘

- **FIFO 큐** — 대기열 자체. [data-structure/04-queue-deque](../../data-structure/04-queue-deque/2-summary.md)(커리큘럼 06).
- **유계 큐·링 버퍼** — 대기 **건수**에 상한을 둔다. 지연 상한까지 되려면 서비스 시간에도 상한(타임아웃)이 있어야 한다. [data-structure/25-ring-buffer](../../data-structure/25-ring-buffer/2-summary.md), 거절 정책은 [reliability/12-backpressure-and-load-shedding](../../reliability/12-backpressure-and-load-shedding/2-summary.md).
- **우선순위 큐(최소 힙)** — 이산 사건 시뮬레이션에서 "다음 사건", 여기서는 "가장 먼저 비는 서버". [data-structure/07-heap](../../data-structure/07-heap/2-summary.md)(커리큘럼 10).
- **포아송 도착·지수 분포** — 지수 간격 샘플링 `−E·ln(1−U)`. 분포는 [math/09-common-distributions](../09-common-distributions/2-summary.md).
- **린들리 점화식·Erlang B 점화식** — 대기 시간과 대기 확률을 순차로 계산하는 점화식. 점화식 일반은 [math/06-recurrences-and-asymptotics](../06-recurrences-and-asymptotics/2-summary.md).
- **커넥션 풀 = 서버 c대 + 공유 큐** — HikariCP 풀이 M/M/c 모양이다. [database/21-connection-pooling](../../database/21-connection-pooling/2-summary.md).

## 적용 — 풀어나가는 법

### 1. 증상 → 어림 → 확인

1. **증상**: 트래픽이 조금 늘었을 뿐인데 p99·평균 지연이 크게 늘었다. 풀 대기 시간 지표가 오른다.
2. **어림**
   - λ(도착률)와 평균 점유 시간 `E[S]`를 재서 `a = λ·E[S]`, `ρ = a / c`를 구한다.
   - ρ가 0.8 이상이면 이미 가파른 구간이다. 서버 1대면 Wq ≈ ρ/(1−ρ)·E[S], 여러 대면 Erlang C.
   - 서비스 시간 분산이 크면(가끔 아주 느린 요청) P-K의 (1 + Cs²)/2 배를 곱한다.
3. **확인**: 측정한 L(진행 중 건수 평균)과 λ×W가 맞는지 본다. 크게 다르면 측정이 틀렸거나 정상 상태가 아니다(큐가 계속 자라는 중).

### 2. 풀 크기 정하기 — Little로 평균, Erlang C로 여유

```java
/** Erlang C: 서버 c대, 제공 부하 a(= λ·E[S]). 도착한 요청이 기다려야 할 확률. a ≥ c면 1(불안정). */
static double erlangC(int c, double a) {
    if (a >= c) return 1;
    double b = 1;
    for (int k = 1; k <= c; k++) b = a * b / (k + a * b);   // Erlang B 점화
    return c * b / (c - a * (1 - b));
}

/** 목표 평균 대기(초) 이하가 되는 가장 작은 c. 포아송 도착·지수 서비스 가정 — 결과는 부하 테스트로 확인한다. */
static int poolSize(double lambda, double meanService, double targetWqSec) {
    double a = lambda * meanService;                         // Little: 평균 동시 점유 수
    for (int c = (int) Math.floor(a) + 1; ; c++) {
        double wq = erlangC(c, a) / (c / meanService - lambda);
        if (wq <= targetWqSec) return c;
    }
}
// poolSize(1000, 0.2, 0.001) → 221  (같은 식을 Python으로 계산: c=220 → 1.09 ms, c=221 → 0.91 ms)
```

- 풀이 하류(DB)의 한도를 넘으면 병목이 하류로 옮겨 간다. DB 쪽 최적 동시성과 함께 본다([database/21](../../database/21-connection-pooling/2-summary.md)).
- 인스턴스 여러 대면 인스턴스별 풀로 쪼개진다. 쪼갠 작은 풀은 같은 이용률에서 대기가 길다(4절 관찰 2).

### 3. 운영 규칙으로 옮기기

- 목표 이용률을 곡선에서 정한다(예: 평소 60~70% — 예시, [reliability/22](../../reliability/22-capacity-and-load-testing/2-summary.md)가 부하 테스트로 정하는 법을 다룬다).
- 대기열에 상한을 두고 넘치면 빨리 거절한다. 무한 큐는 ρ ≥ 1에서 지연과 메모리를 끝없이 키운다([reliability/12](../../reliability/12-backpressure-and-load-shedding/2-summary.md)).
- 느린 작업(분산이 큰 작업)은 다른 풀로 분리해 빠른 작업의 Cs²를 낮춘다([reliability/28-bulkhead](../../reliability/28-bulkhead/2-summary.md)).

## 장애 시나리오와 대처

### 1. 이용률 80% 넘자 지연 급등 (⚠)

- 현상: 트래픽이 10~20% 늘었을 뿐인데 지연이 2배 이상 늘었다.
- 보이는 형태: p99·평균 응답 시간 급등, 스레드풀 큐 길이·풀 대기 시간 지표 상승, CPU·풀 이용률이 80~90%대. 오류율은 처음엔 그대로다.
- 원인: 대기 ∝ ρ/(1−ρ). ρ 0.8 → 0.9에서 M/M/1 평균 대기가 4 → 9배(E[S] 단위)가 된다(시뮬레이션: 3.98~4.05 → 8.83~9.17).
- 대처: 목표 이용률을 낮게 잡고(여유 대수), 오토스케일 기준을 이용률이 아니라 대기·지연 지표로도 건다. 넘치면 로드 셰딩.

### 2. 스레드풀·커넥션풀 크기 오산정 (⚠)

- 현상 A(과소): Little로 구한 평균 동시 처리 수를 그대로 풀 크기로 잡았다.
- 보이는 형태 A: `SQLTransientConnectionException: … Connection is not available, request timed out after 30000ms`(HikariCP 풀 고갈 — [database/21](../../database/21-connection-pooling/2-summary.md)), 풀 대기 스레드 수 증가.
- 원인 A: c = a면 ρ = 1이라 대기가 발산한다(계산: c = 200 발산, c = 201도 평균 183 ms).
- 현상 B(과대): 풀을 아주 크게 잡아 대기는 없앴는데 DB가 느려졌다.
- 원인 B: 병목이 DB로 옮겨 갔다. DB 안에서 동시 실행이 늘어 서비스 시간 E[S] 자체가 늘었다.
- 대처: Little로 평균을, Erlang C로 여유를 어림한 뒤 부하 테스트로 확정한다. 하류 한도(DB `max_connections`)와 함께 정한다.

### 3. 느린 작업이 섞여 모두가 느려짐

- 현상: 평균 처리 시간은 그대로인데 같은 풀을 쓰는 요청들의 대기가 늘었다.
- 보이는 형태: 같은 풀을 쓰는 짧은 요청의 p99가 오른다. 느린 작업(리포트·배치 쿼리)이 실행되는 시간대와 겹친다.
- 원인: P-K 공식에서 대기는 E[S²]에 비례한다. 가끔 아주 긴 작업이 Cs²를 키웠다(시뮬레이션: 같은 ρ = 0.8에서 Cs² 1 → 5.5로 평균 대기 4 → 12.7).
- 대처: 느린 작업을 별도 풀·별도 큐로 분리(벌크헤드), 작업 크기를 쪼개기, 타임아웃으로 긴 꼬리를 자르기.

### 4. 인스턴스별 큐로 쪼개져 대기가 늘어남

- 현상: 서버를 10대로 늘렸는데 1대일 때 기대한 만큼 지연이 줄지 않는다. 어떤 인스턴스는 줄이 길고 어떤 인스턴스는 논다.
- 보이는 형태: 인스턴스별 큐 길이·지연의 편차가 크다.
- 원인: 요청을 무작위·라운드로빈으로 나누면 인스턴스마다 따로 M/M/1에 가깝다. 공유 큐(M/M/c)보다 대기가 길다(시뮬레이션: 서버당 ρ = 0.8에서 3.98 vs 0.203, 약 20배 — 해석: 실제 로드밸런서·요청 분포에 따라 차이 크기는 다르다).
- 대처: 큐 길이·진행 중 요청 수를 보는 분배(최소 요청 수 우선 등), 또는 공유 작업 큐(워커가 꺼내 가는 구조)를 쓴다.

### 5. Little이 안 맞음 → 정상 상태가 아니다

- 현상: 측정한 동시 처리 수 L과 λ×W가 크게 다르다.
- 보이는 형태: 큐 길이·컨슈머 랙(lag)이 단조 증가한다. 지연이 시간에 따라 계속 늘어난다.
- 원인: 랙까지 계속 는다면 도착률이 처리율을 넘었을 가능성이 크다(ρ ≥ 1). 평균이 수렴하지 않아 Little·M/M/1 공식의 전제가 깨졌다. 또는 측정 창보다 체류 시간이 길어 창 끝에 걸친 요청이 빠졌다(reliability/21 실험의 N = 64 행).
- 대처: 처리율을 늘리거나(스케일 아웃) 도착을 줄인다(셰딩·속도 제한). 측정 창을 체류 시간보다 충분히 길게 잡는다.

## 핵심 문장

- Little 법칙 `L = λW`는 장기 평균·정상 상태에서 분포 가정 없이 성립하고, 상자를 어떻게 그리느냐에 따라 대기열·서버·전체에 각각 쓴다.
- M/M/1에서 평균 대기는 `ρ/(1−ρ)·E[S]`다. ρ가 0.8 → 0.9 → 0.99로 가면 4 → 9 → 99배가 된다.
- 평균 서비스 시간이 같아도 분산이 크면 대기가 커진다(P-K: `(1 + Cs²)/2` 배).
- 같은 이용률이면 서버 여럿이 공유 큐 하나를 쓰는 편이 따로 줄을 서는 것보다 대기가 훨씬 짧다.
- Little로 구한 평균 동시 처리 수는 필요한 풀 크기가 아니다. 그만큼만 두면 이용률 100%라 대기가 발산한다. 여유는 Erlang C로 어림하고 부하 테스트로 확정한다.
