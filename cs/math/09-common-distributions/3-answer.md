# math/09-common-distributions — 정답

## 정답

### 1. 무엇을 세나

| 상황 | 분포 | 평균 |
|---|---|---|
| ① 1000건 중 실패 수(실패율 p, 독립) | 이항(1000, p) | 1000p |
| ② 첫 성공까지 시도 수(성공률 p) | 기하(p) | 1/p |
| ③ 초당 도착 수 | 포아송(λ) | λ |
| ④ 다음 요청까지 시간 | 지수(λ) | 1/λ |
| ⑤ 순위별 요청 빈도 | Zipf(s, N) | 1위 비율 1/H(N,s) |

- ①②③④는 독립 가정 위의 모델이다. ⑤는 관측된 쏠림을 기술하는 모델이다.

### 2. 칸 길이

- 칸당 원소 수 ≈ 포아송(0.5): 빈 칸 `e^(−0.5)` = 60.65%, 길이 1 = 30.33%, 길이 2 = 7.58%.
- 실험 A(OpenJDK 21, seed 42): 60.67%, 30.32%, 7.57%. 최대 칸 길이 7.
- OpenJDK 21 `HashMap.java` 주석이 같은 포아송(0.5) 표를 싣고, 길이 8의 확률을 0.00000006으로 적는다. 실제 트리화는 이미 8개인 칸에 9번째가 들어올 때 시도되고, 테이블이 64칸 미만이면 리사이즈로 대신한다(`putVal`·`treeifyBin`). 그 길이가 이렇게 드물어 정상 해시에서는 트리 칸이 거의 쓰이지 않는다. 평균 0.5와 최대 7의 차이는 평균과 꼬리의 차이다.

### 3. 근사 조건과 깨지는 원인

- 이항(n, p) ≈ 포아송(np): n이 크고 p가 작을 때. 칸 예에서는 n = 524,288, p = 2⁻²⁰이라 소수 일곱째 자리 근처까지 같았다.
- 포아송 과정의 가정은 "겹치지 않는 구간의 도착 수가 독립"이고, 도착률 λ가 일정해 길이 t 구간의 도착 수가 포아송(λt)이라는 것이다. 깨지는 원인:
  - 공통 원인: 배치 작업 시작, 푸시 알림 발송, 정각 cron.
  - 재시도 폭풍: 실패가 다음 도착을 만든다(도착이 서로 의존).
  - 상위 계층의 묶음: 페이지 하나가 API 수십 건을 동시에 부른다.
  - 도착률 변화: 시간대별 트래픽 곡선처럼 λ가 구간 안에서 바뀐다.
- Paxson·Floyd(1995)는 사용자 세션 도착에는 포아송이 맞지만 다른 광역 도착 과정에는 맞지 않음을 보였다.

### 4. 포아송 vs 버스트

- 포아송: 분산 = 평균 = 100. p99 = 124(정확 계산).
- 버스트: 분산 = `E[λ] + Var[λ] = 100 + 22,500 = 22,600`.
- 실험 B(10만 초, seed 42): 포아송 분산 99.9·p99 124, 버스트 분산 22,319·p99 580·p50 51.
- 124/s 용량을 넘는 초: 포아송 0.89%, 버스트 9.86%.

### 5. 기하분포와 무기억성

- 평균 시도 수 1/p = 3.33(실험 D 3.331).
- 무기억성: `P(시도 > 8 | 시도 > 3) = P(시도 > 5) = 0.7^5 = 0.1681`(실험 D seed 42: 0.1687).
- 장애에서 틀리는 이유: 시도들이 독립이 아니다. 과부하 때 실패는 서로 상관되어, 재시도도 함께 실패하고 부하만 늘린다. 재시도 예산·서킷 브레이커가 필요하다.

### 6. 정규 근사로 p99

- `33.0 + 2.326 × 43.2 ≈ 133.5ms`. 실제 로그정규 p99는 204.8ms(08 실험 C).
- 68-95-99.7은 정규분포의 비율이다(대칭인 균등분포도 ±1σ 안은 약 57.7%다). 지연은 오른쪽 꼬리가 길어, 평균+표준편차 어림이 p99를 과소평가한다.

### 7. Zipf 캐시

- 1위 키 비율 = `1/H(100000) = 1/12.09 = 8.27%`.
- 실험 C(키 10만, 요청 200만, seed 42): s=1에서 캐시 1,000개(1%) LRU 적중률 50.56%(정적 최적 61.91%).
- s=0.8이면 같은 캐시 20.51%(정적 최적 33.95%). s가 조금만 달라도 적중률이 크게 바뀐다.

### 8. 캐시와 샤드

- 캐시: 소수 키가 요청 대부분이라 작은 캐시로 높은 적중률을 낸다(균등 가정 1% → Zipf 51%).
- 샤드: 1위 키는 한 샤드로만 간다. 샤드 16개면 평균 몫이 6.25%인데 1위 키 하나가 8.27%다. 그 샤드는 1위 키 + 자기 몫의 다른 키들을 받아 평균의 약 2배(실험 C 1.99배)가 된다. 같은 해시로 균등 접근이면 1.02배였다.
- 샤드를 늘려도 1위 키의 8.27%는 그대로 한 샤드에 남는다.

### 9. 초 단위 스파이크 진단

1. 접근 로그를 초(또는 100ms) 단위로 세어 분산/평균과 p99·p99.9를 낸다. 1보다 훨씬 크면 버스트다(1 근처는 포아송과 양립할 뿐 증명은 아니다).
2. 스파이크 시각을 배치·cron·푸시·배포·재시도 지표와 맞춰 공통 원인을 찾는다.
3. 키별 비율로 핫키(Zipf)인지도 본다 — 특정 샤드·인스턴스만 넘치면 핫키 쪽이다.
4. 대처: 용량을 짧은 구간 p99에 맞춘다. 공통 원인에 지터를 넣는다. 넘치는 순간은 백프레셔·부하 차단, 핫키는 복제·분할.
