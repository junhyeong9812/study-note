# math/05-counting-and-birthday-bound — 정답

## 정답

### 1. 왜 √N에서 충돌이 흔한가

- 충돌은 ID 하나가 아니라 **두 ID의 쌍**에서 일어난다. k개면 쌍이 C(k, 2) = k(k−1)/2개다.
- 쌍 하나가 겹칠 확률이 1/N이므로 충돌 쌍 기댓값은 k(k−1)/2N이다. k가 √N 근처면 이 값이 1 근처가 된다.
- 32비트: √(2N·ln 2) ≈ 77,163개에서 충돌 확률 50%(공식 계산). 43억의 0.002% 정도다.

### 2. Snowflake 세기

- ms당 machine당 최대 2^12 = **4,096개**. 곱 법칙의 마지막 칸(sequence)이 상한이다.
- 2^41 ms ≈ 2.2×10¹² ms ≈ **69.7년**(README: "69 years", 사용자 정의 epoch부터).
- 전체 ID 수 = 2^41 × 2^10 × 2^12 = 2^63. 독립적으로 고르는 칸의 곱 = **곱 법칙**(MCS 15.2).

### 3. 비둘기집 vs 생일 한계

| | 보장 | 가정 |
|---|---|---|
| 비둘기집(MCS Rule 15.8.1) | k > N이면 충돌이 **반드시** 있다 | 없음(어떤 배정이든) |
| 생일 한계(MCS 17.4) | k ≈ √N이면 충돌이 **흔하다**(확률) | 균일·독립 |

- 2,000개: 비둘기집은 아무것도 보장하지 않는다(2,000 < 65,536). 생일 한계로 기대 충돌 쌍 C(2000,2)/65536 ≈ 30.5. 실험(git 2.43.0)에서 29쌍이 나왔다.
- 65,537개: 비둘기집으로 겹치는 prefix가 **반드시** 있다.

### 4. 한계식과 N=365, k=23

- 1 − exp(−k(k−1)/2N) **<** P(충돌 ≥ 1) **≤** k(k−1)/2N.
  - 아래 한계: P(충돌 없음) = Π(1 − i/N) < Π e^(−i/N) = exp(−k(k−1)/2N)(1 − x < e^(−x), MCS (17.7)).
  - 위 한계: 쌍마다 확률 1/N인 사건들의 합집합 한계.
- N=365, k=23 계산(Python 3.12.3):

```text
k= 23 exact=0.5073  1-exp(-k(k-1)/2N)=0.5000  1-exp(-k^2/2N)=0.5155  union k(k-1)/2N=0.6932
```

- 아래 한계는 `1 − exp(−k(k−1)/2N)` = 0.5000(정확값 0.5073보다 작다).
- `1 − exp(−k²/2N)` = 0.5155는 정확값보다 커서 아래 한계가 아니다. 위 한계도 아니다(합집합 한계 0.6932보다 작을 뿐, 한계로 증명된 식이 아니다). 그냥 근사다.

### 5. 32비트 PK 첫 실패 지점과 77,163개 실험

- 첫 실패: sqlite 실험(시드 1~5)에서 61,451 · 101,404 · 47,563 · 102,983 · 59,993행. 수만~10만 근처에서 나고, 실행마다 두 배 넘게 흔들린다.
- k = 77,163, 400회 시뮬레이션: 충돌 회차 비율이 시드 1·2·3에서 0.470·0.515·0.528. 이론값 0.5000 근처다.
- 운영 해석: 발급 수가 7만 대에 들어서면 "가끔" 충돌이 정상 동작이다. 버그처럼 보이지만 설계 문제다.

### 6. 10억 개, 10⁻⁶에 필요한 비트

- k²/2N ≤ p에서 b = log₂N ≥ 2·log₂k + log₂(1/(2p)) = 2·29.9 + 18.9 ≈ **78.7비트**(공식 계산).
- UUIDv4의 무작위 부분은 122비트라 충분하다. 단 생성기가 균일·독립이라는 전제에서다(7번).

### 7. 배포 직후 UUID 충돌

- 깨진 전제: **균일·독립.** 생일 한계는 값이 고르게, 서로 독립으로 뽑힐 때의 계산이다.
- 흔한 원인
  - 여러 인스턴스가 같은 시드로 PRNG를 시작했다(이미지에 고정 시드, 기동 시각을 시드로 사용).
  - 엔트로피가 부족한 생성기, 직접 만든 "무작위" ID(시각 + 짧은 난수).
- 확인: 충돌한 ID들의 생성 호스트·기동 시각을 짝지어 본다. 생성 코드가 `UUID.randomUUID()`/`SecureRandom`인지, `setSeed`나 고정 시드를 쓰는지 본다. 사례는 Debian OpenSSL(2008, [security/09](../../security/09-randomness-and-key-management/2-summary.md)).

### 8. git 짧은 SHA가 모호해짐

- 저장소 객체 수가 늘었다. 예전엔 그 prefix를 가진 객체가 하나였지만, 지금은 같은 prefix의 객체가 둘 이상 생겼다.
- 생일 한계로 보면 hex 4자리(16비트)는 객체 수천 개에서 이미 수십 쌍이 겹친다(실험: 2,000개에 29쌍). 7자리(28비트)도 객체가 1만 단위가 되면 겹치는 쌍이 생기기 시작한다(k²/2N ≈ 10⁸/(2·2.7×10⁸) ≈ 0.19쌍, 공식 계산).
- git 문서도 자동 약어 길이는 "당분간" 유일하도록 정한다고 적는다(`core.abbrev`). 기록에는 전체 SHA를 남긴다.

### 9. 연결

- 해시 테이블: 버킷 N개에 키 k개 → 같은 버킷에 떨어지는 쌍 수가 k(k−1)/2N. 로드 팩터와 체인 길이의 출발점([data-structure/05-hashmap](../../data-structure/05-hashmap/2-summary.md)).
- 블룸 필터: 비트 m개에 원소 n개를 해시 k개로 표시할 때 특정 비트가 0으로 남을 확률을 세어 오탐률을 얻는다([data-structure/11-bloom-filter](../../data-structure/11-bloom-filter/2-summary.md)).
- 암호 해시: n비트 출력의 충돌을 무차별로 찾는 데 약 2^(n/2)번이면 된다 — 생일 한계를 공격에 쓴 것(생일 공격, [security/04](../../security/04-hash-functions-and-digests/2-summary.md)).
