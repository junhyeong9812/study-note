# math/15-numerical-stability — 정답

## 정답

### 1. 사라지는 작은 수

- `1e16 + 1.0` × 1000 → `10000000000000000.0`. 1000이 전부 사라진다.
  - 1e16은 [2⁵³, 2⁵⁴) 구간이라 간격이 2다(`Math.ulp(1e16) = 2.0`). `1e16 + 1`은 1e16과 1e16+2의 정확히 가운데라 짝수 쪽(1e16)으로 반올림된다. 매번 같은 일이 반복된다.
- `float`에 `1.0f` × 2천만 → `16777216.0`(= 2²⁴).
  - `float` 가수는 24비트라 2²⁴부터 간격이 2다. 그 뒤 `+1.0f`는 반올림으로 사라진다. 카운터가 멈춘다.

### 2. 오차가 쌓이는 이유

- Goldberg가 정리 8(Kahan 합) 바로 뒤에 든 비교: 단순 합 = `Σ xⱼ(1 + δⱼ)`, `|δⱼ| < (n − j)ε`. 앞쪽 항은 이후 모든 덧셈의 반올림을 겪어 최대 n·ε까지 흔들린다.
- 그래서 최악 오차는 대략 `n · u · Σ|x|`에 비례한다. 1천만 항이면 한 번 오차의 최대 1천만 배다.
- 또 누적값이 커지면 간격도 커져, 작은 항의 하위 비트가 잘린다. 실제 오차는 반올림이 위아래로 섞여 최악보다 작은 경우가 많다.

### 3. 합산법별 차이

| 방법 | 정확한 합과 차이 |
|---|---|
| 단순 `for` | +1.969×10⁻⁴ |
| Kahan | +4.578×10⁻⁷ |
| 쌍별 합 | −4.959×10⁻⁷ |
| `DoubleStream.sum()` | +4.578×10⁻⁷ |
| `reduce(0, Double::sum)` | +1.969×10⁻⁴ |

- Kahan과 `DoubleStream.sum()`이 같은 값, 단순 합과 `reduce`가 같은 값이다.
- 이 JDK(21.0.12)의 `sum()`은 보상 합으로 동작했다. Javadoc은 "보상 합으로 구현될 수 있다"고만 적는다(보장 아님).
- Kahan의 남은 오차는 결과 근처 ulp(약 9.5×10⁻⁷)보다 작다. 마지막 반올림 한 번 수준이다.

### 4. 병렬 reduce의 흔들림

- 같은 설정에서 5번: 실험에서는 5번 모두 같은 값(4999835704.520057)이었다. 분할 방식이 같으면 덧셈 나무도 같다.
- 병렬도 1·3·7·15: `.520057`, `.520033`, `.520006`, `.519991`로 네 값이 다 다르다. 나무 모양이 바뀌어 반올림 지점이 바뀐다.
- 같은 조건의 병렬 `sum()`은 네 설정 모두 `.520000`이었다.
- 교훈: 이 실험에서는 실행 회차별 차이가 보이지 않았고, 분할 방식(코어 수·병렬도·파티션 수)을 바꾸자 결과가 달라졌다. `reduce`는 결합법칙을 만족하는 연산을 요구하는데(Javadoc) 부동소수 덧셈은 아니므로, 같은 설정의 반복 실행이 같은 값을 낸다는 보장도 없다. 그래서 개발 PC와 운영 서버에서 결과가 다를 수 있다. `DoubleStream.sum()` Javadoc도 같은 입력에서 출력이 달라질 수 있다고 적는다.

### 5. Kahan 합 따라가기

```text
y = x − c;  t = s + y;  c = (t − s) − y;  s = t;

s = 1e16, c = 0, x = 1:
  y = 1
  t = 1e16 + 1 = 1e16   (반올림으로 1을 잃음)
  c = (1e16 − 1e16) − 1 = −1    ← 잃은 1을 음수로 기억
  s = 1e16
다음 x = 1:
  y = 1 − (−1) = 2
  t = 1e16 + 2          (간격이 2라 표현 가능 — 두 번 분량이 함께 들어감)
  c = (1e16+2 − 1e16) − 2 = 0
```

- `c`는 직전 덧셈에서 **잘려 나간 부분의 음수**다. 다음 항에 되돌려 준다.
- 대수적으로 `((s + y) − s) − y = 0`이지만, 부동소수에서는 `s + y`가 반올림되므로 0이 아니다. 그 차이가 바로 잃어버린 비트다.
- Goldberg 정리 8: 각 항의 섭동이 `2ε` 이하로 n과 무관해진다(고차 항 `O(N·ε²)·Σ|xⱼ|`은 남는다).

### 6. `-ffast-math`

- 실험(gcc 13.3.0, 1e8 + 0.1 × 천만):
  - `-O2`: naive 100999999.940395, Kahan 101000000.000000
  - `-O2 -ffast-math`: naive와 Kahan 모두 100999999.940395
- `-ffast-math`는 부동소수 재결합을 허용한다. 컴파일러가 `c = (t − s) − y`를 0으로 정리했다. `gcc -S`로 보면 `-ffast-math` 판 Kahan 루프에는 뺄셈(`subsd`)이 없고 단순 합과 같은 덧셈만 남는다(사실 점검에서 확인).
- Java는 JLS §15.7.3이 결합법칙 같은 대수 항등식으로 식을 바꿔 쓰는 것을 금지한다(모든 값에서 같다고 증명되는 경우만 예외). 그래서 `javac`·JIT은 Kahan을 지우지 않는다.

### 7. `(1 − cos x)/x²`

- x = 10⁻⁸: `cos x`가 1로 반올림되어 `1 − cos x = 0`. 결과 **0.0000000000**.
- 참값은 x → 0에서 0.5다(`1 − cos x ≈ x²/2`).
- 고친 식 `2 sin²(x/2)/x²`는 0.5000000000. 뺄셈을 없애 파국적 상쇄를 피했다.
- x = 10⁻⁶에서도 직접 식은 0.5000444503으로 넷째 자리부터 틀렸다.

### 8. 표준편차 `NaN`

- 값이 크고(예: 10⁹ 근처, 에포크 기반 시각) 분산이 작으면 `E[X²]`(10¹⁸ 근처, 간격 128)와 `E[X]²`가 거의 같다. 빼면 원래 반올림 오차만 남는다.
- 실험: 1e9 + {4, 7, 13, 16}에서 `E[X²] − E[X]² = −128`(참값 22.5). `Math.sqrt(−128) = NaN`.
- `NaN`과의 대소·`==` 비교는 거짓이라 `stddev > 문턱` 알람이 조용히 꺼진다.
- 고치는 법: 웰퍼드 갱신(실험: 22.5000), 또는 첫 값·기준 시각을 빼고 계산. 음수·`NaN`은 에러로 드러낸다.

### 9. 정산 합계 불일치

- 확인 순서
  1. 금액을 어떤 타입으로 누적했나(`float`/`double`/`long`/`BigDecimal`). `float`이면 실험에서 약 270만 원 차이.
  2. 같은 데이터를 `BigDecimal`(또는 정수 센트)로 다시 더해 차이를 잰다. `double` 단순 합은 실험에서 1.969×10⁻⁴ 차이 — 센트로 반올림하면 같지만 `compareTo`로 비교하면 불일치다.
  3. 병렬 집계면 병렬도·파티션 수를 바꿔 결과가 흔들리는지 본다.
- 설계 대처
  - 금액은 `long` 최소 단위 또는 `BigDecimal`로 누적한다(domain-modeling/14). 넘침은 `Math.addExact`로 드러낸다.
  - 통계용 부동소수 합은 보상 합을 쓰고, 원장 비교는 통화 자릿수로 반올림한 뒤 한다.
