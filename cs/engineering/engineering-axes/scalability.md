# Scalability (확장성)

> 이 컬렉션의 인덱스는 [README.md](./README.md)에서 시작한다.\
> 출처: `jun-bank/docs/study/notes/axes/scalability.md` (본체) + `08-engineering-axes-deep.md` §2 (「수직/수평」·「확장 사다리」 흡수) · 이관일 2026-09-16.\
> 본문 표·절은 **원고**를 고쳐 쓴 것이다. 「한눈에」의 비유·그림과 맨 끝 `[Claude 추가]`는 **Claude 보강**이다.

**지키는 것: 성장 여력.** "지금 빠른가"가 아니라 "**10배가 되면 무엇이 먼저 터지나**"의 축이다.

---

## 한눈에 — 쉽게 말하면

점심시간 김밥집을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
손님이 10배로 몰렸다. 무엇이 먼저 막히나?

주문 받는 직원을 2명으로 → 이제 김밥 마는 손이 병목
김밥 마는 사람을 늘림     → 이제 재료 다듬는 도마가 병목
도마를 늘림               → 이제 계산대 한 대가 병목
```

**서버도 똑같은 구조다.** 앱 서버를 늘리면 DB 커넥션이, 커넥션을 늘리면 DB CPU가, 읽기 복제본을 붙이면 쓰기가 병목이 된다.\
확장은 병목을 **없애는** 게 아니라 **옮기는** 것이다. 그래서 확장성 이해의 척도는 "지금 병목이 어디인지 말할 수 있는가"다.

---

## Performance와의 구분

| | Performance | Scalability |
|---|---|---|
| 질문 | 요청 하나가 얼마나 빠른가 | 요청이 10배 오면 어떻게 되나 |
| 개선 | 10ms → 5ms | 100 RPS → 1,000 RPS |
| 한계 | 코드·알고리즘 | **구조** |

**핵심**: 단일 요청이 아무리 빨라도 **수평 확장이 막혀 있으면 확장성은 0이다.**\
반대로 느려도 확장 가능하면 서버를 더 넣으면 된다 — **돈으로 풀 수 있는 문제와 아닌 문제**의 구분이다. → [`./performance.md`](./performance.md)

> **수직 확장(scale up) / 수평 확장(scale out)** — 수직은 장비 하나를 더 크게, 수평은 장비를 더 많이. 수직은 코드 변경이 없어 쉽지만 물리적 상한이 있고, 수평은 상태를 밖으로 빼야 해서 어렵지만 상한이 없고 가용성에도 기여한다.\
> 예: DB 서버 램을 64GB→256GB로 올리면 수직, 앱 서버를 1대→4대로 늘리면 수평.

## 확장성의 본질 3가지

> 출처: 원고 §2

### ① 확장은 병목을 옮기는 것이다

```text
앱 증설        → 병목이 DB 커넥션으로
DB 커넥션 확대 → 병목이 DB CPU로
읽기 복제본    → 병목이 쓰기로
샤딩           → 병목이 크로스 샤드 쿼리로
```

> 확장성 이해의 척도는 "**지금 병목이 어디인지 말할 수 있는가**"다.

### ② 직렬 구간이 상한을 정한다

장비를 늘려 풀리는 병목(CPU, 메모리, IOPS)과, **늘려도 안 풀리는 병목**(단일 리더, 전역 락, 단일 파티션)은 다르다.

- 전자는 돈으로 해결.
- **후자는 설계로만 해결.**

### ③ 조율 비용은 노드 수의 제곱으로 는다

노드를 늘렸는데 **오히려 느려지는** 경우가 있다.\
원인은 노드 간 상태를 맞추는 비용(분산 락, 분산 트랜잭션, 캐시 동기화, 브로드캐스트)이다.

> **그래서 "조율이 필요 없게 데이터를 나누는 것(파티셔닝)"이 확장의 본질이다.**

---

## 상태가 확장을 막는다

수평 확장을 막는 것은 대부분 **상태**다.

| 상태 | 증상 | 해법 |
|---|---|---|
| 세션을 서버 메모리에 | 다른 서버로 가면 로그아웃 | 외부 저장소 / 토큰 |
| 로컬 파일 | 다른 서버에서 못 찾음 | 오브젝트 스토리지 |
| 인메모리 캐시 | 인스턴스마다 값이 다름 | 분산 캐시 / 짧은 TTL |
| **인메모리 스케줄러** | **N대면 N번 실행** | 리더 선출 / DB 락 |
| 로컬 락 | 인스턴스 간 무효 | DB 락 / 파티션 직렬화 |
| 인메모리 카운터 | 합계가 틀림 | 중앙 집계 |

**중요**: 상태는 사라지지 않는다. **앱에서 빼서 전용 저장소로 밀어내는 것**이다.\
→ 그래서 **확장의 최종 난이도는 항상 데이터 계층에 있다.**

```text
계층별 확장 난이도

쉬움   앱 서버   (무상태면 그냥 늘림)
  │    캐시     (샤딩 가능, 유실 허용)
  │    DB 읽기  (복제본, 지연 감수)
어려움 DB 쓰기  (샤딩 — 되돌리기 어려움)
```

> **무상태(stateless)** — 요청 처리에 필요한 상태를 서버가 자기 안에 들고 있지 않는 성질. 어느 서버가 받아도 같게 처리된다.\
> 예: 로그인 정보를 서버 메모리 세션이 아니라 토큰이나 외부 저장소에 두면, 다음 요청이 다른 서버로 가도 로그아웃되지 않는다.

## 확장 사다리 (순서를 지킨다)

> 출처: 원고 §4 + `08-engineering-axes-deep.md` §2

```text
1. 측정                    ← 병목 확인 없이 아무것도 하지 않는다
2. 낭비 제거 (N+1, 인덱스)  ← 유일하게 공짜에 가깝다. 복잡도 증가 없음
3. 캐시
4. 수직 확장               ← 장비 하나로 되면 그게 제일 싸고 단순하다
5. 읽기 복제본
6. 파티셔닝
7. 기능별 분할
8. 샤딩                    ← 마지막. 되돌리기 가장 어렵다
```

> **4번을 건너뛰고 8번으로 가는 게 가장 흔한 오버엔지니어링이다.**\
> 현대 서버 1대의 성능은 직관보다 훨씬 높다. 많은 서비스가 잘 튜닝된 DB 한 대로 충분하다.

## 각 수단이 사는 문제와 새로 생기는 문제

| 수단 | 해결 | 새로 생기는 것 |
|---|---|---|
| 무상태화 | 앱 수평 확장 | 세션 저장소 의존 |
| 읽기 복제본 | 읽기 부하 | **복제 지연** (쓰고 바로 읽으면 아직 없다) |
| 캐시 | 반복 조회 | 무효화, 스탬피드, 정합성 |
| 샤딩 | 쓰기·용량 | 크로스 샤드 조인/트랜잭션 불가, **샤드 키는 되돌리기 어려움** |
| 큐 | 피크 흡수 | 순서, 중복, 지연, 백프레셔 |
| CQRS | 조회 최적화 | 최종적 일관성 |

> **모든 확장 수단은 정합성이나 복잡도를 대가로 낸다.** 공짜인 건 2번(낭비 제거)뿐이다.

> **복제 지연(replication lag)** — 쓰기가 복제본까지 퍼지는 데 걸리는 시간. 그 사이 "방금 쓴 걸 바로 읽으면" 아직 없을 수 있다.\
> 예: 글을 올리고 바로 목록을 새로고침했는데 방금 글이 안 보이면, 읽기 요청이 아직 안 따라온 복제본으로 갔을 수 있다.

## 흔한 착각

| 착각 | 실제 |
|---|---|
| "큐를 넣었으니 부하를 견딘다" | 큐는 **피크만 완충**한다. 평균 유입 > 처리면 지연이 무한 증가 |
| "오토스케일링이 있으니 괜찮다" | 직렬 병목이면 무의미. **앱 스케일아웃이 DB 커넥션을 폭증시켜 DB를 죽인다** |
| "복제본을 늘리면 쓰기도 분산된다" | 모든 복제본이 **같은 쓰기를 다 수행**한다 |
| "마이크로서비스가 확장성이 좋다" | 서비스 분리는 **조직 확장**을 위한 것. 성능 확장과는 별개 |
| "서버를 늘리면 빨라진다" | 늘려서 좋아지는 건 **처리량**이지 개별 응답 시간이 아니다 |

## 확장성을 말하는 방식

**나쁜 답변**: "트래픽이 늘어도 괜찮게 설계했습니다."

**좋은 답변의 형태**

> "현재 병목은 X입니다. 지금 구조로 Y까지 버팁니다. 그 이상은 Z를 해야 하고, 아직 안 한 이유는 (복잡도 대비 필요성 / 아직 그 규모가 아님)입니다."

**"안 한 이유를 말할 수 있는 것"이 핵심이다.** 모든 확장 기법을 적용한 시스템은 오버엔지니어링이고, 그 자체가 부채다.

## 체크리스트

- [ ] 지금 병목이 어디인지 아는가 (측정 근거가 있는가)
- [ ] 앱이 무상태인가 (위 표의 6개 항목)
- [ ] 인스턴스를 2배로 늘리면 정말 처리량이 2배가 되는가
- [ ] **앱 인스턴스 수 × 커넥션 풀 크기**가 DB 한계 안에 있는가
- [ ] 복제 지연을 모니터링하고 있는가
- [ ] 데이터 증가율과 보관 정책이 있는가
- [ ] 부하 테스트로 **붕괴 지점과 붕괴 방식**을 아는가

## 핵심 문장

- **확장성은 "요청 하나가 빠른가"가 아니라 "10배가 오면 무엇이 먼저 터지나"다.**
- **확장은 병목을 없애는 게 아니라 옮기는 것 — 지금 병목을 짚을 수 있어야 한다.**
- **수평 확장을 막는 건 대부분 상태다. 상태는 없애는 게 아니라 전용 저장소로 밀어낸다.**
- **확장의 최종 난이도는 항상 데이터 계층(특히 쓰기)에 있다.**
- **수직 확장(4번)을 건너뛰고 샤딩(8번)으로 가는 게 가장 흔한 오버엔지니어링이다.**

## 용어 풀이

- **성장 여력(Scalability)** — 부하가 늘 때 구조를 바꿔 감당할 수 있는 여지.
- **수직 확장(Scale Up)** — 장비 하나를 더 크게. 쉽지만 물리적 상한이 있다.
- **수평 확장(Scale Out)** — 장비를 더 많이. 상태 처리가 필요하지만 상한이 없고 가용성에도 기여.
- **무상태(Stateless)** — 서버가 요청 상태를 자기 안에 들고 있지 않는 성질. 수평 확장의 전제.
- **파티셔닝(Partitioning)** — 자원을 키로 나눠 조율 자체를 없애는 것.
- **샤딩(Sharding)** — 쓰기·용량을 나누려 데이터를 여러 저장소로 분할. 샤드 키는 되돌리기 어렵다.
- **복제 지연(Replication Lag)** — 쓰기가 복제본에 반영되기까지의 시간차.
- **CQRS** — 쓰기 모델과 읽기 모델을 분리하는 설계. 조회는 빨라지지만 최종적 일관성을 감수한다.
- **백프레셔(Backpressure)** — 처리 속도보다 유입이 빠를 때 상류에 "천천히"를 전달하는 흐름 제어.
- **오버엔지니어링(Over-engineering)** — 지금 필요 없는 규모·유연성에 복잡도를 미리 지불하는 것.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문과 섞어 인출하지 않는다.

- **암달의 법칙과 USL.** "직렬 구간이 상한을 정한다"(§2 ②)의 이론적 뼈대. 암달의 법칙은 직렬 구간이 5%만 있어도 무한히 병렬화해도 20배 이상 못 빨라진다고 말한다. USL(Universal Scalability Law)은 여기에 "조율 비용"(§2 ③) 항을 더해, 노드를 늘리면 어느 지점부터 **오히려 느려지는** 곡선을 설명한다.
- **Little's Law.** 대기열 길이 = 도착률 × 평균 체류시간. 성능 개선(체류시간↓)이 곧 용량 확보(같은 동시성으로 더 많은 처리)로 이어지는 이유를 한 줄로 준다 — 그래서 "낭비 제거(2번)가 공짜에 가깝다"가 성립한다.
- **왜 샤드 키가 유독 되돌리기 어렵나.** 샤드 키를 바꾸면 이미 나뉘어 저장된 데이터를 전부 다시 나눠 옮겨야(리샤딩) 하고, 그동안 쓰기는 계속 들어온다. 코드 리팩터링과 달리 "움직이는 데이터를 옮기는" 일이라 무중단으로 하기가 매우 까다롭다.
