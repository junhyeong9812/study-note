**지키는 것: 인수인계 가능성.** 6개월 뒤의 내가(또는 남이) **안전하게 고칠 수 있는가.**

## 한눈에 — 쉽게 말하면

두 종류의 서랍장을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
겉만 예쁜 서랍장            평범하지만 라벨 붙은 서랍장
+------------------+       +------------------+
| 어느 서랍에 뭐가   |       | 서랍마다 라벨      |
| 있는지 열어봐야 앎  |       | 뭘 건드리면 뭐가   |
| 하나 옮기면 다     |       | 바뀌는지 보임      |
| 흔들림            |       |                  |
+------------------+       +------------------+
  → 예쁜데 못 고침           → 투박한데 안전하게 고침
```

**코드도 똑같은 구조다.** 예쁜데 못 고치는 코드가 있고, 투박한데 안전하게 고칠 수 있는 코드가 있다.\
유지보수성은 미학이 아니라 **변경 비용**의 문제다 — 질문을 "깨끗한가"에서 "안전하게 바꿀 수 있는가"로 옮기는 축이다.

---

## 질문을 바꾼다

**"코드가 깨끗한가" → "변경이 안전한가"**

### 측정 가능한 신호

| 신호 | 의미 |
|---|---|
| 기능 하나 바꿀 때 여는 파일 수 | 결합도 |
| 변경 후 배포까지 걸리는 시간 | 파이프라인·테스트 신뢰도 |
| 신규 인원이 첫 PR을 내는 데 걸리는 시간 | 이해 가능성 |
| 버그 수정이 다른 버그를 만드는 비율 | 회귀 방어 수준 |
| 장애 시 원인 파악에 걸린 시간 | 관측 가능성 |

## 구성 요소

> 출처: 원고 §2

### ① 결합도↓ 응집도↑

- 한 곳을 고치면 몇 곳이 따라 바뀌는가 = 결합도.
- 관련된 코드가 한 곳에 모여 있는가 = 응집도.
- **판별법**: 기능 하나를 바꿀 때 열어야 하는 파일 목록을 실제로 세어본다.

> **결합도 / 응집도** — 결합도는 "A를 바꿀 때 B도 바꿔야 하는 정도"(낮을수록 좋다), 응집도는 "한 덩어리 안의 것들이 한 목적으로 뭉친 정도"(높을수록 좋다).\
> 예: 주문 로직을 고쳤을 뿐인데 결제·배송 파일까지 열어야 하면 결합도가 높은 것이다.

### ② 테스트 가능한 구조 ← 가장 중요

> 질문은 "테스트를 짰는가"가 아니라 **"테스트를 짤 수 있는 구조인가"**다.

테스트가 안 짜지는 코드는 대개:

- 의존성이 안에 하드코딩되어 있다 (직접 `new`, static 호출).
- **부수효과와 로직이 섞여 있다.**
- 시간(`now()`), 랜덤, 외부 API에 직접 묶여 있다.

> **테스트 용이성은 설계 품질의 지표다.** 별개 항목이 아니라 결합도의 관측 수단이다.

**추가로 중요한 것**: 테스트가 느리면(전부 통합 테스트) **아무도 안 돌린다.** 빠른 단위 테스트 층이 필요하다.

### ③ 관측 가능성 (Observability)

**운영 중인 시스템은 못 보면 못 고친다.** 유지보수성의 절반은 여기에 있다.

| 축 | 답하는 질문 | 필수 조건 |
|---|---|---|
| **로그** | 무슨 일이 있었나 | **구조화 + 상관관계 ID** |
| **메트릭** | 얼마나 자주, 얼마나 오래 | 골든 시그널 |
| **트레이스** | 어디서 시간을 썼나 | 분산 시스템에선 필수 |

> **상관관계 ID(trace id)가 전 구간에 전파되지 않으면**, 장애 때 로그를 눈으로 맞춰가며 추적하게 된다. 이것이 유지보수 비용의 가장 큰 항목 중 하나다.

> **관측 가능성(observability)** — 시스템 밖에서 남은 신호(로그·메트릭·트레이스)만으로 안에서 무슨 일이 났는지 알아낼 수 있는 성질.\
> 예: 결제가 느려졌을 때, 트레이스를 보고 "결제사 호출 구간에서 3초 걸렸다"를 짚어낼 수 있으면 관측 가능성이 있는 것이다.

### ④ 일관성

- 같은 문제를 같은 방식으로 푼다.
- **일관되게 평범한 것이 군데군데 뛰어난 것보다 낫다** — 읽는 사람이 예측할 수 있기 때문.
- 컨벤션은 문서가 아니라 **자동화(린터·포매터·CI)로 강제**한다. 사람이 지키게 하면 안 지켜진다.

### ⑤ 타입 안정성

컴파일 타임에 잡히는 버그는 런타임 버그보다 훨씬 싸다. 리팩터링의 안전망이기도 하다.

### ⑥ 문서화 — 무엇을 남기나

| 남기지 않는다 | 남긴다 |
|---|---|
| 코드를 읽으면 아는 것 (**무엇을** 한다) | 코드를 읽어도 모르는 것 (**왜** 이렇게 했나) |
| | 검토했다가 **버린 대안과 그 이유** |
| | 제약 조건 (외부 시스템 한계, 계약, 규제) |
| | 알려진 함정 ("여기는 순서를 바꾸면 안 됨") |

**설계 결정 기록(ADR)**: 결정·맥락·대안·결과를 짧게 남긴다. 6개월 뒤 "이거 왜 이렇게 돼 있지?"를 막는 가장 저렴한 수단이다.

> **ADR(Architecture Decision Record)** — "왜 이렇게 결정했는가"를 결정·맥락·대안·결과 네 칸으로 짧게 남기는 문서.\
> 예: "저장소를 서비스마다 복제하기로 함 — 독립 배포를 지키려고. 대가: 정의가 어긋날 위험."

### ⑦ 운영 문서 (런북)

- 이 알림이 울리면 무엇을 확인하고 무엇을 하는가.
- 장애 상황별 대응 절차.
- **새벽 3시에 당번이 읽을 수 있는 수준**으로.

## 유지보수성을 깎는 것들

| 항목 | 결과 |
|---|---|
| **부수효과가 흩어져 있음** | 어디서 무엇이 바뀌는지 추적 불가 |
| **암묵적 순서 의존** | 순서를 바꾸면 조용히 깨짐 |
| **거대한 함수/클래스** | 이해 비용, 변경 위험 |
| **죽은 코드 / 안 쓰는 플래그** | 읽는 사람이 살아 있는 코드로 오해 |
| **테스트 없는 핵심 로직** | 리팩터링 불가 → 코드가 굳는다 |
| **깨진 테스트를 방치** | 전체 테스트 신뢰도 붕괴 (하나가 빨간색이면 다 무시하게 됨) |
| **로그가 없거나 비구조적** | 장애 시 추적 불가 |
| **환경별로 다른 동작** | "로컬에서는 되는데요" |
| **정리 계획 없는 피처 플래그** | 코드 경로 폭발 |

## 부채를 다루는 방식

**기술 부채는 없앨 대상이 아니라 관리할 대상이다.**

| 부채 유형 | 대응 |
|---|---|
| **의도적·단기** ("일단 출시하고 정리") | 티켓으로 남기고 기한을 정한다 |
| **의도적·장기** ("이 규모에서는 이게 맞다") | 결정 기록으로 근거를 남긴다. 부채가 아닐 수도 있다 |
| **비의도적** (몰라서 생긴 것) | 발견 시 기록 → 우선순위 판단 |

**갚는 방식**

- **손대는 김에 정리**(보이스카웃 규칙)가 대규모 리팩터링보다 안전하다.
- **테스트를 먼저 붙이고** 리팩터링한다. 테스트 없는 리팩터링은 도박이다.
- **동작 변경과 구조 변경을 같은 커밋에 섞지 않는다** ← 리뷰와 롤백이 불가능해진다.

> **특성화 테스트(characterization test)** — 지금 코드가 실제로 하는 동작을 그대로 고정해 두는 테스트. 옳은지는 안 따지고 "현재 이렇게 동작한다"를 못 박는다.\
> 예: 손댈 수 없던 정산 로직에 "지금 이 입력엔 이 출력"을 먼저 걸어 두면, 리팩터링이 그 동작을 바꾸는 순간 테스트가 빨개진다.

## 체크리스트

- [ ] 핵심 비즈니스 로직에 **빠른** 단위 테스트가 있는가
- [ ] 새 사람이 로컬 환경을 띄우는 데 얼마나 걸리는가
- [ ] 린터·포매터·CI가 컨벤션을 강제하는가
- [ ] 구조화 로그와 상관관계 ID 전파가 있는가
- [ ] 골든 시그널 대시보드가 있는가
- [ ] 왜 이렇게 했는지에 대한 기록(ADR)이 있는가
- [ ] 런북이 있고, 실제로 그걸 보고 대응 가능한가
- [ ] 깨진 테스트를 방치하고 있지 않은가
- [ ] 죽은 코드·오래된 피처 플래그가 쌓여 있지 않은가

## 자기 경험을 말하는 방식

**나쁜 답변**: "클린 코드를 지향합니다."

**좋은 답변의 형태**

> "인수받은 프로젝트에 테스트가 없어서 아무도 손을 못 대는 상태였습니다. 전면 리팩터링 대신, 장애가 자주 나던 정산 로직부터 특성화 테스트(현재 동작을 그대로 고정하는 테스트)를 붙이고 리팩터링했습니다. 그 다음엔 로그에 상관관계 ID를 넣어서 장애 원인 파악 시간이 평균 30분에서 5분으로 줄었습니다."

**포함해야 할 요소**: 무엇이 문제였나 → 어떻게 접근했나(전면이 아니라 국소) → **무엇이 얼마나 개선됐나(숫자)**.

## 핵심 문장

- **유지보수성의 질문은 "깨끗한가"가 아니라 "변경이 안전한가"다.**
- **테스트 용이성은 별개 항목이 아니라 설계 품질(결합도)의 관측 수단이다.**
- **운영 시스템은 못 보면 못 고친다 — 관측 가능성이 유지보수성의 절반이다.**
- **일관되게 평범한 것이 군데군데 뛰어난 것보다 낫다 — 읽는 사람이 예측할 수 있으니까.**
- **기술 부채는 없앨 대상이 아니라 관리할 대상 — 동작 변경과 구조 변경을 한 커밋에 섞지 않는다.**

## 용어 풀이

- **인수인계 가능성(Maintainability)** — 6개월 뒤의 내가 또는 남이 안전하게 고칠 수 있는 성질.
- **결합도(Coupling)** — A를 바꿀 때 B도 바꿔야 하는 정도. 낮을수록 좋다.
- **응집도(Cohesion)** — 한 덩어리 안 요소들이 한 목적으로 뭉친 정도. 높을수록 좋다.
- **테스트 용이성(Testability)** — 테스트를 짤 수 있는 구조인지. 설계 품질의 지표.
- **관측 가능성(Observability)** — 밖에 남은 신호(로그·메트릭·트레이스)로 안을 알아내는 성질.
- **상관관계 ID(Correlation / Trace ID)** — 한 요청이 지나는 전 구간에 붙여 로그를 이어 붙이는 식별자.
- **골든 시그널(Golden Signals)** — 지연·트래픽·에러·포화도, 가장 먼저 볼 네 메트릭.
- **ADR(Architecture Decision Record)** — 결정·맥락·대안·결과를 짧게 남기는 문서.
- **런북(Runbook)** — 알림별·장애별 대응 절차서. 새벽 3시에 읽을 수 있어야 한다.
- **특성화 테스트(Characterization Test)** — 현재 동작을 그대로 고정하는 테스트. 리팩터링의 안전망.
- **기술 부채(Technical Debt)** — 지금의 편의를 위해 미룬 정리. 없앨 대상이 아니라 관리할 대상.
- **보이스카웃 규칙(Boy Scout Rule)** — "왔을 때보다 깨끗하게" — 손대는 김에 조금씩 정리하는 것.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문과 섞어 인출하지 않는다.

- **골든 시그널(Google SRE).** §2 ③의 "메트릭 = 골든 시그널"이 가리키는 것. 지연(latency)·트래픽(traffic)·에러(errors)·포화도(saturation) 네 가지를, 그것도 "성공과 실패를 나눠" 보는 것이 출발점이다. → [`./performance.md`](./performance.md)의 "성공/실패 분리 측정"과 같은 렌즈.
- **왜 테스트 용이성이 곧 결합도인가.** 테스트가 안 짜진다는 건 "그 코드를 나머지에서 떼어낼 수 없다"는 뜻이고, 떼어낼 수 없다는 게 바로 높은 결합도다. 그래서 원고가 "별개 항목이 아니라 결합도의 관측 수단"이라고 못 박는다. 의존성 주입(DI)이 이 떼어내기를 돕는 대표 기법이다.
- **동작 변경 ≠ 구조 변경(두 모자 원칙).** 리팩터링(겉보기 동작을 유지한 채 구조만 개선)과 기능 변경을 한 커밋에 섞으면, 테스트가 빨개졌을 때 "구조 때문인지 기능 때문인지"를 못 가른다. 그래서 "한 번에 한 모자만 쓴다"가 롤백·리뷰를 가능하게 하는 규칙이 된다.
