# System Design (시스템 설계)

> 이 컬렉션의 인덱스는 [README.md](./README.md)에서 시작한다.\
> 출처: `jun-bank/docs/study/notes/axes/system-design.md` (본체) + `08-engineering-axes-deep.md` §6 · 이관일 2026-09-16.\
> 본문 표·절은 **원고**를 고쳐 쓴 것이다. 「한눈에」의 비유·그림과 맨 끝 `[Claude 추가]`는 **Claude 보강**이다.

**지키는 것: 변경 비용.** 한 줄 정의는 **어떻게 쪼개고, 경계를 어디에 긋는가.**

---

## 한눈에 — 쉽게 말하면

집을 지을 때 벽지 색은 나중에 언제든 바꾸지만, 내력벽(건물을 떠받치는 벽)의 위치는 한 번 정하면 바꾸는 데 공사판을 다시 벌여야 한다. *(Claude 보강 — 원고에 없는 비유)*

```text
바꾸기 쉬운 것            바꾸기 어려운 것
+----------------+       +--------------------+
| 벽지 색         |       | 내력벽 위치         |
| 가구 배치       |       | 배관 경로          |
| = 라이브러리    |       | = 서비스 경계·샤드키 |
+----------------+       +--------------------+
  빨리 정한다              오래 고민한다
```

**설계도 똑같은 구조다.** 코드는 리팩터링하면 되지만, 잘못 그은 서비스 경계나 샤드 키는 되돌리는 데 몇 달이 걸린다.\
그래서 설계 논의의 핵심 질문은 하나다 — **"이 결정은 되돌릴 수 있는가?"**

---

## 왜 가장 중요한 축인가

**되돌리는 비용이 가장 크기 때문이다.**

> 되돌리기 쉬운 결정은 빨리 정하고, 어려운 결정은 오래 고민한다.

| 되돌리기 쉬움 (빨리 정한다) | 되돌리기 어려움 (오래 고민한다) |
|---|---|
| 라이브러리 선택 | **데이터 모델** |
| 내부 클래스 구조 | **서비스 경계** |
| 캐시 도입 | **샤드 키** |
| 배포 방식 | **공개 API 계약** |
| 로깅 포맷 | 동기 → 비동기 전환 |
| | 저장소 종류 (데이터가 쌓인 뒤) |

## 경계를 긋는 기준

> 출처: 원고 §2

### 원칙: 함께 변하는 것끼리 묶는다

경계 기준은 **기술 계층**(API / 로직 / DB 서비스)이 아니라 **비즈니스 능력**(주문 / 결제 / 재고)이다.

### 판별법

> **"이 기능을 바꾸려면 몇 개를 동시에 배포해야 하나?"**\
> 2개 이상이면 경계가 틀렸다. 그게 **분산 모놀리스**다.

### 모놀리스가 기본값이다

- 경계가 확실해지기 전에 쪼개면 **틀린 경계가 코드에 굳는다.**
- 분산의 비용(네트워크, 관측, 배포, 정합성)은 즉시 발생하고, 이점(독립 배포)은 경계가 맞아야만 생긴다.
- **잘 모듈화된 모놀리스 → 경계가 명확해지면 그때 분리**가 안전한 경로다.
- 여러 서비스로 나누는 것은 **조직 확장**을 위한 것이지 성능 확장을 위한 게 아니다. → [`./scalability.md`](./scalability.md)

> **분산 모놀리스(distributed monolith)** — 물리적으로는 서비스가 나뉘었지만 서로 얽혀 있어, 하나를 바꾸려면 여러 개를 같이 배포해야 하는 상태. 분산의 비용은 다 내고 이점은 없다.\
> 예: 주문·결제·재고를 서비스 셋으로 나눴는데 "할인 정책"을 바꿀 때마다 셋을 동시에 배포해야 한다면, 경계가 잘못 그어진 것이다.

## 백엔드 설계의 결정 지점

> 출처: 원고 §3 + `08-engineering-axes-deep.md` §6

### ① 동기 vs 비동기

| | 동기 (HTTP) | 비동기 (메시지) |
|---|---|---|
| 언제 | 즉시 응답 필요, 결과로 분기 | 결과 대기 불필요, 부하 평탄화 |
| 결합 | 강함 (상대가 죽으면 나도 영향) | 약함 |
| **가용성** | **곱셈으로 떨어짐** | 독립적 |
| 비용 | 단순 | 순서·중복·지연·관측 복잡도 |

> **동기 호출 체인은 가용성을 곱셈으로 깎는다.** 5홉이면 99.9%⁵ ≈ 99.5%. → [`./availability.md`](./availability.md)

### ② 저장소 선택

| 성격 | 선택 |
|---|---|
| 트랜잭션·정합성 | RDBMS |
| 대량 집계·분석 | 컬럼 지향 저장소 |
| 전문 검색 | 검색 엔진 |
| 저지연·휘발성 | 인메모리 저장소 |
| 이벤트 스트림 | 로그 기반 메시지 브로커 |

> **저장소를 하나 늘릴 때마다 "맞추는 일"이 하나 늘어난다.**\
> RDBMS 하나로 될 일을 셋으로 나누면, 그 셋의 정합성이 새로운 업무가 된다.

### ③ 데이터 소유권

- **한 데이터의 쓰기 주체는 하나여야 한다.**
- 공유 DB는 결합도를 그대로 두면서 분산 비용만 추가한다.
- 다른 서비스는 API나 이벤트로만 접근한다.

### ④ API 계약

- 버저닝, 하위 호환, 에러 형식 통일, 페이지네이션 방식.
- **소비자가 생기면 사실상 되돌릴 수 없다.**
- 신·구 버전 공존을 전제로 설계한다 (배포 중에는 항상 둘 다 돈다).

### ⑤ 정합성 수준을 화면 단위로 정한다

"전부 강한 정합성"은 확장을 막고, "전부 최종적 일관성"은 사용자를 혼란스럽게 한다.

> **어떤 화면이 얼마만큼의 지연을 허용하는지**를 먼저 정한다.

## 프론트 설계의 결정 지점

### ① 서버 상태 vs 클라이언트 상태 분리 — 가장 중요

| | 서버 상태 | 클라이언트 상태 |
|---|---|---|
| 예 | API로 받은 목록, 상세 | 모달 열림, 폼 입력, 필터 |
| 성질 | **내가 소유하지 않음, 언제든 낡음** | 내가 소유함 |
| 도구 | 데이터 페칭 라이브러리 (캐시·재검증·무효화) | 로컬 state |

> **서버 데이터를 전역 상태에 통째로 넣는 것이 가장 흔한 프론트 설계 실수다.**\
> 캐싱·무효화·로딩·에러·재시도를 전부 직접 만들게 된다.

> **서버 상태(server state)** — 원본이 서버에 있어 내가 소유하지 않고 언제든 낡을 수 있는 데이터. 캐시·재검증·무효화가 필요하다.\
> 예: 상품 목록은 서버 상태(내가 안 바꿔도 서버에서 바뀜), 필터 선택은 클라이언트 상태(내가 소유).

### ② 상태의 위치

필요한 가장 가까운 곳에 둔다. **전역은 최후의 수단.**

### ③ 컴포넌트 경계

재사용 단위(버튼, 모달)와 도메인 단위(주문 카드)를 섞지 않는다.

### ④ 라우팅 / 코드 스플리팅 경계

라우트 경계가 자연스러운 스플리팅 지점이다.

## 설계 트레이드오프 카드

| 선택 | 얻는 것 | 내주는 것 |
|---|---|---|
| 서비스 분리 | 독립 배포, 팀 자율성 | 네트워크 지연, 정합성, 관측 복잡도 |
| 비동기 전환 | 결합도↓, 부하 평탄화 | 순서·중복·지연·디버깅 난이도 |
| 캐시 | 성능, DB 부하↓ | 정합성, 무효화 복잡도 |
| 비정규화 | 조회 성능 | 쓰기 복잡도, 중복 데이터 정합성 |
| 샤딩 | 쓰기·용량 확장 | 조인·트랜잭션 불가, 되돌리기 어려움 |
| 읽기 모델 분리 | 조회 최적화 | 최종적 일관성 |
| 강한 정합성 | 단순한 사고 모델 | 확장성, 가용성 |

## 흔한 실수

| 실수 | 결과 |
|---|---|
| **기술 계층으로 서비스 분리** | 분산 모놀리스 |
| **조기 마이크로서비스** | 틀린 경계가 굳음 |
| **공유 DB** | 결합도 그대로 + 분산 비용 |
| **동기 호출 체인** | 가용성 곱셈 하락, 지연 누적 |
| **저장소 남발** | 정합성 문제 N개 |
| **모든 것에 강한 정합성** | 확장 불가 |
| **프론트 전역 상태에 서버 데이터** | 캐시·무효화를 직접 구현하게 됨 |
| **미래를 위한 과잉 추상화** | 쓰지 않을 유연성에 복잡도 지불 |

## 설계 리뷰 질문지

**경계**
- [ ] 기능 하나를 바꾸려면 몇 개를 배포해야 하는가
- [ ] 각 데이터의 쓰기 주체가 하나인가

**결합**
- [ ] 이 의존성이 죽으면 어떻게 되는가
- [ ] 요청 하나가 몇 홉을 거치는가

**정합성**
- [ ] 어디까지 강한 정합성이 필요한가 (화면 단위로)
- [ ] 최종적 일관성인 곳의 지연 허용치가 정의되어 있는가

**되돌리기**
- [ ] 이 결정 중 되돌리기 어려운 게 무엇인가
- [ ] 그 결정에 충분한 근거가 있는가

**단순함**
- [ ] 이것보다 단순한 방법으로 안 되는 이유가 무엇인가
- [ ] 지금 필요 없는 유연성에 비용을 내고 있지 않은가

## 자기 경험을 말하는 방식

**나쁜 답변**: "마이크로서비스로 설계했습니다."

**좋은 답변의 형태**

> "처음에는 모놀리스로 시작했습니다. 트래픽이 아니라 **배포 경합**이 문제가 돼서, 변경 빈도가 확연히 다른 정산 모듈만 먼저 분리했습니다. 주문과 재고는 트랜잭션 경계가 겹쳐서 함께 뒀고요. 분리한 뒤에는 동기 호출 대신 이벤트로 연결해서 정산이 죽어도 주문은 받도록 했습니다."

**포함해야 할 요소**: 왜 쪼갰나(기술이 아니라 문제) → 무엇을 안 쪼갰나와 그 이유 → 어떻게 연결했나 → 그 대가.

## 핵심 문장

- **시스템 설계가 가장 중요한 축인 이유는 되돌리는 비용이 가장 크기 때문이다.**
- **설계의 핵심 질문은 "이 결정은 되돌릴 수 있는가?" — 쉬운 건 빨리, 어려운 건 오래.**
- **경계는 기술 계층이 아니라 함께 변하는 비즈니스 능력으로 긋는다. 모놀리스가 기본값이다.**
- **동기 호출 체인은 가용성을 곱셈으로 깎는다. 저장소를 늘릴 때마다 정합성 업무가 하나 는다.**
- **프론트의 가장 흔한 실수는 서버 상태를 전역 상태에 통째로 넣는 것이다.**

## 용어 풀이

- **변경 비용(Changeability)** — 기능을 바꾸거나 추가할 때 드는 비용. 설계가 지키는 것.
- **되돌릴 수 있는 결정 / 없는 결정** — 라이브러리처럼 쉽게 무르는 것 vs 서비스 경계·샤드 키처럼 못 무르는 것.
- **비즈니스 능력(Business Capability)** — 주문·결제·재고처럼 함께 변하는 업무 단위. 경계의 기준.
- **분산 모놀리스(Distributed Monolith)** — 나눴지만 얽혀서 같이 배포해야 하는 상태. 분산의 비용만 낸다.
- **동기 / 비동기** — 즉시 응답을 기다림(결합 강함) vs 메시지로 넘기고 안 기다림(결합 약함).
- **데이터 소유권** — 한 데이터의 쓰기 주체는 하나여야 한다는 원칙.
- **API 계약** — 소비자와의 약속(형식·버전·에러). 소비자가 생기면 되돌리기 어렵다.
- **최종적 일관성(Eventual Consistency)** — 지금은 달라도 시간이 지나면 같아지는 정합성.
- **서버 상태 / 클라이언트 상태** — 내가 소유하지 않는 원격 데이터 vs 내가 소유하는 로컬 상태.
- **비정규화(Denormalization)** — 조회를 빠르게 하려 데이터를 중복 저장하는 것. 쓰기 정합성을 대가로.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문과 섞어 인출하지 않는다.

- **콘웨이의 법칙(Conway's Law).** "시스템 구조는 그걸 만든 조직의 소통 구조를 닮는다." 원고가 "마이크로서비스는 조직 확장을 위한 것"이라고 못 박는 이유의 배경 — 서비스 경계는 사실상 팀 경계와 맞물린다.
- **되돌리기 어려움 = one-way door.** "한번 지나면 못 되돌아오는 문(one-way door)"과 "언제든 되돌아올 수 있는 문(two-way door)"으로 결정을 나누는 널리 쓰는 표현. 원고의 "되돌릴 수 있는가?"와 같은 렌즈다. two-way door는 빨리, one-way door는 신중히.
- **Expand-Contract(확장-수축) 마이그레이션.** "되돌리기 어려운" 데이터 모델·API 변경을 안전하게 하는 표준 절차. ①새 형태를 추가하되 옛 형태를 남기고(expand) ②양쪽을 함께 쓰다가 ③옛 형태를 제거(contract)한다. 배포 중 신·구가 공존한다는 §3 ④의 실행판이다. → [`./maintainability.md`](./maintainability.md)
