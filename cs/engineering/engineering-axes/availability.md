# High Availability (고가용성)

> 이 컬렉션의 인덱스는 [README.md](./README.md)에서 시작한다.\
> 출처: `jun-bank/docs/study/notes/axes/availability.md` (본체) + `08-engineering-axes-deep.md` §3 · 이관일 2026-09-16.\
> 본문 표·절은 **원고**를 고쳐 쓴 것이다. 「한눈에」의 비유·그림과 맨 끝 `[Claude 추가]`는 **Claude 보강**이다.

**지키는 것: 연속성.** "죽지 않게 만드는 것"이 아니라 **"죽는 걸 전제하고, 죽어도 서비스가 계속되게 만드는 것"**이다.

---

## 한눈에 — 쉽게 말하면

엘리베이터가 두 대인 건물을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
엘리베이터 1대 건물          엘리베이터 2대 건물
+------------------+         +------------------+
| 한 대가 고장나면   |         | 한 대 고장나도    |
| 아무도 못 올라감   |         | 나머지로 오르내림  |
+------------------+         +------------------+
  → 고장 = 전면 중단           → 고장 = 조금 느려질 뿐

단, 두 대를 각각 정원 70%로 굴리면?
  → 한 대 죽으면 남은 하나에 140% 몰려 → 같이 멈춘다
```

**시스템도 똑같은 구조다.** 이중화만으로 끝이 아니다 — 한쪽이 죽었을 때 남은 쪽이 감당할 여유(용량 계획)까지 있어야 진짜 가용성이다.\
그리고 "죽으면 어떻게 되나"를 실제로 눌러 본 적 없는 이중화는, 없는 것과 같다.

---

## 이분법이 아니라 비율이다

가용성은 "죽었냐/살았냐"가 아니라 **비율**이다.

| 가용성 | 연간 다운타임 | 월 다운타임 |
|---|---|---|
| 99% | 3.65일 | 7.3시간 |
| 99.9% | 8.8시간 | 43분 |
| 99.99% | 53분 | 4.3분 |
| 99.999% | 5.3분 | 26초 |

**9가 하나 늘 때마다 비용은 대략 한 자릿수씩 는다.**\
→ 그래서 **"몇 9가 필요한가"를 먼저 정하고** 거기에 맞는 투자를 한다. 무조건 높이는 게 정답이 아니다.

### 가용성 합성 — 의존성이 많으면 곱셈으로 떨어진다

```text
직렬 (둘 다 필요):  99.9% × 99.9% = 99.8%     ← 떨어진다
병렬 (하나만 살면): 1 − 0.001² = 99.9999%     ← 올라간다
```

요청 하나가 5개 서비스를 거치면, 각각 99.9%여도 전체는 **약 99.5%**가 된다.

> **그래서 여러 서비스로 나눈 구조에서는 격리(벌크헤드·서킷 브레이커)가 선택이 아니라 필수다.** → [`./system-design.md`](./system-design.md)

### RTO / RPO

| | 의미 | 결정하는 것 |
|---|---|---|
| **RTO** | 얼마나 빨리 복구해야 하나 | failover 자동화 수준 |
| **RPO** | 얼마만큼의 유실을 허용하나 | 복제 방식(동기/비동기), 백업 주기 |

**RPO=0을 원하면 동기 복제가 필요하고, 그러면 쓰기 지연과 가용성을 내준다.** (CAP의 실제 모습)

> **RTO / RPO** — RTO(Recovery Time Objective)는 "얼마나 빨리 되살릴까"의 목표 시간, RPO(Recovery Point Objective)는 "얼마만큼의 최근 데이터는 잃어도 되나"의 목표.\
> 예: RTO 5분·RPO 0이면 "5분 안에 복구하되 데이터는 한 건도 잃지 않는다" — 그만큼 비싼 동기 복제가 필요하다.

## 4단계로 나눠 보기

### ① 예방 — SPOF 제거

**방법**: 구성 요소를 하나씩 짚으며 **"이게 죽으면?"**을 물어본다.

- 단일 인스턴스, 단일 AZ, 단일 리더, 단일 커넥션, 단일 배포 파이프라인.

**함정**: 이중화하고 **용량 계획을 안 하는 것.**

```text
2대를 각각 70%로 운영
        ↓
한 대 죽음
        ↓
남은 하나에 140% 몰림
        ↓
남은 하나도 죽음 (연쇄 붕괴)

규칙: N대면 각 노드는 (N−1)/N 이하로 운영한다
```

> **SPOF(Single Point Of Failure)** — 그것 하나가 죽으면 전체가 멈추는 지점.\
> 예: 앞단에 로드밸런서가 한 대뿐이면, 서버를 아무리 이중화해도 그 로드밸런서가 곧 SPOF다.

### ② 격리 — 전파 차단 (실제 장애의 대부분)

| 도구 | 막는 것 |
|---|---|
| **타임아웃** | 무한 대기 → 스레드 고갈 → **전체 마비** |
| **서킷 브레이커** | 죽은 의존성 반복 호출 (자원 낭비 + 상대 복구 방해) |
| **벌크헤드** | 부가 기능이 핵심 기능의 자원을 뺏는 것 |
| **레이트 리밋 / 로드 셰딩** | 과부하로 전부 같이 죽는 것 |

> **타임아웃이 없으면 나머지가 전부 무의미하다.** 실패를 감지할 방법이 없기 때문이다.\
> 그리고 외부 의존성은 **죽지 않고 느려지기만 해도** 전체를 죽일 수 있다.

```text
        CLOSED ──(실패율 임계 초과)──> OPEN
          ^                            │
          │                    (대기 시간 경과)
          │                            v
          └──(시험 호출 성공)──── HALF_OPEN
```

> **서킷 브레이커(circuit breaker)** — 의존성이 계속 실패하면 아예 호출을 잠깐 끊어(OPEN) 자원 낭비와 상대 방해를 막고, 일정 시간 뒤 시험 호출(HALF_OPEN)로 회복을 확인하는 장치.\
> 예: 결제사 API가 먹통일 때, 매 요청을 5초씩 기다리다 스레드가 고갈되느니 즉시 "일시 불가"로 응답하고 30초 뒤 한 건만 찔러 본다.

### ③ 복구 — Failover

- 헬스체크(liveness / readiness 구분), 자동 승격, 리더 선출.
- **Split-brain 방어**: 쿼럼(홀수 노드), 펜싱, 임대.
- **재시도는 양날의 검**: 백오프 + **지터** 없으면 복구 중인 시스템을 다시 죽인다.

> **지터(jitter)** — 재시도 간격에 일부러 섞는 무작위 흔들림. 모두가 정확히 같은 간격으로 재시도하면 복구 중인 시스템을 동시에 다시 때린다.\
> 예: "1초 뒤 재시도" 대신 "1초 ± 무작위 0~0.5초 뒤"로 흩뿌려 재시도 파도(retry storm)를 막는다.

### ④ 완화 — Graceful Degradation

**기능 등급을 미리 나눠 둔다.** 장애 시점에 나누면 늦다.

| 등급 | 예 | 장애 시 |
|---|---|---|
| 핵심 | 로그인, 결제, 주문 | 반드시 살린다 |
| 주요 | 상품 조회, 검색 | 캐시 / 축소 응답 |
| 부가 | 추천, 리뷰 요약 | **꺼도 된다** |

## 가용성을 가장 많이 깎는 것은 변경이다

**하드웨어는 잘 안 고장 난다. 장애의 대부분은 배포·설정 변경 직후에 발생한다.**\
→ 그래서 **배포 전략 자체가 가용성 설계**다.

| 수단 | 복구 시간 |
|---|---|
| 피처 플래그 off | 초 |
| Blue-Green 전환 | 초~분 |
| 이전 이미지 재배포 | 분 |
| 핫픽스 개발 후 배포 | 수십 분~시간 |
| DB 복원 | 시간 |

> **MTTR을 줄이는 가장 강력한 수단은 빠른 롤백이다.**\
> 그래서 "롤백 가능성"이 가용성의 핵심 지표가 된다. 롤백 불가능한 DB 마이그레이션은 가용성 사고의 대표 원인이다.

## 흔한 착각

| 착각 | 실제 |
|---|---|
| "이중화했으니 됐다" | **failover를 실행해본 적 없으면 없는 것과 같다** |
| "복제본이 있으니 백업은 불필요" | 복제는 백업이 아니다. **실수로 지운 데이터는 그대로 복제된다** |
| "백업이 있으니 안전" | **복원해본 적 없는 백업은 백업이 아니다** |
| "헬스체크가 꼼꼼할수록 좋다" | 깊은 헬스체크는 **부분 장애를 전체 장애로 만든다** |
| "재시도하면 가용성이 올라간다" | 잘못하면 **재시도가 장애를 증폭**시킨다 |
| "가용성은 인프라 문제" | 대부분은 애플리케이션의 타임아웃·폴백 부재 |

### 깊은 헬스체크 문제 (중요)

```text
헬스체크가 DB까지 확인
        ↓
DB가 잠깐 느려짐
        ↓
전 인스턴스가 동시에 unhealthy
        ↓
로드밸런서가 보낼 곳이 없음
        ↓
멀쩡한 앱까지 전체 다운
```

> **Liveness는 절대 의존성을 확인하지 않는다.** 의존성 상태는 서킷 브레이커가 다룬다.

## 측정 — SLO와 에러 버짓

| 개념 | 의미 |
|---|---|
| **SLI** | 측정 지표 (성공률, p99) |
| **SLO** | 목표 (99.9%) |
| **에러 버짓** | 허용된 실패량 (1 − SLO) |

**에러 버짓의 쓸모**: 안정성과 개발 속도의 갈등을 숫자로 중재한다.

```text
버짓 남음 → 배포·실험 공격적으로
버짓 소진 → 신규 기능 중단, 안정화 집중
```

> **SLO는 100%가 아니어야 한다.** 100%를 목표로 하면 어떤 변경도 못 한다.

> **에러 버짓(error budget)** — SLO가 허용하는 실패의 총량(1 − SLO). 남아 있으면 공격적으로 배포하고, 다 쓰면 안정화에 집중한다.\
> 예: SLO 99.9%면 한 달에 약 43분의 다운타임 예산이 있다 — 이걸 실험에 쓸지 아낄지를 팀이 숫자로 정한다.

## 체크리스트

- [ ] 가용성 목표(몇 9)가 정해져 있는가
- [ ] 모든 계층에 SPOF가 없는가 (하나씩 짚어봤는가)
- [ ] 이중화 노드가 (N−1)/N 이하 부하인가
- [ ] **모든 외부 호출에 타임아웃이 있는가**
- [ ] 의존성이 죽었을 때의 동작(폴백)이 정의되어 있는가
- [ ] 헬스체크가 연쇄 실패를 유발하지 않는가
- [ ] **failover를 실제로 실행해본 적이 있는가**
- [ ] **백업 복원을 테스트해봤는가**
- [ ] 배포 없이 기능을 끌 수 있는가 (킬 스위치)
- [ ] 롤백 절차가 검증되었는가

## 자기 경험을 말하는 방식

**나쁜 답변**: "이중화해서 고가용성을 확보했습니다."

**좋은 답변의 형태**

> "SLO를 99.9%로 잡았습니다. 다중 AZ로 인프라 장애는 커버되지만, 실제 다운타임의 대부분은 배포와 외부 의존성 장애에서 왔습니다. 그래서 외부 호출 전부에 타임아웃과 서킷 브레이커를 걸고, 추천 같은 부가 기능은 실패 시 숨기도록 폴백을 뒀습니다. 그리고 분기마다 failover 훈련을 했습니다. 다중 리전은 비용 대비 필요성이 없다고 판단해서 안 했습니다."

**포함해야 할 요소**: 목표 수치 → 실제 장애 원인 분석 → 대응 → **테스트했다는 사실** → 안 한 것과 그 이유.

## 핵심 문장

- **가용성은 이분법이 아니라 비율이다 — "몇 9가 필요한가"를 먼저 정하고 거기 맞춰 투자한다.**
- **직렬 의존은 가용성을 곱셈으로 깎는다 — 그래서 격리(타임아웃·서킷 브레이커·벌크헤드)가 필수다.**
- **타임아웃이 없으면 나머지 방어가 전부 무의미하다.**
- **장애의 대부분은 하드웨어가 아니라 변경(배포·설정)에서 온다 — 빠른 롤백이 최고의 방어다.**
- **실행해본 적 없는 failover와 복원해본 적 없는 백업은 없는 것과 같다.**

## 용어 풀이

- **연속성(Availability)** — 일부가 죽어도 서비스 전체는 계속되는 성질. 비율(몇 9)로 말한다.
- **SPOF(Single Point of Failure)** — 그것 하나가 죽으면 전체가 멈추는 지점.
- **가용성 합성** — 직렬 의존은 가용성을 곱해 낮추고, 병렬 이중화는 높인다.
- **RTO / RPO** — 복구 목표 시간 / 허용 유실량. 백업·복제 방식을 결정한다.
- **타임아웃(Timeout)** — 응답이 안 오는 걸 감지해 무한 대기·스레드 고갈을 막는 상한. 가장 자주 빠뜨린다.
- **서킷 브레이커(Circuit Breaker)** — 실패가 잦으면 호출을 끊었다가 시험 호출로 회복을 확인하는 장치.
- **벌크헤드(Bulkhead)** — 자원 풀을 기능별로 나눠 한 기능의 장애가 다른 기능을 못 먹게 격리.
- **로드 셰딩(Load Shedding)** — 과부하 시 일부 요청을 일부러 버려 나머지를 살리는 것.
- **Failover** — 죽은 구성 요소를 살아 있는 것으로 자동 대체하는 복구.
- **Split-brain** — 리더가 둘로 갈려 각자 자기가 리더라 믿는 상태. 쿼럼·펜싱으로 막는다.
- **지터(Jitter)** — 재시도 간격에 섞는 무작위 흔들림. 동시 재시도 파도를 막는다.
- **Graceful Degradation** — 장애 시 부가 기능을 끄고 핵심만 살리는 우아한 성능 저하.
- **MTTR** — 평균 복구 시간. 빠른 롤백으로 줄인다.
- **SLI / SLO / 에러 버짓** — 측정 지표 / 목표 / 허용 실패량. 안정성과 속도를 숫자로 중재한다.
- **Liveness / Readiness** — "프로세스가 살아 있나" / "트래픽 받을 준비가 됐나". Liveness는 의존성을 확인하지 않는다.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문과 섞어 인출하지 않는다.

- **CAP 정리.** RPO=0 동기 복제가 왜 가용성을 깎는지의 이론 배경. 네트워크가 갈라졌을 때(Partition) 정합성(C)과 가용성(A)을 동시에 다 지킬 수는 없다 — 정합성을 지키려면 요청을 거절해야 하고(가용성 손해), 가용성을 지키려면 갈라진 양쪽이 어긋난 값을 받는다(정합성 손해). 원고의 "RPO=0을 원하면 가용성을 내준다"가 이 정리의 실무판이다.
- **왜 "느려지는 장애"가 "죽는 장애"보다 위험한가.** 완전히 죽으면 헬스체크가 바로 빼내지만, 느려지기만 하면 헬스체크는 통과하면서 앞단 스레드를 하나씩 붙잡아 고갈시킨다. 그래서 타임아웃이 "죽음 감지"가 아니라 "느림 감지" 장치라는 점이 중요하다.
- **Thundering herd / retry storm.** 지터 없는 재시도가 위험한 이유. 장애가 잠깐 풀린 순간 밀려 있던 모든 클라이언트가 **동시에** 재시도해 복구 중인 시스템을 다시 넘어뜨리는 현상이다. 백오프는 간격을 벌리고, 지터는 그 간격을 흩뿌린다.
