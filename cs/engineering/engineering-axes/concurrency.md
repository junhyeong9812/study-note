# Concurrency (동시성)

> 이 컬렉션의 인덱스는 [README.md](./README.md)에서 시작한다. 먼저 [혼동 3가지]와 [축 사이 트레이드오프]를 보고 여기로 오면 방향이 잡힌다.\
> 출처: `jun-bank/docs/study/notes/axes/concurrency.md` (본체) + `08-engineering-axes-deep.md` §1 (「사고의 순서」 흡수) · 이관일 2026-09-16.\
> 본문 표·절은 **원고**를 고쳐 쓴 것이다(문체·순서 유지, 프로젝트 고유 상황을 일반 상황으로). 「한눈에」의 비유·그림과 맨 끝 `[Claude 추가]`는 **Claude가 원고 이해를 돕기 위해 보탠 것**이다.

**지키는 것: 정확성.** "빠른가"가 아니라 **"틀리지 않는가"**의 축이다.

---

## 한눈에 — 쉽게 말하면

현금인출기 두 대에 통장 하나를 물려 놓고, 두 사람이 **같은 순간**에 6천 원씩 뽑는 장면을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
잔액 10,000원짜리 통장 하나, 인출기 두 대

인출기 A                 인출기 B
잔액 읽음 = 10,000       잔액 읽음 = 10,000     ← 둘 다 "돈 있네"
6,000 빼서 4,000 씀      6,000 빼서 4,000 씀
        \                   /
         \                 /
          최종 잔액 = 4,000        ← 12,000을 뽑았는데 6,000만 빠졌다
```

**코드도 똑같은 구조다.** 두 실행 흐름이 같은 자원(통장 한 줄)을 각자 읽고, 각자 계산하고, 각자 덮어쓰면 한쪽 결과가 조용히 사라진다.\
동시성은 이 "조용히 사라짐"을 막는 활동이다 — 화면에 에러가 뜨는 게 아니라, 며칠 뒤 정산이 안 맞아서 발견된다.

---

## 이 축이 답하려는 질문

여러 실행 흐름이 **같은 자원을 동시에** 건드릴 때, 결과가 틀리지 않게 지킬 수 있는가.

동시성은 성능과 자주 혼동되지만 방향이 반대다.

- **락을 걸면 느려진다.** 성능을 위해 락을 푸는 게 아니라, **정확성을 위해 성능을 내주는** 것이다.\
  그래서 동시성 설계는 "정확성을 위해 성능을 얼마나 내줄 것인가"의 문제다.

### 왜 어려운가

| 성질 | 결과 |
|---|---|
| **실패가 조용하다** | 예외도 로그도 없다. 며칠 뒤 정산이 안 맞아서 발견한다 |
| **재현이 안 된다** | 단일 스레드 테스트는 항상 통과한다 |
| **부하가 올라야 나타난다** | 개발·스테이징에서는 안 보인다 |
| **규모가 커지면 방어가 무효화된다** | 한 프로세스 안에서만 걸리는 락은 인스턴스가 늘면 무효 |

## 실패 유형 카탈로그

> 출처: 원고 §2 (「실패 유형」)

| 유형 | 시나리오 | 결과 |
|---|---|---|
| **Lost Update** | 둘이 같은 행을 읽고 각자 계산해서 씀 | 나중 쓰기가 앞 쓰기를 덮어씀 (재고·잔액·카운터) |
| **Write Skew** | 각자 조건을 확인하고 각자 통과 | 둘 다 통과하면 안 되는데 통과 (당직 최소 1명인데 둘 다 퇴근) |
| **Phantom Read** | 범위 검사 중 새 행이 끼어듦 | "중복 없음" 확인 후 중복 삽입 |
| **Read Skew** | 여러 행을 읽는 중에 데이터가 바뀜 | 계좌 A는 이체 전, B는 이체 후 값을 읽음 |
| **중복 실행** | 클라이언트 재시도, 더블 클릭 | 결제 2회 |
| **데드락** | 서로의 락을 기다림 | 둘 다 멈춤 (DB가 하나를 죽여줘서 그나마 다행) |
| **분산 중복** | 인스턴스 N대에서 스케줄러가 N번 실행 | 정산 N배 |

> **Lost update(갱신 유실)** — 두 흐름이 같은 값을 읽고 각자 고쳐 쓸 때, 나중 쓰기가 앞 쓰기를 덮어 앞의 변경이 사라지는 것.\
> 예: 위 「한눈에」의 통장 — 6천 원 인출 둘이 겹쳐서 하나만 반영된다.

> **Write skew(쓰기 왜곡)** — 각자 "지금 조건이 괜찮다"를 확인하고 각자 통과했는데, 둘의 변경이 합쳐지면 규칙이 깨지는 것.\
> 예: "당직 최소 1명" 규칙에서 두 당직자가 동시에 "나 말고 한 명 더 있네" 확인하고 둘 다 퇴근한다.

## 도구와 선택 기준

> 출처: 원고 §3

| 도구 | 쓰는 자리 | 대가 |
|---|---|---|
| **조건부 업데이트** | `UPDATE ... WHERE qty >= 1` → 영향 행 0이면 실패 | **가장 저렴하고 강력.** 먼저 검토할 것 |
| **낙관적 락** (version 컬럼) | 충돌이 드물고 재시도 가능 | 충돌 잦으면 재시도 폭증 |
| **비관적 락** (`SELECT ... FOR UPDATE`) | 충돌 잦고 재시도 비용 큼 | 처리량 저하, 데드락 |
| **DB 유니크 제약** | 중복 삽입 방지 | **최후의 방어선.** 앱 로직보다 강함 |
| **CHECK 제약** | `qty >= 0` 같은 불변식 | 마지막 안전망 |
| **트랜잭션 격리 수준** | phantom / read skew 방어 | 높일수록 느려짐. **격리 수준만으로 lost update는 안 막힌다** |
| **멱등성 키** | 클라이언트 재시도 흡수 | 키 저장소 필요 |
| **인박스 테이블** | 메시지 중복 소비 흡수 | 테이블·정리 필요 |
| **파티션 직렬화** | 키로 자원을 나눔 (메시지 키, actor 모델) | 애초에 동시 접근을 없앰. **확장성과 상성 좋음** |
| **분산 락** (Redis 등) | 여러 인스턴스 조율 | ⚠️ **정확성 보장이 아니다** (아래 참고) |

> **낙관적 락 / 비관적 락** — 낙관적 락은 "충돌은 드물 것"이라 보고 일단 진행한 뒤 저장 직전 version이 그대로인지 확인해 어긋나면 재시도한다. 비관적 락은 "충돌이 잦을 것"이라 보고 아예 읽는 순간부터 행을 잠근다.\
> 예: 재고 넉넉한 평범한 상품은 낙관적 락으로 충분하고, 티켓팅처럼 한 행에 수천이 몰리면 비관적 락이나 조건부 업데이트가 낫다.

### 선택 순서 (실무에서 실제로 밟는 절차)

```text
1. 애초에 경합을 없앨 수 있나?     → 파티셔닝, 키 분산
        ↓ (못 없애면)
2. 조건부 업데이트로 되나?         → 한 쿼리로 확인+변경, 가장 저렴
        ↓ (안 되면)
3. 낙관적 락으로 되나?             → 충돌 빈도부터 확인
        ↓ (충돌 잦으면)
4. 비관적 락이 필요한가?           → 처리량 대가를 감수
        ↓
5. 그리고 항상: DB 제약을 최후 방어선으로 깔아 둔다
```

### 도구를 고르기 전에 밟는 사고의 순서

> 출처: `08-engineering-axes-deep.md` §1 (「사고의 순서」)

```text
1. 경합하는 자원이 무엇인가   → 행 하나? 집계값? 외부 API 호출 횟수?
        ↓
2. 경합 범위가 어디까지인가   → 단일 프로세스 / 인스턴스 간 / DB 레벨
        ↓
3. 틀렸을 때 비용이 얼마인가   → 조회수 카운터가 틀리는 것과 잔액이 틀리는 것은 다르다
        ↓
4. 그제야 도구를 고른다
```

> 순서를 거꾸로 밟으면(도구부터 고르면) "일단 락 걸었습니다"가 된다.

## 분산 락에 대한 경고

**분산 락은 정확성 보장 수단이 아니다.**

```text
프로세스 A: 락 획득 (TTL 10초)
        ↓
프로세스 A: GC 일시정지 15초    ← 그 사이 락이 만료됨
        ↓
프로세스 B: 락 획득 (A가 죽은 줄 알고)
        ↓
프로세스 A: 깨어나서 자기가 락을 쥐었다고 믿고 작업 수행
        ↓
→ 둘이 동시에 임계 구역에 있다
```

- TTL 만료, GC 정지, 네트워크 지연으로 **두 프로세스가 동시에 락을 가졌다고 믿을 수 있다.**
- **분산 락은 "중복 작업을 줄이는 최적화"로만 쓴다.**
- 정확성이 필요하면 **저장소 레벨의 조건부 쓰기나 펜싱 토큰**으로 지킨다.

> **펜싱 토큰(fencing token)** — 락을 줄 때마다 1씩 커지는 번호를 함께 발급해, 저장소가 "더 큰 번호만 받는다"로 늦게 온 옛 소유자를 거른다.\
> 예: A가 토큰 33으로 잠갔다 멈춘 사이 B가 토큰 34를 받으면, 뒤늦게 깨어난 A(33)의 쓰기는 저장소가 거부한다.

## 규모별 방어 범위

**같은 방어가 규모가 바뀌면 무효가 된다.**

| 범위 | 유효한 수단 | 무효해지는 것 |
|---|---|---|
| 단일 프로세스 | 프로세스 내 락, 원자적 카운터 | — |
| 다중 인스턴스 | DB 락, 조건부 업데이트, 유니크 제약 | **프로세스 내 락 전부 무효** |
| 다중 리전 | 리전별 소유권 분할, CRDT | DB 락도 지연 문제 |

> **가장 흔한 사고**: 단일 인스턴스에서 잘 돌던 프로세스 내 락이, 인스턴스를 2대로 늘리는 순간 조용히 무효가 된다. 코드는 그대로라 아무도 눈치채지 못한다.

## 자문 체크리스트

- [ ] 이 API가 **동시에 2번** 호출되면 어떻게 되는가
- [ ] 클라이언트가 재시도하면 중복이 생기는가
- [ ] 애플리케이션 로직이 뚫려도 **DB 제약이 막아주는가**
- [ ] 인스턴스가 2대가 되어도 이 방어가 유효한가
- [ ] 스케줄러·배치가 중복 실행되지 않는가
- [ ] 분산 락에 정확성을 의존하고 있지 않은가
- [ ] 트랜잭션 범위 안에 외부 API 호출이 있지 않은가 (락 유지 시간이 폭증한다)

## 자기 경험을 말하는 방식

**나쁜 답변**: "동시성 문제가 있어서 락을 걸었습니다."

**좋은 답변의 형태**

> "재고 차감에서 lost update가 날 수 있었습니다. 충돌 빈도가 낮아 처음엔 낙관적 락을 검토했는데, 인기 상품은 충돌이 잦아 재시도가 폭증했습니다. 그래서 조건부 업데이트(`WHERE qty >= 1`)로 바꿔 한 번의 쿼리로 확인과 차감을 원자적으로 처리했고, 최후 방어선으로 `CHECK (qty >= 0)` 제약을 걸었습니다."

**포함해야 할 요소**: 어떤 실패 유형인지 → 어떤 수단을 왜 골랐는지 → 무엇을 대가로 냈는지 → 최후 방어선이 무엇인지.

## 핵심 문장

- **동시성은 "빠른가"가 아니라 "틀리지 않는가"다 — 정확성을 위해 성능을 내주는 축이다.**
- **동시성 실패는 조용하다 — 예외도 로그도 없고, 단일 스레드 테스트로는 재현되지 않는다.**
- **도구보다 순서가 먼저다 — 무엇이 경합하나 → 범위는 어디까지인가 → 틀리면 비용이 얼마인가 → 그제야 도구.**
- **DB 제약(유니크·CHECK)은 앱 로직보다 강한 최후 방어선이다.**
- **분산 락은 정확성 보장이 아니다 — 정확성은 조건부 쓰기나 펜싱 토큰으로.**

---

## 용어 풀이

- **정확성(Correctness)** — 동시 접근이 있어도 결과가 규칙에 맞게 남는 성질. 성능(빠름)과 별개다.
- **Lost Update(갱신 유실)** — 나중 쓰기가 앞 쓰기를 덮어 앞의 변경이 사라지는 것.
- **Write Skew(쓰기 왜곡)** — 각자 조건 통과했는데 합쳐지면 불변식이 깨지는 것.
- **Phantom Read(팬텀 리드)** — 범위 검사 뒤 새 행이 끼어들어 "없음" 확인이 무효가 되는 것.
- **낙관적 락(Optimistic Lock)** — 충돌이 드물다고 보고 진행 후 저장 직전 version으로 확인, 어긋나면 재시도.
- **비관적 락(Pessimistic Lock)** — 충돌이 잦다고 보고 읽는 순간부터 행을 잠금.
- **조건부 업데이트(Conditional Update)** — `WHERE` 조건에 불변식을 넣어 확인과 변경을 한 쿼리로 원자 처리.
- **멱등성 키(Idempotency Key)** — 같은 키의 재시도는 같은 결과 한 번으로 처리되게 하는 식별자.
- **분산 락(Distributed Lock)** — 여러 인스턴스를 조율하는 락. TTL·GC로 두 소유자가 생길 수 있어 정확성 보장은 아니다.
- **펜싱 토큰(Fencing Token)** — 락과 함께 커지는 번호를 발급해 늦게 온 옛 소유자의 쓰기를 저장소가 거르게 하는 것.
- **격리 수준(Isolation Level)** — 트랜잭션이 서로의 중간 상태를 얼마나 보는지의 등급. 높일수록 안전하고 느리다.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **왜 격리 수준만으로 lost update가 안 막히나.** 표준 격리 수준은 "이미 커밋된 값을 읽는가, 읽는 동안 그 값이 바뀌는가"를 다룰 뿐, "내가 읽은 값을 남이 그 사이 바꿨는지"는 직렬화 가능(Serializable) 수준이나 명시적 락·조건부 쓰기가 있어야 잡힌다. 그래서 원고가 "격리 수준만으로는 안 막힌다"고 콕 집는다.
- **원자성(atomicity)의 두 층.** 조건부 업데이트가 강력한 이유는 "확인"과 "변경"이 **한 문장 = 한 원자 연산**이라 그 사이에 남이 끼어들 틈이 없기 때문이다. 애플리케이션에서 읽고-판단하고-쓰면 그 세 걸음 사이에 틈이 생긴다. 경합 방어의 상당수는 "틈을 없애기"로 환원된다.
- **CAS(Compare-And-Swap).** 낙관적 락의 하드웨어·언어 레벨 형제. "기대값과 같을 때만 새 값으로 바꾼다"는 원자 연산으로, version 컬럼 비교가 이 아이디어의 DB판이다.
