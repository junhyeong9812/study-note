## 한눈에 — 쉽게 말하면

고속도로가 100대 중 99대는 60초에 통과하는데, 1대가 매번 사고 구간에 걸려 5분이 걸린다고 하자. *(Claude 보강 — 원고에 없는 비유)*

```text
평균만 보면        꼬리(p99)를 보면
+-------------+    +----------------------+
| 평균 62초    |    | 100명 중 1명은 5분    |
| "빠르네"     |    | = 그 1명은 서비스를   |
|             |    |   못 쓰는 것          |
+-------------+    +----------------------+
```

**성능도 똑같은 구조다.** 평균 응답 200ms에 p99가 5초면 사용자 1%는 못 쓰는 것이다.\
게다가 한 화면이 API를 10개 부르면 그중 하나라도 느릴 확률이 커져서, **p99가 사실상 체감 성능**이 된다. 성능은 평균이 아니라 꼬리를 보는 축이다.

## 대원칙 3개

> 출처: 원고 §1

### ① 평균이 아니라 꼬리(tail)를 본다

```text
평균 200ms, p99 5초
→ 사용자 100명 중 1명은 서비스를 못 쓴다
```

한 페이지가 API를 10개 호출하면 **그중 하나라도 느릴 확률**은 훨씬 높다. → **p99가 사실상의 체감 성능이다.**

**추가 규칙**: **성공과 실패를 분리해서 측정한다.** 빠르게 실패하는 요청이 많으면 평균 지연이 오히려 좋아 보인다.

> **p99(99퍼센타일)** — 요청을 느린 순으로 줄 세웠을 때 99번째, 즉 "가장 느린 1%의 문턱" 값. 평균이 감추는 꼬리를 드러낸다.\
> 예: p99가 5초라는 건 "100명 중 1명은 5초 이상 기다린다"는 뜻이다.

### ② 측정 없이 최적화하지 않는다

병목은 직관과 거의 항상 다르다. 프로파일링 → 실행 계획 → 트레이스 순으로 근거부터 본다.

### ③ 가장 큰 병목부터 (암달의 법칙)

전체의 5%인 구간을 2배 빠르게 해도 전체는 2.5%밖에 안 빨라진다.

## 백엔드 병목 카탈로그

> 출처: 원고 §3

| 병목 | 진단 | 처방 |
|---|---|---|
| **N+1 쿼리** | 요청당 쿼리 수, 같은 형태 반복 | fetch join, batch size, DataLoader |
| **인덱스 미사용** | 실행 계획에 풀 스캔(Seq Scan) | 복합 인덱스 (선택도 높은 컬럼 선두), 커버링 인덱스 |
| **잘못된 실행 계획** | 통계 낡음, 데이터 분포 변화 | 통계 갱신, 힌트, 쿼리 재작성 |
| **락 대기** | 락 대기 시간, 스레드 덤프 | 트랜잭션 범위 축소, 락 순서 통일 |
| **커넥션 풀 대기** | 풀 대기 시간 지표 | **트랜잭션에서 외부 호출 제거**, 풀 재산정 |
| **직렬 호출** | 트레이스의 순차 구간 | 병렬화, 배치 API |
| **과도한 데이터** | 응답 크기, 전송 시간 | `SELECT *` 제거, 페이지네이션, 필요한 필드만 |
| **직렬화 비용** | CPU 프로파일 | 응답 축소, 포맷 변경 |
| **GC** | GC 로그, stop-the-world | 할당량 감소, 힙 조정 |

> **N+1 쿼리** — 목록 1건을 얻는 쿼리에 이어, 각 항목의 상세를 얻으려 N건을 더 날리는 패턴. 100건이면 1+100 쿼리가 나간다.\
> 예: 주문 100건을 조회한 뒤 주문마다 회원 이름을 따로 조회하면 쿼리가 101번 나간다 — fetch join으로 한 번에 가져오면 1~3번으로 준다.

```text
개선 순서

1. N+1 제거          ← 효과가 가장 크다
2. 인덱스
3. 쿼리 재작성
4. 캐시              ← 여기서부터 복잡도가 는다
5. 비동기화 / 사전 계산
```

## 캐시에 대한 균형 잡힌 시각

캐시는 성능 개선의 대표 수단이지만, 공짜가 아니다.

| 조건 | 결과 |
|---|---|
| 히트율 낮음 | 오버헤드만 증가 |
| 캐시 미스 경로가 느림 | **그게 그대로 p99가 된다** |
| 무효화 로직 복잡 | 새로운 버그 원천 |
| 캐시 의존도 높음 | **캐시가 죽으면 시스템이 죽는다** |

> **원칙: 먼저 쿼리를 고치고, 그 다음 캐시.**\
> 순서를 바꾸면 근본 문제가 덮여서 나중에 캐시를 걷어낼 수 없게 된다.

> **캐시 스탬피드(cache stampede)** — 인기 키의 캐시가 만료된 순간, 그걸 노리던 많은 요청이 동시에 원본(DB)으로 몰려 원본을 때리는 현상.\
> 예: 메인 배너 데이터 캐시가 정오에 만료되면, 그 찰나에 들어온 수천 요청이 전부 DB로 가 DB가 출렁인다.

## 백엔드와 프론트의 접점

**백엔드 p99는 그대로 프론트 LCP가 된다.**

"백엔드는 빠른데 화면이 느리다"는 대부분 **측정 구간이 다른 것**이다.

```text
백엔드가 보는 구간        실제 사용자가 겪는 구간
앱 진입 ~ 응답            DNS + TLS + 네트워크 + 서버 + 다운로드 + 렌더
= 50ms                   = 2초
```

> **종단(end-to-end) 측정, 특히 RUM(실사용자 모니터링)이 있어야 대화가 된다.**\
> 서버 로그의 응답 시간만 보면 영원히 "우리는 빠른데요"가 된다.

## 성능 작업의 함정

| 함정 | 설명 |
|---|---|
| **조기 최적화** | 병목이 아닌 곳을 최적화하며 코드를 망가뜨림 |
| **마이크로 벤치마크 맹신** | JIT 워밍업·캐시 효과로 실제와 다름 |
| **빈 DB에서 테스트** | 데이터가 쌓이면 완전히 다른 결과 |
| **평균만 보기** | p99를 놓침 |
| **가독성 희생** | 측정된 효과 없이 복잡도만 증가 |
| **로컬에서만 측정** | 네트워크 지연·동시성이 빠져 있음 |

## 체크리스트

- [ ] p99를 측정하고 있는가 (평균만 보고 있지 않은가)
- [ ] 성공/실패 지연을 분리해서 보는가
- [ ] 요청당 쿼리 수를 아는가 (N+1 탐지)
- [ ] 느린 쿼리 상위 항목을 정기적으로 보는가
- [ ] 캐시 히트율을 측정하고, **미스 경로의 지연**을 아는가
- [ ] 프로덕션 규모 데이터로 테스트했는가
- [ ] 실사용자 관점(RUM) 지표가 있는가
- [ ] 최적화 전후를 **숫자로** 비교했는가

## 자기 경험을 말하는 방식

**나쁜 답변**: "쿼리를 최적화해서 성능을 개선했습니다."

**좋은 답변의 형태**

> "목록 API의 p99가 3초였습니다. APM으로 보니 요청당 쿼리가 200개 넘게 나가는 N+1이었고, fetch join으로 3개로 줄여서 p99가 300ms가 됐습니다. 캐시도 검토했지만 데이터 변경이 잦아 히트율이 낮을 것 같아서, 쿼리를 먼저 고치는 쪽을 택했습니다."

**포함해야 할 요소**: 어떤 지표가 → 얼마였고 → 원인이 무엇이었고 → 어떻게 확인했고 → 얼마가 됐는가.

## 핵심 문장

- **성능은 평균이 아니라 꼬리(p99)를 보는 축이다 — p99가 사실상 체감 성능이다.**
- **측정 없이 최적화하지 않는다 — 병목은 직관과 거의 항상 다르다.**
- **개선 순서는 N+1 제거 → 인덱스 → 쿼리 재작성 → 그 다음에 캐시.**
- **캐시는 공짜가 아니다 — 먼저 쿼리를 고치고, 못 미더우면 그제야 캐시.**
- **백엔드 p99는 그대로 프론트 LCP가 된다 — 종단(RUM) 측정이 있어야 대화가 된다.**

## 용어 풀이

- **속도(Performance)** — 같은 일을 더 적은 시간·자원으로 처리하는 성질. 확장성(더 많은 일)과 구분된다.
- **p50 / p95 / p99** — 느린 순으로 줄 세웠을 때의 중앙·상위 5%·상위 1% 문턱 값.
- **처리량(RPS)** — 초당 처리 요청 수. 확장으로 좋아지는 건 응답 시간이 아니라 이 값.
- **암달의 법칙(Amdahl's Law)** — 일부 구간만 빨라져도 전체 개선폭은 그 구간 비중에 묶인다는 법칙.
- **N+1 쿼리** — 목록 1건 + 각 항목 상세 N건으로 쿼리가 폭증하는 패턴.
- **LCP / INP / CLS** — 주요 콘텐츠 표시 시점 / 입력 반응 지연 / 레이아웃 밀림. 프론트 체감 지표.
- **TTFB** — 첫 바이트 도착까지의 시간. 서버·네트워크 지연의 합.
- **캐시 스탬피드(Cache Stampede)** — 인기 키 만료 순간 요청이 원본으로 몰리는 현상.
- **RUM(Real User Monitoring)** — 실제 사용자 브라우저에서 측정한 종단 성능 지표.
- **조기 최적화(Premature Optimization)** — 병목도 아닌 곳을 측정 없이 최적화하며 복잡도만 늘리는 것.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문과 섞어 인출하지 않는다.

- **왜 API를 여러 개 부르면 p99가 지배하나(꼬리의 곱).** 한 화면이 독립된 API를 10개 부르고 화면은 다 와야 완성이라면, "10개 다 빠를 확률"은 각 API가 빠를 확률의 곱이다. 각 API의 p99 비율이 1%라도, 10개 중 하나라도 걸릴 확률은 대략 1−0.99¹⁰ ≈ 10%로 뛴다. 그래서 개별 p99보다 화면 p99가 더 나쁘다.
- **커버링 인덱스.** 인덱스만 읽고 테이블 본문을 안 봐도 되게, 조회하는 컬럼까지 인덱스에 포함시키는 것. "인덱스 탔는데도 느리다"의 흔한 해법이다.
- **비동기화는 지연을 없애는 게 아니라 옮긴다.** 무거운 작업을 큐로 넘기면 응답은 빨라지지만, 그 일은 사라지지 않고 뒤에서 처리된다. 사용자에게 "접수됨"을 즉시 주되 결과 반영은 나중이 되는 것 — 성능 개선이자 [`./ux.md`](./ux.md)의 낙관적 처리와 맞닿는 지점이다.
