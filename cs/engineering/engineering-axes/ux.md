# UX (개발자 관점)

> 이 컬렉션의 인덱스는 [README.md](./README.md)에서 시작한다.\
> 출처: `jun-bank/docs/study/notes/axes/ux.md` (본체) + `08-engineering-axes-deep.md` §4 · 이관일 2026-09-16.\
> 본문 표·절은 **원고**를 고쳐 쓴 것이다. 「한눈에」의 비유·그림과 맨 끝 `[Claude 추가]`는 **Claude 보강**이다.

**지키는 것: 사용 가능성.** 디자인이 예쁜가가 아니라 **인터랙션이 답답하지 않은가.** 디자이너가 아니라 **개발자가 책임지는 영역**이 분명히 있다.

---

## 한눈에 — 쉽게 말하면

엘리베이터 버튼을 눌렀는데 불이 안 들어오는 상황을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
불이 안 들어오는 버튼        누르면 불이 들어오는 버튼
+------------------+       +------------------+
| 눌렸나? 몰라서    |       | 접수됐구나        |
| 또 누름, 또 누름   |       | 기다림            |
+------------------+       +------------------+
  → 중복 호출 = 동시성 문제    → 결과 전이라도 "반응"은 즉시
```

**화면도 똑같은 구조다.** 결과를 당장 못 줘도 "반응"은 100ms 안에 줘야 한다 — 버튼 비활성화든 스피너든.\
반응이 없으면 사용자는 버튼을 다시 누르고, 그건 곧 [`./concurrency.md`](./concurrency.md)의 중복 제출 문제가 된다. UX는 디자인이 아니라 이런 개발자 결정의 총합이다.

---

## 개발자가 책임지는 UX

디자인 시안에는 없지만 개발자가 결정하는 것들:

| 영역 | 개발자의 결정 |
|---|---|
| **상태 처리** | 로딩·빈·에러·부분 실패 화면을 만들었는가 |
| **반응 속도** | API 병렬화, 캐싱, 낙관적 업데이트 |
| **에러 메시지** | 사용자가 다음에 뭘 해야 할지 알 수 있는가 |
| **레이아웃 안정성** | 뒤늦게 들어온 콘텐츠가 화면을 밀어내지 않는가 |
| **접근성** | 키보드, 포커스, 스크린리더 |
| **재시도 안전성** | 더블 클릭이 중복 주문이 되지 않는가 |

---

## 상태를 다 만들었는가

> 출처: 원고 §2

**성공 경로만 만든 화면은 미완성이다.**

| 상태 | 빠뜨리면 |
|---|---|
| **Loading** | 화면이 멈춘 것처럼 보임 → **사용자가 버튼을 다시 누름** (동시성 문제로 이어짐) |
| **Empty** | "데이터가 없음"과 "로딩 실패"를 구분 못 함 |
| **Error** | 무슨 일이 났는지 모름. **복구 수단(재시도 버튼)까지** 있어야 완성 |
| **Partial** | 일부만 실패했는데 전체를 못 쓰게 만듦 |
| **Stale** | 오래된 데이터를 최신인 것처럼 보여줌 |
| **Offline** | 네트워크 없는 상태에서 무한 로딩 |

> **스켈레톤 UI가 스피너보다 나은 이유**: 레이아웃을 미리 확보해서 로딩 후 화면이 튀지 않는다. 즉 CLS까지 같이 해결한다.

> **스켈레톤 UI(skeleton UI)** — 콘텐츠가 올 자리에 회색 뼈대 모양을 미리 깔아 두는 로딩 표시.\
> 예: 목록이 오기 전 회색 줄 몇 개를 그려 두면, 실제 데이터가 와도 자리가 밀리지 않아 오클릭이 안 생긴다.

### 에러 메시지 원칙

| 나쁨 | 좋음 |
|---|---|
| "오류가 발생했습니다" | "일시적인 문제입니다. 다시 시도해 주세요" + 재시도 버튼 |
| "500 Internal Server Error" | 내부 코드는 감추되, **추적용 ID는 보여준다** |
| 무엇을 해야 할지 없음 | **다음 행동**을 제시 |

## 반응성

| 지표 | 의미 | 기준 |
|---|---|---|
| **LCP** | 주요 콘텐츠 표시 | 2.5초 이하 |
| **INP** | 입력 반응 지연 | 200ms 이하 |
| **CLS** | 레이아웃 밀림 | 0.1 이하 |

### 체감 규칙

```text
100ms 이내  → 즉각적으로 느낀다
1초 이내    → 흐름이 유지된다
10초 이상   → 다른 일을 하러 간다
```

> **결과를 못 주더라도 "반응"은 즉시 줘야 한다.**\
> 버튼 비활성화, 스피너, 낙관적 업데이트 — 무엇이든 100ms 안에 화면이 바뀌어야 한다.

### 레이아웃 시프트 (CLS)

이미지·광고·폰트가 뒤늦게 들어와 콘텐츠를 밀어내면, **누르려던 걸 못 누르고 엉뚱한 걸 누른다.** (결제 버튼 옆에 광고가 뜨는 경우)

- 이미지에 `width`/`height` 또는 `aspect-ratio` 명시.
- 폰트 로딩 전략(`font-display`).
- 동적 삽입 영역은 미리 공간 확보.

> **CLS(Cumulative Layout Shift)** — 로딩 중 화면 요소가 얼마나 밀렸는지의 누적 지표. 클수록 오클릭이 잦다.\
> 예: 글을 읽으려는데 위에서 배너가 늦게 떠 본문이 아래로 밀리면, 누르려던 링크 대신 배너를 누르게 된다.

## 낙관적 업데이트

서버 응답을 기다리지 않고 UI를 먼저 바꾸고, 실패하면 되돌린다.

| 적합 | 부적합 |
|---|---|
| 좋아요, 북마크 | **결제** |
| 체크박스, 토글 | **삭제** (되돌리면 더 혼란) |
| 정렬·필터 | 잔액 변동 |
| 목록에 항목 추가 | 재고 확정 |

**기준: 실패했을 때 되돌리는 게 사용자에게 자연스러운가?**

- 좋아요가 잠깐 켜졌다 꺼지는 건 괜찮다.
- "결제 완료"가 떴다가 취소되는 건 사고다.

> **낙관적 업데이트(optimistic update)** — 서버가 성공할 것이라 낙관하고 화면을 먼저 바꾼 뒤, 실패하면 되돌리는 방식. 반응은 즉각적이지만 잠깐 "거짓말"을 한다.\
> 예: 좋아요를 누르면 하트가 바로 채워지고, 서버가 실패하면 슬쩍 되돌린다 — 사용자는 대기를 안 느낀다.

## 프론트에도 있는 동시성 문제

| 문제 | 시나리오 | 해법 |
|---|---|---|
| **응답 경쟁 상태** | 빠르게 타이핑 → **늦게 온 옛 응답이 최신 결과를 덮어씀** | 이전 요청 취소, 요청 시퀀스 번호 |
| **중복 제출** | 더블 클릭 | 제출 중 비활성화 + **서버 멱등성 키** |
| **탭 간 상태 불일치** | 여러 탭에서 다른 상태 | 탭 간 브로드캐스트, 포커스 시 재검증 |

> **프론트만으로는 중복 제출을 막을 수 없다.** 네트워크 재시도, 새로고침, 뒤로가기가 있다.\
> **서버 멱등성이 있어야 완성이다.** → [`./concurrency.md`](./concurrency.md)

## 접근성

**많은 나라에서 법적 요구사항이다.** 선택 사항이 아닌 경우가 있다.

- [ ] 키보드만으로 모든 기능에 도달 가능한가
- [ ] 포커스 표시가 보이는가 (`outline: none`만 하고 대체 스타일이 없는 경우가 흔하다)
- [ ] **모달을 열면 포커스가 안으로 들어가고, 닫으면 원래 자리로 돌아오는가**
- [ ] 이미지 대체 텍스트, 폼 레이블이 있는가
- [ ] 색 대비가 충분한가 (색만으로 정보를 전달하지 않는가)
- [ ] 동적 변경이 스크린리더에 알려지는가 (`aria-live`)

## 백엔드 개발자도 UX 지표를 갖는다

**백엔드 p99는 그대로 UX다.**

| 백엔드의 결정 | UX 결과 |
|---|---|
| p99 지연 | 사용자 1%의 체감 속도 |
| 에러 응답 형식 | 프론트가 좋은 에러 메시지를 만들 수 있는가 |
| 부분 실패 지원 | 일부 실패 시 나머지라도 보여줄 수 있는가 |
| 멱등성 제공 | 재시도가 안전한가 |
| 페이지네이션 방식 | 무한 스크롤이 가능한가 |
| 폴백 가능한 응답 | 추천 실패 시 인기 목록이라도 |

> "백엔드라 UX는 잘 모릅니다"보다, "**p99와 에러 응답 설계가 UX에 직결된다**"고 말하는 게 훨씬 강하다. → [`./performance.md`](./performance.md)

## 체크리스트

- [ ] 모든 비동기 화면에 로딩·빈·에러 상태가 있는가
- [ ] 에러 화면에 **다음 행동**(재시도 등)이 있는가
- [ ] 버튼 클릭 후 100ms 안에 화면이 반응하는가
- [ ] 중복 제출이 막히는가 (프론트 + **서버 멱등성**)
- [ ] 늦게 온 응답이 최신 데이터를 덮어쓰지 않는가
- [ ] 이미지·동적 콘텐츠로 레이아웃이 밀리지 않는가
- [ ] 키보드만으로 사용 가능한가
- [ ] 실사용자 지표(RUM)를 측정하고 있는가

## 자기 경험을 말하는 방식

**나쁜 답변**: "UX는 디자이너 영역이라서요."

**좋은 답변의 형태**

> "목록 화면에서 로딩 중에 사용자가 버튼을 여러 번 누르는 문제가 있었습니다. 프론트에서 제출 중 비활성화를 하고, 근본적으로는 서버에 멱등성 키를 도입해서 중복 요청이 같은 결과를 반환하게 했습니다. 그리고 스켈레톤 UI로 바꿔서 로딩 후 레이아웃이 튀는 것도 같이 해결했습니다."

**포함해야 할 요소**: 어떤 인터랙션 문제였나 → 화면에서 무엇을 했나 → 근본 해결(서버)은 무엇이었나 → 곁가지로 무엇까지 같이 해결됐나.

## 핵심 문장

- **UX는 디자인 심미성이 아니라 "인터랙션이 답답하지 않은가" — 개발자가 책임지는 영역이 분명히 있다.**
- **성공 경로만 만든 화면은 미완성이다 — 로딩·빈·에러·부분 실패·낡음까지가 완성.**
- **결과를 못 줘도 반응은 100ms 안에 줘야 한다 — 없으면 사용자가 버튼을 다시 누른다.**
- **프론트만으로는 중복 제출을 못 막는다 — 서버 멱등성이 있어야 완성이다.**
- **백엔드 p99·에러 응답 설계·멱등성은 그대로 UX 지표다.**

## 용어 풀이

- **사용 가능성(Usability)** — 동작은 하는데 쓰기 편한가. UX가 지키는 것.
- **상태(States)** — 로딩·빈·에러·부분 실패·낡음·오프라인. 성공 경로 외 화면들.
- **스켈레톤 UI(Skeleton UI)** — 콘텐츠 자리에 회색 뼈대를 미리 깔아 레이아웃을 확보하는 로딩 표시.
- **LCP / INP / CLS** — 주요 콘텐츠 표시 / 입력 반응 지연 / 레이아웃 밀림. 체감 지표.
- **낙관적 업데이트(Optimistic Update)** — 성공을 낙관해 화면을 먼저 바꾸고 실패 시 되돌리는 방식.
- **응답 경쟁 상태(Response Race Condition)** — 늦게 온 옛 응답이 최신 결과를 덮어쓰는 프론트 동시성 문제.
- **멱등성(Idempotency)** — 같은 요청을 여러 번 보내도 결과가 한 번과 같은 성질. 재시도 안전의 근거.
- **접근성(Accessibility, a11y)** — 키보드·스크린리더 등으로 누구나 쓸 수 있게 하는 것. 종종 법적 요구.
- **RUM(Real User Monitoring)** — 실제 사용자 환경에서 측정한 종단 성능 지표.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문과 섞어 인출하지 않는다.

- **왜 "로딩 없음"이 곧 동시성 버그로 이어지나.** 화면이 반응을 안 주면 사용자는 "안 눌렸나?" 하고 다시 누른다. 그 두 번째 클릭이 서버로 또 한 번 요청을 보내 [`./concurrency.md`](./concurrency.md)의 중복 실행이 된다. UX의 상태 처리와 백엔드의 멱등성이 사실상 같은 문제의 앞뒤라는 점이 이 컬렉션의 핵심 교차점이다.
- **Core Web Vitals.** LCP·INP·CLS는 구글이 정한 "핵심 웹 지표(Core Web Vitals)" 세 축으로, 검색 순위에도 반영된다. 그래서 UX 지표가 "예쁨"이 아니라 측정·목표 관리의 대상이 된다 — [`./performance.md`](./performance.md)의 p99처럼 숫자로 말할 수 있는 UX다.
- **RUM vs 합성 모니터링.** RUM은 실제 사용자 브라우저에서, 합성 모니터링(synthetic)은 정해진 환경에서 봇이 측정한다. "우리 서버는 빠른데 사용자는 느리다"의 간극을 메우려면 RUM이 필요하다는 게 원고의 요지다.
