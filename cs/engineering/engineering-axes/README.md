## 어떻게 읽나

1. **먼저 이 README의 [혼동 3가지]와 [축 사이 트레이드오프]를 본다.** 축을 서로 구별하는 것이 출발점이다.
2. **관심 있는 축 문서로 들어간다.** 각 문서는 「한눈에 → 정의 → 실패/도구 → 체크리스트 → 자기 경험 말하는 방식 → 핵심 문장 → 용어 풀이」 순서로 같은 골격이다. 두 번째 문서부터는 어디에 뭐가 있는지 안 찾아도 된다.
3. **축 사이를 오간다.** 문서 안 「관련 자료」의 상대경로 링크(`./concurrency.md` 등)로 교차점을 따라간다. 이 축들은 독립적이지 않다.
4. **마지막에 [자기 경험 번역]으로 자기 프로젝트를 이 축의 언어로 옮겨 본다.** 빈칸이 곧 다음 공부 주제다.

## 먼저 정리할 혼동 3가지

> 출처: `axes/README.md` · `08-engineering-axes-deep.md` §0

### ① Concurrency ≠ Performance

동시성은 "빠른가"가 아니라 **"틀리지 않는가"**다.\
락을 걸면 오히려 느려진다. 성능을 위해 락을 푸는 게 아니라, **정확성을 위해 성능을 내주는** 것이다.

### ② Scalability ≠ Performance

요청 1건이 10ms인 건 성능. 요청이 10배 와도 10ms인 건 확장성.\
**단일 요청이 아무리 빨라도 수평 확장이 막혀 있으면 확장성은 0이다.**

### ③ Availability ≠ Scalability

레플리카 3대는 둘 다에 기여하지만 목적이 다르다.\
확장성은 **부하 분산**, 가용성은 **대체 가능성**. 부하가 없어도 가용성을 위해 레플리카가 필요하다.

## 축 사이의 트레이드오프

**축은 독립적이지 않다. 하나를 올리면 다른 게 내려간다.** 이걸 말할 수 있으면 이해도가 드러난다.

| 충돌 | 내용 |
|---|---|
| **Concurrency ↔ Performance** | 락은 정확성을 사고 처리량을 판다 |
| **Consistency ↔ Availability** | 분단 시 정합성을 지키면 요청을 거절해야 한다 (CAP) |
| **Scalability ↔ Consistency** | 복제·샤딩은 최종적 일관성을 부른다 |
| **Performance ↔ Maintainability** | 캐시·비정규화는 복잡도를 늘린다 |
| **Availability ↔ 비용** | 9 하나에 비용 한 자릿수 |
| **System Design ↔ 개발 속도** | 미리 쪼개면 오버엔지니어링, 안 쪼개면 나중에 비쌈 |
| **UX ↔ Consistency** | 낙관적 업데이트는 잠깐 거짓말을 한다 |

> **좋은 답변**: "A를 위해 B를 얼마만큼 내줬고, 그 판단 근거는 C였습니다."\
> **나쁜 답변**: "성능도 좋고 확장성도 좋고 유지보수도 좋게 만들었습니다."

> **트레이드오프(trade-off)** — 하나를 얻으려면 다른 하나를 내줘야 하는 맞교환. 공짜 개선은 드물다.\
> 예: 캐시를 넣으면 조회는 빨라지지만(성능↑), 무효화 로직이라는 새 복잡도(유지보수↓)를 떠안는다.

---

## 경계는 깔끔하지 않다 (교차 번역)

"그건 제 영역이 아니라서요"로 선을 긋기보다, 각 축을 **자기 도메인 언어로 번역**하는 게 훨씬 강하다.

| 축 | 백엔드 버전 | 프론트 버전 |
|---|---|---|
| **Concurrency** | 행 락, 격리 수준, 멱등성 키 | 응답 경쟁 상태, 요청 취소, 중복 제출 |
| **Availability** | 이중화, failover, 서킷 브레이커 | CDN, 오프라인 캐시, API 실패 시 폴백 UI |
| **Scalability** | 샤딩, 복제 | 가상 스크롤, 페이지네이션, 점진적 로딩 |
| **UX** | **p99 지연, 에러 응답 설계, 멱등성** | 인터랙션 반응성 |
| **Maintainability** | 계층 분리, 관측성 | 컴포넌트 경계, 디자인 토큰 |

**특히 기억할 두 가지**

- **백엔드 p99는 그대로 UX다.** → [`./performance.md`](./performance.md) · [`./ux.md`](./ux.md)
- **프론트에도 동시성이 있다.** 늦게 온 옛 응답이 최신 데이터를 덮어쓴다. → [`./concurrency.md`](./concurrency.md)

## 자기 경험을 이 축으로 번역하기

### 번역 템플릿

```text
[상황]  어떤 규모/제약에서
   ↓
[축]    어떤 축의 문제였고
   ↓
[선택]  무엇을 골랐고
   ↓
[대가]  무엇을 내줬고
   ↓
[측정]  어떻게 확인했는가
```

**예시** *(일반화한 상황)*

> "일 수백만 건의 이벤트 파이프라인에서(상황) 발행 유실을 막는 게 문제였는데(Concurrency/신뢰성), 정식 아웃박스 대신 발송 로그 + 대조 배치를 택했습니다(선택). 실시간 보장을 배치 주기만큼의 복구 지연으로 바꾼 것이고(대가), 이게 성립한 건 이벤트를 원천 상태에서 다시 만들 수 있었기 때문입니다. 대조 배치의 누락 검출 건수를 지표로 봤습니다(측정)."

### 자기 점검 매트릭스

프로젝트별로 채워보고, **빈칸이 곧 다음 공부 주제이자 예상 질문**이다.

| 축 | 내 사례 | 측정한 수치 | 내준 대가 |
|---|---|---|---|
| Concurrency | | | |
| Scalability | | | |
| Availability | | | |
| Performance | | | |
| System Design | | | |
| Maintainability | | | |
| UX | | | |

> **모든 칸을 채운 시스템은 없다.** 안 한 것을 "안 했다"가 아니라 **"이런 이유로 안 했다"**로 말할 수 있으면 그게 더 좋은 답이다.

## 한 문단 요약

> 출처: `08-engineering-axes-deep.md` §11

> 백엔드 고유 축은 동시성(정확성)·확장성(성장 여력)·가용성(연속성)이고, 프론트 고유 축은 UX(사용 가능성)다. 성능·시스템 설계·유지보수는 공통이지만 분야마다 지표와 수단이 다르다. 이 축들은 독립적이지 않아서 하나를 올리면 다른 게 내려가고, 그래서 좋은 설계 설명은 "다 좋게 만들었다"가 아니라 "무엇을 위해 무엇을 얼마만큼 내줬는가"의 형태를 띤다. 그리고 경계도 깔끔하지 않다. 프론트에도 응답 경쟁 상태라는 동시성 문제가 있고, 백엔드 p99는 그대로 UX 지표가 된다. 그래서 각 축을 자기 도메인 언어로 번역해서 말할 수 있는 게 실제 실력에 가깝다.

## 이 컬렉션의 통합 이력

- **`00`(요약)**: 백엔드 고유 / 프론트 고유 / 공통이라는 분류 뼈대와 교차점 → 이 README의 문서 목록·혼동 3가지·교차 번역으로 흡수.
- **`08`(심화)**: 각 축의 확장 서술(수직/수평, 확장 사다리, 4단계 가용성, 사고의 순서 등) → 해당 축 문서 본문에 흡수.
- **`axes/`(개별 축)**: 가장 다듬어진 본체 → 각 축 문서의 골격이 됨.
- 원본에 있던 외부 심화 링크(`server-design/*` 등 이 컬렉션 밖 문서)는 이관 대상이 아니어서 **죽은 링크가 되지 않도록 링크를 걸지 않았다.** 축 사이 링크만 상대경로로 유지한다.
