# 실패 지점 되짚기 절차 — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.\
> 근거는 [2-summary.md](2-summary.md)와 원고 `jun-bank/docs-backup-2026-09-15/study/notes/07-failure-point-checklist.md`(절차 노트).\
> 이 문서는 지식이 아니라 **절차** 문서다. 그러니 정답도 "무엇을 아는가"가 아니라 **"어떻게 할 것인가"**로 읽는다.

## 정답

**1. 답을 시작하기 전에 먼저 하는 것 — 범위 확정**

답이 아니라 **범위 확정**부터 한다.\
한 문장으로 되짚는다 — "말씀하신 게 **[N]번 지점**(발행 전 / 발행 중 / 브로커 / 소비 중 / 소비 후) 이야기로 이해했는데, 맞을까요? 아니면 전 구간을 말씀하시는 걸까요?"\
바로 답하면 안 되는 이유는 이렇다 — **지식이 있어도 질문의 범위를 좁게 잡으면 답이 반쪽이 된다.**\
"메시지 유실을 어떻게 막나요?"는 머릿속에서 **발행 측 문제로 자동 축소**되고, 그러면 아웃박스만 설명한 채 소비 측이 통째로 공백이 된다.\
듣는 쪽에서는 그게 "발행만 알고 소비는 모른다"로 읽힌다.\
전 구간을 묻는 것이었다면, 5칸을 순서대로 훑는 것만으로 답이 자동으로 완성된다.

**2. 다섯 칸과 각 칸의 실패 형태**

| # | 지점 | 실패 형태 |
|---|---|---|
| **1** | **발행 전** (비즈니스 TX ↔ 이벤트) | 이중 쓰기 — DB는 커밋됐는데 이벤트가 안 나감 |
| **2** | **발행 중** (앱 → 브로커) | 네트워크 실패, 브로커 미응답, 부분 성공 |
| **3** | **브로커** (저장·복제) | 리더 장애, 복제 미달, 보존 기간 만료로 소실 |
| **4** | **소비 중** (poll → 처리 → 커밋) | 처리 실패, 크래시, 커밋 순서에 따른 유실/중복, 리밸런싱 |
| **5** | **소비 후** (다운스트림 반영) | 처리는 됐는데 하위 시스템 미반영, 중복 반영 |

순서를 외우는 방식은 지점 이름 그대로다 — **발행 전 → 발행 중 → 브로커 → 소비 중 → 소비 후**.\
대응은 차례로 트랜잭셔널 아웃박스 / `acks=all`·`enable.idempotence`·재시도+백오프 / `replication.factor≥3`·`min.insync.replicas=2`·`unclean.leader.election=false` / 수동 커밋·재시도 토픽·DLT·멱등 소비(인박스) / 멱등 upsert·정합성 대조 배치·종단 추적(trace id)이다.

**3. 되짚는 한 문장이 하는 일 세 가지**

1. **범위를 확정**해서 반쪽 답을 막는다.
2. **5칸을 입 밖으로 꺼내는 순간** 내가 어디를 빼먹었는지 스스로 보인다.
3. 듣는 사람에게 **전체 구조를 알고 있다는 신호**를 준다.

되묻는 것이 감점이 아니라 가점인 이유가 곧 3번이다.\
5칸을 나열하면서 되묻는 행위 자체가 "나는 이 파이프라인에 실패 지점이 다섯 개라는 걸 안다"를 보여주기 때문이다.\
비용은 한 문장의 지연뿐인데, 그 대가로 "발행만 알고 소비는 모른다"로 읽힐 위험을 통째로 없앤다.

**4. 빈칸을 다루는 법 — 모든 칸을 닫는 게 목표인가**

**아니오.**\
**모든 칸을 닫은 시스템은 없다.**\
빈칸이 있으면 지우려 들지 말고 **"거기는 이런 이유로 열어뒀습니다"**를 준비한다.\
**닫지 않은 칸을 인지하고 있느냐**가 실력의 지표다.\
그래서 5칸 표를 직접 채워보는 연습의 값어치는 칸을 다 채우는 데 있지 않다 — 빈칸이 곧 취약점이자 앞으로 나올 질문이라는 것을 미리 알아두는 데 있다.

**5. 발행 전(1번)과 소비 중(4번) — 하나만 답하면 왜 반쪽인가**

- **발행 전(1번)** — 비즈니스 TX와 이벤트 기록의 관계를 다룬다. 실패 형태는 **이중 쓰기**(DB는 커밋됐는데 이벤트가 안 나감), 대응은 **트랜잭셔널 아웃박스**. 확인 질문은 "비즈니스 커밋과 이벤트 기록이 원자적인가".
- **소비 중(4번)** — poll → 처리 → 커밋 구간을 다룬다. 실패 형태는 처리 실패·크래시·커밋 순서에 따른 유실/중복·리밸런싱, 대응은 수동 커밋·재시도 토픽·DLT·**멱등 소비(인박스)**. 확인 질문은 "커밋이 처리 **후**인가, 중복이 와도 안전한가, 영구 실패가 파티션을 막지 않는가".

한쪽만 답하면 반쪽이 되는 이유는 **둘이 같은 파이프라인의 서로 다른 지점**이기 때문이다.\
1번을 완벽히 닫아도 4번이 새면 최종 결과는 여전히 유실이고, 그 반대도 같다.\
원고가 진단한 실패가 정확히 이 형태다 — 아웃박스(1번)만 설명하고 소비 측(4번)을 비운 답.

**6. 커밋을 처리 전에 하느냐 후에 하느냐**

원고의 4번 칸은 실패 형태를 **"커밋 순서에 따른 유실/중복"**으로 적고, 확인 질문 4번으로 **"커밋이 처리 후인가? 중복이 와도 안전한가?"**를 둔다.\
즉 절차로 정해진 답은 이렇다 — **커밋 시점을 처리 뒤로 옮기고(수동 커밋), 그 결과 남는 중복을 멱등 소비(인박스)로 흡수한다.**\
영구 실패가 파티션을 막지 않도록 재시도 토픽·DLT를 함께 둔다.\
확인 질문이 "중복이 와도 안전한가"만 묻고 "유실이 와도 안전한가"는 묻지 않는다는 점이 이 칸의 설계 방향을 그대로 드러낸다 — 대응 목록에 놓인 것은 중복을 흡수하는 장치(멱등 소비)다.\
「처리 **전** 커밋 = 유실 / 처리 **후** 커밋 = 중복」이라는 귀속과 "왜 후자가 나은가"의 이유 축은 원고가 직접 적지 않는다 — 아래 [Claude 추가]에 분리해 두었다.

**7. 같은 절차를 "성능을 어떻게 개선했나요?"에 적용하기**

되짚을 축은 **클라이언트 / 네트워크 / 앱 / DB**다 — "어디 구간의 레이턴시를 말씀하시는 걸까요?"로 먼저 확정한다.\
이 습관은 특정 브로커 전용이 아니라 **"어느 지점을 묻는지 먼저 확정한다"는 절차 자체가 자산**이기 때문에 그대로 옮겨간다.\
같은 골격으로 다른 질문도 축을 세운다.

| 질문 유형 | 되짚을 축 |
|---|---|
| "성능을 어떻게 개선했나요?" | 클라이언트 / 네트워크 / 앱 / DB — 어디 구간의 레이턴시? |
| "장애 대응 경험은?" | 감지 / 진단 / 완화 / 복구 / 사후 — 어느 단계? |
| "동시성 문제를 어떻게 풀었나요?" | 단일 프로세스 내 / 인스턴스 간 / DB 레벨 — 어느 범위의 경합? |
| "캐시를 어떻게 쓰셨나요?" | 무효화 / 정합성 / 스탬피드 / 만료 정책 — 어느 문제? |
| "확장성을 어떻게 확보했나요?" | 앱 / DB 읽기 / DB 쓰기 / 외부 의존 — 어느 병목? |

**8. 보존 기간 안에 따라잡을 수 있는가를 왜 확인하나**

브로커(3번) 칸의 실패 형태에는 리더 장애·복제 미달과 **나란히** "보존 기간 만료로 소실"이 들어 있다.\
그래서 대응 열도 `replication.factor≥3`·`min.insync.replicas=2`·`unclean.leader.election=false`에서 끝나지 않고 **"보존 기간 vs 컨슈머 최대 지연"**을 함께 보라고 적는다.\
확인 질문 3번이 "노드 하나가 죽어도 데이터가 남는가"와 "컨슈머가 밀렸을 때 보존 기간 안에 따라잡을 수 있는가"를 **두 개로** 묻는 이유가 이것이다 — 복제 설정을 다 맞춰도 남는 실패 형태가 따로 있다.\
못 따라잡으면 브로커가 보존 기간이 지난 메시지를 지우고, 컨슈머는 그 메시지를 영영 받지 못한다 — 아무도 죽지 않았는데 소실이 일어난다.\
그래서 점검 방식은 값 하나를 보는 게 아니라 **비교**다 — 보존 기간과 컨슈머의 최대 지연을 나란히 놓고 후자가 전자 안에 들어오는지 본다.

**9. 같은 지식으로도 답이 반쪽이 되는 이유 — 한 문장**

**답의 폭을 정하는 것은 아는 양이 아니라 답을 시작할 때 잡은 범위이고, 범위를 좁게 잡으면 아는 것도 꺼내지 않은 채 끝나기 때문이다.**\
그래서 교정은 **지식 추가가 아니라 절차 추가**다 — 아는 걸 늘리는 게 아니라, 답하기 전에 범위를 되짚는 절차를 하나 끼워 넣는다.

**10. 이 습관이 값을 하는 질문의 종류**

**구간이 여럿인 질문 전부**다.\
파이프라인·신뢰성 질문이 원래의 자리이고, 일반화하면 성능·장애 대응·동시성·캐시·확장성처럼 **축을 세울 수 있는 큰 질문**이 전부 해당한다.\
공통 조건은 하나다 — 답이 여러 지점에 걸쳐 있는데 질문이 그중 어디를 가리키는지는 말하지 않는 질문.\
그런 질문에서 첫 문장을 범위 확정으로 시작하면 축이 입 밖으로 나오고, 그 순간 빠뜨린 칸이 스스로 보이며, 듣는 사람에게는 전체 구조를 안다는 신호가 된다.\
값을 하는 자리는 답하는 자리만이 아니다 — 내 시스템의 5칸 표를 직접 채워 점검할 때도 같은 절차가 그대로 쓰인다.\
그러니 연습의 목표는 지식이 아니라 **반사**다 — 첫 문장을 범위 확정으로 시작하는 것이 반사가 될 때까지.

## [Claude 추가]

> 아래는 원고에 없던 내용이다. 복습 시 본문(원고 범위)과 섞어 인출하지 않는다.

- **6번의 「전/후」 귀속과 "왜 후자가 나은가".** 원고는 4번 칸의 실패를 "커밋 순서에 따른 유실/중복"이라고만 적고, 어느 순서가 유실이고 어느 순서가 중복인지는 쓰지 않는다. 실제 대응은 이렇다 — 처리 **전**에 커밋하면 처리 도중 크래시 시 그 메시지는 다시 오지 않아 **유실**이 되고, 처리 **후**에 커밋하면 크래시 시 다시 와서 **중복**이 된다. 후자가 나은 이유는 **중복은 멱등 소비(인박스)로 흡수할 수 있지만 유실은 되돌릴 수단이 없다**는 비대칭 때문이다. 원고가 4번 칸의 대응으로 멱등 소비를 든 것이 이 선택의 흔적이지만, 비대칭 자체를 원고가 문장으로 적지는 않는다.
