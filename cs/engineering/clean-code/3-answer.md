## 정답

### 1. (연결) SOLID와 CLEAN의 관계 — 왜 "수단"과 "상태"인가

- **SOLID = 수단**("어떻게 설계할 것인가"), **CLEAN = 상태**("그 결과물이 어떤 성질을 가져야 하는가").
- 비유하면 SOLID는 **만드는 법**, CLEAN은 다 만든 물건의 **품질 검사표**다.
- 그래서 관계는 인과다 — SOLID 원칙을 지켜 설계하면 그 결과물이 CLEAN한 상태(응집·느슨한 결합·캡슐화·단정적·비중복)에 도달한다. 하나는 과정, 하나는 도착점이다.

### 2. (충돌) 서로 긴장 관계인 쌍과 각 판정 기준

원고의 「긴장 관계」 표 그대로 네 쌍이다.

| 긴장 쌍 | 왜 부딪히나 | 판정 기준 |
|---|---|---|
| **N ↔ L** | 중복을 없애려 공유하면 결합이 생긴다 | 서비스 경계를 넘는 공유는 신중히. **경계 안에서는 N 우선** |
| **C ↔ N** | 응집을 위해 함께 두면 다른 곳과 중복될 수 있다 | **함께 변하는 것이 더 중요 → C 우선** |
| **E ↔ 편의성** | 캡슐화하면 매번 메서드를 만들어야 한다 | **불변식이 있으면 E 우선**, 없으면 완화 가능 |
| **A ↔ 계층 분리** | 도메인에 로직을 넣으려는데 인프라가 필요하다 | 도메인 서비스 또는 애플리케이션 계층으로 뺀다 |

### 3. (판단) `Money` 복붙 — N 위반인가, L을 위한 정당한 중복인가

- **둘 다 될 수 있다.** 판정은 다음 재료로 한다.
  1. **복제본들이 실제로 같은가?** 정밀도·통화·반올림 규칙이 서비스마다 달라야 할 이유가 있는가.
  2. **서비스 경계를 넘는가?** 같은 경계(모듈) 안이면 같은 지식의 중복 → **N 위반**, 공유(`Money`를 한 곳으로)로 해소. 서비스 경계를 넘으면 독립 배포를 지키기 위한 **L의 정당한 중복**일 수 있다.
  3. **공유 라이브러리 배포 비용** — 버전 올릴 때마다 여러 서비스를 반영해야 하는 비용이 얼마인가.
- 이 질문의 답이 곧 **ADR**(아키텍처 결정 기록)이다. 트레이드오프: 공유하면 N은 지키나 두 서비스가 같은 라이브러리 버전에 묶이고, 복제하면 L은 지키나 정의가 어긋날 위험을 감수한다.

### 4. (경계) Assertive(단정적) vs SRP(단일 책임)

- **SRP는 책임의 *개수* — 한 클래스는 한 책임만 진다.**
- **Assertive는 책임의 *위치* — 데이터에 대한 판단을 그 데이터를 가진 객체 *안*에 두느냐, 남이 데이터를 꺼내가 *밖*에서 판단하느냐.**
- 즉 SRP는 "이 클래스가 몇 가지 일을 하나"를, Assertive는 "판단이 데이터 옆에 붙어 있나(Tell) 아니면 떨어져 있나(Ask)"를 본다. Assertive의 실천 원칙이 "묻지 말고 시켜라"다.
- *(SRP의 정의 자체는 이 주제의 2-summary가 아니라 형제 주제 `solid-principles`·일반 지식에 근거 — 여기선 질문 힌트(개수 vs 위치)에 맞춰 대비했다.)*

### 5. (판단) 캡슐화가 잘 된 코드는 테스트가 쉬운가

- **쉽다(그리고 더 견고하다).** "내부 상태를 확인할 수 없어 어렵다"는 착각이다.
- 이유: 캡슐화된 객체는 **의미 있는 조작(공개 행위)만 검증하면 된다.** 예로 `Account`의 내부 `balance`·`holdAmount`를 몰라도, `hold()`를 호출한 뒤 `availableBalance()`가 기대대로 나오는지와 초과 점유 시 예외가 나는지로 불변식("가용잔액을 넘겨 점유할 수 없다")을 검증할 수 있다.
- 게다가 내부 표현이 바뀌어도(저장 방식 변경) 공개 행위 계약이 같으면 **테스트가 안 깨진다.** 반대로 필드를 다 노출한 코드는 테스트가 내부 표현에 묶여 리팩토링마다 깨진다. (원고의 감지법 "한 메서드 테스트에 관계없는 것까지 준비해야 하면 응집도가 낮다"와도 통한다.)

### 6. (경계) CLEAN은 서비스 레벨까지 올라가는가

- **올라간다.** 각 속성이 그대로 한 단계 위로 대응된다.
  - **C 응집도 → 바운디드 컨텍스트**: "이 둘은 함께 변하는가?"가 서비스를 나눌 근거.
  - **L 결합도 → 서비스 간 통신**: 동기 호출(HTTP/Feign)은 시간적 결합(상대가 죽으면 나도 멈춤), 이벤트로 바꾸면 결합↓·결과적 일관성 감수.
  - **E 캡슐화 → API 경계**: 내부 저장·표현을 API 밖으로 새지 않게.
  - **N 비중복 / A 단정적**도 서비스 경계에서 나타난다(예: `Money` 복제 판단, 판단을 소유 서비스 안에 둘지).
- CLEAN은 클래스 속성이자 아키텍처 속성이다.

### 7. (왜) setter는 대체로, getter는 경우에 따라 캡슐화를 깬다

- **차이를 만드는 것은 "읽기냐 쓰기냐"다.**
- **setter(쓰기)**: 객체가 검증할 틈 없이 상태를 갈아끼운다 → 객체가 **불변식을 지킬 기회를 잃는다.** 그래서 대체로 깬다. (불변 객체 `record`/`final`로 만들면 setter 문제 자체가 사라진다.)
- **getter(읽기)**: 값을 돌려줄 뿐이라 그 자체로 불변식을 깨진 않는다. 그러나 **가변 객체(내부 컬렉션 등)를 그대로 반환**하면 깨진다 — 밖에서 `getSteps().clear()`처럼 내부를 직접 바꿀 수 있다. 방어적 복사(`List.copyOf`)나 불변 뷰(`unmodifiableList`)로 막는다.

### 8. (경계) 진짜 중복 vs 우연한 중복 — 한 문장 판정과 위험

- **판정 기준(한 문장): "이 둘은 항상 함께 바뀌는가?"** 함께 바뀌면 같은 지식의 **진짜 중복**, 따로 바뀌면 **우연한 중복**이다. DRY는 "코드"가 아니라 "지식"의 중복을 말한다.
- **잘못 합치면 왜 더 위험한가**: 우연히 값이 같을 뿐인 둘(카드 수수료 2.5% / 정산 수수료 2.5%)을 합치면, 카드 수수료가 3%로 오를 때 정산 수수료가 **딸려 바뀐다.** 원래 독립이어야 할 두 지식이 결합되어, 한쪽을 고치면 다른 쪽이 조용히 망가지는 버그가 생긴다.

### 9. (왜) 플래그 인자가 "두 가지 일을 한다"는 자백인 이유와 수정

- `processPayment(payment, isRefund, skipValidation)`처럼 boolean을 받는다는 것은 내부에 `if (isRefund) { … } else { … }` 분기가 있다는 뜻이다. 즉 **한 메서드가 플래그에 따라 서로 다른 두 동작을 담고 있다** — 그것이 자백이다. 호출부 `processPayment(payment, true, false)`도 읽을 수 없다(제어 결합).
- **수정**: 동작마다 이름을 준다 — `postPayment(payment)` / `refundPayment(payment)`. 호출부가 스스로 설명되고, 결합이 제어 결합에서 데이터 결합으로 내려간다.

### 10. (예측) 모았더니 중복이 생겼다 — C와 N 중 무엇을 우선하나

- **C(응집)를 우선한다.**
- 이유: 판정 기준이 "**함께 변하는 것이 더 중요**"이기 때문이다. 함께 변하는 것들을 한곳에 모아 두면(C), 변경이 한 자리에서 일어나 실수가 준다. 그 대가로 다른 곳과 겉모양이 겹치더라도, 그 겹침이 "따로 변할" 성질(우연한 중복)이면 합치지 않는 편이 오히려 안전하다. N을 지키자고 함께 변하는 것을 억지로 떼면 응집이 무너진다.

### 11. (경계) 빈약한 도메인 모델은 항상 나쁜가

- **아니다.** 합리적인 경우 셋:
  1. **CRUD만 하는 단순 영역**(설정값 관리 등) — 규칙이 없는데 억지로 만들 필요 없다.
  2. **조회 전용 모델(Read Model)** — CQRS에서 조회 측은 데이터 그 자체가 목적이다.
  3. **DTO·계약 객체** — 경계를 넘나드는 운반체는 원래 데이터 가방이 맞다.
- **관통하는 판단 기준 하나: "지켜야 할 불변식이 있는가?"** 있으면 규칙을 객체 안에 넣고, 없으면 억지로 행위를 만들지 않는다.

### 12. (예측) 결합을 줄였더니 무엇을 잃었나 — 손해 판정 기준

- **잃은 것**: 흐름의 **가시성**이다. 이벤트 버스를 끼우면 직접 호출이 사라져 흐름을 따라갈 수 없고, 인터페이스를 남발하면 구현체가 하나뿐인 인터페이스가 수십 개 생기며, 서비스를 잘게 쪼개면 네트워크 홉이 늘어 디버깅이 불가능해진다.
- **손해 판정 기준: "결합을 줄인 대가로 무엇을 잃었는가?"** — **흐름의 가시성을 잃었다면 대개 손해다.** 결합 제거 자체가 목적이 아니라, 얻은 것(독립 변경·배포)이 잃은 것(추적 가능성)보다 큰지가 기준이다.

### 13. (연결) 응집도·결합도 7등급 사다리 — 최악·목표·사이 순서

**응집도(7등급, 아래로 갈수록 좋음)** — 최악 = **우연적**, 목표 = **기능적** ★

```text
우연적 → 논리적 → 시간적 → 절차적 → 통신적 → 순차적 → 기능적 ★
(나쁨)                                              (목표)
```

**결합도(아래로 갈수록 좋음)** — 최악 = **내용 결합**, 목표 = **데이터 결합** ★

```text
내용 → 공통 → 외부 → 제어 → 스탬프 → 데이터 ★
(나쁨)                            (목표)
```

- 응집도는 우연적(그냥 모임)에서 기능적(하나의 잘 정의된 작업)으로, 결합도는 내용 결합(남의 내부를 직접 건드림)에서 데이터 결합(필요한 값만 인자로)으로 내려가는 것이 목표다. *(원고 사다리는 응집도 7단계·결합도 6단계로 제시된다 — 결합도는 위 6등급이 정본이다.)*
