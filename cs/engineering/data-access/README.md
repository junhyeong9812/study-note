# 데이터 접근 — JPA와 Spring Data JDBC (data-access) — 컬렉션 인덱스

> 이 컬렉션은 **관계형 DB에 접근하는 두 도구(JPA·Spring Data JDBC)를 "무엇을 감추고 무엇을 드러내는가"로 나란히 이해하고, 내 도메인의 쓰기 경로에 맞는 쪽을 고를 수 있게** 하는 세트다.\
> 출처: `jun-bank/docs/study/tech/data-access/`의 `jpa.md` · `spring-data-jdbc.md` · `comparison.md` · 이관일 2026-09-16.\
> 서로 참조하며 얽혀 있던 세 문서를 **하나의 컬렉션**으로 옮겼다. 본문은 **원고**를 고쳐 쓴 것이고(문체·순서 유지, 특정 프로젝트 고유 상황을 일반 상황으로), 「한눈에」의 비유·그림과 각 문서 맨 끝 `[Claude 추가]`는 **Claude가 원고 이해를 돕기 위해 보탠 것**이다.\
> 원고의 `[실무 의견]`·`[불확실]` 표시는 **원고 저자 본인의 표식**이라 그대로 두었다.

## 이 컬렉션에 무엇이 있나

세 문서는 "같은 문제(객체와 테이블의 불일치)를 정반대로 푼 두 도구 + 그 둘의 축별 비교"다.

| 문서 | 다루는 것 | 한 줄 |
|---|---|---|
| [jpa.md](./jpa.md) | JPA·Hibernate — **영속성 컨텍스트**라는 하나의 결정 | SQL을 안 쓰게 해 주는 대신, "언제 무슨 SQL이 나가는가"를 감춘다 |
| [spring-data-jdbc.md](./spring-data-jdbc.md) | Spring Data JDBC — **애그리게이트 = 저장 단위** | 감춘 것을 전부 도로 드러낸다. 코드를 읽으면 SQL이 보인다 |
| [comparison.md](./comparison.md) | 두 도구의 **다섯 축 비교 + 선택 기준** | 우열이 아니라 "쓰기가 그래프 저장이냐 상태 전이냐"가 가른다 |

> **한 문장으로**: JPA는 그래프를 통째로 다루려고 SQL을 감추고, Spring Data JDBC는 그 감춤이 위험해지는 도메인(조건부 전이·잠금·대량 조회)을 위해 SQL을 드러낸다.

## 어떻게 읽나

1. **[jpa.md](./jpa.md)를 먼저 읽는다.** Spring Data JDBC의 설계는 "JPA의 무엇을 왜 뺐는가"이므로, JPA를 알아야 반대편이 읽힌다.
2. **[spring-data-jdbc.md](./spring-data-jdbc.md)로 넘어간다.** 같은 문제를 정반대 방향에서 푼 도구다.
3. **[comparison.md](./comparison.md)에서 축별로 겹쳐 본다.** 앞 두 문서의 개념이 실제 선택에서 어떻게 부딪히는지, 어떤 도메인이 어느 쪽으로 기우는지를 본다.
4. **문서 사이를 오간다.** 각 문서 「관련 자료」의 상대경로 링크(`./jpa.md` 등)로 교차점을 따라간다.

각 문서는 「한눈에 → 이 개념이 답하려는 질문 → 전체 흐름 → 개념 절들 → 핵심 문장 → 관련 자료 → 용어 풀이 → [Claude 추가]」 순서로 같은 골격이다.\
두 번째 문서부터는 어디에 뭐가 있는지 안 찾아도 된다.

## 컬렉션을 관통하는 한 질문

세 문서 전체가 딱 하나의 질문으로 수렴한다.

```text
내 도메인의 쓰기는 어느 쪽에 가까운가?
        │
        ├── "객체 그래프를 고쳐 통째로 저장한다"
        │        예) 폼을 열어 고치고 저장 · 사내 업무 시스템 · CMS · 설정 관리
        │        → 매핑이 어렵다  → JPA가 그 80~90%를 가져간다
        │
        └── "조건이 참일 때만 이 행을 이렇게 바꾼다"
                 예) 원장 기입 · 재고 차감 · 좌석 예약 · 잡 스케줄러 리스
                 → 동시성·잠금·실행 시점이 어렵다  → JPA가 가져가 줄 게 없다
```

- 왼쪽 도메인에서 "감춰진 SQL"은 비용이 아니라 **목적**이다 — 지우고 싶었던 코드를 지워 준다.
- 오른쪽 도메인에서 "감춰진 SQL"은 곧 **검증 불가능한 구간**이다 — 언제 어떤 문장이 나가는지가 불변식의 일부이기 때문이다.
- 그래서 유용한 판정 질문은 하나다: **"이 시스템의 어려운 부분이 매핑인가, 동시성인가?"**

## 관련 자료

- **결정의 정본은 이 노트가 아니다.** 실제 프로젝트에서 "우리는 왜 이 도구를 골랐나"는 아키텍처 결정 기록(ADR)에 남기고, 학습 노트는 그 결정을 재판정하지 않는다. 이 컬렉션은 두 도구의 개념과 선택 기준을 익히는 용도다.

  > **ADR(Architecture Decision Record)** — "왜 이렇게 결정했는가"를 남기는 짧은 문서.\
  > 예: "쓰기는 Spring Data JDBC로 간다 — 쓰기 경로가 조건부 상태 전이라 SQL이 코드에 드러나야 하기 때문. 대가: 조회 매핑을 직접 쓴다."

- 세 문서가 인용한 **원 출처**(Fowler의 EAA 패턴·OrmHate, Jakarta Persistence 스펙, Hibernate 문서, Schauder의 Spring Data JDBC 블로그, Vernon의 애그리게이트 설계, Vlad Mihalcea의 성능 글)는 각 문서의 「관련 자료」에 모여 있다. JPA를 별도로 공부할 때의 읽기 순서는 [comparison.md](./comparison.md)의 마지막 절에 있다.

## 이관 이력

- **세 문서를 서로의 상대경로로 다시 이었다.** 원고에서 `jpa.md`·`spring-data-jdbc.md`·`comparison.md`가 서로를 가리키던 링크를 컬렉션 내 상대경로(`./jpa.md` 등)로 유지했다.
- **특정 프로젝트 고유명사를 일반화했다.** 원고 곳곳의 결정 문서 참조(ADR 번호·결정 항목 번호·특정 애그리게이트 참조), 도메인 고유 엔티티 이름, 특정 저장소 경로를 "누구나 겪는 형태"로 다시 썼다 — 예: 특정 배치 엔티티의 리스 획득 예제는 일반 「잡 리스(job lease)」 예제로 바꿨다. 지운 게 아니라 일반 상황으로 옮겼다.
- **원고의 결정 재판정 절은 일반 지식으로 흡수했다.** "우리 프로젝트는 왜 이 도구인가" 절은 "어떤 도메인이 어느 쪽으로 기우는가"라는 일반 판단으로 옮겼고, 결정 정본이 ADR이라는 점만 위 「관련 자료」에 일반적으로 남겼다.
- **외부 URL은 원고 그대로 두었다.** 실존하는 공개 문서·스펙·블로그 링크라 죽은 링크가 아니다.
