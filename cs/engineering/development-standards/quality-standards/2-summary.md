## 1. 이 기준이 답하려는 질문

"품질이 좋다"는 말은 사람마다 다른 것을 가리킨다 — 빠르다, 안 죽는다, 고치기 쉽다, 쓰기 편하다.
ISO/IEC 25010은 이 말들을 **9개 특성(characteristics)과 하위 특성(sub-characteristics)의 어휘**로 고정한다.
표준이 주는 것은 측정값이 아니라 **분류 체계**다: 요구사항·테스트·리뷰에서 "지금 어느 특성을 이야기하는가"를 지목할 수 있게 된다.
(측정 방법은 시리즈의 다른 문서 — 25023 제품 품질 측정, 25040 평가 프로세스 — 가 맡는다.)

## 2. 제품 품질 모델 — 9개 특성

| # | 특성 | 묻는 질문 |
|---|------|-----------|
| 1 | **Functional Suitability** (기능 적합성) | 요구된 기능을 완전하고 정확하게 제공하는가 |
| 2 | **Performance Efficiency** (성능 효율성) | 시간 요구(응답·처리율)와 자원 사용량 요구를 만족하는가 |
| 3 | **Compatibility** (호환성) | 다른 시스템과 공존·상호운용되는가 |
| 4 | **Interaction Capability** (상호작용 능력, 구 Usability) | 사용자가 배우고·조작하고·실수로부터 보호받는가 |
| 5 | **Reliability** (신뢰성) | 정해진 조건에서 기능을 유지하는가 |
| 6 | **Security** (보안성) | 정보와 데이터가 권한대로만 접근되는가 |
| 7 | **Maintainability** (유지보수성) | 고치고·분석하고·시험하기 쉬운가 |
| 8 | **Flexibility** (유연성, 구 Portability) | 다른 환경·요구·부하에 적응하는가 |
| 9 | **Safety** (안전성, 2023 신설) | 사람·재산·환경에 위해를 끼칠 위험을 통제하는가 |

## 3. 특성별 상세 — 하위 특성 체크포인트와 예시

> 읽는 법: 특성마다 ①정의 ②하위 특성(들여쓴 항목 = 설계·리뷰 때 스스로 물을 **체크포인트**) ③좋음/나쁨이 대비되는 예시 2개(쉬운 예 + 실무 예).

### 1. Functional Suitability (기능 적합성)

요구된 기능을 **완전하고, 정확하고, 목적에 맞는 방식으로** 제공하는가를 잰다.
"돌아간다"와 "요구를 충족한다"는 다르다 — 이 특성은 명시·암묵 요구사항 대비 커버리지와 결과의 옳음을 본다.
나머지 8개 특성이 전부 좋아도 이것이 나쁘면 "잘 만든 엉뚱한 제품"이라서 별도 특성이다. → 요구사항 커버리지, 승인 테스트가 검증 수단.

- **completeness** — 명시된 목표·과업을 기능이 빠짐없이 커버하는가
  - 요구사항 목록의 각 항목에 대응하는 기능이 실제로 존재하는가?
  - 예외 케이스(빈 입력·경계값·취소 경로)도 요구의 일부로 다뤘는가?
- **correctness** — 필요한 정밀도로 맞는 결과를 내는가
  - 대표 입력만이 아니라 경계 입력에서도 결과가 명세와 일치하는가?
  - "맞다"의 기준(정밀도·반올림·타임존)이 명세에 적혀 있는가?
- **appropriateness** — 사용자의 목적 달성을 촉진하는 방식인가
  - 목적을 이루는 데 불필요한 단계를 강요하지 않는가?
  - 기능이 있긴 한데 "돌아가는 길"이라 실제로는 안 쓰이지 않는가?

**예시**
- 쉬운 예 (계산기): 사칙연산 요구에 나눗셈이 빠짐 → completeness 결함. 나눗셈은 있는데 1/3의 소수 자릿수가 요구 정밀도에 못 미침 → correctness 결함. 퍼센트 계산을 하려면 매번 수동으로 ×0.01을 눌러야 함 → appropriateness 결함.
- 실무 예 (전자상거래 주문): "주문 취소" 요구에 부분 취소가 빠져 CS가 수작업 처리 → completeness. 할인 적용 순서가 명세와 달라 최종 금액이 어긋남 → correctness. 환불 기능은 있지만 관리자 화면 다섯 단계를 거쳐야 함 → appropriateness.

### 2. Performance Efficiency (성능 효율성)

정해진 조건에서 **시간 요구(응답·처리율)와 자원 사용량 요구**를 만족하는가.
시간과 자원은 하나의 "자원 대비 효율" 지표가 아니라 **독립적으로 평가되는 하위 특성**이다 — 같은 응답시간이라도 서버를 10배 쓰면 time behaviour는 좋지만 resource utilization은 나쁘다.
→ p99 지연, 부하 테스트 한계치가 대표 지표.

- **time behaviour** — 응답 시간·처리 시간·처리율이 요구를 만족하는가
  - 목표 수치(p50/p99 등)가 정의돼 있고 실제로 측정하고 있는가?
  - 평균만이 아니라 꼬리 지연(최악 근처)도 보고 있는가?
- **resource utilization** — CPU·메모리·네트워크 등 자원 사용량이 적절한가
  - 부하 대비 자원 사용이 비례하는가, 어느 지점에서 폭증하는가?
  - 유휴 상태에서 불필요하게 자원을 점유하고 있지 않은가?
- **capacity** — 최대 한계(동시 사용자·데이터량·트랜잭션량)가 요구를 만족하는가
  - 시스템의 한계 용량을 추측이 아니라 실측으로 알고 있는가?
  - 예상 성장치(예: 1년 뒤 데이터량)에서도 한계 안에 있는가?

**예시**
- 쉬운 예 (TODO 앱): 항목이 1만 개가 되자 목록 열기에 수 초 — 매번 전체 목록을 다시 그림 → time behaviour·resource utilization 나쁨. 화면에 보이는 부분만 렌더링하면 항목 수와 무관하게 즉시 열림 → 좋음.
- 실무 예 (전자상거래 검색): 평상시엔 빠르지만 세일 트래픽에서 한계 동시 접속을 넘겨 타임아웃 연쇄 → capacity 미달. 사전 부하 테스트로 한계를 알고 캐시·스케일아웃으로 대비 → capacity 관리가 된 상태.

### 3. Compatibility (호환성)

같은 환경·자원을 **공유하면서 서로 방해하지 않고**(공존), 다른 시스템과 **정보를 교환하고 그 정보를 쓸 수 있는가**(상호운용).
"내 시스템 혼자 잘 도는가"가 아니라 "이웃과 상대가 있을 때도 잘 도는가"를 재는 별도 축이다.

- **co-existence** — 자원을 공유하는 다른 제품에 해로운 영향 없이 공존하는가
  - 포트·파일·락·CPU 같은 공유 자원을 독점하거나 충돌시키지 않는가?
  - 내가 폭주하거나 죽을 때 같은 호스트의 이웃 프로세스에 피해가 가는가?
- **interoperability** — 다른 시스템과 정보를 교환하고 상호 사용할 수 있는가
  - 교환 형식(스키마·인코딩·단위·타임존)이 문서화되고 양쪽이 같은 해석을 하는가?
  - 상대가 다른 버전이어도(필드 추가 등) 깨지지 않게 설계했는가?

**예시**
- 쉬운 예 (데스크톱 유틸): 설치하면 8080 포트를 고정 점유해 다른 개발 서버가 못 뜸 → co-existence 나쁨. 계산 결과를 CSV로 내보내 스프레드시트가 바로 읽음 → interoperability 좋음.
- 실무 예 (뱅킹 연동): 이체 API가 금액을 원 단위/센트 단위 혼용 + 문자열/숫자 혼용으로 보내 파트너마다 해석이 갈림 → interoperability 결함(계약 부재). 합의된 메시지 규격과 스키마 버전 관리 → 좋음.

### 4. Interaction Capability (상호작용 능력, 구 Usability)

사용자가 시스템을 **알아보고, 배우고, 조작하고, 실수로부터 보호받으며** 목적을 이루게 하는가.
2023판이 Usability에서 개명하며 하위 어휘도 재편했다 — 2011의 accessibility는 **inclusivity**로 이어지고, user interface aesthetics는 **user engagement**로 바뀌었으며, **user assistance·self-descriptiveness**가 신규 추가. "쓰기 편함"을 넘어 **누구나, 별도 설명 없이도** 쓸 수 있는가까지 어휘가 넓어졌다.
→ 폼 검증 메시지, 실수 되돌리기, 접근성으로 코드에 드러난다.

- **appropriateness recognizability** — 내 요구에 맞는 제품인지 알아볼 수 있는가
  - 첫 화면만 보고 "이걸로 무엇을 할 수 있는지" 드러나는가?
- **learnability** — 배우는 데 드는 노력이 적은가
  - 매뉴얼 없이 핵심 과업을 해낼 수 있는가?
  - 화면의 용어가 사용자의 언어인가, 내부 구현의 언어인가?
- **operability** — 조작·제어하기 쉬운가
  - 자주 하는 작업의 단계 수가 최소인가?
- **user error protection** — 사용자 실수를 예방하고 복구하게 하는가
  - 파괴적 작업 앞에 확인 또는 되돌리기(undo)가 있는가?
  - 잘못된 입력을 제출 시점이 아니라 입력 시점에 알려주는가?
- **user engagement** (2023, 구 user interface aesthetics 대체) — 만족스럽고 계속 쓰고 싶은 상호작용인가
  - 진행 상황·완료가 사용자에게 보상감 있게 전달되는가?
- **inclusivity** (2023, 구 accessibility에서 분리) — 다양한 배경·능력의 사용자가 쓸 수 있는가
  - 스크린리더·키보드만으로도 핵심 과업이 가능한가?
  - 색각·언어·연령 차이가 사용을 막지 않는가?
- **user assistance** (2023 신규) — 도움이 필요한 순간 제품이 도움을 주는가
  - 막히는 지점에 문맥에 맞는 안내가 나오는가?
- **self-descriptiveness** (2023 추가) — 제품 스스로 상태·사용법을 설명하는가
  - 지금 무슨 상태인지(로딩·실패·완료) 화면만 보고 알 수 있는가?

**예시**
- 쉬운 예 (TODO 앱): 삭제 버튼을 누르면 확인도 되돌리기도 없이 영구 삭제 → user error protection 나쁨. 삭제 직후 몇 초간 "실행 취소" 토스트 제공 → 좋음.
- 실무 예 (전자상거래 결제): 카드번호 오류를 결제 버튼을 누른 뒤에야, 그것도 폼 전체 초기화와 함께 알려줌 → error protection·self-descriptiveness 나쁨. 필드별 즉시 검증 + 원인이 보이는 오류 문구 + 키보드·스크린리더 지원 → inclusivity까지 좋음.

### 5. Reliability (신뢰성)

정해진 조건·기간 동안 **기능을 계속 수행**하는가.
성능과 별개 축이다 — 빠르지만 자주 죽는 시스템, 느리지만 절대 안 죽는 시스템이 둘 다 존재한다.
→ 에러율, 재시도·페일오버, 복구 시간으로 드러난다.

- **faultlessness** (2023, 구 maturity) — 정상 운영에서 결함 없이 기능을 수행하는가
  - 에러율·크래시 빈도를 측정하고 있는가?
  - 알려진 결함 목록이 관리되고 있는가, 산발적으로 잊히는가?
- **availability** — 필요한 시점에 접근·사용 가능한가
  - 가동률 목표가 정의돼 있고 다운타임을 집계하는가?
  - 배포·점검이 사용 가능 시간을 얼마나 깎는지 아는가?
- **fault tolerance** — 결함·장애가 있어도 의도대로 동작하는가
  - 의존 대상(DB·외부 API)이 죽었을 때의 동작을 설계했는가, 방치했는가?
  - 부분 실패가 전체 실패로 번지는 경로는 없는가?
- **recoverability** — 장애 후 데이터를 복구하고 원하는 상태를 재확립할 수 있는가
  - 백업이 있는가, 그리고 복구를 실제로 연습해 봤는가?
  - 재시작하면 중단 지점부터 이어지는가, 처음부터 다시인가?

**예시**
- 쉬운 예 (TODO 앱): 저장 도중 강제 종료되면 파일이 반쯤 깨져 다음 실행에 열리지 않음 → recoverability 나쁨. 임시 파일에 쓴 뒤 원자적으로 교체하면 어느 시점에 죽어도 직전 상태는 살아 있음 → 좋음.
- 실무 예 (뱅킹 홈): 추천 배너 서비스 하나가 죽자 메인 페이지 전체가 오류 → fault tolerance 나쁨(비핵심 실패의 전파). 추천 영역만 비우고 조회·이체는 정상 제공, 장애 중 미처리 건은 재처리 큐로 복구 → fault tolerance·recoverability 좋음.

### 6. Security (보안성)

정보와 데이터가 **권한 수준대로만** 접근·변경되도록 보호하는가.
Reliability가 "우연한 고장"을 다룬다면 Security는 **의도적 위협** 아래의 품질이라 별도 특성이다.
2023판은 resistance를 추가 — 공격이 진행되는 동안에도 버티는 능력이 어휘에 들어왔다. → 구체 실행은 보안 축(security-standards)에서.

- **confidentiality** — 권한 있는 주체만 데이터에 접근하는가
  - 이 데이터를 봐야 하는 사람이 누구인지 정의했고, 그 외엔 정말 못 보는가?
  - 저장·전송 구간에서 보호(암호화)되는가?
- **integrity** — 데이터·시스템이 무단 변경으로부터 보호되는가
  - 클라이언트가 보낸 값(가격·수량·권한)을 서버가 다시 검증하는가?
- **non-repudiation** — 행위·이벤트가 일어났음을 나중에 부인할 수 없게 증명 가능한가
  - 중요 거래에 부인 방지 증거(서명·불변 기록)가 남는가?
- **accountability** — 행위를 행위 주체까지 추적할 수 있는가
  - 중요 작업에 "누가·언제·무엇을" 감사 로그가 남는가?
  - 공용 계정 때문에 주체 추적이 끊기는 곳은 없는가?
- **authenticity** — 주체·자원의 신원이 주장하는 그대로임을 증명할 수 있는가
  - 상대(사용자·서버·메시지)가 진짜인지 검증하는 절차가 있는가?
- **resistance** (2023 추가) — 공격이 진행되는 동안에도 견디는가
  - 무차별 대입·과도 요청 같은 공격을 제한(rate limit 등)하는가?

**예시**
- 쉬운 예 (TODO 앱 공유 기능): URL의 사용자 id만 바꾸면 남의 목록이 보임 → confidentiality 붕괴(인가 검증 부재). 요청마다 소유자 검증 → 좋음.
- 실무 예 (전자상거래 결제): 결제 요청의 금액을 클라이언트 값 그대로 믿어 금액 조작이 가능 → integrity 결함. 서버가 장바구니 기준으로 금액을 재계산하고 관리자 행위는 감사 로그로 추적 → integrity·accountability 좋음.

### 7. Maintainability (유지보수성)

**고치고, 분석하고, 시험하기** 쉬운가 — 개발자가 사용자인 품질.
실행 시점이 아니라 변경 시점에 드러나므로 별도 특성이다. 결합도·응집도·SOLID 논의가 전부 이 특성 아래에 산다.
→ 변경 diff의 확산 정도, 테스트 용이성으로 드러난다.

- **modularity** — 한 부분의 변경이 다른 부분에 미치는 영향이 최소인가
  - 이 변경의 diff가 예상한 모듈 안에 머무는가, 여러 곳으로 번지는가?
- **reusability** — 자산을 다른 곳에서 재사용할 수 있는가
  - 이 로직을 다른 화면·서비스에서 쓰려면 복사 말고 방법이 있는가?
- **analysability** — 결함의 원인·변경의 영향 지점을 진단하기 쉬운가
  - 장애 로그만으로 어느 모듈이 문제인지 좁힐 수 있는가?
  - 처음 보는 사람이 코드만 읽고 의도를 알 수 있는가?
- **modifiability** — 새 결함을 만들지 않고 효과적으로 수정할 수 있는가
  - 같은 개념이 여러 곳에 중복돼 있어 한쪽만 고치게 될 위험은 없는가?
- **testability** — 테스트 기준을 세우고 수행하기 쉬운가
  - 이 로직을 DB·네트워크 없이 단위 테스트할 수 있는가?
  - 실패를 재현하는 테스트를 쉽게 쓸 수 있는 구조인가?

**예시**
- 쉬운 예 (계산기): 파싱·계산·화면 출력이 한 함수에 섞여 "연산자 하나 추가"에도 전체를 다시 읽어야 함 → modularity·analysability 나쁨. 파서/평가기/UI를 분리하면 평가기만 따로 단위 테스트 가능 → testability까지 좋음.
- 실무 예 (전자상거래): 배송비 규칙이 주문·정산·프로모션 세 곳에 복사돼 있어 정책 변경 때 한 곳을 빠뜨림 → modifiability 결함이 correctness 결함으로 전이. 규칙을 한 모듈로 모으면 변경 diff가 한 곳 → 좋음.

### 8. Flexibility (유연성, 구 Portability)

**다른 환경·요구·부하 변화에 적응**할 수 있는가.
2023판이 Portability(이식성)를 확장·개명하며 scalability를 편입 — "다른 하드웨어로 옮기는 능력"에서 "변화 일반(환경·부하)에 적응하는 능력"으로 넓어졌다.
→ 환경 이식, 수평 확장, 배포 용이성으로 드러난다.

- **adaptability** — 다른 환경(하드웨어·OS·클라우드)에 효과적으로 적응하는가
  - 환경 의존(경로·OS 전용 API·특정 리전)이 한 곳에 격리돼 있는가?
- **scalability** (2023 추가) — 부하 증감에 맞춰 용량을 조절할 수 있는가
  - 수평 확장을 막는 요소(서버 로컬 상태·로컬 파일 세션)가 있는가?
  - 늘릴 수만 있는가, 부하가 빠지면 줄일 수도 있는가?
- **installability** — 지정 환경에 설치·제거하기 쉬운가
  - 새 환경 셋업이 명령 몇 줄·문서 한 장으로 재현되는가?
- **replaceability** — 같은 목적의 다른 제품으로/을 대체할 수 있는가
  - 특정 벤더 전용 기능에 어디까지 묶여 있는지 파악하고 있는가?

**예시**
- 쉬운 예 (TODO 앱): 저장 경로가 `C:\Users\...`로 하드코딩돼 다른 OS에서 즉시 실패 → adaptability 나쁨. 표준 설정 디렉토리 API를 쓰면 OS가 바뀌어도 동작 → 좋음.
- 실무 예 (전자상거래): 로그인 세션을 웹서버 로컬 메모리에 둬서 서버를 늘리면 사용자 로그인이 풀림 → scalability 나쁨(상태가 확장을 막음). 세션을 외부 저장소로 빼 서버를 무상태로 만들면 서버 수 조절이 자유로움 → 좋음.

### 9. Safety (안전성, 2023 신설)

정해진 조건에서 **사람·재산·환경을 위험에 빠뜨리지 않는** 상태를 유지하는가.
Security와 다른 축이다 — Security는 악의적 접근으로부터 **정보**를 지키고, Safety는 시스템이 **물리 세계에 끼치는 위해**를 통제한다.
소프트웨어가 차량·의료·공장을 움직이는 시대가 이 특성을 25010에 편입시켰다. → 임베디드·차량·의료처럼 물리 세계와 닿는 시스템에서 핵심.

- **operational constraint** — 위험한 상황에서도 운영을 안전 제약 안에 가두는가
  - 물리적으로 허용되면 안 되는 명령(과속·과열·과투여)을 소프트웨어가 거부하는가?
- **risk identification** — 위해로 이어질 수 있는 위험을 식별하는가
  - 이 기능이 오작동하면 최악의 경우 무엇이 다치는지 목록화했는가?
- **fail safe** — 고장 시 자동으로 안전한 상태로 전환되는가
  - 센서·통신이 끊기면 정지(안전) 쪽으로 가는가, 마지막 값으로 계속 진행하는가?
- **hazard warning** — 위험을 통제할 시간 안에 경고하는가
  - 경고가 위험을 회피할 수 있는 시점에 나오는가, 사후에 나오는가?
- **safe integration** — 다른 구성요소와 결합해도 안전을 유지하는가
  - 개별로는 안전한 부품이 결합됐을 때 생기는 위험을 검토했는가?

**예시**
- 쉬운 예 (전기 주전자 제어 SW): 온도 센서 값이 안 읽히면 "마지막 값으로 계속 가열"이 아니라 가열 중단 → fail safe. 물 없이 켜면 경고 후 차단 → hazard warning.
- 실무 예 (의료 주입 펌프): 투여 속도 입력의 단위 실수(mg/mcg)가 치사량으로 이어질 수 있는데 아무 제한이 없음 → risk identification·operational constraint 실패. 임상 한계값을 벗어난 입력은 거부하고 이중 확인을 요구 → 좋음.

## 4. 사용 품질(Quality in use) — 25019로 분리

2011판에서는 "제품 품질"과 "사용 품질(실제 이용 맥락에서의 효과성·효율성·만족도·위험회피·맥락 포괄)"이 25010 한 문서에 있었다.
2023 개정에서 사용 품질 모델은 **ISO/IEC 25019:2023**으로 분리됐다. 25010은 제품 자체의 속성만 다룬다.

## 5. 2011 → 2023 변경 요약

```text
특성 수      8 → 9 (Safety 신설)
이름 변경    Usability → Interaction Capability / Portability → Flexibility
하위 추가    Security에 resistance · Flexibility에 scalability · Interaction Capability에 self-descriptiveness
하위 재편    accessibility → inclusivity · user interface aesthetics → user engagement · user assistance는 신규
하위 개명    Reliability의 maturity → faultlessness
문서 분리    Quality in use → 25019:2023
```

## 6. 현장에서 만나는 상황

- 요구사항에 "빨라야 한다"라고 쓰여 있으면 → Performance Efficiency의 어느 하위 특성인지(시간? 용량?), 수치 목표는 무엇인지 되묻는 도구로 쓴다.
- 코드 리뷰에서 "이건 품질이 나쁘다"는 지적을 → 특성 이름으로 번역하면(예: analysability 저하) 논쟁이 사실 대화가 된다.
- 비기능 요구사항(NFR) 체크리스트로: 9개 특성을 훑으며 "이 시스템에서 이 특성의 요구는 무엇이고 누가 검증하나"를 채운다.

## 핵심 문장

- 25010은 측정이 아니라 **어휘**를 주는 표준이다 — "품질"을 9개 특성으로 분해해 지목 가능하게 만든다.
- 2023판의 방향: 물리 세계와 닿는 소프트웨어(Safety), 공격 아래의 소프트웨어(resistance), 스케일하는 소프트웨어(scalability)를 어휘에 편입.
- 제품 품질(25010)과 사용 품질(25019)은 다른 축이다 — 제품이 완벽해도 쓰는 맥락에서 실패할 수 있다.

## [Claude 추가] 더 알면 좋은 것

> 복습 대상은 본문(이 파일 전체가 검토 대상이기도 하다 — 본문 자체가 Claude 작성). 이 절은 표준 밖의 확장 이야기.

### A. 특성끼리는 충돌한다 — 품질은 트레이드오프 선언

보안(입력 검증·암호화)은 성능을 깎고, 유연성(추상화 계층)은 분석 용이성을 깎을 수 있다. 25010의 실전 가치는 "다 잘하자"가 아니라 **어느 특성을 우선하고 어느 것을 희생하는지 명시적으로 선언**하게 만드는 데 있다 — 아키텍처 결정 기록(ADR)의 어휘로 쓰면 좋다.

### B. ISO 9126 → 25010 계보

25010의 전신은 ISO/IEC 9126(2001)이다. 9126의 6특성(기능성·신뢰성·사용성·효율성·유지보수성·이식성)이 2011년 8특성으로, 2023년 9특성으로 확장돼 왔다 — 시대가 소프트웨어에 요구하는 것이 어휘에 추가되는 역사다.

### C. 측정으로 내려가면 — SQuaRE의 이웃 문서

특성을 실제 숫자로 재려면 25022(사용 품질 측정)·25023(제품 품질 측정)의 메트릭, 25040(평가 프로세스)으로 내려간다. 실무에서는 표준 메트릭보다 SLO(운영 축)와 정적 분석 지표(유지보수성)로 근사하는 경우가 많다.
