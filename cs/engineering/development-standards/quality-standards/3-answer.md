# cs/development-standards/quality-standards — 품질 기준 (ISO/IEC 25010:2023) — 정답

> 복습 시 이 파일은 **최후에만** 연다. 정답을 봤으면 닫고 자기 말로 한 번 재산출한다.
> 작성 방식: **2-summary를 닫고 기억만으로** 쓴다 → 기준 문서(원전)로 검증 → 틀린 부분만 수정.
> ⚠️ 이 정답 목록은 Claude 초안이다(2026-08-24) — 본인 검토 후 이 줄 삭제.

## 정답

**1.** 어휘가 고정되면 "품질이 나쁘다" 같은 말이 사람마다 다른 것을 가리키는 문제가 사라진다 — 요구사항에서는 "빨라야 한다"를 어느 하위 특성(time behaviour? capacity?)·어떤 수치인지로 되물을 수 있고, 리뷰에서는 지적을 특성 이름(예: analysability 저하)으로 번역해 논쟁을 사실 대화로 바꿀 수 있다. 측정은 25010이 아니라 SQuaRE의 이웃 문서가 맡는다 — 25023(제품 품질 측정)·25022(사용 품질 측정)의 메트릭과 25040(평가 프로세스). 실무에서는 SLO·정적 분석 지표로 근사하는 경우가 많다.

**2.** "쓰기 편함(usability)"을 넘어 상호작용 전반 — 누구나(포용), 별도 설명 없이도(자기 설명) 쓸 수 있는가 — 를 담기 위해서다. 하위 어휘 재편: 2011의 accessibility는 **inclusivity**(다양한 배경·능력의 사용자가 쓸 수 있는가 — 접근성·언어·연령)로 이어졌고, **user assistance**(도움이 필요한 순간 제품이 도움을 주는가)와 **self-descriptiveness**(제품이 스스로 상태와 사용법을 설명하는가 — 화면만 보고 지금 무슨 상태인지 알 수 있는가)가 신규 추가됐다. user interface aesthetics는 **user engagement**로 바뀌었다.

**3.** Security는 악의적 접근으로부터 **정보·데이터**를 권한대로 지키는 축이고, Safety는 시스템이 **사람·재산·환경**(물리 세계)에 끼치는 위해를 통제하는 축이다. 예: 병원 주입 펌프가 통신 암호화·인증은 완벽(Security 좋음)한데, 센서 이상 시 마지막 값으로 계속 투여한다면(fail safe 부재) Safety는 나쁘다. 반대로 인터넷에 연결되지 않은 안전 정지 로직이 완벽한 기계라도 관리 콘솔이 무인증이면 Safety 좋음·Security 나쁨.

**4.** 예: 평상시 응답이 매우 빠른 서비스가 하루 몇 번씩 크래시로 재시작되고, 재시작 때 처리 중이던 작업을 잃는다 — time behaviour(성능)는 좋지만 faultlessness·availability·recoverability(신뢰성)는 나쁘다. 성능은 "돌아갈 때 얼마나 잘 도는가", 신뢰성은 "계속 돌아가는가·죽어도 회복하는가"라서 한 축의 점수로 다른 축을 예측할 수 없다 — 그래서 별도 특성이다.

**5.** 예(2-summary의 배송비 사례): 배송비 규칙이 세 곳에 복사돼 있음(modifiability 저하) → 정책 변경 때 한 곳을 빠뜨림 → 화면마다 배송비가 다르게 계산됨 = 맞는 결과를 못 내는 correctness 결함. 특성들은 분류 어휘로는 구분되지만 인과적으로 독립이 아니다 — 유지보수성 결함은 "다음 변경에서 기능 결함이 생길 확률"을 높이는 식으로 다른 특성으로 전이된다.

**6.** 충돌 예: ①보안(입력 검증·암호화·rate limit)은 성능(time behaviour)을 깎는다. ②유연성(추상화 계층·벤더 중립)은 분석 용이성(analysability)을 깎거나 성능을 깎는다. 25010이 해주는 것: 충돌을 특성 이름으로 **지목하고, 어느 것을 우선하고 어느 것을 희생하는지 명시적으로 선언**하게 만든다(ADR의 어휘). 해주지 않는 것: 어느 쪽을 골라야 하는지의 답 — 우선순위 판단은 시스템의 맥락(stakes)이 정한다.

**7.** SOLID는 **Maintainability** 아래에 산다 — 특히 modularity(변경 영향 국소화)·modifiability(안전한 수정)·testability(단위 검증 용이)·reusability에 걸친다. "결합도가 높다"는 지적의 번역: modularity 저하(한 부분의 변경이 다른 부분으로 번진다), 그 결과로 modifiability·testability 저하. 번역하면 "나쁘다"는 인상 논쟁이 "이 변경의 diff가 어디까지 번지는가"라는 검증 가능한 대화가 된다.
