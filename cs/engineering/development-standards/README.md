# development-standards — 개발 기준

개발자가 시스템을 만들 때 지켜야 할 기준을 네 축으로 나눠 공부한다.
각 축마다 "무엇을 기준 문서로 삼는가"를 먼저 고정하고, 그 문서를 읽고 따라 친 원고를 서머리로 정리한다.
파일 포맷·복습 순서·서머리 구조([Claude 추가] 절 분리)는 상위 [cs/README](../README.md)를 따른다.

## 네 축과 기준 문서

```text
development-standards/
├── quality-standards/       품질 기준   — ISO/IEC 25010:2023 (제품 품질 모델)
├── security-standards/      보안 기준   — OWASP Top 10 → OWASP ASVS → NIST SSDF (SP 800-218)
├── operational-standards/   운영 기준   — ISO/IEC 20000-1 (SMS) + Google SRE
└── legal-standards/         법률 기준   — 개인정보보호법 + 관련 법령(정보통신망법·신용정보법·위치정보법 등)
```

| 축 | 묻는 질문 | 기준 문서의 성격 |
|---|---|---|
| 품질 | 좋은 소프트웨어를 무엇으로 재는가 | 특성 모델(분류 체계) |
| 보안 | 무엇이 뚫리고, 무엇을 만족해야 하며, 과정은 어떻게 운영하는가 | 위험 목록 → 검증 요구사항 → 프로세스 관행 |
| 운영 | 서비스가 약속을 지키는지 어떻게 관리·측정하는가 | 관리 체계 요구사항 + 엔지니어링 실천 |
| 법률 | 법이 시스템에 요구하는 의무는 무엇인가 | 법령·고시(강제 규범) |

## 네 축의 관계

- 품질의 Security·Reliability 특성은 각각 보안·운영 축으로 내려가 구체화된다.
- 법률(안전성 확보 조치)은 보안 축의 구현 요구사항과 겹친다 — 같은 통제를 "법이 시켜서"와 "ASVS가 요구해서" 두 근거로 설명할 수 있어야 한다.
- 운영 축의 접속기록·백업·사고 대응은 법률 축의 보관·통지 의무와 맞물린다.

## 공부 순서 (권장)

1. 품질 — 전체 어휘를 잡는다(특성 이름이 나머지 축의 공통어).
2. 보안 — Top 10(인식) → ASVS(요구) → SSDF(과정).
3. 운영 — SRE(실천)로 감을 잡고 20000-1(체계)로 정리.
4. 법률 — 개인정보보호법 본문 → 안전성 확보조치 기준 고시 → 관련 법령.

## 주의

- 표준(ISO) 원문은 유료다 — 공개 개요·해설로 구조를 잡고, 조항 번호는 원문 확인 전까지 "(확인 필요)" 표시.
- 법령은 개정이 잦다 — 인용 시 시행일을 함께 적는다.
