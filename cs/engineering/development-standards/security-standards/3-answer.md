## 정답

1. **IDOR이 인가 실패인 이유.**
   인증(Authentication)은 "당신이 *누구인가*"를 확인하는 단계다 — `GET /api/orders/1337`을 보낸 사용자는 로그인에 성공한 정당한 사용자다. 즉 인증은 통과했다. 문제는 "이 로그인한 사용자가 *1337번 주문이라는 자원*에 접근할 권한이 있는가"를 서버가 확인하지 않은 것 — 이것이 인가(Authorization)다. IDOR은 신원 확인이 아니라 **자원별 권한 검사의 부재**이므로 A01(Broken Access Control)이다. 경계: 인증은 로그인 게이트에서 한 번, 인가는 자원에 닿을 때마다 서버 측에서.

2. **SSRF가 A01로 흡수된 논리.**
   SSRF는 "서버가 외부에서 받은 URL로 요청을 대신 보내주는" 기능을 악용해 서버 측 요청의 대상을 조작하는 공격이다 — 전형 예가 접근하면 안 되는 **내부 자원**(예: `169.254.169.254` 클라우드 메타데이터, 내부 서비스) 도달이고, 외부 대상도 가능하다. "서버라는 주체가 접근해선 안 될 대상에 접근한다"는 점에서 **접근 통제(어떤 주체가 어떤 자원에 접근 가능한가) 관점**과 겹치기 때문에 2025판은 별도 카테고리 대신 A01에 묶었다. 다만 SSRF 전체가 인가 실패로 환원되는 건 아니다 — URL 입력 검증·신뢰 경계·아웃바운드(서버 발신) 통제 실패도 핵심 원인이라, 방어에는 allowlist 같은 발신 통제가 함께 필요하다.

3. **A05 Injection vs A08 무결성(역직렬화)의 갈림.**
   둘 다 외부 입력이 실행으로 이어지지만 방어 지점이 다르다. A05는 입력이 **인터프리터(SQL 엔진·셸·브라우저)에 문자열로 섞여** 코드/데이터 경계가 무너지는 것 — 방어는 파라미터 바인딩·이스케이프처럼 "경계를 다시 세우기". A08 역직렬화는 신뢰할 수 없는 **직렬화된 객체를 복원**하는 과정 자체가 객체 생성 부수효과로 실행을 유발 — 방어는 애초에 "신뢰 못 할 데이터를 역직렬화하지 않기·타입 제한·무결성 서명 검증". 즉 A05는 *경계 세우기*, A08은 *무결성 검증/역직렬화 회피*에 초점. A08은 코드·데이터가 "변조되지 않았음을 검증"하는 문제군에 속한다.

4. **결제 fail-open의 악용과 fail-closed 전환.**
   코드가 인증 서버 타임아웃 시 예외를 잡고 그냥 승인으로 진행하면, "실패 = 허용"이 된다. 공격자는 인증 서버를 일부러 과부하·차단(DoS)시켜 타임아웃을 유도하고, 그 순간 결제/권한 검사를 통과시킬 수 있다 — 방어 로직을 죽이는 것이 곧 우회가 된다. **fail-closed**로 바꾸면 실패 시 기본이 거부이므로, 인증 서버가 죽으면 결제도 막힌다(가용성은 떨어지지만 안전). 인증·인가·결제 경로는 반드시 실패 시 거부여야 한다(A10 핵심).

5. **A01을 세 기준으로 추적.**
   - **Top 10** = *인식*: "IDOR·권한 상승·SSRF가 가장 중대한 위험군이다"라는 위험 목록. 출발점.
   - **ASVS** = *제품 기준*: "모든 자원 접근은 서버에서 권한 검증", "deny by default" 같은 V8 인가 챕터의 검증 가능한 요구사항. "우리 앱이 무엇을 만족해야 하는가".
   - **SSDF** = *과정 기준*: PW(위협 모델링에서 인가 경계 식별, 코드 리뷰 체크리스트) + RV(IDOR 신고 → 근본 원인 분석 → 같은 패턴 전수 점검). "개발 과정을 어떻게 운영하는가".
   층이 달라 대체 불가: Top 10만으로는 검증 문장이 안 되고, ASVS 요구사항이 있어도 그걸 지키게 하는 과정(SSDF)이 없으면 개인기에 의존한다.

6. **ASVS 레벨 선택 기준.**
   레벨은 **데이터 민감도·침해 시 손실·규제 요구**에 비례한다. L1은 민감 데이터가 없는 저위험 서비스의 최소선. 로그인·개인정보·결제가 있으면 흔한 공격만으론 부족하므로 대부분 **L2**를 목표로 한다 — 덜 흔한 공격·더 정교한 방어까지 요구. 은행 코어·의료처럼 침해가 회복 불가하고 규제가 고보증을 요구하면 심층 방어(defense-in-depth)까지 갖춘 **L3**. 즉 "얼마나 잃을 수 있고 얼마나 증명해야 하는가"가 레벨을 가른다.

7. **A02 상승과 가드레일.**
   Misconfiguration이 5→2위로 오른 건 클라우드·컨테이너·IaC로 **설정면이 폭발적으로 넓어졌기** 때문 — 기본값·열린 버킷·디버그 모드가 실수로 노출될 지점이 급증했다. SSDF의 통찰은 이걸 "개발자가 매번 체크리스트로 조심하기"로는 못 막는다는 것 — 사람은 반복 실수한다. 작동하는 형태는 **가드레일**: 안전한 기본값을 가진 프레임워크·파이프라인 자동 게이트로 "실수로 안전"하게 만들기. 체크리스트는 규모가 커지면 무너지지만, 기본값이 안전하면 아무것도 안 해도 안전하다. 그래서 "shift left"가 업무 떠넘기기가 아니라 자동화된 가드레일이어야 한다.
