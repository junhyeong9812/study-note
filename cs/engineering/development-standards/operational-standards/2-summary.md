## 1. ISO/IEC 20000-1:2018 — SMS의 뼈대

IT 서비스 관리 체계(Service Management System)에 대한 **요구사항** 표준(인증 가능). ISO 공통 상위 구조(HLS)를 따른다:

```text
4  조직 상황     이해관계자·범위 정의
5  리더십        경영진 책임 · 정책
6  기획          리스크와 기회 · 목표
7  지원          자원 · 역량 · 인식 · 소통 · 문서화
8  SMS 운영      ← 실무 프로세스가 여기 몰려 있다 (아래 2절)
9  성과 평가     모니터링·측정 · 내부심사 · 경영검토 · 서비스 보고
10 개선          부적합·시정조치 · 지속 개선
```

핵심 사상: 개별 프로세스가 아니라 **체계(system)** — 정책→계획→실행→측정→개선의 고리(PDCA)가 돌아야 인증이 나온다.

## 2. 조항 8 — 운영 프로세스 지도

```text
8.1 운영 기획·통제          SMS 운영 활동의 계획·실행·통제
8.2 서비스 포트폴리오       서비스 제공 · 서비스 계획 · 관련 당사자 통제 · 서비스 카탈로그 · 자산 관리 · 구성 관리
8.3 관계와 합의            비즈니스 관계 관리 · 서비스 수준 관리(SLM — SLA 정의·측정·리뷰) · 공급자 관리
8.4 수요와 공급            예산·회계 · 수요 관리 · 용량 관리(capacity)
8.5 서비스 설계·구축·이행   변경 관리(change) · 서비스 설계와 이행(design & transition) · 릴리즈와 배포 관리
8.6 해결과 이행            사고 관리(incident) · 서비스 요청 관리 · 문제 관리(problem — 근본 원인)
8.7 서비스 보증            가용성 관리(availability) · 서비스 연속성(continuity) · 정보보안 관리
```

### 2.1 (8.2) 서비스 포트폴리오 — "지금 무엇을 어떤 구성으로 제공하고 있나"

제공 중인 서비스의 목록(카탈로그)과, 서비스를 이루는 구성 요소(CI: 서버·DB·라이선스·의존 서비스)의 최신 정보를 유지하라는 요구. 한 줄 예시: "결제 서비스는 어떤 DB·큐·외부 PG에 의존하나?"에 문서(CMDB)로 즉답할 수 있어야, 장애·변경 때 영향 범위를 추정할 수 있다.

### 2.2 (8.3) 관계와 합의 — "고객·공급자와 무엇을 약속했나"

고객과는 SLA를 정의·측정·정기 리뷰하고(SLM), 외부 공급자(클라우드·PG사)에는 우리 SLA를 지탱할 수준의 계약을 걸어 관리하라는 요구. 한 줄 예시: 우리 SLA가 99.9%인데 의존하는 외부 PG 계약이 99.5%라면 — 그 PG에 단일·직렬로 의존하는 구조에서는 약속이 성립하지 않는다는 것을 SLM 리뷰에서 잡아야 한다(복수 PG·비동기 처리 같은 우회 설계가 있으면 달성 가능 — 그 판단까지가 리뷰의 일).

### 2.3 (8.4) 수요와 공급 — "쓸 만큼 준비되어 있고, 비용은 아나"

서비스 수요(트래픽·성장)를 예측하고, 그에 맞는 용량(capacity)과 예산을 계획하라는 요구. 한 줄 예시: "블랙프라이데이에 평시 5배 트래픽" 예측 → 부하 테스트로 한계 확인 → 스케일 계획·비용 승인까지가 한 묶음.

### 2.4 (8.5) 서비스 설계·구축·이행 — 변경 · 설계와 이행 · 릴리즈

**무엇을 요구하나**: 서비스에 가해지는 모든 변경을 분류(표준/일반/긴급)하고, 리스크·영향 평가와 승인을 거쳐서만 반영하라(변경 관리). 신규 서비스나 큰 변경은 설계 단계부터 요구사항·용량·연속성을 계획해 이행하라(설계와 이행). 실제 배포는 계획된 릴리즈 단위로 묶어 검증·배포·실패 시 복귀(rollback)까지 관리하라(릴리즈·배포 관리).

**시나리오 예시 — DB 스키마 변경 배포**:
```text
1. 개발팀이 주문 테이블 컬럼 추가 변경 요청(RFC) 제출 — 영향: 주문 API·정산 배치
2. 변경 관리: 리스크 평가(마이그레이션 중 잠금? 롤백 방법?) → "일반 변경"으로 승인, 배포창 지정(화요일 03시)
3. 릴리즈 관리: 앱 v2.14 + 마이그레이션 스크립트를 한 릴리즈로 묶음 — 스테이징 검증 통과 기록
4. 배포 실행 → 스모크 테스트 → 실패 시 준비된 롤백 절차(컬럼은 남기고 앱만 이전 버전) 실행
5. 변경 기록 종결: 결과(성공/실패)와 실측 소요를 변경 이력에 남김 → 구성 관리(8.2) 정보 갱신
```

**체크포인트**:
- 변경의 분류 기준(표준/일반/긴급)과 각각의 승인 경로가 **정의돼 있는가?**
- 모든 릴리즈에 롤백(또는 forward-fix) 절차가 배포 **전에** 준비돼 있는가?
- "누가 언제 무엇을 배포했나"를 사후에 추적할 수 있는 기록이 남는가?

### 2.5 (8.6) 해결과 이행 — 사고 · 서비스 요청 · 문제

**무엇을 요구하나**: 사고(incident)는 기록·분류·우선순위를 정해 목표 시간 안에 **서비스를 회복**하라 — 중대 사고(major incident)는 별도 절차·사후 보고까지. 서비스 요청(계정 발급·권한 변경 같은 정상 요청)은 사고와 분리해 정해진 절차로 이행하라. 문제(problem)는 사고의 **근본 원인을 분석해 재발을 방지**하고, 당장 못 고치면 알려진 오류(known error)와 임시조치(workaround)로 등록해 관리하라.

**시나리오 예시 — 결제 API 장애, 발생부터 문제 등록까지**:
```text
14:02  알람: 결제 API 에러율 0.1% → 12% 급등. 온콜이 사고 티켓 생성, 심각도 P1(중대 사고) 지정
14:05  영향 파악: 카드 결제만 실패, 간편결제 정상 — 상태 페이지 공지·CS팀 전파
14:11  최근 변경 확인(변경 관리 기록 조회): 13:50 결제 모듈 v3.2 배포 발견
14:15  판단: 원인 규명은 뒤로 미루고 롤백 먼저 — v3.1로 복귀 (사고 관리의 목표는 회복)
14:24  에러율 정상 복귀 확인 → 사고 종결 기록(타임라인·영향 범위·복구 조치)
──── 여기까지가 "사고" ── 이후는 "문제" ────
+1일   문제 티켓 생성: v3.2에서 왜 실패했나 → 분석 결과 PG사 타임아웃 설정 변경이 원인
+3일   근본 조치: 타임아웃 설정을 코드 리뷰 체크리스트에 추가, 통합 테스트 보강 — 문제 종결
```
사고는 14:24에 끝났지만 문제는 3일 뒤에 끝났다 — **같은 사건, 두 개의 트랙, 다른 종료 조건.**

**체크포인트**:
- 사고의 심각도 분류와 심각도별 대응 목표 시간이 **정의돼 있는가?**
- 중대 사고를 선언하는 기준과 선언 시 절차(지휘자·소통 채널)가 정해져 있는가?
- 사고 종결 후 문제 티켓으로 넘어가는 연결 고리(그리고 known error 목록)가 있는가?

### 2.6 (8.7) 서비스 보증 — 가용성 · 연속성 · 정보보안

**무엇을 요구하나**: 서비스별 가용성 목표를 정하고 측정·미달 시 조치하라(가용성 관리). 큰 재해(데이터센터 소실 수준)에도 정해진 시간 안에 서비스를 복구할 계획을 세우고 **실제로 시험**하라(연속성 관리 — RTO/RPO). 정보보안 정책·통제를 수립하고 보안 사고를 관리하라(정보보안 관리).

**시나리오 예시 — 연속성 계획과 DR 훈련**:
```text
1. 목표 합의: 결제 서비스 RTO 30분(복구까지 허용 시간) · RPO 5분(잃어도 되는 데이터 시간)
2. 설계: 다른 리전에 대기(standby) DB — 5분 간격 복제가 RPO 5분의 근거
3. 연 1회 DR 훈련: 주 리전을 의도적으로 차단 → 페일오버 실행 → 실측 복구 22분 = RTO 충족 기록
4. 훈련에서 발견: DNS 전환 수동 단계가 병목 → 자동화 액션 아이템 등록 (→ 10항 개선으로 연결)
```
계획서만 있고 훈련이 없으면 감사에서도, 실제 재해에서도 통하지 않는다 — **시험까지가 요구사항**이다.

**체크포인트**:
- 서비스별 가용성 목표가 숫자로 **정의돼 있고**, 실측치와 비교되고 있는가?
- RTO/RPO가 정의돼 있고, 최근에 실제 훈련으로 검증한 기록이 있는가?
- 보안 사고 발생 시 일반 사고와 다른 보고·대응 경로가 정해져 있는가?

구분이 중요한 쌍:
- **Incident vs Problem** — 사고는 "빨리 복구"(원인 규명보다 서비스 회복 우선), 문제는 "재발 방지"(근본 원인). 같은 사건의 두 국면.
- **Change vs Release** — 변경은 승인·리스크 판단의 관문, 릴리즈는 실제 배포 행위.

## 3. Google SRE — 약속을 숫자로 운영하기

### 3.1 SLI → SLO → SLA — 지표, 목표, 계약

- **SLI** (indicator): 사용자가 체감하는 지표의 측정값 — 성공률, p99 지연, 처리량.
- **SLO** (objective): SLI에 대한 내부 목표 — "30일 창에서 성공률 99.9%".
- **SLA** (agreement): 고객과의 계약(위반 시 결과(consequences) — 크레딧·보상·해지권 등을 명시) — SLO보다 느슨하게 잡는 외부 약속.

**계산 예시** — 30일 창, 요청 1,000만 건, SLO 99.9%:
```text
허용 실패 = 10,000,000 × (1 − 0.999) = 10,000건   ← 요청 기반 SLI의 에러 버짓

SLI를 시간 기반 가용성으로 잡으면 버짓 계산도 별도다(치환 아님 — 트래픽은 시간에
균등하지 않아 실패 10,000건 ≠ 다운타임 43.2분, 피크엔 몇 초 만에 소진될 수도 있다).
30일 = 43,200분 기준, 완전 다운 기준 허용 다운타임:

SLO       월간(30일) 허용 다운타임
99%       432분  (7.2시간)
99.9%     43.2분
99.99%    4.32분
99.999%   0.432분 (약 26초)
```
9 하나가 붙을 때마다 허용치가 1/10 — 99.99%쯤부터는 통상적인 장애 빈도를 가정하면 **사실상 자동화를 요구**하게 된다: 수동 대응(감지+진단+복구)은 보통 분 단위라, 장애 한 번으로 월 버짓 4.32분이 소진되기 쉽다(장애가 극히 드물거나 무중단 구조라면 수동으로도 논리적으로는 가능). 자동 페일오버가 표준이 되는 이유가 이 표에 있다.

### 3.2 에러 버짓 — 갈등을 규칙으로

100% − SLO = 써도 되는 실패량. 버짓이 남았으면 배포·실험을 계속하고, **소진되면 기능 출시를 멈추고 신뢰성 작업**을 한다 — 개발 속도와 안정성의 갈등을 협상이 아니라 규칙으로 바꾼 장치.

**소진 시나리오 예시** — 위 3.1의 버짓 10,000건:
```text
1주차  배포 2회, 소소한 에러 → 누적 1,200건 소진 (12%) — 정상 페이스
2주차  카나리에서 못 잡은 버그로 20분 부분 장애 → 누적 8,000건 (80%)
       → 버짓 정책 발동: 신규 기능 배포 동결 논의, 남은 2주는 버그 수정·테스트 보강만
3~4주차  남은 버짓(20%) 안에서 보수적으로 운영 — 2주차 장애분은 발생 30일 뒤에야
         rolling window 밖으로 빠지므로 당장은 회복되지 않는다(달력 월 방식이면 월
         리셋 때 회복 — 두 방식은 회복 시점이 다르다) → 창을 빠져나간 뒤 배포 재개
```
포인트: 2주차의 "동결"은 누군가의 화난 판단이 아니라 **사전에 합의된 정책의 기계적 발동**이다. 이 정책에 경영진 서명이 없으면 동결은 실제로 작동하지 않는다(아래 [Claude 추가] C).

### 3.3 Toil — 측정해야 줄일 수 있다

수작업·반복적·자동화 가능·서비스 성장에 비례해 늘어나는 운영 노동. SRE는 toil을 측정하고 상한(구글 기준 50%)을 두어 나머지 시간을 자동화·개선에 쓴다.

**구분 예시**:
```text
Toil인 것                                Toil이 아닌 것
──────────────────────────────           ──────────────────────────────
디스크 알람 올 때마다 수동 정리          그 정리를 자동화하는 스크립트 작성
매 배포마다 수동 승인 클릭·확인 절차     배포 파이프라인 개선 작업
사용자 계정을 티켓 받아 수동 생성        온콜 중 새로운 장애의 원인 분석(판단 필요)
같은 known error에 매번 같은 재시작      포스트모템 작성·리뷰(가치가 축적됨)
```
판별 기준: 한 가지로 판정하지 않는다 — 수작업·반복적·자동화 가능·전술적·영속 가치 없음·**서비스가 2배 크면 그 일도 2배**(규모 비례) 같은 특성이 겹칠수록 toil이다(규모 비례 하나만으론 부족 — 용량 설계도 규모 따라 늘지만 판단이 필요한 엔지니어링이다). 자동화하지 않으면 성장이 사람을 갈아 넣는다.

### 3.4 온콜과 포스트모템 — 비난 없이 시스템을 고친다

장애는 비난 없는(blameless) 포스트모템으로 — 사람을 비난하는 대신, 그 행동을 허용한 시스템·절차의 결함을 찾는다. 재발 방지 액션이 산출물.

**blameless 포스트모템 구성 예시** (2.5의 결제 장애 사례로):
```text
제목/심각도   결제 API 부분 장애 (P1) — 2026-08-24
영향          22분간 카드 결제 12% 실패, 약 3,400건 — 매출 영향 추정 포함
타임라인      14:02 알람 → 14:11 원인 후보 식별 → 14:15 롤백 결정 → 14:24 복구 (감지 3분·진단 10분·복구 9분)
근본 원인     PG 타임아웃 설정 변경이 통합 테스트에서 검출되지 않음
기여 요인     카나리가 카드 결제 경로를 커버하지 않음 · 타임아웃 설정이 코드 리뷰 대상 아님
잘된 것       변경 기록 덕에 9분 만에 원인 후보 특정 · 롤백 절차가 준비돼 있었음
액션 아이템   [P1] 카나리에 카드 결제 시나리오 추가(담당 A, ~9/5) · [P2] 설정 diff 리뷰 자동화(담당 B, ~9/19)
```
"누가 실수했나"라는 문장이 하나도 없다는 점에 주목 — 인간의 행동(명령·판단·소통)도 인과관계에는 그대로 기록하되, 분석은 개인 비난이 아니라 그 행동을 허용한 조건(테스트 커버리지·리뷰 절차·당시 정보와 도구)으로 향한다. 비난이 시작되는 순간 다음 장애에서 정보가 숨는다.

### 3.5 모니터링 — 골든 시그널 4개

지연(latency) · 트래픽(traffic) · 에러(errors) · 포화도(saturation). 각 시그널이 잡는 장애 유형:

```text
시그널      무엇을 보나                  잡아내는 장애 예시
──────      ──────────────────────       ─────────────────────────────────────
지연        요청 처리 시간(p99 포함)      DB 슬로우 쿼리, GC 폭주, 다운스트림 지연 전파
트래픽      초당 요청 수                  급증(이벤트·DDoS) / 급감(상위 장애·DNS 문제로 요청이 안 옴)
에러        실패율(5xx·타임아웃)          배포 버그, 의존 서비스 다운, 인증 만료
포화도      자원 사용률(CPU·메모리·큐)    용량 한계 임박 — "아직 안 죽었지만 곧 죽는다"의 조기 경보
```
포인트: 트래픽 **급감**도 장애 신호(사용자가 우리에게 도달을 못 하는 중), 포화도는 임박한 한계를 미리 보여주는 대표적 **예측형** 시그널이다(유일하진 않다 — 지연·에러의 증가 추세도 전조가 된다). 성공 로그만 보면 넷 다 놓친다.

## 4. 두 기준의 연결 — 같은 요구, 다른 층

```text
20000-1 (요구)                     SRE (구현)
─────────────────────────────      ─────────────────────────────
서비스 수준 관리(SLA 정의·측정)  →  SLI 선정 → SLO 설정 → 에러 버짓 정책
가용성 관리                      →  SLO의 가용성 목표 + 다중화·페일오버 설계
사고 관리 / 문제 관리            →  온콜·인시던트 대응 → blameless 포스트모템
변경·릴리즈 관리                 →  카나리 배포·점진 롤아웃·자동 롤백
용량 관리                        →  수요 예측 + 부하 테스트 + 오토스케일링
지속 개선(10항)                  →  toil 측정·자동화, 포스트모템 액션 추적
```

한 줄 대비: 20000-1은 **감사자가 볼 수 있는 체계**를, SRE는 **엔지니어가 매일 쓰는 도구와 규칙**을 요구한다. 서로의 빈 곳(체계 없는 실천 / 실천 없는 체계)을 메운다.

## 5. 현장에서 만나는 상황

- 장애가 나면: 사고(복구) 트랙과 문제(재발 방지) 트랙을 분리해 기록 — 복구 후 포스트모템까지가 한 사이클.
- "언제까지 되어야 하나"는 질문에: SLA/SLO 숫자로 답하고, 그 숫자를 대시보드에서 아무나 볼 수 있게.
- 배포가 무서워지면: 변경 관리가 관료화된 신호 — 승인 단계를 늘리는 대신 카나리·자동 롤백으로 리스크 자체를 줄인다(에러 버짓이 근거).
- runbook: 알람마다 "받은 사람이 새벽 3시에 그대로 따라할 수 있는" 문서가 있는가.

## 6. 선행 주제 연결

[straggler](../../straggler/)의 tail latency — 평균이 아니라 p99가 사용자 경험을 지배한다는 결론은 **SLI를 평균이 아닌 퍼센타일로 정의해야 하는 이유**다. 규모가 커질수록(fan-out) SLO는 하위 서비스에 더 엄격한 꼬리를 요구한다.

## 핵심 문장

- 20000-1 = 무엇을 갖출 것(체계·인증 가능), SRE = 어떻게 할 것(측정·자동화) — 연결고리는 SLA/SLO라는 "약속".
- 에러 버짓은 개발 vs 운영의 갈등을 **협상이 아니라 규칙**으로 바꾼 장치다.
- 사고는 복구, 문제는 재발 방지 — 이 둘을 섞으면 복구도 늦고 재발도 막지 못한다.
- toil을 측정하지 않으면 운영은 서비스 성장에 비례해 사람을 갈아 넣게 된다.
- 9 하나가 늘 때마다 허용 다운타임은 1/10 — 어느 지점부터는 사실상 자동화를 요구하는 약속이 된다(장애 1회의 수동 대응 시간이 월 버짓을 소진하기 때문).

## [Claude 추가] 더 알면 좋은 것

> 이 절은 두 기준 문서 밖의 확장 이야기.

### A. SLO는 "사용자 여정"에서 거꾸로 정한다

좋은 SLI는 서버 메트릭이 아니라 사용자 행동 단위(검색 결과가 보인다, 결제가 완료된다)에서 출발한다. CPU 사용률은 SLI가 아니다 — 원인 지표일 뿐. "사용자가 화내기 직전"이 SLO의 올바른 위치라는 것이 SRE Workbook의 반복되는 조언이다.

### B. DevOps·ITIL과의 관계

ITIL은 20000-1의 실천 카탈로그(관행 34개), DevOps는 문화·자동화 운동, SRE는 "DevOps를 구현하는 구체적 직무 설계"(class SRE implements interface DevOps — SRE Workbook 1장). 셋은 경쟁이 아니라 같은 문제의 다른 절단면이다.

### C. 에러 버짓의 어두운 면

버짓 소진 → 출시 동결 규칙은 경영진 합의 없이는 작동하지 않는다(동결을 강제할 권한). 또 SLO가 느슨하면 버짓이 늘 남아 신뢰성 투자가 미뤄진다 — SLO 자체를 주기적으로 재협상하는 것까지가 제도다.

### D. 국내 맥락

전자금융감독규정의 장애 보고 의무, 재해복구(DR) 목표시간(RTO/RPO) 요구처럼 국내 규제가 20000-1의 연속성·가용성 관리와 겹친다 — 법률 축(legal-standards)과 만나는 지점.
