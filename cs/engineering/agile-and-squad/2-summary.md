# foundations/agile-and-squad — 정리 (힌트)

> 복습은 [1-question.md](1-question.md)에서 시작하고, 막힐 때만 이 파일을 힌트로 연다.\
> 원고 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` (따라 친 원본 노트) · 이관일 2026-09-16.\
> 본문(애자일·스크럼·칸반·스쿼드·콘웨이 절)은 **원고**를 고쳐 쓴 것이다(문체·순서 유지·특정 프로젝트 이름은 일반화).\
> 「한눈에」의 비유 그림은 **Claude가 원고 이해를 돕기 위해 새로 그린 것**이며, 원고에 없던 지식은 맨 끝 `[Claude 추가]`에만 둔다.

**애자일(Agile)** = 짧은 주기로 만들고 · 보여주고 · 배운 것을 반영해 고쳐가는 개발 방식의 총칭.\
특정 방법론 이름이 아니라 **"요구를 처음에 다 알 수 없다"는 전제 위에 세운 태도**다.

---

## 한눈에 — 쉽게 말하면

**길을 모르는 산을 오르는 두 방법**을 떠올리면 된다. *(Claude 보강 — 원고에 없는 비유)*

```text
길을 모르는 산을 오르는 두 방법
+-------------------------------------------+
| [폭포수] 출발 전에 정상까지                 |
|          전체 경로를 다 그려 둔다            |  ← 안개가 끼면 지도가 곧 거짓말이 된다
|                                           |
| [애자일] 다음 능선까지만 정하고             |
|          올라가서 보이는 만큼 다시 그린다     |  ← 자주 멈춰 지도를 고친다
+-------------------------------------------+
```

**소프트웨어도 똑같은 구조다.** 요구·시장·기술은 개발 중에 바뀌는데(안개), 폭포수는 출발 전 지도(초기 설계)를 끝까지 믿는다.\
애자일은 반대로 **짧게 만들어 보여주고**, 거기서 배운 것으로 다음 계획을 고친다.

쉽게 말하면 이렇다.\
**애자일이 "어떻게 일할 것인가"라는 방식이라면, 스쿼드·콘웨이는 "그 방식이 굴러가려면 조직을 어떻게 나눠야 하는가"라는 구조다.** 이 문서는 방식(1~2)에서 시작해 구조(3)로 올라가고, 마지막에 **혼자·소규모일 때 무엇을 살리나**(4~5)로 내려온다.

## 문제 — 이 개념이 답하려는 질문

이 주제에는 풀어야 할 코드 과제가 없다(조직·프로세스 정리다). 대신 각 개념이 하나의 질문에 답한다.

```text
애자일    "요구가 개발 도중에 바뀐다는 걸 전제하면, 개발을 어떻게 짜야 하는가?"
스크럼    "시간을 고정하고 범위를 조절하면 무엇이 좋아지는가?"
칸반      "주기 없이 흐름만 관리하면 무엇이 좋아지는가?"
스쿼드    "제품 자율성과 기술 일관성을 동시에 가지려면 조직을 어떻게 나누나?"
콘웨이    "왜 아키텍처 문서에 조직 이야기가 끼어드는가?"
개인 적용  "이 장치들 대부분이 여러 사람 동기화용인데, 혼자·소규모면 무엇을 살리나?"
```

아래 서머리는 이 질문들을 하나씩 분석·정리한 것이다.

> 애초에 **왜 아키텍처를 이야기하다 조직 이야기가 나오는가**: 콘웨이의 법칙 때문이다.\
> 조직 구조와 아키텍처는 서로를 결정하므로, 조직을 모르고 아키텍처만 그리면 문서와 현실이 갈라진다.

## 전체 흐름

방식 → 구조 → 축소의 세 걸음으로 읽는다.

```text
폭포수의 전제("요구를 처음에 다 안다")가 깨진다
        ↓
애자일 = "모른다"를 전제로 짧게 만들어 배운다   (가치 4가지 · 오해 바로잡기)
        ↓
그걸 실천하는 두 틀
   ├─ 스크럼: 시간(스프린트)을 고정, 범위를 조절
   └─ 칸반:   WIP를 고정, 시간을 조절
        ↓
그 팀들을 어떻게 배치하나 = 스쿼드 모델(세로=제품 / 가로=직군)
        ↓
콘웨이: 조직 모양이 곧 아키텍처 모양 → 원하는 아키텍처면 조직부터 바꾼다
        ↓
혼자·소규모로 축소: 동기화 장치는 버리고, 학습 장치(회고·DoD·작은 증분)는 살린다
```

## 애자일이란 무엇인가

> 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` — §1

### 애자일 선언(2001) — 4가지 가치

> - **개인과 상호작용**을 프로세스와 도구보다
> - **작동하는 소프트웨어**를 포괄적인 문서보다
> - **고객과의 협력**을 계약 협상보다
> - **변화에 대응**을 계획을 따르는 것보다

**가장 흔한 오해**: "문서를 쓰지 말라"가 아니다.\
원문은 **"오른쪽도 가치 있지만 왼쪽을 더 중시한다"**로 끝난다. 문서보다 작동하는 소프트웨어가 우선이라는 뜻이지, 문서가 무가치하다는 뜻이 아니다.

> **현장에서 만나는 상황**: 설계 문서를 잔뜩 쓰는 것이 애자일에 어긋나는가? **어긋나지 않는다.**\
> 그 문서가 "포괄적 문서"(읽는 사람이 없는데도 형식으로 쌓는 문서)가 아니라 **판단의 근거**로 쓰인다면 애자일과 충돌하지 않는다.\
> 특히 산출물이 서비스가 아니라 **이해·학습**인 작업에서는 문서 자체가 결과물이다.

### 왜 폭포수가 잘 안 되는가

폭포수의 전제는 **"요구사항을 처음에 다 알 수 있다"**이다. 그런데 실제로는:

- 사용자는 **써보기 전까지 뭘 원하는지 모른다**
- 만들면서 **문제의 진짜 모양이 드러난다**
- 시장·규제·기술이 **개발 중에 바뀐다**

애자일은 이 전제를 뒤집는다 — **"모른다는 것을 전제로 설계한다."** 짧게 만들어 보여주고 배운 것을 반영한다.

> **폭포수(Waterfall)** — 요구분석 → 설계 → 구현 → 테스트를 순서대로 한 번씩 밟는 방식.\
> 예: 6개월 뒤 한 번에 공개하는 계획. 그 사이 요구가 바뀌면 되돌릴 지점이 없다.

### 애자일이 아닌 것 — 오해 대 실제

| 오해 | 실제 |
|---|---|
| 계획을 안 세운다 | **더 자주** 세운다 (주기마다) |
| 문서를 안 쓴다 | **필요한 만큼만** 쓴다 |
| 설계를 안 한다 | **한 번에 다 하지 않을** 뿐이다 |
| 빠르게 만드는 것 | **빠르게 배우는 것** |
| 매일 야근하는 것 | **지속 가능한 속도**가 원칙 중 하나다 |

## 스크럼 (Scrum)

> 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` — §2.1

**언제 쓰나** — 계획이 어느 정도 서는 신규 개발, 여러 사람이 한 주기를 함께 밟아야 할 때.\
**시간을 고정하고 범위를 조절**하는 방식이다.

> **스프린트(Sprint)** — 스크럼에서 쓰는 반복 주기 하나. 보통 1~4주로 **길이를 고정**한다.\
> 예: "이번 2주 안에 되는 것까지"를 정하고, 못 끝낸 일은 다음 스프린트로 넘긴다(기간은 안 늘린다).

### 역할 3가지

| 역할 | 책임 |
|---|---|
| **프로덕트 오너(PO)** | 무엇을 만들지 결정. 백로그 우선순위의 **단독 결정권자** |
| **스크럼 마스터(SM)** | 프로세스가 굴러가게 함. 장애물 제거. **관리자가 아니다** |
| **개발팀** | 어떻게 만들지 결정. 자기조직화 |

### 이벤트 5가지

| 이벤트 | 시점 | 목적 |
|---|---|---|
| **스프린트** | 1~4주 | 반복 주기 그 자체 |
| **스프린트 계획** | 시작 시 | 이번에 무엇을 할지 정한다 |
| **데일리 스크럼** | 매일 15분 | 어제/오늘/장애물 공유 |
| **스프린트 리뷰** | 종료 시 | **결과물을 보여주고** 피드백받는다 |
| **회고** | 종료 시 | **프로세스**를 개선한다 |

> ⚠️ 리뷰와 회고는 다르다. **리뷰는 제품**, **회고는 프로세스**를 다룬다. 이 둘을 합치면 대개 회고가 사라진다.

### 산출물 3가지

- **제품 백로그**: 전체 할 일 목록 (우선순위 순 정렬)
- **스프린트 백로그**: 이번 주기에 할 일
- **증분(Increment)**: 이번 주기의 결과물. **DoD를 만족해야** 증분이다

> **DoD(Definition of Done)** — "끝났다"의 정의. 팀이 합의한 완료 기준.\
> 예: "테스트 통과 + 코드 리뷰 + 문서 갱신"까지 돼야 done. 기준이 없으면 무엇이든 영원히 "90%"다.

### 유저 스토리 형식

```text
As a   [누가]
I want [무엇을]
So that [왜]
```

예:

```text
As a   카드소지자
I want 결제 취소 내역을 앱에서 확인하고
So that 환불이 정상 처리됐는지 스스로 확인할 수 있다
```

**INVEST 기준** — 좋은 스토리의 조건:

| 글자 | 뜻 |
|---|---|
| **I**ndependent | 다른 스토리와 독립적 |
| **N**egotiable | 세부는 협의 가능 |
| **V**aluable | 사용자에게 가치 있음 |
| **E**stimable | 크기를 가늠할 수 있음 |
| **S**mall | 한 주기에 끝날 만큼 작음 |
| **T**estable | 완료를 검증할 수 있음 |

**비용/트레이드오프** — 역할·이벤트·산출물이 많다. 이 무게의 상당 부분은 **여러 사람을 동기화**하기 위한 것이라, 팀이 작아질수록 순손실로 바뀐다(→ §개인·소규모 적용).

## 칸반 (Kanban)

> 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` — §2.2

**언제 쓰나** — 우선순위가 자주 바뀌는 운영·유지보수, 스프린트로 묶기 어려운 연속 유입 작업.\
**범위를 고정하지 않고 흐름을 관리**하는 방식이다. 스프린트가 없다.

```text
+---------+-----------+-----------+---------+
|  대기   |  진행중    |  리뷰      |  완료   |
|         |  (WIP<=2) |  (WIP<=1) |         |
+---------+-----------+-----------+---------+
| 작업 A  | 작업 C    | 작업 E    | 작업 G  |
| 작업 B  |           |           | 작업 H  |
+---------+-----------+-----------+---------+
```

**핵심 원칙**:

1. **현재 작업을 시각화한다**
2. **WIP를 제한한다** ← 가장 중요하고 가장 안 지켜지는 것
3. **흐름을 관리한다** (리드 타임 측정)
4. **정책을 명시한다**
5. **점진적으로 개선한다**

> **WIP(Work In Progress)** — 동시에 진행 중인 작업의 수. 칸반은 각 단계에서 이 수를 제한한다.\
> 예: "진행중 최대 2개". 세 번째를 시작하려면 먼저 하나를 완료로 밀어내야 한다.

### WIP 제한이 왜 중요한가 — 전/후 대비

```text
WIP 무제한 (다 시작해 둔다)          WIP 제한 (하나씩 끝낸다)
+---------------------------+       +---------------------------+
| 진행중 5건                 |       | 진행중 2건 (상한)          |
| 전부 "끝나지 않은 상태"     |       | 하나 끝내야 다음 시작       |
| 컨텍스트 스위칭 비용 붙음    |       | 완료가 자주 나온다          |
+---------------------------+       +---------------------------+
  -> 완료가 0이라 피드백도 0          -> 총 처리량이 오른다
```

동시에 5개를 진행하면 5개 모두 **끝나지 않은 상태**로 오래 머문다. 컨텍스트 스위칭 비용이 붙고, 완료된 게 없어 피드백도 못 받는다.\
**하나를 끝내고 다음을 시작하는 것**이 총 처리량을 높인다.

**비용/트레이드오프** — 고정 리듬(마감)이 없어 자율에 기댄다. WIP 제한을 스스로 지키지 못하면 그냥 무제한 큐가 된다.

## 스크럼 vs 칸반

> 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` — §2.3

| | 스크럼 | 칸반 |
|---|---|---|
| 주기 | 고정 스프린트 | 연속 흐름 |
| 고정하는 것 | **시간** (범위 조절) | **WIP** (시간 조절) |
| 역할 | 정해져 있음 | 없음 |
| 변경 수용 | 스프린트 중엔 지양 | **언제든** |
| 적합한 상황 | 계획 가능한 신규 개발 | 우선순위가 자주 바뀌는 운영·유지보수 |

**혼자·소규모 개발에는 칸반이 대체로 낫다.** 스프린트 계획·리뷰·데일리의 상당 부분은 **여러 사람의 동기화**를 위한 장치인데, 인원이 적으면 그 비용이 순손실이 되기 때문이다.

## 스쿼드 방식 (Spotify Model)

> 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` — §3

한 스트리밍 회사가 2012년에 소개한 조직 모델이다. **네 가지 단위**로 이루어진다.

```text
       트라이브 — 관련 스쿼드들의 묶음, 100명 이하
   +------------------------------------------------+
   |  +---------+  +---------+  +---------+          |
   |  | 스쿼드1 |  | 스쿼드2 |  | 스쿼드3 |          |  <- 스쿼드: 6~12명 교차기능 팀
   |  | 결제    |  | 계좌    |  | 원장    |          |
   |  +----+----+  +----+----+  +----+----+          |
   |       |            |            |               |
   |  .....+............+............+..... 챕터: 같은 직군 묶음
   |       백엔드 챕터 / QA 챕터 / 프론트 챕터         |    (스쿼드를 가로지름)
   +------------------------------------------------+
   ....................................... 길드: 관심사 기반 자발적 모임
                                                (조직 전체를 가로지름)
```

| 단위 | 성격 | 목적 |
|---|---|---|
| **스쿼드(Squad)** | 6~12명, 교차기능, **자율적** | 한 제품 영역을 **끝까지** 책임 |
| **트라이브(Tribe)** | 관련 스쿼드 묶음, ~100명 | 스쿼드 간 조율 |
| **챕터(Chapter)** | 같은 직군의 사람들 (백엔드 챕터 등) | **기술 역량·표준** 유지 |
| **길드(Guild)** | 관심사 기반 자발적 모임 | 지식 공유 |

> **교차기능(Cross-functional)** — 기획·개발·QA 등 필요한 역할이 팀 안에 다 있는 상태.\
> 예: 스쿼드 하나가 다른 팀을 기다리지 않고 기획부터 배포까지 스스로 끝낸다.

**핵심 발상**: 스쿼드는 **세로(제품)**로 나누고, 챕터는 **가로(직군)**로 묶는다.\
제품 자율성(세로)과 기술 일관성(가로)을 동시에 얻으려는 시도다.

### 스쿼드의 조건

- **하나의 미션**을 가진다 (예: "결제 승인 경험을 책임진다")
- **자율적으로 결정**한다 (무엇을 어떻게 만들지)
- **끝까지 책임진다** — 기획부터 운영까지 (You build it, you run it)
- 다른 스쿼드에 **의존하지 않고 배포**할 수 있다

## 콘웨이의 법칙 (Conway's Law)

> 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` — §3

> **"시스템을 설계하는 조직은 그 조직의 소통 구조를 그대로 닮은 설계를 만든다."** (1967)

**언제 나오나** — 조직 구조와 아키텍처가 어긋날 때. 예:

```text
프론트팀 / 백엔드팀 / DBA팀으로 나뉜 조직   ->  레이어드 아키텍처가 나온다
결제팀  / 계좌팀   / 원장팀으로 나뉜 조직   ->  도메인별 서비스가 나온다
```

**역 콘웨이 전략(Inverse Conway Maneuver)**: 원하는 아키텍처가 있으면 **조직을 먼저 그 모양으로 바꾼다.**\
마이크로서비스를 원하면서 조직은 기술 계층별로 나뉘어 있으면, 결국 **분산 모놀리스**가 나온다.

> **분산 모놀리스(distributed monolith)** — 서비스는 여러 개로 쪼갰는데 서로 강하게 얽혀 독립 배포가 안 되는 상태.\
> 예: A를 배포하려면 B·C도 같이 배포해야 한다면, 나눈 이득 없이 네트워크 홉만 늘어난 것이다.

> **이것이 스쿼드 모델과 마이크로서비스가 함께 언급되는 이유다.**\
> 스쿼드 하나 = 서비스 몇 개를 소유. 독립 배포가 가능하려면 조직도 독립적이어야 한다.

### 스포티파이 모델의 함정

**그 회사 자신도 이 모델을 그대로 쓰지 않는다.** 2012년 영상이 널리 퍼지며 "정답"처럼 받아들여졌지만:

1. **그것은 당시의 스냅샷**이었지 완성된 방법론이 아니었다
2. 스쿼드 간 **의존은 여전히 생겼고**, 조율 비용이 컸다
3. 챕터 리드의 역할이 모호해 **책임 공백**이 발생했다
4. 다른 회사가 형태만 복사하면 **이름만 바뀐 기존 조직**이 된다

> 교훈: **조직 모델은 복사하는 것이 아니라 문제에서 도출하는 것이다.**\
> "우리는 무슨 문제 때문에 이 구조가 필요한가"에 답할 수 없으면 도입하지 않는 게 낫다.

## 개인·소규모 개발에 애자일을 어떻게 적용하는가

> 출처: `jun-bank/docs/study/07-agile-and-squad/README.md` — §4~5 (특정 프로젝트 적용을 일반 맥락으로 일반화)

혼자·소수로 일하면 스크럼 이벤트 대부분이 **여러 사람의 동기화 장치**라 그대로 쓰면 형식만 남는다.\
**살릴 것과 버릴 것**을 가른다.

### 버려도 되는 것

| 항목 | 이유 |
|---|---|
| 데일리 스크럼 | 공유할 상대가 없다 |
| 스토리 포인트·속도 측정 | 상대 추정은 여러 사람의 합의가 있어야 의미가 있다 |
| 역할 분리(PO/SM/개발) | 전부 한 사람 |
| 스프린트 리뷰(형식적 발표) | 보여줄 이해관계자가 없다 |

### 반드시 살려야 하는 것

| 항목 | 이유 | 적용 방식 |
|---|---|---|
| **작은 증분** | 큰 덩어리는 끝이 안 난다 | 완결된 흐름 1개 = 1 사이클 |
| **DoD** | 기준이 없으면 영원히 90%다 | 정해둔 단계를 전부 통과해야 완료 |
| **회고** | **혼자 개발에서 가장 중요하다** | 매 사이클 마지막 단계로 고정 |
| **WIP 제한** | 혼자면 동시 작업의 유혹이 더 크다 | **동시 1개** 권장 |
| **백로그 우선순위** | 하고 싶은 것부터 하면 중요한 게 안 끝난다 | 핵심 관통도 기준 |
| **작동하는 것 우선** | 완벽한 설계보다 도는 코드 | 얇은 수직 슬라이스 |

### 왜 혼자 개발에서 회고가 가장 중요한가

혼자 일하면 **아무도 지적해 주지 않는다.** 잘못된 습관이 그대로 굳는다. **회고는 자기 자신을 상대로 하는 코드 리뷰다.**

회고에서 물을 것:

1. **설계와 실제가 갈라진 지점은 어디인가?** → 문서를 고친다
2. **예상보다 오래 걸린 것은 무엇이고, 왜인가?**
3. **다음 사이클에서 하나만 바꾼다면 무엇인가?**
4. **가정 중 틀린 것이 있었나?**

> 1번이 핵심이다. **설계와 구현이 갈라졌는데 문서를 안 고치면, 그때부터 문서는 거짓말이 된다.**

### 1인 스쿼드로 보기

혼자 하는 일을 **"모든 챕터를 겸하는 1인 스쿼드"**로 보면, 스쿼드의 조건을 스스로에게 물을 수 있다:

- **하나의 미션이 있는가?** (예: 결제 도메인 이해)
- **끝까지 책임지는가?** (설계·구현·운영·회고 전부)
- **독립적으로 배포 가능한가?** (예: 로컬 컨테이너로 전부)

챕터가 없다는 것은 **기술 표준을 스스로 세워야 한다**는 뜻이다. 컨벤션 문서를 따로 두는 이유가 여기 있다.

### 반복 단위 — 스프린트 대신 유스케이스

시간(스프린트) 대신 **완결된 흐름 하나(유스케이스)**를 반복 단위로 잡을 수 있다.

```text
① 유스케이스 선정   <- 백로그 우선순위(핵심 관통도 기준)
② 기능 명세         <- 유저 스토리 + 수용 기준
③ 설계(+ADR)
④ 계약 확정         <- API/이벤트 스키마. 구현보다 먼저
⑤ 구현
⑥ 검증             <- DoD
⑦ 회고·문서 갱신    <- 애자일의 핵심. 여기가 빠지면 폭포수
```

**왜 시간이 아니라 범위를 완결로 고정하나**: 결제 같은 도메인에서 "절반 구현된 승인"은 가치가 0이다.\
시간을 고정하고 범위를 자르면 **반쪽짜리 흐름**이 남는다. 그래서 시간이 아니라 **완결된 흐름 하나**를 단위로 잡는다 — 스크럼보다 **칸반에 가까운 선택**이다.

## 핵심 문장

- **애자일은 "빠르게 만드는 것"이 아니라 "빠르게 배우는 것"이다** — 요구를 모른다는 전제 위에 세운 태도다.
- **스크럼은 시간을 고정하고 범위를 조절, 칸반은 WIP를 고정하고 시간을 조절한다.**
- **콘웨이의 법칙: 조직의 소통 구조가 곧 아키텍처가 된다 — 원하는 아키텍처면 조직부터 그 모양으로.**
- **조직 모델은 복사하는 게 아니라 "무슨 문제 때문에 필요한가"에서 도출한다.**
- **혼자·소규모에선 동기화 장치(데일리·속도·역할)는 버리고 학습 장치(회고·DoD·작은 증분·WIP 제한)를 살린다. 그중 회고가 가장 중요하다.**

## 용어 풀이

- **애자일(Agile)** — 짧은 주기로 만들고 피드백받아 고쳐가는 개발 방식의 총칭. 특정 방법론 이름이 아니다.
- **폭포수(Waterfall)** — 요구분석 → 설계 → 구현 → 테스트를 순서대로 한 번씩 밟는 방식.
- **이터레이션(Iteration)** — 반복 주기 하나.
- **스프린트(Sprint)** — 스크럼에서 쓰는 이터레이션의 이름. 보통 1~4주로 길이를 고정한다.
- **백로그(Backlog)** — 해야 할 일의 목록. 우선순위 순으로 정렬된다.
- **유저 스토리(User Story)** — 사용자 관점에서 쓴 요구사항 한 줄("As a … I want … So that …").
- **에픽(Epic)** — 여러 스토리로 쪼개지는 큰 단위.
- **INVEST** — 좋은 유저 스토리의 6조건(Independent·Negotiable·Valuable·Estimable·Small·Testable).
- **DoD(Definition of Done)** — "끝났다"의 정의. 팀이 합의한 완료 기준.
- **증분(Increment)** — 한 주기의 결과물. DoD를 만족해야 증분으로 인정한다.
- **속도(Velocity)** — 한 스프린트에 처리하는 작업량의 실측값.
- **번다운 차트(Burndown Chart)** — 남은 작업량이 줄어드는 추이 그래프.
- **회고(Retrospective)** — 주기 끝에 "무엇을 개선할지" 논의하는 자리. 제품이 아니라 프로세스를 다룬다.
- **WIP(Work In Progress)** — 동시에 진행 중인 작업의 수. 칸반에서 이 수를 제한한다.
- **리드 타임(Lead Time)** — 작업이 대기에 들어와 완료까지 걸린 총 시간.
- **스쿼드(Squad)** — 한 제품 영역을 끝까지 책임지는 6~12명 교차기능 팀.
- **트라이브(Tribe)** — 관련 스쿼드들의 묶음(~100명).
- **챕터(Chapter)** — 같은 직군의 사람들을 스쿼드 가로질러 묶은 단위. 기술 표준을 유지한다.
- **길드(Guild)** — 관심사 기반 자발적 모임. 조직 전체를 가로지른다.
- **교차기능(Cross-functional)** — 기획·개발·QA 등 필요한 역할이 팀 안에 다 있는 상태.
- **콘웨이의 법칙(Conway's Law)** — 시스템을 설계하는 조직은 그 조직의 소통 구조를 닮은 설계를 만든다.
- **역 콘웨이 전략(Inverse Conway Maneuver)** — 원하는 아키텍처를 얻으려 조직을 먼저 그 모양으로 바꾸는 것.
- **분산 모놀리스(Distributed Monolith)** — 서비스는 쪼갰으나 서로 얽혀 독립 배포가 안 되는 상태.
- **ADR(Architecture Decision Record)** — "왜 이렇게 결정했는가"를 남기는 짧은 문서.

## [Claude 추가] 더 알면 좋은 것

> 아래는 원고에 없던 배경 지식이다. 복습 시 본문(원고)과 섞어 인출하지 않는다.

- **애자일 선언은 2001년 미국 유타 스노우버드에서 17명이 모여 서명했다.** 그전에 XP·스크럼·크리스털 등 "가벼운(lightweight)" 방법론들이 따로 있었고, 이들이 공통점을 모아 "애자일"이라는 우산 이름을 붙인 것이다. 그래서 애자일은 하나의 방법론이 아니라 **여러 방법론의 공통 가치**다.

- **칸반은 도요타 생산방식(TPS)에서 왔다.** 원래 공장에서 "다음 공정이 당겨갈 때만 만든다"는 신호 카드가 칸반(看板)이다. 소프트웨어 칸반의 WIP 제한·흐름 관리는 이 제조업 린(lean) 사고를 옮긴 것이다.

- **WIP를 줄이면 왜 빨라지나 — 리틀의 법칙(Little's Law).** `평균 리드타임 = 평균 WIP ÷ 평균 처리율`. 처리율이 그대로면 WIP(동시 진행)를 줄일수록 리드타임이 짧아진다. "하나씩 끝내라"는 감이 아니라 이 식의 결론이다. *(간단화한 진술 — 정상 상태 가정)*

- **콘웨이를 실무 설계 도구로 정리한 책이 있다 — *Team Topologies*(Matthew Skelton·Manuel Pais, 2019).** 스트림 정렬 팀·플랫폼 팀 등 네 가지 팀 유형과 상호작용 방식을 제시하며, "역 콘웨이 전략"을 조직 설계의 1급 수단으로 다룬다. 스쿼드 모델의 현대적 후계 논의로 볼 수 있다.

- **대규모 스케일 프레임워크(SAFe·LeSS 등)도 있다.** 여러 팀이 한 제품을 함께 만들 때 스크럼을 조직 전체로 확장하는 틀인데, 무게가 커서 "애자일의 관료화"라는 비판도 받는다 — 규모가 커질수록 애자일의 원래 목적(빠른 학습)과 멀어지기 쉽다는 점을 상기시킨다. *(세부 채택 현황은 확인 필요)*
