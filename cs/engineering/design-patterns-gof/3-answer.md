## 정답

### A. 전체 지도

#### 1. (연결) 세 분류와 각 관심사

- **생성(Creational, 5개)** — 객체를 **어떻게 만드는가**(생성 책임을 어디에 두나).
- **구조(Structural, 7개)** — 객체를 **어떻게 조합하는가**(인터페이스를 맞추고 감싸고 트리로 묶는다).
- **행위(Behavioral, 11개)** — 객체가 **어떻게 협력하는가**(책임을 넘기고 상태·알고리즘을 갈아끼운다).

#### 2. (판단) 무엇을 판단할 수 있으면 아는 것인가

23개 암기가 아니라, 이 네 가지를 판단할 수 있으면 안다고 할 수 있다.

- 지금 이 문제에 **어떤 패턴이 답인가**.
- 이 패턴을 쓰면 **무엇을 얻고 무엇을 잃는가**.
- 지금은 오히려 **쓰지 말아야 할 때**가 아닌가.
- 프레임워크(Spring)가 **이미 대신 해주고 있지** 않은가.

### B. 개념·판단

#### 3. (판단) 먼저 적용 vs 리팩토링 끝에 도달

- **리팩토링하다 결과적으로 도달하는 쪽이 건강하다.** "정석을 배우고, 정석을 잊어라"와 같은 태도다("Refactoring to Patterns").
- 왜: 패턴은 **변화 축이 실제로 존재할 때만** 값을 한다. 먼저 알고 적용하면 필요 없는 곳에 패턴을 욱여넣는 **과용**이 나온다(구현체 하나뿐인 인터페이스 등). 좋은 리팩토링의 종착지가 패턴과 겹치는 것이 자연스러운 순서다.

#### 4. (연결) Spring이 대신 해주는 패턴 / DI가 Factory·Singleton을 흡수한 방식

| 패턴 | Spring에서 |
|---|---|
| Singleton | 기본 빈 스코프 |
| Factory / Abstract Factory | `ApplicationContext`, `@Configuration` |
| Proxy | AOP(`@Transactional`, `@Cacheable`), Feign |
| Observer | `ApplicationEventPublisher`, `@EventListener` |
| Chain of Responsibility | Security Filter Chain, `HandlerInterceptor` |
| Template Method | `JdbcTemplate`·`RestTemplate` 등 `*Template` 전부 |
| Strategy | `List<Interface>` 주입 후 `supports(...)`로 선택 |

- **DI 컨테이너의 흡수**: 의존성 주입은 사실상 **Factory + Singleton + Service Locator**를 프레임워크 레벨로 끌어올린 것이다. 컨테이너가 인스턴스 생성(Factory)과 단일 인스턴스 관리(Singleton, 기본 스코프)를 대신하므로, 현대 Java에서 이 세 패턴을 손으로 짤 일이 거의 사라졌다.

#### 5. (경계) 패턴 과용의 냄새

- **구현체가 하나뿐인 인터페이스**, **한 번도 교체되지 않은 Strategy**, 이름만 `~Factory`·`~Manager`인 클래스가 "패턴을 위한 패턴"의 징후다.
- 알아채는 법: 그 패턴이 여는 **변화 축(교체·확장)이 실제로 존재하는지** 묻는다. 축이 없는데 추상화만 있으면 순수 오버헤드다.

#### 6. (판단) State vs `enum + switch` — 결제 상태 전이엔?

- 갈리는 지점: 상태 전이 규칙이 **여러 곳에 복사되거나** 상태별 행동이 복잡하면 State, 분기가 단순하고 한곳이면 `enum + switch`로 충분하다.
- **결제 상태 전이엔 State가 맞다.** 왜: 전이 규칙이 **한 곳에 모이고**, `if (status == APPROVED || …)` 조건이 곳곳에 복사되는 것을 막으며, 상태가 추가되면 **컴파일러가 빠진 곳을 알려주고**, 종료 상태(SETTLED 등)에서 전이를 부르면 그 자리에서 예외로 막힌다. Java에선 `enum + 추상 메서드`(기본은 전부 "허용 안 함", 허용 전이만 오버라이드)가 실용적이다.

#### 7. (경계) 상속 기반 패턴(Template Method) vs 합성 우선 충돌?

- 정면 충돌이라기보다 **트레이드오프**다. Template Method는 상속, Strategy는 합성이며 **일반적으로 Strategy(합성)가 더 유연**하다(런타임 교체 가능).
- Template Method가 여전히 정당한 경우: 알고리즘 **뼈대를 `final`로 고정**하고 일부 단계만 채우는 재사용이 명확할 때. 대가로 컴파일 시점 고정, 상위가 하위를 부르는 **역전된 제어 흐름(할리우드 원칙)**의 디버깅 부담을 안는다. 즉 합성 우선이 기본값이고, 뼈대 공유 이득이 분명할 때만 상속을 쓴다.

#### 8. (연결) sealed interface + 패턴 매칭 switch가 대체하는 것

- **Visitor를 대체한다.**
- 더 나은 이유: 컴파일러가 `permits` 목록을 근거로 **모든 케이스를 다뤘는지 검사**(완전성)해주므로, Visitor의 장점(타입 안정 + 새 연산 추가)을 얻으면서 이중 디스패치 보일러플레이트가 사라져 코드가 훨씬 짧다.

### C. 혼동쌍

#### 9. (경계) Strategy ↔ State

- **"누가 바꾸는가"로 가른다.** Strategy는 **클라이언트가** 알고리즘을 고르고 전략끼리 서로 모른다. State는 **객체 스스로** 상태를 전이하고 상태끼리 다음 상태를 안다.

#### 10. (경계) Decorator ↔ Proxy

- **"의도"로 가른다.** 구조는 거의 같다. Decorator는 **기능 추가**, Proxy는 **접근 제어**(지연 로딩·권한·캐싱·원격).

#### 11. (경계) Adapter ↔ Bridge — 한 단어 "시점"

- Adapter는 **사후**(이미 있는 것을 나중에 맞춘다), Bridge는 **사전**(처음부터 두 축이 따로 자랄 것을 예상하고 분리한다).

#### 12. (경계) Factory Method ↔ Abstract Factory / `Money.of(1000)`은 왜 둘 다 아닌가

- Factory Method = **객체 하나**의 생성을 서브클래스가 결정. Abstract Factory = **제품군(세트)**을 일관되게 생성.
- `Money.of(1000)`은 **정적 팩토리 메서드**로, 둘 다 아니다 — 서브클래스에 생성 책임을 위임(FM)하지도, 제품군 세트를 만들지도(AF) 않는다. 그저 `new` 대신 쓰는 관용법(이름 부여·캐싱·하위타입 반환)일 뿐이다.

#### 13. (경계) Facade ↔ Mediator — 방향

- Facade는 **단방향**(클라이언트 → 하위 시스템, 단순 진입점 제공). Mediator는 **양방향**(참여자들이 중재자를 통해 서로 소통, N:N을 1:N으로).

### D. 함정·안티

#### 14. (예측) 상태를 가진 Singleton이 위험한 이유

- **전역 변수와 사실상 같아진다.** 그 결과 테스트 간 상태가 새고 동시성 문제가 생긴다. 빈으로 만들되 **상태를 두지 않는 것**이 안전하다.

#### 15. (왜) Builder의 진짜 가치와 감수하는 단점

- 진짜 가치: 인자 순서 헷갈림 방지가 아니라, **`build()` 시점에 필수값·불변식을 한 번에 검증**하는 것.
- 감수하는 단점: **필수값 누락을 컴파일 시점에 못 잡는다**(런타임에야 터진다). 그래서 필드가 3~4개 이하로 전부 필수면 생성자가 낫다.

#### 16. (예측) `Cloneable`/`clone()`의 버그 원천과 안전한 대안

- 버그 원천: `clone()`은 **얕은 복사**라 내부 참조를 원본과 공유한다 → 복사본을 고치면 원본도 바뀐다.
- 안전한 대안: **복사 생성자나 `with` 메서드**. 값 객체를 불변으로 만들면 "일부만 바꾼 새 인스턴스"(`withCutOff(...)`)가 자연히 이 형태가 된다.

#### 17. (왜) 자기 자신 내부 호출 시 `@Transactional`이 안 걸리는 이유

- Spring AOP 프록시는 **"바깥에서 들어오는 호출"만 가로챈다.** 같은 클래스 안에서 `this.someTransactionalMethod()`를 부르면 프록시를 거치지 않고 실제 객체를 직접 호출하므로, 트랜잭션 어드바이스가 붙지 않는다(자기 호출 함정).

#### 18. (예측) Decorator를 여러 겹 쌓으면 잃는 것 / 선언적 대안

- 잃는 것: **스택 트레이스가 깊어지고 흐름을 따라가기 어려워진다.**
- 선언적 대안: **Spring AOP** — 같은 효과(로깅·멱등성 등 횡단 관심사)를 애너테이션으로 선언적으로 얻는다.

#### 19. (왜) Observer에서 `AFTER_COMMIT`이 필요한 이유 / 남는 유실과 Outbox

- `AFTER_COMMIT`인 이유: 트랜잭션 커밋 **전에** 이벤트를 처리하면 **롤백됐는데 알림이 나가는** 사고가 생긴다.
- 남는 유실 위험: 커밋 후 발행은 **원자적이지 않다** — 커밋 성공 + 발행 실패 = 이벤트 유실.
- 해법 **Outbox 패턴**: 이벤트를 별도 outbox 테이블에 **같은 트랜잭션으로 함께 저장**하고, 별도 프로세스가 그걸 읽어 발행한다. "커밋됐는데 발행 못 함"을 막는다.

#### 20. (경계) Memento로 되돌릴 수 있는 것/없는 것 / `previousStatus`가 조잡한 이유

- 되돌릴 수 있는 것: **메모리 상의 내부 상태**(스냅샷 복원). 되돌릴 수 없는 것: **이미 외부 시스템에 반영된 것**(분산 트랜잭션의 보상과는 다르다).
- `previousStatus` 롤백 필드가 조잡한 이유: 도메인 모델 안에 **되돌리기라는 다른 관심사(롤백용 필드)를 섞어** 넣은 형태이고, 게다가 외부 반영분은 어차피 못 되돌린다. 별도 스냅샷 객체로 분리하거나 애초에 **분산 트랜잭션(보상) 설계**로 푸는 것이 맞다.

#### 21. (판단) Visitor의 트레이드오프와 적합 구조

- ✅ **연산 추가는 쉽다**(새 Visitor 클래스만 추가). ❌ **타입 추가는 어렵다**(모든 Visitor를 고쳐야 한다).
- 그래서 **타입은 안정적이고 연산이 자주 늘어나는 구조**에만 쓴다. (그마저 Java 17+에선 sealed + 패턴 매칭 switch가 더 낫다 — 8번.)

#### 22. (판단) CoR가 "규칙이 계속 느는 곳"에 맞는 이유 — OCP

- **규칙 추가 = 클래스(핸들러) 하나 추가**로 끝나고 기존 코드는 건드리지 않는다. 이것이 곧 OCP(확장에 열림, 수정에 닫힘)다. 순서는 `@Order`로 준다.
- 그래서 승인 규칙(카드 상태 → 한도 → 잔액 → 가맹점 제한 → 이상거래)처럼 검증 규칙이 계속 붙는 곳에 잘 맞는다.

#### 23. (연결) 상태 전이 규칙을 상태 객체에 두면 얻는 두 이점

1. **전이 규칙이 한 곳에 모인다** — `if (status == …)` 조건이 곳곳에 복사되는 것을 막는다.
2. **컴파일러가 빠진 곳을 잡아준다** — 상태가 추가되면 처리하지 않은 곳을 컴파일러가 알려준다.

### E. 우선순위

#### 24. (판단) 현장 우선순위 "높음" 네 패턴과 적용처

| 패턴 | 붙는 문제 |
|---|---|
| **State** | 결제 라이프사이클 상태 전이(승인 → 매입 → 정산, 각종 취소) |
| **Strategy** | 수수료 정책·정산 주기·취소 유형별 처리("경우마다 계산법이 갈리는 곳") |
| **Adapter** | 헥사고날 인프라 계층 전체(리포지토리·외부 API 어댑터) |
| **Chain of Responsibility** | 승인 규칙 체인(규칙이 계속 늘어나는 곳) |
