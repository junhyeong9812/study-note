# testing/17-characterization-tests-legacy — 정답

## 정답

### 1. 왜 "맞는 동작" 테스트부터 쓰기 어렵나

- 맞는 동작이 무엇인지 적힌 곳이 없다. 아는 사람도 떠났을 수 있다. 명세 테스트는 기대값의 출처(명세)가 있어야 쓸 수 있다.
- Feathers(WELC 머리말): "legacy code is simply code without tests". 테스트가 있으면 동작을 빠르고 검증 가능하게 바꿀 수 있고, 없으면 코드가 나아지는지 나빠지는지 모른다.
- Feathers(2016 블로그): 시스템이 운영에 들어가면 그 시스템이 자기 자신의 명세가 된다. 옳다고 생각하든 아니든, 기존 동작을 바꾸고 있는지는 알아야 한다. 그래서 먼저 **현재 동작**을 고정한다.

### 2. 기대값의 출처

| | 기대값의 출처 | 답하는 질문 |
|---|---|---|
| 명세 테스트 | 명세·요구사항 | 맞는가? |
| 특성 테스트 | 코드를 실행해 관찰한 값 | 바뀌었나? |

### 3. 특성 테스트 절차

1. 코드를 테스트 하네스에서 돌릴 수 있게 한다(필요하면 이음새).
2. 기대값 자리에 일부러 틀린 값을 둔다: `assertEquals("?", line("SILVER", 101, 9.99))`.
3. 돌린다. 실험 A의 메시지: `expected: <?> but was: <S|101|-41>`.
4. 실제 값을 기대값으로 옮긴다: `assertEquals("S|101|-41", …)`. 배운 것을 이름에 적는다(예: `silverBulkDiscountCanMakeTotalNegative`).
5. 바꿀 부분 근처의 다른 입력으로 반복한다.

- 실패 메시지가 알려 준 것: 대량 할인(1000)이 총액보다 커서 청구액이 음수가 되는 숨은 동작.

### 4. 손 테스트 3개 vs 골든 마스터

| | 손 테스트 3개 | 골든 마스터 105줄 |
|---|---|---|
| A(메서드 추출) | 통과 | 통과(0줄 다름) |
| B(BigDecimal + 음수 방지) | 통과 — **못 잡음** | 실패 — 15줄 다름 |

- 손 테스트는 수량 100 미만이라 대량 할인·음수 경로를 지나지 않는다.
- 골든 마스터의 수량 차원(0·1·10·11·99·100·101)은 `>= 100` 경계 양쪽을 덮어 음수 경로를 지났다. 15줄 전부 "음수 → 0" 변화였다.

### 5. 차이 0줄의 의미

- 안 된다. 105조합에 정확히 .5인 총액이 17개 있었지만, 양수 .5(14개)에서는 `Math.round`와 `HALF_UP`이 같은 값을 낸다. 둘이 갈리는 음수 .5 3개(예: BRONZE,101,0.5 = -949.5 → `Math.round` -949, `HALF_UP` -950)는 B의 음수 방지가 0으로 덮어 "음수 → 0" 줄에 묻혔다. `double` 표현 오차가 경계를 넘는 값(x.xx5)은 조합에 없었다.
- 골든 마스터는 깐 입력 안에서만, 그리고 다른 변화에 가려지지 않은 변화만 잡는다.
- 폭 점검:
  1. 골든 마스터를 돌린 상태의 커버리지를 보고, 바꿀 메서드의 덮이지 않은 분기에 맞는 입력을 추가한다.
  2. 바꿀 코드에 일부러 작은 변화(연산자·상수·반올림 모드)를 넣어 골든 마스터가 잡는지 본다 — 변이 테스트의 생각.
- 그리고 바꾸는 부분의 경계(.5 근처, 0, 음수, 최댓값)를 입력 차원에 넣는다.

### 6. 승인 직후 전부 다름

- 출력에 실행마다 바뀌는 숨은 입력이 섞였다. 시각·UUID·난수·해시 순회 순서를 의심한다. 실험 C는 `issued=12:45:06.517203056` 같은 발행 시각 때문에 105줄 전부 달랐다.
- 스크러버(비교 전 정규식으로 `issued=<TIME>`으로 바꿈)
  - 장점: 레거시 코드를 고치지 않는다. 실험 C에서 적용하자 통과했다.
  - 단점: 그 필드의 동작(형식·시간대)은 검증하지 못한다.
- 이음새(시계 주입 후 고정 시계)
  - 장점: 시각 필드까지 결정적으로 검증한다.
  - 단점: 레거시 코드에 생성자 인자·팩토리 같은 변경이 필요하다. 그 변경 자체도 안전하게 해야 한다.

### 7. 분리·감지와 이음새

- 분리: 하네스에서 돌릴 수 없게 하는 의존(`Database.connect()`)을 테스트용 가짜로 갈아 끼운다.
- 감지: 밖으로 나가 버리는 결과(메일 전송)를 가짜 `Mailer`로 붙잡아 값을 확인한다.
- 이음새(WELC 4장): "그 자리를 편집하지 않고도 프로그램의 동작을 바꿀 수 있는 곳". SWE@G 13장도 테스트 더블을 쓸 수 있게 하는 방법으로 정의하고, 의존성 주입을 흔한 기법으로 든다.
- 분리·감지라는 두 이유는 WELC 3장 제목(Sensing and Separation)과 같다. 3장 본문은 미열람이라 풀이는 이 노트의 요약이다.
- seam 종류, enabling point, 인터페이스 추출·매개변수화·sprout·wrap 같은 기법은 software-design/51-legacy-change-techniques로 넘긴다.

### 8. 버그를 지키는 특성 테스트

- 바로 고치지 않는다. 특성 테스트는 원래 현재 동작(버그 포함)을 기록한다.
- Feathers(2016)가 경계하는 상황: 개발자가 버그라 여긴 동작을 사용자는 기능으로 여기고 기대고 있을 수 있다.
- 처리 순서:
  1. 그 동작에 기대는 사용자·하위 시스템(예: 음수 청구를 상계·환불로 쓰는 정산)이 있는지 확인한다.
  2. 고치기로 결정하면, 동작 변경 커밋에서 그 특성 테스트의 기대값을 의도적으로 바꾸고 이유를 적는다.
  3. 리팩터링(동작 보존) 커밋과 섞지 않는다.

### 9. 승인 피로

- 잘못: 한 단계에 동작 보존과 동작 변경을 섞어 diff가 커졌고, 사람이 diff를 읽지 않고 승인해 골든 마스터가 안전망 역할을 잃었다.
- 단계 나누기:
  1. 동작 보존 단계 — 골든 마스터 diff가 0줄이어야 한다. 0줄이 아니면 그 단계를 되돌리고 더 작게 한다.
  2. 동작 변경 단계 — 의도한 변화만 diff에 나와야 한다. 그 diff를 읽고 승인한다.
- 출력 형식을 줄마다 입력과 결과가 함께 보이게(`SILVER,101,9.99 -> S|101|-41`) 만들어 diff를 읽기 쉽게 한다.
