# testing/09-flaky-tests — 정답

## 정답

### 1. 가끔 빨강이 없는 것보다 나쁠 수 있는 이유

- 빨강이 거짓 신호로 자주 오면, 사람들은 빨강 자체를 무시하게 된다. 그러면 진짜 회귀의 빨강도 같이 무시된다.
- SWE@G 11장: 테스트마다 0.1%만 잘못 실패해도 하루 1만 개면 하루 10건을 조사해야 한다. 불안정 비율이 1%에 가까워지면 테스트가 가치를 잃기 시작한다는 것이 저자들의 경험이다.
- Google Testing Blog(2016): 테스트 실행의 약 1.5%가 flaky 결과였고, 통과→실패 전이의 약 84%에 불안정 테스트가 끼어 있었다. 실패 대부분이 "진짜인지부터 따져야 하는" 실패였다는 뜻이다.
- 테스트가 없으면 비용은 "결함을 못 잡음"이다. 불안정 테스트는 그 비용에 "조사 시간 + 신뢰 상실"을 더한다.

### 2. 원인 분류

| 순위 | 범주 | 161건 중 |
|---|---|---|
| 1 | Async Wait | 74 (45%) |
| 2 | Concurrency | 32 (20%) |
| 3 | Test Order Dependency | 19 (12%) |

- 나머지 일곱(합 36건): Resource Leak · Network · Time · IO · Randomness · Floating Point · Unordered Collections.
- 숨은 입력 예:
  - Time → 시스템 시각(UTC 자정이 바뀌는 순간, 플랫폼별 시각 정밀도).
  - Network → 원격 연결 성공 여부, 로컬 소켓 상태.
  - Unordered Collections → 해시 순회 순서.
  - Randomness → 난수 값(논문 예: 1바이트 난수가 정확히 0일 때만 실패).

### 3. 순서 의존 예측

- `startsEmpty`만 공유 상태에 민감하다. 세 테스트 중 `startsEmpty`가 첫 자리에 올 때만 통과한다.
- 세 자리 중 첫 자리일 확률은 1/3이므로 기대 실패율은 2/3, 20번이면 13번 안팎이다.
- 실험 A 결과: 시드 1~20 중 12번 실패. 기본 순서에서도 이 환경에서는 피해자가 마지막에 돌아 실패했다.
- `@BeforeEach`로 `Cart.items.clear()`를 하면 20번 모두 통과했다(0/20).

### 4. sleep 대기 예측

- 부하가 늘수록 작업 스레드가 CPU를 덜 받아 30ms 작업이 50ms를 넘는다. sleep 판의 실패가 늘어난다.
- 실험 B(조건마다 2번 + 사실 점검 재실행 3번): 부하 0개 → 50번 중 0~4회, 부하 2개 → 8~15회, 부하 4개 → 30~32회 실패. 실행마다 수치는 다르다.
- `Future.get(5, SECONDS)` 판은 모든 실행에서 0회였다. 끝났다는 신호를 기다리므로 작업 시간이 늘어도 상한(5초) 안이면 통과한다. 상한을 넘을 만큼 느린 머신이라면 이 판도 실패할 수 있다(Luo 5.1.1: 상한 있는 waitFor 수정은 확률을 낮춘 것으로 분류).
- 덤: 무부하에서 sleep 판이 오히려 더 느렸다(50회 약 4.0초 vs 약 1.9~2.1초). 작업이 일찍 끝나도 50ms를 다 쉬기 때문이다.

### 5. Surefire 재시도의 결과

- 한 번이라도 통과했으므로 그 테스트는 flaky로 세고 **빌드는 성공**한다.
- 요약 줄: `[WARNING] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0, Flakes: 1`, 그리고 `BUILD SUCCESS`. 그 위에 `Run 1: … expected …`·`Run 2: …`·`Run 3: PASS`가 찍힌다(실험 C 출력).
- 진짜 결함을 가리는 조건: 결함이 확률적으로만 드러날 때다. 경쟁 조건이 대표적이다. 실험 C에서 동기화 없는 카운터는 재시도 없이 12번 중 9번 빌드를 깼다. 재시도 3회를 켜자 6번 모두 초록이었다(사실 점검 재실행도 같은 결과).
- 막는 법: `Flakes`를 수집해 실패처럼 다룬다. surefire 3.0.0-M6+의 `failOnFlakeCount`로 상한을 둔다.

### 6. JUnit 5 기본 순서

- 무작위가 아니다. User Guide 2.11: "deterministic but intentionally nonobvious" — 결정적이지만 일부러 드러나지 않는 알고리즘이다.
- 그래서 순서 의존 결함이 있어도 기본 순서가 우연히 피해자를 먼저 돌리면 매번 초록이다.
- 깨지는 경로: 테스트 메서드를 추가·이름 변경하면 순서가 바뀔 수 있다. 피해자 앞에 오염자가 오면 그날부터 실패한다. Luo 3.2절도 나중에 불안정해진 23건의 첫째 원인으로 "격리를 깨는 새 테스트 추가"를 든다. JDK를 올려 순서가 바뀐 예로, 논문은 Java 6→7에서 리플렉션 변화로 JUnit이 찾는 테스트 순서가 바뀐 일을 든다.
- 드러내는 도구: `MethodOrderer.Random` + `junit.jupiter.execution.order.random.seed`로 시드를 남긴다.

### 7. 격리에 대한 경고

- 불안정 테스트 수정의 24%가 제품 코드도 고쳤고, 그중 94%가 버그 수정이었다. 불안정 테스트가 제품 코드 버그의 증상인 경우가 적지 않다. 격리하면 그 버그의 유일한 신호를 끄게 될 수 있다.
- Google 글(2016)도 격리가 "진짜 경쟁 조건이나 다른 버그를 쉽게 가릴 수 있다"고 적는다.
- 격리할 때 붙일 조건:
  1. 담당자와 버그 티켓(Google은 격리하면서 버그를 등록한다).
  2. 기한·상한(Fowler 예: 격리 8개까지 또는 최대 1주).
  3. 격리 스위트도 계속 돌리고 실패율을 측정한다 — 고쳐졌는지 확인하고, 제품 코드 결함부터 의심한다.

### 8. 단독 통과·전체 실패 진단

- 범주: 순서 의존(공유 상태). 메모리 정적 필드, 공유 파일·DB 행·포트 같은 외부 자원을 의심한다.
- 오염자 찾기(이분 탐색):
  1. 전체 실행 순서를 기록하고(시드 고정), 피해자 V 앞에 돈 테스트 목록 P를 얻는다.
  2. P를 반으로 나눠 "앞 절반 + V"를 돌린다.
  3. V가 실패하면 앞 절반에, 통과하면 뒤 절반에 오염자가 있다. 그쪽 절반으로 범위를 줄여 반복한다.
  4. 오염자가 하나면 200개 기준 8번(log₂200 ≈ 7.6) 안팎으로 하나가 남는다.
- 고치기: 오염자가 상태를 원래대로 돌리게 하거나, 피해자가 필요한 상태를 스스로 준비하게 한다(`@BeforeEach`, `@TempDir`, 테스트별 키).

### 9. 확률 계산

- 아니다. 50번 모두 통과는 "실패율이 낮다"는 증거일 뿐이다. 3의 규칙으로 95% 신뢰 상한은 약 3/50 = 6%다.
- 실패율 0.5, 재시도 3회(총 4번 시도) → 끝내 실패할 확률은 0.5⁴ = 1/16 ≈ 6%. 나머지 15/16은 초록으로 넘어간다.
- 단, 이 계산은 시도들이 독립이라고 가정한다. 실험 C에서는 재실행이 데워진 같은 JVM에서 훨씬 짧게 끝났다(0.250s → 0.009s). 그래서 재시도 성공 확률이 독립 가정보다 높을 수 있다고 추정한다.
