# testing/10-testing-time-and-concurrency — 정답

## 정답

### 1. 시계를 직접 읽으면 "오늘"만 시험한다

- 현재 시각이 시그니처에 안 보이는 숨은 입력이다. 테스트가 그 입력을 바꿀 수 없으니, 테스트를 돌린 날짜의 경우만 확인된다.
- `Clock` javadoc(Java SE 21): 애플리케이션은 정적 메서드 대신 객체로 현재 시각을 얻어야 테스트가 쉬워진다. 모범 사례는 현재 시각이 필요한 메서드에 `Clock`을 넘기는 것이고, DI 프레임워크가 그 한 방법이다.
- SWE@G 13장 「Determinism」: 시스템 시계 대신 특정 시각을 하드코딩한 테스트 더블을 쓸 수 있다.

### 2. 시계 세 가지

| 종류 | 맞는 테스트 |
|---|---|
| `Clock.fixed` | 특정 시점의 판정 — 말일·윤일·DST 전날의 결과 |
| `Clock.offset` | 기준 시계에서 일정 시간 뒤의 상대 시점 |
| 가변 시계(직접 구현) | 시간이 흐르는 동작 — 만료·타임아웃·주기 작업. `advance()`로 경계(1999ms/2000ms)를 찍는다 |

- `Clock` javadoc은 모든 구현이 스레드 안전해야 한다고 요구한다. 여러 스레드가 읽는 가변 시계라면 필드를 `volatile`·`AtomicReference` 등으로 보호해야 한다.

### 3. 자정 예측

- 12:00:00 시작 → 두 읽기 모두 2026-10-03 → PASS.
- 23:59:59.999 시작 → 운영 코드는 10-03, 테스트는 1ms 뒤 10-04를 읽어 FAIL(실험 A 출력 그대로).
- 교훈: 기대값을 `now()`로 다시 계산하지 말고, 고정 시계 + 리터럴(`LocalDate.of(2026, 10, 3)`)로 적는다.

### 4. 1년 훑기

- `plusMonths(1)`은 다음 달에 그 날이 없으면 말일로 맞춘다. 실패는 7일: 2026-01-29·30·31, 03-31, 05-31, 08-31, 10-31(실험 B).
  - 12월 31일은 다음 달 1월에 31일이 있어 실패하지 않는다.
- 09:00 기준 `plusHours(24) != plusDays(1)`:
  - 서울: 0일(DST 없음).
  - 뉴욕: 2026-03-07, 2026-10-31 — DST 시작(3-08)과 끝(11-01) 전날이다.
- 서울에서만 돌리는 테스트는 DST 결함을 볼 수 없다. 시간대를 테스트 매개변수로 넣어야 한다.

### 5. 수동 스케줄러

- (마감 시각, 등록 일련번호) 순으로 정렬한 우선순위 큐(이진 힙)에 보관한다. `advanceBy(d)`는 마감이 지난 작업을 순서대로 꺼내 실행한다.
- 같은 마감이면 일련번호가 작은 것(먼저 등록된 것)부터 실행해 순서가 매번 같다.
- 실제 스케줄러는 실제 시간과 OS 스케줄링을 쓴다. "99ms에 아직 없음"을 확인하려면 99ms 근처에서 상태를 읽어야 하는데, 읽는 시점 자체가 몇 ms 흔들린다. 허용 오차를 두면 경계를 못 보고, 오차를 줄이면 불안정해진다.
- 실험 D: 수동 판은 99ms 시점 `[실패#1→100ms 뒤]`, 100ms 시점에 `실패#2`가 추가됨을 정확히 보였다. 실제 판은 723~744ms, 수동 판은 6.12~11.46ms 걸렸다(7번 실행 범위).

### 6. check-then-act 예측

- 출발선이 없으면 스레드가 순서대로 시작해 앞 스레드가 먼저 끝나는 경우가 많다. 겹침이 적어 노출이 낮다.
- 실험 E(7번 실행 범위): 출발선 없음 55~96회, 출발선 있음 169~243회, `computeIfAbsent` 0회(7번 모두). 출발선이 노출을 약 1.8~3.4배 늘렸다.
- 0회는 이 조건에서 안 보였다는 뜻이다. 안전의 근거는 `ConcurrentHashMap.computeIfAbsent` javadoc의 "The entire method invocation is performed atomically"다.

### 7. 스트레스 vs 강제 끼어들기

- 스트레스: 어디가 위험한지 몰라도 찾을 수 있다. 대신 확률적이라 드물게만 드러나고(실험 E에서 출발선이 있어도 약 8~12%), 통과가 안전을 증명하지 않는다.
- 강제 끼어들기: 아는 위험 구간을 결정적으로 1번에 재현한다(실험 E `created=2`). 대신 그 구간을 사람이 알아야 하고, 이음새(테스트 훅)를 코드에 둬야 한다.
- 끼어들기 수: C(20, 10) = 184,756. 무작위 반복은 그중 일부만 본다. Lincheck의 모델 체킹처럼 제한된 범위를 체계적으로 훑는 도구가 이 틈을 메운다.

### 8. 주기 작업이 조용히 멈춤

- 계약: `scheduleAtFixedRate` javadoc — 작업 실행이 예외를 던지면 반환된 `Future`의 `get`이 `ExecutionException`을 던지고 "이후 실행은 억제된다". 예외가 `Future` 안에 갇혀 로그가 없을 수 있다.
- 테스트가 놓친 이유: 수동 스케줄러가 예외 뒤에도 다음 실행을 이어 가도록 짜여 실제 계약과 달랐다.
- 고치기:
  - 코드: 작업 본문을 `try/catch`로 감싸 예외를 기록하고 다음 주기를 살린다(또는 실패를 알림으로 올린다).
  - 테스트: 가짜 스케줄러에 "예외 시 이후 실행 중단" 계약을 반영하고, 예외를 던지는 작업 시나리오를 추가한다. 가짜와 실제 실행기를 같은 계약 테스트로 함께 검증한다.

### 9. 고정 시계 + 타임아웃 루프

- `while (clock.instant().isBefore(deadline))`류 루프는 시간이 흘러야 끝난다. `Clock.fixed`는 시간이 흐르지 않으므로 루프가 끝나지 않는다(예시 추론, 실험 안 함).
- 고치기:
  - 시간이 흘러야 하는 동작은 가변 시계로 시험하고, 루프가 기다리는 지점(sleep·poll)을 테스트가 제어하는 훅이나 스케줄러로 바꿔 그 안에서 시계를 진행시킨다.
  - 테스트에 `@Timeout`을 걸어 멈춤을 빠른 실패로 바꾼다(JUnit 5 User Guide 2.21).
