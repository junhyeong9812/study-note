# testing/16-coverage-and-its-limits — 정답

## 정답

### 1. 낮을 때와 높을 때

- 낮다: 테스트가 아예 실행하지 않는 코드가 어디인지 정확히 안다. 그 부분은 자동 테스트로 검증되지 않는다는 확실한 신호다.
- 높다: 코드가 실행됐다는 것만 안다. 결과를 단언했는지, 경계값을 시험했는지, 빠진 요구사항이 있는지는 모른다.
- Google Testing Blog(2020): 높은 커버리지는 품질을 보장하지 않지만, 낮은 커버리지는 넓은 영역이 테스트되지 않음을 보장한다.

### 2. CFG와 분기 수

```text
  (amount < 0)? ─T→ throw
     │F
  (vip)? ─F──────────────┐
     │T                  │
  (amount >= 100000)? ─F─┤
     │T                  ▼
  return 10%      (amount >= 50000)? ─T→ return 5%
                         │F
                    return amount
```

- 결정점 4개 × 2 = 분기 8개(실험 `jacoco.csv`의 BRANCH 합계 8).
- `vip && amount >= 100_000`은 분기 4개다. JaCoCo는 바이트코드 기준으로 세고, `&&`는 조건부 점프 2개로 컴파일되기 때문이다.

### 3. 포함 관계와 테스트 수

- 분기 100% ⊃ 문장 100%(역은 아님, ISTQB 4.3.2). MC/DC는 정의상 결정 결과·각 조건 결과를 모두 포함하고 독립 영향까지 요구한다. 경로 커버리지는 루프가 있으면 경로 수가 무한해질 수 있다.
- 조건 3개: MC/DC는 일반적으로 최소 n+1 = 4개(하한), 다중 조건(모든 조합)은 2^3 = 8개(NASA/TM-2001-210876 2.3.5·2.3.6).

### 4. NoAssert vs Strong

(실험, JaCoCo 0.8.14 · PIT 1.20.4, 2026-10-03)

```text
NoAssertTest     Pricing,0,30,0,8,0,4     >> Generated 14 mutations Killed 1 (7%)
StrongTest       Pricing,0,30,0,8,0,4     >> Generated 14 mutations Killed 14 (100%)
```

- 둘 다 라인 4/4, 분기 8/8 — 완전히 같다.
- 변이 점수는 7% vs 100%. 커버리지는 단언의 유무를 못 본다.

### 5. WeakTest

```text
WeakTest         Pricing,0,30,1,7,0,4     >> Generated 14 mutations Killed 11 (79%)
<span class="pc bpc" id="L7" title="1 of 4 branches missed.">
```

- 라인 4/4(100%), 분기 7/8.
- 빠진 분기: `amount >= 100_000`의 거짓 쪽 — "VIP인데 10만 원 미만". WeakTest의 VIP 입력은 150000뿐이다.
- HTML 보고서: 7번 줄이 노랑(`pc`), 다이아몬드 툴팁 "1 of 4 branches missed.". 명령은 전부 실행돼 CSV의 줄 수로는 안 보인다. JaCoCo의 줄 상태는 명령 상태와 분기 상태를 합친 값이라 분기 누락만으로도 노랑이 된다.

### 6. 커버리지 100%로도 못 잡는 결함

- 데이터 의존 결함: 분모가 0일 때만 터지는 나눗셈처럼, 문장을 실행해도 특정 값에서만 드러나는 결함(4.3.1).
- 특정 경로 결함: 분기는 다 지났어도 특정 분기 조합(경로)에서만 나는 결함(4.3.2).
- 누락 결함: 명세에 있는데 구현하지 않은 기능. 코드가 없으니 셀 대상도 없다(4.3.3).
- (실험 관점에서 하나 더) 단언 없는 테스트: 실행은 했지만 결과를 확인하지 않는다(NoAssertTest).

### 7. Inozemtseva–Holmes 2014

- 측정: Java 시스템 5개(최대 72만 4천 줄)에 대해 테스트 스위트 31,000개를 만들고, 문장·결정·수정 조건 커버리지와 변이 테스트로 잰 결함 검출력을 비교했다.
- 결론: 스위트 크기를 고정하면 커버리지와 효과의 상관은 낮음~중간. 더 강한 커버리지가 더 나은 예측을 주지도 않았다. 커버리지는 덜 테스트된 곳 찾기에는 유용하지만 품질 목표로 쓰면 안 된다.
- 크기 고정이 중요한 이유: 테스트가 많으면 커버리지도 오르고 검출력도 오른다. 크기를 통제하지 않으면 "테스트 수"의 효과를 "커버리지"의 효과로 착각한다.

### 8. 도구 간 차이

- JaCoCo는 0.8.0부터 인자 없는 빈 private 생성자 등을 보고서에서 필터한다. PIT는 그 생성자 줄(11번)을 줄 수에 넣는다 — PIT HTML 보고서가 11번 줄을 uncovered로 표시했고, PIT 1.20.4의 줄 매핑은 클래스의 모든 메서드를 거르지 않고 센다.
- 대조: 생성자를 지우면 JaCoCo도 컴파일러가 만든 기본 생성자 줄을 미실행으로 세어 4/5가 된다(`Pricing,3,30,0,8,1,4`).
- 게이트 설계: 한 도구·한 버전·한 필터 설정으로 고정한다. 생성 코드·롬복 같은 제외 규칙을 명시한다. 다른 도구의 수치와 직접 비교하지 않는다.

### 9. 커버리지 게이트 뒤의 결함 유출

- 찾을 것: 단언이 없거나 `assertNotNull(result)`뿐인 테스트, 예외만 삼키는 테스트, 결과를 출력만 하는 테스트. 변이 테스트를 돌리면 낮은 점수로 드러난다(NoAssertTest 7%).
- 바꾸기: 전체 수치 게이트 대신 변경분 커버리지 + 리뷰에서 빈칸 설명 요구. 핵심 모듈은 변이 테스트(Test strength)로 단언 품질을 본다. 측정이 목표가 되면 측정을 맞추는 행동이 나온다(굿하트).

### 10. 출처별 입장

- Google Testing Blog(2020, Arguelles·Ivanković·Bender): 이상적인 수치는 없다. 일반 지침 60% acceptable·75% commendable·90% exemplary. 프로젝트 전체 90% 초과는 대개 가치가 없고, per-commit 99%는 합리적, 90%가 좋은 하한. 단언까지 보려면 변이 테스트가 낫다.
- SWE@G 11장: 커버리지는 줄 호출만 잰다. 목표가 되면 80%가 바닥이 아닌 천장이 된다. 대신 "고객이 기대하는 것이 동작한다는 확신이 있나" 같은 질문을 하라.
- Fowler(2012): 테스트 안 된 곳 찾기에는 유용하지만 테스트 품질의 숫자로는 별 쓸모가 없다. 잘 테스트하면 80% 후반~90%대, 100%는 의심스럽다.
- 공통점: 낮은 수치는 신호, 높은 수치는 보장 아님, 수치를 강제 목표로 삼지 말 것.
