# testing/14-property-based-testing — 정답

## 정답

### 1. 예제 기반의 빈틈과 세 요소

- 예제 기반은 사람이 떠올린 입력만 시험한다. 떠올리지 못한 조합(인접하지 않은 중복, 큰 음수·양수 쌍, 10연속 문자)의 버그가 남는다.
- 성질: 입력 전체에 대해 참이어야 하는 조건. 생성기: 그 입력을 무작위로 만든다. 축소: 실패한 입력을 더 작은 반례로 줄여 원인을 보이게 한다.
- 실험에서 예제 테스트 3개는 심어 둔 버그 3개를 하나도 못 잡았다.

### 2. 성질 패턴

- 직렬화: 왕복 `decode(encode(x)) == x`.
- 정렬: 불변식 — 이웃끼리 순서가 맞고, 원소 구성(다중집합)이 입력과 같다.
- 새 가격 계산: 기준 구현 — `newPrice(x) == oldPrice(x)`.
- 공백 정규화: 멱등 — `f(f(x)) == f(x)`.
- 구현을 베끼면 같은 계산을 두 번 하는 셈이라 버그도 같이 나온다. 성질은 구현보다 단순하거나 다른 관점이어야 한다.

### 3. dedup 반례 찾는 비율

(실험, fast-check 4.10.2 · 시드 1~200, 각 100회, 2026-10-03)

```text
dedup full int: found in 47/200 seeds, distinct shrunk = [[-3,0,-3]] [[5,0,5]] ... (37종)
dedup 0..3: found in 200/200 seeds, distinct shrunk = [[1,0,1]] [[0,1,0]] [[2,0,2]] [[3,0,3]]
```

- 전체 int 범위는 "같은 값이 떨어져서 두 번" 나올 일이 적어 47/200. 0..3 범위는 200/200.
- 축소 반례는 `[x, 0, x]` 꼴(같은 값 사이에 다른 값 하나). 0..3 범위에서는 `[0,1,0]` 같은 작은 모양으로 모였다.

### 4. rle 왕복과 생성기

```text
chars: found in 0/200 seeds (numRuns=100 each)
runs: found in 200/200 seeds (numRuns=100 each)
-- chars
longest run 1..9..90.10%
empty..............9.90%
-- runs
longest run >= 10..62.40%
```

- 문자를 하나씩 뽑는 생성기는 1만 개 중 10연속 이상을 한 번도 안 만들었다. 그래서 못 잡는다(0/200).
- "(문자, 반복 수 1..15)" 묶음을 이어 붙이는 생성기로 바꾸면 62.4%가 10연속 이상이고 200/200으로 잡는다. 축소 반례는 `"aaaaaaaaaa"`(10개)였다.

### 5. 통과의 의미

- 뜻하는 것: 이 생성기 분포에서 이 횟수 안에 반례를 못 찾았다.
- 뜻하지 않는 것: 성질이 모든 입력에서 참이라는 증명.
- 확인할 것: 생성기가 버그 영역을 만드는지(`fc.statistics`, `classify`), 사전조건으로 버린 입력이 많지 않은지, 성질이 구현을 베끼지 않는지.

### 6. 축소의 모양과 국소 최소

- fast-check 4.10.2 `shrinkInteger`: 목표(보통 0)까지 남은 거리를 `floor(n / 2)`로 반씩 줄이며 후보를 낸다. 이진 탐색 모양이다.
- 축소는 "실패를 유지하는 첫 후보로 이동"을 반복하는 탐욕적 국소 탐색이다.
- `[2147483618, 0, 2147483618]`: 왼쪽 값만 줄이면 `[0, 0, 2147483618]`처럼 인접 중복이 생기거나 두 값이 달라져 버그가 안 드러난다(성질 통과). 오른쪽도 같다. 두 값을 동시에 줄이는 후보가 없으면 여기서 멈춘다.

### 7. QuickCheck 논문

- 본체에는 축소가 없다. 사용 사례 절(5.4절)에서 Gill이 `smaller :: a -> [a]`를 더해 반례를 찾으면 더 작은 것을 찾게 확장했다고 소개한다.
- 분포 확인 도구는 `classify`·`collect`(2.4절). `ordered xs ==>` 조건의 삽입 성질에서 `OK, passed 100 tests (43% trivial).` — 43%가 빈 목록이었다.

### 8. CI에서 가끔 실패하는 속성 테스트

- 의심: 불안정 테스트가 아니라 **가끔만 밟히는 진짜 버그**. 실행마다 입력이 달라서 그렇다(실험의 dedup 전체 int: 200개 시드 중 47개만 실패, 약 23.5%).
- 재현: 실패 로그의 `seed`(fast-check는 `path`까지)로 다시 돌린다. 로그에 시드가 없으면 남게 설정한다.
- 고정: 축소된 반례를 예제 테스트로 추가한다. 재시도로 덮지 않는다.

### 9. 정렬 반례가 큰 수로 남는 이유

- 버그는 비교자 `a - b`의 32비트 오버플로다. 오버플로가 나려면 두 수의 차이가 커야 한다(int 범위, 약 2^31 이상).
- 한쪽만 줄이면 차이가 줄어 오버플로가 사라지고 성질이 통과한다. 그래서 축소가 국소 최소에서 멈춘다.
- 읽을 것: "부호가 반대이고 차이가 약 2^31인 쌍"이라는 공통 모양 → 뺄셈 오버플로를 의심한다. 두 값이 다 큰 수일 필요는 없다(재실행 시드 1~30 중 5개는 `[8,-2147483641]`처럼 한쪽이 작았다). 고친 뒤(`Integer.compare`) 같은 시드로 다시 돌린다.

### 10. 조건부 성질의 문제

- 무작위 목록은 길수록 정렬돼 있을 확률이 낮다. 조건을 통과하는 입력이 짧은 목록에 몰린다(43% 빈 목록). 조건을 거의 못 만족하면 후보 1000개 안에서 100건을 못 채워 `Arguments exhausted after 64 tests.`처럼 검사 수가 모자란다(2.3절).
- 해법: 조건으로 거르지 말고 `forAll orderedList`처럼 처음부터 정렬된 목록을 생성한다(논문 2.4절이 "가장 좋은 해법"으로 든다).
