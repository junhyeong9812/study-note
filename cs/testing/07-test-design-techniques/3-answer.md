# testing/07-test-design-techniques — 정답

## 정답

### 1. 무작위 예제의 한계와 두 기법의 역할

- 경계 결함은 값 한 점(예: 정확히 2000)에서만 드러난다. 넓은 범위에서 균등하게 뽑은 값이 그 점에 떨어질 확률은 아주 작다.
- 동치 분할: "같게 처리될 묶음"이 몇 개이고 어디서 갈리는지 정한다. 분할마다 대표 하나를 시험한다(ISTQB CTFL 4.0 4.2.1).
- 경계값 분석: 순서 있는 분할의 끝(최소·최대)과 바로 바깥을 시험한다. 결함이 모이는 자리다(4.2.2).

### 2. 배송비 동치 분할

| 분할 | 범위 | 종류 | 대표값(예시) |
|---|---|---|---|
| 무효 하단 | ..0 | 무효 | -500 |
| P1 | 1..2000 | 유효 | 1000 |
| P2 | 2001..5000 | 유효 | 3500 |
| P3 | 5001..30000 | 유효 | 10000 |
| 무효 상단 | 30001.. | 무효 | 40000 |

- 5개 분할, EP 100%에는 최소 5개 테스트. 무효 분할도 커버리지 항목으로 센다(4.2.1).

### 3. 경계 결함 검출 실험

(실험, JDK 21.0.12, 2026-10-03)

```text
B1 w<=2000 -> w<2000     EP=false BVA=true  random=0.00%
B2 w<=5000 -> w<=5001    EP=false BVA=true  random=0.01%
B3 w<1 -> w<0            EP=false BVA=true  random=0.02%
B4 w>30000 -> w>=30000   EP=false BVA=true  random=0.04%
```

- 분할 대표값 5개: 0개. 경계값 8개: 4개 전부. 무작위 8개: 1만 번 중 0~4번.
- 어림: 결함이 드러나는 값은 41,001개 중 1개다. 8개를 뽑으면 약 8/41001 ≈ 0.02%. 측정값이 이 크기와 맞다.

### 4. 2값 vs 3값 BVA

- 2값: 경계값 + 옆 분할의 가장 가까운 값(경계당 2개). 3값: 경계값 + 양쪽 이웃(경계당 3개).
- `x <= 10` → `x == 10` 결함: 2값의 x=10(둘 다 참), x=11(둘 다 거짓)로는 차이가 안 난다. 3값이 더하는 x=9에서 원래는 참, 결함은 거짓이라 잡힌다(4.2.2의 예).
- 순서가 없는 분할(결제 수단 종류 등)에는 경계가 없어 BVA를 못 쓴다.

### 5. 할인 결정 테이블

```text
                  R1   R2   R3   R4   R5   R6
  VIP             T    T    T    F    F    F
  금액 >= 10만     T    F    F    T    F    F
  금액 >= 5만      T    T    F    T    T    F
  10% 할인         X
  5% 할인               X         X    X
  할인 없음                  X              X
```

- 2^3 = 8 중 "10만 이상인데 5만 미만"(C2=T, C3=F) 조합 2개는 불가능하다. 그래서 6열.
- 빠뜨리기 쉬운 열: R4(VIP 아님 + 10만 원 이상 → 5%), R2(VIP + 5만~10만 → 5%). 사람은 "VIP면 10%"만 떠올리기 쉽다.

### 6. 상태 전이 커버리지 기준

- 모든 상태: 상태 5개를 한 번씩 거친다.
- 유효 전이(0-switch): 허용 전이 5개(pay, ship, deliver, CREATED·cancel, PAID·cancel)를 한 번씩 실행한다.
- 모든 전이: 허용 5개 실행 + 금지 15칸 전부 시도. 한 테스트에 금지 전이 하나씩(결함 가림 방지)(4.2.4).
- "SHIPPED에서 cancel 허용" 버그는 금지 칸에 있다. 모든 전이 커버리지에서야 잡힌다. 실험에서 상태표 20칸 테스트 중 12번째(`SHIPPED,cancel,REJECT`)가 `Expecting code to raise a throwable.`로 실패했다.

### 7. 조합 수

(실험, 2026-10-03)

```text
전수 조합 수 = 216
greedy pairwise 조합 수 = 13
모든 값 쌍 덮었나 = true, 쌍 총수 = 89
이론 하한(가장 큰 두 인자 값 수의 곱) = 12
3-way 값 조합 덮는 비율 = 124/261 (47.5%)
```

- 3×3×3×4×2 = 216. 하한은 결제 수단(4) × 3값 인자(3) = 12행. 결제·브라우저 쌍 12개는 서로 다른 행에 있어야 하기 때문이다.
- 탐욕법은 13행이었다(최소 보장 없음). 세 인자 값 조합은 47.5%만 덮었다.

### 8. pairwise의 근거와 한계

- CTAL-TA 4.0 3.1.2: 대부분의 실패는 한 인자 값이나 적은 수 인자의 상호작용으로 일어난다. Kuhn 외 2004에서 약 97%가 조건 하나 또는 둘로 일어났다 — 단 이 값은 의료기기 리콜 데이터이고, 같은 논문의 브라우저·서버는 76.1%·70.3%, NASA DB는 93.3%다.
- 보장하지 않는 것: 세 인자 이상의 특정 조합. 실험에서 "Safari + Android + Point"는 13행 안에 없었다.

### 9. 5만 원 쿠폰 누락

- 의심 코드: `if (amount > 50_000)` — 명세는 "이상"(`>=`).
- 테스트: 49,999 / 50,000 / 50,001을 파라미터 표에 넣는다. 명세의 "이상·초과·미만·이하" 문구를 표 행으로 옮긴다.
- 확인 도구: 변이 테스트의 경계 변이(`>` ↔ `>=`)가 살아남는지 본다(15번).

### 10. 출고 후 취소

- 빠진 것: 금지 전이 테스트. 행복 경로(허용 전이)만 테스트하면 유효 전이 커버리지는 100%여도 금지 칸의 버그는 안 보인다.
- 메우기: 상태표(상태 × 이벤트) 전체를 `@CsvSource`로 옮긴다. 금지 칸은 "예외 + 상태 그대로"를 함께 단언한다. 상태가 DB에 있으면 조건부 갱신으로도 막는다.
