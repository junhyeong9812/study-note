# testing/13-contract-testing — 정답

## 정답

### 1. 둘 다 초록인데 깨지는 이유

- 소비자의 mock은 제공자의 옛 응답을 흉내 낸 채 남는다. 제공자가 바뀌어도 mock은 모른다.
- 제공자 테스트는 "누가 어떤 필드를 쓰는지" 모른다. 그래서 필드를 바꾸고 자기 테스트만 고친다.
- E2E로 함께 띄우면 잡을 수 있지만 느리고 불안정하며, 서비스 수가 늘수록 띄울 조합이 늘어난다.

### 2. 그림

```text
 소비자 코드 ⇄ Pact 모의 제공자 ──(pact 파일 생성)──▶ 파일·Broker ──▶ Pact 검증기 ⇄ 실제 제공자
```

- 계약 파일은 **소비자 테스트**가 만든다. **제공자 검증**이 파일의 요청을 실제 제공자에 재생하고, 응답을 기대(최소 응답 + 매처)와 비교한다.

### 3. 세 계약

- 제공자 계약: 제공자가 내보내는 기능 전체(스키마·인터페이스 등).
- 소비자 계약: 소비자 하나가 거는 기대 — 제공자 계약의 부분집합.
- 소비자 주도 계약: 현재 소비자들의 기대를 모은 것이 제공자가 지킬 범위.
- 자유: 어떤 소비자 계약에도 없는 필드·동작은 제공자가 바꿔도 검증이 막지 않는다.

### 4. 제공자 변경 세 가지

(실험, Pact JVM 4.7.5 · JDK 21, 2026-10-03)

| 변경 | 결과 |
|---|---|
| ① `email` 추가 | 통과 — `has a matching body (OK)` |
| ② `name` → `fullName` | 실패 — `body: $ Actual map is missing the following keys: name` |
| ③ `id` 문자열 | 실패 — `body: $.id Expected '1' (String) to be an integer` |

- 계약 없이 ②를 배포했다면 소비자는 `IllegalStateException: name missing: {"id":1,"fullName":"Kim"}`를 냈다(실험).

### 5. 필드 추가인데 소비자가 깨지는 경우

- 소비자의 역직렬화가 모르는 필드를 오류로 처리하면(예: Jackson `FAIL_ON_UNKNOWN_PROPERTIES`가 켜진 경우) 깨진다. Pact는 응답의 추가 필드를 무시하므로 검증은 통과한다.
- 이것은 소비자 코드의 성질이라 소비자 쪽 테스트·설정이 잡아야 한다. 실험의 클라이언트는 모르는 필드를 무시하도록 설정했다.

### 6. 매처와 Postel의 법칙

- 값을 그대로 비교하면 제공자의 테스트 데이터가 조금만 달라도 깨진다. 소비자가 실제로 기대하는 것은 대개 "정수가 온다", "문자열이 온다"다.
- Pact 매칭 문서: 응답은 관대하게 — 예상하지 않은 JSON 필드를 무시. 요청은 엄격하게 — 본문·쿼리의 예상하지 않은 값을 허용하지 않음(헤더는 예외).

### 7. 맞지 않는 곳

| 경우 | 대신 |
|---|---|
| 소비자를 식별할 수 없는 공개 API | 버저닝·하위 호환 규칙, 폐기 절차 |
| 제공자 기능 테스트 | 제공자 자신의 단위·통합 테스트 |
| 검증 없이 하류로 넘기는 pass-through API, 성능·부하 | 하류와의 계약, 부하 테스트 |

### 8. 의미 변경

- 타입 매처는 "숫자다"만 본다. 원 → 천 원으로 단위가 바뀌어도 숫자는 숫자라 통과한다.
- 막기: 의미가 걸린 필드는 제공자 상태로 데이터를 고정하고 값·범위 규칙을 쓴다. 의미를 바꿀 때는 새 필드(`amountInThousands`)로 내고 옛 필드를 유지한다.

### 9. 앞서 나간 소비자 계약

- Pact Broker의 pending pacts(제공자 검증에서 `enablePending`을 켠 경우): 새 계약 내용은 그 제공자 브랜치에서 처음 성공한 검증이 게시될 때까지 보류이고, 보류 중 불일치는 검증 작업 전체를 실패시키지 않는다.
- 제공자가 그 기능을 구현해 그 브랜치에서 검증이 한 번 성공하면, 이후로는 그 브랜치에서 그 계약이 일반 계약처럼 빌드를 막는다.

### 10. can-i-deploy, record-deployment, Fowler

- `can-i-deploy`: 배포하려는 판과 대상 환경에 이미 있는 상대 판들 사이에 성공한 검증이 있는지 검증 행렬에서 확인한다.
- `record-deployment`: 어느 판이 어느 환경에 있는지 Broker가 알아야 "이미 있는 판"을 정할 수 있다. 이것이 없으면 최신 판끼리만 검증해, 운영에 남은 옛 판과의 호환을 놓친다.
- Fowler "ContractTest"(2011): 테스트 더블이 외부 서비스와 같은 결과를 주는지 주기적으로(외부 서비스 변경 주기에 맞춰, 일반 파이프라인 밖에서) 확인하고, 실패하면 맞추는 작업을 일으킨다.
- Pact식: 소비자 테스트의 더블에서 계약을 뽑아 **제공자 빌드**에서 재생한다. 같은 문제(더블이 낡는다)를 바꾸는 쪽에서 먼저 잡는다.
