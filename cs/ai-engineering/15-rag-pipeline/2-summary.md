# ai-engineering/15-rag-pipeline — RAG 파이프라인: 청킹·검색·프롬프트 조립·출처 표기 — 정리 (힌트)

## 해결하는 문제

LLM은 학습 때 본 것만 "기억"한다. 우리 회사의 환불 규정, 어제 바뀐 배송 정책은 모른다.

```text
  질문: "KA-504 환불 기한은?"
  모델 혼자     → 가중치 안에 없는 사실 → 그럴듯한 숫자를 지어낼 수 있다
  모델 + 검색   → 규정 문서에서 "환불 기한은 구매 후 7일이다"를 찾아 프롬프트에 넣는다
                → 그 문장을 근거로 답하고 [출처]를 붙인다
```

- *RAG(retrieval-augmented generation)*: 생성 전에 외부 문서를 검색해 프롬프트에 넣는 방식. Lewis 외(NeurIPS 2020) 초록은 이를 *파라미터 메모리*(사전학습 seq2seq 모델)와 *비파라미터 메모리*(위키백과의 밀집 벡터 인덱스)의 결합으로 설명한다.
  - *파라미터 지식*: 모델 가중치에 녹아 있는 지식. 바꾸려면 다시 학습한다.
  - *비파라미터 지식*: 검색 인덱스에 든 문서. 문서를 바꾸면 다음 질의부터 반영된다.
- 같은 초록은 "결정의 출처 제공과 세계 지식 갱신"을 열린 문제로 꼽는다. RAG는 이 둘을 검색 인덱스 쪽에서 **완화**한다 — 같은 논문 서론도 검색 기반 메모리가 이 문제의 "일부를 다룰 수 있다(can address some of these issues)"고 쓴다. 인용한 문서가 답을 실제로 뒷받침하는지는 따로 검증한다(적용 2).

쉬운 예: 오픈북 시험이다.
- 머리로 외운 것(파라미터)만으로 풀면 틀린 것을 자신 있게 쓴다.
- 책(인덱스)을 펴서 해당 쪽을 찾고(검색), 그 쪽을 보며 답을 쓰고(생성), 몇 쪽인지 적는다(출처).
- 찾은 쪽이 엉뚱하면 답도 엉뚱하다. 책에 없는 문제면 "없다"고 써야 한다.

똑같은 구조다.\
**근거를 댈 수 있는 답**은 검색이 근거를 찾아왔을 때만 나온다. 다만 검색 결과가 답할 수 있는 범위를 다 정하지는 않는다 — 모델은 가중치 지식으로도 답한다(Lewis 외 4.1절: 검색된 문서에 정답이 없어도 NQ에서 11.8%를 맞혔다). 그런 답은 출처로 확인할 수 없고, 정답 문서를 찾아와도 생성이 틀릴 수 있다.

실무 예:
- 고객센터 챗봇이 상품 규정 문서 수천 편을 근거로 답한다.
- 사내 위키 검색에 "문서 요약 + 링크"를 붙인다.
- 장애 대응 런북에서 오류 코드에 맞는 절차를 찾아 보여 준다.

## 동작·원리

### 1. 파이프라인 전체

```text
  [오프라인 — 문서가 바뀔 때]
   수집 ─→ 정제 ─→ 청킹(분할) ─→ 임베딩 ─→ 색인(벡터 + 메타데이터: 문서 ID·권한·버전)
                                                    │
  [온라인 — 질문마다]                               ▼
   질문 ─→ 임베딩 ─→ 검색 top-k ─────────────→ 걸러내기 ─────────→ 프롬프트 조립 ─→ LLM ─→ 출처 검증 ─→ 응답
                     (16·17번)                  · 권한(검색 단계에서)   · 청크마다 [ID]
                                                · 점수 임계값           · 지시: "자료만 근거로"
                                                · 결과 0건이면 생성 안 함
```

- 오프라인 단계는 문서가 바뀔 때 다시 돈다([18번](../18-index-freshness-and-reembedding/2-summary.md)). 온라인 단계는 질문마다 돈다.
- *청크(chunk)*: 검색·프롬프트에 넣는 단위로 자른 문서 조각.
- *임베딩*: 텍스트를 고정 길이 벡터로 바꾼 것. 정의와 코사인 유사도는 [math/13](../../math/13-linear-algebra-essentials/2-summary.md)과 [05-embeddings-and-similarity](../05-embeddings-and-similarity/2-summary.md)가 단일 출처다.
- *top-k*: 질의와 가장 비슷한 청크 k개.

### 2. 청킹 — 너무 작으면 문맥을 잃고, 너무 크면 희석·비용

```text
  문서 "KA-504 제습기 이용 안내"
  ┌─────────────────────────────────────────────────────────────────┐
  │ KA-504 제품은 가정용 제습기이다. 처음 쓰기 전에 포장재를 …       │
  │ 환불 기한은 구매 후 7일이다. 개봉한 경우 판매가의 10%를 공제한다. │
  │ 배송은 결제 후 2일 안에 출발한다. …                              │
  └─────────────────────────────────────────────────────────────────┘

  고정 40자로 자르기      "…포장재를 모두 제거한다. 정격 소비 전력은 1200W이다. 환불 기"
                          "한은 구매 후 7일이다. 개봉한 경우 판…"        ← 정답 문장이 둘로 잘림
  문장 단위로 자르기      "환불 기한은 구매 후 7일이다."                  ← 문장은 온전
                                                                          그런데 "KA-504"가 없다
  제목 접두 붙여 색인     "KA-504 제습기 이용 안내 | 환불 기한은 구매 후 7일이다."
```

- 작은 청크의 문제: 정답 문장에 **어느 제품 얘기인지**가 없다. 30개 문서가 모두 "환불 기한은 …일이다"를 가지면 검색이 엉뚱한 문서의 같은 문장을 가져온다.
- 고정 길이의 문제: 문장·표·문단이 경계에서 잘린다. 근거가 반쪽만 검색된다.
- 큰 청크의 문제: 한 청크에 주제가 여럿 섞여 유사도가 흐려지고, 프롬프트에 넣는 양(=토큰 비용, [04번](../04-tokenization-and-token-cost/2-summary.md))이 커진다.
- Anthropic "Contextual Retrieval"(2024-09-19): 청크는 보통 "몇백 토큰 이하"로 자른다고 적고(수치 권고는 없다), 청크에 문서 맥락이 빠지는 문제를 다룬다. 청크마다 **LLM이 만든 짧은 맥락 설명**을 앞에 붙여 임베딩·BM25 색인을 만들면 top-20 검색 실패율이 49% 줄었다고 보고한다(5.7% → 2.9%).
  - 아래 실험의 "제목 접두"는 이 기법을 **단순화한 모형**이다(LLM 대신 문서 제목만 붙인다).

### 실험 1: 청크 크기·경계·제목 접두에 따른 검색 적중

- 말뭉치(합성): 제품 안내서 30편, 편마다 9문장(평균 182자). 제품 코드만 다르고 문장 틀이 같다. 질문 90개 = 제품마다 환불·배송·보증 3개. seed 15.
- 검색: TF-IDF(한글은 문자 바이그램, 제품 코드는 통째 토큰) + 코사인 전수 검색, top-3.
- 적중(hit@3): top-3 중 하나가 **정답 문서의 청크**이고 **정답 문장을 통째로** 담고 있다.
- 잘린 정답: 정답 문장을 통째로 담은 청크가 하나도 없는 질문 수(청킹 단계에서 이미 실패).
- 프롬프트 글자 수: top-3 청크 원문 길이의 합(토큰 수의 대용).

(실험, 호스트 Python 3.12.3 표준 라이브러리, 2026-10-08)

```text
문서 30편, 질문 90개, 문서 평균 182자
방식      크기 겹침 접두 | 청크수 hit@3  잘린정답 프롬프트평균자
fixed      40    0    N |    150  0.02       73          120
fixed      40    0    Y |    150  0.19       73          105
fixed      40   15    Y |    240  0.98        2           92
fixed      80    0    Y |     90  0.52       43          182
sent       40    0    N |    197  0.07        0           71
sent       40    0    Y |    197  1.00        0           71
sent       80    0    Y |     90  1.00        0          171
sent      160    0    Y |     60  1.00        0          289
sent     1000    0    N |     30  1.00        0          543
```

- `fixed` = 글자 수로 자름(문장 무시), `sent` = 문장 경계에서 자르고 크기까지 채움, 겹침 = 앞 청크와 겹치는 글자 수, 접두 = 색인할 때 문서 제목을 붙임(프롬프트에는 원문만).
- 관찰 1: 고정 40자·겹침 없음은 정답 90개 중 73개를 잘랐다. 적중 0.02다. 검색 이전에 청킹에서 이미 졌다.
- 관찰 2: 문장 단위 40자는 정답을 하나도 안 잘랐는데 접두 없이 적중 0.07이다. 정답 문장에 제품 코드가 없어 다른 제품의 같은 문장이 올라왔다(아래 예).
- 관찰 3: 같은 문장 단위 40자에 제목 접두를 붙이자 1.00이 됐다. 프롬프트 글자 수는 71로 가장 작다.
- 관찰 4: 문서 통째(1000자)도 1.00이지만 프롬프트가 543자로 약 7.6배다. 정답과 무관한 문장이 같이 들어간다.
- 관찰 5: 고정 길이도 겹침 15자를 주면 잘린 정답이 73 → 2로 줄었다(적중 0.98). 겹침은 경계 손실을 줄이고 청크 수(150 → 240)를 늘린다.
- 이 수치는 문장 틀이 같은 합성 말뭉치의 결과다. 실제 문서에서 최적 크기는 다르다 — 정답셋을 만들어 직접 잰다([19번](../19-llm-evaluation/2-summary.md)).

같은 질문 "KA-504 환불 기한은 며칠인가"의 top-3(같은 실험):

```text
  문장 단위 80자 + 제목 접두
    [d00#1] 0.452  환불 기한은 구매 후 7일이다. 개봉한 경우 판매가의 10%를 공제한다. 배송은 결제 후 2일 안에 출발한다.
    [d00#0] 0.447  KA-504 제품은 가정용 제습기이다. 처음 쓰기 전에 포장재를 모두 제거한다. 정격 소비 전력은 1200W이다.
    [d00#2] 0.272  도서 산간 지역은 2일이 더 걸린다. 무상 보증 기간은 6개월이다. 소모품은 보증 범위에서 제외한다.
  문장 단위 40자, 접두 없음
    [d00#0] 0.464  KA-504 제품은 가정용 제습기이다.
    [d08#2] 0.372  환불 기한은 구매 후 30일이다.          ← 다른 제품(d08)의 환불 문장
    [d12#2] 0.372  환불 기한은 구매 후 30일이다.          ← 또 다른 제품
```

- 아래쪽 결과를 받은 모델은 "30일"이라고 답할 수 있다. 출처도 붙어 있어 더 그럴듯해 보인다(해석).

### 3. 근거가 없을 때 — 점수 임계값

```text
  top-k 검색은 (권한 등 필터를 통과한) 검색 대상이 남아 있는 한 "가장 가까운 것"을 돌려준다.
  가깝다 ≠ 관련 있다. 필터 뒤 대상이 없으면 0건이다.

  질문 "QQ-101 환불 기한은?" (없는 제품)  → top1 = KA-504의 환불 문장(점수 0.288)
                                         → 그대로 생성하면 "7일입니다" — 근거 없는 답
```

(실험 1과 같은 색인 — 문장 단위 80자 + 제목 접두)

```text
답 있는 질문 top1 점수: 최소 0.367 / 중앙 0.471 / 최대 0.615
답 없는 질문 'QQ-101 환불 기한은 며칠인가': top1 0.288 -> d00#1 "환불 기한은 구매 후 7일이다. 개봉한 경우…"
답 없는 질문 'ZM-555 환불 기한은 며칠인가': top1 0.288 -> d00#1 "환불 기한은 구매 후 7일이다. 개봉한 경우…"
답 없는 질문 'XA-000 환불 기한은 며칠인가': top1 0.288 -> d00#1 "환불 기한은 구매 후 7일이다. 개봉한 경우…"
답 없는 질문 '회원 탈퇴는 어떻게 하나': top1 0 -> d00#0 "KA-504 제품은 가정용 제습기이다. 처음…"
답 없는 질문 '포인트 유효 기간은': top1 0.271 -> d09#2 "무상 보증 기간은 24개월이다. 소모품은 보…"
답 없는 질문 '매장 영업 시간은': top1 0.191 -> d09#2 "무상 보증 기간은 24개월이다. 소모품은 보…"
```

- 관찰: 답 없는 질문 6개의 top1 점수(최대 0.288)가 답 있는 질문의 최소(0.367)보다 낮았다. 이 말뭉치에서는 0.3 근처 임계값으로 "근거 없음"을 가를 수 있다.
- 점수 0인 질문도 결과 1건이 돌아왔다. 검색기는 빈 목록 대신 "가장 덜 먼 것"을 준다.
- 임계값은 말뭉치·임베딩 모델마다 다르다. 평가셋의 답 있는/없는 질문 분포로 정한다([19번](../19-llm-evaluation/2-summary.md)).

### 4. 프롬프트 조립과 출처

```text
  아래 자료만 근거로 답하고, 쓴 자료의 [ID]를 문장 끝에 붙여라.
  [d00#1] 환불 기한은 구매 후 7일이다. 개봉한 경우 판매가의 10%를 공제한다.
  [d00#0] KA-504 제품은 가정용 제습기이다.
  질문: KA-504 환불 기한은 며칠인가
```

- 청크마다 **시스템이 붙인 ID**를 단다. 출처는 모델이 지어낸 문서명이 아니라 이 ID로 표기하게 한다.
- 응답의 ID는 "이번에 건넨 ID 집합" 안에 있어야 한다. 밖의 ID는 모델이 만든 출처다 → 걸러낸다(적용 2).
- Liu 외(TACL 2024, "Lost in the Middle") 초록: 관련 정보가 입력의 앞이나 끝에 있을 때 성능이 높고, 긴 문맥의 중간에 있으면 크게 떨어진다. 관련도 높은 청크를 앞에 두고, k를 필요 이상 키우지 않는다(해석).

## 쓰이는 자료구조·알고리즘

- **TF-IDF + 코사인 전수 검색** — 실험 1의 검색기. 코사인은 [math/13](../../math/13-linear-algebra-essentials/2-summary.md), 근사 인덱스는 [16번](../16-vector-index-ann/2-summary.md).
- **문자 n-gram 토큰화** — 한국어 조사가 붙은 어절을 바이그램으로 쪼개 일치시킨다. 검색 분석기 쪽 설명은 [database/46](../../database/46-full-text-search-and-analyzers/2-summary.md).
- **슬라이딩 윈도 분할** — 고정 길이 + 겹침 청킹. [algorithm/09-sliding-window](../../algorithm/09-sliding-window/2-summary.md)
- **상위 k 선택(힙)** — top-k 검색. [data-structure/07-heap](../../data-structure/07-heap/2-summary.md)
- **해시 집합** — 응답 출처 ID ⊆ 건넨 ID 집합 검사. [data-structure/05-hashmap](../../data-structure/05-hashmap/2-summary.md)
- **밀집 검색기(DPR)** — 질문 인코더와 문단 인코더(dual-encoder)로 각각 벡터를 만들고, 유사도를 두 벡터의 내적 `sim(q, p) = E_Q(q)ᵀ E_P(p)`로 정의하는 학습된 검색기(Karpukhin 외 EMNLP 2020, 3.1절 식 (1)). 초록: top-20 문단 검색 정확도에서 Lucene-BM25보다 9~19%p 높았다.

## 적용 — 풀어나가는 법

### 1. 답이 틀렸을 때 — 어느 단계인가

```text
  증상: 챗봇이 틀린 숫자를 말했다
    ① 정답 문장을 통째로 담은 청크가 색인에 있나?     없다 → 청킹(경계·크기·겹침)
    ② 그 청크가 top-k 안에 들어왔나?                 없다 → 검색(맥락 접두·하이브리드 17번·인덱스 recall 16번)
    ③ top-k 안에 있었는데 답이 틀렸나?               있다 → 프롬프트 조립(순서·양)·생성
    ④ 답 없는 질문이었나?                            그렇다 → 점수 임계값·거절 경로
```

- 이 순서대로 로그를 남겨야 따질 수 있다. 질의마다 `질문 · top-k 청크 ID와 점수 · 최종 프롬프트의 청크 ID · 응답의 출처 ID`를 기록한다([23번](../23-llm-observability-and-cost/2-summary.md)).

### 2. 프롬프트 조립과 출처 검증 (Java 21)

```java
import java.util.*;
import java.util.regex.*;

public class CitationCheck {
    record Chunk(String id, String text) {}
    record Verdict(boolean ok, Set<String> cited, Set<String> unknown) {}

    // 형식과 무관하게 대괄호 표기를 전부 모은다 — ID 꼴만 모으면 [d100#1] 같은 틀린 인용을 놓친다
    static final Pattern CITE = Pattern.compile("\\[([^\\[\\]]*)]");

    // 프롬프트 조립: 검색된 청크마다 출처 ID를 붙여 넣는다
    static String assemble(String question, List<Chunk> retrieved) {
        var sb = new StringBuilder("아래 자료만 근거로 답하고, 쓴 자료의 [ID]를 문장 끝에 붙여라.\n");
        for (Chunk c : retrieved) sb.append("[").append(c.id()).append("] ").append(c.text()).append("\n");
        return sb.append("질문: ").append(question).toString();
    }

    // 생성된 답의 출처 ID가 이번에 실제로 건넨 청크 집합 안에 있는지 확인한다
    static Verdict verify(String answer, List<Chunk> retrieved) {
        Set<String> given = new HashSet<>();
        retrieved.forEach(c -> given.add(c.id()));
        Set<String> cited = new LinkedHashSet<>();
        Matcher m = CITE.matcher(answer);
        while (m.find()) cited.add(m.group(1));
        Set<String> unknown = new LinkedHashSet<>(cited);
        unknown.removeAll(given);
        return new Verdict(!cited.isEmpty() && unknown.isEmpty(), cited, unknown);
    }
}
```

### 실험 2: 출처 검증 — 모델 응답 대신 문자열 네 개

(실험, OpenJDK 21.0.12 temurin, Docker `--network none --cpus=2`, `java CitationCheck.java`, 2026-10-08)

```text
구매 후 7일입니다 [d00#1]. -> Verdict[ok=true, cited=[d00#1], unknown=[]]
구매 후 7일입니다 [d00#1]. 개봉 시 10% 공제됩니다 [d07#2]. -> Verdict[ok=false, cited=[d00#1, d07#2], unknown=[d07#2]]
구매 후 7일입니다. -> Verdict[ok=false, cited=[], unknown=[]]
구매 후 7일입니다 [d00#1]. 개봉 시 10% 공제됩니다 [d100#1]. -> Verdict[ok=false, cited=[d00#1, d100#1], unknown=[d100#1]]
```

- 두 번째: 건네지 않은 `[d07#2]`를 인용했다 → 지어낸 출처로 판정.
- 세 번째: 출처가 없다 → 근거 없는 답으로 판정.
- 네 번째: ID 꼴(`d\d{2}#\d+`)에 안 맞는 `[d100#1]`도 거부했다. 처음 쓴 패턴(`\[(d\d{2}#\d+)]`)으로 돌리면 이 줄이 `ok=true, cited=[d00#1]`이 됐다 — `find()`는 패턴에 맞는 부분만 모으므로 틀린 인용이 검사에서 빠진다(같은 환경 재실행).
- 이 검사는 "인용한 ID가 실재하는가"만 본다. 인용한 청크가 그 문장을 **실제로 뒷받침하는가**는 따로 평가한다([19번](../19-llm-evaluation/2-summary.md) — 해석).
- 출처 링크는 응답 텍스트를 파싱해 만들지 않는다. 검증을 통과한 ID로 시스템이 가진 문서 메타데이터(제목·URL)를 붙인다.

### 3. 권한은 검색 단계에서 거른다

```sql
-- 사용자 그룹이 문서 ACL과 겹치는 청크만 검색 대상 (PostgreSQL 17 + pgvector)
SELECT c.id, c.doc_id, c.body
FROM chunks c
WHERE c.acl_groups && $2::text[]          -- 권한 필터를 검색 질의 안에
ORDER BY c.embedding <=> $1
LIMIT 5;
```

- 생성 뒤에 걸러서는 늦다. 권한 밖 문서가 프롬프트에 들어간 순간 그 내용이 답에 섞일 수 있다(해석 — 모델은 지시를 어길 수 있다, [22번](../22-prompt-injection-and-llm-security/2-summary.md)).
- 근사 인덱스에서는 이 필터가 인덱스 탐색 뒤에 적용돼 결과가 모자랄 수 있다([16번](../16-vector-index-ann/2-summary.md) 3절). 권한 그룹 수가 적으면 부분 인덱스·파티션을 쓴다.

### 4. 근거 없음 경로

```java
// top1 점수가 임계값 아래이거나 결과가 비면 생성하지 않고 정해진 응답을 준다
if (hits.isEmpty() || hits.get(0).score() < threshold) {
    return Answer.noEvidence("규정 문서에서 근거를 찾지 못했습니다. 상담원 연결을 안내합니다.");
}
```

- 임계값은 평가셋에서 답 있는/없는 질문의 점수 분포를 보고 정한다(실험 1의 3절처럼).

## 장애 시나리오와 대처

### 1. 청크 경계에서 표·문단이 잘린다 (⚠ 커리큘럼)

- 현상: 규정의 절반만 담은 청크가 검색돼 조건이 빠진 답이 나온다.
- 보이는 형태: 고정 40자 청킹에서 정답 90개 중 73개가 잘렸고 적중 0.02(실험 1).
- 원인: 글자 수로만 자르면 문장·표 행·목록 중간이 경계가 된다.
- 대처: 문장·문단·표 단위로 자르고 크기를 채운다. 고정 길이를 쓰면 겹침을 둔다(겹침 15자에서 잘림 73 → 2). 표는 행 단위로 자르고 머리글을 청크마다 반복한다(해석).

### 2. 청크에 "무엇에 관한 문장인지"가 없다

- 현상: 다른 제품의 같은 틀 문장이 검색된다.
- 보이는 형태: 문장 단위 40자, 접두 없음 → 적중 0.07(실험 1). 답의 숫자가 다른 제품 것이다.
- 원인: 제품 코드·문서 제목이 청크 밖에 있다.
- 대처: 색인할 때 문서 제목·절 제목을 청크 앞에 붙인다(적중 1.00). Anthropic "Contextual Retrieval"은 LLM으로 청크별 맥락을 만들어 붙인다.

### 3. 검색 결과가 없거나 약한데도 생성한다 (⚠ 커리큘럼)

- 현상: 없는 제품을 물었는데 "7일입니다"라고 답한다.
- 보이는 형태: top1 점수가 낮다(답 없는 질문 최대 0.288 vs 답 있는 질문 최소 0.367, 실험 1). 점수 0이어도 결과가 1건 온다.
- 원인: top-k 검색기는 관련 문서가 없어도 "가장 가까운 것"을 돌려주고, 생성은 받은 자료를 근거로 쓰려 한다.
- 대처: 점수 임계값·결과 0건 → 생성하지 않는 경로. 임계값은 평가셋으로 정하고 모델·말뭉치를 바꾸면 다시 잰다.

### 4. 권한 없는 문서 내용이 답에 섞인다 (⚠ 커리큘럼)

- 현상: 일반 직원의 질문에 인사 문서 내용이 인용된다.
- 보이는 형태: 응답의 출처 ID가 사용자 권한 밖 문서를 가리킨다. 오류는 없다.
- 원인: 검색 단계에서 ACL을 거르지 않고 top-k를 그대로 프롬프트에 넣었다.
- 대처: 검색 질의 안에서 권한 필터(적용 3). 출처 검증 단계에서 문서 ACL을 한 번 더 확인한다. 근사 인덱스의 필터 후 결과 부족([16번](../16-vector-index-ann/2-summary.md))을 함께 점검한다.

### 5. 존재하지 않는 출처 (⚠ 커리큘럼)

- 현상: 답 끝의 문서 링크를 누르면 없는 문서다.
- 보이는 형태: 응답 텍스트에서 문서명·URL을 파싱해 링크를 만들었다.
- 원인: 모델이 출처 형식을 흉내 내 지어냈다.
- 대처: 시스템이 붙인 청크 ID로만 인용하게 하고, 건넨 ID 집합 밖의 인용은 거부한다(실험 2). 링크는 검증된 ID로 메타데이터에서 만든다.

## 핵심 문장

- RAG = 생성 전에 비파라미터 메모리(검색 인덱스)에서 근거를 찾아 넣는 것이다. 문서를 바꾸면 재학습 없이 다음 질의부터 반영된다.
- 답의 품질은 검색이 정답 청크를 찾아왔는가로 먼저 갈린다. 실패는 청킹 → 검색 → 조립 → 생성 순서로 따진다.
- 청크는 경계에서 근거를 자르지 않고, 무엇에 관한 문장인지 맥락을 품어야 한다.
- top-k 검색은 관련 문서가 없어도 무언가를 돌려준다. 점수 임계값과 "근거 없음" 경로가 필요하다.
- 권한은 검색 단계에서 거르고, 출처는 시스템이 붙인 ID로 검증한다.
