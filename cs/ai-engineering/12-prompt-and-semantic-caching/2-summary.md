# ai-engineering/12-prompt-and-semantic-caching — 프롬프트(프리픽스) 캐시와 의미 캐시: 정확 일치 접두 vs 유사도 임계값 — 정리 (힌트)

## 해결하는 문제

LLM 호출은 느리고 비싸다. 그런데 요청마다 같은 부분이 반복된다.

```text
  요청 1:  [도구 정의 2k] [시스템 프롬프트 3k] [사내 규정 문서 20k] [질문 "연차는 며칠?"]
  요청 2:  [도구 정의 2k] [시스템 프롬프트 3k] [사내 규정 문서 20k] [질문 "병가 규정은?"]
           └───────────────────── 25k 토큰이 매번 똑같다 ─────────────────────┘
  요청 3:  ...                                                    [질문 "연차 며칠이야?"]  ← 요청 1과 뜻이 같다
```

- 반복 ①: 앞부분(접두)이 매번 같다. 모델은 매번 그 25k 토큰을 다시 처리하고, 우리는 매번 입력 단가를 낸다.
- 반복 ②: 질문 자체가 전에 받은 것과 뜻이 같다. 답도 같아도 되는 경우라면 모델을 부를 필요가 없다.
- 두 반복을 푸는 캐시는 **위치·키·위험이 전혀 다르다.**
  - *프롬프트(프리픽스) 캐시*: 제공자 서버가 같은 접두의 계산 결과(KV 상태)를 재사용한다. 접두가 **정확히** 같아야 적중한다. 답은 매번 새로 생성된다.
  - *의미 캐시(semantic cache)*: 우리 앱이 "비슷한 질문"에 **전에 만든 답**을 돌려준다. 임베딩 유사도가 임계값 이상이면 적중한다. 틀린 답을 줄 위험이 있다.

쉬운 예: 법률 상담 창구다.
- 프리픽스 캐시 = 상담원이 매번 읽는 두꺼운 규정집 앞부분을 이미 읽어 머리에 둔 것. 질문이 달라도 답은 새로 생각한다. 규정집 첫 페이지에 한 글자라도 바뀌면 처음부터 다시 읽는다.
- 의미 캐시 = "아까 비슷한 질문 있었죠?" 하고 지난 답안지를 복사해 주는 것. 빠르지만, 질문이 "가능한가요"였는지 "불가능한가요"였는지 잘못 보면 반대 답을 준다.

똑같은 구조다.\
백엔드의 두 캐시도 "계산 재사용(정확·안전)"과 "결과 재사용(근사·위험)"으로 갈린다. 결과 재사용의 키 설계는 일반 캐시와 같은 규칙을 따른다([database/31-cache-key-versioning-and-serialization](../../database/31-cache-key-versioning-and-serialization/2-summary.md)).

## 동작·원리

### 1. 두 캐시가 놓이는 곳

```text
  앱 ──질문──> [의미 캐시 (우리 Redis·pgvector)] ──적중──> 저장된 답 반환 (LLM 호출 0)
                      │ 놓침
                      ▼
               LLM API 요청 ──> [제공자 프리픽스 캐시: 접두 KV 상태] ──> 모델이 나머지만 처리해 새 답 생성
                                    적중: 접두 토큰 = 캐시 읽기 단가        놓침: 쓰기 단가로 저장
```

- 프리픽스 캐시는 **입력 처리**(프리필)를 줄인다. 첫 토큰까지의 시간과 입력 비용이 준다. 출력 생성 비용은 그대로다.
  - OpenAI 문서(2026-10-08 확인, "Prompt caching"): 캐시가 저장하는 것은 토큰이 아니라 KV(key-value) 텐서다. KV 캐시 자체는 [08-kv-cache-and-inference-memory](../08-kv-cache-and-inference-memory/2-summary.md).
- 의미 캐시는 **호출 자체**를 없앤다. 대신 그 답이 이 질문에 맞는지 아무도 다시 확인하지 않는다.

### 2. 프리픽스 캐시의 키 — 누적 해시와 중단점

```text
  Anthropic Messages API 기준 (2026-10-08 확인)

  순서 고정:   tools ──> system ──> messages[0] ──> messages[1] ──> ...
  블록:        [b1]      [b2]       [b3]             [b4] ◄ cache_control (중단점)
  키:          h1=H(b1)  h2=H(h1,b2) h3=H(h2,b3)      h4=H(h3,b4)  ← 이 위치에만 캐시 항목을 쓴다

  다음 요청에서 b2(시스템 프롬프트) 한 글자만 바뀌면
               h1 같음   h2' 다름 → h3', h4' 모두 다름 → 그 뒤 전부 놓침
```

- 키는 **접두 전체의 누적 해시**다. 중간 블록 하나가 바뀌면 그 뒤 모든 위치의 키가 바뀐다. 문서는 "적중하려면 중단점까지의 프롬프트 조각이 100% 같아야 한다"고 적는다.
- 쓰기는 중단점에서만 일어난다. 읽기는 중단점에서 시작해 이전 블록 쪽으로 최대 20블록까지 거슬러 올라가며 앞선 요청이 써 둔 항목을 찾는다(lookback 20).
- 계층 무효화: tools → system → messages 순서라, 도구 정의를 바꾸면 전체가, 시스템 프롬프트를 바꾸면 system·messages가 무효화된다.
- 최소 길이: 모델마다 512~4,096토큰. 그보다 짧으면 `cache_control`을 붙여도 **오류 없이** 캐시되지 않는다. `cache_creation_input_tokens`와 `cache_read_input_tokens`가 둘 다 0이면 캐시되지 않은 것이다.
- 격리: Claude API에서는 워크스페이스 단위로 격리되고, 다른 조직과는 같은 프롬프트라도 공유하지 않는다(Bedrock·Google Cloud는 조직 단위).

### 3. 수명과 값 — 제공자마다 다르다 (2026-10-08 확인)

| | Anthropic Messages API | OpenAI (GPT-5.6 이후 모델 기준) |
|---|---|---|
| 기본 TTL | 5분. 사용할 때마다 추가 비용 없이 갱신. 요청 **시작** 시각부터 잼 | `prompt_cache_options.ttl` 30분(유일한 값이자 기본). 마지막 쓰기·재사용 뒤 30분 |
| 긴 TTL | 1시간 옵션 | GPT-5.6 이후는 `30m` 하나뿐. 이전 모델은 `prompt_cache_retention`: `in_memory`(보통 비활동 5~10분, 최대 1시간)·`24h`(최대 24시간) |
| 쓰기 단가 | 기본 입력의 1.25배(5분), 2배(1시간) | 기본 입력의 1.25배(GPT-5.6 이전 모델은 쓰기 추가 요금 없음) |
| 읽기 단가 | 대부분 모델 0.1배(일부 모델은 더 낮음) | 대부분 0.1배(일부 모델 0.05배), "최대 95% 할인" |
| 최소 길이 | 모델별 512~4,096토큰 | 1,024토큰(GPT-5.6 이후). 이전 모델은 설정에 따라 다름 |
| 사용량 필드 | `cache_creation_input_tokens`·`cache_read_input_tokens`·`input_tokens`(셋의 합 = 전체 입력) | Responses `input_tokens_details.cached_tokens`·`cache_write_tokens`(`input_tokens`에 포함) |

- 위 두 API에서는 쓰기 단가가 기본보다 비싸다. **적중하지 않는 캐시 쓰기는 손해다.** 한 번 쓰고 한 번 읽으면 1.25 + 0.1 = 1.35배로, 캐시 없이 두 번(2배)보다 싸다(OpenAI 문서의 같은 계산).
- 단가 배수는 모델·날짜마다 바뀐다. 실제 값은 가격표에서 확인한다.

### 실험: 가변값이 접두 앞에 있을 때와 뒤에 있을 때

- 무엇: 요청 100개, 고정 시스템 프롬프트 3,000토큰 + 질문 50토큰(예시). 요청마다 바뀌는 값(`ts=<번호>` — 시각·요청 ID 역할) 하나를 접두 **앞**에 둘 때와 **뒤**에 둘 때를 비교했다. 캐시 키 = 중단점까지 토큰의 SHA-256, 단가 = 쓰기 1.25·읽기 0.1·일반 1.0.

```python
toks = stamp + SYSTEM + q if layout == "앞" else SYSTEM + stamp + q
bp = len(SYSTEM) + (1 if layout == "앞" else 0)       # 캐시 중단점 = 고정부 끝
key = hashlib.sha256(" ".join(toks[:bp]).encode()).hexdigest()
if key in cache: read += bp
else: cache.add(key); write += bp
```

(실험, Python 3.12 `python:3.12-slim`, Docker `--network none --cpus=2`, 2026-10-08 — 결정적, 2회 실행 동일)

```text
[1] 프리픽스 캐시 (요청 100개, 고정 시스템 프롬프트 3000토큰 + 질문 50토큰, 예시)
  가변값 위치=앞  캐시 쓰기 300100 읽기      0 토큰 → 입력 비용 1.25배 (캐시 없을 때 1.00)
  가변값 위치=뒤  캐시 쓰기   3000 읽기 297000 토큰 → 입력 비용 0.13배 (캐시 없을 때 1.00)
```

- 관찰 1: 가변값이 앞에 있으면 100번 모두 쓰기만 하고 읽기 0이다. 캐시를 켰는데 **캐시가 없을 때보다 25% 비싸다.**
- 관찰 2: 같은 내용을 뒤로 옮기기만 해도 첫 요청만 쓰고 나머지 99번은 읽는다. 입력 비용이 0.13배로 준다.
- 한계: 실제 서버는 TTL·라우팅·최소 길이 때문에 적중이 이보다 낮을 수 있다. 실측은 응답의 캐시 사용량 필드로 한다.

### 4. 의미 캐시 — 정확 일치 파티션 + 유사도 임계값

```text
  새 질문 q
    │ ① 정확 일치로 파티션을 고른다: (테넌트, 언어, 모델, 프롬프트 버전, 임베딩 모델, 질문 속 식별자)
    ▼
  파티션 안에서만
    │ ② 임베딩 e(q) ─ 최근접 탐색 ─> 가장 비슷한 저장 질문 s, 유사도 sim
    ▼
  sim ≥ θ ?  ── 예 ──> 저장된 답 반환 (+ 적중 로그: q, s, sim)
     │ 아니오
     ▼
  LLM 호출 → 답 → (q, e(q), 답, TTL) 저장
```

- Regmi·Pun(2024, "GPT Semantic Cache"): 질의 임베딩을 Redis에 두고 HNSW(hnswlib-node)로 최근접을 찾는다. 코사인 유사도 임계값 0.8을 넘으면 저장된 답을 쓴다(2.6절). 항목마다 TTL(2.7절).
  - 그 논문의 결과: API 호출 최대 68.8% 감소, 적중률 61.6~68.8%, 적중 중 맞는 답(positive hit)은 초록에서 "97% 초과"로 요약하지만 결과 표 1의 범주별 값은 92.5~97.3%다(예: 335건 중 310건). 거꾸로 말하면 범주에 따라 적중의 약 3~7.5%가 맞는 답으로 판정되지 않았다. 판정은 GPT-4o Mini가 했으므로 실제 오답률 그 자체는 아니다(해석).
- 임계값 θ 하나로 "같은 뜻"과 "비슷하지만 다른 뜻"을 가르는 것이 이 캐시의 본질적 위험이다. 그래서 유사도로 판정하기 **전에** 정확 일치로 갈라야 하는 것들을 파티션 키로 뺀다.
  - *파티션 키*: 같으면 비교 대상이 되고, 다르면 아예 비교하지 않는 정확 일치 부분.

### 실험: 문자 2-gram 임베딩 의미 캐시의 적중·오적중

- 무엇: 저장 질문 4개(테넌트 t1)와 새 질문 8개. 각 새 질문에 "캐시에서 줘도 되는 답"을 미리 정해 두고, 임계값과 테넌트 키 유무에 따라 옳은 적중·오적중·놓침을 셌다.
- 단순화: 임베딩은 문자 2-gram 빈도 벡터(실제 임베딩 모델이 아님)다. 수치는 모형의 것이고, 보이려는 것은 "임계값 하나로 갈리지 않는 경우가 있다"는 구조다.


- 관찰 1: 뜻이 반대인 "환불이 불가능한가요"(0.84)와 대상이 다른 "주문 1002"(0.86)가 옳은 재사용인 "주문 취소 어떻게 해요"(0.64)·"환불 가능한가요"(0.82)보다 **유사도가 높다.** 어떤 θ를 골라도 옳은 적중만 남기고 오적중을 0으로 만들 수 없다.
- 관찰 2: 다른 테넌트(t2)의 똑같은 질문은 유사도 1.00이라 θ = 0.95에서도 적중했다. 테넌트를 파티션 키에 넣자 사라졌다. 이 오적중은 임계값으로는 못 막는다.
- 관찰 3: "주문 1002"의 오적중은 질문 속 식별자를 파티션 키로 빼면 사라진다(아래 Java 실험). "불가능"의 오적중은 키로도 못 막는다 — 의미 캐시를 쓸 질문 범위 자체를 좁혀야 한다(해석).

## 쓰이는 자료구조·알고리즘

- **누적 접두 해시** — 블록 i의 키 = H(키 i−1, 블록 i). 접두가 같으면 키가 같고, 한 블록이 바뀌면 그 뒤 키가 모두 바뀐다(해시 체인).
- **TTL + 축출** — 프리픽스 캐시는 제공자가 TTL로, 의미 캐시는 우리가 TTL과 크기 상한(LRU 등)으로 관리한다([data-structure/10-lru-cache](../../data-structure/10-lru-cache/2-summary.md)).
- **최근접 탐색 + 임계값** — 저장 질문 임베딩에서 최근접 1개를 찾고 유사도로 적중을 판정한다. 많으면 HNSW 같은 ANN을 쓴다([05](../05-embeddings-and-similarity/2-summary.md), [16-vector-index-ann](../16-vector-index-ann/2-summary.md)).
- **파티션 키 = 정확 일치 해시** — 테넌트·버전·식별자 같은 "값이 의존하는 모든 것"을 키에 넣는 일반 캐시 규칙 그대로다([database/31](../../database/31-cache-key-versioning-and-serialization/2-summary.md)).

## 적용 — 풀어나가는 법

### 1. 증상 → 원리 → 확인

| 증상 | 원리 | 확인 |
|---|---|---|
| 캐시를 켰는데 비용·첫 토큰 지연이 그대로이거나 늘었다 | 접두에 가변값이 있어 키가 매번 다르다 / 최소 길이 미달 / TTL 안에 재사용이 없다 | 응답의 캐시 쓰기·읽기 토큰 비율, 프롬프트 앞부분 diff |
| 의미 캐시 도입 뒤 "엉뚱한 답" 신고 | 임계값이 뜻의 차이를 못 가름 | 적중 로그의 (질문, 저장 질문, 유사도) 표본 검토 |
| 다른 고객의 주문 정보가 답에 나옴 | 테넌트·사용자·식별자가 파티션 키에 없다 | 적중 로그에서 질문의 테넌트 ≠ 저장 질문의 테넌트 |
| 프롬프트를 고쳤는데 옛 답이 계속 나옴 | 모델·프롬프트 버전이 키에 없다 | 적중 항목의 생성 시각·버전 |

### 2. 프리픽스 캐시 — 프롬프트를 "안 바뀌는 것 먼저"로 배치

```text
  좋음:  [도구 정의] [시스템 프롬프트] [고정 문서·예시] ◄중단점  [대화 기록] [오늘 날짜] [질문]
  나쁨:  [현재 시각 2026-10-08T13:05:12Z] [요청 ID] [시스템 프롬프트] ...   ← 첫 블록부터 매번 다름
```

- 측정: Anthropic은 `cache_read_input_tokens ÷ (cache_read + cache_creation + input_tokens)`, OpenAI Responses는 `cached_tokens ÷ input_tokens`를 적중 비율 지표로 남긴다([23-llm-observability-and-cost](../23-llm-observability-and-cost/2-summary.md)).
- 도구 정의의 직렬화 순서(예: JSON 키 순서·도구 목록 순서)가 요청마다 바뀌지 않게 고정한다. 내용이 같아도 바이트가 다르면 다른 접두다(해석 — "100% 동일" 조건에서 따라 나옴).

### 3. 의미 캐시 — 파티션 키를 코드로 고정 (Java 21)

```java
record Partition(String tenantId, String locale, String model, String promptVersion,
                 String embeddingModel, String entityIds) {}

private static final Pattern ID = Pattern.compile("\\d{3,}");   // (예시) 주문번호 같은 식별자

static Partition partition(String tenantId, String locale, String model, String promptVersion,
                           String embeddingModel, String query) {
    var m = ID.matcher(query);
    var ids = new StringBuilder();
    while (m.find()) ids.append(m.group()).append(',');
    return new Partition(tenantId, locale, model, promptVersion, embeddingModel, ids.toString());
}
// 유사도 비교는 hash(partition)이 같은 항목끼리만 한다
```

(실험, OpenJDK 21.0.12 `eclipse-temurin:21-jdk`, 2026-10-08 — `java SemanticCacheKey.java`)

```text
t1 | 주문 1001 배송 상태 알려줘  | ids=1001,  | partition=a10833a8bcaf4575
t1 | 주문 1002 배송 상태 알려줘  | ids=1002,  | partition=1503a65fe8f93a7c
t2 | 주문 1001 배송 상태 알려줘  | ids=1001,  | partition=6fb9ef7dd83dea5b
t1 | 환불이 가능한가요          | ids=       | partition=a02f23b15e06ede5
```

- 주문 번호가 다르거나 테넌트가 다르면 파티션이 달라 유사도 비교 대상이 아예 아니다. 위 Python 실험의 두 오적중 유형이 구조적으로 막힌다.

### 4. 의미 캐시를 쓸지 고르는 기준

1. **답이 사람·시점에 따라 달라지는 질문은 제외**한다 — 주문 상태·잔액·권한이 걸린 답. 이런 질문은 정확 키 캐시나 원천 조회가 맞다.
2. 남은 범위(공개 FAQ·정책 설명 등)에서 라벨 붙은 질문 쌍으로 θ를 오프라인 평가한다. 오적중률을 목표로 θ를 정한다([19-llm-evaluation](../19-llm-evaluation/2-summary.md)).
3. 적중마다 (질문, 저장 질문, 유사도)를 로그로 남겨 표본 검토한다.
4. 지식이 바뀌면(정책 개정·문서 갱신) 해당 파티션을 비운다. TTL은 상한일 뿐 무효화 수단이 아니다.
5. 놓침이 동시에 몰리면 같은 질문으로 LLM을 여러 번 부른다. 요청 합치기(single-flight)를 둔다([reliability/29-cache-stampede](../../reliability/29-cache-stampede/2-summary.md)).

## 장애 시나리오와 대처

### 1. 프롬프트 앞부분의 시각·요청 ID → 프리픽스 캐시 적중 0 (⚠)

- **현상**: 프롬프트 캐시를 켰는데 비용·첫 토큰 지연이 줄지 않고, 오히려 입력 비용이 는다.
- **보이는 형태**: 매 요청 `cache_creation_input_tokens`(또는 `cache_write_tokens`)만 있고 읽기가 0이다.
- **원인**: 접두 키는 누적 해시라 첫 블록이 매번 다르면 그 뒤 전부 다른 키가 된다. 매번 쓰기 단가(1.25배)만 낸다(실험: 1.25배 vs 뒤로 옮기면 0.13배).
- **대처**: 가변값을 중단점 뒤로 옮긴다. 시스템 프롬프트에 초 단위 시각을 넣지 않는다. 직렬화 순서를 고정한다. 캐시 읽기 비율을 지표·알람으로 둔다.

### 2. 의미 캐시 임계값이 느슨 → 뜻이 반대인 질문에 같은 답 (⚠)

- **현상**: "환불이 불가능한가요?"에 "가능합니다" 답이 나간다.
- **보이는 형태**: 적중 로그에서 유사도는 높은데(실험 0.84) 뜻이 반대다. LLM 호출 로그에는 이 요청이 없다.
- **원인**: 표면이 비슷한 질문의 임베딩 유사도가 높게 나온다. 실험에서는 옳은 재사용(0.64·0.82)보다 반대 뜻(0.84)이 높아 어떤 θ로도 깨끗이 갈리지 않았다.
- **대처**: 의미 캐시 범위를 답이 바뀌어도 피해가 작은 공개 FAQ로 좁힌다. 라벨 쌍으로 θ를 평가한다. 재순위 모델로 적중 후보를 한 번 더 확인하는 방법도 있다([17](../17-hybrid-search-and-reranking/2-summary.md)).

### 3. 테넌트·사용자·권한을 키에 안 넣음 → 다른 사용자의 답 노출 (⚠)

- **현상**: A 고객사 사용자가 B 고객사 정책·데이터가 담긴 답을 받는다.
- **보이는 형태**: 질문 문장이 같아서 유사도 1.00으로 적중(실험: θ = 0.95에서도 적중). 보안 사고로 보고된다.
- **원인**: 파티션 키에 테넌트가 없었다. 유사도는 "누가 물었나"를 모른다.
- **대처**: 테넌트·권한 범위·언어를 파티션 키에 넣는다(실험: 넣자 사라짐). 개인 데이터가 섞인 답은 의미 캐시에 저장하지 않는다. 데이터 분류는 [security/27-pii-classification-masking-retention](../../security/27-pii-classification-masking-retention/2-summary.md).

### 4. 모델·프롬프트 버전을 키에 안 넣음 → 배포 뒤에도 옛 답 (⚠)

- **현상**: 프롬프트를 고쳐 배포했는데 일부 질문에는 고치기 전 말투·정책의 답이 나온다.
- **보이는 형태**: 적중 항목의 생성 시각이 배포 전이다. 캐시를 비우면 사라진다.
- **원인**: 값이 의존하는 것(모델·프롬프트 버전·임베딩 모델)이 키에 없었다. 일반 캐시의 버전 누락과 같은 사고다([database/31](../../database/31-cache-key-versioning-and-serialization/2-summary.md)).
- **대처**: 버전을 파티션 키에 넣어 배포가 곧 새 파티션이 되게 한다. 임베딩 모델을 바꾸면 저장 질문 임베딩도 다시 만든다(옛 공간과 섞지 않는다 — [05](../05-embeddings-and-similarity/2-summary.md)).

### 5. 최소 길이 미달·TTL 만료로 캐시가 조용히 안 됨

- **현상**: 프롬프트에 캐시 표시를 했는데 비용이 안 준다. 오류는 없다.
- **보이는 형태**: Anthropic에서 쓰기·읽기 토큰이 둘 다 0(최소 길이 미달), 또는 트래픽이 뜸한 시간대에 매번 쓰기만 발생(TTL 안에 재사용 없음).
- **원인**: 최소 길이 아래는 오류 없이 캐시하지 않는다(Anthropic 문서). TTL(Anthropic 기본 5분)보다 요청 간격이 길면 매번 새로 쓴다.
- **대처**: 캐시할 접두를 최소 길이 이상으로 묶는다. 요청 간격이 긴 작업은 긴 TTL(1시간·24h 보존)의 비용을 따져 고르거나 캐시를 끈다. 쓰기만 있고 읽기가 없는 비율을 알람으로 둔다.

## 핵심 문장

- 프리픽스 캐시는 제공자가 같은 접두의 계산(KV 상태)을 재사용하는 것이고, 의미 캐시는 앱이 비슷한 질문에 전에 만든 답을 재사용하는 것이다. 앞은 정확·안전, 뒤는 근사·위험하다.
- 프리픽스 캐시 키는 접두 전체의 누적 해시다. 안 바뀌는 것을 앞에, 시각·요청 ID 같은 가변값을 중단점 뒤에 둔다.
- 쓰기 요금이 있는 제공자·모델(Anthropic 5분 1.25배, OpenAI GPT-5.6 이후 1.25배 등)에서는 캐시 쓰기가 기본 입력보다 비싸다. 적중하지 않는 캐시는 비용을 늘린다 — 읽기 비율을 잰다.
- 의미 캐시의 임계값 하나로는 "같은 뜻"과 "비슷하지만 다른 뜻"을 깨끗이 가를 수 없다. 테넌트·버전·식별자는 정확 일치 파티션 키로 빼고, 답이 사람·시점마다 다른 질문은 범위에서 뺀다.
- 의미 캐시 적중은 LLM 호출 로그에 남지 않는다. 적중마다 (질문, 저장 질문, 유사도)를 기록해 감사한다.
