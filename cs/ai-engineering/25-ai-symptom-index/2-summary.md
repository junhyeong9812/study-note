# ai-engineering/25-ai-symptom-index — 증상 사전: 잘림·JSON 파싱 실패 · 같은 입력 다른 답 · 첫 토큰 지연·스트림 멈칫 · 429 지속 · 비용 급증 · 검색 엉뚱·결과 부족 · 모델 교체 뒤 품질 붕괴 · 평가 점수 흔들림 · 에이전트 반복 · 문서 속 지시를 따름 → 1차 확인·원인 후보·leaf — 정리 (힌트)

## 해결하는 문제

이 영역의 다른 노트는 **원리에서 증상으로** 간다.\
"출력 한도에 닿으면 생성이 멈춘다 → HTTP는 200이다 → 상태 코드만 보면 잘린 JSON을 성공으로 저장한다"처럼 쓴다.\
현장에서는 반대 방향이 필요하다.\
손에 든 것은 신고 한 줄이다. "요약이 가끔 중간에서 끊겨요", "429가 10분째 안 끝나요", "어제부터 비용이 두 배예요", "검색이 엉뚱한 문서를 줘요".

이 노트는 그 **역방향 색인**이다.

```text
  다른 노트 (정방향)                                    이 노트 (역방향)
  원리 --> 계약·전제가 깨지는 조건 --> 증상              증상 --> 1차 확인(로그·지표·필드) --> 원인 후보 --> leaf
  "중단 사유를 안 보면 잘린 응답이 성공으로 저장된다"     "JSON 파싱 실패다. 먼저 그 행의 중단 사유 필드부터"
```

쉬운 예: 택배 앱이 "배송 완료"를 띄웠다. 상자를 열어 보니 주문한 물건이 반만 들어 있다.\
배송 상태만 보면 성공이다. 상자 안 명세서를 봐야 "2개 중 1개는 재고 부족으로 따로 발송" 같은 사정이 보인다.

똑같은 구조다.\
LLM 호출의 실패는 예외로 보이지 않는 경우가 많다. HTTP는 200이고, 응답 본문도 있고, 비용도 청구된다.\
그래서 상태 코드 대신 **응답 안의 명세서**(중단 사유, 스트림의 종료·오류 이벤트, 응답 모델, 사용량의 토큰 종류, 시도 번호)가 첫 단서다.

실무 예:
- 고객 상담 요약이 가끔 DB에 끊긴 채 저장된다는 신고가 왔다.
- 이때 프롬프트부터 고치지 않는다. 그 행의 중단 사유, 스트림이 종료 이벤트로 끝났는지, 어느 모델이 응답했는지를 먼저 본다. 셋 중 무엇이 걸리는지에 따라 [11](../11-llm-api-client-contract/2-summary.md)·[14](../14-structured-output-and-tool-calling/2-summary.md)·[13](../13-model-routing-and-fallback/2-summary.md)로 갈린다.

  - *역색인*: "leaf → 증상" 목록을 "증상 → leaf" 목록으로 뒤집은 것([data-structure/32-inverted-index](../../data-structure/32-inverted-index/2-summary.md)).
  - *leaf 표기 `NN-k`*: 이 영역 NN번 노트의 「장애 시나리오와 대처」 k번째 시나리오다. 예: `11-2` = [11](../11-llm-api-client-contract/2-summary.md)의 시나리오 2(중단 사유를 확인하지 않아 잘린 응답을 저장). `NN 「…」`은 그 노트의 해당 제목 절이다.
  - *1차 확인*: 증상을 받았을 때 원인 후보를 가르려고 가장 먼저 보는 필드·지표·로그 한 가지. 확정이 아니라 후보 고르기다.
    - 흔한 오해: "200이면 모델 쪽은 정상이다." 스트리밍 응답은 200을 보낸 뒤에도 오류 이벤트를 보낼 수 있고, 출력 한도에 닿은 응답도 200이다(제공자별 동작 — [11](../11-llm-api-client-contract/2-summary.md)). 200은 응답 헤더를 보내는 시점의 "요청 성공"(RFC 9110 15.3.1)이다. 그 뒤 스트림이 끝까지 왔는지, 출력이 쓸 만한지는 말해 주지 않는다.
  - 이 노트는 leaf의 실험 수치를 옮기지 않는다. 증상이 어느 leaf의 어느 절로 가는지만 가리킨다. 숫자·문구는 leaf에서 읽는다.

### 0-1. 색인을 쓰기 전에 남겨 둘 것

색인의 1차 확인은 대부분 **호출 한 건의 기록 필드**다. 필드가 없으면 증상을 받고도 갈래를 못 고른다.

```text
  ① 식별      사용자 요청 ID · 시도 번호 · 기능 · 테넌트            ← 증폭(요청당 시도 수)과 비용 귀속
  ② 모델      요청 모델 · 응답 모델 · 프롬프트 버전 · 파라미터         ← 폴백·교체·버전 회귀
  ③ 결말      HTTP 상태 · 오류 type/code · retry-after             ← 429·400·5xx 분류
              중단 사유 · 스트림 종료 이벤트 수신 여부 · 스트림 안 error 이벤트
  ④ 사용량    입력 · 캐시 읽기 · 캐시 쓰기 · 출력 토큰(제공자별 정규화)  ← 비용 급증 분해
  ⑤ 시각      보냄 · 첫 청크 · 마지막 청크 · 최대 청크 간격             ← TTFT·멈칫
  ⑥ 검색      질의 · top-k 청크 ID와 점수 · 프롬프트에 넣은 청크 ID · 응답의 출처 ID   ← RAG 단계 판정
  ⑦ 도구      도구 이름 · 인자 해시 · 멱등 키 · 결과 분류 · 실행 시각      ← 반복·중복 부작용·인젝션 경로
```

- ①~⑤는 [23](../23-llm-observability-and-cost/2-summary.md)의 스팬·지표가 정본이다. OTel GenAI 규약 이름을 쓸지, 자체 이름을 쓸지도 거기서 정한다.
- ⑥은 [15](../15-rag-pipeline/2-summary.md) 「적용 — 1. 답이 틀렸을 때 — 어느 단계인가」의 기록 항목이다.
- ⑦은 [20](../20-agent-loop-and-tool-safety/2-summary.md) 「적용 — 3. 진단」과 [22](../22-prompt-injection-and-llm-security/2-summary.md) 「적용 — 3. 진단」의 "볼 것"이다.
- 프롬프트·응답 **원문**은 이 목록에 없다. 원문 기록은 기본 끔이 원칙이고, 켤 때의 통제는 [23-2](../23-llm-observability-and-cost/2-summary.md)를 따른다.

### 0-2. 실험: 응답 기록 한 줄을 필드 순서로 분류 (`Triage.java`)

호출 기록 11줄(합성, 예시)을 두 방식으로 분류했다. (가) HTTP 상태만 본다. (나) 0-1절 ③④의 필드를 정해진 순서로 본다 — 429·400 → 스트림 error 이벤트 → 종료 이벤트 → 중단 사유 → 응답 모델 → 스키마 → 캐시 사용량. 분류 규칙과 순서는 이 노트가 만든 모형이고, 어느 제공자·도구의 기능이 아니다.

```java
static String triage(Call c) {
    if (c.http() == 429) {
        if ("enforced_spend_limit_reached".equals(c.errorCode()))
                                       return "429 + 지출 한도 code(retry-after 없음) → 기다려도 안 풀림, 재시도 중지·경보 [11-5]";
        if (c.attempts() > 1)          return "429 + 같은 요청 시도 " + c.attempts() + "회 → 재시도가 한도를 채움 [11-4 · 13-2]";
        if (c.retryAfterSec() == null) return "429, retry-after 없음, 한도 소진 code 아님 → 백오프+지터, 횟수·총 시간 제한 [11 §5]";
        return "429, retry-after " + c.retryAfterSec() + "s → 기다렸다 재시도 [11 §5]";
    }
    if (c.http() == 400)               return "400 → 재시도 무의미, 요청·모델 호환 확인 [07-4 · 11 §5]";
    if (c.http() != 200)               return "기타 " + c.http() + " → 재시도 분류표 [11 §5]";
    if (c.errorEvent())                return "200 + 스트림 error 이벤트 → 반쪽 응답 [11-1]";
    if (!c.terminalEvent())            return "200 + 종료 이벤트 없음 → 끊긴 스트림 [11 §6]";
    switch (c.stopReason()) {
        case "max_tokens", "length", "incomplete" -> { return "잘림(" + c.stopReason() + ") → 저장 금지 [11-2 · 14-2 · 04-2]"; }
        case "refusal" ->                         { return "거부 → 재시도 말고 별도 경로 [14-3]"; }
        default -> {}
    }
    if (!c.reqModel().equals(c.respModel())) return "요청 " + c.reqModel() + " ≠ 응답 " + c.respModel() + " → 폴백 경로 [13-1 · 13-3]";
    if (!c.schemaValid())              return "자연 종료인데 스키마 위반 → 검증 경로 [14-1]";
    if (c.cacheWrite() > 0 && c.cacheRead() == 0) return "캐시 쓰기만, 읽기 0 → 접두 가변값·TTL [12-1 · 12-5]";
    return "계약상 성공 → 품질 문제면 평가·검색 쪽 [19 · 15]";
}
```

- `§n`은 그 노트 「동작·원리」의 n번 절이다(11 §5 = 「429·529/503과 Retry-After」, 11 §6 = 「끊긴 스트림을 어떻게 다시 하나」).
- 잘림 신호는 제공자마다 필드부터 다르다. Anthropic은 `stop_reason: max_tokens`, OpenAI Chat Completions는 `finish_reason: length`다. OpenAI Responses는 `status: incomplete`에 `incomplete_details.reason: max_output_tokens`가 붙는다(`incomplete`는 사유가 아니라 상태 값이고, 사유가 다른 값일 수도 있다). 코드의 `stopReason`은 이 셋을 한 칸에 정규화한 모형 값이다. 매핑은 [11](../11-llm-api-client-contract/2-summary.md) 「중단 사유 — 성공처럼 보이는 실패」에서 읽는다.
- 429에서 `retry-after`가 없는 것만으로는 한도 소진이라고 정하지 않는다. 일시 한도 429도 헤더 없이 올 수 있고, 그때는 백오프한다(OpenAI "Rate limits"). Anthropic 지출 상한 429는 `retry-after`가 없고 `error.details.error_code`가 `enforced_spend_limit_reached`다([11-5](../11-llm-api-client-contract/2-summary.md)). 그래서 모형은 code를 먼저 본다.

(실험, JDK 21.0.12 `eclipse-temurin:21-jdk` 컨테이너 `--network none`, `java Triage.java` 단일 파일 실행, 결정적 — 1회 실행, 2026-10-08)

```text
r01  상태만=성공         분류=계약상 성공 → 품질 문제면 평가·검색 쪽 [19 · 15]
r02  상태만=성공         분류=200 + 스트림 error 이벤트 → 반쪽 응답 [11-1]
r03  상태만=성공         분류=잘림(max_tokens) → 저장 금지 [11-2 · 14-2 · 04-2]
r04  상태만=성공         분류=거부 → 재시도 말고 별도 경로 [14-3]
r05  상태만=성공         분류=200 + 종료 이벤트 없음 → 끊긴 스트림 [11 §6]
r06  상태만=실패(429)    분류=429, retry-after 20s → 기다렸다 재시도 [11 §5]
r07  상태만=실패(429)    분류=429 + 같은 요청 시도 6회 → 재시도가 한도를 채움 [11-4 · 13-2]
r08  상태만=실패(429)    분류=429 + 지출 한도 code(retry-after 없음) → 기다려도 안 풀림, 재시도 중지·경보 [11-5]
r09  상태만=성공         분류=요청 m-main ≠ 응답 m-fallback → 폴백 경로 [13-1 · 13-3]
r10  상태만=성공         분류=캐시 쓰기만, 읽기 0 → 접두 가변값·TTL [12-1 · 12-5]
r11  상태만=실패(400)    분류=400 → 재시도 무의미, 요청·모델 호환 확인 [07-4 · 11 §5]
상태 코드만 본 집계: {성공=7, 실패(400)=1, 실패(429)=3}
```

- 관찰
  - 상태 코드만 보면 7줄이 "성공"이다. 그중 응답 계약을 어긴 줄이 넷이다(반쪽 응답 r02·잘림 r03·거부 r04·끊긴 스트림 r05). 둘은 응답 자체는 계약을 지켰지만 다른 leaf로 갈 후보다(폴백 r09·캐시 쓰기만 r10). 아무 규칙에도 안 걸린 줄은 r01이다. 일곱 줄이 가야 할 leaf가 서로 다르다.
  - 429 세 줄도 처방이 셋이다. 기다리면 되는 것(r06), 재시도를 줄여야 하는 것(r07), 재시도를 멈추고 경보를 내야 하는 것(r08).
  - 순서가 결과를 정한다. r08은 시도가 3회였지만 지출 한도 code 규칙이 먼저 걸렸다. 재시도 폭주와 한도 소진이 겹친 경우에는 둘 다 확인해야 한다(해석).
  - r10 같은 캐시 규칙은 한 줄로는 약한 증거다. 첫 요청은 원래 쓰기만 한다. 비율로 봐야 한다(아래 SQL 실험 (3)).
- 한계(모형): 규칙은 후보를 고를 뿐이다. 예를 들어 r09의 폴백 자체는 정상 동작일 수 있다. 품질 문제의 원인인지는 응답 모델별로 지표를 나눠 본 뒤에 정한다([13-3](../13-model-routing-and-fallback/2-summary.md)).

#### 실험: 같은 1차 확인을 호출 기록 테이블에서 (`first_queries.sql`)

(실험, `postgres:17` = PostgreSQL 17.11, docker `--rm --pull never --network none --cpus=2`, 합성 데이터 — 평소 날(2026-10-07) 1,000건, 사고 날(2026-10-08) 1,000건 + 즉시 재시도 120줄, 결정적 — `generate_series` 나머지 연산으로 생성, 2026-10-08)

사고 날에는 세 가지를 일부러 넣었다. 프롬프트 v2가 캐시 접두 앞을 바꿔 쓰기만 생김, 30분간 429에 같은 요청을 즉시 4번 더 재시도, 50건 중 1건꼴로 폴백 모델이 응답.

```sql
-- (2) 429 — retry-after 유무와 요청당 시도 수(증폭)
SELECT ts::date AS d, count(*) FILTER (WHERE http_status = 429) AS n429,
       count(*) FILTER (WHERE http_status = 429 AND retry_after_s IS NULL) AS n429_no_retry_after,
       round(count(*)::numeric / count(DISTINCT request_id), 3) AS calls_per_request,
       max(attempt) AS max_attempt,
       round(count(*) FILTER (WHERE request_id IN (SELECT request_id FROM llm_call WHERE http_status = 429))::numeric
             / nullif(count(DISTINCT request_id) FILTER (WHERE request_id IN (SELECT request_id FROM llm_call WHERE http_status = 429)), 0), 2) AS calls_per_429_request
FROM llm_call GROUP BY 1 ORDER BY 1;
-- (3) 프롬프트 버전별 캐시 — 읽기 비율, 쓰기만 있는 호출 수
SELECT prompt_version,
       round(sum(cache_read)::numeric / nullif(sum(input_tokens + cache_read + cache_write), 0), 3) AS read_ratio,
       count(*) FILTER (WHERE cache_write > 0 AND cache_read = 0) AS write_only
FROM llm_call WHERE http_status = 200 GROUP BY 1 ORDER BY 1;
-- (6) 같은 토큰, 다른 비용 — 단가는 예시(입력 1.0 · 캐시 쓰기 1.25 · 캐시 읽기 0.1 · 출력 5.0, 100만 토큰당)
SELECT ts::date AS d, sum(input_tokens + cache_read + cache_write) AS input_total,
       round((sum(input_tokens) * 1.0 + sum(cache_write) * 1.25 + sum(cache_read) * 0.1 + sum(output_tokens) * 5.0) / 1e6, 2) AS cost
FROM llm_call GROUP BY 1 ORDER BY 1;
```

### 3. 첫 토큰이 늦다 · 스트림이 멈칫한다

먼저 **어느 시각이 늘었는지**를 나눈다. 보냄 → 첫 청크(TTFT) → 청크 사이 간격 → 마지막 청크(E2E).
"첫 청크"는 OTel 클라이언트 지표의 정의다. Anthropic 스트림은 글자보다 `message_start` 이벤트가 먼저 오므로, 첫 출력 토큰(첫 `content_block_delta`) 시각은 이름을 달리해 따로 남긴다([10](../10-inference-latency-metrics/2-summary.md)). 그리고 측정 위치가 클라이언트인지 서버인지 확인한다([10](../10-inference-latency-metrics/2-summary.md) 「적용 — 1. 클라이언트에서 네 시각을 남긴다」).

### 4. 429가 끝나지 않는다

- 재시도·지터·토큰 버킷의 일반 원리는 [reliability/06](../../reliability/06-retry-backoff-jitter/2-summary.md)·[reliability/11](../../reliability/11-rate-limiter/2-summary.md), 한도 응답의 계약은 [api-design/14](../../api-design/14-rate-limit-and-quota-contracts/2-summary.md)가 정본이다.

### 5. 비용이 급증한다

먼저 **비용을 분해**한다. 무엇이 늘었나 — 요청 수, 요청당 시도 수, 요청당 입력 토큰, 요청당 출력 토큰, 토큰 종류(캐시 읽기 ↔ 쓰기). 그다음 기능·테넌트·모델·프롬프트 버전으로 나눈다([23](../23-llm-observability-and-cost/2-summary.md) 「적용 — 3. 진단 표」).

```text
  "비용이 두 배"
     │
     ├─ 대시보드 비용 ≠ 청구서 ─────────────────────────────────────▶ 계산 쪽 문제
     │    ├─ 제공자를 바꾼 달부터 어긋남 ─────────────────────────────▶ 캐시 토큰 포함 규칙 혼동                23-1

     ├─ 토큰 총량은 그대로, 비용만 늚 ─────────────────────────────────▶ 캐시 읽기 → 쓰기로 바뀜                  12-1 · 12-5
     ├─ 요청당 시도 수가 늚 ────────────────────────────────────────▶ 재시도 중첩·처음부터 재시도               13-2 · 11-3
     ├─ 요청당 입력 토큰이 늚
     │    ├─ 모델 교체 시점부터 ─────────────────────────────────────▶ 토크나이저 변경                          04-3

     │    └─ 요청 하나에 같은 도구 호출이 수백 ────────────────────────▶ 에이전트 루프 예산 없음                   20-1
     ├─ 소수 계정의 긴 입력 반복 ──────────────────────────────────────▶ 무제한 소비                              22-4
```

|---|---|---|---|
| 토큰 그래프는 평평한데 청구서가 뜀 | 토큰 종류별 합(0-2 SQL (5)·(6)), 프롬프트 버전별 캐시 읽기 비율 | 접두 앞 가변값으로 캐시 미적중, 최소 길이 미달·TTL 만료 | [12-1](../12-prompt-and-semantic-caching/2-summary.md) · [12-5](../12-prompt-and-semantic-caching/2-summary.md) |

| 하룻밤 사이 월 예산 초과 | 사용자·테넌트별 토큰, 입력 길이 분포 | 상한 없는 입력·호출 | [22-4](../22-prompt-injection-and-llm-security/2-summary.md) |

- 하지 말 것: 총 토큰 그래프 하나로 원인을 찾는다. 0-2 SQL 실험 (6)처럼 총량이 같아도 비용은 다를 수 있다.

### 7. 모델 교체 뒤 품질이 무너졌다

|---|---|---|---|

| PPL이 절반인 모델로 바꿨는데 그대로 | 두 모델의 토크나이저가 같은가 | 토큰당 정규화 값의 분모가 다름 | [03-1](../03-cross-entropy-and-perplexity/2-summary.md) |
| 베이스 올린 뒤 어댑터 로드 실패·출력 이상 | 어댑터에 저장된 베이스 ID·가중치 해시 | 다른 W0 위의 ΔW | [24-3](../24-fine-tuning-vs-rag-decision/2-summary.md) |

- 처방의 방향: 교체는 **고정 평가셋 + 버전 열 + 한 번에 전환**의 세 장치로 한다. 임베딩은 이중 색인 후 전환([18](../18-index-freshness-and-reembedding/2-summary.md) 「이중 색인 후 전환」), 생성 모델은 짝 비교 게이트([19](../19-llm-evaluation/2-summary.md)), 어댑터는 베이스 ID 대조([24](../24-fine-tuning-vs-rag-decision/2-summary.md)).
- 이 증상의 함정은 **오류가 없다**는 점이다. 같은 차원이면 계산은 되고 값만 무의미하다. 크게 실패하는 쪽(차원 오류)이 오히려 빨리 드러난다([18-5](../18-index-freshness-and-reembedding/2-summary.md)).

### 10. 모델이 문서 속 지시를 따른다

```text
     ├─ 답에 권한 밖 문서 내용 ────────────────────────────────────────▶ 검색 단계에서 권한 미필터               15-4 · 22-5
```

### 2. 첫 쿼리 모음 (PostgreSQL 17 — 0-1절 필드를 담은 `llm_call` 테이블, 이름은 예시)

0-2 SQL 실험에서 돌린 것을 증상별로 다시 놓았다.

```sql
-- 잘림: 날짜·기능별 중단 사유 (1절)
SELECT ts::date, feature, stop_reason, count(*) FROM llm_call WHERE http_status = 200 GROUP BY 1, 2, 3 ORDER BY 1, 2, 3;
-- 429 증폭: 429를 겪은 요청의 시도 수와 retry-after 유무 (4절)
SELECT request_id, count(*) AS attempts, bool_or(retry_after_s IS NULL) AS any_without_retry_after
FROM llm_call WHERE request_id IN (SELECT request_id FROM llm_call WHERE http_status = 429)
GROUP BY 1 ORDER BY attempts DESC LIMIT 20;
-- 비용: 프롬프트 버전별 캐시 읽기 비율 (5절)
SELECT prompt_version, round(sum(cache_read)::numeric / nullif(sum(input_tokens + cache_read + cache_write), 0), 3)
FROM llm_call WHERE http_status = 200 GROUP BY 1;
-- 경로: 요청 모델 ≠ 응답 모델 비율 (1·2·7절)
SELECT ts::date, avg((resp_model IS DISTINCT FROM req_model)::int) FROM llm_call WHERE http_status = 200 GROUP BY 1 ORDER BY 1;
```

(실험, `postgres:17` = PostgreSQL 17.11, 0-2와 같은 합성 데이터, 결정적 — 1회 실행, 2026-10-08. 429 질의는 `LIMIT 3`으로 앞 3줄만 봤다)

```text
잘림   2026-10-07 summary max_tokens 25 · 2026-10-08 summary max_tokens 24 · chat은 두 날 모두 end_turn만
429    request_id 2301 · 2302 · 2300 — attempts 5, any_without_retry_after f
캐시   v1 0.833 · v2 0.000
경로   2026-10-07 0.0000 · 2026-10-08 0.0196   (= 폴백 19 / 200 응답 970)
```

- 네 질의 모두 0-2 실험의 테이블 정의 그대로 돌아간다. 잘림은 기능 하나에, 429 증폭은 요청 단위로, 캐시 미적중은 프롬프트 버전 하나로, 폴백은 날짜 하나로 좁혀진다.
- 검색 쪽 진단 질의(고아 청크·중복 청크·모델별 행 수)는 [18](../18-index-freshness-and-reembedding/2-summary.md) 「진단 질의」, 필터·recall 진단은 [16](../16-vector-index-ann/2-summary.md) 「recall을 운영에서 재기」가 정본이다.

## 장애 시나리오와 대처

색인을 **쓰는 쪽**에서 나는 사고다.

### 1. HTTP 상태만 보고 "모델은 정상"이라고 닫는다 ⚠

- 현상: 잘림·반쪽 응답 신고가 계속 오는데, 호출 로그의 상태 코드가 전부 200이라 "모델 쪽 문제 없음"으로 결론 냈다.
- 보이는 형태: 0-2 실험처럼 "성공" 7줄 가운데 4줄이 응답 계약을 어겼다. 중단 사유·종료 이벤트 필드는 로그에 없거나 아무도 보지 않는다.
- 원인: 200은 헤더를 보낼 때의 판단이라 스트림 완료·출력 유효성을 말하지 않는다. 스트림 오류·잘림·거부·폴백은 200 안에 있다.
- 대처: 성공 판정을 "자연 종료 + 종료 이벤트 수신 + 스키마 통과"로 바꾸고([11](../11-llm-api-client-contract/2-summary.md) 「계약을 코드로 고정한다」), 중단 사유 분포를 대시보드에 둔다.

### 2. 첫 원인 후보에서 조사를 닫는다 ⚠

- 현상: 429 폭주에 "제공자 한도를 올려 달라"고 요청했다. 한도가 올라간 뒤에도 장애 때마다 같은 일이 반복된다.
- 보이는 형태: 429를 겪은 요청의 시도 수가 크다. 층마다 재시도가 켜져 있다.
- 원인: 한도 부족과 재시도 증폭이 함께 있었다. 첫 후보(한도)만 처리했다.
- 대처: 4절 그림의 갈래를 모두 확인한다. 0-2 SQL (2)처럼 평균이 아니라 429를 겪은 요청 단위로 시도 수를 센다([11-4](../11-llm-api-client-contract/2-summary.md) · [13-2](../13-model-routing-and-fallback/2-summary.md)).

### 3. 기록 필드가 없어 색인을 쓸 수 없다

- 현상: "일부 사용자만 답이 이상하다"는 신고를 재현하지 못하고 몇 주를 보낸다.
- 보이는 형태: 로그에 응답 모델·라우팅 이유·프롬프트 버전·시도 번호가 없다. 품질 지표는 전체 평균 하나다.
- 원인: 0-1절의 ②③이 기록되지 않았다. 경로 차이를 볼 방법이 없다.
- 대처: 요청 모델·응답 모델·라우팅 이유·폴백 여부·시도 번호를 매 호출 남기고 지표를 그 차원으로 나눈다([13-3](../13-model-routing-and-fallback/2-summary.md) · [23](../23-llm-observability-and-cost/2-summary.md)). 26 사건 2의 sticky 라우팅 실험이 이 필드가 왜 필요한지 보인다.

### 4. "우리 쪽" 또는 "제공자 쪽"으로 단정한다

- 현상: 품질 저하를 제공자 탓으로 돌리고 기다렸는데, 실제로는 같은 날 배포한 프롬프트 v2가 원인이었다. 또는 그 반대.
- 보이는 형태: 변경 이력(배포·설정·라이브러리)과 제공자 공지를 같은 시간축에 놓은 자료가 없다.
- 원인: ①(언제부터)을 한쪽 변경 목록으로만 대조했다.
- 대처: 고정 평가셋을 주기적으로 돌려 날짜별 점수를 남기고([19](../19-llm-evaluation/2-summary.md) · [07-5](../07-decoding-and-nondeterminism/2-summary.md)), 우리 변경과 제공자 공지를 한 타임라인에 둔다. 사후 분석 형식은 [reliability/26](../../reliability/26-incident-response-and-postmortem/2-summary.md).

### 5. 고친 뒤 같은 증상을 다시 잡을 장치를 두지 않는다 ⚠

- 현상: 캐시 미적중을 고쳤는데, 석 달 뒤 다른 사람이 프롬프트 앞에 날짜를 넣어 같은 비용 급증이 났다.
- 보이는 형태: 지난번 사후 분석에 "원인과 수정"만 있고 지표·경보·테스트 항목이 없다.
- 원인: 증상 → 원인 → 수정에서 멈췄다. 같은 증상을 자동으로 볼 신호를 만들지 않았다.
- 대처: 절마다 1차 확인 칸을 지표로 만든다 — 잘림 비율, 429를 겪은 요청의 시도 수, 캐시 읽기 비율, 응답 모델 비율, 고정 질의셋 recall, 고정 평가셋 점수, 루프 중단 사유 분포. 지표가 사라지는 것도 경보한다([23-4](../23-llm-observability-and-cost/2-summary.md)).

## 핵심 문장

- 이 노트는 증상에서 leaf로 가는 역색인이다. 증상 → 1차 확인(필드·지표 하나) → 원인 후보 → leaf의 장애 시나리오 순으로 읽고, 숫자는 leaf에서 확인한다.
- LLM 호출의 실패는 HTTP 200 안에 숨는다. 중단 사유, 스트림 종료·오류 이벤트, 응답 모델, 토큰 종류별 사용량, 시도 번호가 1차 확인의 재료다.
- 429와 비용 급증은 먼저 분해한다. 429는 기다리면 풀리는 것과 아닌 것으로, 비용은 요청 수·시도 수·토큰 종류로. 평균은 증폭과 종류 변화를 희석한다.
- 검색 품질 문제는 어느 단계에서 정답이 떨어졌는지(색인 → top-k → 프롬프트 → 생성)를 먼저 가린다. 모델 교체 뒤의 붕괴는 오류 없이 오는 경우가 많다.
- 평가 점수의 흔들림은 표본·비결정성·판정자 편향의 크기를 먼저 잰다. 모델이 문서 속 지시를 따르는 증상은 모델 밖 결정적 통제로 피해를 막는다.
- 고친 뒤에는 그 증상의 1차 확인 칸을 지표·경보로 만든다.
