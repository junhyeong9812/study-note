# ai-engineering/20-agent-loop-and-tool-safety — 정답

## 정답

### 1. 워크플로와 에이전트

- 워크플로: 모델과 도구를 미리 정한 코드 경로로 엮는다. 에이전트: 모델이 과정과 도구 사용을 동적으로 지시한다("Building effective agents", 2024-12-19).
- 먼저 물을 것: 고정 경로로 풀리는가. 같은 글은 가장 단순한 해법에서 시작하라고 하고, 많은 경우 검색과 예시를 곁들인 단일 호출로 충분하다고 적는다. 에이전트는 지연·비용을 내고 유연성을 산다.

### 2. 누적 토큰

- 식: `500·T + 300·T(T−1)/2`.
- 8턴: 4,000 + 300×28 = **12,400**. 1000턴: 500,000 + 300×499,500 = **150,350,000**(실험 A 출력과 같음).
- 턴 125배에 토큰 약 12,000배. 매 턴 이력 전체를 자르지 않고 다시 보내고 턴마다 일정량이 쌓이는 이 예시에서는 누적이 턴 수의 제곱에 비례한다. 오래된 도구 결과를 지우거나 요약하면 이 모양이 아니다.

### 3. 예산 하나만으로 안 되는 이유

- 턴 상한만: 한 턴의 관측이 거대하면(큰 도구 결과) 적은 턴으로도 토큰이 폭증한다.
- 토큰 상한만: 느린 도구 호출이 사용자 마감을 넘길 수 있다.
- 마감만: 짧은 시간에 빠른 호출을 많이 해 비용이 튈 수 있다.
- 반복 탐지만: 인자를 바꾸면 피해 간다(4번).
- 실험 A에서 네 예산이 각각 다른 지점(8턴·10턴·10턴·8턴)에서 루프를 멈췄다.

### 4. 정확 일치 반복 탐지

- 세 서명이 번갈아 나오므로 각 서명이 4번째로 나오는 **10턴째**에 멈췄다(실험 A, 종료 사유 REPEAT, 입력 18,500토큰).
- 인자를 매번 조금씩 바꾸면 서명이 매번 달라 정확 일치 탐지는 걸리지 않는다. 도구 이름 단위 횟수·연속 실패 횟수 상한과 토큰 예산을 함께 둔다. 인자는 정규화해서 비교한다.

### 5. 시도마다 새 키

- 타임아웃은 "실패"가 아니라 "모름"이다. 첫 호출이 이미 처리됐을 수 있다.
- 시도마다 새 키를 만들면 서버는 두 요청을 다른 요청으로 본다. 키가 없는 것과 같다(실험 B: 키 없음 2회, 시도마다 새 키 2회, 행동마다 고정 키 1회 + 재생).
- 키는 루프가 **행동을 결정한 시점**에 만든다: 실행 ID + 단계 ID, 또는 의도 하나를 가리키는 업무 키(`refund:order-42:req-7` — 한 주문에 부분 환불이 여러 번 가능하므로 환불 요청 ID까지 넣는다). 같은 키에 다른 금액이 오면 재생하지 말고 오류로 거절한다. 도구 호출 블록의 ID는 같은 호출의 재실행은 막지만, 모델 호출을 다시 하면 새 ID로 같은 행동이 제안될 수 있으므로(해석) 업무 키를 함께 쓴다. 저장소 설계는 [reliability/13-idempotency](../../reliability/13-idempotency/2-summary.md).

### 6. 오류의 두 경로

- MCP 2026-07-28 "Tools" Error Handling: 모르는 도구·잘못된 요청·서버 오류 = JSON-RPC 오류(프로토콜 오류). API 실패·입력 검증·업무 규칙 오류 = 결과 안의 `isError: true`(도구 실행 오류). 클라이언트는 실행 오류를 모델에 제공해 스스로 고치게 하는 것이 SHOULD.
- "모델이 고쳐도 안 되는" 오류(권한 없음·계속되는 업스트림 장애)를 모델에게만 맡기면 모델은 인자를 바꿔 계속 시도한다. 실험 A의 스텁이 그 모양이고, 예산이 없을 때 1000턴까지 갔다.
- 대처: 오류에 "재시도 무의미"를 명시하고, 루프가 연속 실패를 세서 멈춘다. 업스트림 장애는 서킷 브레이커로 끊는다. 일시적 503·429의 재시도는 모델이 아니라 코드가 지연·횟수·마감 예산 안에서 한다(RFC 9110 15.6.4: 503은 일시적, `Retry-After` MAY).

### 7. 마감 뒤 부작용

- 사용자 요청의 마감(취소 신호)이 루프와 도구 호출까지 전파되지 않았다.
- 실험 C: 마감을 모르는 루프는 부작용 6회 중 4회를 마감 뒤에 냈다. 마감 시각을 넘기고 **도구 실행 직전**에 확인하자 마감 뒤 0회였다.
- 진행 중 호출을 실제로 끊는 법은 [reliability/09-cancellation-propagation](../../reliability/09-cancellation-propagation/2-summary.md). 길어질 작업은 요청 밖 비동기 작업으로 뺀다.

### 8. 되돌릴 수 없는 호출

- MCP "Tools": 도구 호출을 거부할 수 있는 사람이 루프 안에 있어야 한다(SHOULD), 민감한 작업에 확인 프롬프트, 호출 전에 도구 입력을 사용자에게 보여 줄 것(클라이언트 SHOULD).
- OWASP LLM06: 고위험 행동은 사람 승인, 확장 기능·권한·자율성을 최소로, 사용자 맥락으로 실행.
- 권한 검사는 **하류 시스템**에 둔다. OWASP LLM06의 complete mediation: 행동이 허용되는지를 LLM이 판단하게 두지 말고 하류 시스템에서 모든 요청을 보안 정책으로 검증한다.
