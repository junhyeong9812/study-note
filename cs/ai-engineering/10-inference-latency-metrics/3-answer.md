# ai-engineering/10-inference-latency-metrics — 정답

## 정답

### 1. 종단 지연 하나로 놓치는 것

- 같은 종단 지연이라도 "오래 빈 화면 뒤 한꺼번에"와 "바로 시작해 꾸준히"는 체감이 전혀 다르다.
- 재생 중 끊김(토큰 사이의 긴 간격)도 종단 지연에 묻힌다.
- 첫 토큰 지연은 주로 대기열 + 프리필이(vLLM 서버 TTFT는 토크나이즈 같은 입력 처리도 포함), 토큰 사이 지연은 디코드가 정한다(DistServe 초록: 프리필 = TTFT, 디코드 = TPOT). 원인과 대책이 다르니 따로 잰다.

### 2. 시간축

```text
 클라이언트 보냄 → [게이트웨이·네트워크] → 서버 도착 → [대기열] → [프리필] → 첫 토큰 → [디코드 …] → 마지막 토큰 → 클라이언트 받음
 |←──────────── 클라이언트 TTFT ────────────────────────────→|
                                 |←── 서버 TTFT ──────→|
 |←──────────────────────────── 종단 지연 ───────────────────────────────────────────────→|
                                                              |←ITL→| 출력 사이 간격 하나하나
```

- 서버 TTFT는 서버 도착부터(vLLM은 토크나이즈 시작 시각), 클라이언트 TTFT는 요청을 보낸 순간부터다.

### 3. TPOT 계산

- TPOT = (1,403 − 645) / (40 − 1) = 758 / 39 ≈ 19.4 ms. 실험 steady 5회차(19.42 ms)와 같다.
- 600 ms 멈춤이 더해지면: (758 + 600) / 39 ≈ 34.8 ms. 실험 stall(34.67~34.83 ms)과 같다.
- 600 ms 끊김이 "토큰당 15 ms 느려짐"으로 보인다. 끊김은 ITL 최댓값(실험 620 ms)으로 보인다.

### 4. 묶음 전송의 TPOT와 ITL

- 실험 bundle4: TPOT 17.50~17.52 ms, 이벤트 간격 평균 75.8 ms, 이벤트 10개.
- 토큰 생성 속도 목표는 TPOT로 판정한다. 이벤트 간격은 토큰이 아니라 청크 사이 간격이라 4배쯤 크게 나온다.
- 화면 끊김 목표라면 청크 간격으로 판정한다. 목적에 따라 지표를 고르고 이름에 단위를 적는다.

### 5. TTFT 셋의 시작점

| 지표 | 시작 | 끝 |
|---|---|---|
| vLLM `vllm:time_to_first_token_seconds` | 프런트엔드 도착(토크나이즈 시작) | 첫 토큰 |
| OTel `gen_ai.server.time_to_first_token` | 서버(규약 설명: 대기열·프리필 시간을 보는 지표) | 첫 토큰 생성 |
| OTel `gen_ai.client.inference.time_to_first_chunk` | 클라이언트가 요청을 보낸 때 | 첫 청크를 받은 때 |

- 사용자 체감에 가장 가까운 것은 클라이언트 쪽(time_to_first_chunk)이다. 게이트웨이·네트워크·연결까지 들어간다.
- OTel GenAI 규약은 상태가 Development라 이름이 바뀔 수 있다(2026-10-08 확인).

### 6. 1토큰 응답과 평균 TPOT

- **낮다.** 1토큰 응답의 TPOT가 0으로 들어가 평균을 끌어내린다. 실험: 0 포함 17.98 ms, 제외 23.97 ms(2회차 18.01 / 24.02 ms).
- `vllm bench serve`는 1토큰 이하 요청을 TPOT 통계에서 뺀다. Prometheus 지표는 0으로 기록한다. 그래서 같은 서버의 TPOT가 도구마다 다를 수 있다고 vLLM 문서가 적는다.

### 7. 멈칫을 보는 지표

- 추가할 것: 청크 간격(ITL) 히스토그램의 p99와 **요청별 최대 간격**의 분위.
- p99로도 못 잡는 경우: 멈칫이 전체 간격의 1%보다 드물 때. 실험에서는 435개 중 5개(약 1.1%)라 p99에 겨우 걸렸다. 더 드물면 p99는 평소 값을 보인다.
- 그래서 요청마다 최대 간격을 하나 뽑아 그 분포(p95 등)를 본다.

### 8. 클라이언트 TTFT만 오를 때

- 의심 구간: 서버 도착 전 — 게이트웨이·프록시, 네트워크, DNS·TLS 연결 수립, 클라이언트 쪽 연결 풀 대기.
- 확인: 클라이언트 TTFT − 서버 TTFT의 차이 추이(실험에서 평소 약 145 ms, 첫 요청은 약 270~330 ms), 게이트웨이 지연 지표, 새 연결 비율.
- 서버 TTFT가 그대로면 모델·대기열 문제가 아니다.

### 9. goodput

- 처리량은 지연 목표를 어긴 요청도 센다. goodput은 지연 목표를 기준으로 용량을 잰다. DistServe는 "SLO 달성 목표(예: 90%)를 지키며 GPU당 감당할 수 있는 최대 요청률"로 정의했다.
- 대시보드 계산: 먼저 SLO 달성률 = `TTFT ≤ 목표 그리고 토큰 간 지연 ≤ 목표`인 요청 수 / 전체 요청 수(구간별)를 낸다. 이 비율 자체는 goodput이 아니다.
- goodput은 이 달성률이 목표(예: 90%) 이상으로 유지되는 최대 요청률이다. 부하를 올려 가며 달성률이 목표 아래로 떨어지기 직전의 요청률을 찾는다(GPU 수로 나누면 DistServe의 GPU당 goodput).

### 10. E2E만 오를 때

- 먼저 출력 토큰 수 분포를 본다. E2E ≈ TTFT + (출력 토큰 − 1) × TPOT라서 출력이 길어지면 모델이 그대로여도 E2E가 오른다.
- 길이가 원인이면 프롬프트·`max_tokens`로 조정한다. 길이 한도에 걸린 응답은 잘린 것으로 처리한다([11](../11-llm-api-client-contract/2-summary.md)).
