# ai-engineering/13-model-routing-and-fallback — 정답

## 정답

### 1. 직접 묶을 때의 문제

- 가용성: 그 제공자가 과부하·장애(529·503·429)면 기능 전체가 멈춘다.
- 비용: 쉬운 요청도 비싼 모델로 간다. FrugalGPT 초록은 API 요금 차이가 두 자릿수 크기(약 100배)까지 난다고 적는다.
- 변경: 모델을 바꾸려면 앱 코드·프롬프트·파서를 함께 바꿔야 한다.
- 게이트웨이가 모으는 것: 라우팅, 폴백, 서킷 브레이커, 재시도(한 층), 한도, 결정 기록.

### 2. 게이트웨이 흐름

```text
 요청 → [라우터: 후보 순서 + 이유 기록] → [서킷 열림? → 다음 후보]
      → [호출] → 성공 → [출력 검증] → 통과 → 응답 + 기록(응답 모델·폴백·시도)
                                     실패 → 재요청 1회 또는 다음 후보
             실패(일시) → [서킷에 기록] → 예산 안에서 재시도 / 다음 후보
```

- 폴백 모델의 출력은 주 모델과 형식·지원 범위가 다를 수 있다. 검증이 게이트웨이 밖(주 모델 전용 파서)에 있으면 폴백 출력이 검증 없이 지나가거나, 폴백 때만 하류가 깨진다.

### 3. 캐스케이드 비용

```text
 E[비용] = c_싼 + p_승격 × c_비싼
 p = 0.3   →  1 + 0.3 × 20 = 7      (비싼 모델만: 20 → 65% 절감)
 p = 0.95  →  1 + 0.95 × 20 = 20    (비싼 모델만과 같다 — 절감 없음)
```

- 지연: 승격된 요청은 싼 모델 + 비싼 모델 두 번을 기다린다. 승격률이 높을수록 평균 지연이 비싼 모델만 쓸 때보다 길어진다.
- 그래서 승격률을 지표로 두고, 평가셋으로 품질을 함께 잰다.

### 4. 폴백에서 달라지는 것

- 토크나이저(같은 프롬프트의 토큰 수·비용), 문맥 창·출력 한도, 구조화 출력 지원 범위, 도구 호출 형식(`tool_use` 블록 vs `tool_calls` 배열), 중단 사유 이름(`max_tokens`·`length`·`incomplete`), 프롬프트 캐시(폴백 모델 쪽이 차갑기 쉬움 → 적중이 낮으면 비용·TTFT 증가, 실제 적중은 usage의 캐시 토큰으로 잰다), 한도 계산 방식.
- `minimum`·`maximum`: Anthropic Structured outputs 문서는 숫자 범위 제약을 지원하지 않는다고 적고, OpenAI Structured Outputs 가이드는 지원 목록에 둔다. 한쪽에서 API가 막아 주던 범위 위반이 다른 쪽에서는 앱 검증까지 내려온다([14](../14-structured-output-and-tool-calling/2-summary.md)).

### 5. 무엇을 실패로 세나

| 센다 | 세지 않는다 |
|---|---|
| 529·503 과부하, 500, 연결 실패, 첫 토큰 타임아웃, 200 뒤 스트림 안 과부하 오류 | 400·413, 거부(refusal), 스키마 위반 |

- 429 일시 한도는 제공자 장애가 아니라 **내 한도**가 찬 것이다. 회로를 열면 멀쩡한 제공자를 끊는다. 클라이언트 쪽 토큰 버킷·`retry-after` 준수로 다루고, 회로와는 따로 센다.
- 회로는 제공자 + 모델(+ 리전) 단위로 둔다.

### 6. 재시도 증폭

- 3 × 3 × 2 = **18회**(실험 [A]).
- 앱 한 층(3회)에만 두면 3회.
- SDK 자동 재시도(Anthropic 기본 2회 → 시도 3회)를 끄지 않으면 앱 코드에 재시도가 없어 보여도 곱셈이 일어난다.

### 7. 실험 [B] 모양

- 파싱 실패율: 장애 전 0.0%, 장애 중 4.7~10.3%(시드 7·8·9), 장애 후 0.0~0.5%. 실패가 장애 시간대에 몰린다.
- 모델별로 모으면 실패는 모두 B에서 나왔다(seed 7: B 307건 중 31건, A 0건).
- 서킷: 장애 중 A로 간 실패 호출 300 → 35건. 각 실패가 실제로는 타임아웃 대기였다면 그만큼 사용자 대기가 줄어든다.
- 대가: 장애는 t=600에 끝났지만 회로는 t=639에 닫혔다. 그 사이 요청이 B로 가서 장애 후 파싱 실패율이 0.2~0.5% 남았다.

### 8. 일부 사용자만 이상함

- 기록하지 않은 것: 응답 모델, 라우팅 이유, 폴백 여부, 시도 번호. 그래서 지표를 경로별로 나눌 수 없다.
- 추가: 매 호출 `요청 모델·응답 모델·라우팅 이유·폴백 여부·시도 번호`(OTel GenAI의 `gen_ai.request.model`·`gen_ai.response.model` 등)를 남기고, 품질·오류 지표를 응답 모델별로 본다.
- sticky 라우팅: 한 사용자를 같은 경로에 고정하므로 잘못된 경로의 영향이 일부 사용자에게 몰린다. Anthropic 2025-09-17 사후 분석의 문맥 창 라우팅 오류가 이런 모양이었다고 적혀 있다(해석: 전체 평균은 조금 나빠지지만 해당 사용자는 반복해서 나쁜 응답을 받는다).

### 9. 429로 회로가 열림

- 잘못: 내 한도 초과(429)를 제공자 장애로 세었다. 트래픽이 몰려 429가 늘자 실패율 임계를 넘어 회로가 열렸다.
- 결과: 멀쩡한 주 모델을 끊고, 형식이 다를 수 있는 폴백으로 전부 보냈다(폴백 쪽 한도도 함께 찰 수 있다).
- 대처: 429를 서킷 실패 집계에서 빼거나 별도 지표로 다룬다. 단 429도 종류가 갈린다. 일시 한도는 클라이언트 쪽 한도 조절·`retry-after` 준수로, 지출 한도 429(Anthropic은 `retry-after` 없음 + `enforced_spend_limit_reached`)는 재시도 없이 경보로 처리한다([11](../11-llm-api-client-contract/2-summary.md)). 400·거부도 세지 않는다.
