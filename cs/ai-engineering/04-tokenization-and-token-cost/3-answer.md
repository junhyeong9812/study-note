# ai-engineering/04-tokenization-and-token-cost — 정답

## 정답

### 1. 단어·바이트·서브워드

- 단어 단위: 어휘표에 없는 단어(이름·신조어·오타)를 표현하지 못한다. 어휘표도 매우 커진다.
- 바이트(글자) 단위: 무엇이든 표현하지만 나열이 길다. 출력은 토큰 하나씩 생성되므로 길수록 느리고 비싸며 문맥 창을 빨리 채운다.
- 서브워드: 자주 나오는 조각은 한 토큰, 드문 단어는 아는 조각 여러 개로 쪼갠다. 짧은 나열(단어처럼)에 가까우면서 미등록 단어를 조각으로 표현한다. 단, 문자 단위 BPE는 학습 때 못 본 문자가 미등록으로 남을 수 있다(Sennrich 외 §3.2). "무엇이든 표현"은 바이트 위에서 돌릴 때(아래)다.
- 바이트 수준 BPE는 기본 어휘 256개라 UNK가 없다(GPT-2 §2.2).

### 2. BPE 병합 그림

```text
  1. e + s     (빈도 6+3 = 9)  → n e w es t </w>,  w i d es t </w>
  2. es + t    (빈도 9)        → n e w est </w>,   w i d est </w>
  3. est + </w> (빈도 9)       → n e w est</w>,    w i d est</w>
```

- 1~3번은 빈도가 같은 쌍이 여럿이었다. 동점 처리는 구현마다 다르다(실행은 dict 삽입 순서).
- `lowest</w>` = `l o w e s t </w>`. 규칙을 순위대로 적용한다: (e,s) → (es,t) → (est,</w>) → (l,o) → (lo,w).
- 결과: `low` + `est</w>`, 토큰 2개. 학습에 없던 단어도 아는 조각으로 쪼개진다.

### 3. 학습 말뭉치 비율과 한국어 토큰 수

- (a) 영어 위주 쪽이 많다. 실험: 영어 위주 7,989토큰, 한국어 위주 3,707토큰 — 약 2.2배.
- 이유: 병합 300회를 어느 언어의 잦은 쌍에 쓰느냐가 학습 말뭉치 비율로 정해진다. 영어 위주로 학습하면 한국어 바이트 쌍에 쓰인 병합이 적어, 한국어가 바이트에 가까운 단위로 남는다.
- 반대로 한국어 위주 토크나이저에서는 영어가 6,917토큰(영어 위주 3,191)으로 늘었다.
- 이 실험의 어휘는 실제보다 훨씬 작다. 실제 모델 비율은 그 모델의 계수기로 잰다.

### 4. "안녕하세요 세계"

- `length()` = 8(공백 포함, 모두 BMP 문자라 코드 유닛 = 코드포인트). UTF-8 = 22바이트(한글 7음절 × 3 + 공백 1).
- 두 번 틀리는 곳
  - 평균 "4바이트/토큰"은 바이트 기준인데 글자 수(8)에 적용했다. 한글은 글자당 3바이트라 같은 글자 수가 바이트로 3배다.
  - 그 평균 자체가 영어 위주 텍스트에서 나온 값이다. 한국어의 토큰/바이트 비율은 토크나이저 학습 말뭉치에 따라 다르다.
- 덤: `length()`는 UTF-16 코드 유닛이라 이모지 하나가 2로 세어진다(실험 `🙂 chars(UTF-16)=2 codePoints=1 utf8Bytes=4`).

### 5. NFC vs NFD

- NFD는 한글 음절을 자모 2~3개로 푼다. 바이트가 늘고(자모도 3바이트씩), 바이트열이 학습 때 본 것과 달라진다.
- 병합 규칙은 학습 때 본 바이트 쌍에만 맞는다. NFD 바이트열에는 맞는 규칙이 없어 바이트 하나가 토큰 하나로 떨어진다.
- 실험: 균형 학습 토크나이저에서 NFC 4,738토큰, NFD 45,003토큰(= 바이트 수).
- 대처: 모델에 보내기 전에 NFC로 정규화한다(`java.text.Normalizer.normalize(s, Form.NFC)`). 실제 토크나이저가 내부에서 정규화하는지는 토크나이저마다 다르므로 앱에서 맞춰 두는 편이 확실하다.

### 6. 잘린 응답 감지 필드 (2026-10-08 확인)

| API | 필드 | 잘림 값 |
|---|---|---|
| Anthropic Messages | `stop_reason` | `"max_tokens"`, `"model_context_window_exceeded"` |
| OpenAI Chat Completions | `choices[].finish_reason` | `"length"` |
| OpenAI Responses | `status` + `incomplete_details.reason` | `"incomplete"` + `"max_output_tokens"` |

- 잘림은 HTTP 오류가 아니라 200 응답의 중단 사유다. 성공 판정에 이 값을 넣고, 잘린 결과는 저장하지 않는다.
- 다른 중단 사유(`tool_use`·`refusal`·`content_filter` 등)도 완성된 답이 아니므로 따로 처리한다.

### 7. 모델 교체 뒤 비용·한도 변화

- 토크나이저가 바뀌었을 수 있다. 토큰 수는 (텍스트, 토크나이저) 쌍의 성질이다.
- 근거 예: Anthropic 문서는 Opus 4.7 이후 모델의 토크나이저가 같은 입력에 대략 30% 더 많은 토큰을 낸다고 적고, 옛 모델의 토큰 수를 재사용하지 말라고 한다(2026-10-08 확인).
- 확인: 같은 요청을 옛·새 모델 ID로 각각 계수기에 넣어 `input_tokens`를 비교한다. 운영에서는 응답 `usage`를 모델 ID별로 집계해 전후를 비교한다.

### 8. 세 단위와 이어지는 주제

- 과금 단위 → 캐시([12](../12-prompt-and-semantic-caching/2-summary.md)): 프리픽스 캐시 적중 토큰은 단가가 다르다. 비용 집계는 [23](../23-llm-observability-and-cost/2-summary.md).
- 한도 단위 → 클라이언트 계약([11](../11-llm-api-client-contract/2-summary.md)): 분당 토큰 한도 초과 429, 문맥 창 초과 400·중단 사유.
- 시간 단위 → 지연 지표([10](../10-inference-latency-metrics/2-summary.md)): 출력은 토큰 하나씩 생성되므로 스트리밍 응답 시간 ≈ TTFT + (출력 토큰 수 − 1) × TPOT이다(vLLM 지표의 TPOT 정의 = (종단 지연 − TTFT)/(출력 토큰 − 1), 2026-10-08 확인).

### 9. 자료구조와 검색 분석기

- 해시맵: 인접 쌍 → 빈도표(학습), 쌍 → 병합 순위표(인코딩).
- 힙: 가장 잦은 쌍을 꺼낸다. 병합 뒤 바뀐 쌍만 갱신하면 매 바퀴 전체를 다시 세지 않아도 된다. 실험 코드는 단순화를 위해 매번 전부 다시 셌다.
- 검색 분석기와 다른 점: 분석기는 사람이 정한 규칙(형태소 사전·n-gram)으로 색인 용어를 만든다. BPE는 말뭉치 빈도로 조각을 학습한다.
- 같은 조건: 색인(학습) 쪽과 질의(추론) 쪽의 토큰화 결과가 맞물려야 한다. 모델은 학습 때와 추론 때 **같은 토크나이저**를 써야 한다. 검색은 보통 색인·질의에 같은 분석기를 쓰지만, 자동완성 `edge_ngram`처럼 질의 쪽을 일부러 다르게 두기도 한다(Elasticsearch `search_analyzer`). 토크나이저·분석기가 바뀌면 검색 쪽은 재색인, 모델 쪽은 토큰 수·비용 재측정이 필요하다.
