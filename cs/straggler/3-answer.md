## 정답

1. 전부 기다리는 설계에서 전체 응답 시간 = 가장 느린 한 대다. 노드 하나가 느릴 확률 1%면 전부 빠를 확률은 0.99^N — N=10이면 90%, N=100이면 37%(느릴 확률 63%), N=1000이면 사실상 0. 개별 노드가 아주 가끔만 느려도 노드 수가 많으면 거의 매번 걸린다. 그래서 규모가 커지면 평균은 의미가 없고 꼬리(p99, p999)가 사용자 경험을 지배한다(The Tail at Scale).

2. 하드웨어: SSD GC, 발열 스로틀링, 재할당 섹터. 런타임: JVM Full GC 수백 ms 정지. 이웃/환경: 같은 머신의 다른 프로세스나 컨테이너(noisy neighbor), 네트워크 스위치 큐잉·재전송, 로그 로테이션·백업·인덱스 재구축·모니터링 에이전트 같은 백그라운드 작업. 데이터: 그 노드에만 큰 파티션이 배정된 data skew. 전부 정상 운영 중에 늘 일어나는 일이라 "어느 한 대가 하필 그 순간" 느려지는 건 확률의 문제지 장애가 아니다.

3. 빠른 2대(5ms, 6ms)가 응답한 시점인 6ms에 성공 처리되고, 느린 1대에는 계속 쓰되 기다리지 않는다 — quorum(정족수). BookKeeper의 Qa가 정확히 이것이다. Kafka acks=all은 "ISR 전원"을 기다리는 설계라 팔로워 한 대가 GC에 걸리면 프로듀서 응답이 그대로 튄다(ISR에서 빠질 때까지). 정족수가 아니라 전원 동기화를 내구성 모델로 택했기 때문이다.

4. Hedged: p95 시간이 지나도 응답이 없으면 다른 노드에 같은 요청을 하나 더 보내고 먼저 온 것을 채택, 나머지 취소 — 여분 부하 ~5%로 tail을 크게 줄임(Cassandra, gRPC). Speculative execution: 배치 태스크가 유독 느리면 다른 노드에서 중복 실행하고 먼저 끝난 쪽 채택(MapReduce/Spark). Tied request: 처음부터 두 노드에 동시에 보내되 "다른 쪽이 시작했으면 취소하라"는 정보를 함께 넘겨 중복 작업 자체를 최소화. 셋 다 "기다리지 않기" 계열이고, 차이는 보내는 시점(지연 후/느림 감지 후/즉시)과 중복 처리(취소/버림/상호 취소)다.

5. BookKeeper의 journal/ledger 분리는 "뒤처진 컨슈머의 랜덤 읽기가 쓰기 디스크를 점유"하는 읽기-쓰기 간섭 원인을 물리적으로 제거한다. Kafka가 메시지를 JVM 힙에 캐싱하지 않고 페이지 캐시에 맡기는 것은 JVM Full GC 정지라는 런타임 원인을 줄인다(힙 밖으로 데이터 빼기). 나머지는 data skew 제거(정교한 부하 분산), 백그라운드 작업 스케줄을 노드마다 어긋나게, GC 튜닝이다.

6. 셋 다 "그 노드만 잠깐 느려지는" 원인이고, 전부 기다리는 설계에서는 전체 p99를 폭증시키는 straggler로 표면화된다. Kafka: JVM 힙을 안 써 GC straggler를 예방하지만 acks=all 전원 대기라 발생하면 그대로 노출. BookKeeper: Qa 정족수로 회피하고 디스크 분리로 읽기-쓰기 간섭도 예방. Redpanda: JVM 자체를 제거하고 thread-per-core로 스케줄링 지터를 예방. 같은 문제에 예방/회피/제거라는 다른 자리를 택한 것이다.
