# data-engineering/15-data-mesh-and-data-products — 정답

## 정답

### 1. 중앙 팀이 느려지는 이유 — 세 실패 모드

1. **중앙 집중·모놀리식**: 모든 원천의 수집·정제·변환·서빙을 한 플랫폼이 한다. 원천과 소비자가 늘수록 한곳에 몰린다.
2. **파이프라인 단계별 분해**: 팀을 수집·준비·집계·서빙 단계로 나눈다. 새 데이터셋 하나(예: 팟캐스트 재생률)가 모든 단계의 변경을 요구한다. 변경 축과 직교하게 나눈 분해라 결합이 크다.
3. **사일로화된 초전문 소유**: 빅데이터 도구 전문가 팀이 원천·소비 도메인과 떨어져 있다. 도메인 지식이 없고, 데이터를 줄 동기가 없는 팀에게서 데이터를 받는다.
- 결과: 소비 팀이 중앙 팀 backlog에서 기다린다(Dehghani 2019).

### 2. 네 원칙과 빠졌을 때

| 원칙 | 빠지면 |
|---|---|
| ① 도메인 소유 | 중앙 병목이 남는다 |
| ② 제품으로서의 데이터 | 찾기·이해·신뢰가 어려워 소비자가 매번 다시 검증한다. 분산할수록 더 심해진다 |
| ③ 셀프서비스 플랫폼 | 도메인마다 인프라를 다시 만든다(비용·장애 방식 제각각) |
| ④ 연합 계산 거버넌스 | 도메인 간 조인이 안 되고, 주인 없는 테이블이 쌓이고, 규정 준수가 제각각이다 |

- 2020년 글은 네 원칙이 "함께 필요하고 충분하도록" 의도했다고 적는다.
- 소유만 나누면 중앙 사일로 하나가 도메인 사일로 여러 개로 바뀐다. ②~④가 그 비용을 막는다.

### 3. 데이터 제품 vs 테이블 하나

- 아키텍처 퀀텀 세 구성 요소(2020)
  - **코드**: 파이프라인(소비·변환·서빙), 데이터·스키마·관측 지표에 접근하는 API, 접근 제어·규정·출처 같은 정책 집행 코드.
  - **데이터와 메타데이터**: 분석 데이터 + 의미·문법 선언·품질 지표·정책 메타데이터.
  - **인프라**: 빌드·배포·실행·저장.
- 테이블 하나는 데이터만이다. 데이터 제품은 그것을 만들고 설명하고 지키는 코드·메타데이터·인프라를 한 단위로 독립 배포한다.
- 2019년 글의 제품 조건(찾을 수 있음·주소·신뢰·자기 서술·상호운용·보안)도 테이블에는 없는 요구다.

### 4. 전역 vs 도메인

- 전역(연합 팀이 정하고 플랫폼이 집행)
  - 다의어의 식별 규칙(사용자·팟캐스트 청취자·아티스트 ID).
  - 품질·SLO를 표현하는 형식, 민감도 등급·규제 요구, 주소·메타데이터·이벤트 형식 표준.
- 도메인
  - 자기 도메인의 데이터 모델(2020년 글: 'podcast audienceship'(팟캐스트 청취층) 데이터 모델의 의미·문법은 팟캐스트 도메인 팀이 정한다).
  - 자기 품질 지표의 목표값, 제품 분할·서빙 형식.
- "계산": 전역 규칙을 사람의 수작업 승인이 아니라 플랫폼의 코드로 자동 집행한다. 2020년 대조표의 "수작업 → 플랫폼이 구현한 자동 프로세스", "오류를 막는다 → 감지하고 자동 복구"가 그 뜻이다.

### 5. '활성 사용자' 네 정의

- 네 숫자는 다르다. 오류는 나지 않는다. 각 SQL·코드는 자기 정의대로 맞다.
- 실험 출력(Python 3.12.3, `random.seed(42)` 합성 데이터): 결제팀 580 > 성장팀 505 > 콘텐츠팀 183 > 마케팅 118.
  - 결제팀은 성장팀 정의에 "결제"를 더했으니 같거나 크다. 마케팅은 기간이 짧으니 성장팀 이하다. 이 두 대소 관계는 정의에서 나온다.
  - 콘텐츠팀 183이 30일 정의 셋 중 가장 작은 것은 합성 데이터의 재생 비율(60%)·날짜 생성 방식 탓이다(데이터 의존).
- 전역 정의 `active_user_30d`(30일 내 로그인) 하나를 공유하자 세 번 모두 505였다.

### 6. 표준 검사 vs 조직 정책 검사

- 표준 필수 필드 검사: `apiVersion`까지 채운 서술자라면 4개 모두 통과한다(소유 팀·계약이 필수가 아니므로). ODPS v1.1.0은 `apiVersion`·`kind`·`id`와 출력 포트 1개 이상(포트마다 `name`)을 필수로 두고, `team`과 `contractId`는 선택으로 둔다.
  - 실험의 `표준=PASS` 4개는 간이 모형 검사 결과다. 모형은 `kind`·`id`·`outputPorts`만 봤고 서술자에 `apiVersion`을 넣지 않았다. 그래서 실제 ODPS 필수 필드 검사라면 실험의 서술자 4개는 모두 `apiVersion`에서 걸린다.
- 조직 정책 검사: (a) 1개만 통과.
  - (b) `포트 plays_raw: 데이터 계약 없음`
  - (c) `소유 팀 없음`, `active인데 SLO(신선도) 없음`
  - (d) `retired인데 소비자 있음: ['finance.monthly_close']`
- 실험 출력이 위와 같았다(Python판·Java판 모두).
- 교훈: 표준을 따랐다고 거버넌스가 된 것은 아니다. 조직이 필요한 규칙을 정책으로 더하고 등록 단계에서 자동 검사한다.

### 7. 바운디드 컨텍스트와 다의어

- 데이터 제품 경계 = 도메인의 바운디드 컨텍스트. 2020년 글은 코드·데이터·인프라를 "도메인 바운디드 컨텍스트의 단위로" 묶는다고 적는다. 경계 안은 한 뜻, 경계 사이는 번역이라는 domain-modeling/16의 생각과 같다.
- 다의어는 전역 거버넌스가 식별 규칙만 정한다. 예: 전역 사용자 ID 또는 연합 엔티티 식별자(2019년 글의 아티스트 예).
- 각 도메인은 자기 속성을 그대로 두고, 합의한 식별 규칙으로 이어 붙인다. 전역 연합 엔티티 ID는 2019년 글이 든 한 가지 접근법("One approach")이다. 정의가 다른 지표는 다른 이름을 쓴다.

### 8. 주인 없는 테이블 찾기와 재발 방지

```sql
SELECT n.nspname || '.' || c.relname AS table_name,
       obj_description(c.oid, 'pg_class')::jsonb ->> 'owner' AS owner,
       s.seq_scan + coalesce(s.idx_scan, 0) AS scans,
       greatest(s.last_seq_scan, s.last_idx_scan) AS last_read
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
JOIN pg_stat_user_tables s ON s.relid = c.oid
WHERE c.relkind = 'r' AND n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND (obj_description(c.oid, 'pg_class')::jsonb ->> 'owner' IS NULL
       OR s.seq_scan + coalesce(s.idx_scan, 0) = 0)
ORDER BY 1;
```

- 로컬 재현(PostgreSQL 17.11): 주석 JSON에 데이터 제품 소유자(`owner`) 표기가 없는 3개 테이블이 나왔고, owner 주석이 있고 읽힌 테이블은 빠졌다. PostgreSQL 자체의 테이블 소유 역할(`pg_class.relowner`)과는 다른 것이다.
- 주의: 통계는 비정상 종료 뒤 시작(크래시·즉시 종료·PITR 등)이나 `pg_stat_reset()`으로 초기화될 수 있다. 정상 종료 뒤 재시작에서는 보존된다(PostgreSQL 17 문서). 읽기 0회는 "통계 기간 안에 0회"다. `last_seq_scan`은 PostgreSQL 16부터 있다.
- 재발 방지: 카탈로그 등록 때 소유자·계약 필수 정책을 자동 검사한다(연합 계산 거버넌스). "카탈로그 테이블 − 출력 포트 테이블" 차집합을 정기적으로 돌려 소유자 지정 → 보관 → 삭제 순으로 처리한다.

### 9. 은퇴 제품 삭제로 정산이 깨짐

- 빠진 것: 소비자 등록과 계보. 누가 그 출력 포트를 읽는지 몰랐다.
- 미리 잡을 수 있었다: 정책 검사의 "retired인데 소비자 있음" 같은 규칙.
- 순서
  1. `deprecated`로 표시하고 소비자에게 알린다(대체 제품·기한).
  2. 계보 그래프·쿼리 로그로 소비자를 찾아 0이 될 때까지 옮긴다.
  3. `retired`로 바꾸고 쓰기를 멈춘다.
  4. 보관 기간이 지난 뒤 데이터를 지운다.
- ODPS의 `status` 값(proposed·draft·active·deprecated·retired)이 이 단계를 표현한다.
