# data-engineering/07-batch-stream-architectures — 정답

## 정답

### 1. 두 요구와 재처리

- 원본 로그를 버리면 과거 입력이 없다. 코드를 고쳐도 다시 돌릴 재료가 없으니 고친 결과는 앞으로의 데이터에만 적용된다.
- Kreps 2014: "Code will always change." 새 출력 필드가 필요하거나 버그를 고치면 출력을 다시 만들어야 한다. 재처리를 고려하지 않은 실시간 시스템은 빨리 진화하지 못한다고 본다.

### 2. Lambda

```text
  불변 원본 ─┬─> 배치 계층(전체를 몇 시간마다 다시 계산) → 배치 뷰 ─┐
            └─> 실시간 계층(최근 몇 시간 증분)        → 실시간 뷰 ─┴─> 질의 시점 병합
```

- human fault-tolerance(Marz 2011): 원본이 불변·추가 전용이라, 버그 있는 코드를 배포했거나 잘못된 데이터를 썼어도 고친 뒤 처음부터 다시 계산하면 된다. 실시간 계층의 실수는 배치가 결국 덮어쓴다.
- 대가(Kreps 2014): 같은 결과를 내야 하는 코드를 두 복잡한 분산 시스템에서 유지해야 한다. 둘을 감싸는 프레임워크도 공통 기능만 쓸 수 있고, 두 시스템의 운영·디버깅 부담은 남는다.

### 3. Kappa 4단계

```text
  1 보존 = 재처리 기간    2 v2를 처음부터, 출력은 새 테이블    3 따라잡으면 앱을 새 테이블로    4 v1 중지, 옛 테이블 삭제
```

- 2배로 필요한 것: 출력 저장소(옛 테이블 + 새 테이블). 새 출력은 대량 쓰기를 견뎌야 한다.
- 옛 테이블을 잠시 남기면 앱이 읽는 테이블을 되돌리는 것만으로 옛 로직으로 즉시 롤백할 수 있다. 중요한 출력은 A/B 비교 뒤 전환할 수도 있다(Kreps 2014).

### 4. 두 경로의 10-01 매출 (실험 A)

- 실시간 경로: (1,000 − 30) × 100 + 20 × 100 = 99,000. 늦은 30건(3,000)은 10-02에 들어갔다.
- 배치 경로: 1,000 × 100 = 100,000.
- 실험 출력과 같다: `23:59 대시보드(속도 계층) = 99000, 다음 날 아침(배치 계층) = 100000, … 10-02에 넣은 10-01 주문 = 3000`.
- 해석: 빼먹음(−3,000)과 중복(+2,000)이 일부 상쇄돼 차이가 작아 보일 뿐, 두 경로의 규칙이 다르다.

### 5. 보존 7일 뒤 처음부터 재처리 (실험 B)

- 880건, 9일(09-29 ~ 10-07). 로그 시작 오프셋이 0에서 2120으로 올랐다.
  - 점검 재실행 두 번에서는 995·906건, 10일(09-28 ~ 10-07)이었다. 생산자 배치 경계에 따라 세그먼트 경계가 달라지므로 정확한 수는 실행마다 다르다. "7일보다 조금 더(9~10일), 앞부분은 사라짐"이 결정적인 부분이다.
- 정확히 7일이 아닌 이유: 삭제가 세그먼트 단위이고, 세그먼트 안 **가장 큰 타임스탬프**가 보존 기간을 넘어야 지운다. 남은 첫 세그먼트에 09-29 기록이 섞여 있었다.
- 에러는 없다. 새 그룹은 `auto.offset.reset=earliest`로 남은 로그 시작부터 읽고 정상 종료했다. 결과가 "앞부분만 빠진 정상 결과"로 보인다. 이 결과는 `earliest`일 때의 것이다. 기본값 `latest`면 새 그룹은 로그 끝부터 읽고, `none`이면 예외가 난다(Kafka 4.1 Consumer Configs).

### 6. 보존보다 긴 재처리

| 방법 | 비용·한계 |
|---|---|
| 보존을 늘린다 | 브로커 디스크. 재처리 때 오래된 세그먼트 읽기가 페이지 캐시를 흔든다 |
| 계층형 저장 | Kafka 4.1 `remote.storage.enable`·`local.retention.*`. 원격 저장 플러그인과 운영이 필요하다 |
| 객체 저장소 아카이브 + 배치 재처리 | 실시간 잡과 배치 코드가 둘이 된다(Lambda 문제 일부 재발). 배치는 파티션 덮어쓰기로 멱등하게 |
| compaction 토픽 | 키별로 최소한 최신 값이 남는다. 정리 전 구간엔 옛 값도 있을 수 있지만 이력 보존은 보장되지 않는다 |

- compaction 토픽으로는 키의 **과거 값들**이 필요한 결과(날짜별 집계, 변경 이력)를 다시 만들 수 없다. "현재 상태" 재구축에만 쓴다.

### 7. 재처리 직후 매출 2배

- 원인: 재처리 잡(v2)이 운영 잡과 같은 출력 테이블·토픽에 썼다. 반영이 증분(더하기)이라 같은 기간 값이 겹쳐 쌓였다. 실험 A: 정답 96,000 → 196,000.
- 확인: 재처리 잡의 출력 설정(테이블·토픽 이름, 그룹 id), 재처리 구간 날짜만 값이 큰지, 출력 테이블의 쓰기 주체·시각.
- 복구: 운영 출력을 원본에서 다시 만든다(새 테이블에 만든 뒤 전환).
- 재발 방지: 재처리는 새 그룹·새 출력으로만 돌리는 절차, 출력 반영을 키·파티션 덮어쓰기로(08번).

### 8. 전환 전 대조

```sql
SELECT coalesce(a.day, b.day) AS day, a.revenue AS v1, b.revenue AS v2, b.revenue - a.revenue AS diff
FROM out_v1 a FULL JOIN out_v2 b ON a.day = b.day
WHERE a.revenue IS DISTINCT FROM b.revenue ORDER BY 1;
```

- 기대: 버그를 고친 영향만큼의 차이(예: 취소 제외로 날마다 조금 작아짐).
- 실험 B 같은 상황: 09-08 ~ 09-28 행이 `v2 = NULL`로 나온다. 보존 부족으로 v2에 그 날짜가 없다는 뜻이다. 이 상태로 전환하면 그 날짜의 숫자가 대시보드에서 사라진다. 전환하지 않고 빠진 구간을 아카이브에서 채운다.

### 9. 재처리 병렬도

- 파티션 수에 묶인다. 한 소비자 그룹 안에서 파티션 하나는 소비자 하나에만 배정되므로, 소비자를 파티션 수보다 늘려도 빨라지지 않는다.
- 따라잡지 못할 때 의심할 곳: (1) 파티션 수(병렬도 상한), (2) 출력 DB의 쓰기 처리량(대량 쓰기 경로·인덱스·락). 재처리 구간을 나눠 여러 잡으로 돌리는 것도 방법이다.
