# data-engineering/14-lakehouse-table-formats — 정답

## 정답

### 1. 디렉터리 = 테이블의 문제

- 중간에 죽을 때: 쓴 파일까지만 디렉터리에 남는다. 읽는 쪽은 반쯤 쓴 테이블을 본다. 여러 파일에 걸친 변경을 원자적으로 할 수 없다.
- 동시에 쓸 때: 두 잡이 같은 파티션을 덮어쓰면 누가 이겼는지, 무엇이 남았는지 알 수 없다.
- 목록 알아내기: 디렉터리를 나열해야 한다. Iceberg 문서 "Reliability"는 Hive 테이블 계획이 파티션 수 n에 비례하는 느린 나열 호출을 한다고 지적한다.
- 테이블 포맷은 파일 목록을 메타데이터로 관리하고, 현재 상태를 원자적으로 바꿔 이 셋을 푼다. Iceberg는 현재 메타데이터를 가리키는 포인터 하나를 바꾸고, Delta는 다음 번호 로그 파일을, Hudi는 타임라인 완료 파일을 만든다(7번).

### 2. Iceberg 메타데이터 트리

```text
  카탈로그 포인터 ─> metadata.json (스키마, 파티션 규칙, 스냅샷 목록, current-snapshot-id)
                     └─ 스냅샷 ─> manifest list ─> manifest A, manifest B ─> 데이터 파일들
```

- append 커밋 하나가 새로 만드는 것: 새 데이터 파일, 그 파일을 담은 새 매니페스트, 새 매니페스트 리스트, 새 메타데이터 파일. 마지막으로 포인터를 바꾼다.
- 공유하는 것: 기존 매니페스트들. 새 매니페스트 리스트가 옛 매니페스트를 그대로 가리킨다(Spec "Overview": 매니페스트는 스냅샷 사이에 재사용된다).

### 3. 동시 append — CAS vs 덮어쓰기

- (a) CAS: 최종 400파일·40000행. 같은 기준 버전에서 출발한 커밋 중 하나만 성공하고 나머지는 새 버전 위에서 다시 한다. append는 조건 없이 다시 적용된다.
- (b) 덮어쓰기: 남의 커밋을 지운 메타데이터로 포인터를 바꾼다. 커밋이 조용히 사라진다.
- 모형 실험 출력(5번 실행, 실행마다 3회): CAS는 15회 모두 400파일·40000행, CAS 실패 971~1447번. 덮어쓰기는 59~96파일·5900~9600행, 오류 0.
- 오류는 어느 쪽도 나지 않았다. 덮어쓰기의 유실은 행 수 대조로만 보인다.

### 4. compaction 도중 원본 삭제

- 정답 행 수: 600 − 100 = 500.
- (a) 검증 O: 재시도 전에 원본 4개 중 1개가 없음을 보고 커밋을 포기한다. 최종 500행.
- (b) 검증 X: 남은 원본 3개를 빼고 병합 파일(400행 — 지운 파일 포함)을 넣는다. 최종 600행. 지운 100행이 되살아난다.
- 모형 실험 출력: `ABORT … 최종 live 행 500` / `COMMITTED (attempt 2) … 최종 live 행 600`.
- 명세가 요구하는 것은 검증이다. replace 작업은 지울 파일들이 아직 테이블에 있는지 확인해야 한다(Spec "Commit Conflict Resolution and Retry"). 검증에 실패한 이 커밋안은 적용할 수 없으니 (a)처럼 포기한다. 현재 스냅샷에서 대상을 다시 골라 새 compaction을 시도하는 것은 별개다.

### 5. 커밋 충돌 규칙

| 작업 | 재시도 전 확인 |
|---|---|
| append | 없음 — 그대로 다시 적용(명세: "can always be applied") |
| replace(compaction 등) | 지울 파일들이 아직 테이블에 있나 |
| 파일 지정 delete | 지울 파일들이 아직 있나 |
| 식 기반 delete(`timestamp < X`) | 없음 — 다시 적용 가능 |
| 스키마·파티션 규칙 변경 | 기준 버전과 현재 사이에 스키마가 안 바뀌었나 |

- append는 기존 파일을 건드리지 않고 새 파일만 더한다. 다른 커밋이 무엇을 했든 "새 파일을 더한다"는 의미가 그대로라서 조건이 없다.
- 기존 파일을 빼는 작업은 그 파일이 이미 빠졌으면 결과가 틀린다(4번).

### 6. MVCC·Merkle 트리와의 대응

| 테이블 포맷 | PostgreSQL MVCC(database/16) |
|---|---|
| 스냅샷 | 스냅샷(그 시점에 보이는 버전 집합) |
| 옛 데이터 파일 | 죽은 튜플 버전 |
| 스냅샷 만료 + 남은 스냅샷에 안 걸린 파일 삭제 | VACUUM(아무 스냅샷도 볼 수 없는 버전 제거) |
| 고아 파일 삭제 | (대응 없음 — 실패한 쓰기의 잔해 정리) |
| compaction | 재작성(VACUUM FULL·pg_repack처럼 새로 써서 줄임 — 비유) |

- Merkle 트리와 닮은 점: 루트에서 잎까지 내려가는 불변 트리이고, 새 버전이 바뀌지 않은 하위 트리를 공유한다.
- 다른 점: Iceberg 매니페스트 리스트 항목에는 자식의 경로·길이·통계가 있고 내용 해시가 없다(Spec "Manifest Lists"). 해시로 위변조를 검증하는 구조가 아니다.

### 7. 세 포맷의 원자성

- Iceberg: 카탈로그 포인터의 원자적 교체. 메타스토어의 check-and-put이 예시다. 파일 시스템 rename 방식은 명세가 폐기 예정으로 표시하고 "객체 저장소와 로컬 파일 시스템에서 안전하지 않다"고 적는다.
- Delta Lake: `_delta_log`의 다음 번호 JSON 파일. 로그 파일 하나가 원자성 단위이고, 기존 항목을 덮어쓰면 안 된다. 저장소의 원자적 기본 연산(PUT-if-absent 등)으로 동시 작성자가 서로 덮어쓰지 않게 한다(PROTOCOL.md).
- Hudi: 타임라인의 상태 전이(REQUESTED → INFLIGHT → COMPLETED)가 저장소의 원자적 연산 위에서 이뤄진다. 다중 작성자는 락 제공자가 전제다(Hudi 문서).
- 시점 차이: CIDR 2021은 "Hudi는 동시 작성자를 지원하지 않는다"고 적었다. 2026-10 현재 Hudi 문서 "Concurrency Control"은 작성자 사이 OCC·NBCC를 설명한다.

### 8. 계획이 실행보다 길다

- 의심: 작은 파일 폭증, 매니페스트 난립.
- 확인: `prod.db.t.partitions`의 `file_count`·평균 파일 크기, `prod.db.t.manifests`의 개수·크기, `prod.db.t.snapshots`의 커밋 빈도.
- 원리: 계획은 매니페스트 항목 수에 비례하고, 실행은 파일 열기 비용을 파일 수만큼 낸다(Iceberg Maintenance 문서). 모형 실험 D에서 파일 10 → 100,000개로 계획 0.02~0.06ms → 63~81ms(중앙값, 같은 질의, 5번 실행 범위).
- 해법: `rewrite_data_files`(병합), `rewrite_manifests`, 적재 커밋 간격 늘리기. 병합 뒤 만료를 돌려야 옛 작은 파일이 실제로 지워진다.

### 9. 비용 증가와 time travel 실패

- 같은 설정의 양면: 스냅샷 보존 정책이 업무 요구와 맞지 않는다.
  - 만료를 안 돌리면 옛 스냅샷이 옛 파일을 붙잡아 비용이 는다.
  - 만료를 짧게 돌리면 감사가 필요로 하는 시점의 스냅샷이 사라진다. 명세는 해당 시각 이전 스냅샷이 없으면 정보 부족 오류를 내라고 한다.
- 해결
  - 정기 `expire_snapshots`로 일반 이력은 짧게 유지한다(Iceberg 기본 5일, 최소 1개 유지).
  - 재현해야 하는 시점(월말 마감 등)은 태그로 고정한다. 태그가 가리키는 스냅샷은 만료되지 않는다(`history.expire.max-ref-age-ms` 기본 무기한일 때).
  - 장기 보존해야 하는 숫자는 time travel에 기대지 말고 별도 테이블로 남긴다.

### 10. 고아 파일 삭제 후 "파일 없음"

- 보존 간격을 쓰기 잡 시간보다 짧게 잡아, 아직 커밋 전이던 파일을 고아로 보고 지웠다. 그 쓰기가 커밋되자 메타데이터는 없는 파일을 가리킨다(Iceberg Maintenance 문서 경고, 기본 간격 3일).
- 경로 표기가 바뀐 경우(HDFS authority 변경 등) 같은 파일을 다른 문자열로 보고 지울 수 있다(같은 문서).
- 대처: 간격을 가장 긴 쓰기 잡보다 넉넉히 둔다. 실행 전에 메타데이터 경로와 실제 나열 결과를 대조한다.
