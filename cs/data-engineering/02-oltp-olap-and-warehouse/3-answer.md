# data-engineering/02-oltp-olap-and-warehouse — 정답

## 정답

### 1. OLTP와 OLAP이 서로를 방해하는 이유

| | OLTP | OLAP |
|---|---|---|
| 한 요청이 읽는 행 | 키로 찾은 몇 행 | 수백만 행의 몇 컬럼 |
| 쓰기 | 작은 INSERT·UPDATE가 잦음 | 대량 적재 |
| 병목 | 지연(ms)·동시성 | 스캔량 |

- 같은 DB에서 돌면 CPU·디스크 대역폭·버퍼 캐시·연결을 나눠 쓴다. 긴 집계 하나가 짧은 요청 수천 건의 자원을 가져간다.
- 저장 방식도 맞지 않는다. 행 저장은 한 행을 읽고 쓰기에, 컬럼 저장은 몇 컬럼 집계에 맞는다([database/37](../../database/37-row-vs-column-storage/2-summary.md)).

### 2. 리포트가 점 조회에 주는 영향 (실험)

- 점 조회만: p99 0.404~0.515 ms, tps 15,605~17,073 (3회).
- 리포트 세션 2개 동시: p99 1.452~2.783 ms, tps 4,338~4,485 (3회). p99는 회차별 약 3.6~6.7배, 처리량은 약 1/4.
- 리포트 자체도 단독 796 ms에서 회당 약 2.4~2.7초로 느려졌다(22초에 8~9회).
- 한계
  - 한 호스트, `--cpus=2`, 269 MB 테이블에서 잰 값이다. 배율은 CPU 수·디스크·데이터 크기에 따라 다르다.
  - CPU 경쟁이 큰 몫이라는 것은 대조 실험이 뒷받침한다. I/O 없는 CPU 전용 쿼리 6개만으로도 p99가 2.303~2.884 ms로 올랐다. 다만 리포트 쪽 처리량 하락이 더 커서 I/O·버퍼 경쟁의 몫을 0이라고 할 수는 없다(해석 — 따로 분리해 재지 않았다).

### 3. 분석 저장소의 층

```text
  운영 DB들 ─► 원본 적재 층(raw) ─► 통합 모델 층(웨어하우스: 팩트·차원) ─► 마트(주제별) ─► BI
```

- 웨어하우스: 여러 운영 시스템의 데이터를 분석용으로 통합한 저장소.
- 마트: 한 주제·부서용으로 좁힌 분석 저장소. 웨어하우스에서 떼어 내면 종속 마트, 운영 시스템에서 직접 받으면 독립 마트다.

### 4. ETL vs ELT

- ETL: 최종 테이블에 적재하기 전에 변환한다. 변환은 흔히 웨어하우스 밖(별도 서버·도구)에서 하지만, 웨어하우스 안 staging 테이블에서 할 수도 있다. 최종 테이블에 적재되는 것은 변환 결과다.
- ELT: 원본을 먼저 웨어하우스(raw 층)에 적재하고, 웨어하우스 안에서 SQL로 변환한다.
- 다시 돌릴 수 있는 이유: 변환 전 원본이 raw 층에 남아 있다. 변환 규칙을 고친 뒤 raw에서 다시 계산하면 된다. 실험의 변환 v2가 그렇게 10,000행·34,995,000으로 원천과 맞췄다.
- 대가
  - 원본을 저장하는 비용.
  - 원본에 든 개인정보·삭제 대상 데이터도 raw 층에 남는다 → 보존·삭제 설계가 필요하다(이 영역 [12](../12-data-retention-and-erasure/2-summary.md)).

### 5. 숫자만 통과시키는 변환

- 잡은 에러 없이 성공한다.
- 웨어하우스: 9,964행, 합계 34,867,682. 원천: 10,000행, 34,995,000. 36행·127,318이 빠진다.
- 대시보드 합계만 운영과 다르다. "파이프라인은 초록인데 숫자가 틀린" 모양이다.

### 6. 대조 쿼리

```sql
SELECT s.paid_on, s.n AS src_n, d.n AS dw_n, s.amt - coalesce(d.amt, 0) AS missing_amount
FROM (SELECT paid_on, count(*) n, sum(amount) amt FROM src_payment GROUP BY 1) s
LEFT JOIN (SELECT paid_on, count(*) n, sum(amount) amt FROM fct_payment GROUP BY 1) d USING (paid_on)
WHERE s.n IS DISTINCT FROM d.n OR s.amt IS DISTINCT FROM d.amt;
```

- 일자별로 행 수와 금액 합계를 비교한다. 실험에서는 `2026-09-01 | 333 | 332 | 1690`처럼 매일 1~2행이 빠진 날이 나왔다.
- `LEFT JOIN` + `coalesce`로 웨어하우스에 아예 없는 날도 잡는다.
- 함께: 변환 거부 행을 별도 테이블에 남기고, 거부 수가 허용 비율(예시 0.1%)을 넘으면 잡을 실패시킨다.

### 7. 복제본 리포트의 충돌

- 원인: 팔로워에서 도는 긴 조회가 보고 있는 옛 행 버전을, 리더의 vacuum 기록이 지우려 한다. 재생은 `max_standby_streaming_delay`(PostgreSQL 17 기본 30초)까지 기다린 뒤 조회를 취소한다. 기다리는 동안은 재생이 밀려 복제 지연이 된다([database/32](../../database/32-replication-leader-follower/2-summary.md)).
- 선택지
  - 지연 허용값을 늘린다 → 그만큼 복제본 데이터가 늦을 수 있다.
  - `hot_standby_feedback = on` → 충돌은 줄지만 리더 쪽 bloat를 감수한다.
  - 긴 분석은 논리 복제·별도 분석 저장소(웨어하우스)로 보낸다.

### 8. 재처리 불가

- 설계: 원본을 남기지 않는 ETL. 웨어하우스에는 변환된 값만 있고, 원천 DB는 그사이 값이 갱신되어 그때 값이 없다.
- 막는 법
  - 추출한 원본을 raw 층에 적재 시각과 함께 남긴다(ELT).
  - 변환을 raw에서 다시 돌 수 있는 결정적 SQL로 만든다. 파티션 단위 덮어쓰기와 백필은 이 영역 [08](../08-idempotent-pipelines-and-backfill/2-summary.md).
