# data-engineering/01-system-of-record-and-derived-data — 정답

## 정답

### 1. 원천을 하나로 정하는 이유

- 값이 서로 다를 때 **어느 쪽이 맞는지 판정**할 수 없다. 판정 규칙이 "원천이 맞다"이기 때문이다.
- 파생본을 **버리고 다시 만들** 기준이 없다. 재구축은 원천을 다시 접는 일이다.
- 수정을 **어디에 기록할지** 정할 수 없다. 원천이 둘이면 두 곳 다 고쳐야 하고, 한쪽을 빠뜨리면 어긋난다.

### 2. 폴드 그림과 결정성 조건

```text
  로그  [placed 0] [item_added 359] [item_added 359] [item_added 359]
          │             │                │                │
  상태  {0,placed} → {359,placed} → {718,placed} → {1077,placed}
        state = apply(state, event) 를 처음부터 끝까지 반복
```

- 조건: `apply`가 결정적이어야 한다. 현재 시각·난수·외부 API 응답을 읽지 않고, 이벤트와 직전 상태만으로 다음 상태를 정한다.
- 실험(PostgreSQL 17.11): 두 번 재구축한 결과의 digest가 `d95f1a566dc2f5d20484c758d8d9903a`로 같았다. Java 21 폴드도 `rebuild1.equals(rebuild2)=true`였다.

### 3. 파생본 직접 수정 뒤 재구축

- 주문 7은 `total=1077, status=placed`로 돌아간다. 실험 출력: 수정 직후 `7 | 0 | refunded` → 재구축 뒤 `7 | 1077 | placed`.
- 이유: 재구축은 `order_view`를 비우고 원천 `order_event`를 다시 접는다. 원천에는 환불 사실이 없다.
- 올바른 방법: 원천에 `refunded` 이벤트(금액 −1077)를 붙이고, `apply`가 그 종류를 처리하게 한 뒤 재구축한다(실험에서는 `rebuild_view()`의 `CASE`에 `refunded` 분기를 더해 다시 정의했다). 실험에서 재구축을 두 번 해도 `7 | 0 | refunded`가 남았다.

### 4. 원천과 파생 구분

| 저장소 | 역할 |
|---|---|
| 캐시 | 파생(DB의 사본, 지워도 DB에서 다시 채운다) |
| 검색 인덱스 | 파생(원천 DB에서 재색인) |
| CQRS 조회 모델 | 파생(쓰기 모델·이벤트를 접은 결과) |
| 이벤트 소싱의 현재 상태 테이블 | 파생(이벤트 로그를 접은 결과) |

- 보통의 CRUD 시스템은 "현재 상태 테이블"이 원천이고, 변경 로그(WAL·binlog)는 그 부산물이다.
- 이벤트 소싱은 반대다. 이벤트 로그가 원천이고 현재 상태가 파생이다([distributed/22](../../distributed/22-event-sourcing/2-summary.md)).

### 5. 비정규화 = 파생본 추가

- 정규화는 한 사실을 한 곳에만 두어 갱신 이상을 없앤다([database/03](../../database/03-normalization/2-summary.md)).
- 비정규화는 읽기를 위해 그 사실의 사본을 하나 더 만든다. 사본은 원천에서 계산되는 파생본이다.
- 같이 정할 세 가지
  1. 원천이 어디인가.
  2. 원천이 바뀌면 사본이 어떤 경로로, 얼마 뒤에 바뀌나.
  3. 어긋남을 어떤 대조로 발견하나.

### 6. 목록 vs 상세 50건 차이

- 의심: 비정규화 사본(목록)의 갱신 경로 누락. 특히 최근에 추가된 쓰기 경로.
- 찾는 쿼리

```sql
SELECT order_id, sum(amount)::int FROM order_event GROUP BY order_id   -- 원천에서 다시 접은 값
EXCEPT
SELECT order_id, total FROM order_list;                                -- 목록 사본
```

- 실험에서는 주문 1~50(`1 | 911`, `2 | 1022`, …)이 나왔고, 차이 합은 25,000이었다.
- 이 쿼리는 한 방향(원천에만 있는 값)이다. 목록 사본에만 남은 행(원천에서 사라진 주문 등)은 `order_list EXCEPT (원천 집계)`를 따로 돌려야 보인다. 중복 행까지 따지려면 `EXCEPT ALL`.
- 원천을 기준으로 하는 이유: 파생본끼리 비교하면 다르다는 것만 알고 어느 쪽이 틀렸는지 모른다. 원천과 비교해야 틀린 쪽이 정해진다.

### 7. 두 원천 주장

- 원인: 같은 사실(고객 등급)에 쓰기 경로가 둘이고, 원천이 정해져 있지 않다. 양방향 동기화는 서로의 값을 덮어쓴다. 어느 값이 남는지는 동기화의 충돌 규칙(나중 쓰기 우선·우선순위 등)에 달려 있어 값이 왔다 갔다 할 수 있다.
- 대처
  - 사실(컬럼) 단위로 원천을 하나 정한다.
  - 다른 쪽의 수정 화면은 원천에 요청을 보내게 바꾸고, 동기화는 원천 → 파생 한 방향으로만 둔다.
  - 역할표(데이터·원천·파생본·갱신 경로·재구축 방법)를 문서로 남긴다.

### 8. 재구축 불가

- 가능한 상황
  - 원천 이벤트가 보존 기간이 지나 지워졌다.
  - 파생본이 과거 변화(이력)를 필요로 하는데 원천이 현재 상태만 가지고 있다(현재 상태만으로 계산되는 파생본은 현재 테이블을 다시 읽어 재구축할 수 있다).
  - 파생본에만 있는 수정(직접 수정)이 쌓여, 재구축하면 그 수정이 사라진다.
- 미리 정해 둘 것: 재구축에 필요한 원천 보존 기간, 파생본 직접 수정 금지(수정은 원천의 보정 사건으로), 파생본마다의 재구축 절차.
