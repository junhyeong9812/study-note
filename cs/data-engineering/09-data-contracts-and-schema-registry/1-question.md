# data-engineering/09-data-contracts-and-schema-registry — 질문

## 질문

1. (왜) 스키마 레지스트리를 쓰고 있어도 데이터 계약이 따로 필요한 이유는? 계약의 다섯 칸(스키마·의미·품질·SLA·소유자) 중 레지스트리가 기계적으로 검사하는 것은 무엇이고, 못 하는 것의 예를 하나 들어라.
2. (정의) Confluent Schema Registry의 BACKWARD·FORWARD·FULL을 "누가 어떤 스키마로 누구의 데이터를 읽나"로 설명하고, 각 모드에서 생산자와 소비자 중 무엇을 먼저 배포해야 하나?
3. (예측) Avro 스키마 v1 `{id long, amount long, memo string 기본 null}`에서 (a) 기본값 없는 `currency` 추가, (b) 필수 `amount` 삭제, (c) `amount`를 `double`로 넓히기를 하면 BACKWARD·FORWARD·FULL 판정은 각각 어떻게 나오나? 모형 실험 A의 출력으로 확인하라.
4. (예측) `region`(선택, 기본 null)을 `region_code`(선택, 기본 null)로 이름만 바꿔 등록하면 FULL 모드에서 통과하나? 통과한다면 옛 소비자가 새 레코드를 읽을 때 무엇을 보나?
5. (경계) v1 `{id}` → v2 `{id, region 기본 "KR"}` → v3 `{id, region 기본값 없음}` 순서로 등록했다. 비transitive BACKWARD와 BACKWARD_TRANSITIVE에서 v3 등록은 각각 어떻게 되나? 운영에서 이 차이가 드러나는 순간은?
6. (장애 진단) JSON으로 적재하는 파이프라인에서 어느 날부터 `region`이 100% NULL이고, 지역 차원과 inner join하는 매출 리포트에서 그날 매출이 사라졌다. 잡은 성공이다. 원인을 확인하는 SQL 두 가지와 즉시 복구·재발 방지책을 대라.
7. (장애 진단) 상태별 주문 리포트에서 "기타"가 0%에서 33%로 뛰었다. 무엇을 의심하고, 소비자 코드는 어떻게 바꾸나?
8. (연결) 계약 위반을 막을 수 있는 강제 지점을 앞에서 뒤로 나열하라. 레지스트리 밖으로 들어오는 데이터(파일·DB 추출)는 어디서 막나? 차단과 경고의 선택은 어느 노트로 이어지나?
9. (연결) 상류가 필드 이름을 정말 바꿔야 한다. DB 컬럼 이름 변경과 같은 절차로 계약을 바꾸는 순서를 쓰고, 소비자 목록은 어디서 얻나?
