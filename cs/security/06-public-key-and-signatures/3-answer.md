# security/06-public-key-and-signatures — 정답

## 정답

### 1. 왜 서명인가 — 검증자 = 위조자 문제

- HMAC은 만드는 키와 검증하는 키가 같다.
  - API 서버 수십 대가 검증하려면 그 키를 수십 곳에 둔다. 한 곳에서 새면 누구나 유효한 태그를 만든다.
  - 검증하는 서버 자신도 태그를 만들 수 있다. "인증 서버만 발급한다"는 경계가 사라진다.
- 서명은 개인키(발급자만)와 공개키(검증자 전부)를 나눈다.
  - 검증 서버에 비밀이 없으니, 검증 서버가 털려도 위조는 못 한다.

### 2. 서명 흐름과 성질

```text
  서명자: M ─> H(M) ─> Sign(d, H(M)) = σ ──(M, σ)──> 검증자: H(M') ─> Verify(Q, H(M'), σ) → true/false
```

- 주는 것: 무결성(한 비트라도 바뀌면 false), 출처 인증(그 개인키 주인), 부인 방지.
- 주지 않는 것: 기밀성. M은 평문으로 간다.
- 실험(OpenJDK 21.0.12): 1비트 바꾼 `pay 900 to bob`에 대해 Ed25519·ECDSA P-256·RSA-PSS 모두 `verify=false`.

### 3. 교과서 RSA 계산

- n = 61 × 53 = 3233, φ = 60 × 52 = 3120, d = 17⁻¹ mod 3120 = 2753.
- σ = 65^2753 mod 3233 = 588, 검증 588^17 mod 3233 = 65 → 일치.
  - 실험 출력: `toy RSA n=3233 phi=3120 d=2753 sig=h^d mod n=588, sig^e mod n=65`.
- 그대로 쓰면 안 되는 이유: 패딩이 없으면 σ(a)·σ(b) mod n = σ(a·b) 같은 곱셈 성질로 서명하지 않은 값의 서명을 만들 수 있다. 같은 입력에 같은 출력이라 추측 공격에도 약하다.
- RFC 8017 §8: 새 응용에는 RSASSA-PSS가 REQUIRED, RSASSA-PKCS1-v1_5는 기존 호환용.

### 4. 같은 메시지를 두 번 서명하면

- Ed25519: **같다.** RFC 8032 §5.1.6이 r = SHA-512(prefix ‖ M)로 정한다. 개인키와 메시지만으로 결정된다.
- JDK 21 `SHA256withECDSA`: **다르다.** 서명마다 난수 k를 새로 뽑는다.
- 실험: `Ed25519 ... same msg twice equal=true`, `ECDSA P-256 ... same msg twice equal=false`. OpenSSL 3.0.13에서도 같은 결과(`ed25519 same msg -> identical sig`, `ecdsa same msg -> different sig`).

### 5. k 재사용 → 개인키

```text
  s₁ = k⁻¹(z₁ + r·d),  s₂ = k⁻¹(z₂ + r·d)     (같은 k → 같은 r)
  s₁ - s₂ = k⁻¹(z₁ - z₂)  →  k = (z₁ - z₂)/(s₁ - s₂) mod n
  d = (s₁·k - z₁)/r mod n
```

- r, s₁, s₂는 서명에 공개돼 있고 z₁, z₂는 메시지 해시라 누구나 계산한다. 그래서 개인키 d가 나온다(PS3 2010).
- RFC 6979: k를 HMAC_DRBG(개인키, 메시지 해시)로 유도한다. 메시지 해시가 다르면 사실상 다른 k가 나오고, 난수 생성기 품질에 기대지 않는다.
- RFC 8032(Ed25519): r = SHA-512(prefix ‖ M). 설계부터 결정적이다.

### 6. 키 크기와 보안 강도

- SP 800-57 Part 1 Rev.5 표 2: 128비트 강도 = RSA k=3072, ECC f=256~383.
- RSA-2048 = 112비트 강도(같은 표의 112 행: k=2048, f=224~255).

### 7. HS256 토큰이 통과했다

- 의심: 알고리즘 혼동. 검증기가 헤더 `alg`를 믿고 HMAC 검증으로 바꿨고, 키 자리에 RSA 공개키 바이트가 들어갔다. 공개키는 공개돼 있으니 누구나 그 "HMAC 키"로 태그를 만든다.
- 고침
  - 키마다 허용 알고리즘을 고정한다(`TrustedKey(kid, key, alg)`). 헤더 `alg`는 일치 확인에만 쓰고, 불일치면 거부.
  - 허용 목록 밖 `alg`(none 포함)는 거부.
  - "HS256으로 바꾼 토큰은 401"이라는 음성 테스트를 둔다.

### 8. 검증 코드가 있는데 위조가 통과

- 흔한 실수
  - `verify()`의 boolean 반환값을 버린다.
  - 검증 예외를 `catch`로 삼키고 계속 진행한다(fail-open).
  - 개발용 "검증 끄기" 설정이 운영에 남았다.
- 재발 방지
  - 검증 실패를 예외로 감싸는 단일 함수만 쓰게 한다.
  - 1비트 바꾼 메시지·다른 키로 만든 서명·빈 서명이 거부되는지 보는 음성 테스트.
  - 검증 실패 수를 지표로 남겨 "0이 계속"인 것도 이상 신호로 본다.

### 9. 공개키의 주인은 누가 보증하나

- TLS: X.509 인증서 체인. CA가 "이 공개키는 이 도메인 것"이라고 서명하고, 클라이언트는 신뢰 저장소의 루트까지 체인을 검증한다([network/30](../../network/30-x509-and-chain-validation/2-summary.md)).
- JWT: 발급자(issuer)의 JWKS 엔드포인트를 TLS로 받아오고, `kid`로 키를 고른다. 발급자 URL을 설정으로 고정하는 것이 신뢰의 시작점이다([security/13-jwks-and-key-rotation](../13-jwks-and-key-rotation/2-summary.md)).
