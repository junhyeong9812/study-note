# security/05-mac-and-hmac — 정답

## 정답

### 1. MAC이 증명하는 것

- 진위(키를 아는 쪽이 만들었다)와 무결성(그 뒤 바뀌지 않았다).
- HMAC은 대칭 키라 검증자도 같은 태그를 만들 수 있다. 그래서 제3자에게 "상대가 보냈다"를 증명하는 **부인 방지**가 없다. 공개 키 서명은 개인 키 보유자만 서명할 수 있어 부인 방지를 **뒷받침**할 수 있다(06번, 원본 §4). 다만 공개 키와 신원의 결합(인증서), 개인 키 단독 관리가 전제이고, 최종 판정은 법적 판단이다(NIST SP 800-57 Part 1 Rev.5 §3.5).

### 2. HMAC 그림과 키 처리

```text
  K0 = (|K| > 64 ? SHA-256(K) : K) 뒤를 0으로 채워 64바이트
  inner = SHA-256((K0 ⊕ 0x36×64) ‖ m)
  tag   = SHA-256((K0 ⊕ 0x5c×64) ‖ inner)
```

- 131바이트 키: 블록(64)보다 길어 먼저 SHA-256으로 32바이트가 된 뒤 0으로 채운다(RFC 4231 TC6가 이 경로).
- 4바이트 키(`"Jefe"`): 그대로 0으로 채운다. 계산은 되지만 RFC 2104 §3은 출력 길이(32바이트)보다 짧은 키를 강하게 권하지 않는다.

### 3. TC1 값과 구현 확인

- `b0344c61d8db38535ca8afceaf0bf12b881dc200c9833da726e9376c2e32cff7`.
- 확인: RFC 4231 벡터(TC1·TC2·TC6처럼 짧은 키·긴 키 경로 포함)를 테스트로 돌린다. 실험 E5에서 JDK `Mac`, 그림대로 짠 손계산, openssl이 TC1·TC2에서 같은 값을 냈고 TC6도 JDK와 손계산이 RFC 값과 일치했다.

### 4. 조기 종료 vs 상수 시간

- 조기 종료 루프(실험 E5, 4096바이트, 3회): 첫 바이트 불일치 23~30 ns, 마지막 바이트 불일치 3,227~13,179 ns. 맞은 길이에 비례해 늘어난다.
- `MessageDigest.isEqual`: 두 경우 모두 약 9.2~10.6 μs(재실행에서는 7.5~10.5 μs). 불일치 위치와 무관한 수준이다 — 첫/마지막 불일치의 차이는 재실행 5회에서 −6%~+8%로 방향이 일정하지 않아 노이즈로 본다. JDK 21 문서: 시간은 첫 인자의 길이에만 의존.
- 절대 수치는 이 환경의 값이고 실행마다 크게 흔들린다(재실행 조기 종료 루프 마지막 불일치 3,069~11,268 ns). 경향만 믿는다.

### 5. `Arrays.equals`로 비교해도 되나

- 안 된다. `Arrays.equals`는 같지 않은 위치를 찾으면 멈추는 의미의 함수이고, 상수 시간을 약속하지 않는다. 4096바이트에서는 차이가 뚜렷했다(328~425 ns vs 25~32 ns, 재실행 297~418 ns vs 28~34 ns).
- 32바이트에서 노이즈에 묻힌 것은 이 측정 환경의 결과일 뿐, 반복 측정·다른 JIT·다른 CPU에서 드러날 수 있다. 약속된 함수(`MessageDigest.isEqual`)를 쓴다.

### 6. 재직렬화 검증

- `json.dumps(json.loads(raw))`: 401. 실험 E5 B — `:`·`,` 뒤에 공백이 생기고 `"가"`가 `"\uac00"`으로 바뀌어 바이트가 달라졌다.
- `sort_keys=True`(공백 없이·`ensure_ascii=False`와 함께): 401. 실험 E5 D — 키 순서가 `amount, id, memo`로 바뀌었다.
- 옵션을 맞춰 원문과 같아진 경우(C)도 있었지만 일반적으로 보장되지 않는다. 원문 바이트로 검증한다.

### 7. Spring MVC 인자

- `@RequestBody byte[] raw`로 원문 바이트를 받는다. 객체(`@RequestBody PayEvent`)로 받으면 원문이 사라진다.
- 순서: 원문으로 HMAC 계산 → `MessageDigest.isEqual`로 비교 → 통과하면 그때 `objectMapper.readValue(raw, ...)`로 파싱 → 타임스탬프 창·요청 ID 중복 확인 → 처리. 파싱 자체가 공격면이라 검증 뒤에 한다(api-design/26).

### 8. 한글 이벤트만 401

- 원인 후보
  - 원문 대신 재직렬화 바이트로 검증(비ASCII 이스케이프 차이).
  - 미들웨어·프록시의 문자셋 변환(UTF-8 이외로 디코드 후 재인코드).
  - 본문을 `String`으로 받는 과정에서 기본 문자셋이 UTF-8이 아님.
- 확인 순서: 받는 쪽이 HMAC에 넣은 바이트를 덤프 → 보내는 쪽 문서의 서명 대상 정의와 대조 → 본문을 바꾸는 미들웨어 확인 → `openssl dgst -sha256 -mac HMAC`으로 원문 파일에 대해 재계산. GitHub 문서도 페이로드를 UTF-8로 다루라고 적는다.

### 9. 같은 이벤트 두 번 처리

- HMAC이 뚫린 것이 아니다. 같은 요청의 복사본은 진짜 태그를 달고 있어 당연히 통과한다(원본 §8). 정상 재시도도 같은 모양이다.
- 빠진 것: 타임스탬프 창 검사, 요청 ID 중복 제거(보관 기간 ≥ 창 × 2), 처리 로직의 멱등성(reliability/13).

### 10. 자르기·키 길이

- 자르기(RFC 2104 §5): 해시 출력의 절반 이상, 그리고 80비트 이상. HMAC-SHA1-80 같은 이름으로 표기한다.
- 키(§3): 무작위로 고르고, 출력 길이 L보다 짧으면 강하게 권하지 않는다. L보다 긴 키는 강도를 크게 늘리지 않으며 블록보다 길면 먼저 해시된다.
