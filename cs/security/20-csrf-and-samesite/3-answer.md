# security/20-csrf-and-samesite — 정답

## 정답

### 1. 성립 조건과 응답 읽기

- 브라우저가 대상 사이트의 쿠키를 "누가 요청을 유발했는지와 무관하게" 자동으로 싣는 성질.
- 공격자는 응답을 **읽지 못한다**(SOP/CORS가 막는다 — 21번). 그래서 목표는 부수효과(이체·비밀번호 변경·설정 변경)뿐이다. 데이터 탈취가 아니라 상태 변경 위조.

### 2. CORS ≠ CSRF 방어

- CORS는 교차 출처 **응답 읽기**를 막는다. 상태 변경 요청(부수효과)이 서버에 닿는 것은 막지 않는다 — 단순 요청은 CORS 검사 전에 서버에 도착한다(21번 실험).
- CSRF는 그 "서버에 닿아 처리되는 것"을 노린다. 응답을 읽을 필요가 없으므로 단순 요청에 대해 CORS는 방어가 되지 못한다.
- 예외적 활용: API가 단순 요청을 받지 않고 커스텀 헤더를 필수로 검사하면, 교차 출처 요청은 preflight를 거쳐야 하므로 엄격한 CORS 허용 목록이 방어에 쓰일 수 있다(OWASP CSRF Cheat Sheet "Custom Headers and CORS").

### 3. SameSite 비교

- `Strict`: 교차 사이트면 어떤 요청에도 쿠키가 안 붙는다(최상위 내비게이션 포함).
- `Lax`: 교차 사이트면 빠지되, 최상위 내비게이션 + 안전 메서드(GET 등)는 예외로 붙는다.
- `None`: 항상 붙는다. `Secure` 필수, 없으면 거부. `Secure` 쿠키는 보통 HTTPS에서만 보내지만 Chrome은 `localhost`·`127.0.0.1`을 예외로 본다(이 노트 실험).
- Chrome 80 롤아웃 이후 SameSite 미지정 쿠키는 `Lax`로 취급(Lax-by-default). 명시한 쿠키는 그대로.

### 4. Lax 쿠키 첨부

- (a) `<img>` GET(하위 리소스): **안 붙는다**. 최상위 내비게이션이 아니다. 실험에서 Lax·Strict 모두 빠지고 None만 붙었다.
- (b) 폼 POST: **안 붙는다**(POST는 Lax 예외가 아니다). 단 Chrome의 "Lax+POST" 유예로 SameSite **미지정** 쿠키는 발급 후 2분 이내면 붙는다(명시적 Lax엔 적용 안 됨. 점검 재실험: 발급 직후 붙고 약 126초 뒤엔 빠짐).
- (c) 최상위 GET 내비게이션: **붙는다**(Lax의 예외 조항). 실험에서 `s_lax`가 붙었다.

### 5. 동기화 토큰

- 공격자 사이트는 응답을 읽을 수 없어 서버가 심은 토큰을 **알 수 없다**. 그래서 위조 폼에 올바른 토큰을 담지 못한다.
- 쿠키로 보내면: 동기화 토큰 패턴에서는 OWASP가 쿠키 전송을 하지 말라고 한다. 쿠키 **값만** 검사하면 교차 사이트에도 자동 첨부되어 의미가 없다. double-submit은 쿠키와 **별도로 제출한 값**(헤더·폼)을 비교하므로 성립하고, 순진한 판의 약점은 쿠키를 심을 수 있는 공격자(취약한 형제 서브도메인 등)다 — OWASP는 서명된 double-submit을 권한다. GET URL에 넣으면: 브라우저 히스토리·서버 로그·`Referer`로 샌다.

### 6. 토큰 인증과 CSRF

- 세션 쿠키 없이 `Authorization: Bearer`로만 인증하면 끌 수 있다. 브라우저가 `Authorization` 헤더를 자동으로 붙이지 않으므로(공격자가 헤더를 못 심는다) 요청이 위조돼도 인증되지 않는다.
- 쿠키 세션을 쓰면서 끄면 뚫린다. "stateless"라는 말만으로 끄면 안 된다 — 실제 인증이 쿠키로 되는지 확인한다.

### 7. 토큰 없이 200

- 그 엔드포인트가 CSRF 보호 밖이다: `GET` 매핑으로 상태를 바꾸거나(GET은 보호 제외), CSRF 보호에서 그 경로를 뺐거나(`csrf.ignoringRequestMatchers`. `permitAll`은 인가 규칙이라 CSRF를 끄지 않는다), REST라며 전역으로 꺼 둔 경우.
- 상태 변경 경로를 전수 점검하고 GET 상태 변경을 없앤다. 실험의 방어 없는 `/transfer`가 `200`으로 뚫린 예.

### 8. SSO 콜백 루프

- 원인: 세션 쿠키가 `SameSite=Lax`/`Strict`라 IdP에서 돌아오는 교차 사이트 **POST** 콜백에 빠졌다. Lax+POST 2분 유예도 명시적 Lax엔 적용 안 된다.
- 대처: 콜백에 관여하는 쿠키만 `SameSite=None; Secure`로 둔다. 콜백은 IdP 출처에서 오는 정상 교차 사이트 POST라 일반 Origin 검사(내 출처만 허용)에서 따로 다루고, OAuth `state`를 요청과 결속해 콜백에서 대조한다(RFC 6749 §10.12). 또는 콜백을 최상위 GET 리다이렉트로 설계해 Lax 예외를 타게 한다.

### 9. XSS가 다 무너뜨린다

- 대상 출처에 XSS가 있으면 공격 스크립트가 CSRF 토큰을 읽고, 쿠키는 자동 첨부되며, 정상 요청을 그대로 만든다. OWASP: "Cross-Site Scripting (XSS) can defeat all CSRF mitigation techniques."
- 따라서 XSS를 먼저 막는다(19번). CSRF 방어는 XSS가 없다는 전제 위에 선다.
