# security/01-security-principles — 정답

## 정답

### 1. CIA와 장애 때의 선택

| 성질 | 잃으면 | FIPS 199 정의 요지 |
|---|---|---|
| 기밀성 | 허가 없는 공개 | 접근·공개에 대한 허가된 제한을 지킴 |
| 무결성 | 허가 없는 변경·파괴 | 부적절한 변경·파괴를 막음(부인 방지·진위 포함) |
| 가용성 | 정당한 사용의 방해 | 제때 믿을 만한 접근·사용 |

- 인가 서버 장애 때 "통과"(fail-open)는 가용성을 지키고, 권한 없는 사람의 읽기(기밀성)·쓰기(무결성)를 허용한다.
- "거부"(fail-closed)는 기밀성·무결성을 지키고 가용성을 버린다.
- 셋은 서로 부딪친다. 장애 때 어느 쪽을 버릴지 미리 정하는 것이 설계다.

### 2. 허가 근거 vs 배제 근거

- 논문: 기본은 접근 없음이고, 보호 체계는 접근이 **허가되는 조건**을 식별한다.
- 허가 방식에서 실수(조건 하나 누락) → 정당한 사용자가 거부된다. 금방 신고가 들어와 발견된다.
- 배제 방식에서 실수(거부 조건 하나 누락) → 공격자가 통과한다. 아무도 불평하지 않아 오래 숨는다.
- 큰 시스템에서는 일부 객체는 덜 검토되기 마련이다(논문의 표현). 그러니 기본이 거부여야 덜 검토된 곳이 안전하다.

### 3. `catch → return true`의 세 경우

| 상황 | 결과 |
|---|---|
| 정상 상태, 허가된 사용자 | 200 |
| 인가 서버가 403 | 403 (예외가 아니므로 정상 분기) |
| 인가 서버 포트 닫힘 | `ConnectException` → catch → **200** |

- 실험 E1(OpenJDK 21.0.12, 127.0.0.1)에서 인가 서버를 끈 뒤 mallory 요청이 fail-open 판은 `200`, fail-closed 판은 `503`이었다. 예외는 `java.net.ConnectException`.
- 정상 테스트는 예외 분기를 지나지 않는다. 의존 서버를 죽인 상태의 테스트(장애 주입)만 이 결함을 잡는다.

### 4. 속도 제한기의 fail-open

- 모순이 아니다. fail-safe 기본값은 **접근 판단**(누가 무엇을 할 수 있나)에 대한 원칙이다.
- 일반 API 속도 제한기는 가용성 보조 장치다. 고장 때 통과시켜도 "권한 없는 사람이 권한 있는 일을 하게" 되지는 않는다. Stripe는 그래서 fail-open을 택했다(reliability/11).
- 기준: "고장 때 통과시키면 누가 무엇을 할 수 있게 되나?"
  - 로그인 시도 제한·OTP 시도 제한처럼 그 자체가 보안 통제면 fail-closed가 맞을 수 있다(무차별 대입이 열린다).
  - 어느 쪽을 골랐는지 문서화하고, fail-open이면 경보를 단다.

### 5. 만료 없는 판정 캐시

- 권한을 회수해도 캐시가 "허가"를 계속 돌려준다. 실험 E1: 회수 후 캐시 판 `200`, 매번 묻는 판 `403`.
- **완전한 중재** 위반이다. 논문은 권한 확인 결과를 기억해 두는 구현은 권한이 바뀌면 그 기억을 체계적으로 갱신해야 한다고 적는다.
- 고치는 법
  - TTL을 둔다. TTL = 회수가 반영되기까지의 최대 지연이라고 문서화한다.
  - 권한 변경 이벤트로 해당 키를 지운다.
  - 송금·권한 변경 같은 민감 작업은 캐시를 거치지 않는다.

### 6. 최소 권한 = 피해 반경

- 막는 원칙이 아니다. 인젝션 자체는 파라미터 바인딩(18번)이 막는다. 바인딩할 수 없는 테이블·열 이름·정렬 방향은 허용 목록으로 제한한다(OWASP SQL Injection Prevention Cheat Sheet). 최소 권한은 **뚫린 뒤**의 피해를 줄인다.
- superuser 계정: 모든 DB 읽기, `DROP`이 열린다. PostgreSQL이면 기본적으로 superuser에게만 허용되는 서버 파일 읽기 함수(`pg_read_file`)까지 열린다.
- 자기 스키마 DML만: 그 앱이 원래 만질 수 있는 테이블 범위로 피해가 줄고, 다른 서비스 데이터에는 직접 닿지 않는다.
  - 단, 자기 스키마 안에 다른 스키마를 참조하는 뷰가 있으면 기본적으로 뷰 소유자 권한으로 원본이 읽힌다(PostgreSQL `CREATE VIEW` 문서). 실제 범위는 뷰·함수까지 확인한다.
- 논문도 최소 권한이 "사고나 오류로 생기는 피해를 제한한다"고 적는다.

### 7. 심층 방어가 한꺼번에 뚫릴 때

- 층들이 **같은 가정**에 기댔을 가능성이 크다.
  - 예: 방화벽·내부 서비스·DB가 모두 "내부망에서 온 요청은 믿는다"에 기댔다. 내부망 안의 서버 하나(SSRF·탈취된 파드)가 뚫리자 세 층이 같이 무력화된다.
- 층은 서로 다른 실패 원인을 가져야 한다: 네트워크 정책 + 요청 단위 인가 + 감사 로그 + 최소 권한 계정.

### 8. `denied=0`, `error` 급증, `/admin` 2xx 80배

- 해석: 인가 서버 장애 동안 예외 경로가 허가로 떨어졌다(fail-open). "거부 0건"은 아무도 막히지 않았다는 뜻이다.
- 확인 순서
  1. 인가 클라이언트 코드의 catch·기본값(`ALLOW` enum, `null` 정책 처리).
  2. 장애 구간 `/admin/**` 2xx 요청의 주체 목록 — 원래 권한이 있는 사용자였는지 대조.
  3. 그 구간의 쓰기 작업 감사 로그.
- 조치: 판정 불가를 503으로 바꾸는 수정 배포, 장애 구간의 무단 작업 되돌림·사고 보고, 장애 주입 테스트 추가.

### 9. `permitAll` vs `denyAll`로 끝내기

- `anyRequest().permitAll()`: 새로 만든 `/internal/debug`가 규칙 추가를 잊으면 **열린다**(배제 방식).
- `anyRequest().denyAll()`: 규칙 추가를 잊으면 **막힌다**. 개발 중 바로 403으로 드러난다(허가 방식 = fail-safe 기본값). Spring Security 레퍼런스(7.1판)도 이를 "규칙 갱신을 잊는 사고를 막는 전략"으로 든다.
- `AuthorizationFilter`가 REQUEST뿐 아니라 FORWARD·ERROR·INCLUDE 디스패치마다 도는 것은 **완전한 중재**다. 에러 페이지 포워드처럼 눈에 안 띄는 경로도 확인한다. 필요한 디스패치 유형만 명시적으로 허가한다.
