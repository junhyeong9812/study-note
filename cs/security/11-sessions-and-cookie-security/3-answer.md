# security/11-sessions-and-cookie-security — 정답

## 정답

### 1. 세션 ID와 bearer

- HTTP는 요청 사이의 상태를 기억하지 않는다. 로그인 때 서버가 무작위 세션 ID를 주고, 브라우저가 매 요청에 쿠키로 돌려보내야 한다. 서버는 그 ID로 저장소에서 "alice 로그인됨"을 찾는다.
- *bearer*: 값을 가진 사람이면 누구든 그 사용자로 취급된다는 뜻이다. 서버는 "누가" 내밀었는지 구분하지 않는다.
- 그래서
  - 추측할 수 없어야 한다: 엔트로피 최소 64비트(OWASP). CSPRNG로 128비트가 흔하다.
  - 의미가 없어야 한다: 사용자 ID·시각을 넣지 않는다. 정보는 서버 쪽 세션에 둔다.
  - 이름은 일반적으로: `JSESSIONID` 같은 기본 이름은 기술 스택을 드러낸다.

### 2. 세션 고정

```text
  공격자: ① 사이트에서 sid=AAA 받음 → ② 피해자 브라우저에 AAA를 심음
  피해자:                          ③ AAA로 로그인
  서버:   취약 → AAA를 로그인 세션으로 승격 → ④ 공격자가 AAA로 alice 행세
          고침 → 로그인 순간 새 ID BBB 발급, AAA 폐기 → ④는 401
```

- 서버 줄 하나(로그인 때 ID 재발급)를 바꾸면 무너진다. 공격자가 아는 ID가 로그인 뒤에는 쓸모없어지기 때문이다.
- 실험: 재발급 없음 → 공격자 sid로 `/me`가 `200 user=alice`, 재발급 → `401`.
- Spring Security: Servlet 3.1+ 기본 전략이 `changeSessionId`다. 컨테이너의 `changeSessionId()`로 ID만 바꾸고 속성은 유지한다.

### 3. 출처와 사이트

| 쌍 | 같은 출처? | 같은 사이트? |
|---|---|---|
| ① `a.shop.example` vs `b.shop.example` | 아니다(호스트 다름) | 맞다(등록 가능 도메인 `shop.example`이 같다고 할 때) |
| ② `127.0.0.1:18431` vs `localhost:18432` | 아니다 | 아니다(호스트 자체가 다름) |
| ③ `app.example:443` vs `app.example:8443` | 아니다(포트 다름) | 맞다 |

- ③에서 쿠키는 공유된다. 쿠키는 포트를 구분하지 않는다(RFC 6265 §8.5). 같은 호스트에 신뢰 수준이 다른 서비스를 포트로만 나누면 쿠키가 섞인다.

### 4. 요청 종류별로 실리는 쿠키

| | 최상위 GET | 최상위 POST | `<img>` |
|---|---|---|---|
| Strict | 안 실림 | 안 실림 | 안 실림 |
| Lax | 실림 | 안 실림 | 안 실림 |
| None; Secure | 실림 | 실림 | 실림 |
| 속성 없음(Chrome) | 실림 | 생성 후 2분 이내면 실림 | 안 실림 |

- 실험(Chrome 151) 결과가 표와 같았다. 속성 없는 쿠키는 생성 직후 POST에 실렸고 130초 뒤에는 안 실렸다.
- 이유: Chrome은 속성 없는 쿠키를 Lax로 취급하되, 호환을 위해 "만든 지 2분 이내"이면 최상위 POST에도 보낸다(Lax + POST, 임시 조치). 6265bis 초안은 이를 Lax-allowing-unsafe로 기술하고 2분을 합리적 한도로 적는다.

### 5. SSO 콜백의 state 불일치

- 원인: IdP가 `form_post`로 콜백을 **다른 사이트의 최상위 POST**로 보낸다. state·세션 쿠키가 Lax(또는 속성 없음)라 실리지 않는다. 빨리 끝내면 성공하는 것은 속성 없는 쿠키의 2분 예외 때문이다.
- 고치는 법
  1. 콜백에 필요한 임시 쿠키(state·nonce)만 `SameSite=None; Secure`로, 수명을 짧게 둔다. 세션 쿠키는 Lax 유지. 인가 요청 상태를 세션이 아니라 그 임시 쿠키에 저장하도록 구성한 경우에 한한다(Spring Security 기본 저장소는 세션 — 그대로면 "세션 없음"이 남는다).
  2. IdP 응답 방식을 쿼리(최상위 GET 이동)로 바꾼다. Lax 쿠키가 실린다.
- 공통: SameSite를 명시해 브라우저 기본값에 기대지 않는다.

### 6. `HttpOnly`의 범위

- 보호됨: XSS 스크립트가 `document.cookie`로 세션 ID를 **읽어 가는 것**. 실험에서 `HttpOnly` 쿠키는 `document.cookie`에 없었다.
- 보호 안 됨: XSS 스크립트가 그 페이지 안에서 요청을 보내는 것. 브라우저가 쿠키를 자동으로 실으므로, 공격자는 세션을 훔치지 않고도 사용자 권한으로 행동한다. XSS 자체를 막아야 한다(19번).

### 7. 하위 도메인이 세션을 오염

- 보이는 것: 요청에 같은 이름 쿠키가 두 개(`Cookie: sid=...; sid=...`), 세션 쿠키가 `Domain=example.com`으로 설정돼 있다.
- 원인: 하위 도메인은 상위 도메인 범위의 쿠키를 설정할 수 있다. 침해된 `promo`가 자기 sid를 심어 세션 고정을 하거나 덮어썼다.
- 고침: 세션 쿠키를 host-only로(`Domain` 생략), 이름에 `__Host-` 접두(Secure + `Path=/` + Domain 없음 강제). 신뢰 수준이 다른 서비스는 다른 등록 도메인으로 분리한다.

### 8. 유휴 만료와 절대 만료

- 유휴 만료: 마지막 요청 뒤 일정 시간이 지나면 끝. 자리를 비운 공용 PC의 세션을 닫는다.
- 절대 만료: 로그인 뒤 일정 시간이 지나면 활동과 무관하게 끝. 탈취된 세션을 공격자가 계속 써서 유휴 만료를 피하는 것을 막는다.
- Spring Boot `server.servlet.session.timeout` 기본값은 `30m`(유휴).
- 절대 만료는 프로퍼티가 없다. 로그인 시각을 세션 속성에 저장하고, 필터에서 `loginAt + 최대 수명`을 넘으면 `invalidate()` 후 `401`.

### 9. 로그아웃 뒤 살아 있는 세션

- 확인: 로그아웃 응답이 쿠키를 `Max-Age=0`으로만 지우는지, 서버 저장소에 그 sid 키가 남아 있는지(`redis-cli EXISTS ...`).
- 원인: 클라이언트 쿠키만 지웠다. 이미 복사된 sid는 서버에서 여전히 유효하다.
- 고침: `session.invalidate()`로 서버에서 지우고, 쿠키도 만료시킨다. 절대 만료를 둔다.
- 모든 기기 로그아웃: 사용자 ID로 그 사용자의 세션들을 찾을 색인이 필요하다(Spring Session `FindByIndexNameSessionRepository`). 비밀번호 변경 때도 같은 기능으로 다른 세션을 끊는다.
