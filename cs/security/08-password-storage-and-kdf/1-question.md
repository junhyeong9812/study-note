# security/08-password-storage-and-kdf — 질문

## 질문

1. (왜) 비밀번호를 AES로 암호화해 저장하는 것과 느린 KDF로 해시해 저장하는 것은 DB 유출 때 무엇이 다른가? 왜 SHA-256 한 번은 "안전한 해시"인데도 비밀번호 저장에 부적합한가?
2. (경계) salt가 막는 공격과 막지 못하는 공격은 각각 무엇인가? salt는 비밀이어야 하나? NIST SP 800-63B-4와 RFC 9106이 요구·권고하는 salt 길이는?
3. (예측) bcrypt cost를 10에서 12로 올리면 해시 한 번의 시간은 대략 몇 배가 되나? 실험 장비에서 cost 10은 약 몇 ms였고, 단일 SHA-256 속도와 비교하면 추측 수는 대략 몇 배 차이 나나?
4. (예측) python3-bcrypt 3.2.2로 `a` 72개의 해시를 만든 뒤 `a` 73개, `a` 71개, 한글 `가` 24자에 `나`를 붙인 입력으로 각각 검증하면 결과는? 그 이유는?
5. (연결) Okta 2024 사고에서 `bcrypt(userId + username + password)` 설계가 왜 문제가 됐나? 52자라는 숫자는 어디서 나오는지 바이트 관점으로 설명하라.
6. (경계) 메모리 하드 함수란 무엇이며, scrypt·Argon2id와 PBKDF2·bcrypt는 이 점에서 어떻게 갈리나? Argon2id가 i와 d 방식을 섞는 방법은?
7. (경계) OWASP Cheat Sheet, RFC 9106, Spring Security 7.1.1 기본값의 Argon2id 메모리 파라미터를 비교하라. 실제 값은 무엇으로 정하나?
8. (장애 진단) 비밀번호 비용 인자를 올린 배포 직후 로그인 p99가 수 초가 되고 파드가 OOMKilled 됐다. 원인과 대처는?
9. (장애 진단) 레거시 DB의 `password` 컬럼이 64자 16진수이고 같은 값이 여러 행에 반복된다. 무엇을 뜻하며, 사용자 비밀번호를 모르는 상태에서 어떻게 안전한 방식으로 옮기나?
10. (연결) pepper는 salt와 무엇이 다르고 어디에 두나? pepper가 바뀌거나 유출되면 왜 대응이 어렵고, 어떻게 대비하나?
