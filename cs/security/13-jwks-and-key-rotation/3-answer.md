# security/13-jwks-and-key-rotation — 정답

## 정답

### 1. 공개키 배포가 어려운 이유

- 공개키로는 서명을 위조할 수 없으니 기밀성은 문제가 아니다. 문제는 **새 키를 검증자에게 제때 전달하고, 옛 키를 제때 거두는 것**이다.
- 설정 파일에 박아 두면, 발급자가 새 키로 서명을 시작하는 순간 검증자는 정상 토큰을 하나도 검증하지 못한다(401 폭증). 피하려면 회전 때마다 모든 검증자를 재배포해 키를 손으로 맞춰야 한다. 원본 [foundations/security/jwks.md](../../foundations/security/jwks.md) §1.

### 2. 캐시 처리 흐름

```text
  토큰 kid
    → TTL 지남? ─예→ JWKS 페치 ─실패→ 401(fail-closed)
    → kid 있음? ─예→ 서명 검증 → 200/401
    → (없음) 쿨다운 지났나? ─예→ JWKS 페치 → 그래도 없으면 401 "kid not found"
                           └아니오→ 401 "kid not found"
```

### 3. 사전 게시 없는 회전

- 재페치 없음: 다음 페치는 TTL이 끝나는 t=600이다(= 회전 전 마지막 페치 t=0 + TTL 600. 회전 시각 + TTL인 t=700이 아니다). t=100~599의 요청 500건이 모두 401이다. 실험 A에서 `{200=300, 401 kid not found=500}`, 첫 200 t=600.
- 재페치(쿨다운 30초) 있음: t=100의 첫 요청에서 미지 `kid`로 재페치해 바로 200. 실험 A에서 `{200=800}`, 페치 2회(t=100 강제, t=700 TTL).

### 4. 정기 회전 절차

1. 새 키 생성(KMS·HSM 안).
2. JWKS에 새 공개키 추가(새 `kid`).
3. 대기 — 하한: 모든 검증자 캐시 TTL의 최댓값. 이 시간이 지나야 모두 새 키를 안다.
4. 서명 키 전환.
5. 대기 — 하한: 옛 키로 마지막 서명한 토큰의 최대 수명 + 허용한 시계 여유(그 토큰이 모두 만료되면 키를 빼도 된다). 검증자 캐시 TTL을 더 기다리는 것은 보수적인 운영 여유다.
6. 옛 공개키 제거.

- 실험 D: 600초 TTL 검증자에 700초 사전 게시 → 재페치 없는 검증자도 401 0건.
- OIDC Core §10.1.1도 은퇴한 키를 "합리적 기간" 남기라고 한다(SHOULD).

### 5. IdP 장애와 401의 시차

- 시차 이유: 검증자는 마지막 성공 페치(t=1990)의 JWKS를 TTL(600초) 동안 쓴다. 캐시가 만료되는 t=2590에 새로 가져오려다 실패하고, 키가 없으니 거부한다. 실험 C가 이 모양이다.
- 검증 생략 금지: 서명 검증을 건너뛰면 아무 토큰이나 통과한다. 인증 장애를 보안 사고로 바꾸는 fail-open이다.
- 검토할 설계: 갱신 실패 시 마지막 JWKS를 상한 시간까지 더 쓰는 장애 허용(Nimbus `outageTolerant`, 기본 꺼짐). 대가는 유출 키를 더 오래 믿는 것이라 상한을 문서로 정한다. 발급자 쪽은 JWKS를 CDN·복제로 고가용화한다.

### 6. 무작위 `kid`와 429

- 원인: 미지 `kid` 재페치에 속도 제한이 없다. 공격자가 매번 다른 `kid`를 단 토큰을 보내면 요청마다 발급자 페치가 생긴다. 실험 B: 쿨다운 0초 → 1000건에 1000회, 30초 → 1회.
- 대처: 재페치 쿨다운, `kid` 형식 검사(허용 문자·길이), 같은 출처의 연속 401에 요청 제한, 재페치 뒤에도 없으면 즉시 거부.
- Spring 주의: `NimbusJwtDecoder.withJwkSetUri(...)`는 Nimbus 빌더를 `rateLimited(false)`로 만든다(main 소스). Nimbus 기본값(최소 간격 30초)이 꺼진다는 뜻이다. 앞단 제한을 따로 둔다.

### 7. `kid`를 조회 키로 쓰면

- `kid`는 서명 검증 **전**에 읽는 값이다. 공격자가 마음대로 쓸 수 있다.
- 파일 경로로 쓰면 경로 조작(`../../...`)으로 엉뚱한 파일을 키로 쓰게 만들 수 있다. DB 조회에 넣으면 인젝션 통로가 된다. 공격자가 아는 값이 "키"가 되면 서명을 위조할 수 있다. RFC 8725 §2.9가 말하는 "받은 claim으로 조회하는 간접 공격" 계열이고, §3.10은 `kid` 조회가 SQL·LDAP 인젝션이 되지 않게 검증·정제하라고 직접 적는다.
- 올바른 역할: 신뢰하는 출처(설정된 발급자의 `jwks_uri`)에서 가져온 JWKS **안에서** 어느 키를 시도할지 좁히는 힌트. 새 출처를 인가하지 않는다. `jku`·`x5u` 헤더를 따라가는 것도 같은 이유로 막는다.

### 8. 긴급 회전

- 정기 회전은 "새 키 먼저 게시, 옛 키는 천천히 제거"다. 긴급 회전은 "옛 키를 즉시 제거"다. JWKS를 새로 받은(또는 캐시를 비운) 검증자부터 옛 키로 서명된 정상 토큰도 무효가 되어 재로그인이 생긴다.
- 캐시 TTL의 영향: JWKS에서 옛 키를 빼도, 각 검증자는 캐시 TTL이 끝날 때까지 그 키를 믿는다. 공격자는 그동안 유출 키로 서명한 토큰을 쓸 수 있다. TTL이 길수록 유출 키의 수명이 길다. 그래서 긴급 시 검증자 캐시를 즉시 비우는 절차(운영자 호출, 재시작)를 준비한다.

### 9. TTL이 정하는 세 기간

| 기간 | TTL을 길게 | TTL을 짧게 |
|---|---|---|
| 폐기·유출 키를 믿는 기간 | 길어진다(위험) | 짧아진다 |
| 새 키를 늦게 아는 기간(재페치 없을 때) | 길어진다(회전 401) | 짧아진다 |
| 발급자 장애를 버티는 기간 | 길어진다(좋음) | 짧아진다(장애 전파) |

- 짧게 하면 발급자 호출이 늘고 발급자 장애가 바로 우리 장애가 된다. 길게 하면 유출 키를 오래 믿는다.
- 미지 `kid` 재페치가 두 번째 칸을 TTL과 분리해 준다. 그래서 TTL은 첫째·셋째 칸의 맞바꿈으로 정하면 된다.
