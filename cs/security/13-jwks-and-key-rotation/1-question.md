# security/13-jwks-and-key-rotation — 질문

## 질문

1. (왜) 공개키는 비밀이 아닌데 왜 "배포"가 어려운 문제인가? 공개키를 설정 파일에 박아 두면 키 회전 때 무슨 일이 생기나?
2. (그림) 검증자 안의 `kid → 공개키` 캐시가 요청 하나를 처리하는 흐름을 그려라. TTL 만료, 미지 `kid`, JWKS 페치 실패 각각에서 어디로 가나?
3. (예측) 검증자 캐시 TTL이 600초이고 미지 `kid` 재페치가 없다. 발급자가 t=100에 새 키를 JWKS에 올리는 동시에 그 키로 서명을 시작했다. 마지막 페치가 t=0이면 언제까지 401이 나나? 재페치(쿨다운 30초)가 있으면?
4. (적용) 사전 게시부터 옛 키 제거까지 정기 회전 절차를 단계로 적어라. 각 대기 시간의 하한은 무엇으로 정하나?
5. (장애 진단) 발급자 IdP 장애가 t=2000에 시작됐는데 우리 API의 401 폭증은 t=2590부터다. 왜 시차가 생기나? 이때 검증을 건너뛰어 서비스를 살리면 안 되는 이유와, 대신 검토할 설계는?
6. (장애 진단) 발급자가 우리 서비스의 JWKS 요청을 429로 막기 시작했다. 검증자 로그에는 매번 다른 `kid`의 "kid not found"가 찍힌다. 원인과 대처는? Spring Security의 JWK Set URI 디코더 기본 설정에서 주의할 점은?
7. (경계) 토큰 헤더의 `kid`를 파일 경로나 DB 조회 키로 써서 공개키를 찾는 설계는 왜 위험한가? `kid`의 올바른 역할은?
8. (경계) 키 유출로 긴급 회전할 때, 정기 회전과 무엇이 반대인가? 검증자 캐시 TTL은 유출 키의 수명에 어떻게 영향을 주나?
9. (연결) 캐시 TTL 하나가 정하는 세 가지 기간은 무엇인가? TTL을 길게·짧게 할 때 각각 무엇을 잃나?
