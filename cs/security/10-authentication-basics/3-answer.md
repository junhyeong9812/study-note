# security/10-authentication-basics — 정답

## 정답

### 1. 저장 방식이 크리덴셜 스터핑을 못 막는 이유

- 크리덴셜 스터핑은 이 서비스의 DB를 깨는 공격이 아니다. 다른 사이트에서 샌 "아이디·비밀번호 쌍"을 **정상 로그인 경로로** 대입한다.
- 사용자가 같은 비밀번호를 재사용했다면, 이 서비스의 KDF는 그 비밀번호가 "맞다"고 정확히 판정한다. 저장 방식은 DB 유출 뒤의 크래킹을 늦출 뿐이다.
- 막는 것
  - 2차 요소(MFA, 가능하면 패스키) — 비밀번호만으로는 로그인이 끝나지 않는다.
  - 유출 비밀번호 차단 목록(NIST SP 800-63B-4 §3.1.1.2) — 가입·변경 때 이미 샌 비밀번호를 거부한다.
  - 남용 제한 — 계정 단위 실패 제한(§3.2.2, 100회 이하), 전역 실패율 감시, 봇 탐지 과제.
- 사례: 23andMe 8-K/A(2023-12-01)는 재사용 비밀번호로 약 0.1% 계정에 접근됐다고 공시했다.

### 2. MFA와 피싱 저항

| 조합 | MFA? | 피싱 저항? |
|---|---|---|
| 비밀번호 + 비밀 질문 | 아니다. 둘 다 "아는 것" | — |
| 비밀번호 + SMS OTP | 맞다(아는 것 + 가진 것) | 아니다 |
| 비밀번호 + WebAuthn 보안 키 | 맞다 | 맞다 |

- SMS OTP는 사람이 값을 옮겨 적는다. 가짜 사이트에 입력한 값을 공격자가 바로 진짜 사이트에 쓴다. SP 800-63B-4 §3.2.5는 수동 입력 방식을 피싱 저항으로 보지 않는다. 전화망 경유는 "restricted" 등급이기도 하다(§3.1.3.3).
- WebAuthn은 검증자 이름 바인딩(출처·rp.id가 서명에 묶임)이라 피싱 저항으로 인정된다(§3.2.5).

### 3. TOTP 계산 과정

```text
  T = floor((지금 − T0) / X)        T0 = 0, X = 30초
  HS = HMAC-SHA-1(K, T를 8바이트 빅엔디언)              → 20바이트
  offset = HS[19] & 0x0F                                → 0~15
  P = HS[offset..offset+3], 최상위 비트를 0으로          → 31비트 정수
  OTP = P mod 10^6                                      → 6자리(앞자리 0 채움)
```

- 최상위 비트를 버리는 이유: 부호 있는 정수와 부호 없는 정수의 나머지 연산이 프로세서·언어마다 달라서다. 31비트로 만들면 모호함이 없다(RFC 4226 §5.3).

### 4. 부록 B의 SHA-256 값이 안 나오는 이유

- 안 나온다. 실험에서 20바이트 키로는 시각 59에 32247374가 나왔다.
- 부록 B 본문은 비밀을 20바이트 하나로 적었지만, SHA-256·SHA-512 행은 32·64바이트로 늘린 비밀(부록 A 참조 코드의 `seed32`·`seed64`)로 계산했다. 승인된 정오표 2866이 이를 확인한다.
- 32바이트 비밀 "12345678901234567890123456789012"로 계산하면 46119246이 나오고, 표의 18개 값이 모두 일치했다(OpenJDK 21.0.12).

### 5. 허용 창과 재사용 거부

- 창: 네트워크 지연용으로 최대 한 칸(현재 칸 + 직전 칸)을 권한다(RFC 6238 §5.2). 넓힐수록 공격 창도 넓어진다.
- 재사용: 같은 칸 안에서 이미 성공한 OTP가 다시 오면 받지 않는다(MUST NOT, §5.2). 사용자별 "마지막 성공 칸 번호"를 저장하고 그 이하 칸은 건너뛴다.
- 동시 요청: 같은 코드를 두 요청이 동시에 보내도 하나만 통과하도록, 갱신을 조건부 UPDATE로 한다.

```sql
UPDATE user_otp SET last_used_step = :step
WHERE user_id = :id AND last_used_step < :step;   -- 영향받은 행이 1이면 성공, 0이면 재사용
```

### 6. 메시지를 통일했는데도 새는 곳

- **응답 시간**: 없는 계정에서 해시 비교를 건너뛰면 응답이 훨씬 빠르다. 실험에서 0.0 ms 대 약 90 ms였다. → 없는 계정도 더미 해시로 같은 비용의 KDF를 돌린다. Spring Security의 `DaoAuthenticationProvider`가 기본으로 하는 방식이다.
- **상태 코드**: 메시지는 같아도 `404`와 `401`로 갈리면 샌다. → 같은 상태 코드.
- **다른 문**: 회원 가입("이미 가입된 이메일"), 비밀번호 재설정("없는 이메일"), 잠금 메시지("계정이 잠겼습니다"는 계정이 있다는 뜻). → 가입·재설정은 "메일을 보냈습니다"로 통일하고 안내는 메일 안에서 한다.
- 막을 수 없는 열거(공개 프로필 등)는 남용 제한으로 속도를 늦춘다.

### 7. 푸시 30건 뒤 승인

- 해석: 공격자가 이미 비밀번호를 가지고 로그인을 반복하며 푸시를 보냈고, 직원이 피로·착각으로 하나를 승인했다(MFA 푸시 피로). Uber 2022-09-19 발표가 같은 형태를 기술했다.
- 즉시
  - 그 승인으로 생긴 세션·토큰·refresh 토큰을 전부 폐기한다(17번).
  - 비밀번호를 재설정하고, 승인 이후 접근한 시스템을 감사 로그로 추적한다(26번).
- 재발 방지
  - 마지막 성공 이후 푸시 횟수 상한(SP 800-63B-4 §3.1.3.2 SHOULD), 연속 거절 시 잠금·알림.
  - 번호 대조(화면의 번호를 휴대폰에 입력).
  - 특권 계정은 WebAuthn 보안 키(피싱 저항).

### 8. WebAuthn이 중계 공격에 강한 이유

- 서명 대상에 브라우저가 채운 `origin`(clientDataJSON)과 rp.id 해시(authenticatorData)가 들어간다. 피싱 사이트에서 만든 응답에는 `bank-login.example`이 적혀 있어 진짜 서버의 검증에서 떨어진다.
- 인증기는 rp.id별로 키를 따로 둔다. `bank-login.example`에서는 `bank.example`의 자격 증명을 쓸 수 없다. 이 범위 제한은 브라우저와 인증기가 함께 강제한다.
- 사람이 값을 옮기는 단계가 없어서 "속아서 입력"할 여지가 없다.
- DB 유출: 서버가 가진 것은 공개키뿐이다. 비밀번호 해시는 크래킹 대상이고, TOTP 비밀 키는 새면 공격자가 OTP를 계속 만들 수 있다. 공개키로는 서명을 만들 수 없다.

### 9. MFA 장애 중 우회

- 보이는 것: 장애 시간대 로그인 성공 로그에 `mfa=skipped` 같은 표시, 외부 호출 예외를 잡아 `true`를 반환하는 코드(`catch (Exception e) { return true; }`).
- 원인: 검증 실패를 허용으로 처리한 fail-open이다.
- 바꾸는 법
  - 외부 검증 실패·타임아웃은 거부로 처리한다.
  - 가용성은 다른 경로로 확보한다: 사용자가 미리 받아 둔 백업 코드, 두 번째 인증기 등록, 다른 요소(예: WebAuthn)로의 전환.
  - 정말 우회가 필요하면 사람이 승인하는 비상 절차를 두고, 누가 언제 왜 우회했는지 기록한다.
