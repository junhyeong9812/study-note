# security/25-supply-chain-security — 정답

## 정답

### 1. "내 코드"가 아닌 "실행하는 모든 바이트"

- 내 코드는 전체의 일부다. 나머지는 의존성이고, 그것들이 또 전이 의존성을 끌어온다.
- 직접 의존성은 내가 적은 것, 전이 의존성은 그것들이 끌어온 것. Log4Shell에서 많은 조직은 log4j-core를 **직접 적은 적이 없었다** — 다른 라이브러리가 끌어온 깊이 박힌 전이 의존성이었다. 그래서 "직접 의존성만" 보면 영향 여부를 놓쳤다.

### 2. 해시가 잡는 것과 못 잡는 것

- 잡는 것: 락파일에 박힌 바이트가 설치·전달 중 **바꿔치기**된 경우(내용 해시 불일치).
- 못 잡는 것: ① 그 고정된 버전이 뒤늦게 취약으로 밝혀진 경우(해시는 여전히 일치), ② 유지보수자가 처음부터 악성 버전을 정식 배포한 경우(악성 바이트의 해시가 박힐 뿐).
- "자동으로 막힌다"가 틀린 이유: 락파일은 **바이트 고정**이다. 세상의 CVE 지식이 바뀌어도 고정된 바이트는 그대로다. 취약으로 밝혀지면 누가 올려 주기 전까지 취약한 채 고정된다.

### 3. tarball 내용 변조 후 npm ci

- `npm ci`가 `EINTEGRITY`로 거부했다(npm 캐시가 빈 환경 기준. 같은 캐시가 남아 있던 재실행에서는 경보 없이 캐시의 원래 바이트를 설치했다 — 바꿔치기가 설치되지 않은 것은 같다).
- 근거: 출력의 `integrity checksum failed when using sha512: wanted sha512-eOphyG8p... but got sha512-c8/AcVBK...`. 락파일에 박힌 해시(wanted)와 실제 설치하려는 바이트 해시(got)가 달라서다. 이름·버전이 같아도 거부된다.

### 4. SBOM과 purl

- SBOM: 산출물에 들어간 구성 요소 목록 — 이름·버전·purl·해시·라이선스·관계. 도구가 찾은 만큼만 담기므로 빠질 수 있다.
- 새 CVE가 공개되면 "우리 산출물 중 그 취약 버전이 어디 있나"를 **목록 조회**로 빠르게 답한다(그 산출물 대상으로 충분히 완전하게 만든 SBOM에 기록된 구성 요소에 한해). 코드를 다시 뒤질 필요가 줄어든다.
- purl(package URL): 생태계·이름·버전을 한 문자열로 적는 표준 식별자(`pkg:npm/demo-left-pad@1.0.0`). 도구·DB 사이에서 같은 구성 요소를 가리키는 공통 키.

### 5. Sigstore / SLSA

```text
  Cosign: 임시 키 쌍 생성 ──공개키 + OIDC 토큰──▶ Fulcio: 신원 확인 + 짧은 수명 인증서 발급
  Cosign: 그 임시 개인 키로 산출물 서명 (키는 버림)
  Rekor: 다이제스트·서명·인증서를 append-only 로그에 기록
  검증자: 서명 + Rekor 기록으로 "기대한 신원이 만든 바이트"를 확인
```

- Rekor가 append-only 머클 로그인 이유: 포함 증명·일관성 증명을 검증하고 제3자가 로그를 감시하면, 기록을 지우거나 조용히 바꾼 것이 **드러난다**(CT와 같은 구조). 감시자가 없으면 운영자 부정이 안 드러날 수 있다(Sigstore Security Model: "If no third parties monitor the logs, then any misbehavior by Rekor and Fulcio might go undetected."). 그래서 "이 서명이 실제로 그때 있었다"가 증명된다.
- SLSA Build L1 vs L3: L1은 provenance가 있으나 위조·우회가 쉽다. L3는 강화된 빌드라 위조에 "대부분의 공격자 능력을 넘는 취약점 악용"이 필요하다(SLSA v1.0).

### 6. minimumReleaseAge와 업데이트 차등

- 이유: 새로 나온 버전이 악성(②③)이어도, 며칠 묵히면 커뮤니티가 알아채 경보가 뜰 시간을 번다. 값싼 방어다.
- 차등: 보안 경보 업데이트는 **즉시**(위험을 줄이는 쪽), 일반 업데이트는 **묵힘**(새 버전이 가져올 위험을 줄이는 쪽). 정리 노트의 예시 설정에서는 묵힌 뒤 patch·minor는 테스트 통과 시 자동 병합, major만 사람 검토다. 둘은 반대 방향의 위험이라 정책을 나눈다.

### 7. 정상 버전의 백도어 (xz형)

- 해시 고정이 못 막은 이유: 업스트림 릴리스 자체에 백도어가 들어가 **악성 바이트가 정식 배포**됐다. 그 악성 바이트의 해시가 락파일에 박힐 뿐, 대조는 통과한다.
- 겨냥하는 방어: `minimumReleaseAge`(묵혀서 들통날 시간), 재현 빌드·tarball 대조(소스 = 배포물 검증 — xz는 백도어를 빌드에 끼우는 스크립트 한 부분이 git엔 없고 배포 tarball에만 있었다. 위장 테스트 파일은 git에도 있었다), 서명·출처(SLSA)로 신뢰 경로 축소.

### 8. 미패치 침해 (Equifax형)

- 빠진 것: 패치가 **있었는데** 적용 대상 식별·적용이 안 됐다. GAO-18-559: 스캔이 해당 포털의 취약점을 탐지하지 못했고, 공지 수신자 목록이 낡아 패치 담당에게 전달되지 않았다.
- 절차 차원: SBOM·자산 목록으로 "어디에 무엇이 있나"를 항상 알고, 자산마다 소유자를 두고, 보안 패치 적용 SLA(며칠 안)를 둔다. 도구(스캐너)만으로는 부족하다 — 누가 언제까지 올리는지가 핵심이다.
