# security/17-refresh-token-rotation-and-revocation — 질문

## 질문

1. (왜) access 토큰은 짧게, refresh 토큰은 길게 두는 이유는? RFC 9700이 refresh 토큰을 "매력적인 표적"이라 부르는 이유는?
2. (그림) 토큰 패밀리 RT1 → RT2 → RT3에서 공격자가 RT2를 훔쳐 RT3 발급 뒤에 쓰면 무슨 일이 일어나나? 서버가 정상 사용자의 RT3까지 폐기하는 이유는?
3. (경계) RFC 9700 §4.14.2가 public client에 요구하는 두 방법은? 각각 무엇으로 재사용을 막거나 알아채나?
4. (예측) 같은 refresh 토큰으로 탭 두 개가 동시에 갱신한다. 유예 창 0초, 10초, 클라이언트 단일 비행일 때 각각의 결과를 실험 출력으로 말하라.
5. (경계) 유예 창(leeway)을 길게 잡으면 무엇을 잃나? Auth0 문서는 유예 창 안에서 어떤 토큰만 재사용을 허용하나?
6. (계산) access 10분, refresh 최종 만료 8시간이다. 로그인 10분 뒤 회전으로 받은 새 refresh 토큰의 남은 수명은 RFC 10017 §6.3.2.3에 따르면 얼마인가? 회전이 수명을 늘리면 무엇이 문제인가?
7. (장애 진단) 비밀번호를 바꿨는데 공격자가 계속 API를 호출한다. refresh와 자기 포함 access 각각에 대해 무엇을 확인하고 어떻게 막나? 실험 4의 539초는 무엇인가?
8. (적용) 서버의 refresh 처리에서 "읽고 판단하고 쓰는" 코드가 경합에 약한 이유와, 조건부 UPDATE로 고친 형태를 써라.
9. (연결) localStorage, 메모리, BFF 중 refresh 토큰을 어디에 두는지에 따라 XSS 앞에서 무엇이 달라지나? RFC 10017이 저장소 격리로도 못 막는다고 한 시나리오는?
10. (장애 진단) 토큰 엔드포인트가 `400 {"error":"invalid_grant"}`를 많이 낸다. 탭 경합인지 탈취인지 로그로 가리는 기준은?
