# security/12-tokens-and-jwt — 정답

## 정답

### 1. 세션 vs 자기 포함 토큰

- 얻는 것: 검증에 저장소 조회가 필요 없다. 키(공개키)만 있으면 어느 서비스든 검증한다. 외부 발급자(OAuth/OIDC)의 토큰도 같은 방식으로 받는다.
- 잃는 것: 서버가 토큰을 기억하지 않으므로 중간 폐기가 어렵다. 탈취된 토큰은 만료까지 유효하다. claim이 늘면 토큰이 커진다.
- 단일 웹 앱: 세션 + `HttpOnly` 쿠키가 단순하고 즉시 폐기가 쉽다.
- 여러 서비스·외부 발급자: 토큰이 맞다. 대신 짧은 수명과 폐기 장치를 함께 설계한다.

### 2. JWT는 암호화가 아니다

- 서명된 JWT(JWS)의 header·payload는 base64url 인코딩일 뿐이다. 누구나 디코딩해 읽는다. 실험에서도 payload가 그대로 보였다.
- 보장하는 것: 무결성(발급 뒤 바뀌지 않음)과 발급자 진위(그 키를 가진 쪽이 서명함).
- 그래서 개인정보·비밀은 넣지 않는다. 토큰은 로그·프록시·브라우저 저장소에 복제된다.

### 3. 검증 단계

```text
  ① 형식(점 2개, 올바른 JSON)
  ② alg ∈ 서버 허용 목록, 키에 묶인 알고리즘과 일치     ← 서명 검증 앞
  ③ 서명 검증(서버가 가진·발급자가 게시한 키만)
  ④ exp·nbf(작은 여유)      ⑤ iss      ⑥ aud      ⑦ typ(토큰 종류)
  ⑧ 그다음 sub·scope로 인가
```

- 빠지기 쉬운 것: `exp`(서명만 보고 끝냄), `aud`(Spring 기본 검증기에도 없다), `typ`(ID 토큰과 access token 혼동 — Spring 기본 `typ` 검사는 `JWT`·없음을 통과시켜 둘을 구별하지 못한다).
- RFC 7519 §7.2: 형식·서명 단계는 하나라도 실패하면 거부해야 한다(MUST). claim 검사는 §4.1의 각 claim 규정(예: `aud` 불일치 시 거부 MUST)과 RFC 8725 §3.8~§3.11이 요구한다.

### 4. `none`과 HS256 혼동

| 토큰 | 취약 검증기 | 고친 검증기(허용 = {RS256}) |
|---|---|---|
| `alg:none`, 서명 없음 | 서명 검사를 건너뛰어 `ACCEPT sub=admin` | `REJECT`(허용 목록 밖) |
| `alg:HS256`, 공개키 PEM으로 HMAC | 같은 공개키로 HMAC을 계산해 일치 → `ACCEPT sub=admin` | `REJECT`(허용 목록 밖) |

- 실험(OpenJDK 21.0.12)에서 위 결과 그대로 나왔다.
- 핵심: 공개키는 공개 정보다. 그것을 HMAC 비밀로 쓰게 두면 공격자도 같은 MAC을 만든다. 막는 법은 알고리즘을 서버가 정하고, 키마다 알고리즘 하나만 허용하는 것(RFC 8725 §3.1)이다. CVE-2015-9235(jsonwebtoken < 4.2.2)가 이 유형이다.

### 5. HS256 vs RS256

- HS256: 같은 비밀로 서명하고 검증한다. 검증할 수 있는 서비스는 모두 토큰을 **발급할 수도** 있다. 한 서비스 안에서만 쓴다.
- RS256(또는 ES256·EdDSA): 개인키로 서명, 공개키로 검증한다. 검증자는 발급할 수 없다. 여러 서비스·외부에 검증을 맡길 때 쓴다.
- 사람이 정한 문자열 키: 토큰 하나만 얻으면 오프라인 사전 대입으로 키를 찾을 수 있다(RFC 8725 §2.2). 찾으면 아무 토큰이나 발급한다. CSPRNG로 충분히 긴 키를 만든다.

### 6. `Jwt used before`

- 해석: 그 인스턴스가 보기에 토큰의 `nbf`가 (60초 여유를 더해도) 아직 미래다. Spring의 `JwtTimestampValidator`는 `exp`와 `nbf`만 본다. 그 인스턴스의 시계가 **느리다**. 다른 인스턴스는 정상이므로 토큰이 아니라 시계 문제다.
- 대처: NTP 동기화 복구(`chronyc tracking`으로 오프셋 확인), 오프셋 알람.
- 여유를 10분으로 늘리면: 증상은 사라지지만 모든 인스턴스가 만료 토큰을 10분 더 받는다. RFC 7519는 여유를 "보통 몇 분 이하"로 둔다. Spring 기본은 60초다.

### 7. 탈취 토큰 즉시 차단

- 사용자 단위 컷오프: 사용자에 `tokensValidAfter` 시각을 두고, 비밀번호 변경 때 지금으로 갱신. `iat < tokensValidAfter`면 거부. 저장 크기는 **사용자 수**(사용자당 시각 하나)에 비례한다.
- `jti` 차단 목록: 폐기한 토큰의 `jti`를 TTL(= exp − 지금 + 시계 여유)과 함께 저장. 저장 크기는 **만료 전 폐기된 토큰 수**에 비례한다. 만료와 여유가 모두 지나면 지워도 된다.
- 둘 다 매 요청 조회가 생긴다. 근본적으로는 access token 수명을 짧게 하고 refresh 토큰을 회전한다(17번).

### 8. 다른 서비스용 토큰이 통했다

- 서명 통과 이유: 같은 발급자가 모든 서비스의 토큰을 같은 키로 서명한다. 서명은 "이 발급자가 발급했다"까지만 말한다.
- 빠진 검사: `aud`. 결제 API는 `aud`에 자기 식별자가 있는 토큰만 받아야 한다(RFC 8725 §3.9). 이것이 대체(substitution) 공격이다(§2.7).
- 같은 이유로 ID 토큰을 access token 자리에 받지 않도록 `typ`·검증 규칙을 나눈다(§3.11·§3.12).

### 9. CVE-2022-21449

- Java 15~18(2022-04 CPU 이전, 발견자 블로그 기준. NVD는 지원 판 17.0.2·18을 적는다)의 ECDSA 검증이 r=0, s=0인 서명을 유효하다고 받아들였다. 어떤 메시지·공개키에도 통하는 "빈 서명"이다. NVD CVSS 3.1 7.5(무결성 높음).
- 실험: JDK 21.0.12에서 64바이트 0 서명(`SHA256withECDSAinP1363Format`)은 `REJECT`.
- 교훈: 애플리케이션의 검증 로직이 맞아도 런타임·라이브러리 결함이 뚫는다. JDK와 JWT 라이브러리를 패치 관리 대상에 넣고(25번), "위조 서명은 거부"를 회귀 테스트로 고정한다.
