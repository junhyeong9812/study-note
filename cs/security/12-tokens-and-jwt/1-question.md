# security/12-tokens-and-jwt — 질문

## 질문

1. (왜) 서버 세션 대신 자기 포함 토큰을 쓰면 무엇을 얻고 무엇을 잃나? 단일 웹 앱과 여러 서비스·외부 발급자 환경에서 선택이 어떻게 달라지나?
2. (경계) "JWT는 암호화돼 있으니 payload에 이메일·주민번호를 넣어도 된다"는 주장의 틀린 점은? 서명된 JWT가 실제로 보장하는 것은?
3. (그림) JWT 검증 단계를 순서대로 적어라. 서명 검증 앞에 와야 하는 검사는 무엇이고, 서명 검증 뒤에 빠지기 쉬운 claim 검사는 무엇인가?
4. (예측) 검증기가 헤더의 `alg`로 검증 방법을 고르고, 설정에는 RSA 공개키 하나만 있다. 공격자가 ① `"alg":"none"`에 서명 없이 ② `"alg":"HS256"`에 그 공개키 PEM을 HMAC 키로 서명해 `sub=admin` 토큰을 보내면 각각 어떻게 되나? 고친 검증기는 어떻게 다르게 판정하나?
5. (경계) HS256과 RS256 중 무엇을 고르나? "검증할 수 있는 쪽"과 "발급할 수 있는 쪽"의 관계로 설명하라. HS256 키를 사람이 정한 문자열로 두면 무슨 일이 생기나?
6. (장애 진단) 한 인스턴스만 정상 토큰에 `401`을 내고, 로그에 `Jwt used before 2026-10-07T03:00:12Z`가 찍힌다. 원인과 대처는? 시계 여유를 10분으로 늘리는 것이 왜 나쁜 대처인가?
7. (적용) 계정 탈취를 확인하고 비밀번호를 바꿨는데 공격자가 access token으로 계속 API를 쓴다. 서버 저장소를 최소한으로 쓰면서 즉시 막는 방법 두 가지를 대라. 각 방법의 저장 크기는 무엇에 비례하나?
8. (장애 진단) 결제 API가 같은 발급자가 다른 서비스용으로 발급한 토큰을 받아들였다. 서명은 왜 통과했고, 어떤 검사가 빠졌나?
9. (연결) 검증 코드가 올바라도 런타임 라이브러리 결함으로 서명 검증이 뚫린 예(CVE-2022-21449)는 무엇을 받아들였나? JDK 21에서 같은 입력은 어떻게 됐나? 이 사례가 운영에 주는 교훈은?
