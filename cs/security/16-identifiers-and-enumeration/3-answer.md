# security/16-identifiers-and-enumeration — 정답

## 정답

### 1. 랜덤 ID ≠ 인가

- 랜덤 ID는 "추측하기 어렵게" 할 뿐이다. ID는 URL·로그·공유 링크·Referer로 퍼진다. 한 번 새면 인가 없이는 누구나 연다.
- 첫째 층은 객체 수준 인가(15번), 랜덤 ID는 둘째 층(피해를 번호 하나로 묶음)이다.
- RFC 9562 §8: UUID가 추측하기 어렵다고 가정하지 말 것(SHOULD NOT), "보유만으로 접근을 주는 보안 수단(security capabilities)"으로 쓰지 말 것(MUST NOT).

### 2. 순차 ID가 흘리는 것

- 열거: 다음·이전 번호가 곧 다른 객체다.
- 규모: 받은 번호의 최대값이 전체 수에 가깝다.
- 속도: 두 시점의 번호 차이로 그 사이 생성량(주문량·가입자 증가)을 대략 추정한다. 롤백 등으로 버려진 번호도 있어 정확한 건수는 아니다(PostgreSQL 시퀀스 문서).

### 3. 추측 적중 기대값

- 랜덤 64비트: 10⁵ × 10⁴ / 2⁶⁴ ≈ 5.4×10⁻¹¹. 실험 3회 모두 0.
- 순차: 1부터 10⁴까지만 시도해도 10⁴개 전부 적중. 실험 출력 `sequential hits=10000`.
- 전제: 이 값은 공격자가 무작위로 찍을 때의 기대값이다. 생성기가 예측 가능하면 공격자는 이보다 잘 맞히므로, 이 값이 상한 노릇을 하려면 CSPRNG가 필요하다(RFC 9562 §6.9).

### 4. 32비트 생일 충돌

- 기대 충돌 쌍 ≈ k(k−1)/(2N) = 10⁵ × (10⁵ − 1) / (2 × 2³²) ≈ 1.16.
- 50% 지점 ≈ √(2N ln 2) ≈ 7.7×10⁴.
- 실험: 20회 평균 1.35·1.30·0.80(3회 실행), 회당 0~3쌍. 점검 재실행 3회는 0.80·1.00·1.40, 회당 0~4쌍. 이론값 근처에서 흔들린다. 43억 칸이라도 10만 개면 충돌이 날 확률이 약 69%다(0쌍인 회차도 있었다 — 확률이지 확정이 아니다).

### 5. v4·v7 비트 배치와 시각 노출

```text
  v4  [ random 48 ][ver=4][ random 12 ][var][ random 62 ]       랜덤 122비트
  v7  [ unix_ts_ms 48 ][ver=7][ rand_a 12 ][var][ rand_b 62 ]   앞 48비트 = 밀리초 시각
```

- 꺼내기: 상위 64비트를 16비트 오른쪽으로 민다(`getMostSignificantBits() >>> 16`) → 유닉스 밀리초. 실험은 `01a113a8-ec00-…`에서 `2026-10-07T00:00:00Z`를 복원했다. 문자열로는 앞 12자리 16진수다.
- 문제 예: 공개 프로필 ID로 가입 시점이, 주문 ID로 주문 시각이 드러난다. RFC 9562 §8은 보안 용도면 v4를 쓰라(SHOULD)고 적는다.

### 6. 단조 ULID

- 짐작할 수 있다. ULID 명세의 단조 모드는 같은 밀리초 안에서 랜덤 80비트를 1 증가시킨다. 명세 예에서 `…MMVRZ` 다음이 `…MMVS0`이다(base32에서 Z 다음 자리올림).
- 그래서 단조 ULID를 외부 ID로 쓰면 이웃 ID 추측이 쉬워진다. 외부에는 랜덤 공개 ID를 둔다.

### 7. 스키마와 생성 코드

```sql
CREATE TABLE orders (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id text   NOT NULL UNIQUE,
  owner_id  bigint NOT NULL
);
SELECT * FROM orders WHERE public_id = ? AND owner_id = ?;
```

- 피할 것
  - 내부 시퀀스를 그대로 노출하는 것.
  - `java.util.Random` 같은 비-CSPRNG, 짧은 길이(예: 6자리 숫자 ≈ 20비트).
- 고친 생성: `SecureRandom`으로 16바이트 → base64url 22자, 또는 `UUID.randomUUID()`(Java 21 문서상 강한 의사난수 생성기 사용).

### 8. 열거 탐지

- 패턴
  - 한 주체(토큰·IP)가 짧은 시간에 서로 다른 ID를 많이 요청.
  - 404·403 비율 급증.
  - 요청 ID가 연속(5332, 5333, …).
- 대처 순서: 인가 확인·복구(15번) → 노출 범위 산정(로그) → 외부 ID 분리 → 주체별 요청 상한·알림 → 403/404 응답 통일.

### 9. 원본 원칙과의 차이

- 원본(identity-and-ids §1·§3): "**무엇으로 판정하나**" — 바뀌고 재사용되는 이름이 아니라 불변 ID로 판정하라.
- 이 노트: "**밖에 보이는 ID가 무엇을 흘리나**" — 불변이어도 순차면 열거·규모가 샌다.
- 둘을 합치면: 판정은 불변 ID로, 외부 노출은 추측 어려운 불투명 ID로, 표시는 이름으로.

### 10. 8자리 16진수 공유 링크

- 8자리 16진수 = 32비트. 생일 경계로 약 7.7만 개에서 충돌 확률 50%다. 발급량이 늘면 충돌이 기대된다.
- 원인 후보
  - UNIQUE 제약 없이 저장해 같은 ID가 두 파일을 가리켰다(조회가 다른 파일을 반환).
  - 32비트라 추측 공격으로 남의 링크에 닿았다(인가 없는 capability 링크).
- 고칠 것: ID를 128비트 CSPRNG로, UNIQUE 제약 + 충돌 시 재생성, 링크 접근에도 만료·권한 확인. 이미 겹친 행을 찾아 정정하고 접근 로그로 노출 범위를 산정한다.
