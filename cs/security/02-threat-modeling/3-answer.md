# security/02-threat-modeling — 정답

## 정답

### 1. 설계 결함 vs 구현 결함

- A04(2021): 안전한 설계도 구현 결함으로 취약해질 수 있다. 그러나 안전하지 않은 설계는 **완벽한 구현으로 고칠 수 없다** — 필요한 보안 통제가 만들어진 적이 없기 때문이다.
- 체크리스트는 대부분 알려진 구현 결함을 묻는다. "내부 서비스가 누가 붙였는지 모르는 헤더를 믿는다"는 통제 자체가 없는 것이라 체크리스트에 안 걸린다.
- 2025판에서는 같은 범주가 A06:2025 Insecure Design이다.

### 2. DFD와 경계

```text
   (브라우저) ─║─①─> [게이트웨이] ┄┄TB2┄┄ ─②─> [주문 서비스] ─③─> ═[주문 DB]═
              ║                                       └─④─> (외부 이미지 서버)  ─║─ (TB1 재횡단)
          TB1(인터넷↔우리 망)
```

- 경계를 건너는 흐름: ①(TB1), ②(TB2), ④(TB1을 안에서 밖으로, 응답은 밖에서 안으로) — 3개.
- ③은 같은 영역 안의 흐름이지만, DB를 별도 경계로 보는 설계도 있다(권한이 다른 계정). 경계를 어디 긋느냐가 곧 "어디서 다시 검증하나"의 결정이다.

### 3. STRIDE와 성질

| 위협 | 깨지는 성질 |
|---|---|
| 위장 | 인증 |
| 변조 | 무결성 |
| 부인 | 부인 방지 |
| 정보 노출 | 기밀성 |
| 서비스 거부 | 가용성 |
| 권한 상승 | 인가 |

- 놓치기 쉬운 예: 비즈니스 로직 남용. 정상 API로 좌석 수백 개를 선점하는 것은 여섯 범주 어디에도 깔끔하게 들어가지 않는다(A04 시나리오 2). STRIDE는 질문 생성기이지 완전한 목록이 아니다.

### 4. 헤더 통과 게이트웨이

- 결과: `200 role=admin`. 실험 E2(OpenJDK 21.0.12, 127.0.0.1)에서 같은 토큰으로 헤더 없이는 `403 role=user`, 헤더를 넣자 `200 role=admin`이었다.
- 클라이언트가 보낸 `X-User-Role`이 경계를 그대로 넘었고, 게이트웨이는 그 값이 있으니 자기 값을 붙이지 않았다. 변조(T) → 권한 상승(E).

### 5. 고친 게이트웨이 + 직접 접근

- 게이트웨이 경유: `403 role=user`(실험 E2의 [2]).
- 내부 포트 직접: `200 role=admin`(실험 E2의 [3]). 내부 서비스는 요청이 게이트웨이에서 왔는지 확인하지 않는다 — 위장(S).
- 막는 법: 내부 서비스에 게이트웨이만 닿게 하는 네트워크 정책, 서비스 간 mTLS(network/32), 또는 게이트웨이가 서명한 짧은 수명 내부 토큰을 검증. 심층 방어(01번)로 두 층을 같이 둔다.

### 6. 사용자 URL 가져오기

- 방향: 외부 입력(URL)이 경계 **안쪽의 서버**에게 요청을 만들게 한다. 요청은 안에서 밖(또는 다른 내부 주소)으로, 응답은 다시 안으로 들어온다.
- 물을 것: 그 URL이 메타데이터 주소(`169.254.169.254`)·`localhost`·사설 대역이면? 리다이렉트로 내부로 튀면? 응답이 느리거나 거대하면?(D)
- IMDSv2(EC2 사용자 안내서): `PUT`으로 세션 토큰을 먼저 받아야 하고, `X-Forwarded-For`가 붙은 `PUT`은 거부, `PUT` 응답의 IP 홉 제한 기본값 1(계정 기본값을 IMDSv2로 두면 새 인스턴스는 2, 홉 제한을 따로 정하지 않았고 AMI가 `ImdsSupport: v2.0`이면 2, 컨테이너 환경은 AWS 권장 2). AWS는 이를 열린 방화벽·리버스 프록시·SSRF에 대한 심층 방어로 설명한다(안내서가 링크하는 AWS 보안 블로그 글 제목). 근본 방어는 목적지 허용 목록(security/22).

### 7. 네 질문

1. 무엇을 만들고 있나?
2. 무엇이 잘못될 수 있나?
3. 그것에 대해 무엇을 할 건가?
4. 충분히 잘했나?

- 네 번째를 빼면 완화책이 실제로 구현됐는지, 다이어그램이 실제 시스템과 같은지 아무도 확인하지 않는다. 문서는 있는데 사고 경로가 문서에 없는 상태(9번)가 된다.

### 8. 일반 사용자의 `/admin` 200

- 찾을 것: 게이트웨이 **앞단**(클라이언트가 보낸 원본) 요청 헤더에 `X-User-Role`·`X-User-Id`·`X-Forwarded-User` 같은 신원 헤더가 있었는지. 내부 서비스 접근 로그의 출발지가 게이트웨이 주소였는지(직접 접근 여부).
- 분류: 흐름 ②(게이트웨이 → 내부)에서 T(헤더 변조) → E(권한 상승). 출발지가 게이트웨이가 아니면 S(위장)도.
- 고치기: 경계에서 예약 헤더 삭제·재작성, 내부 서비스의 출처 증명(네트워크 정책·mTLS·서명 토큰), 같은 패턴의 다른 헤더 전수 점검, 위협 모델의 흐름 ②에 반영.

### 9. 문서에 없던 사고 경로

- 원인: 한 번 만들고 갱신하지 않았다. 그 뒤 추가된 외부 연동·큐·저장소가 다이어그램에 없다. 네 번째 질문(검증)을 하지 않았다.
- 재발 방지: 흐름을 바꾸는 PR(새 외부 연동·새 저장소·권한 모델 변경)에 DFD 갱신을 리뷰 항목으로 둔다. OWASP Cheat Sheet 권고처럼 시스템과 함께 유지하고, A04(2021) 권고처럼 refinement 회의에 넣는다.
