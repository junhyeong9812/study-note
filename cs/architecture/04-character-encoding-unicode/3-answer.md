# architecture/04-character-encoding-unicode — 정답

## 정답

### 1. 두 가지 약속

- 문자 집합(Unicode)은 글자 ↔ 코드 포인트(번호)를 정한다. 인코딩(UTF-8·UTF-16·CP949 등)은 번호 ↔ 바이트를 정한다.
- 모지바케는 대개 **인코딩** 쪽이 어긋날 때 생긴다. 쓴 쪽의 UTF-8 바이트를 읽는 쪽이 ISO-8859-1·CP949로 해석하면 바이트는 그대로인데 다른 글자가 된다.
- 바이트 자체에는 "나는 UTF-8이다"라는 표시가 없다(UTF-8 BOM은 선택 사항). 그래서 인코딩은 메타데이터(HTTP `charset`, DB 연결 설정)로 함께 전해야 한다.

### 2. 손 인코딩

```text
  가 U+AC00 = 1010 1100 0000 0000 → 3바이트 틀 1110xxxx 10xxxxxx 10xxxxxx
     1110 1010 | 10 110000 | 10 000000 = EA B0 80        UTF-16: AC 00

  😀 U+1F600 → 4바이트 틀 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
     0 0001 1111 0110 0000 0000 (21비트)
     11110 000 | 10 011111 | 10 011000 | 10 000000 = F0 9F 98 80
     UTF-16: 1F600 − 10000 = F600 → 위 10비트 03D, 아래 10비트 200
             D800+03D = D83D, DC00+200 = DE00 → D8 3D DE 00
```

- 실험 1에서 손 인코더 결과가 `getBytes(UTF_8)`과 모두 일치했다(RFC 3629 §3 표).

### 3. 서로게이트 절단

- `length()` = 4(코드 유닛 `0061 D83D DE00 0062`), `codePointCount` = 3.
- `substring(0, 2)`는 `0061 D83D` — 외톨이 상위 서로게이트로 끝난다. `getBytes(UTF_8)`는 `61 3F`. Java는 인코딩할 수 없는 입력을 대체 바이트 `?`로 바꾼다(String 문서). 예외는 없다.
- JS `TextEncoder`는 같은 외톨이 서로게이트를 `EF BF BD`(U+FFFD)로 바꿨다(Node 22.23.2 실험).
- 엄격한 인코더(`CodingErrorAction.REPORT`)를 쓰면 Java에서 `MalformedInputException`이 난다.

### 4. 모지바케와 복구

- `63 61 66 C3 A9`를 ISO-8859-1로 읽으면 `C3`→`Ã`, `A9`→`©`. 결과 `cafÃ©`, 길이 5(실험 2).
- 되돌릴 수 있는 조건: 한 번만 잘못 읽었고, 그 문자셋이 바이트 값마다 글자 하나로 1:1 대응한다(ISO-8859-1). 그러면 latin1로 다시 인코딩해 원래 바이트를 얻고 UTF-8로 읽는다. 실험에서 `café`로 돌아왔다.
- CP949 바이트를 UTF-8로 관대하게 읽으면 틀린 바이트가 U+FFFD로 바뀐다. 원래 바이트 정보가 사라졌으므로 원본 없이는 복구할 수 없다. 실험에서는 `�ѱ�`가 나왔다 — 가운데 `D1 B1`은 우연히 올바른 UTF-8이었다.

- 근거: RFC 3629 §3(유일한 표현, 서로게이트 금지), Unicode 3장 C10(틀린 나열은 오류로 다룬다).

### 6. NFC·NFD·NFKC

```text
  NFC  U+D55C U+00E9                      length 2, UTF-8 5바이트
  NFD  U+1112 U+1161 U+11AB U+0065 U+0301  length 5, UTF-8 12바이트
```

- `equals`는 false, 둘 다 NFC로 맞추면 true(실험 5).
- NFKC는 호환 분해까지 한다. `ｶﾞ①ﬁ` → `ガ1fi`. 반각·원문자·합자의 차이가 사라진다. 원래 모양 정보를 버리므로 사람에게 보일 원문은 그대로 두고, 비교·검색 키에만 쓴다.

### 7. 같은 파일 이름 두 개

- 확인: `ls | xxd`. 한쪽 이름이 `e1 84 92 …`(자모 U+1112)로 시작하면 NFD, `ed 95 9c …`(U+D55C)면 NFC다(실험 9). Java로는 두 이름의 `length()`(10 대 6)와 코드 포인트를 찍어 본다.
- 원인: ext4는 이름을 바이트 그대로 저장하고, NFC·NFD 이름은 바이트가 다르다. 보통의(casefold를 켜지 않은) 디렉터리는 바이트로 비교하므로 두 이름이 따로 있게 된다.
- 막기: 업로드·생성 경로에서 이름을 NFC로 정규화하고, 조회 키도 같은 정규화를 거친다. 기존 데이터는 NFC로 묶어 중복을 찾는다.

### 8. MySQL 1366

- MySQL `utf8`은 `utf8mb3`의 별칭이다. BMP 문자만 최대 3바이트로 담는다. 이모지(U+1F600 등)는 UTF-8 4바이트라 담을 수 없다(MySQL 8.0 매뉴얼 12.9.1·12.9.2). 오류 틀은 `Incorrect %s value: '%s' for column '%s' at row %ld`(1366).
- 바꿀 때: 선언한 `VARCHAR(n)`의 n(글자 수)은 그대로다. 인덱스 키 길이·행 크기 한도는 **바이트로** 그대로라서, 글자당 최대 4바이트가 되면 인덱싱할 수 있는 글자 수가 줄어든다. InnoDB COMPACT·REDUNDANT의 767바이트 인덱스는 utf8mb3 255자 → utf8mb4 191자(매뉴얼 12.9.8). DYNAMIC·COMPRESSED(3072바이트)에서는 1024자 → 768자다(같은 절). 인덱스 정의와 연결 문자셋을 함께 확인한다.

### 9. 정렬 어긋남

- `String.compareTo`는 UTF-16 코드 유닛 값으로 비교한다. 보조 평면 문자는 서로게이트(D800~DBFF)로 시작하므로 U+E000~FFFF 글자보다 **작게** 나온다.
- 예: `U+FF61`(｡)과 `😀`(U+1F600). `compareTo`는 양수(｡가 뒤), 코드 포인트·UTF-8 바이트 비교는 음수(｡가 앞)였다(실험 8).
- UTF-8 바이트 순서 = 코드 포인트 순서(RFC 3629 §1)라서, DB의 코드 값 순 collation(PostgreSQL `C`, MySQL `utf8mb4_bin` — 코드 값 순, 끝 공백 무시)과 앱의 `compareTo`가 이런 문자에서 다르게 줄 세운다. 커서 페이지네이션처럼 두 쪽 순서를 섞으면 누락이 생길 수 있다([database/10](../../database/10-collation-and-text-comparison/2-summary.md) 장애 2).

### 10. 바이트 경계 탐색

- 이어지는 바이트가 `10xxxxxx`로만 생겼으므로, 임의 위치에서 뒤로 물러나며 시작 바이트를 찾을 수 있다(자기 동기화). 많아야 3바이트 물러난다.
- 이것으로 바이트 예산 자르기, 역방향 탐색, 스트림 중간에서 읽기 시작하기가 된다.

```java
static int charStart(byte[] b, int off) {
    while (off > 0 && (b[off] & 0xC0) == 0x80) off--;   // 10xxxxxx 이면 이어지는 바이트
    return off;
}
// "A가😀" = 41 EA B0 80 F0 9F 98 80 : off 2 → 1, off 6 → 4 (실험 7)
```
