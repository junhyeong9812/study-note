# architecture/02-integer-overflow-and-truncation — 정답

## 정답

### 1. 하드웨어가 버리는 것과 남기는 것

- w비트 덧셈기는 결과의 하위 w비트를 남기고 그 위 자리올림을 버린다(CS:APP 2.3.1·2.3.2).
- 버린 정보는 플래그로 남는다.
  - CF(Carry Flag): 무부호로 보면 넘쳤나. `setb`·`jc`로 읽는다.
  - OF(Overflow Flag): 2의 보수로 보면 넘쳤나. `seto`·`jo`로 읽는다.
- `0xFFFFFFFF + 1`
  - 무부호: 4294967295 + 1 → 0, CF = 1.
  - 부호 있음: −1 + 1 → 0, 정상이라 OF = 0.
  - 실험(`flags.c`): `same bits 0xFFFFFFFF + 1: as int overflow=0 (0), as unsigned carry=1 (0)`.

### 2. Java 값

(실험, OpenJDK 21.0.12)

```text
int 20억 + 3억 = -1994967296
(short) 70000 = 4464
(int) 40000.7 = 40000, (short) 40000.7 = -25536
(int) 1e10 = 2147483647
(short) 1e10 = -1
short s = 32767; s += 1 -> -32768
```

- `20억 + 3억`: 2,300,000,000 − 2³² = −1,994,967,296(JLS §15.18.2).
- `(short) 70000`: 하위 16비트 = 70000 − 65536 = 4464(JLS §5.1.3).
- `(short) 40000.7`: 1단계 `int` 40000(0 쪽 버림), 2단계 하위 16비트 → 40000 − 65536 = −25536.
- `(int) 1e10`: 범위 밖이라 `int` 최댓값으로 포화.
- `(short) 1e10`: 1단계 포화 2147483647(0x7FFFFFFF), 2단계 하위 16비트 0xFFFF → −1.
- `s += 1`: `s = (short)(s + 1)`과 같다(JLS §15.26.2). 32768을 `short`로 좁혀 −32768.

### 3. 늦은 넓히기와 248일

- 오른쪽 식의 피연산자가 모두 `int`라 곱셈이 `int`로 일어난다. 2,592,000,000,000은 `int`를 넘어 하위 32비트 2,134,720,512만 남는다. 그 **뒤에** `long`으로 넓혀 대입된다.
- 고치는 법: 첫 피연산자를 `long`으로 — `30L * 24 * ...` → 2,592,000,000,000(실험).
- 248일: 2³¹ / 100 / 86400 = 248.55일(실험 출력 `2^31 centiseconds = 248.55 days`).

### 4. 언어별 넘침 의미

| | 정수 넘침 | 범위 밖 부동소수 → 정수 |
|---|---|---|
| Java | 하위 비트로 감김, 알림 없음(JLS §4.2.2·§15.18.2) | `int`/`long`으로 포화 후 필요하면 하위 비트 절단(§5.1.3) |
| C | 부호 있는 넘침 = 미정의 동작(N1570 §6.5 ¶5), 무부호 = 2ʷ 모듈로(§6.2.5 ¶9) | 미정의 동작(§6.3.1.4 ¶1). x86-64 gcc `-O0` 실험에서 `cvttsd2si` → −2147483648(integer indefinite 0x80000000) |
| Python | 넘침 없음(임의 정밀도 정수) | — |
| Ada(Ariane 5 SRI) | — | 변환 중 Operand Error 예외, 보호되지 않은 변환이라 프로세서 정지(보고서) |

### 5. `x + 1 < x`의 운명

(실험, gcc 13.3.0)

- `-O0`: 0. `objdump`에서 함수 본문이 `mov $0x0,%eax`로 이미 접혀 있었다.
- `-O2`: 0. 본문이 `xor %eax,%eax; ret`.
- `-O2 -fsanitize=undefined`: `runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'`를 찍고 1을 돌려줬다.
- 이유: 부호 있는 넘침은 미정의 동작이다. 컴파일러는 넘침이 일어나지 않는다고 가정해 `x + 1 < x`를 상수 거짓(0)으로 바꿔도 된다. 넘침 검사를 넘침에 기대어 쓰면 검사가 사라진다.
- 바른 검사: `if (x > INT_MAX - 1)` 또는 `__builtin_add_overflow`.

### 6. Ariane 5 501편 원인 사슬

(조사 보고서 2.1·2.2절 요지)

1. 관성 기준 장치(SRI)의 정렬 함수가 이륙 뒤에도 약 40초 돌았다. Ariane 4 요구사항이고 Ariane 5에는 필요 없었다.
2. Ariane 5의 초기 궤적은 수평 속도가 훨씬 커서 수평 편향 BH가 예상보다 컸다.
3. BH를 64비트 부동소수에서 16비트 부호 있는 정수로 바꾸다 Operand Error가 났다. 이 변환은 보호되지 않았다.
4. 예외 시 명세대로 실패를 알리고 상태를 EEPROM에 저장하고 프로세서를 멈췄다. 예비 SRI 1은 이미 직전 데이터 주기(72ms)에 같은 이유로 멈춰 있었다.
5. 주 컴퓨터가 SRI 2의 진단 비트 패턴을 비행 데이터로 해석해 노즐을 크게 꺾었다. H0 + 39초에 공력 하중으로 분해됐다.

- 보호: 위험한 변수 7개 중 4개만 보호, 3개(BH 포함)는 "물리적 한계·큰 여유" 추론으로 남겼다. 이유로 SRI 컴퓨터 작업량 목표 80%가 언급됐다.
- 사고를 키운 것: 보고서는 "프로세서를 멈추기로 한 결정이 결국 치명적이었다"고 적는다. 해석하면 좁히기 + 재사용 환경에서 깨진 범위 가정 + "예외 = 정지" 설계가 겹쳤다.

### 7. `size_t` 언더플로와 곱 감김

- 원인 식: `size_t body = total - hdr;`에서 `total = 4`, `hdr = 8`. 무부호 뺄셈이라 2⁶⁴ − 4 = 18446744073709551612가 된다(실험).
- 고친 코드

```c
if (total < hdr) return -1;          /* 빼기 전에 비교 */
size_t body = total - hdr;
```

- 곱 감김: `uint32_t bytes = cnt * 4;`에서 `cnt = 1073741825`면 결과가 4바이트다(실험). 버퍼는 4바이트인데 원소 약 10.7억 개를 복사하므로 힙을 넘어 쓴다. `__builtin_mul_overflow`나 `calloc`·`reallocarray`(곱 넘침이면 오류 — `malloc(3)`)로 막는다.

### 8. Boeing 787 — 원문과 추정

- 원문(FAA AD 2015-09-07): 248일 연속 전원 공급 시 GCU 내부의 소프트웨어 카운터가 넘쳐 그 GCU가 failsafe 모드에 들어간다. 주 GCU 4대를 동시에 켰다면 4대가 동시에 들어가 교류 전원을 모두 잃을 수 있다. AD는 임시 조치로 120일을 넘지 않는 간격의 반복 전원 차단 정비를 요구했다.
- 추정(해석): 2³¹ / 100 / 86400 = 248.55일이므로 1/100초 틱을 부호 있는 32비트로 셌을 가능성. AD는 카운터 폭과 단위를 밝히지 않았다.
- 설계: 경과 시간은 64비트, 비교는 두 시각의 차(`now - start`)로. 시험: 카운터 초기값을 넘침 직전으로 두고 시간을 빠르게 흘리는 테스트.
