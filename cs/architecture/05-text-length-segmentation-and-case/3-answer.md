# architecture/05-text-length-segmentation-and-case — 정답

## 정답

### 1. 길이의 네 가지 뜻

| 단위 | 쓰는 곳 |
|---|---|
| 그래핌 클러스터 | 사람이 화면에서 세는 "글자". 닉네임 "10자" 안내 |
| 코드 포인트 | DB가 세는 "문자"(PostgreSQL·MySQL 문서는 "characters" — 코드 포인트로 추정 [?]) |
| UTF-16 코드 유닛 | Java `String.length()`, JS `length`, 인덱스 |
| UTF-8 바이트 | 저장·전송 한도(행 크기, 인덱스 키, 헤더, 메시지 크기) |

### 2. 네 개의 자 예측

| 문자열 | 그래핌 | 코드 포인트 | UTF-16 | UTF-8 |
|---|---|---|---|---|
| `👨‍👩‍👧` | 1 | 5 | 8 | 18 |
| `🇰🇷` | 1 | 2 | 4 | 8 |
| NFD `한글` | 2 | 6 | 6 | 18 |
| `e`+U+0301 | 1 | 2 | 2 | 3 |

- Java 21 `BreakIterator`와 정규식 `\X` 모두 같은 그래핌 수를 냈다(실험 1). ZWJ 연쇄는 GB11, 국기는 GB12/13, 결합 문자는 GB9, 한글 자모는 GB6~8로 한 칸이 된다(UAX #29 §3.1.1).

### 3. 국기 10개

- 그래핌 10, 코드 포인트 20, UTF-16 40, UTF-8 80바이트(실험 2).
- JS `length <= 10`: 실패(40). 코드 포인트 `<= 10`: 실패(20). 그래핌 `<= 10`: 통과.
- PostgreSQL `VARCHAR(10)`: 들어가지 않을 것으로 예측한다. 문서는 "n characters (not bytes)"라고만 쓰고, 이 "문자"가 코드 포인트라는 해석에 기댄다. 이 작업에서는 DB를 띄워 확인하지 않았다 [?].
- 그래서 "그래핌 10자" 안내를 하면서 DB를 `VARCHAR(10)`으로 두면 저장 단계에서 `value too long`이 난다.

### 4. 국기 짝짓기 상태 기계

```text
       RI 오면 ÷ (새 국기 시작)
  ┌────────┐ ─────────────> ┌────────┐
  │ 짝수개  │                │ 홀수개  │
  └────────┘ <───────────── └────────┘
       RI 오면 × (붙임, 국기 완성)
  🇰 → 홀수(새 시작) → 🇷 → 짝수(붙임) → 🇯 → 홀수(새 시작, ÷) → 🇵 → 짝수(붙임)
  결과 (🇰🇷)(🇯🇵)
```

- 규칙 GB12/13: 앞에 RI가 **홀수 개** 쌓여 있을 때만 다음 RI와 붙인다. 짝수 개 뒤의 RI는 새 국기의 시작이다. 그래서 `🇷` 뒤(짝수)의 `🇯`는 끊긴다.

### 5. 자르기 결과

- UTF-16 단위 3개: `🇰` + `D83C`(외톨이 상위 서로게이트). 인코딩하면 Java `?`, JS `EF BF BD`.
- 코드 포인트 3개: `🇰🇷🇯` — 마지막 국기가 반쪽(🇯만).
- 그래핌 3개: `🇰🇷🇯🇵🇺🇸` 전체(국기 3개).
- `가나다😀라`(16바이트)를 10바이트에서 그냥 자르면 `가나다`(9바이트) + `😀`의 첫 바이트 `F0` → 디코딩하면 `가나다�`. 그래핌 경계로 자르면 `가나다`(실험 3).

### 6. 터키어 로캘 enum 예외

- 메시지: `No enum constant Len05.Level.İNFO`(점 있는 대문자 İ, U+0130). `title`은 `TİTLE`(실험 4, `-Duser.language=tr -Duser.country=TR`).
- 인자 없는 `toUpperCase()`는 기본 로캘 규칙을 쓴다. 터키어에서 `i`의 대문자는 `İ`다(Java `String` 문서의 표와 API Note).
- 고치기: `s.toUpperCase(Locale.ROOT)`. 로캘과 무관한 식별자·키·enum 이름은 모두 `Locale.ROOT`.
- 미리 찾기: 테스트를 터키어 기본 로캘로 한 번 더 돌린다. 인자 없는 대소문자 변환 호출을 정적 분석으로 찾는다.

### 7. `equalsIgnoreCase`

- `"STRASSE".equalsIgnoreCase("straße")` → false. 길이가 다르고(7 대 6), 비교는 코드 포인트 하나씩 `Character.toLowerCase(Character.toUpperCase(c))`로 한다(`String` 문서). `ß` 한 글자가 `SS` 두 글자로 바뀌는 대응은 못 맞춘다. `"straße".toUpperCase(ROOT)`와 비교하면 true였다.
- `"TITLE".equalsIgnoreCase("tıtle")` → true. `ı`(U+0131)의 대문자는 `I`이므로 `toLowerCase(toUpperCase('ı'))` = `i` = `toLowerCase(toUpperCase('I'))`. 로캘은 보지 않는다.

### 8. Spotify 사고(2013년 공개)

```text
  가입         canon("ᴮᴵᴳᴮᴵᴿᴰ") = "BIGBIRD" → "bigbird"와 안 겹침 → 계정 생성(공격자 메일)
  재설정 요청   canon("ᴮᴵᴳᴮᴵᴿᴰ") = "BIGBIRD" → 공격자 계정 메일로 링크 발송
  링크 사용    canon("BIGBIRD")  = "bigbird" → 피해자 계정의 비밀번호 변경
```

- `bigbird`는 설명용 예시 이름이다. 원문은 이 계정이 실제 피해 계정이 아니었다고 밝힌다. 실제 신고에서는 포럼 관리자 계정이 탈취됐다. 사고는 2013년 글보다 몇 년 앞서 일어났다(원문).
- 근본 원인: 정규화 함수(Twisted의 XMPP nodeprep)가 멱등이 아니었다. 경로마다 적용 횟수가 달라 같은 사용자명이 다른 키가 됐다. nodeprep은 Unicode 3.2 입력을 전제했는데 입력 검사를 하지 않았고, Python 2.4 → 2.5의 `unicodedata` 변경 뒤 3.2 밖 문자에서 예외 대신 틀린 결과를 냈다(원문).
- 대처: 즉시 `X == canonical_username(X)`인 이름만 가입 허용. 이어서 `prepare(prepare(name)) != prepare(name)`이면 거부하는 래퍼. 잘못된 정규 이름을 가진 계정을 찾아 피해 계정을 확인했다. Twisted는 11.0.0에서 고쳐졌다(원문).

### 9. 정규화 순서와 멱등성

- `NFKC(lower(x))`가 멱등이 아니다. `ᴮ`(U+1D2E)는 소문자 짝이 없어 `lower`가 그대로 두고, NFKC가 `B`로 바꾼다. 결과에 대문자가 남는다.
  - 한 번: `BIGBIRD`, 두 번: `bigbird`.
- `lower(NFKC(x))`: 한 번 `bigbird`, 두 번 `bigbird`.
- 전 코드 포인트 검사(Java 21, Unicode 15.0): `NFKC(lower(x))` 멱등 아님 629개(예: U+03D2 ϒ → Υ → υ), `lower(NFKC(x))` 0개(실험 5). 판이 바뀌면 다시 검사한다.

### 10. 혼동 문자

- 이 예는 합쳐지지 않는다(정준 동등인 옴 기호 U+2126 같은 일부만 정규화로 합쳐진다). `а`(U+0430)는 라틴 `a`의 다른 표현이 아니라 다른 스크립트의 다른 글자다. NFKC 뒤·소문자화 뒤 모두 `equals` false(실험 6).
- 막기: UTS #39 — skeleton으로 기존 이름과 혼동되는지 검사(§4), 혼합 스크립트·제한 수준 검사(§5.1·§5.2)로 라틴+키릴 조합 거부.
- 단순 규칙의 문제: `한글abc`처럼 정상 조합도 "혼합"으로 걸린다(실험 6). UTS #39 §5.2의 "Highly Restrictive"는 라틴+한자+한글(Latn + Kore)을 허용하고, 라틴과 키릴·그리스의 조합은 "Moderately Restrictive"에서도 빠진다. 허용 조합을 정책으로 정해야 한다.
