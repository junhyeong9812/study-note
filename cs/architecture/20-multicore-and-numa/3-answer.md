# architecture/20-multicore-and-numa — 정답

## 정답

### 1. 토폴로지 읽기

- 같은 `CORE` 번호 = SMT 형제(이 호스트: CPU0·1이 코어0, … CPU14·15가 코어7). `/sys/devices/system/cpu/cpu0/topology/thread_siblings_list` = `0-1`.
- `MAXMHZ`(4800·5000 vs 3700)와 `/sys/devices/cpu_core/cpus`(0-15)·`cpu_atom/cpus`(16-23)로 P/E를 가른다.
- `CACHE` 열의 L2 번호가 같으면 L2 공유: CPU16~19가 L2 8번, 20~23이 9번(2MiB). P코어는 코어마다 L2 1.25MiB.

```text
  노드 0 (메모리 전부)
  P코어 ×8: [0,1] [2,3] ... [14,15]   각 L1d 48K · L2 1.25M
  E코어 ×8: [16][17][18][19] | [20][21][22][23]   각 L1d 32K, L2 2M를 4개가 공유
  L3 30M: 0~23 공유
```

### 2. SMT가 나누는 것

- 따로: 레지스터 상태(아키텍처 상태). 같이: 디코더·스케줄러·실행 유닛·L1·L2.
- Drepper §3.3.4: 이득은 한 스레드가 지연될 때(대개 메모리 접근) 다른 스레드가 ALU 같은 자원을 쓰는 데서 나온다. 대신 두 스레드가 같은 캐시를 써 각자의 실효 캐시 크기가 반으로 준다고 본다(작업 집합이 겹치지 않을 때의 모형 — 고정 배분은 아니다). 단일 스레드의 적중률이 이미 높으면(예: 95%) 반쪽 캐시로 필요한 적중률(예: 80%)을 맞추기 어렵다. 그래서 "제한된 상황에서만 쓸모 있다"고 정리한다.

### 3. SMT 형제 실측

- wide: 혼자 426~469 → 형제 둘 각 200~223 Mops/s(약 절반). 합 403~442로 코어 하나 몫.
- chain: 혼자 138~149 → 형제 둘 각 134~150. 거의 그대로, 합은 약 2배.
- 해석(perf 없이 시간으로만 잼): 실행 유닛이 병목인 일은 나눠 쓰고, 기다림이 병목인 일은 빈 유닛을 서로 채운다. 측정으로 확인한 것은 두 일의 처리량 차이까지다.

### 4. P vs E 포인터 따라가기

- P코어(CPU4) 199~208ns, E코어(CPU20) 248~256ns. E가 약 40~57ns 길다(3회 범위 끝끼리). 점검 재실행 한 회차는 225 대 239ns로 14ns뿐이었다. 방향은 같지만 크기는 부하에 흔들린다.
- 해석: 클록·L2 구조·코어 설계 차이. perf 카운터 없이 시간으로만 잰 값이다.

### 5. 노드 거리

- 펌웨어(ACPI SLIT)가 주는 상대 비용 표다. 자기 노드를 10으로 둔다. 21은 "더 멀다"는 상대값이다.
- 실제 지연 비가 2.1이라는 뜻은 아니다. 플랫폼마다 측정과 다를 수 있어 실측으로 확인한다 `[?]`.
- 이 호스트는 `available: 1 nodes (0)`, 거리 표가 `10` 하나다. 원격 노드가 없으니 원격 접근이 생기지 않는다. `numastat`의 `numa_miss`·`other_node`도 0이다.

### 6. first touch

- 기본 정책은 할당하는 CPU의 노드에서 먼저 준다(kernel docs `numa_memory_policy`). 큰 배열을 스레드 하나가 초기화하면 대부분 그 스레드 노드에 놓인다(그 노드 메모리가 모자라면 다른 노드로 넘어간다 — kernel docs `mm/numa`). 그러면 다른 노드 스레드들의 접근은 원격이 되기 쉽다. 메모리 정책·`numa_balancing`이 배치를 바꿀 수 있다.
- `numa_balancing`: 커널이 페이지를 주기적으로 언매핑해 폴트로 누가 접근하는지 표본을 뜨고, 자주 쓰는 노드로 페이지를 옮긴다(kernel docs `sysctl/kernel`). 옮기는 비용이 있다. 이 호스트는 0(꺼짐).

### 7. 스레드 과다 실측 (`--cpuset-cpus=4,6`)

- 독립: 1개 65,949~70,790 → 2개 138,013~139,915 → 4·8·32개 138,984~146,105. 2개에서 거의 포화(8개가 2개보다 약 3~6% 높았다 — 작은 증가는 있었다). 최악 지연은 32개에서 65~97ms.
- 락: 2개 96,535~105,211이 최고 → 8·32개 64,138~79,457. 같은 회차 2개 대비 약 7~39% 감소. 최악 지연 60~125ms.
- 이유: 처리량 상한 = 일할 수 있는 CPU 몫(여기서는 2개). 락 보유자가 선점되면 나머지가 다 멈추고, 깨어남·문맥 전환 비용이 쌓이는 것이 가능한 설명이다(선점 자체는 재지 않았다).

### 8. NUMA 의심 진단

- 볼 것: `numactl -H`(노드 수·CPU·빈 메모리), `numastat`·`numastat -p <pid>`(노드별 메모리), `/proc/<pid>/numa_maps`(매핑별 `N0=`·`N1=`), `ps -eLo tid,psr`(스레드가 도는 CPU→노드), `/proc/sys/kernel/numa_balancing`.
- 대처: `numactl --cpunodebind=N --membind=N`으로 묶기(힙이 노드 메모리보다 작을 때), 노드당 인스턴스 하나로 쪼개기, `--interleave=all`로 평균화, JVM `-XX:+UseNUMA` 검토, 쓰는 스레드가 자기 데이터를 초기화.

### 9. 풀 확대 후 처리량 하락

- 볼 것: `vmstat 1`의 `r`(실행 대기)·`cs`(문맥 전환), `availableProcessors()`·cgroup 쿼터, 스레드 덤프(`jcmd <pid> Thread.print`)의 같은 락 대기, CPU 사용률이 이미 코어 수만큼인지.
- 고침: 계산 풀은 코어 수 근처로 되돌린다. 경합 지점 축소(락 구간 줄이기, `LongAdder`·샤딩). 대기 작업은 별도 풀·가상 스레드로 분리하되 공유 자원(DB 커넥션 등) 수로 상한.

### 10. 하이브리드 벤치마크 주의

- 같은 일이 P코어와 E코어에서 다르다: 이 노트 chain 약 18~30%, 포인터 따라가기 대개 약 40~57ns 차이. 15번에서는 NVMe 읽기 평균 지연이 E코어 제출 시 약 8~18µs 길었다.
- 스케줄러가 어디에 놓느냐에 따라 결과가 두 무리로 갈린다. 벤치마크는 `taskset`으로 코어 종류를 고정하고, 운영 CPU가 한 종류 코어만 두면 노트북 수치의 분산을 그대로 옮기지 않는다.
