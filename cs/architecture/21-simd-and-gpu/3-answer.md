# architecture/21-simd-and-gpu — 정답

## 정답

### 1. ymm 레지스터

- 256비트 = `int` 8개, `float` 8개, `double` 4개.

```text
  ymm1: | b0 | b1 | b2 | b3 | b4 | b5 | b6 | b7 |
  ymm2: | c0 | c1 | c2 | c3 | c4 | c5 | c6 | c7 |
          +    +    +    +    +    +    +    +       ← 칸끼리만 더함
  ymm0: |b0+c0|b1+c1| ...                 |b7+c7|
```

### 2. 벡터화 조건

- 쉬움: 연속 메모리 순차 접근, 반복 사이 의존 없음(또는 정수 축약), 포인터 겹침 없음(`restrict`), 분기를 양쪽 계산 + 선택으로 바꿀 수 있음, 루프 안 함수 호출 없음.
- 어려움: 포인터 따라가기, 앞 반복 결과를 쓰는 의존, 순서를 바꿔야 하는 부동소수 축약, 루프 안 호출·조기 탈출, 흩어진 인덱스 접근.
- GCC 13.3: `-O2`도 루프 벡터화를 켜지만 비용 모형이 `very-cheap`(남는 반복 처리가 필요 없을 때만), `-O3`는 `dynamic`. 실험에서 `-O2`는 반복 수가 상수인 초기화 루프만, `-O3`는 `add`·`branchy`·`isum`까지 바꿨다.

### 3. L1 vs 64MiB

- L1(16KiB): 1.06~1.09 → 0.21~0.28ns, 약 4~5배.
- 64MiB: 1.77~2.03 → 1.53~1.56ns, 약 1.1~1.3배.
- 큰 배열(배열당 64MiB × 3)은 메모리 쪽(대역폭·지연)이 병목이라고 해석한다. 계산을 8칸씩 해도 load를 기다리는 시간은 그대로다. 측정으로 확인한 것은 "이 실험에서 이득이 작았다"까지다(perf 불가).

### 4. float 합

- `-O3 -march=native`: 2.16~2.17ns로 그대로. `-fopt-info-vec`은 "vectorized"라고 했지만 기계어는 `vaddss`(메모리에서 한 칸을 읽어 더함) 8개를 순서대로 한 레지스터에 더한다. 보고 위치는 fsum 루프(`simd.c:16:36`)다. 순서를 지킨 것이다.
- `-ffast-math`: 0.24~0.25ns(약 9배). 기계어가 `vaddps ymm`(8칸)으로 바뀌고 끝에 칸을 합친다. 결과가 2.919377e+05 → 2.919381e+05로 바뀌었다.
- 구분: `vaddss`/`vaddsd`는 스칼라, `vaddps`/`vaddpd`는 packed(여러 칸).

### 5. Java SuperWord

- 실측(JDK 21.0.12, `--cpuset-cpus=4`): `add` 0.369~0.373 → 끄면 1.666~1.859(약 4.5~5배 느림), `isum` 0.295~0.307 → 1.095~1.131(약 3.6~3.8배), `fsum` 2.148~2.181 → 2.192~2.411(거의 같음).
- JLS §15.7.3: Java 구현은 결합법칙 같은 대수 항등식으로 식을 바꿔 쓸 수 없다(값이 같다고 증명될 때만 예외). `float` 합을 칸별 부분합으로 바꾸면 값이 달라질 수 있으니 JIT이 하지 않는다. 정수 합은 순서를 바꿔도 값이 같아 벡터화된다.

### 6. 분기의 마스크 처리

```text
  x>0 ?  [1][0][1][1][0][0][1][0]   ← vpcmpgtd로 마스크
  A를 8칸 전부 계산, B를 8칸 전부 계산
  vpblendvb: 마스크가 1인 칸은 A, 0인 칸은 B
```

- 비용은 데이터와 무관하게 A + B다. 8칸이 다 A여도 B를 계산한다.

### 7. 무거운 분기 실측

- 스칼라: 전부 양수 7.80~7.94ns, 무작위 20.31~21.49ns. 이 빌드에는 조건 분기(`jle`)가 있어, 무작위 입력의 느려짐은 분기 예측 실패와 부합한다(해석 — 오예측 횟수는 재지 못했다).
- 벡터: 전부 양수 2.68~2.95ns, 무작위 2.73~2.79ns. 데이터와 무관하다. 양쪽 갈래를 다 계산하기 때문이다(전부 양수여도 B를 계산해 일을 2배 한다).

### 8. 워프와 coalescing

- 워프 = 스레드 32개가 같은 명령을 함께 실행하는 묶음. 일부 스레드만 갈래를 타면 나머지는 마스크로 꺼진 채 기다리고, 갈래들을 차례로 실행한다. 이를 warp divergence라 한다(CUDA 가이드 §1.2.2.2). 꺼진 레인만큼 일을 버리는 점은 CPU SIMD의 "양쪽 계산 + blend"와 닮았다. 다만 워프 안 스레드가 모두 같은 갈래를 타면 다른 갈래는 실행하지 않는다. 이 CPU 벡터 판은 입력과 무관하게 양쪽을 다 계산했다.
- coalescing: 워프의 메모리 요청을 32바이트 트랜잭션으로 묶는다. 연속 4바이트 접근이고 시작 주소가 32바이트 경계에 맞으면 128바이트를 트랜잭션 4개로 100% 쓴다(어긋나면 5개). 스레드마다 32바이트 이상 떨어지면 1,024바이트를 가져와 128바이트만 쓴다 → 12.5%(가이드 §2.3.4.1).

### 9. `Illegal instruction`

- 원인: `-march=native`가 빌드 CPU의 명령(AVX2·AVX-512 등)을 넣었다. 그 명령이 없는 CPU가 실행하면 #UD → SIGILL, 종료 코드 132.
- 대처: 운영 CPU의 최소 공통 수준으로 빌드(`-march=x86-64-v2/v3` 등 — v3은 AVX2·FMA 포함, gcc 13.3 `-dM -E`로 확인), 실행 시 CPU 기능 검사로 경로 선택, 배포 전에 `/proc/cpuinfo` 플래그 확인. JVM은 실행 시 CPU를 보고 JIT이 명령을 고른다.

### 10. 분기 많은 GPU 코드

- 원인: 원소마다 갈래가 달라 워프 안에서 갈래들을 차례로 실행한다. 꺼진 레인만큼 일을 버린다. 흩어진 메모리 접근이면 coalescing도 깨진다.
- 대처: 같은 경로를 탈 원소끼리 정렬·버킷으로 모은다, 분기를 산술 선택으로 바꾼다, 데이터를 SoA로 바꿔 연속 접근을 만든다, 경로가 너무 다양하면 CPU에 남긴다.
