# architecture/11-memory-hierarchy-and-locality — 정답

## 정답

### 1. 계층이 없으면

- 이 호스트에서 256MB 무작위 포인터 사슬의 접근 1회는 약 170~195사이클(약 200ns, 클록 0.8~0.9GHz 상태)이었다. DRAM 지연에 TLB 미스 등이 섞인 값이다. 모든 읽기가 이만큼 기다리면 CPU는 대부분 논다.
- 계층은 작고 빠른 층에 "곧 쓸 데이터"를 둔다. 이것이 통하려면 프로그램이 **지역성**을 가져야 한다. 최근 쓴 것을 또 쓰거나(시간), 근처를 곧 쓴다(공간).

### 2. 한 줄 위의 지역성

```text
  for (int i = 0; i < n; i++) sum += a[i];
                              ───    ────
                              시간    공간: a[i], a[i+1], ... 연속 주소
                              (sum·i를 매 반복 다시 씀)
```

- 64B 라인 ÷ 4B `int` = 한 라인에 최대 16원소. 배열이 라인 경계에 맞으면 미스 한 번이 16원소를 데려오고 나머지 15번은 히트다. 안 맞으면 첫·끝 라인의 원소 수만 줄고, 긴 순회에서는 여전히 약 16원소당 미스 1번이다.

### 3. 작업 집합 사다리

- P코어(cpu2, L1d 48KB·L2 1.25MB): 16~40KB 약 5사이클 → 64KB에서 약 15사이클로 꺾임(L2) → 2MB에서 약 62~69사이클(L2 초과) → 8MB 이후 145~195사이클.
- E코어(cpu18, L1d 32KB): 32KB까지 약 3사이클, **40KB에서 이미 약 20사이클**. 같은 40KB가 P코어에서는 L1 히트, E코어에서는 L1 미스였다.
- 1MB 이후에는 TLB 미스가 섞인다는 해석이다(4KB 페이지).

### 4. 같은 256MB, 순차 사슬

- 약 8사이클(9.7ns)이었다. 무작위 사슬(약 182~195사이클)의 20분의 1 남짓.
- 주소가 일정 간격으로 늘면 하드웨어 프리페처가 다음 라인을 미리 가져온다. 데이터는 DRAM에 있어도 지연이 숨는다. 순차·간격 프리페처는 무작위 포인터 사슬을 예측하기 어렵다.

### 5. 행·열 차이가 생기는 조건

- **행렬이 캐시에 다 들어가지 않을 때** 차이가 난다. 다 들어가면(N=64, 16KB) 열 방향으로 건너뛰어도 라인이 캐시에 남아 있어 비 0.9~1.4배였다.
- 덧붙여 행 길이가 2의 거듭제곱이면(N=1024: 9~10배 vs N=1000: 2.3~2.5배) 충돌 미스가 더해진다 — 12번.

### 6. Java 네 배치

- 빠른 순서: `int[]` 0.48~0.51ns → 할당 순서 `ArrayList<Integer>` 5.6~6.2ns(약 10~12배) → 섞은 `ArrayList<Integer>` 17.2~20.3ns(약 35~40배) → `LinkedList` 41.5~43.3ns.
- 할당 순서는 객체가 힙에 차례로 놓였을 가능성이 높아(주소는 확인 안 함 — 해석) 대체로 순차라 덜 나쁘다. 섞으면 같은 객체를 흩어진 순서로 간접 참조해 라인마다 미스가 난다. `LinkedList`는 다음 주소가 노드 안에 있는 의존 사슬이라 더 느리다.

### 7. 빅오 표가 놓치는 것

- 두 구조 모두 순회는 O(n)이지만 원소당 상수가 다르다. 배열은 연속이라 라인당 여러 원소·프리페치를 얻고, 연결 리스트는 노드마다 의존 읽기다.
- 연결 리스트가 맞는 경우: 이미 노드 위치를 쥔 채 중간 삽입·삭제가 대부분이고 순회가 드물 때(LRU의 이중 연결 리스트처럼 해시맵이 노드를 직접 가리키는 경우).

### 8. 10배 데이터, 30배 시간

1. 원소당 처리 시간을 데이터 크기별로 잰다. 어떤 크기에서 계단처럼 뛰는지 본다.
2. 그 크기를 `lscpu -C`의 L2·L3 크기와 비교한다. 작업 집합이 L3(이 호스트 30MB)를 넘는 지점이면 메모리 계층 문제를 의심한다. 확정은 LLC 미스 카운터(perf 등)로 한다.
3. 핫 루프의 데이터 모양을 본다. `jcmd <pid> GC.class_histogram`에 `Long`·`HashMap$Node`가 수백만이면 박싱·간접 참조(`HashMap` 체인·연결 리스트면 포인터 추적)를 의심한다.
4. 원시 배열로 바꾸고, 키 정렬 후 순차 처리로 무작위 접근을 없앤다.

### 9. `getconf` 값

- 안 된다. 이 호스트에서 `taskset -c 2 getconf LEVEL1_DCACHE_SIZE`는 49152, `taskset -c 18 ...`은 32768이었다. 돌린 코어의 값이다.
- 하이브리드 CPU는 코어 종류마다 L1·L2가 다르다. `/sys/devices/system/cpu/cpu*/cache/`를 코어별로 읽는다.

### 10. 세 캐시

- 같은 점: 작고 빠른 층에 곧 쓸 것을 두고, 지역성 가정 위에 서며, 꽉 차면 교체 정책으로 내보낸다.
- 다른 점: 단위(64B 라인 vs 4KB 페이지 vs DB 페이지), 관리자(하드웨어 회로 vs 커널 vs DB 엔진), 교체 정책을 누가 고칠 수 있나(CPU 캐시는 못 고침, 버퍼 풀은 설정·설계로 조정).
