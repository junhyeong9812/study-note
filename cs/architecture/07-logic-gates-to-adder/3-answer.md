# architecture/07-logic-gates-to-adder — 정답

## 정답

### 1. 캐리가 속도 문제인 이유

```text
  손:   0 9 9 9 + 0 0 0 1  → 일의 자리 받아올림이 천의 자리까지 차례로 번진다
  회로: FA0 → c1 → FA1 → c2 → … → FA15 → cout
        캐리 하나가 지나갈 때마다 AND + OR 2단씩 늦어진다
```

- 윗비트의 합은 아래에서 올라오는 캐리가 확정돼야 확정된다. 리플 캐리 가산기의 최장 지연은 비트 수 n에 비례한다(16비트 33단, 실험 3).
- 이 최장 지연이 클록 주기의 하한이 된다.

### 2. NAND로 다른 게이트

```text
  NOT a = NAND(a, a)
  AND   = NAND(n, n),  n = NAND(a, b)
  OR    = NAND(NAND(a,a), NAND(b,b)) = NAND(¬a, ¬b) = a ∨ b     ← 드모르간: ¬(¬a ∧ ¬b) = a ∨ b
  XOR   = NAND(NAND(a, n), NAND(b, n))   (게이트 4개, 깊이 3)
```

- 실험 1의 진리표로 네 게이트가 모두 맞음을 확인했다.

### 3. 반가산기·전가산기

- 반가산기: `s = a XOR b`, `c = a AND b`.
- 전가산기: 반가산기 2개 + OR. `p = a ⊕ b`, `s = p ⊕ cin`, `cout = (a·b) + (p·cin)`.
- `1 + 1 + 1` = `11`(cout 1, s 1). 실험 2 진리표.

### 4. 입력별 안정 시각(16비트 리플, 단위 지연)

| 입력 | 출력 마지막 변화 시각 |
|---|---|
| `0x0001 + 0x0001` | 3 |
| `0x7FFF + 0x0001` | 31 |
| `0xFFFF + 0x0001` | 32 |
| `0x5555 + 0xAAAA` | 2 |

- `0x5555 + 0xAAAA`는 모든 자리에서 `a⊕b = 1`, `a·b = 0`이다. 캐리가 생기지 않으므로 XOR 두 단(합)만 지나면 끝난다.
- `0xFFFF + 1`은 캐리가 16비트 끝까지 번진다. 실험 5에서 2단마다 합 비트가 하나씩 0으로 바뀌며 올라가고 t=32에 cout이 1이 됐다.

### 5. 생성·전달과 룩어헤드

- `g_i = a_i·b_i`: 이 자리가 스스로 캐리를 만든다. `p_i = a_i ⊕ b_i`: 들어온 캐리를 위로 넘긴다.
- 높은 구간 H와 낮은 구간 L을 합치면: H가 스스로 만들거나(G_H), H가 넘기는데 L이 만들면(P_H·G_L) 캐리가 나온다. 둘 다 넘기면 전체가 넘긴다(P_H·P_L).
- 이 합치기는 결합 법칙을 만족한다. 그래서 누적합처럼 구간 길이를 1→2→4→… 로 두 배씩 늘려 log2(n) 단계에 모든 비트의 캐리를 얻는다(병렬 프리픽스).
- 실험 3: 깊이 16비트 11단, 64비트 15단(2·log2 n + 3). 대가는 게이트 수 — 64비트에서 1157개로 리플 320개의 약 3.6배.

### 6. 뺄셈

- `a − b = a + (NOT b) + 1`. `b`를 XOR로 뒤집고 캐리 입력에 1을 넣는다.
- `3 − 5` → `0xFFFE` = 65534, `short`로 읽으면 −2(실험 7).

### 7. 플래그와 명령

- 부호 있는 판: `add %esi,%edi` 뒤 `seto %al`(OF = V). 무부호 판: 같은 `add` 뒤 `setb %al`(CF = C)(실험 8, gcc 13.3 `-O2`).
- `0xFFFFFFFF + 1`: 부호 있게 읽으면 `−1 + 1 = 0`, V = 0. 무부호로 읽으면 `4294967295 + 1`이 넘쳐 C = 1. 결과 비트는 둘 다 0이다.
- V는 "최상위로 들어간 캐리 XOR 나간 캐리"다. 실험 6에서 이 식이 Java `(short)` 오버플로 판정과 무작위 10만 쌍 모두 일치했다.

### 8. 오버클럭과 간헐 오류

- 클록 주기는 `t_clk→Q + 조합 회로 최장 지연 + t_setup`보다 길어야 한다. 오버클럭으로 주기가 이보다 짧아지면, 다음 에지에서 레지스터가 올바른 값을 잡는다는 보장이 없다. 이전 값이나 가산기의 **중간값**을 잡을 수 있고, 에지 근처에서 입력이 바뀌면 메타안정에 빠질 수도 있다.
- 지연은 입력에 따라 다르다. 캐리가 멀리 번지는 입력(예: `0x7F…F + 1`)에서만 최장 경로를 타므로, 그런 입력에서만 틀린다. 08 실험 3(8비트 카운터)에서 주기를 16 단위 이하로 줄이자 12 단위에서 256클록 중 10번, 8 단위에서 46번 틀렸고, 주기 12에서 처음 틀린 것은 62 다음에 127을 잡은 때였다 — 입력이 61→62로 바뀌며 남은 캐리 펄스(글리치)가 위로 번지는 도중에 잡혔다(시뮬레이션, 08 실험 3).

### 9. Meta 2021 조용한 데이터 손상

- 증상: Spark 압축 해제 파이프라인에서 파일 크기 계산이 가끔 0을 돌려줘 파일이 결과 DB에 쓰이지 않았고, 결국 데이터 손실로 보고됐다. 시스템·커널 로그는 깨끗했다.
- 좁히기: 모든 단계에 로깅을 켜 호스트를 찾고, 단일 머신 → 단일 스레드로 줄이자 한 코어(Core 59)에서 특정 값(`Int(1.1^53)` = 0, `Int(1.1^52)` = 142는 정상)에 대해 일관되게 틀렸다. `taskset -c 59`로 코어를 고정해 재현했다.
- 원문의 결함 범주(§3): 장치 오류(설계 코너 케이스, **신호 도착 시각 불확실성으로 인한 타이밍 경로 오류**, 제조 편차), 초기 고장, 사용에 따른 열화, 수명 말기 마모. 타이밍 경로 오류가 이 노트의 "최악 경로가 주기를 넘는" 모델과 같은 범주다(이 사례의 정확한 원인 회로는 원문 범위 밖 — 해석).

### 10. `BigInteger.add`

- OpenJDK 21 `BigInteger.add(int[] x, int[] y)`는 32비트 조각을 낮은 쪽부터 더하고, `sum >>> 32`(넘친 캐리)를 다음 조각 덧셈에 더한다. 리플 캐리 가산기의 비트 대신 32비트 조각을 단위로 쓴 것이다. 남은 조각도 캐리가 있는 동안 계속 1을 더한다.
- 불변식: "k번째 조각까지 처리한 뒤, 결과의 하위 k조각과 carry는 두 수 하위 k조각의 합을 정확히 나타낸다(합 = 결과 + carry·2^(32k))". k=0에서 참이고, 한 조각을 더할 때 유지되므로 끝에서 전체 합이 맞다(귀납 — [math/02](../../math/02-induction-and-invariants/2-summary.md)).
