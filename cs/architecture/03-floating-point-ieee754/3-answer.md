# architecture/03-floating-point-ieee754 — 정답

## 정답

### 1. binary64 필드

```text
  ┌─┬───────────┬──────────────────────────────┐
  │s│   e (11)  │            f (52)            │
  └─┴───────────┴──────────────────────────────┘
  값 = (−1)ˢ × 1.f₂ × 2^(e − 1023)     (정규수, 1 ≤ e ≤ 2046)
```

- 정규수는 맨 앞자리가 1로 정해져 있어 저장하지 않는다(숨은 비트). 저장 52비트 + 숨은 1비트 = 유효숫자 53비트(Goldberg 1991, JLS §4.2.3 표 N = 53).

### 2. 0.1의 비트

(실험, `Double.doubleToRawLongBits`)

```text
0.1  0x3FB999999999999A  s=0 e=01111111011(1019) f=100110011001...
```

- 부호 0(양수). 지수 저장값 1019, 실제 지수 1019 − 1023 = −4. 가수 `1001 1001 …` → 값 ≈ 1.6 × 2⁻⁴ = 0.1.
- 0.1의 2진 전개는 `1.1001 1001 1001 …₂ × 2⁻⁴`로 끝없이 반복된다. 52비트에서 자를 때 버리는 부분이 절반보다 커서 반올림으로 올림이 일어났다. 그래서 끝이 `…1001 1010`(16진 끝자리 `A`)이다. 저장값은 0.1보다 조금 크다(`new BigDecimal(0.1)` = 0.1000000000000000055511151231257827021181583404541015625).

### 3. 지수 칸의 끝값

| e | f = 0 | f ≠ 0 |
|---|---|---|
| 전부 0 | ±0 | 비정규수 |
| 전부 1 | ±무한대 | NaN |

(실험)

```text
4.9E-324   0x0000000000000001   ← Double.MIN_VALUE, 가장 작은 비정규수
Infinity   0x7FF0000000000000
NaN        0x7FF8000000000000   ← Java Double.NaN (NaN 패턴은 여럿)
```

### 4. ε 경계

(실험, OpenJDK 21.0.12)

```text
1 + 2^-53 == 1 ? true
1 + nextUp(2^-53) == 1 ? false, 값 = 1.0000000000000002, x = 1.1102230246251568E-16
```

- 1 + 2⁻⁵³은 1과 1 + 2⁻⁵²의 정확히 가운데다. 동률은 끝 비트 0 쪽(1.0)으로 간다(JLS §15.4 round to nearest).
- 2⁻⁵³ 바로 위의 값은 위쪽이 더 가까워 1 + 2⁻⁵²로 올라간다.
- 그래서 "1.0 + x ≠ 1.0인 가장 작은 x"는 약 1.11×10⁻¹⁶(2⁻⁵³ 바로 위)이고, 기계 엡실론 2⁻⁵² ≈ 2.22×10⁻¹⁶이 아니다. 엡실론의 바른 정의는 "1.0과 다음 표현 가능한 수의 간격"이다(원고 §2.2 98행의 정의는 이 점에서 틀리다).

### 5. 비교 결과

(실험)

```text
NaN == NaN ? false
Double.compare(NaN, NaN) = 0
0.0 == -0.0 ? true
Double.valueOf(0.0).equals(-0.0) = false
Math.min(0.0,-0.0) = -0.0
0.1f+0.2f == 0.3f ? true
```

- `==`는 IEEE 수치 비교: NaN은 무순서, ±0은 같다(JLS §4.2.3).
- `compare`·`equals`는 표현 기준 전체 순서: NaN끼리 같고 −0.0 < +0.0(`Double` Javadoc).
- `Math.min`은 −0.0을 더 작게 본다(JLS §15.20.1).
- `float`에서는 세 값의 반올림이 맞아떨어져 같다. "0.1+0.2≠0.3"은 `double`에서의 사실이다.

### 6. NaN과 손 비교자

(실험)

```text
손 비교자 정렬   = [3.0, NaN, 1.0, 2.0, NaN, 0.5, 4.0]
Double::compare = [0.5, 1.0, 2.0, 3.0, 4.0, NaN, NaN]
손 비교자 TreeSet(1,NaN,2,3) = [1.0, 2.0, 3.0]  size=3
```

- 손 비교자는 NaN과 무엇을 비교해도 `<`·`>`가 모두 거짓이라 0("같다")을 돌려준다. 그러면 3.0 = NaN = 1.0이 되어 추이성이 깨진다. 정렬은 입력 순서를 그대로 두었다.
- `TreeSet`은 비교 결과 0을 "이미 있음"으로 본다. NaN을 넣을 때 루트(1.0)와 "같다"는 답을 받아 넣지 않았다. 원소가 조용히 사라졌다.
- 고치는 법: `list.sort(Double::compare)`, `new TreeSet<>()`(자연 순서) 또는 `Comparator.comparingDouble(...)`. 근본적으로는 NaN이 생긴 경계(0/0, 빈 집합 평균)를 막는다.

### 7. 4.35달러와 434센트

(실험)

```text
new BigDecimal(4.35) = 4.3499999999999996447286321199499070644378662109375
4.35*100 = 434.99999999999994, (long)(4.35*100) = 434, Math.round = 435
BigDecimal 2.675 HALF_UP 2자리 = 2.68, new BigDecimal(2.675) HALF_UP = 2.67
```

- 4.35는 4.3499…로 저장된다. 100을 곱한 결과도 435보다 작고, `(long)`은 0 쪽으로 버리므로 434다(JLS §5.1.3).
- `double`을 거치지 않는 코드

```java
long cents = new BigDecimal("4.35").movePointRight(2).longValueExact();   // 435
```

- `new BigDecimal(2.675)`는 2.67499…를 정확히 담으므로 HALF_UP이어도 2.67이다. 문자열 `"2.675"`에서 만들면 2.68.

### 8. 반올림 모드와 플래그 — 표준 vs 구현

- IEEE 754(Goldberg 1991의 설명): 기본 round to nearest 외에 0 쪽·+∞ 쪽·−∞ 쪽 반올림을 제공해야 하고, 예외가 나면 끈적한 상태 플래그를 세우며 사용자가 읽고 쓸 수 있어야 한다.
- C: `<fenv.h>`의 `fesetround`·`fetestexcept`로 노출한다.
- Java: JLS §15.4는 반올림 정책 두 가지(산술 round to nearest, 정수 변환·나머지 round toward zero)만 정의한다. 모드를 바꾸거나 플래그를 읽는 언어 수단은 JLS 4·15장에서 찾지 못했다.
- 실험(`fenv.c`, gcc 13.3 `-O0`)

```text
TONEAREST  0.1+0.2 = 0.30000000000000004
UPWARD     0.1+0.2 = 0.30000000000000005
DOWNWARD   0.1+0.2 = 0.29999999999999998
TOWARDZERO 0.1+0.2 = 0.29999999999999998
after 0.1+0.2: FE_INEXACT=1
```

- 십진 출력 차이가 곧 덧셈 비트 차이는 아니다. 비트로는 TONEAREST·UPWARD가 `0x3fd3333333333334`, DOWNWARD·TOWARDZERO가 `0x3fd3333333333333`이다. 정확한 합이 두 이웃의 정가운데라서다. UPWARD의 `…05`는 printf 십진 변환도 현재 모드를 따른 결과다(요약 관찰 4-1).

### 9. 2⁵³ 넘는 ID

- [2⁵³, 2⁵⁴) 구간의 표현 가능한 값 간격은 2다. 홀수 정수는 이웃한 짝수로 반올림된다. 더 큰 구간은 간격이 4, 8, …로 커진다.
- JS `Number`와 JSON 숫자를 `double`로 읽는 파서는 binary64라 같은 일이 생긴다.
- 실험: `(long)(double) 9007199254740993L` = 9007199254740992. 9007199254740993은 …992와 …994의 가운데라 끝 비트가 0인 쪽(…992)으로 갔다.
- 대처: ID는 문자열로 보낸다([api-design/29](../../api-design/29-api-incidents/2-summary.md)).
