# architecture/01-number-systems-twos-complement — 정답

## 정답

### 1. 부호 없이 음수를 표현하는 법

- 비트는 그대로 두고 **읽는 규칙**을 바꾼다. 2의 보수는 맨 위 비트의 무게를 +2ʷ⁻¹ 대신 −2ʷ⁻¹로 읽는다(CS:APP 2.2.3).
- 덧셈기 관점
  - w비트 덧셈기는 결과의 하위 w비트만 남긴다. 2의 보수에서는 이 "넘친 자리 버리기"가 그대로 맞는 답이 된다(`1111 + 0001 = 0000`, 곧 −1 + 1 = 0).
  - 그래서 부호 있는 덧셈과 부호 없는 덧셈이 **같은 회로**를 쓰고, x86-64에서는 같은 명령(`add`)이다. 다른 것은 넘침 플래그(OF·CF) 해석뿐이다. 넘침 처리는 ISA마다 다르다(MIPS32는 예외를 내는 `ADD`와 내지 않는 `ADDU`를 둔다).
- 다른 방식의 불리함
  - 부호-크기: 0이 두 개(`0000`·`1000`)다. 부호를 보고 더할지 뺄지 갈라야 한다.
  - 1의 보수: 0이 두 개(`0000`·`1111`)다. 끝자리올림을 다시 더하는 단계가 필요하다.

### 2. `1100 1000`의 두 해석

- 무부호: 128 + 64 + 8 = **200**.
- 2의 보수: −128 + 64 + 8 = **−56**.
- 차이: 맨 위 비트의 무게만 +128과 −128로 다르다. 그 차이가 256 = 2⁸이다.
- −13 만들기

```text
   13 = 0000 1101
  ~13 = 1111 0010
   +1 = 1111 0011   → −13 (확인: −128 + 64+32+16 + 2+1 = −13)
```

### 3. 섞인 비교 예측

(실험, gcc 13.3.0, x86-64)

```text
-1 > 0u           -> 1
-1 > 0 (both int) -> 0
strlen(s) > want (size_t vs int) -> 0
```

- `m1 > z`: `int`가 `unsigned`로 바뀌어 4294967295 > 0 → 참(1)(N1570 §6.3.1.8).
- `m1 > 0`: 둘 다 `int` → 거짓(0).
- `strlen("abc") > -1`: `-1`이 `size_t`의 `SIZE_MAX`가 되어 3 > SIZE_MAX → 거짓(0).
- 경고: `-Wall`만이면 0개, `-Wall -Wextra`면 `-Wsign-compare` 경고 2개(C 모드에서 `-Wsign-compare`는 `-Wextra`가 켠다 — 실험).

### 4. 부호 확장과 0 확장

```text
  0xC8 = 1100 1000
  signed char  → int: 1111 1111 1111 1111 1111 1111 1100 1000 = 0xFFFFFFC8 = −56
  unsigned char→ int: 0000 0000 0000 0000 0000 0000 1100 1000 = 0x000000C8 = 200
```

- 부호 있는 타입은 맨 위 비트를 복사해 채우고, 무부호 타입은 0으로 채운다(CS:APP 2.2.6).
- gcc 13.3 `-O2` `objdump -d`: 부호 있는 쪽 `movsbl %dil,%eax`, 무부호 쪽 `movzbl %dil,%eax`.

### 5. Java 값

(실험, OpenJDK 21.0.12)

```text
byte 0xC8: buf[0]=-56, buf[0] & 0xFF=200, Byte.toUnsignedInt=200
-Integer.MIN_VALUE = -2147483648, Math.abs(MIN) = -2147483648
0xFFFFFFFF (int) = -1, 0xFFFFFFFFL = 4294967295
```

- `x = b`는 부호 확장 → −56. `b & 0xFF`는 `b`를 `int`로 넓힌 뒤(−56 = 0xFFFFFFC8) 하위 8비트만 남김 → 200.
- `-Integer.MIN_VALUE`는 2³¹이 `int`에 없어 다시 −2³¹이다.
- `0xFFFFFFFF`는 `int` 리터럴로 −1이다.

### 6. C11·C23의 부호 표현

- C11은 부호-크기·2의 보수·1의 보수 셋을 허용했다(N1570 §6.2.6.2).
- C23은 WG14 N2412를 반영해 2의 보수만 남겼다.
- 하지만 **표현**과 **넘침의 의미**는 다른 문제다. N2412는 "넘침을 모듈로로 정하는 것은 합의를 못 해 그대로 둔다"고 적는다. 그래서 `INT_MAX + 1`은 C23에서도 미정의 동작이다. 컴파일러는 그런 일이 없다고 가정하고 최적화한다([02](../02-integer-overflow-and-truncation/2-summary.md) 실험: `x + 1 < x`가 0으로 접힘).
- Java는 처음부터 2의 보수이고 넘침도 하위 비트로 정의했다(JLS §4.2, §15.18.2).

### 7. 길이 128 이상에서만 실패

- 원인: `int len = buf[off];`에서 `byte`가 부호 확장된다. 0x80~0xFF는 −128~−1이 된다. `new byte[len]`이 `NegativeArraySizeException`을 낸다.
- 고친 코드

```java
int len = Byte.toUnsignedInt(buf[off]);   // 또는 buf[off] & 0xFF
```

- 테스트 값: 0, 1, 127, **128**, 255. 경계 127 ↔ 128이 부호 비트가 켜지는 지점이다.

### 8. 언어마다 다른 바이트 해시

- "café"의 UTF-8은 `63 61 66 c3 a9`다. 앞 세 바이트는 0x80 미만이라 부호 해석과 상관없다. `c3`·`a9`는 Java `byte`로 −61·−87, C `unsigned char`로 195·169다.
- 실험: Java `byte` 그대로 94414350, Java `b & 0xFF` 94422542, C `unsigned char` 94422542.
- 명세에 적을 것: "바이트는 0~255 무부호로 더한다", 결과 폭(32비트)과 넘침 규칙(2³² 모듈로). 교차 언어 테스트 벡터에 0x80 이상 바이트를 넣는다.
