# architecture/18-pipelining-and-branch-prediction — 정답

## 정답

### 1. 처리량은 늘고, 한 명령의 지연은 그대로

- 파이프라인은 단계마다 다른 명령을 동시에 처리해 **처리량**(단위 시간당 끝나는 명령 수)을 늘린다. 한 명령이 F부터 W까지 가는 **지연**은 줄지 않는다. 단계 사이 레지스터 때문에 오히려 조금 늘 수 있다(CS:APP 4.4).
- 명령 3개: 순차 처리 5 × 3 = 15칸, 파이프라인 5 + 2 = 7칸. 그 뒤로는 칸마다 하나씩 끝난다.

### 2. 두 해저드

```text
  데이터: mov (%rdi),%rax ; add %rax,%rbx     ← add가 rax를 바로 쓴다
          처리: 결과를 다음 명령으로 바로 넘김(forwarding), 메모리 읽기 직후면 한 칸 멈춤(stall)
  제어:   cmp $0x7f,%edx ; jle L              ← 다음에 가져올 명령이 비교 결과에 달렸다
          처리: 분기 예측으로 한쪽을 미리 가져와 실행, 틀리면 버림
```

- CS:APP 4.5.5 Pipeline Hazards 절이 이 둘과 처리법을 다룬다.

### 3. 2비트 포화 카운터와 TTTN

```text
  0(강 안감) ⇄ 1(약 안감) ⇄ 2(약 감) ⇄ 3(강 감)     T면 오른쪽(+1), N이면 왼쪽(−1), 양끝은 제자리
  예측: 0·1 → 안 감,  2·3 → 감
```

- 실험(`predictor.py`): 1비트 50.00%, 2비트 75.00%.
- 1비트는 N에서 한 번 틀리고, 직전이 N이라 다음 T도 "안 감"으로 예측해 또 틀린다. 4번 중 2번 틀린다.
- 2비트는 N 한 번으로 3 → 2로만 내려가 여전히 "감"을 예측한다. 4번 중 N 한 번만 틀린다.
- 직전 3개 결과마다 카운터를 따로 두면(hist3) 100%다. 패턴 주기를 이력이 가려낸다.

### 4. 정렬 vs 무작위 (Java 21)

- 실험(Temurin 21.0.12, `--cpus=2`, 집필 3회 + 점검 2회): 조건 분기 판이 무작위 683~804 ms, 정렬 56~73 ms(정렬을 먼저 돌린 첫 라운드 95~148 ms 제외). 약 10~13배.
- 브랜치리스 판은 무작위 128~243 ms, 정렬 145~220 ms로 순서에 둔감했다.
- 해석: 무작위 조건은 예측 적중률이 약 50%(시뮬레이션 50.25%), 정렬은 99.99%다. 그래서 시간 차의 대부분은 예측 실패로 버린 일이라고 보는 것이 유력한 해석이다. perf를 못 써서 실패 횟수를 직접 세지 못했고 JIT 기계어도 열어 보지 않았으므로 확정은 아니다.

### 5. C `-O2`에서 차이가 사라진 이유

- 분기 예측기가 사라진 것이 아니라 **예측할 분기가 사라졌다**. `objdump -d`로 보면 gcc가 `-O2`에서는 루프를 SSE2로 벡터화해 비교 결과를 마스크(`pcmpgtd` → `pand`)로 더했다. `-O1`에서는 `if`를 `cmp $0x7f,%esi ; cmovg %rdx,%rcx`로 바꿨다.
- `cmov`는 두 값을 다 준비해 두고 조건으로 고른다. 벡터 마스크도 모든 원소를 같은 명령으로 처리한다. 둘 다 데이터 순서와 무관하다(CS:APP 3.6.6).
- 확인할 것: 실제 기계어에 조건 분기(`jle`·`jg`)가 있는지. `-fno-if-conversion -fno-if-conversion2 -fno-tree-vectorize`로 분기를 남기자 무작위 0.950~1.090s vs 정렬 0.070~0.135s로 차이가 돌아왔다.

### 6. 브랜치리스가 지는 경우

- 분기 결과가 한쪽으로 쏠리거나 패턴이 있어 예측이 잘 맞을 때다. 그때 분기는 거의 공짜이고, 브랜치리스는 양쪽 계산을 다 한다.
- 실험(Java): 정렬된 배열에서 분기 판 56~73 ms, 브랜치리스 145~220 ms. 약 2.5배 느렸다.

### 7. 배치 40분 — 입력 순서 가설

- 가설: 뜨거운 루프에 데이터 의존 조건 분기가 있다. 정렬된 입력에선 예측이 맞았고, 섞인 입력에선 절반쯤 틀린다.
- 확인 실험: 오늘 입력을 정렬한 사본으로 같은 배치를 돌린다. 어제 시간으로 돌아오면 가설이 맞을 가능성이 크다. 브랜치리스 판이 순서에 둔감한지도 본다. 가능하면 `perf stat -e branch-misses`로 실패 수를 직접 본다.
- 대처: 입력을 정렬·분할하는 단계를 넣거나, 그 조건을 브랜치리스로 바꾼다. 대표 분포(정렬/섞임) 둘 다로 회귀 테스트를 둔다.

### 8. 이진 탐색 3갈래 비교

- 이진 탐색에서 "왼쪽/오른쪽" 결과는 찾는 키가 고르게 퍼져 있으면 단계마다 반반에 가까워 예측이 약 50% 근처로 떨어진다(키 분포가 치우치면 더 잘 맞는다).
- "같음" 검사를 먼저 하면 비교 분기가 하나 더 생긴다. 대부분 "같지 않음"이라 이 분기는 잘 맞지만, 루프 본문이 길어지고 분기 수가 는다.
- 그래서 비교 횟수로는 이겨도 실제 시간으로 질 수 있다([algorithm/06](../../algorithm/06-binary-search/2-summary.md)). 분기를 조건부 이동으로 바꾼 브랜치리스 이진 탐색이 쓰이는 이유다.

### 9. 예측 실패 1회의 값

- (1.04 − 0.085) s ÷ (65,536,000 × 0.5) = 0.955 s ÷ 32,768,000 ≈ 29 ns. 실패 1회를 직접 잰 값이 아니라, 가정한 실패 횟수로 시간 차를 나눈 **추정값**이다.
- 사이클로 바꾸지 않은 이유: 측정 중 클록이 고정돼 있지 않았다(주파수 관리자 `powersave`, 호스트 load average 약 10). 정렬 쪽 반복 1회가 약 1.3 ns(최대 4.8GHz면 약 6사이클)라 클록이 낮았는지 자원 경쟁이었는지 가를 수 없다. 실패율 50%도 시뮬레이션 가정이고, 시간 차 전체가 실패 비용이라는 것도 가정이다. 그래서 "이 환경에서 약 29 ns로 추정"으로만 말한다(점검 재실행 값으로는 약 27 ns).
