# architecture/18-pipelining-and-branch-prediction — 파이프라인과 분기 예측: 같은 데이터인데 순서만 바꾸면 10배 — 정리 (힌트)

## 해결하는 문제

명령 하나를 끝까지 처리한 뒤에 다음 명령을 시작하면, 회로 대부분이 대부분의 시간 동안 논다.

```text
  순차 처리 (명령마다 5단계를 혼자 다 거친다)
  명령1  F D E M W
  명령2            F D E M W
  명령3                      F D E M W          → 15칸에 명령 3개

  파이프라인 (단계마다 다른 명령을 동시에)
  명령1  F D E M W
  명령2    F D E M W
  명령3      F D E M W                          → 7칸에 명령 3개, 이후 매 칸 1개씩 완료
```

- *파이프라인(pipeline)*: 명령 처리를 여러 단계로 나누고, 단계마다 서로 다른 명령을 동시에 처리하는 방식. 한 명령의 지연은 줄지 않지만(단계 사이 레지스터 때문에 조금 늘 수도 있다) **처리량**이 는다(CS:APP 4.4.1).
  - F(Fetch, 가져오기) · D(Decode, 해독·레지스터 읽기) · E(Execute, 계산) · M(Memory, 메모리 읽기·쓰기) · W(Write back, 결과 쓰기). CS:APP의 Y86-64 PIPE가 이 다섯 단계다(4.5) [?].
- 그런데 조건 분기를 만나면 문제가 생긴다. 분기 결과는 E 단계에서야 나오는데, F 단계는 매 칸 다음 명령을 가져와야 한다.
- 해법: **결과를 찍고 미리 달린다.** 맞으면 이득, 틀리면 달린 만큼 버린다.
  - *분기 예측(branch prediction)*: 조건 분기가 갈지 안 갈지, 어디로 갈지를 결과가 나오기 전에 추측하는 하드웨어.

쉬운 예: 세탁 → 건조 → 개기 3단계 빨래방이다.
- 한 바구니가 건조기에 있을 때 다음 바구니를 세탁기에 넣는다. 세 기계가 동시에 돈다.
- "다음 바구니가 흰 빨래냐 색깔 빨래냐"를 미리 몰라서 세제를 미리 넣어 두면, 틀렸을 때 그 세탁을 버리고 다시 해야 한다.

똑같은 구조다.\
예측이 잘 맞는 데이터면 공짜로 빠르고, 예측이 안 맞는 데이터면 버리는 비용이 쌓인다.

실무 예:
- 같은 배열에 "128 이상만 더하기"를 했는데, 정렬된 배열이 무작위 배열보다 약 10배 빨랐다(아래 실험).
- 이진 탐색의 비교 3갈래가 비교 횟수로는 이겨도 실제 시간으로 질 수 있다([algorithm/06](../../algorithm/06-binary-search/2-summary.md)).

## 동작·원리

### 1. 해저드 — 파이프라인이 멈추는 세 가지 이유

```text
  데이터 해저드: 앞 명령 결과를 뒤 명령이 바로 쓴다
    mov (%rdi),%rax     F D E M W
    add %rax,%rbx         F D . E M W       ← M에서야 값이 나오므로 한 칸 쉼(load-use)
                                               나머지 경우는 E 결과를 바로 옆으로 넘김(forwarding)
  제어 해저드: 다음에 가져올 명령이 분기 결과에 달렸다
    cmp ; jle L           F D E           ← 여기서 결과 확정
    ??? (다음 명령)         F D           ← 예측으로 미리 가져온 명령. 틀리면 버린다
  구조 해저드: 두 명령이 같은 장치를 동시에 쓰려 한다(장치를 늘려 피한다)
```

- *해저드(hazard)*: 다음 명령을 다음 칸에 바로 진행할 수 없게 만드는 의존·충돌. CS:APP 4.5.5 Pipeline Hazards가 데이터·제어 해저드와 처리법(멈춤 stall, 전달 forwarding, 예측)을 다룬다.
- 그림의 칸 수는 5단계 교과서 모델 기준이다. 실제 x86-64 코어는 단계가 훨씬 많고 비순차로 실행한다([19](../19-out-of-order-and-speculation/2-summary.md)). 단계가 많을수록 예측이 틀렸을 때 버리는 일이 늘어난다.

### 2. 2비트 포화 카운터 — 한 번 틀렸다고 바로 바꾸지 않는다

```text
  T(감)이면 오른쪽으로 한 칸, N(안 감)이면 왼쪽으로 한 칸. 양 끝에서는 제자리.

             T              T              T
  [0 강하게 ] ───▶ [1 약하게 ] ───▶ [2 약하게 ] ───▶ [3 강하게 ]
  [  안 감  ] ◀─── [  안 감  ] ◀─── [   감    ] ◀─── [   감    ]
   N: 제자리     N              N              N       T: 제자리

  예측: 0·1 → "안 감",  2·3 → "감"
```

- *포화 카운터(saturating counter)*: 0~3을 오르내리되 끝에서 더 넘어가지 않는 카운터. 분기마다 결과가 "감"이면 +1, "안 감"이면 −1.
- 1비트 예측(직전 결과를 그대로 다음 예측으로)은 루프 끝에서 한 번 빠질 때 두 번 틀린다. 2비트는 한 번 틀려도 예측을 바로 뒤집지 않는다.
- 실제 CPU는 분기 주소와 **최근 분기 이력**을 섞어 표를 찾는 더 복잡한 예측기를 쓴다. 구체적 구조는 공개되지 않은 부분이 많다 [?].

(실험, `predictor.py` — 분기 하나를 32,768번 흉내, Python 3.12.3)

```text
  pattern                  1-bit   2-bit   hist2   hist3   (적중률)
  random(v>=128)          50.28%  50.25%  50.24%  50.65%
  sorted(v>=128)          99.99%  99.99%  99.99%  99.98%
  loop 4-iter (TTTN)      50.00%  75.00%  75.00% 100.00%
  alternating (TN)         0.00%  50.00%  99.99%  99.99%
  hist2·hist3 = 직전 2·3개 결과마다 2비트 카운터를 따로 둔 예측기
```

- **결과가 반반인 무작위는 어떤 예측기도 못 맞힌다**(약 50%). 패턴이 없기 때문이다. 이 실험은 0~255 균등 난수라 `v>=128`이 1/2 확률이다. 한쪽으로 치우친 무작위라면 다수 쪽만 찍어도 50%보다 잘 맞는다.
- 정렬하면 "안 감 … 안 감, 감 … 감"으로 바뀌는 곳이 한 번뿐이라 거의 다 맞는다.
- 이력을 보면 짧은 반복 패턴(TN, TTTN)도 맞힌다. 이력 길이가 패턴 주기를 가려낼 만큼 길어야 한다(TTTN은 hist3부터 100%).

### 3. 실험: 정렬 vs 무작위 — 같은 덧셈, 순서만 다르다

```java
static long sumIf(int[] d) {
    long s = 0;
    for (int v : d) if (v >= 128) s += v;          // 조건 분기
    return s;
}
static long sumBranchless(int[] d) {
    long s = 0;
    for (int v : d) s += v & -((v - 128) >>> 31 ^ 1);   // v>=128이면 마스크 -1, 아니면 0
    return s;
}
// 마스크 식은 실험 입력(0~255)에서는 sumIf와 같지만 int 전 범위에서는 아니다. v < Integer.MIN_VALUE + 128이면
// v - 128이 넘쳐(JLS §15.18.2) 양수가 되고 마스크가 -1이 되어, sumIf가 버리는 값을 더한다.
// 0~255 난수 32,768개(시드 42). 같은 배열을 정렬한 사본도 만든다. 각 2,000번 반복을 5라운드.
```

(실험, Temurin 21.0.12, docker `--cpus=2`, `Branch.java` — 집필 3회(무작위 먼저 2회, 정렬 먼저 1회) + 점검 재실행 2회(순서별 1회)를 합친 범위)

```text
           sumIf(조건 분기)        sumBranchless
  random   683~804 ms              128~243 ms
  sorted   56~73 ms                145~220 ms
           (정렬을 먼저 돌린 실행의 첫 라운드는 95~148 ms — JIT 전)
```

- 같은 데이터·같은 결과(합 6,257,656,000)인데 조건 분기 판은 무작위 쪽이 약 11배 느리다. 정렬 순서를 먼저 돌려도 같았다.
- 브랜치리스 판은 데이터 순서와 무관하게 비슷하다. 대신 정렬된 경우엔 분기 판보다 2.5배쯤 느리다. 예측이 맞는 분기는 거의 공짜이고, 브랜치리스는 조건과 상관없이 계산을 다 한다.
- 해석: 시간 차이는 분기 예측 실패 때문이라고 본다. 데이터 순서만 바꿨고, 브랜치리스 판은 순서에 둔감하며, 아래 시뮬레이션의 적중률(50% vs 99.99%)과 방향이 맞다. 이 환경은 하드웨어 카운터(perf)를 쓸 수 없어 실패 횟수를 직접 세지 못했다. JIT가 만든 기계어도 열어 보지 않았다.

C로도 확인했다. 단, **컴파일러가 분기를 없애 버리면** 차이가 사라진다.

(실험, gcc 13.3.0, `branch.c`, 호스트에서 `taskset -c 0`(P 코어) — 같은 실험 구성)

```text
  -O1 / -O2 / -O3 (기본)             random ≈ sorted   (예: -O2 0.061~0.065s vs 0.067~0.069s)
     ↳ -O1 objdump: cmp $0x7f,%esi ; cmovg %rdx,%rcx      ← 분기 대신 조건부 이동(cmov)
     ↳ -O2·-O3 objdump: pcmpgtd → pand → paddq (xmm)       ← SSE2 자동 벡터화, 비교 결과를 마스크로
       (`-fopt-info-vec`: "loop vectorized using 16 byte vectors")
  -O2 -fno-if-conversion -fno-if-conversion2 -fno-tree-vectorize   (분기 유지)
     ↳ objdump: cmp $0x7f,%edx ; jle ...             ← 진짜 조건 분기
     random  branch 0.950~1.090s   branchless 0.075~0.160s
     sorted  branch 0.070~0.135s   branchless 0.076~0.162s     (집필 3회 + 점검 3회)
  같은 바이너리를 E 코어(taskset -c 20): random 0.898~0.929s / sorted 0.150~0.154s
```

- gcc 13.3은 `-O1`에서 이 `if`를 `cmovg`로 바꿨고, `-O2`·`-O3`에서는 루프를 SSE2로 벡터화해 비교 결과를 마스크(`pcmpgtd`)로 만들어 더했다. 어느 쪽이든 데이터에 따라 갈리는 분기가 없다. *조건부 이동(cmov)*은 두 값을 다 계산해 두고 조건에 맞는 쪽을 고르는 명령이라 예측할 분기가 없다(CS:APP 3.6.6).
- 분기를 강제로 남기자 무작위 쪽이 7.5~13.6배 느려졌다.
- 측정 조건: CPU 주파수 관리자 `powersave`, 다른 작업이 함께 돌던 호스트(load average 약 10)라 측정 시간 자체는 흔들린다. 정렬 쪽 반복 1회가 1 ns 남짓(대표값 0.070~0.085s ÷ 65,536,000 ≈ 1.1~1.3 ns, 최대 4.8GHz면 5~6사이클)이다. 클록이 최대보다 낮았는지, 다른 작업과 자원을 나눴는지는 이 환경에서 가를 수 없다(해석). 그래서 사이클 수로 환산하지 않고 비율만 본다.

### 4. 예측 실패 1회의 값

```text
  (random 시간 − sorted 시간) ÷ (반복 수 × 실패율)
  Java:  (≈0.72s − ≈0.062s) ÷ (65,536,000 × 0.5) ≈ 20 ns
  C   :  (≈1.04s − ≈0.085s) ÷ (65,536,000 × 0.5) ≈ 29 ns   (점검 재실행 ≈0.954s·≈0.073s로는 ≈27 ns)
```

- 이 환경 값이고 **측정값이 아니라 추정값**이다. 실패율 50%는 위 시뮬레이션으로 가정한 값이고, 시간 차 전체를 실패 비용으로 본 것도 가정이다.
- 교재는 예측 실패 비용을 사이클 단위로 다룬다(CS:APP 5.11.2 Branch Prediction and Misprediction Penalties). 구체적 사이클 수는 CPU마다 다르다 [?].

## 쓰이는 자료구조·알고리즘

- **2비트 포화 카운터 = 4상태 유한 상태 기계** — 입력(감/안 감)에 따라 상태가 옮겨 가고, 상태가 출력(예측)을 정한다. 커리큘럼 08(순차 논리·상태 기계)은 [08-sequential-logic-clock](../08-sequential-logic-clock/2-summary.md)에서 다룬다.
- **예측 표 = 분기 주소(와 이력)로 찾는 표** — 주소의 아랫비트로 칸을 고르는 해시 테이블과 같은 모양이다. 다른 분기가 같은 칸을 쓰면 서로 방해한다(충돌). [data-structure/05-hashmap](../../data-structure/05-hashmap/2-summary.md)
- **비트 마스크로 분기 없애기** — `v & -(조건)`처럼 0/−1 마스크로 고른다. [algorithm/29-bit-manipulation](../../algorithm/29-bit-manipulation/2-summary.md)
- **정렬·분할로 예측 가능하게 만들기** — 같은 조건끼리 모으면 분기가 한 방향으로 길게 이어진다. [algorithm/09-sorting-in-practice](../../algorithm/09-sorting-in-practice/2-summary.md)
- **이진 탐색의 분기** — 찾는 키가 고르게 퍼져 있으면 단계마다 좌우가 반반에 가까워 예측이 어렵다(키 분포가 치우치면 더 잘 맞는다). 그래서 브랜치리스 이진 탐색이 쓰인다. [algorithm/06-binary-search](../../algorithm/06-binary-search/2-summary.md)

## 적용 — 풀어나가는 법

### 1. 이런 증상이면 분기 예측을 의심한다

- 같은 코드·같은 양의 데이터인데 **데이터 순서나 분포**에 따라 처리 시간이 몇 배 바뀐다.
- 프로파일러에서 뜨거운 루프가 단순한데(덧셈·비교) 생각보다 느리다.
- 테스트 데이터(정렬된 ID, 같은 값 반복)로 잰 벤치마크보다 운영(무작위 분포)이 느리다.

### 2. 확인 순서

1. 뜨거운 루프의 조건문을 찾는다. 조건 결과가 데이터마다 들쭉날쭉한가?
2. **같은 데이터를 정렬해서** 다시 잰다. 크게 빨라지면 분기 예측이 원인일 가능성이 크다.
3. 브랜치리스 판과 비교한다. 순서에 둔감해지면 확증에 가깝다.
4. Java는 JMH처럼 워밍업·반복을 관리하는 하네스로 잰다. 위 실험처럼 첫 라운드(JIT 전)는 버린다.
5. 하드웨어 카운터를 쓸 수 있는 환경이면 `perf stat -e branches,branch-misses`로 실패율을 직접 본다 [?]. 이 환경은 `perf_event_paranoid=4`라 쓰지 못했다.

### 3. 대처

- **컴파일러에게 맡긴다**: 단순한 `if`는 C 컴파일러가 `cmov`나 벡터 마스크로 바꾼다(위 실험 `-O1` cmov, `-O2`부터 벡터화). JIT도 비슷한 변환을 할 수 있다 [?]. 손으로 바꾸기 전에 먼저 재 본다.
- **데이터를 예측 가능하게**: 미리 정렬하거나, 조건별로 나눠(partition) 두 루프로 처리한다.
- **브랜치리스로**: 마스크·`Math.max`·조건 연산자 등으로 분기 없는 코드를 노린다. `?:`·`Math.max`를 썼다고 분기가 사라진다는 보장은 없다(JLS §15.25는 고른 쪽만 평가한다고 정할 뿐, 기계어는 컴파일러·JIT가 정한다). 생성된 기계어로 확인한다. 예측이 잘 맞는 데이터에서는 오히려 느리다(위 실험 sorted 2.5배).
- **조건을 루프 밖으로**: 루프마다 같은 결과인 조건(설정 플래그 등)은 루프 밖에서 한 번만 검사한다. 이런 분기는 예측이 잘 맞아 비용은 작지만, 루프 본문이 단순해져 다른 최적화(벡터화 등)가 쉬워진다.

## 장애 시나리오와 대처

### 1. 배치 작업 시간이 입력 순서에 따라 10배 흔들린다

- **현상**: 어제는 5분 걸린 집계 배치가 오늘 40분 걸린다. 데이터 양은 비슷하다.
- **보이는 형태**: CPU 100%, I/O·GC·락 대기는 평소와 같다. 입력 파일이 어제는 키 순으로 정렬돼 왔고 오늘은 섞여 왔다.
- **원인**: 뜨거운 루프의 조건 분기가 정렬된 입력에선 예측이 맞고, 섞인 입력에선 절반쯤 틀린다. 위 실험에서 같은 연산이 약 11배 차이 났다.
- **대처**: 입력을 정렬·분할하거나 그 조건을 브랜치리스로 바꾼다. 재현은 "같은 데이터를 정렬/셔플해서 비교"로 한다.

### 2. 벤치마크에선 빨랐는데 운영에선 느리다

- **현상**: 성능 테스트를 통과한 코드가 운영 트래픽에서 기대보다 느리다.
- **보이는 형태**: 같은 서버·같은 JVM 설정인데 처리량이 벤치마크의 몇 분의 1이다.
- **원인**: 벤치마크 데이터가 단조로웠다(같은 값 반복, 정렬된 ID). 분기 예측이 거의 다 맞아 실제보다 빠르게 나왔다.
- **대처**: 운영 분포를 닮은 무작위 데이터로 잰다. 정렬된 입력과 섞인 입력을 둘 다 잰다.

### 3. "브랜치리스로 바꿨더니 더 느려졌다"

- **현상**: 분기를 마스크 연산으로 바꾼 최적화 PR이 오히려 회귀를 냈다.
- **보이는 형태**: 특정 데이터셋(대부분 한쪽 조건인 경우)에서만 느려졌다.
- **원인**: 분기가 한 방향으로 쏠려 예측이 잘 맞던 곳이었다. 브랜치리스는 양쪽 계산을 다 한다(실험: sorted에서 분기 60 ms vs 브랜치리스 160 ms).
- **대처**: 대표 분포 여러 개로 재고, 분기 결과가 들쭉날쭉한 곳에만 브랜치리스를 쓴다.

### 4. 마이크로벤치마크가 "차이 없음"을 냈다

- **현상**: 분기 예측 효과를 재려 했는데 정렬/무작위 시간이 같다.
- **보이는 형태**: C `-O2` 실험에서 0.061s vs 0.067s(점검 재실행 0.065s vs 0.069s).
- **원인**: 컴파일러가 분기를 `cmov`(`-O1`)나 벡터 마스크 연산(`-O2`·`-O3` 자동 벡터화)으로 바꿔 예측할 분기가 사라졌다. 측정 대상이 생각한 코드가 아니다.
- **대처**: `objdump -d`로 실제 기계어에 조건 분기(`jle`·`jg` 등)가 있는지 확인하고, 결론을 "이 컴파일러·옵션에서는"으로 한정한다.

## 핵심 문장

- 파이프라인은 명령 처리를 단계로 나눠 겹쳐서 처리량을 높인다. 한 명령의 지연은 줄지 않는다(오히려 조금 늘 수 있다).
- 조건 분기 결과는 늦게 나오므로 CPU는 예측해서 미리 달리고, 틀리면 달린 만큼 버린다.
- 결과가 반반인 무작위 조건은 어떤 예측기도 약 50%밖에 못 맞히고, 정렬된 조건은 거의 다 맞는다. 실험에서 같은 연산이 약 11배 차이 났다.
- 브랜치리스 코드는 순서에 둔감하지만 예측이 잘 맞는 데이터에선 분기보다 느리다.
- 컴파일러가 분기를 `cmov`로 바꾸면 효과가 사라진다. 결론 전에 기계어를 확인한다.
