# architecture/12-cache-organization — 정답

## 정답

### 1. 주소 분해

- 집합 수 = 48KB ÷ (12 × 64B) = 64. 이 호스트의 `number_of_sets`도 64다.
- 비트 0~5 오프셋(64B), 비트 6~11 인덱스(64개 집합), 비트 12 이상 태그.
- `0x1000`과 `0x2000`은 비트 6~11이 둘 다 0 → **같은 집합(0번)**, 태그만 다르다. 4096(=2^12)의 배수인 주소는 모두 이 L1의 같은 집합이다.

### 2. 세 방식의 맞바꿈

| | 비교기 | 충돌 미스 |
|---|---|---|
| 직접 사상 | 1개 | 많다(같은 인덱스면 즉시 쫓아냄) |
| N-way 집합 연관 | N개 | N개까지 버틴다 |
| 완전 연관 | 칸 수만큼 | 없다(용량 미스만) |

- L1은 매 사이클 가까이 접근하므로 빨라야 한다. 수백 개 태그를 동시에 비교하는 회로는 크고 느리다. 그래서 12개 정도의 집합 연관으로 타협한다(Drepper §3.3.1).

### 3. stride 4096, K=12 vs 13

- 실험(P코어 cpu2, 클록 약 0.81~0.87GHz): K=12까지 약 4.6~5.1사이클(L1 히트), **K=13에서 약 8.3~8.8사이클**, K=14 약 11.7~12.4, K=16~64 약 9.2~11.0사이클.
- 4160바이트 간격이면 K=64까지 약 4.5~5.5사이클로 전부 히트였다. 라인마다 인덱스가 하나씩 달라 집합이 흩어진다.

### 4. 용량 vs 집합

- 집합 하나에 N칸 넘는 라인이 몰리면, 캐시 전체에 자리가 남아도 미스가 난다(충돌 미스).
- 4096B 간격 라인 64개는 4KB어치(라인 64개 × 64B)지만 전부 집합 1개에 몰려 12칸을 다툰다. 48KB 캐시의 대부분이 비어 있어도 미스였다.

### 5. tree-PLRU

```text
          b0
        /    \
      b1      b2
     /  \    /  \
    A    B  C    D

  A 접근: 지나온 길(b0 왼쪽, b1 왼쪽)의 반대를 가리키게 → b0=오른쪽, b1=오른쪽
  희생자: b0(오른쪽) → b2가 가리키는 쪽 → C 또는 D
```

- 비트 N−1개로 끝난다. 정확한 LRU는 칸들의 사용 순서 전체를 유지해야 해서, 연관도가 커지면 회로가 비싸다(Drepper §3.3.5). 대신 가끔 가장 오래된 것이 아닌 칸을 버린다.
- 이 호스트 실험에서 13개 라인을 12칸에 돌린 지연(약 8~9사이클)이 정확한 LRU의 "매번 미스"(L2 약 15사이클)보다 낮았다. 정확한 LRU가 아니어서일 수도, 일정 간격이라 프리페처가 미리 가져와서일 수도 있다 — 카운터 없이 가르지 못했다.

### 6. write-back

- 같은 라인에 여러 번 써도 매번 아래 층에 쓰지 않는다. 보통 라인이 나갈 때 한 번 쓴다(다른 코어의 읽기 요청·`clwb` 같은 명령으로 그 전에 내려갈 수도 있다). write-through는 매 쓰기가 아래 층 트래픽이다(Drepper §3.3.3).
- 새 문제: 수정된 값이 한 코어의 캐시에만 있다. 다른 코어가 같은 주소를 읽으면 메모리의 옛 값이 아니라 그 dirty 라인을 받아야 한다. 이것을 맞추는 것이 일관성 프로토콜(MESI, 14번)이다.

### 7. false sharing 수치

- 서로 다른 P코어(cpu2·cpu4): 스레드 1개 390~498ms, 간격 8B 1437~2341ms, 간격 64B 398~455ms. 같은 라인이면 3~5배(E코어 쌍은 최대 약 6배) 느리고, 떼어 놓으면 스레드 1개 시간에 2배 일을 한다.
- 같은 코어의 두 하드웨어 스레드(cpu2·cpu3): 8B 897~905ms, 64B 1035~1056ms — false sharing 효과가 없었다. 두 스레드가 L1을 공유한다. 대신 실행 자원을 나눠 써서 약 2배 걸렸다.

### 8. `HashMap.hash()`와 stride 충돌

- 둘 다 "2의 거듭제곱 크기 표에서 하위 비트만으로 위치를 고른다"는 같은 구조다. 상위 비트만 다른 키(주소)들은 같은 칸에 몰린다.
- OpenJDK 21 주석이 그대로 말한다: 마스크 위 비트만 다른 해시들은 항상 충돌한다. 그래서 `h ^ (h >>> 16)`으로 상위 비트를 섞는다. 하드웨어도 L3 조각 선택에 주소 비트를 해시한다는 역공학 결과가 있다(Maurice 외 — Sandy Bridge~Haswell 대상. 해시는 조각 선택이고 조각 안 집합은 주소 비트로 직접 정해진다).

### 9. 인접 칸 카운터

1. 칸이 붙어 있는지 본다. `AtomicLongArray` 칸 간격은 8B → 8칸이 한 64B 라인이다.
2. 스레드 1개 vs 2개 총 처리량, 칸 간격 8B vs 128B 판을 비교한다. 이 호스트 Java 실험: 8B 1292~3272ms, 128B 424~556ms(한 번 877ms), 스레드 1개 414~477ms.
3. 다른 코어에서 재는지 확인한다(`lscpu -e=CPU,CORE,CACHE`). 같은 코어 쌍이면 차이가 안 보일 수 있다.
4. 고친다: `LongAdder`, 스레드 로컬 누적 후 합산, 또는 칸 간격 128B(스레드 i → 칸 i×16).

### 10. 1024에서만 느림

- 원인 후보: 행 길이 1024 × 4B = 4096B(2의 거듭제곱) → 열 방향 접근이 한 집합에 몰리는 충돌 미스.
- 확인: 행 길이를 1040처럼 조금 늘린 판과 비교한다. 이 호스트에서 열 방향 합이 11.8~13.5ns/원소 → 1.9~2.9ns/원소로 줄었다.
- 처방: 행 패딩, 행 방향 루프, 블록 단위 처리.
