# architecture/22-arch-symptom-index — 정답

## 정답

### 1. 일곱 증상과 깨진 가정

| 증상 | 깨진 가정 | 절 |
|---|---|---|
| `SIGSEGV`/`SIGBUS`/`SIGILL` | "주소·정렬·명령이 이 CPU에서 유효하다" | 1절 |
| `exec format error` | "실행 파일이 이 CPU의 ISA용이다" | 1절 |
| 음수 금액 | "값이 타입 폭(32비트) 안에 든다" | 2절 |
| 합계 불일치 | "실수 연산이 정확하고 순서와 무관하다", "증가가 원자적이다" | 3절 |
| 모지바케 | "쓰는 쪽과 읽는 쪽의 문자 부호화가 같다" | 4절 |
| 멀티스레드가 더 느림 | "스레드를 늘리면 일이 나뉜다"(라인·코어·락을 공유하지 않는다) | 6절 |
| SSD 지연 톱니 | "저장 장치 지연은 일정하다" | 8절 |

- 첫 질문이 기계와 값인 이유: 같은 코드가 x86에서 맞고 ARM에서 틀리거나(14-4), P코어와 E코어에서 지연이 갈린다(20-4). 값은 경계(2³¹, 2⁵³, 0x80) 근처일 때만 증상이 난다. 이 둘을 모르면 표의 어느 행인지 고를 수 없다.

### 2. 세 신호의 종료 코드

- NULL 쓰기 → `Segmentation fault`, exit 139(128 + SIGSEGV 11).
- `__builtin_trap()`(x86-64 gcc에서 `ud2`, `0f 0b`) → `Illegal instruction`, exit 132(128 + SIGILL 4).
- 잘린 `mmap` 파일 읽기 → `Bus error`, exit 135(128 + SIGBUS 7).
- 메시지는 죽은 프로세스가 아니라 부모 셸이 찍는다. 기본 로캘(한국어)에서는 "세그멘테이션 오류", "명령어가 잘못됨", "버스 오류"로 번역돼 찍혔다. 같은 사고의 로그 문구가 환경마다 달라지므로 종료 코드가 더 안정적인 검색 키다.

### 3. exit 139의 갈래

| 갈래 | 첫 확인 | leaf |
|---|---|---|
| 깊이 × 프레임 크기 > 스택 한도 | `ulimit -s`, 코어 `bt`의 깊이, 큰 지역 배열 유무 | 10-2 |
| 지역 버퍼 넘침(카나리 on이면 134. off면 security/24 실험에서 139였지만, 길이·배치에 따라 죽지 않고 계속 돌 수도 있다) | 입력 길이, 경계 없는 복사 | 10-3 |
| 음수 길이가 무부호로 바뀌어 거대 복사 | 직전 로그의 길이 값을 16진으로(`0xff…fc`), `-Wsign-compare` | 01-1 · 02-3 · 07-4 |
| 타이밍 위반·결함 코어 | 제조사 기본 클록으로 되돌리기, `taskset -c N`으로 코어 고정 재현 | 07-1 · 07-2 |

- 다른 영역 원인(해제된 메모리·NULL 등)은 [os/37](../../os/37-os-symptom-index/2-summary.md) 1절의 139 행으로 간다.

### 4. 16진으로 다시 읽기

- `4294967295` = `0xFFFFFFFF` → −1(또는 0 아래로 감긴 카운터)을 32비트 무부호로 보였다(01-5).
- `65536` = `0x00010000` → 리틀 엔디안 `00 01 00 00`(값 256)을 빅 엔디안으로 읽었다(06-2).
- `-1994967296` → 2³¹ − 1을 넘는 합을 `int`로 더해 2³²만큼 감겼다(02-1). 실제 값은 −1,994,967,296 + 4,294,967,296 = 2,300,000,000이다(계산).

### 5. 합계 불일치의 갈래

- 작은 소수 차이(`…0000004`, 차액 0.01) → 0.1·4.35 같은 10진 소수를 2진으로 정확히 담지 못함 → [03-1](../03-floating-point-ieee754/2-summary.md) · [03-3](../03-floating-point-ieee754/2-summary.md).
- 빌드 옵션마다 끝자리가 다름 → 벡터화가 덧셈 순서를 바꿈(`-ffast-math`, 21번 실험 2.919377e+05 ↔ 2.919381e+05) → [21-2](../21-simd-and-gpu/2-summary.md).
- 부하가 클수록 모자람 → `volatile int++` 비원자 갱신 유실 → [14-3](../14-cache-coherence-and-memory-ordering/2-summary.md).
- 수학 쪽 원인(큰 수 + 작은 수, 파국적 상쇄, 3치 논리)과 Kahan·웰퍼드 처방은 [math/16](../../math/16-math-symptom-index/2-summary.md) 4절.

### 6. 모지바케 판정과 복구 조건

- `é`(U+00E9)의 UTF-8은 `c3 a9`다. 이것을 Latin-1로 읽어 `Ã`(U+00C3)·`©`(U+00A9)가 되고, 그것을 다시 UTF-8로 저장하면 `c3 83 c2 a9`가 된다. 저장값 `xxd`에 `c3 83 c2 a9`가 보이면 이중 인코딩이다.
- 복구는 "한 번, 1:1 문자셋(Latin-1 등)으로 잘못 읽은 것"이 확실할 때만 역변환(Latin-1로 인코딩 → UTF-8로 디코딩)한다. 여러 번 거쳤거나 정상 값과 섞여 있으면 원본에서 다시 받는다(04-1).

### 7. 스레드를 늘려 느려질 때

- 덤프가 `RUNNABLE`뿐(락 대기 없음)이고 CPU만 오름 → 같은 64B 라인의 원자적 갱신(false sharing, 12-1). 칸 간격 128B·`LongAdder`로 비교.
- `vmstat`의 `r`(실행 대기)·`cs`(문맥 전환)가 크고 같은 락 대기 다수 → 코어 수 이상 스레드 경합(20-2). 20번 실험: CPU 2개에서 스레드 2개 96,535~105,211 ops/s → 32개 64,511~78,384 ops/s.
- 결론이 뒤집히는 이유: 두 스레드가 같은 물리 코어의 하드웨어 스레드(SMT 형제)에 배정되면 L1을 공유해 false sharing이 안 보인다(12-3, 12번 실험의 cpu2·cpu3). 다른 코어에 배정되면 크게 보인다. 그래서 결과에 CPU 번호·토폴로지를 적는다.

### 8. SSD 톱니 가르기와 근거 범위

- 가르는 법: 톱니 시각을 앱 GC 로그 시각과 `iostat -x 1`의 `w_await` 봉우리에 대조한다. JVM GC와 안 맞고 쓰기 구간의 `w_await`와 맞으며, 읽기만 하는 시간대에 평평하면 장치 쪽 원인을 의심한다(장애 4). `w_await`에는 큐 대기 시간도 들어가므로 SSD 내부 GC는 확정이 아니라 추가 확인이 필요한 후보다.
- 1차 출처 범위: OSTEP 44.4(읽기 수십 µs, 지우기 "a few milliseconds"), 44.8(GC는 유효 데이터를 읽고 다시 써서 "expensive")의 정성적 서술까지. 메커니즘 정본은 [systems/nand-flash](../../systems/nand-flash/2-summary.md) §8이고, 그 노트의 "100µs → 수 ms" 같은 수치는 출처가 밝혀져 있지 않아 이 색인의 근거로 쓰지 않았다. 톱니 재현 실험은 하지 않았다.
- 이 호스트 값(2026-10-07): `discard_max_bytes` = 2199023255040(TRIM 지원), `rotational` = 0, `fstrim.timer` = `enabled`, 루트 `ext4 rw,relatime`(`discard` 옵션 없음 → 주기적 TRIM).

### 9. 「하지 말 것」의 공통점과 경계값

- 공통점: 증상의 겉(표시 값·메시지·타임아웃·스레드 수)을 고치고 원인이 된 표현·하드웨어 가정은 그대로 둔다. 대신 열은 모두 "원인 층을 먼저 가르는 관찰"이다.
- 경계값 짝
  - `Integer.MAX_VALUE`, 2³¹초(2038-01-19T03:14:08Z) → 2절(음수 금액·카운터 넘침), [23](../23-arch-incidents/2-summary.md) 사건 5.
  - 길이 바이트 127·128·255 → 2절(부호 확장, 01-2).
  - `😀`(4바이트)·`🇰🇷`(코드 포인트 2개)·NFD 한글·터키어 로캘 → 4절(utf8mb3·절단·NFC/NFD·대소문자).
  - 리틀 엔디안 길이 `00 01 00 00` → 5절(06-2).
  - 크기를 L1·L3·RAM 경계 너머로, 정렬/셔플, 스레드 수 1·2·코어 수·코어 수 × 4 → 6·7절.
