# cache-split-lab — 인메모리 캐시를 가진 티어를 복제하면 무슨 일이 일어나는가

- 원본: `/home/jun/project/cache-split-lab` · 기간: 2026-07-17 ~ 2026-07-19 (git 커밋 기준) · 스택: Kotlin 2.1.20 + Spring Boot 3.5.0, nginx, Redis(arm D), k6, Docker Compose, Python(이론 계산)
- 상태: **완료** (Phase 1·0·4·D 실측 완료 / Phase 2 예비 1점 / Phase 3 취소 제안)

## 무엇을 알고 싶었나 — 질문·가설

서버가 버거울 때 scale-up 과 scale-out 은 총 자원이 같으면 보통 비긴다. 그런데 **앱이 인메모리 캐시를 들고 있으면 비기지 않는다** — 노드를 쪼개면 노드당 캐시가 절반인데, 라운드로빈 LB 는 키와 무관하게 뿌려서 두 노드가 각자 전체 키 공간을 상대해야 한다.

> 명제: **문제는 스케일아웃이 아니라 라운드로빈이다. 그리고 그게 얼마나 아픈지는 접근 분포가 정한다.**

- 히트율 붕괴가 접근 분포(Zipf skew)와 캐시 여유(키공간÷캐시)의 함수로 어떻게 변하는지 지도를 그린다.
- **B(라운드로빈)와 C(키 해시)의 우열이 뒤집히는 교차점**을 찾는다.
- 방법론 특징: 페이즈마다 `spec.md`(수학적 예측+판정 기준)를 **런 전에 커밋**하는 사전 등록 방식 — "숫자를 본 뒤 쓴 예측은 사후 합리화"라는 원칙.

## 실험 환경과 방법

물리 3대 구성 — 부하 생성기는 SUT 와 반드시 분리(같이 두면 포화점이 부하 생성기의 포화점이 된다):

```
개발·조종 (Victus, 24코어)
      │ 조종만
      ▼
부하 APC (jun-mini1, 8코어, k6) ──► SUT BPC (jun, 16코어: nginx + 앱×N + origin)
```

실험군 4개 — 총 캐시 용량(10,000)·총 CPU·총 스레드를 동일하게 고정하고 **배치만** 바꾼다:

| Arm | 배치 | 개념 대응 |
|-----|------|-----------|
| A | 1노드 × 캐시 10,000 | 캐시 스케일업 (자/ruler) |
| B | 2노드 × 5,000 + nginx 라운드로빈 | 나이브 스케일아웃 |
| C | 2노드 × 5,000 + nginx 키 해시(`hash $uri`) | 분할 스케일아웃 |
| D | 2노드(RR) + 공유 Redis 캐시 10,000 (CPU 총량에 redis 몫 포함) | 외부화 스케일업 |

- origin 은 실제 DB 가 아니라 CSV 인메모리 + 고정 지연(5ms) — 실 DB 는 버퍼 캐시가 arm 마다 다르게 데워져 효과를 상쇄한다.
- 기준소스: Che's approximation (LRU+Zipf 이론 히트율, `scripts/theory.py`) + 음성 대조군 + 교차 검증(앱 miss 합 ≡ origin 요청 수 등 sanity 9종).

### Phase 1 — 균등 분포(s=0), 15런: 히트율

| 키공간÷캐시 | A 1노드×10,000 | B 2노드 RR | C 2노드 키해시 | A→B 손실 |
|---|---|---|---|---|
| 0.5 | 1.0000 | 1.0000 | 1.0000 | 0.00%p |
| **1.0** | **1.0000** | **0.4999** | **1.0000** | **50.01%p** |
| 2.0 | 0.5007 | 0.2491 | 0.4996 | 25.16%p |
| 4.0 | 0.2528 | 0.1253 | 0.2527 | 12.75%p |
| 8.0 | 0.1250 | 0.0635 | 0.1246 | 6.15%p |

출처: `/home/jun/project/cache-split-lab/README.md` · `docs/phases/phase-1-uniform/result.md`

평균 지연으로 번역하면 비율 1.0 에서 A 0.49ms vs **B 3.14ms (6.41배)**, C 0.40ms — 노드를 한 대 더 띄웠더니 6.4배 느려졌고, nginx 설정 한 줄(`hash $uri`)로 원래대로 돌아온다.

> ⚠️ 원본의 자체 경고: 이 지연 수치는 **부하가 오염된 상태**에서 나왔다(명목 500 RPS 인데 잔여 워밍업 3,000 이 같이 흘렀다 — `phases/phase-1-uniform/result.md` §8). 큐가 안 생겨 지연 자체는 유효하다고 판단하지만 깨끗한 재측정 필요. 히트율은 RPS 무관이라 무사하고, 이론과 0.28%p 이내 일치가 그 증거.

이론 검증 — Che's approximation 이 실측 손실을 전 지점 **0.28%p 이내**로 맞혔다(비율 1.0: 실측 50.01%p vs 예측 50.00%p). 이게 리그(LRU 구현·Zipf 생성기·카운터·라우팅)의 신뢰 근거다.

출처: `/home/jun/project/cache-split-lab/docs/phases/phase-0-saturation/result.md` · `gate.md`

핵심 산수: C 무릎에서 핫 노드 부하 = 4000×0.628 = 2,512 ≈ 0.25CPU 노드 용량 2,500 (오차 0.5%) — **키 해시의 쏠림은 정확히 그만큼의 용량 손실로 번역된다.** (이론 예측 쏠림 69.6% 는 빗나감 — 실측 62.9%. top-2 키가 반대 노드에 떨어진 해시의 우연.)

## 종합 결론

- **s=0 의 정답(키 해시)이 s=1.5 의 오답이 된다** — 같은 배치 결정이 접근 분포에 따라 반대로 채점된다. "라운드로빈이 항상 진다"는 s=0 하나로 일반화한 오류.
- **"중복이 낭비다"는 틀렸다** — 균등 분포에서 B 두 캐시의 교집합은 무작위 기저선(5000/N)에 ±0.9%p 로 붙는다(중복 0). 중복 없는데 손실은 최대(50%p). 라운드로빈 아래에서 중복은 낭비가 아니라 **최적해**고, 낭비인 건 라운드로빈이다.
- 히트율 손실은 용량 손실로 번역된다: C 의 쏠림 62.9% → 무릎 −15%, 오차 0.5% 산수로 닫힘.
- 외부화(공유 Redis)의 청구서는 지연(+0.08ms)이 아니라 용량(무릎 60%)과 과부하 붕괴 모드.
- 이론(Che's approximation)이 실측 히트율을 0.28%p 이내로 재현 — "유도할 수 있는 건 유도하고, 유도 못 하는 것만 측정한다."

## 한계·남은 질문

- **부하 오염 재측정 미완**: Phase 1 지연 수치는 워밍업 잔여 3,000 RPS 오염 상태(러너 결함, 수정 커밋 `633d7fb`). 히트율은 무사.
- **설명 안 되는 것 하나**: 비율 0.5 에서 완전히 같은 조건인데 B 0.66ms vs C 0.41ms (60% 차이) — 원인 미상, 재현 확인 필요.
- 사전 등록 예측 8개 중 온전한 일치는 3개 — Phase 4 의 p50 기반 해석은 탐색적(사전 등록 지표는 p95).
- Phase 2(s=1)는 예비 1점만(손실 10.04%p vs Che 예측 10.14%p), 전 스윕 미실시. Phase 3(s=2)은 이론상 손실 0.01%p 라 취소 제안.
