# 08. Integration Scenario A — Concert Ticketing Commerce

01~07 Lab을 하나의 예매 흐름으로 합쳤을 때만 드러나는
타임아웃 연쇄 / 재시도 증폭 / 병목 이동 / 장애 전파 / 도메인 간 정합성을 검증하는 통합 실험

## Flow

```
Client
  ↓
Queue Server ─────────────────── (01) 대기열, 입장 토큰
  ↓
Seat Map Query ───────────────── (07) 캐시
  ↓
Seat Hold (TTL 5분) ──────────── (01) 좌석 선점
  ↓
Order Orchestrator ───────────── (03) 주문 Saga
 ├── Point Use ──────────────── (04) 포인트 차감 (복합결제 30%)
 └── Card Payment ───────────── (02) PG 결제
        ↓
Reservation Confirm
  ↓
Notification (예매 확정) ────── (06) 알림

Cross-domain Reconciliation Batch
```

## Load Baseline

기준은 가장 트래픽이 큰 01. Seat Reservation Lab을 따른다.

| 단계 | 부하 (파생값) | 도출 근거 |
|------|-------------|---------|
| 대기열 진입 | 동접 200,000명 | 01 Lab 기준 (스타디움 사례) |
| 입장 | 100 / 300 / 1,000 명/s | 01 Lab 변수 |
| 좌석맵 조회 | 약 5,000 RPS | 입장 사용자 1만 명 × 2초 주기 |
| 좌석 선점 시도 | 입장 속도 × 재시도 계수 | 이선좌 재시도 포함 |
| 주문·결제 | 총 약 5,000~6,000건 / 20분 | 10,000석, 1인 최대 2매 |
| 포인트 차감 | 주문의 30% | 03 Lab 복합결제 비율 |
| 예매 확정 알림 | 확정 건수와 동일 | 06 Lab 트랜잭셔널 |

## Questions (통합에서만 생기는 문제)

1. 선점 TTL(5분)보다 결제 타임아웃 × 재시도 합이 길어지면?
2. 클라이언트 · 주문 · 결제가 각각 재시도하면 PG에는 몇 배의 요청이 가는가?
3. 대기열로 예약 API를 보호했더니 병목이 어디로 옮겨갔는가?
4. 알림 발송사가 느려질 때 예매 확정 응답까지 느려지는가?
5. PG 지연 중 좌석이 만료되어 다른 사람에게 팔렸다면?
6. Redis 장애가 좌석맵 · 선점 · 대기열에 동시에 영향을 주면?
7. 모든 도메인의 최종 수치가 서로 일치하는가?

| S6. 복합 | S2 + S4 | 장애 전파 경로 |
