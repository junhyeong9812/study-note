# 06. Notification Lab

외부 발송사를 통한 알림 전달에서 발생하는
중복 발송 / 유실 / 발송사 쿼터 초과 / 대량 발송 중 긴급 알림 지연을 다룬 실험 프로젝트

## Load Baseline (근거)

| 사례 | 내용 | 출처 |

**채택 기준**: Mock 발송사 쿼터 분당 600,000건(초당 약 10,000건), 캠페인 100만 명 발송과 트랜잭셔널 알림 동시 진행

## Questions

1. 같은 알림이 두 번 발송됐다면?
2. 발송사가 429를 반환하면 언제, 몇 번 재시도할까?
3. 100만 명 캠페인 발송 중에 예매 확정 알림이 뒤로 밀린다면?
4. 발송 요청은 성공했는데 우리 DB에 기록하기 전에 서버가 죽었다면?
5. 발송사가 느려질 때 알림을 호출한 주문 API까지 느려진다면?
6. 쿼터를 넘지 않으려면 발송 속도를 어떻게 조절할까?

## Architecture

```
Domain Events (예매 확정, 주문 완료, 상회 입찰 ...)
  ↓
Notification API (idempotency key = event_id + channel)
  ↓
Outbox → Queue
 ├── High Priority  (트랜잭셔널)
 └── Low Priority   (캠페인)
        ↓
   Sender Workers ── Rate Limiter (토큰 버킷)
        ↓
   Mock Provider ←── 쿼터 / 429 / 5xx / 지연 주입
        ↓
   Delivery Log (발송 결과) ── 실패 N회 → DLQ
```
