# 05. Auction Lab

실패가 정상 결과인 경합과 시간 기준의 정확성을 중심으로
최고가 갱신 / 마감 직전 입찰 폭주 / 마감 시각 판정 / 낙찰 후 결제 실패를 다룬 실험 프로젝트

## Load Baseline (근거)

| 사례 | 관찰된 내용 | 출처 |
|------|-----------|------|
| eBay vs Amazon 경매 연구 | 고정 마감(eBay)은 마감 직전 입찰 비중이 크고, 무입찰 10분까지 연장하는 방식(Amazon)은 훨씬 작음 | [Roth & Ockenfels (AER)](https://www.cs.princeton.edu/courses/archive/spr08/cos444/papers/roth_ockenfels02.pdf) |
| 같은 연구 요약 | eBay 경매의 37%에 마지막 1분 입찰, Amazon은 1% 미만 | [NYT 칼럼 사본](https://home.uchicago.edu/~hortacsu/nyt.htm) |
| 후속 연구 | eBay 경매의 절반 이상이 마지막 10분에, 10% 이상이 마지막 10초에 입찰을 받음 | [CESifo WP987](https://www.cesifo.org/DocDL/cesifo_wp987.pdf) |
| 이론 해석 | 마감 순간 트래픽 급증으로 입찰이 누락될 수 있다는 점까지 입찰 전략에 반영됨 | [Hendricks 외](https://users.ssc.wisc.edu/~hendrick/publications\LastMinuteBidding.pdf) |

**채택 기준 (제안값)**: 동시 진행 경매 1,000개 + 핫 경매 1개(참여자 10,000명), 핫 경매 입찰의 50%가 마지막 10분, 10%가 마지막 10초에 도착

## Questions

1. 마감 1초 전에 같은 금액 입찰이 동시에 들어오면?
2. 입찰 실패(상회 입찰됨)를 에러로 볼 것인가, 정상 응답으로 볼 것인가?
3. 요청 도착 시각과 DB 처리 시각 중 무엇이 마감 기준인가?
4. 고정 마감과 연장 마감 중 무엇이 서버에 유리한가?
5. 최고가 갱신과 입찰 이력 저장이 어긋났다면?
6. 낙찰자가 결제하지 않으면 차순위에게 넘길까, 재경매할까?
7. 한 경매 행(row)에 입찰이 몰리는 핫스팟을 어떻게 풀까?

## Architecture

```
Client
  ↓
Bid API
  ↓
Bid Processor (방식 비교)
 ├── A. CAS 조건부 UPDATE (current_price + min_increment <= bid AND end_time > now)
 ├── B. 비관적 락
 ├── C. Redis Lua 스크립트
 └── D. 경매별 단일 처리 큐 (파티션 키 = auction_id)
        ↓
   Bid Log (append-only) + Auction (current_price, winner)
        ↓
   Outbid Event → 상회 입찰 알림 (→ 06. Notification Lab)

Close Scheduler → 낙찰 확정 → 주문 생성 (→ 03. Order Lab)
```
